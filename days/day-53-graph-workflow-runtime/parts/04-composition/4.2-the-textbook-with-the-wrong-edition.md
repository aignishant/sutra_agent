# 4.2 — The textbook with the wrong edition

## One-line answer

Most ADK material on the internet is 1.x, and this part is the translation drill: given a
`SequentialAgent` with `sub_agents`, name what is wrong with it under **trap #1** and write the graph
it becomes — because you will meet ten of these before you meet one written for 2.x.

## The story

The reading list said *chapter 7, questions 1 to 12*, and you have been doing them all evening.

The next morning it turns out that half the class did completely different questions. Yours were about
one thing and theirs were about another, and for a while everyone assumes somebody misheard.

Then somebody puts two copies of the book side by side. Same title. Same cover, near enough. Different
edition. In yours, chapter 7 is one topic; in theirs a chapter was added earlier in the book and
everything after it shifted by one.

Nothing you did was careless. You read the instruction correctly and executed it correctly against the
wrong reference. And the reason it took a morning to find is that both books agreed about almost
everything — the vocabulary was the same, the notation was the same, most of the chapters were the
same, and the disagreement was in the numbering, which is exactly the sort of thing nobody thinks to
check.

## The idea in plain language

ADK 2.0 went GA on 2026-05-19 and introduced the graph Workflow Runtime. Everything written before
that date, and a great deal written after it by people working from older material, uses the 1.x
composition model.

The two are similar enough to be dangerous. Same package name. Same `Agent` class. Same `instruction`
and `model` fields. The disagreement is in how things are **composed**, which is the part that does not
look like it needs checking.

Here is the translation table. It is short, and it is the whole of the porting job:

| 1.x, in tutorials | 2.x, what it becomes |
| --- | --- |
| `SequentialAgent(sub_agents=[a, b, c])` | `Workflow(edges=[("START", a, b, c)])` |
| `ParallelAgent(sub_agents=[a, b])` | `Workflow(edges=[("START", (a, b)), ...])` + a `JoinNode` |
| `LoopAgent(sub_agents=[a], max_iterations=n)` | a routed edge back, plus a counter in state |
| an agent that decides which sub-agent runs | a node emitting a `route`, and routed edges |
| custom agent collecting events into a list | a node that `yield`s ([1.5](../01-the-node/1.5-say-it-as-you-go.md)) |
| the "root agent" containing everything | the `Workflow` **is** the root; agents are nodes in it |

The last row is the mental shift, and it is why *"port compositions to the node model; don't force
everything through agent-tree idioms"* is worded as a warning. The tempting half-port is to keep the
tree and wrap it: build the same nesting, then put the top of it into a `Workflow` as one node. It
runs. It is also the secretary from [4.1](4.1-one-secretary-or-one-register.md), still in the middle,
now with a graph drawn around him.

Two facts you can check yourself rather than taking on trust, both verified against `google-adk==2.7.1`
on 2026-09-05:

- `SequentialAgent`, `ParallelAgent` and `LoopAgent` all emit a `DeprecationWarning`
  ([4.3](4.3-the-bus-pass-with-a-date-on-it.md)).
- `sub_agents` on `BaseAgent` emits nothing. It is not deprecated. Delegation between agents still uses
  it, and that is Day 55.

## Why Sutra needs it

You are going to search for help. On Day 56, planning; on Day 57, orchestrator patterns; on Day 62,
human-in-the-loop. Every one of those searches will return 1.x material near the top, because it has
had longer to accumulate links.

The failure mode is not that you copy something and it errors — an error would be a kindness. It is
that you copy the 1.x *shape* into a 2.x codebase, it works, and you have quietly reintroduced the
tree: two copies of a node instead of one, a wrapper agent whose only job is to be in the middle, and a
flow that is no longer readable from the edge list because half of it is nested inside an object.

## The mechanism

Here is a 1.x snippet of the sort you will find. Read it before reading the criticism.

```python
# 1.x - a shape you will meet in tutorials. Do not copy this into a 2.x project.
classify = Agent(name="classify", model="gemini-2.5-flash", instruction="Classify the ticket.")
research = Agent(name="research", model="gemini-2.5-flash", instruction="Find similar tickets.")
draft = Agent(name="draft", model="gemini-2.5-flash", instruction="Draft a reply.")

triage = SequentialAgent(name="triage", sub_agents=[classify, research, draft])
```

**Line by line:**

- Three agents, each fine on its own — pinned models, clear instructions. Nothing wrong here, and this
  half ports across unchanged.
- `SequentialAgent(sub_agents=[...])` is the whole problem. It is **trap #1**: composition expressed by
  nesting objects inside a special agent class.
- The order — classify, then research, then draft — exists only as list order inside an object. There
  is no edge list to read, no diagram to generate, and nothing to validate.
- `classify` now has `triage` as its parent and cannot be used in a second flow
  ([4.1](4.1-one-secretary-or-one-register.md)).
- In 2.7.1 this also emits a `DeprecationWarning`.

Four specific criticisms, then, and it is worth being able to say them in this order:

1. **The flow is not data.** You cannot print it, diagram it or validate it; it is list order inside an
   object.
2. **The steps are captured.** Each agent has one parent, so none of them is reusable.
3. **It cannot express a merge or a branch.** The moment `research` needs to fan out to two searches
   and rejoin, `SequentialAgent` has nothing to offer and you reach for a nested `ParallelAgent`.
4. **It is deprecated**, with a removal planned.

The port:

```python
# 2.x - the same process, as a graph.
triage = Workflow(
    name="triage",
    edges=[("START", classify, research, draft)],
)
```

**Line by line:**

- One `Workflow`, one chain, three edges after expansion
  ([2.2](../02-the-edge/2.2-the-chain-that-is-a-list-of-edges.md)).
- The three `Agent` objects are **unchanged** — they are nodes because `LlmAgent` is a `BaseNode`
  ([1.2](../01-the-node/1.2-the-four-things-that-can-be-a-node.md)). Porting did not touch the part
  that has the prompts in it.
- No agent has a parent now, so any of them can be used in a second graph.
- The flow is `triage.graph.edges`: printable, diagrammable, and validated at construction.

And the port that is *not* good enough, which is the one to be able to recognise in a review:

```python
# The half-port. It runs, and it is still a tree.
inner = SequentialAgent(name="inner", sub_agents=[classify, research, draft])
triage = Workflow(name="triage", edges=[("START", inner)])
```

**Line by line:**

- `Workflow` on the outside, so it looks ported.
- The composition is still `sub_agents` inside `inner`, so all four criticisms above still apply — the
  flow is still not data, the agents are still captured, and a branch still cannot be added without
  unpicking the nesting.
- The graph has exactly one real node. An edge list of length one is the tell.

## When it breaks

The break is not an exception; it is a code review six weeks later. But there is one hard edge that
turns the half-port into an actual wall, and it is in the second sentence of that warning:

```text
Workflow cannot yet be used as an LlmAgent sub-agent.
```

Nesting goes one way. A `Workflow` can contain an agent; an agent cannot have a `Workflow` as a
sub-agent. So the moment a half-ported tree needs a graph *inside* it — the moment `research` needs to
fan out — you cannot nest a `Workflow` under the `SequentialAgent`, and the half-port has to be
undone properly.

That is worth knowing before you choose the half-port, because it is the reason the half-port is a
detour rather than a shortcut.

The second break is subtler and it is about reading rather than writing: a 1.x snippet that uses event
fields which no longer exist. That is **trap #2** (event fields were renamed and restructured in 2.0),
and it produces an `AttributeError` on an event object rather than anything about composition. Day 7
covered the renames. When a copied snippet fails on an event attribute, it is not that your event is
malformed — it is that the snippet is from the other edition.

## In production

**What a professional writes instead.** They date every piece of external material before reading it,
and they check one thing: does the composition use `sub_agents` or an edge list? That single question
sorts 1.x from 2.x faster than any version banner, because the banner is often absent and the shape
never is.

**What degrades at scale.** A codebase with both shapes in it. Some flows as graphs, some as nested
agents, and a team that has to know which is which before making any change. The graph tooling — the
diagram generator in [4.4](4.4-the-floor-plan-by-the-lift.md), the node-set assertion in
[3.3](../03-the-graph-is-checked/3.3-the-switch-that-turns-nothing-on.md) — only sees the graphs, so
the nested flows are invisible to exactly the tools that were supposed to make the system legible.

**The failure that only appears with real traffic.** A half-ported flow behaves identically until you
need to add a branch under load — a fallback provider, a fast path for a common category. The graph
version is an edge; the nested version is a restructure, and it arrives on the day you least want one.
The cost of the half-port is not paid when it is written.

**The review comment a senior engineer leaves:** *"This is a `SequentialAgent` inside a `Workflow` with
a single edge. That is the 1.x shape with a 2.x wrapper — the flow is still list order inside an
object, so it does not validate, does not diagram, and the three agents are captured by their parent.
Unpick it into edges. It is a four-line change now and a two-day change once the fan-out lands."*

**The interview question:** *"You find a tutorial that composes agents with `sub_agents` in a
`SequentialAgent`. What do you do?"* A confident answer: *"Take the agent definitions and throw away
the composition. The prompts and model pins port across unchanged — an `LlmAgent` is already a node.
The `SequentialAgent` becomes a chain in an edge list, `ParallelAgent` becomes a tuple destination plus
a join, and `LoopAgent` becomes a routed edge back with a counter in state. What I would not do is wrap
the `SequentialAgent` in a `Workflow` and call it ported — it runs, but the flow is still list order
inside an object, so nothing validates it and the agents still have a parent each. And a `Workflow`
cannot be an `LlmAgent` sub-agent, so that shortcut dead-ends the first time you need a branch."*
