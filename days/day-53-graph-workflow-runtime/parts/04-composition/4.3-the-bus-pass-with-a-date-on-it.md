# 4.3 — The bus pass with a date on it

## One-line answer

`SequentialAgent`, `ParallelAgent` and `LoopAgent` still work in 2.7.1 and each one now says
*"deprecated in favor of Workflow and will be removed in a future version"* on construction — which is
a date, not an opinion, and the right response is to port rather than to silence the warning.

## The story

The conductor hands your pass back and says it is fine, and then adds: *"from next month this one
stops."*

You are on the bus. Nobody has thrown you off. The pass worked — he punched it, you sat down, the
journey is happening exactly as it always does. Everything about today is normal.

But he has told you something that today does not contain. There is a date, it is not far away, and on
the other side of it this piece of card is not a pass, it is a piece of card. What you do about that is
your business. You can get the new one this week, in the office near the depot, in about ten minutes.
Or you can do nothing, and find out on the first of the month, at seven in the morning, at the bus
stop, with nowhere to buy one and somewhere to be.

The information arrived early and cheaply. The whole question is whether you act on it while it is
cheap.

## The idea in plain language

A **deprecation warning** is a message a library prints when you use something it intends to remove. It
is not an error. The code runs. It is an announcement with a schedule attached.

In `google-adk==2.7.1`, three classes carry one:

- `SequentialAgent` — ran its `sub_agents` one after another
- `ParallelAgent` — ran its `sub_agents` at the same time, isolated from each other
- `LoopAgent` — ran its `sub_agents` repeatedly until escalation or `max_iterations`

All three say the same two sentences, and both matter:

> *"X is deprecated in favor of Workflow and will be removed in a future version. Workflow cannot yet
> be used as an LlmAgent sub-agent."*

The **first** sentence is the port instruction: these three became shapes of edges, per the table in
[4.2](4.2-the-textbook-with-the-wrong-edition.md).

The **second** sentence is a limitation stated honestly, and it is the reason the word *"yet"* is
there. Nesting currently runs one way: a `Workflow` may contain an `LlmAgent`, but an `LlmAgent` may
not have a `Workflow` as a sub-agent. So if you have an agent that delegates to a sub-agent, and that
sub-agent's job is really a whole graph, you cannot simply swap the sub-agent for a `Workflow` today.
The `Workflow` has to go above.

Being precise about what is and is not deprecated, because getting this wrong in either direction
causes work:

| | status in 2.7.1 |
| --- | --- |
| `SequentialAgent`, `ParallelAgent`, `LoopAgent` | **deprecated**, removal planned |
| `BaseAgent.sub_agents` | **not deprecated** — it is delegation, and it is Day 55 |
| `LlmAgent` / `Agent` | not deprecated; it is now also a node |

## Why Sutra needs it

Principle 14: *if reality changes, the plan is amended first*. A deprecation is reality changing on a
schedule, and the way this curriculum handles it is to notice it on the day it is visible rather than
on the day it breaks.

There is a practical reason too. Days 54 through 59 build the whole triage graph. If any of it is built
on a deprecated class, then some later day — quite possibly Day 84, in the middle of wiring
observability — becomes a porting day instead. Building on the replacement now costs nothing, because
the replacement is what this entire day is about.

## The mechanism

Construct one of each and capture what Python emits.

```python
"""4.3 - the three workflow agent classes, and what ADK 2.7.1 says when you build one."""

import warnings

from google.adk import Agent
from google.adk.agents import LoopAgent, ParallelAgent, SequentialAgent


def children() -> list[Agent]:
    """Fresh agents each time: an agent in a tree may have only one parent."""
    return [
        Agent(name="classify", model="gemini-2.5-flash", instruction="Classify the ticket."),
        Agent(name="draft", model="gemini-2.5-flash", instruction="Draft a reply."),
    ]


BUILDERS = {
    "SequentialAgent": lambda: SequentialAgent(name="old_seq", sub_agents=children()),
    "ParallelAgent": lambda: ParallelAgent(name="old_par", sub_agents=children()),
    "LoopAgent": lambda: LoopAgent(name="old_loop", sub_agents=children(), max_iterations=2),
}
```

**Line by line:**

- `def children()` returns a **fresh pair every call**, and that is not tidiness. Reusing one pair
  raises `Agent 'classify' already has a parent agent` on the second builder — the tree constraint
  from [4.1](4.1-one-secretary-or-one-register.md), met accidentally while writing this script.
- `from google.adk.agents import LoopAgent, ParallelAgent, SequentialAgent` — still importable, still
  exported. Deprecated is not gone.
- `max_iterations=2` on `LoopAgent` is the 1.x way of bounding a loop. In the graph model that becomes
  a counter in `ctx.state` and a routed edge
  ([3.2](../03-the-graph-is-checked/3.2-both-waiting-for-the-other-to-leave.md)) — more code, and
  visible code, which is the trade.
- The builders are lambdas so construction happens *inside* the warning-capturing block below.

```python
for label, build in BUILDERS.items():
    with warnings.catch_warnings(record=True) as caught:
        warnings.simplefilter("always")
        build()
    messages = [str(w.message) for w in caught] or ["(no warning raised)"]
```

**Line by line:**

- `warnings.catch_warnings(record=True)` collects warnings into a list instead of printing them.
- `warnings.simplefilter("always")` overrides Python's default filters for the block. It matters less
  here than you might expect — these are three different classes raising from three different lines, so
  all three appear either way. It matters enormously in the situation `hidden.py` measures below, where
  one line fires repeatedly and the default filter reports it once.
- `or ["(no warning raised)"]` makes a negative result visible rather than an empty line, so the script
  can also *disprove* the claim if a future version changes.

```bash
cd days/day-53-graph-workflow-runtime/lab
uv run python legacy.py
```

**Line by line:**

- One construction of each class, no runs, no model calls. Constructing an `Agent` does not contact a
  provider.

Measured on 2026-09-05, against `google-adk==2.7.1`:

```text
  SequentialAgent:
      SequentialAgent is deprecated in favor of Workflow and will be removed in a future version. Workflow cannot yet be used as an LlmAgent sub-agent.
  ParallelAgent:
      ParallelAgent is deprecated in favor of Workflow and will be removed in a future version. Workflow cannot yet be used as an LlmAgent sub-agent.
  LoopAgent:
      LoopAgent is deprecated in favor of Workflow and will be removed in a future version. Workflow cannot yet be used as an LlmAgent sub-agent.
```

Three for three, and the wording is identical in all three, which tells you it is a deliberate,
coordinated deprecation rather than three separate opinions.

Note what the message does **not** say: it does not give a version number for the removal. *"A future
version"* is all the schedule you get, which means the correct planning assumption is *"the next minor
release could do it"* rather than *"there will be plenty of warning"*.

## When it breaks

The break that makes deprecations dangerous in practice is not in ADK. It is in Python, and it has two
halves, both measured here rather than asserted.

```bash
cd days/day-53-graph-workflow-runtime/lab
uv run python hidden.py
```

**Line by line:**

- `hidden.py` imports `_deprecated_caller.build_twice`, which constructs a `SequentialAgent` twice from
  the same line **inside another module** — the shape of a deprecated call sitting in your own package
  rather than in the script you launched.
- It then repeats the two constructions under `simplefilter("default")` and `simplefilter("always")`
  and counts what each captures.

Measured on 2026-09-05:

```text
1. default filters, deprecation raised inside an imported module:
   ^ nothing printed above means Python hid it

2. simplefilter('default'): captured 1 of 2 constructions
2. simplefilter('always'): captured 2 of 2 constructions
```

**The first block printed nothing.** A `SequentialAgent` was constructed twice, the warning was raised
both times, and Python showed neither — because `DeprecationWarning` is **ignored by default unless it
is triggered from `__main__`**. A deprecated call inside `sutra/`, reached through a server process or
a test runner, is silent.

**The second block shows one against two.** With the default filter, the same warning from the same
location is reported **once**, no matter how many times it fires. So even a warning you *can* see
undercounts: one line in a log is compatible with ten thousand deprecated calls.

Put those together and "we did not see any deprecation warnings" almost always means nobody configured
warnings, not that there were none. The defence is one line, and it belongs in any project that intends
to notice these:

```toml
[tool.pytest.ini_options]
filterwarnings = ["error::DeprecationWarning"]
```

**Line by line:**

- `error::DeprecationWarning` promotes every deprecation warning to an exception **in the test suite
  only**. Production behaviour is unchanged; CI fails the day a dependency deprecates something you use.
- This is Principle 11 applied to a warning: turn a thing you might notice into a thing that goes red.

The second break is the `yet` in the warning's second sentence:

```text
Workflow cannot yet be used as an LlmAgent sub-agent.
```

If your design has an agent delegating to a sub-agent whose job is really a multi-step process, you
cannot port that sub-agent to a `Workflow` in place. The graph must go above the agent, and the agent
becomes a node in it. That is a bigger change than a find-and-replace, and it is much better discovered
now than in the release that removes the classes.

## In production

**What a professional writes instead.** Deprecation warnings are errors in CI, never silenced with
`warnings.filterwarnings("ignore")` in application code. When one appears they open an issue the same
day with the port written down, even if the port is scheduled for later — because the expensive part
of a deprecation is not doing the work, it is rediscovering what the work was six months later under
time pressure.

**What degrades at scale.** Deprecated APIs are load-bearing before anyone notices. A `SequentialAgent`
in one place is a small port; the same class in eleven places, three of them in code paths nobody has
touched in a year, is a project. The cost of a deprecation grows with how long you leave it, and the
growth is not linear because the surrounding code also changes.

**The failure that only appears with real traffic.** The removal release. Your dependency bot opens a
routine minor version bump, CI is green because the tests do not exercise that path, and the
`ImportError` appears in production. This is exactly what the pinned versions and dated
`docs/PACKAGES.md` rows in Principle 7 exist to slow down, and exactly why a pin without a plan is only
a delay.

**The review comment a senior engineer leaves:** *"This uses `LoopAgent`, which is deprecated in the
version we pin. It works today. Port it to a routed edge with a counter now while it is one node, and
add `filterwarnings = ["error::DeprecationWarning"]` so the next one fails CI instead of appearing in
a log we do not read."*

**The interview question:** *"You upgrade a framework and see a deprecation warning on something
central. What do you do?"* A grown-up answer: *"Read what it says to use instead and whether the
message names a removal version — ADK's says 'a future version', which I plan for as 'the next minor
release'. Then port it, or at minimum write the port down in an issue the same day. And I make the
warning fail CI, because `DeprecationWarning` is hidden by default outside `__main__` and Python only
shows each one once per location — so 'we did not see any warnings' usually means nobody configured
them, not that there were none."*
