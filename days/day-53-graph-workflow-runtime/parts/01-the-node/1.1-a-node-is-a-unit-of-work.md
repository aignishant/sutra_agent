# 1.1 — A node is a unit of work, not a unit of intelligence

## One-line answer

A node is one step of your process with a name, and the runtime's only promise about it is
*"I will run this once, when its turn comes, and I will tell everyone what came out"* — which is why
a two-line function that strips whitespace is exactly as much a node as an agent that calls a model.

## The story

There is a man at the fish market who only cuts.

You choose the fish yourself, at the front, from the ice. You pay at the counter on the left. Then you
carry it round to him and say how you want it, and he cuts it, and hands it back in a bag. He does not
weigh. He does not take money. He does not tell you which fish is fresh — ask him and he will point
back towards the front with the knife still in his hand.

The first time, this is annoying. You want one person to do the whole thing.

Then you watch for a while on a Sunday morning, when there are thirty people in the shop, and you see
why it is built this way. The queue at the ice does not block the queue at the knife. Two people can
be paying while four are being cut. When the boy at the counter goes for lunch, someone else stands
there and nothing else changes, because the counter is a job and not a person. And when a customer
comes back angry, everybody in the shop knows exactly where it went wrong, because there are only four
places it could have gone wrong.

The shop is fast because nobody in it does two things.

## The idea in plain language

A **node** is one step in a process, given a name, so that something else can decide when to run it.

That is the entire definition, and the hard part is how little it says. A node is not a kind of
intelligence. It is not an agent. It does not have to think, or call a model, or cost anything. In
ADK 2.x a node is any piece of work that can be started, can produce a result, and can be referred to
by name.

Three words to fix now, because the rest of the day leans on them:

- **The runtime** is the code that decides which node runs next, starts it, and collects what it
  produced. You do not write it; you write the nodes and the wiring, and it does the deciding. On
  Day 7 you met the *agent* runtime, which drove one agent's think–act–observe turn. The **graph
  Workflow Runtime** is the same kind of thing one level up: it drives a whole process made of many
  steps.
- **An event** is one thing that happened, written down. Every node reports what it did by emitting
  events. You met events on
  [Day 7](../../../day-07-events-and-streaming/parts/01-the-event-object/1.1-an-event-is-a-line-in-a-ledger.md)
  as the way an agent narrates itself; nodes use the same channel.
- **Output** is the one piece of an event that the *next* node will receive. Everything else in an
  event is for humans and for the log.

The reason to make a step a node — rather than three lines further down inside a bigger function — is
the same reason the fish shop has a man who only cuts. A named step can be run on its own, watched on
its own, retried on its own, timed on its own, and blamed on its own. A step buried inside another
step has none of those properties, and you cannot add them later without pulling it out first.

There is a temptation, coming from a year of agent tutorials, to think a node must be *smart* to be
worth naming. It is the opposite. The most valuable nodes in the graph you will build on Day 58 are
the stupid ones: the one that lowercases the ticket text, the one that checks whether two sources were
found. They are valuable precisely because they are boring, deterministic, free, and impossible to get
wrong in an interesting way.

## Why Sutra needs it

Day 58 builds the triage graph end to end: intake, classify, research, draft, review. If "a node"
secretly means "an agent", that graph is five model calls per ticket and Sutra runs out of free quota
before lunch.

It is not five model calls. Intake is string cleaning. Review is a length check. Only the middle needs
judgement. You can only make that trade if the runtime treats a plain function as a first-class node,
and the first thing to prove today is that it does.

## The mechanism

Here is a node, and a graph containing exactly one of them.

```python
"""1.1 - one node, run on its own, so you can see what a node is before you see a graph."""

from google.adk import Event, Workflow
from google.adk.workflow import node

from _run import run, show


@node
def intake(node_input: str) -> Event:
    """Normalise whatever the customer typed. That is the whole job of this node."""
    cleaned = " ".join(node_input.split()).lower()
    return Event(output=cleaned)


flow = Workflow(name="one_node", edges=[("START", intake)])
```

**Line by line:**

- `from google.adk import Event, Workflow` — both are top-level exports. `Workflow` is the graph
  itself; `Event` is how a node reports what happened. Verified against `https://adk.dev/graphs/` on
  2026-09-05, and against the installed package with
  `python -c "from google.adk import Event, Workflow; print(Workflow)"` on `google-adk==2.7.1`.
- `from google.adk.workflow import node` — `node` is the decorator that turns a function into a node.
  It lives in the `google.adk.workflow` package, not at top level.
- `from _run import run, show` — the day's small harness, which creates a runner and a session and
  drains the events. It is four lines of ceremony that every script would otherwise repeat; it is
  listed in full in [5.1](../05-the-first-graph/5.1-five-desks-one-form.md).
- `@node` — used bare, with no brackets. It wraps `intake` and hands back a `FunctionNode` object.
  The name `intake` in the rest of the file now refers to the node, not the function. The decorator is
  optional here (a bare function in an edge list is wrapped for you), and it is used anyway because it
  is the only place to set a name, a timeout or a retry policy.
- `def intake(node_input: str)` — `node_input` is a **reserved parameter name**. The runtime looks for
  it and puts the previous node's output there. Call the parameter anything else and it will not be
  filled from the edge; it will be looked up in the session state instead, which is
  [2.5](../02-the-edge/2.5-on-the-edge-or-in-the-register.md)'s subject.
- `return Event(output=cleaned)` — `output` is the field that travels. A node that returns
  `Event(message=...)` instead has said something to the human and passed nothing on
  ([1.4](1.4-what-leaves-a-node.md)).
- `edges=[("START", intake)]` — the smallest possible wiring: from the start of the graph, to this
  node, and stop. `"START"` as a bare string is accepted and resolved to the framework's `START`
  sentinel.

**Line by line:**

- `cd` into `lab/` first, because the scripts import `_run` from beside them.
- `unit.py` runs the one-node graph on a deliberately messy string, then prints what `intake` actually
  is, so the claim "the decorator returns an object" is checked rather than asserted.

Measured on 2026-09-05:

```text
one node, one message:
  intake           'checkout is down'
  1 events

  intake is a FunctionNode
  intake.name = 'intake'
  the graph holds 2 nodes: ['__START__', 'intake']
```

Three facts worth stopping on.

**One event.** One node ran, so one event exists. The event stream is not a log the runtime writes as
a favour; it *is* the record of which nodes ran, and it is what Day 60 replays to resume a run and
what Day 84 traces.

**`intake` is a `FunctionNode`.** After the decorator, the name no longer refers to your function. It
refers to a node object that has a name, a timeout, a retry policy and a schema — none of which a
plain function has. The function is still in there, and the node calls it.

**The graph holds two nodes, and you only wrote one.** `__START__` is a node too. It never executes;
it exists so that "where does the work begin" is answered by an edge like every other question in the
graph. [2.2](../02-the-edge/2.2-the-chain-that-is-a-list-of-edges.md) comes back to it.

## When it breaks

The break that catches everyone is the reserved parameter name. Call the parameter something
descriptive — `ticket`, say, which reads better than `node_input` — and the graph builds happily and
then dies on the first run:

```text
ValueError: Missing value for parameter "ticket" of function "typo". It was not found in state and
has no default value.
```

Read what it actually says. It did not look on the edge for `ticket`; it looked **in state**. That is
the rule underneath: a parameter named `node_input` is filled from the incoming edge, and *every other
parameter* is filled by looking up a key of that name in the session state. `ticket` was not in state,
so there was nothing to pass. The fix is to name the parameter `node_input`, or to put a `ticket` key
in state on purpose, which is [2.5](../02-the-edge/2.5-on-the-edge-or-in-the-register.md)'s subject.

What does *not* break is forgetting the decorator. A bare function is accepted in an edge list and
wrapped for you:

```text
what a bare function became: FunctionNode bare
it runs:
  bare             'HELLO'
  1 events
```

This is convenient and it is worth knowing about, because it means a missing `@node` is not the reason
your graph is misbehaving — and because the auto-wrapped node takes its name from the function, with
no chance to override it. Decorate deliberately when the name matters.

The subtler break is naming. Two node objects with the same name are rejected when the graph is
built, and the message is unusually helpful about *why* you might have done it:

```text
Graph validation failed. Duplicate node names found: ['classify']. This means multiple distinct
node objects have the same name. If you intended to reuse the same node, ensure you pass the exact
same object instance. If you intended to have distinct nodes, ensure they have unique names.
```

That sentence is worth reading twice, because it names the thing that makes a graph different from a
tree: **reuse means the same object, in two places.** Not a copy. The same object.
[4.1](../04-composition/4.1-one-secretary-or-one-register.md) is built on it.

## In production

**What a professional writes instead of the teaching version.** They give the node an explicit name
and a docstring that says what it does *and what it must not do*: `@node(name="intake")` rather than
relying on the function's name, because the function will be renamed one day by someone doing a
refactor who does not know that the string `"intake"` appears in a dashboard query, an alert rule and
a saved trace filter. The node name is a public identifier the moment anything observes the run.

**What degrades at scale.** Nothing about a node degrades — but the *granularity choice* does. Too
coarse and you cannot see inside a step that takes most of the time; too fine and a simple flow has
forty nodes and every trace is a wall of noise. The rule that survives contact with real systems: make
something a node when you would want to retry it alone, time it alone, or read it alone in a trace. If
none of those three is true, it is a function call inside a node.

**The failure that only appears with real traffic.** A node that is cheap on your machine and
expensive in production, because it does I/O you did not notice. A "just formatting" node that reads a
template off disk becomes a filesystem call per ticket, and at a thousand tickets an hour it is the
slowest thing in the graph. Nodes make this *visible* — that is the argument for naming the boring
ones — but only if you look.

**The review comment a senior engineer leaves:** *"Three of these five nodes call a model and two of
them do not need to. `intake` is `str.lower` and a split; `review` is a length check. Make them
functions and keep the model calls for `classify` and `draft`. Right now this graph costs five
requests a ticket and three of them are buying nothing."*

**The interview question:** *"What is a node in a graph-based agent runtime?"* The answer that shows
you have used one: *"A named unit of work the runtime can schedule, observe and retry on its own. The
important part is that it is not a unit of intelligence — most of my nodes are plain functions. I
decide whether something is a node by asking whether I would want to retry it, time it, or see it in a
trace by itself. If not, it stays a function call inside a node, because every node I add is another
row in every trace anyone ever reads."*
