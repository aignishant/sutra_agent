# 1.4 — What leaves a node

## One-line answer

One `Event` can carry three separate things — `output` travels to the next node, `message` is shown to
the human, and `route` decides which edge is taken — and confusing the first two is why a graph
sometimes prints a perfect answer and passes nothing on.

## The story

You go to the doctor for a cough that will not clear.

She examines you, and then she writes three things, and they go to three different places.

She says out loud: *"It's viral, it will settle, don't worry."* That is for you. It is the reason you
stop being anxious in the corridor. It goes nowhere else — she does not write it down and the chemist
will never hear it.

She writes a prescription. That is for the chemist. It is not really addressed to you at all; you are
carrying it, but the person who acts on it is a man behind a counter who will read the dosage and hand
over a box. Whatever she said out loud, he goes by what is on the paper.

And she ticks a box on a form: *follow-up needed / not needed*. That is for the desk outside. It
decides whether you are given another appointment on the way out or simply leave.

Three outputs, one consultation. Say the reassurance and forget the prescription, and you go home calm
and untreated.

## The idea in plain language

An `Event` is one line in the record of a run, and a node produces one or more of them. Three of its
fields do different jobs, and the whole of this part is keeping them apart.

| Field | Who reads it | What happens if you leave it out |
| --- | --- | --- |
| `output` | the next node, as its `node_input` | the next node gets `None` |
| `message` | the human, and the transcript | nothing is shown; the run is silent |
| `route` | the graph, to choose an edge | unrouted edges fire; routed edges do not match |

The convenience keyword `message=` is turned into the event's `content` field, which is where the
model's own text lives. That is why the two are interchangeable in the record and why `message` is not
passed downstream: it is conversation, not data.

`route` is the one that will be new. A node does not name the next node; it emits a **label**, and the
graph looks for an edge tagged with that label. Because that is a whole idea of its own, it gets a
part of its own: [2.3](../02-the-edge/2.3-a-label-not-an-address.md).

Two mechanical facts about returning things, both verified against
`https://adk.dev/graphs/data-handling/` on 2026-09-05 and against `google-adk==2.7.1`:

- **You may return a bare value instead of an `Event`.** `return "incident"` is wrapped into
  `Event(output="incident")` for you. This is fine for small nodes and becomes a trap the moment you
  want a message or a route as well, because a bare return can only ever set `output`.
- **A node may emit more than one event, but only one `output`.** Returning gives one event; yielding
  gives as many `message` events as you like and exactly one `output`, enforced with
  `ValueError: Output already set`. That is [1.5](1.5-say-it-as-you-go.md).

## Why Sutra needs it

The desk has two audiences at once. A support agent is watching the run and needs to see what is
happening in words; the next node needs a structured value it can act on. Day 58's `classify` node has
to do both — tell the human *"this looks like an outage"* and hand `draft` a dictionary with a
category in it.

Get this wrong in the direction people usually get it wrong — put the human-readable sentence in
`output` — and `draft` receives an English sentence where it expected a dictionary, and either crashes
or, worse, does something plausible with the wrong shape.

## The mechanism

One node emitting all three fields at once, and a second node proving which of them arrived.

```python
"""1.4 - what leaves a node: output travels, message is shown, route steers."""

from google.adk import Event, Workflow
from google.adk.workflow import node

from _run import run


@node
def classify(node_input: str) -> Event:
    """Emits all three at once: a message for the human, an output for the next node, a route."""
    return Event(
        message="Looks like an outage. Paging the on-call engineer.",
        output={"kind": "incident", "text": node_input},
        route="urgent",
    )


@node
def page_oncall(node_input: dict) -> Event:
    return Event(output=f"paged for {node_input['kind']}")


flow = Workflow(
    name="leaves",
    edges=[("START", classify), (classify, {"urgent": page_oncall})],
)
```

**Line by line:**

- `Event(message=..., output=..., route=...)` — all three in one constructor call. `message` and
  `route` are convenience keywords: the first becomes `content`, the second becomes `actions.route`.
  You can set `content` and `actions` directly instead, and nobody does.
- `output={"kind": ..., "text": ...}` — a dictionary, not a sentence. The next node indexes into it.
  A structured output is the difference between a downstream node that parses and one that reads.
- `def page_oncall(node_input: dict)` — the annotation says what it expects. The runtime will coerce a
  dict into a Pydantic model if you annotate one, which is how `input_schema` is inferred.
- `(classify, {"urgent": page_oncall})` — a routing map: the key is the label `classify` emits, the
  value is where that label leads.

**Line by line:**

- `leaves.py` pulls the three fields off each event separately — `event.output`, the text inside
  `event.content.parts[0]`, and `event.actions.route` — so that "these are three different fields" is
  shown rather than claimed.

Measured on 2026-09-05:

```text
  node=classify@1
    output  = {'kind': 'incident', 'text': 'checkout is down'}
    message = 'Looks like an outage. Paging the on-call engineer.'
    route   = 'urgent'
  node=page_oncall@1
    output  = 'paged for incident'
    message = None
    route   = None
```

The second block is the interesting one. `page_oncall` set only `output`, so `message` and `route` are
`None` — and the run still worked, because `page_oncall` is the last node and had nothing to steer
towards and nobody to talk to.

The first block shows the three fields coexisting on a single event. The human got a sentence. The
next node got a dictionary. The graph got a label. None of the three had to be squeezed through
another.

## When it breaks

Put the sentence in `output` and the dictionary nowhere, and the annotation on the next node catches
it before your code runs:

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for dict[any,any]
  Input should be a valid dictionary [type=dict_type, input_value='Looks like an outage.',
  input_type=str]
```

Read `input_value='Looks like an outage.'` — the error is holding up the exact sentence that should
never have been on the edge. This is the *good* version of the failure, and you got it for free by
annotating `node_input: dict`. Annotate it `node_input: str`, or leave it unannotated, and there is no
error at all: the sentence flows on, gets pushed into a prompt, and produces a fluent wrong answer.
The annotation is not decoration; on a node boundary it is the check.

The second break is quieter, and it is worth measuring rather than guessing. A node that returns
`None` emits **no event at all**:

```text
classify returns None:
  page_oncall      'page_oncall received None'
  1 events
```

One event, not two. `classify` ran, produced nothing, and left no trace in the stream — the runtime
skips a `None` yield rather than recording an empty event. The graph carried on regardless and
`page_oncall` was handed `None`.

That combination is worth holding on to: **a node that fails to produce anything is invisible in the
event stream and does not stop the run.** Counting events is therefore not a reliable way to tell
which nodes executed, and a node that must produce something should say so with an `output_schema`
rather than trusting the next node to notice.

## In production

**What a professional writes instead.** They give the nodes at every seam an `output_schema` and an
`input_schema` — Pydantic models — so the contract between two nodes is declared rather than
remembered. The payoff is not runtime validation; it is that the graph checks schema compatibility
**when it is built**: an edge from a node whose `output_schema` does not match the next node's
`input_schema` is rejected with `Schema mismatch on edge draft -> review`. That turns a class of
integration bug into a startup error.

**What degrades at scale.** `output` is recorded on the event, and events are persisted. A node that
puts a whole retrieved document in its output writes that document into the session on every run. It
is the same arithmetic as
[Day 50's top-k](../../../day-50-chunking-and-top-k/parts/03-the-k-is-a-budget/3.1-k-is-a-budget-not-a-preference.md):
what you carry, you pay for repeatedly. Pass a reference — a ticket id, an index key — and let the
node that needs the text fetch it.

**The failure that only appears with real traffic.** `message` is what the human sees, so it is where
someone eventually puts a variable that contains customer data, and it is now in every transcript,
every trace and every log sink. Day 69's data-boundary rules land on this field specifically. Decide
early that `message` is for status and not for content.

**The review comment a senior engineer leaves:** *"`classify` returns a sentence. Every node
downstream is doing string matching on English to recover a category the classifier already knew.
Return `{'kind': ...}` in `output` and keep the sentence in `message`, and add an `output_schema` so
the next person cannot undo this."*

**The interview question:** *"Your workflow step needs to tell the user something and pass a value to
the next step. How?"* The answer that shows the seams: *"They are different fields on the same event —
`message` for the human, `output` for the next node, and `route` if it also has to choose a branch.
The failure I have actually seen is putting the human sentence in `output`: the next node gets English
where it wanted a dict, and if that node is a prompt-builder it will not even crash, it will just be
confidently wrong. So the outputs at every seam get a schema."*
