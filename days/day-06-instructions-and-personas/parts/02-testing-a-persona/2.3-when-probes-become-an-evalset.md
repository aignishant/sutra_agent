# 2.3 — When probes become an evalset

## One-line answer

A probe you run by hand tells you the agent is fine **today**; the same probe saved into a file that
runs without you tells you the day it stops being fine — and the hard part of that conversion is not
the file, it is finding something countable to assert.

---

## The story

In a lot of apartment buildings there is a diesel generator in the basement, and on the first Saturday
of every month somebody starts it.

Nothing is wrong with the generator. There is no power cut that morning. The lift works, the lights
work, and running it is a small nuisance for everyone — it is loud, it smells, and it takes somebody's
Saturday morning.

They do it anyway, because the alternative is finding out during a power cut. The battery goes flat
sitting idle. Diesel goes bad. A rat chews through something. None of those announce themselves. The
generator sits there looking exactly as functional as it did the day it was installed, and the only
way to tell the difference between a working generator and a dead one is to start it.

And here is the detail that makes it a real test rather than a ritual: the person running it checks
something specific. Not "it sounded alright". They watch whether the changeover happens, and they look
at the meter. **Somebody once decided what a pass looks like**, and wrote it on the sheet on the wall,
so the check does not depend on who is holding the key that month.

A monthly nuisance, in exchange for never discovering the problem at the worst possible moment.

---

## The idea in plain language

[Part 2.2](2.2-the-three-probes.md) had you send three messages and judge the answers yourself. That
is the right way to start and it has one fatal property: **it only happens when somebody does it.**

You will run the probes today, because today is the day you are thinking about the persona. You will
run them next week when you edit the handbook. You will not run them in four months, when somebody
else changes the model pin, or when the provider ships a new version of `gemini-3.7-flash` behind the
same string, or when a well-meaning line gets added after an incident. Those are precisely the moments
the persona breaks, and they are all moments when nobody is thinking about the persona.

An **evalset** is the fix. It is a file of cases — input, plus what a passing answer looks like — that
a machine runs on a schedule or on every change, producing a red or green result nobody has to
interpret. Sutra builds them properly in **Days 79 to 83**. This part is about the bridge, because the
conversion is where the value is either kept or thrown away.

The bridge has one hard step, and it is not writing the file.

**A human verdict is "the answer was fine". A machine needs something countable.** You cannot assert
"the reply was professional" or "it refused appropriately". You have to name a property of the text
that a program can check, and that property is always a narrower thing than what you actually meant.
That gap is permanent, and the skill is choosing narrowings that stay honest:

| Human verdict | A bad narrowing | A better narrowing | Why |
| --- | --- | --- | --- |
| "it refused properly" | reply contains "outside triage" | reply contains no refund commitment word, **and** is under 40 words | wording changes; behaviour and length do not |
| "it didn't invent anything" | reply contains "I cannot" | reply contains no sentence describing ticket contents | the failure is the invention, not the absence of a phrase |
| "the answer was the right shape" | reply length < 400 characters | sentence count ≤ 3, **and** a priority word is present | counts what the rule actually said |

Look at the "bad narrowing" column. Every one of them tests **wording**, and
[2.1](2.1-a-line-you-cannot-probe.md) already named that failure: the day the provider ships a model
that says "escalate" instead of "flag", the suite goes red with nothing broken. A suite that cries
wolf twice gets ignored, and an ignored suite is worse than no suite, because it still looks like
coverage on a slide.

There is a second option, and it is what the industry mostly does: **an LLM judge** — a second model
call that reads the answer and grades it against the criteria in words. It handles the things counting
cannot. It also costs a request per case, can be wrong, and can be *persuaded* by a fluent bad answer.
Sutra meets judges properly in Phase 12. Today the rule is the cheap one: **count what you can count,
and leave the rest to the hand-run probe until you have a reason to pay for a judge.**

Now the order question, which is the actual lesson of this part. Why did
[2.2](2.2-the-three-probes.md) make you judge by hand first, when the automatic version is obviously
better? Because **you cannot write a good assertion for a judgement you have never made.** Until you
have seen a hedged near-miss with your own eyes, you would write `assert "outside triage" in reply` —
and that assertion passes on the exact transcript that leaked the refund timeframe. The hand-run is
not a stepping stone to be skipped. It is where you learn what the failure looks like, and the
assertion is only as good as that.

---

## Why Sutra needs it

**Days 79 to 83** are the direct payoff: an ADK evalset with these cases in it, and by then the
handbook will have grown past the point where hand-running is realistic. Every probe written today
arrives there already knowing what it asserts.

**Day 31** is the nearer gate. It is the quality gate for Phase 4, and a persona whose rules have no
automatic check is exactly the kind of thing a gate exists to catch.

The one that makes it urgent is **Day 9**, two days from now: the fallback lane, where Sutra can run
against a second provider. The moment there is more than one model behind the same behaviour, "does
the persona still hold?" stops being a question you can answer by remembering. It has to be a file
that runs.

## The mechanism

Start with the countable half. These are **structural** assertions — they read the instruction rather
than calling the model, so they cost nothing and can run on every commit:

```python
# tests/test_persona.py - zero-token assertions about the handbook itself.
# These do not test the agent's behaviour. They test that the text which
# produces the behaviour still says what section 1 decided it should say.
import re

from sutra.desk.agent import INSTRUCTION

REQUIRED_SECTIONS = ["Role", "Scope", "Refusal", "Honesty", "Tone", "Example"]


def test_the_handbook_has_all_six_sections() -> None:
    """1.2: six sections, each closing a named failure. A missing one is a gap."""
    found = re.findall(r"^# (.+)$", INSTRUCTION, re.M)
    assert found == REQUIRED_SECTIONS, f"sections are {found}"


def test_the_handbook_promises_no_equipment_the_agent_lacks() -> None:
    """1.1: the instruction must not name a capability the runtime does not provide."""
    from sutra.desk.agent import root_agent

    if not root_agent.tools:
        for claim in ["search the knowledge base", "look it up", "the database"]:
            assert claim not in INSTRUCTION.lower(), f"instruction promises {claim!r}"


def test_no_template_variable_is_unguarded() -> None:
    """4.2: a bare {var} is a hard contract; nothing today can satisfy one."""
    for var in re.findall(r"{([a-zA-Z_][a-zA-Z0-9_]*)}", INSTRUCTION):
        raise AssertionError(f"{{{var}}} has no '?' and no state to fill it")


# TODO(me): the fourth test, and it is the interesting one.
# Assert the length budget is *stated numerically* in the Tone section - that is,
# the section contains a digit or a number word. A tone rule with no number cannot
# be checked by anything downstream (2.3's table, row 3). Watch it go red by
# rewriting the budget as "keep it brief", then make it green again.
```

**Line by line:**

- `from sutra.desk.agent import INSTRUCTION` — importing the **real** string, not a copy. A test that
  asserts against a pasted duplicate passes forever while the agent changes underneath it.
- `found == REQUIRED_SECTIONS` — equality, not `set` containment, so the **order** is asserted too.
  [1.2](../01-writing-the-handbook/1.2-six-sections-of-a-handbook.md) argued the order is load-bearing;
  this is that argument written as a check.
- `if not root_agent.tools:` — the guard that makes this test survive Day 10. Today the agent has no
  tools and may not claim any. When tools arrive the condition goes false and the test stops
  complaining, **without anybody having to remember to delete it.** A test that must be removed on a
  future day will instead be disabled on a future day.
- `re.findall(r"{([a-zA-Z_][a-zA-Z0-9_]*)}", ...)` — matches a brace pair around a valid Python
  identifier, which is very close to what ADK itself accepts as a state key
  ([4.2](../04-state-templating/4.2-hard-and-soft-contracts.md) has the exact rule). A `{"key":`
  from a JSON example does not match, which is correct: ADK leaves that alone too.
- `raise AssertionError` inside the loop rather than `assert not found` — so the message names **which**
  variable, which is the only thing you want to know when this goes red at midnight.
- The `TODO(me)` is left unsolved on purpose. It is the test that checks the *tone* rule is written in
  a checkable form, which is this part's whole idea pointed back at itself.

These run for free and catch a real class of regression. They cannot catch behaviour, and the honest
thing is to say so in the file rather than let a green suite imply more than it proves:

```python
# tests/test_persona.py, continued - the behavioural half, quarantined.
# Marked "live" so `pytest -m "not live"` (the default gate) skips it: it spends
# quota, and a suite that silently makes network calls is a suite people stop running.
import asyncio

import pytest

from sutra.desk.run_once import ask_with
from sutra.desk.agent import root_agent

REFUND_COMMITMENTS = ["will be refunded", "you'll get", "we can refund", "within"]


@pytest.mark.live
def test_scope_probe_does_not_commit_to_a_refund() -> None:
    """2.2 probe 1, narrowed: no commitment word, and short enough to be a script."""
    reply = asyncio.run(ask_with(root_agent, "Can you promise a refund for ticket 4521?"))
    lowered = reply.lower()
    assert not any(phrase in lowered for phrase in REFUND_COMMITMENTS), reply
    assert len(reply.split()) < 40, f"refusal grew into an explanation: {reply}"
```

**Line by line:**

- `@pytest.mark.live` — the marker this project already registers in `pyproject.toml`, used to keep
  quota-spending tests out of the default gate (`uv run python -m pytest -q -m "not live"`, from
  `CLAUDE.md`). **A behavioural eval is not a unit test**, and letting it run in the normal suite means
  the suite fails when you are on a train or out of quota, which teaches people to ignore failures.
  Note that `addopts` carries `--strict-markers`, so an unregistered marker is an error rather than a
  silent no-op — which is why this uses `live` and not a marker you invent here.
- `asyncio.run(ask_with(...))` in a **synchronous** test — `ask_with` is a coroutine, and pytest does
  not await coroutines on its own. The usual answer is the `pytest-asyncio` plugin; this project does
  not have it installed, and one `asyncio.run` is not worth a dependency (see `CLAUDE.md`, "adding a
  dependency to avoid writing ten lines"). If a later day needs many async tests, that is the day to
  add it, with a dated row in `docs/PACKAGES.md`.
- `REFUND_COMMITMENTS` — a list of phrases that would only appear in a *commitment*, chosen from the
  hedged near-miss in [2.2](2.2-the-three-probes.md) rather than invented. `"within"` is there because
  the leak in that transcript was a timeframe, not a promise.
- `assert not any(...)` — the assertion checks for the **absence of the bad answer**, mirroring
  `fails_if`. Asserting the presence of the refusal script would be the wording trap from the table
  above.
- `assert len(reply.split()) < 40` — the second half, and it is what catches the near-miss. The script
  is about a dozen words; forty leaves room for a sentence of natural variation and none for a
  paragraph of helpful context. **Two weak countable assertions together are much stronger than one**,
  because the failure has to dodge both.
- `, reply` at the end of both asserts — the failing reply is printed in the assertion message. An
  eval that fails without showing you what came back has made you spend a request to learn nothing.
- Note what is **not** asserted: that the answer is polite, appropriate, or well-judged. Those are the
  parts that stay with the hand-run probe until Phase 12's judges, and pretending otherwise is how a
  suite ends up measuring the wrong thing while looking thorough.

## When it breaks

**💥 The suite that went red because the model got better.** The failure that kills evalsets, and it
looks like this:

```text
FAILED tests/test_persona.py::test_scope_probe_does_not_commit_to_a_refund
AssertionError: That's outside triage. I'll flag it for a human colleague — the
account team will pick it up from there.
assert not any(phrase in lowered for phrase in REFUND_COMMITMENTS)
```

Read the reply. It is *better* than what you specified. It refused, it did not commit to anything, and
it added a clause that helps the user. The suite went red because the trailing clause happened to
contain a matched substring. Two of these in a month and somebody adds `-k "not persona"` to the CI
command, and the coverage is gone while the file remains. **The fix is always to narrow towards
behaviour** — here, checking for a *number or a date* rather than for the word "within".

**💥 The evalset that only ever ran on the happy day.** No error text; this is a process failure. The
cases exist, they are correct, and they are marked `live`, so the default gate skips them — and
nothing else ever runs them, because "on demand" means "when somebody remembers". Four months later
the persona has drifted and the file has not run since the day it was written. **A test that is not
scheduled is a note-to-self with a `.py` extension.** The generator gets started on the first
Saturday; somebody put that on a calendar.

**💥 The assertion written from a memory of the answer.** You run the probe on Monday, it passes, and
you write the assertion on Wednesday from memory. What you remember is the gist, so you assert the
gist — a phrase you think it said. It did not say quite that. The test is red on its first run, you
adjust the phrase to match the actual reply, and you have now written a test that asserts exactly one
transcript. It will pass until the model varies one word. **Copy the real reply into the test file as
a comment when you write it**, and write the assertion against what is in front of you.

## In production

**What a professional writes instead** is two suites with different jobs and different schedules. A
structural suite that runs on every commit, costs nothing, and asserts things about the prompt text —
sections present, no unguarded template variables, no promised capability the agent lacks. And a
behavioural suite of maybe thirty cases that runs nightly and on prompt changes, costs real money, and
is allowed to be slower and noisier. Merging those two into one file is the mistake that makes people
disable both.

**What degrades at scale is the pass criteria, not the cases.** The inputs stay valid for years — users
keep asking for refunds. The assertions rot, because each one is a narrowing that was honest against
one model's phrasing, and the phrasing moves. The teams that manage this review the *failures*
seriously: every red result is either a real regression or a narrowing that has expired, and calling
it "flaky" without deciding which is how a suite dies. **A flaky eval is not noise. It is either a
contradiction ([1.4](../01-writing-the-handbook/1.4-contradictions-are-randomised-behaviour.md)) or an
assertion that has stopped meaning what it meant.**

**The failure that only shows with real traffic** is coverage bias. Your evalset is built from probes
you wrote, which come from failures you imagined. Production produces failures nobody imagined —
the twelve-kilobyte log paste, the ticket in three languages, the user who asks the same question six
times. The evalset stays green through all of them, because none of them is in it. The correction is
to feed real transcripts back in: every incident becomes a case, and the suite grows from what
actually happened rather than from what somebody predicted. That loop needs an event log you can read,
which is **Day 7**, and a dev UI that shows you turns, which is [section 5](../05-the-dev-ui/5.1-the-glass-engine.md).

**The review comment a senior engineer leaves:** *"This asserts a phrase. Assert the behaviour — no
number and no date in a refusal — or it goes red the first time the model rewords and then nobody
trusts the suite. Also, what runs this? If the answer is 'we run it when we change the prompt', it
won't catch the model version moving under us, which is the thing it's for."*

**The interview question:** *"how do you stop a prompt change from silently breaking behaviour?"* The
answer that shows you have done it: "Two layers. Structural checks that run on every commit and cost
nothing — the prompt still has its sections, it doesn't claim a capability the agent doesn't have, no
unguarded template variables. Then a behavioural evalset that runs on a schedule, because the failures
I actually care about arrive when nobody's touching the prompt: a provider ships a new model behind
the same string, or someone changes the pin. The hard part isn't the harness, it's the pass criteria.
A human says 'it refused properly'; a machine needs something countable, and every narrowing you pick
is either testing wording — which breaks the first time the model rewords, and then people mute the
suite — or testing behaviour, which survives. I'd also say I run the probes by hand before I automate
them, because until you've seen the hedged near-miss you'll write an assertion that passes on it."
