# 4.1 — The instruction is a template, not a string

## One-line answer

ADK reads your instruction as a **fill-in-the-blank form**: anything in curly braces that looks like a
state key is replaced with a value from the session before the model sees it, which makes the handbook
per-conversation — and makes every stray brace in it a live wire.

---

## The story

The letter from the bank starts: *Dear Mr Sharma, your cheque book for account ending 4417 is ready
for collection at our Andheri branch.*

Nobody at the bank wrote that letter. Somebody wrote this, once, years ago:

*Dear ________, your ________ for account ending ________ is ready for collection at our ________
branch.*

That is the actual document. It sits in a system, unchanged, and eleven thousand people receive a
version of it every week. The blanks are filled at the moment of printing, from a database, by a
machine. What arrives at your house is not the letter the bank wrote. It is the letter plus your row.

This is a genuinely good idea. One document to review, one document to correct, and it is personal to
every reader without anybody writing eleven thousand letters.

It also has a specific way of going wrong that everyone has seen. A letter arrives addressed to *Dear
,* — with nothing in the blank and the comma still there, because the name field was empty for that
row. Or worse, the one that arrives saying *Dear ________,* with the blank still printed, because the
blank was spelled slightly differently from the field name and the machine did not recognise it as a
blank at all.

The letter did not become wrong when it was printed. It became wrong the day somebody typed a blank
whose name did not match anything real, and nobody found out until it was in the post.

---

## The idea in plain language

[Part 3.1](../03-the-instruction-fields/3.1-where-your-instruction-lands.md) said your instruction is
rendered before it is sent. This part is what "rendered" means.

**Session state** is a dictionary attached to a conversation. It lives on the session object you met
on [Day 5, part 4.2](../../../day-05-first-adk-agent/parts/04-the-runner/4.2-sessions-and-the-transcript.md),
it persists across the turns of one conversation, and it is written by your code and your tools rather
than by the model. Day 17 builds it properly. Today only one thing about it matters: **ADK substitutes
it into your instruction.**

The syntax, from adk.dev/agents/llm-agents/ (checked 2026-08-26), which puts it as "The instruction is
a string template, you can use the `{var}` syntax to insert dynamic values into the instruction":

| You write | What arrives | If it is missing |
| --- | --- | --- |
| `{tier}` | the value of `state["tier"]` | **the turn fails** — [4.2](4.2-hard-and-soft-contracts.md) |
| `{tier?}` | the same, when present | an empty string, silently |
| `{artifact.notes}` | the text of a stored artifact called `notes` | the turn fails |
| `{app:region}` | `state["app:region"]` — an app-scoped key | the turn fails |

So the handbook stops being a constant. It becomes a form, and each conversation gets its own filled
copy. *"You are handling a {tier} customer"* is one line that behaves differently for a free-tier user
and an enterprise one, without any code choosing between two prompts.

Now the part that is not in the table, and that decides whether this feature is a gift or a landmine.
**What counts as a blank?**

ADK looks at every `{...}` in your text and asks whether the contents are a valid state key. A valid
key is a Python identifier — letters, digits and underscores, not starting with a digit — optionally
prefixed by one of `app:`, `user:` or `temp:`. If it qualifies, it is a blank and it will be filled or
it will fail. **If it does not qualify, the braces are left exactly as they are.**

That rule is the whole safety story, and it is why a JSON example in your prompt usually survives:
`{"priority": "high"}` has quotes in it, so it is not an identifier, so ADK leaves it alone. It is also
why the rule is dangerous: `{priority}` *is* an identifier, and the difference between the safe version
and the exploding version is two quotation marks.

One more thing, and it is the one that surprises Python programmers. In Python, doubling a brace
escapes it — `"{{x}}"` renders as `{x}`. **That is not what happens here.** ADK's pattern matches runs
of braces and strips them, so `{{tier}}` is substituted just like `{tier}`. There is no escape
sequence. If you need a literal brace around an identifier in your prompt, you cannot get one by
doubling it, and the honest answer is to not have one — which is [1.3](../01-writing-the-handbook/1.3-protocol-does-not-belong-in-prose.md)'s
argument arriving from a different direction.

## Why Sutra needs it

**Day 17** is session state proper, and it is where this feature becomes useful rather than
theoretical: a triage focus for the shift, the engineer's name, which product area this queue covers.
Today you learn the mechanism so that Day 17 is about *what to put in state* rather than about how
substitution works.

**Day 11** is nearer and sharper. Tools get a `ToolContext` and can **write** state, which means a
tool result can change the instruction on the next turn of the same conversation. That is a powerful
and slightly alarming loop, and it is only comprehensible if you already know the instruction is a
template.

The immediate reason is defensive, and it is today's failure lab: Sutra's handbook is about to be
rewritten with headings, colons and examples in it. **Every brace you type from now on is either a
feature or an outage**, and knowing which is a thing you check rather than a thing you hope.

## The mechanism

The renderer is the same one you have been running since [3.1](../03-the-instruction-fields/3.1-where-your-instruction-lands.md);
this time you give the session some state so there is something to substitute.

```python
# lab/templating.py - what ADK does to your braces, with and without state.
# Zero requests: renders the request, never sends it.
import asyncio

from google.adk.agents import LlmAgent
from google.adk.agents.invocation_context import InvocationContext
from google.adk.flows.llm_flows.instructions import _build_instructions
from google.adk.models.llm_request import LlmRequest
from google.adk.sessions import InMemorySessionService


async def render(instruction: str, state: dict | None = None) -> str:
    """The system_instruction ADK would send, for this instruction and this state."""
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="local", state=state or {})
    agent = LlmAgent(name="probe_agent", model="gemini-3.7-flash", instruction=instruction)
    context = InvocationContext(
        session_service=service,
        invocation_id="probe",
        agent=agent,
        session=session,
    )
    request = LlmRequest()
    await _build_instructions(context, request)
    return request.config.system_instruction


CASES = [
    ("plain identifier", "Focus: {focus}.", {"focus": "login issues"}),
    ("app-scoped key", "Region: {app:region}.", {"app:region": "APAC"}),
    ("value is None", "Focus: {focus}.", {"focus": None}),
    ("spaces inside", "Focus: { focus }.", {"focus": "login issues"}),
    ("doubled braces", "Focus: {{focus}}.", {"focus": "login issues"}),
    ("not an identifier", "Reply as {my-var} here.", {}),
    ("a JSON example", 'Reply as {"priority": "high"}.', {}),
]


async def main() -> None:
    for label, instruction, state in CASES:
        print(f"{label:20} {instruction!r:36} -> {await render(instruction, state)!r}")


asyncio.run(main())
```

**Line by line:**

- `state=state or {}` on `create_session` — session state is set at creation here. In a real system it
  is written by your code or by a tool (Day 11), but the substitution step cannot tell the difference
  and neither can this experiment.
- `CASES` as a list of triples — the seven questions you actually want answered, side by side, so the
  rule emerges from the comparison instead of from a paragraph of prose. **Two of these seven behave
  differently from how a Python programmer would guess**, which is the reason to run it rather than
  read it.
- `("value is None", ...)` — the case nobody tests. A key that exists with a value of `None` is not the
  same as a missing key, and the table above cannot tell you which way it goes.
- `("doubled braces", ...)` — the Python escape convention, tested rather than assumed. This is the
  single most likely thing for an experienced Python developer to get wrong today.
- `("a JSON example", ...)` — the realistic one. Everybody eventually puts a JSON snippet in a prompt,
  and this case says whether that is survivable.
- `f"{label:20} {instruction!r:36} -> {...!r}"` — fixed-width columns and `repr` on both sides. Without
  `repr` you cannot see that a value became an empty string rather than disappearing, and the empty
  string is the interesting result.
- `render` takes the instruction as an **argument** rather than reading `sutra.desk.agent`. This file
  is a laboratory for the mechanism, not a check on Sutra's own handbook, and mixing those two makes
  both harder to read.

Run it:

```bash
uv run python days/day-06-instructions-and-personas/lab/templating.py
```

**Line by line:**

- No key needed for the render, no quota spent, safe to re-run while you experiment.
- The output below is what this ran on `google-adk` 2.7.1 on 2026-08-26 — pasted from the terminal.

```text
plain identifier     'Focus: {focus}.'                    -> 'Focus: login issues.'
app-scoped key       'Region: {app:region}.'              -> 'Region: APAC.'
value is None        'Focus: {focus}.'                    -> 'Focus: .'
spaces inside        'Focus: { focus }.'                  -> 'Focus: login issues.'
doubled braces       'Focus: {{focus}}.'                  -> 'Focus: login issues.'
not an identifier    'Reply as {my-var} here.'            -> 'Reply as {my-var} here.'
a JSON example       'Reply as {"priority": "high"}.'     -> 'Reply as {"priority": "high"}.'
```

Read rows three and five. A key present with value `None` renders as **empty**, leaving `Focus: .` — a
sentence fragment the model has to interpret. And `{{focus}}` was substituted, so **doubling a brace
does not escape it.** The last two rows are the good news: anything that is not a valid key is passed
through untouched, which is what saves most accidental braces.

```mermaid
flowchart TD

    B -- "no" --> C["left exactly as written<br/><i>{my-var}, {\"priority\": \"high\"}</i>"]
    B -- "yes" --> D{"ends with '?'"}
    D -- "yes" --> E["present -> value<br/>missing -> ''"]
    D -- "no" --> F{"key in session state?"}
    F -- "yes" --> G["value, or '' when None"]
    F -- "no" --> H["KeyError, before any<br/>network call — 4.2"]
```

## When it breaks

**💥 The heading that was a variable.** The failure that will actually happen to you, because the
handbook from [1.2](../01-writing-the-handbook/1.2-six-sections-of-a-handbook.md) is full of prose
somebody will later make dynamic. Somebody writes a scope line mentioning the product area:

```text
# Scope
You triage tickets for {product} only.
```

...intending to set `state["product"]` later, and the agent stops working entirely:

```text
KeyError: 'Context variable not found: `product`.'
```

Notice **when** this fires: not at import, not at agent construction, not at startup. At the first live
turn, in front of whoever is using it. The agent imported cleanly, the tests that construct it passed,
and the failure waited for a real conversation. [Part 4.2](4.2-hard-and-soft-contracts.md) is the fix
and [6.1](../06-failure-lab/6.1-the-handbook-that-promised-equipment.md) is the day's failure lab.

**💥 The escape that did not escape.** For anyone who has written Python format strings:

```text
'Focus: {{focus}}.'  ->  'Focus: login issues.'
```

You doubled the braces to get a literal `{focus}` in the prompt, as `str.format` would give you, and
instead you got a substitution. Worse: if `focus` were **not** in state, doubling it would raise the
same `KeyError` — so the escape you added to make the string safe is exactly as dangerous as the thing
you were escaping.

**💥 The artifact that had no service.** The other half of the syntax, and its failure is a different
exception:

```text
ValueError: Artifact service is not initialized.
```

`{artifact.notes}` asks for stored file content, and artifacts need an artifact service configured on
the runner. If nothing set one up, the render fails with a message that mentions services rather than
your prompt — and the actual cause is one line of instruction text written on a day when somebody was
thinking about artifacts. Artifacts arrive on Day 18; **until then, no `{artifact.*}` belongs in
Sutra's handbook.**

## In production

**What a professional writes instead** treats the instruction template as an interface between the
prompt and the state schema, and tests it as one. There is a test that renders the prompt against an
**empty** state and asserts either that it succeeds or that it fails for exactly the keys you expect;
and a test that renders it against a realistic state and asserts the result contains no leftover
braces. Both cost nothing to run and catch the entire class of failure above before it reaches a user.

**What degrades at scale is that the instruction develops a dependency nobody declared.** Every `{key}`
is a requirement on the session, and there is no manifest of them. Somebody renames a state key in a
tool, greps for the string, finds the tool and the test, misses the prompt — because a prompt is prose
and does not look like code that references a variable. **The instruction's dependencies are invisible
to every refactoring tool you own.** The teams that handle this generate the list: a small script that
extracts every `{...}` from the prompt and asserts each one is a key some tool actually writes.

**The failure that only shows with real traffic** is state that is present for most users and absent
for some. Your `{tier}` renders for every account in your test data because they all have a tier. In
production there is a user created by an old signup flow, or a session started from a channel that
does not set it, and that fraction of traffic gets a hard failure while the rest is fine. It looks like
an intermittent outage. It is a missing dictionary key, and it is deterministic once you know which
user.

**The review comment a senior engineer leaves:** *"That's a template variable, not a placeholder for
later — the turn will raise a KeyError at the first request. Either write the state key today or use
`{product?}`, and add a render test against an empty state so this can't ship again."*

**The interview question:** *"how do you personalise a system prompt per user?"* The answer that shows
you have done it: "Template the prompt against session state rather than building two prompts, so
there's one document to review. The thing to be careful about is that the prompt has now got runtime
dependencies that don't look like code — every `{key}` is a requirement on the session, and no
refactoring tool knows that, so renaming a state key silently breaks the prompt. I add a render test
against an empty state and one against a realistic state, both free because rendering doesn't call the
model. And I'd warn anyone coming from Python that doubling the braces doesn't escape them in ADK —
`{{x}}` substitutes exactly like `{x}`, so the instinctive escape makes the string no safer at all."
