# 1.1 — One agent is usually the right answer

## One-line answer

A multi-agent system is a cost you pay for a specific reason, and the reason is never "one agent
felt like a lot" — so the first honest question of this day is why you would not simply write better
instructions for the agent you already have.

## The story

There is a tailor at the end of a market street who works alone.

You bring a pair of trousers to be taken up. He looks at them, looks at you, marks the fold with a
sliver of chalk, and tells you to come back on Thursday. On Thursday they are done, and they are
right. He cuts, he pins, he sews, he presses, and he hands them across the counter in a paper bag
with your name written on the corner.

Nobody has ever suggested he needs a team. He does not need a person to do the pinning and a
separate person to do the pressing, and if you asked him he would look at you strangely, because
pinning and pressing are not two jobs. They are one job with a start and an end, held in one head,
and the head that pinned it is the head that knows why the press goes where it goes.

The shop across the road has four people in it, and your trousers take longer.

## The idea in plain language

A **multi-agent system** is one where the work is divided between several separately-instructed
language models, each with its own instructions, its own tools, and its own turn. An
**orchestrator** is the one that decides which of the others runs and when.

Everybody wants to build one. It looks like architecture. It draws well on a whiteboard, with boxes
that have job titles.

The uncomfortable fact you need before you build one is that **most systems that were split into
agents would have been better as one agent with better instructions**. This is not a fringe position
and it is not a warning about complexity for its own sake. It is arithmetic, and the day will
measure every term in it:

- **Every agent is a model call.** Days 24 and 51 established the currency for this project: not
  money, but requests, per provider, per window. A three-agent flow does not cost three times as
  much design; it costs three times as many requests, and
  [5.2](../05-does-it-help/5.2-what-the-pair-costs-in-requests.md) prices it.
- **Every hand-off loses context.** Day 55 built the hand-off and measured what does not survive it.
  A single agent holding the whole problem has, by definition, lost nothing.
- **Every agent is a place a bug can hide.** When one agent gives a bad answer you read one
  instruction block. When six agents produce a bad answer you read six, plus the routing between
  them, and [8.1](../08-in-production/8.1-six-calls-one-answer-one-bug.md) is about the afternoon
  that costs.

So the burden of proof is on the split. The rest of section 1 is that burden being discharged
honestly: [1.2](1.2-what-a-second-duty-costs-the-first.md) measures the one thing a single agent
genuinely cannot do, and [1.3](1.3-the-three-questions-that-decide-a-split.md) turns it into three
questions you can ask about any proposed division of labour.

One term to define now, because it is the thing that actually breaks and it will be used for the
rest of the day. **Instruction dilution** is what happens when an agent is given more
responsibilities than one pass can hold: nothing is removed from the instructions, and yet some of
them stop being honoured. It is not forgetting. The instruction is still there, in the prompt, in
full, and the output does not reflect it.

## Why Sutra needs it

Day 58 assembles the triage graph — intake, classify, research, draft, review — and each of those
five stages is a decision about whether the work belongs to a separate agent or is one more
paragraph in an instruction block that already exists.

If you arrive at Day 58 believing that more agents is better design, you will build five agents, and
the graph will cost five requests per ticket where two would have done, and the free tier that
[5.2](../05-does-it-help/5.2-what-the-pair-costs-in-requests.md) prices will run out before the
afternoon does. The purpose of this part is that you arrive at Day 58 having to *argue* for each
split.

The desk gives the argument its shape. Sutra's reply-writing already works as a single agent: it has
a ticket, retrieved history from Days 49 and 50, and instructions about what a good reply contains.
It produces replies. The question this day answers is not "how do I build a multi-agent system" but
"is there something wrong with those replies that a second head would fix, and is it worth four times
the requests?"

## The mechanism

Here is the single-agent version of the desk's reply writer, stated as what it is: one instruction
block with five rules in it.

```python
# The desk's reply standard, as a single agent would receive it: five rules, one pass.
DUTIES = ("cause", "fix", "next_step", "no_jargon", "short")

# Two more the desk adds three months later, because a single agent is the easy place
# to put a new rule. Nothing is removed to make room.
LATER = ("cite_ticket", "match_tone")
```

**Line by line:**

- `DUTIES` is the house standard from `lab/_desk.py`, reduced to its keys: name the cause, state the
  fix, give a next step, use no jargon, keep it short. Each of these is one sentence in a real
  instruction block.
- `LATER` is the part that matters and the part nobody plans for. Instruction blocks are append-only
  in practice. A rule gets added the week somebody complains, and no rule is ever deleted, because
  deleting a rule requires knowing which complaint it came from.
- Both are plain tuples rather than prose, so that the next part can count them. A rule you cannot
  count is a rule you cannot measure the loss of.

Run the single-agent arm and look at what one pass delivers:

```bash
cd days/day-57-orchestrator-and-critic/lab
uv run python onehead.py
```

**Line by line:**

- `onehead.py` holds a constant called `ATTENTION`, which is how many instructions one pass reliably
  honours. It is a knob standing in for a real effect, not a law of nature, and
  [1.2](1.2-what-a-second-duty-costs-the-first.md) is where that effect is named and cited.
- The script prints what was asked for and what was delivered on two different days of the shop's
  life: five duties, then seven. Printing both is the point — one number alone looks like a fact
  about the model, and two numbers show a direction.
- No model is called. Every number on this day comes from a run, and this run costs nothing.

Measured on 2026-09-05:

```text
one agent, attention 4:
  day one   (five duties)
    asked for  ['cause', 'fix', 'next_step', 'no_jargon', 'short']
    delivered  ['cause', 'fix', 'next_step', 'no_jargon']
    dropped    ['short']
  day ninety (seven duties)
    asked for  ['cause', 'fix', 'next_step', 'no_jargon', 'short', 'cite_ticket', 'match_tone']
    delivered  ['cause', 'fix', 'next_step', 'no_jargon']
    dropped    ['short', 'cite_ticket', 'match_tone']

  dropped at five duties:  1
  dropped at seven duties: 3
```

**On day one the single agent is fine.** One rule out of five slips. That is a reply that is a little
long, which is a real cost and a small one, and against it stands the fact that the whole thing is
one instruction block, one request per ticket, and one place to look when something is wrong. A
reader who stopped here and shipped the single agent would be making a defensible engineering
decision, and this part exists so that they know that.

**On day ninety nothing has changed except that two rules were added.** The instruction block still
contains all seven. Nobody removed anything. Three rules are now not being honoured, and — this is
the part that makes it hard to catch — **the two rules that were dropped are the two that were just
added**, which are the two somebody is currently watching. The person who added `match_tone` will
report that it does not work. The person who added `cite_ticket` will report that it does not work.
Nobody will report that these two arrived together and that `short` quietly stopped working at the
same time.

That is the shape of instruction dilution, and it is why the honest counter-argument in this part is
"one agent, *until*" rather than "one agent".

## When it breaks

The failure of this argument is the reader who takes the wrong half of it and builds nothing.

There is a real error you can produce right now, and it is worth producing, because it shows that the
single agent's limit is a limit and not a preference. Set the attention knob past the number of
duties and watch the whole argument evaporate:

```bash
cd days/day-57-orchestrator-and-critic/lab
uv run python -c "import onehead; print(onehead.satisfied(onehead.DUTIES + onehead.LATER, attention=99))"
```

```text
('cause', 'fix', 'next_step', 'no_jargon', 'short', 'cite_ticket', 'match_tone')
```

Nothing is dropped. If a single pass could genuinely hold every rule you will ever add, this day
would not exist, and the correct architecture for Sutra would be one agent with a long instruction
block. **The entire case for a second head rests on that knob being finite**, so the case has to be
made against a measurement rather than against a feeling — which is what the next part does.

The other break is quieter and has no error text at all. Split a single agent that was working, and
the failure is not that anything crashes; it is that the reply gets slightly worse and the request
count triples, and no dashboard shows either, because the dashboard counts runs and not rubric
lines. [5.1](../05-does-it-help/5.1-did-the-critic-actually-help.md) exists to make that one visible.

## In production

**What a professional writes instead of the teaching version.** They do not start with an
architecture. They start with the single agent, ship it, and instrument it — one counter per rule in
the standard, incremented when the rule is honoured. The split happens when a specific counter has
been flat for a month and prompt changes have stopped moving it. That way the second agent is
introduced against a number, and can later be *removed* against the same number, which is the part
teams forget: an architecture with no metric behind it can never be simplified, because nobody can
show that removing it is safe.

**What degrades at scale.** Instruction blocks grow monotonically and nobody owns them. The failure
appears as a slow drift rather than an incident: replies get longer over a quarter, and the rule
that says they should be short is still sitting there in line forty of the prompt. By the time
somebody notices, the block has fifteen rules and no history, and there is no way to tell which of
them are load-bearing. This is why a written standard held as **data** rather than as prose matters
so much later in the day ([3.2](../03-the-critic/3.2-a-critic-needs-something-it-can-fail-against.md)):
a rule in a table can be counted, versioned and deleted; a sentence in a paragraph cannot.

**The failure mode that only appears with real traffic.** The single agent looks fine on the tickets
you tested it on, because you tested it on tickets where the rules do not compete. Real traffic
contains the ticket where the cause is genuinely complicated, and explaining it properly makes the
reply long — so `cause` and `short` are now in direct conflict, and one instruction block has no way
to express which of them wins. A second head does not automatically solve that either, but it gives
you somewhere to put the priority.

**The review comment a senior engineer leaves:** *"Before I look at the graph — what is the single
agent doing wrong? I want the rule it stopped honouring and the number that shows it, not 'separation
of concerns'. If the answer is that we have not measured, then this pull request is three times the
quota for a hypothesis."*

**The interview question:** *"When would you use multiple agents?"* An honest answer names the cost
first: *"Rarely, and I would want a measurement first. Each agent is another request against a rate
limit, another hand-off that loses context, and another instruction block to read when the output is
wrong. The case for splitting is when one agent has more duties than a single pass honours — I
measured that on my own standard: at five rules one was being dropped, and at seven rules three
were, including the two we had just added, which is the version that is hard to spot because the
rules that go missing are the newest ones. What I would not accept is a split justified by tidiness.
If I cannot say which rule the second agent rescues, I have added latency and quota for a diagram."*
