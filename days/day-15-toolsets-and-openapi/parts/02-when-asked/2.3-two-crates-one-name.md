# 2.3 — Two crates, one name

## One-line answer

Two toolsets can offer tools with the same name, and the later one **shadows** the earlier one with
only a log warning — `tool_name_prefix` is the constructor argument that stops it, by renaming a copy
of every tool the crate hands back.

## The story

Two buses pull into the same stop, and both of them say **12** on the front.

For years there was one route 12. Then the council extended the service, and the new branch turns off
after the hospital and goes to the retail park instead of the town centre. Same number on the front,
because it is the same route as far as the hospital, and nobody wanted to renumber a route people
have used for thirty years.

For the first fortnight it is fine, because the drivers tell people. After that it is not fine. You
get on a 12, you have been getting on a 12 your whole adult life, and you end up at a retail park.
Nothing was broken. The stop was right, the number was right, the bus was a real 12. There were
simply two things with one name, and you had no way to tell which one had arrived.

So the council prints new blinds: **12A** and **12B**. Two letters, and the ambiguity is gone.

## The idea in plain language

A tool's **name** is not a label. It is the identifier the model uses to ask for it, and it is the
key ADK looks the tool up by when the request comes back. It has to be unique inside one agent.

Nothing stops two toolsets offering the same name. Two vendors' APIs both have a status endpoint;
both specs call it `getStatus`; both generate a tool called `get_status`. Neither crate knows the
other exists.

`tool_name_prefix` is a keyword argument to any toolset's constructor. Give a crate a prefix and
every tool it hands back comes out as `<prefix>_<name>`. The two crates become `acme_get_status` and
`globex_get_status`, and the ambiguity is gone the way the bus blinds fixed it: not by changing what
the routes do, but by giving them distinguishable names.

Two details that matter more than they look:

- **The renaming happens in the wrapper**, not in your method. Your `get_tools` returns
  `get_status`; the agent receives `acme_get_status`. This is
  [2.1](2.1-the-wrapper-adk-actually-calls.md)'s point arriving with consequences.
- **The original tool object is not modified.** ADK makes a shallow copy of each tool, renames the
  copy, and patches the copy's declaration. The tool you built is still called `get_status`, which is
  what makes the same crate safely reusable in a second agent with a different prefix.

## Why Sutra needs it

Section 4 generates tools from a vendor's OpenAPI description. Sutra will not have one vendor for
long: the triage desk needs a status API, and Phase 6 adds the ticket archive, and each of them
publishes a spec written by somebody who has never heard of the other.

The moment the second one arrives, the names collide on whatever both APIs happen to call the same
thing — and `status`, `health`, `search` and `list` are the four names every API in the world uses.
The prefix is how Sutra keeps them apart without editing anybody's spec.

It matters again, harder, in **Phase 5**. On Day 32 an agent holds tools from more than one MCP
server, and those servers are written by strangers who cannot coordinate names even in principle.

## The mechanism

From `.venv/Lib/site-packages/google/adk/tools/base_toolset.py`, the second half of
`get_tools_with_prefix`:

```python
if not self.tool_name_prefix:
    self._cached_invocation_id = invocation_id
    self._cached_prefixed_tools = tools
    return tools

prefix = self.tool_name_prefix

# Create copies of tools to avoid modifying original instances
prefixed_tools = []
for tool in tools:
    tool_copy = copy.copy(tool)
    prefixed_name = f"{prefix}_{tool.name}"
    tool_copy.name = prefixed_name
    ...
    prefixed_tools.append(tool_copy)
```

**Line by line:**

- `if not self.tool_name_prefix` — no prefix is the common case and it returns early. Note it tests
  falsiness, so `tool_name_prefix=""` behaves exactly like `None`; you cannot ask for an empty
  prefix and get an underscore.
- `copy.copy(tool)` — a **shallow** copy. The copy shares everything with the original except the
  attributes reassigned below, which is why renaming the copy leaves your tool object alone and why
  this is cheap even for forty tools.
- `f"{prefix}_{tool.name}"` — an underscore, always, and you do not get a say in it. A prefix of
  `acme-` produces `acme-_get_status`, which is a valid Python string and an invalid tool name in
  most model APIs. Use bare words.
- `tool_copy.name = prefixed_name` — the name the agent's dispatch table will be keyed by.
- The elided lines patch `_get_declaration` so the **declaration sent to the model** carries the new
  name too. Both have to change: the declaration is what the model reads, and the name is what ADK
  looks up when the model answers. Change only one and the model asks for a tool that cannot be
  found.

Here is the collision and the fix in one script:

```python
# lab/prefixed.py - two crates, one tool name, and two letters that fix it. Zero model calls.
from __future__ import annotations

import asyncio

from google.adk.agents import LlmAgent
from google.adk.tools.base_toolset import BaseToolset
from google.adk.tools.function_tool import FunctionTool

from stateless import ReactiveModel


def get_status(region: str) -> dict:
    """Current platform status for a region."""
    return {"state": "degraded"}


class Vendor(BaseToolset):
    """One vendor's crate. Two of these is the whole experiment."""

    async def get_tools(self, readonly_context=None):
        return [FunctionTool(func=get_status)]


async def show(label: str, agent: LlmAgent) -> None:
    tools = await agent.canonical_tools()
    print(f"{label}: {[t.name for t in tools]}")


async def main() -> None:
    await show(
        "a) two crates, no prefix   ",
        LlmAgent(name="d", model=ReactiveModel(model="s"), tools=[Vendor(), Vendor()]),
    )
    await show(
        "b) two crates, prefixed    ",
        LlmAgent(
            name="d",
            model=ReactiveModel(model="s"),
            tools=[Vendor(tool_name_prefix="acme"), Vendor(tool_name_prefix="globex")],
        ),
    )
    print("c) the original tool object is untouched:")
    crate = Vendor(tool_name_prefix="acme")
    prefixed = await crate.get_tools_with_prefix(None)
    raw = await crate.get_tools()
    print(f"   through the wrapper: {[t.name for t in prefixed]}")
    print(f"   your own method:     {[t.name for t in raw]}")
    print(f"   declaration name:    {prefixed[0]._get_declaration().name!r}")


asyncio.run(main())
```

**Line by line:**

- `tools=[Vendor(), Vendor()]` — two separate instances of the same crate, which is the honest stand-in
  for two different vendors' crates that happen to agree on a name. Using one class keeps the script
  about names and not about two vendors.
- `Vendor(tool_name_prefix="acme")` — keyword-only, as
  [1.2](../01-crate-not-list/1.2-one-method-and-the-import.md) showed. `Vendor("acme")` is a
  `TypeError`, and a helpful one.
- Case **c** calls **both** entry points on the same instant of the same object. That is the only way
  to see that the rename is not destructive.
- `prefixed[0]._get_declaration()` — reaching for a private method, deliberately, because the
  declaration is the thing the model actually reads and the public surface does not expose it. In a
  test you would assert on this; in library code you would not touch it.

Run it:

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python prefixed.py

a) two crates, no prefix   : ['get_status', 'get_status']
b) two crates, prefixed    : ['acme_get_status', 'globex_get_status']
c) the original tool object is untouched:
   through the wrapper: ['acme_get_status']
   your own method:     ['get_status']
   declaration name:    'acme_get_status'
```

**Case a is the finding.** Two tools, one name, and resolving them raised nothing at all. Verified
against the installed `google-adk` 2.7.1 on 2026-08-30.

## When it breaks

Resolving the tools is silent. Running the agent is not — but only just:

```text
WARNING:root:Duplicate tool name 'get_status': the previously registered tool is shadowed and can no longer be called.
```

Three things about that line are worth reading slowly.

**"the previously registered tool is shadowed"** — the *later* crate wins. So which vendor's status
API your agent actually calls is decided by the order of the entries in `tools=[...]`, a list whose
order nobody thinks of as meaningful. Move one line and the behaviour changes with no other edit.

**It is on the root logger** — `WARNING:root:`, not `WARNING google_adk...`. If your application
configures the `google_adk` logger specifically, as a careful deployment does, this warning is not on
it and your filter will not catch it.

**It appears once per model call**, not once per run, because the dispatch table is rebuilt each
turn. So a run with one tool call logs it twice. That is a small thing that makes the line look like
noise in a busy log, which is exactly how a real warning gets tuned out.

The fix is a prefix on at least one of the two crates. The fix that is not a fix is renaming the
underlying function, because on a generated toolset you do not own the name —
[4.4](../04-machine-packed/4.4-the-name-you-did-not-choose.md) is about who does.

## In production

**Prefix every crate you did not write, from the first one.** The cost is one keyword argument; the
cost of not doing it is a rename later, after the tool names have reached your logs, your evals and
possibly a prompt. Names are an interface, and this is the cheapest moment this name will ever be.

**Prefixes are not free at the model.** `acme_get_status` is longer than `get_status`, and every tool
name appears in every model request. More importantly, a badly chosen prefix damages tool selection:
the model reads names as meaning, and `ts1_get_status` tells it nothing while `acme_get_status` tells
it which vendor. Prefix with the thing a reader would say out loud — the vendor, the domain — never
with an internal identifier.

**Watch the length limit.** [4.4](../04-machine-packed/4.4-the-name-you-did-not-choose.md) shows that
a generated tool name is truncated to sixty characters, and the prefix is added **after** that
truncation. A long prefix on an already-long generated name produces something over the limit that
nobody checked. If your prefixes are longer than one short word, assert on the final names in a test.

The review comment on a diff that adds a second toolset without a prefix is one line: *"these two
both expose `search` — which one wins?"* The interview version goes further, and it is a good
question: *"you have two MCP servers and both expose a tool called `read_file` — what happens, and
what would you have done before it happened?"*
