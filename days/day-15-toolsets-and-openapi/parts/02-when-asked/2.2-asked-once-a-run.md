# 2.2 — Asked once a run, not once a turn

## One-line answer

`get_tools` is called **exactly once per request**, no matter how many model calls or tool calls that
request contains, because `get_tools_with_prefix` caches the answer against the request's
`invocation_id`.

## The story

A table of six in a busy restaurant.

The waiter comes over once, goes round the table, writes down all six orders, and walks away. That
is the whole conversation about food. Everything after it — the starters arriving, the mains,
somebody's plate going back because it is cold — happens without anyone being asked again what they
would like.

Now the person on the end changes their mind. The moment the waiter turned away, they decided they
wanted the fish after all. They say so, quietly, to the table. Everyone at the table now knows. The
kitchen does not, and the kitchen is not going to find out, because the asking already happened and
it happened once.

They will get what they originally ordered. Not because anybody ignored them — because the question
was asked at the start of the meal and not continuously throughout it.

## The idea in plain language

Two words that get confused, and the whole part is about telling them apart.

- A **run** — ADK calls it an *invocation* — is one request. One user message goes in, one final
  answer comes out. It carries an `invocation_id`, a string that identifies it.
- A **model call** is one round trip to the model. A run contains at least one, and more if the model
  asks for tools: [Day 14](../../../day-14-plugins-one-layer-up/LESSON.md) measured this — one tool
  call costs two model calls, because the model is asked once to decide and once again to answer with
  the result in hand.

So a single run with two tool calls in it makes three model calls. The natural assumption is that
the toolset gets asked before each of those three, since each one carries a fresh tool list.

It does not. It gets asked **once**, at the start of the run, and every model call in that run is
built from the same cached answer. `get_tools_with_prefix` remembers the answer along with the
`invocation_id` it was computed for, and hands the same list back for the rest of the request.

The consequence is not obvious and it goes both ways:

- **Good:** an expensive `get_tools` is paid for once per request rather than once per turn. A crate
  that talks to a remote server does not talk to it three times.
- **Bad:** a crate whose inventory depends on session state is reading state **as it was at the start
  of the run**. If a tool writes to state and you expected that to unlock a second tool, it will not
  — not in this run.

## Why Sutra needs it

[1.3](../01-crate-not-list/1.3-what-the-crate-can-see.md) built exactly the crate this bites:
`recall_last_triage` is offered only when `state["triage"]` exists. The obvious next thought is to
have `record_triage` write that key and let the model then recall it, in the same conversation, in
one go. It cannot. The inventory for this run was decided before the first model call, and writing
the key mid-run changes nothing until the customer's **next** message.

That is not a bug to fix; it is a design constraint to know. It also decides where a cost goes. On
**Day 33** an MCP toolset's `get_tools` is a network round trip to another process, and "once per
request" versus "once per model call" is the difference between one hop and three on a slow link.

## The mechanism

From `.venv/Lib/site-packages/google/adk/tools/base_toolset.py`, with the renaming half left out
(that is [2.3](2.3-two-crates-one-name.md)):

```python
@final
async def get_tools_with_prefix(
    self,
    readonly_context: Optional[ReadonlyContext] = None,
) -> list[BaseTool]:
    invocation_id = readonly_context.invocation_id if readonly_context else None

    if (
        self._use_invocation_cache
        and self._cached_prefixed_tools is not None
        and self._cached_invocation_id == invocation_id
    ):
        return self._cached_prefixed_tools

    tools = await self.get_tools(readonly_context)
    ...
    self._cached_invocation_id = invocation_id
    self._cached_prefixed_tools = tools
    return tools
```

**Line by line:**

- `invocation_id = readonly_context.invocation_id if readonly_context else None` — the cache key. If
  there is no context, the key is `None`, which is itself a valid key: two context-free calls in a
  row hit the cache, which is a small surprise waiting in your tests.
- `self._use_invocation_cache` — an instance attribute set to `True` in `__init__`. It is not a
  constructor argument, so turning it off means setting the private attribute yourself. ADK's own
  `SkillToolset` does exactly that; see *In production*.
- `self._cached_prefixed_tools is not None` — an empty list is **not** `None`, so a crate that
  legitimately returns no tools caches that answer like any other. Returning `[]` is remembered, not
  retried.
- `self._cached_invocation_id == invocation_id` — the actual freshness test. A new run has a new id,
  so the first call in each run misses and recomputes.
- `tools = await self.get_tools(readonly_context)` — your method, called exactly here and nowhere
  else in the framework.
- The two assignments after it — the answer and the key stored together. Note there is no expiry and
  no size limit: the cache holds one entry, replaced whenever the id changes.

Here is the measurement:

```python
# lab/how_often.py - model calls, tool calls and asks, side by side. Zero model calls.
from __future__ import annotations

import asyncio

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.adk.tools.base_toolset import BaseToolset
from google.adk.tools.function_tool import FunctionTool
from google.genai import types

from stateless import ReactiveModel

MODEL_CALLS = 0


class Counted(ReactiveModel):
    """The Day 14 model, plus a tally of how often it was asked."""

    async def generate_content_async(self, llm_request, stream=False):
        global MODEL_CALLS
        MODEL_CALLS += 1
        async for response in super().generate_content_async(llm_request, stream):
            yield response


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    return {"id": ticket_id, "summary": "charged twice"}


def search_kb(query: str) -> dict:
    """Search the known-issue knowledge base."""
    return {"hits": ["KB-104"]}


class Counting(BaseToolset):
    """Counts how many times ADK asks for the inventory."""

    def __init__(self, **kwargs) -> None:
        super().__init__(**kwargs)
        self.asks = 0

    async def get_tools(self, readonly_context=None):
        self.asks += 1
        return [FunctionTool(func=lookup_ticket), FunctionTool(func=search_kb)]


async def one_run(crate: Counting, chain: list[str]) -> None:
    agent = LlmAgent(name="desk", model=Counted(model="s", chain=chain), tools=[crate])
    runner = Runner(app=App(name="d15", root_agent=agent), session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name="d15", user_id="alia")
    async for _ in runner.run_async(
        user_id="alia",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="ticket 4521?")]),
    ):
        pass


async def case(label: str, chain: list[str], runs: int) -> None:
    global MODEL_CALLS
    MODEL_CALLS = 0
    crate = Counting()
    for _ in range(runs):
        await one_run(crate, chain)
    print(f"{label}: model calls {MODEL_CALLS}, tool calls {len(chain) * runs}, asks {crate.asks}")


async def main() -> None:
    await case("a) no tools used, one run     ", [], 1)
    await case("b) one tool call, one run     ", ["lookup_ticket"], 1)
    await case("c) two tool calls, one run    ", ["lookup_ticket", "search_kb"], 1)
    await case("d) one tool call, three runs  ", ["lookup_ticket"], 3)


asyncio.run(main())
```

**Line by line:**

- `class Counted(ReactiveModel)` — the Day 14 test double with a counter wrapped round it. Subclassing
  rather than editing keeps `stateless.py` the thing every other script imports.
- `global MODEL_CALLS` and a module-level counter — deliberately *not* an attribute on the model. The
  agent is rebuilt for each run, so an attribute would reset between runs and case **d** would print
  `2` instead of `6`. The counter has to outlive the object being counted.
- `async for response in super().generate_content_async(...)` then `yield` — this is how you wrap an
  async generator. Returning the parent's generator directly would work here and would break the
  moment you wanted to do anything after the loop; wrapping is the habit worth having.
- `self.asks += 1` as the **first** line of `get_tools` — before any work, so a call that later
  raises still counts as an ask.
- `super().__init__(**kwargs)` before `self.asks = 0` — [1.2](../01-crate-not-list/1.2-one-method-and-the-import.md)'s
  rule. Without it the base class's cache attributes never exist and the crate fails on its first ask.
- One `crate` reused across the `runs` loop in `case`, with a **new agent and runner each time** —
  that is what makes case **d** a test of the cache key rather than of object lifetime.

Run it:

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python how_often.py

a) no tools used, one run     : model calls 1, tool calls 0, asks 1
b) one tool call, one run     : model calls 2, tool calls 1, asks 1
c) two tool calls, one run    : model calls 3, tool calls 2, asks 1
d) one tool call, three runs  : model calls 6, tool calls 3, asks 3
```

**Read the last column against the first.** Model calls go 1, 2, 3, 6. Asks go 1, 1, 1, 3. The ask
count does not track model calls at all — it tracks **runs**, exactly one apiece.

Verified against the installed `google-adk` 2.7.1 on 2026-08-30. The caching is not described on
`adk.dev/tools-custom/`; it is read from the package and measured here.

## When it breaks

There is no error text for this one. The failure is a feature that does not arrive:

```python
async def get_tools(self, readonly_context=None):
    tools = [FunctionTool(func=lookup_ticket), FunctionTool(func=record_triage)]
    if readonly_context is not None and readonly_context.state.get("triage"):
        tools.append(FunctionTool(func=recall_last_triage))
    return tools
```

**Line by line:**

- `record_triage` is always offered, so the model can write `state["triage"]` during the run.
- The `if` then offers `recall_last_triage` once that key exists — which is correct logic and reads
  as though the second tool becomes available as soon as the first has run.
- It does not. The `if` was evaluated once, before the first model call, when `state` was empty.
  `record_triage` writes the key, the model looks for `recall_last_triage`, and it is not in the
  list — because the list was decided before any of that happened.

What you see is a model that says it cannot recall anything, in a conversation where it just recorded
something. There is no traceback, no warning, and the tool is demonstrably present in the code. The
way to confirm it in ten seconds is the counter above: add a `print(sorted(readonly_context.state))`
to `get_tools` and watch it print `[]` exactly once in a run where you know the key was written.

The fix is not to defeat the cache. It is to accept that inventory is per-run: offer both tools and
let `recall_last_triage` return an honest "nothing recorded yet", which is what
[Day 11](../../../day-11-tool-context/LESSON.md) had it do in the first place.

## In production

**The cache is why a network call in `get_tools` is survivable, and why it is still a risk.** Once
per request is a defensible budget; it is also on the critical path, before the model has been
called, with the user waiting. The number to know is not "how long does `get_tools` take" but "how
long does it take at the 99th percentile when the thing it calls is unwell". A crate that queries a
remote catalogue with no timeout has added an unbounded wait to every request your agent serves, and
the swallowed exception from [2.1](2.1-the-wrapper-adk-actually-calls.md) means a *failure* there is
quieter than a *slowness* there. Set a timeout, and decide in advance whether a timeout means "no
tools" or "fail the run" — those are different products.

**The cache holds exactly one entry.** Under concurrency — several requests being served by one
process, which is every deployment — the single `_cached_invocation_id` slot is overwritten by
whichever run asked last. Each run's first ask still recomputes for its own id, so correctness holds;
what does not hold is your mental model of it as a cache that saves work across users. At ten
concurrent runs it saves almost nothing and every run recomputes. Budget for `get_tools` running once
per request per user, not once per process.

**ADK turns the cache off in its own code when the inventory must be live.** `SkillToolset` sets
`self._use_invocation_cache = False`. That is the escape hatch and it is a private attribute, which
is the framework saying *you may need this and you should think first*. If you set it, the thing you
have bought is a fresh inventory per model call and the thing you have paid is that same `get_tools`
running two or three times per request instead of once.

The interview question is a good one because the wrong answer sounds informed: *"your toolset reads
from the database — how many times does that query run during one user request, and how would you
find out rather than assume?"*
