# 1.2 — One method, and an import that is not where you would look

## One-line answer

`BaseToolset` requires you to write exactly one method — `async get_tools(...)` — and it is imported
from `google.adk.tools.base_toolset`, not from `google.adk.tools`, where its close relative
`BaseTool` lives.

## The story

Your first morning at a new job.

The whole role, as your manager explained it, is one sentence: when a delivery arrives, check it
against the note and sign. That is it. There is a long staff handbook, but the part that is
genuinely yours is one line, and everything else in the building runs whether you do it or not.

Then you arrive. You walk to the front doors, which have the company's name over them, and they are
locked. There is no sign, no arrow, nothing rude about it — the staff entrance is simply round the
back, past the bins, and everyone who works there has known that for years.

Two facts about the same job, and they are unrelated to each other. One is about what you have to
do. The other is about where the door is. Neither one helps you with the other, and you need both
before you can start.

## The idea in plain language

A **base class** is a class you inherit from, which gives you working behaviour for free and marks
some parts as yours to fill in. The parts marked as yours are called **abstract methods**: Python
refuses to build an object of your class until every one of them exists.

`BaseToolset` has exactly one abstract method:

```
async def get_tools(self, readonly_context=None) -> list[BaseTool]
```

Everything else it gives you is optional. That is the whole contract, and it is worth saying plainly
because the class itself is long: most of what is in it is machinery you inherit and do not
override.

The second fact is about **import paths**. A Python package can choose which names it re-exports
from its own `__init__.py`. `google.adk.tools` re-exports a long list of names — `BaseTool`,
`FunctionTool`, `ToolContext`, `MCPToolset` and about twenty more — and `BaseToolset` **is not on
it**. It exists; it is just not re-exported. So the obvious import fails and the one that works is
one level deeper.

That is not a bug and it is not worth being annoyed about. It is worth *knowing*, because the error
it produces sends you looking for a missing package.

## Why Sutra needs it

Every toolset in the rest of this day is a subclass of this class, and
[7.2](../07-in-production/7.2-testing-a-toolset-without-a-model.md) tests one. If the import line is
wrong, none of it runs.

The abstract-method half matters again in **Phase 5**, on Day 33, where an MCP server is wrapped as
a toolset and the same single method is what you implement — except that there, `get_tools` goes
over a network to find out its answer, which is exactly why the method is `async` even when yours
does nothing that needs awaiting.

## The mechanism

Here is the contract, read from the installed package at
`.venv/Lib/site-packages/google/adk/tools/base_toolset.py`:

```python
class BaseToolset(ABC):
    """Base class for toolset.

    A toolset is a collection of tools that can be used by an agent.
    """

    def __init__(
        self,
        *,
        tool_filter: Optional[Union[ToolPredicate, List[str]]] = None,
        tool_name_prefix: Optional[str] = None,
    ): ...

    @abstractmethod
    async def get_tools(
        self,
        readonly_context: Optional[ReadonlyContext] = None,
    ) -> list[BaseTool]:
        """Return all tools in the toolset based on the provided context."""

    async def close(self) -> None:
        """Performs cleanup and releases resources held by the toolset."""
```

**Line by line:**

- `class BaseToolset(ABC)` — `ABC` is Python's *abstract base class*. It is what makes the
  `@abstractmethod` below actually refuse to instantiate rather than merely suggest.
- `def __init__(self, *, tool_filter=..., tool_name_prefix=...)` — the base constructor takes two
  keyword arguments. The bare `*` makes them **keyword-only**: `DeskTools(["lookup_ticket"])` is a
  `TypeError`, `DeskTools(tool_filter=["lookup_ticket"])` is correct. What they do is section 3
  and [2.3](../02-when-asked/2.3-two-crates-one-name.md); what matters here is that **if you write
  your own `__init__` you must call `super().__init__(**kwargs)`**, or both silently stop working.
- `@abstractmethod` — the one thing that is yours. Omit it and the class cannot be instantiated at
  all; see *When it breaks*.
- `async def get_tools` — `async` is part of the contract, not a style choice. ADK awaits the result.
  A plain `def get_tools` returns a list where a coroutine was expected, and what fails is
  downstream of you.
- `readonly_context: Optional[ReadonlyContext] = None` — the parameter name is `readonly_context`,
  and ADK passes it **positionally** from its own call site, so renaming it is safe and dropping it
  is not. [1.3](1.3-what-the-crate-can-see.md) is about what is inside it.
- `-> list[BaseTool]` — tools, not functions. A bare Python function in this list is a type error
  waiting to become a runtime one; wrap it in `FunctionTool(func=...)` as [1.1](1.1-one-line-many-tools.md)
  did.
- `async def close(self)` — **not** abstract. It is a lifecycle hook ADK calls when the toolset is
  finished with, and the base class's version does nothing. A crate holding a database connection or
  an HTTP session overrides it; a crate holding a list does not need to.

Now the import. This script is four lines long and settles it:

```python
# lab/one_method.py - where the class lives, and what it demands. Zero model calls.
from __future__ import annotations

from google.adk.tools import BaseTool  # this one is re-exported
from google.adk.tools.base_toolset import BaseToolset  # this one is not

print("BaseTool     ->", BaseTool.__module__)
print("BaseToolset  ->", BaseToolset.__module__)

try:
    from google.adk.tools import BaseToolset as WrongPath  # noqa: F401
except ImportError as exc:
    print("the obvious import:", exc)


class Empty(BaseToolset):
    """A toolset that implements nothing."""


try:
    Empty()
except TypeError as exc:
    print("the empty subclass:", exc)
```

**Line by line:**

- `from google.adk.tools import BaseTool` — this works, and it is the reason the wrong import is so
  easy to write. The tool base class and the toolset base class are siblings in the same package,
  and only one of them is re-exported.
- `BaseTool.__module__` — where the class really lives, as opposed to where you imported it from.
  Printing both is how you confirm the claim instead of believing this document.
- `except ImportError` — not `AttributeError`. `google.adk.tools` resolves unknown names through a
  module-level `__getattr__`, which raises `AttributeError`; Python turns that into `ImportError` for
  a `from ... import ...` statement. If you catch the wrong one, your handler never runs.
- `# noqa: F401` — the import is unused on purpose; it exists to fail. Without the marker `ruff`
  removes the whole point of the line.
- `class Empty(BaseToolset)` with only a docstring — no `get_tools`, which is the one thing required.
- `Empty()` inside `try` — the failure is at **construction**, not at use. This is the good case:
  Python stops you at the line where the mistake is.

## When it breaks

The import error, in full, is the one you will actually meet:

```text
ImportError: cannot import name 'BaseToolset' from 'google.adk.tools'
(c:\Users\...\.venv\Lib\site-packages\google\adk\tools\__init__.py)
```

What it means: the package is installed and healthy, and the name is not re-exported from that
module. What it does **not** mean, despite being the first thing everyone tries: that
`google-adk` is out of date, that the feature was removed, or that you need a different version.
Running `uv add google-adk@latest` here is a wasted afternoon and a version pin you now have to
justify in `docs/PACKAGES.md`. The smallest fix is one word longer:
`from google.adk.tools.base_toolset import BaseToolset`.

The abstract-method error is friendlier, because it names the method:

```text
TypeError: Can't instantiate abstract class Empty without an implementation for abstract method
'get_tools'
```

The version of this that is *not* friendly is a typo: name your method `get_tool` or `gettools` and
you have not overridden anything, so the abstract method is still missing and you get the same
message — pointing at a method you are convinced you wrote. Read the quoted name character by
character before doing anything else.

## In production

Two things change once a toolset is real rather than a teaching example.

**`close()` stops being decorative.** A crate that holds an HTTP session, a database pool or a
subprocess must release it, and `close()` is the hook. It matters more than it looks: a long-running
agent server builds and discards toolsets across its lifetime, and a crate that opens a connection
in `__init__` and never closes it leaks one connection per instance. The symptom does not appear in
testing, because a test process exits and the operating system cleans up after it. It appears in
week two of production as a connection-pool exhaustion error naming a component that is not yours.
Day 33's MCP toolset is the first one in Sutra where this is not hypothetical.

**`super().__init__()` becomes a review comment.** Once your toolset has its own `__init__` — to
take a vendor name, a URL, a set of credentials — it must pass the base class's keyword arguments
through:

```python
def __init__(self, vendor: str, **kwargs) -> None:
    super().__init__(**kwargs)
    self.vendor = vendor
```

**Line by line:**

- `**kwargs` in the signature — collects `tool_filter` and `tool_name_prefix` without your class
  having to know about them, so it keeps working when ADK adds a third.
- `super().__init__(**kwargs)` — hands them to the base class. Omit this line and
  `DeskTools(tool_filter=[...])` raises a `TypeError` about an unexpected argument, which is the
  *good* outcome. The bad outcome is writing `def __init__(self, vendor, tool_filter=None)` and
  quietly storing `tool_filter` on `self` yourself, at which point the attribute exists, the
  constructor accepts it, and nothing filters anything. That is
  [3.1](../03-the-filter/3.1-a-filter-you-have-to-apply-yourself.md), arriving early.
- `self.vendor = vendor` **after** the `super()` call — the base constructor sets several attributes,
  and setting yours first works today but is the kind of ordering that breaks on an upgrade.

The interview question here is not about imports. It is: *"your toolset opens a connection — where
do you close it, and how would you know if you had not?"*
