# 1.1 — One line, many tools

## One-line answer

An agent's `tools=[...]` list does not have to contain tools: one entry can be a **toolset**, an
object ADK asks for its contents at the moment the agent needs them.

## The story

Think about a playlist on your phone.

Most lines on it are one song. You picked that song, you know what it is, and it will still be that
song next week. But one line is not a song at all — it is a whole album. It sits on the playlist as
a single line, and when the music actually plays, that one line turns into eleven tracks.

Now the interesting part. If the album gets a bonus track next month, your playlist changes without
you touching it. You never added a line. The line you added says *this album*, and what that means
is decided at the moment the music plays, not at the moment you typed it.

You did not put eleven songs on the playlist. You put one line that knows how to become eleven
songs.

## The idea in plain language

Since [Day 10](../../../day-10-function-tools/LESSON.md) you have given an agent its tools as a
plain Python list:

```
tools=[lookup_ticket, search_kb]
```

Two functions, two tools, and the list is settled the moment you write it.

A **toolset** is a third kind of thing that is allowed on that list. It is not a tool. It is an
object with one job: when asked, hand back a list of tools. ADK asks it. The list it hands back is
the list the model is shown.

That is the whole idea, and the important word is **asked**. A function on the `tools` list is
*read* — it is right there, it is what it is. A toolset is *asked* — the answer is produced by code
you wrote, at the moment of asking, and it can be a different answer than it was last time.

Three words that will be used for the rest of the day, defined once:

- **Tool** — one thing the model may call: a name, a description, an argument schema, and a body.
  Day 10 built these by hand from Python functions.
- **Toolset** — an object that produces a list of tools when asked. One entry on `tools=[...]`,
  many tools in the model's request.
- **Inventory** — what a toolset hands back on one particular asking. The word matters because
  there can be more than one, and the rest of section 2 is about when each one is taken.

Sutra's `tools=[...]` list can therefore hold three different kinds of entry, and ADK names that
union in its own source:

| What you put on the list | What ADK does with it | Where you met it |
| --- | --- | --- |
| a plain Python function | wraps it in a `FunctionTool` | Day 10 |
| a `BaseTool` object | uses it directly | Day 10, `FunctionTool` |
| a `BaseToolset` object | **asks it** for its tools, and splices them in | today |

## Why Sutra needs it

Sutra's triage desk has two tools today. It is about to need many more, and almost none of them
will be written by hand.

On **Day 16** the desk gets built-in tools that arrive already made. In **Phase 5**, starting on
Day 32, it talks to MCP servers, and an MCP server is exactly this: a toolset whose contents live
on somebody else's machine and change without asking you. If the only thing an agent could hold
were a list of functions you wrote, none of that would be expressible.

There is also a smaller, nearer reason. Day 11's tools behave differently depending on session
state, and a tool that is meaningless in one session is noise in the model's request. A toolset can
decline to offer it. That is [1.3](1.3-what-the-crate-can-see.md).

## The mechanism

The union is a real type in the installed package. From
`.venv/Lib/site-packages/google/adk/agents/llm_agent.py`:

```python
ToolUnion: TypeAlias = Union[Callable, BaseTool, BaseToolset]
```

**Line by line:**

- `TypeAlias` — this is a name for a type, not a class. Nothing is constructed here; it is the
  vocabulary ADK uses to say "an entry on the `tools` list".
- `Callable` — a plain Python function. This is why `tools=[lookup_ticket]` has worked since
  Day 10 without you wrapping anything: ADK wraps it for you.
- `BaseTool` — an already-made tool object. `FunctionTool` is one, and so is the `RestApiTool` that
  [4.2](../04-machine-packed/4.2-spec-in-tools-out.md) generates from a spec.
- `BaseToolset` — the new one. Note that it sits in the same union as the other two, which is the
  whole design: from the outside, a crate is just another thing you can put on the list.

Here is the smallest toolset that does anything, and an agent holding both kinds of entry at once:

```python
# lab/shapes.py - one list, three kinds of entry. Zero model calls.
from __future__ import annotations

import asyncio

from google.adk.agents import LlmAgent
from google.adk.tools.base_toolset import BaseToolset
from google.adk.tools.function_tool import FunctionTool

from stateless import ReactiveModel


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    return {"id": ticket_id, "summary": "charged twice"}


def search_kb(query: str) -> dict:
    """Search the known-issue knowledge base."""
    return {"hits": []}


def escalate(ticket_id: str, reason: str) -> dict:
    """Hand a ticket to a person."""
    return {"escalated": ticket_id, "reason": reason}


class DeskTools(BaseToolset):
    """A crate holding two of the desk's tools."""

    async def get_tools(self, readonly_context=None) -> list[FunctionTool]:
        return [FunctionTool(func=lookup_ticket), FunctionTool(func=search_kb)]


agent = LlmAgent(
    name="desk",
    model=ReactiveModel(model="scripted"),
    tools=[escalate, DeskTools()],
)

print("entries on the tools list:", len(agent.tools))
for entry in agent.tools:
    print("   ", type(entry).__name__ if not callable(entry) else entry.__name__)

resolved = asyncio.run(agent.canonical_tools())
print("tools the model will actually be offered:", len(resolved))
for tool in resolved:
    print("   ", tool.name)
```

**Line by line:**

- `from google.adk.tools.base_toolset import BaseToolset` — the full path, and it is not the one you
  would guess. [1.2](1.2-one-method-and-the-import.md) is about that; for now, copy it exactly.
- `FunctionTool(func=...)` — the wrapper ADK would have applied to a bare function anyway. Inside a
  toolset you must apply it yourself, because `get_tools` is declared to return `BaseTool` objects
  and a bare function is not one.
- `async def get_tools(self, readonly_context=None)` — the one method a toolset must have. It is
  `async` because a real toolset may have to go and ask something; ours does not, and still must be.
- `readonly_context=None` — the parameter ADK will pass. It is ignored here on purpose, so this part
  stays about *shape*. What is inside it is [1.3](1.3-what-the-crate-can-see.md).
- `tools=[escalate, DeskTools()]` — **two** entries: a bare function and a crate. This is the line
  the part exists to show.
- `DeskTools()` with brackets — an *instance*, not the class. Passing the class itself is a mistake
  ADK cannot catch for you; see *When it breaks*.
- `agent.canonical_tools()` — ADK's own method for "resolve every entry on the list into actual
  tools". It is `async`, so it needs `asyncio.run`. This is the same call the agent makes internally
  before every model request, which is why running it by hand proves something rather than
  simulating something.

Run it:

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python shapes.py

entries on the tools list: 2
    escalate
    DeskTools
tools the model will actually be offered: 3
    escalate
    lookup_ticket
    search_kb
```

**Two, and then three.** The list you wrote has two entries. The model is offered three tools. The
crate was opened somewhere between those two lines, and the rest of section 2 is about exactly
where.

## When it breaks

Both ways of getting this line wrong are **silent at the moment you get it wrong**, which is why
this section is longer than the mistake deserves.

**Forget the brackets** — `tools=[escalate, DeskTools]` — and the agent builds without complaint.
Resolve the tools and it still does not complain:

```text
tools the model will actually be offered: 2
    escalate
    DeskTools
```

A class is `callable`, so it matches the `Callable` arm of `ToolUnion` before the `BaseToolset` arm
is ever considered. ADK wraps your class as a `FunctionTool` named `DeskTools`, and the two tools
inside the crate are simply not there. The error finally arrives when something asks that tool to
describe itself, which happens on the first model request:

```text
pydantic.errors.PydanticUserError: `DeskToolsParams` is not fully defined; you should define
`Union`, then call `DeskToolsParams.model_rebuild()`.

For further information visit https://errors.pydantic.dev/2.13/u/class-not-fully-defined
```

Read what that names. `DeskToolsParams` is a class you never wrote — ADK built it from your class
name to describe the arguments of the "function" it thinks you handed it. `Union` is a type from
ADK's own signature. Nothing in the message says *toolset*, *brackets*, or the file you typed it in.
The smallest fix is two characters: `DeskTools()`.

**Pass the method instead of the object** — `tools=[escalate, DeskTools().get_tools]` — and there is
no error at all, ever. It resolves cleanly:

```text
tools the model will actually be offered: 2
    escalate
    get_tools
```

and the declaration handed to the model is a real, valid one:

```text
name='get_tools' description=None parameters_json_schema={'properties': {'readonly_context':
{'default': None, 'title': 'Readonly Context'}}, 'title': 'get_toolsParams', 'type': 'object'}
```

The model is now offered a tool called `get_tools` with **no description**, and the desk's actual
tools are gone. Day 10's law applies — a model chooses a tool by its name and description — so it
will never call this one, and the run will look like an agent that simply chose not to use tools.
There is no error text for this failure. The only way to see it is to print the resolved list, which
is why `canonical_tools()` is in the mechanism above rather than in a footnote.

## In production

At three tools, a list and a crate are the same thing wearing different clothes, and a reviewer will
reasonably ask why you introduced the second one.

The answer is never "it is tidier". A crate earns its place when the answer to *which tools?* is not
knowable when the agent object is constructed. There are exactly three such cases in practice, and
Sutra meets all three:

1. **The answer depends on the session** — a tool that is meaningless until something has happened.
   [1.3](1.3-what-the-crate-can-see.md).
2. **The answer is written down somewhere else** — a vendor's API description, which you did not
   write and do not control. [4.2](../04-machine-packed/4.2-spec-in-tools-out.md).
3. **The answer lives on another machine** — an MCP server, Phase 5.

If none of those three is true, a list is correct and a crate is ceremony. A senior reviewer's
comment on a needless toolset is usually one line: *"this returns the same two tools every time —
what is the crate for?"* Have the answer, or delete the crate.

The scale question is different from the tidiness question. At thirty tools spread over four crates,
the model's request carries thirty tool declarations on **every** model call, and each one costs
tokens on every turn of the loop. A crate that offers everything it has, always, is how an agent's
per-call cost quietly triples. That is what [3.1](../03-the-filter/3.1-a-filter-you-have-to-apply-yourself.md)
is for, and the interviewer's version of the question is: *"your agent has forty tools — what does
that cost you per request, and what would you do about it?"*
