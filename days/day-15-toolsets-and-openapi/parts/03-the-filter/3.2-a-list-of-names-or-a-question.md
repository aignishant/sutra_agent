# 3.2 — A list of names, or a question

## One-line answer

`tool_filter` takes either a list of exact tool names — an allowlist that cannot drift — or a
callable that is asked about each tool and can see the session, and the choice between them is a
choice about what happens when somebody adds a tool you have never heard of.

## The story

Two ways of running the door at an event.

The first is a printed list of names. Somebody typed it a week ago, it came out of the printer this
morning, and the person on the door works down it with a finger. If your name is not on it you are
not coming in, and there is no arguing, because the list is a piece of paper and the person holding
it did not write it.

The second is a rule. *Anyone with a staff badge.* Nothing is printed. The person on the door looks
at what is in front of them and decides.

Both are reasonable, and they fail in opposite directions. Someone joins the team on Thursday: the
rule lets them in, because they have a badge, and the printed list does not, because it was printed
on Monday. Then somebody starts handing out badges at reception to make life easier, and the rule
quietly lets in a great many people it was never meant to, while the printed list carries on being
exactly as wrong as it was on Monday and no more.

The list is stale by default. The rule is loose by default. You pick which failure you would rather
have.

## The idea in plain language

`_is_tool_selected` — the helper from [3.1](3.1-a-filter-you-have-to-apply-yourself.md) — accepts two
kinds of `tool_filter`, and checks for them in a fixed order.

**A list of strings.** Exact matches on `tool.name`. No wildcards, no case folding, no prefixes. It
is the printed list.

**A callable.** ADK calls it a `ToolPredicate`. It is handed the tool object and the
`ReadonlyContext` and returns `True` or `False`. It is the rule at the door.

A **predicate**, in this sense, is just a function that answers yes or no about one thing. The
signature is:

```
(tool: BaseTool, readonly_context: ReadonlyContext | None) -> bool
```

The order of the two checks is not a detail. Callables are tested **first**, and the test is
"does it have a `__call__`". Anything callable is treated as a predicate — including, if you are
unlucky, something you meant as data.

And there is a third case, which is neither, and which is where most of the accidents live:

| What you pass | What happens | Why |
| --- | --- | --- |
| `None` | every tool passes | no filter |
| `["lookup_ticket"]` | only that one | list form, exact match |
| `[]` | **every tool passes** | falsy, so it reads as "no filter" |
| `[""]` | **no tools at all** | truthy list, matching nothing |
| `{"lookup_ticket"}` — a set | **no tools at all** | not callable, not a `list` |
| `("lookup_ticket",)` — a tuple | **no tools at all** | same |
| `lambda tool, ctx: ...` | whatever it says | predicate form |

Four of those seven behaviours are surprising, and none of them raises.

## Why Sutra needs it

Section 4 generates tools from a vendor's OpenAPI description, and the vendor edits that description
whenever they like. The two filter forms answer one question differently: *what should happen when
the vendor adds an operation?*

With a list, the new operation is **not offered**, because it is not on the list. Sutra's behaviour
does not change until a person edits the list. With a predicate — say, *any operation whose name
starts with `get`* — the new operation **is** offered the moment it appears, provided it happens to
be named agreeably.

For a vendor's API, the list is almost always right, and [7.3](../07-in-production/7.3-where-trust-moved.md)
is about why. For Sutra's own crate over its own tools, where a new tool means somebody on your team
wrote one deliberately, a predicate on something structural is reasonable.

You need both forms again on **Day 40**, where an MCP server's toolset is filtered before its tools
reach an agent, and the question *"what happens when the server adds a tool?"* is the security
question rather than a convenience one.

## The mechanism

```python
# lab/names_or_rule.py - the same crate, seven filters. Zero model calls.
from __future__ import annotations

import asyncio

from google.adk.tools.base_toolset import BaseToolset
from google.adk.tools.function_tool import FunctionTool


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    return {"id": ticket_id}


def search_kb(query: str) -> dict:
    """Search the known-issue knowledge base."""
    return {"hits": []}


def escalate(ticket_id: str, reason: str) -> dict:
    """Hand a ticket to a person."""
    return {"escalated": ticket_id}


ALL = [lookup_ticket, search_kb, escalate]


class Desk(BaseToolset):
    """A crate that actually applies its filter."""

    async def get_tools(self, readonly_context=None):
        tools = [FunctionTool(func=f) for f in ALL]
        return [t for t in tools if self._is_tool_selected(t, readonly_context)]


def reads_only(tool, readonly_context=None) -> bool:
    """A predicate: nothing that changes anything."""
    return not tool.name.startswith(("escalate", "record", "delete"))


async def main() -> None:
    cases = {
        "None            ": None,
        "a list          ": ["lookup_ticket", "search_kb"],
        "empty list      ": [],
        'a list of ""    ': [""],
        "a set           ": {"lookup_ticket"},
        "a tuple         ": ("lookup_ticket",),
        "a predicate     ": reads_only,
    }
    for label, tool_filter in cases.items():
        offered = [t.name for t in await Desk(tool_filter=tool_filter).get_tools()]
        print(f"{label} -> {offered}")


asyncio.run(main())
```

**Line by line:**

- `def reads_only(tool, readonly_context=None)` — a plain function, not a lambda, because a predicate
  that is worth having is worth naming and testing on its own. Its name is what a reviewer reads.
- `readonly_context=None` with a default — ADK passes it positionally, so the name is yours to
  choose; the default is what lets you call the predicate directly in a test.
- `tool.name.startswith(("escalate", "record", "delete"))` — a **tuple** passed to `startswith`, which
  is the one place a tuple is right in this part. Note the shape of the rule: it is a denylist wearing
  a predicate's clothes, and *In production* is about why that direction matters.
- `not ...` — the predicate returns `True` for *keep*. Getting the polarity backwards gives you
  exactly the tools you meant to exclude, with no error and a plausible-looking agent.
- The `cases` dictionary keeps every filter in one place, so the output is a table rather than seven
  scattered prints. The labels are padded so the arrows line up, which matters more than it sounds
  when the finding is a comparison between rows.

Run it:

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python names_or_rule.py

None             -> ['lookup_ticket', 'search_kb', 'escalate']
a list           -> ['lookup_ticket', 'search_kb']
empty list       -> ['lookup_ticket', 'search_kb', 'escalate']
a list of ""     -> []
a set            -> []
a tuple          -> []
a predicate      -> ['lookup_ticket', 'search_kb']
```

**Rows three and four are the ones to sit with.** `[]` offers everything and `[""]` offers nothing,
and the two are one character apart. Verified against the installed `google-adk` 2.7.1 on 2026-08-30.

## When it breaks

Nothing raises, so the failures are read out of the output above.

**The set.** This is the common one, because a set is the natural Python type for a membership test
and reads better than a list:

```python
DeskTools(tool_filter={"lookup_ticket", "search_kb"})
```

`_is_tool_selected` tests `isinstance(self.tool_filter, list)`, and a set is not a list, so it falls
through to `return False` and every tool is rejected. The agent gets **no tools**. What you see is a
model answering from memory, confidently, about a ticket it never looked up. Change the braces to
brackets.

**The empty allowlist that opens the door.** Building the list at run time is where this bites:

```python
allowed = [name for name in os.environ.get("ALLOWED_TOOLS", "").split(",") if name]
DeskTools(tool_filter=allowed)
```

Set nothing, and `allowed` is `[]`, which is falsy, which `_is_tool_selected` reads as *no filter* —
so an empty allowlist offers **every** tool the crate has. That is a fail-open configuration path,
which is the direction you never want a security-shaped control to fail in. The fix is three lines and
belongs in your constructor:

```python
if allowed is not None and not allowed:
    raise ValueError("an empty allowlist would offer every tool; pass None to mean 'no filter'")
```

**Line by line:**

- `allowed is not None and not allowed` — distinguishes *not asked for* from *asked for and empty*,
  which is the distinction the framework does not make.
- `raise ValueError` rather than returning nothing — Principle 10. A misconfiguration that opens
  every tool should stop the process, not log.
- The message says what to pass instead. An error that names the correct alternative is the difference
  between a fix and a search.

## In production

**Prefer the list for anything you did not write.** The list's failure mode is that it goes stale, and
a stale allowlist offers *fewer* tools than intended, which is visible: someone reports that the agent
cannot do a thing it should be able to do, and you add a name. The predicate's failure mode is that it
matches something new, which offers *more* tools than intended, and nobody reports that. Choose the
failure that generates a support ticket over the one that does not.

**A predicate written as a denylist is the worst of both.** `reads_only` above excludes names starting
with `escalate`, `record` or `delete` — and it will happily offer `remove_account`, `purge_tickets`
and `wipe`, because nobody thought of those words. A denylist has to be right about every future name;
an allowlist only has to be right about the ones you chose. If you write a predicate, write it in the
positive: *the name is in this set of four*, or *the operation's method is GET*.

**Predicates run on every tool on every run**, so keep them pure and fast. A predicate that reads a
database or calls a policy service turns one inventory into N network calls, on the request path, once
per tool — and because they run inside `get_tools`, an exception in one of them is swallowed by
[2.1](../02-when-asked/2.1-the-wrapper-adk-actually-calls.md)'s `except Exception` and takes the whole
crate down to zero tools. Read from `readonly_context.state`, which is in memory, and nothing else.

**Filter the generated names, not the spec names.** This one costs an afternoon when it happens:
`tool_filter` matches `tool.name`, which for a generated toolset is the snake-cased `operationId`
([4.3](../04-machine-packed/4.3-where-each-part-of-a-tool-comes-from.md)) and **not** the string in the
vendor's document. An allowlist containing `getVendorStatus` matches nothing;
`get_vendor_status` is what the tool is called. And if the crate has a prefix, the prefix is applied
*after* the filter, so the filter still uses the unprefixed name. Print the resolved names once and
copy them.

The interview question is the one that separates people who have configured this from people who have
read about it: *"your allowlist is empty because the config was not set — does the agent get no tools
or all of them, and which would you rather?"*
