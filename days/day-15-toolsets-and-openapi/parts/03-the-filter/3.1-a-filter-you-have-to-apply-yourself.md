# 3.1 — A filter you are given, and have to apply yourself

## One-line answer

`tool_filter` is accepted by every toolset's constructor and applied by **none of them** unless the
subclass calls `self._is_tool_selected` inside `get_tools` — so a filter you set can be stored,
readable, and doing absolutely nothing.

## The story

A speed limit sign on a quiet road.

It says forty. It is a real sign, put there by the council after real complaints, and it is the
correct number for that road. Every driver who goes past reads it, and most of them slow down,
because most people do.

There is no camera. There has never been a camera. There is no patrol car that sits there, and the
junction is not one anybody gets stopped at. The sign is a statement of what should happen, and
between the sign and what actually happens there is nothing at all.

The dangerous part is not the drivers who ignore it. It is the residents who asked for it, saw it go
up, and stopped worrying. They have a sign. They believe they have a speed limit. What they have is
a sign.

## The idea in plain language

`BaseToolset.__init__` takes an argument called `tool_filter`. You pass it a list of tool names — or
a function, which is [3.2](3.2-a-list-of-names-or-a-question.md) — and the intent is obvious: only
these tools, please.

The base class stores it on `self.tool_filter` and gives you a helper to apply it:

```
self._is_tool_selected(tool, readonly_context) -> bool
```

And then it stops. **Nothing in the base class calls that helper.** It cannot, because the base class
does not know what your `get_tools` returns or in what order or whether filtering is even meaningful
for your crate. Applying the filter is one line in your method, and if you do not write that line the
filter is a sign with no camera.

The reason this catches people is that it looks like the opposite kind of argument. `tool_name_prefix`
is on the same constructor, right next to it, and *that* one is applied for you, in the wrapper, with
no cooperation required ([2.3](../02-when-asked/2.3-two-crates-one-name.md)). Two neighbouring
arguments, two entirely different contracts, and only one of them tells you when you have got it
wrong.

The distinction is worth naming, because it recurs everywhere in this framework:

| | `tool_name_prefix` | `tool_filter` |
| --- | --- | --- |
| Applied by | ADK, in `get_tools_with_prefix` | you, in `get_tools` |
| If you do nothing | it works | it silently does not |
| ADK's own toolsets | inherit it | each one applies it itself |

## Why Sutra needs it

Sutra is about to hold tools it did not write. A vendor's OpenAPI description generates one tool per
operation ([4.2](../04-machine-packed/4.2-spec-in-tools-out.md)), and a real vendor's API has
operations you want, operations you do not, and operations you would very much rather your agent
could not reach — `deleteAccount` sitting in the same spec as `getStatus`.

`tool_filter` is the allowlist for that. It is the difference between *the crate offers what the
vendor happens to publish* and *the crate offers the four operations we reasoned about*. On **Day 40**
this stops being hygiene and becomes the control that keeps a third-party MCP server's tools out of
your agent, and a filter that silently does nothing is worse than no filter, because you wrote it
down and stopped worrying.

## The mechanism

The helper, from `.venv/Lib/site-packages/google/adk/tools/base_toolset.py`:

```python
def _is_tool_selected(self, tool: BaseTool, readonly_context: Optional[ReadonlyContext]) -> bool:
    if not self.tool_filter:
        return True

    if isinstance(self.tool_filter, ToolPredicate):
        return self.tool_filter(tool, readonly_context)

    if isinstance(self.tool_filter, list):
        return tool.name in self.tool_filter

    return False
```

**Line by line:**

- `if not self.tool_filter: return True` — no filter means everything passes. Note it is falsiness
  again, so `tool_filter=[]` means **no filter**, not *nothing allowed*. An empty allowlist computed
  at run time from a config file therefore opens the crate completely; that is a real deployment
  failure and it is in *When it breaks*.
- `isinstance(self.tool_filter, ToolPredicate)` — `ToolPredicate` is a `runtime_checkable` Protocol
  whose only member is `__call__`, so this test means *is it callable*. It is checked **first**, which
  is why a function works and why a list — not callable — falls through to the next test.
- `self.tool_filter(tool, readonly_context)` — the predicate gets the whole tool and the context, so
  it can decide on more than a name. [3.2](3.2-a-list-of-names-or-a-question.md).
- `tool.name in self.tool_filter` — the list form is an exact-match allowlist on the name. No
  wildcards, no prefixes, no case folding. `"Lookup_Ticket"` does not match `lookup_ticket`.
- `return False` — anything that is neither callable nor a list rejects **everything**. Pass a set or
  a tuple by mistake and your crate offers no tools at all, with no error. A set is the natural thing
  to reach for and it is the wrong one.

Now the part that matters: who calls it.

```python
# lab/filter_ignored.py - the same filter, on two crates that differ by one line. Zero model calls.
from __future__ import annotations

import asyncio

from google.adk.tools.base_toolset import BaseToolset
from google.adk.tools.function_tool import FunctionTool


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    return {"id": ticket_id}


def search_kb(query: str) -> dict:
    """Search the known-issue knowledge base."""
    return {"hits": []}


def escalate(ticket_id: str, reason: str) -> dict:
    """Hand a ticket to a person."""
    return {"escalated": ticket_id}


ALL = [lookup_ticket, search_kb, escalate]


class Naive(BaseToolset):
    """Accepts a filter, stores it, and never looks at it again."""

    async def get_tools(self, readonly_context=None):
        return [FunctionTool(func=f) for f in ALL]


class Obedient(BaseToolset):
    """The same crate, one line longer."""

    async def get_tools(self, readonly_context=None):
        tools = [FunctionTool(func=f) for f in ALL]
        return [t for t in tools if self._is_tool_selected(t, readonly_context)]


async def main() -> None:
    allowed = ["lookup_ticket", "search_kb"]
    print("a) no filter at all        ->", [t.name for t in await Naive().get_tools()])
    print(
        "b) Naive, tool_filter set  ->",
        [t.name for t in await Naive(tool_filter=allowed).get_tools()],
    )
    print(
        "c) Obedient, same filter   ->",
        [t.name for t in await Obedient(tool_filter=allowed).get_tools()],
    )
    crate = Naive(tool_filter=allowed)
    print("d) the filter is stored:      crate.tool_filter =", crate.tool_filter)


asyncio.run(main())
```

**Line by line:**

- `Naive` and `Obedient` return the same three tools from the same list. The only difference between
  the classes is the list comprehension on the last line of `Obedient`.
- `self._is_tool_selected(t, readonly_context)` — the one line. It is a private method, which is a
  fair criticism of the design and does not change the fact that it is the supported way: every
  toolset ADK ships calls it exactly like this.
- `readonly_context` is passed straight through, because the predicate form needs it. Passing `None`
  here would work for the list form and quietly break [3.2](3.2-a-list-of-names-or-a-question.md)'s.
- Case **d** prints `crate.tool_filter` on the naive crate — the attribute is there, holding the
  right value, on an object that is not filtering. That line is the whole part in one print.

Run it:

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python filter_ignored.py

a) no filter at all        -> ['lookup_ticket', 'search_kb', 'escalate']
b) Naive, tool_filter set  -> ['lookup_ticket', 'search_kb', 'escalate']
c) Obedient, same filter   -> ['lookup_ticket', 'search_kb']
d) the filter is stored:      crate.tool_filter = ['lookup_ticket', 'search_kb']
```

**Compare a and b.** They are identical. Setting the filter changed nothing at all, and `escalate` —
the one tool the allowlist did not name — is offered in both. Verified against the installed
`google-adk` 2.7.1 on 2026-08-30.

## When it breaks

There is no error text. That is the entire problem, and it is why this part exists at
`production` level rather than as a footnote in [1.2](../01-crate-not-list/1.2-one-method-and-the-import.md).

The way it actually reaches you is a debugging session that goes nowhere, because every check you
run says the filter is fine:

```text
>>> crate.tool_filter
['lookup_ticket', 'search_kb']
>>> crate._is_tool_selected(escalate_tool, None)
False
```

The filter is set. The helper works and returns `False` for the tool you want excluded. And the agent
can still call it, because nothing joins those two facts together. You can lose an afternoon between
those two lines.

Two related failures with the same silence:

**The empty allowlist.** Read the allowlist from configuration and get it wrong —

```python
DeskTools(tool_filter=os.environ.get("ALLOWED_TOOLS", "").split(","))
```

An unset variable gives `[""]`, a truthy list containing one empty string, which matches no tool and
therefore offers **none**. Set it to nothing deliberately and `"".split(",")` still gives `[""]`. But
write it as a comprehension that drops blanks and you get `[]`, which is falsy, which
`_is_tool_selected` reads as *no filter* and opens the crate completely. The same configuration
mistake produces both zero tools and all tools depending on one character, and neither says anything.
Validate the parsed list, and fail loudly on empty.

**The wrong container.** `tool_filter={"lookup_ticket", "search_kb"}` — a set, written in a hurry.
Not callable, not a `list`, so `_is_tool_selected` falls to its final `return False` and every tool
is rejected. The agent runs with no tools, answers from memory, and looks like a model that has
stopped using its tools.

## In production

**Write the filter line into every toolset you own, even when there is no filter.** The one-line
comprehension in `Obedient` costs nothing when `tool_filter` is `None` — `_is_tool_selected` returns
`True` immediately — and it means the argument works the day somebody sets it. A crate that will
accept a filter it does not honour is a booby trap for the next person, and the next person is you in
Phase 5.

**Do not rely on the filter as the only control.** Not offering a tool is not the same as making it
unreachable. The tool object still exists, the underlying endpoint still exists, and any other agent
holding the same crate without the filter can call it. If `deleteAccount` must never be called, the
allowlist is the first of two controls and the second lives at the endpoint or in the credential.
This is [Day 14](../../../day-14-plugins-one-layer-up/LESSON.md)'s blast-radius argument, one layer
down: a rule written where it is convenient is not the same as a rule written where it binds.

**Assert on the resolved names, not on the filter.** The only test that can catch this failure is one
that resolves the crate through `get_tools_with_prefix` ([2.1](../02-when-asked/2.1-the-wrapper-adk-actually-calls.md))
and asserts on the names that come out. A test that asserts `crate.tool_filter == [...]` passes on
the broken crate — it is asserting that you typed the constructor argument correctly, which was never
in doubt. [7.2](../07-in-production/7.2-testing-a-toolset-without-a-model.md) writes the real one.

A senior reviewer's comment on a `get_tools` with no filter line is short: *"this accepts
`tool_filter` and ignores it."* The interview question is better, because the wrong answer is
confident: *"you allowlist four tools from a vendor's toolset — what exactly enforces that, and how
would you prove it in a test?"*
