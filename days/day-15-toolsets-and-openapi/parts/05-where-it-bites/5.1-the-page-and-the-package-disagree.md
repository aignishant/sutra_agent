# 5.1 — The page and the package disagree

## One-line answer

`adk.dev` says a generated tool's description comes from *"the `summary` or `description`"*; the
installed package reads `description or summary`, so when a spec has both — and good specs do — the
model is shown the one the page names second.

## The story

The box says one tablet twice a day. The leaflet folded up inside says one tablet once a day.

Both came from the same manufacturer, in the same box, printed in the same week. Neither is a
forgery, neither is out of date in any way you can see, and there is no third document to break the
tie. You are standing in your kitchen holding two official statements that do not agree, about a
decision you have to make in the next thirty seconds.

What you do is take the leaflet, because the leaflet is the one that is revised with the medicine.
The box is printed in advance, in bulk, months earlier. Once somebody tells you which of the two is
closer to the thing itself, the question stops being hard — and until somebody does, you have a
fifty-fifty guess and no way to know you got it wrong.

## The idea in plain language

An OpenAPI operation may carry two human-readable fields, and the specification defines them
differently:

- **`summary`** — *"A short summary of what the operation does."* One line, for a list.
- **`description`** — *"A verbose explanation of the operation behavior."* The long one.

A tool has room for exactly one description, so something has to choose. And the two documents you
would consult give opposite answers:

| Source | What it says |
| --- | --- |
| `adk.dev/tools-custom/openapi-tools/` | "Uses the `summary` or `description` from the operation for the LLM." |
| `google-adk` 2.7.1, in the source | `operation.description or operation.summary or ""` |

The page names `summary` first, which any reader takes as the precedence. The package takes
`description` first and falls back to `summary`.

This is not a disaster and it is not a bug report. It is a documentation page that is a little behind
its package, which is ordinary and which
[Day 14](../../../day-14-plugins-one-layer-up/LESSON.md) met already in a different form. What makes
it worth a part is the *consequence*: the two fields are written for different readers, so which one
wins decides what the model is shown, and picking wrong is a tool the model does not call.

## Why Sutra needs it

A well-written spec has a short `summary` for a documentation index and a long `description` for
somebody integrating. Which of those is a better tool description?

Almost always the `description`, because a tool description's job is to say **when to use this**, and
that does not fit in a summary. *"Vendor status."* tells a model nothing about whether to reach for
it when a customer reports a login failure. *"Current AcmeCloud platform status and any active
incident. Use when a ticket may be caused by a vendor-side outage."* tells it exactly that.

So the package's behaviour is the one you want, and the page is the thing to distrust. But you only
know that by looking, and the cost of not looking is spending an afternoon improving a `summary`
field that never reaches the model at all.

This is Principle 8 with teeth. *Never invent an API* is usually read as "do not guess at a method
name". The sharper version is: **when the page and the package disagree, the package is what runs**,
and the way you find out which you are dealing with is to print it.

## The mechanism

The claim, from `openapi_tool/openapi_spec_parser/openapi_spec_parser.py`:

```python
parsed_op = ParsedOperation(
    name=operation_parser.get_function_name(),
    description=operation.description or operation.summary or "",
    ...
)
```

**Line by line:**

- `operation.description or operation.summary or ""` — Python's `or` returns the first operand that
  is truthy, so `description` is taken whenever it is a non-empty string.
- An **empty** `description` — `"description": ""` — is falsy, so it falls through to `summary`. Both
  empty or both absent gives `""`, which is the invisible tool from
  [4.3](../04-machine-packed/4.3-where-each-part-of-a-tool-comes-from.md).
- The same expression appears a second time in `rest_api_tool.py`'s `from_parsed_operation`, which is
  belt and braces rather than a second rule; both say `description` first.

Four cases, one script:

```python
# lab/which_description.py - which of the two fields reaches the model. Zero model calls.
from __future__ import annotations

import asyncio
import json

from google.adk.tools.openapi_tool import OpenAPIToolset

CASES = {
    "both present    ": {"summary": "SUMMARY", "description": "DESCRIPTION"},
    "description only": {"description": "DESCRIPTION"},
    "summary only    ": {"summary": "SUMMARY"},
    "neither         ": {},
}


def spec_for(fields: dict) -> str:
    """The same one-operation spec, with only the two text fields varying."""
    operation = {"operationId": "getVendorStatus", "responses": {"200": {"description": "ok"}}}
    operation.update(fields)
    return json.dumps(
        {
            "openapi": "3.0.0",
            "info": {"title": "t", "version": "1"},
            "servers": [{"url": "http://127.0.0.1:8765"}],
            "paths": {"/status": {"get": operation}},
        }
    )


async def main() -> None:
    print("what the spec has     -> what the model is shown")
    for label, fields in CASES.items():
        crate = OpenAPIToolset(spec_str=spec_for(fields), spec_str_type="json")
        tool = (await crate.get_tools())[0]
        print(f"  {label} -> {tool.description!r}")


asyncio.run(main())
```

**Line by line:**

- `CASES` as a dictionary of four — the full truth table, not two cases and an assumption. Three of
  the four rows are uninteresting, and printing them is what makes the first row a *measurement*
  rather than an anecdote.
- `spec_for(fields)` rebuilds the whole document each time, so nothing carries over between cases.
  Mutating one shared dictionary would be shorter and would let case three see case two's
  `description`, which is the classic way a truth table lies.
- `"SUMMARY"` and `"DESCRIPTION"` in capitals — the values are labels, not prose, so the output reads
  as an answer rather than as text you have to compare word by word.
- `operation.update(fields)` **after** the base operation is built, so `operationId` and `responses`
  are constant across all four and only the two fields under test vary.
- No service is needed: nothing is called, only generated. Note that a spec pointing at a port with
  nothing on it still produces perfectly good tools —
  [4.2](../04-machine-packed/4.2-spec-in-tools-out.md)'s point about a spec being a claim.

Run it:

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python which_description.py

what the spec has     -> what the model is shown
  both present     -> 'DESCRIPTION'
  description only -> 'DESCRIPTION'
  summary only     -> 'SUMMARY'
  neither          -> ''
```

**Row one is the finding.** Both fields present, and `DESCRIPTION` is what the model gets. Verified
against `adk.dev/tools-custom/openapi-tools/` and the installed `google-adk` 2.7.1, both read on
2026-08-30; the OpenAPI Specification's own wording for the two fields is quoted from revision 3.2.0,
published 19 September 2025.

## When it breaks

There is no error. The failure is an afternoon spent in the wrong file.

The sequence goes like this. The model will not call your vendor tool. You look at the description it
was given, decide it is too terse, and go and improve it — in the `summary`, because that is the
field the documentation page told you was used. You redeploy. Nothing changes. You improve it again.
Nothing changes. Somewhere in the third round you start suspecting the model, the instruction, or
the tool-choice behaviour of the provider, and none of those is the problem: the `description` field
next to it is what the model has been reading the whole time, and you have not touched it.

The check that ends this in ten seconds is one line, and it belongs in your notes rather than in your
memory:

```text
  op_7f3a
    description: ...
```

Print the **generated tool's** description, never the spec's fields, whenever a generated tool is not
being chosen. The tool is the thing the model sees; the spec is two candidates and a rule you may
have backwards.

## In production

**Print what reached the model, not what you meant to send.** That habit generalises well past this
part: whenever a documentation page and a running package could disagree, the running package is what
serves your users, and it is usually one `print` away. Sutra's rule that a part names the adk.dev
page it checked *on the day* exists precisely so that a future reader knows the page was consulted
and can go and check whether it has since caught up.

**Fill in both fields on specs you own.** It costs nothing, it is correct under either precedence,
and it means a future ADK release that switches to matching its own page cannot change your agent's
behaviour. For specs you do not own, read the operation's `description` first, because that is the
one that is reaching the model — and if it is empty while the `summary` is good, that is a case for
the pinned, edited copy from
[5.2](5.2-a-crate-that-never-changes-its-mind.md).

**Do not report this as a bug without checking the version.** The page may be right for a newer or
older release than the one you have pinned, and the version you are running is the only fact that
matters to your incident. `docs/PACKAGES.md` records that `google-adk` is pinned at 2.7.1 and when it
was observed, which is the whole reason that ledger exists.

The interview question here is not about OpenAPI at all: *"the docs and the library disagree — what
do you do, and what do you write down?"* The answer that lands is that you go to the installed source,
you record the version you checked, and you leave the finding somewhere the next person meets it.
