# 5.2 — A crate that never changes its mind

## One-line answer

`OpenAPIToolset` parses the spec in its constructor and stores the resulting tools on the instance, so
it is the one toolset whose answer can never change — the vendor's document drifts and the crate does
not notice.

## The story

The photograph of the fuse box.

You took it the week you moved in, standing on a chair with your phone, because the labels were tiny
and you were not going to be able to read them from the floor. Kitchen sockets, upstairs lights,
immersion heater. It was a good idea and it worked: for two years, whenever something tripped, you
opened the photo instead of climbing on the chair.

Then the kitchen was rewired. Then a shower went in and the electrician moved two breakers along to
make room. Nobody updated the photo, because the photo is on your phone and the electrician is not.

The photo is still perfectly clear. It is a sharp, well-lit, completely accurate picture of a fuse box
that has not existed since the spring. And the day it matters is a dark evening with the power off,
when you switch the thing the photo calls "upstairs lights" and nothing happens.

## The idea in plain language

Section 1 made a promise about toolsets: they are *asked*, not *read*. The list is produced when the
question is put, so it can be a different list than it was last time.

`OpenAPIToolset` does not keep that promise, and it is worth being precise about why. Its `get_tools`
does exactly one thing: it filters a list that already exists. The parsing — fetching nothing,
reading the document, building one `RestApiTool` per operation — happened back in the constructor,
on the line where you wrote `OpenAPIToolset(...)`.

So the crate is a photograph of the vendor's document at the moment your process started. Everything
in section 2 about *when* a toolset is asked is still true and is now beside the point: asking a
photograph more often does not make it more recent.

Two consequences, and the second is the one that hurts:

- **A new operation never appears.** The vendor publishes something useful; your agent does not get
  it until you restart.
- **A changed operation is not noticed.** A renamed `operationId`, a parameter that became required,
  a path that moved — your crate keeps the old tools, which now describe a service that has moved on.
  The tools still generate, still look right, and fail at call time.

That gap between the document and the running service has a name worth knowing: **drift**.

## Why Sutra needs it

Sutra will hold vendor crates that live for as long as the process does, and processes in production
live for weeks.

The concrete decision this forces is *where the spec comes from*, and there are only three answers:

1. **Fetch it at start-up**, as [4.2](../04-machine-packed/4.2-spec-in-tools-out.md) does. Fresh at
   boot, stale thereafter, and your boot now depends on the vendor being up.
2. **Pin a copy in your repository.** Never surprises you, drifts silently and on your schedule, and
   is diffable — you can see exactly what changed and when, because it is in git.
3. **Rebuild the crate periodically.** Fresh, and now you have a background job, a race with
   in-flight requests, and a new failure mode when the fetch fails.

Sutra takes the second, and the reason is Principle 1: the thing your agent runs on should be a file
you reviewed, not a document a stranger can change while you sleep. The cost is that drift becomes
your responsibility, which is what the *In production* section is about.

## The mechanism

From `openapi_tool/openapi_spec_parser/openapi_toolset.py` — the constructor, and then `get_tools`:

```python
    if not spec_dict:
        spec_dict = self._load_spec(spec_str, spec_str_type)
    ...
    self._tools: Final[List[RestApiTool]] = list(self._parse(spec_dict))

@override
async def get_tools(
    self, readonly_context: Optional[ReadonlyContext] = None
) -> List[RestApiTool]:
    """Get all tools in the toolset."""
    return [
        tool
        for tool in self._tools
        if self._is_tool_selected(tool, readonly_context)
    ]
```

**Line by line:**

- `self._load_spec(spec_str, spec_str_type)` — the JSON or YAML is parsed **here**, in `__init__`.
  Anything you pass has already been fetched by you; this class never makes a network request to get
  a document.
- `self._tools: Final[...] = list(self._parse(spec_dict))` — every `RestApiTool` is built now and
  stored. `Final` is a type-checker annotation saying *this is never reassigned*, which is exactly the
  claim this part is making, written by the authors themselves.
- `list(...)` around the generator — forces it, so the work genuinely happens on this line rather than
  being deferred to the first iteration.
- `get_tools` returns a **filtered view of `self._tools`** and nothing else. No fetch, no parse, no
  re-read. Compare it with the crates you wrote in section 1, where the whole body ran on every ask.
- `self._is_tool_selected(...)` — note that `OpenAPIToolset` *does* apply the filter, which is
  [3.1](../03-the-filter/3.1-a-filter-you-have-to-apply-yourself.md)'s point from the other side: ADK's
  own toolsets all remember the line that your hand-written one has to remember too.

Two crates over the same document, one built each way:

```python
# lab/drifted.py - the vendor publishes a third operation. Zero model calls.
from __future__ import annotations

import asyncio
import json

from google.adk.tools.base_toolset import BaseToolset
from google.adk.tools.openapi_tool import OpenAPIToolset


def spec_with(paths: list[str]) -> str:
    """A spec describing one GET per path."""
    return json.dumps(
        {
            "openapi": "3.0.0",
            "info": {"title": "AcmeCloud status API", "version": "1.0.0"},
            "servers": [{"url": "http://127.0.0.1:8765"}],
            "paths": {
                path: {
                    "get": {
                        "operationId": f"get{path.strip('/').title()}",
                        "description": f"The {path.strip('/')} endpoint.",
                        "responses": {"200": {"description": "ok"}},
                    }
                }
                for path in paths
            },
        }
    )


VENDOR = {"published": spec_with(["/status", "/incidents"])}


class Rereading(BaseToolset):
    """A hand-written crate that asks the source every time it is asked."""

    async def get_tools(self, readonly_context=None):
        inner = OpenAPIToolset(spec_str=VENDOR["published"], spec_str_type="json")
        return await inner.get_tools()


async def main() -> None:
    generated = OpenAPIToolset(spec_str=VENDOR["published"], spec_str_type="json")
    rereading = Rereading()

    print("before the vendor deploys:")
    print("  OpenAPIToolset ->", [t.name for t in await generated.get_tools()])
    print("  re-reading     ->", [t.name for t in await rereading.get_tools()])

    VENDOR["published"] = spec_with(["/status", "/incidents", "/maintenance"])
    print("\n-- the vendor publishes a third operation --\n")

    print("after the vendor deploys:")
    print("  OpenAPIToolset ->", [t.name for t in await generated.get_tools()])
    print("  re-reading     ->", [t.name for t in await rereading.get_tools()])


asyncio.run(main())
```

**Line by line:**

- `VENDOR` as a dictionary rather than a plain string — so the "deploy" is one assignment to a key
  and neither crate holds a reference to the old value. A module-level string reassigned inside
  `main` would need `global` and would read as a Python trick rather than as a vendor deploying.
- `spec_with(paths)` builds the whole document from a list of paths, so the difference between before
  and after is one list element. Anything more elaborate would leave room to wonder what else changed.
- `class Rereading(BaseToolset)` wrapping an `OpenAPIToolset` **inside** `get_tools` — this is the
  pattern for a crate that stays current, and it is exactly what
  [1.2](../01-crate-not-list/1.2-one-method-and-the-import.md)'s single abstract method is for. Note
  the cost: it re-parses the document on every ask, which
  [2.2](../02-when-asked/2.2-asked-once-a-run.md) tells you is once per request.
- `generated` is constructed **before** the change and `rereading` builds its inner toolset **after**,
  which is the entire experiment. Both lines look the same in a diff and they are not the same
  program.

Run it (no service needed):

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python drifted.py

before the vendor deploys:
  OpenAPIToolset -> ['get_status', 'get_incidents']
  re-reading     -> ['get_status', 'get_incidents']

-- the vendor publishes a third operation --

after the vendor deploys:
  OpenAPIToolset -> ['get_status', 'get_incidents']
  re-reading     -> ['get_status', 'get_incidents', 'get_maintenance']
```

**The two crates agreed and then stopped agreeing**, with no code change between the two prints.
Verified against the installed `google-adk` 2.7.1 on 2026-08-30.

## When it breaks

A *new* operation not appearing is invisible and mostly harmless. A *changed* operation is neither.

Say the vendor renames a path from `/incidents/{incident_id}` to `/incidents/{id}`, which is the kind
of tidy-up that ships in a minor release. Your crate still holds the old tool, still declares
`incident_id`, and the model still calls it correctly according to the document your process read at
boot. The request goes to a path that no longer exists:

```text
API call failed for tool get_incident: Status 404 - {"detail":"Not Found"}
```

and the tool returns, rather than raising, with the model-facing text from
[4.5](../04-machine-packed/4.5-one-key-for-the-whole-crate.md) — which means the model is invited to
retry a call that cannot succeed, up to three more times, at your quota's expense.

Two things about diagnosing it are worth having in advance. The `404` names the tool but **not the
URL**, so nothing in your logs says which path was attempted unless you put it there. And the vendor's
current documentation will show `{id}`, matching nothing you can find in your own repository, because
the document your process is running on was fetched at boot and exists only in that process's memory.
Restarting fixes it, which is the worst possible property: it makes the incident go away before
anybody understands it, and it comes back on the next deploy that is slow to happen.

## In production

**Pin the spec, and diff it on a schedule.** Keeping the vendor's document as a file in your
repository turns drift from an invisible property into a pull request. A small scheduled job that
fetches the live spec and compares it against the pinned copy is perhaps twenty lines, and it moves
the discovery of a breaking change from *an incident* to *a diff somebody reads on a Tuesday*. This
is the same instinct as `docs/PACKAGES.md`: the version you are running is a fact worth writing down.

**Decide what a start-up fetch does when it fails, before it fails.** If you fetch at boot, the
vendor being down means your process cannot start. In a container platform that is a crash loop, and a
crash loop during someone else's outage is how a degraded dependency becomes your outage. Fetch with a
timeout, fall back to the pinned copy, and log loudly which one you used.

**Rebuilding the crate at run time is a bigger change than it looks.** It sounds like a small
improvement — re-read every hour, stay current — and it brings in a background task, a moment where
two versions of the tool list exist at once, and a decision about what an in-flight run should see.
[2.2](../02-when-asked/2.2-asked-once-a-run.md)'s per-run cache actually helps here, because a run
that has already asked keeps its answer for the rest of the request. If you do it, swap the whole
toolset object atomically rather than mutating one in place.

**This is the argument for hand-writing the two operations you truly depend on.** Generation is
excellent for breadth — forty operations, cheap, most of them rarely used. For the one call your
product does not work without, a hand-written tool with its own test is a thing that fails in *your*
test suite when the vendor changes, rather than in production. Senior engineers usually end up with
both, and the review question is *"which of these tools do we notice breaking?"*

The interview version is a good one: *"you generate tools from a vendor's spec at start-up — how would
you find out that the vendor changed it, and how would you find out before your users do?"*
