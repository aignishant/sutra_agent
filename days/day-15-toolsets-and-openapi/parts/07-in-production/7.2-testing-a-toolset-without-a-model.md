# 7.2 — Testing a toolset without a model

## One-line answer

A toolset is tested by resolving it through `get_tools_with_prefix` and asserting on the names that
come out — five assertions, no API key, no model, and one of them is the only thing in this day that
turns [6.1](../06-failure-lab/6.1-the-crate-that-arrived-empty.md)'s silence into a red build.

## The story

Checking the spare tyre on the driveway.

It takes four minutes. The boot is open anyway, the pump is in the garage, and you find out that the
spare has been sitting at half pressure since some time last year. You put air in it and close the
boot and think about it no further.

The alternative is finding out on the hard shoulder of a dual carriageway, in the rain, in the dark,
with the jack already under the car and no way to put the situation back the way it was. Same fact,
same tyre, same four minutes of work — discovered at the one moment you can do nothing about it.

Nobody checks the spare because checking it is interesting. They check it because the cost of the
same discovery, made later, is not four minutes.

## The idea in plain language

Everything a toolset decides is decided before the model is involved: which tools exist, what they
are called, and which ones were filtered out. None of that needs a model to check, and none of it
needs a network.

So the test is simply: **build the crate, resolve it, look at the names**. What makes it a real test
rather than a decorative one is one detail from [2.1](../02-when-asked/2.1-the-wrapper-adk-actually-calls.md) —
resolve it the way the agent does, through `get_tools_with_prefix`, and not through your own
`get_tools`. A suite that calls your method tests your method. A suite that calls ADK's method tests
what the agent receives, which is the thing that can actually be wrong.

Five things are worth asserting, and they map onto the five ways this day showed a crate going wrong:

1. The crate offers what you think it offers.
2. The filter is **applied**, not merely stored ([3.1](../03-the-filter/3.1-a-filter-you-have-to-apply-yourself.md)).
3. The operation you deliberately excluded is not there.
4. The prefix reaches the **declaration** the model reads ([2.3](../02-when-asked/2.3-two-crates-one-name.md)).
5. A crate that raises leaves the agent with no tools and the run still completes
   ([6.1](../06-failure-lab/6.1-the-crate-that-arrived-empty.md)) — pinning the silence, so that if a
   future ADK version starts raising instead, you find out from a test rather than from an outage.

And one thing that is deliberately **not** asserted, left as a skipped test with a `TODO(me)`: that
the pinned spec still matches what the vendor publishes. Nothing in this file can check that without
the network, and a green suite that seemed to cover it would be lying.

## Why Sutra needs it

Principle 11 says every day ends with a check that can go RED, and this day's failures are all silent
ones. There is no exception to catch and no error string to match on. The only observable is *the
list of names the agent was given*, so that list is what the suite has to assert.

The test is also the answer to a question [6.1](../06-failure-lab/6.1-the-crate-that-arrived-empty.md)
asked and left open: what would have caught the empty crate? A deploy-time check that the vendor crate
offers exactly two named tools would have failed the morning the spec moved, before any customer was
told the vendor was healthy.

## The mechanism

First, the thing under test. `sutra/toolsets.py`, new today, at the **package root** — not under
`sutra/desk/`, because a crate is not one agent's:

```python
"""Sutra's toolsets: the desk's own crate, and the vendor crate generated from a spec.

Layer: a toolset decides *which tools exist*, never what a tool does. Anything
that belongs to one tool belongs in that tool; anything that belongs to the
whole application belongs in a plugin (Day 14).
"""

from __future__ import annotations

from google.adk.tools.base_toolset import BaseToolset
from google.adk.tools.function_tool import FunctionTool
from google.adk.tools.openapi_tool import OpenAPIToolset

from sutra.desk.tools import escalate, lookup_ticket, search_kb

DESK_TOOLS = [lookup_ticket, search_kb, escalate]

VENDOR_ALLOWED = ["get_vendor_status", "get_incident"]


class DeskToolset(BaseToolset):
    """The desk's own tools, as a crate that applies its filter."""

    NAME = "sutra_desk_tools"

    async def get_tools(self, readonly_context=None) -> list[FunctionTool]:
        tools = [FunctionTool(func=func) for func in DESK_TOOLS]
        return [tool for tool in tools if self._is_tool_selected(tool, readonly_context)]


class VendorToolset(OpenAPIToolset):
    """AcmeCloud's crate. Subclassed only so a failure names the vendor (6.1)."""

    def __init__(self, spec_str: str, **kwargs) -> None:
        kwargs.setdefault("tool_filter", VENDOR_ALLOWED)
        kwargs.setdefault("tool_name_prefix", "acme")
        super().__init__(spec_str=spec_str, spec_str_type="json", **kwargs)
```

**Line by line:**

- The module docstring opens with `Layer:` — the same convention Day 14 put on its callbacks, and the
  subject of [7.3](7.3-where-trust-moved.md). It exists so the next person does not have to re-derive
  which of three places a rule belongs in.
- `VENDOR_ALLOWED` as a module constant — the allowlist is a reviewable object with a name, not an
  argument buried in a constructor call. A reviewer can find every allowed operation with one grep.
- The names in it are the **generated** names, `get_vendor_status` and not `getVendorStatus`
  ([4.4](../04-machine-packed/4.4-the-name-you-did-not-choose.md)). Writing the vendor's spelling here
  is the mistake that offers nothing and says nothing.
- `self._is_tool_selected(tool, readonly_context)` in `DeskToolset.get_tools` — the one line from
  [3.1](../03-the-filter/3.1-a-filter-you-have-to-apply-yourself.md), present even though the desk
  crate is usually constructed without a filter. It costs nothing when there is no filter and it means
  the argument works the day somebody passes one.
- `class VendorToolset(OpenAPIToolset)` — a five-line subclass that does almost nothing, and the
  "almost" is the point: it gives the crate a class name, so
  [6.1](../06-failure-lab/6.1-the-crate-that-arrived-empty.md)'s warning says `VendorToolset` instead
  of `OpenAPIToolset` and you can tell which vendor failed.
- `kwargs.setdefault(...)` rather than a plain assignment — the defaults are defaults, so a caller can
  still pass a narrower filter for a particular agent without editing this file.
- `super().__init__(spec_str=spec_str, spec_str_type="json", **kwargs)` — the base constructor call
  from [1.2](../01-crate-not-list/1.2-one-method-and-the-import.md)'s rule, and the line where the spec
  is actually parsed ([5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md)).

Now the suite. `tests/test_toolsets.py`:

```python
"""Day 15 - five assertions about the crates, and one skip. No API key, no model."""

from __future__ import annotations

import asyncio
import json

import pytest
from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.adk.tools.base_toolset import BaseToolset
from google.genai import types

from sutra.toolsets import DeskToolset, VendorToolset
from tests.scripted import ReactiveModel

SPEC = json.dumps(
    {
        "openapi": "3.0.0",
        "info": {"title": "AcmeCloud status API", "version": "1.0.0"},
        "servers": [{"url": "http://127.0.0.1:8765"}],
        "paths": {
            "/status": {
                "get": {
                    "operationId": "getVendorStatus",
                    "description": "Current AcmeCloud platform status.",
                    "responses": {"200": {"description": "ok"}},
                }
            },
            "/incidents/{incident_id}": {
                "get": {
                    "operationId": "getIncident",
                    "description": "One incident, by its id.",
                    "parameters": [
                        {
                            "name": "incident_id",
                            "in": "path",
                            "required": True,
                            "schema": {"type": "string"},
                        }
                    ],
                    "responses": {"200": {"description": "ok"}},
                }
            },
            "/accounts/{account_id}": {
                "delete": {
                    "operationId": "deleteAccount",
                    "description": "Delete an account.",
                    "parameters": [
                        {
                            "name": "account_id",
                            "in": "path",
                            "required": True,
                            "schema": {"type": "string"},
                        }
                    ],
                    "responses": {"200": {"description": "ok"}},
                }
            },
        },
    }
)


def offered(crate: BaseToolset) -> list[str]:
    """What the agent receives - through the wrapper, never through get_tools (2.1)."""
    return [tool.name for tool in asyncio.run(crate.get_tools_with_prefix(None))]


class Broken(BaseToolset):
    """A crate that cannot answer, standing in for a vendor spec that would not load."""

    async def get_tools(self, readonly_context=None):
        raise RuntimeError("the vendor spec could not be loaded")


def test_the_desk_crate_offers_every_tool_when_it_is_unfiltered() -> None:
    assert offered(DeskToolset()) == ["lookup_ticket", "search_kb", "escalate"]


def test_the_desk_crate_actually_applies_its_filter() -> None:
    assert offered(DeskToolset(tool_filter=["lookup_ticket", "search_kb"])) == [
        "lookup_ticket",
        "search_kb",
    ]


def test_the_vendor_crate_never_offers_the_operation_we_did_not_allow() -> None:
    names = offered(VendorToolset(SPEC))
    assert names == ["acme_get_vendor_status", "acme_get_incident"]
    assert not any("delete" in name for name in names)


def test_the_prefix_reaches_the_declaration_the_model_reads() -> None:
    tools = asyncio.run(VendorToolset(SPEC).get_tools_with_prefix(None))
    assert [tool._get_declaration().name for tool in tools] == [
        "acme_get_vendor_status",
        "acme_get_incident",
    ]


def test_a_crate_that_raises_leaves_the_agent_with_no_tools_and_the_run_succeeds() -> None:
    agent = LlmAgent(name="desk", model=ReactiveModel(model="scripted", chain=[]), tools=[Broken()])
    assert asyncio.run(agent.canonical_tools()) == []

    async def drive() -> list[str]:
        runner = Runner(
            app=App(name="test", root_agent=agent), session_service=InMemorySessionService()
        )
        session = await runner.session_service.create_session(app_name="test", user_id="u")
        texts = []
        async for event in runner.run_async(
            user_id="u",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text="is acme down?")]),
        ):
            for part in event.content.parts if event.content else []:
                if part.text:
                    texts.append(part.text)
        return texts

    assert asyncio.run(drive()), "the run produced no answer at all"


@pytest.mark.skip(
    reason="TODO(me): decide the trigger, then compare the pinned spec with the live one"
)
def test_the_pinned_spec_still_matches_what_the_vendor_publishes() -> None:
    raise AssertionError("not written")
```

**Line by line:**

- `def offered(crate)` — one helper, used by three tests, and it is the whole discipline of this part
  in three lines. Every assertion about what an agent receives goes through it.
- `crate.get_tools_with_prefix(None)` — ADK's entry point, with `None` for the context because there
  is no live request. Swap it for `crate.get_tools()` and one test stops being able to fail; that is
  measured below.
- `asyncio.run(...)` inside a **synchronous** test — this project has no `pytest-asyncio`, and
  `--strict-markers` in `pyproject.toml` means an `@pytest.mark.asyncio` would be an error rather than
  a silently skipped test. Day 11 left the question of adopting that plugin open; this file is written
  the way the rest of the suite is written.
- `SPEC` includes a `deleteAccount` operation that is **never allowed**. A spec containing only the
  operations you want cannot test an allowlist — the third assertion would pass on a crate with no
  filter at all. The dangerous operation has to be in the document for its absence to mean anything.
- `assert names == [...]` — a list, not a set and not a subset check. Order is part of what you are
  pinning, and an equality assertion fails when something is *added*, which is the case that matters
  when a vendor publishes a new operation.
- `assert not any("delete" in name for name in names)` — a second, looser assertion beside the exact
  one. It is deliberately redundant: the exact match catches everything today, and this one keeps
  catching the *dangerous* thing if somebody relaxes the exact match later.
- `class Broken` — a raising crate defined in the test file rather than imported, because it is a
  property of ADK being pinned, not a part of Sutra.
- `assert asyncio.run(agent.canonical_tools()) == []` — the silence, asserted. This is the line that
  would go red if a future ADK stopped swallowing toolset exceptions, which is exactly the change you
  would want to hear about.
- `assert asyncio.run(drive())` — and the run still produces an answer. Both halves matter: no tools,
  and no failure. Asserting only the first would leave the more surprising half untested.
- `@pytest.mark.skip(reason="TODO(me): ...")` — the skip carries the reason and the reason names the
  work. If this file ever reports `6 passed`, somebody deleted a `TODO(me)` instead of doing it.

Run it:

```text
$ uv run python -m pytest tests/test_toolsets.py -q -m "not live"

.....s                                                                   [100%]
5 passed, 1 skipped, 2 warnings in 1.74s
```

Verified against the installed `google-adk` 2.7.1 and `pytest` 9.1.1 on 2026-08-30.

**How to watch it go RED before it goes green.** Write `sutra/toolsets.py` as an empty file first and
run the suite: every test fails on the import. Then fill it in.

And then break it on purpose. These are **measured**, not predicted — each break was applied on its
own to a green suite:

| Break this | Tests that go red | What it is telling you |
| --- | --- | --- |
| delete the `_is_tool_selected` line from `DeskToolset.get_tools` | 1 — `actually_applies_its_filter` | the filter that is stored and ignored (3.1) |
| delete the `tool_name_prefix` default | 2 — `never_offers_the_operation_we_did_not_allow`, `prefix_reaches_the_declaration` | names are an interface (2.3) |
| delete the `tool_filter` default | 2 — the same two | an allowlist that is not applied (3.1) |
| resolve through `get_tools()` in the helper | 1 — `never_offers_the_operation_we_did_not_allow` | testing your method, not the agent's (2.1) |

Read the last row. Bypassing the wrapper leaves **four of five green**, and the one that fails does so
because the names lose their prefix. That is the honest measure of how little a naive suite notices:
the filter test, which is about the exact behaviour ADK will not do for you, passes either way.

## When it breaks

The suite's own most likely failure is one you should recognise on sight:

```text
E       AssertionError: assert ['lookup_ticket', 'search_kb', 'escalate'] == ['lookup_ticket', 'search_kb']
E         Left contains one more item: 'escalate'
```

That is the filter test after somebody removed the one line. Note how good this failure is compared
with the production version of the same bug: a name, an expected list, an actual list, and a diff. In
production the same bug is an agent that can escalate tickets it should not have been able to
escalate, discovered by a person.

The other failure worth knowing about is the import:

```text
E   ModuleNotFoundError: No module named 'tests.scripted'
```

`tests/scripted.py` is new today and it is the same test double Day 14 kept in its lab folder. It
moves into `tests/` because a test suite must not import from a day folder — day folders are records
of what was true when they were written, and a test that imports one couples the project's health to a
document nobody intends to change again.

## In production

**Run this check at deploy time, not only in CI.** The assertion that the vendor crate offers exactly
two named tools is a statement about a document a stranger controls, and CI runs when *you* change
something. The failure mode from [6.1](../06-failure-lab/6.1-the-crate-that-arrived-empty.md) happens
when *they* change something, on a morning you shipped nothing. A start-up check that resolves each
crate and refuses to boot on an unexpected inventory turns that into a deploy that does not go out.

**Assert on names, and be careful about asserting on descriptions.** Names are an interface and should
be pinned. Descriptions are prose from a vendor's document, and pinning them exactly gives you a test
that goes red every time somebody fixes a typo. If a description matters enough to test — and the one
that decides whether the model calls your vendor tool does — assert that it is non-empty and long
enough to be a sentence, not that it equals a string.

**A skipped test is a promise, and it should have a trigger.** The sixth test here has a `TODO(me)`
and no date, which is the honest state today and a bad state in six months. The trigger to write it is
the first time the vendor's spec changes under you; the shape of it is a scheduled job rather than a
unit test, because it needs the network and it needs to run when nobody is deploying.

A senior reviewer will ask one question of this file: *"which of these would have caught the incident
we had?"* If the answer is none of them, the suite is testing that you can construct objects. The
interview version is: *"how do you test an agent's tools without calling a model, and what does that
leave untested?"* — and the second half is the part that gets you the job.
