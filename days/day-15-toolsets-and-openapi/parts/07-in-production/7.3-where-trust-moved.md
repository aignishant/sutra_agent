# 7.3 — Where trust moved

## One-line answer

Generating tools does not remove the need to vouch for them; it moves what you vouch for — from lines
of your own code to **a document and an endpoint you do not control** — and the controls that follow
from that are different controls.

## The story

The day you stopped baking your own bread.

When you baked it, you knew what was in it because you put it there. Flour, water, salt, yeast, and
the oven you have used for six years. If it came out badly you knew why, because there were only four
things it could have been and you had handled all of them.

Now you buy it from the bakery on the corner. It is better bread, it takes four minutes instead of an
afternoon, and you would not go back. But the question you ask about it has completely changed. You no
longer ask *did I let it prove long enough*. You ask *is this the bakery that has the certificate in
the window*, and *has it been the same person behind the counter for two years*, and — once, when
somebody in the family stopped being able to eat something — *can I read what is actually in it*.

You have not stopped being careful. You are careful about a different thing, in a different place, and
the care you used to apply to the dough would now be entirely wasted.

## The idea in plain language

On [Day 10](../../../day-10-function-tools/LESSON.md), every tool Sutra had was one you wrote. What
you vouched for was code: this function does what its docstring says, its arguments are right, it
returns what it claims.

After today, a tool can arrive from a document. Nobody wrote the wrapper, so there is no wrapper to
review. What you now vouch for is two different things:

- **The document.** Are these operations the ones I think? Are the descriptions honest? Is there
  anything in here I would not want a model to be able to call?
- **The endpoint.** Is this URL the service I mean? Is it production or a sandbox? Who can change what
  it points at?

That is not less trust. It is trust relocated, and the relocation matters because **the controls that
worked on code do not work on a document**. Code review catches a bad function. It does not catch a
spec that grew a `deleteAccount` operation last Tuesday, because the spec is not in your diff.

So the day leaves you with three replacement controls, each of which was a part:

| What you used to rely on | What replaces it | Where |
| --- | --- | --- |
| reading the wrapper in review | an allowlist, reviewed instead | [3.2](../03-the-filter/3.2-a-list-of-names-or-a-question.md) |
| the code not changing under you | a pinned spec, diffed on a schedule | [5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md) |
| an exception when something is wrong | an asserted inventory | [7.2](7.2-testing-a-toolset-without-a-model.md) |

## Why Sutra needs it

Because the direction of travel is entirely one way, and it accelerates.

Today a document you fetched over HTTP produced two tools. In **Phase 5**, from Day 32, whole toolsets
arrive from other processes over MCP, and on **Day 40** those processes are run by people you have
never met. The question *what exactly am I vouching for* gets harder every phase, and the honest
answer stops being "the code" quite early.

Getting the instinct now, on a stub server you wrote yourself, is the cheapest it will ever be. The
allowlist you wrote in [7.2](7.2-testing-a-toolset-without-a-model.md) is a habit; on Day 40 it is a
security control with a threat model behind it.

## The mechanism

There is no new API here. The mechanism is a decision procedure and a place to write the answer down.

**Three questions, asked in order, about any tool that is about to reach an agent:**

1. **Who wrote what the model reads?** If you wrote the name and the description, you own them. If a
   spec did, the vendor owns them and you own the choice to accept them.
2. **What is the worst operation in this crate?** Not the one you intend to use — the one that is in
   the document. If the answer is `deleteAccount`, an allowlist stops being tidiness.
3. **What tells me when the answer to either changes?** If nothing does, the crate is a dependency
   with no monitoring, and [6.1](../06-failure-lab/6.1-the-crate-that-arrived-empty.md) is what that
   looks like on the morning it changes.

And the place the answer goes is the module docstring, in the same `Layer:` convention Day 14
established for callbacks and plugins:

```python
"""Sutra's toolsets: the desk's own crate, and the vendor crate generated from a spec.

Layer: a toolset decides *which tools exist*, never what a tool does. Anything
that belongs to one tool belongs in that tool; anything that belongs to the
whole application belongs in a plugin (Day 14).

Trust: DeskToolset's tools are ours - reviewed as code. VendorToolset's are
generated from AcmeCloud's published spec, so what is reviewed is VENDOR_ALLOWED
and the base URL, not the tools. The spec is pinned at spec/acme.json; a change
to that file is a change to what the agent can do, and is reviewed as one.
"""
```

**Line by line:**

- `Layer:` — the first paragraph answers *where does a rule belong*, which is the question Day 14 left
  you with. A toolset sits between a tool and a plugin, and saying so once stops the next person
  putting a credential rule in `get_tools`.
- `Trust:` — the second paragraph answers *what did we vouch for*, and it names the two crates
  separately because they are not the same kind of thing. A single docstring that treated them alike
  would be worse than none.
- `so what is reviewed is VENDOR_ALLOWED and the base URL` — it names the two objects a reviewer
  should actually look at. This is the sentence that makes a future pull request reviewable; without
  it, a reviewer looks at a five-line subclass and approves it.
- `The spec is pinned at spec/acme.json` — a path, so the claim is checkable. A docstring that says
  "we pin the spec" without saying where is a claim nobody can verify and everybody believes.
- `a change to that file is a change to what the agent can do` — the sentence that gets the file
  treated as code. Data files slip through review precisely because they look like data.

## When it breaks

The failure this part exists to prevent has no error text, because it is a review that happened and
did not look at the right thing.

A pull request adds a second vendor. The diff is eleven lines: an import, a constant, a subclass, one
entry on an agent's `tools` list. Two people approve it in four minutes, correctly, because there is
nothing wrong with those eleven lines.

The spec that pull request points at has thirty-one operations, four of which write, one of which
cancels a customer's subscription. Nobody read it, because it is not in the diff — and if it had been
fetched at start-up rather than pinned, it could not have been in the diff.

The observable, weeks later, is a support ticket that says a customer's subscription was cancelled and
nobody can find who did it. The audit trail says your agent, with a valid credential, using an
operation it was offered because it was in the document.

What would have caught it is not a better reviewer. It is the allowlist being **required** rather than
optional — which is why `VendorToolset` in [7.2](7.2-testing-a-toolset-without-a-model.md) sets one by
default, and why the test asserts the excluded operation is absent rather than asserting the included
ones are present.

## In production

**Make the allowlist the default, not the improvement.** A crate class whose constructor sets a
`tool_filter` and whose test asserts an exclusion is a small piece of design that survives the person
who wrote it. A crate that offers everything by default relies on every future caller remembering, and
they will not, because the version without a filter works fine in testing.

**Put the spec in the repository, and make its diff a review.** This is
[5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md)'s pinned copy earning its
second keep. It gives you the thing generation took away: a diff a person reads before the agent's
capabilities change. Fetch-at-start-up is more current and it removes the only review point you had
left.

**Credential scope is the control that survives the others failing.** The allowlist is in your process
and the spec is in your repository, and both are things a future change can undo. A credential the
vendor issued with read-only scope cannot cancel a subscription no matter what your agent decides to
call. When both a narrow key and an allowlist are available, take both, and know which one you would
still have if the other were misconfigured. That is Day 14's blast-radius question asked about
credentials instead of about rules.

**The review comment worth internalising** is the one to leave on any pull request that adds a
generated toolset: *"what is the most dangerous operation in this spec, and what stops us calling
it?"* Two answers are acceptable — an allowlist, or a credential that cannot — and "we would not call
it" is not one of them, because the thing deciding what to call is a language model.

The interview question is the one this whole day was building towards, and it is a genuinely good one:
*"you moved from hand-written tools to generated ones — what got easier, what got harder, and what did
you have to start doing that you did not do before?"*
