# 7.1 — The wrappers we are not installing

## One-line answer

ADK ships adapters that turn other frameworks' tools into ADK tools, and four toolsets besides the
one you used today — Sutra installs none of the adapters, and 🅿️ knowing *why not* is the skill this
part is teaching.

## The story

The travel adaptor in the kitchen drawer.

You bought it for a trip you did not end up taking, and it has been in the drawer ever since, under
the spare batteries. It is a perfectly good adaptor. It works. If you ever go to that country you
will be glad it is there.

The drawer also contains four other things you cannot name, two chargers for devices you no longer
own, and a plug with a cracked casing that somebody should have thrown out. None of them is doing any
harm, exactly. But the drawer is now a place you rummage in rather than look in, and when the smoke
alarm needs a battery at eleven at night, the difference between a drawer with six things in it and a
drawer with thirty is about four minutes and a certain amount of swearing.

Nobody decided to fill the drawer. Every single item went in for a reason that was good at the time.

## The idea in plain language

Other frameworks have their own tool objects, written to their own interfaces. ADK ships **adapters**
so those tools can be used from an ADK agent: `LangchainTool` and `CrewaiTool` each wrap one
foreign tool and present it as a `BaseTool`.

They exist because ecosystems meet at the tool boundary. A team with fifty tools already written for
another framework does not want to rewrite them to try ADK, and an adapter is how that team gets to
try ADK at all.

**Sutra installs neither**, and the reason is not that they are bad. It is that they are not free:

- Neither adapter works without its framework installed. Importing `LangchainTool` with no
  `langchain-core` present fails, so using one means adding a dependency — and that dependency has
  dependencies.
- Every dependency is an **audit surface**: something to pin, to update, to check for advisories, and
  to explain when the repository goes public in Phase 14.
- Nothing in Sutra needs one. Sutra's tools are written here, generated from a spec
  ([4.2](../04-machine-packed/4.2-spec-in-tools-out.md)), or — from Phase 5 — served over MCP.

The general rule this is an instance of: *do not add a dependency to avoid writing ten lines*. The
version that applies here is stronger, because an adapter is not ten lines you avoided — it is a
whole framework you brought in to avoid rewriting some functions.

🅿️ **Parked** means exactly this: you can say what it is, why it exists, and why you did not use it.
That is the interview answer, and it is a better one than having installed it.

## Why Sutra needs it

Two reasons, and the second is the one that will matter to you.

**Phase 4 makes dependency review formal.** Agent Skills arrive with their own provenance ledger, and
the habit of asking *what does this bring in* starts here, on the cheapest possible example.

**The other four toolsets are your map of what is coming.** `OpenAPIToolset` is one of several
`BaseToolset` subclasses in the installed package, and the others are days you have not reached yet:
`MCPToolset` is Phase 5, `SkillToolset` is Phase 4. Seeing them in one list now means that when Day 32
introduces `MCPToolset`, it is a subclass of a class you have already implemented twice by hand — not
a new concept.

## The mechanism

```python
# lab/wrappers.py - what ships, what imports, and what it would cost. Zero model calls.
from __future__ import annotations

import importlib
import inspect

from google.adk.tools.base_toolset import BaseToolset

CANDIDATES = [
    ("LangchainTool", "google.adk.tools.langchain_tool", "adapter"),
    ("CrewaiTool", "google.adk.tools.crewai_tool", "adapter"),
    ("MCPToolset", "google.adk.tools.mcp_tool.mcp_toolset", "toolset"),
    ("APIHubToolset", "google.adk.tools.apihub_tool.apihub_toolset", "toolset"),
    ("OpenAPIToolset", "google.adk.tools.openapi_tool", "toolset"),
    ("ToolboxToolset", "google.adk.tools.toolbox_toolset", "toolset"),
    ("SkillToolset", "google.adk.tools.skill_toolset", "toolset"),
]


def report(name: str, module: str, kind: str) -> str:
    """Import it, and say what happened in one line."""
    try:
        obj = getattr(importlib.import_module(module), name)
    except Exception as exc:
        return f"needs a dependency - {type(exc).__name__}: {str(exc).splitlines()[0]}"
    is_crate = inspect.isclass(obj) and issubclass(obj, BaseToolset)
    return f"imports cleanly - {'a BaseToolset' if is_crate else 'a BaseTool'}"


for tool_name, module_path, kind in CANDIDATES:
    print(f"{tool_name:<16} {kind:<8} {report(tool_name, module_path, kind)}")
```

**Line by line:**

- `importlib.import_module(module)` rather than a plain `import` — an `import` that fails stops the
  file, and the whole point is to keep going and report each one. This is the honest way to ask "is
  this available here".
- `except Exception` rather than `except ImportError` — because the failures are not all the same
  type, and this script exists to find that out rather than to assume it.
- `str(exc).splitlines()[0]` — some of these messages are several lines long with installation
  instructions in them. The first line is the fact; the rest is advice.
- `issubclass(obj, BaseToolset)` — the question that sorts the list into *one tool* and *a crate of
  tools*, which is the distinction section 1 spent three parts on.
- `inspect.isclass(obj) and ...` first — `issubclass` raises `TypeError` on a non-class, and some of
  these names could be functions in a future release.

**Read the top three against the bottom four.** Everything that would connect Sutra to another
framework, or to another process, is a dependency that is not installed. Everything that works today
works on what is already pinned. Verified against the installed `google-adk` 2.7.1 on 2026-08-30.

What the four available crates are, so the names are not new later:

| Toolset | What it wraps | When Sutra meets it |
| --- | --- | --- |
| `OpenAPIToolset` | an HTTP API's published description | today |
| `SkillToolset` | Agent Skills | Phase 4, from Day 25 |
| `MCPToolset` | tools served by an MCP server | Phase 5, from Day 32 |
| `APIHubToolset` | specs stored in Google's API Hub | 🅿️ parked — a paid, hosted registry |
| `ToolboxToolset` | a database toolbox service | 🅿️ parked — needs a service to run |

## When it breaks

The two adapters fail differently, and the difference is worth thirty seconds:

```text
ModuleNotFoundError: No module named 'langchain_core'
```

That is Python, not ADK. It tells you a package is absent and nothing at all about which extra
installs it, so you go and find out — and `langchain_core` is not a package name most people would
guess from `LangchainTool`.

```text
ImportError: Crewai Tools require pip install 'google-adk[extensions]'.
```

That is ADK catching the same class of failure and replacing it with a sentence that names the fix.
It is a better error, and it contains one thing to be careful about: this project does not use `pip`.
The equivalent is `uv add "google-adk[extensions]"`, and running the command as printed would install
into whatever interpreter `pip` happens to be, which on Windows is frequently not your virtual
environment. Read installation instructions in an error message as *what* to install, never as *how*.

The third one is the one you will actually meet, on Day 32:

```text
ModuleNotFoundError: No module named 'mcp'
```

MCP is not installed today and is not supposed to be — packages arrive on the day they are first
used. When you reach Phase 5 and see this, it is not a broken environment; it is the correct state of
a repository that has not got there yet.

## In production

**"We did not install it" is a design decision and belongs in writing.** A repository that goes
public — and this one does, in Phase 14 — is read by people who will wonder whether you knew the
adapter existed. A line in an ADR, or a comment where somebody would reach for it, is worth more than
the adapter would have been. The review comment on a pull request that adds a framework adapter is
always the same: *"what does this pull in, and what stops using it?"*

**Interoperability at the tool boundary is a real strategy, not a compromise.** The reason these
adapters exist is that a tool is a small, well-defined thing — a name, a description, a schema, a
body — and that makes it the cheapest place for two ecosystems to meet. If you ever do need one, the
right shape is a thin edge: adapt the foreign tool once, at the boundary, and keep everything inside
your own agent speaking ADK's types. What you must not do is let the foreign framework's types spread
inward, because then removing it later is a rewrite rather than a deletion.

**The dependency question has a number attached.** Before adding any of these, the honest version of
the question is: how many packages does this pull in, how many of them are maintained, and what is
your plan when one of them pins a version that conflicts with `google-adk`? For an agent framework
adapter the answer is usually "dozens, mostly yes, and there is no plan", and that is a fine reason to
decline.

The interview question is one that people over-answer: *"why not use LangChain's tools with ADK?"*
The good answer is short — they can be adapted, here is the class that does it, we did not need to and
every dependency is something to own — and it is much better than a defence of one framework over
another.
