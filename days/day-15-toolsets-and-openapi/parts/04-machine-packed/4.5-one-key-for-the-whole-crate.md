# 4.5 — One key for the whole crate

## One-line answer

`auth_scheme` and `auth_credential` are given to the toolset once and applied to every tool it
generates, so a forty-operation API is authenticated by one pair of constructor arguments and one
line in `.env`.

## The story

Checking into a hotel.

You get one card. It opens your room, and it opens the gym, and it works on the lift for your floor
and on the door to the pool that is locked after nine. Nobody hands you five cards. Nobody asks you,
at the pool door, to remember which of five you should be holding.

The card is also the whole of your access. When you check out they deactivate it once, and every one
of those doors closes at the same moment. That is the good half and the frightening half of the same
design: one thing to carry, and one thing to lose. A card left on a café table is not a room key, it
is the room and the gym and the pool and the lift.

Which is why the front desk never writes your room number on it.

## The idea in plain language

Almost every real API needs a credential. The two common shapes are an **API key** — a long secret
string sent in a header on every request — and a **bearer token**, which is the same idea with a
different header and usually a shorter life.

Hand-written tools each carry that themselves: every function reads the key and adds the header, and
you write that line once per tool. Forty operations is forty copies of one line, and one of them will
be missed.

`OpenAPIToolset` takes it once. You build two objects — a **scheme**, which describes *how* the
credential is sent, and a **credential**, which is the secret itself — and pass them to the
constructor. Every tool generated from the spec is configured with them, at construction time, in a
loop.

ADK gives you a helper that builds both from four plain arguments, so you never construct the
underlying types by hand:

```
token_to_scheme_credential("apikey", "header", "X-API-Key", value)
```

Two terms, because both appear in error messages:

- **`AuthScheme`** — the *shape*. Which header or query parameter, and what kind of credential goes
  in it. It contains no secret and is safe to log.
- **`AuthCredential`** — the *secret*. This one is never logged, never committed, and never printed
  in a lab script.

## Why Sutra needs it

Sutra's stub vendor needs no key, which is exactly why this part is written against a service that
does. Every real API in the phases ahead needs one, and the first is Phase 6's ticket archive.

Principle 9 says secrets never touch git, and this is where a generated toolset either honours that
or quietly breaks it. The danger is specific: a spec is a document, documents get committed, and the
tempting shortcut is to put the key in the spec — in a `servers` URL as a query parameter, or in an
`example` — where it will be committed along with everything else. The constructor argument exists
so the key can come from the environment and the document can stay a document.

## The mechanism

From `openapi_tool/openapi_spec_parser/openapi_toolset.py`, at the end of `__init__`:

```python
self._tools: Final[List[RestApiTool]] = list(self._parse(spec_dict))
if auth_scheme or auth_credential:
    self._configure_auth_all(auth_scheme, auth_credential)
```

**Line by line:**

- `self._tools = list(self._parse(spec_dict))` — the tools exist **before** anything about
  authentication happens. Order matters here: the credential is applied to objects that are already
  built, which is why it reaches every one of them and why a tool added later could not be reached at
  all.
- `if auth_scheme or auth_credential` — the whole authentication path is skipped when neither is
  given, so an unauthenticated crate costs nothing and takes no different code path. That is what
  makes the `plain` control in the script below a fair comparison.
- Both lines are inside `__init__`. Everything about credentials on this class happens once, on the
  line where you construct it, and never again — which is the sentence *In production* turns into a
  rotation problem.

and the loop it calls:

```python
def _configure_auth_all(self, auth_scheme, auth_credential) -> None:
    """Configure auth scheme and credential for all tools."""
    for tool in self._tools:
        if auth_scheme:
            tool.configure_auth_scheme(auth_scheme)
        if auth_credential:
            tool.configure_auth_credential(auth_credential)
```

**Line by line:**

- `if auth_scheme or auth_credential` — either alone is enough to enter the loop, and each is applied
  independently. Passing a credential with no scheme therefore configures a secret with no
  instructions for sending it, which is silent and useless. Pass both, which is what the helper
  returns.
- `for tool in self._tools` — every generated tool, with no way to authenticate only some of them
  from this constructor. Two credentials against one spec means two `OpenAPIToolset` instances built
  from two filtered copies of it.
- The loop runs **in `__init__`**, over the tools that already exist by then. That is the same
  once-at-construction behaviour as everything else in this class, and its consequence — a rotated
  key does not reach a crate that was built at start-up — is
  [5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md).

Here is the whole thing, against a service that echoes back the headers it saw:

```python
# lab/one_key.py - one credential, every tool. Zero model calls. Never a real key.
from __future__ import annotations

import asyncio
import json
import os

from google.adk.tools.openapi_tool import OpenAPIToolset
from google.adk.tools.openapi_tool.auth.auth_helpers import token_to_scheme_credential

from echo import BASE, serve_in_background

SPEC = {
    "openapi": "3.0.0",
    "info": {"title": "AcmeCloud status API", "version": "1.0.0"},
    "servers": [{"url": BASE}],
    "paths": {
        "/status": {
            "get": {
                "operationId": "getVendorStatus",
                "description": "Current AcmeCloud platform status.",
                "responses": {"200": {"description": "ok"}},
            }
        },
        "/incidents": {
            "get": {
                "operationId": "getIncidents",
                "description": "Open incidents right now.",
                "responses": {"200": {"description": "ok"}},
            }
        },
    },
}


async def main() -> None:
    serve_in_background()
    key = os.environ.get("ACME_API_KEY", "sk-not-a-real-key")

    scheme, credential = token_to_scheme_credential("apikey", "header", "X-API-Key", key)
    print(f"scheme: {type(scheme).__name__}   credential: {type(credential).__name__}")

    crate = OpenAPIToolset(
        spec_str=json.dumps(SPEC),
        spec_str_type="json",
        auth_scheme=scheme,
        auth_credential=credential,
    )
    for tool in await crate.get_tools():
        seen = await tool.run_async(args={}, tool_context=None)
        print(f"  {tool.name} -> {seen}")

    plain = OpenAPIToolset(spec_str=json.dumps(SPEC), spec_str_type="json")
    first = (await plain.get_tools())[0]
    print(f"  without auth -> {await first.run_async(args={}, tool_context=None)}")


asyncio.run(main())
```

**Line by line:**

- `os.environ.get("ACME_API_KEY", "sk-not-a-real-key")` — the key comes from the environment, and the
  fallback is obviously fake so the script runs on a fresh clone with no `.env`. Principle 9: the
  default must be a placeholder, never a working key, because a working default is a key in git.
- `token_to_scheme_credential("apikey", "header", "X-API-Key", key)` — four arguments in the order
  *kind, where, name, value*. `"apikey"` and `"oauth2Token"` are the two kinds; `"header"`, `"query"`
  and `"cookie"` are the three places, and `oauth2Token` only accepts `"header"`. `X-API-Key` is the
  header **this** vendor wants — it is not a standard, and using the wrong name is a `401` with a
  perfectly-formed request.
- It returns **two** objects, and both go to the constructor. Assigning only the first and passing
  `auth_scheme=scheme` alone gets you the shape with no secret, and a `401`.
- `print(type(scheme).__name__ ...)` — the **type**, never the value. There is no line in this file
  that prints the key, and that is deliberate: lab output gets pasted into chat windows and issues.
- `auth_scheme=` and `auth_credential=` on the constructor — the single place the credential is
  configured for both operations.
- The `plain` crate at the end is the control. Same spec, same tools, no auth arguments — so the
  difference in the last line is caused by those two arguments and nothing else.

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python one_key.py

scheme: APIKey   credential: AuthCredential
  get_vendor_status -> {'saw_headers': {'x-api-key': 'sk-not-a-real-key'}, 'path': '/status'}
  get_incidents -> {'saw_headers': {'x-api-key': 'sk-not-a-real-key'}, 'path': '/incidents'}
  without auth -> {'saw_headers': {}, 'path': '/status'}
```

**Two tools, one pair of constructor arguments, and the header on both.** The last line is the
control: the same spec with the two arguments removed sends nothing. Verified against
`adk.dev/tools-custom/openapi-tools/` and the installed `google-adk` 2.7.1 on 2026-08-30.

## When it breaks

Point the same crate at a service that answers `401` and the generated tool does something you need
to see before you rely on it. A log line goes out:

```text
API call failed for tool get_vendor_status: Status 401 - {"detail":"Not authenticated"}
```

and then the tool **returns normally**, with this as its result:

```text
{'error': 'Tool get_vendor_status execution failed. Analyze this execution error and your inputs.
Retry with adjustments if applicable. But make sure don\'t retry more than 3 times. Execution Error:
Status Code: 401, {"detail":"Not authenticated"}'}
```

Read what that is. The HTTP failure was caught, turned into English, and handed to the **model** as a
tool result containing an instruction to retry. Nothing raised. So the tool-error door you learned on
[Day 13](../../../day-13-callbacks-four-doors/LESSON.md) never fires, the plugin-level
`on_tool_error_callback` from [Day 14](../../../day-14-plugins-one-layer-up/LESSON.md) never fires,
and your run ledger records a successful tool call. This is the fourth 1.x → 2.x trap — *don't
swallow exceptions* — and here it is the framework doing the swallowing, on purpose, inside code you
did not write. Whatever error handling you built in the last two days does not cover generated tools,
and knowing that is the point of this paragraph.

It also means an authentication failure costs you up to three more model calls, because the model was
told it may retry, and a `401` does not get better on the second attempt.

The message itself names the status and the vendor's body, which is the useful half. What it cannot
tell you is which of four mistakes you made:

1. **The credential is missing.** `ACME_API_KEY` is not set and the placeholder went to the vendor.
2. **The scheme is missing.** You passed `auth_credential` and forgot `auth_scheme`, so nothing was
   ever attached to the request.
3. **The header name is wrong.** `X-API-Key` where the vendor wants `Authorization`, or
   `x-api-key` where they are case-sensitive about it — which they should not be, and some are.
4. **The key is fine and the account is not** — expired, rate-limited, or not entitled to that
   operation.

Only one of those is fixed by looking at your key. The way to tell them apart in one run is the echo
trick above: point the same crate at a service that prints the headers it received, and the first
three become visible immediately. Keep a tiny echo server in the lab for exactly this; it costs
nothing and it is faster than reading a vendor's authentication page.

The failure with no message at all is worse and it is a Principle 9 failure. Put the key in the spec:

```json
"servers": [{"url": "https://api.acme.example/v1?api_key=sk-live-9f3a"}]
```

This works. Every generated tool authenticates. And the key is now in a document, in your
repository, in your git history, and in the log line of anything that records request URLs. Nothing
errors, ever. It is found later by somebody grepping, or by nobody.

## In production

**One credential per crate is a blast radius, so scope the credential rather than the crate.** The
hotel card opens every door on it. If the vendor issues keys with per-operation scopes, take the
narrowest one that covers the operations on your allowlist, and take a second key for the operations
that need more. Two `OpenAPIToolset` instances with two keys and two allowlists is more code and a
much smaller incident. This is [Day 14](../../../day-14-plugins-one-layer-up/LESSON.md)'s blast-radius
argument again: the question is never *does this work* but *what else does this reach*.

**Key rotation does not reach a crate built at start-up.** `_configure_auth_all` runs in `__init__`,
so the credential the process holds is the one it read when it booted. Rotate the key in your secret
store and the running agent keeps sending the old one until it is restarted — which is either fine or
an outage, depending on whether the old key is revoked immediately. Know which, and if you need
live rotation, the tool for it is `header_provider`, which is a callable ADK invokes per request
rather than a value it captured once.

**Never log a request URL from a crate whose credential goes in the query string.** `"query"` is one
of the three locations the helper accepts, some vendors require it, and it puts the secret in
somewhere that gets logged by default at every hop — your process, the proxy, the vendor's access
log. If you must use it, the review comment writes itself: *"this key is in the URL — what logs
URLs?"*

The interview question is the one that separates configuring auth from owning it: *"your agent
authenticates to a vendor with one API key across forty operations — what happens when that key
leaks, and what did you do beforehand to make that answer shorter?"*
