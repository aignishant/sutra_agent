# 4.1 — The manual the service publishes about itself

## One-line answer

An OpenAPI description is a machine-readable manual an HTTP service publishes about itself — every
operation, its address, its arguments and a sentence about what it does — and it contains, in the
service's own words, everything you would otherwise write by hand into a tool.

## The story

A flat-pack shelf unit, in a box, on the floor of a room you have not decorated yet.

You have never seen this shelf before. Nobody has told you anything about it. And you will have it
standing up within the hour, because inside the box is a folded sheet with pictures on it: this
piece, that piece, this many of these screws, in this order, this way up.

Think about what that sheet replaces. Without it, you would need the person who designed the shelf,
on the phone, describing it. Or you would work it out by trial, and get it wrong twice. Or somebody
who assembled one last year would write down what they remembered, and their notes would be nearly
right — right about the shelf they built, wrong about the one in your box, because the design changed
in March and their notes did not.

The sheet is not a courtesy. It is the thing that lets a stranger use the product without talking to
anyone. And it comes from the same factory as the shelf, which is the only reason you can trust it.

## The idea in plain language

An **HTTP API** is a service you talk to over the web: you send a request to an address and it sends
back an answer, usually as JSON. The triage desk will need several of them — a vendor's status page,
a ticket archive, a partner's system.

To call one, you need four things: **where** to send the request, **which** operation you want, **what
arguments** it takes, and **what it does** — the sentence a human needs to decide whether this is the
operation for the job.

Traditionally you get those four things from a documentation page written for people, and you copy
them into your code by hand. That copying is the problem. It has to be done once per operation, it
has to be redone whenever the service changes, and nobody notices when it goes stale, because your
code keeps compiling.

An **OpenAPI description** is the same four things written in a format a machine can read. It is a
JSON or YAML document, often served by the service itself at a well-known address, and its structure
maps exactly onto the four questions:

| The question | Where it lives in the description | What Day 10 called it |
| --- | --- | --- |
| where to send it | `servers[0].url`, plus the path | the URL in your function body |
| which operation | a path plus a method, named by `operationId` | your function's name |
| what arguments | `parameters` and the request body schema | your type hints |
| what it does | `description`, or `summary` | your docstring |

Read the right-hand column again. On [Day 10](../../../day-10-function-tools/LESSON.md) you built a
tool by writing a name, a docstring, type hints and a body. Every one of those four things is
already in this document, written by the people who built the service.

Two terms that will be used constantly from here on:

- **Operation** — one thing the service can do: one path plus one HTTP method. `GET /status` is an
  operation; `POST /status` would be a different one.
- **`operationId`** — a name the description gives that operation, so anything reading the document
  can refer to it. It is optional in the specification, and
  [4.4](4.4-the-name-you-did-not-choose.md) is about what happens when it is missing.

## Why Sutra needs it

The triage desk currently has two hand-written tools. Sutra's next few phases add a vendor status
API, a ticket archive (Phase 6) and, in the capstone, a partner integration. If each of those is
wrapped by hand, the work is one function per operation — plus a docstring *about somebody else's
API*, which you have to keep true as their API drifts.

That is not craft. It is transcription, and it is transcription of a document that already exists.
[4.2](4.2-spec-in-tools-out.md) hands the transcription to a machine.

There is also a reason that has nothing to do with saving typing, and it is the one that matters in
**Phase 5**. MCP works because a server can describe its own tools to a client that has never seen
it before. The idea that *a service publishes a machine-readable description of what it can do* is
the same idea, and meeting it here — over plain HTTP, with a service you can read the source of —
is what makes Day 32 an application of something you know rather than a new protocol to memorise.

## The paper behind it

> **Implementing remote procedure calls**
> `doi:10.1145/2080.357392` · 1984 · ACM Transactions on Computer Systems 2(1), 39–59
> <https://doi.org/10.1145/2080.357392>

It claimed that a program should be able to call a procedure on another machine by writing an
ordinary call, with the code that puts the arguments on the wire **generated from an interface
description** rather than written by hand.

That is the idea this whole section runs on, forty years early. It is taught in
[the paper part](../../papers/01-implementing-remote-procedure-calls.md) — read it after the parts.

## The mechanism

Here is a complete OpenAPI description of a service with two operations. This is the whole document,
not an excerpt:

```json
{
  "openapi": "3.0.0",
  "info": {"title": "AcmeCloud status API", "version": "1.0.0"},
  "servers": [{"url": "http://127.0.0.1:8765"}],
  "paths": {
    "/status": {
      "get": {
        "operationId": "getVendorStatus",
        "summary": "Vendor status.",
        "description": "Current AcmeCloud platform status and any active incident. Use when a ticket may be caused by a vendor-side outage.",
        "responses": {"200": {"description": "Status object."}}
      }
    },
    "/incidents/{incident_id}": {
      "get": {
        "operationId": "getIncident",
        "description": "One incident, by its id.",
        "parameters": [
          {"name": "incident_id", "in": "path", "required": true, "schema": {"type": "string"}}
        ],
        "responses": {"200": {"description": "Incident object."}}
      }
    }
  }
}
```

Six keys carry everything:

- `openapi` — the version of the *specification* this document is written to, not the version of the
  service. `3.0.0` here; the current revision of the specification is 3.2.0, published on
  19 September 2025.
- `info` — the service's own name and version. Human-facing, and the only part of the document that
  never affects what gets generated.
- `servers` — a list, and **the first entry is the one that gets used**. That is not a rule of the
  specification; it is what ADK's parser does, and it is the kind of detail that decides whether your
  agent calls production or staging.
- `paths` — the operations, keyed by path and then by HTTP method. Two paths here, one method each,
  so two operations.
- `operationId` — the name. `getVendorStatus` becomes a tool called `get_vendor_status` in
  [4.3](4.3-where-each-part-of-a-tool-comes-from.md).
- `parameters` — one entry per argument, each saying its name, **where** it goes (`in: path` means it
  is part of the URL), whether it is required, and its type.

Note what `/status` does **not** have: a `parameters` key at all. An operation with no arguments
simply omits it, which becomes a tool the model calls with no arguments.

Note also that `/status` has **both** a `summary` and a `description`, saying different things. Only
one of them reaches the model, the specification does not say which, and the two documents that
matter here disagree about it — that is [5.1](../05-where-it-bites/5.1-the-page-and-the-package-disagree.md).

The service in the lab publishes this document about itself, at `/openapi.json`:

```bash
cd days/day-15-toolsets-and-openapi/lab && uv run python vendor.py
# in a second terminal:
curl -s http://127.0.0.1:8765/openapi.json
curl -s http://127.0.0.1:8765/status
```

**Line by line:**

- `uv run python vendor.py` — the stub service, written with nothing but the standard library. It
  costs no quota, needs no key and no account, and it is a real HTTP server making real responses.
  The whole of section 4 runs against it.
- **A second terminal** is genuinely required: the first one is blocked serving. On Windows, open a
  second Git Bash window rather than backgrounding it, so you can watch the access log.
- `curl -s` — `-s` silences the progress meter, which otherwise writes over the JSON you are trying
  to read.
- `/openapi.json` is a **convention**, not a rule. Services put their description at
  `/openapi.json`, `/swagger.json`, `/v3/api-docs` or nowhere at all, in which case somebody emails
  you a file.
- Fetching `/status` straight after is the point of the pair: the same server answers both, so the
  manual and the machine cannot drift apart. When they come from different places, they do —
  [5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md).

## When it breaks

Two ways of not getting the document you asked for, and only one of them says so.

**The address serves a page for humans.** Many services host the Swagger UI — a documentation page
you read in a browser — at the address you assumed held the description, and it answers `200 OK` with
HTML. Hand that to the parser and this is the error, character for character:

```text
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

It names JSON and it names a column, and it says nothing whatever about the actual mistake, which is
the URL. `line 1 column 1` is the giveaway: the very first character was already wrong, which is what
`<` looks like to a JSON parser. The description is usually one link away from the page, and the
page's own JavaScript fetches it, so opening the browser's network tab and reading the request the
page makes is the fastest way to the real address.

**The address is simply wrong, and the service says so in JSON.** A `{"detail":"Not Found"}` body
parses perfectly, because it is valid JSON. It just has no `paths` key:

```text
404 JSON    -> 0 tools generated, no error
empty paths -> 0 tools generated, no error
```

No exception, no warning, no tools. A document with nothing in it and a document you were never
served are indistinguishable from here, and both give you an empty crate.
[6.1](../06-failure-lab/6.1-the-crate-that-arrived-empty.md) is what that looks like from the agent's
side, and it is the day's failure lab because it is the failure that does not announce itself.

## In production

**Somebody else owns this document, and that is the whole trade.** A hand-written tool is wrong when
you make a mistake. A generated tool is wrong when the *description* is wrong — and descriptions are
wrong often, because they are frequently generated from code annotations by a build step nobody
watches, or maintained by hand alongside a service that has moved on. The question to ask about any
spec before you generate from it is not "is this valid" but "who updates this, and when did they
last".

**A published description is a security surface.** It is a complete, structured list of everything a
service can do, including the operations that were never meant for you. Reading a vendor's spec and
finding `deleteAccount` next to `getStatus` is normal; generating tools from all of it and handing
them to a model is how a status check becomes an incident.
[3.2](../03-the-filter/3.2-a-list-of-names-or-a-question.md)'s allowlist is the control, and the
habit is to read the operation list before generating anything.

**Version the document you generated from.** The reason is drift, and drift is
[5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md). A team that pins a copy of
the spec in its own repository can diff it against the live one on a schedule and see the day an
operation changed. A team that fetches the live spec at start-up gets a silent behaviour change
whenever the vendor deploys, and no record of what it used to be. Both are defensible; only one of
them can answer "what changed" during an incident.

The interview question is the one that separates reading about this from doing it: *"you generate
tools from a vendor's OpenAPI spec — what do you review before shipping it, and what do you monitor
after?"*
