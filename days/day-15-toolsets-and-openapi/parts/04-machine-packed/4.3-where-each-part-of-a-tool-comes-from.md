# 4.3 — Where each part of a generated tool comes from

## One-line answer

Every field of a generated tool traces to one field of the description — name from `operationId`,
description from `description` or `summary`, arguments from `parameters`, URL from `servers[0]` plus
the path — which is Day 4's translation table with a machine doing the typing.

## The story

Filling in a passport application at a kitchen table.

There are about thirty boxes on the form and you do not invent a single one of them. Your name comes
off your birth certificate, spelled exactly as it is there and not as you usually write it. The
address comes off a utility bill. The date comes off the certificate again. Every box on the form is
a copy of a box on a document already in the folder in front of you.

Which means the form cannot be more correct than the folder. If the certificate spells your middle
name with one L and everything else in your life uses two, the form gets one L — because the form is
not asking what your name is, it is asking what the certificate says. People discover this at
airports.

And it means that when the form is wrong, there is always a specific document to go and look at. You
do not debate the form. You find out which piece of paper that box came from.

## The idea in plain language

A tool has four things the model can see, and on
[Day 10](../../../day-10-function-tools/LESSON.md) you wrote all four by hand:

| The tool has | On Day 10 you wrote |
| --- | --- |
| a name | the function's name |
| a description | the docstring |
| an argument schema | the type hints |
| a body that does the work | the function body |

Generation does not invent any of them. It copies each one from a specific place in the description,
and the whole of this part is that mapping — because when a generated tool misbehaves, the fix is
never in your Python. It is in whichever field of the document that box came from.

| The tool's | comes from | and if that is missing |
| --- | --- | --- |
| name | `operationId`, snake-cased, cut to 60 characters | a name is built from the path and method — [4.4](4.4-the-name-you-did-not-choose.md) |
| description | the operation's `description`, falling back to `summary` | the description is the empty string |
| arguments | `parameters`, plus the request body's schema | the tool takes no arguments |
| URL | `servers[0].url` joined to the path | the base URL is empty and requests go nowhere useful |

Two of those rows have a sharp edge. The name row is [4.4](4.4-the-name-you-did-not-choose.md). The
description row says `description` **first** and `summary` second — which is the opposite of what the
documentation page says, and that is [5.1](../05-where-it-bites/5.1-the-page-and-the-package-disagree.md).

## Why Sutra needs it

This table is what makes a generated toolset auditable rather than magical.

When the model refuses to call the vendor tool, there are only two possible causes and this table
tells them apart: either the description does not say when to use it, or the name does not read like
the thing the model wants. Both are fields in a document you can open. Without the mapping, the same
symptom looks like the model being unreliable, and the fix people reach for is prompt engineering —
editing the agent's instruction to nag it into using a tool whose description is blank.

It matters again on **Day 40**, where reviewing a third-party toolset before allowing it means
reading exactly these four fields for each operation and deciding whether you believe them.

## The mechanism

The mapping is in two files in the installed package. From
`openapi_tool/openapi_spec_parser/openapi_spec_parser.py`, where operations are collected:

```python
base_url = ""
if openapi_spec.get("servers"):
    base_url = openapi_spec["servers"][0].get("url", "")
...
parsed_op = ParsedOperation(
    name=operation_parser.get_function_name(),
    description=operation.description or operation.summary or "",
    endpoint=url,
    ...
)
```

**Line by line:**

- `base_url = ""` first, then overwritten — so a description with **no** `servers` key does not fail.
  It produces tools whose requests go to a relative path with no host. That generates cleanly and
  fails at call time, which is the worst order.
- `openapi_spec["servers"][0]` — index zero, always. A description listing production, staging and a
  sandbox gets production only if production happens to be written first. Nobody in your team chose
  that; the vendor's document ordering did.
- `.get("url", "")` — a `servers` entry with no `url` also degrades quietly to empty rather than
  raising.
- `operation.description or operation.summary or ""` — the precedence, in one line. `description`
  wins. Both missing gives the empty string, and an empty description is a tool the model cannot
  choose.
- `operation_parser.get_function_name()` — the name, covered in [4.4](4.4-the-name-you-did-not-choose.md).

And from `operation_parser.py`:

```python
def get_function_name(self) -> str:
    """Returns the generated function name."""
    operation_id = self._operation.operationId
    if not operation_id:
        raise ValueError("Operation ID is missing")
    return _to_snake_case(operation_id)[:60]
```

**Line by line:**

- `_to_snake_case` — ADK's own converter. `getVendorStatus` becomes `get_vendor_status`; it also
  replaces every run of non-alphanumeric characters with a single underscore, so `get-vendor.status`
  arrives as `get_vendor_status` too.
- `[:60]` — a hard truncation, with no ellipsis and no warning. Two operations whose ids agree for
  their first sixty characters become two tools with the same name, which is
  [2.3](../02-when-asked/2.3-two-crates-one-name.md)'s shadowing arriving through the vendor's
  document rather than through your `tools` list.
- `raise ValueError('Operation ID is missing')` — this line looks like the answer to "what if there
  is no `operationId`", and it is not: the parser fills one in before this method is ever reached.
  [4.4](4.4-the-name-you-did-not-choose.md) shows what it fills in.

Here is the table made visible, one row per operation:

```python
# lab/provenance.py - every field of a tool, next to the field it came from. Zero model calls.
from __future__ import annotations

import asyncio
import json
import urllib.request

from google.adk.tools.openapi_tool import OpenAPIToolset

from vendor import BASE


def operations(spec: dict):
    """Every (method, path, operation) in the document, in document order."""
    for path, methods in spec["paths"].items():
        for method, operation in methods.items():
            yield method, path, operation


async def main() -> None:
    with urllib.request.urlopen(f"{BASE}/openapi.json") as response:
        raw = response.read().decode()
    spec = json.loads(raw)

    crate = OpenAPIToolset(spec_str=raw, spec_str_type="json")
    tools = await crate.get_tools()

    print(f"base url in the spec: {spec['servers'][0]['url']!r}")
    for (method, path, operation), tool in zip(operations(spec), tools, strict=True):
        schema = tool._get_declaration().parameters_json_schema
        print(f"\n{method.upper()} {path}")
        print(f"  operationId : {operation.get('operationId')!r}")
        print(f"  summary     : {operation.get('summary')!r}")
        print(f"  description : {operation.get('description', '')[:40]!r}")
        print(f"  parameters  : {[p['name'] for p in operation.get('parameters', [])]}")
        print(f"  -> tool name : {tool.name!r}")
        print(f"  -> tool desc : {tool.description[:40]!r}")
        print(f"  -> tool args : {sorted(schema.get('properties', {}))}")


asyncio.run(main())
```

**Line by line:**

- The spec is fetched **once** and used twice — parsed with `json.loads` for reading, and passed as
  the raw string to `OpenAPIToolset`. Fetching twice would risk comparing two different documents,
  which is the exact bug this script exists to make visible.
- `spec['servers'][0]['url']` — printed on its own line because it is the one field that belongs to
  the whole document rather than to an operation.
- `operation.get('summary')` and `operation.get('description', '')` printed **separately**, so the
  precedence in the next block is something you read off the output rather than take on trust.
- `[:40]` on both descriptions — long enough to tell which of the two won, short enough to fit on a
  line.
- `zip(operations(spec), tools, strict=True)` — the pairing, and `strict=True` is the important half.
  ADK generates tools in document order, so position lines them up; `strict` makes the script raise
  if the two sequences are ever different lengths instead of silently pairing the wrong ones. That is
  not paranoia: two operations whose ids collide after truncation
  ([4.4](4.4-the-name-you-did-not-choose.md)) produce exactly that mismatch.

## When it breaks

The failure that this mapping explains has no error text at all: the model does not call the tool.

```text
  TEXT  I don't have a way to check AcmeCloud's status.
```

That is a model looking at a tool called `op_7f3a` with an empty description and concluding, quite
reasonably, that it has nothing to check the vendor with. The tool is present, correct and perfectly
functional. It is invisible, because **the model chooses tools by name and description alone** —
Day 10's law — and both of those came from a document somebody exported without filling in.

The diagnosis is the table. Print the generated names and descriptions before blaming the model:

```text
  op_7f3a
    description: ...
    arguments:   []
```

A zero-length description is the answer, and the fix is not in your repository. It is either a change
to the vendor's spec, if it is yours, or a local override, if it is not — and the fact that there is
no supported way to override a generated description without editing the document is the honest cost
of generation. The usual workaround is to keep an edited copy of the spec in your own repository,
which is [5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md)'s pinned copy with a
second job.

## In production

**Audit a spec the way you audit a docstring.** [Day 10](../../../day-10-function-tools/LESSON.md)
established that a tool's docstring is prompt engineering; this part establishes that a generated
tool's docstring is prompt engineering **somebody else wrote, for a different audience**. A `summary`
written for a human browsing a documentation page — *"Vendor status."* — is a bad tool description,
because it says what the operation is and not when to use it. Before generating from a spec, read the
description of every operation you intend to allow and ask whether it would help a model decide. If
it would not, that is a finding, not a detail.

**The `servers[0]` rule is a production incident waiting for the right spec.** A vendor whose
document lists the sandbox first hands you an agent that has been reading test data for a month. It
is not visible in your code, your tests pass, and the data looks plausible. Assert on the resolved
base URL in a test, or read `servers` yourself and pick deliberately by passing a `spec_dict` you
edited.

**Generated argument names are the vendor's, not yours.** A spec with a parameter called `q` produces
a tool whose argument is `q`, and the model has to guess what to put in it from the description
alone. This is the strongest argument for the hybrid approach a senior engineer usually lands on:
generate the bulk, and hand-write the two or three operations whose semantics the spec cannot
express. The review comment is *"we generated all forty — which ones does the model actually get
right?"* and the interview question is: *"when would you hand-write a tool for an endpoint your spec
already describes?"*
