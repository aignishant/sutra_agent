# 4.4 — The name you did not choose

## One-line answer

When an operation has no `operationId`, ADK builds a name from the path and the method — `/incidents`
becomes `incidents_get` — and when the `operationId` is longer than sixty characters it is cut off
mid-word, both without a word of warning.

## The story

A parcel arrives at a depot with no name on it.

Just an address, a barcode from the sender, and a weight. The depot cannot leave it nameless, because
everything in the building is tracked by a label, so the system makes one up: the street, the round
it goes out on, the date. The parcel gets a label like `HIGHST-R4-0312` and continues on its way,
perfectly deliverable.

Then the label goes through the printer, and the printer prints a fixed width. Anything past that
width is simply not there. Two parcels on the same street on the same round now have labels that are
identical for as far as the printer got, and the difference between them was in the part that fell
off the end.

Nothing was broken. Nobody made a mistake. There were rules for both steps and both rules were
followed, and the result is two things with one name and a driver holding a scanner that beeps twice
and shows one address.

## The idea in plain language

[4.3](4.3-where-each-part-of-a-tool-comes-from.md) said the tool's name comes from `operationId`.
That field is **optional** in the OpenAPI Specification. Plenty of real documents do not have it —
especially ones generated from code by a framework that had no reason to fill it in.

ADK does not refuse. Before the naming code runs, the parser fills the gap in:

```
operationId = snake_case(f"{path}_{method}")
```

So `GET /incidents` becomes `incidents_get`, and `GET /maintenance/windows` becomes
`maintenance_windows_get`. Note the shape: the method goes on the **end**, not the front, so a name
that a person would write as `get_incidents` arrives as `incidents_get`.

Separately, the name is truncated to **sixty characters**. Not shortened intelligently, not hashed,
not warned about — cut, mid-word if that is where sixty falls.

Both rules are reasonable and both produce names you did not choose, which matters for exactly one
reason: **the model picks tools by name**. A name is not an internal identifier here. It is half of
the prompt.

## Why Sutra needs it

Sutra's vendor spec is written by hand in `vendor.py`, so it has good `operationId`s. Every spec
after it will not.

The immediate consequence is that any allowlist you write must use the **generated** name.
[3.2](../03-the-filter/3.2-a-list-of-names-or-a-question.md) said this in passing; here is why it is
easy to get wrong: you read the vendor's documentation, which shows paths, and you write
`tool_filter=["/incidents"]` or `["getIncidents"]`, and neither of those is what the tool is called.
The filter matches nothing, the crate offers nothing, and nothing says so.

The second consequence is [2.3](../02-when-asked/2.3-two-crates-one-name.md)'s shadowing arriving
from outside. Two long operations that agree for sixty characters produce one name twice, from a
single spec, and the later one silently wins.

## The mechanism

From `openapi_tool/openapi_spec_parser/openapi_spec_parser.py`, before any naming happens:

```python
# If operation ID is missing, assign an operation id based on path
# and method
if "operationId" not in operation_dict:
    temp_id = _to_snake_case(f"{path}_{method}")
    operation_dict["operationId"] = temp_id
```

**Line by line:**

- `if "operationId" not in operation_dict` — a **missing key**, not a falsy value. An
  `"operationId": ""` present but empty is not filled in here, and goes on to
  `get_function_name`, which raises `ValueError('Operation ID is missing')`. Missing and empty are two
  different outcomes for what looks like the same problem.
- `f"{path}_{method}"` — path first, method second. This is the whole reason the generated name reads
  backwards compared to how anyone would write it by hand.
- `_to_snake_case` — collapses every run of non-alphanumeric characters into a single underscore, so
  the leading slash, the internal slashes, and the braces of a path parameter all become underscores
  and then get tidied. `/maintenance/windows_get` comes out as `maintenance_windows_get`.
- `operation_dict["operationId"] = temp_id` — **the spec dictionary is mutated**. The document ADK
  parsed is not the document you handed it, which is worth knowing if you pass `spec_dict=` and then
  read your own dictionary back expecting it to be unchanged.

```python
# lab/no_operation_id.py - names for operations that never had one. Zero model calls.
from __future__ import annotations

import asyncio
import json

from google.adk.tools.openapi_tool import OpenAPIToolset

LONG = "getTheCurrentPlatformStatusIncludingAllActiveIncidentsAndScheduledMaintenanceWindows"

SPEC = {
    "openapi": "3.0.0",
    "info": {"title": "AcmeCloud status API", "version": "1.0.0"},
    "servers": [{"url": "http://127.0.0.1:8765"}],
    "paths": {
        "/status": {
            "get": {
                "operationId": "getVendorStatus",
                "description": "Named.",
                "responses": {"200": {"description": "ok"}},
            }
        },
        "/incidents": {
            "get": {
                "description": "No operationId at all.",
                "responses": {"200": {"description": "ok"}},
            }
        },
        "/maintenance/windows": {
            "get": {
                "description": "Nested path, no operationId.",
                "responses": {"200": {"description": "ok"}},
            }
        },
        "/everything": {
            "get": {
                "operationId": LONG,
                "description": "A very long name.",
                "responses": {"200": {"description": "ok"}},
            }
        },
        "/op": {
            "get": {
                "operationId": "op_7f3a",
                "description": "",
                "responses": {"200": {"description": "ok"}},
            }
        },
    },
}


async def main() -> None:
    crate = OpenAPIToolset(spec_str=json.dumps(SPEC), spec_str_type="json")
    print(f"the long operationId is {len(LONG)} characters\n")
    for tool in await crate.get_tools():
        print(f"  {tool.name!r}")
        print(f"     {len(tool.name)} characters, description {len(tool.description)} characters")


asyncio.run(main())
```

**Line by line:**

- `LONG` pulled out as a module constant — so its length can be printed next to the truncated result,
  which is the only way the truncation is visible rather than merely asserted.
- `/incidents` and `/maintenance/windows` both omit `operationId` entirely, and differ in **depth**.
  One path segment against two is what shows that the slashes become underscores rather than being
  dropped.
- `"operationId": "op_7f3a"` with `"description": ""` — a real export from a real code generator looks
  like this. It is included because it is the case that costs a day: the tool is present, correct,
  named and useless.
- `json.dumps(SPEC)` rather than `spec_dict=SPEC` — deliberately, because the parser mutates the
  dictionary it is given, and dumping to a string means the constant above stays the document you
  wrote when you go back and read it.
- `len(tool.description)` printed rather than the description — the number is the finding for the last
  row, and a zero is easier to see than an empty pair of quotes.

Run it (no service needed — nothing is called):

**Read the fourth one.** Eighty-four characters in, sixty out, and the cut lands in the middle of
`incidents` leaving `inciden`. That is the name the model is shown. Verified against the installed
`google-adk` 2.7.1 on 2026-08-30.

## When it breaks

The truncation is silent by design, so the failure it causes is the one from
[2.3](../02-when-asked/2.3-two-crates-one-name.md), arriving from a document rather than from your
code:

```text
WARNING:root:Duplicate tool name 'get_the_current_platform_status_including_all_active_inciden': the previously registered tool is shadowed and can no longer be called.
```

Two operations, one name, and the vendor's document is entirely valid — their `operationId`s are
different, they simply agree for the first sixty characters. There is nothing to fix in your code and
nothing wrong with theirs.

The other failure has no message. An allowlist written from the vendor's documentation:

```python
OpenAPIToolset(spec_str=spec, spec_str_type="json", tool_filter=["getIncidents"])
```

matches no tool, because the tool is called `incidents_get`. The crate offers nothing, the agent runs
with no vendor tools, and this is
[3.1](../03-the-filter/3.1-a-filter-you-have-to-apply-yourself.md)'s silence again. The habit that
prevents it is to print the generated names once and copy them, which is the entire purpose of the
script above.

## In production

**Print the generated names into your test suite, and assert on them.** Not because the names are
interesting, but because they are an interface you do not control and did not choose. A test that
lists them turns a vendor's rename into a red test instead of a support ticket, and it is the only
place the sixty-character truncation will ever be visible.

**A generated name is prompt text, so read it as one.** `incidents_get` is a worse name than
`get_incidents` for exactly the reason a person would say — it reads backwards — and the model reads
it the way you do. Where the names are bad enough to hurt tool selection, you have three options and
they are all real: keep an edited copy of the spec with proper `operationId`s, wrap the crate in your
own toolset that renames tools in `get_tools`, or hand-write the two operations that matter. The
first is the usual answer for a spec you can pin; the third is the usual answer for the one endpoint
the agent actually needs.

**Ask who generates the vendor's spec before trusting its names.** A document hand-written by an API
team has meaningful `operationId`s. A document emitted by a framework's introspection often has
`op_7f3a` or nothing at all, and the difference tells you how much of section 4 is going to work for
you. That question — *"is this spec written or exported?"* — is worth asking in the integration
kick-off rather than in the incident.

The interview question is a good filter, because the confident wrong answer is "we generate them":
*"the model won't call one of your generated tools — where do you look first, and what can you
actually change?"*
