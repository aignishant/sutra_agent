# 4.2 — Spec in, tools out

## One-line answer

`OpenAPIToolset` takes a service's description and produces one working tool per operation — name,
description, arguments and a real HTTP call — with no wrapper code written by anybody.

## The story

You put a new SIM card in a phone.

You do not open the settings. You do not type in an access point name, a proxy address or an MMS
gateway, all of which you would have had to do fifteen years ago, out of a leaflet, in a shop, while
somebody read the numbers to you. You put the card in, wait a moment, and the phone works.

What happened is that the network sent the phone its own settings, and the phone applied them. The
network knows how the network is configured — obviously it does, it is the network — so the leaflet
was always a copy of something the network already had. Once the phone could ask for the real thing,
the leaflet stopped being necessary, and so did the shop assistant reading the numbers out.

The settings did not become simpler. Somebody stopped copying them by hand.

## The idea in plain language

`OpenAPIToolset` is a toolset — a `BaseToolset` subclass, exactly like the ones you wrote in
section 1 — that you construct with a description instead of with a list of functions.

You hand it the JSON or YAML from [4.1](4.1-the-manual-the-service-publishes.md). It reads every
operation in `paths` and builds one tool for each. Each tool is a `RestApiTool`: a real `BaseTool`
that knows its own URL and, when called, makes the HTTP request with `httpx` and hands the response
back.

You write no function, no docstring, no type hints and no request code. Put the toolset on the
agent's `tools` list — one entry, as [1.1](../01-crate-not-list/1.1-one-line-many-tools.md) showed —
and the agent is offered every operation the service published.

Two terms:

- **`RestApiTool`** — the tool class ADK generates. One per operation. You never write one; you read
  about them so that when a stack trace mentions one, you know it is a generated tool and not
  something you imported.
- **`spec_str` / `spec_dict`** — the two ways in. `spec_str` takes the document as text and needs
  `spec_str_type="json"` or `"yaml"` alongside it; `spec_dict` takes it as an already-parsed Python
  dictionary and needs no type. Use `spec_str` when you fetched it, `spec_dict` when you built it.

## Why Sutra needs it

The vendor status check is the first tool Sutra will hold that it did not write, and it is the
pattern for every one after it: Phase 6's ticket archive, and the Researcher agent in the capstone,
which lives on other people's pages.

The immediate value is arithmetic. A partner API with forty operations is forty hand-written
functions, each with a docstring describing somebody else's endpoint, each needing an edit when that
endpoint changes. Generated, it is one constructor call and an allowlist.

The value that outlasts the arithmetic is that this is the shape of **Day 32**. An MCP client asks a
server what tools it has and builds tools from the answer. Today the answer is a JSON document
fetched over HTTP; on Day 32 it is a JSON-RPC response over a protocol — the same move, and you will
have made it once already.

## The paper behind it

> **Implementing remote procedure calls**
> `doi:10.1145/2080.357392` · 1984 · ACM Transactions on Computer Systems 2(1), 39–59
> <https://doi.org/10.1145/2080.357392>

It claimed that the code which marshals a call across a network should be **generated from an
interface description**, so that a caller writes an ordinary procedure call and nothing about the
wire.

`RestApiTool` is that generated code, and `OpenAPIToolset` is the generator. It is taught in
[the paper part](../../papers/01-implementing-remote-procedure-calls.md) — read it after the parts.

## The mechanism

```python
# lab/generated.py - a vendor's manual in, working tools out. Zero model calls.
from __future__ import annotations

import asyncio
import urllib.request

from google.adk.tools.openapi_tool import OpenAPIToolset

from vendor import BASE


def published_spec() -> str:
    """Fetch AcmeCloud's own manual, as a string, exactly as ADK wants it."""
    with urllib.request.urlopen(f"{BASE}/openapi.json") as response:
        return response.read().decode()


async def main() -> None:
    spec = published_spec()
    print(f"the manual is {len(spec)} characters of JSON, and we wrote none of it")

    crate = OpenAPIToolset(spec_str=spec, spec_str_type="json")
    tools = await crate.get_tools()
    print(f"tools generated: {len(tools)}")
    for tool in tools:
        print(f"  {tool.name}")
        print(f"    description: {tool.description[:60]}...")
        schema = tool._get_declaration().parameters_json_schema
        print(f"    arguments:   {sorted(schema.get('properties', {}))}")

    status = await tools[0].run_async(args={}, tool_context=None)
    print(f"a real HTTP call, made by code nobody wrote: {status}")


asyncio.run(main())
```

**Line by line:**

- `from google.adk.tools.openapi_tool import OpenAPIToolset` — the short path, and it works. The
  documented path on `adk.dev/tools-custom/openapi-tools/` is the much longer
  `google.adk.tools.openapi_tool.openapi_spec_parser.openapi_toolset`; both resolve to the same class,
  because the package re-exports it. Prefer the short one and know the long one exists, because that
  is the one you will meet in other people's code.
- `urllib.request.urlopen` rather than `httpx` — the standard library is enough to fetch one
  document, and adding a dependency to save four lines is the anti-pattern this project has a rule
  about. `httpx` is installed anyway, as a dependency of `google-adk`; that is not a reason to reach
  for it here.
- `.read().decode()` — text, not a parsed object, because `spec_str` wants the raw document. Parsing
  it yourself and passing `spec_dict=` would work equally well and would mean parsing it twice.
- `OpenAPIToolset(spec_str=..., spec_str_type="json")` — keyword-only, both of them. **The parsing
  happens on this line**, inside the constructor, not later when the tools are asked for. That is a
  much bigger deal than it looks and it has a part of its own:
  [5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md).
- `await crate.get_tools()` — the same method you implemented by hand in section 1. `OpenAPIToolset`
  is not special; it is a subclass that fills in `get_tools` from a document instead of from a list.
- `tool.description[:60]` — truncated for reading. The full description is what the model sees, and
  where it came from is [4.3](4.3-where-each-part-of-a-tool-comes-from.md).
- `tool._get_declaration().parameters_json_schema` — the argument schema ADK will send to the model,
  reached through a private method because there is no public one. Fine in a lab script and in a
  test; not something to build on.
- `tools[0].run_async(args={}, tool_context=None)` — calling a generated tool **directly**, with no
  agent and no model at all. `args={}` because this operation takes none. This is the line that
  proves the generated code really talks to the server rather than describing it.

Now the same crate on a real agent, driven by the scripted model so it still costs nothing:

```python
# lab/generated_agent.py - an agent calling a tool that was never written. Zero model calls.
from __future__ import annotations

import asyncio
import urllib.request

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.adk.tools.openapi_tool import OpenAPIToolset
from google.genai import types

from stateless import ReactiveModel
from vendor import BASE


def published_spec() -> str:
    """Fetch AcmeCloud's own manual, as a string."""
    with urllib.request.urlopen(f"{BASE}/openapi.json") as response:
        return response.read().decode()


async def main() -> None:
    crate = OpenAPIToolset(spec_str=published_spec(), spec_str_type="json")
    agent = LlmAgent(
        name="desk",
        model=ReactiveModel(model="s", chain=["get_vendor_status"]),
        tools=[crate],
    )
    runner = Runner(app=App(name="d15", root_agent=agent), session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name="d15", user_id="alia")
    async for event in runner.run_async(
        user_id="alia",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="is acme down?")]),
    ):
        for part in event.content.parts if event.content else []:
            if part.function_call:
                print(f"  CALL  {part.function_call.name}({dict(part.function_call.args)})")
            elif part.function_response:
                print(f"  REPLY {part.function_response.response}")
            elif part.text:
                print(f"  TEXT  {part.text.strip()}")


asyncio.run(main())
```

**Line by line:**

- `chain=["get_vendor_status"]` — the scripted model is told to ask for the **generated** name. It
  could not have been told the vendor's `getVendorStatus`, because that is not what the tool is
  called; [4.3](4.3-where-each-part-of-a-tool-comes-from.md) is where the name comes from.
- `tools=[crate]` — one entry on the list, two tools offered, exactly as
  [1.1](../01-crate-not-list/1.1-one-line-many-tools.md) established. The agent does not know or care
  that these tools were generated.
- The event loop prints three kinds of part: the model's request, the tool's answer, and the final
  text. Printing all three is what shows the round trip rather than just the result.
- `dict(part.function_call.args)` — the arguments the model actually sent, which is worth watching
  and is the finding below.

```text
  CALL  get_vendor_status({'ticket_id': '4521'})
  REPLY {'state': 'degraded', 'since': '09:10Z', 'incident': 'INC-9'}
  TEXT  done.
```

Verified against `adk.dev/tools-custom/openapi-tools/` and the installed `google-adk` 2.7.1 on
2026-08-30.

**Read the `CALL` line.** The scripted model sent `ticket_id='4521'` — it sends that to everything,
because that is what Day 14's test double does. `get_vendor_status` declares **no** arguments, and
the call worked anyway: the extra argument was dropped and the request went out clean. That is worth
knowing before you rely on it, and *In production* is where it stops being charming.

## When it breaks

The document parses and the tools generate. Then:

```text
generated fine: ['get_vendor_status']
httpx.ConnectError: All connection attempts failed
```

You forgot the first terminal. The description said the service is at `127.0.0.1:8765`, ADK believed
it, and nothing is listening.

**Read how little that error says.** No host. No port. No tool name. No mention of OpenAPI, of a
toolset, or of the vendor. `httpx` is a dependency you did not install and may not know you have, and
"all connection attempts failed" is what it says whether the address is wrong, the service is down,
or a proxy ate the request. With one generated toolset you can guess; with three, this line does not
tell you which vendor is unreachable, and you will be adding logging during the incident rather than
before it.

Note also what generated **fine**. The spec is a *claim* about where a service is, and generating
tools from it never checks that claim. The tools exist, the agent is confident, and the first
evidence that the vendor is unreachable arrives after the model has already decided to call it.

The version of this that reaches production is the same error with a real hostname in it, and the
thing to have decided in advance is what your agent does then. A `ConnectError` inside a tool
propagates as a tool error, which
[Day 13](../../../day-13-callbacks-four-doors/LESSON.md) gave you a door for and
[Day 14](../../../day-14-plugins-one-layer-up/LESSON.md) gave you an application-wide one. It is not
this part's job to handle it; it is this part's job to say that generating a tool generates a
dependency, and a dependency is something that goes down.

## In production

**The extra argument was silently dropped, and that cuts both ways.** A model that invents an
argument does no harm here. A model that invents an argument *name* for one you meant to send — sends
`incident` where the spec says `incident_id` — is also silently dropped, and the request goes out
without it. What comes back is a `404` or a list where you expected one record, and the diagnosis
starts at the vendor. Log the arguments the model actually sent, at least while a new generated
toolset is bedding in; the `CALL` line above is that log.

**Fetching the spec at start-up couples your boot to their uptime.** `generated.py` fetches
`/openapi.json` before it can build anything, so if the vendor is down, your process does not start —
and it fails with a `ConnectError` during import, which in most deployments looks like a crash loop
rather than a degraded dependency. The alternatives are to ship a pinned copy of the spec in your own
repository, or to fetch with a timeout and fall back to the pinned copy. Both mean thinking about
[5.2](../05-where-it-bites/5.2-a-crate-that-never-changes-its-mind.md)'s drift; neither means
pretending the vendor is always up.

**Generated tools are not reviewed, so the spec must be.** There is no diff to read: the pull request
that adds a vendor is one constructor call, and forty tools appear behind it. What a reviewer can
actually review is the operation list, the allowlist, and the URL in `servers[0]`. Make those three
visible in the change — print the resolved tool names in a test, as
[7.2](../07-in-production/7.2-testing-a-toolset-without-a-model.md) does — or the review is a
rubber stamp on somebody else's document.

The interview question is the one that shows whether you have shipped this: *"you generated forty
tools from a spec — what does your pull request actually show a reviewer, and what would you add?"*
