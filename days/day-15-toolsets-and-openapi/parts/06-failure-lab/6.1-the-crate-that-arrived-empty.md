# 6.1 — 💥 The crate that arrived empty

## One-line answer

When a toolset raises, ADK catches the exception, logs one `WARNING`, and gives the agent **zero
tools from that crate** — so the run succeeds, the answer is confident, and it is wrong.

## The story

The rota said the shift was covered.

Two people on the late shift, as always: one permanent, one from the agency. The permanent one turns
up. The agency one does not — not late, not ill, just never allocated, because something did not go
through at the agency's end on Thursday afternoon.

Nobody rings. The agency's system shows the booking as sent. The rota on the wall, printed that
morning, shows two names. The person who did turn up assumes their colleague is somewhere else in the
building, because that is the ordinary explanation, and gets on with it.

The shift runs. Things get done, more slowly, by one person doing the parts they can reach. The
manager reads the next morning's report — shift completed, no incidents — and it is true. It says
nothing about the fact that half the shift did not exist, because there is no box on the form for a
person who was never there.

## The idea in plain language

A toolset failure does not look like a failure.

Everywhere else in this curriculum, when something goes wrong an exception travels: it stops the
thing that was happening, it carries a message, and something upstream is given the chance to catch
it. That is what makes a bug findable — there is a moment where the program stopped, and a line
number attached to it.

A toolset is the exception. ADK asks each entry on the `tools` list for its tools inside a `try`, and
if the crate raises, the exception is caught right there and never travels. What reaches the agent is
an empty list, which is a perfectly ordinary thing for a crate to return —
[1.3](../01-crate-not-list/1.3-what-the-crate-can-see.md) had you build one that returns different
lists on purpose. So the run has no way to tell *the vendor is unreachable* from *there is nothing to
offer today*, and it treats both the same way: it carries on.

The result is a failure whose only symptom is **an agent doing less than it should, fluently**.

### 🎬 The scene

Sutra's triage desk has grown a vendor crate. It is the pattern from
[4.2](../04-machine-packed/4.2-spec-in-tools-out.md): fetch AcmeCloud's OpenAPI description at
start-up, generate the tools, put the crate on the agent.

It has worked for three weeks. This morning a customer writes in: *"nobody on my team can log in."*
The desk answers within seconds: **"AcmeCloud looks fine; this is probably on our side."**

An engineer spends the morning on Sutra's own authentication. AcmeCloud, meanwhile, has had a
degraded EU auth cluster since 09:10.

### 😬 The naive fix

*"The model got it wrong. Tighten the instruction — tell it to always check the vendor status before
blaming our own systems."*

That is the reasonable first move and it is aimed at the wrong layer. It also cannot work, and the
reason it cannot work is the finding of this part.

## Why Sutra needs it

Because this is the failure mode Sutra is most exposed to from tomorrow onwards, and it gets worse
every phase.

Day 16 adds built-in tools. Phase 5, from Day 32, adds toolsets whose contents live in another
process — and a process on the other end of a socket has many more ways to not answer than a
dictionary does. Every one of those failures arrives here, at the same four lines, and produces the
same empty list.

It is also the part that decides what
[7.2](../07-in-production/7.2-testing-a-toolset-without-a-model.md) is for. A day whose failures all
raise can be tested by asserting that something raises. This one cannot, so the eval has to assert
the *inventory* instead — and that is the only check in the whole day that would have caught the
morning described above.

## The mechanism

The model was never offered a vendor tool. It could not have checked the vendor status if the
instruction had begged it to.

Overnight, AcmeCloud moved its published description to a new address. The fetch now returns a
`404` page, `OpenAPIToolset` was constructed from something that is not a spec, and the crate raises
when ADK asks it for tools. ADK, from
[2.1](../02-when-asked/2.1-the-wrapper-adk-actually-calls.md)'s four lines:

```python
try:
    return await tool_union.get_tools_with_prefix(ctx)
except Exception as e:
    logger.warning(
        "Failed to get tools from toolset %s: %s",
        type(tool_union).__name__,
        e,
    )
    return []
```

**Line by line:**

- `except Exception` — everything. A parse error, a network timeout, a `KeyError` in your own
  `get_tools`, a bug you introduced this morning. All of them arrive here and all of them mean the
  same thing to the code below.
- `logger.warning` — **`WARNING`, not `ERROR`.** A great many production deployments log at `ERROR`
  or above. On those, this line does not exist.
- `type(tool_union).__name__` — the **class name** of the toolset, not the vendor, not the URL, not
  the file. Two crates of the same class and you cannot tell which one failed.
- `return []` — the crate contributes nothing, and the run continues as though it had contributed
  nothing on purpose. There is no distinction anywhere downstream between *a crate that failed* and
  *a crate that legitimately had no tools to offer today*, which is a thing
  [1.3](../01-crate-not-list/1.3-what-the-crate-can-see.md) taught you to build deliberately.

So the agent ran with the tools it had left, which was none, and answered from what the model already
knew about AcmeCloud — which is nothing, expressed confidently.

Here is the whole failure, both halves, in one script:

```python
# lab/arrived_empty.py - the same question, with and without a working crate. Zero model calls.
from __future__ import annotations

import asyncio
import logging
from collections.abc import AsyncGenerator

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.models import BaseLlm, LlmRequest, LlmResponse
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.adk.tools.base_toolset import BaseToolset
from google.adk.tools.function_tool import FunctionTool
from google.genai import types

from scripted import call, text

logging.basicConfig(level=logging.WARNING, format="%(levelname)s %(name)s: %(message)s")


def get_vendor_status() -> dict:
    """Current AcmeCloud platform status and any active incident."""
    return {"state": "degraded", "incident": "EU auth cluster errors since 09:10Z"}


class Honest(BaseLlm):
    """Uses the vendor tool when it is offered; answers from memory when it is not."""

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        offered = {
            declaration.name
            for tool in (llm_request.config.tools or [])
            for declaration in (tool.function_declarations or [])
        }
        answered = any(
            part.function_response
            for content in llm_request.contents
            for part in (content.parts or [])
        )
        if "get_vendor_status" in offered and not answered:
            yield LlmResponse(content=call("get_vendor_status"))
        elif answered:
            yield LlmResponse(content=text("AcmeCloud is degraded - EU auth cluster errors."))
        else:
            yield LlmResponse(content=text("AcmeCloud looks fine; this is probably on our side."))


class Working(BaseToolset):
    """The crate on a good day."""

    async def get_tools(self, readonly_context=None):
        return [FunctionTool(func=get_vendor_status)]


class Broken(BaseToolset):
    """The crate the morning the vendor moved their spec."""

    async def get_tools(self, readonly_context=None):
        raise RuntimeError("the vendor spec could not be loaded")


async def ask(label: str, crate: BaseToolset) -> None:
    agent = LlmAgent(name="desk", model=Honest(model="scripted"), tools=[crate])
    runner = Runner(app=App(name="d15", root_agent=agent), session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name="d15", user_id="alia")
    print(f"{label}")
    async for event in runner.run_async(
        user_id="alia",
        session_id=session.id,
        new_message=types.Content(
            role="user", parts=[types.Part(text="Customer can't log in. Is AcmeCloud down?")]
        ),
    ):
        for part in event.content.parts if event.content else []:
            if part.function_call:
                print(f"  CALL  {part.function_call.name}")
            elif part.text:
                print(f"  ANSWER {part.text.strip()}")


async def main() -> None:
    await ask("a) the crate works", Working())
    print()
    await ask("b) the crate raises", Broken())


asyncio.run(main())
```

**Line by line:**

- `class Honest(BaseLlm)` — a new test double, and the day's most important one. Day 14's
  `ReactiveModel` decides from a fixed `chain`, so it would ask for the vendor tool whether or not it
  was offered, and the run would fail loudly with `Tool 'get_vendor_status' not found`. That would be
  a **different bug** from the one in production, where a real model simply does not call a tool it
  cannot see. To reproduce the real failure you need a double that reads the offer.
- `llm_request.config.tools` and `tool.function_declarations` — the declarations actually sent to the
  model, which is the only honest source for "what was on offer". Reading `agent.tools` instead would
  read the crate, not the request, and the whole point is that those two disagree today.
- `answered = any(part.function_response ...)` — has a tool already replied in this conversation? It
  is what stops the model looping forever on its own tool call, and it is why case **a** ends after
  one round trip.
- The **third branch** is the failure: no tool offered, nothing answered, so the model says the thing
  it believes. `"AcmeCloud looks fine"` is not a bug in the double. It is what a language model does
  when it has no tool and a confident-sounding question.
- `Broken.get_tools` raising `RuntimeError` — standing in for a `JSONDecodeError` from
  [4.1](../04-machine-packed/4.1-the-manual-the-service-publishes.md)'s HTML page, or a timeout, or
  anything else. The *kind* of exception does not matter; that is the point of `except Exception`.
- `logging.basicConfig(level=logging.WARNING)` — without this line the warning does not appear at all,
  and the two cases differ **only** in the final sentence. Try it that way once.

Run it:

```text
$ cd days/day-15-toolsets-and-openapi/lab && uv run python arrived_empty.py
```

Standard output:

```text
a) the crate works
  CALL  get_vendor_status
  ANSWER AcmeCloud is degraded - EU auth cluster errors.

b) the crate raises
  ANSWER AcmeCloud looks fine; this is probably on our side.
```

and, on standard error, one line for the whole incident:

```text
WARNING google_adk.google.adk.agents.llm_agent: Failed to get tools from toolset Broken: the vendor spec could not be loaded
```

Verified against the installed `google-adk` 2.7.1 on 2026-08-30.

### 💡 The insight

**A toolset failure is not an error; it is a silence.** The run completes, the caller gets an answer,
the answer is fluent, and the only difference between a working system and a broken one is a sentence
that happens to be false.

Look at what is *absent* from case **b**: no traceback, no `error` field, no failed event, no
exception at the caller. Everything you built on
[Day 13](../../../day-13-callbacks-four-doors/LESSON.md) and
[Day 14](../../../day-14-plugins-one-layer-up/LESSON.md) to notice failures — the tool-error door, the
model-error door, `on_run_error_callback`, the run ledger — sees a clean run, because nothing raised
past those four lines. Your ledger records a successful request with fewer tool calls than usual, and
"fewer tool calls than usual" is not something anybody alerts on.

And notice the shape of the wrong answer. The agent did not say *"I could not check"*. It said the
vendor was fine. An agent stripped of its tools does not become cautious; it becomes a language model
with an opinion. That is the part worth carrying out of this day: **removing a tool changes what the
agent claims, not just what it can do.**

## When it breaks

The warning is the only evidence, and it is a bad witness. Read it again:

```text
WARNING google_adk.google.adk.agents.llm_agent: Failed to get tools from toolset Broken: the vendor spec could not be loaded
```

- It says `Broken` — the **class name**. With two `OpenAPIToolset` instances for two vendors, both
  say `OpenAPIToolset` and neither says which.
- It is `WARNING`, so it is below the threshold on a lot of production logging configurations.
- The message after the colon is whatever `str(exception)` gives. For a `JSONDecodeError` that is
  `Expecting value: line 1 column 1 (char 0)`, which mentions neither the vendor, nor the URL, nor
  OpenAPI.
- It is emitted **once per run**, thanks to [2.2](../02-when-asked/2.2-asked-once-a-run.md)'s cache —
  so a broken crate produces one warning per user request, which is enough volume to be tuned out and
  not enough to look like an outage.

The one thing that makes this diagnosable is a name you control. Give the crate a subclass with a
meaningful class name — `AcmeStatusToolset` rather than a bare `OpenAPIToolset` — and the warning
becomes:

```text
WARNING ...: Failed to get tools from toolset AcmeStatusToolset: Expecting value: line 1 column 1 (char 0)
```

which is still a bad message, and now names the vendor. That is a genuinely worthwhile five-line
subclass.

## In production

**Assert the inventory, do not hope for it.** The control that actually catches this is a check that
runs on every deploy and says *the vendor crate offers exactly these four tools*. It is the test in
[7.2](../07-in-production/7.2-testing-a-toolset-without-a-model.md), and it is the only thing in this
day that turns a silence into a red build. If a crate is important enough to put on an agent, its
tool list is important enough to assert.

**Fail fast at start-up rather than silently at request time.** Nothing stops you calling
`await crate.get_tools_with_prefix(None)` yourself as the process boots, checking the count, and
refusing to start if it is zero. A process that will not start is an obvious problem with an obvious
owner; an agent that answers wrongly for a fortnight is neither. Whether "refuse to start" is right
depends on whether the vendor is load-bearing — but it should be a decision, not a default.

**Alert on the shape of the run, not on errors.** There are no errors here. What there is, is a
sudden change in the number of tool calls per request: the desk called `get_vendor_status` on most
tickets for three weeks, and this morning it called it on none. That signal exists in the ledger you
built on Day 14 and it costs nothing extra to watch. It is also the only signal that would have caught
this one on the morning it happened.

**Two things a senior reviewer will say about the code in this part.** The first is *"this crate can
fail — what does the agent do then?"*, and having an answer is most of what this day is for. The
second is about the instruction: an agent whose vendor tool is missing should be told, in its
instruction, to say it could not check rather than to guess — because the instruction is the only
layer that can turn a confident wrong answer into an honest one when everything below it has already
decided to be quiet. That is Principle 10 written where it still has an effect.

The interview question is one of the best in this whole phase: *"your agent's toolset failed to load
— walk me through what your users saw, what your logs saw, and what your alerts saw."*
