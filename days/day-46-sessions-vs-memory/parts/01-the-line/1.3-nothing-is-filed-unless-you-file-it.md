# 1.3 — Nothing is filed unless somebody files it

## One-line answer

Sessions accumulate whether you want them to or not; memory accumulates nothing at all until a line
of your code calls `add_session_to_memory`, and a system with a memory service and no such line
behaves exactly like a system with no memory at all.

## The story

You buy a mixer grinder. In the box there is a small card: model number, date of purchase, the
shop's stamp, two years.

The shop assistant fills it in and hands it back to you with the receipt. You put the card in the
box, you take the box home, and the box goes on top of the cupboard. You are not being careless — the
card is filled in correctly, it is not lost, and you could find it in five minutes.

Fourteen months later the motor starts making a noise. You ring the company. They ask for the
registration number.

There isn't one. The card said, in small print at the bottom, that the warranty had to be registered
— by post, or on their website — within thirty days. Nobody told you that the *filling in* and the
*registering* were two different acts. The shop did its part. You kept the card. And as far as the
company's records go, this mixer grinder was never sold to anybody.

Everything about that afternoon was correct except the one step that made it visible to somebody
else, and nothing anywhere gave you an error.

## The idea in plain language

Two stores, two very different defaults.

**A session fills itself.** You do not append events to a session in normal operation; the runner
does. Every user message, every model reply, every tool call and every tool result is written into
the session by the framework as it happens. If you build an agent and never think about sessions at
all, you still have a complete session, because accumulating is what a session *is*.

**Memory fills only when told.** There is no automatic promotion. Nothing observes a session ending
and files it — in fact, nothing in ADK is watching for a session to end at all, because a session
does not have an event for ending. A conversation simply stops receiving messages, and there is no
moment at which the framework could say *"that one is over, file it"*.

So the asymmetry is:

| | Session | Memory |
| --- | --- | --- |
| What happens by default | everything is kept | nothing is kept |
| Who writes to it | the runner, on every turn | your code, once, explicitly |
| The failure when nobody writes | impossible | silent and total |

The third row is the one to sit with. If nobody writes to a session, that situation cannot arise. If
nobody writes to memory, you get a system that has a memory service wired in, has a memory tool on
the agent, answers questions about the past — and answers all of them with *"no past case on file"*,
forever, without a single warning.

**This is a feature, not an oversight.** Filing is a *decision*, and it should be one. Deciding
what is worth carrying out of a conversation is a real question with real consequences — privacy,
cost, correctness — and Day 48, *Memory design*, is the whole day about answering it. Automatic
promotion would take that decision away and make it invisible. The framework's silence here is the
framework declining to choose on your behalf.

Two things you might reasonably expect to trigger a write, and do not:

1. **Reading memory does not write memory.** Calling `search_memory` never files anything. The
   current conversation is not added to the store as a side effect of consulting it.
2. **A session going out of scope does not file it.** Python garbage-collecting your `Session` object
   has no effect on the memory service, and neither does the session service dropping it.

## Why Sutra needs it

This is the line Sutra's build brief turns into a `TODO(me)`, and it is the first genuinely open
question this phase asks: **when does Sutra file a conversation?**

Every plausible answer is defensible and every one is different. At the end of every turn — cheap to
write, and it files half-finished reasoning. At the end of the agent's run, in an
`after_agent_callback` — which is what
[3.2](../03-three-wires/3.2-the-line-where-it-crosses.md) shows. Only when a ticket is marked
resolved — the most useful store and the one that needs the most plumbing. Never automatically,
only when a human presses a button.

You cannot choose between those without first understanding that the choice exists, which is what
this part is for. And Day 48 cannot write a retention policy for a store that nothing ever writes to,
so the decision has to be visible before that day can do its job.

## The mechanism

Three finished conversations, and a search that finds nothing.

```python
# days/day-46-sessions-vs-memory/lab/optin.py
async def main(*, file_it: bool) -> None:
    sessions = InMemorySessionService()
    memory = InMemoryMemoryService()

    for n in (1, 2, 3):
        session = await sessions.create_session(app_name=APP, user_id=USER, session_id=f"s{n}")
        for i, (author, text) in enumerate(PAST_CASE):
            await sessions.append_event(session, said(author, f"[case {n}] {text}", float(i)))
        if file_it:
            await memory.add_session_to_memory(session)

    listed = await sessions.list_sessions(app_name=APP, user_id=USER)
    print(f"sessions the session service is holding : {len(listed.sessions)}")
    print(f"    ids                                 : {[s.id for s in listed.sessions]}")
    print(f"    filed into memory                   : {'yes, all three' if file_it else 'no'}")

    found = await memory.search_memory(app_name=APP, user_id=USER, query=TODAY)
    print(f"\nmemory.search_memory({TODAY!r})")
    print(f"    memories returned                   : {len(found.memories)}")
    print("\nnothing failed. Nothing was even asked to fail.")
```

**Line by line:**

- The loop builds **three complete conversations** and then walks away from each one. That is what
  makes the scenario honest: these are not abandoned or broken sessions, they are finished work.
- `f"[case {n}] {text}"` tags each conversation so that, in the filed arm, you can see three distinct
  cases come back rather than one repeated.
- `if file_it: await memory.add_session_to_memory(session)` is **the only line that differs between
  the two runs**, and it sits inside the loop because a session is filed one at a time. There is no
  bulk call, and there is no "file everything" method on the interface.
- `list_sessions(app_name=..., user_id=...)` proves the sessions are still there and still complete.
  This matters: the naive explanation for an empty search is "the sessions were lost", and this line
  removes it. The sessions are fine. They were simply never registered anywhere else.
- `search_memory(..., query=TODAY)` uses the same question in both arms, so the only variable is the
  filing.
- The final `print` says the quiet part. There is no exception, no log line, no warning. A test that
  asserted *"the code ran without errors"* passes in both arms.

**Three sessions in both runs. Zero memories against six.** The store is not partially populated in
the first run and it is not stale — it is empty, and it will stay empty for the life of the process
no matter how many conversations happen.

Note the `6`, too, because it is a preview of a problem. Three conversations of two events each were
filed, and the query matched **all six events**, including the three user messages that just restate
the complaint. `add_session_to_memory` files every event that has content; it does not select, it
does not summarise, and it does not know which half of a conversation was worth keeping. That is
Day 48's subject and
[5.4](../05-failure-lab/5.4-the-store-that-outgrew-its-value.md)'s measurement.

Verified against the installed source at
`.venv/Lib/site-packages/google/adk/memory/in_memory_memory_service.py` on 2026-09-05, where
`add_session_to_memory` stores `[event for event in session.events if event.content and
event.content.parts]` — every event with content, filtered on nothing else.

## When it breaks

The break has no error text, which is the whole difficulty. What it has instead is a shape you can
learn to recognise: **a feature that works in the demo and never once works afterwards.**

Here is how it gets built. Somebody follows the wiring in
[3.3](../03-three-wires/3.3-the-tool-the-model-may-call.md), attaches `load_memory` to the agent,
runs a scripted demo in which they file one session by hand, and watches the agent recall it. The
demo is genuine. Then the code ships without the filing line, because the filing line was in the
demo script rather than in the application, and it is the only line in the whole feature that lives
outside the agent.

What you see afterwards, in the event stream, is this:

```text
    TOOL CALL   load_memory({'query': 'logged out'})
    TOOL RESULT 0 memories
    FINAL       No past case on file.
```

Every part of that is working correctly. The model asked. The tool ran. The store answered honestly.
The answer is wrong about the world and right about the store.

The second break is subtler and it survives review: the filing line exists but sits somewhere that
runs before the interesting part of the conversation. File in a `before_agent_callback` and you store
the conversation *as it was at the start of this turn* — the user's question, not the answer. Nothing
errors, the store fills up, searches return results, and the results are all questions and no
findings. The tell is a store whose entries are almost all `author='user'`.

The third is the one that costs money rather than correctness: filing on **every** turn. It is not
wrong, and `add_session_to_memory` is explicitly documented for it — the interface docstring says *"A
session may be added multiple times during its lifetime."* — but with a store that keeps the whole
session under its id, re-filing a forty-turn conversation forty times means the last write does forty
times the work of the first. With `InMemoryMemoryService` you will not notice. With anything that
crosses a network you will.

## In production

**What a professional writes instead of the teaching version.** The filing call appears exactly once
in the codebase, in a callback, and it is accompanied by a log line naming the session id and the
number of events filed — because *"did this conversation ever enter the store"* is the first of the
three questions you ask when memory misses, and no other line of code can answer it. Above the call
sits a predicate: not every conversation is worth keeping, and the predicate is data rather than an
`if`, which is Day 48's `sutra/memory/policy.py`.

**What degrades at scale or under concurrency.** Filing is a write into shared state, and every agent
in the fleet does it. `InMemoryMemoryService` serialises them with a `threading.Lock`, which is
correct and free at this scale; a database-backed store makes each filing a network round trip, and
the tempting fix — filing asynchronously, after responding to the user — introduces a window in which
the conversation is over and not yet stored. If the process dies in that window the conversation is
lost from memory and still present in the session store, which is a genuinely confusing state to
debug. The safer shape is to file synchronously and to accept the latency, or to file from a queue
that survives the process.

**The failure mode that only appears with real traffic.** Filing every turn is invisible until a
conversation gets long. A support chat that runs to sixty turns is filed sixty times, each time
storing the whole growing session, so the work done is quadratic in the length of the conversation.
Nothing about that is visible in a test with three-turn fixtures.

**The review comment a senior engineer leaves:** *"Where is `add_session_to_memory` called in the
application, as opposed to in the demo script? I can see the tool on the agent and the service on the
runner and nothing that writes. Also log the write — when this misses in six weeks, the first
question is whether the conversation was ever filed, and right now nothing in the system can answer
that."*

**The interview question:** *"Does an agent framework remember conversations automatically?"* An
honest answer: *"The conversation is kept automatically — every turn lands in the session — but that
is not memory, it is history for that one conversation. Crossing into a store that a later
conversation can search is always an explicit call. I like that it is explicit, because deciding what
is worth keeping is a real decision with privacy and cost attached to it. The trap is that the
failure is completely silent: I built the whole feature once, tool and service and all, and shipped
it with the filing call still sitting in the demo script. Every search returned zero memories and
every log line said the code was working."*
