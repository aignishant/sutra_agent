# 1.2 — Putting it somewhere, and finding it again

## One-line answer

Session state is a place you **put** a value under a name you chose, so reading it back either
returns that value or fails loudly; memory is a place you put something and later have to **find**
it by describing it, and a description can match the wrong thing, several things, or nothing at all.

## The story

There is a hook by your front door, and your house keys live on it.

You have never once searched for those keys. You do not look for them; you go to the hook and take
them. If the hook is empty you know immediately and exactly what has gone wrong — somebody has the
keys, or you left them in the door — and you know that within a second of looking. The hook cannot
give you the wrong keys. It cannot give you *nearly* your keys.

Now think about your passport.

A year ago you put it somewhere safe. You remember doing it. You remember it was somewhere sensible,
and you remember thinking at the time that you would obviously remember. Today you need it, and you
are going through the cupboard, the file of old bills, the drawer with the chargers in it, the shelf
above the wardrobe. You will probably find it. You will also open four things that turn out to hold
something else, and at least once you will pull out a document that looks right for a second and is
not.

Both objects were put away carefully. The difference is not care. It is that one of them has an
**address** and the other one has only a **description**, and a description is something you compare
against candidates until one seems close enough.

## The idea in plain language

**Session state** is a dictionary attached to one conversation. Day 17's
[1.1](../../../day-17-state-scopes-and-lifetimes/parts/01-form-not-story/1.1-the-transcript-is-not-a-database.md)
called it a small labelled form attached to the story, written for your code to read rather than for
the model to read. You write `state["severity"] = "high"`, and later you read `state["severity"]` and
get `"high"`. If the key is not there, Python raises `KeyError`. There is no third outcome.

**Memory** has no keys. You call `search_memory(app_name=..., user_id=..., query="something")` and
you get back a list. The list might have one entry, or six, or none, and nothing in the response
tells you whether the right thing is in it. In the words the ADK documentation uses, the service
*"searches its store, using keyword matching or semantic search, and returns matching snippets"*.
The word doing the work in that sentence is **matching**, and matching is a judgement.

The two are different *kinds* of operation, and it is worth naming them:

| | Session state | Memory |
| --- | --- | --- |
| How you reach it | by a key you chose | by a description you wrote |
| Result when it is there | exactly the value | some list containing it, maybe |
| Result when it is not | `KeyError`, loudly | an empty list, silently |
| Result when you are wrong | `KeyError`, loudly | **a plausible wrong answer** |
| Who decides what matches | you did, when you named the key | the implementation, at read time |

The last two rows are the ones that matter and the ones people skip. A lookup that fails tells you it
failed. **A search that returns the wrong thing looks exactly like a search that returned the right
thing**, and there is nothing in the return value that distinguishes them. That single fact is why
this day has a four-part failure lab, and why section 5 opens with an agent confidently quoting the
wrong knowledge-base article.

One more term, because it comes back in section 4. A **query** is the string you hand to
`search_memory`. It is not a key and it is not a question — it is a bag of words that the
implementation will compare against stored text somehow. Who writes that string is a real design
decision: the model writes it when you use `load_memory`, and the framework uses the user's raw
message when you use `preload_memory`. Section 3 covers both.

## Why Sutra needs it

Sutra already writes to session state. Day 17 taught the three safe ways to do it, and the desk uses
the first one — [an ordinary assignment inside a tool](../../../day-17-state-scopes-and-lifetimes/parts/03-three-safe-writes/3.1-writing-from-inside-a-tool.md).
Everything the desk knows about the current ticket lives there under names the code chose:
`severity`, `ticket_id`, `root_cause`.

Today Sutra gains a second store, and the temptation is to treat it as a bigger version of the first
one. It is not. It is a different kind of thing, and if you carry the state habits across you will
write code that assumes a search behaves like a lookup — code that says *"if the search came back
empty, there is no past case"*, which is a claim the search is not able to support.

That claim is exactly what
[4.2](../04-the-choice/4.2-sutras-memory-policy.md) turns into rule 4 of Sutra's memory policy, and
it is why Day 49, *Retrieval and embeddings*, exists: when the matching is
this weak, the honest sentence is *"nothing matched the words I searched for"*, not *"there is no
precedent"*.

## The mechanism

The same two facts, stored twice — once as state under a name, and once as text in memory — and then
read back both ways.

```python
# days/day-46-sessions-vs-memory/lab/putfind.py
    # --- putting: one key, one write, one read, no search anywhere ------------------
    write = Event(
        author="desk",
        invocation_id="inv-1",
        actions=EventActions(state_delta={"severity": "high", "root_cause": "cookie flags"}),
    )
    await sessions.append_event(session, write)
    fetched = await sessions.get_session(app_name=APP, user_id=USER, session_id="sess-a")
    print("PUTTING - session state")
    print(f"    state['severity']   -> {fetched.state['severity']!r}")
    print(f"    state['root_cause'] -> {fetched.state['root_cause']!r}")
    print(f"    keys                -> {sorted(fetched.state)}")
    try:
        fetched.state["cause"]
    except KeyError as err:
        print(f"    state['cause']      -> KeyError({err.args[0]!r})  <- absence is loud")
```

**Line by line:**

- `Event(author=..., invocation_id=..., actions=EventActions(state_delta=...))` is Day 17's
  [3.3](../../../day-17-state-scopes-and-lifetimes/parts/03-three-safe-writes/3.3-writing-from-outside-a-run.md)
  pattern: when no agent is running, you write state by building an event whose only cargo is the
  change. The write goes **through the history**, which is what makes it recoverable later.
- `invocation_id="inv-1"` is required for an event that carries a state delta. It ties the change to
  the question that caused it, which is Day 17's
  [7.3](../../../day-17-state-scopes-and-lifetimes/parts/07-in-production/7.3-state-as-a-trace.md):
  state answers *what*, and the event answers *who set this, and when*.
- `state_delta={"severity": "high", ...}` — two keys, chosen by you, written by you. Nobody has to
  guess later what `severity` means or where it is; it is at `state["severity"]`, and it is there or
  it is not.
- `get_session(...)` re-fetches from the service rather than reading the object we already hold,
  because that is what a later turn would do. Day 17's
  [6.1](../../../day-17-state-scopes-and-lifetimes/parts/06-failure-lab/6.1-the-write-that-was-never-written.md)
  is the failure lab for people who skip this and mutate their local copy instead.
- `fetched.state["cause"]` is a deliberate mistake — the key is `root_cause`, not `cause` — and it is
  in a `try` so the script can print the failure. **The point of the line is the exception.** A wrong
  name in a lookup is caught the instant the code runs.
- `err.args[0]` is the key that was missing. `KeyError`'s string form quotes it; taking `args[0]`
  prints it once rather than twice.

Now the same facts, searched for:

```python
# days/day-46-sessions-vs-memory/lab/putfind.py (continued)
QUERIES = [
    "cookie",
    "logged out",
    "SameSite",
    "sign-in trouble",
    "authentication loop after redirect",
    "the customer",
]

    for i, (author, text) in enumerate(PAST_CASE):
        await sessions.append_event(session, said(author, text, float(i)))
    await memory.add_session_to_memory(session)

    print("\nFINDING - memory search, same facts, six queries")
    for query in QUERIES:
        found = await memory.search_memory(app_name=APP, user_id=USER, query=query)
        print(f"    {query!r:40} -> {len(found.memories)} memories")
```

**Line by line:**

- `QUERIES` runs from the most obvious wording to the least, on purpose. The first three are words
  that appear in the stored text; the next two are descriptions a real support agent would type; the
  last one is a phrase that carries no meaning at all. Watching the counts move across that list is
  the whole demonstration.
- `add_session_to_memory(session)` files the whole conversation, both events. Note that it takes the
  **session**, not a string and not a summary. What lands in the store is the raw text of what was
  said.
- The loop prints only `len(found.memories)`. Deliberately: this part is about *how many candidates
  came back*, not what they said. [2.3](../02-the-interface/2.3-what-comes-back-is-not-a-session.md)
  opens one up.

Run it:

```bash
cd days/day-46-sessions-vs-memory/lab
uv run python putfind.py
```

**Line by line:**

- One command, one arm, **zero model calls**. There is no ablation here because the two halves of the
  script *are* the comparison.

Measured on 2026-09-05:

```text
PUTTING - session state
    state['severity']   -> 'high'
    state['root_cause'] -> 'cookie flags'
    keys                -> ['root_cause', 'severity']
    state['cause']      -> KeyError('cause')  <- absence is loud

FINDING - memory search, same facts, six queries
    'cookie'                                 -> 1 memories
    'logged out'                             -> 1 memories
    'SameSite'                               -> 1 memories
    'sign-in trouble'                        -> 0 memories
    'authentication loop after redirect'     -> 1 memories
    'the customer'                           -> 2 memories
```

Six queries against two stored sentences, and there are three different failure shapes in that list.

**`'sign-in trouble'` returns nothing.** Every word in it is about the stored case. None of those
words is *in* the stored case, and `InMemoryMemoryService` compares words. This is the miss you
cannot see: an empty list looks the same whether there is no past case or there is one and you
described it differently.

**`'authentication loop after redirect'` returns one.** Not because the service understood the
phrase — it matched on the single word `redirect`, which happens to appear in the stored sentence.
The right answer arrived for the wrong reason, which means the next query of the same shape is a coin
toss.

**`'the customer'` returns two.** Two words, both of them content-free, and both stored sentences
contain one of them. This is the over-match, and it is the most dangerous of the three because it
returns *more* rather than less. [5.1](../05-failure-lab/5.1-the-past-that-matched-on-nothing.md) is
this behaviour scaled up to a full ticket archive, where "returns everything" and "returns the wrong
thing first" are the same event.

Verified against the installed source at
`.venv/Lib/site-packages/google/adk/memory/in_memory_memory_service.py` on 2026-09-05. The class
docstring says it is *"for prototyping purpose only"* and *"Uses keyword matching instead of semantic
search"*, and the match itself is one line:

```text
if any(query_word in words_in_event for query_word in words_in_query):
```

`any`, not `all`. **One shared word is a match.** That is the whole ranking function, and it explains
every row in the table above.

## When it breaks

The break that reaches production is not an exception. It is this line, written by somebody who has
only ever used state:

```python
found = await memory.search_memory(app_name=APP, user_id=USER, query=question)
if not found.memories:
    return "There is no past case like this."
```

**Line by line:**

- `if not found.memories:` treats an empty list as evidence of absence. It is not. It is evidence
  that nothing matched the words in `question`, which is a much weaker statement.
- `return "There is no past case like this."` is the sentence a customer reads. It is a claim about
  the world, made on the strength of a keyword comparison, and it is wrong every time a query is
  phrased like `'sign-in trouble'`.

There is no traceback here, and that is precisely the problem. The honest version says what actually
happened:

```python
if not found.memories:
    return f"Nothing in the archive matched the words {question!r}. That is not the same as no past case."
```

**Line by line:**

- The message names **what was searched for**, so the person reading it can try different words. An
  error a human can act on is Day 21's whole argument, in
  [4.1](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.1-the-swallowed-exception.md).
- The second sentence refuses the inference. It costs eleven words and it is the difference between a
  system that is honest about its limits and one that is confidently wrong.

The other break is a genuine exception, and it comes from the opposite direction — treating memory
like a dictionary:

```text
Traceback (most recent call last):
  File "...\demo.py", line 12, in <module>
    print(found["cookie"])
          ~~~~~^^^^^^^^^^
TypeError: 'SearchMemoryResponse' object is not subscriptable
```

`SearchMemoryResponse` is a pydantic model with one field, `memories`, which is a list. There are no
keys in it because there were never any keys.

## In production

**What a professional writes instead of the teaching version.** Two rules, and both of them exist to
stop a search being read as a lookup. First, every call site that consults memory records **what it
searched for** alongside what it got, in the structured log Day 22 built — because when somebody asks
in three weeks why the desk missed an obvious precedent, the query string is the only thing that will
answer them. Second, anything the code needs to *branch on* goes in session state, never in memory. A
`severity` you will compare against `"high"` must be at an address. A past case you will show to a
human may be a search result, because a human can tell that it is wrong.

**What degrades at scale or under concurrency.** A lookup's cost does not change when the store grows;
a search's does, in two ways at once. It gets slower — `InMemoryMemoryService` walks every stored
event on every query, and there is no index anywhere in it — and it gets *less precise*, because more
stored text means more accidental word overlap. Both curves are measured in
[5.4](../05-failure-lab/5.4-the-store-that-outgrew-its-value.md): at 500 filed cases a single query
matches all 500. Under concurrency, the lookup is a dictionary read and the search takes a lock and
copies the store.

**The review comment a senior engineer leaves:** *"`if not results: return 'no past case'` — you have
turned a retrieval miss into a factual claim. Say what you searched for and say that nothing matched
it. And log the query: the first thing anyone will ask when this misses is what string we actually
sent."*

**The interview question:** *"Your agent has a memory store and keeps missing relevant history. How do
you debug it?"* An honest answer: *"I would split it into three places it can fail before touching
anything. Filing: did the conversation ever enter the store — is there a log line for the write?
Retrieval: does a direct `search_memory` with the user's own wording return it? Usage: did the model
ever ask? In my case it was the middle one, and the finding was uncomfortable: the search was matching
on any single shared word, so the query 'sign-in trouble' found nothing while 'the customer' found
everything. That is not a tuning problem, it is a representation problem — no amount of prompt
rewording fixes it, you swap the matching behind the same interface."*
