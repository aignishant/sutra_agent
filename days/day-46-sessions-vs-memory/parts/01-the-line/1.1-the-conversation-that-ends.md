# 1.1 — The conversation that ends

## One-line answer

A **session** is one conversation and it has an end; **memory** is whatever you deliberately carry
out of it so a different conversation, on a different day, can find it.

## The story

Your broadband stops working on a Friday evening. You ring the helpline.

You spend a long call with somebody patient. You give the account number, the colour of the lights on
the box, the fact that it started after the building had a power cut, the fact that your neighbour on
the same line is fine. Together you work out that the line is up but the router has forgotten its
settings. They walk you through resetting it. It works. You thank them and put the phone down.

On Monday it happens again. You ring the same number.

Somebody else answers. And you start from the beginning: the account number, the lights, the power
cut, the neighbour. Not because this person is careless — they are perfectly helpful. They simply
were not in Friday's call, and Friday's call ended when you put the phone down.

Now think about what would have had to happen for Monday to go differently. Not a longer call on
Friday. Not a better person on Monday. Somebody would have had to take the one useful sentence out
of Friday's call — *"this router loses its settings after a power cut"* — and put it somewhere that
Monday could look.

That act, of taking something out of the conversation that is ending and putting it where a
different conversation can find it, is the whole subject of this day.

## The idea in plain language

Two words, and they are not two names for the same thing.

A **session** is one conversation between a person and your agent. It has an identity, it holds an
ordered list of everything that happened in it — the messages, the tool calls, the results — and it
has a beginning and an end. In ADK a session is a `Session` object with an `id`, an `app_name`, a
`user_id`, a list of `events`, and a small dictionary called `state`. Day 17's part
[2.2](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.2-an-invocation-is-not-a-session.md)
drew the line between one *invocation* — a single question answered end to end — and the *session*
that holds many of them. Today draws the next line out: the one past the session's own edge.

**Memory** is a separate store that holds material from *finished* sessions, so that a *new* session
can search it. It is not the session's history. It is not the session's state. It is a second
service, with its own object, its own methods and its own lifetime, and in ADK it is called a
`MemoryService`.

Here is the sentence to keep, because everything else in this day follows from it:

> **A session is what this conversation knows. Memory is what the desk has learned.**

Three consequences, stated now and proved later:

1. **Sessions are automatic; memory is not.** Every message your agent handles lands in a session
   without you asking. Nothing at all lands in memory unless a line of your code puts it there.
   [1.3](1.3-nothing-is-filed-unless-you-file-it.md) is that asymmetry, measured.
2. **A session is reached by name; memory is reached by search.** You know the session id, so you can
   fetch exactly that session. You do not know which memory you need, so you have to describe it and
   hope. [1.2](1.2-putting-versus-finding.md) is that difference.
3. **Search can be wrong.** Fetching session `sess-a` either returns `sess-a` or raises. Searching
   memory for *"logged out"* returns some list, and the list may contain the wrong past case, or none
   at all, and it will not tell you which. Section 5 is four ways that goes badly.

## Why Sutra needs it

Sutra's desk has been an island since it first ran. Day 8 gave it a session so that a conversation
could have more than one turn. Day 17 gave that session
[state with four lifetimes](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.1-the-prefix-is-the-lifetime.md),
and one of those lifetimes — `user:` — already crosses between a person's sessions. But `user:` state
is still a *place you put a known key*, not a store you can ask a question of.

Today is where the desk stops being an island. Tomorrow,

Day 47 makes one side of that line durable and Day 48 writes the policy for the other side.

And Day 49, *Retrieval and embeddings*, exists entirely because of
consequence 3 above. Search can be wrong; today you measure exactly *how* wrong the free
implementation is, and Day 49 is the fix.

## The mechanism

Everything in this day's lab runs with **no model at all**. That is not a compromise: the session
service and the memory service are ordinary Python objects, and you can drive them by hand. Start
with the fixtures every script in this day shares.

```python
# days/day-46-sessions-vs-memory/lab/_desk.py
from __future__ import annotations

from datetime import datetime

from google.adk.events import Event
from google.genai import types

APP = "sutra_desk"
USER = "agent_riya"

# A fixed epoch so every transcript in this day prints the same timestamps on any machine.
# 2026-08-29 16:10:00 local, expressed as a Unix timestamp at import time.
BASE_TS = datetime(2026, 8, 29, 16, 10, 0).timestamp()

PAST_CASE = [
    ("user", "Ticket 4521: the customer keeps getting logged out of the portal."),
    (
        "desk",
        "Root cause on 4521: the session cookie was set without the SameSite and Secure "
        "flags, so the browser dropped it on a cross-site redirect. Fix is KB-104.",
    ),
]

TODAY = "Any past case where a user keeps getting logged out?"


def said(author: str, text: str, offset: float = 0.0) -> Event:
    """Build one conversation event by hand, with no model and no runner."""
    role = "user" if author == "user" else "model"
    return Event(
        author=author,
        timestamp=BASE_TS + offset,
        content=types.Content(role=role, parts=[types.Part(text=text)]),
    )
```

**Line by line:**

- `APP` and `USER` are constants because they are **not decoration** — they are the two halves of the
  key that memory is bucketed by, and [2.4](../02-the-interface/2.4-the-bucket-is-a-person.md) is
  entirely about them. Getting them from one place means no script in this day can accidentally
  disagree with another about which bucket it is writing to.
- `BASE_TS` is a fixed date turned into a Unix timestamp, rather than `time.time()`. A memory entry
  carries a timestamp, and a demo whose printed timestamps change every run cannot be compared
  against the transcript in this document. Day 24's part
  [3.1](../../../day-24-token-accounting-and-budgets/parts/03-counting-before-spending/3.1-the-ledger.md)
  made the same choice for the same reason: *pass the clock in, do not read it*.
- `PAST_CASE` is two lines of a conversation, one from the person and one from the desk. It is written
  out in full rather than generated, because in section 5 you will be reading these exact words back
  out of a search result and asking whether they were the right ones.
- `said(...)` builds an `Event`, which is ADK's unit of "a thing that happened in a session". It takes
  an `author` — a free string, `"user"` for the person and the agent's name otherwise — and a
  `types.Content` holding the text.
- `role = "user" if author == "user" else "model"` — `author` and `role` are **two different fields**
  and both matter. `author` is who ADK thinks said it; `role` is what the provider's chat format
  calls it. They are usually parallel and are not the same field, which is why the memory entry you
  will see in [2.3](../02-the-interface/2.3-what-comes-back-is-not-a-session.md) carries `author` and
  the content underneath it carries `role`.
- `offset` shifts the timestamp so that two events in one conversation are not simultaneous. Ordering
  matters to a reader of the transcript, and it will matter to the paper this day reads, where
  **recency is one third of the retrieval score**.

Now the demonstration itself: one session learns something, a second session asks about it.

```python
# days/day-46-sessions-vs-memory/lab/island.py
async def main(*, use_memory: bool) -> None:
    sessions = InMemorySessionService()
    memory = InMemoryMemoryService()

    a = await sessions.create_session(app_name=APP, user_id=USER, session_id="sess-a")
    for i, (author, text) in enumerate(PAST_CASE):
        await sessions.append_event(a, said(author, text, float(i)))
    print("session A - Friday afternoon, ticket 4521")
    transcript(a)

    if use_memory:
        await memory.add_session_to_memory(a)
        print("    [session A filed into memory]")

    b = await sessions.create_session(app_name=APP, user_id=USER, session_id="sess-b")
    print(f"\nsession B - Monday morning, a different conversation ({len(b.events)} events)")
    print(f"    the question: {TODAY}")

    print("\nwhat session B can reach on its own:")
    print(f"    its own events        : {len(b.events)}")
    print(f"    its own state         : {dict(b.state)}")

    found = await memory.search_memory(app_name=APP, user_id=USER, query=TODAY)
    print(f"    memory search results : {len(found.memories)}")
```

**Line by line:**

- `InMemorySessionService()` and `InMemoryMemoryService()` are **two separate objects**, constructed on
  two separate lines. That is the picture of the whole day: sessions live in one place, memory lives
  in another, and nothing connects them until a line of code does. Both are imported from different
  packages — `google.adk.sessions` and `google.adk.memory`.
- `create_session(app_name=..., user_id=..., session_id=...)` — every argument is keyword-only. Passing
  `session_id` yourself, rather than letting the service mint one, is what makes this script's output
  reproducible; in a real run you would let it generate an id.
- `append_event(a, said(...))` writes one event into the session. This is Day 17's
  [3.3](../../../day-17-state-scopes-and-lifetimes/parts/03-three-safe-writes/3.3-writing-from-outside-a-run.md)
  — writing into a session from outside a run, by building the event yourself and appending it. It is
  the honest way to set up a scenario without spending a model call on it.
- `if use_memory: await memory.add_session_to_memory(a)` — **this is the ablation, and it is one
  line**. Everything else in both arms is identical. If the two runs differ, they differ because of
  this line and nothing else.
- `create_session(... session_id="sess-b")` makes a genuinely new conversation. It shares the
  `app_name` and the `user_id` with session A and shares nothing else — no events, no state.
- `search_memory(app_name=..., user_id=..., query=...)` takes the two scoping arguments and a string.
  Notice what it does **not** take: a session id. It is not asking about a conversation, it is asking
  about everything that has ever been filed under this app and this person.

Read the two blocks against each other. **Session B's own events and its own state are `0` and `{}`
in both runs.** The new conversation did not gain a single event. What changed is that a *different
service*, asked a question, returned two entries instead of none.

That is the shape of memory, and it is worth saying plainly because people expect the other shape:
memory does not make the new session bigger. It makes a search possible.

Verified against `https://adk.dev/sessions/memory/` on 2026-09-05, which states that a memory service
provides *"Ingesting Information: `add_session_to_memory`, `add_events_to_memory`, `add_memory`"* and
*"Searching Information (`search_memory`)"*. Note that `https://adk.dev/docs/sessions/memory/`
returns **HTTP 404**; the live page is at the path without `/docs`.

## When it breaks

The first break is the one everybody hits, and it is a `ValueError` that arrives from a place you
were not looking at. Build a runner with no memory service, give the agent a memory tool, and the
failure lands inside the framework rather than in your loop:

```text
  File "...\google\adk\tools\load_memory_tool.py", line 49, in load_memory
    search_memory_response = await tool_context.search_memory(query)
  File "...\google\adk\agents\context.py", line 986, in search_memory
    raise ValueError('Memory service is not available.')
ValueError: Memory service is not available.
```

`Memory service is not available.` means exactly one thing: the `Runner` was constructed without
`memory_service=`. It does not mean the store is empty, and it does not mean the search failed.
[3.1](../03-three-wires/3.1-the-service-rides-the-runner.md) is that wire.

The second break is quieter, and it is the reason this part exists. Somebody reads *"memory is what
survives the session"* and concludes that a longer session is a form of memory — so they stop
creating new sessions and keep appending to one. It works. For a while. Then the conversation is four
hundred turns long, the whole of it is re-sent to the model on every call (Day 19's
[1.3](../../../day-19-context-engineering-selection/parts/01-the-binder/1.3-the-organ-that-grows-by-itself.md)
measured that growth), and the bill for remembering March is paid on every question asked in
September. There is no error text for this one. It shows up as latency and as quota, and the symptom
never mentions sessions.

The third is the opposite mistake: expecting the *new* session to contain the past. A reader who
believes memory copies old events into the new conversation will write `len(session.events)` and see
`0`, and conclude that filing failed. It did not. Look at the transcript above: `its own events : 0`
in both arms. Memory is a service you query, not a transfusion.

## In production

**What a professional writes instead of the teaching version.** Nobody hand-appends events in a real
system — the runner does it. What a professional does write, and what this teaching version stands in
for, is the moment of *promotion*: the explicit call that moves a finished conversation into the
long-lived store. In a real desk that call sits in one place, usually an `after_agent_callback`
(3.2), never scattered through the tools, and it is guarded by a policy about which conversations are
worth keeping — which is [Day 48](../../../day-48-memory-design/LESSON.md)'s whole subject.

**What degrades at scale or under concurrency.** The session side and the memory side degrade
differently, and confusing them is a common outage. Sessions grow *per conversation* and are bounded
by how long one person talks; memory grows *per organisation*, forever, and is bounded by nothing.
A support desk with two hundred agents handling forty tickets a day each adds eight thousand
conversations a day to the store and never removes one. Under concurrency the two also differ: two
turns of one session are naturally serialised by the person typing, while two hundred agents write
to memory at once. `InMemoryMemoryService` takes a `threading.Lock` around every read and write for
exactly that reason, and its `search_memory` copies the event lists into a snapshot before iterating
them, with a comment saying that iterating a live reference *"would race with concurrent writers"*.

**The review comment a senior engineer leaves:** *"You have described this as 'the agent remembers
now'. It does not remember, it searches, and a search returns a guess. Before this ships I want to
see what happens on a query that matches the wrong past ticket, because 'the desk confidently told a
customer about somebody else's outage' is the failure this feature introduces and it is not in the
test plan."*

**The interview question:** *"What is the difference between session state and memory in an agent
system?"* An honest answer: *"Scope and access. A session is one conversation — its events and its
state — and it is reached by its id, so a read either gets exactly what you asked for or raises.
Memory is a separate store holding material from finished conversations, and it is reached by a
search, so a read returns a guess that can be empty or wrong. The thing I would emphasise is that
they are two services on the runner, not one, and nothing crosses between them automatically. On the
desk I built, filing a session into memory was one line in an after-agent callback, and until
somebody wrote that line the system had a perfect memory of every conversation and could not answer a
single question about any of them."*
