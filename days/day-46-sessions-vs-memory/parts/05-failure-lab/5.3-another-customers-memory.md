# 5.3 — 💥 Another customer's memory

## One-line answer

Filing every case under the **support agent's** id puts two companies' tickets in one bucket, so a
search on Blue Peak's ticket returns Northwind's billing address first — correctly filed, correctly
retrieved, by code with no bug in it except one string.

## The story

Your family has one library card.

It was taken out in your father's name years ago, and everybody uses it. You take out novels, your
sister takes out her exam guides, your father takes out books about gardening. One card, one number,
one page in the register. It has never caused the slightest problem.

Then the library computerises. Now, when you go to the counter, the screen shows the librarian
everything that card has ever borrowed, and she is helpful, and she says: *"I see you enjoyed the
book on rose cultivation — there's a new one in."*

You have never read a book about roses in your life.

Nothing has gone wrong. Nobody has broken in, nothing is lost, no rule was bent. The card was always
a family card, and the library was always keeping a list. What changed is that somebody started
**reading the list back to whoever is standing at the counter**, and on that day the fact that three
people share one number stopped being a convenience and became something else.

## The idea in plain language

The bucket is `(app_name, user_id)` and nothing else
([2.4](../02-the-interface/2.4-the-bucket-is-a-person.md)). There is no session id in the key, no
customer field, and no filter you can pass to `search_memory` — it takes three arguments, `app_name`,
`user_id` and `query`, and it returns everything in that one bucket that shares a word with the
query.

Sutra has filed everything under `agent_riya` since Day 8, because until today `user_id` decided only
which conversation you resumed. So the desk's bucket is *one support agent*, and every customer that
agent has ever helped is in it.

Now put the two facts together:

1. Every ticket the agent has worked is in one bucket.
2. The matcher counts one shared word as a hit
   ([5.1](5.1-the-past-that-matched-on-nothing.md)).

Two companies with the same symptom — *"keeps getting logged out"* — share five words. The search
returns both. And the memories are not summaries; they are the **events**, verbatim, with whatever
was said in them: a billing contact address, a contract value, a named person at the other company.

There is no access check anywhere in this path. `search_memory` does not know what a customer is. It
does not know what a permission is. It reads the bucket you named and hands back what matched, and
the only thing separating one company's data from another's is which string your code put in
`user_id` on the day it was written.

**The fix is one line and it is not free.** File under the customer instead, and each company gets
its own bucket and nothing crosses. You also lose the thing the desk existed for: an agent working
Blue Peak's ticket can no longer see that Northwind hit the same fault last month, which was the
whole promise of *"seen anything like this before?"*. That trade is the subject of this part, and it
does not have a correct answer that fits in a sentence.

## Why Sutra needs it

Because this is the first failure in Sutra where the damage lands on somebody who is not the user.

Everything else in this day's failure lab costs the desk quality: a wrong article number
([5.1](5.1-the-past-that-matched-on-nothing.md)), an empty store
([5.2](5.2-the-store-that-was-never-a-store.md)), a bill that grows
([5.4](5.4-the-store-that-outgrew-its-value.md)). Those are bad. This one puts one customer's
contract value in front of another customer's ticket, and the person harmed never touched the system.

Principle 13 says a new power arrives with its containment story. Memory is the largest new power
Sutra has been given since tool calling, and this is its containment story: **the bucket is the
boundary, and Sutra picked its bucket by accident four phases ago.** Day 48 cannot write a retention
policy until this is settled — *"delete this customer's data"* is a sentence about buckets, and if the
bucket is an agent then the sentence has no implementation.

## The mechanism

Two companies, one symptom, and one flag that changes which string goes into `user_id`.

```python
# days/day-46-sessions-vs-memory/lab/leak.py
AGENT = "agent_riya"
CASES = [
    (
        "cust_northwind",
        "4521",
        "Northwind Foods: keeps getting logged out. Billing contact is "
        "accounts@northwind.example, plan is Enterprise at 4.2 lakh a year.",
    ),
    (
        "cust_bluepeak",
        "4610",
        "Blue Peak Logistics: keeps getting logged out after the SSO "
        "change. Contact is ops@bluepeak.example.",
    ),
]
QUESTION = "keeps getting logged out"
```

**Line by line:**

- Each row carries **both** candidate ids — the customer (`cust_northwind`) and, through `AGENT`, the
  agent — so the two arms differ in exactly one expression and nothing else.
- The two ticket texts deliberately contain the kind of thing a real ticket contains: an email
  address and a contract value. This is not decoration. The failure is uninteresting if the leaked
  memory is *"the customer had a problem"*; it is a reportable incident if it is a billing contact
  and an annual figure, and a lab that only leaks harmless text teaches the wrong sense of severity.
- Both entries share the phrase **"keeps getting logged out"**, which is realistic rather than
  contrived — companies hit the same faults, which is precisely why anybody wants a memory feature.
- `QUESTION` is five words with no ticket number and no company name in it. Even a perfect keyword
  matcher would return both rows for this query, so the failure below is **not** caused by the weak
  matcher of [5.1](5.1-the-past-that-matched-on-nothing.md). It is caused by the bucket.

```python
# days/day-46-sessions-vs-memory/lab/leak.py (continued)
    for customer, ticket, text in CASES:
        user_id = customer if per_customer else AGENT
        session = await sessions.create_session(app_name=APP, user_id=user_id, session_id=ticket)
        await sessions.append_event(session, said("desk", text, 0))
        await memory.add_session_to_memory(session)

    print(f"buckets in the store     : {sorted(k[1] for k in memory._session_events)}\n")

    asking_as = CASES[1][0] if per_customer else AGENT
    found = await memory.search_memory(app_name=APP, user_id=asking_as, query=QUESTION)
    for entry in found.memories:
        text = "".join(p.text or "" for p in (entry.content.parts or []))
        leaked = "  <-- NOT BLUE PEAK'S" if "Northwind" in text else ""
        print(f"      {text[:84]}{leaked}")
```

**Line by line:**

- `user_id = customer if per_customer else AGENT` is the entire difference between a correct system
  and an incident. One conditional expression, in the line that creates a session — which is exactly
  where this decision gets made in real code, several files away from anything that mentions privacy.
- `session_id=ticket` uses the ticket number, which is sensible and completely irrelevant: session id
  is **not** part of the memory key, so two sessions with different ids land in the same bucket
  whenever their `user_id` matches ([2.4](../02-the-interface/2.4-the-bucket-is-a-person.md)).
- `sorted(k[1] for k in memory._session_events)` reads the store's private dictionary to print its
  keys. Reaching into a private attribute is not something to do in application code; it is done here
  because **the store offers no way to ask what buckets it holds**, and the number of buckets is the
  finding. One key means one boundary for everybody.
- `asking_as` is the id the search runs under, and it mirrors the filing decision — because in real
  code the same variable is used for both. A system that filed under the customer and searched under
  the agent would find nothing at all, which is a different and much safer bug.
- The `leaked` marker is computed by looking for `"Northwind"` in a search made on Blue Peak's ticket.
  It is a test assertion written as a print statement: if that string can appear, the boundary is not
  a boundary.
- No model, no key, no network. **Zero model calls in both arms.**

**Line by line:**

- The first arm is what Sutra does today: `user_id` is the support agent.
- `--per-customer` is the fix, and it is the only change. Same store, same question, same matcher,

Measured on 2026-09-05:

```text

now working ticket 4610 for Blue Peak, searching as user_id='agent_riya'
    memories returned    : 2
      Northwind Foods: keeps getting logged out. Billing contact is accounts@northwind.exa  <-- NOT BLUE PEAK'S

```

```text
user_id used when filing : the customer

    memories returned    : 1
      Blue Peak Logistics: keeps getting logged out after the SSO change. Contact is ops@b
```

**One bucket becomes two, and two results become one.** Read the leaked line properly before moving
on: a search made while working Blue Peak's ticket returned another company's name, another company's
billing contact and another company's contract value — **first**, ahead of the correct result, because
Northwind was filed earlier and the list is in insertion order
([5.1](5.1-the-past-that-matched-on-nothing.md)).

Now read what the fix cost. In the second arm the desk has two buckets and can never look across
them. The agent working 4610 cannot be told that the identical fault was diagnosed on 4521 last month
and closed with KB-104. The leak is gone and so is the feature.

Verified on 2026-09-05 against `.venv/Lib/site-packages/google/adk/memory/in_memory_memory_service.py`:
the key is `_user_key(app_name, user_id) -> (app_name, user_id)`, `search_memory` reads
`self._session_events.get(user_key, {})` and iterates only that, and `add_session_to_memory` writes
`self._session_events[user_key][session.id]`. There is no filter argument on `search_memory` and no
authorisation check anywhere in the module. Confirmed against `https://adk.dev/sessions/memory/`,
which describes the call as one that *"lets an agent (typically via a `Tool`) query the knowledge
store"* and names no scoping beyond the service's own.

## When it breaks

The incident above is the break. Three more shapes of it are worth naming, because two of them
survive the fix you just watched work.

**A memory filed under the wrong bucket cannot be moved.** Once a year of tickets is in the
`agent_riya` bucket, switching to per-customer buckets does not migrate anything; it strands
everything. The old bucket is still there, still searchable by anybody who passes that string, and
still full of every customer's text. Cleaning it up means writing a migration that can attribute each
stored **event** to a customer — and events do not carry a customer field, so the attribution has to
be inferred from the text. That is the real cost of getting a key wrong, and it is why this decision
belongs at the start rather than after the pilot.

**The third bucket choice leaks to everybody.** [2.4](../02-the-interface/2.4-the-bucket-is-a-person.md)
listed a constant `user_id` — one bucket for the whole desk — as the option that gives you shared
institutional knowledge. It also gives every agent every customer's text, and it is the most tempting
option precisely because it makes the feature work best. A team that hits the "agents cannot learn
from each other" problem in the second arm above will reach for it, and it is a larger version of the
same incident.

**The bucket is right and the text is still wrong.** Per-customer bucketing contains the *store*; it
does nothing about what the model then says. A desk that retrieved Blue Peak's own past ticket and
quoted its internal note back to the customer has leaked nothing across buckets and has still said
something it should not. Containment at the store is necessary and it is not sufficient, which is
Day 48's problem: what should have been filed at all.

There is no error text for any of this. The only artefact is the transcript, and the transcript is
only there because Sutra chose `load_memory` over `preload_memory`
([4.2](../04-the-choice/4.2-sutras-memory-policy.md) rule 1). Under automatic injection the same leak
happens with no query and no result anywhere in the record — the memories are in the prompt and
nothing else.

## In production

**What a professional writes instead of the teaching version.** The bucket is never assembled at a
call site. One function — `memory_scope(request) -> tuple[str, str]` — turns the authenticated caller
plus the ticket's customer into the pair, and every `create_session` and `search_memory` call in the
codebase goes through it. That is one place to review, one place to test, and one place to log. The
test that matters is not *"does search work"* but *"does a search under caller A ever return text
filed under caller B"*, written as an explicit assertion over two buckets, exactly like the `leaked`
marker in `leak.py` — which is a test wearing a print statement's clothes.

They also **write down which of the three bucket choices was made and why**, next to the function,
with a date. This is a privacy decision expressed as a string literal, and a string literal with no
comment beside it is a decision that will be changed by somebody who thinks they are fixing a bug.

**What degrades at scale or under concurrency.** The blast radius grows with the bucket, and the
bucket is chosen once. Per-agent bucketing means one agent's bucket holds every customer that agent
has ever touched — after a year that is thousands of companies, all reachable by a five-word query
from any conversation that agent is in. Per-customer bucketing scales the opposite way: many small
buckets, fast searches, and a deletion request that is a key removal rather than a scan. Under
concurrency neither is worse, because the boundary is a dictionary key rather than a lock — but a
mis-scoped key under concurrency is a leak on every request rather than an occasional one.

**The failure mode that only appears with real traffic.** Similar customers. In testing you write two
tickets and they are obviously different companies. In production you have forty customers in the
same industry with the same integration hitting the same fault in the same week, and every query
matches all of them. The leak rate is not a constant; it rises with how homogeneous your customer
base is, which is the opposite of what anybody assumes.

**The review comment a senior engineer leaves:** *"`user_id=agent_riya` in `create_session` and in
`search_memory`. That makes one agent's memory bucket span every customer they have ever worked with,
and the store has no filter argument — so any five-word query in any conversation can return another
company's ticket text verbatim. Route both call sites through one `memory_scope()` function, decide
per-customer or per-agent explicitly, and write the reason and the date beside it. And please add the
cross-bucket assertion to the test suite; it is three lines and it is the only thing that will catch a
regression here."*

**The interview question:** *"How do you stop an agent's memory leaking between users?"* An honest
answer: *"You cannot stop it after the fact, because the store has no access control — in ADK the
memory bucket is the tuple `(app_name, user_id)` and `search_memory` takes no filter, so whatever
string you pass is the boundary. The mistake is easy to make: our support desk had used the support
agent's id as `user_id` since long before memory existed, because until then it only decided which
conversation resumed. The moment we filed tickets into it, one agent's bucket contained every
customer they had ever helped, and a five-word query — 'keeps getting logged out' — returned another
company's billing contact and contract value, ahead of the right result, with no error. Switching the
id to the customer fixed it in one line and cost us the feature: agents could no longer see that a
different customer had hit the same fault. So the real answer is that the bucket is a product
decision, not an implementation detail, it should be made through a single scoping function so there
is one place to review it, and there should be a test that asserts nothing filed under one caller can
be read by another."*
