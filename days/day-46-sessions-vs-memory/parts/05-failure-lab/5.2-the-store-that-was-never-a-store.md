# 5.2 — 💥 The store that was never a store

## One-line answer

`InMemoryMemoryService` keeps everything in one Python dictionary on one object inside one process,
so the afternoon where five filed cases returned ten memories becomes a Monday where the same search
returns **zero** — with no error, no warning and no log line, because nothing failed.

## The story

There is a whiteboard on the wall of the room your team sits in.

Over one long afternoon it fills up. The on-call rota for the month. Three phone numbers. A rough
drawing of how the two systems talk to each other, which took four people and a lot of arguing to get
right. Somebody writes **DO NOT WIPE** in the corner, underlined twice, and everybody goes home
pleased.

On Monday the board is blank and clean and smells faintly of spirit.

Nobody did anything wrong. The person who cleans that floor cleans the boards, has done for years,
and does not read English well enough for the corner to have meant anything. There was no argument
and no incident. The rota is simply gone, and the four people who worked out the drawing are going to
have to work it out again, and the first thing that happens on Monday morning is that nobody can
remember whose week it is.

The board was never storage. It was a surface that happened not to have been wiped yet.

## The idea in plain language

Every part of this day so far has been about a store: things go in
([1.3](../01-the-line/1.3-nothing-is-filed-unless-you-file-it.md)), things come out
([1.2](../01-the-line/1.2-putting-versus-finding.md)), the bucket is a person
([2.4](../02-the-interface/2.4-the-bucket-is-a-person.md)). All of that is true, and all of it is
true **only while the process is alive**.

`InMemoryMemoryService` holds one attribute:

> `self._session_events: dict[tuple[str, str], dict[str, list[Event]]] = {}`

That is the whole store. A dictionary, on an instance, in the heap of one Python process. It has no
file behind it, no database connection, no directory, no flush and no `close()`. When the process
ends — a deploy, a crash, a restart, a machine that reboots for updates, or just pressing `Ctrl+C` —
the dictionary is garbage and so is everything in it.

`InMemorySessionService` is exactly the same shape for sessions. So the failure comes in two halves
that arrive together:

| What is lost | Where it lived | What the user sees |
| --- | --- | --- |
| Every session, including the one open right now | `InMemorySessionService`'s dict | The conversation restarts mid-sentence |
| Every filed memory, however carefully filed | `InMemoryMemoryService._session_events` | *"I have no record of that"* |

And here is the part that makes this a failure lab rather than a footnote. **Nothing tells you.** The
service does not raise on an empty store, because an empty store is a perfectly legal store. A search
against nothing returns `SearchMemoryResponse(memories=[])`, which is the same object a search that
genuinely found nothing returns. There is no `is_empty`, no startup warning, no *"the store you are
searching has never had anything filed into it"*.

The word **in-memory** is in the class name, and it is doing all the warning that anybody is going to
get.

## Why Sutra needs it

Because this is the failure that survives the demo and dies in the deployment, and the gap between
those two events is where the damage happens.

Everything in sections 1 to 4 works. Filing works, searching works, the wiring works, the policy has
five green rules. You can run the desk all afternoon, file case after case, ask *"have we seen this
before?"* and get real answers with real article numbers in them. Every check on the checklist is
green, honestly.

Then you deploy, and the thing you demonstrated is not the thing you shipped. A support desk that
loses its memory on every deploy is worse than one that never had any, because the team has already
started relying on it and nobody has any reason to suspect the store — the store worked yesterday.

This is why **Day 47 exists**, and it is the reason it comes immediately after this day rather than
three phases later. Day 47 replaces `InMemorySessionService` with `DatabaseSessionService` and gives
sessions a file to live in. It is also why rule 3 of
[4.2](../04-the-choice/4.2-sutras-memory-policy.md) — *the store rides the runner* — is worth its
place: the service is constructed in one assembly function, so making it durable is a change in one
place rather than in every agent.

## The mechanism

One script, two processes' worth of work simulated in one run: an afternoon that works, then the
same code against fresh objects.

```python
# days/day-46-sessions-vs-memory/lab/restart.py
async def afternoon(sessions, memory) -> None:
    for n in range(5):
        session = await sessions.create_session(app_name=APP, user_id=USER, session_id=f"case-{n}")
        for i, (author, text) in enumerate(PAST_CASE):
            await sessions.append_event(session, said(author, text, float(i)))
        await memory.add_session_to_memory(session)
```

**Line by line:**

- `afternoon` takes the two services as **arguments** rather than building them, which is the whole
  trick of this script: the same function is called against one pair of objects and then the second
  pair is simply never given to it. That is what a restart is, expressed in Python.
- `range(5)` files five separate cases, each with its own `session_id`. Five is enough to make the
  "before" number obviously non-zero and small enough to read.
- `PAST_CASE` is the two-event exchange from `_desk.py` — a customer complaint and the root cause —
  so each filed session contributes **two** events, and the search below should therefore find ten
  memories rather than five. Memories are events, not sessions
  ([2.3](../02-the-interface/2.3-what-comes-back-is-not-a-session.md)).
- `sessions.append_event(session, ...)` goes through the **service**, not through `session.events`,
  because the service is what `add_session_to_memory` will read from
  ([3.2](../03-three-wires/3.2-the-line-where-it-crosses.md)).
- `memory.add_session_to_memory(session)` is the deliberate filing act. Every one of these five calls
  succeeds. Not one of them is undone by what happens next; they are simply unreachable.

```python
# days/day-46-sessions-vs-memory/lab/restart.py (continued)
    print("--- process 1: the afternoon everything worked ---")
    sessions, memory = InMemorySessionService(), InMemoryMemoryService()
    await afternoon(sessions, memory)
    found = await memory.search_memory(app_name=APP, user_id=USER, query=TODAY)
    print(f"    store lives at  : {type(memory).__name__}._session_events, id={id(memory):#x}")

    print("\n--- the deploy on Monday morning: a new process, new objects ---")
    sessions, memory = InMemorySessionService(), InMemoryMemoryService()
    found = await memory.search_memory(app_name=APP, user_id=USER, query=TODAY)
    listed = await sessions.list_sessions(app_name=APP, user_id=USER)
```

**Line by line:**

- The two `sessions, memory = ...` lines are **identical**. Nothing is deleted, nothing is closed,
  nothing is corrupted. The second line simply rebinds both names to new objects, and the old ones —
  with the five filed cases inside them — have nothing referring to them any more.
- `id(memory):#x` prints the object's address in hexadecimal. It is the only visible evidence that
  anything changed at all, and it is evidence you would never have in production. Two different
  numbers mean two different dictionaries; that is the entire failure, made printable.
- `search_memory(...)` is called with **the same three arguments** in both halves: same `app_name`,
  same `user_id`, same query. If the store were a store, the answer would be the same too.
- `sessions.list_sessions(...)` asks the other service the same question. It is here so that the
  transcript shows both halves of the loss together — the sessions and the memories go at the same
  instant, for the same reason.
- The script imports nothing beyond ADK and `_desk.py`, and calls no provider. **Zero model calls.**

Run it:

```bash
cd days/day-46-sessions-vs-memory/lab
uv run python restart.py
```

**Line by line:**

- Run from `lab/` because the script imports `_desk.py` from beside it.
- There is no second arm and no flag. The point of this part is that **there is no switch** — nothing
  in `InMemoryMemoryService` can be configured to survive, which is why the fix is a different class
  and a different day.

Measured on 2026-09-05:

```text
--- process 1: the afternoon everything worked ---
    sessions filed  : 5
    search finds    : 10 memories
    store lives at  : InMemoryMemoryService._session_events, id=0x135bef41550
    every check on the checklist is green

--- the deploy on Monday morning: a new process, new objects ---
    sessions held   : 0
    search finds    : 0 memories
    store lives at  : InMemoryMemoryService._session_events, id=0x135bef40b00

    no error. No warning. No log line. The desk is simply new again.
```

**Ten memories, then zero.** The two addresses differ, and that is the only difference in the entire
run. Your machine will print two different hexadecimal numbers from these, because an object's
address is whatever the allocator gave it; what must match is the shape — two numbers, not one.

Verified on 2026-09-05 against the installed source at
`.venv/Lib/site-packages/google/adk/memory/in_memory_memory_service.py`, whose class docstring says
*"An in-memory memory service for prototyping purpose only"* and *"it should be used for testing and
development only"*, and whose only state is the `_session_events` dict quoted above — there is no
file, socket or path anywhere in the module. Confirmed against `https://adk.dev/sessions/memory/`,
read the same day, which gives `InMemoryMemoryService` a persistence row of **None** and describes it
as *"best for prototyping and simple testing scenarios where persistence isn't required"*.
`https://adk.dev/sessions/session/` says the same thing about the session side in stronger words:
*"None. All conversation data is lost if the application restarts."*

## When it breaks

It has already broken. What is worth having in front of you is the four shapes the break arrives in,
because only one of them looks like a restart.

**A deploy.** The obvious one, and the least damaging, because somebody was watching.

**A crash and an automatic restart.** The supervisor brings the process back in a second or two and
nothing in the dashboard goes red for long enough to notice. The memory is gone and the graph says
the service is healthy, which it is.

**A second instance.** This one is not a restart at all and it is much worse. Put the desk behind two
processes and you now have **two stores**, and which one answers depends on which instance took the
request. A case filed through instance A is invisible to instance B, so the desk remembers
intermittently — the failure mode everybody blames on the model, because it looks exactly like a
model being flaky. Nothing in the code changed; the deployment changed.

**A test suite.** Every test that builds its own `InMemoryMemoryService` gets its own store, which is
correct and desirable. It also means that no test in your suite can ever catch any of the three
failures above, because a fresh store per test is the very condition you are failing to notice in
production.

The one honest signal available is at construction, and it is the class name. So the check is not a
traceback to recognise; it is a line to grep for:

```text
$ grep -rn "InMemoryMemoryService\|InMemorySessionService" sutra/
sutra/memory/service.py:14:    return InMemoryMemoryService()
```

A production module that names either class is a production module with no memory, and that is a
finding whether or not anything has gone wrong yet.

## In production

**What a professional writes instead of the teaching version.** They do not construct either
in-memory service anywhere except in tests. The assembly function reads the store from configuration
and the in-memory implementation is what the **absence** of configuration falls back to — with a
startup log line at `WARNING` saying so in words: *"no session database configured; sessions and
memory will be lost on restart"*. That single line converts a silent architectural fact into
something a person scanning a log at deploy time can see. It costs nothing and it is the difference
between finding this out on your terms and finding it out from a customer.

**What degrades at scale or under concurrency.** The second-instance case above is the whole answer,
and it is not a degradation so much as a cliff. One process is a system that forgets on restart. Two
processes is a system that forgets **at random**, and the randomness scales with your instance count:
with four instances a filed case is found by roughly one request in four. Everything Day 43 taught
about [stateless servers](../../../day-43-stateless-by-default/LESSON.md) applies here in reverse —
the reason a deploy-shaped process may hold no state is precisely that any instance must be able to
answer any request, and an in-process memory store breaks that rule while looking like ordinary code.

**The failure mode that only appears with real traffic.** Partial memory. In a pilot with one
instance and no deploys, the store fills up over days and the desk gets visibly better, which is a
powerful and completely misleading experience: the team learns to trust it. The first deploy after
that resets the quality to day one, and because quality is a soft thing nobody has a metric that goes
red. The complaint arrives as *"it feels worse than it was last month"*, which is unfalsifiable and
therefore ignored.

**The review comment a senior engineer leaves:** *"`build_memory_service()` returns
`InMemoryMemoryService()` unconditionally. That is fine for now, but it means the store is
per-process, so it is empty after every deploy and inconsistent the moment we run two replicas. Add
the log line at startup that says so, and put the class behind the same configuration switch Day 47
is adding for sessions, so the two cannot drift apart."*

**The interview question:** *"What is the first thing you check when an agent 'sometimes' remembers
things?"* An honest answer: *"How many instances are running. The default memory and session services
in ADK are dictionaries on an object inside one process — the docs give them a persistence row of
'None' — so with one replica they lose everything on a deploy, and with more than one they only see
what was filed through the same replica. That reads as an intermittent model problem and it is a
deployment problem. I proved it to myself with a script that files five cases, finds ten memories,
then rebinds the two service objects and runs the identical search: zero memories, no error, no
warning, and the only visible difference in the whole run is the object's address. The fix is not a
better retriever, it is a store with a file behind it — a database-backed session service and a
managed memory service — and the interim mitigation is a `WARNING` at startup naming the fact, so at
least the team knows which of the two problems they are looking at."*
