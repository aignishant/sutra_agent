# 2.4 — The bucket is a person, not a conversation

## One-line answer

Every memory is filed under the pair `(app_name, user_id)` and can be found only by a search using
that same pair — so the single most consequential decision in this whole day is **who you decide the
user is**.

## The story

The tailor two streets over keeps a thick notebook under the counter.

Each customer has a page. Your page has your shoulder, your sleeve, your chest, the note that you
like the kurta a little longer than most people, and the date each measurement was taken. When you
walk in he does not measure you again. He turns to your page.

He also never reads your page to anybody else. Not out of ceremony — it simply does not come up,
because he works one customer at a time and one page at a time, and the page he has open is yours.

The whole system rests on one thing, and it is not the notebook. It is that he can reliably decide
**whose page this is**. And the one time that goes wrong is when two customers have the same name and
he writes both sets of measurements on one page. Nothing is lost. Nothing is stolen. But now one of
them is going to collect a kurta cut to somebody else's shoulder, and the notebook will look
perfectly tidy the whole time.

## The idea in plain language

`InMemoryMemoryService` holds a dictionary. Its keys are built by one function, and the function is
three lines long:

> `def _user_key(app_name: str, user_id: str) -> tuple[str, str]: return (app_name, user_id)`

That tuple is the **bucket**. Filing puts events into the bucket named by the session's `app_name`
and `user_id`. Searching looks in the bucket named by the `app_name` and `user_id` you passed. There
is no other index, no global pile, and no way to search across buckets.

Three things follow, and the third one is the one that bites.

**Session id is not part of the key.** Everything one user ever files under one app lands in one
bucket, whichever conversation it came from. That is the point — memory that could only be read by
the session that wrote it would be session state with extra steps.

**`app_name` genuinely separates.** Two applications sharing a store do not see each other's
memories. A nightly summariser writing under `sutra_nightly` cannot be read by the desk running as
`sutra_desk`, even for the same person. That is either an isolation guarantee or a bug, depending on
whether you meant it.

**`user_id` is a string you chose, and the store will not check it.** It is not authenticated, not
validated and not connected to any identity system. Whatever your code passes is the bucket.
`search_memory` will happily read a bucket the caller has no right to. The only thing standing
between one person's history and another's is the correctness of the value your code passed, and
[5.3](../05-failure-lab/5.3-another-customers-memory.md) is that going wrong in the most ordinary
possible way.

So: **who is the user?** For a consumer chat assistant the answer is obvious — the person typing. For
a support desk it is genuinely not. There are at least three candidates and they give three different
systems:

| `user_id` is… | What memory becomes | What leaks |
| --- | --- | --- |
| the support agent | one agent's private notebook | nothing across agents; **everything across customers** |
| the customer | one customer's history | nothing; but agents cannot learn from each other |
| the whole desk (a constant) | shared institutional knowledge | **everything, to everyone** |

None of those is wrong in the abstract and all three are wrong for some product. What is definitely
wrong is picking one by accident, which is what happens when `user_id` is filled in with whatever
value was already lying around.

Day 17's part
[2.3](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.3-where-user-and-app-live.md)
drew this same line for `user:`-prefixed state: it is *"not stored on the session at all"* and lives
in a separate place keyed by app and user. Memory uses the identical key. What is new today is that
memory is the store where getting the key wrong stops being an inconvenience and starts being a
privacy incident, because state holds facts your code chose and memory holds whatever anyone said.

## Why Sutra needs it

Sutra's desk has always run with `user_id` set to the support agent — `agent_riya` in every lab
script since Day 8 — because until today that value only decided which conversation you resumed.
Today it decides which customers' histories are visible to each other, and the value that was
harmless for eight phases is a defect in this one.

That is not a hypothetical. Run [5.3](../05-failure-lab/5.3-another-customers-memory.md) and watch
one company's billing contact surface in another company's ticket, filed correctly, retrieved
correctly, by a system with no bug in it anywhere except a string.

So Sutra's build brief has a `TODO(me)` for it, and Day 48's retention policy has to know the answer
before it can say anything about expiry — because "delete this customer's data on request" is a
sentence about buckets.

## The mechanism

Three sessions, three different `(app_name, user_id)` pairs, then every combination searched.

```python
# days/day-46-sessions-vs-memory/lab/scope.py
BUCKETS = [
    ("sutra_desk", "agent_riya"),
    ("sutra_desk", "agent_vikram"),
    ("sutra_nightly", "agent_riya"),
]


async def main() -> None:
    sessions = InMemorySessionService()
    memory = InMemoryMemoryService()

    for n, (app, user) in enumerate(BUCKETS):
        session = await sessions.create_session(app_name=app, user_id=user, session_id=f"s{n}")
        for i, (author, text) in enumerate(PAST_CASE):
            await sessions.append_event(session, said(author, f"[{app}/{user}] {text}", float(i)))
        await memory.add_session_to_memory(session)
```

**Line by line:**

- `BUCKETS` deliberately holds three of the four possible combinations of two apps and two users. The
  missing fourth is the control: it must return nothing, and if it does not, the key is not what the
  source says it is.
- `f"[{app}/{user}] {text}"` stamps each stored line with the bucket it was written into, so a leak
  in the output is visible rather than inferred.
- `await memory.add_session_to_memory(session)` passes only the session. **You never tell the memory
  service which bucket to use** — it reads `session.app_name` and `session.user_id` off the object.
  That is why a session created with the wrong `user_id` files into the wrong bucket silently: by the
  time you are filing, the mistake is three function calls upstream.

```python
# days/day-46-sessions-vs-memory/lab/scope.py (continued)
    apps = sorted({a for a, _ in BUCKETS})
    users = sorted({u for _, u in BUCKETS})
    print(f"    {'app_name':16} {'user_id':16} memories")
    for app in apps:
        for user in users:
            found = await memory.search_memory(app_name=app, user_id=user, query="cookie")
            print(f"    {app:16} {user:16} {len(found.memories)}")

    print(f"    buckets that exist now: {sorted(memory._session_events)}")
```

**Line by line:**

- The nested loop searches **all four** combinations with the same query, so the only variable across
  the four rows is the key.
- `query="cookie"` is a word present in every stored case. Holding the query constant is what makes
  the row counts a statement about scoping rather than about matching.
- `memory._session_events` is a **private** attribute, and reading it here is deliberate: the public
  interface offers no way to ask what buckets exist, and seeing the real dictionary keys is worth one
  underscore in a lab script. Do not do this in `sutra/` — the point of reading it once is that you
  never have to guess again.

crossing at all.

## When it breaks

There is no exception for this failure, which is exactly what makes it dangerous. Every wrong answer
is a well-formed answer.

**A search under a bucket nobody wrote to** returns an empty list, and looks identical to a search
that found nothing relevant:

```text
    memories returned    : 0
```

That is the whole diagnostic output. A misspelled `user_id`, a missing `app_name`, a service reading
under `"sutra-desk"` while the writer used `"sutra_desk"` — all of them produce that same line, and
none of them produces a warning. When memory "stops working" after a deploy, compare the two strings
first, before anything else.

**A search under a bucket too many people wrote to** returns the wrong person's history and looks
perfectly successful:

```text
    memories returned    : 2
      Northwind Foods: keeps getting logged out. Billing contact is accounts@northwind.exa  <-- NOT BLUE PEAK'S
      Blue Peak Logistics: keeps getting logged out after the SSO change. Contact is ops@b
```

Two results where one was correct, and the incorrect one is first. Nothing raised.
[5.3](../05-failure-lab/5.3-another-customers-memory.md) is that run in full, with the fix.

**A key that changes shape mid-life** is the third one, and it is the deploy that quietly erases a
year. Somebody renames the application from `sutra_desk` to `sutra-desk`, or moves `user_id` from an
internal username to an email address. Every existing memory is still in the store, under the old
key, unreachable forever. Sessions have the same property and Day 17 warned about it; memory makes it
worse, because a session nobody can reach is one conversation and a bucket nobody can reach is all of
them.

## In production

**What a professional writes instead of the teaching version.** `app_name` and `user_id` are not
literals anywhere in the application. They come from one function — something like
`memory_scope(request) -> tuple[str, str]` — that turns the authenticated caller into a bucket, and
every call site uses it. That gives you one place to review the privacy decision, one place to change
it, and one place to log it. A `user_id` derived inline from whatever object happens to be in scope is
how the leak in 5.3 gets written, and it is written by a competent person in a hurry.

**What degrades at scale or under concurrency.** Buckets are how a memory store shards, so their shape
decides both cost and blast radius. One bucket per customer gives you many small buckets: searches
stay fast, deleting a customer's data is deleting a key, and no query can ever cross a customer. One
bucket for the whole desk gives you a single enormous bucket that every search walks — with
`InMemoryMemoryService`, linearly — and no way to answer a deletion request at all. Under concurrency
the difference is starker still: every agent in the fleet contends on the same bucket's lock in the
shared design, and on nothing in the per-customer design.

**The failure mode that only appears with real traffic.** Cross-customer leakage is invisible in
testing because test fixtures usually have one customer. It appears the first week two customers have
similar problems, and it appears as an answer that is *helpful and slightly wrong* rather than as an
error. The person best placed to notice is the customer reading a reply about somebody else's
account.

**The review comment a senior engineer leaves:** *"`user_id=agent.name` — so every customer this agent
has ever handled shares one memory bucket, and a search on ticket 4610 can return Northwind's billing
contact. Decide whose memory this is and put the decision in one function. If the answer is 'the
agent', then filing has to redact customer identifiers before they go in, and I want to see that
too."*

**The interview question:** *"How do you keep one user's memory out of another user's session?"* An
honest answer: *"You do not, really — the store does it for you, and only as well as the key you give
it. In ADK memory is bucketed by `(app_name, user_id)`, and `user_id` is an unvalidated string, so
the isolation is exactly as good as the correctness of the value the application passes. The hard
part is not the mechanism, it is deciding who the user is. On a support desk the obvious answer is
the support agent, and it is the wrong one: it gives you one bucket per agent holding every customer
they have ever spoken to, and a keyword search will happily return the wrong company's details. I
would derive the bucket in one function from the authenticated caller, and I would test the negative
case — that a search under one customer never returns another's — because that test is the only thing
that fails when somebody changes the key."*
