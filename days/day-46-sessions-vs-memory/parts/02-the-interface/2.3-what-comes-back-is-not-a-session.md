# 2.3 — What comes back is not a session

## One-line answer

A search returns `MemoryEntry` objects — some content, and optionally who said it, when, an id and
some metadata — and it deliberately does **not** return the session those words came from, so the
ticket number, the state and the rest of the conversation are all gone unless they happened to be in
the text.

## The story

There is a shoebox on top of the almirah with about two hundred photographs in it.

You pull one out. Four people outside a house, squinting, one of them holding a plate. On the back,
in blue ink, somebody has written *Aug 1998*. You can see who is in it. You can read the date. That
is genuinely a lot.

What you cannot see is why everybody was there. Whether it was somebody's birthday or somebody's
funeral. What happened twenty minutes later. Who took the photograph, and whether they were arguing
with the person on the left. The afternoon had all of that in it, and the photograph has four people
and a plate.

A photograph is not the afternoon. It is a rectangle cut out of it, plus whatever somebody thought
to write on the back.

## The idea in plain language

`search_memory` returns a `SearchMemoryResponse`, which holds a list of `MemoryEntry`. That is a
different type from `Session`, and the difference is not cosmetic.

A `MemoryEntry` has exactly five fields, and four of them are optional:

| Field | Type | Optional? | What it holds |
| --- | --- | --- | --- |
| `content` | `types.Content` | **no** | the actual words, as parts, with a `role` |
| `author` | `str \| None` | yes | who said it, as ADK records authors |
| `timestamp` | `str \| None` | yes | when, as a string — *"Preferred format is ISO 8601"* |
| `id` | `str \| None` | yes | the store's own identifier for this memory |
| `custom_metadata` | `dict[str, Any]` | defaults to `{}` | whatever the store chose to attach |

Now the list of what is **not** there, which is longer and more important:

- **No session id.** You cannot get from a memory back to the conversation it came from.
- **No `app_name` or `user_id`.** You supplied those to the search; they do not come back.
- **No session state.** Everything Day 17 taught you to put in `state` — the ticket id, the severity,
  the root cause you carefully wrote to a named key — is **absent from every memory entry**. It was
  never in the events; it was beside them.
- **No neighbours.** The entry is one event. The reply that followed it, the tool result that
  explained it, the correction three turns later — all separate entries if they matched, and simply
  gone if they did not.
- **No score.** Nothing says how well this entry matched, so nothing distinguishes a perfect hit from
  an accidental one.

Put those together and you get the sentence that governs how you write to memory:

> **Whatever is not in the text of an event will not be in the memory.**

Which means a conversation that says *"I've marked this one high severity"* out loud keeps that fact,
and a conversation that quietly writes `state["severity"] = "high"` loses it completely — even though
the second version is the better-engineered one for every other purpose. That is a genuinely
uncomfortable tension, and Day 48 is where it gets resolved with a policy rather than a habit.

`timestamp` deserves one more sentence, because it is a trap in a helpful disguise. It is a **string**,
not a `float` and not a `datetime`. `InMemoryMemoryService` produces it with
`datetime.fromtimestamp(timestamp).isoformat()`, so it carries the machine's local time zone and no
offset marker. It is described in its own docstring as *"This string will be forwarded to LLM"* —
that is what it is for. It is not a field to sort on.

## Why Sutra needs it

Sutra's desk deals in ticket numbers. A memory that says *"the session cookie was set without the
SameSite flag"* and does not say **which ticket** is a memory a support agent cannot act on, because
the next question is always *"show me that one"*.

So the shape of what comes back drives a decision about what goes in. If the desk wants ticket
numbers in its memories, the ticket number has to be in the **text of an event** — which either means
the agent says it out loud in its replies, or means Sutra files something other than the raw
conversation. Both are real options; Day 48 chooses between them.

Nearer than that: section 4's policy rule 2 caps how many memories come back, and a cap is only
defensible if you know how big one is. An entry is one event's worth of text, which for Sutra's desk
runs to a couple of hundred characters — so a cap of three is roughly six hundred characters of
context and a cap of fifty is ten thousand.
[5.4](../05-failure-lab/5.4-the-store-that-outgrew-its-value.md) turns that into a table.

## The mechanism

File a session that has both state and events, then look at what a search hands back.

```python
# days/day-46-sessions-vs-memory/lab/entry.py
    session = await sessions.create_session(
        app_name=APP, user_id=USER, session_id="sess-a", state={"severity": "high"}
    )
    for i, (author, text) in enumerate(PAST_CASE):
        await sessions.append_event(session, said(author, text, float(i)))
    await memory.add_session_to_memory(session)

    print("the session that was filed:")
    print(f"    id            : {session.id}")
    print(f"    app_name      : {session.app_name}")
    print(f"    user_id       : {session.user_id}")
    print(f"    state         : {dict(session.state)}")
    print(f"    events        : {len(session.events)}")
```

**Line by line:**

- `state={"severity": "high"}` seeds the session with state at creation. This is the field the demo
  is really about: it is set, it is correct, and it is about to disappear.
- `add_session_to_memory(session)` is handed the **whole session object**, state included. That is
  worth dwelling on — the service *could* have kept the state. It chose not to, and the interface
  never promised it would.
- The five prints are the "before" picture, so the "after" can be read against something concrete
  rather than against your memory of what a session holds.

```python
# days/day-46-sessions-vs-memory/lab/entry.py (continued)
    found = await memory.search_memory(app_name=APP, user_id=USER, query="cookie")
    entry = found.memories[0]
    print(f"\nwhat came back: {type(entry).__name__}, {len(found.memories)} of them")
    print(f"    fields        : {sorted(MemoryEntry.model_fields)}")
    print(f"    author        : {entry.author!r}")
    print(f"    timestamp     : {entry.timestamp!r}  ({type(entry.timestamp).__name__})")
    print(f"    id            : {entry.id!r}")
    print(f"    custom_metadata: {entry.custom_metadata!r}")
    print(f"    content.role  : {entry.content.role!r}")
    text = "".join(p.text or "" for p in (entry.content.parts or []))
    print(f"    content text  : {text[:64]}...")
```

**Line by line:**

- `type(entry).__name__` prints `MemoryEntry`, which is the single most important line in the script.
  A reader who expected a `Session` finds out here.
- `MemoryEntry.model_fields` is pydantic's own record of the declared fields. Reading it from the
  class rather than listing the fields by hand means the transcript cannot drift out of date when
  ADK adds a field.
- `entry.timestamp!r` with `type(...).__name__` beside it prints both the value and its type,
  because the type is the surprise. A reader who assumed a number is told in the same line.
- `entry.id!r` prints `None`, which is not a bug — `InMemoryMemoryService` does not assign ids. A
  service that does would let you cite a memory by handle; this one does not, so "show me that
  memory again" is not an operation Sutra can offer today.
- `entry.content.role` is the **provider's** notion of who spoke, and `entry.author` is **ADK's**. Both
  are printed because they differ: `author` is `'desk'` and `role` is `'model'`. Code that filters
  memories by speaker has to pick one, and the right pick is `author`, because `role` collapses every
  agent in a multi-agent system into `model`.
- `"".join(p.text or "" for p in (entry.content.parts or []))` — `parts` may be `None` and any part's
  `text` may be `None`, because a part can carry inline data instead. The `or ""` on both is what
  stops this from being an `AttributeError` on the first non-text part. This exact expression appears
  in ADK's own `_memory_entry_utils.extract_text`, minus the `or ""`.

**`state : {'severity': 'high'}` went in. Nothing in the entry carries it.** The session was handed to
the service whole, and what came back is one event's content with three pieces of paperwork attached,
two of which are empty.

Note also `1 of them`, from a session that had `2` events. The query was `"cookie"`, and only the
desk's reply contains that word. So a memory search does not return conversations, it returns
*fragments of conversations*, and which fragments you get depends on which words you typed.

Verified on 2026-09-05 against `.venv/Lib/site-packages/google/adk/memory/memory_entry.py` (the five
fields, and the docstring *"This string will be forwarded to LLM. Preferred format is ISO 8601
format."*) and `.../memory/_utils.py`, whose whole content is
`datetime.fromtimestamp(timestamp).isoformat()`.

## When it breaks

The first break is reaching for a field that was never there:

```text
Traceback (most recent call last):
  File "...\demo.py", line 18, in <module>
    print(entry.session_id)
          ^^^^^^^^^^^^^^^^
AttributeError: 'MemoryEntry' object has no attribute 'session_id'
```

This one is fine, because it is loud. Pydantic models forbid unknown attributes, so the mistake
cannot survive a single run.

The second break is the same mistake made against a field that *does* exist and is `None`:

```text
Traceback (most recent call last):
  File "...\demo.py", line 22, in <module>
    print(entry.timestamp.year)
          ^^^^^^^^^^^^^^^^^^^^
AttributeError: 'str' object has no attribute 'year'
```

and its cousin, from code that assumed the store assigns ids:

```text
Traceback (most recent call last):
  File "...\demo.py", line 25, in <module>
    seen.add(entry.id.lower())
             ^^^^^^^^^^^^^^^^
AttributeError: 'NoneType' object has no attribute 'lower'
```

Both of these are the cost of silence from [2.2](2.2-the-silence-that-lets-you-swap.md), arriving on
schedule. Four of five fields are optional; treat all four as absent.

The third break has no traceback at all and it is the expensive one. Somebody writes a desk that
records everything important in session state — properly, exactly as Day 17 taught — and then files
sessions into memory. The store fills up. Searches return results. And every result is
conversational chatter, because all the *decisions* were written to state and none of them were ever
said out loud. The store is full and worthless, and there is no error anywhere, because nothing went
wrong. The system was engineered well for one purpose and that engineering removed the material the
other purpose needed.

## In production

**What a professional writes instead of the teaching version.** They stop filing raw sessions. A
production desk files a **written record** — a short structured statement of what the ticket was, what
the cause turned out to be and what fixed it — rather than the transcript that produced it, because
what comes back from a search has to stand alone and a transcript fragment does not. There are two
ways to do that with this interface, and both appear in ADK: use `add_memory` on a service that
supports it, which takes `MemoryEntry` objects directly, or append one summarising event to the
session before filing it. Day 48 is where Sutra chooses. What a professional does **not** do is hope
that the ticket number happened to be in the text.

**What degrades at scale or under concurrency.** Entry size is the whole cost of memory, and it is
decided by the size of an event. A desk whose agent replies in three paragraphs produces memories of
three paragraphs, and a search returning twenty of them puts six paragraphs of unrelated history in
front of a model that has to answer one question. The degradation is not an error, it is Day 19's
[3.2](../../../day-19-context-engineering-selection/parts/03-selection/3.2-facts-not-blobs.md):
send the finding, not the evidence. Under concurrency nothing here degrades at all — entries are
immutable values — which is worth knowing, because it means the expensive part of memory is what you
put in, not how many people read it.

**The review comment a senior engineer leaves:** *"Every memory we file is a raw conversation event,
and none of them mention the ticket number, because the ticket number lives in session state. So a
search result tells an agent that some customer once had a cookie problem and gives them no way to
look it up. Either say the ticket number in the reply or file a summary event that carries it."*

**The interview question:** *"What does a memory search actually return?"* An honest answer:
*"Fragments, not conversations. In ADK you get a list of `MemoryEntry` — the content of a single
event, plus an optional author, an optional timestamp as a string, an optional id and a metadata
dict. What you do not get is the session it came from, its id, or its state, and that last one caught
me out: I had done the right thing and put the ticket id and the severity in session state under
proper keys, and none of it was in a single memory. The lesson I took is that memory only ever holds
what was said, so if a fact has to survive the conversation it has to be written into the
conversation, or filed deliberately as its own record."*
