# 2.2 — The silence that lets you change the brain

## One-line answer

`BaseMemoryService` never says how matching works, and that omission is the most valuable thing
about it: the same calling code runs unchanged over a service that compares words and one that
compares meanings, and the quality of what comes back changes completely.

## The story

You turn the tap in your kitchen and water comes out. That is the whole promise of a tap.

What the tap does not tell you is where the water came from. Some days it is the municipal line. In
the dry months it is the borewell. On the worst day last summer it was a tanker that reversed into
the lane at six in the morning and pumped into the tank on the roof. Every one of those days, you
turned the same tap, in the same direction, and water came out.

What did change — and changed a lot — was the water. The tanker water left a ring in the kettle. The
borewell water was harder and the soap did not lather. Nobody had to re-plumb the flat for any of
this. The connection between the tank and the tap is the part that stayed still, and it stayed still
precisely because it never said anything about the source.

That is a good interface: it promises the thing you build on, and stays quiet about the thing you
will want to change.

## The idea in plain language

Look again at what `BaseMemoryService` actually says about `search_memory`, from its own docstring:

> *"Searches for sessions that match the query."*

And what it says about how "match" is decided: nothing. Not a word. There is no ranking function, no
similarity metric, no threshold, no result limit, no ordering guarantee, and no scores in the
response. The interface describes the *shape* of the operation — a query goes in, a list of entries
comes out — and stops.

That is not laziness. It is what makes the following possible:

- `InMemoryMemoryService` compares **words**. Its docstring says so: *"Uses keyword matching instead
  of semantic search."*
- `VertexAiRagMemoryService` compares **vectors** — the documentation says it *"stores conversations
  in Knowledge Engine and retrieves them by vector similarity"*.
- `VertexAiMemoryBankService` uses a **model** to extract durable facts and then searches those, with
  what the documentation calls *"advanced semantic search"*.

Three completely different machines, one calling convention. The agent that calls `load_memory` does
not change. The line in your runner that says `memory_service=...` changes, and that is all.

Two words for this, because they come up in reviews and interviews:

**Substitutability.** If two objects satisfy the same interface, code written against the interface
works with either. That is the whole point of writing against an interface rather than a class.

**The cost of silence.** Everything the interface refuses to promise is a thing that varies between
implementations, and code that *assumes* it will therefore break on some of them. The interface does
not promise that results are ranked, so do not write code that reads `memories[0]` as "the best
match". It does not promise a limit, so do not write code that assumes ten results. It does not
promise ordering, so do not write code that assumes the newest is last. Every one of those
assumptions is true for exactly one implementation and false for another.

The silence buys you the swap. It bills you for the assumptions.

## Why Sutra needs it

Sutra runs on `InMemoryMemoryService` for the whole of this phase, and by
[5.1](../05-failure-lab/5.1-the-past-that-matched-on-nothing.md) you will have watched it return the
wrong ticket with total confidence. The natural conclusion — *"memory does not work"* — is wrong. The
correct conclusion is *"this implementation of matching does not work for this problem"*, and the
reason that distinction is worth anything is that the interface lets you change one without changing
the other.

That is Day 49's whole opportunity: a local embedding index over the ticket archive, dropped in
behind `search_memory`, with the agent, the tools and the calling code untouched. Today you build
the seam. Day 49 slides something better through it.

And nearer than that, section 4's policy requires Sutra to cap every retrieval. A cap is implemented
as exactly this: a small class that satisfies `BaseMemoryService`, wraps another one, and changes
what comes back. You cannot write that wrapper without believing the substitution actually works, so
this part is where you prove it to yourself.

## The mechanism

One calling function, two services, four queries.

```python
# days/day-46-sessions-vs-memory/lab/swap.py
SAME_THING = {
    "signin": "logout",
    "login": "logout",
    "logout": "logout",
    "out": "logout",
    "session": "cookie",
    "cookie": "cookie",
    "redirect": "cookie",
}


def concepts(text: str) -> set[str]:
    """Map words to the handful of concepts this desk actually deals in."""
    return {SAME_THING[w.lower()] for w in re.findall(r"\w+", text) if w.lower() in SAME_THING}


class ConceptMemoryService(BaseMemoryService):
    """Same interface as InMemoryMemoryService. Matches concepts instead of words."""

    def __init__(self) -> None:
        self._events: list = []

    async def add_session_to_memory(self, session) -> None:
        self._events.extend(e for e in session.events if e.content and e.content.parts)

    async def search_memory(self, *, app_name: str, user_id: str, query: str):
        wanted = concepts(query)
        response = SearchMemoryResponse()
        for event in self._events:
            text = " ".join(p.text for p in event.content.parts if p.text)
            if wanted & concepts(text):
                response.memories.append(MemoryEntry(content=event.content, author=event.author))
        return response
```

**Line by line:**

- `SAME_THING` is a hand-written table mapping surface words to concepts. It is deliberately tiny and
  deliberately incomplete — it is a **strawman for a better retriever**, not a proposal. Watch what
  it fails to catch in the transcript below; that failure is the argument for embeddings.
- `concepts(text)` is a set comprehension with an `if` filter, so words not in the table simply
  vanish. That is the crucial behavioural difference from `InMemoryMemoryService`: unknown words
  contribute nothing rather than contributing a chance of an accidental match. It is why `"the
  customer"` cannot over-match here.
- `class ConceptMemoryService(BaseMemoryService)` implements exactly the two required methods from
  [2.1](2.1-two-promises-and-two-refusals.md) and neither optional one. It is a complete, legal
  memory service in eleven lines.
- `self._events.extend(e for e in session.events if e.content and e.content.parts)` filters out events
  with no content — tool-call bookkeeping, state deltas — because an event with nothing to read has
  nothing to match. `InMemoryMemoryService` applies the same filter, on the same line of its own
  source.
- `wanted & concepts(text)` is a set intersection, and a non-empty intersection is a match. This is
  the same *"any overlap"* rule `InMemoryMemoryService` uses; the only thing that changed is **what
  the overlap is computed over**. That is the point: the machinery is not more clever, the
  representation is.
- `MemoryEntry(content=event.content, author=event.author)` builds the return object by hand. Note
  what is *not* set: no `timestamp`, because this service does not bother. The interface permits it —
  every field on `MemoryEntry` except `content` is optional
  ([2.3](2.3-what-comes-back-is-not-a-session.md)) — and a caller that relied on `timestamp` being
  present would break on the swap. That is the cost of silence, in one line.

The calling code, which does not know which service it has:

```python
# days/day-46-sessions-vs-memory/lab/swap.py (continued)
async def ask(service: BaseMemoryService, session) -> None:
    await service.add_session_to_memory(session)
    print(f"service: {type(service).__name__}")
    for query in QUERIES:
        found = await service.search_memory(app_name=APP, user_id=USER, query=query)
        print(f"    {query!r:20} -> {len(found.memories)} memories")


async def main(*, synonyms: bool) -> None:
    ...
    await ask(ConceptMemoryService() if synonyms else InMemoryMemoryService(), session)
```

**Line by line:**

- `service: BaseMemoryService` is the type annotation that states the intent: this function is written
  against the **interface**, not against either class. Nothing in the body touches anything the
  interface does not declare.
- `type(service).__name__` prints which one it actually got, so the transcript identifies itself.
  Without this line the two runs' outputs would be indistinguishable at the top.
- `ConceptMemoryService() if synonyms else InMemoryMemoryService()` is the whole ablation: **one
  expression, one object, no other line in the file changes**. This is what substitutability looks
  like when it is real rather than claimed.

Run both:

```bash
cd days/day-46-sessions-vs-memory/lab
uv run python swap.py
uv run python swap.py --synonyms
```

**Line by line:**

- The first arm is the free implementation Sutra actually uses.
- `--synonyms` swaps the brain. **Zero model calls in either arm** — the concept table is a
  dictionary.

Measured on 2026-09-05:

```text
service: InMemoryMemoryService
    'logged out'         -> 1 memories
    'sign-in trouble'    -> 0 memories
    'login loop'         -> 0 memories
    'printer offline'    -> 0 memories
```

```text
service: ConceptMemoryService
    'logged out'         -> 1 memories
    'sign-in trouble'    -> 0 memories
    'login loop'         -> 1 memories
    'printer offline'    -> 0 memories
```

One row changed. `'login loop'` went from **0 to 1**, because `login` and `logout` are the same
concept in the table and are entirely different strings. The stored case does not contain the word
"login" anywhere, and the second service found it anyway.

`'printer offline'` correctly returns nothing in both arms, which matters: an improvement that
returns *more* for every query is not an improvement, it is a broken filter. The swap made one query
better and left the irrelevant one alone.

And **`'sign-in trouble'` still returns nothing, in both arms.** That is the honest result and it is
worth more than the row that worked. `re.findall(r"\w+", "sign-in trouble")` yields `sign`, `in` and
`trouble` — the hyphen splits the word — and `signin` is what is in the table. A hand-written synonym
list is finished exactly until the next spelling somebody uses, and that is not a bug in this table.
It is the reason the field stopped writing synonym tables.

Verified on 2026-09-05 against `.venv/Lib/site-packages/google/adk/memory/base_memory_service.py`
(the docstring quoted above) and `https://adk.dev/sessions/memory/`, which describes
`InMemoryMemoryService` as performing *"basic keyword matching"* and `VertexAiRagMemoryService` as
retrieving *"by vector similarity"*.

## When it breaks

The swap breaks when the calling code has quietly relied on something the interface never promised.
The most common one is treating position as ranking:

```python
best = found.memories[0]
return f"The closest past case is: {text_of(best)}"
```

**Line by line:**

- `found.memories[0]` is the first element of a list. It is **not** the best match, because nothing in
  the interface says the list is sorted by anything at all.
- With `InMemoryMemoryService` the order is the order events were stored in — insertion order of a
  dictionary, then list order within it. That is chronological-ish and completely unrelated to
  relevance. [5.1](../05-failure-lab/5.1-the-past-that-matched-on-nothing.md) is a run in which
  `memories[0]` is the wrong ticket and the right one is third.
- The word `closest` in the message is a claim the data cannot support, which is Day 21's
  [1.2](../../../day-21-errors-surface-not-swallow/parts/01-who-hears-it/1.2-an-error-is-a-fact.md)
  in a different costume: say what you know, not what would be convenient.

The second break is a missing optional field, and it arrives as an ugly string rather than an
exception:

```text
Time: None
desk: Root cause on 4521: the session cookie was set without the SameSite flag.
```

`preload_memory` builds its injected block from `memory.timestamp` and `memory.author`, and both are
`Optional`. A service that does not set `timestamp` — like `ConceptMemoryService` above — produces
memories that a formatter written for a different service renders with a literal `None` in them, or
that a `datetime.fromisoformat(entry.timestamp)` call turns into:

```text
TypeError: fromisoformat: argument must be str
```

The fix is not to demand that every service fill the field. It is to treat every field except
`content` as absent until proved otherwise.

The third break is the one that looks like success. Swap in a service with far better recall and
every query starts returning fifty entries instead of two. Nothing errors. The context bill triples,
and the model's answers get *worse*, because Day 19's
[3.3](../../../day-19-context-engineering-selection/parts/03-selection/3.3-position-is-not-presence.md)
is still true: a fact in the window is not a fact the model will use. Better matching without a cap
is a regression wearing an upgrade's clothes.

## In production

**What a professional writes instead of the teaching version.** They write the wrapper, not the
replacement. Improving retrieval almost never means editing a memory service — it means composing
one: a `Capped` that limits results, a `Logged` that records every query and count, a `Redacted` that
strips anything the store should not have kept. Each is thirty lines, each satisfies
`BaseMemoryService`, and they stack. The one rule is that a wrapper must be **at least as capable**
as what it wraps: forward the optional methods inside a `try/except NotImplementedError`, and never
drop a field from a `MemoryEntry` on the way through.

**What degrades at scale or under concurrency.** The swap that looks free in a lab is not free in a
system, and the reason is latency rather than correctness. Keyword matching over an in-process
dictionary answers in microseconds; a vector search over a managed corpus is a network call, and a network call has a slow tail — which is
what Day 44's [deadline section](../../../day-44-client-hardening/parts/02-the-deadline/2.1-two-clocks-not-one.md)
spent four parts on. Once retrieval crosses a network it needs a deadline and it needs a decision about what to do
when it times out — and the honest answer is usually "answer without the past and say so", not
"wait". Under concurrency, an in-process store serialises on a lock and a remote one serialises on a
connection pool; both are invisible until the day they are not.

**The review comment a senior engineer leaves:** *"You are reading `memories[0]` and calling it the
closest match. The interface returns an unordered list with no scores — that index is meaningless
today and will be differently meaningless when we change the backend. If you need a best match, rank
them yourself and say what you ranked on."*

**The interview question:** *"Why is the memory interface so thin?"* An honest answer: *"Because the
part that will change is the matching, and the part that must not change is the agent. In ADK the
interface promises a query in and a list of snippets out and says nothing about how matching is done
— so the same agent runs over keyword matching in development and semantic search in production. I
proved the swap to myself by writing an eleven-line memory service that matched concepts instead of
words: one query went from finding nothing to finding the right case, and not a single line of the
calling code changed. The flip side is that everything the interface does not promise is a landmine.
No ordering, no scores, no result limit, and every optional field on the entry genuinely optional. I
have seen code read `memories[0]` as the best match, which is true for zero of the implementations."*
