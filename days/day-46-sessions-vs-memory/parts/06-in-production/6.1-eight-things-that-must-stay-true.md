# 6.1 — Eight things that must stay true

## One-line answer

Everything this day taught about `MemoryService` is behaviour you observed rather than behaviour
anybody promised you, so it goes into a script of eight assertions that runs in six thousandths of a
second with no key, no network and no model — and that will go red on the upgrade that changes any
of it.

## The story

On the first Saturday of every month, the lights in the building go out for a moment.

It is deliberate. The man who looks after the generator switches the mains off at the panel,
everybody's fans stop, and a few seconds later the generator catches and the lights come back. People
grumble about it. The lift is out for a moment. Somebody's video call drops.

Two years ago it did not catch. The battery was flat, and the generator turned over twice and gave
up, and there was a long silence in the stairwell. He had it fixed by the afternoon.

That is the entire argument. The generator failed on a Saturday morning, in front of the one person
who could fix it, with everybody's lights already back on within a minute. The alternative was that
it failed for the first time in the middle of the night during a storm, with the water pump down and
nobody who knows where the battery is.

A test you run on purpose is a failure you have chosen the date of.

## The idea in plain language

Look back at what this day established. Every single one of these came from reading a source file or
running a script:

1. Nothing is in memory until code files it
   ([1.3](../01-the-line/1.3-nothing-is-filed-unless-you-file-it.md)).
2. A filed session is findable by a word that is in it
   ([1.2](../01-the-line/1.2-putting-versus-finding.md)).
3. The bucket is `(app_name, user_id)`, so another user sees nothing
   ([2.4](../02-the-interface/2.4-the-bucket-is-a-person.md)).
4. And another `app_name` under the same person sees nothing either
   ([2.4](../02-the-interface/2.4-the-bucket-is-a-person.md)).
5. What comes back is a `MemoryEntry`, not a `Session` — no state, no session identity
   ([2.3](../02-the-interface/2.3-what-comes-back-is-not-a-session.md)).
6. Filing the same session twice replaces rather than duplicates
   ([3.2](../03-three-wires/3.2-the-line-where-it-crosses.md)).
7. A word that is not in the text finds nothing, however close its meaning
   ([5.1](../05-failure-lab/5.1-the-past-that-matched-on-nothing.md)).
8. The store is per-process: a fresh service knows nothing
   ([5.2](../05-failure-lab/5.2-the-store-that-was-never-a-store.md)).

Not one of those is in a specification. `https://adk.dev/sessions/memory/` documents four methods and
three implementations; it does not promise you that re-filing replaces, or that `app_name` isolates,
or that the returned object carries no session id. Those are **observations of one version of one
implementation**, and Sutra's whole memory design rests on them.

There is a name for a test whose job is to pin down behaviour you depend on but were never promised:
a **characterization test**. It does not assert that the behaviour is correct. It asserts that the
behaviour is **what it was when you built on it**, so that the day it changes, the change arrives as
a red line in your own repository rather than as a customer complaint six weeks later.

Two things make this specific script worth writing rather than talking about.

**It costs nothing to run.** No key, no network, no model, no fixture file, no database. It is a
plain function and eight comparisons, and it finishes faster than reading its own output.

**It is the honest half of the day's gate.** [4.2](../04-the-choice/4.2-sutras-memory-policy.md)'s
`verdict.py` checks that Sutra's *own* module has the right shape — that decisions have names. This
one checks that the *framework underneath it* still behaves the way the module assumes. Those are two
different questions and they fail on two different days.

## Why Sutra needs it

Because three later days build directly on these eight statements and none of them re-checks any of
them.

**Day 47** swaps the session service for a database-backed one. Statement 8 is what makes that day
necessary, and statements 1, 2 and 6 are what must survive the swap — a persistent store that
duplicated on re-filing, or that changed the bucket, would break Sutra's memory without touching a
line of memory code. Running this script against the new wiring is how you find out.

**Day 48** writes the retention policy. Statement 6 — re-filing replaces — is the assumption that
makes *"file the session again after each turn"* a safe pattern rather than a duplication machine.
Statements 3 and 4 are the boundary any deletion rule is written against.

**Day 49** replaces the retriever. Statement 7 is the one Day 49 is *supposed* to break, and that is
the point of writing it down: when embeddings arrive, a search for `"sign-in trouble"` will match
`"logged out"`, this check will go red, and the red line is the evidence that the new retriever
actually does something. A check that only ever goes green is decoration.

And Principle 11 says evals are tests. A day that ends without a check that can go RED has not
finished.

## The mechanism

Eight assertions over a real `InMemoryMemoryService`, with the session faked by hand.

```python
# days/day-46-sessions-vs-memory/lab/checks.py
class Session:
    """The three fields add_session_to_memory actually reads."""

    def __init__(self, app_name: str, user_id: str, sid: str, events: list[Event]) -> None:
        self.app_name, self.user_id, self.id, self.events = app_name, user_id, sid, events
```

**Line by line:**

- This is a **local class called `Session`**, not ADK's. It is here because
  `add_session_to_memory(session)` reads exactly four attributes — `app_name`, `user_id`, `id` and
  `events` — and nothing else. Anything carrying those four is a session as far as the memory
  service is concerned.
- Writing it by hand rather than calling `InMemorySessionService.create_session` removes the second
  service from the test. If a future ADK release changes how sessions are created, this script still
  measures the memory service and only the memory service, which is what a characterization test of
  the memory service should do.
- It is also the proof of a claim [3.2](../03-three-wires/3.2-the-line-where-it-crosses.md) made: the
  crossing point between a session and memory is a **read of four fields**, not a privileged
  handshake. If you can see the four fields, you can see everything memory gets.
- `sid` rather than `id` as the parameter name, assigned to `self.id`, because `id` is a Python
  built-in and shadowing it in a parameter list is a habit worth not having.

```python
# days/day-46-sessions-vs-memory/lab/checks.py (continued)
    memory = InMemoryMemoryService()
    case = Session(APP, USER, "s1", [said("desk", "Ticket 4521: cookie flags. Fix KB-104.")])

    # 1 - nothing enters memory until code files it
    empty = await memory.search_memory(app_name=APP, user_id=USER, query="cookie")
    if empty.memories:
        out.append("1: an unfiled session was already searchable")

    await memory.add_session_to_memory(case)

    # 3 - the bucket is (app_name, user_id): another user sees nothing
    other = await memory.search_memory(app_name=APP, user_id=OTHER, query="cookie")
    if other.memories:
        out.append(f"3: user {OTHER} can read {USER}'s memories")

    # 5 - what comes back is a MemoryEntry, not a Session
    entry = hit.memories[0]
    if hasattr(entry, "state") or hasattr(entry, "id") and entry.id is not None:
        out.append("5: the entry carries session identity it should not")
```

**Line by line:**

- Assertion 1 runs **before** `add_session_to_memory`, and it is the only one that has to. It is
  written first for that reason: the order of the checks in this file is not decoration, it is a
  dependency.
- Every check appends a **sentence** to `out` rather than raising. That is deliberate: a raise stops
  at the first problem, and when a framework upgrade changes three behaviours at once you want all
  three named in one run, not one at a time across three runs.
- The sentences are written as **what went wrong**, not what was expected — `"user cust_b can read
  cust_a's memories"` is a finding a person can act on without opening this file.
- Assertion 5 reads as `hasattr(entry, "state") or (hasattr(entry, "id") and entry.id is not None)`,
  because `and` binds tighter than `or`. The two halves are different questions. `state` should not
  exist on a `MemoryEntry` **at all** — that is a `Session` field, and the entry is a photograph of
  one event rather than the conversation ([2.3](../02-the-interface/2.3-what-comes-back-is-not-a-session.md)).
  `id` **does** exist as a declared field on the model, defaulting to `None`, and the in-memory
  service never sets it — so the check is not "is the field absent" but "did anything put session
  identity in it". A managed service that filled `id` in with its own memory identifier would be
  fine; one that filled it in with the session id would not.
- `APP`, `USER` and `OTHER` are module constants — `"sutra_desk"`, `"cust_a"`, `"cust_b"` — so the
  two identity checks, 3 and 4, differ in exactly one argument each.

```python
# days/day-46-sessions-vs-memory/lab/checks.py (continued)
def main() -> int:
    started = time.perf_counter()
    problems = asyncio.run(findings())
    for problem in problems:
        print(f"  {problem}")
    print(f"findings: {len(problems)}  ({time.perf_counter() - started:.3f}s, 0 model calls)")
    return 1 if problems else 0


if __name__ == "__main__":
    sys.exit(main())
```

**Line by line:**

- The **length** of the findings list is the exit code and the **contents** are for a person. This is
  the same shape as [4.2](../04-the-choice/4.2-sutras-memory-policy.md)'s `verdict.py`, on purpose:
  two checks that report differently are two checks somebody has to learn twice.
- `time.perf_counter()` around the whole run prints the cost of the check in its own output. That
  number is an argument — a check this cheap has no excuse for not being in `./m check`, and printing
  it is how the argument gets made to the next person.
- `0 model calls` is printed as a literal because it is a property of the file rather than a
  measurement: there is no model in it. Saying so in the output means nobody has to read the source
  to know whether running it costs quota.
- `sys.exit(main())` makes the exit code the result, which is the only thing CI reads.

Run it:


**Line by line:**

- From the repository root or from `lab/` — this one is portable either way, because unlike the other
  scripts in this folder it imports nothing from `_desk.py`. It is self-contained on purpose: a check
  with fewer dependencies is a check that keeps working.
- `echo "exit: $?"` prints the exit code, which is the half a machine reads.

Verified on 2026-09-05 against the installed source: `add_session_to_memory` in
`.venv/Lib/site-packages/google/adk/memory/in_memory_memory_service.py` reads
`session.app_name`, `session.user_id`, `session.id` and `session.events` and writes
`self._session_events[user_key][session.id] = [...]` — an assignment, which is why re-filing replaces
rather than appends. `MemoryEntry` in `.../memory/memory_entry.py` declares exactly `content`,
`custom_metadata`, `id`, `author` and `timestamp`, all but the first optional — no `state`, no
`session_id`. Confirmed against `https://adk.dev/sessions/memory/`, read the same day, which
documents `add_session_to_memory` as taking *"a completed `Session`"* and `search_memory` as
returning *"relevant snippets or context"* — and which promises none of the eight behaviours above.

## When it breaks

The break this script exists for is **a version bump**, and there are three flavours of it.

**A behaviour changes and the script goes red.** The good case, and the only one it was written for.
The finding names the assertion and the fix is a decision: either adapt Sutra's code to the new
behaviour, or pin the old version, and either way somebody made the choice on purpose.

**A behaviour changes and the script goes red for a reason nobody understands.** More common than it
should be, because assertion sentences rot. `"5: the entry carries session identity it should not"`
means nothing to a person who has not read [2.3](../02-the-interface/2.3-what-comes-back-is-not-a-session.md).
The mitigation is the link, which is why each of the eight statements above names the part it came
from — a check is only as useful as the trail back to the reasoning.

**A behaviour changes and the script stays green.** The failure of the check itself, and the one to
take seriously. Every one of these eight assertions is written as *"the bad thing did not happen"*,
and a bad thing can stop happening for the wrong reason. Suppose an upgrade makes
`search_memory` raise on an empty bucket instead of returning an empty list: assertion 1 checks
`if empty.memories`, an exception is not a truthy list, and the script does not survive to report
anything at all — it dies with a traceback, which is loud and fine. But suppose instead that
`search_memory` starts returning `None` for a bucket it has never seen. `if empty.memories` on `None`
raises `AttributeError: 'NoneType' object has no attribute 'memories'`. Also loud. Now suppose it
returns a `SearchMemoryResponse` whose `memories` is always empty because a required argument was
silently renamed: **every assertion passes and the store is broken**. Assertion 2 catches exactly
that — it is the only one that requires something to be *present* — which is why a suite of negative
checks needs at least one positive one in it.

There is no traceback to show for the last case because the whole point is that there is not one.
That is what makes it the dangerous one.

## In production

**What a professional writes instead of the teaching version.** These eight become eight `pytest`
functions in `tests/test_memory_semantics.py`, one assertion each, named as sentences —
`test_refiling_a_session_replaces_rather_than_duplicates`,
`test_another_app_name_cannot_read_this_apps_memories`. Eight test names in the CI output is eight
statements of intent that a new joiner can read without opening a file; one script printing
`findings: 0` is one line that says nothing until it fails. The script in this lab is the teaching
form; the test file is the shipped form, and Day 30's
[lesson on testing](../../../day-30-skill-testing-and-versioning/LESSON.md) is where that distinction
was drawn.

They also mark the file with the version it characterises — a comment saying *"observed against
google-adk 2.7.1 on 2026-09-05"* — because the whole value of a characterization test is the pairing
of a behaviour with the version that had it. Without the version, a red line six months from now is a
mystery instead of a diff.

**What degrades at scale or under concurrency.** The check itself does not — it is single-threaded,
in-process and finishes in thousandths of a second. What degrades is the **relevance** of the check,
in one specific way: every assertion is written against `InMemoryMemoryService`, and the moment
production runs a managed service, seven of the eight are being verified against an implementation
nobody deploys. Statement 8 is the clearest example — *the store is per-process* is true of the
in-memory service and is exactly what a real store must not do. So the shipped version of this file
should be parameterised over whichever service the assembly function returns, with the assertions
that are genuinely implementation-specific marked as such.

**The failure mode that only appears with real traffic.** None, and that is the honest answer. This
check cannot see leaks, dilution, cost or a wrong past case; it sees eight structural facts. Reading
a green run as *"memory works"* is the failure mode, and it belongs to the reader rather than to the
code. Sections 4 and 5 of this day are what tell you whether memory works.

**The review comment a senior engineer leaves:** *"Good — but say which version you observed this
against, in a comment at the top, and add one assertion that something is actually **found**. Seven
of these eight pass if the store silently stops storing, and a suite of 'the bad thing did not
happen' checks is exactly the suite that goes green on an empty system."*

**The interview question:** *"How do you keep a framework upgrade from silently breaking you?"* An
honest answer: *"By writing down the behaviour you are relying on that nobody promised you. When I
built on ADK's memory service, my design depended on eight things — that nothing is stored until you
file it, that the bucket is app name plus user id and isolates both ways, that re-filing replaces
rather than duplicates, that what comes back is an entry with no session identity on it, that a
synonym matches nothing, and that the store dies with the process. None of that is in the
documentation; all of it came from reading the source and running experiments. So it became eight
assertions in a script with an exit code, no key, no network, no model, running in about six
thousandths of a second, and it goes into the same gate as the linter. The subtlety I would raise is
that seven of the eight are negative — they assert a bad thing did **not** happen — and a suite like
that passes on a completely dead system, so at least one has to assert something is found. And I
would date it and name the version it was observed against, because a characterization test without a
version is a mystery waiting to happen."*
