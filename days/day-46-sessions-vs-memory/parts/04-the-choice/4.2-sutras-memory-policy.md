# 4.2 — Sutra's memory policy

## One-line answer

Sutra chooses `load_memory` even though [4.1](4.1-pricing-both-in-tokens.md) measured it as the more
expensive option, because a retrieval you cannot see is a retrieval you cannot debug — and the policy
is written as five checks with an exit code so that the code cannot drift away from it in silence.

## The story

Somebody in the flat before you taped a strip of paper inside the fuse box.

It is not tidy. The handwriting is not good. But it says which switch is the geyser, which is the
kitchen plugs, and which is the one that trips when the pump and the iron are on together. There is
also a line that says *do not switch on 4 and 6 at the same time*, with no explanation, which took a
plumber to understand and is completely correct.

Whoever wrote it had to work all of that out once, in the dark, with a torch. The strip of paper is
what stops the next person having to do it again. And the reason it is inside the fuse box, rather
than in a drawer, is that it is only useful where the decision is made.

A decision somebody made carefully and then did not write down is a decision that will be re-made,
worse, by somebody in a hurry.

## The idea in plain language

A **policy** here is a small set of rules about how Sutra uses memory, each of which is a decision
that could have gone the other way, with the reason attached.

Sutra's memory policy, in five rules:

| # | Rule | What it says |
| --- | --- | --- |
| 1 | **The desk asks; it is not told** | The desk agent carries `load_memory`, not `preload_memory`. |
| 2 | **Every retrieval is capped** | `build_memory_service()` returns a service that returns at most `TOP_K` memories, and `TOP_K` is a constant. |
| 3 | **The store rides the runner** | The memory service is passed to `Runner`, never constructed inside an agent or a tool. |
| 4 | **A miss is reported, not interpreted** | A lookup that returns nothing produces *"nothing matched these words"*, never *"there is no past case"*. |
| 5 | **Lookups are budgeted** | `MAX_LOOKUPS_PER_INVOCATION` bounds how many times one question may search, and it is a named constant. |

Rule 1 is the one that needs defending, because [4.1](4.1-pricing-both-in-tokens.md) measured it as
the loser on both axes that a cost-conscious reader would look at.

**The case against rule 1, stated fairly.** At one lookup in ten turns, `load_memory` cost 3,130
tokens against `preload_memory`'s 1,898. At five in ten it cost 7,927 against the same 1,898, and
fifteen model requests against ten — three quarters of a twenty-request daily allowance for one
conversation. Preloading is cheaper in tokens at any realistic hit rate and cheaper in requests
always. That is not close, and it is not a rounding error.

**The case for rule 1, which Sutra accepts.** Four things, none of which is about cost:

1. **The lookup is an event.** Under `load_memory` the exact query and the exact result are in the
   session, in the logs, replayable. Under `preload_memory` neither is anywhere
   ([3.4](../03-three-wires/3.4-the-past-pushed-in-before-the-turn.md)). Three of the four failures
   in section 5 are diagnosed by reading the query.
2. **The failure is loud.** A missing memory service raises `ValueError: Memory service is not
   available.` under `load_memory` and produces `WARNING:root:Failed to preload memory for query: ...`
   under `preload_memory` — on the **root** logger, which a project configuring `google_adk` by name
   will not see. Principle 10 is not a preference.
3. **The query is chosen.** `preload_memory` sends `user_content.parts[0].text`, the user's raw
   message, greeting and all. Against a store that matches on any shared word, that is the difference
   between [5.1](../05-failure-lab/5.1-the-past-that-matched-on-nothing.md)'s four results and its
   one.
4. **Blast radius** (Principle 13). Preloading injects into every turn of every session, so one bad
   memory reaches every answer. `load_memory` injects only where the model asked, so the same bad
   memory reaches the turns that went looking for it.

**And the cost gap is smaller than it looks, once rule 2 is in force.** The 7,927 figure is
`load_memory` against an **uncapped** retriever returning everything that shares a word. Capped at
three, the same five-lookup run is still 7,927 — but the store can now grow to thirty cases, or three
thousand, without that number moving at all
([4.1](4.1-pricing-both-in-tokens.md), third table). The uncapped column is where the real money was,
and rule 2 takes it off the table for both policies.

**Where Sutra would use `preload_memory`, and says so.** An agent whose every answer needs history —
*"summarise this customer's last six months"* — should not be asking permission, and the audit trail
argument is weaker when there is only one thing it could have searched for. Rule 1 is about the desk,
not about the framework.

**Where the policy lives.** Not in this document. A rule that exists only in prose is a rule that
quietly stops being true, because nothing fails when somebody breaks it. So it is a script with an
exit code, checking the real module, and it is **red as shipped** because `sutra/memory/` does not
exist yet. Making it green is the build brief. That is the same instinct as Day 31's `./m check` and
Day 36's
[3.3](../../../day-36-long-jobs-and-tasks/parts/03-the-handle/3.3-sutras-handle-policy.md): a
standard you can run is a standard, and a standard you can only quote is a preference.

## Why Sutra needs it

Three later days each assume one of these rules and none of them will say so.

**Day 47** makes sessions durable. Rule 3 is what makes that a one-line change: because the store is
passed to the runner, swapping `InMemorySessionService` for `DatabaseSessionService` touches the
assembly function and nothing else.

**Day 48** writes what is worth remembering. Rule 2 is the precondition — a retention policy is
pointless if retrieval returns everything anyway — and rule 4 is the shape of the sentence Day 48's
policy has to produce when it declines to keep something.

**Day 49** replaces the retriever. Rules 1 and 2 are what make that safe: the seam is in one place,
the cap survives the swap, and the query is visible so you can tell whether the new retriever is
better on the queries you actually get.

## The mechanism

The policy, as five checks over the real module.

```python
# days/day-46-sessions-vs-memory/lab/verdict.py
RULES = """
1  the desk agent carries load_memory, not preload_memory
2  every retrieval is capped: build_memory_service returns a service with a stated k
3  the memory service is passed to the Runner, never constructed inside an agent
4  a lookup that returns nothing is reported, not silently treated as "no past case"
5  the number of memory lookups per invocation is bounded and the bound is a constant
""".strip()


def findings() -> list[str]:
    out: list[str] = []
    try:
        service = importlib.import_module("sutra.memory.service")
    except ModuleNotFoundError as err:
        return [f"rule 1-5: sutra.memory.service is not importable: {err}"]

    exported = dir(service)
    source = inspect.getsource(service)

    if "preload_memory" in source and "load_memory" not in source:
        out.append("rule 1: the module reaches for preload_memory and never for load_memory")
    if "build_memory_service" not in exported:
        out.append("rule 2: no build_memory_service - nothing states the retrieval cap")
    if "MEMORY_TOOLS" not in exported:
        out.append("rule 3: no MEMORY_TOOLS - the tool list is not stated in one place")
    if "TOP_K" not in exported:
        out.append("rule 4: no TOP_K constant - the cap is a literal somewhere instead")
    if "MAX_LOOKUPS_PER_INVOCATION" not in exported:
        out.append("rule 5: no MAX_LOOKUPS_PER_INVOCATION - the lookup budget is unbounded")
    return out
```

**Line by line:**

- `RULES` is printed by the script every run. A check that prints its own standard is a check somebody
  can act on without opening the file, and it means the policy and the code cannot separate.
- `importlib.import_module("sutra.memory.service")` imports by name rather than with a plain `import`
  statement, because the module does not exist yet and a top-level import would make the script
  itself unrunnable. The check has to be able to report the absence, not die of it.
- The early `return` on `ModuleNotFoundError` collapses all five findings into one while the module is
  missing. Five identical "not importable" lines would bury the signal; one says exactly what to do
  next.
- `dir(service)` lists what the module exports. This is a **structural** check, not a behavioural one:
  it asserts that the decisions have names, not that they are correct. That is a deliberate limit and
  it is stated in *When it breaks* below.
- `inspect.getsource(service)` reads the module's text so rule 1 can look for a symbol rather than
  call anything. Rule 1 is about which tool is wired, and wiring is visible in source.
- Rule 1's condition is `"preload_memory" in source and "load_memory" not in source` — deliberately
  narrow. It fires only when the module reaches for the pushed variant **and nothing else**, so a
  module that uses both (a desk agent and a summariser agent) is not flagged. A check that forbade
  `preload_memory` outright would be enforcing a slogan rather than the policy in rule 1.
- Every finding names the rule number and says what is missing in words. `rule 5: no
  MAX_LOOKUPS_PER_INVOCATION - the lookup budget is unbounded` is actionable; `False` is not.

```python
# days/day-46-sessions-vs-memory/lab/verdict.py (continued)
def main() -> int:
    print(RULES)
    print()
    problems = findings()
    for problem in problems:
        print(f"  {problem}")
    print(f"findings: {len(problems)}")
    return 1 if problems else 0


if __name__ == "__main__":
    sys.exit(main())
```

**Line by line:**

- `findings()` returns a list of sentences and `main` turns its **length** into the exit code. The
  count is what a machine reads and the sentences are what a person reads, and separating those two
  is why this is a check rather than a print statement.
- `sys.exit(main())` makes the exit code the result. `./m check` and CI care about nothing else.

Run it:

```bash

```

**Line by line:**

- From the repository root, not from `lab/`, because it imports `sutra.memory.service` and needs the
  project on the path. **Zero model calls.**

## When it breaks

The interesting break is the one where the check goes **green and the system is still wrong**. Every
one of these five rules is checked structurally — the symbol exists, the name is right — and none of
them is checked behaviourally.

Define `TOP_K = 10_000` and rule 2 passes. Define `MAX_LOOKUPS_PER_INVOCATION = 50` and rule 5 passes.
Define both and never read either anywhere in the codebase, and all five pass, and the system behaves
exactly as it did before you wrote the module.

That is not an argument against the check. It is the honest statement of what a structural check buys
you: it makes a decision **have a name**, which is what a reviewer needs in order to argue with it. A
constant of `10_000` is visible in a diff and a literal buried in a function is not. What it does not
buy you is correctness, and the version that does is a test in `tests/` that asserts a capped service
returns three memories from a store of thirty — which is the build brief, and which is Day 30's whole
lesson about the difference between a check and a test.

The second break is the policy drifting the other way: somebody with a legitimate need for
`preload_memory` — the summariser agent — adds it, rule 1's condition does not fire because
`load_memory` is also in the file, and the desk quietly gains automatic injection because the two
agents share a builder. The check cannot see that, and the guard is the review comment below rather
than the script.

The third is running it from the wrong directory:

```text
  rule 1-5: sutra.memory.service is not importable: No module named 'sutra'
```

Note `'sutra'`, not `'sutra.memory'`. Those two messages look almost the same and mean completely
different things: the first is "you are in `lab/`", the second is "the module has not been written".
Read the name in the message before you go looking for a bug.

## In production

**What a professional writes instead of the teaching version.** The five rules become five test
functions in `tests/`, with names that read as sentences — `test_retrieval_is_capped_at_top_k`,
`test_a_miss_does_not_claim_there_is_no_past_case` — running against the real module rather than
against `dir()`. They run in CI on every commit, so the policy is enforced by the thing that stops a
merge rather than by a script somebody remembers to run. And the two constants get a comment each
saying **what they were sized against**, because `TOP_K = 3` with no reason beside it is a number
somebody will double in a hurry.

**What degrades at scale or under concurrency.** The policy's numbers are the parts that age. `TOP_K`
is sized against how much context you can afford, which changes when the model changes.
`MAX_LOOKUPS_PER_INVOCATION` is sized against a request budget of twenty a day, which changes the
moment there is a paid tier. Both should be read from configuration in a real deployment, with the
default in code and the reason in a comment. What does **not** age is rules 1, 3 and 4, which are
about visibility and honesty rather than about numbers.

**The failure mode that only appears with real traffic.** Rule 5's bound is invisible until a model
starts retrying its own searches. A model that gets an unhelpful result will often try again with
different words — genuinely sensible behaviour — and one question becomes four lookups and five model
requests. In testing, with scripted models, that never happens.

**The review comment a senior engineer leaves:** *"`TOP_K = 3` with no comment. Three what — three
memories, or three conversations? And sized against what: the context budget, or the fact that three
looked nice in the demo? Put the reason in the constant's comment, because the next person to touch
this will be somebody who has just watched a search miss and whose first instinct will be to raise
it."*

**The interview question:** *"You have a memory retrieval tool and an automatic injection option.
Which do you pick?"* An honest answer: *"I measured both and then picked the more expensive one, so
the interesting part is why. On a ten-turn conversation with one lookup, the tool cost about 3,100
tokens and eleven model requests against 1,900 tokens and ten requests for automatic injection, and
the gap widened as the hit rate rose — because a tool result is written into the session and re-sent
on every later turn, while an injected block is transient. So injection wins on cost, clearly. I
still default to the tool, because the lookup is an event: the query and the result are in the
transcript, which is how you debug the three failures that actually happen — the wrong past case, the
leaked customer, and the store that grew. Automatic injection has neither in the transcript and
swallows retrieval errors with a warning on the root logger. The thing I would emphasise is that the
bigger win was not the choice at all: capping retrieval at three results took a thirty-item store's
injected block from ten thousand tokens to fourteen hundred, which is a factor of six against a
factor of two."*
