# 3.1 — The service rides the runner, not the agent

## One-line answer

`memory_service=` is an argument to `Runner`, not to `Agent` — so the agent stays portable and the
deployment decides which store stands behind it, and an agent carrying a memory tool with no service
on its runner raises `ValueError: Memory service is not available.` from inside the framework.

## The story

A friend of yours drives for a living.

He is the same driver whichever vehicle he is given. Same habits, same route knowledge, same way of
easing off before a speed breaker. On Monday it is the small hatchback and he can park it anywhere.
On Wednesday it is the seven-seater and he plans differently, because reversing out of that lane is
a job. On Friday the seven-seater is in the workshop and he has the hatchback again.

Nothing about *him* is changed by any of this. What changes is what he can carry, how far he can go
before filling up, and what happens on a bad road.

Now imagine the alternative: a driver who came welded into one particular car. You would have to
replace the person to change the vehicle, and every vehicle would need its own person. Nobody
organises it that way, and neither does ADK.

## The idea in plain language

There are two objects in an ADK application and it matters which one holds what.

An **`Agent`** is the description of behaviour: which model, what instruction, which tools. It says
nothing about where anything is stored. You can define one in a module, import it from a test, and
run it three different ways.

A **`Runner`** is the thing that actually runs an agent against real infrastructure. It holds the
services: `session_service` (required), and optionally `artifact_service`, `credential_service` and —
from today — `memory_service`.

The rule that follows is worth memorising because it applies to every service ADK has:

> **Capability goes on the agent. Storage goes on the runner.**

`load_memory` is a *capability* — a tool the model may call — so it goes in the agent's `tools=[...]`.
`InMemoryMemoryService` is *storage*, so it goes on the runner. The tool does not hold a reference to
the store; when it runs, it reaches through its `tool_context` to whatever the runner was given.

The mechanism behind that reach is worth one sentence of detail, because it is what produces the
error message in this part's title. `Context.search_memory` — the method both `ToolContext` and
`CallbackContext` inherit — does this:

> `if self._invocation_context.memory_service is None: raise ValueError('Memory service is not available.')`

So the check happens **at the moment the tool runs**, not at construction and not at startup. An
agent with a memory tool and a runner without a memory service is a perfectly valid object graph that
fails on first use.

That split is what makes three useful things possible:

1. **The same agent in three environments.** In-memory in a test, a real store in production, and
   nothing at all in a unit test that only cares about the instruction.
2. **Swapping the store without touching the agent** — [2.2](../02-the-interface/2.2-the-silence-that-lets-you-swap.md)'s
   whole argument, made concrete.
3. **Testing an agent with no store at all**, which is how you find out whether it degrades honestly
   when memory is unavailable.

## Why Sutra needs it

Sutra has been doing this since Day 8, with the session service, and Day 18 did it again with
[artifacts on a separate wire](../../../day-18-artifacts-that-survive/parts/01-not-a-state-key/1.3-a-separate-wire.md).
Memory is the third service on the same runner, wired the same way, and that repetition is the point:
once you see that all storage hangs off the runner, ADK's shape stops being a list of facts.

Concretely, this is what lets [Day 47](../../../day-47-persistent-sessions/LESSON.md) work at all.
Day 47 swaps `InMemorySessionService` for `DatabaseSessionService` and the desk agent does not change
by a character. If services lived on the agent, every persistence change would be an agent change,
and the "same agent, different deployment" story Sutra has been telling since Phase 1 would be a lie.

And it is why `sutra/memory/service.py` is a **builder** rather than a global. The build brief asks
for `build_memory_service()`, a function that returns a configured service, precisely so that the
choice happens at the point where the runner is assembled and nowhere else.

## The mechanism

The same agent, twice, against two runners that differ in one argument.

```python
# days/day-46-sessions-vs-memory/lab/wiring.py
    # The agent is identical in both arms. Not one character of it changes.
    model = ScriptedModel(
        turns=[calls("load_memory", query="logged out"), says("Yes - ticket 4521, cookie flags.")]
    )
    agent = Agent(name="desk", model=model, instruction="You are Sutra.", tools=[load_memory])

    runner = Runner(
        agent=agent,
        app_name=APP,
        session_service=sessions,
        memory_service=memory if with_memory else None,
    )
    print(f"agent.tools           : {[t.name for t in agent.tools]}")
    print(f"runner.memory_service : {type(runner.memory_service).__name__}")
```

**Line by line:**

- `ScriptedModel(turns=[...])` is this day's stand-in for a provider — a `BaseLlm` subclass that
  yields pre-written responses instead of calling anything. Day 19's
  [2.1](../../../day-19-context-engineering-selection/parts/02-anatomy/2.1-opening-the-envelope.md)
  introduced the trick; here it costs **zero quota** and makes the transcript reproducible. `_script.py`
  holds it, and 3.3 walks through it.
- `calls("load_memory", query="logged out")` scripts a turn in which the model asks for the tool. Real
  models decide this for themselves; scripting it removes the only source of nondeterminism in the
  demo, which is what lets the two arms be compared.
- `tools=[load_memory]` puts the **capability** on the agent. Note that `load_memory` here is not a
  function — ADK's `google.adk.tools` re-exports the *instance* `load_memory_tool` under the name
  `load_memory`, so what you are appending is a `LoadMemoryTool` object.
- `Runner(agent=..., app_name=..., session_service=..., memory_service=...)` — every argument is
  keyword-only; `Runner.__init__` starts with a bare `*`. There is no positional form, which is a
  small mercy given how many optional services it accepts.
- `memory_service=memory if with_memory else None` is the ablation, and `None` is the **default**.
  Leaving the argument out entirely produces exactly this arm, which is why the mistake is so easy to
  make.
- `type(runner.memory_service).__name__` prints `NoneType` in the failing arm. That is the one line
  that would have saved an hour, and it is the first thing to print when memory "does not work".

Run both arms:

```bash
cd days/day-46-sessions-vs-memory/lab
uv run python wiring.py
uv run python wiring.py --memory
```

**Line by line:**

- The first arm has the tool and no store, and it **exits non-zero**. That is intended; the traceback
  is the finding.
- `--memory` supplies the store. **Zero model calls in either arm** — the model is scripted.

and exposed through `tool_context.search_memory()` and `callback_context.search_memory()`"*.

## When it breaks

The break is the traceback above, and the useful thing about it is **where it is not**. Read the
frames from the bottom: `context.py` raised it, `load_memory_tool.py` called it, `function_tool.py`
called that, `functions.py` called that. Your code appears nowhere in the last five frames. The last
line of yours is `runner.run_async(...)`, and the mistake was three lines above it, in a constructor.

`ValueError: Memory service is not available.` means precisely one thing: `Runner` was built without
`memory_service=`. It does not mean the store is empty, the query was bad, or the tool is broken.

Two variants worth recognising.

**The one that does not raise.** Wire `preload_memory` instead of `load_memory` and the same missing
service produces *nothing at all*. `PreloadMemoryTool.process_llm_request` wraps its call in a bare
`try/except Exception` and calls `logging.warning`, so the run completes, the answer arrives without
any past, and the only evidence is a warning line — logged, moreover, through the root `logging`
module rather than the `google_adk` logger, so a project that configures its own loggers by name may
never see it at all. That asymmetry is a real argument in section 4 and it is the subject of
[3.4](3.4-the-past-pushed-in-before-the-turn.md).

**The one where the runner has the service and the agent has no tool.** Nothing raises and nothing
warns; the model simply has no way to reach the store, and answers from what it already knows. The
tell is a store that fills up and is never read. `grep` for `load_memory` in your agent definition
before you go looking anywhere else.

## In production

**What a professional writes instead of the teaching version.** One function assembles the runner —
services, agent, plugins — and every entry point calls it. Not because assembly is hard, but because
a runner built in three places will eventually be built three different ways, and the third one will
be missing a service. That function reads its choices from configuration: which session service,
which memory service, whether memory is on at all. And it **asserts at startup** rather than
discovering at runtime: if the agent's tool list contains a memory tool and `memory_service` is
`None`, raise there and then, with a message naming both, instead of letting a customer's request be
the thing that finds out.

**What degrades at scale or under concurrency.** The runner is constructed once and used by many
concurrent invocations, so the services on it are shared mutable state. `InMemoryMemoryService` is
explicitly thread-safe — it takes a lock on every read and write, and its own comment explains that
iterating the live store without one raises *"dictionary changed size during iteration"* — but
thread-safe is not the same as scalable. Every search takes the same lock, so retrieval across the
whole process is serialised, and the lock is held for the whole scan. That is invisible with a store
of ten entries and is a queue with a store of a hundred thousand.

**The failure mode that only appears with real traffic.** The runner is usually assembled from
environment variables, and the memory service is usually the last one added. A deployment that sets
`SESSION_BACKEND` and forgets `MEMORY_BACKEND` starts perfectly, serves every request that does not
need the past, and raises `ValueError` on the first one that does — which will be hours later, in
production, in a code path nobody was watching.

**The review comment a senior engineer leaves:** *"The agent lists `load_memory` and the runner is
built in `main()` with no `memory_service`. That is a `ValueError` inside a tool call, in front of a
customer, at some unpredictable future moment. Assemble the runner in one function, and assert there
that every memory tool on the agent has a service behind it."*

**The interview question:** *"Where does a memory service live in an ADK application, and why there?"*
An honest answer: *"On the runner, beside the session service, not on the agent. The agent carries
the capability — the `load_memory` tool — and reaches the store through its tool context at call
time. The reason is portability: the same agent object runs in a test with an in-memory store and in
production against a real one, so persistence choices never become agent changes. The cost of that
design is that the check is deferred: an agent with a memory tool and a runner with no memory service
is a valid object graph that raises `ValueError: Memory service is not available.` on first use. I
assert the pairing at startup for exactly that reason."*
