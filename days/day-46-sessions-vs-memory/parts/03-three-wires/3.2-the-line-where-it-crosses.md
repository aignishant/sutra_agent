# 3.2 — The line where it crosses

## One-line answer

`add_session_to_memory` is the single line where a conversation becomes something a later
conversation can find, it may be called more than once on the same session, and inside a run the
same act is `await callback_context.add_session_to_memory()`.

## The story

You have the rent money in an envelope in your bag. Four thousand rupees, counted twice.

You go to the bank, you take a slip from the pile, you fill in the account number and the amount, and
you join the queue. Right up until the cashier stamps it, the money is yours and yours only. It is in
the room. It is a metre from the counter. And your landlord cannot see a single rupee of it, because
nothing in the bank's records knows it exists.

Then the stamp comes down, and in that one second the money changes category. It stops being cash in
your bag and starts being a number in a system somebody else can read.

Two details about that moment are worth carrying into this part. First, nothing gradual happened —
there is no partial deposit. Second, if you go back an hour later with another two thousand, you fill
in another slip. Depositing twice into the same account is completely normal, and the bank does not
mind.

## The idea in plain language

`add_session_to_memory(session)` is the stamp.

Before it, a conversation exists only in the session service, reachable by its id. After it, its
events are in the memory store, reachable by search from any other conversation in the same bucket.

Three facts about the call, each of which changes how you use it.

**It takes the session, not a summary.** You hand over the `Session` object. The service reads
`app_name`, `user_id`, `id` and `events` off it — that is the whole input. You do not get to say
"file this bit"; that is what the optional `add_events_to_memory` is for
([2.1](../02-the-interface/2.1-two-promises-and-two-refusals.md)).

**It may be called repeatedly.** The interface docstring says so in one sentence: *"A session may be
added multiple times during its lifetime."* For `InMemoryMemoryService` that is not merely tolerated,
it is the intended usage, because the store is keyed by session id and a second call **replaces** the
first — the source assigns rather than appends:

> `self._session_events[user_key][session.id] = [event for event in session.events if ...]`

So filing a growing conversation ten times leaves you with one copy of the latest version, not ten
copies of ten versions. That is a property of *this* implementation. `add_events_to_memory`, by
contrast, appends and deduplicates on `event.id`, which is a different bargain.

**Inside a run there is a second way to do the same thing.** When code is running as part of an
invocation — a tool, a callback — it holds a context object, and `Context` provides
`await ctx.add_session_to_memory()` with no arguments. It reaches the memory service and the current
session through the invocation context. That is the idiom for filing *automatically at the end of an
agent's turn*, and it is what an `after_agent_callback` is for.

Which of the two you use is a real decision and it is about *where the decision to file lives*:

| | Filing from outside a run | Filing from a callback |
| --- | --- | --- |
| Who decides | your application code | the agent's own configuration |
| When | whenever you like — on ticket close, nightly | end of every agent turn, every time |
| What it can see | anything the application knows | only the invocation |
| Easy to forget | **yes** — it is a separate line somewhere else | no — it travels with the agent |

## Why Sutra needs it

This is the `TODO(me)` from [1.3](../01-the-line/1.3-nothing-is-filed-unless-you-file-it.md), turned
into two concrete mechanisms so it can actually be answered.

The desk's honest answer is probably neither of the two extremes. Filing on every agent turn is
cheap to write and fills the store with half-finished reasoning — every *"let me look that up"* turn
becomes a memory. Filing only when a human marks the ticket resolved gives a store of genuine
findings and requires a hook Sutra does not have yet. Day 48's `sutra/memory/policy.py` is where the
predicate goes, and this part is where you learn which line the predicate will guard.

The mechanism also matters for Day 47. `add_session_to_memory` reads `session.events`, so what gets
filed depends on what the session service handed you — and once sessions live in a database, "the
session object I am holding" and "the session as stored" can differ.
[Day 47](../../../day-47-persistent-sessions/LESSON.md) has a whole vocabulary for that; today the
relevant habit is to file the session you just fetched, not one you have been carrying around.

## The mechanism

First, filing from outside a run, twice on the same session.

```python
# days/day-46-sessions-vs-memory/lab/filing.py
async def by_hand() -> None:
    sessions = InMemorySessionService()
    session = await sessions.create_session(app_name=APP, user_id=USER, session_id="sess-a")

    for i, (author, text) in enumerate(PAST_CASE):
        await sessions.append_event(session, said(author, text, float(i)))
    print(f"session has {len(session.events)} events; filing now")
    await MEMORY.add_session_to_memory(session)
    print(f"    memory holds: {count()} events")

    await sessions.append_event(session, said("user", "One more thing: it also drops the cart.", 2))
    await sessions.append_event(session, said("desk", "Same cookie. Noted on 4521.", 3))
    print(f"\nconversation continued: {len(session.events)} events; filing the SAME session again")
    await MEMORY.add_session_to_memory(session)
    print(f"    memory holds: {count()} events  <- replaced, not appended")


def count() -> int:
    return sum(len(v) for b in MEMORY._session_events.values() for v in b.values())
```

**Line by line:**

- `MEMORY` is a module-level service here so that both halves of the script — the by-hand path and the
  callback path — write into the same store and can be compared. In `sutra/` it would be built by
  `build_memory_service()` and passed in; a module-level store is a lab convenience, and 3.1's
  production section says why.
- The first `add_session_to_memory(session)` files a two-event conversation. Note it happens *mid
  conversation*: nothing about the call requires the conversation to be over, and nothing about the
  session says whether it is.
- The two further `append_event` calls continue the same conversation. This is what makes the second
  filing interesting — the object being filed is the same object, and it now has more in it.
- The second `add_session_to_memory(session)` is the repeat the docstring permits. Watch the count in
  the transcript: it goes from 2 to 4, **not** from 2 to 6. Assignment, not append.
- `count()` reaches into `_session_events` — a private attribute, read here for the same reason as in
  [2.4](../02-the-interface/2.4-the-bucket-is-a-person.md): the public interface has no "how many
  things are in you" method, and the raw number is what the demonstration is about. The double
  comprehension flattens buckets, then sessions within buckets.

Now the same act, from inside a run:

```python
# days/day-46-sessions-vs-memory/lab/filing.py (continued)
async def file_it(callback_context: CallbackContext) -> None:
    """After the agent has answered, push this session into memory."""
    await callback_context.add_session_to_memory()
    print("    [after_agent_callback: session filed]")

    agent = Agent(
        name="desk", model=model, instruction="You are Sutra.", after_agent_callback=file_it
    )
    runner = Runner(agent=agent, app_name=APP, session_service=sessions, memory_service=MEMORY)
```

**Line by line:**

- `async def file_it(callback_context: CallbackContext)` — the parameter **must be named
  `callback_context`**. ADK invokes the callback as `callback(callback_context=callback_context)`, by
  keyword, so any other parameter name is a `TypeError` at run time. This is the one place where
  ADK's own docstring will lead you astray; see *When it breaks*.
- `await callback_context.add_session_to_memory()` takes **no arguments**. It reads the memory service
  and the current session off the invocation context, which is why it is the safe form: it cannot file
  the wrong session or into the wrong bucket, because it is not given the chance to.
- The callback returns `None`. An after-agent callback may return `types.Content` to replace the
  agent's answer; returning nothing means *"I only observed"*, which is what filing is.
- `after_agent_callback=file_it` puts the decision **on the agent**, so it travels with the agent into
  every deployment. That is the whole difference from the by-hand path, and it is why the agent
  definition is where a reviewer will look for it.
- `memory_service=MEMORY` on the runner is still required. The callback reaches for a service; it does
  not create one. Without it, `add_session_to_memory` raises
  `ValueError: Cannot add session to memory: memory service is not available.` — a *different* message
  from the search-side one in [3.1](3.1-the-service-rides-the-runner.md), which is useful, because the
  two tell you which half of the wiring is missing.

**2 then 4, not 2 then 6.** Re-filing a session is safe with this implementation, and that is the
fact that makes "file on every turn" a viable policy rather than a duplication bug.

In the callback arm, read the order of the last three lines. The agent's answer is produced
**first**, and the filing happens after — so what lands in memory includes the model's reply. Move
the same call to a `before_agent_callback` and you file the question without the answer, which is the
second failure in [1.3](../01-the-line/1.3-nothing-is-filed-unless-you-file-it.md).

`https://adk.dev/sessions/memory/`.

## When it breaks

The first break is one this document owes you a warning about, because the misleading source is
ADK's own. The docstring for `Context.add_session_to_memory` carries this example:

```text
Example:
    async def my_after_agent_callback(ctx: Context):
        # Save conversation to memory at the end of each interaction
        await ctx.add_session_to_memory()
```

Copy it and you get:

```text
  File "...\google\adk\agents\base_agent.py", line 555, in _handle_after_agent_callback
    result = callback(callback_context=callback_context)
             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
TypeError: file_it() got an unexpected keyword argument 'callback_context'
```

The parameter in the documented example is called `ctx`; the call site passes `callback_context=`.
The example does not run. Name the parameter `callback_context` and it does. This is Principle 8 in
its least glamorous form: the installed source is the specification, and it disagreed with the
docstring three lines above it.

Worse, look at where that `TypeError` surfaces. It comes out of `_handle_after_agent_callback`, which
runs **after** the agent has produced its answer — so in the transcript the user's reply is printed
and *then* the run collapses, and the exception propagates all the way out of `runner.run_async`.
A user-visible failure caused by a bookkeeping step that had nothing to do with the answer.

The second break is filing a session you are no longer holding correctly:

```python
session = await sessions.get_session(app_name=APP, user_id=USER, session_id=sid)
await runner.run_async(...)  # the runner appends events to the STORED session
await memory.add_session_to_memory(session)  # ...and this files the copy you fetched earlier
```

**Line by line:**

- `get_session(...)` returns a session object as it was at that moment.
- `runner.run_async(...)` appends events through the session **service**. Whether your earlier object
  sees them depends entirely on the implementation — with `InMemorySessionService` you may be holding
  the same object and see them; with a database-backed service you are holding a snapshot and will
  not. Day 17's
  [6.1](../../../day-17-state-scopes-and-lifetimes/parts/06-failure-lab/6.1-the-write-that-was-never-written.md)
  is the same trap on the state side.
- `add_session_to_memory(session)` then files whatever that object contains, which may be the
  conversation as it was before the turn. No error. A store full of questions with no answers.

The fix is to re-fetch immediately before filing, or to use the callback form, which cannot make this
mistake.

The third is filing on every turn against a store that is not `InMemoryMemoryService`. Replacement is
free in a dictionary and is a full rewrite over a network. A forty-turn conversation filed forty
times sends the whole growing transcript forty times, and the work is quadratic in the length of the
conversation. Nothing warns; the bill does.

## In production

**What a professional writes instead of the teaching version.** The `after_agent_callback` form, with
a predicate in front of it and a log line after it:

```python
async def file_if_worth_keeping(callback_context: CallbackContext) -> None:
    """File this conversation into memory when the policy says it is worth keeping."""
    if not worth_keeping(callback_context.state):
        return
    await callback_context.add_session_to_memory()
    log.info("memory.filed", extra={"session": callback_context._invocation_context.session.id})
```

**Line by line:**

- `worth_keeping(...)` is Day 48's `sutra/memory/policy.py`. It is a separate function so the decision
  is testable without a runner, and so a reviewer can read the policy without reading the plumbing.
- The early `return` means "not filed" is a normal outcome rather than an error. Most turns of most
  conversations are not worth keeping.
- The log line is not optional. *"Was this conversation ever filed?"* is the first question anybody
  asks when memory misses, and nothing else in the system can answer it.
- Reaching `_invocation_context` for the session id is uncomfortable and is the reason a production
  version usually carries the id in state instead. It is flagged here rather than hidden, because a
  private attribute in a code sample should always be a sentence rather than a silence.

**What degrades at scale or under concurrency.** Filing is a write, and every agent in the fleet does
it at the end of every turn. Two properties decide whether that is fine. First, whether the store
replaces or appends: replacement makes repeat filing idempotent, appending makes it grow. Second,
whether the write is on the response path: filing synchronously adds its latency to every answer,
and filing asynchronously opens a window in which the process can die between answering and storing.
The honest middle is to file synchronously and keep the payload small — which means filing a summary
rather than a transcript, which is [2.3](../02-the-interface/2.3-what-comes-back-is-not-a-session.md)
arriving as an operational requirement rather than a design opinion.

**The review comment a senior engineer leaves:** *"The filing call is in the request handler, after
`run_async`, using a session object fetched before it. Once sessions are in Postgres that object is a
stale snapshot and we will file the question without the answer, silently. Move it into the
after-agent callback, which reads the live session off the invocation context and cannot get this
wrong."*

**The interview question:** *"How does a conversation get into long-term memory?"* An honest answer:
*"One explicit call — in ADK, `add_session_to_memory`, either on the service with a session, or
argument-free on the callback context inside a run. I default to the second, in an after-agent
callback, for two reasons: it reads the live session rather than a snapshot I fetched earlier, and it
lives on the agent so it travels with it into every deployment instead of being a line somebody has to
remember in each entry point. The subtlety worth knowing is that the same session may be filed many
times — the interface says so explicitly — and whether that duplicates depends on the implementation.
The in-memory one replaces by session id, so re-filing is idempotent, but I would not assume that of
a store I did not read the source of."*
