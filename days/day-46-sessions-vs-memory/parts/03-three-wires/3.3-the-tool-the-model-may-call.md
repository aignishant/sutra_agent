# 3.3 — The tool the model may call

## One-line answer

`load_memory` is an ordinary tool the model decides to call, with a query it writes itself — so
nothing is retrieved unless the model asks, the ask is visible in the event stream, and the tool
quietly adds a paragraph to your system instruction on every request whether it is used or not.

## The story

You take the car in because there is a rattle at low speed.

The mechanic listens to you describe it, walks round the car, and then does one of two things. Some
mechanics get straight under it. This one goes back to the counter, pulls out the service book, and
turns to the last three visits. Twenty seconds later he says: *"the front subframe bolts were done in
March — I want to check those first."*

He did not have to do that. Nothing forced him. He looked because the noise you described made him
think the history might be worth a look, and if you had come in with a flat tyre he would not have
bothered.

Two things about that. It cost twenty seconds, and only on the visits where it was worth it. And you
saw him do it — you watched him take the book out, you know that is where the subframe idea came
from, and if he turns out to be wrong you know which page to argue with.

## The idea in plain language

`load_memory` is a **tool**, in exactly the sense Day 4 built by hand: a function the model can be
told about, which it may choose to call, whose result comes back into the conversation as a tool
result before the model answers.

It takes one argument, `query`, a string. Its declaration is three lines of JSON schema:

> `{'type': 'object', 'properties': {'query': {'type': 'string'}}, 'required': ['query']}`

When the model calls it, the tool does one thing:

> `search_memory_response = await tool_context.search_memory(query)`

and wraps the result in a `LoadMemoryResponse`. That is the entire implementation. It is a thin lid
over `search_memory`, and everything [2.2](../02-the-interface/2.2-the-silence-that-lets-you-swap.md)
said about matching applies unchanged.

Three consequences.

**The model writes the query.** Not you, and not the framework. Whatever the model decides is a good
search string is the string that reaches the store. That is a genuine advantage — the model can
narrow a rambling user message down to *"logged out cookie"* — and a genuine risk, because you cannot
predict it and it will not be in your tests.

**The lookup is an event.** A `load_memory` call produces a function-call event and a
function-response event in the session, the same as any other tool. So it appears in the transcript,
in the logs Day 22 set up, and in anything replaying the session. When somebody asks *"why did the
desk mention ticket 4521?"*, the answer is in the record.

**It costs a standing charge.** Two of them, in fact, and this is the part people miss.
`LoadMemoryTool.process_llm_request` appends this to the system instruction, on **every** request:

> *"You have memory. You can use it to answer questions. If any questions need you to look up the
> memory, you should call load_memory function with a query."*

Plus the tool declaration itself, which like every tool declaration is sent on every call — Day 19's
[2.3](../../../day-19-context-engineering-selection/parts/02-anatomy/2.3-the-menu-costs-more-than-the-handbook.md)
measured six small tools at 1,855 characters against a 145-character instruction. So `load_memory` is
not free when unused. It is *cheap* when unused, which is a different claim, and
[4.1](../04-the-choice/4.1-pricing-both-in-tokens.md) puts a number on it.

There is a fourth consequence that only shows up when the model declines to call it: **nothing
happens and nothing says so**. A model that does not think to search produces a confident answer from
nothing, and the transcript contains no `load_memory` line to explain the absence. That is not a
failure of the tool; it is the shape of the design.

## Why Sutra needs it

Sutra's desk answers questions where the past sometimes matters and usually does not. *"What is the
status of 4610?"* needs the ticket system.  *"Have we seen this before?"* needs the archive. A desk
that consults the archive on every question is spending context on the majority of turns that do not
need it, and [4.1](../04-the-choice/4.1-pricing-both-in-tokens.md) measures exactly that.

More importantly, this is the option that leaves an audit trail. Section 5 has four failures in it,
and three of them — the wrong past case, the leaked customer, the store that grew — are diagnosed by
reading **what was searched for and what came back**. Under `load_memory` both are events in the
session. Under `preload_memory` neither is. That asymmetry, not the token count, is what decides
Sutra's default in [4.2](../04-the-choice/4.2-sutras-memory-policy.md).

## The mechanism

The scripted model this day uses, first, because everything in section 3 rests on it.

```python
# days/day-46-sessions-vs-memory/lab/_script.py
class ScriptedModel(BaseLlm):
    """Yields pre-written responses in order, and keeps every request it was sent."""

    model: str = "scripted"
    turns: list[LlmResponse] = []
    seen: list[LlmRequest] = []

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        self.seen.append(llm_request)
        yield self.turns.pop(0)


def calls(name: str, **args: object) -> LlmResponse:
    """A scripted turn in which the model asks for a tool."""
    part = types.Part(function_call=types.FunctionCall(name=name, args=dict(args)))
    return LlmResponse(content=types.Content(role="model", parts=[part]))
```

**Line by line:**

- `class ScriptedModel(BaseLlm)` — `BaseLlm` is a pydantic model, so `model`, `turns` and `seen` are
  **declared fields** rather than attributes set in `__init__`. Assigning them in an `__init__` would
  fight pydantic; declaring them lets you write `ScriptedModel(turns=[...])`.
- `model: str = "scripted"` satisfies the one field `BaseLlm` requires. It is the string a real
  agent would set to `gemini-3.7-flash`. Nothing here reaches a provider, so the value is a label.
- `seen: list[LlmRequest] = []` records every request the agent built. That list is the measuring
  instrument for [4.1](../04-the-choice/4.1-pricing-both-in-tokens.md) — you cannot price a memory
  policy without seeing what actually went out.
- `generate_content_async(self, llm_request, stream=False)` is the one abstract method, and the
  signature must match exactly. It is an **async generator**, so the body must `yield`; writing
  `return` gives you `TypeError: object LlmResponse can't be used in 'await' expression` at the first
  turn.
- `self.turns.pop(0)` takes the next scripted response and removes it, so a script that runs out
  raises `IndexError: pop from empty list` — which is the honest failure for *"the agent made more
  calls than I expected"*, and much better than silently repeating the last one.
- `calls(name, **args)` builds a response whose content is a `function_call` part rather than text.
  That is precisely what a real model emits when it decides to use a tool; ADK's flow does not care
  that it came from a script.

Now the demonstration:

```python
# days/day-46-sessions-vs-memory/lab/asked.py
    turns = [calls("load_memory", query="logged out"), says(ANSWER)] if asks else [says(GUESS)]
    model = ScriptedModel(turns=turns)
    agent = Agent(name="desk", model=model, instruction="You are Sutra.", tools=[load_memory])
    runner = Runner(agent=agent, app_name=APP, session_service=sessions, memory_service=memory)

    await sessions.create_session(app_name=APP, user_id=USER, session_id="sess-b")
    message = types.Content(role="user", parts=[types.Part(text=TODAY)])
    print("event stream for session B:")
    async for event in runner.run_async(user_id=USER, session_id="sess-b", new_message=message):
        for call in event.get_function_calls():
            print(f"    TOOL CALL   {call.name}({call.args})")
        for response in event.get_function_responses():
            found = response.response["result"].memories
            print(f"    TOOL RESULT {len(found)} memories")
        if event.is_final_response() and event.content and event.content.parts:
            print("    FINAL      ", "".join(p.text or "" for p in event.content.parts))
```

**Line by line:**

- The `turns` ternary is the ablation. The `asks` arm scripts two model turns — the tool call, then
  the answer. The other arm scripts one: the model answers immediately, without looking. **The tool is
  attached to the agent in both arms**, which is what makes the comparison fair: the difference is
  the model's decision, not the wiring.
- `tools=[load_memory]` — as in 3.1, this is the exported instance, not a function.
- `event.get_function_calls()` and `event.get_function_responses()` are helpers on `Event` that pull
  the function-call and function-response parts out of the content. Reading them here rather than
  digging into `event.content.parts` is what a real observability hook does.
- `response.response["result"].memories` — the tool's return value is wrapped by ADK under the key
  `"result"`, and what is under it is a `LoadMemoryResponse` object with a `memories` list. That
  double indirection is worth knowing, because a naive `response.response["memories"]` raises
  `KeyError: 'memories'`.
- `event.is_final_response()` is true only for the event carrying the agent's finished answer, so
  this loop prints exactly one `FINAL` line per turn regardless of how many tool calls happened.

And the measurement that makes the standing charge visible:

```python
# days/day-46-sessions-vs-memory/lab/asked.py (continued)
    print(f"\nmodel requests made: {len(model.seen)}")
    for n, request in enumerate(model.seen):
        lines = render(request)
        print(f"    request {n}: {len(lines)} content items, {sum(map(len, lines))} characters")
        for line in lines:
            print(f"        {line[:88]}")
    instruction = model.seen[0].config.system_instruction
    print(f"\nsystem instruction sent ({len(str(instruction))} characters):")
    print(f"    {str(instruction)[:300]}")
```

**Line by line:**

- `len(model.seen)` is the number of times the agent went to the model in one turn. That number is
  what the free tier rations — Day 24's
  [1.3](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.3-the-unit-that-gets-rationed.md)
  established that the quota metric is `generate_content_free_tier_requests`, not tokens — so a
  policy that turns one question into two requests has spent 10% of a day's allowance of twenty.
- `render(request)` flattens each request's contents into readable lines; it lives in `_script.py`
  and prints `[call load_memory]` and `[result of load_memory]` rather than dumping the objects.
- `request.config.system_instruction` is where `LoadMemoryTool` appended its paragraph. Printing its
  **length** rather than eyeballing it is what makes the comparison with
  [3.4](3.4-the-past-pushed-in-before-the-turn.md) meaningful: 219 characters against 63.

Four things in those two blocks.

**Two model requests against one.** The tool call is not free: a turn that consults memory goes to the
model twice, once to decide and once to answer. Out of a twenty-request daily allowance that is a
real number, not a rounding error.

**The lookup is in the transcript.** `TOOL CALL load_memory({'query': 'logged out'})` — the exact
string that was searched for, recorded, in order, in the session. Compare that with 3.4.

**The system instruction is 219 characters in both arms.** The paragraph is appended whether or not
the tool is called, because `process_llm_request` runs when the request is built, not when the tool
runs. **You pay the standing charge on every turn of every session, forever.**

**And the second arm is confidently wrong.** *"No past case on file"* — with the case sitting in the
store, one search away. Nothing in the run is broken. The model simply did not ask, and there is no
line anywhere saying so.

Verified on 2026-09-05 against `.venv/Lib/site-packages/google/adk/tools/load_memory_tool.py` (the
one-line body, the JSON-schema declaration, and the appended instruction quoted verbatim) and
`https://adk.dev/sessions/memory/`, which describes `load_memory` as *"Retrieves memory when your
agent decides it would be helpful"*.

## When it breaks

The first break is the one in the transcript above, and it has no error text at all: **the model does
not call the tool.** You get an answer, it is fluent, and it is made of nothing. The tell is an event
stream with no `load_memory` line in a turn where you expected one.

The causes, in the order worth checking:

1. The instruction does not tell the model that past cases exist or matter. ADK's appended paragraph
   is generic; a desk-specific line like *"When a user asks whether something has happened before,
   always call `load_memory` first"* is worth more than any amount of tuning.
2. The tool is not on the agent at all — `grep` first, before theorising.
3. The model is small and the tool list is long. Day 19's
   [2.3](../../../day-19-context-engineering-selection/parts/02-anatomy/2.3-the-menu-costs-more-than-the-handbook.md)
   noted that every tool costs the model a decision as well as tokens; the eleventh tool is not
   chosen as reliably as the second.

The second break is the tool being called and the query being wrong. This one *is* visible, and it is
the whole reason to prefer visibility:

```text
    TOOL CALL   load_memory({'query': 'Any past case where a user keeps getting logged out?'})
    TOOL RESULT 4 memories
```

A model that passes the user's whole sentence through as the query hands the store a bag of words
including `any`, `case`, `a`, `user` and `where` — and with `InMemoryMemoryService`'s *any shared
word* rule, that matches nearly everything.
[5.1](../05-failure-lab/5.1-the-past-that-matched-on-nothing.md) is that failure at archive scale.
The fix is in the instruction, and you can only write it because you can see the query.

The third break is the shape of the response tripping up a caller:

```text
Traceback (most recent call last):
  File "...\demo.py", line 31, in <module>
    print(len(response.response["memories"]))
              ~~~~~~~~~~~~~~~~~^^^^^^^^^^^^
KeyError: 'memories'
```

The tool's return value is under `"result"`, and the object there is a `LoadMemoryResponse`. Only
inside it is there a `memories` list.

## In production

**What a professional writes instead of the teaching version.** Two additions to the agent, neither of
them large. First, an instruction sentence that says *when* to search, in the desk's own vocabulary,
because the framework's generic paragraph does not know what a past case is. Second, a **budget**: a
constant naming the maximum number of memory lookups in one invocation, enforced in a callback, so a
model that decides to search four times with four rewordings cannot turn one question into five
requests. Section 4's policy makes that constant `MAX_LOOKUPS_PER_INVOCATION`, and the reason it is a
named constant rather than a literal is Day 44's
[3.4](../../../day-44-client-hardening/parts/03-backing-off/3.4-with-retries.md): *attempts are a
budget on the request, not a number in a function*.

**What degrades at scale or under concurrency.** The extra model request is the cost that scales
worst, because it scales with traffic rather than with the store. A desk answering ten thousand
questions a day, a fifth of which trigger a lookup, makes twelve thousand model requests instead of
ten thousand — twenty per cent more latency-bearing calls, twenty per cent more rate-limit pressure,
and a p99 that now includes two round trips instead of one. The store-side cost, meanwhile, is a
search that is not on the model's critical path more than once per turn. If you are going to be
surprised by a bill, it will be the requests.

**The failure mode that only appears with real traffic.** The model's query is unpredictable, so the
distribution of queries you see in production is nothing like the three you tested. Log every query
string. Within a week you will find that a tenth of them are the user's entire message pasted through
unchanged, and that is a prompt fix you would never have guessed at.

**The review comment a senior engineer leaves:** *"There is no cap on `load_memory` calls per turn. A
model that gets an unhelpful result will try again with different words — that is the behaviour we
want, right up until it is five extra requests against a twenty-a-day quota. Put a counter in a
callback and make the second refusal say why."*

**The interview question:** *"How does an agent decide when to look something up in memory?"* An
honest answer: *"With `load_memory` it is genuinely the model's decision — the tool takes a query
string the model writes itself, and if the model does not think to call it, nothing is retrieved and
nothing tells you. That is the trade I take on purpose, because the call is an event: I can see what
was searched for and what came back, in the session, in the logs, replayable. The things I would flag
are that a lookup costs an extra model request, which matters a lot on a rationed free tier, and that
the tool is not free when unused — ADK appends a paragraph to your system instruction on every
request whether the tool fires or not. I measured that at 219 characters of instruction against 63
without it."*
