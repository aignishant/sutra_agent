# 3.4 — The past pushed in before the turn

## One-line answer

`preload_memory` searches the store with the user's raw message and injects the results into the
request **before every turn**, so nothing depends on the model deciding to look — and nothing appears
in the transcript, nothing is logged that you will see, and a search that raises is swallowed.

## The story

The newspaper arrives under your door at half past six every morning.

Nobody asks whether you want today's. There is no decision and no step — you open the door and it is
there. On the mornings you have twenty minutes and a cup of tea, that is a very good arrangement. On
the mornings you leave at seven, the paper goes onto the pile by the shoe rack, unread, and at the
end of the month you pay for all thirty of them.

The other thing about a paper under the door is that you never see it arrive. If it does not come one
morning, you do not get a note. You look at the empty patch of floor and you are not sure whether the
boy was ill, or the bill lapsed, or it is a holiday. Something that happens invisibly is something
whose absence is also invisible.

## The idea in plain language

`preload_memory` is **not a tool the model calls**. It is on the agent's `tools=[...]` list, and it
has a name and a description, and neither is ever used — the class's own docstring says *"This tool
will be automatically executed for each llm_request, and it won't be called by the model."*

What it actually is: a hook. `PreloadMemoryTool` implements `process_llm_request`, which ADK runs
while assembling every request to the model, and inside it the tool does four things.

1. Takes `tool_context.user_content.parts[0].text` — **the first text part of the user's message**, raw
   and entire — as the query.
2. Calls `search_memory` with it.
3. Formats every returned memory as `Time: <timestamp>` and `<author>: <text>`, wraps them in a
   `<PAST_CONVERSATIONS>` block with two lines of preamble.
4. Inserts that block into the request as a **transient** user message, immediately before the real
   one.

*Transient* is the word that decides most of this part's economics. The block is put into the
outgoing request and is **not** written into the session, so it does not accumulate: turn five is not
carrying turns one to four's injections. But it is also rebuilt from scratch every turn, so it is
paid for every turn.

Put beside [3.3](3.3-the-tool-the-model-may-call.md), the differences line up like this:

| | `load_memory` | `preload_memory` |
| --- | --- | --- |
| Who decides to search | the model, per question | nobody — always |
| Who writes the query | the model | the framework: the user's raw first text part |
| Model requests per turn | 2 when it fires, 1 when it does not | always 1 |
| Visible in the transcript | yes, as a tool call and result | **no** |
| Persists in the session | yes — the tool result is an event | no — transient |
| When the store is empty | the model sees an empty result | nothing is injected at all |
| When the search raises | the exception surfaces | **swallowed**, `logging.warning` |
| Standing charge on the instruction | 219 characters, measured | none |

Read the last three rows together. `preload_memory` is the option that **cannot fail loudly**. Its
`process_llm_request` wraps the search in `try / except Exception`, logs a warning through the root
`logging` module rather than through the `google_adk` logger the rest of ADK uses, and returns. The
turn proceeds. The answer arrives. Nothing in the session, the event stream or a
logger-name-based configuration records that memory was supposed to help and did not.

That is not a bug in the tool. It is a deliberate choice: retrieval failing should not take down the
answer. But it is the property you are buying, and it should be bought on purpose.

## Why Sutra needs it

Because the honest answer to *"which of the two should Sutra use?"* is not obvious, and the
conventional answer — *"the tool, because it only costs when it fires"* — turns out to be wrong on
tokens once you actually measure it. [4.1](../04-the-choice/4.1-pricing-both-in-tokens.md) is that
measurement, and this part is the half of it you need to understand first: **why preloading can be
cheaper than a tool call**, which is that its injection is transient and a tool result is not.

There is also a class of Sutra agent where preloading is obviously right and no measurement is
needed: an agent whose *every* answer depends on history. A "summarise this customer's last six
months" agent should not be asking permission to look; the lookup is the job. Recognising that class
is what stops the day's verdict from being a slogan.

## The mechanism

The same agent shape as 3.3, one tool swapped, and two turns instead of one.

```python
# days/day-46-sessions-vs-memory/lab/pushed.py
    model = ScriptedModel(turns=[says(ANSWER), says("KB-104.")])
    agent = Agent(name="desk", model=model, instruction="You are Sutra.", tools=[preload_memory])
    runner = Runner(agent=agent, app_name=APP, session_service=sessions, memory_service=memory)
    await sessions.create_session(app_name=APP, user_id=USER, session_id="sess-b")

    for question in (TODAY, FOLLOW_UP):
        message = types.Content(role="user", parts=[types.Part(text=question)])
        print(f"turn: {question}")
        async for event in runner.run_async(
            user_id=USER, session_id="sess-b", new_message=message
        ):
            for call in event.get_function_calls():
                print(f"    TOOL CALL {call.name}")
            if event.is_final_response() and event.content and event.content.parts:
                print("    FINAL    ", "".join(p.text or "" for p in event.content.parts))
```

**Line by line:**

- `turns=[says(ANSWER), says("KB-104.")]` scripts **two** plain text answers and no tool calls at all.
  That is the shape of the whole demonstration: with `preload_memory` the model never emits a
  function call, so a script that contains one would never be consumed.
- `tools=[preload_memory]` — the same list, the same argument, a different object. From the agent's
  point of view nothing has changed; from the request's point of view everything has.
- The `for question in (TODAY, FOLLOW_UP)` loop runs **two turns in one session**, and that is
  deliberate. One turn cannot show you the thing that matters, which is that the injection happens
  again on turn two even though the answer is already in the transcript.
- `event.get_function_calls()` is still here, printing nothing. Leaving the line in is the point: you
  are meant to watch it stay silent.
- `FOLLOW_UP` is *"What is the KB article number again?"* — a question whose answer is two lines above
  it in the same conversation. It does not need the past at all. Watch what gets sent anyway.

The measurement:

**Line by line:**

- Identical to 3.3's measurement block, on purpose, so the two transcripts can be read side by side
  without wondering whether the instrument changed.
- `sum(map(len, lines))` counts characters of content. Day 19's
  [4.1](../../../day-19-context-engineering-selection/parts/04-measuring/4.1-a-scale-for-prompts.md)
  argued for characters as the continuous measure and tokens only when a number has to be exact;
  [4.1](../04-the-choice/4.1-pricing-both-in-tokens.md) does the conversion.
- Printing the system instruction's **length** is what makes the standing-charge comparison work: 63
  characters here against 219 in 3.3, for the same agent with a different memory tool.

Five things.

**No `TOOL CALL` line anywhere.** Two turns, memory used on both, and the event stream has nothing in
it about memory. If you were handed this transcript and asked where the desk got ticket 4521 from,
you could not tell from the transcript.

**Two turns, two model requests.** Not four. Compare 3.3, where one turn cost two requests.

**522 characters against 58** on turn one. The injection is nine times the size of the question, for
a store containing one past case.

**And it happens again on turn two.** Look at request 1: the block is there a second time, inserted
between the previous answer and the new question, for a question whose answer was already three lines
above it. That is the newspaper on the morning you leave at seven.

**But it does not accumulate.** Turn two's request is 645 characters, not 522 + 522. The injection is
transient, so the session carries the conversation and not the injections — which is exactly why the
arithmetic in [4.1](../04-the-choice/4.1-pricing-both-in-tokens.md) comes out the way it does.

The system instruction is **63 characters in both arms**, against 219 with `load_memory`. Preloading
adds nothing to the instruction, because it never has to explain itself to the model.

Verified on 2026-09-05 against `.venv/Lib/site-packages/google/adk/tools/preload_memory_tool.py` —
`user_content.parts[0].text` as the query, the `try/except Exception` around the search, the
`logging.warning('Failed to preload memory for query: %s', user_query)` call, the
`<PAST_CONVERSATIONS>` template, and `llm_request._insert_transient_user_content([...])` — and
against `https://adk.dev/sessions/memory/`, which describes `preload_memory` as *"Automatically
retrieves memory at the beginning of each turn."*

## When it breaks

The first break is the one that has no output, so here is what it looks like when it happens. Wire
`preload_memory`, forget `memory_service=` on the runner, and run:

```text
turn: Any past case where a user keeps getting logged out?
    FINAL     No past case on file. Try clearing the browser cache.
```

That is the entire evidence. Exit code `0`. Compare 3.1, where the same mistake with `load_memory`
produced a nine-frame traceback ending in `ValueError: Memory service is not available.` The
difference is one `except Exception` in ADK's source, and it converts a loud configuration error into
a silently degraded product.

The warning that *is* emitted is worth quoting because of how easily it is missed:

```text
WARNING:root:Failed to preload memory for query: Any past case where a user keeps getting logged out?
```

Note `root`. `PreloadMemoryTool` defines a module logger — `logger = logging.getLogger('google_adk.'
+ __name__)` — and then calls `logging.warning(...)` on the module, not on it. A project that
configures the `google_adk` logger and leaves the root logger at its default, which is a completely
normal thing to do, will never see this line.

The second break is the query. Because it is `user_content.parts[0].text` — the raw message — a
question like *"Hi, quick one: the customer on 4610 keeps getting logged out, any past case? Thanks"*
becomes the search string in full, greeting and all. Against
`InMemoryMemoryService`'s *any shared word* rule, `hi`, `quick`, `one`, `the`, `any` and `thanks` are
all live ammunition. [5.1](../05-failure-lab/5.1-the-past-that-matched-on-nothing.md) is the
measurement; [5.4](../05-failure-lab/5.4-the-store-that-outgrew-its-value.md) is what it costs once
the store is large.

And note `parts[0]`: only the **first** part. A message whose first part is an image and whose second
is the question preloads nothing at all, and — because of the `if not user_content.parts[0].text:
return` guard at the top — does so without even reaching the warning.

The third break is the one that looks like a win. Preloading works, everybody is happy, and six
months later the store has fifty thousand entries and the injected block is the largest thing in
every request. The system did not change. The store did.

## In production

**What a professional writes instead of the teaching version.** They do not use the shipped
`preload_memory` unchanged on a general-purpose agent. What they write instead is a
`before_model_callback` doing the same job with three things the shipped tool does not have: a
**query** built from something better than the raw message (the last user turn with stopwords
removed, or a field the agent already put in state), a **cap** on how many memories are injected, and
a **log line** naming the query and the count. That is thirty lines, it keeps the transient-injection
property that makes preloading cheap, and it removes the two properties that make it hard to operate.

**What degrades at scale or under concurrency.** Preloading puts a store read on the critical path of
**every single turn**, which is the strongest statement you can make about a dependency. When the
store is an in-process dictionary that is free. When it is a managed vector service it means every
turn now has two network calls in series, and the slower one has a tail. It also means an outage in
the memory backend degrades every answer rather than the answers that needed history — mitigated,
ironically, by the same `except Exception` that hides the failure. Under concurrency, every turn of
every session contends for the store, so the retrieval path is hit N times harder than it would be
under `load_memory` with the same traffic.

**The failure mode that only appears with real traffic.** The injected block's size is a function of
the store, and the store grows in production and not in test. A demo store of five entries injects
655 characters; the same code at 500 entries injects 48,175 —
[5.4](../05-failure-lab/5.4-the-store-that-outgrew-its-value.md), measured. Nothing changes in the
code between those two numbers, so nothing in code review can catch it.

**The review comment a senior engineer leaves:** *"`preload_memory` sends the user's raw message as
the search query and injects everything that comes back, on every turn, with no cap. On day one that
is two hundred characters. Show me what it is at ten thousand stored conversations, and show me the
log line that would tell us when retrieval started failing — because right now the failure path is a
`logging.warning` on the root logger and we do not configure the root logger."*

**The interview question:** *"When would you inject memory automatically instead of giving the model a
retrieval tool?"* An honest answer: *"When every answer needs history, so asking permission is
ceremony — a 'summarise this customer's account' agent, say. The reasons to like it are real: no
extra model request, and the injection is transient so it does not accumulate in the transcript the
way a tool result does, which actually made it cheaper in tokens than the tool in my measurements.
The reasons I default against it are operational rather than economic. The lookup is not in the event
stream, so you cannot tell from a transcript why the agent said what it said; the query is the user's
raw message, so a polite greeting becomes search terms; and the failure path swallows the exception
and warns on the root logger, so a misconfigured memory service degrades every answer silently. I
would use it, but with my own callback rather than the shipped tool."*
