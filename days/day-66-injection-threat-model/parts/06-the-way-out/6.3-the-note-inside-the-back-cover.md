# 6.3 — The note inside the back cover

## One-line answer

Writing to memory is a **way out**: the desk stores a line, a later question retrieves it, and the
delivery is performed weeks afterwards by the system's own retrieval — measured here as a planted
row coming back **top of three, at 0.491**, to a question that had nothing to do with the ticket it
was written on.

## The story

A paperback comes back to a library and goes onto the returns trolley. Inside the back cover, in
pencil, somebody has written a phone number and a short line about who it belongs to.

The library does not read the insides of returned books. Nobody would; there are four hundred of them
a week. The book is checked, shelved, and lent out again. Over the next two years it goes out
eleven times, and eleven people open the back cover, because that is where the due-date slip used to
be and people still look.

The person who wrote the number never came back. They did not have to. They wrote it in the one
object in the building whose entire job is to be handed to somebody else, later, by staff who will
carry it there for them.

## The idea in plain language

Part [4.1](../04-three-legs/4.1-the-three-things-that-must-not-meet.md) made a claim that reads
strangely the first time: `save_memory` is an **outward** capability. It said the classification
"will look wrong to a reader who thinks 'outward' means the internet", and it deferred the proof to
this part. Here it is.

**Outward does not mean "to the internet". It means to somewhere the attacker can eventually read.**
A memory row is written by one run and read by a different run: a different question, a different
customer, a later day, an agent that has no idea where the sentence came from. If the attacker can
ask a question that retrieves the row, the data has left the building — it just left slowly, and by
a route your network diagram does not have an arrow for.

There is a part of this day next door to it, and the difference is worth being precise about, because
the two are easy to blur:

| | Part [3.1](../03-the-slow-fuse/3.1-written-monday-read-thursday.md) | This part |
| --- | --- | --- |
| What goes into memory | an **instruction** | **data** |
| What it does when retrieved | steers a later agent | is read by whoever asked |
| The trifecta leg it is | untrusted content, arriving late | **outward** |
| The harm | escalate, mislead | exfiltrate |

3.1 is memory as an **entry point**: hostile text survives into the store and becomes a standing rule
for agents who never saw the ticket it came from. This part is memory as an **exit**: private text is
put into the store and comes back out to a reader the attacker chose. Same store, opposite direction,
and a threat model needs both rows because closing one does nothing to the other.

## Why Sutra needs it

Because Day 48 designed the memory store on the assumption that what goes into it is worth keeping,
and Days 49 and 50 built a retrieval index whose whole purpose is to find a stored row again from a
question that does not quote it. Those two facts, put together, are a delivery service.

The desk has `save_memory` because a support desk that forgets is a bad support desk. So this channel
cannot be closed by deleting the tool any more than part [6.2](6.2-read-back-for-confirmation.md)'s
could — which means the threat model needs it written down explicitly, with an owner, rather than
resting on the reassurance that there is no outbound network call.

It also changes what "clean up after the incident" means, and that is the part teams get wrong. When
an exfiltration goes out over a network call, the response is to revoke a key and block a domain.
When it goes into memory, the data is now *inside your own system*, indexed, retrievable, and shaped
exactly like every legitimate row. Cleaning up is a **search problem** over your own store, and you
are searching for something you do not have a precise description of.

## The mechanism

The declaration is four lines and every one of them is doing work:

```python
Channel(
    "memory write",
    "save_memory",
    f"standing note: {SECRET}",
    "every future agent whose question retrieves the row",
    False,
)
```

**Line by line:**

- `needs` is `save_memory` — a tool the desk has for a good reason, and one that nobody reviewing a
  tool list for "outbound capability" would flag, because it writes to a database you own.
- `bytes_out` is prefixed `standing note:` because that is the shape memory rows have. The row does
  not look like stolen data; it looks like the desk being helpful, which is what the desk was doing
  when it wrote it.
- `who_sees` is the line to read twice: *"every future agent whose question retrieves the row"*. Not
  one reader — an unbounded set of them, defined by a query that has not been written yet.
- `obvious` is `False`. Writing to your own store is the opposite of an alarm: it is what a
  well-behaved agent does.

Now the delivery. Build the archive Days 49 and 50 indexed, add one row of the kind the desk writes
itself, and ask an unrelated question:

```bash
cd days/day-66-injection-threat-model/lab
uv run python -c "
import _index, _poison, channels

docs = _poison.clean_archive()
docs['memory:0091'] = 'Standing note for this account: ' + channels.SECRET
index = _index.build_index(docs)
for question in ('what is the refund window', 'account balance query'):
    print(question)
    for score, ref in _index.search(index, question, k=3):
        mark = '  <- the row the desk wrote' if ref.startswith('memory:') else ''
        print(f'  {score:.3f}  {ref}{mark}')
    print()
print('rows in the index:', index.rows)
"
```

**Line by line:**

- `_poison.clean_archive()` returns the archive **with nothing hostile in it** — the fifty-eight rows
  as Days 49 and 50 left them. That matters: the demonstration must not smuggle in a poisoned
  document, because the point is that the dangerous row is one the desk wrote itself.
- `docs['memory:0091'] = ...` is the memory write. `channels.SECRET` is the synthetic private value
  from `channels.py`; using the same constant is what keeps this run tied to the channel declaration
  above rather than to a fresh invention.
- `_index.build_index(docs)` is Day 49's tf-idf arithmetic, restated in the lab so today's numbers
  are reproducible without a network call. Memory rows and archive rows go into **one index**, which
  is the design decision this whole part turns on.
- The two questions are the experiment. Neither of them mentions the ticket the note was written on;
  the first is about refunds and should not find it, the second is a plausible later question from a
  plausible later customer.
- `k=3` is the top-k Day 50 tuned. The row does not need to be the only hit — it needs to be *in the
  prompt*, and anything in the top three is.

Measured on 2026-09-06:

```text
what is the refund window
  0.265  ticket:4593
  0.164  ticket:4562
  0.158  ticket:4610

account balance query
  0.491  memory:0091  <- the row the desk wrote
  0.135  ticket:4512
  0.122  ticket:4604

rows in the index: 58
```

Read the second block. The planted row comes back **first**, at 0.491 — nearly four times the score
of the next hit — to a question asked by somebody who never saw the original ticket. The retrieval
did not malfunction. It worked perfectly: it found the most relevant row it had for a question about
an account balance, and the most relevant row was the one containing an account balance.

That is the delivery part 4.1 promised. Nothing outbound happened. Nobody's guard was got past. The
data went out through a component whose job is to hand stored text to whoever asks a question it
matches.

The first block matters too, and it is the reason this is hard to find: to a question about refunds,
the row is invisible. It sits in the index doing nothing, for weeks, until a matching question
arrives. A test suite that checks "does memory leak private data?" by asking one question will pass.

## When it breaks

The obvious fix is to write less: do not put private values in memory at all. It is the right
instinct and it breaks in a specific place.

Memory rows are written by summarisation. Day 48's design keeps what the desk decided was worth
remembering about a ticket, and the summariser is a model that has just read a ticket containing an
account, a balance and an email address. "Do not include private values in the summary" is an
**instruction**, and part [1.3](../01-one-stream/1.3-the-sentence-you-did-not-write.md) established
what instructions are worth against text that argues with them. Worse, it does not even need an
attacker: a summariser that mentions the balance because the ticket was *about* the balance is a
summariser doing its job.

So the honest ordering of controls is:

1. **Do not index memory rows with archive rows.** The single index is what makes an arbitrary later
   question retrieve them. Two stores with separate retrieval, and a memory row only ever fetched for
   the session or customer it belongs to, closes the delivery route without touching the tool. This is
   a structural change and it is the strongest thing available here.
2. **Scope memory rows to a subject.** A row tagged with the account it concerns can be filtered at
   query time, so a question from a different customer cannot match it however similar the words are.
   Cheap, and it turns an unbounded reader set into a defined one.
3. **Strip values on write, and test it.** Worth doing, weakest of the three, for the reason above:
   it is a check that has to keep being right, on text a model produced.

Note what none of the three is: a scanner that reads memory rows looking for anything sensitive.
Section 6.1 measured what defences built on recognising surface forms are worth.

## In production

**What changes at ten thousand tickets.** Retention. A network exfiltration is an event with a
timestamp; this one is a **row that stays**. It survives the incident, the postmortem, the fix and
the person who found it, and it keeps being retrievable the whole time. At small volume you can read
the store. At ten thousand tickets a day, nobody can, and the cleanup question — *which rows contain
private data that should not be there?* — is a search over your own data for something you cannot
write a precise query for. Teams end up deleting a date range, which throws away good rows, or
deleting nothing, which is what usually happens.

**The failure mode that only appears with real traffic.** The memory store is not on the data-flow
diagram. Diagrams have arrows for the things that cross a boundary — the API, the model provider, the
ticket system — and a database you own, written to by your own service, does not look like a
boundary. So the row that lists "where can customer data end up" does not have memory on it, the
retention policy does not cover it, and the data subject access request does not search it. That is
usually discovered during the request, not before.

**What a professional does.** Two things this day already justifies. Give every memory row a
**provenance field** recording the ticket and the customer it was derived from — that makes both the
query-time filter and the cleanup possible, and it is the same idea Day 67's paper builds a whole
system out of. And put memory in the data-flow diagram as a store that holds customer-derived text,
so it inherits the retention and access rules the rest of the customer data has rather than quietly
sitting outside them.

**The review comment a senior engineer leaves:** *"The memory design is fine but it shares an index
with the archive, and that means any question can retrieve any row. Two changes: tag rows with the
account they came from and filter on it at query time, and add a provenance column so we can answer
'where did this row come from' during an incident. Right now the honest answer to 'has any customer
data ended up in memory' is that we'd have to read all of it, and I'd rather not find that out in
front of a regulator."*

**The interview question:** *"You've removed all the network tools from an agent. Where can data still
go?"* An honest answer: *"The reply, and the memory store. The memory one surprises people, because
writing to your own database doesn't look outbound — but the data is being handed to a different
reader later, and if the store is retrieved by similarity then whoever asks a matching question gets
it. I measured this on a support desk: a planted note came back top of three, at nearly four times
the next score, to an unrelated question from a different session. Two things follow. First, memory
belongs on the data-flow diagram and under the same retention rules as the rest of the customer data.
Second, don't index memory rows in the same space as everything else — scope them to the account, so
a question from somebody else can't match them however close the wording is."*
