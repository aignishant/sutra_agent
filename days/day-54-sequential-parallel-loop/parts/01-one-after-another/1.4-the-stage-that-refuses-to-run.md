# 1.4 — The stage that refuses to run

## One-line answer

Five different mistakes in a graph are all rejected the moment `Workflow(...)` is constructed, with
a message that names the offending node — and knowing all five by sight is the difference between a
two-minute fix and an evening.

## The story

The parcel goes to the depot with the label you printed at home. It does not go on a van.

It sits on a bench by the scanner because the barcode did not read, and the man at the bench works
through a short list without thinking about it. Is there a house number. Is there a postcode. Is
the postcode a real postcode. Is the weight on the label the weight on the scale. Is there a second
label from a previous journey still stuck to the box.

He does not open the parcel. He does not attempt the delivery and see what happens. Everything he
checks, he checks against the label alone, before the parcel costs anybody a mile of diesel. The
five questions take him seconds because he has asked them ten thousand times, and four out of five
parcels on that bench go back to the counter with one of five sentences.

Your graph gets the same treatment, and there are five sentences.

## The idea in plain language

A `Workflow` is **validated when it is constructed**. Not when it runs, not on the first request:
when the object is made. If the shape is wrong, the constructor raises and there is no workflow
object at all.

This is possible because of [1.3](1.3-why-calling-them-in-order-is-not-a-workflow.md) — the shape is
data, so it can be read before it is executed. It is the concrete payoff of that argument, and it
is worth meeting all at once rather than one bad afternoon at a time.

The validator asks five questions of the edges you gave it, in this order:

| # | The question | What it is protecting |
| --- | --- | --- |
| 1 | Do two different node objects share a name? | A node is addressed by name, so two of them make the graph ambiguous. |
| 2 | Is there a `START`, and does everything have a path from it? | A node nothing reaches is a stage you thought you wired up. |
| 3 | Does any edge point *into* `START`? | `START` is where the run begins; an arrow into it has no meaning. |
| 4 | Is the same edge declared twice? | A duplicate edge triggers the target twice, which is almost never intended. |
| 5 | Does any edge out of `START` carry a route? | A route is a decision made by a node's output, and `START` produces none. |

There is a sixth, about unrouted cycles, which belongs to section 3 and is covered in
[3.2](../03-around-again/3.2-the-cycle-the-runtime-refuses.md).

One more term, used in the messages. A **route** is a label on an edge that says "take this arrow
only when the node upstream said so". Section 3 builds on it; here you only need to know that an
edge with no route is always followed and an edge with one is followed conditionally.

## Why Sutra needs it

The triage graph on Day 58 has six nodes and eight edges, and it will be edited on Day 59, on
Day 62 when a human approval step lands in the middle of it, and again on Day 64. Every one of
those edits is an opportunity to leave a node dangling or to name two nodes `review`.

The value of this part is not that the checks exist. It is that when one of them fires at half past
ten at night, you read the sentence, recognise it, and fix it in one line — instead of reading a
Pydantic `ValidationError` wrapper for the first time and assuming your data is malformed.

## The mechanism

All five, built on purpose. Each one is a graph that is meant to be rejected.

```python
from google.adk.workflow import START, Edge, FunctionNode, Workflow

node_a = FunctionNode(func=a, name="fetch")
node_b = FunctionNode(func=b, name="draft")
node_c = FunctionNode(func=c, name="review")

# 1. a node nothing points at
Workflow(name="orphan", edges=[(START, node_a), Edge(from_node=node_b, to_node=node_c)])

# 2. two different nodes sharing a name
Workflow(name="twins", edges=[(START, FunctionNode(func=a, name="draft"), node_b)])

# 3. the same edge declared twice
Workflow(name="double", edges=[(START, node_a, node_b), Edge(from_node=node_a, to_node=node_b)])

# 4. an edge back into START
Workflow(name="backwards", edges=[(START, node_a), Edge(from_node=node_a, to_node=START)])

# 5. a condition on the edge out of START
Workflow(name="conditional_start", edges=[Edge(from_node=START, to_node=node_a, route="maybe")])
```

**Line by line:**

- `Edge(from_node=..., to_node=..., route=...)` — the explicit form of an edge, as opposed to the
  tuple sugar in [1.1](1.1-the-order-you-declare-is-the-order-you-get.md). You need it whenever an
  edge is not simply "the next element of a chain": a route, or an arrow that goes somewhere the
  chain has already been. Verified with
  `python -c "from google.adk.workflow import Edge; print(sorted(Edge.model_fields))"` on
  `google-adk==2.7.1`, which prints `['from_node', 'route', 'to_node']`.
- Case 1 declares two separate tuples, so `draft` and `review` form an island with no path from
  `START`.
- Case 2 builds a *second* node object also called `draft`. Both are perfectly valid nodes; the
  graph cannot hold both.
- Case 3 gives `fetch → draft` twice, once through the tuple and once explicitly. This is what
  happens when you add an edge you already had.
- Case 4 points an edge at `START`, which is what a first attempt at a loop often looks like.
- Case 5 puts a route on the very first edge, which is what "only start if…" looks like before you
  learn that the condition belongs on a node.

**Line by line:**

- `refuse.py` builds each of the five inside a `try`, prints the one line of the exception that
  starts `Graph validation failed`, and moves on to the next.

Measured on 2026-09-05:

```text
--- a node nothing points at
    ValidationError: Graph validation failed. The following nodes are unreachable from START: ['draft', 'review']
--- two different nodes sharing a name
    ValidationError: Graph validation failed. Duplicate node names found: ['draft']. This means multiple distinct node objects have the same name. If you intended to reuse the same node, ensure you pass the exact same object instance. If you intended to have distinct nodes, ensure they have unique names.
--- the same edge declared twice
    ValidationError: Graph validation failed. Duplicate edge found: from=fetch, to=draft
--- an edge back into START
    ValidationError: Graph validation failed. START node must not have incoming edges.
--- a condition on the edge out of START
    ValidationError: Graph validation failed. Edges from START must not have routes (edge to fetch has route maybe)
```

Five graphs, five refusals, no nodes run. Every message names the thing: which nodes are stranded,
which name is duplicated, which edge is doubled, which route is on the wrong edge.

The second message is worth reading twice, because it tells you the two ways out and they lead to
opposite fixes: *"if you intended to reuse the same node, ensure you pass the exact same object
instance"* versus *"if you intended to have distinct nodes, ensure they have unique names."* One of
those is a variable you forgot to reuse and the other is a name you forgot to change.

## When it breaks

The five above are the graph refusing to be built. There is a sixth failure that lives one layer
down and is easy to confuse with them, because it also mentions a node by name and also stops the
run — but it happens at run time, not at construction, and the fix is somewhere else entirely.

```python
def assign(ticket_id: str) -> str:
    return f"assigned ticket {ticket_id}"
```

**Line by line:**

- A node whose parameter is not called `node_input`, so the runtime binds it from session state by
  name — the rule from [1.2](1.2-what-the-next-stage-can-see.md).
- No default value, and nothing upstream wrote `state["ticket_id"]`.

The graph builds without complaint. Then, when the node is reached:

```text
ValueError: Missing value for parameter "ticket_id" of function "assign". It was not found in
state and has no default value.
```

This is the difference worth carrying away. **Structure is checked before the run; data is checked
when the node reaches it.** The five messages above all begin `Graph validation failed` and you fix
them by editing the `edges=` list. This one does not, and you fix it by finding out why the state key
is absent — never by adding a default, which converts a stopped run into a wrong answer, as
[1.2](1.2-what-the-next-stage-can-see.md) measured.

## In production

**What a professional writes instead.** They construct every graph once, at start-up, in a place
where a failure is loud — an application factory, a module-level `build()` called from `main()`.
Some go further and add a test whose whole body is `triage_graph()`, with no assertion at all. It
looks pointless and it is not: constructing the graph *is* the assertion, because construction is
where validation happens. That test fails on the day somebody adds a node and forgets its edge, and
it costs one line.

**What degrades at scale.** The messages stay useful; the graphs stop being readable. `Duplicate
node names found: ['review']` is instant in a six-node graph and a hunt in a forty-node one built
from four composed sub-graphs. The move is a naming convention that includes the sub-graph —
`research.rank`, `reply.review` — so the name in the error message tells you which file to open.

**The failure mode that only appears with real traffic.** None of these five, and that is exactly the
point of them: they are the class of bug that *cannot* reach traffic, because the object refuses to
exist. What does reach traffic is the run-time cousin above, which depends on the data rather than
the shape. A graph that validates cleanly at start-up and then dies on one ticket in five hundred is
almost always a state key that only some paths write.

**The review comment a senior engineer leaves:** *"You are catching `ValidationError` around
`Workflow(...)` and logging a warning. Do not. If the graph is invalid the process should not start
— that is the whole benefit of validating at construction. Catching it here means we ship a
container that boots, serves, and fails on the first request."*

**The interview question:** *"What does your workflow framework check for you, and when?"* An honest
answer: *"ADK's graph runtime validates at construction, so five structural mistakes never reach a
run: duplicate node names, nodes unreachable from START, an edge into START, a duplicated edge, and
a routed edge out of START — plus an unrouted cycle. I know them by the first line of the message,
which always starts `Graph validation failed`. What it cannot check at construction is the data: a
node whose parameter binds from state fails when it is reached, with a different message that names
the parameter and the source it looked in. I keep those two apart in my head, because one is fixed
by editing the edge list and the other by finding out which upstream node did not write the key."*
