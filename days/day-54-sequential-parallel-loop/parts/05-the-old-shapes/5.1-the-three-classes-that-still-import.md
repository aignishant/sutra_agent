# 5.1 — The three classes that still import

## One-line answer

`SequentialAgent`, `ParallelAgent` and `LoopAgent` are the 1.x way of writing this day's three shapes;
in `google-adk==2.7.1` they still import, still construct, and carry a deprecation warning that is
**printed when you build one in a script and completely silent when you build one inside a module** —
which is where real code builds things.

## The story

The medicine cabinet has a box of the tablets you take for a bad back.

The box looks fine. The blister strip inside is intact, the printing is sharp, the leaflet is folded
in the way it was folded at the factory. You take two.

The expiry date is on the crimped end of the box, in grey, four millimetres high, and it was two
years ago. Nothing about the box announced this. It did not go soft, or change colour, or refuse to
open. Everything that was easy to see said the box was fine, and the one thing that said otherwise was
printed where nobody looks.

There is a version of this that is worse, and it is the one worth thinking about: the box you keep
loose in a drawer, without the outer carton. Now the date is not printed anywhere at all, and there
is nothing to check even if you thought to check.

## The idea in plain language

Plan §5.1 lists four traps for anyone moving from ADK 1.x to 2.x. **Trap #1 is the node model**, and
it is the one that owns this day.

In 1.x, the three shapes of this day were three **agent classes**. You built a `SequentialAgent` with
a list of `sub_agents` and it ran them in order; a `ParallelAgent` ran them at once; a `LoopAgent` ran
them repeatedly, with an optional `max_iterations`. Composition was a tree of agents, and workflow
agents were special agents that happened to arrange other agents.

In 2.x the composition layer is the graph Workflow Runtime that Day 53 introduced and this day has
been using: nodes and edges, with agents as **one kind of node** rather than as the organising
principle.

The trap is not that the old way is gone. The trap is precisely that **it is not gone**. All three
classes are importable in 2.7.1 and all three construct without error. Every 1.x tutorial on the
internet still runs. So a reader who has been learning from those tutorials gets working code, and
never encounters a moment where something forces them to notice that the composition model changed
underneath them.

What the package does say is in the docstrings and in a `DeprecationWarning` — and Python's default
warning filter shows `DeprecationWarning` only when it is triggered from `__main__`. In a script you
run directly, you see it. In a module your application imports, you do not. That is the expiry date
printed on the crimp, and then the box out of its carton.

## Why Sutra needs it

Sutra is being built from adk.dev and from these documents, so it will not accidentally use a 1.x
class. The risk is the other direction: you will read something outside this curriculum — an example,
an answer, a repository — and it will use `SequentialAgent`, and it will look authoritative because it
works.

This part is so that you recognise the shape on sight and know what it maps to. That recognition is
also the interview answer, because "which ADK version is this person actually familiar with" is a
question a graph-model question is often really asking.

## The mechanism

What the installed package says about its own classes.

```python
from google.adk.agents import LoopAgent, ParallelAgent, SequentialAgent

CLASSES = (SequentialAgent, ParallelAgent, LoopAgent)

for cls in CLASSES:
    note = [
        line.strip()
        for line in (cls.__doc__ or "").splitlines()
        if "deprecated in favor of" in line
    ]
    print(f"{cls.__name__}: {note[0] if note else '(no deprecation note)'}")

print("LoopAgent.max_iterations default:", LoopAgent.model_fields["max_iterations"].default)
```

**Line by line:**

- `from google.adk.agents import ...` — note the module. These live under `google.adk.agents`, not
  under `google.adk.workflow`, which is itself the statement: in 1.x they were agents, and the graph
  layer they were replaced by is somewhere else entirely.
- `cls.__doc__` — reading the shipped docstring rather than quoting one from memory. What the package
  says about itself is a fact you can check on your own machine; what a blog post says about it is
  not.
- `LoopAgent.model_fields["max_iterations"].default` — the old loop class had an iteration cap built
  in, which the graph runtime does not. What its default is turns out to matter.

Run it:

```bash
cd days/day-54-sequential-parallel-loop/lab
uv run python oldshapes.py
```

**Line by line:**

- `oldshapes.py` prints the docstring notes, the `max_iterations` default, and then constructs one of
  each with warnings turned all the way up.
- `--quiet` constructs one from inside an imported module instead, which is the second half of this
  part.

Measured on 2026-09-05, on `google-adk==2.7.1`:

```text
importable in google-adk 2.7.1: SequentialAgent, ParallelAgent, LoopAgent

what the shipped docstrings say:
    SequentialAgent: SequentialAgent is deprecated in favor of Workflow and will be removed in
    ParallelAgent: ParallelAgent is deprecated in favor of Workflow and will be removed in a
    LoopAgent: LoopAgent is deprecated in favor of Workflow and will be removed in a

LoopAgent.max_iterations default: None

constructing in __main__, with warnings turned all the way up:
    DeprecationWarning: SequentialAgent is deprecated in favor of Workflow and will be removed in a future version. Workflow cannot yet be used as an LlmAgent sub-agent.
    DeprecationWarning: ParallelAgent is deprecated in favor of Workflow and will be removed in a future version. Workflow cannot yet be used as an LlmAgent sub-agent.
    DeprecationWarning: LoopAgent is deprecated in favor of Workflow and will be removed in a future version. Workflow cannot yet be used as an LlmAgent sub-agent.
```

Three things in that output are worth stopping on.

**All three constructed.** There is no error, no failure, no missing import. Code written against 1.x
runs on 2.7.1.

**`LoopAgent.max_iterations` defaults to `None`.** So even the old class, which *does* have an
iteration cap, does not use one unless you set it. If you have been carrying an assumption that the
1.x loop was safer than the graph, it was not: it had a place to put the cap and no cap in it.
[3.5](../03-around-again/3.5-the-guard-you-write-yourself.md) is the answer in either model.

**The last sentence of the warning is the important one:** *"Workflow cannot yet be used as an
LlmAgent sub-agent."* That is not a footnote, it is the reason these classes are still here. There is
one composition — a graph nested inside an agent's `sub_agents` tree — that the new model does not yet
express, so the old classes remain for it. Knowing that is what stops you reading the deprecation as
"delete these on sight".

Here is the mapping, which is the practical content of this part:

| 1.x | 2.x |
| --- | --- |
| `SequentialAgent(sub_agents=[a, b, c])` | `Workflow(edges=[(START, a, b, c)])` |
| `ParallelAgent(sub_agents=[a, b, c])` | `Workflow(edges=[(START, (a, b, c), JoinNode(name="j"))])` |
| `LoopAgent(sub_agents=[a], max_iterations=3)` | a routed back edge plus a cap you write ([3.5](../03-around-again/3.5-the-guard-you-write-yourself.md)) |

Note the second row: the 1.x parallel agent had no join, because there was nowhere for one to go. The
`JoinNode` is not extra ceremony in the translation — it is the thing the old model had no way to say,
which is why the old model's downstream step received one result rather than all of them.

## When it breaks

It breaks by not breaking. Run the same constructions from inside an imported module:

```python
# _oldshapes_module.py
from google.adk.agents import SequentialAgent


def build() -> SequentialAgent:
    """Construct a deprecated 1.x workflow agent from inside a package."""
    return SequentialAgent(name="built_inside_a_module", sub_agents=[])
```

**Line by line:**

- Nothing here is unusual. This is what every real application looks like: a builder function in a
  module, imported and called by something else.
- The construction is identical to the one that printed three warnings above. The only thing that
  changed is which file it happens in.

```bash
uv run python oldshapes.py --quiet
```

**Line by line:**

- `--quiet` imports that module and calls `build()`, instead of constructing in `__main__`.

```text
constructing from inside an imported module:
    (nothing printed above this line)
```

Nothing. Python's default warning filter shows `DeprecationWarning` only for warnings triggered by
code in `__main__`, so the same line of code that announced itself in a script is silent in a package.

This is why the trap survives. A person exploring in a script sees the warning and looks it up. A team
with the same call in `app/agents.py` sees nothing, for as long as the class exists, and finds out
when it is removed.

The fix is to make deprecation warnings visible on purpose:

```bash
uv run python -W error::DeprecationWarning -m your_app
```

**Line by line:**

- `-W error::DeprecationWarning` promotes every `DeprecationWarning` to an exception, wherever it is
  raised, so a deprecated call fails loudly instead of passing quietly.
- Run it in CI rather than in production. You will find other people's deprecations too — running this
  against Sutra's own dependencies surfaces an unrelated one from a config base class — so the useful
  form filters to the module you care about rather than turning everything into an error at once.

## In production

**What a professional writes instead.** They do not migrate a working `SequentialAgent` because it is
deprecated. They migrate when they need something the graph model has and the tree model does not,
which for this day's material means: per-node retry and timeout, an explicit join, a routed
conditional, or resumption from a recorded node
([1.3](../01-one-after-another/1.3-why-calling-them-in-order-is-not-a-workflow.md)). What they do
immediately is stop writing *new* code against the old classes, and put the deprecation check in CI so
the count can only go down.

**What degrades at scale.** A codebase with both models in it. The two do not compose in one
direction — the warning says a `Workflow` cannot yet be an `LlmAgent` sub-agent — so a tree with a
graph inside it is not currently expressible, and a half-migrated system tends to grow an adapter
layer whose only job is to bridge the two. That adapter is the most expensive artefact of a
half-finished migration, and it is worth deciding the direction of travel before writing one.

**The failure mode that only appears with real traffic.** None from the classes themselves; they work.
The failure is a **version bump**. The docstrings say "will be removed in a future version", so the
day the pin moves, an application that never saw a warning stops importing. That is why the pin is
exact in `pyproject.toml` and why `docs/PACKAGES.md` carries a dated row for `google-adk==2.7.1` —
Principle 7 exists for the upgrade, not for the install.

**The review comment a senior engineer leaves:** *"This is a `SequentialAgent`, which is deprecated in
2.x in favour of `Workflow`. It works, so I am not blocking on it — but do not add another one, and
when this file needs a retry on the middle step, that is the moment to convert it, because the graph
model has per-node retry and this does not."*

**The interview question:** *"You have inherited an ADK codebase using `SequentialAgent` and
`LoopAgent`. What do you do?"* An honest answer: *"Nothing urgent, and I would say so out loud. They
are deprecated in 2.x in favour of the graph `Workflow` — the shipped docstrings say so, and
constructing one raises a `DeprecationWarning` — but they still work in 2.7.1, and one composition,
a `Workflow` as an `LlmAgent` sub-agent, is not supported yet, which is why they are still there. So:
turn `DeprecationWarning` into an error in CI so the count cannot grow, stop writing new ones, and
convert a given file when it needs something the graph gives you — per-node retry or timeout, a real
join, or resumability. The thing I would flag on day one is that the warning is invisible in normal
running, because Python only shows `DeprecationWarning` from `__main__`, so 'we have never seen a
warning' is not evidence of anything."*
