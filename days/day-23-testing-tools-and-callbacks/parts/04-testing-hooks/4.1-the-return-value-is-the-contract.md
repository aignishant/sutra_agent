# 4.1 — A callback's return value is its whole contract

## One-line answer

Every ADK hook says the same thing with its return value — `None` means *carry on* and anything else
means *stop and use this instead* — so a hook is tested by driving it with `asyncio.run` and asserting
on exactly one thing: what came back.

## The story

The inspector comes down the aisle of the train checking tickets.

Most of the time nothing happens. He glances at the screen you are holding up, gives a small nod, and
moves on. You do not get a receipt for having a valid ticket. The absence of an interaction *is* the
result.

Occasionally something else happens. He stops, he does not move on, and he writes you a penalty
notice. And the notice replaces the journey you thought you were having: you are no longer a passenger
with a ticket, you are a passenger with a fine, and everything downstream — the guard, the barrier at
the far end, the letter in three weeks — follows from the piece of paper rather than from the ticket
you showed.

So there are exactly two outcomes and they are told apart by whether he handed you anything.

## The idea in plain language

[Day 13](../../../day-13-callbacks-four-doors/LESSON.md) taught the four callback doors and one rule.
[Day 14](../../../day-14-plugins-one-layer-up/LESSON.md) moved the same idea one layer up into
plugins. [Day 21](../../../day-21-errors-surface-not-swallow/parts/02-four-hooks/2.2-the-two-that-can-rescue.md)
showed which hooks can rescue an error. Underneath all three is one convention, and it is worth stating
in isolation because it is the entire testable surface of a hook:

> **Return `None` and the framework carries on. Return a value and the framework uses that instead of
> whatever it was about to do.**

For `before_tool_callback`, returning a dictionary means the tool **is not run** and your dictionary is
handed back as its result. For `on_tool_error_callback`, returning a dictionary means the exception
stops there and your dictionary becomes the tool's result. For `on_event_callback`, returning an
`Event` means your event is persisted instead of the original.

That is a very unusual shape for a Python function and it is why hooks are easy to get subtly wrong. A
hook that returns something by accident — a stray `return result` at the end, a helper that returns a
truthy value — does not raise. It silently changes what the system did.

Which is why testing a hook is simpler than testing almost anything else: **there is one assertion, and
it is about the return value.** The interesting cases are the two directions of it:

- The hook decided to do nothing → `assert verdict is None`.
- The hook decided to intervene → `assert verdict == {...}`.

`is None`, not `== None` and not `not verdict`. An empty dictionary is falsy and is *not* the same
answer as `None`; returning `{}` from `before_tool_callback` means *"skip the tool and give the model
an empty result"*, which is a completely different outcome from *"run the tool"*. `assert not verdict`
would accept both, and that is a bug the test would be unable to see.

The mechanical part is the same as [3.3](../03-testing-tools/3.3-the-async-tool-without-a-runner.md):
every hook on `BasePlugin` is `async def`, so `asyncio.run` drives it. And every one of them is
**keyword-only** — verified against the installed `google-adk` 2.7.1 on 2026-09-04, where
`before_tool_callback` is declared
`(self, *, tool: BaseTool, tool_args: dict[str, Any], tool_context: ToolContext) -> Optional[dict[str, Any]]`.
The `*` means positional arguments are refused, so the test must call it with names.

## Why Sutra needs it

Because Sutra's hooks are where its safety rules live, and a safety rule that stops firing is a rule
nobody notices has stopped.

The `before_tool_callback` from [Day 16](../../../day-16-built-in-tools-with-brakes/LESSON.md) is what
stops a write tool running without approval. Day 21's `on_tool_error_callback` is what turns a timeout
into a marked substitute instead of an outage. Day 22's recorder is what writes the line that any later
question will be answered from. Every one is a policy expressed as a return value, and every one is
invisible when it fails: the agent still answers, the run still succeeds, and the brake is simply not
there any more.

There is also a nastier version, and Day 21 named it: a hook that rescues **too much**. An
`on_tool_error_callback` that returns a dictionary for every exception has re-created the swallowed
`try`/`except` that day spent itself removing, only one layer up where it is harder to see. The test
that catches that is `assert verdict is None` for an error the policy did not plan for — and it is the
assertion nobody writes, because it asserts that nothing happened.

## The mechanism

A plugin whose two hooks are Sutra's two real policies, written with the signatures ADK declares.

```python
# days/day-23-testing-tools-and-callbacks/lab/hooks_demo.py
class Policy:
    """Day 21's error policy and Day 16's brake, reduced to what a test can drive."""

    WRITE_TOOLS = frozenset({"issue_refund", "close_ticket"})

    def __init__(self) -> None:
        self.seen: list[str] = []

    async def before_tool_callback(
        self, *, tool: object, tool_args: dict[str, object], tool_context: object
    ) -> dict[str, object] | None:
        """Returning a dict skips the tool and hands that dict back as its result."""
        if tool.name in self.WRITE_TOOLS and not tool_args.get("approved"):
            return {"status": "blocked", "reason": f"{tool.name} needs approval first"}
        return None
```

**Line by line:**

- `*` after `self` makes every parameter keyword-only, matching `BasePlugin`. This is not stylistic:
  ADK calls these hooks with keywords, and a hook written positionally would work in a test that calls
  it positionally and fail in the framework, which is the worst possible ordering of discoveries.
- `WRITE_TOOLS` is a `frozenset` at class level. Frozen because it is a rule rather than state — a
  mutable class attribute is the shared-object trap from
  [2.3](../02-pytest-house-rules/2.3-fixtures.md) — and a set because the operation is membership.
- `tool.name` rather than a string parameter. ADK passes the `BaseTool` object, so the double in the
  test needs `.name` and nothing else, which is the same minimal-shape rule as
  [3.2](../03-testing-tools/3.2-the-fake-tool-context.md).
- `not tool_args.get("approved")` uses `.get`, so a call with no `approved` key at all is treated as
  unapproved. `tool_args["approved"]` would raise `KeyError` on the most common input, and a hook that
  raises turns a brake into an outage.
- **`return None` is written explicitly** on the last line rather than falling off the end of the
  function. Both behave identically, and the explicit form is what makes the contract visible to the
  next reader: this branch is a decision to allow, not an absence of code.
- The whole method has no `try`/`except`. If the policy itself raises, the exception should surface —
  Principle 10, and [21.4.2](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.2-the-handler-that-became-the-error.md)
  measured what happens when a handler becomes the error.

Now the tests. Three of them, and the middle one is the assertion people leave out.

```python
# days/day-23-testing-tools-and-callbacks/lab/test_hooks_demo.py
import asyncio
from dataclasses import dataclass

import pytest
from hooks_demo import Policy


@dataclass
class FakeTool:
    """A BaseTool double. The hooks read `.name`, so `.name` is the whole of it."""

    name: str


def test_a_write_tool_without_approval_is_blocked_before_it_runs() -> None:
    verdict = asyncio.run(
        Policy().before_tool_callback(
            tool=FakeTool("issue_refund"), tool_args={"amount": 40}, tool_context=None
        )
    )
    assert verdict == {"status": "blocked", "reason": "issue_refund needs approval first"}


def test_an_approved_write_tool_is_allowed_through() -> None:
    verdict = asyncio.run(
        Policy().before_tool_callback(
            tool=FakeTool("issue_refund"), tool_args={"approved": True}, tool_context=None
        )
    )
    assert verdict is None, "returning anything but None replaces the tool call"


@pytest.mark.parametrize("name", ["lookup_ticket", "search_kb"])
def test_a_read_tool_is_never_blocked(name: str) -> None:
    verdict = asyncio.run(
        Policy().before_tool_callback(tool=FakeTool(name), tool_args={}, tool_context=None)
    )
    assert verdict is None
```

**Line by line:**

- `@dataclass class FakeTool` with one field. A dataclass gives a constructor and a readable `repr` for
  free, so a failing assertion prints `FakeTool(name='issue_refund')` instead of an object address.
- `tool_context=None` — the hook never touches it, so the double for it is **nothing at all**. That is
  the dummy from [1.4](../01-where-the-line-falls/1.4-four-doubles.md): a value present only because the
  signature requires it. If the hook ever starts using the context, `None` produces an immediate
  `AttributeError` rather than a quiet wrong answer, which is exactly what a dummy is for.
- Every call uses keywords, because the hook is keyword-only. Calling it positionally raises
  `TypeError: Policy.before_tool_callback() takes 1 positional argument but 4 were given`, which is a useful
  failure to have seen once.
- `Policy()` is constructed fresh inside each test rather than shared. It has mutable state (`seen`), so
  sharing it would couple the tests — [2.3](../02-pytest-house-rules/2.3-fixtures.md) again, and in a
  real suite this would be a fixture.
- The first test asserts the **whole dictionary**, including the reason string. The reason is what the
  model will read and turn into a sentence for the customer, so it is part of the contract rather than
  a debug detail.
- `assert verdict is None, "returning anything but None replaces the tool call"` — `is None`, and a
  message, because a bare `assert verdict is None` failing prints `assert {...} is None`, which is true
  but does not say what the consequence is. The consequence is that the refund never happened.
- The third test parametrizes over two read tools, which is the *negative space* of the rule: the brake
  must not fire on anything outside `WRITE_TOOLS`. A policy that blocks everything passes the first
  test and fails this one.


## When it breaks

Change the policy to block every tool rather than only the write tools, and the negative-space test is
the one that catches it:

```text
E       AssertionError: assert {'status': 'blocked', 'reason': 'lookup_ticket needs approval first'} is None
```

Read what that failure means in the running system: every read the agent attempts is refused, the model
is told the lookup needs approval, and the customer is asked to authorise reading their own ticket. The
happy-path test still passes, because blocking a refund is still correct.

The mistake with no error text at all is the one this part is really warning about. Add a line at the
end of the hook — `self.seen.append(tool.name)` followed by `return self.seen` because a helper was
refactored — and the hook now returns a truthy list for **every** call. Every tool is skipped. Every
tool's "result" is a list of names. Nothing raises, the run completes, and the agent answers from
nothing.

The only thing standing between that and production is `assert verdict is None` on the allow path. A
suite that only tests the block path is green for all of it.

## In production

**Hook tests are written in pairs, always.** One assertion that it fires when it should and one that it
does not fire when it should not. That is not thoroughness for its own sake — the second one is the
test of the *condition*, and the condition is the part that gets broadened by accident when somebody
adds a tool name to a list.

**What changes at scale** is that hooks start interacting. Two plugins both offering
`before_tool_callback` are called in order, and the **first one that returns a value ends the chain** —
which means a permissive plugin registered ahead of a strict one silently disables it. Unit tests on
each plugin in isolation cannot see that; the test that can is one that builds the plugin list and asks
which verdict wins. Sutra has two plugins from today onward, a `Flight` recorder and a `Policy`, and
the order they are listed in is a design decision rather than a detail.

**The failure that only appears with real traffic** is the hook that is correct and slow. A
`before_tool_callback` that checks an approval in a database adds its latency to **every single tool
call**, and unit tests through a double return instantly. The rule of thumb worth carrying: anything on
the hot path of every call gets a stated budget, and anything that needs a network round trip does not
belong in a `before_*` hook without a cache.

**The review comment a senior engineer leaves:** *"there's no test for the case where the hook should do
nothing. Add `assert verdict is None` for an ordinary read tool, or the day someone broadens that
condition we'll find out from a customer."*

**The interview question:** *"how does an ADK callback tell the framework what to do?"* The answer that
shows you have written one: *"by what it returns. `None` means carry on, anything else replaces the
thing that was about to happen — the tool result, the model response, the persisted event. Which is why
the test I always write first is the one asserting it returned `None`, because a hook that
accidentally returns something doesn't crash, it just quietly stops the tool from running."*
