# 4.2 — Testing the hook that rescues

## One-line answer

An `on_tool_error_callback` needs **two** tests that look almost identical: one asserting it returns a
substitute for the failure it was designed for, and one asserting it returns `None` for a failure it
was not — because a hook that rescues everything is Day 21's swallowed exception wearing a plugin's
clothes.

## The story

The pharmacist reads the prescription, goes to the shelf, and comes back with a box that is not the
one written down.

She says so. *"We don't have that brand, this is the same medicine from a different maker, same
strength."* She puts a sticker on it, writes the substitution on the slip, and you leave with
something that works and a record of the fact that it is not what the doctor wrote.

Two things happened there and only one of them is the medicine. The other is the sentence. Without the
sentence you would go home believing you had the exact prescription, and when you next spoke to the
doctor you would both be describing different treatments — not because anything went wrong, but
because a fact was not passed along.

And there is a version of this that is not acceptable at all. If the prescription had been for
something she could not substitute — a controlled drug, a dose she is not permitted to guess at — the
correct outcome is not a different box. It is *"I can't fill this, go back to the doctor."* A pharmacy
that substituted for everything would be convenient and dangerous.

## The idea in plain language

[Day 21](../../../day-21-errors-surface-not-swallow/parts/01-who-hears-it/1.3-retry-substitute-escalate.md)
established that there are exactly three things a system can do about a failure: **retry**,
**substitute**, or **escalate**. And it established that a substitute must **say so** — the returned
value carries a status marking it as degraded, so nothing downstream mistakes it for a real answer.

`on_tool_error_callback` is where substitution happens in ADK. It receives the exception, and its
return value decides everything:

- Return a **dictionary** → the exception stops here, and that dictionary becomes the tool's result. A
  rescue.
- Return **`None`** → the exception carries on climbing to `on_agent_error_callback` and then
  `on_run_error_callback`, and finally out. An escalation.

So the hook is a **classifier with two outcomes**, and it has exactly two tests. What makes this part
worth its own document rather than a paragraph in the last one is that the second test is the one
people do not write, and it is the one that matters.

Here is why. A hook written as *"catch the error, return a friendly fallback"* looks responsible. It is
the swallowed `try`/`except` that
[21.4.1](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.1-the-swallowed-exception.md)
spent a whole part removing, moved one layer up where it is harder to see and applies to every tool at
once. A `ValueError` from a genuine bug in your own tool — a malformed article id, a bad cast, a typo
in a key — gets converted into *"the knowledge base is temporarily unavailable"*, and the bug lives
forever, because nothing ever goes red.

The test that prevents that is three lines: pass an error the policy never planned for, and assert
`verdict is None`.

There is a third assertion this part insists on, and it belongs to Day 21 rather than to pytest:
**assert on the marker, not just on the rescue.** A substitute that returns
`{"status": "degraded", ...}` and one that returns `{"articles": []}` both stop the exception. The
first makes the agent say *"I could not reach the knowledge base"*; the second makes it say
*"KB-104 has no content recorded"*, which is a false statement about the world. Only the assertion on
`status` can tell those two apart.

## Why Sutra needs it

Because Sutra's error policy is the single piece of code most likely to be quietly broadened.

It will be broadened by a good intention. A new failure appears in production, somebody adds it to the
rescue branch, and the easiest way to do that is to widen the `isinstance` check. Two or three of those
and the hook catches `Exception`, which means Sutra can no longer fail — and a system that cannot fail
is a system whose bugs are invisible, which is precisely the trap Day 21 was written to close.

`./m check` runs on every change. A test asserting that a `ValueError` is **not** rescued is what turns
that broadening from an invisible edit into a red line in the terminal, at the moment it is made, by
the person who made it.

## The mechanism

The rescue half of the same `Policy` from [4.1](4.1-the-return-value-is-the-contract.md).

```python
# days/day-23-testing-tools-and-callbacks/lab/hooks_demo.py
    async def on_tool_error_callback(
        self, *, tool: object, tool_args: dict[str, object], tool_context: object, error: Exception
    ) -> dict[str, object] | None:
        """Returning a dict rescues the run; returning None lets the exception keep climbing."""
        if isinstance(error, TimeoutError):
            return {"status": "degraded", "tool": tool.name, "detail": "knowledge base timed out"}
        return None
```

**Line by line:**

- The signature adds `error: Exception` to the three parameters `before_tool_callback` takes, and it is
  keyword-only like the rest. Verified against the installed `google-adk` 2.7.1 on 2026-09-04:
  `on_tool_error_callback(self, *, tool, tool_args, tool_context, error) -> Optional[dict[str, Any]]`.
- `isinstance(error, TimeoutError)` and **not** `except`-style breadth. The hook rescues one named
  class of failure. Everything else falls through to the `return None` on the last line, which is the
  escalation path.
- `TimeoutError` is Python's own built-in, which since 3.10 is the same object as
  `asyncio.TimeoutError` and `socket.timeout`. Choosing a standard exception rather than a custom one
  means a timeout raised by any library in the stack matches without a translation layer.
- `"status": "degraded"` is the marker, and it is the first key on purpose. This is Day 21's rule made
  mechanical: the returned dictionary announces that it is a substitute, so the model composing the
  reply has the fact available rather than having to infer it from an absence.
- `"tool": tool.name` puts the failing tool in the payload. When this dictionary reaches a log line
  ([Day 22](../../../day-22-structured-logging/parts/02-wiring-the-run/2.1-one-line-per-happening.md))
  the tool name is what makes the record answerable — *which* tool degraded, not *a* tool.
- `"detail"` is a fixed string rather than `str(error)`. The raw exception text of a database or HTTP
  client can carry a connection string, a query and its parameters, which is exactly the leak
  [22.3.1](../../../day-22-structured-logging/parts/03-failure-lab/3.1-the-log-that-leaked.md) measured.
  A hand-written detail is a deliberate sentence; `str(error)` is whatever the library felt like saying.
- `return None` explicitly on the last line, for the same reason as in
  [4.1](4.1-the-return-value-is-the-contract.md): the escalation path is a decision, and decisions
  should be visible.

The two tests, and they are deliberately near-identical so the difference stands out:

```python
# days/day-23-testing-tools-and-callbacks/lab/test_hooks_demo.py
def test_a_timeout_is_rescued_with_a_substitute_that_says_so() -> None:
    verdict = asyncio.run(
        Policy().on_tool_error_callback(
            tool=FakeTool("search_kb"),
            tool_args={},
            tool_context=None,
            error=TimeoutError("kb read timed out"),
        )
    )
    assert verdict is not None
    assert verdict["status"] == "degraded", "a substitute that does not say so is a lie (Day 21)"


def test_an_unexpected_error_is_not_rescued() -> None:
    verdict = asyncio.run(
        Policy().on_tool_error_callback(
            tool=FakeTool("search_kb"),
            tool_args={},
            tool_context=None,
            error=ValueError("malformed article id"),
        )
    )
    assert verdict is None, "rescuing an error you did not plan for is the swallow from Day 21"
```

**Line by line:**

- `error=TimeoutError("kb read timed out")` constructs a **real exception object**, not a string or a
  double. Exceptions are ordinary objects and constructing one costs nothing, so there is never a
  reason to fake one — and using the real class is what makes the `isinstance` check under test a real
  check.
- `assert verdict is not None` comes **before** the subscript. Without it, a hook that returned `None`
  would fail with `TypeError: 'NoneType' object is not subscriptable`, which is true but describes the
  test rather than the bug. Asserting the shape before reading into it is the presence-before-detail
  discipline.
- `assert verdict["status"] == "degraded"` is the Day 21 assertion. It is not checking that the rescue
  happened — the line above did that — it is checking that the rescue **announced itself**. A payload
  of `{"articles": []}` would pass the first assertion and fail this one, and the difference between
  them is an agent that says *"I could not reach the knowledge base"* and one that says *"KB-104 has no
  content recorded"*.
- The message quotes the rule rather than the expectation: *a substitute that does not say so is a
  lie*. A reader who hits this failure needs the principle, not a restatement of the assertion.
- The second test changes **one thing**: `TimeoutError` becomes `ValueError`. Everything else is
  identical, so the diff between the two tests is exactly the behaviour under examination.
- `assert verdict is None` with a message naming the failure mode. This is the whole point of the part,
  and without the message a future reader sees `assert {...} is None` and may well decide the test is
  out of date and delete it.

```bash
cd days/day-23-testing-tools-and-callbacks/lab

```

**Line by line:**

- `-k` matches on the test name substring, so this selects the pair rather than the whole file.

## When it breaks

Broaden the rescue — change `isinstance(error, TimeoutError)` to `isinstance(error, Exception)`, which
is the edit a well-meaning afternoon produces — and exactly one test goes red:

```text
E       AssertionError: rescuing an error you did not plan for is the swallow from Day 21
E       assert {'status': 'degraded', 'tool': 'search_kb', 'detail': 'knowledge base timed out'} is None
```

**The first test still passes.** Timeouts are still rescued, and every check of the intended behaviour
is green. Only the negative test can see what changed — and what changed is that a `ValueError` from a
bug in Sutra's own code is now reported to the customer as a knowledge-base outage, permanently.

Weaken the marker instead — return `{"articles": [], "tool": tool.name}` — and the other assertion
catches it:

```text
E       AssertionError: a substitute that does not say so is a lie (Day 21)
E       assert 'ok' == 'degraded'
E
E         - degraded
E         + ok
```

Except that this one only fires because the test asserts on `status` specifically. A test that checked
only `verdict is not None` would be perfectly green while the agent invented an empty knowledge base.

## In production

**The rescue list is a table, not a chain of `isinstance`.** Once there are four rescuable failures the
hook becomes unreadable and, worse, unorderable — `isinstance` checks are tried in source order and a
broad class listed early shadows the specific ones after it. The mature shape is a mapping from
exception class to substitute, and the test parametrizes over that mapping
([2.4](../02-pytest-house-rules/2.4-parametrize.md)), so a new entry gains a test automatically and the
"everything else escalates" test stays a single case.

**Rescue is per tool, not per system.** Substituting for a read is usually fine; substituting for a
**write** is not. If `issue_refund` times out, the honest answer is not a degraded success — the money
may or may not have moved, and only the payment provider knows. A production policy keys on
`tool.name` as well as on the exception class, and the test for it asserts that a write tool is never
rescued at all.

**What changes at scale** is that rescues need to be counted, not just tested. A substitute that fires
once a week is a resilience feature; the same substitute firing on a third of all requests is an outage
being hidden by your own error handling, and it will be hidden for as long as nobody is counting. That
is the metric side of [Day 22](../../../day-22-structured-logging/parts/04-in-production/4.1-what-to-log-and-what-to-count.md):
a counter on `status == "degraded"`, with an alert on the rate rather than on any single occurrence.

**The failure that only appears with real traffic** is the rescue that hides a retry storm. The hook
returns a substitute, the model sees a degraded result, decides to try a different tool, that one times
out too, and the invocation ends up making six calls where one failed. Each individual rescue is
correct; the aggregate is a system that responds to a slow dependency by asking it more questions.
Unit tests cannot see it, and the log can.

**The review comment a senior engineer leaves:** *"there's no test for an error this policy doesn't
know about. Add one that asserts `None`, or the first time someone widens that isinstance we'll stop
seeing real bugs."*

**The interview question:** *"how do you stop error handling from hiding bugs?"* The answer that shows
you have been bitten: *"the handler only catches the failure classes it has a plan for, everything else
re-raises, and there's a test asserting the everything-else case. The test that matters is the one
saying the handler did nothing — because the handler that catches too much never fails, it just makes
the system unable to report that anything is wrong."*
