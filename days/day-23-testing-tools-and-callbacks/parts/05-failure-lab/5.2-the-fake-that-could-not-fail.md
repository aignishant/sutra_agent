# 5.2 — 💥 The fake that could not fail

## One-line answer

A plain dictionary standing in for ADK's `State` treats `temp:` and `user:` identically, so
`'temp:raw_search' in fake.state` is **True** while the same key survives the turn **False** — a test
that is green about a value production throws away, and no error anywhere.

## The story

The padlock on the side gate closes with a very satisfying click.

You push the shackle down, it clicks, you give it a tug and it holds, and you walk away. You have done
this for months.

What you have never done is turn the key. The lock is one of those where the shackle snaps into the
body and *feels* closed, but the mechanism is only engaged when the key goes round. Pull hard enough
and it opens. The click was the shackle seating, not the lock locking.

Every check you performed was passed. The gate looked shut. It felt shut. And the thing you were
actually relying on — that a stranger could not open it — was never true for a single day.

## The idea in plain language

[3.2](../03-testing-tools/3.2-the-fake-tool-context.md) built a fake tool context with `state` as a
plain `dict`, and said it was enough. This part is where that claim gets its limit.

[Day 17](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.1-the-prefix-is-the-lifetime.md)
taught that in ADK the **prefix on a state key is its lifetime**:

| Prefix | Lives for |
| --- | --- |
| *(none)* | this session |
| `user:` | every session belonging to this user |
| `app:` | every session, everybody |
| `temp:` | **this invocation only — never written to storage** |

A plain dictionary knows nothing about any of that. It is a bag of keys. Write `temp:raw_search` into
it and it stays there for as long as the object lives, exactly like `user:reply_style`.

So a test that asks *"did my tool put this value somewhere it will survive?"* gets the answer **yes**
from the fake, for every prefix, including the one where the true answer is no. The assertion passes.
Nothing is raised. And the bug it was written to catch — a tool writing a value under `temp:` that the
next turn needs — is exactly the bug it cannot see.

This is the general shape and it is worth naming, because it is the one failure mode that makes fakes
dangerous rather than merely imperfect:

> **A double can only fail a test in the ways it was built to fail.** A double with no rules can fail
> in no ways, so a test using it proves the code ran, not that it was right.

It is the mirror image of [5.1](5.1-the-test-that-phoned-the-model.md). That part's test could go red
for reasons unrelated to the code; this part's test cannot go red at all for the thing it claims to
check. Both produce a suite nobody should trust, and this one is worse, because it produces *green*.

## Why Sutra needs it

Because Sutra's state layer is entirely built on prefixes, and its tool tests are entirely built on a
dictionary.

`sutra/state.py` from Day 17 declares `SEVERITY` and `TICKET_ID` unprefixed, `REPLY_STYLE` as `user:`,
`REFUND_WINDOW` as `app:` and `RAW_SEARCH` as `temp:` — four constants whose whole content is a prefix.
Day 18's `save_note` writes `note_file` and `note_version` unprefixed on purpose, because a note
pointer that vanished at the end of the invocation would make the artifact unreachable.

Every one of those decisions is a lifetime decision, and every one of them looks identical to a
`dict`. Which means the tests written this morning against `FakeToolContext` are green whether the
constants are right or wrong — and the day somebody "tidies up" `RAW_SEARCH` to be unprefixed, or
demotes `REPLY_STYLE` to `temp:`, the suite will say nothing at all.

## The mechanism

Run the same two tools against a dictionary and against ADK's real `State`, and put the framework's own
trimming code between the state and what gets stored.

```python
# days/day-23-testing-tools-and-callbacks/lab/drifted_fake.py
from google.adk.events.event import Event
from google.adk.events.event_actions import EventActions
from google.adk.sessions.in_memory_session_service import InMemorySessionService
from google.adk.sessions.state import State


class FakeToolContext:
    """The five-line double from 3.2, with a plain dict standing in for State."""

    def __init__(self) -> None:
        self.state: dict[str, object] = {}


class RealStateContext:
    """The same double, one layer more honest: ADK's own State object behind `.state`."""

    def __init__(self) -> None:
        self.state = State(value={}, delta={})


def carry_between_tools(raw: str, tool_context: object) -> None:
    """Hand a value from one tool to the next within one turn. `temp:` is the right prefix."""
    tool_context.state["temp:raw_search"] = raw


def remember_the_style(style: str, tool_context: object) -> None:
    """Remember an engineer's preference across every future session. `user:` is required."""
    tool_context.state["user:reply_style"] = style


def persisted(delta: dict[str, object]) -> dict[str, object]:
    """What ADK 2.7.1 actually writes, run through the framework's own trimming code."""
    event = Event(author="desk", actions=EventActions(state_delta=dict(delta)))
    service = InMemorySessionService()
    return service._trim_temp_delta_state(event).actions.state_delta
```

**Line by line:**

- `State(value={}, delta={})` constructs ADK's real state object directly. It takes the current values
  and a delta dictionary that records what this turn changed, which is the distinction a plain `dict`
  has no room for at all.
- `RealStateContext` differs from `FakeToolContext` by **one expression**. That is the whole
  experiment: same shape, same attribute name, one of them carries the framework's rules and one does
  not.
- Both tools take `tool_context` and write one key. Neither of them knows or cares which class is
  behind `.state` — which is duck typing working exactly as
  [1.3](../01-where-the-line-falls/1.3-the-seam.md) described, and exactly why the substitution is
  silent.
- `persisted()` builds a real `Event` with a real `EventActions` carrying the state delta, then runs it
  through `InMemorySessionService._trim_temp_delta_state`. That method is ADK's own, and reading its
  source on 2026-09-04 is what this part rests on: *"Removes temporary state delta keys from the
  event. This prevents temp-scoped state from being persisted."*
- The method is private, and using it in a lab script is a deliberate trade: the alternative is to
  build a full runner and drive an invocation, which would prove the same thing behind fifty lines of
  setup. **In `sutra/` this would not be acceptable** — a private API can move without warning — and
  the honest version of this check in a real suite runs one invocation through the public path.
- `State.to_dict()` is used as the delta at the call site because the state started empty, so
  everything in it was written this turn. There is no public accessor for the delta on `State` in
  2.7.1 — `has_delta()` exists, the delta itself does not — and inventing one would be worse than
  saying so.

**Line by line:**

- Imports ADK, makes no model call, needs no key.

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text
the dict fake keeps:   {'temp:raw_search': 'refund policy', 'user:reply_style': 'brief'}
the real State holds:  {'temp:raw_search': 'refund policy', 'user:reply_style': 'brief'}
ADK persists only:     {'user:reply_style': 'brief'}
State.has_delta():     True

green against the fake, and wrong about production:
    'temp:raw_search' in fake.state           -> True
    'temp:raw_search' survives the turn       -> False
    'user:reply_style' survives the turn      -> True

dict fake exposes  11: ['clear', 'copy', 'fromkeys', 'get', 'items', 'keys', 'pop', 'popitem', 'setdefault', 'update', 'values']
real State exposes 8: ['APP_PREFIX', 'TEMP_PREFIX', 'USER_PREFIX', 'get', 'has_delta', 'setdefault', 'to_dict', 'update']
only in State: ['APP_PREFIX', 'TEMP_PREFIX', 'USER_PREFIX', 'has_delta', 'to_dict']
```

**Look at the first two lines.** They are identical. The dictionary and the real `State` agree
completely about what is in memory, which is why the substitution is invisible in every test that
inspects `ctx.state` — and inspecting `ctx.state` is what every test in
[3.2](../03-testing-tools/3.2-the-fake-tool-context.md) does.

**The third line is where they part company.** `ADK persists only: {'user:reply_style': 'brief'}`. The
`temp:` key is gone. Not renamed, not moved: gone, by design, on purpose, and with nothing logged.

So the middle block is the failure in three lines. `'temp:raw_search' in fake.state` is `True` — a test
asserting it would be green. `'temp:raw_search' survives the turn` is `False`. **A test can be green
about a value that production throws away**, and the reason is that the double has no rule to break.

The last block is the tell you can look for. The two objects have almost disjoint surfaces: `dict`
offers `clear`, `copy`, `pop`, `popitem`, `keys`, `values`, `items` — seven methods `State` does not
have, so a tool calling any of them works in tests and raises in production. And `State` offers
`APP_PREFIX`, `USER_PREFIX`, `TEMP_PREFIX`, `has_delta` and `to_dict` — five members the fake does not
have, three of which are the very constants that encode the rules being tested.

## When it breaks

The interesting property of this failure is that **there is no error text to show**, and that is the
finding rather than an omission.

The nearest thing to a signal is what happens when a tool uses a method one side lacks. Call
`tool_context.state.to_dict()` in a tool and the fake raises:

```text
AttributeError: 'dict' object has no attribute 'to_dict'
```

Call `tool_context.state.pop("temp:raw_search")` and the real one raises the mirror image:

```text
AttributeError: 'State' object has no attribute 'pop'
```

Both are loud and both are easy to fix. They are also the *lucky* cases: the divergence happened to
be in the shape rather than in the behaviour. The dangerous divergence — a prefix meaning something —
produces no attribute error at all, because both objects support `__setitem__` and `__contains__` and
disagree only about consequences.

Which gives the diagnostic question, and it is worth memorising: **"what rule does the real thing have
that my double does not?"** For a state object it is prefixes. For a queue it is ordering and
redelivery. For an HTTP client it is timeouts and status codes. For a filesystem it is permissions and
case sensitivity. Every one of those is a rule, and a double without it is a padlock that clicks.

## In production

**The fix is a contract test, and it is the most valuable thing on this page.** One suite of assertions,
parametrized over two implementations — the fake and the real one — asserting the behaviour they must
share. Run it against the fake on every change and against the real thing on a schedule or behind a
`live` marker ([2.5](../02-pytest-house-rules/2.5-markers-and-the-not-live-line.md)). The two cannot
drift without something going red, which is the only durable answer to this problem.

**Use the framework's own fake wherever one exists.** ADK ships `InMemorySessionService`,
`InMemoryArtifactService` and `InMemoryMemoryService`, and they are maintained by the people who
maintain the real ones. A hand-written double is only worth writing when nothing is provided — and when
you do write one, the honest place for it is beside the production code, reviewed with the same
seriousness, rather than buried in a test file.

**What changes at scale** is that fakes accumulate quietly. Every service acquires one, each written by
whoever needed it that week, and after a year there are eleven doubles of varying fidelity and nobody
knows which are trustworthy. The teams that avoid this keep a rule: **one fake per collaborator, in one
place, with a contract test.** Eleven doubles with no contract tests is a suite that is green for
reasons unrelated to the system.

**The failure that only appears with real traffic** is precisely this part's failure, arriving as a
support ticket. The engineer's reply style resets every conversation, or a search result vanishes
between two tools in the same turn, and the suite is green throughout. Nothing in the logs says
"discarded"; the trimming is silent by design. The only way it gets found is somebody reading
`sutra/state.py` and noticing a prefix.

**The review comment a senior engineer leaves:** *"this fake is a dict, so the test passes whichever
prefix we use. If the prefix is the thing under test, use `State` — and if nothing tests the prefixes,
say so in the docstring so the next person knows what this suite does not cover."*

**The interview question:** *"how do you know your test doubles are correct?"* The answer that shows
you have been burned: *"contract tests — the same assertions run against the fake and against the real
implementation, the second one on a schedule rather than on every commit. Without that, a fake is a
statement of what I believed the dependency did on the day I wrote it, and the test that uses it can
only fail in the ways I anticipated."*
