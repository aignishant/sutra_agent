# 5.1 — 💥 The test that phoned the model

## One-line answer

The same test file ran three ways on 2026-09-04: deselected it was **green in 1.04 seconds**; with no
key it was **red with `ValueError: No API key was provided`**; and with a real key it was red twice
more, first with `503 UNAVAILABLE` because the provider was busy and then with
`429 RESOURCE_EXHAUSTED … quotaValue: '20'` because the day's free requests were gone — three
failures, none of them about the code under test.

## The story

You wake up with a headache and you want to know whether you have a fever.

There is a thermometer in the drawer. It takes a moment, it costs nothing, and it gives you a number
you can compare with the number from yesterday.

The other option is to ring the clinic. That takes a while to get through, somebody has to be free to
speak to you, they will ask you questions, and at the end of it a person who cannot see you will offer
an opinion. Ring twice in one morning and you may get two different opinions, both reasonable. Ring on
a busy day and you will not get through at all.

The clinic is not worse than the thermometer. It is for something else. Using it to answer a question
the thermometer answers is how you end up knowing less, slower, at greater cost — and how you end up
not checking at all on the days when the line is engaged.

## The idea in plain language

A test that calls a real model breaks all three properties from
[1.2](../01-where-the-line-falls/1.2-fast-isolated-specific.md) at once, and it is worth being precise
about *how*, because "don't call the network in tests" is advice everybody has heard and many people
ignore.

**It is not fast.** One TLS handshake to the model host was measured at 419 ms before any question was
asked. A generation on top of that is a second or more. Multiply by however many tests, and the suite
crosses the threshold at which running it becomes a decision rather than a reflex.

**It is not isolated**, in four separate ways, each of which produces a red build with correct code:

1. **No key.** The default state of a continuous-integration machine.
2. **Provider unavailable.** A `503` because the model is busy. Nothing you did.
3. **Quota exhausted.** A `429` when the day's twenty free requests are gone — and the day's requests
   include the ones your own suite spent.
4. **A different answer.** The model is not obliged to say the same thing twice.

**And it is not specific.** When it goes red, the first question is not *"what did I break"* but
*"is it me or is it them"* — and answering that costs a re-run, which costs another request.

The consequence is the thing worth remembering. A suite that fails for reasons unrelated to the code
does not get fixed; it gets **ignored**. And a suite that is ignored is worse than no suite at all,
because everybody believes it is protecting them.

## Why Sutra needs it

Because Sutra's `./m check` is about to become the gate that every change passes through, and this is
the single mistake that would destroy it.

The arithmetic is brutal and worth doing out loud. The free tier allows **20 generate requests per day
per model** — the number is not from a marketing page, it was read off a live `429` body on Day 9 and
confirmed again today. One live test in the suite, run on every change, at ten changes a day, is fifty
percent of the entire daily allowance spent on a check that a dictionary lookup still works. Add a
second live test and the allowance is gone before lunch, at which point **the agent you are building
cannot be run**, because your tests ate the quota it needed.

That is not a hypothetical. It happened on the day this part was written, and the evidence is below.

## The mechanism

The lab already contains the offending test — the `@pytest.mark.live` one in `test_markers_demo.py`
([2.5](../02-pytest-house-rules/2.5-markers-and-the-not-live-line.md)). This part runs it three ways on
purpose and records what each one costs.

```python
# days/day-23-testing-tools-and-callbacks/lab/phoned_the_model.py
MODEL = "gemini-3.7-flash"  # free tier, 20 requests per day; re-verified 2026-09-04
PROMPT = "In one sentence, what should a support agent do first with ticket 4521?"


def ask(client: genai.Client) -> tuple[str, float]:
    """One generation, with the 429 handling Addendum 02 requires of every call path."""
    for attempt in range(3):
        start = time.perf_counter()
        try:
            reply = client.models.generate_content(model=MODEL, contents=PROMPT)
        except errors.ClientError as exc:
            if exc.code != 429:
                raise
            wait = 2**attempt
            print(f"429 on attempt {attempt + 1}; backing off {wait}s then retrying")
            time.sleep(wait)
            continue
        return (reply.text or "").strip(), time.perf_counter() - start
    raise RuntimeError("three 429s in a row - this is the daily ceiling, not the per-minute one")
```

**Line by line:**

- `MODEL` is pinned to `gemini-3.7-flash` with the date it was re-checked. Verified on 2026-09-04 by
  listing the provider's models live, not from memory: it is still there. Addendum 02 requires the
  lookup because free rosters move, and a model string that quietly stops existing fails as a `404`
  that looks like a bug in your code.
- `if exc.code != 429: raise` — every error that is **not** a rate limit is re-raised immediately.
  That is Principle 10: this function handles one thing and refuses to become a general-purpose
  swallower, which is exactly the rule [4.2](../04-testing-hooks/4.2-testing-the-hook-that-rescues.md)
  tests for in a hook.
- `wait = 2**attempt` gives 1, 2, 4 — **exponential backoff**, so a per-minute ceiling has a chance to
  clear while a per-day ceiling is abandoned quickly instead of being hammered.
- The `raise RuntimeError` after the loop names the diagnosis rather than the symptom. Three `429`s in
  a row separated by growing waits is not a burst limit; it is the daily one, and Day 21's classifier
  exists because those two need different responses.
- `time.perf_counter()` around only the call itself, so the number reported is the provider's latency
  rather than the script's.
- `(reply.text or "").strip()` guards against `reply.text` being `None`, which happens when a response
  is blocked or empty. Without the guard the failure is `AttributeError: 'NoneType' object has no
  attribute 'strip'`, several lines away from the cause.

Now the three runs.

**Run one — the way `./m check` does it.** The live test is deselected:

```bash
cd days/day-23-testing-tools-and-callbacks/lab
uv run python -m pytest test_markers_demo.py -m "not live"
```

**Line by line:**

- `-m "not live"` is the same filter that has been in `./m check` since Day 0.

```text
...                                                                      [100%]
3 passed, 1 deselected in 1.04s
```

**Run two — the same file on a machine with no key**, which is what CI is:

```bash
GOOGLE_API_KEY= GEMINI_API_KEY= uv run python -m pytest test_markers_demo.py
```

**Line by line:**

- No marker filter. The live test is collected and run, and there is no credential for it.

```text
E         ValueError: No API key was provided. Please pass a valid API key. Learn how to create an API key at https://ai.google.dev/gemini-api/docs/api-key.

..\..\..\.venv\Lib\site-packages\google\genai\_api_client.py:831: ValueError
=========================== short test summary info ===========================
FAILED test_markers_demo.py::test_the_model_actually_answers - ValueError: No...
1 failed, 3 passed in 2.23s
```

**Run three — with a real key, on a real free tier, on a real day.** Twice:

```bash
uv run python phoned_the_model.py
```

**Line by line:**

- Two generations, same prompt, so the third line of its output would say whether an assertion written
  against the first answer would still hold for the second.

Measured on 2026-09-04, first attempt:

```text
google.genai.errors.ServerError: 503 UNAVAILABLE. {'error': {'code': 503, 'message': 'This model is currently experiencing high demand. Spikes in demand are usually temporary. Please try again later.', 'status': 'UNAVAILABLE'}}
```

And immediately afterwards, second attempt:

```text
RuntimeError: three 429s in a row - this is the daily ceiling, not the per-minute one
```

The body behind those `429`s, captured directly:

```text
429 RESOURCE_EXHAUSTED. {'error': {'code': 429, 'message': 'You exceeded your current quota, please check your plan and billing details. ... * Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests, limit: 20, model: gemini-3.7-flash\nPlease retry in 26.45714483s.', 'status': 'RESOURCE_EXHAUSTED', 'details': [..., {'@type': 'type.googleapis.com/google.rpc.QuotaFailure', 'violations': [{'quotaMetric': 'generativelanguage.googleapis.com/generate_content_free_tier_requests', 'quotaId': 'GenerateRequestsPerDayPerProjectPerModel-FreeTier', 'quotaDimensions': {'model': 'gemini-3.7-flash', 'location': 'global'}, 'quotaValue': '20'}]}, {'@type': 'type.googleapis.com/google.rpc.RetryInfo', 'retryDelay': '26s'}]}}
```

**So the demonstration failed, and the failure is the demonstration.**

This part set out to show that two calls to the same model with the same prompt can return two
different sentences. It never got two calls. The first attempt met a `503` because the provider was
busy; the second met the daily ceiling. Whether the model would have said the same thing twice is
**still unknown**, and finding out has to wait for tomorrow's quota — which is itself the point, made
more forcefully than a pair of differing sentences would have made it.

Read `quotaId: 'GenerateRequestsPerDayPerProjectPerModel-FreeTier'` and `quotaValue: '20'`. That is
Day 21's per-day ceiling, named by the provider in its own words. The `retryDelay: '26s'` beside it is
the trap that day measured: a suggestion that sounds like a window reset and is not, which is why
`ask()` gives up after three attempts instead of sleeping through the afternoon.

**What this would have looked like inside a test suite.** Two red tests. A traceback pointing at
`_api_client.py`. A `503` and a `429`, neither of which is a defect in `lookup_ticket`. And an engineer
re-running the suite to see if it passes this time — spending more of the quota that was already gone.

## When it breaks

The version of this failure that costs the most is not the red build. It is the **flaky** one.

A live test that passes most of the time and fails occasionally does not get deleted; it gets re-run.
People learn the incantation — *"just run it again"* — and within a month that incantation is applied
to every red build, including the real ones. The suite has not become useless because it is wrong; it
has become useless because nobody believes any individual failure.

The second-worst version is the assertion on model prose. The sentence below came from a **stub**, not
from a model — today's quota was gone before it could be captured live, and inventing a transcript is
not an option (Principle 10). The failure *shape* is real and is what matters:

```text
E       AssertionError: assert 'refund' in 'You should begin by reviewing the ticket history.'
E        +  where 'You should begin by reviewing the ticket history.' = stub_reply()
```

Picture that line with a real model behind it. The test is red and the code is fine: the model said
something reasonable that did not contain the word the test wanted. There is no fix that makes it reliable — loosening the assertion until it always
passes turns it into a test that asserts the model returned *some* text, which is not worth a request.
Model behaviour is measured by evals, in Phase 12, which score many samples and expect variation;
asserting on it in a unit test is using the wrong instrument.

## In production

**Live tests exist, and they are not in the same lane.** The mature arrangement is three lanes: a unit
suite on every save with no credentials at all; an integration suite on merge, against fakes or a
recorded transcript; and a small live suite on a schedule, with a real key, a budget, and an owner who
is notified when it fails. The live lane's job is to detect that the *provider* changed — a retired
model, a new response shape, a moved error code — which is a real risk and is not what unit tests are
for.

**The recording is what most teams reach for.** Capture a real exchange once, save the response as a
fixture, and replay it in tests. That is what Sutra has been doing since Day 21 with its recording
models, and it is why today's suite runs offline. It costs one request, once, and it turns the model
into a stub ([1.4](../01-where-the-line-falls/1.4-four-doubles.md)). The discipline that keeps it
honest is re-recording on a schedule, because a fixture captured a year ago describes a model that no
longer exists.

**What changes at scale** is that the money becomes visible. A hundred engineers running a suite with
one live test each is not a quota problem, it is a line item — and the first time it appears on a bill
somebody will fix it in an afternoon. On a free tier there is no bill, so the feedback arrives as
*"the agent stopped working this afternoon"*, which is harder to trace back to its cause.

**The failure that only appears with real traffic** is the live test that becomes the load. A scheduled
live suite running every few minutes against a rate-limited endpoint is itself the reason the endpoint
rate-limits you, and the alert it raises is about a problem it created.

**The review comment a senior engineer leaves:** *"this test needs a key and a request. Mark it `live`,
record the response as a fixture, and write the offline version — otherwise it runs in CI, fails, and
someone turns the whole suite off."*

**The interview question:** *"have you ever had a test suite people stopped trusting?"* The answer with
a war story in it: *"we had model calls in the unit suite. It was red maybe one run in five — a 503, a
429, or the model phrasing something differently — and within a month the team's reflex for any red
build was to re-run it. That reflex is the damage. We moved the model behind a fake, recorded one real
response as a fixture, and put the live checks on a nightly schedule with an owner. The unit suite went
from about ninety seconds to under two, and a red build meant something again."*
