# 6.1 — Coverage is a map, not a score

## One-line answer

Twenty lines of `ast` say that **11 of Sutra's 25 public functions are named anywhere in `tests/`**,
and the useful part of that measurement is not the 44% — it is the list of the fourteen that are not,
which turns out to be almost entirely `main()` and demo functions that nobody should be testing.

## The story

The shop does a stock-take on the last Sunday of the month, and there are two ways to do it.

The first is to walk every aisle with a clicker and count how many shelves you passed. At the end you
have a number. The number goes up if you walk more aisles. It tells you that you were thorough, and it
tells you nothing about the shop.

The second is to go down the list of things the shop sells and, for each one, find it. Twelve of the
sixteen kinds of rice are where they should be. Two are on the wrong shelf. One has been out of stock
for a fortnight and nobody noticed because it never got asked for at the counter. One is there but the
price label is from last year.

The second takes the same afternoon and produces a **list of things to do**. The first produces a
number to report.

## The idea in plain language

**Code coverage** is the proportion of your code that ran while the tests ran. A tool watches the
interpreter, records which lines were executed, and prints a percentage.

It is genuinely useful, and it is misused more than almost any other measurement in software, for one
reason: **it measures execution, not assertion.** A line that ran while nothing checked its result is
covered. So this test gives 100% coverage of the function below it:

```
def test_it_runs():
    lookup_ticket("4521")
```

No assertion. No claim. Full marks.

Which leads to the rule this part is about. Coverage is a **map** — it tells you where the untested
country is — and it is a terrible **score**, because the moment a number becomes a target people
optimise the number. A team asked to reach 90% will reach 90%, and the last stretch will be made of
tests that execute code without asserting anything about it, because those are the cheapest kind to
write.

There is a second, subtler problem with the percentage: it treats every line as equally worth testing.
It counts `main()`, demo scripts, `__repr__`, logging calls and the error branch that decides whether a
customer's refund is retried, and it gives them all the same weight. The refund branch matters
enormously and `main()` does not, and no percentage can tell you which is which.

So the version of the measurement worth having is the list, not the number: **which named pieces of
behaviour has nobody written a sentence about?** That question can be answered with the standard
library alone, and the answer is short enough to read.

## Why Sutra needs it

Because Day 31's `./m check` gate is where a coverage threshold would naturally be added, and the
decision about whether to add one should be made deliberately rather than by habit.

Sutra has a rule that matters more than a percentage: `sutra/x.py` is tested by `tests/test_x.py`. That
mapping means a missing test file is visible in a directory listing, and it means "what tests this?" is
answered by a filename rather than by a report. A gap that a person can see is worth more than a gap
that a tool reports, because the person can also see whether the gap matters.

And Sutra has an honest reason to look at the gaps today rather than later. Days 17 to 22 each ended
with a build brief telling you to write a module and its tests. This part is how you find out which of
those you actually did.

## The mechanism

No new dependency. `ast` for the code, plain text search for the tests.

```python
# days/day-23-testing-tools-and-callbacks/lab/untested_map.py
import ast
from pathlib import Path

ROOT = Path(__file__).resolve().parents[3]
PACKAGE = ROOT / "sutra"
TESTS = ROOT / "tests"


def public_functions(path: Path) -> list[str]:
    """Top-level `def`s whose names do not start with an underscore."""
    tree = ast.parse(path.read_text(encoding="utf-8"))
    return [
        node.name
        for node in tree.body
        if isinstance(node, ast.FunctionDef | ast.AsyncFunctionDef)
        and not node.name.startswith("_")
    ]


def main() -> None:
    corpus = "\n".join(p.read_text(encoding="utf-8") for p in sorted(TESTS.rglob("test_*.py")))
    named = total = 0
    for path in sorted(PACKAGE.rglob("*.py")):
        funcs = public_functions(path)
        if not funcs:
            continue
        missing = [f for f in funcs if f not in corpus]
        total += len(funcs)
        named += len(funcs) - len(missing)
        rel = path.relative_to(ROOT).as_posix()
        mark = "ok " if not missing else "GAP"
        print(f"{mark} {rel:<26} {len(funcs) - len(missing)}/{len(funcs)}  missing: {missing}")
    print(f"\n{named} of {total} public functions are named in tests/ ({named / total:.0%})")
```

**Line by line:**

- `tree.body` rather than `ast.walk(tree)`, unlike
  [1.1](../01-where-the-line-falls/1.1-the-nondeterminism-excuse.md)'s script. Here we want **top-level**
  functions only: a nested helper inside another function is an implementation detail, and demanding a
  test that names it would be demanding a test of something private.
- `not node.name.startswith("_")` for the same reason. A leading underscore is Python's way of saying
  *this is not part of the interface*, and testing through the public surface is what lets an
  implementation change without the suite going red.
- `corpus` is every test file concatenated into **one string**, and the check is `f not in corpus`. That
  is a deliberately crude test — a substring search, not an import graph — and its crudeness is a
  feature: it is twenty lines with no dependency, and being *named* in a test is a reasonable proxy for
  being *thought about* by one.
- It is crude in a specific direction, and worth knowing which. A function named `get` would match the
  word `get` anywhere in any test file, so short generic names produce **false "ok"s**. It never
  produces a false GAP, so every line marked GAP is real and the total is an upper bound.
- `if not funcs: continue` skips files with no functions at all — `__init__.py`, and Day 4's
  `tools.py`, which is pure declarations. Printing a `0/0` row for them would add noise and a division
  by zero to the summary.
- `mark = "ok " if not missing else "GAP"` puts the verdict in the first column, so the output can be
  read by scanning down the left edge rather than by parsing every line.
- `missing: {missing}` prints **the names**, which is the entire difference between this and a coverage
  percentage. A number tells you there is work; a list tells you what the work is.

**Line by line:**

- Reads files, parses them, searches strings. No dependency, no import of `sutra` itself — so a module
  that would fail to import is still mapped.

Measured on 2026-09-04:

```text
GAP sutra/agent.py             1/2  missing: ['main']
ok  sutra/config.py            4/4  missing: []
GAP sutra/desk/multi_turn.py   0/2  missing: ['two_turns_one_session', 'main']
GAP sutra/desk/run_once.py     2/4  missing: ['ask_once', 'main']
GAP sutra/loop.py              3/4  missing: ['main']
GAP sutra/mechanics.py         1/9  missing: ['demo_ask', 'demo_tokens', 'demo_thinking', 'demo_memory', 'demo_server_state', 'demo_sampling', 'demo_capped', 'main']

11 of 25 public functions are named in tests/ (44%)
The gaps are a reading list. The percentage is not a target.
```

**Now read the list instead of the number, and watch the 44% dissolve.**

Five of the six GAP rows are `main()`. A `main()` that parses no arguments and calls one function is an
entry point, not behaviour; a test that asserted it printed something would be pinning the shape of a
demo. Seven more are `demo_*` functions in `sutra/mechanics.py` — Day 2's demonstration file, which
[1.1](../01-where-the-line-falls/1.1-the-nondeterminism-excuse.md) already identified as 9 of 10
model-touching and therefore the one module where evals rather than unit tests are the right
instrument.

Strip those out and the real gaps are **two**: `two_turns_one_session` and `ask_once`. Both drive a
conversation, both are the kind of thing an integration test covers rather than a unit test, and both
are now a decision rather than an oversight.

Meanwhile `sutra/config.py` is 4 of 4, which is the number that would have been invisible in an
aggregate. It is also the module most likely to break somebody's evening, so being fully named is
exactly right.

**The percentage said 44% and the truth is that two functions are genuinely uncovered.** That gap
between the number and the answer is the whole argument.

## When it breaks

Run this on a repository whose `tests/` directory does not exist yet and the honest failure appears
immediately:

```text
ZeroDivisionError: division by zero
```

because `total` is zero when nothing has any public functions. That is the same guard
[1.1](../01-where-the-line-falls/1.1-the-nondeterminism-excuse.md) needed, and it is a reminder that
"no data" and "zero percent" are different answers that a naive script conflates.

The failure mode of the *idea*, rather than the script, is the false "ok". A function called `run`,
`get` or `main` will match the substring somewhere in almost any test file, and the report will call it
covered. That is why the output ends with the sentence it does: this is a reading list. Anything it
marks GAP is genuinely unnamed; anything it marks ok deserves a glance rather than trust.

## In production

**Teams that use coverage well use it as a diff.** Not "we are at 78%" but "this pull request adds
forty lines and covers six of them". The absolute number is noise; the change is a conversation. Most
CI tools can report exactly that, and it is the only form of the metric that survives contact with
people whose promotions depend on it.

**Branch coverage beats line coverage** and is worth asking for specifically. A one-line `if` that is
only ever entered on the true path shows as fully covered by line, and the false path — which is where
the refund does not happen, the retry is skipped, the write is blocked — has never run. Every
interesting bug in this day's material lives on a branch.

**What changes at scale** is what you measure instead. Large systems stop asking "is this line covered"
and start asking "is this *behaviour* covered": one test per rule in the specification, tracked
deliberately. That is what
[22.4.3](../../../day-22-structured-logging/parts/04-in-production/4.3-testing-that-you-logged.md)
gestured at with a test pinning the set of event names a system may emit — a test about the vocabulary
rather than about the lines.

**The failure that only appears with real traffic** is the code that is 100% covered and wrong.
Coverage cannot see a missing test, only an unexecuted line, so the entire class of bug where you
**forgot a case** is invisible to it. The unknown ticket id, the whitespace, the second save, the error
you did not plan for — every one of those is a test that does not exist, and no coverage report has
ever mentioned a test that does not exist.

**The review comment a senior engineer leaves:** *"coverage went up but I can't find an assertion about
the not-found path. What does this test actually claim?"*

**The interview question:** *"what coverage do you aim for?"* The answer that shows judgement rather
than compliance: *"I don't aim for a number, because coverage measures execution and not assertion — a
test with no asserts gets full marks. I use it as a map: which branches never ran, and which of those
matter. On a pull request I care that new logic came with tests; across the repository I care that the
error paths are covered, because those are the ones nobody exercises by hand."*
