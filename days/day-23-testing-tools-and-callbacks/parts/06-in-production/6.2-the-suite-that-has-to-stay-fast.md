# 6.2 — The suite that has to stay fast

## One-line answer

Sutra's whole suite runs in **6.02 seconds** and its slowest test takes **0.02** — because
`from google.adk.agents import LlmAgent` costs **5.74 seconds** on its own, which means the suite's
wall clock is almost entirely one import and speeding up the tests would change nothing.

## The story

The hot tap in the upstairs bathroom takes a while to run warm.

Nobody has ever measured it. What happened instead is that everyone in the house quietly stopped using
it. You wash your hands in cold water, because standing there with your hand under the tap waiting
feels longer than it is, and cold water is fine, really.

Nobody decided this. There was no conversation about the boiler. The tap works perfectly and the water
does eventually come through hot, and the household has simply reorganised itself around not waiting.

The interesting part is that if you asked anyone whether the hot water works, they would say yes.

## The idea in plain language

A test suite has one property that determines whether it is used, and it is not correctness. It is
**how long you have to wait**.

Under a couple of seconds, running the suite is a reflex. You save, you run, you look. Above ten or
so, it becomes a decision — you batch up changes first, and when the red bar appears you no longer know
which of the five changes caused it. Above a minute, it moves to "before I push", and the feedback that
was worth having arrives after the mistake has been built on. Nobody announces any of these
transitions. Like the tap, the household reorganises itself.

Which makes suite speed an ordinary engineering problem with a measurement in front of it, and the
measurement usually surprises people. **The time is rarely in the tests.**

Where it actually goes:

**Import time.** Every test session imports the modules under test and everything they import. A
framework with a large import graph is paid for once per session, before a single assertion.

**Collection.** pytest imports every test module to find the tests. A module that constructs something
expensive at import time pays that cost even when its tests are deselected.

**A handful of slow tests.** Real sleeps, real network, real filesystem. These are visible and are what
people assume the answer is.

**And process startup**, which is small until you multiply it by a hundred parallel workers.

`--durations=N` prints the slowest N. Comparing that number with the total is the diagnosis: if the
slowest test is a tiny fraction of the run, the run is not made of tests.

## Why Sutra needs it

Because `./m check` is the gate — ruff, format, pytest, depth, trace, wiki — and it runs on every
change from Day 31 onward. Everything in it competes for the same patience.

Today the suite is small enough that speed feels like a non-problem, and that is exactly the moment to
measure it, because the number only ever goes one way. Sutra will add tests for state, artifacts,
context, errors, logging, quota, skills and MCP over the next fifty days. Knowing today that the
baseline is one import rather than the tests themselves means that when the suite becomes slow, the
first place to look is already known.

## The mechanism

Time the imports in fresh processes, then run the real suite and compare.

```python
# days/day-23-testing-tools-and-callbacks/lab/suite_speed.py
import subprocess
import sys
import time
from pathlib import Path

ROOT = Path(__file__).resolve().parents[3]


def time_import(statement: str) -> float:
    """Seconds for one import, measured in a fresh interpreter so nothing is cached."""
    start = time.perf_counter()
    subprocess.run([sys.executable, "-c", statement], check=True, capture_output=True)
    return time.perf_counter() - start


def main() -> None:
    baseline = time_import("pass")
    adk = time_import("from google.adk.agents import LlmAgent")
    stdlib = time_import("import json, logging, asyncio")

    print(f"a bare interpreter starts in            {baseline:.2f}s")
    print(f"+ import json, logging, asyncio         {stdlib:.2f}s")
    print(f"+ from google.adk.agents import LlmAgent {adk:.2f}s")
    print(f"the framework import alone costs        {adk - baseline:.2f}s")
```

**Line by line:**

- Each import runs in a **fresh subprocess**. Timing an import inside the current interpreter measures
  nothing after the first one, because `sys.modules` caches it — the second import of anything is
  instant and the number is a lie.
- `time_import("pass")` establishes the **baseline**: what it costs to start Python at all. Without it
  the framework number includes interpreter startup and looks worse than it is; the subtraction at the
  end is what makes the figure attributable.
- `sys.executable` rather than `"python"`. Inside a virtual environment those are different
  interpreters, and measuring the wrong one measures the wrong package set.
- `capture_output=True` keeps the child's output out of the report. `check=True` means a failed import
  raises rather than being silently timed as a fast success — which is a real hazard, because a
  `ModuleNotFoundError` returns very quickly.
- `import json, logging, asyncio` is the control. Three standard-library modules of a size comparable
  to what a small project imports, so the framework figure has something to be compared against rather
  than being a number on its own.
- `{value:.2f}s` everywhere: two decimal places, because measuring this to the millisecond implies a
  precision that process startup does not have.


**Put those two numbers side by side. The suite takes 6.02 seconds and the slowest thing in it takes
0.02.** Thirty-two tests, and if every one of them were made infinitely fast the run would still take
about six seconds, because 5.74 of those seconds are `from google.adk.agents import LlmAgent`.

That single fact reorganises what "make the suite faster" means here. Optimising an assertion would be
pointless. The lever that exists is **which tests import ADK at all** — and it turns out most do not
need to. Every test written today runs against doubles ([3.2](../03-testing-tools/3.2-the-fake-tool-context.md),
[4.1](../04-testing-hooks/4.1-the-return-value-is-the-contract.md)) and imports nothing from the
framework, which is why the lab files run in a fifth of a second while the repository suite takes six.

That is not a happy accident of testing style. **Testing at the seam is also what makes the suite
fast**, and the two arguments — testability and speed — turn out to be the same argument seen from
different sides.

## When it breaks

The failure is gradual and has no error text at all, which is why it needs a number watching it. A
suite does not announce that it has crossed from three seconds to three minutes; it arrives one test at
a time, and the moment people stopped running it locally is invisible in the history. The only symptom
is a sentence in a stand-up — *"I'll just push it and see what CI says"* — and by then the habit has
already changed.

There is one genuine error worth recognising, because it appears the first time somebody tries to fix
speed with parallelism. Reproduced on 2026-09-04 with two SQLite connections to one file, which is what
two test workers sharing a database look like:

```text
sqlite3.OperationalError: database is locked
```

That, and its cousins — a port already in use, a file written by two tests at once — are not
parallelism bugs. They are pre-existing isolation bugs
([2.3](../02-pytest-house-rules/2.3-fixtures.md)) that a serial run was hiding, and the fix is the
fixture rather than going back to one worker.

## In production

**The number gets a budget and the budget gets a test.** Some teams fail the build if the unit suite
exceeds a stated wall clock; more commonly the CI report prints the total and somebody notices a jump.
Either way the point is that *someone owns the number*, because the alternative is that everybody
tolerates a small increase and nobody is responsible for the sum of them.

**Parallelism is the standard answer and it is a second-order one.** `pytest-xdist` splits the suite
across processes and typically gives a large speedup — and every worker pays the import cost again, so
on a suite dominated by imports the gain is smaller than expected. Fixing what gets imported comes
first; splitting what remains comes second.

**What changes at scale** is that the suite stops being one thing. A large project runs a fast lane on
every save, a full lane on every push, and a nightly lane for the slow and live tests — the same
three-lane arrangement [5.1](../05-failure-lab/5.1-the-test-that-phoned-the-model.md) describes for
credentials, now applied to time. The markers from
[2.5](../02-pytest-house-rules/2.5-markers-and-the-not-live-line.md) are how the lanes are defined, and
this is the second reason that day's `slow` marker exists alongside `live`.

**The failure that only appears with real traffic** is the suite that is fast for the person who wrote
it and slow for everybody else. A warm import cache, a populated `.pytest_cache`, a local database
already running — all of these make the author's run unrepresentative. The number that matters is from
a cold checkout on a machine that has never run it, which is what CI does every time and what nobody
does locally.

**The review comment a senior engineer leaves:** *"this test imports the whole agent module to check a
string helper. Import the helper directly and it stops paying the framework's import cost."*

**The interview question:** *"your test suite has got slow. What do you do first?"* The answer that
shows you have actually done it: *"measure before changing anything — `--durations` and the total. If
the slowest tests add up to a small fraction of the run, the time is in imports and collection, not in
the tests, and optimising assertions would be wasted work. On the last project I looked at, the
framework import was most of the wall clock and the fix was making sure unit tests didn't import the
framework at all."*
