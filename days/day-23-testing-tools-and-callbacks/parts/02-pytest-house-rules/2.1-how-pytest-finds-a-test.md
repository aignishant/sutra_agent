# 2.1 — How pytest finds a test, and why `assert` is enough

## One-line answer

pytest collects any function whose name starts with `test_` in any file whose name starts with
`test_`, and it rewrites your plain `assert` statements so that a failure prints the **values that
were compared** rather than the word `False`.

## The story

The register in a classroom is read out from a list, and the list has one rule: you are on it if
somebody wrote your name on it.

Nobody stands at the door deciding who counts as a pupil. There is no discussion each morning about
whether the boy who only comes on Thursdays should be called. The teacher reads the names in order,
each name gets a mark, and at the end there is a row of marks that anyone can total.

The rule is boring on purpose. Because it is boring, a substitute teacher can take the register on
their first day without being told anything, and because nobody has to think about it, nobody argues
about it.

Two things follow. If your name is on the list, you get called whether or not anyone remembers you
should be. And if your name is not on the list, you are not called — and you can stand at the back of
the room all year, present, uncounted, and nobody will notice.

## The idea in plain language

**pytest** is a program you run. It looks through your project for tests, runs each one, and prints a
dot for each pass and an `F` for each failure. It is a *test runner*: it does not know anything about
your code, it only knows the naming rule.

The rule has three parts and no exceptions:

1. **Files** whose names match `test_*.py` (or `*_test.py`) are searched.
2. Inside them, **functions** whose names start with `test_` are collected. So are classes named
   `Test*`, and methods inside them starting with `test_`.
3. Everything else in the file is left alone. Helper functions, constants, imports — pytest walks past
   them, and they are yours to use.

That is the whole of the convention. It is worth stating so plainly because the convention **is** the
configuration: there is no list of tests to maintain, no registration call, no decorator required.
Add a function with the right name and it is in the suite. Rename it and it is out, silently — which
is the second half of the register story, and a real way for a test to disappear.

The second idea is about the word `assert`.

In most testing libraries you compare values by calling a method — `assertEqual(a, b)`,
`expect(a).toBe(b)` — and the reason is technical: if you wrote a plain `assert a == b`, the language
would evaluate `a == b` down to `True` or `False` before the assertion saw it, and a failure could
only report *False*, which tells you nothing.

pytest solves this with **assertion rewriting**. When it imports a test file it rewrites the file's
compiled form, replacing each `assert` with code that remembers the sub-expressions. So `assert a == b`
fails with both values printed, and a chain of calls fails with every intermediate result printed. You
write the language's own keyword and get a better failure message than a method call would have given
you.

One consequence worth knowing now: rewriting happens at **import** time, and only for files pytest
recognises as test files. An `assert` inside a helper module that pytest merely imports is not
rewritten, so it fails with the bare message. If you want rich output from assertions in a shared
helper, the helper has to be registered with `pytest.register_assert_rewrite`, or the assertion has to
live in the test file.

## Why Sutra needs it

Because the repository has been configured for this since Day 0 and has had nothing to collect.

`pyproject.toml` already carries a `[tool.pytest.ini_options]` block with `testpaths = ["tests"]`, and
`./m check` already runs `uv run python -m pytest -q -m "not live"` — with a comment explaining that
exit code 5, *no tests collected*, is tolerated because before today there were none. Today that
tolerance stops being needed.

Understanding the naming rule is what makes the difference between a suite that grows and one that
quietly stops growing. A test file added under `days/` instead of `tests/` is never run, because
`testpaths` points at one directory. A test function renamed to `check_...` during a tidy-up is
skipped forever, and the suite gets *faster*, which is the least suspicious symptom imaginable.

## The mechanism

A file with three tests and one helper, so you can watch the helper not get collected.

```python
# days/day-23-testing-tools-and-callbacks/lab/test_discovery_demo.py
TICKETS = {"4521": "Refund not received", "4522": "Login loop after password reset"}


def lookup_ticket(ticket_id: str) -> dict[str, str]:
    """A known id returns the ticket; an unknown one says so instead of inventing one."""
    if ticket_id not in TICKETS:
        return {"status": "not_found", "ticket_id": ticket_id}
    return {"status": "ok", "ticket_id": ticket_id, "title": TICKETS[ticket_id]}


def helper_that_is_not_collected() -> str:
    """Not named test_*, so pytest walks past it. Test files may hold helpers."""
    return "4521"


def test_a_known_ticket_comes_back_with_its_title() -> None:
    result = lookup_ticket("4521")
    assert result["status"] == "ok"
    assert result["title"] == "Refund not received"


def test_an_unknown_ticket_says_not_found_rather_than_inventing_one() -> None:
    result = lookup_ticket("9999")
    assert result["status"] == "not_found"
    assert "title" not in result


def test_the_helper_above_was_not_collected_as_a_test() -> None:
    assert helper_that_is_not_collected() == "4521"
```

**Line by line:**

- There is **no import of pytest** anywhere in this file. That is not a simplification for teaching;
  it is what a pytest file normally looks like. You import pytest when you need a marker, a fixture
  decorator or `pytest.raises`, and not before.
- `lookup_ticket` lives in the test file only because this part is about collection. In real work it
  lives in `sutra/` and the test file imports it — mixing the code under test into the test file
  means the test can pass while the shipped code is broken.
- The two `assert` lines in the first test are deliberate. pytest stops at the **first** failing
  assertion in a function, so ordering them from most general to most specific means the failure you
  see is the most informative one available at that moment.
- `assert "title" not in result` asserts an **absence**, which is the assertion people forget. A tool
  that answers `not_found` and *also* includes a leftover title is a tool that teaches the model to
  make things up, and only the negative assertion catches it.
- `helper_that_is_not_collected` returns a value and is called by the third test. If pytest were
  collecting it as a test it would be reported as a passing test with a return value, and modern
  pytest warns about exactly that — `PytestReturnNotNoneWarning` — because a test that returns
  something is usually a test that meant to assert something.
- Every test function is annotated `-> None`. pytest does not require it; the house style does, and
  it makes the return-value mistake above impossible to write by accident.

Collect without running, to see the rule at work:

```bash
cd days/day-23-testing-tools-and-callbacks/lab
uv run python -m pytest test_discovery_demo.py --collect-only -o addopts=""
```

**Line by line:**

- `--collect-only` finds tests and stops. It is the fastest way to answer *"is my file being seen at
  all"*, which is the first question when a test does not seem to run.
- `-o addopts=""` overrides the `addopts = "-q --strict-markers"` line in `pyproject.toml` for this
  one run. Without it the repository's `-q` suppresses the tree and prints a one-line summary
  instead. `-o` is how you temporarily unset a configured option without editing the file.

**Three items, and `helper_that_is_not_collected` is not one of them.** The rule did the work.

Two lines at the top are worth more attention than the tree. `rootdir` is the directory pytest decided

in force — so when a marker or an option seems to be ignored, this is the line that tells you whether
pytest is reading the file you are editing.

## When it breaks

The failure that costs people the most is the one with no error at all: **the file that is never
collected**. Ask pytest to run a file it does not think is a test file and it says so, but only if you
name the file directly. Left to `testpaths`, it simply reports nothing:

```text
no tests ran in 0.03s
```

That message, with no `error` and no `F`, means one of exactly four things: the filename does not
start with `test_`, the function names do not start with `test_`, the file is outside `testpaths`, or
a marker filter deselected everything. Check them in that order — and note that the fourth prints
differently, `3 deselected in 0.10s`, which is the one case that tells you the tests exist.

The second failure is louder and stops the whole run. Two test files with the **same basename** in two
directories that have no `__init__.py`:

```text
=================================== ERRORS ====================================
__________________ ERROR collecting .tmp_b/test_same_name.py __________________
import file mismatch:
imported module 'test_same_name' has this __file__ attribute:
  C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\.tmp_a\test_same_name.py
which is not the same as the test file we want to collect:
  C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\.tmp_b\test_same_name.py
HINT: remove __pycache__ / .pyc files and/or use a unique basename for your test file modules
=========================== short test summary info ===========================
ERROR .tmp_b/test_same_name.py
!!!!!!!!!!!!!!!!!!! Interrupted: 1 error during collection !!!!!!!!!!!!!!!!!!!!
1 error in 0.79s
```

Without `__init__.py`, a test file's module name is just its basename, so two files called
`test_same_name.py` are one module name and pytest refuses to guess. The hint mentions `__pycache__`
because a stale one causes the same message; the real fix is the second half of the sentence, a unique
basename. This is why `tests/` in this repository has an `__init__.py` and why every lab file on this
day has a name nothing else uses.

## In production

**Nobody types the naming rule after the first week; they feel it.** What survives is the discipline
underneath it: the test file mirrors the module. `sutra/errors.py` is tested by `tests/test_errors.py`.
When that mapping holds, finding the tests for a file is not a search, and noticing that a file *has*
no tests is a glance at a directory listing rather than a coverage report.

**What changes at scale** is collection time. At a few hundred tests, collection is instant. At tens of
thousands, importing every test module takes long enough that people start passing paths to narrow it
down, and then somebody discovers that the import of one module has a side effect — a client
constructed at module level, a config read — and collection itself starts touching the network.
`--collect-only` is how that gets found, because it imports everything and runs nothing.

**The failure that only appears with real traffic** is the test that was renamed. A tidy-up renames
`test_refund_window_is_thirty_days` to `check_refund_window`, the suite goes from 412 tests to 411,
everything is green, and the assertion is gone. Nothing reports it. The defence is watching the test
**count** as a number that should only go up, which some teams assert on in CI and everyone else
learns to notice by eye.

**The review comment a senior engineer leaves:** *"this new file is `tests_helpers.py`, so nothing in
it is collected. Either rename it `test_helpers.py` or move the helpers into `conftest.py`."*

**The interview question:** *"how does pytest know what to run?"* The answer that shows you have
debugged it: *"filename `test_*.py`, function `test_*`, inside `testpaths`. When something isn't
running I use `--collect-only` before anything else, because 'no tests ran' and 'all tests passed' look
almost identical at the bottom of a terminal and mean opposite things."*
