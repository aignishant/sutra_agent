# 2.5 — Markers, and the `-m "not live"` line you have been typing

## One-line answer

A marker is a label on a test, `-m "not live"` is the filter that reads it, and `--strict-markers` is
what turns a one-character typo from a warning that runs the test anyway into an error that stops the
run — `'liv' not found in \`markers\` configuration option`.

## The story

There are two bins outside the house and they are collected on different days.

The general waste goes every week. The garden waste goes once a month, and only if the bag is the
right one with the council's label on it. The rule is not enforced by anybody standing there; it is
enforced by the lorry. A bag with the label goes on the monthly lorry. A bag without it does not.

Everyone learns this the same way. You put out a bag of hedge clippings in an ordinary black sack,
the weekly lorry ignores it because it is garden waste, the monthly lorry ignores it because it has
no label, and it sits by the gate for a fortnight while you walk past it twice a day.

The label is not paperwork. The label is the thing that decides which lorry takes it, and a bag with
the wrong label is worse than a bag with none, because you *believe* it has been dealt with.

## The idea in plain language

A **marker** is a tag you attach to a test with `@pytest.mark.<name>`. It carries no behaviour by
itself. It exists so that you can later say *run these* or *do not run these*.

`-m` is the filter, and it takes an expression: `-m live`, `-m "not live"`, `-m "slow and not live"`.
Tests that do not match are **deselected** — not skipped, not failed, just not run, and the count
appears at the end of the report so nothing disappears silently.

This repository has two markers, declared in `pyproject.toml` since Day 0:

```toml
[tool.pytest.ini_options]
addopts = "-q --strict-markers"
testpaths = ["tests"]
markers = [
    "live: hits a real API, model or database - skipped by default, never run in CI",
    "slow: takes more than a few seconds",
]
```

Three things in that block do work.

**`markers = [...]`** is the declaration. A marker listed here is known; anything else is not.

**`--strict-markers`** in `addopts` turns an unknown marker into a **collection error**. Without it,
`@pytest.mark.liv` is a warning that most people never read, and the test runs — in every lorry, so
to speak, because it is in nobody's filter. This is the setting that makes markers trustworthy rather
than decorative.

**`addopts`** means "always add these options", so the strictness applies whether you type
`uv run python -m pytest` or `./m check` runs it for you. Options nobody has to remember are options
that are actually in force.

And `-m "not live"` is the line that has been in `./m check` since Day 0, doing nothing, waiting for
today. It is the sentence *"run everything that does not touch a real API"*, and it is what allows one
suite to contain both kinds of test without the expensive kind holding the cheap kind hostage.

The distinction worth being precise about: a **marker** is a label, and a **skip** is a decision.
`@pytest.mark.skipif(not os.environ.get("GOOGLE_API_KEY"), reason=...)` decides at collection time and
reports `s`; a marker decides nothing and waits to be filtered. Use a marker when the *caller* should
choose, and a skip when the *environment* has already chosen.

## Why Sutra needs it

Because Sutra will have tests that must never run in `./m check`, and it will have them tomorrow.

Day 24 needs at least one test that a real `429` is classified correctly, and that means a real
refusal from a real provider. Day 31 wires `./m check` into a gate that runs constantly. Phase 12
builds evals, which by definition call models. Every one of those is a test worth having and a test
that cannot be in the default run — because the default run happens on a machine with no key, and
because twenty free requests a day does not survive being spent by a pre-commit hook.

Without a marker the choice is binary: put them in and break the gate, or leave them out and never
write them. The marker is what makes *both* possible, and `--strict-markers` is what stops the whole
arrangement being undone by a typo six months from now.

## The mechanism

Four tests: two ordinary, one slow, one that needs a key and a request.

```python
# days/day-23-testing-tools-and-callbacks/lab/test_markers_demo.py
import time

import pytest

from test_discovery_demo import lookup_ticket


def test_the_lookup_is_a_dict_and_needs_nothing() -> None:
    assert lookup_ticket("4521")["status"] == "ok"


def test_an_unknown_id_is_still_free_to_check() -> None:
    assert lookup_ticket("9999")["status"] == "not_found"


@pytest.mark.slow
def test_something_that_takes_real_wall_clock() -> None:
    start = time.perf_counter()
    time.sleep(1.0)
    assert time.perf_counter() - start >= 1.0


@pytest.mark.live
def test_the_model_actually_answers() -> None:
    """Needs GOOGLE_API_KEY and spends one of the day's twenty free requests."""
    from google import genai

    from phoned_the_model import ask  # `ask` carries the 429 backoff Addendum 02 requires

    answer, _seconds = ask(genai.Client())
    assert answer
```

**Line by line:**

- `@pytest.mark.slow` and `@pytest.mark.live` are **two different labels for two different reasons**,
  and a test can carry both. Slow means it costs wall clock; live means it costs money, quota or a
  credential. Conflating them into one marker loses the ability to run the slow-but-free tests in CI.
- The docstring on the live test states what it costs. That is not decoration: the next person to
  consider running `-m live` needs to know it spends one of twenty daily requests before they run the
  whole file.
- `from google import genai` is imported **inside** the function. At module level it would be imported
  during collection, so every run — including the deselected one — would pay ADK's import cost, and a
  machine without the package installed could not even collect the file.
- `genai.Client()` with no arguments reads the key from the environment. That is the line that fails
  when there is no key, and the failure is the point of the second run below.
- `ask` comes from `phoned_the_model.py` rather than being written inline, because Addendum 02
  requires **every** model call path to handle a `429` with backoff, and there is no version of that
  rule that exempts a test. Importing the one helper means the rule is obeyed in one place, and the
  cost of the call — one of twenty daily requests — is stated where the helper is defined.
- `time.perf_counter()` again rather than `time.time()`, for the same reason as
  [1.2](../01-where-the-line-falls/1.2-fast-isolated-specific.md): a duration wants a monotonic clock.
- The slow test asserts `>= 1.0` rather than a range. An assertion that the sleep took *at most* some
  amount would be a flaky test on a loaded machine, and a flaky test is worse than no test.

Run it the way `./m check` does:

```bash
cd days/day-23-testing-tools-and-callbacks/lab
uv run python -m pytest test_markers_demo.py -m "not live"
```

**Line by line:**

- `-m "not live"` selects everything without the `live` label. The quotes matter in a shell: without
  them, `not` and `live` are two arguments.

Measured on 2026-09-04:

```text
...                                                                      [100%]
3 passed, 1 deselected in 1.04s
```

**`1 deselected` is the important half.** The live test did not run, did not fail, and did not
disappear — the report says one was set aside, so a test that has quietly been excluded for months is
visible in every single run.

Now run it with no filter, on a machine with no key, which is what CI looks like:

```bash
GOOGLE_API_KEY= GEMINI_API_KEY= uv run python -m pytest test_markers_demo.py
```

**Line by line:**

- Setting the variables to empty in front of the command applies only to this one run and does not
  touch your `.env`.

## When it breaks

Misspell the marker. One character:

```bash
uv run python -m pytest test_typo_marker_demo.py
```

**Line by line:**

- The file contains a single test decorated `@pytest.mark.liv`, and it is meant to be red at
  **collection** time rather than at run time.

```text
=================================== ERRORS ====================================
_ ERROR collecting days/day-23-testing-tools-and-callbacks/lab/test_typo_marker_demo.py _
'liv' not found in `markers` configuration option
=========================== short test summary info ===========================
ERROR test_typo_marker_demo.py - Failed: 'liv' not found in `markers` configu...
!!!!!!!!!!!!!!!!!!! Interrupted: 1 error during collection !!!!!!!!!!!!!!!!!!!!
1 error in 0.92s
```

Now take `--strict-markers` away and run exactly the same file:

```bash
uv run python -m pytest test_typo_marker_demo.py -o addopts="-q"
```

**Line by line:**

- `-o addopts="-q"` replaces the configured options for this run, dropping `--strict-markers` while
  keeping the quiet output.

```text
.                                                                        [100%]
============================== warnings summary ===============================
test_typo_marker_demo.py:11
  ...: PytestUnknownMarkWarning: Unknown pytest.mark.liv - is this a typo?  You can register custom marks to avoid this warning - for details, see https://docs.pytest.org/en/stable/how-to/mark.html
    @pytest.mark.liv

-- Docs: https://docs.pytest.org/en/stable/how-to/capture-warnings.html
1 passed, 1 warning in 0.11s
```

**One passed.** Read that carefully, because it is the whole case for strictness. The test was
supposed to be excluded from the default run. It carries a label nobody filters on. So `-m "not live"`
selects it — it is not `live`, after all — and in CI, with no key, it goes red for a reason that has
nothing to do with the change under review. Or worse, on a machine that *does* have a key, it passes
and silently spends quota on every commit.

The warning did say so. Warnings scroll past. The error does not.

## In production

**Every project ends up with the same three markers**, whatever they are called: something for tests
that need credentials, something for tests that are slow, and something for tests that are known to be
flaky and are being tolerated deliberately. Naming the third one honestly is more valuable than it
sounds, because the alternative is that flaky tests get deleted or, worse, that everybody learns to
re-run the suite until it is green.

**What changes at scale** is that the filter moves out of people's hands and into the pipeline. The
pre-commit hook runs `-m "not live and not slow"`, the pull-request job runs `-m "not live"`, and a
nightly job runs `-m live` with a real key from a secret store and a budget. The markers are the same;
the audience differs. Getting there requires the labels to be trustworthy, which is the whole reason
for `--strict-markers`.

**The failure that only appears with real traffic** is the live suite nobody runs. It is marked, it is
excluded, and after a few months it does not compile — the API it calls has moved, the model string is
retired, the fixture it wanted no longer exists. The defence is scheduling it: a marked test that is
never run is a comment with a decorator on it. If there is no schedule, be honest and delete it.

**The review comment a senior engineer leaves:** *"this test constructs a client at module level, so
collection imports it even when it's deselected. Move the import inside the test."*

**The interview question:** *"how do you keep tests that need a real API in the same repository as your
unit tests?"* The answer that shows you have run a CI pipeline: *"a marker, a default filter that
excludes it, and strict markers so a typo is an error rather than a warning. Then a scheduled job that
actually runs the excluded ones, because a marked test with no schedule is a test that has been
deleted without anyone deciding to delete it."*
