# 2.4 — `parametrize`: one test, many cases

## One-line answer

`@pytest.mark.parametrize` turns one test function into one test **per case**, each with its own name
in the output — so a failure reads
`test_a_transient_failure_is_worth_another_attempt[connection_reset]` instead of "the classifier is
broken", and the other cases still run.

## The story

The optician does not ask whether you can read.

There is a chart on the wall with eight rows, and the letters get smaller as you go down. She covers
one of your eyes, points at a row, and you read it out. Then the next row. Then the next. She is not
making a judgement about your eyesight in general; she is finding **the row where it stops**, and
writing that row down.

Imagine if she stopped the moment you got a letter wrong and wrote *"vision: poor"*. You would learn
nothing you did not already know. The value in the whole procedure is that every row gets attempted,
and the result is a specific line on a specific chart with a specific eye covered.

## The idea in plain language

Most tests are the same three lines repeated with different values. There are two ways to write that
and they behave very differently.

**The loop.** Put the values in a list and iterate inside one test function. This looks tidy and it
has two flaws. The first is that the test **stops at the first bad value** — `assert` raises, and the
remaining values are never tried, so you find out about one problem at a time. The second is that
there is one test in the report, so its name has to cover all the cases, which means it cannot name
any of them.

**The parametrized test.** Decorate the function with `@pytest.mark.parametrize` and pytest generates
**a separate test per case**. Each one runs independently, each one is reported separately, and each
one carries the case in its name in square brackets.

That last detail is why this exists. In a suite of hundreds, the failure line is what you read, and

```
test_the_lookup_answers_the_same_way_for_every_shape_of_id[trailing-space]
```

tells you the rule, the input class and the bug, in one line, without opening anything.

The decorator takes two arguments: the names of the parameters, and a list of values. When there is
one parameter the list is a list of values; when there are several, the names go in one string or
tuple and each case is a tuple of the same length.

There is a third form worth learning immediately, `pytest.param(..., id="...")`, which lets you name
the case yourself. pytest generates ids automatically from the values, and for strings and numbers
those ids are fine — but a case whose value is `""` gets the unreadable id `[]`, and a case whose
value is an object gets `[kind0]`. Naming them is a small courtesy to the person reading the failure,
who is you.

## Why Sutra needs it

Because almost every rule Sutra has built in the last week is a rule about **a set of inputs**, not
about one.

[Day 21](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.1-which-429-is-it.md)'s
classifier has to say *retryable* for a per-minute ceiling, a timeout and a reset connection, and
*not retryable* for a per-day ceiling, a bad request and a missing article. That is six cases of one
rule. Written as a loop it is one test whose failure says "the classifier is broken". Written with
`parametrize` it is six tests, and a failure names the exact `kind` string that changed behaviour.

Day 22's scrub filter is the same shape — one case per secret pattern, parametrized over the very
dictionary the filter uses, so adding a pattern adds a test case automatically. Day 24's quota
arithmetic will be the same again: one case per provider. This decorator is the single highest-value
piece of pytest syntax in the whole day.

## The mechanism

Three parametrized tests, ending with the form that names its own cases.

```python
# days/day-23-testing-tools-and-callbacks/lab/test_parametrize_demo.py
import pytest

RETRYABLE = {"per_minute", "timeout", "connection_reset"}


def is_retryable(kind: str) -> bool:
    """The Day 21 rule: a per-minute ceiling clears on its own, a per-day ceiling does not."""
    return kind in RETRYABLE


@pytest.mark.parametrize("kind", sorted(RETRYABLE))
def test_a_transient_failure_is_worth_another_attempt(kind: str) -> None:
    assert is_retryable(kind), f"{kind} should clear on its own, so retry is the right answer"


@pytest.mark.parametrize("kind", ["per_day", "bad_request", "not_found"])
def test_a_permanent_failure_must_not_be_retried(kind: str) -> None:
    assert not is_retryable(kind), f"retrying {kind} spends quota to learn nothing new"


@pytest.mark.parametrize(
    ("ticket_id", "expected"),
    [
        pytest.param("4521", "ok", id="known-id"),
        pytest.param("9999", "not_found", id="unknown-id"),
        pytest.param("", "not_found", id="empty-string"),
        pytest.param("4521 ", "not_found", id="trailing-space"),
    ],
)
def test_the_lookup_answers_the_same_way_for_every_shape_of_id(
    ticket_id: str, expected: str
) -> None:
    from test_discovery_demo import lookup_ticket

    assert lookup_ticket(ticket_id)["status"] == expected
```

**Line by line:**

- `@pytest.mark.parametrize("kind", sorted(RETRYABLE))` iterates **the same set the function under
  test uses**. That is the trick worth stealing: add a fourth retryable kind to `RETRYABLE` and a
  fourth test case appears by itself. A hand-written list of three strings beside a set of three
  strings is two things that will drift.
- `sorted(...)` and not the bare set. A set has no order, so the generated case ids would appear in a
  different order between runs — which makes two CI logs impossible to diff and breaks
  `pytest --last-failed`. Sorting costs nothing and makes the ids stable.
- The second test lists its values literally, because the "not retryable" set is *everything else* and
  cannot be derived from a constant. Three representative members is the right size: a quota ceiling,
  a client mistake and a missing resource, which are three genuinely different reasons not to retry.
- `assert not is_retryable(kind), f"retrying {kind} spends quota to learn nothing new"` — a **negative**
  assertion, so the value pytest would print is `True` and says nothing. This is exactly the case
  [2.2](2.2-arrange-act-assert.md) says must carry a message.
- The third decorator takes `("ticket_id", "expected")` as a tuple of names, and each case is a
  `pytest.param(...)` with two values and an `id`. The tuple form is clearer than the older
  `"ticket_id,expected"` string, and it is what a reader can check at a glance against the function's
  signature.
- The four ids — `known-id`, `unknown-id`, `empty-string`, `trailing-space` — are the **classes of
  input**, not the values. `empty-string` would otherwise be generated as `[]`, which is unreadable,
  and `trailing-space` would be `[4521 ]`, which looks like a typo rather than a deliberate case.
- `"4521 "` with the trailing space is the real bug this shape of test catches: a ticket id arriving
  from a form with whitespace on the end is a different dictionary key, and the tool must fail
  honestly rather than half-matching.
- The import sits inside the function rather than at the top. That is unusual and deliberate here: it
  keeps this demonstration file readable as one idea per block. In real code the import belongs at the
  top of the file.

## When it breaks

Break the rule under test — narrow `is_retryable` so that a reset connection is no longer retryable —
and the report names the case:

```text
    @pytest.mark.parametrize("kind", sorted(RETRYABLE))
    def test_a_transient_failure_is_worth_another_attempt(kind: str) -> None:
>       assert is_retryable(kind), f"{kind} should clear on its own, so retry is the right answer"
E       AssertionError: connection_reset should clear on its own, so retry is the right answer
E       assert False
E        +  where False = is_retryable('connection_reset')

=========================== short test summary info ===========================
FAILED test_parametrize_demo.py::test_a_transient_failure_is_worth_another_attempt[connection_reset]
1 failed, 2 passed in 0.13s
```

**One failed, two passed.** That is the whole argument in one line. A loop would have reported one
failure and told you nothing about the other two values, so you would not know whether one rule broke
or all of them.

The mistake that produces a confusing failure is a **mutable default in the case list**. Passing the
same dictionary object as a case value to several tests means every test shares it, and the second
test sees what the first one wrote — the same coupling
[2.3](2.3-fixtures.md) exists to prevent, arriving through a different door. Case values should be
immutable: strings, numbers, tuples, frozensets. If a case needs a mutable object, build it inside the
test from an immutable description.

The other one is silent and worth watching for: `parametrize` with an **empty list** generates zero
tests and reports nothing at all. A parametrized test whose values come from a constant that has
become empty simply vanishes from the suite, and the count goes down by however many cases it used to
have.

## In production

**The mature use is one parametrized test over a table of real cases**, often loaded from a file:
every 429 body the team has actually seen, every malformed tool argument that has arrived, every
customer id shape. When a new one appears in production it is added as a row, and the test that
catches it in future is generated for free. This is how a suite accumulates institutional memory
instead of opinions.

**What changes at scale** is that parametrization multiplies. Three parameters with four values each
is sixty-four tests from one function, and now the suite has thousands of cases whose names nobody can
read. The discipline that keeps it useful is to parametrize over **one axis of variation per test**
and to name the axis in the function name. Two axes are sometimes right; three almost never are.

**The failure that only appears with real traffic** is the case that was never in the table. A
parametrized test proves the rule holds for the inputs you thought of, and it is very convincing —
convincing enough that people stop asking what else could arrive. The counterweight is property-based
testing, where the framework generates inputs you did not think of, and it is the natural sequel to
this page rather than a competitor to it.

**The review comment a senior engineer leaves:** *"these cases are hard-coded but the function reads
them from `RETRYABLE` — parametrize over the constant so the two can't drift."*

**The interview question:** *"how do you test something with many input cases?"* The answer that shows
you have read a CI log: *"parametrize, not a loop, because a loop stops at the first failure and
reports one test. Parametrized cases each get their own name, so the failure line tells me which input
class broke without opening the file — and I name the cases explicitly whenever the auto-generated id
would be unreadable, like an empty string."*
