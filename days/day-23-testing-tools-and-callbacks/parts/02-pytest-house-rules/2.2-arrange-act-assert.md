# 2.2 — Arrange, act, assert — and the name that says the crime

## One-line answer

A test body has three parts in a fixed order — set up the world, do **one** thing, check **one**
outcome — and the assertion's message is worth more than everything else in the file, because the
same failing condition reported as `assert 'not_found' == 'ok'` and as *"9999 reached the tool but is
not in TICKETS"* costs two very different evenings.

## The story

There is a book on the counter at the shop where you bought the bag, and the assistant slides it
towards you and asks you to write down the problem.

You could write *"faulty"*. It is true. It takes a second. And when the form reaches the supplier
three weeks later, somebody reads *faulty*, looks at a bag that appears to be entirely intact, and
writes back asking what exactly is faulty about it.

What you could write instead is: *"the zip on the left outer pocket splits open when the pocket is
full — happens every time, not once."*

Same complaint. Same bag. But the second one contains the reproduction steps, the specific component
and the frequency, so the person at the other end can act on it without a conversation. The cost of
writing it was ten extra seconds, paid once, by you. The cost of not writing it is a round trip,
paid three weeks later, by somebody who has never seen the bag.

## The idea in plain language

**Arrange, act, assert** is the shape of a test body, and it is worth following because a test that
does not have this shape is usually a test that is checking two things.

- **Arrange** — build the inputs and the doubles. Everything the code under test needs in order to
  run.
- **Act** — call the thing being tested. **Exactly one call.** If there are two, you have two tests.
- **Assert** — check the outcome. One outcome, or several assertions describing one outcome.

That is the whole pattern, and it is often three lines with a blank line between the groups.

The second half of this part matters more than the first, because it is the half people skip.

**A test's name is a sentence about behaviour, not a label for a function.** `test_lookup` names the
function it calls. `test_an_unknown_ticket_returns_not_found_rather_than_inventing_one` names the
**rule** the code has to obey. When a suite of four hundred goes red, you read names, not code — so
the name has to be enough on its own. Long names are correct here; this is the one place in Python
where a forty-character identifier is good style.

**And an assertion's message is the second sentence.** pytest's rewriting
([2.1](2.1-how-pytest-finds-a-test.md)) already prints the values that were compared, which tells you
*what* was unequal. It cannot tell you *why that matters* or *what to do about it*, because it does
not know. That is what the second argument to `assert` is for:

```
assert condition, "the sentence a person reads at eleven at night"
```

The distinction to hold on to: **the values come free, the meaning does not.** A message is worth
writing when the values alone would leave the reader guessing — which is most of the time, and always
on a negative assertion, where the value being printed is `None` or `False` and says nothing at all.

## Why Sutra needs it

Because Sutra's tests will be read almost exclusively when they are red, by you, months later, in the
worst possible circumstances.

This is the fifth consecutive day on which deliberately failing a green suite has exposed a weak
assertion. Day 19 found two. Day 20 found a `StopIteration` that said nothing. Day 21 found a bare
`assert False`. Day 22 found two `KeyError`s in a suite that was otherwise excellent, and the one
test with a message was the only one whose failure could be read without opening the file. Today's
lab, written for this part, produced the same result again.

That is not a coincidence, it is a pattern, and it has a cause: **you only ever read a failure message
when you have caused the failure on purpose.** A green test's message is invisible. So unless breaking
things deliberately is part of the routine, every message in the suite is unreviewed — and messages
are the part of a test that a reviewer cannot check by reading.

## The mechanism

Three tests that fail on purpose. The first shows what rewriting gives you for nothing; the second and
third assert **exactly the same condition** and differ only in the name and the message.

```python
# days/day-23-testing-tools-and-callbacks/lab/test_red_on_purpose.py
from test_discovery_demo import lookup_ticket


def test_plain_assert_prints_the_values_it_compared() -> None:
    assert lookup_ticket("9999").get("title")


def test_it_works() -> None:
    assert lookup_ticket("9999")["status"] == "ok"


def test_every_ticket_the_desk_can_be_asked_about_is_in_the_lookup_table() -> None:
    result = lookup_ticket("9999")
    assert result["status"] == "ok", (
        f"9999 reached the tool but is not in TICKETS - either the desk is routing a ticket "
        f"the tool cannot serve, or the table is stale. Got: {result}"
    )
```

**Line by line:**

- The first test is a **chain**: a call, then `.get("title")`. That is deliberate, because rewriting's
  best trick is showing every intermediate value of a chain, and a single `==` comparison does not
  demonstrate it.
- The second and third assert `result["status"] == "ok"` on the same input. Nothing about the code
  under test differs between them. **Every difference in the output below is a difference in how the
  test was written.**
- The third splits the call out into `result` on its own line — the *arrange* step — so that the
  message can interpolate the whole dictionary. A one-liner cannot show you what it actually got
  without calling the function a second time.
- The message is an f-string over two lines wrapped in parentheses, which is how you keep a useful
  message inside a line limit without a backslash continuation.
- The message names **two possible causes** — a stale table or a bad route — because at eleven at
  night the useful thing is not "this is wrong" but "here are the two places to look".
- `test_it_works` is the honest name for a badly named test. Nobody sets out to write it; it appears
  when a test is written to make a red bar go green rather than to state a rule.

**The first failure is free lunch.** Four `where` lines walk the chain backwards: `None` came from
`.get('title')`, which came from that dictionary, which came from `lookup_ticket('9999')`. You have
not written a single word of explanation and you already know the tool returned a `not_found` result
and the test asked it for a title anyway. That is assertion rewriting, and it is the reason nobody in
Python needs `assertEqual`.

**The second failure is what rewriting cannot do.** `assert 'not_found' == 'ok'` is completely
accurate and completely uninformative. It does not say what `'not_found'` is a status *of*, what
should have been in the table, or which of the two systems is at fault. And the test's name —
`test_it_works` — adds nothing, so the reader has to open the file. Note the short summary line at the
bottom, too: `AssertionError: assert 'not_fo...`, truncated to nothing.

**The third failure is the same bug, reported like the complaint form.** The message comes first,
before pytest's own output, and it names the id, the table, the two candidate causes and the actual
result. And look at its line in the short summary: because the name is a sentence, the summary line
alone is enough to know what broke, without the detail above it.

The cost of that difference was one line of f-string.

## When it breaks

The pattern has two failure modes of its own, and both look like good intentions.

**The test that acts twice.** Two calls in one test body, and now a failure could belong to either.
The tell is a comment in the middle of the function saying "and now check that…". The fix is not a
better message; it is two tests. This is the one-idea rule applied to a test function.

**The over-explained message.** A message that restates the assertion — `assert x == 5, "x should be
5"` — is noise. pytest already printed both values. A message earns its place only by adding something
the values cannot carry: the *why*, the *consequence*, or the *place to look*.

There is also a failure that is not about the pattern at all, and it is worth recognising because it
appears often when you start writing negative assertions:

```text
E       AssertionError: assert 'title' not in {'status': 'not_found', 'ticket_id': '9999', 'title': 'x'}
```

That is pytest handling `not in` well. Contrast it with `assert not result.get("title")`, which fails
with a bare `assert not None` and no clue what was being checked. **Prefer the assertion form that
puts the interesting value in the failure line**, and when the natural form does not, add the message.

## In production

**Teams stop arguing about assertion messages and start reviewing them, once.** A useful review rule:
every assertion whose failure would print only `True`, `False`, `None` or an empty collection must
carry a message. That covers almost every negative assertion and almost nothing else, so it is cheap
to follow and it catches the cases that actually hurt.

**What changes at scale** is that the test *name* becomes the interface. At four hundred tests, a
failure arrives as a line in a CI log, on a phone, in a corridor. The name is all there is. Teams that
have felt this write names as full sentences and stop worrying that they are long, and the suite reads
like a specification when you list it with `--collect-only`.

**The failure that only appears with real traffic** is the flaky assertion whose message hides the
flake. `assert response.status == "ok"` failing intermittently in CI tells you nothing about *why*; the
same assertion carrying the request id and the attempt number turns a week of shrugging into a
ten-minute diagnosis. Anything that can fail intermittently should print the state that would let you
correlate it with a log line — which is exactly the `invocation_id` from
[Day 22](../../../day-22-structured-logging/parts/02-wiring-the-run/2.2-the-correlation-id.md).

**The review comment a senior engineer leaves:** *"the name of this test tells me it exists, not what
it protects. What is the rule it's enforcing? Put that in the name and I won't have to read the
body."*

**The interview question:** *"what makes a good test failure?"* The answer that shows you have been on
call: *"the name tells me the rule that broke, the message tells me the two places to look, and both
of those are visible in the one-line summary without expanding anything. Everything else — the values,
the traceback — pytest gives me for free, so the only part I have to actually write is the part it
can't infer."*
