# 1.1 — The nondeterminism excuse, counted

## One-line answer

"You cannot unit test an agent, the model is nondeterministic" is a claim about a percentage, and
when you actually count the functions in `sutra/` the percentage is **47%** — which means the excuse
is being used to avoid testing the other **eighteen functions that are plain Python**.

## The story

The bus from your neighbourhood is late about as often as it is on time.

Ask why and everyone gives you the same answer: the road. A lorry breaks down, a procession closes a
junction, it rains and the whole city slows to a crawl. Nobody can promise you a bus at a particular
moment, and anybody who says otherwise has not driven that road.

Now walk into the depot early in the morning.

There is a man with a clipboard going along the row of buses. Tyre pressure. Oil. Brake fluid. Does
the horn work, does the ticket machine print, is the fuel card in the holder. He is not writing down
guesses. Every line on his sheet is a yes or a no, and if the answer is no the bus does not leave.

Nobody has ever walked up to that man and said *"there is no point checking the brakes, the traffic
is unpredictable."* The traffic being unpredictable is exactly why the brakes are checked. The
uncertainty lives on the road, and it does not spread backwards into the workshop.

## The idea in plain language

An **agent system** is a program that lets a language model decide what to do next, and then does
it. Somewhere inside it there is a call to a model, and that call is genuinely unpredictable: send
the same question twice and you may get two different sentences back.

A **unit test** is a small program that runs one piece of your code, checks one thing about the
result, and says green or red. It is worth having only when the answer does not change on its own,
because a check that reports red for reasons outside your control stops meaning anything very
quickly.

Put those two sentences together and you get the excuse this part exists to demolish:

> The model is unpredictable, therefore the system is unpredictable, therefore it cannot be tested.

The middle step is the lie. **The model is a component, not an atmosphere.** It sits behind one
function call with an argument list and a return value. Everything on your side of that call —
looking a ticket up in a dictionary, checking a severity against a list of allowed values, deciding
whether a `429` is worth retrying, building a filename out of a ticket id, refusing to run a write
tool without approval — is ordinary Python that returns the same answer every time you ask.

You cannot know that by feel. You have to count, because the answer is different for every codebase
and it decides how much of yours has no excuse.

Two terms this part uses and will keep using:

- The **deterministic shell** is every function whose output is a function of its input alone. Same
  input, same output, forever. It gets **unit tests**, starting today.
- The **stochastic core** is the model call itself, and any function whose answer depends on what
  the model said. It gets **evals** — a different instrument, built in Phase 12, which scores a
  spread of answers instead of asserting one. *Stochastic* just means "with randomness in it"; there
  is no deeper meaning hiding in the word.

## Why Sutra needs it

Because Sutra is now about a thousand lines of load-bearing Python with **no tests at all** over the
parts that matter, and the parts that matter are the ones that go wrong quietly.

Concretely: [Day 21](../../../day-21-errors-surface-not-swallow/LESSON.md) built a classifier that
decides whether an HTTP `429` is a per-minute ceiling worth retrying or a per-day ceiling that is
not. That decision is a dictionary lookup. It is also the difference between spending three of your
twenty daily requests learning nothing and spending zero. Nothing about it involves a model, and
nothing about it is currently checked by anything except you running a demo and reading the screen.

Day 24 adds quota arithmetic on top of it — counting requests against `RPM` and `RPD` ceilings — and
arithmetic that nobody tests is arithmetic that is wrong. If the deterministic shell is not under
test by the end of today, tomorrow's budget enforcement is built on sand.

## The paper behind it

**Mock roles, not objects** · `doi:10.1145/1028664.1028765` · 2004 ·
<https://doi.org/10.1145/1028664.1028765>

It argued that a test should stand in for the **role a collaborator plays in your design** rather
than for some concrete class you happened to import — which is what turns the line between "your
code" and "someone else's service" into a design decision instead of an accident.

Read it after the parts: [`papers/01-mock-roles-not-objects.md`](../../papers/01-mock-roles-not-objects.md).

## The mechanism

Stop arguing and count. This walks every Python file under `sutra/`, parses it, and asks of each
function whether its own body names anything that reaches a model or the network.

```python
# days/day-23-testing-tools-and-callbacks/lab/count_the_shell.py
import ast
from pathlib import Path

PACKAGE = Path(__file__).resolve().parents[3] / "sutra"

# A name that can only appear in a function that reaches out: the ADK runtime, the genai client,
# or an HTTP call. Anything else is arithmetic, dicts and strings.
REACHES_OUT = (
    "Runner",
    "run_async",
    "LlmAgent",
    "generate_content",
    "genai",
    "httpx",
    "requests",
    "Gemini",
    "LiteLlm",
)


def touches_a_model(node: ast.AST) -> bool:
    """True when this function's own body names something that reaches a model or the network."""
    return any(
        isinstance(child, ast.Name | ast.Attribute)
        and any(needle in ast.unparse(child) for needle in REACHES_OUT)
        for child in ast.walk(node)
    )
```

**Line by line:**

- `ast.parse` reads the file as a **syntax tree** rather than as text. A `grep` for `Runner` would
  also match the word inside a docstring or a comment; the tree knows the difference between a name
  the code uses and a name somebody wrote about.
- `Path(__file__).resolve().parents[3]` walks up from `lab/` to the repository root, so the script
  works from any directory. `parents[0]` is `lab`, `[1]` is the day folder, `[2]` is `days`, `[3]` is
  the root — count them once and the path never has to be edited again.
- `REACHES_OUT` is a **list of names, not a list of modules**, because the thing that makes a
  function untestable is that it *calls* out, and a call shows up as a name in the body. A function
  whose file imports `genai` at the top but which never uses it is testable, and this counts it
  correctly.
- `ast.walk(node)` visits every node inside the function, so a call nested three levels deep inside a
  comprehension still counts. Looking only at `node.body` would miss it.
- `isinstance(child, ast.Name | ast.Attribute)` narrows to the two node kinds that can be a name:
  `genai` is a `Name`, `client.models.generate_content` is an `Attribute`. Everything else — numbers,
  strings, operators — cannot be a call target.
- `ast.unparse(child)` turns the node back into source text, so the substring test works against
  `client.models.generate_content` as one string. Comparing `child.attr` alone would only ever see
  the last segment, `generate_content`, and would miss `genai.Client`.
- The function answers **per function**, not per file, because the whole argument of this part is
  that the split runs *through* a module rather than between modules.

Run it against your own repository:

```bash
cd days/day-23-testing-tools-and-callbacks/lab
uv run python count_the_shell.py
```

**Line by line:**

- No key, no network, no model. It reads files and parses them.
- It measures **your** tree as it stands right now, so the numbers below are not an answer to copy.
  They are the answer on the day this part was written, and yours will differ.

Measured on 2026-09-04:

```text
sutra/__init__.py                  0          0      0

34 functions, 16 reach a model or the network -> 47%
18 of them are plain Python with nothing to be nondeterministic about.
```

**Three rows in that table are worth more than the total.**

`sutra/config.py` is **0 out of 4**. Every function in it — reading `.env`, choosing a provider,
refusing to run without a key — is pure logic, and it is also the file whose bugs cost you an
evening, because a misconfigured provider fails in a way that looks like a model problem.

`sutra/mechanics.py` is **9 out of 10**, and that is correct: it is Day 2's demonstration file, and
demonstrating what a model does requires a model. Nobody should feel bad about that number. It is
what a genuinely stochastic module looks like, and it is one file out of ten.

`sutra/tools.py` has **no functions at all**. It is Day 4's tool declarations: dictionaries
describing functions to a provider. A file with no functions cannot be nondeterministic, and it can
still be wrong — a required parameter missing from a schema is a bug that surfaces only as the model
behaving strangely. That is testable today, with an assertion about a dictionary.

So the shape of the answer is not "five percent of the system is unpredictable". It is: **the line
runs through your package module by module, and exactly one module is on the far side of it.**

## When it breaks

The measurement lies in one direction, and it is worth knowing which.

A function that calls another function which calls the model is counted as **pure**, because its own
body names nothing that reaches out. `sutra/desk/multi_turn.py` shows 1 of 2 reaching out, and the
other one is a wrapper around the first. So the real proportion of *behaviour* that depends on a
model is higher than 47%.

That does not weaken the argument; it sharpens it. A wrapper around a model call is testable exactly
because the call can be handed in from outside — which is the seam [1.3](1.3-the-seam.md) is about,
and the reason this number is a starting point rather than a verdict.

The other failure is the honest one. Run this against a fresh clone where the package is still empty
and you get:

```text
ZeroDivisionError: division by zero
```

The guard is already in the script — `share = 100 * reaching / total if total else 0` — and it is
there because an empty package is a real state on the first day of a project, not an impossible one.

## In production

**A real team does not run this script; they have the number already.** They know which modules are
"the model bits", because those are the ones nobody can debug on a Friday afternoon. The habit worth
taking is not the script, it is the question: *for this function, is there any input that produces
two different outputs?* If the answer is no, it has no excuse.

**What changes at scale** is that the boundary moves. A system with one model call has a clean split.
A system with a planner, a router, three sub-agents and a summariser has model calls at five levels,
and "the deterministic shell" is no longer one ring around one core — it is the mortar between the
bricks. Teams that survive this write the rule down: **model calls happen in named places, and
nowhere else.** Then the shell is testable by construction rather than by luck, and a reviewer can
check the rule with `grep`.

**The failure that only appears with real traffic** is a function that is deterministic on your
machine and not in production, because it reads a clock, a random number or an environment variable.
`datetime.now()` inside a business rule is the classic one: green all week, red the first time the
suite runs across midnight. This script does not catch those, because they are not model calls.
Day 24's quota window is exactly such a function, which is why tomorrow's tests take the clock as a
parameter instead of reading it.

**The review comment a senior engineer leaves:** *"this whole file is dictionary lookups and string
formatting, and it has no tests. Which part of it did you think was nondeterministic?"*

**The interview question:** *"how do you test something built on an LLM?"* The answer that shows you
have done it: *"I split it. Most of what I write is not the model — it's tool bodies, policy
callbacks, retry rules, schema handling — and that half is ordinary Python with ordinary unit tests.
The model itself gets evals, which are a different instrument: scored, sampled, allowed to be
imperfect. The mistake is letting the second half's difficulty become an excuse for skipping the
first."*
