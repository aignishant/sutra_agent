# 1.4 — Four doubles, and the two Sutra needs

## One-line answer

There are four useful kinds of stand-in — **dummy** (must never be called), **stub** (answers with a
fixed value), **spy** (answers, and remembers what it was asked) and **fake** (a working
implementation with a shortcut) — and Sutra needs the stub and the spy for tools, and the fake for
anything that has rules of its own.

## The story

The first-aid course happens in a room with the chairs pushed back, and on the floor there is a
plastic torso.

It is not a person. It has no arms, no legs and half a head. But it has a chest that resists exactly
as much as a chest resists, and somewhere inside it there is a little device that clicks when you
press hard enough and deep enough. Press too softly and it stays silent. That click is the entire
reason the thing exists.

Along the wall there are other props. A folded blanket that stands in for a casualty in the
recovery-position exercise; nobody presses on it, it is just there so the space is occupied. A poster
of a face with the airway drawn in. And, in the cupboard, a full-body mannequin with a working
one-way valve and a bag you can actually ventilate.

Four objects, and none of them is a person. What separates them is not how realistic they look. It is
**which question each one can answer.** The blanket answers none. The torso answers *was the
compression deep enough*. The valve mannequin answers *did the air go into the lungs and not the
stomach*. Choosing between them is choosing what you want to find out.

## The idea in plain language

A **test double** is any object handed to your code in place of the real collaborator
([1.3](1.3-the-seam.md)). The word covers four different things that people frequently confuse, and
the confusion is expensive, because the four differ in exactly what a test can then assert.

**A dummy** is a placeholder. It exists because a parameter has to be filled and the code path under
test is not supposed to reach it. The right dummy does not return an innocuous value; it **raises**,
so that if the code path *does* reach it the test fails loudly rather than passing on a lie.

**A stub** answers with a canned value. Its whole job is to control the input to the code under test:
*given that the knowledge base returns this article, does the summariser produce that summary?* A
stub does not remember anything and cannot be asked questions afterwards.

**A spy** answers and also records. It keeps a list of what it was called with, so the test can assert
on the **interaction** rather than only on the return value: *the audit call happened, and it happened
once, and it carried this id.* Anything you want to check about "did my code talk to its collaborator
correctly" needs a spy.

**A fake** is a real implementation with a shortcut — a dictionary instead of a database, an
in-memory list instead of a queue. It has behaviour of its own: it can raise on an unknown key, it
can enforce a uniqueness rule, it can return things in the order they went in. A fake is the only
double that can be *wrong in an interesting way*, which is both its value and its danger.

There is a fifth word in circulation, **mock**, and it means different things to different people. In
its strict sense it is a spy with the expectations declared **in advance**: you say what calls you
expect before running the code, and the double itself fails the test if reality differs. In everyday
speech "mock" has come to mean "any double at all", which is why this part avoids the word. When
somebody says *"just mock it"*, the useful reply is *"as a stub, or as a spy?"*

**Which two does Sutra need?** For a tool, a stub for `.state` and a spy for `save_artifact` — and in
practice they are the same small object, because the stub half is a dictionary and the spy half is a
list ([3.2](../03-testing-tools/3.2-the-fake-tool-context.md)). For anything with rules of its own —
session state, a quota counter, a knowledge base — a fake, because a stub cannot express a rule and a
rule is what you want to test against.

## Why Sutra needs it

Because "write a fake" is not a decision you get to make once. Sutra is about to acquire doubles for
a tool context (today), a session state object (today, in
[5.2](../05-failure-lab/5.2-the-fake-that-could-not-fail.md)), a quota ledger (Day 24), a skill
loader (Day 30) and an MCP server (Phase 5) — and each time the question is the same: *what do I want
to be able to assert?*

If the answer is "the value my code produced", a stub is enough and anything more is wasted work. If
the answer is "that my code called the thing correctly", nothing but a spy will do, and reaching for
a stub means writing an assertion you cannot make. Getting that wrong is how people end up with tests
that are elaborate and prove very little.

## The paper behind it

**Mock roles, not objects** · `doi:10.1145/1028664.1028765` · 2004 ·
<https://doi.org/10.1145/1028664.1028765>

It claimed that a double should stand for a **role in your design** — an interface you named and own
— rather than for a concrete class from someone else's library, because a suite full of doubles of
other people's classes is a suite that has copied their API into your tests.

Read it after the parts: [`papers/01-mock-roles-not-objects.md`](../../papers/01-mock-roles-not-objects.md).

## The mechanism

One collaborator, four doubles, and the same code under test running against each.

```python
# days/day-23-testing-tools-and-callbacks/lab/doubles.py
class DummyKb:
    """Passed because the signature demands an argument. Calling it is a bug in the test."""

    def article(self, article_id: str) -> str:
        raise AssertionError("the dummy was called - this code path was supposed to skip the KB")

    def record_read(self, article_id: str) -> None:
        raise AssertionError("the dummy was called")


class StubKb:
    """Answers with a fixed value, so the test controls the input to the code under test."""

    def article(self, article_id: str) -> str:
        return "Refunds are issued to the original payment method."

    def record_read(self, article_id: str) -> None:
        pass


class SpyKb:
    """Answers, and remembers what it was asked, so the test can assert on the interaction."""

    def __init__(self) -> None:
        self.reads: list[str] = []

    def article(self, article_id: str) -> str:
        self.reads.append(article_id)
        return "Refunds are issued to the original payment method."

    def record_read(self, article_id: str) -> None:
        self.reads.append(f"audit:{article_id}")


class FakeKb:
    """A working implementation with a shortcut: a dict instead of a database."""

    def __init__(self, articles: dict[str, str]) -> None:
        self.articles = articles
        self.audit: list[str] = []

    def article(self, article_id: str) -> str:
        if article_id not in self.articles:
            raise KeyError(article_id)
        return self.articles[article_id]

    def record_read(self, article_id: str) -> None:
        self.audit.append(article_id)


def summarise_article(article_id: str, kb: object) -> dict[str, str]:
    """The code under test: read one article, audit the read, return the first sentence."""
    text = kb.article(article_id)
    kb.record_read(article_id)
    return {"status": "ok", "summary": text.split(".")[0] + "."}
```

**Line by line:**

- `DummyKb.article` raises `AssertionError` rather than returning `""` or `None`. This is the whole
  difference between a dummy that works and a dummy that hides a bug: if the code path under test
  unexpectedly reaches the knowledge base, an empty string would sail through and the test would go
  green having tested the wrong path. `AssertionError` is chosen over `RuntimeError` because pytest
  presents it as a failed assertion, which is what it is.
- `StubKb.record_read` is `pass`, not a raise. A stub is not a dummy: the audit call is *allowed* to
  happen, the test simply has nothing to say about it.
- `SpyKb.reads` is created in `__init__`, not as a class attribute. A list on the class would be
  shared by every instance ever created, so two tests would see each other's calls — the exact
  cross-test leak [2.3](../02-pytest-house-rules/2.3-fixtures.md) exists to prevent.
- `SpyKb.record_read` appends `f"audit:{article_id}"` rather than the bare id, so one list can record
  two different kinds of call and the assertion can still tell them apart. A spy with one list per
  method is also fine; a spy with one list and no labels is a spy you cannot make a precise assertion
  against.
- `FakeKb.article` **raises `KeyError` on an unknown id**, which is the line that makes it a fake
  rather than a stub. It has a rule, and the rule matches the real collaborator's rule. A test can
  now check what the code does when an article is missing, which no stub can express.
- `FakeKb.__init__` takes the articles as an argument, so each test builds the world it needs. A fake
  with hard-coded contents is a stub with extra steps.
- `summarise_article(article_id, kb)` takes the collaborator as a **parameter**. That is the seam from
  [1.3](1.3-the-seam.md) applied to a collaborator that ADK does not supply — nobody handed it in, so
  the code had to be written to accept it.
- The annotation is `kb: object` and not `kb: RealKnowledgeBase`, which is honest: this function needs
  *something with those two methods*. Naming the real class in the annotation would suggest a
  constraint Python does not enforce, and would be the beginning of the mistake the paper is about.

**Line by line:**

- Pure Python, no imports at all beyond the file itself. Every double in this day costs nothing to
  run.

Measured on 2026-09-04:

```text
stub  -> Refunds are issued to the original payment method.
spy   -> calls recorded: ['KB-104', 'audit:KB-104']
fake  -> Refunds take five working days. | audit: ['KB-104']
fake  -> unknown id raises, exactly as the real one would: KeyError('KB-999')
dummy -> the dummy was called - this code path was supposed to skip the KB
real  -> opens a connection; never in a unit test
```

**Line 2 is what a spy buys you.** `['KB-104', 'audit:KB-104']` is a claim no stub could support:
that the code read the article *and then* recorded the read, in that order, for that id. If a refactor
drops the audit call, the return value is unchanged and only the spy notices.

**Line 4 is what a fake buys you.** `KeyError('KB-999')` came out of the double, not out of a
`pytest.raises` you wrote — the fake has the real thing's rule inside it, so the test of the unhappy
path is a genuine test rather than a rehearsal of your own assumption.

**Line 5 is what a dummy buys you.** It failed. That is the correct outcome for a dummy that gets
called, and it is why `DummyKb` raises instead of returning.

## When it breaks

The most common mistake is reaching for a spy when a stub would do, and then asserting on the calls
because the spy makes it possible. That produces a test that is coupled to *how* the code works
rather than *what it produces*, and it goes red on every harmless refactor:

```text
AssertionError: assert ['KB-104', 'audit:KB-104'] == ['KB-104']
```

That failure means somebody added an audit call. Whether that is a bug depends entirely on whether
auditing is part of the contract. If it is, the assertion is right and the code was wrong. If it is
not, the test was over-specified and has now cost an afternoon for nothing. **Assert on an interaction
only when the interaction is the requirement.**

The second mistake has a quieter failure: a fake that drifts away from the real thing. `FakeKb` raises
`KeyError`; if the real client actually returns `None` for a missing article, every test of the
unhappy path is testing a world that does not exist, and nothing anywhere goes red.
[5.2](../05-failure-lab/5.2-the-fake-that-could-not-fail.md) is that failure, measured against ADK's
own state object.

## In production

**A team keeps its fakes in one place and treats them as product code.** An `InMemoryKb` that lives
beside the real one, imports nothing from the tests, and is reviewed with the same seriousness — because
a fake nobody maintains becomes a fake that is wrong, and a wrong fake is worse than no tests at all.
ADK does exactly this with `InMemorySessionService` and `InMemoryArtifactService`: they ship in the
package, they are not test helpers, and they are the reason so much of the last week has been testable
offline.

**What changes at scale** is that fakes need their own tests. The mature pattern is a **contract test**:
one suite of assertions run twice, once against the fake and once against the real implementation, so
they cannot drift without something going red. The real run sits behind a marker
([2.5](../02-pytest-house-rules/2.5-markers-and-the-not-live-line.md)) and runs on a schedule rather
than on every commit. This is the single most valuable thing on this page and almost nobody does it
until they have been burned.

**The failure that only appears with real traffic** is the fake that is too kind. An in-memory queue
that never loses a message, a fake HTTP client that never times out, a fake state store with no size
limit — every one of them makes the code look correct and leaves the real failure mode untested. When
you write a fake, the useful question is not *"does this behave like the real one on a good day"* but
*"what does the real one do on a bad day, and can my fake do that too?"*

**The review comment a senior engineer leaves:** *"this is a spy but the test only checks the return
value — use a stub and delete the recording, or keep the spy and assert on the call you actually care
about."*

**The interview question:** *"what's the difference between a stub and a mock?"* The answer that shows
you have used both: *"a stub controls what my code receives, so I can test the output. A mock — or a
spy, depending on who's asking — records what my code sent, so I can test the interaction. I reach for
the second only when the interaction is the requirement, because otherwise I've written a test that
fails every time somebody refactors something harmless."*
