# 1.3 — The seam: test up to the boundary

## One-line answer

ADK hands a tool an object with **46 public members**, a real Sutra tool touches **one** of them, and
that gap — 2.2% — is the seam: the place where you can substitute something you built for something
the framework normally supplies, and test everything on your side of it.

## The story

An electric kettle has a plug on the end of its cable, and that plug is the most important part of
the design.

Not because it carries current — the cable does that — but because it is where the kettle stops. On
one side there is a factory that knows about heating elements and cut-off switches and how much water
a household boils. On the other side there is a power station, a grid, a substation and a set of
wires in your wall that nobody in the kettle factory has ever seen.

Because the plug exists, the factory can test a kettle. They do not need a power station. They need
230 volts at two pins, and they can produce that on a bench.

If kettles were sold hard-wired into the wall, testing one would mean building a house.

## The idea in plain language

A **seam** is a place in a program where you can change the behaviour without editing the code on
either side of it. The word is worth learning because it names something you will otherwise only
notice by its absence.

Here is the seam that matters today, in the plainest possible terms.

In ADK, a **tool** is a function you write. The framework calls it. If the function's last parameter
is named `tool_context`, the framework fills that parameter in with an object carrying the session,
the state, the artifact store and a great deal more — and, crucially,
**it does not show that parameter to the model** (that is Day 11's rule; see
[11.1.1](../../../day-11-tool-context/parts/01-the-extra-parameter/1.1-the-parameter-the-model-never-sees.md)).

Read that again, because the whole day turns on it: **the context is an ordinary function argument.**
It arrives from outside. Which means a test can pass a different one.

That is the seam. On the framework's side there is a runner, a session service, an artifact service,
an event loop and a model. On your side there is a function with a parameter. To test your side you
do not need the framework — you need something with the right shape in that parameter.

Two more terms, defined here because the rest of the day uses them constantly:

- A **test double** is any object you pass in place of the real collaborator. The name comes from
  film: a stand-in who does the dangerous part. [1.4](1.4-four-doubles.md) sorts them into four
  kinds.
- **Duck typing** is Python's rule that an object is acceptable if it has the attributes you use, not
  if it belongs to a particular class. The tool says `tool_context.state[...]`; Python asks the
  object for `.state`; anything that has one will do. This is what makes the seam free rather than
  something you have to build.

## Why Sutra needs it

Because without a seam, testing one tool means constructing the entire runtime.

Count what that would involve. `Runner(...)` in `google-adk` 2.7.1 takes **eleven** arguments — an
app, an app name, an agent, a node, plugins, an artifact service, a session service, a memory
service, a credential service, a close timeout and a session-creation flag. Then a session has to be
created, a message assembled, the async loop driven, and events consumed until the right one appears.
All of that, to find out whether `remember_triage` rejects a severity it does not recognise.

Sutra has tools from Day 10, Day 11, Day 17 and Day 18, and every one of them has decisions inside it
that are worth pinning down. If pinning one down costs an entire runtime, none of them will ever be
pinned down. The seam is what makes [3.2](../03-testing-tools/3.2-the-fake-tool-context.md)'s
five-line stand-in a reasonable thing to write.

## The mechanism

Measure the seam rather than describing it. This asks the installed ADK how big the object is, and
then asks a real tool how much of it it uses.

```python
# days/day-23-testing-tools-and-callbacks/lab/the_seam.py
import inspect

from google.adk.agents.context import Context
from google.adk.agents.readonly_context import ReadonlyContext
from google.adk.runners import Runner


def members(cls: type) -> tuple[list[str], list[str]]:
    """The properties and public methods a class defines itself, ignoring what it inherits."""
    props = sorted(n for n, v in vars(cls).items() if isinstance(v, property))
    meths = sorted(
        n for n, v in vars(cls).items() if inspect.isfunction(v) and not n.startswith("_")
    )
    return props, meths


def remember_triage(ticket_id: str, severity: str, tool_context: Context) -> dict[str, str]:
    """A real Sutra tool: it writes two keys and reads nothing else off the context."""
    tool_context.state["ticket_id"] = ticket_id
    tool_context.state["severity"] = severity
    return {"status": "ok", "ticket_id": ticket_id, "severity": severity}
```

**Line by line:**

- `vars(cls)` rather than `dir(cls)`. `dir` walks the whole inheritance chain and would count
  `ReadonlyContext`'s members twice — once on the parent and once on the child. `vars` returns only
  what this class declares itself, which is what makes the two lines of the report add up instead of
  overlapping.
- `isinstance(v, property)` finds the attributes that look like plain data from the outside —
  `ctx.state`, `ctx.session` — but are actually computed. They matter for a double, because a double
  has to provide them as *something*, and a plain attribute is enough.
- `inspect.isfunction(v)` finds the methods. Note that `save_artifact` is in this list, which is why
  the double in [3.2](../03-testing-tools/3.2-the-fake-tool-context.md) needs a method and not just a
  dictionary.
- `not n.startswith("_")` drops the private members. A double that has to reproduce a private method
  is a double that has bound itself to an implementation detail, and it will break on an upgrade that
  breaks nothing else.
- `remember_triage` is written **exactly as ADK wants a tool written**: ordinary parameters first,
  `tool_context` last, a `dict` returned. Nothing about it is test-shaped. That is the point — the
  seam is already there, put in by the framework's own convention, and today is simply the day
  somebody uses it.
- The annotation `tool_context: Context` is documentation for a human reader. Python does not check
  it at runtime, which is exactly why a double with the right shape works, and exactly why
  [5.2](../05-failure-lab/5.2-the-fake-that-could-not-fail.md) is a real danger.

**Line by line:**

- It imports ADK, so it is not instant, but it makes no model call and needs no key.

Verified against the installed `google-adk` 2.7.1 source on 2026-09-04 — `google/adk/agents/context.py`
and `google/adk/agents/readonly_context.py`, read rather than remembered:

```text
Runner(...) takes 11 arguments
ReadonlyContext: 8 properties, 1 methods
Context:         21 properties, 16 methods
the object a tool is handed has 46 public members
remember_triage touches 1 of them: ['state']
a fake with just ['state'] is 2.2% of the real class, and enough
```

**That last line is the entire argument of this part.** Forty-six members exist; the tool needs one;
therefore the stand-in needs one. Everything else in `Context` — `save_artifact`, `search_memory`,
`request_confirmation`, `run_node`, `telemetry_context` — belongs to tools that use those things, and
a double for *this* tool has no business pretending to offer them.

**One name deserves a warning, and it is a 1.x → 2.x trap in disguise.** In ADK 2.x, `ToolContext`
and `CallbackContext` are **the same class**: both are aliases for `Context`. Verified on 2026-09-04
by asking the installed package — `ToolContext is Context` is `True`, and so is
`CallbackContext is Context`. Tutorials written against ADK 1.x talk about them as two different
types with two different capability sets, and a double built from that belief will offer the wrong
half. When you write the stand-in, build it from what your function actually touches, not from what
an article says the type contains.

## When it breaks

The seam is only as good as the shape you give the double, and getting the shape wrong produces one
of exactly two errors.

Pass an object with no `state` at all and Python says so immediately:

```text
AttributeError: 'FakeToolContext' object has no attribute 'state'
```

That is the good failure: loud, instant, and it names the missing member. Add the attribute and move
on.

The bad one is passing something with the right attribute and the wrong behaviour, which produces no
error at all — a green test and a broken system. That is
[5.2](../05-failure-lab/5.2-the-fake-that-could-not-fail.md), and it is the reason this day has a
failure lab rather than a warning.

There is also a version of the seam that is not there. If a function reaches out and *fetches* its
collaborator instead of receiving it — `client = genai.Client()` in the middle of a function body —
there is no argument to substitute, and the only ways in are monkey-patching or an environment
variable. Both work; neither is as good as a parameter. When you find yourself unable to test
something, the first question is not *"how do I mock this"* but *"where should this have been passed
in?"*

## In production

**The professional version of this is called dependency injection, and it is one sentence long:** a
function receives what it needs instead of going and getting it. ADK already does this for you with
`tool_context`, which is why today is easy. Your own code will not do it unless you decide to, and
the decision shows up as a parameter with a default: `def summarise(article_id, source=None)` with
`source = source or VendorArticleSource()` inside. Production passes nothing; the test passes a
double.

**What changes at scale** is the number of seams. One is a gift. Twenty parameters on every function
is a different disease, and the cure is to group collaborators into a small object with a name — a
`Deps` dataclass, a context — which is precisely what ADK has done with `Context`. The lesson runs
both ways: frameworks converge on one context object because forty seams are unmanageable, and then
the object gets large enough that nobody can double it faithfully. Both problems are real; you are
choosing which one to have.

**The failure that only appears with real traffic** is the seam that leaks. A double that returns
instantly hides the fact that the real collaborator takes 400 ms and is called in a loop, so the code
is correct and unusably slow. Unit tests through a seam cannot see performance, by construction. That
is not an argument against them; it is an argument for having one test that goes through the real
thing, which Day 31 wires in behind a marker.

**The review comment a senior engineer leaves:** *"this function constructs its own client, so the
only way to test it is to patch a module attribute. Take the client as an argument and the test
becomes three lines."*

**The interview question:** *"how would you test a tool that writes to session state without booting
the framework?"* The answer that shows you have done it: *"the context arrives as a parameter, so I
pass my own. The tool reads one thing off it, so my stand-in has one attribute. I assert on the
dictionary afterwards. The only thing I have to be careful about is that a plain dict behaves
differently from the framework's state object for prefixed keys — so anything about scope gets a test
against the real state class, not the dict."*
