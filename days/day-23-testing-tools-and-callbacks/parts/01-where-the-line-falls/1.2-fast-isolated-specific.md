# 1.2 — Fast, isolated, specific

## One-line answer

A test earns its place by being **fast** (one tool call here is 1.03 microseconds, against 419 ms
for a single TLS handshake to the model host — a ratio of about **408,000 to one**), **isolated**
(green on a train, with no key in the environment) and **specific** (its name tells you what broke
before you open the file).

## The story

There is a weighing scale in the corner of the bathroom.

You stand on it most mornings, not because you are especially disciplined but because it takes no
effort at all. Step on, look down, step off. If the number drifts, you notice within days, because
you have a long line of numbers to compare it against.

Now imagine the same scale, except that to use it you have to carry it to a shop across town where
somebody calibrates it and reads it for you. It gives a better number. You would use it once a year,
if that, and you would find out about a problem a year late.

And imagine a third scale, the modern kind, which shows nothing at all unless the house wifi is up.
It is accurate, it is fast, and on the morning the router is dead it tells you nothing — so you stop
trusting it, because a thing that is sometimes silent is a thing you stop looking at.

The good scale is not the accurate one. It is the one that is cheap enough and reliable enough to be
used every single day.

## The idea in plain language

Three properties, and every one of them is really a statement about human behaviour rather than
about software.

**Fast** means the test costs so little that running it is not a decision. If the whole suite runs
while your hands are still on the keyboard, you run it after every change and you find out
immediately which change broke it. If it takes long enough that you go and do something else, you
batch up ten changes first, and now the red result does not tell you which of the ten was the crime.
Speed is not about efficiency; it is about **keeping the distance between a mistake and its
discovery short**.

**Isolated** means the test depends on nothing outside itself: no network, no API key, no database,
no file left behind by a previous test, no wall clock, no other test having run first. The reason is
not purity. It is that every external dependency is a way for the test to go red without your code
being wrong, and a test that cries wolf gets ignored — and then the one real failure is ignored too.
The plain version of the rule: **a test must be green on a plane.**

**Specific** means that when it fails, the name and the message tell you the crime.
`test_lookup` failing tells you nothing. `test_an_unknown_ticket_returns_not_found_rather_than_
inventing_one` failing tells you that somebody made the tool hallucinate a ticket, and you know
which line to open before you have opened anything.

A useful way to hold all three: **fast decides how often it runs, isolated decides whether you
believe it, specific decides how long the fix takes.** A test missing any one of the three quietly
stops being a test and becomes decoration.

## Why Sutra needs it

Because the very next thing Sutra does is add a test suite to `./m check`, and `./m check` runs on
**every change** — that is the whole point of it, and Day 31 makes it a gate.

A suite that needs `GOOGLE_API_KEY` cannot run in that gate, because the gate must work on a machine
that has no key. A suite that spends model requests cannot run in that gate, because the free tier
gives twenty per day and the gate would eat them before lunch. A suite that takes long enough to be
annoying will be skipped with `--no-verify`, which is the same as not having it.

So the three properties are not advice. They are the acceptance criteria for the thing you are about
to build, and the failure lab in [5.1](../05-failure-lab/5.1-the-test-that-phoned-the-model.md) is
what happens when one of them is dropped.

## The mechanism

Two of the three can be measured rather than asserted. This script does exactly that.

```python
# days/day-23-testing-tools-and-callbacks/lab/three_properties.py
import os
import socket
import ssl
import time

TICKETS = {"4521": "Refund not received", "4522": "Login loop after password reset"}

HOST = "generativelanguage.googleapis.com"


def lookup_ticket(ticket_id: str) -> dict[str, str]:
    """The deterministic half of a tool: a dict lookup with an honest miss."""
    if ticket_id not in TICKETS:
        return {"status": "not_found", "ticket_id": ticket_id}
    return {"status": "ok", "ticket_id": ticket_id, "title": TICKETS[ticket_id]}


def time_pure(rounds: int) -> float:
    """Seconds to call the tool `rounds` times with no network and no framework."""
    start = time.perf_counter()
    for _ in range(rounds):
        lookup_ticket("4521")
    return time.perf_counter() - start


def time_one_handshake() -> float | str:
    """Seconds to open one TLS connection to the model host - no request, just the door."""
    start = time.perf_counter()
    try:
        with socket.create_connection((HOST, 443), timeout=10) as raw:
            with ssl.create_default_context().wrap_socket(raw, server_hostname=HOST):
                pass
    except OSError as exc:  # offline is a result, not a crash
        return f"{type(exc).__name__}: {exc}"
    return time.perf_counter() - start
```

**Line by line:**

- `time.perf_counter()` rather than `time.time()`. `perf_counter` is **monotonic**: it cannot jump
  backwards when the operating system adjusts the clock, and it has the finest resolution Python
  offers. `time.time()` measures the wall clock, which is the wrong instrument for a duration and
  the same mistake [Day 22](../../../day-22-structured-logging/parts/01-a-line-you-can-query/1.4-timestamps-are-not-an-order.md)
  measured on log lines.
- `rounds` is a parameter and the loop is inside the timer, because timing **one** call of something
  this small measures the timer, not the call. Ten thousand rounds divided by ten thousand is a
  number you can believe.
- The handshake opens a socket and wraps it in TLS and then **does nothing else**. No request body,
  no model, no key. This is deliberately the cheapest possible version of "talking to the model
  host", so the comparison is generous to the networked side and still loses by five orders of
  magnitude.
- `socket.create_connection((HOST, 443), timeout=10)` — port 443 is HTTPS, and the timeout is there
  because a socket with no timeout can hang until the operating system gives up, which on a bad
  network is a long time to stare at a blank terminal.
- `ssl.create_default_context()` rather than a hand-built context: the default already verifies the
  certificate and picks a safe protocol version, and hand-building one is how people accidentally
  turn verification off.
- `except OSError` returns **a string instead of raising**, because being offline is a legitimate
  outcome of this script and not a bug in it. `OSError` is the parent of `socket.gaierror`,
  `ConnectionRefusedError` and `TimeoutError`, so one clause covers every way the network can be
  absent. This is Principle 10 in miniature: the error becomes a reported fact rather than a
  traceback that hides the rest of the output.
- The return type is `float | str` and the caller checks with `isinstance`, which is honest about the
  two outcomes rather than returning `-1.0` and hoping somebody notices.

**Line by line:**

- Needs the network for the second measurement only. With no network it prints the error text and
  the rest of the script still runs.

Measured on 2026-09-04:

```text
fast:     10000 pure tool calls took 10.3 ms
          one call is 1.03 microseconds
isolated: one TLS handshake to generativelanguage.googleapis.com took 419.2 ms
          that is 408,753 pure calls, for zero asserts
isolated: GOOGLE_API_KEY is absent in this shell
          a test that needs it is green on your laptop and red in CI
```

**Read the third line twice.** 419 milliseconds buys you *the connection*. Not a question, not an
answer, not a token. Before the model has been asked anything at all, a networked test has already
spent the time that four hundred thousand deterministic assertions would have taken.

And the last two lines are the isolation half, produced by nothing more exotic than
`os.environ.get("GOOGLE_API_KEY")`. In the shell this ran in, the key is absent — which is exactly
the state of a continuous-integration machine, and exactly the state in which a test that needs one
fails for a reason that has nothing to do with your code.

## When it breaks

Run the script with the network unplugged and the middle measurement is replaced by the real error
rather than a crash. Reproduced on 2026-09-04 by pointing `HOST` at
`generativelanguage.googleapis.invalid`, which no resolver can answer:

```text
isolated: no network here - gaierror: [Errno 11001] getaddrinfo failed
```

`getaddrinfo failed` is DNS: the machine could not turn the hostname into an address. `[Errno 11001]`
is the Windows code for it; on Linux the same condition prints `[Errno -2] Name or service not
known`. Both mean the same thing and both are worth recognising on sight, because they are what a
networked test prints in CI when the runner has no outbound access — and the first instinct is
always to suspect your credentials instead.

The subtler failure is the one with no error text at all: a test that *is* fast and isolated but is
named `test_it_works`, so when it goes red you learn only that something, somewhere, is wrong.
[2.2](../02-pytest-house-rules/2.2-arrange-act-assert.md) has that failure side by side with its
cure, and the difference in the output is larger than you would expect.

## In production

**Teams put a number on "fast" and enforce it.** A common rule is that the unit suite must finish
inside a handful of seconds and anything slower moves behind a marker
([2.5](../02-pytest-house-rules/2.5-markers-and-the-not-live-line.md)). The number matters less than
having one, because without it the suite gets slower one test at a time and nobody can point at the
change that did it.

**Isolation gets enforced by the environment rather than by good intentions.** The mature version is
a CI job with no secrets at all in it: not "please don't call the network" but "there is nothing to
call the network with". Some teams go further and block outbound sockets in the test process, so a
test that reaches out fails loudly instead of quietly costing money.

**What degrades at scale** is isolation between tests rather than from the outside world. At thirty
tests nobody shares state by accident. At three thousand, somebody has a module-level dictionary that
one test writes and another reads, and the suite passes in file order and fails when it is run in
parallel or shuffled. The tool that finds it is running the suite in a random order deliberately —
and the fix is always the same shape, which is
[2.3](../02-pytest-house-rules/2.3-fixtures.md)'s fixture.

**The failure that only appears with real traffic** is the test that is fast on your machine because
of a warm cache. First run after a clean checkout takes far longer, and the person who feels it is
the new joiner on their first morning, who now believes the suite is slow. Measure from cold at least
once.

**The review comment a senior engineer leaves:** *"this test needs a key, so it won't run in CI —
which means it will only ever run when someone remembers. Either fake the collaborator or mark it
`live` and write the fake version as well."*

**The interview question:** *"what makes a good unit test?"* The answer that sounds like experience:
*"fast enough that running it isn't a decision, isolated enough to be green offline, and named so
that the failure line tells me what broke. If I have to open the file to find out what a red test
means, the test needs a better name, not a better assertion."*
