# 3.1 — A tool is a function first

## One-line answer

A tool with no `tool_context` parameter is an ordinary Python function, so testing it needs no
framework at all — and the assertion worth writing first is the **negative** one, that an unknown
ticket comes back as `not_found` and does **not** carry a title.

## The story

The repair shop writes everything on a job card before anyone touches the machine.

Customer, item, what it is doing wrong, what was found, what was replaced, what it cost. The card
travels with the machine down the bench, and by the time it reaches the counter the whole history is
on one side of one piece of paper.

The useful thing about the card is that it is complete on its own. The man at the counter can read it
without the machine in front of him. The parts clerk can price it without the customer present. If
the shop closes and a different technician opens it in the morning, the card still says what
happened.

Nobody designed it that way to be clever. It is just what a written record is: a thing that makes
sense away from the situation that produced it.

## The idea in plain language

In [Day 10](../../../day-10-function-tools/LESSON.md) you learned that ADK builds a tool's schema by
reading your function — the name, the parameters, the type hints, the docstring. Nothing about the
function is special. There is no base class to inherit from, no decorator to apply, no registration
call. You write a function; ADK reads it.

That has an immediate consequence for testing that is so simple it is easy to walk past:
**a tool can be imported and called like any other function.**

```
result = lookup_ticket("4521")
```

That is the whole technique for a tool that takes no context. There is no runner, no session, no
event, no model. And an enormous amount of the behaviour worth pinning down lives exactly here: what
happens on a miss, what happens on a malformed id, what the return dictionary's keys are called, what
it does *not* contain.

That last one deserves its own paragraph, because it is the assertion people leave out.

A tool's return value is not read by a person. It is read by a language model, which will use whatever
it finds to compose an answer for a customer. So a tool that answers *"I could not find ticket 9999"*
by returning `{"status": "not_found", "title": ""}` has handed the model an empty title, and the model
will do something with it — most likely say the ticket exists and has no subject. The bug is not in
the model. The bug is a key that should not have been there.

Which gives the rule this part is really about: **for a tool, assert what is absent as carefully as
what is present.** `assert "title" not in result` is the line that stops a lie downstream, and it
costs one line.

## Why Sutra needs it

Because Sutra's tools have accumulated real decisions and none of them is currently checked.

`lookup_ticket` decides what a miss looks like. `remember_triage`
([Day 17](../../../day-17-state-scopes-and-lifetimes/LESSON.md)) decides which severities are
acceptable and refuses the rest. `save_note` ([Day 18](../../../day-18-artifacts-that-survive/LESSON.md))
decides how a filename is derived from a ticket id, and it calls `int(ticket_id)` on purpose so that
`"4521 "` and `"4521"` cannot become two different files. Every one of those is a sentence somebody
wrote once, in a hurry, and nothing anywhere would notice if it changed.

Testing the ones with no context is where you start, because there is nothing to learn first. By the
end of this part you will have written tests for a third of Sutra's tool surface without touching
ADK at all.

## The mechanism

Three tools, written exactly as ADK wants them, in a module that imports nothing.

```python
# days/day-23-testing-tools-and-callbacks/lab/tools_demo.py
TICKETS = {"4521": "Refund not received", "4522": "Login loop after password reset"}

NOTE_MIME = "text/markdown"


def lookup_ticket(ticket_id: str) -> dict[str, str]:
    """No context at all: the purest kind of tool, and the easiest to pin down."""
    if ticket_id not in TICKETS:
        return {"status": "not_found", "ticket_id": ticket_id}
    return {"status": "ok", "ticket_id": ticket_id, "title": TICKETS[ticket_id]}


def remember_triage(ticket_id: str, severity: str, tool_context: object) -> dict[str, str]:
    """Writes two session-scoped keys. The only thing it needs from the context is `.state`."""
    if severity not in {"low", "normal", "high"}:
        return {"status": "rejected", "reason": f"unknown severity {severity!r}"}
    tool_context.state["ticket_id"] = ticket_id
    tool_context.state["severity"] = severity
    return {"status": "ok", "ticket_id": ticket_id, "severity": severity}
```

**Line by line:**

- `lookup_ticket` returns a **dict, not a string**. That is Day 21's rule — an error is a fact, not a
  sentence — and it is also what makes the test able to ask a question: `result["status"]` is checkable,
  `"Sorry, I could not find that ticket"` is not.
- The miss branch returns `ticket_id` but **not** `title`. Two different shapes for two different
  outcomes, which is what lets the negative assertion exist at all. A tool that always returns the same
  keys with empty values cannot be tested for absence.
- `remember_triage` **validates before it writes**. The order matters: the rejection returns before
  `tool_context.state` is touched, so a bad severity leaves no trace. A version that wrote first and
  validated afterwards would pass a test of the return value and fail a test of the state, which is
  exactly the pair of assertions this day teaches.
- `f"unknown severity {severity!r}"` uses `!r` so that `""` prints as `''` rather than vanishing. A
  rejection message that renders an empty string as nothing at all is a message that describes no
  input.
- `tool_context: object` in the annotation rather than the real `ToolContext`. This is a lab module
  written to have no imports; in `sutra/` the real annotation is right, because the annotation is what
  ADK reads to decide the parameter is the context and to keep it out of the model's schema
  ([11.1.2](../../../day-11-tool-context/parts/01-the-extra-parameter/1.2-detected-by-type-not-by-name.md)).
- `NOTE_MIME` sits at module level as a constant. Constants are the cheapest thing to test and the
  easiest to get wrong: a MIME type that changes breaks an artifact reader silently, and one assertion
  pins it.

Now the tests for the context-free one:

```python
# days/day-23-testing-tools-and-callbacks/lab/test_tools_demo.py
from tools_demo import lookup_ticket


def test_a_known_ticket_returns_its_title() -> None:
    assert lookup_ticket("4521") == {
        "status": "ok",
        "ticket_id": "4521",
        "title": "Refund not received",
    }


def test_an_unknown_ticket_returns_not_found_rather_than_inventing_one() -> None:
    result = lookup_ticket("9999")
    assert result["status"] == "not_found", "a tool that invents a ticket teaches the model to lie"
    assert "title" not in result
```

**Line by line:**

- The first test compares the **whole dictionary** with `==` rather than checking three keys
  separately. That is deliberate: an equality assertion on the whole object also fails when an
  *unexpected* key appears, which is the change nobody writes a test for. pytest's rewriting prints a
  readable diff of the two dicts when it fails, so the usual objection — that whole-object comparison
  gives bad failure messages — does not apply here.
- The second test does **not** compare the whole dictionary, because the interesting claim is about
  absence and an equality assertion would bury it. Two assertions, one positive and one negative, each
  saying one thing.
- The message on the positive assertion explains the *consequence* rather than the expectation:
  a tool that invents a ticket teaches the model to lie. That is the sentence that makes somebody stop
  and fix it properly instead of adjusting the test.
- `assert "title" not in result` has no message, and does not need one: pytest prints
  `assert 'title' not in {...}` with the whole dictionary, which is self-explanatory. Messages are for
  assertions whose failure output says nothing
  ([2.2](../02-pytest-house-rules/2.2-arrange-act-assert.md)).
- Neither test constructs anything. There is no arrange step, because a pure function needs no world —
  which is the fastest possible version of
  [2.2](../02-pytest-house-rules/2.2-arrange-act-assert.md)'s three steps.

```bash

uv run python -m pytest test_tools_demo.py
```

**Line by line:**

- Ten tests in the file altogether, covering all three tools. No key, no network, no ADK import.

Measured with `pytest` 9.1.1 on 2026-09-04:

```text

10 passed in 0.21s
```

Ten assertions about tool behaviour, for a fifth of a second and no quota. This is
[1.1](../01-where-the-line-falls/1.1-the-nondeterminism-excuse.md)'s deterministic shell, being tested
exactly as promised.

## When it breaks

Make the tool invent a title on a miss — return `{"status": "not_found", "title": ""}` — and only one
of the two assertions notices:

```text
E       AssertionError: assert 'title' not in {'status': 'not_found', 'ticket_id': '9999', 'title': ''}
```

The status assertion above it still passes, because the status is still `not_found`. That is the
argument for writing the negative assertion in the first place: the tool is now lying in a way that
every check of the happy path agrees with.

The other failure is the one that catches people importing a tool from `sutra/` for the first time:

```text
E   ModuleNotFoundError: No module named 'sutra'
```

That means pytest is running with a `sys.path` that does not include the repository root. In this
repository it does not happen, because `tests/` has an `__init__.py` and the root holds
`pyproject.toml`, so pytest inserts the root — but it appears immediately if a test file is moved
somewhere else, and the fix is to run pytest from the root rather than to add path manipulation to the
test.

## In production

**Real tool tests are written from the tool's docstring**, because the docstring is what the model
sees. If the docstring promises *"returns the ticket's title and body, or a message saying no such
ticket exists"*, then there are exactly two tests to write and they are already specified. A tool
whose docstring and behaviour disagree is a bug that no amount of prompt engineering will fix, and
this is where it gets caught.

**What changes at scale** is that the return shape becomes an interface with consumers. Once a
dashboard filters on `status == "not_found"`, and a second agent branches on it, and an alert counts
it, that string is a contract and renaming it is a breaking change no Python test notices. Mature
suites pin the vocabulary: one test asserting the **set** of status values a tool can return, so adding
one is a deliberate act rather than a typo.

**The failure that only appears with real traffic** is the input shape nobody imagined. Ticket ids
arrive with whitespace, with a `#` in front, in the wrong case, as integers when the schema said
string. The parametrized test in
[2.4](../02-pytest-house-rules/2.4-parametrize.md) exists for exactly this, and the honest way to grow
it is to add a case every time production produces one.

**The review comment a senior engineer leaves:** *"the happy path is covered but nothing asserts what
the miss looks like. What does the model see when the ticket doesn't exist?"*

**The interview question:** *"what would you test about a tool an LLM calls?"* The answer that shows
you have watched a model misbehave: *"the shape of the return value on both paths, and especially the
absence of keys on the failure path — because the model will use whatever's in that dictionary. An
empty title on a not-found result is how you get an agent confidently describing a ticket that doesn't
exist."*
