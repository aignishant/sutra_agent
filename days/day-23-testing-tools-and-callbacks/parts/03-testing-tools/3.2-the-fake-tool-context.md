# 3.2 — The fake `ToolContext`, in five lines

## One-line answer

The stand-in for ADK's 46-member context is a small class with a `state` dictionary and a
`save_artifact` method that appends to a list — a stub and a spy in one object — and it is enough
because the tool asks Python for `.state`, not for a type.

## The story

The delivery driver is at the gate and you are not at home.

You do not send him the house keys. You do not put him on the family group chat, give him the alarm
code or explain where the spare is kept. You send him four digits that open the pedestrian gate, and
he leaves the parcel inside the porch.

Four digits is the whole of what the job needs. Everything else you own is irrelevant to it, and
handing any of it over would be a decision with consequences and no benefit.

It also means you can check the arrangement works without involving your house at all. Stand at the
gate, type the four digits, watch it open. That test tells you what you needed to know, and nobody had
to move in.

## The idea in plain language

[1.3](../01-where-the-line-falls/1.3-the-seam.md) established the seam: `tool_context` arrives as an
ordinary function argument, so a test can pass its own. This part is what you pass.

The object ADK normally supplies has 46 public members. A tool typically touches one or two. So the
double declares one or two, and **Python does not object**, because Python resolves attributes by name
at the moment they are used rather than checking a type in advance. The annotation on the parameter is
for human readers and static tools; the interpreter never consults it.

That makes the double genuinely small. Two members cover almost every Sutra tool written so far:

**`state`** — a plain dictionary. This is the **stub** half from
[1.4](../01-where-the-line-falls/1.4-four-doubles.md): it holds values a tool reads and accepts values a
tool writes, and the test inspects it afterwards.

**`save_artifact`** — a method that records the call and returns a version number. This is the **spy**
half: `save_note` calls it, and the only way to check that the right filename and the right bytes were
handed over is to keep them.

There is one detail that has to be right and is easy to get wrong: `save_artifact` is **async** in
ADK, so the double's must be too. A double whose method is synchronous will hand back a plain integer
where the tool expects something to `await`, and the failure — `object int can't be used in 'await'
expression` — is confusing precisely because it points at the tool rather than at the double.

The last idea in this part is the one worth arguing about, and
[5.2](../05-failure-lab/5.2-the-fake-that-could-not-fail.md) makes the argument properly: **a plain
dictionary is not the same thing as ADK's `State`.** It is close enough for a tool that reads and
writes unprefixed keys, and it is wrong for anything that depends on a prefix. Knowing which of those
you are testing is the difference between a double that helps and a double that lies.

## Why Sutra needs it

Because from Day 17 onward, most of Sutra's tools take a context, and the ones that do are the ones
with the interesting decisions in them.

`remember_triage` validates a severity and refuses to write on a bad one. `save_note` derives a
filename with `int(ticket_id)` so that whitespace cannot fork a file into two, saves the artifact, and
records `note_file` and `note_version` in state — **in one call**, so that both land on one event. Each
of those is a sentence from a design decision on an earlier day, and each is currently protected by
nothing.

The double is what makes all of them testable in a fifth of a second, and it is also the object Day 24
will extend with a quota counter and Day 30 will extend again for skills. Writing it once, small and
honestly, is worth doing carefully.

## The mechanism

The whole double, and then the tool tests that use it.

```python
# days/day-23-testing-tools-and-callbacks/lab/fake_context.py
class FakeToolContext:
    """A stub for `.state` and a spy for `save_artifact`, in one small object."""

    def __init__(self, state: dict[str, object] | None = None) -> None:
        self.state: dict[str, object] = dict(state or {})
        self.saved: list[tuple[str, object]] = []
        self.next_version = 0

    async def save_artifact(self, filename: str, artifact: object) -> int:
        """Records the call and hands back a version number, exactly as the real one does."""
        self.saved.append((filename, artifact))
        version = self.next_version
        self.next_version += 1
        return version
```

**Line by line:**

- `state: dict[str, object] | None = None` and then `dict(state or {})` — the default is `None`, not
  `{}`. A mutable default argument in Python is created **once**, at function definition, and shared by
  every call, so `def __init__(self, state={})` would give every `FakeToolContext` in the whole suite
  the same dictionary. That is the cross-test leak from
  [2.3](../02-pytest-house-rules/2.3-fixtures.md) arriving through the oldest trapdoor in the language.
- `dict(state or {})` **copies** rather than storing the caller's dictionary. A test that passes a
  starting state and then asserts on its own dictionary afterwards would otherwise be asserting on the
  same object the tool mutated, which proves nothing.
- `self.saved` is a list of `(filename, artifact)` **tuples**, so the spy records both halves of each
  call in order. A dictionary keyed by filename would lose the second save of the same name, which is
  exactly the case the version counter exists for.
- `self.next_version` starts at `0` because ADK's real `save_artifact` returns `0` for the first
  version of a file. A double that started at `1` would produce tests that pass against the double and
  fail against the framework, which is the drift this whole day is trying to avoid.
- `async def save_artifact` — **async**, matching ADK. Verified against the installed `google-adk`
  2.7.1 on 2026-09-04: `Context.save_artifact` is a coroutine function, and so is `load_artifact`. Its
  real signature is
  `save_artifact(self, filename: str, artifact: types.Part, custom_metadata: dict[str, Any] | None = None) -> int`,
  and the double deliberately omits `custom_metadata` and types the artifact loosely — because nothing
  under test passes the third argument, and a double that reproduces parameters nobody uses is making
  claims about ADK that no test checks.
- The parameters are named `filename` and `artifact` because the tool calls them by keyword. A double
  whose parameter names differ works for positional calls and breaks for keyword ones, and the failure
  is a `TypeError` about an unexpected argument.
- There is **no** `session`, `user_id`, `invocation_id` or `search_memory`. The double declares what
  the tools under test touch and nothing else, which is the four-digit gate code rather than the
  keyring.

Now the tests. Note that every one of them ends by inspecting the double.

```python
# days/day-23-testing-tools-and-callbacks/lab/test_tools_demo.py
import pytest
from fake_context import FakeToolContext
from tools_demo import remember_triage


def test_remember_triage_writes_both_keys_and_nothing_else() -> None:
    ctx = FakeToolContext()
    remember_triage("4521", "high", ctx)
    assert ctx.state == {"ticket_id": "4521", "severity": "high"}


@pytest.mark.parametrize("severity", ["urgent", "HIGH", "", "1"])
def test_an_unknown_severity_is_rejected_without_touching_state(severity: str) -> None:
    ctx = FakeToolContext()
    result = remember_triage("4521", severity, ctx)
    assert result["status"] == "rejected"
    assert ctx.state == {}, f"{severity!r} was rejected but state was written anyway"
```

**Line by line:**

- `ctx = FakeToolContext()` is the entire arrange step. One line, no framework — compare that with the
  eleven-argument `Runner` from [1.3](../01-where-the-line-falls/1.3-the-seam.md).
- `assert ctx.state == {...}` compares the **whole** dictionary rather than checking two keys. That is
  what makes the test's name honest: *"writes both keys and nothing else"* is a claim about absence as
  much as presence, and only whole-object equality can make it.
- The parametrized cases are the four ways a severity can be wrong that a real system produces:
  a plausible synonym (`"urgent"`), the right word in the wrong case (`"HIGH"`), nothing at all
  (`""`), and a number the model decided to send instead of a word (`"1"`). Each gets its own reported
  case, so a failure names which one changed behaviour.
- `assert ctx.state == {}` is the assertion that makes the rejection real. Checking only
  `result["status"] == "rejected"` would pass for a tool that says "rejected" and writes anyway — and
  that tool exists, because validating after writing is the easier code to write.
- The message interpolates `severity!r`, so the failure line names the exact input. Without `!r` the
  empty-string case would produce a message with a hole in it.
- The two tests together are the pair this part exists to teach: **what the tool returned, and what it
  did to the world.** A tool with a context always needs both, because the return value goes to the
  model and the state change goes to the next turn.

## When it breaks

Forget a member and Python says which one, immediately:

```text
AttributeError: 'FakeToolContext' object has no attribute 'state'
```

That is the failure you want. It names the missing attribute, it happens on the first run, and the fix
is one line. A double grows exactly this way: run the test, add whatever the error names, repeat.
Trying to guess the full surface in advance produces a double with members nothing uses.

Make `save_artifact` synchronous by removing `async` and the failure moves to the tool instead:

```text
TypeError: object int can't be used in 'await' expression
```

Read that carefully, because the message points at the wrong file. The tool's `await` is correct; it
is the double that is wrong. Any time a `TypeError` mentions `await` and an ordinary type, the first
place to look is whether the double matches the real thing's async-ness.

And the failure with no message at all is the one this day has a failure lab for. A double that has
the right attribute and the **wrong behaviour** produces a green test and a broken system.
[5.2](../05-failure-lab/5.2-the-fake-that-could-not-fail.md) measures exactly that, using the
difference between a plain dictionary and ADK's own `State`.

## In production

**The double lives in `conftest.py` as a fixture, not in each test file.** One
`fake_context` fixture, function-scoped, returning a fresh `FakeToolContext` — because it is mutable
and [2.3](../02-pytest-house-rules/2.3-fixtures.md) applies. Then every tool test is three lines and
the double is defined once, which matters when the framework moves and the double has to move with it.

**What changes at scale** is that the double stops being hand-written. Once a project has fifty tools,
somebody discovers `unittest.mock.MagicMock`, which fabricates any attribute you ask for. It is
convenient and it removes the `AttributeError` above — which is the whole safety mechanism. A
`MagicMock` will happily answer `ctx.stat`, `ctx.sate` and `ctx.state_`, so a typo in the code under
test passes. The disciplined version is `MagicMock(spec=Context)`, which restricts it to members the
real class actually has, and is the only form worth using.

**The failure that only appears with real traffic** is the double that is too permissive about
ordering. `FakeToolContext` lets a tool write state and never save the artifact, or save it twice, and
records both without complaint. The real runtime has opinions about when a state delta is committed
relative to an event. A unit test through this double proves the tool's own logic; it does not prove
the tool behaves correctly inside the runtime, which is what the integration test in the build brief
is for.

**The review comment a senior engineer leaves:** *"this fake has eight attributes and the tools use
two. Delete the six — every one of them is a claim about ADK that nothing verifies."*

**The interview question:** *"how do you test code that depends on a framework object you can't
construct?"* The answer that shows you have done it: *"I don't construct it. The object arrives as a
parameter, so the test passes a small class with only the attributes the code actually touches —
usually a dict and one recording method. The thing to be careful about is matching behaviour, not just
shape: async where the real one is async, the same starting version number, and a real state object
rather than a dict anywhere prefixes matter."*
