# 3.3 — The async tool, without a runner

## One-line answer

`asyncio.run(save_note("4521", body, ctx))` runs one async tool to completion in a synchronous test —
no plugin, no event loop of your own, no runner — and without it pytest refuses the test outright with
*"async def functions are not natively supported."*

## The story

The washing machine has a start button on the front and you are allowed to press it.

You do not need to phone the building manager, book a slot, or wait for the block's laundry schedule.
You put the clothes in, turn the dial, press start, and stand there while it fills. When it beeps you
open the door.

The machine runs a whole programme — fill, wash, drain, spin — and none of that is your business
while it runs. Your entire involvement is *start it and wait for it to finish*.

That is not a simplification of what the machine does. It is the interface the machine was given, on
purpose, so that using it does not require understanding it.

## The idea in plain language

Some of Sutra's tools are `async def` rather than `def`. `save_note` is, because the artifact save it
performs is `await`ed ([3.2](3.2-the-fake-tool-context.md)).

Calling an `async def` function does **not** run it. It builds a **coroutine** — an object that
represents work that has not started — and hands it back. Something has to drive it. Inside ADK that
something is the runner's event loop; inside a test it has to be you.

`asyncio.run(coroutine)` is that something, in one line. It starts an event loop, runs the coroutine to
completion, returns its result, and shuts the loop down. It is the start button.

So an async tool is tested from an ordinary synchronous test function:

```
result = asyncio.run(save_note("4521", "body", ctx))
```

The test function itself stays `def`, not `async def`, and this matters more than it looks. **pytest
does not run `async def` tests by itself.** Left alone it collects the test, notices it is a coroutine
function, and fails it with an error telling you to install a plugin. `pytest-asyncio` and `anyio` are
those plugins, they are perfectly good, and this repository does not have either — because for a
handful of async tools, `asyncio.run` costs one import and no dependency, and CLAUDE.md's *prefer the
stdlib* rule points straight at it.

There is one limitation worth stating so it is not a surprise later. `asyncio.run` creates a **new**
event loop each call, so two `asyncio.run` calls in one test are two separate loops. For independent
calls that is fine and is exactly what the version test below does. For anything that has to share a
loop — a client held open across calls, a task started in one and awaited in another — you need one
`asyncio.run` around a single `async def` helper that does both, or the plugin.

## Why Sutra needs it

Because everything ADK hands you that touches storage is async, and that is not going to reverse.

`save_artifact` and `load_artifact` are coroutine functions — verified against the installed
`google-adk` 2.7.1 on 2026-09-04. Every plugin hook on `BasePlugin` is `async def`, which is why the
whole of [section 4](../04-testing-hooks/4.1-the-return-value-is-the-contract.md) uses the same
technique. Sessions, memory and the runner are async. From Day 18 onward, a growing share of Sutra's
own code is `async def`, and a testing habit that stops at synchronous functions would stop covering
the parts that touch state.

One line of stdlib buys the rest of the curriculum.

## The mechanism

Three tests over one async tool: the happy path, the version counter, and the whitespace case that a
design decision on Day 18 exists to prevent.

```python
# days/day-23-testing-tools-and-callbacks/lab/tools_demo.py
async def save_note(ticket_id: str, body: str, tool_context: object) -> dict[str, object]:
    """Saves an artifact and records the version in state, in one call (Day 18)."""
    filename = f"note-{int(ticket_id)}.md"
    version = await tool_context.save_artifact(filename=filename, artifact=body)
    tool_context.state["note_file"] = filename
    tool_context.state["note_version"] = version
    return {"status": "ok", "filename": filename, "version": version}
```

**Line by line:**

- `int(ticket_id)` is not a type conversion for its own sake. It is the line that makes `"4521 "`,
  `"4521"` and `"04521"` produce **one** filename instead of three, which is Day 18's rule that a
  filename is derived and never taken from user text.
- `await tool_context.save_artifact(...)` — the `await` is what turns the coroutine the double returns
  into an integer. Remove it and `version` becomes a coroutine object, which then gets written into
  state and returned to the model.
- The artifact save happens **before** the two state writes, so a failure in the save leaves no
  dangling pointer in state. State that names a file which was never written is worse than no state at
  all.
- Both state keys are written in the same call, which is Day 18's reason for this tool existing at all:
  the file and the pointer to it land on one event, so a reader can never see one without the other.
- The return dictionary includes `version`, so the model can say *"saved as version 2"* rather than
  guessing. The tool tells the truth about what it did.

```python
# days/day-23-testing-tools-and-callbacks/lab/test_tools_demo.py
import asyncio

from fake_context import FakeToolContext
from tools_demo import save_note


def test_save_note_saves_the_artifact_and_records_where_it_went() -> None:
    ctx = FakeToolContext()
    result = asyncio.run(save_note("4521", "customer wants a refund", ctx))
    assert result == {"status": "ok", "filename": "note-4521.md", "version": 0}
    assert ctx.saved == [("note-4521.md", "customer wants a refund")]
    assert ctx.state == {"note_file": "note-4521.md", "note_version": 0}


def test_the_second_save_gets_the_next_version() -> None:
    ctx = FakeToolContext()
    asyncio.run(save_note("4521", "first", ctx))
    second = asyncio.run(save_note("4521", "second", ctx))
    assert second["version"] == 1, "two saves of one filename are two versions, not two files"


def test_a_ticket_id_with_a_trailing_space_still_makes_one_filename() -> None:
    ctx = FakeToolContext()
    result = asyncio.run(save_note("4521 ", "customer wants a refund", ctx))
    assert result["filename"] == "note-4521.md"
```

**Line by line:**

- Every test function is `def`, not `async def`. The asynchrony is confined to the one expression
  inside `asyncio.run(...)`, which is why no plugin is needed and why the file has no configuration.
- The first test makes **three** assertions in three different places: the return value the model will
  see, the spy's record of what was handed to the artifact store, and the state the next turn will
  read. Those are three separate promises and a tool can keep two and break one.
- `ctx.saved == [("note-4521.md", "customer wants a refund")]` compares the whole list, so it also
  asserts that `save_artifact` was called **exactly once**. Checking `ctx.saved[0]` would pass for a
  tool that saved twice, which is a real bug shape when a retry gets added later.
- The second test calls `asyncio.run` twice, deliberately. Two separate event loops, one shared
  `ctx` — which is fine because the state lives on the double, not on the loop, and it is a clean
  demonstration of the limitation named above.
- `assert second["version"] == 1` with a message that states the rule in words: two saves of one
  filename are two versions, not two files. That sentence is the design decision, and putting it in the
  assertion message is how it survives being forgotten.
- The third test is the whitespace case. `"4521 "` goes in and `note-4521.md` comes out, which is
  `int()` doing its job. Without that line, a ticket id copied out of a form with a trailing space
  would create a second artifact and the first one would become unreachable.

## When it breaks

There are exactly two mistakes here and both have unmistakable output. Write the test as `async def`
and forget that pytest cannot run it:

```text
async def functions are not natively supported.
You need to install a suitable plugin for your async framework, for example:
  - anyio
  - pytest-asyncio
  - pytest-tornasync
  - pytest-trio
  - pytest-twisted
```

That is pytest **failing** the test rather than skipping it, which is the right behaviour and was not
always the default. The fix is either to install one of those plugins or to do what this day does and
wrap the call in `asyncio.run`.

The second mistake is calling the tool without awaiting or running it at all:

```text
    def test_forgot_to_await() -> None:
        ctx = FakeToolContext()
        result = save_note("4521", "body", ctx)
>       assert result["status"] == "ok"
               ^^^^^^^^^^^^^^^^
E       TypeError: 'coroutine' object is not subscriptable

sys:1: RuntimeWarning: coroutine 'save_note' was never awaited
```

Two messages, and the second one is the diagnosis. `'coroutine' object is not subscriptable` says the
call returned a coroutine instead of a dictionary; `coroutine 'save_note' was never awaited` says why.
The warning arrives at the very bottom of the output, after the summary, which is exactly where nobody
looks — so it is worth recognising the `TypeError` on its own.

The subtle one, which produces no error, is a tool that forgets its own `await` internally. `version`
becomes a coroutine object, gets written to state, and the test's equality assertion fails with
something like `assert {'note_version': <coroutine object ...>} == {...}`. That is why the state
assertion in the first test compares whole dictionaries rather than checking `"note_version" in
ctx.state`.

## In production

**A project with more than a handful of async tests installs the plugin.** `pytest-asyncio` with
`asyncio_mode = "auto"` lets test functions be `async def` and runs them, which removes the
`asyncio.run` wrapper and, more importantly, gives every test in a module one shared event loop. That
matters as soon as fixtures become async — an async client, a database connection, a started server —
because those cannot be built by `asyncio.run` in a synchronous fixture and handed across loops.

Sutra does not install it today, and the reason is worth stating rather than assuming: it would be a
new dependency, on a day whose subject is the standard library's own conventions, for a benefit that
begins at a scale this repository has not reached. That is a decision with an expiry date, and the
honest place for it is the build brief rather than a comment.

**What changes at scale** is that async tests start hiding concurrency bugs rather than finding them.
`asyncio.run` executes one coroutine to completion with nothing else on the loop, so a tool that is
unsafe when two invocations interleave passes every test here. Finding that needs `asyncio.gather` over
several calls and an assertion about the combined result — which is a different kind of test, and one
worth writing for anything that reads-then-writes shared state.

**The failure that only appears with real traffic** is the coroutine that is never awaited in
production code rather than in a test. Python only warns, at garbage-collection time, on standard
error, long after the request finished — so the symptom is a save that silently did not happen. The
defence is the assertion on the spy: if `ctx.saved` is empty, the save did not occur, whatever the
return value said.

**The review comment a senior engineer leaves:** *"this test wraps three separate `asyncio.run` calls
— if any of them ever need to share a loop, this will start failing in a way that looks like a race.
Consider one `async def` helper and one `run`."*

**The interview question:** *"how do you unit test an async function?"* The answer that shows you have
done it without ceremony: *"`asyncio.run` around the call, in an ordinary synchronous test — no plugin
needed for simple cases. I move to `pytest-asyncio` when fixtures become async or when tests need to
share a loop, because that's the point where the wrapper stops working rather than the point where it
stops being fashionable."*
