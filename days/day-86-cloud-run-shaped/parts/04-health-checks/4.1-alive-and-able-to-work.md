# 4.1 — Alive and able to work are different questions

## One-line answer

*Is the process running* and *can the process do its job* have different answers, different
consequences and different endpoints — `/healthz` decides whether to restart a container and
`/readyz` decides whether to send it traffic, and pointing both at the same code throws away the
distinction.

## The story

The shutter is up and there is no stock.

You walk past at ten. The shutter is up, the lights are on, the man is behind the counter. By
every outward sign the shop is open, and it is: he is there, he will say good morning, he will
take a message.

He has no bread. The delivery did not come. Anybody who walks in for bread walks out again, and
the shop has spent their trip to find that out.

There are two useful questions about that shop and they have different answers. *Is it open?*
Yes. *Should I go there for bread?* No. A sign saying OPEN answers only the first, and it is the
first that nobody actually wanted to know.

## The idea in plain language

Two questions, two endpoints, two consequences.

| Question | Endpoint | Who asks | What they do about it |
| --- | --- | --- | --- |
| Is this process alive? | `/healthz` | the supervisor | restart the container if not |
| Can this process do work? | `/readyz` | the load balancer | stop sending it requests if not |

Conflating them produces one of two bad outcomes, depending on which way you conflate.

**If liveness is really readiness**, a container whose dependency is briefly unavailable gets
*restarted*. Restarting does not bring back the dependency, so it restarts again, and a temporary
outage of something else becomes a crash loop in your service — and the restart destroys whatever
in-flight work there was.

**If readiness is really liveness**, a container that is alive and useless keeps receiving
traffic. Every request fails. The service reports itself healthy throughout, which is part
[4.2](4.2-the-check-that-only-watched-the-process.md)'s measurement.

The distinction generalises to a rule: **a check should be as narrow as the action it triggers.**
Restarting is a big hammer, so liveness should check almost nothing — if the process can answer
at all, it is alive. Removing from a load balancer is cheap and reversible, so readiness can
check as much as it needs to.

Sutra's readiness has one dependency to check, and it is the quota ledger, because a desk that
cannot read its own spending record cannot safely call a model at all — Day 78's argument
arriving as an endpoint.

## Why Sutra needs it

Because the Dockerfile's `HEALTHCHECK` points at `/readyz`, and part
[2.1](../02-the-image-contract/2.1-writing-the-dockerfile.md) asserted that was the right choice
without demonstrating it. This part and the next are the demonstration.

And because Day 88's cluster has both probes as separate configuration, with separate
consequences, and an image that exposes only one endpoint forces both probes to point at it.
Whichever meaning you pick, one of the two behaviours is then wrong.

## The mechanism

Two handlers, deliberately unequal in what they touch:

```python
@app.get("/healthz")
def healthz() -> dict[str, object]:
    """Liveness: the process is running and can answer. It checks nothing else."""
    return {"status": "ok", "pid": os.getpid()}
```

**Line by line:**

- No dependency is consulted. That is not laziness — it is the definition. If this handler can
  execute and return, the interpreter is running, the event loop is turning and the socket is
  bound, which is the entire claim liveness makes.
- `os.getpid()` in the body, so a reply identifies which process answered. Free, and it is what
  makes part [5.2](../05-the-word-stateless/5.2-two-replicas-one-failure.md)'s two-replica run
  legible.
- No try/except. If this raises, the process is in a state where "alive" is genuinely doubtful,
  and a handler that catches everything to keep returning 200 is a handler that cannot report the
  one thing it exists to report.

```python
@app.get("/readyz")
def readyz() -> JSONResponse:
    """Readiness: every dependency this process needs to do work is actually there."""
    if not LEDGER.is_file():
        return JSONResponse({"status": "not_ready", "reason": "quota_ledger_missing"}, 503)
    try:
        json.loads(LEDGER.read_text(encoding="utf-8"))
    except json.JSONDecodeError:
        return JSONResponse({"status": "not_ready", "reason": "quota_ledger_unreadable"}, 503)
    return JSONResponse({"status": "ready", "pid": os.getpid()}, 200)
```

**Line by line:**

- Two separate failures with two different `reason` strings. *Missing* and *unparseable* have
  different causes — a volume that did not mount versus a file that was written badly — and a
  single "not ready" would send an operator looking in the wrong place.
- The file is **read and parsed**, not merely checked for existence. A readiness check that only
  tests presence passes on a zero-byte file, which is exactly what a half-written file looks like.
- `503`, not `500`. Five-hundred-three is *service unavailable*, which is the status a load
  balancer is built to interpret as "take this one out of rotation and try again later"; a 500 is
  a bug and is treated differently.
- The reason is in the **body**, and the status is the machine-readable part. A probe reads the
  status; a human reads the body. Both channels carry the finding, which is the lesson from Day
  82's nightly that reported a regression on stdout and exited zero.
- `except json.JSONDecodeError` specifically, not `except Exception`. A permission error on the
  file is a different problem and should surface as a 500 rather than be reported as "not ready",
  because it will not fix itself.

Both endpoints, against a real running process:

```bash
cd days/day-86-cloud-run-shaped/lab
uv run python health.py; echo "exit: $?"
```

**Line by line:**

- `health.py` starts the app in a subprocess on a port the operating system chooses, waits for it
  to come up, and asks both endpoints twice — once healthy, once with the dependency removed.

Measured on 2026-09-07:

```text
the app, in its own process, on http://127.0.0.1:56172
its quota ledger: sutra-quota-56172.json

                            /healthz              /readyz
  dependency present        200 ok                200 ready
  ledger deleted            200 ok                503 quota_ledger_missing

  the process is alive (200) and cannot work (503 quota_ledger_missing)
  a platform watching only liveness keeps sending it requests
exit: 0
```

The top row is the uninteresting one and it matters: when everything is fine, the two endpoints
agree. A distinction that showed up all the time would be noise. This one appears exactly when
something is wrong, which is what makes the bottom row worth having.

## When it breaks

Readiness breaks by checking too much, and this is the failure that is harder to reason about
than the obvious one.

Suppose `/readyz` also checked the model provider by making a request. Then:

```text
1. the provider has a slow moment
2. every replica's readiness probe fails at once
3. every replica is removed from rotation at once
4. the service is now completely down
5. the provider recovers; the probes pass; traffic returns as a thundering herd
```

Nothing was broken in step one except latency. The readiness check converted a degradation in a
dependency into a total outage of this service, and then converted the recovery into a load
spike. This is why a readiness probe should check things this process needs *and controls*, and
why a shared downstream dependency generally belongs behind a circuit breaker rather than in a
probe.

The other break is cost. A probe runs on a schedule, for ever, on every replica. A readiness
check that calls a model is a standing charge against the quota — Day 78's budget, spent on
asking whether we can spend. Sutra's readiness reads a local file for exactly this reason.

There is no error text for either failure. Both look like a service that is behaving correctly
and being unlucky.

## In production

**What a professional does.** Writes liveness to check nothing and readiness to check the
dependencies this instance owns — its own disk, its own connection pool, its own warm-up — and
keeps shared downstream services out of both. And gives readiness a *reason*, so that a page at
three in the morning starts from a named cause rather than from a status code.

**What degrades at scale.** Probe traffic. Two endpoints, per replica, at a fixed interval, is a
constant request rate proportional to fleet size — and if either probe does real work, that work
also scales with the fleet rather than with the traffic. Teams discover this when a health check
becomes the largest single consumer of a database's connections.

**The failure that only shows with real traffic.** Readiness that is true at start-up and stops
being maintained. A process that checks a dependency once, caches "ready", and never rechecks
reports ready for ever — including for the hour after the dependency went away. Sutra's readiness
reads the file on every request, which costs a stat and a small parse and is the right trade at
this size.

**The review comment a senior engineer leaves:** *"Liveness must not touch the ledger. If you
ever add a dependency check to `/healthz`, a slow disk starts restarting containers, and a
restart never fixes a disk."*

**The interview question:** *"What is the difference between a liveness and a readiness probe?"*
The answer that shows experience gives the consequence rather than the definition — one restarts
the container and one removes it from the load balancer — and then names the failure mode of
getting it backwards, which is a dependency outage turning into a crash loop.
