# 4.2 — The health check that only watched the process

## One-line answer

💥 The dependency is deleted, the service can do no work at all, and `/healthz` answers `200 ok` —
so a run that asks only the liveness endpoint reports a healthy service and exits `0`, while the
readiness endpoint two lines away is saying `503 quota_ledger_missing`.

## The story

💥 **The printer that says READY.**

🎬 **The scene.** The office printer has a small screen. It says READY. It has said READY all
morning, in green, and the little light beside it is on.

😬 **The naive fix.** Somebody's document has not come out. Obviously the document did not reach
the printer — check the network, check the driver, re-send it. Three people try. The screen still
says READY, so the printer is fine and the problem must be upstream.

💥 **Why it fails.** The paper tray is empty. The screen is reporting on the printer's own
state — powered, connected, no jam, firmware loaded — which is genuinely all fine. It is not
reporting on whether it can print anything, because from the controller's point of view that is a
different subsystem, and it has been perfectly happy to accept eleven jobs into the queue.

💡 **The insight.** READY is a true statement about the wrong subject. The printer is answering
*am I working?* and everybody in the room is asking *will my document come out?* Nobody has to
be wrong for the morning to be wasted.

## The idea in plain language

Part [4.1](4.1-alive-and-able-to-work.md) drew the distinction. This part is what the distinction
is worth, measured, and the number that matters is not the 503 — it is the 200 beside it.

The setup is deliberately minimal. The app has one dependency it genuinely cannot work without:
the quota ledger, which is the file recording what has been spent against the free tier. Delete
it and the desk cannot safely call a model, because it has no idea what it has already spent —
Day 78's whole argument, reduced to a file being present.

So: start the app, confirm both endpoints are happy, delete the file, ask again.

The failure mode is not that liveness gives a wrong answer. It gives a correct answer to its own
question, exactly as designed and exactly as part 4.1 argued it should. The failure is a
**monitoring** decision made somewhere else — a platform, a load balancer, a dashboard — that
asks only that endpoint and treats the answer as a summary of the service.

And that decision is the default nearly everywhere, because a single health endpoint is the
simplest thing to configure, and because when everything is fine both endpoints agree.

## Why Sutra needs it

Because the Dockerfile's `HEALTHCHECK` points at `/readyz` and the compose file's api service does
not define one at all, and until this is measured, "point it at readiness" is advice rather than
a finding.

And because this is the fourth time this shape has appeared in this repository, which is what
makes it worth a part of its own rather than a footnote:

| Day | The report that was true and hid the finding |
| --- | --- |
| 79 | a suite whose cases could not fail, reporting green |
| 81 | an accuracy printed without its baseline |
| 82 | a nightly that found a regression and exited `0` |
| 86 | a liveness probe reporting `200` on a service that can do nothing |

Every one of them is a correct statement about a narrower subject than the reader assumes, and in
every one the arm that hides the finding is the arm that exits zero.

## The mechanism

The breakage is one line, and it is a real file being removed from a real running process's view:

```python
        ledger.unlink()  # the dependency goes away, the process does not
```

**Line by line:**

- `unlink()` rather than corrupting the contents, because absence is the cleanest possible
  breakage: there is no question of a partial read or a race, and readiness has a specific reason
  string for it.
- The comment is the whole part in six words. Nothing happens to the process. It is not signalled,
  not reloaded, not touched — and every subsequent request still runs, because the code path that
  needs the file is not the code path that answers liveness.

Both endpoints are then asked again, and the two answers are printed side by side:

```python
        live2, live_why2 = ask(base, "/healthz")
        ready2, ready_why2 = ask(base, "/readyz")
        print(f"  {'ledger deleted':<26}{f'{live2} {live_why2}':<22}{ready2} {ready_why2}")
```

**Line by line:**

- The two calls are adjacent, so nothing about timing or load differs between them. The only
  variable is which endpoint was asked.
- Both are printed on one row, which is the reporting decision this part is arguing for: a health
  report that shows only one column is how the finding disappears.
- `ask()` returns the status **and** the body's reason, so the row carries a cause rather than a
  number.

The verdict then depends on which endpoints the run is allowed to consider:

```python
        if liveness_only:
            print(f"\n  liveness says {live2}: the process is up and answering")
            print("  nothing was asked about whether it can do any work, so nothing was found")
            return 1
```

**Line by line:**

- Note what this branch does *not* do: it does not fake anything, skip the readiness call, or
  change the app. The measurement is identical; only the conclusion drawn from it is narrowed.
- `return 1` because a run that cannot find the problem is a failed check, not a passed one. The
  exit code says the *check* is inadequate — which is the opposite of what a real monitoring
  setup would report, and naming that inversion is the point.

Run both:

```bash
cd days/day-86-cloud-run-shaped/lab
uv run python health.py; echo "exit: $?"
```

**Line by line:**

- No flag: both endpoints are consulted, and the run is judged on whether readiness caught what
  liveness missed.

Measured on 2026-09-07:

```text
                            /healthz              /readyz
  dependency present        200 ok                200 ready
  ledger deleted            200 ok                503 quota_ledger_missing

  the process is alive (200) and cannot work (503 quota_ledger_missing)
  a platform watching only liveness keeps sending it requests
exit: 0
```

## When it breaks

Now the same run, with the same app, in the same state, asking only the endpoint most systems are
configured to ask:

```bash
uv run python health.py --liveness-only; echo "exit: $?"
```

Measured on 2026-09-07:

```text
                            /healthz              /readyz
  dependency present        200 ok                200 ready
  ledger deleted            200 ok                503 quota_ledger_missing

  liveness says 200: the process is up and answering
  nothing was asked about whether it can do any work, so nothing was found
exit: 1
```

**`200 ok` on a service that cannot perform its function, and an exit code of `0` from the arm
that draws the wrong conclusion.** There is no error anywhere. The process did not crash, no
exception was raised, no log line was written. A dashboard fed by this endpoint is green.

What happens next in a real system is worse than a green dashboard, and it composes with things
this repository has already measured:

```text
1. the volume fails to mount after a node is replaced
2. every replica's ledger is missing
3. liveness is 200 everywhere, so no container is restarted
4. traffic continues to arrive and every request fails
5. the quota ledger is gone, so nothing knows what has been spent   (day 78)
6. the failures are retried, because they look transient           (day 72)
```

Steps five and six are the expensive ones. The service is not merely down; it is down in a way
that spends the free-tier allowance on retries while reporting itself healthy.

The composite failure has no single error message, which is the recurring property of this whole
class. What it has is a status code that is correct and a reader who wanted a different question
answered.

## In production

**What a professional does.** Configures the two probes separately and points the *alerting* at
readiness, not liveness — because liveness failing is a thing the platform already handles by
restarting, whereas readiness failing across many replicas at once is a thing only a person can
fix. And puts the reason string in the alert, so the page says `quota_ledger_missing` rather than
`readiness failed`.

**What degrades at scale.** The correlation. One replica not ready is routine and self-healing;
all of them not ready is an outage, and the two look identical in a per-replica view. The metric
that matters is the *proportion* ready, and it is the one nobody adds until after the first
incident.

**The failure that only shows with real traffic.** Readiness that is right and ignored. A service
can report `503` correctly on every replica while a load balancer configured with a
generous failure threshold keeps sending traffic, because removing every backend would mean
serving nothing at all — so it serves everything to backends that cannot answer. The probe was
correct throughout, and the honest lesson is that a correct signal nobody acts on is
indistinguishable from no signal.

**The review comment a senior engineer leaves:** *"The compose api service has no healthcheck at
all — add one, pointed at `/readyz`, same as the Dockerfile. And whatever we hook the dashboard
to, make it show both columns; a single green light is how we get a morning like the printer."*

**The interview question:** *"Your monitoring says the service is healthy and users say it is
down. Where do you start?"* The answer that shows experience asks what the health check actually
checks, and expects the answer to be "that the process is running" — because that is the default,
and it is a true statement about the wrong subject.
