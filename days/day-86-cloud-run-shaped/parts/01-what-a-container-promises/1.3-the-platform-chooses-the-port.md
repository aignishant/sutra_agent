# 1.3 — The platform chooses the port and the address

## One-line answer

A container does not pick where it listens: the platform hands it a port in an environment
variable and expects it to bind every interface — so `--port $PORT` and `--host 0.0.0.0` are not
style choices, and the second one is the exact opposite of what is correct on a laptop.

## The story

The pitch number at the weekend market.

You have booked a stall. You do not choose where it goes — you turn up, the organiser looks at a
sheet, and says *"you are on pitch thirty-one this week"*. Last week you were on nine. Next week
it depends on who else booked.

A trader who has painted their stall number on the awning has to repaint it or hang it in the
wrong place. A trader who reads the sheet on the morning sets up anywhere, every week, without
thinking about it.

And there is a second, less obvious rule: the stall has to be open on all sides that face the
aisle. A trader who serves only through a hatch facing the back wall is, from the point of view
of everybody walking past, closed.

## The idea in plain language

Two settings decide whether a container is reachable, and both are counter-intuitive because
both are the reverse of the local habit.

**The port comes from outside.** A platform starts many containers on one machine and cannot let
each choose a number. So it sets an environment variable — on the platform this day is shaped
for, that variable is `PORT` — and the container is expected to listen on whatever it says. An
image with `--port 8080` hard-coded works right up until the platform hands it something else,
and then it listens on the wrong port and is marked unhealthy with no error in its own logs.

**The address must be every interface.** Inside a container, `127.0.0.1` means *this container's
own loopback*, which nothing outside the container can reach — not the host, not a sibling
container, not the platform's health checker. `0.0.0.0` means "every interface", which is what
makes the process reachable at all.

That second one is worth dwelling on, because it is the one place in this curriculum where
`0.0.0.0` is right. Everywhere else it is a warning sign: a development server bound to
`0.0.0.0` on a laptop is listening on the coffee-shop network. The difference is the boundary.
Inside a container, the network namespace *is* the isolation, so binding everything inside it
exposes nothing outside it.

| Where | `--host 127.0.0.1` | `--host 0.0.0.0` |
| --- | --- | --- |
| your laptop | correct: only you can reach it | exposes the port to the local network |
| inside a container | unreachable from anywhere | correct: the namespace is the boundary |

The lab's own app binds loopback, deliberately, because the lab runs on a laptop:

```text
uvicorn.run(app, host="127.0.0.1", port=port, log_level="warning")
```

and the Dockerfile's command binds `0.0.0.0`. Both are right, for different boundaries, and
noticing that they differ is the point of this part.

## Why Sutra needs it

Because Day 88 runs this image in a local cluster, where a health probe from outside the pod is
the thing that decides whether traffic arrives. A process bound to loopback passes every check a
developer runs by hand — they run them inside the container — and fails every check the platform
runs.

And because Day 87's managed platform makes the port assignment explicit and non-negotiable. An
image that ignores `PORT` cannot be deployed there at all, so getting this right today is what
makes tomorrow's walkthrough a reading exercise rather than a debugging one.

## The mechanism

One line in the Dockerfile carries both decisions:

```dockerfile
ENV PORT=8080
EXPOSE 8080
CMD ["sh", "-c", "uvicorn sutra.api:app --host 0.0.0.0 --port $PORT"]
```

**Line by line:**

- `ENV PORT=8080` is a **fallback**, so that `docker run` with no environment still starts. A
  platform overrides it. Writing the default here rather than in Python keeps the fact in the
  file a deployer reads.
- `EXPOSE 8080` opens nothing and publishes nothing — it is metadata. Tools read it to offer a
  sensible default mapping. Believing it does more is one of the most common first-container
  misunderstandings, and the symptom is a container that "should be" reachable and is not.
- `CMD ["sh", "-c", ...]` — the shell form. The list form `["uvicorn", "--port", "$PORT"]` passes
  the four characters `$PORT` to uvicorn as a literal string, because there is no shell to expand
  it, and uvicorn fails to parse it as an integer. This is the trade named in part
  [1.1](1.1-an-image-is-a-recipe.md): a shell becomes process one, which makes signal handling
  slightly worse, and it buys variable expansion.
- `--host 0.0.0.0` — every interface inside the network namespace. Not a security relaxation:
  the namespace is the boundary and it is unchanged by this flag.

`lab/image.py` checks both, from the `CMD` line, because both are invisible in a running system
until something outside tries to connect:

```python
(("the port comes from the platform", "$PORT" in cmd, cmd[:60]),)
(("binds 0.0.0.0, not loopback", "0.0.0.0" in cmd, cmd[:60]),)
```

**Line by line:**

- Two separate rows rather than one combined check, because they fail for different reasons and
  a combined row would not say which.
- A substring test on the command, not a parse. The check is deliberately shallow: it can be
  fooled by a comment containing `$PORT`, and it catches the failure that actually happens, which
  is somebody writing a literal port. Naming the limit is better than pretending to a rigour the
  check does not have.
- `cmd[:60]` as evidence, truncated so the table stays readable. The reader can see which line
  was judged.

Run it:

```bash
cd days/day-86-cloud-run-shaped/lab
uv run python image.py --sloppy | sed -n '9,10p'
```

**Line by line:**

- The `--sloppy` arm is a Dockerfile with `--host 127.0.0.1` and a hard-coded port, which is what
  a first attempt looks like when it is adapted from a local run command.

Measured on 2026-09-07:

```text
  the port comes from the platform      BAD ["uvicorn", "sutra.api:app", "--host", "127.
  binds 0.0.0.0, not loopback           BAD ["uvicorn", "sutra.api:app", "--host", "127.
```

Both fail on the same line, and that line is the one somebody copied out of their terminal
history. It is a perfectly good command. It is a local command.

## When it breaks

There is no error message on the container's side, which is what makes this hard the first time.
The process starts, logs that it is serving, and answers nothing.

What you get instead is a timeout from outside:

```text
ConnectionRefusedError: [WinError 10061] No connection could be made because the target machine actively refused it
```

or, on a platform with a health probe, a container killed and restarted in a loop with a
message about failing readiness — while the container's own logs say it started normally. The
tell is that logs *inside* look healthy and everything *outside* cannot connect.

The diagnostic that settles it in one command is to ask the process what it bound, rather than
what you think it bound:

```bash
uv run python -c "import socket; s=socket.socket(); s.connect(('127.0.0.1', 8080)); print('reachable')"
```

**Line by line:**

- A raw socket connect rather than an HTTP request, because it separates "nothing is listening"
  from "something is listening and the application is broken". Those two have very different
  fixes and the same symptom in a browser.

## In production

**What a professional does.** Reads the port from the environment with no default in the
application code, and lets the deployment artefact supply the default. Two places can define a
port and only one of them is deployed, so the application having an opinion is how a container
ends up listening somewhere the platform is not looking.

**What degrades at scale.** Nothing about this gets harder with more traffic; it gets harder with
more *environments*. A service that runs correctly on a laptop, in a cluster and on a managed
platform has three different ideas of what "the port" is, and the only way that stays sane is
that all three go through one variable.

**The failure that only shows with real traffic.** A second container in the same pod. Day 88's
sidecar pattern puts two containers in one network namespace, where they reach each other on
`127.0.0.1` and must not collide on a port. At that point `0.0.0.0` and loopback stop being a
simple rule and become a question about which boundary you are on — which is why that day comes
after this one.

**The review comment a senior engineer leaves:** *"`--host 0.0.0.0` in the Dockerfile and
`127.0.0.1` in the lab is right, and it will confuse the next person. Put a comment on both
saying which boundary each is inside."*

**The interview question:** *"Your container starts fine and nothing can reach it. Where do you
look?"* The answer that shows experience checks the bind address before anything else, because
that failure produces healthy logs and no connection, and every other cause produces at least
one error somewhere.
