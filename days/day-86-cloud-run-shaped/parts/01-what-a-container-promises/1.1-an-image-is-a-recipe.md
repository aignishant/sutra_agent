# 1.1 — An image is a recipe a stranger can follow

## One-line answer

Everything the desk needs to run is currently an unwritten assumption about one laptop — a
particular Python, a particular lockfile, a file called `.env` in a particular folder — and an
image is that list written down so completely that a machine which has never seen the project
can reproduce it.

## The story

The recipe card that says *"cook till done"*.

Two people write down the same dish. The first writes: some stock, an onion, simmer till done.
The second writes: eight hundred millilitres of stock, one onion of about a hundred and fifty
grams, a bare simmer in a twenty-centimetre pan until the liquid has dropped by a third.

Both cards work perfectly — for the person who wrote them. The first one works because the
writer already knows what "done" looks like, how big their onions are, and which pan they
meant. None of that is on the card. It is in the kitchen.

Hand both cards to somebody who has never cooked the dish. Only the second one is a recipe.
The first is a reminder, and a reminder is only useful to the person who does not need it.

## The idea in plain language

An **image** is a filesystem plus the command to run, packaged as a single file that a machine
can unpack and execute. A **container** is one running copy of an image.

The interesting property is not isolation, which is a side effect. It is that the image is a
recipe of the second kind: the base operating system, the exact interpreter, the exact
dependency versions, the exact files, the exact command. Nothing is left in the kitchen.

Ask what the desk currently needs in order to run, and the list is long and nowhere written:

| What it needs | Where that fact currently lives |
| --- | --- |
| Python 3.12 exactly | `pyproject.toml`, and whatever is on your `PATH` |
| the exact package versions | `uv.lock`, if somebody runs `uv sync` |
| three environment settings | a `.env` file that is deliberately not in git |
| a writable folder for its state | your home directory, by accident |
| a port nobody else is using | your memory |

Only two of those five are written down anywhere a second machine could read. *"It works on my
machine"* is not a joke about this system; it is currently the specification.

Writing the image forces every one of those rows to become a line in a file. That is the whole
value, and it is worth having even if the image is never once run in production — which,
honestly, is the situation this day is in.

## Why Sutra needs it

Because Day 93 makes this repository public, and a public repository whose build instructions
are *"install some things and it should work"* is a repository nobody can run. The image is the
part of the project that a stranger executes.

And because the next two phase days depend on it. Day 87 looks at a managed platform that takes
an image and runs it; Day 88 puts an image into a local cluster. Both take the image as given,
so if it is wrong they are both measuring the wrong thing.

## The paper behind it

> **An updated performance comparison of virtual machines and Linux containers**
> 2015 IEEE International Symposium on Performance Analysis of Systems and Software (ISPASS),
> 2015, pages 171–172. `doi:10.1109/ISPASS.2015.7095802`

The claim in one sentence: containers match or beat virtual machines on nearly every workload,
and both are close to untouched hardware on processor and memory — so the isolation you get from
a container is very nearly free, and what costs is input and output.

That is why the unit of deployment is an image rather than a machine image, and it is why "just
run it in a container" stopped being a performance argument. The full treatment, with a demo
that measures a boundary's cost directly, is in
[papers/01](../../papers/01-what-isolation-costs.md).

## The mechanism

Here is the recipe, top to bottom, as it is actually written in `lab/Dockerfile`. Read it as
five decisions rather than as syntax.

```dockerfile
FROM python:3.12-slim-bookworm

COPY --from=ghcr.io/astral-sh/uv:0.12.3 /uv /usr/local/bin/uv

WORKDIR /app

COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project
```

**Line by line:**

- `FROM python:3.12-slim-bookworm` — the starting filesystem. `3.12` because
  `pyproject.toml` says `requires-python = "==3.12.*"`; `slim` because the full image carries a
  compiler toolchain this project does not need at run time; `bookworm` because naming the
  Debian release stops the base moving underneath you when a new one becomes the default.
  Part [1.2](1.2-a-layer-is-written-once.md) is why `:latest` would be a bug rather than a
  shortcut.
- `COPY --from=ghcr.io/astral-sh/uv:0.12.3` — copy one binary out of another image instead of
  installing it. `0.12.3` is the version this repository actually runs, read from
  `uv --version` on 2026-09-07 rather than remembered. Principle 7 applies to a base image
  exactly as it applies to a package.
- `WORKDIR /app` — creates the directory and makes it the default for every later instruction.
  Without it, later `COPY` targets are relative to `/`, which works and scatters the app across
  the root of the filesystem.
- `COPY pyproject.toml uv.lock ./` **before** the source, which is the single most consequential
  ordering decision in the file. Part [1.2](1.2-a-layer-is-written-once.md) explains why.
- `uv sync --frozen` — install exactly what the lockfile says. `--frozen` means "fail rather
  than update the lockfile", so a build cannot quietly resolve a different version than the one
  that was tested. `--no-dev` leaves out `ruff` and `pytest`, which have no business in a
  running image. `--no-install-project` installs the dependencies but not the project itself,
  because the project's source has not been copied yet.

Then the source, the user, and the command:

```dockerfile
COPY sutra ./sutra
COPY sutra_mcp ./sutra_mcp

RUN useradd --create-home --uid 10001 desk && chown -R desk:desk /app
USER desk

ENV PORT=8080
EXPOSE 8080

CMD ["sh", "-c", "uvicorn sutra.api:app --host 0.0.0.0 --port $PORT"]
```

**Line by line:**

- Two narrow `COPY` lines rather than `COPY . .`. Naming the directories means a new folder at
  the repository root cannot silently end up in the image; part
  [2.3](../02-the-image-contract/2.3-the-build-context-nobody-looked-at.md) measures what
  `COPY . .` would actually have collected, and the number is larger than anybody guesses.
- `useradd --uid 10001` then `USER desk` — after this line every instruction, and the running
  process, is unprivileged. Containers run as root unless told otherwise, and root inside a
  container is much closer to root outside it than people assume. This is Principle 13 in one
  line: the capability arrives with its containment.
- `chown -R desk:desk /app` in the *same* `RUN` as the `useradd`. Splitting them into two
  instructions would write a second copy of every file in `/app` into a new layer — again part
  [1.2](1.2-a-layer-is-written-once.md).
- `ENV PORT=8080` is a **default for a local run**, not a choice. Part
  [1.3](1.3-the-platform-chooses-the-port.md) is about who really decides.
- `EXPOSE 8080` publishes nothing and opens nothing. It is documentation that a tool can read,
  and believing it does more than that is a common first-container surprise.
- `CMD ["sh", "-c", ...]` — the shell form, deliberately, because `$PORT` has to be expanded at
  run time and the plain list form does not run a shell. The cost is that the shell becomes
  process one and signal handling gets a little worse, which is a real trade and worth knowing
  you are making.

## When it breaks

The recipe breaks by being written against the kitchen it was developed in. The classic version
has no error message at all on the machine that wrote it, and one line on every other machine:

```text
ModuleNotFoundError: No module named 'sutra'
```

That is what `--no-install-project` produces if the source is copied but the project is never
installed and nothing puts `/app` on the import path. It is invisible locally, because locally
you run from the repository root where `sutra/` is simply *there*.

The subtler break is the one this day cannot check for itself. **No image was built here.** This
machine has no container runtime:

```bash
docker --version
```

```text
/usr/bin/bash: line 1: docker: command not found
```

So every line above is checked statically by
[2.2](../02-the-image-contract/2.2-eight-properties-checked.md) and none of it has been
executed. That is stated in the hub's request budget and repeated in the checklist, and it is a
real limitation rather than a formality: a Dockerfile that has never been built is a hypothesis.
The exact command that would test it is a `TODO(me)`, and it is free to run.

## In production

**What a professional does.** Builds the image in continuous integration on the first day the
Dockerfile exists, so that "it builds" is a fact with a date rather than an intention. The build
is also the cheapest possible integration test: it proves the lockfile resolves, the base image
exists, and the entry point imports.

**What degrades at scale.** Build time. A naive Dockerfile reinstalls every dependency whenever
any source file changes, which is fine at four dependencies and intolerable at four hundred —
and the fix is the ordering decision above, made before anybody notices the problem. Once a team
is waiting on builds, the ordering is a refactor rather than a line.

**The failure that only shows with real traffic.** The base image moves. `python:3.12-slim`
resolves to a different filesystem next month, with a different OpenSSL and a different libc,
and a build that has not changed produces an image that behaves differently. Pinning by tag
narrows this; pinning by digest closes it, and doing that needs a registry lookup this machine
cannot make — so it is a `TODO(me)` in the Dockerfile with the exact command.

**The review comment a senior engineer leaves:** *"Pin the base by digest, not by tag, and put
the digest in the same file so the diff shows when it moves. Also: this has never been built.
Add it to CI before we write another line of it."*

**The interview question:** *"Why containerise a Python service?"* The answer that shows
experience does not lead with isolation or with scaling. It leads with the environment stopping
being an unwritten assumption, and then names the second-order benefit — that the same artefact
runs on a laptop, in CI and in production, so a bug is reproducible.
