# 1.2 — A layer is written once and kept forever

## One-line answer

Each instruction in a Dockerfile produces a layer that is stored, addressed by its contents and
never edited — which is why the ordering of instructions decides how fast a rebuild is, and why
deleting a file in a later instruction does not remove it from the image.

## The story

The photocopy that still has the mistake.

A form goes round the office. Somebody notices a wrong figure on page two, crosses it out, and
writes the right one beside it. Fine — except forty photocopies were taken that morning and are
already in forty folders.

You can correct the original as many times as you like. You cannot correct the copies, because a
copy is not a view of the original; it is a separate sheet of paper that recorded what the
original looked like at one moment. The only way to fix the folders is to take fresh copies and
physically remove the old ones, and the only way to know which folders need it is to have kept a
list.

The correction is real. The copies do not care.

## The idea in plain language

An image is not one filesystem. It is a **stack of layers**, one per instruction that changes
the filesystem, each recording the difference from the one below. Running a container stacks
them and shows you the result.

Two consequences follow, and between them they explain most of what is odd about Dockerfiles.

**A layer is cached by what went into it.** If the instruction and its inputs are unchanged
since last time, the stored layer is reused and the instruction does not run. That is why
`COPY pyproject.toml uv.lock` comes before `COPY sutra ./sutra`: editing a source file
invalidates only the layers *after* the copy of the source, so the dependency install — the slow
one — is reused. Put the source first and every source edit reinstalls every package.

**A layer is never edited.** Adding a file writes it into a layer. Deleting it in a *later*
instruction writes a marker that hides it, and the bytes are still in the earlier layer, still
in the image, still in the registry, still extractable by anybody who can pull the image. This
is the property that makes part
[2.3](../02-the-image-contract/2.3-the-build-context-nobody-looked-at.md) a security finding
rather than a housekeeping note.

The mental model worth keeping: **an image is a stack of photocopies, and a later correction is
a fresh sheet placed on top of the old one, not an erasure of it.**

That also settles the `:latest` question. A tag is a label somebody can move to point at a
different stack of layers; a digest is the identity of the stack itself. Building `FROM
python:latest` today and tomorrow can produce two different systems from an unchanged
Dockerfile, and nothing in the file records which one you got.

## Why Sutra needs it

Because Principle 9 says secrets never touch git, and this is the same rule with a second
storage medium that nobody applies it to. The `.env` file is correctly excluded from the
repository and would be copied into a layer by one careless line — and once there, it is in
every copy of that image anybody ever pulls. Day 92's security review gets a line because of
this part: grep the image, not only the repository.

And because rebuild speed is what decides whether a container is used at all. A build that
reinstalls the world on every edit gets bypassed — people run the app outside the container "just
for now" — and then the image stops being tested and is wrong by the time it matters.

## The mechanism

The ordering, from `lab/Dockerfile`:

```dockerfile
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project

COPY sutra ./sutra
COPY sutra_mcp ./sutra_mcp
```

**Line by line:**

- Two files copied, then the install, then the source. Four instructions, four layers, and the
  boundary between the second and third is where the cache does its work.
- Editing `sutra/agent.py` changes the input to the third instruction. Layers one and two are
  unchanged, so they are reused, and the install does not run.
- Editing `uv.lock` changes the input to the first, so everything after it is rebuilt. That is
  correct: a dependency change genuinely is a different environment.
- If these four lines were reordered so the source came first, every layer after it would depend
  on the source, and every edit to any Python file would reinstall every package.

The checker in `lab/image.py` looks for exactly that ordering, because it is a property a person
cannot eyeball reliably in a longer file:

```python
def _deps_first(copies: list[str]) -> bool:
    """The lockfile must be copied before any application source, or the cache is useless."""
    lock = next((i for i, c in enumerate(copies) if "uv.lock" in c or "requirements" in c), None)
    source = next((i for i, c in enumerate(copies) if c.strip().startswith(("sutra", ". ."))), None)
    return lock is not None and (source is None or lock < source)
```

**Line by line:**

- `copies` is every `COPY` line in file order, so comparing indices compares positions in the
  build.
- `next(... , None)` gives the *first* matching line rather than all of them. The first lockfile
  copy and the first source copy are the pair that decides the cache boundary; later ones cannot
  rescue a bad ordering.
- `"uv.lock" in c or "requirements" in c` accepts either package manager, because a checker that
  only understands this project's choice stops being useful the moment the project changes it.
- `source is None or lock < source` — a Dockerfile that copies no source at all still passes,
  because there is nothing for the ordering to be wrong about. Failing that case would be the
  check inventing a requirement.
- Returns a plain `bool`, so the caller can put it in a table beside the evidence rather than
  raising. A build-shape check that raises stops at the first problem and reports one of eight.

Run it and read the second row:

```bash
cd days/day-86-cloud-run-shaped/lab

```

**Line by line:**

- `head -6` for the header and the first two properties; the rest are other parts' subjects.

Measured on 2026-09-07:

```text
Dockerfile: this folder

  check                                     evidence
  base image is pinned, not :latest     ok  python:3.12-slim-bookworm

```

The evidence column is the point: it prints the line that decided the verdict, so a reader can
disagree with the checker.

## When it breaks

The cache breaks quietly and the immutability breaks expensively.

**The quiet one.** Somebody adds a line that copies something changeable above the install —
a version file, a git hash, a timestamp — and the dependency layer stops being reusable. There
is no error. Builds simply get slow, gradually, and nobody attributes it to the commit that did
it.

**The expensive one** has no error text either, which is the whole problem:

```text
1. COPY . . copies .env into layer 4
2. a later RUN rm -f .env writes a deletion marker into layer 7
3. `docker run … cat /app/.env` reports: No such file or directory
4. the key is still in layer 4, and layer 4 is in the registry
```

Step three is what makes this dangerous. The file genuinely is not there in the running
container, so every obvious check says the problem is fixed. Extracting layer four requires no
special access — anyone who can pull the image can unpack it.

The fix is not a deletion. It is to keep the file out of the build context in the first place,
which is part
[2.3](../02-the-image-contract/2.3-the-build-context-nobody-looked-at.md)'s subject, and — if a
secret has already been built into a published image — to rotate the secret, because the image
cannot be unpublished from everybody who has it.

## In production

**What a professional does.** Treats layer order as part of the design: base, then system
packages, then language dependencies, then application source, in that order, because that is
increasing order of change frequency. And treats "was a secret ever in an image we pushed" as a
rotation question rather than a rebuild question.

**What degrades at scale.** Image size and registry cost. Layers accumulate: a build that
installs a toolchain, compiles something, and deletes the toolchain still ships the toolchain,
because the deletion is a marker. The standard answer is a multi-stage build, where the final
image copies only the artefacts out of a builder stage and the toolchain's layers are never part
of the result. This Dockerfile is single-stage because the project is pure Python and there is
nothing to compile — and that is a decision, not an oversight.

**The failure that only shows with real traffic.** A cache that is correct locally and absent in
continuous integration. A fresh CI runner has no layer cache, so the ordering that makes local
rebuilds instant does nothing there, and the first time anybody measures build time it is the
uncached number. Teams then optimise the wrong thing.

**The review comment a senior engineer leaves:** *"This copies the source before the lockfile.
Swap them and the build stops reinstalling everything on every commit. And no `rm` of a secret
in a later layer — if it went in, rotate it."*

**The interview question:** *"Why does the order of Dockerfile instructions matter?"* The answer
that shows experience gives both halves: caching, which is about speed, and immutability, which
is about secrets — and notes that only the second one is unrecoverable.
