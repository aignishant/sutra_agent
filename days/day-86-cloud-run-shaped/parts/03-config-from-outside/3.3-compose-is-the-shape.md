# 3.3 — compose.yaml is the shape, not the tool

## One-line answer

The compose file is not a way to run containers on a laptop; it is the first written statement
that Sutra is a *system of processes* rather than a program — two services with different
lifecycles and different privileges, one shared volume, and one number that is a confession.

## The story

The seating plan drawn before anybody arrives.

A family function, a hall, and somebody sits down the week before with a sheet of paper. Who is
at which table. Which two aunts are not at the same table. Where the children go so they are near
a door. Who is next to the kitchen because they will get up twenty times.

The plan is not the evening. The evening will differ from it. But drawing it is when you discover
that the two aunts are a problem, that there is no table near a door, and that you have invited
more people than there are chairs — and every one of those is much cheaper to find on the sheet
of paper than at seven o'clock with everyone standing in the hall.

The plan's real output is the arguments it forces you to have early.

## The idea in plain language

Up to now Sutra has been described as a program: a package, an entry point, a run command. A
compose file describes it as a **system**, and doing that forces three questions that a program
never has to answer.

**What are the separate processes, and why are they separate?**

| Service | What it is | Why it is not in the same process |
| --- | --- | --- |
| `sutra-api` | the front door from Day 85 | it is the thing that would scale, in a world where it could |
| `sutra-mcp` | the MCP server from Day 33 | it owns the data boundary; different lifecycle, different privileges |

That second row is the argument Day 32 made about MCP, arriving as a deployment fact. Two
processes because they have different reasons to be restarted and different things they are
allowed to touch — not because of performance.

**What do they share, and how do they find each other?** One named volume for state, and a
hostname. Inside a compose network, `http://sutra-mcp:9000` resolves to the other service. No
addresses are configured anywhere; the service name *is* the address.

**How many of each?** This is the question that produces the honest answer, and it is the reason
this part exists. The file says `replicas: 1`, and that is not a modesty setting or a
laptop-sized default. It is the largest number this system can currently run without breaking,
and part [5.2](../05-the-word-stateless/5.2-two-replicas-one-failure.md) measures what the second
one does.

A comment in a deployment file that says *"one, and here is why"* is worth more than any amount
of documentation elsewhere, because it is next to the number somebody would otherwise raise.

## Why Sutra needs it

Because Day 88 puts this into a local cluster, where the same three questions are asked in a
different syntax — a Deployment with a replica count, a Service for the name, a volume claim for
the state. The compose file is where those answers are worked out; the cluster manifests are a
translation.

And because the phase gate for Phase 13 is *"traced end-to-end; runs in local k8s"*. Both halves
assume the system has been described as more than one process. Until this file existed, nothing
in the repository said how many processes Sutra is.

## The mechanism

The whole file is short. The parts that carry weight:

```yaml
services:
  sutra-api:
    build: .
    environment:
      PORT: "8080"
      SUTRA_API_KEY: ${SUTRA_API_KEY:?set it in the shell or a .env that is never copied}
      SUTRA_QUOTA_LEDGER: /app/state/quota.json
      SUTRA_MCP_URL: http://sutra-mcp:9000
    ports:
      - "8080:8080"
    volumes:
      - desk-state:/app/state
    depends_on:
      - sutra-mcp
    deploy:
      replicas: 1
```

**Line by line:**

- `build: .` rather than `image:` — the service is built from this repository, so there is no
  registry in the loop and no version skew between the file and the code. A deployed system would
  name a tagged image instead, and that is the one line that changes.
- `SUTRA_MCP_URL: http://sutra-mcp:9000` — the hostname is the *service name* from this file. Not
  an IP address, not a variable pointing at one: compose runs a resolver on its network, so the
  name is stable across restarts where an address is not.
- `ports: - "8080:8080"` publishes the container's port on the host. Only the api has one; the
  MCP service has none, so it is reachable from the api and from nothing else. That is a
  privilege boundary expressed as an absence, and absences are easy to delete by accident.
- `volumes: - desk-state:/app/state` — a **named volume**, not a bind mount of a host directory.
  A named volume is managed, has consistent ownership, and does not depend on the host's
  filesystem semantics; a bind mount on a desktop virtual machine is a network share, and
  databases behave badly on those. Both services mount the same one, which is how they share
  state and is exactly what part 5.2 examines.
- `depends_on: - sutra-mcp` controls **start order only**. It does not wait for the other service
  to be ready, which is a very common misreading: the api can start, be told the MCP service
  exists, and get a connection refused for the first several seconds. The fix is retry in the
  client, not a longer wait here.
- `deploy: replicas: 1` — the confession. In compose this key is only honoured by some
  deployment backends, so its practical effect on a laptop is limited; its real function is that
  it is the number, written down, next to a comment explaining it, in the file somebody edits
  when they want more.

Checking it needs an actual parse rather than a grep, and `pyyaml` is already installed:

```python
    compose = yaml.safe_load((HERE / "compose.yaml").read_text(encoding="utf-8"))
    api = (compose.get("services") or {}).get("sutra-api") or {}
    replicas = (api.get("deploy") or {}).get("replicas")
```

**Line by line:**

- `yaml.safe_load`, never `yaml.load`. The unsafe loader can construct arbitrary Python objects
  from a document, which turns reading a config file into running one.
- `(compose.get("services") or {})` rather than `compose["services"]` — a file that is valid YAML
  and missing the key should produce a failed check with evidence, not a `KeyError` that looks
  like a broken checker.
- The `or {}` idiom repeats because YAML can produce `None` for an empty mapping, so
  `.get("deploy", {})` is not sufficient: the key can exist with a null value.
- `replicas` is left as `None` when absent, and the check compares `replicas == 1`. A file that
  does not say how many replicas it runs fails, because "unstated" is the condition this part
  exists to eliminate.

## When it breaks

The compose file breaks by being read as a laptop convenience, and then by being trusted in the
two places where it is silent.

**`depends_on` does not mean ready.** The api starts, resolves `sutra-mcp`, connects, and gets:

```text
httpx.ConnectError: All connection attempts failed
```

for the first moments of the system's life, because the other container is running and its server
has not bound yet. Everything is configured correctly. The fix is a retry with backoff in the
client — Day 72's subject — and the trap is that adding a `healthcheck` and a
`condition: service_healthy` fixes it on a laptop and does nothing in the cluster, which has no
such ordering guarantee at all.

**The replica count is advisory.** Nothing enforces it. Somebody types `--scale sutra-api=2`,
which is a documented and inviting flag, and gets two containers with no warning of any kind. The
number in the file did not stop them; the comment beside it is the only thing that might. Part
[5.2](../05-the-word-stateless/5.2-two-replicas-one-failure.md) is what happens next, measured.

**And this file has never been run.** No container runtime exists here:

```text
/usr/bin/bash: line 1: docker: command not found
```

so the YAML is parsed and asserted on, and the composition has never been started. `compose up`
is a `TODO(me)` in the hub with the exact command. The things it would find that parsing cannot:
whether the image builds, whether the volume permissions match the container's uid, and whether
the MCP service's entry point exists.

## In production

**What a professional does.** Keeps the compose file as the local development and integration
environment, and treats it as the place where "how many processes is this system" is answered
first. In deployment the same shape is expressed in the platform's own language — and the value
of having written it here is that the translation is mechanical rather than a design exercise
done under time pressure.

**What degrades at scale.** Service count. Two services fit in a file a person reads; fifteen
becomes a file where nobody can see which service talks to which, and the dependency graph
matters more than any individual entry. That is the point at which the file stops being the
documentation and needs one.

**The failure that only shows with real traffic.** The shared volume. Two services mounting one
volume is fine while only one writes. The moment both write — or one writes while the other
reads — the semantics depend on the filesystem underneath, and on a desktop virtual machine that
filesystem is a network share with locking behaviour that databases explicitly do not support.
Part [5.1](../05-the-word-stateless/5.1-the-statefulness-audit.md) is where this repository's
version of that gets inventoried.

**The review comment a senior engineer leaves:** *"`depends_on` is start order, not readiness —
put the retry in the client now, because the cluster gives us even less. And keep the comment
next to `replicas: 1`; it is the only thing standing between us and `--scale`."*

**The interview question:** *"What does a compose file give you that a run command does not?"*
The answer that shows experience does not say convenience. It says the file forces the system to
be described as multiple processes with explicit boundaries, and that most of its value is
extracted while writing it, before anything is run.
