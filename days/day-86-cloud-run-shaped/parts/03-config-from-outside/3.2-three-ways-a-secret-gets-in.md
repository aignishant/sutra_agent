# 3.2 — Three ways a secret gets in, one of them acceptable

## One-line answer

A key can be baked into a layer, passed as a build argument, or injected at run time; the first
two put it in an artefact that gets copied, and only the third keeps it in the part of the system
that is never rebuilt and never pushed.

## The story

The spare key, and the three places people keep it.

Under the mat. In the drawer inside, cut for the cleaner and forgotten about. Or with the
neighbour, handed over on the morning you leave and taken back when you return.

All three work in the sense that somebody who needs to get in can get in. They differ in who else
can, and for how long. The one under the mat is available to everybody who has ever heard of
mats, permanently. The one in the drawer is fine until the flat is let to somebody else and
nobody remembers the drawer. The one with the neighbour exists only while you are away, is given
to a person you chose, and comes back.

Nobody thinks the mat is a good idea. People still use it, because it is the option that requires
no arrangement.

## The idea in plain language

Three places a secret can enter a container, and they are not equivalent:

| Way | What it looks like | Where the secret ends up | Verdict |
| --- | --- | --- | --- |
| baked into a layer | `COPY .env .` or `ENV SUTRA_API_KEY=...` | in the image, permanently, for everyone who pulls it | never |
| a build argument | `ARG API_KEY` used during the build | in the build metadata, readable from the image history | never |
| injected at run time | `-e SUTRA_API_KEY=...`, compose `environment:`, a platform secret | in the process's environment only | yes |

The first two fail for the same underlying reason and it is part
[1.2](../01-what-a-container-promises/1.2-a-layer-is-written-once.md)'s: **an image is copied.**
Not moved — copied, to a registry, to every machine that runs it, into every cache along the way.
A secret in an image has as many copies as the image has, and no way to count them.

The build argument is the subtle one, because it *feels* like run-time injection: the value is
not in the Dockerfile, it is passed on the command line, and it is used only during the build. It
still ends up recorded in the image's build history, which is readable from the image itself. It
is the key in the drawer: not obviously exposed, and permanently there.

Run-time injection is the neighbour. The value exists in the environment of a running process,
supplied by whoever started it, and it is gone when the process is gone. Nothing that gets copied
ever contains it.

The formulation worth keeping, from part
[2.3](../02-the-image-contract/2.3-the-build-context-nobody-looked-at.md): **the image is the
public artefact and the environment is the private part.**

## Why Sutra needs it

Because this repository has a real `.env`, Day 93 makes the repository public, and an image built
from a public Dockerfile is reproducible by anybody — so the only thing standing between the
project and a leaked key is that the key was never in anything reproducible.

And because "injected" has to have a testable meaning rather than being a word in a document.
There are three checks that make it testable, and all three run here.

## The mechanism

**Check one: nothing secret is in an `ENV`.** From `lab/image.py`:

```python
    baked = [e for e in envs if SECRET_NAMES.search(e.split("=")[0])]
```

**Line by line:**

- `e.split("=")[0]` looks at the variable's **name**, not its value. Matching on values means
  guessing what a key looks like, which is a losing game; matching on names catches
  `ENV GOOGLE_API_KEY=` regardless of what follows.
- The list comprehension collects every offending line rather than stopping at the first, so the
  report names all of them.
- `SECRET_NAMES` is the pattern from part [2.2](../02-the-image-contract/2.2-eight-properties-checked.md),
  written without word boundaries precisely so it matches inside `GOOGLE_API_KEY`.

**Check two: the secret-bearing files never reach the build context.** That is part
[2.3](../02-the-image-contract/2.3-the-build-context-nobody-looked-at.md), measured: with the
`.dockerignore` in place, `.env` is excluded; without it, `.env` and `.git/config` are both in.

**Check three: the app cannot start without the value.** That is part
[3.1](3.1-an-app-that-refuses-to-start.md), measured: `ConfigError: missing required environment:
SUTRA_API_KEY`. This is the one that turns injection from a convention into a property — if the
image *could* run without the variable, then some path exists where a default is used, and that
default came from somewhere.

Together the three say: it is not in the layers, it is not in the context, and the container is
useless without it. Where compose supplies it:

```yaml
    environment:
      PORT: "8080"
      SUTRA_API_KEY: ${SUTRA_API_KEY:?set it in the shell or a .env that is never copied}
      SUTRA_QUOTA_LEDGER: /app/state/quota.json
```

**Line by line:**

- `${SUTRA_API_KEY:?message}` is compose's *required-variable* form: it substitutes the value
  from the environment compose itself is running in, and if that is unset or empty it refuses to
  start and prints the message. A plain `${SUTRA_API_KEY}` would substitute an empty string and
  start a broken container.
- The value is not in this file. The file names the variable; the operator's shell supplies it.
  That is what makes `compose.yaml` safe to commit, which matters because it is a deployment
  artefact and belongs in the repository.
- `PORT` and `SUTRA_QUOTA_LEDGER` are written literally, because neither is secret. Treating
  every setting as a secret is how teams end up with a secret store full of port numbers, and
  then nobody can tell which entries matter.

```bash

```

**Line by line:**

- Line eight of the table is the `ENV` row; the rest of the table is other parts' subjects.

Measured on 2026-09-07:

```text

```

The evidence column prints the variable name and its value, which in a real finding is itself a
problem — a checker that logs secrets has moved the leak rather than fixed it. Here the value is
a teaching placeholder in a string constant. In `sutra/deploy.py` it should print the name and
redact the value, and that is a `TODO(me)` in the hub.

## When it breaks

The failure has no error text at any point, which is why it recurs. Written out, it is short and
every step is somebody being reasonable:

```text
1. the app needs a key locally, so it goes in .env         (correct)
2. .env is added to .gitignore                              (correct)
3. a Dockerfile is written with COPY . .                    (fast)
4. the image is built and pushed to a registry              (routine)
5. .env is now in a layer, in the registry, permanently
6. six months later the repository goes public
```

Step six is not what leaked the key. Step four did. Step six is only when somebody could find the
Dockerfile that explains where to look.

And the two responses that do not work:

- **Deleting the file in a later instruction.** Part
  [1.2](../01-what-a-container-promises/1.2-a-layer-is-written-once.md): the deletion is a marker
  in a later layer and the bytes remain in the earlier one. The running container genuinely does
  not have the file, which is what makes people believe it is fixed.
- **Rebuilding without it.** The new image is clean. The old image is still in the registry, in
  every cache, and on every machine that pulled it.

The only response that works is rotating the key, and the reason to know this part is that
rotation is expensive and the prevention is a one-line file.

## In production

**What a professional does.** Uses the platform's secret mechanism rather than plain environment
variables where one exists — a managed secret injected at start-up, or a file mounted into the
container and read once. The advantage is not secrecy in transit; it is that the value is
auditable, rotatable and revocable from one place, which a variable typed into a deployment
configuration is not.

**What degrades at scale.** Sprawl. Three variables is a list; a hundred services with their own
keys is an inventory problem, and the failure mode is a key nobody can attribute — it works, so
nobody dares rotate it. That is why the rotation story has to exist before the first key does.

**The failure that only shows with real traffic.** Logging. A service that logs its configuration
at start-up "for debugging" writes the key into a log aggregator, which is a second copied
artefact with the same properties as an image and usually broader access. This is the leak that
survives every image-level control, and the guard is to redact by name — the same
`SECRET_NAMES` list, applied to log output.

**The review comment a senior engineer leaves:** *"The `${VAR:?}` form is right. Now make the
checker redact the value when it reports a baked secret — right now our lint output is a place a
key can appear, and lint output goes to CI logs."*

**The interview question:** *"How do secrets get into a container?"* The answer that shows
experience names all three routes, explains that a build argument is recorded in the image
despite feeling transient, and finishes with the operational consequence: if it was ever in a
pushed image, the fix is rotation, not a rebuild.
