# 3.1 — An app that refuses to start

## One-line answer

Configuration that is missing should stop the process at import, naming the setting, rather than
producing a working-looking service that fails on the first request that needs it — and the
difference is measurable: a complete environment exits 0 and an incomplete one exits 1 with
`ConfigError: missing required environment: SUTRA_API_KEY`.

## The story

The cylinder that is not handed over without the booking slip.

The delivery arrives at the gate. The man has the cylinder on his shoulder and asks for the slip.
You cannot find it. He does not leave the cylinder and trust you to sort it out later — he takes
it back down and it comes on the next round.

It is annoying, and it is right. The alternative is a household that has a cylinder and no record
of it, discovered a month later by somebody else, when the discrepancy is harder to unpick and
the man who delivered it is not there to ask.

The check happens at the gate because the gate is where it is cheap.

## The idea in plain language

Every service needs settings it cannot invent: which key to use, which port to bind, where its
state lives. There are two moments to discover that one is missing.

**At start-up**, where the process has done nothing yet, no request is in flight, and the error
can name the setting. A platform sees the container exit immediately, reports a crash loop, and
somebody reads one line and fixes it.

**On the first request that needs it**, where the service has already reported itself healthy,
accepted traffic, and now fails somewhere deep — as a `None` where a key should be, a
`KeyError` in a library, or, worst, a silent fall back to a default that is wrong.

The second is the default behaviour of almost every codebase, because the natural way to read a
setting is at the point of use:

```text
key = os.environ.get("SUTRA_API_KEY")   # None if absent, and nothing happens yet
```

That line does not fail. It produces `None`, which travels, and fails later somewhere with no
connection to the cause.

The rule is: **read every setting once, at import, and refuse.** In a container this matters more
than elsewhere, because a container's whole configuration arrives from outside at start-up, so
start-up is the moment when the information is complete and the blast radius is zero.

And there must be **no defaults for anything that matters**. A default is a decision made by
whoever wrote the code, applied in an environment they never saw. `PORT` defaulting to 8080 in a
Dockerfile is fine — it is a deployment artefact, read by a deployer. `SUTRA_API_KEY` defaulting
to anything is a service that runs with the wrong credentials and says nothing.

## Why Sutra needs it

Because the container gets its entire configuration from the environment, which means the set of
ways it can be misconfigured is exactly the set of environment variables. That is a small,
enumerable list, and checking it costs one function.

And because Day 88's cluster restarts a container that exits. An app that refuses to start
produces a visible, named, repeating failure. An app that starts half-configured produces a
healthy pod serving errors, which is the harder thing to notice and the harder thing to attribute.

## The mechanism

The whole of it is one tuple and one function, run at import time:

```python
REQUIRED_ENV = ("SUTRA_API_KEY", "PORT", "SUTRA_QUOTA_LEDGER")


class ConfigError(RuntimeError):
    """Raised at import time when the environment is incomplete."""


def load_config() -> dict[str, str]:
    """Read every required setting, or refuse to start and say which one is missing."""
    missing = [name for name in REQUIRED_ENV if not os.environ.get(name)]
    if missing:
        raise ConfigError(f"missing required environment: {', '.join(missing)}")
    return {name: os.environ[name] for name in REQUIRED_ENV}


CONFIG = load_config()
```

**Line by line:**

- `REQUIRED_ENV` is a tuple at module level, so the list of settings is a readable fact rather
  than something scattered through the code. A deployer can find it in one grep.
- `not os.environ.get(name)` rather than `name not in os.environ` — an empty string is a missing
  setting. `SUTRA_API_KEY=` in a compose file is a real and common way to have a variable that
  exists and is useless.
- `missing` collects **all** of them before raising. Raising on the first means somebody fixes
  one setting, redeploys, and discovers the second — three rounds for three variables.
- A named `ConfigError` subclassing `RuntimeError`, so a caller can catch this specifically and a
  bare `except Exception` does not swallow it into something vague. Principle 10: raise a
  specific exception.
- `CONFIG = load_config()` at module scope, so the failure happens on **import**. Putting it
  inside a start-up hook would delay it past the point where the server has bound its port.
- The return is a plain dict of exactly the required keys, so nothing downstream reads
  `os.environ` again. One place reads the environment; everything else reads `CONFIG`.

Measuring it needs two processes, because "refuses to start" is a property of a process rather
than of a function:

```python
    clean = {k: v for k, v in os.environ.items() if k not in _app_settings()}
    done = subprocess.run(
        [sys.executable, "-c", code],
        cwd=HERE,
        env={**clean, **env},
        capture_output=True,
        text=True,
    )
```

**Line by line:**

- The child starts from this shell's environment **minus** the app's own settings, so it inherits
  what an operating system needs and nothing the app reads. An earlier version handed the child a
  nearly empty environment and got
  `OSError: [WinError 10106] The requested service provider could not be loaded or initialized` —
  the socket layer needs `SYSTEMROOT`. That run measured Windows, not the app.
- `capture_output=True` so the child's traceback comes back as a string to be printed as evidence
  rather than interleaved with the parent's output.
- `sys.executable` rather than `"python"`, so the child is the same interpreter `uv run` chose.

Run it:

```bash
cd days/day-86-cloud-run-shaped/lab
uv run python config.py; echo "exit: $?"
```

**Line by line:**

- No flag: boot with a complete environment, then boot again with one setting removed.

Measured on 2026-09-07:

```text
the app reads three settings and has a default for none of them:
  PORT, SUTRA_API_KEY, SUTRA_QUOTA_LEDGER

  complete environment   -> exit 0
    started, config keys: ['PORT', 'SUTRA_API_KEY', 'SUTRA_QUOTA_LEDGER']

  SUTRA_API_KEY removed  -> exit 1
    _app.ConfigError: missing required environment: SUTRA_API_KEY

  a complete environment starts; an incomplete one refuses, and says which
  setting is missing before it has served a single request
exit: 0
```

The second block is the deliverable: a non-zero exit, and a message naming the variable. That is
everything an operator needs, produced before the process has bound a port.

## When it breaks

The check breaks by never being given a bad input — which is the same defect as an eval suite
whose cases cannot fail, and it is what the ablation demonstrates:

```bash
uv run python config.py --half; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  complete environment   -> exit 0
    started, config keys: ['PORT', 'SUTRA_API_KEY', 'SUTRA_QUOTA_LEDGER']

  --half: only the complete boot was tried, so nothing was disproved
  a check that never supplies a bad input cannot tell you the app validates anything
exit: 1
```

The app is unchanged and correct in both runs. What changed is that one of them tested the
refusal and one only tested the success — and a run that only tests the success reports exactly
the same green as an app with no validation at all.

The other way this breaks is a partial guard. A `REQUIRED_ENV` that lists two of the three
settings passes its own check and fails at the first request that needs the third:

```text
KeyError: 'SUTRA_QUOTA_LEDGER'
```

raised from inside a request handler, after the health check has already reported the service
ready. Nothing about that traceback says "misconfigured" — it looks like a bug in the code that
raised it.

## In production

**What a professional does.** Puts the settings in a typed, validated object at start-up — a
dataclass or a settings model — so that missing, empty and malformed are three distinct errors
with three distinct messages, and so the rest of the code cannot read the environment at all.
The list of settings then has one home, which is the thing a deployer actually needs.

**What degrades at scale.** The number of settings, and their coupling. Three variables are a
tuple; thirty are a document, with defaults that are only correct in one environment and
overrides nobody can trace. The failure is not technical — it is that no single person knows what
the service needs, and the answer stops being derivable from the code.

**The failure that only shows with real traffic.** A setting that is present and wrong. This part
catches absence, which is the easy half. A key that is well-formed and belongs to a different
project produces a service that starts cleanly, reports ready, and fails on the first real
request with an authentication error from a provider — and no amount of start-up validation finds
it, because the value is only wrong relative to something the app cannot see.

**The review comment a senior engineer leaves:** *"Fail at import, list all the missing names at
once, and treat empty string as missing. Also: nothing below this line should touch `os.environ`
again — if it does, the list at the top stops being the list."*

**The interview question:** *"Where should a service read its configuration?"* The answer that
shows experience says once, at start-up, into a validated object, with no defaults for anything
that has security or cost consequences — and then explains why: the alternative is discovering a
missing setting in production, in a request, at a point in the code that has no idea what it is
for.

Same app, two exit codes. Say which run you would rather have in a pipeline, and what the other
