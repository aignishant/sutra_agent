# 2.3 — The build context nobody looked at

## One-line answer

💥 Without a `.dockerignore` the build would send **414,219,769 bytes across 22,020 files** to be
packaged, including this repository's real `.env` and `.git/config`; with one it sends **40 files
and 2,207,035 bytes** — and the difference is not a build-time optimisation, it is whether a live
key ends up in an immutable layer.

## The story

💥 **The box of papers for the accountant.**

🎬 **The scene.** Year end. The accountant asks for the invoices. You are busy, the invoices are
in the filing drawer along with everything else, so you take the drawer out, tip it into a box,
and send the box. Everything they asked for is definitely in there.

😬 **The naive fix.** They will pick out what they need. That is their job, and anything they do
not need they will ignore.

💥 **Why it fails.** The drawer also had the medical letters, the salary slips for the person who
works in your house, and a bank statement with the full account number. None of that was
requested, none of it is relevant, and all of it is now in somebody else's office, photocopied
into their file, and outside your control. The accountant did nothing wrong. You did not decide
to send those papers — you decided not to look.

💡 **The insight.** The mistake is not what was sent. It is that **the default was "everything"
and nobody chose the default.** The invoices were the intention; the drawer was the instruction.

## The idea in plain language

Before a build runs, everything in the build directory is packaged and handed to the builder.
That package is the **build context**, and it is assembled before any instruction executes.
`COPY` can then only copy from it, but the whole thing has already been collected.

`.dockerignore` is the list of what is left out of that collection. It is usually explained as a
speed optimisation — smaller context, faster build — and that framing is why it gets written
late, or not at all.

It is a security control. The reasoning is two facts already established:

- part [1.2](../01-what-a-container-promises/1.2-a-layer-is-written-once.md): a layer is written
  once and never edited, so a file copied in is in the image permanently, whatever a later
  instruction does;
- Principle 9: this repository has a real `.env` with real keys, deliberately kept out of git,
  and Day 93 makes the repository public.

Put those together and the conclusion is uncomfortable: **git is not the only place a secret can
leak, and the image is the one nobody greps.** An image is pulled by anybody who has access to
the registry, and unpacking a layer requires no privilege at all.

The rule worth carrying: *the image is a public artefact and the environment is the private part.*
Anything secret must live outside the thing you can rebuild.

## Why Sutra needs it

Because the `.env` in this repository is not a placeholder. It is 730 bytes of real settings, it
is correctly gitignored, and until today nothing has ever asked whether it would end up in an
image.

And because the fix has to be written **before the first build**. The first `docker build`
anybody runs is the one that would bake the file into a layer, and a layer that has been pushed
cannot be recalled from everybody who pulled it. The remedy after the fact is not a rebuild; it
is rotating every key that was in the file.

## The mechanism

The measurement walks the repository the way a build would collect it, and applies the real
ignore rules:

```python
def ignored(rel: str, rules: list[str]) -> bool:
    """Would a build exclude this path?

    A faithful subset of docker's matcher: a directory rule excludes everything beneath it,
    and a glob is matched against the whole relative path and against each single segment.
    Docker's real syntax also has `!` re-includes and `**`; neither appears in this
    .dockerignore, and pretending to implement them would be worse than saying so.
    """
    for rule in rules:
        bare = rule.rstrip("/")
        if rel == bare or rel.startswith(bare + "/"):
            return True
        if fnmatch.fnmatch(rel, rule) or fnmatch.fnmatch(Path(rel).name, rule):
            return True
    return False
```

**Line by line:**

- `rule.rstrip("/")` then a prefix test — that is the directory case. `data/` has to exclude
  `data/sessions.db`, and a plain glob match would not, because `fnmatch` does not treat `/`
  specially.
- Two `fnmatch` calls: one against the whole relative path, one against the final segment. That
  is what makes `*.pyc` match `sutra/__pycache__/agent.cpython-312.pyc`, where a whole-path match
  alone would fail.
- The docstring names what this is not. Docker's matcher supports `!` re-inclusion and `**`,
  neither of which appears in the `.dockerignore` this day wrote — so the subset is faithful *for
  this file*, and a check that quietly ignored a `!` line would produce a confidently wrong
  answer. Stating the limit is the difference between a measurement and a claim.
- Returns on the first matching rule. Docker's real semantics are last-match-wins because of
  `!`; with no `!` lines the two agree, which is exactly why the limitation had to be checked
  rather than assumed.

The walk itself is deliberately naive:

```python
def walk() -> list[tuple[str, int]]:
    """Every file under the repository root, as a build would find it."""
    out = []
    for path in ROOT.rglob("*"):
        if not path.is_file():
            continue
        try:
            out.append((path.relative_to(ROOT).as_posix(), path.stat().st_size))
        except OSError:
            continue
    return out
```

**Line by line:**

- `rglob("*")` with no exclusions at all, because the point is to measure the default. A walk
  that skipped `.git` would be measuring the answer it wanted.
- `as_posix()` so the paths are `data/sessions.db` on every platform. On Windows the separator is
  a backslash and every pattern in the ignore file would silently fail to match.
- `except OSError: continue` — a file that vanishes mid-walk, or that the process cannot stat, is
  skipped rather than crashing the measurement. On a live repository with caches being written,
  this happens.
- Sizes come from `stat()`, so the total is bytes on disk rather than a file count. The file count
  is the impressive number and the byte count is the one that decides build time.

Run it:

```bash

```

- No flag: the `.dockerignore` this day wrote is applied.

**Forty files out of twenty-two thousand.** Eighteen rules remove 99.5% of the bytes, and the
files that survive are the ones the Dockerfile actually names.

## When it breaks

Delete the file — or, far more commonly, never write it — and run the same measurement:

```bash
uv run python context.py --no-ignore; echo "exit: $?"
```

Measured on 2026-09-07:

```text
.dockerignore: not used (the ablation)

  everything under the repository root:  22020 files  414,219,769 bytes
  what COPY . . would send:              22020 files  414,219,769 bytes
  excluded:                                  0 files            0 bytes
  .env          IN THE CONTEXT (1 file)
  .env.local    excluded
  .git/config   IN THE CONTEXT (1 file)
  data/         excluded
  logs/         excluded

  2 file(s) that must never ship are in the build context
  a layer is immutable: deleting the file in a later RUN does not remove it
exit: 1
```

Two files. The first is this repository's real `.env`. The second is `.git/config`, which is the
less obvious one and often the more damaging: it carries remote URLs, and a remote URL is where a
token gets embedded when somebody clones with credentials in the address.

Note what the Dockerfile in this lab does *not* do — it has no `COPY . .`, only
`COPY sutra ./sutra` and `COPY sutra_mcp ./sutra_mcp`. So with this Dockerfile the `.env` is
collected into the context and never copied into a layer. That is a second line of defence and it
is not a substitute for the first, because:

```text
1. the context is still transferred in full: 414 MB across the wire to the builder
2. one COPY . . added later, by anybody, in a hurry, undoes it
3. some build backends cache the context itself
```

The security property you want is *the file was never collected*, not *the file was collected and
then not used*. There is no error text for the difference, and the difference is the whole
finding.

## In production

**What a professional does.** Writes `.dockerignore` before the Dockerfile, treats it as a
denylist starting from `*` with explicit re-inclusions where the team is disciplined enough, and
adds "grep the built image" to the security review rather than only "grep the repository". Day
92's review gets that line because of this part.

**What degrades at scale.** Context transfer time and cache invalidation. A large context is slow
to send on every build, and a context that includes churning directories — build caches, test
output — invalidates layers for reasons unrelated to the code. Teams feel this as "the build got
slow" long before anybody looks at what is being sent.

**The failure that only shows with real traffic.** A secret that was correct to have locally.
Nobody adds a key to an image on purpose. The path is always the same: a developer needs the app
to run locally, puts the settings in a file, the file is correctly gitignored, and then a build
instruction that predates the file copies the whole directory. Every step is reasonable and the
result is a credential in a registry.

**The review comment a senior engineer leaves:** *"`.dockerignore` before anything else, and make
it deny by default. And since we have a real `.env` in this repo — if any image has ever been
built and pushed from this tree, rotate the keys rather than argue about whether it was in a
layer."*

**The interview question:** *"What goes in `.dockerignore`?"* The answer that shows experience
does not list files. It says the file is a security control, explains that a layer is immutable
so a later deletion is not a deletion, and mentions `.git` — which most people forget and which
carries both history and remote credentials.
