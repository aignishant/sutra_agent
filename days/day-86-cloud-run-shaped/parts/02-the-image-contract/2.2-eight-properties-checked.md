# 2.2 — Eight properties, checked without a daemon

## One-line answer

Eight of the things a deployable image has to get right are visible in the text of the Dockerfile
and the compose file, so they can be checked on a machine with no container runtime at all — and
a Dockerfile written quickly gets one of the eight.

## The story

The pre-delivery check on a new bicycle.

The bike arrives at the shop in a box, half assembled. Before it is handed over, somebody runs
through a list: brakes bite, wheels true, gears index, bolts to torque, reflectors on, bell
fitted. It is a short list and it takes a few minutes.

None of it is a test ride. A test ride finds different things — a creak, a saddle at the wrong
height, whether it suits the rider. The list is not trying to be a test ride. It is trying to
catch the eight things that are wrong often enough, and cheap enough to check, that not checking
them is negligence.

A shop that skips the list because "we will find it on the test ride" finds most of it. And once
in a while somebody rides away with the front brake pads rubbing.

## The idea in plain language

There is no container runtime on this machine, so the image cannot be built and cannot be run.
That rules out a whole class of checks and leaves a surprisingly useful one: everything that is a
property of the **text**.

Eight properties, and each of them is a failure that ships regularly:

| # | Property | What it prevents |
| --- | --- | --- |
| 1 | base image pinned, not `:latest` | the environment moving under an unchanged file |
| 2 | dependencies copied before source | a full reinstall on every source edit |
| 3 | a named non-root `USER` | a container escape landing on root |
| 4 | no secret in an `ENV` | a key baked into an immutable layer |
| 5 | the port comes from `$PORT` | listening where the platform is not looking |
| 6 | binds `0.0.0.0`, not loopback | a healthy process nothing can reach |
| 7 | a `HEALTHCHECK` exists | a wedged container that is never replaced |
| 8 | compose declares exactly one replica | the failures in part 5.2, in production |

What the list is **not** is a test that the image works. It cannot tell you the base image exists,
that the packages resolve, or that the entry point imports. Saying so is part of the check: a
list that oversells itself gets trusted for things it does not do, which is worse than not having
it.

## Why Sutra needs it

Because the alternative on this machine is nothing. The image is a deliverable of this phase, it
cannot be built here, and "we will check it when someone installs a runtime" is how a Dockerfile
gets to Day 93 unexamined.

And because seven of the eight are exactly the failures Days 87 and 88 would hit. A managed
platform rejects an image that ignores `PORT`; a cluster's readiness probe fails against a
loopback bind; a shared registry keeps a baked secret for ever. Catching them in text costs
nothing and each would otherwise be found by a deployment.

## The mechanism

Every check reads a real file and returns a triple — the property, whether it holds, and the
evidence that decided it:

```python
def checks(dockerfile: str, compose: dict) -> list[tuple[str, bool, str]]:
    """Eight properties, each with the evidence that decided it."""
    froms = re.findall(r"(?mi)^FROM\s+(\S+)", dockerfile)
    base = froms[0] if froms else ""
    envs = re.findall(r"(?mi)^ENV\s+(.+)$", dockerfile)
    copies = re.findall(r"(?mi)^COPY\s+(.+)$", dockerfile)
    cmd = " ".join(re.findall(r"(?mi)^CMD\s+(.+)$", dockerfile))
```

**Line by line:**

- `(?mi)` — multiline so `^` matches the start of each instruction, and case-insensitive because
  `FROM` and `from` are both legal and people mix them.
- `froms[0]` rather than the last one. A multi-stage build has several `FROM` lines and the first
  is the one this single-stage file has; taking the last would silently check the wrong stage in a
  file that later grows a builder stage. That is a real limitation and it is why the variable is
  named for what it is.
- `cmd` joins every `CMD` line into one string. A Dockerfile with two `CMD` lines is legal and
  only the last takes effect — joining them means the check reads a command that never runs.
  Deliberate: it makes the check conservative, and a second `CMD` is a bug worth failing on
  anyway.
- Everything is a regular expression over text, not a parse. A real parser would handle line
  continuations and here-documents; this handles the file that exists. Naming what it does not do
  is what keeps it honest.

The secret check has one subtlety worth its own line:

```python
# No word boundaries around the alternatives. An underscore is a word character, so
# `\bAPI_KEY\b` never matches inside GOOGLE_API_KEY - which is the exact name people bake in.
SECRET_NAMES = re.compile(r"(API_KEY|TOKEN|SECRET|PASSWORD|CREDENTIAL)", re.I)
```

**Line by line:**

- The comment records a bug that was in this file. The first version used `\bAPI_KEY\b`, which
  looks more careful and is wrong: `_` counts as a word character, so there is no boundary
  between `GOOGLE` and `API_KEY`, and the check passed a Dockerfile containing
  `ENV GOOGLE_API_KEY=...`.
- Dropping the boundaries makes the check greedier, which is the right direction for a security
  check: a false alarm costs a glance, a miss costs a rotated key.
- `re.I` because `Env api_key=` is legal Dockerfile.

Eight of eight, with the deciding line printed beside each. The evidence column is not decoration:
it is what lets a reader disagree with the checker instead of trusting it.

## When it breaks

A check that passes everything has not been shown to work. So the ablation is a Dockerfile
written the way a first one is written — adapted from a local run command, in a hurry:

```bash
uv run python image.py --sloppy; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  base image is pinned, not :latest     BAD python:latest
  dependencies copied before source     BAD no lockfile COPY
  runs as a named non-root user         BAD no USER line
  no secret baked into an ENV           BAD GOOGLE_API_KEY=AIzaSyDummyValueForTeaching
  the port comes from the platform      BAD ["uvicorn", "sutra.api:app", "--host", "127.
  binds 0.0.0.0, not loopback           BAD ["uvicorn", "sutra.api:app", "--host", "127.
  a HEALTHCHECK exists                  BAD no HEALTHCHECK line
  compose declares exactly one replica  ok  replicas=1

  2 of 8 properties hold
```

**Seven lines of Dockerfile, six failures.** Not one of them is exotic; every one is what you get
by writing down what you type locally. And the one property it passes — the replica count — it
passes because that lives in the compose file, which was not the thing written in a hurry.

The failure this check cannot see has no output at all, because nothing runs:

```text
/usr/bin/bash: line 1: docker: command not found
```

So `8 of 8` means *eight text properties hold*. It does not mean the image builds. The honest
reading of a green run here is "nothing on the list is wrong", and the list is short on purpose.

## In production

**What a professional does.** Runs a real container linter in continuous integration alongside
the build — the ecosystem has several, and they check dozens of rules rather than eight. This
list exists because it can run where no runtime does; where a runtime exists, build the image and
lint it properly, and keep a small local list only for the project-specific rules a general
linter cannot know, such as the replica count.

**What degrades at scale.** Rule count against attention. Eight findings get read. Eighty
findings get a baseline file, and a baseline file is where rules go to be permanently ignored —
Day 82's quarantine, in a different costume. The discipline is the same: a suppressed rule needs
a date and an owner.

**The failure that only shows with real traffic.** Drift between the checked file and the
deployed one. A team that builds from `Dockerfile` and deploys from `Dockerfile.prod` is linting
one and running the other, and every finding in this part is available again in the file nobody
checks.

**The review comment a senior engineer leaves:** *"Print the evidence, which you do — but also
print what this does not check. Somebody is going to read `8 of 8` and think the image builds."*

**The interview question:** *"How do you validate a Dockerfile?"* The answer that shows
experience separates the layers: text properties by a linter in CI, buildability by actually
building it in CI, and behaviour by starting the container and probing it — and notes that most
teams do the first and skip the third, which is where health-check bugs live.
