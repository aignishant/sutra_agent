# 2.1 — Writing the Dockerfile

## One-line answer

The file is twenty lines and every one of them is a decision somebody will otherwise have to
remember — so it is written in the order things change, from the base image that changes yearly
to the source that changes hourly, with the user dropped from root exactly once.

## The story

The tiffin carrier packed the same way every day.

Four tiers, and everybody in the house knows the order: rice at the bottom, dal above it, the
dry vegetable next, the pickle in the small top tier so it never leaks into anything.

Nobody decided this at a meeting. It settled because of what the order costs. The pickle goes on
top because it is the thing most likely to change day to day and the least trouble to swap. The
rice goes at the bottom because it is the same every day and because everything else sits on it.
And once the order is fixed, anybody in the house can pack it and anybody can open it and find
what they want without unpacking the lot.

Change the order and nothing is broken. It is just that every morning is now slightly harder,
for ever.

## The idea in plain language

A Dockerfile is a sequence of instructions, and the sequence is the design. Part
[1.2](../01-what-a-container-promises/1.2-a-layer-is-written-once.md) established why: each
instruction is a layer, layers are cached by their inputs, and everything after a changed layer
is rebuilt.

So the file is written in **increasing order of change frequency**:

| Order | What | Changes |
| --- | --- | --- |
| 1 | the base image | yearly, and only when you decide |
| 2 | the package manager binary | rarely, and pinned |
| 3 | the dependency install | when `uv.lock` changes |
| 4 | the application source | every commit |
| 5 | the user, the port, the command | almost never, and cheap to rebuild |

Rows four and five look out of order — surely the cheap ones go last regardless? They do go
last, and the reason is different: `USER` has to come after every instruction that needs to
write to `/app`, because after it the build itself is unprivileged. It is not about caching at
all. Two different rules produce the same layout, which is why the layout looks obvious once
written and is not obvious while writing.

The whole file is in `lab/Dockerfile`. Part
[1.1](../01-what-a-container-promises/1.1-an-image-is-a-recipe.md) walked the first half and
part [1.3](../01-what-a-container-promises/1.3-the-platform-chooses-the-port.md) the command.
This part is about the two instructions neither of them covered, which happen to be the two that
carry the most weight per character.

## Why Sutra needs it

Because this file is the deliverable that Days 87 and 88 both consume, and it is the one artefact
in the phase that a stranger executes without reading. Everything else in the repository is read
by people; an image is read by a machine.

And because the two instructions this part covers — the user and the health check — are the two
that a first Dockerfile omits, and both are the kind of omission that is invisible until the
day it is not.

## The mechanism

**Dropping privilege.** One instruction, and the placement matters more than the content:

```dockerfile
RUN useradd --create-home --uid 10001 desk && chown -R desk:desk /app
USER desk
```

**Line by line:**

- `useradd` and `chown` joined with `&&` in a single `RUN`. Two `RUN` lines would produce two
  layers, and the second would contain a fresh copy of every file in `/app` with new ownership —
  doubling the image's application layer for nothing. This is part
  [1.2](../01-what-a-container-promises/1.2-a-layer-is-written-once.md)'s immutability showing up
  as a size problem rather than a security one.
- `--create-home` because the process needs somewhere writable that is not `/app`; several Python
  tools want a home directory and fail obscurely without one.
- `--uid 10001` — an explicit, high, non-system id. Left to the system, the number varies between
  base images, and it matters the moment a volume is mounted: file ownership on a mount is by
  number, not by name, so an image whose user id drifts loses access to its own data.
- `chown -R desk:desk /app` before dropping, because after `USER desk` the build cannot change
  ownership of anything.
- `USER desk` applies to every later instruction **and** to the running container. It is one
  line, it costs nothing, and it is the difference between a container escape landing on an
  unprivileged account and landing on root.

**The health check.** The instruction is long, and every part of it is a decision:

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD python -c "import os,urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:'+os.environ['PORT']+'/readyz').status==200 else 1)"
```

**Line by line:**

- `--start-period` exists so that a slow first start is not counted as a failure. Without it, an
  application that takes a moment to import its dependencies is killed and restarted, repeatedly,
  and the restart loop looks like a crash rather than a timing problem.
- `--retries=3` means three consecutive failures before the container is declared unhealthy. One
  failed probe is a blip; three in a row is a state.
- `--timeout=3s` — a probe that hangs is a failed probe. Without a timeout, a wedged process
  keeps a health checker waiting instead of being replaced, which is the exact situation the
  check exists to detect.
- `python -c` rather than `curl`, because the base image is `slim` and does not have `curl`. A
  health check that invokes a binary the image does not contain fails every time, and the failure
  looks exactly like the application being broken.
- `127.0.0.1` here, not `0.0.0.0` — the probe runs *inside* the container, so loopback is
  correct and is the narrower choice. Part
  [1.3](../01-what-a-container-promises/1.3-the-platform-chooses-the-port.md) is the general rule
  and this is the case where the inside is where you are standing.
- `os.environ['PORT']` — the probe reads the same variable the server does. Hard-coding `8080`
  here would produce a health check that fails whenever the platform assigns anything else, which
  is a self-inflicted restart loop.
- `/readyz`, not `/healthz`. Section 4 is the whole argument; the short version is that a process
  which is alive and cannot work should stop receiving traffic, and only readiness knows that.

## When it breaks

The user instruction breaks on volumes, and the error is about permissions rather than about
users:

```text
PermissionError: [Errno 13] Permission denied: '/app/state/quota.json'
```

That is what a container running as uid 10001 gets when the mounted directory on the host is
owned by a different id. The fix is not to run as root; it is to make the ownership match, which
means the uid has to be a number you chose rather than one the base image happened to assign.

The health check breaks in a way that is worse, because it is silent on the machine that wrote
it:

```text
/usr/bin/bash: line 1: docker: command not found
```

That is this machine, today. **The `HEALTHCHECK` above has never been executed.** It is
syntactically checked by `image.py` and has never run against a live container, and neither has
any other line in the file. The exact command that would test it is in the hub's `TODO(me)`
list, it needs a container runtime, and it costs nothing but an installation.

That limitation is worth stating plainly rather than burying: a Dockerfile that has never been
built is a hypothesis with good grammar. The static checks in part
[2.2](2.2-eight-properties-checked.md) catch the eight failures that are visible in text. They
cannot catch a base image that does not exist, a package that will not install, or an entry point
that does not import.

## In production

**What a professional does.** Builds the image in continuous integration from the first commit
that contains a Dockerfile, and runs the container once in that job — start it, probe `/readyz`,
stop it. That converts every one of the failures this part lists from "found in a deployment" to
"found in a build", and it is roughly ten lines of CI configuration.

**What degrades at scale.** The user and the volume. One service with one mount is a uid you set
once; twenty services sharing mounted storage is a numbering scheme somebody has to own, and
teams that did not choose numbers early end up with images that cannot read each other's data.

**The failure that only shows with real traffic.** The health check that is too cheap. A probe
that only checks the process — or, subtly, one that checks a dependency by reading a cached value
— reports healthy under load precisely when the dependency is saturated. Part
[4.2](../04-health-checks/4.2-the-check-that-only-watched-the-process.md) measures the simplest
version of this.

**The review comment a senior engineer leaves:** *"Good, but pin the uid and say why in a comment
— the next person will delete the number because it looks arbitrary, and then the volume mount
breaks in an environment we do not test."*

**The interview question:** *"What is wrong with a container running as root?"* The answer that
shows experience does not stop at "it is bad practice". It says that root in the container is
often mapped to root on the host, so a container escape or a mounted host path turns a small
application bug into a machine-level one — and then notes that the fix is one line and is
therefore inexcusable to omit.
