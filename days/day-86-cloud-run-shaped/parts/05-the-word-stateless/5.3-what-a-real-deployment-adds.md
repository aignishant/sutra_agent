# 5.3 — What a real deployment adds

## One-line answer

The lab wrote a correct image and proved two real defects without ever building anything, and the
distance between that and a deployment is nine items — the first three of which are free, one of
which is an installation, and two of which are the reason the replica count is one.

## The story

The snag list before you take the keys.

The flat is finished. You walk round it with the builder and a notepad, and the list comes out
short and specific: the second bedroom socket is not live, the bathroom door catches on the tile,
one window handle is missing, the kitchen tap drips.

None of those stop you moving in. What they do is turn "it looks done" into a set of things with
names, and the walk is the only moment when the builder is still there and still cheap. A snag
found the week after handover is a phone call and a favour; the same snag found on the walk is
half an hour with a screwdriver.

The list's value is not its length. It is that it was made while somebody could still act on it.

## The idea in plain language

This day produced a real Dockerfile, a real `.dockerignore`, a real compose file and five
measurements. It also never built an image, because there is no container runtime on this
machine. So the honest summary has two columns: what is done, and what is a snag.

Here is the list, in the order it should be worked, with what each costs.

**1. Install a container runtime and build the image.** Everything below assumes an image exists.
The Dockerfile has been checked in eight ways by text and has never been executed — it could fail
on the base image, the lockfile, or the entry point, and no check here would know.

**2. Run the container once and probe it.** Start it, ask `/readyz`, stop it. That converts the
`HEALTHCHECK`, the `$PORT` handling and the `0.0.0.0` bind from arguments into facts. Ten lines of
continuous integration.

**3. Add the healthcheck to the compose api service.** The Dockerfile has one; `compose.yaml`
does not. Part [4.2](../04-health-checks/4.2-the-check-that-only-watched-the-process.md)'s review
comment, and it is four lines of YAML.

**4. Pin the base image by digest.** The Dockerfile has a `TODO(me)` with the exact command. It
needs a registry lookup, so it needs item 1 first.

**5. Move the session store out of the process.** Part
[5.2](5.2-two-replicas-one-failure.md)'s first failure. Day 47 built persistent sessions; this is
pointing the app at them rather than at a dictionary, and it is what makes a second replica
possible at all.

**6. Make the ledger increment atomic.** Part [5.2](5.2-two-replicas-one-failure.md)'s second
failure, which is already live with one replica. Not a lock — a store with a transaction, or a
write that is atomic by construction.

**7. Redact secret values in the checker's output.** Part
[3.2](../03-config-from-outside/3.2-three-ways-a-secret-gets-in.md): `image.py` currently prints
the offending line, which in a real finding means printing a key into a CI log.

**8. 🅿️ Parked — a managed deployment.** `adk deploy` packages this shape onto a hosted runtime,
and Addendum 02 forbids anything that needs a billing account. Day 87 walks the configuration
without running it, which is why building the shape locally is the part that teaches.

**9. 🅿️ Parked — more than one replica.** Blocked on items 5 and 6, and it stays parked until both
are done, because the measurement in part 5.2 is what happens otherwise.

**Items 3 and 7 are free and neither needs a runtime.** Item 1 is an installation. Items 5 and 6
are the real work, and they are the two that the number in the compose file is waiting on.

## Why Sutra needs it

Because Day 88 needs an image that has been built at least once, and discovering on that day that
the Dockerfile does not build turns a cluster day into a debugging day.

And because items 5 and 6 are not deployment concerns that can be deferred to a deployment. Item
6 is a live defect in the system as it runs today, with one replica, measured — the ledger loses
updates now, and the free-tier allowance it is supposed to protect is Day 78's entire subject.

## The mechanism

The list, with costs and what each unblocks:

| # | Item | Where | Roughly | Unblocks |
| --- | --- | --- | --- | --- |
| 1 | install a runtime, build the image | a laptop | an installation | everything below |
| 2 | run and probe it in CI | `.github/` or equivalent | a short job | items 4, 8, 9 |
| 3 | healthcheck in the compose api service | `compose.yaml` | four lines | nothing; it is just right |
| 4 | pin the base by digest | `Dockerfile` | one command | reproducible builds |
| 5 | session store outside the process | `sutra/` | a day | item 9 |
| 6 | atomic ledger increment | `sutra/` | a day | item 9, and today's correctness |
| 7 | redact values in the checker output | `lab/image.py`, `sutra/deploy.py` | one function | safe CI logs |
| 8 | 🅿️ managed deployment | not built | needs a billing account | — |
| 9 | 🅿️ more than one replica | not built | needs 5 and 6 | scaling |

Item 3 is the one to do while reading this, since it is four lines and the argument for it was
measured two parts ago:

```yaml
    healthcheck:
      test: ["CMD", "python", "-c", "import os,urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:'+os.environ['PORT']+'/readyz').status==200 else 1)"]
      interval: 30s
      timeout: 3s
      retries: 3
```

**Line by line:**

- `test:` takes the same probe as the Dockerfile's `HEALTHCHECK`, deliberately identical, so the
  two cannot drift into disagreeing about what healthy means.
- `["CMD", ...]` runs the command directly rather than through a shell, which is correct here
  because there is no variable to expand in the outer command — the `$PORT` lookup happens inside
  Python.
- `/readyz` rather than `/healthz`, which is part
  [4.1](../04-health-checks/4.1-alive-and-able-to-work.md)'s whole argument: this probe decides
  whether the container is considered usable, so it must ask whether the container can work.
- No `start_period` here, unlike the Dockerfile, and that is a gap worth noticing rather than a
  simplification — without it a slow first start counts as a failure.

And the item that is not a line of code, because it is the honest state of the day:

```bash
docker build -t sutra-api:local days/day-86-cloud-run-shaped/lab
```

**Line by line:**

- The exact command, so item 1 is a `TODO(me)` with an address rather than an intention. It builds
  from the lab folder, where the Dockerfile lives; a real build would run from the repository root
  so that `sutra/` is in the context, which is itself a thing the first real build will teach.

Measured on 2026-09-07 — which is to say, not measured:

```text
/usr/bin/bash: line 1: docker: command not found
```

## When it breaks

The list breaks by being read as a backlog rather than as a snag list, and the difference is that
two items on it are already costing something.

Item 6 is the clearest case. Written as a sequence:

```text
1. the ledger loses updates under concurrency, today, with one replica   (part 5.2)
2. the desk therefore under-counts what it has spent
3. it keeps calling the model, believing it has allowance left
4. the provider refuses: 429 RESOURCE_EXHAUSTED                          (day 78)
5. the refusal is retried, because a 429 looks transient                 (day 72)
6. the retries also fail, and also are not counted
```

Nothing in that sequence involves a container, a replica or a deployment. It is a defect in the
running system that the containerisation work happened to find, and putting it on a deployment
list is how it stays open.

The other way the list breaks is item 1 being deferred indefinitely because "the Dockerfile is
obviously fine". It has eight text properties verified and zero behaviours verified. The specific
things a first build would find, none of which any check here can:

```text
the base image tag does not resolve
uv sync --frozen fails because the lockfile does not match pyproject.toml
sutra.api does not exist yet, so the CMD has nothing to import
the uid 10001 cannot write to the mounted volume
```

The third of those is certain rather than possible — `sutra/api.py` is Day 85's build brief and
this repository's `sutra/` does not contain it. The image, if built today, would start and
immediately fail to import its entry point. That is worth writing down plainly rather than
leaving for somebody to discover.

## In production

**What a professional does.** Builds the image on the first day the Dockerfile exists, in CI, and
runs it once in the same job. Everything else on this list can wait; that one converts a document
into an artefact, and it is the difference between a deployment day and a debugging day.

**What degrades at scale.** The parked items get more expensive, in opposite directions. Item 5
gets cheaper the earlier it is done, because every feature built against an in-memory store is a
feature that has to be revisited. Item 9 gets more tempting under load, which is precisely when
doing it without items 5 and 6 does the most damage.

**The failure that only shows with real traffic.** Everything in this day ran on one machine with
twenty requests. A real deployment adds a load balancer that does not know about sessions, a node
that is replaced while requests are in flight, and a rolling update that runs the old and new
versions at the same time — which is two replicas by definition, briefly, even when the replica
count is one. That last one deserves emphasis: **a rolling update makes the replica count two for
a moment**, so part 5.2's session failure is reachable today, during any deployment, without
anybody scaling anything.

**The review comment a senior engineer leaves:** *"Item 6 is not a deployment task, it is a bug —
move it to the normal backlog and fix it this week. Item 1 goes in CI before Day 88. Items 5 and
9 stay linked: nobody raises the replica count until the session store moves, and put that in the
compose comment rather than in a document."*

**The interview question:** *"You have containerised a service. What is left before it can be
deployed?"* The answer that shows experience does not describe orchestration. It names the state
that lives in the process, says what happens to it during a rolling update, and only then talks
about images and probes — because the first is a design change and the rest are configuration.
