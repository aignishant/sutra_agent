# 5.1 — The statefulness audit

## One-line answer

A container is a process that will be replaced without notice, so the only useful question about
this system's state is which parts survive replacement — and the answer, measured by killing it
and starting it again, is one of two: the ledger file comes back and the session store does not.

## The story

The hotel room stripped between guests.

You check out at eleven. By two the room has been reset: bed remade, towels replaced, bin
emptied, the little bottles put back. The next person walks into a room that has no memory of
you.

Two things survive that reset. The safe, if you used it and the desk logs it. And whatever you
gave to reception to hold. Everything else — the charger in the drawer, the note by the phone,
the way you moved the chair — is gone, and the housekeeping trolley did not make a decision about
it. Resetting the room *is* the job.

Nobody who has stayed in a hotel is surprised by this. Everybody who has left a charger has been
surprised by it once.

## The idea in plain language

"Stateless" is one of those words that gets used as a compliment rather than a description, and
the useful version is narrower: **a stateless process is one that can be replaced by a fresh copy
of itself without anything being lost.**

That is not a claim about whether the process holds data. It holds plenty. It is a claim about
where the data that matters *lives*: a stateless process keeps nothing that only exists inside
it.

So the audit is one question asked of every piece of state the process touches:

- **does it survive the process being replaced?** — the restart column;
- **is it visible to a second copy running at the same time?** — the shared column, which part
  [5.2](5.2-two-replicas-one-failure.md) measures.

Neither question is answerable by reading the code carefully, because the interesting cases are
the ones nobody thought of as state. A cache is state. A counter is state. A dictionary of
sessions that "will be replaced by a real store later" is state, and it is the one that decides
the replica count.

The measurement is blunt and honest: give the process some state, kill it, start it again on the
same port with the same files, and ask what is still there.

## Why Sutra needs it

Because the compose file says `replicas: 1` and part
[3.3](../03-config-from-outside/3.3-compose-is-the-shape.md) called that a confession. This part
is where the confession is itemised, and the next one is where it is proved.

And because Day 88 puts this in a cluster, where containers are replaced routinely and without
anybody asking — a node is drained, a deployment rolls, a probe fails three times. In that
environment "survives a restart" stops being a hypothetical and becomes the ordinary case.

## The mechanism

The experiment is a restart with everything else held constant:

```python
    server = start(port, ledger)
    try:
        ...
        session = httpx.post(f"{base}/sessions", timeout=2.0).json()["session_id"]
        for _ in range(SPENDS):
            httpx.post(f"{base}/spend", timeout=5.0)
        before = json.loads(ledger.read_text(encoding="utf-8"))["spent"]
    finally:
        stop(server)

    server = start(port, ledger)
```

**Line by line:**

- The **same port and the same ledger path** on both starts. If either changed, a difference in
  the result would be attributable to the change rather than to the restart, and the experiment
  would prove nothing.
- Two kinds of state are created before the kill: a session, which lives in a dictionary in the
  process, and three units of spend, which are written to a file. Choosing one of each is the
  whole design — a run that only created sessions would conclude that nothing survives, and a run
  that only spent would conclude that everything does.
- `before` is read from the file rather than from the app, so the comparison after the restart is
  against the file's own record and not against a number the process remembered.
- `stop(server)` is in a `finally`, so a failure midway does not leave a server running on a port
  for the rest of the session. Part
  [5.2](5.2-two-replicas-one-failure.md) does the same for two of them.

`stop` is worth its own look, because terminating a subprocess is where labs leak processes:

```python
def stop(server: subprocess.Popen) -> None:
    server.terminate()
    try:
        server.wait(timeout=10)
    except subprocess.TimeoutExpired:
        server.kill()
```

**Line by line:**

- `terminate()` first, which asks politely and lets the server close its socket — otherwise the
  port can still be held when the second server tries to bind it.
- `wait(timeout=10)` because `terminate()` returns immediately and does not mean the process is
  gone. Starting the replacement before the old one has released the port produces a bind error
  that looks like a bug in the app.
- `kill()` only after the polite request has failed. Escalating, in that order, is the same shape
  as Day 65's argument about stopping a run: ask, then wait, then insist.

Run it:

```bash

```

**Line by line:**

- One arm only. There is no ablation here because the finding is the state of the system rather
  than a property of the check — the run is red today and the hub's build brief is what makes it
  green.

Measured on 2026-09-07:

```text
before the restart: pid 8972, session 6ec0cee8, ledger spent=3
after the restart:  pid 6300, ledger spent=3

  what it holds       where it lives            survives restart  shared?
  the session store   a dict in this process    NO                no
  the quota ledger    a file on a mounted path  yes               no

  session 6ec0cee8 after the restart: 404
  1 of 2 kinds of state did not survive: the session store
  the container contract is that the process is replaceable, and the only
  state that survives replacement is state kept somewhere else
exit: 1
```

Two pids, so the process really was replaced. `spent=3` on both sides, so the file survived. And
`404` for a session that existed a moment earlier — not an error, not a warning, just a
conversation that is no longer there.

The `shared?` column says `no` for both rows, and the second `no` is the one that is easy to
misread. The ledger is on a shared path, so it *is* visible to a second replica — what it is not
is safely shared, and part [5.2](5.2-two-replicas-one-failure.md) is why that distinction costs
something.

## When it breaks

The audit breaks by being done from memory, and the giveaway is that the list comes out short.
The categories that get missed are the same ones every time:

```text
in-memory caches           "it is only a cache" - until a cache miss changes behaviour
counters and rate limiters state, and the kind where two copies is worse than none
open connections           a pool warmed over minutes, cold on every replacement
temporary files            /tmp is per-container and is not a scratch space you can share
uploaded files             written to the local filesystem because that is the default
background work in flight  a task started and not finished when the process was replaced
```

The last one has no error text and is the most damaging. A request that was being handled when
the container was replaced simply stops. Nothing raises on the server, because the server is
gone; the client sees a connection reset and, if it is well written, retries — and Day 73's
idempotency argument is what decides whether that retry is safe or whether it refunds somebody
twice.

The failure this audit **cannot** see is state that survives a restart and is nonetheless wrong.
A ledger file that persists correctly across replacement, while two replicas both write to it, is
green in this table and broken in the next part. The restart column and the shared column are
different questions, and passing one says nothing about the other.

## In production

**What a professional does.** Writes the inventory down as a table in the deployment document,
with a row per writable path and a named owner for each — and treats an unlisted writable path as
a defect rather than a discovery. The valuable column is not "does it survive" but "what happens
if it does not", because that is what decides whether the fix is a volume, an external store, or
nothing at all.

**What degrades at scale.** The number of things that are quietly state. A small service has two;
a mature one has a dozen, most of them added by libraries rather than by the team — a client that
caches tokens, a metrics buffer, a retry queue. The audit stops being derivable from the code the
team wrote.

**The failure that only shows with real traffic.** The volume that is not there. Everything in
this table assumes the ledger's directory is mounted. In a cluster it is a volume claim that can
fail to bind, and the container starts anyway with an empty local directory in its place — so the
file is missing, readiness correctly says `quota_ledger_missing`, and the cause is three layers
away in a storage subsystem. Part [4.2](../04-health-checks/4.2-the-check-that-only-watched-the-process.md)
is exactly that scenario with the file deleted by hand.

**The review comment a senior engineer leaves:** *"Add the columns for `/tmp` and for the model
client's token cache before you call this list complete. And say what the loss of each one costs
— a dropped session is a re-login, a lost ledger is spending we cannot account for, and those two
need different fixes."*

**The interview question:** *"Is your service stateless?"* The answer that shows experience never
says yes. It lists what the process holds, says which of it survives replacement, and names the
one thing that does not — because a person who answers "yes" has not looked.
