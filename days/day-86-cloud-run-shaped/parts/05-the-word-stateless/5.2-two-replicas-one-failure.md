# 5.2 — Two replicas, and only one failure is about replication

## One-line answer

💥 Scale to two and two things break — a session created on one replica returns `404` on the
other, and twenty units of spend leave a shared ledger recording **six** — but only the first is
caused by the second replica, and finding that out is what the ablation is for.

## The story

💥 **Two shopkeepers, one stock register.**

🎬 **The scene.** A busy morning, so the owner puts a second person on the counter. One register
book, kept under the counter, where each sale is written down and the running total updated.

😬 **The naive fix.** Both of them use the same book — it is right there, they can both reach it,
and the total is in one place. What could be simpler than sharing the one authoritative record?

💥 **Why it fails.** Two things go wrong and they are not the same kind of thing.

The first: a customer asks the second shopkeeper about the order they placed with the first an
hour ago. He has no idea. It was never written down anywhere — it was in the first man's head,
because for one person a head is a perfectly good place to keep an hour of context.

The second: both of them read the total, both add their sale to what they read, both write the
new total. Two sales, one increment. The book is not wrong about arithmetic; it is wrong because
reading, adding and writing are three moments and somebody else moved in between.

💡 **The insight.** Only the first problem is caused by the second shopkeeper. The second one —
read, add, write — was already unsafe with one person serving two customers at once, and hiring
the second man did not create it. **It removed the fix**: one person can hold the book while they
write. Two cannot.

## The idea in plain language

`replicas: 1` in the compose file is a number somebody will eventually raise, because raising it
is the obvious response to load and because the flag is right there. This part runs the
experiment first.

Two processes, on two ports, sharing one ledger file. That is what a second replica is: the
isolation between two containers on one host is a process boundary and a mount, which is exactly
what the lab can create without a container runtime.

Two failures come out, and the important discovery is that they are not the same species:

| What breaks | Caused by the second replica? | What the fix is |
| --- | --- | --- |
| a session is invisible to the other replica | **yes** — one replica cannot fail this way | move the store out of the process |
| the shared ledger loses updates | **no** — already true with one | serialise writes somewhere both can see |

The second row is the one worth the day. Read-modify-write on a shared file is a race whenever
anything else is writing, and a single web server serving synchronous handlers from a thread pool
already has that. So the lost updates are not a replication bug — they are a concurrency bug that
replication makes **unfixable in the obvious way**, because the obvious way is a lock inside the
process and there is now more than one process.

Distinguishing those two costs one flag and changes what you build. Mixing them up produces a
team that adds a mutex, sees the single-replica numbers improve, and ships.

## Why Sutra needs it

Because Day 88 runs this in a cluster, where the replica count is a field in a manifest and
scaling is the first thing anybody tries. The number in the compose file is only as good as the
reason written beside it, and this part is that reason, measured.

And because the session store is not a placeholder that will obviously be replaced. It is the
default: ADK's in-memory session service keeps conversations in a dictionary in the process, which
is correct for a laptop and is exactly the shape measured here.

## The mechanism

The two replicas are ordinary subprocesses, differing only in port:

```python
def start(port: int, ledger: Path) -> subprocess.Popen:
    """One replica: its own process, its own memory, the same ledger file."""
    env = {
        **os.environ,
        "SUTRA_API_KEY": "not-a-real-key",
        "PORT": str(port),
        "SUTRA_QUOTA_LEDGER": str(ledger),
        "SUTRA_RMW_DELAY": "0.02",
    }
```

**Line by line:**

- The same `ledger` path is handed to both, which is the shared volume from
  [`compose.yaml`](../03-config-from-outside/3.3-compose-is-the-shape.md) reduced to its essential
  feature: one file, two writers.
- Different `PORT` per replica, because two processes cannot bind one port. In a cluster each
  replica gets its own network namespace and they can share a port number; here they cannot, and
  that is a difference between the model and the thing worth knowing about.
- `SUTRA_RMW_DELAY` inserts a pause between the read and the write in the spend handler. It
  **widens a window that exists without it** — the race is present at zero delay and shows up
  occasionally; the delay makes it reproducible. A demonstration that only fires sometimes teaches
  nothing, and pretending the delay creates the bug would be worse.

The spend handler is the shared-state half, and it is three ordinary statements:

```python
    ledger = json.loads(LEDGER.read_text(encoding="utf-8"))
    ledger["spent"] += 1
    time.sleep(float(os.environ.get("SUTRA_RMW_DELAY", "0")))
    LEDGER.write_text(json.dumps(ledger), encoding="utf-8")
```

**Line by line:**

- Read, modify, write — three separate operations on a file with no lock between them. There is
  nothing clever or wrong-looking here; this is how a counter in a file is written by everybody
  the first time.
- The whole file is rewritten, so a writer that started from a stale read overwrites everything
  that happened since. That is why the loss is total rather than partial: the last writer wins and
  takes everything with it.
- `os.environ.get(..., "0")` so the delay defaults to nothing. Outside this experiment the handler
  is the code somebody would actually write.

And the traffic is genuinely concurrent, split across whatever replicas exist:

```python
        with ThreadPoolExecutor(max_workers=len(bases) * 4) as pool:
            list(
                pool.map(
                    lambda i: httpx.post(f"{bases[i % len(bases)]}/spend", timeout=10.0),
                    range(SPENDS),
                )
            )
```

**Line by line:**

- `i % len(bases)` round-robins requests across replicas, so with two replicas each gets half.
  With one, all twenty go to the same process — which is the ablation, and the reason it still
  loses updates.
- `max_workers` scales with the replica count so the concurrency per replica is constant. Holding
  that fixed is what makes the two arms comparable.
- `list(pool.map(...))` forces the iterator, because `map` is lazy and a run that never consumed
  it would send nothing and report a perfect ledger.

Run it:

```bash

```

**Line by line:**

- No flag: two replicas, twenty spends, one ledger.

Measured on 2026-09-07:

```text
replicas: 2   shared ledger: sutra-shared-14504.json
  http://127.0.0.1:56203  pid 14228
  http://127.0.0.1:56204  pid 18056

--- state that lives in a process ---
  created session 47ab99e0 on replica 1 (pid 14228)
  replica 1 asked for it: 200 {'session_id': '47ab99e0', 'pid': 14228}
  replica 2 asked for it: 404 {'error': 'no_such_session', 'pid': 18056}

--- state that lives in a shared file ---
  requests that each took one unit: 20
  units the ledger ended up recording: 6

```

**A `200` and a `404` for the same session id, one line apart.** And twenty spends recorded as
six. The exact count moves between runs — it is a race, so it lands somewhere in the region of
five or six — and the direction never does.

The second number is the one with teeth. Day 78 established that the free tier is a daily
allowance and that the ledger is how the desk knows what it has left. A ledger that records six of
twenty means the desk believes it has spent six. It will keep spending until the provider refuses,
and Day 78's recorded refusal is what arrives:

```text
429 RESOURCE_EXHAUSTED
generativelanguage.googleapis.com/generate_content_free_tier_requests
```

## When it breaks

Now remove the second replica and change nothing else:

```bash
uv run python replicas.py --single; echo "exit: $?"
```

Measured on 2026-09-07:

```text
replicas: 1   shared ledger: sutra-shared-3380.json
  http://127.0.0.1:56244  pid 8912

--- state that lives in a process ---
  created session 5604b1f7 on replica 1 (pid 8912)
  replica 1 asked for it: 200 {'session_id': '5604b1f7', 'pid': 8912}

--- state that lives in a shared file ---
  requests that each took one unit: 20
  units the ledger ended up recording: 5
  updates lost: 15

  one replica: its own memory is the only memory, so nothing was invisible
  and the ledger is still short anyway -
  the file race needs concurrency, not a second replica, and one process
  serving sync handlers from a thread pool already has it

  so only one of the two failures is about replication, and this arm
  is how you find out which
exit: 1
```

**The session failure disappears and the lost updates do not.** Fifteen of twenty, with one
process.

That is the finding, and it is worth stating carefully because it inverts the obvious reading of
the first run. Scaling to two replicas did not cause the ledger corruption. The corruption was
already there, in the single-replica system that has been running through this entire phase, and
the second replica's contribution is to remove the cheap fix — a lock inside the process
serialises threads and does nothing about another process.

So the two failures need two different answers:

| Failure | Fix that works | Fix that looks like it works |
| --- | --- | --- |
| session invisible across replicas | a session store outside the process | sticky sessions, until a replica is replaced |
| lost updates on the ledger | atomic write, or a store with transactions | a mutex, which passes the single-replica test |

The second column of the second row is the trap this part exists to prevent. A team that finds the
lost updates with one replica, adds a `threading.Lock`, and watches the number go to twenty of
twenty has a green test and a bug that returns the day somebody scales.

## In production

**What a professional does.** Decides where each piece of state lives *before* raising a replica
count, and treats the count as a property of the design rather than a knob. For the two here that
means a session store both replicas read — Day 47's persistent sessions — and a spending record
with an atomic increment, which in practice means a database with a transaction rather than a
JSON file with a lock.

**What degrades at scale.** The window. At two replicas and twenty requests the loss is
observable; at ten replicas and real traffic it is continuous, and the ledger converges on
recording roughly one write per interval rather than one per request. The system does not fail —
it under-counts, steadily, which is the worst behaviour for a budget.

**The failure that only shows with real traffic.** The read that is stale rather than lost. This
lab measures writes clobbering each other, which is visible in a final total. The other half is a
replica reading a value another replica has already superseded and *acting* on it — approving a
refund whose approval was already consumed, or deciding there is quota left when there is not.
Nothing in the final state records that it happened.

**The review comment a senior engineer leaves:** *"Do not put a lock in the handler. It will make
the single-replica number correct and hide this until the day we scale. The ledger needs an atomic
increment somewhere both processes can see, and until it has one the replica count stays at one —
with the comment."*

**The interview question:** *"Your service loses counter updates under load. What do you check
first?"* The answer that shows experience asks whether it reproduces with one instance, because
that single question splits the problem into two entirely different fixes — and most people
assume it is a distributed-systems problem before they have checked.
