# 2.2 — The interpreter who relays the last sentence

## One-line answer

Only the agent's **final** response crosses the wire, converted block by block — text becomes text,
inline images and audio become image and audio blocks, and anything the converter has no shape for,
including every tool call the agent made, is silently dropped.

## The story

You are in a consultation and there is an interpreter in the room, because you and the doctor do not
share a language.

The doctor reads your file. She says something to herself, half under her breath, and turns a page.
She asks a nurse a short question and gets a short answer. She writes something. Then she looks up
and says four sentences to you, and the interpreter turns those four sentences into your language.

You get the four sentences. You do not get the muttering, and you would not have understood it
anyway. You do not get the question she asked the nurse. When she holds up the scan and points at a
shadow on it, you see the scan, because a scan does not need translating.

If you had asked at the start — *"please tell me everything she says, not just the conclusions"* —
the interpreter would have done it, and you would have heard the muttering too, in real time, without
the file ever having been read out to you. But you did not ask, so you got the four sentences, and
you left the room thinking the doctor had barely looked at anything.

## The idea in plain language

Running an ADK agent produces a stream of **events**. Every model turn, every tool call, every tool
result and every fragment of streamed text is an event, and the `Runner` yields them one at a time.
That stream is what `adk web` draws when it shows you the agent's working.

`to_mcp_server` reduces that stream to a single reply, and it does so with one rule. An event where
`event.is_final_response()` is true has its parts converted and collected; every other event with
text is sent as a **progress notification** if the caller asked for progress, and thrown away if it
did not.

**A progress notification** is the MCP mechanism Day 36's
[2.1](../../../day-36-long-jobs-and-tasks/parts/02-progress/2.1-the-token-you-have-to-ask-for.md)
taught: a message a server can send while a call is still in flight, but *only* if the caller put a
`progressToken` in the request. No token, no notifications, and the server has no way to insist. That
is the interpreter who relays everything only if you asked at the start.

The conversion of the final response is a small function with three branches and one default:

| The ADK part holds | The caller receives |
| --- | --- |
| `text` | a `TextContent` block |
| `inline_data` with a MIME type starting `image/` | an `ImageContent` block, base64-encoded |
| `inline_data` with a MIME type starting `audio/` | an `AudioContent` block, base64-encoded |
| `inline_data` with any other MIME type | an `EmbeddedResource` block wrapping a blob |
| **anything else** — including a `function_call` or a `function_response` | **nothing. The part is dropped.** |

The last row is the one to remember.

## Why Sutra needs it

Because Sutra's desk agent does its most important work in the parts that get dropped.

The desk answers by calling `lookup_ticket`, reading the result, calling `search_kb`, reading that,
and only then writing an answer. Those two calls and their results are `function_call` and
`function_response` parts, and every one of them is `None` after conversion. The caller receives the
answer and no evidence.

That matters twice. It matters for **trust**: Day 39's database tools and Day 40's allowlists exist
so that a reviewer can see which tool touched what, and the served door removes exactly that
visibility from the caller's side. And it matters for **debugging**: when a caller says *"your desk
gave me the wrong article"*, the reply they hold contains nothing that tells either of you which
article it looked at.

Day 22's [correlation id](../../../day-22-structured-logging/parts/02-wiring-the-run/2.2-the-correlation-id.md)
is the answer, and this is the part that makes it mandatory rather than nice. If the caller cannot
see the working, the working has to be in your logs under an identifier the caller also holds.

## The mechanism

Here is the converter, from `.venv/Lib/site-packages/google/adk/tools/mcp_tool/_agent_to_mcp.py`,
read on 2026-09-05:

```python
def _part_to_content(part: types.Part) -> Optional[mcp_types.ContentBlock]:
    if part.text:
        return mcp_types.TextContent(type="text", text=part.text)
    blob = part.inline_data
    if blob is not None and blob.data is not None:
        data = base64.b64encode(blob.data).decode("ascii")
        mime = blob.mime_type or "application/octet-stream"
        if mime.startswith("image/"):
            return mcp_types.ImageContent(type="image", data=data, mimeType=mime)
        if mime.startswith("audio/"):
            return mcp_types.AudioContent(type="audio", data=data, mimeType=mime)
        return mcp_types.EmbeddedResource(
            type="resource",
            resource=mcp_types.BlobResourceContents(
                uri=_INLINE_RESOURCE_URI, blob=data, mimeType=mime
            ),
        )
    return None
```

**Line by line:**

- `if part.text:` is a **truthiness** test, not `is not None`. An empty-string text part is falsy and
  falls through to the blob branch and then to `return None`. That is almost always what you want and
  it is worth noticing, because a model that emits an empty text part contributes nothing to the
  reply rather than an empty block.
- `base64.b64encode(blob.data).decode("ascii")` is why an image in a reply is roughly a third larger
  than the file. MCP content blocks are JSON, JSON has no bytes, so every image and every audio clip
  crosses the wire base64-encoded and inline. There is no streaming and no separate fetch.
- `mime or "application/octet-stream"` is the fallback for a blob with no declared type. It sends
  the bytes as an opaque resource, which is the honest thing to do and also means the caller has no
  idea what they received.
- `_INLINE_RESOURCE_URI` is the module constant `"resource://adk-agent/inline-data"` — the **same
  URI for every blob**. Two attachments in one reply come back as two embedded resources with
  identical URIs. A caller keying anything by resource URI collapses them.
- `return None` at the end is the drop. It is reached by every `function_call` part, every
  `function_response` part, every thought part and every part carrying only metadata. Nothing is
  logged, nothing warns, and the caller has no way to know a part existed.

And the loop that decides what is final and what is narration:

```python
async for event in runner.run_async(
    user_id=_MCP_USER_ID, session_id=session_id, new_message=new_message
):
    if not (event.content and event.content.parts):
        continue
    if event.is_final_response():
        for part in event.content.parts:
            block = _part_to_content(part)
            if block is not None:
                final_content.append(block)
    elif ctx is not None:
        text = "".join(part.text or "" for part in event.content.parts)
        if text:
            await ctx.report_progress(progress=0.0, message=text)
```

**Line by line:**

- `if not (event.content and event.content.parts): continue` skips events with no content at all —
  state deltas, control events. They never reach the caller in any form.
- `event.is_final_response()` is ADK's own predicate for "this is the answer". If your agent yields
  two final responses, both are converted and **both sets of blocks are appended to one reply**, so
  the caller gets a concatenation rather than two messages.
- `await ctx.report_progress(progress=0.0, message=text)` sends the narration. `progress=0.0` on
  every single notification, with no `total`, which means a host drawing a progress bar from these
  gets a bar that never moves. Day 36's
  [2.3](../../../day-36-long-jobs-and-tasks/parts/02-progress/2.3-progress-is-narration-not-state.md)
  argued that progress is narration and not state; here the framework has made that decision for you.
- `elif ctx is not None` is the whole conditional half. Without a context there is no progress, and
  the SDK's `report_progress` is itself a no-op when the caller sent no `progressToken`, so there are
  **two** independent reasons the narration can vanish.
- Note the asymmetry: a non-final event's *text* is narrated, and a non-final event's *image* is not.
  A picture produced mid-run and not repeated in the final answer is simply gone.

## When it breaks

Run `lab/blocks.py`. It serves an agent that yields three events in one run — a partial thought, a
tool call, and a final answer carrying text and an eight-byte PNG — and prints what arrives:

```text
arm: listening for progress
  progress notification: 'reading the archive'
isError : False
blocks  : 2
  TextContent: 'KB-104 explains it.'
  ImageContent: 'image/png'
```

Three events went in. Two blocks came out. **The tool call is not in the list, and there is no
notification about it either**, because its part carries a `function_call` and no text, so it fails
both branches.

Now the ablation. Same agent, same three events, one thing changed on the caller's side:

```text
arm: --deaf (no progress callback)
isError : False
blocks  : 2
  TextContent: 'KB-104 explains it.'
  ImageContent: 'image/png'
```

Identical. The `reading the archive` line is gone and nothing marks its absence. Every client that
does not opt into progress — which is most of them, because a `progressToken` is something a client
has to deliberately send — sees the second output and has no reason to suspect the first exists.

💡 **The insight:** **the reply is a conclusion, not a transcript.** Everything a served agent does
between receiving a string and producing an answer is invisible to the caller by default, and the
half of it that is not invisible is opt-in on the caller's side and silently dropped when they do not
opt in. If you want the working to be recoverable, it has to be recoverable from *your* logs, keyed
by something the caller also holds.

## In production

**What a professional writes instead:** a correlation identifier, minted per call, logged on the
server with every tool call and every model turn, and **returned to the caller in the final text**.
One line at the end of the answer — a short reference the caller can quote back — turns an
un-debuggable service into one where a support conversation takes a minute. Day 22's
[2.2](../../../day-22-structured-logging/parts/02-wiring-the-run/2.2-the-correlation-id.md) already
gives you the logging half; this is the half that makes it reachable from outside.

**What degrades at scale:** the base64 payload. An agent that occasionally returns a screenshot is
returning it inline, in JSON, base64-encoded, through whatever proxies sit between you and the
caller. Every one of those has a body size limit, and the failure when you exceed it is at the
transport layer, where your error message is not.

**The failure mode that only appears with real traffic:** silent partial answers. An agent whose
final event carries a text part *and* a data part with an unrecognised MIME type sends the text and
drops the data, with `isError: false`. The caller receives a coherent-looking answer that is missing
its attachment, and nothing anywhere records that a part was dropped.

**The review comment a senior engineer leaves:** *"the caller gets the conclusion and nothing else —
no tool calls, no intermediate reasoning, and the progress narration only if they happened to send a
progress token. That is fine as a design, but then our logs are the only record of what the agent
actually did, so put a correlation id in the response text and make every tool call log it. Right
now, if a caller disputes an answer, neither of us can reconstruct it."*

**The interview question:** *"a caller says your served agent gave a wrong answer. How do you find
out what happened?"* The honest answer: *"Not from the reply, because the reply is only the final
response — every tool call and tool result is dropped by the converter, and the intermediate text is
sent as progress notifications that most clients never ask for. So the reply is a conclusion with no
evidence attached. What I do is mint a correlation id per call, log every model turn and tool call
against it, and put the id in the answer text so the caller can quote it back. It costs one line of
output and it is the difference between a five-minute support conversation and a guess."*
