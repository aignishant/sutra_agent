# 2.1 — The enquiry slip with one box

## One-line answer

The declaration a served agent publishes has exactly one property, `request`, typed `string`, with
no output schema and no structure of any kind — so every constraint you want the caller to respect
has to be written in prose or not at all.

## The story

Every other slip in that office has boxes. Name, father's name, address, ward number, date, the
serial number of the last receipt. Thirty boxes and a man behind the counter who will send you away
if box eleven is blank, which is annoying, and which also means that when the form comes back it is
right.

The enquiry slip is one box. It says *Write your requirement here* and it is four lines long.

The first time you use it you write two words and get sent away. The second time you write half a
page and get an answer to a question you did not ask. Eventually you learn what to write — the
system, the date, what you already tried, what you want to happen — and after that the enquiry slip
works better than any of the thirty-box forms, because it does not force your problem into somebody
else's categories.

But nobody taught you that. There is no note on the slip saying what to write. The man behind the
counter cannot send it back for a missing box, because there are no boxes. He just answers whatever
you wrote, as best he can, and if you wrote badly you get a bad answer and no warning that you did.

## The idea in plain language

A **JSON Schema** is the machine-readable description of what arguments a tool takes. Day 34's
[2.1](../../../day-34-building-sutra-mcp-tools/parts/02-function-to-declaration/2.1-the-decorator-that-writes-your-schema.md)
showed the SDK deriving one from a Python function: parameter names become properties, type hints
become types, and required arguments become a `required` list. A client reads that schema before it
calls anything, and a well-built client will refuse to send a call that does not match it.

A **served agent has no schema worth the name.** The function being registered is `call_agent(request:
str, ctx)`, the SDK strips `ctx` out as an injected context parameter, and what is left is one
string. So the declaration is the same for every agent anybody ever serves: one property called
`request`, of type `string`, required.

That has one very large consequence. **Schema validation cannot help you.** Day 34's
[2.3](../../../day-34-building-sutra-mcp-tools/parts/02-function-to-declaration/2.3-the-argument-that-changed-on-the-way-in.md)
found that `'04521'` sent to an `int` parameter arrives as `4521`, which is a bug the schema at least
*names*. Here there is nothing to coerce and nothing to reject. Any string at all is a valid call.
The only defence between a caller's request and your model loop is the agent's own instruction.

## Why Sutra needs it

Because Day 45's audit reads every tool declaration Sutra publishes and asks one question: *could a
competent stranger use this correctly from the declaration alone?*

For `lookup_ticket` the answer is checkable. It has a parameter called `ticket_id`, typed `str`, and
Day 34's build brief made you write a description saying what a ticket id looks like. For the served
agent the answer depends entirely on one paragraph of prose, and that paragraph is `agent.description`
— which you wrote on [Day 5](../../../day-05-first-adk-agent/parts/02-the-agent-object/2.2-name-and-description.md)
for a completely different audience. On Day 5 the `description` field existed so that a *parent
agent* inside your own process could route to a sub-agent. Today it is the public interface of a
network service.

Those are not the same job, and the sentence that does the first one well usually does the second one
badly.

## The mechanism

Build a server and ask it what it offers. This is `lab/served_surface.py`, and it costs nothing
because listing tools never runs the agent:

```python
kb_answerer = LlmAgent(
    name="sutra_kb_answerer",
    model="gemini-3.7-flash",
    description=(
        "Answers one self-contained question from the internal knowledge base and "
        "cites the article id. Keeps no memory between calls."
    ),
    instruction="Answer only from search_kb. Cite the article id. Never invent an article.",
    tools=[search_kb],
)


async def main() -> None:
    server = to_mcp_server(kb_answerer)
    for tool in await server.list_tools():
        print(
            json.dumps(
                {
                    "name": tool.name,
                    "description": tool.description,
                    "inputSchema": tool.inputSchema,
                    "outputSchema": tool.outputSchema,
                },
                indent=2,
            )
        )
```

**Line by line:**

- `LlmAgent(...)` with a `model` string is constructed but never run, so no key is needed and no
  generation is spent. The script sets `GOOGLE_API_KEY` to a placeholder for exactly this reason:
  ADK wants the variable to exist at construction time and never uses it here.
- `description=` is written as two sentences because it has two jobs. The first says what kind of
  question fits. The second states an operational fact — *"Keeps no memory between calls"* — that
  the caller has no other way to discover, since [1.3](../01-the-back-office/1.3-the-hall-that-came-with-its-own-chairs.md)
  showed sessions living in a dictionary the caller cannot see.
- `instruction=` is the agent's private handbook and **does not cross the wire**. Nothing in the
  declaration reflects it. A caller cannot tell that this agent refuses to answer from anything but
  `search_kb`, which is a constraint they would very much like to know about.
- `tools=[search_kb]` likewise stays inside. The caller sees no trace of it —
  [2.4](2.4-the-errand-you-sent-someone-on.md) is what that hides.
- `await server.list_tools()` is the same call a client makes as `tools/list`, reached directly
  rather than over a transport. Building the server and listing its tools runs no agent code at all.
- `tool.outputSchema` is printed on purpose, because it is `null`, and that absence is a fact worth
  looking at rather than a field worth skipping.

Run it and this is what a caller receives, measured on 2026-09-05:

```text
server object : mcp.server.fastmcp.server.FastMCP
server name   : sutra_kb_answerer
instructions  : None
--- what a caller gets back from tools/list ---
{
  "name": "sutra_kb_answerer",
  "description": "Answers one self-contained question from the internal knowledge base and cites the article id. Keeps no memory between calls.",
  "inputSchema": {
    "properties": {
      "request": {
        "title": "Request",
        "type": "string"
      }
    },
    "required": [
      "request"
    ],
    "title": "call_agentArguments",
    "type": "object"
  },
  "outputSchema": null
}
```

Four things in that output are worth stopping on.

**`"title": "call_agentArguments"`** is the SDK's generated name for the argument object, and it
leaks ADK's internal function name, `call_agent`, onto the wire. It is harmless and it is also
completely uninformative to a caller who wondered what this thing is called.

**`"required": ["request"]`** is the only enforcement that exists. A call with no `request` is
rejected. A call with a `request` of `""` is not.

**`outputSchema: null`** is `structured_output=False` from
[1.2](../01-the-back-office/1.2-twelve-words-in-the-classifieds.md) showing up on the wire. Day 34's
[3.3](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.3-one-call-one-result.md)
described a client that validates results against `outputSchema`; there is nothing here to validate
against, so the reply is whatever content blocks come back.

**`instructions: None`** is the server-level field, distinct from the tool description, and it is
empty because `to_mcp_server` was called without `instructions=`. That is a second place you could
put prose, and a host may or may not show it.

## When it breaks

The break is the empty string, and it is not theoretical — it is what happens the first time a
caller's model produces a tool call with a blank argument.

The declaration says `request` is required and typed `string`. `""` satisfies both. So the call is
valid, it reaches your server, your server starts a `Runner`, the `Runner` sends an empty user turn
to Gemini, and **a generation is spent** producing a model's best guess at what somebody meant by
nothing. On a twenty-a-day ceiling that is five per cent of your daily budget spent on an empty box.

There is no schema field that stops this. JSON Schema has `minLength`, and the SDK derives the
schema from a Python type hint, and `str` has no minimum length. You cannot annotate your way out of
it, because you do not own the function being registered.

The fix is in the only place you own:

```text
Error executing tool sutra_desk: request must be a question, not an empty string
```

That is what a caller sees when the guard is in the agent, and Day 34's
[4.1](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.1-the-tool-said-no.md)
explains why it comes back as `isError: true` on a successful call rather than as a JSON-RPC error.
Writing that guard is one of the day's `TODO(me)` items, and the reason it is a `TODO` rather than a
gift is that where you put it is a real decision: a `before_agent_callback`, a wrapping `BaseAgent`,
or a check in the instruction that costs a generation to enforce.

## In production

**What a professional writes instead:** a `description` written as a contract, in a specific order —
what the agent answers, one example question that fits, one that does not, and the two operational
facts (this call runs a model; do not retry it blindly). Then a cheap, deterministic guard in front
of the model for the cases the schema cannot express: empty, absurdly long, and obviously not a
question. Every one of those rejections is a generation not spent.

**What degrades at scale:** the prose. A description is read by a model on every single turn of
every caller's loop, so it is on the hot path of somebody else's token budget as well as being your
interface. Day 28's
[2.4](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.4-the-crowded-shelf.md)
measured what happens when a shelf of descriptions gets crowded: routing accuracy falls, and the
tool with the vaguest, broadest description wins. A served agent's description is structurally the
broadest one on any shelf it lands on.

**The failure mode that only appears with real traffic:** callers discovering they can put anything
in the box. One string with no schema is an invitation to send *everything* — the whole ticket, the
whole conversation, a pasted log file — because there is no field saying not to. Your token bill and
your latency both follow the largest thing anyone ever tried, and you find out from the bill.

**The review comment a senior engineer leaves:** *"the input schema is one required string and there
is no length bound anywhere between the caller and the model. An empty request spends a generation.
A hundred-kilobyte request spends a lot more than one. Put a deterministic check in front of the
`Runner` and make the description say what a good request looks like — right now the only
documentation of our public API is a sentence written on Day 5 for a router inside our own process."*

**The interview question:** *"how do you validate input to an agent exposed as a tool?"* The honest
answer: *"You mostly cannot, at the schema layer. The declaration is one required string, because
that is the signature of the function the framework registers, and I do not own that function. JSON
Schema could express a minimum length, but nothing derives one from `str`. So validation moves into
my code: a deterministic guard before the runner for empty, oversized and obviously-not-a-question
input, which is cheap and rejects before a generation is spent, and then the agent's own instruction
for anything that needs judgement. The part people miss is that the description is doing the work
the schema normally does, so it gets reviewed like an API signature, not like a comment."*
