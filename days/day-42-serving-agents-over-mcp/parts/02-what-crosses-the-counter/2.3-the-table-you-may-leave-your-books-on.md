# 2.3 — The table you may leave your books on

## One-line answer

A served agent keeps **one conversation per MCP connection** — successive calls on one connection see
each other, a second connection starts from nothing, and every one of them runs as the same user —
which is a memory model the protocol has no field to describe.

## The story

The reading room has a rule you learn on your second visit. You may leave your books on the table
while you go down for tea, and they will be there when you come back. Nobody moves them. There is an
understanding.

The moment you walk out of the building, the understanding ends. Somebody clears the table, the books
go back on the trolley, and if you return in the evening you start again from the catalogue.

There is a second thing about that reading room and it takes longer to notice. The cards you fill in
at the desk all say the same thing in the name field: *Reader*. Not your name — the room does not
issue cards to people, it issues them to seats. So the desk can tell that somebody has requested four
books today. It cannot tell whether that was you four times or four different people once each, and
on the day two readers ask for the same restricted volume, there is no way to decide who has the
prior claim.

## The idea in plain language

A **connection** is the open channel between one client and one server: a stdio pipe to a subprocess,
or an HTTP session. It begins when the client connects and ends when it disconnects. Several
`tools/call` requests can travel down one connection.

An **ADK session** is a conversation: the list of events the agent has produced and received, so that
turn two can see turn one. It is what `session_service` stores.

`to_mcp_server` maps one to the other. The first `tools/call` on a connection creates an ADK session
and remembers it, keyed by the connection. Every later call on that same connection reuses it. A
different connection gets a different session.

Day 32's
[2.1](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.1-the-call-that-remembered-you.md)
is the reason to be uneasy about that. The 2026-07-28 revision of MCP moved deliberately away from
the held session: a request carries what it needs, any instance can answer it, and the server does
not remember you between calls. This function does the opposite — quietly, usefully, and with no way
to declare it.

## Why Sutra needs it

Because it is exactly the pattern Day 43 spends a whole day undoing, and Day 43 starts from this
file.

Day 43's subject is a deploy-shaped server: any instance answers any request. A server whose
correctness depends on the caller staying on the same connection cannot be run twice. `build_server()`
is already `stateless_http=True` because Day 34 made it so. `build_agent_server()` is not, and cannot
be, because the memory is inside the object rather than in the payload.

The second reason is Day 37's badge. Day 37 taught how a caller proves who it is, and
[1.3](../01-the-back-office/1.3-the-hall-that-came-with-its-own-chairs.md) showed the identity being
thrown away at the door. This part is where you see what that costs: two callers on two connections
are distinguishable to the *transport* and identical to the *agent*. Any rule the agent's instruction
tries to enforce about "the person who asked" is unenforceable.

## The mechanism

The whole memory model is four lines, from
`.venv/Lib/site-packages/google/adk/tools/mcp_tool/_agent_to_mcp.py`, read on 2026-09-05:

```python
sessions: MutableMapping[object, str] = weakref.WeakKeyDictionary()

# inside _run_agent:
session_id = sessions.get(ctx.session)
if session_id is None:
    session = await runner.session_service.create_session(
        app_name=runner.app_name, user_id=_MCP_USER_ID
    )
    session_id = session.id
    sessions[ctx.session] = session_id
```

**Line by line:**

- `sessions` is a dictionary living in the closure `to_mcp_server` builds. It is **per server
  object**, so two servers built from the same agent have two independent maps, and a server rebuilt
  after a restart has an empty one.
- `weakref.WeakKeyDictionary()` means the map does not keep a connection alive. When the MCP session
  object is garbage-collected, its entry disappears. This is a genuine leak fix for the *map* — and
  note what it does not fix: the ADK session itself is still in `session_service`, holding every
  event of that conversation, with nothing evicting it.
- `ctx.session` is the **key**, and it is the MCP `ServerSession` object — one per connection. Not a
  user, not a token, not a request. Reconnect and you are a different key, even from the same
  process, the same second, the same credentials.
- `sessions.get(...)` returning `None` is the "first call on this connection" branch. There is no
  lock around the get-then-create, so two concurrent first calls on one connection can both see
  `None`; the second write wins and one ADK session is orphaned with a turn in it.
- `user_id=_MCP_USER_ID` is the fixed identity from
  [1.3](../01-the-back-office/1.3-the-hall-that-came-with-its-own-chairs.md), and this is the line
  that reads it. Passing your own `Runner` does not change it, because this line is in `_run_agent`,
  not in `_build_runner`.

Drawn out, the lifetime looks like this:

```mermaid
sequenceDiagram
    participant C1 as Client, connection 1
    participant S as Served agent
    participant SS as InMemorySessionService
    C1->>S: tools/call "who am I (1)"
    S->>SS: create_session(app, mcp_user)
    SS-->>S: session 8c3283a4
    S-->>C1: turns=1
    C1->>S: tools/call "who am I (2)"
    Note over S: sessions[ctx.session] hit
    S-->>C1: session 8c3283a4, turns=2
    C1--xS: disconnect
    Note over S,SS: the map entry goes; the session's events stay
```

## When it breaks

`lab/connections.py` serves a five-line agent that reports its own bookkeeping instead of answering.
Two calls on one connection, then two on a second:

```text
connection 1 call 1: session=8c3283a4 app=sutra_desk user=mcp_user turns=1
connection 1 call 2: session=8c3283a4 app=sutra_desk user=mcp_user turns=2
connection 2 call 1: session=38e14613 app=sutra_desk user=mcp_user turns=1
connection 2 call 2: session=38e14613 app=sutra_desk user=mcp_user turns=2
```

Read it twice. The first read is the good news: `turns` climbs on one connection, so a caller *can*
have a conversation. The second read is the bad news, and it is in the last two lines. Connection 2
is a different session with `turns` back at 1 — and the caller did nothing wrong. They reconnected,
which is a thing every client does after an idle timeout, a network blip, or a host restarting a
stdio subprocess.

🎬 **The scene:** a caller's agent is walking your desk through a complicated ticket. Turn four
establishes that the customer is on version 2.3.

😬 **The naive fix:** the caller's host, which pools connections, drops an idle one and opens a fresh
one for turn five.

💥 **Why it fails:** turn five arrives in a brand-new ADK session that has never heard of version
2.3. Your agent answers with a generic article. Nothing errored. The caller's model has the whole
conversation in *its* context, so it reads your answer as your desk being unhelpful rather than as
your desk having amnesia, and it rephrases and asks again — spending another generation of yours.

💡 **The insight:** **the caller cannot see the boundary of your memory, and the protocol has no
field to tell them.** There is no `sessionScope` in a tool declaration. The only place this fact can
live is the tool description, in prose, which is why the sample agent in
[2.1](2.1-the-enquiry-slip-with-one-box.md) says *"Keeps no memory between calls"* — that is a
deliberate lie in the safe direction, and it is a much better interface than the truth, because a
caller who assumes nothing survives is never surprised.

## In production

**What a professional writes instead:** they pick one of two honest designs and say which in the
description. Either **stateless** — the agent is instructed to treat every request as
self-contained, the description says so, and the session-per-connection behaviour becomes a harmless
implementation detail — or **explicitly stateful**, where the caller passes a conversation handle in
the request text and the server keys its session on that instead of on the connection. Day 32's
[3.4](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md)
is the pattern for the second, and Day 36's
[3.3](../../../day-36-long-jobs-and-tasks/parts/03-the-handle/3.3-sutras-handle-policy.md) is
Sutra's rule for what such a handle may look like. What you do not do is leave it implicit.

**What degrades at scale:** two things at once. `InMemorySessionService` grows without bound, since
nothing evicts an ADK session when its connection dies — the `WeakKeyDictionary` only drops the
*pointer*. And the moment there are two server instances, connection affinity becomes the thing
holding your correctness together, which works until a deploy.

**The failure mode that only appears with real traffic:** the concurrency window in `sessions.get`.
Two calls arriving on one connection at the same moment both miss, both create a session, and the
second write wins. One conversation's first turn is now stranded in a session nothing will ever read
again. At low traffic this never happens; at high traffic it happens quietly and shows up as
occasional amnesia.

**The review comment a senior engineer leaves:** *"our served agent has per-connection memory and
the tool description does not mention it, so callers will either not use it or accidentally depend
on it. Pick one. If we want conversations, the handle goes in the request and we key on that so it
survives a reconnect and a second instance. If we do not, say 'each call is independent' in the
description and instruct the agent to ignore history. Right now we are shipping the worst of both:
memory that works often enough to be relied on and vanishes without an error."*

**The interview question:** *"does an MCP-served agent remember anything between calls?"* The honest
answer: *"It depends on something the caller cannot see. ADK keeps one session per MCP connection in
a weak-keyed map, so two calls down the same pipe share a conversation and a reconnect starts a fresh
one, with no error either way. That is a memory model the protocol has no field to advertise, and the
current spec revision deliberately pushed the other way, towards state travelling in the payload. So
in production I either declare the thing stateless and mean it, or I move the conversation key into
the request so it survives a reconnect and works across instances. And I would always mention it in
the tool description, because the failure mode is not an error, it is a slightly worse answer."*
