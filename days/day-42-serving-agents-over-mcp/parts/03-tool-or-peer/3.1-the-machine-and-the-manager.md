# 3.1 — The machine and the manager

## One-line answer

**Agent-as-tool** means the caller *uses* you — one instruction in, one result out, no identity and
no conversation — while **agent-as-peer** means the caller *talks to* you, with two named parties, a
conversation that has a lifetime, and the right to ask questions back.

## The story

The pump at the fuel station is self-service. You tap the card, you say how much, the fuel goes in,
and you drive off. It does not ask where you are going. It does not remember that you were here
yesterday, or notice that your rear tyre is soft. If your card is refused it prints six words, and
the six words are the same six words for every reason a card gets refused.

You are not talking to it. You are using it.

The man in the forecourt office is a different thing entirely. You go in about the receipt that did
not print, and it turns into a conversation. He asks which pump and what time. He asks whether you
have used the loyalty card, which you had forgotten about. Halfway through you find out that what you
actually needed was not what you walked in for, and he can say *"come back tomorrow, the printer roll
is being changed in the morning"* — a thing the pump has no way to express, because it is not an
answer, it is the conversation continuing.

Neither is better. On a Tuesday when you want twenty litres and nothing else, the office is a waste
of everybody's afternoon, and the pump is exactly right.

## The idea in plain language

Two ways to make an agent reachable from outside your process, and they are not two implementations
of one idea. They are different shapes.

**Agent-as-tool.** The agent appears in somebody else's tool list. Their model decides to call it the
same way it decides to call a date parser. One request, one reply. Nothing about the exchange says
there is an agent on the other side, and nothing needs to. This is what MCP gives you, and
`to_mcp_server` is the one-line way to get it.

**Agent-as-peer.** The agent is a service another agent addresses as a counterpart. It has a public
description of itself that the caller fetches. There is a unit of work with an identity and a
lifetime, which can be started, watched, added to and cancelled. Either side can send a message. This
is what **A2A** — the Agent-to-Agent protocol, Day 89 — gives you, and ADK's one-line way to get it
is `to_a2a`.

The two words that separate them are **use** and **talk to**. Everything else follows:

| | Agent-as-tool (MCP) | Agent-as-peer (A2A) |
| --- | --- | --- |
| What the caller has | a tool in a list | a counterpart with an address |
| The unit of exchange | one request, one reply | a task with a lifetime |
| Who may speak first | the caller, always | either side |
| Identity | whatever the transport carries, and ADK discards it | part of the model |
| Can the callee ask a question back? | not in a tool call | yes, that is the point |
| Discovery | `tools/list` — a name and a sentence | an agent card describing capabilities |
| ADK's one-liner | `to_mcp_server(agent)` → a `FastMCP` server | `to_a2a(agent, port=...)` → a Starlette app |

Read the last row twice. The two functions return **different kinds of object**, and that is not an
accident of implementation. `to_mcp_server` returns a server you may run over a pipe on the same
machine. `to_a2a` returns a web application, because a peer has an address, and an address means
something is deployed and hosted.

## Why Sutra needs it

Because Sutra will eventually be both, and choosing wrongly today makes Day 89 a rewrite instead of
an addition.

The plan puts A2A in Phase 14, at Day 89. That is the day Sutra learns to be a peer. Today is the day
Sutra learns to be a tool, and the reason both exist in one curriculum is that **the same agent can be
served both ways at once, and usually should not be**. Serving one agent through two doors with two
identity models and two failure stories is how a system ends up with a rule that holds on one route
and not the other.

Sutra's concrete question, which [3.3](3.3-the-guillotine-and-the-press.md) answers, is: *which of
Sutra's callers actually needs a conversation?* If the answer is none of them, agent-as-tool is not a
compromise. It is the right shape, and A2A would be a hosting bill for a property nobody wanted.

## The mechanism

Both one-liners exist in the installed ADK. Here they are side by side, and the difference is
readable in the signatures alone.

```python
# Agent-as-tool. Verified in .venv/Lib/site-packages/google/adk/tools/mcp_tool/_agent_to_mcp.py
from google.adk.tools.mcp_tool import to_mcp_server

server = to_mcp_server(agent, name=None, instructions=None, runner=None)
server.run(transport="stdio")
```

**Line by line:**

- Three optional keyword arguments and one of them is a `Runner`. There is no host, no port, no path
  and no card, because a tool does not have an address — the transport it runs over is chosen by
  whoever starts it.
- `transport="stdio"` is a legitimate production choice here. A host can launch your server as a
  subprocess and talk to it over a pipe, which needs no network, no certificate and no deployment.
  That is a real advantage and it disappears the moment you become a peer.
- `run(...)` blocks. The object returned by `to_mcp_server` is inert until something runs it, exactly
  as Day 34's
  [1.2](../../../day-34-building-sutra-mcp-tools/parts/01-the-server-object/1.2-a-server-you-build-not-one-that-runs.md)
  established.

```python
# Agent-as-peer. Read from .venv/Lib/site-packages/google/adk/a2a/utils/agent_to_a2a.py on
# 2026-09-05. It does not import here: the `a2a` package is a separate extra, not installed
# in this repository, and Day 89 is the day that installs it.
from google.adk.a2a.utils.agent_to_a2a import to_a2a

a2a_app = to_a2a(agent, host="localhost", port=8001, agent_card=None, task_store=None)
```

**Line by line:**

- `host` and `port` are in the signature. A peer is something you can point at, so its identity
  includes where it lives. That is one fact and it drags a deployment, a certificate and a DNS entry
  along behind it.
- `agent_card=` is the discovery document. Where MCP gives a caller a name and a sentence, A2A gives
  them a structured description of the counterpart, auto-generated from the agent if you pass
  nothing. A caller can read it before deciding to talk.
- `task_store=` exists because a peer's unit of work is a **task** with a lifetime and a status, so
  something has to hold it between messages. Day 36's
  [4.2](../../../day-36-long-jobs-and-tasks/parts/04-the-tasks-extension/4.2-five-statuses-and-the-terminal-rule.md)
  taught that state machine on the MCP side as an extension; on the A2A side it is the core model.
- The return type is a `Starlette` application, not a server object. You do not `run()` it — you
  serve it with an ASGI server. That is the shape Day 43 builds for Sutra's MCP server, and it is
  what a peer requires from the first line.
- `to_a2a` is **documented on adk.dev** at `https://adk.dev/a2a/quickstart-exposing/`, checked
  2026-09-05. `to_mcp_server` is not documented anywhere on that site. Two functions the source
  itself calls counterparts, and only one of them has a page — which is a fact worth carrying into
  [6.1](../06-in-production/6.1-the-school-in-two-sheds.md).

The MCP function's own docstring makes the pairing explicit, and it is the clearest single sentence
on the subject in either project:

```text
This is the MCP counterpart of ``to_a2a``; it lets harnesses that speak MCP drive an ADK agent.
```

*"Harnesses that speak MCP **drive** an ADK agent."* Drive, not converse with. The word choice is the
distinction.

## When it breaks

The break is choosing peer-shaped semantics and building them on a tool-shaped door.

🎬 **The scene:** your served desk needs one clarification before it can answer — the ticket id was
ambiguous. You know MCP has a mechanism for exactly this: **elicitation**, from Day 37's
[3.1](../../../day-37-auth-and-elicitation/parts/03-the-question/3.1-the-job-that-stopped-and-left-a-number.md),
where a server asks the caller a question mid-call.

😬 **The naive fix:** have the agent call elicitation from inside the served tool.

💥 **Why it fails:** the function `to_mcp_server` registers is `call_agent(request, ctx)`, and the
only thing it does with `ctx` is `report_progress`. There is no path from your agent's execution back
out to `ctx.elicit`. The agent is running inside a `Runner` that knows nothing about MCP. To wire it
up you would have to build the `Runner` yourself, thread the MCP context through a callback into the
agent, and handle the case where the caller declared no elicitation capability — at which point you
have written a peer protocol badly, on top of a tool protocol, by hand.

💡 **The insight:** **the question a service can ask back is the line between the two shapes.** A tool
answers or fails. A peer can say *"which of these two did you mean?"* and stay alive while it waits.
If your design needs that sentence, you are describing a peer, and building it out of tool calls will
cost you a state machine you did not budget for. Day 89 is where that gets built properly.

## In production

**What a professional writes instead:** they decide with one question — *does the caller need a
conversation, or an answer?* — and then they write the answer down in an ADR before any code. The
decision is expensive to reverse because it leaks into the caller's code: a tool integration is three
lines in a host config, and a peer integration is a deployment, a card, a task store and a retry
policy on the caller's side.

**What degrades at scale:** the mismatch. A tool-shaped door under peer-shaped load looks like a lot
of short calls that each re-establish context from scratch, which is expensive in tokens and produces
worse answers as the conversation lengthens. A peer-shaped door under tool-shaped load looks like a
deployment, a task store and an operations burden for exchanges that were always one-shot.

**The failure mode that only appears with real traffic:** callers simulating a conversation. Given a
tool that answers questions and no way to have a dialogue, a caller's model will paste the entire
prior exchange into the next `request` string. It works. It also means your token cost per call grows
with the length of somebody else's conversation, and you find out from latency before you find out
from anything else.

**The review comment a senior engineer leaves:** *"before we pick a protocol, tell me whether the
caller needs to be asked a question. If they do, this is A2A and we should say so now rather than
discover it after three teams have wired up an MCP tool. If they do not, MCP over stdio is a
subprocess and a pipe, and we should be glad we do not have to deploy anything."*

**The interview question:** *"MCP or A2A for exposing your agent?"* The honest answer: *"They answer
different questions, so I start with the caller. MCP makes my agent a tool: one string in, one reply
out, the caller's model routes to it like any other function, and I can ship it over stdio as a
subprocess with no deployment at all. A2A makes it a peer: it has an address, an agent card, and a
task with a lifetime that either side can send messages about. The thing that decides it for me is
whether my service ever needs to ask the caller a question mid-work. A tool call cannot do that —
there is no path from inside the agent back out to the caller — so if I need it, I am building A2A
whether I meant to or not. For a read-only question-answering service, MCP, and I would be suspicious
of anyone who reached for the heavier one without naming a caller who needs it."*

The first prints a signature. **The second fails**, on purpose:

```text
ModuleNotFoundError: No module named 'a2a'
exit: 1
```

That is not a broken instruction — it is the honest state of this repository on 2026-09-05. A2A is
Day 89, its `a2a` package is not installed, and a day pins only what it installs. The third command
is how you read the signature anyway, straight off the file, which is where every claim in this part
came from.

Put the two signatures side by side and name every argument that exists in one and not the other.
Each of those differences is a property of the shape, not a preference of the author.
