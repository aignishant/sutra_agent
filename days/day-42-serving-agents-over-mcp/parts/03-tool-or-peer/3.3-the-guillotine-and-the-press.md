# 3.3 — The guillotine and the press

## One-line answer

Sutra serves a **narrow, read-only answering agent as a tool over MCP**, does not serve the whole
desk, and does not serve anything as a peer — because the only lever `to_mcp_server` gives you is the
choice of what to hand it, and every other control you want lives on the agent you chose.

## The story

The printing co-operative has two machines that outsiders keep asking about.

One is the guillotine. It cuts a stack of paper straight. Anybody can be shown how to use it in ten
minutes, it does one thing, and the worst outcome is a wasted ream. The co-op rents it out by the
hour and has done for years. There is a sheet by the door where you write your name.

The other is the big press. It is older than most of the members, it has a temperament, and the one
man who really understands it has been running it for eleven years. Outsiders ask to rent it and the
answer is always no — not because the co-op is precious about it, but because the failure modes are
not the kind you can write on a sheet by the door. You can bring your job to the co-op and the co-op
will print it for you. What you cannot do is stand at the press yourself.

That is not a refusal to help. It is a different offer, and it is a better one for everybody.

## The idea in plain language

You now have every fact this decision needs. This part spends them.

The lever, from [2.4](../02-what-crosses-the-counter/2.4-the-errand-you-sent-someone-on.md): the
only thing you control about a served agent's power is **which agent you pass in**. There is no
filter argument, no permission argument, no per-caller scope. Serving `build_desk()` and serving a
purpose-built answerer are the same one line of code and completely different exposures.

The constraints, from sections 1 and 2:

| Fact | Established in | What it rules out |
| --- | --- | --- |
| every caller is `mcp_user` | [1.3](../01-the-back-office/1.3-the-hall-that-came-with-its-own-chairs.md) | any rule about *who* asked |
| the input is one unvalidated string | [2.1](../02-what-crosses-the-counter/2.1-the-enquiry-slip-with-one-box.md) | schema-level defence |
| tool calls do not reach the caller | [2.2](../02-what-crosses-the-counter/2.2-the-interpreter-who-relays-the-last-sentence.md) | the caller auditing what happened |
| memory is per connection and undeclarable | [2.3](../02-what-crosses-the-counter/2.3-the-table-you-may-leave-your-books-on.md) | a conversation you can rely on |
| the reach is the whole sub-agent tree | [2.4](../02-what-crosses-the-counter/2.4-the-errand-you-sent-someone-on.md) | serving anything with a write in reach |
| a retry may repeat the work | [3.2](3.2-a-note-handed-over-and-money-sent.md) | non-idempotent operations |

Six facts, and five of them point the same way: **serve something that cannot do damage and cannot be
damaged by being called twice.**

## Why Sutra needs it

Because this decision is the one Day 45's audit will read back, and because a decision not written
down is a decision the next person will make differently.

Sutra is a support desk. Its callers, when they exist, will be other teams' agents wanting an answer
about a ticket or a knowledge-base article. Nobody has asked for a conversation. Nobody has asked to
close a ticket through Sutra. Those are the two things that would push towards a peer and towards
serving the whole desk, and neither is on the table.

Meanwhile section 4 is about to show that on twenty generations a day, the whole desk cannot serve
anybody anyway. The verdict below is not a compromise forced by the free tier — it is what the
security argument already said, and the quota argument agrees with it.

## The mechanism

**Sutra's verdict, in three lines.**

**1. Agent-as-tool, over MCP. Not agent-as-peer.** No caller needs to be asked a question mid-work,
and no caller needs a task with a lifetime. [3.1](3.1-the-machine-and-the-manager.md)'s deciding
question — *does the caller need a conversation, or an answer?* — has the answer *an answer*, so A2A
would buy a deployment, an address, a card and a task store for a property nobody wanted. It stays
parked until Day 89 gives it a caller.

**2. A narrow read-only agent, not `build_desk()`.** The desk keeps `close_ticket` when the multi-agent
phase gives it one, and it keeps the ability to hand work to a billing sub-agent. Neither of those may
be reachable from an unauthenticated string.

**3. One endpoint, separate from `sutra-mcp`, with the cost stated in the description.**
[1.4](../01-the-back-office/1.4-the-counter-by-the-side-door.md) is the argument for separateness;
[4.3](../04-what-a-call-costs/4.3-the-notice-on-the-ration-shop-board.md) is what the description
must say.

What that looks like:

```python
"""Sutra's knowledge-base answerer, served over MCP. Read-only, one question at a time."""

SERVED_AGENT_NAME = "sutra_kb_answerer"

# Every tool one `request` string can set in motion. The gate walks the served agent and
# fails if this list and the write set ever intersect - 2.4 is the argument.
REACH = ["search_kb"]

SERVED_DESCRIPTION = (
    "Answers one self-contained question from Sutra's internal support knowledge base and "
    "cites the article id it used. Good: 'why do users get logged out after the 2.3 update?' "
    "Not for: closing tickets, refunds, or anything about a specific customer's account. "
    "Each call runs a language model on a free-tier quota, so calls are slow, limited to a "
    "small number per day, and must not be retried automatically."
)


def build_served_agent() -> LlmAgent:
    """A read-only answerer built for the door, not the desk built for us."""
    return LlmAgent(
        name=SERVED_AGENT_NAME,
        model=MODEL,
        description=SERVED_DESCRIPTION,
        instruction=SERVED_INSTRUCTION,
        tools=[search_kb],
        sub_agents=[],
    )
```

**Line by line:**

- `SERVED_AGENT_NAME` differs from the desk's name on purpose. Two agents, two names, so a log line,
  a session key and a tool name all say which one ran. Reusing `desk` would make the served
  conversations indistinguishable from the internal ones in `session_service`.
- `REACH = ["search_kb"]` is written down as data rather than computed, so it is reviewable in a
  diff. The gate computes the real reach and compares; a constant that disagrees with reality is a
  finding, and that is the point.
- `SERVED_DESCRIPTION` is four sentences doing four jobs: what it answers, an example that fits, an
  example that does not, and the operational facts a caller cannot discover. It is written here as a
  module constant rather than inline, because Day 45's audit needs something to import and a test
  needs something to assert on.
- *"must not be retried automatically"* is the sentence [3.2](3.2-a-note-handed-over-and-money-sent.md)
  earned. It cannot be enforced — nothing in MCP lets a server forbid a retry — so it is stated. A
  stated constraint that a good caller honours is worth more than an unstated one nobody knows about.
- `tools=[search_kb]` and **not** the desk's toolset. `lookup_ticket` is deliberately absent: it takes
  a ticket id, which is customer-specific, and a stranger with an unauthenticated string should not be
  reading tickets by id. That is a policy decision, it is arguable, and the point is that it is made
  here in one visible line.
- `sub_agents=[]` is written explicitly even though it is the default, because an empty list here is
  a *decision* — it is the line somebody would edit to reintroduce the whole problem
  [2.4](../02-what-crosses-the-counter/2.4-the-errand-you-sent-someone-on.md) described, and a blank
  where a decision should be is not reviewable.
- `build_served_agent()` is a function so that nothing runs at import, matching every builder in this
  repository since Day 5.

**What is deliberately not built** 🅿️: per-caller identity, a caller quota, and elicitation from
inside the served call. The first two need an identity `to_mcp_server` discards before your code
runs; the third needs a path from the agent back to the MCP context that does not exist. All three
are properties of the peer shape, and Day 89 is where they arrive together rather than one at a time
as hacks.

## When it breaks

The break is what happens if you take the easy line instead.

🎬 **The scene:** it is late, `build_desk()` already exists, and `to_mcp_server(build_desk())` is one
line that works immediately.

😬 **The naive fix:** ship that, and add a note to the instruction saying *"never close a ticket for
a request that came over MCP"*.

💥 **Why it fails:** the instruction cannot tell. `_run_agent` builds a `types.Content(role="user")`
from the request string and hands it to the runner, and there is nothing in that content, or in the
session, or anywhere the agent can read, that says this turn arrived over MCP rather than from
`adk web`. The distinction the instruction is trying to make does not exist in the data the agent
has. And even if it did, you would be enforcing a security boundary with a sentence in a prompt,
against input that is itself a sentence in the same prompt — which Day 40's
[6.2](../../../day-40-filtering-and-allowlists/parts/06-the-posture/6.2-the-attacks-a-filter-does-not-stop.md)
already established is not a boundary.

💡 **The insight:** **the safe agent and the capable agent have to be two objects, because the only
enforcement point is the choice of object.** Any design that serves one agent and hopes to narrow it
afterwards is enforcing policy in prose, inside the same channel as the attack.

## In production

**What a professional writes instead:** two agents and one shared implementation. The tools are
written once — `search_kb` is the same function both agents call — and the *agents* differ. That way
the narrow one cannot drift away from the real one's behaviour, and the broad one cannot leak into
the narrow one's reach. The decision itself goes in an ADR with the six facts from the table above as
its evidence, because the next person will ask why there are two.

**What degrades at scale:** the number of served agents. One narrow answerer is easy to reason about.
An organisation that has said yes to nine such requests has nine agents, nine descriptions, nine
reaches and nine quota lines, and no single place that says which of them may write. The scaling
answer is not a better instruction; it is a registry and a gate that walks all of them.

**The failure mode that only appears with real traffic:** the request to broaden it. Six months after
this ships, a caller asks whether the served agent could *just* also close a ticket, because they
already have the integration and it would save them a day. Every fact in the table above still holds
and none of them is visible in the pull request that adds one tool. This is what the gate is for, and
it is why the deny set is a constant with a comment rather than a convention.

**The review comment a senior engineer leaves:** *"good — a separate narrow agent rather than the
desk with a warning in its prompt. Two things: put the reach check in the gate so adding a tool to
this agent fails the build, and make the description's last sentence non-negotiable in review. The
callers cannot see our quota, and the only place we can tell them is that string."*

**The interview question:** *"you can expose your agent as an MCP tool or an A2A peer. Which did you
pick and why?"* The honest answer: *"Tool, and a narrow one. The deciding question was whether any
caller needed a conversation or needed to be asked something mid-work, and none did — they wanted an
answer. Once it is a tool, the only lever the API gives you is which agent you hand it, because
identity is discarded, the input is one unvalidated string, and the reach is the whole sub-agent tree.
So I built a second, read-only agent specifically for the door rather than serving the real desk with
a rule in its prompt, since the prompt cannot tell where a request came from and would be enforcing a
boundary inside the same channel as the attack. The peer shape stays parked until somebody names a
caller who needs to be asked a question, because it costs a deployment, an address and a task store
to buy properties nobody has asked for yet."*
