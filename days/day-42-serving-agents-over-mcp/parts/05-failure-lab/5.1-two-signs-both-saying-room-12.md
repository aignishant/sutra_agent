# 5.1 — Two signs, both saying Room 12

## One-line answer

Nothing stops a served agent from having your own server on its tool list, and when that happens one
caller request becomes as many agent runs as something else eventually stops — with every run
spending a generation.

## The story

The sign at the end of the corridor says **Enquiries: Room 12**, with an arrow.

You follow it. Room 12 has a door, and on the door there is another sign, printed on the same paper
by the same printer, and it says **Enquiries: Room 12**, with an arrow pointing back the way you came.

You stand there for a while. Neither sign is wrong. Somebody put up the first one because enquiries
go to Room 12, which is true. Somebody put up the second one because this is a corridor and corridors
get signs, which is also true. Nobody has ever walked the route, because everybody who works here
already knows where enquiries go.

The only reason the building does not fill up with people going round in circles is that people get
tired and leave.

## The idea in plain language

Two facts you already have, put together.

From [2.4](../02-what-crosses-the-counter/2.4-the-errand-you-sent-someone-on.md): a served agent's
reach is every tool it owns plus every tool of every sub-agent.

From Day 33: an ADK agent can be given a `McpToolset`, which mounts somebody else's MCP server and
turns its tools into tools this agent may call.

Nothing anywhere checks whether "somebody else's MCP server" is *this* server. The agent has a
toolset. The toolset points at an address. The address happens to be the process it is running in.
Neither ADK nor MCP has any notion of "the server I am currently answering a request for", so there
is no place the check could even live.

The result is not a stack overflow. Python's recursion limit never fires, because each level is a
fresh async task talking over a transport rather than a nested function call. It is an **unbounded
fan-out**, and the things that eventually stop it are, in order of how much they cost you: your daily
quota, the caller's timeout, the server's memory.

Two shapes of the same bug:

- **Direct.** Agent A is served, and A's toolset includes A's own server.
- **Mutual.** Agent A's toolset includes B's server; B's toolset includes A's. Neither team can see
  the loop, because each of them is looking at one half of it.

The second is the one that happens in real organisations, and it is invisible in both repositories.

## Why Sutra needs it

Because Sutra has both halves already and the plan puts them together.

`sutra_mcp/server.py` is a server Sutra publishes. `sutra/mcp/client.py` is the client Day 33 built
so that Sutra's agents can mount servers. Day 40's `sutra/mcp/filtering.py` decides which tools
survive the mount. All that is missing is one configuration line pointing the desk's toolset at
Sutra's own address, and there is a very ordinary reason somebody would write it: the desk would like
to use the archive tools over the wire so it works the same way in every deployment.

That is a reasonable thought and it is one line away from a loop that costs a whole day's quota in
the first request.

Principle 13 — blast radius before capability — is why this is a part rather than a footnote. And
Principle 15 is why it is not merely embarrassing: every level of the fan-out is a generation, on a
budget of twenty.

## The mechanism

`lab/recurse.py` builds the smallest honest version. The agent is a plain `BaseAgent`, so the loop
costs nothing to demonstrate, and the script counts the runs a live desk would have paid for:

```python
# Without this the script does not terminate. It is a lab ceiling, not a fix - a real
# deployment hits the quota, the request timeout or the memory limit instead.
CEILING = 8

runs = 0
in_flight = False


class Delegator(BaseAgent):
    """An agent that answers by asking the desk - which is itself."""

    async def _run_async_impl(self, ctx: InvocationContext) -> AsyncGenerator[Event, None]:
        global runs, in_flight
        runs += 1
        mine = runs
        was_in_flight = in_flight
        in_flight = True
        try:
            if GUARDED and in_flight:
                print(f"  run {mine}: refused to delegate - sutra_desk is the server calling me")
            elif mine < CEILING:
                async with create_connected_server_and_client_session(SERVER) as client:
                    await client.call_tool("sutra_desk", {"request": "ask the desk"})
        finally:
            in_flight = was_in_flight
        yield Event(
            author=self.name,
            invocation_id=ctx.invocation_id,
            content=types.Content(role="model", parts=[types.Part(text=f"run {mine} answered")]),
        )


SERVER = to_mcp_server(Delegator(name="sutra_desk", description="Delegates to the desk."))
```

**Line by line:**

- `CEILING = 8` exists so the script terminates, and the comment says outright that it is not the
  fix. This matters: a reader who sees a constant like this and thinks *"so there is a limit"* has
  learned the opposite of the lesson. In production nothing counts the levels.
- `runs` and `in_flight` are module globals, which is exactly what a real deployment does not have —
  a real fan-out is spread across tasks and connections. They are here because the lab has to be
  readable in one screen, and `runs` is what makes the cost visible at the end.
- `class Delegator(BaseAgent)` rather than `LlmAgent`, so the whole demonstration runs on zero
  generations. The structure of the failure — an agent whose tool is its own server — is identical;
  only the price tag is simulated.
- `create_connected_server_and_client_session(SERVER)` is the SDK's in-memory client-server pair, from
  `mcp.shared.memory`. It is a genuine MCP session over an in-process transport, so the call really
  does go out through the protocol and come back in through `call_agent`. Using it rather than a
  socket keeps the lab hermetic.
- `SERVER` is a module-level constant referenced from inside the agent that the server serves. That
  circular reference is the entire bug, in one line, and it is the shape a configuration file
  produces without anybody writing anything circular-looking.
- `if GUARDED and in_flight:` is the fix, and it is one question asked before the outbound call: *is
  the server I am about to call already busy running me?* On a self-call the answer is always yes.
- `try/finally` restoring `was_in_flight` rather than setting `in_flight = False` is what makes the
  guard correct under nesting. Setting it to `False` on the way out would clear the flag for an outer
  run that is still in flight.
- The `Event` is yielded **after** the delegation, so each level answers only once its child has. That
  is the ordinary shape of an agent that delegates, and it means the caller waits for the whole depth
  of the fan-out before receiving anything.

## When it breaks

The unguarded arm, measured on 2026-09-05:

```text
arm: unguarded
isError            : False
caller sees        : run 1 answered
agent runs executed: 8
generations a live desk would have spent: 8
```

Read the third line against the second. **The caller sees one perfectly normal answer.** No error, no
warning, no hint that anything unusual happened. `isError` is `False`. From the outside this call was
a success.

And eight agent runs happened. On Sutra's real desk at three generations each, that is
twenty-four generations for one question, against a daily ceiling of twenty — so the *first* request
of the day exhausts the day, and the caller who caused it gets a clean answer and no idea.

The ablation, one flag, same agent:

```text
arm: --guarded
  run 1: refused to delegate - sutra_desk is the server calling me
isError            : False
caller sees        : run 1 answered
agent runs executed: 1
generations a live desk would have spent: 1
```

**The caller sees the identical answer.** `run 1 answered`, both times. That is the sharpest thing in
this part: the guard changes nothing a caller can observe and changes everything you pay. Which also
means no client-side test would ever have caught it.

🎬 **The scene:** the mutual version. Your desk mounts the search team's server, because their
retrieval agent is genuinely better at finding articles. Last month the search team mounted your
server, because your desk is genuinely better at reading tickets.

😬 **The naive fix:** neither team does anything, because neither team's configuration contains a
loop. Yours points at theirs. Theirs points at yours.

💥 **Why it fails:** one question that both agents think the other should handle bounces until
something external stops it. Your quota goes, or theirs does. The traces are in two different
observability systems owned by two different teams, and each half looks like a normal outbound call
to a normal collaborator.

💡 **The insight:** **a loop through a network is invisible to every party in it.** The cycle guard
you would write for an in-process agent tree — the `seen` set in
[2.4](../02-what-crosses-the-counter/2.4-the-errand-you-sent-someone-on.md)'s `reach` walk — does not
work here, because the tree does not exist as an object anywhere. What has to travel instead is a
marker in the request, and the only place a marker can travel is a field somebody has agreed on.

## In production

**What a professional writes instead:** a depth counter that travels with the call. Every request
carries a hop count and a list of server names already in the chain; a server that finds its own name
in that list refuses immediately, and a server that finds the hop count over a small maximum refuses
too. Day 32's
[3.1](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.1-the-label-on-the-envelope.md)
is the mechanism — metadata on the request rather than state on the server — and this is exactly the
kind of thing it is for. The cheap version, which costs nothing and catches the direct case, is a
startup check that no mounted server URL is this server's own.

**What degrades at scale:** the number of pairs. Two agents can be checked by hand. Twelve served
agents across four teams is sixty-six possible pairs, and the property you need — no cycle in the
call graph — is a property of the graph nobody owns. This is the point at which an organisation
either has a registry of served agents or has this outage.

**The failure mode that only appears with real traffic:** the loop that is not a loop until Tuesday.
Nothing is circular when the search team mounts you. It becomes circular the day *you* mount *them*,
which is a change in your repository that passes review because your side is obviously fine. Day 40's
[3.1](../../../day-40-filtering-and-allowlists/parts/03-when-the-server-changes/3.1-the-tuesday-a-tool-appeared.md)
is the same shape of surprise from the tool-list direction.

**The review comment a senior engineer leaves:** *"this adds our own MCP server to the desk's
toolset, and the desk is the agent we serve on that server. That is a self-call: one request becomes
however many runs the quota allows, and the caller gets a normal answer, so nothing will alert. At
minimum, refuse at startup if a mounted server URL is our own. Better, put the server chain in the
request metadata and refuse when we see our own name in it — that is the only version that catches
the mutual case with the search team."*

**The interview question:** *"what happens if an agent you serve over MCP can call the server that
serves it?"* The honest answer: *"One request becomes an unbounded fan-out, and the thing that stops
it is your quota, the caller's timeout or your memory — not a recursion limit, because each level is
a separate task over a transport rather than a nested call. The nasty part is that the caller sees a
completely normal successful answer, so nothing on their side alerts and no client test catches it. I
have run that: eight runs behind one call, `isError` false, and the guarded version returns the
identical answer for one run. The direct case you catch at startup by refusing to mount your own URL.
The mutual case, where two teams each mount the other, needs the chain of server names to travel in
the request metadata, because neither repository contains a loop."*
