# 6.2 — Red before you serve

## One-line answer

Six statements have to be true of `sutra_mcp/agent_server.py` before a stranger may call it, and the
only useful form for those statements is a script with an exit code that was **red before you wrote
the module**.

## The story

On the first of every month, at eleven, the building tests the generator.

The lights flicker, the lift stops for a moment, and for about a minute the whole place runs on
diesel. It is mildly annoying and everybody knows it is coming. What it buys is that when the power
actually goes at nine on a wet Tuesday evening, the generator starts, because somebody found the flat
battery on the first of last month and replaced it in daylight with the shop still open.

The building next door does not do this. Their generator is newer. It has also never been started
since it was installed, and the honest position is that nobody there knows whether it works — they
know it *exists*, which is a different thing, and they will find out which on the wet Tuesday.

## The idea in plain language

Principle 11 says an eval is a test and a test must be able to go red. Day 34's
[6.2](../../../day-34-building-sutra-mcp-tools/parts/06-in-production/6.2-red-before-you-ship-it.md)
turned that into a shape this repository now reuses: a script that collects **findings** — sentences,
not booleans — prints them, and exits non-zero when there are any.

Today's gate checks six statements. Each one is a decision made somewhere in this day, turned into
something a machine can disagree with:

| # | The statement | Where the decision was made |
| --- | --- | --- |
| 1 | `sutra_mcp.agent_server` imports | [6.1](6.1-the-school-in-two-sheds.md) — the silent import guard |
| 2 | `build_agent_server()` returns a `FastMCP` | [1.2](../01-the-back-office/1.2-twelve-words-in-the-classifieds.md) |
| 3 | the served surface has exactly one tool, named `SERVED_AGENT_NAME` | [1.2](../01-the-back-office/1.2-twelve-words-in-the-classifieds.md) |
| 4 | that tool's description is not empty | [2.1](../02-what-crosses-the-counter/2.1-the-enquiry-slip-with-one-box.md) |
| 5 | `REACH` contains no write tool | [2.4](../02-what-crosses-the-counter/2.4-the-errand-you-sent-someone-on.md), [3.3](../03-tool-or-peer/3.3-the-guillotine-and-the-press.md) |
| 6 | `sutra_mcp/server.py` does not mention `agent_server` | [1.4](../01-the-back-office/1.4-the-counter-by-the-side-door.md) |

Every one of those is something a person would otherwise have to remember six months from now, in a
pull request that looks unrelated.

## Why Sutra needs it

Because five of the six protect a decision whose *reason* is not visible in the code the decision
lives in.

Nothing in `sutra_mcp/server.py` explains why it must not import `agent_server`. Nothing in the
served agent's definition explains why `sub_agents` is empty. A future reader sees an empty list and
a missing import and has no way to distinguish a decision from an oversight, and the natural
engineering instinct — tidy it up, share the server, reuse the desk — undoes the whole day.

A gate is where a reason lives in an executable form. And Day 45's audit is going to run it: the
Phase 6 gate audits every server days 32–44 built, and *"this one has its own gate and it is green"*
is a much better finding than a paragraph of prose.

## The mechanism

`lab/gate.py`, in full. It calls no model and starts no server:

```python
WRITE_TOOLS = {"close_ticket", "refund", "export_archive"}


def findings() -> list[str]:
    """Every statement that is false right now, as a sentence."""
    out: list[str] = []

    try:
        agent_server = importlib.import_module("sutra_mcp.agent_server")
    except Exception as exc:  # noqa: BLE001 - the finding is the exception text
        return [f"sutra_mcp.agent_server is not importable: {type(exc).__name__}: {exc}"]

    build = getattr(agent_server, "build_agent_server", None)
    if build is None:
        out.append("sutra_mcp.agent_server has no build_agent_server")
        return out

    server = build()
    if type(server).__name__ != "FastMCP":
        out.append(f"build_agent_server returned {type(server).__name__}, not FastMCP")
        return out

    listed = asyncio.run(server.list_tools())
    if len(listed) != 1:
        out.append(f"the served surface has {len(listed)} tools, not exactly 1")

    served_name = getattr(agent_server, "SERVED_AGENT_NAME", None)
    if served_name is None:
        out.append("sutra_mcp.agent_server has no SERVED_AGENT_NAME")
    elif listed and listed[0].name != served_name:
        out.append(f"the served tool is {listed[0].name!r}, not SERVED_AGENT_NAME {served_name!r}")

    if listed and not (listed[0].description or "").strip():
        out.append("the served tool has an empty description; the caller has nothing to route on")

    reach = getattr(agent_server, "REACH", None)
    if reach is None:
        out.append("sutra_mcp.agent_server has no REACH naming every tool one request can run")
    else:
        writes = sorted(set(reach) & WRITE_TOOLS)
        if writes:
            out.append(f"one `request` string reaches write tools: {writes}")

    source = (REPO / "sutra_mcp" / "server.py").read_text(encoding="utf-8")
    if "agent_server" in source:
        out.append("sutra_mcp/server.py imports agent_server; the two servers must stay separate")

    return out
```

**Line by line:**

- `WRITE_TOOLS` is a **module constant with a comment**, not a condition buried in an `if`. It is the
  line a reviewer reads to learn the policy, and the line somebody edits when the policy changes —
  which is exactly the edit you want to see in a diff.
- `except Exception` with `# noqa: BLE001` and a reason on the same line. The rule against broad
  excepts is Principle 10, and this is the case it does not apply to: the finding *is* the exception,
  the exception is being reported rather than swallowed, and narrowing it to `ImportError` would let a
  `RuntimeError` from Day 27's skill loader crash the gate instead of being reported as a finding.
- `f"...{type(exc).__name__}: {exc}"` puts the class **and** the message in the finding.
  [6.1](6.1-the-school-in-two-sheds.md) is why: `ImportError: cannot import name
  'to_mcp_server'` and `RuntimeError: refusing to start: unloadable skills [...]` need completely
  different responses, and the class is the fastest way to tell them apart.
- The two early `return`s after checks 1 and 2 are deliberate. Once the module will not import or the
  builder returns the wrong kind of object, every later check would produce a cascade of findings
  about a consequence rather than the cause, and a gate that prints seven findings for one bug trains
  people to skim it.
- `type(server).__name__ != "FastMCP"` compares a name rather than doing `isinstance`. That avoids
  importing `mcp.server.fastmcp` in the gate, which would make the gate itself depend on the package
  whose absence check 1 exists to catch.
- `asyncio.run(server.list_tools())` is the only asynchronous thing in the file, and it runs the same
  code path a caller's `tools/list` runs. **It does not run the agent**, so the gate costs zero
  generations.
- `(listed[0].description or "").strip()` guards `None` and whitespace in one expression. Day 34's
  [2.1](../../../day-34-building-sutra-mcp-tools/parts/02-function-to-declaration/2.1-the-decorator-that-writes-your-schema.md)
  found that a missing docstring produces `""` rather than `None`; here the fallback string from
  `to_mcp_server` means it is never empty by accident, so this check catches the *deliberate* empty
  description and the `None` a future version might produce.
- `set(reach) & WRITE_TOOLS` is an intersection, printed sorted so the finding is stable across runs.
  A finding that changes order between runs is a finding that shows up as noise in a diff.
- `read_text(encoding="utf-8")` rather than importing `sutra_mcp.server`, so the check has no side
  effects — [1.4](../01-the-back-office/1.4-the-counter-by-the-side-door.md) is the argument.
- `findings()` returns a list and `main()` prints it and converts the length to an exit code. Keeping
  the two apart means a test can call `findings()` and assert on sentences, which is how Day 45's
  audit will consume this.

## When it breaks

Red, before the module exists. Measured on 2026-09-05:

```text
- sutra_mcp.agent_server is not importable: ModuleNotFoundError: No module named 'sutra_mcp.agent_server'
findings: 1
exit: 1
```

That is the state the gate must start in, and it is the only proof that the gate can fail. A check
written after the code it checks is a check nobody has ever seen go red, which is the generator next
door.

Then break it on purpose, once it is green. Add `refund` to `REACH`:

```text
- one `request` string reaches write tools: ['refund']
findings: 1
exit: 1
```

And add `from sutra_mcp import agent_server` to `sutra_mcp/server.py`:

```text
- sutra_mcp/server.py imports agent_server; the two servers must stay separate
findings: 1
exit: 1
```

Both of those are edits a reasonable person makes for a reasonable reason. Both are caught by a
sentence that says what the rule is, not by a stack trace.

**What the gate cannot check**, and this is the honest half:

- whether the description is any *good*. It checks that it is not empty. A description that is one
  useless word passes.
- whether `REACH` is **true**. It is a constant somebody wrote. Making the gate walk the real agent
  tree and compare is one of the day's `TODO(me)` items, and it is the difference between a check and
  a declaration.
- anything about cost. Nothing in the gate knows that a served call spends three generations, because
  nothing in the code says so — [4.3](../04-what-a-call-costs/4.3-the-notice-on-the-ration-shop-board.md)
  put that in prose because prose is the only channel.

A gate that pretends to check things it cannot is worse than a short one, so those three are written
down here rather than faked.

## In production

**What a professional writes instead:** the same checks, in the test suite rather than in a script,
running on every commit rather than when somebody remembers. The lab script is the teaching form; the
production form is `tests/test_agent_server.py` with one test per finding, so a failure names itself
in the runner's output. And the reach check stops being a constant comparison and becomes a walk over
the real agent object, so that adding a tool to a sub-agent three files away turns the build red.

**What degrades at scale:** the number of served agents again. Six statements about one agent is a
script. Six statements about nine agents is a framework, and the thing it needs that this does not
have is a registry: a list of every served agent, its endpoint, its reach and its owner, generated
rather than maintained. Day 45 builds the Phase 6 version of that for MCP servers.

**The failure mode that only appears with real traffic:** the check that was true at start-up and is
not now. The gate runs at build time against a freshly built server. A long-running process whose
agent is mutated at runtime — a tool added by a plugin, a sub-agent registered dynamically — passes
the gate and then drifts. Day 41's
[3.1](../../../day-41-capabilities-and-mcp-apps/parts/03-declared-versus-implemented/3.1-a-promise-not-a-proof.md)
made this argument about capability declarations and it holds here exactly: a build-time check is a
promise about build time.

**The review comment a senior engineer leaves:** *"the gate is good and it is checking a constant.
`REACH` is whatever somebody typed, so the write-tool check passes on a list that has drifted from
the agent. Walk the real agent and compare the walk against the constant — then the constant is
documentation and the walk is the check, and they can disagree loudly. Also move this into pytest;
a script nobody runs is a comment."*

**The interview question:** *"how do you know a served agent is safe to expose?"* The honest answer:
*"I write down the properties that have to hold and make them fail. For this one it was six: the
module imports, the builder returns a server, exactly one tool with the name I expect, a non-empty
description, no write tool anywhere in the agent's reach, and the agent server not wired into our
other MCP server. I ran it before writing the module so I know it can go red, and then broke two of
them on purpose. What it does not check is whether the description is any good and whether the reach
constant is actually true — that second one is the important gap, and the fix is to walk the agent
tree and compare rather than trust a list. I would rather say that out loud than have a green gate
people believe more than it deserves."*
