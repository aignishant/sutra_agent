# 6.1 — The school in two sheds

## One-line answer

`to_mcp_server` is decorated `@experimental`, lives in a private module, has no page on adk.dev, and
sits behind an import guard that turns any failure in its dependency chain into *"this name does not
exist"* with the reason logged at `DEBUG` — so shipping it means shipping four separate risks, and
three of them are manageable.

## The story

The school has been running out of two sheds behind the playground for eleven months, while the
building is repaired.

Everything works. Classes happen, the teachers are the same teachers, the children learn the same
things, and the results at the end of the year are the same results.

But the timetable is a sheet of paper taped inside the door, handwritten, because the printed board
is still on the wall of the old building. The address on the certificates is the old address. Twice
now the timings on that sheet have changed with no notice. And once, on a Wednesday, the sheds were
not where they had been, because they had been moved fifteen feet to let a lorry through.

None of that makes the school fake. It makes it *provisional*, and the way you deal with a
provisional thing is not to refuse to use it — it is to read the sheet on the door before you set
off, and to keep a plan for the Wednesday it has moved.

## The idea in plain language

Four separate things are true about this function, and lumping them together as "it is experimental"
loses the useful distinctions.

**1. It is decorated `@experimental(FeatureName.MCP_AGENT_SERVER)`.** In ADK's feature registry that
name is configured `FeatureStage.EXPERIMENTAL, default_on=True`. The practical effect is a
`UserWarning` printed once on first use and a statement, from the people who wrote it, that the
behaviour may change without a deprecation cycle.

**2. It lives in `_agent_to_mcp.py`.** The leading underscore says the *module* is private. The name
is exported from the package's `__init__.py` and is therefore public; the file is not. So you import
`from google.adk.tools.mcp_tool import to_mcp_server` and never from the module directly, because the
module may be renamed and the export is the contract.

**3. It has no documentation page.** Checked on 2026-09-05: `https://adk.dev/tools-custom/mcp-tools/`
covers ADK as an MCP client and hand-building a server around ADK tools, `https://adk.dev/mcp/` links
to the same page, and neither names this function. Its counterpart `to_a2a` **does** have a page, at
`https://adk.dev/a2a/quickstart-exposing/`. That asymmetry is a signal about maturity, and it also
means Principle 8 — never invent an API, verify against the docs — has to be satisfied by reading the
installed source instead.

**4. Its import is guarded, and the guard is silent.** This is the one that will actually cost you an
evening, and it is worth reading the code:

```text
__all__ = []

try:
  from ._agent_to_mcp import to_mcp_server
  from .conversion_utils import adk_to_mcp_tool_type
  # ... eight more imports ...
  __all__.extend([...])

except ImportError as e:
  import logging

  logger = logging.getLogger('google_adk.' + __name__)
  logger.debug('MCP Tool is not installed')
  logger.debug(e)
```

(Quoted as text rather than as Python because it is copied verbatim from the installed file, down to
the two-space indent and the single quotes, which are ADK's house style and not this repository's.)

**Line by line:**

- `__all__ = []` before the `try` is why a failure produces an *empty* package rather than a partial
  one. Nothing half-imports.
- One `try` around **ten imports**. Any `ImportError` anywhere in that chain — including from a
  transitive dependency four levels down — is caught by the same handler and produces the same
  outcome.
- `except ImportError` catches `ModuleNotFoundError` too, since it is a subclass. So a genuinely
  missing package and a broken one are indistinguishable here.
- `logger.debug(...)`, twice, at **DEBUG**. Under any ordinary logging configuration, including the
  default, those two lines go nowhere at all. The message *"MCP Tool is not installed"* is a
  reasonable guess by the library and it is not necessarily true — it is what the library says
  whatever the reason was.
- `logger.debug(e)` is the only place the real cause exists. Turn DEBUG on and you get it; leave it
  off, which is everybody, and the cause is gone.
- The failure your code then sees is `AttributeError` or `ImportError` about a **name**, several
  layers away from the package that was actually missing.

## Why Sutra needs it

Because Principle 14 says that if reality changes, the plan is amended first — and an experimental
API is reality announcing in advance that it intends to change.

Sutra is going to depend on this function in `sutra_mcp/agent_server.py`. Day 45's audit will read
that file. The honest way to depend on an experimental API is not to avoid it; it is to write down
what you are depending on, where you verified it, and what the fallback is. This part is that
writing-down, and the hub's §8 carries it as a dated list.

The import guard matters for a second, concrete reason. `mcp` is an **optional extra** of
`google-adk`. A deployment that installs `google-adk` without it gets a server that starts, imports
cleanly, and then fails at the line that calls `to_mcp_server` — with a message about a name rather
than about a package. Catching that at start-up rather than at first request is what
[6.2](6.2-red-before-you-serve.md) is for.

## The mechanism

`lab/guarded_import.py` reproduces the swallow deterministically, inside the working venv, by making
`import mcp` fail the way a machine without the extra does:

```python
BLOCKED = "mcp"


def block_mcp() -> None:
    """Make `import mcp` fail, the way a machine without the extra installed does."""
    real_import = builtins.__import__

    def guarded(name: str, *args: object, **kwargs: object) -> object:
        if name == BLOCKED or name.startswith(BLOCKED + "."):
            raise ModuleNotFoundError(f"No module named {BLOCKED!r}")
        return real_import(name, *args, **kwargs)  # type: ignore[arg-type]

    builtins.__import__ = guarded
    for loaded in [m for m in sys.modules if m == BLOCKED or m.startswith(BLOCKED + ".")]:
        del sys.modules[loaded]
    for loaded in [m for m in sys.modules if m.startswith("google.adk.tools.mcp_tool")]:
        del sys.modules[loaded]
```

**Line by line:**

- Replacing `builtins.__import__` is a blunt instrument and it is the right one here, because the
  failure has to happen **inside** ADK's `try` block rather than in this file. Any approach that
  raises in this module would not exercise the guard.
- `raise ModuleNotFoundError(...)` rather than `ImportError`, because that is the class Python
  actually raises for a missing package, and the whole point is that ADK's `except ImportError`
  catches it anyway — a subclass relationship most people have to look up.
- `name.startswith(BLOCKED + ".")` blocks submodules too. Blocking only the top-level name would let
  `from mcp.server.fastmcp import FastMCP` through on a cached parent.
- Deleting the already-loaded `mcp*` entries from `sys.modules` is necessary because Python caches
  modules, and `mcp` is genuinely installed here. Without this the block does nothing.
- Deleting the `google.adk.tools.mcp_tool*` entries forces ADK's `__init__.py` to run **again**, which
  is what re-executes the `try` block. Import side effects happen once per process; this is how you
  get a second one.
- `# type: ignore[arg-type]` with no explanation would be a code smell. The reason is that
  `builtins.__import__`'s real signature is not expressible with `*args: object`, and narrowing it
  would add four lines of typing to a lab script whose subject is not typing.

## When it breaks

The default arm, measured on 2026-09-05:

```text
arm: default (logging off)
module imported : google.adk.tools.mcp_tool
__all__         : []
what you get    : AttributeError: module 'google.adk.tools.mcp_tool' has no attribute 'to_mcp_server'
and by name     : ImportError: cannot import name 'to_mcp_server' from 'google.adk.tools.mcp_tool' (C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\.venv\Lib\site-packages\google\adk\tools\mcp_tool\__init__.py)
```

Read the last line as somebody meeting it for the first time. It names a file that **exists**, in a
package that **is installed**, and says a name is not in it. Every instinct that message triggers is
wrong: you go and look at the file, and the name is right there on line 19. You check your ADK
version, and it is correct. You check your spelling. The one thing the message does not say is that a
completely different package is missing.

Now the ablation, which is one logging call away:

```text
  google_adk.google.adk.tools.mcp_tool DEBUG: MCP Tool is not installed
  google_adk.google.adk.tools.mcp_tool DEBUG: No module named 'mcp'
arm: --debug (DEBUG logging on)
module imported : google.adk.tools.mcp_tool
__all__         : []
what you get    : AttributeError: module 'google.adk.tools.mcp_tool' has no attribute 'to_mcp_server'
and by name     : ImportError: cannot import name 'to_mcp_server' from 'google.adk.tools.mcp_tool' (...)
```

Two extra lines, and the second of them is the answer: `No module named 'mcp'`. (They appear above
`arm:` because logging goes to stderr and `print` to stdout, and the two streams are buffered
separately.)

💡 **The insight:** **a `try/except ImportError` around an optional feature converts a precise error
into a vague one, and the precision is only recoverable at DEBUG.** This is not an ADK failing — the
pattern is everywhere, because the alternative is a library that refuses to import at all when an
optional extra is missing. What it means for you is a habit: when a name that should exist does not,
turn DEBUG on before you do anything else.

## In production

**What a professional writes instead:** a start-up assertion. Before a served process accepts
traffic, it imports the symbol it needs and fails loudly if it is absent, with a message naming the
package to install. Three lines, and they convert *"the request failed"* into *"the deployment did
not happen"*. The same three lines are the first check in [6.2](6.2-red-before-you-serve.md)'s gate.

For the experimental half, what a professional writes is a **row**, not code: the symbol, the version
it was verified against, the date, where it was verified, and what happens if it changes. Sutra's
row lives in the hub's §8 and Day 45's audit reads it.

**What degrades at scale:** the number of experimental dependencies. One is a note in an ADR. Fifteen
across a codebase, each with its own upgrade risk and none of them tracked, is a library bump that
breaks four services for four different reasons. The scaling answer is a list — every experimental or
undocumented symbol the codebase depends on, in one file, checked at review time.

**The failure mode that only appears with real traffic:** the silent behaviour change. A version bump
that keeps the signature and changes what the function *does* — say, one ADK session per request
instead of per connection — passes every import check, every type check and probably every unit test,
and shows up as callers losing conversation context. `google-adk` is at `2.8.0` on PyPI while this
repository is pinned at `2.7.1`, checked 2026-09-05, and the honest position is that nobody has read
that diff. Nothing is bumped today, because a day pins only what it installs.

**The review comment a senior engineer leaves:** *"we are depending on an undocumented, experimental
function in a private module, and I am fine with that as long as it is written down. Add the version
and the verification date to the day's §8, put a start-up import check in the module so a missing
`mcp` extra fails the deploy instead of the first request, and pin `google-adk` exactly — an
experimental API behind a caret range is a version bump that changes behaviour with no diff in our
repository."*

**The interview question:** *"would you ship an experimental API?"* The honest answer: *"Yes, with
three things written down. Which symbol, which version I verified it against, and what I do if it
changes. In this case the function has no documentation page at all — its A2A counterpart does — so
the source is the specification, and I read it rather than a tutorial. The specific trap I would warn
about is the import guard: the whole export block sits in one `try/except ImportError` that logs at
DEBUG, so a missing optional package arrives as 'cannot import name X from a package that is plainly
installed'. I have hit that, and the fix was `No module named 'mcp'` two DEBUG lines away. So the
habit is to turn DEBUG on first, and the fix is a start-up import check so it fails the deploy rather
than the request."*
