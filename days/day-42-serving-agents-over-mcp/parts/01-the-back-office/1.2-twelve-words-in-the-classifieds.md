# 1.2 — Twelve words in the classifieds

## One-line answer

`to_mcp_server(agent)` is one function call that turns any ADK agent into a server object exposing
**exactly one tool**, and everything the outside world will ever know about your agent has to fit in
that tool's name and description.

## The story

You have been doing the same work for eleven years, and everybody who needs you already knows where
you are. Then you decide to put an advertisement in the classified pages, and the rate is by the
word. Twelve words.

You sit with a pencil and find out something uncomfortable. Eleven years of judgement, the jobs you
will not take, the ones you are better at than anyone in the district, the way you always ask two
questions before quoting — none of it fits. You write a version. You cross it out. You write another.

What finally goes in is a name, a trade and a phone number. That is the whole advertisement, and it
is now the only thing standing between eleven years of skill and a stranger deciding whether to
call. People who ring the wrong number ring it because of what you wrote. People who never ring, who
needed exactly you, did not ring because of what you wrote.

The work behind the advertisement is enormous. The advertisement is twelve words, and you only get
to write it once.

## The idea in plain language

**A server object** is a thing in memory that knows its own name, knows which operations it offers,
and knows how to answer a request for one of them. Day 34's
[1.2](../../../day-34-building-sutra-mcp-tools/parts/01-the-server-object/1.2-a-server-you-build-not-one-that-runs.md)
drew the line that matters: *building* a server is instant and returns to you, while *running* one
blocks forever because it sits in a loop reading requests. `build_server()` returns; `run()` does
not.

`to_mcp_server` is a **factory**: a function whose whole job is to construct an object and hand it
back. You give it an ADK agent, it gives you a `FastMCP` server object. Nothing starts. Nothing
listens. No model is called. You are still the one who decides when — and over which transport — the
server begins accepting requests.

The important part is what it puts *on* that server. Not one tool per tool the agent owns. **One
tool, full stop**, named after the agent, taking a single string argument called `request`, and
described by the agent's own `description` field.

That is the twelve-word advertisement. The agent behind it can call five tools, hand work to three
sub-agents, and run a dozen model turns. A caller reading `tools/list` sees a name and a sentence.

## Why Sutra needs it

Because this is the one line of Sutra's `sutra_mcp/agent_server.py` that does the work, and every
other decision today is downstream of it.

The module you write in §4 of the hub is small. It imports `build_desk()` — the function Day 27 told
you to write in `sutra/desk/skills.py`, which loads the skill shelf and returns the desk agent with
its toolset — and it calls `to_mcp_server` on something. **What that something is** is the decision
section 3 makes, and it is decided by what fits in the advertisement.

You meet the consequence again on Day 45, when the MCP audit reads every tool description Sutra
publishes and asks whether a stranger could use the tool correctly from the description alone. For
the two tools Day 34 put on the wire that is a fair question with a checkable answer. For a served
agent it is the *entire* interface.

## The mechanism

The function lives in `google.adk.tools.mcp_tool`. Here is its real signature, copied from the
installed package at `.venv/Lib/site-packages/google/adk/tools/mcp_tool/_agent_to_mcp.py` on
2026-09-05:

```python
from google.adk.tools.mcp_tool import to_mcp_server

server = to_mcp_server(
    agent,  # any BaseAgent - the whole loop goes behind one name
    name=None,  # the MCP server name AND the tool name; defaults to agent.name
    instructions=None,  # optional text the MCP host may show to its own model
    runner=None,  # bring your own Runner; otherwise one is built for you
)
```

**Line by line:**

- `from google.adk.tools.mcp_tool import to_mcp_server` — the public import path. It resolves to
  `_agent_to_mcp.py`, whose leading underscore says the *module* is private and the *name* is not.
  Part [6.1](../06-in-production/6.1-the-school-in-two-sheds.md) is about what that
  underscore, and the `@experimental` decorator above the function, actually cost you.
- `agent` is the only positional argument. Its type is `BaseAgent`, not `LlmAgent`, so a plain
  Python class that yields events works exactly as well as one with a model behind it. Every lab
  script in this day exploits that, which is why the whole day costs zero generations.
- Everything after `agent` is **keyword-only** — the signature has a bare `*` before them. You cannot
  write `to_mcp_server(agent, "sutra-desk")`; it raises `TypeError`. That is deliberate on ADK's
  part: three optional arguments of which two are strings is exactly where positional calls go wrong.
- `name` sets **two** things, not one: `FastMCP(name=tool_name, ...)` and
  `server.add_tool(..., name=tool_name, ...)`. The server and its single tool share a name. If you
  pass nothing it falls back to `agent.name`, then to the literal `"adk_agent"`. Day 34's
  [1.3](../../../day-34-building-sutra-mcp-tools/parts/01-the-server-object/1.3-the-name-is-an-identity.md)
  argued that a server name is an identity a client writes down; here that identity is also the tool
  name a model routes on, so one careless string does two kinds of damage.
- `instructions` goes to `FastMCP(instructions=...)`. It is server-level prose, separate from the
  tool description, and a host is free to ignore it. Leave it `None` and the server reports
  `instructions: None`, which is what `lab/served_surface.py` prints.
- `runner=None` is the argument you will care about most and the one this part will not spend:
  [1.3](1.3-the-hall-that-came-with-its-own-chairs.md) is entirely about what gets built when you
  leave it as `None`.
- Nothing here starts anything. The returned object is a `FastMCP` instance; you choose the
  transport later with `server.run(transport="stdio")` or
  `server.run(transport="streamable-http")`.

Where does the single tool come from? Straight out of the ADK source, and it is worth reading
because there is no documentation page to read instead:

```python
tool_name = name or agent.name or "adk_agent"
server = FastMCP(name=tool_name, instructions=instructions)


async def call_agent(request: str, ctx) -> list[mcp_types.ContentBlock]:
    return await _run_agent(agent_runner, request, ctx, sessions)


server.add_tool(
    call_agent,
    name=tool_name,
    description=agent.description or f"Run the {tool_name} agent.",
    structured_output=False,
)
```

**Line by line:**

- `tool_name = name or agent.name or "adk_agent"` is a three-step fallback in one line, and the third
  step is unreachable. `BaseAgent` is a pydantic model that validates its own name, so an empty one
  never gets as far as this function — constructing `BaseAgent(name="")` raises
  `pydantic_core._pydantic_core.ValidationError: ... Value error, Node name '' must be a valid Python
  identifier.` Measured on 2026-09-05. That matters less as trivia than as a habit: when you read a
  library's fallback chain, check whether the last link can ever be taken, because a fallback nobody
  can reach is a fallback nobody has tested.
- `FastMCP(...)` is the same server class Day 34's `build_server()` constructs. **You are not getting
  a different kind of server.** Everything Day 34 taught about `tools/list`, `tools/call`, `isError`
  and the caching hints applies unchanged; there is simply one tool on it instead of two.
- `async def call_agent(request: str, ctx)` is the whole public interface. One parameter the caller
  fills, typed `str`. `ctx` is injected by the SDK and never appears in the schema — the framework
  strips context parameters out before it builds the JSON Schema, which is why
  [2.1](../02-what-crosses-the-counter/2.1-the-enquiry-slip-with-one-box.md) shows exactly one
  property.
- `description=agent.description or f"Run the {tool_name} agent."` is the sentence in the
  advertisement. If your agent has no `description`, every caller in the world reads *"Run the
  sutra_desk agent."*, which tells them nothing. Writing that field is not documentation hygiene
  today; it is the interface.
- `structured_output=False` turns off the machinery Day 34's
  [3.3](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.3-one-call-one-result.md)
  measured, where a return type annotation produces an `outputSchema` and the same text arrives twice.
  A served agent returns content blocks and nothing else, so `outputSchema` is `null`.
- `add_tool` rather than the `@server.tool()` decorator, because the function being registered is a
  closure built at call time, not a module-level definition. Same registration, different spelling.

And the whole of `sutra_mcp/agent_server.py`, in the smallest honest form:

```python
"""Sutra's desk, served over MCP. One tool, one string, one answer."""

from google.adk.tools.mcp_tool import to_mcp_server
from mcp.server.fastmcp import FastMCP

from sutra.desk.skills import build_desk

SERVED_AGENT_NAME = "sutra_desk"


def build_agent_server() -> FastMCP:
    """Build the server that exposes the desk agent. Starts nothing."""
    return to_mcp_server(build_desk(), name=SERVED_AGENT_NAME)


if __name__ == "__main__":
    build_agent_server().run(transport="stdio")
```

**Line by line:**

- `from sutra.desk.skills import build_desk` reaches for Day 27's builder rather than constructing an
  agent here. One agent, two doors: the same object `uv run adk web sutra/desk` runs is the one
  strangers now reach. Two agents that drift apart is a desk that answers differently depending on
  who asked.
- `SERVED_AGENT_NAME` is a module constant because it is an identity, exactly as Day 34's
  `SERVER_NAME` is. It appears in the served tool's name, in the server's name, and in every log
  line a caller correlates against. A string literal buried in a function call is a name nobody can
  grep for.
- `build_agent_server() -> FastMCP` returns; it does not run. Day 34's
  [1.2](../../../day-34-building-sutra-mcp-tools/parts/01-the-server-object/1.2-a-server-you-build-not-one-that-runs.md)
  is the argument, and it holds here for the same reason: a function that blocks forever cannot be
  imported by a test.
- `build_desk()` is called **inside** the function, not at import time. Day 27's builder walks the
  skills folder and raises `RuntimeError` if a skill will not load. At import time that is an
  unimportable module; inside the function it is a failed build with a readable reason.
- `run(transport="stdio")` under `if __name__ == "__main__":` and nowhere else. This is the *only*
  line that blocks, and it is the only line that must never execute on import.
- Note what is **not** here: no call into `sutra_mcp/server.py`, and no line added to
  `build_server()`. That break with the convention every day since 34 has followed is real, it is
  deliberate, and [1.4](1.4-the-counter-by-the-side-door.md) is the argument for it.

*Verified against the installed package rather than a documentation page: `to_mcp_server` is **not
documented on adk.dev** as of 2026-09-05. `https://adk.dev/tools-custom/mcp-tools/` covers ADK as an
MCP client and hand-building a server around ADK tools, and `https://adk.dev/mcp/` links to the same
page; neither names this function. The authority for every line above is
`.venv/Lib/site-packages/google/adk/tools/mcp_tool/_agent_to_mcp.py`, read on 2026-09-05. See
[6.1](../06-in-production/6.1-the-school-in-two-sheds.md) for what to do about that.*

## When it breaks

Get the keyword-only rule wrong and Python stops you immediately:

```text
TypeError: to_mcp_server() takes 1 positional argument but 2 were given
```

That is the friendly failure. Here is the unfriendly one. Build a server from an agent with no
`description`, and everything works:

```text
{
  "name": "sutra_desk",
  "description": "Run the sutra_desk agent.",
  "inputSchema": {"properties": {"request": {"title": "Request", "type": "string"}}, ...}
}
```

Nothing raised. Nothing warned. The tool is on the wire and it is useless, because the only sentence
a stranger's model gets in order to decide whether this tool answers their question is a sentence
ADK wrote as a fallback. Day 34's
[2.2](../../../day-34-building-sutra-mcp-tools/parts/02-function-to-declaration/2.2-the-schema-is-all-they-get.md)
made this argument about a function's docstring. Here it is worse, because a function at least has
parameter names to hint with, and this one has `request: str`.

The third break is a name collision, and it is silent on your side entirely. Your server is called
`sutra_desk`. So is the tool. A host that mounts your server alongside another one that also exposes
something called `sutra_desk` now has two identical names in one list, and Day 40's
[6.1](../../../day-40-filtering-and-allowlists/parts/06-the-posture/6.1-two-servers-one-tool-name.md)
is what happens next. You will never see it, because it happens in someone else's process.

## In production

**What a professional writes instead:** the description is written *first*, before the agent is
served, and it is written for a model that has never met you. It says what kinds of question the
agent answers, gives one example of a question that fits and one that does not, and states the two
operational facts a caller cannot discover — that a call runs a model and that calls are not free to
retry. Then the agent's `description` field is edited until it says that, and only then is
`to_mcp_server` called.

**What degrades at scale:** the fallback description. One agent with no description is a
documentation bug. Twenty served agents across an organisation, each defaulting to *"Run the X
agent."*, is a tool catalogue that a routing model cannot distinguish between at all, and the
symptom is not an error — it is a model that picks the wrong service and produces a plausible wrong
answer.

**The failure mode that only appears with real traffic:** description drift. The agent's instruction
grows, its skills change, it starts refusing a category of question it used to answer — and the
`description` string, which is a different line in a different file, does not move. The advertisement
is now a promise the shop stopped keeping, and only the callers find out.

**The review comment a senior engineer leaves:** *"the tool description is `Run the sutra_desk
agent.` — that is ADK's fallback, which means nobody wrote one. This is the entire public interface
of a service that spends our model quota. Write the description, put a query that fits and a query
that does not in it, and add a test that fails if it is ever the fallback string."*

**The interview question:** *"you have wrapped an agent as an MCP tool. What is its API?"* The honest
answer: *"One string in, content blocks out, and a sentence of prose. That is genuinely all of it —
no per-field schema, no typed arguments, no output schema, because the framework turns structured
output off. So the description is not documentation, it is the interface, and I would treat it the
way I treat a public function signature: reviewed, tested against, and versioned. The specific test I
would write is that the description is never the framework's fallback and never shorter than a
sentence naming one query that fits and one that does not."*
