# 1.3 — The hall that came with its own chairs

## One-line answer

Leaving `runner=None` makes `to_mcp_server` build you a whole runtime — sessions, memory, artifacts
and credentials, all in memory, all forgotten on restart, and every caller in the world logged in as
the same user.

## The story

You book a hall for a family function. The rate is per day, you pay it, and you turn up on the
morning with the food and the decorations.

The hall already has chairs. A hundred and twenty of them, stacked at the back, and they came with
the booking. There is a table by the door, a register, and a man who writes down who comes in. None
of that was on the form you filled in. Somebody, at some point, decided a hall needs chairs, and now
those are the chairs.

They are fine. They are also not your chairs. The register goes in a drawer at the end of the day
and nobody keeps it. The man at the door writes *"guest"* for everyone, because he does not know any
of you and it is not his job to. And when you ask, on the way out, whether you can have the list of
who attended, there is no list, because the register was for the hall's purposes and not for yours.

You did not choose any of it. You did not object to any of it either — you just never thought about
it, and the assumptions came with the room.

## The idea in plain language

An ADK **`Runner`** is the object that actually executes an agent. You have used it since
[Day 5](../../../day-05-first-adk-agent/parts/04-the-runner/4.1-the-runner-is-your-run-loop.md): you hand
it an agent, a user id and a session id, and it drives the think-act-observe loop, storing every
event it produces.

A `Runner` needs four services to do that:

| Service | What it holds | Why it exists |
| --- | --- | --- |
| `session_service` | the events of one conversation | so turn two can see turn one |
| `memory_service` | facts that outlive one conversation | so next week can see last week |
| `artifact_service` | files the agent produced or was given | so a generated report has somewhere to live |
| `credential_service` | tokens the agent's tools authenticated with | so a tool does not re-authenticate every call |

When you call `to_mcp_server(agent)` and leave `runner=None`, **ADK builds a `Runner` for you and
picks all four**. It picks the in-memory implementation of every one, and it picks the app name and
the user id too. You did not fill any of that in on the form.

## Why Sutra needs it

Because those choices are the difference between "the desk is served" and "the desk is served
correctly", and three of them will be wrong for Sutra by Day 47.

Day 46 draws the line between a **session** — one conversation — and **memory** — what survives it.
Day 47 makes sessions durable by putting them in a database. Both of those days are about replacing
exactly the two services this function chose for you without asking. If you serve the desk today
with `runner=None` and forget, then on Day 47 you will make sessions durable everywhere in Sutra
*except* behind the MCP door, and nothing will tell you.

The third wrong choice is more urgent. Every caller becomes the same user, and section 3 uses that
fact to decide what Sutra is willing to serve at all.

## The mechanism

Here is `_build_runner`, the private function that runs when you pass no runner. Copied from
`.venv/Lib/site-packages/google/adk/tools/mcp_tool/_agent_to_mcp.py` on 2026-09-05:

```python
_MCP_USER_ID = "mcp_user"


def _build_runner(agent: BaseAgent) -> Runner:
    """Builds a Runner for the agent using in-memory services."""
    return Runner(
        app_name=agent.name or "adk_agent",
        agent=agent,
        artifact_service=InMemoryArtifactService(),
        session_service=InMemorySessionService(),
        memory_service=InMemoryMemoryService(),
        credential_service=InMemoryCredentialService(),
    )
```

**Line by line:**

- `_MCP_USER_ID = "mcp_user"` is a module constant, and there is no argument anywhere in
  `to_mcp_server` that changes it. **Every request from every caller over every connection runs as
  the user `mcp_user`.** Not "defaults to"; there is no other value. Whatever identity the caller
  presented at the transport, it is gone by the time the agent runs.
- `app_name=agent.name or "adk_agent"` is the key the session store is filed under. Day 5's
  [4.1](../../../day-05-first-adk-agent/parts/04-the-runner/4.1-the-runner-is-your-run-loop.md) made the
  point that changing `app_name` orphans every existing session. Here it is derived from the agent's
  name, which means **renaming your agent silently orphans every session behind the served door**.
- `InMemorySessionService()` keeps conversations in a Python dictionary in this process. Restart the
  server and every conversation is gone. There is no file, no database, no eviction policy and no
  size limit, which is also a slow leak — [6.2](../06-in-production/6.2-red-before-you-serve.md)
  puts that in the gate.
- `InMemoryMemoryService()` is the same story for the longer-term half. Day 46 is where the two are
  told apart properly; the relevant fact today is that both were chosen for you.
- `InMemoryArtifactService()` matters more than it looks, because
  [2.2](../02-what-crosses-the-counter/2.2-the-interpreter-who-relays-the-last-sentence.md) shows
  that an agent *can* return an image through this door. The bytes come back inline in the reply, and
  nothing is kept.
- `InMemoryCredentialService()` triggers an experimental warning of its own the moment it is
  constructed — you will see `[EXPERIMENTAL] InMemoryCredentialService` on stderr in every lab
  script in this day. Two experimental features stacked is worth knowing about before you deploy.
- Note what the function is *not*: it is not configurable. There is no
  `to_mcp_server(agent, session_service=...)`. The only way to change any of the four is to build
  the whole `Runner` yourself and pass it as `runner=`.

Which is exactly what you do when you want your own chairs:

```python
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService

from sutra.desk.skills import build_desk

SERVED_AGENT_NAME = "sutra_desk"


def build_agent_server() -> FastMCP:
    """The desk, served, with a Runner Sutra chose rather than inherited."""
    agent = build_desk()
    runner = Runner(
        app_name=SERVED_AGENT_NAME,
        agent=agent,
        session_service=InMemorySessionService(),  # TODO(me): Day 47 replaces this
        artifact_service=None,
        memory_service=None,
        credential_service=None,
    )
    return to_mcp_server(agent, name=SERVED_AGENT_NAME, runner=runner)
```

**Line by line:**

- `app_name=SERVED_AGENT_NAME` pins the session key to a constant you control, so renaming the agent
  no longer orphans sessions. This is the smallest of the four fixes and the one most likely to save
  you an afternoon.
- The `TODO(me)` on `session_service` is deliberate and stays unsolved. Day 47 is the day that
  swaps `InMemorySessionService` for a database-backed one; today's job is to make sure there is a
  line here for Day 47 to change, instead of a decision buried inside a library.
- `artifact_service=None` and the two beside it are a decision, not an omission: this agent produces
  no files, remembers nothing across conversations, and authenticates no tools, so it gets none of
  the three. Handing a served surface a memory service it does not use is a cache with no eviction
  policy attached to a public endpoint.
- `to_mcp_server(agent, ..., runner=runner)` — the same agent object goes to both, because the
  `Runner` holds a reference to it and `to_mcp_server` reads `agent.description` and `agent.name`
  for the declaration. Passing two different agent objects here builds a server that describes one
  agent and runs another, and nothing checks.
- What this does **not** fix is `mcp_user`. That constant is read inside `_run_agent`, not inside
  `_build_runner`, so bringing your own `Runner` does not buy you per-caller identity.
  [2.3](../02-what-crosses-the-counter/2.3-the-table-you-may-leave-your-books-on.md) is what that
  costs and [3.3](../03-tool-or-peer/3.3-the-guillotine-and-the-press.md) is what Sutra does about
  it.

## When it breaks

Run `lab/connections.py`. It serves a five-line agent that answers with its own bookkeeping instead
of with an answer, so you can read the runtime's choices off the output rather than trusting this
page:

```text
connection 1 call 1: session=8c3283a4 app=sutra_desk user=mcp_user turns=1
connection 1 call 2: session=8c3283a4 app=sutra_desk user=mcp_user turns=2
connection 2 call 1: session=38e14613 app=sutra_desk user=mcp_user turns=1
connection 2 call 2: session=38e14613 app=sutra_desk user=mcp_user turns=2
```

Read the `user=` column. Four calls, two different callers, one identity. Now imagine the desk agent
had a tool that wrote to the archive and an instruction saying *"only close a ticket the requester
raised"*. It cannot tell who the requester is. Not "it forgot to check" — the information was
destroyed at the door, and the agent's instruction is asking a question the runtime cannot answer.

The second break is quieter and arrives on a restart:

🎬 **The scene:** a caller has been having a useful multi-turn conversation with your served desk.
Six exchanges in, it is going well.

😬 **The naive fix:** you deploy a small change to the server and restart it.

💥 **Why it fails:** `InMemorySessionService` was a dictionary in the old process. The new process
has an empty one. The caller's next `tools/call` opens a new connection, gets a brand-new ADK
session, and the agent answers the seventh question as if it were the first. There is no error. The
caller's model, which has the whole conversation in its own context, reads an answer that ignores
five turns of established context and concludes the desk is being unhelpful.

💡 **The insight:** **in-memory state behind a network boundary is not "simple", it is undeclared.**
Nothing in the protocol lets you say *"my sessions do not survive a restart"*, so the caller has no
way to find out except by being surprised. If the conversation matters, the store has to be
somewhere a restart cannot reach — which is Day 47 — and if it does not matter, say so in the
description so nobody builds on it.

## In production

**What a professional writes instead:** an explicit `Runner`, always, with each of the four services
either named or explicitly `None`, and a comment beside each one saying why. The rule is not "never
use the default"; it is "never let a default cross a network boundary without somebody having read
it". A default inside your process is a convenience. A default behind a public endpoint is a
decision you made without noticing.

**What degrades at scale:** `InMemorySessionService` under real traffic is an unbounded dictionary
keyed by connection. Nothing evicts. A long-lived server accumulating one session per connection,
with every event of every conversation in it, is a memory leak whose growth rate is your popularity.
The `WeakKeyDictionary` that maps connections to sessions drops its *entry* when a connection is
collected — but the session itself is still in the session service.

**The failure mode that only appears with real traffic:** two instances. The moment this server runs
behind anything that load-balances, a caller's second call can land on the instance that never saw
their first. In-memory sessions make that invisible rather than loud: instead of an error, the caller
gets a fresh conversation and a slightly worse answer. Day 43 is the whole day about that, and it
starts from exactly this default.

**The review comment a senior engineer leaves:** *"we are serving this with `runner=None`, which
means a library picked our session store, our memory store and our user id. Two of those we replace
in five days and the third we cannot replace at all. Build the `Runner` here so the session line is
one line I can change, and put a comment on `mcp_user` explaining that per-caller identity does not
survive this door — because somebody is going to write an instruction that depends on it."*

**The interview question:** *"you wrapped an agent as an MCP server in one line. What did that one
line decide for you?"* The honest answer: *"Four services and an identity. It built a `Runner` with
in-memory sessions, memory, artifacts and credentials, keyed the sessions on the agent's name, and
ran every request as a hard-coded user id called `mcp_user`. Three of those are fine for a demo and
wrong for anything real: the sessions vanish on restart and cannot survive two instances, and the
user id means an agent behind that door can never enforce a per-caller rule. I pass my own `Runner`
so the session store is one line I can point at, and I treat the fixed user id as a hard constraint
on what I am willing to put behind that door at all."*
