# 4.1 — The kettle and the car

## One-line answer

A plain MCP tool costs one database read per call and a served agent costs **one generation to decide
plus one more for every tool result it reads back**, so the same `tools/call` is either free or three
per cent of a free-tier day depending on what is behind it.

## The story

The office has a kettle by the window. Nobody books it, nobody logs it, and nobody has ever had a
conversation about kettle policy. You want tea, you switch it on. If four people want tea at once,
they wait ninety seconds and then everyone has tea.

The office also has a car.

There is a book for the car. You write your name, where you are going and when you will be back. If
somebody else has it on Tuesday morning, you are not going anywhere on Tuesday morning — there is no
version of the arrangement where two people both take it and it works out. There is a fuel budget
that runs out. And the whole apparatus of the book, the budget and the arguments exists for exactly
one reason: **the car is a limited thing and the kettle is not.**

Nobody sat down and decided the kettle needed no policy. The policy is absent because the constraint
is absent. The moment something becomes limited, the book appears.

## The idea in plain language

Day 24 established the unit this curriculum counts in. Not dollars — **requests**. Free-tier Gemini
gives you a fixed number of `generateContent` calls per day, and once they are gone they are gone
until the day rolls over, regardless of how short the prompts were.

Sutra's number, read off a live 429 on
[Day 2](../../../day-02-llm-mechanics/parts/01-first-contact/1.5-the-only-door-429.md) and
recorded in `docs/PACKAGES.md`, is **20 generations per day** on `gemini-3.7-flash`. There is no
published quota table; that is the measured figure.

Now count what one `tools/call` spends, in each of the two things you can put behind it.

**A plain MCP tool.** Day 34's `lookup_ticket` reads a dictionary — Day 39 made it read SQLite — and
returns. **Zero generations.** Not "a small number". Zero. You can call it ten thousand times a day
on the free tier and the free tier does not know.

**A served agent.** The `Runner` sends the request to the model, which decides what to do. That is
one generation. If it decides to call a tool, the tool runs locally, and the result goes back to the
model, which decides again. That is a second generation. Each further tool result is one more. The
final answer comes out of the last one.

So the arithmetic is:

```text
generations per call = 1 + (number of tool round-trips)
```

A question the model can answer from its instruction alone: 1. A question needing one knowledge-base
search: 2. Sutra's ordinary desk answer, which looks up a ticket and then searches the knowledge
base: 3.

## Why Sutra needs it

Because the tool list Day 34 published and the tool list `agent_server.py` publishes look identical
to a caller and differ by a factor no caller can see.

[1.4](../01-the-back-office/1.4-the-counter-by-the-side-door.md) argued for two endpoints on the
grounds of cost profile. This is that cost profile, with numbers in it. And it is the argument that
Day 45's audit has to be able to check: a server whose tools all cost zero can be rate-limited by
politeness, and a server where one call is three generations out of twenty needs a limit that exists
in code.

It also decides something about Sutra's own working day. You have twenty generations. Every one spent
answering a stranger's question is one you do not have for building the next day of this curriculum.
That is not a metaphor for a budget; it is the budget.

## The mechanism

`lab/price.py` is arithmetic and nothing else — no model, no server, no network:

```python
# Free-tier Gemini, read off a live 429 on Day 2 and recorded in docs/PACKAGES.md.
# There is no published quota table; this is the measured number.
DAILY_GENERATIONS = 20
MODEL = "gemini-3.7-flash"

# One served call = one generation to decide, one more to read each tool result back.
# A desk answer that looks up a ticket and then searches the KB is three.
TOOL_ROUND_TRIPS = [0, 1, 2, 3]


def generations_per_call(round_trips: int, *, tools_only: bool) -> int:
    """How many model generations one `tools/call` spends."""
    if tools_only:
        return 0
    return 1 + round_trips
```

**Line by line:**

- `DAILY_GENERATIONS = 20` is a measured constant with its provenance in the comment above it, not a
  guess. Principle 7 applies to quotas exactly as it applies to versions: the number came from a
  refusal this repository actually received, and the comment says so, so the next reader can check.
- `MODEL` is here even though nothing calls it, because a quota is per model. Moving to a different
  free-tier model changes `DAILY_GENERATIONS`, and a constant sitting beside the number it governs is
  how that stays true.
- `TOOL_ROUND_TRIPS = [0, 1, 2, 3]` is the range of real behaviour, not an abstraction. Zero is a
  refusal or a canned answer, one is a single knowledge-base search, three is the desk working a
  ticket properly.
- `*, tools_only: bool` is keyword-only so that no call site ever reads `generations_per_call(2,
  True)`, where the second argument means nothing to a reader.
- `return 0` in the `tools_only` branch is the ablation, and it is a *fact* rather than a
  simplification: Day 34's tools call no model at all, so the honest number is zero.
- `return 1 + round_trips` is the whole model. It is deliberately the simple version — it assumes one
  generation per decision and no retries, no reflection loop and no parallel tool calls, all of which
  make it worse rather than better. A cost model that errs optimistic and still fails the budget is a
  stronger argument than one that errs pessimistic.

Run it and read the third column, which is the one that matters:

```text
arm: served agent on gemini-3.7-flash
free-tier budget: 20 generations per day

round-trips  gens/call  calls the budget buys
          0          1                     20
          1          2                     10
          2          3                      6
          3          4                      5
```

Twenty calls if the agent never uses a tool. **Six** if it does what Sutra's desk actually does.

Now the ablation, which is the identical script with one flag, pricing the identical traffic as Day
34's plain tools:

```text
arm: plain MCP tools (Day 34)
free-tier budget: 20 generations per day

round-trips  gens/call  calls the budget buys
          0          0              unlimited
          1          0              unlimited
          2          0              unlimited
          3          0              unlimited
```

The word in that column is not a rounding. A tool that reads a database is not *cheap* compared with a
served agent; it is a different kind of thing, and the free tier has no opinion about it at all.

## When it breaks

The break is that nothing on the wire distinguishes the two columns.

Here is a caller's `tools/list`, with one tool from each server, side by side as a routing model sees
them:

```text
search_kb          Find one knowledge-base article matching a symptom. Returns id and title.
sutra_kb_answerer  Answers one self-contained question from Sutra's internal support knowledge
                   base and cites the article id it used.
```

There is no `cost` field. There is no `expensive: true`. The `Tool` type has nine fields and none of
them is a price — [4.3](4.3-the-notice-on-the-ration-shop-board.md) prints the list and finds the one
field that comes closest, `annotations.idempotentHint`, sitting at `null` because `to_mcp_server`
never sets it. Day 41's
[1.3](../../../day-41-capabilities-and-mcp-apps/parts/01-what-a-server-declares/1.3-an-extension-is-a-capability-with-a-surname.md)
established that you cannot invent a field of your own and have it mean anything.

So a model choosing between those two lines chooses on prose. And the second line sounds better,
because it promises an *answer* rather than a *search result*. The expensive one wins on wording,
every time, and the caller's model has no idea it just spent three of your twenty.

The failure that follows is not an error. It is a 429 four hours later, in a completely different
part of your day, when you go to run something of your own —
[5.3](../05-failure-lab/5.3-the-price-sticker-underneath.md) is what that looks like from the
caller's side.

## In production

**What a professional writes instead:** the cost goes in the description, in the caller's units, and
a counter goes in the server. The description sentence is the honest half of an interface that has no
field for this. The counter is the enforceable half: a per-day and per-caller-connection tally that
refuses before it spends, so the budget is protected by code rather than by the wording of a
sentence.

**What degrades at scale:** the assumption that one call is one unit of anything. A served agent's
cost is a function of the *question*, which is a function of the caller. A caller sending
well-formed, self-contained questions costs you two generations each. A caller pasting an entire
ticket thread and asking the agent to work it out costs four or five, and the difference is invisible
in every metric that counts requests.

**The failure mode that only appears with real traffic:** cost drift with no code change. Improve the
agent's instruction so it double-checks its answer against a second article, and every call gains a
round-trip. Your per-call cost went from three to four — a third more — and the diff that did it was
one sentence of English in a prompt with no number anywhere in it.

**The review comment a senior engineer leaves:** *"this tool costs three model calls and the one
above it costs zero, and a caller's model picks between them by reading two sentences. Put the cost
in the description and put a counter in front of the runner. We are on twenty generations a day; six
calls from one enthusiastic caller is our entire budget, and the first thing we will notice is our own
work failing."*

**The interview question:** *"what does it cost to serve an agent as a tool?"* The honest answer:
*"One generation to decide, plus one for every tool result it reads back — so one to four for a
typical support answer, against a plain tool's zero. The thing that makes it dangerous rather than
just expensive is that the protocol has no field for it. A caller's routing model sees two
descriptions and picks the one that sounds more capable, which is always the expensive one. So the
cost has to go in the description, because that is the only channel, and a counter has to go in front
of the runner, because a description is not enforcement. And I would track generations per call as a
metric, since a one-sentence change to a prompt can raise it by a third with no number in the diff."*
