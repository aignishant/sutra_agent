# 2.2 — The toolkit you did not need

## One-line answer

ADK's own error message tells you to install `google-adk[extensions]`, which brings Kubernetes,
Docker, two agent frameworks and a search index along with the one library you actually want — so
you install `litellm` directly, pin it exactly, and write down why.

---

## The story

A tap is dripping. You need one washer and a spanner to get the tap apart.

At the shop, the man shows you a boxed toolkit. Sixty-four pieces, plastic case with moulded slots,
a picture of a smiling man on the front. It is cheaper than buying the spanner and a few other things
separately, and it has the spanner in it, so you take it.

Two years later, here is where that box is: on top of the cupboard, taking up as much room as a small
suitcase. You have used four of the sixty-four pieces. Twelve of them are for a kind of screw head
that does not exist in your house. The hacksaw blade has gone rusty because it came without oil and
nobody ever oiled it.

And the spanner — the one thing you actually went in for — is a slightly worse spanner than the one
you would have bought on its own, because it was designed to fit a slot in a moulded case.

Nothing about this was a scandal. It was the sensible-looking option in the shop, and the cost
arrived later, in small amounts, from a direction you were not looking at.

Software dependencies do exactly this, and today ADK's own error message is the man in the shop.

## The idea in plain language

When you tried a provider string without the library,
[1.1](../01-one-model-field/1.1-a-name-is-a-lookup.md) showed you this:

```text
ValueError: Model groq/llama-3.3-70b-versatile not found.

Provider-style models (e.g., "provider/model-name") require the litellm package.
Install it with: pip install google-adk[extensions]
Or: pip install litellm>=1.75.5
```

Two suggestions, and they are not equivalent. Here is what `extensions` actually contains, read from
the installed package's metadata rather than from a page:

| Package | What it is |
| --- | --- |
| `litellm` | **the one you want** |
| `langgraph`, `langgraph-checkpoint` | another agent framework |
| `crewai[tools]` | a third agent framework |
| `kubernetes`, `k8s-agent-sandbox` | a Kubernetes client |
| `docker` | a Docker client |
| `openai`, `anthropic` | two provider SDKs |
| `google-cloud-firestore` | a Google Cloud database client |
| `llama-index-embeddings-google-genai`, `llama-index-readers-file` | a retrieval framework |
| `beautifulsoup4`, `lxml`, `nltk`, `pypika`, `toolbox-adk` | HTML parsing, XML, NLP, SQL building, a toolbox |

Seventeen top-level packages, and their dependencies, to get one.

**So take the second suggestion.** ADK's own documentation page for LiteLLM agrees — it says
`pip install "litellm>=1.84"` with no extra at all (`adk.dev/agents/models/litellm/`, checked
2026-08-26), and the import guard only checks whether `litellm` can be found. Installing it directly
satisfies everything.

There is one honest wrinkle worth naming rather than smoothing over. The error message says
`litellm>=1.75.5`. The package metadata for the `extensions` extra says `litellm>=1.84`. The
documentation page says `litellm>=1.84`. **Three numbers in the same project, two of them agreeing.**
Nothing is broken — the error's floor is simply older than the extra's — and this is a good small
lesson in why Principle 7 says to look things up rather than to trust the first number you are shown.

### Pinning it

Principle 7: never invent a version. Look it up, pin it exactly, record the date.

```bash
curl -s https://pypi.org/pypi/litellm/json | python -c "import sys,json; d=json.load(sys.stdin)['info']; print(d['version'], d['requires_python'])"
```

**Line by line:**

- `curl -s` — silent, so the progress bar does not end up in your terminal. PyPI's JSON API needs no
  key and no account.
- `python -c` reading from standard input — three fields out of a large document, using the standard
  library, with nothing installed to do it.
- `d['version']` — the **latest** version, which is what you are about to pin. Whatever this prints
  today is what goes in `pyproject.toml`; if it disagrees with what is written below, yours is the
  correct one and this document is out of date.
- `d['requires_python']` — printed because a package whose Python floor is above yours will fail to
  resolve, and finding that out from one line beats finding it out from a resolver error.

Observed on **2026-08-26**: `1.98.0` and `<3.15,>=3.10`. The floor is below this project's 3.12, so
it resolves.

```bash
uv add "litellm==1.98.0"
```

**Line by line:**

- `uv add` rather than `uv pip install` — `add` writes the pin into `pyproject.toml` and updates
  `uv.lock`, which is what makes the environment reproducible for anybody who clones this repository.
  `pip install` changes only your machine.
- `==` and not `>=` — an exact pin, per `CLAUDE.md`. The next section explains why that matters more
  for this package than for most.
- A **runtime** dependency rather than a dev one, because Day 70's Quota-Router will route production
  traffic through it. Sutra's default path stays Gemini-native; this is the lane the router needs.

Then the row in `docs/PACKAGES.md`, the same day, with the date you looked it up.

### Why the exact pin matters here specifically

ADK's own documentation page carries a security note:

> *"Unauthorized code was identified in LiteLLM versions 1.82.7 and 1.82.8 (March 2026). Update
> immediately if using ADK Python with `eval` or `extensions` extras."*
> (`adk.dev/agents/models/litellm/`, checked 2026-08-26)

Read what that means rather than only that it is alarming. Two specific published versions of a
widely-used package contained code that should not have been there. Anybody whose dependency said
`litellm>=1.80` and who installed during that window got them, without changing a line of their own
code and without any signal that anything had happened.

An exact pin does not make you safe. What it does is make the question *answerable*: with
`litellm==1.98.0` in `pyproject.toml` and a dated row in `docs/PACKAGES.md`, "were we ever on an
affected version?" is a lookup. With `>=`, it is an investigation, and the honest answer is usually
"we do not know."

That is the same argument `uv.lock` makes for transitive dependencies, and it is why this project
commits the lockfile.

## The mechanism

The whole thing is three commands and one row, and the interesting part is the before-and-after:

```bash
# 1 - before: the registry cannot resolve three correct strings
uv run python days/day-09-four-free-providers/lab/resolve.py

# 2 - look the version up, then pin it
curl -s https://pypi.org/pypi/litellm/json | python -c "import sys,json; d=json.load(sys.stdin)['info']; print(d['version'], d['requires_python'])"
uv add "litellm==1.98.0"

# 3 - after: the same script, three lines different
uv run python days/day-09-four-free-providers/lab/resolve.py
```

**Line by line:**

- Step 1 is not ceremony. Running the script **before** the install is what makes step 3 mean
  something; a reader who only ever sees the working output has learned nothing about what changed.
- Step 2's lookup comes before the `add`, in that order, always. Typing a version from memory and
  then checking is not the same discipline as checking and then typing.
- `uv add` will also update `uv.lock`, which is a file you commit. Look at the diff: it is much larger
  than one line, because this package has a substantial dependency tree of its own, and seeing that
  is part of the point of this part.
- Step 3 is the same command as step 1, deliberately, so the diff is in the output and not in the
  instructions.

Before, on a machine with no LiteLLM:

```text
gemini-3.7-flash                 -> Gemini
gemini-3.5-flash-lite            -> Gemini
groq/llama-3.3-70b-versatile     -> ValueError: Model groq/llama-3.3-70b-versatile not found.
openrouter/z-ai/glm-5.2:free     -> ValueError: Model openrouter/z-ai/glm-5.2:free not found.
ollama_chat/llama3.1:8b          -> ValueError: Model ollama_chat/llama3.1:8b not found.
llama-3.3-70b-versatile          -> ValueError: Model llama-3.3-70b-versatile not found.
```

After:

```text
gemini-3.7-flash                 -> Gemini
gemini-3.5-flash-lite            -> Gemini
groq/llama-3.3-70b-versatile     -> LiteLlm
openrouter/z-ai/glm-5.2:free     -> LiteLlm
ollama_chat/llama3.1:8b          -> LiteLlm
llama-3.3-70b-versatile          -> ValueError: Model llama-3.3-70b-versatile not found.
```

Three lines changed. The fourth did not, and never will, because it has no provider prefix — which is
[1.1](../01-one-model-field/1.1-a-name-is-a-lookup.md)'s point surviving a change that fixed
everything around it.

And one thing worth checking, because it explains why `openrouter/` works at all when ADK's own
pattern list does not mention it:

```python
# lab/providers.py - what the translation library says it can reach.
import importlib.metadata as metadata

import litellm

print("litellm version :", metadata.version("litellm"))
print("providers known :", len(litellm.provider_list))
for name in ("groq", "openrouter", "ollama", "ollama_chat", "gemini"):
    print(f"  {name:<12}: {name in litellm.provider_list}")
```

**Line by line:**

- `importlib.metadata.version("litellm")` rather than `litellm.__version__` — because this package
  does **not** expose `__version__`, and asking for it raises `AttributeError`. The metadata route
  works for any installed distribution and is the habit worth having.
- `litellm.provider_list` — a plain list of provider names the library knows. This is the table ADK
  falls back to when its own patterns do not match, which is exactly how `openrouter/` resolves.
- The named checks rather than printing all of them — the list is long, and five specific answers are
  more useful than a wall.

```text
litellm version : 1.98.0
providers known : 149
  groq        : True
  openrouter  : True
  ollama      : True
  ollama_chat : True
  gemini      : True
```

`gemini` is in there too, which is worth a moment: you *could* reach Gemini through the adapter. You
do not, because ADK speaks it natively and a layer you do not need is a layer that can be wrong.

## When it breaks

**💥 Following the error's first suggestion.**

```bash
uv add "google-adk[extensions]==2.7.1"
```

It works. You now have Kubernetes and Docker clients, two other agent frameworks and a retrieval
library in your lockfile, none of which you use, all of which you now own — they show up in every
audit, every vulnerability scan and every image build for the rest of the project. There is no error
and no warning, and the cost is entirely in the future.

**💥 Pinning with `>=`.**

```toml
litellm = ">=1.84"
```

Resolves today, resolves differently in three weeks, and makes "which version were we running in
March?" unanswerable — which is the exact question the security note above forces. This is why
`CLAUDE.md` says exact pins, and it is worth being able to say *why* rather than only obeying it.

**💥 The version that will not resolve.**

```text
error: Distribution `litellm==1.98.0` can't be installed because it doesn't have a source
distribution or wheel for the current platform
```

or a Python-floor conflict. Both are why the lookup prints `requires_python` alongside the version:
one line, checked before the `add`, instead of a resolver error you have to read backwards.

## In production

**What a professional writes instead of the teaching version** is the narrow dependency plus a
comment saying which fat option was declined and why. Six months later somebody will see `litellm`
in `pyproject.toml`, notice that ADK's error message recommends an extra, and "fix" it. A dated line
in `PACKAGES.md` is what stops that, and it costs one sentence.

**What degrades at scale** is the transitive tree rather than the direct list. One extra with
seventeen packages in it pulls perhaps two hundred, and each of those is a thing that can have a
vulnerability, a licence you have not read, or a maintainer who stops. Teams that take this seriously
measure the count and treat a large increase as a review item, not because size is inherently bad but
because **a dependency you did not choose is a dependency nobody is watching**.

**The failure that only shows with real traffic** is the version drift between environments. A `>=`
pin plus a lockfile that is regenerated rather than committed means your laptop, CI and production
can each be on different versions of a library that sits between you and every model call. The
symptom is a behaviour difference nobody can reproduce, and the cause is not in any diff.

**The review comment a senior engineer leaves:** *"Don't take the extras — that's seventeen packages
for one. Add `litellm` directly, pin it exactly, and put a line in `PACKAGES.md` saying we declined
`google-adk[extensions]` and why, otherwise someone will helpfully switch it back."*

**The interview question:** *"how do you decide whether to install a package's extra or the
dependency directly?"* The answer that shows judgement: "Read what the extra contains before taking
it. In one case the framework's error message recommended an extra that brought seventeen packages —
two other agent frameworks, a Kubernetes client, a Docker client — to get one translation library,
and the framework's own docs said to install that library directly. Every one of those becomes part
of your audit surface and your image, and nobody is watching a dependency they didn't choose. I also
pin exactly rather than with a floor, and that's not pedantry: there was a supply-chain incident in
that exact package where two published versions contained unauthorised code, and with an exact pin
and a dated record 'were we ever on an affected version' is a lookup rather than an investigation."
