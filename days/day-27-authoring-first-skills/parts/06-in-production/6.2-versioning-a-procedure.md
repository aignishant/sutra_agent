# 6.2 — Versioning a procedure, and the answer you cannot explain

## One-line answer

`metadata.version` is a string ADK never reads, the activation register records only skill **names**,
and the consequence is that an answer given last Tuesday cannot be explained today unless you log the
version yourself.

## The story

The pharmacy changed the strength of the tablet and kept the same box.

Same brand, same colour, same size of box, same place on the shelf. What changed was the number on the
back, from 5 mg to 10 mg, because the manufacturer consolidated two products. The pharmacist knew. The
person collecting the repeat prescription for their father did not, because the box that came home
looked exactly like the eleven boxes before it.

Nothing was hidden. The number was printed on it. But the box was the thing everybody used to identify
what was inside, and the box did not change.

## The idea in plain language

`ticket-triage` carries `metadata.version: "1.0"`
([1.3](../01-extraction/1.3-the-six-question-pass.md)). Three facts about that string are worth being
exact about, because together they are a gap:

**ADK never reads it.** The frontmatter model treats `metadata` as a free dictionary, and only two keys
in it mean anything to the framework — `adk_additional_tools` and `adk_inject_state`
([26.1.2](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.2-the-skill-object.md)).
The version is inert.

**It is sent to the model on every activation.** The `load_skill` result includes the whole frontmatter
dumped as JSON, metadata and all
([26.2.3](../../../day-26-loading-skills-into-adk/parts/02-the-four-tools/2.3-what-activation-actually-costs.md)),
so `"version": "1.0"` costs a few tokens on every activation and every turn afterwards, and the model
does nothing with it.

**The activation register does not carry it.** `_adk_activated_skill_desk` is a list of **names**
([26.3.3](../../../day-26-loading-skills-into-adk/parts/03-wiring-the-toolset/3.3-activation-is-a-line-in-state.md)).
So the session records *that* `ticket-triage` was used and never *which* `ticket-triage`.

Put those together and you get the failure this part is about. A skill can change with **no deploy and
no code review** — it is a Markdown file, and the whole point of the format is that a non-engineer can
edit it. So:

> An engineer asks why ticket 4390 was triaged `normal` in March. You open the rubric. It says the
> case is `high`. Both things are true, because the rubric changed in April, and nothing anywhere
> records which version answered in March.

That is not a hypothetical shape of problem; it is the ordinary consequence of putting policy in a file
and not logging which version of the file ran. The fix is small and it has to be deliberate, because
none of the three facts above will produce it for you.

## Why Sutra needs it

Because the severity rubric is exactly the file that will change, and severity is exactly the field
somebody will ask about later.

[1.7](../01-extraction/1.7-what-goes-behind-a-link.md) put the rubric behind a link **because** it will
grow and because support leadership owns it. That was the right call and it has a consequence nobody
mentions when recommending it: a file owned by somebody else, editable without a deploy, is a file that
will change without you noticing.

There is a second reason that arrives sooner. [4.1](../04-the-authoring-loop/4.1-draft-run-read-sharpen.md)'s
loop edits the description four to six times in an afternoon. If two of those runs are being compared,
"which version of the description produced this?" is a question you will ask within the hour, and the
answer is not in the transcript.

## The mechanism

Two changes, neither of them large.

First, a version that can actually change meaning. `"1.0"` as a quoted string
([25.2.4](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.4-the-optional-fields.md)),
with a rule about when it moves:

```yaml
metadata:
  owner: support-desk
  version: "1.1"
  changed: "2026-09-04"
  adk_additional_tools: ["lookup_ticket", "search_kb"]
```

**Line by line:**

- `version` is **quoted**, because unquoted YAML reads `1.10` as the float `1.1` and silently breaks
  any ordering built on it. The trap is a year away and the quote costs nothing today.
- The rule Sutra uses, and it fits on one line: **the minor number moves when the wording changes, the
  major number moves when an answer would change.** Rewording step 2 for clarity is `1.0` → `1.1`.
  Moving the boundary between `normal` and `high` is `1.x` → `2.0`, because tickets that were `normal`
  yesterday are `high` today.
- `changed` is a date, and it is the field a human actually uses. A version number tells you two
  documents differ; a date tells you whether it differs from the one that ran in March.
- These are Sutra's keys, not ADK's, which is why they carry no `adk_` prefix — and why a different
  client reading this folder will ignore them without harm.

Second, the version in the log line, which is the change that makes the March question answerable:

```python
# days/day-27-authoring-first-skills/lab/log_versions.py
"""What to put on the invocation log line so an old answer can be explained."""

import pathlib

from google.adk.skills import load_skill_from_dir, models


def skill_versions(skills: list[models.Skill]) -> dict[str, str]:
    """Name -> version for every skill on the shelf, at the moment it was loaded."""
    return {s.name: str(s.frontmatter.metadata.get("version", "unversioned")) for s in skills}


def activated_with_versions(state: dict, agent_name: str, versions: dict[str, str]) -> list[str]:
    """The skills this run activated, each tagged with the version that was loaded."""
    names = state.get(f"_adk_activated_skill_{agent_name}") or []
    return [f"{n}@{versions.get(n, 'unknown')}" for n in names]


if __name__ == "__main__":
    from sutra.desk.skills import load_shelf

    skills, _ = load_shelf()
    versions = skill_versions(skills)
    print("shelf     :", versions)
    print("a run     :", activated_with_versions(
        {"_adk_activated_skill_desk": ["ticket-triage"]}, "desk", versions
    ))
```

**Line by line:**

- `skill_versions` is computed **once, from the loaded objects**, not read from disk per request. That
  matters for correctness rather than speed: the version you want to log is the one that was in memory
  when the answer was produced, and if somebody edits the file mid-run, the file on disk is no longer
  it.
- `.get("version", "unversioned")` gives a skill with no version a value rather than a `KeyError`, and
  the value is a word rather than an empty string, so `unversioned` shows up in a log search. A silent
  blank is how a gap stays invisible.
- `str(...)` around it, because a skill whose author forgot the quotes has a float there and a log
  field that is sometimes a string and sometimes a number is a log field that breaks a query.
- `f"{n}@{versions.get(n, 'unknown')}"` produces `ticket-triage@1.1` — one token in a log line, greppable,
  and immediately readable. `unknown` rather than `unversioned` here, deliberately: they mean different
  things. *Unversioned* is a skill with no version field; *unknown* is a skill that was activated and is
  not on the shelf we loaded, which should never happen and is worth seeing if it does.
- The function takes `state` and `versions` as arguments rather than reaching for globals, so it is
  testable with two dictionaries and no ADK at all.
- **Zero model calls.**

Run it from the repository root:

```bash
uv run python days/day-27-authoring-first-skills/lab/log_versions.py
```

**Line by line:**

- Needs no key. `load_shelf` is the loader from
  [3.2](../03-procedure-and-capability/3.2-honouring-the-contract.md), so this reports on the real
  shelf.

Measured on 2026-09-04, with both skills at `1.0`:

```text
shelf     : {'kb-answer-style': '1.0', 'ticket-triage': '1.0'}
a run     : ['ticket-triage@1.0']
```

That second line is the field to add to Day 22's structured log
([22.2.1](../../../day-22-structured-logging/parts/02-wiring-the-run/2.1-one-line-per-happening.md)).
It is one string, and it turns *"why was 4390 normal in March?"* from archaeology into a query.

## When it breaks

**A version that never moves.** Six edits, still `1.0`, and the field is worse than absent because it
looks like information. The habit that works is mechanical: the version is part of the same change as
the edit, and a review comment when it is not.

**A version that moves and nothing records it.** The number in the file is the *current* version. Only
the log says which one ran. A team that versions carefully and logs nothing has documented the present
and not the past.

**The reference file with its own life.** `references/severity-rubric.md` has no frontmatter and no
version of its own, so a rubric change with no body change leaves the skill at the same version and
changes the answers. That is a real hole and Sutra's answer is that the version lives on the **skill**
and moves when anything in the folder changes, including a reference. Which is a rule that only works
if it is written down, so it goes in `skills/README.md`.

**Two versions in production at once.** The moment the shelf is loaded at startup
([26.1.1](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.1-load-skill-from-dir.md))
and there is more than one process, a rolling deploy has old and new skills answering simultaneously.
That is normal and it is only a problem if you cannot tell which was which — which is, again, the log
line.

## In production

**Log `name@version` on every invocation, and never only at startup.** The startup line tells you what
was loaded; the invocation line tells you what answered. Only the second one is joinable to a specific
answer, and the specific answer is what somebody will ask about.

**Treat a major bump as a change that needs an announcement.** Moving the `normal`/`high` boundary
changes every dashboard that counts severities, retroactively breaks comparisons across the change, and
will make somebody's weekly number jump. That is not a skill edit; it is a policy change that happens
to be delivered as a skill edit, and the version number is the only place the system marks it.

**Keep old versions readable.** The skill is in git, so *"what did version 1.0 say?"* is
`git show <commit>:skills/ticket-triage/SKILL.md`. That only works if the version bump is in the same
commit as the change — the same discipline as
[2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md)'s move-in-one-commit rule, for the same
reason.

**What changes at scale** is that skills are edited by people who have never heard of your versioning
convention, and the version stops being trustworthy. At that point the honest identifier is not the
version at all but a **content hash** of the folder, computed at load and logged — it cannot be
forgotten, it cannot be wrong, and it is exactly reproducible from git. The human-facing version stays,
because `2.0` communicates *"this changes answers"* in a way a hash never will. They do different jobs
and a mature system logs both.

**The review comment a senior engineer leaves:** *"this moves the boundary between normal and high, and
the version is still 1.0. Bump it to 2.0 and say so in the commit message — every severity count before
and after this change is measuring a different thing, and in three months nobody will remember why the
line moved."*

**The interview question:** *"a skill changed and now an old answer looks wrong — how do you explain
it?"* The answer that shows you have been asked: *"only if you logged the version. ADK does not read
`metadata.version`, and the activation record it keeps is a list of skill names with no versions, so
nothing in the framework connects an answer to the document that produced it. We log `name@version` on
the invocation line, bump the minor number for wording and the major number when an answer would
change, and keep the bump in the same commit as the edit so git can show us the old text. At scale I
would log a content hash of the skill folder as well, because a hash cannot be forgotten and a version
number can."*
