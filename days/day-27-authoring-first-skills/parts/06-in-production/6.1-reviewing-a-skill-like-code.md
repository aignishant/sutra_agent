# 6.1 — Reviewing a skill like code

## One-line answer

A skill review has three readers with three different jobs — the machine checks structure, an engineer
checks the couplings, and the person who owns the procedure checks whether it is *right* — and a review
where one person does all three is a review where the third job does not happen.

## The story

Five people proofread the wedding invitation and the date was still wrong.

Everyone read it. The aunt checked the spelling of the venue, the brother checked the map, somebody
noticed the missing full stop after the RSVP line, and a friend who does design said the margins were
tight. Four hundred cards went to the printer with a Saturday that was actually a Sunday.

Nobody had the job of checking the date. Five careful readings, all of them of the parts each reader
happened to be qualified to notice, and the one fact that mattered belonged to nobody in particular.

## The idea in plain language

A skill is a document that changes what a system does. That makes it code in the only sense that
matters for review — and it makes it worse than code in one specific way: nothing about it fails
loudly, so a bad review produces no signal at all.

Three readers, three jobs, in this order:

**The machine reads the structure.** The preflight
([4.3](../04-the-authoring-loop/4.3-sharpening-without-a-model.md)): required tools exist, links
resolve, no orphan references, house sections present. This is not part of the review; it is the
**entry condition** for one. A human reading a skill that has not passed it is a human spending
attention on things a regex settles.

**An engineer reads the couplings.** The things a skill touches outside itself, and there are exactly
four:

| Coupling | The question |
| --- | --- |
| tool names | do the names in the body and the metadata match the real functions? |
| quoted outputs | does `No ticket with id` still match what the tool returns? |
| the handbook | does anything here contradict the instruction, or duplicate it? |
| the other skills | does this description compete with an existing one? |

Each one is checkable in under a minute by somebody who knows the codebase, and none of them is
visible to somebody who does not.

**The owner reads the procedure.** Is this what we actually do? Is the rubric right? Is the tone one we
would defend? That is the reading the whole day exists to enable — the reason for putting the procedure
in a folder rather than in Python was so that this person could do it — and it is the one that gets
skipped, because they are the least likely to be on the pull request.

`metadata.owner` from [1.3](../01-extraction/1.3-the-six-question-pass.md) is the machine-readable
answer to *who is that person*, and it is worth having for exactly this moment.

The failure this arrangement prevents is the wedding invitation: three thorough readings of structure,
couplings and prose style, and nobody asked whether `normal` is really the right severity for a single
blocked customer on a Pro plan.

## Why Sutra needs it

Because the two skills written today were authored, reviewed and approved by one person, and that
person is the same one who wrote the code they couple to.

That is unavoidable at this stage and it is worth naming rather than pretending otherwise. What is
avoidable is carrying the habit forward: the moment a second person exists, the split above is what
stops a skill from being reviewed the way the invitation was.

There is also an immediate, concrete reason. `ticket-triage`'s body quotes two strings verbatim —
`No ticket with id` and `No KB article matched`
([1.4](../01-extraction/1.4-steps-for-a-competent-stranger.md)). Those are couplings to
`sutra/loop.py`, they are invisible to anybody reading the skill alone, and the only thing that will
ever catch them drifting is either a reviewer who knows or a test. Today it should be the test.

## The mechanism

The couplings that a reviewer would otherwise have to hold in their head, as three assertions:

```python
# tests/test_skill_couplings.py
"""The four things a skill touches outside itself, pinned so review does not have to."""

import pathlib

import pytest
from google.adk.skills import load_skill_from_dir

from sutra.desk.skills import SHELF
from sutra.loop import TOOLS, lookup_ticket, search_kb


@pytest.fixture
def triage():
    """The real skill from the real shelf."""
    return load_skill_from_dir(SHELF / "ticket-triage")


def test_declared_tools_exist(triage) -> None:
    """Every tool the procedure requires is one the dispatch actually has."""
    declared = set(triage.frontmatter.metadata.get("adk_additional_tools") or [])
    assert declared <= set(TOOLS)


def test_quoted_failure_strings_still_match(triage) -> None:
    """The body quotes what the tools return; if the tools change, this goes red."""
    assert lookup_ticket("9999").startswith("No ticket with id")
    assert search_kb("nothing at all").startswith("No KB article matched")
    assert "No ticket with id" in triage.instructions
    assert "No KB article matched" in triage.instructions


def test_the_handbook_does_not_name_the_field_differently(triage) -> None:
    """One field, one word - the failure from part 5.2, pinned."""
    from sutra.desk.agent import INSTRUCTION

    assert "priority" not in INSTRUCTION.lower()
    assert "severity" in triage.instructions.lower()
```

**Line by line:**

- The fixture loads from `SHELF`, imported from `sutra.desk.skills`
  ([3.2](../03-procedure-and-capability/3.2-honouring-the-contract.md)), so the tests read the **real**
  shelf. A test that builds its own skill tests its own skill.
- `declared <= set(TOOLS)` is a **subset** assertion, which reads as *"everything required is
  available"* and allows the system to have tools no skill requires. Getting the direction right
  matters: equality here would fail the day somebody adds a tool.
- The second test asserts **both halves of the coupling** — that the tool still produces the string,
  and that the body still quotes it. Either one alone is half a check: the tool could change, or the
  body could be rewritten, and the pairing is what is being pinned.
- `lookup_ticket("9999")` uses an id chosen to miss, and `search_kb("nothing at all")` a query chosen
  to match no keyword. Both are exercising the failure path deliberately, which is the path the skill's
  steps are written around.
- The third test is [5.2](../05-failure-lab/5.2-two-notices-on-one-door.md) as an assertion. `"priority"
  not in INSTRUCTION` is blunt and it is exactly the check that would have caught the drift — it fails
  the moment somebody reintroduces the old word.
- The import of `INSTRUCTION` is **inside** the test rather than at the top, so this file's other tests
  do not depend on the agent module. A small thing, and it keeps the failure localised when the desk
  module is being changed.
- No `live` marker on any of them: no model and no network, so they belong in the default
  `-m "not live"` run. The second or so they take is almost all ADK's import, not the assertions
  ([23.2.5](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.5-markers-and-the-not-live-line.md)).

Run them:

```bash
uv run python -m pytest tests/test_skill_couplings.py -q
```

**Line by line:**

- In `tests/`, not in the day's lab, because these pin the shipped skills and should run in
  `./m check` from now on.

Measured on 2026-09-04 against the finished skills:

```text
...                                                                      [100%]
3 passed in 1.11s
```

Three couplings that a reviewer no longer has to remember, which is the point: **review is for the
things only a person can judge**, and every check that can be automated is a check that should stop
consuming attention.

Then the human half, written down so it is a checklist rather than a mood:

```text
Engineer reviewing a skill:
- [ ] preflight is green
- [ ] the description's trigger words are words a requester would type
- [ ] the description does not overlap an existing skill on trigger words
- [ ] every step is one action, imperative, with its failure branch attached
- [ ] nothing in the body contradicts or duplicates the instruction
- [ ] nothing in the body is a control pretending to be a sentence

Owner reviewing a skill:
- [ ] this is what we actually do, not what we wish we did
- [ ] the worked example is a case we would be happy to be judged on
- [ ] the edge cases are things that really happened
- [ ] the rubric's boundaries are where I would put them
```

**Line by line:**

- The engineer's list is six checkable things and every one of them comes from a part of this day. It
  is deliberately not about prose quality, because prose quality is the owner's column.
- *"nothing in the body is a control pretending to be a sentence"* is
  [2.2](../02-what-leaves-the-prompt/2.2-what-never-leaves-code.md) as a review step: scan for *never*,
  *must*, *always*, and for each one ask which tier it belongs in.
- The owner's list is **four questions and no jargon**, on purpose. A checklist a support lead cannot
  read is a checklist that guarantees the third reading does not happen.
- *"a case we would be happy to be judged on"* is the useful form of *"is the example good?"*. It gives
  a non-engineer a concrete standard rather than an aesthetic one.

## When it breaks

**The review that only reads the diff.** A skill change is small and the context is the whole document:
adding one step can contradict a step three lines up, and a diff of four lines shows neither. Skill
reviews read the file, not the change.

**The engineer reviewing the procedure.** Well-meant and it is the wedding invitation: an engineer will
review what they can evaluate, which is the couplings and the prose, and will nod at the rubric. If the
owner is not on the review, the rubric is not reviewed, and saying *"looks fine to me"* about a policy
you do not own is how a wrong boundary ships.

**The owner reviewing the couplings.** The mirror image, and it wastes their attention. A support lead
should not be checking whether `lookup_ticket` is spelled the same in two files. That is what the tests
above are for.

**The preflight treated as the review.** Green means the plumbing is sound. It says nothing about
whether the procedure is right, and a team that ships on green has automated the easy third and
dropped the other two.

## In production

**Put the owner on the review, mechanically.** `metadata.owner` is a field; a `CODEOWNERS` entry
mapping `skills/ticket-triage/` to the support team is one line. Relying on somebody remembering to
add a reviewer is relying on the thing that failed on the invitation.

**Require a transcript in the pull request.** Not an answer — an event stream showing `list_skills`,
`load_skill`, and the tool calls
([4.1](../04-the-authoring-loop/4.1-draft-run-read-sharpen.md)). It is the only evidence that the
document does anything, and it costs the author three generations rather than costing the reviewer a
week.

**Review the description separately, and first.** The body only matters if the description got
selected. Teams that read them together read the body and skim the description, which is backwards. A
two-line review comment on a description is worth more than a paragraph on step 4.

**What changes at scale** is that skills stop being reviewed at all, because they are Markdown and
Markdown feels safe. The countermeasure is not more process; it is making the couplings automatic —
tests, the preflight, the overlap check — so that the human review has one job left and that job is
worth doing. A review with ten obligations gets skimmed; a review with one gets done.

**The review comment a senior engineer leaves:** *"structure is green and the couplings are pinned by
tests, so I have nothing to add on the mechanics. I have not approved the rubric — that is the support
lead's call and they are not on this pull request. Adding them."*

**The interview question:** *"how do you review a skill?"* The answer that shows you have watched one go
wrong: *"in three passes with three readers. A lint checks the structure — tools exist, links resolve,
sections present — and that is the entry condition, not the review. An engineer checks the four
couplings to the codebase: tool names, quoted tool outputs, the system prompt, and overlap with other
skills, all of which we now pin with tests so it is fast. And the person who owns the procedure checks
whether it is *right*, which is the entire reason the procedure is in a folder. The failure mode is
three careful readings of the parts each reader is qualified to notice, and nobody checking the one
thing that mattered."*
