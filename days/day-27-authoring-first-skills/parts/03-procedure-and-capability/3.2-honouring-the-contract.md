# 3.2 — Honouring the contract: the tools arrive with the procedure

## One-line answer

`SkillToolset(skills=..., additional_tools=[lookup_ticket, search_kb])` is where the requirement is
met — and because ADK resolves those tools out of the activated skill's metadata, the desk agent goes
from four tools to six the moment the triage procedure is loaded, and not before.

## The story

The plumber reads the job card before he opens the van.

*Kitchen tap dripping, single lever mixer, flat on the second floor.* He stands at the back doors for
maybe fifteen seconds, then takes out the cartridge box, the adjustable spanner, the small basin
wrench that only comes out for taps, and a towel. He leaves the drain rods, the pipe cutter and the
blowtorch where they are.

The van has everything. What decides what comes upstairs is the card. And the reason he can do that at
all is that whoever wrote the card wrote *what the job is* precisely enough that the tools follow from
it — which is a property of the card, not of the plumber.

## The idea in plain language

[3.1](3.1-a-named-tool-is-a-contract.md) put the requirement in the skill:
`adk_additional_tools: ["lookup_ticket", "search_kb"]`. This part supplies it.

The supply side is one argument on the toolset:

```python
skill_toolset.SkillToolset(skills=..., additional_tools=[lookup_ticket, search_kb])
```

**Line by line:**

- `additional_tools=` is keyword-only, and it is the **second** list on this constructor. `skills=` is
  the procedures; this is the capabilities they may ask for.
- The two names passed here are the two functions from `sutra/loop.py`, and the names ADK derives from
  them are what the skill's metadata has to match.
- `skills=...` is elided because the shelf loading is
  [1.4](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.4-the-whole-shelf.md)'s
  subject and this line is about one argument.

And the behaviour is the one Day 26 measured, which is worth restating because it is not what the
argument's name suggests. Passing those two functions does **not** give them to the agent. They are
held. They appear only when a skill that names them has been activated, resolved out of session state
on the next `get_tools` call
([26.3.2](../../../day-26-loading-skills-into-adk/parts/03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md)).

So Sutra's desk agent, from the model's point of view, has:

| Moment | Tools declared |
| --- | --- |
| every request, before anything is activated | `list_skills`, `load_skill`, `load_skill_resource`, `run_skill_script` |
| after `load_skill("ticket-triage")` | those four, **plus** `lookup_ticket` and `search_kb` |

Two consequences, and they are the reason this is worth doing rather than just attaching the tools to
the agent directly.

**The cost is conditional.** A conversation about refunds never activates the triage skill, so it never
carries the declarations for two tools it will not use. Day 19 found the tool menu to be one of the
most expensive parts of the request
([19.2.3](../../../day-19-context-engineering-selection/parts/02-anatomy/2.3-the-menu-costs-more-than-the-handbook.md)),
and this is that cost made conditional.

**The blast radius is smaller.** `lookup_ticket` reads a ticket store. There is no moment in a refund
conversation when the model should be able to call it, and with this wiring there is no moment when it
can. That is Principle 13 arriving from an unexpected direction: the containment came free with a
design chosen for a different reason.

The honest counter-argument, which Day 28 will take seriously: **the tools are unavailable on the runs
where the skill did not fire.** If the model does not activate `ticket-triage`, it cannot look a ticket
up at all — and an agent that answers a triage question with neither the procedure nor the tools is
worse than one with the tools and no procedure. Whether that is acceptable depends on how reliably the
skill fires, which is [4.2](../04-the-authoring-loop/4.2-which-rung-did-it-climb.md)'s measurement and
not a matter of opinion.

## Why Sutra needs it

Because the alternative is giving the desk agent every tool it might ever need, permanently, and that
is the design Sutra has been drifting towards since Day 10.

Right now `sutra/desk/agent.py` has no tools at all — the desk agent was built on Day 5 with an
instruction and nothing else, and Day 10's function tools were wired into a different entry point. So
Sutra is at the one moment where the decision is still free: the tools can be attached to the agent, or
attached to the procedure that uses them. Choosing the second costs one argument and buys the two
properties above.

It also makes the pairing **reviewable in one place**. A support engineer reading
`skills/ticket-triage/SKILL.md` sees the steps and, three lines up, the tools those steps require. They
do not have to open a Python file to find out what the procedure is allowed to do.

## The mechanism

The desk agent, with skills and the tools its skills require.

```python
# sutra/desk/skills.py - the desk's shelf and the agent built from it (Days 26-27).
"""Build the desk agent from the repository's skills folder.

The shelf is loaded once, at import, and a bad folder is named rather than fatal
(Day 26, part 4.1). The tools the procedures need are passed to the toolset rather
than to the agent, so they appear only once a procedure that names them is active.
"""

import logging
import pathlib

from google.adk.agents import Agent
from google.adk.skills import load_skill_from_dir, models
from google.adk.tools import skill_toolset

from sutra.desk.agent import INSTRUCTION
from sutra.loop import lookup_ticket, search_kb

logger = logging.getLogger("sutra.skills")

MODEL = "gemini-3.7-flash"
SHELF = pathlib.Path(__file__).resolve().parents[2] / "skills"


def load_shelf(shelf: pathlib.Path = SHELF) -> tuple[list[models.Skill], list[str]]:
    """Every skill under `shelf`, plus the folder names that would not load."""
    skills: list[models.Skill] = []
    rejected: list[str] = []
    for folder in sorted(p for p in shelf.iterdir() if (p / "SKILL.md").is_file()):
        try:
            skills.append(load_skill_from_dir(folder))
        except (ValueError, OSError) as exc:
            rejected.append(folder.name)
            logger.error("skill rejected", extra={"skill_folder": folder.name, "why": str(exc)})
    return skills, rejected


def build_desk() -> Agent:
    """The desk agent: its handbook, its shelf, and the tools its procedures name."""
    skills, rejected = load_shelf()
    if rejected:
        raise RuntimeError(f"refusing to start: unloadable skills {rejected}")
    toolset = skill_toolset.SkillToolset(
        skills=skills,
        additional_tools=[lookup_ticket, search_kb],
    )
    return Agent(model=MODEL, name="desk", instruction=INSTRUCTION, tools=[toolset])
```

**Line by line:**

- `SHELF = pathlib.Path(__file__).resolve().parents[2] / "skills"` anchors the path to **this module**,
  not to the working directory. The loader resolves relative paths against the process's cwd
  ([26.1.1](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.1-load-skill-from-dir.md)),
  which works on a laptop and fails in a container. `parents[2]` is `sutra/desk/skills.py` →
  `sutra/desk` → `sutra` → the repository root.
- `load_shelf` is [26.4.1](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.1-one-bad-folder.md)'s
  loop, verbatim, because that part's whole argument was that the built-in bulk loader gives you a
  traceback with no folder name in it.
- `raise RuntimeError(...)` is Sutra's chosen policy: **fail fast**. With two skills, one of which is
  the triage procedure, a desk that starts without them improvises severities and says nothing about
  it. The alternative — log and continue — is one line, and the hub's build brief asks you to write
  down which you chose and why.
- `from sutra.desk.agent import INSTRUCTION` reuses the handbook rather than copying it. One fact, one
  home ([2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md)) applies to imports too.
- `from sutra.loop import lookup_ticket, search_kb` — the same functions the hand-rolled loop has used
  since Day 4. They return **strings**, not dictionaries: ADK wraps a bare return value into a result
  object for you ([10.2.2](../../../day-10-function-tools/parts/02-what-a-tool-returns/2.2-the-bare-value-the-spec-rewrites.md)),
  and the skill's steps quote those strings exactly
  ([1.4](../01-extraction/1.4-steps-for-a-competent-stranger.md)), so the coupling is deliberate rather
  than accidental.
- `additional_tools=[lookup_ticket, search_kb]` and **not** `tools=[toolset, lookup_ticket, search_kb]`.
  That one-line difference is the whole part: the second form gives the agent the tools permanently,
  the first gives them to the procedure.
- The bare functions are passed rather than `FunctionTool` instances, so ADK takes the name from the
  function and the description from the docstring
  ([10.1.2](../../../day-10-function-tools/parts/01-the-form-fills-itself/1.2-the-docstring-is-the-description.md)).
  The name it takes is what `adk_additional_tools` has to match.
- `build_desk()` is a function, so importing this module does nothing. That has been the rule since
  Day 5, and here it also means the shelf is not walked at import time in a test that only wanted the
  loader.

Prove the wiring without a model:

```python
# days/day-27-authoring-first-skills/lab/before_and_after.py
"""The desk's tool list, cold and after the triage skill is activated."""

import asyncio

from sutra.desk.skills import build_desk


class FakeContext:
    """Enough of a readonly context for the toolset to resolve additional tools."""

    def __init__(self, activated: list[str] | None = None) -> None:
        self.agent_name = "desk"
        self.invocation_id = "inv-1"
        self.state = {"_adk_activated_skill_desk": activated} if activated else {}


async def main() -> None:
    """Ask the toolset for its tools twice, with and without an activation."""
    toolset = build_desk().tools[0]
    for label, activated in (("cold", None), ("after triage", ["ticket-triage"])):
        tools = await toolset.get_tools(FakeContext(activated))
        print(f"{label:14}: {sorted(t.name for t in tools)}")


asyncio.run(main())
```

**Line by line:**

- `build_desk().tools[0]` reaches into the agent for the toolset, which is fine in a probe and would be
  a smell in `sutra/`. It is here so the script exercises the **real** agent rather than a
  reconstruction of it.
- `FakeContext` is Day 26's double with the state key pre-filled
  ([26.3.2](../../../day-26-loading-skills-into-adk/parts/03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md)),
  because writing the key by hand is what makes the two calls differ in exactly one thing.
- `{"_adk_activated_skill_desk": activated} if activated else {}` gives the cold case an empty
  dictionary rather than a key with `None` in it. Both work; the empty one is what an untouched session
  actually looks like.
- **Zero model calls.**

Measured on 2026-09-04:

```text
cold          : ['list_skills', 'load_skill', 'load_skill_resource', 'run_skill_script']
after triage  : ['list_skills', 'load_skill', 'load_skill_resource', 'lookup_ticket', 'run_skill_script', 'search_kb']
```

Four, then six. The two extra declarations exist for exactly as long as the procedure that needs them.

## When it breaks

**Nothing appears, and nothing complains.** Three causes, byte-identical output, all silent — never
activated, no metadata key, or a name that does not match
([26.4.2](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.2-the-tool-that-never-appeared.md)).
The lint from [3.1](3.1-a-named-tool-is-a-contract.md) catches the third. The first is
[4.2](../04-the-authoring-loop/4.2-which-rung-did-it-climb.md). The second is a review habit.

**The tools attached to the agent as well.** `tools=[toolset, lookup_ticket, search_kb]` is harmless
until you notice it makes the whole mechanism pointless: the tools are now permanent, and the
`additional_tools` list is decoration. It also produces a duplicate-name situation the toolset handles
by dropping its own copy, logged at `ERROR` through ADK's logger and invisible if your logging is not
configured ([22.2.3](../../../day-22-structured-logging/parts/02-wiring-the-run/2.3-adk-logs-too.md)).

**A tool named the same as one of the four.** A function called `load_skill` is refused with a
collision message and silently absent from the model's view. Sutra's two are safe; a third-party skill
pack's might not be, which is Day 29's problem.

**The shelf that will not load.** With `raise RuntimeError` in `build_desk`, an unloadable skill is a
startup failure — which is the policy, and which means a support engineer's typo in a Markdown file can
stop the desk. That is a real cost of fail-fast and the reason the validator belongs in CI, before the
file ever reaches the shelf.

## In production

**Pass tools to the procedure that names them, not to the agent, as the default.** The exception is a
tool the agent needs with no procedure at all — a clock, a "who am I" lookup, anything used in
answering rather than in following a procedure. Those go on the agent. The test is whether the tool is
useful when no skill is active.

**Log the resolved tool names per request, not just at startup.** The set is dynamic now, so a startup
log describes the cold case only, and the question *"what could the model call when it made that
decision?"* has no answer after the fact without a per-request line
([22.2.1](../../../day-22-structured-logging/parts/02-wiring-the-run/2.1-one-line-per-happening.md)).

**Watch for the pairing making a skill unfireable.** If a procedure's tools only appear after
activation, and activation depends on the description, then a weak description now costs you both the
procedure and the capability. That is a compounding failure and it is the strongest argument for
measuring activation rate rather than assuming it.

**What changes at scale** is that several skills come to share a tool, and `additional_tools` becomes a
long list on one toolset. It still works — resolution is by name — but the reverse question, *"which
procedures use this tool?"*, is now the thing you need in review, and it is exactly what
[3.1](3.1-a-named-tool-is-a-contract.md)'s lint already computes. Print it.

**The review comment a senior engineer leaves:** *"the tools are on the agent and also in
`additional_tools`. Pick one. If they are on the agent, the metadata key is decoration and the model
can call `lookup_ticket` in a refund conversation; if they are in `additional_tools`, delete them from
`tools=` so the conditional wiring actually does something."*

**The interview question:** *"how do you give an agent the tools a particular procedure needs?"* The
answer that shows you have wired it: *"pass them as `additional_tools` on the skills toolset and
declare them in the skill's `metadata.adk_additional_tools`. ADK then surfaces them only after that
skill has been activated — our desk goes from four tools to six on the turn after the triage procedure
loads. That makes the tool-menu cost conditional and shrinks the window in which a ticket-reading tool
can be called at all. The trade is that if the skill never fires, the capability is missing too, so
activation rate becomes something you have to measure rather than assume."*
