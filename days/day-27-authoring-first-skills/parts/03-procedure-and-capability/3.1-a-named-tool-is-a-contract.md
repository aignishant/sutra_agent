# 3.1 — A skill that names a tool has written a contract

## One-line answer

The moment a body says *"call `lookup_ticket`"*, the skill has declared a requirement — and nothing in
the format, the loader or the runtime checks that the requirement is met, so the check has to be
yours.

## The story

The exam paper says *"use the graph paper provided"*.

You turn the page. There is no graph paper. You look under the desk, you look at the person beside you
— they do not have any either — and you raise your hand, and the invigilator says she will find out,
and eleven minutes go by.

The question was fine. The graph paper exists somewhere in the building. What failed is that the paper
and the stationery were prepared by two different people, and nothing between the printing and the
desk checked that the sentence and the world agreed.

You still had to answer the question. Most people drew their own axes.

## The idea in plain language

`ticket-triage`'s body names two tools: `lookup_ticket` in step 1 and `search_kb` in step 3
([1.4](../01-extraction/1.4-steps-for-a-competent-stranger.md)). That is a **contract**: the skill has
stated what it needs in order to be followable.

Nothing enforces it. Walk the whole path and there is no check anywhere:

- The **spec validator** checks frontmatter fields and the name rules. It does not read the body's
  prose ([25.5.1](../../../day-25-skills-the-open-spec/parts/05-in-production/5.1-validating-before-you-ship.md)).
- The **loader** parses the frontmatter and reads the files. It never looks at what the body says
  ([26.1.1](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.1-load-skill-from-dir.md)).
- The **toolset** matches `metadata.adk_additional_tools` against the tools you passed in — and if a
  name matches nothing, it is silently dropped
  ([26.4.2](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.2-the-tool-that-never-appeared.md)).
- The **model** finds out at request time, mid-procedure, and improvises.

Four opportunities, four passes. So the contract is real and unenforced, which is the definition of a
thing that needs a lint.

There is one wrinkle that makes the lint less obvious than it sounds, and
[1.4](../01-extraction/1.4-steps-for-a-competent-stranger.md) already found it: backticks in a body do
three different jobs. In `ticket-triage`'s body, the seven backticked spans are two tool names
(`lookup_ticket`, `search_kb`), two quoted tool outputs (`No ticket with id`, `No KB article matched`)
and three example values (`logout`, `export`, `billing`). A lint that treats every backticked span as
a required tool reports five false positives on a correct skill, and a lint with a five-in-seven false
positive rate is a lint that gets switched off.

So the contract has to be **declared**, not inferred. The skill says, in a field, which tools it
requires; the lint compares that field against what the system provides; and the body's backticks stay
prose. That field already exists and ADK already reads it —
`metadata.adk_additional_tools` — which [3.2](3.2-honouring-the-contract.md) is about.

Declaring it twice, once in the body and once in the frontmatter, is not duplication in the sense
[2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md) warned about. They are two different
statements: the body says *when to call it*, the metadata says *that it is required*. What the lint
checks is that they agree.

## Why Sutra needs it

Because `lookup_ticket` and `search_kb` are ordinary Python functions in `sutra/loop.py`, and Python
functions get renamed.

Nothing in this repository would notice. `grep -rn lookup_ticket sutra/` finds the definition and the
callers; it does not find `skills/ticket-triage/SKILL.md`, because nobody greps a Markdown file when
renaming a function. The rename passes the tests, passes review, and silently removes step 1 from
Sutra's triage procedure — after which the agent activates the skill, reads a step it cannot perform,
and does something else.

That is the exact failure Day 26 built in a lab
([26.4.2](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.2-the-tool-that-never-appeared.md)).
Today it stops being a lab: the skill is real, the tools are real, and the binding between them is a
string in a file that no test covers.

## The mechanism

The declaration first, added to `ticket-triage`'s frontmatter beside the keys from
[1.3](../01-extraction/1.3-the-six-question-pass.md):

```yaml
metadata:
  owner: support-desk
  version: "1.0"
  adk_additional_tools: ["lookup_ticket", "search_kb"]
```

**Line by line:**

- The key is ADK's, prefixed `adk_` because `metadata` is a namespace shared with every client that
  might read this folder
  ([26.1.2](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.2-the-skill-object.md)).
  A client that is not ADK ignores it, and the skill still works there — the body still says which
  tools to call.
- The values are **tool names**, matching the function names exactly. Not import paths, not
  descriptions: the toolset matches on `tool.name`, and for a plain function that is the function's
  own name
  ([10.1.1](../../../day-10-function-tools/parts/01-the-form-fills-itself/1.1-the-declaration-you-no-longer-write.md)).
- Both tools are listed even though ADK will only surface them after activation. The list is the
  requirement, not the delivery; delivery is [3.2](3.2-honouring-the-contract.md).

Then the lint, which is the deliverable of this part:

```python
# days/day-27-authoring-first-skills/lab/required_tools.py
"""Compare what each skill declares it needs against what the system provides."""

import pathlib

from google.adk.skills import load_skill_from_dir, models

SHELF = pathlib.Path("skills")


def required_tools(skill: models.Skill) -> set[str]:
    """The tool names this skill declares as requirements."""
    return set(skill.frontmatter.metadata.get("adk_additional_tools") or [])


def unmet(shelf: pathlib.Path, provided: set[str]) -> dict[str, list[str]]:
    """Skill name -> the required tools nobody provides. Empty dict means healthy."""
    problems = {}
    for folder in sorted(p for p in shelf.iterdir() if (p / "SKILL.md").is_file()):
        skill = load_skill_from_dir(folder)
        missing = sorted(required_tools(skill) - provided)
        if missing:
            problems[skill.name] = missing
    return problems


if __name__ == "__main__":
    from sutra.loop import TOOLS

    result = unmet(SHELF, set(TOOLS))
    for name, missing in result.items():
        print(f"{name}: requires {missing}, which nothing provides")
    print("unmet requirements:", sum(len(v) for v in result.values()))
```

**Line by line:**

- `required_tools` reads the **declared** list and never the body. That is the decision this part
  argued for, and it is why the function is three lines instead of a regex with an exception list.
- `.get("adk_additional_tools") or []` handles both *"the key is absent"* and *"the key is there and
  empty"*. A skill that requires nothing is not a problem; a skill whose key is missing is also not a
  problem, and treating them the same is correct here.
- `(p / "SKILL.md").is_file()` skips folders that are not skills, mirroring the loader's own
  silent-skip rule ([26.1.4](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.4-the-whole-shelf.md)).
  Without it a `.git` directory becomes a lint failure.
- `required - provided` is a **set difference in one direction only**. The other direction — tools
  provided that no skill requires — is not an error: it is a tool waiting for a skill, or a tool the
  agent has directly. Reporting it would produce noise.
- `from sutra.loop import TOOLS` is inside `__main__` rather than at the top, and that is deliberate:
  the two functions are importable by a test with a set the test controls, and the real tool registry
  is only needed when the script runs as a lint. It also means the lint reads the **same dictionary the
  dispatch uses** ([4.3.1](../../../day-04-tools-by-hand/parts/03-rebuilding-the-loop/3.1-one-door-one-new-parameter.md)),
  rather than a retyped list that can drift from it.
- The exit is a printed count rather than a `sys.exit`, because today this is a lab script. Day 31
  turns the count into an exit code and wires it into `./m check`.
- **Zero model calls.**

Run it:

```bash
uv run python days/day-27-authoring-first-skills/lab/required_tools.py
```

**Line by line:**

- From the repository root, because `SHELF` is a relative path
  ([26.1.1](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.1-load-skill-from-dir.md)).

Measured on 2026-09-04, with both skills on the shelf and `TOOLS` holding `lookup_ticket` and
`search_kb`:

```text
unmet requirements: 0
```

Now break it on purpose. Change one letter in the frontmatter — `lookup_tickets` — and run again:

```text
ticket-triage: requires ['lookup_tickets'], which nothing provides
unmet requirements: 1
```

One line, naming the skill and the tool. That is the whole difference between this failure being a
build error and being a support agent that quietly stopped looking tickets up.

## When it breaks

**The lint that reads a retyped list.** If `provided` is built by hand in the lint rather than imported
from where the tools actually live, the two drift and the lint passes against a fiction. Importing
`TOOLS` is not a convenience; it is the correctness of the check.

**The body that names a tool the metadata does not.** The lint above is blind to this by design, and it
is a real gap: a body can say *"call `escalate_ticket`"* with nothing in the metadata, and the lint is
happy. The check for it is a grep of the body's backticks against the declared list, with the
false-positive problem from earlier — three of `ticket-triage`'s seven spans are example values. That
is a `TODO(me)` in the hub and it is a judgement call about how much noise a check may produce before
people stop reading it.

**A tool renamed in Python and in the metadata but not in the body.** Now the metadata and the code
agree, the lint is green, and the body tells the model to call something that no longer exists. The
lint checks one of the three pairings, which is worth being honest about: metadata against code. The
other two — body against metadata, body against code — are still human work.

**A skill from somewhere else requiring a tool you do not have.** This is Day 29's problem arriving
early. The lint reports it as an unmet requirement, which is exactly right, and the decision about what
to do — provide the tool, or refuse the skill — is a judgement about trust rather than about
configuration.

## In production

**Run the lint at startup as well as in CI.** CI catches the pull request; startup catches the case
where a skill folder is mounted from somewhere else or edited in place. It is the same three lines,
and the log line — *"skill `ticket-triage` requires `lookup_ticket`, which is not configured"* — is the
one that saves the incident.

**Treat the declared list as a public interface of your tool module.** Renaming a function is a
breaking change to every skill that names it, and the only reason it does not feel like one is that
the compiler cannot see the other side. Teams that get bitten twice end up with named constants and a
test asserting the skill files and the constants agree.

**Decide what an unmet requirement means before you have one.** Two defensible policies: refuse to
start, or start and log. It is the same choice as an unloadable skill
([26.4.1](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.1-one-bad-folder.md)) and the
same reasoning applies — if the missing tool means the procedure produces a wrong answer rather than
no answer, refuse.

**What changes at scale** is that the contract becomes many-to-many. Forty skills, sixty tools, and
several skills sharing a tool: now a rename affects an unknown number of procedures, and the only way
to answer *"what breaks if I rename this?"* is the reverse index the lint already computes. Print it
occasionally; it is the map of which procedures depend on which capabilities, and nobody has it
otherwise.

**The review comment a senior engineer leaves:** *"this renames `lookup_ticket` and updates the four
Python call sites. `skills/ticket-triage/SKILL.md` names it too, in the body and in the metadata. Add
the skills lint to CI in this pull request rather than the next one."*

**The interview question:** *"a skill's instructions reference a tool — what makes sure that tool
exists?"* The answer that shows you have looked for the check: *"nothing does, at any layer. The
validator only reads frontmatter, the loader never reads the body, and ADK silently drops a declared
tool name that matches nothing. So we declare the requirement in the skill's metadata and lint it
against the tool registry the dispatch actually uses — not a retyped list. We do not infer it from the
body's backticks, because backticks in a body also quote outputs and example values, and a check with
that many false positives gets turned off."*
