# 1.5 — One worked example, and why one is enough

## One-line answer

Question 4 produces exactly one worked case — real input, the calls in order, the real output —
because a single concrete trace teaches the shape of a good answer in a way seven steps cannot, and a
second example teaches almost nothing extra for twice the tokens.

## The story

The handwriting practice book has the letter at the top of the page, printed properly, once.

Then four faint grey versions to trace over, and then eleven empty lines for you to do it yourself.
The printed one is small and you look at it constantly — not to copy it stroke for stroke, but to check
whether the thing you just made looks like the thing at the top.

Nobody prints the letter eleven times. One correct example at the top of the page is what a page of
practice is anchored to, and a second correct example, slightly different, would only start an
argument about which one is right.

## The idea in plain language

A worked example is one real case walked end to end: what came in, what was called, what came back,
and what was said.

It sits after the steps and before the edge cases, and it does something the steps cannot. Steps are
general instructions; an example is a **shape**. It shows the length of a good answer, the tone, which
details get mentioned and which do not, and — most usefully — what the tool calls actually looked like
in a case that went well.

Three rules make an example carry its weight.

**Use a real case, with real values.** Ticket 4521 exists in `sutra/loop.py`, `search_kb("logout")`
returns KB-104, and the rubric has a row that matches. An example built on invented ids teaches the
shape and quietly teaches wrong data, and the wrong data is what gets copied.

**Show the calls, not just the answer.** The trace — `lookup_ticket(4521)` → symptom → `search_kb` →
article → severity — is the part that removes ambiguity from the steps. An example that shows only the
final paragraph leaves the model to guess how many tool calls were involved in producing it.

**One example, not three.** This is the rule people resist and it is the one with the measurement
behind it. Every line of the body is loaded whole on activation and carried for the rest of the
conversation
([25.3.1](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.1-the-body-is-loaded-whole.md)),
so a second example is a permanent cost. And its benefit is small: the first example teaches the
shape; the second mostly teaches that there is variation, which the edge cases already say better and
shorter.

The honest exception is worth stating so the rule does not get applied blindly. **Add a second example
when the two cases are shaped differently, not when they merely have different values.** A successful
triage and a triage where the KB found nothing produce genuinely different answers, and the second one
is the one people get wrong. That is a case for two — and even then, the second belongs in
`references/` if it is long, which is [1.7](1.7-what-goes-behind-a-link.md).

## Why Sutra needs it

Because the answer Sutra should produce has a shape that is not derivable from the steps.

Read step 7 — *"tell the engineer the severity and the rubric row that decided it, in one sentence"* —
and try to predict what the answer looks like. How much of the ticket does it restate? Does it quote
the article or paraphrase it? Is the severity first or last? Does it address the engineer or the
customer? Every one of those is a real decision, none of them is in the steps, and all of them are
visible instantly in one example.

There is also a Sutra-specific reason. `kb-answer-style` is a whole second skill about the shape of a
reply ([1.2](1.2-one-job-four-words.md)), which means `ticket-triage`'s example has to show a
**triage** answer — addressed to the engineer, not to the customer — or the two skills will teach
overlapping and slightly different shapes. Writing the example is what makes that boundary concrete,
and it is where you find out whether the split from 1.2 actually holds.

## The mechanism

First, get the real values. An example built from memory is an example with a wrong id in it.

```bash
uv run python -c "
from sutra.loop import lookup_ticket, search_kb
print(lookup_ticket('4521'))
print(search_kb('logout'))
"
```

**Line by line:**

- Both calls are the ones step 1 and step 3 tell the model to make, with the argument step 2 tells it
  to construct. Running the procedure by hand before writing it down is the cheapest possible check
  that the procedure works at all.
- **Zero model calls.** These are ordinary Python functions.

Measured on 2026-09-04:

```text
Title: Keeps getting logged out. Body: I keep getting logged out of the dashboard every few minutes. Started yesterday. Plan: Pro.
KB-104 'Unexpected logouts': cookies set with SameSite=Strict plus an http:// dashboard URL end sessions early; fix is forcing https.
```

Now the example, appended to the body after the steps:

```markdown
## Worked example

**Engineer asks:** "Triage 4521."

1. `lookup_ticket("4521")` returns:
   `Title: Keeps getting logged out. Body: I keep getting logged out of the dashboard every few
   minutes. Started yesterday. Plan: Pro.`
2. Symptom, in one word: `logout`.
3. `search_kb("logout")` returns:
   `KB-104 'Unexpected logouts': cookies set with SameSite=Strict plus an http:// dashboard URL end
   sessions early; fix is forcing https.`
4. Rubric row: one user blocked, a workaround exists (logging back in) - **normal**.

**Answer to the engineer:**

> 4521 is a repeated-logout problem on the dashboard, started yesterday, Pro plan. KB-104 says this
> happens when cookies are set with SameSite=Strict and the dashboard is reached over http:// - the
> fix is forcing https. Severity **normal**: one user blocked with a workaround.
```

**Line by line:**

- The example is numbered to **mirror the steps**, so a reader can hold the two side by side. It is not
  a second procedure; it is the first one with the values filled in.
- Every returned string is quoted **verbatim** from the run above. That is the whole reason the run
  came first: a paraphrased tool output in an example teaches the model to expect a paraphrase.
- Line 2 is the one to look at. It shows `logout` and not *"keeps getting logged out"*, which makes
  step 2's rule visible rather than merely stated — and it is the single most valuable line in the
  example, because it is the step that would otherwise be got wrong every time.
- Line 4 names the **rubric row in words** rather than quoting the rubric, because the rubric is behind
  a link ([1.7](1.7-what-goes-behind-a-link.md)) and copying it into the example would defeat the
  split.
- The answer is **three sentences**, addressed to the engineer, and it does four things: restates the
  ticket, cites the article by id, gives the fix, and gives the severity with its reason. That is the
  shape, and it is now teachable without a single adjective about tone.
- The answer says *"KB-104 says"* rather than asserting the cause directly. That one construction is
  step 5's honesty rule made visible, and a model that copies the shape copies the attribution with it.
- It is written as a **blockquote** so that the boundary between "this is the example" and "this is
  instruction to you" is unambiguous. A model reading an un-delimited example can mistake it for a
  step.

Check the body again:

```bash
uv run python -c "
import pathlib, re
from google.adk.skills import load_skill_from_dir
body = load_skill_from_dir(pathlib.Path('skills') / 'ticket-triage').instructions
print('body chars :', len(body))
print('sections   :', re.findall(r'^## (.+)$', body, re.M))
"
```

**Line by line:**

- The section scan is here to make one thing visible: the body now has a shape, and it is the same
  shape [1.3](1.3-the-six-question-pass.md)'s six questions produce. When `kb-answer-style` is written
  it should print the same list of headings, and if it does not, one of the two was written by
  improvising.
- **Zero model calls.**

Measured on 2026-09-04:

```text
body chars : 1850
sections   : ['Steps', 'Worked example']
```

Eight hundred characters for one example, roughly doubling the body. Worth it — and a good reason to
stop at one.

## When it breaks

**An example with an invented ticket id.** It reads perfectly and it is a lie in the file. The model
will happily produce `lookup_ticket("1234")` in a real conversation because that is what the example
showed, and the tool will return a not-found message for a ticket the engineer never asked about.
Every value in an example should be one you can produce by running something.

**An example that skips the tool calls.** A worked example consisting only of a question and a
beautiful answer teaches the answer's shape and hides the work. The model then produces the shape
without the calls — a fluent, well-structured, ungrounded paragraph, which is the single worst output
this system can produce.

**An example that has drifted from the steps.** Edit step 2 and forget the example, and the body now
contains two different instructions about the same decision. The model has no way to know which is
current. This is the same one-fact-one-home problem as
[2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md), inside a single file — and it is why the
example is numbered to mirror the steps: a mismatch is visible rather than subtle.

**Three examples, one of which is now wrong.** The cost of examples is not only tokens; it is
maintenance. Every example is a thing that can go stale, and the probability that all three stay
correct is the probability that one stays correct, cubed.

## In production

**Regenerate examples from real runs, and date them.** An example is a snapshot of a system that
changes. The cheapest discipline that works is a comment in the body — *"trace captured 2026-09-04"* —
and a test that asserts the quoted tool output still matches what the tool returns. Three lines, and
it converts a silent drift into a red build.

**Prefer the boring case.** The instinct is to pick an interesting example, because interesting
examples are more fun to write. The model needs the *modal* case: the one that happens two hundred
times a week. Interesting cases belong in edge cases, where they take one line each.

**Watch for the example becoming the specification.** In a mature skill, people start reading the
example instead of the steps, and then they start editing the example to change behaviour. That is
fine, and it means the example needs the same review as the steps. The failure is a team where the
steps say one thing, the example shows another, and everybody has learned to trust the example — at
which point the steps are decoration.

**What changes at scale** is that one example stops covering the population. Forty skills across six
teams, and *"the modal case"* is different per team, per region, per plan tier. The answer is not more
examples in one body; it is either more skills
([1.2](1.2-one-job-four-words.md)) or examples moved into `references/` and fetched only when the case
matches, which is exactly the split [1.7](1.7-what-goes-behind-a-link.md) is about.

**The review comment a senior engineer leaves:** *"the worked example jumps from the question to the
answer. Show the two tool calls and what they returned — that is the part the steps cannot teach, and
without it we are training the model to write the paragraph without doing the work."*

**The interview question:** *"how many examples do you put in a skill?"* The answer that shows you have
priced it: *"one, unless a second case has a genuinely different shape. The body is loaded whole on
activation and carried for the rest of the conversation, so every example is a permanent cost — ours
roughly doubled the body. And the second example's benefit is small, because the first one already
taught the shape. What the one example must include is the tool calls and their real returned values,
not just the final answer, or you teach the model to produce the answer without doing the work."*
