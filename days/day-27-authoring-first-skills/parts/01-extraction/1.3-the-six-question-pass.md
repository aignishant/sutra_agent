# 1.3 — The six-question pass, and where each answer lands

## One-line answer

Six questions — scope, trigger, steps, example, edges, overflow — turn a procedure in your head into a
skill folder, and each answer has exactly one destination, so nothing ends up in two places.

## The story

The leave application form has six boxes and you have never thought about any of them until now.

Dates from and to. Type of leave. Reason. Who is covering your work. Contact number while away.
Signature. It takes four minutes and it feels like bureaucracy, right up to the box that says *who is
covering your work* — and you stop, because you had not thought about it, and it turns out somebody has
to.

That box is the whole reason the form exists. Not the record-keeping. The form is a list of the
questions people forget to ask themselves, arranged so they cannot be skipped, and the value is in the
one box that makes you put the pen down.

## The idea in plain language

Extraction has six questions. They are always the same six, they are asked in this order, and each
answer goes to exactly one place in the folder:

| # | The question | Where the answer goes |
| --- | --- | --- |
| 1 | What **one job** is this? | the folder name and `name` |
| 2 | **When** should an agent reach for it? | `description` |
| 3 | What would I tell a careful new colleague, **in order**? | the body's numbered steps |
| 4 | What does **one** real case look like, start to finish? | the body's worked example |
| 5 | Where have I actually been **burned**? | the body's edge cases |
| 6 | What is **true but long**? | a file in `references/` |

Question 1 was [1.2](1.2-one-job-four-words.md). Questions 3 to 6 are the next three parts. This part
is about the pass as a whole and about question 2, because question 2 is the box that makes you put
the pen down.

**Question 2 is not "what does this do".** It is *when should an agent reach for this*, and the
difference decides whether the skill is ever used. Day 25 measured it: a description with both halves
— what it does **and** when to use it — overlapped seven words with realistic requests, and deleting
only the *"use when"* sentence took it to three
([25.2.3](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.3-the-description-field.md)).

Two rules make the "when" half work, and both are about vocabulary rather than about accuracy:

**Use the requester's words, not yours.** A support engineer types *"how bad is 4521?"* and
*"what priority is this?"*. They do not type *"perform severity classification"*. The description
exists to be matched against what people actually write.

**Name the trigger conditions, not the trigger category.** *"Use when triaging"* is a category and
matches nothing. *"Use when a ticket arrives without a severity, when someone asks how urgent a ticket
is, or when the words triage, severity or priority appear"* is three conditions, and each is a
separate chance to match.

There is a limit worth knowing before you write: **1024 characters** for the description, enforced by
ADK's own validator
([26.1.3](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.3-building-a-skill-in-code.md)).
That is generous — roughly a long paragraph — and the constraint that bites first is not the ceiling
but the cost: every character of the description is paid for in the index on every listing
([26.5.1](../../../day-26-loading-skills-into-adk/parts/05-in-production/5.1-what-a-skill-really-costs-here.md)),
and a longer description dilutes its own overlap.

## Why Sutra needs it

Because the two folders from [1.2](1.2-one-job-four-words.md) are empty and the next four parts each
fill one section of them. Without an order, the writing turns into an essay: people start with the
steps, discover the steps depend on an edge case, go back, and produce a document with the rules
scattered through it.

The order also protects against the specific failure Day 26 measured. The description is written at
question 2, **before** the steps — so it is written against the job rather than against the document.
A description written last is a summary of what you happened to write, and summaries make bad
selection interfaces.

And there is one Sutra-specific reason to do the pass properly today: two skills are being written at
once. Six questions asked twice, in the same order, is what stops the two bodies from drifting into
different shapes — which matters more than it sounds, because Day 28 is going to redesign both and a
consistent shape is a shape you can redesign.

## The mechanism

The pass, run once for `ticket-triage`. Questions 1 and 2 produce the frontmatter; 3 to 6 produce the
rest and are the next three parts.

```yaml
---
name: ticket-triage
description: Sutra's standard procedure for triaging a support ticket - look the ticket up, find
  the symptom, search the knowledge base, and choose a severity with the rule that decided it. Use
  when a ticket id needs triage, when someone asks how urgent or serious a ticket is, when a
  severity or priority has to be set, or when a first diagnosis is wanted.
license: Apache-2.0
metadata:
  owner: support-desk
  version: "1.0"
---
```

**Line by line:**

- `name: ticket-triage` matches the folder exactly, because the loader refuses otherwise
  ([26.1.1](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.1-load-skill-from-dir.md)).
  Lowercase kebab-case, no underscore — the validator rejects underscores even though a docstring in
  the same file says otherwise
  ([26.5.2](../../../day-26-loading-skills-into-adk/parts/05-in-production/5.2-experimental-means-experimental.md)).
- The description is **two sentences and they do different jobs.** The first is *what*, and it names
  the four steps in the order they happen so the model can tell at a glance whether this is the right
  procedure. The second is *when*, and it is four conditions rather than one category.
- The "when" sentence contains the words a support engineer actually types: `urgent`, `serious`,
  `severity`, `priority`, `triage`, `first diagnosis`. Those are the overlap, and
  [4.3](../04-the-authoring-loop/4.3-sharpening-without-a-model.md) measures them rather than trusting
  them.
- The description is written in YAML **block form** — the continuation lines are indented, so YAML
  folds them into one string. Note there is no colon-space inside it: an unquoted description
  containing `: ` becomes a nested mapping and the failure is confusing
  ([25.2.1](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.1-two-required-fields.md)).
  The dashes in *"ticket - look the ticket up"* are there instead of colons for exactly that reason.
- `license: Apache-2.0` matches the repository's licence. It is optional, it is never read by ADK, and
  it is sent to the model on every activation as part of the frontmatter dump
  ([26.2.3](../../../day-26-loading-skills-into-adk/parts/02-the-four-tools/2.3-what-activation-actually-costs.md))
  — which is an argument for keeping the rest of the frontmatter short, not for dropping the licence.
- `metadata.owner` and `metadata.version` are Sutra's own keys, and `version` is **quoted** because
  unquoted YAML turns `1.10` into the float `1.1`
  ([25.2.4](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.4-the-optional-fields.md)).
  `owner` is the answer to *"who is allowed to change this"*, which [1.2](1.2-one-job-four-words.md)
  said decides scope; writing it in the file makes the answer checkable.
- There is **no `adk_additional_tools` key yet**. It belongs to question 3 — you cannot declare the
  tools a procedure needs before you have written the steps that need them — and
  [3.2](../03-procedure-and-capability/3.2-honouring-the-contract.md) adds it.

And the same pass, questions 1 and 2, for the second skill:

```yaml
---
name: kb-answer-style
description: The house style for a customer-facing reply that is grounded in one knowledge-base
  article - structure, tone, and how to cite the article id. Use when drafting or rewriting a reply
  to a reporter, when a reply has to cite a KB article, or when someone asks how we word an answer.
license: Apache-2.0
metadata:
  owner: customer-comms
  version: "1.0"
---
```

**Line by line:**

- A different `owner`, which is the point of [1.2](1.2-one-job-four-words.md)'s split written down in
  a machine-readable place.
- The "when" half names *drafting*, *rewriting*, *cite*, *word an answer* — none of which appear in
  `ticket-triage`'s description. Two skills whose trigger words overlap are two skills the model has
  to choose between, and [5.2](../05-failure-lab/5.2-two-notices-on-one-door.md) is what that costs.
- The description says **one** article, singular, which is a scope boundary hiding in a word. A reply
  synthesising four articles is a different job, and this description declines it.

Check both frontmatters load before writing another line:

```bash
uv run python -c "
from pathlib import Path
from google.adk.skills import load_skill_from_dir
for name in ('ticket-triage', 'kb-answer-style'):
    s = load_skill_from_dir(Path('skills') / name)
    print(f'{s.name:18} desc {len(s.frontmatter.description):>4} chars, body {len(s.instructions):>4} chars')
"
```

**Line by line:**

- Loading is the cheapest possible check that the YAML is valid, the name matches the folder and the
  description is inside its limit. **Zero model calls.**
- Printing the body length as well is a small habit worth having: at this point in the day it should
  be near zero, and by the end of section 1 it should not be. It is a progress bar you did not have to
  build.

Measured on 2026-09-04, with both bodies still empty:

```text
ticket-triage      desc  344 chars, body    0 chars
kb-answer-style    desc  278 chars, body    0 chars
```

Both well under the 1024-character ceiling, and both costing about a third of it.

## When it breaks

**Questions asked out of order.** Writing the steps first and the description afterwards produces a
description that summarises the document. It reads well and it selects badly, because the words a
reader would use to *summarise* a procedure are not the words a requester uses to *ask for* one.

**An empty body that loads fine.** The check above passes with a body of zero characters, because the
format requires only the two frontmatter fields
([25.2.1](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.1-two-required-fields.md)). A
loading skill is not a finished skill, and the `body 0 chars` column is there so you cannot mistake
one for the other.

**A colon in an unquoted description.** The most common YAML failure in a skill. Write
`description: Sutra: the standard triage procedure for a support ticket.` and the loader refuses
before pydantic ever sees it:

```text
ValueError: Invalid YAML in frontmatter: mapping values are not allowed here
  in "<unicode string>", line 3, column 19:
    description: Sutra: the standard triage procedure  ...
                      ^
```

The caret points at the **second** colon, which is the one YAML could not accept: it had already
decided `description` was the key, and a second `: ` inside the value looks like a nested mapping.
Quote the whole description, or write around the colon the way the one above does with a dash.

**A description over the ceiling.** Rarely a problem in practice, and the message is exact when it is:

```text
ValidationError: description
  Value error, description must be at most 1024 characters. Description length: 1100
```

## In production

**Keep the six questions somewhere people can find them.** A team's second skill is written by someone
who did not write the first, and the difference between a consistent collection and a pile is whether
the second author had the same six boxes. A `skills/README.md` with the table in it costs nothing and
is the highest-leverage document in the folder.

**Review the description separately from the body, and by a different person.** They are two different
artefacts with two different audiences: the description is read by a model choosing, the body by a
model executing. Teams that review them together review the body and skim the description, which is
exactly backwards — the body only matters if the description worked.

**Put the owner in the metadata and mean it.** `metadata.owner` is the field that turns "somebody
should update this" into a name. It costs a few tokens on every activation, which is a real cost and a
small one, and the alternative is a skill that goes stale because it belongs to everybody.

**What changes at scale** is that question 2 becomes the hard one and stays hard. With forty skills,
descriptions start competing: two of them both plausibly match *"how urgent is this?"*, and the model
picks one. At that point the discipline shifts from writing a good description to writing a
**distinguishing** one, and the review question becomes *"which existing skill does this one now
overlap with?"* — a question nobody can answer without reading all forty, which is why the index is
worth printing regularly.

**The review comment a senior engineer leaves:** *"the description explains what the skill does and
never says when to use it. That is the half that carries the selection — add the trigger conditions in
the words an engineer would actually type, and put the owner in the metadata while you are in there."*

**The interview question:** *"how do you write a skill's description?"* The answer that shows you have
measured it: *"two sentences with two jobs. The first says what the procedure does, in the order it
happens. The second says when to reach for it — as concrete conditions, in the vocabulary of whoever
is asking, not as a category. The second one carries most of the findability: we measured word overlap
against real requests and deleting the 'use when' sentence more than halved it. And it is written
before the body, so it describes the job rather than summarising the document."*
