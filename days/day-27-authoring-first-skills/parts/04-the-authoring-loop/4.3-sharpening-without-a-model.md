# 4.3 — Sharpening without a model: the preflight

## One-line answer

Four checks — required tools, dead links, unused references, and the house shape — run in under a
second with no key and no quota, and they catch the mistakes that would otherwise be discovered by
spending a request to find out.

## The story

You read the letter once more before you fold it.

Not for the argument — the argument was settled while you were writing it — but for the things that
would embarrass you at the other end. The date says last month. There is a *"see attached"* and there
is nothing attached. The second paragraph says *"as I mentioned above"* and you moved that paragraph
to the bottom yesterday.

Four minutes. None of it required you to be clever, and all of it was invisible while you were writing,
because while you were writing you knew what you meant.

The alternative is posting it and finding out in a week.

## The idea in plain language

[4.1](4.1-draft-run-read-sharpen.md) established that Sutra gets four to six loop iterations a day.
That is a hard budget, and it makes one question worth asking before every run: **could a script have
told me this?**

Sort the things that can be wrong with a skill into two piles:

| Only a model can tell you | A script can tell you |
| --- | --- |
| whether the description gets selected | whether the required tools exist |
| whether the steps get followed | whether the body's links resolve |
| whether the answer is any good | whether a reference is orphaned |
| whether the tone is right | whether the body has the house sections |

The right-hand column costs nothing and takes a second. Every item in it, discovered by a live run
instead, costs three to five generations and an iteration you cannot get back.

Two of those checks were built earlier in the day and one is new:

- **required tools** — the lint from
  [3.1](../03-procedure-and-capability/3.1-a-named-tool-is-a-contract.md), comparing
  `adk_additional_tools` against the tools the system actually provides;
- **dead links** — every `references/…` link in a body must resolve to a real reference key
  ([1.7](../01-extraction/1.7-what-goes-behind-a-link.md)), because a broken one ends the turn at
  request time
  ([26.2.4](../../../day-26-loading-skills-into-adk/parts/02-the-four-tools/2.4-the-third-rung-and-its-fence.md));
- **unused references** — the reverse: a file in `references/` that no body links to can never be
  fetched, because `load_skill_resource` is a fetch by exact path and not a directory listing;
- **the house shape** — every body has `## Steps`, `## Worked example` and `## Edge cases`, which is
  the six-question pass ([1.3](../01-extraction/1.3-the-six-question-pass.md)) made checkable.

The last one is the one that will feel like bureaucracy and is not. A missing section is not a style
problem: no worked example means the shape is untaught
([1.5](../01-extraction/1.5-one-worked-example.md)), and no edge cases usually means somebody wrote a
skill without asking question 5.

## Why Sutra needs it

Because this is the day's eval, and it is the one thing here that can go **red**.

Everything else in Day 27 is prose. Prose does not fail a build. Principle 11 asks every day to end
with at least one check that can go red, and a day about writing documents has to find that check
somewhere real — which it does, because a skill is a document with structure, and structure is
checkable.

There is also a sequencing reason. Day 31 wires a skills lint into `./m check`, and Day 25 asked, as a
`TODO(me)`, for three checks the spec validator does not make
([25.5.1](../../../day-25-skills-the-open-spec/parts/05-in-production/5.1-validating-before-you-ship.md)).
These are those three plus one. Writing them today, against skills that exist, means Day 31 is wiring
rather than inventing.

## The mechanism

One script, four checks, one exit code.

```python
# days/day-27-authoring-first-skills/lab/preflight.py
"""Every check on a skill that does not need a model. Exit 1 if any finding stands."""

import pathlib
import re
import sys

from google.adk.skills import load_skill_from_dir, models

SHELF = pathlib.Path("skills")
LINK = re.compile(r"\]\((references/[^)]+)\)")


def skills_on(shelf: pathlib.Path) -> list[models.Skill]:
    """Every skill under the shelf, loaded one at a time."""
    return [load_skill_from_dir(p) for p in sorted(shelf.iterdir()) if (p / "SKILL.md").is_file()]


def unmet_tools(skill: models.Skill, provided: set[str]) -> list[str]:
    """Tool names the skill requires that nobody provides."""
    asked = set(skill.frontmatter.metadata.get("adk_additional_tools") or [])
    return sorted(asked - provided)


def dead_links(skill: models.Skill) -> list[str]:
    """references/ links in the body with no matching file in resources."""
    have = set(skill.resources.references)
    return sorted(
        {t for t in LINK.findall(skill.instructions) if t[len("references/") :] not in have}
    )


def unused_references(skill: models.Skill) -> list[str]:
    """Reference files the body never links to."""
    linked = {t[len("references/") :] for t in LINK.findall(skill.instructions)}
    return sorted(set(skill.resources.references) - linked)


def missing_sections(skill: models.Skill, expected: tuple[str, ...]) -> list[str]:
    """Headings the house shape requires and this body does not have."""
    have = set(re.findall(r"^## (.+)$", skill.instructions, re.M))
    return [s for s in expected if s not in have]


def main() -> int:
    from sutra.loop import TOOLS

    shape = ("Steps", "Worked example", "Edge cases")
    findings: list[str] = []
    for skill in skills_on(SHELF):
        for tool in unmet_tools(skill, set(TOOLS)):
            findings.append(f"{skill.name}: requires tool {tool!r}, which nothing provides")
        for link in dead_links(skill):
            findings.append(f"{skill.name}: body links {link!r}, which does not exist")
        for ref in unused_references(skill):
            findings.append(f"{skill.name}: reference {ref!r} is never linked from the body")
        for section in missing_sections(skill, shape):
            findings.append(f"{skill.name}: body has no '## {section}' section")
    for line in findings:
        print(line)
    print(f"findings: {len(findings)}")
    return 1 if findings else 0


if __name__ == "__main__":
    sys.exit(main())
```

**Line by line:**

- `LINK = re.compile(r"\]\((references/[^)]+)\)")` matches the **target** of a Markdown link, capturing
  only paths that start `references/`. That prefix is not decoration: it is the string the model must
  pass to `load_skill_resource`, and a link written without it is refused at request time. So this
  regex checks the thing that actually matters rather than every link in the document.
- `t[len("references/") :]` strips the prefix to get the **resource key**, because the loader keys
  references relative to their own folder
  ([26.1.2](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.2-the-skill-object.md)).
  Two spellings of one file, and this line is where they are reconciled.
- `dead_links` and `unused_references` are the same set difference in **both directions**, and both are
  worth having: one catches a link with no file, the other a file with no link. The second is the
  quieter failure — the material exists, is loaded into memory, and is unreachable.
- Each check is a **separate top-level function** taking a `Skill` and returning a list. That shape is
  not decoration either: every one of them is directly testable with a skill built in code
  ([26.1.3](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.3-building-a-skill-in-code.md))
  with no folder on disk, which is how Day 30 will test the lint itself.
- `from sutra.loop import TOOLS` is inside `main` for the same reason as in
  [3.1](../03-procedure-and-capability/3.1-a-named-tool-is-a-contract.md): the four checks import
  cleanly with no Sutra dependency, and only the runner needs the real registry. It reads the
  **dispatch table**, not a retyped list, so it cannot drift.
- `missing_sections` returns in the order of `expected` rather than sorted, so the output reads in the
  order the sections should appear — a small thing that makes the finding legible at a glance.
- `main()` **returns an exit code and `sys.exit`s it.** That single decision is what turns a report into
  a gate, and it is what Day 31 needs in order to put this in `./m check`.
- `findings: N` on the last line whether or not there are any, so a green run still prints something.
  A check that prints nothing when it passes is a check people cannot tell they ran.
- **Zero model calls, no key required.**

Three breaks, **four** findings — the renamed file is both a dead link and an orphan, which is exactly
right and is why both directions of the check exist. Every line names the skill and the thing, and the
exit code is 1.

## When it breaks

**A check that is right and unhelpful.** `unused_references` will fire on a reference you have added
and not yet linked, mid-edit, which is a normal state to be in. That is the correct behaviour for a
gate and an annoyance in an editor, and the resolution is where it runs rather than what it says: red
in CI, informational while you work.

**A regex that misses a link.** The pattern matches inline Markdown links only. A reference-style link,
or a bare path in prose, is invisible to it — so a body that says *"see references/severity-rubric.md"*
without brackets passes the dead-link check and can still send the model to a path that does not
exist. Worth knowing, and worth not over-engineering: the fix is to write links as links.

**The house shape enforced on a skill that does not need one.** A skill with no tools and no edge cases
is legitimate, and this check will fail it for a missing `## Edge cases`. The honest options are to
allow an empty section, to make the shape configurable, or to accept that every skill writes at least
one edge case. Sutra takes the third, because question 5 has an answer for every real procedure.

**Green preflight, broken skill.** The whole left-hand column of the table is still unchecked. A skill
that passes every one of these can still have a description nobody selects and steps nobody follows.
The preflight buys iterations; it does not replace them.

## In production

**Run it on every change to `skills/`, and make it a required check.** The four findings it produces are
all things that would otherwise be found by a user, at request time, one at a time. There is no
argument for discovering them slowly.

**Add checks as you find failures, and keep them cheap.** The rule that keeps a lint alive is that it
must be fast and it must not cry wolf — a five-in-seven false positive rate kills a check in its second
week ([1.4](../01-extraction/1.4-steps-for-a-competent-stranger.md) found exactly that rate for a
backtick-based tool scan, which is why the tool check reads the declared list instead).

**Report findings, not a boolean.** Each line names the skill and the specific problem, which means the
person who broke it can fix it without reading the lint's source. A check that prints `FAILED` is a
check that generates a conversation.

**What changes at scale** is that the preflight becomes the definition of a valid skill in your
organisation, and it stops being obvious that it is yours. New teams will assume it is the spec.
Documenting what it checks and what it deliberately does not — *"we do not check that the description
is good, because we cannot"* — is what stops people believing a green build means a working skill.

**The review comment a senior engineer leaves:** *"the preflight is green and this skill has never been
run against a model. Green means the plumbing is sound, not that it works — put three transcripts in the
pull request."*

**The interview question:** *"what can you check about a skill without running it?"* The answer that
shows you have drawn the line: *"more than people expect and less than they hope. That the tools its
steps require actually exist, that every `references/` link resolves, that no reference is orphaned,
and that the body has the sections our house shape requires. Those run in under a second with no key,
and each one would otherwise cost a live run to discover. What you cannot check without a model is the
part that matters most — whether the description gets selected and whether the steps get followed — so
the preflight exists to stop you spending scarce iterations on things a regex could have told you."*
