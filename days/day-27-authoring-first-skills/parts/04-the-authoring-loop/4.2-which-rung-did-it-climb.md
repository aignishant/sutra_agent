# 4.2 — Which rung did it climb: turning a transcript into a verdict

## One-line answer

The list of tool calls a run made, in order, is enough to say which rung the model stopped at — so the
diagnosis can be a twenty-line function rather than a judgement, and that function is testable without
a model.

## The story

The parcel was marked *"attempted delivery — nobody home"*, and somebody was home all day.

The argument that follows is unwinnable in both directions. He says he rang; she says the bell works
and she was in the front room. Neither of them is lying, exactly, and there is no way to settle it from
what either of them remembers.

Then the neighbour mentions the camera above his porch, which happens to see the gate. Eleven seconds
of footage: a van stops, a man walks to the gate, photographs the house number, and walks back.

Nobody has to be persuaded of anything after that. The thing that made it settleable was not a better
memory — it was a record of what happened, kept for a reason that had nothing to do with this argument.

## The idea in plain language

Day 26 laid out the ladder and named the three model decisions between *"a skill exists"* and *"a skill
was followed"*
([26.4.3](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.3-the-manual-nobody-opened.md)).
[4.1](4.1-draft-run-read-sharpen.md) turned the observations into an edit table. This part makes the
mapping mechanical.

The input is two things a run produces, both cheap to collect:

- **the tool call names, in order** — `["list_skills", "load_skill", "lookup_ticket", ...]`;
- **the activation register** — `_adk_activated_skill_desk`, read off the session afterwards.

From those two, the rung the run reached is determined. There is no judgement in it:

| Evidence | Rung reached | The edit |
| --- | --- | --- |
| no `list_skills` | 0 — never looked | the instruction |
| `list_skills`, no `load_skill` | 1 — looked, chose nothing | the description |
| activated something else | 1 — chose wrong | both descriptions |
| activated, a required tool never called | 2 — read, did not follow | the steps |
| all tools called, no reference fetch | 3 — followed, stayed shallow | step 6, or the split |
| everything | 4 — full climb | nothing; look at the answer |

The last row is the interesting one. When the mechanics are all green, the remaining question is
whether the answer is any good — and that is a judgement, which is where a human belongs. The point of
the table is to stop humans from spending judgement on things a comparison can settle.

Two properties make this worth writing as code rather than reading by eye:

**It is deterministic.** Same inputs, same verdict, and a verdict you can put in a test.

**It does not need a model.** The function takes lists of strings. The lists come from a run that costs
quota, but the function itself can be tested exhaustively for nothing — which means the diagnosis
logic is trustworthy before the first expensive run is spent on it.

## Why Sutra needs it

Because [4.1](4.1-draft-run-read-sharpen.md)'s loop has four to six iterations a day and each one
produces a wall of output that has to be read correctly under mild time pressure.

Reading a transcript by eye works and it fails in a specific way: you see what you expected. A run
where `load_skill` was called and `search_kb` was not looks, at a glance, like a run that worked —
because the interesting line is present and the missing one is, by definition, not there. Absence is
the hardest thing to notice, and it is the thing this whole day keeps turning on.

There is a second reason and it outlasts today. This function is the seed of Day 30's tests. *"The
triage skill was activated and both its tools were called"* is an assertion, and it is the assertion
that distinguishes a skill that works from an answer that reads well.

## The mechanism

The verdict function, and it is deliberately dull.

```python
# days/day-27-authoring-first-skills/lab/which_rung.py
"""Turn a run's tool calls and activation record into a verdict about which rung it reached."""

from dataclasses import dataclass


@dataclass(frozen=True)
class Verdict:
    """Which rung a run reached, and the one thing to edit next."""

    rung: int
    finding: str
    edit: str


def which_rung(
    calls: list[str],
    activated: list[str],
    expected_skill: str,
    required_tools: set[str],
) -> Verdict:
    """Diagnose one run from its calls and its activation record.

    Args:
        calls: tool names in the order they were called.
        activated: the skills recorded in `_adk_activated_skill_<agent>`.
        expected_skill: the skill this request should have used.
        required_tools: the tools that skill's steps name.
    """
    if "list_skills" not in calls:
        return Verdict(0, "never listed the skills", "the agent instruction")
    if "load_skill" not in calls:
        return Verdict(1, "listed and activated nothing", f"{expected_skill}'s description")
    if expected_skill not in activated:
        return Verdict(1, f"activated {activated} instead", "both descriptions")
    missing = sorted(required_tools - set(calls))
    if missing:
        return Verdict(2, f"activated but never called {missing}", f"{expected_skill}'s steps")
    if "load_skill_resource" not in calls:
        return Verdict(3, "followed the steps, fetched no reference", "the step that links it")
    return Verdict(4, "full climb", "nothing - now read the answer")
```

**Line by line:**

- A **frozen dataclass** rather than a tuple or a dict, so the three fields have names at the call site
  and nothing can mutate a verdict after the fact. `rung` is the number, `finding` is what to say out
  loud, `edit` is where to go.
- The checks are in **ladder order**, and that ordering is the design. Each one is only reached if
  every rung below it succeeded, so the first failure returned is the **lowest** failure — which is the
  one to fix, because fixing a higher rung when a lower one is broken changes nothing.
- `"list_skills" not in calls` is first because it is the failure that no amount of description work
  can fix, and it is the one people diagnose last
  ([26.4.3](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.3-the-manual-nobody-opened.md)).
- `expected_skill not in activated` uses the **register**, not the calls, because that is the record
  ADK itself keeps and it is what Day 30's tests will assert on
  ([26.3.3](../../../day-26-loading-skills-into-adk/parts/03-wiring-the-toolset/3.3-activation-is-a-line-in-state.md)).
  A `load_skill` call that returned `SKILL_NOT_FOUND` appears in `calls` and not in `activated`, and
  this line is what separates those two.
- `required_tools - set(calls)` is a **set difference**, and `sorted()` on the result so the message is
  stable between runs. The tools come from the skill's own metadata
  ([3.1](../03-procedure-and-capability/3.1-a-named-tool-is-a-contract.md)), so the function is checking
  the procedure against its own declared requirements rather than against a list somebody retyped.
- The `load_skill_resource` check is **last and softest**, and its `edit` field says *"the step that
  links it"* rather than asserting a fault — because a run that did not need the rubric is a run that
  correctly did not fetch it. Rung 3 is information, not a failure.
- Rung 4's edit is *"nothing - now read the answer"*, which is the function knowing where its own
  competence ends. A diagnostic that pretends to judge quality is a diagnostic people stop trusting.

The tests, which need no model and cover every branch:

```python
# days/day-27-authoring-first-skills/lab/test_which_rung.py
"""Every rung, including the ones that are easy to get wrong."""

from which_rung import which_rung

TOOLS = {"lookup_ticket", "search_kb"}
FULL = ["list_skills", "load_skill", "lookup_ticket", "search_kb", "load_skill_resource"]


def test_never_listed() -> None:
    assert which_rung([], [], "ticket-triage", TOOLS).rung == 0


def test_listed_but_activated_nothing() -> None:
    assert which_rung(["list_skills"], [], "ticket-triage", TOOLS).rung == 1


def test_activated_the_wrong_skill() -> None:
    verdict = which_rung(["list_skills", "load_skill"], ["kb-answer-style"], "ticket-triage", TOOLS)
    assert verdict.rung == 1
    assert "kb-answer-style" in verdict.finding


def test_called_load_skill_but_it_failed() -> None:
    verdict = which_rung(["list_skills", "load_skill"], [], "ticket-triage", TOOLS)
    assert verdict.rung == 1


def test_activated_but_skipped_a_tool() -> None:
    calls = ["list_skills", "load_skill", "lookup_ticket"]
    verdict = which_rung(calls, ["ticket-triage"], "ticket-triage", TOOLS)
    assert verdict.rung == 2
    assert "search_kb" in verdict.finding


def test_no_reference_fetch() -> None:
    verdict = which_rung(FULL[:-1], ["ticket-triage"], "ticket-triage", TOOLS)
    assert verdict.rung == 3


def test_full_climb() -> None:
    assert which_rung(FULL, ["ticket-triage"], "ticket-triage", TOOLS).rung == 4
```

**Line by line:**

- Seven tests for six branches, and the extra one is `test_called_load_skill_but_it_failed`: the tool
  was called and nothing was activated, which is what a `SKILL_NOT_FOUND` looks like from outside
  ([26.2.3](../../../day-26-loading-skills-into-adk/parts/02-the-four-tools/2.3-what-activation-actually-costs.md)).
  It lands on rung 1 with the same verdict as "chose nothing", which is a deliberate simplification and
  worth knowing about.
- `FULL[:-1]` in the reference test rather than a retyped list, so the two cases cannot drift apart.
- `assert "search_kb" in verdict.finding` checks the **message**, not just the number. A diagnosis that
  gets the rung right and names the wrong tool sends you to the wrong line.
- Every input is a plain list of strings. There is no ADK import in this file at all, which is why it
  runs in milliseconds and belongs in the default suite
  ([23.2.5](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.5-markers-and-the-not-live-line.md)).

## When it breaks

**A verdict that is right and useless.** Rung 3 fires on every run where the rubric was not fetched,
including the ones where the ticket obviously matched row one and no fetch was needed. Read rung 3 as
*"look at this"*, not *"fix this"* — the `edit` field says *"the step that links it, or the split"* for
exactly that reason.

**Tool calls the procedure did not ask for.** `which_rung` checks that the **required** tools were
called and says nothing about extras. A run that called `search_kb` four times passes rung 2 cleanly.
That is a real gap and the fix is a second, separate check on call **counts**, which is a `TODO(me)`
rather than a complication of this function.

**A skill activated late.** The register is a set-like list with no timestamps, so a run that answered
first and activated afterwards looks identical to one that did it in the right order. The call order in
`calls` is the only ordering information available; using it properly means comparing indices rather
than membership, and that is worth adding the day you see it happen.

**The function drifting from ADK's tool names.** `list_skills`, `load_skill` and `load_skill_resource`
are string literals here, and they are ADK's names on an experimental surface
([26.5.2](../../../day-26-loading-skills-into-adk/parts/05-in-production/5.2-experimental-means-experimental.md)).
If a version renames one, every run diagnoses as rung 0 — a monitoring failure that looks exactly like
the failure being monitored, which is the same trap Day 26 flagged. The surface test from that part is
what catches it.

## In production

**Run the verdict on live traffic, not only during authoring.** The two inputs are available from any
invocation: the calls from the events, the register from the session. A daily count by rung is the
single most useful number about a skills deployment — *"eighty per cent rung 4, twelve per cent rung 0"*
tells you immediately whether to work on descriptions or on the instruction.

**Alert on rung 0 specifically.** It is the only rung that means the skills system is not being used at
all, and it is invisible in every other measure: the answers are fluent, the latency is good, and the
token bill is lower than usual. A rising rung-0 rate after a prompt change is the fastest signal you
will get that the change broke skill selection.

**Keep the verdict beside the transcript in the pull request.** A skill change reviewed with three
transcripts and three verdicts is reviewable in two minutes. The same change reviewed with three
transcripts alone requires the reviewer to do the diagnosis themselves, which they will not.

**What changes at scale** is that the expected skill stops being obvious. With two skills you know
which one *should* have fired; with forty, the question *"was this the right skill?"* is itself a
judgement, and the verdict function can only check that **something** was activated and that its
declared tools were called. At that point the useful measure shifts from "did the right one fire" to
the distribution of activations against the distribution of request types — which is a dashboard, not a
function.

**The review comment a senior engineer leaves:** *"the transcript shows the answer was fine, and it also
shows `search_kb` was never called — so the citation in that answer was invented. Run it through
`which_rung`: that is a rung 2, and the edit is step 4 of the body, not the description."*

**The interview question:** *"how do you debug a skill that is not working?"* The answer that shows you
have a method rather than an instinct: *"from the tool calls and the activation record, in ladder
order. No `list_skills` means the model never looked, and that is the instruction, not the description.
Listed but nothing activated is the description. Activated but a required tool never called is the
steps. All the tools called and no reference fetched is the split. And only when all of those are clean
do I read the answer, because that is the only part that needs judgement. It is about twenty lines of
code and it turns a wall of transcript into one line naming the file to edit."*
