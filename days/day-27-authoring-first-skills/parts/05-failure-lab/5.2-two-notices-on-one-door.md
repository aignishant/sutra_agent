# 5.2 — 💥 Two notices on one door

## One-line answer

Skip the deletion half of extraction and the handbook and the skill end up describing the same field
with two different words — *priority* in one, *severity* in the other — and the model receives both,
in the same request, with no way to know which is current.

## The story

🎬 **The scene.** The door between the office and the stairwell has two notices on it at eye level.
The older one, sun-faded, says PUSH. The newer one, printed and laminated, says PULL. Somebody changed
the hinges in the spring.

😬 **The naive fix.** Everybody who works there has learned to pull, so nobody removes the old one.
Taking a sign down is a decision; leaving it is not.

💥 **Why it fails.** It works perfectly for the people who know. It fails for the courier, the new
starter, the person carrying a box with both hands who reads the top sign because it is the one at eye
level. And it fails silently: they push, the door does not move, they assume it is locked, and they go
back down. Nobody ever hears about it.

💡 **The insight.** **Two instructions for one thing is not redundancy, it is a coin flip** — and the
person who flips it is always the one with the least context.

## The idea in plain language

[2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md) said extraction is a move and not a copy,
and gave the failure in the abstract. Here it is in Sutra's own files.

`sutra/desk/agent.py`'s instruction, as written on Day 6, says:

> Recommend a priority - low, normal or high - with one reason.

`skills/ticket-triage/` and its rubric, written this afternoon, say **severity**, nine times, with the
same three values.

That is one field with two names, and the model receives both in the same request: the instruction
always, the skill body after activation. Nothing in the format, the loader, the toolset or the runtime
compares them
([26.5.2](../../../day-26-loading-skills-into-adk/parts/05-in-production/5.2-experimental-means-experimental.md)
is about a page and a package disagreeing; this is two of your own files).

The consequences are worse than they look, because they are not evenly distributed:

**On a run where the skill fires**, the model has both words and will probably use the skill's — the
body is more recent in the context and more specific.

**On a run where the skill does not fire**, it uses *priority*, and the answer is shaped by the older,
vaguer rule with no rubric behind it.

**Downstream, both are strings.** Anything that parses the answer, greps the logs, or builds a
dashboard now has two field names for one concept, and only the runs that used one of them are
counted.

So the failure is not that the agent gives a wrong answer. It is that it gives **two kinds of right
answer** depending on something invisible, and every measurement built on top of it quietly splits in
half.

## Why Sutra needs it

Because this is not a hypothetical: it is the state of the repository the moment section 1 is finished
and section 2 is not.

`ticket-triage` was written in section 1 using *severity*, which is the right word — it is what the
rubric is called, it is what support means, and it is not the same concept as the queue priority an
engineer might set later. The instruction has said *priority* since Day 6 and nobody has re-read it.

[2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md)'s rewrite deletes the sentence, and that
deletion is the entire fix. This part exists so that the deletion is not experienced as tidying —
because the version of this day where you write two beautiful skills and leave the instruction alone
is a version that ships this bug.

## The mechanism

Count both vocabularies in one place. The disagreement is a table, not an opinion.

```python
# days/day-27-authoring-first-skills/lab/two_notices.py
"""Count the words the handbook and the skill each use for the same field."""

import pathlib
import re

from google.adk.skills import load_skill_from_dir

from sutra.desk.agent import INSTRUCTION

WORDS = ("priority", "severity", "critical", "high", "normal", "low", "medium")

skill = load_skill_from_dir(pathlib.Path("skills") / "ticket-triage")
procedure = skill.instructions + (skill.resources.get_reference("severity-rubric.md") or "")

print(f"{'word':12} {'handbook':>9} {'skill':>6}")
for word in WORDS:
    in_handbook = len(re.findall(rf"\b{word}\b", INSTRUCTION, re.I))
    in_skill = len(re.findall(rf"\b{word}\b", procedure, re.I))
    print(f"{word:12} {in_handbook:>9} {in_skill:>6}")
```

**Line by line:**

- `WORDS` is written by hand and is the whole judgement in this script. There is no way to discover
  *"these two words mean the same field"* automatically, so the list is the part a person maintains —
  and keeping it short and specific to your domain is what stops it becoming noise.
- The skill's text is the body **plus the reference**, because a rubric fetched at rung 3 reaches the
  model too, and half of `severity`'s nine occurrences are in it. A comparison that reads only the body
  undercounts the vocabulary the model actually sees.
- `or ""` on the reference, so a renamed file produces a smaller count rather than a `TypeError`. The
  preflight ([4.3](../04-the-authoring-loop/4.3-sharpening-without-a-model.md)) is what catches the
  rename; this script should not also fail on it.
- `\b{word}\b` with `re.I` — word boundaries so that *low* does not match *below*, case-insensitive
  because a heading may capitalise it.
- Two columns rather than a verdict. A word appearing in **both** columns is fine; a word appearing in
  exactly one, when its synonym appears in the other, is the finding. That is a judgement, which is why
  this prints a table instead of an exit code.
- **Zero model calls.**

Run it from the repository root, **before** applying
[2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md)'s rewrite:

```bash
uv run python days/day-27-authoring-first-skills/lab/two_notices.py
```

**Line by line:**

- Needs no key. It imports `INSTRUCTION` from the module, so it reports on whatever is currently
  committed rather than on a copy.

Measured on 2026-09-04, against the Day 6 instruction and this day's skill:

```text
word          handbook  skill
priority             1      0
severity             0      9
critical             0      0
high                 1      1
normal               1      4
low                  1      1
medium               0      0
```

Read the top two rows together. `priority` appears once in the handbook and **never** in the skill;
`severity` appears nine times in the skill and **never** in the handbook. The three values agree —
`high`, `normal`, `low` in both — which is what makes it insidious: the vocabulary that disagrees is
the field name, and the vocabulary that agrees is everything around it.

The bottom row is worth a glance too. `medium` is zero in both, and it was in the legacy draft of this
rubric. A word that has left both files is a word that will still be in somebody's saved query.

Apply [2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md)'s rewrite — which deletes the whole
*"you do exactly three things"* block — and run it again. `priority` goes to zero in both columns, and
the field has one name.

## When it breaks

**The fix that adds instead of removing.** Changing the instruction to say *"severity (priority)"* puts
both words in one sentence and makes the model's output unpredictable in a new way. One name. Pick it,
and change every other place to match.

**The synonym you did not list.** This script finds what you tell it to look for. *Urgency*,
*importance*, *impact* — every domain has a cluster of near-synonyms, and the ones that bite are the
ones nobody thought were synonyms. The practical version of this check is to read the two documents
side by side once, properly, and use the script afterwards to keep them honest.

**The disagreement that is not about words.** Vocabulary is the easy case. The hard one is the
instruction saying *"at most three sentences"* while `kb-answer-style` teaches a three-paragraph
reply — two rules about length, no shared word, and a direct contradiction. Sutra has exactly that,
and it is resolved by audience: the handbook's limit is for answers **to the engineer**, and the style
skill is for replies **to the reporter**. That resolution has to be written in one of the two documents
or it is not a resolution, and it is why `kb-answer-style`'s scope line says *reporter*.

**The stale rule that is nobody's job.** *"You cannot look anything up"* survived twenty days
([1.1](../01-extraction/1.1-where-the-procedure-lives-now.md)) because re-reading the handbook was not
part of adding a tool. The class of bug is not "somebody was careless"; it is "the file has no reader".

## In production

**Make the diff show the transfer.** Add the skill and trim the instruction in the same commit, so a
reviewer sees a rule leaving one file and arriving in another. Two commits is a window in which both
are true, and windows like that outlive the sprint.

**Keep a glossary, and make it short.** Ten terms with one agreed word each — *severity*, not
*priority*; *article id*, not *KB reference*; *reporter*, not *customer* — is enough to settle most of
these before they are written. It costs one file and it is the cheapest alignment tool available.

**Grep on every skill change.** The script above is fifteen lines and takes a second. Run it when a
skill changes and when the instruction changes, because the failure appears when **either** side moves
and is invisible from either side alone.

**What changes at scale** is that the number of pairs explodes. One instruction and two skills is three
comparisons; one instruction and forty skills is forty, plus the skills against each other. Nobody
reads that. What survives is the glossary and a check that flags any new term in a skill that is not in
it — noisier than this script, and the only thing that works past a certain size.

**The review comment a senior engineer leaves:** *"the skill says severity and the prompt says
priority, and both go to the model in the same request. Delete the sentence from the prompt — it was
the procedure anyway — and add `severity` to the glossary so the next skill uses the same word."*

**The interview question:** *"what goes wrong when a rule is in the prompt and in a skill?"* The answer
that shows you have found one: *"they drift, and the drift is silent. Ours had the prompt calling the
field priority and the skill calling it severity, with the same three values — so the answer depended
on whether the skill fired, and any dashboard built on it counted half the runs. Nothing compares the
two files, so the fix is process: extraction is a move rather than a copy, the delete happens in the
same commit as the add, and a fifteen-line script counts the vocabulary on both sides whenever either
one changes."*
