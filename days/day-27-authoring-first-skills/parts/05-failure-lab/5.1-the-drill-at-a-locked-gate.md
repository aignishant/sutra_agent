# 5.1 — 💥 The drill at a locked gate

## One-line answer

Ship the procedure without the tools it names and everything looks correct — the skill loads, the
model activates it, the steps are read — and then step 1 is impossible, at which point the model does
something, and the something is not in your control.

## The story

🎬 **The scene.** The fire drill is at eleven. The alarm goes, four hundred people file down the
stairs exactly as the laminated notice says, and walk to the assembly point in the yard behind the
building. The gate to the yard is padlocked. It has been padlocked since the contractors left in
March.

😬 **The naive fix.** Somebody says *"we should have checked the gate"*, everybody agrees, and the
drill is recorded as completed with a note.

💥 **Why it fails.** The procedure was followed perfectly. Four hundred people did exactly the right
thing and ended up standing in a corridor, and the reason is not that anybody was careless — it is
that the notice and the padlock are maintained by different people and nothing ever compares them. A
note in a file does not compare them either. Next March there will be different contractors.

💡 **The insight.** **A procedure is a claim about the world**, and a claim nobody checks is a claim
that decays silently. The failure is never in the procedure or in the world; it is in the absence of
anything that reads both.

## The idea in plain language

`ticket-triage`'s step 1 says *"Call `lookup_ticket` with the ticket id"*. Build the toolset without
`additional_tools`, or misspell one name in the metadata, or rename the Python function, and the model
is handed a procedure whose first step names a tool that is not in its menu.

Everything up to that point works. The skill loads, the index lists it, `load_skill` returns the body,
the activation is recorded. The verdict function from
[4.2](../04-the-authoring-loop/4.2-which-rung-did-it-climb.md) would report **rung 2** — activated but
never called the required tools — and it would be right, but it cannot tell you *why*, because from the
outside "the model chose not to" and "the tool was not there" look identical.

What the model does next is the interesting part, and it is genuinely not in your control. There are
three plausible behaviours and you get one of them, per run:

**Refuse honestly.** *"I do not have a tool to look up tickets."* This is the good outcome, and Sutra
has stacked the deck for it: the instruction's honesty rule survived
[2.1](../02-what-leaves-the-prompt/2.1-one-fact-one-home.md) precisely because it has to hold when no
skill is in play.

**Improvise.** Answer from the ticket id and general knowledge, producing a fluent, confident,
ungrounded paragraph — the single worst output this system can make, because it is indistinguishable
from a good one until somebody checks the ticket.

**Substitute.** Use whatever tool it does have. If `search_kb` is present and `lookup_ticket` is not, a
model that searches the KB for *"4521"* has done something reasonable-looking and useless.

Three outcomes, one of them acceptable, and no way to choose. That is what makes this a design failure
rather than a model failure: the system was constructed so that a model's judgement stands where a
guarantee should be.

## Why Sutra needs it

Because Sutra has, today, three independent ways to arrive here.

The pairing is a **string in a Markdown file** matched against a **Python function name**
([3.1](../03-procedure-and-capability/3.1-a-named-tool-is-a-contract.md)). Rename the function: broken.
Typo the metadata: broken. Build the toolset without `additional_tools`: broken. None of the three
produces an error, a warning or a log line at any layer
([26.4.2](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.2-the-tool-that-never-appeared.md)).

And the third way is the most likely, because it is the *default*. `SkillToolset(skills=skills)` is the
obvious constructor call. `additional_tools=[...]` is the thing you have to remember. A refactor that
simplifies the agent builder can delete it without any test going red.

## The mechanism

Reproduce it deterministically, with no quota, by building the toolset both ways.

```python
# days/day-27-authoring-first-skills/lab/locked_gate.py
"""The same activated skill, with and without the tools its steps name."""

import asyncio
import pathlib

from google.adk.skills import load_skill_from_dir
from google.adk.tools import skill_toolset

from sutra.loop import lookup_ticket, search_kb

SHELF = pathlib.Path("skills")


class FakeContext:
    """A context with the triage skill already recorded as activated."""

    def __init__(self) -> None:
        self.agent_name = "desk"
        self.invocation_id = "inv-1"
        self.state = {"_adk_activated_skill_desk": ["ticket-triage"]}


async def main() -> None:
    """Two toolsets, one skill, one difference."""
    skill = load_skill_from_dir(SHELF / "ticket-triage")
    named = set(skill.frontmatter.metadata.get("adk_additional_tools") or [])

    for label, extras in (("with tools", [lookup_ticket, search_kb]), ("locked gate", [])):
        toolset = skill_toolset.SkillToolset(skills=[skill], additional_tools=extras)
        tools = {t.name for t in await toolset.get_tools(FakeContext())}
        print(f"{label:12}: {len(tools)} tools, procedure needs {sorted(named - tools)}")


asyncio.run(main())
```

**Line by line:**

- The **same skill object** is used for both toolsets, so the procedure the model would read is
  identical in the two cases. Only the supply side differs, which is the point being isolated.
- `FakeContext` has the activation pre-recorded, so both calls are past rungs 0 and 1
  ([4.2](../04-the-authoring-loop/4.2-which-rung-did-it-climb.md)). The failure being demonstrated is
  strictly a rung-2 failure, and pre-recording the activation is what removes the model from the
  experiment.
- `named` reads the skill's **own declared requirements** rather than a hard-coded pair, so this probe
  keeps working when the skill changes.
- `sorted(named - tools)` is the gap: what the procedure needs and the agent does not have. In the
  good case it is empty; in the broken case it is the list of steps that cannot be performed.
- **Zero model calls.** The failure is visible entirely from the tool list, which is the argument for
  the preflight in [4.3](../04-the-authoring-loop/4.3-sharpening-without-a-model.md).

- The `unmet_tools` check compares the skill's declared requirements against `sutra.loop.TOOLS`

  the typo. It does **not** catch the third case, where the tools exist and the toolset was built
  without them, because that is a fact about the agent rather than about the shelf.

Which is worth stating plainly rather than glossing: **the preflight catches two of the three routes to
this failure.** The third needs a different check — an assertion on the built agent — and that is the
one the hub leaves as a `TODO(me)`.

## When it breaks

**The failure that presents as a bad description.** Rung 2 in the verdict says *"activated but never
called `lookup_ticket`"*, and the instinct is to look at the step. If the tool is not in the menu, the
step is fine and the wiring is broken. Check the tool list before rewriting the body — one line,
`await toolset.get_tools(ctx)`, and it settles the question.

**The substitute that looks like success.** A model that calls `search_kb("4521")` has made a call, so
a check that only asks *"was a tool called?"* is satisfied. The verdict function avoids this by checking
the **required set**, not the count — which is the reason it takes `required_tools` as an argument
rather than counting calls.

**The half-broken pairing.** Misspell one of two names and the procedure gets one tool. The model then
performs step 1, fails at step 3, and produces an answer built on a real ticket and an imagined cause.
Partial failures produce more convincing wrong answers than total ones.

**The test that passes because it stubs the tools.** A test that builds the agent with its own fake
tools tests the procedure and not the wiring. Assert on the **real** `build_desk()`, or the one thing
you most want to know is the one thing you have arranged not to check.

## In production

**Assert the pairing on the built agent, in a test.** For every skill on the shelf, every name in its
`adk_additional_tools` must appear in the tool set the agent actually resolves after that skill is
activated. That is fifteen lines using the `FakeContext` above, it needs no model, and it closes the
third route the preflight cannot see.

**Prefer an honest refusal to a hopeful one, in writing.** The instruction's honesty rule is doing real
work here, and it is worth being explicit that it is load-bearing rather than decorative: *"if a lookup
fails, say it failed"* is what makes the good outcome likely when the wiring is wrong. Deleting it as
"obvious" removes the only thing standing between a broken pairing and an invented ticket.

**Log the gap rather than only the tools.** A startup line naming every skill's unmet requirements —
even when the answer is *none* — is the difference between noticing this on deploy day and noticing it
in a support escalation. It is the same field the preflight already computes.

**What changes at scale** is that the gap becomes normal. Forty skills, sourced from three places, and
several of them will name tools you do not have — a vendor pack's triage skill wants
`get_customer_plan`, which you have never built. At that point *"unmet requirement"* is not an error,
it is a **fact about a skill you should probably not have installed**, and the decision moves from
configuration to trust. That is Day 29's subject, and it starts with the number this check produces.

**The review comment a senior engineer leaves:** *"this refactor drops `additional_tools` from the
toolset. Every test still passes because none of them builds the real agent and checks that
`ticket-triage`'s declared tools resolve. Add that assertion in this pull request, then make the
change."*

**The interview question:** *"what happens if a skill's instructions name a tool the agent does not
have?"* The answer that shows you have watched it: *"nothing fails. The skill loads, the model
activates it, reads step 1, and finds no such tool — and then it either refuses honestly, improvises an
ungrounded answer, or substitutes a different tool. Which of the three you get is not under your
control, so the system has to be built so it cannot happen: declare the required tools in the skill's
metadata, lint them against the registry, and assert on the built agent that they resolve after
activation. The diagnostic is rung 2 — activated but the required tools were never called — and the
first thing to check is the tool list, not the wording of the step."*
