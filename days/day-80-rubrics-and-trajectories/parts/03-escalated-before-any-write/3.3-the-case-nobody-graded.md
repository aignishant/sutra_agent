# 3.3 — The case nobody graded

## One-line answer

💥 When the rater answers in prose instead of the expected format, the parser correctly refuses to
guess and the case comes back `overall_score: None`, `EvalStatus.NOT_EVALUATED` — which is not a
pass, is not a failure, and will be counted as neither by anything that tallies results.

## The story

A courier delivers a box against a packing slip that lists five items.

The box has four in it. Nobody counts, because counting is not what happens at a delivery — you sign
where the man points and he leaves, and the slip goes into a drawer.

Three weeks later somebody needs the fifth item and it is not there. Now the interesting question is
not where it went. It is what the paperwork says, and the paperwork says: delivered, signed for. There
is no line anywhere reading *"four of five received"*, because nothing in the process was capable of
producing that line. The system had two states — delivered and not delivered — and the thing that
actually happened was a third one it had no way to write down.

The loss did not happen at the warehouse. It happened at the moment a partial delivery had to be
recorded in a form with two boxes.

## The idea in plain language

Part [2.3](../02-the-evaluator/2.3-four-verdicts-one-number.md) walked the four steps from a rater's
prose to a `PASSED`, and noted that step one refuses to produce a partial parse. That refusal is
right. This part is about the state it leaves behind.

`DefaultAutoRaterResponseParser` returns `[]` when the counts of properties, rationales and verdicts
do not match. `AutoRaterScore` then has `score=None`. `get_eval_status(None, threshold)` gives
`EvalStatus.NOT_EVALUATED`. If every sample comes back that way, the whole case does.

So there are **three** outcomes for a case, not two:

| `overall_eval_status` | `overall_score` | What happened |
| --- | --- | --- |
| `PASSED` | a number ≥ threshold | graded, and it cleared the line |
| `FAILED` | a number < threshold | graded, and it did not |
| `NOT_EVALUATED` | `None` | **nobody graded it** |

This is the same three-valued shape Day 78 spent a whole part on — *fits*, *over*, and **cannot
say** — and the same argument applies with the same force: the third value needs a different person
and a different action. A `FAILED` case is a job for whoever owns the desk. A `NOT_EVALUATED` case is
a job for whoever owns the eval harness, and no amount of fixing the desk will change it.

The specific danger is arithmetic. A suite that computes a pass rate as `passed / total` counts an
ungraded case as a failure, which is at least loud. A suite that computes it as
`passed / (passed + failed)` — which is the version people write, because it feels more careful —
**drops the ungraded case entirely** and reports a pass rate over a smaller population without saying
so. It is [Day 78 part 3.2](../../../day-78-inside-free-quota/parts/03-when-you-cannot-afford-it/3.2-the-shrunken-run-that-reports-as-full.md)'s
missing denominator, arriving from a completely different direction.

And there is a second reason `NOT_EVALUATED` is easy to misread, which part
[1.3](../01-a-rubric-is-a-decomposition/1.3-the-whole-conversation-is-the-unit.md) already found: this
metric marks every turn but the last `NOT_EVALUATED` **by design**, on a perfectly graded case. So the
same enum value means "the verdict is not attached here" in one place and "nobody could grade this" in
another, and telling them apart means looking at the *overall* status rather than the per-invocation
ones.

## Why Sutra needs it

Because Day 82 puts this suite in CI and on Day 73's nightly, and a nightly job that reports
`3 of 3 conversations passed` when one of them was never graded is
[Day 73 part 3.2](../../../day-73-ambient-agents/parts/03-the-morning-after/3.2-the-digest-that-reassures.md)'s
digest that reassures — every number true, and the reader misled.

It also matters more here than it did for the deterministic metrics. ROUGE and trajectory comparison
cannot fail to produce a number; they are arithmetic. A judged metric has a whole extra way to
return nothing, and it is a way that gets **more** likely as conversations get longer and the rater
gets less compliant.

## The mechanism

The fault is injected by swapping the judge for one that answers in sentences. From `lab/parse.py`:

```python
class Prose(_judge.ScriptedJudge):
    """A judge that answers in sentences instead of in the format it was asked for."""

    async def generate_content_async(self, llm_request, stream=False):
        yield LlmResponse(
            content=genai_types.Content(
                parts=[genai_types.Part(text="The agent did fine overall.")], role="model"
            )
        )
```

**Line by line:**

- It subclasses `ScriptedJudge` so it inherits the registration and the `supported_models()` pattern,
  and overrides the one method that matters.
- The response is a single plausible sentence with no `Property:`, no `Rationale:` and no `Verdict:`.
  That is not a strawman — it is what a rater does when the conversation is long, the instruction
  block is 8,900 characters, and the format request is at the top.
- It yields exactly one response, as the real judge does for a non-streaming call.

And the injection, which is the one line in this lab that reaches into an object's internals:

```python
    evaluator._judge_model = Prose(model=_judge.JUDGE_MODEL)  # noqa: SLF001 - the fault injection
```

**Line by line:**

- `_judge_model` is set in `LlmAsJudge.__init__` by `_setup_auto_rater()`, so replacing it afterwards
  is the smallest way to change the rater for one run without touching the registry — which is
  process-global, as part [2.1](../02-the-evaluator/2.1-the-real-evaluator.md) warned.
- The `# noqa: SLF001` carries its reason, which is what plan §2's house style asks for: a suppressed
  lint rule with no explanation is a decision nobody can review. Reaching into a private attribute is
  acceptable **in a fault-injection harness** and would not be acceptable in `sutra/`.
- Everything downstream is untouched: the same evaluator instance, the same criterion, the same
  `num_samples=3`, the same parser.

Run it:

```bash
cd days/day-80-rubrics-and-trajectories/lab
uv run python parse.py --prose; echo "exit: $?"
```

**Line by line:**

- `--prose` grades `refunded_first` — the conversation a person scores 0.25 — with the off-format
  judge, end to end through the real evaluator.

Measured on 2026-09-06 (the three warning lines come first and are quoted below):

```text
conversation: refunded_first (a person grades it 0.25)
  overall_score:       None
  overall_eval_status: EvalStatus.NOT_EVALUATED
  rubric scores:       []

  the case has no score, and NOT_EVALUATED is not FAILED
  a suite that counts failures counts none here
exit: 1
```

**`None`, and an empty rubric-score list.** Not 0.0, which would be a failing case. Not 1.0, which
would be a lie. The library declines, and it says so first — this is on stderr, once per sample:

```text
Auto-rater response did not match the expected Property/Rationale/Verdict format; no rubric verdicts
were parsed. Raw auto-rater response: The agent did fine overall.
```

That message is genuinely good. It names the problem, it names the expected format, and it includes
the raw response so you can see what the rater actually did. It is also a **log line**, at warning
level, in a nightly job — which is to say, in the place
[Day 73 part 3.3](../../../day-73-ambient-agents/parts/03-the-morning-after/3.3-nobody-notices-silence.md)
established that nothing is read.

The arithmetic this produces, for a three-conversation suite where one case goes this way:

```text
  passed / total            = 2/3 = 67%   (counts the ungraded one as a failure - loud, and wrong)
  passed / (passed+failed)  = 2/2 = 100%  (drops it - quiet, and worse)
  graded / total            = 2/3 = 67%   (the number that should be on the dashboard)
```

## When it breaks

The way this reaches production is not a judge that returns prose every time. It is one that returns
prose **occasionally**, and the occasions are correlated.

A rater that emits perfect blocks on a two-turn conversation starts adding preamble on a
twelve-turn one, or drops the `ID:` line when there are nine rubric properties instead of four, or
wraps its answer in a code fence. Each is a small format drift and each produces a total parse
failure, because the parser's length check is all-or-nothing. So the `NOT_EVALUATED` rate rises with
conversation length and rubric size — and long, complicated conversations are exactly the ones a
trajectory rubric exists for.

You will not see it in the score, because the score is computed over the cases that were graded. You
will see it in a count nobody is keeping.

The smallest fix is one number in the report:

```python
graded = sum(1 for r in results if r.overall_eval_status is not EvalStatus.NOT_EVALUATED)
print(f"graded {graded} of {len(results)} conversations")
```

**Line by line:**

- `is not EvalStatus.NOT_EVALUATED` rather than `== PASSED or == FAILED`, so a fourth status added in
  a future version counts as graded rather than silently disappearing.
- It prints a fraction with the denominator in it — the rule from
  [Day 78 part 3.2](../../../day-78-inside-free-quota/parts/03-when-you-cannot-afford-it/3.2-the-shrunken-run-that-reports-as-full.md):
  a rate is only meaningful next to the population it was taken from.
- Printed unconditionally, not only when it is below the total. A line that appears only when
  something is wrong is a line nobody learns to look for.

## In production

**What a professional writes instead of a pass rate.** Three numbers: passed, failed, and
**ungraded**, always all three, always with the total. The third one is a health metric for the eval
harness rather than for the system under test, and it belongs next to the score precisely so that a
falling denominator is visible beside a rising percentage.

**What degrades at scale.** Format compliance is a property of the judge model, and the judge model
gets swapped — for cost, for availability, for a new version. A model change that improves answers
and loosens formatting will raise the ungraded rate and *improve* the reported pass rate at the same
time, because the cases it fails to format are disproportionately the hard ones. Nothing in a
score-only report can distinguish that from a genuine improvement.

**The failure that only shows with real traffic.** Retries hide it. A harness that re-asks the judge
when the parse fails will usually get a well-formed answer on the second attempt, so the ungraded
rate stays near zero and the cost quietly doubles for a subset of cases — and that subset is
invisible unless somebody counts retries. Both numbers, ungraded and retried, are the same signal
seen from two sides.

**The review comment a senior engineer leaves:** *"NOT_EVALUATED must not be aggregated with PASSED
or dropped from the denominator. Put ungraded on the dashboard as its own number. And that warning is
logged per sample — with `num_samples=5` one bad case logs five identical lines, which is how it gets
filtered out. Log a rate at the end of the run instead."*

**The interview question:** *"Your LLM-as-judge pipeline reports a 94% pass rate. What do you check
before believing it?"* The answer that shows experience asks how many cases were **graded**, not how
many passed — because a judged metric can fail to produce a verdict, and the pass rate is computed
over whatever survived. A candidate who goes straight to the threshold has not yet had a judge wander
off format on them.
