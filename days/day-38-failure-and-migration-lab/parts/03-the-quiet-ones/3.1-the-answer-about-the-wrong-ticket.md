# 3.1 — 💥 The answer about the wrong ticket

## One-line answer

A reply can pass every envelope check — valid JSON, valid JSON-RPC, your id, exactly one `result`,
the right payload shape — and still be an answer to a different question, and there is no check in
the protocol that catches it because from the protocol's point of view nothing is wrong.

## The story

You leave a washing machine at the repair shop and they write a job card.

The card has your name, your phone number, the fault — *drains but does not spin* — and the model
number copied off the sticker. The boy who wrote it copied one digit wrong. Not a wild guess: the
number he wrote is a real model, from the same manufacturer, from the year before.

Everything after that is done correctly. The technician looks up the parts diagram for the number on
the card. He orders the belt for that number. He fits it. It goes on, because the two models are
nearly the same machine and the belt is nearly the same belt. He runs the test cycle, it spins, he
signs off, and the card goes in the file.

Three weeks later it stops spinning again, because the belt is a size out and has been slipping since
the day it went on. And when you ring, the shop is genuinely puzzled, because the paperwork is
perfect. Every step in the process was performed correctly on the information available. The
information was wrong at the very first step and nothing downstream was ever going to catch it,
because nothing downstream ever looks back at the machine.

## The idea in plain language

Section 2 built a boundary that answers the question *"is this a well-formed reply?"*. This part is
about the question that comes immediately after and that nothing in section 2 asks: **is this a reply
about the thing I asked about?**

Those are genuinely different questions, and only one of them is the protocol's business. JSON-RPC
gives you the request id, which links a reply to a *request*. It does not link a reply to the
*subject* of the request. If you ask about ticket T-4521 and the server answers, correctly formatted,
about T-4520, every layer between you and it is satisfied.

The name for the check that catches it is an **echo check**: the request's own key must appear in the
answer. You asked about T-4521, so the answer has to say T-4521 somewhere you can read it, and if it
does not, you do not have an answer — you have a well-formed object.

This is the second half of [2.1](2.1-five-questions-before-you-believe.md)'s paper. The end-to-end
argument says a correctness check belongs where the meaning lives, and the meaning of "this answer is
about my ticket" lives in your application and nowhere else. No transport, no schema and no SDK can
perform it on your behalf, because none of them knows what your request was *for*.

There is a reason this failure deserves its own part rather than a sixth bullet in a checklist.
Everything in section 2 fails **loudly** — an exception, a quarantine, a named crime. This one
succeeds. It produces a plausible, fluent, confident answer, and the user reads it and acts on it. A
system that crashes tells you it is broken. A system that answers the wrong question tells you
nothing at all, and it keeps telling you nothing for as long as it runs.

## Why Sutra needs it

Sutra is a support desk. Its whole output is sentences about tickets, delivered to a human who will
act on them, and its two tools — `lookup_ticket` and `search_kb` from `sutra/loop.py`, re-exposed
over the wire by Day 34 — both answer questions *about* a specific thing.

Put a model in front of that. The model receives a tool result saying `ticket: T-4520, status:
closed`, and it was asked about T-4521. It will not notice. It will write *"Ticket T-4521 is closed.
Nothing further is needed."* — because writing fluent sentences from the material in front of it is
exactly what it does, and it has no independent knowledge of which ticket it asked about. The model
is not the safety net here. It is the amplifier.

And every mechanism in this day makes this failure more likely, not less. A duplicated reply shifts
the stream by one ([2.4](../02-the-x-ray/2.4-the-reply-that-arrived-twice.md)). A reused request id
lets a stale answer match ([1.4](../01-the-clock/1.4-a-broken-stream-loses-the-request.md)). A retry
after a timeout can race the original. Each of those produces exactly this: a valid answer to the
wrong question.

## The mechanism

> 🎬 **The scene:** your boundary is in place. Five checks, all passing, every reply validated before
> anything touches it. You are, correctly, more confident than you were yesterday.
>
> 😬 **The naive fix:** none is needed — the validator says the reply is good. Ship it.
>
> 💥 **Why it fails:** the validator was asked whether the message is well-formed and it answered
> that question honestly. Nobody asked whether the message is *relevant*, and no field in JSON-RPC
> encodes relevance. The result is an answer about T-4520 handed to a user who asked about T-4521,
> with the number silently swapped in the sentence they read.
>
> 💡 **The insight:** validation proves the shape. Only the caller can prove the subject, because
> only the caller knows what it asked. Echo the key.

The reply below is deliberately not a crime. It would pass all five checks in
[`xray.py`](../02-the-x-ray/2.1-five-questions-before-you-believe.md):

```python
# days/day-38-failure-and-migration-lab/lab/plausible.py
ASKED = "T-4521"
REPLY = json.dumps(
    {
        "jsonrpc": "2.0",
        "id": 1,
        "result": {
            "resultType": "complete",
            "content": [{"type": "text", "text": "status: closed"}],
            "structuredContent": {"ticket": "T-4520", "status": "closed", "owner": "desk"},
        },
    }
)


def check_echo(result: dict, asked: str) -> None:
    """The request's own key must come back in the answer."""
    got = result.get("structuredContent", {}).get("ticket")
    if got != asked:
        raise Malformed(f"answer is about {got!r}, we asked about {asked!r}")
```

**Line by line:**

- `ASKED` is a module constant so that the question and the answer are visible on one screen. In a
  real client it is whatever argument you put in `params`, and the echo check's whole job is to
  compare those two values that normally live far apart.
- `id: 1` matches the id the script sends, so check 3 passes. This is important: the message is *not*
  a stale reply from another request. It is the reply to this request, and it is about the wrong
  ticket. A stale reply is [1.4](../01-the-clock/1.4-a-broken-stream-loses-the-request.md)'s problem;
  this is a server-side error, and the same check catches both.
- `content` and `structuredContent` are the two halves of a modern tool result. `content` is the
  human-readable part a model reads; `structuredContent` is the machine-readable part, and it is the
  one you can check against. Notice that `content` says only `status: closed` and never names a
  ticket at all — so the check *cannot* be done against the text a model sees, only against the
  structured half.
- `check_echo` imports `Malformed` from `xray.py` rather than defining its own exception. The
  disposition is identical — quarantine — so it belongs in the same class as the five envelope
  crimes, and merging them means one `except` clause covers "not a valid reply" and "not my reply".
- `result.get(..., {}).get(...)` chains defensively because `structuredContent` is optional in the
  specification. A tool may return only `content`, in which case the echo check has nothing to check
  against — which is a finding about that tool's design and is discussed in *In production* below.
- The message names **both** values: what came back and what was asked. A message saying only
  "unexpected ticket" would send the reader to a debugger to find out which two things disagreed.

Run both arms:

```bash

ECHO_CHECK=1 uv run python plausible.py
```

**Line by line:**

- `ECHO_CHECK=0` runs the five envelope checks and stops there, which is where
  [2.1](../02-the-x-ray/2.1-five-questions-before-you-believe.md) left you.
- `ECHO_CHECK=1` adds the sixth. **Zero model calls** — the "answer shown to the user" is an
  f-string, and that is the point: a model would have written the same sentence, just as confidently
  and rather more smoothly.

Measured on 2026-09-04:

```text
envelope checks: all five passed
echo check     : not run
answer shown to the user: "Ticket T-4521 is closed. Nothing further is needed."
that sentence is about T-4520
```

```text
envelope checks: all five passed
echo check     : QUARANTINE -> answer is about 'T-4520', we asked about 'T-4521'
answer shown to the user: (none - the desk escalated to a human)
```

`envelope checks: all five passed` appears in **both** runs. That line is the finding. Everything
section 2 built is working perfectly, and in the first run the user is told that a ticket which may
well be open is closed and that nothing further is needed.

Read the last line of the first transcript once more. The sentence the user reads says `T-4521`. The
data it was built from says `T-4520`. The number in the sentence came from the *question*, not from
the answer, which is how a templated response and a model both behave — you interpolate the thing you
asked about, because you asked about it.

## When it breaks

There is no error text to paste for the failure itself, and that is the whole of *When it breaks*.
The failure produces this and nothing else:

```text
answer shown to the user: "Ticket T-4521 is closed. Nothing further is needed."
```

Exit code zero. No log line above `INFO`. No metric moves. The first artefact this bug ever produces
is a human being annoyed, some days later, and by then the request that caused it has aged out of the
logs.

The check itself has two ways to go wrong, and both are worth knowing before you write it.

**Checking the wrong half.** Run the comparison against `content` — the text the model reads — and
you get either a false pass or a false quarantine depending on how the tool happens to phrase itself.
`"status: closed"` contains no ticket number at all, so a substring search finds nothing and
quarantines a perfectly good reply. Check `structuredContent`, which is typed.

**Checking a key that is not a key.** Echoing `status` proves nothing, because two tickets can share
a status. The field you echo has to be the one that **identifies** the subject of the request. If a
tool's result contains no such field, that is a real finding: the tool cannot be verified by its
caller, and the fix is on the server — return the identifier you were given.

And there is a failure of the check itself, which is a normalisation mismatch:

```text
Malformed: answer is about 't-4521', we asked about 'T-4521'
```

A server that lower-cases identifiers now quarantines every reply. The fix is to compare normalised
values and to decide the normalisation once, in one function, rather than at each call site.

## In production

**What a professional writes instead:** a per-tool assertion that lives beside the tool's schema, not
scattered through the calling code. Every tool whose result is *about* something declares which field
carries the subject, and the client's result handler checks it automatically. That turns "remember to
echo-check" from a discipline into a property of the toolset, and it means a new tool cannot be added
without somebody deciding what its identity field is.

It also changes what you ask of servers you do not own. "Does the tool return the identifier it was
given?" becomes an intake question, alongside the ones Day 32's
[6.2](../../../day-32-mcp-stateless-core/parts/06-in-production/6.2-before-you-depend-on-a-server.md)
already asks, and it goes into [Day 45](../../../day-45-the-mcp-audit/LESSON.md)'s audit sheet.

**What degrades at scale:** the rate. This failure needs a mis-correlation, and mis-correlations are
rare at low concurrency and routine at high concurrency — the shifted stream, the reused id, the
retry racing its original. A bug that occurs in one call per hundred thousand is invisible in testing
and produces several wrong answers a day in production, which is exactly the rate that generates
complaints without generating a reproduction.

**The failure mode that only appears with real traffic:** correlation errors that follow load rather
than input. Because the trigger is timing, the same request succeeds when replayed, so every
investigation ends with "cannot reproduce". Teams close these as user error more often than they
solve them, and the echo check is the cheapest way to convert them into a counter you can watch.

**The review comment a senior engineer leaves:** *"we validate the envelope and then trust the
payload. Nothing here checks that the ticket in the response is the ticket in the request. Add the
echo check to the result handler and give it a metric — if that counter is ever non-zero we have been
telling customers about other customers' tickets, and I would rather find out from a graph than from
support."*

**The interview question:** *"your client validates every response against the schema. What can still
go wrong?"* This is the answer that separates people who have run something from people who have read
about it: *"the response can be valid and about the wrong thing. Schema validation answers 'is this
well-formed', and the question nobody asks is 'is this about what I asked'. We hit the version of it
where a reply carried our request id and somebody else's ticket — every envelope check passed and the
user was told a ticket was closed that we had never actually looked up. The fix is an echo check: the
request's identifying key has to come back in the structured half of the result, and a mismatch is a
quarantine, not a warning. It is the one check the protocol cannot do for you, because relevance is
not a protocol property."*
