# 1.3 — Hanging up is the whole cancel message

## One-line answer

Over Streamable HTTP there is no cancel message: closing the response stream *is* the cancellation,
which means the server only learns about it the next time it tries to write, and may have done
several more pieces of work by then.

## The story

The gate at the compound has an intercom.

You press the button, someone inside says "coming", and there is a click. Then you realise you have
left your phone in the car, so you walk back to get it. You do not press the button again, because
what would you even say.

The guard walks out to the gate, opens it, and there is nobody there. He looks up and down the road,
waits, and goes back in. He was not told you had gone. There is no button for that. He found out by
arriving.

The gap between you leaving and him finding out is not a fault in the intercom. It is just how a
one-way button works. If you want him to know sooner, the only thing you can do is be somewhere he
looks sooner — and he only looks when he opens the gate.

## The idea in plain language

[1.2](1.2-giving-up-ends-the-wait.md) said the server is never told when you give up. That is exactly
true on stdio, where there is nothing to tell it with. Over HTTP it is *almost* true, and the
difference is worth a part of its own.

An HTTP request has a **response stream** — the connection the server writes its answer down. When
the client closes that connection, the operating system on the server's side eventually notices. It
does not deliver a message, because there is no message. What happens is that the **next write the
server attempts fails**, with an error meaning "there is nobody at the other end of this socket".

So cancellation over HTTP is:

- **discovered, not announced.** The server finds out by trying to speak.
- **late.** It finds out at its next write, which might be its next progress update, or might be the
  final result. Everything between the hang-up and that write happens.
- **cooperative.** The server chooses what to do about the error. A well-written one stops. A
  badly-written one catches the exception and carries on to the end.

Day 33's
[3.3](../../../day-33-client-and-transports/parts/03-streamable-http/3.3-standing-up-is-how-you-cancel.md)
established that this is the one place where the two transports genuinely differ. This part measures
the delay, because the delay is the part people get wrong: they read "closing the stream cancels the
request" and picture something immediate.

One term, because it appears in the output below. A **socket buffer** is a small amount of memory the
operating system keeps for bytes you have written but the other side has not read yet. A write into a
buffer with space in it succeeds *locally* without anything being confirmed by the far end, so a
server can write two or three more times after the client has gone before it hits the buffer's limit
and finally sees the truth.

## Why Sutra needs it

Sutra reaches partner servers over Streamable HTTP, which Day 33 wired as `connect_http` in
`sutra/mcp/client.py`. When [Day 44](../../../day-44-client-hardening/LESSON.md) writes
`with_timeout`, what that function will actually *do* at the deadline is close the response stream.
It is worth knowing, before writing it, that this is a hint rather than a stop.

It also settles a design question that comes up on [Day 43](../../../day-43-stateless-by-default/LESSON.md).
If cancellation is discovered late and cooperatively, then a server that does something expensive and
irreversible cannot rely on being cancelled — it has to be safe against being run to completion.
That is the same conclusion [1.2](1.2-giving-up-ends-the-wait.md) reached from the other side, and
two independent routes to the same rule is usually a sign the rule is real.

And it explains a piece of the 2026-07-28 revision that otherwise looks arbitrary. The old protocol
had a `notifications/cancelled` message. On stdio it survives, because a pipe is bidirectional and a
notification costs nothing. Over HTTP the revision leaned on the transport instead: the request's own
stream is the unit of cancellation, so there is nothing to correlate and nothing to route.

## The mechanism

> 🎬 **The scene:** a tool call is streaming progress updates. Your deadline fires at two seconds and
> your HTTP client closes the connection, exactly as it should.
>
> 😬 **The naive fix:** assume the server stopped. Log "cancelled", free the slot, move on.
>
> 💥 **Why it fails:** the server's next write goes into a socket buffer that still has room, and
> succeeds. So does the one after it. The server does not discover the hang-up until a write
> genuinely has to reach the client, which can be several units of work later — and if the server
> catches the resulting exception and continues, never.
>
> 💡 **The insight:** closing the stream is the only cancel signal there is, and it is delivered by
> failure rather than by message. Design as though the server will finish.

The experiment needs a real socket, because the whole effect lives in the operating system's
buffering. This is a plain `http.server` that streams four chunks, and a client written at the socket
level so it can hang up in the middle:

```python
# days/day-38-failure-and-migration-lab/lab/cancel.py
CHUNKS = 4
PAUSE = 0.4
log: list[str] = []


class Handler(BaseHTTPRequestHandler):
    """One POST, answered as an SSE stream scoped to that one request."""

    def do_POST(self) -> None:  # noqa: N802 - the name is BaseHTTPRequestHandler's
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.send_header("X-Accel-Buffering", "no")
        self.end_headers()
        for n in range(1, CHUNKS + 1):
            try:
                self.wfile.write(f"data: progress {n}/{CHUNKS}\n\n".encode())
                self.wfile.flush()
                log.append(f"server wrote chunk {n}")
            except (BrokenPipeError, ConnectionAbortedError, ConnectionResetError) as exc:
                log.append(f"server saw {type(exc).__name__} on chunk {n} -> CANCELLED, stopping")
                return
            time.sleep(PAUSE)
        log.append("server finished all chunks")
```

**Line by line:**

- `BaseHTTPRequestHandler` is the standard library's HTTP server. No framework is needed and none is
  wanted: the subject is the socket, and every layer above it hides the socket.
- `Content-Type: text/event-stream` is the header that makes this a **stream** rather than a single
  JSON body. It is the same choice a real MCP server makes when it has progress to report, which Day
  33's [3.2](../../../day-33-client-and-transports/parts/03-streamable-http/3.2-handed-over-or-told-to-wait.md)
  covered.
- `X-Accel-Buffering: no` asks any reverse proxy in the path not to hold the chunks back. There is no
  proxy here, but leaving it out of the teaching version would teach the wrong habit — with a proxy
  buffering, the server's writes all succeed into the proxy and it never notices the client at all.
- `self.wfile.write(...)` then `.flush()`. The flush is what pushes the bytes at the socket. Without
  it Python's own buffer would absorb every chunk and the experiment would measure Python, not TCP.
- The `except` clause names **three** exception types because the operating systems disagree.
  Windows raises `ConnectionAbortedError`, Linux and macOS usually raise `BrokenPipeError`, and a
  reset in flight gives `ConnectionResetError`. Catching only one of them is a portability bug that
  presents as "cancellation does not work on the build server".
- `return` inside the handler is the **cooperative** part. Nothing forces it. Replace it with `pass`
  and the server finishes all four chunks into a socket nobody is holding, which is a completely
  legal thing for a server to do.
- `log` is a module-level list rather than `print`, so that the client's lines and the server's lines
  end up in one transcript instead of interleaving on the terminal. It is appended to from two
  threads, so the first two lines can swap between runs; nothing after them does.
- `CHUNKS = 4` and `PAUSE = 0.4` are small on purpose. Small writes fit in the socket buffer, which
  is precisely the effect being measured — a server discovers a hang-up on a write that has to reach
  somebody, not on the first write after it happens.

The client's whole job is to read one chunk and then genuinely hang up:

```python
    sock = socket.create_connection(("127.0.0.1", port))
    sock.sendall(
        b"POST /mcp HTTP/1.1\r\nHost: 127.0.0.1\r\n"
        b"Accept: application/json, text/event-stream\r\n"
        b"Content-Length: 2\r\n\r\n{}"
    )
    stream = sock.makefile("rb")
    while (line := stream.readline()) not in (b"\r\n", b""):
        pass  # skip the status line and headers
    log.append(f"client read: {stream.readline().decode()[:24].strip()!r}")
    log.append("client CLOSED the stream - no notifications/cancelled was sent")
    stream.close()
    sock.shutdown(socket.SHUT_RDWR)  # a real hang-up, not just dropping the object
    sock.close()
```

**Line by line:**

- The request is typed out as raw bytes rather than built with a library because a library would
  reuse the connection from a pool, and a pooled connection is not closed when you think it is. The
  experiment needs one socket whose life you control exactly.
- `Accept: application/json, text/event-stream` is the header the 2026-07-28 transport requires on
  every POST — a client must be willing to receive either shape. It is here so the request is a legal
  MCP request and not merely an HTTP one.
- `sock.makefile("rb")` wraps the socket so `readline()` works. The `while` loop then walks past the
  status line and headers, stopping on the blank `\r\n` that separates headers from body.
- The walrus `:=` keeps the read and the test in one expression, which matters only because the loop
  body is empty and would otherwise need a duplicated read above it.
- `sock.shutdown(socket.SHUT_RDWR)` is the line that makes this a hang-up rather than a leak. Closing
  the Python object drops your reference; `shutdown` tells the kernel to send the FIN. Without it the
  server may not notice for a long time, and the experiment would print nothing interesting.
- **No cancellation message is constructed anywhere in this file.** That absence is the finding.

**Line by line:**

- The server binds to `127.0.0.1` on port `0`, which asks the operating system for any free port, so
  the script never collides with anything you have running. **Zero model calls, no network beyond
  loopback.**

Measured on 2026-09-04:

```text
server wrote chunk 1
client read: 'data: progress 1/4'
client CLOSED the stream - no notifications/cancelled was sent
server wrote chunk 2
server saw ConnectionAbortedError on chunk 3 -> CANCELLED, stopping
```

The first two lines are appended from different threads and may swap places on your machine. Nothing
below them does, and the line that matters is the fourth.

**The server wrote chunk 2 successfully after the client had gone.** That
write went into a buffer, returned without error, and the server had every reason to believe it had
been received. Only on chunk 3 did the truth arrive, as an exception, on a machine running Windows —
on Linux the same line would read `BrokenPipeError`, which is why the handler catches all three.

So the delay between cancelling and being cancelled is not zero, it is not fixed, and it is measured
in units of work rather than in units of time.

## When it breaks

The exception you meet is one of these, and which one you get depends on the operating system rather
than on anything you did:

```text
ConnectionAbortedError: [WinError 10053] An established connection was aborted by the software in your host machine
```

```text
BrokenPipeError: [Errno 32] Broken pipe
```

Both mean the same thing: you wrote to a socket the other side has closed. The trap is that they are
different classes with no useful common parent — `ConnectionError` covers `BrokenPipeError`,
`ConnectionAbortedError` and `ConnectionResetError`, but not `TimeoutError`, and code that catches
`OSError` to be safe also swallows a great deal it should not.

There is a worse variant, which is when this exception is caught by a framework and logged at
`ERROR`. A cancelled request is a normal, expected event — every user who closes a tab produces one —
and a server that pages somebody for it will be paged constantly and will learn to ignore the page.
Cancellation is `INFO`.

The smallest fix on the server side is to treat that exception as *the message it is*: stop the work,
release the resources, and do not attempt to write an error body down a socket that has already gone.

## In production

**What a professional writes instead:** a server whose long-running work checks for cancellation at
its own boundaries rather than only at write time, and a client that does not treat closing the
stream as proof of anything. In practice that means the pairing Day 36 built: work that genuinely
takes a while returns a task handle, so cancelling is an explicit `tasks/cancel` against a handle
rather than a socket closing and a hope.

**What degrades at scale:** buffering in the middle. Put a reverse proxy, a load balancer and a
service mesh between client and server and each of them holds bytes. The server's writes now succeed
into the nearest hop, and the hang-up may not reach it at all until the proxy's own idle timeout
fires. At one hop the delay is a chunk or two; at four hops it can be the whole request. Every
system that says "we cancel by closing the connection" is quietly assuming a short path.

**The failure mode that only appears with real traffic:** work amplification during a client-side
incident. Something upstream starts timing out and closing streams. Every one of those requests is
still executing on the server, and the server's CPU and database load do not drop at all while its
apparent success rate stays high. Operators looking at the server see a healthy service; operators
looking at the client see a total outage. Both dashboards are correct.

**The review comment a senior engineer leaves:** *"this catches `BrokenPipeError` only. Our CI runs
on Windows and it will raise `ConnectionAbortedError` there, so cancellation will be an unhandled
exception on half our machines. Catch `ConnectionError`, and log it at INFO — a closed tab is not an
error."*

**The interview question:** *"how does a client cancel an in-flight MCP call over HTTP?"* A precise
answer earns the follow-up: *"it closes the request's response stream. There is no cancel message in
the 2026 revision over HTTP — `notifications/cancelled` only lives on stdio. What I would add is that
it is not immediate. We measured it: the server wrote one more chunk successfully into the socket
buffer after the client had hung up, and only discovered the close on the chunk after that. And it is
cooperative — the server can catch that exception and finish anyway. So for anything expensive we use
a task handle and an explicit cancel, and for anything irreversible we make it safe to have run."*
