# 1.4 — A broken stream loses the request

## One-line answer

The 2026-07-28 revision deleted stream resumption, so a response stream that breaks loses the request
entirely and the client must re-issue it — with a **new** request id, because reusing the old one
lets a late reply to the first attempt be accepted as the answer to the second.

## The story

You order food and the app stops halfway through placing it.

The wheel spins, then the screen goes back to the basket with everything still in it. No order, no
number, no message. So you place it again, and this time it works, and a number appears at the top:
order 8842.

What the app does not offer you — and this is the part worth noticing — is a way to *continue* the
first attempt. There is no button for that. There is only starting again, and the new attempt gets
its own number, which is how the kitchen tells your order from everybody else's.

Now imagine it had reused the number. The first attempt, the one you thought had failed, reaches the
kitchen a minute later carrying 8842 as well. Two different orders, one number, and a rider is going
to be handed whichever one is ready first.

The new number is not bureaucracy. It is the only thing keeping the two attempts apart.

## The idea in plain language

**Resumption** is the ability to pick a broken transfer back up where it stopped, instead of starting
again. It needs the sender to remember what it already sent and the receiver to say how far it got.

Earlier revisions of MCP had it. A response stream carried event ids, and a client whose connection
dropped could reconnect with a `Last-Event-ID` header meaning *"I got up to here, carry on"*. The
2026-07-28 revision **removed** it, along with the SSE event ids that made it possible.

So the current rule is short, and the specification's changelog states it plainly:

> Remove SSE stream resumability and message redelivery (the `Last-Event-ID` header and SSE event
> IDs) from the Streamable HTTP transport. A broken response stream loses the in-flight request;
> clients **MUST** re-issue it as a new request with a new request ID.

Two words in there carry the weight. *Loses* — not "pauses", not "delays". And *new request ID*.

The **request id** is the number in the JSON-RPC message that lets a client match an answer to a
question. It is the only correlator the protocol gives you: there is no other field that says which
request a result belongs to. Which means an id is not a label, it is an identity, and reusing one is
the same as two people having the same name in a system that files by name.

Why remove something useful? Because resumption is state. To resume, the server must remember what it
sent you, which means it must know who you are, which means the request that reconnects has to land
on the same instance — and that is precisely the pinning the revision deleted when it removed
sessions, taught on
[Day 32's 2.2](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md).
Resumption was the last thing in the transport that required a server to remember a client, so it
went with the rest.

## Why Sutra needs it

Sutra's client will retry. Every real client does, and
[Day 44](../../../day-44-client-hardening/LESSON.md) writes `with_retries` into
`sutra/mcp/hardening.py`. The question this part settles is what a retry *is* in this protocol, and
the answer is stronger than it looks: a retry is not a continuation, it is a completely new request
that happens to ask the same question.

That has a consequence Day 44 has to build for. If a retry is a new request, then the server has
never heard of the first one and will do the work again — which is
[1.2](1.2-giving-up-ends-the-wait.md)'s problem arriving from a different direction, and why
[3.2](../03-the-quiet-ones/3.2-the-ticket-closed-twice.md) exists.

And it has a consequence for correctness that is easy to miss and produces a wrong answer rather than
an error. If Sutra keeps a dictionary of in-flight requests keyed by id — which is how every client
is written — and it reuses an id on the retry, then a straggling reply to the first attempt is
indistinguishable from the reply to the second. The client will believe it, because by its own rules
it is the right answer.

## The mechanism

> 🎬 **The scene:** a `tools/call` to a partner server dies mid-answer. The connection reset; you got
> half a JSON object. You retry, sensibly, and you keep the same request id because it is the same
> question.
>
> 😬 **The naive fix:** exactly that. Reusing the id feels *more* correct than inventing a new one —
> it is one logical operation, so surely it is one id.
>
> 💥 **Why it fails:** the first attempt was not cancelled ([1.3](1.3-hanging-up-is-the-message.md)),
> so its answer may still arrive. Your correlation table matches on id and only on id. The stale
> answer arrives first, matches, and is handed to the caller as the result of the retry. No exception
> is raised, because nothing is wrong from the client's point of view.
>
> 💡 **The insight:** the request id is an identity, not a label. A new attempt is a new request, so
> it gets a new identity — and then the stale reply matches nothing and is discarded.

The script replays one in-flight window by hand, so that the ordering on the wire is explicit rather
than accidental:

```python
# days/day-38-failure-and-migration-lab/lab/reissue.py
REUSE_ID = os.environ.get("REUSE_ID", "0") == "1"

FIRST_ATTEMPT = {"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {"name": "search_kb"}}
STALE_REPLY = {"jsonrpc": "2.0", "id": 1, "result": {"resultType": "complete", "hits": ["OLD"]}}


def correlate(inflight: dict, frames: list[dict]) -> dict | None:
    """Return the frame answering `inflight`, matched on the JSON-RPC id alone."""
    for frame in frames:
        if frame.get("id") == inflight["id"]:
            return frame
    return None
```

**Line by line:**

- `REUSE_ID` is the ablation. One environment variable turns the rule off, so the two behaviours can
  be compared rather than asserted.
- `FIRST_ATTEMPT` and `STALE_REPLY` share `id: 1` because that is the situation: the first attempt
  went out with id 1, and somewhere out on the network there is a reply carrying id 1.
- `resultType: "complete"` is on the reply because every result in this revision carries that field.
  A result from an older server that omits it must be treated as `"complete"` — which is worth
  knowing here, since the whole part is about not mistaking one message for another.
- `correlate` matches **only** on the id, and that is not a simplification for teaching. It is what
  the protocol offers. There is no timestamp, no attempt counter, no nonce. If two messages carry the
  same id, no client can tell them apart, however carefully it is written.
- It returns `None` rather than raising when nothing matches, because "no answer yet" is a normal
  state in a client that has several requests outstanding.

The rest of the script is the sequence:

```python
    new_id = 1 if REUSE_ID else 2
    second = {**FIRST_ATTEMPT, "id": new_id, "params": {"name": "search_kb", "q": "printer jam"}}

    fresh = {"jsonrpc": "2.0", "id": new_id, "result": {"resultType": "complete", "hits": ["NEW"]}}
    frames = [STALE_REPLY, fresh]

    matched = correlate(second, frames)
    hits = matched["result"]["hits"] if matched else None
```

**Line by line:**

- `new_id = 1 if REUSE_ID else 2` is the entire difference between the two arms. Everything else in
  the file is identical.
- `{**FIRST_ATTEMPT, "id": new_id, ...}` builds the retry from the original, which is how a real
  client builds one: same method, same tool, possibly refined arguments.
- `frames = [STALE_REPLY, fresh]` puts the **stale** reply first. That is the ordering that makes the
  bug visible, and it is the realistic one: the first attempt was sent earlier, so its answer has had
  longer to travel. A retry that arrives second and is answered second still races a straggler that
  was sent first.
- `hits` reads `["OLD"]` or `["NEW"]`. Two string constants stand in for a search result because the
  content is irrelevant — what matters is *which attempt produced it*, and a label is the clearest
  way to see that.
- **No model is called.** The answer is a list of strings written in the file.

Run both arms:

```bash
cd days/day-38-failure-and-migration-lab/lab
REUSE_ID=0 uv run python reissue.py
REUSE_ID=1 uv run python reissue.py
```

**Line by line:**

- `REUSE_ID=0` follows the specification: the retry gets id 2.
- `REUSE_ID=1` reuses id 1, which is the thing that feels natural.
- **Zero model calls.**

```text

           stream broke mid-answer - nothing usable, no Last-Event-ID to resume with
attempt 2: id=2 tools/call search_kb  (REUSE_ID=0)

```


The second run answers a question about a printer jam with a result computed before the words
"printer jam" were ever sent. Nothing raised, nothing logged, and the answer is well-formed.

## When it breaks

The break you get if you try to resume anyway is at least loud. A client written against an older
revision reconnects with the header it used to use, and a current server has no idea what it means:

```text
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32020, "message": "Header mismatch", "data": {"header": "Last-Event-ID"}}}
```

`-32020` is `HeaderMismatch`, renumbered from `-32001` in this revision, and Day 32's
[3.2](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.2-the-header-that-must-match.md)
owns it. A server is free to ignore an unknown header instead, in which case you get a **fresh** full
response and simply pay for the whole request again — annoying, correct, and silent.

The break from the reused id is the one with no error text at all, and that is the finding: the
transcript above is the entire evidence, because the wire is well-formed and the client is behaving
exactly as designed. The only way to catch it is a check the protocol cannot do for you, which is
[3.1](../03-the-quiet-ones/3.1-the-answer-about-the-wrong-ticket.md)'s subject.

The smallest fix is one line: allocate the id from a counter that never rewinds, and never
reconstruct a request object by mutating the previous attempt in place. A retry helper that takes the
old request dictionary and edits it is exactly how ids get reused by accident.

## In production

**What a professional writes instead:** a monotonic id source owned by the client — an
`itertools.count()` or a UUID per attempt, never a value derived from the operation. Alongside it, a
correlation table with an entry per **attempt**, not per operation, so that a stale reply finds no
entry and is dropped with a counter incremented rather than silently accepted.

**What degrades at scale:** id collisions across concurrency. A per-operation id is unique enough in
a script and not unique at all in a worker pool where two goroutines, threads or tasks are calling
the same tool for two different tickets. The bug appears as a tiny percentage of answers about the
wrong subject, which is the hardest kind of bug to get anyone to believe.

**The failure mode that only appears with real traffic:** retries during a partial network incident.
Latency rises, streams break, everyone retries, and the network is now carrying both the retries and
the delayed originals. This is the exact window in which stale replies are most numerous, and it is
also the window in which every log is full of noise, so a wrong-answer bug hides inside a latency
incident.

**The review comment a senior engineer leaves:** *"the retry reuses `req.id`. The spec says a
re-issued request MUST have a new id, and the reason is not pedantry: the first attempt's reply can
still land. Take the id from the client's counter and add a metric for replies that match no
in-flight attempt — if that counter is not zero we have been eating stale answers."*

**The interview question:** *"an MCP response stream breaks mid-answer. What does your client do?"*
The complete answer covers both halves: *"it re-issues, because there is no resumption in the 2026
revision — they removed `Last-Event-ID` and the SSE event ids, so a broken stream loses the request
outright. The part people miss is that it has to be a new request id. We demonstrated why: with the
id reused, a straggling reply to the first attempt matched the retry's correlation entry and got
handed back as the answer, and since JSON-RPC has no correlator other than the id there is no way for
the client to tell. With a fresh id the straggler matches nothing and gets dropped. And because the
first attempt was never cancelled, the server ran the work twice, which is why the operation also has
to be idempotent."*
