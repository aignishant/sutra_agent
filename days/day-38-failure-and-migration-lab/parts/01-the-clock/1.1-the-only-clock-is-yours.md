# 1.1 — The only clock in the room is yours

## One-line answer

Nothing in MCP promises that a server will ever answer, so a client that has no deadline of its own
has no way to stop waiting, and "the request is still running" and "the request will never finish"
look exactly the same from the outside.

## The story

The plumber said he would come today.

You stayed in. By the middle of the afternoon you had stopped doing anything useful, because
starting something would mean not hearing the door. You did not want to ring him and be a nuisance,
and anyway what would you ask — he said today, and it is still today.

At six you rang. No answer. At eight you accepted he was not coming, and the annoying part was not
the eight hours. It was that at any point in those eight hours you could have decided *"if he is not
here by four, I will book someone else and go out"*, and you would have lost four instead of eight.
You did not lose the day because he failed to come. You lost the day because you never said when you
would stop waiting.

Nobody was ever going to ring you to say he was not coming. That is not a service anyone offers.

## The idea in plain language

A **timeout** is a limit you put on your own waiting. It is not a promise the other side makes, and
it is not something the network gives you. It is a decision you take before you start: *if the answer
is not here by then, I stop waiting and do something else.*

Everything else in this part follows from one sentence: **there is nothing in the protocol that
obliges a server to reply.** A server can be slow, it can be stuck on a lock, it can have crashed
with the pipe still open, it can be waiting on a database that is waiting on another database. From
where the client sits, all of those look identical. There is no message that means *"I am never going
to answer you"*, because a process that could send that message is a process that could have sent the
answer.

Two terms, because they get used interchangeably and are not the same thing:

- A **hang** is when nothing comes back and nothing ends. The connection is fine. The process is
  alive. There is simply no reply, and there never will be.
- A **timeout** is what you do about a hang. It is your own clock firing.

A hang without a timeout is not an error. It is silence, and silence is what you get for free.

This is not particular to MCP. It is the shape of every request that crosses a process boundary —
and it is why every network library ships a `timeout` argument. What *is* particular to MCP is that
the 2026-07-28 revision took away the one thing that used to soften it: there is no stream resumption
any more, so a request that does not come back is not merely late — it is gone.
[1.4](1.4-a-broken-stream-loses-the-request.md) is that half of the story.

## Why Sutra needs it

Sutra's client is real code now. Day 33 wrote `sutra/mcp/client.py` with `connect_stdio`,
`connect_http` and `list_tools`, and every one of those functions is at some point sitting on a read
that may never return. Days 34 to 37 put a server, resources, prompts, long jobs and an auth flow
behind that client. None of them added a clock.

The day this bites is not a day when something is broken. It is a day when a partner's server is
merely slow — a database that is being re-indexed, a machine that is swapping — and Sutra's triage
loop stops answering tickets, with no exception in the log and no alert, because every worker is
sitting in a `readline()` that is going to return eventually. Eventually is not a service level.

On [Day 44](../../../day-44-client-hardening/LESSON.md) you write `sutra/mcp/hardening.py` and the
deadline becomes policy: `with_timeout`, `with_retries`, and the rule that no connection is held. That
day is only worth writing if you have already felt the hang. This is where you feel it (Principle 4:
build the mechanism by hand, then adopt the framework).

## The mechanism

> 🎬 **The scene:** a partner's MCP server answers `tools/list` in about fifty milliseconds, every
> time, for a month. Then one afternoon it starts taking six seconds. Nothing is down. Nothing logs
> an error. Sutra's ticket queue quietly stops moving.
>
> 😬 **The naive fix:** nothing, because nothing looks wrong. There is no exception to catch and no
> status code to check. The client is doing exactly what it was written to do, which is wait.
>
> 💥 **Why it fails:** a read with no deadline cannot distinguish "slow" from "never". Both are the
> absence of bytes. Waiting is the default behaviour of every socket and every pipe on the machine,
> and the default behaviour is to wait forever.
>
> 💡 **The insight:** the only clock in the conversation is the one the caller brings. If you did not
> bring one, there is not one.

Two files. First, a server that is slow on purpose — this is the stdio wire from
[Day 33's 2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md),
one JSON message per line, with nothing but the standard library behind it:

```python
# days/day-38-failure-and-migration-lab/lab/slow_server.py
SLEEP = 6.0


def main() -> None:
    """Read one line per request; behave according to the mood on the command line."""
    mood = sys.argv[1] if len(sys.argv) > 1 else "fast"
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        request = json.loads(line)
        if mood == "hang":
            time.sleep(3600)  # never answers; the caller's clock is the only clock
        if mood == "slow":
            time.sleep(SLEEP)
        print(f"[server] work finished for id={request.get('id')}", file=sys.stderr, flush=True)
        sys.stdout.write(json.dumps(answer(request)) + "\n")
        sys.stdout.flush()
```

**Line by line:**

- `mood` comes from the command line rather than an environment variable because you will want to run
  the same script three ways in one shell session, and `sys.argv[1]` is the shortest thing to change.
- `for line in sys.stdin` is the stdio transport in one clause. A request is one line; the loop is a
  server. There is no framing header and no length prefix, which is exactly what Day 33 taught.
- The `if not line: continue` guard skips blank lines. A blank line is not a message, and
  `json.loads("")` raises rather than returning `None`.
- `mood == "hang"` sleeps for an hour. It does not exit, it does not close the pipe, and it does not
  answer. That combination — alive, connected, silent — is the failure this part is about, and you
  cannot reproduce it by killing the process, because a closed pipe *does* wake the reader up.
- `mood == "slow"` sleeps for six seconds and then answers correctly. Slow is not broken. That is the
  point: your client has to make a decision that cannot be made correctly from the outside.
- The `print(..., file=sys.stderr, flush=True)` line is what makes
  [1.2](1.2-giving-up-ends-the-wait.md) possible. stderr is the only place a stdio server may talk
  without corrupting the protocol
  ([Day 33's 2.3](../../../day-33-client-and-transports/parts/02-stdio/2.3-the-only-place-left-to-talk.md)),
  and `flush=True` is required because otherwise Python buffers it and the timestamps in the next
  part would be a lie.
- `sys.stdout.flush()` after the write is not optional either. Without it the reply sits in a buffer
  and the client sees a hang that the server does not believe it is causing.

Now the client, with the deadline as the one thing that changes between the two runs:

```python
# days/day-38-failure-and-migration-lab/lab/deadline.py
DEADLINE = float(os.environ.get("DEADLINE", "2.0"))


def call(mood: str, deadline: float) -> tuple[str, float]:
    """Send one request to slow_server.py and wait at most `deadline` seconds."""
    proc = subprocess.Popen(
        [sys.executable, "slow_server.py", mood],
        stdin=subprocess.PIPE,
        stdout=subprocess.PIPE,
        text=True,
    )
    started = time.monotonic()
    box: list[str] = []

    def read() -> None:
        line = proc.stdout.readline()
        box.append(line)

    reader = threading.Thread(target=read, daemon=True)
    proc.stdin.write(json.dumps(REQUEST) + "\n")
    proc.stdin.flush()
    reader.start()
    reader.join(timeout=deadline if deadline > 0 else None)

    elapsed = time.monotonic() - started
    if reader.is_alive():
        proc.kill()
        return "TimeoutError: no response within the deadline", elapsed
    proc.kill()
    if not box or not box[0].strip():
        return "empty response: the server closed without answering", elapsed
    return "result: " + json.dumps(json.loads(box[0])["result"]["tools"]), elapsed
```

**Line by line:**

- `DEADLINE` is read from the environment so that the two arms differ by one word on the command
  line and nothing else. An ablation you have to edit a file to run is an ablation nobody runs.
- `subprocess.Popen([...], stdin=PIPE, stdout=PIPE, text=True)` is the stdio transport, by hand. The
  server's address is a command line, which is Day 33's
  [2.1](../../../day-33-client-and-transports/parts/02-stdio/2.1-connecting-is-launching.md).
  `text=True` gives strings instead of bytes so the JSON layer does not need decoding.
- `time.monotonic()` rather than `time.time()`. Monotonic time cannot go backwards when the machine
  syncs its clock, and every elapsed measurement in this day depends on that.
- The reader runs on a **thread** because `readline()` on a pipe has no timeout argument. There is no
  `proc.stdout.readline(timeout=2)` in the standard library, and that absence is not an oversight —
  the operating system's read call genuinely blocks. Putting the block on a thread you can abandon is
  the smallest honest way to bolt a clock onto something that has none.
- `daemon=True` means the thread does not keep the process alive. Without it, the script itself would
  hang at exit waiting for the reader it just gave up on — the same bug, one level up.
- `box` is a plain list because it is the simplest thing a thread can hand back. A `queue.Queue`
  would be more idiomatic and would say nothing extra here.
- `reader.join(timeout=...)` is the deadline. `join` returns when the thread finishes **or** when the
  timeout expires, and it does not tell you which, so the next line has to ask.
- `if reader.is_alive()` is how you find out which of those two things happened. The thread is still
  blocked in `readline()`, so the answer never came.
- `deadline if deadline > 0 else None` maps `DEADLINE=0` onto `join(timeout=None)`, which waits
  forever. That is the arm with no clock, and it is written as the absence of a number rather than a
  very large number on purpose: those are different behaviours and conflating them is how "we do have
  a timeout, it is one hour" gets written down.
- `proc.kill()` on both paths. A client that gives up and leaves the child process running has traded
  a hang for a leak.
- The empty-line check exists because a pipe that closes returns `""` from `readline()`, and `""` is
  not a hang — it is a different failure with a different fix. Day 33's
  [2.4](../../../day-33-client-and-transports/parts/02-stdio/2.4-closing-up.md) owns that one.

Run both arms:

```bash

DEADLINE=2.0 uv run python deadline.py slow
```

**Line by line:**

- `cd` into `lab/` first, because `deadline.py` launches `slow_server.py` by relative path. The two
  files are a pair.
- `DEADLINE=0` is the arm with no clock: the client waits as long as the server likes.
- `DEADLINE=2.0` is the arm with a clock, against the same server doing the same work.
- **Zero model calls.** There is no model anywhere in this section.

Measured on 2026-09-04:

```text
server mood : slow
deadline    : none
elapsed     : 6.05s
outcome     : result: [{"name": "lookup_ticket"}, {"name": "search_kb"}]

server mood : slow
deadline    : 2.0s
elapsed     : 2.01s
outcome     : TimeoutError: no response within the deadline
```

The server is identical in both runs. The work is identical. The only difference is whether the
caller decided in advance how long it was prepared to wait, and that decision is the whole of the
difference between `6.05s` and `2.01s`.

Now the version that has no happy ending:

```bash
DEADLINE=0 uv run python deadline.py hang
```

**Line by line:**

- Same script, same arm, one different mood. The server reads the request and sleeps for an hour.
- It prints the two header lines and then nothing. **Press Ctrl-C.** The absence of any further
  output is the finding; there is no traceback to paste because nothing raised.

That is the shape of the failure, and it is worth sitting with for a second: the process is healthy,
the pipe is open, no exception exists anywhere in the system, and the request will never complete.
Your monitoring sees a live process. Your logs are clean.

## When it breaks

Add a deadline in the wrong place and you get a new failure that reads like the old one.

The most common wrong place is the socket, on HTTP. `urllib` and `httpx` both accept a `timeout`
argument that limits how long the client waits for the *next chunk of bytes*, not how long the whole
request may take. A server that sends one byte a second for an hour never trips it. The error you get
when it does trip is this:

```text
Traceback (most recent call last):
  File "client.py", line 12, in <module>
    with urllib.request.urlopen(req, timeout=2.0) as resp:
  ...
TimeoutError: The read operation timed out
```

That message says *read*, and it means it. It is a per-read deadline, not a per-request one. The fix
is not a bigger number — it is a second, outer deadline on the whole call, which is exactly what Day
44's `with_timeout` is for.

The second wrong place is a deadline with no policy behind it. A client that times out and
immediately retries with the same deadline, forever, has not stopped waiting; it has arranged to wait
in a loop, and it is now also generating load on a server that is already struggling.
[2.2](../02-the-x-ray/2.2-malformed-is-not-transient.md) is where that bill gets counted.

The third is a deadline shorter than the work. Set two seconds against a tool that legitimately takes
ten, and you have converted a working system into one that never completes anything, while the server
does all the work anyway ([1.2](1.2-giving-up-ends-the-wait.md)). The fix for genuinely long work is
not a longer deadline; it is a task handle, which
[Day 36](../../../day-36-long-jobs-and-tasks/LESSON.md) built.

## In production

**What a professional writes instead:** two deadlines, not one. A **connect** deadline of a second or
two, because a server that has not accepted your connection is not going to get better, and a
**total** deadline per call, chosen per tool rather than globally, because `lookup_ticket` and
`reindex_archive` do not deserve the same patience. Both are configuration, not constants, because
the right numbers are discovered in production and nobody wants to ship a build to change one.

**What degrades at scale:** thread and connection exhaustion. One hung call is invisible. Two hundred
hung calls, each holding a worker, is an outage in a service where nothing crashed. This is the
failure mode that makes people think a timeout is a nicety: at low traffic it looks like patience,
and at high traffic it is the difference between a slow dependency and a dead application.
[Day 44](../../../day-44-client-hardening/LESSON.md) is where Sutra writes the rule down, and it is
the day whose paper is about exactly this: the slowest few calls, not the average one.

**The failure mode that only appears with real traffic:** deadlines that do not compose. Sutra gives
an MCP call ten seconds. The caller above Sutra gave the whole request five. The inner deadline never
fires, because the outer one already killed the request — so your careful per-tool numbers are dead
code and you cannot tell from a log. Systems that get this right pass a **remaining budget** down
instead of a fixed timeout, so each hop asks for less than the one above it.

**The review comment a senior engineer leaves:** *"there is no timeout on this call. What happens to
the queue if this server takes six seconds instead of fifty milliseconds? Give me the number you want
and where it is configured — 'it has always been fast' is not a deadline."*

**The interview question:** *"a downstream service stops responding. What does your service do?"* The
honest answer names the clock first: *"whatever it does, it does because we chose it, because the
transport will never tell us the peer is dead. We put a per-call deadline in front of every MCP call
and we set it per tool, because a lookup and a re-index do not deserve the same patience. We proved
it the boring way — a server that sleeps for six seconds and a client with a two-second budget, and
we watched the client stop at 2.01 seconds while the server carried on. The thing that surprised me
is that with no deadline there is no error at all. It is not that you get a bad answer late. It is
that nothing ever happens and nothing is ever logged."*
