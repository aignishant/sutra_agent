# 5.3 — What the migration actually costs

## One-line answer

A migration path that reads *"integrate directly with LLM provider APIs"* is one sentence in a
registry and a list of things you now own — an account, a key, a budget, a rate-limit strategy, a
failure path and a bill — which is why a deprecation is a planning item and not a rename.

## The story

The building had one water connection and the landlord looked after it.

There was a tank on the roof, a pump, and a man who came when the pump made a noise. Everybody paid a
share in the maintenance and nobody in any of the flats had ever thought about water, except on the
days it did not come.

Then the arrangement ended, and each flat got its own connection.

The bit everyone had expected was the plumber and the meter. The bits nobody had expected were: your
own tank, so your own decision about how big; your own bill, which arrives to you and which you now
have an opinion about; your own responsibility on the day the supply is cut, which used to be a
notice on the noticeboard and is now a phone call you make; and the discovery that the flat on the
top floor has terrible pressure, which was always true and had always been the landlord's problem.

Nothing about the water changed. What changed is who owns the parts of it that were previously
invisible.

## The idea in plain language

[4.2](../04-the-leaving-list/4.2-three-things-being-taken-away.md) listed the three migration paths
in the registry:

- Roots → *"Pass directories or files via tool parameters, resource URIs, or server configuration"*
- Sampling → *"Integrate directly with LLM provider APIs"*
- Logging → *"Log to `stderr` for stdio transports; use OpenTelemetry for observability"*

Each of those is one line, and each of them is a different size. The registry is not being evasive —
it is a registry, and its job is to name the destination rather than to draw the map. But a plan built
by reading only that column will be wrong by an order of magnitude, because **the size of a migration
is not the size of the sentence describing it.**

The useful way to read a migration path is to ask what the deprecated feature was **doing for you
that you never had to think about**, because that is what you are about to acquire. A feature is a
bundle: the visible mechanism, plus the operational concerns it absorbed.

Take the three in order.

**Roots → tool parameters.** The visible change is small: instead of a capability handshake, the path
goes in the arguments. What you acquire is validation. A path in a capability block was negotiated
once, by a client you trusted, and checked once. A path in a tool argument arrives on every call and
can be anything the caller says, including `../../etc`. So the migration is one schema field plus a
path-containment check plus a decision about what to do when it fails — and, as
[4.2](../04-the-leaving-list/4.2-three-things-being-taken-away.md) argued, that is a security
*improvement*, because the permission is now visible in every call rather than invisible after the
first one. It is still work that did not exist before.

**Logging → stderr and OpenTelemetry.** The visible change is a function call. What you acquire is an
observability stack: a collector, a place to send spans, a retention decision, and an agreement about
what the fields are called. For a server that already has one, this is genuinely a rename. For a
server that does not, "use OpenTelemetry" is a project.

**Sampling → your own provider integration.** The visible change is that you now call a model API. What
you acquire is the whole of what the client was quietly providing: an account with a provider, a key
to keep out of git, a **budget**, a rate-limit strategy, a retry-and-backoff path for 429, a decision
about which model, and the ongoing job of noticing when that model is retired. This is not a rename by
any reading. It is the difference between a service that has no relationship with a model provider and
one that does.

That is why this part exists as its own part. The three sentences look parallel in the registry and
are not parallel in a plan.

## Why Sutra needs it

Sutra owns nothing on the leaving list ([4.1](../04-the-leaving-list/4.1-a-feature-with-a-leaving-date.md)
printed `features Sutra must migrate: 0`), so this is not a repair job. It is the estimating skill,
practised on a case where the answer is already known, so that it is available on
[Day 45](../../../day-45-the-mcp-audit/LESSON.md) when the audit asks what an exposure is worth.

And there is one place where Sutra can price the Sampling migration exactly, because Sutra has already
paid it. Everything in the "what you acquire" list above is something this project did on
[Day 9](../../../day-09-four-free-providers/LESSON.md) and has been maintaining since: the key in
`.env` and out of git (Principle 9), the free-tier roster re-verified rather than remembered, the
`gemini-3.7-flash` pin with its date in `docs/PACKAGES.md`, roughly twenty generations a day as the
standing budget, and a 429 path with `retry-after` and backoff on every call (Addendum 02). A server
that migrates off Sampling is signing up for all of it.

That is also the answer to a design temptation this day should name. `sutra_mcp` will eventually want
a model — to summarise a ticket thread, say. Borrowing the caller's would once have been the elegant
option. It is not available now, and this part is why that is a better outcome: the spend moves to
whoever caused it, and the budget is somebody's actual responsibility.

## The mechanism

> 🎬 **The scene:** a partner runs a helpdesk MCP server that uses Sampling. The deprecation scan
> from [4.3](../04-the-leaving-list/4.3-dating-somebody-elses-server.md) flags it, and you send them
> the row. They reply: *"noted, it is a one-line change, we will do it next quarter."*
>
> 😬 **The naive fix:** believe them and plan around it. The registry says *"integrate directly with
> LLM provider APIs"*, which does sound like a one-line change.
>
> 💥 **Why it fails:** they have never had a model provider account. They will discover the key
> handling, the budget, the rate limits and the model-retirement treadmill in that order, mostly in
> production, and "next quarter" becomes "we are evaluating options". Meanwhile your integration is
> built on a feature with a date.
>
> 💡 **The insight:** price a migration by what the feature was absorbing, not by what the sentence
> says. Then ask the question that actually predicts the timeline: *does this team already own one of
> these?*

There is no script here, because the mechanism is an estimate rather than an algorithm. What there is
is a way of laying it out that survives contact with a planning meeting: for each migration, the
visible change, and then the things that arrive with it.

| Migration | The visible change | What arrives with it |
| --- | --- | --- |
| Roots → tool parameters | a `paths` field in the tool schema | per-call validation · path containment · a rejection path · an audit decision |
| Logging → stderr / OpenTelemetry | `print` to stderr, or a span | a collector · a destination · retention · field naming · a cost line |
| Sampling → your own provider | a call to a model API | an account · a key kept out of git · a budget · a 429 path · a model choice · model retirement, forever |

The last row is not longer because the writing is padded. It is longer because a model provider
relationship has six ongoing obligations and a `paths` field has one.

Two rules of thumb come out of this, and they generalise past MCP.

**The first is that a migration to a thing you already own is cheap, and a migration to a thing you do
not own is a project.** "Use OpenTelemetry" costs a team that already emits spans about an afternoon,
and costs a team that has never emitted one a quarter, and the registry text is identical for both.
This is the single most reliable predictor of a migration's timeline, and it is a question you can ask
a partner directly.

**The second is that the deadline is not the migration's schedule.** Twelve months of window
([4.1](../04-the-leaving-list/4.1-a-feature-with-a-leaving-date.md) measured `327 days`) sounds
generous until it is spent on the discovery phase of a project nobody sized. The work to schedule is
not "do the migration"; it is "find out how big the migration is", and that piece is small, cheap and
can be done immediately.

There is a third thing worth saying plainly, because it is the outcome the registry cannot list. Some
servers will not migrate. A free community server that borrowed its callers' models has no budget for
its own, and the honest response to that deprecation may be to stop. When you depend on a third-party
server, "will they migrate?" is a question about their business rather than their code, and the
deprecation scan's non-zero exit is the moment to ask it.

## When it breaks

The failure is a plan, so its error text is a calendar rather than a traceback. But the *technical*
breaks that follow a rushed Sampling migration are specific and worth recognising, because they are
the shape of a system that acquired a model provider last week.

The most common is the one Addendum 02 exists to prevent:

```text
google.genai.errors.ClientError: 429 RESOURCE_EXHAUSTED. {'error': {'code': 429,
'message': 'You exceeded your current quota, please check your plan and billing
details.', 'status': 'RESOURCE_EXHAUSTED', 'details': [{'@type':
'type.googleapis.com/google.rpc.QuotaFailure', 'violations': [{'quotaMetric':
'generativelanguage.googleapis.com/generate_content_free_tier_requests',
'quotaId': 'GenerateRequestsPerMinutePerProjectPerModel-FreeTier',
'quotaValue': '5'}]}, {'@type': 'type.googleapis.com/google.rpc.RetryInfo',
'retryDelay': '47s'}]}}
```

That is the exact body this project recorded on
[Day 2](../../../day-02-llm-mechanics/parts/01-first-contact/1.3-listed-is-not-callable.md), and the
useful field is `retryDelay`. A server that used to borrow a caller's quota had no reason to handle
any of it, because it never saw it. Now it does, on every call path, and a `429` whose `retryDelay` is
ignored in favour of a client's own guess turns a rate limit into an outage.

The second is the key. A server that never had one now has one, and the first place it lands is a
configuration file next to the code:

```text
$ git show --stat HEAD | grep -i "key\|env"
 config/settings.yaml | 3 +
```

That is the commit Principle 9 exists to prevent, and it is committed by a team that has never had a
secret to look after.

The third has no error text at all and arrives months later: the model string that was correct when
the migration was done is retired, and the call starts failing on a service whose owner has moved on.
This project's own note about free rosters moving is the same hazard from the same direction —
`docs/PACKAGES.md` exists so that a model pin has a date beside it.

## In production

**What a professional writes instead:** a migration record per deprecated feature, sized before it is
scheduled. Four fields — the registry row, what the feature was absorbing, what we already own, and
what we would have to acquire — and the estimate falls out of the last two. It sits next to the
architecture decision records, because a migration forced by a deprecation is a decision even when
there is only one option.

**What degrades at scale:** the number of teams, not the amount of code. A migration that costs one
team an afternoon costs an organisation of forty services a quarter, because the expensive part is
coordination and discovery rather than the change. Platform teams that handle this well provide the
acquired thing centrally — a shared model gateway, a shared collector — which converts every team's
project back into a rename.

**The failure mode that only appears with real traffic:** the partner who migrated badly. They moved
off Sampling to their own provider, with no budget alarm and no 429 handling, and now their server
fails during *your* busy periods, because your traffic is what pushes them over their quota. Their
outage is correlated with your load and looks, from your side, exactly like their server being
unreliable under pressure. Which it is — for a reason that started as a line in a registry.

**The review comment a senior engineer leaves:** *"the migration ticket says 'switch from Sampling to
our own provider API — 1 point'. That is not one point. We have no provider account, no key handling,
no budget and no 429 path today, and all four are in scope. Split the discovery out, size it
properly, and tell me what our monthly spend becomes."*

**The interview question:** *"a protocol you depend on deprecates a feature you use. Walk me through
how you plan the migration."* The answer that sounds like experience: *"first I read the registry row
for the date and the named migration path, so I know the window rather than guessing it — MCP's is a
minimum of twelve months from the revision that marks it. Then I stop reading the sentence and ask
what the feature was absorbing on our behalf, because that is the actual work. Sampling is the good
example: the registry says 'integrate directly with LLM provider APIs', which sounds like a rename, and
what you are really acquiring is an account, a key you have to keep out of git, a budget, a 429 path,
a model choice and a permanent job tracking model retirements. Logging says 'use OpenTelemetry', which
is an afternoon if you already emit spans and a quarter if you do not. So the estimate turns on one
question — do we already own the thing we are migrating to — and the first thing I schedule is not the
migration, it is finding that out."*
