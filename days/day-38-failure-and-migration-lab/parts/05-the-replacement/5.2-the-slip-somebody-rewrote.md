# 5.2 — 💥 The slip somebody rewrote

## One-line answer

`requestState` travels through the client, so the client can edit it — and a server that decodes what
comes back without verifying it has handed an attacker a pen and its own memory to write in.

## The story

The parking token has the entry time written on it by hand.

You take it at the barrier, put it on the dashboard, and when you leave the man at the exit reads the
time off it, works out the hours and charges you. It is a good system. It is cheap, it needs no
computer, and it has worked for years.

It works because almost nobody has a pen.

A man who does have a pen changes the `9` to a `10` before he drives out, and pays for one hour
instead of two. The attendant is not careless; he is doing exactly what the system asks. He reads the
number and applies the rate. There is nothing on the ticket that lets him tell a real `10` from a
`9` with a stroke added, because the ticket was never designed to survive being edited — it was
designed on the assumption that the person carrying it would not edit it.

The fix costs almost nothing and it is not "watch the customers more carefully". It is a stamp.

## The idea in plain language

[5.1](5.1-the-question-that-comes-back-as-an-answer.md) established the pattern: the server hands
back an opaque `requestState`, the client carries it, and the client returns it unchanged. The word
"opaque" describes what the client is **permitted** to do. It says nothing about what a client is
**able** to do.

Base64 is an encoding. It scrambles nothing, protects nothing and can be reversed in one line. A
`requestState` that is base64 of JSON — which is the obvious, natural, documented-as-acceptable
implementation — is fully readable and fully editable by anyone holding it.

The specification is direct about the consequence:

> If a client request contains a `requestState` field, servers **MUST** treat `requestState` as an
> attacker-controlled input. If `requestState` influences authorization, resource access, or business
> logic, servers **MUST** protect its integrity (e.g. HMAC or AEAD) and **MUST** reject state that
> fails verification.

There is one narrow exemption, and it is worth quoting because it is the only reason not to sign:
integrity protection *"**MAY** be omitted only when tampering can cause nothing worse than request
failure."*

The tool for this is an **HMAC** — a short tag computed from the data and a secret key that only the
server has. Anyone can read the data. Nobody without the key can produce a tag that matches an edited
version. The server recomputes the tag on receipt and compares. Signing is not encryption: the
contents stay readable, and what changes is that they become unforgeable.

The specification goes further than integrity, because integrity alone stops editing and does not
stop **replay** — taking a valid, correctly-signed blob and using it again, or somewhere else. So it
says servers *"**SHOULD** include the following inside the integrity-protected `requestState` payload
and verify each on receipt"*:

| Field | Stops |
| --- | --- |
| the authenticated principal | one user redeeming another user's state |
| a short expiry | a blob kept and used weeks later |
| an identifier for the originating request | state minted for one call being spent on another |

And it adds a warning that is easy to skim past: those measures *"bound the replay window and prevent
cross-user and cross-request reuse, but do not by themselves guarantee single-use."* If the state
authorises something that must happen at most once, the server has to enforce that separately — which
is [3.2](../03-the-quiet-ones/3.2-the-ticket-closed-twice.md)'s idempotency store, arriving for the
second time today from a different direction.

## Why Sutra needs it

Day 37's `close_ticket` flow is the exact shape this attacks. The server discovers duplicates,
records *which ticket and how many* in its state, asks the user to confirm, and closes that many when
the answer comes back. The count lives in `requestState` because that is where the pattern says it
lives, and the count is a number that changes what the server does.

That makes it business logic, which puts it squarely inside the specification's **MUST**. The
exemption does not apply: tampering with `n` does not cause the request to fail, it causes the request
to succeed at a larger scale.

There is a second, quieter reason. Sutra's server will eventually run behind auth
(`sutra_mcp/auth.py`, Day 37) and against a real database
([Day 39](../../../day-39-database-tools/LESSON.md)). At that point `requestState` becomes one of very
few pieces of data that leave the trust boundary and come back, and any such thing is a place where a
security review will look. Signing it costs about six lines; explaining why it is not signed costs a
meeting.

## The mechanism

> 🎬 **The scene:** you implement MRTR the natural way. The server base64-encodes a small JSON
> context, the client carries it, the server decodes it on the retry. Everything works, including the
> three-instance case, and the tests are green.
>
> 😬 **The naive fix:** none, because nothing looks wrong. It is opaque, the specification said
> opaque, and the client is your own code anyway.
>
> 💥 **Why it fails:** "the client is your own code" stops being true the moment a request can be
> shaped by anything a user controls — a browser extension, a proxy, a modified desktop client, or a
> prompt-injected agent. Four lines of `base64` and `json` turn *close 4 tickets* into *close 400*,
> and the server does it, because it asked for its own note back and got something that looked
> exactly like one.
>
> 💡 **The insight:** opacity is a rule for well-behaved clients. Integrity is a property of the data.
> Only the second one survives a client that does not follow rules.

The mint-and-redeem pair, with the signature as the ablation:

```python
# days/day-38-failure-and-migration-lab/lab/tamper.py
SIGNED = os.environ.get("SIGNED", "0") == "1"
SERVER_KEY = b"a key that never leaves the server"  # in real life, from the environment


def mint(context: dict) -> str:
    """Pack the server's context into the string the client will carry back."""
    body = base64.b64encode(json.dumps(context).encode()).decode()
    if not SIGNED:
        return body
    tag = hmac.new(SERVER_KEY, body.encode(), hashlib.sha256).hexdigest()[:16]
    return f"{body}.{tag}"


def redeem(state: str) -> dict:
    """Unpack state the client sent back, verifying it first when we signed it."""
    if not SIGNED:
        return json.loads(base64.b64decode(state))
    body, _, tag = state.partition(".")
    expected = hmac.new(SERVER_KEY, body.encode(), hashlib.sha256).hexdigest()[:16]
    if not hmac.compare_digest(tag, expected):
        raise Rejected("requestState failed integrity check - signature does not match")
    return json.loads(base64.b64decode(body))
```

**Line by line:**

- `SERVER_KEY` is a literal here and must never be one in a real server. The comment says where it
  belongs — the environment, alongside `GOOGLE_API_KEY`, under Principle 9's rule that secrets never
  touch git. A key in the source is a key in every clone of the repository.
- `mint` produces `body` first and signs the **encoded** body rather than the original dictionary.
  That matters: signing the dictionary would mean re-serialising it on the way back to check, and two
  JSON serialisers can produce different bytes for the same object (key order, whitespace, unicode
  escaping) so the tag would sometimes fail for correct input. **Sign the bytes you send.**
- `hmac.new(key, message, hashlib.sha256)` is the standard library's HMAC. Not `hashlib.sha256(key +
  body)` — that construction is vulnerable to length extension, and the reason to reach for `hmac` is
  that it is the version somebody already got right.
- `[:16]` truncates the tag to sixteen hexadecimal characters. Truncation is legitimate and common,
  and it is a **trade**: a shorter tag is a shorter blob and a smaller forgery space. Sixteen hex
  characters is sixty-four bits, which is fine for a short-lived token and would not be for a
  long-lived one.
- `f"{body}.{tag}"` puts the two parts in one string with a separator that cannot appear in base64
  output. A dot is the conventional choice and is why signed tokens generally look like this.
- `redeem` uses `str.partition` rather than `split(".")`, so a state with no dot yields an empty tag
  instead of raising `ValueError` — a malformed input should be **rejected**, not crash the handler.
- `hmac.compare_digest(tag, expected)` rather than `tag == expected`. A plain string comparison
  returns as soon as it finds a difference, so its **duration** leaks how many leading characters were
  correct, and an attacker who can time enough requests can build a valid tag one character at a time.
  `compare_digest` takes the same time whatever it is comparing. This is one line and it is the line
  people leave out.
- `raise Rejected(...)` and not `return None`. The request stops here. The specification says a server
  **MUST** reject state that fails verification, and returning a falsy value invites a caller to carry
  on with a default.

The attack is four lines, and its shortness is the argument:

```python
def tamper(state: str) -> str:
    """The client edits the blob it was told not to look at. Four lines."""
    body, _, tag = state.partition(".")
    context = json.loads(base64.b64decode(body))
    context["n"] = 400
    edited = base64.b64encode(json.dumps(context).encode()).decode()
    return f"{edited}.{tag}" if tag else edited
```

**Line by line:**

- It needs **no key, no secret and no special access** — only the blob, which the protocol hands it.
- `context["n"] = 400` changes a count that the server will act on. Not a display value: a number
  that decides how many tickets get closed and how many customers get emailed.
- `f"{edited}.{tag}" if tag else edited` re-attaches the **old** tag when there is one. That is what a
  real attacker does — keep everything that looks official — and it is what makes the signed arm's
  rejection meaningful rather than accidental. The tag is valid; it is valid for different bytes.

Look at the two `client returns` lines. In both runs the client sent back a blob that *looks* exactly
like the one it was given. In the signed run the tag is even the correct tag — for the original body.
Four hundred tickets against nought, and the difference is a sixteen-character suffix.

Notice also what the blob contains in plain sight: `principal` is `desk@sutra`, readable by anyone who
holds it. Signing did not hide that and was never meant to. If the contents are sensitive, the tool is
encryption (AEAD), which the specification names alongside HMAC for exactly this reason.

## When it breaks

The signed arm's rejection is the error you want:

```text
Rejected: requestState failed integrity check - signature does not match
```

Short, unambiguous, and it does not say **why** it does not match — deliberately. An error that
distinguished "wrong tag" from "expired" from "wrong principal" would be telling an attacker which
part of the forgery to work on next.

The breaks in the *implementation* are more interesting than the attack, because they produce a server
that appears to be signing and is not.

**Signing the object instead of the bytes.** Serialise, sign the object, then serialise again on the
way back to verify, and you are comparing tags over two different byte strings whenever key order or
whitespace differs:

```text
Rejected: requestState failed integrity check - signature does not match
```

— on perfectly legitimate traffic, intermittently, which is the worst possible failure signature
because it looks like an attack and is a bug.

**Verifying after using.** Decode the body, read `n`, then check the tag. The check now happens after
the damage.

**A key that is not secret.** Committed to the repository, baked into a container image, or shared
between the client and the server. Any of those and the tag is decoration: an attacker with the key
signs whatever they like, and the server accepts it happily, with no error text at all.

**No expiry.** The tag stays valid forever, so a blob captured today works next year. This is the one
the specification's `SHOULD` list is aimed at, and it is why the fields in that list go **inside** the
protected payload rather than beside it.

## In production

**What a professional writes instead:** a signed, short-lived, self-describing token. The protected
payload carries the principal, an expiry, and a digest of the originating request's method and salient
parameters, and the server verifies all three before touching the business fields. In most stacks this
is not hand-rolled at all — it is a signed token library — and the reason to hand-roll it in a lab is
to see that the whole mechanism is `hmac.new` and `compare_digest`.

Where single-use genuinely matters, the token is paired with a server-side record of redemption, which
is the same table [3.2](../03-the-quiet-ones/3.2-the-ticket-closed-twice.md) built for idempotency.
The specification says as much: the `SHOULD` list bounds the replay window, and anything that must
happen at most once needs enforcing server-side.

**What degrades at scale:** key rotation. One key in one process is easy. A fleet where a blob minted
by an instance holding key *n* is redeemed by an instance already rotated to key *n+1* rejects
legitimate traffic during every rotation. The standard answer is a key **identifier** in the token and
a small set of accepted keys, with an overlap window longer than the token's lifetime — which is a
design decision to make before the first rotation, not during it.

**The failure mode that only appears with real traffic:** the blob that outgrew its purpose. A
`requestState` that started as `{"ticket": ..., "n": ...}` accretes fields, and one day somebody puts
a permission or a role in it. It has been signed all along, so nothing breaks — but the security
posture quietly changed from "state that only causes a failed request" to "state that grants access",
and the exemption clause that once applied no longer does. Nobody notices because the code that
changed was one dictionary key.

**The review comment a senior engineer leaves:** *"`requestState` here is base64 of JSON and we decode
it and act on the count. The spec says treat it as attacker-controlled and protect its integrity if it
influences business logic — this does. HMAC it, use `compare_digest`, and put the principal and an
expiry inside the signed payload, not next to it."*

**The interview question:** *"the MRTR pattern sends server state through the client. Is that safe?"*
The answer is a distinction: *"only if the server signs it. Opacity is a rule for clients — the spec
says a client must not inspect or modify `requestState` — and integrity is a property of the data.
Base64 satisfies the first and gives you nothing of the second. We demonstrated it: four lines of
`base64` and `json` changed a count from 4 to 400 and the server closed 400 tickets. With an HMAC and
`compare_digest` the identical edit is rejected, and the spec requires it whenever the state
influences authorisation, resource access or business logic. Beyond integrity you also want the
principal, an expiry and a request digest inside the signed payload, because a valid blob replayed by
somebody else is still valid — and if the operation must happen at most once, that is a server-side
record, not a token property."*
