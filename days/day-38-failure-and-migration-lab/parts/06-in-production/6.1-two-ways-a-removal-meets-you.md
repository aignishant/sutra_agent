# 6.1 — 💥 Two ways a removal meets you

## One-line answer

The same removal can raise the same exception class and cost you either a minute or a day, depending
entirely on whether whoever removed it left a message in the error — and `mcp` 2.1.1 contains one
example of each, which you can run today without touching the pin.

## The story

Two shops on the same street closed.

The first one had a printed sheet taped inside the glass: *we have moved to number 14, opposite the
bank, from the 3rd — same phone number.* You read it standing on the pavement, walked two minutes,
and that was the end of it.

The second one had a blank shutter. Nothing on it. You came back the next day in case it had been a
holiday, asked in the shop next door, who thought maybe they had closed for good but were not sure,
and eventually somebody said they had heard the owner had moved somewhere near the market. You found
it a fortnight later.

Both shops moved. Both moves were entirely reasonable. One of them cost the whole street two minutes
each and the other cost the whole street a fortnight each, and the difference was a sheet of paper
that took one person five minutes to write.

## The idea in plain language

When something is removed from a library, the code that used it stops working. That much is fixed.
What is not fixed is **what the failure tells you**, and that turns out to matter more than the
removal itself.

There are two shapes.

A **bare removal** is when the thing is simply gone. Python's import machinery looks for a module,
does not find it, and says so:

```text
ModuleNotFoundError: No module named 'mcp.shared.version'
```

That message is true and complete, and it contains nothing you did not already know. It does not say
whether the module moved or vanished, what replaced it, or that you are on a different major version
from the one your code was written against.

A **maintained removal** is when somebody anticipated this exact moment and put the answer in the
error. The `mcp` SDK does this for one of its removals, and the file that does it is worth reading
because it is nine lines and it exists for no other reason:

> *"This module has no API. Importing it, or anything below it, raises `ModuleNotFoundError` with a
> message that points at the migration guide. It exists only because the bare 'No module named
> `mcp.server.fastmcp`' gave v1 code no hint that the installed SDK is a different major version."*

Both are `ModuleNotFoundError`. Both stop the program at the same line. One of them ends the
investigation and the other one starts it.

The name for the second shape is a **deprecation shim** — a stub left at the old address whose only
job is to say where the new one is. This connects directly to
[4.1](../04-the-leaving-list/4.1-a-feature-with-a-leaving-date.md)'s lifecycle policy: a policy
governs the *specification*, and a shim is the same courtesy applied to an *implementation*. They are
independent, and the SDK's own policy says so outright — *"Removal from the specification does not
oblige an SDK to drop the feature from releases. That timeline is governed by the SDK's own
revision-support policy."*

## Why Sutra needs it

Day 32 found that this repository's pinned `mcp==1.29.1` tops out at protocol revision `2025-11-25`
while the specification is at `2026-07-28`, and that PyPI's current `mcp` is `2.1.1` and speaks the
newer one. It recorded the gap and changed nothing, because a version bump is a plan decision.

That decision is still open, and this day is where the reader earns the right to make it — by finding
out what the bump actually breaks rather than by assuming. **The pin is not being changed here
either.** What this part does is rehearse the bump in a throwaway environment, so the two failure
shapes above are things you have seen rather than things you have read about.

It also gives Sutra a rule to apply to its own code. `sutra/mcp/` and `sutra_mcp/` are packages other
days import from — Day 33 owns `client.py`, Day 34 owns `server.py`, and days 35 to 44 add modules
beside them. When one of those moves, the choice between a bare removal and a shim is a choice
somebody makes, and this part is the argument for which one.

## The mechanism

> 🎬 **The scene:** somebody bumps `mcp` in `pyproject.toml` from `1.29.1` to `2.1.1`, runs `uv sync`,
> and the test suite goes red. They open the first failure.
>
> 😬 **The naive fix:** read `ModuleNotFoundError: No module named 'mcp.shared.version'`, conclude
> that the install is broken, and run `uv sync --reinstall`. It is a reasonable first move and it
> changes nothing.
>
> 💥 **Why it fails:** the module is not missing because of a bad install. It moved to
> `mcp.types.version` in a major version that reorganised the package, and nothing in the error says
> so. Every minute spent on the install is a minute spent on the wrong problem.
>
> 💡 **The insight:** the cost of a removal is set by its error message. The removal is the same
> either way; a sentence in the exception is what decides whether it is a lookup or an investigation.

You can run this against 2.1.1 **without changing the pin**, because `uv` will build a throwaway
environment for one command:

```bash
uv run --isolated --no-project --with "mcp==2.1.1" python -c "from mcp.shared.version import SUPPORTED_PROTOCOL_VERSIONS"
```

**Line by line:**

- `--isolated` ignores the project's own environment, so nothing that follows can be answered by the
  packages already installed.
- `--no-project` stops `uv` reading `pyproject.toml` at all. Without it, `uv` would try to resolve the
  project's dependencies alongside the one you asked for, and a conflict would produce a resolver
  error instead of the experiment.
- `--with "mcp==2.1.1"` names the version to fetch into that throwaway environment. **`pyproject.toml`
  and `uv.lock` are not touched, and `git diff` is empty afterwards** — which is the whole reason this
  is allowed on a day that is forbidden to bump the pin.
- `python -c "..."` runs one import and nothing else. The smallest possible probe: does this name
  exist.

Measured on 2026-09-04:

```text
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'mcp.shared.version'
```

Two frames and a sentence. Now the other one, from the same package, in the same style of command:

```bash
uv run --isolated --no-project --with "mcp==2.1.1" python -c "from mcp.server.fastmcp import FastMCP"
```

**Line by line:**

- Identical in every respect except the module being imported. That is what makes the comparison worth
  anything: same SDK, same version, same command shape, same exception class.

Measured the same day:

```text
Traceback (most recent call last):
  File "<string>", line 1, in <module>
  File "C:\Users\nisha_gnzw\AppData\Local\uv\cache\archive-v0\_MCF-7DjSs0jHP4r\Lib\site-packages\mcp\server\fastmcp.py", line 16, in <module>
    raise ModuleNotFoundError(_MESSAGE, name=__name__)
ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x, where FastMCP was renamed to MCPServer (from mcp.server.mcpserver import MCPServer) and other APIs changed; see the migration guide at https://py.sdk.modelcontextprotocol.io/v2/migration/#fastmcp-renamed-to-mcpserver or pin 'mcp<2' to keep running v1 code.
```

Count what that message contains. **What happened** — this is mcp 2.x. **The new name** —
`MCPServer`. **The exact import to write** — `from mcp.server.mcpserver import MCPServer`. **A
warning that there is more** — "and other APIs changed". **Where the full answer is** — a URL. And
**an escape hatch** — `pin 'mcp<2'` to keep running today's code while you plan.

Six pieces of information, in one string, delivered at the exact moment somebody needs them, to
somebody who by definition is looking at the traceback. There is no documentation strategy that beats
that, because no documentation strategy gets to choose its moment.

The mechanism producing it is not clever, which is the encouraging part:

```python
# mcp/server/fastmcp.py, from mcp==2.1.1
_MESSAGE = (
    "No module named 'mcp.server.fastmcp'. This is mcp 2.x, where FastMCP was renamed to MCPServer "
    "(from mcp.server.mcpserver import MCPServer) and other APIs changed; see the migration guide at "
    "https://py.sdk.modelcontextprotocol.io/v2/migration/#fastmcp-renamed-to-mcpserver "
    "or pin 'mcp<2' to keep running v1 code."
)

raise ModuleNotFoundError(_MESSAGE, name=__name__)
```

**Line by line:**

- The module's entire body is a constant and a `raise`. It defines no classes and exports no names,
  because a shim that offered a working `FastMCP` would be a compatibility layer with a maintenance
  cost, and this is deliberately not that.
- The message **starts** with the text the bare error would have produced — *"No module named
  'mcp.server.fastmcp'"* — so that anybody searching for the standard string still finds this. That
  is a small decision and it is the difference between the message helping and the message replacing
  the thing people search for.
- `name=__name__` sets the exception's `name` attribute to the module being imported, which is what
  the bare `ModuleNotFoundError` would have carried. Tooling that inspects `exc.name` — an IDE, a
  dependency analyser — keeps working.
- `raise` at **module scope**, not inside a function. The exception fires on import, which is the
  moment the old code touches the old address, rather than later when something is called.
- The escape hatch is named last and is a real one: `pin 'mcp<2'` is advice against upgrading, offered
  by the people who wrote the upgrade. A migration note that does not tell you how to *not* migrate
  today is a note written for the author's convenience.

Now compare the two failures side by side, which is the actual finding:

| | `mcp.shared.version` | `mcp.server.fastmcp` |
| --- | --- | --- |
| Exception class | `ModuleNotFoundError` | `ModuleNotFoundError` |
| Frames in the traceback | 2 | 3 |
| Says what replaced it | no | yes, with the import line |
| Says which major version you are on | no | yes |
| Offers a way to keep running | no | yes |
| Cost to resolve | search, guess, read a changelog | read the message |

The removal is equally complete in both cases. `mcp.shared.version` really is gone; its contents live
at `mcp.types.version` with a larger set of names. Nothing about the *code* differs in quality. What
differs is that somebody spent five minutes writing a sentence for a stranger.

## When it breaks

The shim itself has a failure mode, and it is the reason not every removal gets one.

A shim that **works** — that quietly forwards to the new location — is not a signpost, it is a
compatibility layer. Code keeps running, nobody migrates, and the shim has to be maintained across
every future change until somebody finally deletes it and everyone is surprised on that day instead of
this one. That is why the file above raises rather than re-exporting: it is a message, not a bridge.

A shim can also be **wrong**, and a wrong shim is worse than none. A message naming a symbol that has
since been renamed again sends the reader confidently in the wrong direction, and they will trust it
more than they would have trusted their own search. The maintenance cost of a shim is not zero; it is
the cost of keeping one sentence true.

And a shim only covers the addresses somebody thought of. Here is a *third* removal in the same
package, which is neither of the two shapes above —
`uv run --isolated --no-project --with "mcp==2.1.1" python -c "from mcp.types import TASK_STATUS_INPUT_REQUIRED"`:

```text
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ImportError: cannot import name 'TASK_STATUS_INPUT_REQUIRED' from 'mcp.types' (C:\Users\nisha_gnzw\AppData\Local\uv\cache\archive-v0\_MCF-7DjSs0jHP4r\Lib\site-packages\mcp\types\__init__.py)
```

That is the shape you get when the module still exists and a name inside it does not: an `ImportError`
rather than a `ModuleNotFoundError`, and it names the file it looked in, which is at least a
starting point. The constant itself belonged to the experimental tasks API that
[Day 36](../../../day-36-long-jobs-and-tasks/LESSON.md) met, and it is gone. There is no place to put
a signpost for a missing attribute short of a module-level `__getattr__`, which is possible and which
almost nobody writes. So most removals will meet you as one of these two bare shapes, and the lesson
is not "expect a message" — it is "leave one".

## In production

**What a professional writes instead:** for anything other people import, a removal comes in two
steps. First a release where the old name still works and emits a `DeprecationWarning` naming the new
one. Then a release where the old name is a stub that raises with the same text. The rule of thumb is
that the message must contain the **new import line**, verbatim, so it can be copied — a message that
says "this was moved" without saying where is the blank shutter with better manners.

Inside Sutra, this applies the moment a module under `sutra/` or `sutra_mcp/` is renamed. It is nine
lines, and this day is the argument for spending them.

**What degrades at scale:** the number of consumers. One consumer means a conversation; a hundred
means a hundred separate investigations of the same removal, and the cost of the missing sentence is
multiplied by every one of them. This is why library authors are held to a standard that application
authors are not — not because they are better engineers, but because their mistakes are multiplied by
their user count.

**The failure mode that only appears with real traffic:** the transitive bump. Nobody upgraded `mcp`
on purpose; a dependency of a dependency did, and the removal surfaces in a service whose team has
never heard of the SDK. They see `ModuleNotFoundError: No module named 'mcp.shared.version'` in a
build log and have no context at all. A message that names the major version is the only thing that
gets them to the right page, and it is worth writing precisely because the reader may not know what
library they are looking at.

**The review comment a senior engineer leaves:** *"you are deleting `sutra/mcp/client.py`'s old entry
point. Leave a stub that raises with the new import line in the message — nine lines, and it saves
every one of our services a search. Do not make it forward to the new module, or nobody will ever
migrate."*

**The interview question:** *"you maintain a library and you are removing a public module. What do you
do?"* Answer with the comparison: *"leave a stub at the old address that raises with a message
containing the new import line, the fact that this is a major version, a link to the migration guide,
and how to pin back. I have a favourite example — `mcp` 2.1.1 removed two things and handled them
differently. `mcp.shared.version` is gone, and you get 'No module named mcp.shared.version', which is
true and useless. `mcp.server.fastmcp` is a nine-line module whose only job is to raise a
`ModuleNotFoundError` whose message names `MCPServer`, gives the exact import, links the guide and
tells you to pin `mcp<2` if you are not ready. Same exception class, same removal, and one of them
ends the investigation in the traceback. The one thing I would not do is make the shim actually work,
because then it is a compatibility layer and nobody ever migrates."*
