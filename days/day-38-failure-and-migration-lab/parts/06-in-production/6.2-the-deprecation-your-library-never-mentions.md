# 6.2 — 💥 The deprecation your library never mentions

## One-line answer

A specification deprecation is invisible in your editor and silent at runtime: `mcp` 1.29.1 exports
Roots, Sampling and Logging with no marker of any kind, `mcp` 2.1.1 mentions two of the three in a
docstring and warns about none of them — so the only way to know a feature is on its way out is to
read the registry, not to ask the library.

## The story

The strip of tablets has no date printed on it.

The date was on the box. The box went in the bin the week you opened it, because it was a box and the
tablets were in a drawer. Now there is a strip of eight left in the drawer with the name of the
medicine embossed on the foil, and nothing else.

You look at it carefully. You turn it over. There is genuinely nothing there — not because anyone was
careless, but because the expiry belongs to the packaging and this is not the packaging. The strip is
doing exactly its job, which is to hold eight tablets, and it never had another one.

So you cannot tell from the thing in your hand. You have to remember when you bought it, or find the
box, or ask. And the honest answer is that most people, holding a strip that looks perfectly fine,
take the tablet.

## The idea in plain language

[4.1](../04-the-leaving-list/4.1-a-feature-with-a-leaving-date.md) established that a deprecated
feature *"remains fully functional"* and that the registry is the record. This part is about what
happens when you skip the registry and ask your tools instead, which is what everybody actually does.

There are three places a Python developer would expect a deprecation to show up:

| Where | What you would expect |
| --- | --- |
| The type does not exist | An `ImportError` — the strongest possible signal |
| The type is marked | `@deprecated`, so an editor strikes it through and a type checker complains |
| Using it warns | A `DeprecationWarning` at runtime, visible with `-W always` or in a test run |

The lifecycle policy actually asks for two of these. It says Tier 1 SDKs *"must mark the corresponding
API surface deprecated using the language's native mechanism"* — naming `@Deprecated` in Java,
`[Obsolete]` in .NET, `@deprecated` JSDoc in TypeScript — and *"should emit a runtime warning when a
deprecated feature is exercised, using the language's idiomatic mechanism (for example Python's
`DeprecationWarning`…)"*.

So the expectation is reasonable and is written down. The measurement below is what is actually
shipped, and it is the finding of this part: **on both the pinned SDK and the current release, using
a deprecated feature produces no warning at all**, and on the pinned SDK there is no marker either.

The reason this matters more than it sounds is a pattern of reasoning that feels rigorous and is not:
*"I checked — nothing in our code raises a deprecation warning, so we are clear."* That sentence is
true and its conclusion is false. Absence of a warning is not evidence of currency. It is evidence
that nobody added a warning.

## Why Sutra needs it

Sutra's whole defence against this is `deprecation_scan.py` from
[4.3](../04-the-leaving-list/4.3-dating-somebody-elses-server.md), which reads a registry copied from
a published page rather than asking a library. This part is the justification for having built it that
way. If the SDK told you, the scanner would be redundant.

It also matters for how [Day 45](../../../day-45-the-mcp-audit/LESSON.md)'s audit is written. An audit
step that says "run the test suite with `-W error::DeprecationWarning` and confirm it is clean" would
pass today on a codebase using all three deprecated features, and would therefore be an audit step
that certifies nothing. The audit has to compare against the registry.

And it settles a question about the bump this repository has not made. A reader might reasonably
assume that upgrading to `mcp` 2.1.1 would at least *tell them* what is deprecated. Measured below: it
tells them slightly more than 1.29.1 does, in a place no tool reads, and it still warns about nothing.

## The mechanism

> 🎬 **The scene:** you have inherited an MCP server and you want to know whether it uses anything on
> the way out. You have an editor with a type checker and a test suite.
>
> 😬 **The naive fix:** grep for strikethrough, run the tests with `-W error::DeprecationWarning`, and
> see what comes up. Nothing does, so the code is clean.
>
> 💥 **Why it fails:** the SDK exports `ListRootsRequest`, `CreateMessageRequest` and
> `SetLevelRequest` as ordinary, unmarked types, and constructing any of them raises nothing. Your
> tooling agreed with you because your tooling was never told. The three features are deprecated in
> the specification and invisible in the library.
>
> 💡 **The insight:** deprecation lives in the specification, not in the package. Check the registry,
> and treat "no warning" as "not measured".

One probe, run against two SDKs. Its three blocks answer three separate questions, and the third is
the one this part is about:

```python
# days/day-38-failure-and-migration-lab/lab/bump_probe.py
DEPRECATED = [
    ("Roots", "ListRootsRequest", {"method": "roots/list"}),
    (
        "Sampling",
        "CreateMessageRequest",
        {
            "method": "sampling/createMessage",
            "params": {
                "messages": [{"role": "user", "content": {"type": "text", "text": "hi"}}],
                "maxTokens": 1,
            },
        },
    ),
    ("Logging", "SetLevelRequest", {"method": "logging/setLevel", "params": {"level": "info"}}),
]


def marker(obj: object) -> str:
    """Say whether a class carries any deprecation marker a reader could see."""
    doc = (getattr(obj, "__doc__", "") or "").lower()
    if getattr(obj, "__deprecated__", None):
        return "yes (__deprecated__)"
    return "yes (docstring)" if "deprecat" in doc else "no"


def warns(cls: object, **kwargs: object) -> str:
    """Build one instance and report any warning the SDK raised while doing it."""
    with warnings.catch_warnings(record=True) as caught:
        warnings.simplefilter("always")
        try:
            cls(**kwargs)  # type: ignore[operator]
        except Exception as exc:  # noqa: BLE001 - a construction error is still an answer
            return f"could not build ({type(exc).__name__})"
    return ", ".join(type(w.message).__name__ for w in caught) if caught else "no"
```

**Line by line:**

- Each `DEPRECATED` row carries the **smallest keyword arguments that build one**, which is not
  decoration. A probe that cannot construct the object cannot ask whether construction warns, and the
  first version of this script reported `could not build (ValidationError)` for two of three rows —
  which would have been a measurement of the probe rather than of the SDK. The `params` blocks are
  there so all three rows reach the question.
- `marker` checks `__deprecated__` **first**, because that is the attribute Python's own
  `typing.deprecated` and `typing_extensions.deprecated` set. If it is present, an editor and a type
  checker both know, and that is the strong answer the policy asks for.
- Falling back to a **docstring** search is a deliberately generous second test. A sentence in a
  docstring is not the language's native mechanism and no tool acts on it, but it is at least
  something a reader could find, so counting it separates "documented somewhere" from "nowhere at
  all".
- `warnings.catch_warnings(record=True)` with `simplefilter("always")` is what makes the runtime
  question answerable. Python **hides** `DeprecationWarning` by default outside `__main__`, so a
  naive check would report no warning even from a library that raises one properly. Overriding the
  filter removes that excuse from the measurement.
- The bare `except Exception` here is one of the few places it is right, and the comment says why: a
  construction failure is a legitimate answer to "does building this warn?", and letting it propagate
  would abort the probe on the first awkward type.
- `type(w.message).__name__` reports the **class** of each warning, so a `DeprecationWarning` and a
  `PendingDeprecationWarning` and a `UserWarning` are distinguishable. What matters is not that
  something was said but what kind of thing it was.

Run it against the pin, and then against the release, without touching `pyproject.toml`:

```bash
cd days/day-38-failure-and-migration-lab/lab
uv run python bump_probe.py
uv run --isolated --no-project --with "mcp==2.1.1" python bump_probe.py
```

**Line by line:**

- The first uses the project's own environment — `mcp==1.29.1`, exactly what `uv sync` installed.
- The second is the throwaway environment from
  [6.1](6.1-two-ways-a-removal-meets-you.md): `--isolated` ignores the project environment,
  `--no-project` stops `uv` reading `pyproject.toml`, and nothing is written to the lockfile.
- **Zero model calls.** The script imports and introspects.

Measured on 2026-09-04, against `mcp==1.29.1`:

```text
deprecated in the specification since 2026-07-28 (SEP-2577):
  feature    type exists  marked deprecated    warns when used
  Roots      yes          no                   no
  Sampling   yes          no                   no
  Logging    yes          no                   no
```

And against `mcp==2.1.1`:

```text
deprecated in the specification since 2026-07-28 (SEP-2577):
  feature    type exists  marked deprecated    warns when used
  Roots      yes          yes (docstring)      no
  Sampling   yes          yes (docstring)      no
  Logging    yes          no                   no
```

Three columns, and the important one is the last. **Nine cells, and not one of them says a warning was
raised.** A test suite run with `-W error::DeprecationWarning` is green against code using all three
features, on both SDKs.

The middle column is more interesting than a yes/no suggests. On 2.1.1 the marker is a **docstring
sentence**, not `@deprecated`, so no editor strikes anything through and no type checker complains.
Here is what is actually there:

```text
    A standalone JSON-RPC request through 2025-11-25; on 2026-07-28 it is
    embedded in `InputRequiredResult.input_requests`. Deprecated in 2026-07-28 (SEP-2577).
```

That sentence is genuinely useful — it names the revision, the proposal and the replacement, which is
more than the registry row gives you in one place. It is also invisible to every tool you own, and you
will only read it if you were already looking.

And the `Logging` row says `no` even on 2.1.1, which is the detail worth chasing. Its docstring is not
missing; it says something different:

```text
    A request from the client to the server, to enable or adjust logging.

    Removed in protocol 2026-07-28; sent/received on sessions negotiating <= 2025-11-25.
    On 2026-07-28 the client opts in per-request via `_meta` (`LOG_LEVEL_META_KEY`).
```

It says **removed**, not deprecated, and it is right —
[4.2](../04-the-leaving-list/4.2-three-things-being-taken-away.md) drew this line: the *feature*
Logging is Deprecated in the registry, while the *method* `logging/setLevel` was removed outright in
the same revision. `SetLevelRequest` is the method, so the SDK is describing the method's fate
accurately, and the probe's word-search for "deprecat" misses it. That is a limitation of the probe
and a genuine lesson about the material: a registry row and a type are not the same unit, and mapping
one onto the other is a judgement the scanner in
[4.3](../04-the-leaving-list/4.3-dating-somebody-elses-server.md) makes explicitly, in
`FINGERPRINTS`, because nothing does it for you.

## When it breaks

The failure has no error text, and that is precisely the report. The nine cells above are the whole
of it: three features, two SDKs, `warns when used` reading `no` every time.

The practical consequence is the check that certifies nothing. Promote every deprecation warning to
an error with `uv run python -m pytest -q -W error::DeprecationWarning` and a suite exercising all
three features passes, because there is nothing to promote. The measurement above is the reason: not
one construction raised a warning, so no warning filter can turn one into a failure.

The second break is the one that follows from believing that. A team writes a new server, reaches for
`SetLevelRequest` because it is exported and unmarked, ships it, and has built new code on a method
that was removed from the protocol in the revision they are targeting. The SDK will keep accepting it
for as long as it supports the older revisions, so the failure does not arrive at build time — it
arrives when a peer refuses:

```text
{"jsonrpc": "2.0", "id": 4, "error": {"code": -32601, "message": "Method not found", "data": {"method": "logging/setLevel"}}}
```

The third break is subtler and is a trap in the *measurement*. Run a check for
`DeprecationWarning` without overriding the warning filters and you will see nothing even from a
library that does raise them properly, because Python suppresses `DeprecationWarning` by default
outside `__main__`. So "we checked and there were no warnings" can be false for two entirely different
reasons, and the person saying it usually cannot tell you which.

## In production

**What a professional writes instead:** a check that compares the code against the **registry**, not
against the library. Concretely: the list of deprecated features and their wire names lives in the
repository with a fetch date, a scheduled job re-fetches the published page and diffs it, and a lint
step fails if any of those names appear in first-party code. That is exactly the shape of
`deprecation_scan.py`, pointed inward instead of outward, and it is what
[Day 45](../../../day-45-the-mcp-audit/LESSON.md)'s audit should carry.

**What degrades at scale:** the false sense of coverage. In a large codebase there *are* real
`DeprecationWarning`s — from the standard library, from other packages — so the log is not empty, and
a team that filters them to keep the build readable is now guaranteed not to see a new one. The
warnings that get read are the ones that are rare, which means the mechanism works least well exactly
where it is needed most.

**The failure mode that only appears with real traffic:** the specification moving under a library
that does not. An SDK supports several protocol revisions at once, so it must keep the types for all
of them, which means it cannot mark them deprecated without annoying every user still on the older
revision. That is a reasonable position, and its consequence is that **an SDK's API surface can never
be a reliable indicator of a specification's current state.** Anybody using it as one is making a
category error, and the more revisions the SDK supports, the wronger they are.

**The review comment a senior engineer leaves:** *"'no deprecation warnings' does not mean 'no
deprecated features'. The SDK exports all three of the SEP-2577 features unmarked and warns about none
of them — we measured it. Check the names against the deprecated registry with the date you read it,
and put that check in CI rather than in a paragraph."*

**The interview question:** *"how do you know whether your code uses a deprecated protocol feature?"*
The answer that shows you have actually looked: *"not by asking the library. We probed it: MCP
deprecated Roots, Sampling and Logging in the 2026-07-28 revision, and on the SDK we have pinned all
three types are exported with no marker and constructing them raises no warning. On the current
release two of the three mention it in a docstring — not `@deprecated`, a docstring, so no editor or
type checker sees it — and still nothing warns. So the check has to compare against the specification's
deprecated-features registry, which is a published page, and it has to live in CI with the date it was
read. The trap is the reasoning 'we ran with `-W error::DeprecationWarning` and it was clean', which is
true and means nothing — and it is doubly misleading because Python hides `DeprecationWarning` by
default anyway, so people often are not even measuring the thing they think they are."*
