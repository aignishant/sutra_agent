# 6.3 — The bill for a bump nobody has authorised

## One-line answer

`mcp` is pinned at `1.29.1` and speaks protocol `2025-11-25`; the release is `2.1.1` and speaks
`2026-07-28`; and the difference is not a number in `pyproject.toml` but a named, countable list of
imports across this repository — which is why Principle 14 says you price it and amend the plan
before you change the pin.

## The story

The gas connection is being changed and the man comes to look first.

He does not start by disconnecting anything. He looks at the stove and says the new regulator has a
different thread, so the stove's hose needs replacing. He looks behind the geyser and says that one is
fine, same fitting. Then he asks whether the neighbour's line runs off the same point, because it
does, and that means it is not one flat's job.

Fifteen minutes, and he leaves with a list: two things that change, one that does not, and one
conversation you are going to have to have with the flat upstairs. He has not touched a spanner.

The list is the work. Anyone can turn the valve; knowing what is downstream of it before you turn it
is why he came.

## The idea in plain language

Day 32 found the gap and wrote it down: this repository's pinned `mcp==1.29.1` reports
`LATEST_PROTOCOL_VERSION = '2025-11-25'`, while the specification is at `2026-07-28` and PyPI's
current `mcp` is `2.1.1`. It recorded that and changed nothing, because a version bump is a plan
decision.

That is Principle 14 — *if reality changes, the plan is amended first* — and this part is what
"amended first" means in practice. It is not a delay. It is a survey: produce a list of exactly what
breaks, so that whoever authorises the bump is authorising something with a size.

Three things have to be separated, because they move independently and people collapse them:

| | What it is | Where it is recorded |
| --- | --- | --- |
| **The specification revision** | `2026-07-28`, the protocol on the wire | `modelcontextprotocol.io/specification/versioning` |
| **The SDK version** | `1.29.1` here, `2.1.1` published | `pyproject.toml`, `docs/PACKAGES.md` |
| **The revisions that SDK speaks** | `2025-11-25` and older, here | only by asking the package |

A bump changes the second, and the reason you would want to is the third. The first has already
changed and is not waiting for you.

The survey is a diff between two symbol tables. Nothing more sophisticated is needed, and nothing
less is honest.

## Why Sutra needs it

Phase 5 is fourteen days of protocol built against revision `2026-07-28`, on an SDK that does not
speak it. Everything written so far is still correct, because days 32 to 38 read the wire rather than
depending on the SDK's newest features — but that is a property of how the days were written, not a
guarantee that holds forward.

[Day 43](../../../day-43-stateless-by-default/LESSON.md) makes `sutra_mcp` deploy-shaped and
[Day 45](../../../day-45-the-mcp-audit/LESSON.md) audits the phase. Somewhere in there, somebody has
to decide about this pin, and the decision needs a `docs/PACKAGES.md` row and a
`docs/CHANGELOG_PLAN.md` entry behind it. This part produces the evidence that decision needs.

**Nothing is bumped today.** `git diff pyproject.toml uv.lock` is empty when you finish this day, and
that is a checklist item.

## The mechanism

> 🎬 **The scene:** the SDK is a major version behind and speaks the wrong protocol revision.
> Somebody, reasonably, opens `pyproject.toml`.
>
> 😬 **The naive fix:** change `mcp==1.29.1` to `mcp==2.1.1`, run `uv sync`, and see what the test
> suite says. It is the fastest way to find out.
>
> 💥 **Why it fails:** it is fast for the person doing it and slow for everyone else. The lockfile is
> now different, the branch does not build for anyone who has not re-synced, the failures arrive as
> a wall of unrelated tracebacks, and the question "is this bump worth doing now?" has been answered
> by doing it. If the answer turns out to be no, backing out is a revert of a lockfile plus whatever
> was half-migrated.
>
> 💡 **The insight:** you can measure the whole bump without making it. Run the same probe under both
> SDKs in a throwaway environment, diff the outputs, and grep the repository for the names that
> moved. The result is a list, and a list can be argued with.

Two runs of one script, and neither touches the project's environment:

```bash
cd days/day-38-failure-and-migration-lab/lab
uv run python bump_probe.py
uv run --isolated --no-project --with "mcp==2.1.1" python bump_probe.py
```

**Line by line:**

- The first run uses the project's own environment, so it reports what `uv sync` actually installed
  rather than what `pyproject.toml` claims — those can differ and only one of them is the truth.
- The second builds a throwaway environment for the duration of one command, as
  [6.1](6.1-two-ways-a-removal-meets-you.md) established. `--isolated` ignores the project
  environment; `--no-project` stops `uv` reading `pyproject.toml`, so the pin cannot influence the
  resolution and the lockfile cannot be rewritten.
- **Zero model calls, and `git status` is unchanged afterwards.**

```text
  mcp.types.version          -> present
  mcp.server.fastmcp         -> ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x, where FastMCP w
  mcp.server.mcpserver       -> present

  mcp.types.InitializeRequest      present
  mcp.types.InputRequiredResult    present
  mcp.types.ListRootsRequest       present

```

Read the two together and the bill is four lines long.

| What changes | 1.29.1 | 2.1.1 | Cost |
| --- | --- | --- | --- |
| `mcp.shared.version` | present | gone, no signpost | rewrite the import as `mcp.types.version` |
| `mcp.server.fastmcp` / `FastMCP` | present | raises, with the new name in the message | rename to `MCPServer` from `mcp.server.mcpserver`, plus "other APIs changed" |
| `mcp.types.InputRequiredResult` | absent | present | nothing breaks; a capability arrives |
| Protocol revisions | up to `2025-11-25` | adds `2026-07-28`, and names it *modern* | the reason to do it at all |

`MODERN_PROTOCOL_VERSIONS` is worth pausing on. 2.1.1 does not merely add a revision to a list; it
puts `2026-07-28` in a category of its own, because that is the revision with the stateless
per-request envelope and the handshake ones are a different shape. The SDK has adopted the same split
this phase teaches.

Now find who pays. The probe says which names moved; a grep says where they are used:

```bash
cd "$(git rev-parse --show-toplevel)"
grep -rn "mcp.shared.version\|mcp.server.fastmcp\|FastMCP" --include=*.py --include=*.md days/ sutra/ sutra_mcp/ tests/ | grep -v "day-38-failure" | cut -d: -f1 | sort | uniq -c | sort -rn
```

**Line by line:**

- `git rev-parse --show-toplevel` finds the repository root, so the command works from anywhere and
  does not depend on where you happen to be standing.
- The three names come straight out of the diff above. They are the only ones that moved; the probe
  is what makes this list short and trustworthy rather than a guess.
- `--include=*.py --include=*.md` searches both the code and **the teaching**, because a day document
  containing a code block that no longer runs is as broken as a module — and on this project the
  documents are the deliverable.
- `grep -v "day-38-failure"` excludes this day, which mentions all three names on purpose and would
  otherwise dominate the count.
- `cut -d: -f1 | sort | uniq -c | sort -rn` collapses the hits to a count per file, most-affected
  first. The individual line numbers matter when you do the work; the file counts are what you take
  to the decision.
- Read-only. **Zero model calls, nothing written.**

What it finds today is the shape of the answer rather than a fixed number, because Phase 5 is still
being written: `days/day-32-mcp-stateless-core/lab/sdk_era.py` imports
`from mcp.shared.version import SUPPORTED_PROTOCOL_VERSIONS`, its part 5.1 prints the same import in a
code block, and Day 34's server work is built on `FastMCP` throughout — including the `build_server()`
that days 35 to 43 all extend. Day 33's client code is untouched: `from mcp import StdioServerParameters`,
`mcp.client.stdio.stdio_client` and `mcp.client.sse` all still import cleanly under 2.1.1.

So the bill has a shape worth stating plainly, and it is not the shape people expect. **The client
side survives the bump. The server side is a rename that propagates through every day that touches
`sutra_mcp/server.py`.** That is a fact about which parts of a codebase sit closest to a library's
public surface, and it is the sort of thing you want on a page before you turn the valve.

And the last line of the bill is the one that is not a cost: nothing about the specification requires
this bump *today*. The pinned SDK speaks a revision that servers still accept, because the current
revision's backward-compatibility rules exist for exactly this. The bump buys the ability to speak
`2026-07-28` natively — which
[Day 43](../../../day-43-stateless-by-default/LESSON.md) will want and Day 38 does not.

## When it breaks

The thing that breaks is the process, not the code, and it breaks in the direction of doing the bump
casually.

If somebody edits `pyproject.toml` and runs `uv sync`, the first failure they see is this, and it is
the bare one from [6.1](6.1-two-ways-a-removal-meets-you.md):

```text
ModuleNotFoundError: No module named 'mcp.shared.version'
```

which is a five-minute detour into whether the install is broken. The second is better, because
somebody wrote it:

```text
ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x, where FastMCP was renamed to MCPServer (from mcp.server.mcpserver import MCPServer) and other APIs changed; see the migration guide at https://py.sdk.modelcontextprotocol.io/v2/migration/#fastmcp-renamed-to-mcpserver or pin 'mcp<2' to keep running v1 code.
```

Note the last clause of that message: *"or pin `mcp<2` to keep running v1 code."* The library's own
authors are telling you that not upgrading is a supported position. That is the sentence a survey
exists to let you take seriously.

The phrase to worry about is the one in the middle — *"and other APIs changed"*. The probe measured
five symbols and four modules, which is not the whole surface. A survey that reports "four things
change" when the migration guide says more changed has under-counted, and the honest way to say so is
in the survey itself: this is a lower bound.

```text
TODO(verify: read https://py.sdk.modelcontextprotocol.io/v2/migration/ in full and extend
bump_probe.py's SYMBOLS list with every renamed symbol it names, then re-run both arms)
```

That is left as a `TODO` rather than guessed at, because the alternative is a confident list that is
wrong — and a wrong survey is worse than none, since somebody will plan against it.

## In production

**What a professional writes instead:** a **migration spike** with a time-boxed scope and a written
output — a branch that is never merged, or a probe like this one that is. Its deliverable is the list,
not the upgrade. The decision to bump then happens in a review, with the list attached, and the ledger
rows (`docs/PACKAGES.md` for the pin, `docs/CHANGELOG_PLAN.md` for the amendment) are written as part
of the decision rather than after it.

The probe itself is the reusable half. A script that prints an SDK's public surface and can be run
against any version is worth keeping in `tools/`, because every future bump asks the same question.

**What degrades at scale:** the number of services on the pin. One repository is a survey; forty are a
coordination problem where each team discovers the same four breaks independently. The pattern that
works is one team producing the list once and publishing it, which is what a good migration guide is —
and note that the SDK's authors already did exactly this, and put a link to it inside an exception.

**The failure mode that only appears with real traffic:** the partial fleet. Bump some services and
not others and you now run two SDK versions against one protocol, negotiating different revisions with
the same servers. A bug that reproduces against one service and not another, with the same request, is
an era difference until proven otherwise — which is Day 32's
[5.1](../../../day-32-mcp-stateless-core/parts/05-failure-lab/5.1-the-tutorial-from-four-months-ago.md)
warning, arriving with a fleet attached.

**The review comment a senior engineer leaves:** *"this pull request bumps `mcp` to 2.1.1 and fixes
the two imports that broke. Where is the list? The migration guide says 'other APIs changed' and we
have measured five symbols. Run the probe against both versions, paste both outputs, and tell me what
we get for it — the only thing on the list I can see as a benefit is `2026-07-28` support, and nothing
we ship this quarter needs it."*

**The interview question:** *"how do you decide when to take a major version bump?"* The answer that
sounds like somebody who has been burned: *"I measure it before I take it. For our MCP SDK the pin was
`1.29.1` speaking protocol `2025-11-25` and the release was `2.1.1` speaking `2026-07-28`. Rather than
editing the pin, I ran the same introspection script under both — `uv run --isolated --with` builds a
throwaway environment, so the lockfile never moves — and diffed the symbol tables. Four things changed:
`mcp.shared.version` moved to `mcp.types.version` with no signpost, `FastMCP` became `MCPServer` with a
very good one, `InputRequiredResult` appeared, and the protocol list gained the new revision. Then I
grepped for those names and found the client code untouched and the server code affected everywhere.
That is a page, it took an afternoon, and it turned 'should we upgrade?' from an opinion into a
decision with a size — and the answer was 'not yet, and here is the date we will need to'."*
