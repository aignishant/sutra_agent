# 6.4 — The test that must be able to go red

## One-line answer

Everything in this day is a rehearsal until it is a test: `tests/test_mcp_failures.py` drives Sutra's
client against a server that hangs and a server that lies, and it is only worth having if you have
watched it fail before you watched it pass.

## The story

The neighbour has your spare key.

She has had it for years. It is in a drawer with the string and the batteries, and everybody involved
is quite sure it works, because it is a key and keys work.

The one time you actually needed it — bag in the taxi, phone at four percent — she brought it down
and it did not turn. The lock had been changed after the break-in two doors along. Nobody was
careless. The key sat in a drawer being a key, and the door quietly stopped being the door it opened.

The man on the ground floor does something that looks slightly odd. Once a year, standing at his own
front door with his own key in his pocket, he goes and gets the spare from his neighbour and opens
his door with it. Takes a moment. He is not locked out and he is not worried.

He is the only person on the street who knows his spare key works.

## The idea in plain language

Principle 11 in this project says **evals are tests**, and its sharper half is the one that matters
here: a test that has never been red does not test anything you can name.

A test asserts that a thing behaves a certain way. Its value is not in it passing — an empty test
passes, and a test asserting `True` passes forever. Its value is in the fact that if the behaviour
changed, it would **stop** passing. That property has to be demonstrated, not assumed, and the only
way to demonstrate it is to break the code on purpose and watch the test go red.

For this day, the behaviours to assert are the ones you have already measured by hand:

| From | The assertion |
| --- | --- |
| [1.1](../01-the-clock/1.1-the-only-clock-is-yours.md) | a call against a hanging server raises within the deadline, rather than blocking |
| [2.1](../02-the-x-ray/2.1-five-questions-before-you-believe.md) | each of the five crimes raises, and the message names which check failed |
| [2.4](../02-the-x-ray/2.4-the-reply-that-arrived-twice.md) | a duplicated reply does not produce an answer to the previous question |
| [3.1](../03-the-quiet-ones/3.1-the-answer-about-the-wrong-ticket.md) | a well-formed reply about a different subject is rejected |

Every one of those needs a **fixture** — a fake server that misbehaves on demand. Which is exactly
what `lab/` already holds: `slow_server.py`, `crooked_server.py` and `echo_twice.py` are three
misbehaving servers you have already run. Turning a day's lab into a test suite's fixtures is the move
that makes a failure lab permanent instead of an afternoon.

One term, because it decides where the file goes. A **fixture** in pytest is a named piece of setup
that a test asks for by putting its name in the signature. It is how a test says "give me a server
that hangs" without knowing how one is made.

## Why Sutra needs it

`./m check` exists as of Day 31 and runs `pytest -q -m "not live"` among other things. Today's day
adds a file to that run, and `tests/` currently holds `test_persona.py`, `test_skill_couplings.py` and
`test_skills.py`, plus Day 29's fixtures — nothing that exercises `sutra/mcp/client.py` against a
server that is anything other than well-behaved.

That is the gap. Day 33 built the client, days 34 to 37 built the server it talks to, and every test so
far runs against a server that works. The first misbehaving server Sutra meets will be somebody else's,
in production.

[Day 44](../../../day-44-client-hardening/LESSON.md) writes `sutra/mcp/hardening.py` —
`with_retries`, `with_timeout`, and the rule that no connection is held. **This file is what makes
that day reviewable.** Without it, Day 44 adds functions and nobody can say what they fixed; with it,
Day 44 turns a red test green, which is the only definition of "fixed" that survives a code review.

Which means today's file is expected to be **partly red**, and that is the design rather than an
accident. Some of these assertions describe behaviour the client does not have yet.

## The mechanism

> 🎬 **The scene:** you have spent a day breaking things by hand. The deadline fired at 2.01 seconds,
> five crimes were named at the boundary, a duplicated reply desynchronised a stream. You close the
> terminal.
>
> 😬 **The naive fix:** write it up. A section in the design document listing the failure modes and
> what the client should do about each, so the knowledge is not lost.
>
> 💥 **Why it fails:** a document does not run. In four months somebody will refactor the client's
> reader, the id check will be dropped as redundant, every existing test will pass, and the document
> will be exactly as correct and exactly as ineffective as it was the day it was written.
>
> 💡 **The insight:** a failure you have reproduced is worth a test; a failure you have described is
> worth a paragraph. Move each of today's measurements into `tests/` while the fixture that produced
> it is still on disk.

The brief is a file, and it is yours to write — the shape below is the contract, and the bodies are
`TODO(me)`:

```python
# tests/test_mcp_failures.py  -  yours to write today
"""Drive Sutra's MCP client against servers that hang, lie and repeat themselves."""

import pytest

LAB = "days/day-38-failure-and-migration-lab/lab"


@pytest.fixture
def hanging_server() -> ...:
    """Launch `slow_server.py hang` and yield something the client can connect to."""
    raise NotImplementedError("TODO(me)")


@pytest.fixture
def crooked_server() -> ...:
    """Launch `crooked_server.py`, which answers with five crimes in rotation."""
    raise NotImplementedError("TODO(me)")


def test_deadline_fires_against_a_hanging_server(hanging_server) -> None:
    """A call with a deadline raises rather than blocking. This is 1.1, asserted."""
    raise NotImplementedError("TODO(me)")


@pytest.mark.parametrize("crime", range(5))
def test_each_crime_is_named_at_the_boundary(crooked_server, crime: int) -> None:
    """Five crimes, five distinct messages. This is 2.1, asserted."""
    raise NotImplementedError("TODO(me)")


def test_a_reply_about_another_subject_is_rejected() -> None:
    """The echo check. This is 3.1, asserted, and needs no server at all."""
    raise NotImplementedError("TODO(me)")
```

**Line by line:**

- The module docstring says what the file is for in one sentence, because a test file's name says
  what it covers and only its docstring can say what it *means* by covering it.
- `LAB` is a constant pointing at this day's folder. That is a real decision with a cost: the tests
  now depend on a day's directory, so renaming the day folder breaks them. The alternative is copying
  the three fake servers into `tests/fixtures/`, which is what Day 29 did with its poisoned-skill
  fixtures. **Choose deliberately** — the `TODO(me)` in the hub asks you to, and there is a defensible
  answer either way.
- `@pytest.fixture` on `hanging_server` because launching a subprocess is setup, not assertion. A test
  that starts its own server has two reasons to fail and tells you neither.
- The return annotation is `...` on purpose. What the fixture yields depends on how you decide the
  client is driven — a `subprocess.Popen`, a connected client object, a set of connection parameters —
  and that decision belongs to whoever writes it, not to this document.
- `raise NotImplementedError("TODO(me)")` rather than `pass`. A body of `pass` makes the test **pass**,
  which is the exact failure this part is about: a green suite that asserts nothing. Raising means the
  file is red the moment it is created, which is honest and is Principle 11 applied to the act of
  writing a test.
- `@pytest.mark.parametrize("crime", range(5))` produces five separately-named test cases rather than
  one test with a loop. When crime 3 breaks, you want the failure to say crime 3, not to say that a
  loop failed somewhere.
- `test_a_reply_about_another_subject_is_rejected` takes **no fixture**, because the echo check needs
  no server at all — a string constant is enough, as
  [3.1](../03-the-quiet-ones/3.1-the-answer-about-the-wrong-ticket.md) showed. The cheapest tests in
  this file are the ones about correctness rather than about timing, and they are also the fastest and
  the least flaky. Write those first.
- **No test here calls a model.** Every assertion in this file is about a protocol, and a protocol is
  deterministic. This is the day's request budget being kept by the tests as well as by the parts.

Two names are deliberately absent from the brief and worth saying why. There is no
`test_timeout_does_not_cancel_the_work`, because
[1.2](../01-the-clock/1.2-giving-up-ends-the-wait.md)'s finding is about the *server's* behaviour and
is not something the client can assert. And there is no test for
[3.2](../03-the-quiet-ones/3.2-the-ticket-closed-twice.md)'s idempotency, because Sutra has no write
tool with a key yet — that test belongs to the day that adds one.

Now the part that makes the file worth having. Run it, then break the thing it tests:

```bash
uv run python -m pytest tests/test_mcp_failures.py -q
```

**Line by line:**

- One file, quietly. `-q` because the interesting output is the failure list, not the progress dots.
- Run it **before** you implement anything and every test is red on `NotImplementedError`, which tells
  you the file is wired up and nothing more.
- Run it after you implement the assertions and some go green. **The ones that stay red are the
  specification for [Day 44](../../../day-44-client-hardening/LESSON.md)** — write them down.
- Then, for each test that went green, break the code it covers on purpose and confirm it goes red
  again. A test you have not seen fail is a spare key in a drawer.
- **Zero model calls.**

## When it breaks

The most common way this file goes wrong is that it hangs. A test that connects to
`slow_server.py hang` and forgets its own deadline does not fail — it stops, and it takes the whole
suite with it. The symptom in CI is a job that runs until the platform's limit and is then killed with
no useful output at all.

The guard is a deadline on the test itself, and pytest will not give you one by default. Either the
client under test genuinely has a timeout — which is the thing being asserted, so relying on it is
circular — or the test brings its own, exactly as
[1.1](../01-the-clock/1.1-the-only-clock-is-yours.md)'s client did with a thread and a `join`.

The second is the subprocess that survives. A fixture that launches a server and does not kill it on
teardown leaves processes behind, and after enough runs the machine has a hundred Python processes
sleeping for an hour each. Where those servers bound a fixed port, the message the operating system
gives you is this one:

```text
OSError: [WinError 10048] Only one usage of each socket address (protocol/network address/port) is normally permitted
```

That message is about ports and the cause is leaked processes from earlier runs. It is also the
reason [1.3](../01-the-clock/1.3-hanging-up-is-the-message.md)'s server binds to port `0` and lets the
operating system choose. The fixture must
clean up in a `finally` or with a `yield` fixture, on the failure path as well as the success path.

The third is a flaky timing assertion, and this one you can reason about from a number you measured
rather than take on trust. [1.1](../01-the-clock/1.1-the-only-clock-is-yours.md)'s elapsed time was
`2.01s` against a `2.0s` deadline, on an idle machine with nothing else running. Assert
`elapsed < 2.1` and a loaded build machine will one day take longer than that and fail the test on a
client that is behaving perfectly.

Assert the **property**, not the number: that the call raised, and that it raised in materially less
time than the server's work would have taken. A wide margin is not sloppiness here; it is the
difference between testing your code and testing the build machine.

## In production

**What a professional writes instead:** a small library of misbehaving servers, kept beside the tests
rather than inside a lesson, and reused by every test that needs a bad peer. Each one does exactly one
wrong thing and is named for it. That collection grows every time an incident reveals a new way for a
peer to misbehave, which is the discipline that turns outages into regression tests — the incident
review's output is a fixture, not a paragraph.

**What degrades at scale:** wall-clock time. Failure tests are slow by nature, because most of them
are about waiting. A suite with thirty timing tests at two seconds each is a minute of CI that
everybody eventually skips. The answer is to make the deadlines injectable, so the test can use
milliseconds where production uses seconds, and to keep the genuinely slow ones behind a marker — this
project already has `-m "not live"` for exactly that kind of split.

**The failure mode that only appears with real traffic:** the failure nobody wrote a fixture for. A
suite of failure tests is a list of the failures you have imagined, and production's imagination is
better than yours. This is not an argument against the suite; it is an argument for adding to it from
incidents rather than only from design, and for the client's default disposition on an unrecognised
failure being quarantine rather than retry
([2.2](../02-the-x-ray/2.2-malformed-is-not-transient.md)).

**The review comment a senior engineer leaves:** *"these all pass. Show me each one failing — break the
id check and show me `test_each_crime_is_named_at_the_boundary[2]` going red. If you cannot make a
test fail, I do not know what it is asserting."*

**The interview question:** *"how do you test that your client survives a bad server?"* The answer with
fixtures in it: *"with servers that are bad on purpose. We keep small fake peers next to the tests —
one that never answers, one that returns five specific malformed replies in rotation, one that writes
every reply twice — and drive the real client against them. The rule I hold to is that every one of
those tests has to have been red at some point, on purpose: break the id check and watch the crime-3
case fail. Two practical traps. The hanging-server test needs its own deadline or it takes the suite
down instead of failing, and timing assertions have to test the property rather than the number,
because a loaded CI machine will beat any tight bound you write. And the last thing is that some of
those tests stay red on purpose — they are the specification for the hardening work that comes next."*

## Check yourself

```bash
uv run python -m pytest tests/test_mcp_failures.py -q
```

Once the assertions are written and some are green, break one thing in the client on purpose — delete
the id comparison — and run it again. Write down which tests went red. If deleting a check turns
nothing red, the check has no test.

**Out loud, without scrolling up:** say why a test body of `pass` is worse than one that raises
`NotImplementedError`, and say what a test that has never been red actually proves.
