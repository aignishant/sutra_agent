# 4.3 — Dating somebody else's server

## One-line answer

A server tells you its age without being asked: the capabilities and methods it advertises map
one-to-one onto rows of the deprecated registry, so a scan over one `server/discover` reply produces
a dated list of what that server is still running and what it must eventually move to.

## The story

The mechanic does not ask how old the car is.

He asks you to open the bonnet, and then he spends four minutes not looking at the engine so much as
looking at the *parts*. The battery has a sticker with a date on it. The belt is the original, and he
can tell because of the moulding on the side. There is a bracket that was only fitted before a certain
year. The oil filter is a size that was discontinued.

Then he tells you roughly when the car was last properly serviced, which of those parts will need
doing and in what order, and he is right, and you never told him anything.

He is not guessing from the mileage. He is reading a list of components against a list of dates that
he has in his head, and the reason he can do it in four minutes is that it is a lookup rather than a
judgement. Anyone with the same list could do it. Most people do not have the list.

## The idea in plain language

A **fingerprint** here is a name that only appears in servers of a certain age. `sampling/createMessage`
in a method list, or a `roots` key in a capability block, is a fingerprint: it does not prove the
server is old, but it proves the server still carries something the specification has scheduled for
removal.

Day 32's
[2.4](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.4-server-discover-the-optional-question.md)
established the source of the material. `server/discover` is a single request that a server **MUST**
implement and a client **MAY** call, and it returns the server's supported protocol versions, its
capabilities, and its identity — all in one reply, without a handshake and without anything being
remembered afterwards.

So the whole audit is: take that reply, flatten out every capability key and method name it
advertises, and look each one up in the registry from
[4.1](4.1-a-feature-with-a-leaving-date.md). Anything that matches is a row, and a row comes with a
migration path and a date already attached.

Two properties make this worth automating rather than eyeballing.

**It is a lookup, not an opinion.** Every judgement is in the registry, which is copied from a
published page. The scan contributes no interpretation of its own, so two people running it get the
same answer, and a disagreement is a disagreement about the registry rather than about the server.

**It has an exit code.** A script that returns non-zero when it finds something can sit in a review
gate. A paragraph in an onboarding document cannot. This is the same move Day 28's routing gate and
Day 32's server intake made: the difference between a check somebody remembers to do and a check that
runs.

## Why Sutra needs it

Day 32's
[6.2](../../../day-32-mcp-stateless-core/parts/06-in-production/6.2-before-you-depend-on-a-server.md)
built the intake list — six questions to ask before depending on a server, with an exit code. It asks
about identity, provenance and namespace. It does not ask about age, because when it was written this
day had not happened yet.

This is the missing column. Sutra will meet third-party servers on
[Day 40](../../../day-40-filtering-and-allowlists/LESSON.md), and
[Day 45](../../../day-45-the-mcp-audit/LESSON.md) audits everything Phase 5 and 6 produced. Both need
a mechanical answer to *"is anything in this server on the way out, and by when?"*, and both benefit
from that answer being a file rather than a memory.

It also decides something practical about `sutra/mcp/client.py`. A server that advertises `sampling`
is asking to spend Sutra's model quota ([4.2](4.2-three-things-being-taken-away.md)), and Sutra's
whole budget is about twenty generations a day. Finding that out at intake is a decision; finding it
out from a quota alert is an incident.

## The mechanism

> 🎬 **The scene:** a partner sends you the address of their MCP server and a one-line note saying it
> supports MCP. You are about to wire it into Sutra's toolset.
>
> 😬 **The naive fix:** connect and see if `tools/list` works. It does, so you ship.
>
> 💥 **Why it fails:** "supports MCP" is not a fact, it is a family of facts with dates. Their server
> may be running three features that are on a published leaving list, and you will discover that when
> one of them is removed and their integration breaks inside your product.
>
> 💡 **The insight:** ask once, at the beginning, and compare against a list rather than an
> impression. The reply to `server/discover` already contains everything you need.

The input is one saved reply. This is a realistic one — a helpdesk server, a couple of years old,
maintained but not modernised:

```json
{
  "serverInfo": { "name": "com.example/helpdesk", "version": "3.2.0" },
  "protocolVersions": ["2025-11-25", "2026-07-28"],
  "capabilities": {
    "server": { "tools": {}, "resources": {}, "logging": {} },
    "client": { "roots": { "listChanged": true }, "sampling": {} }
  },
  "methods": ["tools/list", "tools/call", "logging/setLevel", "sampling/createMessage"]
}
```

Three things in there are worth reading before any code touches it. The server declares **both**
protocol revisions, which is legal and common — clients and servers may support several at once. Its
`capabilities.client` block says which *client* features it expects to use, and it names `roots` and
`sampling`, which is the server telling you what it intends to ask of you. And `methods` still lists
`logging/setLevel`, which was removed outright in the 2026-07-28 revision.

The scan itself:

```python
# days/day-38-failure-and-migration-lab/lab/deprecation_scan.py
from lifecycle import REGISTRY

FINGERPRINTS = {
    "roots": "Roots",
    "roots/list": "Roots",
    "notifications/roots/list_changed": "Roots",
    "sampling": "Sampling",
    "sampling/createMessage": "Sampling",
    "logging": "Logging",
    "logging/setLevel": "Logging",
    "notifications/message": "Logging",
}

BY_NAME = {feature.name: feature for feature in REGISTRY}


def declared(discover: dict) -> list[str]:
    """Every capability key and method name the reply advertises, flattened."""
    found = list(discover.get("capabilities", {}).get("client", {}))
    found += list(discover.get("capabilities", {}).get("server", {}))
    found += discover.get("methods", [])
    return found
```

**Line by line:**

- `from lifecycle import REGISTRY` rather than a second copy of the table. There is exactly one place
  in this day where the migration text and the dates live, and it is the file whose docstring names
  the page they were copied from. A scanner with its own inline copy of the facts is a scanner that
  will disagree with the registry in six months.
- `FINGERPRINTS` maps **wire-visible names** to registry rows, and it is many-to-one on purpose. One
  feature shows up under several names — `roots` as a capability key, `roots/list` as a method,
  `notifications/roots/list_changed` as a notification — and all three mean the same row. Writing it
  as a flat dictionary keeps the lookup a single `in` test rather than three separate rules.
- `notifications/message` maps to Logging even though `logging/setLevel` is the removed method. That
  is the distinction [4.2](4.2-three-things-being-taken-away.md) drew: the *feature* Logging is
  Deprecated, and it has two wire faces, one of which is already gone. A scanner that only looked for
  `logging/setLevel` would miss a server that pushes log notifications without offering to set a
  level.
- `BY_NAME` inverts the registry list into a dictionary keyed by feature name, so a fingerprint hit
  resolves to a full row — SEP, deprecation date, migration text, earliest removal — with no second
  lookup and no chance of the two drifting.
- `declared` reads **three** places, and the order matters less than the completeness. `capabilities.client`
  is what the server intends to ask of you; `capabilities.server` is what it offers; `methods` is what
  it will answer. A feature can be advertised in one and not the others, and a scan that reads only
  the method list misses the capability blocks entirely — which is precisely where `roots` and
  `sampling` appear in the fixture above.
- `.get(..., {})` at every level, because a discover reply is a stranger's output and the whole of
  section 2 applies to it. A `KeyError` here would be the scanner crashing on the servers it most
  needs to describe.

And the part that makes it a gate rather than a report:

```python
def main() -> int:
    """Scan one discover reply; return 1 if anything on the registry is still declared."""
    path = sys.argv[1] if len(sys.argv) > 1 else "partner_server.json"
    discover = json.loads(open(path, encoding="utf-8").read())
    hits = {FINGERPRINTS[name] for name in declared(discover) if name in FINGERPRINTS}
    for name in sorted(hits):
        feature = BY_NAME[name]
        print(f"  DEPRECATED  {name}")
        print(f"              deprecated in {feature.deprecated_in} by {feature.sep}")
        print(f"              migrate to: {feature.migration}")
        print(f"              eligible for removal from {feature.earliest_removal}")
    return 1 if hits else 0
```

**Line by line:**

- `hits` is a **set** comprehension, so a feature declared under three different names is reported
  once. A list would print Roots three times and make a server look worse than it is, which is the
  kind of inaccuracy that gets a check ignored.
- `sorted(hits)` makes the output deterministic. A set has no order, and a report whose lines move
  between runs cannot be diffed against the last one — which is how you would notice a partner
  actually migrating something.
- Each hit prints **four** lines, not one. The name alone is a complaint; the name with the SEP, the
  date, the migration and the removal window is something a partner can act on without a conversation.
  The whole value of the registry is in those three extra lines.
- `return 1 if hits else 0` and `sys.exit(main())` at the bottom. Non-zero means "found something",
  which is the convention every gate in this repository uses and what lets it join `./m check` or a
  review checklist later.
- `main() -> int` rather than `-> None`, which is the signature the house style uses for anything
  that becomes a command.

Run it:

```bash
cd days/day-38-failure-and-migration-lab/lab
uv run python deprecation_scan.py partner_server.json; echo "exit: $?"
```

**Line by line:**

- The filename is an argument so the same scanner can be pointed at any saved discover reply,
  including one you capture from a real server.
- `echo "exit: $?"` prints the exit code, because that is the half of the output a gate uses and it is
  otherwise invisible. **Zero model calls, no network.**

Measured on 2026-09-04:

```text
scanning partner_server.json: com.example/helpdesk
  DEPRECATED  Logging
              deprecated in 2026-07-28 by SEP-2577
              migrate to: log to stderr for stdio transports; use OpenTelemetry for observability
              eligible for removal from 2027-07-28
  DEPRECATED  Roots
              deprecated in 2026-07-28 by SEP-2577
              migrate to: pass directories or files via tool parameters, resource URIs, or server configuration
              eligible for removal from 2027-07-28
  DEPRECATED  Sampling
              deprecated in 2026-07-28 by SEP-2577
              migrate to: integrate directly with LLM provider APIs
              eligible for removal from 2027-07-28

```

Three findings and a non-zero exit, from a server that works perfectly and whose owner has done
nothing wrong. That is what this output means and it is worth saying plainly: `exit: 1` is not an
accusation. It is a date, three times over, attached to an integration you were about to depend on.

## When it breaks

The scanner's own failure modes are the interesting part, because a checker that is quietly wrong is
worse than no checker.

**A server that declares nothing.** `capabilities.client` is optional, and plenty of servers omit it.
The scan then reports zero findings for a server that may well still answer `sampling/createMessage`
if you send it, because declaring a capability and honouring a method are different things. Absence of
a fingerprint is not evidence of modernity, and the honest way to close that gap is to probe: send
the method and read the error, which is [2.3](../02-the-x-ray/2.3-the-error-you-threw-away.md)'s
`-32601` used as an instrument.

**A missing file.** Point it at a path that does not exist and you get:

```text
Traceback (most recent call last):
  File "deprecation_scan.py", line 45, in main
    discover = json.loads(open(path, encoding="utf-8").read())
                          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
FileNotFoundError: [Errno 2] No such file or directory: 'partner.json'
```

Which is fine for a lab script and not fine for a gate: a gate that crashes exits non-zero for the
wrong reason and gets treated as flaky. A production version distinguishes "found problems" from
"could not run" with different exit codes.

**A stale registry.** The scan is only as current as `lifecycle.py`, whose `TODAY` and rows were
copied on a specific date. Six months from now it will confidently report a picture that has moved,
and nothing in the output will say so — which is why the file's docstring carries the URL and the read
date, and why [6.3](../06-in-production/6.3-the-bill-for-a-bump.md) argues for re-fetching on a
schedule rather than on a hunch.

## In production

**What a professional writes instead:** the scan runs against a **live** `server/discover` call rather
than a saved file, on a schedule, for every server in the allowlist, and it writes a row per server
per run so that a partner migrating away from a deprecated feature is visible as a change rather than
noticed by accident. Its output joins the provenance ledger — the same idea as
`docs/SKILL_PROVENANCE.md` from Day 29, applied to servers instead of skills.

**What degrades at scale:** the number of servers, and the fact that they change without telling you.
Ten servers is a page; a hundred is a table nobody reads unless it only shows differences. The version
that survives reports **deltas** — new deprecated features, features that disappeared, protocol
versions added or dropped — and stays silent otherwise.

**The failure mode that only appears with real traffic:** a fleet where the discover reply varies
between instances. A partner mid-rollout has some instances answering with the new capability block
and some with the old, so your scan's answer depends on which instance it reached. If the numbers
matter, sample repeatedly and record the spread, not one reply.

**The review comment a senior engineer leaves:** *"we are adding a third-party server and there is no
record of what it declares. Run the deprecation scan against its discover reply, paste the output in
the pull request, and if it comes back non-zero say what our exposure is when those features are
removed — 'they said they support MCP' is not an answer."*

**The interview question:** *"a partner says their integration supports MCP. How do you find out what
that actually means?"* This is the answer with a method in it: *"I call `server/discover` — it is one
request, servers must implement it, and it returns their supported protocol versions, their
capabilities and their identity in one reply. Then I flatten every capability key and method name and
look them up against the deprecated features registry, which since the 2026-07-28 revision is one
published page with migration paths and removal windows on it. On a real partner server that took
about a minute and came back with three: Roots, Sampling and Logging, each with a migration path and
an earliest removal a year out. It exits non-zero, so it sits in the review rather than in somebody's
memory. The caveat I would state is that a server declaring nothing is not necessarily modern — it may
just be quiet — so for anything important I also probe the methods and read the `-32601`."*
