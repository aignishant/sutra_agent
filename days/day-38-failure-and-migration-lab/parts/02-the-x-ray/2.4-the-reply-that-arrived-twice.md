# 2.4 — The reply that arrived twice

## One-line answer

A server that writes each reply twice produces nothing but valid messages, and a client that reads
one line per request is permanently one answer behind from the second request onwards — with no
exception, no warning and no way to notice except the id check.

## The story

The cloakroom at the wedding hall works by numbers.

You hand over your coat, get a paper tag with a number on it, and at the end of the night you give
the tag back and the boy behind the counter fetches the coat hanging on that hook. It is a simple
system and it has never gone wrong.

Tonight the boy is new, and at some point he calls a number twice — reads it off a tag, fetches the
coat, then reads the same tag again because it is still in his hand, and hands the next coat down the
line as well. Nobody notices, because nobody is looking at anyone else's coat.

From then on every single person gets the coat of the person in front of them. They are all real
coats. They all come off real hooks. Everybody walks out into the cold wearing something that
almost fits, and the first person to work it out is the one at the very end, who is handed nothing at
all and is told there must be some mistake.

The mistake was thirty coats ago and it was one number, read twice.

## The idea in plain language

[2.1](2.1-five-questions-before-you-believe.md) checked the shape of a message. This part is about a
failure where **every message is the right shape** and the sequence is wrong — which is why it needs
its own part, and why check 3, the id comparison, is the one that earns its keep here.

On stdio, the transport is a stream of lines. A client sends a request and reads a line. That works
because of an assumption nobody writes down: **one request, one reply line**. Break that assumption
in either direction and the stream desynchronises.

- An **extra** line — a log message, a duplicated reply — pushes every later answer one place back.
- A **missing** line pulls them forward.

The first is what a duplicated write does. And a duplicate is much easier to produce than it sounds.
A retry inside the server's own transport layer; a `write` that was not guarded when a handler was
made re-entrant; a process supervisor that starts two copies of the server on one pipe; a library
that flushes a buffer that was already flushed. None of those produce a malformed message. They
produce a correct message, twice.

The name for the resulting state is **desynchronisation**: the client's model of which reply belongs
to which request has drifted from reality, and because the drift is constant, nothing ever looks
wrong locally. Every reply parses. Every reply is a real answer to a real question. It is simply not
the question that was asked.

Two things make this the nastiest failure in section 2. It is **silent** — no exception, ever. And it
is **persistent** — once the stream has drifted by one, it stays drifted for the life of the
connection, so it is not a rare glitch but a permanent, quiet wrongness.

## Why Sutra needs it

Sutra's stdio path is not hypothetical. Day 33 wrote `connect_stdio` in `sutra/mcp/client.py`, and it
is the transport Sutra will use for every local server — including `sutra_mcp` itself, launched as a
subprocess by Day 34.

The failure mode this part teaches is the same shape as the one Day 33's
[5.1](../../../day-33-client-and-transports/parts/05-failure-lab/5.1-the-log-line-that-ate-the-reply.md)
already taught, and the difference is worth naming rather than glossing. That part was about a server
writing **non-protocol bytes** to stdout — a `print()` — and the fix was to write to stderr instead.
This part is about a server writing **perfectly good protocol bytes twice**, where there is no rule
being broken at the byte level at all, and the fix cannot be on the server, because you do not own it.

That distinction is the reason it belongs to MCP-12 rather than MCP-03. The client's defence against
"a stranger's server does something surprising" cannot depend on the stranger writing correct code.

## The mechanism

> 🎬 **The scene:** you point Sutra at a local MCP server, ask about three tickets in a row, and read
> the three answers. They are all well-formed. Two of them are about the wrong ticket.
>
> 😬 **The naive fix:** look for a bug in your own request-building code, because clearly the wrong
> ticket id is being sent. It is not; the requests are perfect.
>
> 💥 **Why it fails:** the server wrote its first reply twice. Your second `readline()` picked up the
> leftover copy, and from that point on the stream is one line ahead of you, forever. Nothing you can
> check about any individual message will reveal it.
>
> 💡 **The insight:** the only thing that catches a correctly-shaped answer to somebody else's
> question is the id. Compare it on every single read, and treat a mismatch as a message to discard
> rather than as a message to use.

The server whose only fault is a `for` loop of length two:

```python
# days/day-38-failure-and-migration-lab/lab/echo_twice.py
def main() -> None:
    """Answer each request correctly, then answer it correctly a second time."""
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        request = json.loads(line)
        reply = {
            "jsonrpc": "2.0",
            "id": request["id"],
            "result": {
                "resultType": "complete",
                "ticket": request["params"]["t"],
                "status": "open",
            },
        }
        for _ in range(2):  # the whole bug, on one line
            sys.stdout.write(json.dumps(reply) + "\n")
        sys.stdout.flush()
```

**Line by line:**

- The server reads the request properly and answers it properly. `reply["id"]` is the id it was sent
  and `reply["result"]["ticket"]` is the ticket it was asked about. There is no crime here in the
  sense of [2.1](2.1-five-questions-before-you-believe.md); every message would pass all five checks
  on its own.
- `resultType: "complete"` is present because the 2026-07-28 revision requires it on every result.
  Including it keeps the fixture legal, so the failure cannot be blamed on a shortcut in the fixture.
- `for _ in range(2)` is the entire bug and it is written as a loop rather than two `write` calls so
  that it is visible as an intent rather than as a typo. In the wild it is usually not a loop; it is
  a base class that writes and a subclass that also writes.
- `flush()` is outside the loop, so both lines leave together. That is worse for the client than
  flushing between them, because the two copies arrive as one burst and there is no timing gap that
  might have made somebody suspicious.

The client, with the check as the ablation:

```python
# days/day-38-failure-and-migration-lab/lab/twice.py
CHECK_ID = os.environ.get("CHECK_ID", "0") == "1"
QUESTIONS = ["T-4521", "T-4522", "T-4523"]

        for n, ticket in enumerate(QUESTIONS, start=1):
            request = {"jsonrpc": "2.0", "id": n, "method": "tools/call", "params": {"t": ticket}}
            proc.stdin.write(json.dumps(request) + "\n")
            proc.stdin.flush()

            reply = json.loads(proc.stdout.readline())
            if CHECK_ID and reply["id"] != n:
                print(f"asked {ticket}: DROPPED a reply for id {reply['id']}, re-reading")
                reply = json.loads(proc.stdout.readline())

            answered = reply["result"]["ticket"]
            wrong += answered != ticket
```

**Line by line:**

- `enumerate(QUESTIONS, start=1)` makes the request id and the loop counter the same number, which is
  a shortcut worth being explicit about: a real client takes ids from a counter it owns
  ([1.4](../01-the-clock/1.4-a-broken-stream-loses-the-request.md)), and the only reason to derive it
  from the loop here is so the transcript reads clearly.
- The write-then-`readline` pair is the whole of a synchronous stdio client. There is no framing to
  check, no length prefix, and no place to notice that two lines arrived where one was expected —
  Day 33's [2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md)
  is where that transport was established.
- `if CHECK_ID and reply["id"] != n` is check 3 from
  [2.1](2.1-five-questions-before-you-believe.md), applied at the one place it can help. Note what it
  does on a mismatch: it **discards and reads again**, rather than raising. That is the right response
  here because the mismatch is not a malformed message, it is a stale one, and the next line probably
  is the answer.
- It is an `if`, not a `while`, and that is a deliberate limitation you will meet in *Check yourself*.
  One `if` discards exactly one stale line and then trusts whatever comes next without asking again,
  which is enough for a server that duplicates once and not enough for a server that duplicates
  twice. The production shape is a bounded loop: drop mismatches until you find your id or until a
  limit, and raise `Malformed` at the limit rather than draining a stream forever
  ([1.1](../01-the-clock/1.1-the-only-clock-is-yours.md) is what an unbounded version becomes).
- `wrong += answered != ticket` compares the ticket in the answer with the ticket that was asked
  about, which is the same idea as
  [3.1](../03-the-quiet-ones/3.1-the-answer-about-the-wrong-ticket.md)'s echo check. Here it is a
  measuring instrument rather than a defence: the id check is the defence, and this counter exists to
  prove the id check worked.

Run both arms:

```bash
cd days/day-38-failure-and-migration-lab/lab
CHECK_ID=0 uv run python twice.py
CHECK_ID=1 uv run python twice.py
```

**Line by line:**

- `CHECK_ID=0` is the client every tutorial shows: write, read, use.
- `CHECK_ID=1` adds one comparison. **Zero model calls.**

Measured on 2026-09-04:

```text
asked T-4521: server said T-4521   OK
asked T-4522: server said T-4521   WRONG
asked T-4523: server said T-4522   WRONG
answers about the wrong ticket: 2/3
```

```text
asked T-4521: server said T-4521   OK
asked T-4522: DROPPED a reply for id 1, re-reading
asked T-4522: server said T-4522   OK
asked T-4523: DROPPED a reply for id 2, re-reading
asked T-4523: server said T-4523   OK
answers about the wrong ticket: 0/3
```

Two of three answers wrong in the first arm, and the process exited zero. There was no error, no
warning and no anomaly in any single message. Had this been a real desk, two customers would have
been told the status of somebody else's ticket, in a fluent sentence, with a ticket number in it.

Notice also that the drift is **permanent**. The third question is wrong for the same reason the
second was; adding a fourth would make it three of four. There is no self-correction, because nothing
in the loop ever compares anything.

## When it breaks

The pathological case is when the extra line is not a duplicate but something the client cannot parse
at all. Then the desynchronisation is loud, once, and then silent:

```text
Traceback (most recent call last):
  File "twice.py", line 38, in main
    reply = json.loads(proc.stdout.readline())
  ...
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

That is the failure Day 33's
[5.1](../../../day-33-client-and-transports/parts/05-failure-lab/5.1-the-log-line-that-ate-the-reply.md)
taught, and — counter-intuitively — it is the *better* outcome. A crash names the moment. A duplicate
gives you three answers, all valid, two of them lies, and an exit code of zero.

There is a second break specific to the fix. If the client re-reads on a mismatch without a bound,
and the server has simply stopped talking, then `readline()` on a still-open pipe blocks and you have
converted a wrong-answer bug into a hang — which is [1.1](../01-the-clock/1.1-the-only-clock-is-yours.md)'s
subject, arriving from the direction of the fix rather than the fault. The bounded version reads at
most a few extra lines and then raises.

And there is a variant worth recognising because it looks like a network problem and is not: over
Streamable HTTP a duplicated reply cannot desynchronise a stream, because each request has its own
response ([Day 33's 3.1](../../../day-33-client-and-transports/parts/03-streamable-http/3.1-one-endpoint-one-trip.md)).
The same server bug is harmless on one transport and corrupting on the other. That asymmetry is a
real reason to prefer HTTP for servers you do not control, and it is a better reason than the ones
usually given.

## In production

**What a professional writes instead:** a reader that does not assume one line per request at all. It
reads lines into a **dispatch table** keyed by id, hands each parsed message to whichever waiting call
matches, and counts the ones that match nothing. That structure is what every real SDK does, and it
makes the failure in this part impossible rather than merely detectable: a duplicate arrives, finds
no waiting caller, and increments a counter.

**What degrades at scale:** concurrency turns the assumption from fragile to false. The moment two
calls are in flight on one stdio connection, "read the next line" is not even approximately correct,
because the replies may come back in either order. A synchronous read-the-next-line client is
accidentally correct only while it is single-threaded, and the day somebody adds concurrency the
correctness quietly disappears with no code change at the site of the bug.

**The failure mode that only appears with real traffic:** partial drift under load. A server that
duplicates only on a timeout path duplicates only when it is busy, so the desynchronisation appears
during traffic peaks and vanishes when you go to reproduce it. The reports read as "sometimes it
shows the wrong ticket, but only in the afternoon", which sounds like a caching problem and is not.

**The review comment a senior engineer leaves:** *"this reads one line per request and trusts it. If
the server ever writes twice — a retry in its transport, two handlers on one pipe — we are one answer
behind forever and nothing throws. Key the replies by id and drop the ones that match nothing, and
add a counter so we can see it happening."*

**The interview question:** *"what is the worst failure mode you have seen with a line-oriented
protocol?"* This is the story: *"a server that wrote every reply twice. Nothing malformed, nothing
throwing, every message individually perfect. The client read one line per request, so from the
second request onwards every answer was the previous request's answer, permanently, and the process
exited zero. We reproduced it with a three-question script — two of three answers about the wrong
ticket. The fix is one comparison, the request id, and it is the check people leave out of a
validation checklist because it is the only one a schema cannot do for you. The real fix is
structural: read into a dispatch table keyed by id rather than assuming one line per request, which
is also the only thing that survives two calls being in flight at once."*
