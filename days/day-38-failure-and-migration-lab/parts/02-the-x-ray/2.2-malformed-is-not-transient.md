# 2.2 — Malformed is not transient

## One-line answer

Retrying is medicine for a failure that would give a different answer next time, and a malformed
reply will give the same answer every time — so a retry loop around a malformed reply spends every
request it has, learns nothing, and adds load to a server that is already misbehaving.

## The story

The drinks machine at the station ate your coin.

You pressed the button, the light came on, nothing came out. So you put in another coin, because the
first one clearly did not register, and the same thing happened. Then a third. By the fourth you were
not really expecting a drink any more, you were just annoyed and the machine was there.

Behind the glass, the bottle you wanted is stuck on the coil. It has been stuck since before you
arrived. It will still be stuck tomorrow. There was never a number of coins that would move it,
because the fault is not the kind of fault that varies.

The man who comes at the end of the shift with a key opens the front, unhooks the bottle, and writes
something on a clipboard. That is the only thing that was ever going to fix it. Your coins bought
nothing at all — and they did something slightly worse than nothing, because the machine now has four
coins it will have to refund and no record of who they came from.

## The idea in plain language

Failures come in two kinds, and the kind decides the cure.

A **transient** failure is one where the same request, sent again, may get a different answer. The
server was busy. An instance restarted. A connection reset. A rate limiter said no and told you when
to come back. Nothing about the request was wrong; the timing was. Patience genuinely helps.

A **deterministic** failure is one where the same request, sent again, gets the same answer. The
server's response schema is wrong. A proxy in the path mangles bodies. The tool's output does not
match its declared shape. Nothing has changed between attempt one and attempt ten, so attempt ten
fails identically.

The rule is one sentence: **classify before you cure.** Transient gets patience — a bounded number of
retries with growing gaps between them, then an escalation. Deterministic gets **quarantine**: stop
calling, record the diagnosis, tell a human. A retry loop applied to a deterministic failure is not
merely useless. It is actively harmful in three ways, and the third is the one that costs you a day:

1. It multiplies your load on a server that is already unwell.
2. It spends real elapsed time before failing anyway, so the thing that eventually surfaces to the
   user is *slower* than it would have been with no retry at all.
3. It usually destroys the diagnosis, because the shape of a retry loop is
   `except: continue`, and the exception it discarded had the answer in it.

This is where [2.1](2.1-five-questions-before-you-believe.md) pays off. Its five checks do not only
stop the crash; they produce a **named** failure, and the name is what makes the classification
possible. `not JSON` is deterministic. `TimeoutError` is transient. A boundary that raises
`Exception("something went wrong")` has made this part impossible to apply.

**Backoff** — the growing gap between retries — is the standard treatment for the transient case and
is Day 72's subject. It is worth naming now so it is clear what is being argued: not "never retry",
but "retry the failures that retrying can fix".

## Why Sutra needs it

[Day 44](../../../day-44-client-hardening/LESSON.md) writes `with_retries` into
`sutra/mcp/hardening.py`. A `with_retries` that wraps everything is a `with_retries` that is wrong
half the time, and it will be wrong invisibly, because a retry loop that fails looks exactly like a
call that failed.

There is a Sutra-specific edge, too. The free-tier budget in this project is about twenty generations
per day (`gemini-3.7-flash`, recorded in `docs/PACKAGES.md`). A retry ladder that fires around a
model call and treats every failure as transient can burn a whole day's quota against a request that
was malformed from the start. Quota is the currency here (Principle 15), and a retry is a purchase.

And it settles what `sutra/mcp/client.py` should do when it meets a bad server. Skip it, record it,
carry on with the tools it does have — which is exactly the failure isolation Day 33's
[6.2](../../../day-33-client-and-transports/parts/06-in-production/6.2-ten-servers-ten-clients.md)
argued for, applied to content rather than to connections.

## The mechanism

> 🎬 **The scene:** a partner's `tools/list` starts coming back with `tools` as a string instead of a
> list. Your boundary catches it, raises `Malformed`, and your call fails.
>
> 😬 **The naive fix:** the loop everybody writes.
> `for attempt in range(10): try: return call() except: continue`. It has fixed a hundred flaky
> problems before.
>
> 💥 **Why it fails:** the mangling is in the partner's serialiser. Attempt ten meets the same
> serialiser. You have sent ten requests to a struggling server, waited the full ladder before
> failing, and swallowed ten copies of the sentence that said what was wrong.
>
> 💡 **The insight:** the question is never "should I retry?" It is "will the answer be different?"
> Everything else follows from that one question, and the boundary's diagnosis is what lets you
> answer it.

The script runs the same naive ladder against six failures — three of each kind — and counts what the
requests bought:

```python
# days/day-38-failure-and-migration-lab/lab/classify.py
ATTEMPTS = 10
BACKOFF = [0.25, 0.5, 1.0, 2.0, 4.0, 8.0, 8.0, 8.0, 8.0]  # seconds, capped

FAILURES = [
    ("stream closed by an overloaded instance", "transient", 2),
    ("HTTP 429 with retry-after", "transient", 3),
    ("connection reset in the middle of a body", "transient", 2),
    ("a proxy serving an HTML error page", "deterministic", None),
    ("tools/list where tools is a string", "deterministic", None),
    ("answer about a ticket we did not ask for", "deterministic", None),
]


def ladder(succeeds_on: int | None, attempts: int) -> tuple[int, bool, float]:
    """Run a naive retry ladder and report (requests spent, succeeded, seconds waited)."""
    waited = 0.0
    for attempt in range(1, attempts + 1):
        if succeeds_on is not None and attempt >= succeeds_on:
            return attempt, True, waited
        if attempt < attempts:
            waited += BACKOFF[min(attempt - 1, len(BACKOFF) - 1)]
    return attempts, False, waited


def policy(kind: str) -> str:
    """The disposition each class earns, stated once so it can be argued with."""
    return "retry with backoff, then escalate" if kind == "transient" else "quarantine and surface"
```

**Line by line:**

- `BACKOFF` doubles and then **caps** at eight seconds. Doubling without a cap reaches numbers no
  user will wait for, and a cap is what every production backoff has. Real ladders also add a random
  jitter so that a thousand clients do not retry in lockstep; it is left out here because it would
  make the transcript different on every run and prove nothing extra.
- `succeeds_on` is `None` for the deterministic rows, and `None` is doing real work: it is not "fails
  ten times", it is "there is no attempt number at which this succeeds". Writing it as a large
  integer would have implied that patience is on a spectrum, which is the mistake being corrected.
- The three transient rows are the three transient failures you actually meet: an instance going
  away, a rate limiter, a connection reset. The `429` row is there because it is the one transient
  failure that *tells you* how long to wait, in the `retry-after` header, and a client that ignores
  that and uses its own ladder is guessing when it was given the answer.
- The three deterministic rows are three of the crimes from
  [2.1](2.1-five-questions-before-you-believe.md), which is the link between the two parts: the
  boundary produces these names, and this table decides what to do with each.
- `ladder` **simulates** the wait rather than sleeping it. Running the real ladder would take about
  forty seconds per deterministic row and would teach nothing that the arithmetic does not.
- `attempt >= succeeds_on` rather than `==` so that a row could be marked as succeeding on attempt 1,
  which is the no-failure case, without a special branch.
- `if attempt < attempts` stops the last iteration adding a wait nobody waits: after the final
  attempt you fail, you do not sleep.
- `policy` is a function of the **kind** and nothing else. Not of the server, not of the method, not
  of how important the caller thinks the call is. That narrowness is the argument.

Measured on 2026-09-04:

```text

stream closed by an overloaded instance        transient          2    0.25s  retry with backoff, then escalate
HTTP 429 with retry-after                      transient          3    0.75s  retry with backoff, then escalate
connection reset in the middle of a body       transient          2    0.25s  retry with backoff, then escalate
a proxy serving an HTML error page             deterministic     10   39.75s  quarantine and surface
tools/list where tools is a string             deterministic     10   39.75s  quarantine and surface
answer about a ticket we did not ask for       deterministic     10   39.75s  quarantine and surface

requests that bought an answer      : 7
requests that bought nothing        : 30
a struggling server was hit         : 30 extra times, for no result
```

Seven requests bought three answers. Thirty bought nothing, and each of those thirty landed on a
server that was already producing garbage. The elapsed column is the second cost: each deterministic
row waited `39.75s` before reporting a failure it could have reported immediately.

Turn that around and it is the design rule. A boundary that names the failure lets you look the name
up in a table with two rows. Without the name, every failure gets the same treatment, and the only
treatment anybody defaults to is retry.

## When it breaks

The `except: continue` loop is the version that breaks worst, because it destroys the evidence. Here
is what the boundary raised, once:

```text
Malformed: tools/list result: tools is str, not a list
```

and here is what a loop with a bare `except` leaves in the log after ten attempts:

```text
WARNING: tools/list failed, retrying (1/10)
WARNING: tools/list failed, retrying (2/10)
WARNING: tools/list failed, retrying (3/10)
...
ERROR: tools/list failed after 10 attempts
```

The first message names the bug in one line and could be pasted into a ticket for the server's owner.
The second is ten copies of "it did not work" and one summary of "it did not work", and finding the
first message from there means reproducing the problem with a debugger attached.

This is Day 21's rule about errors surfacing rather than being swallowed, meeting a network. A bare
`except` in a retry loop looks different from a bare `except` around a parse, and it is the same
mistake: catching a class of exception broader than the one you know how to handle.

There is also a rate-limit version, which is the one that makes an outage worse. If the failure is a
`429` and you ignore the `retry-after` header in favour of your own ladder, you retry sooner than you
were told to and get another `429`. Ten clients doing that is a small, sincere flood aimed at a
server that has explicitly asked for quiet.

The smallest fix is a classification function with a default of **quarantine**, not retry. Unknown
failures should not be retried, because the failures you have not thought about are more likely to be
bugs than to be weather.

## In production

**What a professional writes instead:** a table, not a `try`. Failure classes map to dispositions —
retry-with-backoff, retry-after-the-header-says, quarantine, escalate — and the mapping is data that
can be reviewed, tested and changed without touching the call site. Alongside it, a **circuit
breaker**: after N deterministic failures from one server, stop calling it entirely for a while, so
one bad partner cannot consume your capacity. That is Day 44's job and this is the argument for it.

**What degrades at scale:** retries stack multiplicatively. Three layers each retrying three times is
twenty-seven requests for one logical call, and nobody designed that number — it emerged from three
reasonable local decisions. Systems that survive this pick one layer to own retries, usually the
outermost one that still knows what the user wanted, and forbid the rest.

**The failure mode that only appears with real traffic:** the retry storm that converts a partial
failure into a total one. A server degrades and starts returning errors for one request in five.
Every client retries. The load quintuples. Now it returns errors for four in five. It is a positive
feedback loop, and the only thing that breaks it is clients that give up — which is exactly what
quarantine and circuit breaking are for.

**The review comment a senior engineer leaves:** *"this retries on every exception. `Malformed` is
deterministic — the tenth attempt hits the same broken serialiser, and we will have hidden the one
log line that named the bug. Retry `TimeoutError` and `ConnectionError`; quarantine everything else,
and make unknown default to quarantine rather than retry."*

**The interview question:** *"when do you retry?"* The short answer is a question: *"only when the
answer could be different next time. We split failures into transient and deterministic at the
boundary, because the validator already names them. We put numbers on it: a ten-deep ladder against
three transient failures cost seven requests and bought three answers; against three deterministic
ones it cost thirty requests, bought nothing, waited nearly forty seconds each before failing, and
hit a struggling server thirty extra times. And the version with a bare `except` also loses the
diagnosis, which is the expensive part — one line saying `tools is str, not a list` is worth more
than ten saying `retrying`."*
