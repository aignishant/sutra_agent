# 2.3 — The error you threw away

## One-line answer

A JSON-RPC error is a reply, not the absence of one: it carries a numbered code and a `data` block
that usually contain the instructions for fixing the call, and a client that treats every error as
"the server is unwell, retry" throws away the only structured diagnosis it will ever be given.

## The story

The card machine at the fuel pump says `DECLINED — CODE 51`.

You try again. Same thing. You try the other card, which works, and you drive off mildly irritated
with your bank.

Three days later somebody explains what 51 means. It means insufficient funds — not "the card is
broken", not "the machine is having a moment". Your salary had gone in a day late, and the pump had
told you so, in a two-character code printed on a screen you looked directly at and did not read.

The number was not an insult and it was not decoration. It was the answer to the question you spent
three days not asking, and it was free.

## The idea in plain language

Every JSON-RPC response is one of two shapes: a `result`, or an `error`. Both are successful
*responses*. The server received your message, understood it, processed it and replied. An `error` is
what a reply looks like when the answer is "no, and here is why".

An error object has three fields:

| Field | What it is |
| --- | --- |
| `code` | An integer from a defined range. Machine-readable, and the thing you branch on. |
| `message` | A short sentence for a human. Not stable; do not match on it. |
| `data` | Optional, method-specific, and frequently the part that tells you how to fix it. |

The 2026-07-28 revision made the codes worth branching on by tidying them up. It defined an
allocation policy that splits the JSON-RPC server-error range: `-32000` to `-32019` stays
implementation-defined, and `-32020` to `-32099` is reserved for the MCP specification itself. Then
it renumbered the codes introduced in that draft to fit —
`HeaderMismatch` from `-32001` to `-32020`, `MissingRequiredClientCapability` from `-32003` to
`-32021`, `UnsupportedProtocolVersion` from `-32004` to `-32022` — and moved resource-not-found from
`-32002` to `-32602`, the standard JSON-RPC "invalid params".

The practical consequence is that a code now tells you **whose problem it is**, and that is a
different axis from [2.2](2.2-malformed-is-not-transient.md)'s transient-or-deterministic:

- **Your problem, fixable right here.** `-32022` comes back with a `data.supported` list of protocol
  revisions. You do not need a human, a retry or a second server: you pick one from the list and
  send again.
- **Your bug.** `-32020` means your own HTTP header disagreed with your own JSON body. No amount of
  retrying will make them agree.
- **A fact about the server.** `-32601` (method not found) is not a failure so much as an answer to
  a question you did not know you were asking: this server does not have that method. That is
  **feature detection**, and [4.3](../04-the-leaving-list/4.3-dating-somebody-elses-server.md) builds
  a whole tool on it.
- **The caller's bug.** `-32602` (invalid params) means the arguments were wrong. Sending them again
  unchanged is the definition of pointless.
- **Genuinely the server's problem.** `-32603` (internal error) is the one that really is worth a
  retry with backoff.

Five codes, and only one of them is a retry. A client that collapses all five into "call failed" has
converted a rich, structured, standardised diagnosis into a boolean.

## Why Sutra needs it

Day 32 taught the header rules and the `-32020` that enforces them. Day 33 built the client that
sends those headers. Neither of them said what Sutra should *do* when one of these codes comes back,
and `sutra/mcp/client.py` currently has no answer.

`-32022` is the one that will actually happen to this repository, and soon. The pinned SDK speaks
`2025-11-25` and the specification is at `2026-07-28` — Day 32 measured that, and
[6.3](../06-in-production/6.3-the-bill-for-a-bump.md) turns it into a bill. The first time Sutra
meets a server that only speaks the newer revision, it will get `-32022` with a `data.supported` list
in it, and whether that is a five-line fix or a two-day incident depends entirely on whether anybody
read the `data` block.

The `-32601` case matters for a different reason. Sutra will eventually talk to servers of different
ages, and "method not found" is how you find out that a server predates a feature. Treating it as a
fault means you retry a method that will never exist; treating it as information means you stop
offering that feature for that server and carry on.

## The mechanism

> 🎬 **The scene:** a partner's server starts returning errors on `tools/list`. Your client logs
> `tools/list failed` and retries. It has been doing that all morning.
>
> 😬 **The naive fix:** raise the retry count, then open a ticket with the partner asking why their
> server is down.
>
> 💥 **Why it fails:** their server is not down. It is returning `-32022` with
> `data.supported: ["2025-11-25", "2026-07-28"]`, which is a complete, actionable instruction — they
> dropped an old revision and your client is still asking for it. Your log line has been discarding
> that sentence once a second since eight in the morning.
>
> 💡 **The insight:** an error is a reply. Read it the way you would read a result: parse it, branch
> on the code, and use the `data`.

Five error bodies, written to the shapes the specification defines for them:

```python
# days/day-38-failure-and-migration-lab/lab/errors.py
BODIES = [
    '{"jsonrpc": "2.0", "id": 1, "error": {"code": -32022, "message": "Unsupported protocol '
    'version", "data": {"supported": ["2025-11-25", "2026-07-28"], "requested": "2019-01-01"}}}',
    '{"jsonrpc": "2.0", "id": 2, "error": {"code": -32020, "message": "Header mismatch", '
    '"data": {"header": "Mcp-Method", "headerValue": "tools/call", "bodyValue": "tools/list"}}}',
    '{"jsonrpc": "2.0", "id": 3, "error": {"code": -32601, "message": "Method not found", '
    '"data": {"method": "sampling/createMessage"}}}',
    '{"jsonrpc": "2.0", "id": 4, "error": {"code": -32602, "message": "Invalid params", '
    '"data": {"uri": "ticket://T-9999"}}}',
    '{"jsonrpc": "2.0", "id": 5, "error": {"code": -32603, "message": "Internal error"}}',
]

MOVES = {
    -32022: ("re-issue with a version from data.supported", "fixable here, no retry"),
    -32020: ("our own header disagreed with our own body - fix the client", "our bug"),
    -32601: ("the server does not have this method - stop offering it", "feature detection"),
    -32602: ("the arguments were wrong - do not send them again unchanged", "caller's bug"),
    -32603: ("the server broke on its own - this one really is retryable", "retry with backoff"),
}
```

**Line by line:**

- The bodies are **strings** rather than dictionaries for the same reason
  [2.1](2.1-five-questions-before-you-believe.md)'s crimes were: this is what arrives on the wire, and
  reading it as text keeps the parse step honest and visible.
- `-32022` carries `data.supported` — a list — and `data.requested`, the version you asked for. That
  pair is what makes the failure self-repairing: you are told what you asked for, what is available,
  and therefore what to ask for next.
- `-32020`'s `data` names the header, its value and the body's value. All three, because a mismatch
  is a relationship and reporting one side of it would not be enough to fix anything. Day 32's
  [3.2](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.2-the-header-that-must-match.md)
  explains why the server refuses rather than picking a winner.
- `-32601`'s `data.method` is `sampling/createMessage` on purpose. That is the method a server on the
  leaving list still answers and a modern one does not, which makes this exact error the probe that
  [4.3](../04-the-leaving-list/4.3-dating-somebody-elses-server.md) uses.
- `-32603` has **no** `data` block. Internal errors usually do not, and should not: whatever went
  wrong inside the server is not the caller's business and leaking it is an information disclosure
  bug. That absence is why it is the one row that earns a blind retry — there is nothing else to act
  on.
- `MOVES` is keyed by the integer, never by the message. Message text is explicitly not stable in
  JSON-RPC, and a client that matches on `"Method not found"` breaks when the server's author
  improves the wording.
- Each value is a `(what to do, what kind of problem it is)` pair, so that the disposition and its
  justification live on the same line and cannot drift apart.

The comparison itself is short, because the argument is arithmetic:

```python
        code, message, data = read(raw)
        if SWALLOW:
            spent += RETRIES
            print(f"  error -> retried {RETRIES}x, gave up. code discarded.")
            continue
        move, kind = MOVES[code]
        spent += 1 if code != -32603 else RETRIES
        fixed += 1 if kind in ("fixable here, no retry", "feature detection") else 0
```

**Line by line:**

- The `SWALLOW` branch does not even bind the code to anything it uses. That is the fidelity of the
  simulation: a client that treats errors as opaque has the code in memory and never looks at it.
- `spent += 1 if code != -32603 else RETRIES` charges one request for the four errors you can act on
  and a full ladder for the one that is genuinely a retry. The point is not that reading codes makes
  everything free; it is that four of the five stop costing anything.
- `fixed` counts only the two rows that need no other party — the version renegotiation and the
  feature detection. `-32020` and `-32602` are also *understood* immediately, but understanding them
  means changing your code, not recovering this call, so counting them as fixed would be flattering.
- `MOVES[code]` uses a bare subscript rather than `.get(code, default)`, so an unknown code raises
  `KeyError` here rather than being quietly bucketed. A code you have never seen is a finding
  (Principle 10), and the default disposition for it is quarantine, not silence.

## When it breaks

The failure that costs the most is not throwing the code away. It is matching on the wrong thing.

A client written before this revision has code that reads:

```text
if error["code"] == -32001:   # HeaderMismatch
```

and against a current server that branch is now dead, because `HeaderMismatch` is `-32020`. The
condition is never true, so the client falls through to whatever its default is, which is usually
retry — and there is no error and no warning, because a comparison returning `False` is not a
failure. Day 32's list of renumbered codes is the reference; an older document is right about the
concepts and wrong about every number.

The second break is matching on the message:

```text
if "not found" in error["message"].lower():
```

which is true for `Method not found` and also for a server whose author wrote `Resource not found` for
`-32602`, and false for one who wrote `Unknown method`. The specification never promised the wording.

The third is assuming `data` is present. `-32603` has none, and this is the traceback:

```text
Traceback (most recent call last):
  File "client.py", line 41, in handle_error
    supported = error["data"]["supported"]
                ~~~~~^^^^^^^^
KeyError: 'data'
```

The fix for all three is the same shape: branch on `code`, treat `data` as optional, and never read
`message` except to show it to a person.

## In production

**What a professional writes instead:** an error taxonomy that lives in one module — a mapping from
code to a disposition enum, with the unknown case mapping to quarantine. Both the `code` and the
whole `data` block get attached to the structured log line and to the trace span, because the field
that explains an incident is often one you did not think to extract. Day 22's structured logging is
the machinery; this is the content that makes it worth having.

**What degrades at scale:** unlogged `data`. When one server in a fleet starts returning `-32022`,
the question "which revision is it asking for?" is answerable in seconds if `data.supported` is in
the log and needs a reproduction if it is not. At small scale you reproduce; at large scale you
cannot, because the server that did it has been replaced.

**The failure mode that only appears with real traffic:** a mixed fleet. Half a partner's instances
are upgraded and half are not, so `-32022` appears for some fraction of calls and disappears on
retry — which makes it look transient, so a retry loop "fixes" it and nobody investigates. The
version skew stays invisible until the last old instance is drained and every call starts failing at
once.

**The review comment a senior engineer leaves:** *"we are logging `error.message` and dropping
`error.code` and `error.data`. The code is the only stable field and the data is what tells us how to
fix it — log all three, branch on the code, and show the message to humans only."*

**The interview question:** *"an MCP call comes back with a JSON-RPC error. Walk me through what your
client does."* An answer with the codes in it: *"first, it treats it as a reply rather than a
failure — the server understood us and answered. Then it branches on `code`, never on `message`,
because the message text is explicitly not stable. In the 2026 revision the codes are worth branching
on: `-32022` comes back with a `data.supported` list, so a version mismatch is self-repairing;
`-32020` means our own header disagreed with our own body, which is our bug and never a retry;
`-32601` is feature detection rather than a fault; `-32602` means bad arguments; and `-32603` is the
one that is genuinely retryable, which is also the only one with no `data`. We counted it once:
reading the codes turned fifty wasted requests into fourteen and resolved two of the five failures
without anybody else being involved."*
