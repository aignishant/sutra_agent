# 2.1 — Five questions before you believe a byte

## One-line answer

A client must validate the envelope of every reply — is it JSON, is it JSON-RPC, is the id mine, is
there exactly one of `result` and `error`, does the payload match what the method promised — before
any field of it reaches the rest of the program, because the alternative is that a stranger's bug
raises an exception in the middle of your business logic.

## The story

The man at the money-changer's window does not take the note and hand you the cash.

He takes the note and holds it up to the light. He looks for the thread running through it. He turns
it over and tilts it so the number changes colour. He runs a thumb across the raised printing. Then
he looks at the serial number, and only then does he count out your money.

It takes him about four seconds and he does it for every single note, including from people he has
seen every week for years. He is not being suspicious of you. He is being suspicious of the note,
which is a different thing, and it is a habit rather than a judgement.

The reason he does it at the window, and not later at the back of the shop, is that at the window he
can still hand it back. Once it is in the drawer with the rest of the day's takings, the problem is
his.

## The idea in plain language

Your client sends a request and gets bytes back. Between those bytes and anything useful there are
five separate questions, and each one can be answered wrongly by a server that is buggy, half-broken,
or behind a proxy that is mangling responses.

Here they are, in the order that lets each one assume the previous one passed:

| # | Question | What a wrong answer looks like |
| --- | --- | --- |
| 1 | Is it JSON at all? | An HTML error page from a proxy, a stack trace, an empty line |
| 2 | Is it a JSON-RPC 2.0 message? | Valid JSON with no `jsonrpc` field — someone's REST handler |
| 3 | Is the `id` one I sent? | A reply to a different request, or to nobody's request |
| 4 | Does it have exactly one of `result` and `error`? | Both, or neither |
| 5 | Does the payload match what this method promises? | `tools/list` whose `tools` is a string |

The word for doing this at the edge of your program is **validation at the boundary**. The boundary
is the last line of code that still thinks in terms of "bytes from a stranger". Everything past it
thinks in terms of tickets and tools, and a `KeyError` raised there is a bug report about your code
for a fault in someone else's.

A **quarantine** is what a failed check earns: the reply is discarded, the failure is recorded with
the reason, and the server it came from is marked as untrustworthy for this call. It is not a retry.
[2.2](2.2-malformed-is-not-transient.md) is why that distinction matters more than it sounds.

The five checks are not equally famous, and check 3 is the one people leave out. It is the only one
that catches a *well-formed* message that is not yours, and Day 33's
[2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md) already
showed how one stray line on stdout shifts every reply by one.

## Why Sutra needs it

`sutra/mcp/client.py` from Day 33 calls `list_tools`, and something inside it eventually does the
equivalent of reaching into a parsed reply for a list of tools. Days 34 to 37 add resources, prompts,
task handles and an auth flow, each with its own reply shape, each reached the same way.

Every one of those is a place where a stranger's output is trusted. As long as the only MCP server
Sutra talks to is `sutra_mcp`, which you wrote, that is survivable. Phase 6 ends that: Day 39 puts a
database behind it, Day 40 introduces third-party servers and the allowlist, and
[Day 45](../../../day-45-the-mcp-audit/LESSON.md) audits the lot. The moment there is a server you
did not write, "it will send me what the schema says" stops being a fact and becomes a hope.

The concrete failure this prevents: a proxy in front of a partner's server starts returning an HTML
error page for one request in a thousand. Without the boundary, that page reaches
`json.loads(...)["result"]["tools"]` and raises inside Sutra's triage loop, which is three frames
away from anything that knows what an MCP server is.

## The paper behind it

> **End-to-end arguments in system design** · `doi:10.1145/357401.357402` · 1984 ·
> `https://doi.org/10.1145/357401.357402`

It argued that a correctness check belongs at the end points of a communication, because only the end
points know what the data is supposed to mean — the layers in between can help with performance but
cannot be trusted to establish correctness on the application's behalf.

That is exactly the claim being made here: JSON-RPC over a pipe, TCP checksums, TLS and a well-tested
SDK all guarantee that the bytes arrived intact, and not one of them can tell you that a `tools/list`
result contains a list of tools. Taught on Day 21 —
[`01-end-to-end-arguments.md`](../../../day-21-errors-surface-not-swallow/papers/01-end-to-end-arguments.md).

## The mechanism

> 🎬 **The scene:** you are pointing Sutra at a server somebody else operates, and you write the line
> every tutorial writes: `tools = json.loads(raw)["result"]["tools"]`.
>
> 😬 **The naive fix:** wrap it in `try/except Exception` and log. It stops the crash.
>
> 💥 **Why it fails:** the exception you catch is `JSONDecodeError` or `KeyError` or `TypeError`
> depending on which crime you met, and by catching all of them together you have thrown away the one
> piece of information the failure contained — *which* thing was wrong. You are left knowing that
> something did not work, which is the one fact you already had.
>
> 💡 **The insight:** check the envelope in order, and make each failure name itself. A boundary that
> produces a diagnosis is worth ten that produce a log line.

First, a server built to fail in five specific ways. It is not hostile; it is broken on purpose, in
the five ways real servers are broken:

```python
# days/day-38-failure-and-migration-lab/lab/crooked_server.py
CRIMES = [
    # 1 - not JSON at all. A proxy served an HTML error page over the MCP endpoint.
    "<html><head><title>502 Bad Gateway</title></head></html>\n",
    # 2 - JSON, but not a JSON-RPC message: no `jsonrpc`, no `id`.
    '{"tools": [{"name": "lookup_ticket"}]}\n',
    # 3 - JSON-RPC, but answering a request nobody sent.
    '{"jsonrpc": "2.0", "id": 999, "result": {"resultType": "complete", "tools": []}}\n',
    # 4 - both `result` and `error`. JSON-RPC says exactly one.
    '{"jsonrpc": "2.0", "id": 3, "result": {"tools": []}, "error": {"code": -1, "message": "x"}}\n',
    # 5 - the envelope is perfect and the payload is not what tools/list promises.
    '{"jsonrpc": "2.0", "id": 4, "result": {"resultType": "complete", "tools": "lookup_ticket"}}\n',
]


def main() -> None:
    """Answer each incoming line with the next crime. That is the whole server."""
    for n, _request in enumerate(sys.stdin):
        sys.stdout.write(CRIMES[n % len(CRIMES)])
        sys.stdout.flush()
```

**Line by line:**

- Each crime is a **string**, not a dictionary, because four of the five could not survive being
  built by `json.dumps` — crime 1 is not JSON, and crimes 3 and 4 are things a serialiser would
  cheerfully produce but a typed model would refuse. The wire is text, so the fixture is text.
- Crime 1 is an HTML error page rather than random characters, because that is the realistic version:
  a gateway between you and the server answers on its behalf and does not know it is meant to be
  speaking JSON-RPC.
- Crime 3 carries `id: 999`, an id no client in this experiment ever sends. Note it is otherwise a
  *perfect* message.
- Crime 4 has `result` **and** `error`. JSON-RPC 2.0 permits exactly one, and a message with both is
  ambiguous in a way no reader can resolve: whichever you read first, you are guessing.
- Crime 5 is the interesting one. `tools` is the string `"lookup_ticket"` instead of a list of tool
  objects, so `for tool in result["tools"]` iterates over eleven characters and produces eleven
  "tools" named `l`, `o`, `o`, `k`… That is a valid Python loop over a wrong thing.
- `_request` is discarded. The server does not read what you asked, which is honest: a broken server
  is often broken *before* it gets as far as caring.
- `n % len(CRIMES)` cycles, so the fixture can be driven for as many requests as you like.

Now the boundary, one function, one exception type, five named failures:

```python
# days/day-38-failure-and-migration-lab/lab/xray.py
class Malformed(ValueError):
    """A server reply that failed the boundary check, with the crime named."""


def validate(raw: str, sent_id: int, method: str) -> dict:
    """Check the envelope before trusting a byte of it, and say what failed."""
    try:
        message = json.loads(raw)  # 1 - is it JSON at all?
    except json.JSONDecodeError as exc:
        raise Malformed(f"not JSON: {exc}") from exc
    if not isinstance(message, dict) or message.get("jsonrpc") != "2.0":
        raise Malformed("not a JSON-RPC 2.0 message: no jsonrpc field")  # 2
    if message.get("id") != sent_id:
        raise Malformed(f"id mismatch: sent {sent_id}, got {message.get('id')!r}")  # 3
    if ("result" in message) == ("error" in message):
        raise Malformed("must carry exactly one of result / error")  # 4
    if "result" in message and method == "tools/list":
        tools = message["result"].get("tools")
        if not isinstance(tools, list):
            raise Malformed(f"tools/list result: tools is {type(tools).__name__}, not a list")  # 5
    return message
```

**Line by line:**

- `Malformed(ValueError)` is one exception type for all five failures, with the difference carried in
  the **message** rather than in the class. That is deliberate: the caller's decision is the same for
  all five — quarantine — so five classes would be five ways to write the same `except`. The
  diagnosis belongs in the string a human reads.
- `raise ... from exc` preserves the original `JSONDecodeError` as the `__cause__`, so the traceback
  still shows the character position where the parse died. Re-raising without `from` throws that
  away, and Day 21's rule about errors surfacing rather than being swallowed applies to the *detail*
  as much as to the fact.
- `not isinstance(message, dict)` comes before `.get()` because `json.loads("[1,2]")` returns a list
  and `json.loads("4")` returns an integer. Both are valid JSON, and both would raise
  `AttributeError` on `.get` — an exception from the wrong layer, describing your code instead of
  the server's.
- `message.get("id") != sent_id` uses `!=` on the raw values because JSON-RPC ids may be strings or
  numbers, and `2` and `"2"` are different ids. Coercing them to compare would make crime 3 pass in
  the one case where it matters most.
- `("result" in message) == ("error" in message)` is the exactly-one rule written as one comparison.
  It is true when both are present and true when neither is, which are the two failures, and false in
  the two legal cases. It reads oddly the first time and is the shortest correct form.
- Check 5 is **per method**, which is why `method` is a parameter. There is no single "is this a
  valid MCP result" test: `tools/list` promises `tools`, `resources/read` promises `contents`. This
  is the check a schema library does properly and a hand-written client does for the two or three
  methods it actually calls.
- The function **returns the message** rather than a boolean, so there is no way to use it and then
  forget to use its result. A validator that returns `True` invites `validate(raw)` on a line of its
  own, followed by code that reads the unvalidated original.

And the two arms, which differ by one branch:

```python
            if not HARDENED:
                names = json.loads(raw)["result"]["tools"]  # the tutorial line
                print(f"req {n}: accepted {names!r}")
                continue
            try:
                validate(raw, sent_id=n, method="tools/list")
                print(f"req {n}: accepted (!?)")
            except Malformed as exc:
                caught += 1
                print(f"req {n}: QUARANTINE -> {exc}")
```

**Line by line:**

- `json.loads(raw)["result"]["tools"]` is written out in full because it is the line this whole part
  exists to argue with, and it is the line every quick example contains.
- The `try` block wraps **only** the validation, not the printing. A `try` that also contains the
  work is a `try` that will one day catch an exception from the work and report it as a protocol
  error.
- `except Malformed` catches one type. Nothing broader. If `validate` raises something unexpected,
  that is a bug in `validate` and it should surface (Principle 10).
- The loop **continues** after a quarantine. That is the property being demonstrated: five bad
  replies produce five diagnoses and one process that is still running.

## In production

**What a professional writes instead:** a schema, not five `if` statements. The MCP SDK models the
message types with pydantic, and a hand-written client should validate against generated models
rather than hand-rolled checks. The five checks here are teaching material and a good mental
checklist — but at production scale the payload rules are too many to hand-write and too fast-moving
to hand-maintain. What does *not* come free with a schema is check 3, the id match, because the
schema does not know what you sent; that one stays yours.

**What degrades at scale:** the cost of validating everything on every call. Full schema validation
of a large `resources/list` result is not free, and a client under load will show it in a profile.
The usual compromise is to validate the envelope always and the payload at the boundary of trust —
always for third-party servers, sampled for your own.

**The failure mode that only appears with real traffic:** intermittent malformation. A single
misbehaving instance behind a load balancer means one reply in twenty is garbage, and a client
without a boundary produces a scatter of unrelated exception types from unrelated places in the code.
With a boundary it produces the same diagnosis twenty times an hour with the server's name attached,
and the incident takes one look instead of a day.

**The review comment a senior engineer leaves:** *"`json.loads(resp)["result"]` — this is a
third-party server. If they return an HTML error page this raises `JSONDecodeError` inside the triage
loop. Validate the envelope where the bytes come in, name the failure, and let the loop see something
it can act on."*

**The interview question:** *"how do you protect an agent from a misbehaving MCP server?"* Give them
the checklist and the reason: *"envelope validation at the boundary, in order — is it JSON, is it
JSON-RPC 2.0, is the id one I sent, is there exactly one of result and error, does the payload match
the method's schema. Each failure raises one exception type with a message naming which check failed,
so the disposition code has a diagnosis rather than a log line. We drilled it against a fixture
server that commits five specific crimes: the hardened reader names all five and keeps running, and
the one-line version dies on the first and never sees the other four. The check people leave out is
the id one, because it is the only one that catches a well-formed message that is not yours."*
