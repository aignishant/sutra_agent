# 1.4 — The client declares too

## One-line answer

Capability declaration runs both ways: the client's capabilities ride in `_meta` on **every single
request**, they are **required**, and a server that needs one the client did not declare must answer
`-32021 MissingRequiredClientCapability` rather than guess.

## The story

You book a taxi and you give the drop address. Then you book another one the next morning and you
give the drop address again, and it is the same address, to the same company, from the same phone.

It feels wasteful the first few times. Then one evening you get a driver who is new to the city, and
you realise that every ride you have taken has worked because the address travelled with the ride and
not with the driver. Nobody had to remember you. Nobody had to look you up. The ride carried
everything the ride needed.

The company can hire a hundred drivers overnight and every one of them can take you home on their
first shift, because the thing that makes the ride work is written on the ride.

## The idea in plain language

Day 32's
[2.3](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.3-every-request-introduces-itself.md)
taught that every request in the 2026-07-28 revision carries its own `_meta` block with the protocol
version and the client's identity in it. This part is about **the third field in that block**, which
is the client's own capability declaration, and about what it costs and what it buys.

The two directions are not symmetrical, and the asymmetry is worth stating plainly:

| | Server capabilities | Client capabilities |
| --- | --- | --- |
| Where they travel | in a `server/discover` reply, or an `initialize` reply on a legacy server | in `_meta` on **every request** |
| How often | once, cacheable | every time, never cached |
| Required? | the reply carries them | **yes** — a request without them is malformed |
| What happens when one is missing | the client skips that family | the server returns `-32021` |

The server declares **once because it can**: a declaration is a fact about the deployment and it is
the same for everyone. The client declares **every time because it must**: there is no session to
hold the answer in, and the next request may reach a different instance that has never seen this
client before.

The client-side families are the ones where the **server** asks the **client** for something:

- `elicitation` — the server can ask the user a structured question mid-tool
  ([Day 37](../../../day-37-auth-and-elicitation/parts/03-the-question/3.2-a-form-the-till-can-print.md)).
- `sampling` — the server can ask the client's model for a completion.
- `roots` — the server can ask which directories it may see.
- `tasks` — the client can hold a task handle across requests
  ([Day 36](../../../day-36-long-jobs-and-tasks/parts/03-the-handle/3.1-a-name-the-server-mints.md)).
- `extensions` — the same reverse-DNS map as
  [1.3](1.3-an-extension-is-a-capability-with-a-surname.md), from the other side.

And the rule that makes them load-bearing, from the base protocol page
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/index`, read 2026-09-04):

> *"A server **MUST NOT** rely on capabilities the client has not declared. If processing a request
> requires a capability the client did not include in
> `io.modelcontextprotocol/clientCapabilities`, the server **MUST** return a
> `MissingRequiredClientCapabilityError` (`-32021`) whose `data.requiredCapabilities` lists the
> missing capabilities."*

That is the sentence that makes a client declaration worth sending. Without it a server would have to
try and see what happened, halfway through doing real work.

## Why Sutra needs it

Sutra is a client on Days 33, 40 and 44, and a server on Days 34 through 43. Both halves have a
decision here.

**The client half.** Sutra's `sutra/mcp/client.py` sends requests to strangers' servers. What Sutra
puts in `clientCapabilities` decides what those servers are allowed to ask of it. Declaring
`elicitation` means a stranger's tool may interrupt a run to put a question in front of your user.
Declaring the Apps extension means a stranger's server may hand you HTML to render.
[4.5](../04-a-server-that-draws/4.5-parked-why-sutra-ships-no-app.md) is the decision about that
second one, and it is a decision precisely because the declaration is what enables it. Principle 13
in one line: **the declaration is the blast radius.**

**The server half.** `sutra_mcp` will one day want to ask a question mid-tool. When it does, it must
read the caller's declaration first and return `-32021` when elicitation is absent, rather than
sending a question into a client that will drop it. Day 37's
[3.3](../../../day-37-auth-and-elicitation/parts/03-the-question/3.3-three-answers-not-two.md) taught
the three answers a question can get; the fourth outcome — *the caller cannot be asked at all* — is
this one, and it is not an answer, it is a refusal.

## The paper behind it

> **Principled design of the modern Web architecture** · `doi:10.1145/514183.514185` · 2002 ·
> `https://doi.org/10.1145/514183.514185`

It argued that an interaction is scalable exactly when every message carries everything needed to
understand it, so that no intermediary and no server instance has to remember anything about what
came before. A capability declaration riding in `_meta` on every request — rather than negotiated
once and stored — is that argument applied to a single field.

Taught on Day 32:
[`papers/01-modern-web-architecture.md`](../../../day-32-mcp-stateless-core/papers/01-modern-web-architecture.md).

## The mechanism

The envelope, built the way Sutra's client would build it. From `lab/client_meta.py`:

```python
REVISION = "2026-07-28"
UI_EXTENSION = "io.modelcontextprotocol/ui"
APP_MIME = "text/html;profile=mcp-app"


def envelope(extensions: dict[str, Any] | None = None) -> dict[str, Any]:
    """Build the _meta block that rides inside params on every request Sutra sends."""
    capabilities: dict[str, Any] = {}
    if extensions:
        capabilities["extensions"] = extensions
    return {
        "io.modelcontextprotocol/protocolVersion": REVISION,
        "io.modelcontextprotocol/clientInfo": {"name": "sutra", "version": "0.1.0"},
        "io.modelcontextprotocol/clientCapabilities": capabilities,
    }
```

**Line by line:**

- The three keys are the specification's exact reserved names, copied from the base protocol page
  rather than remembered. `protocolVersion` and `clientCapabilities` are **required** on every
  request; `clientInfo` is optional and **SHOULD** be sent, which is why it is here rather than
  behind a flag.
- `capabilities` starts as `{}` and stays `{}` when nothing is passed. An empty object is the correct
  declaration for a client that supports no optional feature — it is not the same as omitting the
  key, which would make the request malformed and earn a `-32602`.
- `extensions` is added **only when non-empty**. A declaration with `"extensions": {}` in it says the
  same thing as one without, and sending the empty map on every request is bytes you pay for on every
  request.
- `REVISION` is a module constant. The version travels in two places on HTTP — here and in the
  `MCP-Protocol-Version` header from Day 32's
  [3.2](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.2-the-header-that-must-match.md)
  — and they must agree, so there is one source for both.

And the request that wraps it:

```python
def request(
    method: str, params: dict[str, Any], extensions: dict[str, Any] | None = None
) -> dict[str, Any]:
    """Wrap one JSON-RPC call, with the declaration inside params._meta."""
    return {
        "jsonrpc": "2.0",
        "id": 1,
        "method": method,
        "params": {**params, "_meta": envelope(extensions)},
    }
```

**Line by line:**

- `_meta` sits **inside `params`**, not beside it. That is the one placement mistake that produces a
  silently-ignored declaration: a server reads `params._meta`, and a `_meta` at the top level of the
  request object is simply not there as far as the specification is concerned.
- `{**params, "_meta": ...}` builds a new dictionary rather than mutating the caller's. A client that
  mutates the argument will, on its second retry of the same call, send an envelope built from the
  first attempt's state — which is exactly the kind of bug that only appears under retry.
- `"id": 1` is a constant here because the lab prints one request at a time. In real code the id must
  be unique among outstanding requests; Day 33's
  [2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md) is where the
  framing that depends on it was established.

Eighty-six bytes, on every request, forever. That is the arithmetic of statelessness made small
enough to argue with: the declaration is not amortised, because there is nowhere to amortise it to.

## When it breaks

The break is a server that reads the declaration once and then assumes it.

A server handles `tools/call`, sees `elicitation` in the caller's capabilities, and stashes it on
whatever it has that looks like a connection. Later, in a background continuation, it decides to ask
the user a question — and by then the request that carried the declaration is long finished. What
comes back to the caller is not an error and not an answer, but a question sent down a wire nobody is
reading, and a tool that never returns.

The specification's own failure, which is the one you want instead, looks like this:

```text
{"jsonrpc":"2.0","id":4,"error":{"code":-32021,"message":"Missing required client capability",
 "data":{"requiredCapabilities":["elicitation"]}}}
```

`-32021` is in the reserved range `-32020` to `-32099` that the 2026-07-28 revision carved out for
itself, so it cannot collide with an implementation-defined code. The `data.requiredCapabilities`
list is the useful half: the client now knows exactly what to add before retrying, rather than
knowing only that something was wrong.

The smallest fix on the server is a rule rather than a patch: **read the caller's capabilities from
the request you are answering, and never from anything that outlives it.** If the work needs a
capability, check it at the top of the handler and refuse there, before any side effect has happened.

## In production

**What a professional writes instead:** a client whose capability declaration is one frozen constant
built at start-up and attached by the transport layer, never assembled per call site. Assembling it
per call site means two call sites eventually declare different things, and a server will then see
one client that sometimes supports elicitation.

**What degrades at scale:** the byte count, and only the byte count — but it is worth knowing the
number. Eighty-six bytes per request across a million calls a day is about eighty megabytes of
request body that exists purely so that no instance has to remember anything. That is a real cost and
it is the correct trade, and being able to say the number out loud is the difference between having
chosen statelessness and having inherited it.

**The failure mode that only appears with real traffic:** a client that declares more than it can do.
Declaring `elicitation` and then dropping the question because the UI has no place to put it produces
tools that hang rather than tools that fail. There is no error anywhere — the server is waiting, the
client has moved on, and the only symptom is a timeout attributed to the wrong service.

**The review comment a senior engineer leaves:** *"we declare `elicitation` in the client envelope and
our host has no dialog surface. Take it out. A capability you declare and cannot honour turns a clean
`-32021` refusal into a hung tool call, and the person paged for that will be looking at the server's
logs, where nothing is wrong."*

**The interview question:** *"why does the client send its capabilities on every request instead of
once?"* The answer: *"Because there is nowhere to send them once to. The revision removed the session,
so any instance behind a URL may answer any request and no instance has seen this caller before. The
declaration is required in `_meta` on every request, and the rule that gives it teeth is that a server
must not rely on a capability the client did not declare — if it needs one that is missing it returns
`-32021` with the missing names in `data.requiredCapabilities`, rather than starting work it cannot
finish. It costs us about eighty-six bytes a request for the extension claim, which is the honest
price of any instance being able to answer anything. It is the same argument the Web architecture
paper made about self-descriptive messages, applied to one field."*
