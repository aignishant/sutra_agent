# 1.1 — The programmes on the dial

## One-line answer

A capability is not a feature and not a tool: it is a **whole family of methods** a server says it
answers, so `tools` means *I answer `tools/list` and `tools/call`*, and a family the server does not
name is a family whose methods simply do not exist there.

## The story

You buy a washing machine and the first thing you look at is the dial.

Cotton. Synthetics. Wool. Quick wash. Rinse. Spin. Six positions, printed in white on the plastic,
and the dial stops at each one with a click. There is no seventh position. Not a hidden one, not a
locked one, not one you unlock by holding two buttons — the dial physically does not turn any
further.

Your neighbour's machine, the same brand, has a seventh position that says *Drying*. Yours does not,
because yours does not have a heater in it. Nobody removed the drying programme from your machine. It
was never there, and the dial is an honest picture of the machine behind it.

Now the part that matters. When you want to know whether the machine can dry clothes, you do not put
wet clothes in and press start and see what happens. You look at the dial. It takes a second, it
costs nothing, and it is the manufacturer telling you, in advance, the complete list of things this
box will do.

## The idea in plain language

Sutra's ticket archive is now a server that strangers can call
([Day 34](../../../day-34-building-sutra-mcp-tools/LESSON.md)). A stranger's first problem is the
same as yours in front of the washing machine: **what does this thing do?**

MCP answers with a **capability declaration**. It is a small JSON object the server produces that
lists, by name, the families of methods it answers. Not the tools. Not the descriptions. The
*families*.

A **method family** is a group of related requests that share a prefix. There are only a handful in
the core protocol, and you have met most of them already:

| Family | The methods in it | Taught on |
| --- | --- | --- |
| `tools` | `tools/list`, `tools/call` | [Day 34](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.1-the-list-and-who-may-keep-it.md) |
| `resources` | `resources/list`, `resources/read`, `resources/templates/list` | [Day 35](../../../day-35-resources-and-prompts/parts/02-the-shelf/2.1-an-address-not-a-call.md) |
| `prompts` | `prompts/list`, `prompts/get` | [Day 35](../../../day-35-resources-and-prompts/parts/03-the-card/3.1-the-words-the-house-owns.md) |
| `logging` | `logging/setLevel` | Day 38 |
| `completions` | `completion/complete` | not taught; argument autocomplete for prompts |
| `tasks` | `tasks/get`, `tasks/list`, `tasks/cancel` | [Day 36](../../../day-36-long-jobs-and-tasks/parts/04-the-tasks-extension/4.1-four-messages-on-the-wire.md) |

Read the middle column again and notice what a capability is **not**. `tools` does not mean *"I have
`lookup_ticket`"*. It means *"the two methods whose names start with `tools/` will get a real answer
here"*. Which tools those methods return is a completely separate question, answered by actually
calling `tools/list`.

That separation is the whole design, and it is why the declaration is tiny. There are six families,
so the declaration is at most six keys long no matter how big the server is. Sutra's archive could
grow to four hundred tools and its capability declaration would not gain a single character.

Two words that get confused, so define them once and keep them apart for the rest of the day:

- **Declaration** — the small object naming the families. Cheap, fixed-size, read first.
- **Catalogue** — what a family's `list` method returns: the actual tools, resources or prompts.
  Grows with the server, and is a separate request.

The dial is the declaration. The clothes you can actually put in are the catalogue.

## Why Sutra needs it

Because Sutra is on both ends of this question, and gets it wrong in a different way on each end.

**As a client**, Sutra mounts other people's servers. Day 33's
[1.3](../../../day-33-client-and-transports/parts/01-the-connector/1.3-before-the-model-sees-a-tool.md)
listed a stranger's tools before a model ever saw one. But a client that calls `prompts/list` on a
server with no `prompts` family gets an error rather than an empty list, and the difference between
*"no prompts here"* and *"this server does not do prompts"* is the difference between a retry that
might work and a retry that never will.

**As a server**, `sutra-mcp` produces a declaration whether or not anyone wrote one, and this day's
[1.2](1.2-nobody-types-the-declaration.md) shows that the one it currently produces is wrong. Day
45's audit reads that declaration against every server on Sutra's list, including Sutra's own, and a
declaration nobody checked is a row in an audit that says nothing.

## The mechanism

The pinned SDK models the declaration as a single class. Read it rather than trust this page —
`.venv/Lib/site-packages/mcp/types.py`, checked on 2026-09-04:

```python
class ServerCapabilities(BaseModel):
    """Capabilities that a server may support."""

    experimental: dict[str, dict[str, Any]] | None = None
    logging: LoggingCapability | None = None
    prompts: PromptsCapability | None = None
    resources: ResourcesCapability | None = None
    tools: ToolsCapability | None = None
    completions: CompletionsCapability | None = None
    tasks: ServerTasksCapability | None = None
    model_config = ConfigDict(extra="allow")
```

**Line by line:**

- Every field is `| None = None`. **Absent means "this family does not exist here"**, and it is the
  default. A server declares by *adding* a key, never by setting a flag to false — so the smallest
  possible declaration is `{}` and it is a perfectly legal server that answers nothing but `ping`.
- `prompts`, `resources` and `tools` are not booleans. Each is a small object carrying the *options*
  within that family: whether the server will send a `listChanged` notification, and, for resources,
  whether a client may subscribe. The family is named by the key existing; the object says how the
  family behaves.
- `experimental` is a free-form map of vendor-defined names to settings objects. It is the pinned
  SDK's slot for anything the core protocol has not standardised, and
  [1.3](1.3-an-extension-is-a-capability-with-a-surname.md) is entirely about why the current
  specification stopped using it for extensions.
- `tasks` is here because the Tasks extension was folded into this SDK's type before it was folded
  into the type list you would expect. Day 36's
  [4.4](../../../day-36-long-jobs-and-tasks/parts/04-the-tasks-extension/4.4-which-dialect-your-sdk-speaks.md)
  measured which half of it the pin actually speaks.
- `model_config = ConfigDict(extra="allow")` is the line that will matter most on this day. Pydantic
  normally rejects a field it has never heard of; `extra="allow"` tells it to keep the field instead.
  That is why a hand-built declaration on this SDK can carry an `extensions` key the class does not
  define — the type is a revision behind, and this one line is what stops it being a wall.

Now build two servers that differ by exactly one handler and print what each declares. From
`lab/declared.py`:

```python
def tools_only() -> Server[Any]:
    """A server that answers tools/list and nothing else."""
    server: Server[Any] = Server("tools-only")

    @server.list_tools()
    async def _list_tools() -> list[Tool]:
        return [Tool(name="lookup_ticket", description="d", inputSchema={"type": "object"})]

    return server


def declaration(
    server: Server[Any], extra: dict[str, dict[str, Any]] | None = None
) -> dict[str, Any]:
    """Ask the SDK what this server declares, and return it as plain JSON."""
    caps = server.get_capabilities(NotificationOptions(), extra or {})
    return caps.model_dump(by_alias=True, exclude_none=True)
```

**Line by line:**

- `Server("tools-only")` is the **low-level** server, not `FastMCP`. That choice is deliberate and it
  is the only way to see the mechanism: the low-level class declares what you registered, while
  `FastMCP` registers everything up front and therefore declares everything. [1.2](1.2-nobody-types-the-declaration.md)
  measures the difference.
- `@server.list_tools()` registers a handler for `ListToolsRequest`. Registering it is the *entire*
  act of declaring the `tools` family — there is no separate declaration step and no argument
  anywhere that says `tools=True`.
- `NotificationOptions()` carries the three `listChanged` flags, all defaulting to `False`. They end
  up inside the family objects, which is why the printed output says `{"listChanged": false}` rather
  than `{}`.
- `extra or {}` is the experimental map, passed straight through. `None` and `{}` behave the same, so
  the caller can omit it.
- `model_dump(by_alias=True, exclude_none=True)` turns the pydantic object into the JSON the wire
  would carry. `exclude_none=True` is what makes absence visible: without it every unset family would
  print as `null` and the output would suggest six families where there is one.

## When it breaks

The break is reading a capability as a promise about *contents*, and it produces a bug that looks
like a server problem and is a client problem.

A client reads `"tools": {"listChanged": false}` and concludes the server has tools. It then calls
`tools/list` and gets:

```text
{"jsonrpc":"2.0","id":2,"result":{"tools":[]}}
```

An empty list, and a successful call. Nothing is wrong. The server declared that the `tools` family
works, and it does work — it just currently returns nothing, which is what an archive with no tools
registered yet looks like, and what a filtered server looks like after Day 40's allowlist has removed
everything the caller is permitted to see.

The mirror-image break is worse because it raises. Call a family the server never declared:

```text
prompts/list -> error -32601: Method not found
```

That is `lab/undeclared.py`, run on 2026-09-04, and `-32601` is the plain JSON-RPC *Method not found*
code — the same code you would get for a typo. [2.3](../02-discovery-without-sessions/2.3-asking-for-what-was-never-declared.md)
is entirely about that reply and what a client should do with it.

The smallest fix for both: **branch on the declaration for whether to ask at all, and on the list for
whether there is anything there.** Two different questions, two different requests, and a client that
collapses them into one will either send requests that cannot succeed or skip families that would
have answered.

## In production

**What a professional writes instead:** a client that reads the declaration once per server, stores
it as a set of family names beside the server's URL, and gates each family's requests on membership.
No `try/except` around `prompts/list` to discover whether prompts exist — that is using an exception
as a question, and it costs a round trip to learn something the server already told you.

**What degrades at scale:** nothing about the declaration itself; it is six keys and it stays six
keys. What degrades is the code around it when families multiply. A client with a hard-coded
`if "tools" in caps` for each family grows a branch per family per call site. The version that
survives is a small table mapping family name to the requests it permits, consulted once.

**The failure mode that only appears with real traffic:** a mixed fleet behind one URL. Day 32's
[2.2](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md)
established that any instance may answer any request. During a rolling deploy that adds a family,
half the instances declare it and half do not, so a client that read the declaration from a new
instance can send `prompts/list` to an old one and get `-32601` for a family that "exists". Capability
changes must be additive and the error must still be handled — the declaration is a hint, never a
contract.

**The review comment a senior engineer leaves:** *"you are calling `resources/list` on every server
we mount and swallowing the error when it fails. That error is the server telling you it has no
resources family, and you already fetched that fact when you connected. Read the capability set, skip
the request, and let a real `-32601` be loud again — right now a genuine routing bug looks identical
to a server that simply does not do resources."*

**The interview question:** *"what is an MCP capability, exactly?"* The answer that shows you have
read the schema rather than a blog post: *"It is a declaration of method families, not of contents. A
server that declares `tools` is promising that `tools/list` and `tools/call` will get a real answer;
it is promising nothing at all about how many tools there are, and an empty tool list is a perfectly
successful call. Absence is the default — a family you do not name simply does not exist on that
server, and asking for it gets `-32601 Method not found` rather than an empty result. The practical
consequence is that a client needs two checks, not one: the declaration says whether to ask, and the
list says whether there is anything there."*
