# 1.3 — An extension is a capability with a surname

## One-line answer

A core family is named by a bare word (`tools`); an extension is named by a **reverse-DNS
identifier** (`io.modelcontextprotocol/ui`) inside a separate `extensions` map — and the pinned
SDK has no `extensions` map at all, so on `mcp==1.29.1` an extension claim goes into `experimental`
or nowhere.

## The story

Your school runs the exams for an outside board.

The hall is the school's. The invigilators are the school's teachers. The timetable is on the
school's noticeboard. But the certificate that arrives four months later does not have the school's
name at the top — it has the board's, along with a centre number that identifies your school within
the board's own system.

Two names, two systems, and everybody knows which is which. When you tell an employer you passed, you
name the board, not the school, because the board is what makes the certificate mean the same thing
in another city. And when a second board starts using the same hall next year, nothing collides:
different name at the top, different centre number, same room.

## The idea in plain language

The core MCP families — `tools`, `resources`, `prompts` — are named by bare words because there is
exactly one MCP and it owns those words. Nobody else may add a family called `widgets`, because there
is no way to tell whose `widgets` it is.

So everything outside the core is named with a **prefix that identifies who defined it**, written in
reverse-DNS notation: the domain name backwards, then a slash, then the name. Day 37's
[5.1](../../../day-37-auth-and-elicitation/parts/05-policy/5.1-the-optional-extras-list.md) taught
the extensions framework itself — versioned, opt-in, off by default. This part is about one narrow
thing: **where the identifier physically goes in a declaration, and what happens to it in the SDK you
have installed.**

The current revision puts extensions in a map of their own. From the specification's versioning page
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning`, read 2026-09-04):

> *"Extensions are advertised in the `extensions` field of capabilities, which is a map of extension
> identifiers to per-extension settings objects."*

and the naming rule, from the base protocol page
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/index`, read the same day):

> *"Any prefix where the second label is `modelcontextprotocol` or `mcp` is **reserved** for MCP
> use."*

So the three official extensions you meet in this curriculum are:

| Extension | Identifier | Taught on |
| --- | --- | --- |
| Tasks | `io.modelcontextprotocol/tasks` | [Day 36](../../../day-36-long-jobs-and-tasks/parts/04-the-tasks-extension/4.1-four-messages-on-the-wire.md) |
| MCP Apps | `io.modelcontextprotocol/ui` | [4.1](../04-a-server-that-draws/4.1-a-tool-that-brings-its-own-window.md) |
| Enterprise Managed Authorization | `io.modelcontextprotocol/enterprise-managed-authorization` | [Day 37](../../../day-37-auth-and-elicitation/parts/05-policy/5.3-policy-that-can-name-a-feature.md) |

Note the second row. The extension is called **MCP Apps** and its identifier says **`ui`**. A search
for the string `apps` in a capability declaration finds nothing, which is a small thing that costs
somebody an afternoon roughly once per team.

The settings object beside the identifier is not decoration. For Apps it is
`{"mimeTypes": ["text/html;profile=mcp-app"]}` — the party is not merely saying *I do Apps*, it is
saying *these are the content types I can render*. An empty object means *supported, no settings*.

## Why Sutra needs it

Because `sutra_mcp/capabilities.py`, the module you write today, has to hold an extension claim in a
place that is honest about two things at once: what the specification says the shape is, and what the
installed library can actually put on the wire. Those are different, and pretending otherwise is the
kind of quiet lie Principle 10 exists to stop.

There is also a client-side reason arriving on Day 44. Sutra mounts other people's servers, and an
enterprise policy — the one Day 37's
[5.3](../../../day-37-auth-and-elicitation/parts/05-policy/5.3-policy-that-can-name-a-feature.md)
described, where a company blocks any server carrying a named extension — can only be enforced if
Sutra can read the identifier out of a declaration and match it exactly. `io.modelcontextprotocol/ui`
and `io.modelcontextprotocol/UI` are two different strings and only one of them is the extension.

## The mechanism

The specification's own example, copied from the versioning page on 2026-09-04:

```json
{
  "capabilities": {
    "roots": {},
    "extensions": {
      "io.modelcontextprotocol/ui": {
        "mimeTypes": ["text/html;profile=mcp-app"]
      }
    }
  }
}
```

Two levels, and the nesting is the whole point: core families sit directly under `capabilities`,
extensions sit one level deeper under `extensions`. A client reading a declaration therefore looks in
two places, and a client that looks in one will see either no extensions or no core families.

Now what the pinned SDK does with that. `ServerCapabilities` in `mcp==1.29.1` has no `extensions`
field — [1.1](1.1-the-programmes-on-the-dial.md) listed the seven it does have. What it has instead is
`experimental`, and `lab/declared.py`'s third arm uses it:

```python
UI_EXTENSION = "io.modelcontextprotocol/ui"
APP_MIME = "text/html;profile=mcp-app"

print("\nC. the same server, claiming the MCP Apps extension by hand")
print(json.dumps(declaration(tools_and_resources(), {UI_EXTENSION: {"mimeTypes": [APP_MIME]}}), indent=2))
```

**Line by line:**

- `UI_EXTENSION` is a module constant, not a literal at the call site. An identifier that appears once
  can be typed wrong once; a constant is typed wrong in one place and the whole file is wrong
  together, which is a failure you find rather than a failure you ship.
- `APP_MIME` is `"text/html;profile=mcp-app"` — no space after the semicolon. That is the exact string
  the Apps specification requires, and a media-type parameter is not whitespace-insensitive in every
  implementation, so it is copied rather than reformatted.
- The dictionary passed as `extra` is the **experimental capabilities** argument from
  [1.2](1.2-nobody-types-the-declaration.md)'s `get_capabilities`. It is the only channel this SDK
  offers for a name it does not know.
- The value is a settings object, not `True`. Even here, where the SDK has no idea what the key means,
  the shape stays specification-correct — so the day the pin moves, the value moves across unchanged
  and only its parent key changes.

Run it and read arm C:

```bash
uv run python days/day-41-capabilities-and-mcp-apps/lab/declared.py
```

**Line by line:**

- From the repository root. **Zero generations, no network.**

On 2026-09-04:

```text
C. the same server, claiming the MCP Apps extension by hand
{
  "experimental": {
    "io.modelcontextprotocol/ui": {
      "mimeTypes": [
        "text/html;profile=mcp-app"
      ]
    }
  },
  "resources": {
    "subscribe": false,
    "listChanged": false
  },
  "tools": {
    "listChanged": false
  }
}
```

The identifier and its settings survive intact. The **parent key is wrong**: `experimental`, where
the specification says `extensions`. A 2026-07-28 client reading this sees a server with no
extensions and an experimental map full of something it was told not to make assumptions about — and
it will be right to ignore it.

There is a second, sharper limit, and it is the one that decides how much of section 4 you can
actually run. `FastMCP` never passes an experimental map at all. From
`.venv/Lib/site-packages/mcp/server/fastmcp/server.py`, read 2026-09-04, the two places a server
starts:

```python
self._mcp_server.create_initialization_options(),
```

**Line by line:**

- No arguments. `create_initialization_options(notification_options=None, experimental_capabilities=None)`
  therefore fills both with defaults, and the default for the experimental map is `{}`.
- The line appears twice in that file — once on the stdio path, once on the HTTP path — and both are
  identical. There is no transport on which a `FastMCP` sends an extension claim.
- So on `mcp==1.29.1`, arm C above is reachable only by holding the low-level `Server` yourself. A
  server built the way Day 34 built `sutra_mcp` **cannot declare any extension at all** through a
  supported API.

That is not a thing to work around today. It is a thing to write down, which is exactly what
[6.1](../06-in-production/6.1-the-declaration-you-keep-in-git.md)'s module does.

## When it breaks

The break is matching an extension identifier loosely, and it fails in the direction that opens a
door rather than closing one.

A policy layer written to block Apps looks for the substring `apps`:

```python
if "apps" in str(declaration):
    refuse(server)
```

**Line by line:**

- `str(declaration)` flattens a nested dictionary into text, so the check no longer knows whether it
  matched a key, a value, or part of a tool description.
- `"apps"` is not in `io.modelcontextprotocol/ui`. The extension is called Apps and identified as
  `ui`, so this check lets the thing it was written to block straight through.
- It also matches a server whose knowledge-base resource is called `mobile-apps-faq`, which it then
  refuses for no reason. Wrong in both directions from one line.

The correct comparison is exact, against the identifier, in the right place:

```python
BLOCKED = frozenset({"io.modelcontextprotocol/ui"})
claimed = set(declaration.get("extensions") or declaration.get("experimental") or {})
if claimed & BLOCKED:
    refuse(server)
```

**Line by line:**

- `frozenset` of exact identifiers. Adding a second blocked extension is a new element, not a new
  branch.
- `declaration.get("extensions") or declaration.get("experimental") or {}` reads both places, because
  during the era overlap Sutra will meet servers on both sides of the pin. The `or` chain is ordered:
  the specification-correct key wins when both are present.
- `claimed & BLOCKED` is a set intersection, so it is exact and it reports *which* identifier matched,
  which is what the log line needs.

## In production

**What a professional writes instead:** a single constant per known extension identifier, in one
module, imported everywhere — never a literal at a call site and never a substring test. The
identifiers are long, they contain punctuation that is easy to mistype, and a typo produces silence
rather than an error because an unknown key is legal.

**What degrades at scale:** the number of extensions, and therefore the chance that two of them
interact. Tasks changes what a result looks like; Apps changes what a tool result may carry. A client
supporting several has to decide what to do when a server claims one it half-implements, and the only
scalable answer is the specification's own rule: *"If one party supports an extension but the other
does not, the supporting party **MUST** either revert to core protocol behavior or reject the
request."* Degrading is the default, not the exception path.

**The failure mode that only appears with real traffic:** the era overlap. Some servers on Sutra's
list will put extensions under `extensions` and some under `experimental`, and a fleet is mixed for
however long it takes everyone to upgrade. A reader that checks one key will silently miss half the
population, and the missed half is exactly the half running old software — the half a policy layer
most wants to know about.

**The review comment a senior engineer leaves:** *"this reads `capabilities['extensions']` and
nothing else. Half the servers we mount are on an SDK that has no such field and puts vendor keys in
`experimental`. Read both, prefer `extensions`, and log which one you found it in, because that field
name is the cleanest signal we have of which protocol era a server is really on."*

**The interview question:** *"how does MCP stop two vendors from defining the same capability?"* The
short honest answer: *"Naming. Core families get bare words because the specification owns them, and
everything else gets a reverse-DNS identifier — `io.modelcontextprotocol/ui` for Apps,
`io.modelcontextprotocol/tasks` for Tasks — with any prefix whose second label is
`modelcontextprotocol` or `mcp` reserved. They live in their own `extensions` map so a reader can
tell a standardised family from a vendor one at a glance. The practical trap is that the extension
called *Apps* is identified as `ui`, so any check written against the word `apps` matches nothing.
And on our pinned SDK there is no `extensions` field yet, so a claim lands in `experimental` — and the
high-level server class never sends that map at all, which means we currently cannot declare an
extension over the wire even if we wanted to."*
