# 1.2 — Nobody types the declaration

## One-line answer

The SDK writes your capability declaration for you by looking at which handlers you registered — and
`FastMCP`, the class Day 34 built on, registers all of them at construction, so **an empty
`FastMCP` server declares tools, resources and prompts before you have written a single one.**

## The story

A driving licence has the vehicle classes printed on the back.

Nobody at the counter asked you which classes you would like. You sat the test on a motorcycle, so
the motorcycle class is on the card. You did not sit the test for a heavy goods vehicle, so that
class is not on the card, and there was no form on which you could have requested it. The card is
generated from what you actually did.

That is the honest kind of licence, and it is the kind you want, because the card cannot claim
anything the tests did not back up.

Now imagine a licensing office that prints every class on every card by default, and only leaves one
off if somebody remembers to strike it out. The cards would look identical. The tests behind them
would not. And the first person to find out would be whoever handed a lorry to someone whose card
said they could drive it.

## The idea in plain language

In the MCP SDK there is no `declare_capabilities()` call and no `capabilities=` argument on a server.
The declaration is **derived**. The server looks at its own table of registered request handlers and
emits one family key for each kind of handler it finds.

That is a good design. A declaration you type by hand is a second source of truth, and a second
source of truth drifts. A declaration read off the handlers can only lie if the handlers lie.

The catch is that *which* class you build on decides how honest the derivation is, and the two
classes in this SDK behave completely differently:

| Class | What it is | When handlers appear |
| --- | --- | --- |
| `mcp.server.lowlevel.Server` | the protocol machinery, nothing else | only when you register one |
| `mcp.server.fastmcp.FastMCP` | a convenience layer with tool/resource/prompt managers | **all of them, at construction** |

`FastMCP` is what Day 34's
[1.1](../../../day-34-building-sutra-mcp-tools/parts/01-the-server-object/1.1-three-things-and-no-fourth.md)
told you to build `sutra_mcp/server.py` on, and it is the right choice for almost everything. It
writes your JSON schemas from type hints, it handles content blocks, it turns a docstring into a
description. What it also does — because it has to be ready for you to add a resource at any moment —
is register the handler for every family up front, empty managers and all.

The low-level `Server` derives an honest declaration. `FastMCP` derives one that is honest about the
*machinery* and dishonest about the *server*. Both are doing exactly what they were built to do, and
the second one is the reason section 3 of this day exists.

## Why Sutra needs it

`sutra_mcp/server.py` is a `FastMCP`. That is not going to change today, and it should not.

What changes today is that you find out what it currently tells strangers. On Day 34 `sutra_mcp`
had two tools and no resources and no prompts, and its declaration already said it did all three.
Day 35 then added resources and prompts, which made two of those three true by accident rather than
by decision. That is a strange way for a public contract to become correct.

Day 45's audit reads this declaration off every server Sutra mounts, `sutra-mcp` included, and
records it beside the provenance row. An audit that records a declaration nobody verified has
recorded a guess. So this day gives Sutra a module — `sutra_mcp/capabilities.py`, designed in
[6.1](../06-in-production/6.1-the-declaration-you-keep-in-git.md) — whose job is to state what the
server *intends* to declare and check it against what the SDK actually emits.

## The mechanism

Here is the derivation, copied from `.venv/Lib/site-packages/mcp/server/lowlevel/server.py` on
2026-09-04:

```python
def get_capabilities(
    self,
    notification_options: NotificationOptions,
    experimental_capabilities: dict[str, dict[str, Any]],
) -> types.ServerCapabilities:
    """Convert existing handlers to a ServerCapabilities object."""
    prompts_capability = None
    resources_capability = None
    tools_capability = None

    if types.ListPromptsRequest in self.request_handlers:
        prompts_capability = types.PromptsCapability(listChanged=notification_options.prompts_changed)

    if types.ListResourcesRequest in self.request_handlers:
        resources_capability = types.ResourcesCapability(
            subscribe=False, listChanged=notification_options.resources_changed
        )

    if types.ListToolsRequest in self.request_handlers:
        tools_capability = types.ToolsCapability(listChanged=notification_options.tools_changed)
```

**Line by line:**

- The docstring says it outright: *"Convert existing handlers to a ServerCapabilities object."* The
  handler table **is** the declaration. There is no other input.
- `if types.ListPromptsRequest in self.request_handlers` — the test is on the **`list`** handler of
  each family, not on the family's other methods. A server with a `prompts/get` handler and no
  `prompts/list` handler declares nothing, and a server with `prompts/list` and no `prompts/get`
  declares the whole family. That asymmetry is where a hand-rolled server most often goes wrong.
- `subscribe=False` is **hard-coded**. The low-level server never advertises resource subscriptions
  no matter what you registered, which is the finding Day 35's
  [4.2](../../../day-35-resources-and-prompts/parts/04-freshness/4.2-subscribing-with-nobody-on-the-line.md)
  already recorded from the other direction.
- `notification_options.*_changed` are the only values you can influence, and they default to
  `False`. They say whether the server will push a `listChanged` notification — a promise about
  future messages, not about methods.
- Nothing in this function looks at whether a manager is empty. A registered handler that returns
  `[]` forever is indistinguishable, from here, from one that returns four hundred tools.

Now the finding. `lab/declared.py`'s fourth arm constructs a `FastMCP` with nothing in it at all:

```python
print("\nD. an empty FastMCP - no tool, no resource, no prompt anywhere")
empty = FastMCP("empty")
print(json.dumps(declaration(empty._mcp_server), indent=2))
print("   handlers registered:", sorted(t.__name__ for t in empty._mcp_server.request_handlers))
```

**Line by line:**

- `FastMCP("empty")` takes only a name. No tool decorator is applied, no resource is added, no prompt
  is registered. This object is as empty as a `FastMCP` can be.
- `empty._mcp_server` is the low-level `Server` that `FastMCP` wraps. The underscore says it is
  private and you should not reach for it in project code — this is a lab whose entire subject is
  what the wrapper does to the thing underneath, so reaching in is the point.
- `declaration(...)` is the same function the first three arms used, so the comparison is fair: same
  call, same dump options, different server.
- Printing `request_handlers` alongside the declaration is what turns a surprise into an explanation.
  Without it you would see three families and have to guess why.

## When it breaks

The break is a client that trusts the declaration and skips the list, which is a perfectly reasonable
optimisation and the exact thing the declaration is supposed to enable.

A host connects to a freshly deployed `sutra-mcp`, reads `prompts` in the declaration, and puts a
"Prompts" tab in its sidebar. The user clicks it. `prompts/list` returns:

```text
{"jsonrpc":"2.0","id":3,"result":{"prompts":[]}}
```

An empty tab, with no error anywhere. The user reports that prompts are broken. Nothing is broken;
the server said it does prompts and it does — it has none. Two teams then spend an afternoon on a
problem whose entire content is that a constructor is eager.

The version of this that actually costs money is a filter. Day 40's allowlist can leave a family with
nothing in it for one caller and a full catalogue for another, so *"declared but empty"* is a real
and correct state that the client must be able to render. A client that treats it as a fault will
raise an alarm every time a permission is tightened.

The smallest fix is on the server: **do not let a declaration be an accident.** Decide which families
`sutra-mcp` intends to declare, write them down as data, and make a check fail when the emitted
declaration and the written-down one disagree. That is what
[6.1](../06-in-production/6.1-the-declaration-you-keep-in-git.md) builds and what `lab/gate.py`
enforces.

## In production

**What a professional writes instead:** a declaration that is asserted, not observed. One constant
listing the families the service intends to serve, one test that builds the server and compares. It
is four lines of test and it turns "we declare whatever the library felt like" into a decision with a
diff on it.

**What degrades at scale:** the cost of a wrong declaration goes up with the number of clients, and
none of it lands on you. Every host that reads `prompts` builds a tab, a menu entry or a cache key
for it. Removing that family later means every one of those clients has to notice —
[5.2](../05-failure-lab/5.2-the-family-that-went-away.md) is what that costs. Declaring a family you
do not serve is therefore not a harmless over-share; it is a promise you will have to withdraw.

**The failure mode that only appears with real traffic:** silent over-declaration plus a gateway.
Some deployments route by family — send everything `resources/*` to a read-only pool, everything
`tools/*` to a pool with write access. A server that declares `resources` and has none causes the
routing layer to provision and health-check a pool that will never serve a byte. Nobody sees a bug;
somebody sees a bill.

**The review comment a senior engineer leaves:** *"our declaration says we do prompts. We do not, and
we did not decide to say that — `FastMCP` registers all three families in its constructor and the
capability object is derived from the handler table. Put the intended families in a constant and add
the assertion; right now the public contract of this service is a side effect of a library's
convenience layer."*

**The interview question:** *"where does a server's capability declaration come from?"* The honest
answer: *"It is derived, not written. The SDK walks its own registered request handlers and emits one
key per family it finds — it even tests on the `list` handler specifically, so a family with a `get`
handler and no `list` handler declares nothing. The trap we hit is that the high-level wrapper we
build on registers every handler in its constructor, so a completely empty server already declares
tools, resources and prompts. We measured it: eight handlers registered from a one-argument
constructor, three families declared, nothing implemented. So we keep the intended family set as a
constant and fail the build when the emitted declaration disagrees with it, because otherwise our
public contract is decided by whichever library version we happen to have pinned."*
