# 2.2 — The request your SDK cannot send

## One-line answer

Grep the installed SDK for the four things this day's protocol depends on — `server/discover`,
`ttlMs`, `cacheScope`, `resultType` — and every count is **zero**, so on `mcp==1.29.1` the only place
a capability declaration exists is inside a legacy `initialize` reply, and everything else on this
page is design work for a pin that has not moved yet.

## The story

You photocopy last year's application form because the office has run out of the new ones.

You fill it in neatly. Every box is complete, the handwriting is careful, and you join the queue. The
clerk turns it over, looks at the back, and says there is no column here for the new reference number
— they added that column in April.

You cannot add a column. You can write the number in the margin and hope, you can go and find a
current form, or you can hand it in as it is and be told, correctly, that this is not the form they
accept. What you cannot do is make an old form into a new one by filling it in better. The paper
decides what fields exist.

## The idea in plain language

Sutra's `pyproject.toml` pins `mcp==1.29.1`. Days 32, 33 and 34 all recorded the same gap in
different words: the specification is at revision **2026-07-28**, and this SDK's
`LATEST_PROTOCOL_VERSION` is **2025-11-25**.

That gap has been a version number so far. This is the day it becomes a list of missing things,
because every one of them is this day's subject.

The four things sections 1 and 2 have been built on, and where each of them lives in the
specification:

| Thing | What it does | Where it is specified |
| --- | --- | --- |
| `server/discover` | the one request that returns a declaration | `/specification/2026-07-28/server/discover` |
| `ttlMs` | how long the declaration may be cached | `/specification/2026-07-28/server/utilities/caching` |
| `cacheScope` | who may share the cached copy | the same page |
| `resultType` | which shape of result this is | `/specification/2026-07-28/basic/index` |

Principle 8 says never invent an API. Day 34 already measured three of these from the other
direction. **Measure them again here, yourself, in the way that takes one command** — because a
finding you inherited is a claim, and a finding you reproduced is a fact.

## Why Sutra needs it

Because the module you write today, `sutra_mcp/capabilities.py`, has to be designed around a hole,
and you cannot design around a hole you have not put your hand into.

If `server/discover` existed on this SDK, `capabilities.py` would be almost nothing: a place to hang
an extension claim, and the SDK would do the rest. It does not exist, so the module's job changes.
It becomes the place where Sutra writes down **what it intends to declare**, so that the intention is
in version control and can be compared against what the library actually emits. That is a genuinely
different module, and [6.1](../06-in-production/6.1-the-declaration-you-keep-in-git.md) builds it.

The second reason is Day 45. The audit will ask every server for a declaration, and `sutra-mcp` will
be one of the servers it asks. An audit that reports *"sutra-mcp: could not discover"* without saying
why is a red row nobody can action. An audit that reports *"sutra-mcp: legacy era, declaration read
from the `initialize` reply, `server/discover` unimplemented — pinned SDK 1.29.1"* is a row with a
next step in it.

## The mechanism

One command, run against the installed package rather than against documentation:

```bash
cd .venv/Lib/site-packages/mcp
for s in "server/discover" "ttlMs" "cacheScope" "resultType" "DiscoverResult"; do
  printf '%-16s %s\n' "$s" "$(grep -rn "$s" . | wc -l)"
done
```

**Line by line:**

- `cd .venv/Lib/site-packages/mcp` — the installed package, not the source repository and not the
  documentation site. This is the code that will actually run, which is the only code whose absence
  proves anything.
- The five strings are chosen so that a hit would be unambiguous. `server/discover` and
  `DiscoverResult` are the method and its result type; `ttlMs`, `cacheScope` and `resultType` are
  field names that appear nowhere else in a JSON-RPC library.
- `grep -rn` recurses and numbers the lines, so a non-zero count is immediately followable. The count
  is what matters here; the line numbers are for the day the count stops being zero.
- `printf '%-16s %s\n'` pads the name to a fixed width so the five counts line up in a column. A
  ragged list of five numbers is a thing you have to read twice.
- `wc -l` on an empty grep gives `0` rather than an error, so a missing string and a present string
  produce the same shape of output. A check whose two outcomes look different is a check you can
  misread.

On 2026-09-04:

```text
server/discover  0
ttlMs            0
cacheScope       0
resultType       0
DiscoverResult   0
```

Five for five. And the version constants that explain it:

```bash
uv run python -c "from mcp.types import LATEST_PROTOCOL_VERSION as l; from mcp.shared.version import SUPPORTED_PROTOCOL_VERSIONS as v; print(l); print(v)"
```

**Line by line:**

- `LATEST_PROTOCOL_VERSION` comes from `mcp.types`; `SUPPORTED_PROTOCOL_VERSIONS` does **not** and
  must be imported from `mcp.shared.version`. Day 34's
  [5.2](../../../day-34-building-sutra-mcp-tools/parts/05-lifecycle/5.2-what-your-server-actually-answers.md)
  recorded the `AttributeError` that the obvious import raises.
- Both are printed rather than asserted, because the point here is the number, not a pass or a fail.
  The assertion belongs in `lab/gate.py` and in Day 34's, where it is already red on purpose.

```text
2025-11-25
['2024-11-05', '2025-03-26', '2025-06-18', '2025-11-25']
```

`2026-07-28` is not in that list, and the four features above are the four this day would have used.

There is one more measurement worth taking, because it explains the error message you get rather than
the one you expect:

```bash
uv run python -c "import typing; from mcp.types import ClientRequest; print(len(typing.get_args(ClientRequest.model_fields['root'].annotation)))"
```

**Line by line:**

- `ClientRequest` is a pydantic root model wrapping a **union** of every request type a client may
  send. `model_fields['root'].annotation` is that union; `typing.get_args` unpacks it into its
  members.
- Counting them is the whole point. When a `server/discover` message arrives, the SDK tries every
  member of this union and fails against each one, which is why the stderr line Day 34 captured says
  *"validation errors for ClientRequest"* and why the number in it is large.

```text
17
```

Seventeen request types, and `server/discover` is none of them. A message the union cannot match
becomes a `-32602 Invalid request parameters` — a reply about *parameters* for a problem with the
*method*. Day 34's 5.2 has the full transcript over a real pipe; there is no reason to send it twice.

**No pin is bumped here.** PyPI's current `mcp`, checked on 2026-09-04, is `2.1.1` and Day 32
verified that it speaks `2026-07-28`. Moving from `1.29.1` to `2.1.1` is a major-version change to
the library every file in `sutra_mcp/` imports, and Principle 14 says the plan is amended before the
code. A day pins only what it installs, and this one installs nothing.

## When it breaks

The break is writing code against the specification and discovering the gap at run time rather than
at design time.

You add a discovery call to Sutra's client using the name from the specification page:

```python
result = await session.send_request(types.ClientRequest(DiscoverRequest()), types.DiscoverResult)
```

**Line by line:**

- `DiscoverRequest` and `DiscoverResult` are the natural names, and they are what the specification's
  schema calls them.
- Neither exists in `mcp==1.29.1`. The grep above found zero occurrences of `DiscoverResult`, so this
  line does not reach a server at all.

It fails at import:

```text
ImportError: cannot import name 'DiscoverRequest' from 'mcp.types'
```

That is the good failure — loud, immediate, at the top of the file. The bad version is the one where
you hand-build the JSON instead, because that *does* reach the server and comes back as
`-32602 Invalid request parameters`, which reads like your parameters were wrong and sends you to
inspect an envelope that was correct.

The smallest fix is to make the gap explicit rather than to route around it: one constant naming the
revision Sutra targets, one assertion that the installed SDK supports it, and that assertion left
**red** with a comment saying why it is red. Day 34's build brief already asked for that assertion.
This part is the reason it must not be quietly deleted when someone finds it failing.

## In production

**What a professional writes instead:** a capability layer with two implementations behind one
function — `discover(server_url)` that sends `server/discover` when the SDK has it, and falls back to
reading the declaration out of an `initialize` reply when it does not. The caller sees a family set
either way. The era is recorded in the result, not raised as an exception, because both eras are
normal for years.

**What degrades at scale:** nothing about the request; everything about the fleet. A pin that is one
revision behind is fine for one service and expensive for forty, because the fallback path has to be
maintained in every one of them until the last is upgraded. The number worth tracking is not *"are we
current"* but *"how many of our services are on the old path"*, which is a dashboard, not a ticket.

**The failure mode that only appears with real traffic:** a partial upgrade. Bump the SDK on the
client and not the server, and the client starts sending `server/discover` to servers that answer
`-32602`. Because the fallback is meant to trigger on *any* non-modern error, it will trigger — and
then a genuinely malformed request, which also earns `-32602`, will silently take the legacy path and
appear to work. The rule the specification gives is exact: fall back on anything that is **not** a
recognised modern error, and treat a recognised modern error as proof the server is current.

**The review comment a senior engineer leaves:** *"the ticket says we implement `server/discover`. We
do not, and we cannot: the pinned SDK has zero occurrences of the string, `DiscoverResult` does not
exist, and its `LATEST_PROTOCOL_VERSION` is a revision behind. Do not hand-roll the JSON to make the
ticket true — write the fallback that reads capabilities out of the `initialize` reply, leave the
version assertion red with a comment, and open the SDK bump as its own decision with its own
migration."*

**The interview question:** *"what do you do when the SDK is behind the spec?"* The honest answer:
*"Measure the gap and write it down rather than route around it. We grepped the installed package for
the four things our design depended on — the discovery method, the two cache fields and the result
type — and got zero for all four, and the SDK's supported-versions list confirmed why. So we did
three things. We kept the design specification-correct, so the day the pin moves it is a dependency
change and not a rewrite. We wrote the fallback that reads the declaration out of the legacy
handshake reply, because both eras will be live for a long time. And we left an assertion in the
suite that the SDK supports our target revision, failing, with a comment explaining that neither
lowering the target nor deleting the assertion is allowed. The one thing we did not do was hand-build
the JSON, because a request the server's own validator cannot match comes back as 'invalid
parameters', and that error sends the next person to look in the wrong place."*
