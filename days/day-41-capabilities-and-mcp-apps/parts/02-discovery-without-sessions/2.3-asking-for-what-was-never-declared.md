# 2.3 — Asking for what was never declared

## One-line answer

Call a family a server never declared and you get `-32601 Method not found` — a **third** kind of no,
distinct from the tool-level `isError` and the argument-level `-32602`, and the only one that means
*stop asking, this will never work.*

## The story

The lift in the building has buttons for the ground floor up to six, and one of them has a strip of
tape over it.

The taped one is the fifth floor. Something is wrong with the landing and nobody is allowed off there
until it is fixed, so the button is disabled and the tape tells you why without anybody having to
stand there and explain.

Now the interesting one. There is no button for the seventh floor, and there is no tape either. The
building has six floors. A visitor who wants the seventh does not press anything and wait; they look
at the panel, count, and go and ask someone whether they have the right address.

Tape means *not right now*. A missing button means *not here, not ever, you want a different
building*. Two very different pieces of information, from the same panel, and a visitor who cannot
tell them apart will either stand in a lift that is never going to move or walk out of a building that
does have their floor.

## The idea in plain language

By the end of Day 34 you had two kinds of no, and they were carefully separated:

- **`isError: true`** — the tool ran and could not do the job. A successful call, an unsuccessful
  outcome, and a message written for the model to act on
  ([4.1](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.1-the-tool-said-no.md)).
- **A JSON-RPC `error`** — the call never happened. Nothing ran
  ([4.2](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.2-the-call-never-happened.md)).

The second kind has codes in it, and the codes are not interchangeable. Three of them show up on this
day, and the difference between them is the difference between *fix your request*, *fix your client*
and *go somewhere else*:

| Code | Name | What actually happened | What the caller should do |
| --- | --- | --- | --- |
| `-32602` | Invalid params | the method exists; your arguments do not fit | fix the arguments and retry |
| `-32601` | Method not found | **the method does not exist here** | stop; this family is not served |
| `-32021` | Missing required client capability | the server needs something you did not declare | declare it and retry |

`-32601` is the one this part is about, and it is the only one of the three with **no useful retry**.
An argument can be corrected. A missing client capability can be added. A method that does not exist
on the other end will not start existing because you asked twice.

That is why the capability declaration is worth reading. It is the panel with six buttons on it. A
client that reads it never sends a request that can only earn `-32601`, and a client that does not
read it will send that request every time a user clicks the wrong thing.

## Why Sutra needs it

Sutra mounts servers it did not write. Day 40's filtering module decides which *tools* Sutra will
allow; nothing so far decides which *families* Sutra will ask about.

Concretely: `sutra/mcp/client.py` from Day 33 has `list_tools`. Days 42 and 44 will want the resource
and prompt equivalents, and the moment they exist, Sutra will be calling three list methods against
every mounted server. Some of those servers serve one family. Every call to the other two comes back
`-32601`, and if the client's answer to that is a caught exception and an empty list, then two things
that must stay separate have been flattened into one: *this server has no prompts* and *this server
does not do prompts*.

The first is a normal state that may change tomorrow. The second is a fact about the deployment. Day
45's audit needs to record the second and would be actively misled by the first.

## The mechanism

A server with exactly one family, and a client that asks for two. From `lab/undeclared.py`:

```python
server: Server[Any] = Server("tools-only")


@server.list_tools()
async def _list_tools() -> list[Tool]:
    return [Tool(name="lookup_ticket", description="Look up one ticket.", inputSchema={"type": "object"})]


@server.call_tool()
async def _call_tool(name: str, arguments: dict[str, Any]) -> list[TextContent]:
    return [TextContent(type="text", text=f"{name} ran")]
```

**Line by line:**

- `Server`, the low-level class, not `FastMCP`. [1.2](../01-what-a-server-declares/1.2-nobody-types-the-declaration.md)
  showed that `FastMCP` registers every family's handlers in its constructor, so a `FastMCP` cannot
  produce a `-32601` for `prompts/list` at all. To see the error you need a server that genuinely
  lacks the handler.
- Two decorators, one family. `list_tools` is what puts `tools` in the declaration;
  `call_tool` is what makes the family useful. Neither registers anything for prompts.
- `list[TextContent]` as the return type is what the low-level API expects from a tool handler; the
  wrapping into a `CallToolResult` happens above it. Day 34's
  [3.3](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.3-one-call-one-result.md) is
  where that shape was taught.

And the client, running in the same process:

```python
async with create_connected_server_and_client_session(server) as client:
    result = await client.initialize()
    declared = result.capabilities.model_dump(by_alias=True, exclude_none=True)
    print("families :", sorted(k for k in declared if k != "experimental"))

    try:
        await client.list_prompts()
    except McpError as err:
        print(f"prompts/list -> error {err.error.code}: {err.error.message}")
```

**Line by line:**

- `create_connected_server_and_client_session` wires a client and a server together over in-memory
  streams. No subprocess, no socket, no port — which is what makes this a check that runs anywhere,
  including in CI on a machine with no network.
- `await client.initialize()` is the **legacy handshake**. On a 2026-07-28 server there would be no
  such call and the declaration would come from `server/discover`;
  [2.2](2.2-the-request-your-sdk-cannot-send.md) is why this is the only route available on
  `mcp==1.29.1`. The declaration is the same object either way.
- `k != "experimental"` filters the one key that is not a family, exactly as
  [2.1](2.1-one-question-instead-of-three.md)'s `families()` function did with an explicit list.
- `except McpError` and not `except Exception`. `McpError` is the SDK's wrapper for an error that
  came back **from the peer**; a bare `except` here would also swallow a local timeout or a broken
  stream, which are entirely different problems and must not be reported as "no prompts".
- `err.error.code` and `err.error.message` are the JSON-RPC fields, reached through the wrapper. The
  code is the part a program branches on; the message is the part a human reads. Branching on the
  message is how a client breaks when a library reworks its strings.

Run it:

```bash
uv run python days/day-41-capabilities-and-mcp-apps/lab/undeclared.py
```

**Line by line:**

- From the repository root. **Zero generations, no network, no subprocess.**

On 2026-09-04:

```text
declared : {'experimental': {}, 'tools': {'listChanged': False}}
families : ['tools']
tools/list -> ok: ['lookup_ticket']
prompts/list -> error -32601: Method not found
```

Four lines, and the third and fourth are the whole lesson. The declared family answered. The
undeclared family did not merely return nothing — it returned a code that says the method is not
here.

## When it breaks

The break is the catch that turns a fact into a shrug:

```python
try:
    prompts = (await client.list_prompts()).prompts
except Exception:
    prompts = []
```

**Line by line:**

- `except Exception` catches four unrelated things: `-32601` from a server without the family,
  `-32602` from a malformed request, a local read timeout, and a transport that died mid-call.
- All four become `[]`. The caller sees an empty list and has no way to ask which of the four
  happened, because the information was destroyed at the point it was available.
- The one that hurts is the timeout. A slow server produces an empty prompt list, the agent proceeds
  without the prompt it needed, and the user gets an answer built from less context than intended —
  with nothing in any log to say so. This is Principle 10's failure mode exactly: an error was
  swallowed and a result was fabricated in its place.

What the caller actually sees when it is not swallowed:

```text
mcp.shared.exceptions.McpError: Method not found
```

with `err.error.code == -32601` on the object. That is a fact worth keeping: it belongs in the
server's record beside its URL, and it belongs in the audit.

The smallest fix is two branches instead of one:

```python
if "prompts" not in families:
    prompts = []                      # the server does not serve this family, and said so
else:
    prompts = (await client.list_prompts()).prompts   # let every error surface
```

**Line by line:**

- The first branch never sends a request. That is the saving the declaration exists for, and it is
  also what makes the second branch meaningful.
- The second branch has no `try` at all. Once the declaration says the family exists, **any** error
  from it is a real finding — a deploy that removed the family, a routing bug, a dead instance — and
  Principle 10 says the layer that cannot fix it must not be the layer that hides it.
- `families` is the set from [2.1](2.1-one-question-instead-of-three.md), fetched once and cached, so
  this costs nothing per call.

## In production

**What a professional writes instead:** a thin wrapper that maps JSON-RPC codes to named outcomes
before anything else sees them — `MethodNotServed`, `BadArguments`, `MissingClientCapability` — and
lets everything unrecognised propagate. The rest of the codebase then branches on a name, and the day
a new code appears in the reserved range it surfaces as an unhandled error rather than as silence.

**What degrades at scale:** the cost of the requests you should not have sent. One client asking three
families of forty servers on every start-up sends eighty pointless requests, most of which will be
answered by a gateway that has to route them somewhere before rejecting them. The declaration turns
eighty into zero, and the difference is visible on somebody's dashboard as an error rate that never
goes to zero and has no owner.

**The failure mode that only appears with real traffic:** `-32601` from a server that *does* serve the
family. Day 32's
[2.2](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md)
established that any instance may answer any request, so during a rolling deploy that adds `prompts`,
a client that discovered against a new instance can be answered by an old one. The reply is
indistinguishable from a permanent absence. The only defence is that capability changes are additive
and short-lived, and that a `-32601` for a family the declaration promised is logged loudly rather
than cached as a new fact.

**The review comment a senior engineer leaves:** *"this catches `Exception` around `list_prompts` and
returns an empty list. That branch is currently catching read timeouts and reporting them as 'this
server has no prompts', which is why last week's incident took an afternoon — the agent ran without
its prompt and nothing anywhere said it had. Check the capability set before you ask, and let
everything else raise."*

**The interview question:** *"a client calls a method the server does not implement. What comes back,
and what should the client do?"* The answer: *"`-32601 Method not found`, and the client should stop
asking rather than retry — it is the one error in this family with no useful retry, unlike `-32602`
where you fix the arguments or `-32021` where you add the capability and try again. The real answer is
that it should not have sent the request: the server's capability declaration names the families it
serves, so a client that reads it once knows which requests can never succeed. Where I have seen this
go wrong is a broad `except` around the list call that turns `-32601` into an empty list — because
then a read timeout also becomes an empty list, and an agent silently runs with less context than it
was meant to have, with nothing in the logs."*
