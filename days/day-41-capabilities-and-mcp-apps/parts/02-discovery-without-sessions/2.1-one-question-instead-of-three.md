# 2.1 — One question instead of three

## One-line answer

Without a session there is no moment at which a server introduces itself, so `server/discover` is the
request that carries the introduction — and its **capability half** is what saves a client from
probing `tools/list`, `resources/list` and `prompts/list` to find out which of them will even answer.

## The story

A thick appliance manual has an index at the front, one page long.

You want to know whether this model can be connected to your home network. Without the index you open
the manual and start turning pages: chapter one, installation; chapter two, controls; chapter three,
cleaning. You reach the back cover having read a third of it, and you now know there is no chapter on
networking — which is the answer, obtained the expensive way.

With the index you read seven chapter titles and you are done. And the index is not a summary of the
manual. It does not tell you *how* to connect to the network. It tells you *whether there is a
chapter about it*, which is a much smaller question and the only one you were asking.

The manual with no index is not missing information. It is missing the one page that tells you where
the information is not.

## The idea in plain language

Day 32's
[2.4](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.4-server-discover-the-optional-question.md)
introduced `server/discover` as the answer to a **version** question: which revisions does this server
speak, and should I retry at a different one. It also established the asymmetry — servers **MUST**
implement it, clients **MAY** call it — and that the server remembers nothing afterwards.

This part is about the other field in the same reply. Alongside `supportedVersions` sits
**`capabilities`**, and it is the declaration from
[1.1](../01-what-a-server-declares/1.1-the-programmes-on-the-dial.md), delivered in one request.

Why that matters is arithmetic. There are three list methods a client might want to try. Without the
declaration, finding out which families a server serves costs three requests, and up to three of them
fail:

| Approach | Requests | What the failures look like |
| --- | --- | --- |
| probe each family | 3 | up to three `-32601 Method not found` replies |
| ask once | 1 | one reply naming exactly the families that exist |

And the specification says so in as many words
(`https://modelcontextprotocol.io/specification/2026-07-28/server/discover`, read 2026-09-04):

> *"a client can present the capabilities a server supports from a single `server/discover` response
> instead of probing with separate `tools/list`, `prompts/list`, and `resources/list` requests."*

Read that carefully, because it is narrower than it first looks. The saving is not *"one request
instead of three"* for a client that was going to call all three anyway — a client that wants every
catalogue still has to fetch every catalogue. The saving is for a client that wants to know **what
exists**, which is a different question, asked at a different moment, usually by something that is
not the agent: a settings screen, an inventory job, an audit.

One more field in the same reply, and one warning attached to it. The reply carries
`_meta['io.modelcontextprotocol/serverInfo']`, the server's self-reported name and version, and the
specification is blunt about what that is worth:

> *"`serverInfo` is self-reported by the server and is not verified by the protocol… Clients
> **SHOULD NOT** use it to change their behavior, and **SHOULD NOT** rely on it for security
> decisions."*

It is for a log line and a screen. It is not identity. Day 32's
[4.3](../../../day-32-mcp-stateless-core/parts/04-governance-and-registry/4.3-a-name-that-proves-its-publisher.md)
is where a name that actually proves something comes from.

## Why Sutra needs it

Day 45 audits every MCP server `sutra-core` talks to. The audit's first question about each one is
*what does this server claim to be, and what families does it claim to serve*, and the answer wants to
be a single artefact you can store, diff between runs, and attach to the provenance row.

Three probe requests do not give you that. They give you three replies, two of which may be errors,
and a human then has to reconstruct the declaration from what did and did not fail. One
`server/discover` reply is the artefact — and because it is cacheable, running the audit against forty
servers does not cost forty times three requests.

There is a second use arriving on Day 43. When `sutra_mcp` is deployed behind a URL with several
instances, `server/discover` is the cheapest thing that says what a given deployment currently is. It
is not a health check — a health check tells you the process is alive — but it is the request that
tells you *which build* answered, which during a rolling deploy is the more useful of the two.

## The mechanism

The whole exchange, copied from the specification page on 2026-09-04. The request first:

```json
{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

Note that the request itself carries a declaration — the client's, from
[1.4](../01-what-a-server-declares/1.4-the-client-declares-too.md). Even the request that asks *"what
can you do"* has to say what the asker can do, because there is no earlier message in which it could
have said so.

And the reply:

```json
{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "tools": {},
      "resources": {}
    },
    "_meta": {
      "io.modelcontextprotocol/serverInfo": { "name": "ExampleServer", "version": "1.0.0" }
    },
    "instructions": "This server provides weather and resource utilities.",
    "ttlMs": 3600000,
    "cacheScope": "public"
  }
}
```

Four things to read off it, in order of how often they are missed.

**`capabilities` here has no `prompts` key.** That is the whole answer to *"does this server do
prompts"*, and it is an absence rather than a `false`. A client parsing this must treat a missing key
as "no", which is why the family test is `in`, never `== True`.

**`ttlMs: 3600000` and `cacheScope: "public"`.** The declaration is cacheable exactly like the lists
in Day 32's
[3.3](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md), and
those two fields are why *"ask first"* does not become *"ask every time"*. `"public"` means a shared
proxy may serve one caller's copy to another, which is safe for a declaration in a way it is not
always safe for a tool list.

**`resultType: "complete"`.** Every result in this revision carries it; Day 32's 2.4 explained the
other value.

**`instructions`.** Optional plain-language guidance meant for a model. It is the one field in the
reply that costs context rather than bytes, because a client that pastes it into a system prompt is
paying for it on every turn.

Here is the client-side shape that follows, written the way Sutra's audit will want it:

```python
FAMILIES = ("tools", "resources", "prompts", "logging", "completions", "tasks")


def families(discover_result: dict[str, Any]) -> frozenset[str]:
    """The core families a server declares, as a set, from one server/discover reply."""
    declared = discover_result.get("capabilities") or {}
    return frozenset(name for name in FAMILIES if name in declared)
```

**Line by line:**

- `FAMILIES` is an explicit tuple, not `declared.keys()`. Taking the keys would sweep up `experimental`
  and `extensions`, which are not families and must not be treated as ones —
  [1.3](../01-what-a-server-declares/1.3-an-extension-is-a-capability-with-a-surname.md) is why they
  live in a separate namespace.
- `discover_result.get("capabilities") or {}` handles both a missing key and an explicit `null`. A
  server that returns no capabilities at all is legal — it serves nothing but `ping` — and it must
  produce an empty set rather than an exception.
- `name in declared` and never `declared[name] is True`. A family's value is a settings object; the
  truth is in the key existing. `{"tools": {}}` is a server with tools.
- The return is a `frozenset`, so the result can be a dictionary key, cached beside the server URL,
  and compared between audit runs with a plain `!=`.

## When it breaks

The break is calling `server/discover` and getting nothing that looks like a reply, because the server
on the other end is a revision behind and has never heard of the method.

That is not hypothetical for Sutra — it is what `sutra_mcp` itself does today, which is
[2.2](2.2-the-request-your-sdk-cannot-send.md)'s entire subject. Sent over stdio to a server built on
`mcp==1.29.1`, the request comes back as:

```text
{"jsonrpc":"2.0","id":1,"error":{"code":-32602,"message":"Invalid request parameters","data":""}}
(stderr) Failed to validate request: 31 validation errors for ClientRequest
```

`-32602` is *Invalid params*, which is a strange thing to say about a request whose params were
copied verbatim from the specification. What actually happened is that the SDK tried to fit the
message into its union of known client requests and failed against every member, so the nearest error
it had was "your parameters are wrong". Day 34's
[5.2](../../../day-34-building-sutra-mcp-tools/parts/05-lifecycle/5.2-what-your-server-actually-answers.md)
measured this first and it has not changed.

The smallest fix is not on the server, because the pin cannot be fixed here. It is on the client, and
the specification names it: on stdio, a client that must talk to both eras **SHOULD** send
`server/discover` first and treat anything that is not a recognised modern error as a legacy server,
then fall back to `initialize`. The probe is designed to fail informatively. A client that treats a
failed probe as a dead server has thrown away the fallback it was for.

## In production

**What a professional writes instead:** one `server/discover` per server per process, cached under the
server's URL with the `ttlMs` the server returned, re-fetched when a request fails with a version or
capability error rather than on a timer. The parsed result is stored as two values — the family set
and the extension set — because those are what every later decision actually consults.

**What degrades at scale:** a client with forty mounted servers that probes each one on start-up pays
forty round trips before it can answer its first question. The fix is not to skip the probe; it is to
make start-up not depend on it — mount lazily, discover on first use, and treat the cached
declaration as warm state that a restart may legitimately lose.

**The failure mode that only appears with real traffic:** a proxy honouring `cacheScope: "public"`
across an authorisation boundary. A declaration is usually the same for everyone, but a server whose
families differ by caller — one that hides the `tools` family entirely from an unauthenticated caller
— must send `"private"`, and Day 34's
[3.1](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.1-the-list-and-who-may-keep-it.md)
already flagged that this is a security field wearing a performance field's clothes. A shared cache
plus the wrong scope means one caller's view of a server is served to another.

**The review comment a senior engineer leaves:** *"the audit calls `tools/list`, `resources/list` and
`prompts/list` against every server and records which ones threw. That is three requests and two
exceptions to learn what one `server/discover` reply states directly, and the record you end up with
is a list of failures rather than a declaration. Ask once, store the reply, and let a `-32601`
afterwards be a real finding instead of the normal case."*

**The interview question:** *"you have a server URL and nothing else. How do you find out what it can
do?"* The answer: *"One request: `server/discover`. Servers must implement it and clients may skip it,
and it returns the supported protocol versions, the capability declaration and the server's
self-reported identity in one reply, with `ttlMs` and `cacheScope` on it so I am not paying for it
again. The capability half is the part that saves work — it names the families that exist, so I do not
probe `tools/list`, `resources/list` and `prompts/list` and read three errors to learn the same thing.
Two cautions I would state up front: `serverInfo` is self-reported and the spec says not to make
security decisions on it, and the whole thing is a hint rather than a contract, because the next
request can land on a different instance mid-deploy."*
