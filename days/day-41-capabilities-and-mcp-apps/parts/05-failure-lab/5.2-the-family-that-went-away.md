# 5.2 — 💥 The family that went away

## One-line answer

Removing the last prompt from a server removes the whole `prompts` **family**, and a client holding a
cached declaration gets `-32601 Method not found` instead of the empty list or the retirement message
a removed *tool* would have produced — a bigger, blunter failure than Day 34's, and it needs two
deployments for a different reason.

## The story

The post office near you used to renew passports, and you have been there twice.

The third time you take an afternoon off, carry the folder of documents across town, and the man at
the window tells you they stopped doing passports in March. Not *the forms have run out*. Not *the
officer is on leave*. They do not do it here any more — it moved to two offices in the city and this
is not one of them.

There is a difference between a service that cannot help you today and one the office no longer
provides, and you can hear it in the answer. The first sends you back tomorrow. The second sends you
somewhere else entirely, and if the man had said *"nothing available today"* out of politeness you
would have come back tomorrow, and the day after that.

## The idea in plain language

Day 34's
[6.1](../../../day-34-building-sutra-mcp-tools/parts/06-in-production/6.1-the-tool-you-deleted-is-still-called.md)
taught the removal of a **tool**: the name disappears from `tools/list`, clients holding a cached list
keep calling it, and the answer is two deployments — keep the name and return a retirement message,
wait out the TTL, then delete. Day 35's
[4.3](../../../day-35-resources-and-prompts/parts/04-freshness/4.3-the-list-that-outlived-the-deploy.md)
taught the same thing for a **resource**.

This part is a level up. Remove the last member of a family and, because
[1.2](../01-what-a-server-declares/1.2-nobody-types-the-declaration.md) showed the declaration is
derived from registered handlers, the **family** disappears with it. Three things then change at once:

| | Removing one tool | Removing the whole family |
| --- | --- | --- |
| What the catalogue says | the name is gone from a list that still works | the list method itself is gone |
| What the caller gets | `isError: true`, *"Unknown tool: X"* | `-32601 Method not found` |
| Who sees an error | nobody counting JSON-RPC errors | everybody |
| Can the model recover? | yes — it reads the message and picks another tool | no — nothing ran, there is no message for it |
| What the declaration said | unchanged, still correct | **changed, and every cached copy is now wrong** |

The last row is the one that makes this its own failure rather than a bigger version of Day 34's. A
removed tool leaves the declaration untouched, so a client's cached *declaration* stays accurate even
while its cached *list* goes stale. A removed family invalidates the declaration itself — and the
declaration is the thing clients cache hardest, because it is small, it is cacheable with `ttlMs`, and
it is supposed to be the stable fact about a server.

## Why Sutra needs it

Because Sutra will do this, and there is a specific plausible day.

`sutra_mcp/prompts.py` from Day 35 holds the house's prompt cards. Day 42 exposes the whole desk agent
over MCP with `to_mcp_server`, and Day 43 reshapes the server for deployment. It is entirely
reasonable that somewhere in there somebody decides the prompt cards belong to the agent rather than to
the server and deletes `register_prompts(server)` from `build_server()`. One line. It removes a
family.

Everything mounting `sutra-mcp` that read the declaration and built something around `prompts` then
gets `-32601` for the length of whatever TTL it cached. Nothing in Sutra's own tests would catch it,
because Sutra's tests call the server they just built.

Day 45's audit is where this is meant to be caught, and the check is exactly the one
[6.1](../06-in-production/6.1-the-declaration-you-keep-in-git.md) builds: the intended family set,
written down, compared against what the server emits.

## The mechanism

Three servers that differ only in which handlers are registered. From `lab/stale.py`:

```python
def before() -> Server[Any]:
    """Yesterday's build: tools and prompts, both declared and both implemented."""
    server: Server[Any] = Server("sutra-mcp")

    @server.list_tools()
    async def _list_tools() -> list[Tool]:
        return [TOOL]

    @server.list_prompts()
    async def _list_prompts() -> list[Prompt]:
        return [PROMPT]

    @server.get_prompt()
    async def _get_prompt(name: str, arguments: dict[str, str] | None) -> GetPromptResult:
        return GetPromptResult(
            messages=[PromptMessage(role="user", content=TextContent(type="text", text="triage it"))]
        )

    return server
```

**Line by line:**

- The low-level `Server` again, for
  [1.2](../01-what-a-server-declares/1.2-nobody-types-the-declaration.md)'s reason: on `FastMCP` every
  family is registered by the constructor, so a family cannot be removed at all and this failure is
  invisible.
- `@server.list_prompts()` is what puts `prompts` in the declaration. Deleting this one decorator is
  the entire deployment being modelled.
- `@server.get_prompt()` is the family's other method. Note that removing **only** this one would
  leave `prompts` declared and `prompts/get` broken — the over-declaration from
  [3.1](../03-declared-versus-implemented/3.1-a-promise-not-a-proof.md), reached by a different route.
- `GetPromptResult` wrapping a `PromptMessage` is the shape Day 35's
  [3.3](../../../day-35-resources-and-prompts/parts/03-the-card/3.3-what-a-prompt-hands-back.md)
  taught: a prompt hands back messages, not a string.

The one-deployment removal, and the survivable version:

```python
def after_one_deploy() -> Server[Any]:
    """Today's build with both prompt handlers deleted in a single deployment."""
    server: Server[Any] = Server("sutra-mcp")

    @server.list_tools()
    async def _list_tools() -> list[Tool]:
        return [TOOL]

    return server


def after_first_of_two() -> Server[Any]:
    """The first of two deployments: the family stays, its one member is retired in place."""
    server = before()

    @server.list_prompts()
    async def _list_prompts() -> list[Prompt]:
        return []

    @server.get_prompt()
    async def _get_prompt(name: str, arguments: dict[str, str] | None) -> GetPromptResult:
        return GetPromptResult(
            messages=[
                PromptMessage(
                    role="user",
                    content=TextContent(
                        type="text",
                        text=f"The prompt {name!r} was retired. Ask the desk agent directly.",
                    ),
                )
            ]
        )

    return server
```

**Line by line:**

- `after_one_deploy` is built from scratch rather than from `before()`, because you cannot un-register
  a handler in this SDK. That is not a lab limitation — it is what a deployment is: a different
  process, built from different source.
- `after_first_of_two` **re-registers** both prompt handlers over `before()`'s, which the SDK allows
  because `request_handlers` is a dictionary and the later decorator wins. That is a lab convenience
  standing in for editing the source, and the effect is the one that matters: the family key is still
  in the declaration.
- `return []` from `list_prompts` — the catalogue is empty and the family still exists. That is the
  intermediate state the whole two-deploy procedure needs, and it is exactly the *declared but empty*
  state [1.2](../01-what-a-server-declares/1.2-nobody-types-the-declaration.md) warned a client not to
  treat as a fault.
- The retirement message is a **prompt result**, not an error. A client asking for a prompt that used
  to exist gets something it can render and a human can read, which is the same discipline Day 34's
  6.1 applied to a retired tool.
- `{name!r}` puts the requested name in quotes so a reader can see exactly what was asked for. `!r` and
  not `{name}` because a name with a trailing space is otherwise invisible in the message.

```bash
uv run python days/day-41-capabilities-and-mcp-apps/lab/stale.py
uv run python days/day-41-capabilities-and-mcp-apps/lab/stale.py --two-deploys
```

**Line by line:**

- From the repository root. **Zero generations, no network, no subprocess** — client and server run in
  one process over memory streams.
- The first command is the mistake; the second is the procedure. Both must be run, because the whole
  argument is the difference between two outputs.

On 2026-09-04, the one-deployment arm:

```text
--- the build every cached declaration describes
    declares : ['prompts', 'tools']
    prompts/get -> ok: triage it
--- the whole family removed in one deployment
    declares : ['tools']
    prompts/get -> error -32601: Method not found
```

And the two-deployment arm:

```text
--- the build every cached declaration describes
    declares : ['prompts', 'tools']
    prompts/get -> ok: triage it
--- deploy 1 of 2: family kept, member retired
    declares : ['prompts', 'tools']
    prompts/get -> ok: The prompt 'triage_note' was retired. Ask the desk agent directly.
--- deploy 2 of 2: family removed, one TTL later
    declares : ['tools']
    prompts/get -> error -32601: Method not found
```

Read the middle row of the second arm. `declares` is **unchanged**, so every cached declaration in
every client is still accurate. The call still succeeds. The answer is a sentence a human can act on.
Then, one TTL later — long enough that no client can still be holding the old declaration — the family
goes, and the `-32601` that follows is correct rather than surprising, because by then nobody is asking.

## When it breaks

The break is doing the second deployment without waiting, or without knowing what to wait for.

Day 34's build brief asked you to choose `sutra_mcp`'s `ttlMs`. This is the day that number acquires a
second meaning: it is not only how long a client may keep a list, it is **how long you must wait
between the two deployments**. Ship the second one early and clients that cached under the old
declaration meet `-32601` on a family their declaration promises.

What that looks like on the client, unswallowed:

```text
mcp.shared.exceptions.McpError: Method not found
```

with `err.error.code == -32601`. And the reason it is worse than a stale tool name: a stale tool name
comes back as `isError: true` with a message, which the model reads and routes around
([Day 34](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.1-the-tool-said-no.md)).
A `-32601` means nothing ran. There is no message for the model, no `isError` to inspect, and whatever
the client does next it does without any information from the server.

The second break is a client that treats `-32601` as new truth and updates its cached declaration.
That is the wrong lesson to learn from one reply, because Day 32's
[2.2](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md)
established that any instance may answer any request: during a rolling deploy the very next request may
reach an instance that still has the family. A `-32601` against a declared family is a signal to
re-discover, not a fact to cache.

The smallest fix is a rule with a number in it: **withdraw in two deployments, and the gap between
them is at least the longest `ttlMs` you have ever sent.**

## In production

**What a professional writes instead:** a deprecation entry with a date, not a deletion. The family
stays, the catalogue empties, the members return a retirement message naming the replacement, and a
calendar entry a TTL later removes the handlers. The second deployment is a separate pull request so
that it can be reviewed on its own and reverted on its own.

**What degrades at scale:** the coordination. One client is a conversation. Forty clients you do not
control is a published deprecation window, and the window has to be at least the longest TTL any of
them might be holding — which is a number you chose, months earlier, and which is therefore worth
choosing small. A short TTL costs requests; a long one costs your ability to change anything.

**The failure mode that only appears with real traffic:** the family that comes back. Somebody
withdraws `prompts`, a caller complains, and it is restored in a hotfix. Clients now hold three
different declarations depending on when they last discovered, and the ones that cached during the gap
will not ask again until their TTL expires. Restoring a capability is not free either, and the same
two-step applies in reverse: add the family, wait, then advertise members.

**The review comment a senior engineer leaves:** *"this deletes `register_prompts` from
`build_server()` in one commit. That removes the whole `prompts` family, not just the prompt — every
client holding our declaration will get `-32601` on a family we told them we had, and unlike a removed
tool there is no message for the model to route around. Two deployments: empty the list and return a
retirement message now, delete the handlers after the longest TTL we have ever advertised, and say
which number that is in the commit message."*

**The interview question:** *"you need to remove a feature from a server other people depend on. How?"*
The answer: *"In two deployments, and which two depends on whether I am removing a member or a whole
capability family. Removing one tool leaves the family intact, so a stale client gets `isError: true`
with a message and the model can route around it. Removing the last prompt removes the `prompts` family
— the declaration is derived from which handlers are registered — so a client holding a cached
declaration gets `-32601 Method not found`, nothing ran, and there is no message for anyone. So: first
deployment empties the catalogue and returns a retirement message from the members, keeping the family
declared; then you wait at least the longest `ttlMs` you have ever sent, because that is how long a
client may still be holding the old declaration; then the second deployment removes the handlers. And
a client seeing `-32601` on a family its declaration promised should re-discover rather than cache the
absence, because during a rolling deploy the next instance may still have it."*
