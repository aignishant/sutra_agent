# 6.2 — Before a stranger draws on your screen

## One-line answer

Enabling a server's UI is a **review decision, not a configuration flag** — nine questions, asked in
order, and the first four can be answered by fetching the template before anything renders, which is
the entire reason the specification made you pre-declare it.

## The story

The kitchen tap has been dripping for a week and the plumber is at the door with a bag of tools.

You do not stand aside and go back to your desk. You show him to the kitchen, which means he walks
through one room and not the others. The bag comes with him. Somebody stays within earshot. If he asks
to turn the mains off you say yes, and if he asks for the wifi password you notice the question,
because the question is not about taps.

None of that is suspicion of this man in particular. It is what you do with any tradesman, including
one you have used before, and it takes no effort because it is a routine rather than a judgement. The
day somebody arrives who should not be there, the routine is what catches it — not your instinct,
which was busy thinking about the tap.

## The idea in plain language

MCP Apps is the largest thing a server can do to a client. Not because of what the sandbox permits —
[4.3](../04-a-server-that-draws/4.3-what-the-sandbox-actually-stops.md) showed that is narrow — but
because of what it puts in front of a human. Pixels next to your product's pixels, in your product's
frame, with your product's credibility behind them.

Everything else a server does is mediated by a model that a user knows is a model. A panel is not
mediated by anything. The user sees an interface and assumes it is yours.

So the decision to render a stranger's App belongs to a review, and a review needs a list. Nine
questions, in the order that lets you stop early:

| # | Question | Answerable before rendering? |
| --- | --- | --- |
| 1 | Which extension does this server claim, exactly? | yes — the declaration |
| 2 | Which `ui://` resources does it serve? | yes — `resources/list` |
| 3 | What is in the template? Read it. | yes — `resources/read` |
| 4 | What does its `_meta.ui.csp` declare, and does it need to? | yes — the resource's metadata |
| 5 | What `permissions` does it request? | yes — the same metadata |
| 6 | Which of its tools are `visibility: ["app"]`, and what do they do? | yes — `tools/list` |
| 7 | Which `ui/` methods will our host honour for this server? | **our decision**, not theirs |
| 8 | What does the audit record when a user clicks? | **our decision** |
| 9 | Is the template pinned by digest, and who approves a change? | **our decision** |

Questions 1 to 6 are answerable by fetching things, before the server has rendered a single pixel.
**That is what pre-declaration is for** — [3.3](../03-declared-versus-implemented/3.3-declared-before-anything-runs.md)
said a client must be able to review everything a server will ever do to it before anything runs, and
this table is the cash value of that sentence.

Questions 7 to 9 are not about the server at all. They are about your host, and they have to be
answered once rather than per server.

## Why Sutra needs it

Sutra has parked shipping an App ([4.5](../04-a-server-that-draws/4.5-parked-why-sutra-ships-no-app.md)),
and this list is the other half of that decision — the client half, which is not parked so much as
*not yet asked*.

Day 40 built the tool filter: which of a stranger's tools Sutra will call. Day 44 hardens the client
against servers that are slow or gone. Neither of them touches rendering, and the moment Sutra's
`clientCapabilities` grows `io.modelcontextprotocol/ui`
([1.4](../01-what-a-server-declares/1.4-the-client-declares-too.md)), every mounted server gains the
right to draw. That is a single line of code with a blast radius the size of the server list.

Day 45's audit is where this list becomes rows. For each mounted server: does it declare the UI
extension, do we render it, and if we do, which of the nine questions has an answer written down.

## The mechanism

The first four questions, answered by asking rather than by reading documentation:

```python
def ui_surface(
    declaration: dict[str, Any], resources: list[Any], tools: list[Any]
) -> dict[str, Any]:
    """Everything a host can learn about a server's UI before rendering anything."""
    claimed = declaration.get("extensions") or declaration.get("experimental") or {}
    templates = [r for r in resources if str(r.uri).startswith("ui://")]
    app_only = [t.name for t in tools if (t.meta or {}).get("ui", {}).get("visibility") == ["app"]]
    return {
        "claims_ui": UI_EXTENSION in claimed,
        "templates": [str(r.uri) for r in templates],
        "csp": [(r.meta or {}).get("ui", {}).get("csp") for r in templates],
        "permissions": [(r.meta or {}).get("ui", {}).get("permissions") for r in templates],
        "app_only_tools": app_only,
    }
```

**Line by line:**

- `declaration.get("extensions") or declaration.get("experimental") or {}` reads both maps, for
  [1.3](../01-what-a-server-declares/1.3-an-extension-is-a-capability-with-a-surname.md)'s reason: the
  specification says `extensions` and the SDK era Sutra is on says `experimental`, and a review that
  reads one will miss half the servers.
- `str(r.uri).startswith("ui://")` — the URI scheme is the discriminator, and it is checked on the
  string because a pydantic `AnyUrl` compares unhelpfully. A resource whose scheme is not `ui://` is
  data and is not this review's business.
- `(t.meta or {}).get("ui", {}).get("visibility") == ["app"]` finds the tools **only the panel can
  call**. Those are the ones to read carefully: they are outside the model's world, so nothing the
  model does can trigger them, and equally nothing that reviews the model's tool list will ever have
  looked at them.
- `csp` and `permissions` are collected **per template**, not merged. Two templates with different
  policies is a legitimate thing for a server to ship, and flattening them would hide the permissive
  one behind the strict one.
- The return is a plain dictionary because it is going into a report and a JSON file. Day 45's audit
  will store it; a class here buys nothing and costs a schema.
- Nothing in this function renders, connects or executes. Every value comes from three list-shaped
  reads, which is exactly the property that makes the review possible.

And the host-side answers to questions 7 and 9, which are policy rather than discovery:

```python
ALLOWED_UI_METHODS = frozenset(
    {
        "ui/initialize",
        "ui/notifications/size-changed",
        "tools/call",
    }
)

PINNED_TEMPLATES = {
    # "ui://partner/panel.html": "sha256:...",
}
```

**Line by line:**

- `ALLOWED_UI_METHODS` is an **allowlist**, so a method the host has never heard of is refused rather
  than forwarded. Day 40's argument, in a new place: a denylist of dangerous methods is wrong the day
  the extension adds one.
- The three chosen here are deliberately minimal. `ui/open-link` is absent, so a panel cannot send a
  user to an external page. `ui/update-model-context` is absent, so a panel cannot write into what the
  model reads next turn — the injection channel
  [4.4](../04-a-server-that-draws/4.4-the-dialect-spoken-through-the-glass.md) named. `ui/message` is
  absent, so a panel cannot put words in the conversation. Each of those is a feature given up on
  purpose, and a host that needs one adds it with a reason.
- `tools/call` **is** allowed, because it is the feature. It goes through the same filter as a
  model-initiated call, which is the rule
  [4.4](../04-a-server-that-draws/4.4-the-dialect-spoken-through-the-glass.md) ended on.
- `PINNED_TEMPLATES` maps a `ui://` URI to the digest of the template a reviewer approved. Empty, with
  a commented example, because Sutra pins none — it renders none. A template whose digest is not in
  this map is not rendered, which turns question 9 into a lookup.
- Both are module constants, so a change to either is a diff in a pull request rather than a value in
  a configuration store that nobody reviews.

resource ui://sutra/approval.html  mime=text/html;profile=mcp-app  _meta={'ui': {'csp': {}, 'prefersBorder': True}}
tool     close_ticket    ui.resourceUri=ui://sutra/approval.html  visibility=['model', 'app']

One template, an empty CSP declaration, one app-only tool, and 268 bytes a human can read in full. That
is a reviewable server. A server whose answer to question 3 is *forty kilobytes of minified
JavaScript* is a different conversation, and the honest answer there is that nobody reviewed it.

## When it breaks

The break is a review that happened once.

The nine questions get answered, the server is approved, the template's digest goes in the map. Six
months later the partner ships a redesign. If the digest is pinned, rendering stops and somebody is
annoyed but safe. If it is not — and it usually is not, because pinning was the row everyone agreed
was a nice-to-have — the new template renders on the strength of a review of a page that no longer
exists.

There is no error text. That is the entire problem with this failure and the reason it needs a
mechanical control rather than a process one. What you get instead, with the digest pinned, is a
refusal you can act on:

```text
refused ui://partner/panel.html: digest sha256:9f2c... is not in PINNED_TEMPLATES
```

`TODO(me: this line is the shape the refusal should take, not a run — write the host-side check that
emits it, and decide whether an unpinned template blocks rendering or renders with a visible warning)`.

The second break is answering question 7 per server instead of once. A host that lets each server
negotiate which `ui/` methods it may use has no policy, it has a set of exceptions, and the union of
those exceptions is what an attacker gets. The allowlist is a property of the host.

## In production

**What a professional writes instead:** the nine answers as a file per server, committed, next to the
provenance row from Day 29's ledger. Not a wiki page and not a ticket — a file, so that changing an
answer is a diff and so that the audit script can read it. The template digest lives in the same file
as the review that approved it.

**What degrades at scale:** question 3, and only question 3. Everything else is a field lookup and
scales fine. *Read the template* does not scale, because templates get big and bundled and minified,
and a reviewer who cannot read one will approve it anyway. The realistic answer above a handful of
servers is not better reviewing — it is a stricter rule: no external origins in `csp`, a size ceiling,
and a rejection of anything not human-readable. Those are checkable.

**The failure mode that only appears with real traffic:** the panel that behaves differently for one
user. Nothing in the six discoverable answers is per-user, but the template's script can branch on
whatever the host pushes into it. A review that watched one flow saw one branch. This is why question 8
— what the audit records when a user clicks — is not paperwork: the audit trail is the only artefact
that covers behaviour the review did not see.

**The review comment a senior engineer leaves:** *"we render this partner's App because the flag is on
in config. There is no record of anyone reading the template, the template is not pinned, and our host
forwards every `ui/` method including `update-model-context` — so their page can write into our
model's context on every turn. Answer the nine questions, commit the answers, pin the digest, and cut
the method list down to what the panel actually needs."*

**The interview question:** *"a partner's MCP server ships a UI. What do you check before turning it
on?"* The answer: *"Nine things, and the first six I can answer before it renders anything, which is
exactly why the spec makes you pre-declare the template. Which extension it claims and under which key,
which `ui://` resources it serves, what is actually in the template — read it — what its `_meta.ui.csp`
declares and whether it needs any external origin at all, what device permissions it asks for, and
which of its tools are marked app-only, because those are outside the model's world and nothing that
reviews the model's tool list will have looked at them. The last three are about my host, not their
server: which `ui/` methods we forward — an allowlist, and I would leave out `open-link`,
`update-model-context` and `message` until somebody argues for them — what our audit records when a
user clicks, and whether the template is pinned by digest with a named approver for changes. The
pinning is the one people skip and it is the one that matters, because otherwise the review covers a
page the partner has since replaced, and there is no error anywhere when that happens."*
