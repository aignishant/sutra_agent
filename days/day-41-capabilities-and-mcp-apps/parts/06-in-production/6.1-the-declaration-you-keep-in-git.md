# 6.1 — The declaration you keep in git

## One-line answer

`sutra_mcp/capabilities.py` is the day's project code: the families and extensions Sutra **intends**
to declare, written down as data, plus an `audit(server)` that compares the intention against what the
SDK actually emits — because the emitted declaration is derived and the intended one is a decision.

## The story

You photograph the electricity meter on the first of every month.

It takes ten seconds and for two years it achieves nothing at all. Then a bill arrives for four times
the usual amount and the office says the meter was read on the eighteenth and here is the figure.

You have a photograph from the first and one from the following first, with the date in the file, and
the two of them bracket the eighteenth. The argument is over in one visit, and it is over because you
have a record from before anyone was arguing.

The photograph is not a better meter. The meter was always right. What the photograph gives you is a
second, independent record of what the meter said — and the whole value of it is that it was written
down by someone who was not the person sending the bill.

## The idea in plain language

Everything this day has measured points at one gap.
[1.2](../01-what-a-server-declares/1.2-nobody-types-the-declaration.md): the declaration is derived
from registered handlers, and `FastMCP` registers all of them.
[2.2](../02-discovery-without-sessions/2.2-the-request-your-sdk-cannot-send.md): the pinned SDK cannot
send `server/discover` at all and `FastMCP` never sends an extension claim.
[3.1](../03-declared-versus-implemented/3.1-a-promise-not-a-proof.md): a declaration is a promise
nothing verifies.

So Sutra's public contract is currently whatever the library emits. Nobody chose it, nothing checks
it, and there is nothing to diff when it changes.

`sutra_mcp/capabilities.py` closes that. It does **not** try to change what the SDK emits — you cannot
on this pin, and pretending otherwise would be the confident invention Principle 8 forbids. It is the
photograph of the meter: an independent, version-controlled statement of what Sutra means to say about
itself, with a function that compares it against reality and returns the differences.

Five public symbols, and the day's build brief in §4 of the hub asks for exactly these:

| Symbol | What it is |
| --- | --- |
| `DECLARED_FAMILIES` | the core capability families `sutra-mcp` intends to declare |
| `EXTENSIONS` | the extension identifiers it claims, as a map to settings objects |
| `UI_RESOURCES` | the `ui://` resource URIs it serves — empty, per [4.5](../04-a-server-that-draws/4.5-parked-why-sutra-ships-no-app.md) |
| `register_capabilities(server)` | attaches the claim to a built server, following Day 34's convention |
| `audit(server)` | every disagreement between the intention and the emitted declaration |

## Why Sutra needs it

Day 45 is the phase gate and its subject is `sutra-core`'s data boundary. The single most useful thing
this day can hand that gate is a file that says, in code, what the boundary claims to be.

There is also the immediate reason. Day 42 exposes the desk agent over MCP and Day 43 reshapes the
server for deployment. Both will touch `build_server()`. Without `audit(server)` in the gate, a change
that adds or removes a family passes review as a one-line diff in a different file, and the first
person to find out is a client.

And the registration convention matters as much as the content. Day 34's
[1.4](../../../day-34-building-sutra-mcp-tools/parts/01-the-server-object/1.4-the-shape-later-days-register-into.md)
fixed it: each later day adds **one module** to `sutra_mcp/` and **one line** to `build_server()`, and
the import arrow runs one way — `server.py` imports the capability modules, never the reverse. Today's
module follows that convention exactly, and following it is part of the exercise.

## The mechanism

The shape of the module. Constants first, because they are the decision:

```python
"""What sutra-mcp intends to declare about itself, and the check that it does."""

from typing import Any

# The core capability families sutra-mcp promises. Compare with what the SDK emits, never
# assume they agree: FastMCP registers every family's handlers in its constructor.
DECLARED_FAMILIES: frozenset[str] = frozenset({"tools", "resources", "prompts"})

# Extension identifiers claimed, reverse-DNS, mapped to their settings objects.
# Empty by decision (Day 41, part 4.5): Sutra ships no MCP App.
EXTENSIONS: dict[str, dict[str, Any]] = {}
UI_RESOURCES: tuple[str, ...] = ()
```

**Line by line:**

- `DECLARED_FAMILIES` is a `frozenset`, not a list. It is compared with set operations in `audit`, it
  is never ordered, and it must not be mutable — a module-level list is one `.append()` away from
  being changed at run time by something that should not have.
- The three names are the three `FastMCP` will emit anyway, which is the point: the module is
  currently *agreeing* with the library, deliberately and in writing. The day somebody removes
  `register_prompts` from `build_server()`, this line and the emitted declaration disagree and
  `lab/gate.py` says so — which is exactly the failure
  [5.2](../05-failure-lab/5.2-the-family-that-went-away.md) walked through.
- The comment on `DECLARED_FAMILIES` names the reason the check exists. A constant with no comment is
  a value; a constant with the reason is a decision.
- `EXTENSIONS` and `UI_RESOURCES` are the parked pair from
  [4.5](../04-a-server-that-draws/4.5-parked-why-sutra-ships-no-app.md). Both empty, and the gate
  enforces that they are empty *together*.
- `dict[str, dict[str, Any]]` rather than `dict[str, Any]` — the value is a settings object, which is
  always a map, and typing it as one is what makes an empty `{}` read as *supported with no settings*
  rather than as a placeholder.

Then the registration, following Day 34's signature:

```python
def register_capabilities(server: Any) -> None:
    """Attach Sutra's capability claims to a built server. Called from build_server()."""
    # TODO(me): on mcp==1.29.1, FastMCP calls create_initialization_options() with no
    # arguments, so an extension claim never reaches the wire (Day 41, part 1.3). Decide:
    # reach past the SDK, or leave EXTENSIONS as a recorded intention until the pin moves.
    ...
```

**Line by line:**

- `register_capabilities(server) -> None` matches `register_tools`, `register_resources` and
  `register_prompts` exactly. Same shape, same call site, one more line in `build_server()`. A
  different signature here would be a small inconsistency that every later reader has to notice.
- `server: Any` rather than `server: FastMCP` is a decision you should make and defend rather than
  copy. Day 34's modules type it; whether this one can depends on what you decide the function does.
- The `TODO(me)` is left **unsolved** and it is the real content of this function. There is no correct
  answer handed to you: reaching past a library's public surface is sometimes right and sometimes the
  start of a maintenance problem, and the argument is what the day is asking for.
- `...` rather than `pass` — an ellipsis body reads as *deliberately unimplemented*, where `pass` reads
  as *nothing to do here*. They compile the same and they say different things to the next reader.

And the check, which is the part with teeth:

```python
def audit(server: Any) -> list[str]:
    """Every disagreement between what Sutra intends to declare and what the server emits."""
    emitted = set(declaration(server))
    findings = []
    findings += [f"promised but not emitted: {f}" for f in sorted(DECLARED_FAMILIES - emitted)]
    findings += [f"emitted but not promised: {f}" for f in sorted(emitted & KNOWN_FAMILIES - DECLARED_FAMILIES)]
    return findings
```

**Line by line:**

- The return is a **list of sentences**, not a boolean. A check that says `False` sends somebody
  reading source; a check that says `emitted but not promised: completions` sends them to one line.
  Day 29's audit pipeline and Day 31's linters both return findings for the same reason.
- Two set differences, both directions. Under-declaration and over-declaration are different bugs
  ([3.1](../03-declared-versus-implemented/3.1-a-promise-not-a-proof.md)) and merging them into one
  message would make the more dangerous one harder to spot.
- `emitted & KNOWN_FAMILIES` intersects with the real family names before subtracting, so
  `experimental` — which is in the emitted declaration and is not a family
  ([1.1](../01-what-a-server-declares/1.1-the-programmes-on-the-dial.md)) — never becomes a finding.
  You will need to define `KNOWN_FAMILIES`; `mcp.types.ServerCapabilities.model_fields` is where the
  real list lives.
- `sorted(...)` on both, so two runs against the same server produce byte-identical output. A findings
  list that reorders between runs cannot be diffed, and diffing is the whole point of writing it down.
- `declaration(server)` is the reader that pulls the emitted capability object off a built `FastMCP`.
  `lab/gate.py` has one; deciding whether it belongs in the module or stays in the lab is part of the
  build.

The gate that enforces all of it:

**Line by line:**

- From the repository root. **Zero generations, no network.**
- Six statements: the module imports, `register_capabilities` is callable, `DECLARED_FAMILIES` names
  only real fields, the built server declares every promised family, `audit(build_server())` is clean,
  and the extension claim and the `ui://` resources are empty or non-empty together.

## When it breaks

The break is a second source of truth that nothing compares.

`capabilities.py` exists, `DECLARED_FAMILIES` says three families, and `audit` is never called by
anything. Somebody removes a family from `build_server()`; the constant still says three; the file
looks authoritative and is wrong. That is worse than not having written it, because the next reader
believes it.

There is a sharper version of the same failure. Write `audit(server)` and call it from
`build_server()` itself, raising on a finding, and you get a server that refuses to start when its
declaration drifts. That sounds strict and correct. It means a one-character typo in a constant takes
production down at the next restart, and the on-call person is looking at a crash loop caused by a
comment somebody edited.

The smallest fix is placement rather than logic: **the audit runs in the gate, not in the
constructor.** A check that fails a build is a bug caught; the same check inside a start-up path is an
outage waiting for a deploy.

## In production

**What a professional writes instead:** a generated artefact committed alongside the module. The build
writes the emitted declaration to `docs/` or a fixture file, sorted and deterministic, and the test
asserts the file matches. A change to what the server declares then arrives as a **diff in a pull
request**, visible to a reviewer who has not read `build_server()`, which is the whole point.

**What degrades at scale:** the number of services with their own hand-maintained constant. Two is
fine. Twenty is a fleet where each team wrote a slightly different set of family names and nobody can
answer *which of our servers declare resources* without reading twenty files. At that size the
constant moves out of the service and into a shared schema the services are validated against.

**The failure mode that only appears with real traffic:** the declaration that is right in staging and
wrong in production. Anything that registers conditionally — a family behind a feature flag, a tool
registered only when a database URL is present — makes the emitted declaration depend on the
environment. The audit passes in CI, where the flag is on, and the production server declares
something else. The rule that avoids it: **capability registration is unconditional**, and a family
that is not always available is not a family this server has.

**The review comment a senior engineer leaves:** *"good — but `audit()` is only called from the lab
gate, which nobody runs in CI. Wire it into `./m check` behind Day 45's audit script, and commit the
emitted declaration as a fixture so a change to it shows up as a diff. Right now this file is a
comment that happens to be executable."*

**The interview question:** *"your framework generates your service's public capability declaration.
Is that a problem?"* The answer: *"It is, and it is the kind that stays invisible. The declaration is
derived from which request handlers are registered, and the high-level server class we use registers
every family in its constructor — so an empty server already declares three families it cannot serve.
Nobody decided that. What we did was write the intended set down as a constant in its own module, with
a function that returns the differences between the intention and what the server actually emits, in
both directions, as sentences rather than a boolean. That runs in the build gate and never in the
constructor, because a declaration mismatch should fail a deploy, not crash a running process. The
next step is committing the emitted declaration as a fixture, so that changing our public contract is
a diff a reviewer sees rather than a side effect of a line in a different file."*
