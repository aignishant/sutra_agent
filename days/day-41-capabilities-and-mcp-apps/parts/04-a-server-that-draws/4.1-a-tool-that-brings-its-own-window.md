# 4.1 — A tool that brings its own window

## One-line answer

MCP Apps — extension identifier `io.modelcontextprotocol/ui` — lets a tool point at an HTML page the
server also serves, which the host renders **inside the conversation**, so a server that has never had
a screen can put a form in front of your user.

## The story

The vegetable seller comes down your street with a cart, and he brings his own weighing scale.

He does not use yours. He does not expect you to have one. The scale sits on the cart, you can see the
needle from where you are standing, and when he puts the tomatoes on it you both look at the same
number at the same time. The transaction happens at your gate, on his equipment, in front of you.

Compare that with the shop two streets away that sells the same tomatoes. Their scale is inside, on
their counter, and it is a perfectly good scale. But to use it you have to walk there, and once you
are there you are in their shop, on their terms, and the reason you called the cart in the first place
was that you did not want to go anywhere.

The seller brings the scale because the whole point is that you do not move.

## The idea in plain language

Everything `sutra-mcp` returns today is text. A tool runs, a string comes back, the model reads it,
the model writes a sentence, and a human reads that. For *"what does ticket 4521 say"* that is
exactly right.

For *"close ticket 4521 and its three duplicates, yes or no"* it is not. The human has to read a
paragraph the model wrote and type a word back into a chat box. Free text, typed by a person under
mild time pressure, is a poor way to record a decision that closes four tickets, and Day 37's
[3.3](../../../day-37-auth-and-elicitation/parts/03-the-question/3.3-three-answers-not-two.md) already
made half this argument: a question deserves a **form**, not a sentence.

**MCP Apps** is the other half. The server ships a small HTML page. The host renders it in the
conversation, in a locked box. The user clicks a button. The click becomes an ordinary tool call.

The question that decides whether this is interesting is *why not just link to a web page*, and the
official overview answers it directly
(`https://modelcontextprotocol.io/extensions/apps/overview`, read 2026-09-04). Four reasons, and only
two of them are about convenience:

| Reason | What it means |
| --- | --- |
| Context preservation | the panel is in the conversation, not in another tab the user has to find again |
| Bidirectional data flow | the page can call the server's tools and the host can push results into it, with no separate API |
| Host integration | the page asks the **host** for an outcome, and the host uses connections the user already has |
| Security guarantees | the page runs in a sandbox the host controls, so a host can render a stranger's page |

The last one is the load-bearing one, and it is why this is a protocol feature rather than a link.
Anyone can send a user a URL. Nobody can send a user a URL that is guaranteed not to read their
cookies, and that is precisely what a host-controlled sandbox is for.

Three moving parts and no more:

1. **A UI resource** — an HTML page the server serves as an ordinary MCP resource, at a URI beginning
   `ui://`, with mime type `text/html;profile=mcp-app`.
2. **A link** — the tool's `_meta.ui.resourceUri` naming that resource.
3. **A bridge** — a JSON-RPC dialect over `postMessage` between the page and the host, with method
   names prefixed `ui/`.

Parts one and two are ordinary MCP and run on `mcp==1.29.1` today —
[4.2](4.2-the-template-is-declared-the-data-flows-in.md) runs them. Part three needs a browser and a
host that implements the bridge, and there is no such thing in this repository —
[4.4](4.4-the-dialect-spoken-through-the-glass.md) teaches it from the specification and says so.

## Why Sutra needs it

It may well not, and that is a real answer that [4.5](4.5-parked-why-sutra-ships-no-app.md) argues
properly. But the question has to be asked here, because Sutra has exactly the shape of problem MCP
Apps was designed for.

Phase 9 builds approval gates. The moment a human has to approve a write — closing a ticket, sending a
refund — three things are true at once: the **server** knows what a duplicate ticket is, the **host**
owns the screen, and the **decision** must be recorded exactly, not paraphrased. Those three facts are
the entire premise of MCP Apps.

There is also a client-side obligation regardless of what Sutra ships. Day 40 filters the tools Sutra
will call. Nothing yet decides whether Sutra will *render* a stranger's page, and by
[1.4](../01-what-a-server-declares/1.4-the-client-declares-too.md)'s rule, that decision is made by
what Sutra puts in `clientCapabilities` — not by what a server offers. Principle 13: the new power
arrives with its containment story or it does not arrive.

## The mechanism

The whole loop, from the official overview's own sequence, drawn as a diagram:

```mermaid
sequenceDiagram
    participant U as User
    participant H as Host
    participant A as App iframe
    participant S as MCP server

    H->>S: tools/list
    S-->>H: close_ticket, _meta.ui.resourceUri = ui://sutra/approval.html
    H->>S: resources/read ui://sutra/approval.html
    S-->>H: HTML, mime text/html;profile=mcp-app
    Note over H,A: host may fetch and review the template before any call
    U->>H: "close 4521 and its duplicates"
    H->>S: tools/call close_ticket
    S-->>H: result
    H->>A: render template, then ui/notifications/tool-result
    U->>A: clicks Approve
    A->>H: tools/call record_verdict
    H->>S: tools/call record_verdict
    S-->>H: recorded
    H-->>A: fresh data
```

Read the third and fourth arrows again. The host fetches the template **before the tool is called** —
the overview calls this *UI preloading* — which is the pre-declaration rule from
[3.3](../03-declared-versus-implemented/3.3-declared-before-anything-runs.md) turned into a
performance feature as well as a safety one.

And read the last five arrows. The user's click does **not** reach the server directly. It reaches the
host, and the host makes the tool call. That is why a button is not a new attack surface: it is a
normal `tools/call`, going through the same allowlist Day 40 built, appearing in the same audit trail
as a call the model made.

The declaration side, in code that runs on the pinned SDK. From `lab/apps_sketch.py`:

```python
APP_MIME = "text/html;profile=mcp-app"
PANEL_URI = "ui://sutra/approval.html"


@server.list_tools()
async def _list_tools() -> list[Tool]:
    return [
        Tool(
            name="close_ticket",
            description="Close one ticket after a human approves.",
            inputSchema={"type": "object", "properties": {"ticket_id": {"type": "string"}}},
            _meta={"ui": {"resourceUri": PANEL_URI, "visibility": ["model", "app"]}},
        ),
        Tool(
            name="record_verdict",
            description="Record the human's verdict.",
            inputSchema={"type": "object", "properties": {"verdict": {"type": "string"}}},
            _meta={"ui": {"resourceUri": PANEL_URI, "visibility": ["app"]}},
        ),
    ]
```

**Line by line:**

- `APP_MIME` is `"text/html;profile=mcp-app"` exactly — the `profile` parameter is what distinguishes a
  page meant to be rendered as an App from any other HTML a server might serve. Copied from the
  specification, not reformatted.
- `PANEL_URI` starts `ui://`. The specification requires that prefix so a host can tell a UI resource
  from a data resource without reading it, which matters because it decides whether the bytes go to a
  renderer or to a model's context.
- `_meta={"ui": {...}}` on the **tool** is the link. `_meta` is the same extension-metadata channel
  Day 32's
  [2.3](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.3-every-request-introduces-itself.md)
  introduced; here it carries an extension's fields rather than the protocol's own.
- `"visibility": ["model", "app"]` on `close_ticket` — the model may call it and the app may call it.
  `["app"]` on `record_verdict` — **only the panel may call it**, never the model. That single field is
  the reason a click is safer than a sentence: the tool that records a human's decision is not in the
  model's tool list at all, so no amount of prompt injection can make the model record a verdict.
- Two tools, not one. The tool that *shows* the panel and the tool that *records the answer* are
  separate because they have different callers and different blast radius. Merging them would put the
  recording tool back in the model's hands.

The last line is the one worth staring at. Two tools exist; the model is offered one.

## When it breaks

The break is assuming a host will render it, and the specification is explicit that most will not
unless they opt in.

MCP Apps is an **extension**, which by Day 37's
[5.1](../../../day-37-auth-and-elicitation/parts/05-policy/5.1-the-optional-extras-list.md) means
off by default and negotiated by both sides. A server that ships a panel and no text result gets this
outcome on a host that does not implement Apps: the tool call succeeds, a `ui://` resource sits in the
catalogue unread, and the user sees nothing at all. There is no error. There is no log line. The
feature is simply absent for that user.

The specification's own rule for this, from the versioning page (read 2026-09-04):

> *"If one party supports an extension but the other does not, the supporting party **MUST** either
> revert to core protocol behavior or reject the request. Extensions **SHOULD** document their
> expected fallback behavior."*

So the fix is not a check for host support. It is that **the tool must return a useful text result
regardless**, and the panel is an enhancement on top. A tool whose only output is a rendered interface
has made a required feature out of an optional extension — and, incidentally, has made itself
unusable to anybody using a screen reader or a terminal client.

## In production

**What a professional writes instead:** a tool with two outputs and one of them mandatory. The text
result carries the whole decision in words, and `_meta.ui.resourceUri` carries the panel for hosts
that can render one. Every code path is tested with the panel turned off, because that is the path
most users are on.

**What degrades at scale:** the panel is HTML, and HTML that a host must fetch before it can render.
A server with forty tools each pointing at its own template is forty extra `resources/read` calls at
warm-up. The templates are cacheable like any resource, so the number that matters is how often they
change — a template with a short TTL is a template being fetched on every conversation.

**The failure mode that only appears with real traffic:** the panel and the text drifting apart. The
text result says three duplicates; the panel, built from a slightly different query, shows four. Both
are the server's own output and both are shown to the same human at the same moment, and the one they
act on is whichever they read first. The only defence is that one query produces both.

**The review comment a senior engineer leaves:** *"`close_ticket` returns an empty text block and a
`ui://` pointer. On any host without the Apps extension — which is most of them, it is opt-in on both
sides — this tool returns nothing and the model has nothing to say. Put the full verdict in the text
result and treat the panel as decoration on top, then delete the extension from your dev host and run
the whole flow again."*

**The interview question:** *"a tool wants to show a human an interactive UI. Walk me through it."*
The answer: *"MCP Apps, extension `io.modelcontextprotocol/ui`. The server registers the interface as
an ordinary MCP resource at a `ui://` URI with mime `text/html;profile=mcp-app`, and the tool points at
it with `_meta.ui.resourceUri` — so the host can fetch and review the template before the tool is ever
called. When the tool runs, the host renders that template in a sandboxed iframe in the conversation
and pushes the result into it. A click in the panel becomes an ordinary `tools/call` routed through
the host, so it goes through the same filtering and the same audit trail as a call the model made. The
detail I would want to mention is `visibility`: the tool that records the human's verdict is marked
app-only, so it is not in the model's tool list at all and prompt injection cannot reach it. And
because the extension is opt-in on both sides, the tool has to return a complete text result anyway —
the panel is never the only path."*
