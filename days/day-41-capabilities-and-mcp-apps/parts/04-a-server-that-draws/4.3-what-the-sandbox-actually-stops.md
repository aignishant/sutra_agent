# 4.3 — What the sandbox actually stops

## One-line answer

The host builds a Content-Security-Policy from the resource's own `_meta.ui.csp` declaration, starting
at `default-src 'none'` and adding **only origins the server named** — so a page that declares nothing
can load nothing, reach nothing and phone nowhere, and a host may narrow that policy but must never
widen it.

## The story

There is a child-safety gate at the top of your stairs.

It does not stop the toddler existing, moving, shouting or pulling books off the shelf. It stops
exactly one thing: going down the stairs unaccompanied. Everything else about the landing is still
available to them, and that is deliberate — a gate that stopped everything would be a locked door, and
you would take it off within a week because you also live here.

The gate is worth having precisely because it is narrow. You know what it prevents, you know what it
does not, and you do not confuse the two. Nobody with a safety gate believes the upstairs is now
childproof.

## The idea in plain language

"Sandboxed iframe" is two mechanisms doing two different jobs, and people say the phrase as if it were
one.

**The iframe sandbox** stops the page reaching *outwards into the host*. From the official overview
(`https://modelcontextprotocol.io/extensions/apps/overview`, read 2026-09-04), the sandbox prevents an
App from *"accessing the parent window's DOM, reading the host's cookies or local storage, navigating
the parent page, or executing scripts in the parent context."*

**The Content-Security-Policy** stops the page reaching *outwards into the network*. It is a separate
control, built by the host from the resource's declaration, and it decides which origins the page may
load scripts, styles, images, fonts and media from, and which origins it may open connections to.

Both are needed and neither substitutes for the other. A page with a perfect sandbox and no CSP can
still send every byte it is given to a server of its choosing. A page with a strict CSP and no sandbox
can still read the host's page around it.

What neither of them stops is worth listing plainly, because it is the list a reviewer needs:

| The sandbox and the CSP do **not** stop | Which means |
| --- | --- |
| the page calling the server's own tools | that is the whole feature; see [4.4](4.4-the-dialect-spoken-through-the-glass.md) |
| the page showing the user something misleading | pixels are pixels; a convincing fake button is trivial |
| the page asking the user to type something | it is a form, and the user does not know whose form |
| the template being wrong on purpose | the host renders what the server registered |

That last block is why [6.2](../06-in-production/6.2-before-a-stranger-draws-on-your-screen.md)
exists. Containment is not the same as trust.

## Why Sutra needs it

Both directions again, and this time the client direction is the dangerous one.

**As a server**, if `sutra-mcp` ever ships a panel, its `_meta.ui.csp` is a public statement about what
that panel reaches for. Declaring `{}` — nothing — is the strongest thing Sutra can say and the easiest
to defend in Day 45's audit. Every origin added to it is a row somebody has to justify.

**As a client**, Sutra is on the other side of this the moment it declares
`io.modelcontextprotocol/ui` in `clientCapabilities`. A stranger's server then names origins and
Sutra's host is the thing that must build the policy correctly. Building it *loosely* — adding an
origin the server did not declare, or falling back to a permissive default when the declaration is
missing — is a hole with somebody else's code on the other side of it.

The specification is unambiguous about the direction of that pressure: *"If metadata is omitted, hosts
apply the restrictive default. Hosts must never allow undeclared domains."* Restrictive by default,
never wider than declared. That is Principle 13 written into a specification.

## The mechanism

The formula, from the Apps specification
(`https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx`,
read 2026-09-04), implemented in `lab/csp.py`:

```python
Csp = dict[str, list[str]]


def build_csp(csp: Csp | None) -> str:
    """Return the CSP string a host must enforce for a UI resource with this metadata."""
    csp = csp or {}
    resource = " ".join(csp.get("resourceDomains", []))
    connect = " ".join(csp.get("connectDomains", []))
    frame = " ".join(csp.get("frameDomains", [])) or "'none'"
    base = " ".join(csp.get("baseUriDomains", [])) or "'self'"
    return "; ".join(
        [
            "default-src 'none'",
            f"script-src 'self' 'unsafe-inline' {resource}".rstrip(),
            f"style-src 'self' 'unsafe-inline' {resource}".rstrip(),
            f"connect-src 'self' {connect}".rstrip(),
            f"img-src 'self' data: {resource}".rstrip(),
            f"font-src 'self' {resource}".rstrip(),
            f"media-src 'self' data: {resource}".rstrip(),
            f"frame-src {frame}",
            "object-src 'none'",
            f"base-uri {base}",
        ]
    )
```

**Line by line:**

- `csp = csp or {}` turns both a missing declaration and an explicit `None` into the same empty map,
  and the empty map is what produces the restrictive default. There is no branch anywhere for "no
  declaration" — absence and emptiness are the same thing by construction, which is how you avoid a
  permissive fallback appearing by accident.
- `"default-src 'none'"` is the **first** directive and it is not built from anything the server said.
  It means: nothing loads from anywhere unless a later, more specific directive allows it. Every other
  line is an exception to this one.
- The four declared lists have four different jobs. `resourceDomains` is for things the page *loads*
  (scripts, styles, images, fonts, media). `connectDomains` is for connections the page *opens* —
  `fetch`, `XMLHttpRequest`, WebSocket. Those are the two that matter, and they are separate because
  loading a font from somewhere is a very different risk from being able to send data there.
- `resource` is interpolated into **five** directives. One `resourceDomains` entry therefore widens the
  policy in five places at once, which is worth knowing before adding one.
- `'unsafe-inline'` on `script-src` and `style-src` looks alarming and is deliberate: an App is a
  single self-contained HTML document with its script inline, so forbidding inline script would forbid
  the format. The compensating control is that the document is fixed and reviewed
  ([4.2](4.2-the-template-is-declared-the-data-flows-in.md)) — the inline script is not arbitrary, it
  is the script somebody read.
- `.rstrip()` on every interpolated line removes the trailing space when the declared list is empty.
  A CSP with a stray trailing space parses fine; a policy string that differs between two servers only
  by whitespace does not compare equal, and these strings get logged and diffed.
- `frame-src` falls back to `'none'` and `base-uri` to `'self'` rather than being omitted. Omitting them
  would leave them to `default-src`, which is already `'none'` — writing them out means the policy says
  what it does rather than relying on the reader to know the inheritance rules.
- `object-src 'none'` is unconditional and cannot be widened by anything the server declares. Plugins
  and embedded objects are simply not available to an App, at all.

And the permissions half, which is a different control on a different attribute:

```python
def allow_attribute(permissions: dict[str, Any] | None) -> str:
    """Return the iframe allow= attribute a host builds from requested permissions."""
    wanted = ["camera", "microphone", "geolocation"]
    return " ".join(name for name in wanted if (permissions or {}).get(name) is not None)
```

**Line by line:**

- `wanted` is an explicit allowlist of permission names the host understands. Iterating the server's
  keys instead would let a server request a permission this host has never heard of and get it passed
  through — Day 40's lesson about allowlists over denylists, in a new place.
- `.get(name) is not None` rather than a truth test, because the specification's permission values are
  **objects**, and `{}` is a legitimate "yes, with no settings" that is falsy in Python. A truth test
  here silently drops every permission requested with default settings.
- This builds the iframe's `allow` attribute, not the CSP. They are separate: the CSP governs where
  bytes come from, `allow` governs which device APIs the document may touch.
- Nothing here grants anything on its own. The host still asks the user, and the specification's
  security model puts the host in charge — this function computes the *most* a page could be granted,
  not what it gets.

Compare the two `connect-src` lines. That single added origin is the difference between a panel that
cannot talk to anyone and a panel that can send whatever it is shown to a server of the author's
choosing — and it is one line in a declaration a reviewer can read before the page ever renders. Which
is exactly the point of pre-declaring it.

## When it breaks

The break is a host that treats a missing declaration as "no restrictions" instead of "all
restrictions".

The reasoning is always the same and always sounds like compatibility: some servers do not send
`_meta.ui.csp` at all, panels from those servers render blank, so somebody adds a fallback that lets
the page load what it likes until the ecosystem catches up.

What a browser then reports when such a page does something it should not have been able to do is
nothing at all — the whole failure of a permissive CSP is that it produces no message. The message you
*want* is the one a correct policy produces: a browser console line naming the blocked URL and quoting
the directive that blocked it, emitted at the moment of the attempt.

**This repository cannot produce that line**, because there is no browser in it and no host that
renders an App. Recording the real text is a rep, not a claim:
`TODO(me: open the panel under a host that enforces the policy, trigger a fetch to an undeclared
origin, and paste the browser console's refusal verbatim into your notes)`.

That line is a security control working. A host without it has the same panel, the same pixels, and
no line anywhere.

The smallest fix is the one the specification already states: absence means the restrictive default,
and a page that renders blank under it is a page whose author must declare what it needs. The
declaration is the interface. A host that fills it in on the server's behalf has removed the review
step and kept the risk.

The second break is subtler and is the one [4.2](4.2-the-template-is-declared-the-data-flows-in.md)
flagged: a template whose digest you pinned but whose behaviour comes from a CDN. `script-src` with
`https://cdn.example.com` in it means the reviewed page can execute code that was written after the
review. The policy is doing its job — it allowed exactly what was declared — and the review is worth
much less than it looks.

## In production

**What a professional writes instead:** the policy string is built once, logged, and stored with the
audit record for that server. Not recomputed per render and never assembled from user-supplied
fragments. When somebody asks *what was that panel allowed to reach*, the answer is a string in a log
rather than a reconstruction from source.

**What degrades at scale:** the number of declared origins across all mounted servers, which is the
real security metric here. Forty servers each declaring one CDN is forty third parties whose
compromise reaches your users' screens. The number worth tracking on a dashboard is not *how many
panels* but *how many distinct origins any panel may load code from*, and the target for that number
is zero.

**The failure mode that only appears with real traffic:** an origin that resolves differently for
different users. A declared domain behind a geographic CDN serves different bytes in different
regions, all of them allowed by the same policy string. The review happened in one region. This is why
a self-contained template with `csp: {}` is not merely the safest option but the only one that is
genuinely reviewable.

**The review comment a senior engineer leaves:** *"we default to a permissive policy when
`_meta.ui.csp` is absent, so that panels from older servers still render. Turn that around: absent
means the restrictive default, per the spec, and a blank panel is the server author's bug to fix. Right
now a server can get an unrestricted iframe on our users' screens by omitting a field, which is the
easiest possible thing to do by accident."*

**The interview question:** *"what does the sandbox in MCP Apps actually protect you from?"* The
answer: *"Two separate things that people say as one phrase. The iframe sandbox stops the page reaching
into the host — no parent DOM, no host cookies or local storage, no navigating the parent, no scripts
in the parent context. The Content-Security-Policy stops it reaching into the network, and the host
builds that policy from the resource's own `_meta.ui.csp` declaration, starting at `default-src 'none'`
and adding only origins the server named. A page that declares nothing can load nothing and connect
nowhere. The rule that matters is directional: a host may narrow the policy and must never widen it,
and an absent declaration means the restrictive default rather than a free-for-all. What neither
control stops is the page lying to the user — it can draw a convincing button that does something else,
and it can ask the user to type something. Containment is not trust, which is why enabling a server's
UI is a review decision and not a configuration flag."*
