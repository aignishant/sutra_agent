# 3.2 — Probing every promise

## One-line answer

Walk the catalogue and call every entry once — that is the whole check — and the useful part is not
that it finds broken promises but that **the two kinds of broken come back down different wires**:
one as `isError: true` on a successful call, one as a JSON-RPC error with the undefined code `0`.

## The story

The string of festival lights comes out of the box in a tangle every year, and every year somebody
says just hang it and we will see.

The person who has done this before does not. They plug it in on the floor first, walk the whole
length, and touch each bulb. Two are dead. One flickers when you press it, which is worse than dead
because it will work for the first evening. Ten minutes on the floor, and the two dead ones get
replaced from the spare packet before anybody is on a ladder.

The year somebody skipped the floor test, the dark section was in the middle of the run, six metres
up, and taking it down meant taking all of it down.

The test is not clever. It is a walk down a list, touching each thing once, at the cheapest moment
there is.

## The idea in plain language

[3.1](3.1-a-promise-not-a-proof.md) said the declaration is a promise. This part is the smallest
honest way to find out whether the promise holds, and it has three steps:

1. Read the declaration. That gives you the families.
2. For each declared family, call its `list` method. That gives you the catalogue.
3. Call every entry in the catalogue **once**, and record what came back.

Step 3 is where every design question lives. Calling a tool has side effects — you cannot probe
`close_ticket` by closing a ticket — so a real probe needs the server to cooperate, and Sutra's answer
to that is in *In production* below. The lab probes a server where every tool is read-only, which is
what makes it a lab.

What the probe measures is the thing no declaration can express: **the ratio of promises made to
promises kept.** Two families, four entries, two failures. And the two failures do not look alike:

| What failed | How it comes back | Would an error dashboard see it? |
| --- | --- | --- |
| a declared tool with no body | `isError: true` on a **successful** call | **no** |
| a listed resource that cannot be read | a JSON-RPC error, code `0` | as an error with no name |

Neither of those is what you would guess. A tool that raises does not produce an error response, and
a resource that raises produces an error response with a code that the specification does not define
at all. Both are measured below.

## Why Sutra needs it

Day 45 is the phase gate: a full MCP audit of `sutra-core`. An audit that reads declarations and
stops there has checked the sticker on the door.

`lab/drift.py` is the shape that audit needs, at one-server scale. It returns a **count of broken
promises** and exits non-zero when the count is not zero, which makes it a check that can go RED —
Principle 11 — rather than a report somebody reads.

There is a second, nearer use. `sutra_mcp/capabilities.py`'s `audit(server)` function, specified in
[6.1](../06-in-production/6.1-the-declaration-you-keep-in-git.md) and enforced by `lab/gate.py`, is
this idea applied to Sutra's own server at build time instead of to strangers' servers at audit time.
The same walk, one process earlier.

## The mechanism

The probe, in full, from `lab/drift.py`:

```python
async def probe(client: Any) -> list[tuple[str, str, str]]:
    """Call every promise the server made once, and record how it answered."""
    findings: list[tuple[str, str, str]] = []

    for tool in (await client.list_tools()).tools:
        try:
            result = await client.call_tool(tool.name, {})
        except McpError as err:
            findings.append((f"tool:{tool.name}", "BROKEN", f"-{abs(err.error.code)} {err.error.message}"))
            continue
        state = "BROKEN" if result.isError else "kept"
        detail = result.content[0].text if result.content else ""
        findings.append((f"tool:{tool.name}", state, detail))

    for res in (await client.list_resources()).resources:
        try:
            await client.read_resource(res.uri)
        except McpError as err:
            findings.append((f"resource:{res.uri}", "BROKEN", err.error.message))
        else:
            findings.append((f"resource:{res.uri}", "kept", "read"))

    return findings
```

**Line by line:**

- The tool loop has **two** failure branches and that is the point. `except McpError` catches the call
  that never happened; `result.isError` catches the call that happened and failed. Day 34's
  [4.2](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.2-the-call-never-happened.md)
  is where those two were separated, and a probe that watches only one of them misses half the
  breakage.
- `client.call_tool(tool.name, {})` sends **empty arguments**. That is deliberate: the probe is asking
  *does a handler exist and run*, not *does it work on real input*. A tool that rejects empty
  arguments will report `isError: true` and be counted broken, which is a false positive the real
  audit has to handle — see *In production*.
- `continue` after the `McpError` branch, so one tool contributes exactly one finding. Without it a
  failed call would fall through and record a second row from a `result` that does not exist.
- `f"-{abs(err.error.code)} ..."` normalises the sign. JSON-RPC codes are negative; formatting them
  consistently means the output column lines up whether the SDK handed back `-32601` or, as you are
  about to see, `0`.
- `result.content[0].text if result.content else ""` guards the two assumptions Day 34's
  [3.3](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.3-one-call-one-result.md)
  named: that the content list is non-empty, and that its first block is text. A probe that crashes on
  an unusual result has stopped being a probe.
- The resource loop has only the `McpError` branch, because `resources/read` has no `isError` field.
  Day 35's
  [2.3](../../../day-35-resources-and-prompts/parts/02-the-shelf/2.3-the-miss-that-must-be-an-error.md)
  is why: a resource miss is an error, full stop, so there is no successful-but-failed shape to check.
- The return type is a list of three strings rather than a dataclass. The findings are printed and
  counted and nothing else, so a class here would be a structure nothing reads a field of.

And the caller, which turns findings into an exit code:

```python
async def audit() -> int:
    """Run the probe against the in-memory server and return the number of broken promises."""
    async with create_connected_server_and_client_session(server) as client:
        caps = (await client.initialize()).capabilities
        declared = caps.model_dump(by_alias=True, exclude_none=True)
        print("declared families:", sorted(k for k in declared if k != "experimental"))
        findings = await probe(client)
    ...
    broken = [f for f in findings if f[1] == "BROKEN"]
    print(f"\npromises: {len(findings)}  broken: {len(broken)}")
    return len(broken)


if __name__ == "__main__":
    raise SystemExit(1 if anyio.run(audit) else 0)
```

**Line by line:**

- The declaration is printed **before** the probe, so the output reads in the order the argument runs:
  here is what was promised, here is what happened.
- `async with` around the whole probe, and the findings are printed **after** it exits. Printing inside
  the block interleaves with the SDK's own logging on some transports; printing after is
  reproducible.
- `1 if anyio.run(audit) else 0` — any non-zero count of broken promises is exit `1`. It is not the
  count, because an exit code above `1` means something else to a shell and to CI, and "how many"
  belongs in the output rather than in the status.
- `raise SystemExit(...)` rather than `sys.exit(...)`, which is the same thing and does not need an
  import.

Run it:

```bash

```

**Line by line:**

- From the repository root. **Zero generations, no network, no subprocess.**
- `echo "exit: $?"` because the exit code is half the output. A check whose status you never look at
  is a print statement.

On 2026-09-04:

```text
declared families: ['resources', 'tools']

kept    tool:lookup_ticket                 lookup_ticket ran
kept    tool:search_kb                     search_kb ran
BROKEN  tool:export_archive                export_archive was declared but never written
BROKEN  resource:file:///kb/refunds.md     file:///kb/refunds.md is listed but not on disk

promises: 4  broken: 2

```

Two families declared. Four promises underneath them. Two of the four do not hold, and **the
declaration is identical to what an honest server would emit.**

## When it breaks

The break here is not in the probe. It is in what the two failures actually carry, and it is worth
seeing on its own because it will mislead you.

Ask the resource error for its code:

```text
resource read error code: 0 'file:///kb/refunds.md is listed but not on disk'
```

**Zero.** JSON-RPC has no error code `0`, the MCP specification defines none, and the reserved range
for MCP errors is `-32020` to `-32099`. Where it comes from is one line in
`.venv/Lib/site-packages/mcp/server/lowlevel/server.py`, read 2026-09-04:

```python
except Exception as err:  # pragma: no cover
    if raise_exceptions:
        raise err
    response = types.ErrorData(code=0, message=str(err), data=None)
```

**Line by line:**

- `except Exception` is the SDK's last-resort handler around a request handler. Anything a handler
  raises that the SDK did not expect ends up here.
- `code=0` is a placeholder, not a decision. It means *"an exception escaped and we had no code for
  it"*, which is genuinely different from every defined code and is the one piece of information the
  caller most needs.
- `message=str(err)` puts your exception's text on the wire, which is Day 34's
  [4.3](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.3-the-message-that-escaped.md)
  arriving in the resource family as well as the tool family. `FileNotFoundError` here would leak a
  filesystem path to a stranger.
- `data=None`, so there is nothing structured to branch on. A client gets a code that means nothing
  and a message written for a Python programmer.
- `# pragma: no cover` on the branch says the SDK's own test suite does not exercise it. That is a
  fair signal about how load-bearing it is meant to be.

And the tool failure, from the same run:

```text
tool isError: True | export_archive was declared but never written
```

`isError: True` on a call that succeeded at the protocol level. Nothing counted an error. This is
exactly the asymmetry the probe exists to expose, and it is why the probe's tool loop checks two
things and the resource loop checks one.

The smallest fix, for both, is on the server: a handler must not let an unexpected exception escape.
Catch it, log it with the traceback for the operator, and return a message written for the caller —
which is the guard Day 34's 4.3 built and which nothing in this lab's server has.

## In production

**What a professional writes instead:** a probe that runs against a **staging** deployment, not
production, and that reads a per-tool probe argument from the tool's own metadata rather than sending
`{}` to everything. A tool that cannot be called safely declares so, and the probe records
`not probed` — an honest third state — instead of counting a false positive or, far worse, actually
running `close_ticket`.

**What degrades at scale:** the probe becomes destructive before it becomes slow. Forty servers with
three hundred tools between them is three hundred calls, which is nothing; three hundred calls that
include six writes is an incident. The scaling constraint on this check is not time, it is side
effects, and the only durable answer is that write tools are marked and skipped.

**The failure mode that only appears with real traffic:** a probe that passes against an empty
catalogue. Day 40's filtering can leave a caller with zero visible tools, and zero promises means zero
broken promises means a green check. A probe therefore needs a floor — *"at least this many entries
were probed"* — or it will report health most loudly at the moment a permission change has hidden
everything.

**The review comment a senior engineer leaves:** *"the probe calls every tool with empty arguments and
counts `isError` as broken. Half our tools require an id, so this will be red forever and somebody
will delete it in a month. Put a `probe_args` in each tool's metadata, skip anything marked as a
write, and assert a minimum number of probes so an empty catalogue cannot pass."*

**The interview question:** *"how would you tell whether a server actually does what it declares?"*
The answer: *"Walk it. Read the declaration to get the families, call each family's list method to get
the catalogue, and call every entry once. The part I would want to be asked about is that the failures
do not arrive the same way. A tool whose handler raises comes back as a *successful* call with
`isError: true`, so nothing in an error dashboard moves — and a resource whose handler raises comes
back as a JSON-RPC error with code `0`, which is not a code the spec defines; it is the SDK's
last-resort branch for an escaped exception, and the message is `str(exception)`, so it also leaks
whatever your traceback would have said. So the probe checks two things on tools and one on
resources, and the real-world version needs per-tool probe arguments and a skip for anything that
writes, or it is either useless or dangerous."*
