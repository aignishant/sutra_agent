# 3.1 — A promise, not a proof

## One-line answer

A capability declaration is something a server **says**, not something the protocol checks, so
"declared" and "implemented" are two different facts — and the client that treats the first as
evidence of the second is the one that pages somebody.

## The story

The sticker on the shop door says **Cards accepted**, in three colours, with the logos.

You fill your basket, you get to the counter, and the machine is dark. It has been dark since
Tuesday. The line company was supposed to come. The owner is apologetic and entirely honest about it
— he is not trying to trick anyone, he just cannot peel a sticker off the glass every time the
machine goes down and stick it back on when it recovers.

So the sticker is true about the shop and false about this afternoon. It tells you what the owner
intends to offer. It does not tell you what the counter will do when you get there, and the only way
to find that out is to get there.

The customer who checked their wallet at the door because of the sticker is the one now walking to a
cash machine with a basket of frozen food in their hands.

## The idea in plain language

Nothing in MCP verifies a declaration. There is no conformance step, no registry that tests servers,
no signature over the capability object. A server emits a small JSON structure saying which families
it serves, and every client on earth takes it at its word.

That is the correct design — a protocol that tried to verify claims would need to run every method to
check, which is the thing the declaration exists to avoid — but it means **the declaration is a
promise, and promises break in specific ways**. Three of them, and they are worth naming because they
fail differently:

| Kind of drift | What it looks like | Who caused it |
| --- | --- | --- |
| **Over-declaration** | family declared, nothing in it, or nothing that works | usually a library, not a person |
| **Under-declaration** | family works, declaration does not mention it | a hand-rolled server that registered a handler and forgot the capability |
| **Staleness** | declaration was true when it was cached and is not now | a deployment |

You have already met the first, and it was nobody's fault.
[1.2](../01-what-a-server-declares/1.2-nobody-types-the-declaration.md) measured an empty `FastMCP`
declaring `tools`, `resources` and `prompts` with none of the three implemented. No engineer typed
that. A constructor did.

The second is rarer and more dangerous, because it fails in the *safe* direction and therefore never
gets fixed. A server that serves prompts without declaring them works perfectly for every client that
ignores declarations and is invisible to every client that reads them. Nobody files a bug about a
feature they cannot see.

The third is the one that costs an evening, and it gets its own part:
[5.2](../05-failure-lab/5.2-the-family-that-went-away.md).

The sentence to keep is short. **A declaration tells you what to try. It never tells you what will
work.**

## Why Sutra needs it

Because `sutra-mcp` is currently an over-declarer, and Day 45's audit is going to say so.

Right now the server Day 34 built and Day 35 extended declares `tools`, `resources` and `prompts`. By
the end of Day 35 all three had something in them, so the declaration became accurate — but it was
accurate the way a stopped clock is right twice a day. It was never decided. If Day 39's database
tools had been the only additions and nobody had written a resource, the declaration would still have
said `resources`, and a host would still have built a tab for it.

The module this day asks you to write, `sutra_mcp/capabilities.py`, exists to turn that accident into
a decision. Not by changing what `FastMCP` emits — you cannot, and
[2.2](../02-discovery-without-sessions/2.2-the-request-your-sdk-cannot-send.md) explained why — but by
writing down the families Sutra *intends* to declare and failing a check when the two disagree.

The client half matters just as much on Day 44. Sutra mounts strangers' servers, and a stranger's
declaration is a stranger's promise. Day 44 hardens the client against servers that are slow or
absent. This is the softer version of the same problem: a server that is up, answering, and wrong
about itself.

## The mechanism

Here is the shape of the trap, in the smallest code that shows it. A server declares a family
because a handler exists, and the handler does not work:

```python
TOOLS = ["lookup_ticket", "search_kb", "export_archive"]
IMPLEMENTED = {"lookup_ticket", "search_kb"}


@server.list_tools()
async def _list_tools() -> list[Tool]:
    return [
        Tool(name=n, description=f"{n} over the wire", inputSchema={"type": "object"})
        for n in TOOLS
    ]


@server.call_tool()
async def _call_tool(name: str, arguments: dict[str, Any]) -> list[TextContent]:
    if name not in IMPLEMENTED:
        raise NotImplementedError(f"{name} was declared but never written")
    return [TextContent(type="text", text=f"{name} ran")]
```

**Line by line:**

- `TOOLS` is what the catalogue advertises; `IMPLEMENTED` is what the code can actually do. Keeping
  them as two separate names is the whole point — in a real codebase they are the same drift, spread
  across two files, and nothing joins them up.
- `export_archive` is in the first and not the second. That is the entire bug, and it is one line of
  a list. Somebody added a tool to the catalogue in a hurry, meaning to write the body next.
- `raise NotImplementedError(...)` inside the handler does **not** produce a JSON-RPC error. Day 34's
  [4.1](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.1-the-tool-said-no.md)
  established that the SDK catches every exception from a tool body and returns a result with
  `isError: true` and `str(exception)` as the text. So this failure arrives as a *successful call*
  and the model is the first thing to read about it.
- `inputSchema={"type": "object"}` with no properties, on all three, because the schema is not what is
  being taught here. Day 34's section 2 is where a real declaration comes from.

And a resource that is listed and cannot be read:

```python
@server.list_resources()
async def _list_resources() -> list[Resource]:
    return [Resource(uri=u, name=u.rsplit("/", 1)[-1], mimeType="text/markdown") for u in RESOURCES]


@server.read_resource()
async def _read_resource(uri: Any) -> str:
    raise FileNotFoundError(f"{uri} is listed but not on disk")
```

**Line by line:**

- Registering `list_resources` is what puts `resources` in the declaration —
  [1.2](../01-what-a-server-declares/1.2-nobody-types-the-declaration.md)'s `ListResourcesRequest`
  test. The family is now promised.
- `read_resource` raising is the second half of the promise failing. Day 35's
  [2.3](../../../day-35-resources-and-prompts/parts/02-the-shelf/2.3-the-miss-that-must-be-an-error.md)
  established that a resource miss must be an error rather than empty content, so this is the correct
  behaviour for a genuine miss — and indistinguishable from a wholesale lie.
- `uri.rsplit("/", 1)[-1]` names the resource after its filename. Cosmetic, and it is here so the
  output is readable rather than a column of full URIs.

The point of putting both in one server is that the declaration is identical either way. Print it and
you get `['resources', 'tools']` — two families, both promised, four promises underneath them, two of
which are lies. Nothing in the declaration hints at which.

## When it breaks

The break is a client that plans work from the declaration.

A host reads `resources` and pre-fetches every listed resource into a cache at start-up, so the first
user question is fast. It gets:

```text
BROKEN  resource:file:///kb/refunds.md     file:///kb/refunds.md is listed but not on disk
```

Start-up fails, or worse, start-up succeeds with an empty cache and every later read is a miss that
nobody attributes to this.

The tool version is quieter and therefore worse:

```text
BROKEN  tool:export_archive                export_archive was declared but never written
```

That line came back as `isError: true` on a **successful** call, which means every metric that counts
JSON-RPC errors saw nothing. The model saw the string *"export_archive was declared but never
written"*, decided that was a temporary problem, and tried again. Day 34's
[4.3](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.3-the-message-that-escaped.md)
is the other half of this: an exception message becomes model-facing text, so a `NotImplementedError`
you wrote for yourself is now a sentence in a customer-facing loop.

The smallest fix is not to make the declaration honest by hand — that is a second source of truth and
it will drift. It is to **check it**, once, in a place that fails loudly:
[3.2](3.2-probing-every-promise.md) is that check.

## In production

**What a professional writes instead:** a start-up self-test on the server, not a hope on the client.
Before a server accepts traffic it calls its own catalogue and its own handlers once, and refuses to
start if a promise does not hold. That is a smoke test, it costs one pass over a small list, and it
converts an over-declaration from a customer's problem into a deploy that did not happen.

**What degrades at scale:** the blast radius of one bad promise. A single server with a broken
declared family is a bug. Forty mounted servers, each declaring three families, is a hundred and
twenty promises no human has ever checked, and the failures arrive as an error rate spread across
teams that do not know about each other. This is where an audit stops being paperwork.

**The failure mode that only appears with real traffic:** partial implementations that work for the
common argument. A tool that handles the three ticket types on the demo data and raises on the fourth
is declared, listed, and correct in every test — until a real archive contains the fourth. The
declaration was never the problem; the promise was finer-grained than the declaration can express, and
no protocol field will ever fix that.

**The review comment a senior engineer leaves:** *"we advertise `export_archive` in `tools/list` and
the handler raises `NotImplementedError`. That comes back as a successful call with `isError: true`,
so it is invisible in our error dashboards and the model reads the exception text and retries. Either
implement it or take it out of the catalogue — a name in a list is a promise, and right now we are
making one to every client that connects."*

**The interview question:** *"a server tells you it supports resources. How much do you trust that?"*
The answer: *"As far as knowing what to try, and no further. Nothing in the protocol verifies a
declaration — it is derived from which handlers are registered, and on the high-level Python server
class every handler is registered by the constructor, so a completely empty server already declares
three families. So there are three ways it drifts: over-declaring, which is usually a library rather
than a person; under-declaring, which is dangerous because it fails safe and nobody reports it; and
staleness, where the declaration was true when it was cached. What I would actually do is probe: call
every listed tool once and read every listed resource once, at start-up, and refuse to serve traffic
if a promise does not hold. It costs one pass over a small list and it moves the failure from the
customer to the deploy."*
