# 3.3 — Declared before anything runs

## One-line answer

Every mechanism this curriculum has met since Day 34 obeys one rule — **whatever a server will do to
a client is declared before the client does anything** — and that rule is not a coincidence, it is
the design stance that makes a stranger's server reviewable at all.

## The story

You take a rented flat and the agent hands you two sheets of paper before the keys.

The first lists every fitting in the flat: four fans, two geysers, a gas connection, seven windows,
one of them with a cracked pane, noted. The second is the same list with a column for you to sign
next to each line. You walk the rooms with the sheet, you find that one fan is missing and one extra
cupboard is there, and both get written in before anybody signs anything.

The sheet is not there because anyone expects to be cheated. It is there because in eleven months,
when you move out and somebody says the pane was fine when you arrived, the argument is already
settled — it was settled on the day you arrived, in writing, by both parties, before you had put a
single box down.

The inventory is not a record of the flat. It is the thing that makes the eleventh month arguable.

## The idea in plain language

Look at what has been declared up front, across the whole of Phases 5 and 6, and the pattern is
unmistakable:

| Mechanism | Declared before use | Taught on |
| --- | --- | --- |
| a tool | name, description, `inputSchema` — before any call | [Day 34](../../../day-34-building-sutra-mcp-tools/parts/02-function-to-declaration/2.2-the-schema-is-all-they-get.md) |
| a resource | URI, name, mime type — before any read | [Day 35](../../../day-35-resources-and-prompts/parts/02-the-shelf/2.1-an-address-not-a-call.md) |
| a prompt | name and its typed arguments — before any `get` | [Day 35](../../../day-35-resources-and-prompts/parts/03-the-card/3.2-arguments-are-declared.md) |
| a long job | a handle contract; state travels in the payload | [Day 36](../../../day-36-long-jobs-and-tasks/parts/03-the-handle/3.1-a-name-the-server-mints.md) |
| a question to the user | a schema for the answer, before the question | [Day 37](../../../day-37-auth-and-elicitation/parts/03-the-question/3.2-a-form-the-till-can-print.md) |

| **a user interface** | the `ui://` template, before it is ever rendered | [4.2](../04-a-server-that-draws/4.2-the-template-is-declared-the-data-flows-in.md) |

Seven mechanisms, one rule. The rule is worth stating in one sentence because it is the sentence you
will use in a design review for the rest of your career:

**A client must be able to review everything a server will ever do to it, before anything runs.**

That is a stance about *when*, not about *what*. Nothing in it forbids a server from being powerful.
It forbids a server from being powerful **in a way that arrives at run time**, because a thing that
arrives at run time cannot be reviewed, cannot be pinned, cannot be diffed between deployments, and
cannot be refused by a policy that has not seen it yet.

The opposite design is easy to describe and it is what almost every early integration does: the tool
returns whatever it likes and the client does whatever the return value says. It is faster to build
and it has no review surface at all. Day 29's audit of third-party skills was the same argument in a
different medium — you can read a skill folder before you load it, and that reviewability is the whole
of its safety.

The word for what the declaration buys is **pinnable**. Day 40 taught allowlists over tool names; a
name can be allowlisted because it exists before it is used. Nothing can be allowlisted that is minted
at the moment of use.

## Why Sutra needs it

Two of Sutra's remaining days are direct applications of this rule, and one of them is today.

**Today.** `sutra_mcp/capabilities.py` writes down what the server declares. It is the inventory
sheet: a list, in version control, of what a stranger may expect, checked against reality by
`lab/gate.py`. Without it the declaration is whatever the SDK emitted this week, and there is nothing
to diff.

**Day 45.** The audit's core question is whether `sutra-core`'s data boundary is reviewable. Every row
of that audit is *"was this declared before it was used"*, and a server that ships anything
undeclared fails the gate regardless of how well it works.

There is also the negative case, which is the whole of section 4. MCP Apps let a server put a **user
interface** in front of your user. That is the largest thing a server has ever been able to do to a
client, and the reason it is tolerable at all is that the interface is a pre-declared resource rather
than a blob in a tool result. Take the pre-declaration away and the feature is unshippable. Section 5's
[5.1](../05-failure-lab/5.1-the-panel-that-grew-a-button.md) is what taking it away looks like.

## The mechanism

The rule has a shape in code, and it is the same shape every time. Something is registered into a
catalogue, then something else refers to it **by name**:

```python
PANEL_URI = "ui://sutra/approval.html"

Resource(
    uri=PANEL_URI,
    name="approval_panel",
    description="Approve or reject one ticket closure.",
    mimeType="text/html;profile=mcp-app",
)

Tool(
    name="close_ticket",
    description="Close one ticket after a human approves.",
    inputSchema={"type": "object", "properties": {"ticket_id": {"type": "string"}}},
    _meta={"ui": {"resourceUri": PANEL_URI}},
)
```

**Line by line:**

- `PANEL_URI` is a constant used in two places: the resource that *is* the panel and the tool that
  *points at* the panel. One string, two references — which is what makes it an address rather than a
  payload.
- The `Resource` is a catalogue entry. It appears in `resources/list` and can be read, reviewed, hashed
  and cached by the host **before any tool is ever called**.
- The `Tool` carries no HTML. It carries `_meta.ui.resourceUri`, which is a pointer. The largest thing
  this tool can hand a client is a reference to something already on the shelf.
- `mimeType="text/html;profile=mcp-app"` is how a host tells a UI resource from a plain HTML file it
  should not render. The profile parameter is the discriminator, and
  [4.2](../04-a-server-that-draws/4.2-the-template-is-declared-the-data-flows-in.md) is where it
  matters.
- The alternative — a tool that returned the HTML in its result — would put the same bytes on the
  wire. The difference is entirely *when*, and *when* is the whole security property.

Contrast that with the shape the rule forbids:

```python
# what "declared before it runs" exists to prevent
async def close_ticket(ticket_id: str) -> dict[str, Any]:
    ticket = archive[ticket_id]
    return {"html": f"<p>{ticket['body']}</p><button>Approve</button>"}
```

**Line by line:**

- The markup is built inside the handler, from data read at call time. Nothing about it existed before
  the call, so nothing about it could have been reviewed.
- `f"<p>{ticket['body']}</p>"` interpolates a ticket body — text a stranger typed into a web form —
  directly into markup. [5.1](../05-failure-lab/5.1-the-panel-that-grew-a-button.md) is what that
  costs, measured.
- The return is a plain dictionary with an `html` key. There is no field in the MCP tool result schema
  that means "render this", so a client can only act on it by agreeing to a private convention — which
  means no policy layer, no allowlist and no audit understands it either.
- Even with the injection fixed, this shape is unreviewable by construction: the host cannot fetch the
  template in advance, cannot hash it, cannot compare today's against yesterday's, and cannot refuse
  it before it has already arrived.

## When it breaks

The rule breaks quietly, by exception, and the exception always sounds reasonable.

A tool needs one extra argument that depends on the caller's account tier. Rather than declaring two
tools or a union in the schema, somebody makes the schema depend on who is asking. It works. Then a
client caches `tools/list` — which it is entitled to do, with the `ttlMs` the server itself sent — and
serves the cached copy to a second caller on a different tier.

The specification forbids exactly this, and Day 34's
[3.1](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.1-the-list-and-who-may-keep-it.md)
recorded the sentence: a tool list **MUST NOT** vary per connection, with a narrow exemption for
authorization. What the caller sees when it breaks is not an error at all:

```text
{"jsonrpc":"2.0","id":9,"error":{"code":-32602,"message":"Invalid request parameters","data":""}}
```

A `-32602` on a call whose arguments match the schema the client is holding. Both sides are behaving
correctly. The schema the client has is a real schema this server really sent, to somebody else.

The smallest fix is to make the variation explicit rather than dynamic: two declared tools, or one
tool with an optional field, and the refusal at call time carrying a message that says which. A
declaration that changes shape per caller is not a declaration; it is a run-time value wearing one.

## In production

**What a professional writes instead:** a build-time artefact. The catalogue — tools, resources,
prompts, template URIs — is generated from the code, written to a file, and committed. A pull request
that changes what the server declares then shows that change as a diff, and a reviewer can see the new
capability without reading the implementation. This is the single highest-value hour of work in this
whole phase, and it costs about that.

**What degrades at scale:** the review, not the mechanism. Ten declared tools can be read by a human
before a deploy. Three hundred cannot, so the review moves to the diff, and the diff is only useful if
the artefact is deterministic — sorted, stable, no timestamps. Day 34's
[3.2](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.2-the-same-order-every-time.md)
made the tool list deterministic for a caching reason; this is the second reason, and it is the one
that matters to a human.

**The failure mode that only appears with real traffic:** a declaration that is correct and enormous.
Every declared tool is context the model carries on every turn, and Day 28's progressive-disclosure
work exists because that budget is real. Declaring everything up front is a security property that
costs tokens, and a server with two hundred honestly-declared tools has traded one problem for
another. The resolution is fewer, better tools — not fewer declarations.

**The review comment a senior engineer leaves:** *"this tool returns HTML in its result and the host
renders it. Nothing about that markup exists before the call, so there is nothing for us to review,
nothing to pin and nothing for the policy layer to refuse. Register it as a `ui://` resource and have
the tool point at it — same bytes, same feature, and now a diff on the template is a diff in the pull
request."*

**The interview question:** *"MCP makes you declare tools, resources, prompts and UI templates up
front. Why?"* The answer: *"So that a client can review everything a server will ever do to it before
anything runs. It is one stance applied seven ways — a tool's schema, a resource's URI, a prompt's
arguments, a task handle contract, an elicitation schema, the capability families, and a UI template.
Everything a stranger's server can do is a name in a catalogue you fetched, which means it can be
pinned, allowlisted, diffed between deploys and refused by policy. The moment a server can mint
something at call time — markup, a schema that varies by caller — none of those are possible, because
you cannot review a thing that does not exist yet. The cost is real, by the way: every declared tool
is context on every turn, so 'declare everything' is a token budget as well as a security property."*
