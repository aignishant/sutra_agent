# 1.1 — The hand that reaches first

## One-line answer

You do not choose between a tool, a resource and a prompt by looking at the data — you choose by
naming **whose hand reaches for it first**: the model's, the host program's, or the person's.

## The story

At the chemist's shop there are three ways to walk out with a box of medicine, and they are not
three ways of doing the same thing.

The first way: you describe your problem and the pharmacist decides. He asks two questions, thinks,
turns around, and takes something off the locked shelf behind him. You could not have taken it
yourself. He had to judge whether you should have it at all, and he wrote it in the register.

The second way: you pick it up yourself. The plasters and the cough drops are on the open shelf by
the door with the prices on them. Nobody judges anything. You already knew what you wanted before
you came in, and you would have been annoyed to queue for it.

The third way: you take a leaflet. There is a rack of printed leaflets by the till — *how to store
insulin*, *what to do about a burn*. Taking one is free and changes nothing. You take it because
you would rather have the shop's wording than invent your own.

Now the important part. All three might be about the same illness. The subject is not what separates
them. What separates them is **who reached out their hand first**: the pharmacist, you, or you again
but for different reasons — once to get a thing, once to get the words.

## The idea in plain language

MCP servers publish three kinds of thing, and they are separated by control rather than by content.
Day 32 introduced them in
[32.1.3](../../../day-32-mcp-stateless-core/parts/01-the-socket/1.3-tools-resources-prompts.md).
Today you have to *decide* with them, so the definitions need to be sharper than "tools act,
resources inform, prompts phrase".

Three terms, each defined by its first mover:

**A tool is model-initiated.** The server publishes a name, a description and a JSON Schema of the
arguments. The model reads that, decides to call it, and picks the arguments. Nobody else is in the
loop at the moment of choosing. That is why a tool is the surface that can have side effects and the
surface that needs a consent gate.

**A resource is host-initiated.** The server publishes an address — a **URI**, a string that names
one exact thing, like `ticket://4521` — and the host program decides what to read and when to put it
in front of the model. The model never chooses. It is handed the material, the way you are handed a
document before a meeting rather than being asked whether you would like one.

**A prompt is user-initiated.** The server publishes a named template with named arguments. A person
picks it out of a menu — the slash-command list in a chat client is the usual shape — supplies the
arguments, and the server returns finished messages. Neither the model nor the host chooses. A
person does.

Here is the same three-way split written out as the question you actually ask:

| Question | If the answer is yes | Wire methods |
| --- | --- | --- |
| Does something outside the server change, or must someone judge *whether* to do it at all? | **tool** | `tools/list`, `tools/call` |
| Is it data with a stable address that a program could have known to fetch? | **resource** | `resources/list`, `resources/read` |
| Is it a *way of asking* that we want every host to use identically? | **prompt** | `prompts/list`, `prompts/get` |

The 2026-07-28 specification says this in its own words, and it is worth having the exact phrasing
in your head because it is the sentence people misremember. The resources page opens its user
interaction section with:

> "Resources in MCP are designed to be **application-driven**, with host applications determining
> how to incorporate context based on their needs."

And the prompts page:

> "Prompts are designed to be **user-controlled**, meaning they are exposed from servers to clients
> with the intention of the user being able to explicitly select them for use. This refers to who
> decides when the prompt is used, not who authors its content. Prompt content is defined by the
> server."

Read that second quotation twice. **Who decides when** and **who wrote the words** are different
questions, and the prompt surface splits them deliberately: the server writes the wording, the
person decides to use it. That split is the whole reason the surface exists, and it is the thing
people get backwards.

(Both pages read live on 2026-09-04 —
`https://modelcontextprotocol.io/specification/2026-07-28/server/resources` and
`https://modelcontextprotocol.io/specification/2026-07-28/server/prompts`.)

One consequence, stated now so the rest of the day can lean on it: **the same data may appear behind
two doors, and the same action may not.** A ticket can be both `lookup_ticket` (a tool) and
`ticket://4521` (a resource), because reading it twice is harmless. A `close_ticket` can only ever be
a tool, because a second door onto it is a second way to close a ticket without a gate in front of
it. Part [1.3](1.3-should-lookup-ticket-stop-being-a-tool.md) is that argument in full.

## Why Sutra needs it

Because Sutra is about to publish, and everything it has ever published has been a tool.

`sutra/loop.py` holds `TOOLS = {"lookup_ticket": lookup_ticket, "search_kb": search_kb}` and nothing
else. Day 34 took those same two functions and put them over the wire in `sutra_mcp/tools.py`. If
today does nothing, `sutra-mcp` ships as a server whose entire vocabulary is *ask the model to decide
to call something* — which is the junk-drawer server every MCP audit complains about, and Day 45 is
the day that audit happens to Sutra.

## The mechanism

The rule is small enough to write as a function, which is a good sign — a design rule you cannot code
is usually a preference.

```python
# days/day-35-resources-and-prompts/lab/surface.py  (extract)
@dataclass(frozen=True)
class Candidate:
    """One thing Sutra could publish, described by the three questions."""

    name: str
    writes: bool  # does using it change anything outside the server?
    addressable: bool  # is there a stable name for the exact thing you want?
    needs_search: bool  # must someone choose arguments the caller does not know yet?


def surface(c: Candidate) -> str:
    """Return 'tool', 'resource' or 'prompt' for one candidate."""
    if c.writes:
        return "tool"
    if c.name in PHRASING:
        return "prompt"
    if c.needs_search or not c.addressable:
        return "tool"
    return "resource"
```

**Line by line:**

- `@dataclass(frozen=True)` gives a small immutable record with a generated `__init__`, so a
  candidate is described once and cannot be edited halfway through the run. `frozen` is not
  decoration: the whole point is that the three answers are fixed before the rule sees them.
- `writes` is asked first, and asked as *"does anything outside the server change"* rather than
  *"is it a write"*. Sending an email changes nothing in your database and is still a write.
- `addressable` asks whether a caller can name the exact thing it wants **before** the call. That is
  what a URI is: a name for one thing, not a query for a set of things.
- `needs_search` is the one people forget. Searching is not reading, because the caller does not know
  the address yet — the arguments have to be *chosen*, and choosing is what a model is for.
- `if c.writes: return "tool"` is first because it is the only branch that is about safety rather
  than convenience. A thing that changes the world goes behind the gated door, and no other answer is
  allowed to override that.
- `if c.name in PHRASING` looks like a cheat and is honest. There is no structural test that
  distinguishes *the house wording* from data; it is a judgement about what you are publishing, and
  the code says so instead of pretending.
- `if c.needs_search or not c.addressable: return "tool"` is the reason `search_kb` stays a tool. It
  has no stable address, so there is nothing for a host to fetch — the model must supply the query.
- The final `return "resource"` is the default only after three refusals. That ordering matters:
  resources are the cheapest door, so they are the one you fall into rather than the one you reach
  for.

everything a resource"*. Searching needs a query nobody has written down yet. There is no URI for
*"the article about people getting logged out"* until somebody decides those are the words. Deciding
words is a model's job, so it stays a tool — and that is not a compromise, it is the rule working.

## When it breaks

The rule breaks when a capability answers *yes* to two questions, and the commonest case is a read
that quietly writes.

A `resources/read` handler that increments a view counter, refreshes an access token, writes an audit
row, or lazily creates something on first read is a **write wearing a read's clothes**. Nothing in
the protocol stops you. The host, meanwhile, believes what the specification told it to believe: a
read is safe, so it may prefetch it, read it twice, read it speculatively, or hand it to a cache.

The failure does not arrive as an error. It arrives as a number that does not add up:

```text
dashboard shows 3 views on ticket 4521; the customer opened it once
```

The smallest fix is a rule you enforce in your own server rather than hope for in others: **a
`resources/read` handler may not write.** If it must write, it is a tool, however read-like it looks.
Day 40's allowlists are how you defend against the servers you did not write.

The second break is the mirror image: a *tool* whose only job is to hand back a fixed document. It
works, and it costs a model decision every single turn, which
[1.2](1.2-what-a-door-costs.md) prices exactly.

## In production

**What a professional writes instead:** the decision is made once, written down beside the handler as
a comment, and re-checked at review time — not re-argued per feature. A one-line rule beside each
registration (*"resource: read-only, addressable, host attaches it"*) survives the next engineer, and
a design argument in a chat log does not.

**What degrades at scale:** the number of surfaces grows and the *sorting* stops being obvious. With
six capabilities anyone can hold the argument in their head. With ninety, the shelf and the counter
blur, somebody publishes a `resources/read` that runs a report, and a host prefetches it on every
picker open. The rule has to be mechanical by then, which is why it is written here as a function
rather than as advice.

**The failure mode that only appears with real traffic:** hosts prefetch. A resource picker that
shows previews reads every resource it lists. A design that is fine when a human clicks one item is a
load test when a UI renders forty.

**The review comment a senior engineer leaves:** *"`get_active_incident` is a tool. Why? It takes no
arguments, it changes nothing, and the host knows when it wants it. That is a resource with a fixed
URI, and making it one removes a decision the model is currently getting wrong about one turn in
four."*

**The interview question:** *"How do you decide whether something should be an MCP tool or a
resource?"* The honest answer: *"by who initiates it. If the host already knows the address, it is a
resource, and a resource costs zero model decisions — the model can't forget to fetch something it
was handed. If the caller has to choose arguments the host doesn't have, like a search query, it's a
tool. And anything that changes state is a tool no matter how read-like it looks, because tools are
the surface that has a consent gate in front of it. The trap is doing it by content — 'tickets are
data so tickets are resources' — when search over tickets is genuinely a tool."*
