# 1.2 — What a door costs

## One-line answer

A tool costs a decision the model has to make and can get wrong on every turn; a resource costs
nothing at decision time, because the host already knew the address and simply handed the material
over.

## The story

Two rooms, the same exam, the same students, the same paper.

In the first room, the formula sheet is already on every desk when the students walk in. Nobody asks
for it. Nobody has to know it exists. It is simply there, face up, and every student who needs a
formula looks down at the desk and finds it.

In the second room, the formula sheet is at the front on the invigilator's table, and a notice on the
wall says you may ask for it. Most students ask. Some do not — not because they are careless, but
because they were halfway through a question, or they did not think this one needed it, or they
forgot the notice was there. Three of them hand in a paper where the arithmetic is fine and one
number is wrong, and the number is wrong because they never fetched the sheet.

The papers from the second room look exactly like the papers from the first room until you mark them.
Nothing was refused. Nobody was told no. The sheet was available, on the wall, in writing.

And there is a smaller cost in the second room that nobody notices at all: the notice on the wall
takes up wall space. It is read, silently, by every student, again and again, and it is competing for
attention with the actual questions.

## The idea in plain language

Both doors get the data to the model. They do not cost the same.

A **tool** is a door the model opens. To open it, the model must first notice the door exists, decide
that this turn needs it, and choose the arguments. That is a decision, and a decision has a failure
rate that is not zero. Sutra has already measured a version of this: Day 27's triage procedure needed
a step whose entire content was *remember to search the knowledge base*
([27.1.4](../../../day-27-authoring-first-skills/parts/01-extraction/1.4-steps-for-a-competent-stranger.md)),
and Day 27 also showed that writing the step down does not guarantee it is followed
([27.4.2](../../../day-27-authoring-first-skills/parts/04-the-authoring-loop/4.2-which-rung-did-it-climb.md)).

A **resource** is a door the *host program* opens, before the model is asked anything at all. The host
is ordinary code. It knows which ticket the user is looking at because the user clicked on it. It
reads `ticket://4521` and puts the text in the context, and the model is never asked to want it. A
decision that is never made cannot be made wrongly.

Two terms, because both are used from here on and both are easy to blur:

**A model decision** is any point in a turn where the model's output changes what happens next —
choosing to call a tool, choosing arguments, choosing not to call anything. It is the unit this part
counts in, rather than milliseconds, because latency is the cost you notice and a wrong decision is
the cost you pay.

**A tool declaration** is the name, description and JSON Schema that a server publishes for a tool and
a host puts into the model's prompt so the model knows the tool exists. Day 4 built one by hand
([4.1.2](../../../day-04-tools-by-hand/parts/01-the-schema/1.2-declaring-a-tool.md)). It is text, it
sits near the front of the prompt, and it is re-sent on every single turn. That is the notice on the
wall.

So the price list has two lines, and only one of them is obvious:

| | A tool | A resource |
| --- | --- | --- |
| decisions per turn | one, and it can go wrong | zero |
| prompt cost | the declaration, on every turn | nothing, unless the host attaches the data |
| who can forget it | the model | nobody |
| what a miss looks like | an answer with a fact missing | not possible; the data was already there |

The line people miss is the last one. When a model forgets to call `lookup_ticket`, it does not
report an error. It answers anyway, from the words in the customer's message, confidently and
plausibly, and the answer is a support reply that never read the ticket.

## Why Sutra needs it

Because Sutra's whole reason for touching MCP is to stop guessing, and one door guesses.

Day 3 built the loop and Day 4 built the tools, and ever since then `lookup_ticket` has been the
model's to call. That was correct while Sutra was one process with one caller. From Day 34 onward
`sutra-mcp` has *other* hosts — an IDE, a chat client, a partner's agent — and each of them will get
whatever surface Sutra publishes. Publish only tools and every one of those hosts inherits the miss
rate.

The arithmetic below is also what Day 43 will care about. A stateless server answers whatever arrives;
if what arrives is twelve `tools/call` requests per session per client rather than three
`resources/read` requests the host made once, that is a capacity number, not a style preference.

## The mechanism

The two doors, priced over one working session at the desk:

```python
# days/day-35-resources-and-prompts/lab/decision_cost.py  (extract)
TURNS = 12  # one working session at the support desk
MISS_RATE = 0.25  # how often the model forgets to fetch the thing it needed
DECL_TOKENS = 84  # tokens the tool declaration costs, in every prompt, on every turn


def tool_door(turns: int, miss_rate: float) -> dict[str, float]:
    """The ticket text arrives as a tool call the model must choose to make."""
    return {
        "model decisions": turns,
        "turns with no ticket text": round(turns * miss_rate, 1),
        "declaration tokens carried": turns * DECL_TOKENS,
    }


def resource_door(turns: int) -> dict[str, float]:
    """The ticket text is attached by the host before the turn starts."""
    return {
        "model decisions": 0,
        "turns with no ticket text": 0.0,
        "declaration tokens carried": 0,
    }
```

**Line by line:**

- `TURNS = 12` is one working session, not a benchmark. The point of a small number is that the
  difference shows up inside a single afternoon rather than only in a quarterly report.
- `MISS_RATE = 0.25` is **an assumption, and it is written as a constant so it can be argued with**.
  It is not measured on Sutra, and this part does not pretend it is. Change it to `0.05` and the
  conclusion still holds in the same direction; change it to `0.0` and you are asserting that a model
  never forgets a tool, which Day 27 already showed is false for the equivalent instruction.
- `tool_door` returns `turns` decisions because the choice is re-made every turn. This is the number
  people forget: it is not one decision for the session, it is one per turn, and each is independent.
- `turns * miss_rate` is the number of turns that produce an answer with no ticket text behind it.
  Note what it is *not*: it is not an error count. There is no error.
- `DECL_TOKENS = 84` is the size of one tool declaration and it is carried whether or not the tool is
  used, because the model cannot choose a tool it has not been told about. Day 26 measured skill cards
  at 83 tokens each ([26 hub](../../../day-26-loading-skills-into-adk/LESSON.md)); a tool declaration
  sits in the same place in the prompt and costs the same order.
- `resource_door` returns zeros for all three, and it takes `turns` and ignores it deliberately —
  the signature matches so the two can be printed side by side, and the ignored argument is the
  finding: the cost does not scale with turns, because there is no per-turn choice.
- `dict[str, float]` rather than a dataclass, because these three numbers exist to be printed next to
  each other once and never to be passed around.

```bash

```

**Line by line:**

- From the repository root. **Zero generations** — this is multiplication.

Measured on 2026-09-04:

```text
one desk session: 12 turns, model miss rate 25%

                               model decisions     turns with no ticket text    declaration tokens carried
tool door                                   12                           3.0                          1008
resource door                                0                           0.0                             0

turns rescued by moving one door: 3.0
the resource door cannot be forgotten, because nobody decided to open it
```

**Three turns.** Out of twelve, three replies went out without the ticket text, and all twelve looked
like successes. That is the cost of the second exam room, and it is invisible in every log you have,
because "the model did not call a tool" is not an event anyone records.

The `1008` is the smaller half of the finding and worth one sentence. Eighty-four tokens, twelve
turns, and the declaration is paid even on the three turns where the tool was not used and on the
nine where it was. A resource that the host attaches costs the ticket's own text and nothing else.

## When it breaks

The arithmetic breaks when the host does not, in fact, know the address.

Here is the case that ruins the table: a customer writes *"my export is broken again, same as last
time"*. There is no ticket id in that sentence. The host has nothing to attach. The only way to find
the right ticket is to search, and searching means choosing search terms, and choosing search terms is
exactly the decision that a model exists to make.

If you take the arithmetic above as a slogan — *resources are free, so make everything a resource* —
you will publish `ticket://{id}` and then discover the host cannot fill in `{id}`. The failure is not
an error message. It is a host that reads nothing, a model that has no tool to search with, and an
answer built entirely out of the customer's own sentence.

The smallest fix is the rule from [1.1](1.1-the-hand-that-reaches-first.md), stated the other way
round: **a resource is only cheaper when the address is already known.** When it is not known, finding
it is a search, and a search is a tool. That is why `search_kb` stays a tool in
`lab/surface.py`'s output and why that row is the one that keeps the rule honest.

## In production

**What a professional writes instead:** both doors, on purpose, with the split written down. The host
attaches `ticket://<id>` whenever the user is looking at a ticket, and a `search_tickets` tool exists
for when they are not. The decision is recorded next to the registration, not in a design document
nobody opens.

**What degrades at scale:** the miss rate stops being a number in a table and becomes a support
metric. At twelve turns a day, three misses is an anecdote. At twelve thousand, it is a weekly
complaint about replies that "did not read the ticket", arriving from a channel that will never
connect it to a tool-choice statistic, because nothing in the pipeline emits one.

**The failure mode that only appears with real traffic:** the miss rate is not constant. It goes up
when the prompt gets longer, when more tools are declared, and when the customer's message is itself
long and urgent — which is exactly the ticket you least want answered without evidence. A rate you
measured on your quiet test cases is a rate measured under the wrong conditions.

**The review comment a senior engineer leaves:** *"we are counting tool calls in the dashboard. We are
not counting the turns where the model called nothing and answered anyway. That second number is the
one that costs us, and right now nobody can produce it. Log the turns where a reply cites no source."*

**The interview question:** *"You keep saying resources are cheaper than tools. Cheaper in what?"* The
honest answer: *"in decisions, not in latency. A tool costs the model a choice on every turn — notice
the tool, decide it applies, pick the arguments — and that choice has a non-zero failure rate that
shows up as a confident answer with no evidence behind it, not as an error. A resource costs zero
choices because the host already knows the URI and attaches the content before the turn starts. The
catch is that this is only true when the address is known. If finding the thing requires choosing
search terms, that is a tool and no amount of resource design makes it cheaper."*
