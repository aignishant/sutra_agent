# 6.2 — The shelf a stranger can use

## One-line answer

Every optional metadata field — `title`, `description`, `mimeType`, `annotations` — is what a host
needs to build a picker out of your server, so a shelf that is technically valid and metadata-poor is
a shelf nobody can find anything on, and the day's gate is a script that says so.

## The story

The office storeroom has forty cardboard boxes in it and thirty-one of them say **MISC** in marker pen.

Whoever packed them was not lazy. They were in a hurry on the last day of the move, and at the time
they knew perfectly well that the third box on the left had the projector cables in it. The knowledge
was real. It just lived in one person's head for about a week, and then it did not live anywhere.

Now a new person needs a projector cable. Everything in that room is present, correctly packed and
undamaged. There is no way to find anything except opening boxes, and after the fourth box they give
up and order a new cable, which arrives on Thursday and costs nine hundred rupees. The room did not
fail. The labels did.

## The idea in plain language

Go back to the field table in [2.1](../02-the-shelf/2.1-an-address-not-a-call.md). Of the eight fields
on a resource, exactly two are required: `uri` and `name`. Everything else is optional, and everything
else is what makes the resource usable by somebody who did not write it.

The same is true of a prompt: `name` is required, and `title`, `description` and the per-argument
descriptions are not ([3.2](../03-the-card/3.2-arguments-are-declared.md)).

So a perfectly conformant server can publish this:

| `uri` | `name` |
| --- | --- |
| `ticket://{ticket_id}` | `ticket_resource` |
| `kb://{key}` | `kb_resource` |
| `archive://summary` | `archive_summary` |

Nothing is wrong with it. A validator passes it. And a host trying to render a picker has three rows of
snake_case Python identifiers to show a person, no idea what type any of them returns, and no basis for
ranking them.

**Annotations** are the field that goes furthest and gets skipped most, so it is worth defining
properly. The specification gives three
(`https://modelcontextprotocol.io/specification/2026-07-28/server/resources`, read 2026-09-04):

> * **`audience`**: An array indicating the intended audience(s) for this resource. Valid values are
>   `"user"` and `"assistant"`.
> * **`priority`**: A number from 0.0 to 1.0 indicating the importance of this resource. A value of 1
>   means "most important" (effectively required), while 0 means "least important" (entirely optional).
> * **`lastModified`**: An ISO 8601 formatted timestamp indicating when the resource was last modified

And what a host does with them:

> Clients can use these annotations to:
>
> * Filter resources based on their intended audience
> * Prioritize which resources to include in context
> * Display modification times or sort by recency

Read that middle line against [5.2](../05-failure-lab/5.2-the-read-that-filled-the-window.md). *Prioritize
which resources to include in context* is the host deciding what to drop when the window is tight, and
`priority` is the only input you get to give it. A resource with no priority is a resource the host
ranks by nothing.

This is the same problem Day 28 measured for skills, arriving with different field names. There, the
finding was that a description is a routing decision rather than documentation
([28.2.1](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.1-a-description-is-a-routing-row.md)),
and that a shelf gets crowded faster than anyone plans for
([28.2.4](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.4-the-crowded-shelf.md)).
Everything Day 28 said about skill cards applies to resource and prompt metadata unchanged, and the
audience is now a host you have never met rather than your own agent.

## Why Sutra needs it

Because Day 45 audits this, and because `sutra-mcp` is meant to be used by somebody other than Sutra.

The Phase 6 gate on Day 45 is a full MCP audit of what days 32 to 44 built. A shelf with no titles and
no descriptions is a finding on that day, and the cheapest time to fix it is the day it is written —
while there are three entries and the person who knows what they are is still in the room.

There is a sharper reason too. Every one of these fields is *the server's opinion travelling with the
data*. Sutra knows that a ticket body matters more than a count of tickets, that a raw ticket is for
the model rather than for the person, and that the knowledge-base article is Markdown rather than
plain text. None of that is inferable from a URI. If it is not in the metadata it does not cross the
boundary, and the host guesses.

## The mechanism

The day's gate reads the shelf and grades it. Every rule in it is a field a host actually needs:

```python
# days/day-35-resources-and-prompts/lab/shelf_audit.py  (extract)
def grade_resources(server: object) -> None:
    """Every published address needs a title, a description and a MIME type."""
    manager = getattr(server, "_resource_manager", None)
    if manager is None:
        note("the server exposes no resource manager - is it a FastMCP instance?")
        return
    items = list(manager.list_resources()) + list(manager.list_templates())
    if not items:
        note("nothing is on the shelf: resources/list and templates/list are both empty")
    for item in items:
        address = getattr(item, "uri", None) or getattr(item, "uri_template", "?")
        for field in ("title", "description", "mime_type"):
            if not getattr(item, field, None):
                note(f"resource {address}: no {field}")
        if getattr(item, "annotations", None) is None:
            note(f"resource {address}: no annotations, so no host can rank it")
```

**Line by line:**

- `getattr(server, "_resource_manager", None)` reaches for a private attribute, and the leading
  underscore is a warning the audit is choosing to accept. There is no public way to enumerate a
  FastMCP server's registrations in `mcp==1.29.1`, so the honest options are this or driving the server
  over a transport. The `if manager is None` branch is what makes the choice safe: when a future
  release renames it, the audit reports a finding instead of crashing.
- `list_resources() + list_templates()` grades **both lists**, because a template is a published
  address too and it is the one people forget — it lives in the other listing
  ([2.4](../02-the-shelf/2.4-one-label-for-a-family.md)) and so it escapes an audit that only looked at
  one.
- `getattr(item, "uri", None) or getattr(item, "uri_template", "?")` gets an address out of either
  kind of item. A concrete resource has `uri`; a template has `uri_template`. The `"?"` fallback means
  a finding can always name something, even for an object shaped like neither.
- The three fields checked are `title`, `description` and `mime_type` — the SDK's Python spellings,
  not the wire's `mimeType`. Two vocabularies again, and mixing them up produces an audit that reports
  every resource as broken.
- `if not getattr(...)` rather than `is None`, deliberately: an empty string is as useless as a missing
  field and should be a finding too. A `description=""` passes a null check and tells a reader nothing.
- The annotations check is `is None` rather than falsy, because an `Annotations` object with nothing
  set is still a decision somebody made, and reporting it would be nagging rather than auditing.
- `note(...)` appends and returns. Nothing raises. An audit that stops at the first problem makes you
  run it once per problem, which is the slowest possible way to fix five things.

The prompt half asks the equivalent questions, and one extra:

```python
# days/day-35-resources-and-prompts/lab/shelf_audit.py  (extract)
    for prompt in prompts:
        if not getattr(prompt, "description", None):
            note(f"prompt {prompt.name}: no description, so nobody knows when to pick it")
        for argument in getattr(prompt, "arguments", None) or []:
            if not getattr(argument, "description", None):
                note(f"prompt {prompt.name}: argument {argument.name} has no description")
```

**Line by line:**

- The prompt's own `description` is checked first, because that is the line a person reads in a
  slash-command menu before they pick anything.
- The inner loop is the rule that gets missed everywhere: **each argument needs its own description.**
  A person is being asked to type a value into a box labelled `ticket_id`, and `ticket_id` is not an
  explanation ([3.2](../03-the-card/3.2-arguments-are-declared.md)).
- `getattr(prompt, "arguments", None) or []` handles both a missing attribute and a `None` value, so a
  prompt with no arguments is not a crash. `or []` after `getattr` is doing the second half of that
  and is why there is no separate check.
- The messages say **why**, not just what. *"no description, so nobody knows when to pick it"* is a
  finding somebody will act on; *"missing field: description"* is a finding somebody will suppress.

Run it:

```bash
uv run python days/day-35-resources-and-prompts/lab/shelf_audit.py; echo "exit: $?"
```

**Line by line:**

- **Zero generations.** It builds a server object in-process and reads its registrations; nothing is
  spawned and nothing is sent anywhere.

Red, and correctly red. It will stay red through Day 34's arrival and go green only when

You can see what a graded shelf looks like without waiting, because `lab/shelf.py` is registered the
way the audit wants. Its `resources/list` line from `read_shelf.py`:

```text
resources/list
   archive://summary    archive_summary  mime=text/plain ann=audience=['user', 'assistant'] priority=0.3
```

Compare the two annotations across the lab's three registrations and notice they are not copies of each
other:

| Resource | `audience` | `priority` | Why |
| --- | --- | --- | --- |
| `archive://summary` | user and assistant | 0.3 | a person may want the counts; include it if there is room |
| `ticket://{ticket_id}` | assistant only | 0.9 | the model reasons over it; the person already has the ticket open |
| `kb://{key}` | assistant only | 0.7 | supporting evidence, wanted less often than the ticket itself |

Three lines of metadata carrying three genuine judgements that only Sutra is in a position to make.
Copy-pasting the same annotation onto all three would have been faster and would have communicated
nothing.

## When it breaks

The break is that nothing breaks. That is the whole difficulty.

A metadata-poor server starts, serves, passes every conformance check and answers every request
correctly. There is no error, no warning, no log line and no failing test. The cost is entirely on the
other side of the boundary, where a host renders a picker of Python identifiers and a person scrolls
past your server to one that told them what it had.

The symptom, when it finally arrives, is not a bug report:

```text
"we connected your server but the team ended up not using it, they couldn't tell what anything was"
```

The second break is a `mimeType` that is wrong rather than missing, and this one does have a visible
effect. Return Markdown labelled `text/plain` and a host renders your knowledge-base article with every
asterisk and hash visible, in a chat window, to a customer-facing agent. Nothing errored; you told the
reader how to parse it and the reader believed you.

The third break is `priority` used as a wish rather than a ranking. Everything at `0.9`, because
everything feels important when you are writing it. A host that drops low-priority resources under
context pressure now has nothing to drop and drops by some rule of its own, which is exactly the
outcome the field existed to prevent. A priority scale where nothing is low is not a scale.

## In production

**What a professional writes instead:** metadata is written at registration time, not added later,
because later never comes and the person who knew is gone. `title` and `description` are written for a
stranger — the test is whether somebody who has never seen your system could pick correctly from the
listing alone. `priority` is assigned relative to the other resources on the same server and is
revisited when one is added, which makes it a small, real design conversation rather than a field.

**What degrades at scale:** the shelf crowds. Three resources need no ranking; thirty need one, and by
then the sensible priorities are a redistribution of every existing value rather than a choice about
the new one. `lastModified` becomes load-bearing at the same point — a host sorting by recency is a
useful picker and an impossible one if half the entries have no timestamp.

**The failure mode that only appears with real traffic:** `audience` filtering does something you did
not intend. A host that honours `audience: ["assistant"]` may hide the resource from its own picker
entirely, so a person who wants to look at a ticket cannot find it — and you marked it that way for
sound reasons about context. Annotations are hints, but they are hints that a real client acts on, so
they need to be chosen by imagining a host that obeys them literally.

**The review comment a senior engineer leaves:** *"every resource in this file has
`annotations=Annotations(audience=['assistant'], priority=0.9)`. Either that is copy-paste or we
genuinely think a summary count matters as much as the ticket body. If it is the second, the priority
field has stopped meaning anything and a host has nothing to drop when the window is tight."*

**The interview question:** *"Most of the metadata on an MCP resource is optional. Why bother?"* The
honest answer: *"because the required fields are a URI and a name, and neither of those is usable by
someone who did not write the server. `title` and `description` are what a host shows in a picker,
`mimeType` is how the content gets parsed, and `annotations` carry the one thing only the server knows
— who this is for and how much it matters, which is what a host uses to decide what to drop when the
context window is tight. None of it fails loudly. A metadata-poor server is completely conformant and
completely unusable, and the way that arrives is as a team quietly not adopting it. We turned the check
into a script with an exit code so it fails in CI instead."*
