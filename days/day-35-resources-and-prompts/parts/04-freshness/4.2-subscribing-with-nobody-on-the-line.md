# 4.2 — Subscribing with nobody on the line

## One-line answer

"Subscribe to a resource" survived the stateless rewrite by becoming **one long-lived request the
client opens on purpose** — `subscriptions/listen` — which means the held connection did not disappear,
it became something you have to ask for, pay for and re-establish yourself.

## The story

At the bank there are two ways to wait for your number.

You can sit facing the display. Your number appears the instant it is called, and you are up and at the
counter before the beep has finished. It costs you a seat and it costs you your attention, and you
cannot go and do anything else while it is happening. If you step outside to take a call and your
number goes past, nobody at the bank is holding it for you.

Or you can go across to the tea stall and come back to look every so often. You get your errands done.
You will also, sometimes, arrive back to find your number was called four ahead of where you thought,
and the display cannot tell you that — it only shows the current number, not the ones you missed.

The bank has no third option to offer you. It does not know who you are, it did not take your phone
number, and it is not going to ring you. Somebody has to keep watching, and the only question is who is
sitting there while it happens.

## The idea in plain language

Before the 2026-07-28 revision, a client subscribed with an RPC called `resources/subscribe` and the
server *remembered*. It kept a list of who was watching what, attached to the connection, and pushed
notifications down it. That worked because there was a connection and it belonged to one server
instance.

Section 2 of the revision deleted the handshake and the session
([32.2.1](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.1-the-call-that-remembered-you.md)),
which removed the place that list lived. What replaced it is described in one sentence
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions`, read
2026-09-04):

> "`subscriptions/listen` opens a long-lived notification stream from the server to the client. Unlike
> one-off requests, the stream stays open and delivers notifications until the client cancels it. It
> replaces the former `resources/subscribe` RPC and the HTTP GET endpoint."

Read that carefully, because the honest reading is uncomfortable. **The connection did not go away.**
A stream that stays open is a connection somebody is holding. What changed is that it is now a
*request the client made deliberately*, with an id, a filter and a lifetime, instead of a property of
having connected at all.

Three mechanics follow from that, and each one is a cost made visible.

**The client says exactly what it wants.** The request carries a `notifications` filter, and the server
**MUST NOT** send anything that is not in it:

| Field | Type | What it asks for |
| --- | --- | --- |
| `toolsListChanged` | boolean | `notifications/tools/list_changed` |
| `promptsListChanged` | boolean | `notifications/prompts/list_changed` |
| `resourcesListChanged` | boolean | `notifications/resources/list_changed` |
| `resourceSubscriptions` | string array | `notifications/resources/updated` for these exact URIs |

`resourceSubscriptions` is the one this day cares about: a list of URIs, sent by the client, and the
server watches them for the life of that stream.

**Every message on the stream is tagged.** The first thing the server sends is
`notifications/subscriptions/acknowledged`, carrying a subscription id in `_meta` under
`io.modelcontextprotocol/subscriptionId`, and the id is the JSON-RPC id of the `subscriptions/listen`
request itself. Everything after it carries the same tag. On stdio, where every subscription shares one
pipe, the specification says clients **MUST** use that field to work out which stream a notification
belongs to.

The acknowledgment is also a **negotiation result**, and this is the field to read rather than assume:

> "The `notifications` field in the acknowledgment reflects the subset the server agreed to honor.
> Notification types the server does not support are omitted."

So a client that asked for resource updates and got an acknowledgment without `resourceSubscriptions`
in it has been told *no*, politely, in a message it will otherwise ignore.

**Nothing survives a reconnect.** The rule is stated for stdio and it is the whole architecture in one
line:

> "On **stdio**, if the connection is terminated and then re-established, the client **MUST** re-send
> `subscriptions/listen` to re-establish its subscriptions — the server holds no subscription state
> across reconnections."

That is the sentence that tells you what "stateless" bought and what it cost. The server is not keeping
a subscriber table between connections, so a restart, a deploy or a dropped TCP connection ends every
subscription — silently, unless the server got a chance to close gracefully.

The graceful close is worth knowing because it is the only signal you get: a server ending a
subscription on purpose **SHOULD** respond to the original `subscriptions/listen` request with a
completion result before closing. A stream that just stops carries no response, and the specification
says a client **MAY** treat that as a trigger to reconnect. So *"did the server say goodbye?"* is a
real distinction with a real code path behind it.

## Why Sutra needs it

Because the honest answer for `sutra-mcp` is that it will not implement this, and knowing why is worth
more than implementing it.

Sutra's tickets change when a customer replies. A host that has cached `ticket://4521` would like to
know. `subscriptions/listen` is the mechanism that tells it, and it requires the server to hold one
open stream per watching client, on one instance, for as long as the watching lasts. Day 43 deploys
`sutra_mcp` as an app where any instance answers any request; a held stream is the one thing in the
whole protocol that is pinned to an instance, and adding forty of them to a three-instance deployment
undoes the property that day exists to establish.

So the design decision is made here and recorded here: **Sutra's resources are cacheable and not
subscribable.** Freshness comes from a short `ttlMs` on the read
([4.1](4.1-every-read-carries-its-expiry.md)) and from the client checking when it needs the data. That
is a worse guarantee than a notification and a far better fit for a stateless server, and being able to
say which one you chose and why is what Day 45's audit asks for.

## The mechanism

Ask the installed SDK which era it can speak. `lab/subscribe_probe.py` names the wire methods of both
generations and the SDK class each one would need:

```python
# days/day-35-resources-and-prompts/lab/subscribe_probe.py  (extract)
WANTED = [
    ("resources/subscribe", "SubscribeRequest", "2025 - one RPC per URI, server remembers you"),
    ("resources/unsubscribe", "UnsubscribeRequest", "2025 - the matching cancel"),
    ("subscriptions/listen", "SubscriptionsListenRequest", "2026 - one opted-in stream"),
    (
        "notifications/subscriptions/acknowledged",
        "SubscriptionAcknowledgedNotification",
        "2026 - the first message on that stream",
    ),
    (
        "notifications/resources/updated",
        "ResourceUpdatedNotification",
        "both - the payload either way",
    ),
]
```

**Line by line:**

- The list is `(wire name, SDK class name, era)` triples, so the printed table can be read as *what the
  protocol calls it* beside *what the library calls it*. Those two vocabularies diverge constantly and
  conflating them is how people end up searching the wrong documentation.
- The class names are **strings**, not imports. Importing a class that does not exist raises at import
  time and the script would never run; `hasattr(types, cls)` asks the question without assuming the
  answer.
- `notifications/resources/updated` is listed last and marked *"both"* deliberately. The payload
  survived the rewrite unchanged — only the way you ask to receive it changed — and that is the piece
  of continuity that makes the migration comprehensible.

The rest of the script prices the three strategies:

```python
# days/day-35-resources-and-prompts/lab/subscribe_probe.py  (extract)
INSTANCES = 3
WATCHERS = 40
POLL_MS = 60_000
NOTIFY_LAG_MS = 250
```

**Line by line:**

- `WATCHERS = 40` is forty clients that care about a ticket. It is deliberately small — this is a
  support desk, not a social network — and forty is already enough for the conclusion.
- `INSTANCES = 3` is Day 32's three-instance deployment
  ([32.2.2](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md)),
  reused so the arithmetic lands in the architecture the phase already established.
- `POLL_MS = 60_000` is milliseconds, matching `ttlMs`'s unit rather than the reader's intuition. It
  is the polling interval **and** the worst-case staleness, which is the point: with polling those two
  numbers are the same number.
- `NOTIFY_LAG_MS = 250` is a stand-in for how quickly a push arrives. It is an assumption and it is
  named as one; the conclusion does not depend on its exact value, only on it being much smaller than
  `POLL_MS`.

Run it:

```bash
uv run python days/day-35-resources-and-prompts/lab/subscribe_probe.py
```

**Line by line:**

- From the repository root. **Zero generations**, zero network, no server: it inspects a module and
  multiplies.

Measured on 2026-09-04:

```text
installed mcp SDK speaks: 2025-11-25

wire name                                    SDK class                              present
--------------------------------------------------------------------------------------------
resources/subscribe                          SubscribeRequest                       yes
resources/unsubscribe                        UnsubscribeRequest                     yes
subscriptions/listen                         SubscriptionsListenRequest             NO
notifications/subscriptions/acknowledged     SubscriptionAcknowledgedNotification   NO
notifications/resources/updated              ResourceUpdatedNotification            yes

what each era costs to notice one changed ticket:
strategy                             requests per hour   worst-case lag (ms)
----------------------------------------------------------------------------
poll resources/read on a timer                    2400                60,000
ttlMs on the read, checked on use       0 until needed                60,000
subscriptions/listen stream                         40                   250

a listen stream is 40 held connections across 3 instances.
statelessness did not delete that cost - it made you declare it.
```

The top half is the migration, stated by the library rather than by a tutorial. **The pinned SDK has
the 2025 mechanism and not the 2026 one.** `SubscribeRequest` and `UnsubscribeRequest` are there;
`SubscriptionsListenRequest` is not. So if you build subscriptions on `mcp==1.29.1` today you will
build the deprecated ones, and they will work, against clients that also predate the revision.

The bottom half is the reason the design decision above went the way it did. Three rows, three
different currencies:

- **Polling costs requests.** 2400 an hour, for a ticket that probably did not change. Every one of
  them is a real request against a real instance.
- **`ttlMs` costs nothing until somebody needs the data**, and buys exactly the same worst-case
  staleness as polling. That is the trade the caching page describes when it says the TTL is a
  freshness hint and not a polling interval ([4.1](4.1-every-read-carries-its-expiry.md)) — same lag,
  a fraction of the traffic.
- **The stream costs held connections.** Forty of them, spread across three instances, each one pinned
  to the instance that answered it. Forty is fine. Four thousand is a capacity plan.

## When it breaks

The break is a subscription that ended and nobody noticed.

There is no error. The stream closes — a deploy, a scale-in, a network blip — and if the server did not
manage a graceful close, the client simply stops receiving notifications. It is not disconnected in any
way it can see; it made one request a while ago and messages used to arrive on it. Now they do not. The
cached ticket stays cached, the customer's reply never arrives, and the model answers from a body that
is two days old.

The correct handling is in the specification and it is three separate cases:

> A subscription ends when:
>
> * The **client** cancels it — close the SSE stream (HTTP) or send `notifications/cancelled`
>   referencing the `subscriptions/listen` request ID (stdio).
> * The **server** tears it down (e.g., during shutdown) — it **SHOULD** send a successful
>   `subscriptions/listen` response to signal a graceful end, then close the stream.
> * The underlying transport closes (HTTP timeout, TCP disconnect, stdio process exit).

Only the second one tells you anything. A client that treats "no messages" as "nothing changed" has
confused silence with a fact, and it will do so indefinitely.

The second break is the one you will hit first, and it is the SDK gap:

```text
AttributeError: module 'mcp.types' has no attribute 'SubscriptionsListenRequest'
```

Captured on 2026-09-04 from the pinned package. Following any 2026-dated article about subscriptions
against `mcp==1.29.1` ends here, immediately, which is the good version of this problem — the bad
version is finding `SubscribeRequest`, using it because it exists, and shipping the deprecated
mechanism.

The third break has no code at all. It is a server that implements `subscriptions/listen`, deploys
behind a load balancer with three instances, and discovers that a client's stream is on instance two
while the write that changed the ticket happened on instance one. Instance two has no idea. The
subscription is alive, correct, acknowledged and useless, and the missing piece is a message bus
between instances that the protocol never promised you.

## In production

**What a professional writes instead:** most servers do not implement subscriptions at all, and say so
in their capability declaration by omitting `subscribe`. The specification explicitly allows it —
*"Servers may advertise either feature independently, together or neither"* — and a server that
advertises `subscribe: true` and cannot deliver across instances is worse than one that never claimed
to. Freshness is a short `ttlMs`, and clients re-read when they need the data.

**What degrades at scale:** held streams are the one thing in this protocol that does not scale
horizontally. Every other request can go to any instance. A stream cannot move, so a rolling deploy
drops every subscription in the fleet, and the reconnect arrives as one synchronised spike from every
client at once — the same stampede shape as an expiring cache
([4.1](4.1-every-read-carries-its-expiry.md)), with connection setup on top.

**The failure mode that only appears with real traffic:** subscription leaks. A client that opens a
listen stream per user session and never cancels accumulates streams as sessions are abandoned. Nothing
errors, memory climbs on the server, and the count only becomes visible when file descriptors run out.
The cancel path is the one nobody tests, because in development the process exits and cleans up for
you — the same lesson Day 33 recorded about `close()`
([33.1.5](../../../day-33-client-and-transports/parts/01-the-connector/1.5-somebody-has-to-give-it-back.md)).

**The review comment a senior engineer leaves:** *"we advertise `subscribe: true` and we run three
instances with no bus between them. A client subscribing on instance two will never hear about a write
on instance one, and it has no way to find out. Either take the capability out of the declaration or
put the notification on a shared channel — but do not ship a promise we cannot keep on a healthy day."*

**The interview question:** *"After MCP went stateless, how do resource subscriptions work?"* The
answer that shows you have read the revision: *"the old `resources/subscribe` RPC and the standalone
GET stream are gone. A client now opens `subscriptions/listen` — a long-lived request with an explicit
filter naming what it wants, including the exact resource URIs — and the server acknowledges with a
subscription id that tags every subsequent notification, which matters on stdio where everything shares
one channel. The honest part is that this did not remove the held connection, it made it explicit and
opt-in, and nothing survives a reconnect: the spec says the server holds no subscription state, so the
client must re-send. That is why most stateless deployments do not offer subscriptions at all and use a
short `ttlMs` instead — same worst-case staleness as polling, a fraction of the requests, and no
instance affinity."*
