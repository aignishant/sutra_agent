# 4.1 — Every read carries its own expiry

## One-line answer

`resources/read` is the only non-list operation the revision made cacheable, so every read must say
how long it stays fresh and who may keep it — and the SDK pinned in this repository cannot say either,
which is a finding rather than a footnote.

## The story

There are two questions about the milk in the fridge and people answer them as if they were one.

The first is on the carton: a date. It tells you how long the milk is any good for, and it is a
promise about the milk and nothing else. Past that date you check it yourself.

The second question is not printed anywhere: **whose fridge is this?** The carton in your own kitchen
is yours, and if it is still in date you drink it. The carton in the shared fridge at work has a name
written on the side in marker pen, and the date on it does not give anybody else permission to take
it. Somebody who reads only the date and helps themselves has read the carton correctly and got the
answer wrong.

Two facts, two different kinds of fact. *How long is this good for* is about the contents. *Who may
take it* is about whose it was. A fridge full of in-date milk that everyone treats as communal is a
fridge where somebody's lunch keeps disappearing, and no expiry date ever prevented that.

## The idea in plain language

Day 32 taught the two caching fields
([32.3.3](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md)):
`ttlMs` is how long a result may be reused, `cacheScope` is who may keep it. That part was about
**lists**. This one is about the operation on that list which is not a list at all.

The caching page names six operations
(`https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching`, read
2026-09-04):

> Servers MUST include caching hints on results with `resultType: "complete"` returned by the
> following operations:
>
> * `server/discover`
> * `tools/list`
> * `prompts/list`
> * `resources/list`
> * `resources/templates/list`
> * `resources/read`

Five of those are listings. The sixth is **`resources/read`** — a request for one specific thing's
content — and that is the one worth stopping on. It means a ticket's body is a cacheable object with a
stated shelf life, which is a much stronger claim than *the list of things is cacheable*, and it is
where the shared-fridge question arrives.

The specification answers it directly:

> * **`"public"`** is appropriate for lists of tools, prompts, and resource templates when they are
>   identical for all users.
> * **`"private"`** is appropriate for `resources/read` results that depend on the authenticated user,
>   or for filtered list results that vary per user.

And it spells out what `"private"` actually forbids, which is stricter than *do not share with
strangers*:

> "Cached responses **MAY** be reused for the same authorization context. Caches **MUST NOT** be
> shared across authorization contexts (e.g. a different access token requires a different cache)."

An **authorization context** is, in practice, one access token. Two tokens are two contexts even if
they belong to the same person on two machines. So a `"private"` cache is keyed by credential, not by
user and not by connection — which is the only definition that still makes sense once there are no
connections ([32.2.1](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.1-the-call-that-remembered-you.md)).

Two more rules on `ttlMs`, both easy to get wrong in the same direction:

> "If `ttlMs` is absent, clients **SHOULD** assume a default of `0` (immediately stale) and rely on
> their own caching heuristics or notifications. **This should only occur in older server versions.**"

> "Clients **SHOULD NOT** treat TTL as a polling interval that triggers automatic background
> refetches. The TTL is a freshness hint: the client checks freshness when it needs the data, and
> re-fetches only if stale."

That second one is the sentence people implement backwards. A TTL of one minute does not mean *ask
again every minute*. It means *if you need this and it is older than a minute, ask again*. A client
that polls on the TTL has turned a saving into a load generator, and the specification adds that
implementations which do choose to poll **MUST** apply jitter and backoff.

## Why Sutra needs it

Because Sutra is about to publish tickets, and a ticket is the textbook case of the shared fridge.

`ticket://4521` is one customer's words, sitting behind whatever authorisation Day 37 adds. Marked
`"public"`, it may be stored by a shared gateway and served to the next caller. That is one JSON field
between a correct server and a data-leak incident, and there is no error, no log line and no test that
catches it — Day 32 said this about list results and it is worse here, because the content of a read is
the sensitive thing rather than a list of names.

There is also a decision waiting from Day 32. Its `TODO(me)` asked which `ttlMs` and `cacheScope`
`sutra_mcp`'s `tools/list` should return. Today's build brief asks the same question about
`resources/read`, and the two answers are different: a tool list is the same for everybody and lasts
until a deploy, while a ticket body is one caller's data and changes when the customer replies.

## The mechanism

Ask the installed SDK whether it can carry the fields at all. `lab/cache_hint.py` names the six
operations from the caching page and checks each SDK result model for the two required fields:

```python
# days/day-35-resources-and-prompts/lab/cache_hint.py  (extract)
REQUIRED_ON = {
    "server/discover": None,
    "tools/list": types.ListToolsResult,
    "prompts/list": types.ListPromptsResult,
    "resources/list": types.ListResourcesResult,
    "resources/templates/list": types.ListResourceTemplatesResult,
    "resources/read": types.ReadResourceResult,
}

HINTS = ("ttlMs", "cacheScope")


def fields(model: type | None) -> set[str]:
    """Declared field names on a pydantic result model, or an empty set when absent."""
    return set() if model is None else set(model.model_fields)
```

**Line by line:**

- The dictionary is keyed by the **wire method name** and valued by the SDK class, so the output reads
  as a comparison between the specification and the library rather than a list of Python classes.
- `"server/discover": None` is `None` because the pinned SDK has no class for it at all. That is not a
  missing field, it is a missing operation — the whole request type arrived in the revision this SDK
  does not speak ([32.2.4](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.4-server-discover-the-optional-question.md)).
  Encoding it as `None` rather than omitting the row keeps the absence visible.
- `model_fields` is pydantic's map of declared fields on a model. Asking the class rather than an
  instance means no request has to be made and no server has to be running.
- `set(...)` because the only question is membership. Order and types are irrelevant here.
- `HINTS` as a tuple of the two field names, spelled exactly as the specification spells them —
  `ttlMs`, not `ttl_ms`. These are JSON field names and the casing is part of them.

Run it:

```bash
uv run python days/day-35-resources-and-prompts/lab/cache_hint.py; echo "exit: $?"
```

**Line by line:**

- `echo "exit: $?"` prints the exit code, because this script is a **check** and its verdict is the
  code, not the table. Principle 11: it must be able to go red.
- **Zero generations**, zero network, no server.

Measured on 2026-09-04:

```text
mcp SDK protocol revision: 2025-11-25
specification revision    : 2026-07-28

operation                  result class                     ttlMs   cacheScope
----------------------------------------------------------------------------
server/discover            (no class in this SDK)           NO      NO
tools/list                 ListToolsResult                  NO      NO
prompts/list               ListPromptsResult                NO      NO
resources/list             ListResourcesResult              NO      NO
resources/templates/list   ListResourceTemplatesResult      NO      NO
resources/read             ReadResourceResult               NO      NO

missing required caching fields: 12
this server cannot answer the 2026-07-28 caching contract without a bump
exit: 1
```

**Twelve out of twelve missing, and `exit: 1`.** The pinned `mcp==1.29.1` reports
`LATEST_PROTOCOL_VERSION = "2025-11-25"`, which is the revision *before* the one that introduced
`CacheableResult`. The fields do not exist on any of its result models, so a server built on it cannot
emit them however carefully you write the handler.

The same fact from the other end, in `read_shelf.py`'s last block:

```text
caching hints the 2026-07-28 revision requires on every one of these:
   resources/list   ttlMs=None cacheScope=None
   resources/read   ttlMs=None cacheScope=None
```

That is a live server answering a live client, and both hints are absent. Which, by the rule quoted
above, a conformant client must read as `ttlMs: 0` — *immediately stale, re-fetch every time*. So the
practical consequence of the SDK gap is not that caching is broken; it is that **caching is off**, and
every read costs a request.

This is Day 32's finding arriving where it bites. Day 32 recorded that the pinned SDK tops out at
`2025-11-25` and that nothing was broken yet. This is the yet. Nothing here is bumped: a version
change is a plan decision with a `docs/PACKAGES.md` row behind it (Principle 14), and the hub's §8
records it for whoever makes that decision.

## When it breaks

The break that costs money is `"public"` on a ticket, and there is nothing to see when it happens.

A shared gateway in front of three server instances caches a `resources/read` for `ticket://4521`
marked `"public"`, with a `ttlMs` of an hour. The next caller — a different customer, a different
token, a different company — reads the same URI and is served from the cache. Every component behaved
correctly. The server said the response was not user-specific and the gateway believed it.

The specification's security section is unusually blunt about this, and the sentence is worth having:

> "Servers MUST be aware that responses with a `"public"` `cacheScope` may be shared between callers
> even if the Result is coming from an authenticated endpoint."

Authenticating the request does not make the response private. Those are two separate decisions and
only one of them is made by your auth middleware.

The second break is a `ttlMs` in the wrong unit. `3600` looks like an hour and is three and a
fractional part of a second. Nothing warns you; the field is an integer and every integer is valid. The
symptom is a request rate a thousand times higher than you planned, on a Monday, in production.

The third break is the polling client, and it is the one that turns a cache into an outage. A client
that re-fetches on a timer set to `ttlMs` generates traffic proportional to the number of clients
rather than to the amount of work being done — and when they all deployed at the same time, they all
re-fetch at the same time. That is why the specification says **SHOULD NOT** poll and **MUST** apply
jitter if you do.

## In production

**What a professional writes instead:** `cacheScope` is decided per handler and written beside it,
never defaulted. Anything derived from a user's data is `"private"` with a short `ttlMs`, or is not
cached at all. Lists that are the same for every caller are `"public"` with a generous one. The value
is a named constant, in milliseconds, with the unit in the name — `TICKET_TTL_MS` — because the unit
is where the mistakes are.

**What degrades at scale:** the cache becomes load-bearing, and therefore a bad `ttlMs` becomes a
capacity incident rather than a correctness one. Too short and every host re-reads every ticket on
every turn. Too long and a customer's update is invisible for as long as the number says, which on a
support desk is a reply that answers a question the customer has already withdrawn.

**The failure mode that only appears with real traffic:** cache stampede. Every host fetched at deploy
time, so every host's copy expires in the same second, and the fleet's re-read arrives as one spike.
Jitter — varying `ttlMs` slightly per response — is trivial to add before the fleet is large and
awkward afterwards.

**The review comment a senior engineer leaves:** *"`resources/read` on `ticket://` returns
`cacheScope: "public"`. The endpoint is authenticated, so somebody assumed that made it safe. It does
not — the spec says a public response can be shared across authorization contexts even from an
authenticated endpoint. This is `private`, and there needs to be a test that fails if anybody changes
it."*

**The interview question:** *"MCP made resource reads cacheable. What is the risk?"* The honest answer:
*"the same one HTTP has had for thirty years, with a new field name. `ttlMs` is a freshness window, so
for that long a client can be holding content that is no longer true — fine for a document, not fine
for a ticket a customer just updated. And `cacheScope: public` on user data lets a shared proxy serve
one caller's content to the next, which the spec calls out explicitly because authenticating the
request does not make the response private. In our repository there is a third answer: the pinned SDK
predates `CacheableResult`, so it emits neither field, and a conformant client has to treat every read
as immediately stale. Caching is not misconfigured, it is off, and we wrote that down rather than
discovering it under load."*
