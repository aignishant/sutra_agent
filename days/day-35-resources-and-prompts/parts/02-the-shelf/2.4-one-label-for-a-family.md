# 2.4 — One label for a whole family

## One-line answer

A resource template publishes the *shape* of an address rather than every address —
`ticket://{ticket_id}` instead of twenty thousand entries — and the shape promises more addresses than
you own, including ones that do not exist and ones you never meant to offer.

## The story

Every vehicle in the state carries a plate, and every plate is built the same way: two letters for the
state, two digits for the district, two letters for the series, four digits for the vehicle.

Nobody keeps a book of every plate. There are millions. What everyone keeps in their head is the
**shape**, and the shape is enough for almost everything you actually do with a plate. A guard at a
gate can look at something scrawled on a piece of paper and say *that is not a plate* without checking
any list. A form can have the right number of boxes printed on it. A neighbour can read one out over
the phone and you can write it down correctly, because you know how many of each thing to expect.

Here is the part that catches people. The shape describes plates that have never been issued. Nothing
about the format says which combinations are on real vehicles and which are simply well-formed. A
delivery driver who is told *"the van has a plate in this format"* has been told something true and
something useless: knowing the shape tells you nothing about whether that particular van exists.

## The idea in plain language

Sutra's archive will have twenty thousand tickets in it before long. Listing twenty thousand entries
in `resources/list` is not a shelf, it is a phone book, and nobody can page through it usefully.

So MCP has a second listing:

> "Resource templates allow servers to expose parameterized resources using
> [URI templates](https://datatracker.ietf.org/doc/html/rfc6570)."
>
> (`https://modelcontextprotocol.io/specification/2026-07-28/server/resources`, read 2026-09-04)

Three terms, in order.

**A URI template** is a URI with named holes in it. `ticket://{ticket_id}` has one hole called
`ticket_id`. Filling the hole gives you a real URI: `ticket://4521`.

**RFC 6570** is the document that defines the syntax of those holes. It is a large specification with
several kinds of expansion, and MCP names it as the reference rather than defining its own.

**`resources/templates/list`** is where templates are published, and it is a **separate list** from
`resources/list`. This surprises everyone once: a server can look empty in a picker while offering
millions of addresses, because the picker only asked the first list. Each entry carries `uriTemplate`
instead of `uri`, and otherwise the same `name`, `title`, `description` and `mimeType` fields as a
concrete resource.

The thing to hold on to is what a template actually *is*. It is not a query, and it is not a promise
that the addresses exist. It is a statement of the form *addresses shaped like this belong to me*. A
host that has a ticket id can construct the URI without asking you anything; a host that does not
cannot use the template at all, which is why the archive summary in
[2.1](2.1-an-address-not-a-call.md) lists the ids it holds.

🅿️ **Parked: the completion API.** The specification notes that template arguments *"may be
auto-completed through the completion API"* — a separate endpoint where a host asks the server for
candidate values as the user types. It is real, it is the right answer to *"how does a picker help me
fill in `{ticket_id}`?"*, and Sutra does not build it. Know it exists and that it is a per-argument
request, not a listing.

## Why Sutra needs it

Because the ticket archive is the one dataset Sutra has that cannot be listed.

Two tickets fit in `resources/list` today, which is exactly why doing it that way now would be the
wrong lesson: the shape that works at two is the shape that has to be rewritten at twenty thousand.
Publishing `ticket://{ticket_id}` as a template gets the design right while it is still cheap, and it
is what [Day 49's](../../../day-49-retrieval-and-embeddings/LESSON.md) retrieval index will record
against every chunk it stores.

It matters immediately for a second reason. Day 34's `sutra_mcp/server.py` will be running behind a
gateway by Day 43, and the gateway routes on `Mcp-Name`
([32.3.1](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.1-the-label-on-the-envelope.md)).
A template is a routing rule a gateway can act on. Twenty thousand individual URIs are twenty thousand
rules nobody will write.

## The mechanism

The registration is the same decorator as a plain resource. The braces are what change its meaning:

```python
# days/day-35-resources-and-prompts/lab/shelf.py  (extract)
@mcp.resource(
    "ticket://{ticket_id}",
    title="Support ticket",
    description="The raw text of one support ticket, addressed by its id.",
    mime_type="text/plain",
    annotations=Annotations(audience=["assistant"], priority=0.9),
)
def ticket_resource(ticket_id: str) -> str:
    """One ticket by id. A miss is a protocol error, never a polite sentence."""
    ...
```

**Line by line:**

- `{ticket_id}` in the URI and `ticket_id: str` in the signature must be **the same name**. The SDK
  compares the two sets and raises at import time on a mismatch; the exact text is in
  [2.1](2.1-an-address-not-a-call.md)'s *When it breaks*.
- The decorator is `@mcp.resource`, not a separate `@mcp.resource_template`. There is only one
  decorator, and the presence of braces or of function parameters is what routes the registration to
  `add_template` — verified by reading `.venv/Lib/site-packages/mcp/server/fastmcp/server.py` on
  2026-09-04.
- `priority=0.9` here against `0.3` on the archive summary in [2.1](2.1-an-address-not-a-call.md).
  That is the server saying *the ticket itself matters much more than the count of tickets*, and it
  is the kind of hint a host uses to decide what to drop when context is tight
  ([6.2](../06-in-production/6.2-the-shelf-a-stranger-can-use.md)).
- `audience=["assistant"]`, not `["user", "assistant"]`. The raw ticket text is for the model to
  reason over; a person looking at the picker already has the ticket open in front of them.

What matters more than the registration is what the template actually matches, and that is not a
question to answer from memory. `lab/template_match.py` asks the SDK's own matcher:

```python
# days/day-35-resources-and-prompts/lab/template_match.py  (extract)
def probe(template: str, uri: str) -> dict[str, str] | None:
    """Ask the SDK's matcher, not a regex we wrote, whether this URI is in the family."""
    t = ResourceTemplate(
        uri_template=template,
        name="probe",
        description="",
        mime_type="text/plain",
        fn=lambda **kw: "",
        parameters={},
    )
    return t.matches(uri)
```

**Line by line:**

- `ResourceTemplate` is imported from `mcp.server.fastmcp.resources.templates`. Constructing one
  directly, rather than registering a server and asking it, is what keeps this script to one page and
  zero subprocesses.
- `fn=lambda **kw: ""` and `parameters={}` are required fields that this probe never uses. The
  template is being asked about *matching*, and matching happens before the function is called at all.
- `t.matches(uri)` returns a dict of bound parameters on a hit and `None` on a miss. That return type
  is the answer to *"is this URI in the family, and if so what does it bind?"* in one call.
- Nothing here asserts a pattern. The whole reason this function exists is that the answer is a
  property of the installed library, and a document that states it from memory is a document that goes
  stale on the next release.

Run it:

```bash
uv run python days/day-35-resources-and-prompts/lab/template_match.py
```

**Line by line:**

- From the repository root. **Zero generations**, zero network, no subprocess — this is a regular
  expression.

Measured on 2026-09-04:

```text
the matcher, from mcp/server/fastmcp/resources/templates.py:

   match = re.fullmatch(pattern, uri)

template                 uri                        params
------------------------------------------------------------------------------
ticket://{ticket_id}     ticket://4521              {'ticket_id': '4521'}
ticket://{ticket_id}     ticket://4521/history      None
ticket://{ticket_id}     kb://logout                None
ticket://{ticket_id}     ticket://                  None
doc://{path}             doc://readme.md            {'path': 'readme.md'}
doc://{path}             doc://..%2F..%2F.env       {'path': '..%2F..%2F.env'}
doc://{path}             doc://../../.env           None
```

The first two printed lines are the entire matcher, lifted out of the installed file by
`inspect.getsource`. It is two lines: turn `{name}` into a named regex group matching `[^/]+`, then
`re.fullmatch`. Read those two lines and every row below them becomes predictable.

- `ticket://4521` binds, as intended.
- `ticket://4521/history` does **not**, because `[^/]+` refuses a slash. So a template with one
  placeholder can never describe a nested path — `doc://{path}` cannot match `doc://notes/plan.md`,
  which is a real limitation and not a safety feature.
- `kb://logout` does not match a `ticket://` template. Schemes are matched literally.
- `ticket://` with nothing after it does not match, because `+` requires at least one character. A
  template does not accidentally offer its own bare prefix.
- `doc://..%2F..%2F.env` **does** bind, with the percent-encoded text handed over as-is. The matcher
  saw no slash because there was no slash — there were the three characters `%`, `2`, `F`. What the
  handler does with them is [5.1](../05-failure-lab/5.1-the-address-that-reached-outside.md), and it is
  the failure lab for a reason.

## When it breaks

The break that bites first is the one the plate-shape story sets up: **a template promises addresses
that do not exist.**

Publish `ticket://{ticket_id}` and you have told every host that any well-formed ticket URI is yours.
A host with a stale id, a typo, or a guessed number constructs `ticket://9999` and reads it. That is
not misuse — you advertised the shape. The correct answer is `-32602`
([2.3](2.3-the-miss-that-must-be-an-error.md)), and a server that publishes templates and has not
thought about its miss path will meet that path on its first real day.

The second break is the one there is no error for: **a template is a listing that is not a listing.**
A host that calls only `resources/list` sees one entry — the archive summary — and concludes the
server has almost nothing on it. Nothing failed. The templates were in the other list, and nobody
asked. This is why [2.1](2.1-an-address-not-a-call.md)'s summary resource exists and names the ids it
holds: it is the bridge for a host that cannot fill in a placeholder by itself.

The third break has a real traceback, and it is the one that will actually happen to you while typing:

```text
ValueError: Mismatch between URI parameters {'ticket_id'} and function parameters {'id'}
```

Captured on 2026-09-04. You renamed the function's argument and not the URI, or the other way round.
It raises at import, so the server refuses to start — which is the kindest possible version of this
mistake.

## In production

**What a professional writes instead:** the template's `description` says what a valid parameter looks
like, in words, because the placeholder name alone does not. `"The ticket id, digits only, for example
4521"` is the difference between a host that constructs a working URI and one that sends
`ticket://TICKET-4521` and gets an error it cannot interpret. And the handler validates the parameter
shape before it uses it, because the matcher's `[^/]+` is not validation.

**What degrades at scale:** the miss rate. With two tickets, every URI a host constructs is one you
have. With twenty thousand and a host that keeps ids in its own database, a percentage of reads will
always be for tickets that were merged, deleted or never existed, and `-32602` becomes normal traffic
rather than an incident. It has to be counted separately from server errors or your error rate looks
like an outage.

**The failure mode that only appears with real traffic:** enumeration. A template is an invitation to
iterate, and nothing in the protocol rate-limits it. A host — or something wearing a host's
credentials — can walk `ticket://1` through `ticket://99999` and read the archive one address at a
time, and every single request is individually legitimate. Day 40's allowlists and Day 37's
authorisation are where that is answered; noticing it is a property of *templates*, not of any one
request, is the part that has to happen here.

**The review comment a senior engineer leaves:** *"`doc://{path}` matches `[^/]+`, so it cannot serve
a nested document at all — the whole `notes/` directory is unreachable through it. Either publish one
template per directory, or accept an encoded path and validate it properly. What you have now is a
template that silently covers a third of the corpus."*

**The interview question:** *"How do you expose a large dataset over MCP without listing it?"* The
answer that shows you have done it: *"a resource template — you publish the shape `ticket://{id}` in
`resources/templates/list` rather than the members in `resources/list`. Two things follow that people
miss. First, the template is a separate list, so a host that only reads `resources/list` sees an almost
empty server; we publish a small summary resource that names what is available so there is a way in.
Second, the template promises addresses you do not own, so the not-found path is not an edge case, it
is normal traffic — and it also means the shape is an invitation to enumerate, which is an
authorisation problem rather than a protocol one."*
