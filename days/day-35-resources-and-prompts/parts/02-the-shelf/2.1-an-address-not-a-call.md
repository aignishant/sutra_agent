# 2.1 — An address, not a call

## One-line answer

A resource is not a function you invoke, it is a **name** — a URI — and publishing one means promising
that anybody who says that name gets the same thing, without describing what they want or being asked
who they are.

## The story

Every bus stop in the city has a short code stencilled on the pole.

Before the codes, asking when the next bus was coming meant describing where you were standing. *"The
stop outside the hospital, on the side going towards the market, not the one across the road."* Two
people standing at the same pole would describe it differently, and the person you asked had to work
out which pole you meant before they could answer anything.

Now you read four characters off the pole and send them. There is nothing to describe. Your cousin,
standing at the same pole next week, sends the same four characters and gets the same stop. Somebody
who has never been to the city can be told the code over the phone and they will be asking about the
right pole.

Two things changed and only one of them is obvious. The obvious one is that it got shorter. The other
one is that the code now works **without you**. It is not a question you asked; it is a name for a
thing, and the name keeps meaning that thing when you are not there to explain it.

## The idea in plain language

A **URI** — a Uniform Resource Identifier — is a string that names one thing. `ticket://4521` is a
URI. So is `https://example.com/index.html`, and so is `file:///home/me/notes.txt`. The part before
the `://` is the **scheme**, and it says what family of names this is. The rest identifies one member
of that family.

MCP takes that idea literally. The specification opens the resources page with it
(`https://modelcontextprotocol.io/specification/2026-07-28/server/resources`, read 2026-09-04):

> "Each resource is uniquely identified by a [URI](https://datatracker.ietf.org/doc/html/rfc3986)."

**RFC 3986** is the document that defines what a URI may look like. You do not need to read it to use
one, but you do need to know it exists, because the specification hands you the freedom to invent a
scheme and then points at that document as the boundary:

> "Custom URI schemes **MUST** be in accordance with
> [RFC3986](https://datatracker.ietf.org/doc/html/rfc3986), taking the above guidance in to account."

So `ticket://4521` and `kb://logout` are legitimate. They are not standard schemes and they are not
meant to be — a custom scheme is how a server says *these names mean something inside my world*.

Discovering what is on the shelf is `resources/list`, and there is one rule on it that is easy to read
past and is the entire reason the shelf is worth having:

> "…but **MUST NOT** vary per-connection or as a side effect of other requests on the connection."

A list that does not vary per connection is a list that can be shared, cached and printed on a page.
That is Day 32's stateless core arriving as a consequence rather than as a principle
([32.3.3](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md)).
The specification adds one exception, and it is a precise one:

> "The set **MAY** vary by the authorization presented on the request — for example, returning only
> the resources the caller's granted scopes permit — since credentials are per-request input, not
> connection state."

Credentials arrive with each request, so filtering by them is still stateless. Remembering who
connected is not. Day 37 is where that distinction becomes code.

Each entry in the list is a small record, and the field names matter because a host builds its picker
out of them:

| Field | What it is for | Required |
| --- | --- | --- |
| `uri` | the name — the only field a `resources/read` needs | yes |
| `name` | the identifier a program uses | yes |
| `title` | the words a human sees in a list | no |
| `description` | how a host or a model decides whether this is the one | no |
| `mimeType` | how a reader should parse the bytes | no |
| `size` | bytes, so a host can decide before it reads | no |
| `icons` | display only | no |
| `annotations` | audience, priority and last-modified hints ([6.2](../06-in-production/6.2-the-shelf-a-stranger-can-use.md)) | no |

Only the first two are required, which is exactly why an unusable shelf passes every validator.

## Why Sutra needs it

Because Sutra's data currently has no names at all.

`TICKETS` is a Python dictionary inside `sutra/loop.py`. The key `"4521"` is a name **inside one
process**. Nothing outside can say it. When Day 34 put `lookup_ticket` on the wire, the ticket became
reachable — but only by asking a model to ask for it. Giving it the URI `ticket://4521` is the first
time a piece of Sutra's data has a name that a program somewhere else can hold, write down, put in a
log line, or send to a colleague.

That matters concretely on **Day 49**, where a retrieval index over the ticket archive has to record
*where each chunk came from*. A row that says "ticket 4521" is a note; a row that says `ticket://4521`
is an address something can go and fetch.

## The paper behind it

> **Principled design of the modern Web architecture** · `doi:10.1145/514183.514185` · 2002 ·
> `https://doi.org/10.1145/514183.514185`

It argued that identifying every thing by a name, separately from any operation on it, is what lets
caches, proxies and independent clients cooperate at all — because they can agree on what they are
talking about without agreeing on what they intend to do with it.

The paper is taught in Day 32's
[`../../../day-32-mcp-stateless-core/papers/01-modern-web-architecture.md`](../../../day-32-mcp-stateless-core/papers/01-modern-web-architecture.md).

## The mechanism

A resource with a fixed address, registered on the lab's teaching server:

```python
# days/day-35-resources-and-prompts/lab/shelf.py  (extract)
@mcp.resource(
    "archive://summary",
    title="Ticket archive summary",
    description="How many tickets and articles the desk holds, and where to start reading.",
    mime_type="text/plain",
    annotations=Annotations(audience=["user", "assistant"], priority=0.3),
)
def archive_summary() -> str:
    """A cheap 'what is on this shelf?' read, with no arguments and a fixed address."""
    return (
        f"Sutra archive: {len(TICKETS)} tickets, {len(KB)} knowledge-base articles. "
        f"Ticket ids: {', '.join(sorted(TICKETS))}. Start at ticket://4521."
    )
```

**Line by line:**

- `@mcp.resource("archive://summary", ...)` is the FastMCP decorator, and the first argument is the
  URI itself. Verified by reading the installed source,
  `.venv/Lib/site-packages/mcp/server/fastmcp/server.py`, on 2026-09-04: the signature is
  `resource(self, uri, *, name=None, title=None, description=None, mime_type=None, icons=None, annotations=None, meta=None)`.
- The URI has **no braces**, and the function takes **no arguments**. That combination is what makes
  this a plain resource rather than a template. The SDK decides between the two by inspecting both:
  `has_uri_params = "{" in uri and "}" in uri` and `has_func_params = bool(sig.parameters)`. Either
  one being true routes the registration to `add_template` instead
  ([2.4](2.4-one-label-for-a-family.md)).
- `archive://` is a scheme this server invented. Nothing registers it anywhere; it is meaningful
  inside `sutra-mcp` and nowhere else, which is precisely what a custom scheme is for.
- `title=` is separate from `name=` and both exist deliberately. `name` defaults to the function name
  (`archive_summary`) and is what a program matches on; `title` is what a person reads in a picker.
  Omitting `title` does not fail — it just means the picker shows `archive_summary`.
- `mime_type="text/plain"` tells the reader how to parse what comes back. Without it a host has to
  guess, and a host that guesses wrong renders your Markdown as a wall of asterisks.
- `annotations=Annotations(audience=[...], priority=0.3)` is a hint, not a rule.
  `priority=0.3` says *include this if you have room*, which is honest for a summary. The field is
  explained properly in [6.2](../06-in-production/6.2-the-shelf-a-stranger-can-use.md).
- The function returns a `str`. FastMCP wraps it into the `contents` array for you
  ([2.2](2.2-what-comes-back-from-a-read.md)); returning `bytes` would produce a base64 `blob`
  instead.
- The body reads `TICKETS` and `KB` and computes the counts on every read. That is a real decision
  and not laziness: a summary computed at import time is a summary that is wrong the moment a ticket
  arrives.

Now ask the server what it has. `lab/read_shelf.py` starts `shelf.py` as a child process over stdio
and speaks the protocol to it, using the client shape Day 33 built
([33.2.1](../../../day-33-client-and-transports/parts/02-stdio/2.1-connecting-is-launching.md)):

```bash
cd days/day-35-resources-and-prompts/lab
uv run python read_shelf.py
```

**Line by line:**

- `cd` first, because `read_shelf.py` resolves the server file relative to its own directory and then
  launches it. Running it from the repository root works too; the `cd` is here so the `SHELF=`
  variant in [2.3](2.3-the-miss-that-must-be-an-error.md) reads the same way.
- **Zero generations.** A server answering `resources/list` does not involve a model at any point.

The first block of what it printed, on 2026-09-04:

```text
driving shelf.py

resources/list
   archive://summary    archive_summary  mime=text/plain ann=audience=['user', 'assistant'] priority=0.3
```

One line, and every field on it was declared in the decorator above. The URI is the name; `name` is
`archive_summary` because it was not overridden; the MIME type and the annotations came across
unchanged.

What is **not** in that list is the interesting part. There are two tickets and two knowledge-base
articles on this server and none of them appear. They are addressed by a template, and templates are
listed separately — which is [2.4](2.4-one-label-for-a-family.md).

## When it breaks

The break is a URI that is not a name for one thing.

Write `@mcp.resource("search://{query}")` and the SDK accepts it, the host lists it, and a picker
shows it. It is still wrong, and it fails in a way nothing reports: a URI is supposed to identify a
resource, so a host may cache the answer under that string, prefetch it, or read it twice expecting
the same bytes. A search result is none of those things. The same query returns different results
tomorrow, and the cache does not know that.

The second break is scheme collision, and it produces a genuine error you can see. Publish
`file://{path}` and you have taken over a scheme with an established meaning; a host that already
knows how to fetch `file://` may never call you at all. The specification is explicit about the
adjacent case:

> "Servers **SHOULD** use this scheme only when the client is able to fetch and load the resource
> directly from the web on its own—that is, it doesn't need to read the resource via the MCP server."

That sentence is about `https://`, and it generalises: **a standard scheme is a promise about who
resolves it.** If the client must come to you, invent your own scheme.

The third break has a real traceback, and you will meet it the first time you write a template by
accident:

```text
ValueError: Mismatch between URI parameters {'ticket_id'} and function parameters set()
```

That is `mcp/server/fastmcp/server.py` refusing a registration where the URI names a placeholder the
function does not accept. It is raised at import time, not at request time, which is the good case —
the server will not start rather than starting broken.

## In production

**What a professional writes instead:** the URI scheme is chosen once, written down, and treated as
public API. `ticket://{id}` is a commitment: hosts will store those strings, log them, and put them in
bug reports. Renaming the scheme later is a migration, not a refactor, so the naming argument happens
before the first release rather than after.

**What degrades at scale:** `resources/list` becomes a listing problem. A shelf with two entries is a
table; a shelf with two hundred thousand tickets cannot be listed at all, which is why the archive is
published as a template and only the *summary* is listed. A server that enumerates its whole dataset
in `resources/list` works perfectly in development and returns a response nobody can page through in
production.

**The failure mode that only appears with real traffic:** pickers prefetch. A host that shows a
preview beside each listed resource reads every resource it lists, so an expensive `archive://summary`
that recomputes counts over a real database is executed every time a user opens the picker — not when
they choose something. Cheap-to-list and cheap-to-read are two different requirements and only the
first is obvious.

**The review comment a senior engineer leaves:** *"`resources/list` returns whatever order the
decorator registry produced, and the URIs are being generated from a set. Sort them. A shelf that
comes back in a different order every deploy invalidates every client cache for no reason at all."*

**The interview question:** *"What actually makes something a resource rather than an endpoint?"* The
answer that shows you have used it: *"a stable name that identifies the thing rather than the
operation. `ticket://4521` means the same ticket to every caller, on every instance, so a host can
cache it, log it, hand it to another process, or attach it before a turn starts. The moment the same
URI can return different content for different callers for reasons other than their credentials, it
has stopped being an identifier and everything downstream that assumed it was one — caches, proxies,
retries — is quietly wrong. That is why a search is a tool and not a resource, however read-only it
looks."*
