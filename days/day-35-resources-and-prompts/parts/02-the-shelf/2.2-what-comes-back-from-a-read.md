# 2.2 — What comes back from a read

## One-line answer

`resources/read` never returns a document — it returns a **list** of contents, and every item in that
list carries its own URI and its own MIME type, so a single read may legitimately hand back several
things at once.

## The story

You ordered one water filter and the courier hands you three boxes.

The delivery note has one order number on it, and underneath, three lines: *1 of 3 — filter body. 2
of 3 — cartridge. 3 of 3 — mounting kit.* Each box has its own label stuck on it saying what is
inside. The mounting kit's label also says **FRAGILE**, and the cartridge's says **KEEP UPRIGHT**,
which the filter body's does not.

You sign once. You received one delivery. But if you carry the boxes inside as though they were the
same kind of thing, you will put the cartridge on its side and it will leak, and nobody will have
lied to you: the label was on the box.

The lesson is not that three is more than one. It is that **the note is a list, and each line on the
list carries its own instructions**, and the person who reads only the order number at the top has
read the smallest part of it.

## The idea in plain language

`resources/read` takes one URI and returns one result. Inside that result is a field called
`contents`, and it is always a JSON array, even when it has one element in it.

Here is the specification's own example response, copied exactly
(`https://modelcontextprotocol.io/specification/2026-07-28/server/resources`, read 2026-09-04):

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "contents": [
      {
        "uri": "file:///project/src/main.rs",
        "mimeType": "text/x-rust",
        "text": "fn main() {\n    println!(\"Hello world!\");\n}"
      }
    ],
    "ttlMs": 60000,
    "cacheScope": "private"
  }
}
```

Four things in that block are worth naming, because three of them surprise people.

**`contents` is an array with one element.** One file was requested, one file came back, and it is
still a list. Code that reaches for `result["contents"]["text"]` fails with a `TypeError` on the very
first read, which is the good outcome; code that does `result["contents"][0]` and never thinks about
it again is the one that eventually loses data.

**Each item repeats the `uri`.** The item says which resource *it* is, which is redundant when there
is one item and essential when there are several. The specification permits several:

> "Servers **MAY** return multiple resource contents in response to a single `resources/read` request.
> For example, a server could return the contents of several files when a directory resource is read."

**Each item carries its own `mimeType`.** Not the result — the item. Read a directory and you may get
back one Markdown file, one PNG and one CSV in a single answer, each parsed differently.

**An item is text or binary, never both.** Two shapes exist:

| Shape | Field | What it holds |
| --- | --- | --- |
| text | `text` | the characters, as a normal JSON string |
| binary | `blob` | the bytes, base64-encoded into a string |

The installed SDK models this exactly. Read on 2026-09-04, `.venv/Lib/site-packages/mcp/types.py`
declares `ReadResourceResult.contents: list[TextResourceContents | BlobResourceContents]`, where both
inherit `uri` and `mimeType` from a shared `ResourceContents` and add `text: str` or `blob: str`
respectively. So *"text or blob"* is not a convention you have to remember — it is a type, and
`getattr(item, "text", None)` is how you ask which one you got.

And `resultType: "complete"` is the fourth field. It means *this is the answer*, as opposed to
`"input_required"`, which is the 2026 revision's way for a server to say *I need something from the
user first*. Day 37 builds that; here it matters only because the caching rules attach to `complete`
results and to no others ([4.1](../04-freshness/4.1-every-read-carries-its-expiry.md)).

## Why Sutra needs it

Because Sutra's very first resource read is a one-element list, and the shape of the code you write
around it decides whether the second one is a bug.

Today `ticket://4521` returns one ticket, so `contents[0].text` is right and always will be for that
URI. But Day 39 replaces the ticket dictionary with a SQLite table, and the obvious next resource is
`ticket://4521/attachments` — several items, mixed types, one read. A client written as *"take
element zero"* will silently return the first attachment and drop the rest, and the symptom will be a
support reply that mentions one screenshot when the customer sent three.

There is a second reason, and it is the one Day 33 flagged. Its transport part closed by pointing
here: the answer to *"can I return the whole file through a tool result?"* is usually *"return a
resource URI and let the client fetch it"*
([33.2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md)). That
only works if the read result can carry binary, and it can — as `blob`.

## The mechanism

The read, and what the SDK hands you:

```python
# days/day-35-resources-and-prompts/lab/read_shelf.py  (extract)
hit = await session.read_resource(AnyUrl("ticket://4521"))
print("\nresources/read ticket://4521")
print(f"   contents is a list of {len(hit.contents)}")
item = hit.contents[0]
print(f"   uri={item.uri} mime={item.mimeType}")
print(f"   text={head(getattr(item, 'text', ''))}")
```

**Line by line:**

- `session.read_resource(...)` is the SDK's `resources/read`. It is `await`ed because the transport is
  asynchronous; the protocol itself is one request and one response.
- `AnyUrl("ticket://4521")` wraps the string in pydantic's URL type. The SDK's signature demands it,
  and the wrapping is not ceremony: `AnyUrl` parses the string, so a URI that is not a URI fails here,
  in your code, rather than on the wire.
- `len(hit.contents)` is printed rather than assumed. The whole point of this part is that this number
  is not always `1`, and printing it is how the transcript proves the claim instead of asserting it.
- `hit.contents[0]` takes the first item — correct for this URI, and the line that would need to be a
  loop for a directory-shaped resource. It is written this way because it is what the reader will
  write, and naming it here is cheaper than debugging it later.
- `item.uri` is read off the **item**, not off the result. For one item they are the same string; for
  several, this is the only thing that says which is which.
- `getattr(item, "text", "")` rather than `item.text`. A `BlobResourceContents` has no `text`
  attribute at all, and `getattr` with a default is how you handle the union without an `isinstance`
  ladder. The empty-string default is honest here because this line only prints.
- `head(...)` truncates to one readable line. It exists so the transcript below fits on a page and for
  no other reason.

Measured on 2026-09-04:

```text
resources/read ticket://4521
   contents is a list of 1
   uri=ticket://4521 mime=text/plain
   text=Title: Keeps getting logged out. Body: I keep getting l...
```

`a list of 1`. The handler in `shelf.py` returned a bare Python `str`, and the SDK turned it into a
one-element array with the URI and the MIME type filled in from the registration. You never wrote the
array, and it is still an array, which is the shape you have to code against.

Where does `text/plain` come from? From `mime_type="text/plain"` in the decorator
([2.1](2.1-an-address-not-a-call.md)). Remove it and the SDK picks a default; the item still has a
`mimeType` field and it is no longer one you chose.

## When it breaks

The break that costs an evening is treating the result as a document.

Reaching for `result.contents.text` on a real `ReadResourceResult` raises this, captured on
2026-09-04:

```text
AttributeError: 'list' object has no attribute 'text'
```

That one is harmless because it happens immediately. The expensive version has no error at all:

```python
text = result.contents[0].text  # the first attachment
```

The customer sent three screenshots. The read returned three items. The reply quotes one, and the
agent says *"based on the screenshot you sent"* — singular, confident, and missing two thirds of the
evidence. Nothing in the logs distinguishes this from a ticket that genuinely had one attachment.

The second break is binary arriving where text was assumed:

```text
AttributeError: 'BlobResourceContents' object has no attribute 'text'
```

This one is worth welcoming. The union in the SDK's type is doing its job: a resource whose handler
returned `bytes` produced a `blob` item, and the code that assumed characters found out at the first
opportunity rather than by writing base64 into a support reply.

The smallest fix for both is one helper, written once:

```python
def as_text(result: ReadResourceResult) -> list[str]:
    """Every text item in a read result, in order. Binary items are skipped, loudly."""
    out = []
    for item in result.contents:
        if hasattr(item, "text"):
            out.append(item.text)
        else:
            logger.warning("skipping binary item %s (%s)", item.uri, item.mimeType)
    return out
```

**Line by line:**

- It returns a `list[str]`, so the caller cannot forget there may be several. A helper that returned
  `str` would have re-created the bug it exists to prevent.
- `hasattr(item, "text")` follows the SDK's own union rather than checking `mimeType`, because a
  server may send `text/plain` in a `blob` and the field is the ground truth.
- The `else` **logs** rather than raising or passing silently. Principle 10: a skipped attachment is a
  fact, and a fact that only exists as an absence is one nobody will ever notice.
- It preserves order, because the server chose that order and the reader has no better one.

## In production

**What a professional writes instead:** every `resources/read` goes through one function that returns
a list and logs what it dropped. Nobody indexes `contents[0]` in application code. The rule is
enforced by review rather than by a linter, and it is written in the client module's docstring so a
new engineer meets it before they meet the bug.

**What degrades at scale:** message size. There is no chunking in `resources/read` — a read returns
everything, in one message, and on stdio that is one very long line held in memory on both sides
([33.2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md)). Base64
makes it worse by about a third: a 3 MB screenshot is roughly 4 MB of `blob`. A server that reads
attachments must decide, before it ships, whether it returns the bytes or returns an `https://` URI
that the client fetches for itself — and the specification prefers the second for exactly this reason.

**The failure mode that only appears with real traffic:** partial reads that are not partial. A
directory-shaped resource whose backing store is paginated returns whatever page the handler happened
to fetch, in a `contents` array that looks complete because `resultType` says `"complete"`. There is
no field for *"there is more"* on a read. If your data has more, the URI has to say so.

**The review comment a senior engineer leaves:** *"this returns `contents[0].text` and the resource is
a ticket, so it is right today. It is right by coincidence. Write the loop now — it is four lines —
because the day somebody adds attachments, this line silently starts dropping evidence and there is no
test that can catch it."*

**The interview question:** *"What does an MCP resource read actually return?"* The honest answer: *"a
result with a `contents` array, not a document. Each item carries its own URI and MIME type and is
either `text` or a base64 `blob`, and a server is allowed to return several items for one read — a
directory resource returning its files is the spec's own example. So the client code is a loop, even
when you know there is one item, because the day there are two the single-item version does not fail,
it just quietly returns the first one. The result also carries `resultType`, and only `complete`
results are cacheable."*
