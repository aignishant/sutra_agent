# 2.3 — The miss that must be an error

## One-line answer

A resource that does not exist **MUST** come back as JSON-RPC error `-32602` and never as content —
and the convenience wrapper in the pinned SDK quietly turns your correct `-32602` into `code: 0`,
which you can only find out by looking at the wire.

## The story

The weighing machine at the clinic prints a slip with your weight on it.

One morning the platform is empty and somebody presses the button anyway. The machine does what it
always does: it measures, it prints, and out comes a slip that says **0.0 kg**. The nurse standing
there laughs and drops it in the bin, because obviously nobody weighs nothing.

The slip that goes into the file is a different story. Somebody keys it into the register, because
keying in slips is the job, and the register does not laugh. Now there is a patient in the system who
weighs nothing. Six months later the dietician's report shows a dramatic loss, the machine that
printed it is fine, the nurse who binned the other one is fine, and the only thing that was ever wrong
is that a *reading* and *no reading at all* came out looking exactly the same.

The machine's fault is not that it was inaccurate. It is that it had no way of saying **I do not have
a measurement for you**. It only had numbers.

## The idea in plain language

The specification closes the resources page with three sentences that exist because of exactly this
failure (`https://modelcontextprotocol.io/specification/2026-07-28/server/resources`, read
2026-09-04):

> "If the requested resource does not exist, servers **MUST** return a JSON-RPC error with code
> `-32602` (Invalid Params). Servers **SHOULD** return `-32603` for internal errors."
>
> "For backwards compatibility, clients **SHOULD** also accept `-32002` as a resource not found
> error, as earlier protocol versions used this code."
>
> "Servers **MUST NOT** return an empty `contents` array for a non-existent resource. An empty array
> is ambiguous—it could mean the resource exists but has no content, or that it doesn't exist at all."

Three terms first, because two of them are numbers and numbers are easy to copy without
understanding.

**JSON-RPC** is the message format MCP speaks. A reply is either a `result` or an `error`, never both,
and an `error` carries a numeric `code`, a `message` and optional `data`. Day 32 laid out the envelope
([32.1.3](../../../day-32-mcp-stateless-core/parts/01-the-socket/1.3-tools-resources-prompts.md)).

**`-32602`** is JSON-RPC's standard *Invalid params* code. The 2026-07-28 revision moved
resource-not-found onto it from the MCP-specific `-32002`, which is why a document written a year ago
gives you a different number and is not wrong about anything else.

**Ambiguous** in that third sentence is the whole argument. `contents: []` could mean *this file is
empty* or *there is no such file*, and a program cannot tell which. So the spec forbids the shape
rather than asking servers to be careful with it.

And there is a fourth thing, which is the reason this part is not two paragraphs long: **your server
can obey all three rules and still put the wrong thing on the wire.** Whether the code survives
depends on which SDK layer you registered your handler with.

## Why Sutra needs it

Because Sutra has been answering a miss with a polite sentence since Day 3, and that habit is correct
on one door and catastrophic on the other.

`lookup_ticket` returns `"No ticket with id '9999'."` and should keep doing so
([1.3](../01-who-initiates/1.3-should-lookup-ticket-stop-being-a-tool.md)): a model reads it and can
tell the customer. The instinct to make the resource behave the same way is strong, symmetrical, and
wrong — a host reading `ticket://9999` would file that apology as the ticket's body, cache it under
that URI for as long as `ttlMs` allows ([4.1](../04-freshness/4.1-every-read-carries-its-expiry.md)),
and hand it to the model on a later turn as evidence.

It matters again on **Day 44**, where the client grows retries. A retry policy has to distinguish
*this failed, try again* from *this does not exist, stop*. It does that by reading the code. A server
that answers every miss with `code: 0` has made every one of its failures indistinguishable from every
other, and a client cannot write a correct policy against it.

## The mechanism

`shelf.py` does exactly what the specification asks:

```python
# days/day-35-resources-and-prompts/lab/shelf.py  (extract)
@mcp.resource("ticket://{ticket_id}", title="Support ticket", mime_type="text/plain")
def ticket_resource(ticket_id: str) -> str:
    """One ticket by id. A miss is a protocol error, never a polite sentence."""
    if ticket_id not in TICKETS:
        raise McpError(
            ErrorData(
                code=INVALID_PARAMS,
                message="Resource not found",
                data={"uri": f"ticket://{ticket_id}"},
            )
        )
    return TICKETS[ticket_id]
```

**Line by line:**

- `raise` rather than `return`. There is no way to return an error from this function — its return
  type is the resource's content — so a miss has to leave by the exception path or not at all.
- `McpError` is the SDK's carrier for a protocol error, imported from `mcp.shared.exceptions`. It
  wraps an `ErrorData`, which is the JSON-RPC error object itself.
- `code=INVALID_PARAMS` is the named constant from `mcp.types` and it is `-32602`. Using the name
  rather than the number is not style: the number changed between revisions, and the constant is what
  moves with the SDK.
- `message="Resource not found"` is copied from the specification's own example, deliberately. A
  message that varies per server is a message no client can match on.
- `data={"uri": ...}` echoes the address that failed. The code says what kind of failure; the data
  says which one, and it is what turns a log line into something you can act on.
- The guard comes **before** the read. Writing `TICKETS[ticket_id]` inside a `try` and converting the
  `KeyError` works too, and this shape is preferred because the reader sees the miss handled first,
  in the first three lines of the body.

Now look at what actually arrives at the client. `read_shelf.py` asks for a ticket that is not there:

```bash
cd days/day-35-resources-and-prompts/lab
uv run python read_shelf.py
```

**Line by line:**

- The same six-exchange script as [2.1](2.1-an-address-not-a-call.md) and
  [2.2](2.2-what-comes-back-from-a-read.md). The fourth exchange is the miss.
- **Zero generations.**

Measured on 2026-09-04:

```text
resources/read ticket://9999   (the miss)
   code=0 message='Error creating resource from template: Error creating resource from template: Resource not found' data=None
```

**`code=0`.** Not `-32602`. The `data` you attached is gone. The message you wrote is buried inside
two layers of someone else's prefix, and the prefix is there twice.

That is not a bug in your handler. Here is the exact path, read out of the installed source on
2026-09-04:

1. `mcp/server/fastmcp/resources/templates.py`, `create_resource`, ends with
   `except Exception as e: raise ValueError(f"Error creating resource from template: {e}")`. Your
   `McpError` is an `Exception`, so it is caught here and re-raised as a plain `ValueError` carrying
   only its text.
2. `mcp/server/fastmcp/resources/resource_manager.py`, `get_resource`, wraps the same call in the
   same way — `raise ValueError(f"Error creating resource from template: {e}")` — which is where the
   prefix appears a second time.
3. `mcp/server/lowlevel/server.py`, in the request handler, has two branches:
   `except McpError as err: response = err.error` and, below it,
   `except Exception as err: ... response = types.ErrorData(code=0, message=str(err), data=None)`.

By the time the exception reaches step 3 it is no longer an `McpError`, so it takes the second branch,
and the second branch **hard-codes `code=0`**. Your error code was destroyed two frames earlier by a
convenience wrapper trying to be helpful about a different problem.

The fix is to register the handler one layer down. `shelf_strict.py` is the same shelf written on
`mcp.server.lowlevel.Server`, which does not wrap:

```python
# days/day-35-resources-and-prompts/lab/shelf_strict.py  (extract)
def not_found(uri: str) -> McpError:
    """The error the specification requires for a resource that does not exist."""
    return McpError(
        types.ErrorData(code=types.INVALID_PARAMS, message="Resource not found", data={"uri": uri})
    )


@server.read_resource()
async def read_resource(uri: AnyUrl) -> str:
    """Route one URI by hand, and raise McpError for anything the shelf does not hold."""
    text = str(uri)
    if text == "archive://summary":
        return f"Sutra archive: {len(TICKETS)} tickets, {len(KB)} knowledge-base articles."
    for prefix, store in (("ticket://", TICKETS), ("kb://", KB)):
        if text.startswith(prefix):
            key = text[len(prefix) :]
            if key not in store:
                raise not_found(text)
            return store[key]
    raise not_found(text)
```

**Line by line:**

- `not_found` is a **function returning** an exception rather than raising one, so the call sites read
  `raise not_found(text)`. That keeps the three raise points on one line each and the error's shape in
  exactly one place.
- `@server.read_resource()` is the low-level decorator. There is one handler for the whole server, not
  one per URI, which is the trade: you get the error path back and you route by hand.
- `uri: AnyUrl` — the low-level server hands you the parsed URL object, so `str(uri)` is the first
  line of the body.
- The `archive://summary` branch is checked by exact match because it is one fixed address, while the
  two families are checked by prefix. That difference is the template mechanism, done manually
  ([2.4](2.4-one-label-for-a-family.md)).
- `text[len(prefix):]` takes everything after the scheme. No decoding, no normalising — which is
  correct here and is exactly the assumption that
  [5.1](../05-failure-lab/5.1-the-address-that-reached-outside.md) breaks on purpose.
- The **final** `raise not_found(text)` catches a URI matching no prefix at all. Without it the
  function falls off the end and returns `None`, and `None` becomes a successful read of nothing —
  the empty-contents shape the specification forbids.
- Nothing here is wrapped in `try`. That is the point: the low-level server's own handler catches
  `McpError` first and uses `err.error` unchanged.

Run the same six exchanges against it. The only thing that changes is which server is spawned:

```bash
cd days/day-35-resources-and-prompts/lab
SHELF=shelf_strict.py uv run python read_shelf.py
```

**Line by line:**

- `SHELF=shelf_strict.py` is the ablation switch. `read_shelf.py` reads it out of the environment and
  launches that file instead; every request it sends is byte-for-byte the same.
- **Zero generations**, again.

Measured on 2026-09-04:

```text
resources/read ticket://9999   (the miss)
   code=-32602 message='Resource not found' data={'uri': 'ticket://9999'}
```

Same specification, same intent, same `McpError` — and two different things on the wire. The
difference is a decorator.

## When it breaks

The break with the highest cost is the one that produces no error at all, and it is a two-line
temptation:

```python
@mcp.resource("ticket://{ticket_id}")
def ticket_resource(ticket_id: str) -> str:
    return TICKETS.get(ticket_id, f"No ticket with id {ticket_id!r}.")
```

Every read succeeds. `contents[0].text` is a string. `resultType` is `complete`. The host caches it,
attaches it to the next turn, and the model writes a support reply that reasons about a ticket whose
entire body is an apology. The evidence that anything went wrong looks like this, and it is not a log
line:

```text
reply sent to customer quotes "No ticket with id '9999'." as the reported problem
```

The empty-array version is the same failure wearing a different coat:

```python
return []  # "there is no such ticket"
```

The specification forbids it in those words — *"An empty array is ambiguous"* — because a reader
cannot distinguish it from a genuinely empty document.

And the third break is the one this part exists for: writing the correct `McpError` and never checking
what left the process. `code=0` is not a JSON-RPC code at all — the standard reserves `-32768` to
`-32000` for protocol errors and leaves the rest to applications, and zero means nothing to anybody. A
client's retry policy reads it, finds no case that matches, and falls through to whatever the default
is. On Day 44 that default is *retry*, which turns a permanent miss into a loop.

The smallest fix, in order of preference: register on the low-level `Server` when the error path
matters; or, if you are keeping FastMCP, assert the code in a test rather than trusting the raise:

```python
with pytest.raises(McpError) as caught:
    await session.read_resource(AnyUrl("ticket://9999"))
assert caught.value.error.code == INVALID_PARAMS
```

That test goes red against `shelf.py` today. A test that goes red against your own working code is
exactly the kind Principle 11 asks for.

## In production

**What a professional writes instead:** the error shape is a function, not a literal, and it lives
beside the handlers — one `not_found(uri)` used by every read path in the server. The message string is
the specification's, not a friendly variant, so clients can match on it. And there is one test per
surface asserting the code that actually reaches the client, because the wire is the contract and the
handler is only an intention.

**What degrades at scale:** misses stop being rare. A host with a stale `resources/list` reads URIs
that were deleted at the last deploy ([4.3](../04-freshness/4.3-the-list-that-outlived-the-deploy.md)),
so `-32602` becomes routine traffic rather than an exception, and the difference between *a miss* and
*a server fault* has to be visible in a dashboard. If every failure is `code: 0`, that dashboard cannot
be built.

**The failure mode that only appears with real traffic:** the message leaks. `data={"uri": ...}` is
safe; `message=f"No ticket {ticket_id} for account {account}"` is a user identifier in an error body
that a shared gateway may log, and the person who wrote it was being helpful. Keep the identifying
part in `data`, where you can decide per field what is returned.

**The review comment a senior engineer leaves:** *"the handler raises `McpError` with `-32602` and the
integration test asserts that a read of a missing ticket raises. It does raise — with `code: 0`,
because FastMCP re-wraps it. Assert the code, not the exception type, and either move to the low-level
server or write down that we are knowingly non-conformant here."*

**The interview question:** *"What does your MCP server return when a resource does not exist?"* The
honest answer: *"`-32602` with the URI in `data`, because the spec makes it a MUST and explicitly
forbids returning empty contents — an empty array cannot be told apart from a real empty document. The
thing I would flag is that we found the framework destroying the code. FastMCP wraps a resource
handler's exception in a `ValueError`, so by the time the low-level server sees it, it is no longer an
`McpError` and the catch-all hard-codes `code: 0`. We only found it because we drove our own server
over stdio and printed the raw error object. The lesson I took is that the wire is the contract: a
handler that raises the right exception has proved nothing until you have read what left the
process."*
