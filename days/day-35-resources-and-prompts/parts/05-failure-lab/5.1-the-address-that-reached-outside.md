# 5.1 — 💥 The address that reached outside the room

## One-line answer

The SDK's template matcher refuses a `/` in a parameter, which looks like a safety check and is not
one — percent-encode the slashes and the matcher passes them through untouched, and it is your handler
that decodes them and opens a file outside the directory you meant to publish.

## The story

🎬 **The scene.** The watchman at the gate of the apartment block keeps a register. Anyone going in
writes their name, who they are visiting, and the flat number. He checks the flat number is a flat
number — three digits, nothing odd — and he waves them through.

😬 **The naive fix.** Somebody points out that people could write anything in the flat box. So the rule
is tightened: the number must be digits only, no slashes, no words. Now the register is clean. Every
entry is a real-looking flat number and the watchman can say, truthfully, that he checks every one.

💥 **Why it fails.** The watchman is at the gate. The lift is inside. A visitor writes `402`, is waved
through, walks past him, and presses whichever button they like — the basement where the meters are,
the terrace, the flat on the other stack. The register is complete and accurate and it recorded a
decision that was never enforced. What the watchman checked and what actually happened are two
different things separated by thirty feet of corridor.

💡 **The insight.** A check that runs somewhere other than where the action happens has not checked the
action. It has checked a piece of paper, and the paper and the lift do not have to agree.

## The idea in plain language

Sutra's shelf publishes tickets and knowledge-base articles, both keyed by short ids. The obvious next
resource is documents, and the obvious template for documents is `doc://{path}`.

Two facts collide there.

**Fact one: the SDK's matcher does not allow a slash inside a parameter.** Read out of the installed
library on 2026-09-04, `mcp/server/fastmcp/resources/templates.py` builds its regular expression like
this:

```text
pattern = self.uri_template.replace("{", "(?P<").replace("}", ">[^/]+)")
match = re.fullmatch(pattern, uri)
```

`[^/]+` means *one or more characters that are not a forward slash*. So `doc://../../.env` does not
match `doc://{path}` at all. The request never reaches your function. That feels like a guard.

**Fact two: `%2F` is not a slash.** In a URI, characters that would otherwise be structural are
written as a percent sign and two hexadecimal digits. `%2F` is how you write a `/` that is data rather
than a separator. It is three ordinary characters — `%`, `2`, `F` — and `[^/]+` is perfectly happy with
all three.

So the matcher sees no slash, binds the parameter, and hands your handler the string `..%2F..%2F.env`.
And then your handler, being a sensible handler, decodes it — because a percent-encoded parameter that
is not decoded is not usable — and now it is holding `../../.env`.

The check was at the gate. The `open()` is in the lift.

The specification names this exact failure in its security section, and it is worth reading as two
separate requirements rather than one:

> 1. Servers **MUST** validate all resource URIs
> 5. Servers **MUST** sanitize file paths to prevent directory traversal attacks when serving `file://`
>    resources
>
> (`https://modelcontextprotocol.io/specification/2026-07-28/server/resources`, read 2026-09-04)

Rule 1 is about the URI. Rule 5 is about the **path you build from it**, and it exists separately
because doing the first does not do the second.

One term, defined properly because it is the whole attack. **Directory traversal** is using `..` — the
name every filesystem gives to "the folder above this one" — to walk out of a directory that was
supposed to contain you. `public/../secret.env` and `secret.env` are the same file, and only one of
them looks like it is outside `public/`.

## Why Sutra needs it

Because Sutra's repository has a `.env` in it, and Principle 9 says secrets never touch git precisely
because they are the thing worth stealing.

Nothing in `sutra_mcp` serves files today. That is the reason to do this now rather than later: the
first `file://`-shaped resource anyone adds will be added by someone who has read
[2.4](../02-the-shelf/2.4-one-label-for-a-family.md), seen `[^/]+` refuse a slash, and concluded the
template was doing the validating. This part exists to remove that conclusion before the code exists.

It arrives for real on **Day 39**, when tickets move into SQLite and the natural next step is
attachments on disk, and again on **Day 40**, where allowlists are the defence against servers you did
not write. A traversal in your own server is not something an allowlist can help with — it is one URI
your own code resolved wrongly.

## The mechanism

`lab/traversal.py` builds a throwaway directory in a temp folder: a published root with two documents
in it, and one secret file that lives *outside* the root, as an environment file would.

The two handlers are four lines apart:

```python
# days/day-35-resources-and-prompts/lab/traversal.py  (extract)
def read_naive(root: pathlib.Path, path: str) -> str:
    """What everybody writes first: decode the parameter, join it, open it."""
    return (root / unquote(path)).read_text(encoding="utf-8")


def read_strict(root: pathlib.Path, path: str) -> str:
    """Decode first, resolve both sides, then refuse anything that left the root."""
    target = (root / unquote(path)).resolve()
    if not target.is_relative_to(root.resolve()):
        raise PermissionError(f"outside the published root: {path}")
    return target.read_text(encoding="utf-8")
```

**Line by line:**

- `unquote(path)` is `urllib.parse.unquote`, and it turns `%2F` back into `/`. Both handlers call it,
  because both must — a handler that does not decode cannot serve a document whose name contains a
  space. The decoding is not the bug.
- `root / unquote(path)` uses `pathlib`'s `/` operator to join. It does no normalising and no checking;
  `Path("public") / "../secret.env"` is simply `public/../secret.env`, and the operating system
  resolves the `..` when the file is opened.
- `read_naive` opens it right there. Every character of that function is reasonable and it is the
  version that gets written, because the template already refused the obvious attack and it felt
  handled.
- `read_strict` calls `.resolve()` **first**. That is the load-bearing line: `resolve()` collapses
  every `..`, follows symbolic links, and returns an absolute path. Until you resolve, you are
  comparing a string that has not been interpreted yet.
- `target.is_relative_to(root.resolve())` asks whether the resolved target is underneath the resolved
  root. Both sides are resolved, which matters: comparing a resolved target against an unresolved root
  fails on any machine where the root itself contains a symbolic link, which every temp directory on
  this platform does.
- `is_relative_to` rather than `str(target).startswith(str(root))`. String prefixes are the classic
  wrong version — `/srv/public-backup` starts with `/srv/public` and is a different directory.
- `raise PermissionError` rather than returning empty. A refusal is a fact and it must leave a trace
  ([2.3](../02-the-shelf/2.3-the-miss-that-must-be-an-error.md)); in a real server this is the
  `McpError` shape from that part, and this script uses the built-in exception so it stays runnable on
  its own.

Run the naive version:

```bash
uv run python days/day-35-resources-and-prompts/lab/traversal.py; echo "exit: $?"
```

**Line by line:**

- The script creates its own temporary directory, writes three files into it, and deletes the lot when
  it exits. **Nothing in the repository is read or written**, which is the only responsible way to
  demonstrate this.
- `echo "exit: $?"` because the verdict is the exit code: non-zero when a read escaped.
- **Zero generations**, zero network.

Measured on 2026-09-04:

```text
handler: read_naive
published root: public/  (readme.md, notes/plan.md)
outside it: secret.env

uri                            matcher binds          handler
------------------------------------------------------------------------------------
doc://readme.md                readme.md              'the readme a host may read'
doc://notes/plan.md            (no match)             never reaches the handler
doc://../secret.env            (no match)             never reaches the handler
doc://..%2Fsecret.env          ..%2Fsecret.env        'GOOGLE_API_KEY=not-a-real-key'  <-- OUTSIDE THE ROOT
doc://%2E%2E%2Fsecret.env      %2E%2E%2Fsecret.env    'GOOGLE_API_KEY=not-a-real-key'  <-- OUTSIDE THE ROOT

reads that escaped the published root: 2
exit: 1
```

Read the middle two rows and the bottom two rows together, because the whole lesson is in the contrast.

`doc://../secret.env` — the attack written plainly — **does not match**. The matcher stopped it. If you
had tested only this, you would have concluded the template was safe and you would have been testing
the wrong string.

`doc://..%2Fsecret.env` — the same attack, encoded — **matches, binds, and reads the file**. The `<--`
marker is the script noticing that the content it got back is the secret rather than a published
document.

And the last row is there to close a door people reach for next. `%2E` is an encoded `.`, so
`%2E%2E%2F` is `../` with every character encoded. A filter that looks for the literal characters `..`
in the raw parameter does not see it. **Blocking `..` is not the fix.** Resolving the path is.

Now the ablation. Same script, same URIs, one environment variable:

```bash
STRICT=1 uv run python days/day-35-resources-and-prompts/lab/traversal.py; echo "exit: $?"
```

**Line by line:**

- `STRICT=1` selects `read_strict` instead of `read_naive`. Nothing else changes: same directory, same
  five requests, same matcher.

```text
handler: read_strict
published root: public/  (readme.md, notes/plan.md)
outside it: secret.env

uri                            matcher binds          handler
------------------------------------------------------------------------------------
doc://readme.md                readme.md              'the readme a host may read'
doc://notes/plan.md            (no match)             never reaches the handler
doc://../secret.env            (no match)             never reaches the handler
doc://..%2Fsecret.env          ..%2Fsecret.env        REFUSED: outside the published root: ..%2Fsecret.env
doc://%2E%2E%2Fsecret.env      %2E%2E%2Fsecret.env    REFUSED: outside the published root: %2E%2E%2Fsecret.env

reads that escaped the published root: 0
exit: 0
```

**2 → 0**, from four lines that resolve before they open.

There is a second finding sitting in row two of both runs, and it is the reason this template was a bad
design before it was a vulnerability. `doc://notes/plan.md` — an ordinary document in a subdirectory,
nothing hostile about it — **does not match either**. `[^/]+` refuses it. So `doc://{path}` cannot serve
a nested document at all, and a server that publishes it has published a template covering only the top
level of its own corpus, with no error anywhere to say so.

## When it breaks

It has already broken; this whole part is the break. What is worth adding is what the break looks like
when it is not a lab.

There is no traceback. `read_naive` succeeded. The server returned `resultType: "complete"`, a
`contents` array with one `text` item in it, and a `mimeType` of `text/plain`. Every layer behaved. The
only evidence is in the content, and the content went to a model.

If you are lucky, it looks like this in a transcript:

```text
resources/read doc://..%2Fsecret.env -> contents[0].text: "GOOGLE_API_KEY=..."
```

If you are not lucky, nobody reads the transcript, and the key is in a context window that was logged,
cached with `cacheScope: "public"` ([4.1](../04-freshness/4.1-every-read-carries-its-expiry.md)), and
handed to a model whose provider you do not run.

The two fixes that do not work, in the order people try them:

- **Rejecting `..` in the parameter.** Beaten by `%2E%2E`, as the last row of the transcript shows.
  Encoding is not one layer deep; you can encode the encoding.
- **Trusting the matcher.** It refused three of five hostile inputs and passed two, and which three it
  refused is a property of a regular expression inside somebody else's library that can change in a
  release.

The fix that works is resolving both paths and comparing them, and it works because it asks the
operating system the same question the `open()` is about to ask.

## In production

**What a professional writes instead:** the published root is an absolute, resolved path computed once
at startup, and every read goes through one function that resolves and compares before opening. The
function raises, and there is a test with the encoded traversal string in it that fails if the check is
removed. Most production servers also do not publish a `{path}` template at all — they publish an
opaque id and keep the id-to-path mapping on the server, so there is no path in the URI to attack.

**What degrades at scale:** symbolic links. A published directory containing a link to somewhere else
resolves out of the root, and `resolve()` follows links by design, so the strict handler refuses it —
correctly, and to the surprise of whoever put the link there. That is the right failure and it will be
reported as a bug, so the refusal message needs to say *outside the published root* rather than
*permission denied*.

**The failure mode that only appears with real traffic:** case and Unicode. On a case-insensitive
filesystem, `public/` and `PUBLIC/` are the same directory and two different strings; on any
filesystem, Unicode normalisation means two different byte sequences can name one file. Both of those
defeat string comparison and neither defeats `resolve()` plus `is_relative_to`, which is one more
reason not to compare strings.

**The review comment a senior engineer leaves:** *"the resource template is `doc://{path}` and the
handler joins the parameter onto a base directory. The SDK's matcher rejects a raw slash, which is why
this looks fine, and `%2F` walks straight through it. Resolve the joined path and check it is under the
root — and add the percent-encoded case to the tests, because the plain one passes today for the wrong
reason."*

**The interview question:** *"Your MCP server exposes files through a URI template. What do you check?"*
The honest answer: *"that the resolved path is inside the published root, and I check it in the handler
rather than relying on the URI. The SDK's template matcher rejects a slash inside a parameter, so
`doc://../../.env` never matches and it looks like the template is validating for you. It is not —
`%2F` is not a slash, so the encoded version matches, binds, and the handler decodes it into a
traversal. We measured that: two of five hostile URIs read a file outside the root, and blocking the
literal `..` does not help because `%2E%2E` gets past it too. The fix is `resolve()` on both sides and
`is_relative_to`, never a string prefix, and the best fix is not to put a path in the URI at all."*
