# 3.2 — Arguments are declared, not guessed

## One-line answer

A prompt publishes its arguments by name, with a description and a `required` flag, so a host can
build a form instead of guessing — and the specification says a missing one is `-32602`, which is a
promise you have to check your server actually keeps.

## The story

The tailor's measurement slip has printed boxes on it, and the boxes have names.

Chest. Waist. Sleeve. Shoulder. Length. Beside three of them there is a small star, and at the bottom
of the slip it says the starred ones must be filled in. The others are useful and the tailor can work
without them.

You bring the slip back with the chest box empty. He does not guess. He does not average it out from
the shoulder measurement, and he does not cut the cloth and hope. He hands the slip back across the
counter and points at the star. It costs you a second trip and it is the cheapest thing that happens
all week, because the alternative is a shirt that fits nobody, made out of cloth that is now cut.

And there is a box he does not have. You write *"make it look smart"* in the margin. He reads it,
because it is on the slip, and there is nothing on the slip that tells him whether *smart* is a
measurement or a mood. The printed boxes protected him from the empty chest. Nothing on the slip
protects him from the margin.

## The idea in plain language

A prompt's arguments are declared in `prompts/list`, not discovered when someone calls it. Here is the
specification's own example entry, copied exactly
(`https://modelcontextprotocol.io/specification/2026-07-28/server/prompts`, read 2026-09-04):

```json
{
  "name": "code_review",
  "title": "Request Code Review",
  "description": "Asks the LLM to analyze code quality and suggest improvements",
  "arguments": [
    {
      "name": "code",
      "description": "The code to review",
      "required": true
    }
  ]
}
```

Three fields on an argument, and each does a different job:

| Field | Who reads it | What breaks without it |
| --- | --- | --- |
| `name` | the host, to key the value it sends | nothing — it is required |
| `description` | the **person** filling in the box | the user does not know what to type |
| `required` | the host, to decide whether to block submission | the call goes out incomplete and fails at the server |

Notice what is **not** there: there is no type, no pattern, no enumeration of allowed values. A tool's
arguments are described by a full JSON Schema
([4.1.2](../../../day-04-tools-by-hand/parts/01-the-schema/1.2-declaring-a-tool.md)). A prompt's are
described by a name, a sentence and a boolean. Every argument is a string as far as the protocol is
concerned.

That is a deliberate difference and it has a consequence you carry for the rest of the day: **nothing
in the protocol validates a prompt argument's content.** The host can enforce presence, because
`required` tells it to. It cannot enforce shape, because nothing describes the shape. The margin of
the slip has no printed box.

For the failures that *are* covered, the specification is short and unambiguous:

> Servers **SHOULD** return standard JSON-RPC errors for common failure cases:
>
> * Invalid prompt name: `-32602` (Invalid params)
> * Missing required arguments: `-32602` (Invalid params)
> * Internal errors: `-32603` (Internal error)

And a line that reads like boilerplate and is not:

> "Servers **SHOULD** validate prompt arguments before processing"

## Why Sutra needs it

Because `triage_ticket` takes a ticket id, and a ticket id is the one argument in this whole day that a
caller can get wrong in an interesting way.

A host that has the id sends it. A host that does not — a chat client where the user typed the command
and then typed whatever they remembered — sends whatever the person typed. `required: true` guarantees
the box was not left blank. It guarantees nothing else, and the interesting failures are all in the
"nothing else": a ticket id with a `#` on the front, an id for a different system, a whole sentence,
or the hostile string that [5.3](../05-failure-lab/5.3-the-argument-that-gave-an-order.md) is about.

It matters again on **Day 37**, where elicitation lets a server ask the *user* a structured question
mid-call. That mechanism exists partly because this one is so thin: when a server needs a typed,
validated answer, a prompt argument is not the surface that gives it one.

## The mechanism

On the low-level server, the argument is declared by hand, and the declaration is where the
description lives:

```python
# days/day-35-resources-and-prompts/lab/shelf_strict.py  (extract)
@server.list_prompts()
async def list_prompts() -> list[types.Prompt]:
    """One card, declared with its argument described rather than merely named."""
    return [
        types.Prompt(
            name="triage_ticket",
            title="Triage a ticket the Sutra way",
            description="The desk's house phrasing for diagnosing one ticket honestly.",
            arguments=[
                types.PromptArgument(
                    name="ticket_id",
                    description="The id of the ticket to triage, for example 4521.",
                    required=True,
                )
            ],
        )
    ]
```

**Line by line:**

- `types.Prompt` and `types.PromptArgument` are the SDK's models for the two records above, imported
  from `mcp.types`. Building them explicitly is what the low-level server asks for, and it is why this
  file can say things FastMCP's decorator cannot.
- `description="The id of the ticket to triage, for example 4521."` includes an **example**. The
  person filling in the box has never seen your id format. `"The ticket id"` tells them nothing they
  could not infer from the name; the example tells them whether to type `4521` or `TICKET-4521`.
- `required=True` is explicit rather than defaulted. The SDK's declaration is
  `required: bool | None = None`, read from `.venv/Lib/site-packages/mcp/types.py` on 2026-09-04 — so
  leaving it out sends no `required` field at all, and a host reading that has been told nothing
  rather than told `false`. A required argument that arrives as *unspecified* produces a call the host
  is happy to send and the server cannot answer.
- The whole thing is a **list**, returned from a function. Every call to `prompts/list` re-runs it, so
  a server whose prompt set depends on something can express that — and must still obey the rule that
  it MUST NOT vary per connection ([3.1](3.1-the-words-the-house-owns.md)).

Rendering it is where the validation has to happen, because nothing above did any:

```python
# days/day-35-resources-and-prompts/lab/shelf_strict.py  (extract)
@server.get_prompt()
async def get_prompt(name: str, arguments: dict[str, str] | None) -> types.GetPromptResult:
    """Render the card, rejecting an unknown name and a missing argument by hand."""
    if name != "triage_ticket":
        raise McpError(
            types.ErrorData(code=types.INVALID_PARAMS, message=f"Unknown prompt: {name}")
        )
    ticket_id = (arguments or {}).get("ticket_id")
    if not ticket_id:
        raise McpError(
            types.ErrorData(code=types.INVALID_PARAMS, message="Missing argument: ticket_id")
        )
    ...
```

**Line by line:**

- One handler serves every prompt on the server, so the first thing it does is check the name. This is
  the same trade as the resource handler in
  [2.3](../02-the-shelf/2.3-the-miss-that-must-be-an-error.md): you route by hand and you keep the
  error path.
- `arguments: dict[str, str] | None` — the parameter is genuinely optional on the wire, so `None` is a
  case, not a defensive habit. `(arguments or {})` collapses both shapes into one before the lookup.
- `.get("ticket_id")` rather than `arguments["ticket_id"]`. Indexing raises a `KeyError`, which is not
  an `McpError`, which means the low-level server's catch-all turns it into `code: 0` and the whole
  point of this handler is lost.
- `if not ticket_id` catches the empty string as well as the missing key. A host that sends
  `{"ticket_id": ""}` has sent the argument and has not sent a value, and treating those differently
  helps nobody.
- Both raises use `types.INVALID_PARAMS`, which is `-32602` — the code the specification names for
  both of these cases.
- The messages are short and specific. `"Missing argument: ticket_id"` names the field, so a host can
  put the error next to the right box on its form.

Now ask both servers three bad questions. `lab/card_probe.py` sends a call with no argument, a call
naming a prompt that does not exist, and a call with an argument nobody declared:

```bash
cd days/day-35-resources-and-prompts/lab
uv run python card_probe.py
```

**Line by line:**

- It drives `shelf.py` by default and `shelf_strict.py` when `SHELF` is set, exactly like
  `read_shelf.py`. The three cases are a list at the top of the file so a fourth is one line to add.
- **Zero generations.** A rejected `prompts/get` never reaches a model, and neither does an accepted
  one.

Measured on 2026-09-04, against the FastMCP shelf:

```text

missing argument   (spec says -32602)
   code=0 message="Missing required arguments: {'ticket_id'}"

   code=0 message='Error rendering prompt triage_ticket: 1 validation error for triage_ticket'
```

And against the low-level one, same three requests:

```bash
SHELF=shelf_strict.py uv run python card_probe.py
```

**Line by line:**

- The ablation switch. Only the server changes; the client sends identical bytes.

```text
driving shelf_strict.py

missing argument   (spec says -32602)
   code=-32602 message='Missing argument: ticket_id'
unknown prompt     (spec says -32602)
   code=-32602 message='Unknown prompt: no_such_card'
extra argument     (spec says server's choice)
   NO ERROR - rendered 'You are triaging one support ticket for the Su'...
```

Three rows, and each one says something different.

**Row one and row two** repeat [2.3](../02-the-shelf/2.3-the-miss-that-must-be-an-error.md)'s finding
on a new surface: FastMCP raises `ValueError` internally, the low-level server's catch-all hard-codes
`code=0`, and the specification's `-32602` never reaches the wire. Same cause, same fix.

**Row three is new, and it goes the other way.** FastMCP *rejects* an undeclared argument, because it
passes the arguments as keyword arguments into a `validate_call`-wrapped function and pydantic refuses
an unexpected keyword. The hand-written server *accepts* it: it reads `ticket_id`, ignores `tone`
entirely, and renders happily. Neither is wrong — the specification does not say what to do with an
extra argument — and that is the finding. **The strict server is stricter about codes and looser about
inputs**, and if you had assumed "low-level means safer" you would have assumed wrongly.

## When it breaks

The break with no error is row three, generalised: **a host sends something you never declared and you
never notice.**

A host adds a `locale` argument to every prompt call because its own product supports languages. Your
handler ignores it. Every reply comes back in English. Nothing anywhere reports a problem, because
from the protocol's point of view nothing went wrong — you were sent a key and you did not read it.

The break with an error is what a FastMCP prompt does on a missing argument, and it is worth seeing in
full because the useful line is at the bottom of a stack that looks like a server crash. Captured from
the server's stderr on 2026-09-04:

```text
Error getting prompt triage_ticket
Traceback (most recent call last):
  File "...\mcp\server\fastmcp\server.py", line 1081, in get_prompt
    messages = await prompt.render(arguments, context=self.get_context())
  File "...\mcp\server\fastmcp\prompts\base.py", line 149, in render
    raise ValueError(f"Missing required arguments: {missing}")
ValueError: Missing required arguments: {'ticket_id'}
```

Two things to read out of it. The server did **not** crash — this is a logged exception and the
process kept serving. And `ValueError` is the reason the client saw `code=0`: it is not an `McpError`,
so the low-level handler's second branch caught it.

The smallest fix, if you are staying on FastMCP, is to validate before the framework does — check the
argument yourself at the top of the function body and raise `McpError` there. It does not help: the
wrapper catches your `McpError` too. The honest options are to move that prompt to the low-level
server, or to write down in the server's README that its prompt errors are non-conformant and why.

## In production

**What a professional writes instead:** every argument gets a description with a worked example in it,
and the handler validates shape before it renders — a regular expression for an id, a length cap for
free text. The validation is not there to be pedantic; it is the only place it can happen, because the
protocol carries no schema for prompt arguments and the host therefore cannot check anything but
presence.

**What degrades at scale:** argument sets drift between what the card declares and what the handler
reads. A prompt with six arguments, four of them optional, is a form somebody added a field to and a
function somebody else forgot to update. The list and the handler are two functions in two places and
nothing compares them, so a test that renders every declared prompt with every declared argument is
worth more than it looks.

**The failure mode that only appears with real traffic:** free-text arguments arrive full of the
things people type. Newlines, quotation marks, a pasted stack trace, a pasted email thread, the
customer's entire complaint in a box that was meant to hold a number. Everything in
[5.3](../05-failure-lab/5.3-the-argument-that-gave-an-order.md) starts here.

**The review comment a senior engineer leaves:** *"`ticket_id` is declared `required: true` and the
handler does `arguments['ticket_id']`. A host that sends the key with an empty string gets a `KeyError`
turned into `code: 0`, and a host that sends it as `#4521` gets a resource read that fails later,
somewhere else. Validate the shape here, where you can say what is wrong."*

**The interview question:** *"How does a client know what to pass to an MCP prompt?"* The answer that
shows you have used it: *"from `prompts/list` — each prompt declares its arguments by name, with a
description and a `required` flag, and that is all. There is no JSON Schema like there is for a tool,
so the host can build a form and enforce that the required boxes are filled, and it cannot enforce
anything about what is in them. Every argument is a string. That means the server is the only place
validation can happen, and it also means an argument is untrusted text arriving inside wording the
server itself wrote — which is a prompt injection with your own name on it if you interpolate it
carelessly."*
