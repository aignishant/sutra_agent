# 3.4 — The card that points at the shelf

## One-line answer

A prompt message can carry the document itself (`resource`) or only its address (`resource_link`), and
the choice is the same one the shelf and the counter were about — whether the server decides what gets
read, or the host does.

## The story

The teacher hands out the reading for next week, and there are two ways she does it.

Some weeks it is a photocopy. Four pages, stapled, in every child's hand before they leave the room.
Nobody has to go anywhere, nobody can lose their turn, and the child whose family has no library card
is in exactly the same position as everybody else. It also costs forty photocopies, it weighs
something in every bag, and when the textbook is revised in the spring the photocopies do not change.

Other weeks it is a line on the board: *chapter four, the copy in the library*. Nothing to carry.
Always the current edition. But now the child has to get to the library, the library has to be open,
and there is one copy for the whole class.

Neither is the right answer in general. What decides it is how many children there are, whether the
chapter is likely to change, and whether you can be sure everyone can reach the library.

## The idea in plain language

The `content` of a prompt message can be five things
([3.3](3.3-what-a-prompt-hands-back.md)). Two of them refer to a resource, and they refer to it in
opposite ways.

**An embedded resource** carries the content inline. The specification's shape
(`https://modelcontextprotocol.io/specification/2026-07-28/server/prompts`, read 2026-09-04):

```json
{
  "type": "resource",
  "resource": {
    "uri": "resource://example",
    "mimeType": "text/plain",
    "text": "Resource content"
  }
}
```

> "Embedded resources enable prompts to seamlessly incorporate server-managed content like
> documentation, code samples, or other reference materials directly into the conversation flow."

**A resource link** carries the address and the metadata, and nothing else:

```json
{
  "type": "resource_link",
  "uri": "file:///project/src/main.rs",
  "name": "main.rs",
  "description": "Primary application entry point",
  "mimeType": "text/x-rust"
}
```

> "Prompt messages **MAY** include links to
> [Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources), to provide
> additional context or data without embedding the resource contents directly. In this case, the
> prompt message returns a URI that can be fetched by the client."

Read the two quotations next to each other and the difference is one word: *directly*. Embedding puts
the bytes in the message. Linking puts a name in the message and leaves the fetching to somebody else.

That "somebody else" is the whole decision, and it is
[1.1](../01-who-initiates/1.1-the-hand-that-reaches-first.md)'s question arriving in a new place:

| | Embedded `resource` | `resource_link` |
| --- | --- | --- |
| who decides it is read | the **server**, at render time | the **host**, afterwards or never |
| freshness | frozen at render | read when read |
| size of the message | the whole document | a few hundred bytes |
| what a host that ignores it loses | nothing — it is already there | everything the link pointed at |
| works when the host cannot read resources | yes | no |

That last row is the one people forget, and it is the same argument as
[1.3](../01-who-initiates/1.3-should-lookup-ticket-stop-being-a-tool.md): a host is not obliged to
implement resource reading. A card built entirely out of links is a card that does nothing at all in
such a host, and it does nothing *silently* — the messages arrive, they contain URIs, and the model
reasons about a filename.

## Why Sutra needs it

Because today's card names the address in prose, which is the weakest of the three options and worth
knowing you have chosen.

`triage_ticket` renders the sentence *"Read `ticket://<that id>`"*
([3.1](3.1-the-words-the-house-owns.md)). That is a **string** that happens to contain a URI. No host
can act on it programmatically. A host that wanted to prefetch the ticket for the model would have to
parse English to find the address, which nobody does. So the sentence is aimed at the model, and the
model can only follow it if it has a tool that reaches Sutra's shelf.

Turning that sentence into a `resource_link` makes the same address machine-readable: the host sees a
typed content block with a `uri` field on it, and can decide to read it, show it, or ignore it. Turning
it into an embedded `resource` makes the ticket text arrive whether the host wanted it or not.

The decision matters more in Phase 8, where Sutra's own triage graph will be the host. A graph node
that receives a link can decide, per ticket, whether the body is worth the context it costs — which is
[5.2](../05-failure-lab/5.2-the-read-that-filled-the-window.md)'s whole subject. A graph node that
receives an embedded ticket has already spent it.

## The mechanism

Both shapes, built with the SDK's own types so the field names are the library's rather than a
memory's:

```python
# days/day-35-resources-and-prompts/lab/linked_card.py  (extract)
def embedded() -> types.PromptMessage:
    """The whole ticket, inline in the message. The host needs nothing else."""
    return types.PromptMessage(
        role="user",
        content=types.EmbeddedResource(
            type="resource",
            resource=types.TextResourceContents(
                uri=AnyUrl(TICKET_URI), mimeType="text/plain", text=TICKET_TEXT
            ),
        ),
    )


def linked() -> types.PromptMessage:
    """The ticket's address only. The host decides whether to read it, and when."""
    return types.PromptMessage(
        role="user",
        content=types.ResourceLink(
            type="resource_link",
            uri=AnyUrl(TICKET_URI),
            name="ticket_4521",
            title="Support ticket 4521",
            description="The raw text of the ticket being triaged.",
            mimeType="text/plain",
        ),
    )
```

**Line by line:**

- `types.EmbeddedResource` wraps a **`resource` field**, and that inner object is the exact same
  `TextResourceContents` a `resources/read` would have returned
  ([2.2](../02-the-shelf/2.2-what-comes-back-from-a-read.md)). That is not a coincidence and it is the
  useful thing to notice: embedding is literally pasting a read result into a message.
- `types.ResourceLink` is flat. There is no inner object because there is no content — the URI *is*
  the payload, and everything else on it is metadata to help a host decide.
- `name="ticket_4521"` on the link and no `name` anywhere on the embedded version. A link needs a
  handle a host can show in a list; an embedded resource is already open in front of you.
- `description=` appears only on the link, for the same reason. It answers *should I fetch this?*, and
  that question does not exist once the bytes are already there.
- `type="resource"` and `type="resource_link"` are written out even though the class implies them.
  They are the discriminator on the wire, and a client's parser routes on the string, not on the class
  you happened to construct.
- `AnyUrl(TICKET_URI)` for both. The same address, expressed the same way, in two messages that mean
  very different things.

**Line by line:**

- From the repository root. **Zero generations, zero network, no server** — this builds two objects and
  serialises them.

Measured on 2026-09-04:

```text
=== embedded resource
   content.type : resource
   on the wire  : {"role":"user","content":{"type":"resource","resource":{"uri":"ticket://4521","mimeType":"text/plain","text":"Title: Keeps getting logged out. Body: I keep getting logged out of the dashboard every few minutes. Started yesterday. Plan: Pro."}}}

=== resource_link
   content.type : resource_link
   on the wire  : {"role":"user","content":{"name":"ticket_4521","title":"Support ticket 4521","uri":"ticket://4521","description":"The raw text of the ticket being triaged.","mimeType":"text/plain","type":"resource_link"}}

card shape              bytes per message       x20000
--------------------------------------------------------
embedded resource                     244    4,880,000
resource_link                         205    4,100,000
the ask itself                        110    2,200,000
```

Look at the numbers before the conclusion, because they are more honest than the story led you to
expect. **244 against 205.** The link is smaller and it is barely smaller, because this ticket is one
short paragraph and the link's own metadata — name, title, description, MIME type — is nearly as long
as the ticket.

That is the finding, and it is the opposite of the intuition. The link wins on size only when the
document is large. For a two-line ticket, embedding costs almost nothing extra and removes an entire
round trip and an entire way for the host to end up with nothing.

So the choice is **not** primarily about bytes. It is about who decides and when the content was
true:

- Embed when the document is small, you know the host needs it, and you would rather it arrived than
  arrived correctly. A frozen copy of a two-line ticket is fine.
- Link when the document is large, when the host may not need it, or when it changes and the host
  should see the current version rather than the one you rendered from.

## When it breaks

The break is a link nobody follows.

You publish a card whose only substance is a `resource_link`. A host that reads resources renders it,
fetches the ticket, and everything works beautifully in your test. A host that does not — and there are
many, because tools were the first thing everyone implemented — passes the message to the model with a
URI in it and no content. The model sees `ticket://4521` and has no idea what is in it, so it does the
thing models do with a name they cannot resolve: it reasons about the name.

```text
"Ticket 4521 appears to be a routine support request. Based on the ticket number..."
```

That paragraph is generated from a URI. There is no error, no empty result, and no signal anywhere
that the ticket text never arrived.

The second break is an embedded resource that has gone stale. The card was rendered at ten past nine.
The customer added *"it also happens on my phone"* at half past. The model reads a ticket that is
correct and out of date, and the version it read is the one you froze, which is a fact recorded nowhere
in the message.

The third break is the one with a real error, and it is the client's:

```text
AttributeError: 'EmbeddedResource' object has no attribute 'text'
```

Captured on 2026-09-04. The text is one level deeper — `content.resource.text` — and a client written
for `TextContent` walks into it the first time a card embeds anything.

The smallest fix for all three is on the reading side: match on `content.type` explicitly and have a
branch for every shape, including a logged `else`. The specification's five types are a closed list,
and a client that handles two of them is a client that will one day be handed a third.

## In production

**What a professional writes instead:** links for anything that could be large or could change, and
embeds for small fixed reference material — a policy paragraph, a style example. The choice is written
down beside the card, because it is not recoverable from the code: both shapes are three lines and
neither one looks like a decision.

**What degrades at scale:** embedding turns your prompt render into a data fetch. A card that embeds
the ticket now reads the ticket store on every `prompts/get`, which means the prompt surface inherits
the resource surface's load, its latency and its failure modes — and a `prompts/get` that fails because
a database was slow is a failure in a place nobody was watching.

**The failure mode that only appears with real traffic:** links to resources the caller may not read.
Your server renders the card, so it decides what to link. Whether the caller is *allowed* to read
`ticket://4521` is checked later, on the read, by different code. Under real authorisation those two
answers can differ, and the symptom is a card full of links that all return errors — which looks like a
broken server and is a permissions bug.

**The review comment a senior engineer leaves:** *"the card embeds the full ticket body. That is a
one-paragraph ticket today and an email thread with four replies in it next quarter, and every render
will carry all of it into a host whose context budget we cannot see. Link it, and put the ticket title
in a text message so the model knows what it is being offered."*

**The interview question:** *"When would you embed a resource in a prompt instead of linking to it?"*
The honest answer: *"when it is small, when I know the host will need it, and when a frozen copy is
acceptable. Linking is better for anything large or anything that changes, because the host reads the
current version and can decide not to read it at all. The trap with links is that resource reading is
optional for a host — a client that only implements tools gets a message containing a URI and no
content, and the model then reasons about a filename with nothing behind it. There is no error for
that, so I would not build a card whose only substance is a link unless I knew who was calling."*
