# 5.2 — 💥 The header that lied

## One-line answer

Forge `Mcp-Name` so the header says one tool and the body says another, and you discover what the
`-32020` rule is actually defending: a gateway that has already allowed, counted and routed a request
that the server is about to execute as something else entirely.

## The story

You sign the visitor register at the office gate. Name, whom you are meeting, floor, time in.

You write *"4th floor, accounts"*, because that is where you were told to go. The guard reads the
line, hands you a pass with a green sticker, and waves you through the turnstile that serves floors
three to five. He does not walk you up. He has forty people to sign in and one register.

Inside, you take the lift to the second floor instead, where the server room is, because that is
actually where you were going.

Nothing at the gate malfunctioned. The register is accurate — it accurately records what you wrote.
The green sticker is a real sticker, correctly issued according to the line you filled in. The guard
did his job exactly as designed. And the day somebody asks *"who was on the second floor on Tuesday
afternoon?"*, the register answers *"nobody"*, confidently, in your handwriting.

The failure is not that the guard was fooled. It is that two things were separated: the thing that was
checked, and the thing that happened.

## The idea in plain language

[3.2](../03-headers-and-caches/3.2-the-header-that-must-match.md) stated the rule — a server that
processes the body **MUST** reject a request whose headers disagree with it, with HTTP `400` and
JSON-RPC `-32020 HeaderMismatch`. This part is where you break it on purpose and look at what is
underneath.

The setup has three parties and it is the ordinary production shape, not a contrived one:

| Party | Reads | Acts on |
| --- | --- | --- |
| gateway | `Mcp-Method`, `Mcp-Name` | routing, rate limiting, authorisation, metrics |
| server | the JSON body | `params.name`, `params.arguments` |
| you | both | the discrepancy |

A forged header does not attack the server. The server is going to run whatever the body says, which
is what it would have done anyway. **The forgery attacks everything in front of the server.** Consider
what a gateway typically has been configured to do with `Mcp-Name`:

- allow `lookup_ticket` for everybody and require an extra scope for `close_ticket`;
- rate limit `search_kb` to protect the index behind it;
- send `tools/call` for one expensive tool to a bigger instance pool;
- record per-tool call counts that somebody bills against or alerts on.

Now send `Mcp-Name: lookup_ticket` with a body that calls `close_ticket`. Every one of those four
decisions is made about a request that never happens, and the request that *does* happen is the one
that needed the extra scope.

The specification names this directly as the reason the rule exists — *"different components in the
network rely on different sources of truth"* — and the important consequence is which component is
required to fix it. Not the gateway. The gateway cannot fix it: it has deliberately not parsed the
body, and parsing the body is the cost the headers exist to avoid. **The server is the only party that
sees both, so the server is where the check has to live.** That is the end-to-end argument again,
taught on Day 21 and applied here without ceremony: put the check at the layer with enough knowledge
to complete it.

## Why Sutra needs it

Because Day 34 writes `sutra_mcp`, and this check is the single easiest thing in the whole protocol to
leave out.

Leaving it out is invisible. Every conforming client sends matching headers, so the server behaves
identically with and without the check, forever — until the day it sits behind a gateway that somebody
else configured. The test suite cannot notice an absent check that nothing exercises, which is exactly
why breaking it on purpose is a part of this day rather than a line in a checklist.

There is a second reason, and it is about Sutra's own future gate. Day 40 builds tool filtering and an
allowlist on Sutra's **client** side. Day 43 deploys `sutra_mcp` behind an edge. The moment both exist,
Sutra is running the three-party shape in this part, with itself in two of the roles. A Sutra server
that skips header validation would be undermining a Sutra gateway.

## The mechanism

> 🎬 **The scene:** the gateway in front of `sutra-mcp` has one rule that everybody agreed was
> sensible — `close_ticket` requires an elevated scope, everything else is open to the desk agents.
> It is three lines of gateway configuration, matching on `Mcp-Name`, and it has been there since the
> service launched.
>
> 😬 **The naive fix:** when a client reports that its header library lower-cases header values and
> nothing works, somebody makes the server compare case-insensitively. While they are in there they
> notice the mismatch branch is *"a bit strict"* and change it to log a warning and carry on, because
> the body is what gets executed anyway and rejecting valid work over a header seemed unhelpful.
>
> 💥 **Why it fails:** the gateway is now the only thing enforcing a rule, on a value nobody
> validates. A request with `Mcp-Name: lookup_ticket` and a body calling `close_ticket` sails through
> the open lane and closes a ticket. The access log says `lookup_ticket`. The metrics say
> `lookup_ticket`. The one place that knows what really happened is the server's own application log,
> and nobody correlates that with the gateway's, because until today they always agreed.
>
> 💡 **The insight:** a check that never fires still has a job. It is what makes another component's
> data trustworthy, and removing it moves a security property out of the system without changing any
> behaviour you can observe.

Forge it and watch the two outcomes:

```python
# days/day-32-mcp-stateless-core/lab/forge.py
"""Forge the header, then validate against the body it does not match. Run from inside lab/."""

from headers import CALL, derive, validate

honest = derive(CALL)
forged = honest | {"Mcp-Name": "search_kb"}

print(f"body executes : {CALL['params']['name']}")
print(f"gateway sees  : {forged['Mcp-Name']}")
print(f"strict server : {validate(forged, CALL)}")
print(f"lenient server: executes {CALL['params']['name']} and says nothing")
```

**Line by line:**

- `from headers import ...` imports the validator built in
  [3.2](../03-headers-and-caches/3.2-the-header-that-must-match.md) rather than reimplementing it, so
  the thing being attacked is the thing you wrote. Run this from inside `lab/` so the bare import
  resolves.
- `honest | {"Mcp-Name": "search_kb"}` builds the forgery by **overriding one key** on a correct set of
  headers. That is the honest depiction of the attack: everything else about the request is valid, and
  a gateway inspecting anything other than that one value sees nothing wrong.
- `search_kb` is used here rather than `close_ticket` because `close_ticket` does not exist yet in
  Sutra — inventing a tool to make the demo scarier would be inventing a result. The mechanism is
  identical and the two names differ only in what a policy would say about them.
- The four prints are deliberately parallel: what runs, what is policed, what a correct server does,
  what an incorrect one does. The gap between line two and line one is the whole vulnerability, and it
  is one line of output wide.
- **Zero model calls, no network, no server.** Two dicts and a comparison.

Run it from inside the lab folder:

```bash
cd days/day-32-mcp-stateless-core/lab
uv run python forge.py
```

**Line by line:**

- `cd` first, because `forge.py` imports `headers` by bare name — the same arrangement the paper demo
  uses, and the reason both live beside the module they import.
- **Zero generations, no network.**

Measured on 2026-09-04:

```text
body executes : lookup_ticket
gateway sees  : search_kb
strict server : {'jsonrpc': '2.0', 'id': 1, 'error': {'code': -32020, 'message': "Header mismatch: Mcp-Name header value 'search_kb' does not match body value 'lookup_ticket'"}}
lenient server: executes lookup_ticket and says nothing
```

A `-32020` and nothing runs. Now perform the ablation, which is the point of a failure lab: open
`headers.py`, change `validate` to `return None` unconditionally, and run `forge.py` again.

```text
strict server : None
```

`None` means *proceed*. The server will execute `lookup_ticket`. The gateway already counted a
`search_kb` against the search index's rate limit, and if the rule had been an authorisation rule
instead of a rate limit, it would already have applied the wrong one. **Put the check back.**

## When it breaks

The break to plan for is not the deliberate forgery. It is the accidental one, and it looks identical
on the wire.

A client that sets headers from a template while building the body from a loop will eventually reuse
a header from the previous request. A retry that rebuilds the body but reuses a cached header object
does the same. Both produce exactly the error above, from a client whose author is certain the values
match:

```text
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32020, "message": "Header mismatch: Mcp-Name header value 'search_kb' does not match body value 'lookup_ticket'"}}
```

Read that message as a **stale-copy** report rather than an attack report, and the bug is usually one
scope up from where you are looking: somewhere a header outlived the body it was derived from. The
fix is the discipline from [3.1](../03-headers-and-caches/3.1-the-label-on-the-envelope.md) — derive
the headers from the body at the moment of sending, and remove the parameter that lets a caller set
them.

The second break is a proxy that rewrites rather than forwards. The client was correct, the server is
correct, and something in between changed a value; you cannot tell from either end. An echo endpoint
that returns the headers as received settles it in one request, and it is worth having before you
need it.

## In production

**What a professional writes instead:** validation as middleware at the very edge of the server
process, running before any routing, with a metric on the rejection count. Not a check inside a
handler, because the next handler will not have it.

**What changes at scale:** the `-32020` rate becomes a signal with two distinct shapes, and they are
worth alerting on separately. A step change at a deploy time, all from one `clientInfo` value, is a
broken client release. A low, steady trickle spread across clients and tool names is somebody probing
whether your headers and bodies are checked against each other — which is a reconnaissance step, not
an outage, and the only place it is ever visible is this counter.

**The failure mode that only appears with real traffic:** validating some headers and not others.
`Mcp-Method` and `Mcp-Name` get checked because they are the ones the documentation talks about, and
`MCP-Protocol-Version` is skipped because the version is already validated elsewhere. Now a request can
claim an old revision in the header — where the gateway reads it, and where, per the specification's
own guidance, an old revision means *these headers are not validated, do not trust them* — while the
body says otherwise. The gateway's compatibility rule is being fed the one value nobody checked.

**The review comment a senior engineer leaves:** *"you removed the header check because a client was
sending mismatched values. That client is broken — fix the client. The check is what makes the
gateway's `Mcp-Name` rules mean anything, and if it is off, our `close_ticket` scope rule is decorative
and the access log is fiction."*

**The interview question:** *"MCP mirrors the tool name into an HTTP header. What stops a client from
lying about it?"* The answer that shows you have thought about the shape: *"the server must reject a
mismatch with 400 and `-32020`. It has to be the server, because it is the only party that sees both
the header and the body — the gateway deliberately never parses the body, which is the entire point of
having the header. And the reason it matters is that the forgery does not attack the server at all: it
attacks whatever is in front of it. The gateway routes, rate limits and authorises on a value the
server then ignores, so every decision it made was about a request that did not happen — and its access
log will say so."*
