# 5.1 — 💥 The tutorial from four months ago

## One-line answer

The date on a document is part of the document — and this is not only true of blog posts: the `mcp`
SDK pinned in this repository reports `LATEST_PROTOCOL_VERSION = '2025-11-25'`, so the library Sutra
will install on Day 34 cannot speak the revision this whole phase is built on.

## The story

The washing machine stops mid-cycle with water in the drum and three lights blinking.

You find the model number on the sticker inside the door, search for it, and download a service
manual. It is the right brand and the right model. Step four says *"hold the START and SPIN buttons
together for five seconds to drain."*

Your machine has no SPIN button.

You look again at the manual, then at the panel, then at the manual. Same model number. Same picture
on the front page, near enough. Right at the bottom of the last page, in grey, there is a revision
code and a date — and the date is from before the panel was redesigned.

Nothing in the manual was wrong when it was written. Everybody who wrote it was competent. The one
piece of information that would have saved the afternoon was printed in grey at the bottom of the
last page, and you did not read it first because manuals are not usually the thing that is out of
date.

## The idea in plain language

Everything in the day so far was learned from the specification. The specification is dated. But most
of what anybody reads about a protocol is *not* the specification — it is a blog post, a Stack Overflow
answer, a code sample in somebody's repository, a generated tutorial. Those carry dates too, in grey,
at the bottom.

MCP changed on 2026-07-28 in a way that invalidates the opening of every earlier tutorial. Anything
written before that date starts with `initialize`, stores a session identifier, and re-sends it on
every request. It is correct material for a revision that still exists, and following it now means
building machinery the protocol removed.

This is the same trap as ADK 1.x patterns, which the plan names as a trap you can walk into by reading
good material ([Day 5's](../../../day-05-first-adk-agent/LESSON.md) subject). It is worse here for one
reason: the ADK traps have been around long enough that most search results are 2.x. MCP's revision is
recent, so the *majority* of what you will find is the old era, and it looks confident.

And then the sharper version of the lesson, which is the reason this part is in the failure lab rather
than in a footnote: **the SDK is a document too.** A library has an implicit date — the revision it was
written against — and pinning a version pins that date. You cannot see it in `pyproject.toml`. You have
to ask the library.

## Why Sutra needs it

Because Sutra has `mcp==1.29.1` pinned right now, and Day 34 is going to import it.

`docs/PACKAGES.md` records the pin. Nothing in the pin says which protocol revision it implements, and
nothing in `uv sync` will warn you. A learner who reads this day, understands the stateless core
perfectly, and then writes a server with the pinned SDK will produce a `2025-11-25` server — correct
code, correct library, wrong era — and the mismatch will not surface until something tries to speak
2026-07-28 to it.

That is a fact about this repository on this date, and the measurement is in the mechanism below. It
is exactly the kind of thing Principle 14 exists for: reality moved, so it gets recorded and reported
before code is written on top of it, rather than discovered halfway through Day 34.

The reading habit this part installs is also what protects every remaining day of the phase. Days 33
to 45 all involve reading somebody else's material about MCP. The first question about each is not
*"is this good?"* — most of it is good — but *"which revision was this written against?"*

## The mechanism

> 🎬 **The scene:** it is the evening before Day 34 and you want a head start, so you search for
> *"python mcp server tutorial"*. The top results are detailed and well written. Each one opens with a
> handshake: the client sends `initialize`, waits for `notifications/initialized`, and stores the
> session identifier for every later call.
>
> 😬 **The naive fix:** follow the best one. It has thousands of upvotes, the code runs, and the author
> clearly knows the subject.
>
> 💥 **Why it fails:** you would be hand-building the machinery the protocol deleted. Against a modern
> client your server waits for an `initialize` that never arrives. Against a modern server your client
> waits for a handshake nobody answers. And the failure is quiet — no exception says *"you are in the
> wrong era"*, because both sides are speaking a real version of a protocol with the same name.
>
> 💡 **The insight:** the date on a document is part of the document, and a library has a date too.
> Ask the library which revision it speaks before you write a line against it.

Asking is six lines:

```python
# days/day-32-mcp-stateless-core/lab/sdk_era.py
from mcp.shared.version import SUPPORTED_PROTOCOL_VERSIONS
from mcp.types import DEFAULT_NEGOTIATED_VERSION, LATEST_PROTOCOL_VERSION

SPEC_REVISION = "2026-07-28"  # read off modelcontextprotocol.io/specification on 2026-09-04

print(f"specification says current : {SPEC_REVISION}")
print(f"mcp SDK LATEST_PROTOCOL_VERSION : {LATEST_PROTOCOL_VERSION}")
print(f"mcp SDK DEFAULT_NEGOTIATED_VERSION : {DEFAULT_NEGOTIATED_VERSION}")
print(f"mcp SDK SUPPORTED_PROTOCOL_VERSIONS : {SUPPORTED_PROTOCOL_VERSIONS}")
print(f"SDK speaks the current revision : {SPEC_REVISION in SUPPORTED_PROTOCOL_VERSIONS}")
```

**Line by line:**

- The two imports come from the **installed package**, not from documentation. That is the whole method:
  the authoritative answer to *what does this library do* is the library, and it is faster to read than
  a changelog.
- `SPEC_REVISION` is a literal with the date it was checked in a comment beside it. A constant with no
  provenance is a fact somebody remembered; a constant with a source and a date is a fact somebody
  verified, and the next reader can re-check it in one action.
- `LATEST_PROTOCOL_VERSION` is what the SDK considers newest. `DEFAULT_NEGOTIATED_VERSION` is what it
  assumes when a client sends no version at all, which is a backwards-compatibility fallback and is
  therefore *older still* — two different numbers that both matter and are easy to confuse.
- `SUPPORTED_PROTOCOL_VERSIONS` is the list, and the list is the answer. A library can support several
  eras at once, so a single "latest" value would under-report what it can talk to.
- The last line reduces all of it to one boolean, because a boolean is what you can put in a test.
  Day 34 should have a test that asserts this, and it should be allowed to go red.
- **Zero model calls, no network, no server.** It reads constants.

Run it:

```bash
uv run python days/day-32-mcp-stateless-core/lab/sdk_era.py
```

**Line by line:**

- From the repository root, against whatever `uv sync` installed. **Zero generations.**

Measured on 2026-09-04, against `mcp==1.29.1` as pinned in `pyproject.toml`:

```text
specification says current : 2026-07-28
mcp SDK LATEST_PROTOCOL_VERSION : 2025-11-25
mcp SDK DEFAULT_NEGOTIATED_VERSION : 2025-03-26
mcp SDK SUPPORTED_PROTOCOL_VERSIONS : ['2024-11-05', '2025-03-26', '2025-06-18', '2025-11-25']
SDK speaks the current revision : False
handshake type still exported : InitializeRequest
```

**`SDK speaks the current revision : False`.** The pinned library's newest revision is the one before
the one this day teaches, and `InitializeRequest` — the handshake type — is still exported, because for
`2025-11-25` it is still correct.

This is not a defect in the library. A specification and its implementations are separate artefacts on
separate release cycles, which is visible in
[4.1](../04-governance-and-registry/4.1-a-standard-nobody-owns.md)'s governance diagram. It is a fact
about **this repository, on this date**, and it has to be recorded rather than assumed away.

Two lookups, run the same day, complete the picture:

```bash
curl -s https://pypi.org/pypi/mcp/json | uv run python -c "import sys,json;print(json.load(sys.stdin)['info']['version'])"
curl -s https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v2.1.1/src/mcp-types/mcp_types/version.py | grep -A1 "^MODERN_PROTOCOL_VERSIONS"
```

**Line by line:**

- The first asks PyPI what the newest published `mcp` is, reading `info.version` out of the JSON API.
  This is the exact command the house rules require instead of remembering a version number.
- The second reads the protocol-version constants straight out of that release's source on GitHub,
  because *"a newer version exists"* and *"a newer version speaks the revision I need"* are different
  questions and only the second one matters.
- `grep -A1` prints the constant and the docstring line under it, which is where the SDK says in its
  own words what the tuple means.
- Both are read-only HTTPS GETs. **Zero generations, nothing installed.**

Output, 2026-09-04:

```text
2.1.1
MODERN_PROTOCOL_VERSIONS: Final[tuple[str, ...]] = ("2026-07-28",)
"""Protocol revisions that use the stateless per-request envelope."""
```

So the SDK ecosystem has caught up — `mcp` 2.1.1 speaks `2026-07-28` and even names the concept
*"stateless per-request envelope"* — and **this repository is pinned to 1.29.1, which does not.**
Today changes nothing: no package is added or upgraded on Day 32, because a version bump is a plan
decision with a `docs/PACKAGES.md` row and a `CHANGELOG_PLAN.md` entry behind it, not a side effect of
a reading day. What today does is put the number in front of you before Day 34 depends on it.

## When it breaks

Two ways, and the second is the one that costs an evening.

**A modern client against an old-era server.** The server is waiting for `initialize` and gets
`tools/call`. Under the pre-2026 revisions the correct answer is a JSON-RPC error saying the request
came too early:

```text
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32600, "message": "Received request before initialization was complete"}}
```

That one is survivable because it says what is wrong. The specification's fallback rule
([2.1](../02-the-reframe/2.1-the-call-that-remembered-you.md)) reads the body, sees an error that is
not a recognised modern one, and falls back to `initialize`.

**An old-era client against a modern server, over stdio.** There are no status codes on a pipe. The
client writes `initialize` and waits. A modern server has no such method, so it answers with a
method-not-found error — and an old client that was written to expect an `InitializeResult` may not
handle an error in that position at all. The visible symptom is that nothing happens:

```text
$ uv run python client.py
(no output; the process does not exit)
```

That is the worst failure shape available: no exception, no log, no traceback to search for. This is
exactly why `server/discover` exists as the stdio probe
([2.4](../02-the-reframe/2.4-server-discover-the-optional-question.md)) and why the era question has to
be settled before the connection, not during it.

The smallest fix for both is the same and it is a habit rather than code: **before writing anything
against a protocol library, print the versions it supports.** Six lines, once, at the top of the day.

## In production

**What a professional writes instead:** a test. Not a comment, not a note in the design document — an
assertion that the SDK's supported versions contain the revision the system targets, so the day
somebody bumps the pin the suite says whether the era changed. Sutra's version of that belongs in
`tests/` on Day 34, and it must be able to go red today.

**What changes at scale:** era skew becomes a fleet property. Different services pin different SDK
versions, so *"which revision do we speak?"* stops having one answer, and a gateway in the middle sees
both eras at once — which the specification anticipates with its compatibility rules, and which nobody
enjoys operating. The organisations that handle it well are the ones that record the targeted revision
per service somewhere a person can query.

**The failure mode that only appears with real traffic:** the partial upgrade. An SDK bump that
supports both eras will negotiate the new one with servers that offer it and the old one with servers
that do not, and the resulting behaviour differs per server. A bug that reproduces against one server
and not another, with the same client code, is an era difference until proven otherwise.

**The review comment a senior engineer leaves:** *"the design document says we implement MCP. Which
revision? And does the SDK version in `pyproject.toml` actually support it? Print
`SUPPORTED_PROTOCOL_VERSIONS` and paste the output in the pull request — I have been bitten by that
gap twice this year."*

**The interview question:** *"how do you keep up with a protocol that is changing quickly?"* An answer
with a war story in it: *"you read the specification's own versioning page first and treat the revision
like a pinned dependency — ours is 2026-07-28, checked on the day we wrote the design. Then you check
your library separately, because they move independently. We did that and found our pinned SDK topped
out at the previous revision while the current release already spoke the new one. Nothing was broken
yet, and it would have been the day we wrote a server against it. The habit is: the date on a document
is part of the document, and a library is a document."*
