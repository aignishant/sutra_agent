# 4.2 — The registry, queried live

## One-line answer

There is one official catalogue of public MCP servers, it is a plain REST API at
`registry.modelcontextprotocol.io/v0/servers` needing no key, and it holds **metadata about where a
server lives** rather than the server's code — which is why what it does and does not check is the
part to learn.

## The story

The gas connection needs transferring and you do not know who to call.

There is a number written in marker on the wall by the stairwell — somebody's uncle, apparently, very
reliable. There is also a printed sheet pinned inside the municipal office listing the registered gas
agencies for this ward, with addresses and licence numbers.

The sheet is not a recommendation. It does not say which agency is good, which one answers the phone,
or which one overcharges. Two of the names on it are, by common agreement, useless. What the sheet
does say is that each of these agencies proved, to somebody, that they are who they say they are and
that they are permitted to do this work.

The number on the wall proves nothing at all, and the uncle may well be excellent.

Most people use the sheet anyway, and they are right to, because the sheet answers a question the wall
cannot answer at all: *if this goes wrong, is there anybody I can identify?*

## The idea in plain language

A protocol makes servers interoperable. It does not make them **findable**. Once anybody can write an
MCP server, the practical question becomes *which ones exist, and where do I get them?*

The official answer is the **MCP Registry**, and the project describes it plainly
(`https://modelcontextprotocol.io/registry`, read 2026-09-04):

> *"The MCP Registry is the official centralized metadata repository for publicly accessible MCP
> servers"*

Four things it holds, and one it does not:

| It holds | It does not hold |
| --- | --- |
| a server's unique name | the server's code |
| where to get it — an npm or PyPI package, or a remote URL | a rating or a review |
| how to run it — arguments, environment variables | a security audit |
| description and discovery data | any opinion about quality |

The distinction between a **package registry** and this one is the thing to get straight. npm, PyPI
and Docker Hub host the code. The MCP Registry hosts *metadata that points at* that code. It is a
sheet of addresses, not a warehouse.

Three properties matter for how you use it.

**It is a plain REST API and it needs no key.** `GET /v0/servers` returns JSON. That is a deliberate
choice: discovery has to be available to a client at runtime, and anything requiring credentials would
not be.

**It is explicitly in preview.** The page says so: *"The MCP Registry is currently in preview.
Breaking changes or data resets may occur before general availability."* The `/v0` in the path is not
decoration.

**It is not meant to be consumed directly by host applications.** The project expects **downstream
aggregators** — marketplaces, curated catalogues — to pull from it and add the opinions it refuses to
hold. The registry deliberately publishes *"deliberately unopinionated"* metadata and leaves curation
to others.

And the security posture is stated rather than implied: the registry *"delegates security scanning"* to
the underlying package registries and to downstream aggregators, and focuses on **namespace
authentication** and metadata hosting. That is a narrow, honest promise, and
[4.3](4.3-a-name-that-proves-its-publisher.md) is about exactly what it buys.

## The mechanism

One HTTPS GET, no key, and a little bit of care about failing loudly:

```python
# days/day-32-mcp-stateless-core/lab/registry.py  (extract)
URL = "https://registry.modelcontextprotocol.io/v0/servers?limit=5"


def fetch(url: str) -> dict:
    """GET the registry, and fail loudly rather than returning an empty list (Principle 10)."""
    request = urllib.request.Request(url, headers={"Accept": "application/json"})
    try:
        with urllib.request.urlopen(request, timeout=15) as response:
            return json.loads(response.read())
    except urllib.error.HTTPError as failure:
        raise SystemExit(
            f"registry returned HTTP {failure.code}: {failure.read()[:200]!r}"
        ) from failure
    except urllib.error.URLError as failure:
        raise SystemExit(f"registry unreachable: {failure.reason}") from failure


def namespace(name: str) -> str:
    """Everything before the first slash - the part a publisher had to prove they control."""
    return name.split("/", 1)[0]
```

**Line by line:**

- `urllib.request` from the standard library, not an HTTP package. Sutra has not added one and this
  day does not justify one — a dependency to save ten lines is the anti-pattern the house rules name
  outright.
- `?limit=5` because the registry paginates and the full list is long. The response carries a
  `nextCursor` for the rest; asking for everything at once would be a different program.
- `Accept: application/json` is polite rather than required, and it is the header that makes the
  intent readable to whoever debugs this from a proxy log.
- `timeout=15` because `urlopen` has **no default timeout** and will otherwise hang forever on a
  network that is up but not answering. A script that hangs is worse than one that fails, because
  nobody knows which state it is in.
- The two `except` clauses distinguish *the registry answered, badly* from *the registry did not
  answer*, and both `raise SystemExit` rather than returning an empty list. Returning `[]` here would
  make "the registry is down" indistinguishable from "there are no servers", which is Principle 10
  exactly: never fabricate a result to cover an error.
- `failure.read()[:200]` includes the beginning of the error body, because an HTTP status alone rarely
  says what was wrong with the request.
- `from failure` preserves the original exception as the cause, so the traceback still names the socket
  error underneath.
- `namespace` splits on the **first** slash only. Everything before it is the part
  [4.3](4.3-a-name-that-proves-its-publisher.md) is about; everything after is the publisher's own
  naming and may contain more slashes.
- **Zero model calls.** One HTTPS GET to a public endpoint.

Run it:

```bash
uv run python days/day-32-mcp-stateless-core/lab/registry.py
```

**Line by line:**

- From the repository root. Needs the network and nothing else — no key, **zero generations**.

```text
      version   : 0.3.0   status: active
      published : 2026-04-02   latest: False
      remotes   : ['https://tandem.ac/mcp']
```

Three observations that are only visible in a real response.

**The same server appears more than once.** `ac.inference.sh/mcp` is listed at `1.0.0` and `1.0.1`, and
in the full run at `2.0.0` and `2.0.1` as well. The registry keeps **versions**, not just servers, and
each row carries `isLatest`. A client that lists five entries and reports "five servers" has miscounted
by four.

**Entries are ordered by name, not by relevance.** These are the alphabetical beginning of the
catalogue, which is a reminder that the registry has no ranking to offer — that is the aggregator's
job, and its absence here is the design working as intended.

**`remotes` changes between versions.** Version `1.0.0` lists two URLs and `2.0.1` lists one. That is a
real deployment detail that a pinned name would hide, and it is why the audit records the version you
actually used rather than the name.

## When it breaks

The break is the network, and the way it breaks tells you which failure you have. Both of these were
produced on 2026-09-04 by editing one string in the script and running it.

Point it at a host that does not exist, and nothing is contacted at all:

```text
registry unreachable: [Errno 11001] getaddrinfo failed
```

That is DNS. `11001` is the Windows resolver's *host not found*, and the important word is
*unreachable* — no request was ever sent, so nothing about the registry is implicated. A corporate
proxy that refuses the connection lands in the same branch with a different reason.

Now misspell the path and the registry itself answers:

```text
registry returned HTTP 404: b'{"detail":"Endpoint not found. See /docs for the API documentation.","status":404,"title":"Not Found"}'
```

Two failures, two different fixes: one is your network, the other is your URL. The reason the script
separates them is that the separation *is* the diagnosis. A version of `fetch` that caught `Exception`
and returned `{}` would have printed *"0 entries"* for both, and you would have gone looking for a bug
in the registry.

The second break is treating a registry listing as a security review. It is not one and does not claim
to be — the project delegates scanning to the package registries and to downstream aggregators. A
malicious server can be published under a correctly verified namespace, and it will appear in this
list looking exactly as legitimate as anything else. What the listing proves is covered in
[4.3](4.3-a-name-that-proves-its-publisher.md), and it is narrower than most people assume.

## In production

**What a professional writes instead:** nobody queries the registry from the agent's hot path. It is a
build-time or review-time tool — you find a server, you evaluate it, you pin it in configuration with a
version, and the running system connects to what configuration says. Runtime discovery of arbitrary
servers is a supply-chain decision made by a machine, and Day 40's allowlist exists to stop it.

**What changes at scale:** the registry becomes an input to procurement rather than to code. An
organisation mirrors it, filters it against an internal allowlist, and publishes the filtered view as
its own private registry — which the project explicitly anticipates by defining an OpenAPI interface
other registries can implement.

**The failure mode that only appears with real traffic:** silent version drift. A server referenced by
name resolves to whatever `isLatest` points at today, and a server whose `remotes` list changed between
versions is now a different endpoint than the one you evaluated. The fix is boring and it is the same
fix as for packages: pin the version, record it, and re-evaluate deliberately.

**The review comment a senior engineer leaves:** *"this fetches the registry at startup and connects to
whatever it finds. Pin it. The registry is in preview, it can data-reset, and 'whatever the catalogue
says today' is not a dependency we can reproduce in six months."*

**The interview question:** *"how do you find MCP servers, and what does being in the official registry
prove?"* The honest answer draws the line: *"there is an official registry — a plain REST API, no key —
and it holds metadata pointing at packages or remote URLs rather than code. What it proves is
namespace ownership: the publisher verified control of a domain or a GitHub account. What it does not
prove is that the server is safe, maintained or good — the project says outright that it delegates
security scanning to the package registries and to downstream aggregators. So we use it to find
candidates and to fill in the provenance row, then we pin a version and review the server ourselves."*
