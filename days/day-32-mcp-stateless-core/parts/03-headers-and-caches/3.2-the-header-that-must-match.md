# 3.2 — The header that must match

## One-line answer

A server that reads the body **MUST** reject any request whose headers disagree with it — HTTP
`400 Bad Request` and JSON-RPC error `-32020 HeaderMismatch` — because a router deciding on one value
while the server executes another is a security hole, not an inconsistency.

## The story

The pharmacist turns the box over, opens it, reads the leaflet inside, and puts the box back on the
counter.

The box says one strength. The leaflet inside says another. Both are printed by the same company, both
look official, and the difference is small enough that you would not have noticed. She will not sell
it to you, and she will not decide which of the two is right, and she will not sell you the one she
thinks is probably correct.

That refusal is the only safe move available to her. If she trusts the box, you may take a dose that
matches the leaflet. If she trusts the leaflet, you may take a dose the box's label prepared you for.
Either way, somebody downstream — you — acts on the *other* number.

The mismatch does not tell her which one is wrong. It tells her that something upstream is broken,
and that anything she does other than refuse will push the problem onto the person least able to
catch it.

## The idea in plain language

[3.1](3.1-the-label-on-the-envelope.md) copied two values from the body onto the outside of the
request. Copying creates a new failure mode that did not exist before: the copy and the original can
differ.

Who reads which:

- The **intermediary** reads the headers. It routes, rate limits, authorises and logs on them, and it
  never opens the body.
- The **server** reads the body. It executes `params.name` with `params.arguments`.

So if the header says `Mcp-Name: search_kb` and the body says `"name": "lookup_ticket"`, the gateway
applies the search pool's rules and the server runs the ticket lookup. Every policy the gateway
applied was applied to a request that did not happen.

That is not a bug in one component. It is what the specification calls out as the reason the rule
exists at all
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http`, read
2026-09-04):

> *"Servers that process the request body **MUST** reject requests where the values specified in the
> headers do not match the corresponding values in the request body. This prevents potential security
> vulnerabilities when different components in the network rely on different sources of truth (e.g., a
> load balancer routing on the header value while the MCP server executes based on the body value)."*

The rejection is exact: HTTP `400 Bad Request`, and a JSON-RPC error with code **`-32020`**, named
`HeaderMismatch`. Three conditions trigger it:

| Condition | Example |
| --- | --- |
| a required standard header is missing | no `Mcp-Method` at all |
| a header value does not match the body | `Mcp-Name: search_kb` over a body naming `lookup_ticket` |
| a header value contains invalid characters | a raw newline in a tool name |

Two details that catch people out.

**Header names are case-insensitive; header values are not.** `mcp-method` and `Mcp-Method` are the
same header. `Tools/Call` and `tools/call` are different values, and only one of them matches.

**A non-ASCII name is Base64-encoded, and the server must decode before comparing.** A tool or
resource URI that cannot be written in plain ASCII travels as
`Mcp-Name: =?base64?SGVsbG8sIOS4lueVjA==?=`, with those exact lowercase markers. The comparison
happens after decoding, so a server that compares the raw strings will reject every correctly-encoded
request from a client that had a non-ASCII URI.

`-32020` is worth memorising because it is new. The specification renumbered its own error codes in
this revision, reserving `-32020` to `-32099` for the protocol and leaving `-32000` to `-32019`
implementation-defined. `HeaderMismatch` moved from `-32001` to `-32020`,
`MissingRequiredClientCapability` from `-32003` to `-32021`, and `UnsupportedProtocolVersion` from
`-32004` to `-32022`. An older document quoting `-32001` is not wrong about the concept and is wrong
about the number.

## Why Sutra needs it

Because Day 34's server has to implement the check, and it is the kind of check that is easy to skip
and impossible to notice you skipped.

A server that ignores the headers works perfectly against every well-behaved client. Its tests pass.
Its tools return correct answers. The absence only shows up the day a gateway in front of it is making
decisions on values nobody validates — which is to say, the day it goes to production behind
infrastructure the server author did not configure.

Sutra has met this shape before. On
[Day 27](../../../day-27-authoring-first-skills/parts/03-procedure-and-capability/3.1-a-named-tool-is-a-contract.md)
a skill that named a tool had written a contract that no layer checked, and renaming the Python
function silently removed a step from a procedure. This is the same category of failure with a
security consequence bolted on, and the protocol's answer is better than Sutra's was: **the check is
mandatory and it has a number.**

It also constrains the client. Day 44 hardens Sutra's client, and a client that lets a caller
override a header without changing the body has handed its users a way to produce a `-32020` — or,
against a server that skips the check, a way to lie to a gateway.

## The mechanism

Validation is a comparison, and writing it out shows how small the rule is:

```python
# days/day-32-mcp-stateless-core/lab/headers.py  (extract)
def validate(headers: dict[str, str], body: dict) -> dict | None:
    """What the server checks before executing. None means the request may proceed."""
    lowered = {key.lower(): value for key, value in headers.items()}
    for name, expected in derive(body).items():
        actual = lowered.get(name.lower())
        if actual is None:
            return error(body, f"required header {name} is missing")
        if actual != expected:
            return error(
                body, f"{name} header value {actual!r} does not match body value {expected!r}"
            )
    return None


def error(body: dict, message: str) -> dict:
    """The -32020 HeaderMismatch response, in the shape the transport page prints it."""
    return {
        "jsonrpc": "2.0",
        "id": body.get("id"),
        "error": {"code": -32020, "message": f"Header mismatch: {message}"},
    }
```

**Line by line:**

- `lowered` normalises the **names** and leaves the **values** untouched, which is exactly the
  case-sensitivity rule. Lower-casing the values too would be a one-character change that makes the
  server accept `Tools/Call`, and no test would catch it.
- The loop iterates over `derive(body)` — the headers the body *requires* — rather than over the
  headers that arrived. That direction matters: iterating over what arrived would silently accept a
  request that omits `Mcp-Name`, because a missing key cannot mismatch anything.
- `actual is None` is checked before the comparison and reported differently, because *missing* and
  *wrong* are different bugs in the client even though the protocol gives them one error code. The
  message is what the developer reads at 11pm.
- `return error(...)` on the first problem rather than collecting every problem. A request with two
  bad headers is not more informative than a request with one; it is the same broken client.
- `body.get("id")` rather than `body["id"]`, because a malformed request may have no `id` — and a
  crash while rejecting a bad request is a bad request that took the server with it.
- `return None` for success is deliberate over `return True`: the caller writes
  `if problem := validate(...)`, so the success path has no branch to forget.
- This validator is **not** complete for production: it does not implement the Base64 sentinel
  decoding, and it does not compare integer `Mcp-Param-*` values numerically as the specification
  says it should. Both are named in the hub's build brief as `TODO(me)`.
- **Zero model calls, no network.** It compares strings.


`validate(honest) -> None` is the boring line and it is the one that has to be true first. The other
two are the same error code arriving from two different client mistakes.

## When it breaks

The break that is genuinely hard to find is a **conforming** client behind a **transforming** proxy.

Some proxies rewrite headers. A corporate egress gateway that normalises casing, an observability
sidecar that adds a prefix, a load balancer configured years ago to strip unknown headers — none of
them know what MCP is. The client sent a correct request. The server received an incorrect one. And
the error the developer sees names their own client's header:

```text
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32020, "message": "Header mismatch: required header Mcp-Name is missing"}}
```

The client author reads that, opens their code, finds `Mcp-Name` being set, and loses an evening. The
thing that shortens it is a habit rather than a fix: when a header error contradicts your own source
code, **capture the request as the server saw it** before debugging the client. An echo endpoint that
returns the headers it received is ten lines and it settles the question immediately.

The second break is the tempting shortcut on the server side: *"the header and the body disagree, so
use the body, since that is what we execute anyway."* It is the pharmacist deciding which number is
probably right. It works, it is friendly to sloppy clients, and it silently re-opens the exact hole
the rule exists to close — because the gateway has already applied the header's policy and nobody
downstream will ever learn that it applied it to something else.

## In production

**What a professional writes instead:** validation runs at the edge of the server, before any handler,
and is not something a handler can opt out of. On the client side, headers are derived from the body
at send time ([3.1](3.1-the-label-on-the-envelope.md)) so a mismatch is unrepresentable rather than
merely rejected.

**What changes at scale:** the check becomes an intrusion signal. A well-behaved client never produces
`-32020` after the first day, so a sudden rate of them means either a deployment went out with a
broken client, or somebody is probing your gateway to see whether the header and the body are checked
against each other. Both are worth an alert, and they look different: one starts at a deploy and
affects one `clientInfo` value, the other is low-volume and varied.

**The failure mode that only appears with real traffic:** partial validation. A server validates
`Mcp-Method` and `Mcp-Name` but not `MCP-Protocol-Version`, because the version is also checked
elsewhere. Now a request can claim an old version in the header — where the gateway reads it, and
where, per the specification, an old version means *do not trust these headers* — while the body says
otherwise. The gateway's own compatibility rule is being fed a value nobody validated.

**The review comment a senior engineer leaves:** *"the mismatch branch logs a warning and continues.
Make it return `-32020`. If we execute the body after routing on the header, every policy the gateway
applied was applied to a different request, and we will not be able to tell that from any log we
keep."*

**The interview question:** *"why must an MCP server reject a request whose headers disagree with its
body?"* The answer names the attack: *"because two components would be acting on different values. The
gateway routes, rate limits and authorises on `Mcp-Name`; the server executes `params.name`. If they
differ, everything the gateway decided was decided about a request that never ran. So the server must
return 400 with `-32020 HeaderMismatch` rather than picking a winner — the mismatch does not tell you
which side is wrong, it tells you the request cannot be trusted by anybody."*
