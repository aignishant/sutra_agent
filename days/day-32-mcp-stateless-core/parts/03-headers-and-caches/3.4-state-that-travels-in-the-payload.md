# 3.4 — State that travels in the payload

## One-line answer

Statelessness does not mean a server can never remember anything; it means the memory is **named by an
opaque handle the server mints and the client passes back as an ordinary tool argument**, so the
memory lives in shared storage instead of in one instance's process.

## The story

You hand your bag over at the cloakroom counter and get a small numbered token.

Nobody wrote your name down. The woman behind the counter will not be there when you come back — her
shift ends before the event does — and it does not matter, because the token is not a memory of you.
It is a *pointer to a shelf*. Whoever is on the counter at the end reads the number, walks to that
shelf, and hands you your bag.

The token is deliberately dumb. It does not say what is in the bag, whose it is, or when it arrived.
If you drop it in the street, somebody could collect your bag — which is why the counter is a counter
and not an unattended rack, and why the numbers are not simply 1, 2, 3 in a place where that matters.

What the token buys is that the person and the memory are separated. The bag is on the shelf whether
or not anybody remembers you, and the shelf is reachable by anyone working there.

## The idea in plain language

Section 2 removed sessions. That immediately raises the obvious objection: some work genuinely spans
more than one call. You build up a draft reply over three turns. You start a long re-index and want to
ask about it later. You open a database transaction. What happens to those?

The changelog answers it in one sentence:

> *"Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool
> arguments."*

Four words in that sentence are load-bearing.

**Explicit.** The state has a name that appears in the tool's JSON Schema. A reader of the tool
definition can see that this tool has memory. Under a session, the memory was invisible — it lived in
the protocol, not in the interface.

**Server-minted.** The client does not choose the handle. The server creates it and hands it back, so
the server controls the namespace, the lifetime and the unguessability. A client-chosen key is a
client that can read another client's state by guessing.

**Handle.** An opaque string. *Opaque* means the client must not parse it, derive anything from it, or
construct one — it is a token, not a structure. The moment a client starts reading meaning out of it,
the server can no longer change how it is made.

**Ordinary tool argument.** It travels in `arguments`, alongside the ticket identifier and everything
else. Not in a header, not in `_meta`, not in a session. That is what makes it survive the trip to a
different instance: it is part of the request, and the request is self-contained.

The consequence people miss: **the state does not stop existing, it moves.** It goes from one
instance's process memory into somewhere every instance can reach — a database, a cache, a durable
store. That is not free. You have swapped a dictionary lookup for a network read, and you have
acquired a lifetime problem, because something now has to decide when the row is deleted. A session
had a natural end; a handle does not.

## Why Sutra needs it

Because Sutra will want cross-call memory in Phase 5, twice, and the shape of the answer is decided
here.

**Day 36** is long jobs. A re-index of the ticket archive cannot block a `tools/call` for its whole
duration, so it returns a **task handle** immediately and the client polls `tasks/get` with it. That
is this pattern with a specific name and its own extension.

**Day 37** is elicitation and multi round-trip requests. A server that needs to ask the user something
mid-tool cannot hold the call open waiting; it returns an `InputRequiredResult` with **opaque state**,
the client gathers the answer, and re-issues the original request carrying that state back. Same
shape again: the server's memory of a half-finished operation, carried by the client.

Both of those are on the road ahead, and both are unreadable if the handle idea is not already in
place. It also settles a temptation Day 34 will present. `sutra_mcp` will want a module-level
dictionary — a cache of tickets, a partly-built draft — and that dictionary is a session by another
name. If the state is genuinely needed, it goes behind a handle. If it is only a cache, it must be
rebuildable from the request that reads it, and it must be correct when empty.

## The mechanism

The same cross-call memory, done both ways, against three interchangeable workers:

```python
# days/day-32-mcp-stateless-core/lab/handles.py  (extract)
SHARED_STORE: dict[str, list[str]] = {}


class Worker:
    """One replica. `local` is memory only this replica has; the store is everyone's."""

    def __init__(self, name: str) -> None:
        self.name = name
        self.local: dict[str, list[str]] = {}

    def start_session(self, first: str) -> str:
        """The 2025 shape: the replica remembers, and the client is given a key to its memory."""
        session_id = f"{self.name}-{next(COUNTER)}"
        self.local[session_id] = [first]
        return session_id

    def add_with_session(self, session_id: str, item: str) -> str:
        if session_id not in self.local:
            raise KeyError(f"{self.name} has no session {session_id!r}")
        self.local[session_id].append(item)
        return f"{self.name}: {self.local[session_id]}"

    def mint_handle(self, first: str) -> str:
        """The 2026 shape: the replica writes to shared storage and hands back an opaque string."""
        handle = f"draft-{next(COUNTER)}"
        SHARED_STORE[handle] = [first]
        return handle

    def add_with_handle(self, handle: str, item: str) -> str:
        SHARED_STORE[handle].append(item)
        return f"{self.name}: {SHARED_STORE[handle]}"
```

**Line by line:**

- `SHARED_STORE` is a module-level dict standing in for a database or a cache. In the demo it is a
  dict because the point is *where the state lives*, not what technology holds it. In `sutra_mcp` it
  will be SQLite or Postgres, and the code shape is identical.
- `self.local` versus `SHARED_STORE` is the entire difference between the two eras, expressed as two
  places to put the same list. Everything else in the class is duplicated on purpose so that the two
  paths can be compared line for line.
- `start_session` names the handle after the replica — `i1-1` — which is exactly what a real session
  identifier encodes even when it does not say so. The name is a confession: the memory is *there*,
  not *somewhere*.
- `mint_handle` names it `draft-2` with no replica in it. That is the deliberate contrast: the handle
  says what kind of thing it points at and nothing about who made it, because who made it must not
  matter.
- `raise KeyError` rather than returning an error object, because in this demo the failure should be
  loud and attributable. In `sutra_mcp` this becomes a JSON-RPC error with an unknown-handle message —
  and it is a **404-shaped** error, not a 500: an unknown handle is a client passing something stale,
  not a server fault.
- `add_with_handle` does not check whether the handle exists, and that is a real gap rather than an
  oversight to gloss over. A production handle store needs an expiry, an owner check and a
  not-found path. The hub's build brief asks you to decide all three.
- `next(COUNTER)` uses `itertools.count`, so the two demonstrations cannot accidentally produce the
  same identifier and appear to work for the wrong reason.
- **Zero model calls, no network, no server.** Three objects in one process.

```text
  i1: ['4521', 'note']

  refused: "i3 has no session 'i1-1'"

  i3: ['4521', 'note', 'note', 'note']

```

Three lines of refusal against three lines of accumulation, and the last line is the one to hold on
to: **the client only ever held a string.** It did not hold a connection, it did not have to reach the
same instance twice, and it could have been restarted between any two of those calls.

Where the handle sits in the actual request is the other half of the mechanism, and it is
unremarkable on purpose:

```json
{
  "jsonrpc": "2.0",
  "id": 5,
  "method": "tools/call",
  "params": {
    "name": "append_to_draft",
    "arguments": { "draft": "draft-2", "text": "Sorry about the delay." },
    "_meta": { "io.modelcontextprotocol/protocolVersion": "2026-07-28" }
  }
}
```

`"draft"` is a string argument like any other. It appears in the tool's `inputSchema`, the model sees
it in the tool declaration, and a reviewer reading the tool list can see that this tool has memory —
none of which was true when the memory lived in a session.

## When it breaks

The break is a handle with no expiry, and it does not look like a bug for months.

Every draft ever started, every task ever polled, every half-finished operation stays in the store,
because a session used to be cleaned up when the connection dropped and a handle has no equivalent
event. The table grows. Then one morning:

```text
sqlite3.OperationalError: database or disk is full
```

The failure lands on the store, not on the protocol, and the person paged has no reason to connect it
to a design decision taken in a tool signature. The smallest fix is to write the expiry when you write
the handle — a `created_at`, a rule for how long an unfinished draft is worth keeping, and a job that
deletes.

The second break is guessability. A handle like `draft-2` is fine in a demo and is an access-control
failure in production: any client can ask for `draft-3`. The specification says the handle is
server-minted and opaque; it does not say *unguessable*, because that is your job. A real handle is a
random string long enough not to be enumerated, and the store checks that the caller owns it.

The third break is the client that parses the handle. Somebody notices that `draft-2` contains a
number, sorts by it, and now the server cannot change the format without breaking a client it has
never met. *Opaque* is a promise the client makes, and nothing enforces it — which is exactly the
category of unenforced contract Sutra keeps meeting.

## In production

**What a professional writes instead:** a random handle from `secrets.token_urlsafe`, a row with an
owner and an expiry, an unknown-handle error that is distinct from a server error, and a background
sweep. The handle is short-lived by default and extended deliberately, never the reverse.

**What changes at scale:** the shared store becomes the thing that is actually stateful, and every
property you removed from the server reappears there. It needs backups, it needs to survive a
failover, and it is now the bottleneck three instances contend on. Statelessness did not delete the
state; it moved it somewhere designed to hold state, which is the honest version of the claim and the
one worth saying in a review.

**The failure mode that only appears with real traffic:** the store's latency joins every request.
A handle read on the hot path adds a round trip to a tool call that used to be a dictionary lookup,
and under load the store's tail latency becomes the tool's tail latency. Day 44's client hardening is
where the timeouts for this get chosen.

**The review comment a senior engineer leaves:** *"`draft_id` is sequential and there is no owner
column. Two problems: it is enumerable, and there is nothing stopping one client appending to
another's draft. Make it a random token and check ownership on every call — the fact that our own
client would never do it is not a control."*

**The interview question:** *"if MCP is stateless, how do you build something that spans several
calls?"* The answer: *"the server mints an opaque handle and returns it, and the client passes it back
as an ordinary tool argument. The state moves out of one instance's memory into shared storage, so any
instance can serve the next call. It is explicit — the handle is in the tool's schema, so you can see
which tools have memory — and it is honest about the cost: you have swapped process memory for a
network read, and you now own an expiry policy that a session used to give you for free."*
