# 3.3 — Lists you may keep

## One-line answer

Because a list no longer varies per connection, every list result now **must** carry `ttlMs` and
`cacheScope` — turning 60 `tools/list` requests into 3 when each client caches, and into 1 when a
shared proxy may — and tools **should** come back in a deterministic order so the prompt built from
them is byte-identical every time.

## The story

The menu is taped to the inside of the restaurant window, and you photograph it on the way past.

You are not going in today. You photograph it because you will be choosing lunch for six people
tomorrow and you would rather argue about it on the way over than standing in the doorway. At the
bottom of the menu, in small print, it says *prices valid to the end of the month*.

That line is what makes the photograph useful. Without it you would not know whether your picture is
information or a souvenir, so you would have to walk past again to check — which is exactly as much
effort as not photographing it at all.

Now the second thing, which is easier to miss. Tomorrow the six of you read your photograph and the
argument is short, because everybody is looking at the same list in the same order. If the restaurant
reprinted the menu each morning with the dishes shuffled, your photograph would still be *correct* and
it would no longer be *the same* — and the person comparing it against the board on the wall would
have to read both from the top every time.

## The idea in plain language

Under the old protocol, `tools/list` could legitimately return different answers to different clients,
because the server knew who was asking: it had negotiated capabilities with you during the handshake.
A list that depends on who is asking cannot be shared, and a list that might change at any moment
cannot be kept. So clients re-fetched, constantly.

Section 2 removed the negotiation, and the changelog states the consequence directly:

> *"List endpoints (`tools/list`, `resources/list`, `prompts/list`) no longer vary per-connection."*

Once a list is the same for everybody, it becomes worth caching — and the revision makes the server
say how:

> *"Require `ttlMs` and `cacheScope` fields on results returned by `tools/list`, `prompts/list`,
> `resources/list`, `resources/read`, and `resources/templates/list` via a new `CacheableResult`
> interface. `ttlMs` is a freshness hint (in milliseconds) allowing clients to cache responses and
> reduce polling; `cacheScope` (`"public"` or `"private"`) controls whether shared intermediaries may
> cache the response."*

Two fields, two questions:

| Field | The question it answers | Values |
| --- | --- | --- |
| `ttlMs` | how long may this be reused | a number of milliseconds |
| `cacheScope` | who may keep it | `"public"` — anyone, including a shared proxy · `"private"` — this client only |

`"private"` is the safe default and it is not paranoia: a `resources/read` result may be one user's
data, and a shared proxy caching it would serve it to the next person. `"public"` is for things that
are genuinely the same for every caller — a tool list, a public document.

And a third change, listed as minor and worth more than its billing:

> *"Servers **SHOULD** return tools from `tools/list` in a deterministic order to enable client-side
> caching and improve LLM prompt cache hit rates."*

**Deterministic** means the same input produces the same output, every time, in the same order. Two
different things depend on it. A client cache compares what it has against what it got; if the order
wobbles, every comparison says *changed*. And a **prompt cache** — the provider-side cache that lets a
model skip re-processing a prefix it has seen before — is keyed on the exact bytes of the prompt. Tool
declarations sit near the front of the prompt, so a shuffled tool list changes the prefix and misses
the cache for the entire conversation.

This is not new thinking. Cacheability is one of the named constraints in the paper this phase rests
on, and it is the constraint whose benefit is inseparable from its cost: a cache that is allowed to
serve a stale answer will occasionally serve one.

## Why Sutra needs it

Because Sutra has already paid for an uncached tool list, in the currency that actually hurts.

[Day 26](../../../day-26-loading-skills-into-adk/LESSON.md) measured the skill index at 479 tokens of
preamble and 83 per card, and
[Day 24](../../../day-24-token-accounting-and-budgets/LESSON.md) established that Sutra runs on twenty
free generations a day. Tool declarations sit in exactly the same place as skill cards — at the front
of every prompt, on every turn. A deterministic tool list is the difference between a prompt prefix
that a provider cache can recognise and one it cannot.

On the network side, the arithmetic is in the mechanism below and it is stark: with three clients over
a working session, an uncached list is 60 requests and a publicly cached one is 1.

And on **Day 34** it becomes something you must write. `sutra_mcp`'s `tools/list` has to return
`ttlMs` and `cacheScope`, and it has to decide what they should be — a decision with a real
consequence, because `ttlMs` is also *how long a client may keep calling a tool you have removed*.

## The paper behind it

> **Principled design of the modern Web architecture** · `doi:10.1145/514183.514185` · 2002 ·
> `https://doi.org/10.1145/514183.514185`

It argued that the web's scale comes from a chosen set of constraints, of which **cacheability** —
responses labelling themselves as reusable or not — is the one that removes interactions entirely
rather than making them faster, at the price of a window in which a client may hold data that is no
longer true.

`ttlMs` and `cacheScope` are that label, twenty-four years later, on a different protocol. The paper
is taught in this day's
[`../../papers/01-modern-web-architecture.md`](../../papers/01-modern-web-architecture.md).

## The mechanism

The two questions, counted:

```python
# days/day-32-mcp-stateless-core/lab/cache_math.py  (extract)
TTL_MS = 3_600_000
CLIENTS = 3
TURNS = 20


def fetches(scope: str, cached: bool) -> int:
    """How many tools/list requests reach the server across every client and every turn."""
    if not cached:
        return CLIENTS * TURNS
    return 1 if scope == "public" else CLIENTS


def prompt_key(tools: list[dict]) -> str:
    """The cache key a prompt cache would compute for this tool list, in this order."""
    return hashlib.sha256(json.dumps(tools).encode()).hexdigest()[:12]
```

**Line by line:**

- `TTL_MS = 3_600_000` is the value the specification's own `server/discover` example uses, written
  with underscores so a reader can see it is three million six hundred thousand milliseconds rather
  than counting zeros. Milliseconds, not seconds — a `ttlMs` of `3600` is not what you meant and the
  server will not tell you.
- `fetches` returns `CLIENTS * TURNS` when nothing is cached: every client asks on every turn, which
  is what a client does when it has no freshness hint and cannot risk a stale tool list.
- `return 1 if scope == "public" else CLIENTS` is the entire difference between the two scopes. A
  private cache is per client, so three clients means three fetches. A public one is shared by the
  proxy in front of them, so the second and third client are served from the first client's answer.
- `prompt_key` hashes `json.dumps(tools)` — the serialised bytes, in list order. That is a stand-in
  for what a provider's prompt cache keys on, and the stand-in is honest: **order changes the bytes,
  and bytes are the key**. Truncating to twelve characters is for readability only.
- `hashlib` and `json` are stdlib. **No model, no network, no key** — this is arithmetic and a hash.

**Line by line:**

- From the repository root. **Zero generations.**

Measured on 2026-09-04:

```text
3 clients, 20 turns each, ttlMs=3600000 (1 hour)
  cacheScope=private, cached=False   tools/list requests: 60
  cacheScope=private, cached=True    tools/list requests: 3
  cacheScope=public, cached=True     tools/list requests: 1

deterministic order is a cache key, not a tidiness preference:
  as declared      ['lookup_ticket', 'search_kb', 'list_open_tickets'] -> eca645e9d3d7
  two tools swapped ['search_kb', 'lookup_ticket', 'list_open_tickets'] -> 6e3f8b83aa69
  same tools, same descriptions, same key: False
```

**60 → 3 → 1.** The first step is the client obeying `ttlMs`. The second is `cacheScope: "public"`
letting a shared intermediary answer for everybody, and it is the step that only exists because
section 2 made the list identical for every caller.

**`False` on the last line** is the part worth remembering. Nothing about the tool list changed — same
three tools, same descriptions, same schemas. Two of them swapped position, and the key is different.
Every cache downstream of that list, including the model provider's, now treats it as new.

The listing endpoints also keep their `listChanged` notifications, and the specification says the two
mechanisms *"complement"* each other rather than replacing one another. `ttlMs` bounds how stale you
can be; a notification tells you sooner when you happen to be listening
([2.4](../02-the-reframe/2.4-server-discover-the-optional-question.md) mentioned
`subscriptions/listen`, and Day 36 builds it).

## When it breaks

Caching breaks in the direction that is hardest to see: the answer is not wrong, it is *old*.

A tool is removed from the server at noon. The list was fetched at a quarter to twelve with a `ttlMs`
of one hour. Until a quarter to one, a client cheerfully offers the model a tool that no longer
exists, the model calls it, and the server answers:

```text
{"jsonrpc": "2.0", "id": 12, "error": {"code": -32602, "message": "Unknown tool: close_ticket"}}
```

`-32602` is *Invalid params* — and note that this revision **changed** the resource-not-found code from
`-32002` to `-32602` to line up with JSON-RPC, so an older document will tell you the wrong number
here too.

The trap is that this error looks like a client bug and is not one. The client did exactly what the
server's own `ttlMs` permitted. The fix is on the server: a tool you intend to remove gets a shortened
`ttlMs` before it is removed, not after — which means a removal is two deployments, and knowing that
is the difference between a planned change and an incident.

The second break is `cacheScope: "public"` on something that is not. A `resources/read` returning one
customer's ticket, marked public, cached by a shared proxy, served to the next caller. Nothing errors.
Nobody finds out from a log. This is the most expensive mistake available in this part, and it is one
JSON field.

## In production

**What a professional writes instead:** `cacheScope` is decided per endpoint and written down beside
the handler, not chosen by a default. Tool and prompt lists are `"public"` with a generous `ttlMs`;
anything derived from a user's data is `"private"` with a short one, or has no cache story at all.
Tool ordering is fixed by sorting explicitly, because "the order we happened to register them in" is
deterministic right up until somebody reorders an import.

**What changes at scale:** the cache becomes the reason your server survives a busy morning, and
therefore the reason a bad `ttlMs` is a capacity incident rather than a correctness one. Set it too
low and every client polls; the 60 in the table above is the shape of that. Set it too high and a
rollback does not take effect, because half your clients are still holding the previous list.

**The failure mode that only appears with real traffic:** cache stampede. Every client fetched the list
at deploy time, so every client's copy expires at the same instant, and the server takes the whole
fleet's re-fetch in one second. The standard answer is jitter — vary `ttlMs` slightly per response —
and it is much easier to add before the fleet is large.

**The review comment a senior engineer leaves:** *"`tools/list` returns whatever order the decorator
registry produced. Sort it. Right now every reordering of our own imports invalidates every client
cache and every prompt cache downstream, and nobody will connect the two."*

**The interview question:** *"MCP made list results cacheable — what did that require, and what does it
cost?"* The answer: *"it required removing per-connection state, because a list that depends on who
negotiated what cannot be shared. Once lists are identical for everybody, results carry `ttlMs` and
`cacheScope`, and a shared proxy can answer for every client — we measured 60 requests dropping to 3
with a private cache and 1 with a public one. The cost is a staleness window: for up to `ttlMs`, a
client can be offering a tool you have deleted. So removing a tool is two deployments — shorten the
TTL, then remove — and anything user-specific is `private` or is not cached at all."*
