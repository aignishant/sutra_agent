# 2.3 — Every request introduces itself

## One-line answer

What the handshake used to establish once now rides inside every request in a block called `_meta` —
the protocol version, the client's capabilities and the client's name — and on this machine that
block measures **184 bytes**, repeated forever.

## The story

At the bank counter you fill in a deposit slip. Account number, name, amount, date, signature.

You hand it over, and the clerk asks for a second slip because the first transaction needs to be
split. On the second slip you write the account number again. And the name. And the date. And you
sign it again.

You know she has your account number. It is on the slip in her hand and it is on the screen in front
of her. Writing it a second time feels like the bank not paying attention.

But watch what the repetition buys. The slip can be handed to the clerk at the next window without
explanation. It can be put in a batch and processed this evening by somebody who has never seen you.
It can be found in a drawer next year and still make sense. If the counter had simply remembered you,
none of that would be true — the transaction would only be interpretable by the person you were
standing in front of, for as long as you stood there.

The repetition is not the bank being slow. It is what makes a slip a document instead of a
conversation.

## The idea in plain language

`_meta` is a plain JSON object that MCP allows inside `params` on any request and inside any result.
It carries information *about* the message rather than arguments *for* it, and its keys are namespaced
with a reverse-DNS prefix — `io.modelcontextprotocol/…` — so that anybody can add their own keys
without colliding with the specification's.

Three keys replace the handshake
(`https://modelcontextprotocol.io/specification/2026-07-28/changelog`, read 2026-09-04):

| Key | What it carries | Required? |
| --- | --- | --- |
| `io.modelcontextprotocol/protocolVersion` | the revision this request is written to | yes, on every request |
| `io.modelcontextprotocol/clientCapabilities` | what the client can handle if the server needs something back | yes |
| `io.modelcontextprotocol/clientInfo` | the client's name and version, for display and logs | SHOULD |

And one comes back the other way: the server SHOULD put
`io.modelcontextprotocol/serverInfo` in each result's `_meta`, so a response identifies its author the
same way a request does.

Two more `_meta` keys are worth knowing today because they are consequences of the same design:

- `io.modelcontextprotocol/logLevel` sets the log level **for this one request**. There is no longer a
  `logging/setLevel` call, because a setting that persists is state. The specification is strict about
  the pairing: servers *"MUST NOT emit `notifications/message` for requests that did not include this
  field"*. Verbose logging is now something you ask for per request, which is a better fit for how
  debugging actually happens.
- `traceparent`, `tracestate` and `baggage` are documented for OpenTelemetry trace propagation.
  Sutra already threads a correlation identifier through every log line
  ([22.2.2](../../../day-22-structured-logging/parts/02-wiring-the-run/2.2-the-correlation-id.md));
  these are the standard names for doing the same across a protocol boundary.

The property all of this buys has a name: **self-contained**. A request is self-contained when
everything needed to interpret it is inside it. That is the same property that makes a bank slip
processable by the evening shift, an HTTP request cacheable by a proxy, and an MCP request answerable
by any instance.

The price is real and should be stated as a number rather than waved at, which is what the mechanism
below does.

## Why Sutra needs it

Because Day 34 writes a server that has to read this block, and Day 44 hardens a client that has to
write it.

On the server side, `_meta` is where you find out whether you can answer at all. A request whose
`protocolVersion` you do not implement must be rejected with a named error rather than answered
optimistically — and that check happens per request, not once per connection, because there is no
connection to check once.

On the client side, `clientInfo` is what makes a server's logs useful. When something misbehaves in
production and the server operator asks *"which client is doing this?"*, the answer is either the
string Sutra put there or a guess based on IP addresses. Sutra's `clientInfo` should say `sutra` and
a version, and it should change when Sutra's does.

There is also a budget consequence that lands on Day 24's ledger. Every repeated `_meta` block is
bytes on the wire on every call. It is not tokens — this never reaches a model — but it is real, it
scales with tool-call volume, and it is the kind of cost that is invisible until somebody plots it.

## The mechanism

Two eras of the same tool call, printed side by side so the difference is countable rather than
described:

```python
# days/day-32-mcp-stateless-core/lab/letter.py  (extract)
VERSION_KEY = "io.modelcontextprotocol/protocolVersion"

NEW_CALL = {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/call",
    "params": {
        "name": "lookup_ticket",
        "arguments": {"ticket_id": "4521"},
        "_meta": {
            VERSION_KEY: "2026-07-28",
            "io.modelcontextprotocol/clientInfo": {"name": "sutra", "version": "0.1.0"},
            "io.modelcontextprotocol/clientCapabilities": {},
        },
    },
}


def self_contained(body: dict) -> bool:
    """True when this one request states its own protocol version."""
    return VERSION_KEY in body.get("params", {}).get("_meta", {})
```

**Line by line:**

- `VERSION_KEY` is pulled out as a constant because the full string
  `io.modelcontextprotocol/protocolVersion` appears in the request, in the header check
  ([3.2](../03-headers-and-caches/3.2-the-header-that-must-match.md)) and in every test. Typing it
  four times is four chances to typo a key that fails silently — a `_meta` key the server does not
  recognise is simply ignored, so a misspelling looks exactly like an omission.
- `_meta` sits **inside `params`**, not beside it. That placement is easy to get wrong and it matters:
  `params` is the object the method's schema describes, and `_meta` rides inside it so that one
  extension point serves every method rather than needing a new top-level field.
- `"io.modelcontextprotocol/clientCapabilities": {}` is an **empty object, not a missing key**. Empty
  means *I can handle nothing beyond the core*, which is a statement. Absent means the server has to
  guess, and a server that guesses generously will hand you something you cannot process.
- `clientInfo` is a name and a version, and the specification is explicit that it is self-reported and
  unverified — *"Clients SHOULD NOT use it to change their behavior"* is said about the server's
  equivalent, and the same caution applies in reverse. It is for display, logs and debugging, never
  for a security decision.
- `self_contained` reads through `params` then `_meta` with `.get(..., {})` at each step, so an old
  request without `_meta` returns `False` instead of raising. The function is the definition of the
  whole revision, in one expression.

The last three lines of the output, measured on 2026-09-04:

```text
  second message self-contained: False
  extra HTTP header on the second: Mcp-Session-Id: <minted by the server>
  self-contained: True
  bytes of _meta repeated on every request: 184
```

**184 bytes**, on every request, forever. For Sutra that is nothing: a support conversation makes a
handful of tool calls. For a service handling a hundred million calls a day it is about eighteen
gigabytes of introductions, and the answer is not to remove the envelope — it is compression, which
HTTP has had all along and which works especially well on a field that is byte-identical every time.

## When it breaks

The break that costs an evening is a `_meta` key spelt slightly wrong, because **nothing rejects it**.
`_meta` is an open extension point; unknown keys are ignored by design. So a client sending
`io.modelcontextprotocol/protocolversion` — lower-case `v` — has sent a request with no protocol
version at all, and the server rejects it with `400 Bad Request` and an
`UnsupportedProtocolVersionError` listing the versions it does support. The transport page states the
rule; no live 2026-07-28 server was reachable from this machine to capture the exact body, so the
version string below is the one to check rather than to trust:

```text

  curl -sS -X POST http://127.0.0.1:8000/mcp \
    -H 'Content-Type: application/json' -H 'MCP-Protocol-Version: 2026-07-28' \
    -H 'Mcp-Method: tools/list' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

`-32022` is `UnsupportedProtocolVersion`, and it is one of three codes the specification renumbered
into its own reserved range in this revision — `-32020` `HeaderMismatch`, `-32021`
`MissingRequiredClientCapability`, `-32022` `UnsupportedProtocolVersion`. The renumbering matters when
you are reading an old blog post: these three used to be `-32001`, `-32003` and `-32004`.

The confusing part is what the error points at. It says the version is unsupported, and the developer
looks at their code, sees `protocolVersion` set right there in the source, and concludes the server is
broken — when in fact the key never arrived under the name the server reads. The smallest fix is to
stop writing the key by hand: one constant, referenced everywhere, exactly as the extract above does.

The second break is more expensive and quieter: putting something in `_meta` that belongs in
`arguments`. `_meta` is not a place for parameters. A server that reads a business value out of
`_meta` has invented a private protocol, and the next client — which followed the specification — will
not send it.

## In production

**What a professional writes instead:** one function that builds the envelope, used by every call
site, with the version string coming from a constant that a test asserts against the revision the
server advertises. Never a literal at each call site.

**What changes at scale:** `clientInfo` becomes an operations tool. Server operators grep it, rate
limit on it, and email whoever owns it when a client misbehaves. A client that reports
`"name": "python-app"` is anonymous in exactly the situation where being identifiable is in your own
interest, because the alternative to *"we contacted the owner"* is *"we blocked the IP range"*.

**The failure mode that only appears with real traffic:** log volume. `io.modelcontextprotocol/logLevel`
is per request, which is a genuine improvement over a persistent setting, and it is also a switch a
client can leave turned on. A debug flag set in one code path and never cleared produces a server-side
log bill nobody can attribute — because the setting is no longer stored anywhere on the server to
inspect. It is only ever visible in the requests themselves.

**The review comment a senior engineer leaves:** *"every one of these forty call sites builds its own
`_meta`. When we move to the next protocol revision, that is forty edits and at least one miss. One
builder function, one constant, one test that asserts it matches what `server/discover` advertises."*

**The interview question:** *"if there is no handshake, how does the server know what the client can
do?"* The answer: *"the client says so on every request. There is a `_meta` block inside `params`
carrying the protocol version, the client's capabilities and its name, and the server SHOULD put its
own identity in each result's `_meta` coming back. It costs a couple of hundred bytes per request —
ours measures 184 — and it buys the property that any instance can answer any request, because there
is nothing to look up."*
