# 2.4 — The optional question

## One-line answer

`server/discover` is the one RPC every server **MUST** implement and every client **MAY** skip: it
returns the versions, capabilities and identity a handshake used to negotiate, without being a
handshake, because nothing is remembered afterwards.

## The story

You carry a broken mixer down the road to the repair shop.

Outside the shop there is a painted board: *radios, fans, mixers, irons — no laptops, no phones*. You
read it, see "mixers", and go in.

The man next door with the same mixer never reads boards. He walks straight in, puts the mixer on the
counter and says *"can you fix this?"* Ninety per cent of the time the answer is yes and he has saved
himself a stop. The other ten per cent he is told no, and he picks the mixer back up and walks to the
next shop, having lost a minute.

Neither of them is wrong. The board is faster when you are about to be told no; walking in is faster
when you are not. What would be wrong is a shop with no board at all, because then the only way to
find out anything is to carry a mixer in — and some questions are heavier to carry than a mixer.

## The idea in plain language

Removing the handshake removed something genuinely useful along with the thing that had to go. The
handshake was two jobs stuck together:

1. **Negotiate** — agree a version and exchange capabilities, and *remember the agreement*.
2. **Introduce** — tell me who you are and what you can do.

Job 2 is fine. Job 1 is the sticky note. So the revision kept the introduction and threw away the
memory, and the result is `server/discover`.

The specification is precise about its two halves
(`https://modelcontextprotocol.io/specification/2026-07-28/server/discover`, read 2026-09-04):

> *"`server/discover` lets a client query a server's supported protocol versions, capabilities, and
> identity before sending any other requests. Servers **MUST** implement it."*

and

> *"Calling `server/discover` is optional for clients — a client may invoke any RPC inline and handle
> `UnsupportedProtocolVersionError` if the server does not support the requested version."*

**MUST** on one side, **MAY** on the other. That asymmetry is the whole design. The server has to be
askable, so a client always has a way to find out. The client does not have to ask, so nothing about
discovery is on the critical path of a request that was going to work anyway.

The critical difference from `initialize`: after `server/discover` returns, **the server remembers
nothing**. It is a read, like any other. Two clients calling it get the same answer, and a client that
calls it and then sends a request to a different instance is in exactly the same position as one that
never called it.

What comes back:

| Field | What it is |
| --- | --- |
| `supportedVersions` | the revisions this server implements, as a list |
| `capabilities` | which of tools, resources, prompts and which extensions it offers |
| `_meta['io.modelcontextprotocol/serverInfo']` | the server's self-reported name and version |
| `instructions` | optional plain-language guidance for a model on using this server |
| `ttlMs`, `cacheScope` | how long the answer may be cached, and by whom |

The last row is easy to skim past and is the reason the probe is affordable. `server/discover` is a
cacheable result like any list ([3.3](../03-headers-and-caches/3.3-lists-you-may-keep.md)), so *"ask
first"* does not mean *"ask every time"*.

And a caution the specification states outright about `serverInfo`: *"Clients SHOULD NOT use it to
change their behavior, and SHOULD NOT rely on it for security decisions."* It is self-reported. It
identifies for a log, not for a policy.

## Why Sutra needs it

Two concrete places, one this week and one later.

**Day 33**, connecting Sutra to its first server. Over Streamable HTTP a client can skip the probe,
because a wrong guess comes back as an HTTP status with a JSON-RPC error in the body. Over **stdio**
it cannot: stdio is a pipe to a subprocess, there are no status codes, and a request the far end does
not understand may produce a parse error, a log line on stderr, or nothing at all. So the
specification says a client supporting both eras **SHOULD** send `server/discover` first on stdio and
use the answer as the fallback probe. Day 33 chooses transports; this is one of the ways the two
differ that is not about performance.

**Day 34**, writing `sutra_mcp`. `server/discover` is not optional to implement. A server that skips
it is not a 2026-07-28 server, however well the rest works, and it will fail exactly the audit Day 45
performs.

There is also a display use that matters more than it sounds. When Day 45 audits every server Sutra
talks to, *"what does this server say it is, and what does it claim to offer"* is one request rather
than three, and the answer is a document you can keep beside the provenance row.

## The mechanism

The request carries no parameters at all beyond the envelope every request carries — copied from the
specification page, read 2026-09-04:

```json
{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

And the reply:

```json
{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": { "tools": {}, "resources": {} },
    "_meta": {
      "io.modelcontextprotocol/serverInfo": { "name": "ExampleServer", "version": "1.0.0" }
    },
    "instructions": "This server provides weather and resource utilities.",
    "ttlMs": 3600000,
    "cacheScope": "public"
  }
}
```

Note `"resultType": "complete"`. Every result in this revision carries that field, and the other
possible value — `"input_required"` — is how a server says *I need something from you before I can
finish*. That pattern replaces server-initiated requests entirely and belongs to Days 36 to 38; today
it is enough to know why an unfamiliar field is sitting in every reply.

Now the cost question, which is the one you actually have to decide:

```python
# days/day-32-mcp-stateless-core/lab/discover_cost.py  (extract)
VERSIONS_WE_SPEAK = ["2026-07-28", "2025-11-25"]


def probe_first(server_versions: list[str]) -> tuple[int, str]:
    """Ask server/discover, pick a shared version, then send the real request."""
    shared = [v for v in VERSIONS_WE_SPEAK if v in server_versions]
    if not shared:
        return 1, "no shared version - stop after the probe"
    return 2, f"discover, then tools/call at {shared[0]}"


def straight_in(server_versions: list[str]) -> tuple[int, str]:
    """Send tools/call at our preferred version and handle the error if it comes back."""
    if VERSIONS_WE_SPEAK[0] in server_versions:
        return 1, f"tools/call at {VERSIONS_WE_SPEAK[0]}, accepted"
    shared = [v for v in VERSIONS_WE_SPEAK if v in server_versions]
    if not shared:
        return 1, "tools/call rejected, nothing shared - stop"
    return 2, f"tools/call rejected, retry at {shared[0]}"
```

**Line by line:**

- `VERSIONS_WE_SPEAK` is **ordered by preference**, newest first. `shared[0]` therefore picks the best
  mutually supported revision rather than the first one the server happened to list, which is the
  detail that keeps a client from silently downgrading to a legacy era it merely still supports.
- Both functions return `(requests, explanation)` rather than just a number, because a count without
  the reason is unreadable in the output table and unarguable in a review.
- `probe_first` returns **1** when nothing is shared. That is the interesting row: the probe is not
  pure overhead — against a server you cannot use, asking is *cheaper*, because you never send the
  doomed request at all.
- `straight_in` returns **2** only when a retry is possible. The retry is the whole risk of skipping
  the probe, and it is exactly one extra request, not a loop.
- No network and no server: these are pure functions over a list of version strings, so the trade can
  be argued from arithmetic rather than from a benchmark somebody ran once.

**Line by line:**

- From the repository root. **Zero generations, no network.**

Measured on 2026-09-04:

```text
server               probe first  straight in  what happens
modern               2            1            tools/call at 2026-07-28, accepted
modern and legacy    2            1            tools/call at 2026-07-28, accepted
legacy only          2            2            tools/call rejected, retry at 2025-11-25
nothing we speak     1            1            tools/call rejected, nothing shared - stop

one-off cost of the probe, amortised over a long-lived client:
    1 tool calls -> probe first: 2 requests, straight in: 1
   10 tool calls -> probe first: 11 requests, straight in: 10
  100 tool calls -> probe first: 101 requests, straight in: 100
```

Read the four rows and the rule falls out. Probing costs one extra request in the common case and
saves nothing in three rows out of four. Over a long-lived client it is one request in a hundred —
noise. Over a short-lived one that makes a single call, it is a doubling.

So the honest rule is not *"always probe"* or *"never probe"*. It is: **probe when you are about to be
told no, cache the answer, and skip it otherwise.** On stdio you are always about to be told no in a
way you cannot read, so you probe.

## When it breaks

The break is treating `server/discover` as a handshake, which is easy because it looks like one.

A client calls it, gets `supportedVersions`, and then behaves as though an agreement now exists. It
does not. The next request may land on a different instance behind the same URL, and that instance may
be mid-deployment on a different build. Nothing about the earlier answer binds it.

The symptom is a version error on a request that "cannot" fail, arriving after a successful probe:

```text
{"jsonrpc": "2.0", "id": 7, "error": {"code": -32022, "message": "unsupported protocol version"}}
```

after `server/discover` said `["2026-07-28"]` two seconds earlier. The client author's instinct is
that the server is inconsistent. The server is not inconsistent; it is *several servers*, which is the
whole point of section 2.

The smallest fix is to handle `-32022` on every request regardless of what discovery said. The probe
is a hint, not a contract, and a client that cannot cope with the hint being stale has quietly
reintroduced the assumption the revision removed.

The second break is skipping the cache. `server/discover` before every single tool call turns a
one-off into a doubling of your request count, and the `ttlMs` in the response exists precisely to
stop that.

## In production

**What a professional writes instead:** discovery once per server per process, cached with the `ttlMs`
the server returned, re-fetched on a version error rather than on a timer. The cache is keyed by
server URL, never by conversation.

**What changes at scale:** `server/discover` becomes the health-and-inventory endpoint. It is cheap,
it is required, and it tells you what a deployment currently is — so it ends up in dashboards, in
deployment verification, and in the audit script. Sutra's Day 45 audit will call it against every
server on the list and store the answer beside the provenance row.

**The failure mode that only appears with real traffic:** a rolling deploy. Half the instances
advertise a new capability, half do not, and a client that discovered against a new one and then sent
a request to an old one gets a capability error for something discovery promised. This is not a bug in
either side. It is what *"any instance can answer any request"* means when the instances are not
identical, and the answer is to make capability changes additive and to keep handling the error.

**The review comment a senior engineer leaves:** *"you call `server/discover` before every tool call.
The response has a `ttlMs` of one hour on it — cache it. And you are treating the result as a
guarantee: keep the `-32022` handler on the tool call too, because the next request can hit a
different container."*

**The interview question:** *"if MCP is stateless, why does it still have a discovery call?"* The
answer that shows you read the specification rather than a summary: *"because losing the handshake
lost the introduction along with the session, and the introduction was useful. `server/discover` is
mandatory for servers and optional for clients — it returns supported versions, capabilities and
identity in one request, and crucially the server remembers nothing afterwards, so it is a read and
not a negotiation. On HTTP you can skip it and let a 400 tell you; on stdio there is no status code,
so it is the probe you use to detect an old server."*
