# 6.2 — Before you depend on a server

## One-line answer

A server inside the data boundary is a dependency with a publisher, a version and a protocol
revision — so the intake is six questions with an exit code, and *"it worked when I tried it"* is not
one of them.

## The story

The water purifier under the kitchen sink stops working and you go looking for the folder.

In it there should be four things: the invoice with the model number, the installation slip saying
who fitted it and when, the service contract saying who is obliged to come and until when, and the
card from the last engineer's visit with the filter type he put in.

If all four are there, the phone call takes a minute. You read the model number, you read the contract
number, and somebody is coming.

If the folder has only the invoice, you are starting from nothing. You do not know whether the unit is
still covered. You do not know which of the two shops in the market fitted it, and both will tell you
it was the other. You do not know what filter is inside it, so nobody can bring one. The purifier is
the same purifier either way, and the difference between an afternoon and a fortnight is four pieces
of paper somebody either kept or did not.

Nobody keeps the folder because they enjoy filing. They keep it because the day it is needed is not
the day it can be assembled.

## The idea in plain language

Adding an MCP server to Sutra is not like adding a library. A library is code you can read, pinned by
a hash, running in your own process. A server is **somebody else's running program**, reachable over
the network, inside the boundary that [1.5](../01-the-socket/1.5-one-gate-to-guard.md) said would be
the one place worth guarding — and everything it returns is data a model will treat as true.

So the intake needs answers to six questions, and every one of them was earned by something earlier in
this day:

| Question | Where the answer comes from | If it is blank |
| --- | --- | --- |
| Who publishes it? | the registry namespace ([4.3](../04-governance-and-registry/4.3-a-name-that-proves-its-publisher.md)) | nobody to notify, nobody to revoke |
| Which version? | the registry entry, and `isLatest` | you cannot reproduce today's behaviour later |
| Where does it actually run? | `remotes`, or the package it points at | you do not know what you are trusting |
| Which protocol revision does it speak? | `server/discover` ([2.4](../02-the-reframe/2.4-server-discover-the-optional-question.md)) | you will find out at the worst moment ([5.1](../05-failure-lab/5.1-the-tutorial-from-four-months-ago.md)) |
| What is it allowed to be asked? | your allowlist, Day 40 | it can be asked anything |
| Who approved it? | a person's name | the decision has no owner |

Two of those deserve a sentence each, because they are the ones people argue about.

**"Which version?"** feels bureaucratic until the first time behaviour changes with no deployment on
your side. A registry name resolves to whatever is current; a name plus a version is a fact you can
return to. And as [4.2](../04-governance-and-registry/4.2-the-registry-queried-live.md) showed with a
real listing, the `remotes` URLs can differ between versions of the same server — so "the same server"
may not be the same endpoint.

**"Who approved it?"** is not ceremony. It is the difference between a decision and an accident.
Sutra already applies this to skills: `docs/SKILL_PROVENANCE.md` carries a row per skill with its
source, licence and date, and Day 27 filled the first two rows. Servers are strictly more dangerous
than skills — a skill can only suggest, a server runs code and returns facts — so they get at least
the same ledger.

The honest framing for all six: **the registry answers three of them, and you answer three.** The
registry proves authorship and tells you where the thing lives. It says explicitly that it delegates
security scanning elsewhere. The revision, the allowlist and the reviewer are yours.

## Why Sutra needs it

Because Day 33 is tomorrow and it connects Sutra to a server for the first time, and the row you write
then is the row Day 45 audits.

`docs/SKILL_PROVENANCE.md` exists because Day 25 asked *"where did this skill come from?"* and the
answer had to be somewhere other than a person's memory. Phase 5 raises the same question about
servers, and it raises it eleven more times before Day 45: `sutra-mcp` on Day 34, a database server on
Day 39, whatever the grounding fallback turns out to be, and anything Day 42 exposes outward.

An audit that starts by *assembling* provenance has already lost. Day 45's job should be checking rows
that already exist, not reconstructing them from commit history and chat messages — which is exactly
the folder with only the invoice in it.

There is also a specific gap this closes. [1.5](../01-the-socket/1.5-one-gate-to-guard.md) measured
whether anything on the agent side reaches past the boundary. That check answers *"is there a second
door?"* It says nothing about who is on the other side of the first one. This part is the other half.

## The mechanism

Six questions, one exit code:

```python
# days/day-32-mcp-stateless-core/lab/server_intake.py  (extract)
ALLOWED_NAMESPACES = {"ac.tandem"}

ENTRY = {
    "name": "ac.tandem/docs-mcp",
    "version": "0.3.0",
    "remotes": ["https://tandem.ac/mcp"],
    "status": "active",
    "isLatest": False,
}

CLAIMED_REVISION = ""  # TODO(me): fill from server/discover on Day 33
REVIEWED_BY = ""  # TODO(me): a person, before this reaches an allowlist


def findings(entry: dict) -> list[str]:
    """Every reason this server is not ready to sit inside the boundary."""
    found = []
    space = namespace(entry["name"])
    if space not in ALLOWED_NAMESPACES:
        found.append(f"namespace {space!r} is not in the allowlist")
    if entry["status"] != "active":
        found.append(f"registry status is {entry['status']!r}")
    if not entry["isLatest"]:
        found.append(f"version {entry['version']} is not the latest published")
    if not entry["remotes"]:
        found.append("no remote URL and no package - nothing to connect to")
    if not CLAIMED_REVISION:
        found.append("protocol revision unknown - server/discover has not been called")
    if not REVIEWED_BY:
        found.append("no named reviewer")
    return found
```

**Line by line:**

- `ENTRY` is a **real** registry entry, captured by `registry.py` on 2026-09-04 and pinned here rather
  than fetched. That is deliberate: an intake check that depends on the network gives a different
  answer when the network is down, and a check whose output moves is a check people stop reading.
- `CLAIMED_REVISION = ""` and `REVIEWED_BY = ""` are **empty on purpose**, and each carries a
  `TODO(me)`. A blank is a finding, not a default — the alternative design, where an unknown revision
  quietly passes, is how a check ends up green and meaningless.
- `findings` returns a **list of reasons** rather than a boolean, because the caller needs to know
  which of the six failed. A boolean intake check tells you to go and run it again by hand.
- Each condition names the value in its message — `{space!r}`, `{entry['version']}` — so the output can
  be pasted into a pull request without the reader also needing the source.
- `isLatest` is checked separately from `status`. A server can be `active` and superseded, which is the
  most common real state and the one a name-only reference hides completely.
- `not entry["remotes"]` is not the same as *no way to run it*: a server may ship as a package instead
  of a remote URL, so a production version of this check looks at both. The hub's build brief asks you
  to extend it, because Sutra has not yet met a package-only server.
- **Zero model calls, no network.** Dictionary lookups over a pinned entry.

The script ends by raising `SystemExit(1 if problems else 0)`, so it is an eval that can go red, and
by printing the provenance row it would produce. Run it:

```bash
uv run python days/day-32-mcp-stateless-core/lab/server_intake.py; echo "exit: $?"
```

**Line by line:**

- From the repository root. `echo "exit: $?"` prints the exit code, because that is the part a CI job
  reads. **Zero generations.**

Measured on 2026-09-04:

```text
  version 0.3.0 is not the latest published
  protocol revision unknown - server/discover has not been called
  no named reviewer
  findings: 3

  provenance row to paste once the findings are zero:
  | ac.tandem/docs-mcp | 0.3.0 | ac.tandem | registry | 2026-09-04 | 32 |
exit: 1

```

**Three findings on a server nobody suspects of anything.** The namespace check passed — it is on the
allowlist, and its status is active. What is missing is not evidence of a problem; it is evidence of a
decision. The version is stale, nobody has asked the server which protocol it speaks, and no human
name is attached.

That is the useful shape for an intake check. It does not detect malice — nothing here could — and it
is not trying to. It refuses to let a dependency arrive without the four pieces of paper.

## When it breaks

The break is the check that is run once and then routed around.

Somebody needs a server today, the intake reports three findings, and the findings are all
paperwork — so the server gets wired in and the row gets written *"next week"*. Nothing goes wrong.
The server behaves. Six months later:

```text
$ grep -c "" docs/SERVER_PROVENANCE.md
4
$ uv run python -c "import tomllib,pathlib; print(len(tomllib.loads(pathlib.Path('mcp_servers.toml').read_text())['server']))"
9
```

Four rows, nine servers. Nobody can now say which five were reviewed, by whom, or against which
version — and reconstructing it means reading commit history and asking people what they remember.
That is the folder with only the invoice in it, and it is not recoverable by trying harder later.

The second break is subtler and it looks like diligence: an intake check that grows until it is a
substitute for reading the server. A list of automated conditions cannot tell you whether a tool's
description is written to manipulate a model, whether the server logs your arguments, or whether the
publisher is who you think they are — which is precisely why `REVIEWED_BY` is a **person's name** and
not a boolean the script can set for itself.

## In production

**What a professional writes instead:** the intake runs in CI over a configuration file listing every
server, not over one pinned entry, and it fails the build when a row is missing. The provenance ledger
is generated from that file rather than maintained by hand, so the two cannot disagree — the same
discipline `./m trace` already applies to curriculum identifiers.

**What changes at scale:** the ledger becomes the answer to questions asked under pressure. *"Are we
affected by the advisory for this publisher?"* is a grep against a namespace column, and it takes a
minute if the column exists and a week if it does not. That is the entire argument for keeping it,
and it is worth making in exactly those terms rather than as a principle.

**The failure mode that only appears with real traffic:** the server that changed underneath you. You
reviewed version `0.3.0`; the deployment behind that URL is now something else, because a remote server
is not pinned by anything you control — you pinned a name, and the operator ships whenever they like.
This is the honest limit of the whole exercise and it deserves saying out loud: for a **remote** server
you are recording provenance of a decision, not of an artefact. For a **package** server you can pin
the artefact, which is one real argument for preferring one.

**The review comment a senior engineer leaves:** *"this pull request adds a server to the boundary and
the provenance row is missing. I do not need it to be perfect — name, version, namespace, date, and
your name as the reviewer. If we cannot say who approved this in six months, we do not have a boundary,
we have a habit."*

**The interview question:** *"how do you decide whether to trust a third-party MCP server?"* An answer
that separates what is checkable from what is not: *"the registry gives you three things — a verified
namespace, so there is an identifiable publisher; a version; and where it actually runs. It explicitly
does not give you a security review. So we add three of our own: which protocol revision it speaks,
which tools it is allowed to be asked for, and a named human reviewer. That goes in a provenance
ledger in CI, and the check fails the build if a row is missing. The limit worth being honest about is
that for a remote server you are recording provenance of a decision, not of an artefact — the operator
can redeploy whenever they like, which is why the audit is periodic rather than one-off."*
