# 2.3 — Words before it matters

## One-line answer

The two orderings contain **exactly the same facts**, and the number that separates them is **words
before the first sentence that needs a person: 0 against 25** — not length, position.

## The story

You get home and there is a saved message waiting on the phone. You press play while you are still
taking your coat off.

The voice starts by saying who it is, then explains that they tried the other number first and it
just rang out, then that they were not sure whether to try you at work, then that they know you are
busy, then a little about how their week has been going. You are half listening. You have started
opening the post. Somewhere near the end, in a slightly quicker voice, they say the actual thing:
they need you to ring the garage back today because the part has come in and they will only hold it
until the end of the day.

You catch the word *garage* and the word *today*, and then the message ends.

Now you have to play the whole thing again, from the beginning, through all of it, to get back to
the one sentence that was for you. Nothing in that message was untrue and nothing was missing. It
was just arranged so that the only part you had to act on arrived after you had stopped properly
listening.

## The idea in plain language

Part [2.1](2.1-one-function-one-order.md) built `lines(queue, night)`: one function that returns the
standup as a list of `(text, attention)` pairs — a sentence, and a flag saying whether that sentence
is one somebody has to act on. Part [2.2](2.2-carry-the-flag.md) fixed how that flag is set: it is
carried from the ticket data, never recovered by searching the sentence for a phrase.

This part runs both orderings and reads the numbers off.

Two words are worth pinning down before the numbers, because everything below uses them.

- A **flagged line** is a sentence whose `attention` flag is `True` — a sentence that exists because
  somebody has to decide something. In the printed output it is the line that begins with `>`.
- An **ablation** is the same system with one idea deliberately switched off, run so that the two
  results can be put side by side. Here the ablation is `--flat`: the queue read out in the order it
  happens to sit in, which is what you get when nobody makes an ordering decision at all.

The measurement is **words before the first flagged line**. It is a *prefix*: count the words of
each sentence in turn, stop at the first flagged one, report the running total. It is not the length
of the report and it is not an average over the report. It is the amount of talking a listener has to
sit through before the first thing that was for them.

And here is the part that is easy to get backwards. Attention first is 5 sentences, queue order is
14, and **that is not the finding**. Shorter is not the goal. *Earlier* is. A standup can be long and
still put the thing that needs a decision first — and section 3 of this day has a report that is
short and still bad, because being brief and being useful are different properties.

## Why Sutra needs it

Because the build brief in the hub asks for one specific, checkable thing: `lines(...)[0][1] is True`
when the queue has a blocked ticket. That assertion is this part made into a test. Without a
measurement behind it, it is an opinion about style that a future change would quietly delete.

It also gives the day a number to argue with. "Attention first reads better" is not something a
reviewer can disagree with usefully. "The first sentence that needs you is 25 words in" is. When part
[4.1](../04-in-production/4.1-what-a-standup-costs.md) prices a standup in a listener's attention
rather than in tokens, this is the number it prices.

And it is the honest floor for what this day can claim. The lab has no speech in it. What it can
count is words, and what it must not do is dress a word count up as a claim about seconds of a real
person's morning.

## The mechanism

The whole measurement is one function in `lab/standup.py`, quoted here whole and unchanged — it
already sits at column 0 in the file, so nothing was dedented:

```python
def before_attention(lines: list[Line]) -> tuple[int, int]:
    """(words, sentences) a listener hears before the first sentence that needs them."""
    words = 0
    for index, (text, attention) in enumerate(lines):
        if attention:
            return words, index
        words += len(text.split())
    return words, len(lines)
```

**Line by line:**

- `lines: list[Line]` takes the standup as part [2.1](2.1-one-function-one-order.md) returns it — a
  list of `(text, attention)` pairs. This function never builds a standup and never reorders one. It
  only measures, which is why both arms of the day can be measured by the same code.
- `if attention: return words, index` — the loop **stops** at the first flagged line and returns what
  it has counted so far. That early return is the definition of the quantity. It is not a total over
  the report and it is not an average across the flagged lines; it is a **prefix**, and a prefix is
  the only shape that answers "how much before". Move the `return` after the `words +=` line and you
  are measuring something else entirely.
- `words += len(text.split())` runs only on lines the listener has already sat through, because the
  flagged case returned above it. `str.split()` with no argument splits on any run of whitespace, so
  `"4688, refund over the limit - needs an approval."` counts as seven words. It is crude — the
  hyphen is counted as a word of its own — and it is crude *identically* in both arms, which is what
  makes the comparison fair.
- `if attention` reads the **flag**, not the text. This is part [2.2](2.2-carry-the-flag.md)'s whole
  subject, and it is the reason the numbers below can be trusted at all. The two orderings word the
  same fact differently — "Two tickets need you" against "which needs you" — so a version of this
  function that searched the sentence for a phrase would count one arm correctly and the other one
  wrong, and would look completely plausible while doing it.
- `return words, len(lines)` is the fall-through: the loop ran to the end and found no flagged line
  at all. It reports the entire report, which is the **correct** answer for a morning when nothing
  needs anybody — the listener really did hear all of it before reaching anything that was for them,
  because there was nothing. That case is part
  [3.1](../03-the-quiet-morning/3.1-nothing-needs-you.md)'s subject, and it is worth noticing that
  the `for ... return ... else fall-through` shape handles it without a single `if` about emptiness.

**Read the second run's `>` lines by their position, not by their content.** The first one is
sentence **six** of fourteen. The second one is sentence **eleven**. That second number is the one
worth sitting with: a listener who hears half of this report — who takes the tea off the hob, who
gets talked to by somebody else, who simply drifts — has heard one of the two things that were for
them and does not know there was another.

Put the two runs side by side:

| What is measured | Attention first | Queue order (ablation) |
| --- | --- | --- |
| sentences in the standup | 5 | 14 |
| words in total | 53 | 103 |
| words before the first flagged line | **0** | **25** |
| position of the second flagged line | sentence 2 of 5 | sentence 11 of 14 |
| every fact present | yes | yes |

**The last row is the row that matters.** Both reports name all twelve tickets' worth of state, both
name both blocked tickets and the reason each is blocked, and both report last night's job. Neither
one omits anything, neither one is wrong, and neither one would fail a test that checked the facts.
That is what makes this a **design finding** and not a bug report: there is no error here to fix,
only a decision that somebody either made or did not make.

## When it breaks

**Words are a proxy for how long the listener is held, and a rough one.** Sentences are not all the
same length, people read out loud at different speeds, and the listener's attention does not drain
at a constant rate per word anyway. Worse, this lab has no speech in it at all — nothing on this page
was ever said aloud. Day 75 part 3.1 measured the honest version of the same worry from the other
side: audio is priced by **duration**, so that day's budget was in seconds of speech. This part
counts words. The two are related by a speaking rate that nobody here has measured, so "0 against 25
words" must not be quietly upgraded into a claim about anybody's morning.

**The measurement rewards putting the flagged line first, and says nothing about whether the right
lines are flagged.** `before_attention` reads `attention` and believes it. A standup that flags every
single sentence scores a perfect 0 and is the flat report wearing a `>` on every line — same
fourteen sentences, same position for the ticket that needs an approval, and now with the added
damage that the flag has stopped meaning anything. This is Day 73 part 3.2's failure in a new place:
a signal that fires on everything reassures exactly as much as a signal that fires on nothing, and
both are worse than no signal, because somebody is now relying on it. The number on this page is only
as good as `Ticket.needs_person`, which `_state.py` deliberately makes a field somebody sets rather
than something derived from age or category.

**Attention first is not automatically shorter.** It happens to be here for a reason that has nothing
to do with ordering: the flat version reads out every ticket individually, and the attention-first
version replaces eleven of those sentences with one summary of the queue's shape. Change that.
Suppose `attention_first` said its three flagged sentences and *then* read all twelve tickets. That
report is 17 sentences and around 130 words — longer than the ablation — and it still scores **0
words before the first flagged line**, because the first thing said is still the thing that needs a
person. The score and the length are independent, and confusing them is how a team ends up
optimising a standup by deleting sentences from the middle of it.

## In production

**What a professional measures about a report nobody watches being read.** Not its length. The
**position of the actionable item** — how far in the reader or listener has to get before reaching
the thing that requires them to do something. On a page it is how far down the fold; in an alert body
it is whether the affected service is in the first line or the fourth; in a spoken report it is this
number. Length is easy to measure and almost never the thing that went wrong, which is exactly why it
is the number teams end up watching.

**What changes as the report gets older.** Reports grow by **appending**. Somebody adds a section for
deploys, somebody adds a section for on-call handover, somebody adds a line about last week's
incident, and each of those changes is individually sensible and individually reviewed. The total
size grows visibly — everyone can see the report got longer, and somebody will eventually complain
about it. What degrades **silently** is the position: nobody's pull request said "this moves the
approval request from sentence one to sentence nine", because no reviewer was looking at that. A
report that was designed attention-first stops being attention-first without a single commit that
looks wrong. The defence is that this measurement is a test, not a paragraph in a document — which is
why the hub's build brief asks for `lines(...)[0][1] is True` rather than for a style guide.

**The review comment a senior engineer leaves:** *"Good — but please rename the test. Calling it
`test_standup_is_short` will get it deleted the first time somebody legitimately needs to add a
section, and then we lose the property we actually care about. Assert on the position of the first
flagged line and nothing else, and put the word 'position' in the name. Second thing: this number is
only meaningful if the flag is meaningful. Add a check that not every line comes back flagged, or in
six months somebody will fix a missed escalation by flagging everything and this test will go green
on a report that is strictly worse."*

**The interview question:** *"You have a report that is correct and complete and people still say it
is not useful. How would you measure what is wrong with it?"* An honest answer: *"I'd measure where
the thing that needs a decision sits, rather than how long the report is. I did exactly this on a
spoken standup: the same twelve tickets, the same two that needed somebody, said two ways. Attention
first put the first line that needed a person at word zero. Queue order put it at word 25, and the
second one at sentence eleven of fourteen — so anyone who heard half the report heard one of the two
things that were for them and had no idea there was another. Every fact was present and correct in
both, which is the point: there was nothing to fix, only a decision nobody had made. The honest
limits are that words are a rough proxy for how long you hold someone's attention — I hadn't measured
a speaking rate — and that the measurement rewards putting the flagged line first without checking
that the right lines are flagged. Flag everything and you score perfectly. So I'd pair it with a
check that the flag is still selective."*
