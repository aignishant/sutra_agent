# 2.1 — One function, one order

## One-line answer

The order a standup is said in is **one decision**, so it belongs in **one function** —
`lines(queue, night)`, returning the sentences in the order they will be spoken — and because that
function returns data instead of printing text, the order becomes something a test can read.

## The story

A school concert. Somebody has to stand at the side of the stage with the running order, and this
year it is one parent with a single sheet of paper. Item one, the recorder group. Item two, the
choir. Item three, the head's thank-yous. Item four, the year-three play, after the interval.

The sheet is not clever. It is a list. But it is *one* list, in *one* hand, and anyone who is unsure
what happens next walks over and looks at it. When the choir teacher wants her group moved earlier,
there is exactly one place that change gets made, one person who makes it, and everybody who needs
to know finds out by looking at the same sheet as before.

Now picture the year they did not print it, because everybody knows roughly what happens. The
recorder group goes on. The head, seeing them finish, walks up to do the thank-yous — while the
choir, who were told they follow the recorders, are already filing on from the other side. Two
things happen at once in front of a hall full of people. And the year-three play, which was supposed
to be after the interval, never goes on at all, because the person who was going to fetch them
thought somebody else had. Nobody notices until the lights come up.

Here is the part that matters for today. With the sheet, you can check the concert before it
happens: read the top line and you know what the hall will hear first, without waiting for the hall
to fill up. Without the sheet, the only way to find out the order is to hold the concert.

## The idea in plain language

A standup has two ingredients. The **facts** — twelve tickets open, two of them stuck on a decision,
last night's digest died — and the **order** those facts are said in.

The facts come from the queue. Nobody has to decide them; they are read. The order is different: it
is a **decision somebody makes**, and part 1.3 measured what that decision is worth. Same twelve
tickets, same true sentences, and one ordering delivered every part that needed a person while the
other delivered none of them.

A decision that valuable needs an **address** — one named place in the code where it lives, so it
can be found, read, changed and tested. Call that place `lines(queue, night)`: a function that takes
the state and gives back the sentences, in the order they will be said.

Where else could it live? Four options, and they are not equally good:

| Where the ordering lives | How you would test it | What two people editing it does |
| --- | --- | --- |
| Inside the function that prints | capture the printed output and match strings in it | two printers drift apart; the order you get is whichever one ran |
| Spread across the callers that assemble the report | a test per call site, and not one of them tests *the order* | each site is edited separately, so there is no longer *an* order |
| In the prompt handed to a model | you cannot; you can only read the output and judge it by eye | the instruction gets edited in two prompts and nothing goes red |
| In one function that returns data | call it and look at the first element | one diff, one review, one test that can go red |

The last row is the one the hub's build brief asks for, and it is the running-order sheet: one list,
one hand, readable before the concert starts.

There is a second reason this decision so often ends up in the wrong place, and it is worth saying
plainly. **The ordering is a product decision expressed as code.** "What do we say first" is the
kind of question a product owner asks, not the kind an engineer usually files under *interface* — so
it does not get one. Nobody sits down and writes a function whose job is *the order*. Instead the
order emerges: a little of it in a template, a little in a system prompt, a little in the loop that
walks the tickets, and a little in the two call sites that stitch those together. Every one of those
edits was reasonable on its own. Together they are a running order nobody holds.

## Why Sutra needs it

Because the hub's §4 build brief asks for exactly one function — `lines(queue, night)` returning
`(text, attention)` pairs — and the gate checks its **shape**, because on this day the shape *is*
the design.

And because part 1.3 already showed that correctness is not the question here. Both orderings say
only true things. The difference between a standup somebody can act on and a standup that wastes
their attention is entirely the ordering decision, which means the ordering decision is the product.
A property that decides the quality of the product should not be an emergent side effect of whoever
edited the report last.

Two of this day's other parts sit on top of this one and are deliberately not taught here:

- **How the attention flag is represented and why it is carried rather than recovered from the
  text** is part 2.2, [Carry the flag, do not search for it](2.2-carry-the-flag.md). That part is a
  real bug from this lab.
- **How much a listener hears before the part that needs them** — the sentence and word counts, and
  both transcripts — is part 2.3,
  [Words before it matters](2.3-words-before-it-matters.md). All this part will say about the
  numbers is that the two orderings produce **5 sentences** and **14** on identical facts, and 2.3
  is where that is shown and argued.

## The mechanism

Here is the ordering decision, whole, from `lab/standup.py`. It is a top-level function, so it is
reproduced exactly as it sits on disk, at column 0:

```python
def attention_first() -> list[Line]:
    """What needs a person, then the shape of the queue, then last night."""
    blocked = _state.needs_a_person()
    lines: list[Line] = []
    if blocked:
        lines.append((f"Two tickets need you: {', '.join(t.ref for t in blocked)}.", True))
        lines += [(f"{t.ref}, {t.why}.", True) for t in blocked]
    else:
        lines.append(("Nothing needs you.", True))
    lines.append(_queue_shape())
    lines.append(_night())
    return lines
```

**Line by line:**

- `def attention_first() -> list[Line]` — the return type is the whole argument of this part. It
  returns a **list**, not `None`, and it does not print. Printing is somebody else's job (`main()`
  does it, further down the file). A function that prints can only be checked by capturing what it
  wrote and searching that text; a function that returns a list can be checked by *looking at the
  list*. That is what makes the gate's fourth check possible at all, and it is the running-order
  sheet: you read the top line without holding the concert.
- `Line` is the alias declared near the top of the same file — `Line = tuple[str, bool]`, one
  sentence plus whether it is one somebody has to act on. What that `bool` is and why it is carried
  in the tuple rather than worked out later is part 2.2's subject, not this one's.
- `blocked = _state.needs_a_person()` — the tickets that will not move without a person, asked for
  **once**, at the top, before any sentence exists. Not asked again inside the loop, not asked again
  by the caller. One question, one answer, one name.
- `lines: list[Line] = []` — the running order, empty, about to be filled in the order it will be
  spoken. The variable is the sheet.
- `if blocked:` / `else:` — the branch that decides what to say when nothing needs a person. That is
  a genuine design question with a wrong-looking obvious answer, and it belongs to part 3.1,
  [Nothing needs you is a report](../03-the-quiet-morning/3.1-nothing-needs-you.md). Read it there.
  What matters *here* is that both arms append to the same list, in the same place, so there is
  still exactly one running order however the morning turns out.
- The two appends in the `if` arm are the attention block: one summary sentence naming the
  references, then one sentence per blocked ticket giving the reason. Both flagged `True`.
- `lines.append(_queue_shape())` and `lines.append(_night())` — and this is the point of the two
  helpers. `_queue_shape()` builds the "the queue is 4 sign-in, 5 billing, 3 export" sentence and
  `_night()` builds the sentence about last night's job, each returning a finished `Line`. They
  exist so that the **order** is three appends you can read in one glance, rather than something you
  have to reconstruct by reading twenty lines of string building. Move the string work out and the
  decision is left standing on its own.
- `return lines` — the sheet, handed over. Nothing has been said out loud yet.

Three appends, top to bottom, is the entire specification of this standup. That is what it looks
like when a product decision has an interface.

The file also has `flat()` right underneath, which builds the same facts in the order the queue
happens to sit in. It is the **ablation** — the switch that turns this idea off so you can see
whether it mattered — and its output is part 2.3's to show.

**One difference between the lab and the build brief, on purpose.** `attention_first()` takes no
arguments and reads `_state` directly, because the lab is a fixed measurement over one fixed queue.
The brief asks you to write `lines(queue, night)` with the state **passed in**, and the reason is
visible in the gate: it calls your function twice, once with the full queue and once with a queue
that has had the blocked tickets removed. A function that reaches out to module-level state can only
ever be tested against one world.

Now the check that reads the sheet. This fragment lives inside `main()` in `lab/gate.py`, so its
four spaces of common leading whitespace have been removed here:

```python
check(
    "what needs a person is said first",
    bool(shaped) and said[0][1] is True,
    "a listener who hears one sentence must hear that one; see part 2.3",
)
```

**Line by line:**

- `check(label, ok, detail)` is the gate's own two-line helper: it prints `ok` or `FAIL` with the
  label, and on failure appends the detail to `FINDINGS`, which becomes the exit code at the end.
- `said` is what your `lines(queue, night)` gave back a few lines earlier in `main()`. The gate
  **called your function and is looking at its answer.** A gate that could only read your source
  would have to guess: it would grep for the word `blocked`, or check that some string appears
  before some other string, and be wrong the first time you renamed a variable. This one asks the
  function what it says and reads the reply.
- `bool(shaped)` — the previous check established that `said` really is a list of two-element
  `(str, bool)` tuples. Reusing that here is what stops this check from exploding with a
  `TypeError` when the module is half written, which matters because on this day the module is *not
  yet written* and a check that crashes teaches nothing.
- `said[0][1] is True` — **this is the whole of today's design decision, written as one subscript.**
  `[0]` is the first thing the listener will hear; `[1]` is its attention flag. "The first sentence
  must be one that needs a person" turns into six characters of Python. It is only expressible this
  way because `lines` returns data: had it printed, the equivalent assertion would have been a
  string search over captured output, and it would go red the day somebody rewrote a sentence
  without changing the order at all.
- `is True` and not `if said[0][1]:` — deliberate, and Day 72 part 2.3 is where the reason was
  measured. A truthy test accepts `1`, `"yes"`, a non-empty list and anything else that is not
  falsy, so a flag that has quietly become a string still passes. `is True` accepts exactly the
  boolean `True` and nothing else, which is precisely the contract the check above it asserted.
- The detail string is not decoration: a failing gate that names the part explaining the failure is
  the difference between a red line and a red line you can act on.

## When it breaks

**One function fixes *where* the decision lives and says nothing about whether the decision is
right.** This is the honest limit of the whole part. `attention_first` puts blocked tickets first;
that is a choice, and putting the choice in one readable place does not make it correct. Part 4.2,
[Who it is for](../04-in-production/4.2-who-it-is-for.md), argues that the right order depends on
who is listening — the engineer, the person on support and the manager want three different reports
from the same queue. If that argument holds, a single fixed order is wrong for two of the three
audiences, and the fix is an **argument to the function**, not a second function. The interface
survives; the ordering inside it does not.

**The gate checks the first element and nothing else.** `said[0][1] is True` says the first sentence
is the important one. It says nothing about the second, nothing about whether the remaining blocked
tickets are buried at the bottom, and nothing about whether the sentence is any good. It is a real
check that can genuinely go red, and it is a fraction of the design. Do not mistake a green gate for
a good standup.

**And the failure mode that looks like less work: putting the ordering in a model's prompt.** It is
tempting, because it reads like English and takes one line:

> *System instruction: summarise the queue for a standup. Mention anything that needs a person
> first.*

Now the running order lives in a sentence inside a prompt. Three things follow.

- **There is nothing to test.** No function returns a list, so no assertion can look at element
  zero. The only check available is to run the model, read the answer and judge it by eye — which is
  not a check, because it cannot go red on its own.
- **It drifts silently with the model.** The prompt did not change, the code did not change, the
  facts did not change, and the new model version happens to lead with the queue counts because it
  found them a more natural opening. Every sentence is still true, so nothing you have looks broken.
  This is the same shape as part 2.2's bug: a wrong result that is plausible on its face.
- **It multiplies.** Prompts get copied. The instruction ends up in two prompt files and one
  template, they are edited on different days, and now the answer to "what do we say first" is
  "depends which prompt this call went through".

A model is a fine way to choose the **words**. The **order** is a decision your product owns, and a
decision you cannot assert on is a decision you have not really made.

## In production

**What a professional does.** One function. It returns data, never printed text. The order is
visible in the first ten lines of the body — appends in sequence, not scattered through string
building — and everything else is pushed into helpers so the sequence stays readable. And the test
asserts on the **first element**, not on the whole rendered string. That is the difference between a
test that goes red when the order changes and a test that goes red when somebody fixes a typo.

**What changes at scale.** One standup becomes several audiences, and the moment you have three of
them the tempting move is three functions: `engineer_lines`, `support_lines`, `manager_lines`.
Resist it. Three functions is three running orders, edited on three days by three people, and within
a year the shared parts have quietly diverged. An **argument** — who this is for — keeps one
function, one place to read the whole policy, and one diff when the policy changes. Part 4.2 is the
argument for why the audiences differ in the first place; this part is why they should not become
separate code paths.

**The review comment a senior engineer leaves:** *"Two things. First, this function prints — make it
return the lines and let the caller print them, because right now the only way to test our most
important product decision is to capture stdout and grep it, and that test will go red the first
time somebody rewords a sentence without touching the order. Second, the ordering is also implied in
the template and in the system prompt, so there are three answers to 'what do we say first' in this
change. Delete two of them. And put the audience in the signature now rather than forking this into
three near-identical functions in six months — I've watched that happen and the shared half always
drifts."*

**The interview question:** *"You've built an agent that reports on some state. Where does the
decision about what it says first live?"* An honest answer: *"In one function that returns the
sentences as data, in the order they'll be said — for us that was `lines(queue, night)` returning
`(text, attention)` pairs. The reason is testability. On a voice line the order is the product, not
the presentation: we measured the same true facts in two orders and one delivered every item that
needed a person while the other delivered none of them. If that decision is spread across the call
sites or written into a prompt, there's nothing to assert on — you can only run it and judge by eye,
and it drifts when the model changes without anything going red. With a function returning data, the
whole specification is one line in the test: the first element's attention flag is `True`. The thing
I'd flag as unresolved is that a single function fixes where the decision lives, not whether it's
right — the right order depends on who's listening, and I'd take that as an argument rather than
forking the function."*

## Check yourself

Run the gate and read the fourth line of its output:

```bash
cd days/day-77-the-standup-agent/lab
uv run python gate.py; echo "exit: $?"
```

**Line by line:**

- `cd …/lab` — the gate imports `_state` as a sibling module, so it has to be run from inside `lab/`.
- `uv run python gate.py` — runs it against the project's pins. It contacts nothing and calls no
  model.
- `; echo "exit: $?"` — prints the exit code, which is `1` while any check is failing. Today every
  check fails, because `sutra/standup.py` is the build brief and you have not written it yet. The
  fourth line — *what needs a person is said first* — is the one this part is about, and it will go
  green only when your `lines(queue, night)` returns a list whose first pair carries `True`.

Two exercises.

1. Write the smallest `sutra/standup.py` that turns the fourth check green, then break it on purpose
   in two different ways and predict the gate's output before running it each time. First, make
   `lines` print the sentences and return `None`. Second, make it return the pairs in the queue's
   own order. Which failure is caught by which check, and which of the two would you have noticed by
   reading the standup out loud?
2. Take the flag out of the tuple: return plain strings and have the caller decide which sentence is
   important by looking for a phrase in the text. Get the fourth check passing again that way. Then
   go and read part 2.2 and work out what you have just built.
