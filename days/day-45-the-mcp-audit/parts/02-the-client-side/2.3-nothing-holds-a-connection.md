# 2.3 — A03: nothing holds a connection

## One-line answer

`A03` walks the top level of every module under `sutra/mcp/` and fails any assignment whose value is a
call to a connector, because a session created at import time is a session created once, held forever,
and shared by everything that imports the module.

## The story

There are two free chairs left in the waiting room and you put your bag on one of them, because your
friend is parking and will be up in a moment.

For the next stretch, that chair is not available to anybody. People come in, look at it, look at the
bag, and stand. The chair is doing no work at all. It is not empty, in the sense that it cannot be
used, and it is not occupied, in the sense that nobody is sitting in it.

Then your friend messages to say the car park is full and they are going home.

Now the chair is worse than useless. It is being kept for somebody who is not coming, and the only
person who knows that is you, and you have stopped thinking about the chair. It stays reserved until
somebody eventually moves the bag, and every person who stood in the meantime stood for nothing.

The cost was never the chair. It was that a thing which should have been decided fresh each time —
*who sits here now* — was decided once, early, on the strength of an assumption that later stopped
being true, and nothing in the room was set up to notice.

## The idea in plain language

A **connection** to an MCP server is a live object: a process on the other end of a pipe, or an open
HTTP session, with buffers and a lifetime. Creating one is not free, which is exactly why the tempting
thing is to create it once, at the top of a module, and reuse it.

```text
SESSION = ClientSession()
```

That single line makes four commitments, and none of them was written down:

**It is created at import time**, before anything is configured and before anyone has decided to use
it. If the server is not running, the import fails — and an import failure surfaces as
`ModuleNotFoundError`-shaped noise a long way from the actual cause.

**It is shared.** Every module that imports this one gets the same object, including concurrent
requests. Whatever state it accumulates, they accumulate together.

**It is never replaced.** When the server behind it goes away — and Day 43 made "goes away" ordinary,
because a deploy-shaped server is replaced routinely — the object stays. Later calls fail against a
socket to a process that no longer exists.

**It cannot be tested.** A test cannot substitute a fake, because the object was built the moment the
module was imported, which was before the test ran.

Day 32's
[2.1 — The call that remembered you](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.1-the-call-that-remembered-you.md)
described the protocol-level version of this shift: the 2026-07-28 revision removed the held session
from MCP entirely, and every request is now self-contained. `A03` is that architecture pointed at your
own client code. **The protocol stopped holding a session; a module-level connector puts one back.**

The rule: no module-level binding under `sutra/mcp/` whose value is a call to a connector. Connections
are made where they are used and released when the work finishes.

## Why Sutra needs it

Because Day 44's `sutra/mcp/hardening.py` carries "no held connections" as one of its three rules, and
a rule with no check is a preference.

The concrete consequence is a failure that only ever appears against a real deployment. Day 43 made
`sutra_mcp/app.py` the deploy-shaped entry point: any instance answers any request, instances come and
go. That property is the whole argument for the stateless core, and it is *entirely wasted* on a client
that pinned itself to one instance at import. The first time that instance is replaced, every
subsequent call from this process fails, and restarting the process fixes it — which is the worst
diagnostic signature there is, because it teaches everybody that restarting is the fix.

It also breaks Day 38's failure lab retrospectively. `tests/test_mcp_failures.py` drives the client
against a deliberately broken fake server, and it can only do that if the client can be handed a
different connection. A module-level session means the test is driving whatever the import created.

## The mechanism

```python
# tools/mcp_audit.py
CONNECTORS = {
    "connect_stdio",
    "connect_http",
    "ClientSession",
    "stdio_client",
    "streamablehttp_client",
}


def check_held_connections(root: Path) -> list[Finding]:
    """A03 no held connections: nothing module-level holds an open session."""
    client = root / "sutra" / "mcp"
    if not client.exists():
        return [_missing("A03", "sutra/mcp/", "day 33")]
    findings = []
    for path in _py_files(client):
        tree = _parse(path)
        if tree is None:
            continue
        for node in tree.body:
            if not isinstance(node, ast.Assign) or not isinstance(node.value, ast.Call):
                continue
            fn = node.value.func
            name = fn.id if isinstance(fn, ast.Name) else getattr(fn, "attr", "")
            if name in CONNECTORS:
                findings.append(
                    Finding("A03", "block", path.as_posix(), f"module-level {name}() is held open")
                )
    return findings
```

**Line by line:**

- `CONNECTORS` holds the two names Day 33 gave `sutra/mcp/client.py` — `connect_stdio` and
  `connect_http` — plus the three from the `mcp` library underneath them. Both layers are listed
  because the shortcut can be written at either.
- `for node in tree.body` — **the module's top level only**, not `ast.walk`. This is the one check in
  the module that deliberately does *not* walk the tree, and the reason is the whole rule: a
  `ClientSession()` inside a function is correct and normal. Only a binding at module level is held
  open. Walking here would turn a precise rule into a check that fires on every correct call site.
- `isinstance(node, ast.Assign)` catches `SESSION = ...` and `A = B = ...`. It does **not** catch
  `SESSION: ClientSession = ClientSession()`, which is an `ast.AnnAssign` — a real gap, and the kind
  worth knowing about rather than papering over, because an annotated module-level connector is exactly
  what a careful person writes.
- `node.value.func` is the thing being called. `fn.id` handles a bare name, `getattr(fn, "attr", "")`
  handles an attribute access like `mcp.ClientSession()`. The `getattr` default of `""` means an
  unusual callable — a subscript, a lambda — falls through to "not a connector" rather than raising.
- The message names the connector, so the reader knows which of the five was found without opening the
  file.
- The severity is `block` rather than `note`, and that is a judgement: a held connection is not a style
  issue, it is the client giving up the property the whole of Phase 6 was built to get.

The correct shape, for contrast — this is what the check is protecting:

```python
# sutra/mcp/client.py - the shape the rule leaves room for
async def call(name: str, args: dict[str, object]) -> str:
    """Open, ask, close. The connection lives for one call."""
    async with connect_stdio(LAUNCH) as session:
        return await with_timeout(session.call_tool(name, args), seconds=DEADLINE)
```

**Line by line:**

- `async with` — the connection is created inside the function and closed by the context manager on the
  way out, including when the body raises. That last part is why it is a context manager and not a
  `try`/`finally` somebody has to remember to write.
- `connect_stdio(LAUNCH)` appears **inside a function body**, which is why `A03` does not fire on it.
  `LAUNCH` at module level is fine: it is connection *parameters*, which are data, not a connection.
  The distinction between a description of a connection and an open one is the whole content of this
  rule.
- `with_timeout(...)` from Day 44 is here too, which is what keeps `A02` green in the same file. The two
  rules pull in the same direction: a short-lived connection with a deadline.
- The cost is real and should be said plainly: this opens a connection per call. For stdio that means
  starting a process, which is not cheap. **A pool is the professional answer** and it is a different
  thing from a held session — see *In production*.

## When it breaks

**The connector is annotated and the check misses it.** The gap named above, in the wild:

```text
SESSION: ClientSession = ClientSession()
```

`ast.AnnAssign`, not `ast.Assign`, so nothing fires. The fix is three characters of `isinstance`
tuple — and the reason it is left as a `TODO(me)` in the hub rather than written here is that finding
it yourself, by planting it in the fixture and watching the check stay green, teaches more than reading
the patched version.

**The connection is held one level down.** A module-level factory object with a `.session` attribute
populated on first use. No assignment at module level names a connector, so `A03` is green, and there is
still exactly one connection for the life of the process. This is the general limit of a static check on
a dynamic language, and the honest response is not a cleverer regular expression — it is a test that
asserts two calls do not share an object.

**The rule is right and the fix is wrong.** Somebody removes the module-level session and opens a fresh
stdio connection inside a loop that runs per ticket. The audit is green and the process is now spawning
a subprocess per iteration:

```text
OSError: [Errno 24] Too many open files
```

A connection per *call* is the teaching shape. A connection per call inside a hot loop is a different
problem, and the answer is a pool, not a comeback for the module-level session.

## In production

**What a professional writes instead:** a **pool** with a lifecycle — connections created lazily,
health-checked before handing out, retired after a maximum age or a failure, and closed on shutdown. A
pool looks superficially like the thing this rule forbids, and the difference is precise and worth being
able to state: a pool can throw a connection away and make another one, and a module-level global cannot.
Every property the rule is protecting — replaceability, testability, surviving a deploy on the other
side — is a property of "can be discarded", not of "is created per call".

**What degrades at scale:** connection setup cost becomes visible. Under stdio it is process creation;
under HTTP it is the TLS handshake. At low volume, per-call connections are free and correct. At high
volume they dominate, and the moment somebody notices, the tempting fix is the module-level global,
because it is one line and it works on the developer's machine. Teams that have been burned write the
pool the first time rather than the second.

**The failure mode that only appears with real traffic** is the half-open connection. The object is
still there, the socket still looks open, and the process on the other end died some time ago. Calls do
not fail fast; they hang until the deadline from
[2.2](2.2-every-call-carries-a-deadline.md) fires, and then the next call uses the same dead object and
hangs again. That is why a pool health-checks on **checkout** rather than on return, and why "the
connection object exists" is never evidence that the connection works.

**The review comment a senior engineer leaves:** *"This session is created at import. That means one
per process, shared across requests, never replaced when the server behind it is redeployed, and
impossible to stub in a test. If the cost of opening per call is the problem, say so and put in a pool
with a max age — a pool can drop a bad connection and this cannot."*

**The interview question:** *"Why not just keep one client connection open for the life of the
process?"* The honest spoken answer: *"Because you've then pinned yourself to one instance of something
that is designed to be replaced. Under the current MCP revision every request is self-contained
precisely so any instance can answer it, and a held session throws that away — the first redeploy on the
other side and every call from that process fails, restarting fixes it, and now everyone believes
restarting is the fix. It's also untestable, because the object was built at import before the test
existed. If setup cost is the real concern, the answer is a pool: it looks similar and it's the opposite
in the way that matters, because a pool can discard a connection and make a new one, and a global
can't."*
