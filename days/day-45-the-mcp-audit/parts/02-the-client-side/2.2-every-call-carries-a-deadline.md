# 2.2 — A02: every call carries a deadline

## One-line answer

`A02` reads every module under `sutra/mcp/` and fails any file that mentions `call_tool` or
`list_tools` without `with_timeout` in scope, because a call with no deadline is not slow — it is a
call that never returns an answer of any kind.

## The story

You ring the helpline about the electricity bill and they put you on hold.

The music loops. Every so often a recorded voice thanks you for your patience and says your call is
important. You have the phone against your ear and you are doing something else with your other hand,
and the thing you are doing is not going well because a quarter of your attention is on the music,
waiting for it to stop.

Here is the part worth noticing. At no point do you decide to keep waiting. There is no moment where
you weigh it up. The music simply continues and so do you, and forty minutes later you are still there,
and the reason you are still there is not that you judged it worth it — it is that you never set a
number before you started.

The person who says out loud, before dialling, *"ten minutes, then I go to the office in person"* has a
completely different afternoon. Not because ten minutes is the right number. Because there is a number,
so there is a moment where something else happens, and the thing that happens can be planned for.

The bad outcome of a call with no limit is not a long wait. It is that the waiting has no end you can
build anything around.

## The idea in plain language

A **deadline** is a number, decided by the caller, after which a call is abandoned and the failure is
handled. The words that matter are *by the caller*: the server cannot set your deadline, because the
server is the thing that might have stopped answering.

Day 44 built this into `sutra/mcp/hardening.py` as `with_timeout`, alongside `with_retries` and the
rule about not holding connections. This check is not the timeout; it is the rule that the timeout is
**not optional on any path**.

There is a specific asymmetry that makes a timeout different from most defensive code, and it is worth
stating because it decides how strict this rule should be. Most defensive code protects against
something going wrong. A missing timeout produces a failure with **no error at all**: no exception, no
status code, no log line, nothing to search for. The call is simply still open. Whatever was waiting on
it is still waiting, and if that thing is a request handler, its caller is waiting too, and so on
outward until something upstream has a deadline of its own and everybody finds out at once.

That is why the rule is written as *every path*, not *the important paths*. The one call site without a
deadline is the one that will hang, precisely because nobody thought about it hard enough to give it a
number.

The check is deliberately crude. It does not track which call is wrapped by which decorator; it asks
whether a module that calls out **has the wrapper in scope at all**. Crude on purpose, for two reasons:
tracking a wrapper through a call graph is a static-analysis project rather than a fifty-line check,
and the failure it is aimed at is not a subtle mis-wiring — it is a new module written in a hurry that
calls the server directly and imports nothing.

## Why Sutra needs it

Because Sutra's client is the thing that survives when a server does not, and Phase 6 spent a whole day
making that true.

Day 44 wrote `with_retries` and `with_timeout` in `sutra/mcp/hardening.py`. Day 43 made the server
deploy-shaped, which means any instance answers any request — and *"any instance"* includes an instance
that is being replaced while your call is in flight. The whole argument for statelessness is that a
dying instance costs one request rather than a session, and that argument only holds if the client
notices the request died. Without a deadline, a call to an instance that went away does not fail. It
waits.

Day 39 sharpens it further. `sutra_mcp/db_tools.py` runs SQL, and a query against a table that grew can
take an unbounded amount of time without anything being broken at all. That is the case where the
server is healthy, responsive, and simply not finished — and where a client with no deadline holds a
worker for as long as the query takes.

## The mechanism

```python
# tools/mcp_audit.py
def check_deadlines(root: Path) -> list[Finding]:
    """A02 deadlines: a module that calls out imports the deadline wrapper."""
    client = root / "sutra" / "mcp"
    if not client.exists():
        return [_missing("A02", "sutra/mcp/", "day 33")]
    findings = []
    for path in _py_files(client):
        text = path.read_text(encoding="utf-8")
        if "call_tool" not in text and "list_tools" not in text:
            continue
        if "with_timeout" not in text:
            findings.append(
                Finding("A02", "block", path.as_posix(), "calls out with no with_timeout in scope")
            )
    return findings
```

**Line by line:**

- The scope is `sutra/mcp/` and only that. Everywhere else in `sutra/` is already covered by `A01`,
  which forbids reaching out at all — the two rules are the inside and the outside of the same line,
  and neither is complete alone.
- `path.read_text` rather than `ast.parse`, and this is the one check in the module that works on text
  instead of a syntax tree. The reason is honest rather than principled: the question is *"is this name
  anywhere in this file"*, and a syntax tree buys nothing for that. Where a check needs to know
  **where** a name is — `A03`, `A05`, `A07` — it parses.
- `encoding="utf-8"` explicitly. Without it, Python uses the platform default, which on Windows is
  still not UTF-8 in every configuration, and a check that raises `UnicodeDecodeError` on one machine is
  worse than one that is merely crude.
- The `continue` on files that mention neither call is what stops this rule from demanding a timeout in
  `sutra/mcp/__init__.py`. A module that does not call out needs no deadline, and a rule that fires on
  files it has no business judging teaches people to ignore it.
- `"with_timeout" not in text` matches the import, the decorator and any mention in a comment. Matching
  a comment is a genuine weakness and it is the acceptable half of the trade: the false **negative** —
  a file that names the wrapper in a docstring and never applies it — is possible, and the false
  positive is not. This check is a floor, not a proof, and the *In production* section below says what
  replaces it.
- The message says *"in scope"* rather than *"imported"*, because that is precisely what was checked.
  A message that claims more than the code established is how a check loses the reader's trust the
  first time somebody looks at the source.
- `_missing("A02", "sutra/mcp/", "day 33")` — the day number is in the finding so that a filed finding
  carries its own destination ([1.2](../01-what-an-audit-is/1.2-a-finding-is-the-audit-working.md)).

The red case. A module in the fixture tree calls the server and imports nothing from `hardening`:

```python
# a scratch copy of sutra/mcp/client.py - the module written in a hurry
from mcp import ClientSession

SESSION = ClientSession()


async def call(name: str, args: dict) -> str:
    return await SESSION.call_tool(name, args)
```

**Line by line:**

- `await SESSION.call_tool(...)` with nothing around it. In the good state this is
  `await with_timeout(SESSION.call_tool(name, args), seconds=...)`, and the difference between the two
  lines is invisible in review unless somebody is looking for it — which is the entire argument for a
  check.
- This same file also violates `A03`, because `SESSION` is created once at module level and held. Two
  rules firing on one file is normal and useful: they are different mistakes that happen to be made by
  the same person in the same afternoon.
- Nothing here raises, logs or times out. If the server behind `SESSION` stops answering, this coroutine
  never completes, and the only symptom anywhere in the system is that something upstream got quieter.

Measured on 2026-09-05 against the fixture:

```text

  [A03] block sutra/mcp/client.py: module-level ClientSession() is held open
```

## When it breaks

**The timeout is set and it is longer than the thing waiting for it.** The client waits sixty seconds;
the request handler in front of it waits thirty. The client's deadline is never reached, so it never
runs its own error path, and the failure surfaces one layer up as a handler timeout with no
information about which call was slow. The rule of thumb is that deadlines shrink as you go inward, and
a call whose deadline exceeds its caller's is a deadline that does not exist.

**The timeout fires and the error is swallowed.** The wrapper is present, so `A02` is green, and the
call site looks like this:

```text
except TimeoutError:
    return ""
```

Now a hung server is indistinguishable from a server that answered with nothing, and the model is told
the ticket has no body. This is Principle 10 exactly, and `A07`
([3.3](../03-the-server-side/3.3-every-tool-has-a-path-that-raises.md)) is the rule that catches the
same shape on the server side.

**The retry makes it worse.** `with_retries` around a call with a long timeout turns one hung request
into three, sequentially, and the total wait is now three times a number nobody chose deliberately.
Day 44's ordering — the timeout inside, the retry outside, and the retry budget counted against the
outer deadline — is what makes the pair safe, and neither `A02` nor any other static check can verify
it. That one is read by a person.

## In production

**What a professional writes instead:** the deadline is not per call, it is per **request**, and it
travels. One number is set when work arrives, and every downstream call gets whatever is left of it
rather than a fresh timeout of its own. That is what "deadline propagation" means, and it is the
difference between a system where a slow dependency costs one request and one where it costs a
thread pool. The check for it also changes shape: instead of asking whether a wrapper is imported, you
assert in a test that a call made with an already-expired deadline fails immediately rather than
running.

**What degrades at scale:** timeouts that were generous become the system's slowest path. A ten-second
deadline is invisible while everything answers in fifty milliseconds and becomes the dominant latency
the day one dependency degrades, because every caller now waits the full ten before giving up. Teams
that have been through this set deadlines from measured percentiles rather than from round numbers, and
alarm on the **rate of deadline expiry** rather than on latency, because the expiry rate moves first.

**The failure mode that only appears with real traffic** is the retry storm. A dependency slows down,
every client's timeout fires, every client retries, and the additional load is what finishes the
dependency off. The system was stable at one request per call and unstable at three, and nothing in any
one client looks wrong. The countermeasures — jitter, a retry budget as a fraction of total traffic,
and a circuit breaker that stops retrying once the failure rate crosses a line — all live in the client
library, which is precisely why Day 44 put them in one module rather than at each call site.

**The review comment a senior engineer leaves:** *"This call has no deadline. I know the server is ours
and it's fast; that's not the point. Without a number this can't fail, it can only stop, and a request
that stops holds everything behind it. Give it a timeout, and tell me what happens in the except
branch — if the answer is that we return an empty string, we've built something worse than a hang."*

**The interview question:** *"What's the first thing you add to a client that calls a remote service?"*
The honest spoken answer: *"A deadline, before retries and before anything clever. A call without one
doesn't fail slowly, it fails in a way that produces no signal at all — no exception, no status, nothing
to search the logs for — and whatever was waiting on it is now waiting too, all the way up. Then
retries, and the ordering matters: the timeout goes inside so each attempt is bounded, and the retry
budget comes out of the outer deadline so three attempts can't quietly triple the worst case. The
subtlety I'd raise unprompted is that deadlines have to shrink inward. If my client waits longer than
the handler in front of it, my timeout is decoration — the caller gives up first and I never run my own
error path."*
