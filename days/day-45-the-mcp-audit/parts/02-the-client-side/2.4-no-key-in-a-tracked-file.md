# 2.4 — A04: no key in a tracked file

## One-line answer

`A04` asks `git` which files are tracked, reads the code trees among them, and fails on anything shaped
like a provider key — and it deliberately does not read `days/`, because a check that fires on its own
documentation is a check somebody switches off.

## The story

The spare key lives under the mat, and everybody in the family knows it.

That was fine for years. Then somebody sends a photo to the family group — the new plant by the door,
the mat, the corner of the key showing. Six people see it. One of them forwards it to a cousin who was
asking about the plant. Nobody involved has done anything wrong, and nobody could now list every phone
that photo is sitting on.

Here is the part that catches people out. Deleting the message does not fix it. It is on the cousin's
phone, and in somebody's automatic backup, and in a chat export. **The only thing that actually restores
the situation is moving the key** — after which every copy of the photo is a picture of a place where
the key is not.

The lesson is not about being careful with photos. It is that once a secret has been copied by a system
that keeps copies, the fix is never at the copy. It is at the secret.

## The idea in plain language

Principle 9 has been in this repository since Day 1: **secrets never touch git.** Keys live in `.env`,
`.env` is in `.gitignore`, and the repository is going public in Phase 14, so the discipline is real
rather than theoretical.

A key that reaches a commit is not removed by a later commit that deletes the line. Git keeps the
history, so the key is still there, reachable by hash, and it is in every clone anybody made in between.
The revision-control system is doing precisely what it is for. **The only real fix is to rotate the key
at the provider**, after which every copy of it — in the history, in a clone, in a fork — is a string
that opens nothing. Deleting the line is worth doing afterwards, for tidiness, and it is not the fix.

`A04` is a **late** defence. Three earlier ones already exist and are better: `.gitignore` stops the file
being staged, a pre-commit hook stops the commit, and reading the diff stops the human. This one runs in
`./m check`, after the fact, and its honest job is to catch the case where all three failed — which is
usually a key pasted into a Python file "just to test something" rather than a `.env` that slipped
through.

Two design decisions in it are worth more than the regular expressions.

**It asks `git` what is tracked, rather than walking the tree.** Files git ignores are not the
repository's problem — `.env` is *supposed* to sit in the working directory with a real key in it, and a
check that walked the filesystem would report it on every run, correctly and uselessly, until somebody
turned the check off.

**It reads code trees, not `days/`.** This is a deliberate blind spot with a real cost, and it exists
because Day 31's
[3.3 — The alarm that fires on toast](../../../day-31-the-quality-gate/parts/03-the-free-suffix-lint/3.3-the-alarm-that-fires-on-toast.md)
made the argument better than it can be made again: a smoke alarm that goes off every time somebody
makes breakfast is taken down, and after that it does not detect fires either. Teaching documents are
full of strings that look like keys because they are *examples of keys*. Scoping the check to code is
what keeps it running.

## Why Sutra needs it

Because Phase 5 and Phase 6 multiplied the number of places a credential can be typed.

Before Day 33 there was one kind of secret in this project: a model provider key, read by
`sutra/config.py` from `.env`. Since then there are three more shapes. Day 37 added auth on both sides —
`sutra_mcp/auth.py` validates an issuer, `sutra/mcp/auth.py` handles a token on the client. Day 39 added
a database, and a database has a connection string, and a connection string is a credential wearing a
URL's clothes. Day 40's `ServerPolicy.launch` carries how a server is started, and the tempting place to
put an environment variable's value is right beside the command that needs it.

And the repository goes public. That is not a Phase 14 problem; it is a today problem, because the
history goes public with it. A key committed on Day 39 and deleted on Day 40 is still in the history that
gets published, and the only way to make it harmless is to have rotated it.

## The mechanism

```python
# tools/mcp_audit.py
KEY_SHAPES = (
    re.compile(r"AIza[0-9A-Za-z_\-]{35}"),
    re.compile(r"gsk_[A-Za-z0-9]{40,}"),
    re.compile(r"sk-or-v1-[a-f0-9]{48,}"),
    re.compile(r"(?:API_KEY|SECRET|TOKEN)\s*=\s*[\"'][A-Za-z0-9_\-]{24,}[\"']"),
)

SECRET_ROOTS = ("sutra", "sutra_mcp", "tools", "tests", "scripts")


def check_secrets(root: Path) -> list[Finding]:
    """A04 secrets: no key-shaped literal in a tracked code file."""
    try:
        tracked = subprocess.run(
            ["git", "ls-files", *SECRET_ROOTS],
            cwd=root,
            capture_output=True,
            text=True,
            check=True,
        ).stdout.split()
    except (subprocess.CalledProcessError, FileNotFoundError):
        return [Finding("A04", "block", "git", "git ls-files failed - cannot list tracked files")]
    findings = []
    for name in tracked:
        path = root / name
        if path.suffix not in {".py", ".toml", ".md", ".txt", ""}:
            continue
        try:
            text = path.read_text(encoding="utf-8")
        except (UnicodeDecodeError, FileNotFoundError):
            continue
        for line_no, line in enumerate(text.splitlines(), start=1):
            for shape in KEY_SHAPES:
                if shape.search(line):
                    findings.append(
                        Finding("A04", "block", f"{name}:{line_no}", "key-shaped literal")
                    )
                    break
    return findings
```

**Line by line:**

- The first three patterns are the **published prefixes** of the three providers Addendum 02 names, with
  a length floor on the part that follows. A prefix plus a length is a far better signal than entropy
  scoring, because it produces almost no false positives and it is readable by the person who has to
  decide whether a finding is real.
- The fourth pattern is the generic one and it is the one that will misfire: an assignment to a name
  containing `API_KEY`, `SECRET` or `TOKEN` with a long literal on the right. The `{24,}` floor is what
  keeps it off `TOKEN = "abc"` in a test. **The floor is a `TODO(me)`** — it is the dial between missing
  a short credential and firing on a long test fixture, and where you set it depends on what your tests
  actually contain.
- `subprocess.run(["git", "ls-files", *SECRET_ROOTS], ...)` — the argument list form, never a shell
  string. There is no shell to quote for, so a path with a space in it cannot break the command, and
  nothing here can be turned into shell injection by a filename.
- `cwd=root` rather than relying on where the process happens to have been started, so the check gives
  the same answer from any directory.
- `check=True` turns a non-zero `git` exit into an exception, which the `except` converts into a
  **finding**. That is the rule from [1.1](../01-what-an-audit-is/1.1-the-list-is-written-before-you-look.md)
  applied to the check's own failure: *"I could not look"* is a result the gate must hear, not a reason to
  return an empty list. `FileNotFoundError` is in the same clause because it is what a missing `git`
  binary raises.
- The suffix filter keeps the check off binary files. The empty string in that set is for extensionless
  tracked files — the `m` driver is one — which are exactly where a launch command with an inline
  credential would live.
- `except UnicodeDecodeError: continue` — an image or a lockfile that slipped past the suffix filter is
  skipped rather than crashing the run. This is the one place in the module where a swallow is right, and
  the reason is that the alternative is an audit that cannot complete because somebody committed a PNG.
- `enumerate(text.splitlines(), start=1)` so the finding carries a **line number**. `where` as
  `path:lineno` is what makes a finding actionable from the output alone, and it is the format editors
  and terminals turn into a clickable link.
- The inner `break` reports one finding per line rather than one per matching pattern. A key that matches
  two patterns is still one key.

The red case, in the fixture tree — a config module somebody wrote to get past an authentication problem:

```text
GROQ_KEY = "gsk_<forty-plus characters of the real key>"
GOOGLE = "AIza<thirty-five more characters>"
```

Measured on 2026-09-05:

```text
  [A04] block sutra/config_local.py:1: key-shaped literal
  [A04] block sutra/config_local.py:2: key-shaped literal
```

Two lines, two findings, each with a line number. Note what the message does **not** do: it does not
print the key. An audit that echoes the secret it found has copied it into a build log, which is a
system that keeps copies.

And against this repository as it stands:

```text
ok  A04 secrets              no key-shaped literal in a tracked code file
```

That green is real, and it is narrow. It means no tracked file under those five directories contains a
string matching those four shapes. It says nothing about `days/`, nothing about untracked files, and
nothing about a credential in a shape no pattern here knows.

## When it breaks

**The key is in the history and not in the working tree.** `git ls-files` lists what is tracked *now*, so
a key committed on Tuesday and deleted on Wednesday is invisible to this check from Wednesday onward —
and it is still published when the repository goes public. This is the single most important limitation
of the rule and it cannot be fixed by improving the patterns. The tools for it scan the whole history,
and the response to a hit is always the same: rotate first, rewrite the history second, if at all.

**The key does not look like a key.** A database connection string:

```text
DB_URL = "postgresql://sutra:<password>@10.0.0.4:5432/tickets"
```

No prefix from the list, no assignment to a name containing `SECRET`. Nothing fires, and a password has
just been committed. Adding a URL-with-credentials pattern is a genuine improvement and it is left as a
`TODO(me)` because the interesting part is not the regular expression — it is noticing that the
categories you enumerated are the only ones you will ever catch.

**The check fires on a test fixture and somebody deletes the check.** A test that needs a realistic key
shape gets one, the audit reports it, and the pressure is to weaken the pattern. The right fix is the
opposite direction: keep the pattern and make the fixture obviously fake — a string that begins with the
right prefix and continues `xxxxxxxx` fails the length floor by design, and if it does not, the fixture
should be generated at test time rather than typed into a file.

## In production

**What a professional writes instead:** secret scanning runs on the whole history at the forge, and the
provider is wired in so that a leaked key is **revoked automatically** rather than reported. That
automatic revocation is the part worth internalising, because it is the only response that scales: a
report tells a human to rotate, and humans are slow at three in the morning; a revocation makes the leak
worthless before anyone reads the alert. Alongside it, secrets are injected at runtime from a manager
rather than read from a file at all, so there is no file for a scanner to find.

**What degrades at scale:** the false-positive rate, and always in the same way. In a large repository,
generic patterns match test data, base64-encoded fixtures and example documentation, and the team's
response is a suppression file. Suppression files grow and are never pruned, so within a year the scanner
is running against a set of exclusions nobody has read. The countermeasure is to prefer prefix-based
patterns for real providers and to keep exactly one generic pattern, tuned so it almost never fires.

**The failure mode that only appears with real traffic** is the key in a log. Nothing was committed. A
tool call was logged with its arguments, one argument was a token, and it is now in a log aggregator with
a ninety-day retention and a much wider read permission than the repository has. Sutra's own defence
against this is not here — it is the redaction that Day 22's structured logging and Day 40's boundary
plugin are the right places for, and it is worth naming here because a repository that is clean and a
system that leaks nothing are different claims.

**The review comment a senior engineer leaves:** *"This is a real key in a tracked file. Rotate it at the
provider now, before you touch this branch — removing the line does not remove it from the history, and
this repository is going public. Then read it from `.env` like everything else, and tell me why the
pre-commit hook did not catch it, because that is the actual failure here."*

**The interview question:** *"You find an API key committed to a repository. What do you do, in order?"*
The honest spoken answer: *"Rotate it first. Not remove it, not rewrite the history — rotate, because the
moment it was pushed you lost control of every copy, and the only action that makes those copies harmless
is invalidating the credential. Then work out the blast radius: what could that key reach, and check the
provider's access logs for use you cannot account for. Then clean up — remove it from the working tree,
decide with the team whether rewriting the history is worth the disruption, and it usually isn't once the
key is dead. And last, the part that actually matters: find out why it got in. A scanner in the build is
a backstop, and if that's the thing that caught it, the pre-commit hook and the review both missed, so
that is the gap I'd fix."*
