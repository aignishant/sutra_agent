# 3.3 — A07: every tool has a path that raises

## One-line answer

`A07` finds every exception handler under `sutra_mcp/` and fails the ones that return a value without
raising anything, because a tool that answers an error with a plausible empty result has told a model
something false and left nothing behind to find.

## The story

The cash machine takes the card, whirs, and prints a slip.

The slip says the transaction was successful. There is no cash. You stand there for a moment doing the
thing everybody does, which is looking into the slot as if the notes are further back, and then you read
the slip again, because the slip is the only source of information available and it is unambiguous.

Now consider what you can actually do. If the machine had said *"unable to dispense — transaction
cancelled"*, you would go to the counter, mildly annoyed, and it would be sorted out there. Instead you
have a piece of paper asserting that you were paid. The person at the counter has a record saying the
same. Sorting this out is now a dispute rather than a problem, and it takes days, and for the whole time
your evidence and theirs agree — and both are wrong.

The failure was never that the machine could not dispense. Machines run out. The failure is that it
**reported success it had not achieved**, and by doing so it destroyed the one thing everybody needed,
which was a shared, accurate account of what happened.

## The idea in plain language

Principle 10 has been in this repository since Day 1: **fail honestly.** Errors surface, escalate, and are
logged. Never fabricate a result to cover an error.

Day 21 spent a whole day on it. Its
[5.1 — One policy, not a hundred](../../../day-21-errors-surface-not-swallow/parts/05-in-production/5.1-one-policy-not-a-hundred.md)
made the specific argument that error policy belongs in one place, because the same policy written into
eleven tools becomes ten policies and a mistake. `A07` is that principle pointed at the server side of the
boundary, where the consequence is sharper than usual for a reason worth spelling out.

An ordinary function that swallows an exception returns a wrong value to code, and code tends to notice —
an empty string flows onward and something downstream raises. **A tool that swallows an exception returns a
wrong value to a model**, and a model does not notice. It reads *"the ticket body is empty"* as a fact
about the ticket, tells the user the ticket has no description, and does it fluently. There is no
traceback, no status code, and no log line, because the code that would have produced them was replaced by
a `return`.

The pattern the check looks for is exactly this:

```text
try:
    ...
except SomeError:
    return ""
```

A handler with a `return` and no `raise` anywhere in it. The good shapes all keep a raise in the path:
re-raise as a protocol error, wrap in an `McpError` with a real code, log and re-raise, or return a value
that is *explicitly an error* rather than a plausible answer.

One clarification, because the rule sounds stricter than it is. `A07` does not forbid handling errors. It
forbids handling them by producing a normal-looking answer. A handler that catches a database timeout,
logs it, and raises a protocol error with `-32603` is doing exactly what it should, and passes.

## Why Sutra needs it

Because Day 35 already found the protocol doing this to us, and the response cannot be to do it to
ourselves.

Day 35's
[2.3 — The miss that must be an error](../../../day-35-resources-and-prompts/parts/02-the-shelf/2.3-the-miss-that-must-be-an-error.md)
measured what happens when a resource read fails on the pinned SDK. The error arrives at the client as
`code=0` — not the `-32602` the specification calls for, with the `data` payload gone and the message
buried in a doubled prefix — because a handler two frames inside the library catches a broad exception and
hard-codes the code. That is a swallow performed by somebody else's code, it is a known finding, and it is
filed rather than fixed because the fix is a version bump
([7.3](../07-the-phase-gate/7.3-the-pin-and-the-amendment.md)).

Living with that makes this rule *more* important, not less. When the transport already degrades error
information, a tool that discards it before it reaches the transport leaves nothing at all.

There is a second reason, specific to Phase 6. Day 39 put real SQL behind these tools. A query can fail for
reasons that have nothing to do with the request — a lock, a disk, a migration mid-flight — and every one
of those is temporary. A tool that returns `""` on a database error tells the model there are no results,
and the model reports that there is no such ticket, and the ticket exists.

## The mechanism

```python
# tools/mcp_audit.py
def check_error_paths(root: Path) -> list[Finding]:
    """A07 error paths: no handler under `sutra_mcp/` returns instead of raising."""
    server = root / "sutra_mcp"
    modules = _py_files(server)
    if not any(p.name != "__init__.py" for p in modules):
        return [_missing("A07", "sutra_mcp/*.py", "day 34")]
    findings = []
    for path in modules:
        tree = _parse(path)
        if tree is None:
            continue
        for node in ast.walk(tree):
            if not isinstance(node, ast.ExceptHandler):
                continue
            where = f"{path.as_posix()}:{node.lineno}"
            if node.type is None:
                findings.append(Finding("A07", "block", where, "bare except"))
                continue
            body = list(ast.walk(node))
            raises = any(isinstance(n, ast.Raise) for n in body)
            returns = any(isinstance(n, ast.Return) for n in body)
            if returns and not raises:
                findings.append(Finding("A07", "block", where, "handler returns without raising"))
    return findings
```

**Line by line:**

- `ast.ExceptHandler` is the node for one `except` clause. A `try` with three `except` branches produces
  three of them, judged separately, which is right — one branch re-raising does not excuse another
  returning.
- `node.type is None` is a **bare `except:`**, and it is reported without looking at the body at all,
  because a bare except catches `KeyboardInterrupt` and `SystemExit` along with everything else. `ruff`
  already flags this under `E722`, and the duplication is deliberate: the audit's output is what somebody
  reads at a gate, and a rule that quietly relies on a different tool having been run is a rule with a
  hidden dependency. `A09` ([4.2](../04-the-policy/4.2-a-rule-with-one-owner.md)) is where that tension
  gets resolved properly.
- `continue` after the bare-except finding, so one handler produces one finding rather than two.
- `list(ast.walk(node))` descends into the **whole** handler body, including inside an `if`. That matters:
  the common real shape is a handler that raises in one branch and returns in another, and walking is what
  sees both.
- `raises and returns` is checked as *returns and not raises* — a handler that does both is passed. That is
  a deliberate false negative: `if retryable: raise; return fallback` is a legitimate design, and a rule
  that failed it would be arguing about policy rather than checking for a swallow.
- A handler that returns **nothing** — logs and falls through — is not reported either. Falling out of a
  handler continues after the `try`, which is a different pattern with different problems, and the rule is
  aimed at the specific one where a fabricated value goes back to a model.
- `where` carries the handler's line number, not the function's, because a long tool can have several and
  the reader needs the branch.

The red case:

```python
# a scratch copy of sutra_mcp/server.py - the handler that reports success
@server.tool()
def lookup_ticket(ticket_id):
    try:
        return CACHE[ticket_id]
    except KeyError:
        return ""
```

**Line by line:**

- `except KeyError: return ""`. The intention was kind — a missing ticket should not crash the server —
  and the effect is that "this ticket does not exist" and "this ticket has an empty body" become the same
  answer.
- The model receives an empty string with no indication that anything went wrong, and the fluent thing to
  say next is that the ticket has no description. Nothing in any log contradicts it.
- The good version raises. On the pinned SDK that means accepting Day 35's `code=0` degradation on the way
  out, which is still strictly better than silence: the client sees an error, the retry policy from Day 44
  can act on it, and the failure is in the trace.
- The smallest honest fix is two lines: `raise ValueError(f"no ticket {ticket_id}")`, and a docstring line
  saying the tool raises when the ticket is unknown — so the *description* from
  [3.2](3.2-every-tool-says-what-it-takes.md) tells the model that an error is a possible outcome.

Measured on 2026-09-05 against the fixture:

```text
  [A07] block sutra_mcp/server.py:11: handler returns without raising
```

And against this repository as it stands:

```text

```

## When it breaks

**The swallow is in a decorator and the check never sees it.** A `@safe_tool` wrapper that catches
everything and returns a default. Each tool body is clean, `A07` is green, and every tool swallows. This is
the recurring limitation of a form-based rule, and the honest complement is a test that calls a tool with
an input guaranteed to fail and asserts an error comes back over the wire — not an empty result.

**The raise happens and the information is gone anyway.** `except Exception: raise ValueError("failed")`.
There is a raise, so the check passes, and the original exception has been discarded. In Python the fix is
one word — `raise ValueError("failed") from err` — and it is the difference between a traceback that names
the database error and one that says a tool failed. Worth knowing that `A07` cannot see this, and that
`ruff`'s `B904` can.

**The finding is real and the fix causes an outage.** Somebody removes a swallow that had been quietly
absorbing a routine, expected condition — a cache miss, a not-found on an optional lookup — and now every
one of those raises to the client and the retry policy hammers a server that is behaving correctly. The
lesson is that a swallow is often hiding a **missing distinction** rather than a missing raise: "not found"
and "could not look" are different answers, and the code had one branch for both.

## In production

**What a professional writes instead:** one error boundary per service, not one per tool. A middleware or a
decorator applied at registration converts exceptions into protocol errors with the right code, attaches a
correlation id, logs once with the traceback, and scrubs anything internal from the message that goes out.
Individual tools then raise domain exceptions and never think about the wire at all. That is Day 21's
one-policy argument made concrete, and it is also the shape that makes `A07` mostly redundant in a mature
codebase — the rule earns its place while the boundary is still being built.

**What degrades at scale:** the distinction between retryable and permanent errors. At low volume every
error is a human reading a log. At high volume, the client's behaviour is decided by the code it gets back:
a `-32602` means the argument was wrong and retrying is pointless, while a timeout means try again. A tool
that raises one generic error type for both makes correct client behaviour impossible, and the cost lands
on somebody else's service as a retry storm.

**The failure mode that only appears with real traffic** is the partial result. A tool that searches three
sources, has one fail, and returns the two it got — with no indication that a third existed. Nothing was
swallowed in a way any rule can see; a value was returned and it was not wrong, it was **incomplete**, and
the model presents it as the complete answer. Systems that care about this return the failures alongside
the results as data, so the caller can decide, which is the same instinct as returning findings rather than
a boolean.

**The review comment a senior engineer leaves:** *"This returns an empty string when the lookup fails.
That's not graceful, it's a lie the model will repeat in a sentence to a customer. Raise, and say in the
docstring that it raises when the ticket is unknown. If a missing ticket is genuinely a normal outcome
rather than an error, then it needs its own return shape that says so — what it must not be is
indistinguishable from a ticket with nothing in it."*

**The interview question:** *"Why is swallowing exceptions worse in an agent system than in ordinary
code?"* The honest spoken answer: *"Because the caller can't tell. In ordinary code a swallowed error
returns a wrong value to more code, and something downstream usually falls over, so you find out. In an
agent system the caller is a model, and it will take an empty result as a fact about the world and write a
confident sentence around it. There's no exception, no status, no log line — the code that would have
produced all three is what got replaced by the return. So my rule is that a tool either returns a real
answer or raises, and if 'not found' is a normal outcome it gets its own shape that is impossible to
confuse with an empty answer. The other half is doing it in one place — an error boundary at registration
rather than a try/except in every tool — because eleven copies of an error policy is ten policies and a
mistake."*
