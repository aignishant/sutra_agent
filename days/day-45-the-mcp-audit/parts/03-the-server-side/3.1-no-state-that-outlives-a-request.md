# 3.1 — A05: no state that outlives a request

## One-line answer

`A05` walks the top level of every module under `sutra_mcp/` and fails any assignment whose value is a
dictionary, a list, a set or a call that builds one, because a mutable module-level binding is state one
request leaves behind for the next — and the next request may be on a different instance.

## The story

The barber has two chairs and two barbers, and you have been going there for years.

You sit in whichever chair is free. The one on the left knows how you like it, because he has cut your
hair every time. Today the left chair is busy, so you sit on the right, and the man there asks how you
want it, and the honest answer is *"the same as last time"*, which tells him nothing at all.

You end up describing it, badly, and it comes out slightly wrong, and it is not his fault. He was never
told. The knowledge that made the left chair work was in one person's head, and it was never anywhere
else, and the shop only worked as long as you happened to get that chair.

The shop that solves this properly does something small and boring. There is a slip in your file: number
two on the sides, scissors on top, no parting. Either barber reads it, either chair works, and the shop
can hire a third man on Saturday without anything breaking. The knowledge did not get bigger. It moved
out of a head and into the thing that travels with the customer.

## The idea in plain language

**State** is anything a program remembers between one request and the next. A dictionary at the top of a
module is the simplest possible way to have some, and it is nearly always written for a good reason: a
cache, a counter, a registry of things in flight.

Day 32's
[3.4 — State that travels in the payload](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md)
explained what the 2026-07-28 revision did about this at the protocol level. State does not live in a
held session any more; it travels **inside the payload as an explicit handle**, so any server instance
can pick up any request. Day 43 turned that into `sutra_mcp/app.py`, the deploy-shaped entry point where
*any instance answers any request*.

`A05` is the rule that keeps the code honest about it. A module-level mutable binding is the left
barber's memory: it works perfectly while there is one instance and one process, and it fails the moment
there are two — not loudly, with an error, but by giving a **different answer depending on where the
request landed**.

Three shapes it takes, all of which this rule catches:

| The code | What it is for | What breaks with two instances |
| --- | --- | --- |
| `CACHE = {}` | avoiding repeated work | a hit on one instance, a miss on the other |
| `TASKS = {}` | Day 36's task handles | `tasks/get` on the wrong instance says the task does not exist |
| `SEEN = set()` | idempotency, deduplication | the same write applied twice |

The middle row is the dangerous one, because it is the one that looks most like it has to be a module
global. Day 36's `sutra_mcp/tasks.py` hands out a handle and the client polls for it, and the obvious
implementation is a dictionary. The correct implementation puts the task in shared storage and hands out
a key to it — the slip in the file, not the barber's memory.

What the rule permits, and why the distinction is exactly right: a module-level **constant** is fine. A
string, a number, a tuple, a frozen dataclass. Those are configuration, they are the same on every
instance, and no request can change them. The rule is not "no module-level names"; it is "nothing at
module level that a request can write to".

## Why Sutra needs it

Because Phase 6's central claim is that Sutra's server can be deployed as more than one instance, and
that claim is worth exactly as much as the code behind it.

Day 43 wrote the entry point. Day 44 hardened the client on the assumption that a dying instance costs
one request. Day 36 handed out task handles that a *later* request has to resolve. All three of those
are false if `sutra_mcp/` holds a dictionary, and the failure they produce is the worst kind: the system
works in development, where there is one process, and behaves erratically in production, where there are
three, with no error message anywhere.

There is also a smaller reason that shows up sooner. A module-level cache makes the test suite
order-dependent. `tests/test_mcp_failures.py` from Day 38 drives the server through several failure
scenarios, and a dictionary that survives between them means test three sees what test one left. That
surfaces as a test that passes alone and fails in the suite, which is a full afternoon for anyone who
has not seen it before.

## The mechanism

```python
# tools/mcp_audit.py
MUTABLE_CALLS = {"dict", "list", "set", "defaultdict", "Counter", "deque"}


def check_stateless_server(root: Path) -> list[Finding]:
    """A05 stateless server: no module-level mutable state under `sutra_mcp/`."""
    server = root / "sutra_mcp"
    modules = _py_files(server)
    if not any(p.name != "__init__.py" for p in modules):
        return [_missing("A05", "sutra_mcp/*.py", "day 34")]
    findings = []
    for path in modules:
        tree = _parse(path)
        if tree is None:
            continue
        for node in tree.body:
            if not isinstance(node, ast.Assign):
                continue
            value = node.value
            mutable = isinstance(value, ast.Dict | ast.List | ast.Set) or (
                isinstance(value, ast.Call)
                and isinstance(value.func, ast.Name)
                and value.func.id in MUTABLE_CALLS
            )
            if mutable:
                target = ast.unparse(node.targets[0])
                findings.append(
                    Finding("A05", "block", f"{path.as_posix()}:{node.lineno}", f"mutable {target}")
                )
    return findings
```

**Line by line:**

- `not any(p.name != "__init__.py" for p in modules)` is the emptiness test, and it is more careful than
  `if not server.exists()`. `sutra_mcp/__init__.py` has existed since Day 1 and is empty until Day 34, so
  a plain existence check would find the directory, find one file, find nothing wrong in it, and report
  green on a package that has not been written. **The check asks whether there is anything to audit**,
  not whether the folder is there — which is [6.1](../06-failure-lab/6.1-green-because-the-path-did-not-exist.md)'s
  failure, avoided one line at a time.
- `for node in tree.body` — module top level only, the same decision as
  [2.3](../02-the-client-side/2.3-nothing-holds-a-connection.md) and for the same reason: a dictionary
  inside a function is a local variable, which is the correct way to build one.
- `ast.Dict | ast.List | ast.Set` catches the literal forms — `{}`, `[]`, `{1, 2}`. The `X | Y` syntax in
  `isinstance` needs Python 3.10 or later; this repository is on 3.12, so it is available, and it reads
  better than a tuple.
- An empty `{}` parses as `ast.Dict` with no keys, which is exactly the case that matters. `CACHE = {}` is
  the canonical form of this bug.
- The `ast.Call` branch catches `dict()`, `defaultdict(list)`, `Counter()` — the same object built through
  a constructor. Without it, the rule is one autocomplete away from being bypassed accidentally.
- `isinstance(value.func, ast.Name)` before reading `.id`, because `collections.defaultdict(list)` has an
  `ast.Attribute` as its func and would raise otherwise. That form is a known gap: the check catches the
  imported name and misses the dotted one. It is in the hub as a `TODO(me)`.
- `ast.unparse(node.targets[0])` turns the assignment target back into source, so the message says
  `mutable CACHE` rather than `mutable Name`. `ast.unparse` handles tuple targets and subscripts too,
  which a hand-written formatter would get wrong on the first unusual assignment.
- `node.lineno` in `where`, so the finding is `path:line`. A module with several globals needs to say
  which one.
- **What this check deliberately does not do** is judge whether the mutation is safe. A module-level dict
  that is only ever read is harmless, and this rule fires on it anyway. That is the right trade for a
  fifty-line check: proving a global is never written means tracking every reference, and the false
  positive costs one conversation while the false negative costs a production mystery.

The red case, and it is worth reading as the reasonable code it is:

```python
# a scratch copy of sutra_mcp/server.py - the cache that makes the demo fast
from mcp.server.fastmcp import FastMCP

CACHE = {}
server = FastMCP("sutra-mcp")


@server.tool()
def lookup_ticket(ticket_id):
    try:
        return CACHE[ticket_id]
    except KeyError:
        return ""
```

**Line by line:**

- `CACHE = {}` is the whole finding. Somebody added it because the same ticket was being looked up three
  times in one conversation, which is a real observation and a real improvement — on one instance.
- `server = FastMCP("sutra-mcp")` does **not** fire, and should not. It is a call, but `FastMCP` is not in
  `MUTABLE_CALLS`, and a server object built at import is how the library is meant to be used. Whether
  *that* object holds request state is a different question, and it is one Day 34's `stateless_http=True`
  flag answers.
- The same file also fails `A06` — `ticket_id` has no annotation and the function has no docstring — and
  `A07`, because the handler returns instead of raising. Three rules on one seven-line function is not
  the rules being fussy; it is what a tool written quickly actually looks like.

Measured on 2026-09-05 against the fixture:

```text
  [A05] block sutra_mcp/server.py:3: mutable CACHE
```

And against this repository as it stands:

```text
  [A05] block sutra_mcp/*.py: target does not exist (built on day 34)
```

`sutra_mcp/__init__.py` is there and it is empty, and the check says so rather than passing.

## When it breaks

**The state moves into the server object and the check goes green.** Instead of `CACHE = {}` somebody
writes `server.cache = {}`, or stores it on a class attribute. Not an `ast.Assign` at module level with a
dict on the right, so nothing fires, and the state is exactly as shared as it was. This is the general
shape of every static check's limit: it recognises a *form*, and the bug is a *behaviour*. The complement
is a test — start two instances, write through one, read through the other — which is what Day 43 built
and what no amount of parsing replaces.

**The finding is correct and the fix is worse.** The dictionary is replaced by a module-level SQLite
connection, or a file. `A05` goes green because the value is not a dict, and there is now per-instance
state on the local filesystem, which is the same bug with worse failure modes — a container's disk is not
shared and does not survive a restart.

**Everything is green and the answers still differ between instances.** The state is in the model
provider's context, or in a temporary directory, or in an environment variable set at start-up. Green here
means one specific class of local state is absent. It does not mean the server is stateless, and the gap
between those two sentences is why the phase gate has six conditions and only one of them is a command
([7.1](../07-the-phase-gate/7.1-six-things-that-must-be-true.md)).

## In production

**What a professional writes instead:** shared state goes to something external and explicitly chosen —
Redis for ephemeral things with a TTL, a database table for anything that must survive — and the choice is
made per piece of state rather than once for the service. The habit that goes with it is to make
statelessness testable rather than assumed: run two instances in the test environment and put a
round-robin in front of them, so an accidental global fails a test rather than a deployment.

**What degrades at scale:** the cache-hit rate, in a way that looks like a caching bug and is not. With one
instance a cache warms up and stays warm; with twenty, each instance sees a twentieth of the traffic, so
each cache warms twenty times more slowly and the hit rate collapses. Nothing is broken. The design simply
assumed a request distribution that stopped being true, which is why a shared cache is a different
component from a local one and not a bigger version of it.

**The failure mode that only appears with real traffic** is the one that also corrupts data: a module-level
set used for idempotency. It works, deduplication succeeds, and then a second instance is added and the
same write is applied twice because the second instance has never seen the key. The symptom is duplicated
records with no error anywhere, and the cause is one line that was correct when it was written.

**The review comment a senior engineer leaves:** *"This dictionary is per-process. We run three of these,
and they get replaced on every deploy, so a request that writes here and a request that reads here will
frequently be talking to different copies. If this genuinely needs to be shared, put it in the database and
hand out a key; if it's only a cache, say so in the name and give it a TTL, so the next person doesn't
build something load-bearing on top of it."*

**The interview question:** *"What does it actually mean for a service to be stateless?"* The honest spoken
answer: *"That any instance can serve any request, so nothing a request needs is held only in the memory of
the process that handled the previous one. In practice the audit is boring: no module-level mutable
globals, nothing cached on the server object, nothing written to local disk. Anything genuinely shared goes
somewhere external and the request carries a handle to it. The reason I care isn't purity — it's that a
stateless service can be scaled and redeployed without anyone thinking about it, and the failure mode of
getting it wrong is horrible. There's no exception and no error, you just get a different answer depending
on which instance you landed on, and that reproduces about one time in three."*
