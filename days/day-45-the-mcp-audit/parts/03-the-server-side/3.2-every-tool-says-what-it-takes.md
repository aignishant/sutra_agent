# 3.2 — A06: every tool says what it takes

## One-line answer

`A06` finds every function under `sutra_mcp/` carrying a `@server.tool()`, `@server.resource()` or
`@server.prompt()` decorator and fails it if the docstring is missing or any parameter is unannotated,
because on the wire the docstring is the description and the annotations are the schema.

## The story

The jars on the kitchen shelf were labelled when they were bought, and then they were refilled.

Salt into the one that says coffee, because the coffee jar was the right size. Sugar into an old pickle
jar. Two identical steel containers with nothing on them at all, one of which is rice flour and one of
which is not.

The person who did the refilling can cook in that kitchen perfectly well. They know. The labels are
irrelevant to them, which is exactly why they stopped keeping them up to date — every day the labels were
wrong, nothing went wrong, so the labels were clearly not needed.

Then somebody else cooks. A cousin staying for a week, a neighbour helping out. They do the sensible
thing, which is to read the labels, and the labels are the most authoritative-looking wrong information
in the room. Nothing about their reasoning was careless. They were given a description of the shelf and
they used it.

The labels were never for the person who filled the jars. They were for everybody else, and there is
always eventually an everybody else.

## The idea in plain language

When you decorate a Python function with `@server.tool()`, the library reads three things out of it and
puts them on the wire:

| What the library reads | What it becomes on the wire | Who reads it |
| --- | --- | --- |
| the function name | the tool's `name` | the client, for routing and allowlists |
| the docstring | the tool's `description` | **the model**, when it decides whether to call this |
| the parameter annotations | the tool's `inputSchema` | the model, to build arguments; the server, to validate them |

That third column is the whole part. The docstring is not documentation in the ordinary sense — nobody
opens the file to read it. It is **the text a model uses to decide**, transmitted to a stranger's process,
and it is the only thing they have. Day 28's
[2.4 — The crowded shelf](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.4-the-crowded-shelf.md)
made the same argument for a skill's description and showed it decide routing; a tool description does the
identical job with less room.

The annotations are the other half. A parameter with no annotation produces a schema entry with no type,
which means the model is free to send anything and the server has agreed to accept it. That is not merely
untidy. It is the difference between a bad argument being rejected at the boundary with a clear error, and
a bad argument arriving inside your function where the failure will be a `TypeError` three frames deeper.

Day 34's
[3.1 — The list and who may keep it](../../../day-34-building-sutra-mcp-tools/parts/03-the-two-calls/3.1-the-list-and-who-may-keep-it.md)
showed the actual `tools/list` payload this produces. `A06` checks the source that generates it, because
checking the source is something a static tool can do on every commit and inspecting the payload requires a
running server.

## Why Sutra needs it

Because everything Sutra does about tool safety depends on the tool surface being described, and Day 40
built a whole policy module on top of that assumption.

`ServerPolicy.pinned` is a mapping from tool name to a hash of the description and schema a person read and
approved. A tool with no description hashes an empty string, so the pin certifies nothing, and the drift
check from Day 40's
[3.2 — The name held, the sentence moved](../../../day-40-filtering-and-allowlists/parts/03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)
cannot fire on a change from nothing to something. The audit rule is upstream of the policy: pinning is
worthless on a surface that is blank.

There is a second reason, and it is about how Sutra's own server will be used. Day 42 exposes the desk agent
over MCP, and the plan's Phase 5 material is explicit that any MCP host — an IDE, a partner's agent —
can call it. That is the cousin in the kitchen. The description is what they get.

## The mechanism

```python
# tools/mcp_audit.py
WIRE_DECORATORS = {"tool", "resource", "prompt"}


def _wire_functions(tree: ast.Module) -> list[ast.FunctionDef | ast.AsyncFunctionDef]:
    out = []
    for node in ast.walk(tree):
        if not isinstance(node, ast.FunctionDef | ast.AsyncFunctionDef):
            continue
        for dec in node.decorator_list:
            call = dec.func if isinstance(dec, ast.Call) else dec
            name = call.attr if isinstance(call, ast.Attribute) else getattr(call, "id", "")
            if name in WIRE_DECORATORS:
                out.append(node)
                break
    return out


def check_tool_schemas(root: Path) -> list[Finding]:
    """A06 tool schemas: every tool on the wire has a description and full annotations."""
    server = root / "sutra_mcp"
    modules = _py_files(server)
    if not any(p.name != "__init__.py" for p in modules):
        return [_missing("A06", "sutra_mcp/*.py", "day 34")]
    findings = []
    for path in modules:
        tree = _parse(path)
        if tree is None:
            continue
        for fn in _wire_functions(tree):
            where = f"{path.as_posix()}:{fn.lineno}"
            if not ast.get_docstring(fn):
                findings.append(Finding("A06", "block", where, f"{fn.name} has no description"))
            bare = [a.arg for a in fn.args.args if a.annotation is None]
            if bare:
                findings.append(
                    Finding("A06", "block", where, f"{fn.name} params unannotated: {bare}")
                )
            if fn.returns is None:
                findings.append(
                    Finding("A06", "note", where, f"{fn.name} has no return annotation")
                )
    return findings
```

**Line by line:**

- `WIRE_DECORATORS` holds the three registration decorators Days 34 and 35 use. The set is small and it is
  the reason this check knows the difference between a helper function, which needs nothing, and a function
  that is about to be described to a stranger.
- `dec.func if isinstance(dec, ast.Call) else dec` handles both spellings. `@server.tool()` is an
  `ast.Call` wrapping an `ast.Attribute`; `@server.tool` without parentheses is the attribute alone. Both
  appear in real code and the library accepts both.
- `call.attr` for `server.tool`, `getattr(call, "id", "")` for a bare imported `tool`. The `""` default
  means an unusual decorator — a subscript, a call on a call — is treated as "not a registration" rather
  than raising, which keeps one strange file from stopping the whole audit.
- `break` after the first matching decorator, so a function with two of them is collected once.
- `ast.walk` here, unlike `A03` and `A05`. Registration decorators legitimately appear on nested functions
  — a tool defined inside `register_resources(server)` from Day 35 is normal — so the check has to descend.
  **Each rule's traversal choice is part of the rule**, and it is worth noticing that three checks in this
  module make three different choices deliberately.
- `ast.get_docstring(fn)` rather than looking at `fn.body[0]` by hand. It handles the concatenated-string
  and `None`-body cases, and — importantly — it returns `None` for a function whose first statement is a
  bare expression that is not a string, which is the case a hand-rolled version gets wrong.
- `fn.args.args` covers positional and positional-or-keyword parameters. It **misses** keyword-only
  parameters, which live in `fn.args.kwonlyargs`. That is a real gap and it is left as a `TODO(me)`,
  because finding it by planting a keyword-only tool parameter in the fixture is a better lesson than
  reading the corrected line.
- `bare` is a list of names, and the message prints it, so the finding says *which* parameters rather than
  how many.
- The return annotation is a **note**, not a block, and the asymmetry is the point. A missing parameter
  annotation means the model can send anything; a missing return annotation means the library infers the
  output shape, which is a quality problem rather than a safety one. Two severities, used to mean
  something ([1.2](../01-what-an-audit-is/1.2-a-finding-is-the-audit-working.md)).

The red case:

```python
# a scratch copy of sutra_mcp/server.py - the tool as first written
@server.tool()
def lookup_ticket(ticket_id):
    try:
        return CACHE[ticket_id]
    except KeyError:
        return ""
```

**Line by line:**

- No docstring, so the wire carries an empty description, and a model choosing between this and `search_kb`
  has the function name and nothing else.
- `ticket_id` with no annotation, so the schema says a property exists and does not say it is a string. A
  client can send a list. The function will index a dictionary with it and raise `TypeError: unhashable
  type` — inside your process, with a traceback, rather than at the boundary with a `-32602`.
- No return annotation, which is the note.
- The good version is four lines longer and every added line is on the wire:
  `def lookup_ticket(ticket_id: str) -> str:` with a docstring whose first line says what the tool does and
  whose second paragraph says when **not** to call it.

Measured on 2026-09-05 against the fixture:

```text
  [A06] block sutra_mcp/server.py:8: lookup_ticket has no description
  [A06] block sutra_mcp/server.py:8: lookup_ticket params unannotated: ['ticket_id']
  [A06] note  sutra_mcp/server.py:8: lookup_ticket has no return annotation
```

Three findings on one function, two blocking and one not. And against this repository as it stands:

```text
  [A06] block sutra_mcp/*.py: target does not exist (built on day 34)
```

## When it breaks

**The docstring exists and is useless.** `"""Look up a ticket."""` passes this check and tells a model
nothing it could not guess from the name. The rule can require presence and cannot require quality, which
is the exact boundary [5.2](../05-a-server-you-did-not-write/5.2-what-no-script-can-check.md) is about. The
only defence against a bad description is somebody reading it — which is why Day 40's intake makes
*"read every description"* question two and marks it as the one no script can do.

**The annotation is present and meaningless.** `ticket_id: object`, or `args: dict`. The check is
satisfied, the schema says the parameter accepts anything, and the situation is identical to having no
annotation except that it now looks deliberate. A stricter version of this rule would refuse `object`,
`Any` and bare `dict`, and deciding whether to is a real design conversation rather than an obvious
improvement.

**The wrong thing is annotated.** A tool takes a `Context` parameter that the library injects, and somebody
annotates it and writes a docstring line about it. It appears in the schema, the model tries to supply it,
and every call fails validation. Day 34 covers which parameters the library strips; the audit knows nothing
about it, so a passing `A06` on a tool that has never actually been called successfully is entirely
possible. Green here means described, not working.

## In production

**What a professional writes instead:** the schema is not inferred from annotations at all. It is written
explicitly — a model class per tool with field descriptions, constraints and examples — and the annotations
merely reference it. That buys three things annotations cannot: a per-field description the model can read,
validation constraints such as a maximum length or an enumeration, and a schema that can be reviewed as a
document because it is one. The docstring then explains the *decision* — when to call this and when not to
— rather than restating the fields.

**What degrades at scale:** description quality, invisibly, as the tool count grows. Descriptions are
written for a shelf of four tools and are still there on a shelf of forty, where the model's actual problem
is telling this tool apart from the three that sound like it. Day 28's routing scorer is the honest
measurement of that, and the reason it is a *scorer* rather than a lint is that the property being measured
is comparative — a description is not good or bad in isolation, it is distinguishable or not from its
neighbours.

**The failure mode that only appears with real traffic** is the description that is accurate and
mis-scoped. `search_kb` says it searches the knowledge base, which is true, and says nothing about the
index being three weeks stale, so the model uses it for questions about last week and answers confidently
from old articles. No exception, no bad argument, no finding from any static check. The gap between what a
tool *does* and what a description implies about **when to trust it** is where most real tool-use failures
live.

**The review comment a senior engineer leaves:** *"This tool goes on the wire with no description and an
untyped parameter, which means the model gets a name and permission to send anything. The docstring is the
product here — it is the only thing the caller sees. Say what it returns, and say in one line when not to
call it, because that sentence prevents more bad calls than the rest of the description put together."*

**The interview question:** *"How do you make a tool easy for a model to use correctly?"* The honest spoken
answer: *"By remembering that the model only ever sees the name, the description and the schema — it never
sees the implementation. So the schema does the constraining: typed fields, enumerations rather than free
strings where the values are known, required versus optional stated properly, so a wrong argument is
rejected at the boundary with a clear error instead of blowing up inside. And the description does the
routing: what it does in one line, and when *not* to call it, which is the part people leave out. The
failure I've actually seen isn't a malformed argument, it's a model picking a tool that sounds right —
which means the description's job is to be distinguishable from its neighbours, not just accurate on its
own."*
