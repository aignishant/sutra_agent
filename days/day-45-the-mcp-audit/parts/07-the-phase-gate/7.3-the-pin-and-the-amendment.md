# 7.3 — The pin and the amendment

## One-line answer

`mcp` stays at `1.29.1` today, and not because bumping is frightening: `google-adk` 2.8.0, the newest release,
still declares `mcp>=1.24,<2`, so the framework forbids it — which turns the phase's headline finding from
*"we are behind"* into *"we are blocked upstream"*, and that is a sentence an amendment can be written around.

## The story

The phone has been asking you to update for weeks, and you keep pressing Later.

It is not that you disagree. You have read what is in it, and some of it you would like. The problem is that
the update wants more free space than the phone has, and freeing that space means deciding which photographs
to move off, and moving them means finding the cable, and the cable is in the drawer in the other room.

So the notification comes back every few days and you press Later again, and the pressing has quietly become
the decision. Nobody ever sat down and chose to stay on the old version. There was just never a moment where
choosing was easier than deferring.

The version of this that works is not more willpower. It is saying out loud, once, *"I am not updating until
the weekend, and on Saturday I am moving the photographs"* — because now there is a decision with a date on
it, and the difference between a plan and a habit is exactly that.

## The idea in plain language

Phase 5 and Phase 6 were built on a documented gap. The specification is revision `2026-07-28`. The pinned
SDK, `mcp==1.29.1`, reports `LATEST_PROTOCOL_VERSION = "2025-11-25"` and does not list `2026-07-28` among the
revisions it supports at all.

Six days measured a concrete piece of that gap, and each recorded it rather than working around it:

| Day | What was measured | The specification says |
| --- | --- | --- |
| 34 | no `initialize` in the current revision, and the SDK still requires the handshake over stdio | the handshake is gone; requests are self-contained |
| 35 | a resource miss arrives as `code=0` with the message doubled and `data` dropped | `-32602`, with the error data preserved |
| 35 | the server emits no `ttlMs` on a listing, so a conformant client cannot cache | list results carry an explicit freshness |
| 36 | the SDK's own `DeprecationWarning` says its tasks API was removed from the specification and will return as an extension | Tasks is now a published extension with `resultType`, `ttlMs`, `pollIntervalMs` and `tasks/update` |
| 41 | four greps for `server/discover`, four zeroes | `server/discover` is how a client learns what a server offers |
| 41 | no `resultType` and no `cacheScope` anywhere in the SDK | both are part of the current result envelope |

Read that table as one finding rather than six. **Every divergence is the SDK trailing the specification, and
none of them is Sutra's design being wrong.** Day 34's
[5.3 — Building for the revision you are not on](../../../day-34-building-sutra-mcp-tools/parts/05-lifecycle/5.3-building-for-the-revision-you-are-not-on.md)
made that the strategy on purpose: accept the gaps the library owns, and get right the things your own code
decides — no state between requests, sorted listings, honest errors, long-lived context travelling in the
payload as an explicit handle. That is the empty pipe laid under the road, and this audit's `A05`, `A07` and
`A03` are the checks that it is still empty and still straight.

So the question at the gate is not *"is our code wrong?"* It is *"do we move the pin?"*, and there is one
fact that answers it.

## Why Sutra needs it

Because Principle 14 says the plan is amended before the code changes, and a version bump made at a gate,
without an amendment, is precisely the silent adaptation the principle exists to forbid.

It also has to be settled **today** rather than deferred to whenever it next hurts. Phase 7 is memory and
retrieval and touches no MCP at all, so nobody has a reason to look at this again until Phase 8 or later. If
the answer is *"not yet"*, the reason has to be written down now, with the condition that would change it —
otherwise Later becomes the decision by default, exactly like the phone.

## The mechanism

The fact that settles it. `google-adk` declares what it can tolerate, and you can read it out of the
installed distribution rather than from anybody's summary:

```bash
uv run python -c "
import importlib.metadata as md
for r in md.requires('google-adk') or []:
    if r.lower().startswith('mcp'):
        print(r)
"
```

**Line by line:**

- `importlib.metadata.requires` returns the dependency specifiers from the **installed** distribution's
  metadata, which is the authoritative statement of what this version of the framework accepts. It is not a
  documentation page and it cannot be out of date relative to what you have.
- `r.lower().startswith('mcp')` filters to the protocol library, and it is a prefix test rather than a
  substring test on purpose: a substring match on `mcp` also catches `anyio>=4.9,<5 ; extra == "mcp"`, which
  is a constraint on a different package that happens to live in the same extra.
- Each specifier carries an environment marker naming the extra it belongs to. That matters: a constraint
  under `extra == "mcp"` applies when the MCP extra is installed, which for this repository it is.
- **Zero model calls, no network** — it reads `.venv`.

Result on 2026-09-05:

```text
mcp>=1.24,<2 ; extra == "all"
mcp>=1.24,<2 ; extra == "mcp"
mcp>=1.24,<2 ; extra == "test"
```

`<2`. And the obvious next question — whether the newer framework release relaxes it — has a live answer:

```bash
curl -s "https://pypi.org/pypi/google-adk/2.8.0/json" | python -c "
import json,sys
for r in json.load(sys.stdin)['info'].get('requires_dist') or []:
    if r.lower().startswith('mcp'):
        print(r)
"
```

**Line by line:**

- The index's per-version metadata endpoint — `/pypi/<name>/<version>/json` — returns the metadata of one
  specific release rather than the latest, which is what lets you ask about a version you have not installed.
- `requires_dist` is the same field the local check read, under the name the index uses for it.
- This is the check that turns *"presumably the next release fixes it"* into a fact. It is one command and it
  is the difference between a decision and an assumption.

Result on 2026-09-05:

```text
mcp<2,>=1.24; extra == "all"
mcp<2,>=1.24; extra == "mcp"
mcp<2,>=1.24; extra == "test"
```

**The newest `google-adk` still refuses `mcp` 2.x.** So the honest verdict, written as it should appear in
the gate log:

> **Finding (Phase 6 gate, 2026-09-05): the `mcp` pin stays at `1.29.1`. Not deferred — blocked.**
> The index offers `mcp==2.1.1`, whose own project description says v2 exists to support the `2026-07-28`
> specification and every earlier revision, keeps 1.x on a branch with security support, and recommends
> pinning `mcp>=1.28,<2` until migration is complete. Sutra cannot take that advice past `<2`, because
> `google-adk` 2.7.1 **and** 2.8.0 both declare `mcp>=1.24,<2`. Moving the protocol SDK requires the
> framework to move first. **Disposition: filed, with a trigger rather than a date.**

Two things follow from that, and both are worth stating.

**The trigger, not a date.** *"Revisit when a `google-adk` release declares `mcp>=2`"* is a condition somebody
can check in one command, and it is the right shape for a filed finding whose timing is not yours. A date
would be a guess about somebody else's release schedule.

**The pin is honest, and it was already being handled honestly.** Days 34 to 41 did not paper over the gap.
Each one measured it, named the day it was measured, and wrote code that does not depend on the missing
feature. Day 34's `serverInfo.version` reporting `1.29.1` because the SDK reports its own version, Day 35's
resource miss arriving as `code=0`, Day 41's `capabilities.py` written so that the day `server/discover`
exists it becomes almost nothing — those are the empty pipe, and they are why the eventual bump is a
dependency change rather than a rewrite.

**What the amendment would have to say.** When the trigger fires, Principle 14's ordering means a document
comes before a `uv add`. It is not a long document, and it has to carry six things:

1. **The dated facts, quoted.** The specification revision, the SDK's `LATEST_PROTOCOL_VERSION` before and
   after, and the framework specifier that unblocked it — each read live on the day, each with the command
   that read it, in the shape `docs/PACKAGES.md` rows already use.
2. **Which plan text goes stale.** `docs/01_MASTER_PLAN_ADDENDUM_GAPS.md` Part 2 is written as *"the
   specification did this and the SDK has not caught up"*. Half of that sentence stops being true, and the
   addendum needs a new part rather than an edit, because the old text is the record of why Phase 5 and 6 were
   written the way they were.
3. **Which days are affected, by part.** The six rows in the table above, each naming the day and the part
   that measured it. Every one of those parts contains a real measurement against `1.29.1`, and a measurement
   is not wrong when the world moves — it is **dated**. The amendment says whether those parts get a dated
   note appended or get re-measured, and *"append a note"* is the answer that keeps the history honest.
4. **What breaks.** The SDK's own migration guide, read rather than summarised, against the specific symbols
   this repository uses: `FastMCP`, `ClientSession`, `stdio_client`, `streamablehttp_client`,
   `types.LATEST_PROTOCOL_VERSION`, and the `stateless_http=True` constructor flag Day 34 relies on — which
   may not exist as a flag once statelessness is the architecture rather than a mode.
5. **An eval that can go red.** Principle 11 applies to an amendment like anything else: one check that fails
   before the bump and passes after. The obvious one is an assertion that `LATEST_PROTOCOL_VERSION` equals
   `2026-07-28`, which is a single line and is exactly the kind of test that would have caught a partial
   upgrade.
6. **A row in `docs/CHANGELOG_PLAN.md`, and an ADR if the day structure changes.** A pin bump alone is a
   changelog row. If the amendment concludes that a day has to be rewritten rather than annotated, that is
   structural and gets an architecture decision record, per the plan's §15 condition 6.

## When it breaks

**The bump happens quietly during an unrelated change.** Somebody runs a general dependency update, the
resolver finds a combination that installs, the tests pass, and the pin has moved with no amendment and no
record. Six weeks later nobody can say whether the change was a decision. This is the failure Principle 14 is
worded to prevent, and the practical defence is that `pyproject.toml` uses exact `==` pins, so a bump is
always a visible line in a diff rather than a lockfile resolution.

**The trigger fires and nobody is watching for it.** *"Revisit when `google-adk` declares `mcp>=2`"* is a
perfectly good condition that will be checked by nobody, because it lives in a gate log for a phase that
ended. The fix is to move it into the recurring list: the freshness check in [7.2](7.2-the-freshness-recheck.md)
already reads `google-adk`'s releases at every boundary, and adding the specifier read to that loop costs one
command and makes the trigger something that gets looked at rather than remembered.

**The constraint is worked around instead of waited out.** `uv` can be forced past a declared conflict, and
the resulting environment installs and imports. What it produces is a framework running against a library
version its own authors excluded, which is a class of failure with no error message: something in
`google.adk.tools.mcp_tool` calls a function whose signature changed, and it surfaces as a `TypeError` at the
one call site nobody exercised. The guard against it is already in place — Day 33 recorded that the MCP import
in ADK is wrapped in a `try/except ImportError` that logs *"MCP Tool is not installed"*, so a broken
combination can present as an absence rather than a crash.

## In production

**What a professional writes instead:** a dependency policy that names, for each critical dependency, who
decides, on what evidence, and what the rollback is. For a protocol library that means a compatibility matrix
— which SDK versions speak which revisions, which framework versions accept which SDKs — kept as a small table
in the repository rather than re-derived by whoever is doing the upgrade. The reason to write it down is that
the derivation takes an afternoon and the table takes a minute to read.

**What degrades at scale:** transitive constraints stop being legible. Five direct dependencies each with
their own bounds is solvable by reading; fifty is solvable only by the resolver, and the resolver's answer is
*"here is a set that installs"*, which is not the same claim as *"here is a set that works"*. Teams past that
point pin everything, upgrade on a schedule, and treat a constraint conflict as a design conversation rather
than a puzzle to defeat with a flag.

**The failure mode that only appears with real traffic** is the version skew between a client and a server
that are deployed separately. Your client is bumped, your server is not, and both are correct in isolation.
The protocol negotiates down to a common revision, quietly, and a feature the client now assumes is silently
unavailable — which is Day 38's whole migration lab, and it is the reason a protocol bump is a rollout plan
rather than a commit.

**The review comment a senior engineer leaves:** *"We're three protocol revisions behind and I don't want that
fixed in this pull request. What I want in the description is one line saying why: which upstream constraint
blocks it, the command you ran to establish that, and the condition under which we look again. 'Not yet' with
a reason is a decision I can review. 'Not yet' on its own is a habit."*

**The interview question:** *"Your framework pins you to an old version of a protocol library and the
specification has moved on. What do you do?"* The honest spoken answer: *"First I check whether it's actually
blocked, because 'we're behind' and 'we're blocked' need different responses. In our case the framework
declared a hard upper bound on the protocol SDK and its newest release still did, so bumping wasn't a choice
we could make — and knowing that changed what we wrote down. Second, I make the gap explicit rather than
letting it be ambient: which features are missing, which day measured each one, and whether any of them
affects our own design. Ours didn't, because we'd deliberately built to the newer architecture even though
the library couldn't speak it — no state between requests, state travelling in the payload, honest errors —
so the eventual bump is a dependency change and not a rewrite. And third, the finding gets a trigger rather
than a date: revisit when the framework accepts version 2, which is one command in our recurring freshness
check. What I'd avoid is forcing past the constraint. That gets you a framework running against a library
its own authors excluded, and the failure has no error message."*
