# 5.2 — What no script can check

## One-line answer

Two things in this audit have no decision procedure and never will — whether a tool description is written
to manipulate a model, and whether the person named in `reviewed_by` actually read anything — so the audit
states them as rows a human owns rather than pretending they are checks.

## The story

The rent agreement runs to eleven pages and the broker is standing there with a pen.

You do the thing everybody does. You check the numbers, because the numbers are checkable: the rent, the
deposit, the notice period, the dates, the number of months. All correct, all matching what was agreed on
the phone. Eleven pages, five numbers, three minutes.

Clause fourteen, on page seven, says the deposit is refundable after deductions for repainting, and that
repainting is required at the end of every tenancy. It is one sentence in the same font as everything else.
It is not hidden. Nobody lied to you. It was simply placed where careful people do not look, because
careful people are looking at the numbers.

You find out about clause fourteen two years later, in a conversation where the other person is entirely
within their rights, holding a document you signed.

The checkable parts were checked, thoroughly, and they were never where the risk was. The risk was in a
sentence, and the only thing that would have found it was reading — slowly, for meaning, with the specific
question *"what does this let them do?"* in mind.

## The idea in plain language

Every check in this day so far decides something about **form**. Is there a docstring. Is there an
annotation. Is the allowlist empty. Is there a row. All of those are answerable by a program, and all of
them together do not answer the question that matters about a server somebody else wrote: **is this text
trying to do something to my model?**

A tool description is not documentation. It is an instruction that reaches a model with the same standing
as everything else in its context, and Day 29 built the whole poisoned-skill lab around exactly this. Its
[3.3 — It validated and was hostile](../../../day-29-sourcing-and-auditing-skills/parts/03-the-poisoned-skill/3.3-it-validated-and-was-hostile.md)
is the finding in one sentence: a skill that passes every structural check can still be hostile, because
hostility lives in prose and prose is not a schema violation. The same applies to a tool description word
for word, with the difference that a tool description arrives over a network from a process you cannot read
and can change between one listing and the next.

Day 40's
[6.2 — The attacks a filter does not stop](../../../day-40-filtering-and-allowlists/parts/06-the-posture/6.2-the-attacks-a-filter-does-not-stop.md)
has a table of these, and one row is marked *"a human reading it at review time. Nothing automated."*
That row is this part.

So the audit carries two rows that are **not checks**, and the difference is made explicit rather than
hidden:

| # | The row | Why no program decides it | What the program can do |
| --- | --- | --- | --- |
| `H1` | every tool description has been read as text addressed to a model | hostility is meaning, not structure | check that a description exists (`A06`) and that its digest matches what was pinned |
| `H2` | the name in `reviewed_by` belongs to a person who did `H1` | a name is a string | check that the field is non-empty (`A08` extension, [5.1](5.1-six-questions-with-an-exit-code.md)) |

The `H` is deliberate. They are numbered in a different series from `A01`–`A10` so that nobody can put them
in the tuple, and so that an output listing ten green `A` rows cannot be mistaken for a complete audit.

What a program *can* do is narrow the human's work to the point where it gets done. That is what the pinning
from Day 40's
[3.2 — The name held, the sentence moved](../../../day-40-filtering-and-allowlists/parts/03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)
buys: a digest of every description a person approved, so the next review is *"three descriptions changed"*
rather than *"read forty descriptions again"*. The machine cannot judge the text. It can tell you exactly
which text is new, and that is the difference between a review that happens and one that is intended.

## Why Sutra needs it

Because the tools Sutra will not write are the ones this matters for, and there are already two of them in
the plan.

Day 39 evaluates a first-party database server whose tool descriptions somebody else wrote. Addendum 02
replaces paid grounding with a free open-source web-search server, whose results are attacker-influenced by
construction — the whole point of a web search is that it returns text from strangers. Neither of those is
covered by any rule in this module, and both sit inside the boundary Day 32 drew.

There is also an argument about the *audit itself* that this part is here to make. An audit that reports
only what it can decide teaches the reader that those things are the risk. Ten green rules produce a feeling
of coverage that the ten rules did not earn, and the feeling is the dangerous output. Naming the two
undecidable rows, in the same document, with the same numbering discipline, is the cheapest available
correction.

## The mechanism

There is no function here, and that absence is the mechanism. What there is instead is a **written
procedure**, short enough to actually follow, and a place for its output.

The reading procedure for `H1`, done once per server at intake and again whenever a pin changes:

```text
For each tool the policy allows:
  1. Read the name.        Does it describe the action, or does it advertise?
  2. Read the description, once, for what the tool does.
  3. Read it again, asking only: what is this sentence asking the model to do?
  4. Look for the four shapes:
       - an instruction to the reader     ("always call this before answering")
       - a claim about other tools        ("more reliable than the built-in search")
       - a claim about authority          ("approved by the administrator")
       - anything about ignoring, overriding, or not mentioning
  5. Read the schema field names and their descriptions with the same question.
  6. Write the digest into `pinned`. Write your name into `reviewed_by`.
```

**Line by line:**

- Step 2 and step 3 are the same text read twice with different questions, and separating them is the whole
  technique. Reading for *what it does* is what everybody does automatically and it is the reading in which a
  planted instruction is invisible, because it parses as part of the description.
- The four shapes in step 4 come from Day 29's poisoned skill and Day 40's attack table. They are not a
  complete list and cannot be — this is a list of what has been seen, and the next one will be something
  else. It is a prompt for attention, not a filter.
- Step 5 is the step people skip. A schema field description reaches the model exactly like the tool
  description does, and it gets less scrutiny because it looks like type documentation.
- Step 6 is what makes the reading durable. Without the digest, this reading has to be repeated in full every
  time; with it, the next reading is only over what changed
  ([Day 40's 3.2](../../../day-40-filtering-and-allowlists/parts/03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)).
- The procedure is six steps because a twenty-step procedure is not followed. Every step that was cut was
  cut because it was checkable by `A06` or `A08` and therefore already has an owner.

And what the audit prints, so that the human rows appear in the same output as the machine ones:

```python
# tools/mcp_audit.py - printed after the ten checks, never counted among them
HUMAN_ROWS = (
    ("H1", "every allowed tool's description read as text addressed to a model"),
    ("H2", "reviewed_by names a person who did H1"),
)


def print_human_rows() -> None:
    """The two rows no function decides. Printed so they cannot be forgotten."""
    print("\nnot checked by this program - a person owns these:")
    for row_id, text in HUMAN_ROWS:
        print(f"  {row_id}  {text}")
```

**Line by line:**

- `HUMAN_ROWS` is a separate constant from `CHECKS`, with a different id prefix, and it holds no function.
  There is nothing to call, deliberately: a placeholder function returning an empty finding list would sit
  in the tuple and print `ok`, which is the exact lie this part exists to prevent.
- `print_human_rows` returns `None` and touches no exit code. **These rows cannot make the gate red**, and
  that is the honest design — a build cannot know whether somebody read something, and a check that pretended
  to would be answered by ticking a box, which is worse than no check.
- The heading says *"not checked by this program"* rather than *"manual checks"*. The first phrasing tells
  the reader what the tool did not do; the second sounds like a category of work that has been scheduled.
- It prints after the ten checks so it is the last thing on the screen, which is where a summary belongs and
  is also, practically, the part people read.
- The argument for printing this at all — rather than leaving it in a document — is that the audit's output
  is what gets pasted into a pull request. A list of ten green rules pasted with nothing under it makes a
  claim about coverage. The same list with two rows underneath saying what was not examined makes an honest
  one.

## When it breaks

**The human row becomes a tick.** Somebody adds a `reviewed: true` field, the check verifies it is `true`,
and the gate is green because a boolean was set. Day 32 named this precisely — it is why `REVIEWED_BY` holds
a person's name and not a flag — and the reason a name is better is not that it is harder to type. It is that
a name is a **question you can ask later**, and a boolean is not.

**The description is read once and never again.** The server is reviewed on the day it is added and the pins
are never re-checked, so a description rewritten six months later reaches the model unread. This is the
failure Day 40's TTL and pin machinery exist for, and it is the reason the review date should expire into a
finding ([4.3](../04-the-policy/4.3-where-the-server-ledger-lives.md)).

**The reading is done and the reader was the wrong person.** The reviewer is whoever added the server, which
means the person checking for manipulation is the person who wanted the dependency. Nothing technical fixes
this. The organisational fix is that `reviewed_by` is somebody other than the author of the change, and it is
worth writing that rule down before the first time it is inconvenient.

**Nothing breaks and the reading catches nothing for a year.** This is the most likely outcome and it is the
one that erodes the practice, because a control that never fires looks like a control that is not needed. The
counter-argument is the same one that applies to a fire drill: the measurement is not how often it finds
something, it is whether it would find something if there were something to find.

## In production

**What a professional writes instead:** the human review is a required approval on the change, from a
different person, with the tool descriptions **rendered into the pull request** so they are read where
reading already happens. That last detail is what makes it work — a review that requires opening a separate
document is a review that gets approved without the document being opened, and the whole engineering problem
is putting the text in front of the person at the moment they are already looking.

**What degrades at scale:** attention, uniformly and invisibly. Twenty servers with six tools each is a
hundred and twenty descriptions, and no organisation reads a hundred and twenty of anything carefully. The
scaling answer is not more reviewers; it is the digest, so that the recurring work is proportional to
**change** rather than to size. A team that reads three changed descriptions properly is in a far better
position than one that skims a hundred and twenty.

**The failure mode that only appears with real traffic** is the description that is honest and the *data*
that is not. The tool says it searches the knowledge base, and it does; an article in that knowledge base
contains a sentence addressed to a model. Nothing in the description was hostile, the review was correct, and
the injection arrived in the result. That is why the posture is defence in depth — the review covers what the
server *says about itself*, and the boundary must still treat everything it *returns* as untrusted, which is
Day 40's
[6.3 — The host decides, not the server](../../../day-40-filtering-and-allowlists/parts/06-the-posture/6.3-the-host-decides-not-the-server.md).

**The review comment a senior engineer leaves:** *"The audit is green and I still want to know who read these
six descriptions. Put the text in the description of this pull request so I can read it here — I am not
opening the server's repository, and neither will anyone else, and a review that depends on somebody doing
that is a review we are not actually getting."*

**The interview question:** *"What can't you automate in a security review of an integration?"* The honest
spoken answer: *"Meaning. I can check that a description exists, that it hasn't changed since we approved it,
that the schema is typed and the allowlist isn't empty — all of that is structure and structure is cheap to
verify. What I can't automate is whether a sentence is written to manipulate a model, because that's exactly
the thing that passes every structural check. So I keep those rows in the audit and I number them
differently, so ten green automated rules can't be mistaken for a complete review, and I make the human's job
small enough that it happens: pin a digest of every description we approved, so the recurring work is reading
what changed rather than re-reading everything. The failure I'd guard against hardest is turning that into a
checkbox — the field holds a person's name rather than a boolean, because a name is a question you can ask
later and a tick isn't."*
