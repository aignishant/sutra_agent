# 5.1 — Six questions with an exit code

## One-line answer

Auditing a server you did not write is a different job from auditing your own: you cannot read the code, so
the audit becomes six questions about the *relationship* — publisher, version, endpoint, revision, permitted
surface, named reviewer — and the honest version of the check separates the three a machine can answer from
the three only a person can.

## The story

You are buying a second-hand fridge from somebody in the next block, and you are standing in front of it.

What you can check, you check. It is plugged in and it is cold. The door seal grips a piece of paper you slide
into it. The compressor comes on and it does not rattle. The light works, the shelves are all there, the
model number on the plate inside matches what the advertisement said.

What you cannot check is everything that would actually decide whether this is a good fridge. Whether it has
been serviced. Whether the gas has ever been topped up, and by whom. Whether it was in a house that lost
power for a week last summer. Whether the compressor that sounds fine has sounded fine for a month and is on
its way out.

So you do the only sensible thing, which is to check what can be checked, ask about the rest, and write down
the answers along with who gave them. Not because a name makes an answer true. Because in four months, when
it stops cooling, *"the seller said it was serviced last year"* is a different position to be in from *"I
assumed it was fine"* — and the difference was made by a notebook, not by the fridge.

## The idea in plain language

Everything so far in this day has audited code you wrote. `A01` through `A10` parse your own modules and
your own policy. That is the easy half, and it is easy for a reason that disappears the moment you depend on
somebody else's server: **you can read the source.**

For a third-party MCP server you cannot. It runs in another process, possibly on another machine, and the
only surface you have is what it says about itself over the wire plus whatever the registry says about who
published it. Day 32's
[6.2 — Before you depend on a server](../../../day-32-mcp-stateless-core/parts/06-in-production/6.2-before-you-depend-on-a-server.md)
turned that into six intake questions, and this part turns them into something with an exit code.

The honest framing Day 32 gave, restated because it is the design: **the registry answers three of them and
you answer three.**

| # | Question | Answered by | Checkable? |
| --- | --- | --- | --- |
| 1 | Who publishes it? | the registry namespace | **yes** — the namespace is in the entry |
| 2 | Which version? | the registry entry, and `isLatest` | **yes** — both are fields |
| 3 | Where does it actually run? | `remotes`, or the package | **yes** — present or absent |
| 4 | Which protocol revision does it speak? | the server, when asked | **partly** — see below |
| 5 | What is it allowed to be asked? | your allowlist | **yes** — it is `ServerPolicy.allow` |
| 6 | Who approved it? | a person's name | **no** — a machine can check the field is non-empty and nothing more |

Question 4 is the interesting one and it is the one Phase 5 spent a day on. The 2026-07-28 revision defines
`server/discover` as the single request that returns a server's declaration, and Day 41's
[2.2 — The request your SDK cannot send](../../../day-41-capabilities-and-mcp-apps/parts/02-discovery-without-sessions/2.2-the-request-your-sdk-cannot-send.md)
measured that the pinned `mcp==1.29.1` does not implement it — four greps, four zeroes. So the answer to
*"which revision does this server speak?"* comes from the `initialize` reply on the older path, which is a
different question wearing the same clothes, and the ledger records it as a claim rather than a
measurement.

Question 6 is the one that must not be automated, and
[5.2](5.2-what-no-script-can-check.md) is why.

The rule this produces: **three of the six are fields the audit reads, one is a claim recorded with its
source, and two are a person's work whose only machine-checkable property is that they were done.**

## Why Sutra needs it

Because Sutra is going to depend on servers it did not write, and the plan says so.

Day 39 evaluates a first-party database server against hand-written tools — that is a third-party binary in
Sutra's boundary. Addendum 02 replaces paid search grounding with *"a free open-source web-search MCP
server"*, which is a stranger's process returning text a model will treat as true. And beyond this
curriculum, every MCP integration anyone does at work is this case rather than the `sutra_mcp` case.

There is also a specific inheritance from Day 32 that lands today. Its `lab/server_intake.py` ends on
`exit: 1` with three findings — a stale version, an unknown protocol revision, and no named reviewer — and
each one carries a `TODO(me)`. Those are **filed findings**
([1.2](../01-what-an-audit-is/1.2-a-finding-is-the-audit-working.md)) whose day is today, and the
disposition is not to solve them. It is to decide where they live now: the version and the revision become
columns of `docs/SERVER_PROVENANCE.md`
([4.3](../04-the-policy/4.3-where-the-server-ledger-lives.md)), and the reviewer becomes the
`reviewed_by` field on `ServerPolicy` that the ledger renders.

## The mechanism

Day 32's intake, promoted from a lab script into the shape the policy record already has. The point of the
promotion is that the intake stops being something you run once, by hand, on the day you add a server, and
becomes a property of a record that `./m check` re-reads on every commit.

```python
# sutra/mcp/filtering.py - the intake answers, as fields on the record
@dataclass(frozen=True)
class ServerPolicy:
    """One reviewed MCP server, and everything Sutra is allowed to take from it."""

    launch: StdioServerParameters  # Q3 - where it actually runs
    allow: tuple[str, ...]  # Q5 - what it may be asked
    deny: tuple[str, ...] = ()
    writes: tuple[str, ...] = ()
    pinned: Mapping[str, str] = field(default_factory=dict)
    publisher: str = ""  # Q1 - the registry namespace
    version: str = ""  # Q2 - the pinned version, not "latest"
    revision: str = ""  # Q4 - what it claimed, and when
    reviewed_on: str = ""
    reviewed_by: str = ""  # Q6 - a person, and TODO(me) decides who
    ttl_seconds: float | None = None
```

**Line by line:**

- The first six fields are Day 40's, unchanged. **Nothing is being redesigned here** — four fields are added
  to a record that already exists, which is the cheapest possible way to make an intake permanent.
- `publisher`, `version` and `revision` are the three registry-answerable questions, stored as strings
  because that is what the registry returns. `version` is deliberately not a version object: the value being
  recorded is *what we pinned*, and a string cannot be accidentally compared with `>=`.
- `revision` carries the protocol revision the server claimed. Day 41 measured that `server/discover` is
  absent from the pinned SDK, so on this repository the value comes from the `initialize` reply and the
  ledger should say so — a claim with a source, not a measurement.
- `reviewed_by` is the new field the ledger needs
  ([4.3](../04-the-policy/4.3-where-the-server-ledger-lives.md)), and it is a `str` holding a person's
  identifier rather than a boolean, for the reason Day 32 gave: a boolean is something the script can set
  for itself.
- Every new field defaults to `""`. **A blank is a finding, not a default.** That is Day 32's design
  decision carried across intact, and the alternative — an unknown revision quietly passing — is how a check
  ends up green and meaningless.
- `allow` still has no default while everything else does. A record without a review date is incomplete; a
  record without an allowlist is a server with no policy, and the dataclass refuses to construct it.

And the intake, as an extension to `A08`, which the build brief leaves for you:

```python
# tools/mcp_audit.py - the shape; TODO(me) in the hub asks you to finish it
INTAKE_FIELDS = ("publisher", "version", "revision", "reviewed_on", "reviewed_by")


def _blank_intake_fields(call: ast.Call) -> list[str]:
    """Which of the six intake answers this ServerPolicy left empty."""
    given = {kw.arg: kw.value for kw in call.keywords}
    blank = []
    for field_name in INTAKE_FIELDS:
        value = given.get(field_name)
        if value is None:
            blank.append(field_name)
        elif isinstance(value, ast.Constant) and not value.value:
            blank.append(field_name)
    return blank
```

**Line by line:**

- `INTAKE_FIELDS` is five names, not six, because question 5 — the allowlist — is already checked by `A08`
  and a rule has one owner ([4.2](../04-the-policy/4.2-a-rule-with-one-owner.md)).
- `{kw.arg: kw.value for kw in call.keywords}` builds a map of what was actually passed. A field omitted
  entirely and a field passed as `""` are different in the source and identical in effect, so both are
  collected.
- `isinstance(value, ast.Constant) and not value.value` catches the empty string and also `None` and `0`, by
  way of the falsy test. A value built from an expression is not judged, which is the same honest limit
  every check in this module has.
- What is **not** here is the decision about severity, and that is the `TODO(me)`. A blank `reviewed_by` on a
  server that only reads is a different risk from a blank one on a server in `writes`, and deciding whether
  the rule is uniform or graduated is the exercise.
- Note what this cannot do at all: it checks that a name was typed. It cannot check that the person named
  read anything.

## When it breaks

**The registry answers and the answers are about a different thing.** You look up `some.publisher/docs-mcp`,
the entry is active, the namespace is verified, and the URL under `remotes` points at a deployment the
publisher updated this morning. Every field you recorded is accurate about the *listing*. None of it is
about the code answering your calls. This is not a flaw in the process; it is the process being honest about
what a remote dependency is.

**The version says `latest` and everything passes.** `version` is non-blank, so no finding fires, and the
value pins nothing. Day 32's intake caught this with a separate `isLatest` check and the field-blank rule
here does not. Adding a rule that rejects the literal string `latest` is two lines and is worth writing,
because *"we pinned latest"* is the most common way a version field becomes decorative.

**The server is fine and the transport degrades the evidence.** You ask a third-party server for a resource
it does not have, expecting `-32602` so your client can tell a permanent error from a temporary one, and Day
35's
[2.3](../../../day-35-resources-and-prompts/parts/02-the-shelf/2.3-the-miss-that-must-be-an-error.md)
measurement applies to their server too if they are on the same SDK generation:

```text
   code=0 message='Error creating resource from template: Error creating resource from template: Resource not found' data=None
```

`code=0` is not a JSON-RPC code at all. Auditing somebody else's server means auditing it through a library
whose limits you have already measured on your own, and that measurement is now an asset: you know the
difference between *their server is wrong* and *this SDK flattens errors*.

## In production

**What a professional writes instead:** third-party service intake is a review checklist attached to a
change request, with the machine-checkable half enforced in CI and the human half signed off in the tracker
by a named person. The signature is not ceremony — it is the mechanism by which an organisation can later
find out *who to ask*, which is the only question that matters when a dependency misbehaves at three in the
morning.

**What degrades at scale:** the review becomes a rubber stamp. The first ten servers get a real reading; the
fiftieth gets approved because the previous forty-nine were fine, and the approval is now a measure of
throughput rather than of scrutiny. Setups that resist this make the *scope* of the review proportional to
the blast radius — a read-only server gets a short form, a server with a tool in `writes` gets the long one
— rather than pretending every dependency deserves the same attention.

**The failure mode that only appears with real traffic** is the server that behaves differently for you than
it did in review. Rate limiting, a feature flag, a regional deployment, a different response under load.
Everything you checked was checked from one machine at one moment, and none of it is a property of the
service. The countermeasure is not a better intake; it is treating every response as untrusted data at
runtime — which is Day 40's whole posture and the reason the allowlist sits on the host side.

**The review comment a senior engineer leaves:** *"You have recorded the version as `latest`. That is not a
pin, it is a promise the publisher makes to themselves. Put the resolved version in, and if the transport
only gives us a name, write that down as the limitation — I would rather read 'we cannot pin this' than a
field that looks like a pin and is not."*

**The interview question:** *"How do you decide whether to trust a third-party MCP server?"* The honest
spoken answer: *"I separate what's checkable from what isn't, and I write both down. The registry gives me
three things — a verified publisher namespace, a version, and where it actually runs — and it says
explicitly that it doesn't do a security review. So I add three of my own: which protocol revision it
claims, which tools it's allowed to be asked for, and a named human who read the tool descriptions. That
goes in a policy record in code, the build fails if a field is blank, and the provenance ledger is generated
from it. The limit worth stating up front is that for a remote server you're recording provenance of a
decision, not of an artefact — the operator can redeploy whenever they like — so the review date has to
expire, and everything the server returns stays untrusted at runtime regardless of how the intake went."*
