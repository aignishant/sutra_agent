# 6.1 — 💥 Green because the path did not exist

## One-line answer

Change one line in each check — `return []` instead of a finding when the target is missing — and this
audit reports eight green rules on a repository where none of the audited code exists, which is why **a
missing target is a finding** is the most load-bearing decision in the module.

## The story

The generator behind the building is tested on the first Saturday of every month, and there is a log on the
wall beside it.

Date, tester's initials, one word: OK. Twelve rows a year, going back six years. It is a good log, kept by
somebody conscientious, and it is the reason nobody worries about the generator.

In March the generator went to the workshop for a rewind and came back in the second week of April. The
first Saturday of April, the man came down, found the concrete pad empty, and wrote OK — because the test
had not failed. Nothing had gone wrong. There was simply nothing there to go wrong, and the log has no
column for that.

Read the log now. Seventy-two rows, all saying OK, and one of them means *"there was no generator"*. From
the wall, the two are the same mark. The only person who could tell you which row is which is the man who
made it, and he has forgotten, because it was one Saturday.

The row that says OK on the empty pad is worse than a blank row would have been. A blank invites a
question. **A mark answers one.**

## The idea in plain language

Every check in this audit begins the same way: find something, read it, judge it. Which means every check
has a branch for *the thing is not there*, and that branch has two possible bodies:

```text
if not target.exists():
    return []                    # the skip
    return [_missing(...)]       # the finding
```

The first is what almost everybody writes, because it reads as obviously correct. There is nothing to
check, so there are no findings. It is also the empty concrete pad, and it produces a green mark that is
indistinguishable from a real one.

Day 31 taught this exact shape one level up. Its
[5.2 — Green because nothing ran](../../../day-31-the-quality-gate/parts/05-the-gate-that-lied/5.2-green-because-nothing-ran.md)
showed a `pytest` run where a single hyphen in a marker expression deselected every test, the gate forgave
exit code 5, and `OK all green` was printed on a run where nothing executed. The insight there was that the
day sheet had a column for failures and no column for *how many did you attempt*.

This part is the MCP-specific version, and it is worse in one specific way. Day 31's failure needed a typo.
This one needs **nothing at all**: it happens by default, in a normally-functioning system, whenever a
directory is renamed, a module is moved, or a phase is only half built. Nobody makes a mistake. The paths
that were correct stop matching, silently, and the audit gets quieter and greener as it gets less true.

The rule that prevents it fits in a sentence: **a check that could not look must say so, in the same
channel as a check that looked and found something.** Not a warning, not a different colour — a finding,
with a severity, counted in the total.

## Why Sutra needs it

Because this repository is, right now, exactly the state that produces the false green — and that is not a
flaw in the curriculum, it is the ordinary condition of any system mid-build.

Days 33 to 44 are written as documents. The code they describe is typed by the learner, so on any given day
some of `sutra/mcp/` and `sutra_mcp/` exists and some does not. An audit that skipped missing targets would
have gone green somewhere around Day 34 and stayed green through the entire phase, reporting louder
confidence the less there was to audit.

It gets worse after today, not better. Phase 7 starts tomorrow and introduces `sutra/memory/`. Phase 8 and
beyond restructure things. Every rename is an opportunity for a path in this module to stop matching, and
the only defence that survives a rename is a check that complains when it finds nothing.

## The mechanism

The helper, which is three lines and is the whole subject:

```python
# tools/mcp_audit.py
def _missing(check: str, where: str, built_on: str) -> Finding:
    return Finding(check, "block", where, f"target does not exist (built on {built_on})")
```

**Line by line:**

- It returns a `Finding`, not a warning and not `None`. It goes into the same list as every other finding,
  gets counted in the same total, and blocks the same gate. There is deliberately no separate channel: a
  separate channel is a place for things to be ignored.
- The severity is `"block"`. That is a strong choice and it is worth defending: a missing target means the
  audit has **no information** about a rule it claims to enforce, which is a strictly worse position than
  knowing about a violation. A violation you can fix. An absence you cannot even size.
- `built_on` puts the day number in the message, so the finding arrives with its own disposition
  ([1.2](../01-what-an-audit-is/1.2-a-finding-is-the-audit-working.md)) — filed, to that day. That one
  parameter is what turns eleven red lines into a table somebody can act on rather than a wall of alarm.
- The wording is *"target does not exist"* rather than *"skipped"*. The reader has to be able to tell, from
  the output alone, the difference between *"I looked and it was fine"* and *"there was nothing to look
  at"*, and the words are the only place that distinction can live.

Now break it on purpose. This takes one substitution — every `return [_missing(...)]` becomes `return []`
— written to a scratch copy, because you never edit the thing you are measuring:

```bash
cd days/day-45-the-mcp-audit/lab
sed -e 's/return \[_missing(\([^)]*\))\]/return []/' audit_preview.py > _skips.py
python _skips.py; echo "exit: $?"
rm -f _skips.py
```

**Line by line:**

- `sed -e 's/return \[_missing(\([^)]*\))\]/return []/'` replaces the finding with an empty list wherever a
  check returns early on a missing target. `\([^)]*\)` matches the arguments without crossing the closing
  parenthesis, which is what keeps the substitution from eating the rest of the line.
- `> _skips.py` writes the broken copy beside the original. It has to be **in this directory** rather than
  in a temporary folder, because `main` computes the repository root by walking up from `__file__`, and a
  copy somewhere else audits somewhere else. That is itself a small lesson about a check that decides for
  itself what it is looking at.
- `rm -f _skips.py` afterwards. A broken copy of the audit left in the tree is a thing somebody will run.
- **Zero model calls.** It parses files.

Measured on 2026-09-05, against this repository:

```text
ok  A01 boundary             nothing agent-side reaches past sutra/mcp/
ok  A02 deadlines            a module that calls out carries with_timeout
ok  A03 no-held-connections  no module-level open session
ok  A04 secrets              no key-shaped literal in a tracked code file
ok  A05 stateless-server     no module-level mutable state in sutra_mcp/
ok  A06 tool-schemas         every tool has a description and annotations
ok  A07 error-paths          no handler returns instead of raising
ok  A08 allowlist            REGISTRY is populated and no allow= is empty
RED A09 one-rule-one-owner   the gate runs the stages this audit assumes
  [A09] block m: check) does not run tools.lint_free_suffix
  [A09] block m: check) does not run tools.lint_skills
  [A09] block m: check) does not run tools.mcp_audit
RED A10 provenance           every registered server has a ledger row
  [A10] block docs/SERVER_PROVENANCE.md: target does not exist (built on day 45)
  [A10] block sutra/mcp/filtering.py: target does not exist (built on day 40)

5 finding(s), 5 blocking, over 10 checks
```

Compare it, line for line, with the real run from
[1.2](../01-what-an-audit-is/1.2-a-finding-is-the-audit-working.md). **Eight rules green instead of two.**
`A01` through `A08` all report `ok`, on a repository containing no `sutra/mcp/`, no `sutra_mcp/*.py` and no
policy module. Every one of those eight greens is the empty concrete pad.

The two that stayed red are the accident that makes this demonstration honest. `A09` reads `m`, which
exists, so it is genuinely checking something. `A10` appends its missing-target findings instead of
returning them, so the substitution did not reach it — which is a reminder that this failure is not one
decision made once. It is a decision **per check**, and getting it right in nine places and wrong in one
gives you a nine-tenths-honest audit whose output looks identical to an honest one.

And notice which way the numbers move. Eleven findings became five. **The audit got quieter and the
repository did not change.** That is the signature to watch for: an audit whose finding count drops without
a corresponding fix has usually stopped looking rather than started passing.

## When it breaks

**The guard is removed and the check crashes instead of skipping.** Take the missing-target guard out of
`A10` — not replace it with `return []`, just delete it — and the audit does this:

```text
Traceback (most recent call last):
  File "...\lab\_skips.py", line 419, in main
    findings = run_all(root)
  File "...\lab\_skips.py", line 412, in run_all
    out.extend(check.fn(root))
  File "...\lab\_skips.py", line 377, in check_provenance
    tree = _parse(policy)
  File "...\lab\_skips.py", line 89, in _parse
    return ast.parse(path.read_text(encoding="utf-8"))
FileNotFoundError: [Errno 2] No such file or directory: '...\\sutra\\mcp\\filtering.py'
```

This is a **better** failure than the silent skip, and it is worth saying why out loud: it is loud, it names
the path, and the gate stops. It is still not good enough, because one missing file now prevents the other
nine checks from running at all — a check that cannot look should report that it cannot look and let the
rest of the audit finish.

**The skip is deliberate and reasonable.** Somebody adds a `--phase` flag so the audit only runs the rules
relevant to the current phase, and the rules for later phases return empty. Entirely sensible, and now the
output has two kinds of `ok` in it again. The fix is not to refuse the feature; it is to print a third
state — `ok`, `RED`, and `n/a` — so the reader can count how many rules actually ran, which is the *how
many did you attempt* column Day 31's van driver did not have.

**The check runs and looks at the wrong tree.** `main` walks up from `__file__` to find the repository root.
Copy the module somewhere else — a scratch directory, a packaged install, a different checkout — and it
audits whatever is four levels above wherever it landed, reporting confidently on a repository nobody asked
about. This happened while writing this part, which is how it got into the document.

## In production

**What a professional writes instead:** the check reports **how many units it examined**, not only what it
found. A linter that says *"scanned 47 files, 0 findings"* is falsifiable; one that says *"0 findings"* is
not. Some tools go further and let you assert a floor — fail if fewer than N files were scanned — which is
the same idea as a minimum test count and exists for the same reason. Where a target is genuinely optional,
mature setups make the absence itself configurable, so *"this path does not exist"* is either an error or an
explicitly declared exemption with a reason, and never a silence.

**What degrades at scale:** the number of paths a check depends on. A rule that hard-codes one directory
survives; a rule that hard-codes fifteen accumulates dead branches as the codebase is reorganised, and
because each dead branch fails silently, the check appears to keep working while covering less and less
each quarter. The countermeasure is to make the check's *scope* a declared thing — a list of paths in
configuration that itself gets validated — rather than a set of literals scattered through functions.

**The failure mode that only appears with real traffic** is the one this part is named after, and it has a
specific shape in continuous integration: a job that is skipped by a path filter. The pipeline is
configured to run the audit only when files under `sutra/` change, somebody moves the code, the filter
stops matching, and the job stops running. There is no red build and no error. The pipeline summary shows
the job as skipped, in grey, and nobody reads grey.

**The review comment a senior engineer leaves:** *"This returns an empty list when the directory is
missing. That means the day someone renames that folder, this rule reports success forever and nobody finds
out. Return a finding — 'I could not look' is a result, and it's the one I most want to know about, because
a violation I can fix and an absence I can't even size."*

**The interview question:** *"How do you know a check in your pipeline is still doing anything?"* The honest
spoken answer: *"By making it report what it examined, not just what it found. Zero findings and zero files
scanned print the same green, and they mean opposite things. So every check I write treats 'the target
isn't there' as a finding rather than a skip, and prints a count of what it looked at. I tested this on my
own audit by changing the missing-target branch to return an empty list — eight of ten rules went green on
a repository where none of the audited code existed, and the finding count dropped from eleven to five with
nothing fixed. That's the signature I watch for now: a check that gets quieter without anyone doing work
has usually stopped looking."*
