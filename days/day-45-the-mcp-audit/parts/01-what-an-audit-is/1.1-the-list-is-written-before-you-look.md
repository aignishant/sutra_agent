# 1.1 — The list is written before you look

## One-line answer

An audit is a list of named rules written **before** you open the thing being audited, because a list
written while looking at the code bends to the code, and the whole value of the exercise is that it
does not.

## The story

You write the shopping list at home, standing in front of the open fridge.

There is no milk, the dal is nearly finished, and there is one onion left. Four items go on the back
of an envelope and you put it in your pocket.

In the shop the list stops being a memory aid and starts being a defence. There is an offer on
biscuits. There is a stack of something new at the end of the aisle. The vegetables at the front look
better than the ones you came for. None of that was visible from your kitchen, and all of it is
designed to be visible here.

Now think about the alternative, which is what most people actually do: walk in with no list and
decide in the aisle. You come home with biscuits and no dal. Nothing went wrong exactly. You made a
reasonable decision at every single step. It is just that every one of those decisions was made in a
room built to influence it, and the one place you could see what was missing was the room you left.

The list is not smarter than you. It was written somewhere with better information.

## The idea in plain language

An **audit** is a walk over a written list of rules, where each rule has three things: a name, a
statement of what must be true, and a way of deciding whether it is.

The word that does the work is **before**. The rules are fixed in advance of looking, and they are
fixed by somebody standing where the information is good — reading the design decision, the
specification, the day the rule was made — rather than standing in front of the code that is about to
be judged by them.

Sutra has done this once already, on skills. Day 29's
[2.1 — Read it like the thing that will obey it](../../../day-29-sourcing-and-auditing-skills/parts/02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md)
laid out five passes over a third-party skill folder, in a fixed order, decided before any particular
skill was opened. Today applies the same discipline to something larger and less readable: a protocol
integration spread across two packages, a policy module, a driver script and a ledger.

Three properties make a rule usable, and each of them is a decision you make while writing it.

**A name.** Not "check the imports" but `A01 boundary`. A rule with an identifier can be referred to
in a commit message, argued with in a review, suppressed with a reason, and counted. A rule described
only in a sentence gets re-described slightly differently by each person who repeats it, and after
three repetitions there are three rules.

**A statement of what must be true**, phrased as the good state rather than the bad one.
*"Nothing under `sutra/` outside `sutra/mcp/` imports a database driver"* is checkable. *"No sneaky
back doors"* is a mood.

**A decision procedure.** Ideally a function that returns findings. Where no function is possible —
and there are two of those today — the rule says so explicitly and names what a person must read
instead ([5.2](../05-a-server-you-did-not-write/5.2-what-no-script-can-check.md)). A rule with no
decision procedure at all is not a rule; it is a wish that will be marked green by whoever is tired.

The shape this day builds is a tuple of ten of them:

| Field | What it holds | Why it is a field and not a comment |
| --- | --- | --- |
| `id` | `A01` … `A10` | so a finding has an address you can grep for |
| `name` | `boundary`, `deadlines`, `secrets` | so output is readable without the source |
| `rule` | one sentence, the good state | so the check's own output explains itself |
| `fn` | the function that returns findings | so the answer is produced, not remembered |

## Why Sutra needs it

Because Phase 6 ends today, and the phase gate in the plan's §15 says *"MCP audit of `sutra-core`
passes"* — which is a claim about a system that nobody can evaluate without a list.

Thirteen days built the thing being audited. Day 33 wrote the client, Day 34 the server, Day 35
resources and prompts, Day 36 long jobs, Day 37 auth, Day 39 database tools, Day 40 the allowlist and
the policy record, Day 41 capabilities, Day 42 the agent served as a tool, Day 43 the deploy-shaped
entry point, Day 44 the hardened client. Each of those days ended green. **"Each piece was correct
when it was built" is the sentence that appears in the first paragraph of most postmortems**, because
it is true and it is not the same claim as "the system is correct now".

There is a specific reason the list must be written first, and it is not hypothetical. You wrote
every line of the code being audited. You know why each shortcut is there and you remember that it was
reasonable. That memory is exactly the influence the shopping list defends against: reading the code
first and then deciding what to check produces a list of rules the code already passes.

Day 40 already anticipated this. Its
[6.4 — What you write down before you connect](../../../day-40-filtering-and-allowlists/parts/06-the-posture/6.4-what-you-write-down-before-you-connect.md)
ends by saying that the reusable half of its lab scripts becomes `tools/mcp_audit.py` today, and that
*"`tools/mcp_audit.py` can only check things that exist"*. The list is the specification for that
file.

## The mechanism

The two dataclasses the rest of the day hangs on. This is the whole of the audit's structure; the ten
rules are data poured into it.

```python
# tools/mcp_audit.py
@dataclass(frozen=True)
class Finding:
    """One thing the audit found, addressed well enough to act on."""

    check: str
    severity: str  # "block" or "note"
    where: str
    message: str

    def __str__(self) -> str:
        return f"  [{self.check}] {self.severity:5} {self.where}: {self.message}"


@dataclass(frozen=True)
class Check:
    """One numbered, named rule, and the function that decides it."""

    id: str
    name: str
    rule: str
    fn: Callable[[Path], list[Finding]]
```

**Line by line:**

- `@dataclass(frozen=True)` on both. A finding that can be edited after it is produced is a finding
  somebody can quietly soften between the check and the report, and the whole point of the exercise is
  that the output is not negotiable.
- `check: str` on `Finding` carries the rule's id rather than a pointer to the `Check` object. That is
  deliberate: findings get printed, sorted, counted and pasted into a pull request, and a string
  survives all four. An object reference survives none of them.
- `severity: str` with exactly two values, `"block"` and `"note"`, and the comment says so because
  there is no enum. Two values is the honest number: an audit that grades findings on five levels
  spends its review time arguing about whether something is a three or a four. **Which findings block
  is a judgement, and it is one of the hub's `TODO(me)` decisions.**
- `where: str` is a path, usually with a line number appended as `path:lineno`. It is a string rather
  than a `Path` because some findings are not about a file at all — `A10` reports a server *name*, and
  a type that forces every finding to be about a file would have pushed that check into a shape it
  does not have.
- `message: str` says what is wrong in one clause, with the offending value in it. `"imports sqlite3"`
  rather than `"forbidden import"`, because the second one sends the reader back to the source to find
  out which.
- `__str__` formats one line. Having it on the dataclass rather than in the printer means every place
  that shows a finding shows it identically, including a future test that asserts on the text.
- `Check.rule` is a sentence, and it is printed **next to the check's own result**. A reader who sees
  `RED A05 stateless-server` learns nothing; a reader who sees the rule beside it can tell whether they
  disagree with the finding or with the rule, which are different conversations.
- `fn: Callable[[Path], list[Finding]]` — every check takes the repository root and returns findings.
  Not a boolean, for the reason Day 32's
  [6.2](../../../day-32-mcp-stateless-core/parts/06-in-production/6.2-before-you-depend-on-a-server.md)
  gives about its own intake: a boolean tells you to go and run it again by hand.
- Taking `root` as an **argument** rather than computing it inside each check is what makes the checks
  testable at all. You can point them at a fixture directory holding a deliberate violation and assert
  that the right finding comes out — which is how every red example in this day was produced.

The ten rules, as data:

```python
# tools/mcp_audit.py
CHECKS: tuple[Check, ...] = (
    Check("A01", "boundary", "nothing agent-side reaches past sutra/mcp/", check_boundary),
    Check("A02", "deadlines", "a module that calls out carries with_timeout", check_deadlines),
    Check("A03", "no-held-connections", "no module-level open session", check_held_connections),
    Check("A04", "secrets", "no key-shaped literal in a tracked code file", check_secrets),
    Check(
        "A05",
        "stateless-server",
        "no module-level mutable state in sutra_mcp/",
        check_stateless_server,
    ),
    Check(
        "A06", "tool-schemas", "every tool has a description and annotations", check_tool_schemas
    ),
    Check("A07", "error-paths", "no handler returns instead of raising", check_error_paths),
    Check("A08", "allowlist", "REGISTRY is populated and no allow= is empty", check_allowlist),
    Check(
        "A09",
        "one-rule-one-owner",
        "the gate runs the stages this audit assumes",
        check_gate_stages,
    ),
    Check("A10", "provenance", "every registered server has a ledger row", check_provenance),
)
```

**Line by line:**

- A `tuple`, not a `list`. The set of rules is fixed at import; a module that can append to it at
  runtime is a module where a conditional import can silently remove a rule.
- The ids run `A01` to `A10` with no gaps, and **the order is the reading order of this day**: section
  2 is `A01`–`A04`, section 3 is `A05`–`A07`, section 4 is `A08`–`A10`. Three lists agree — the code,
  the day's sections and the checklist — which is the same argument Day 31's
  [4.1](../../../day-31-the-quality-gate/parts/04-wiring-the-gate/4.1-two-lines-in-the-driver.md) made
  for the order of its two lint stages.
- The grouping is by **what the rule protects**, and it is worth stating because a reader will look for
  it: `A01`–`A04` are the client side, the code Sutra runs; `A05`–`A07` are the server side, the code
  strangers call; `A08`–`A10` are the policy between them.
- Each `rule` string is written as the good state. Read the column downward and it is a description of
  a healthy system, which means the tuple doubles as documentation that cannot go stale, because the
  string is what gets printed.
- The functions are referenced, not called. An obvious point that is worth one sentence because the
  mistake — `check_boundary(root)` inside the tuple — turns the rule list into a set of results
  computed once at import, against whatever the working directory was.

## When it breaks

The failure is not a crash. It is a list that was written afterwards.

It looks like this. You open `sutra_mcp/server.py`, notice that the tool functions have good
docstrings, and write down *"every tool has a description"*. You look at the client, see the retry
wrapper, and write down *"calls are retried"*. Then you run the list and it is green, and the green
means nothing at all, because every rule was reverse-engineered from a system that already satisfied
it.

The tell is the count. A first audit over a thirteen-day integration that produces **zero findings**
has almost certainly measured the auditor
([1.2](1.2-a-finding-is-the-audit-working.md) is that whole subject).

The second break is a rule with no decision procedure, which survives because it sounds responsible:

```text
  [A11] block sutra_mcp/: tools are appropriately scoped
```

Nothing produced that line. Somebody typed it, or worse, somebody typed the green version of it. A
rule you cannot fail is a rule that will be marked passed, and it crowds out the ones that can fail
because the list is now longer and the person reading it is skimming.

## In production

**What a professional writes instead:** the rules live in a policy file — a linter configuration, a
policy-as-code bundle, a set of custom lint rules shipped with the repository — and the rule text is
generated into the documentation from the same source that runs it. The property being bought is that
the sentence people read and the code that decides cannot drift apart, which is the identical argument
this repository already makes for `docs/TRACEABILITY.md` being generated rather than typed.

**What degrades at scale:** the list grows and nobody removes anything. A ten-rule audit is read; a
sixty-rule audit is scrolled. The rules that survive contact with a real team are the ones that
produce few findings and each finding is acted on, and mature setups measure that directly — a rule
whose findings are suppressed more often than they are fixed is a rule that is wrong, and it gets
deleted rather than defended.

**The failure mode that only appears with real traffic** is the rule that becomes true by accident. A
check passes for six months, then somebody restructures a package and the check's path no longer
matches anything, and it keeps passing.
[6.1](../06-failure-lab/6.1-green-because-the-path-did-not-exist.md) is that failure, built on
purpose, and the reason `A01`–`A10` treat a missing target as a **finding** rather than as a skip.

**The review comment a senior engineer leaves:** *"These rules read like a description of the code as
it is today. Which of them could fail on this branch? If the answer is none, we have written a
summary and called it an audit — take one rule and show me the change that makes it go red."*

**The interview question:** *"How do you audit an integration you built yourself?"* The honest spoken
answer: *"The hard part isn't technical, it's that I know why every shortcut is there and I remember
it being reasonable. So I write the rules before I open the code, from the design decisions rather
than from the implementation — one named rule per decision, each phrased as the good state and each
with a function that returns findings rather than a yes or no. Then I run it and I expect findings. A
first pass over something I built that comes back clean means I wrote the rules to match what I'd
already done, and I'd rather find that out at the gate than in a postmortem."*
