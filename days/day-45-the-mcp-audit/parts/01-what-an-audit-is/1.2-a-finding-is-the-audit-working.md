# 1.2 — A finding is the audit working

## One-line answer

Every finding ends in exactly one of two states — **fixed**, with the change beside it, or **filed**,
with the day it is scheduled for — and the third state, *"we should look at that sometime"*, is the
one that turns an audit into a document nobody re-runs.

## The story

Somebody goes up on the roof before the rains and comes down saying one tile near the parapet has
slipped.

That is a good morning. It is a small job, the tile costs almost nothing, and the man who fixes it is
already in the building. Nobody treats the report as bad news, because the alternative to knowing
about the tile is not a roof without a slipped tile — it is a slipped tile and a stain spreading across
a ceiling in the first week of July, by which time the tile is the cheapest part of the problem.

Now think about the year somebody went up and came down and said it was all fine.

You cannot tell, from that sentence alone, whether the roof was fine. It has exactly the same shape as
the sentence somebody says when they went up, found the sun hot, looked at the near corner, and came
down. And the two are indistinguishable **until it rains**, which is the worst possible moment to
learn which one you got.

The report that says "one tile" tells you two things: something about the roof, and something about
the person who went up. The report that says "all fine" only tells you the second thing, and only if
you already trust them.

## The idea in plain language

A **finding** is one thing the audit noticed, with an address. It is not an accusation and it is not a
failure of the person who wrote the code. It is the output the exercise exists to produce.

That framing matters because the natural reaction to your own audit is to want it clean, and wanting
it clean is precisely the pressure that produces bad audits. Three specific ways it gets in, worth
naming so you can catch yourself:

**Auditor's optimism.** *"That was fine last month."* It probably was. The check costs one command,
and a month is long enough for two other days to have touched the file.

**Scope mercy.** *"That one is only a lab prop."* Props get checked too. A prop's job description is
being wrong in an instructive way, so *"is it still contained?"* is a live question about it rather
than a formality.

**Finding shame.** The quiet one. You find something, and because you wrote the code, the finding
feels like a report on you rather than on the repository. So it gets softened into a note, or fixed
silently in the same commit with no record, and the audit's own history — which is the thing that
makes the next audit cheaper — loses the entry.

Against all three, the discipline is a **binary disposition**. When you reach the end of the run,
every finding is in one of exactly two states:

| Disposition | What it means | What has to be beside it |
| --- | --- | --- |
| **fixed** | the change is in this commit | the change itself, reviewable in the diff |
| **filed** | it is real and it is not today's work | the day number it is scheduled for, written down |

There is deliberately no third column. *"Won't fix"* is a **filed** finding whose day is "never" and
whose reason is written out — which forces the reason to exist. *"Look into it"* is not a
disposition; it is the absence of one, wearing a verb.

And the counting rule, stated plainly because it is the part people find counter-intuitive: **on a
first audit over a system this size, zero findings is a worse result than five.** Five findings mean
the rules had teeth and somebody ran them. Zero means either the rules were written to match the code
([1.1](1.1-the-list-is-written-before-you-look.md)), or the checks did not actually reach anything
([6.1](../06-failure-lab/6.1-green-because-the-path-did-not-exist.md)), or the auditor flinched.

## Why Sutra needs it

Because this repository has carried findings across days on purpose, and today is the day they are
dispositioned rather than forgotten.

Day 32's server intake ends on `exit: 1` with three findings and a `TODO(me)` on each. Day 40's
description pinning left the question of what to do when a pinned description changes on a tool that
writes. Day 41 measured five ways the pinned SDK and the specification revision disagree and fixed
none of them, correctly, because a day that installs nothing does not bump a pin. Every one of those
is a **filed** finding, and the gate is where they either get a day number or get argued out of the
list.

There is a second reason and it is about the ledger, not the code.
[4.3](../04-the-policy/4.3-where-the-server-ledger-lives.md) makes `docs/SERVER_PROVENANCE.md` a
generated file — and a generated ledger only tells the truth if the findings that produced its rows
were recorded honestly in the first place. An audit whose findings were quietly absorbed produces a
ledger that vouches for decisions nobody made.

## The mechanism

The runner, and the two lines at the end that decide the exit code:

```python
# tools/mcp_audit.py
def run_all(root: Path) -> list[Finding]:
    """Every check, in order, over one repository root."""
    out: list[Finding] = []
    for check in CHECKS:
        out.extend(check.fn(root))
    return out


def main() -> int:
    """Print every finding, then return 1 if any of them blocks."""
    root = Path(__file__).resolve().parents[1]
    findings = run_all(root)
    by_check = {c.id: [f for f in findings if f.check == c.id] for c in CHECKS}
    for check in CHECKS:
        rows = by_check[check.id]
        mark = "ok " if not rows else "RED"
        print(f"{mark} {check.id} {check.name:20} {check.rule}")
        for row in rows:
            print(row)
    blocking = [f for f in findings if f.severity == "block"]
    print(f"\n{len(findings)} finding(s), {len(blocking)} blocking, over {len(CHECKS)} checks")
    return 1 if blocking else 0
```

**Line by line:**

- `run_all` returns findings and prints nothing. Separating the deciding from the printing is what lets
  a test call `run_all` against a fixture directory and assert on the result, which is how every red
  example in this day was produced.
- `check.fn(root)` — every check gets the same root, and no check is allowed to decide for itself which
  tree it is looking at. [6.1](../06-failure-lab/6.1-green-because-the-path-did-not-exist.md) shows
  what goes wrong when one of them computes its own.
- `Path(__file__).resolve().parents[1]` in `main` walks up from `tools/mcp_audit.py` to the repository
  root. `resolve()` first, because `__file__` can be relative depending on how the module was invoked,
  and `parents[1]` on a relative path is not the repository.
- `by_check` groups before printing so the output is **one block per rule** rather than a flat list.
  That matters more than it sounds: a reader scanning `ok`/`RED` down the left margin can see the shape
  of the system in ten lines, and only reads the findings under the RED ones.
- `f"{mark} {check.id} {check.name:20} {check.rule}"` prints the rule text on the same line as its
  result, for the reason [1.1](1.1-the-list-is-written-before-you-look.md) gave: the reader needs to be
  able to disagree with the rule, not only with the finding.
- `"ok "` has a trailing space so it is the same width as `"RED"` and the ids line up. A column that
  does not line up is a column people stop scanning.
- The summary line prints **three numbers**: total findings, blocking findings, and how many checks
  ran. The third one is the *how many did you attempt* number that Day 31's
  [5.2](../../../day-31-the-quality-gate/parts/05-the-gate-that-lied/5.2-green-because-nothing-ran.md)
  showed a green run can hide. Without it, "0 findings" and "nothing ran" print almost the same line.
- `return 1 if blocking else 0` — **notes do not fail the gate.** That is what the two severities are
  for, and it is what keeps the audit runnable on every commit rather than only at a gate.
- `if __name__ == "__main__": raise SystemExit(main())` sits at the bottom of the file. `raise
  SystemExit(...)` rather than `sys.exit(...)` is the same shape Day 31's linters use, so all three
  modules in `tools/` are invoked and terminated identically.

## When it breaks

**The finding that was fixed in the same commit with no record.** Nothing in the diff is wrong. The
audit output shows nine green rules, and six months later, when the same thing recurs, nobody can find
out that it happened before or what made it happen. The fix costs nothing: the finding goes in the
commit message beside the change.

**The finding that was downgraded to a note to make the gate pass.** The tell is a `severity` change in
a diff that touches no logic:

```text
-        findings.append(Finding("A05", "block", where, f"mutable {target}"))
+        findings.append(Finding("A05", "note", where, f"mutable {target}"))
```

That is a real decision and it might be the right one. What makes it a break is doing it while the gate
is red and calling it maintenance. A severity change is a change to the rule, and it belongs in a
commit of its own with a reason.

**The audit that ran and was not read.** The output is thirty lines and the last one is `exit: 1`, and
the person running it reads the exit code and re-runs it after making an unrelated change. The
countermeasure is the one already in the code: findings print under their rule with the rule's sentence
beside them, so the output can be read at a glance rather than parsed.

## In production

**What a professional writes instead:** findings go to an issue tracker automatically, with the rule id
in the title so duplicates collapse, and the audit reports which findings are new since the last run
rather than the full list. That "new since last run" framing is what makes a long-running audit usable
— a team facing 200 pre-existing findings ignores all of them, and a team facing the three that
appeared this week fixes three.

**What degrades at scale:** the ratio of blocking to note findings drifts, always in the same
direction. Every time the gate blocks somebody who is in a hurry, there is pressure to make that rule a
note, and nobody ever proposes the reverse. Mature setups fight this by making the severity itself a
reviewed field — a change from `block` to `note` requires the same approval as a change to the rule —
because otherwise a gate becomes advisory one commit at a time.

**The failure mode that only appears with real traffic** is the finding that is correct and useless: a
rule that fires on every file in a large repository. It is not a false positive, so nobody can argue it
away, and it is unactionable, so nobody acts. It gets suppressed wholesale, and the suppression usually
takes a real rule down with it.

**The review comment a senior engineer leaves:** *"Your audit came back with zero findings on the first
run over thirteen days of work. I'd like to believe it and I don't. Show me one rule going red against
a deliberate violation, and then I'll read the green as evidence."*

**The interview question:** *"Your security audit came back clean — is that good news?"* The honest
spoken answer: *"On a first pass over a system of any size, it's suspicious rather than reassuring. A
clean sheet usually measures the auditor: rules written after reading the code so they already pass,
checks whose paths stopped matching anything, or a scope that quietly excluded the awkward parts. So I
look at three numbers before I look at the findings — how many rules ran, how many files each one
actually opened, and how many findings are new. When I ran mine at a phase gate I got eleven findings
and every single one was 'this file does not exist yet', which was completely correct and told me my
checks were reaching real paths. Findings are the output; zero is a result I have to explain, not one I
get to celebrate."*
