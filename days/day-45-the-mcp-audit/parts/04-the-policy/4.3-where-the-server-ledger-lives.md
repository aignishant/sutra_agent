# 4.3 — A10: where the server ledger lives

## One-line answer

The server provenance ledger is `docs/SERVER_PROVENANCE.md`, it is **generated by `tools/mcp_audit.py`
from the `REGISTRY` in `sutra/mcp/filtering.py`**, and `A10` fails when the two disagree in either
direction — which is the answer to the question Day 32 left open.

## The story

The plumber's number is in your phone as *Plumber*.

He came once, he was good, and you saved him. Eighteen months later the bathroom tap is dripping and you
open the contacts, and there are four. *Plumber*. *Plumber 2*. *Plumber (Sunday)*. And one saved by
somebody else in the house as *plumber bhaiya*.

You have no idea which one was the good one. You cannot tell from the numbers. You could ring all four,
which takes an evening and involves explaining the tap to three people who will not be coming. What you
actually do is ring the first one, because deciding is worse than guessing.

The thing that would have fixed this took four seconds and had to happen at one particular moment: saving
him as *Plumber — society gate 2, Feb, fixed the kitchen line, ₹400*. Not because you are organised.
Because the four seconds were available exactly once, on the day he was standing there, and after that
they were never available again at any price.

## The idea in plain language

**Provenance** is the record of where a thing came from and who decided to use it. Sutra has one already:
`docs/SKILL_PROVENANCE.md`, established on Day 29, with seven columns and one rule —
[4.1 — No row, no run](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.1-no-row-no-run.md):
a skill with no row does not get loaded, and **a rejected audit is a row too**.

Day 32's
[6.2 — Before you depend on a server](../../../day-32-mcp-stateless-core/parts/06-in-production/6.2-before-you-depend-on-a-server.md)
said servers need at least the same, and argued why they need more: *"a skill can only suggest, a server
runs code and returns facts."* It then left two things open. It named a file called
`docs/SERVER_PROVENANCE.md` in a failure scenario without ever establishing it, and it said, in its *In
production* section, that the ledger *"is generated from that file rather than maintained by hand, so the
two cannot disagree"* — without saying which file, or which program does the generating.

Both are answered here.

**Where it lives:** `docs/SERVER_PROVENANCE.md`, beside `docs/SKILL_PROVENANCE.md`, in the ledger
directory the plan's §16 defines. Not in `sutra/`, because it is a ledger and not code. Not inside a day
folder, because it outlives days.

**Who generates it:** `tools/mcp_audit.py`. The single source of truth is `REGISTRY` in
`sutra/mcp/filtering.py` — the same dictionary Day 40 built, the same one `A08` checks — and the ledger is
its printed form. The audit reads the registry, renders the table, and compares it with the committed
file. A row for a server that is not registered is a finding. A registered server with no row is a
finding.

That is deliberately the same arrangement `docs/TRACEABILITY.md` already has in this repository: generated
from the day hubs by `scripts/trace.py`, regenerated by `./m check`, never edited by hand. The plan's §16
divides the ledgers into two kinds for exactly this reason, and this new one joins the generated half.

Why generated rather than written? Because the failure mode of a hand-written ledger is not that it is
wrong. It is that it becomes **partially right**, which is worse. Four rows, nine servers, and no way to
tell which five were reviewed — the exact scenario Day 32's *When it breaks* section measured. A generated
ledger cannot be partially right. It is either in step with the registry or the audit is red.

The columns, and where each one comes from:

| Column | Source | Written by |
| --- | --- | --- |
| Server | the `REGISTRY` key | the code |
| Reached by | `ServerPolicy.launch` | the code |
| Allowed tools | `ServerPolicy.allow` | the code |
| Writes | `ServerPolicy.writes` | the code |
| Revision | the revision it claims to speak | **a person**, from Day 41's probe |
| Reviewed on | `ServerPolicy.reviewed_on` | **a person** |
| Reviewed by | `ServerPolicy.reviewed_by` | **a person**, by name |

Four columns are generated from code and three are typed by a human — and the three human ones live
**inside the `ServerPolicy` record**, not in the ledger. That placement is the whole design. The generator
only moves information; it never invents it, and there is nowhere to type a review date except in the
record the code actually consults.

`ServerPolicy` as Day 40 wrote it has `reviewed_on` and does not have `reviewed_by`. Adding that field is
today's small change to the record, and it is deliberate rather than incidental: Day 32's intake made
*"who approved it?"* one of its six questions and observed that a blank there means *"the decision has no
owner"*.

## Why Sutra needs it

Because the question a provenance ledger answers is only ever asked under pressure, and by then it is too
late to assemble one.

*"An advisory has been published for this publisher — are we affected?"* With the ledger, that is a grep on
one column and it takes a minute. Without it, it is reading commit history and asking people what they
remember, and it takes a week, during which the honest answer is *"we think not"*.

There is a Sutra-specific reason as well, and it is about Phase 7 starting tomorrow. Day 46 introduces
memory, Day 47 makes sessions durable, and Day 49 builds a local retrieval index. Every one of those
touches storage, and the question of which server holds which data — and who signed off on that — gets
harder every phase, not easier. Today is the cheapest day this ledger will ever cost.

And there is the plan's own rule. Day 29 established *no row, no run* for skills. The same sentence applied
to servers is **no row, no connection**, and Day 40 already built the enforcement half: the registry lookup
raises rather than returning a default. `A10` is the other half — the record that says a human was involved
in putting the entry there.

## The mechanism

```python
# tools/mcp_audit.py
def check_provenance(root: Path) -> list[Finding]:
    """A10 provenance: every registered server has a ledger row, and the reverse."""
    policy = root / "sutra" / "mcp" / "filtering.py"
    ledger = root / "docs" / "SERVER_PROVENANCE.md"
    findings = []
    if not ledger.exists():
        findings.append(_missing("A10", "docs/SERVER_PROVENANCE.md", "day 45"))
    if not policy.exists():
        findings.append(_missing("A10", "sutra/mcp/filtering.py", "day 40"))
    if findings:
        return findings
    tree = _parse(policy)
    registered = set()
    for node in ast.walk(tree) if tree else []:
        if isinstance(node, ast.Dict):
            registered |= {k.value for k in node.keys if isinstance(k, ast.Constant)}
    rowed = {
        line.split("|")[1].strip()
        for line in ledger.read_text(encoding="utf-8").splitlines()
        if line.startswith("| ") and line.count("|") >= 7
    }
    for name in sorted(registered - rowed):
        findings.append(Finding("A10", "block", name, "in REGISTRY, no provenance row"))
    for name in sorted(rowed - registered - {"Server", "------"}):
        findings.append(Finding("A10", "note", name, "provenance row, not in REGISTRY"))
    return findings
```

**Line by line:**

- Both missing-target findings are collected before either is returned, so a repository missing both files
  gets told about both. Returning on the first would send the reader round twice.
- `if findings: return findings` — when a source is absent there is nothing to compare, and the check stops
  rather than producing a misleading empty-versus-empty match. **Two absent files agreeing with each other
  is not a green result**, and this early return is what stops it being reported as one.
- `registered` is built from every `ast.Dict` in the file rather than from the `REGISTRY` assignment
  specifically. That is deliberately loose: it also picks up a policy dictionary defined in a helper. The
  strict version — only the `REGISTRY` node, which `A08` already locates — is a `TODO(me)`, and the trade
  is that loose over-collects while strict misses a registry built in an unusual way.
- `k.value for k in node.keys if isinstance(k, ast.Constant)` reads the literal string keys. A key that is
  a variable is skipped, silently, which is a gap worth knowing: a registry keyed by constants defined
  elsewhere is invisible to this check.
- `line.count("|") >= 7` is how a data row is told apart from prose. Seven pipes means six columns plus the
  closing one, which is the shape the ledger's table has. It excludes the header separator by accident and
  the `{"Server", "------"}` subtraction catches what slips through — crude, and honest about being crude.
- `line.split("|")[1].strip()` takes the first cell. Index `1`, not `0`, because a Markdown row starts with
  a pipe so `split` produces an empty first element.
- **Both directions are checked**, and they have different severities. A registered server with no row is a
  `block`: a connection nobody approved. A row with no registered server is a `note`: usually a server that
  was removed and whose row correctly stays, since a ledger is append-only history — Day 29's *"a rejected
  audit is a row too"* applies to a retired server as well.
- `sorted(...)` on both differences so the output is stable between runs.

The ledger itself, which the hub's build brief asks you to create:

```markdown
# Server Provenance Ledger — Project Sutra

Generated by `tools/mcp_audit.py` from `REGISTRY` in `sutra/mcp/filtering.py`. Do not edit by hand;
edit the policy record and re-run `./m check`. Every MCP server Sutra may reach gets a row **before
it is ever connected** — Day 29's rule for skills, applied to something strictly more dangerous.

| Server | Reached by | Allowed tools | Writes | Revision | Reviewed on | Reviewed by |
| ------ | ---------- | ------------- | ------ | -------- | ----------- | ----------- |
```

**Line by line:**

- The header says **who generates it and what to edit instead**, in the file, at the top. A generated file
  that does not say so is a file somebody will edit, and the next `./m check` silently overwrites their
  work — a trap the plan's §16 already warns about for `TRACEABILITY.md` and `TRACKER.md`.
- Seven columns, matching the table above and matching `SKILL_PROVENANCE.md`'s shape closely enough that a
  reader who knows one can read the other.
- *Before it is ever connected* is the rule, in the same words Day 29 used, because it is the same rule.
- The table is empty today. It fills as `REGISTRY` fills, which is Day 33 onward.

Measured on 2026-09-05 against this repository:

```text
  [A10] block docs/SERVER_PROVENANCE.md: target does not exist (built on day 45)
  [A10] block sutra/mcp/filtering.py: target does not exist (built on day 40)
```

Two findings. The first is today's build step; the second is filed to Day 40.

## When it breaks

**The ledger and the registry agree, and both are wrong.** Somebody adds a server, adds it to `REGISTRY`,
runs the audit, and pastes the regenerated ledger — with `reviewed_by` left as an empty string, because the
generator does not require it. `A10` is green: the sets match. The row exists and it certifies nothing. The
fix is a second rule inside `A08` — a policy with a blank `reviewed_by` is a finding — and it is a
`TODO(me)` in the hub, because writing it yourself is how you discover that *the rows match* and *the rows
say something* are different claims.

**The generated file drifts and nobody notices because nobody regenerates.** `A10` compares two sets of
names, not two whole tables, so a change to `allow` updates the registry and leaves the ledger's *Allowed
tools* column stale — with the same names on both sides, so no finding. The stronger version renders the
whole table and compares text, failing on any difference, exactly as `./m wiki --check` does for the wiki.
That is the right design and it is more code than this check has.

**The row is right about the decision and wrong about the artefact.** This is Day 32's honest limit, and it
does not go away by generating the file. For a **remote** server you are recording provenance of a
*decision*, not of running code: you reviewed what was behind that URL on a Tuesday, and the operator can
deploy anything on Wednesday. That is the argument for preferring a package-pinned server where you have
the choice, and for the ledger's review date being read as *"when somebody last looked"* rather than as a
guarantee.

## In production

**What a professional writes instead:** a software bill of materials, generated by the build and published
as an artefact with each release, listing every dependency and service the system talks to with versions
and identifiers. The properties are the same three this ledger has — generated rather than typed, one
source of truth, complete or red — and the reason the industry converged on generating it is precisely the
partially-right failure: a hand-maintained inventory is 80% correct and nobody knows which 80%.

**What degrades at scale:** the review date becomes meaningless. A ledger with a `reviewed_on` column
acquires rows from three years ago, and nobody can say whether that server is still what it was. Mature
setups make freshness a check rather than a column — a review older than an agreed age is a finding, which
turns "we should re-review these sometime" into a red build with a date on it. That is one line of code
against the policy record and it is the single best addition to this rule.

**The failure mode that only appears with real traffic** is the transitive dependency. Your registry lists
four servers. One of those servers calls two more, which you have never heard of and did not approve, and
its answers to you are shaped by theirs. Your ledger is complete and your actual dependency graph is
larger than it. There is no clean fix — you cannot audit what you cannot see — and the honest responses are
contractual rather than technical: ask what a server depends on, record the answer as a claim rather than
a fact, and treat everything a server returns as untrusted data regardless.

**The review comment a senior engineer leaves:** *"This pull request adds a server to the boundary and the
provenance row is missing. I do not need it to be perfect — name, version, namespace, date, and your name
as the reviewer. If we cannot say who approved this in six months, we do not have a boundary, we have a
habit."*

**The interview question:** *"How do you keep track of the external services an agent depends on?"* The
honest spoken answer: *"In a generated ledger, not a written one. There's a single policy record per server
in code — how it's reached, which tools we allow, who reviewed it and when — and the ledger is rendered
from that by the same check that runs in the build, so the two can't disagree; if they do, the build is
red. The reason it's generated is that hand-kept inventories don't go wrong all at once, they go
partially right, and a list that's four rows for nine servers is worse than no list because it looks
authoritative. The limitation I'd state up front is that for a remote service you're recording provenance
of a decision, not of an artefact — the operator can redeploy whenever they like — which is why the review
date has to expire and become a finding rather than sitting there as a tick."*
