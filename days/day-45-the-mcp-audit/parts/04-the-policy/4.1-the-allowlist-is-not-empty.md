# 4.1 — A08: the allowlist is not empty

## One-line answer

`A08` parses `sutra/mcp/filtering.py` and fails on an empty `REGISTRY` or on any `ServerPolicy`
constructed with an empty or missing `allow=`, because in ADK an empty tool filter does not mean *nothing*
— it means *everything*, and that is a policy failing open.

## The story

The notice outside the exam hall lists what you may bring in.

Pen, pencil, ruler, a transparent water bottle, and a non-programmable calculator. Five things. If your
lucky pen is not one of the listed kinds, it stays outside, and the person at the door does not have to
know anything about your pen to make that call. Whatever is not on the notice does not come in.

The other way to run that door is a list of what is banned. Phones, smart watches, notes. It reads as more
reasonable and it fails in one specific way: somebody arrives with something nobody thought of. A pen with
a screen in it. A calculator that turned out to be programmable after all. The person at the door has no
basis to refuse it, because the rule they were given is a list of things to stop, and this is not one of
them.

The five-item notice is not stricter out of suspicion. It is stricter because it is the only one of the
two that gives a correct answer about a thing nobody has imagined yet, and there is always a thing nobody
has imagined yet.

## The idea in plain language

Day 40 built Sutra's version of that notice. Its
[1.1 — The list of things you thought of](../../../day-40-filtering-and-allowlists/parts/01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md)
made the allowlist argument and its
[4.2 — A policy you can diff](../../../day-40-filtering-and-allowlists/parts/04-the-policy-module/4.2-a-policy-you-can-diff.md)
turned it into a record: one `ServerPolicy` per server, holding `launch`, `allow`, `deny`, `writes`,
`pinned`, `reviewed_on` and `ttl_seconds`, all in a `REGISTRY` dictionary in `sutra/mcp/filtering.py`.

`A08` checks two things about that file, and both of them are about a policy that is present in form and
absent in effect.

**`REGISTRY` is not empty.** A registry with no entries is a lookup that always raises, which sounds
safe — nothing can be reached. It is also indistinguishable from a repository where somebody wired a
toolset up directly and bypassed the policy module entirely, and the second reading is the one that
matters, because the code that reaches servers is elsewhere. An empty registry is evidence that the door
is not being used, not evidence that nobody came in.

**No `allow=` is empty.** This one is sharper, and it is the reason the check exists at all. Day 40's
[2.4 — The empty list that admits everything](../../../day-40-filtering-and-allowlists/parts/02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md)
measured ADK's behaviour: a `tool_filter` that is empty or `None` is treated as *no filter*, so every tool
the server offers is admitted. The natural reading of `allow=()` is "allow nothing". The actual behaviour
is "allow everything". A policy that fails in that direction is worse than no policy, because it looks like
one in a code review.

The rule, stated as the good state: **the registry has entries, and every entry names at least one tool it
permits.**

## Why Sutra needs it

Because Sutra reaches more than one server by the end of Phase 6, and the number will keep going up.

`sutra_mcp` from Day 34 is the first. Day 39 adds a database lane and evaluates a first-party database
server against it. Day 42 exposes the desk agent, which some other host will hold a policy about. Every one
of those is an entry in `REGISTRY`, and the value of having one file with all of them is precisely that a
question like *"what can this agent reach?"* is answered by reading it.

An empty `allow=` on any one of those entries silently undoes the whole of Day 40 for that server: the
filter that was supposed to admit two tools admits whatever the server currently offers, including tools
added since the last review, including the one Day 40's
[3.1 — The Tuesday a tool appeared](../../../day-40-filtering-and-allowlists/parts/03-when-the-server-changes/3.1-the-tuesday-a-tool-appeared.md)
is about.

## The paper behind it

> **The protection of information in computer systems** · `doi:10.1109/PROC.1975.9939` · 1975 ·
> `https://doi.org/10.1109/PROC.1975.9939`

Among its design principles is **fail-safe defaults**: base access decisions on permission rather than
exclusion, so that the default is denial and a mistake in the mechanism denies access rather than granting
it.

That is exactly the property `A08` is protecting, and the interesting part is that ADK's empty filter
violates it — the mistake grants rather than denies — so the check exists to catch a place where the
framework's default runs the other way. The paper is taught in full on Day 40, at
[`../../../day-40-filtering-and-allowlists/papers/01-protection-of-information.md`](../../../day-40-filtering-and-allowlists/papers/01-protection-of-information.md).

## The mechanism

```python
# tools/mcp_audit.py
def check_allowlist(root: Path) -> list[Finding]:
    """A08 allowlist: the registry is populated and no policy allows everything."""
    policy = root / "sutra" / "mcp" / "filtering.py"
    if not policy.exists():
        return [_missing("A08", "sutra/mcp/filtering.py", "day 40")]
    tree = _parse(policy)
    if tree is None:
        return [Finding("A08", "block", policy.as_posix(), "does not parse")]
    findings = []
    registry = None
    for node in tree.body:
        if isinstance(node, ast.AnnAssign | ast.Assign):
            target = node.target if isinstance(node, ast.AnnAssign) else node.targets[0]
            if isinstance(target, ast.Name) and target.id == "REGISTRY":
                registry = node.value
    if registry is None:
        findings.append(Finding("A08", "block", policy.as_posix(), "no REGISTRY"))
    elif isinstance(registry, ast.Dict) and not registry.keys:
        findings.append(Finding("A08", "block", policy.as_posix(), "REGISTRY is empty"))
    for node in ast.walk(tree):
        if not isinstance(node, ast.Call):
            continue
        if getattr(node.func, "id", "") != "ServerPolicy":
            continue
        allow = next((kw.value for kw in node.keywords if kw.arg == "allow"), None)
        where = f"{policy.as_posix()}:{node.lineno}"
        if allow is None:
            findings.append(Finding("A08", "block", where, "ServerPolicy with no allow="))
        elif isinstance(allow, ast.Tuple | ast.List) and not allow.elts:
            findings.append(Finding("A08", "block", where, "allow= is empty - admits everything"))
    return findings
```

**Line by line:**

- `if tree is None: return [Finding(..., "does not parse")]` — this is the one check that reports a syntax
  error rather than skipping it, and the asymmetry with `A01` is deliberate. `A01` scans many files, so a
  broken one is skipped and `ruff` reports it. `A08` scans exactly one file, and if that file does not
  parse then the check has no answer at all. **A check that cannot look must say so** rather than return an
  empty list of findings, which is indistinguishable from a clean result.
- `ast.AnnAssign | ast.Assign` catches both `REGISTRY: dict[str, ServerPolicy] = {...}` and a bare
  `REGISTRY = {...}`. Day 40's version is annotated; the check accepts either, because the shape of the
  declaration is not the thing being audited.
- `node.target` for the annotated form and `node.targets[0]` for the plain one — the AST names them
  differently, singular and plural, and mixing them up is the most common error when writing this kind of
  check.
- The loop does not `break` on the first match, so a file that assigns `REGISTRY` twice leaves the check
  looking at the **last** assignment, which is the one that wins at runtime. A `break` here would audit a
  value that never exists.
- `isinstance(registry, ast.Dict) and not registry.keys` is the empty test. A registry built by a function
  call — `REGISTRY = load_policies()` — is not an `ast.Dict`, so nothing fires, and that is honest: the
  check can read a literal and cannot evaluate a function.
- `getattr(node.func, "id", "") != "ServerPolicy"` matches the constructor by name. It misses
  `filtering.ServerPolicy(...)`, which is an `ast.Attribute` — the same gap `A05` has, and it is in the hub
  as a `TODO(me)` for the same reason.
- `next((kw.value for kw in node.keywords if kw.arg == "allow"), None)` finds the keyword argument, with
  `None` when it is absent. Day 40 gave `allow` **no default** in the dataclass precisely so a missing one
  is a construction error, and this check catches it earlier, in a place that names the file and the line.
- `isinstance(allow, ast.Tuple | ast.List) and not allow.elts` — empty literal. `allow=()` and `allow=[]`
  both land here. An `allow` built from a variable is not judged, for the same reason the registry is not.
- The message says **"admits everything"**, not "is empty". The reader needs the consequence, not the
  observation, because the observation reads as harmless and the consequence does not.

The red case, in the fixture — both failures in three lines:

```python
# a scratch copy of sutra/mcp/filtering.py
REGISTRY: dict[str, object] = {}

VENDOR = ServerPolicy(launch=None, allow=())
```

**Line by line:**

- `REGISTRY = {}` with the annotation intact. The file looks finished. Nothing about it says "unwired".
- `allow=()` reads, to almost everybody, as "this server may offer nothing". Day 40 measured that it means
  the opposite.
- `VENDOR` is assigned outside the registry, which is its own quiet problem: a policy object that exists and
  is not in the lookup table is a policy nobody consults. `A08` does not check that, and noticing it is one
  of the hub's `TODO(me)` items.

## When it breaks

**The allowlist is populated and the filter is not applied.** `REGISTRY` is full, every `allow` names real
tools, and somewhere a toolset is constructed without consulting any of it. `A08` is green and the policy is
decoration. Day 40's
[4.1 — One door, and a check there is one](../../../day-40-filtering-and-allowlists/parts/04-the-policy-module/4.1-one-door-and-a-check-there-is-one.md)
is the rule that catches that shape, and it is a genuine gap in this audit: `A08` checks the policy's
contents, and nothing here checks that the policy is consulted.

**The names in `allow` are stale.** They were correct when they were reviewed, and the server renamed a
tool. The filter now admits a list of names that partly do not exist, so the agent silently has fewer tools
than the policy claims — a failure in the safe direction, which is why it goes unnoticed for months. The
detector for that is Day 40's resolve step, which compares the policy against a live listing, and it needs a
running server, which is why it is not in the static audit.

**The check fires on a deliberately empty registry.** Early in Phase 5 there genuinely is no server in the
policy yet, and `A08` blocks the gate. That is correct behaviour and it is also friction, and the honest
response is not to soften the rule but to notice that the finding has a **day number** — filed to Day 40 —
and that the gate for Phase 5 is a different gate from the one for Phase 6.

## In production

**What a professional writes instead:** the policy is data, not Python — a YAML or TOML file validated
against a schema at load — and the audit validates the file rather than parsing source. That buys two
things. The policy can be reviewed by somebody who does not read Python, which widens the set of people who
can meaningfully approve a change, and the check becomes schema validation, which cannot be defeated by
writing the same policy in a slightly different syntax. The reason this repository parses source instead is
that `ServerPolicy.launch` holds live connection parameters, and turning those into data is a refactor Day
40 chose not to do.

**What degrades at scale:** the allowlist becomes a list of everything, one exception at a time. Every
addition is individually reasonable, nobody ever removes a name, and after a year the policy admits the full
surface of every server while still being technically an allowlist. Teams that survive this measure
**usage** — which permitted tools were actually called in the last period — and prune from the measurement
rather than from memory.

**The failure mode that only appears with real traffic** is the ambiguous tool name. Two servers offer a
tool called `search`, both are allowed by their own policies, and which one a call reaches depends on
registration order. Day 40's
[6.1 — Two servers, one tool name](../../../day-40-filtering-and-allowlists/parts/06-the-posture/6.1-two-servers-one-tool-name.md)
is that failure. No policy is violated; the two policies are individually correct and jointly ambiguous,
which is a class of bug a per-record check can never see.

**The review comment a senior engineer leaves:** *"`allow=()` here does not mean what it looks like it
means — in ADK an empty filter admits every tool the server offers. Write the names you actually want, even
if that is one name, and if the intent really is to admit nothing then remove the server from the registry,
because a policy that says nothing and means everything is the worst artefact we could leave for the next
person."*

**The interview question:** *"Allowlist or denylist for tools, and why?"* The honest spoken answer:
*"Allowlist, and the argument isn't about strictness — it's about what happens to a thing nobody thought
of. A denylist gives the wrong answer for anything new, and with MCP the server can add tools between one
listing and the next, so 'new' is routine rather than exceptional. The trap I'd flag from experience is
that an empty filter in ADK doesn't mean deny-all, it means no filter at all, so a policy that reads as
maximally restrictive is actually wide open. I check for that specifically in the build, because it's the
one mistake in this area that survives review — everyone reads an empty tuple as 'nothing'."*
