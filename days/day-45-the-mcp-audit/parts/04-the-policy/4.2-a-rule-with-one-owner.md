# 4.2 — A09: a rule with one owner

## One-line answer

The `:free` suffix rule already has a linter, so `A09` does not re-implement it — it reads the `check)`
target in `m` and fails if the stages this audit assumes are not actually wired in, which is how a rule
gets exactly one owner and one place where it can be switched off.

## The story

There is a money plant on the landing between the two flats, and everybody agrees it is nice to have.

For a while it does well, because both households water it. Then it starts looking waterlogged, so one of
them cuts back, quietly, without saying anything — there is no conversation to be had, it is a plant. The
other family notices it perking up and concludes their watering is working, and carries on.

Then the second family goes away for two weeks.

The first family are not neglecting it. They stopped watering it for a good reason and the reason was
correct at the time. Nobody made a mistake. It is simply that the question *"is this plant watered?"* had
no owner, so the answer was an emergent property of two people's independent decisions, and there was no
moment at which anybody was responsible for noticing that the answer had become no.

The plant that survives is the one where somebody says out loud: I water it. Not because they are better at
watering. Because now there is one person whose absence is visible.

## The idea in plain language

Every rule in a build needs exactly one owner: one piece of code that decides it, in one place that runs
it. Two implementations of the same rule is not redundancy — it is the money plant. Each one can be
relaxed on the assumption that the other is strict, and neither change looks wrong on its own.

This day is where the temptation is strongest, because an audit's natural instinct is to check everything.
Addendum 02 has a rule about model strings: **an `openrouter/` model string must end in `:free`**, because
the missing suffix bills a paid model. That is a real rule, an MCP-adjacent one now that Phase 6 servers
can launch with model configuration in their environment, and it would be four lines to add here.

It is not being added, and the reason is a decision rather than laziness. Day 31 wrote
`tools/lint_free_suffix.py` and wired it into `./m check` as its own stage. It owns the rule. If this
audit also checked it, then two things follow. A change to the rule — a new provider prefix, a different
suffix — has to be made twice, and the second one is the one that gets forgotten. And a finding appears
twice in the gate's output, from two stages, which trains the reader to skim.

So `A09` does the useful thing instead. It checks that **the stages exist**:

| Stage the gate must run | Owner | What it decides |
| --- | --- | --- |
| `tools.lint_skills` | Day 30 and Day 31 | skill folder structure |
| `tools.lint_free_suffix` | Day 31 | the `:free` suffix rule |
| `tools.mcp_audit` | today | these ten checks |

That is a rule about the **gate**, which no other stage owns, and it closes the specific hole where
somebody deletes a line from `m` and everything stays green because the check that would have complained
is the one that was deleted.

## Why Sutra needs it

Because `m` is one file, edited by hand, and it is the only thing standing between a broken repository
and a commit.

Day 31's
[5.3 — The swallowed exit code](../../../day-31-the-quality-gate/parts/05-the-gate-that-lied/5.3-the-swallowed-exit-code.md)
covered one way a stage stops mattering: a `|| true` appended in a hurry. There is a simpler one that is
harder to spot, because it leaves nothing behind. Somebody comments out a stage to get an urgent fix
through, and does not uncomment it. The gate is green, it is faster than it used to be, and nothing in the
output says a stage is missing — a gate reports what ran, never what did not.

This matters more today than it did on Day 31, because today adds the third stage to that block and Phase 7
starts tomorrow. An audit that is in the repository and not in the gate is a script, and a script is run by
whoever remembers it.

## The mechanism

First, what `./m check` runs today. This is the `check)` target as it stands in `m` on 2026-09-05, before
today's edit:

```bash
  check)
    uv run ruff check .
    uv run ruff format --check .
    # pytest exits 5 for "no tests collected". Before Day 23 there are none, and an empty suite
    # is not a failure - so 0 and 5 pass and everything else stops the gate.
    uv run python -m pytest -q -m "not live" || [ $? -eq 5 ]
    uv run python scripts/depth_check.py
    uv run python scripts/trace.py
    uv run python scripts/wiki.py
    echo "OK all green"
    ;;
```

**Line by line:**

- Six stages, cheapest first, exactly as Day 31's
  [1.2](../../../day-31-the-quality-gate/parts/01-what-a-gate-is/1.2-six-stages-cheapest-first.md)
  describes: two lint stages that read text, then the test suite that imports the framework, then the three
  generators that walk `days/`.
- Day 31's two linter stages are **not in this listing**, and that is not an error in the day document —
  it is the state of the repository. Day 31 tells the learner to add them; the learner types every line of
  project code in this curriculum, and until they do, `m` holds what Day 0 wrote. `A09` reports it, which
  is the check working.
- `set -euo pipefail` at the top of the file is what makes each line a gate: a non-zero exit anywhere
  aborts the script ([Day 31's
  1.3](../../../day-31-the-quality-gate/parts/01-what-a-gate-is/1.3-the-line-that-makes-it-stop.md)).
  Nothing in the target needs an `if`.
- `echo "OK all green"` is the last line, and it is reachable only if every stage above it exited zero.

Today's edit is one line:

```diff
   check)
     uv run ruff check .
     uv run ruff format --check .
     uv run python -m tools.lint_skills
     uv run python -m tools.lint_free_suffix
+    uv run python -m tools.mcp_audit
     # pytest exits 5 for "no tests collected". Before Day 23 there are none, and an empty suite
     # is not a failure - so 0 and 5 pass and everything else stops the gate.
     uv run python -m pytest -q -m "not live" || [ $? -eq 5 ]
```

**Line by line:**

- One `+` line. The two lines above it are Day 31's, shown here so the position is unambiguous.
- `uv run` like every other stage, so the audit runs under the project's Python 3.12 rather than whatever
  `python` is first on the path.
- `python -m tools.mcp_audit`, **not** `python tools/mcp_audit.py`. The `-m` form is what puts the
  repository root on `sys.path` so `tools` is importable as a package; the path form fails with
  `ModuleNotFoundError: No module named 'tools'`, which is Day 31's
  [4.2](../../../day-31-the-quality-gate/parts/04-wiring-the-gate/4.2-the-module-the-script-cannot-find.md)
  in full. This module does not currently import a sibling, so it would run either way — and it uses `-m`
  anyway, because three stages in one block should be invoked identically and the next person will copy
  whichever line they happen to look at.
- **Position: after the two linters, before pytest.** The audit parses a few dozen small files with
  `ast` and imports nothing outside the standard library, so it belongs with the cheap decisive checks. A
  run that is going to fail on a held connection should fail before it pays for importing `google-adk`.
- No `if`, no error message, no `&&`. The module already prints findings with file and line, and `set -e`
  handles the exit code. A wrapper that adds *"mcp audit failed"* is a line of noise above the useful
  output.

And the check that the edit actually happened:

```python
# tools/mcp_audit.py
def check_gate_stages(root: Path) -> list[Finding]:
    """A09 one rule one owner: the stages this audit relies on are in the gate."""
    driver = root / "m"
    if not driver.exists():
        return [_missing("A09", "m", "day 0")]
    text = driver.read_text(encoding="utf-8")
    body = text.split("check)", 1)[-1].split(";;", 1)[0]
    findings = []
    for stage in ("tools.lint_free_suffix", "tools.lint_skills", "tools.mcp_audit"):
        if stage not in body:
            findings.append(Finding("A09", "block", "m", f"check) does not run {stage}"))
    return findings
```

**Line by line:**

- `text.split("check)", 1)[-1].split(";;", 1)[0]` isolates the `check)` branch of the `case` statement:
  everything after the first `check)` and before the first `;;` that follows it. Crude string slicing
  rather than a shell parser, and the reason is proportion — writing a shell parser to check three
  substrings would be a larger project than the audit.
- Isolating the branch is what makes the check meaningful. A plain `if "tools.mcp_audit" not in text`
  would pass on a line that was accidentally added to the `done)` branch, which is Day 31's
  [4.1](../../../day-31-the-quality-gate/parts/04-wiring-the-gate/4.1-two-lines-in-the-driver.md)
  *"the stage is there and the gate is still green"* failure, in reverse.
- The stage names are module paths, not full command lines. Matching `uv run python -m tools.mcp_audit`
  exactly would fail on a harmless change of invocation; matching `tools.mcp_audit` asks the question the
  rule is actually about, which is whether the module is reached.
- `tools.mcp_audit` is in its own list. **The audit checks that the audit runs**, which sounds circular
  and is not: this module can be invoked directly by a person at any time, and the check is asking whether
  the *gate* invokes it. A rule that only fires when somebody remembers to run it is the money plant.
- The severity is `block` on all three. A missing stage is not a style issue; it is a rule with no owner.

Measured on 2026-09-05, against this repository:

```text
  [A09] block m: check) does not run tools.lint_free_suffix
  [A09] block m: check) does not run tools.lint_skills
  [A09] block m: check) does not run tools.mcp_audit
```

Three findings, and all three are honest. Two are filed to Day 31 — the day that adds those stages — and
one is today's own build step.

## When it breaks

**The stage is present and does nothing.** The line is in `m`, `A09` is green, and
`tools/mcp_audit.py` has a `main` that returns `0` unconditionally because somebody was debugging. The
gate runs it, it exits zero, everything is fine. `A09` checks wiring, not behaviour, and the only defence
against that one is the drill: plant a violation, run the gate, watch it stop at the right stage.
[6.1](../06-failure-lab/6.1-green-because-the-path-did-not-exist.md) is the version of this failure that
happens without anybody debugging anything.

**The stage moved to the wrong branch.**

```text
$ grep -n "mcp_audit" m
118:    uv run python -m tools.mcp_audit
```

One line, with a number well past the end of `check)`. `A09` still reports the stage as missing, because it
only reads the `check)` branch — which is the check being right about something a `grep` would get wrong.

**The whole `case` statement breaks.**

```text
m: line 92: syntax error near unexpected token `)'
```

`m` is the driver, so this stops `./m depth`, `./m done` and everything else, not just the gate. Recover
with `git diff m` and read what you actually changed. This is the standing hazard of editing the one file
every other command runs through, and it is why the edit is one line and is read back before being relied
on.

## In production

**What a professional writes instead:** the pipeline is declared in a configuration file the build system
reads, and required stages are enforced by branch protection at the forge rather than by a check inside the
pipeline. That is strictly better, because a check inside the pipeline can be removed by the same commit
that removes the stage, and a rule enforced outside it cannot. The version here is the honest one for a
repository whose gate is a shell script, and the property it buys — you cannot silently delete a stage —
is the same property, enforced one layer lower down.

**What degrades at scale:** the list of required stages goes stale. Somebody renames a module, the check
looks for a name that no longer exists, and it reports a missing stage that is actually present under a new
name. The finding is wrong, it is annoying, and the fix people reach for is to delete the check rather than
to update it. Setups that survive this generate the required list from the pipeline definition instead of
hard-coding it, so a rename updates both sides at once.

**The failure mode that only appears with real traffic** is the stage that is skipped conditionally. A
pipeline that runs the full gate on the main branch and a shortened one on pull requests looks reasonable
and means every change is merged after the shorter gate. Nothing was deleted, so no check for a missing
stage fires, and the rule that matters is enforced only after the code is already in.

**The review comment a senior engineer leaves:** *"This adds a second implementation of the `:free` rule.
We already have `lint_free_suffix` and it owns that rule. Two copies means the next change to it gets made
once, and the copy that goes stale is the one nobody remembers exists. If the concern is that the stage
could be removed from the gate, check for the stage — that's a different rule and nothing owns it yet."*

**The interview question:** *"Where do you draw the line on how much a build check should verify?"* The
honest spoken answer: *"One rule, one owner. If something already has a check, my new check verifies that
the existing one still runs rather than re-deciding it. Two implementations of one rule always drift, and
they drift in the dangerous direction — each gets relaxed on the assumption the other is strict, and
neither change looks wrong in review. The specific thing I do add is a check on the gate's own
composition, because that's the gap nothing else covers: every stage reports what it found, none of them
report that a stage was deleted, and a build script is exactly the file people edit under pressure."*
