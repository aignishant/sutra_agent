# 2.1 — Three schedulings

## One-line answer

A tool result has to reach the model, and on an open line there is a second question a request never
had to ask — **when should the model react to it?** The installed package answers it with a field and
three values: `SILENT`, `WHEN_IDLE` and `INTERRUPT`, documented as *"Controls when the model reacts
to the tool's response"*.

## The story

You inherit a car from an aunt and there is a switch on the dashboard you have never used. Small,
unlabelled except for a symbol you cannot interpret, sitting between two things you do understand.

You drive it for weeks without touching it. Then one wet evening you go through the glovebox looking
for something else and find the handbook, and there is one paragraph about that switch. Three
positions, a sentence each. It takes as long to read as it took to find.

And now you know two things you did not know that morning. What the switch does — and that you have
been driving around in the middle position because that is where the last person left it.

## The idea in plain language

Sections 1 established the round trip: the model asks for a tool, the runtime runs it, the runtime
hands the result back through the connection, the model answers. In a request/response agent that is
the whole story, because the model has nothing else to be doing.

On an open line it does. The caller might be mid-sentence. The model might be mid-answer. So handing
a result back is no longer just *delivery*, it is **timing**, and the framework exposes that as a
field on the tool rather than as a decision made at the call site.

Two fields on `BaseTool` decide how a tool behaves inside a session, and they answer different
questions:

| Field | The question it answers |
| --- | --- |
| `is_long_running` | does this tool return an answer, or a receipt it will redeem later? |
| `response_scheduling` | when the answer does arrive, should the model react to it now, later, or not out loud? |

This part is about the second. It is a small field with a large consequence, and — like the switch on
the dashboard — the important thing about it is not that it exists but that it has a value right now,
whether or not anybody chose one.

## Why Sutra needs it

Because the build brief asks you to declare, on at least one tool in `sutra/livetools.py`, how its
result comes back — and the gate checks for it. Not because a particular value is correct, but
because the alternative is a field left at whatever the default is for a tool nobody thought about
in these terms.

And because this is Principle 8's ordinary working shape. The field is not in a tutorial this
curriculum read; it is in the package that is installed, with a docstring the package's authors
wrote, and reading it takes one command. Every claim below is that docstring or an enum member, and
where this day has not run something it says so.

Four things in that output are worth reading slowly.

**There are four enum members and three meanings.** `SCHEDULING_UNSPECIFIED` is the protocol's way of
saying nothing was chosen, which is not a fourth behaviour — it is the absence of a choice, and it
pairs with the field's own default of `None`.

**The docstring says "Live API only".** This field does nothing in a request/response agent, which is
why it has not come up in seventy-five days. It is one of the small number of things that exist only
because a connection stays open.

**And it says the field is *ignored* by models that do not support asynchronous function calling.**
That is a real and slightly uncomfortable property: a setting can be correct, deliberate, reviewed —
and inert, with nothing telling you. Part [2.2](2.2-choosing-one.md) takes that up.

**The last paragraph of the output is the script being honest about itself.** Nothing on this day has
run any of the three values against a model. Day 74 part 4.2's free-quota check parked the paid Live
API and recorded that it could not even verify the free-tier status, and that has not changed. What
this part establishes is what the framework offers and what its authors say it does — a contract, not
an evaluation — and the difference matters enough to be printed by the script rather than left to a
reader's charity.

Here is the slicing that produces the quoted block, because a document that quotes a docstring should
show how it got it:

```python
    src = inspect.getsource(BaseTool)
    start = src.index("response_scheduling:")
    block = src[start : src.index('"""', src.index('"""', start) + 3) + 3]
```

**Line by line:**

- `inspect.getsource(BaseTool)` reads the class as it is installed, so the quotation cannot drift from
  the package the way a copied paragraph in a document would.
- `src.index("response_scheduling:")` finds the field's declaration. It is a plain substring search,
  which is crude and correct here: the string appears once in the class.
- The nested `src.index('"""', ...)` calls find the opening triple quote and then the closing one, and
  `+ 3` includes it. Slicing a docstring out of source by counting quotes is the sort of thing that
  would be fragile in a library and is fine in a script whose only job is to show you something.
- Nothing is reformatted, which is why the pasted output carries the package's own indentation and its
  trailing whitespace on blank lines. A quote that has been tidied is a quote you cannot check.

## When it breaks

**A field that is ignored looks exactly like a field that is working.** The docstring says models
without asynchronous function calling ignore it. So `INTERRUPT` on a model that does not support it is
not an error, a warning or a log line — it is nothing, and the tool behaves as it would have anyway.
That makes this one of the settings you cannot verify by reading your own code; you verify it by
observing behaviour, against a model, which this day does not have.

**The output above is version-specific and dated.** `2.7.1` on 2026-09-06 offers these four members
and this docstring. The correct response to an upgrade is to run the script again rather than to trust
this page — the same instruction Day 74 part 4.1 gave for `trigger_sources` and for the same reason
(P7, P8).

**And the enum is a shape, not a manual.** Three sentences tell you what the values mean and nothing
about what a caller experiences for each. Turning those sentences into a choice is part 2.2's job and
it requires judgement the package cannot supply.

## In production

**What this field actually is: a courtesy setting with an API.** Most configuration decides what a
system can do. This one decides how it behaves towards a person who is mid-sentence, which is a
different kind of decision and tends to be made by whoever was closest to the code rather than by
whoever thinks about the product.

**What a professional does on finding a field like this.** Reads the package rather than the tutorial,
records the version and the date, and — the step people skip — checks what the current value is,
because a default is a value. The dashboard switch was already in a position.

**What changes at scale.** One tool with a considered scheduling is a nice detail. Thirty tools, added
over two years by different people, of which four have a scheduling and twenty-six inherited the
default, is the normal end state — and it is impossible to reason about because the behaviour of the
system is now the accumulated history of who read the docstring.

**The review comment a senior engineer leaves:** *"Where did you read that? Put the ADK version and
the date next to it in the docstring, because that field's behaviour is documented as Live-API-only
and it's ignored outright by models that don't support async function calling — I don't want us
believing a setting is doing something. And when you set it, set it explicitly on every tool,
including the ones where the default is what you want. A field that's set on four of thirty tools
tells the next person nothing about the other twenty-six."*

**The interview question:** *"How does a tool result get back to a model in a live session, and what
can you control about it?"* An honest answer: *"The runtime runs the tool and sends the result back
over the same connection as a function response — that part is the same as any agent. What's
different on an open line is that you can control **when the model reacts** to it, because the model
might be mid-answer and the caller might be mid-sentence. In ADK that's `BaseTool.response_scheduling`,
and the values are silent, when-idle and interrupt: feed it back without prompting a turn, wait until
the model is idle, or react immediately. I read that off the installed package rather than from docs
— the docstring is explicit that it's Live API only and that models without asynchronous function
calling ignore it entirely, which is worth knowing because a setting that's ignored looks identical to
one that's working. I haven't run the three against a live model; that's a contract I've read, not a
behaviour I've measured."*
