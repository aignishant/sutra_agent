# 1.3 — The line that goes dead

## One-line answer

With the lookup written as `await asyncio.sleep(...)`, **4 slices** of the caller's audio reach the
model's connection while the tool is still running; with the identical lookup written as
`time.sleep(...)`, **0** do — and the tool is declared `async def` in both cases.

## The story

There is a stretch of road near you down to one lane, with a stop-go board at each end.

It works. Traffic goes one way for a while, then the other, and everybody grumbles and gets through.
And on the afternoon the crew is waiting for a part to arrive, the digger sits exactly where it was,
in the middle of the lane, because that is where it stopped. Nothing is being dug. The road is
blocked anyway.

Somebody who has done this before would have reversed it into the layby while they waited. Same
delay, same part, same arrival — and the road open the whole time. The difference is not how long
the wait was. It is whether the thing that was waiting got out of the way while it waited.

## The idea in plain language

Part [1.2](1.2-the-sequence-measured.md) established the round trip: the model asks for a tool, the
runtime runs it, the result goes back, the model answers. This part is about step two, and about
something that is happening at the same time as step two — the task that reads the caller's
microphone.

Both of those live in one **event loop**: a single thread that runs one piece of work at a time and
switches between them whenever a piece of work *awaits* something. The switching is co-operative. The
loop cannot take control back from a piece of work that has not offered it; it can only pick up the
next task when the current one says *I am waiting, carry on without me.*

`await` is how a piece of work says that. `time.sleep` is a piece of work that does not.

So there are two ways to write a tool that waits half a second, and they produce two very different
sessions:

| The tool waits with | Does the loop get control? | What happens to the caller's audio |
| --- | --- | --- |
| `await asyncio.sleep(...)` | yes, immediately | delivered while the tool runs |
| `time.sleep(...)` | no, not until it returns | not delivered at all until afterwards |

And here is the part that makes this worth measuring rather than asserting. **Both versions are
`async def`.** Declaring a function `async` does not make it non-blocking. It makes it *awaitable* —
something the runtime can call and wait for — and what it does inside is a separate question. A tool
that is `async def` and calls a synchronous database driver blocks the loop exactly as thoroughly as
one that calls `time.sleep`, and it looks correct in every review that checks for the keyword.

## Why Sutra needs it

Because the desk is about to have tools on a voice line, and every tool this repository has written
so far was written for a request. Nothing about them was wrong. They were simply never in a room with
somebody who could hear the silence.

And because the gate's third and fourth checks are exactly this: every tool in `sutra/livetools.py`
must be a coroutine function, and none of them may contain `time.sleep`. The hub is honest that the
second check is a lint for the easy case — a blocking HTTP client is invisible to it — which makes
this one of the places where the reader has to carry the rule rather than lean on the check.

## The mechanism

The whole ablation is one `if`, and what does **not** change across it is the point:

```python
async def check_order(order_id: str) -> dict:
    """Look up an order in the warehouse system.

    Args:
        order_id: the order reference the caller read out.

    Returns:
        The order's status. Slow, because looking things up in somebody else's system is slow.
    """
    if BLOCKING:
        # Does not yield. Nothing else in this process runs while it waits - including the task
        # reading the caller's microphone. A synchronous database driver, a blocking HTTP client
        # and a busy loop all behave exactly like this line.
        time.sleep(LOOKUP_SECONDS)
    else:
        # Yields. The event loop is free to run everything else while this tool waits.
        await asyncio.sleep(LOOKUP_SECONDS)
    return {"order": order_id, "status": "shipped"}
```

**Line by line:**

- `async def` is on the outside of both branches. Whatever this function does inside, the runtime
  awaits it the same way, which is why the keyword tells a reviewer nothing about whether it blocks.
- `time.sleep(LOOKUP_SECONDS)` occupies the thread. It is not slow *and* co-operative; it is slow and
  silent, and the loop has no way to interrupt it.
- `await asyncio.sleep(LOOKUP_SECONDS)` hands control back for the same duration. The tool takes just
  as long — this is not an optimisation and nothing about it is faster.
- The `return` is identical on both paths, so the model receives the same result either way. Nothing
  downstream of the tool can tell which branch ran, which is exactly why nothing downstream reports a
  problem.

The measurement drives one real session in which the caller keeps talking while the desk looks
something up:

```bash
cd days/day-76-vad-and-non-blocking-tools/lab
uv run python freeze.py; echo "exit: $?"
```

**Line by line:**

- `freeze.py` sends the question, then starts a second task that pushes four slices of audio into the
  live queue, spaced so that all four fall inside the lookup.
- The connection timestamps everything that passes through it, so "arrived during the tool call" is a
  fact about ordering rather than an inference.
- `echo "exit: $?"` prints the exit code, because the claim is the exit code.

Measured on 2026-09-06:

      caller says something

    | caller audio arrives

  The line stayed open. Audio reached the model's connection while the lookup was

Now the same call with the same tool, waiting the other way:

```bash
uv run python freeze.py --blocking; echo "exit: $?"
```

**Line by line:**

- `--blocking` sets the module flag that selects `time.sleep`. The caller sends the same four slices
  at the same moments; the agent, the model, the question and the duration are unchanged.

Measured on 2026-09-06:

```text
the lookup: time.sleep - blocking (ablation)
the lookup takes 0.5s

  what the connection saw, in order:
      caller says something
      model asks for the tool
      tool result in: check_order
      model answers
      hang up

  audio slices sent while the tool ran   0
  the session ended                      yes

  Nothing arrived between asking for the tool and getting it back. The caller spoke
  and the line was not listening, which on a voice call is indistinguishable from
  the system having hung up.
```

| | `await` | `time.sleep` |
| --- | --- | --- |
| audio slices delivered during the tool | **4** | 0 |
| lines in the connection's log | 9 | 5 |
| the session ended cleanly | yes | yes |
| anything raised | no | no |
| exit code | 0 | 1 |

**Read the second row before the first.** The blocking run's log is not the same log with four lines
moved to the end. It is four lines *shorter*. The audio did not arrive late — it never appears at all,
because the task that would have delivered it never ran, and by the time the loop was free the caller
had been cancelled along with the rest of the run.

**And read the third and fourth rows together.** Both sessions ended cleanly and neither raised
anything. The tool returned the right answer, the model gave the right reply, the caller was told
their order had shipped. Everything the system was asked to do, it did. What it stopped doing, for
the length of the lookup, was listening — and there is no exception for that, because not listening
is not an error condition. It is an absence.

## When it breaks

**The easy case is the one the gate catches, and it is not the one you will meet.** Nobody ships
`time.sleep` in a tool. What they ship is a synchronous database driver, an HTTP client that was
chosen before anything was asynchronous, a library that reads a file, or a loop that does real work
over a large list. Every one of those behaves exactly like the ablation, and none of them contains the
string the gate greps for.

**A tool can also block for a moment rather than for half a second, which is worse in a specific
way.** A short block does not produce a symptom anybody can describe; it produces audio that arrives
in bursts and voice detection that behaves oddly, and the investigation goes to the microphone, the
network and the model before it goes to the tool.

**The lab's caller is a task in the same process, which flatters the measurement in one direction and
not the other.** A real caller's audio arrives over a network into a server that is also running the
event loop, so there are more places for the same failure to appear and none fewer. What the lab
demonstrates — that a blocking tool stops the loop delivering input — is the mechanism, and the
mechanism does not become gentler with more layers on top of it.

**One thing this part does not show:** what the caller *hears*. There is no speaker here. The audio
was going in, not coming out, and the outbound half of a frozen line is the same failure pointed the
other way — the model's own words stop being delivered too. It is the same cause and the same cure,
and this lab only measured the inbound direction.

## In production

**How this reaches you as a bug report.** Not as "a tool blocked the event loop". As *"it stops
hearing me when it's looking something up"*, or more often as *"it cuts me off"* — because from the
caller's side, a line that stops accepting speech and a system that has decided you finished talking
are the same experience. Section 3's voice-activity settings are the first place people look, and
they are the wrong place.

**What a professional does about the whole class, rather than about this tool.** Runs blocking work
somewhere other than the loop. Every asynchronous runtime provides a way to hand a synchronous call to
a thread and await the result, and using it turns a blocking dependency into a well-behaved tool
without rewriting the dependency. The rule worth carrying is simpler than the mechanism: **inside an
async tool, everything you call is either awaitable or it is blocking**, and the second kind needs
somewhere else to run.

**What changes at scale.** One blocked loop stops one session on one worker — but that worker is
almost certainly serving several callers, and the block is not per-session. Day 75 part 4.1 argued
that capacity is connections held open; this is the other half of it, because one badly written tool
freezes every caller on that process, not only the one who asked for it.

**What to measure, given that nothing raises.** The gap between input events. A line that is being
listened to produces a steady trickle of inbound audio; a frozen one produces a hole. Nothing in the
framework will tell you about the hole, and part
[4.1](../04-in-production/4.1-the-silence-you-cannot-see.md) is about building the signal for it.

**The review comment a senior engineer leaves:** *"This tool is `async def` and then calls the
synchronous client, which means it blocks the loop for the whole lookup — every caller on this worker
stops being heard, not just this one. Run it in a thread and await that. And add the test that starts
the tool and asserts something else gets a chance to run while it's waiting; the `async def` keyword
is what everybody checks and it's exactly what doesn't tell you anything here."*

**The interview question:** *"You made your tool `async def` and the voice agent still freezes. Why?"*
An honest answer: *"Because `async def` makes a function awaitable, not non-blocking. The event loop
is one thread that switches between tasks only when a task awaits something, so a tool that's declared
async and then calls `time.sleep`, or a synchronous database driver, holds the thread for the whole
call and nothing else runs — including the task reading the caller's audio. I measured it with an
identical tool either way: with `await asyncio.sleep` four slices of the caller's audio reached the
model's connection during the lookup; with `time.sleep`, none did, and they didn't arrive late — they
never appeared in the log at all. Both runs ended cleanly and neither raised anything, which is what
makes it nasty. The fix is to run blocking work off the loop, in a thread, and the rule I'd give a
team is that inside an async tool everything you call is either awaitable or it's blocking, and the
second kind needs somewhere else to run."*
