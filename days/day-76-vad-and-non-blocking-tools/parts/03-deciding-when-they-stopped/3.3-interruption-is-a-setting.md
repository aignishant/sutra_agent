# 3.3 — Interruption is a setting

## One-line answer

Whether the caller speaking cuts off the answer is not a property of the framework and not a bug to
avoid — it is a field with a name, `ActivityHandling`, whose value `NO_INTERRUPTION` is exactly the
ablation Day 75 part 2.2 built to prove barge-in mattered, which means somebody has to choose it and
there are flows where the "wrong" choice is the right one.

## The story

There is a little switch on the side of your phone that silences everything.

You flick it before a meeting, because the alternative is your phone singing in a quiet room while
somebody is presenting. That is the switch doing its job perfectly. Nothing is allowed to interrupt,
and nothing does.

Then you walk out, put the phone in your bag, and forget about it. That afternoon the courier stands
outside your door with a parcel that needs a signature, rings you twice, waits, and takes it back to
the depot. Your phone did exactly what you told it. The screen lit up in a dark bag. That is the
same switch, in the same position, doing the same job — and this time it cost you a trip across
town.

Here is the part worth sitting with. There is no correct position for that switch. There is a
correct position *for a meeting* and a correct position *for an afternoon when somebody is trying to
reach you*, and they are opposite. The switch is nearly always in whichever position you last left
it, which means most of the time nobody is choosing at all: the meeting is choosing on the courier's
behalf, from this morning.

A voice agent has that switch. It decides whether the caller speaking is allowed to stop the answer.
Both positions are right somewhere, and leaving it where it is is itself a decision — made earlier,
for a different situation, by somebody who was not thinking about this call.

## The idea in plain language

**Barge-in** is the caller talking over the agent while the agent is still speaking, and expecting
the agent to stop. Day 75 part 2.2 is where the curriculum met it and measured it.

That measurement was built as an **ablation** — a pair of runs identical in every respect except one
switched-off idea, so that the difference between the two runs is the idea's worth. One connection
honoured interruptions; the other ignored them. The numbers were not close. With interruptions
honoured, the caller heard **3 of a 6-chunk answer** and an `interrupted` event appeared in the
stream. With them ignored, the caller heard all **6**, then a second complete answer on top — **12
chunks in total** — with no such event, no error, and a session that ended cleanly both times.

Day 75 treated the second run as the wrong way to build a voice loop, and for that call it was.

Here is what has changed today. Part [3.1](3.1-the-knobs.md) read the installed package's voice
settings and printed them, and one of the things it printed is an **enum** — a fixed, named set of
allowed values for a field, where each name in the set is an **enum member**. The enum is
`types.ActivityHandling`, and it has three members:

- `ACTIVITY_HANDLING_UNSPECIFIED`
- `START_OF_ACTIVITY_INTERRUPTS`
- `NO_INTERRUPTION`

Yesterday's ablation has a name in the protocol. It is not a hack, not a bug, not a thing you avoid
— it is a supported configuration with a spelling, sitting in the same enum as the behaviour Day 75
argued for.

**Say what that does to how you read an ablation.** An ablation shows that an idea mattered *in the
situation you measured it in*. It is an argument about a context, not a universal verdict. A switch
that makes a system behave worse in one situation is very often the same switch that makes it behave
better in another — which is why the protocol offers both positions rather than hard-coding the one
that won yesterday's measurement. When you read "we turned it off and it got worse", the honest next
question is *for whom, doing what*.

**State the limit before going further.** Nothing on this day has applied `ActivityHandling` — or
any other voice-activity field — to a model. Part 3.1 read these names off `google-adk==2.7.1` and
`google-genai` as installed on 2026-09-06 and printed them. What follows is a census plus reasoning
about what the three names denote. It is not a measurement, and the difference matters enough to say
twice.

## Why Sutra needs it

Because `sutra/voice.py` is going to answer calls, and one of those calls is going to include a
sentence the desk is not allowed to be talked out of.

The build brief in the hub asks you to decide what the caller hears while a tool runs. This part
asks the adjacent question: whether the caller is allowed to stop what they are hearing. Both are
settings on the same session, both have a default, and the default was chosen by the protocol's
authors for a general assistant rather than by you for your flow.

There is also a specific hazard for Sutra. Day 75 part
[2.3](../../../day-75-the-bidi-voice-loop/parts/02-talking-over/2.3-what-the-client-does.md) built
the client half of barge-in: on an `interrupted` event, stop playback, discard the buffer, then
render what comes next. If a later day sets `NO_INTERRUPTION` on the session while that client is
still stopping the speaker on its own, Sutra has two mechanisms with different opinions. *When it
breaks* returns to this, because it is the failure most likely to be introduced by a one-line change
that reads as obviously correct.

## The mechanism

Part [3.1](3.1-the-knobs.md) owns the census and prints the full surface; this part uses one loop
out of it. From `lab/vadconfig.py`, the loop that prints the enums — shown here dedented to column
0, because on disk it sits inside `main()` at one level of indentation:

```python
for enum_name in ("StartSensitivity", "EndSensitivity", "ActivityHandling", "TurnCoverage"):
    enum = getattr(types, enum_name)
    print(f"  types.{enum_name}")
    for member in enum:
        print(f"    {member.name}")
    print()
```

**Line by line:**

- `for enum_name in (...)` walks the four enums by **name**, as strings, rather than importing four
  symbols at the top of the file. That choice is the whole point of the next line.
- `enum = getattr(types, enum_name)` fetches the enum object off the `types` module by that string
  at the moment the script runs. The script therefore reports **what is installed**, not what was
  importable when the file was written. If a future version of `google-genai` renames or removes one
  of the four, this raises `AttributeError: module 'google.genai.types' has no attribute
  'ActivityHandling'` and the script stops — which is the honest failure. A top-of-file import would
  fail the same way, but a hand-written list of members would not fail at all: it would keep
  printing yesterday's names about today's package, confidently and wrongly. This is Principle 8 as
  code — verify the API on the day it is used, by reading it rather than remembering it.
- `for member in enum:` iterates the enum, which yields its members **in declaration order**. That
  is why `ACTIVITY_HANDLING_UNSPECIFIED` prints first: it is where the protocol put it, not where an
  author of this curriculum decided it should go. Ordering you did not choose is evidence; ordering
  you did choose is an opinion, and it is worth knowing which one you are reading.
- `print(f"    {member.name}")` prints `member.name` and deliberately not `member.value`. The value
  is the wire representation — an implementation detail of how the setting travels to the service.
  The name is what you type in your own code, so the name is what a reader needs.
- The bare `print()` at the end separates the four blocks. Cosmetic, and mentioned only so that no
  line in the block is left unexplained.

Where this field lives, from part 3.1's census: `activity_handling` is a field on
`types.RealtimeInputConfig`, alongside `automatic_activity_detection` (part
[3.2](3.2-sensitivity-is-a-trade.md)'s sensitivity knobs) and `turn_coverage`. A
`RealtimeInputConfig` reaches a session through `RunConfig.realtime_input_config`. So the path from
a decision to a running session is: you build a `RealtimeInputConfig` with an `activity_handling`
value, you hand it to `RunConfig`, and the session carries it.

### The three values

| Value | What the name denotes | A situation it is right for | What it costs there |
| --- | --- | --- | --- |
| `START_OF_ACTIVITY_INTERRUPTS` | Detected speech from the caller interrupts what is being said | Almost every conversational flow: a caller asking about an order, correcting an address, saying "no, the other one" | The answer in flight is thrown away — produced, transmitted and discarded. A caller who interrupts constantly costs more than a patient one, and a cough near the microphone can end a sentence nobody wanted ended |
| `NO_INTERRUPTION` | Detected speech does not interrupt; the turn continues | A passage that is only correct if it is delivered whole — a required disclosure, a safety instruction, an amount being read back for confirmation | A caller who genuinely needs to stop it cannot. Every one of them experiences a system that talks over them, and that is the exact complaint Day 75 measured at 12 chunks against 3 |
| `ACTIVITY_HANDLING_UNSPECIFIED` | Nothing was chosen | Nowhere, deliberately. It is what a session carries when the field was never set | The behaviour is whatever the far end defaults to, which is a real behaviour with real consequences that nobody on your team argued for |

### When `NO_INTERRUPTION` is right

Three cases, and the argument is the same shape in all three: **the cost of not stopping is smaller
than the cost of stopping half-way.**

**A legally required disclosure.** Some sentences have to be said in full because saying them is the
compliance record — the terms of a cancellation, the fee on a transfer, the fact that a call is
being recorded. If the caller starts talking part-way through and the passage stops, what you have
is a disclosure that was partly delivered, which for most purposes is a disclosure that was not
delivered. The caller is mildly annoyed at being talked over, once. The alternative is a record that
will not stand up. That trade is not close.

**A safety instruction.** "Do not restart it until you have switched off at the wall." A caller who
speaks over the middle of that hears the first clause and acts on it. This is the one where "the
caller wanted to interrupt" is not a good enough reason to let them, because what they wanted was to
skip a step, and the whole reason the sentence exists is that skipping the step hurts.

**A read-back for confirmation.** The agent reads an amount, or a delivery address, back to the
caller and waits for a yes. Read-back is only worth doing if the whole value is read: an amount cut
off after the first two digits and confirmed anyway produces a record that says "the caller
confirmed this" when the caller confirmed something shorter. Here `NO_INTERRUPTION` is not
politeness, it is the integrity of a field in your database. Note the shape: the risk is not that
the caller is inconvenienced, it is that a **half-confirmed record looks exactly like a confirmed
one afterwards.**

Notice what all three have in common. They are short, they are bounded, and their value is in
completeness rather than in responsiveness. That is the test — not "is this important?" (everything
is important) but "**is a half-delivered version of this worse than a delayed one?**"

### When it is wrong, which is most of the time

Everywhere else. A person on a phone expects to be able to interrupt, and that expectation was not
built by software — it was built by every conversation they have ever had. Interrupting is how
humans signal *I already know this*, *you have misunderstood me*, and *stop, that is the wrong
account*. Removing it does not make the agent sound more authoritative. It makes it sound like it is
not listening, because it is not.

The failure mode is also worse than it looks, and Day 75 part 2.2 has the number: the ablation did
not crash, time out or drop anything. It finished everything it started. The caller heard a complete
answer they had already abandoned and then a complete answer to the question they actually asked —
two voices' worth of talking where one was wanted, with a session that ended cleanly and nothing
anywhere reporting a problem. `NO_INTERRUPTION` applied to a general conversational flow reproduces
exactly that, on purpose, with the same silence in your logs.

So the default for a voice agent is interruption on. `NO_INTERRUPTION` is an exception you argue
for, per passage, in writing.

### The third value is not a third behaviour

`ACTIVITY_HANDLING_UNSPECIFIED` is the same argument parts
[2.1](../02-when-the-answer-comes-back/2.1-three-schedulings.md) and [3.1](3.1-the-knobs.md) both
made about their own enums: **a default is a value.** The enum has three members and two meanings.
The unspecified member is the protocol's way of recording that nobody chose, and it pairs with the
field simply being left unset.

That is not the same as harmless. The session still behaves some way. Somebody's caller still either
can or cannot interrupt. The only thing the unspecified value guarantees is that when you go looking
for the person who decided, there isn't one — and on the day a complaint arrives about a caller
being talked over, "we never set it" is a worse answer than either of the other two.

### And one field this day has not opened

`turn_coverage` is the third field on `types.RealtimeInputConfig`, next to `activity_handling` and
`automatic_activity_detection`. Part 3.1's census records that it exists and that it has three
values; what it names is **what counts as part of the turn**, and its values mention video.

This curriculum has never sent video to a model. Nothing here has read enough of the field's
contract to say what each of its values does, and describing behaviour on the strength of a member
name is exactly the invention Principle 8 forbids. So it is named as adjacent and unexplored rather
than skipped silently: it sits on the same config object as the setting this part is about, a reader
who prints the census will see it, and the honest thing to say is that it is there and that today's
knowledge of it stops at the field name.

## When it breaks

**This part is a census plus reasoning, not a measurement.** Everything above about *what each value
does to a call* is an argument from the name and from Day 75's numbers. The behaviour itself belongs
to the model at the far end of the connection, and no value of `ActivityHandling` has been sent to
one on this day. Read every claim here as "this is what the name denotes and what that would mean",
and put a measurement under it before you rely on it for a flow that matters.

**Two mechanisms with different opinions.** Suppose a session sets `NO_INTERRUPTION`, and the client
is the one Day 75 part 2.3 built — the one that stops playback the moment an `interrupted` event
arrives. There is now a setting saying *the caller speaking does not stop the answer* and a client
whose job is to stop the answer. What the caller experiences is whichever mechanism wins, and that
depends on details neither the setting nor the client makes visible: whether the event is emitted at
all under this configuration, and whether anything else in the stream trips the client's handler.
The point is not that one of them is wrong. It is that **the system now has two answers to one
question**, and the time to notice that is while writing the second one, not while reading a
complaint. If you set `NO_INTERRUPTION`, go and read your client's interrupt handler in the same
change, and write down which one is meant to be in charge.

**"Supported configuration" does not mean "supported by every model".** Part 2.1 recorded exactly
this caveat for `response_scheduling`, whose own docstring says the field is ignored by models that
do not support asynchronous function calling — a setting that is correct, deliberate, reviewed, and
inert, with nothing telling you. There is no reason to assume the voice-activity fields are
different in kind. A value that travels to a service that does not honour it fails the worst way a
setting can fail: silently, in the direction of the default, months after the person who set it
stopped thinking about it.

## In production

**The shape of a real answer is not one switch.** It is interruption on by default, off for the
specific passages that require completeness, and the switch made **per flow rather than per
product**. A team that sets `NO_INTERRUPTION` globally because of one disclosure has made every
ordinary call worse to protect one paragraph; a team that never sets it has a read-back that can be
half-confirmed. The unit of the decision is the passage, and that has a design consequence: the
flows that need completeness have to be separable in your code, so that the setting can be applied
to them and not to their neighbours. If your voice agent is one long prompt with no seams, this
decision cannot be made at all — which is a thing to notice before you need it.

**What gets recorded, so that a complaint is traceable.** "The system talked over me" is a support
ticket, and answering it requires knowing three things about that call: which `activity_handling`
value the session was configured with, whether an `interrupted` event was emitted, and what the
client did when it arrived. Day 75 part 2.2 already argued for recording *delivered* separately from
*produced*; this adds the configuration itself to the record. A voice system that logs the audio but
not the settings the audio was produced under can replay the complaint and still not explain it.

**And the setting needs an owner with a reason.** Not a constant in a config file, but a line saying
*this passage is `NO_INTERRUPTION` because it is the compliance disclosure and a partial one does
not count*. That sentence is what lets the next person change it safely, and its absence is why
settings drift back to the default during refactors.

**The review comment a senior engineer leaves:** *"You've set `NO_INTERRUPTION` on the whole session
and the PR description says it's for the terms read-out. That's one paragraph paying for every call
— put it on that flow and leave the rest interruptible. Second, our client still stops playback on
the `interrupted` event; if this setting means that event never comes, fine, but say so in the
docstring and decide which of the two is in charge, because right now we've got two mechanisms with
different opinions and no test on either. Third, we haven't run this against a model — it's read off
the package — so treat it as unverified until somebody does, and don't let the config comment imply
otherwise. And log the value we sent alongside the call, or the first 'it talked over me' ticket
will be unanswerable."*

**The interview question:** *"Should a voice agent let the caller interrupt it?"* An honest answer:
*"Usually yes, and the interesting thing is that it's a setting rather than a property. I'd built
the measurement first — a connection that honoured interruptions against one that ignored them, and
with them ignored the caller heard all six chunks of an answer they'd already talked over plus a
second complete answer on top, twelve chunks against three, with the session ending cleanly and no
error anywhere. I treated that second run as the wrong way to build a voice loop. Then I read the
protocol and found it has a name: `ActivityHandling.NO_INTERRUPTION`, sitting in the same enum as
`START_OF_ACTIVITY_INTERRUPTS`, as a supported configuration. So yesterday's ablation was today's
setting, which changed how I read ablations generally — a switch that makes something worse in one
situation is often the switch that makes it better in another. And there are real cases for it: a
required disclosure, a safety instruction, a read-back of an amount, where a half-delivered version
is worse than an unstoppable one — a half-confirmed record looks exactly like a confirmed one
afterwards. Everywhere else it's wrong, because a person on a phone expects to be able to interrupt.
The third enum value is just 'nothing was chosen', which is the trap: the session still behaves some
way and nobody argued for it. The thing I'd check in review is that the client and the setting
agree, because a client that stops playback on an interrupt event and a session configured not to
interrupt are two mechanisms answering one question."*
