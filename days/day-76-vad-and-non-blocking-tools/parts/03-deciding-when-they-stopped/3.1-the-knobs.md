# 3.1 — The knobs

## One-line answer

Day 75 found two candidates for deciding that a caller has stopped speaking — the far end working
it out from the sound, or the client saying so — and left the first one looking like a fixed
property of the service. It is not. **It is a `disabled` flag and five named settings**, every one
of which is a decision somebody has to make.

## The story

The coffee machine in the corner of the office makes coffee. That is the whole of what anyone
knows about it. You press the middle button, it grinds, it hisses, you get a cup.

Then one week it starts making the coffee weak, and you are the person standing nearest it when
somebody complains. So you look at it properly for the first time, and there is a small plastic
flap on the side you have never opened. Behind the flap is a screen and a little wheel, and behind
those are settings. Not one. Five, on a list you scroll through: how hard it grinds, how much
water it pulls, how hot it runs, how hard the water in the building is, how often it rinses
itself.

All five already have values.

You go round the office asking who set them. Nobody set them. The person who ordered the machine
has left. One colleague thinks somebody changed the grind before Christmas because the coffee was
bitter, and cannot remember which way. The values on that screen are the accumulated result of
everyone who has ever opened that flap, minus everyone who wrote it down, which is everyone.

Notice what actually changed in that story. The machine did not change. What changed is that you
stopped thinking of "makes coffee" as a thing the machine *is* and started seeing it as the
outcome of five numbers that are currently set to something. And the moment you can see them, weak
coffee stops being a mood the machine is in and becomes a question with an answer.

## The idea in plain language

Two terms first, because the rest of this part is made of them.

**Voice activity detection** — VAD — is the mechanism Day 75 part 3.2 named: the far end looks at
the incoming sound in short slices, decides for each slice whether it is speech or not speech, and
when enough not-speech slices go by in a row it declares the turn over and starts answering. That
part established the choice between letting the far end infer the boundary this way and having the
client state it with turn markers. It treated inference as one thing you either use or do not.

**A pydantic model field** is the second. `pydantic` is the library that both `google-adk` and
`google-genai` use to define their data classes: you declare attributes with types, and pydantic
builds, at import time, a dictionary called `model_fields` describing every one of them. That
dictionary is not documentation about the class. It *is* the class, as installed, on this machine.

Put those together and you get this part's one idea. Inference is not a black box the provider
owns. The installed package hands you a `disabled` flag and five settings that shape how that
classifier behaves, and reading them takes one command.

That reframes the Day 75 question rather than repeating it. Yesterday asked *which of the two
mechanisms decides the boundary.* Today's answer is that even after you have picked the first one,
you have picked a panel and not a behaviour — and the panel currently has values, chosen by
whoever wrote the defaults rather than by anyone who has met your callers.

Two things this part deliberately does not do. It does not argue what the sensitivity settings
should be — cutting people off and never letting them finish are the same dial from opposite ends,
and part [3.2](3.2-sensitivity-is-a-trade.md) owns that argument. And it does not take up whether
a caller speaking should interrupt an answer in progress, which is a different field in the same
config object and belongs to part [3.3](3.3-interruption-is-a-setting.md). This part is the
census: what exists, what each name denotes, and where it lives.

## Why Sutra needs it

Because the hub's trap 7 is *treating voice activity detection as fixed*, and a trap you cannot
see is not a trap you can avoid. A team that never opens the flap ships whatever the machine came
with, and then debates the coffee.

And because this is the same argument part
[2.1](../02-when-the-answer-comes-back/2.1-three-schedulings.md) made about `response_scheduling`,
now made about five fields at once instead of one. **A default is a value.** There is no
configuration in which these settings are absent; there is only configuration in which nobody has
looked at them.

The day's voice client will eventually have to answer, out loud and in writing, how it decides
that a caller has finished. "We use the built-in detection" is not an answer to that question. It
is a statement about which panel is in use, and the panel has five positions on it.

## The mechanism

`lab/vadconfig.py` prints every voice-activity field the installed packages offer. It contacts
nothing, runs no model, and sends no audio anywhere.

```bash
cd days/day-76-vad-and-non-blocking-tools/lab
uv run python vadconfig.py
```

**Line by line:**

- `cd .../lab` — the day's scripts import their siblings as plain modules, so they are run from
  the lab directory rather than from the repo root.
- `uv run python vadconfig.py` — `uv run` uses the project's pinned interpreter and dependencies,
  so the `google-adk` being read is the one in `pyproject.toml` and not whatever happens to be on
  the path. That matters more here than usual: the entire output is a claim about *the installed
  version*, and reading the wrong install would produce a page of confident wrong names.
- There is no `; echo "exit: $?"` on this one, unlike the day's measurements. The script has no
  verdict to encode. It always exits `0`, because printing a list of field names cannot succeed or
  fail in the way an ablation can.

### Where it lives

Read the output from the top down, because it is a path rather than a list. `RunConfig` is the
object a live session is started with, and it carries `realtime_input_config`. That holds a
`RealtimeInputConfig`, which has exactly three attributes. One of the three,
`automatic_activity_detection`, is the panel this part is about; the other two,
`activity_handling` and `turn_coverage`, are part 3.3's and are named here only so the map is
complete.

So the five knobs are three objects deep from the thing you construct. That depth is the practical
reason they get left alone: nothing in the ordinary flow of writing an agent walks you past them.

### The five fields, and what their names denote

**Read the next table carefully, because of what it is not.** These are field names and type
annotations, printed off the installed package. They are not documentation of behaviour. No page
was read that explains what any of these settings does to a classifier, and nothing here was
applied to a model. What the table asserts is what each name plainly denotes and nothing further —
no default values, no permitted ranges, no description of what a particular setting produces,
because none of that was read and Principle 8 forbids inventing it.

One term the table needs. A **millisecond** is a thousandth of a second, and **padding** is extra
audio kept on the outside of a boundary — sound from before the moment the start of speech was
detected, retained rather than thrown away.

| Field | Type as printed | What the name denotes |
| --- | --- | --- |
| `disabled` | `Optional[bool]` | Whether the automatic detection is turned off |
| `start_of_speech_sensitivity` | `Optional[StartSensitivity]` | How readily the *start* edge of speech is declared; the enum offers `HIGH`, `LOW` and an unspecified member |
| `end_of_speech_sensitivity` | `Optional[EndSensitivity]` | How readily the *end* edge of speech is declared; the same three members |
| `prefix_padding_ms` | `Optional[int]` | An amount of audio before the detected start, in milliseconds |
| `silence_duration_ms` | `Optional[int]` | An amount of silence, in milliseconds |

Two of those five are the same knob at opposite edges of a turn, which is worth noticing now: the
start and end sensitivities are separate fields, so a system can be eager about noticing that
someone began and patient about deciding they finished. Part 3.2 is about what you buy and pay for
at each end.

And `disabled` is the field that connects this page back to yesterday. Setting it turns the
automatic detection off, which — as the script's own last paragraph says — leaves the client's
turn markers as the only signal about where a turn ended. Day 75 part 3.2 presented those two as
alternatives you choose between. Here is the switch that implements the choice.

### How the knobs get printed

Here is the loop that produces that fourth block. On disk it is inside `main()`, so it is indented
by four spaces; the common leading whitespace has been removed here and it is otherwise unchanged.

```python
print("  types.AutomaticActivityDetection - the knobs themselves")
for name, field in types.AutomaticActivityDetection.model_fields.items():
    print(f"    {name:<28} {field.annotation}")
```

**Line by line:**

- `types.AutomaticActivityDetection.model_fields` is the pydantic dictionary described above, and
  using it rather than a hand-written list is the whole point of the script. It enumerates the
  fields the installed version **actually has**. A list typed into a document goes stale silently
  on the next upgrade; this loop cannot, because it has nothing to be stale about — it reads the
  class in front of it. That is Principle 8 in its cheapest possible form.
- `.items()` gives both halves, `name` and `field`, because the name alone would not be enough.
  The name tells you a knob exists; the field object is where the type lives.
- `field.annotation` prints the **declared type**, not a value, and that is deliberate. There is
  no instance here and no model — nothing has been configured, nothing has been sent. The script
  is describing a *shape*: what could be set and what kind of thing each setting would be.
  Printing values would require inventing an object first, and an object you constructed tells you
  what you put in it, not what the package offers.
- Read those annotations and notice that **every one of the five is `Optional`**. That is a fact
  about the API with a consequence: leaving any of them unset is a legitimate state, so a config
  object with nothing set at all is valid and will be accepted. What happens then is the model's
  business rather than the framework's — the framework has been told nothing, so it forwards
  nothing, and the behaviour comes from the far end's own defaults.
- `{name:<28}` left-aligns the name in a column of twenty-eight characters, purely so the
  annotations line up in the terminal. `28` is the width of the longest field name plus a gap,
  chosen by looking at the output rather than by a rule.

## When it breaks

**This is a census, not an evaluation, and that is the biggest thing on the page.** Nothing above
was applied to a model. No audio was classified, no turn boundary was detected, no setting was
changed and observed to change anything. Every line is a name, a type or an enum member read out
of an installed package. So this part is not entitled to an opinion about what any of these
settings *does* — only about what exists and where. Changing that would take a live model that
supports the Live API and a real microphone, and Day 74 part 4.2's free-quota check parked exactly
that: the paid surface stays unexercised, and the day's budget records zero requests to every
provider. A page that quietly slid from *these fields exist* to *this is how they behave* would be
inventing the second half, which is the failure Principle 8 exists to prevent.

**Every field is optional, so a system that sets none of them still has behaviour.** This is part
2.1's argument arriving a second time, and it lands harder here because there are five fields
instead of one. An unset `silence_duration_ms` does not mean silence duration is not consulted; it
means it is consulted at a value you did not choose. There is no configuration of this object that
opts out of having a policy. A default is a value.

**`explicit_vad_signal` sits on `RunConfig` right next to `realtime_input_config`, and this day
does not establish how the two interact.** Both were printed off `RunConfig.model_fields`, so both
certainly exist and both are `Optional`. Whether setting one overrides the other, whether
`explicit_vad_signal` is the same lever as `disabled` reached from a different object, or whether
they are independent and can contradict each other — none of that was read and none of it was
tested. It is named here as an open question on purpose, because it is precisely the kind of gap
that gets filled in by a plausible-sounding sentence written from the field names, and a plausible
sentence about which setting wins is worse than no sentence at all.

**And `TurnCoverage` mentions video.** `TURN_INCLUDES_AUDIO_ACTIVITY_AND_ALL_VIDEO` is a member of
an enum that this curriculum reached through an audio problem, which is a reminder that this
configuration surface is shared with a modality Sutra has never touched. Nothing on this day, or
any day before it, has sent a video frame anywhere. The honest reading of that member is that the
object is more general than the use being made of it — and the practical warning is that a setting
whose name mentions something you do not use may still be doing something to what you do use.

## In production

**What a professional records.** The package version, the date it was read, and the values they
set. Then the step almost everyone skips: **the values they deliberately left unset, and why.**
Five optional fields produce a config object where "not set" and "not considered" are
indistinguishable from the outside, and the difference between them is the entire difference
between a system somebody designed and a system somebody assembled. A comment saying *end
sensitivity left unset: we have no evidence about our callers yet, revisit once we have a corpus
of real transcripts* is worth more than the setting it declines to make, because it converts an
absence into a decision with a reason attached.

**These are the settings a support ticket will eventually be about.** Not the model, not the
prompt, not the tools. The complaints a voice system gets are *it cut me off* and *it just sat
there*, and both of those resolve to this object. Which means the current values need to be
discoverable from a **log** rather than from the code. Log the config that was actually applied
when a session opens — every field, including the ones that are `None` — and the first ticket is a
query. Leave it in the source and the first ticket is an archaeology exercise across branches,
environments and whatever the deployed build was, and the honest answer to *what were we running?*
is *probably this*.

*The review comment a senior engineer leaves: "Good — you found them. Now write down the five, the
ADK version and the date, in the module that builds the `RunConfig`, and put an explicit `None`
with a reason on the ones you're not setting, because otherwise nobody can tell the difference
between a default you accepted and a field you never saw. Second: this config has to appear in the
session-open log line, all of it. When we get the 'it cut me off' ticket — and we will — I want to
know what was applied on that session, not what's on main today. Third: you've written that these
settings shape detection, and that's a claim we haven't tested. Say in the docstring that these
are field names read off the package on a date, and that we've observed no behaviour. I'd rather
the next person knows they're the first one measuring."*

*The interview question: "How does your voice agent decide the caller has stopped talking, and
what control do you have over it?" An honest answer: "There are only two mechanisms — the far end
infers it from the sound, which is voice activity detection, or the client states it with turn
markers. What I'd push back on is the idea that the first one is fixed. In the ADK it reaches the
session through `RunConfig.realtime_input_config`, which holds a `RealtimeInputConfig`, which
holds an `AutomaticActivityDetection` with a `disabled` flag and five settings: start and end
sensitivity, each high or low, a prefix padding in milliseconds and a silence duration in
milliseconds. Alongside it there's `activity_handling`, which is whether the caller speaking
interrupts the answer at all, and `turn_coverage`. All five knobs are optional, which is the part
I'd flag in a review: unset doesn't mean unused, it means somebody else's default, so a team that
never opens that object has still chosen a policy. I'd want the applied config in the session-open
log, because 'it cut me off' is the commonest complaint and it's unanswerable otherwise. And I
should be straight about what I actually did: I read this off the installed package — version and
date — as a census of what exists. I haven't run a live model against any of these values, so I
can tell you what the fields are and what they're named, not what setting one of them does to a
real caller."*
