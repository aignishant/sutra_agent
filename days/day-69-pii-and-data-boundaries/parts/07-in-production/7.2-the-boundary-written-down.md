# 7.2 — The boundary written down

## One-line answer

A data boundary that exists only as a shared understanding is not a boundary — today's gate turns it
into **six checks that can go red**, four of which are red right now, including a redactor whose
free-text recall is **69% against a 90% floor** and a check that every fixture value comes from a
range reserved for fiction.

## The story

Two shops on the same street, both of which handle food.

The first has a laminated card by the till, printed by the owner, saying the kitchen is cleaned daily
and staff wash their hands. It is almost certainly true. The owner is conscientious and the card was
written in good faith.

The second has a green sticker in the window with a number on it. Somebody who does not work there
came in unannounced, looked at the fridge temperatures, read the cleaning log, opened the bins, and
wrote down a rating that the shop does not control and cannot print itself.

Both shops may be equally clean. Only one of them has made a claim that can be **wrong** — and that
is the only kind of claim worth anything to a customer standing outside deciding where to eat.

## The idea in plain language

This day has produced a lot of understanding: what counts as personal data here, where the copies are,
what the provider does with what you send it, why the fixtures are synthetic, how good the redactor
actually is, and what a delete has to reach. Every bit of that currently lives in `parts/` — which is
to say, in prose that a person has to read and remember.

Prose is where a boundary goes to die. Not because people are careless, but because the system keeps
changing and the prose does not, and nothing happens when the two diverge. The card by the till stays
on the wall whatever the fridge is doing.

So the boundary needs two things that prose cannot give it:

- **A document that is the reference** — `docs/DATA_BOUNDARY.md`, saying which stores hold personal
  data, how each is reached for erasure, what the retention is, and what crosses to a provider. That
  is the answer part [7.1](7.1-answering-what-do-you-hold.md) is assembled from and the map part
  [6.3](../06-the-delete-that-did-not/6.3-the-loop-over-a-list-somebody-kept.md)'s registry is checked
  against.
- **Checks that fail** — because a document nobody verifies is the laminated card. The gate is where
  each claim this day makes becomes a sentence somebody could argue with, and then a check that goes
  red when it stops being true.

The distinction those two make together is the one this part exists for: **a policy is what you intend,
a boundary is what fails.**

## Why Sutra needs it

Because four of this day's conclusions are load-bearing for the rest of the curriculum and every one
of them is currently a sentence in a document:

- No real personal data enters this repository, because Sutra's primary provider trains on free-tier
  content (section 3, SEC-13).
- Every fixture is synthetic (section 4).
- The redactor's free-text recall is a number somebody has to look at, not a feeling (section 5).
- A purge reaches every registered store (section 6).

Days 70 to 96 will keep building on this repository, and each of those days is a chance for one of the
four to quietly stop being true — a new fixture pasted from somewhere real, a new store added without
a registry row, a redactor changed for a different reason. The gate is what turns "quietly" into
"loudly".

## The mechanism

The gate is six findings, and the interesting design choice is in its docstring: a check that **cannot
run** reports as a **failure** rather than as skipped.

```python
"""The check that must be able to go red, and is red until the build brief is done.

    uv run python gate.py; echo "exit: $?"

Six findings, each one a sentence somebody could argue with. A check that cannot fail is a check
nobody has to pass (Principle 11), so this script reports "cannot check" as a **failure** rather
than skipping it: an absent module is exactly the state the day starts in, and pretending that is
neutral would make the gate green on an empty repository.
"""
```

**Line by line:**

- *"each one a sentence somebody could argue with"* is the test for whether a check belongs in a gate
  at all. A check nobody could disagree with is measuring something nobody cared about.
- The skip-is-a-failure rule is the important one, and it is easy to get backwards. A gate that reports
  "skipped — module not found" goes **green** on a repository where somebody has deleted the module,
  which is the exact failure a gate exists to catch. Principle 11: a check that cannot go red is a
  decoration.

Two of the six checks are worth reading in full, because they are the ones that measure this day rather
than the build brief.

The recall floor:

```python
    # 4 - free-text recall, the number section 5 says must exist and be looked at
    table = score(V2)
    hits, total = table["free"]
    pct = 100 * hits / total
    if pct < 90:
        out.append(f"redactor free-text recall is {pct:.0f}% ({hits}/{total}), below the 90% floor")
```

**Line by line:**

- It scores `V2` — the improved redactor from section 5 — rather than a fixed number written down when
  the day was authored. The check re-derives the measurement every run, so a change to the redactor
  moves the check rather than dating it.
- `table["free"]` is the **free-text** column specifically, not the overall figure. Section 5's whole
  argument is that the overall number is flattered by the structured fields, which score 100%
  trivially; putting the free-text number in the gate is that argument made mechanical.
- `90` is a **floor somebody chose**, and it is currently above what the code achieves. That is
  deliberate and it is the most useful shape a gate check can have: the number is a target with a name
  against it rather than a description of the status quo.
- The message carries `9/13` as well as `69%`, for the reason section 5.1 gave — a rate hides the size
  of the sample it came from.

And the check that the fixtures are fiction:

```python
    # 6 - every fixture value is from a range reserved for fiction
    for ref in TICKETS:
        text = whole(ref)
        for addr in EMAIL_ANY.findall(text):
            if not SAFE_DOMAIN.search(addr):
                out.append(f"{ref} carries {addr!r}, which is not an RFC 2606 domain")
        for num in PHONE_ANY.findall(text):
            if not SAFE_PHONE.search(num):
                out.append(f"{ref} carries {num!r}, which is not a reserved drama number")
```

**Line by line:**

- `EMAIL_ANY` matches **any** address shape and `SAFE_DOMAIN` matches only the reserved ones, so the
  test is *found an address that is not reserved* rather than *did not find a reserved address*. That
  direction matters: the second version passes on a fixture with no addresses at all.
- RFC 2606 reserves `example.com`, `example.net` and `example.org` for documentation precisely so that
  a fixture cannot reach a real inbox. Using them is not a convention this repository invented; it is a
  standard whose whole purpose is this.
- `SAFE_PHONE` is the same idea for numbers: the `07700 900xxx` range is reserved for drama, so a
  number in a fixture cannot ring a real phone.
- This check is currently **green**, and it is the one that will catch the most likely future mistake:
  somebody adding a realistic-looking fixture, in good faith, because it makes a test more convincing.

Run it:

```bash
cd days/day-69-pii-and-data-boundaries/lab
uv run python gate.py; echo "exit: $?"
```

**Line by line:**

- `cd` first: the lab's scripts import their siblings by plain name.
- `echo "exit: $?"` prints the exit code, because the gate is a test rather than a report — it is meant
  to be run by something, not only read.

Measured on 2026-09-06:

```text
  - sutra/data_boundary.py does not exist (cannot check its behaviour)
  - docs/DATA_BOUNDARY.md does not exist - the boundary is not written down
  - tests/test_data_boundary.py does not exist
  - redactor free-text recall is 69% (9/13), below the 90% floor

findings: 4
exit: 1
```

Four findings. Three of them are the build brief — the module, the document and the test are yours to
write. The fourth is a measurement, and it is the one to sit with: **the redactor this day improved is
still 21 points below the floor this day set for it.**

That is an uncomfortable thing to leave in a gate and it is the correct thing to leave in a gate. The
alternatives are worse. Lowering the floor to 69% makes the check describe what the code does, which
measures nothing. Removing the check makes the number disappear, which is section 5.1's failure exactly.
Leaving it red states, in a form that runs, that the redactor is not yet good enough and that somebody
decided how good it has to be.

Note also the two checks that are **not** in the output, because they passed: the purge really does
empty every registered store, and every fixture value is from a range reserved for fiction. Those two
are the day's actual achievements, and they are visible only as an absence — which is the ordinary
condition of a working control.

## When it breaks

**A floor that is never met stops being a target and becomes wallpaper.** A red check that has been red
for six months is a check people learn to scroll past, and at that point it is worse than no check,
because it also trains the reader to scroll past the other three. The discipline that prevents it is
the one Day 66 part 7.3 argued for: a finding gets a verdict. Either the floor is met, or it is
lowered with a written reason, or it is **accepted** with the condition it is accepted under —
*accepted at 69% while every reply is reviewed by a human before sending* is a defensible sentence, and
*69%, we'll fix it* is not.

**The gate checks the repository, not the deployment.** Everything above runs against files in this
repo. It says nothing about the machine the desk runs on, the backup taken last night, or the copy of
`state/` somebody put in a bug report. Part [2.2](../02-where-the-copies-are/2.2-a-boundary-is-a-line-you-can-name.md)
named a boundary as a line you can name, and the honest scope of this gate is *inside the line*.

**And the document can rot in a way the gate cannot see.** `docs/DATA_BOUNDARY.md` is checked for
**existence**, not for accuracy — a file with the right name and stale contents passes. The version of
this check with teeth compares the document against the registry: every store in `STORES` has a row,
every row has a store. That is the same diff Day 68 used for tools with no permission row and part
[2.1](../02-where-the-copies-are/2.1-one-sentence-seven-places.md) used for copies, and it is the
`TODO(me)` worth doing first.

## In production

**Who the document is actually for.** Not the engineers who wrote the system — they have the code. It
is for the person answering an access request under a deadline, the person writing the privacy notice,
the person doing a vendor assessment, and the engineer joining in eighteen months. Every one of those
people needs the same four facts per store — what, why, how long, who else — and none of them is going
to read `_stores.py`. A data boundary document that engineers find redundant is a document written for
the right audience.

**What degrades at scale, and the shape that survives it.** One repository with a gate is easy. An
organisation has dozens, and the document drifts from the system fastest in exactly the repositories
that change most. The pattern that survives is **generation plus a diff**: derive the store table from
the registry, commit it, and fail the build when a fresh derivation differs from what is committed —
which is Day 66 part 7.2's argument about generated threat models, applied to a data map. What must
stay hand-written is the *why* and the *how long*, because those are decisions rather than facts, and
that is the same split Day 66 arrived at.

**The failure mode that only appears with real traffic.** The floor gets met by changing the
measurement rather than the redactor. It happens without anybody deciding to cheat: the answer key is
refreshed, the new fixtures are a bit easier, recall goes to 92%, the check goes green, and the
redactor never changed. Section 4.3 measured that exact effect — 100% on generated data against 80% on
hand-written — so the countermeasure is to bind the check to a **held-out** fixture set that the
redactor's author does not edit, and to treat a jump in recall with no code change as a finding rather
than as good news.

**The review comment a senior engineer leaves:** *"Keep the 90% floor red rather than lowering it, but
give it a verdict — either an owner and a date, or write it down as accepted with the condition, which
is that a human reviews every reply before it's sent. If that condition ever stops being true this
check has to become blocking. Separately, the `DATA_BOUNDARY.md` check only tests that the file exists;
make it diff the store table against the registry, otherwise we'll have a document with the right name
and last year's architecture in it."*

**The interview question:** *"How do you stop a privacy policy from being fiction?"* An honest answer:
*"By making each claim in it a check that can fail. On the desk I worked on, the boundary was six
checks: the module exists, the boundary document exists, the test exists, the redactor's free-text
recall is above a floor we chose, a purge really empties every registered store, and every fixture
value comes from a range reserved for fiction — RFC 2606 domains and the drama phone range, so no
fixture can reach a real person. Four were red and I left them red, including a recall floor of 90%
against a measured 69%, because lowering the floor to what the code does measures nothing. The two
green ones were the day's real achievements and they're only visible as an absence. The subtlety is
that a floor can be met by changing the measurement rather than the code, so the check has to run
against a held-out set the author doesn't edit — otherwise recall improves and nothing has."*
