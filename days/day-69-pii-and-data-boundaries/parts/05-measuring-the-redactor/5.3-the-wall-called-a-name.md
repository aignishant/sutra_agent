# 5.3 — The wall called a name

## One-line answer

A name is not a pattern and a hash of a name is still a name: a redactor cannot match a name because
names have no shape, and hashing one does not stop it naming somebody — **6 of 8** addresses in this
archive come back from their hashes, and the salted column comes back exactly the same **6 of 8**.

## The story

You order a coffee and they ask for your name to write on the cup.

Notice what the counter can and cannot check. The card machine two feet away will refuse a card
number with one digit wrong, because a card number has a shape and the machine knows the shape. The
name goes on in marker pen exactly as it sounded. It has been spelled three different ways on three
different Tuesdays. You could give a name that is not yours and nothing in the building would know,
because there is nothing to check it against — a name is not right or wrong in the way a number is,
it is just what somebody answers to.

Then the shop changes the system. Shouting names across a room is not ideal, so cups get a number
now, printed on the receipt.

It works for about a week, and it fails for a reason nobody planned for. The person on the counter
knows you. You come in on Tuesdays, you order the same thing, and when a cup with a `4` on it is
sitting at the end of the counter they can tell you exactly whose it is without looking at anything
at all. The number is quieter than the name and it points at you just as precisely.

There is one cup on the counter they genuinely cannot place, and it belongs to the man who came in
for the first time that morning, whom nobody has ever seen before.

## The idea in plain language

Everything this day has done to identifiers works on **shape**, and a name has none.

That sentence has two halves and they look like separate problems. They are the same problem seen
from two sides, and the sentence that unifies them is this: **a value identifies somebody because of
the population it sits in, not because of the characters it is made of.** Matching works on
characters. Masking changes characters. Neither of them touches the population, which is where the
identification actually lives.

**Side one: you cannot match a name.** Look at why the patterns in
[5.2](5.2-fifty-per-cent-and-it-looked-fine.md) work at all. An email address has an `@` in it, and
almost nothing else does — that is a **delimiter**, a character that announces "a value of this kind
starts here". A UK postcode has a fixed alternation of letters and digits. `88-4471` is two digits,
a hyphen and four digits, and the desk chose that shape itself. A card number carries a checksum, so
a machine can tell a real one from a typo without asking anybody.

A name has none of these. It has no delimiter, no fixed length, no alphabet, no checksum and no
authority that decides which strings are names. Any string can be a name, in any script, of one word
or five, with or without punctuation. Worse, names **collide with ordinary words**: this archive
contains a customer whose surname would also pass as a place, and a plan called `Pro`, and sentences
beginning `Password reset` and `Reset link`. A pattern loose enough to catch `Lin Zhou` — say, two
capitalised words in a row — catches `Password reset`, `Reset link`, `Both charges` and `Order 88`
on the very same fourteen tickets. The pattern that catches the names catches the prose, and the
pattern that spares the prose spares the names. There is no setting in between, because there is
nothing in the characters to aim at.

🅿️ What people do instead is worth knowing and this day does not build it: a **gazetteer**, which is
a long list of known names to look for, or a trained model that predicts which spans of text are
names from their context. Both work, imperfectly, and both are recall problems again — a gazetteer
misses every name not on it, which for a customer list is most of them, and a model has a recall
figure that needs an answer key exactly like [5.1](5.1-the-answer-key-comes-first.md)'s. Neither
turns a name into something with a shape.

**Side two: you cannot mask a name either.** The move everybody reaches for once matching fails is
to stop trying to find names and start disguising them: replace each value with a **hash**, a
fixed-length string computed from it by a function that cannot be run backwards. The column stays
**joinable** — the same person always produces the same hash, so rows can still be grouped by
customer — and the plaintext is gone. It feels like the best of both.

"Cannot be run backwards" is true and it is not the property that matters. Nobody has to run the
function backwards. They run it **forwards**, over every value the answer could plausibly be, and
compare. If the set of possible inputs is small and guessable, the hash is a lookup table waiting to
be built. Email addresses at a known company are about as guessable as inputs get: a first name or
an initial, a separator, a surname, one of three domains.

The half-remedy people reach for next is a **salt** — a fixed extra string mixed in before hashing,
so that the stored value is the hash of `salt + address` rather than the hash of the address. And a
salt does something real, which is why the advice exists. It just does not do this.

### The second measurement

Since the names cannot be found, the proposal on the table becomes: stop finding them, and store
every identifier as a hash instead. `lab/hashcheck.py` does that to the addresses — the identifiers
this archive has most of — and then tries to get them back.

```python
def digest(value: str, salted: bool) -> str:
    """The stored value: a hash of the address, optionally with a fixed salt in front of it."""
    raw = (SALT + value) if salted else value
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()
```

**Line by line:**

- `hashlib.sha256` is a cryptographic hash function from the standard library: same input, same
  sixty-four-character output, every time, on every machine. It is the standard choice and nothing
  in this part is a criticism of it — SHA-256 is not broken here, and a stronger function would
  change nothing that follows.
- The determinism is the feature being bought. A store that hashes addresses can still ask *"which
  rows belong to the same customer?"*, because the same address always produces the same digest.
  That is **joinability**, and it is the entire reason anybody hashes instead of deleting.
- `raw = (SALT + value) if salted else value` is the salt: a fixed string, `"sutra-day-69"`, glued
  on the front before hashing. **Fixed** is the word to hold on to. Every row uses the same salt,
  because a different salt per row would produce different digests for the same customer and destroy
  the joinability that was the point.
- `.encode("utf-8")` because hashing works on bytes rather than characters, and `.hexdigest()` turns
  the bytes back into a printable string — the form a column in a database would actually hold.

Now the attack, which is not much of an attack:

```python
def candidates(wide: bool = False) -> list[str]:
    """Every address the known shape can produce - the search space, generated not guessed."""
    firsts = FIRSTS + FIRSTS_WIDE if wide else FIRSTS
    out = []
    for first, sep, surname, domain in product(firsts, SEPARATORS, SURNAMES, DOMAINS):
        out.append(f"{first}{sep}{surname}@{domain}")
    return out
```

**Line by line:**

- `product` is `itertools.product`, the Cartesian product: every combination of one item from each
  list. That is the whole method. There is no cryptography here and no cleverness — the search space
  is **generated**, not guessed at.
- `FIRSTS` is the twenty-six single letters, because `p.oyelaran@` and `t.abiodun@` are the shape
  this company uses. `SEPARATORS` is `"."` and `""`. `DOMAINS` is the three example domains.
  `SURNAMES` is twelve surnames.
- 26 × 2 × 12 × 3 = **1872 candidates**. That is the size of the haystack, and it is small enough to
  hash on a laptop without noticing.
- Every one of those four lists is **public shape**, not stolen knowledge. How a company forms its
  addresses is on any email it has ever sent. Who its customers are is on its own case-study page,
  in its press releases, and on the professional profiles of everybody who works there. The attacker
  needs no access to the database whose column they are reading.
- `wide` adds eight full first names to the list, and the flag exists because of what it
  demonstrates below.

```python
    salted = "--salted" in sys.argv
    targets = sorted({i.value for i in TRUTH if i.kind == "email"})
    stored = {digest(t, salted): t for t in targets}

    space = candidates(wide="--wide" in sys.argv)
    table = {digest(c, salted): c for c in space}

    recovered = {h: table[h] for h in stored if h in table}
```

**Line by line:**

- `targets` is every distinct address in the answer key — the plaintext that a real system would not
  have, kept here only so the script can print which recoveries were correct.
- `stored` is **the database column**: hashes as keys, and that is all a real attacker would see.
  The values are there for the report.
- `table` is the same function applied to all 1872 candidates. This is the rainbow-table idea in one
  line, built on the spot rather than downloaded.
- `recovered` is a dictionary intersection: for every stored hash, is that exact hash also in the
  candidate table? Two matching digests mean the same input, so a hit **is** the plaintext. There is
  no inversion, no brute-force decryption and no weakness in SHA-256 involved. The function was run
  forwards 1872 times.
- Note what `salted` changes in that block: exactly one thing. Both `stored` and `table` are built
  with the same `digest` call, so the salt is applied on both sides. That is not the script being
  kind to the attacker — it is what happens in reality, because the salt is a constant in the
  codebase or a config value, and anybody who has the column has usually had the code for years.

**Line by line:**

- The output prints the first sixteen characters of each stored hash beside its verdict, so the two

Be precise about why, because "add a salt" is genuinely good advice in the place it belongs. A salt
defeats a **precomputed** table: a file somebody built in advance, containing the hashes of every
common password or every address they could think of, usable against any database that hashed the
same way. With a salt in place, that file is worthless, and the attacker has to build their own.
Building their own is the loop above. It costs 1872 hash computations, which is nothing. The salt
raised the price of the attack from *download a file* to *run a script*, and the whole security of
the scheme was resting on the assumption that the attacker cannot enumerate the inputs — which, for
addresses derived from names at a company whose staff are on the internet, was never true.

And the two survivors are the measurement that makes this exact rather than rhetorical. They are not
protected by the hash. They are protected by not being in the guess list — both spell the first name
out in full, and the narrow list only tries single initials. Widen the list and they fall:

```bash

```

**Line by line:**

- `--wide` adds eight whole first names to `FIRSTS`, taking the candidate count from 1872 to 34 × 2
  × 12 × 3 = 2448.
- Nothing else changes: same hash function, same stored column, same comparison. The only variable
  in this whole part is how good the guess list is.

### And so the reply says the name

a column.

## When it breaks

The failure here is not the hash. It is the sentence somebody writes underneath the hash.

🎬 **The scene:** a data-science team asks for support tickets to analyse. Handing over addresses is
obviously not on, so an engineer does the careful thing: hash the address column, keep it joinable
so sessions can still be grouped by customer, and pass the file along with a note saying the data
has been anonymised.

😬 **The naive fix:** somebody in review asks whether the hash is strong enough, and the engineer
adds a salt. The question felt like the right question and the answer felt like the right answer.

💥 **Why it fails:** the run above. Six of eight addresses come back from 1872 forward hashes, salted
or not, from public knowledge about how the company forms addresses and who its customers are. And
in the file that was handed over, every row still carries a **name in the free-text body**, which
nobody hashed because it is not in a column. The word "anonymised" in that note is now attached to a
file that names people twice over.

💡 **The insight:** hashing changes who has to do a little work; it does not change who the row is
about. A one-to-one function of an identifier is an identifier, and one-to-one is exactly the
property that was wanted.

**What pseudonymisation is genuinely good for**, because the opposite over-correction is also wrong
and gets people to stop doing something useful:

- **A stolen dump is worth less.** An attacker with the file and no interest in your company gets a
  column of hex. Recovery costs them the effort above, per column, and most opportunistic theft
  never pays it. That is a real reduction in exposure and it is not nothing.
- **Casual reading stops.** An analyst running a query, an engineer scrolling a table, a screenshot
  in a bug report: none of them now shows an address. Most everyday exposure inside a company is
  accidental rather than adversarial, and this addresses the accidental kind well.
- **Joinability survives.** Rows can still be grouped by customer without the plaintext travelling,
  which is usually the actual requirement.
- **It narrows the blast radius of a mistake.** A hashed value pasted into a log line or a
  third-party tool is a smaller incident than a plaintext one — smaller, not absent.

What it is **not** is anonymisation, and the distinction is not a matter of degree. The test that
separates them is one question, and it is worth memorising in this form:

> **Can this value be linked back to one person by anybody, with any auxiliary data they could
> reasonably get?**

If yes, the data is **pseudonymised**: still personal data, still inside the boundary
([2.2](../02-where-the-copies-are/2.2-a-boundary-is-a-line-you-can-name.md)), still subject to
erasure, still needing an access list. If genuinely no — for anybody, including you, including your
own customer table — then it is anonymous and outside all of that. Note that the question is about
the *population and the auxiliary data*, not about the algorithm, which is the same sentence this
part opened with. It is also the same test
[1.4](../01-who-a-record-names/1.4-the-number-that-only-means-something-here.md) applied to the
account number, arriving at a value that looks much more disguised and answering the same way.

## In production

**The bar that actually applies is k-anonymity, and it is a bar about rows rather than values.**
[1.2](../01-who-a-record-names/1.2-three-columns-that-name-one-person.md) defined it: a table is
*k*-anonymous if every combination of quasi-identifiers is shared by at least *k* rows, and `k = 1`
means somebody is alone in their group, which is the same sentence as "this row is identified".
Hashing a column does not move `k` at all — it renames a value, and `k` counts rows. The measurement
in [1.2](../01-who-a-record-names/1.2-three-columns-that-name-one-person.md) is what makes this
concrete and it is worth re-reading before anybody signs off an export: a twelve-row customer table
with no name, email, phone or address in it still had `city + plan + signup` naming **ten of
twelve** accounts, and `city + signup + seats` naming **twelve of twelve**. Replace the account
number with a hash of the account number and every one of those numbers is unchanged.

That is why reaching real anonymity is hard and why most teams should not claim it. It requires
suppressing or generalising the quasi-identifiers until the smallest group is big enough — dropping
`seats`, widening `city` to a region, `signup` to a year — and each of those steps removes the
analytical value that motivated the export. The honest position is usually: this is pseudonymised
data, it stays inside the boundary, and here is its access list and its retention period.

**"Anonymised" is a word that needs an argument attached to it, every single time.** Not a process
name, not a function name, not a reassurance — an argument, in a sentence somebody can disagree
with: *"anonymous against an attacker who has our public case studies and the professional profiles
of our customers' staff, because the smallest quasi-identifier group in this export has forty rows
in it."* Written that way, the claim can be attacked, which means it can be defended. Written as
"the addresses are hashed", it cannot be either. And treat the word as a **claim about a specific
file against a specific attacker**, because that is what it is: the same file is anonymous against a
stranger and transparent to you, and you are the one who holds the customer table.

**What changes at ten thousand.** Everything moves against the hash. The candidate space grows
linearly with your customer count while the cost of hashing a candidate stays flat, so a bigger
company is a *more* enumerable one, not a less. Every ordinary business activity publishes more of
the guess list — job adverts naming teams, conference talks, customer logos on a website, support
agents' own addresses in email footers. And the number of places the hashed column appears grows, so
the chance that one of them sits next to a table containing the plaintext grows with it. A
pseudonymised column is only as pseudonymous as the least careful join anybody performs on it, and
nobody reviews the joins.

**The failure mode that only appears with real traffic.** Names in free text arrive at a rate that
is a property of politeness rather than of unusual input. Customers sign their messages. Agents
write *spoke to the same person each time*. The model addresses people by name because it was tuned
to be helpful. So the identifier that no pattern can find is also the identifier that appears most
reliably, in the half of the record that nobody redacts, on every single request. You will not see
it in a test suite and you will see it immediately in a sample of ten stored replies.

**The review comment a senior engineer leaves:** *"This export is described as anonymised because
the address column is hashed. I ran the obvious attack against our own column and got six of eight
back from under two thousand candidates, and the salted version gave exactly the same six — the salt
stops a downloaded rainbow table, not somebody who can guess our address format. Separately, the
bodies in this export still contain customers' names in the sign-offs, and we have no detector for
those and are not going to have one. Call it pseudonymised, keep it inside the boundary, and give me
the access list and the retention period."*

**The interview question:** *"Is hashing an email address enough to anonymise it?"* The answer that
shows you have done this: *"No, and it is easy to demonstrate rather than argue about. On our own
column I hashed every address, generated the candidate space from the format the company uses and a
dozen surnames anybody could find publicly — about eighteen hundred candidates — and recovered six
of eight. Adding a fixed salt recovered exactly the same six, because a salt kills a precomputed
table and does nothing against somebody who can enumerate the inputs. The two that survived were the
two whose plaintext was not in my guess list, and widening the list by eight first names got all
eight, so what I was really measuring was the guess list rather than the hash. The bigger problem
was the other direction: names in free text, which no regular expression finds — a name has no
delimiter, no length, no checksum and it collides with ordinary words — so our reply opened with the
customer's name and it was stored in seven places. What I say now is that hashing gives you
pseudonymisation, which is real and worth doing, and that the test for anonymity is whether anybody
could link the value back to one person with data they could get. If the answer is yes, it stays
inside the boundary."*
