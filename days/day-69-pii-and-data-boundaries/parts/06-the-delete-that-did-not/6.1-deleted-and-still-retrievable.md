# 6.1 — Deleted, and still retrievable

## One-line answer

Deleting the ticket from the archive succeeds, raises nothing, and leaves the customer's address in
**6 of 7 stores** — and the search index will hand the whole message back, signature and all, to the
next question that matches it.

## The story

A man moves house and rings his bank to change the address. The person on the phone updates it while
he waits, reads the new one back, and confirms it is done. It is done: the account screen shows the
new address that afternoon.

Over the next four months, post keeps arriving at the old house. A card for the anniversary of the
account. A regulatory notice. A replacement debit card, which the new occupants leave on the hall
table for a fortnight before anybody thinks to do anything about it.

Nobody at the bank did anything wrong on the phone. The address was changed in the system the person
on the phone could see. The mailing list for annual statements is generated by a different team from
an extract taken monthly. The card fulfilment supplier holds its own copy. The archived
correspondence system was never in the conversation at all.

Everyone involved would say, truthfully, that the address was changed.

## The idea in plain language

Part [2.3](../02-where-the-copies-are/2.3-the-copy-nobody-calls-a-copy.md) counted where one
customer's sentence ends up after a single ordinary run, and promised that this part would run the
delete and print what comes back. Here it is.

The delete this part performs is the one everybody writes first, and it is not lazy or careless. It
is the delete that follows from the mental model most people have: **the archive is where the tickets
live, so removing the ticket from the archive is removing the ticket.**

That model was true on the day the archive was built. It stopped being true on the day something else
was added that keeps a copy — and every one of those additions was a feature, built for a good
reason, by somebody who was not thinking about deletion:

- Day 47 gave the desk **persistent sessions**, so a conversation survives a restart.
- Day 48 gave it a **memory store**, so it remembers what mattered about a ticket.
- Days 49 and 50 gave it a **retrieval index**, so an old ticket can be found from a new question.
- Day 51 gave it a **response cache**, so an answer is not paid for twice.
- Days 60 and 61 gave it an **event log** and **checkpoints**, so a run survives being killed.

Seven stores, one of which anybody would call "the tickets". The other six were each a good idea, and
between them they are where the data now is.

The word that makes this precise is **derived data**: a copy that some other component made for its
own purposes, from the original, without being asked. Derived data is invisible to a delete written
against the original, because the component that made the copy is not in the conversation.

## Why Sutra needs it

Because the day's earlier sections have been building towards a claim that has to be tested rather
than asserted. Section 1 said what counts as personal data here. Section 2 counted the copies. Section
5 measured the redactor. All of that is about text **arriving**. This section is about text
**leaving**, and it is the half where a system either has an answer or does not.

There is also a hard obligation behind it, and it is worth naming plainly rather than gesturing at.
When a person asks for their data to be erased, the answer *"we deleted the record"* is only true if
it names every store. Day 48 introduced that obligation and this part is where the desk is measured
against it: the delete succeeded, the record is gone from the archive, and the honest answer to
*"have you erased my data?"* is **no**, by six stores and eleven copies.

## The mechanism

The delete under test is four lines, and there is nothing wrong with any of them:

```python
def delete_from_archive(ref: str) -> None:
    """What "delete the customer's ticket" means when nobody has listed the derived stores."""
    archive = load("archive")
    archive.pop(ref, None)
    save("archive", archive)
```

**Line by line:**

- `load("archive")` reads the one store whose name contains the word for the thing being deleted. That
  is the whole mental model, in one function call.
- `archive.pop(ref, None)` removes the row. The `None` default means a missing ref is not an error,
  which is the correct behaviour for an idempotent delete and is also why this function can never tell
  you it did nothing.
- `save("archive", archive)` writes it back. The operation completes, returns `None`, and raises
  nothing.
- There is no `return` value and no report. A function that deletes and says nothing is a function
  whose caller has no way to check the claim — which is the shape of every deletion this part is about.

Run it and count the stores afterwards:

```bash
cd days/day-69-pii-and-data-boundaries/lab
uv run python deleted.py
```

**Line by line:**

- `cd` first: the lab's scripts import their siblings by plain name.
- `deleted.py` calls `run()` to produce one ordinary handled ticket across all seven stores, counts
  occurrences of the customer's address in each, performs the archive delete, and counts again. The
  before and after come from the same counter, so the comparison is not two different measurements.

Measured on 2026-09-06:

```text
deleted ticket:7006 from the archive. No error was raised.

  store         before  after
  archive            2      0
  session            2      2
  memory             2      2
  index              2      2
  cache              2      2
  log                1      1
  checkpoint         2      2

  stores still holding 'lin.zhou@example.com'   6 of 7
  copies remaining                          11
  still there: session, memory, index, cache, log, checkpoint
```

The `archive` row went from 2 to 0. Every other row is unchanged. **Eleven copies remain**, in six
stores, and the operation reported success because it succeeded — at the thing it was written to do.

Now the part that turns this from an accounting problem into an incident. Ask the search index a
question:

```bash
uv run python deleted.py --retrieve
```

**Line by line:**

- `--retrieve` runs the identical delete and then calls `search_index`, which is Day 49's retrieval
  reduced to its essentials — rank rows by shared terms, return the top three.
- The query is *"downgrade did not take effect"*, which is a plausible question from a different
  customer with a similar problem. Nothing about it mentions the deleted ticket or the person it
  concerns.

Measured on 2026-09-06 — the last three lines of the same run:

```text
  asking the index for "downgrade did not take effect":
    ticket:7006#0
      'From: lin.zhou@example.com\n\nDowngrade did not take effect. Plan still shows Pro after a week.\n\n-- \nLin Zhou\n+44 7700 900318\nlin.zhou@example.com'
```

That is the deleted ticket. Not a fragment, not a hash, not a summary — the whole message, with the
address at the top, the name in the signature, the phone number, and the address again at the bottom.
It came back to a question asked by somebody else, from a store nobody thought of as holding tickets,
after the ticket was deleted.

Three things about that result deserve to be separated, because they fail for different reasons:

| What survived | Why the delete missed it | Can it be found by key? |
| --- | --- | --- |
| `session`, `memory`, `checkpoint` | keyed by something other than the ticket ref | yes, once you know to look |
| `index` | holds a **chunk** with a derived ref (`ticket:7006#0`) | yes, if the key scheme is known |
| `cache` | keyed by a hash of the prompt | no — part 6.2 |
| `log` | the record that the event happened | must not be deleted — part 6.2 |

Part [6.2](6.2-the-store-you-cannot-address.md) is the last two rows, and part
[6.3](6.3-the-loop-over-a-list-somebody-kept.md) is the delete that reaches all seven.

## When it breaks

The natural response is *"then delete from the index too"*, and it is right and it is not the lesson.
Adding the index makes this delete reach two stores instead of one, and leaves five. Adding the five
makes it reach seven — until Day 70 adds a router with its own cache, or somebody adds a queue, or a
metrics pipeline starts sampling ticket bodies for a dashboard.

The failure is not that a store was missed. It is that **the list of stores lives in somebody's head**,
and a list in somebody's head has no mechanism that notices when it is out of date. Part
[2.1](../02-where-the-copies-are/2.1-one-sentence-seven-places.md) already argued this from the other
direction — a map maintained by intention will drift, so the count has to be runnable — and part
[6.3](6.3-the-loop-over-a-list-somebody-kept.md) is what a runnable list looks like.

There is a second failure here, quieter and worse. The delete **reported success**. If an access
request were answered from the archive alone, the answer would be *"the record is gone"*, given
honestly, checked by somebody competent, and false. A deletion routine that cannot report which stores
it reached is a routine whose output cannot be used as evidence — and evidence is precisely what it
will be asked for.

## In production

**What degrades at scale.** The number of derived stores grows monotonically and nothing in the
development process makes any of them announce itself. A cache is added for latency, a search index
for a feature, a data-warehouse extract for analytics, a vector store for a new retrieval strategy —
each shipped by a different team, each justified on its own terms, and none of them arriving with the
sentence *"and this now holds customer text, so the erasure routine needs a row."* After two years the
honest answer to *where does this customer's data live* requires an audit rather than a lookup.

**The failure mode that only appears with real traffic.** Backups. Every store above has a backup, and
a backup is a copy that deliberately resists deletion — that is its entire purpose. The professional
answer is not to delete from backups, which would defeat them; it is to state the retention period, to
ensure a restore re-applies outstanding erasures, and to write that down as the answer rather than
discovering it during an audit. The same applies to the replica, the staging environment refreshed
from production last month, and the developer's laptop with a debugging dump on it.

**What a professional does before the first delete is ever written.** They make the store list a
**registry** that code iterates, and they require a new store to register at the point it is created
rather than at the point somebody remembers it. That inverts the failure: an unregistered store is a
missing row somebody can check for, instead of a store nobody has thought about since it shipped. That
is section 6.3's subject, and the reason it is framed as *a loop over a list somebody kept* rather than
as a cleverer delete.

**The review comment a senior engineer leaves:** *"This deletes from the archive and returns `None`, so
there is no way for the caller to say what it reached — and right now it reaches one store out of
seven. Two changes: return a per-store report so a deletion can be evidenced, and get the store list
out of this function and into a registry. Also, please add the test that searches the index after the
delete. I'd rather that goes red in CI than in an access request."*

**The interview question:** *"A customer asks you to delete their data. What actually has to happen?"*
An honest answer: *"First, find out where the copies are, because it is never one place. On the desk I
measured this on, deleting the ticket from the archive succeeded, raised nothing, and left the
customer's address in six of seven stores — session, memory, the search index, a response cache, the
event log and a checkpoint. The index handed the entire message back, signature and phone number
included, to an unrelated later query. The fix isn't a cleverer delete; it's a registry of stores that
code iterates, so an unregistered store is a missing row rather than something nobody thought of, plus
an honest position on the two stores that can't be handled the same way — a cache you can't address by
customer, and a log that has to survive because it is the record that the event happened. And the
delete has to return what it reached, because it will be asked for as evidence."*
