# 6.3 — The loop over a list somebody kept

## One-line answer

The delete that reaches everywhere is not a cleverer delete — it is a **loop over a registry**, and
the measured result is `copies remaining 0` across all seven stores, with the whole difference from
part 6.1 being that the list of stores is data the code iterates rather than a list a person
remembers.

## The story

A teacher takes thirty-one children to a museum. At the end of the visit she stands by the coach and
counts heads: thirty-one. Everybody back on.

The next term a different teacher does the same trip and does something duller. She has a printed
register, and she reads out thirty-one names, and each child answers. It takes four minutes longer
and she feels slightly foolish doing it in front of the museum staff.

Halfway through the list she reads out a name and nobody answers, because that child went home at
lunchtime with her father, which the office knew and the teacher did not.

The head count would have come to thirty-one that day as well, because a boy from another school had
drifted over to the coach while his own group was loading. Two errors, cancelling, invisible to
counting and impossible to miss on a register — and the register found it not because it is clever but
because it names things one at a time.

## The idea in plain language

Part [6.1](6.1-deleted-and-still-retrievable.md) ran the delete everybody writes first and found six
of seven stores untouched. Part [6.2](6.2-the-store-you-cannot-address.md) established that two of
the seven need a different treatment from the rest. This part puts them together, and the interesting
thing about the result is how boring the mechanism is.

There is no clever delete. There is a **registry** — a list of the stores, in code, that other code
iterates — and a rule per store saying how it is reached. `purge` walks the registry, applies the
rule, and reports how many rows each store gave up.

Two properties come out of that shape, and both of them are the point:

**A store not in the registry is a visible absence rather than an invisible one.** Part
[2.1](../02-where-the-copies-are/2.1-one-sentence-seven-places.md) already made this argument from the
other direction: a map maintained by intention will drift, so the count has to be runnable. The
registry is the same claim applied to deletion. It does not guarantee the list is complete — nothing
can — but it moves the question from *did anyone think of the cache?* to *is the cache in `STORES`?*,
and the second question has an answer you can grep for.

**The report is per store.** `purge` returns a dict of how many rows each store gave up, which means
an erasure can be evidenced rather than asserted. Part 6.1's delete returned `None`, and a routine
that returns nothing cannot be quoted in an answer to an access request.

This is the same shape as Day 68's permission table, and the resemblance is not a coincidence: both
are lists somebody maintains, checked by a diff, where the failure mode is drift rather than logic.

## Why Sutra needs it

Because part [7.1](../07-in-production/7.1-answering-what-do-you-hold.md) has to answer *what do you
hold about me* and *please erase it*, and neither answer can be given from a function that reaches one
store and reports nothing.

There is also a specific obligation this discharges. Day 48 introduced erasure as an obligation rather
than a feature, and part [1.4](../01-who-a-record-names/1.4-the-number-that-only-means-something-here.md)
established why the keys make it possible at all: the session id, the memory holder, the cache key and
the run id are the addresses a purge uses. Those keys were built for other reasons — Day 47 for
persistence, Day 48 for memory, Day 51 for caching, Day 61 for checkpoints — and this part is where
that accident becomes a capability.

## The mechanism

The registry is seven lines and lives beside the stores rather than inside the erasure routine:

```python
STORES: dict[str, str] = {
    "archive": "archive.json",
    "session": "session.json",
    "memory": "memory.json",
    "index": "index.json",
    "cache": "cache.json",
    "log": "log.jsonl",
    "checkpoint": "checkpoint.json",
}
```

**Line by line:**

- It maps a **name** to a **file**, which is what makes it a registry rather than a comment. Code that
  wants to iterate the stores imports this; code that wants one store's file calls `path(store)`.
  There is no second place where the list of stores exists.
- It lives in `_stores.py`, next to `load`, `save` and `reset` — so the module that knows how to read a
  store is the module that knows the stores exist. A registry kept somewhere else drifts from the
  thing it registers.
- Seven entries, and every one of them was added by a different day for a different reason. Nothing
  here was designed for erasure; the registry is the retrofit that makes erasure possible.

The purge is a loop with three branches, and the loop is the contribution:

```python
def purge(ref: str) -> dict[str, int]:
    """Remove or neutralise every trace of `ref`, returning how many rows each store gave up."""
    removed: dict[str, int] = {}

    for store in STORES:
        how = REACH[store]
        data = load(store)
```

**Line by line:**

- `for store in STORES` — the registry, not a hand-written sequence of calls. Adding a store to
  `STORES` puts it in the erasure path automatically, which is the property the whole part exists for.
- `REACH[store]` is a **subscript, not a `.get()`**. A store with no declared reach raises `KeyError`
  and stops the purge, which part [6.2](6.2-the-store-you-cannot-address.md) argued is the right
  failure: an under-erasure that reports success is worse than an erasure that stops and says why.
- `removed: dict[str, int]` accumulates a per-store count. The function returns evidence rather than
  `None` — compare part 6.1's `delete_from_archive`, which returned nothing and could therefore make no
  claim about what it had done.

The keyed branch carries the wrinkle part 6.2 named:

```python
        if how == "key":
            if store == "index":
                # Index rows are "<ref>#<n>", so the reference is a prefix rather than the key.
                doomed = [k for k in data if k.split("#")[0] == ref]
            else:
                doomed = [k for k in data if k == ref]
            for k in doomed:
                data.pop(k)
            removed[store] = len(doomed)
```

**Line by line:**

- The `if store == "index"` special case is Day 50's chunking showing up in an erasure routine three
  weeks later. An index row is keyed `ticket:7006#0`, so an equality test against `ticket:7006` matches
  nothing and the purge would report `0` for the index — a success message for a store that still holds
  the whole message.
- `k.split("#")[0] == ref` compares the parent reference rather than doing a prefix test with
  `startswith`, because `startswith` would also match `ticket:70061`. That is the kind of bug that
  never fires in a test fixture and fires in production the day the ticket numbering passes ten
  thousand.
- `doomed` is built first and popped second, because mutating a dict while iterating it raises
  `RuntimeError`. Ordinary Python, and worth noticing that the erasure routine is ordinary Python
  throughout — there is no library and no framework here.

**Line by line:**

- `cd` first: the lab's scripts import their siblings by plain name.
- `derived.py` calls `run()` to produce the same ordinary handled ticket part 6.1 used, counts the
  address in every store, purges, and counts again — so this run and part 6.1's run are the same
  experiment with a different delete.

Measured on 2026-09-06:

```text
purged ticket:7006 across all 7 registered stores

  store         rows  before  after
  archive          1       2      0
  session          1       2      0
  memory           1       2      0
  index            1       2      0
  cache            1       2      0
  log              1       1      0
  checkpoint       1       2      0

  copies remaining   0
```

**`copies remaining 0`**, against part 6.1's eleven. The `rows` column is the evidence: one row from
each of the seven stores, so the report can say what was reached rather than that something was done.

Read the `log` row carefully, because it is the one that looks wrong. It says `1` row and `after 0`,
and part [6.2](6.2-the-store-you-cannot-address.md) said the log line **must survive**. Both are true:
the row was not deleted, it was redacted, and the `after` column counts occurrences of the customer's
address rather than lines in the store. The line is still there, still saying that a ticket was
handled and when — `--how` prints it — and it no longer carries the customer's words. A count of
personal data is not a count of records, and conflating the two is how a redaction gets reported as a
deletion.

## When it breaks

**The registry is still a list somebody maintains, and this part's title says so on purpose.** Nothing
here guarantees completeness. If Day 70's quota router adds a cache of its own and nobody adds a row
to `STORES`, this purge will loop over seven stores, report `copies remaining 0`, and be wrong — and it
will be wrong *confidently*, which is worse than part 6.1's delete, because part 6.1's delete at least
made no claim.

That is the honest limit and it has a structural answer rather than an exhortation. Make registration
the way a store is created: a `Store` type whose constructor registers, so a store that exists is a
store in the registry, and forgetting is not an available move. Failing that, a test that walks the
state directory and asserts every file present has a registry row — which is a five-line test and turns
drift into a red build. Part [2.1](../02-where-the-copies-are/2.1-one-sentence-seven-places.md)'s
`copies.py --files` is exactly the instrument for it.

**The second limit is one the scan branch inherits.** `copies remaining 0` is a count of one search
term — the customer's address. Section 5 measured the redactor's free-text recall at 69%, and a purge
that matches on content is subject to the same arithmetic: a cached response that names the customer
some other way survives, and the counter that says zero is counting the term it was given. So the
number is honest about what it measured and must not be quoted as *all traces removed*.

**And the third:** this runs on one machine against seven files. A real purge crosses services, has to
be retried, has to be idempotent, and can partially fail — three stores erased, one timing out. The
per-store report is what makes that survivable: an erasure that reaches five of seven and says so can
be resumed, while one that returns `None` has to be run again from the beginning and hoped about.

## In production

**Erasure is a distributed transaction that nobody gets to call one.** The stores are owned by
different services and different teams, some behind APIs, some in another region, some in a warehouse
with a nightly load. The realistic shape is a **request with a state machine** — accepted, in progress
per store, completed, with a deadline — rather than a function call, and the per-store report above is
the row that state machine keeps. Everything in this part scales to that; the loop becomes a fan-out
and the return value becomes the record.

**What degrades at scale.** The registry falls behind the architecture, always, and in one direction:
stores get added. The countermeasure that works is not diligence but **discovery** — something that
periodically enumerates what actually exists (buckets, tables, indices, caches) and diffs it against
the registry, so an unregistered store is a finding rather than an absence. That is the same technique
Day 68 used for tools with no permission row, and the same technique this day's part 2.1 used for
copies. Three different subjects, one method: make the list runnable and diff it.

**The failure mode that only appears with real traffic.** An erasure request arrives for a customer who
has an open ticket. Deleting the row underneath a running conversation produces a session referring to
an archive row that no longer exists, and depending on the code that is either a graceful degradation
or a crash on somebody else's turn. The professional answer is that erasure has a **precondition** —
no in-flight work for this subject — and a documented order: stop accepting new work for the subject,
drain, then purge. That belongs in the runbook next to the routine, and it is the sort of thing that
is obvious in hindsight and absent from every first implementation.

**The review comment a senior engineer leaves:** *"The loop is right and the per-store report is the
bit I care about — keep it, and log it, because that report is what we'll be asked for. Two things
before this ships: a test that walks the state directory and fails if a file has no row in `STORES`,
so the registry can't silently fall behind; and please rename `copies remaining` in the output, because
it's the count for one search term and somebody will read it as 'all traces gone'. Call it what it is."*

**The interview question:** *"How do you implement the right to erasure across a system with a dozen
data stores?"* An honest answer: *"Not with a clever delete — with a registry of stores that code
iterates, and a declared rule per store for how it is reached. On the desk I did this on, the naive
version deleted from the archive, reported success and left the data in six of seven stores. The loop
version reached all seven and returned a per-store count, which matters because that report is the
evidence you'll be asked for. Three of the stores needed different treatment: an index whose keys are
chunk ids rather than ticket ids, a cache that isn't addressable by customer at all so it has to be
scanned or given a TTL, and an append-only log that must survive, where the operation is redacting the
excerpt and keeping the line that proves the event happened. And I'd be honest that the registry is
still a list somebody maintains, so the real control is a discovery job that diffs what exists against
what's registered — otherwise the next cache somebody adds makes the routine confidently wrong."*
