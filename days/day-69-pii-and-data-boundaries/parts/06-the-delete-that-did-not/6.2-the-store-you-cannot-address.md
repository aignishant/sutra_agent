# 6.2 — The store you cannot address

## One-line answer

Five of the seven stores can be reached by key, one has to be **scanned** because its key is a hash of
the prompt and cannot be asked *what do you hold about this person*, and one — the log — **must
survive**, so erasing it means removing the personal part and keeping the line that proves the event
happened.

## The story

A locksmith is called to a block of flats where the managing agent wants every key to flat 7 accounted
for after a tenant leaves.

Most of it is straightforward. There is a board in the office with a hook per flat, labelled, and the
spare for flat 7 is on it. The cleaner's set is signed out in a book, with a name and a date, and it
comes back the same afternoon.

Two are not straightforward. There is a drawer of unlabelled keys that has accumulated over eleven
years, and the only way to find out whether any of them opens flat 7 is to walk up there and try them,
one at a time. And there is the fire brigade's key safe on the outside wall — which certainly holds a
key, which certainly must not be emptied, and which is not a filing problem at all.

The agent's report cannot say *"all keys recovered"*. It can say: eleven accounted for by the board and
the book, one drawer scanned and three keys destroyed, and the fire safe left as it is, deliberately,
with the reason written next to it.

## The idea in plain language

Part [6.1](6.1-deleted-and-still-retrievable.md) ended with a table listing what survived the archive
delete and hinted that two of the surviving stores fail differently from the rest. This part is those
two, and the distinction they teach is the one that decides whether an erasure routine is honest.

Every store falls into one of three kinds, and the kind is a property of **how the store is keyed**,
not of how important it is:

- **Addressable by key.** The row can be found from the customer or the ticket reference, directly.
  `archive`, `session`, `memory` and `checkpoint` are all this, and so is `index` — with a wrinkle, because
  an index row is a *chunk* whose key is `ticket:7006#0`, so the reference is a prefix rather than the
  key itself. Day 50's chunking produced that, and it is the sort of detail an erasure routine gets
  wrong silently.
- **Not addressable — must be scanned.** The response cache from Day 51 keys on a hash of the prompt.
  That is exactly right for a cache: the key is a fingerprint of the input, which is what makes a
  lookup fast. It also means there is no query of the form *what does this cache hold about Lin Zhou*,
  because the key carries no information about who the prompt was about. The only way to find the rows
  is to open every value and read it.
- **Must survive.** The event log from Day 22 is append-only on purpose. It is the record that things
  happened, and Days 60 to 65 built durability and audit on top of that property. Deleting lines from
  it destroys the thing it exists for — so the right operation is not deletion. It is **redaction in
  place**: the personal part goes, the line stays.

The point of separating these is that a routine which treats all three the same is wrong in one
direction or the other. Treat the cache like a keyed store and it is silently missed. Treat the log
like a keyed store and you have destroyed your audit trail in order to satisfy an erasure request,
which is a worse outcome than the request.

## Why Sutra needs it

Because the desk has both awkward stores, and it has them for good reasons this curriculum built
deliberately. Day 51 added the cache because quota is the currency and paying twice for one answer is
the most avoidable cost there is. Day 22 made the log append-only, and Days 60 to 65 leaned on that
so hard that a phase gate was built out of it.

So this is not a case where a bad design created an awkward store. Two well-made components, each
correct for its purpose, have properties that make erasure hard — and the honest response is to say so
in the design rather than to discover it when somebody asks.

It also decides what part [7.1](../07-in-production/7.1-answering-what-do-you-hold.md) can truthfully
answer. *"We erased your data"* is a claim about seven stores, and two of them need a different sentence
each.

## The mechanism

The reach of each store is a declaration, not a guess:

```python
# How each store can be reached. "key" means the row is addressable by the ticket reference, which
# is Day 48's `holder` idea generalised. "scan" means it is not, and the only way to find the data
# is to look inside every value. "redact" means the row must survive for a different reason.
REACH: dict[str, str] = {
    "archive": "key",
    "session": "key",
    "memory": "key",
    "index": "key",
    "cache": "scan",
    "log": "redact",
    "checkpoint": "key",
}
```

**Line by line:**

- It is a **dict beside the store registry**, so every store has a reach and a store added without one
  raises a `KeyError` in `purge` rather than being quietly skipped. That is deliberate: a store with no
  declared reach should stop the routine, not pass through it.
- The three values are the three kinds above and there is no fourth. A vocabulary this small is what
  makes the table reviewable — somebody can read seven rows and disagree with one.
- `index` is `key` and the comment in `purge` explains why that is not quite true: the reference is a
  prefix of the key. The distinction is one line of code and it is the difference between erasing a
  ticket and erasing nothing.

The scan branch is what "not addressable" looks like when written out:

```python
        elif how == "scan":
            # The cache key is a hash of the prompt. There is no way to ask it "what do you hold
            # about this customer?", so every value has to be opened and read.
            doomed = [k for k, v in data.items() if ref in v.get("prompt", "") or NEEDLE in str(v)]
            for k in doomed:
                data.pop(k)
            removed[store] = len(doomed)
```

**Line by line:**

- `data.items()` — every entry, without exception. There is no index to consult and no filter to apply
  first, which is the entire cost of this branch: it is `O(cache)` per erasure request rather than
  `O(rows for this customer)`.
- The condition tests **two** things: the ticket reference inside the stored prompt, and the customer's
  address anywhere in the value. Both are needed because a cache entry may be keyed on a prompt that
  quotes the ticket and may hold a *response* that names the customer without quoting the reference.
- `str(v)` flattens the whole value to search it. That is crude and it is honest about what a scan is:
  when you cannot address the data, you match on its content, which brings you back to the redactor
  that section 5 measured at 69% recall on free text. **A scan is only as good as the search term**,
  and a customer
  whose name is spelled differently in one cached response is a customer that scan misses.
- Nothing here can prove it found everything. That is the property to carry away.

And the log, which is the opposite problem:

```python
        else:
            # The log is append-only on purpose: it is the record of what happened, and deleting
            # lines from it destroys the property Day 22 built it for. So the line stays and the
            # personal part of it goes, leaving a row that still proves the event occurred.
            count = 0
            for row in data:
                if row.get("ref") == ref:
                    row["excerpt"] = "[ERASED ON REQUEST]"
                    count += 1
            removed[store] = count
```

**Line by line:**

- The row is **not** popped. It is edited in place, which is the whole distinction between this branch
  and the other two.
- Only `excerpt` changes. The `event` and the `ref` stay, so the log still answers *did the desk handle
  this ticket, and when* — the questions Day 65's audit was built on — while no longer carrying the
  customer's words.
- `[ERASED ON REQUEST]` is a marker rather than an empty string, and the difference matters during an
  audit: an empty excerpt is indistinguishable from an event that never had one, and this says a
  decision was taken.
- `count` records how many lines were touched, so the erasure report can say *the log was redacted, not
  deleted, in n places* — which is the sentence a regulator or an auditor actually wants.

The last line is the deliverable. The event survives, the reference survives, and the customer's words
are gone — which is the only shape that satisfies both an erasure obligation and an audit obligation
at the same time.

## When it breaks

**The scan does not scale, and pretending otherwise is the failure.** Seven entries in a test cache is
a loop. A production cache with millions of entries, scanned per erasure request, on a system that
receives erasure requests routinely, is a job rather than a function call — and the honest engineering
answer is usually to change the store rather than to keep scanning it. Two options, and both are
design changes rather than deletion tricks:

- **Add an addressable index alongside the cache**: a second map from customer to the cache keys their
  data appears in, maintained on write. It costs a write per cache entry and turns an `O(cache)` scan
  into a lookup.
- **Give the cache a short TTL and say so.** A cache whose entries expire in a day does not need an
  erasure routine at all; it needs a stated retention period and the confidence that it is enforced.
  This is usually the right answer, and it is a decision somebody has to take and write down rather
  than a property caches automatically have.

**The redaction has a limit that must be stated, not implied.** Redacting the excerpt leaves the
`ref`, and part [1.4](../01-who-a-record-names/1.4-the-number-that-only-means-something-here.md)
already argued that a reference which resolves to one person is an identifier in its own right. So the
redacted log line is not anonymous — it says *a ticket belonging to this customer was handled at this
time*. Whether that is acceptable is a decision about what the log is for, and the defensible position
is that the record of processing must survive because it is itself required. What is not defensible is
calling the redacted line anonymous, which is the same error part
[5.3](../05-measuring-the-redactor/5.3-the-wall-called-a-name.md) measured on hashing.

**The third failure is a store with no declared reach.** `purge` looks up `REACH[store]`, so a store
added to the registry and not to the reach table raises `KeyError` and the erasure stops. That is the
right behaviour and it will feel wrong the first time it happens in production, when an erasure request
fails because somebody added a queue last week. The alternative — defaulting to `scan` or skipping —
is a routine that silently under-erases, which is worse.

## In production

**What degrades at scale.** The scan branch is where erasure cost becomes visible. At small volume
nobody notices; at large volume erasure requests arrive continuously and each one wants to read every
cache entry, so either the store gets an addressable index or the requests get batched into a nightly
job with a stated latency. Both are fine and both have to be **stated** — *we complete erasure within
n days* is a commitment somebody has to make on the record, and it is decided by the slowest store
rather than the fastest.

**The failure mode that only appears with real traffic.** The scan misses things the search term did
not match, and nobody finds out. A cached response that refers to *"Lin"* rather than to the full name
or the address survives a scan for either. That is the same recall problem section 5 measured, applied
to erasure instead of to redaction — and it is worse here, because a redactor's misses are measurable
against an answer key while a scan's misses are, by construction, the entries you did not know to look
for. This is the strongest practical argument for the addressable-index option: it removes the need to
be right about the search term.

**What a professional writes down.** A per-store row in the data map saying: how it is reached, what
happens on erasure, why, and what the residual is. Four columns, seven rows, in the repository next to
the code. That document is what part [7.1](../07-in-production/7.1-answering-what-do-you-hold.md)
answers an access request from, and its value is entirely in the two awkward rows — the five keyed
stores would be guessed correctly by anybody.

**The review comment a senior engineer leaves:** *"The three reach kinds are right and I want the
residual written next to each one. The cache scan matches on the reference or the address, so it will
miss a cached answer that says 'Lin' — either add a customer-to-keys index on write, or give the cache
a TTL short enough that we can say the data is gone by expiry and stop scanning. And on the log: the
redacted line still carries the ref, which resolves to one person, so please don't describe it as
anonymised in the policy. Say it's the minimum record of processing, retained deliberately, and say
for how long."*

**The interview question:** *"Some data can't be deleted. How do you handle erasure then?"* An honest
answer: *"By splitting the stores by how they're keyed rather than by how important they are. Most are
addressable — you can find the rows from the customer or the ticket, and you delete them. Some aren't:
our response cache keys on a hash of the prompt, so there's no way to ask it what it holds about a
person, and the only option is to open every value and match on content — which inherits the recall
problem of whatever you're matching on, so at scale I'd add a customer-to-keys index on write or give
the cache a TTL and stop scanning. And some must survive: the event log is the record that processing
happened, and deleting lines from it destroys the audit trail, so there the operation is redaction in
place — the excerpt goes, the event and the reference stay, with a marker saying a decision was taken.
The thing I'd insist on is that each store's answer is written down with its residual, because 'we
erased your data' is a claim about every store and two of them need a different sentence."*
