# 2.3 — The copy nobody calls a copy

## One-line answer

An index and a cache feel like they hold structure rather than content, and both of them hold the
**full text** — which is why a delete from the archive leaves the customer's name, telephone number
and address sitting in `index.json`, readable with `cat`.

## The story

A corner shop keeps a notebook by the till.

It is not the accounts. The accounts are a separate thing that the shop's owner does properly with
receipts. The notebook is for the shopkeeper's own use: *number 14 takes two pints on Fridays and
pays at the end of the month. The lady with the twins wants the bread put by if it comes late. The
man from the flats above, bad knee, brings his own bag, always asks about the cricket.*

Ask the shopkeeper whether they keep customer records and they will say no, of course not, it is a
corner shop. And they are being honest: the notebook is not records. It is how they do the job. It
lives by the till and it has never once felt like a filing cabinet.

It is also the only document in the building that would let a stranger walk in and know who lives
where, who is unwell, and who is behind on paying.

## The idea in plain language

A **derived store** holds data computed from another store. The archive is the original; the index,
the cache and the checkpoint are derived from it.

People consistently under-count derived stores when they think about where personal data lives, and
the reason is that we name things after their *purpose* rather than their *contents*. "Index" sounds
like the thing at the back of a book — page numbers, not paragraphs. "Cache" sounds like a speed
optimisation. "Checkpoint" sounds like a bookmark.

The names are honest about the purpose and misleading about the contents, and in two of these three
cases the misleading part is not an implementation detail that a better design would avoid. It is
forced.

**An index must store the text it indexed.** Day 50 established why: what you retrieve is a chunk,
and the chunk has to *be* somewhere so it can be returned and put into a prompt
([1.1](../../../day-50-chunking-and-top-k/parts/01-the-unit-you-index/1.1-the-unit-you-store-is-the-unit-you-find.md)).
An index that stored only term frequencies and pointers could tell you *which* document matched and
would then have to go back to the archive to fetch it — which is a legitimate design, and it is a
different one, and it costs a lookup per hit. Almost every real vector store keeps the text beside
the vector for exactly this reason.

**A cache must store what it is caching.** A response cache exists to return the response, so the
response is in it. Day 51 keyed it on a fingerprint of the prompt, and to be able to check a
fingerprint collision it keeps the prompt too
([2.3](../../../day-51-caching-the-quota-lifeline/parts/02-the-context-cache/2.3-the-fingerprint-is-the-key.md)).
Both halves are customer text.

**A checkpoint must store the run's state**, and on this desk the run's state includes the ticket it
is working on and the draft it has written. Day 61 needed that so a killed run could resume with
what it had.

So the sentence to carry away is not "be careful with derived stores". It is: **a derived store of a
document store is a document store.** The word "derived" describes where the data came from, and
nothing at all about what it now contains or how long it will keep it.

## Why Sutra needs it

Section 6 is the erasure section, and this part is the reason it is hard. Day 48 built erasure
against a store with a `holder` field, addressable by design
([4.2](../../../day-48-memory-design/parts/04-privacy-and-erasure/4.2-you-cannot-delete-what-you-cannot-address.md)).
That machinery works, and it works on the store it was built for.

The index is keyed by `ticket:7006#2`. The cache is keyed by a hash. Neither of them has ever heard
of `holder`, both of them are full of the same customer's text, and both were added after the erasure
policy was written.

## The mechanism

Run the desk and then open the derived stores. Do not take anybody's word for what is in them,
including this document's.

```bash
cd days/day-69-pii-and-data-boundaries/lab
uv run python copies.py > /dev/null
cat state/index.json
```

**Line by line:**

- `copies.py` populates all seven stores; the count is
  [2.1](2.1-one-sentence-seven-places.md)'s subject and is discarded here.
- `cat` is the whole point of the exercise. A store you can print is a store whose contents you can
  stop guessing about, and the reason `_stores.py` writes plain JSON files rather than using a real
  database is so that this command works.

The index rows for `ticket:7006`, measured on 2026-09-06:

```json
{
  "ticket:7006#0": {
    "text": "From: lin.zhou@example.com\n\nDowngrade did not take effect. Plan still shows Pro after a week.\n\n-- \nLin Zhou\n+44 7700 900318\nlin.zhou@example.com",
    "terms": [
      "7700", "900318", "after", "com", "did", "downgrade", "effect", "example",
      "from", "lin", "not", "plan", "pro", "shows", "still", "take", "week", "zhou"
    ]
  }
}
```

Two things in that row, and the second is a surprise even to people who expected the first.

**The `text` field is the whole ticket**, including the sign-off — the customer's name, their
telephone number with the country code, and their email address twice. This is the row that comes
back from a search, and it is a complete copy of the message.

**The `terms` list has the personal data in it too.** `zhou` is a term. `900318` is a term, because
splitting on non-alphanumeric characters turned `+44 7700 900318` into pieces and one of the pieces
is six digits of a telephone number. `lin` is a term. Even if somebody rewrote the index to drop the
`text` field, the search structure *itself* would still carry fragments of the identifiers, because
an index of text is built out of the words in the text and some of those words are people.

Now the cache, which has a different shape and the same problem:

```bash
cat state/cache.json
```

```json
{
  "a4655bc21c2e": {
    "prompt": "From: lin.zhou@example.com\n\nDowngrade did not take effect. Plan still shows Pro after a week.\n\n-- \nLin Zhou\n+44 7700 900318\nlin.zhou@example.com",
    "response": "Hello Lin Zhou, the downgrade did not apply because the change was made mid-cycle. I have corrected the plan."
  }
}
```

The key is a hash and tells you nothing. Both values are customer text — and the `response` is the
subject of [2.4](2.4-the-reply-is-personal-data-too.md).

## When it breaks

The break is the one section 6 proves, and it is worth seeing the shape of it here.

🎬 **The scene:** a customer asks to be removed. Somebody deletes their tickets from the archive.
The deletion succeeds. `archive.json` no longer has the row.

😬 **The naive fix:** confirm to the customer that the record is gone, because it is — you can look
in the archive and see for yourself.

💥 **Why it fails:** the index was not asked. Nothing about deleting from the archive touches a
derived store, because "derived" describes provenance and not lifecycle. The index still has the
chunk, and the chunk still has the sign-off, and the retrieval path still returns it. The customer's
name comes back in an answer to a completely unrelated question, weeks later.

💡 **The insight:** derived data does not inherit deletions. It inherits **writes** — that is what
makes it derived — and the inheritance runs one way. Every derived store needs its own delete, and
the delete has to be found by a mechanism, because a person listing the stores from memory will list
the ones they think of as stores.

[6.1](../06-the-delete-that-did-not/6.1-deleted-and-still-retrievable.md) runs that exact sequence
and prints what comes back.

There is a second break with no customer in it at all. Somebody rebuilds the index from the archive
after a deletion, which is the right instinct — a full rebuild does remove the deleted rows. It also
does nothing to the cache, because the cache is not derived from the archive; it is derived from
*prompts that were sent*, and no rebuild will ever regenerate it. Two derived stores, two different
provenances, and only one of them is fixed by the obvious remedy.

## In production

**What a professional writes instead.** Every derived store gets registered with three things: the
store it derives from, the key that maps a source record to its derived rows, and a delete function.
The middle one is the piece people skip and the piece that makes it work — the index in this lab is
deletable only because its keys are `ticket:7006#0`, so the source reference is a prefix. Had the
rows been keyed by a random id with the reference buried inside the value, deleting one customer
would have meant scanning the whole index, which is exactly the state the cache is in.

**What degrades at scale.** Real vector stores make this harder in two specific ways. Deletion is
often a **soft** delete — the row is marked and remains on disk until a compaction runs, so "deleted"
and "gone" are separated by an interval nobody documents. And embeddings themselves are derived data
that no one thinks of as text at all: a vector is not readable by a person, but it is a function of
the text, and published inversion work has recovered substantial parts of the original from
embeddings alone. Treating the vector as safe because it looks like numbers is
[1.1](../01-who-a-record-names/1.1-the-list-of-fields-is-not-the-answer.md)'s list mistake wearing a
different hat.

**The failure mode that only appears with real traffic.** Search results outlive their source in a
way that is visible to users. A deleted ticket keeps being retrieved as context for other customers'
questions, so the *symptom* is not a privacy report — it is a support agent noticing that the desk
keeps citing a ticket that no longer exists. That is a data-integrity complaint, it gets triaged as a
bug in retrieval, and the privacy consequence is discovered by whoever picks up the bug.

**The review comment a senior engineer leaves:** *"This index stores `text` alongside the vector, so
it is a copy of the ticket, not a pointer to it. That means it needs a delete path and a retention
period of its own. Right now the only way to remove a customer from it is a full rebuild, and the
cache cannot be rebuilt at all — write the delete function now, while the key scheme still makes it
a prefix match."*

**The interview question:** *"You deleted a customer's records. Are they gone?"* The answer that shows
you have done this: *"Almost certainly not, and the place I would look first is the search index. I
ran this: deleted a ticket from the archive, then queried the index, and the top hit came back with
the full text including the customer's name, phone number and address — no error, no warning. The
reason is that derived stores inherit writes and not deletes, and an index has to store the text
because retrieval returns the chunk. What I do now is register each derived store with the key that
maps a source record to its rows and a delete function, and the key scheme matters: ours worked
because index rows are prefixed with the ticket reference. The cache had no such key and had to be
scanned."*
