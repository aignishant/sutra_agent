# 6.1 — 🅿️ `generate_content`: the door every tutorial walks through

> **🅿️ Parked.** Awareness-level and interview-ready, deliberately **not** built on. You are learning
> to *read* this surface, not to write it. Sutra's code uses the Interactions API (ADR-0006); this
> part exists so that the enormous body of existing writing about Gemini is legible to you rather
> than confusing.

## One-line answer

`client.models.generate_content(...)` is the older Gemini surface — **not deprecated, still fully
supported, and relabelled "Legacy" in the documentation** — and because virtually every tutorial,
blog post and older repository uses it, being unable to read it is a real handicap even if you never
type it.

---

## The story

Someone learns to drive on a car with an automatic gearbox. They are a competent driver: they
understand the road, the rules, the hazards.

Then they borrow a friend's car and cannot move it, because it has a clutch. Not a small problem —
they are stuck in a car park. And the deeper issue is not the clutch pedal, which takes an afternoon.
It is that half the driving advice they have ever heard now makes no sense to them. *"Drop it into
second before the bend"* was never advice about gearboxes; it was advice about cornering, phrased in
the vocabulary of the majority of cars.

They had not learned less than other drivers. They had learned a strictly newer thing, and it left
them unable to parse the accumulated wisdom of everyone who learned before.

This is the position you would be in, having learned only the Interactions API, opening almost any
existing piece of writing about Gemini. The advice in those posts about prompt structure, safety
settings, streaming and token accounting is largely still correct and useful. It is written in a
vocabulary you would not recognise.

---

## The idea in plain language

There are two ways to call a Gemini model from the same `google-genai` package.

**`client.models.generate_content(...)`** is the older one. It is stateless in the strong sense — no
server-side conversation, no ids, you always send everything. It is what every example written before
mid-2026 uses.

**`client.interactions.create(...)`** is what Google's quickstart now leads with, and what this day
taught. It adds server-side state as an option
([3.3](../03-context-and-memory/3.3-the-server-will-remember.md)).

The status, checked on 2026-08-24 and worth being precise about because the internet will not be:

- **`generate_content` is not deprecated.** The SDK reference documents it fully, with no deprecation
  notice.
- **Its documentation pages have been retitled "Gemini Generate Content API (Legacy)."** The label
  moved; the support did not.
- **ADK 2.x uses it by default**, reaching Interactions only when you opt in — see below.

So it is neither dead nor the future. It is the incumbent.

### The translation table

This is the practical content of this part. When you read a tutorial, translate:

| Concept | `generate_content` (legacy) | Interactions (what you learned) |
| --- | --- | --- |
| The call | `client.models.generate_content(...)` | `client.interactions.create(...)` |
| The prompt | `contents=` | `input=` |
| Settings | `config=GenerateContentConfig(...)` | `generation_config={...}` |
| The text | `response.text` | `interaction.output_text` |
| The receipt | `response.usage_metadata` | `interaction.usage` |
| Reasoning tokens | `thoughts_token_count` | `total_thought_tokens` |
| History | `contents=[Content(role=…, parts=…)]` | `input=[{"type": "user_input", …}]` |
| Server-side state | *(does not exist)* | `previous_interaction_id`, `store` |

**Note the two field names for reasoning tokens.** That row is the single most likely thing to waste
your time, and it is exactly the `AttributeError` that
[2.2](../02-tokens-the-meter/2.2-reading-the-receipt.md) showed you.

## The mechanism

The same call, both ways, so the mapping is concrete rather than a table you skim:

```python
# 🅿️ LEGACY — what you will read in tutorials. Do not build Sutra on this.
from google.genai import types

response = client.models.generate_content(
    model="gemini-3.7-flash",
    contents="Why is the sky blue? Answer in one sentence.",
    config=types.GenerateContentConfig(temperature=0.0, max_output_tokens=400),
)
print(response.text)
print(response.usage_metadata.thoughts_token_count)
```

**Line by line:**

- `from google.genai import types` — the legacy surface uses **typed config objects** from a `types`
  module, where Interactions accepts a plain dict. Seeing `types.` in a snippet is a fast tell that
  you are reading legacy code.
- `client.models.generate_content(...)` — note `models`, not `interactions`. Same client, different
  resource.
- `contents=` — the parameter Interactions calls `input`. It accepts a string or a list of `Content`
  objects, the same shape/shape distinction as
  [3.2](../03-context-and-memory/3.2-history-is-a-list-you-own.md).
- `config=types.GenerateContentConfig(...)` — a constructed object rather than a dict, and note the
  parameter is `config` rather than `generation_config`. **Both the name and the type differ**, which
  is why copying a config block between the two surfaces fails twice.
- `response.text` — not `output_text`. Same meaning, and it carries the same trap: **it can be `None`
  on a successful call**, exactly as [5.1](../05-the-failure-lab/5.1-the-cap-that-ate-the-answer.md)
  demonstrated.
- `response.usage_metadata.thoughts_token_count` — **the other name for reasoning tokens**, on the
  other name for the receipt. Two levels of renaming in one attribute access.

And the version you actually write:

```python
# ✅ SUTRA — the surface this project uses.
interaction = ask(
    client,
    "Why is the sky blue? Answer in one sentence.",
    config={"temperature": 0.0, "max_output_tokens": 400},
)
print(interaction.output_text)
print(interaction.usage.total_thought_tokens)
```

**Line by line:**

- `ask(...)` — through the one door from
  [1.5](../01-first-contact/1.5-the-only-door-429.md), which supplies the model pin, `store=False`
  and the 429 handling. **The legacy example above has none of those** — no retry, no store decision
  — which is a fair illustration of what a tutorial snippet leaves out.
- `config={"temperature": 0.0, ...}` — a plain dict. No `types` import, no constructor.
- The remaining two lines differ from the legacy block only in field names, and **that is the point
  of putting them side by side**: the ideas transfer completely, only the vocabulary changes.

### The bridge to Day 5

ADK 2.x can use either surface, and this is the line to remember:

```python
from google.adk.agents.llm_agent import Agent
from google.adk.models.google_llm import Gemini

root_agent = Agent(
    model=Gemini(model="gemini-3.7-flash", use_interactions_api=True),
    name="triage_agent",
)
```

**Line by line:**

- `from google.adk.models.google_llm import Gemini` — ADK's Gemini model wrapper. Verified against
  `adk.dev/agents/models/google-gemini/` on 2026-08-24; **re-verify on Day 5**, per Principle 8, since
  the plan's ADK baseline has already moved once (§5 says 2.6.3; PyPI showed **2.7.1** on 2026-08-24).
- `model=Gemini(...)` rather than `model="gemini-3.7-flash"` — the plain string form works and gives
  you ADK's defaults. **Wrapping it in `Gemini(...)` is what lets you configure the model**, and it is
  the form you need in order to reach the next parameter.
- `use_interactions_api=True` — **the bridge.** ADK calls `generateContent` unless you set this. So
  Day 2's surface and Day 5's framework meet here, and the fact that this is an opt-in flag is
  precisely why understanding both surfaces is not optional.
- `name="triage_agent"` — every ADK agent needs a name; it is how the framework identifies it in
  traces and in multi-agent composition later.
- **Do not type this today.** ADK is not installed until Day 5, and packages arrive on the day they
  are used. This block is a forward reference you will recognise, not an instruction.

## When it breaks

**Mixing the two surfaces' vocabulary:**

```text
Traceback (most recent call last):
  File "sutra/mechanics.py", line 52, in ask
    return client.interactions.create(model=MODEL, contents=prompt)
TypeError: create() got an unexpected keyword argument 'contents'
```

**What it means.** You copied `contents=` from a tutorial into an Interactions call. **This is the
single most likely error you will produce this week**, and it is why the translation table above is
the real content of this part. The Interactions parameter is `input`.

**The config that is silently the wrong type:**

```text
google.genai.errors.ClientError: 400 INVALID_ARGUMENT. {'error': {'code': 400,
'message': 'Invalid JSON payload received. Unknown name "generation_config" at
'interaction': Cannot bind query parameter.', 'status': 'INVALID_ARGUMENT'}}
```

**What it means.** A `types.GenerateContentConfig` object was passed where a plain dict was expected,
or the parameter name came from the other surface. **The fix is to stop translating from memory** and
print what your installed version actually accepts.

**The tutorial that will not run at all:**

```text
Traceback (most recent call last):
  File "example.py", line 1, in <module>
    import google.generativeai as genai
ModuleNotFoundError: No module named 'google.generativeai'
```

**What it means.** You found an even older tutorial. `google-generativeai` is a **third**, superseded
package — not `google-genai` at all. **Three generations of this SDK are in circulation**, and dating
a blog post before trusting it is a genuine professional skill. If a snippet imports
`google.generativeai`, close the tab.

## In production

**What a professional does when meeting a legacy surface is date the source before trusting it.**
The question is not "is this correct?" but "correct as of when, and against which version?" A 2025
post about Gemini may be entirely right about prompt structure and entirely wrong about every field
name. **Separating the durable advice from the versioned vocabulary is the actual skill**, and it is
the same skill this whole plan encodes as Principle 8: verify APIs against the live source on the day
you use them.

**What degrades at scale is a codebase that has both surfaces in it.** This happens naturally: an
older service uses `generate_content`, a new one uses Interactions, someone copies a helper across.
Now there are two retry paths, two usage-field names, and two config shapes, and the monitoring that
sums token usage silently under-counts one of them because it reads `thoughts_token_count` and half
the fleet reports `total_thought_tokens`. **A metric that is quietly wrong is worse than a metric
that is missing.** The defence is the one Sutra already has: one door
([1.5](../01-first-contact/1.5-the-only-door-429.md)), so that migrating surfaces is a change in one
function rather than an audit.

**The failure that only appears with real traffic** is the half-migration. Because both surfaces
work, a partial migration passes every test — each path is individually correct. What breaks is the
*combination*: a conversation started with `previous_interaction_id` cannot be continued by a
`generate_content` call, so any request routed to the older path mid-conversation loses the history
entirely. The user sees an assistant that abruptly forgets, on a fraction of requests, correlated with
nothing they can describe. **Migrations that leave two working paths are more dangerous than
migrations that break loudly.**

**The review comment a senior engineer leaves:** *"This PR adds a `generate_content` call in a service
that otherwise uses Interactions. Was that deliberate, or copied from a doc? If deliberate, note why,
because we now have two usage-field names and the cost dashboard only knows one. If not, route it
through `ask` like everything else."*

**The interview question.** *"The vendor released a new API surface and marked the old one legacy —
do you migrate?"* This is a judgement question, and an unconditional yes or no both answer it badly.
The considerations: **legacy is not deprecated** — no removal date means no forced timeline, so
migration competes with other work on merit rather than urgency; **what does the new surface buy
you**, concretely, for your workload; **what does it cost** in ecosystem support, since the older
surface has years of accumulated documentation, examples and third-party adapters built against it;
and **can you migrate behind a seam**, so the change is one function rather than a sweep. The detail
that shows experience: **watch for the half-migration** — because both surfaces work, a partial
migration passes all its tests and fails only where the two meet, which is the worst failure shape
there is. Then the honest close: *the strongest reason to learn a new surface early is rarely the
features — it is that the vendor's documentation and defaults are moving there, and you will be
reading their docs for years.*
