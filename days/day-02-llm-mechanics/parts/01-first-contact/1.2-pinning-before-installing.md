# 1.2 — Pinning before installing: the version you looked up, not the one you remember

## One-line answer

Sutra installs its first package today, and the rule that governs it is **the version goes in the
command, the lookup happens before the command, and the observation goes in a ledger** — because a
dependency you cannot name the version of is a dependency you cannot debug a year from now.

---

## The story

A team has an application that has worked for eight months. On a Tuesday, a new engineer joins,
clones the repository, runs the install command in the README, and starts the server. It crashes
immediately on a function that does not exist.

Nobody changed the code. The last commit is from March. The tests pass on everyone else's machine
and on the build server, and they have passed every day for eight months.

What happened is that the README said `pip install requests` and the application was written against
a version of that library from March. In the intervening months the library released a new major
version that renamed a function. Every existing machine already had the old version sitting in its
environment and kept happily using it. The new engineer's machine, being new, got today's version —
the only correct thing for the installer to do, given it was told nothing.

The bug was not introduced on Tuesday. It was introduced in March, in a README, by not writing down
a number. It simply waited eight months for someone with an empty machine to walk into it.

This is the most boring failure in software and it costs an enormous number of hours, because the
symptom appears nowhere near the cause and the person who hits it is always the person with the
least context — the new joiner, the build server rebuilt from scratch, you in a year.

---

## The idea in plain language

A **package** is somebody else's code that your project uses. A **dependency** is a package your
project cannot run without. **Installing** one means downloading a copy into your project's
environment.

When you ask for a package without naming a version, the installer gives you whatever is newest at
that moment. That is a **floating** dependency: the same command, run on two different days, gives
two different programs. **Pinning** means naming the exact version, so the command means the same
thing forever.

Three terms you need, defined once:

| Term | Plain meaning |
| --- | --- |
| **Pin** | Naming an exact version: `google-genai==2.19.0`, not `google-genai` |
| **Lockfile** | A machine-written record of every version actually installed, including the dependencies of your dependencies. Sutra's is `uv.lock`, and it is committed to git |
| **Ledger row** | A human-written note saying what you observed, when, and why. Sutra's is `docs/PACKAGES.md` |

The lockfile and the ledger look redundant and are not. The lockfile answers *"what is installed?"*
— a machine reads it and reproduces your environment exactly. The ledger answers *"why, and what did
you actually see on the day?"* — a human reads it in eight months when something has gone strange.
Reproducibility and accountability are different problems, and Sutra keeps both.

This is Principle 7 from the plan, and it is worded strongly on purpose: **never invent a version
number.** Look it up live, or leave a `TODO` containing the exact command that would look it up. A
guessed version in a document is worse than no version, because it looks like it was checked.

## The mechanism

The order matters, and it is the opposite of what most people do. **Look up, then pin, then install,
then record.** Not install-then-discover-what-you-got.

**Step 1 — look it up live.** Do not trust this document; this document was written on a specific
day and packages move.

```bash
curl -s https://pypi.org/pypi/google-genai/json \
  | python -c "import sys,json; d=json.load(sys.stdin); print(d['info']['version'], d['info']['requires_python'])"
```

**Line by line:**

- `curl -s https://pypi.org/pypi/<name>/json` — PyPI is the Python Package Index, the public registry
  every Python install reads from. Every package has a JSON endpoint at this exact shape describing
  its releases. `-s` is "silent": suppress the progress meter so only the JSON reaches the pipe.
- `| python -c "..."` — pipe the JSON into a tiny inline Python program rather than reading it by
  eye. The response is thousands of lines listing every release ever made; you want two fields.
- `json.load(sys.stdin)` — parse whatever arrived on standard input. `sys.stdin` is the pipe.
- `d['info']['version']` — the **current** version. This is the number that goes in your pin.
- `d['info']['requires_python']` — which Python versions the package supports. Check it against your
  own: Sutra runs 3.12 (plan §5), and a package requiring 3.13 would be a problem to discover now
  rather than after installing.
- **Why this and not just `uv add google-genai`?** Because that would install *and* pin in one step,
  leaving you to read the version back out afterwards. Looking first means you write the number
  down deliberately. The lookup is the discipline; the install is just typing.

**Step 2 — pin it into the project.** This document observed **`google-genai` 2.19.0** on
**2026-08-24** (uploaded 2026-08-19, requires Python >= 3.10). Use what *your* lookup printed:

```bash
uv add google-genai==2.19.0
```

**Line by line:**

- `uv add` — adds the dependency to `pyproject.toml` **and** installs it **and** updates `uv.lock`,
  in one operation. Day 0 chose `uv` precisely so these three never drift apart. The older habit of
  `pip install` followed by hand-editing a requirements file is exactly how the story at the top of
  this page happens.
- `==2.19.0` — the double equals is an exact pin. `>=2.19.0` would float upward and re-open the
  problem; `~=2.19.0` would allow patch releases, which is a legitimate policy for some projects and
  not this one. Sutra pins exactly, because the plan says exact `==` pins and because a curriculum
  whose examples change under the reader is not a curriculum.
- **Nothing else is installed today.** Not `httpx`, not `python-dotenv`, not a retry library. The
  `.env` loading you need was written by hand in stdlib on Day 1
  ([3.3](../../../day-01-bootstrap-and-map/parts/03-keys-and-env/3.3-loading-keys-failing-loudly.md)),
  and the retry logic gets written by hand in [1.5](1.5-the-only-door-429.md). Adding a dependency
  to avoid writing ten lines is a habit this project does not want you to form.

**Step 3 — verify what actually landed.** The install is not the observation; the observation is.

```bash
uv pip show google-genai | head -3
uv run python -c "import google.genai as g; print('import ok')"
```

**Line by line:**

- `uv pip show <name>` — prints the metadata of what is **installed in this environment right now**,
  which can differ from what you asked for if a resolver had to compromise. Read the version it
  prints, not the one you typed. `head -3` trims to name, version and location.
- `uv run python -c "..."` — `uv run` executes inside the project's virtual environment. Running a
  bare `python` might use a different interpreter entirely, which is one of the classic ways to
  spend an evening confused about a package you definitely installed.
- `import google.genai` — note the import path is **`google.genai`**, while the package on PyPI is
  **`google-genai`**. They differ, which is common and catches people. There is also an older,
  unrelated package called `google-generativeai`; it is not this one, and tutorials using it are
  writing against a different SDK.
- **Why import at all?** Because a package can install cleanly and still fail to import — a missing
  system library, a Python version mismatch. Two seconds here saves a confusing failure inside your
  first real call.

**Step 4 — record it.** One row in `docs/PACKAGES.md`, appended, never edited. The exact row is in
the hub's §11, and the rule is that it contains **what your terminal printed**, not what this
document printed.

## When it breaks

**The pin that does not exist:**

```text
error: Distribution `google-genai==2.19.9` can't be installed because it doesn't have a
source distribution or wheel for the current platform

hint: You require google-genai==2.19.9 but only the following versions are available:
      2.18.0, 2.19.0
```

**What it means.** You typed a version that was never released — a transposed digit, or a number
someone remembered rather than looked up. **This is Principle 7 catching you, and it is the good
case**: the error is loud, immediate, and names the versions that do exist. Fix the digit and move
on. The bad case is the version that *does* exist but is not the one you meant.

**The floating install that already happened:**

```text
$ uv pip show google-genai | head -2
Name: google-genai
Version: 2.18.0
```

**What it means.** You ran `uv add google-genai` with no `==`, on a machine that already had an older
copy resolved in the lockfile, and got that instead of today's release. Nothing errored. Nothing
will error — until a call in [1.4](1.4-the-first-interaction.md) uses a field that only exists in the
newer version, and then you will debug your *code* for an hour. **The smallest fix:**
`uv add google-genai==2.19.0` explicitly, then `uv pip show` again to confirm the number changed.

**Python too old:**

```text
error: No solution found when resolving dependencies:
  Because google-genai==2.19.0 requires Python>=3.10 and the current Python
  version is 3.9.18, we can conclude that your requirements are unsatisfiable.
```

**What it means.** `requires_python` from step 1, met at install time instead of lookup time. This is
why step 1 prints that field: it converts a resolver error into something you knew before you typed.

## In production

**What a professional writes instead** is not a different command — it is the same command plus a
committed lockfile and a build that installs *from* the lockfile rather than resolving fresh. `uv
add` maintains `uv.lock`; the production behaviour is `uv sync --frozen` in the build, which refuses
to proceed if the lockfile and `pyproject.toml` disagree. **The pin says what you want; the lockfile
says what you got, all the way down to your dependencies' dependencies.** Only the second one is
reproducible, because your direct pins say nothing about the twenty transitive packages underneath.

**What degrades at scale is not the install — it is the upgrade.** One pinned dependency is trivial.
Two hundred pinned dependencies across fifteen services is a standing organisational cost, and the
failure mode is that nobody upgrades anything for a year because every upgrade is scary, and then a
security advisory forces a jump across eighteen months of breaking changes under time pressure.
**Pinning without a routine for moving the pins is how you get stuck**, which is why mature teams run
automated dependency updates continuously and why this plan puts a freshness check in every phase
gate rather than at the end.

**The failure that only appears with real traffic** belongs to the *unpinned transitive* dependency.
Your pins are exact, your lockfile is committed, and one of your dependencies specifies its own
requirement loosely. A patch release of that inner package ships a subtly different behaviour — a
changed default timeout, a stricter parser — and it reaches production through a rebuild that
touched none of your code. The symptom is a latency graph that steps up on a day with no deploy of
yours. **This is exactly what the lockfile prevents and what "just pin your direct dependencies"
does not.**

**The review comment a senior engineer leaves:** *"`uv add google-genai` with no version — what did
this actually install? I need the lockfile in this PR, not just the toml. And can you put the
observed version in PACKAGES.md with today's date? When this breaks in six months the first question
is going to be 'what changed', and right now this commit can't answer it."* The subtext is that
**a dependency change is a change to the program**, and it deserves the same review as a code change.

**The interview question.** *"What's the difference between a pin and a lockfile, and why do you need
both?"* The answer that shows experience: a pin is your **intent**, expressed in `pyproject.toml`,
and it covers only what you named. A lockfile is the **resolved reality** — every direct and
transitive package, with hashes — and it is what makes two machines identical. You need both because
pins alone leave the transitive graph floating, and lockfiles alone lose the human intent behind a
version choice. The follow-up that separates the practised from the theoretical is *"so what do you
put in CI?"* — and the answer is a frozen install that **fails** when the lockfile is stale, because
a build that silently re-resolves is a build that can differ from the one you tested.

## Check yourself

Run the whole procedure and confirm each step told you something:

```bash
curl -s https://pypi.org/pypi/google-genai/json \
  | python -c "import sys,json; d=json.load(sys.stdin); print(d['info']['version'])"
uv pip show google-genai | head -2
grep google-genai pyproject.toml
```

All three must agree on one number. If `pyproject.toml` says something different from
`uv pip show`, your environment and your declaration have drifted — resolve it now, while it is a
two-line fix.

**Answer out loud, without scrolling up:**

> Your teammate says "pinning is overkill, the lockfile already covers us." Give the one case the
> lockfile covers and the pin does not, and the one case the pin covers and the lockfile does not.
> Then say what `PACKAGES.md` records that *neither* of them does, and who reads it.
