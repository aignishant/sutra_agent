# 2.2 — Reading the receipt: what `interaction.usage` actually tells you

## One-line answer

Every response carries a **usage** object that is the true, measured account of what the call cost —
input, output, and a third number most people do not know exists — and reading it is the only way to
replace estimates with facts.

---

## The story

Two engineers are asked the same question about the same system: *"which of our features is the
expensive one?"*

The first reasons carefully. They know roughly how long the prompts are, roughly how many calls each
feature makes, roughly what the output length looks like. They produce a confident ranking, with
percentages. It takes an afternoon and it is entirely plausible.

The second runs a query. It takes four minutes, because their code has logged the usage numbers from
every response since the day it was written.

The rankings disagree — not at the margins, but at the top. The feature the first engineer ranked
third is the most expensive by a wide margin, because it uses a model setting that generates a large
amount of internal reasoning that nobody had accounted for. It never appeared in the estimate because
it does not appear in the output either. It is invisible unless you look at the receipt.

The first engineer's reasoning was not sloppy. Every individual assumption was defensible. But
estimates compound: five reasonable assumptions, each off by a modest amount in the same direction,
produce an answer that is off by a factor of three. **The second engineer did not out-think the
first. They just had the data, because six months earlier they wrote one extra line.**

---

## The idea in plain language

The response object from a call carries more than text. Its **usage** field is a receipt: a count of
the tokens the transaction actually consumed, measured by the provider, not estimated by you.

The fields on it, verified against the Gemini API documentation on 2026-08-24:

| Field | What it counts |
| --- | --- |
| `total_input_tokens` | Everything you sent — instructions, history, the new question |
| `total_output_tokens` | The tokens generated in reply |
| `total_thought_tokens` | Tokens the model spent **reasoning internally**, which you never see |
| `total_tokens` | The sum — what the transaction cost in total |

Three of those are intuitive. The third is the one from the story, and it deserves its own part —
[2.3](2.3-the-thinking-tax.md) is entirely about it. For now, the fact to absorb: **on a modern
thinking model, a substantial share of what you pay for produces no visible text.**

Two distinctions that trip people up:

**Estimated versus measured.** [2.1](2.1-what-a-token-is.md)'s `len(text) // 4` is a planning tool.
The usage object is the truth. When they disagree, the usage object is right and your estimate needs
revising — never the other way round.

**Input versus output are not equivalent.** They are counted separately because they cost the
provider differently: input is read in one pass, output is generated one token at a time, each
requiring a full pass through the network. Output is slower, and on paid tiers substantially more
expensive per token. **A prompt twice as long is a bit slower; an answer twice as long is twice as
slow.** This is why "be concise" is a latency instruction as much as a cost one.

## The mechanism

Add a demo to `sutra/mechanics.py` that makes one call and reads the whole receipt:

```python
def demo_tokens(client: genai.Client) -> None:
    """Estimate first, then measure — and compare the two.

    Usage:  uv run python -m sutra.mechanics tokens     (1 model call)
    """
    prompt = "Why is the sky blue? Answer in one sentence."

    print(f"estimate before the call : ~{len(prompt) // 4} input tokens")

    interaction = ask(client, prompt)
    usage = interaction.usage

    print(f"model said               : {interaction.output_text}")
    print(f"input tokens (measured)  : {usage.total_input_tokens}")
    print(f"output tokens (visible)  : {usage.total_output_tokens}")
    print(f"thought tokens (unseen)  : {usage.total_thought_tokens}")
    print(f"total tokens (the bill)  : {usage.total_tokens}")
```

**Line by line:**

- `prompt = "Why is the sky blue? Answer in one sentence."` — short and closed. **"Answer in one
  sentence" is doing budget work**: it bounds the output, which is the expensive half. Bounding
  output with the *prompt* is the right instrument;
  [5.1](../05-the-failure-lab/5.1-the-cap-that-ate-the-answer.md) shows what happens when you reach
  for a hard token cap instead.
- `print(f"estimate before the call : ~{len(prompt) // 4} ...")` — the estimate **first**, deliberately.
  Seeing your guess before the truth is what calibrates the guess. Do this a dozen times and you will
  be able to eyeball a prompt accurately, which is a genuinely useful skill.
- `interaction = ask(client, prompt)` — through the one door from
  [1.5](../01-first-contact/1.5-the-only-door-429.md), never `client.interactions.create` directly.
  Today's demos are the first callers of that rule.
- `usage = interaction.usage` — bind it once. The receipt is an object with several fields and you
  are about to read four of them.
- `usage.total_input_tokens` — the **measured** input count. Compare it to your estimate above. They
  will not match exactly; the interesting question is whether they are in the same neighbourhood.
- `usage.total_output_tokens` — the visible reply, counted.
- `usage.total_thought_tokens` — **the field almost nobody prints.** On a thinking model this is
  frequently *larger* than the visible output. If this number surprises you, that reaction is the
  entire point of [2.3](2.3-the-thinking-tax.md).
- `usage.total_tokens` — the total. **Check whether it equals input + output + thought on your own
  output** rather than assuming; that arithmetic is what tells you which meters are actually running.

Register it in the dispatcher from [1.4](../01-first-contact/1.4-the-first-interaction.md):

```python
demos = {"ask": demo_ask, "tokens": demo_tokens}
```

**Line by line:**

- One new key, one new value. Every part in this day adds exactly one entry here, which is why the
  dispatcher was built as a dict rather than a chain of `if` statements — **new behaviour is a new
  row, not a new branch.**

Run it:

```bash
uv run python -m sutra.mechanics tokens
```

**Line by line:**

- `tokens` selects `demo_tokens` from the dict. One model call, so one unit of your per-minute quota.
  If you have just run `ask`, you may hit a 429 and watch
  [1.5](../01-first-contact/1.5-the-only-door-429.md)'s wrapper wait it out — which is worth seeing.

## When it breaks

**The field that is `None` rather than a number:**

```text
input tokens (measured)  : 11
output tokens (visible)  : 24
thought tokens (unseen)  : None
total tokens (the bill)  : 35
```

**What it means.** Not every model reports every field. A non-thinking model has no thought tokens to
report, so the field is `None` rather than `0`. **The bug this causes** is arithmetic:
`usage.total_input_tokens + usage.total_thought_tokens` raises `TypeError: unsupported operand
type(s) for +: 'int' and 'NoneType'` the first time you run against a model that does not think.
**The smallest fix** is `(usage.total_thought_tokens or 0)` wherever you do arithmetic — and the
habit is to treat every field on a vendor's response object as optional until proven otherwise.

**The attribute that does not exist:**

```text
Traceback (most recent call last):
  File "sutra/mechanics.py", line 74, in demo_tokens
    print(usage.thoughts_token_count)
AttributeError: 'InteractionUsage' object has no attribute 'thoughts_token_count'
```

**What it means.** You used the field name from the **other** API surface. `thoughts_token_count`
belongs to `generate_content`'s `usage_metadata`; the Interactions API's usage object calls it
`total_thought_tokens`. This is a real and easy mistake, because tutorials for the older surface are
everywhere — see [6.1](../06-the-legacy-door/6.1-generate-content-parked.md), which exists precisely
so you can read those tutorials without being confused by them. **The fix when a field name fails is
to print the object itself** and read what is actually there:

```text
InteractionUsage(total_input_tokens=11, total_output_tokens=24,
                 total_thought_tokens=288, total_tokens=323)
```

That printout is more reliable than any documentation, including this page, because it came from the
version you actually have installed.

**The estimate that was badly wrong:**

```text
estimate before the call : ~11 input tokens
input tokens (measured)  : 27
```

**What it means.** Your prompt was 44 characters, so `// 4` said 11. The measured count is more than
double, because short prompts carry fixed overhead — the request has structure around your text, and
that structure is tokens too. **The rule of thumb is a rule about long prose**, and it is worst
exactly where you are most likely to test it: on a tiny example.

---

## In production

**What a professional writes instead of `print`** is one structured log line per call, carrying
model, input tokens, output tokens, thought tokens, latency, and a correlation id tying it to the
request that caused it. That is the extra line the second engineer in the story wrote six months
early. The reason it must be structured — key-value, not prose — is that its whole value is being
**aggregated later**: sum by tenant, percentile by endpoint, trend by prompt version. A human-readable
sentence in a log file cannot be summed.

**What degrades at scale is the assumption that the average is meaningful.** Token usage per request
is not normally distributed; it is heavily skewed. Most tickets are short, and a few are enormous
because a customer pasted a log file. If you provision on the mean, the tail breaks you — those few
requests hit the context window, blow the per-minute token quota, and take the longest. **Track
percentiles, not averages**, and design for p99 rather than p50, because p99 is where the failures
live and the mean is where nothing interesting happens.

**The failure that only appears with real traffic** is the *silent* cost regression. Someone improves
a prompt: they add three examples to the system instruction, quality goes up, everyone is pleased. The
input token count per call rises by 400. Nothing errors. No test fails — the tests check behaviour,
not cost. Six weeks later the daily quota starts running out mid-afternoon and nobody connects it to
a prompt change from six weeks ago. **A prompt change is a cost change**, and the only defence is
having the number graphed so the step is visible on the day it happens.

**The review comment a senior engineer leaves:** *"We're logging the response text but not the usage.
Add the token counts — all four fields — and put the prompt version in there too. When someone asks
in three months why our spend doubled, I want to answer that with a query and not with an
afternoon."* The general form is worth internalising: **instrument the thing you will be asked about,
before you are asked, because this data cannot be reconstructed retroactively.**

**The interview question.** *"How do you know what your LLM feature costs?"* An answer that only
describes reading a pricing page is describing arithmetic, not operations. The strong answer is that
every response carries a measured usage record, you log it on every call with enough dimensions to
slice it, and you alert on the *rate* rather than the total, because a total tells you after the money
is gone. The detail that shows real experience: pointing out that **on thinking models the visible
output is not the whole output** — reasoning tokens are billed and invisible — so an estimate built
from prompt length plus answer length can be off by a large factor in a direction that always favours
being surprised.
