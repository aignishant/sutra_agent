# 4.3 — Stability is not reproducibility: why temperature 0 is not a guarantee

## One-line answer

`temperature=0` removes the *deliberate* randomness and gives you output that is stable in practice —
but it is **not a contractual promise of identical bytes**, because floating-point arithmetic,
serving infrastructure and model updates can all shift the front-runner, which is why tests that
assert exact strings eventually fail for reasons nobody deployed.

---

## The story

A machine shop cuts a part to a tolerance of a hundredth of a millimetre. The customer, impressed,
asks whether every part is *identical*.

The foreman says no, and the distinction is the whole subject of this page. Every part is **within
tolerance** — that is the guarantee, it is written in the contract, and it is what the customer
actually needs. No two parts are identical. They differ in the fourth decimal place because steel
expands as the shop warms through the day, because tools wear microscopically, because the coolant
temperature drifts.

The customer, who has been comparing parts with a very good micrometer, has been finding differences
and treating each as a defect. They built an inspection process around exact equality, it flagged
things constantly, and they had begun to distrust a supplier who was meeting every specified
requirement.

**They tested for the wrong property.** Not a stricter version of the right one — a different one.
The contract promised tolerance and they measured identity, so their process generated an endless
supply of alarming, meaningless failures. When they switched to measuring what was actually promised,
the false alarms stopped and the process started catching real problems.

---

## The idea in plain language

At `temperature=0`, the sampler always takes the highest-probability token. There is no dice roll.
It is natural to conclude that the output must therefore be identical every time.

In practice it very nearly is. In principle, and occasionally in fact, it is not, for reasons that
have nothing to do with sampling.

**Floating-point arithmetic is not associative.** Adding the same numbers in a different order can
give minutely different results. Models run on hardware that parallelises aggressively, and the order
in which partial results are combined can vary between runs depending on how work was scheduled. When
two tokens are nearly tied — 0.4001 versus 0.4000 — a difference in the last bits can swap which one
is the front-runner. **One swapped token near the start conditions everything after it**
([4.1](4.1-the-probability-list.md)), so a microscopic numerical difference can produce a visibly
different sentence.

**Batching changes the arithmetic.** Your request is processed alongside others, and the composition
of that batch varies with load. Same input, differently-shaped batch, slightly different arithmetic.

**The model behind a name can change.** Providers update models, and a name like
`gemini-flash-latest` is explicitly a moving target
([1.3](../01-first-contact/1.3-listed-is-not-callable.md)). Even a pinned version may sit behind
serving changes.

So the honest formulation, and the one to carry:

> **Temperature 0 gives you stability, not reproducibility.** It is the right setting for
> classification and routing. It is not a guarantee that two runs produce identical bytes, and no
> provider offers one.

### Why this matters more than it sounds

Because it determines how you write tests. If you believe output is reproducible, the natural test is
`assert result == "billing"`. That test will pass in development, pass in CI, pass for weeks — then
fail on an unrelated deploy, and someone will spend a morning investigating a change that did nothing.

The correct assertion is about the **property** you actually need: that the category is one of the
five allowed values, that the output parses as JSON, that a required field is present. **The
classifier's contract is "returns a valid category", not "returns this exact string"** — and Phase
12's evals are built entirely on this distinction.

## Why Sutra needs it

- **Days 79–83 (AG-26..28, the evals phase)** exist because of this page. An eval scores behaviour
  across many cases rather than asserting exact strings, and a test suite built on string equality is
  the thing evals replace.
- **Day 12 (ADK-13, structured output)** wants valid JSON matching a schema. **"Valid and matching"
  is a property; "byte-identical" is not available.**
- **Day 31 (OPS-08)** is the quality gate. A gate built on brittle equality assertions fails
  randomly, and a check that fails randomly is one people learn to re-run rather than read — which
  makes it worse than no check at all.
- **Day 70's quota router** may send the same request to a different provider on a different day.
  Cross-provider identity is not even theoretically available; only properties are.
- **Principle 11 — evals are tests.** Every day ends with a check that can go RED. This part is what
  keeps those checks meaningful rather than flaky.

## The mechanism

Test the property, not the string. The contrast is the lesson:

```python
import json

VALID_CATEGORIES = {"billing", "bug", "account", "feature", "other"}


def check_classification(raw: str | None) -> dict:
    """Validate a classifier response by its contract, not by its bytes.

    Raises:
        ValueError: when the response violates the contract — never a silent default.
    """
    if raw is None:
        raise ValueError("no text in response — check the finish reason and usage")

    try:
        parsed = json.loads(raw)
    except json.JSONDecodeError as error:
        raise ValueError(f"not valid JSON: {error}") from error

    category = parsed.get("category")
    if category not in VALID_CATEGORIES:
        raise ValueError(f"category {category!r} not in {sorted(VALID_CATEGORIES)}")

    return parsed
```

**Line by line:**

- `VALID_CATEGORIES = {...}` — a **set**, at module level. Membership testing is what this is for, and
  writing the allowed values down explicitly is what turns "the model said something" into "the model
  said something we accept."
- `def check_classification(raw: str | None) -> dict:` — the parameter is typed `str | None` because
  `output_text` **can be `None` on a successful call**, as
  [1.4](../01-first-contact/1.4-the-first-interaction.md) and
  [2.3](../02-tokens-the-meter/2.3-the-thinking-tax.md) both established. Typing it honestly forces
  the caller to confront that.
- `raise ValueError("no text in response ...")` — **not** `return {}`. A silent default here would be
  Principle 10's fabricated result: downstream code would treat an empty classification as a real
  one. The message names what to look at next, which is what separates a useful error from an
  annoying one.
- `except json.JSONDecodeError as error: raise ValueError(...) from error` — catch the specific
  exception, not `Exception`. **`from error` preserves the original traceback**, so the person
  debugging can see the underlying parse failure rather than only your summary.
- `category not in VALID_CATEGORIES` — **the actual assertion.** Not equality against an expected
  answer: membership in the contract. This test passes whether the model says `billing` or `bug`, and
  fails when it invents `Billing Issues (Urgent)` — which is exactly the behaviour you want.
- `return parsed` — the validated dict. Everything downstream can now rely on the contract, because
  it was enforced here rather than assumed everywhere.

And the test that goes with it, which is the shape Sutra's evals will take:

```python
def test_classification_contract() -> None:
    """The contract holds; the exact wording is not asserted."""
    assert check_classification('{"category": "billing"}')["category"] == "billing"

    for bad in ('{"category": "Billing!"}', "not json at all", None):
        try:
            check_classification(bad)
        except ValueError:
            continue
        raise AssertionError(f"should have rejected: {bad!r}")
```

**Line by line:**

- The first assertion checks that a **valid** response survives, using a literal string that is test
  data rather than a model output — so this line is not asserting anything about the model.
- `for bad in (...)` — three violations, one per failure mode: wrong value, unparseable, absent. **A
  validator is only worth having if you have watched it reject things.**
- `except ValueError: continue` then `raise AssertionError(...)` — the inverted structure asserts
  that an exception **was** raised. Reaching the `raise` means the validator let something through,
  which is the bug this test exists to catch.
- **Nothing here asserts an exact model output**, which is the entire point. This test cannot become
  flaky because a provider re-batched your request.

## When it breaks

**The flaky test, arriving weeks after it was written:**

```text
FAILED tests/test_classifier.py::test_billing_ticket
E       AssertionError: assert 'billing' == 'Billing'
E         - Billing
E         + billing
```

**What it means.** Nothing was deployed. The model's front-runner shifted between two nearly-tied
tokens, or a serving-side change altered the arithmetic. **The instinct to resist is "add a
`.lower()` and move on"** — that patches this instance and leaves the underlying mistake, which is
that the test asserts identity where the contract promises validity. The next shift will be a
synonym, not a capitalisation, and `.lower()` will not save you.

**Temperature 0 drifting, which surprises people:**

```text
run on Monday : "The customer cannot log in after switching tabs."
run on Friday : "The customer is unable to log in when switching tabs."
```

**What it means.** Same prompt, same pinned model, `temperature=0`, different output. **Nothing is
broken.** This is the tolerance-versus-identity distinction from the story, live. If your system
depended on the Monday string, your system depended on something no provider promised.

**The eval that cannot be interpreted:**

```text
eval run 2026-08-20: 47/50 passed
eval run 2026-08-24: 44/50 passed
```

**What it means.** Three cases changed and **you cannot tell why** — a real regression, a model
update, or sampling noise are all consistent with this data. The missing ingredient is the recorded
configuration: model version, temperature, thinking level, prompt version. **An eval score without
its configuration is a number without units**, which is why Phase 12 records all of it.

---

## In production

**What a professional does is decide, per assertion, which property actually matters.** Very few
things genuinely require exact output. Most require: valid structure, a value from an allowed set, a
required field present, a cited source that exists, no leaked personal data. **Those properties are
stable under sampling noise and under model updates**, which means a suite built on them fails when
something is wrong rather than when something merely changed.

**What degrades at scale is trust in your own test suite.** A suite with a handful of
occasionally-flaky assertions trains everyone to re-run on red. Once that habit forms, the suite has
stopped being a signal — the real failure arrives, someone re-runs it, it fails again, and they
re-run it a third time before reading the message. **A flaky test is worse than a missing one**,
because a missing test does not teach people to ignore evidence.

**The failure that only appears with real traffic** is the model update nobody told you about. Your
pinned version is stable, your evals are green, and the provider adjusts something in serving — a
quantisation change, a new inference kernel, a different batching strategy. No version string changes.
Outputs shift slightly. **A property-based suite stays green because the contract still holds; an
equality-based suite lights up everywhere and tells you nothing about whether anything is actually
wrong.** This is the practical argument for the whole approach: it fails for reasons you care about.

**The review comment a senior engineer leaves:** *"This asserts the exact summary text. That'll pass
today and fail in three weeks when nothing has changed on our side. What do we actually require here
— that it's under 200 characters, mentions the product area, and doesn't contain the customer's
email? Assert those. And if we genuinely need byte-stability for a cache key, hash the input, not the
output."*

**The interview question.** *"How do you test something non-deterministic?"* The weak answer sets
temperature to 0 and calls it solved — which is the trap, because it treats stability as
reproducibility. The strong answer separates the two: temperature 0 removes deliberate randomness and
gives you stability in practice, but no provider guarantees identical bytes, since floating-point
non-associativity, batch composition and serving updates can all flip a near-tie. **So you assert
properties rather than strings** — valid schema, allowed value, required field, no leaked data — and
you score behaviour across a set of cases rather than one. The detail that shows real experience:
**pin and log the full configuration with every eval run** — model version, temperature, thinking
level, prompt version — because without it a score change has four possible causes and you cannot
distinguish a regression from a dice roll.

## Check yourself

```bash
uv run python -c "
import json
VALID = {'billing', 'bug', 'account', 'feature', 'other'}
def check(raw):
    p = json.loads(raw)
    assert p.get('category') in VALID, f\"bad category: {p.get('category')!r}\"
    return p
print(check('{\"category\": \"billing\"}'))
try:
    check('{\"category\": \"Billing Issues (Urgent)\"}')
except AssertionError as e:
    print('correctly rejected:', e)
"
```

The first passes, the second is rejected by its **contract** rather than by comparison to an expected
string. That difference is what makes a check survive a model update.
