# 2.4 — Handing the runner a store

## One-line answer

The session service is a constructor argument to the `Runner`, not a property of the agent, so
making a conversation durable is one line at one place — and `adk web` already made that choice for
you, which is why the CLI and your own code disagree about whether sessions survive.

## The story

You buy a second-hand scooter and the seller hands you two things: the keys, and a small booklet.

The booklet is the service history. Every oil change, every brake job, every time it went in for
something, with a date and a stamp. It is not part of the scooter. You could throw it away and the
scooter would start perfectly tomorrow morning.

The first time you take it to a mechanic he asks for the booklet, and what he does next depends
entirely on which booklet you hand him. Give him the real one and he reads three years of history
and knows the chain was replaced in March. Give him a fresh blank one from the shop and he does good
work on a machine he believes is new.

The scooter is the same scooter either way. What changed is which record it is being worked against.

## The idea in plain language

An agent — the instruction, the tools, the model — knows nothing about storage. It is handed a
conversation, it produces a turn, and it is done.

The thing that knows about storage is the **runner**. `Runner` is the object that drives one turn:
it loads the session, runs the agent, and appends every event the agent produces. It takes the
session service as a constructor argument:

```
Runner(agent=..., app_name=..., session_service=...)
```

That single argument is the whole of today's wiring. Swap `InMemorySessionService()` for
`SqliteSessionService(db_path=...)` and every conversation becomes durable, with no change to the
agent, the tools, the instruction or the prompts.

This is worth naming, because it is a design decision you are meant to copy. **Storage is a
deployment concern, expressed as an argument, not a capability the agent declares.** The same agent
runs against memory in a unit test, a file on a laptop and Postgres in production, and the agent
source is byte-identical in all three.

There is one more fact, and it is the one that confuses people most, so it goes here rather than in
a footnote. **`adk web` and `adk run` do not use the in-memory service by default.** In
`google-adk==2.7.1` they default to per-agent local storage: a SQLite file at
`<agent folder>/.adk/session.db`. So the CLI's conversations survive a restart, out of the box,
without a flag. A `Runner` you construct yourself does not, because you chose its service.

That mismatch is why so many people believe sessions are persistent by default and are then
surprised in their own code. Both halves are true. They are true about different programs.

## Why Sutra needs it

Because this is the day `sutra/memory/persistence.py` gets written, and this part is its
specification.

Day 46 creates `sutra/memory/` and owns `__init__.py` and `service.py`, which are about
[memory](../../../day-46-sessions-vs-memory/LESSON.md) — recall across conversations — rather than
about sessions. You are adding one module beside those, not creating the package. Day 48 adds
`policy.py`. Three files, three subjects, one package.

`persistence.py` exists so that every future caller — the desk, a test, a script, whatever Phase 8's
graph turns into — asks one function for a session service and never repeats the unexported import
from [2.1](2.1-the-class-that-is-not-exported.md) or the path rule from
[2.3](2.3-the-url-that-names-a-file.md). It is also the natural home for the one operation the
session API does not offer, which
[6.1](../06-forgetting-on-purpose/6.1-delete-the-session-keep-the-customer.md) will ask you to add.

## The mechanism

The wiring, as it appears in a runner:

```python
# the shape sutra/memory/persistence.py exists to make one line long
from google.adk.runners import Runner

from sutra.desk.agent import build_desk
from sutra.memory.persistence import session_service

runner = Runner(
    agent=build_desk(),
    app_name="sutra_desk",
    session_service=session_service(),
)
```

**Line by line:**

- `Runner` comes from `google.adk.runners`. Its `session_service` parameter is typed
  `BaseSessionService`, which is why any of the four services can be passed and why your own
  subclass could be.
- `app_name` is not decoration. It is the first component of the session primary key from
  [1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md), so changing this string orphans
  every session already in the store. It belongs in one constant, not typed at each call site.
- `build_desk()` is Day 27's agent factory, unchanged and unaware. That is the property to protect:
  if you ever find yourself passing the session service *into* an agent, something has gone wrong
  with the layering.
- `session_service()` is a function call rather than a module-level object, so nothing is
  constructed at import time. Day 43's
  [1.1](../../../day-43-stateless-by-default/parts/01-accidental-state/1.1-the-dictionary-nobody-called-state.md)
  is why: a service built at import time is a lifetime you did not choose, in a process you may fork.
- The `Runner` is built here, at the edge of the application, and not inside a tool or an agent. One
  place constructs, everything else receives.

What the module has to do, in the order it has to do it:

```python
# sutra/memory/persistence.py - the shape, not the answer. You type every line.
from pathlib import Path

from google.adk.sessions.base_session_service import BaseSessionService

# ADK 2.7.1: SqliteSessionService is NOT in google.adk.sessions.__all__ (checked 2026-09-05).
# See day 47 part 2.1. This import is the only one in the project; the tripwire is lab/reach.py.
from google.adk.sessions.sqlite_session_service import SqliteSessionService

ROOT = Path(__file__).resolve().parents[2]
SESSION_DB = ROOT / "data" / "sessions.sqlite3"


def session_service() -> BaseSessionService:
    """The desk's durable session store, at an absolute path, parent created."""
    SESSION_DB.parent.mkdir(parents=True, exist_ok=True)
    return SqliteSessionService(db_path=f"sqlite:///{SESSION_DB.as_posix()}")
```

**Line by line:**

- `Path(__file__).resolve().parents[2]` anchors the store to the repository rather than to the
  working directory: `persistence.py` → `memory` → `sutra` → the root. `resolve()` first, because
  `__file__` can be relative depending on how the process was started, and `parents` on a relative
  path counts from the wrong place.
- `parents[2]` is fragile in exactly one way, and it is worth knowing rather than avoiding: move the
  file one directory deeper and the index is wrong, silently. A test that asserts
  `SESSION_DB.parent.parent == ROOT` costs one line and catches it.
- `SESSION_DB` is a `Path` and is exported as one, so a caller can ask it questions —
  does it exist, how big is it, is it ignored by git — which is what
  [6.2](../06-forgetting-on-purpose/6.2-a-store-in-a-public-repo.md)'s check and the day's gate both
  do.
- `mkdir(parents=True, exist_ok=True)` before constructing, because
  [2.3](2.3-the-url-that-names-a-file.md) showed that a missing directory produces
  `unable to open database file` at the first write and not at start-up. Two keyword arguments:
  `parents` makes the whole chain, `exist_ok` makes a second call harmless.
- The return type is `BaseSessionService`, not `SqliteSessionService`. Callers should be unable to
  reach anything SQLite-specific, so that moving to Postgres later is a change inside this function.
- `f"sqlite:///{...as_posix()}"` builds the URL from an already-absolute path, so the three-slash
  relative form can never apply. `as_posix()` because a Windows backslash in a URL is not a
  separator.
- The comment naming the ADK version and the date is not politeness. It is the record §17.4.1 rule 1
  asks for, sitting where the next person will actually read it.

Verified against `https://adk.dev/sessions/session/` (fetched 2026-09-05) for the
`Runner(session_service=...)` shape, and against the installed
`.venv/Lib/site-packages/google/adk/cli/utils/service_factory.py` for the CLI default described
below. `https://adk.dev/docs/sessions/session/` 404s.

## When it breaks

The day's gate runs against the module before you have written it, and this is the whole of its
output today:

```text
- sutra.memory.persistence is not importable: ModuleNotFoundError: No module named 'sutra.memory'
findings: 1
exit: 1
```

That is the eval Principle 11 asks for: a check that is red now, for a reason you can read, and that
turns green when the work is done rather than when you say it is.

The second break is the one that wastes a day, and it is not an error at all. Here is the ADK's own
default, from `create_session_service_from_options`:

```text
# Default to per-agent local SQLite storage in <agents_root>/<agent>/.adk/.
try:
    return create_local_session_service(
        base_dir=base_path, per_agent=True, app_name_to_dir=app_name_to_dir,
    )
```

So `adk web sutra/desk` writes to `sutra/desk/.adk/session.db` and its conversations survive a
restart with no flag, no URL and no configuration. Meanwhile `uv run python -m sutra.desk.multi_turn`
uses whatever service you constructed, and on Day 8 that was `InMemorySessionService`.

Now picture the afternoon. Somebody tests persistence through the dev UI, sees the conversation come
back, and closes the ticket. The same build loses every conversation in production, where nothing
runs through `adk web`. Both observations were correct. They were observations of two different
programs, and the only way to tell is to know that the CLI makes this choice for you and your runner
does not.

There is a third thing hiding in the same code path, and it is worth having read once:

```text
if _is_cloud_run() or _is_kubernetes():
    warning_message = (
        "Detected Cloud Run/Kubernetes runtime; using in-memory services "
        "instead of local .adk storage. Set %s=1 to force local storage."
    )
```

The CLI detects a container platform and **switches back to in-memory**, at WARNING level. That is
the right decision — a container's local disk is not durable — and it means the very deployment
where you most need a store is the one where the convenient default quietly stops applying.

## In production

**What a professional writes instead:** the store is chosen from configuration in one module and the
choice is logged once at start-up, at INFO, naming the class and the resolved path. One line in the
log removes the entire class of confusion above: whoever is looking at the incident can see which
store this process is using rather than inferring it from the code that was deployed.

**What degrades at scale:** the service object is cheap, and the connection is not free. The SQLite
service opens a fresh `aiosqlite` connection per operation and closes it, so a busy process pays
file-open cost on every turn. That is fine at desk volumes and it is the first thing to measure when
turn latency starts mattering — and it is an argument for constructing the service once and reusing
it, rather than for constructing it per request.

**The failure mode that only appears with real traffic:** `app_name` drift. A deploy renames the app
from `sutra_desk` to `sutra-desk` because somebody normalised a constant, and every existing session
becomes unreachable — not deleted, unreachable, because the primary key changed. Session counts drop
to zero and disk usage does not, which is the fingerprint of exactly this bug.

**The review comment a senior engineer leaves:** *"the runner is constructed with
`InMemorySessionService()` inline and there is a comment saying `TODO: make this configurable`. That
comment is the bug. Take the service from `sutra/memory/persistence.py`, make the durable one the
default, and log the class and path at start-up — I do not want the next incident to begin with
somebody reading source to find out where the sessions were."*

**The interview question:** *"how much of your code changes when you move sessions from memory to a
database?"* The honest answer: *"One line, if you have kept the session service on the runner rather
than in the agent — it is a constructor argument typed as the base class, so the agent, the tools
and the prompts are untouched. The part people get wrong is believing they have already tested it:
`adk web` in ADK 2.7 defaults to per-agent SQLite under `.adk/`, so the dev UI survives restarts
whatever your own runner does. And on Cloud Run or Kubernetes the CLI detects the platform and goes
back to in-memory with a warning, because container disk is not durable. So the answer is one line
of code and one log line at start-up saying which store you actually got."*
