# 2.1 — The class that is not exported

## One-line answer

`SqliteSessionService` exists in `google-adk==2.7.1`, is what the ADK itself uses for local session
storage, and is absent from `google.adk.sessions.__all__` — so the import every reader tries first
raises, and the supported way in is a URI, not a class name.

## The story

There is a place near the office that does one thing better than anywhere else, and it is not on the
menu.

The menu has fourteen items, laminated, on every table. Ask for any of them and it arrives. But if
you ask for the fish the way the cook's mother made it — not on the menu, no price on the board —
you get it, and it is the best thing in the building. Half the regulars order it. The staff are not
surprised by the request.

It is still not on the menu, and that is not an oversight. The menu is a promise: this is what we
sell, at this price, every day you come. The fish depends on what the market had. Putting it on the
menu would commit the kitchen to something it cannot commit to.

So you can order it. You should know that on the day it stops, nobody will have broken a promise to
you.

## The idea in plain language

In Python, a module can declare which names it considers its public interface, in a list called
`__all__`. It is not a lock. Nothing stops you importing a name that is not in it — usually.

`google/adk/sessions/__init__.py` declares seven names: `BaseSessionService`, `Session`, `State`,
`StateSchemaError`, `InMemorySessionService`, `DatabaseSessionService` and `VertexAiSessionService`.

The package directory contains a file called `sqlite_session_service.py`, holding a fully
implemented `SqliteSessionService`. It is not one of the seven.

That is more than a documentation gap, because of *how* the package is written. Most of the seven
are imported lazily, through a `__getattr__` function that maps a name to the module it lives in.
`SqliteSessionService` is not in that map either. So the ordinary import genuinely fails, with an
`ImportError`, rather than merely being undocumented.

There are three routes to the class and they are not equal:

1. **From the package** — `from google.adk.sessions import SqliteSessionService`. Raises.
2. **From the module** — `from google.adk.sessions.sqlite_session_service import
   SqliteSessionService`. Works, and this is precisely what the ADK's own code does.
3. **By URI** — hand the string `sqlite:///path/to/file` to the CLI or to the service registry, and
   get a `SqliteSessionService` back without naming the class at all.

Route 3 is the one with the promise on it. `--session_service_uri` is a documented command-line
flag; `sqlite://` is one of the schemes it accepts; the registry that turns one into the other is
the ADK's own indirection. The class is the implementation behind the scheme, the way the fish is
the implementation behind "the usual".

## Why Sutra needs it

Because this day has to actually construct one, and Principle 8 says never invent an API.

Everything from [1.1](../01-what-restart-costs/1.1-the-book-under-the-shutter.md) onward imports
this class from its module, and a reader is owed the reason. Copying an import that the package's
own export list disowns, without knowing that is what you are doing, is how a project acquires a
dependency nobody can defend in review.

It also decides the shape of the module you write today. §4 of the hub asks for
`sutra/memory/persistence.py`, and the whole reason it is a module and not an import scattered
through the codebase is this: **one file names the unexported symbol, and the rest of Sutra names
that file.** When the symbol moves, one line changes.

And [2.2](2.2-the-driver-you-do-not-have.md) is about the class the export list *does* advertise,
which this repository cannot use. The pair is the lesson: what is exported and what is available are
two different questions.

## The mechanism

Try all three routes and print what each one does.

```python
# days/day-47-persistent-sessions/lab/reach.py  (extract)
def route_one_package_import() -> str:
    """The route a reader would try first, because it works for every sibling."""
    try:
        from google.adk.sessions import SqliteSessionService  # noqa: F401
    except ImportError as err:
        return f"ImportError: {err}"
    return "imported"


def route_three_uri() -> str:
    """The route the ADK treats as public: a URI scheme, resolved by a registry."""
    registry = get_service_registry()
    service = registry.create_session_service("sqlite:///./reach.sqlite3")
    return type(service).__name__ if service is not None else "None"
```

**Line by line:**

- The import sits **inside** the function, not at the top of the file. A failing import at module
  scope takes the whole script down before it can report anything, and the report is the point.
- `# noqa: F401` tells ruff that a name imported and never used is intentional here. Every other
  `noqa` in this repository needs a reason beside it, and this is the reason: the import *is* the
  experiment.
- `except ImportError` and not `except Exception`. A missing name raises `ImportError` and nothing
  else; catching more would hide a genuine bug in the ADK behind a tidy message.
- `get_service_registry()` returns the ADK's singleton registry of URI scheme to factory. This is
  the object `adk web` and `adk run` use to turn `--session_service_uri` into a service, so calling
  it directly is asking the CLI's own question without starting the CLI.
- `create_session_service` returns `None` for a scheme it does not know, rather than raising. That
  is quiet, and it is the trap in [2.2](2.2-the-driver-you-do-not-have.md).
- Constructing the service does **not** create the file. `SqliteSessionService.__init__` only checks
  whether an existing file has an old schema; the file and its tables appear on the first actual
  operation.

The mapping the registry is built from, in the ADK's own source:

```python
# .venv/Lib/site-packages/google/adk/cli/service_registry.py  (extract)
def sqlite_session_factory(uri: str, **kwargs: Any) -> BaseSessionService:
    from ..sessions.sqlite_session_service import SqliteSessionService

    parsed = urlparse(uri)
    db_path = parsed.path
    if not db_path:
        # Treat sqlite:// without a path as an in-memory session service.
        return memory_session_factory("memory://", **kwargs)
    elif db_path.startswith("/"):
        db_path = db_path[1:]
    return SqliteSessionService(db_path=db_path)


registry.register_session_service("sqlite", sqlite_session_factory)
for scheme in ["postgresql", "mysql"]:
    registry.register_session_service(scheme, database_session_factory)
```

**Line by line:**

- The ADK's own factory uses **route 2**, the module import, inside the function. That is the
  strongest evidence available that route 2 is how the class is meant to be reached: the framework
  reaches it that way itself.
- `sqlite:` is registered to `SqliteSessionService`. `postgresql:` and `mysql:` are registered to
  `DatabaseSessionService`. **SQLite no longer goes through the SQLAlchemy service at all**, which
  is a change from what a great deal of writing about ADK still says.
- `sqlite://` with an empty path silently becomes an *in-memory* service. A typo that drops the
  third slash therefore gives you a store that loses everything on restart, with no error — the
  exact failure [1.1](../01-what-restart-costs/1.1-the-book-under-the-shutter.md) is about, reached
  by a missing character.
- The `db_path.startswith("/")` strip is why `sqlite:///data/x.db` is a path relative to your working
  directory and `sqlite:////data/x.db` is absolute. [2.3](2.3-the-url-that-names-a-file.md) is that
  whole subject.
- The import is inside the function rather than at the top of the file so that a user of Postgres
  never pays for importing the SQLite service, and a user of SQLite never triggers the SQLAlchemy
  import that [2.2](2.2-the-driver-you-do-not-have.md) shows failing.

Verified against `https://adk.dev/sessions/session/`, fetched on 2026-09-05, and against the
installed source at `.venv/Lib/site-packages/google/adk/sessions/` and
`.venv/Lib/site-packages/google/adk/cli/service_registry.py` on the same day. The adk.dev page
names `InMemorySessionService`, `DatabaseSessionService` and `VertexAiSessionService` and **does not
mention `SqliteSessionService` at all**. `https://adk.dev/docs/sessions/session/` returns HTTP 404;
the path with no `/docs/` segment is the live one.

## When it breaks

All three routes, run on 2026-09-05:

```text
google.adk.sessions.__all__:
  BaseSessionService
  DatabaseSessionService
  InMemorySessionService
  Session
  State
  StateSchemaError
  VertexAiSessionService

SqliteSessionService in __all__: False
registered session URI schemes : ['agentengine', 'memory', 'mysql', 'postgresql', 'sqlite']

route 1  from google.adk.sessions import SqliteSessionService
         -> ImportError: cannot import name 'SqliteSessionService' from 'google.adk.sessions' (C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\.venv\Lib\site-packages\google\adk\sessions\__init__.py)

route 2  from google.adk.sessions.sqlite_session_service import SqliteSessionService
         -> imported SqliteSessionService

route 3  registry.create_session_service('sqlite:///./reach.sqlite3')
         -> SqliteSessionService

  [ok] route 1 still fails
  [ok] route 2 still works
  [ok] route 3 still yields SqliteSessionService

changed: 0
```

Route 1's message is worth reading in full, because it is the one you will meet:
`cannot import name 'SqliteSessionService' from 'google.adk.sessions'`, followed by the path of the
`__init__.py` it looked in. That path is the most useful part. It tells you which installation
answered, which matters when there are two Pythons on a machine, and it tells you exactly which file
to open to see the export list for yourself.

The genuinely dangerous failure is not this one. It is the upgrade. `uv sync` pulls a new ADK, the
module is renamed or the class is folded into something else, and route 2 stops working — at import
time, on start-up, in whatever environment ran `uv sync` first. There is no deprecation warning to
catch, because nothing was ever promised.

That is what the three `[ok]` lines are for. `reach.py` is not a demonstration; it is a **tripwire**.
It asserts the three facts this day was written against, and it goes red the day one of them stops
being true, at a moment of your choosing rather than at a moment of the deploy's.

## In production

**What a professional writes instead:** they isolate it. One module — for Sutra,
`sutra/memory/persistence.py` — contains the unexported import, with a comment saying it is
unexported, the ADK version it was checked against, and the date. Everything else imports from that
module. Then they add the tripwire to the test suite, so an upgrade fails in continuous integration
rather than in a container. The pattern has a name in review: *depend on a stable interface, and if
you must depend on an unstable one, depend on it exactly once.*

**What degrades at scale:** nothing about this is a runtime cost. It is an **upgrade** cost, and it
compounds. One unexported import is a note in a file. Fifteen of them, added by different people
over a year, is a team that cannot take a minor version bump without a week of work, which is how
projects end up pinned to an old version of the thing they most need patches for.

**The failure mode that only appears with real traffic:** the URI route hides a variant of it. A
service configured as `sqlite://` with the third slash missing starts cleanly, serves cleanly, and
is an in-memory store. Every conversation works. Every restart is a silent amnesia event, and it
looks like customers abandoning their tickets rather than like a configuration bug.

**The review comment a senior engineer leaves:** *"this imports `SqliteSessionService` from
`google.adk.sessions.sqlite_session_service`, which is not in that package's `__all__`. I am fine
with using it — it is what the ADK's own CLI uses — but it needs to be in one module with the
version we checked it against, and a test that fails on upgrade. Right now it is imported in four
files and none of them mention that it is unsupported."*

**The interview question:** *"what do you do when the symbol you need exists but is not exported?"*
The honest answer: *"First find out whether there is a supported way to reach the same object. Here
there was: the class is not in `__all__`, but the ADK registers `sqlite://` as a session-service URI
scheme and its own factory imports the class from the module, so the URI is the supported surface
and the class is the implementation behind it. When I do import the unexported name directly I put
it in exactly one module, with the version and date I verified it against, and I write a test that
asserts the import still works so an upgrade fails in CI rather than on a box. What I do not do is
copy the import into five files and hope."*
