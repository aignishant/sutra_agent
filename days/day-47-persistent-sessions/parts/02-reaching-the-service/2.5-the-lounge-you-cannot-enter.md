# 2.5 — 🅿️ The lounge you cannot enter

## One-line answer

`VertexAiSessionService` stores sessions in a managed Google Cloud service and is **parked** for
this curriculum, because it needs a billing account — but you should be able to say precisely what
it does, what it gives you that a file does not, and what it takes away.

## The story

Your flight is delayed and you walk past the lounge for the fourth time.

The door is right there. There is a printed list beside it saying who may go in, and the list is
short: business class, or a card of a kind you do not have. Nobody is hiding it. You can see the
seats, the counter, the people who are not standing in the corridor.

You are not confused about what a lounge is. You know exactly what is on the other side of that
door, and you can describe it to somebody, and the description is worth having, because next year
you might travel on a ticket that opens it. What you cannot do today is walk in.

The useful thing is knowing what you are outside of, and what it would cost to be inside.

## The idea in plain language

`VertexAiSessionService` is the third session service in `google.adk.sessions.__all__`, and unlike
the other two it is not a store you run. It is a **client for a managed service**: your sessions live
in Google Cloud's Agent Engine, and your process talks to it over the network.

The signature, read off the installed class:

```
VertexAiSessionService(project=None, location=None, agent_engine_id=None, *, express_mode_api_key=None)
```

`project` is a Google Cloud project. `location` is a region. `agent_engine_id` names a deployed
Agent Engine instance — a resource you create in that project. There is no path, because there is no
file.

What it gives you, honestly, and each of these is real:

- **No storage to operate.** No file to back up, no disk to size, no `VACUUM`, no migration script.
- **Many instances, no shared filesystem.** Every instance talks to the same managed store over
  HTTPS, which is the problem [Day 43](../../../day-43-stateless-by-default/LESSON.md) spent a whole
  day on, solved by somebody else.
- **Sessions that are a first-class cloud resource** — listed, inspected and governed by the same
  console and permissions as everything else in that project, which is what an audit asks for.

What it takes away:

- **A billing account.** Agent Engine is a paid product. There is no free tier that this
  curriculum's Addendum 02 can build on.
- **The ability to open the store.** [1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md)
  opened four tables with `sqlite3` and read them. You cannot do that here. Debugging goes through an
  API and a console.
- **Local development that matches production.** Your laptop is either talking to a real cloud
  project — with real latency and real cost per test run — or to a different service entirely, in
  which case you are not testing what you ship.
- **Latency you do not control.** Every `get_session` and every `append_event` becomes a network
  call, which is Day 44's subject: they can be slow, and
  [the tail is what hurts](../../../day-44-client-hardening/papers/01-the-tail-at-scale.md).

🅿️ **Parked** in this curriculum means exactly this: you can describe it, you can defend the choice
not to use it, and there is no build step. It is not "not important". It is "not buildable at zero
budget", which is a different sentence.

## Why Sutra needs it

Because "why not the managed one?" is asked in every design review, and *"it costs money"* is only
half an answer.

The full answer is a comparison, and Sutra is in an unusually good position to make it. By the end
of this day the repository has a durable store, a measured concurrency limit
([3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md)), a measured load cost
([5.3](../05-shape-and-size/5.3-the-session-that-never-ended.md)) and a deletion story
([6.1](../06-forgetting-on-purpose/6.1-delete-the-session-keep-the-customer.md)). Those four numbers
are what tells you whether the managed service would be buying you something. Without them, "we
should use the managed one" and "we should not" are both opinions.

It also matters for what this repository *is*. Everything in Sutra runs for anybody who clones it,
with a free API key and no card. A required step that needs a billing account would quietly exclude
most readers, and Principle 15 makes that a design constraint rather than a compromise.

## The mechanism

The mechanism you can run is the one that shows you the door. This is the whole of it:

```python
# the probe, and the only VertexAI code in this day
import asyncio
import inspect

from google.adk.sessions import VertexAiSessionService

print(inspect.signature(VertexAiSessionService.__init__))
try:
    service = VertexAiSessionService()
    asyncio.run(service.create_session(app_name="sutra_desk", user_id="asha"))
except Exception as err:  # noqa: BLE001 - the probe wants whatever comes back
    print(f"{type(err).__name__} : {err}")
```

**Line by line:**

- The import at module scope **succeeds**. Nothing about the class is gated behind an extra at
  import time, which is different from
  [2.2](2.2-the-driver-you-do-not-have.md)'s `DatabaseSessionService` and worth noticing: the
  package's lazy loader maps this name to its module and imports it happily.
- `inspect.signature(...)` reads the real parameter list off the installed class. This is how you
  check an API you cannot call — the object is here, so ask it rather than a search engine.
- Every parameter defaults to `None`, so `VertexAiSessionService()` constructs with nothing. That is
  not permission; it means the class intends to fall back to environment variables and application
  default credentials, the way most Google Cloud clients do.
- The first real call is what fails, not the constructor. That pattern is worth carrying: for
  network-backed services, construction proves nothing and the first operation is the test.
- `except Exception` with a `noqa` and a reason, because the point of a probe is to report whatever
  arrives rather than to have guessed its type in advance. This is the one shape where the
  everything-catch is honest, and it prints the type name so nothing is hidden.

The wiring, if you ever did have a project, is the same one line as
[2.4](2.4-handing-the-runner-a-store.md):

```python
# not run in this repository - it needs a billing account (Addendum 02)
runner = Runner(
    agent=build_desk(),
    app_name="sutra_desk",
    session_service=VertexAiSessionService(project=PROJECT, location=LOCATION),
)
```

**Line by line:**

- The `Runner` line is byte-identical apart from the service. That is
  [2.4](2.4-handing-the-runner-a-store.md)'s claim about layering, tested against the most different
  implementation there is: one is a file, one is a cloud API, and the runner cannot tell.
- `project` and `location` come from configuration, never from a literal, and they are not secrets —
  the credential is separate, and under Principle 9 it never enters git.
- There is no `db_path` and no URL, so none of
  [2.3](2.3-the-url-that-names-a-file.md) applies. There is also nothing to `mkdir`, nothing to
  `.gitignore`, and nothing to back up.
- `agent_engine_id` is omitted here, and in a real deployment it is the resource this service reads
  and writes through. Getting it wrong points your sessions at somebody else's Agent Engine in the
  same project, which is a permissions question and not a code question.

Read from the installed class at
`.venv/Lib/site-packages/google/adk/sessions/vertex_ai_session_service.py` and verified against
`https://adk.dev/sessions/session/`, fetched 2026-09-05, which gives
`VertexAiSessionService(project=PROJECT_ID, location=LOCATION)` and names the `gcp` extra.

## When it breaks

Run the probe on this repository, on 2026-09-05:

```text
(self, project: 'Optional[str]' = None, location: 'Optional[str]' = None, agent_engine_id: 'Optional[str]' = None, *, express_mode_api_key: 'Optional[str]' = None)
ImportError : The 'google-cloud-aiplatform' package is required to use this feature. Please install it by running: pip install google-adk[gcp]
```

The same helper as [2.2](2.2-the-driver-you-do-not-have.md), a different extra: `gcp` instead of
`db`. And notice **when** it arrived — not on the import, not on the constructor, but on the first
`create_session`. The class imported, the object was built, and everything looked healthy right up
to the first customer.

That is the failure shape to remember for anything network-backed, and it is worse in the case this
message is hiding. Install the extra and the ImportError goes away; what you meet next is
authentication, and its errors are `403 PERMISSION_DENIED` and
`DefaultCredentialsError: Could not automatically determine credentials`, which arrive at the same
place — the first real call, in whatever environment first ran it, which is usually the deploy.

There is a second, quieter break, and it is the one that actually costs money. `location` is a
region. Sessions stored in the wrong one are not an error: they are conversations sitting in a
jurisdiction your data-protection policy did not agree to, working perfectly, for as long as nobody
checks. A file on a disk has exactly one location and you know where it is.

## In production

**What a professional writes instead:** they choose the store from the deployment's shape, not from
the framework's list. One instance and a mounted volume is a file. Several instances and no shared
disk is either a managed store or a database everyone can reach. The decision is written down with
the numbers behind it, so that the next person can re-open it when the numbers change rather than
re-litigating it from taste.

**What degrades at scale:** the direction of the problem reverses. The file store's limit is
concurrent writers on one machine; the managed store has no such limit and instead has a request
budget, a rate limit and a bill that scales with turns. A chatty agent that writes six events per
customer message is fine against a local file and is a line item against a managed service.

**The failure mode that only appears with real traffic:** the store becomes a network dependency,
which means it can be slow rather than only present or absent. Every one of
[Day 44](../../../day-44-client-hardening/LESSON.md)'s lessons now applies to *loading a
conversation*: deadlines, retries that must be safe to repeat, and a policy for what the desk says
when the store does not answer. A local file cannot time out. A remote store can, and it will do it
first at the busiest moment.

**The review comment a senior engineer leaves:** *"before we adopt the managed session service, put
the numbers in the design doc: our write rate per instance, the p99 of a `get_session` today, and
what we currently spend operating the file. Right now this says 'managed is more scalable', which is
true and is not a reason. We are one instance with a volume; the thing that would actually force
this is running several, and we are not."*

**The interview question:** *"when would you use a managed session store instead of your own?"* The
honest answer: *"When I have more than one instance and no shared disk between them, or when
operating the store is genuinely more expensive than paying for it — and I would want the numbers,
not the adjective. What I would be giving up is worth saying out loud: I can no longer open the
store and read it, so debugging goes through an API; every session load becomes a network call with
a tail latency I do not control; and my laptop is either talking to a real paid project or to a
different implementation than the one I ship. In this project I stayed on a local file because it is
one instance, and because everything here has to run for someone with no billing account at all."*
