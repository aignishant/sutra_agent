# 2.2 — The driver you do not have

## One-line answer

`DatabaseSessionService` is exported, documented and unusable in this repository, because it needs
SQLAlchemy and SQLAlchemy is an optional extra that `google-adk==2.7.1` does not pull in — which is
why this day installs nothing and uses the SQLite service instead.

## The story

The washing machine arrives on a Saturday morning and it is exactly the one in the photograph.

Two men bring it up the stairs, level it, and leave. You unpack it, push it into the gap under the
counter, and reach round the back for the hose that connects it to the tap.

There is no hose.

The box has a manual, a bag of bolts, and a drain pipe. The inlet hose is a separate item, listed in
the manual under *accessories*, sold by the same shop, two hundred rupees, and not in this box. The
machine is complete and correct and it cannot wash anything today.

The shop is not being dishonest. Different flats have different taps; shipping one hose with every
machine would be the wrong hose for half of them. But nobody said so at the counter, and the
difference between owning a washing machine and having clean clothes turned out to be a part you did
not know you needed.

## The idea in plain language

A Python package can declare **optional dependencies**, grouped under names called **extras**. You
ask for them with brackets: `pip install google-adk[db]` installs `google-adk` plus everything in
its `db` group.

`google-adk==2.7.1` puts SQLAlchemy in the `db` extra. Sutra's `pyproject.toml` asks for plain
`google-adk==2.7.1`, so SQLAlchemy is not installed and never has been.

`DatabaseSessionService` is built on SQLAlchemy. It is the general relational service: give it any
SQLAlchemy URL — Postgres, MySQL, MariaDB — and it stores sessions there. It is in
`google.adk.sessions.__all__`, and it is what adk.dev's session page tells you to use for SQLite.

So the package advertises a class that this installation cannot construct. It is honest about it:
the package's `__getattr__` catches the failed import and re-raises with an instruction.

```text
ImportError: The 'sqlalchemy' package is required to use this feature. Please install it by running: pip install google-adk[db]
```

Notice what that is not. It is not `ModuleNotFoundError: No module named 'sqlalchemy'`, which is
what you would get if the ADK simply imported SQLAlchemy at the top of the file and let the error
escape. Somebody wrote a helper whose only job is to turn a missing import into a sentence naming
the extra. That is a small, deliberate kindness and it is worth stealing.

The second half of this part is the more interesting half. **Not installing it is the right answer
here**, and not merely the cheap one. Addendum 02 forbids anything that needs a billing account, and
the general service's reason to exist is a database server — Postgres or MySQL — which is a managed
service you pay for or a server you operate. For a local file, `SqliteSessionService` is the ADK's
own answer, has no dependency beyond `aiosqlite` which is already installed, and is what the ADK's
CLI now uses for `sqlite://`.

## Why Sutra needs it

Because the day would otherwise install a package for nothing, and Principle 7 says every pin gets a
dated row and a reason.

Sutra's whole deployment story is a file on a disk. [Day 43](../../../day-43-stateless-by-default/LESSON.md)
built a server with no state of its own; today gives it a durable store; and the store is SQLite
because SQLite is a library, not a service. There is no host to provision, no password to keep out
of git, and no monthly bill. `git diff pyproject.toml uv.lock` must be empty when this day is
finished.

It also settles what happens later. When Sutra outgrows one file — several instances writing hard
enough that [3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md)'s contention starts to
bite — the move is Postgres, and *then* `DatabaseSessionService` is the right class, and *then*
`uv add "google-adk[db]"` earns its row in `docs/PACKAGES.md`. Knowing which future needs it is more
useful than installing it now in case.

## The mechanism

Three read-only probes. None of them installs anything.

```python
# days/day-47-persistent-sessions/lab/driver.py  (extract)
def sqlalchemy_present() -> bool:
    """True when the optional dependency is installed, without importing it."""
    return importlib.util.find_spec("sqlalchemy") is not None


def database_session_service() -> str:
    """Ask for the class the docs point at and report exactly what comes back."""
    try:
        from google.adk.sessions import DatabaseSessionService  # noqa: F401
    except ImportError as err:
        return f"ImportError: {err}"
    return "imported"


def registry_for(uri: str) -> str:
    """What the CLI's registry resolves a URI to, before any fallback runs."""
    service = get_service_registry().create_session_service(uri)
    return type(service).__name__ if service is not None else "None (no factory for this scheme)"
```

**Line by line:**

- `importlib.util.find_spec` asks the import system whether a module *could* be imported without
  actually importing it. That distinction matters for a probe: importing SQLAlchemy would run its
  package initialisation, which is slow and has side effects, and all you wanted was yes or no.
- `find_spec` returns `None` for an absent module and a spec object for a present one, so the
  comparison is `is not None` rather than a bare truth test.
- The `DatabaseSessionService` import is inside a function for the same reason as
  [2.1](2.1-the-class-that-is-not-exported.md)'s: a failing import at module scope ends the script
  before it can report.
- `except ImportError` catches this correctly even though the underlying cause is a
  `ModuleNotFoundError`, because `ModuleNotFoundError` is a subclass of `ImportError`. The ADK
  re-raises as a plain `ImportError` with `from e`, so the original is still on the chain and
  visible in a traceback.
- `registry_for` returns a **string** rather than the service, so that the `None` case has a
  readable name in the report instead of printing the word `None` and leaving the reader to guess
  whether that was the answer or a bug in the script.

The helper that produces the message, in the ADK's own source:

```python
# .venv/Lib/site-packages/google/adk/utils/_dependency.py
def missing_extra(package: str, extra: str) -> ImportError:
    """Returns an ImportError with a standard message for a missing extra."""
    return ImportError(
        f"The '{package}' package is required to use this feature. "
        f"Please install it by running: pip install google-adk[{extra}]"
    )
```

**Line by line:**

- It **returns** the exception rather than raising it, so the caller writes
  `raise missing_extra('sqlalchemy', 'db') from e` and keeps the original cause attached. A helper
  that raises would put its own frame at the top of every traceback.
- Two arguments, and they are different things: `package` is what is missing, `extra` is what to
  install. Those are often not the same word — here `sqlalchemy` and `db` — and conflating them is
  how error messages end up telling people to `pip install sqlalchemy`, which works and leaves the
  version unpinned by anything.
- The message contains the exact command. That is the whole value of the helper. Compare it with
  the bare `ModuleNotFoundError: No module named 'sqlalchemy'` a reader would otherwise get, which
  is true, useless, and sends them to a search engine.
- Sutra should copy this shape wherever an optional path exists: catch the import error at the
  boundary and re-raise with the command.

Verified against `https://adk.dev/sessions/session/`, fetched 2026-09-05. That page gives
`DatabaseSessionService(db_url="sqlite+aiosqlite:///./my_agent_data.db")` and names
`pip install google-adk[db]`. The installed 2.7.1 registry does **not** route `sqlite` to that class
— see the output below, and [2.1](2.1-the-class-that-is-not-exported.md)'s extract of the registry.

## When it breaks

Run on 2026-09-05, against `google-adk==2.7.1` with no extras:

```text
sqlalchemy installed                  : False
aiosqlite installed                   : True

from google.adk.sessions import DatabaseSessionService
  -> ImportError: The 'sqlalchemy' package is required to use this feature. Please install it by running: pip install google-adk[db]

registry.create_session_service('sqlite+aiosqlite:///./data/sessions.db')
  -> None (no factory for this scheme)

registry.create_session_service('sqlite:///./data/sessions.sqlite3')
  -> SqliteSessionService

  [ok] sqlalchemy is still absent
  [ok] DatabaseSessionService still raises ImportError
  [ok] the documented sqlite+aiosqlite URL has no registered factory
  [ok] plain sqlite:// resolves to SqliteSessionService
```

The third line is the one that costs an evening.

`sqlite+aiosqlite:///./data/sessions.db` is the URL adk.dev prints. Pass it to the registry and you
get `None` — there is no factory registered for the scheme `sqlite+aiosqlite`. What happens next is
worse than an error. The ADK's own `create_session_service_from_options` treats a `None` from the
registry as *"this must be some SQLAlchemy database we do not know about"* and falls through to
`DatabaseSessionService(db_url=...)`, which on this installation immediately raises the ImportError
above. So the documented URL, on a documented flag, produces an error about a package the
documentation never told you the URL required — and the plain `sqlite://` form the documentation
does not mention is the one that works.

`aiosqlite` being present while SQLAlchemy is absent is the tell. `SqliteSessionService` talks to
the file through `aiosqlite`, which `google-adk` depends on unconditionally. The async driver is
already here. What is missing is the layer above it.

## In production

**What a professional writes instead:** a comment beside the constructor naming the class **not**
used and why. One line — *"SqliteSessionService, not DatabaseSessionService: SQLAlchemy is in the
`db` extra and we do not need a server"* — turns a future reviewer's *"why not the documented one?"*
into a decision they can agree or disagree with. They also pin the moment: the ADK version and the
date the extras were checked, because extras move between minor versions.

**What degrades at scale:** the SQLite service is one process's library talking to one file, and
that stops being enough at a rate you can measure —
[3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md) is where the measuring happens. The
migration path is the point: `DatabaseSessionService` against Postgres is the same
`BaseSessionService` interface, so the change is `uv add "google-adk[db]"`, a URL from an environment
variable, and a data migration. The interface is what makes the change small; the extra is what
makes it a deliberate step.

**The failure mode that only appears with real traffic:** an optional extra that is present on one
machine and absent on another. A developer runs `uv add "google-adk[db]"` locally to try something,
never commits it, and the code path that needs it is exercised once a week by a scheduled job. It
passes locally forever and fails in production the first time that job runs. Optional dependencies
belong in `pyproject.toml` and the lockfile or nowhere.

**The review comment a senior engineer leaves:** *"the connection string here is
`sqlite+aiosqlite://`, copied from the docs. On our ADK version that scheme has no registered
factory, so it falls through to `DatabaseSessionService` and needs the `db` extra we do not install.
Either add the extra deliberately, with a row in `PACKAGES.md` and a reason, or use `sqlite://`,
which the registry resolves to the SQLite service with no new dependency. Right now this is broken
in a way that only fails on start-up."*

**The interview question:** *"the documentation says to use class X and it will not import. What
now?"* The honest answer: *"Read the error rather than the docs. Ours said the `sqlalchemy` package
is required and named the extra, `google-adk[db]`, which told me it was an optional dependency
rather than a broken install. Then I asked whether I needed it: that class exists to speak to a
database server, and we store sessions in a local file. The ADK's own URI registry maps `sqlite://`
to a SQLite-specific service that only needs `aiosqlite`, which is already a dependency. So the
answer was to install nothing and use the other class — and to write down the version and date I
checked, because the extra could become a core dependency next release and that would change the
decision."*
