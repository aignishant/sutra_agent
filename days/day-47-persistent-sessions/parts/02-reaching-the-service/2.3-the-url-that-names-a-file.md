# 2.3 — The URL that names a file

## One-line answer

`db_path` accepts a plain path or a `sqlite:` URL, and one slash decides whether the rest is
relative to the process's working directory or absolute — so the same string can name two different
files and neither of them raises.

## The story

You give a driver directions to your flat: *third lane after the school, blue gate, first floor.*

He finds it. He has been to that school before, so "third lane after the school" starts from
somewhere he already is. The directions were never the address; they were the address **plus where
he was standing**.

A month later you give the same words to a driver who has never been to that part of town, and he
starts from a different school with a similar name, counts three lanes, and rings the bell of a blue
gate that is not yours. He followed your directions exactly. He was in a different place when he
started.

The written address on your electricity bill does not have this problem. It works from anywhere,
because it does not begin from where anybody is standing.

## The idea in plain language

`SqliteSessionService(db_path=...)` takes one string, and that string may be four different things:

| What you type | What it means |
| --- | --- |
| `data/sessions.sqlite3` | a plain path, relative to the working directory |
| `C:/sutra/data/sessions.sqlite3` | a plain path, absolute |
| `sqlite:///data/sessions.sqlite3` | a URL, **relative** — three slashes |
| `sqlite:////data/sessions.sqlite3` | a URL, **absolute** — four slashes |

The three-versus-four slash rule is inherited from SQLAlchemy, and it is the single most confusing
piece of syntax in this whole area, so it is worth pulling apart rather than memorising.

A URL is `scheme://host/path`. After `sqlite:` come two slashes for the empty host, because a file
has no host. Then a third slash begins the path. So `sqlite:///data/x.db` has path `/data/x.db`,
and the convention is that the leading slash is stripped and the rest is relative to your working
directory. Four slashes leaves one slash after stripping, and that one is a genuine absolute path.

The **relative** part is the dangerous half, and not because relative paths are bad. It is because
"relative to what" is a property of the process, not of the string. The same configuration value
opens a different file depending on the directory the process was started in. Run it from the repo
root and you get `<repo>/data/sessions.sqlite3`. Run the same code from `days/day-47.../lab` and you
get a brand-new, empty `<lab>/data/sessions.sqlite3` — and the store appears to have forgotten
everything.

Nothing raises. SQLite creates a missing file, and the session service creates missing tables.
**A wrong path is not an error; it is a second, empty database.**

## Why Sutra needs it

Because the store's location is a configuration value that Sutra will read from more than one
place, and every one of them starts in a different directory.

`uv run python -m sutra.desk.multi_turn` starts at the repository root.
`uv run adk web sutra/desk` also starts at the root but writes its own default store under the agent
folder. A test started by pytest inherits pytest's working directory. A container's working
directory is whatever the image says. Five callers, five ideas of where `data/` is, one string in
`sutra/memory/persistence.py`.

The rule this day adopts, and the one
[2.4](2.4-handing-the-runner-a-store.md) writes into the module, is: **resolve the path against the
repository root, once, and hand an absolute string to the service.** It costs three lines and
removes the entire category.

It also matters for
[6.2](../06-forgetting-on-purpose/6.2-a-store-in-a-public-repo.md). `.gitignore` already carries
`*.db` and `*.sqlite3`, so a store anywhere in the tree is ignored — but a path that escapes the
tree entirely, which four slashes will happily do, is outside anything `.gitignore` can protect and
outside any backup that covers the project.

## The mechanism

Resolve each form with the service's own parser rather than guessing.

```python
# days/day-47-persistent-sessions/lab/urls.py  (extract)
from google.adk.sessions.sqlite_session_service import _parse_db_path

for form in FORMS:
    fs_path, connect_arg, use_uri = _parse_db_path(form)
    try:
        resolved = str(Path(fs_path).resolve())
    except OSError:  # a URI form with a query string is not a plain path
        resolved = fs_path
    print(f"{form:<45} {str(use_uri):<6} {resolved}")
```

**Line by line:**

- `_parse_db_path` has a leading underscore, which in Python means *not part of the interface*. It is
  used here **only to inspect**, never in Sutra's own code, and that distinction is the whole
  difference between a lab and a dependency. The lab wants the service's real answer; the project
  wants an absolute path it computed itself.
- The parser returns three values: the filesystem path (for existence checks and error messages),
  the argument actually handed to the driver, and whether that argument is a URI. They differ only
  for the query-string form on the last row.
- `Path(...).resolve()` turns a relative path into an absolute one **against the current working
  directory**, which is exactly the resolution the service will do later. Printing it is how the
  invisible dependency on the working directory becomes visible.
- `except OSError` is there because `resolve()` on a string containing `?mode=ro` is not a valid
  path on Windows. Catching `OSError` rather than `Exception` keeps a genuine bug visible.
- The loop prints the input beside the output on one line, because the value of this script is the
  comparison. A list of resolved paths with no inputs beside them would prove nothing.

The rule inside the parser, from the ADK's own source:

```python
# .venv/Lib/site-packages/google/adk/sessions/sqlite_session_service.py  (extract)
normalized_path = raw_path
if normalized_path.startswith("//"):
    normalized_path = normalized_path[1:]
elif normalized_path.startswith("/"):
    normalized_path = normalized_path[1:]

if parsed.query:
    # sqlite3 only treats the filename as a URI when it starts with `file:`.
    return normalized_path, f"file:{normalized_path}?{parsed.query}", True
```

**Line by line:**

- `urlparse("sqlite:///data/x.db").path` is `/data/x.db` — one leading slash, which the `elif`
  strips, leaving the relative `data/x.db`.
- `urlparse("sqlite:////data/x.db").path` is `//data/x.db` — two leading slashes, and the first
  branch strips **one**, leaving `/data/x.db`, still absolute. That is the entire three-versus-four
  rule, in four lines.
- The two branches strip the same single character. They look redundant and are not: the first
  preserves absoluteness and the second removes it, and swapping them would silently change every
  absolute URL in the world into a relative one.
- The query-string branch rewrites the argument to `file:...?...` because Python's `sqlite3` only
  interprets a filename as a URI when it begins with `file:` **and** you pass `uri=True`. That is how
  `?mode=ro` becomes an actual read-only connection rather than a filename containing a question
  mark.
- A string that does not start with `sqlite:` or `sqlite+aiosqlite:` is returned unchanged, which is
  why a plain path works at all.

Read from the installed source at
`.venv/Lib/site-packages/google/adk/sessions/sqlite_session_service.py` on 2026-09-05.
`https://adk.dev/sessions/session/` documents the URL form only for `DatabaseSessionService` and
does not describe this parser; the installed source is the specification here.

## When it breaks

Seven forms, resolved from `days/day-47-persistent-sessions/lab`:

```text
working directory: C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\days\day-47-persistent-sessions\lab

what you type                                 uri=   resolves to
--------------------------------------------------------------------------------------------------------------
data/sessions.sqlite3                         False  ...\day-47-persistent-sessions\lab\data\sessions.sqlite3
./data/sessions.sqlite3                       False  ...\day-47-persistent-sessions\lab\data\sessions.sqlite3
sqlite:///data/sessions.sqlite3               False  ...\day-47-persistent-sessions\lab\data\sessions.sqlite3
sqlite:///./data/sessions.sqlite3             False  ...\day-47-persistent-sessions\lab\data\sessions.sqlite3
sqlite:////tmp/sessions.sqlite3               False  C:\tmp\sessions.sqlite3
sqlite+aiosqlite:///data/sessions.sqlite3     False  ...\day-47-persistent-sessions\lab\data\sessions.sqlite3
sqlite:///data/sessions.sqlite3?mode=ro       True   ...\day-47-persistent-sessions\lab\data\sessions.sqlite3
                                                     passed to sqlite as: file:data/sessions.sqlite3?mode=ro
```

Four of those seven strings look different and name the same file. One of them —
`sqlite:////tmp/sessions.sqlite3` — names a directory at the root of the drive that almost certainly
does not exist, and it did not complain.

That last one is the failure worth having met. Ask the service to create a session there:

```text
sqlite3.OperationalError: unable to open database file
```

Six words, no path, no reason. It is the message SQLite gives for a directory that does not exist,
for a directory you may not write to, and for a filename with a character the filesystem refuses. It
does not distinguish between them and it does not tell you which file it tried. And it arrives at
the **first write**, not at construction — the service's `__init__` only inspects an existing file,
so a wrong path constructs cleanly, passes any start-up check you wrote, and fails on the first
customer.

Now the quiet one, which is the same bug wearing better clothes. The `urls.py` run above is the
evidence for it: every relative row resolved against
`…\day-47-persistent-sessions\lab`, because that is where the script was started. Start the same
script from the repository root and every one of those rows resolves to `<repo>\data\…` instead.
Two directories, one configuration string, two files.

Both runs work. Both create their tables. The second one shows an empty session list and a customer
whose ticket history has vanished, and the only evidence is two files with the same name in
different folders. Whoever debugs it will spend the first hour looking at the session service.

## In production

**What a professional writes instead:** they never let the working directory decide. The path is
computed once from a known anchor — the package's own location, or an environment variable that must
be absolute — and the service is handed an absolute string. Three lines in
`sutra/memory/persistence.py`:

- find the repository root from `Path(__file__)`,
- join the configured relative path onto it,
- create the parent directory before constructing the service, so `unable to open database file`
  cannot happen.

**What degrades at scale:** in a container the working directory is set by the image and can change
in a base-image bump nobody read. Worse, a relative path inside a container points at the container's
own filesystem, which is discarded when the container is replaced — so a store that is correctly
durable on a laptop is effectively in-memory in production, restarting empty on every deploy. The
path has to point at a mounted volume, and only an absolute path can be checked for that.

**The failure mode that only appears with real traffic:** a store that silently moved is
indistinguishable from a store that was silently wiped, and both look like customers not coming
back. Nothing in the metrics says "wrong file". The signal is that session counts reset to zero at
exactly the moment of a deploy, which is only visible if somebody happens to be graphing session
counts.

**The review comment a senior engineer leaves:** *"`db_path` here is `data/sessions.sqlite3`, which
is relative to whatever directory the process starts in. Our web entry point and our worker start in
different places, so those are two different stores that we will believe are one. Resolve it against
the package root and assert it is absolute, and `mkdir` the parent — right now a missing directory
gives us `unable to open database file` on the first customer of the day rather than at start-up."*

**The interview question:** *"what is the difference between three slashes and four in a SQLite
URL?"* The honest answer: *"Three is relative to the process's working directory, four is absolute.
It comes from SQLAlchemy's convention — after `sqlite:` you have two slashes for an empty host, then
the path, and the parser strips one leading slash. The reason it matters is that neither form fails
loudly: a relative path resolved from the wrong directory just creates a second empty database and
the service creates its tables in it, so it looks like every conversation was lost. I resolve the
path against a fixed anchor and pass an absolute string, and I create the parent directory first,
because the error for a missing directory is `unable to open database file` with no path in it."*
