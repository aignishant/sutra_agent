# 4.3 — Losing the race on purpose

## One-line answer

A refused write is only recoverable if the retry re-reads first: retrying the same session object
sends the same stale timestamp, is refused identically every time, and spends the whole attempt
budget proving something you already knew.

## The story

You are booking a train seat on your phone, in the last few days before a festival.

The seat map loads. Two lower berths are free in that coach and you tap one, fill in the passenger
details, and press *book*. The page thinks for a while and comes back: **this seat is no longer
available.**

Somebody else booked it in the time you spent typing a name.

Now watch what most people do. They press *book* again. Same page, same seat, same everything. It
fails, in the same way, with the same words. They press it a third time. It fails a third time. By
now they are annoyed with the railway, and the railway has done nothing wrong — the seat has been
gone since the first attempt, and every press since has been an argument with a fact.

The person sitting next to them, who has done this before, taps *refresh*. The seat map comes back
with the two berths gone and a different one free. They pick that one, and they get it.

The difference is not patience and it is not luck. One of them retried the request. The other
retried the *intention*, against what is actually there now.

## The idea in plain language

[4.1](4.1-refused-not-overwritten.md) established the refusal: `append_event` compares your
session's `last_update_time` against the store's `update_time` and raises `StaleSessionError` when
the store has moved on. [4.2](4.2-the-read-that-raises-nothing.md) established what the store does
*not* check. This part is what you do about the refusal.

The wrong answer is the one that looks most like ordinary error handling:

```
for attempt in range(3):
    try:
        append(handle, note)
        break
    except StaleSessionError:
        continue
```

That loop is a `try` and a `continue`, which is the shape every retry in every codebase has. It is
also completely useless here, and it is useless in a way worth naming. `handle` does not change
between attempts. Its `last_update_time` is the same number on attempt three as on attempt one, and
the store's `update_time` has only moved further away. The comparison that failed will fail again.
**A retry that changes nothing is a slower way of failing once.**

The right answer has three steps and the order is the whole of it:

1. **Re-read** the session from the store, so you are holding what is actually there.
2. **Re-apply** your intention to that fresh copy — not the value you computed from the old one.
3. **Write**, and if you are refused again, go back to step one, up to a bounded number of attempts.

Step 2 is the one people leave out, and it is why "just re-read and retry" is not sufficient advice.
If your event carries a *state delta* rather than a whole state, re-applying is free —
[1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md)'s `json_patch` merges your key into
whatever is there now. If it carries a value you computed from the old state — `count + 1`,
`"closed" because it was "open"` — then re-applying means recomputing, and if you skip that you have
written a fresh timestamp over a stale decision, which is [4.2](4.2-the-read-that-raises-nothing.md)
with better manners.

And step 3 is bounded because the loop can genuinely never succeed. If a busier writer touches the
session between every one of your attempts, you lose every race. A retry loop with no ceiling is a
process that will sit there forever, and the honest thing is to give up, log it and escalate —
Principle 10, and Day 44's
[6.1](../../../day-44-client-hardening/parts/06-the-last-word/6.1-what-you-say-when-it-all-failed.md).

## Why Sutra needs it

Because Day 44 already gave Sutra a retry loop, and this is the case that loop gets wrong.

`sutra/mcp/hardening.py`'s `with_retries` re-runs a callable that failed. If that callable closes
over a session object loaded before the first attempt — which is the natural way to write it — then
every retry is the blind arm below, and the retry budget is spent on refusals that were guaranteed.
Worse, `StaleSessionError` is not a transport failure. Day 44's
[1.3](../../../day-44-client-hardening/parts/01-what-may-be-repeated/1.3-the-line-through-every-call.md)
classifies calls by whether they may be repeated; a stale append **may** be repeated, but only
after a re-read, and "retry after doing something else first" is not a shape a generic retry wrapper
can express.

So the rule Sutra adopts is: **the retry boundary for a session write is outside the session load,
never inside it.** The unit that gets retried is *load, decide, write* — all three — and never the
write on its own.

That also settles what
[6.1](../06-forgetting-on-purpose/6.1-delete-the-session-keep-the-customer.md) and any other
maintenance job must look like, because they touch sessions a customer may be talking to at the same
moment.

## The mechanism

Six workers, one session, and one line of difference between the arms.

```python
# days/day-47-persistent-sessions/lab/recover.py  (extract)
async def append_with_retry(
    svc: SqliteSessionService, handle: Session, worker: int, blind: bool
) -> tuple[bool, int]:
    """Try to append, re-reading between attempts unless `blind`. Returns (ok, tries)."""
    for attempt in range(1, ATTEMPTS + 1):
        try:
            await svc.append_event(handle, note(worker))
            return True, attempt
        except StaleSessionError:
            if blind:
                continue  # same handle, same stale timestamp, same refusal
            handle = await svc.get_session(app_name=APP, user_id=USER, session_id=SESSION)
    return False, ATTEMPTS
```

**Line by line:**

- `for attempt in range(1, ATTEMPTS + 1)` counts from one because the number is reported to a human.
  An attempt count that starts at zero reads as an off-by-one in a log line and gets queried every
  time.
- `except StaleSessionError` and nothing broader. A `sqlite3.OperationalError` from
  [3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md)'s locked file is a different failure
  with a different answer, and catching both here would retry a lock storm into a worse lock storm.
- `if blind: continue` is the ablation and the entire experiment. It is one word away from the
  correct branch, and in review it reads as the same thing: both are "try again".
- `handle = await svc.get_session(...)` **rebinds the local name**. The refreshed session replaces
  the stale one for the next iteration, which is why the loop parameter is used rather than a
  separate variable — a fresh handle stored somewhere else while the loop keeps using the old one is
  the bug this line exists to avoid.
- `note(worker)` is called **inside** the loop, so each attempt builds a new event. An event built
  once outside the loop carries a fixed `id` and a fixed timestamp, and re-sending it after a
  successful partial write would be a duplicate rather than a retry.
- The return is `(ok, tries)` rather than a bare boolean, because the interesting number in the
  output below is not whether it worked but how many attempts it cost.
- Returning `False` after the loop is the bounded give-up. There is no `while True` here, and there
  is no `raise` either: the caller is given a fact to report rather than an exception to swallow.

Why re-applying is free in this particular case, and when it is not:

```python
# the event this lab writes carries no computed value
Event(
    author=f"worker-{worker}",
    invocation_id=f"inv-{worker}",
    content=types.Content(role="model", parts=[types.Part(text=f"note from worker {worker}")]),
)
```

**Line by line:**

- There is no `state_delta` on this event at all, so nothing in it depends on what the session's
  state was when the handle was loaded. Re-applying it to a fresh handle means literally sending the
  same event, which is why the correct arm needs no step between the re-read and the write.
- `content` carries a fixed sentence. Compare with a delta of `{"reply_count": old + 1}`, where
  `old` came off the stale handle: re-sending that after a re-read writes a number computed from a
  version that no longer exists, and the store will accept it, because
  [4.1](4.1-refused-not-overwritten.md)'s check is on the timestamp and not on your arithmetic.
- `author` is per worker, which is what makes the count at the end meaningful — six distinct lines,
  so a missing one is identifiable rather than merely absent.
- The safe pattern to carry away: **put the change in a `state_delta` and let `json_patch` merge
  it**, so re-applying is re-sending. Compute the new value in Python only when the store cannot,
  and then recompute it after every re-read.

## When it breaks

The blind arm, run on 2026-09-05. Every worker holds a handle loaded before anybody wrote:

```text
worker 0: wrote after 1 attempt(s)
worker 1: gave up after 3 attempt(s)
worker 2: gave up after 3 attempt(s)
worker 3: gave up after 3 attempt(s)
worker 4: gave up after 3 attempt(s)
worker 5: gave up after 3 attempt(s)

arm            : --blind
workers        : 6
total attempts : 16
events stored  : 1
lines lost     : 5
exit: 1
```

Sixteen attempts, one line stored, five lost. Worker 0 succeeded because it was first and its handle
was current; the other five were stale from the moment worker 0 committed, and each of them proved
it three times.

Read `total attempts : 16` against `events stored : 1`. Fifteen of those sixteen calls were work the
process could have known in advance would fail. In a real desk each of them may sit behind a model
call that already happened, which means the wasted attempt is not free — it is the expensive half of
the turn, thrown away and then thrown away again.

Now the same six workers, with one line changed:

```text
worker 0: wrote after 1 attempt(s)
worker 1: wrote after 2 attempt(s)
worker 2: wrote after 2 attempt(s)
worker 3: wrote after 2 attempt(s)
worker 4: wrote after 2 attempt(s)
worker 5: wrote after 2 attempt(s)

arm            : re-read between attempts
workers        : 6
total attempts : 11
events stored  : 6
lines lost     : 0
```

Six lines, eleven attempts, nothing lost. Every worker except the first pays exactly one extra
attempt: it is refused once, re-reads, and is accepted. **The refusal is not an error to be
eliminated; it is a message, and the loop's job is to act on it rather than repeat itself.**

The genuinely nasty version of the blind arm is the one where it looks like it works. Set
`ATTEMPTS` high enough and add a delay, and a blind retry starts succeeding sometimes — not because
re-sending helped, but because the contention passed and some other code path happened to refresh
the handle. Now you have a loop that is wrong, passes its tests, and fails only when the system is
busy, which is exactly when the writes matter most.

## In production

**What a professional writes instead:** they make the retryable unit a function that loads the
session itself. The wrapper is given `lambda: load_decide_write(session_id)`, never
`lambda: append(handle, event)`, so a re-read is structurally unavoidable rather than remembered.
They bound it — three attempts is a normal number — and the give-up path logs the session id, the
attempt count and what was not written, because none of those are in `StaleSessionError`'s own
message ([4.1](4.1-refused-not-overwritten.md)).

**What degrades at scale:** the number of attempts needed rises with the number of writers on one
session, and past a handful of contending writers most attempts are refused even with re-reads. The
loop is a shock absorber for occasional contention, not a queueing system. When the refusal rate
stops being occasional the answer is upstream — fewer things writing to one session, or a single
worker per conversation — and a retry loop tuned larger is a way of hiding that for another month.

**The failure mode that only appears with real traffic:** the retry that re-reads but does not
re-apply. It passes every test written against an event with no `state_delta`, because there is
nothing to recompute. The first time somebody adds `{"reply_count": old + 1}` to that event, the
loop silently starts overwriting other workers' increments — a lost update, produced by the code
that was supposed to prevent one, and reached through a two-line change nobody would flag.

**The review comment a senior engineer leaves:** *"the retry here wraps `append_event` and nothing
else, so every attempt re-sends a session object that was stale before the first attempt failed. It
will burn all three attempts and drop the note. Move the boundary out: retry the whole
load-decide-write, cap it at three, and on the last failure log the session id and escalate rather
than `pass`."*

**The interview question:** *"a write is refused because your copy is stale. What does your retry
look like?"* The honest answer: *"Not a loop around the write. The unit I retry is load, decide,
write — all three — because retrying the write alone re-sends the same stale timestamp and is
refused identically every time. I measured that: six workers each holding a handle loaded before any
of them wrote, three attempts each. Retrying blindly cost sixteen attempts and stored one line out
of six. Re-reading between attempts cost eleven attempts and stored all six. The part that is easy
to get wrong even after the re-read is re-applying the intention: if the event carries a value
computed from the old state you have to recompute it, otherwise you have written a fresh timestamp
over a stale decision and the store will happily accept it. And the loop is bounded — if I lose
every race I log the session id and escalate, because an unbounded retry is a process that never
finishes."*
