# 4.2 — 💥 The read that raises nothing

## One-line answer

The store guards writes and not reads, so a worker that loaded a session, did some work, and then
made a decision from the copy in its hand gets no error at all — just last week's answer with this
morning's confidence.

## The story

You go to the doctor with a cough and she asks whether you are on anything.

You hand over the folder. In it is a blood test — properly done, properly printed, entirely
accurate. Your haemoglobin was low, so she writes a prescription that assumes it still is.

The test is from five weeks ago. In between, another doctor at another clinic saw the same numbers,
put you on a course of iron, and you finished it a fortnight back. That is in a different folder, at
a different clinic, and it is not in this room.

Nothing that happened was wrong. The test was not a forgery, the doctor was not careless, and the
prescription follows correctly from what was in front of her. The paper simply stopped being true
after it was printed, and paper does not announce that.

## The idea in plain language

[4.1](4.1-refused-not-overwritten.md) showed the store refusing a **write** built on a stale copy.
It is easy to walk away from that with the wrong conclusion: *the store protects me from stale
sessions.*

It protects one thing, at one moment: an `append_event` whose session object is older than the
stored row. That is it.

There is no check on reading. There is no check on **using**. A `Session` object is an ordinary
Python object holding a snapshot of a row and a list of events, and the instant it is returned it
begins to be out of date. Look at `session.state["status"]` a minute later and you get whatever was
true a minute ago, with no indication that a minute has passed or that anything happened in it.

The gap is easy to miss because it is invisible in the shape of the code. These two lines look the
same:

```
status = session.state["status"]        # a dictionary lookup
status = live_status_from_the_store()   # a question to the database
```

The first is free and answers about the past. The second costs a read and answers about now. Nothing
in the syntax says which one you wrote.

The name for this is a **stale read**, and it is the quieter half of the same family as
[Day 43's lost update](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md).
A lost update destroys data. A stale read destroys a **decision**, and leaves the data perfectly
intact so that the decision looks defensible forever afterwards.

## Why Sutra needs it

Because Sutra's desk makes decisions from state, and state is the thing that goes stale.

Day 17's [4.1](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.1-state-steers-the-next-turn.md)
put state into the instruction so it steers the next turn. That is the whole point of state, and it
means every stale value becomes a stale *instruction* — a prompt built from a status that changed
while the model was thinking.

Two concrete places in this repository:

- A tool from [Day 4](../../../day-04-tools-by-hand/LESSON.md) reads `state["status"]` to decide
  whether a ticket may be closed. Between the read and the close, the ticket was closed by somebody
  else and reopened by the customer.
- Day 24's [budget](../../../day-24-token-accounting-and-budgets/LESSON.md) reads a spend counter and
  decides whether there is quota left. Read it from a session loaded three turns ago and the number
  is three turns old, which is precisely the over-spend Day 43 measured, arriving by a different
  route.

Neither of those raises. Both produce a wrong outcome that the store will faithfully record.

## The mechanism

B loads the session. A closes the ticket. B decides.

```python
# days/day-47-persistent-sessions/lab/staleread.py  (extract)
handle_b = await b.get_session(app_name=APP, user_id=USER, session_id=SESSION)

handle_a = await a.get_session(app_name=APP, user_id=USER, session_id=SESSION)
await a.append_event(
    handle_a,
    Event(
        author="worker-a",
        invocation_id="inv-a",
        actions=EventActions(state_delta={"status": "closed", "closed_by": "worker-a"}),
    ),
)

if fresh:
    handle_b = await b.get_session(app_name=APP, user_id=USER, session_id=SESSION)

status = handle_b.state.get("status")
approved = status == "open"
```

**Line by line:**

- B's load comes **first**, before A has done anything, which is the ordinary case: B started
  handling this customer, and then something else happened.
- A's write is a pure state change with no content, exactly the event shape from
  [1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md). It succeeds, because A's own
  handle is current.
- B then reads `handle_b.state`. **This is a dictionary lookup on an object B is holding.** No
  connection is opened, no row is read, no comparison against the store happens. There is no place
  in this line for the store to object.
- `approved = status == "open"` is the decision. In real code it would be a branch guarding a refund,
  a closure or a message to the customer, and it would look completely reasonable in review.
- `state.get("status")` rather than `state["status"]`, because a key that has never been written is
  absent rather than `None`, and a `KeyError` inside a turn is a different bug from the one being
  demonstrated.
- The `fresh` branch is one line, and it is the only difference between the two arms.

The comparison that would have caught it, and why nobody writes it:

```python
# the check the store does not do for you
stored = await svc.get_session(app_name=APP, user_id=USER, session_id=SESSION)
if stored.last_update_time > handle.last_update_time:
    handle = stored  # somebody wrote while we were thinking
```

**Line by line:**

- It is the same comparison `append_event` makes in
  [4.1](4.1-refused-not-overwritten.md), moved to before the decision instead of before the write.
  Nothing clever; just earlier.
- It costs a full `get_session`, which reads and deserialises **every event in the conversation** —
  the cost measured in [5.3](../05-shape-and-size/5.3-the-session-that-never-ended.md). Doing it
  before every state read would be slower than the work it guards.
- That cost is exactly why nobody writes it everywhere, and why the right answer is not "re-read
  always" but "re-read before decisions that matter" — a judgement, made once per decision, and
  written down.
- `handle = stored` replaces the handle rather than patching the state into the old one, because a
  handle with fresh state and a stale `last_update_time` is worse than either: it decides correctly
  and then cannot write.

## When it breaks

The default arm, run on 2026-09-05. No exception is raised anywhere in it:

```text
B loaded the session. state = {'status': 'open'}
A closed the ticket.

B reads status = 'open' and APPROVES the refund

arm            : decide from the copy in hand
B believed     : status='open'
store says     : status='closed'
exceptions     : 0
verdict        : refund approved on a closed ticket
exit: 1
```

`exceptions : 0`. That line is the part of the output to stare at.

Compare it with [4.1](4.1-refused-not-overwritten.md), which printed a `StaleSessionError` naming
itself. There, the system told you. Here it did not, and it *could* not: nothing B did was an
operation the store took part in. B looked at a dictionary.

Worse, the refund B approves will now be recorded — with an `append_event` that may well succeed,
because B can re-read before writing and be perfectly current by then. The store ends up holding a
consistent, well-formed, atomic record of a refund on a closed ticket. Every mechanism from
[3.1](../03-writes-that-survive/3.1-the-ticket-torn-in-two.md) onwards worked. The outcome is still
wrong.

And the one-line fix:

```text
B re-read the session. state = {'status': 'closed', 'closed_by': 'worker-a'}

B reads status = 'closed' and refuses the refund

arm            : --fresh
B believed     : status='closed'
store says     : status='closed'
exceptions     : 0
verdict        : decision matches the store
```

Still `exceptions : 0` in the correct arm too. Which is the honest summary of this whole part:
**you cannot tell these two runs apart by looking for errors.** You can only tell them apart by
knowing which decisions in your system are allowed to be made from a snapshot.

## In production

**What a professional writes instead:** they separate reads that inform from reads that decide. A
value used to phrase a sentence can be a snapshot; a value used to authorise money, close a record
or send something irreversible is re-read immediately before the act, or — better — the act is
expressed as a conditional statement the database evaluates: `UPDATE tickets SET status='refunded'
WHERE id=? AND status='open'`, where the row count tells you whether you were allowed. That is
[Day 43's 4.2](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md)'s
single-statement rule, and it removes the window rather than narrowing it.

**What degrades at scale:** the window is the length of a turn, and a turn contains a model call.
Longer answers, slower providers and retried tool calls all widen it. So the probability of a stale
decision rises with exactly the thing you cannot control, and it rises fastest for the most
complicated conversations — the ones with the most at stake.

**The failure mode that only appears with real traffic:** it is unreproducible by construction.
Support reports a refund on a closed ticket. You read the transcript and it is coherent. You read the
code and it checks the status. You run it and it works. The only artefact is a timestamp ordering
across two workers that nobody logged, and the ticket is closed as "could not reproduce" — twice,
before somebody thinks of the word *stale*.

**The review comment a senior engineer leaves:** *"this reads `session.state['status']` at the top of
the handler and decides on it forty lines later, after two tool calls and a model call. That value is
as old as the turn. For phrasing the reply I do not mind; for the branch that issues the refund I do.
Re-read before the branch, or make the refund a conditional update that fails if the ticket is no
longer open."*

**The interview question:** *"you have optimistic concurrency on writes. Are you safe?"* The honest
answer: *"No — that is a guarantee about writes and there is a whole class of bugs that never
reaches a write. A session object is a snapshot, so reading `state` gives you what was true when you
loaded it, and the store cannot object because it is not involved: it is a dictionary lookup. I
demonstrated it with a refund approved on a ticket that had been closed while the worker was
thinking, and the run raised zero exceptions in both the broken and the fixed arm — so you cannot
find these by looking for errors. The rule I use is that a value that only shapes wording may be a
snapshot, and a value that authorises something is either re-read at the moment of acting or turned
into a conditional update the database evaluates."*
