# 5.2 — 💥 The migration that passed

## One-line answer

A migration that checks row counts checks the one thing that cannot go wrong: a thousand
conversations came across as a thousand empty rows, every count matched, and the script reported
success.

## The story

The cooking gas runs out halfway through a Sunday lunch, which is when it always runs out.

You book a refill. Two days later a man carries a cylinder up the stairs, takes the empty one away,
and holds out a slip. You sign it. *One cylinder delivered, one empty collected.* He is not
dishonest, you are not careless, and the slip is entirely accurate: one went out, one came in.

That evening the burner will not light. There is gas in the pipe for about four seconds and then
nothing. The cylinder on the floor is the right size, the right colour, has the right seal, weighs
enough that you did not think to check — and it was never filled at the plant.

Your slip is not wrong. It is a count of cylinders. It was never a statement about gas.

## The idea in plain language

Sooner or later your store needs a column it does not have. A channel the ticket came in on. A
retention date. A flag.

SQLite's `ALTER TABLE` can add a column, and for a simple case that is all you need. The moment you
want anything it cannot do — change a type, add a constraint, reorder, drop a column on an older
build — the standard recipe is four steps:

1. `CREATE TABLE events_new (...)` with the shape you want;
2. `INSERT INTO events_new (...) SELECT ... FROM events` to copy the rows across;
3. `DROP TABLE events`;
4. `ALTER TABLE events_new RENAME TO events`.

This is the recipe SQLite's own documentation gives, and it is correct. All four statements go
inside one `BEGIN IMMEDIATE ... COMMIT`, for [3.1](../03-writes-that-survive/3.1-the-ticket-torn-in-two.md)'s
reason: a migration interrupted between step 3 and step 4 is a store with no `events` table at all.

Now the part that goes wrong, and it is in step 2.

`INSERT INTO events_new (a, b, c) SELECT a, b, c FROM events` requires you to **list the columns**,
twice. Nobody enjoys typing that, so it is copied from somewhere — the `CREATE TABLE` above it, a
previous migration, the output of `PRAGMA table_info` — and in the copying one name goes missing, or
is replaced by a placeholder while somebody works out what to put there, and never goes back.

The rows still copy. SQLite does not object: a column you did not name gets its default, and a
literal you supplied instead of a column is a perfectly valid thing to select. The count is right.
Every row is present. Every row is empty in exactly one place.

And then the migration script prints the check everybody writes: `rows before == rows after`. It
passes, because a count of rows was never a statement about what is in them.

## Why Sutra needs it

Because [5.1](5.1-the-store-the-code-cannot-read.md) established that the ADK's own migration tool
cannot run in this repository, which means the migration Sutra ever runs is one somebody here wrote.

And because of what is actually in the column that goes missing.
[1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md) established that `event_data` is the
**entire event** — the customer's words, the agent's answer, the tool calls, the state deltas — as
one JSON document. Every other column in that table is an identifier or a timestamp. So `events` has
exactly one column that carries meaning and six that carry addresses, and the one is the one whose
absence a row count cannot see.

The row-count check is not stupid; it is the right check for a different failure. It catches a
`WHERE` clause that excluded rows, a copy that stopped halfway, a join that multiplied. It is a check
on the *copy*, and what it cannot do is be a check on the *contents*. Sutra's rule after this part:
**a migration is verified by reading something out of the new store, not by counting what went into
it.**

That is the same sentence as [7.1](../07-in-production/7.1-the-backup-nobody-restored.md)'s, and the
two parts are the same idea pointed at two operations.

## The mechanism

The recipe, with the one line that differs between the arms.

```python
# days/day-47-persistent-sessions/lab/dropped.py  (extract)
UNSAFE_COPY = """
INSERT INTO events_new (id, app_name, user_id, session_id, invocation_id, timestamp, event_data)
SELECT id, app_name, user_id, session_id, invocation_id, timestamp, ''
FROM events;
"""
SAFE_COPY = """
INSERT INTO events_new (id, app_name, user_id, session_id, invocation_id, timestamp, event_data)
SELECT id, app_name, user_id, session_id, invocation_id, timestamp, event_data
FROM events;
"""
```

**Line by line:**

- The two statements differ by **one token**: `''` where `event_data` should be. Put them side by
  side in a diff and the change is a two-character deletion; put either one alone in a pull request
  and it looks exactly like a migration.
- The target column list is identical in both, and it *names* `event_data`. That is what makes the
  unsafe version so quiet: the column is not missing from the insert, it is being filled with the
  wrong thing, so no "column has no default" error can fire.
- `''` rather than `NULL`, because the real schema has `event_data TEXT NOT NULL`. A `NULL` would
  have raised a constraint violation and saved everybody. **The empty string is what the constraint
  permits and the reader cannot use** — the shape of every good `NOT NULL` column that is not also
  checked for emptiness.
- The safe form is not cleverer. It is the same statement with the column named on both sides, which
  is the entire fix, and it is why this failure is a review failure rather than a design failure.
- Both are triple-quoted strings rather than built with f-strings. Nothing here is interpolated from
  a caller, so there is nothing to inject, and a migration that builds its own SQL from variables is
  a much harder thing to review than one you can read as text.

The recipe around it, and the transaction that has to hold it:

```python
# days/day-47-persistent-sessions/lab/dropped.py  (extract)
conn = sqlite3.connect(DB, isolation_level=None)
(before,) = conn.execute("SELECT COUNT(*) FROM events").fetchone()
# One statement per execute(), because executescript() commits any open
# transaction before it starts - which would silently discard the BEGIN.
conn.execute("BEGIN IMMEDIATE")
conn.execute(NEW_EVENTS_TABLE)
conn.execute(SAFE_COPY if safe else UNSAFE_COPY)
conn.execute("DROP TABLE events")
conn.execute("ALTER TABLE events_new RENAME TO events")
conn.execute("COMMIT")
(after,) = conn.execute("SELECT COUNT(*) FROM events").fetchone()
```

**Line by line:**

- `isolation_level=None` turns off the driver's implicit transactions, so the `BEGIN IMMEDIATE` here
  is the only transaction in play. Without it you would have the driver's deferred `BEGIN` from
  [3.1](../03-writes-that-survive/3.1-the-ticket-torn-in-two.md) wrapped around your explicit one,
  and which one commits becomes a question you have to answer rather than a thing you control.
- `BEGIN IMMEDIATE` and not a plain `BEGIN`. Immediate takes the write lock at the `BEGIN`, so a
  migration either has the file from the start or fails at the start. A deferred begin would take the
  lock at the first write, having already read a count from a store somebody else may be changing —
  [Day 43's 4.2](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md).
- The comment is load-bearing and the trap it names is real: `executescript()` issues a `COMMIT`
  before running its script. Passing all four statements to `executescript` after a `BEGIN IMMEDIATE`
  ends the transaction you just opened, and the migration runs unprotected while appearing to be
  wrapped.
- `DROP TABLE events` before the rename, so the name is free. Between those two statements the store
  has no `events` table, which is the reason the transaction is not optional: a crash there leaves a
  file the session service will open and find empty.
- The `after` count is read **after** the commit and through the same connection. Reading it inside
  the transaction would count rows nobody else can see yet, which is the check being fooled by the
  thing it is checking.
- Nothing here disables foreign keys, and it matters: `events` has a cascading key onto `sessions`
  ([1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md)). Under SQLite's defaults foreign
  keys are off, so the drop is allowed. Run this same script with `PRAGMA foreign_keys = ON` and the
  `DROP TABLE` behaves differently — worth knowing before you copy this recipe onto a table something
  else references.

## When it breaks

The default arm, run on 2026-09-05 against a store holding a thousand conversations:

```text
arm                 : columns listed by hand
event rows before   : 1000
event rows after    : 1000
row-count check     : PASS
readable before     : 1000
readable after      : 0
conversations lost  : 1000
exit: 1
```

`row-count check : PASS`. That is the line a migration script prints, and it is the line that goes in
the change ticket, and it is true.

`readable after : 0`. A thousand conversations, every one of them present as a row with the right
identifiers and the right timestamp, and not one of them containing a word anybody said.

Nothing raised. The database is not corrupt — run an integrity check and it is perfect. The foreign
keys line up. The primary keys are unique. Every `NOT NULL` column has a value in it. **The store is
internally consistent and externally worthless**, which is exactly
[3.1](../03-writes-that-survive/3.1-the-ticket-torn-in-two.md)'s point about a torn write arriving by
a completely different route: the database can only check what it was told to check, and "this
column holds a customer's sentence" is not something SQL can be told.

The same script with the column named on both sides:

```text
arm                 : --safe
event rows before   : 1000
event rows after    : 1000
row-count check     : PASS
readable before     : 1000
readable after      : 1000
conversations lost  : 0
exit: 0
```

Both arms print `row-count check : PASS`. **The check that everybody writes is identical in the run
that worked and the run that destroyed a year of transcripts.** Only the two lines below it tell them
apart, and those two lines exist because somebody decided that "readable" was the property that
mattered and wrote a function that opens a row and looks for text in it.

The delayed discovery is the part that costs most. Nobody notices at migration time, because nobody
opens an old conversation at migration time. They notice weeks later, when a customer replies to a
ticket from before the change and the desk answers as though the conversation had never happened —
and by then the backup that still had the data has rotated away.

## In production

**What a professional writes instead:** a migration script whose last step reads. Not a count — an
actual read of a handful of rows, chosen from the oldest, the newest and the middle, deserialised
through the same code path the application uses, with an assertion that a known sentence is still in
there. And a copy of the file kept beside it until somebody has confirmed the new one works, which
is [7.1](../07-in-production/7.1-the-backup-nobody-restored.md).

**What degrades at scale:** the window between running the migration and discovering it was wrong
grows with the age of your store. On a week-old store somebody opens an old conversation the same
afternoon. On a two-year-old store the affected conversations are the ones nobody touches, so the
signal arrives one customer at a time, spread over months, and never looks like one incident. The
older the data, the longer the fuse.

**The failure mode that only appears with real traffic:** the migration that runs while the desk is
serving. `BEGIN IMMEDIATE` holds the write lock for the whole copy, and the copy is proportional to
the store, so every service constructed during it fails —
[3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md)'s `database is locked`, arriving at
`__init__`. On a small store the window is too short to notice and the habit forms. On a big one it
is an outage, and the habit is already there.

**The review comment a senior engineer leaves:** *"the copy statement lists seven columns on the left
and six columns plus a literal on the right, and the literal is where `event_data` should be. That
is every transcript we own. Separately: the only check after this runs is a row count, and a row
count cannot see this class of bug at all — add a read of a few rows through `Event.model_validate_json`
and assert the text is still there, or the next one of these ships too."*

**The interview question:** *"how do you know a data migration worked?"* The honest answer: *"Not
from row counts. I have run the one that proves it: a thousand sessions migrated with one column
name replaced by an empty string, and the before-and-after counts matched exactly, the database
passed its own integrity check, every `NOT NULL` constraint was satisfied, and every transcript was
gone. The row count is a real check for a real failure — a `WHERE` that excluded rows, a copy that
stopped — and it is structurally incapable of seeing an empty column. So the verification has to
read: take rows from the oldest, the newest and the middle, deserialise them through the same code
the application uses, and assert that a sentence you know is in there is still in there. And keep
the old file until somebody has done that."*
