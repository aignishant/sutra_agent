# 5.1 — The store the code cannot read

## One-line answer

A durable store is a promise you make to your future self, and the ADK's own schema has already
changed once: a file written by an older version makes the constructor raise, and the migration the
error names needs a package this repository deliberately does not have.

## The story

There is a video cassette in a cupboard at home with a wedding on it.

The tape is fine. It has been in a box, away from the sun, and the label is still legible in
somebody's handwriting. Nothing has rotted and nothing has been erased. The recording is as good as
the day it was made.

There is no player in the house. There has not been one for years. The shop on the main road that
used to copy tapes onto discs — the one with the handwritten rate card in the window — closed, and
the man who ran it moved away. Somebody says there is a place two towns over. Somebody else says
they have a player but the belt has gone.

So the wedding is on that tape, and it is unreachable, and the reason has nothing to do with the
tape. **What went missing was the thing that could read it.**

The family who copied their tapes onto a disc in the year the shop was still open did not do
anything clever. They did it while the machine was still in the room.

## The idea in plain language

Everything so far in this day has treated the file as a fact: you write it, it stays, you read it
back. That is true for as long as the code that reads it exists and still understands the shape.

The shape has already changed once. Earlier versions of the ADK stored a session's events **exploded
into columns** — an `events` table with `author` and `content` as separate fields, and timestamps
stored as `TIMESTAMP` rather than as floating-point seconds. `google-adk==2.7.1` stores the whole
event as one JSON document in a column called `event_data`, for the reason
[1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md) gave: an event that grows a new
field costs no schema change.

Both shapes are legitimate. The problem is a file written in the first one and opened by code that
expects the second.

`SqliteSessionService` handles this deliberately, and its choice is worth studying because it is the
right one. **It refuses.** The constructor opens the file, looks at the `events` table, and if the
table exists without an `event_data` column it raises rather than proceeding. It does not silently
create a second `events` table. It does not read what it can and skip the rest. It does not migrate
your data for you behind your back.

The word for this shape of decision is **fail fast**: when the situation is one the code cannot
handle correctly, stop at the earliest possible moment, loudly, with the situation named. The
alternative is to carry on and produce something plausible, which is
[Principle 10](../../../day-21-errors-surface-not-swallow/LESSON.md) inverted.

The error also tells you what to run. And that is where this part stops being about the ADK and
starts being about you, because on this installation, the thing it tells you to run **cannot run**.

## Why Sutra needs it

Because Sutra is about to put real conversations in a file and keep them, and a store is only
durable for as long as something can open it.

Two commitments follow from this part, and the hub's build brief asks for both.

The first is a **version note beside the store**. `sutra/memory/persistence.py` names an ADK version
and a date already, for the unexported import in
[2.1](../02-reaching-the-service/2.1-the-class-that-is-not-exported.md). The same comment is where
the schema generation belongs, because when a future `uv sync` produces the error below, the first
question is *what wrote this file*, and the answer should not require archaeology through the git
log.

The second is that **the migration path is checked before it is needed, not after**. This part
checks it and finds it unavailable — the ADK's migration tool imports SQLAlchemy, which
[2.2](../02-reaching-the-service/2.2-the-driver-you-do-not-have.md) established is an optional extra
this repository does not install. That is not a crisis; it is a fact worth knowing on a quiet day
rather than during an upgrade.

It is also the reason [5.2](5.2-the-migration-that-passed.md) exists. If the supplied migration
cannot run, somebody writes their own, and that is where the interesting failure lives.

## The mechanism

Build a store in the old shape, fill it, and point the current service at it.

```python
# days/day-47-persistent-sessions/lab/oldschema.py  (extract)
OLD_SCHEMA = """
CREATE TABLE events (
    id TEXT, app_name TEXT, user_id TEXT, session_id TEXT,
    invocation_id TEXT, timestamp TIMESTAMP NOT NULL,
    author TEXT NOT NULL, content TEXT,
    PRIMARY KEY (app_name, user_id, session_id, id)
);
"""


def construct() -> str:
    """Point the current service at the old file and report what comes back."""
    from google.adk.sessions.sqlite_session_service import SqliteSessionService

    try:
        SqliteSessionService(db_path=f"sqlite:///{DB.as_posix()}")
    except RuntimeError as err:
        return f"RuntimeError: {err}"
    return "constructed without complaint"
```

**Line by line:**

- `author TEXT NOT NULL, content TEXT` and **no `event_data`** is the whole difference. The old shape
  gave each field its own column, which is what a database person would do and what makes SQL
  queries over a transcript possible — and which is why every new field in an `Event` needed a schema
  change.
- `timestamp TIMESTAMP NOT NULL` rather than `REAL`. SQLite has no real date type; `TIMESTAMP` is
  accepted and stored with whatever affinity the value has, so the old shape held date *strings*.
  That is the comparison problem [1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md)
  warned about, and it is why the current schema uses a float.
- The `PRIMARY KEY` is unchanged between the shapes. Sessions and their identity survived the
  redesign; only the event body moved.
- The import is inside `construct()`, so the script can describe the file before anything touches it.
  The same reason as [2.1](../02-reaching-the-service/2.1-the-class-that-is-not-exported.md)'s
  probes: the report is the product.
- `except RuntimeError` and not `except Exception`. The service raises exactly `RuntimeError` here,
  and catching the specific type is what makes a *different* failure — a missing directory, a locked
  file — still crash the script visibly.
- **Nothing is awaited.** This failure happens in `__init__`, before any session is created, which is
  the same fact [3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md) met from the other
  direction: constructing the service reads the disk.

The check itself, in the ADK's own source:

```python
# .venv/Lib/site-packages/google/adk/sessions/sqlite_session_service.py  (extract)
cursor.execute("SELECT 1 FROM sqlite_master WHERE type='table' and name='events'")
if not cursor.fetchone():
    return False  # No events table, so no migration needed.

cursor.execute("PRAGMA table_info(events)")
columns = [row[1] for row in cursor.fetchall()]
if "event_data" in columns:
    return False  # New schema: event_data column exists.
else:
    return True  # Old schema: events table exists, but no event_data column.
```

**Line by line:**

- The test is **one column's presence**, not a version number stored in the file. There is no
  `schema_version` table anywhere in this design; the shape is inferred from the shape.
- `SELECT 1 FROM sqlite_master ... name='events'` first, because a file with no `events` table is a
  brand-new store rather than an old one. That branch is what lets you point the service at a path
  that does not exist yet.
- `PRAGMA table_info(events)` and index `1` for the column name — the same catalogue query
  [1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md) used, here as a decision rather
  than as a report.
- Inferring the version from a column is cheap and it has one honest weakness: it can only tell these
  two shapes apart. A third shape, or a file that is not an ADK store at all but happens to have an
  `events` table with an `event_data` column, passes.
- The whole block is wrapped in `except sqlite3.Error` that re-raises as `RuntimeError` — which is
  where [3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md)'s `database is locked`
  `RuntimeError` came from. One `try` produces two very different failures with the same exception
  type.

Read from the installed source on 2026-09-05. `https://adk.dev/sessions/session/`, fetched the same
day, documents neither the schema nor the migration; the installed source is the specification here.
`https://adk.dev/docs/sessions/session/` returns HTTP 404.

## When it breaks

A thousand sessions in the old shape, and the current service opened against them, on 2026-09-05:

```text
old store: 1000 sessions, events columns = ['id', 'app_name', 'user_id', 'session_id', 'invocation_id', 'timestamp', 'author', 'content']
'event_data' present: False

RuntimeError: Database .../lab/oldschema.sqlite3 seems to use an old schema. Please run the migration command to migrate it to the new schema. Example: `python -m google.adk.sessions.migration.migrate_from_sqlalchemy_sqlite --source_db_path .../lab/oldschema.sqlite3 --dest_db_path .../lab/oldschema.sqlite3.new` then backup .../lab/oldschema.sqlite3 and rename .../lab/oldschema.sqlite3.new to .../lab/oldschema.sqlite3.

the migration the error names imports sqlalchemy; sqlalchemy installed: False

  [ok] the service refuses the old file
  [ok] the error names the migration module
  [ok] that migration cannot run here

changed: 0
```

That error message is unusually good and it is worth saying why. It names the file. It names the
condition — *an old schema*, not "invalid database". It gives the **exact command**, with both paths
filled in. And it says what to do afterwards, in order: back up the original, then rename the new
one over it. Compare it with `unable to open database file` from
[2.3](../02-reaching-the-service/2.3-the-url-that-names-a-file.md), which names nothing at all.

Now the third line of the report, which is the break.

`migrate_from_sqlalchemy_sqlite` imports `sqlalchemy` at module scope. On this installation
SQLAlchemy is not present, so the command in that helpful message fails at import before it reads a
byte of your data. The error told you the truth and handed you a door that is locked from the other
side.

The shape of the day this happens on is worth picturing, because it is not a lab. A container is
rebuilt, `uv sync` pulls a newer ADK, the process starts, and the constructor raises before the
first request. Every instance does the same thing at the same moment, because they all read the same
file. There is no partial degradation: the desk is simply down, and it is down at start-up, which is
the best possible time for it to happen and does not feel that way at the time.

And the fix is not available in the container, because the container does not have the `db` extra
either.

## In production

**What a professional writes instead:** they take a copy before the upgrade, not after the failure.
The sequence is: stop writing, copy the store, run the migration against the copy, point a process
at the copy and **read a conversation out of it**, and only then swap. Every one of those steps is
cheap and the last one is the one people skip —
[7.1](../07-in-production/7.1-the-backup-nobody-restored.md) is what skipping it costs. They also
pin the ADK version in `pyproject.toml`, which this repository already does, so a schema change
arrives when somebody chose it rather than when a base image moved.

**What degrades at scale:** the migration is proportional to the store, and the store only grows. A
thousand sessions is instant; the same script against a year of a busy desk is a job with a
duration, run while nothing is writing, which means it is a maintenance window. And a maintenance
window on a SQLite file is [3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md)'s exclusive
lock: every process that tries to construct a service during it dies. The migration and the outage
are the same event.

**The failure mode that only appears with real traffic:** the half-migrated fleet. One instance is
redeployed with the new version and refuses to start; the old instances are still serving happily
from the same file. The dashboard shows a partial outage, the logs on the new instance show a schema
error, and the obvious reading — "the new build is broken" — sends somebody rolling back, which
works, which is the worst outcome, because now nobody investigates.

**The review comment a senior engineer leaves:** *"we are pinned to `google-adk==2.7.1` and the
session store is on disk, and there is nothing anywhere saying which schema generation wrote it. Put
the ADK version and the date in a comment beside the store path in `persistence.py`, and add a line
to the upgrade checklist: copy the file, migrate the copy, read a conversation out of it, then
swap."*

**The interview question:** *"your framework changed how it stores sessions. What happens to the
data you already have?"* The honest answer: *"In our case the service refuses to open it, which is
the right behaviour — it checks the `events` table for an `event_data` column in its constructor and
raises rather than reading half of what is there. The error is good: it names the file and gives the
exact migration command. The catch was that the migration tool it names imports SQLAlchemy, which we
deliberately do not install because we use the SQLite service and not the general database one, so
the documented fix does not run in our environment. That is worth finding on a quiet day rather than
during an upgrade, so we test it: copy the store, migrate the copy, open the copy and read a
conversation back, then swap. And because the file itself carries no version marker — the schema is
inferred from a column — the ADK version and the date go in a comment beside the store path."*
