# 5.3 — The session that never ended

## One-line answer

`get_session` reads and deserialises **every** event in the conversation, so the cost of one turn
grows with everything that has ever been said in it — and the fix is a limit pushed into the SQL,
not a slice taken afterwards.

## The story

You ring the helpline about a bill that is wrong, and you get through to somebody in about a minute,
which is a good start.

You explain it. The wrong amount, the month, the meter number, the two previous calls. It takes a
while because there is a lot of it. She listens, says she will transfer you to the billing team, and
the line goes quiet with music on it.

The billing team picks up and says: *tell me the problem.*

So you tell it again. All of it. The amount, the month, the meter number, and now also the fact that
you have just explained this to somebody else. He listens, and says this is really for the meter
section, and transfers you.

The meter section says: *tell me the problem.*

By the fourth telling it takes longer than it did the first time, because there is more of it now —
the original complaint plus the history of the call itself. Nobody has been rude to you. Everybody
has listened properly. The system simply has no way to hand your story forward, so **every person
who joins pays the full price of everything that has already been said**, and that price goes up
every time somebody joins.

## The idea in plain language

A session's `events` table is append-only ([1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md)).
Nothing removes a turn. So a conversation that stays open gets longer, forever, and the interesting
question is what that costs.

It costs on every turn, and here is the chain. Each turn begins with `get_session`. `get_session`
runs one query for the session row and one for the events, and the events query — with no
configuration — has no `LIMIT` on it. Every row comes back. Then, in Python, each row's JSON is
handed to `Event.model_validate_json`, which builds a Pydantic model out of it. A thousand stored
events is a thousand JSON parses and a thousand model constructions, on the way in to a turn where
the agent will look at the last two.

That is **linear cost**: the work per turn is proportional to the length of the conversation, so the
total work over a conversation is proportional to its length squared. A conversation twice as long
does not cost twice as much to hold; it costs four times as much.

There is a supported answer, and it is not slicing the list afterwards. `get_session` takes a
`config` argument of type `GetSessionConfig`, with two fields:

| Field | What it does |
| --- | --- |
| `num_recent_events` | a `LIMIT` on the events query — only the most recent N rows are read |
| `after_timestamp` | a `WHERE timestamp >= ?` — only events since a moment are read |

Both of those go **into the SQL**. That is the whole point. `session.events[-20:]` in Python gives
you the same twenty events and pays for all thousand: the rows still travel, the JSON is still
parsed, the models are still built, and then you throw them away. A limit that is not in the query
is not a limit on the work.

The second half of the answer is not a parameter at all. Some of what a long transcript is being
read *for* is a handful of facts the agent keeps re-deriving — the customer's ticket number, their
tier, what was agreed three days ago. Those belong in state, and specifically in the `user:` scope
from [1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md): one row, read in one
statement, instead of four hundred events deserialised to work out the same thing.

## Why Sutra needs it

Because Sutra's desk answers tickets, and a ticket is a conversation that nobody ever formally ends.

A customer writes on Monday, gets an answer, writes again on Thursday about the same thing, and the
ticket is still open in March. There is no logout, no "conversation over" button, and no natural
moment at which the session id changes. The realistic shape of a support session is *long and
punctuated*, which is the worst case for the mechanism above: the conversation is long enough to be
expensive and idle enough that nobody is watching the latency.

This is also the number [2.5](../02-reaching-the-service/2.5-the-lounge-you-cannot-enter.md) needs.
"Should we move to a managed session store?" is only answerable with measurements, and load cost per
turn against transcript length is one of the four. If your load is flat at twenty events, the store
is not your problem, whatever it is.

And it is the fact [Day 48](../../../day-48-memory-design/LESSON.md) is built on. Day 48 decides
what is worth remembering out of a conversation; this part is why that question has a cost attached
rather than being a matter of taste. Everything you keep in the transcript, you re-read.

## The mechanism

Grow one conversation to four hundred turns, and time a full load at five points along the way.

```python
# days/day-47-persistent-sessions/lab/grow.py  (extract)
config = GetSessionConfig(num_recent_events=RECENT) if recent else None

for n in range(1, max(MARKS) + 1):
    handle = await svc.get_session(app_name=APP, user_id=USER, session_id=SESSION)
    await svc.append_event(handle, Event(author="user", invocation_id=f"inv-{n}", content=...))
    if n in MARKS:
        started = time.perf_counter()
        loaded = await svc.get_session(
            app_name=APP, user_id=USER, session_id=SESSION, config=config
        )
        elapsed = (time.perf_counter() - started) * 1000
        print(f"{n:>7}  {DB.stat().st_size:>9}  {len(loaded.events):>7}  {elapsed:>8.1f}")
```

**Line by line:**

- `GetSessionConfig` is imported from `google.adk.sessions.base_session_service`, where it is defined
  beside the interface it configures. It is a Pydantic model with both fields optional, so
  `GetSessionConfig()` is legal and does nothing — which is a trap worth knowing, because a typo in
  a field name is a validation error and a *missing* field is silence.
- `config = ... if recent else None`, and `None` is what a caller who has never heard of this
  argument passes. **The unlimited read is the default**, which is the right default for correctness
  and the wrong one for a long conversation.
- The loop re-loads the session before each append rather than reusing the handle, because that is
  what a real turn does: a turn starts by loading the conversation. Reusing one handle for four
  hundred appends would measure something no production code ever does.
- `time.perf_counter()` and not `time.time()`. `perf_counter` is monotonic and has the highest
  resolution the platform offers; `time.time()` can go backwards when the clock is adjusted, which
  produces negative durations in a log and an afternoon of confusion.
- The timing brackets **only** the `get_session` call, not the append, so the number is the cost of
  reading and nothing else.
- `len(loaded.events)` is printed beside the milliseconds because it is the number that is actually
  a fact. The milliseconds are one laptop on one day; the event count is what the exit code is
  decided on, and it is reproducible anywhere.

The query the limit goes into, from the service's own source:

```python
# .venv/Lib/site-packages/google/adk/sessions/sqlite_session_service.py  (extract)
query_parts.append("ORDER BY timestamp DESC, id DESC")

if config and config.num_recent_events is not None:
    query_parts.append("LIMIT ?")
    params.append(config.num_recent_events)
...
events = [Event.model_validate_json(event_data) for event_data in reversed(storage_events_data)]
```

**Line by line:**

- `ORDER BY timestamp DESC` — **descending**, so that a `LIMIT` takes the *most recent* N rather than
  the oldest N. Ordering ascending and limiting would give you the beginning of the conversation,
  which is almost never what "recent" means.
- `, id DESC` breaks ties. Two events written in the same instant — a tool call and its response,
  commonly — have equal timestamps, and without a tiebreaker SQLite may return them in either order
  on either read. That would make a replayed conversation shuffle, and it would make
  `num_recent_events` cut at an arbitrary point inside the tie.
- `LIMIT ?` is bound as a parameter rather than interpolated, even though it is an integer you
  produced. Consistency is the reason: a codebase where *some* values are interpolated is one where
  the next value is too.
- `reversed(...)` puts the rows back into chronological order after the descending read. The database
  is asked for the newest first because that is what a limit needs; the caller is given oldest first
  because that is what a transcript is.
- `Event.model_validate_json` is where the real cost sits. It is a JSON parse plus full Pydantic
  validation, per row, in Python. This is the line the `LIMIT` above exists to run fewer times.
- Note what is **not** here: no cache, no lazy loading, no pagination handle. Every read is a fresh
  read of whatever you asked for, which is the honest behaviour for a store that several processes
  write to ([4.2](../04-two-workers/4.2-the-read-that-raises-nothing.md)) and is also why the limit
  is the only lever.

## When it breaks

Four hundred turns, loaded in full at each mark, on 2026-09-05:

```text
 events   db bytes   loaded   load ms
      1      36864        1       4.4
     50     139264       50       5.1
    100     249856      100       6.8
    200     462848      200      15.5
    400     888832      400      54.2

arm            : whole session
events per load: 400 (budget 50)
worst load     : 54.2 ms
verdict        : the load still grows with the conversation
exit: 1
```

Read the `load ms` column downwards. One event: 4.4. Fifty: 5.1 — barely moved, which is why nobody
catches this early. A hundred: 6.8. Two hundred: 15.5. Four hundred: **54.2**.

Between 200 and 400 the cost more than tripled for a doubling of length. That is not a linear line;
it is a linear line plus everything that gets worse when a working set stops fitting comfortably —
more rows, bigger allocations, more Python objects alive at once. The shape is the point: the curve
is flat exactly where you test it and steep exactly where your oldest customers live.

The `db bytes` column is the honest counterweight. Four hundred turns of a fairly wordy line is
about 890 kilobytes. **Disk is not the problem.** A hundred such conversations is under a hundred
megabytes, which is nothing. The cost is not storage, it is the read, and confusing the two is how
teams end up deleting data they needed to solve a latency problem they had not measured.

Now the same four hundred turns with the limit in the query:

```text
 events   db bytes   loaded   load ms
      1      36864        1       4.1
     50     139264       20       5.0
    100     249856       20       5.7
    200     462848       20       4.7
    400     888832       20       6.0

arm            : --recent (num_recent_events=20)
events per load: 20 (budget 50)
worst load     : 6.0 ms
verdict        : the load has stopped growing
```

The `loaded` column stops at twenty and stays there, and the milliseconds stop climbing. The store is
the same size; the file grew exactly as before. What changed is how much of it comes back.

And here is the break that this fix creates, which is why it is a decision rather than a setting.
**The agent can no longer see turn number one.** If the customer said "my number is 4521" on Monday
and it is Thursday and there have been thirty turns since, that sentence is now outside the window,
and the agent will ask again — or worse, answer as though it had never been told. The limit did not
lose the data; the data is still in the file, and every read is now choosing not to look at it.

That is the trade, stated plainly: **a bounded read means facts must live somewhere other than the
transcript.** Which is [1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md)'s `user:`
scope, and it is [Day 48](../../../day-48-memory-design/LESSON.md)'s entire subject.

## In production

**What a professional writes instead:** they pass a `GetSessionConfig` at the one place sessions are
loaded — for Sutra, beside `session_service()` in `sutra/memory/persistence.py` — rather than at
call sites, so the window is one number in one file with a reason beside it. They choose the number
from the model's context budget rather than from taste (Day 24's
[token accounting](../../../day-24-token-accounting-and-budgets/LESSON.md)), and they write down what
is expected to live in state instead of in the window.

**What degrades at scale:** the distribution, not the average. Most conversations are short and cost
nothing; a small number are enormous, and they are usually the escalated, complicated, important
ones. So the mean load time looks fine while the worst customers get the worst latency, which is
[Day 44's tail](../../../day-44-client-hardening/papers/01-the-tail-at-scale.md) arriving through the
session store. Graph the p99 of session load against transcript length, or you will not see it.

**The failure mode that only appears with real traffic:** it is invisible in testing by
construction. Tests create a session, add three events and assert something. Nobody writes a test
with four hundred turns in it, because it would be slow — and "it would be slow" is the finding.
The first evidence is a support ticket about the desk being sluggish for one customer, which reads
like a network problem.

**The review comment a senior engineer leaves:** *"we load the whole session on every turn and then
use the last few events. That is fine today and it is a curve, not a constant: our oldest tickets
are already over two hundred turns. Set `num_recent_events` where the service is constructed, write
the number's reason next to it, and list what has to move into `user:` state so that a bounded window
is still correct."*

**The interview question:** *"what happens to your agent when a conversation gets very long?"* The
honest answer: *"Loading it gets slower, linearly, because the session service reads every stored
event and deserialises each one into a model before the turn starts. I measured it — one event
loaded in about four milliseconds, four hundred in fifty-four, and the file was under a megabyte, so
it is a read cost and not a storage cost. The fix is a limit pushed into the query, not a slice in
Python: the ADK's `GetSessionConfig(num_recent_events=N)` becomes a `LIMIT` on the events select, and
with twenty the load stopped growing at about six milliseconds. The important half is the
consequence — a bounded window means the agent cannot see the beginning of the conversation any
more, so any fact that must survive has to be written into user-scoped state rather than left in the
transcript. That is a design decision, not a tuning knob."*
