# 7.1 — The backup nobody restored

## One-line answer

Copying the file is not a backup of a live SQLite store — the recent turns are in a side file the
copy leaves behind — and the only way to know is to restore it and read a conversation out, which is
the step every backup routine skips.

## The story

There is a fire extinguisher on the landing between the second and third floors, and it has a small
paper tag hanging off it.

The tag has a table printed on it, with a column for a date and a column for initials. There are
entries on it going back years, in different pens. The extinguisher is red, it is full — you can tell
by the weight — the pin is in, and the tag says somebody looked at it four months ago.

The evening there is a fire in the meter cupboard, a neighbour takes it off the wall, pulls the pin,
squeezes the handle, and a small amount of powder comes out and then nothing. The hose had perished
where it bends. It had been like that for a long time, and it was not visible, and it had no effect
whatsoever on the extinguisher's weight, colour or tag.

Every inspection that was recorded on that tag actually happened. Not one of them was a test.

## The idea in plain language

A store you cannot lose is not the same thing as a store you have a copy of. This part is the
difference, and it has two halves.

**The first half is that copying the file is not enough.** Under write-ahead logging — the mode
[3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md) measured, and the mode most people
switch on — a committed transaction is written to a side file called `<name>-wal`, not to the main
database file. It stays there until a **checkpoint** folds it back in, which happens automatically
after enough pages, and when the last connection to the database closes.

So at any moment while your desk is running, some of your most recent turns are in the `-wal` and not
in the `.sqlite3`. `shutil.copyfile` copies the file you named and nothing else. The copy is a
valid, openable, internally consistent database that is **missing everything since the last
checkpoint**, and it does not tell you: it opens cleanly and answers questions, with less in it.

SQLite gives you the right tool, and it is one statement:

```
VACUUM INTO 'backup.sqlite3'
```

It takes a read lock, walks the whole database as it currently is — main file plus write-ahead log —
and writes a fresh, compacted, standalone copy. It does **not** take the exclusive lock that a plain
`VACUUM` takes, which is
[3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md)'s outage, so it can run while the desk
is serving.

**The second half is that a copy nobody has opened is not a backup.** This is the part that is not
about SQLite at all. The failures in [5.1](../05-shape-and-size/5.1-the-store-the-code-cannot-read.md)
and [5.2](../05-shape-and-size/5.2-the-migration-that-passed.md) both produced files that existed,
had the right size, had the right number of rows, and were useless. Every one of them would pass a
backup routine that checks the file exists. The only check that catches all three is the same one:
**open the copy and read a conversation out of it, through the same code the application uses.**

## Why Sutra needs it

Because this is the last part of the day, and the day has been an argument that runs in one
direction.

[1.1](../01-what-restart-costs/1.1-the-book-under-the-shutter.md) made the sessions survive a
restart. [3.1](../03-writes-that-survive/3.1-the-ticket-torn-in-two.md) made each write survive a
crash. [4.1](../04-two-workers/4.1-refused-not-overwritten.md) made concurrent writers survive each
other. Every one of those hardened the store against something.

None of them hardens the store against *itself*. A file can be deleted by a script with a wrong path
([2.3](../02-reaching-the-service/2.3-the-url-that-names-a-file.md)), emptied by a migration
([5.2](../05-shape-and-size/5.2-the-migration-that-passed.md)), refused by an upgraded library
([5.1](../05-shape-and-size/5.1-the-store-the-code-cannot-read.md)), or over-deleted by an erasure
([6.1](../06-forgetting-on-purpose/6.1-delete-the-session-keep-the-customer.md)). Durability against
a crash is not durability against a mistake, and only a second copy is.

For Sutra this stays deliberately small. `SESSION_DB` is a path
([2.4](../02-reaching-the-service/2.4-handing-the-runner-a-store.md)), so a backup is one statement
against it, and the restore drill is a script that opens the copy with `session_service()` pointed at
a different path and asserts that a known conversation comes back. That is the whole commitment, and
it is the answer to the question a design review will ask after every other question in this day has
been answered: *and if the file goes?*

It also closes the loop with [2.5](../02-reaching-the-service/2.5-the-lounge-you-cannot-enter.md).
"No storage to operate" is what the managed service sells, and the honest price of the file is
exactly this part — one statement, one drill, and remembering to do them.

## The mechanism

Two hundred turns, a backup taken while a reader is still on the store, and a restore that reads.

```python
# days/day-47-persistent-sessions/lab/backup.py  (extract)
def take_backup(vacuum: bool) -> None:
    """Take the backup while the store is open and nothing has been checkpointed."""
    wipe(RESTORED)
    if not vacuum:
        shutil.copyfile(DB, RESTORED)
        return
    conn = sqlite3.connect(DB)
    try:
        conn.execute("VACUUM INTO ?", (str(RESTORED),))
    finally:
        conn.close()
```

**Line by line:**

- `shutil.copyfile(DB, RESTORED)` copies **one path**. Nothing here is wrong as Python; it is wrong
  as a backup, and the two are hard to tell apart in review because the second one is not visible in
  the code at all. What is missing is `DB + "-wal"`, and copying that too would be a different bug —
  a `-wal` copied a moment after its main file is a mismatched pair.
- `wipe(RESTORED)` first, removing the destination and its own side files. `VACUUM INTO` **fails** if
  the target exists, which is deliberate on SQLite's part: a backup command that silently overwrites
  is one that can destroy last night's good copy with this morning's bad one.
- `VACUUM INTO ?` takes the destination as a bound parameter, which is unusual for a filename and is
  supported here. It means the path is not interpolated into SQL, so a directory name containing a
  quote is a non-event.
- The connection is a plain `sqlite3.connect` with no pragmas. `VACUUM INTO` reads inside its own
  read transaction and produces a consistent snapshot of the database as of that moment, so nothing
  needs to be stopped and no lock needs to be taken by hand.
- `try/finally` around the statement, so the connection closes even if the vacuum raises — and it can
  raise, for a full disk or an existing target. A leaked connection here would keep the *source*
  store's write-ahead log from being checkpointed, which is the very condition this part is about.

Why the copy is short, and what makes it deterministic in a lab:

```python
# days/day-47-persistent-sessions/lab/backup.py  (extract)
reader = sqlite3.connect(DB)
reader.execute("PRAGMA journal_mode=WAL")

svc = SqliteSessionService(db_path=f"sqlite:///{DB.as_posix()}")
session = await svc.create_session(app_name=APP, user_id=USER, session_id=SESSION)
reader.execute("BEGIN")
reader.execute("SELECT COUNT(*) FROM events").fetchone()
```

**Line by line:**

- `PRAGMA journal_mode=WAL` is a **persistent** property of the file: set once, and every later
  connection uses it. That is why one line here changes the behaviour of the session service, which
  sets no journal mode of its own ([3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md)).
- The `reader` connection stands in for the other process that is always there on a live system — a
  report, a dashboard, a second instance. SQLite checkpoints the write-ahead log when the **last**
  connection to a file closes, so an open reader is what keeps the recent turns in the side file.
- `BEGIN` followed by a read starts a read transaction and holds it. A connection that has merely
  been opened has not yet joined the write-ahead protocol; it has to actually read for the effect to
  be reliable, which is why the `SELECT COUNT(*)` is there and is not decoration.
- The read happens **after** `create_session`, because the `events` table does not exist until the
  service creates the schema on its first operation
  ([2.1](../02-reaching-the-service/2.1-the-class-that-is-not-exported.md)).
- `.fetchone()` and not just `execute`. A cursor with unread rows is not the same as a completed
  read, and the point of this line is that a read actually happened.
- Nothing about this is a trick to make the lab fail. It is the ordinary state of a running system;
  the lab only makes it happen at a moment you choose rather than at a moment you do not.

And the step that is the whole point:

```python
# days/day-47-persistent-sessions/lab/backup.py  (extract)
async def restore() -> int:
    """Open the backup as a session store and read the conversation back."""
    svc = SqliteSessionService(db_path=f"sqlite:///{RESTORED.as_posix()}")
    session = await svc.get_session(app_name=APP, user_id=USER, session_id=SESSION)
    return 0 if session is None else len(session.events)
```

**Line by line:**

- The backup is opened with `SqliteSessionService`, **the same class the desk uses**, not with a raw
  `sqlite3` connection. That is what makes this a restore drill rather than a file inspection: it
  exercises the schema check from
  [5.1](../05-shape-and-size/5.1-the-store-the-code-cannot-read.md), the JSON deserialisation from
  [5.3](../05-shape-and-size/5.3-the-session-that-never-ended.md), and the state merge from
  [1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md), all of which can fail on a file
  that opens perfectly.
- `session is None` is handled explicitly, because a store that opens and has no such session is the
  outcome a naive check reads as success —
  [1.1](../01-what-restart-costs/1.1-the-book-under-the-shutter.md)'s `None` again, in the last part
  of the day.
- The function returns a **count**, not a boolean. "The backup restored" and "the backup restored 200
  of 200 turns" are different claims, and only the second one is checkable.
- It is `async` and awaited by the caller, like every other session operation, so the drill runs
  through exactly the code path a request would.
- Nothing is asserted in here. The comparison against `TURNS` is done by the caller and turned into
  an exit code, so this function can be reused by a script that wants the number for a log line.

## When it breaks

The copy arm, run on 2026-09-05:

```text
arm             : shutil.copyfile
turns written   : 200
store bytes     : 36864
-wal bytes      : 2360792
backup bytes    : 135168
turns restored  : 0
turns lost      : 200
verdict         : the backup opened and is short
exit: 1
```

Look at the three sizes. The main file is 36 864 bytes — the same as an empty store from
[1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md), because essentially nothing has been
folded into it. The write-ahead log is 2.3 **megabytes**, and it holds the entire conversation. The
backup is a copy of the small one.

`turns restored : 0`. Not a truncated conversation, not a corrupted file, not an exception — the
session was created and its turns were appended after the reader took its snapshot, so the copy holds
a store in which this conversation does not exist. `get_session` returned `None`, exactly as it does
for a session id nobody ever used.

**Nothing failed.** The copy succeeded. The file exists, is the right kind of file, opens with the
session service without a murmur, and has a plausible size. A backup routine that checks the file
exists and is non-empty passes this. So does one that runs an integrity check, because the file is
perfectly intact — it is intact and it is not your data.

The `--vacuum` arm, same script, same reader still holding the store open:

```text
arm             : --vacuum (VACUUM INTO)
turns written   : 200
store bytes     : 36864
-wal bytes      : 2463792
backup bytes    : 135168
turns restored  : 200
turns lost      : 0
verdict         : the conversation came back
exit: 0
```

Two hundred of two hundred. The backup is 135 168 bytes — bigger than the main file it was made from,
because it contains what the main file did not.

Two details worth noticing. The `-wal` is *larger* in this arm, because `VACUUM INTO` reads through
the same store and its own transaction lands there too; a backup is not free and it is not
invisible. And the backup is a compacted copy rather than a byte-for-byte one, so its size will never
match the source — which rules out the other check people write, comparing file sizes.

## In production

**What a professional writes instead:** a backup command that ends in a restore. `VACUUM INTO` to a
dated filename, then open that file with the application's own session service and read a known
session out of it, then and only then rotate the old copies. The exit code is on the read, not on the
copy. For a bigger store the same drill runs less often against the whole thing and always against
the newest copy, because a copy that has never been opened is a copy whose status is unknown.

**What degrades at scale:** the drill stops being cheap. `VACUUM INTO` reads the whole database, so
the cost is proportional to the store, and at some size the daily copy is no longer daily. That is
the point at which the answer changes shape — a replica the writes stream to, or a database server
with continuous archiving — and it arrives sooner than the write-rate ceiling from
[3.3](../03-writes-that-survive/3.3-the-pragma-nobody-set.md) does. Backup cost, not throughput, is
usually what pushes a file-backed store onto a server.

**The failure mode that only appears with real traffic:** the backup that only fails on a busy day.
On a quiet system the write-ahead log gets checkpointed frequently and copying the file gets almost
everything, so the naive backup looks fine for months and its gaps are invisible. Under load,
checkpoints fall behind and long-running readers keep the log alive, so the gap grows — and the day
you actually need the backup is a day the system was busy. The failure is anti-correlated with the
testing.

**The review comment a senior engineer leaves:** *"the nightly job copies `sessions.sqlite3` to
object storage and reports success on the exit code of the copy. We run in WAL mode, so that copy is
missing everything since the last checkpoint, and it will open without complaining. Use `VACUUM
INTO`, and make the job's last step open the copy with our own session service and read one known
conversation out of it — if that read is not in the job, we do not have backups, we have files."*

**The interview question:** *"how do you back up a SQLite database that is being written to?"* The
honest answer: *"Not with a file copy. In write-ahead logging mode the recent commits live in the
`-wal` side file until a checkpoint, so copying the main file gives you a database that opens
cleanly and is missing everything since the last one. I measured that: two hundred turns written, a
copy taken while a reader held the store open, and the restored copy had zero of them — the main file
was 36 kilobytes and the write-ahead log was 2.3 megabytes. The right tool is `VACUUM INTO`, which
takes only a read lock, so it runs while the service is serving, and produces a standalone
compacted copy — that one restored all two hundred. And the copy is only half of it: the backup job
has to end by opening the copy with the application's own code and reading a known conversation out,
because a file that exists and has a plausible size passes every other check and can still be empty,
stale or in a schema the current library refuses."*
