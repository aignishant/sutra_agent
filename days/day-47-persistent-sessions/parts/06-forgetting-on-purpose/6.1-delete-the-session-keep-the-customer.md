# 6.1 — Delete the session, keep the customer

## One-line answer

`delete_session` removes one conversation and, through a cascade, its turns — and it does not touch
the customer's `user:` state, because user state is *defined* as outliving conversations, so a loop
that deletes every session a person had leaves the person behind.

## The story

You change mobile operators, and the number goes with you.

The old connection ends. The bills stop, the SIM in the drawer will never work again, and as far as
you are concerned you have left. You have. That relationship is over.

Four months later your phone rings and it is them. A recorded voice, then a person, with an offer for
a new connection at a good rate, and they know your name, and they know which plan you used to be on,
and they know roughly what you used to spend.

Nobody has done anything sneaky. The **connection** was closed, properly, on the day you asked. What
was never closed is the file with your name on it, because that file was never part of the
connection. It was the thing the connections hung off. Closing one of them was never going to touch
it, and nobody at the counter said so, because from where they were standing you had asked about a
connection.

## The idea in plain language

Somebody writes in and asks you to delete their data. It is an ordinary request, and increasingly a
legal one.

The obvious implementation is four lines:

```
for session in await svc.list_sessions(app_name=APP, user_id=USER):
    await svc.delete_session(app_name=APP, user_id=USER, session_id=session.id)
```

It works. It removes every conversation that customer ever had, and every turn inside them. It is
also incomplete, and it is incomplete by design rather than by oversight.

Recall [1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md): a state key's prefix decides
which table it lands in. A key with no prefix goes into the `sessions` row. A `user:` key goes into
`user_states`, a table keyed on `(app_name, user_id)` **with no session in the key at all**. That is
the definition of user scope — it outlives any one conversation. It is the entire reason the table
exists.

So `delete_session` cannot touch it. Deleting a conversation is not evidence that the customer is
gone; they may have thirty other conversations, and the whole point of `user:tier` is that it is
still true in the next one.

Which means **the operation "erase this customer" is not in the API.** `BaseSessionService` offers
`create_session`, `get_session`, `list_sessions`, `delete_session`, `get_user_state`, `append_event`
and `flush`. There is no `delete_user`. Nothing there removes a `user_states` row, and nothing there
removes an `app_states` row either.

That is not a bug in the ADK. A framework that does not know your retention policy should not guess
at it. But it does mean the last statement of your erasure path is one you write yourself, against
the schema, and the moment you are writing SQL against a store the framework owns you have taken on
[1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md)'s obligations: the transaction, the
pragma, and knowing exactly which tables exist.

## Why Sutra needs it

Because the repository goes public in Phase 14 and the desk handles customer text, so "can you
actually remove somebody?" is a question Sutra has to be able to answer with a command rather than
an intention.

This part is where `sutra/memory/persistence.py` gets its second public symbol. Alongside
`session_service()` from [2.4](../02-reaching-the-service/2.4-handing-the-runner-a-store.md), the
module gets `purge_user(app_name, user_id)`, and the day's gate asserts it: create a session with a
`user:` key in it, call `purge_user`, then check that `list_sessions` is empty **and**
`get_user_state` is empty. Two checks, because one of them passes with the incomplete
implementation.

It also settles a boundary with the next day.
[Day 48](../../../day-48-memory-design/LESSON.md) is about what is worth remembering, and its
[4.3](../../../day-48-memory-design/parts/04-privacy-and-erasure/4.3-erasure-is-an-obligation.md)
is about erasure as an obligation across everything Sutra stores. Today's half is narrower and
concrete: the session store specifically, the four tables it holds, and which of them the API can
reach. Day 48 cannot design a retention rule for a store nobody can empty.

## The mechanism

Delete every session the customer has, then count what is left, everywhere.

```python
# days/day-47-persistent-sessions/lab/forget.py  (extract)
listed = await svc.list_sessions(app_name=APP, user_id=USER)
for session in listed.sessions:
    await svc.delete_session(app_name=APP, user_id=USER, session_id=session.id)
```

**Line by line:**

- `list_sessions` returns a `ListSessionsResponse`, not a list, so the sessions are on
  `.sessions`. Iterating the response object directly is a `TypeError`, and it is the first thing
  everybody gets wrong here.
- The sessions it returns carry **no events** — `events=[]` in the constructor — because listing is a
  catalogue operation and loading four hundred turns per row would make it useless
  ([5.3](../05-shape-and-size/5.3-the-session-that-never-ended.md)). That is fine for deletion, which
  needs the ids and nothing else.
- `user_id` is optional on `list_sessions`; omit it and you get every session in the app. Passing it
  is what makes this one customer's erasure rather than everybody's, and it is one keyword away from
  a catastrophe.
- The loop deletes one at a time, each in its own transaction. There is no bulk delete on the
  interface, so an interruption halfway leaves some conversations gone and some present — recoverable
  by running it again, which is worth checking is true before you rely on it.
- Listing and then deleting is a read followed by writes, with a gap: a conversation started between
  the two is not in the list and is not deleted.
  [4.2](../04-two-workers/4.2-the-read-that-raises-nothing.md) is that gap, arriving in the erasure
  path, and the practical answer is to stop the customer from being served before you erase them and
  to re-run the count afterwards.

What `delete_session` actually runs, and the pragma that makes it enough:

```sql
-- from sqlite_session_service.delete_session, in full
DELETE FROM sessions WHERE app_name=? AND user_id=? AND id=?;
```

**Line by line:**

- One statement, and it names only `sessions`. The events go because of the `ON DELETE CASCADE` on
  the foreign key in [1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md), which is the
  database doing the second delete rather than a Python loop that can be interrupted between rows.
- The cascade only fires because the service issues `PRAGMA foreign_keys = ON` on every connection
  it opens. **Your own connection to the same file does not inherit that.** A hand-run
  `DELETE FROM sessions` from `sqlite3` leaves the events, still holding the customer's words,
  pointing at a session that no longer exists.
- All three key columns are in the `WHERE`, so a session id that belongs to a different customer is
  not matched. This is why the primary key is the triple: a stolen or guessed session id alone
  deletes nothing.
- Deleting a session that does not exist affects zero rows and **raises nothing**. So a deletion loop
  cannot tell you whether it deleted anything, which is why the verification below counts rather than
  trusting the call.
- There is no `user_states` in this statement and there is no second statement. That is the whole
  subject of this part, visible in one line of SQL.

The statement the interface does not offer:

```sql
-- the one BaseSessionService has no method for
DELETE FROM user_states WHERE app_name=? AND user_id=?;
```

**Line by line:**

- Two columns, because that is the whole primary key of `user_states`
  ([1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md)). There is no session component
  to supply, which is exactly why no session-scoped method can reach this row.
- It goes inside `BEGIN IMMEDIATE ... COMMIT` with the session deletions if you want the erasure to
  be one indivisible act, which you do:
  [3.1](../03-writes-that-survive/3.1-the-ticket-torn-in-two.md)'s rule is that statements which must
  be true together go in one transaction, and "the customer is gone" is one fact.
- `app_states` is deliberately **not** in the erasure path. It holds one row for the whole
  application, shared by every customer, so deleting it during one person's erasure would remove
  everybody's application state. If personal data has reached `app_states`, the fix is upstream in
  what gets written there, not in the deletion.
- Whether this belongs in `persistence.py` at all is a real question, and the answer here is yes: it
  is the one module that already knows the store's shape, so it is the only place where a raw
  `DELETE` against ADK's schema is not a surprise.

## When it breaks

Two customers, three conversations. Erase one of them the way the API allows, on 2026-09-05:

```text
deleted 2 sessions for 'asha'

table                     before   after
sessions                       2       0
events                         2       0
user_states                    1       1
other users' sessions          1       1

arm            : delete_session only
rows left for 'asha': 1
other customers intact: True
verdict        : the customer is still in the file
exit: 1
```

Read the `user_states` row: **1 before, 1 after.** Everything else went. Two sessions and two events,
including the cascade, exactly as advertised. And a row holding `{"phone": "+91 90000 11223"}` is
sitting in the file after an operation whose name is *delete*.

Nothing raised. `delete_session` returns `None` and it returned `None` twice, successfully, and it
did precisely what it says. Somebody reading the code — a loop over `list_sessions` calling
`delete_session` — would review it as a complete erasure, because it names both of the concepts the
API has.

The thing that makes this dangerous rather than merely incomplete is that the answer you give is
*checkable by somebody else*. You told a customer their data was removed. The data is in a file, and
a regulator, an auditor or a curious engineer can open that file with `sqlite3` and find their phone
number in it. There is no version of that conversation that goes well.

Now the same run with the one statement the API does not give you:

```text
deleted 2 sessions for 'asha'
deleted the user_states row too

table                     before   after
sessions                       2       0
events                         2       0
user_states                    1       0
other users' sessions          1       1

arm            : --purge
rows left for 'asha': 0
other customers intact: True
verdict        : nothing of the customer remains
exit: 0
```

Zeros across the three tables that mentioned this customer, and `other users' sessions` still at 1 —
which is the check that matters just as much. **An erasure that is too broad is a different
incident, not a safer one**, and the only way to know is to count somebody else's rows before and
after.

Note what the verification is: four `SELECT COUNT(*)` statements against the file, not a return value
from the API. The API's own answer to "did it work" is silence.

## In production

**What a professional writes instead:** `purge_user` as one function, one transaction, all the
statements, and a **count returned** rather than nothing — so the caller can log *how many rows were
removed for this customer* and put that number in the record of the request. They also run the count
again afterwards, from a separate connection, because a function that reports on its own work is not
evidence.

**What degrades at scale:** erasure has to reach every copy, and by the time a system is real there
are copies — a backup ([7.1](../07-in-production/7.1-the-backup-nobody-restored.md)), a replica, an
export somebody made for a report, a log file that recorded the customer's message on the way in.
Deleting from the live store is the easy one. The honest version of "we can erase a customer" is a
written list of every place their words land, and that list is a design artefact, not a script.

**The failure mode that only appears with real traffic:** the conversation started during the
erasure. `list_sessions` returns a snapshot; the customer sends one more message while the loop is
running; that session is created after the list and survives the purge. It is one row, it is
invisible, and it will be found by whoever next opens the store — which, when the reason for the
erasure was a complaint, is likely to be somebody official.

**The review comment a senior engineer leaves:** *"this erasure loops over `list_sessions` and calls
`delete_session`, which is the whole of the API and about eighty per cent of the job. User-scoped
state lives in its own table keyed on app and user with no session in the key, so it survives every
one of those deletes — that is where we put the phone number. Add the `user_states` delete, put the
whole thing in one `BEGIN IMMEDIATE`, and return a row count so the audit record has a number in
it."*

**The interview question:** *"a customer asks you to delete their data. What do you actually run?"*
The honest answer: *"More than the framework gives me. The session service has `delete_session`,
which removes the conversation row and cascades to its events, and looping that over
`list_sessions` looks like a complete erasure. It is not, because user-scoped state is a separate
table keyed on application and user with no session in the key — that is what `user:` *means*, it
outlives conversations — so there is no session-scoped method that can reach it, and there is no
`delete_user` on the interface. I proved it by counting: two sessions and two events gone, the
`user_states` row still there with the phone number in it, and no error anywhere. So the last
statement is one I write, inside the same transaction, and I verify by counting rows in the file
afterwards rather than by trusting a return value — including a count of *other* customers' rows,
because an erasure that took too much is a different incident. And the live store is only the first
copy; backups and exports need the same list."*
