# 6.2 — 💥 A store in a public repository

## One-line answer

The file this day taught you to create is a plain-text archive of everything customers typed, it
appears in your working tree the first time you run anything, and the only thing standing between it
and a public repository is two lines in `.gitignore` that you should verify by asking git rather
than by reading them.

## The story

The office replaces its computers, which is a good day for everybody.

The old ones go into a corner and eventually a dealer takes them away for a small amount of money.
Before they go, somebody sensible deletes the files: the shared folder, the desktop, the downloads,
the recycle bin emptied. It takes a while and it is done properly.

Some months later a person who bought one of those machines runs a recovery tool on the disk, the way
people do when they buy a second-hand disk, and finds three years of quotations, a spreadsheet of
customer phone numbers, and a folder of scanned identity documents.

Nobody in that office was careless in the way the word usually means. They deleted the files. What
they did not know is that deleting a file removes the entry that points at it and leaves the bytes
where they were, and that the disk was the thing being sold rather than the computer.

The mistake was not the deletion. It was believing that the deletion was the last step.

## The idea in plain language

Look at what is actually in the file you have been building all day.

`events.event_data` holds every sentence anybody typed, verbatim, as JSON text
([1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md)). `sessions.state` and
`user_states.state` hold whatever the agent wrote down — a phone number, an order id, an address,
whatever the tool put there. `sessions.user_id` is the customer's identity, in a column, one row per
conversation. None of it is encrypted, none of it is hashed, and all of it is readable by anybody
with `sqlite3` and the file, which is the property
[1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md) sold you as a *feature*.

It is still a feature. It is also the reason this part exists, because the same file is now sitting
in the repository's working tree, and this repository goes public in Phase 14.

**Principle 9 says secrets never touch git.** The usual reading is API keys, and this file is not a
secret in that sense — it holds no credential. It is worse in a different way. A leaked key is
revoked in a minute and the damage stops. A leaked transcript cannot be revoked, cannot be
un-published, and is not yours to forgive: it belongs to the people who typed it.

Two lines in `.gitignore` cover it:

```
*.db
*.sqlite3
```

And there is a third thing worth knowing, which is that `.gitignore` **only applies to files git is
not already tracking**. Add the line after you have committed the file once and git carries on
tracking it, ignoring your ignore rule, because the rule is about untracked files. The file has to be
removed from the index — and even then it is in the history, which is a different and much harder
problem.

The habit this part is really about is smaller than any of that: **do not read `.gitignore` and
conclude. Ask git.** `git check-ignore -v <path>` answers with the file and line number of the rule
that matched, or exits non-zero if nothing matched. It knows about the global ignore file, the
repository's `.git/info/exclude`, negation rules and precedence, and you do not.

## Why Sutra needs it

Because the store's path is a decision `sutra/memory/persistence.py` makes and the gate checks it.

[2.4](../02-reaching-the-service/2.4-handing-the-runner-a-store.md) put `SESSION_DB` at
`<repo>/data/sessions.sqlite3`, inside the tree, on purpose: a path inside the repository is one
`.gitignore` can protect and one a developer can find. The alternative —
[2.3](../02-reaching-the-service/2.3-the-url-that-names-a-file.md)'s four-slash form pointing
somewhere outside the tree — escapes `.gitignore` entirely and also escapes every backup that covers
the project, which trades one problem for two.

So the day's gate asserts it, with git rather than with a string match:

> `git check-ignore -q <SESSION_DB>` must exit 0, or the finding reads *"the session store … is not
> ignored by git (Principle 9)"*.

That check is worth more than it looks, because it is the one that survives somebody moving the
store. Rename `data/` to `var/`, put it under `sutra/`, point it at a temporary directory — the
check keeps working, because it asks about the actual resolved path rather than about the line
somebody wrote a year ago.

It also gives [Day 48](../../../day-48-memory-design/LESSON.md) something to build on. Day 48's
[4.4](../../../day-48-memory-design/parts/04-privacy-and-erasure/4.4-the-store-that-must-not-be-committed.md)
is the same problem for the memory store; today's is the session store, which is bigger, more
verbatim and created earlier.

## The mechanism

Open a store and describe it the way a privacy review would, then ask git what it thinks.

```python
# days/day-47-persistent-sessions/lab/leak.py  (extract)
EMAIL = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")
PHONE = re.compile(r"\+?\d[\d\s-]{7,}\d")


def git_ignores(path: Path) -> tuple[bool, str]:
    """Ask git itself, rather than reading .gitignore and guessing."""
    done = subprocess.run(
        ["git", "check-ignore", "-v", str(path)], capture_output=True, text=True, check=False
    )
    return done.returncode == 0, done.stdout.strip() or "(not ignored by any rule)"
```

**Line by line:**

- The two regular expressions are **deliberately crude**. They will match things that are not phone
  numbers and miss things that are. That is the right calibration for this job: the output is a
  prompt to look, not a classification, and a detector tuned to be precise would give a comforting
  zero on a store full of addresses it was not taught about.
- `PHONE` requires at least nine digits with separators allowed, which is why it also matches a long
  order number. A false positive here costs a glance; a false negative costs a customer's number in
  a public repository.
- `git check-ignore -v` prints `<ignore-file>:<line>:<pattern>\t<path>` for a match. The `-v` is the
  difference between "yes" and "yes, because of this rule, on this line" — and the second one is what
  lets you tell an intentional rule from an accidental one.
- `returncode == 0` is the answer. `check-ignore` exits 0 when the path is ignored, 1 when it is not,
  and 128 on a real error, so `check=False` is required: `check=True` would raise on the ordinary
  "not ignored" case, which is the case you most need reported.
- Shelling out to git rather than parsing `.gitignore` is the whole point of the function, and the
  docstring says so. Precedence, negation with `!`, the global ignore file and
  `.git/info/exclude` are all in git's answer and none of them are in the file you would have read.
- `subprocess.run` with a **list**, never a string with `shell=True`. The path may contain spaces —
  on this machine it certainly does — and a shell would split it.

What the report counts, and why it counts state as well as text:

```python
# days/day-47-persistent-sessions/lab/leak.py  (extract)
said = texts(db)
states = state_blobs(db)
haystack = said + states
with_email = sum(1 for text in haystack if EMAIL.search(text))
risky = bool(haystack) and not ignored
```

**Line by line:**

- `texts` pulls every `part["text"]` out of every event's JSON — the words. `state_blobs` pulls the
  `state` column from `sessions`, `user_states` and `app_states` — the facts the agent wrote down.
  Both are personal data and only one of them is a transcript.
- Reading `state` from all three tables matters because of
  [1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md): a `user:` key is the one most
  likely to hold a durable identifier, and it is in the table
  [6.1](6.1-delete-the-session-keep-the-customer.md) showed surviving deletion.
- `haystack = said + states` is one list because the question is about the file, not about which
  table embarrassed you.
- `risky = bool(haystack) and not ignored` — **both** conditions. An ignored file full of transcripts
  is fine, and so is a tracked file with nothing personal in it. The finding is the intersection, and
  reporting either half alone would train people to skip the check.
- `sum(1 for ...)` counts matching *turns*, not matching addresses. One turn containing three emails
  is one turn to look at.

## When it breaks

Run against one of this day's own stores, on 2026-09-05:

```text
store           : forget.sqlite3  (36864 bytes)
customers       : 1
turns of text   : 1
state documents : 2
looks like email: 1
looks like phone: 1
git check-ignore: .gitignore:34:days/*/lab/	"...\day-47-persistent-sessions\lab\forget.sqlite3"

verdict         : safe
exit: 0
```

Green — and read *why* it is green. The rule that matched is `.gitignore:34:days/*/lab/`, which
ignores the whole lab directory. The rules that were written for exactly this purpose,
`.gitignore:25:*.db` and `.gitignore:26:*.sqlite3`, did not get a chance, because a directory rule
earlier in the file matched first. Point the same script at `data/sessions.sqlite3` and
`git check-ignore -v` answers `.gitignore:26:*.sqlite3` instead.

That is the value of `-v`. **"It is ignored" and "it is ignored for the reason I intended" are
different statements**, and only one of them survives somebody tidying up `.gitignore`.

Now the ablation, which is the state this repository was in before anybody wrote those lines:

```text
store           : forget.sqlite3  (36864 bytes)
customers       : 1
turns of text   : 1
state documents : 2
looks like email: 1
looks like phone: 1
git check-ignore: (ablation: pretending .gitignore says nothing)

verdict         : a store of customer words is trackable
exit: 1
```

Identical file, identical contents, opposite verdict. Nothing about the data changed; one line of
configuration did.

And now the failure that the exit code cannot see. Suppose the line had been missing for a week and
somebody ran `git add -A`. The store is now tracked. Adding `*.sqlite3` to `.gitignore` afterwards
changes **nothing** — the rule applies to untracked files, and git carries on staging every change to
a file it is already tracking. `git status` will keep showing it, and the person who added the ignore
rule will assume the file is showing up for some other reason.

Removing it from the index with `git rm --cached` fixes the working tree and does not fix the
history: every commit that contained it still contains it, and every clone and every fork has a copy.
The only real remedy is rewriting history, which means every collaborator re-cloning — and if the
repository was public in the meantime, it means telling the people whose words those were.

**The check is cheap and it has to happen before the first commit, because after it there is no
cheap version.**

## In production

**What a professional writes instead:** they make it impossible rather than remembered. The store
lives in one directory that is ignored as a directory rather than by extension, so a file with an
unexpected name is covered too. The gate that runs before every commit asks `git check-ignore` about
the resolved store path, so the check follows the file if it moves. And in a real deployment the
store is not in the repository tree at all — it is on a mounted volume named by an absolute path from
configuration ([2.3](../02-reaching-the-service/2.3-the-url-that-names-a-file.md)), which removes the
question rather than answering it.

**What degrades at scale:** the number of copies. The live store is one file and one `.gitignore`
line. Then there is a backup ([7.1](../07-in-production/7.1-the-backup-nobody-restored.md)), a copy
somebody took to debug an incident, a `VACUUM INTO` left in a home directory, a test fixture built
from real data because synthetic data was slow to write. Every one of those is the same content with
none of the protection, and none of them appear in any diff.

**The failure mode that only appears with real traffic:** the test fixture. A store recorded from a
real conversation is enormously useful for a test, so somebody commits `tests/fixtures/session.sqlite3`
— deliberately, with a good reason, in a directory nobody thought to ignore because it is meant to
contain committed files. It passes review because it is a fixture. It is a customer's words, in a
public repository, forever.

**The review comment a senior engineer leaves:** *"the store path is fine and it is ignored, but the
only thing enforcing that is a line in `.gitignore` and my memory of it. Put `git check-ignore -q` on
the resolved `SESSION_DB` into the gate, and while we are here: no fixture under `tests/` may be a
recorded store. If we need a realistic transcript for a test, we generate one."*

**The interview question:** *"what is the risk of a local session store?"* The honest answer:
*"That it is a plain-text archive of everything customers typed, in a file that appears in your
working tree the first time you run anything. It holds no credential, so it does not look like a
secret, and it is worse than one: a leaked key gets revoked, and a leaked transcript cannot be. Two
`.gitignore` lines cover it, and I check them by running `git check-ignore -v` on the resolved path
rather than by reading the file, because that tells me which rule matched and on which line — in our
repository a directory rule matches before the extension rules, which is fine and is not what
anybody assumes. The timing is the part that matters: `.gitignore` does not apply to a file git is
already tracking, so if it was committed once, removing it later fixes the working tree and not the
history, and by then every clone has it."*
