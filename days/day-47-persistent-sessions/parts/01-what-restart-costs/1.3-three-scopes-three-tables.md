# 1.3 — Three scopes, three tables

## One-line answer

The four state prefixes Day 17 taught are not a naming convention: on disk they are three different
tables and one deliberate absence, and `temp:` is absent because absence is what it means.

## The story

You join the library on the corner because it is cheaper than buying books.

Three different pieces of paper govern that afternoon, and they are kept in three different places.
Taped inside the front door is a printed notice: *closed on public holidays, two books at a time,
returns by the 14th*. It is the same notice for everybody, it has been there for years, and no
individual member's business changes a word of it.

In your bag is your **borrower card**, with your name and number on it. It goes with you from visit
to visit. If you lose a book, that is recorded against the card, and it is still recorded against
the card next month.

And on the desk in front of the librarian, right now, is the book you are actually taking home,
with a slip in it. When you walk out, the slip is filed and the desk is clear for the next person.

Same building, same afternoon, three lifetimes. Nobody has to think about which is which, because
they are physically in different places. You could not accidentally write "returns by the 14th" on
your borrower card if you tried; there is no room.

## The idea in plain language

[Day 17](../../../day-17-state-scopes-and-lifetimes/LESSON.md) taught that a key in session state
carries its lifetime in its name:

| You write | It means | Lives as long as |
| --- | --- | --- |
| `draft` | this conversation | the session |
| `user:tier` | this customer | the customer, across every conversation |
| `app:kb_version` | this application | the application |
| `temp:token_estimate` | this invocation | one turn, and no longer |

Day 17 could only assert that, because an in-memory service keeps all four in one dictionary and
strips the prefixes on the way in and out. Today you can check it, because each of the first three
has a table of its own and the fourth has nothing.

The mechanism that does it is called **extracting the state delta**. When you write state, you do
not hand the service a new dictionary — you hand it a **delta**, a small set of keys that changed.
The service sorts that delta by prefix, sends each group to its own table, and throws the `temp:`
group away before anything reaches the disk. On the way back out, `get_session` reads all three
tables, puts the prefixes back on the `user:` and `app:` keys, and merges them into the one
dictionary your agent sees.

So the dictionary your code reads is **assembled**, not stored. Nothing on disk holds the key
`user:tier`; `user_states` holds `tier`, and the prefix is added at read time.

`temp:` is the one that surprises people. It is not "stored somewhere fast" or "stored briefly". It
is applied to the in-memory session so that later agents in the same turn can read it, then
**removed from the event before the event is written**. The turn ends and it is as if it was never
written, because it was never written.

## Why Sutra needs it

Because two of this day's hardest questions are decided by which table a key is in.

[6.1](../06-forgetting-on-purpose/6.1-delete-the-session-keep-the-customer.md) asks what happens
when a customer asks you to erase their data. `delete_session` removes rows from `sessions` and
`events`. It does not touch `user_states`, and it cannot, because user state is *defined* as
outliving any one conversation. So every `user:` key you ever wrote is a row that a deletion loop
walks straight past.

[5.3](../05-shape-and-size/5.3-the-session-that-never-ended.md) asks what to do with a conversation
that has grown too long to load. Part of the answer is that facts you keep re-deriving from the
transcript should have been `user:` keys in the first place — a row you read in one statement rather
than four hundred events you deserialise to work out the same thing.

And [Day 48](../../../day-48-memory-design/LESSON.md) is the whole subject: what is worth
remembering after this conversation ends. That question has no meaning until "after this
conversation ends" corresponds to something physical, and today it does — it is the difference
between the `sessions` row that gets deleted and the `user_states` row that does not.

## The mechanism

One event carrying one key per scope, then a look at where each key physically went.

```python
# days/day-47-persistent-sessions/lab/scopes.py  (extract)
DELTA = {
    "draft": "will send today",  # session scope: this conversation only
    "user:tier": "gold",  # this user, every conversation
    "app:kb_version": "2026-09",  # every user of this app
    "temp:token_estimate": 1240,  # this invocation, never stored
}


async def write_all_four() -> dict[str, object]:
    """One event carrying one key per scope. Returns the merged in-memory state."""
    svc = SqliteSessionService(db_path=f"sqlite:///{DB.as_posix()}")
    session = await svc.create_session(app_name=APP, user_id=USER, session_id=SESSION)
    await svc.append_event(
        session,
        Event(author="triage", invocation_id="inv-1", actions=EventActions(state_delta=DELTA)),
    )
    fresh = await svc.get_session(app_name=APP, user_id=USER, session_id=SESSION)
    return dict(fresh.state)
```

**Line by line:**

- `EventActions(state_delta=...)` is the only supported way to change state. Day 17's
  [6.1](../../../day-17-state-scopes-and-lifetimes/parts/06-failure-lab/6.1-the-write-that-was-never-written.md)
  is the part about what happens when you assign to `session.state` instead: the dictionary in your
  hand changes, nothing reaches the store, and the next read undoes you.
- The event carries `actions` and **no `content`**. That is legal and common. An event whose only
  job is to record a state change has nothing to say to the customer, and it is exactly the event
  shape that makes the `if e.content else []` guard in
  [1.1](1.1-the-book-under-the-shutter.md) necessary.
- `author="triage"` is required on every event. It is who produced it, and it is what lets you read
  a transcript later and tell the customer's words from the agent's.
- The four keys go in **one** delta, in one call. They are not four writes to four tables from your
  side; the split happens inside the service, which is the point — one event either lands whole or
  does not land at all.
- `get_session` is called again rather than reusing `session`, because the returned object is what a
  *different process* would see. Reading the in-memory object you just wrote through would prove
  nothing about the disk.

The split itself, in the service's own SQL:

```sql
-- what the service runs for a user: key, from sqlite_session_service.py
INSERT INTO user_states (app_name, user_id, state, update_time) VALUES (?, ?, ?, ?)
ON CONFLICT(app_name, user_id)
DO UPDATE SET state = json_patch(state, excluded.state), update_time = excluded.update_time;
```

**Line by line:**

- `INSERT ... ON CONFLICT ... DO UPDATE` is an **upsert**: insert the row, and if one with that key
  already exists, update it instead. Without it the service would need a `SELECT` to find out which
  statement to run, and that gap between the read and the write is exactly the lost update
  [Day 43's 4.2](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md)
  measured. One statement has no gap.
- `json_patch(state, excluded.state)` merges the new keys into the stored JSON document rather than
  replacing it. `excluded` is SQLite's name for the row that the `INSERT` *would* have written. So
  a delta of one key changes one key, and the other twenty in that customer's state are untouched by
  a statement that never read them.
- `json_patch` follows the JSON Merge Patch rule that a `null` value **deletes** the key. That is
  the supported way to remove something from state, and it is also a live trap: writing
  `{"user:tier": None}` because a lookup failed does not store "unknown", it erases the tier.
- `update_time = excluded.update_time` copies through the timestamp the service passed in, which is
  the event's own timestamp — not the database's clock. Whose clock it is matters when two machines
  disagree, which is
  [Day 22's paper](../../../day-22-structured-logging/papers/01-time-clocks-ordering.md).
- The `sessions` and `app_states` writes are the same statement with a different key. There is no
  fourth statement, because there is no fourth table.

## When it breaks

The script writes the four keys and then reads the tables directly. Every line below is real output:

```text
what get_session() gives you back:
  app:kb_version       '2026-09'
  draft                'will send today'
  user:tier            'gold'

where each key physically is:
  sessions.state       {'draft': 'will send today'}
  user_states.state    {'tier': 'gold'}
  app_states.state     {'kb_version': '2026-09'}

  [ok] session key in sessions.state
  [ok] user: key in user_states, unprefixed
  [ok] app: key in app_states, unprefixed
  [ok] user: key re-prefixed on read
  [ok] temp: key in no table
  [ok] temp: key not in the reloaded session

failures: 0
```

Three keys came back out of four. `temp:token_estimate` is in no table and in no reloaded session,
and no error was raised when it was written.

That silence is the break. Consider a plausible mistake: a tool computes an expensive summary, puts
it in `temp:summary` because the name sounded like a cache, and a later part of the same turn reads
it happily. Every test passes, because a test runs one turn. In production the next turn recomputes
it, and the turn after that, and the only symptom is a bill and a latency profile that nobody can
explain from the code, because the code does contain a cache — one that is emptied between every
turn by design.

The mirror-image mistake is worse and more common. A key that should have been `temp:` is written
without the prefix, so a working note — a half-formed plan, a raw tool response, a customer's card
number read out to be checked — goes into `sessions.state` and stays there. It is now in a file, in
a backup, and in whatever
[6.2](../06-forgetting-on-purpose/6.2-a-store-in-a-public-repo.md) is about. `temp:` is the only
prefix whose whole purpose is to *not* end up on a disk, and forgetting it is a data-retention
decision made by a typo.

## In production

**What a professional writes instead:** the prefixes are not scattered as string literals through
the codebase. They are named constants in one module, with a comment per constant saying which
lifetime it is and why, so that a reviewer reading a diff sees `USER_TIER` rather than a string that
might be missing four characters. ADK gives you `State.APP_PREFIX`, `State.USER_PREFIX` and
`State.TEMP_PREFIX` for building them.

**What degrades at scale:** `app_states` has exactly one row per application, and every write to it
from any conversation touches that row. It is a single hot row, which is the bottleneck
[Day 43's 4.2](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md)
described: everything that writes it serialises behind everything else that writes it. App state is
for things that change when you deploy, not things that change when a customer talks. A counter in
`app:` is a design mistake that only shows up under load.

**The failure mode that only appears with real traffic:** `user_states` is keyed on
`(app_name, user_id)` with no session in it, so two conversations by the same customer at the same
time write to the same row. `json_patch` makes that safe key-by-key, and it does not make it safe
*decision*-by-decision: if one conversation reads `user:credit`, subtracts, and writes it back
while the other does the same, both merges succeed and one subtraction is gone. The upsert protects
the row's structure, not your arithmetic.

**The review comment a senior engineer leaves:** *"`user:last_ticket_id` gets written on every turn.
That is a write to a shared row for every customer message we handle, and it is a fact we can
already recover by listing that customer's sessions. Move it out of user state, or write it once
when the ticket is created rather than on every turn."*

**The interview question:** *"how does the framework know which state to keep after a conversation
ends?"* The honest answer: *"By the prefix on the key, and it is not a convention — it decides which
table the value is written to. No prefix goes to the session row and dies with the session. `user:`
goes to a per-customer row that outlives every conversation. `app:` goes to a single row for the
whole application. `temp:` is stripped from the event before it is written, so it is readable for
the rest of that turn and is in no table at all. The consequence that catches teams out is
deletion: a loop that deletes every one of a customer's sessions leaves their `user:` row exactly
where it was."*
