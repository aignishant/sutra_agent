# 1.2 — A session is four tables

## One-line answer

Once a session is on disk it is an ordinary SQLite database with four tables — `app_states`,
`user_states`, `sessions` and `events` — that any tool can read without ADK in the room.

## The story

You take a scooter to the repair shop because the front brake is soft.

The man at the counter does not fix it. He writes a **job card**: your name and number at the top,
the registration, today's date, and one line — *front brake soft*. The card goes onto a hook with
the others, and the scooter goes into the yard.

The mechanic who eventually looks at it is not the man who wrote the card. He reads it, does the
work, and adds a line: *pads worn, replaced, bled the line*. Later somebody at the counter reads
both lines to you and adds a third: *paid*.

Three people touched that scooter and none of them talked to each other. The card did all the
talking. And the reason it could is that the card has a fixed shape — a header with who and what,
then a list of lines added in order, each with who added it. Anyone in the shop can pick up any card
and know how to read it, including the man who joins next month.

## The idea in plain language

The last part said the sessions go into a file. This part opens the file.

There is no ADK format, no custom binary, no proprietary anything. There is a **SQLite database**:
one file on disk holding tables, which are exactly what the word suggests — rows and named columns,
queried with SQL. SQLite is not a server you run; it is a library that reads and writes that file
directly, and it ships inside Python as the `sqlite3` module, which is why this whole day costs
nothing to install.

The service creates four tables the first time it touches the file:

| Table | One row per | Holds |
| --- | --- | --- |
| `sessions` | conversation | the session's own state, when it was created, when it was last written |
| `events` | turn | the whole event as a JSON document, plus the ids needed to find it |
| `user_states` | customer, per app | state that outlives any single conversation |
| `app_states` | app | state shared by every customer of that app |

Two of those are the job card. `sessions` is the header — who this conversation belongs to and what
is currently known about it. `events` is the list of lines added in order, each stamped with who
added it and when. The other two tables are the shop's own notes, and they get their own part:
[1.3](1.3-three-scopes-three-tables.md).

The important word for `events` is **append-only**. Nothing rewrites a turn that already happened.
A conversation is not a document that gets edited; it is a list that gets longer. That is why the
column is called `event_data` and holds the entire event as JSON rather than being split into
`author`, `text`, `tool_name` and so on: the shape of an event changes as ADK grows, and a JSON
column can hold a new field without a schema change. It is a deliberate trade — flexibility now, in
exchange for not being able to ask SQL "find every event mentioning the printer" without unpacking
JSON. [5.1](../05-shape-and-size/5.1-the-store-the-code-cannot-read.md) is the day that trade was
made, and what it cost the people who had the old shape.

## Why Sutra needs it

Because a store you cannot open is a store you cannot debug, back up, or answer a question about.

Three concrete moments in this day depend on the file being readable by ordinary tools:

- [4.1](../04-two-workers/4.1-refused-not-overwritten.md) explains a refusal by reading the
  `update_time` column, which is a fact about a row and not a fact about ADK.
- [5.2](../05-shape-and-size/5.2-the-migration-that-passed.md) loses a thousand conversations in a
  migration whose row counts all match, and the only way to see it is to look at what is *in* the
  rows.
- [6.1](../06-forgetting-on-purpose/6.1-delete-the-session-keep-the-customer.md) answers "is this
  customer really gone?" with four `SELECT COUNT(*)` statements, because the API's own answer is
  incomplete.

It also settles a question that comes up in every design review: *what have we actually committed
to?* The answer is "a documented SQLite schema", which is a much smaller commitment than "a
framework's internal storage", and it is why moving to a different store later is a data migration
rather than an archaeology project.

## The mechanism

Write one small conversation through the service, then open the same file with plain `sqlite3` and
ask it what is there.

```python
# days/day-47-persistent-sessions/lab/tables.py  (extract)
def show_schema(conn: sqlite3.Connection) -> None:
    """Every table the service created, and the columns it chose."""
    print("=== tables ===")
    for (name,) in conn.execute(
        "SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%' ORDER BY name"
    ):
        columns = [row[1] for row in conn.execute(f"PRAGMA table_info({name})")]
        print(f"{name:<12} {', '.join(columns)}")
```

**Line by line:**

- `sqlite_master` is SQLite's own catalogue: one row per table, index, view and trigger in the file.
  Reading it is how you find out what a database contains when nobody has told you.
- `name NOT LIKE 'sqlite_%'` hides SQLite's internal bookkeeping tables, which exist in every
  database and are not yours.
- `PRAGMA table_info(<table>)` returns one row per column; index `1` of each row is the column name.
  A `PRAGMA` is SQLite's way of asking a question about the database rather than about the data.
- The f-string interpolating `name` into the SQL is safe **only** because `name` came out of
  `sqlite_master` a moment ago. Table names cannot be bound as parameters in SQL, so this is the
  one place interpolation is unavoidable — and the rule that keeps it honest is that the value must
  come from the database itself, never from a caller.

The four tables the service created, and one event row laid out:

```sql
-- the schema SqliteSessionService creates on first use
CREATE TABLE IF NOT EXISTS sessions (
    app_name TEXT NOT NULL,
    user_id TEXT NOT NULL,
    id TEXT NOT NULL,
    state TEXT NOT NULL,
    create_time REAL NOT NULL,
    update_time REAL NOT NULL,
    PRIMARY KEY (app_name, user_id, id)
);
CREATE TABLE IF NOT EXISTS events (
    id TEXT NOT NULL,
    app_name TEXT NOT NULL,
    user_id TEXT NOT NULL,
    session_id TEXT NOT NULL,
    invocation_id TEXT NOT NULL,
    timestamp REAL NOT NULL,
    event_data TEXT NOT NULL,
    PRIMARY KEY (app_name, user_id, session_id, id),
    FOREIGN KEY (app_name, user_id, session_id) REFERENCES sessions(app_name, user_id, id) ON DELETE CASCADE
);
```

**Line by line:**

- The `sessions` primary key is the **three** values from
  [1.1](1.1-the-book-under-the-shutter.md) together. Two apps may use the same session id without
  colliding, and so may two users. Changing your `app_name` therefore orphans every existing
  session: they are still in the file, and nothing will ever look them up again.
- `state TEXT NOT NULL` holds a JSON object as text. SQLite has no dictionary type, and this column
  is why the service can store whatever your agent puts in state without knowing what it is.
- `create_time` and `update_time` are `REAL`, which is a floating-point Unix timestamp — seconds
  since 1970 with a fractional part. Not a date string, not a `TIMESTAMP`. That choice matters in
  [4.1](../04-two-workers/4.1-refused-not-overwritten.md), where `update_time` is the entire
  concurrency mechanism, and a string comparison would sort `"10:00"` before `"9:00"`.
- `event_data TEXT NOT NULL` is the whole event, serialised by Pydantic with `exclude_none=True` so
  absent fields cost nothing. This is the flexibility trade named above.
- `invocation_id` gets a column of its own even though it is also inside the JSON, because one user
  turn can produce several events and the invocation id is what groups them. Day 17's
  [2.2](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.2-an-invocation-is-not-a-session.md)
  is the distinction.
- `ON DELETE CASCADE` is the line that makes deletion work at all: removing a session row removes
  its events, in one statement, without an application loop that can be interrupted halfway.
  [6.1](../06-forgetting-on-purpose/6.1-delete-the-session-keep-the-customer.md) is what it does and
  does not reach.
- A cascade only fires when foreign keys are switched on, and in SQLite they are **off by default**
  for backwards compatibility. The service issues `PRAGMA foreign_keys = ON` on every connection it
  opens. Your own connection to the same file does not inherit that, which is a real trap: delete a
  session row by hand from `sqlite3` and the events stay.

## When it breaks

The script prints the file's actual contents. This is the output, not a description of it:

```text
=== tables ===
app_states   app_name, state, update_time
events       id, app_name, user_id, session_id, invocation_id, timestamp, event_data
sessions     app_name, user_id, id, state, create_time, update_time
user_states  app_name, user_id, state, update_time

=== sessions ===
('sutra_desk', 'asha', 'ticket-4521', '{"ticket": "4521"}')

=== events (one row, event_data pretty-printed) ===
id            = a6e03667-0acf-42ec-a3fb-8c2761011b66
invocation_id = inv-1
timestamp     = 1788554716.0137377
event_data    =
  {
    "actions": {
      "artifact_delta": {},
      "requested_auth_configs": {},
      "requested_tool_confirmations": {},
      "state_delta": {}
    },
    "author": "user",
    "content": {
      "parts": [
        {
          "text": "the printer is offline"
        }
      ],
      "role": "user"
    },
    "id": "a6e03667-0acf-42ec-a3fb-8c2761011b66",
    "invocation_id": "inv-1",
    "node_info": {
      "path": ""
    },
    "timestamp": 1788554716.0137377
  }

=== row counts ===
app_states   0
user_states  0
sessions     1
events       2

file size     36864 bytes
```

Two things in that block are worth stopping on.

**Two turns cost 36 864 bytes.** That is not because two turns are big; it is SQLite's page size
times a handful of pages, most of which are the schema and the free list. The file starts at tens of
kilobytes and then grows roughly with the text you put in it —
[5.3](../05-shape-and-size/5.3-the-session-that-never-ended.md) measures the slope. If you are ever
tempted to conclude from a small test that sessions are expensive on disk, measure at four hundred
turns instead of at two.

**The event carries fields you never set.** `actions`, `node_info` and an `id` you did not choose are
all in there. That is what "the whole event as JSON" means, and it is the first hint of the failure
in [5.2](../05-shape-and-size/5.2-the-migration-that-passed.md): a person hand-writing a migration
sees `author` and `content` and copies those, and every field they did not know about is gone.

Now the break. Open the file yourself and delete a session the obvious way — a plain connection, a
`DELETE FROM sessions`, a re-count of the events:

```text
events before: 2
events after (no pragma): 2
```

Two orphaned events, pointing at a session that no longer exists. The cascade did not fire, because
your `sqlite3` shell did not run `PRAGMA foreign_keys = ON` and SQLite's default is off. Nothing
raised. The next `get_session` returns `None` and the transcript is still on the disk — which is
precisely the wrong outcome when the reason you deleted it was that somebody asked you to.

## In production

**What a professional writes instead:** they do not write against the schema at all in application
code. They use the service's methods, and they open the file directly only for the things the API
does not cover — a backup, a count, an investigation, a deletion the API cannot express
([6.1](../06-forgetting-on-purpose/6.1-delete-the-session-keep-the-customer.md)). When they do open
it, the first statement is `PRAGMA foreign_keys = ON` and the second is a `BEGIN IMMEDIATE`, exactly
as
[Day 43's 4.2](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md)
established.

**What degrades at scale:** `events` is the table that grows, and it grows in two directions at
once — more conversations and longer conversations. Its primary key is
`(app_name, user_id, session_id, id)`, which serves the one query the service makes, and nothing
indexes `timestamp` on its own. So "show me everything that happened yesterday across all customers"
is a full table scan, and it gets slower every day you run. Reporting queries belong on a copy, not
on the store the desk is writing to.

**The failure mode that only appears with real traffic:** JSON in a text column is invisible to the
database's own integrity checking. A field that changes type — a number that becomes a string, a
string that becomes a list — passes every constraint the schema can express and fails at
`Event.model_validate_json` when a customer opens a six-month-old conversation. The traceback names
Pydantic and a session id, and nothing points at the deploy that changed the shape.

**The review comment a senior engineer leaves:** *"this reads `event_data` with a `LIKE '%printer%'`
to find tickets about printers. That is a scan over every event ever written, matching against JSON
punctuation as often as against words, and it will be the slowest query we own within a month. If we
need to search transcripts, that is a separate index built from the events, not a query against the
store the runner writes to."*

**The interview question:** *"what does a session look like on disk?"* The honest answer: *"For the
SQLite service it is four tables in one file: `sessions` for the conversation and its state,
`events` for the turns, and `user_states` and `app_states` for the two wider scopes. Events are
stored as whole JSON documents rather than exploded into columns, which is what lets the event shape
evolve without a schema migration, and the price is that you cannot query inside a transcript from
SQL. The events table has a cascading foreign key to sessions, so deleting a session takes its
turns with it — but only if foreign keys are on, and SQLite has them off by default, so a hand-run
`DELETE` leaves orphans."*
