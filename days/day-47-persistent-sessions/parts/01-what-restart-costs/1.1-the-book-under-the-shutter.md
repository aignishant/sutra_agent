# 1.1 — The book that survives the shutter

## One-line answer

A session service decides where a conversation is kept, and the only difference between one that
survives a restart and one that does not is whether that place is a file on disk or a dictionary
in one process's memory.

## The story

There is a small shop at the end of the road that sells rice, oil and soap, and half the street
buys on credit.

For years the owner kept the credit in his head and on the shutter. Somebody would buy a bag of
rice and he would chalk the amount on the metal, and at the end of the month he would look at the
chalk and add it up. It worked, and it was fast, and he never had to look anything up.

Then one evening it rained hard, and in the morning the shutter was clean.

He knew roughly who owed what. He did not know exactly. Some people told him and some people did
not, and the ones who did not were not necessarily lying — they did not know either. He lost some
money and he lost more goodwill, and by the end of that week there was a hardbound book under the
counter with one page per customer, and every sale went into it in pen before the goods left the
shop.

The book is slower. Every sale is a line to write. He has to find the page. Twice a month he has to
start a new volume because the old one is full.

He has never once lost a month.

## The idea in plain language

A **conversation** with an agent is not one question and one answer. It is a series of turns: the
customer says something, the agent answers, a tool runs, the agent answers again. Everything the
agent knows about that conversation — what has been said, and any facts it has written down along
the way — has to be kept somewhere between one turn and the next.

In ADK that "somewhere" has a name. A **session** is one conversation, identified by three things
together: the **app name**, the **user id**, and the **session id**. A **session service** is the
thing that stores sessions and hands them back.

There is more than one session service, and they differ in exactly one respect: where the sessions
physically live.

- `InMemorySessionService` keeps them in a Python dictionary inside the running process. This is the
  chalk on the shutter. It is fast, it needs no setup, and when the process ends the dictionary is
  freed and the conversations are gone.
- `SqliteSessionService` keeps them in a file on disk. This is the book under the counter. Every
  turn is a row written to a file, and the file is still there when the process is not.

The word people reach for here is **persistence**, which just means *the data outlives the program
that wrote it*. It is worth saying plainly, because "persistent" is often used to mean "reliable"
or "safe" and it means neither. It means the bytes are on a disk.

**Restart** is the word for the moment that matters. A process ends and another starts. That
happens far more often than beginners expect. You press Ctrl-C. A deploy replaces the running
version. A container is rescheduled. A machine reboots for an update. A crash. Every one of those
is a restart, and after every one of them the in-memory dictionary is a fresh empty dictionary.

## Why Sutra needs it

Because [Day 43](../../../day-43-stateless-by-default/LESSON.md) built a server whose whole design
depends on this.

`sutra_mcp/app.py` is deploy-shaped: any instance answers any request, because no instance keeps
anything between requests.
[Day 43's 3.5](../../../day-43-stateless-by-default/parts/03-two-instances/3.5-the-handle-b-had-never-heard-of.md)
showed what happens when it does — a handle minted by instance A that instance B has never heard of.
The fix in
[Day 43's 4.1](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.1-down-out-or-nowhere.md)
was to move that state *down*, into a store both instances can reach.

A durable session store is that store, for the one kind of state that matters most: the
conversation itself. Statelessness is not the absence of state. It is state that lives somewhere
other than the process, so that any process can pick it up. **A stateless server needs a persistent
session store more than a sticky one does, not less.**

You will also meet it on
[Day 48](../../../day-48-memory-design/LESSON.md), which decides what is worth keeping out of what
this day makes keepable, and again in Phase 9, where a run is killed on purpose and asked to resume.
You cannot resume a conversation that stopped existing.

## The mechanism

The whole of it is which object you construct. Here are both, side by side, with two processes
proving the difference.

```python
# days/day-47-persistent-sessions/lab/amnesia.py  (extract)
from google.adk.sessions import InMemorySessionService
from google.adk.sessions.sqlite_session_service import SqliteSessionService


def service(memory: bool):
    """The one line the whole day turns on: which store the sessions live in."""
    if memory:
        return InMemorySessionService()
    return SqliteSessionService(db_path=f"sqlite:///{DB.as_posix()}")
```

**Line by line:**

- `InMemorySessionService` comes straight out of the package, because it is in the package's export
  list. `SqliteSessionService` is imported from its **module** rather than the package, because it is
  not in that list. That is a genuine oddity and it gets a part of its own —
  [2.1](../02-reaching-the-service/2.1-the-class-that-is-not-exported.md). For now, copy the import
  line exactly.
- `db_path` is the constructor's only argument. It takes either a plain filesystem path or a
  `sqlite:` URL, and the number of slashes decides what the rest means —
  [2.3](../02-reaching-the-service/2.3-the-url-that-names-a-file.md).
- `DB.as_posix()` turns a Windows `Path` into forward slashes, because a URL uses forward slashes
  everywhere, including on Windows. Passing the backslash form here is a common Windows-only bug.
- Neither constructor takes an agent, a runner or a model. **The session service is not part of the
  agent.** It is handed to the runner, which is what makes swapping it a one-line change —
  [2.4](../02-reaching-the-service/2.4-handing-the-runner-a-store.md).
- The function returns the object rather than storing it in a module-level variable, so nothing
  in this lab holds a service at import time. That is
  [Day 43's rule](../../../day-43-stateless-by-default/parts/01-accidental-state/1.1-the-dictionary-nobody-called-state.md)
  about module-scope state, applied to the very object this day is about.

The two processes:

```python
# days/day-47-persistent-sessions/lab/amnesia.py  (extract)
async def first_process(memory: bool) -> None:
    """Process one: start the conversation and write two turns."""
    svc = service(memory)
    session = await svc.create_session(
        app_name=APP, user_id=USER, session_id=SESSION, state={"ticket": "4521"}
    )
    await svc.append_event(session, turn("the printer is offline", 1))
    await svc.append_event(session, turn("i already rebooted it", 2))


async def second_process(memory: bool) -> int:
    """Process two: a brand-new interpreter asks for the same session."""
    svc = service(memory)
    session = await svc.get_session(app_name=APP, user_id=USER, session_id=SESSION)
    if session is None:
        print(f"process 2: get_session({SESSION!r}) -> None")
        return 1
    said = [p.text for e in session.events for p in (e.content.parts if e.content else [])]
    print(f"process 2: found {len(session.events)} turns, state={session.state}")
    return 0
```

**Line by line:**

- Every method is `async` and every call is awaited. `BaseSessionService` is an asynchronous
  interface, so a synchronous caller has to sit inside `asyncio.run(...)`. Forgetting the `await`
  gives you a coroutine object that is truthy, so `if session is None` passes and the bug appears
  two lines later.
- `create_session` takes `app_name`, `user_id` and `session_id` as **keyword-only** arguments —
  there is a bare `*` in the signature. Passing them positionally is a `TypeError`, and that is
  deliberate: three strings in a row is exactly the argument list people get in the wrong order.
- `session_id` is optional. Leave it out and the service generates a UUID. Supplying your own is
  what lets a second process ask for *this* conversation instead of listing everything and guessing.
- `state={"ticket": "4521"}` is the session's initial state — the small dictionary of facts that
  travels with the conversation. Day 17's
  [1.2](../../../day-17-state-scopes-and-lifetimes/parts/01-form-not-story/1.2-what-may-live-in-state.md)
  is what belongs in it.
- `get_session` returns `None` for a session that does not exist. It does not raise. That matters:
  the failure of an in-memory store after a restart is not an exception you would notice in a log,
  it is a `None` that your code has to be written to expect.
- `session.events` is the transcript, in order. `event.content.parts` is a list because one turn can
  carry several parts — text, a function call, a function response.
- The `if e.content else []` guard is not decoration. Plenty of real events carry no content at all:
  an event whose only job is to change state has `content=None`, and iterating it unguarded is an
  `AttributeError` on live data and never in a test.

## When it breaks

Run the file-backed arm. Process one writes and exits; process two starts from nothing:

```text
process 1: wrote 2 turns to session 'ticket-4521'
process 1: exits now - this is the restart
process 2: found 2 turns, state={'ticket': '4521'}
process 2: ['the printer is offline', 'i already rebooted it']

store   : SqliteSessionService -> desk.sqlite3
survived: yes
exit: 0
```

Now the same script with `--memory`, which changes one constructor and nothing else:

```text
process 1: wrote 2 turns to session 'ticket-4521'
process 1: exits now - this is the restart
process 2: get_session('ticket-4521') -> None
process 2: the conversation does not exist

store   : InMemorySessionService
survived: no
exit: 1
```

Read the second block carefully, because the shape of the failure is the lesson. There is no
traceback. There is no error. There is no warning that a store was empty when it should not have
been. `get_session` returned `None`, which is the same thing it returns for a session id somebody
typed wrongly, and for a session that was deleted last week, and for a customer who has never
written in before.

**The store cannot tell you that it lost something, because it does not know it ever had it.** In
the shop, the chalk did not report itself missing; the shutter simply looked clean, exactly the way
it looks on the morning of a day when nobody has bought anything yet.

The version of this that costs a real afternoon is subtler still. A developer runs `adk web`, has a
conversation, restarts the server, and finds the conversation still there — so they conclude
sessions are persistent by default and move on. They are not wrong about `adk web`, and they are
wrong about the runner they wrote themselves.
[2.4](../02-reaching-the-service/2.4-handing-the-runner-a-store.md) is where those two facts get
separated.

## In production

**What a professional writes instead:** not a boolean and an `if`. The store is chosen once, in one
module, from configuration — and the same call site works in a test, on a laptop and on a server.
The teaching version above branches on a command-line flag because a lab needs to show both arms in
one run. Real code has one arm and a configuration value; §4 of this day's hub asks you to write it
as `sutra/memory/persistence.py`.

**What degrades at scale:** the in-memory service does not merely lose data on restart. It grows
without limit while the process lives, because nothing evicts a session that nobody has closed. A
long-lived process serving many customers is a memory leak with an event log inside it, and it is
usually diagnosed as "the container gets OOM-killed every few days" rather than as a session
problem. A file-backed store moves that growth onto disk, where it is visible, measurable and
[5.3](../05-shape-and-size/5.3-the-session-that-never-ended.md)'s subject.

**The failure mode that only appears with real traffic:** with one instance and a sticky load
balancer, an in-memory store looks fine for a long time. Sessions survive because the same customer
keeps landing on the same process. Then you scale to two instances, or a deploy rolls, and
conversations start dropping — not all of them, and not reproducibly, which is the worst possible
shape for a bug report. Day 43's
[6.2](../../../day-43-stateless-by-default/parts/06-in-production/6.2-sticky-sessions-the-anaesthetic.md)
is about exactly that anaesthetic.

**The review comment a senior engineer leaves:** *"this constructs `InMemorySessionService` inside
the request handler. That is two separate problems in one line: the sessions do not survive a
restart, and they do not survive this function returning either, because a new service is built
each time. Construct it once, from config, and make the default the durable one — a laptop losing
its sessions is a mild annoyance, and production losing them is an incident."*

**The interview question:** *"where does your agent's conversation history live?"* The honest
answer: *"In a session service, and which one is a deployment decision rather than an agent one. The
default in-memory service is a dictionary in the process, so anything that restarts the process
empties it — a deploy, a crash, a container reschedule. I proved it with two processes: the same
session id, written by one and read by the other, comes back with two turns from the SQLite service
and `None` from the in-memory one. And `None` is the dangerous part, because it is indistinguishable
from a session that never existed, so nothing in the logs says data was lost."*
