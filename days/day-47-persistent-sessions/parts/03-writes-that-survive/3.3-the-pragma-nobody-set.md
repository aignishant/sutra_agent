# 3.3 — 💥 The pragma nobody set

## One-line answer

The session service sets one pragma on every connection and it is not `journal_mode` or
`busy_timeout` — four workers on one file still all succeed, because the driver's default five-second
wait absorbs the queueing, and the moment anything holds the file longer than that the service fails
at *construction* with `database is locked`.

## The story

There is one tap for the four houses at the end of the lane, and it runs for two hours in the
morning.

Most mornings this is fine. People come out with their buckets, and if somebody is already filling
you put yours down and wait, and it takes a minute. Nobody has agreed anything; everyone simply
waits, because waiting works.

Then the water board sends a man to change the washer. He shuts the tap off and works on it. The
first person out with a bucket waits. The second and third put their buckets down and wait too. And
at some point the woman from the end house — who has been waiting long enough — picks her bucket
back up, goes inside, and does the washing with what was in the drum.

She did not do anything wrong. She waited as long as she was prepared to wait. The point is that
nobody ever said how long that was, so nobody could have predicted which of the four would leave, or
when, or that leaving was even one of the outcomes.

## The idea in plain language

A SQLite database is a file, and several processes can open the same file at once. What stops them
corrupting it is **locking**: a writer takes a lock on the file, and anybody else who wants to write
has to wait for it.

"Has to wait" needs a number, and the number has a name: **`busy_timeout`**, in milliseconds. It is
how long a connection will keep retrying a locked database before it gives up and raises. SQLite's
own default is **zero** — fail on the first collision — which is where most of the folklore about
SQLite not handling concurrency comes from, as
[Day 43's 4.2](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md)
showed.

Python's `sqlite3` driver does not use SQLite's default. `sqlite3.connect` has a `timeout` parameter
that defaults to `5.0` seconds and sets the busy timeout accordingly. `aiosqlite.connect` passes its
keyword arguments straight through to `sqlite3.connect`, and the ADK's session service passes none —
so every connection it opens waits up to **five seconds** for a lock.

Five seconds is generous for a write that takes a millisecond. It is why the measurement below comes
out the way it does, and it is a number nobody chose for this workload.

The other pragma is **`journal_mode`**. The default, `delete`, keeps a rollback journal: a writer
copies the old pages aside, changes the real ones, and deletes the journal on commit — the file you
watched appear in
[3.1](3.1-the-ticket-torn-in-two.md)'s crash. Under that mode a writer excludes readers. The
alternative, **WAL** (write-ahead logging), appends changes to a side file instead, so readers and
the writer do not block each other and only writer-against-writer contends. WAL is a persistent
property of the file, set once, and it survives every later connection.

The session service sets neither. The only pragma it issues is `PRAGMA foreign_keys = ON`, which is
about the cascade in
[1.2](../01-what-restart-costs/1.2-a-session-is-four-tables.md) and has nothing to do with
concurrency.

## Why Sutra needs it

Because Sutra's whole deployment shape is several instances behind one URL, and this is the number
that says how many.

[Day 43](../../../day-43-stateless-by-default/LESSON.md) built `sutra_mcp/app.py` so that any
instance answers any request. The session store is what makes that safe, and it is also the one
thing all those instances share. If the store is a file, the instances must be on one machine
sharing one filesystem, and the write rate they can sustain together is a property of that file.

So the measurement below is the input to a real decision: how many instances Sutra can run on one
box before it has to move to Postgres and pay
[2.2](../02-reaching-the-service/2.2-the-driver-you-do-not-have.md)'s price. Guessing that number
from a blog post is how teams either over-engineer a desk that serves forty tickets a day, or
discover the ceiling during a busy week.

Every day carries one part whose subject is a deliberate failure. This is that part, and the failure
is the third arm below.

## The mechanism

Four processes, each with its own session, all appending to one file.

```python
# days/day-47-persistent-sessions/lab/locked.py  (extract)
async def worker(index: int) -> int:
    """One process: create its own session, then append to it APPENDS times."""
    user = f"agent-{index}"
    errors: collections.Counter[str] = collections.Counter()
    try:
        svc = SqliteSessionService(db_path=f"sqlite:///{DB.as_posix()}")
        session = await svc.create_session(app_name=APP, user_id=user, session_id=f"tkt-{index}")
    except Exception as err:  # noqa: BLE001 - the lab wants every failure named
        print(f"  worker {index}: never started - {name_of(err)}", file=sys.stderr)
        return 1
    ...
```

**Line by line:**

- Each worker uses **its own session id**. That is deliberate and it is what makes this a clean
  measurement: nothing here is a lost update or a stale write, so anything that goes wrong is
  contention on the file itself.
- The service construction is *inside* the try, not before it. That looks like over-caution until you
  see the third arm, where construction is exactly what fails — the constructor reads the file to
  check for an old schema
  ([5.1](../05-shape-and-size/5.1-the-store-the-code-cannot-read.md)) and that read can block.
- `collections.Counter` rather than a list, because under contention the same message arrives
  dozens of times and a count is the useful shape.
- Errors go to `stderr` while the report goes to `stdout`, so the two can be read separately when
  four processes interleave.
- Each worker is a real `subprocess`, not a task. Threads in one process share a connection pool and
  an event loop, and the thing being measured is file locking between operating-system processes.

The lock-holder that makes the third arm happen:

```python
# days/day-47-persistent-sessions/lab/locked.py  (extract)
def hold_the_file(seconds: float) -> int:
    """A maintenance job: take the write lock on the whole file and sit on it."""
    conn = sqlite3.connect(DB, isolation_level=None, timeout=1.0)
    conn.execute("BEGIN EXCLUSIVE")
    conn.execute("CREATE TABLE IF NOT EXISTS maintenance (note TEXT)")
    time.sleep(seconds)
    conn.execute("ROLLBACK")
    conn.close()
    return 0
```

**Line by line:**

- `BEGIN EXCLUSIVE` takes the strongest lock SQLite has: no other connection may read or write. It is
  what a `VACUUM`, a schema migration or a naive backup script does, so this is not a contrived
  scenario — it is Tuesday.
- `isolation_level=None` turns off the driver's implicit transactions so that the explicit
  `BEGIN EXCLUSIVE` is the only transaction in play. Without it the driver's own `BEGIN` competes for
  control of something that must be explicit — the same reasoning as
  [Day 43's 4.2](../../../day-43-stateless-by-default/parts/04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md).
- `timeout=1.0` on the **holder** so that the holder itself does not wait long. It is the workers'
  patience that is being measured, not the holder's.
- The `CREATE TABLE` is there because a lock with no write behind it can be optimised away. One
  statement makes the transaction real.
- `ROLLBACK` rather than `COMMIT`, so the maintenance table is never actually created and the file
  is left exactly as it was found. The experiment measures waiting, not its own side effects.

## When it breaks

Three arms, run on 2026-09-05. First, the file as the service creates it:

```text
journal mode  : delete
maintenance   : none
workers       : 4 processes x 25 appends = 100
events stored : 100
workers with errors: 0
wall clock    : 4.12s
```

A hundred appends, a hundred stored, nothing lost, nothing raised. This is the result to be honest
about: **four processes writing to one SQLite file did not lose a single write.** They queued, and
the driver's five-second patience absorbed the queueing entirely.

Turn on write-ahead logging and the same hundred land:

```text
journal mode  : wal
workers       : 4 processes x 25 appends = 100
events stored : 100
workers with errors: 0
wall clock    : 4.18s
```

No difference worth the ink. WAL earns its keep when readers and writers contend, and this workload
is four writers, which is the one case WAL does not help. A number that does not move is still a
result, and it is worth having before writing WAL into a configuration file as a superstition.

Now the third arm. One maintenance job holds the file for twenty seconds and the same four workers
arrive:

```text
  holder: exclusive lock taken for 20s
  worker 0: never started - RuntimeError: Error accessing database ...\locked.sqlite3: database is locked
  worker 3: never started - RuntimeError: Error accessing database ...\locked.sqlite3: database is locked
  worker 2: never started - RuntimeError: Error accessing database ...\locked.sqlite3: database is locked
  worker 1: never started - RuntimeError: Error accessing database ...\locked.sqlite3: database is locked

journal mode  : delete
maintenance   : holding the file for 20.0s
workers       : 4 processes x 25 appends = 100
events stored : -1
workers with errors: 4
wall clock    : 10.11s
```

Four out of four dead, and none of them got as far as writing anything. The whole traceback:

```text
Traceback (most recent call last):
  File "...\google\adk\sessions\sqlite_session_service.py", line 609, in _is_migration_needed
    cursor.execute(
sqlite3.OperationalError: database is locked

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "...\lab\tb_probe.py", line 13, in <module>
    SqliteSessionService(db_path=f"sqlite:///{DB.as_posix()}")
  File "...\google\adk\sessions\sqlite_session_service.py", line 165, in __init__
    if self._is_migration_needed():
       ^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "...\google\adk\sessions\sqlite_session_service.py", line 625, in _is_migration_needed
    raise RuntimeError(
RuntimeError: Error accessing database ...: database is locked
```

Read the frames. The failure is in `__init__`, in `_is_migration_needed`, which opens the file to
check whether its schema is old. **Constructing the session service touches the disk**, so a locked
file is not a slow write — it is a service that cannot be built. Every one of
[2.4](../02-reaching-the-service/2.4-handing-the-runner-a-store.md)'s callers gets an exception
before it has a runner, and if that construction happens at start-up the process does not start.

Two more details worth taking away. The error surfaces as `RuntimeError` and not
`sqlite3.OperationalError`, so a caller that catches database errors specifically will not catch it.
And with WAL set, the same arm fails at `create_session` with a bare
`OperationalError: database is locked` instead, because the constructor's read succeeds under WAL
and the write does not — the same cause, a different exception type, in a different frame. Any
handler written for one of those two shapes misses the other.

## In production

**What a professional writes instead:** they set the file's journal mode once, at creation, and they
choose the busy timeout deliberately rather than inheriting `5.0` from a driver. With the SQLite
service there is no constructor argument for either, so the honest options are to run
`PRAGMA journal_mode=WAL` on the file when it is created — it is persistent — and to treat the
five-second default as a documented fact rather than a decision. They also catch **both**
`RuntimeError` and `sqlite3.OperationalError` at the point the service is constructed, and fail the
health check rather than the request.

**What degrades at scale:** the ceiling is writers, not readers, and it is a wall rather than a
slope. Below it every write queues briefly and succeeds; above it, waits start exceeding five
seconds and errors arrive in a burst at the busiest moment, which looks like an outage rather than
saturation. The two levers are shortening the time each write holds the lock — which means no
network call and no model call anywhere near the store — and moving off a single file. Postgres is
the move, and [2.2](../02-reaching-the-service/2.2-the-driver-you-do-not-have.md) is what it costs.

**The failure mode that only appears with real traffic:** the maintenance job. Nightly backups,
`VACUUM`, a hand-run migration, and any tool that opens the store with an exclusive lock will, one
night, overlap with traffic. The system was healthy at midnight and every process that started at
00:05 died on construction. Whoever reads the logs sees `database is locked` and starts tuning
concurrency, which is the wrong place entirely — the fix is that backups take a copy rather than a
lock, using SQLite's own online backup or a `VACUUM INTO` to a new file.

**The review comment a senior engineer leaves:** *"our backup script opens the session store and
runs `VACUUM`. That takes an exclusive lock for as long as it takes, and every service constructed
during that window raises — including at start-up, because the constructor reads the file. Use
`VACUUM INTO 'backup.sqlite3'` or the online backup API, and while you are there catch `RuntimeError`
as well as `OperationalError` where we build the service; the ADK wraps one in the other."*

**The interview question:** *"can SQLite handle concurrent writers?"* The honest answer: *"For a
desk-sized write rate, yes, and I measured it rather than assuming: four processes doing a hundred
appends to one file lost nothing and took four seconds, because Python's driver defaults to a
five-second busy timeout, so writers queue instead of failing. Enabling WAL changed nothing here,
because WAL separates readers from writers and this workload was four writers. What does break it is
anything holding the file longer than that timeout — a `VACUUM`, a migration, a naive backup. In our
case all four workers died at *construction*, because the ADK's constructor reads the file to check
the schema version, and the error came back as a `RuntimeError` wrapping the `OperationalError`. So
the real answer is: it handles our write rate, and the thing to design around is maintenance, not
traffic."*
