# 3.2 — What a restart still loses

## One-line answer

A durable store saves every event that was committed, and a turn is several events of which only
the final one is committed — so a process killed mid-answer leaves a question in the transcript with
nothing after it, and no record that anything was in flight.

## The story

The man who reads the electricity meters does the whole colony on a Tuesday.

He carries a handheld device. At each meter he punches in the reading, it beeps, and he moves on.
The device is not talking to anything — there is no signal in half these lanes — so the readings sit
in it. At the end of the round he goes back to the office, puts it in a cradle, and the whole day
goes up in one go.

One Tuesday his scooter is hit at the junction. He is fine. The device is in three pieces on the
road.

Nobody in that colony gets a bill that month based on a real reading, and the readings he took are
not partially recovered — they are gone, all of them, including the ones from the first lane he did
at eight in the morning. What survived is what had been put in the cradle, which is last month.

The colony's records are not damaged. They are simply as they were before he set out.

## The idea in plain language

[3.1](3.1-the-ticket-torn-in-two.md) established that a committed event is safe. This part is about
the part of a turn that is not an event yet.

One customer message does not produce one event. It produces a sequence:

1. the customer's message, appended as an event;
2. a run of **partial** events while the model's answer is still arriving, one per chunk;
3. one final event carrying the whole answer;
4. possibly more events — a tool call, a tool response, another answer.

Partial events exist so that a user interface can show text appearing as it is produced. They are
not turns; they are fragments of one turn, each a longer prefix of the same sentence.

`append_event` returns immediately for any event whose `partial` flag is set, before touching the
database. So the partials are never stored, and there is no half-written answer on disk to recover.
What is on disk after a crash is: the customer's message, and nothing.

That is a good design and it is not a free one. It means **the store's durability is at the
granularity of a committed event, and a turn is bigger than an event.** Everything below that
granularity — the partial text, anything in `temp:` state
([1.3](../01-what-restart-costs/1.3-three-scopes-three-tables.md)), whatever the agent had worked out
but not yet written — is in memory, and memory is what a restart takes.

There is one more thing that lives in that gap. `BaseSessionService` has a `flush()` method whose
docstring says *"Flushes any buffered events. For non-buffering implementations, this can be a
no-op."* The SQLite service does not buffer, so its `flush()` does nothing. But the method exists on
the interface, which means a service **may** buffer — and a buffering implementation loses whatever
it was holding. If you ever swap the store, that method stops being decoration.

## Why Sutra needs it

Because Phase 9 kills a run on purpose and demands that it resume, and "resume" needs a definition
before it needs an implementation.

After this day, the definition is available and precise: **a resumed conversation restarts from the
last committed event.** Not from the last thing the customer saw on their screen, because the
customer may have watched half an answer appear that was never stored. Not from the agent's
half-formed plan, because that was in `temp:`.

That distinction decides how the desk behaves after a crash. If the last stored event is the
customer's message, the correct thing is to answer it again — which means the answer must be safe to
produce twice, which is
[Day 44's idempotency question](../../../day-44-client-hardening/parts/01-what-may-be-repeated/1.1-the-button-you-can-press-twice.md)
arriving from a completely different direction. If the last stored event was a tool call whose
response never landed, the same question applies to the tool.

## The mechanism

One turn, played out as events, with the process killed at a chosen point.

```python
# days/day-47-persistent-sessions/lab/restart.py  (extract)
async def child(complete: bool) -> None:
    """One turn: the question, three partials, and - if allowed - the answer."""
    svc = service()
    session = await svc.get_session(app_name=APP, user_id=USER, session_id=SESSION)
    await svc.append_event(session, event("user", "any update on the printer?"))

    seen = ""
    for chunk in ANSWER:
        seen += chunk
        await svc.append_event(session, event("triage", seen, partial=True))

    if not complete:
        os._exit(9)

    await svc.append_event(session, event("triage", seen))
```

**Line by line:**

- The partials carry a growing prefix, not a chunk each. That is how streaming events are actually
  shaped: each one is the whole answer so far, so a display can replace rather than concatenate.
- `partial=True` is a field on `Event`. It is the flag `append_event` checks first, before any
  database work, and it is the only reason those three calls cost nothing.
- `os._exit(9)` and not `sys.exit(9)`. `sys.exit` raises `SystemExit`, which runs `finally` blocks,
  flushes buffers and closes connections — everything a real kill does not do. `os._exit` skips all
  of it, which is the only honest way to simulate a process that stopped rather than ended.
- The exit sits **between** the last partial and the final event, because that is the widest and
  most likely window: it is the whole time the model was producing text.
- `service()` is called again in the child rather than a service being passed in, because the child
  is a separate process. Nothing in-memory crosses that boundary; only the file does.

The check inside the service that makes the partials free:

```python
# .venv/Lib/site-packages/google/adk/sessions/sqlite_session_service.py  (extract)
async def append_event(self, session: Session, event: Event) -> Event:
    if event.partial:
        return event
    self._apply_temp_state(session, event)
    event = self._trim_temp_delta_state(event)
```

**Line by line:**

- `if event.partial: return event` is the first statement in the method. No connection is opened, no
  transaction begins, nothing is written. A hundred partials cost one attribute lookup each.
- The returned object is the event you passed in, unchanged. Code that logs what `append_event`
  returned will log partials that were never stored, which is worth knowing when a log and a store
  disagree.
- `_apply_temp_state` copies `temp:` keys into the **in-memory** session before anything is trimmed,
  so a later agent in the same turn can read them. That is the whole life of a `temp:` value: it
  exists in this object, in this process, until this turn ends.
- `_trim_temp_delta_state` then removes those keys from the event, so what is written carries no
  `temp:` anything. The order matters: trim first and the later agent in the same turn would see
  nothing.
- Both are methods on `BaseSessionService`, shared by every implementation, so this behaviour is not
  SQLite-specific. Swapping the store does not change what `temp:` means.

## When it breaks

The killed arm, run on 2026-09-05. Three partials went in and one event came out:

```text
parent: session created, empty
  child: question stored
  child: partial 'raised with ' appended
  child: partial 'raised with the print team, ' appended
  child: partial 'raised with the print team, reference PRT-118' appended
  child: dies here, before the final event
parent: child exited with 9

arm            : killed mid-turn
partials sent  : 3
events stored  : 1
  user    'any update on the printer?'
last author    : user
verdict        : a question with no answer
exit: 1
```

And the same code allowed to finish:

```text
arm            : --complete
partials sent  : 3
events stored  : 2
  user    'any update on the printer?'
  triage  'raised with the print team, reference PRT-118'
last author    : triage
verdict        : answered
exit: 0
```

The store is not damaged in the first run. It is *consistent* — one question, correctly recorded,
and no answer, correctly not recorded, because no answer was ever committed. The paper's word for
this is that the transaction did not commit, so as far as the database is concerned it did not
happen.

The break is what that consistency looks like to a person. A customer watching the dev UI saw
`raised with the print team, reference PRT-118` appear on their screen, word by word. They have the
reference number. They may have written it down. Reopen the conversation and the desk has no record
of ever having said it, and if you ask it again it may well produce a different reference.

**The customer's memory and the store disagree, and the store is the one that is right.** No error
was raised on either side. That is the failure mode to be able to describe, because the fix is a
product decision — replay the turn, or tell the customer plainly that the last answer was not
recorded — and it cannot be made by whoever notices it at eleven at night.

## In production

**What a professional writes instead:** they make the boundary visible. A structured log line at the
end of every turn, carrying the session id and the id of the last committed event, means a restart
can be reconciled: whatever the log's last line says was committed *is* what the store holds. Day
22's [structured logging](../../../day-22-structured-logging/LESSON.md) is where that line belongs,
and the session id is the correlation key that makes it useful.

**What degrades at scale:** the width of the window is the model's response time, and that is the
one number in the system you do not control. A fast answer is a narrow window and a rare loss; a
long answer, or a slow tool inside a turn, keeps the window open for seconds. So the conversations
most likely to lose their answer are the long, complicated, expensive ones — the ones where losing
the answer costs most, and where re-running it costs most too.

**The failure mode that only appears with real traffic:** rolling deploys. A deploy replaces
instances one at a time, and every replacement kills whatever turns were in flight on that instance.
At one turn a minute nobody notices. At a hundred a minute, every deploy silently drops a handful of
answers, and the graph that would show it — turns that started and never produced a final event —
is one nobody thinks to build until after the first complaint.

**The review comment a senior engineer leaves:** *"the shutdown handler here calls `sys.exit` in a
signal handler and we call that graceful. It is not: the in-flight turn is abandoned mid-answer and
the customer has already seen text we never stored. Either stop accepting new turns and let the
in-flight ones commit before exiting, or accept the loss deliberately and log which sessions were
in flight so we can find them afterwards."*

**The interview question:** *"your sessions are in a database. What does a crash still cost you?"*
The honest answer: *"Everything below the granularity of a committed event, which is bigger than
people expect. A turn is several events and only the final one is stored — the streaming partials
are returned early and never written, and `temp:` state is stripped before the write on purpose. So
a process killed mid-answer leaves the customer's question with nothing after it. The store is
consistent, which is the point of the transaction, and it is still a loss: the customer watched an
answer appear on their screen that the system has no record of. I measured it — three partials sent,
one event stored. The thing that makes it recoverable is logging the last committed event id per
turn, so after a restart you can tell what actually landed."*
