# 5.1 — The reader who leaves

## One-line answer

Streaming hands the reader a connection they control, so they can hang up half-way — and when they
do, the run is cancelled and the session ends up holding **one** event, their question, with **no
assistant turn at all**: the reader saw two chunks of an answer that, as far as the conversation's
history knows, was never given.

## The story

You are on the phone sorting out something tedious, and the person on the other end is finally
telling you what to do. *"Right — so you'll need to bring the original and a copy, and there's a form,
it's the one on the second floor, ask for—"*

Your train goes into a tunnel.

You have half of it. You know there is a form and you know it is on the second floor, and you have no
idea what the last word was going to be or whether there was a sentence after it.

So you call back. And the person who picks up is not the same person, and the notes on the account
say *"customer called"*. Not what was said. Not how far the last person got. Just that you called —
which is somehow worse than nothing, because it looks like you have been dealt with.

## The idea in plain language

Every part of this day so far has treated the stream as something your program produces. This part is
about the other end of it, and the fact that the other end has a hand on the wire.

A streamed answer travels over a connection that stays open for the whole turn. Anything that closes
that connection — the reader navigating away, hitting stop, closing a laptop, losing signal — stops
the consumer asking for the next event. And a producer finds out that nobody is listening in the only
way a producer ever finds out: the consumer stops asking.

Two things happen then, and only the first is obvious.

**The run is cancelled.** The framework notices the consumer has gone and stops the work. That is the
right behaviour and it is what you would want.

**And the turn is not saved.** The session — the conversation's memory, the thing every later turn is
prompted with — only gains the assistant's message when the turn *finishes*. An interrupted turn
finishes nothing, so it stores nothing. The reader's screen and the conversation's history now
disagree, and the history is the one the model will read next time.

That is the tunnel. The reader has half an answer. The record says *"customer called"*.

## Why Sutra needs it

Because the desk is going to be a thing people talk to, and people close tabs. This is not an edge
case dug out of a specification; it is the single most common way a streamed turn ends other than
finishing.

And because the build brief has a `TODO(me)` for it that most people would not think to write:
*decide what your handler does when the client disconnects mid-turn.* There is no correct default
here. Saving a partial answer as though the agent said it is a lie of a particular kind — Day 72 part
3.1's kind, a plausible thing recorded where a real thing should be. Saving nothing is what happens
now, and it means the next turn is asked of a conversation in which the agent never spoke. Both are
defensible and neither is free, which is exactly why it has to be a decision rather than a default.

## The mechanism

`cancel.py` consumes two events and then hangs up the way a web framework does when its client
disconnects:

```python
    consumed = 0
    async for _event in stream:
        consumed += 1
        if stop_after is not None and consumed >= stop_after:
            # Closing the generator is what a web framework does when the client disconnects.
            await stream.aclose()
            break
```

**Line by line:**

- `async for _event in stream` — the underscore is deliberate. This part does not care what the
  events contain; it cares about how many were asked for.
- `await stream.aclose()` is the hang-up. `run_async` returns an asynchronous generator, and closing
  a generator tells the code producing values that nobody will ask for another one. A web framework
  does exactly this when the client's socket goes away, which is why this is a simulation of a
  disconnect rather than a metaphor for one.
- `break` leaves the loop afterwards. Without the `aclose()` the loop would simply stop asking, and
  the generator would be closed later by garbage collection — at a time nobody chose. Closing it
  explicitly is the difference between cancelling and abandoning.
- `stop_after is not None` is how the same function serves both runs: `None` means consume everything,
  which is the comparison run.

Then it asks the session what it kept:

```python
    after = await runner.session_service.get_session(
        app_name=_fake.APP, user_id="learner", session_id=session.id
    )
    stored = after.events if after else []
    return consumed, len(stored), [event.author for event in stored]
```

**Line by line:**

- `get_session(...)` re-reads the session **after** the run rather than inspecting anything the run
  returned, because the question is what a *later* turn would see. Anything still in memory in this
  process is not the answer.
- `after.events` is the conversation's stored history. This is the list that gets turned back into a
  prompt on the next turn, which is why its contents are the whole point.
- `[event.author for event in stored]` records **who** wrote each stored event. Counting them is not
  enough: two events could be two user messages, and the interesting question is whether the agent is
  in there at all.

Run it both ways:

```bash
cd days/day-74-live-api-streaming/lab
uv run python cancel.py
uv run python cancel.py --finish
```

**Line by line:**

- The first run hangs up after two events. The second consumes the whole turn and exists to be
  compared against.

Measured on 2026-09-06:

```text
reader: closed the connection after two events

  events consumed              2
  events stored in the session 1
  who wrote them               ['user']

  The reader saw two chunks of an answer. The session contains the question and
  nothing else - no assistant turn at all, because the turn never finished. Ask a
  follow-up now and the model is answering a conversation in which it never spoke.
```

```text
reader: stayed to the end

  events consumed              6
  events stored in the session 2
  who wrote them               ['user', 'desk']

  Six events reached the reader and two were stored. The five partials are not in
  the session: the transcript keeps the finished turn, not the pieces it arrived in.
```

And the cancelled run says so on **stderr**, in the runtime's own words:

```text
Root node desk was cancelled.
```

Three findings, and the second is the one people miss.

| | reader stayed | reader left after two events |
| --- | --- | --- |
| events consumed | 6 | 2 |
| events stored in the session | 2 | **1** |
| who wrote them | `['user', 'desk']` | `['user']` |
| what a later turn sees | the question and the answer | the question, and silence |

**The run really is cancelled**, and the runtime says so out loud rather than leaving you to infer it.
That is good behaviour and it is worth knowing the exact string, because it is what you will grep for.

**Partials are never stored, even on a perfect run.** Six events reached the reader and two are in the
session. The five `partial=True` events are display, not history — which is a completely reasonable
design and is also the thing that makes the cancelled case so stark, because *display* is all the
reader ever got.

**And a cancelled turn stores nothing at all.** Not a truncated answer. Not an empty assistant
message. The session has one event, written by `user`, and no trace that a model was ever asked.

## When it breaks

**The lab's disconnect is clean and a real one is not.** `await stream.aclose()` is a polite hang-up
inside one process. A real client vanishing is a socket that stops being readable, discovered by a web
server at a moment of its choosing, and the run may keep going for a while before anything notices.
Whether the work is actually stopped depends on the server, the framework and how the handler is
written — so *"the run is cancelled"* is a property of this lab's arrangement, not a promise about
yours. Verify it in your own stack before relying on it.

**Cancellation is not free, and it is not instant.** Anything already in flight is already paid for.
If the turn had called a tool, the tool call may well have completed; if it had spent a model request,
Day 70's counter has already counted it. Cancelling stops future work, and the reader who leaves after
two chunks of a long answer has still bought most of it.

**The honest gap in this measurement:** `InMemoryRunner` keeps its sessions in memory, so what is
being observed is one implementation's behaviour rather than a rule about session services in general.
A different service could be written to persist partial turns. None of the reasoning above changes —
the question *"what does a later turn see?"* is the same question — but the answer is a property of
the service you actually use, and it is worth asking of yours rather than assuming this one.

## In production

**What the disagreement actually costs.** The reader believes they were told something. The
conversation's history does not contain it. So their follow-up — *"and what about the second one?"* —
arrives attached to a transcript in which nobody said anything about a first one, and the model does
the only thing it can, which is to answer as though the question came out of nowhere. The user
experiences this as the assistant forgetting what it just said, which is a much worse-sounding bug
than the one that caused it.

**The three usual answers, none of them free.** Save nothing, and accept the disagreement — fine for a
throwaway question, bad for anything the user will refer back to. Save what was streamed, flagged as
incomplete, and make sure everything that reads history knows what the flag means — honest, and it
puts a partial answer into the model's own context, where it will be treated as something the agent
said. Or finish the turn regardless of whether anyone is listening and store the complete answer —
which costs the full request for an answer nobody read, and is often the right call precisely because
it keeps the history true.

**What a professional records either way.** That the turn was interrupted, and at which point. A
cancelled turn that leaves no trace anywhere is Day 73 part 3.3's problem arriving in a new place: the
absence of a thing is not a signal, and *"users abandon this answer half-way"* is a fact worth having
rather than a silence.

**What changes at scale.** Abandonment rate becomes a metric rather than an anecdote, and it is one of
the more useful ones a streaming system has — a rise in readers leaving mid-answer says something is
wrong with the answers that no eval will tell you. It also becomes a cost line: work paid for and
thrown away, which is the same accounting Day 72 part 5.2 called wasted requests, one layer up.

**The review comment a senior engineer leaves:** *"What happens when the client disconnects half-way?
Right now we store nothing, so the user has half an answer on screen and the session has only their
question — their next message lands on a transcript where we never replied, and it'll look like we
forgot. Pick one: either finish the turn and store it even though nobody's watching, or store what we
streamed with an explicit incomplete flag and make sure the prompt builder handles that flag. Write
the choice in the docstring. And log the interruption with how far we got — I want abandonment as a
number, not as something support tells us about."*

**The interview question:** *"A user closes the tab half-way through a streamed answer. What happens?"*
An honest answer: *"The consumer stops asking for events, so the run gets cancelled — in the framework
I measured, the runtime logs that the node was cancelled. The part people don't expect is what's left
in the session: nothing. The assistant's turn is only written when the turn completes, so the session
has the user's question and no reply. I measured two events consumed and one event stored, authored by
`user`. The user saw two chunks of an answer that the conversation's history says was never given, so
their follow-up is asked of a transcript where we never spoke, and it reads to them as the assistant
forgetting. There's no correct default — you either finish the turn anyway and pay for an answer
nobody read, or store what you streamed with an explicit incomplete flag — but it has to be a
decision, and it should be logged either way, because abandonment is a metric worth having."*

findings you had not absorbed.
