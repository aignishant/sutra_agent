# 5.2 — What a real streaming system adds

## One-line answer

The lab streams correctly, and the distance between it and something you would put in front of users
is not vague "hardening" — it is a **list of nine specific things**, each one cheap on the day the
feature is written and expensive on the day it is needed, and several of them are deliberately parked
by this curriculum rather than forgotten.

## The story

You put a tent up in a field on a still, warm evening, and it goes up beautifully. Poles through the
sleeves, four pegs at the corners, done. You sit outside it feeling clever.

In the morning you notice the tent on the next pitch, and how much more of it there is. The guy ropes
are out and pegged, not tucked away inside the flysheet where they came from the shop. There is a
groundsheet under the floor. There is a mallet, instead of the side of somebody's shoe. There is a
torch hanging from the loop by the door, pointing down. And there is a small bag with four spare pegs
in it, which is the strangest one, because who buys spare pegs.

None of that cost much. A mallet is a mallet. What it cost was knowing to buy it, and the way you
learn to buy it is the same way for everyone: one night, in the dark, in the rain, with a bent peg.

The two tents look the same on a still evening. They are not the same tent.

## The idea in plain language

The lab works. `wire.py` frames a payload with a newline in it and gets all ninety characters back.
`partials.py` turns six events into ninety characters instead of a hundred and eighty.
`cancel.py` hangs up half-way and tells you exactly what the session kept. Nothing in any of it is
wrong.

But "it streams" and "I would put this in front of users" are two different claims, and the gap
between them is a **list**. Not a mood, not a quality bar, not "make it production-ready" — an
enumerable set of items, each of which you can point at, price, and decide about. Here is the whole
of it for this day's stream.

| What the lab has | What a real one adds | What it costs |
| --- | --- | --- |
| `data:` lines and nothing else | an **`id:` on every message**, and a client that sends the last one it saw back when it reconnects | the server must be able to resume from an id, which means keeping the turn's recent messages where it can read them again |
| a stream that simply ends | an explicit **end-of-turn message** | one more message, and every client has to understand it |
| no keep-alive at all | a **heartbeat** on an idle stream, so nothing in the middle decides the connection is dead (part [3.3](../03-the-wire/3.3-what-sits-in-between.md)) | traffic on connections that have nothing to say, and a client that ignores heartbeats correctly |
| a consumer that reads as fast as it likes | **backpressure**: a decision about what happens when the reader is slower than the producer | a buffer with a bound on it, and a rule for what to drop or block |
| a rule for turning events into an answer, written once inside a lab script | the same rule, in one importable place, named for its job (part [2.2](../02-the-final-chunk/2.2-three-rules.md)) | nothing at all, if it is done on the first day |
| nothing stored when the reader disconnects | a decision about the interrupted turn, and a log line saying it happened (part [5.1](5.1-the-reader-who-leaves.md)) | a schema that can express "incomplete" |
| the final aggregated event trusted as the answer | the same, plus a check that the turn actually completed | one field |
| one metric: did it work | **time to first token** and time to completion, measured separately | two metrics instead of one |
| a renderer that appends every chunk the moment it arrives | batching chunks before touching the screen | a small delay, introduced on purpose |

Four terms in that table are used here for the first time, so they get plain definitions before
anything else happens.

**Resumption** is picking a stream up where it stopped, rather than starting it again from the
beginning or losing the rest of it. A **heartbeat** is a message sent for no reason except to keep
bytes moving on a connection that currently has nothing to say. **Backpressure** is what a system
does when the side reading the data is slower than the side producing it. And **time to first token**
is the gap between the reader asking and the first piece of the answer appearing in front of them —
as opposed to time to completion, which is the gap between asking and the last piece.

Three of the nine deserve more than a table row, because all three look trivial and none of them is.

## Why Sutra needs it

Because the hub's §4 hands you a build brief for `sutra/stream.py`, and the brief is not this list.
It asks for `collect`, a mode parameter, a `frame` that splits on newlines and a decision about the
disconnect. That is what the day teaches, and it is deliberately smaller than what you would deploy,
because a build brief containing all nine of these would be a fortnight of work with the teaching
buried somewhere inside it.

So this part is the bag of spare pegs. Everything in the table is something the person who has run a
streaming endpoint knows and might never write down, and the whole reason to write it as a list is
that a list can be argued with. A reader who finishes this day believing `wire.py` is
production-shaped has learned the mechanism and is going to learn the rest of it in the dark.

## The mechanism

There is no new code today. The mechanism is three rows of the table, argued properly.

### Resumption, and why it needs `id:`

Part [3.1](../03-the-wire/3.1-what-sse-actually-is.md) named the four fields the format defines and
said the lab implements exactly one of them. Here is the encoder, unchanged, from `lab/wire.py`:

```python
def frame(chunk: str) -> str:
    """One `data:` line per line of the chunk. The parser rejoins them with a newline."""
    body = "".join(f"data: {line}\n" for line in chunk.split("\n"))
    return body + "\n"
```

**Line by line:**

- `body` is built entirely from `data:` lines, and there is no other field anywhere in the function.
  That is the missing `id:` — not hidden behind a flag, not stubbed out, simply absent.
- Where it would go is the easy half: one more line, of the shape `id: <number>`, written **before**
  the `data:` lines of the same message, since fields of one message travel together and the blank
  line at the end of `body` is what separates messages. Prepending it is a one-line change to this
  function.
- The counter that produces that number cannot live inside `frame`. This function is called once per
  chunk with no memory between calls, so a message number has to be owned by whatever is driving the
  turn — which is the first sign that the change is not really about this function.

Now the hard half, and it is not on the client's side at all. The client's side is already written
for you: this format reconnects by itself, and the reconnecting client sends back the last id it saw.

The hard half is what your **server** must now be able to do. It is handed "I last saw message 41"
and it has to produce message 42 onwards. For a model's output there are exactly two ways to do that,
and both have a bill.

**Keep the turn's messages.** Every message you emit is also written somewhere a reconnecting request
can read it — in memory on that one machine, which stops working the moment there are two machines,
or in a store both machines can reach, which is a piece of infrastructure with a lifetime, an
eviction policy and a decision about how long a resumable turn stays resumable.

**Or generate it again.** Ask the model the same question, throw away the first forty-one messages'
worth of output, and stream the rest. This is genuinely simpler and it costs a second request for an
answer you have already paid for once — Day 72's wasted-requests accounting, arriving one layer down
— and it is not even the same answer, because the model is free to word it differently the second
time, so the reader gets a join in the middle of a sentence.

That is the point worth carrying away. "It just reconnects" is true of the *format*. On the server it
is a design decision with a bill attached, and the decision is between storage you have to operate
and a request you have to pay for. Neither is free, and picking neither is also a choice: it means a
dropped connection loses the tail of every answer in progress.

### End-of-turn, and why a stream that simply ends is ambiguous

From the reader's side, a turn that finished and a connection that dropped look **identical**. The
events stop. That is all either of them does.

This is exactly the shape of Day 73 part 3.3's argument about the nightly job that quietly stops
being triggered: the absence of a thing is not a signal, because nothing arrives to carry it. There
the missing signal was a digest that never appeared. Here it is one layer down, on a single
connection, over a single turn — but it is the same hole, and it has the same fix, which is to make
something arrive.

An explicit terminator — a final message the client can recognise, whether that is a named event or a
sentinel inside `data:` — changes two things at once:

- *"It stopped"* becomes *"it finished"*, which is what lets the client stop the spinner, enable the
  copy button, and store the answer without hedging.
- And the absence of that terminator becomes a **detectable failure** rather than a normal ending.
  The client can now say "the stream ended and I never got the done message", which is a branch you
  can write code in. Before the terminator existed, there was nothing to branch on.

The cost is one message and the fact that every client has to understand it. That is the whole cost,
which is why leaving it out is one of the least defensible items on the list — and it is left out of
first versions constantly, because on a working demo the connection never drops and the ambiguity
never shows.

### Backpressure

The lab's consumer is a `for` loop over an in-memory string. It never falls behind, because there is
nothing for it to fall behind. Every real consumer can.

A browser on a slow connection reads the response as fast as the network hands it over, which on a
bad train is not very fast. A logger writing each chunk to disk goes at the speed of the disk. A
process that forwards each chunk to somewhere else goes at the speed of that somewhere else. In all
three, the producer — the model, which is producing tokens at whatever rate it produces them — can be
faster than the thing consuming them, and then something has to give. There are exactly three
options.

| Option | What happens | What it costs |
| --- | --- | --- |
| **Buffer** — hold the unread chunks in memory | the reader eventually catches up and gets everything | memory that grows with the gap; with no bound on it, one slow reader can take the whole process down |
| **Drop** — throw away chunks the reader was not fast enough for | memory is bounded and the connection stays healthy | the reader is silently missing text, and nothing on either end knows which text |
| **Block** — stop producing until the reader asks for more | nothing is lost and memory is flat | the model connection is held open while nobody is reading, and on some providers that is a resource you are paying to keep idle |

The choice depends on one question: **is the content replaceable?** For a live video feed it is —
dropping a frame is invisible, and the next frame is along shortly. For a metrics stream it usually
is: a missed sample is a gap in a graph.

For a model's answer it is not. Every chunk is a piece of a sentence, and there is no later chunk
that makes up for a missing earlier one. So the drop option is out, on the content's own terms,
before you have looked at any code — which leaves a bounded buffer, blocking when it fills, and an
explicit decision about what happens when a reader stays slow for a long time. Making that decision
badly is how a streaming endpoint that works perfectly for one reader falls over with four hundred.

## When it breaks

**The shape of this list is the interesting thing about it.** Every item is cheap on the day the
feature is written and expensive on the day it is needed. An `id:` per message is one line now and a
lost answer tail later. A terminator is one message now and an unfixable client ambiguity later. Time
to first token is a timestamp now and an unanswerable question later, when somebody asks whether
streaming actually helped and there is no number to answer with.

And yet almost no first version has any of them — including this one. That is not laziness. It is
that **each item is individually skippable and only collectively necessary**. Take any single row on
its own and the case for skipping it is genuinely good: connections rarely drop on a fast office
network, the client can just assume the stream ended cleanly, one reader is never slow, the answers
are short. Every one of those arguments is true. What is false is the conclusion you reach by making
all nine of them in a row, which is an endpoint that demos perfectly and cannot be operated.

Nobody buys the guy ropes on the still evening either.

**Several items are parked by this curriculum, and parked is not forgotten.**

🅿️ **Everything that needs a browser or a deployed server.** The heartbeat, the buffering
intermediary of part [3.3](../03-the-wire/3.3-what-sits-in-between.md), the batching renderer, a real
client disconnect rather than part [5.1](5.1-the-reader-who-leaves.md)'s polite `aclose()`, and any
honest measurement of time to first token. The lab has neither a browser nor a deployed path, and a
measurement taken without one would be a measurement of `_fake.py`, which produces its chunks with no
delay at all. Naming these as parked is the honest move; pasting numbers for them would not be.

🅿️ **The bidirectional session.** Part
[4.1](../04-the-bill-for-voice/4.1-what-a-live-session-is-made-of.md) showed that `run_live` is a
different shape of program — a queue you keep pushing into rather than a message you send — and part
4.2 recorded why Addendum 02 will not pay for a model that holds an audio session open. Every item in
this part's table is about a one-directional stream. The bidirectional case has its own list, and
this day does not own it.

**And the honest thing about the list itself.** It is not a standard. There is no specification
anywhere that says "a streaming endpoint shall have these nine properties". It is drawn from the
failures this day actually measured — the doubled answer, the dropped tail, the cancelled turn — plus
ordinary field knowledge about what streaming systems grow once real readers use them. So treat it as
a checklist to **argue with** rather than one to comply with. If you can say why a row does not apply
to your system, that is a better outcome than ticking it, and a row you cannot argue about is a row
you have not understood.

## In production

**What you would actually build first, for a small product with real users.** Not a ranking asserted
— an order, with a reason each time, and the reasons compound.

1. **The end-of-turn message.** It comes first because it is the only item that turns an ambiguity
   into a branch, and several later items need that branch to exist before they can be written. You
   cannot log an interrupted turn if you cannot tell an interrupted turn from a finished one. It
   costs one message.
2. **Time to first token and time to completion, separately.** Second because it is nearly free and
   because it is the number every later argument needs. Without it, "should we keep streaming on for
   this endpoint?" is a matter of taste, and the whole case for the feature — the one the paper makes
   — is a claim about the first of those two numbers while the second is unchanged.
3. **The disconnect decision, plus a log line.** Third because it is a correctness bug in the
   conversation's history rather than a performance nicety: part 5.1 measured a session holding the
   user's question and no reply. It also gives you abandonment as a number, which is the first real
   signal about whether the answers are any good.
4. **The heartbeat.** Fourth because it is cheap and it prevents a class of failure that looks
   exactly like a bug in your code — an answer that dies part-way through, on some networks and not
   others, with nothing in your logs. Cheap prevention of an expensive-to-diagnose failure earns its
   place high on the list even though nothing has gone wrong yet.
5. **`id:` and resumption.** Fifth, deliberately, because it is the expensive one — it is the row
   that makes you operate a store or pay for a second request — and because items 2 and 3 will tell
   you how much you need it. If almost nobody is disconnecting mid-answer, this is a large piece of
   infrastructure bought for a rare event.

Backpressure and the batching renderer sit below all five, and honestly so: both are about a real
client under real load, and until one exists you would be guessing at the bound on the buffer and the
size of the batch. The one thing to do about them early is to leave the seam — make the consumer a
thing you can put a bounded queue behind, rather than a `for` loop welded to a socket.

**A streaming endpoint has a test problem, and it is worth stating plainly.** Almost every failure in
this part's table is invisible to a unit test. A unit test runs the producer and the consumer in one
process, on no network, with nothing in between: the connection cannot drop, so resumption is
untestable; the reader is never slow, so backpressure never triggers; nothing buffers the response,
so part 3.3's intermediary cannot appear; and the fake model answers instantly, so time to first
token is zero. Part 3.3 makes the same point from the other side — nothing on your server can detect
a proxy that is re-assembling your stream. The only test that catches these has to run against a
**deployed path**, with a real client, over a real network. That is a slower and more annoying test
than the ones you have, and it is the only one that is about the subject.

**The review comment a senior engineer leaves:** *"Streaming works and I'm happy with the framing.
Three things before this goes in front of users. Send an explicit done event — right now a finished
answer and a dead connection are the same thing to the frontend, and it will guess wrong in the
direction that leaves a spinner running forever. Record time to first token and time to completion as
two separate metrics, because the whole argument for this feature is about the first one and we
currently can't show it moved. And decide what happens on disconnect and log it, per the other
review. I'd take an `id:` per message and a resume path as a ticket rather than a blocker, but let's
be clear that we're choosing not to have it: today a dropped connection loses the rest of that
answer, and the fix is either keeping recent messages somewhere or paying for the turn twice. Also,
please don't append straight into the DOM on every chunk — batch them — and put a bound on whatever
buffer sits between the model and the socket before we find the bound the hard way."*

**The interview question:** *"You've got streaming working. What's left before you'd put it in front
of users?"* An honest spoken answer: *"I'd answer with a list rather than 'harden it', because the
gap is specific. First, an explicit end-of-turn message — without one, a completed answer and a
dropped connection look identical to the client, since both are just the events stopping, and that
ambiguity is what makes every other failure undiagnosable. Second, two metrics instead of one: time
to first token and time to completion, separately, because streaming doesn't change the second at all
and the entire case for it is about the first. Third, a decision about what happens when the reader
disconnects mid-turn — in the runtime I measured, the session keeps the user's question and no
assistant turn at all, so their next message lands on a transcript where we never replied. Fourth, a
heartbeat, because an idle connection gets cut by something in the middle and it looks like a bug in
your code. Fifth, an `id:` on every message so a reconnecting client can resume — and I'd say out
loud that this is the expensive one, because the server then has to be able to produce message
forty-two onwards, which means either keeping the turn's messages somewhere retrievable or
regenerating and paying for the answer twice. After that, backpressure: my consumer is currently a
loop that never falls behind, and a real one is a browser on a bad connection, so I have to choose
between buffering, dropping and blocking — and for a model's answer dropping is out, because every
chunk is part of a sentence and there's no later chunk that replaces a missing one. The last thing
I'd say is that most of that can't be unit tested. The interesting failures need a deployed path and
a real client, so the test that matters is the slow one."*
