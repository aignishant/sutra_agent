# 1.2 — One field on RunConfig

## One-line answer

Streaming is not a display setting: the `streaming_mode` field you put on `RunConfig` travels all the
way down to the model call and becomes the model's `stream` argument — one expression,
`stream=run_config.streaming_mode == StreamingMode.SSE` — so it changes **what the model yields**,
not how a client draws it, and any design that files it under front-end has put the seam in the
wrong place.

## The story

You order a spare part for the washing machine, a heavy box, and at the checkout there is a small
tick box under the address. *If I'm out, leave with a neighbour.* It sits between the phone number
and the *place order* button, in the same grey as everything else on the form, and it reads like a
preference — the sort of thing that decides which message you get rather than what anyone does.

You tick it. Of course you do. Better that than another card through the door.

On the delivery day you are out, and what happens is not what the tick box sounded like.

The van never stops outside your flat at all. The driver's handheld had already re-planned the drop
before he pulled out of the depot: it sent him to number 41, because number 41 has been taking this
street's parcels for as long as anyone can remember and the round is quicker done that way. The name
on the signature line is not yours. The tracking page says *delivered*, against a name you have to
squint at. And when the part turns out to be the wrong one, the return is being argued about a
delivery that a different household signed for, which is a different conversation with the shop than
the one you were expecting to have.

None of that was a display choice. You did not change how you were told about the parcel. You
changed how the parcel was carried, where the van went, and whose signature ends up on the record.
One tick box, on a form, a long way from the street it rearranged.

Hold on to that box. Everything below is the same shape: one small field, set far away from where
its consequences appear, that changes how the work is done rather than how the result is presented.

## The idea in plain language

Part [1.1](1.1-the-blank-screen.md) argued that streaming changes *when the reader is served* and
never how fast the work is. This part is about the field that asks for it, and about how far that
field travels.

`RunConfig` is the settings object for **one run**. You hand it to the runner when you start a turn,
and it carries the choices that are about *this* execution rather than about the agent: how many
model calls are allowed, what the run may save, and — the field this day is about — `streaming_mode`.

`streaming_mode` is an **enum**. An enum is a type whose values are a fixed, named set: not any
string you like, but exactly these members and no others. `StreamingMode` has exactly three, read
off the installed `google-adk==2.7.1` on 2026-09-06.

| Member | What it says where you set it | What it actually causes |
| --- | --- | --- |
| `NONE` | do not stream this run | the model is called with `stream=False` and yields one response carrying the whole answer |
| `SSE` | stream this run over one ordinary HTTP response | the model is called with `stream=True` and yields chunks, then a final response |
| `BIDI` | a live, two-way session | nothing at all on `run_async` — it belongs to a different entry point, `Runner.run_live` |

The important word in the third column is *causes*. The mode is not read by the browser, and it is
not read by whatever renders the text. It is read by the runtime, one layer above the model, and
turned into an argument on the model call itself.

The place where that happens has a name worth having. A **seam** is the single point where a
decision crosses from one layer into another — where a setting stops being a setting and becomes
something a lower layer acts on. Find the seam and you know the true blast radius of a config field,
because everything downstream of the seam is affected and everything upstream of it is not.

For streaming in ADK, the seam is one expression, and it is short enough to memorise. That is the
whole of this part.

## Why Sutra needs it

Because ADK-52 is *streaming architecture*, and the word in it that earns the day is **architecture**.
If `streaming_mode` were a display preference, it would belong in the web layer with the font size
and there would be nothing to design. It is not, and the difference shows up in three places this
project has to get right.

**The mode is a parameter, not a constant.** §4's build brief asks for `answer(..., mode)` in
`sutra/stream.py` precisely because a hard-coded mode cannot be turned off. Day 73 built an ambient
agent — the nightly job that assembles a digest with nobody watching — and that job calls the same
desk as a person does. A person wants the words as they arrive. A nightly batch has no screen, no
reader and no reason to handle six events where one will do. Same agent, same instruction, two
callers, two modes.

**The safe answer has to be the default.** Partial events are a different shape of output. A caller
that never asked for them should never be handed them, and the way that is guaranteed is that saying
nothing means `NONE`.

**And the free-quota question hangs off the same enum.** ADK-53 asks what live voice would cost, and
`BIDI` looks like it is one more setting of the dial you are already turning. It is not. Part
[4.1](../04-the-bill-for-voice/4.1-what-a-live-session-is-made-of.md) shows what it actually needs,
and the first step to understanding that is seeing that the seam below tests for `SSE` specifically
and therefore has nothing to say about `BIDI` at all.

## The mechanism

Three places, top to bottom: where you set the field, where the runtime reads it, and where the model
receives it.

### Where you set it

This is `drive()` in `lab/_fake.py` — the function every measurement on this day goes through. One
turn, one mode, and a list of the events that carried text.

```python
async for event in runner.run_async(
    user_id="learner",
    session_id=session.id,
    new_message=message,
    run_config=RunConfig(streaming_mode=mode),
):
```

**Line by line:**

- `runner.run_async(...)` is the ordinary way to run a turn: you give it who is asking, which session
  the turn belongs to, and the message. It returns an asynchronous generator of events, which is why
  the call sits behind `async for` rather than an `await` — the events arrive one at a time and the
  loop body runs on each.
- `run_config=` is passed **by name**, and it has to be. In ADK it is a **keyword-only argument**: an
  argument that can only be supplied as `name=value` and never by position, no matter how the
  arguments are ordered in the signature. On the installed `google-adk==2.7.1` it is declared as
  `run_config: Optional[RunConfig] = None`. The practical consequence is that you cannot pass it by
  accident, and you cannot pass it in the wrong slot: it is either named or it is not there.
- Because its default is `None`, **passing nothing gets you `NONE` behaviour** — no partial events, a
  single response. That is the correct default and it is the tick-box lesson pointed the other way: a
  caller who never ticked anything should get the plain delivery to their own door, not a rearranged
  round. A library that streamed by default would be handing every existing caller a new output shape
  on an upgrade.
- `RunConfig(streaming_mode=mode)` is constructed **inside the call**, per run. Read that literally:
  the mode is not on the agent and it is not on the app. `desk()` two functions up builds the agent
  and knows nothing about streaming — its docstring says so. The same agent object can be streamed
  for a person at a keyboard and not streamed for Day 73's nightly digest run, and neither run has to
  know the other exists.
- `mode` is a parameter of `drive()` rather than a literal, which is what makes `lab/modes.py` able
  to run the identical turn twice and compare. Part [1.3](1.3-one-event-or-six.md) is that comparison.

### Where the runtime reads it

Now find the seam yourself rather than taking this page's word for it. This asks the installed
package for its own source and prints every line in the flow that passes a `stream=` argument.

```bash
uv run python -c "
import inspect
from google.adk.flows.llm_flows import base_llm_flow
src = inspect.getsource(base_llm_flow)
for i, line in enumerate(src.splitlines(), 1):
    if 'stream=' in line:
        print(i, line.strip())
"
```

**Line by line:**

- `uv run` executes this inside the project's own environment, so what it reads is the version this
  repository pins rather than whatever Python is first on your `PATH`. That matters more than usual
  here: the whole point of the command is to be told the truth about *your* install.
- `base_llm_flow` is the module that drives one turn: it assembles the request, calls the model, and
  turns what comes back into events. It is the layer directly above the model, which is where a seam
  of this kind has to live.
- `inspect.getsource(...)` hands back the module's own text from disk. Nothing is fetched and nothing
  is guessed — this is Principle 8 as a command rather than as a claim.
- `enumerate(src.splitlines(), 1)` numbers the lines from one, so the output tells you *where* as well
  as *what*. Keep the number; it is half of the record you write down.
- The filter is `'stream=' in line` and not the full expression, deliberately. Searching for the
  answer you expect will only ever confirm it. Searching for the argument shows you every place the
  flow decides anything about streaming, including any you did not know about.
- No output is pasted here on purpose. The line number depends on the installed version and was not
  captured for this page, and inventing one would be exactly the failure this command exists to
  prevent.

What it printed on 2026-09-06, against `google-adk==2.7.1`, is this expression — and this is the
sentence the rest of the day rests on. It is quoted exactly as it appears in the package, trailing
comma and all, which is why it is shown as text rather than as Python: on its own it is a fragment of
an argument list rather than a statement.

```text
stream=run_config.streaming_mode == StreamingMode.SSE,
```

**Line by line:**

- `stream=` is the argument being built. To the right of the equals sign is not a variable being
  looked up but a comparison being evaluated, and the result of a comparison in Python is a `bool`.
  So the value handed to the model is `True` or `False`, and nothing else ever reaches it.
- `run_config.streaming_mode` is the field you set at the top of this section, read here, one layer
  above the model. Between your call and this line the config was carried along unchanged; this is
  the first and only place it is turned into something a lower layer acts on.
- `== StreamingMode.SSE` tests for **one member by name**. It does not ask "is streaming enabled",
  because there is no such question — there is an enum with three members and this expression is
  interested in exactly one of them.
- Which makes `BIDI` a genuine trap, and it is the sharp edge of this part. `SSE` and `BIDI` share an
  enum, so they look like two settings of one dial. They are two different programs. `SSE` is this
  expression evaluating to `True` on the ordinary path. `BIDI` is a different entry point altogether,
  `Runner.run_live`, which part
  [4.1](../04-the-bill-for-voice/4.1-what-a-live-session-is-made-of.md) takes apart. Against *this*
  expression, `BIDI` is simply not `SSE`, and the comparison is `False`.
- The trailing comma is worth a glance too: this is one argument among several in a call that is
  spread over several lines. The seam is not a function, not a branch and not a strategy object. It
  is an argument expression inside a call, which is why it is easy to miss and why finding it is
  worth a command of its own.

### Where the model receives it

And here is the other side of the seam, in `lab/_fake.py`'s scripted model:

```python
async def generate_content_async(
    self, llm_request: LlmRequest, stream: bool = False
) -> AsyncGenerator[LlmResponse, None]:
```

**Line by line:**

- This is not a shape invented for the lab. `BaseLlm.generate_content_async(self, llm_request:
  LlmRequest, stream: bool = False)` is the abstract method every model in ADK implements, on the
  installed `google-adk==2.7.1`. `stream` is therefore part of the **model interface** — not a runner
  detail, not a transport detail, and not a thing the web layer knows about.
- `stream: bool = False` repeats the safe default one layer further down. A model called with no
  opinion about streaming answers in one piece.
- `-> AsyncGenerator[LlmResponse, None]` is why a single flag can change the output shape at all. The
  method does not return a response; it *yields* them. `stream=False` yields once, `stream=True`
  yields many. Same method, same caller, different number of things coming out of it, decided by the
  argument.
- `_fake.py`'s implementation branches on the flag: `if not stream:` yields the whole answer and
  returns, otherwise it yields the five scripted chunks and then a final response. That branch is a
  faithful model of what a real provider does, which is the reason this day costs no quota.
- A model that **ignores** the flag is not broken. It simply always returns one response — which is
  precisely how a non-streaming provider behaves. The flag is a request, and the honest reading of
  the interface is that the runtime asks and the model answers in whatever shapes it has. What you
  must not do is assume that setting `SSE` guarantees more than one event.

So the chain is four links long and has no branch in it: your `RunConfig`, the runner, one comparison
in the flow, the model's `stream` argument. That is the entire distance between a field on a settings
object and the number of things the model yields — and part [1.3](1.3-one-event-or-six.md) measures
what that does to one identical turn.

## When it breaks

**A line number is not an API.** The expression above is stable enough to teach and to build on; the
file it sits in and the line it sits on are not. Modules get split, flows get refactored, and a
number that was true against `2.7.1` on 2026-09-06 is a fact with a date on it rather than a
contract. So the correct response to a version bump is not to trust this page — it is to run the
command again, read what comes back, and write down the version, the line and the date you ran it.
That is Principle 7 and Principle 8 in the same breath: never invent a version, never invent an API,
and when you cannot verify something today, record the command rather than a guess.

**`BIDI` on `run_async` does not raise, and that is the problem.** Read the expression again and
follow it honestly. It tests `run_config.streaming_mode == StreamingMode.SSE`. Set `BIDI` and the
comparison is `False`, exactly as `NONE` would be. Nothing in that line is looking for a mistake, so
nothing complains: what you have asked for is a bidirectional live session, and what the code as
written would hand the model is `stream=False`. The practical result is an ordinary non-streaming
run, silently, from a setting whose name promises the most interactive thing in the framework. This
is a reading of the quoted expression rather than a measurement — this page did not run it — and it
is exactly the tick box again: you can tick a box the form accepts and still have the round planned
by a rule that was only ever looking for a different box. If you want a live session, you change
entry point, not enum member. Part
[4.1](../04-the-bill-for-voice/4.1-what-a-live-session-is-made-of.md) is what changing entry point
costs.

**The decision is made before the first token, so it cannot be changed half-way.** `stream` is
evaluated once, when the model call is constructed. There is no way to start a turn plainly and
promote it to streaming because the answer turned out long, and no way to give up on streaming
mid-turn and ask for the whole thing instead. Whatever you decide is decided for the entire turn,
before a single token exists. If a product wants "stream only when the answer will be long", that is
not a config change — it is a routing decision taken before the run starts, on evidence you have
before the model has said anything, and it belongs wherever you choose the mode rather than anywhere
downstream of it.

## In production

**One place decides, and it is the entry point.** The mode is per-run, which is a gift and a hazard.
The gift is that one agent serves an interactive surface and a batch worker without knowing which it
is talking to. The hazard is that "per-run" quietly means "per call site", and a codebase that
constructs `RunConfig` in fifteen places has fifteen independent opinions about streaming, none of
them written down. What a professional does is thread the mode from the boundary: the HTTP handler
that serves a human passes `SSE`, the scheduled worker that produces Day 73's nightly digest passes
`NONE`, and the agent code in between takes it as a parameter and never names a member. That is what
`answer(..., mode)` in the build brief is for.

**What changes at scale is the cost of the choice, not the cost of the tokens.** Streaming does not
change the work the model does; the same tokens are produced. What it changes is what your system
holds open and how much it handles. A streamed turn is a connection that stays alive for the length
of the answer, a client that must survive a mid-answer disconnect, and one event per chunk to be
routed, logged and rendered instead of one per turn. Multiply the number of events by every
concurrent reader and streaming becomes a load characteristic of your service, not a preference on a
form. Turning it off for machine callers is not tidiness; it is the largest and cheapest saving
available, and it is one argument.

**Non-streaming is also what you test with.** An evaluation harness, a replay, a regression suite:
none of them have a reader, and every one of them is easier to assert about when a turn produces one
event carrying the whole answer. Deciding the mode at the boundary means your tests can pin it
without touching the agent, and it means the streaming-specific rules — the ones part
[1.3](1.3-one-event-or-six.md) starts measuring and section 2 turns into a real bug — are tested
deliberately rather than incidentally.

**The review comment a senior engineer leaves:** *"Two things. First, `streaming_mode` is not a UI
flag, so I don't want it defaulted inside the agent or read from a template — it comes in from the
call site, and the batch path passes `NONE` explicitly so that anyone reading the worker can see
that it isn't streaming. Second, nobody writes `StreamingMode.BIDI` anywhere near `run_async` in this
codebase. That combination doesn't raise; it just quietly gives you a non-streaming run, because the
flow tests for `SSE` specifically. If we ever want a live session, that's a different entry point and
a separate design review, not an enum member. And the line you quoted from the flow — keep the
command that finds it in the repo next to the note, so the next person who bumps the pin re-runs it
instead of believing our comment."*

**The interview question:** *"Is streaming a front-end concern?"* An answer that shows the work:
*"No, and you can point at the exact place it stops being one. In ADK you set `streaming_mode` on
`RunConfig` when you start a run, and one layer above the model the flow builds the model call with
`stream=run_config.streaming_mode == StreamingMode.SSE`. That's the seam — one comparison, one
argument. Below it, `generate_content_async` is an async generator, so the flag decides whether it
yields once or many times. It changes what the model produces, not how anything is rendered, which
means the mode has to be decided by the caller: the interactive endpoint asks for it, the nightly
batch job doesn't, and the agent in between takes it as a parameter. The detail I'd flag in a review
is that the comparison tests for `SSE` by name, so setting `BIDI` and calling the ordinary run path
gives you a non-streaming run with no error — bidi is a different entry point entirely. And that
expression is what I read off the installed version on the day I used it; the line number it lives on
is a fact with a date attached, so the check is a command we re-run rather than a comment we
trust."*

```bash
uv run python -c "
import inspect

```

**Line by line:**

- It imports the flow module, reads its source off disk with `inspect.getsource`, numbers the lines
  from one, and prints every line mentioning a `stream=` argument. No network call, no API key, and
  nothing that depends on this page being right.
- Run it and read the whole output, not just the line you were hoping for. If more than one line
  comes back, that is information about your version and you want it.
