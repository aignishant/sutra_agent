# 1.3 — One event or six

## One-line answer

The same agent, the same question, one field changed: the answer arrives as **six** things instead of
**one**, five of them flagged `partial`, so what your code consumes has changed **shape** and not
only its timing.

## The story

A small station, one platform, and a board above the entrance that lists the next departures. The
board shows the whole list at once. You walk in, look up, read four lines, and you know where you
stand. If nothing is settled yet, the board is empty and you learn nothing at all from it.

The same station on a bad morning, when the board is broken. A member of staff stands on the platform
with a clipboard and calls each train out as it is confirmed. "Nine-forty to the junction, platform
one." A pause. "Ten-oh-five, delayed." A pause. Same trains, same information, in the end.

But you stand differently. With the board you glance once and go and sit down. With the caller you
have to stay within earshot, listen to every announcement, and keep your own note of what you have
heard so far, because no single announcement is the list — the list is what you have written down.
Miss one and your note is wrong, and nothing about the announcement you did hear will tell you that.

And her last announcement is not like the others. She says "that's the confirmed board" before it,
which is a different kind of statement from the ones before it — what she actually reads out then is
part [2.1](../02-the-final-chunk/2.1-the-answer-twice.md)'s whole subject, and it catches people.

## The idea in plain language

Part [1.2](1.2-one-field-on-runconfig.md) showed that `RunConfig(streaming_mode=...)` reaches the
model as a `stream` argument, in one expression. This part runs the same turn both ways and counts
what comes out.

Two words first, because everything below is made of them.

An **event** is one item the runtime hands your code as a turn proceeds. `runner.run_async(...)` is
an async generator, so your code sits in an `async for` loop and receives events one at a time until
the turn is over. An event can carry text, a function call, or nothing you care about at all.

**Partial** is a boolean flag on an event. `partial=True` means "this is a piece of an answer that is
still being written"; `partial=False` means "this one is not a piece". It is an ordinary field —
`event.partial` — and it is the only thing in the stream that tells the two kinds apart.

So the board and the caller are the two modes. `StreamingMode.NONE` is the board: one event, after
everything is settled, nothing before it. `StreamingMode.SSE` is the caller: a run of events you have
to stay in the loop for, each one a piece, and a last one marked differently.

The point of measuring it is that these are not the same programming problem wearing two coats. A
consumer written for the board reads one thing and is finished. A consumer written for the caller
keeps state across events, decides what to do with each one as it arrives, and has to have an opinion
about that flag. Swapping one field on a config object swaps which of those two programs you needed.

## Why Sutra needs it

The build brief asks for `sutra/stream.py` with a `collect(events)` function and an `answer(...,
mode)` that takes the mode as a parameter. Both of those exist only because the answer to "what does
a turn look like?" is *it depends on a field*, and the ledger of what it depends on has to be
measured rather than assumed.

The desk has two callers already, and they want opposite things. A person waiting on a support reply
is the platform, listening; the ambient nightly job from Day 73 is nobody in the building at all, and
would rather have the board — one object, once, with no loop to babysit. A hard-coded mode serves one
of them and taxes the other, which is why the mode is an argument in the brief.

And `collect` is the piece of code that has to work for **both** shapes. Six events in, one answer
out; one event in, the same answer out. Writing that function without first knowing that the counts
differ by six to one is how the bug in part 2.1 gets written.

## The mechanism

`modes.py` runs one turn against the scripted model in `_fake.py` and reports what it saw. The agent,
the instruction and the question are identical between the two runs; only the `RunConfig` field
differs.

```bash
cd days/day-74-live-api-streaming/lab
uv run python modes.py
```

**Line by line:**

- `cd` into the lab first. Every script here imports its siblings by plain name — `import _fake` — so
  it only resolves when the lab directory is the working directory.
- No flag means `StreamingMode.SSE`, which is the mode the runtime turns into `stream=True`.

Measured on 2026-09-06:

```text
streaming_mode: SSE
the model was asked to stream: [True]

  events carrying text        6
    of which partial          5
    of which final            1
  characters in the answer    90
  chars before first render   12  (13% of the answer)

    event 0  partial  'The invoice '
    event 1  partial  'PDF is blank '
    event 2  partial  'because the billing page '
    event 3  partial  'renders it before the fonts '
    event 4  partial  'have loaded.'
    event 5  FINAL    'The invoice PDF is blank because the billing page renders it before the fonts have loaded.'

  five partials and one final. The final is not the last chunk - it is the whole
  answer again, which is part 2.1's subject.
```

One line in that run is not part of the measurement and it is worth naming before it worries you. The
process also prints this on **stderr** — the second output channel a program writes to, the one
reserved for diagnostics, kept separate from the results on stdout so that logs and answers do not
get mixed together:

```text
Skipping missing token usage metadata for agent desk and model fake/streaming
```

That is the runtime saying it wanted to record how many tokens the turn cost and found no such number
to record, because the model here is a script and scripts do not report token counts. It is a gap
reported honestly rather than a failure, nothing was dropped from the answer, and the exit code is
unaffected. It is Principle 10 pointed at the runtime itself, and you will see it under both modes.

Now the ablation — the same turn with streaming switched off:

```bash
uv run python modes.py --none
```

**Line by line:**

- `--none` selects `StreamingMode.NONE`. That is the entire difference; the file has no second agent
  and no second code path for it.

Measured on 2026-09-06:

```text
streaming_mode: NONE
the model was asked to stream: [False]

  events carrying text        1
    of which partial          0
    of which final            1
  characters in the answer    90
  chars before first render   90  (100% of the answer)

    event 0  FINAL    'The invoice PDF is blank because the billing page renders it before the fonts have loaded.'

  one event, after the model finished. Nothing was on screen until everything was.
```

Side by side:

| Measure | `StreamingMode.SSE` | `StreamingMode.NONE` |
| --- | --- | --- |
| events carrying text | 6 | 1 |
| of which partial | 5 | 0 |
| chars before first render | 12 (13% of the answer) | 90 (100% of the answer) |
| characters delivered in total | 90 | 90 |

**The last row is the argument.** Ninety characters either way. Nothing was made faster, nothing was
made shorter, and the model did exactly the same work — which is the claim part
[1.1](1.1-the-blank-screen.md) made in words, now with a number under it. What moved is the third
row: the share of the answer that has to exist before the screen can change at all, from everything
to about an eighth. And
the price of that is the first two rows — six objects to handle where there was one, and a flag on
each of them that your code now has to read.

Where those numbers come from is one loop in `_fake.py`, and it is worth reading closely because
every guard in it is there for a reason you will meet later today:

```python
        for part in event.content.parts if event.content and event.content.parts else []:
            if part.text:
                seen.append((index, bool(event.partial), part.text))
        index += 1
```

**Line by line:**

- `if event.content and event.content.parts else []` is not defensive noise. A stream contains events
  that carry **no content at all** — bookkeeping the runtime emits as a turn proceeds — and both
  `event.content` and `event.content.parts` are optional, so either can be absent. Reaching straight
  for `event.content.parts` works on the happy path and raises `AttributeError` on the first event
  that is not one. Falling back to `[]` means such an event simply contributes nothing.
- `bool(event.partial)` is a conversion, not a habit. The field is optional: it can be `True`,
  `False`, or `None` when nothing set it. `None` and `False` behave the same in an `if`, so the bug
  never shows up in a condition — it shows up in the *output*, where a reader printing the raw field
  sees `None` in a column of `True`/`False` and has to guess what it meant. Converting once, at the
  point of collection, means the tuple only ever holds a real boolean.
- `if part.text:` is checked because a part can carry things that are not text — a function call,
  inline bytes, a thought. Those are part [2.3](../02-the-final-chunk/2.3-not-always-text.md)'s
  subject; here the check keeps the count honest, so `events carrying text` means exactly that and
  not `events`.
- `index += 1` sits **outside** the inner loop and outside the `if`, so it counts **every** event the
  runtime yielded, not just the ones that survived the filters. That is why the printed `event 0` …
  `event 5` are positions in the real stream rather than positions in a list of interesting things.
  Renumbering after filtering would make the output tidier and make it a fiction.
- The tuple is `(index, partial, text)` and nothing else. `modes.py` needs the position, the flag and
  the characters to produce every figure in both tables above, and collecting more would invite the
  script to answer questions it has not measured.

## When it breaks

Nothing raised in either run. That is the whole difficulty.

Go back to the platform. You hear "nine-forty to the junction, platform one", write it down, and walk
off satisfied — you have an announcement, in your own handwriting, and it is not the list. Nothing
about it looked incomplete.

The code version of walking off is any consumer that reaches for one event and stops. Take the first
one and render it, and under `NONE` you get:

```text
'The invoice PDF is blank because the billing page renders it before the fonts have loaded.'
```

while under `SSE` the identical line of code gets:

```text
'The invoice '
```

Same function, same agent, same question. One config field away, and the failure is a **plausible
short answer** rather than an exception. No traceback, no warning, no non-zero exit — because from
the runtime's point of view nothing went wrong: it yielded six events and the consumer chose to look
at one. The two things the language could have caught for you, an absent `content` and a `partial`
that is `None`, are exactly the two the loop above guards, and neither is the one that hurts.

The mirror-image break is the one this section refuses to teach: a consumer that keeps state across
events and adds up everything it is handed. That one is correct for five events out of six and wrong
for the sixth, and it is the subject of part
[2.1](../02-the-final-chunk/2.1-the-answer-twice.md).

The honest summary is that switching this field switches which bugs you are exposed to, and does it
without changing a single line of the agent.

## In production

**What changes at scale is arithmetic.** Six events per turn where there was one is six times the
plumbing on every path an event touches. If a turn writes one structured log line, it now writes six.
If it opens a tracing span, it opens six or it opens one and keeps it open across all of them, and
those are different designs with different failure modes. If each event is persisted, the write rate
into the session store is six times what your capacity plan assumed. A per-event hook that was
cheap enough to be invisible when it fired once a turn is now firing six times, and a real answer is
not five chunks, it is hundreds. That is the number to plan against: **per-event cost multiplied by
the length of the answer**, on every concurrent turn. Anything you attach to an event handler is
paid on every token, and code review is where that gets noticed, because a profiler will not find it
until the traffic is real.

**What a professional adds is a boundary.** One function that consumes events and returns an answer,
in one file, so the flag is read in exactly one place in the codebase — which is what the build brief
means by putting `collect` in `sutra/stream.py` rather than in each caller. Around it: the mode as an
argument rather than a constant, so the interactive path and the batch path can differ; a counter of
events per turn, because that number quietly tracks answer length and is free to record; and one
test that feeds `collect` a one-event stream and a six-event stream and asserts the **same** answer
comes back. That test is what stops the two modes from drifting into two code paths that only one
of them exercises.

**What only appears with real traffic** is the reader who stops listening. Six events assume six
opportunities to hand something over, and the caller can walk off the platform between two of them.
Part [5.1](../05-in-production/5.1-the-reader-who-leaves.md) measures what the session is left
holding when they do, and the answer is worse than most people guess.

**The review comment a senior engineer leaves:** *"This counts events with text, which is the right
thing to count for the table, but don't let that filter leak into the consumer — the production loop
has to survive events with no content, and the index has to stay the position in the real stream or
the logs won't line up with anything. Two asks. Put the mode behind a parameter now rather than when
the nightly job needs it, because that job wants one object and not a loop. And add up what we're
doing per event before we ship: we log, we trace and we persist on each one, and at one event a turn
that was free. At a few hundred it's the hot path."*

**The interview question:** *"What actually changes in your code when you turn streaming on?"* An
honest answer: *"The shape of what you consume, not the speed. I measured the same agent and the same
question under both modes: one event with streaming off, six with it on — five partials and a final —
and the total delivered was ninety characters in both cases, so nothing got faster. What moved was
how much of the answer had to exist before anything could go on screen, a hundred per cent down to
thirteen. The consequence is that a consumer written for one event is not a consumer that handles
six. The one-event version doesn't crash under streaming, it just renders the first chunk as if it
were the answer, which is a plausible-looking wrong result with no exception anywhere. So I'd put the
rule that turns events into an answer in exactly one place, take the mode as a parameter because
batch callers genuinely want the single object, and test both shapes through the same function. And
I'd count the per-event work early — six times the logging and tracing is fine, but a real answer is
hundreds of events, not five."*

## Check yourself

```bash
cd days/day-74-live-api-streaming/lab
uv run python modes.py
uv run python modes.py --none
```

**Line by line:**

- Both runs, one after the other, so the two outputs are on the screen together and the identical
  `characters in the answer` row is visible in both.

Before you run anything: add a sixth string to `CHUNKS` in `_fake.py` and predict all four numbers in
the SSE run — events carrying text, of which partial, characters in the answer, chars before first
render — then run it and check every one. Getting `chars before first render` right is the test of
whether you have understood which event it is measured from.

Then delete the `if part.text:` line and re-run both modes. Say what the counts do, and say why the
`index` column is the one thing in the output that does not move.

**Out loud, without scrolling up:** both runs delivered ninety characters and one of them showed
something on screen far earlier. If nothing got faster, what did?
