# 3.1 — What SSE actually is

## One-line answer

Server-Sent Events is not a protocol you need a library for — it is **one ordinary web response held
open**, carrying lines of the shape `field: value`, where a **blank line ends a message** and a line
whose field name you do not recognise is **ignored**; that is small enough to write and read back in
forty lines of Python, which is exactly why it is worth writing them.

## The story

You are standing in the shop with a basket, and your flatmate is at home reading the list down the
phone.

Neither of you ever agreed on a method. You just both know how it goes. They say a thing, then they
stop. The stop is what tells you the thing has finished. "Bread." Stop. "Six eggs." Stop.
"Washing-up liquid." Stop. Every time you hear the gap, you move your thumb down to the next line of
the note on your phone. The gap is doing all the work. Nothing else in the conversation tells you
where one item ends and the next begins — not the words, not the tone, not the length. The gap.

It works so well that neither of you can see it. Until the cheese.

"Two hundred grams…" — and here they turn the old packet over to check what it was called — "…of the
good cheese."

You already moved your thumb. You come home with two hundred grams of nothing in particular and,
separately, a block of the good cheese.

Nobody misheard a word. Every single sound arrived, in the right order, undamaged. The convention
was the whole design, and one item happened to have the separator sitting in the middle of it.

Hold on to that phone call. The rest of this part is the same conversation, written down: a stop
that means *this item is finished*, and — the piece the two of you never needed but a machine does —
a word at the front of everything that counts, so that anything else said on the line can be safely
ignored.

## The idea in plain language

Start with the thing SSE is built on top of, because there is nothing exotic underneath it.

When a program asks a web server for something, the server sends back an **HTTP response**: a few
lines saying what kind of thing this is and how long it is, then a blank line, then the content. In
the normal case that content is finished before it is sent, the server writes it, and the connection
closes. Response over.

**Server-Sent Events changes exactly one thing about that.** The server sends the opening lines,
says the content type is `text/event-stream`, and then *does not finish*. It holds the response open
and writes into it whenever it has something to say. The client is not polling, not reconnecting,
not asking again. It is reading the tail of a response that has not ended yet. That is the entire
mechanism, and everything else is a convention about what to write into that open pipe.

The convention has two halves and they are both in the phone call.

**A field is a line.** A **field** is one line of the shape `name: value` — a name, a colon, then
the rest of the line. The name says what sort of line this is. There are four names the format
defines, and no more:

| Field | What it carries | In the lab |
| --- | --- | --- |
| `data:` | the payload — the actual content of this message | ✅ implemented |
| `event:` | a name for this message, so the client can route kinds apart | ❌ not implemented |
| `id:` | a cursor: the client sends the last one it saw back on reconnect | ❌ not implemented |
| `retry:` | how long the client should wait before reconnecting | ❌ not implemented |

**A blank line is the stop.** A **message** is one complete item — a run of field lines, terminated
by an empty line. That empty line is the phone call's gap, and it is the only thing that says where
one message ends and the next begins.

Then the rule that makes the format survivable, and that the two of you on the phone never needed:
**a line whose field name is not one of those four is ignored.** Not an error. Not a warning. Thrown
away in silence, and the stream carries on. That rule is why a server can add a field next year
without breaking every client written this year, and it is a deliberate part of the design rather
than laxness.

`lab/wire.py` implements `data:` and nothing else, on purpose, because `data:` is the half that
shows the framing. The two fields worth knowing you are *not* getting are `id:` and `retry:` — those
are what make SSE **reconnectable**. A stream that stamps each message with an `id:` lets a client
that lost the connection say "I got as far as here" and be sent the rest, rather than the whole
answer again or nothing at all. This format is what browsers implement natively, and those two
fields exist for exactly that reason: the reconnect is meant to be the format's job rather than
yours. [5.2](../05-in-production/5.2-what-a-real-streaming-system-adds.md) is where resumption is
picked up properly, and where the gap between "streams" and "streams reliably" gets measured.

## Why Sutra needs it

Principle 4 says build the mechanism by hand once, then adopt the framework — so that the framework
is a convenience and never a mystery. This part is that principle applied to the thinnest,
most-ignored layer of the whole day.

Everything above section 3 has treated the stream as a Python object.
`RunConfig(streaming_mode=SSE)` goes in
([1.2](../01-the-blank-screen/1.2-one-field-on-runconfig.md)), events come out
([1.3](../01-the-blank-screen/1.3-one-event-or-six.md)), and a rule turns those events back into an
answer ([2.2](../02-the-final-chunk/2.2-three-rules.md)). None of that is what travels between your
server and a browser. What travels is text, and if you have never looked at it you have exactly one
debugging move available when the reader sees a truncated answer: read your own Python again and
hope.

The alternative is worth being concrete about. A format like this one can be watched live with
`curl`, because it is lines of text on an open response and nothing else. You can see the messages
arrive, in order, with your own eyes, and the question "did the server send it or did the client
lose it?" stops being a matter of opinion. A websocket frame cannot be read that way without
tooling.

There is also a specific debt in the day's build brief. `sutra/stream.py` is asked for a
`frame(chunk)` that splits a payload on newlines, and `lab/gate.py` calls it with `"a\nb"` and
expects **two** `data:` lines. That requirement looks arbitrary until you have read the two rules
above, at which point it is the only framing that can possibly be correct — and
[3.2](3.2-the-newline-in-your-payload.md) is the measured proof of what the obvious alternative
costs.

## The mechanism

Run the correct framing first, so you have seen the format work before you see it fail:

```bash
cd days/day-74-live-api-streaming/lab
uv run python wire.py; echo "exit: $?"
```

**Line by line:**

- `cd days/day-74-live-api-streaming/lab` — `wire.py` has no imports from the repository, so it runs
  from its own directory with nothing on `PYTHONPATH`. Nothing here reaches a network, which is the
  point: the format is checkable without a provider, a key or a request against anyone's quota.
- `uv run python wire.py` — `uv run` uses the project's pinned interpreter and environment rather
  than whatever `python` happens to mean in this shell. No package is added today, so this changes
  nothing in `pyproject.toml`.
- `; echo "exit: $?"` — `$?` is the exit status of the command that just finished. This run encodes
  its verdict in that number rather than only in its prose, which is what makes it usable as a check
  that can go red (Principle 11). `0` means every chunk survived the round trip.

Measured on 2026-09-06:

```text
framing: one data: line per line
4 chunks sent

  the bytes on the wire:
    'data: The invoice '
    ''
    'data: PDF is blank '
    ''
    'data: because the billing page '
    ''
    'data: renders it before the fonts'
    'data: have loaded.'
    ''
    ''

  what the receiver read back:
    'The invoice '
    'PDF is blank '
    'because the billing page '
    'renders it before the fonts\nhave loaded.'

  messages sent       4
  messages parsed     4
  characters sent     90
  characters received 90
  round-trip exact    yes

  Every chunk came back as one message, newline and all.
exit: 0
```

Read the middle block slowly, because the interesting thing is sitting in plain sight.

The first three chunks each became one `data:` line followed by one empty line — item, stop, item,
stop. The fourth chunk is different. `"renders it before the fonts\nhave loaded."` contains a line
break of its own, so it went onto the wire as **two** `data:` lines with **no blank line between
them**, and the receiver rejoined them into one message —
`'renders it before the fonts\nhave loaded.'`, newline intact. Four chunks sent, four messages
parsed, ninety characters each way.

That is the format doing exactly what it was designed to do. A message is not "a line" — it is
"everything up to the next stop", and a message is free to be several lines long. The phone call had
no way to express that, which is why the cheese went wrong. The written format does: keep talking
without leaving a gap, and it is all still one item.

Here is the encoder and the parser, whole. Forty lines is the entire subject of this part:

```python
def frame(chunk: str) -> str:
    """One `data:` line per line of the chunk. The parser rejoins them with a newline."""
    body = "".join(f"data: {line}\n" for line in chunk.split("\n"))
    return body + "\n"


def parse(stream: str) -> list[str]:
    """Read a stream back into messages. A blank line ends a message."""
    messages: list[str] = []
    lines: list[str] = []
    for raw in stream.split("\n"):
        if raw == "":
            if lines:
                messages.append("\n".join(lines))
                lines = []
            continue
        field, _, value = raw.partition(":")
        if field == "data":
            lines.append(value.removeprefix(" "))
    return messages
```

**Line by line:**

- `chunk.split("\n")` then one `data: {line}\n` for each piece **is the whole encoder**. There is no
  cleverness left over. A chunk with no line break in it splits into a list of one and produces a
  single `data:` line, which is the ordinary case; a chunk with a line break produces one `data:`
  line per piece, which is the case the fourth chunk exercised above.
- `return body + "\n"` appends the **blank line that terminates the message**. Every `data:` line
  already ends with its own `\n`, so this extra one produces the empty line between messages — the
  stop. Delete this single character and the whole stream becomes one enormous message, because
  nothing anywhere else says where a message ends.
- `raw.partition(":")` splits on the **first** colon only and returns three pieces: before, the
  separator itself, and everything after. This matters more than it looks. A payload can contain
  colons — a time, a URL, a Python dict printed out — and `raw.split(":")` would chop the payload up
  at every one of them. `partition` cannot, by construction, because it stops at the first.
- `field, _, value` unpacks those three. The middle one is the colon, which is never needed, so it
  is bound to `_` by convention to say "deliberately discarded" rather than silently indexed past.
- `value.removeprefix(" ")` strips **exactly one** leading space. The format's convention is a
  single space after the colon for readability — `data: hello`, not `data:hello` — and it is not
  part of the payload. `removeprefix` takes off one space if one is there and does nothing if it is
  not. `value.lstrip()` would have been the tempting one-word alternative and it would be a bug: it
  eats *all* leading whitespace, so a payload that is a line of indented code inside a Markdown
  block comes back left-aligned, and the indentation is gone with no error anywhere.
- `if field == "data":` with **no `else`** is the ignore-unknown-fields rule, implemented by
  omission. Say this out loud: **that missing `else` is a rule, not an oversight.** A line whose
  field name is `event`, `id`, `retry`, something invented next year, or nothing recognisable at all
  is dropped and the loop carries on. Everything in [3.2](3.2-the-newline-in-your-payload.md)
  depends on this behaviour being correct, so it is worth being sure now that a real parser does
  exactly the same thing.
- `if raw == "":` is the stop. An empty line closes the message under construction, joins its
  `data:` lines back together with `"\n"` — which is what makes the fourth chunk come back whole —
  and clears the buffer for the next one.
- `if lines:` before appending guards against a **run** of blank lines. Two empty lines in a row
  would otherwise append an empty message on the second one, and the stream in the output above ends
  with exactly that: two `''` entries, because the last message's terminator is followed by the
  split's trailing empty string. Four messages sent, four parsed — that guard is why the count is
  not five.
- `messages: list[str]` and `lines: list[str]` are annotated at the point of assignment because an
  empty list literal tells a reader nothing about what will end up in it.

## When it breaks

**This is a model of the format, not an implementation of the standard.** Be exact about what has
been left out, because "I wrote an SSE parser" is a claim, and this one is forty lines:

- No `event:`, `id:` or `retry:` handling. The parser sees those lines and drops them, which is
  correct for an unknown field and *wrong* for a field the standard defines and a real client acts
  on.
- No comment lines. A line beginning with a colon — `: this is a comment` — is legal and is meant to
  be ignored. Here it partitions into an empty field name, which is not `data`, so it is dropped,
  and the right answer by accident is still not the right answer for the right reason.
- No `\r\n` line endings. The standard permits a carriage return, a line feed, or both, and this
  code splits on `"\n"` alone. Point it at a server that ends lines with `\r\n` and every payload
  comes back with a trailing `\r` welded onto it.
- No HTTP layer at all. No headers, no `text/event-stream` content type, no chunked transfer
  encoding, no connection to hold open. The stream here is a Python string built in memory and read
  back in the same process.

Name those rather than implying completeness. A day that teaches you to hand-roll a mechanism owes
you the list of what the hand-rolled version is not.

**SSE is text.** That is not a detail; it is the format's one hard limit. There is no binary field
and no length-prefixed frame — every payload has to survive being a line of characters, which means
anything that is not text must be encoded into text first, typically base64, at a cost of roughly a
third more bytes on the wire plus the encode and decode at both ends. Part
[2.3](../02-the-final-chunk/2.3-not-always-text.md) showed that a partial is not always text — audio
bytes and inline data arrive as parts too — so this is not a hypothetical. Anything the model
streams that is not characters costs you a conversion before it can go down this pipe at all.

**SSE is one-directional.** The server sends; the client listens. There is no way for the client to
say anything back on this connection, because the connection *is* one response and a response only
travels one way. Anything the reader wants to send — a follow-up question, an interruption, a
microphone — needs a separate request, which is a second connection with its own lifetime and its
own failure modes. That asymmetry is precisely the difference that
[4.1](../04-the-bill-for-voice/4.1-what-a-live-session-is-made-of.md) turns into `run_live`, where
the input is not a message at all but a queue that stays open alongside the output.

And one that is not in this file at all, because it is not on your side of it: between your server
holding this response open and the reader's browser sits everything the request passes through, and
some of it would rather collect a response than forward it in pieces. That is
[3.3](3.3-what-sits-in-between.md), and nothing in `wire.py` can detect it.

## In production

**Why this format survives at all.** Websockets exist, are bidirectional, are binary-capable, and
are better than SSE at almost everything SSE does — and SSE is still what most streaming answers
arrive over. Four reasons, and the first one is most of the answer:

- **It is an ordinary HTTP response.** So it goes through what HTTP goes through: your existing load
  balancer, your existing authentication, your existing logging, your existing corporate proxy, your
  existing CDN. A websocket needs a protocol upgrade and a conversation with every one of those
  things. SSE needs a content type.
- **It reconnects by itself.** The reconnect is defined by the format — `id:` and `retry:` — and
  implemented for you, rather than being a state machine you write, get subtly wrong, and discover
  on a bad network.
- **You can read it with `curl`.** An engineer with a terminal can see the exact bytes the server
  emitted, which turns most streaming arguments into a two-command investigation.
- **It is one-directional, and so is the thing being sent.** A model answering a question is a
  one-directional problem. Paying for a bidirectional transport to solve it is buying a failure mode
  you have no use for.

**What a professional adds on top of these forty lines.** Three things, and none of them is a bigger
parser:

- **`id:` on every message**, so a reader whose connection drops resumes from the last message it
  saw instead of losing the tail of an answer or receiving the whole thing twice. Without it, a
  dropped connection is indistinguishable from a finished one.
- **A heartbeat.** An idle connection is a connection that something in the middle will eventually
  decide is dead. A periodic comment line — a bare `:` — keeps bytes moving without producing a
  message the client has to handle, which is what the comment syntax is actually for.
- **An explicit terminator message.** This is the one people leave out and regret. If the only
  signal that a turn has ended is the connection closing, then "the answer is complete" and "the
  network dropped" look **identical** to the client, and the client has to guess which one just
  happened. A final `event: done` — or a sentinel in `data:` — makes the difference explicit and
  turns a guess into a branch. Section 5's cancellation measurement is the same problem seen from
  the server's end.

**The review comment a senior engineer leaves:** *"This pulls in a client library to parse four
field names and a blank line, and then still doesn't handle the case where the connection drops
mid-answer — we have no `id:` on anything, so we can't resume, and there's no terminator, so the
frontend treats a dead socket exactly like a finished turn. Drop the dependency or keep it, I don't
mind, but frame the payload per line, stamp an id on each message, and send an explicit done event.
And put a `curl` of a real stream in the runbook, because next time this breaks the first question
is going to be whether we sent it."*

**The interview question:** *"Why would you use Server-Sent Events rather than a websocket for
streaming a model's answer?"* An honest spoken answer: *"Because it's an ordinary HTTP response that
I never end, so it travels through everything HTTP already travels through — the load balancer, the
auth, the proxy — with no upgrade handshake to negotiate with any of them. The format is tiny: lines
of `field: value`, a blank line ends a message, and an unknown field is ignored, which is what makes
it extensible without breaking old clients. I can read the whole thing with `curl`, which matters
more than it sounds when you're arguing about whether the server sent the bytes. And it's
one-directional, which fits a model answering a question, so a bidirectional transport would be
buying failure modes I have no use for. The two things I'd insist on before shipping it are an `id:`
per message so a dropped connection can resume, and an explicit end-of-turn message — because
otherwise a completed answer and a dead connection look exactly the same to the client. Where I'd
switch to a websocket is the moment the client needs to speak while the server is talking: live
audio, an interrupt, anything bidirectional. SSE genuinely cannot do that."*
