# 3.2 — The newline in your payload

## One-line answer

The encoder everybody writes first — one `data:` line per chunk, built with a single f-string — is
correct for every payload that happens not to contain a newline, and **silently loses everything
after the first newline** in one that does: **90 characters sent, 77 received, 13 gone**, exit code
`1`, and not one error anywhere.

## The story

🎬 **The scene.** You are filling in a paper form at a counter. The address block is a grid of
boxes, one line per row, and the person behind the counter tells you what everyone gets told: *"Put
the building on the first line and the street on the second."* So you write **Nandan Apartments** on
line one and **14 Kalyani Road** on line two. It is your address. It is legible. Anybody standing
next to you could read it back.

😬 **The naive fix.** Two weeks later a letter has not arrived, so you ring up and they read your
address back to you off the screen: *"Nandan Apartments."* That is all there is. So you say the
street again and they type it into the same first box, on the end, and you both agree the problem is
solved.

💥 **Why it fails.** The letter comes back marked undeliverable, and so does the next one. The form
had two lines. The screen behind the counter has one field, and whoever built it wired the first row
of boxes to that field. The second row was never wired to anything. Nothing was rejected: the form
was accepted, the clerk was competent, your handwriting was clear. The second line was read by a
person, looked at, and set aside, because nothing in the system knew what a second line *was*.

💡 **The insight.** The information was not lost because it was wrong or missing or malformed. It
was lost because the format split it into two pieces, and only one of the pieces had a label the
reader recognised. The other piece sat there, perfectly readable, addressed to nobody.

That is exactly what happens to a newline in a Server-Sent Events payload, and this part measures
it. Keep the second row of boxes in mind: everything below is that row.

## The idea in plain language

Part [3.1](3.1-what-sse-actually-is.md) established the two framing rules of Server-Sent Events
— the text format a server writes down one held-open HTTP response — and they are worth restating
as a pair because the bug lives in the gap between them:

1. A **blank line ends a message.**
2. A line whose field name is not one the format knows is **ignored**.

Rule 2 is not an accident and it is not sloppiness. It is how the format stays extensible: a server
can write a field a client has never heard of, and old clients carry on working instead of falling
over. Ignoring the unknown is a feature.

Now put a payload with a newline in it through an encoder that assumes payloads have no newlines.
The chunk `renders it before the fonts\nhave loaded.` is written into a template that puts `data: `
at the front and a blank line at the end. What lands on the wire is:

```text
data: renders it before the fonts
have loaded.

```

**Line by line:**

- Line 1 is a perfectly good `data:` field. It says `renders it before the fonts`. Nothing wrong
  with it.
- Line 2 is `have loaded.` — the tail of the payload, sitting on its own line, with no `data:`
  prefix in front of it. It is not truncated, not garbled, not out of order. It is just unlabelled.
- Line 3 is blank, so by rule 1 the message ends here, and the receiver hands up whatever `data:`
  lines it collected — which is line 1 and only line 1.
- By rule 2, line 2 has a field name of `have loaded.` with no colon at all, which is not `data`,
  `event`, `id` or `retry`. So the receiver ignores it. Correctly. By design.

That is the whole failure. The second half of the payload is the second row of boxes on the form:
present, legible, and wired to nothing.

## Why Sutra needs it

Because the payloads Sutra streams are exactly the payloads that contain newlines.

Look at what the day's agent actually says. It answers support questions, and a support answer that
is worth reading has a numbered list of steps in it, or a bullet list of things to check, or a code
block, or two paragraphs. Every one of those is a newline in the middle of a string. A newline is
not an exotic input here; it is the shape of a good answer.

The day's build brief asks for `frame(chunk)` in `sutra/stream.py` and says the gate calls it with
`"a\nb"` and expects two `data:` lines. This part is why that one test is in the brief instead of
being left to taste. Without it, `frame` will be written as one f-string — because that is what
everybody writes — and it will pass every test whose fixture is a short answer with no line break in
it, which is every test anybody writes by hand.

## The mechanism

Here is the naive encoder, from `lab/wire.py`, exactly as it sits on disk:

```python
def frame_naive(chunk: str) -> str:
    """One `data:` line per chunk. Correct until a chunk contains a newline."""
    return f"data: {chunk}\n\n"
```

**Line by line:**

- It is one line of code, and it is the shape everybody writes. That is the point of quoting it. It
  is not a strawman, not a deliberately clumsy version put up to be knocked down — it is the first
  thing that comes out of your fingers when you know the format is `data:` followed by a blank line.
- `\n\n` is **correct**. The first newline ends the `data:` field's line; the second is the blank
  line that ends the message. The bug is not in the terminator, and if you go looking for it there
  you will find nothing wrong and conclude the function is fine.
- The bug is the **assumption**: that `chunk` is a single line. Read the function and try to find
  where that is stated. It is not in the signature — the type is `str`, and `str` cheerfully holds
  newlines. It is not checked at runtime. It is not asserted. The only place it appears is in the
  docstring, and only because this lab wrote the docstring after measuring the failure.
- `f"data: {chunk}"` is an f-string dropping arbitrary text straight into the middle of a
  **line-oriented format** — a format where the position of the line breaks is what carries the
  meaning. That is the general shape of an entire family of bugs: content interpolated into a format
  whose framing is textual, where the content is allowed to contain the framing characters. SQL
  injection is a string dropped into a language where `'` and `;` are framing. Log injection is a
  string dropped into a file where `\n` starts a new record. This is the same bug in a smaller
  format, and the only reason it does not have a scary name is that nobody has worked out how to
  make money from it. Day 66 built the injection threat model for the case where the content is
  hostile; this is the case where the content is merely *ordinary*, and the outcome is the same
  because the format cannot tell the difference.

The corrected encoder is in part [3.1](3.1-what-sse-actually-is.md): it splits the chunk on `\n`
first and writes one `data:` line per line, so the same payload produces two consecutive `data:`
lines and the receiver rejoins them with a newline. Both live in the same file, so the same run can
be done twice with one flag changed and nothing else.

Run the ablation:

```bash
cd days/day-74-live-api-streaming/lab
uv run python wire.py --naive; echo "exit: $?"
```

**Line by line:**

- `--naive` swaps `frame` for `frame_naive` and changes nothing else. Same chunks, same parser, same
  arithmetic at the end. A demo you cannot switch off has proved that code ran, not that this idea
  mattered.
- `echo "exit: $?"` prints the exit status of the command just run. `wire.py` returns `1` when the
  round-trip is not exact, so the verdict is in the exit code and can be read by a script rather
  than by a person squinting at output.

Measured on 2026-09-06:

```text
framing: naive (one data: line per chunk)
4 chunks sent

  the bytes on the wire:
    'data: The invoice '
    ''
    'data: PDF is blank '
    ''
    'data: because the billing page '
    ''
    'data: renders it before the fonts'
    'have loaded.'
    ''
    ''

  what the receiver read back:
    'The invoice '
    'PDF is blank '
    'because the billing page '
    'renders it before the fonts'

  messages sent       4
  messages parsed     4
  characters sent     90
  characters received 77
  round-trip exact    NO

  13 characters never arrived. Nothing errored and no message was malformed:
  the second line of the split payload had no `data:` prefix, so it was an unknown
  field, and an unknown field is ignored by design.
exit: 1
```

**Find the one line that matters.** In *the bytes on the wire*, seventh entry down, is
`'have loaded.'`. No `data:` in front of it. It is on the wire. It was transmitted. It arrived at
the receiver. You can read it with your own eyes, right there in the output, and the receiver threw
it away — not because it was broken, but because by rule 2 it was an unknown field and unknown
fields are ignored by design. Contrast it with the correct run from part 3.1, where the same payload
produced two consecutive `data:` lines and the parser rejoined them into one message ending
`...before the fonts\nhave loaded.`

**Now look at the counts, because this is what makes it reach production.**

```text
  messages sent       4
  messages parsed     4
```

They are **equal**. Four went in, four came out. Nothing is missing at the level anybody would
think to check — no message vanished, no message was duplicated, no message arrived out of order,
the stream did not end early and the connection did not drop. Every property you would naturally
monitor is green.

It is the *content* of one message that is short. That is why a test which counts messages passes
and a test which compares text fails, and why the build brief asks for the second kind.

Side by side, the two runs of the same four chunks:

| | correct framing | naive framing |
| --- | --- | --- |
| characters sent | 90 | 90 |
| characters received | 90 | 77 |
| round-trip exact | yes | NO |
| messages sent / parsed | 4 / 4 | 4 / 4 |
| exit code | `0` | `1` |
| errors, warnings, malformed messages | none | none |

The last two rows are the whole part. The exit code differs because `wire.py` was written to compare
the text it sent against the text that came back. Nothing else in the run differs, and nothing in
the format, the parser or the runtime would have told you.

## When it breaks

**It breaks on the answers you actually ship.** A payload contains a newline whenever the answer
has a markdown list, a numbered set of steps, a fenced code block, or more than one paragraph. That
is not an edge case — that is the normal, good output of a support agent. The reason this survives
code review is the mirror image: the answers in the *tests* are short. `"hello"`, `"the invoice is
blank"`, `"OK"`. None of them contain a line break, so the naive encoder round-trips every fixture
perfectly, and the reviewer reads a passing suite.

**The damage is proportional to what comes after the first newline.** A two-line answer loses its
second line. A three-paragraph answer loses two paragraphs. A code block — where the payload is a
line of prose, a newline, and then ten lines of shell — loses everything except the sentence
introducing it, which is the worst possible outcome because the reader is left holding a promise
with nothing behind it. The bug is not a fixed cost; it scales with how useful the answer was.

**Carriage returns are a second way to break the same framing, and this lab does not handle them.**
`wire.py` splits only on `\n`. The real Server-Sent Events format treats a carriage return (`\r`), a
line feed (`\n`), and the pair (`\r\n`) as line terminators, all three. So a payload containing a
lone `\r` — which is what you get from a Windows-authored file read carelessly, or from a terminal
capture pasted into a document — passes straight through the *corrected* encoder as a single
`data:` line with a `\r` sitting inside it, and a conforming browser client will split that line in
two on arrival and drop the tail exactly as described above. This is a **known omission** in the
lab, stated rather than papered over. The general rule is that the encoder must split on every
terminator the receiver recognises, and `\n` is not the whole list.

**And the corrected encoder is not a general defence.** It fixes newlines. It fixes nothing else
about a payload you did not write. It does not stop a payload from being enormous — a single chunk
holding a megabyte of text will be framed impeccably as one very long `data:` line, and every hop
between you and the reader will have an opinion about that. It does not bound how many messages you
write, or how fast. Those are separate problems with separate defences, and part
[5.2](../05-in-production/5.2-what-a-real-streaming-system-adds.md) is where they live. Correct
framing is table stakes, not safety.

## In production

**What a professional does: stop shipping bare text.** Encode the payload as JSON before it goes on
the wire — one JSON object per message, so `data: ` is followed by a single opaque token with no
line breaks in it, because the JSON encoder escapes a newline to the two characters `\` and `n`.
The framing problem disappears into the encoder, where somebody has already thought about it
harder than you will, and it disappears for every payload rather than for the payloads you
remembered to test.

That is not free, and pretending otherwise is how people end up distrusting the advice:

- **Bytes.** JSON adds braces, quotes, a field name and escape sequences to every message. On a
  stream of small chunks that overhead is a real fraction of the traffic.
- **A client that must now parse.** The receiver can no longer render `data:` straight to the
  screen; it must `JSON.parse` each message and handle the case where parsing fails. You have moved
  work from the encoder to every consumer.
- **A schema you now own.** The moment the payload is an object, its field names are an interface,
  and changing them breaks clients you cannot deploy.

The trade is almost always worth taking, and it should be taken deliberately rather than by default.

**"Just use a library" is the right answer here** — a maintained Server-Sent Events implementation
already splits on all three terminators, handles the `id:` and `retry:` fields, and has been hit by
payloads you have not imagined. Write the framing by hand once anyway. That is Principle 4, and this
part is the argument for it: you have now watched `'have loaded.'` sit on the wire and get dropped,
which means that when a library's behaviour surprises you at some unreasonable hour, you have a
model of what it is doing rather than a belief that it works.

**What degrades at scale.** Not throughput — correct framing costs a `split` per chunk and nothing
noticeable. What degrades is *confidence*. One service framing its own SSE is fine. Four services,
each with its own hand-rolled encoder written by somebody who read the same three lines of the spec,
is four chances at this bug and four different symptoms. The defence is the same as everywhere else
in this day: one function, in one module, imported.

**The review comment a senior engineer leaves:** *"This f-strings the chunk straight into a `data:`
line, and our answers contain markdown lists — so the first newline in a payload ends the `data:`
field and everything after it goes out as an unlabelled line, which the spec says receivers must
ignore. It won't error and the message count will still be right; you'll just lose the tail. Two
things please: split the payload on line terminators and emit one `data:` line per line, and add a
test that round-trips a string with a `\n` in it, because every fixture we have is one line long.
Longer term I'd rather we sent JSON per message so the transport carries an opaque token and this
class of bug can't come back — but fix the encoder first."*

**The interview question:** *"Your streamed answers are arriving cut off, always at the same point,
and there's nothing in the logs. Where do you look?"* An honest answer: *"At the first newline in
the payload. Server-Sent Events is line-oriented: a blank line ends a message, and a line whose
field name isn't recognised is ignored — that second rule is deliberate, it's how the format stays
extensible. So if you frame a chunk as one `data:` line with an f-string, a payload containing its
own newline splits in two, the second line has no `data:` prefix, and the receiver drops it. It's
not malformed, it's just not addressed to anyone. I measured it in a lab: 90 characters sent, 77
received, thirteen gone, no exception. And the part that makes it dangerous is that the message
count is unchanged — four sent, four parsed — so anything monitoring for lost or duplicated messages
stays green, and only a test that compares the text catches it. The fix is one `data:` line per line
of the payload, and the real fix is to send JSON so the transport carries one opaque token per
message. It survives review because test answers are short and short answers have no line breaks in
them, which means the fixtures don't look like production."*
