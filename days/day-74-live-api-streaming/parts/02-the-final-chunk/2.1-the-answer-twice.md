# 2.1 — The answer, twice

## One-line answer

The last event of a stream is not the last piece of the answer — it is **the whole answer again** —
so the obvious rule of concatenating every text you were handed produces **180 characters where the
answer is 90**, with nothing raised, nothing corrupted and nothing out of order.

## The story

You are sitting in a talk, taking notes, and the speaker is good: one point at a time, each one
clear, and you write each one down as it arrives.

At the end she says *"so, to recap"* — and goes through all six points again, in order, in the same
words. You are still writing. Your pen has not stopped since the beginning and your rule has not
changed: write down what she says.

Later you read your notes back and there are twelve points. Not six wrong ones, and nothing missing.
Six correct points, followed by the same six correct points, and no line anywhere in your notebook
saying which half was the recap.

Nobody made a mistake. The speaker did exactly what a good speaker does. You did exactly what a
diligent note-taker does. The rule was simply written for a talk that has no recap in it.

## The idea in plain language

Part [1.3](../01-the-blank-screen/1.3-one-event-or-six.md) measured a turn arriving as six events
instead of one, with five flagged `partial=True` and one flagged `partial=False`. What it deliberately
did not say is what that last event contains.

It contains the recap.

ADK states this in the contract of the method every model implements. Quoted from
`BaseLlm.generate_content_async` in `google-adk==2.7.1` as installed on 2026-09-06 — the indentation
is the package's own two-space style, which is why this is a text block rather than a Python one:

```text
      **Streaming mode (stream=True):**

        Yields multiple LlmResponse objects as chunks arrive:

        - Intermediate chunks: `partial=True` (progressive updates)
        - Final chunk: `partial=False` (aggregated content from entire turn,
          identical to stream=False output)
        - Text consolidation: Consecutive text parts of the same type
          (thought/non-thought) SHOULD merge without separator, but client
          code must not rely on this - unconsolidated parts are unusual but also
          valid
```

Read the second bullet twice. *"Aggregated content from entire turn, identical to `stream=False`
output."* The final chunk is not a chunk. It is the non-streaming answer, delivered at the end of the
streaming one, so that a caller who does not care about progress can ignore everything before it.

That is a sensible design and it is the whole trap. It means the event stream contains the answer
**twice** — once in pieces and once whole — and which of those two you are supposed to use is a
decision the framework has deliberately left to you.

The rule almost everyone writes first does not make that decision:

```python
"".join(event_text for event in events)
```

**Line by line:**

- `for event in events` walks every event the stream produced, in order, with no test applied to any
  of them. That absence is the bug: the events are not all the same kind of thing, and this rule has
  no way to say so.
- `"".join(...)` with no separator is the right join for chunks of one sentence — a space between them
  would land in the middle of a word — so the joining is not what is wrong here.
- What is wrong is that the sequence being joined ends with the final event, and the final event is
  the whole answer. The rule is correct for a stream of pieces and this is not one.

It is not a careless rule. It is what you write when you think of a stream as *the answer, arriving*.
It is what a debug print does. It is what the first draft of a renderer does. And it is wrong in a way
that raises nothing.

## Why Sutra needs it

Because the build brief asks for `collect(events)` in `sutra/stream.py`, and the gate spends a whole
check reading its source for the word `partial`. That is a crude test for a real property, and the
hub says so — but a `collect` that never mentions `partial` cannot be doing anything except
concatenating everything, and that is the one implementation that is definitely wrong.

It also matters because of where the doubled text ends up. On screen a person would notice; the answer
would visibly appear and then appear again. The dangerous paths are the ones with no reader: text
stored into a session as the turn's content, text handed to an eval as the model's answer, text
counted for a token budget. In every one of those the doubled string is simply accepted, and the next
thing to read it is another model.

## The mechanism

Three rules, applied to one identical stream. This is the first, and it is the bug:

```python
def naive(rows: list[Row]) -> str:
    """Concatenate every text you were given. This is the bug."""
    return "".join(text for _index, _partial, text in rows)
```

**Line by line:**

- `rows` is exactly what part 1.3's loop collected: `(index, partial, text)` for every event that
  carried text. Nothing has been filtered out, because the whole question is what to filter.
- `_index, _partial, text` — the underscores are the bug made visible. The rule unpacks the `partial`
  flag and then does not look at it, which is the difference between this function and a correct one.
- `"".join(...)` with no separator is right for the partials, because the chunks are pieces of one
  sentence and a space between them would put a space in the middle of a word. It is the joining of
  the *final* event onto the end that does the damage, not the separator.

Run all three rules against the same stream:

```bash
cd days/day-74-live-api-streaming/lab
uv run python partials.py
```

**Line by line:**

- `partials.py` drives one real turn through the runner in `StreamingMode.SSE` and then applies each
  rule to the identical list of events, so the only difference between the three answers is the rule.

Measured on 2026-09-06:

```text
6 events carrying text, from one turn

  rule                      chars  correct?
  naive: join everything      180  NO
  partials only                90  yes
  final only                   90  yes

  the answer is 90 characters

  what the naive rule produced:
    'The invoice PDF is blank because the billing page renders it before the fonts have loaded.The invoice PDF is blank because the billing page renders it before the fonts have loaded.'

  Nothing raised. The text is not corrupted, not truncated and not out of order.
  It is the answer, followed by the answer.
```

**180 against 90**, and look at what the doubled string actually is. There is no separator, no
overlap, no garbled join — the answer ends with `have loaded.` and the next character is `T`. It reads
like a system that repeated itself, because that is precisely what it did.

Now the part that decides whether this reaches production: nothing about the failure is loud.

| What you might expect | What actually happened |
| --- | --- |
| an exception | none |
| a warning in the log | none |
| corrupted or reordered text | none; both halves are perfect |
| a wrong length that some check would catch | only if something knows the expected length, and nothing does |

The one signal available is the length, and the length is only suspicious if you already know what the
answer should have been — which you do not, because that is what you asked the model for.

The rule that turns this into a caught bug is the one the day's build brief asks for, and it is one
test: run a stream that ends in a non-partial event through `collect`, and assert the answer appears
**once**. That test is three lines and it is the difference between this part being a war story and
this part being a paragraph in a docstring.

## When it breaks

**It hides in the tests before it hides in production.** A hand-written fake model that yields three
partial chunks and stops will make the naive rule pass, because there is no final event to double
anything. Part [1.3](../01-the-blank-screen/1.3-one-event-or-six.md)'s `_fake.py` deliberately does
not take that shortcut — it emits the aggregated final exactly as the contract describes — and that is
the only reason this day could measure the bug at all. A fake that is easier to write than the real
contract will hide precisely the failures the contract exists to warn you about.

**The correct rules have a caveat of their own**, and it is in the third bullet of the quoted
docstring: consecutive text parts *"SHOULD merge without separator, but client code must not rely on
this — unconsolidated parts are unusual but also valid"*. So a single event can itself carry more than
one text part, and a rule that reads only `parts[0]` will drop text on the unusual-but-valid path.
Part 1.3's loop iterates every part for that reason.

**And it gets worse where an answer is long.** The failure is proportional: a 90-character answer
becomes 180, and a 4,000-token answer becomes 8,000 tokens — which is a real cost against a real
budget, silently, on a path where Day 70's router is counting requests and nothing is counting
characters. The bug does not scale into an error; it scales into a bill.

## In production

**Where the doubled text actually causes damage.** Not on the screen. On screen a reader sees the
answer appear and then appear again, and somebody files a bug within a day. The paths that stay broken
are the quiet ones: the collected string written into the session as the assistant's turn, so every
later turn is prompted with a doubled message; the string handed to an evaluator, which now scores a
model that repeats itself; the string counted for a token budget, which now over-reports by a factor
of two. A person is in the loop on exactly one of those.

**What a professional does about the whole class.** Collects in one place. The reason `sutra/stream.py`
exists as a module rather than as a snippet in a handler is that the rule for turning events back into
an answer is exactly the kind of thing that gets re-derived — slightly differently — in every place
that consumes a stream, and the second implementation is where the bug lives. One function, one
docstring saying which rule it uses and why, one test.

**What degrades at scale.** More consumers, not more traffic. A single web handler is easy to get
right. It is the third consumer — a logger, an evaluator, a webhook forwarder — written months later
by somebody reading the event stream directly, that reinvents the naive rule. The defence is not
vigilance; it is that the correct rule is somewhere obvious enough to import.

**The review comment a senior engineer leaves:** *"This joins every event's text, and the last event
is the whole turn again — check the `generate_content_async` docstring, it says 'identical to
stream=False output'. So we're storing the answer twice in the session, which means every follow-up
turn gets a doubled message in its history and our token accounting is out by 2x on streamed turns.
Please move the rule into one function, say in its docstring whether it accumulates partials or takes
the final, and add the test that asserts the answer appears once. And make the fake model in the tests
emit the aggregated final — the current one stops after the chunks, which is why this passed."*

**The interview question:** *"You switched a handler to streaming and the answers started coming out
doubled. What happened?"* An honest answer: *"The final event of a streamed turn isn't the last chunk
— it's the entire turn's content again, so a caller who doesn't want progress can ignore everything
before it. ADK's own model contract says it's identical to the non-streaming output. So joining every
event's text gives you the answer followed by the answer. I measured it: 180 characters where the
answer was 90, no exception, nothing corrupted, both halves perfect. The fix is one flag —
`event.partial` — and the decision of which correct rule you want: accumulate the partials, or take
the final. What makes it dangerous is where it goes when nobody's watching. On screen you'd spot it
immediately; written into a session, or handed to an eval, or counted against a token budget, it's
just accepted. And it hides in tests too, because a fake model that yields chunks and stops has no
final event to double."*
