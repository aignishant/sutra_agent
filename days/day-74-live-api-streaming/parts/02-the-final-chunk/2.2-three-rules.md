# 2.2 — Three rules, two of them right

## One-line answer

Two of the three rules return the answer, and they are **not two ways of doing one job** — accumulate
the partials is the rule for **the screen**, because it is the only one that has anything to show
before the turn ends, and take the final is the rule for **storage**, because it is the one string
the model asserts is its complete answer.

## The story

Saturday football at the local ground. Two people are recording the same match.

One is a parent standing by the touchline, typing into the parents' group chat as it happens.
*"They've kicked off."* *"Goal — the tall lad in the red boots."* *"Their keeper has just saved a
penalty."* Anyone reading at home knows where the match is, all the way through.

The other is the club secretary, who writes nothing at all while the match is on. At the end he
fills in the result sheet: final score, scorers, cards, signed. That sheet goes to the league. It is
the record.

Both people are accurate. Neither is doing the other's job. And you can tell which is which the day
the referee calls it off part-way through the first half because the pitch is flooded. The group
chat still has everything that happened, in order. The result sheet is blank — the secretary never
got to fill it in, and correctly so, because there is no result.

Now imagine the club decides to save effort and use one method for both. If the group chat is fed
from the result sheet, the parents at home get nothing until the final whistle. If the league is
sent the group chat, the league gets a stitched-together best guess of a score instead of the thing
the secretary signed.

That is exactly the choice in front of `collect(events)`, and it is the same choice in the same
shape.

## The idea in plain language

Part [2.1](2.1-the-answer-twice.md) established the trap: the last event of a streamed turn is the
whole answer again, so joining every text you were handed gives **180 characters where the answer is
90**. That part ended by naming the fix as one flag and one decision. This part is the decision.

Both surviving rules read the same flag. `partial` is a boolean on the event — `True` means "a piece
of an answer still being written", `False` means "the finished thing". One rule keeps the pieces and
throws the finished thing away. The other throws the pieces away and keeps the finished thing. On a
turn that runs to completion they hand back identical strings, which is why they look
interchangeable.

They are not, and one question separates them: **what does the rule have in its hands before the
turn is over?**

Accumulating the partials has the answer-so-far, at every moment, from the first chunk onwards. That
is the entire reason to stream. Taking the final has nothing — an empty string — right up until the
last event arrives, and then it has everything at once.

So a system that streams needs both, for two different consumers, and the mistake is not choosing
wrong. The mistake is thinking there is one thing to choose.

## Why Sutra needs it

The hub's build brief asks for `collect(events)` in `sutra/stream.py`, and its second `TODO(me)`
says: decide **which** correct rule you want, and write the reason in the docstring. That is not a
style request. A docstring saying "returns the answer" is true of both rules and useless, because
the caller who reads it cannot tell whether the function will give them something to render while
the model is still writing.

There is also a third `TODO(me)` in the brief, in the test file: a test for a stream that stops after
two partials, where you must decide what `collect` returns and assert it. That test cannot be written
until this decision is made, because the two rules give different, equally defensible answers to it —
the two chunks, or the empty string. "Whatever happens" is not a decision, and an unwritten decision
becomes whichever rule the first author happened to type.

## The mechanism

The two correct rules, from `lab/partials.py`:

```python
def partials_only(rows: list[Row]) -> str:
    """Concatenate the partials and ignore the final. Correct, and it throws the final away."""
    return "".join(text for _index, partial, text in rows if partial)


def final_only(rows: list[Row]) -> str:
    """Take the last non-partial event. Correct, and it is not streaming any more."""
    finals = [text for _index, partial, text in rows if not partial]
    return finals[-1] if finals else ""
```

**Line by line:**

- `if partial` and `if not partial` are the same flag read two ways. That is the whole mechanism.
  There is no clever parsing, no length check, no de-duplication — one boolean, and the two correct
  rules are its two sides. The naive rule in part [2.1](2.1-the-answer-twice.md) is the version that
  does not read the flag at all, which is why its parameter was named `_partial` with a leading
  underscore.
- `"".join(...)` with no separator in `partials_only` is right because the chunks are pieces of one
  sentence; a space between them would land in the middle of a word.
- `finals = [...]` builds a list rather than taking the first match, and `finals[-1]` takes the
  **last** non-partial event, not the first. A single turn can contain more than one non-partial
  event — a function call the model made, then the answer it wrote after seeing the result — and
  what you want is the last thing the model said, not the first. Be honest that this is a
  simplification: for a turn carrying several distinct model messages you would key them by author
  and invocation rather than reaching for the end of a list.
- `return finals[-1] if finals else ""` — that `else ""` branch is not defensive padding for a case
  that cannot happen. It is exactly the case that separates the two rules. A turn whose reader closed
  the tab has partial events and **no final event at all**, so `finals` is empty and this rule
  returns nothing while the other returns everything that was said. Part
  [5.1](../05-in-production/5.1-the-reader-who-leaves.md) measures that turn.
- `partials_only` returns the whole answer here **because the partials happen to tile the answer
  exactly** — five chunks, no gaps, no overlap. That is what the contract promises for text, and part
  [2.3](2.3-not-always-text.md) is about the parts of a stream where you do not get that for free.

**Line by line:**

- `partials.py` drives one real turn through the runner in `StreamingMode.SSE` and applies all three

Measured on 2026-09-06:

```text
6 events carrying text, from one turn

  rule                      chars  correct?
  naive: join everything      180  NO
  partials only                90  yes
  final only                   90  yes

  the answer is 90 characters
```

Two `yes` rows, same length, same string. Nothing in this run tells you which one to ship, and that
is the point: a turn that finishes cannot distinguish them. The questions that can:

| question | accumulate the partials | take the final |
| --- | --- | --- |
| what it has mid-turn | the answer so far | nothing |
| what it returns if the turn is cancelled | what was said before the reader left | an empty string |
| does it depend on the chunks tiling exactly | yes | no |
| what it is the right rule for | the screen | storage, evals, token accounting |

Read the last row as the summary of the three above it. The screen needs something before the end,
and only one rule has anything. Storage needs the string the model asserts is its finished answer,
and only one rule has that.

## When it breaks

**`partials_only` trusts the chunks to concatenate into exactly the answer, and the contract
explicitly declines to guarantee that.** The docstring quoted in part [2.1](2.1-the-answer-twice.md)
says consecutive text parts *"SHOULD merge without separator, but client code must not rely on
this"*. `SHOULD` in a specification means "do this unless you have a good reason not to" — it is not
`MUST`. So the screen rule is the one carrying an assumption. It is a documented assumption, on a
path where a small error is visible to a human and gets reported, which is why it is an acceptable
one to carry — but it is carried, and the other rule does not carry it.

**`final_only` is correct and gives you nothing until the end.** A system that uses it to feed the
screen has streaming that does not stream: the config field is on, six events arrive, the model
yields chunks, and the reader watches a blank space and then the whole answer at once. Nothing
errors. The worst part is that it passes every test you have, because tests run turns to completion
and a completed turn always has a final event. The failure only exists for a reader watching in real
time, and no test is a reader watching in real time.

**Using one rule for both jobs breaks in whichever direction you picked.** Render from the final and
you get the blank screen above. Persist from the partials and you have stored a best-effort
reconstruction — assembled by your code, under an assumption the contract hedges — in the place where
the next turn's history, the evaluator's ground truth and the token count all read from. You have
replaced the string the model asserted was its answer with your own stitching of the pieces, and
nothing anywhere records that you did.

## In production

**What a professional does: both, in one place, named for their jobs.** Not one function with a
boolean flag, and not two functions in two files that drifted. Either two clearly named functions
side by side —

- `for_display(events)` — accumulates partials, returns whatever exists now, safe to call mid-turn;
- `for_storage(events)` — returns the final event's text, or the empty string if the turn never
  finished;

— or a single `collect` whose docstring names the rule it uses **and** says what the other rule
would have returned and why you did not want it. The build brief asks for one function, so the
docstring is where the second half of the decision lives. Either shape is fine. What is not fine is
a function called `collect` whose name is silent on the question this part is about.

**What changes at scale.** Not the traffic — the number of consumers. One handler that renders and
then saves is easy to keep honest. Add a websocket fan-out, a transcript logger, an evaluation
harness and a webhook forwarder, and you have five consumers, of which two want the screen rule and
three want the storage rule, all reading the same event stream. If the choice lives in each consumer,
the fifth one written gets it wrong, and it will be a storage-shaped consumer using the display rule,
because the display rule is the one people write from memory. If both rules live in one module with
names that say what they are for, the fifth consumer picks by reading two function names.

The second thing that changes with scale is that the empty string stops being rare. Cancelled turns
are a rounding error on a demo and a steady fraction of real traffic, because readers close tabs.
So `for_storage` returning `""` is a normal Tuesday, not an anomaly, and every caller of it needs an
answer to "what do I write when there is no answer" — which is part
[5.1](../05-in-production/5.1-the-reader-who-leaves.md)'s whole subject.

**The review comment a senior engineer leaves:** *"This is the partials rule and it's correct, but
it's being used to write the session's assistant turn. That's the display rule doing the storage
job. What gets persisted is our reconstruction of the answer rather than the aggregated final the
model actually asserted, and the model contract says we must not rely on the chunks merging cleanly.
Please split it: one function for the screen that accumulates partials, one for persistence that
takes the last non-partial event, both in `sutra/stream.py`, both named for their job. And decide
what the storage one returns when the turn was cancelled and there is no final event, because right
now it returns a partial answer that will look to every later turn like a complete one."*

**The interview question:** *"There are two correct ways to reassemble a streamed answer. When does
it matter which one you use?"* An honest answer: *"When the turn doesn't finish. If you accumulate
the partials you have the answer-so-far at every moment, which is the only reason to stream at all —
that's the rule for the screen. If you take the last non-partial event you have nothing until the
end, and then you have the exact string the model says is its complete answer — that's the rule for
storage, evals and token counting. On a turn that runs to completion they return the identical
string, so tests can't tell them apart; tests always run turns to completion. The difference shows up
when a reader closes the tab: the partials rule gives you what was said, the final rule gives you an
empty string, and both of those are the right answer to different questions. There's a smaller
asymmetry too — the partials rule assumes the chunks concatenate into exactly the answer, and the
contract says text parts SHOULD merge without a separator but you must not rely on it. So I'd ship
both, in one module, named for their jobs, rather than pick one and use it everywhere."*
