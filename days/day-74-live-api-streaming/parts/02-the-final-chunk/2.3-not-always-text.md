# 2.3 — A partial is not always text

## One-line answer

"Streaming" does not mean "text arriving in pieces": **every** intermediate chunk is flagged
`partial=True` no matter what it carries — text, a function call, raw bytes, or the model's own
reasoning — so a consumer written as *"append `part.text` to the screen"* is not a streaming
consumer at all. It is a **text**-streaming consumer, and everything that is not text vanishes from
it without a sound.

**Say the limitation before the lesson.** This part measured nothing. The scripted model in this
day's lab emits text and only text, so there is no run on this page and no output pasted anywhere in
it. What follows is a reading of the framework's written contract plus the one line of lab code that
the contract catches out. That is weaker evidence than the rest of Day 74 offers, it is the honest
state of this page, and the exercise at the bottom is for you to go and check it against a real
model when you have one and record what actually arrives (Principle 10).

## The story

There is a mat behind your front door, and things land on it. You have a rule, and you follow it
without thinking about it: pick up the envelopes, carry them to the kitchen table, open them in
order. Everything else that came through the same slot — the folded takeaway menu, the free local
paper, the flyer for a gutter cleaner — is scooped up on the way past and dropped in the recycling.

The rule works. Bills get paid. Nothing is ever late. You would describe yourself, fairly, as someone
who deals with the post.

Then the recycling goes out, and over the next few days three things turn out to have gone with it.
A small padded packet had been lying flat under the free paper — the spare fob for the boiler you had
been waiting on. A loose handwritten sheet, no envelope, had asked everyone in the terrace to move
their cars on Thursday because the road was being resurfaced; your car is now behind a barrier. And
on the back of that same sheet, in different handwriting, someone had drafted the notice before
writing it out properly: two crossed-out dates and the line *"don't say we're behind schedule"* — a
page nobody meant to push through anybody's door.

Nothing went wrong. No delivery failed, no one made a mistake, no alarm was raised. The rule did
exactly what it said. It said *envelopes*, and it had never been asked what to do about anything
else that comes through the same slot.

## The idea in plain language

An event's content is not a string. It is a list of **parts**, and a part is a **container** — a slot
that holds one piece of a message. What is in the slot varies. Part
[2.1](2.1-the-answer-twice.md) already relied on this quietly when it noted that a single event can
carry more than one text part; the bigger point is that a part does not have to carry text at all.

Four kinds of thing turn up in that slot, and ADK says so in the contract of the method every model
implements. Quoted verbatim from `BaseLlm.generate_content_async` in `google-adk==2.7.1` as installed
on 2026-09-06 — the two-space indentation is the package's own docstring style, which is why this is
a text block and not a Python one:

```text
      **Common content in partial chunks:**

        All intermediate chunks have `partial=True` regardless of content type.
        Common examples include:

        - Text: Streams incrementally as tokens arrive
        - Function calls: May arrive in separate chunks
        - Bytes (e.g., images): Typically arrive as single chunk, interleaved
          with text
        - Thoughts: Stream incrementally when thinking_config is enabled
```

Read the first line of it slowly: *"regardless of content type."* The `partial` flag is not a
statement about text. It is a statement about **position** — this chunk is in the middle of the turn
— and part [2.2](2.2-three-rules.md) built two correct rules on exactly that meaning. Those rules
stay correct here. What changes is that they were written over a stream of strings, and the stream
is not made of strings.

Three of the four kinds need naming before we go further, because none of them is obvious:

- A **function call** is the model asking for a tool to be run: a name and a set of arguments, as
  structured data rather than as prose. Day 4 built tool calling by hand, before any framework, so
  that this would be a familiar shape rather than a magic one.
- **Inline bytes** are raw binary carried inside the part itself — an image, a rendered chart, an
  audio clip — together with a label saying what kind of file the bytes are. Not a link to a file.
  The file.
- A **thought** is the model's own reasoning written out as it works, which some models will emit
  when thinking is switched on in the request. It is not the answer. It is the working.

Now the table that matters, and it is the whole part:

| Content type | What is in the slot | How it tends to arrive | What a `part.text`-only consumer does |
| --- | --- | --- | --- |
| Text | a string | incrementally, as tokens arrive | renders it — the one case that works |
| Function call | a tool name and arguments | possibly split across several chunks | drops it; the tool is never called |
| Inline bytes | binary plus its file type | usually one chunk, between text chunks | drops it; the answer reads as if a piece is missing |
| Thought | the model's reasoning | incrementally, only when thinking is on | drops it — the one case where dropping is a mercy |

Three of those four rows are the recycling bin.

## Why Sutra needs it

Because the build brief asks for `collect(events)` in `sutra/stream.py`, and `collect` returns a
string. That is a reasonable thing for today's module to do — Day 74's agent answers questions with
prose — but it is a decision, and the day should say it is a decision rather than let it look like
the shape of the world.

It matters more the moment Sutra's streamed agent has tools, which it already does. An agent that can
call a tool emits function calls, and a handler that reads only text will show the reader a paused
screen while the interesting half of the turn goes past it unread. The screen will not be blank and
it will not be wrong. It will be *incomplete*, which is the failure mode with no error message
attached to it.

## The mechanism

Here is the line, from `drive()` in this day's `lab/_fake.py`. It is dedented to column 0 from inside
the loop; nothing else about it is changed:

```python
for part in event.content.parts if event.content and event.content.parts else []:
    if part.text:
        seen.append((index, bool(event.partial), part.text))
```

**Line by line:**

- `event.content.parts` — the loop is over **parts**, plural, not over the event. One event holds a
  list, and each entry is one of the containers described above. Iterating them is not
  defensiveness; it is the actual shape of the data.
- `if event.content and event.content.parts else []` — the guard exists because `event.content` can
  be **absent entirely**. Not every event in a run is a message from the model. Some carry state
  changes, control signals or nothing at all, and reaching for `.parts` on those raises
  `AttributeError` on the first turn you run. The `else []` makes "this event has no parts" a
  perfectly ordinary case instead of a crash.
- `if part.text:` — **this is the line this part is about.** Here it is correct. `drive()` exists to
  collect text for parts 1.3, 2.1 and 2.2, the scripted model emits nothing else, and the filter says
  so honestly. Copy the same three lines into a renderer, though, and the filter is no longer a
  statement about this lab. It is a policy: *if the slot does not hold a string, this system has no
  opinion about it.* Every function call, every image and every reasoning trace hits that `if`,
  evaluates falsy, and is stepped over — the envelopes rule, in Python.
- `bool(event.partial)` — `partial` is read off the **event**, not off the part, which is the
  contract's own arrangement. The flag describes where the chunk sits in the turn; the part describes
  what the chunk contains. Two independent questions, and conflating them is how "partial" comes to
  be read as "a fragment of text".

Now take the four rows one at a time, because each one fails differently.

**Text — the case everyone builds for.** This is the case the whole day measured: five chunks and a
final aggregate, a string growing on a screen. It is also the case that makes the other three
invisible, because it works so completely that nothing ever suggests the loop is filtering anything.
A rule that has only ever been shown one kind of input has not been tested; it has been agreed with.

**Function calls arriving in chunks.** The contract's second bullet says they *"may arrive in separate
chunks"*, and the practical consequence is sharper than "remember to handle them". A function call
split across chunks is **not complete** in any single chunk: a name may have arrived and its arguments
may not, or the arguments may be a half-written structure. So a partial function call is not something
to execute. It is something to **wait for**. The rule is the same one part 2.2 argued for text, in a
harsher setting: you may render a partial, and you may not act on one. Day 16 put brakes on tool
calling — confirmation, limits, a way to refuse — and every one of those brakes assumes it is being
handed a whole call to judge. Firing a tool on a fragment does not just produce a wrong result; it
produces a wrong result that the brakes never saw properly.

**Bytes interleaved with text.** The contract says bytes *"typically arrive as single chunk,
interleaved with text"* — so the stream is text, then an image, then more text, in that order,
because the order is the answer. A consumer that concatenates strings has **nowhere to put an image**.
There is no slot in a string for a picture, so the failure is not a dropped call or a raised
exception; it is a paragraph that says *"the chart below shows the spike on the third day"* followed
immediately by the next paragraph. Nothing is broken. The answer simply reads as though something is
missing, because something is.

**Thoughts.** These arrive only when thinking is enabled in the request, so most systems will never
see one — right up until somebody turns thinking on to improve answer quality and ships it. And this
row has a different shape from the other three. The other three are rendering problems: content that
should have reached the reader did not. A thought is the reverse. It is the model's working, and it
can contain the rejected drafts, the uncertainty, and the intermediate quotations of whatever the
model was given — including material the reader is not entitled to. Day 69 drew Sutra's data
boundaries and made the argument that what a component may *see* and what it may *emit* are two
different permissions. A reasoning trace piped straight to a browser because it happened to be in a
part is exactly that boundary crossed by accident. The safe default is that thoughts are logged, not
displayed, and displaying them is a deliberate product decision with a reason written down next to
it.

## When it breaks

**This page is a reading of a contract, not a measurement, and that is a real weakness.** Every other
claim on Day 74 has a number behind it and a command that produces the number. This one has a
docstring. A docstring describes what the framework intends; it does not tell you what a specific
model on a specific day actually emits, in what order, or how often a function call really does get
split. The table above is therefore a set of cases to **check**, not a set of results. Treat it the
way you would treat any other undertested assumption in a system you are responsible for.

**The contract hedges, and the hedge is load-bearing.** The same docstring that part
[2.1](2.1-the-answer-twice.md) quoted says consecutive text parts *"SHOULD merge without separator,
but client code must not rely on this — unconsolidated parts are unusual but also valid"*. Read that
next to this part's subject and it says something stronger than it first appears: the number of parts
in an event is not fixed, their merging is not guaranteed, and "unusual but also valid" is precisely
the class of thing that never shows up in development and shows up in production. A consumer that
handles one part per event is relying on a SHOULD.

**And a fake model that only yields text will never surface any of it.** This lab's `_fake.py` emits
five text chunks and one text aggregate. It is a good fake — part 2.1 praised it for emitting the
aggregated final chunk instead of taking the easy route — and it is still blind here, because nothing
in it has ever produced a function call or a byte. That is the same trap part 2.1 named for the final
chunk, pointed at a different field: **a fake that is simpler than the contract hides exactly the
failures the contract exists to warn you about.** Extending the fake to emit one function-call part
and one bytes part is a short piece of work, and it is the only way this page's table becomes
something you have seen rather than something you have read.

## In production

**What a professional's event handler looks like.** Not a filter. A **branch per part type**, with a
default arm that **logs**:

- text → append to the growing answer;
- function call → buffer it until the turn's non-partial event confirms it is complete, then hand it
  to whatever does tool authorisation;
- inline bytes → store it, and put a reference to it in the right position in the rendered output, so
  the ordering the model chose survives;
- thought → route to the log, and to the reader only if a product decision says so;
- anything else → **log a warning naming the part's fields, and carry on.**

That last arm is the whole difference between a system that ages well and one that does not. A part
type nobody has written a branch for is going to happen: the field's content types are not a closed
set, and a model release can start emitting something new without any code of yours changing. Silence
turns that into an unknown unknown, discovered by a user. A warning turns it into a known unknown,
discovered in a log search, before anybody files a ticket.

**What changes at scale.** Not the volume of traffic — the number of *paths* through the handler.
With one model and one prompt style you can convince yourself the stream is text, and be right for a
long while. Add a second model, or enable thinking on one route, or give one agent a tool, and the
same handler is now serving streams with different shapes. Nothing in the code changed and nothing
failed. The output simply became quietly less complete on some routes than on others, and the metric
that would have caught it — how many parts were seen versus how many were rendered — is a metric
almost nobody records. Record it. A counter of dropped parts, by type, costs nothing and is the only
instrument that makes this failure visible at all.

**The review comment a senior engineer leaves:** *"This handler does `if part.text:` and nothing
else, so it works today because our model only sends text. The docstring for
`generate_content_async` says every intermediate chunk is `partial=True` regardless of content type
and lists function calls, bytes and thoughts alongside text — so the day someone attaches a tool to
this agent, the call goes straight in the bin and the user sees a stall with no error. Please make it
a branch per type with a default arm that logs the unknown type rather than skipping it, buffer
function calls until the non-partial event rather than acting on a fragment, and decide explicitly
whether thoughts are shown or only logged — that one is a data-boundary question, not a rendering
one. Also add a dropped-parts counter so we find out from a dashboard rather than from a customer."*

**The interview question:** *"You have a streaming handler that renders `part.text` for every event.
What does it get wrong?"* An honest answer: *"It's a text-streaming handler, not a streaming handler.
The framework's contract says every intermediate chunk is flagged partial regardless of what it
carries, and it names four kinds: text, function calls, bytes like images, and thoughts when thinking
is enabled. Only the first one has a `text` attribute, so the other three evaluate falsy and get
stepped over — no exception, no log line. The consequences differ per type. A dropped function call
means the tool never runs and the user sees a stall. Dropped bytes mean an answer that references an
image that isn't there. Thoughts are the opposite problem: the risk is showing them, because a
reasoning trace is content the user probably wasn't meant to see. And the important one about
function calls is that a partial call isn't something to execute, it's something to wait for — you
can render a fragment, you can't act on one. I should be straight that I reasoned this from the
framework's documented contract rather than measuring it. My own lab's fake model only ever emitted
text, so I couldn't produce a single non-text chunk to prove it, and extending that fake is the first
thing I'd do before trusting any of it in a handler I owned."*
