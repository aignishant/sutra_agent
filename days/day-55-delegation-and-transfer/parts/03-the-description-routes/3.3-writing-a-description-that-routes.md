# 3.3 — Writing a description that routes

## One-line answer

A description that routes has four parts in a fixed order — what it does, what it returns, what it
does **not** do, and nothing else — and the third part is the one that does the work, because a
routing decision is won by being *false* for other people's requests.

## The story

The garage at the end of our road has two men and one hand-written sign in the window.

*MOT, servicing, brakes, exhausts, tyres. No bodywork, no electrics, no diagnostics on hybrids.*

I have taken three cars there and never once been sent away, which is a strange thing to be able to
say about a garage. Everyone who walks in with a hybrid dashboard warning has already read the
sign and gone somewhere else. The two men spend their day doing brakes and exhausts, which is what
they are good at.

The sign in the next street says *"All makes and models — no job too small."* That garage has a
man permanently on the phone explaining why they cannot do the thing you have just driven over for.

Both signs are true. One of them does a job.

## The idea in plain language

[3.1](3.1-the-staff-list-behind-the-counter.md) established that the description is the routing
rule, and [3.2](3.2-the-clerk-whose-sign-said-all-enquiries.md) measured what a wide claim does.
This part is the procedure, and the procedure is short because the failure is always the same one.

A description that routes has four parts:

1. **What it does** — one sentence, one job, no "and". If you need "and", check whether you have
   two agents.
2. **What it returns** — the shape of the answer, in words. *"Returns the article id and the fix in
   one sentence."* This is not for the caller's benefit; it tells the router whether the answer will
   be usable for the request in hand.
3. **What it does not do** — the exclusions, named specifically enough to be false for a real
   request. *"Does not read tickets."* Not *"does not do everything"*.
4. **Nothing else.** No tone, no persona, no capability marketing, no history. All of that belongs
   in the instruction, where it costs the agent one prompt instead of costing every router on every
   request ([3.1](3.1-the-staff-list-behind-the-counter.md) priced this).

Part 3 is the one that gets left out, and it is the one that does the work. A routing decision is a
competition, and you do not win a competition by being more true — every candidate is true. You win
by the others being *false*. An exclusion is the only sentence in a description that can make
another agent's claim fail.

There is a test for whether an exclusion is doing anything: **write the request it excludes.** *Does
not read tickets* excludes *"what does ticket 4521 say"*. *Does not handle billing* excludes *"why
was I charged twice"*. If you cannot write the sentence, the exclusion is decoration.

## Why Sutra needs it

Tonight's build brief asks for `sutra/delegation.py` with a lead and specialists, and `gate.py`
checks for exactly one thing about the descriptions: that at least one of them contains the words
*does not*. That check is crude on purpose. It cannot judge whether the exclusion is good, but it
can refuse a file where nobody thought about exclusions at all, and that is the failure that
actually happens.

Day 58 has five stations. Day 68 will decide what each is permitted to do. The exclusions written
today are the first draft of the permission model written then — *"does not handle refunds"* in a
description becomes *"has no refund tool"* in a permission set, and the two should agree.

## The mechanism

Here is the desk's existing description, which already follows the shape, annotated:

```text
Triages incoming customer support tickets: explains what a ticket is    <- 1. what it does
about, proposes a likely cause as a hypothesis, and recommends a
priority. Works only from ticket text supplied in the request.         <- 2. what it returns/needs
Does not look anything up, and does not handle refunds, billing or     <- 3. what it does NOT do
account changes.
```

**Line by line:**

- *Triages incoming customer support tickets* is the job in three words; everything after the colon
  is elaboration of that one job, not a second one.
- *Works only from ticket text supplied in the request* is doing double duty — it says what input
  the agent needs, which is what a router most needs to know when it is deciding whether this agent
  can even start.
- *Does not look anything up* excludes every request of the form "find me…". It is checkable: you
  can write the request it turns away.
- *does not handle refunds, billing or account changes* names three subjects rather than saying
  "out of scope". Three nouns beat one abstraction, because the router is matching against a user's
  words and users write nouns.

Now the same shape applied to the two specialists tonight's build needs, with the exclusions
chosen so that no two agents claim the same words:

```python
KB = (
    "Answers one question against the knowledge base and returns the article id "
    "and its fix in one sentence. Does not read tickets and does not write replies."
)
ARCHIVE = (
    "Reads one ticket by its number from the archive and reports what it says. "
    "Does not search the knowledge base and does not propose a fix."
)
```

**Line by line:**

- Each is one sentence of job plus one sentence of exclusion. Two sentences is the working length;
  three is usually a second job hiding.
- The exclusions are **reciprocal**: the KB agent excludes reading tickets, and the archive agent
  excludes searching the knowledge base. That is deliberate. A pair of descriptions that exclude
  each other's territory cannot tie, and a tie is what
  [3.2](3.2-the-clerk-whose-sign-said-all-enquiries.md) measured going wrong.
- *does not write replies* on the KB agent is there because Day 58 adds a drafting station. The
  exclusion is written before the agent it excludes exists, which is cheap now and awkward later.
- No tone, no *"you are a helpful..."*, no mention of the model. None of that helps a router and
  all of it is charged on every request.

The reciprocity is worth one more line, because it is the difference between descriptions that were
written and descriptions that were designed. Lay the roster out as a grid and check that every cell
is decided:

| request about… | kb_specialist | archive_specialist | the lead |
| --- | --- | --- | --- |
| a KB article | **claims** | excludes | excludes (does not look up) |
| a ticket by number | excludes | **claims** | excludes (works from pasted text) |
| triaging pasted text | excludes (no reply writing) | excludes (no fix proposed) | **claims** |
| a refund | excludes | excludes | excludes (named exclusion) |

Every row has exactly one **claims** or none at all, and the *none at all* row is the one that
matters most: a refund is claimed by nobody, so it reaches the lead's refusal, which is the
behaviour Day 6 tested and Day 63 will turn into an approval gate.

## When it breaks

The break is an exclusion that excludes nothing, and it is very common because it feels like
diligence.

```text
Answers knowledge base questions. Does not handle anything outside its scope.
```

*Does not handle anything outside its scope* is unfalsifiable. Apply the test: write the request it
turns away. You cannot, because the sentence defines the excluded set in terms of the included set.
It adds prompt weight, it adds nothing to routing, and it reads to a reviewer as if the exclusion
question has been answered.

The other break is subtler and shows up as an intermittent routing failure. Two agents both exclude
things, but their exclusions do not meet:

```text
kb_specialist:       "... Does not handle billing."
archive_specialist:  "... Does not handle billing."
```

Both exclude billing, neither excludes the other, and every ticket-shaped request is a coin toss
between them. Exclusions have to be **against each other**, not against a third party they both
already avoid. The grid above is how you catch it, and it takes about a minute.

You can check the crude version mechanically:

```bash
cd days/day-55-delegation-and-transfer/lab
uv run python gate.py; echo "exit: $?"
```

**Line by line:**

- `gate.py` reads the file the build brief asks you to write and greps for `does not` / `Does not`
  in it.
- It cannot tell a good exclusion from a bad one, and it does not pretend to. It fails a file with
  no exclusions at all, which is the case worth failing automatically.
- It exits non-zero, so it is a test and not a report.

Measured on 2026-09-05, before the build brief is done:

```text

exit: 1
```

## In production

**What a professional writes instead.** They keep the descriptions of a roster in one place and
review them together — a module of string constants, or a table in the design document — rather
than scattered across the agent definitions where no two are ever on screen at once. The grid above
is then a five-minute review artefact instead of an archaeology exercise. Some teams go further and
generate the grid: score every description against a fixed request set in CI and fail on a tie or
on a row with two claims.

**What degrades at scale.** Exclusions rot in one direction. *"Does not handle billing"* is
accurate until the day billing moves into this agent, and then it is a false statement in a prompt,
which is worse than a missing one — the router will actively avoid sending it work it can now do.
Nobody updates a description when they add a capability, because the description lives in a
different sentence from the code they changed. The guard is to put the exclusion next to the thing
that makes it true: if the agent has no billing tool, a test asserting *"does not handle billing"
appears in the description if and only if no billing tool is attached* is a strange-looking test
that catches a real class of drift.

**The failure that only appears with real traffic.** Exclusions are written against the requests
you imagined. Real users produce requests that fall between two exclusions and are claimed by
nobody, which surfaces as the fallback path being hit far more than expected. That is not a
failure of the descriptions so much as evidence that the roster is missing a member, and the
routing log — grouped by requests that scored zero everywhere — is the list of agents you have not
built yet. It is one of the more useful artefacts a routing system produces.

**The review comment a senior engineer leaves:** *"Both of these say 'does not handle billing' and
neither says anything about the other. What routes 'what does ticket 4188 say about the cookie
fix'? Right now, whichever sorts first. Make the exclusions reciprocal: the KB agent should say it
does not read tickets, and the archive agent should say it does not propose fixes."*

**The interview question:** *"How do you write a good description for a sub-agent?"* An honest
answer: *"Four parts in order: what it does in one sentence with no 'and', what it returns, what it
does not do, and then stop. The exclusions are the part that does the work, because routing is a
competition where every candidate's claim is true, so you win by the others being false. My test
for an exclusion is that I can write the request it turns away — 'does not read tickets' turns away
'what does ticket 4521 say', whereas 'does not handle anything outside its scope' turns away
nothing and is just prompt weight. And I make exclusions reciprocal across the roster, so no two
agents can tie; I lay them out as a grid of request types by agent and check that every row has one
claimant or none."*
