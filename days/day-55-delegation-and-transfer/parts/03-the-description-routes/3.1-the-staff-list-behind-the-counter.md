# 3.1 — The staff list behind the counter

## One-line answer

An agent's `description` is not documentation: ADK pastes it verbatim into the routing agent's
system prompt, under the heading `Agent description:`, and you can print the exact text it builds
without spending a request.

## The story

Behind the counter at the council office there is a laminated card taped to the wall, facing the
staff. It lists everyone in the building and what they deal with. It is not a beautiful document.
Somebody typed it once, printed it, and it has been there ever since.

*Ravi — housing benefit, council tax reduction. Not housing repairs.*
*Farida — parking permits, blue badges, bus passes.*
*Desk 3 — anything else, or if unsure.*

That card is the entire routing system of the building. Not the org chart on the intranet, not the
job descriptions in HR. This card, because it is the one the clerk can see while a person is
standing in front of them.

And you can tell which lines were written by someone who had been on the counter. *Not housing
repairs* is on Ravi's line because for two years everyone sent him housing repairs. The person who
added those three words fixed more misrouted enquiries than any reorganisation did.

## The idea in plain language

Day 10 established that a function's docstring becomes its tool description, and Day 12 sharpened
the general form: [the schema is the prompt
again](../../../day-12-structured-output/parts/02-schemas-in-practice/2.4-the-schema-is-the-prompt-again.md).
Things you write for the machine's benefit end up in front of the model, and are read as
instructions.

An agent's `description` field is the strongest case of that rule in the whole framework, because
the framework does not paraphrase, summarise or transform it. It concatenates it into a block of
text and appends that block to the routing agent's system instruction.

So the description is:

- **the routing rule**, and the only one the model has;
- **prompt weight**, paid on every request the router handles, for every colleague on the list;
- **a public interface**, in the strict sense: change it and you change the behaviour of an agent
  you did not edit.

That last point is the one that surprises people. Editing `billing_agent.description` changes what
`triage_lead` does, without `triage_lead` being touched. Two agents, one coupling, no import.

There is a second field in play and it is worth separating now. An agent's **instruction** is read
by *that agent*, about how to do its job. An agent's **description** is read by *other agents*,
about whether to send work to it. They are different audiences and they are frequently confused —
the instruction is long and internal, the description is short and external.

## Why Sutra needs it

Tonight's build brief asks for `triage_lead` with specialists attached, and the temptation is to
spend the evening on the lead's instruction. That is the wrong place. The lead's routing behaviour
is mostly determined by text the lead does not contain: the descriptions of its colleagues. If the
lead is routing badly, editing the lead is the second thing to try.

Day 58 makes this concrete at graph scale: five stations, each with a description, and the routing
between them is the sum of those five strings. Day 66 makes it a security concern, because a
description is untrusted text if any part of it is ever assembled from something a user supplied.

## The mechanism

`staff.py` builds a real lead with two real specialists and prints the exact text ADK appends. The
function it calls, `_build_transfer_instruction_body`, is the framework's own, imported from
`google.adk.flows.llm_flows.agent_transfer`. It is a pure string builder, so this costs no request.

```bash
cd days/day-55-delegation-and-transfer/lab
uv run python staff.py
```

**Line by line:**

- `_get_transfer_targets(lead)` returns the agents this lead may hand over to
  ([4.3](../04-transfer-in-2x/4.3-parents-peers-and-two-switches.md) is about how that list is
  computed).
- `_build_transfer_instruction_body("transfer_to_agent", targets)` builds the block that gets
  appended to the lead's system instruction. Passing the tool name in is how the framework keeps
  the instruction and the declaration consistent.
- Both are private helpers, marked with a leading underscore. Reading them is legitimate — this is
  a lab establishing what the framework does — but a production agent should not import them, and
  [4.4](../04-transfer-in-2x/4.4-from-agent-tree-to-node-graph.md) says what to do instead.

Verified against `google-adk` 2.7.1 (`google/adk/flows/llm_flows/agent_transfer.py`) and
adk.dev/workflows/collaboration/ on 2026-09-05.

Measured on 2026-09-05:

```text
--- the instruction ADK appends to the lead's system prompt ---

You have a list of other agents to transfer to:


Agent name: kb_specialist
Agent description: Answers one question against the knowledge base. Returns the article id and its fix in one sentence. Does not read tickets.


Agent name: archive_specialist
Agent description: Reads one ticket by its number from the archive and reports what it says. Does not search the knowledge base.


If you are the best to answer the question according to your description,
you can answer it.

If another agent is better for answering the question according to its
description, call `transfer_to_agent` function to transfer the question to that
agent. When transferring, do not generate any text other than the function
call.

**NOTE**: the only available agents for `transfer_to_agent` function are
`archive_specialist`, `kb_specialist`.
```

Four things in that text are worth reading closely, because each is a decision the framework made
on your behalf.

1. **`Agent description:` followed by your exact string.** No summarisation, no truncation, no
   reformatting. What you typed is what the model reads. If your description is three words, the
   model routes on three words.
2. **The routing rule is stated twice in terms of the description** — *"according to your
   description"* and *"according to its description"*. The framework is telling the model, in
   English, that the description is the criterion. There is nothing else it could route on; it has
   no other information about these agents.
3. **The model is told it may answer itself.** *"If you are the best to answer the question
   according to your description, you can answer it."* The lead's own `description` is therefore
   also a routing input, competing with its colleagues'. A lead described as *"a helpful support
   assistant"* is claiming everything, and [3.2](3.2-the-clerk-whose-sign-said-all-enquiries.md) is
   about what that does.
4. **The enum is repeated in prose.** The `**NOTE**` line lists the valid names again, in addition
   to the schema constraint that [4.2](../04-transfer-in-2x/4.2-the-enum-that-refuses-a-stranger.md)
   shows. Belt and braces, and a hint about how often models invent colleagues.

Now the cost side. Every one of those characters is on every request the lead handles.

| | Characters |
| --- | --- |
| Fixed framing (the "You have a list…" text and the note) | about 480 |
| `kb_specialist` name + description | about 160 |
| `archive_specialist` name + description | about 140 |

Add a fifth specialist with a paragraph-long description and the lead is carrying roughly a
thousand characters of staff list on every request, including the requests it answers itself. Day
24's arithmetic applies unchanged: this is [charged again every
turn](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.2-charged-again-every-turn.md).
A description should be one or two sentences not because brevity is elegant but because it is
rent.

## When it breaks

The break here is a description that is empty, and it fails in the most unhelpful way available:
silently, with a plausible-looking prompt.

`description` defaults to the empty string on `LlmAgent` — it is not required. Attach a sub-agent
without one and the framework builds this:

```text
Agent name: kb_specialist
Agent description:
```

No error, no warning. The model is now routing on the *name* alone, because that is all it has
been given. Names route surprisingly well when they are good (`kb_specialist` is legible) and not
at all when they are not (`agent_2`, `helper`, `sutra_worker_v3`). The failure is invisible in code
review because the missing thing is a field that is not there, and it is invisible at runtime
because routing on a name mostly works until it does not.

The check is one line and worth putting in the quality gate:

```python
for sub in lead.sub_agents:
    assert sub.description.strip(), f"{sub.name} has no description - it cannot be routed to"
```

**Line by line:**

- `sub.description` rather than `sub.instruction`: the instruction can be as long as you like and
  says nothing to the router.
- `.strip()` because a description of `" "` passes a truthiness check and fails a model.
- The message names the consequence, not the rule. A reviewer who sees *"it cannot be routed to"*
  fixes it; a reviewer who sees *"description required"* adds the word "assistant".

## In production

**What a professional writes instead.** They treat descriptions as a set rather than as
per-agent documentation, and they review them together, on one screen, the way the council office's
card is one card. The question is never "is this description good?" but "given these five, which
one wins for a request about X?" — which is exactly what
[3.3](3.3-writing-a-description-that-routes.md) turns into a procedure.

**What degrades at scale.** Descriptions are written when an agent is created and almost never
revisited, while the set they compete in changes every time somebody adds a colleague. So they
degrade *passively*: a description that was unambiguous among three agents becomes ambiguous among
eight, without anybody editing it. The cheap defence is to print the assembled block — exactly what
`staff.py` does — in CI, and diff it. A pull request that adds an agent then shows a diff of the
routing prompt of every agent that can reach it, which is the honest representation of what the
change actually does.

**The failure that only appears with real traffic.** The description is written in the vocabulary
of the person who built the agent (*"knowledge base"*, *"archive"*), and users write in theirs
(*"the help articles"*, *"old tickets"*). Routing quality is really vocabulary overlap between user
language and description language, and you cannot measure it from inside the team that chose the
words. Real routing logs, grouped by the phrasing users actually used, are the only source.

**The review comment a senior engineer leaves:** *"This PR adds `escalation_agent` with a
two-paragraph description. That text goes into the system prompt of every agent that can transfer
to it, on every request, forever. Cut it to the one sentence that distinguishes it from
`billing_agent`, and put the rest in its instruction where it belongs."*

**The interview question:** *"How does a coordinating agent decide which sub-agent to use?"* An
honest answer: *"On the sub-agents' `description` fields, and essentially on nothing else. ADK
appends a block to the coordinator's system instruction listing each candidate as `Agent name:` and
`Agent description:` with the string copied verbatim, and it tells the model in so many words to
choose 'according to its description'. Two consequences I care about: editing one agent's
description changes the behaviour of a different agent that imports nothing from it, and every
description is prompt weight on every request the router handles. So I review descriptions as a set
rather than individually, and I print the assembled routing block in CI so a PR that adds an agent
shows what it did to everyone else's prompt."*
