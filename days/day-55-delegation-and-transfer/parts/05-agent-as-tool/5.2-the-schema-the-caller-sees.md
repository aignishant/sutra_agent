# 5.2 — The schema the caller sees

## One-line answer

By default a sub-agent-as-tool exposes exactly one argument — `{"request": {"type": "string"}}`,
required — so the caller hands over one blob of free text; giving the specialist an `input_schema`
replaces that with named, described, required fields, and the difference is the difference between
a blank line and a form.

## The story

The old repair shop took jobs on a scrap of paper. You said what was wrong, the man wrote a line,
and the line said things like *"noise"* or *"not charging properly"*. Then the technician in the
back would open the job, read *"noise"*, and have to phone you to ask which kind of noise, when,
and whether it happened cold or hot.

The new job card has boxes. *Symptom. When it happens. What you have already tried. Model number.*
It is not longer to fill in — it is shorter, because you are not composing a sentence, you are
answering four questions. And the technician does not phone anybody, because the four things they
were always going to need are on the card.

Same shop, same work, same two people. The form moved the missing information from a phone call to
the moment of asking.

## The idea in plain language

Day 12 established the shape on the way in: [the sheet you fill in before you are
called](../../../day-12-structured-output/parts/01-the-shape-on-the-way-out/1.4-the-sheet-you-fill-in-before-you-are-called.md)
— an `input_schema` is a form the caller must complete, and its field descriptions are read by the
model that fills it in.

A sub-agent used as a tool has to be given *something* by its caller, and ADK has to decide what
the argument list looks like. Its default is deliberately minimal:

```text
{"type": "object", "properties": {"request": {"type": "string"}}, "required": ["request"]}
```

One string, called `request`, required. Whatever the caller wants the specialist to know has to be
composed into that string by the caller's model, in prose, on the spot.

That default is fine for genuinely open-ended specialists and bad for everything else, for three
reasons:

1. **Nothing is required except the blob.** If the specialist needs the product area to do its
   job, there is no way to say so. It either guesses or asks, and it cannot ask — it is a
   single-turn agent that does not talk to the user.
2. **The caller decides what to include.** Which means it decides what to leave out, differently
   each time, and the specialist's quality now varies with the caller's summarising.
   [6.2](../06-price-of-a-handoff/6.2-what-the-specialist-cannot-see.md) measures that loss.
3. **You cannot validate it.** A string is a string. A schema with named fields is checked before
   your specialist ever runs.

`input_schema` replaces the blob. Give the specialist a pydantic model and ADK builds the tool's
argument list from it: field names, types, descriptions, and which are required.

## Why Sutra needs it

Tonight's `kb_specialist` answers knowledge-base questions. What does it need? The symptom, and the
product area — because *"cookie problem"* means one thing under auth and another under analytics.
With the default schema, whether the product area arrives depends on whether the lead thought to
mention it in a sentence. With an `input_schema`, it is a required field, and a call that omits it
does not happen.

Day 58's research station is the same argument at graph scale, and Day 79's evals need stable
inputs to be evaluated against — a free-text blob composed differently on every run is not a stable
input.

## The mechanism

`astool.py` builds the same specialist twice, once with and once without an `input_schema`, and
prints the declaration ADK generates.

```bash
cd days/day-55-delegation-and-transfer/lab
uv run python astool.py
```

**Line by line:**

- `declaration(agent)` attaches the agent to a throwaway lead so ADK performs the wrapping, then
  reads `lead.tools[0]._get_declaration()`. The declaration is what goes to the provider.
- `KbQuestion` is an ordinary pydantic `BaseModel` with two fields and a `Field(description=...)`
  on each. Day 12's rule applies: those descriptions are read by the model filling the form.
- Both runs print the tool's `description` as well, so it is visible that the description does not
  come from the schema — it is the agent's own `description` field
  ([3.1](../03-the-description-routes/3.1-the-staff-list-behind-the-counter.md)).

Verified against `google-adk` 2.7.1 (`google/adk/tools/agent_tool.py`) and
adk.dev/tools/function-tools/ on 2026-09-05.

Measured on 2026-09-05:

```text
1. no input_schema - the caller gets one string
  wrapper       _SingleTurnAgentTool
  tool name     kb_specialist
  description   Answers one question against the knowledge base. Returns the article id and its fix in one sentence. Does not read tickets and does not write replies.
  arguments     {'type': 'object', 'properties': {'request': {'type': 'string'}}, 'required': ['request']}

2. with input_schema - the caller gets named fields
  wrapper       _SingleTurnAgentTool
  tool name     kb_specialist
  description   Answers one question against the knowledge base. Returns the article id and its fix in one sentence. Does not read tickets and does not write replies.
  arguments     {'description': 'The named fields a caller fills in instead of one free-text `request`.', 'properties': {'symptom': {'description': 'What the customer sees going wrong.', 'title': 'Symptom', 'type': 'string'}, 'product_area': {'description': 'One of: auth, billing, onboarding.', 'title': 'Product Area', 'type': 'string'}}, 'required': ['symptom', 'product_area'], 'title': 'KbQuestion', 'type': 'object'}
```

Four things changed and one did not.

**`required` went from `['request']` to `['symptom', 'product_area']`.** That is the whole point.
The product area is now structurally required; a call without it is not a valid call.

**The field descriptions travelled.** `'One of: auth, billing, onboarding.'` is in the declaration,
so the caller's model is told the permitted values at the moment it is filling the form. That
sentence would have been a hope in an instruction; here it is on the form.

**The model's own docstring became the argument-object description.** `'The named fields a caller
fills in instead of one free-text `request`.'` is the class docstring of `KbQuestion`. Day 10's
rule again, one level up: docstrings are prompt.

**Titles appeared.** `'title': 'Symptom'` is pydantic's doing, not ADK's. Harmless, and worth
recognising so you do not go looking for where you configured it.

**The tool description did not change.** Identical in both runs, because it comes from the agent's
`description`, not from the schema. Argument shape and routing text are two separate fields with
two separate jobs, and confusing them is a common way to end up with a well-described tool nobody
can call correctly.

There is one more consequence, and it is in the framework's handling of the input. When an
`input_schema` is set, `AgentTool` validates the arguments and then sends the specialist a bare
JSON document as its user message. The comment in the installed source says why:

```text
      # The text must stay a bare JSON document: the node runtime re-validates
      # it against this same schema, so any prose here fails that parse.
```

So the schema is enforced twice — once when the caller fills the form, once when the specialist
receives it. That is a good property and it has a sharp edge:
[5.4](5.4-a-failure-that-arrives-as-a-string.md) shows what a validation failure looks like from the
caller's side.

## When it breaks

The break is a validation failure, and it arrives as a **string**, not an exception:

```text
  quota    type=str   failed=True
           Error running sub-agent: 429 RESOURCE_EXHAUSTED: quota exceeded for gemini-3.7-flash, retry in 27s
```

That is `swallow.py` showing what the caller receives when the specialist cannot run. An input that
fails schema validation takes the same route: `_SingleTurnAgentTool.run_async` catches it and
returns `f"Error validating input: {e}"` as the tool result. Your caller's model receives a
sentence, sees a tool result, and — unless you have written the check — carries on as if it were an
answer. [5.4](5.4-a-failure-that-arrives-as-a-string.md) is that whole subject.

The other break is over-specifying. A schema with eight required fields means the caller's model
must produce eight correct values before the specialist runs at all, and every one of them is a
place to fail. Worse, some of them are things the caller genuinely does not know — a required
`customer_id` on a specialist called from a context where no customer has been identified is a call
that can never be made. The working heuristic: **required means the specialist cannot function
without it and the caller can always know it.** Anything else is optional with a sensible default,
or is not a field.

## In production

**What a professional writes instead.** They give an `input_schema` to any specialist whose inputs
are actually known, and leave the free-text `request` for the genuinely open-ended ones. The tell
is whether you can name the fields: if you can write down what the specialist always needs, write
it as a schema; if the honest answer is "it depends what they ask", the blob is correct and you
should not invent structure to look tidy.

**What degrades at scale.** Schemas are a contract between two agents, and contracts drift. Add a
field to `KbQuestion` and every caller's prompt changes shape, silently, on the next deploy —
including callers written by other teams who have never read your specialist. Making it required is
a breaking change to them. The discipline is the same as any API: new fields arrive optional, and
become required only after the callers have been updated. Day 38's migration lab is the general
version of this argument.

**The failure that only appears with real traffic.** Field descriptions are read by the caller's
model, and a description like *"One of: auth, billing, onboarding"* is advice, not enforcement —
the type is still `string`. Real traffic produces `"Auth"`, `"authentication"`, `"auth/login"`.
If the value matters, make it an enum in the schema (the same mechanism
[4.2](../04-transfer-in-2x/4.2-the-enum-that-refuses-a-stranger.md) uses for agent names) rather
than a sentence in a description, and normalise in the specialist anyway.

**The review comment a senior engineer leaves:** *"This specialist needs the product area to give a
useful answer, and right now the only argument is a free-text `request`, so whether it gets the
product area depends on how the lead phrases a sentence. Give it an `input_schema` with
`product_area` as a required enum. You will also get validation for free, and the eval will stop
being non-deterministic on inputs."*

**The interview question:** *"What does one agent actually send to another when it calls it as a
tool?"* An honest answer: *"By default, one required string called `request` — ADK generates that
declaration when the sub-agent has no `input_schema`, so the caller's model composes a prose blob
and everything the specialist needs has to be in it. That makes the specialist's quality depend on
the caller's summarising, and there is no way to require a field. If I know what the specialist
needs, I give it an `input_schema`: the declaration then carries named fields with descriptions and
a real `required` list, and the framework validates twice — once when the caller fills the form and
again in the specialist. I keep `required` to what the specialist cannot work without *and* the
caller can always know, because a required field the caller cannot supply is a call that can never
be made."*
