# 4.2 — The enum that refuses a stranger

## One-line answer

Because `transfer_to_agent` does not validate its argument, ADK constrains it at the schema
instead: the declaration the model receives carries `"enum": ["kb_specialist",
"archive_specialist"]`, turning "name a colleague" from free text into a choice from a list.

## The story

The parcel office has a form for redirecting a delivery, and it used to have a blank line for the
depot you wanted it sent to. People wrote all sorts of things on that line. *The one near the
station.* *Croydon (big one).* *Same as last time.* Every one of those had to be read by a human,
guessed at, and often got the parcel sent to the wrong place — or nowhere, which took three weeks
to find out.

They changed the form. Now that line is a row of tick-boxes with the six real depot names printed
next to them. You cannot write *the one near the station* any more, because there is nowhere to
write it. You have to look at six names and pick one.

Nobody was retrained. The form stopped accepting the wrong answer.

## The idea in plain language

Day 12 established the general principle: [a schema a model can
fill](../../../day-12-structured-output/parts/02-schemas-in-practice/2.1-a-schema-a-model-can-fill.md)
is a constraint the model works inside rather than a rule it is asked to remember. A field typed as
a string invites any string. A field typed as *one of these five values* invites one of five
values.

An **enum** — short for enumeration — is that: a schema constraint listing the permitted values of
a field. The provider's structured-output machinery enforces it when it builds the function call,
so an invalid value is prevented at generation rather than caught afterwards.

[4.1](4.1-transfer-is-a-signal.md) showed that `transfer_to_agent` accepts whatever string it is
handed and writes it into an action. That is a deliberate division of labour, not an oversight: the
function is dumb and the *declaration* is where the safety lives. ADK builds a special tool class
for this, `TransferToAgentTool`, whose only job is to take the ordinary declaration and pin an enum
of real agent names onto the `agent_name` parameter.

The failure it prevents has a name worth knowing. A model asked to produce an identifier from
memory will sometimes produce a plausible one that does not exist — `billing_specialist` when the
agent is called `billing_agent`, or `kb_agent` when it is `kb_specialist`. It is the same class of
error as an invented citation or an invented package version, and it is common precisely because
the invented name is *reasonable*. An enum removes the opportunity.

## Why Sutra needs it

Tonight's lead has two specialists, so the enum has two entries and the whole issue looks
theoretical. Day 58's graph has five stations, and Day 70's quota router adds providers as
routing targets. Names multiply, and they multiply in the direction of being similar to each other
— `kb_specialist`, `kb_agent`, `archive_specialist`, `archive_agent` — which is exactly the
condition under which a near-miss name gets generated.

It also matters for what you write in the lead's instruction. Once you know the enum is there, you
know you do not need to list the valid names again in your own prose. The framework already does it
twice, and a third copy is prompt weight you are paying for nothing.

## The mechanism

`handover.py` builds a real lead with two real sub-agents, constructs the transfer tool the way
the framework does, and prints the declaration the model would receive.

```bash
cd days/day-55-delegation-and-transfer/lab
uv run python handover.py
```

**Line by line:**

- `_get_transfer_targets(lead)` computes the reachable agents. The enum is built from that list, so
  the constraint and the reachability cannot drift apart — a target that is not reachable is not in
  the enum, and vice versa.
- `TransferToAgentTool(agent_names=[...])` is the real class. It subclasses `FunctionTool` around
  `transfer_to_agent` and overrides only the declaration.
- `tool._get_declaration().parameters_json_schema` is the JSON Schema sent to the provider. It is
  the thing the model is actually constrained by, as opposed to anything in the prose.

Verified against `google-adk` 2.7.1 (`google/adk/tools/transfer_to_agent_tool.py`) and
adk.dev/workflows/collaboration/ on 2026-09-05.

Measured on 2026-09-05:

```text
--- 2. the declaration the model is shown ---
{'properties': {'agent_name': {'title': 'Agent Name', 'type': 'string', 'enum': ['kb_specialist', 'archive_specialist']}}, 'required': ['agent_name'], 'title': 'transfer_to_agentParams', 'type': 'object'}
```

Three things are being done there at once.

- `'type': 'string'` — the base type, inferred from the function's `agent_name: str` annotation,
  which is Day 10's [type hints are the
  schema](../../../day-10-function-tools/parts/01-the-form-fills-itself/1.3-type-hints-are-the-schema.md)
  doing its job.
- `'enum': ['kb_specialist', 'archive_specialist']` — the constraint added by
  `TransferToAgentTool`, and the whole subject of this part. The names are the live reachable set,
  not a hand-maintained list.
- `'required': ['agent_name']` — you cannot transfer to nobody. If the model calls this tool it
  must name a target.

And note what the class's own docstring says about why it exists, from the installed source:

```text
  This tool enhances the base transfer_to_agent function by adding JSON Schema
  enum constraints to the agent_name parameter. This prevents LLMs from
  hallucinating invalid agent names by restricting choices to only valid agents.
```

The framework says the quiet part out loud. This is anti-hallucination machinery, and it is in the
schema rather than in the prompt because a schema is enforced and a prompt is advice.

There is a belt-and-braces arrangement here that is easy to miss. The valid names appear in
**three** places on every request:

| Where | What it is | Enforced? |
| --- | --- | --- |
| `Agent name:` lines in the injected instruction | prose, one per candidate | no |
| The `**NOTE**` line listing valid names | prose, a reminder | no |
| `enum` in the declaration | JSON Schema on the parameter | yes |

Only the third is a constraint. The first two are the framework hedging, because structured-output
enforcement is a property of the provider and not of ADK, and a provider that ignores an enum leaves
only the prose.

## When it breaks

There are two breaks, and the interesting one is the second.

**The name is not in the enum.** The transfer request never forms in the first place. What you see
is not an error but an absence: the model picks one of the names it was offered, or answers
itself. That is the system working.

**The enum is empty.** If an agent has no transfer targets, ADK does not build the tool at all —
the request processor returns early when `_get_transfer_targets` is empty. That is why `reach.py`
prints `(nobody)` for an agent with both switches on
([4.3](4.3-parents-peers-and-two-switches.md)). The failure mode is a lead that cannot transfer and
gives no indication of why: no tool, no instruction block, nothing in the prompt about colleagues.
If your lead is stubbornly answering everything itself, check the target list before you rewrite
the instruction.

**The name is in the enum but the agent is gone.** This is the one worth planning for. The enum is
built from the live tree at request-assembly, so it cannot list a deleted agent. But
[4.1](4.1-transfer-is-a-signal.md) showed the *function* writing whatever string it receives into
an action, with no validation — so if a call arrives that did not come through this declaration
(a replayed event, a hand-written test, a model that ignored the schema), the action carries a name
nothing resolves. The error then surfaces in the runtime, at control-transfer time, well away from
the code that caused it. When you see an unresolvable agent name in a traceback, the question is
not "why did the model say that" but "how did this call bypass the enum".

## In production

**What a professional writes instead.** They do not restate the valid agent names in the lead's
instruction. It is a tempting belt-and-braces move and it is a third copy of something already
present twice, charged on every request, and guaranteed to drift the day someone adds a specialist
and forgets the prose. Trust the enum; it is generated from the same list the runtime uses.

**What degrades at scale.** Enum size. With five colleagues the constraint is a genuine help. With
sixty — a large routing tree, or providers as targets — the enum is sixty strings in every request,
and the model is picking from a list too long to be a meaningful constraint. That is the point at
which flat routing stops working and the tree gets a layer: route to a *group* first, then within
it, which puts a small enum at each level. Day 58's graph is where that structure starts.

**The failure that only appears with real traffic.** Enum enforcement is a provider behaviour, and
the free-tier lanes this curriculum uses are not all equally strict. A provider that treats
`enum` as advisory will occasionally produce a name outside it, and the failure surfaces as an
unresolvable transfer target rather than as a validation error. The defence is not to rely on the
enum alone for anything that matters: validate the name against the live roster in a
`before_tool_callback` before letting the transfer through, which costs nothing and turns a runtime
error into a clean refusal.

**The review comment a senior engineer leaves:** *"The lead's instruction lists the four specialist
names again. Delete that paragraph — ADK already puts the names in the injected block, in the
`**NOTE**` line, and as an enum on the parameter. Your copy is the only one that will not update
itself when someone adds a fifth."*

**The interview question:** *"How do you stop a model from routing to an agent that does not
exist?"* An honest answer: *"With a schema constraint rather than a prompt instruction. ADK wraps
the transfer function in a tool class whose only job is to attach an enum of the currently
reachable agent names to the `agent_name` parameter, so the invalid choice is prevented at
generation instead of caught afterwards. The function itself does no validation at all — it just
assigns the string to an action — so the enum is the entire defence, and that means it is only as
strong as the provider's structured-output enforcement. On a free-tier lane I would not rely on it
alone: I validate the target against the live roster in a tool callback, so a name that slipped
through becomes a clean refusal instead of an unresolvable transfer deep in the runtime."*
