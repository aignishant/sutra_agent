# 2.2 — What comes back when the tool refuses

## One-line answer

A refused tool call does not raise and does not return nothing; it returns an ordinary result that
says *this needs confirmation*, and that string goes back to the model — which means the wording of
a refusal is part of your prompt, not just part of your logs.

## The story

The ATM at the corner takes your card and gives you nothing.

You stand there for a moment wondering whether it has eaten the card, and then it prints a slip.
The slip says: *unable to complete transaction — please contact your branch*.

That slip is doing two jobs at once and it is only good at one of them. For the bank's own records
it is fine — somewhere there is a code that says exactly what happened, whether it was your balance
or your daily limit or a bad network line to the card network. For **you**, standing there, it is
almost useless. You do not know whether to try a smaller amount, try tomorrow, try a different
machine, or go and stand in a queue at the branch.

So you do the thing everybody does. You put the card back in and try again, with the same number,
because the slip did not tell you not to.

The refusal was correct. The refusal was also an instruction to the person in front of it, and
nobody wrote it as one.

## The idea in plain language

When ADK's gate stops a call, the tool still **returns a value**. It does not raise an exception and
it does not silently return `None`. It returns a dict:

```
{'error': 'This tool call requires confirmation, please approve or reject.'}
```

This matters because of where that value goes. A tool's return value is fed back to the model as the
result of the call it asked for. The model then decides what to do next, reading that sentence the
same way it reads any other tool output.

So a refusal message is **text in the model's context window**. It is not a log line. It is closer
to an instruction, and the model will act on it.

That gives you three separate audiences for one string, and they want different things:

| Audience | What they need from a refusal |
| --- | --- |
| The model | What to do next: wait, tell the user, try something else, or stop |
| The human approver | What is being asked, with enough detail to decide |
| The incident review, later | Which call, which policy, which version |

ADK's default sentence serves the first audience adequately and the other two not at all, which is
fine — it is a default. The point of this part is that you now know it is a default, and that
changing it is a prompt-engineering decision rather than a cosmetic one.

One term, defined once: **the tool result** is whatever a tool hands back to the runtime, which the
runtime turns into a `function_response` and puts in the next model request. Day 4 built this by
hand — [`days/day-04-tools-by-hand/`](../../../day-04-tools-by-hand/LESSON.md) — and the shape has
not changed: a tool that returns a string is a tool that is writing part of the next prompt.

## Why Sutra needs it

The desk's gated action is a reply going to a customer. When the gate stops it, the agent is still
mid-run and still has to do something sensible: not retry the same call in a loop, not tell the
customer the reply was sent, and not fabricate a result — which is Principle 10, and is exactly the
failure Day 21 was about
([`days/day-21-errors-surface-not-swallow/`](../../../day-21-errors-surface-not-swallow/LESSON.md)).

Whether the agent behaves sensibly there depends on a sentence, and section 4 shows the graph-shaped
version of the same problem, where the "message" is written by you rather than by the framework.

## The mechanism

The refusal string is not assembled at the call site. It comes from the library, and the way to know
what it says is to read what the library actually returned — which is what `toolgate.py` printed in
part [2.1](2.1-one-argument-turns-a-tool-into-a-gate.md):

```text
  2 gated, nobody asked yet          {'error': 'This tool call requires confirmation, please approve or reject.'}
                                     effects: []
                                     requested for: ['fc-1']
```

Two things are being returned at once, and only one of them is the dict.

The dict goes back to the model. The line `requested for: ['fc-1']` is something else entirely: the
tool has written into the call's **context actions**, a side channel the runtime reads after the
tool returns, saying "I want a confirmation for the call with id `fc-1`". The model never sees that.
It is how the runtime knows to pause and ask rather than simply carrying on with an error.

So a refusal is one event with two outputs: a **message to the model** and a **request to the
runtime**. Confusing them is the source of most of the trouble in this area.

To see what the runtime does with that request, run:

```bash
cd days/day-64-approval-gates-build/lab
uv run python pending.py
```

**Line by line:**

- `pending.py` calls the gated tool exactly as part 2.1 did, then prints the contents of
  `ctx.actions.requested_tool_confirmations` — the side channel — field by field.
- It then hands the pieces to ADK's own `generate_request_confirmation_event`, the function the
  runtime uses to turn that request into an event a client can receive. Calling the library's own
  builder rather than constructing an event by hand is what makes the printed shape trustworthy.
- Nothing here is a model call. The arguments are supplied by the script.

Measured on 2026-09-06:

```text
what the tool wrote when it refused:

  keyed by function_call_id  fc-4655
  hint                       'Please approve or reject the tool call close_ticket() by responding with a FunctionResponse with an expected ToolConfirmation payload.'
  confirmed                  False
  payload                    None
```

Three fields, and they are the three the installed `ToolConfirmation` model declares — `hint`,
`confirmed`, `payload`. Verified by introspection against `google-adk==2.7.1` on 2026-09-06.

`confirmed: False` is the default, not a rejection. This is the single most common misreading of
this object, and part [2.3](2.3-a-rejection-is-not-a-failure.md) is about the difference.

`hint` is the string a human is meant to read, and the default is a sentence about
`FunctionResponse` payloads written for whoever is integrating the client. It is not a sentence you
would put in front of a shift lead at the end of a shift. That is the gap section 4 closes, where
the message is yours to write.

`payload` is `None` and is the interesting empty field: it is the slot for the data the human needs
in order to decide. Nothing fills it automatically. Part
[3.2](../03-binding-the-answer/3.2-the-request-carries-a-copy-of-the-call.md) shows what does get
carried automatically, which is the call itself.

## When it breaks

The failure here is not an exception. It is a loop, and it is quiet.

An agent asks for a gated tool. The tool returns `{'error': 'This tool call requires
confirmation...'}`. The agent reads a string containing the word *error*, concludes something went
wrong, and — because that is what models do with transient-looking errors — **tries the same call
again**. Here is what the framework does with a caller that will not take no for an answer:

```bash
cd days/day-64-approval-gates-build/lab
uv run python -c "
import asyncio, _actions, _adk, _policy
from google.adk.tools import FunctionTool


def gate_close(ticket_id: str, resolution: str) -> bool:
    return _policy.needs_approval('close_ticket', {'resolution': resolution})


async def main():
    ic = await _adk.invocation()
    tool = FunctionTool(_actions.close_ticket, require_confirmation=gate_close)
    _actions.reset()
    for attempt in (1, 2, 3):
        r = await tool.run_async(
            args={'ticket_id': '4655', 'resolution': 'refund'},
            tool_context=_adk.context(ic, call_id=f'fc-{attempt}'),
        )
        print(f'  attempt {attempt}  {r}')
    print(f'  effects: {_actions.EFFECTS}')


asyncio.run(main())
"
```

**Line by line:**

- Three calls with three different `call_id` values, because a retrying agent produces a *new*
  function call each time rather than resending the old one. That detail is what makes this a loop
  rather than a duplicate, and part
  [3.4](../03-binding-the-answer/3.4-one-approval-delivered-twice.md) is about the other case.
- `_actions.reset()` once, before the loop, so the ledger accumulates across all three attempts.
- The gate and the tool are built exactly as in `toolgate.py`; only the loop is new.

Measured on 2026-09-06:

```text
  attempt 1  {'error': 'This tool call requires confirmation, please approve or reject.'}
  attempt 2  {'error': 'This tool call requires confirmation, please approve or reject.'}
  attempt 3  {'error': 'This tool call requires confirmation, please approve or reject.'}
  effects: []
```

The good news is in the last line: `effects: []` after three attempts. The gate holds, however many
times you push on it, and no amount of retrying gets the refund out. The bad news is everything
above it. Nothing raised, nothing logged a failure, and each of those attempts in a real run is a
model request against a free-tier quota — spent to be told the same sentence three times.

This is a refusal that reads like a failure instead of like a wait, and left alone it runs until
Day 59's containment guard fuses the run.

The smallest fix is not in the framework. It is in the agent's instruction: tell it, in words, that
a confirmation request means the run will pause and be resumed by a person, that it must not retry,
and that it must not report the action as done. A gate you did not tell the agent about is a gate
the agent will fight.

## In production

**What a professional writes instead.** They replace the default hint with a sentence written for
the approver, and they keep a separate, structured record for the audit — the two audiences get two
artefacts rather than one string trying to be both. The approver's sentence names the customer-
visible effect (*"send a refund reply to the customer for ticket 4655, by email"*), not the function
(*"call close_ticket"*). Nobody outside your team knows what `close_ticket` means, and the approver
is often outside your team.

**What degrades at scale.** Every refusal is tokens in the next model request, on every retry, for
every gated call. A verbose refusal message multiplied by a busy shift is a real line on a quota
that Day 24 taught you to count
([`days/day-24-token-accounting-and-budgets/`](../../../day-24-token-accounting-and-budgets/LESSON.md)).
Keep the model-facing string short and put the detail in the payload, which the model does not read.

**The failure mode that only appears with real traffic.** The refusal string ends up quoted to the
customer. The agent is drafting a reply, a tool is refused mid-draft, and the refusal text is in its
context alongside everything else it is about to write. Transcripts where an end user is told *"This
tool call requires confirmation, please approve or reject"* are not rare, and they are the reason
the output guardrails on Day 67 exist.

**The review comment a senior engineer leaves:** *"The refusal says 'error'. The model is going to
treat it as retryable and we will pay for that four times per gated call. Either change the wording
or handle it in the instruction — right now nothing tells the agent that a pause is a normal
outcome."*

**The interview question:** *"When your approval gate blocks a call, what does the model see?"* An
honest answer: *"An ordinary tool result — in ADK a dict with an `error` key saying confirmation is
required. That is important because it lands in the context and the model acts on it, so the wording
is part of the prompt. The first version of ours caused retry loops until we told the agent in its
instruction that a confirmation request means stop and wait. Separately, the runtime gets a request
on a side channel keyed by the function call id, and that is what actually causes the pause — the
model never sees it."*
