# 1.3 — The arguments decide, not the tool

## One-line answer

The same tool called two ways can be routine or irreversible, so the gate has to be a **function of
the arguments**, and a policy that cannot see the arguments is guaranteed to be wrong for a large
fraction of real calls — on this desk, for twenty of twenty-four.

## The story

A courier is at your door with two parcels.

The first one he hands over without breaking step. He is already turning away as you take it.

The second one he holds on to. "Signature, please." He turns his machine round so you can scribble
on it with your finger, waits for the screen to change, and only then lets go of the box.

Same courier. Same company. Same van, same street, same afternoon. The only difference is what is
inside, and he did not decide the difference — somebody, somewhere, marked one consignment as
needing a signature and the other as not.

Now imagine the two obvious ways to get this wrong.

Make every parcel need a signature, and the round takes twice as long, and by Thursday the driver
is signing for you himself so he can finish before dark. Make no parcel need one, and the first
time an expensive item goes missing there is nothing at all to point at.

The rule that works is not about the courier and not about the company. It is about the parcel in
his hand.

## The idea in plain language

Part [1.1](1.1-a-gate-is-a-decision-about-one-action.md) said the gate is a decision about a call.
This part is about *why the arguments carry so much of the weight*, and what it costs when they are
ignored.

Take Sutra's `send_reply`. It takes a ticket, a channel and a body. Three channels are possible:

| channel | where it goes | can you take it back? |
| --- | --- | --- |
| `portal` | a page inside the customer's account | yes — edit it, and if they have not looked, nobody knows |
| `email` | their inbox | no |
| `sms` | their phone | no, and it arrives with a buzz at whatever hour you send it |

One function. Three blast radii. The difference between the first row and the last two is not a
matter of degree — it is the difference between *changeable* and *gone*.

A policy that can only see the name `send_reply` has exactly two options, and both are bad:

- **Gate it.** Now every portal note — the overwhelming majority of the desk's traffic — waits for a
  human. Part [7.1](../07-in-production/7.1-the-queue-in-front-of-the-approver.md) measures what
  that does to the queue, and the number is worse than people expect.
- **Do not gate it.** Now refund emails go out unread.

The word for the property that makes the arguments matter is **conditionality**: the rule holds
under a condition on the call, not over the call's name. In `policy.json` that is the `when` key
from part [1.2](1.2-the-policy-is-a-file-not-a-habit.md), and this part is the argument for its
existence.

There is a second reason, less obvious and more important in an agentic system. **The arguments are
the part the model chose.** The tool name was chosen by you when you registered it; the arguments
were produced by a language model reading a ticket that a stranger wrote. If an injected
instruction is going to turn a note into a refund — the threat Day 66 opens Phase 10 with — it will
do so by changing an argument, not by inventing a tool. A gate that does not look at the arguments
is blind to precisely the thing an attacker controls.

## Why Sutra needs it

The measurement below is the reason this day exists as a build day rather than a paragraph in
Day 63. On one shift of the desk, twenty of twenty-four calls do not need a human, and four do.
Those four are two refunds and two emails — and they are made by the same two functions as sixteen
of the twenty that pass straight through.

If Sutra gated by tool name, `send_reply` and `close_ticket` would both be gated, and the shift
would generate fourteen approval requests instead of four. Part
[7.1](../07-in-production/7.1-the-queue-in-front-of-the-approver.md) shows that fourteen is more
than one approver clears, which means the gate stops being a control and starts being a queue that
people learn to clear without reading.

## The mechanism

The gate is one function, and its whole body is the policy lookup:

```python
def gate_close(ticket_id: str, resolution: str) -> bool:
    """The policy, asked about these arguments. This is the whole gate."""
    return _policy.needs_approval("close_ticket", {"resolution": resolution})
```

**Line by line:**

- The signature is the **tool's own signature**. That is not a coincidence and it is not optional:
  ADK calls this function with the tool's arguments, by name, so the parameters have to match. Part
  [2.1](../02-the-tool-gate/2.1-one-argument-turns-a-tool-into-a-gate.md) is where that contract is
  spelled out.
- `ticket_id` is accepted and unused. Leaving it in the signature rather than swallowing it with
  `**kwargs` is deliberate: a reader can see exactly which arguments the gate could have looked at,
  and adding a condition on the ticket later is a one-line change rather than a signature change.
- The body has no `if` in it. Every branch lives in `policy.json`, which is the point of part
  [1.2](1.2-the-policy-is-a-file-not-a-habit.md). A gate function with logic in it is a second place
  the policy lives.
- It returns `bool` and nothing else. It does not raise on a dangerous call and it does not log —
  deciding and acting are separate, and section 2 is where the acting happens.

Now the same policy applied across the shift, twice: once with the arguments and once by name only.

```bash
cd days/day-64-approval-gates-build/lab
uv run python decide.py
uv run python decide.py --all-writes
```

**Line by line:**

- The first run uses `policy.json`, which means every decision consults the `when` clause and
  therefore the arguments.
- `--all-writes` is the ablation: the same twenty-four calls, judged by a rule that can only see the
  action name — *anything that is not a read needs a human*. It is the policy a team writes in its
  first week, and it is exactly the policy you get when the gate cannot see arguments.
- Nothing else differs. Same shift, same order, same code path.

Measured on 2026-09-05:

```text
policy: policy.json v3
  calls this shift      24
  stopped for a human   4
  gate rate             17%

policy: gate every write
  calls this shift      24
  stopped for a human   14
  gate rate             58%
```

Four against fourteen. Every one of the extra ten is a portal note or a memory write, which is to
say: ten interruptions of a person's afternoon that protect nothing, because a portal note is
editable and a memory row is overwritable.

And the ten are not evenly spread. They cluster, because a desk works ticket by ticket, which is
what makes the queue in part
[7.1](../07-in-production/7.1-the-queue-in-front-of-the-approver.md) form.

## When it breaks

The break is subtler than "the policy is too broad". It is what a broad policy does to the *people*.

Here is the shape, in the four beats:

> 🎬 **The scene:** the gate ships with `--all-writes` semantics. Fourteen approval requests a
> shift, most of them portal notes reading *"we have applied a note"*.
>
> 😬 **The naive fix:** the approver gets faster. They learn the shape of the routine request and
> start clearing them in a batch without opening each one.
>
> 💥 **Why it fails:** the two requests a shift that genuinely matter now look exactly like the
> twelve that do not. They arrive in the same list, in the same format, with the same buttons. The
> approver's accuracy on the ones that matter has fallen, and nothing in the system measured it —
> the dashboard shows fourteen approvals a shift, all answered, all green.
>
> 💡 **The insight:** a gate's value is not the number of things it stops. It is the *attention per
> stop*. Widening a gate reduces attention per stop, so past a certain width, adding actions to a
> policy makes the system less safe. This is the argument Day 63 made from the design side; this is
> it with a number on it.

The mechanical break is smaller and worth seeing too. Get the parameter name wrong in the gate
function and it fails at call time, not at registration:

```text
TypeError: gate_close() got an unexpected keyword argument 'resolution_code'
```

That is what you get when the tool's parameter is renamed and the gate's is not. It is loud, which
is the good case — compare it with the silent `None` in part
[1.2](1.2-the-policy-is-a-file-not-a-habit.md)'s *When it breaks*, where a mismatch produced no
error and no gate.

## In production

**What a professional writes instead.** They derive the gate's parameter list from the tool's
signature in a test, so a rename cannot silently unhook the two. One parametrised test that asserts
`set(signature(gate).parameters) <= set(signature(tool).parameters)` for every gated tool catches
the whole class.

**What degrades at scale.** The `when` clause is a single field with a value list, which is enough
for a support desk and runs out fast. The next thing that gets asked for is a threshold — *refunds
over ten thousand rupees* — and then a combination — *over ten thousand, or any amount for an
account opened this month*. The temptation is to put an expression language in the policy file. It
is worth resisting for as long as you can, because an expression language in a config file is a
program that nobody tests. The usual landing place is a small set of named predicates in Python,
referenced by name from the file, so the file stays enumerable and the logic stays testable.

**The failure mode that only appears with real traffic.** Argument distributions move. The policy
was written when three per cent of closures were refunds. A pricing change makes it fifteen, the
gate rate triples overnight, and the first anybody hears of it is the approver asking why their
queue is full. Gate rate is a metric to put on a dashboard next to the request budget, not a
constant to assume.

**The review comment a senior engineer leaves:** *"This gate takes `**kwargs`. That means I cannot
tell from reading it which arguments influence the decision, and neither can the next person who
adds a parameter. Spell the parameters out — the tool's signature is short."*

**The interview question:** *"How do you stop an approval gate becoming a rubber stamp?"* An honest
answer: *"By keeping it narrow enough that every request is worth reading, and the way you keep it
narrow is by gating on arguments rather than on tool names. I measured both on one shift of our
support desk: the argument-aware policy stopped four calls out of twenty-four, and the
name-only version stopped fourteen. The extra ten were all portal notes, which are editable, so they
bought nothing and cost ten interruptions. Past some width the approver stops reading, and at that
point a wider gate is strictly worse than a narrower one — you have the same protection and less
attention."*
