# 1.4 — The guard that was only added in three places

## One-line answer

Writing the gate as a condition at each place the action happens gives you as many policies as you
have call sites, and they drift apart silently — measured here, two of four call sites let a call
through that the policy file stops, and **one of the two has a guard**; it is just out of date.

## The story

An office block has four ways out. The main entrance, a side door onto the car park, a fire exit at
the back, and a loading bay that only the delivery people use.

After a laptop goes missing, the committee decides bags will be checked on the way out. A guard is
put on the main entrance the following Monday. Two weeks later somebody points out the side door,
and a second guard appears there.

Nobody mentions the fire exit, because it is a fire exit and you are not supposed to use it. Nobody
mentions the loading bay, because the delivery people are not really *staff*.

Ask anybody in that building what the rule is and they will tell you, honestly, that bags are
checked on the way out. They have watched it happen. They have had it happen to them. The rule
exists, it is enforced, and everyone can describe it.

And a laptop still leaves through the loading bay every few months, and each time there is a meeting
where somebody says *"but we check bags"*.

The problem was never the guards. It is that the rule was implemented as *people standing at doors*
rather than as *a list of doors*, and a list of doors is the only artefact that can be checked
against the building.

## The idea in plain language

The two ways to write the policy, from part [1.2](1.2-the-policy-is-a-file-not-a-habit.md), differ
in one property that only shows itself over time: **whether the policy can be enumerated.**

A policy in a file is one object. Ask it a question, get one answer.

A policy written as conditions at call sites is not one object at all. It is *n* objects that happen
to have been written to resemble each other, where *n* is a number nobody knows, because it is the
number of places the action can be reached from — and new places appear whenever somebody needs the
same action in a new flow.

Three things then happen, in this order, over about a year:

1. **A call site is added without a guard.** Usually a retry path, a batch job or an admin tool.
   Whoever wrote it was solving a different problem and did not know there was a policy. Nothing
   fails; the tests pass; the new path simply does not stop.
2. **A guard goes stale.** The policy gains a value — `credit` joins `refund` — and three of the
   four sites are updated. The fourth still reads correctly. It has an `if`. It looks guarded in
   review. It is wrong.
3. **Nobody can answer the question.** *"What does this system stop for?"* has no answer that is
   not a search, and a search over a codebase finds the sites you thought of.

Stage 2 is the dangerous one, and it is the one this part measures, because a call site with a stale
guard is invisible to every technique people reach for. Grep finds it. Coverage covers it. A
reviewer reads it and nods. It is a lock fitted to the door, set to the wrong key.

## The mechanism

`scatter.py` writes the same policy twice. Once as data, once as four guards at four call sites —
two for `close_ticket` and two for `send_reply` — and then asks both versions the same question: the
call that must stop.

```python
def close_from_draft_flow(args: dict[str, Any]) -> str:
    if args.get("resolution") in ("refund", "credit"):
        return "ask a human"
    return "do it"


def close_from_bulk_tidy(args: dict[str, Any]) -> str:
    if args.get("resolution") == "refund":  # credit was added to the policy later
        return "ask a human"
    return "do it"


def send_from_draft_flow(args: dict[str, Any]) -> str:
    if args.get("channel") in ("email", "sms"):
        return "ask a human"
    return "do it"


def send_from_retry_path(args: dict[str, Any]) -> str:
    return "do it"  # nobody added a guard here
```

**Line by line:**

- `close_from_draft_flow` is the guard as it should be: both gated resolutions, matching
  `policy.json`. This is the one everybody reads in review, and it is correct.
- `close_from_bulk_tidy` is stage 2. It has an `if`. It is guarded. It was written when `refund` was
  the only gated resolution and was never revisited when `credit` was added — the comment says so,
  because in real code there is no comment, and that is the point.
- `send_from_draft_flow` is correct again.
- `send_from_retry_path` is stage 1: a call site with no guard at all. The retry path was added by
  somebody making retries work, and retries had nothing to do with approvals.
- Every one of the four returns a string rather than raising, because that is how these are actually
  written — the guard decides and the caller carries on. Nothing here is a strawman.

The measurement counts the `if` statements too, by parsing each function, so that "has a guard" and
"is guarded correctly" can be told apart:

```python
def guard_count(fn: Any) -> int:
    """How many `if` statements guard this call site - 0 means the gate is not there."""
    tree = ast.parse(inspect.getsource(fn).strip())
    return sum(isinstance(node, ast.If) for node in ast.walk(tree))
```

**Line by line:**

- `inspect.getsource(fn)` reads the function's own text at run time, so the count is of the code
  that is actually loaded rather than of a copy in a document.
- `.strip()` matters: `getsource` returns the function indented as it appears in the file, and
  `ast.parse` refuses to parse an indented block.
- `ast.walk` descends into nested statements, so a guard inside a loop or another branch is still
  counted. Counting `if`s is a crude proxy for "somebody thought about this here", which is exactly
  the thing a reviewer's eye is using, and the point is that the proxy is wrong.


**Line by line:**

- `scatter.py` asks the same question twice about the same probe call: once of `policy.json`, and once
  of each of the four call sites. Putting both answers in one output is the whole design — the
  disagreement is the finding, and a script that printed only the call sites would show four opinions
  and no way to tell which is right.
- It prints `ifs=` per call site from `guard_count` above, so a site with a guard and a site without
  one are visibly different rows even when they reach the same wrong answer.
- `<-- HOLE` marks a site whose answer differs from the policy's. Marking rather than raising is
  deliberate: the point is that all four of these run happily in a real repository.

Measured on 2026-09-05:

```text
one policy, two spellings. Probe: the call that must stop.

  as data (policy.json):
    close_ticket   {'resolution': 'credit'}  ->  ask a human
    send_reply     {'channel': 'sms'}  ->  ask a human

  as `if` statements, per call site:
    close_from_draft_flow    ifs=1  ->  ask a human
    close_from_bulk_tidy     ifs=1  ->  do it  <-- HOLE
    send_from_draft_flow     ifs=1  ->  ask a human
    send_from_retry_path     ifs=0  ->  do it  <-- HOLE

  call sites                 4
  call sites that let it past 2
  places to read the policy   1 (data) vs 4

  policy.json rows: 6, every one carrying a `because`.
```

Read the `ifs` column, because it is the finding. `close_from_bulk_tidy` has **one** `if`, the same
as the two correct sites. On the metric a reviewer actually uses — *is there a check here* — it is
indistinguishable from the code that works. It lets a credit through anyway.

`send_from_retry_path` has zero, and that one at least is findable: a lint rule could demand a guard
in any function that calls `send_reply`. No lint rule can tell you that a guard's value list is one
element short.

## When it breaks

The break is what happens when somebody tries to fix this by hand.

You have four sites. You update all four. You are careful. Six weeks later a fifth arrives and the
count is five, and the person who wrote it never saw this document.

The error that eventually surfaces is not a Python error. It is a line in the effects ledger:

```text
  effects: [('close_ticket', '4655', 'credit')]
```

A credit applied with nobody asked. There is no traceback, because nothing went wrong: the code did
exactly what it says. That is the whole difficulty with this failure class and the reason the fix
has to be structural rather than careful.

The structural fix has two halves, and section 6 builds both:

- **One place that decides** — the policy file, so there is one thing to update.
- **One place that acts** — the wrapper, so there is one thing to route through. Part
  [6.2](../06-wiring-the-desk/6.2-three-roads-to-one-function.md) shows that the second half is the
  harder one, and measures a system that has the first and not the second.

## In production

**What a professional writes instead.** They make the ungated path harder to reach than the gated
one. The raw action moves behind a leading underscore or into a private module, and the only public
name is the gated wrapper. That does not make bypass impossible in Python — nothing does — but it
converts "somebody did not know" into "somebody typed an underscore", which is a thing you can see
in review and a thing a reviewer will ask about.

**What degrades at scale.** The number of call sites grows with the number of teams, not with the
number of features, because each new team arrives with its own flow and its own idea of what already
exists. At two teams, updating four sites by hand is annoying. At six teams nobody knows the
denominator, and the honest answer to *how many call sites are there* becomes *we think about
twelve*.

**The failure mode that only appears with real traffic.** The path that skips the gate is almost
always a path that only runs under stress: a retry after a timeout, a backfill after an outage, a
manual replay of a stuck queue. It gets no traffic in testing and all its traffic on the worst day
of the quarter, which is also the day everyone is too busy to notice a refund going out unasked.

**The review comment a senior engineer leaves:** *"This is the third place I have seen this
condition. Two of them list `refund` and `credit` and this one lists `refund`. Please move the list
into the policy file and have all three call it, because right now the only way to know they agree
is to read all three, and next quarter there will be four."*

**The interview question:** *"You have an approval check in four places. What is wrong with that?"*
An honest answer: *"That you now have four policies. I built exactly that as an experiment: four
call sites for two gated actions, and when I probed them with the call the policy says must stop,
two of the four let it through. The one that surprised me had an `if` in it — it was written when
only refunds were gated and never updated when credits were added, so it reads as guarded and is
not. That is the failure a code review cannot catch, because the reviewer's test is 'is there a
check here' and the answer is yes. The fix is not diligence, it is having one place that decides and
one place that acts."*
