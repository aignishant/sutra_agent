# 1.2 — The policy is a file, not a habit

## One-line answer

The list of gated actions belongs in a data file that a person can read end to end in one sitting,
with a written reason on **every** row including the ungated ones, because a policy you have to
reconstruct by reading code is a policy nobody reviews.

## The story

Your housing society has a rule about deliveries. Or it might have two rules. It depends who you
ask.

The watchman on the day shift lets couriers walk up to your flat. The one on nights makes them
leave everything at the gate and phones you. Nobody has ever written this down. When a new watchman
joins, he learns by standing next to whoever is on duty, so the rule drifts a little each time,
like a story retold.

Then somebody's parcel goes missing and there is a meeting. And the meeting cannot start, because
the first question — *what is our rule?* — has no answer. Four people give four versions, each of
them describing what they have personally seen happen, each of them right about that.

Compare it with the notice that eventually gets pinned up in the lobby. Six lines. What may come
up, what waits at the gate, and beside each line, in brackets, why. Now a new watchman reads it on
his first morning. Now the committee can argue about the rule instead of about what the rule is.
And now, when somebody wants to change it, there is a specific line to change and a specific reason
to argue with.

## The idea in plain language

The decision from part [1.1](1.1-a-gate-is-a-decision-about-one-action.md) — *does this call need a
human?* — has to be recorded somewhere. There are two places it can live:

- **In the code**, as conditions at the places where actions happen. This is what grows on its own
  when nobody decides. Part [1.4](1.4-the-guard-that-was-only-added-in-three-places.md) measures
  what it costs.
- **In data**, as a file the program reads and a person can read too.

"Data" here does not mean anything exotic. It means a `.json` file with one row per action. The
important properties are not about the format:

1. **It is enumerable.** You can answer *"what does this system stop for?"* by reading one file to
   the end. With code you can only answer it by searching, and a search tells you about the places
   you thought to look.
2. **It is diffable.** Changing the policy shows up in review as a change to the policy, not as
   three lines buried in a refactor of the drafting stage.
3. **Every row carries a reason.** Including — especially including — the rows that say *not
   gated*. A policy file that lists only the gated actions is a list, not a policy. It cannot tell
   you whether `write_memory` is ungated because somebody thought about it, or because nobody has
   ever mentioned it.
4. **It is versioned.** The version number goes into the approval record (part
   [5.1](../05-the-record/5.1-the-decision-is-already-written-down.md)), so that six months later
   you can answer *"which policy was in force when this was approved?"* — the question every
   incident review eventually asks.

Point 3 is the one that is easy to skip and is worth the most. Day 63's argument was that the
actions you decide **not** to gate are decisions too, and a decision with no recorded reason is
indistinguishable from an oversight.

## Why Sutra needs it

Two days from now the Phase 9 gate asks whether a human approved the write. The honest way to answer
that is not to demonstrate one approval — it is to show the file that says which writes need one,
and then show that the system obeys it. A demonstration proves that the path you walked works. The
file plus a check that reads it is what covers the paths you did not walk.

Day 63 produced the classification. This part is where it stops being a table in a document and
becomes something `sutra/approval.py` can import. The eval in part
[6.3](../06-wiring-the-desk/6.3-the-check-that-goes-red-when-the-gate-goes.md) asserts that the
file exists, precisely because "the policy got inlined during a refactor" is a change that would
otherwise pass review.

## The mechanism

The file. Six rows, one per action the desk can take:

```json
{
  "version": 3,
  "rules": [
    {
      "action": "read_ticket",
      "gated": false,
      "because": "read-only; reversible by doing nothing"
    },
    {
      "action": "close_ticket",
      "gated": true,
      "when": {"field": "resolution", "in": ["refund", "credit"]},
      "because": "moves money; the undo is a second money movement plus an apology"
    },
    {
      "action": "send_reply",
      "gated": true,
      "when": {"field": "channel", "in": ["email", "sms"]},
      "because": "leaves the building and cannot be recalled"
    }
  ]
}
```

That is three of the six rows; `lab/policy.json` has all six. The shape of a row:

- `action` — the name from part [1.1](1.1-a-gate-is-a-decision-about-one-action.md). Not the tool
  name and not the function name, so that two tools performing one action get one answer.
- `gated` — the coarse answer. `false` here ends the matter for that action.
- `when` — the fine answer, and the reason this is not simply a list of names. It names one argument
  field and the values of it that make the call dangerous. Part
  [1.3](1.3-the-arguments-decide-not-the-tool.md) is entirely about this key.
- `because` — prose, for a person. Nothing reads it. That is the point: it is the row's argument for
  its own existence, and if you cannot write one, you have not made a decision.

Now the code that reads it. The whole of it:

```python
def needs_approval(action: str, args: dict[str, Any]) -> bool:
    """True when this call, with these arguments, must be approved by a human."""
    rule = _rule(action)
    if not rule["gated"]:
        return False
    when = rule.get("when")
    if when is None:
        return True
    return args.get(when["field"]) in when["in"]
```

**Line by line:**

- `rule = _rule(action)` — a lookup that raises `UnknownAction` rather than returning a default.
  Deny-by-default is enforced here, once, instead of at every caller
  ([1.1](1.1-a-gate-is-a-decision-about-one-action.md)).
- `if not rule["gated"]: return False` — the coarse answer first. An ungated action never looks at
  its arguments, so adding a field to a read-only call cannot accidentally make it gated.
- `when = rule.get("when")` — `.get`, not `[...]`, because `when` is optional: an action can be
  gated unconditionally, and a row that always stops is a legitimate row.
- `if when is None: return True` — the unconditional case, stated separately rather than folded into
  the expression below, because "gated with no condition" and "gated when the field matches" are two
  different intentions and a reader should be able to see both.
- `args.get(when["field"]) in when["in"]` — `.get` again: a call that omits the field entirely
  yields `None`, and `None` is not in the list, so the call is **not** gated. That is a deliberate
  choice and it is arguable the other way; part *When it breaks* below is about exactly this line.

## When it breaks

The break is in the `.get` on the last line, and it is the kind that produces no error at all.

`send_reply` is gated `when` the `channel` field is `email` or `sms`. Now somebody calls it without
a channel — a default parameter, a partially-built payload, a retry that dropped a field:

```text
>>> _policy.needs_approval("send_reply", {"body": "your refund is on its way"})
False
```

No exception. No warning. `args.get("channel")` returned `None`, `None` is not in
`["email", "sms"]`, and the answer is *no human needed*. A gated action just walked through the gate
because a field was missing.

There are two defensible fixes and you must choose one on purpose:

- **Require the field.** If a rule names a field, a call that omits it raises. This is
  deny-by-default applied one level down, and it is what a policy guarding money should do.
- **Gate on absence.** Treat a missing field as matching, so an incomplete call is always stopped.
  Safer still, and noisier: every malformed call becomes an approval request, and the approver's
  attention is the thing you are trying not to waste.

The lab file does neither, deliberately, so this part has something real to show you. The build
brief in the hub's §4 asks you to pick one and defend it in a comment.

## In production

**What a professional writes instead.** They give the policy file a schema and validate it at
startup, not at first use. A typo in `"gated"` should stop the process from starting, not surface as
an ungated refund at two in the morning. In this repository that means a small Pydantic model over
the file and a call to it in the module body — the same discipline Day 12 applied to model output,
pointed at configuration.

**What degrades at scale.** One file works until two teams own actions. Then it grows a section per
team, then the sections disagree about names, and eventually somebody adds a second file. The move
that survives is to keep one file and make ownership a column in it, rather than to split the file
and lose the property that made it worth having: that you can read all of it.

**The failure mode that only appears with real traffic.** Policy drift in the *arguments*. The
`when` clause names `resolution` values `refund` and `credit`. Six months later the product adds
`goodwill_credit`, which is a refund with a nicer name, and it is not in the list. The rule still
reads correctly, still passes review, and no longer covers the case it was written for. The
defence is a test that asserts the policy's value lists against the enum the rest of the code uses,
so adding a resolution without classifying it fails the build.

**The review comment a senior engineer leaves:** *"Three of these six rows have no `because`. I
cannot tell whether `write_memory` is ungated on purpose or because nobody got to it, and that is
exactly the row an auditor will ask about. Either write the sentence or gate it."*

**The interview question:** *"Where does your approval policy live?"* An honest answer: *"In a JSON
file with one row per action, loaded once, with a version number that goes into every approval
record. Every row has a written reason including the ungated ones, because 'we decided not to gate
this' and 'nobody thought about this' look identical in code and an auditor cannot tell them apart.
The thing that convinced me was trying to answer 'what does this system stop for?' on a codebase
where the answer was scattered across four call sites — I could not answer it, and two of the four
turned out to be wrong."*
