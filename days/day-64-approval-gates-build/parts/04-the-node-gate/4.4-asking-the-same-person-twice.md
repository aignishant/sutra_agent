# 4.4 — Asking the same person the same question twice

## One-line answer

`rerun_on_resume=True` makes the asking node's body run again on resume — and a body that asks
unconditionally **asks again**, pausing the run for ever unless it reads `resume_inputs` and notices
the answer is already there.

## The story

You call the electricity helpline because the bill is wrong.

The recorded voice takes your consumer number. Then a person picks up, and the first thing they ask
is your consumer number. You give it. They listen to the problem, say this is a billing matter, and
transfer you.

The billing person picks up and asks for your consumer number.

You have now said it three times, to a system that already had it after the first. Nothing is broken
— every one of those people did their job correctly, and each of them genuinely did not have it. The
number was collected and then not carried forward, so every stage started from nothing and did the
only sensible thing a stage that knows nothing can do, which is ask.

The cost lands entirely on you. From inside the helpline this looks like three successful
interactions. From where you are sitting it is one question asked three times, and by the third you
are not thinking about your bill any more.

## The idea in plain language

Part [4.2](4.2-where-the-answer-lands.md) measured the default: the asking node's body does **not**
run again on resume, and the answer is handed forward to the successor.

There is a setting that changes this. `adk.dev/graphs/dynamic/`, fetched 2026-09-06, states both
halves: with `rerun_on_resume` false *"the resume payload is routed to the node's successor as input,
bypassing the interrupted node"*, and when true *"the node body re-runs from the top"*.

Re-running from the top is genuinely useful, and the docs say when: *"leaf nodes requesting input
should use `rerunOnResume: false`"*, while *"parent orchestrators calling such nodes must set
`rerunOnResume: true`"*. A node that merely asks does not need to run again. A node that asked
*through* a child and then has to do something with the answer does.

But "re-runs from the top" is exactly as literal as it sounds. The body starts again at line one. It
does not resume after the `yield`. Everything before the `yield` happens a second time, including the
`yield` itself — and a node whose body is *"ask the human"* will, on being re-run, ask the human.

That is the loop this part is about, and the escape from it is `resume_inputs`: a mapping from
interrupt id to the answer that arrived. A node that re-runs must **look there first** and only ask
if the answer is absent. The shape is:

```
answer = ctx.resume_inputs.get(INTERRUPT)
if answer is None:
    yield RequestInput(...)      # first time through
else:
    yield {...}                  # second time: use what came back
```

One term, defined once: **re-entrant** describes code that can be started again from the beginning
without doing its work twice. A node with `rerun_on_resume=True` must be re-entrant, and the only way
to make an asking node re-entrant is to make the ask conditional on not already having the answer.

## Why Sutra needs it

Day 60 measured the same trade-off from the durability side and named the default's cost: on resume
2.7.1 **skips** the node that was running when the process died, so a node with real work in it does
not get to finish that work
([`days/day-60-durable-execution/`](../../../day-60-durable-execution/LESSON.md)).

That is the reason to reach for `rerun_on_resume=True` — and this part is the bill that comes with
it. Part [6.1](../06-wiring-the-desk/6.1-the-sixth-station.md) has to choose one for the desk's gate
node, and the choice is only defensible once both failures have been seen.

The human cost is the real argument. Part
[7.1](../07-in-production/7.1-the-queue-in-front-of-the-approver.md) shows the approver's attention
is the scarcest resource in the system; a node that asks twice spends it twice for one decision.

## The mechanism

`rerun.py` builds the same asking node at three settings and counts how many times its body ran.

```bash
cd days/day-64-approval-gates-build/lab
uv run python rerun.py --rerun
```

**Line by line:**

- `--rerun` wraps the node with `node(ask, rerun_on_resume=True)`. `node()` is ADK's decorator, and
  introspection against installed `google-adk==2.7.1` on 2026-09-06 shows `rerun_on_resume` among its
  keyword parameters — snake-case in Python, though the documentation writes it `rerunOnResume`.
- `--aware` is **not** passed, so `aware` is false and the node's body never consults
  `ctx.resume_inputs`. It asks unconditionally.
- `BODY_RUNS` counts executions; `paused_again` collects the ids of any function calls seen during
  the resume, which is how a second question announces itself.

Measured on 2026-09-06:

```text
rerun_on_resume=True   node reads resume_inputs=False

  ask body executed   2 time(s)
  asked again         ['approval:4655']
  output              (none - the successor never ran)
```

Three facts, and the third is the damage.

**`ask body executed 2 time(s)`** — the body ran in pass 1 and again in pass 2. That is the setting
doing exactly what it says.

**`asked again ['approval:4655']`** — and because the body is *"ask the human"*, running it again
emitted a second `RequestInput`, with the same interrupt id. The shift lead's answer arrived, and the
system's response to receiving it was to ask the same question again.

**`output (none - the successor never ran)`** — the run is paused again. It never reached `after`.
Feed it another answer and it will ask a third time. This is not a slow path or a wasted call; it is
a run that cannot finish, and the only thing stopping it running for ever is that a person eventually
gives up.

Now the same setting with the node made re-entrant:

```bash
cd days/day-64-approval-gates-build/lab
uv run python rerun.py --rerun --aware
```

**Line by line:**

- `--aware` makes the body read `ctx.resume_inputs.get(INTERRUPT)` before deciding what to do.
- `ctx: Context` in the signature is what gives the node access to that mapping. A node that takes
  no arguments — like `ask` in part 4.1 — cannot read `resume_inputs` and therefore cannot be made
  re-entrant.

Measured on 2026-09-06:

```text
rerun_on_resume=True   node reads resume_inputs=True

  ask body executed   2 time(s)
  asked again         no
  output              {'decision': {'approved': True, 'by': 'shift_lead'}, 'decided_in_node': True}
  output              {'successor_saw': {'decision': {'approved': True, 'by': 'shift_lead'}, 'decided_in_node': True}}
```

The body still ran twice — that is what the setting means and it does not change. But the second run
found the answer in `resume_inputs`, took the other branch, and produced a value instead of a
question. `asked again no`, and the successor ran.

And note what the output now contains: `'decided_in_node': True`. Because the body ran again, the
node was able to do something *with* the answer — validate it, enrich it, reshape it — before passing
it on. That is the capability you bought by turning the setting on, and it is why the docs recommend
it for orchestrating nodes.

| | body runs | asks again | successor sees |
| --- | --- | --- | --- |
| default (part 4.2) | 1 | no | the raw answer |
| `rerun_on_resume=True`, not aware | 2 | **yes — run stalls** | nothing |
| `rerun_on_resume=True`, aware | 2 | no | whatever the node made of the answer |

## When it breaks

The failure above has no error text, which is what makes it expensive: a stalled run and a shift lead
answering the same question repeatedly, with every component reporting success.

The break that does produce text is the one you meet while fixing it. Reach for `ctx.resume_inputs`
from a node that did not ask for a context and Python stops you:

```traceback
Traceback (most recent call last):
  File "<string>", line 1, in <module>
NameError: name 'ctx' is not defined
```

That is the honest version. The subtler one is a node that *does* take `ctx` but reads the wrong key
— `ctx.resume_inputs.get("approval:4699")` when the request went out as `approval:4655`. `.get`
returns `None`, `None` means "no answer yet", and the node asks again. The stall is back, and now
there is a plausible-looking line of code that reads `resume_inputs` sitting in the file, so the next
person to read it will assume that path is handled.

Both are the same bug as part [4.1](4.1-a-node-that-stops-and-asks.md)'s mismatched interrupt id,
arriving from the other side. The interrupt id is used in two places — to publish the question and to
find the answer — and nothing checks that the two agree. Derive it once, from the proposal, and pass
it; do not spell it twice.

## In production

**What a professional writes instead.** They keep the asking node dumb and leave it at the default,
and put any work that needs to happen after the answer in a separate node downstream. Then no node in
the graph needs to be re-entrant, and `rerun_on_resume` stays off — the setting is reserved for the
orchestrating case the documentation describes, where a parent node calls a child that interrupts and
must regain control afterwards.

**What degrades at scale.** Every re-run repeats everything before the `yield`. If the asking node
also fetches the ticket, renders the draft or calls a model to summarise the proposal, all of that
happens twice per approval — and on a free-tier quota the model call is the one that hurts, because
Day 24's accounting counts requests and this doubles them for the gated path
([`days/day-24-token-accounting-and-budgets/`](../../../day-24-token-accounting-and-budgets/LESSON.md)).
Put the expensive work in a different node from the question.

**The failure mode that only appears with real traffic.** A node that is re-entrant against one
interrupt but not against two. The moment a proposal needs a second question — approve the refund,
then choose the channel — the body has two `yield`s, and "re-run from the top" means the first
question is re-asked while the second is being answered. Re-entrancy has to be per interrupt, and a
node with two of them is a node that should have been two nodes.

**The review comment a senior engineer leaves:** *"This node has `rerun_on_resume=True` and yields a
`RequestInput` without checking `resume_inputs`. On resume it will re-ask and the run will never
finish. Either drop the flag or guard the yield on the answer already being present — and add a test
that resumes and asserts the successor ran."*

**The interview question:** *"What does re-running a node on resume cost you?"* An honest answer:
*"The body starts from the top, so everything before the pause happens again — including the pause.
I measured a node with `rerun_on_resume=True` that asked, got its answer, and immediately asked the
same question again, leaving the run stalled with the successor never running. The fix is to make the
node re-entrant: read the answer out of `resume_inputs` and only ask if it is not there. The reason
to turn the flag on at all is that the default skips the interrupted node entirely, so a node with
real work after the question never gets to do it — but the cleaner answer is usually to split the
question and the work into two nodes and leave the flag off."*
