# 4.5 — NodeTool, and where it actually lives

## One-line answer

`NodeTool` lets an agent call a pausing node as if it were a tool, joining section 2's world to
section 4's — and in `google-adk==2.7.1` it exists, works, and is **not exported**: it imports only
from `google.adk.tools._node_tool`, is absent from `__all__`, and appears nowhere in the docs.

## The story

The scooter needs a small rubber part where the footboard meets the frame. It has perished and the
panel rattles over every speed breaker.

At the authorised service centre the man looks it up on his screen and says the part is not listed
separately — you have to buy the whole footboard assembly, which costs more than the repair is worth.

At the workshop under the tree by the bus stop, the mechanic listens for about four seconds, walks to
a steel almirah at the back, opens a drawer full of unlabelled rubber bits, and finds it. Fits it in
a couple of turns of a spanner. It is the correct part. It has been in that drawer for years.

It is not in the catalogue. That is a fact about the catalogue, not about the part.

But now think about what you can and cannot rely on. The part works. You can go back to that mechanic
and he will find another one. What you cannot do is order it by name, or expect the next mechanic to
know what you are talking about, or assume the drawer will have it after the shop is reorganised.
Using something that is not in the catalogue is often the right call, and it is a call you should
make knowingly.

## The idea in plain language

Sections 2 and 4 have built two gates that do not meet.

Section 2's gate is on a **tool**: an agent decides to call `close_ticket`, and `require_confirmation`
stops it. Section 4's gate is a **node**: a graph reaches a station that yields a `RequestInput` and
the run pauses.

The gap is an agent that wants to *ask a human* as one of the things it can choose to do. It is not
calling a function that happens to need approval — the approval **is** the action. An agent deciding
"this one is beyond me, I should get a person to confirm before I go on" needs the pause to be
something it can select, like a tool.

`NodeTool` is the piece that joins them: it wraps a **node** so it can be handed to an agent as a
**tool**. The agent calls it the way it calls anything else; underneath, the node runs, and if the
node pauses, the run pauses. This is the second half of what Addendum 01 records as ADK-76 —
*HITL resumption for standalone nodes + `NodeTool`* — the first half being section 4's standalone
pausing node.

The practical thing this buys is that the pause becomes **schema-shaped**. A tool has parameters, and
a model filling them in is a model deciding *what to ask about*. Instead of a node with a hard-coded
interrupt id, the agent supplies the ticket and the resolution, and those become the question.

One term, defined once: **exported** means a name is part of a package's public surface — importable
from the package itself and listed in its `__all__`. A name that exists but is not exported is
usable, unsupported, and free to move between releases without that counting as a breaking change.
This is Principle 8's territory: the rule is never invent an API, and the corollary is to know exactly
what kind of API you are standing on.

## Why Sutra needs it

Sutra's desk is a graph, so the gate part [6.1](../06-wiring-the-desk/6.1-the-sixth-station.md)
builds is a node and does not need this. But the desk is not the only shape in this curriculum:
Day 55 established delegation and agent-as-tool
([`days/day-55-delegation-and-transfer/`](../../../day-55-delegation-and-transfer/LESSON.md)), and an
agent that can delegate is an agent that will eventually need to escalate to a person as one of its
options rather than as something done to it.

The reason it is in this day rather than left for later is Principle 8. ADK-76 names `NodeTool`, and a
day that closes ADK-76 owes the reader an honest account of what that name resolves to in the pinned
version — including the answer *not where the plan implies*.

## The mechanism

`nodetool.py` asks four questions and prints the answers. It is written as a probe rather than a
demonstration, because on this surface the interesting output is where things are.

```bash
cd days/day-64-approval-gates-build/lab
uv run python nodetool.py
```

**Line by line:**

- Step 1 tries the public import and catches the failure, so the failure is *shown* rather than
  described. A `try`/`except ImportError` around an import is the honest way to document a name's
  absence.
- Step 2 imports from the private module and prints `'NodeTool' in google.adk.tools.__all__`, which
  is the machine-readable answer to "is this supported".
- Step 3 wraps three nodes with different signatures, because the constraint on what may be wrapped
  is the part a reader will hit first.
- Step 4 prints the declaration a model would be shown for the accepted node.

Measured on 2026-09-06:

```text
1. from google.adk.tools import NodeTool
   ImportError: cannot import name 'NodeTool' from 'google.adk.tools' (C:\Users\nisha_gnzw\AppData\Roaming\Python\Python312\site-packages\google\adk\tools\__init__.py)

2. from google.adk.tools._node_tool import NodeTool
   ok: <class 'google.adk.tools._node_tool.NodeTool'>
   'NodeTool' in google.adk.tools.__all__: False
```

The name is real and the front door is shut. `google.adk.tools._node_tool` — the leading underscore
is the package telling you this is internal — and `__all__` confirms it: `False`.

It is also absent from the documentation. `adk.dev/graphs/dynamic/`, fetched 2026-09-06, is the page
that covers pausing nodes, `RequestInput` and `rerun_on_resume`, and **`NodeTool` does not appear on
it**. So the plan's ADK-76 names a feature that is, in the pinned version, present in the code and
absent from both the public API and the docs. The hub's §8 records this; it is not something to work
around silently.

Now what it does when you use it:

```text
3. wrapping three nodes
   state_only   ValueError: Node 'state_only' does not have an input_schema defined. NodeTool requires an explicit Pydantic input_schema on the wrapped node.
   untyped      accepted   params=['node_input']   with a declared type: []
   typed        accepted   params=['resolution', 'ticket_id']   with a declared type: ['ticket_id', 'resolution']
```

Three signatures, three outcomes, and the error message is unusually good — it names the node, the
missing thing and the requirement in one sentence.

**`state_only`** is a node that reads everything from shared state and takes no input. `NodeTool`
refuses it, and refusing is right: a tool with no parameters gives a model nothing to fill in, so the
model could not express *what* it wants approved.

**`untyped`** takes a bare `node_input` and is accepted, with one parameter and no declared type. A
model can call it, and it can put anything in — which is the shape that produces part
[4.2](4.2-where-the-answer-lands.md)'s validation errors one step later.

**`typed`** declares a Pydantic input schema, and the parameters come out as `ticket_id` and
`resolution` — the fields of the schema, flattened into the tool's signature.

That last row is the one worth wanting, and step 4 shows why:

```text
4. what the model is shown for `typed`
   is_long_running   True
   description       Ask a human to approve closing a ticket.
   parameters:
     {
       "description": "The shape an agent must fill in to ask for approval.",
       "properties": {
         "resolution": {
           "title": "Resolution",
           "type": "string"
         },
         "ticket_id": {
           "title": "Ticket Id",
           "type": "string"
         }
       },
       "required": [
         "ticket_id",
         "resolution"
       ],
       "title": "ApprovalRequest",
       "type": "object"
     }
```

**`is_long_running True`** is the connection to everything else in this day. It is the same flag part
[3.1](../03-binding-the-answer/3.1-the-question-has-to-be-written-down.md) found in
`long_running_tool_ids` on the tool path: *do not wait for this to return*. An approval and a job that
takes a long time are the same shape to the runtime, and this is where the two mechanisms visibly
converge.

The `description` is the node's docstring, and it is what the model reads when deciding whether to
ask a human — so on this surface a docstring is a routing instruction, exactly as Day 55 argued about
sub-agent descriptions.

## When it breaks

Wrapping a node that reads its inputs from state — the common shape in a real graph, where stations
communicate through `ctx.state` rather than through arguments — fails immediately:

```text
ValueError: Node 'state_only' does not have an input_schema defined. NodeTool requires an explicit Pydantic input_schema on the wrapped node.
```

The fix is in the sentence, and it is more work than it looks: giving the node an explicit schema
means deciding what the *agent* is allowed to specify, which is a permissions question, not a typing
one. A schema with a `ticket_id` field lets the model choose which ticket to ask about. A schema with
a `recipient` field lets the model choose who gets the email. Section 2's whole argument — the gate is
about the arguments — applies here in reverse: the schema is the list of things a model may put into
a proposal, and every field you add is authority you have handed it.

The second break is the one the story is about, and it will not happen today. `from
google.adk.tools._node_tool import NodeTool` works against 2.7.1 and carries no promise beyond it: a
private name may be renamed, moved or removed in any release, and the failure will be an `ImportError`
at start-up after an upgrade that the changelog will not mention, because nothing was publicly
broken.

## In production

**What a professional writes instead.** They put the private import behind one module of their own —
`sutra/adk_compat.py` or similar — with a comment naming the version it was verified against and a
test that imports it. Then an upgrade that moves the name fails in one place, with a message that
says what happened, instead of failing wherever the import happened to be written. That is the whole
mitigation and it costs three lines.

**What degrades at scale.** Every private import is a version pin you did not write down. Day 51's
caching and Day 60's resumability each leaned on ADK internals to some degree; the moment there are
several, upgrading ADK becomes a research project. Keep a list — the hub's §8 is where this day's
entry goes — so the cost of an upgrade is a page you can read rather than a surprise.

**The failure mode that only appears with real traffic.** A model that asks a human too often. Once
the pause is a tool, asking becomes something the model *chooses*, and a model that is uncertain will
choose it — which is exactly when it looks most helpful and costs most. The gate stops being a policy
decision made by your code and becomes a judgement made by a model, and part
[7.1](../07-in-production/7.1-the-queue-in-front-of-the-approver.md) shows what that does to the
approver's queue. Keep the policy gate from section 1 in place underneath: the model may ask, and the
policy still decides what *must* be asked.

**The review comment a senior engineer leaves:** *"This imports from `google.adk.tools._node_tool`.
That is a private module — it is not in `__all__` and it is not documented, so it can move on any
release. Wrap it in our own module with the verified version in a comment and a test that would go
red on upgrade."*

**The interview question:** *"How do you decide whether to use an undocumented API from a
framework?"* An honest answer: *"By finding out precisely what it is first. With ADK's `NodeTool` I
checked three things: whether it imports from the public package, whether it is in `__all__`, and
whether it is in the docs — no, no and no, though the class itself works fine in 2.7.1. That does not
make it unusable; it makes it a pinned dependency with no compatibility promise. So I put it behind
one internal module with the verified version recorded and a test that imports it, and I wrote the
fact down where whoever does the next upgrade will read it. The mistake is not using a private API;
it is using one without knowing you have."*
