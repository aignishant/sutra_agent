# 3.4 — Letters that are not the letters they look like

## One-line answer

A single Cyrillic character inside an English word defeats every string comparison in the ladder
while remaining perfectly readable to a model — and catching it needs a **mixed-script** check, not
Unicode normalisation, because confusable characters deliberately do not normalise.

## The story

A cheque arrives at a bank with a signature on it. The clerk holds it beside the signature card and
looks at both.

They match. Same loops, same slant, same little flourish at the end. She pays it.

Three weeks later it turns out the signature was traced from a letter the account holder had sent to
somebody else. Nothing about the shape was wrong — that was the point of tracing it. What was wrong
was invisible in the shape: the pressure, the speed, the order the strokes were made in. A person
comparing appearances was always going to pass it, because appearance was the only thing the forger
had to get right and the only thing she was checking.

## The idea in plain language

Unicode contains many characters that look like other characters. Cyrillic small ie (U+0435) is
rendered as `е`. ASCII lowercase e (U+0065) is rendered as `e`. In almost every typeface these are
the same shape.

They are not the same character, and to a program they are no more equal than `e` and `7`. So
`"prеvious" == "previous"` is `False`, `"ignore" in text` is `False`, and every string check in
[1.1](../01-the-ladder/1.1-one-lock-is-not-security.md)'s ladder walks straight past.

The model, meanwhile, reads it. Not because it "sees" shapes, but because its tokenizer splits the
odd string into pieces that still sit near the ordinary word in meaning, and because the surrounding
sentence disambiguates completely. Day 2's subword-units part is the mechanism: a word the tokenizer
has never seen becomes several familiar pieces rather than an error.

That asymmetry — **invisible to string comparison, legible to the model** — is what makes confusables
worth a part of their own.

Now the trap inside the trap, which is where most implementations get it wrong. The obvious fix is
Unicode normalisation:

```python
if unicodedata.normalize("NFKC", text) != text:
    return "text changes under NFKC normalisation"
```

**Line by line:**

- `unicodedata.normalize("NFKC", text)` applies compatibility decomposition followed by canonical
  composition — the aggressive normalisation form, the one that folds the most.
- Comparing the result with the original is the check: if normalising changed anything, the text
  contained characters that have a plainer equivalent, which is worth reporting.
- The check returns a reason rather than a boolean, which is the interface every rung of the ladder
  shares.

That check is real and worth having, and **it does not catch confusables.** NFKC folds
*compatibility* characters — fullwidth Latin, ligatures, styled mathematical letters — to their plain
forms, because those genuinely are alternative encodings of the same character. Cyrillic `е` is not
an alternative encoding of Latin `e`; it is a different letter that means a different thing in a
different alphabet, and normalising them together would break the Russian language. So NFKC leaves it
exactly as it is, correctly, and your check reports nothing.

The check that does work asks a different question: **does one word contain letters from two
alphabets?** An English ticket does not spell half a word in Latin and half in Cyrillic. A word that
does is either a forgery or something so unusual it deserves a look.

## Why Sutra needs it

Sutra's ladder is mostly string comparison. `phrase_match` is literally a list of substrings, and it
is the rung that
[1.1](../01-the-ladder/1.1-one-lock-is-not-security.md)'s measurement showed is carrying the entire
detection rate — 6 of 6, with the other three checks contributing nothing on that corpus.

A defence resting on substring matching, against text an attacker can spell however they like, needs
this check or it has a one-character bypass. And because `bad_encoding` is arithmetic rather than
judgement, it is a *boundary*-ish check in the sense of
[1.3](../01-the-ladder/1.3-a-sign-is-not-a-gate.md) — there is no rephrasing that makes a
mixed-script word not be a mixed-script word.

## The mechanism

```python
def bad_encoding(text: str) -> str | None:
    if unicodedata.normalize("NFKC", text) != text:
        return "text changes under NFKC normalisation"
    for word in re.findall(r"\S+", text):
        letters = [c for c in word if c.isalpha()]
        ascii_letters = sum(1 for c in letters if ord(c) < 128)
        if letters and 0 < ascii_letters < len(letters):
            odd = next(c for c in letters if ord(c) >= 128)
            safe = word.encode("ascii", "backslashreplace").decode()
            return f"mixed-script word '{safe}' contains U+{ord(odd):04X}"
    return None
```

**Line by line:**

- The NFKC test comes first and answers a genuinely different question — compatibility characters,
  which *do* fold. Both tricks live under one heading and only one of them is a normalisation problem.
- `re.findall(r"\S+", text)` splits on whitespace rather than using `.split()` on words, because
  punctuation must stay attached: `previous,` and `previous` should both be examined as one token.
- `letters = [c for c in word if c.isalpha()]` drops digits and punctuation. Without this, a
  perfectly ordinary `£400` or `café` in a price or a name trips the check — the test is about
  *letters* from two alphabets, not about any non-ASCII byte.
- `0 < ascii_letters < len(letters)` is the whole test: **some** ASCII letters and **not all** of
  them. A word entirely in Cyrillic passes, correctly — a Russian word in a ticket is a Russian word,
  not an attack. Only mixing within one word is suspicious.
- `word.encode("ascii", "backslashreplace")` escapes the character before it goes into the message.
  This is not cosmetic: a Windows console is cp1252 and **cannot encode the very character this check
  exists to report**, so printing it raw crashes the reporter. That is a real bug found by running
  this, not a hypothetical.
- `U+{ord(odd):04X}` prints the codepoint, which is the only unambiguous way to name a character
  whose whole purpose is to be visually ambiguous. A log line saying *"suspicious character е"* is
  useless to whoever reads it.


Two things in that table, and the second is more important than the first.

**The homoglyph is caught at position 2**, before the phrase list at position 3 and before the fuzzy
check at position 4. The ladder ordering is doing exactly what
[1.2](../01-the-ladder/1.2-cheap-and-certain-first.md) designed it to do: a free arithmetic check
caught an attack and spared the expensive one behind it. Note also that this is the row where
`bad_encoding` earns its place — on the day's main corpus it caught nothing at all, and a team that
had deleted it as dead weight would have had no answer here.

**Three of five still got through.** Spaced-out letters, base64 with an instruction to decode it, and
a plain rephrasing with no keyword in it. The mixed-script check closed one hole precisely and left
the others exactly where they were, which is what a narrow, certain check does and all it claims to
do.

## When it breaks

The check has a false-positive shape, and it is a serious one: **legitimate multilingual text.**

A customer writing from a country where names are transliterated will produce mixed-script words
naturally. A ticket containing `Xiaomi` beside a Chinese product name, an address with a Cyrillic
street name in a Latin sentence, a surname carrying a diacritic that somebody typed with an unusual
keyboard layout — all of these can produce a word with letters from two scripts, and all of them are
ordinary customers.

The check as written above narrows this deliberately — it examines only letters, and only *within* a
single whitespace-delimited word — so `Иван Petrov` as two separate words passes cleanly. But
`Иванov`, one word, does not, and that is a real name spelled the way somebody's system mangled it.

The consequence is the one [5.3](../05-measure-it/5.3-five-more-words.md) measures in general terms:
a desk serving international customers will block real people with this check, and the block will
correlate with which alphabet the customer's name is in. That is worse than a random false positive,
because the errors are not evenly distributed across your customers — they fall on a specific group.

The honest deployment is therefore not "block on mixed script". It is *flag, log, and let through*,
with the block reserved for the cases where the mixed-script word also matches a known phrase after
normalisation — that is, when the two cheap checks agree. A single cheap check with a demographically
skewed false-positive rate should not be a refusal on its own.

## In production

**What a professional writes instead.** They use a maintained confusables table rather than the
crude ASCII/non-ASCII split above. Unicode publishes confusable mappings — the data behind
"is this string visually identical to that one?" — and the production version *skeletonises* a string
into a canonical form and compares that against the phrase list, which catches the homoglyph without
needing to flag the word as suspicious at all. That turns a detection problem into a normalisation
problem, and normalising is the better answer because it produces no false positives: the Cyrillic
`е` maps to `e`, the phrase matches, and a legitimate Russian word skeletonises to something that is
not in the phrase list and passes.

**What degrades at scale.** The naive check is O(characters) with a regex, which is fine. The
skeletonising version needs a table lookup per character and is meaningfully slower on long tickets,
so it belongs at the *retrieval row* level rather than on whole assembled prompts — and Day 50's
900-character chunks are conveniently the right unit.

**The failure that only shows with real traffic.** Emoji, and the rest of modern text. Real tickets
contain emoji, box-drawing characters from pasted terminal output, and non-breaking spaces from
copy-pasted web pages. A first implementation that flagged all non-ASCII would flag a large fraction
of ordinary traffic — which is why the check above filters to `isalpha()` first, and why the version
before that filter existed was unshippable.

**The review comment a senior engineer leaves:** *"NFKC does not catch confusables — Cyrillic е does
not fold to Latin e and it never will, so this check as originally written was inert against the
attack it was named for. The mixed-script test is right. But make it a flag rather than a block:
`Иванov` is a customer, not an attacker, and a refusal here falls on a specific group of our users."*

**The interview question:** *"An attacker replaces one letter in their payload with a lookalike from
another alphabet. What happens to your filter?"* The answer that shows you have implemented it:
*"Every substring check misses it, because they are different characters — and the fix most people
reach for, Unicode normalisation, does not help, because confusables deliberately do not normalise.
NFKC folds fullwidth and ligatures, not Cyrillic. What works is either a mixed-script check on each
word, or better, skeletonising through the Unicode confusables table so the lookalike maps back to
the letter it imitates and the ordinary phrase check fires. I would prefer the second, because the
first blocks customers whose names legitimately mix alphabets."*
