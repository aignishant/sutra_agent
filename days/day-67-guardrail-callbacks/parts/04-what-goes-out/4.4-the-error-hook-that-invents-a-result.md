# 4.4 — The error hook that invents a result

## One-line answer

Returning a value from `on_tool_error_callback` **stops the exception reaching the caller and
substitutes your value as the tool's result** — so a guardrail author reaching for a tidy refusal
turns a database outage into the sentence *"I could not find any prior tickets"*, which is a
fabricated result standing in for a failure.

## The story

A woman rings a parcel company because something she posted a week ago has not arrived. She gives the
tracking number.

There is a pause, and then: *"I'm not showing any record of that item."*

She hangs up and starts working out what to do. She goes back to the shop she posted it from and asks
whether they actually sent it. She rings the person expecting the parcel and apologises. She spends
an afternoon on it, and she starts from the assumption she has been given, which is that the item was
never in the system.

What had happened is that the tracking database was down. The person on the phone typed the number
in, got nothing back, and said what the screen showed. Nobody decided to mislead her. The screen said
no results, so she said no results — and *no results* and *cannot currently look* are the same picture
on that screen and completely different pieces of information.

## The idea in plain language

Part [2.1](../02-where-a-check-stands/2.1-the-eight-places-you-can-stand.md) enumerated the eight
places an ADK callback can stand, and two of them are error hooks: `on_model_error_callback` and
`on_tool_error_callback`. They exist so that a callback can **see** an exception — count it, log it,
attach context, decide whether it is worth alerting on.

They have a second property, and it is not obvious from the name. **If the callback returns a value,
the exception stops there and the value becomes the tool's result.** The run continues. The model
receives your value as though the tool had succeeded, and answers on the strength of it.

That is a reasonable capability to offer, and it is a trap laid exactly where a guardrail author is
standing. The author's instinct is a good one: a raw `ConnectionError` reaching the customer is ugly,
so catch it and return something tidy. `{"refs": [], "count": 0, "note": "no results found"}` is tidy.
It is also a **claim about the world** — that the archive was searched and held nothing — and the
archive was not searched at all.

The master plan names this directly. §5.1 lists four traps in moving from ADK 1.x to 2.x, and trap
**#4** is *don't swallow exceptions*: the 1.x habit was tool errors caught and returned as strings,
hiding failures, and 2.x surfaces exceptions through the runtime precisely so callbacks can act on
them. Acting on them means observing. It does not mean answering in their place.

And this is Principle 10, in its most literal form: *never fabricate a result to cover an error*. The
difference between this part and part [4.3](4.3-the-rewrite-that-lies.md) is worth holding onto — 4.3
fabricates the **record** of what happened, and this one fabricates the **result** the customer acts
on.

## Why Sutra needs it

Because the day is putting checks in eight places, and two of those places can turn a failure into an
answer. A day that teaches where guardrails can stand without teaching what the error hooks do would
be handing over a loaded footgun with the safety catch described as a feature.

It is also a specific risk for a *security* day rather than a general one. The guardrail author is the
person most likely to reach for this hook, because refusing tidily is their whole job. "Return a
polite refusal instead of an exception" is one line of code away from "return a polite fiction instead
of an outage", and the two are written by the same person on the same afternoon.

Sutra has a concrete version of it. The desk's archive is what Days 49 and 50 built, and the answer
*"there are no prior tickets for this customer"* is a real answer the desk gives, routinely, and it is
correct most of the time. That is what makes the fabricated version so hard to see: it is not an
implausible output, it is the **most ordinary output the tool has**.

## The mechanism

The failing dependency first, written the way a real one fails:

```python
def exploding_search(query: str) -> dict:
    """The archive is down. This is what a real dependency failure looks like.

    Args:
        query: the words to look for.
    """
    raise ConnectionError("archive unreachable: connection refused on 127.0.0.1:5432")
```

**Line by line:**

- `ConnectionError` with a message naming a host and a port. That specificity is the point: the
  failure is infrastructural and unambiguous, exactly the kind of thing you would want to know about
  within seconds.
- It is a plain function, registered as a tool by `d.desk(tools=[exploding_search])`, so the exception
  is raised in the same place a real tool's would be — inside the runtime's tool-execution path — and
  reaches the error hook by the same route.

The hook, written by somebody with good intentions:

```python
def swallowing(tool, args, tool_context, error):
    """Turn the failure into a plausible empty result. The run continues, wrongly."""
    return {"refs": [], "count": 0, "note": "no results found"}
```

**Line by line:**

- The four parameter names `tool`, `args`, `tool_context` and `error` are the keyword contract for
  `on_tool_error_callback`. Getting them wrong is part
  [2.4](../02-where-a-check-stands/2.4-the-guardrail-that-never-ran.md)'s failure — a `TypeError` on
  the first request instead of a guardrail.
- `error` is bound and then **never used**. That single fact is the whole bug: the callback has the
  exception in its hand, has been given it deliberately by the runtime so it can act, and discards it.
- The returned dict is shaped exactly like a successful result, because it has to be — the model is
  going to read it as one. It is a well-formed lie.
- The `note` field says `"no results found"`, which is a statement about the archive. Nothing in the
  callback looked at the archive.
- There is no `raise`. That absence is what stops the exception, and it is invisible: the failure mode
  here is a line of code that is not there.

Run it:

```bash
cd days/day-67-guardrail-callbacks/lab
uv run python swallow.py
```

**Line by line:**

- `cd` first: the lab's scripts import their siblings by plain name.
- No flag installs `swallowing` as `on_tool_error_callback` and runs one turn in which the tool is
  called and then the desk answers.

Measured on 2026-09-06:

```text
on_tool_error_callback returns a dict

  tool results   [{'name': 'exploding_search', 'refs': [], 'count': 0, 'note': 'no results found'}]
  the answer     ['I could not find any prior tickets.']

  The archive was unreachable. The desk told the customer there were no prior tickets.
  That is a fabricated result standing in for an outage - Principle 10, exactly.
```

Read the second line as the customer receives it. *"I could not find any prior tickets."* It is
grammatical, confident, plausible and false, and there is no way for the customer to tell — this is
the sentence the desk says on all the days when it is true.

Now the honest version. Take the callback away entirely:

```bash
uv run python swallow.py --raise
```

**Line by line:**

- `--raise` passes `callbacks = {}` — no error hook at all — so the exception travels through the
  runtime and out of `d.run(agent)` the way an unhandled exception does.

Measured on 2026-09-06. Two things are abbreviated and nothing else is changed: the site-packages
prefix on each ADK path is written as `...`, and six frames of the flow's own event plumbing are

The frame worth stopping on is `functions.py`, line 640: `raise tool_error`. That is the runtime
**re-raising** the tool's exception after the error hook has had its chance — which is 2.x doing
exactly what trap #4 says it does, surfacing the exception so a callback can act on it, and then
continuing to surface it because the callback returned nothing.

This run is uglier and it is the correct one. The customer got no answer. The on-call engineer gets a
`ConnectionError` naming a host and a port. Nobody was told the archive was empty, because it was not
empty — it was unreachable, and those are different facts.

## When it breaks

The error hooks are not a mistake and this part is not an argument for never using them. They exist
for a reason, and the reason is worth stating so the line is usable rather than a slogan.

**What they are legitimately for:** seeing the exception. Incrementing a counter for this tool and
this error type. Writing a log line with the run id, the arguments and the failure. Attaching context
a stack trace does not have — which customer, which stage, which retry. Deciding that this particular
error class is worth waking somebody for. All of that is observation, and all of it is what the hook
was added to enable.

**The rule:** observe, then re-raise. A hook that returns nothing lets the exception continue on its
way; a hook that returns a value has answered on the tool's behalf.

```text
allowed:      look at the error, record it, add context, then let it through
not allowed:  answer in its place
```

There is one genuine exception, and it has a precondition. A **retry** or a **fallback** may
legitimately produce a value where a tool failed — search a replica, use a cached answer — because in
those cases something really did happen and there really is a result. The precondition is that the
substitution is **recorded and visible**: the result says where it came from, an event says the
primary failed, and the answer the customer sees can be traced back to a degraded path. That is the
same rule part [4.3](4.3-the-rewrite-that-lies.md) arrived at from the other direction — a system may
do something unusual, and it may not do it quietly.

The version to refuse outright is the one in the measurement above: a substitute value that asserts
something about the world, with no record that the world was never consulted.

## In production

**How this looks in monitoring, and why nobody finds it.** The error rate goes to zero. That is the
whole problem in one sentence. Every dashboard, alert and SLO built on "how often do our tools fail"
reads clean, because the failures are being converted into successes one layer below the metric. What
moves instead is answer quality, resolution rate, repeat-contact rate — numbers that drift slowly,
have a dozen plausible explanations, and are owned by a different team from the one that would
recognise the cause.

**Why it is worse than a crash.** A crash is loud, immediate and attributable: somebody is paged, the
stack trace names the host and port, and the fix is a fix. A fabricated result is quiet, and it
converts an infrastructure problem into wrong answers given to real people who then act on them. The
parcel in the story is the point — the cost was not the outage, it was the afternoon she spent
starting from a false premise.

**What degrades at scale.** Swallowing spreads, because each instance is locally reasonable. One team
adds it to stop a noisy alert. Another copies the pattern because it is in the codebase. After a year
the system has several layers that each turn a failure into a plausible default, and the composite
behaviour is a service that never reports being broken. The structural defence is to make the
substitution visible in the data — a `degraded: true` field that propagates, and an alert on its rate
rather than on the exception count that no longer exists.

**What a professional does instead.** Let it raise, and make the raise pleasant to receive: an error
hook that records the failure with full context, a run that fails cleanly, and a customer-facing
message that says the desk cannot check right now rather than that there is nothing to find. Those two
sentences are almost the same length and are completely different claims, and choosing between them is
a product decision that should be made once, deliberately, rather than accidentally inside a callback.

**The review comment a senior engineer leaves:** *"The error callback returns a result dict, which
means a database outage reaches the customer as 'no prior tickets' — that's an outage being reported
as a fact about their account. Bind the error, log it with the run id and the tool arguments, and then
return `None` so it propagates. If we want a friendly message, it belongs in the layer that renders
the failure, not in the hook that hides it. And if we ever do add a cached fallback, it has to carry a
flag saying so, or we'll be having this conversation again with a nicer-looking bug."*

**The interview question:** *"Your agent's tool throws. What should the framework do, and what should
you do?"* An honest answer: *"The framework should surface it — ADK 2.x does, and the error hooks exist
so a callback can see it rather than replace it. What I should do is observe and re-raise: log it with
context, count it, and let it propagate. The thing to avoid is returning a value from the error hook,
because that becomes the tool's result and the model answers as though the call succeeded. I've seen
the concrete version of that: an archive was unreachable and the desk told the customer there were no
prior tickets, which is the same sentence it says when that's true. From monitoring it looked perfect
— the error rate was zero, because the errors had been converted into answers. If you genuinely want a
fallback, that's fine, but the result has to carry a flag saying it's degraded, so the substitution is
in the data rather than hidden in a callback."*
