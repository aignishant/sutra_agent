# 6.2 — When the guardrail itself throws

## One-line answer

A guardrail is code, and code raises — and in ADK 2.7.1 the exception propagates and the run stops,
which is **fail-closed by accident**: it is a property of the framework re-raising, not of your
policy, and a policy that depends on somebody else's re-raise is a policy you have not written down.

## The story

A woman is buying a coat in a small shop. She is at the counter with her card out and the assistant
is frowning at the terminal, which is showing a spinner and has been for a while.

*"Sorry — the line's down. It's cash only until it comes back."*

Two streets away, in a café, the same thing has happened and the answer is different: the young man
behind the counter waves the customer off with the coffee. *"Take it, we'll sort it later."*

Neither of them is improvising. Each shop decided, once, what to do when the terminal cannot reach
the bank, and then never mentioned it again. The coat shop decided the risk of not getting paid was
worse than a lost sale. The café decided a two-pound coffee was not worth losing a regular over.

Both decisions are defensible. What is not defensible is the third shop, where nobody ever decided,
and what happens when the line goes down depends on which member of staff is on that day and what
they guess the manager would want.

## The idea in plain language

Every check in this day has been analysed for what it does when it **works**. This part is about what
happens when the check itself is broken — not fooled, not bypassed, but throwing an exception because
somebody wrote a bug in it.

Two answers are possible and they have names:

- **Fail open** — the guardrail crashed, so the action proceeds unchecked. The system stays available
  and is unprotected for the duration.
- **Fail closed** — the guardrail crashed, so the action is refused. The system is protected and
  partly unavailable.

Neither is right in general. Which one you want depends entirely on what is behind the guardrail, and
that is Principle 13 — blast radius before capability. A check in front of `delete_ticket` should
fail closed, because the cost of a wrong delete is unrecoverable and the cost of a refusal is a delay.
A check in front of a read-only lookup arguably should not.

The thing that is always wrong is the third shop. **Not knowing** which way yours fails is the
failure, and the reason it is so common is that a guardrail's crash path is never exercised: it is not
in the tests, because the tests are about attacks; it is not in the reviews, because the reviews are
about coverage; and it does not appear in production until the day it does.

Part [2.5](../02-where-a-check-stands/2.5-the-empty-dict-that-fails-open.md) is the neighbouring case
and the difference is worth holding. There, the guardrail ran fine and its **refusal** was overwritten
because it was falsy — a bug in what the check returned. Here the check does not return at all.

## Why Sutra needs it

Because the desk's tool list includes actions that change the world, and Day 63 and Day 64 built an
approval gate in front of one of them. A gate is a promise, and a promise made by code that can raise
is only as good as what happens when it does.

There is a Sutra-specific reason to measure rather than assume. This day's whole method has been to
find out what the framework actually does rather than what the documentation implies — part
[2.3](../02-where-a-check-stands/2.3-a-ladder-is-a-list.md) found that the runtime stops at the first
**truthy** result, part [2.4](../02-where-a-check-stands/2.4-the-guardrail-that-never-ran.md) found
that callbacks are called by keyword. The behaviour of an exception inside a callback is the same kind
of fact, it is not something to reason about from first principles, and it is one command away.

And the answer, once measured, produces an uncomfortable finding rather than a comfortable one, which
is why it gets a part.

## The mechanism

The broken guardrail is not contrived. It is a policy lookup with a missing key:

```python
def broken(tool, args, tool_context):
    """A guardrail with an ordinary bug in it: the config key is not there."""
    policy = {"send_reply": "allow"}
    return {"error": "blocked"} if policy[tool.name] == "deny" else None
```

**Line by line:**

- The parameter names `tool`, `args` and `tool_context` are the keyword contract for
  `before_tool_callback` — part
  [2.4](../02-where-a-check-stands/2.4-the-guardrail-that-never-ran.md)'s subject.
- `policy` has one key. The agent has more tools than that, and it is called for `delete_ticket`. That
  is the entire bug, and it is the most ordinary bug there is: a config that has fallen behind the
  thing it configures. Nobody wrote this deliberately; somebody added a tool and did not add its row.
- `policy[tool.name]` raises `KeyError` before the conditional is ever evaluated. The refusal path and
  the allow path are both unreachable — the check does not decide *anything*, which is a state a
  reviewer reading the function will not picture.
- Note what a code review sees: a one-line policy check, correct in shape, with an explicit
  `{"error": "blocked"}` refusal and a `None` allow. It looks like a working guardrail.

Run it against a tool that deletes:

```bash

uv run python failmode.py
```

**Line by line:**

- `cd` first: the lab's scripts import their siblings by plain name.
- No flag installs `broken` directly as `before_tool_callback`, on an agent whose scripted turn calls
  `delete_ticket` on `ticket:4610` and then answers. `d.DELETED` records what was actually deleted, so
  the outcome is checked from outside the run rather than from what the run says about itself.

Measured on 2026-09-06, with the site-packages prefix on each ADK path abbreviated to `...` and eleven
frames of the workflow and flow plumbing elided at the marked point. Nothing else is changed, and the
frames showing the callback being invoked are kept:

The frame to look at is `functions.py`, line 613: `callback_result = before_callback(`. That is the
runtime calling your guardrail, and the exception travels straight back out through it. Nothing in
ADK 2.7.1 catches it.

**So the measured answer is: fail-closed.** `tickets deleted: []` — the delete did not happen, the run
stopped, and the failure is loud and named.

That is the outcome you wanted. It is worth being precise about why it is still a finding.

**You did not choose it.** Your policy said `send_reply` is allowed and everything else is
unspecified. It did not say what happens if the lookup fails, because the person who wrote it did not
picture a lookup that fails. The behaviour came from the framework's decision to re-raise. That is the
right decision and it is **somebody else's** decision, and it can change: a minor version, a different
callback position, a runtime that logs and continues. A security property inherited from a dependency
without a test is a security property you are renting.

Making it yours costs seven lines:

```python
def fail_closed(inner):
    """Wrap a guardrail so that an exception inside it becomes a refusal, not a pass."""

    def wrapped(tool, args, tool_context):
        try:
            return inner(tool, args, tool_context)
        except Exception as error:
            return {"error": f"blocked: guardrail failed ({type(error).__name__}: {error})"}

    return wrapped
```

**Line by line:**

- It is a decorator taking a guardrail and returning a guardrail, so it composes with the callback
  list from part [2.3](../02-where-a-check-stands/2.3-a-ladder-is-a-list.md) without any rung knowing
  about it.
- `wrapped` repeats the three keyword parameter names, because the runtime still calls it by keyword —
  the wrapper is what the framework sees, so it carries the contract.
- `except Exception` is deliberately broad, and this is the one place in this curriculum where that is
  correct rather than the anti-pattern the house style warns about. The purpose is not to handle a
  known failure; it is to guarantee a **verdict** whatever happens inside. A narrow `except KeyError`
  would fail closed on the bug you thought of and fail however-the-framework-feels on the one you did
  not.
- The returned dict is **truthy**, which is what makes the refusal stick — part
  [2.5](../02-where-a-check-stands/2.5-the-empty-dict-that-fails-open.md) is the part about the falsy
  refusal that gets overwritten by the next callback in the list. A fail-closed wrapper returning `{}`
  would be a fail-open wrapper.
- The message carries `type(error).__name__` and the exception text. The refusal is not *"blocked"*; it
  is *"blocked because the guardrail crashed, and here is what it crashed with"*. That distinction is
  the whole operational value: it turns a mysterious outage into a bug report.

```bash
uv run python failmode.py --closed
```

**Line by line:**

- `--closed` wraps the same broken guardrail in `fail_closed` and runs the identical turn, so the only
  variable is the wrapper.

Measured on 2026-09-06:

```text
guardrail wrapped to fail closed

  tool results     [{'name': 'delete_ticket', 'error': "blocked: guardrail failed (KeyError: 'delete_ticket')"}]
  tickets deleted  []
  answer           ['done']
```

Same protection — nothing deleted — and three differences that all matter:

- **The run completed.** The customer got an answer instead of a stack trace, and the desk is still
  serving the rest of the queue.
- **The refusal is in the tool result**, so it is in the event stream, the trace and whatever the run
  is logged into. It is a decision that was recorded, which is part
  [4.3](../04-what-goes-out/4.3-the-rewrite-that-lies.md)'s standard.
- **The reason names the bug.** `KeyError: 'delete_ticket'` is in the refusal. The on-call engineer
  reading this sees a broken guardrail, not an unexplained refusal, and the fix is a config line
  rather than an investigation.

One honest note about the answer: the model said `done`. It received a refusal in the tool result and
told the customer the job was finished, which is its own problem and belongs to the days about how a
model reports tool failures. It is left visible here rather than tidied away, because tidying it away
would be the mistake part [4.4](../04-what-goes-out/4.4-the-error-hook-that-invents-a-result.md) is
about.

## When it breaks

Fail-closed is not free, and the case against it is strong enough to state properly.

**A fail-closed guardrail with a bug is a self-inflicted outage.** The wrapper above turns every
exception into a refusal. Deploy a guardrail whose config is wrong for a commonly-used tool and the
desk stops working for everybody, immediately, in a way that looks like the product being broken
rather than a security control engaging. And guardrails change often — they are the part of the system
that gets edited after every incident, by whoever is most alarmed, under time pressure. That is not a
population of changes you want wired directly to availability.

So the choice is per tool, and Principle 13 gives the rule: **the fail mode follows the blast radius
of what is behind it.**

| Behind the guardrail | Cost of a wrong allow | Cost of a wrong refusal | Fail |
| --- | --- | --- | --- |
| `delete_ticket` | unrecoverable | a delay | closed |
| `send_reply` | data leaves, irreversible | a customer waits | closed |
| `search_archive` | a read, recoverable | the desk cannot answer | open, with an alarm |

The third row is the one people get wrong in both directions. Failing closed on a read-only lookup
converts a guardrail bug into a total outage for no protective benefit; failing open on it without an
alarm means nobody ever finds out the check has been broken for a month.

**Whichever you pick, the exception is not allowed to be silent.** A guardrail that fails open quietly
is the worst configuration available: unprotected, available, and reporting success. If a check fails
open, the exception must be recorded and alerted on, and the honest name for that state is *degraded*
rather than *fine*.

## In production

**Alert on guardrail exceptions as a first-class signal.** Not as part of a general error rate — on
their own, by check name, with a threshold near zero. The rate should normally be zero, which makes it
a wonderful signal: any movement means either a bug shipped or an input arrived that nobody
anticipated, and both are things you want to know within the hour rather than at the next review. This
is also the number that tells you whether your fail-mode choice is being exercised at all, and a
fail-closed policy that has never fired is a policy nobody has tested.

**Deploying a guardrail change is a production risk, and it is usually not treated as one.** Guardrail
edits feel like safety work, so they get the review a config change gets rather than the review a
code change gets. With a fail-closed policy they are directly wired to availability. The mitigations
are the ordinary ones and they are worth insisting on precisely because the change does not feel like
it needs them: roll out behind a flag, watch the exception counter and the refusal rate for the first
traffic, and be able to revert without a deploy.

**What degrades at scale.** Fail modes drift apart. One team wraps their checks, another does not, a
third wraps some. After a year the system's behaviour under guardrail failure is a patchwork nobody
can state, which is the third shop from the story at organisational scale. The fix is structural: one
wrapper, applied centrally where callbacks are registered, with the fail mode declared per tool
alongside the tool's other properties — so that the answer to *"which way does this fail?"* is
readable in one place rather than inferred from six.

**The review comment a senior engineer leaves:** *"This guardrail can raise — the policy dict doesn't
have a row for every tool — and right now we're relying on ADK re-raising to save us. That happens to
be fail-closed today, and it's not written down anywhere as our decision. Wrap it, return a truthy
refusal that carries the exception type and message, and put the fail mode next to the tool
definition so it's per-tool rather than global. And add the test: a guardrail that throws, asserting
the tool did not run. Without that test we're depending on a dependency's behaviour for a security
property."*

**The interview question:** *"Your safety check throws an exception. What happens?"* An honest answer:
*"Whatever your framework happens to do, unless you decided. I measured it on ADK 2.7.1: an exception
in a `before_tool_callback` propagates and the run stops, so it's fail-closed — but by accident, not by
design, because the policy I'd written said nothing about it. Making it mine was a seven-line wrapper
that turns any exception into a refusal carrying the exception type, so the run completes, the refusal
is in the event stream, and on-call sees a broken guardrail instead of a mystery. The important part is
that it's a per-tool decision. Fail closed in front of a delete or a send, where a wrong allow is
irreversible and a wrong refusal is a delay. In front of a read-only lookup I'd fail open and alert,
because otherwise a bug in the check takes the whole product down for no protective benefit. What's
never acceptable is failing open silently — unprotected, available, and reporting success."*
