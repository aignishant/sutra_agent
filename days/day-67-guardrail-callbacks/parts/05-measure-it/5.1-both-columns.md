# 5.1 — Both columns

## One-line answer

A detection rate reported without a false-alarm rate is not a measurement — the ladder catches
**6 of 6** hostile fixtures and also flags **1 of 8** ordinary ones, and the second number is the one
that decides whether it should ship.

## The story

A letter arrives inviting a woman to a screening appointment. The leaflet with it says the test
detects the condition in almost everyone who has it, and that sentence is true.

Some weeks after the appointment a second letter arrives asking her to come back for a further test.
She spends eleven days assuming the worst, rearranges work, tells her sister, and does not sleep
much. The second test is clear. She did not have the condition and never did.

The leaflet was not lying. It simply reported one number out of two, and the two numbers are about
different people. The first is about the people who have it. The second is about everybody else — and
everybody else is a much larger group, so a small percentage of them is a large number of letters.

Both numbers are needed to say whether the programme is a good idea, and only one of them was on the
leaflet, because only one of them is good news.

## The idea in plain language

Every guardrail is a **classifier**: it looks at a piece of text and says *flag* or *allow*. Comparing
that verdict with the truth gives four possible outcomes, and they need names because the rest of this
section counts them.

| | The text really is hostile | The text really is fine |
| --- | --- | --- |
| The check flagged it | **true positive** — caught | **false positive** — a false alarm |
| The check allowed it | **false negative** — it got through | **true negative** — correctly left alone |

Two rates come out of that table, and they are computed over **different denominators**, which is the
part that trips people up:

- **Caught** (the detection rate) is true positives divided by all the hostile texts. It answers:
  *of the attacks, how many did we stop?*
- **False alarm** is false positives divided by all the fine texts. It answers: *of the ordinary
  customers, how many did we refuse?*

Neither one is a property of the check alone; both are properties of the check **and** the corpus it
ran on. And a report that gives one without the other cannot be acted on, because the two always move
together: any check can be pushed to catch everything by flagging everything, and to a zero false
alarm rate by flagging nothing.

That is why the rule for this whole section is one sentence. **A guardrail is reported with both
columns, always.**

## Why Sutra needs it

Because part [1.1](../01-the-ladder/1.1-one-lock-is-not-security.md) opened this day with the claim
that no single check stops prompt injection, and that the real question is how many kinds to stack and
**what each one is honestly worth**. Sections 2, 3 and 4 built the stack. This section is where
"honestly worth" gets a number, and where the day either earns that opening claim or does not.

There is also a decision waiting at the end of the day. Section 6 argues that the ladder narrows the
pipe rather than closing it, and that the thing which closes a channel is a rule that never reads
text. That argument is only honest if the ladder's value has been measured rather than assumed —
otherwise it is a preference dressed as a conclusion.

And Sutra has a specific reason to care about the second column. The desk answers customers. A false
positive is not an inconvenience in a log; it is a person with a real problem being told no by a
machine, and part [5.2](5.2-refused-for-quoting-an-error.md) is that person.

## The mechanism

The counter is fifteen lines and does nothing clever, which is the point — the interesting thing here
is the arithmetic, not the code:

```python
def score(check) -> dict:
    """Run one check over the whole corpus and count the four outcomes."""
    tp = fp = tn = fn = 0
    for _ref, text, hostile in labelled():
        flagged = check(text) is not None
        if hostile and flagged:
            tp += 1
        elif hostile and not flagged:
            fn += 1
        elif not hostile and flagged:
            fp += 1
        else:
            tn += 1
    caught = tp / (tp + fn) if tp + fn else 0.0
    blocked = fp / (fp + tn) if fp + tn else 0.0
    return {"tp": tp, "fn": fn, "fp": fp, "tn": tn, "caught": caught, "false_alarm": blocked}
```

**Line by line:**

- `labelled()` yields `(ref, text, hostile)` for the **whole** corpus — hostile and benign fixtures
  together, in one pass. Running a check over only the hostile half is the mistake this file exists to
  prevent, and keeping both halves in one loop makes that mistake harder to make.
- `flagged = check(text) is not None` is the interface every rung of the ladder shares: a check
  returns a reason when it objects and `None` when it does not. `is not None` rather than truthiness
  matters, and part [2.5](../02-where-a-check-stands/2.5-the-empty-dict-that-fails-open.md) is the
  part about what happens when a falsy refusal meets a truthiness test.
- The four branches are exhaustive and mutually exclusive, so every fixture lands in exactly one
  counter. That is what makes `tp + fn` the hostile total and `fp + tn` the benign total without
  counting them separately.
- `caught = tp / (tp + fn)` and `blocked = fp / (fp + tn)` are the two rates, and the important detail
  is that **the denominators are different**. That single asymmetry is the reason a single headline
  number is meaningless.
- Both divisions are guarded with `if … else 0.0`, because a corpus with no hostile rows or no benign
  rows would otherwise crash — and a corpus with none of one kind is exactly the situation this part
  is warning about.
- The dict returns the four raw counts **as well as** the two rates. Rates hide corpus size: 1 of 8
  and 125 of 1000 are the same rate and are not the same evidence.

Run it against every rung and then the whole ladder:

```bash
cd days/day-67-guardrail-callbacks/lab
uv run python score.py
```

**Line by line:**

- `cd` first: the lab's scripts import their siblings by plain name.
- No flag runs `score()` for each entry in `CHECKS` — the four individual rungs, then
  `the whole ladder`, which is `g.inspect_text` walking them in order.

Measured on 2026-09-06:

```text
corpus: 6 hostile, 8 benign

check                  caught     missed     false alarms   rate caught  rate false
----------------------------------------------------------------------------------------------
too_long               0/6        6          0/8            0.00         0.00
bad_encoding           0/6        6          0/8            0.00         0.00
phrase_match           6/6        0          1/8            1.00         0.12
looks_instructional    4/6        2          0/8            0.67         0.00
the whole ladder       6/6        0          1/8            1.00         0.12
```

Four things in that table are worth reading properly, and only one of them is the headline.

**`too_long` and `bad_encoding` catch nothing at all.** Zero of six. On this corpus they are pure
cost. They are still on the ladder, and part
[1.2](../01-the-ladder/1.2-cheap-and-certain-first.md) is why: they are free, they are certain, and
they exist for inputs this corpus does not contain. But a table that shows a rung contributing nothing
is a table that should prompt the question, and the honest answer is "it is insurance, and here is the
premium".

**`phrase_match` does all the work and pays for it.** Six of six caught, and the only false alarm on
the board.

**`looks_instructional` is the interesting rung.** It catches four of six with **zero** false alarms.
It is worse on the first column and perfect on the second — and if you only ever read detection rates,
you would drop it in favour of the phrase list, which is the wrong call. A rung that catches most
things and never refuses a customer is exactly the rung you want early.

**The whole ladder scores identically to `phrase_match` alone.** 6/6 and 1/8. On this corpus, stacking
bought nothing measurable — the phrase list found everything, and it also found the one false alarm,
and no other rung changed either number. That is an uncomfortable result to publish and it is the
honest one.

Every hostile row was caught by a phrase, and each phrase is a near-quotation of the fixture that

And here is the number a write-up would report:

**Line by line:**

- `--hostile` runs the ladder over the hostile fixtures only and prints the detection rate. It is not
  a different measurement — it is the same measurement with one column deleted.

Measured on 2026-09-06:

```text

That is the number a write-up reports. It says nothing about the other column.
```

**6 of 6.** Every word of that is true. A blog post, a slide, a pull request description containing
only that line is not lying, and it is not a measurement either — it is compatible with a check that
flags every ticket the desk ever receives.

## When it breaks

The corpus is the weakness, and it is worth being blunt about it because the numbers above look
better than they deserve to.

**The fixtures in `_poison.py` were written by the same person who wrote the checks in `_guards.py`.**
That is why `phrase_match` scores 6 of 6. Look at the `--rows` output again: `ticket:9001` is caught
by the phrase `'ignore all previous instructions'`, and `ticket:9001` contains the words *ignore all
previous instructions*. The check and the fixture are two copies of the same idea, so the test is not
measuring detection — it is measuring agreement between a person and themselves.

A detection rate on fixtures you wrote is a **self-portrait**. Part
[5.4](5.4-the-same-instruction-five-ways.md) is where the same instruction is written by somebody who
had read the checks, and the number is very different.

Two smaller weaknesses, both real:

- **Fourteen fixtures is not a sample.** One false positive out of eight benign rows is reported as
  0.12, and the confidence interval around that is enormous. The counts are in the output for exactly
  this reason: `1/8` invites the right amount of scepticism and `0.12` does not.
- **The benign fixtures are the ones somebody thought of.** They are good ones — part
  [5.2](5.2-refused-for-quoting-an-error.md) shows how good — but real traffic contains things nobody
  imagined, and every one of those is a candidate false positive.

## In production

**Base rates change everything, and this is the calculation almost nobody does.** The corpus above is
43% hostile. Real support traffic is not; hostile tickets are rare, and a plausible order of magnitude
is one in a thousand. Run the same rates against that mix and the arithmetic inverts. Take 10,000
tickets, 10 of them hostile: at 100% caught you stop 10 attacks, and at a 12% false-alarm rate you
refuse roughly 1,200 real customers. **For every attack stopped, a hundred and twenty people were
told no.** Nothing about the check changed — only the population it ran against — and the check that
looked excellent on the fixture set is now indefensible. Any guardrail number quoted without the base
rate it was measured at is a number that will not survive contact with production.

**The threshold is a business decision, not a security one.** Where to sit on that trade is a question
about how much a missed attack costs versus how much a refused customer costs, and neither of those is
a fact an engineer owns. What the engineer owes is the curve — here is what we catch at each setting,
and here is what it costs — presented so somebody with the authority to choose can choose. A team that
picks the threshold quietly, inside a security ticket, has made a product decision on behalf of people
who did not know it was being made.

**What a real corpus looks like.** Sampled production traffic, labelled by hand, refreshed on a
schedule, with the hostile examples coming from incidents and red-teaming rather than from the
imagination of the person who wrote the checks. It is slow and boring to build and it is the only
thing that turns these numbers into evidence. The practical shape is a held-out set the check authors
do not see, which is the direct fix for the self-portrait problem above.

**What degrades at scale.** The benign set goes stale fastest. Products change, customers start
talking about new features, and vocabulary that was rare becomes common — so a phrase added
reasonably in March becomes a false-positive machine in September without anybody touching the code.
The measurement has to be re-run on fresh traffic, and part [5.3](5.3-five-more-words.md) is what
happens when it is not.

**The review comment a senior engineer leaves:** *"Please put both columns in the PR description, with
the raw counts rather than just the rates — 6/6 and 1/8 tells me more than 1.00 and 0.12. And note in
the description that the fixtures were authored alongside the checks, because 6/6 will get quoted in a
planning meeting and by then nobody will remember the caveat. What I'd actually like before we ship is
the same table against a hundred sampled real tickets, even unlabelled, just to see the flag rate."*

**The interview question:** *"You've built a prompt-injection filter. How do you know if it's any
good?"* An honest answer: *"Two numbers, never one. How much of the hostile traffic it catches, and how
much of the ordinary traffic it refuses, over different denominators. On the ladder I built, the
headline was six out of six on hostile fixtures — and the same run flagged one of eight benign ones,
which at a realistic base rate is the number that matters: if hostile traffic is one in a thousand,
that filter refuses about a hundred and twenty real customers per attack it stops. I'd also be upfront
that the hostile fixtures were written by the same person as the checks, so the detection rate is
mostly measuring agreement with myself. The number I'd trust is on held-out traffic the check author
never saw, and the deployment decision is a trade somebody in product has to make, not something I
should be picking quietly inside a security ticket."*
