# 2.5 — The empty dict that fails open

## One-line answer

The runtime stops walking a callback list only on a **truthy** result, and overwrites its running
answer with every callback it visits — so a guardrail that refuses by returning an empty dict is
silently overridden by any later callback that returns `None`, and the tool it refused runs.

## The story

An office has a small paper form for approving expense claims. It goes into a tray, the approver
looks at it, and it comes back.

The convention is that the approver writes their reasoning in the box and signs it. Somebody
decided years ago that a refusal is obvious enough — if you are not approving it, just send the form
back with the box empty.

For a long time this works, because one person handles the tray.

Then the team grows and the tray gets a second person, who checks claims for the right cost code
after the first has looked at them. She has nothing to say about most claims, so she passes them on
with the box untouched — which is the same empty box the first person uses to mean *refused*.

A claim comes in that the first approver rejects. She puts it back with an empty box. The second
person picks it up, finds nothing to object to on the cost code, and passes it along untouched. It
reaches the finance system as a claim that went through two approvers and collected no objections.

Nobody did anything wrong by their own rules. The refusal and the shrug were written in the same ink.

## The idea in plain language

The runtime's loop, quoted in full in [2.3](2.3-a-ladder-is-a-list.md), does two things in this
order:

```text
        function_response = callback_result
        if function_response:
          break
```

Assignment first, truthiness test second. So:

- Every callback **overwrites** the running result, including a callback that returns `None`.
- The walk stops only when the result is **truthy**.

Then, after the loop:

```text
    if function_response is None:
      ... call the tool
```

Now put an empty dict through that. Your guardrail returns `{}` meaning *blocked*. The assignment
happens, so `function_response` is `{}`. The truthiness test fails — `{}` is falsy — so the loop does
**not** break. The next callback runs, returns `None` because it has no opinion, and overwrites
`{}` with `None`. The loop ends. `function_response is None` is now true, and the tool is called.

The refusal was erased by an abstention, and nothing anywhere raised.

Two terms worth having straight, because the whole day turns on the difference. A guardrail
**fails closed** when a problem in the guardrail results in the action being refused. It **fails
open** when a problem results in the action being permitted. Fail-open is the dangerous default, and
here it arrives not from an error but from a type choice that looks like nothing.

## Why Sutra needs it

Sutra's guardrail module will return dictionaries, because that is the shape `before_tool_callback`
demands. The natural way to write a refusal is to return the thing the tool would have returned, with
the dangerous bits removed — and for a tool whose successful result is `{"refs": [...]}`, "with the
dangerous bits removed" is very often `{}`.

That is not a contrived mistake. It is the *obvious* implementation of "return an empty result
instead of running the search", and on a desk with a logging callback anywhere behind it, it does the
opposite of what it says.

## The mechanism

`lab/failopen.py` builds the exact two-callback ladder: a blocker that refuses `delete_ticket`, and
an audit callback that records and returns `None`.

```python
def make_blocker(payload: dict):
    """Guardrail one: refuses every delete, by returning `payload`."""

    def blocker(tool, args, tool_context):
        SEEN.append("blocker")
        if tool.name == "delete_ticket":
            return payload
        return None

    return blocker


def audit(tool, args, tool_context):
    """Guardrail two: records the call and says nothing, the way most loggers are written."""
    SEEN.append("audit")
    return None
```

**Line by line:**

- `make_blocker` takes the refusal payload as an argument so the *only* difference between the two
  runs is `{}` against `{"error": ...}`. Everything else — the logic, the ordering, the tool, the
  model — is held constant.
- `blocker` returns `None` for tools it does not care about. That is correct and it is also the
  behaviour that makes the bug possible: a ladder is full of callbacks returning `None` for things
  outside their remit.
- `audit` is deliberately the most ordinary code in this day. It appends and returns `None`. There is
  no mistake in it, which is the point — the bug is not in either callback, it is in their
  combination.
- `SEEN` records execution order, so the output distinguishes *"did not run"* from *"ran and said
  nothing"*.

```bash
cd days/day-67-guardrail-callbacks/lab
uv run python failopen.py
uv run python failopen.py --truthy
```

**Line by line:**

- The default run uses `{}` as the refusal. `--truthy` uses `{"error": "blocked: ..."}`.
- The scripted model asks for `delete_ticket`, so the observable outcome is whether
  `days/day-67-guardrail-callbacks/lab`'s in-memory `DELETED` list gains an entry.

Measured on 2026-09-06:

```text
  blocker returns {}, then audit
    guardrails that ran   ['blocker', 'audit']
    tool result           {'name': 'delete_ticket', 'deleted': 'ticket:4610'}
    tickets deleted       ['ticket:4610']
    verdict               FAIL-OPEN - the tool ran
```

```text
  blocker returns {'error': ...}, then audit
    guardrails that ran   ['blocker']
    tool result           {'name': 'delete_ticket', 'error': 'blocked: delete_ticket is not reachable from a ticket body'}
    tickets deleted       []
    verdict               blocked
```

**The ticket was deleted.** A guardrail explicitly written to refuse `delete_ticket` ran, refused,
and the ticket was deleted anyway. No exception, no warning, no log line saying anything went wrong —
the run looks like a completely ordinary successful turn.

Now compare the `guardrails that ran` rows, because they carry a second finding. In the working case
the list is `['blocker']` — the audit callback **did not run**, because the truthy refusal broke the
loop. That is [2.3](2.3-a-ladder-is-a-list.md)'s problem, and here it sits right beside this one.

So the two orderings trade against each other in a genuinely awkward way:

| refusal value | audit position | tool blocked? | audit ran? |
| --- | --- | --- | --- |
| `{}` | after | **no** | yes |
| `{"error": ...}` | after | yes | **no** |
| `{}` | before | yes | yes |
| `{"error": ...}` | before | yes | yes |

Only the bottom two rows are correct, and both of them put the logger first. The rule that falls out
of the table is short: **a refusal must be truthy, and anything that must always run goes in front of
anything that can block.**

## When it breaks

It breaks silently, which is the whole problem, and the silence is worth dwelling on because it
defeats the obvious test.

A unit test of the blocker passes. Call `blocker(tool, args, ctx)` directly, assert it returns `{}`
for `delete_ticket`, and it does. The function is correct in isolation. The bug exists only in the
composition, and only when a second callback is present — so a test suite that tests each guardrail
alone reports full coverage over a system that fails open.

The test that catches it has to assert the **effect**, not the return value:

```python
def test_delete_is_blocked_end_to_end():
    agent = desk([call("delete_ticket", ref="ticket:4610")], before_tool_callback=[blocker, audit])
    run(agent)
    assert DELETED == []
```

**Line by line:**

- It builds the agent with the **real ladder**, both callbacks, in the order production uses. A test
  with one callback cannot see this class of bug.
- It asserts on `DELETED` — the side effect the tool would have had — rather than on what the
  callback returned. The callback returned the right thing; that was never in question.
- There is no assertion about the message or the shape, deliberately. This test is about whether the
  thing happened, and keeping it narrow means it stays true when the refusal text changes.

There is also a static way to catch it, and it is the reason the day's gate script contains a check
that looks strange out of context:

```text
  FAIL  a refusal is truthy
  - a refusal is truthy - a falsy block is overwritten by the next callback; see part 2.5
```

That gate check asserts `bool(sutra.guardrails.REFUSAL)` is true. It is checking that the constant
the module refuses with is not something falsy, which is a one-line guard against re-introducing this
bug the next time somebody tidies the refusal payload.

## In production

**What a professional writes instead.** They never let each guardrail invent its own refusal value.
The module exports one constant — `REFUSAL = {"error": "blocked", ...}` — and every guardrail returns
either that or `None`. Two properties follow for free: the refusal is truthy by construction, and the
refusal is greppable, so "how often did we block anything" is a question the logs can answer without
pattern-matching on prose.

**What degrades at scale.** The probability of this bug scales with the number of callbacks on a
hook, and callbacks accumulate. A single-guardrail system cannot exhibit it at all — with one
callback, `{}` blocks correctly, because there is nothing behind it to overwrite the result. So the
bug is *introduced by adding a second guardrail*, which is a change that reviews as strictly
increasing safety. The system got less safe by getting more checks, and the diff that did it touched
neither the blocker nor the tool.

**The failure that only shows with real traffic.** It shows the first time a blocked action is one
you would have noticed — which, on a desk whose dangerous tool is `delete_ticket`, means it shows as
missing data with no explanation. There is no error in the logs to correlate against, because there
was no error. The investigation starts from "rows are disappearing" and has no reason to look at the
guardrail, which is, after all, the component that is supposed to be preventing exactly that.

**The review comment a senior engineer leaves:** *"This returns `{}` to mean blocked. ADK's callback
loop breaks on a truthy result and overwrites on every iteration, so an empty dict does not stop the
walk and the next callback's `None` puts us back to calling the tool. Return `REFUSAL`. And add an
end-to-end test with both callbacks wired — the unit test on this function passes and will keep
passing while the system fails open."*

**The interview question:** *"What does your guardrail return when it blocks something?"* The answer
that shows you have been bitten: *"A truthy value, always, and I would say why. ADK walks the
callback list and only short-circuits on a truthy result, assigning as it goes — so returning an
empty dict to mean 'blocked' gets silently replaced by the next callback's `None` and the tool runs.
It is a fail-open that appears when you add a second guardrail, so it arrives in a change that looks
like an improvement, and the unit test on the guardrail still passes because the function is fine. We
export one refusal constant and test the effect end to end."*
