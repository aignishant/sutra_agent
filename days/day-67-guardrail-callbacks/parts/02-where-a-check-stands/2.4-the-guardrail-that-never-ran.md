# 2.4 — The guardrail that never ran

## One-line answer

ADK calls callbacks **by keyword**, so the names of your parameters are part of the contract — a
guardrail written as `def guard(ctx, req)` raises `TypeError` on the first request instead of
guarding anything, and neither your editor nor a type checker will warn you, because the type alias
is written positionally.

## The story

A friend moves into a first-floor flat and gives you the address for a delivery you are sending.

The parcel arrives at the building. The driver looks at the panel by the door, finds the button
labelled with her flat number, and presses it. Nothing happens. He presses it again, waits, and
leaves a card saying nobody was home.

She was home the whole time, sitting fifteen feet away.

The electrician who wired the panel two years ago connected the button to the wrong flat. Everything
looks right: the label is right, the button works, the wire is sound, and somewhere on the second
floor a bell rings in an empty flat. There is nothing to notice from the outside, and the only
symptom is that a thing which is supposed to happen does not.

## The idea in plain language

The type annotation on `before_model_callback` reads, in effect,
`Callable[[Context, LlmRequest], ...]` — two positional parameters. Any Python programmer reading
that writes:

```python
def guard(ctx, req):
    ...
```

and it is wrong. Not stylistically — it does not work at all.

The runtime calls the function by **keyword**, with names fixed by the framework:
`callback_context` and `llm_request` for the model hooks, `tool`, `args` and `tool_context` for the
tool hooks. Your parameters must be spelled exactly that way.

To be fair to the framework, this is documented. adk.dev's callbacks page carries the note directly:
*"In Python, callback function parameter names must match the documented names exactly because ADK
passes callback arguments by keyword."* So this is not a hidden behaviour — it is a documented one
that the **type annotation contradicts**.

That combination is what makes it a trap rather than merely a rule. The annotation says positional.
The prose says keyword. A reader who works from the signature, from autocomplete, or from a type
checker gets the annotation, and none of those tools will flag the mistake, because as far as the
type system is concerned a two-parameter callable is a two-parameter callable.

The framework's own source is candid about it. The line that makes the call carries this comment:

```text
    # The callback type aliases are declared positionally, but the framework
    # has always invoked them by keyword.
    agent_response = callback(  # type: ignore[call-arg]
        callback_context=callback_context, llm_request=llm_request
    )
```

The `# type: ignore[call-arg]` is the framework suppressing a type error *on its own call*, because
the alias and the invocation disagree. That suppression is the doorbell wired to the wrong flat: it
is the point where the mismatch was known and papered over, and it is the reason your type checker
stays quiet.

## Why Sutra needs it

Every guardrail this day writes is a callback, so this failure mode applies to all of them at once.

Worse, it applies at the moment of *deployment* rather than the moment of *attack*. A guardrail with
mis-spelled parameters does not fail quietly and let things through — it raises, and it raises on
every request, including the ordinary ones. So you find out immediately, which is genuinely the
lucky version of this bug.

The unlucky version is a guardrail wired on a **rarely-used** hook: `on_tool_error_callback`, say,
which only fires when a tool actually raises. Mis-spell those parameters and everything works
perfectly for six weeks, until the archive goes down and the error handler you wrote to make that
graceful is itself the thing that breaks.

## The mechanism

`lab/names.py` wires the same guardrail twice, once with each spelling.

```python
def guard_right(callback_context, llm_request):
    """Parameters named as the runtime calls them."""
    return LlmResponse(content=d.say(BLOCKED))


def guard_wrong(ctx, req):
    """The same guardrail, with the parameter names a reader would naturally choose."""
    return LlmResponse(content=d.say(BLOCKED))
```

**Line by line:**

- The two function bodies are **character-for-character identical**. Nothing about the logic differs;
  only the parameter names do.
- `guard_wrong`'s names are not careless — `ctx` and `req` are what a competent Python programmer
  writes when handed a positional annotation, and shorter names are normally better style.
- Both are wired to `before_model_callback` on a desk whose scripted model asks to delete a ticket,
  so a working guardrail is observable as `deleted=[]`.

```bash
cd days/day-67-guardrail-callbacks/lab
uv run python names.py
uv run python names.py --tool
```

**Line by line:**

- The default run tests `before_model_callback`; `--tool` tests `before_tool_callback`, because the
  two hooks have different keyword names and a reader needs to see that the rule is per-hook rather
  than one global convention.
- Each attempt is wrapped in `try: ... except TypeError`, so the script reports both outcomes in one
  table instead of dying on the first.

Measured on 2026-09-06:

```text

  (callback_context, llm_request) ran. texts=['Refused: this ticket carries an injected instruction.'] deleted=[]
  (ctx, llm_request)       TypeError: guard_wrong() got an unexpected keyword argument 'callback_context'
```

```text

  (tool, args, tool_context) ran. texts=['done'] deleted=[]
  (tool, args, ctx)        TypeError: tool_guard_wrong() got an unexpected keyword argument 'tool_context'
```

Note the second table carefully. `tool` and `args` are spelled correctly, and only the **third**
parameter is wrong. It still fails completely. There is no partial credit: one wrong name out of
three and the guardrail does not exist.

The final frame shows the `# type: ignore[call-arg]` comment in the source line itself. That is the
whole bug in one screen: the framework suppressed the type error on its call, so the mismatch could
not be caught statically, and it surfaces at run time as a `TypeError` naming a keyword the reader
never wrote.

## When it breaks

It breaks on the first request through the hook, and the message is unusually good — it names your
function and the exact keyword it could not deliver. The smallest fix is to rename the parameter.

The version that is genuinely dangerous is the one that does **not** break on the first request,
because the hook is rarely reached. Consider a desk with a correct `before_tool_callback` and a
mis-spelled `on_tool_error_callback`. Everything is fine until a tool raises — and at that moment the
runtime tries to call your error handler, fails with a `TypeError`, and the original exception is now
travelling alongside a second one raised by the code you wrote to handle it.

The rule that follows is worth stating on its own: **a callback that has never executed is not
installed, it is merely declared.** A test that asserts the callback *runs* — not that it returns the
right verdict, just that it runs at all — catches this in every case including the rare hooks, and it
is one line. That is why the day's gate script checks the parameter names by signature rather than
checking behaviour:

```python
    check(
        "the guard's parameters are named (tool, args, tool_context)",
        module is not None
        and hasattr(module, "block_disallowed_send")
        and list(__import__("inspect").signature(module.block_disallowed_send).parameters)
        == ["tool", "args", "tool_context"],
        "the runtime calls callbacks by keyword; see part 2.4",
    )
```

**Line by line:**

- `inspect.signature(...).parameters` gives the parameter names in order, which is exactly the thing
  the runtime cares about and exactly the thing no type checker will verify.
- Comparing to a literal list rather than a set checks order too. Order does not matter for keyword
  calls, but a guard whose parameters are in a surprising order is a guard somebody will later
  "fix" into a positional call.
- The failure message names the part rather than restating the rule, because the person who trips
  this needs the explanation, not the assertion.

## In production

**What a professional writes instead.** They do not hand-write the signature at each call site. They
keep one decorator or one base class per hook type in the codebase, so the names are written once and
inherited everywhere:

the guardrail author writes the logic, and the wrapper owns the parameter names. The second thing
they do is assert *installation* in a test — build the agent, run one request through it with a
recorded model, and assert the callback's side effect happened. That test costs nothing and it is the
only thing that catches a mis-wired rare hook.

**What degrades at scale.** Nothing about this degrades; it is binary. But it *spreads*: the
mis-spelling is usually copied. One engineer writes `def guard(ctx, req)`, hits the `TypeError`,
fixes their own by renaming, and the broken version survives in the internal wiki snippet everyone
else pastes from. Bugs that are fixed locally and copied globally are the reason the wrapper matters
more than the knowledge.

**The failure that only shows with real traffic.** The rare-hook case above. `on_model_error_callback`
fires when the provider errors, which on a free tier means it fires on a 429 — that is, it fires
under exactly the load conditions where you least want a second exception. Day 70's quota router is
built on paths that must survive a 429, and a mis-spelled error callback turns a handled rate limit
into an unhandled crash.

**The review comment a senior engineer leaves:** *"These parameters have to be named
`callback_context` and `llm_request` — ADK calls them by keyword and the annotation lying about it
is a known wart. Use the wrapper in `sutra/guardrails.py` rather than writing the signature by hand,
and add a test that asserts this callback actually executed, because a `TypeError` here is silent
until the hook is reached."*

**The interview question:** *"How would you test that a guardrail is wired up correctly?"* The answer
that shows scar tissue does not talk about verdicts: *"Separately from testing what it decides, I
test that it runs at all. In ADK the callbacks are invoked by keyword while the type alias is
positional, so a guardrail with sensibly-named parameters raises `TypeError` instead of guarding, and
no type checker catches it — the framework has a `type: ignore` on its own call site. On the common
hooks you find that in a minute. On `on_tool_error_callback` you find it during an outage, which is
why the test asserts execution rather than behaviour."*
