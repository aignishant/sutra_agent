# 4.2 — 💥 Thirteen taught, three shipped

## One-line answer

The plan names sixteen security controls; six of them have their vocabulary somewhere in `sutra/`,
three survive when comments and docstrings are stripped, and two of the three the ledger reports as
**closed** are not in the product at all.

## The story

💥 **The fire-exit door that is chained shut.**

🎬 **The scene.** A building with a green running-man sign over a door at the end of a corridor,
lit, correct, exactly where the drawings say it should be. There is an evacuation plan on the wall
and the door is on it.

😬 **The naive fix.** Somebody was propping it open to smoke, and the alarm kept going off, so a
chain and a padlock went on it. Sensible response to a real problem, taken by somebody solving the
problem in front of them.

💥 **Why it fails.** The sign is still lit. The plan on the wall still shows the route. The annual
inspection ticks "fire exit present". Everything that records the control still records it, and the
one thing that would reveal the state — pushing the bar — is the thing nobody does except on the day
it matters.

💡 **The insight.** **A control's documentation and a control's existence are two different objects,
and every routine check reads the first one.** The sign is not lying. It is describing a door.

## The idea in plain language

This repository's plan defines sixteen security controls, SEC-01 to SEC-16. Days were written for
them, labs were run, checks went red and then green. That work is real and it is on disk.

The question this check asks is different: **is the control in `sutra/`?** That is the package the
learner builds and the thing that would run in front of a user. Everything else — the day documents,
the labs, the fixtures — is teaching material.

Three answers, and keeping them apart is the whole part:

| Claim | Means | Here |
| --- | --- | --- |
| **taught** | the day is written and its ledger row exists | 3 of 16 |
| **mentioned** | the vocabulary appears anywhere under `sutra/` | 6 of 16 |
| **implemented** | it appears with comments and docstrings stripped | **3 of 16** |

And the gap between *mentioned* and *implemented* is three controls whose only presence in the
product is a word in a comment.

That gap is not an accident of this repository. It is the normal outcome of a codebase with good
comments: the vocabulary of the thing you meant to build is in the file, next to the code that does
something else, and any check that greps for the vocabulary finds it.

## Why Sutra needs it

Because the review before publication is exactly where somebody would say *"we covered security, it
is Phase 10"* — and that sentence is true about the curriculum and false about the code.

And because two of the three controls the traceability ledger marks **closed** are not implemented:
SEC-01, sandboxing at first code execution, and SEC-03, MCP allowlists and filtering. Those closures
are correct on their own terms — the days are written and logged — and a reader who takes "closed" to
mean "in the product" has been misled by a ledger that never claimed that.

## The mechanism

The first version of this check was wrong in the reassuring direction, which is the honest way into
the mechanism. It searched the package as text:

```python
def product_text() -> str:
    """Every line of the product package, lowercased - comments and prose included."""
    parts = []
    for path in sorted(PRODUCT.rglob("*.py")):
        try:
            parts.append(path.read_text(encoding="utf-8").lower())
        except OSError:
            continue
    return "\n".join(parts)
```

**Line by line:**

- Reads every file as one lowercased haystack. Simple, fast, and it reports **six of sixteen**.
- `except OSError: continue` so an unreadable file skips rather than aborting the audit — but note it
  also skips *silently*, which is its own small version of the day's theme.

Three of those six were prose. `scope` appears in a prompt string and a comment; `capability` appears
in two explanatory comments. Neither is a control.

The fix is to search the code with the prose removed:

```python
def product_code() -> str:
    parts: list[str] = []
    for path in sorted(PRODUCT.rglob("*.py")):
        try:
            source = path.read_text(encoding="utf-8")
            for token in tokenize.generate_tokens(io.StringIO(source).readline):
                if token.type not in (tokenize.COMMENT, tokenize.STRING):
                    parts.append(token.string.lower())
        except (OSError, tokenize.TokenError, IndentationError, SyntaxError):
            continue
    return " ".join(parts)
```

**Line by line:**

- `tokenize.generate_tokens` gives Python's own lexical split, so "is this a comment" is answered by
  the language rather than by a regex that would trip on a `#` inside a string.
- Dropping `COMMENT` **and** `STRING` removes docstrings too, because a docstring is a string
  expression. That is the intent: a control described in a docstring is documentation.
- The exception tuple is wide on purpose. A file that does not tokenise is not evidence of a control,
  and an audit that crashes on one malformed file has audited the files before it.
- `" ".join` rather than newlines, because tokens are already separated and the haystack is only ever
  substring-searched.

actual bound on an actual loop. `SEC-15` is the 429 handling in `mechanics.py`.

## When it breaks

The composite is the one this whole day exists to catch:

```text
1. a security curriculum is written and every day passes its own checks
2. the ledger records each day as closed
3. a review asks "are the controls in place?"
4. somebody greps the codebase for the control vocabulary and finds it
5. the review passes
6. the controls that ran were in the labs, and the product has three
```

Step four is the failure and it is indistinguishable from diligence. There is no error text: the grep
succeeds, the words are there, and the words are in comments explaining what the code will do when
somebody writes it.

**What this check still cannot tell you**, and the limit is real:

- **A word is not an implementation.** `max_steps` appearing in code proves a parameter exists, not
  that it is enforced, not that the bound is right, and not that anything calls it. The check
  distinguishes *absent* from *present*, which is a coarse and useful first cut and nothing more.
- **A control can be implemented under a different name.** The signature list is generous — three or
  four synonyms each — and a codebase that spells its guardrail something else reports absent. False
  absences are the safe direction for a security check, and they are still wrong.
- **This audits `sutra/` only.** `sutra_mcp/` exists, `skills/` exists, and neither is in the
  haystack. A control implemented in the MCP server reports absent here.

## In production

**What a professional does.** Ties each control to a **test**, not to a symbol. "SEC-05 is
implemented" is unfalsifiable; "`test_refund_requires_approval` passes" is a claim with a failure
mode, and the traceability matrix maps control identifiers to test identifiers rather than to
documents. Then a control that stops working goes red in the same run as the change that broke it.

**What degrades at scale.** Controls drift out of code faster than they drift out of documents,
because code gets refactored and documents do not. A control implemented once and then moved behind a
framework upgrade, a middleware change or a service boundary can vanish without any document
noticing, and the compliance artefact still says it is there.

**The failure that only shows with real traffic.** The control is present and disabled. A guardrail
behind a feature flag that defaults off, a rate limiter with its threshold set beyond any real load,
an approval gate whose approver list is empty — all three are implemented, all three would pass a
symbol search, and none of them does anything. Day 67 part 2.4 measured exactly this shape: a
guardrail that never ran.

**The review comment a senior engineer leaves:** *"Three of sixteen is fine for where this project
is — most of these are build briefs and everybody knows it. What is not fine is that the ledger says
SEC-01 and SEC-03 are closed. Either the ledger means 'taught' and says so, or it means 'shipped' and
those two rows are wrong."*

**The interview question:** *"Your compliance matrix says every control is implemented. How would you
check?"* The answer that shows experience does not grep for the control names. It asks for the test
that fails when the control is removed — and if there is no such test, treats the row as
undemonstrated regardless of what the code contains.
