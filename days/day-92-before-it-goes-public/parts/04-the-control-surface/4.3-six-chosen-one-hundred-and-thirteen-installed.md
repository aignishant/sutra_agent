# 4.3 — Six chosen, one hundred and thirteen installed

## One-line answer

`pyproject.toml` names six dependencies and the environment contains one hundred and thirteen
distributions — a factor of nineteen — and every one of the other hundred and seven imports at
exactly the same privilege as the code that chose it, with no row in `docs/PACKAGES.md` recording a
decision about any of them.

## The story

The guest list where everybody brings family.

Six invitations go out, one per household, because six is who you actually want there. Each one is
written by hand and each household was thought about.

On the day, a hundred and thirteen people arrive. Nobody gate-crashed. Every single person came with
somebody who was legitimately invited — a spouse, two children, a visiting cousin, the cousin's
friend who was staying that week. Every link in every chain is reasonable, and nobody at any point
made a decision to have a hundred and thirteen people in the house.

You did not invite them and you are feeding them.

## The idea in plain language

A dependency is not a library you use. It is **code that runs with your privileges**, in your
process, with your environment variables, your filesystem handle and your network access. That is
true of the ones you chose and equally true of the ones that arrived with them.

Principle 13 is *blast radius before capability*, and this repository has applied it carefully to
tools — Day 40's allowlists, Day 68's least privilege, and part
[4.1](4.1-the-keys-you-hand-over.md)'s inventory. It has never applied it to packages.

The numbers:

| | Count |
| --- | --- |
| named in `pyproject.toml` | 6 |
| installed in the environment | 113 |
| arrived as somebody else's dependency | 107 |
| with a dated row in `docs/PACKAGES.md` | 6 |

`docs/PACKAGES.md` is a genuinely good ledger. It has a dated row for every direct pin, with the
version observed live, the lookup URL, and a note on what the package is for. It records six
decisions. The environment contains a hundred and thirteen packages.

That is not a criticism of the ledger — a ledger of a hundred and thirteen transitive packages would
be unmaintainable and nobody writes one. It is a statement of where the boundary of deliberate choice
actually sits, which is the sort of thing a review is for.

## Why Sutra needs it

Because the environment is the largest untracked surface in the repository, and Day 93 publishes a
`uv.lock` that pins every one of the hundred and thirteen. A reader who clones this repository and
runs `uv sync` executes all of it.

And because this is the surface where the industry's real incidents happen. The failures that make
the news are rarely a clever attack on application code; they are a package nobody had heard of,
three levels down a dependency tree, that changed hands or shipped a compromised release.

## The mechanism

Both sets come from the same two authorities, so the comparison cannot drift:

```python
def direct() -> list[str]:
    """The dependencies this repository asked for, by name."""
    spec = tomllib.loads((ROOT / "pyproject.toml").read_text(encoding="utf-8"))
    out = []
    for entry in spec["project"]["dependencies"]:
        name = entry.split("==")[0].split(">=")[0].split("[")[0].strip()
        out.append(name.lower())
    return sorted(out)
```

**Line by line:**

- `tomllib` from the standard library since 3.11, so reading the manifest adds no dependency to a
  check about dependencies — which would be a funny way to fail.
- The chain of `split` calls strips a pin, a floor and an extras marker in turn, so
  `google-adk[eval]>=2.7` and `google-adk==2.7.1` both reduce to `google-adk`.
- `.lower()` because distribution names are case-insensitive and normalised differently by different
  tools. Comparing `PyYAML` against `pyyaml` as raw strings produces a phantom finding.

```python
def installed() -> dict[str, str]:
    """Every distribution present in the environment, name -> version."""
    found: dict[str, str] = {}
    for dist in metadata.distributions():
        name = dist.metadata["Name"]
        if name:
            found[name.lower()] = dist.version
    return found
```

**Line by line:**

- `importlib.metadata.distributions()` reads what is actually installed, not what the lockfile says
  should be. Those differ whenever somebody has run a bare `pip install` in the environment, and the
  difference is exactly the thing worth knowing.
- `if name` guards a distribution with broken metadata, which does occur and which would otherwise
  put a `None` key in the dictionary and produce a confusing count.
- Returning versions as well as names means the same function can answer "which version" later
  without a second walk.

## When it breaks

The failure is not that a transitive package is malicious. It is that nothing distinguishes the case
where one is:

```text
1. six dependencies are chosen carefully and pinned with dated rows
2. each pulls its own dependencies, which pull theirs
3. the lockfile pins all one hundred and thirteen, correctly and reproducibly
4. a maintainer three levels down transfers ownership of a package
5. a new release ships with an install-time script
6. somebody runs uv sync
```

Steps one to three are this repository doing everything right. There is no error text at step six,
because installing a package is not an error — and a lockfile is protection against *drift*, not
against a pinned version being bad.

**Two things this check deliberately does not do**, and both matter:

- **It does not scan for known vulnerabilities.** That needs a vulnerability database and a tool this
  environment does not have — `pip-audit` is absent, and adding it would itself add dependencies.
  Naming the gap is the honest answer; a `TODO(me)` with the exact command is in the build brief.
- **It does not judge.** A package with a hundred and thirteen entries is not worse than one with
  ten. The finding is that the ratio is nineteen and nobody knew it, not that nineteen is too many.

The count also moves under you. Adding `a2a-sdk` for Day 89 brought six more distributions with it,
so the number in this transcript is a measurement of one environment on one date — which is why the
report prints it rather than hard-coding it, and why `docs/PACKAGES.md` rows carry dates.

## In production

**What a professional does.** Treats the lockfile as the security artefact and reviews changes to it
with the same seriousness as changes to code. A pull request that adds one line to `pyproject.toml`
and four hundred to `uv.lock` is a pull request that added four hundred things, and the review that
looks only at the first file has looked at the wrong one.

**What degrades at scale.** The ratio grows with every direct dependency, and the graph gets deeper
rather than wider — so the packages you have never heard of are increasingly the ones with the most
transitive dependents, which is the opposite of the intuition that obscure means peripheral.

**The failure that only shows with real traffic.** Install-time execution. A package can run code
during installation, which happens in the build environment before any test runs and often with more
privilege than the application ever has. Nothing in this repository's pipeline inspects that, and a
lockfile pins *what* is installed rather than *what it does while installing*.

**The review comment a senior engineer leaves:** *"Add `uv pip list --outdated` and a vulnerability
scan to the nightly, not the commit gate — it needs network and it will be flaky. And when a pull
request changes `uv.lock`, put the count of added distributions in the description. One line in the
manifest is not one decision."*

**The interview question:** *"How many dependencies does your service have?"* The answer that shows
experience gives two numbers — direct and total — and then says which of the two the team reviews,
because everyone knows the first and the second is what runs.
