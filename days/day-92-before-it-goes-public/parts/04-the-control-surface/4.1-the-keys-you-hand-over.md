# 4.1 — The keys you hand over

## One-line answer

The desk declares two tools, both read an in-memory dictionary, neither can change anything, and no
approval step exists anywhere in `sutra/` — which is a pass, and a pass that expires the moment
somebody adds a third tool.

## The story

The keys handed to the new watchman.

He starts on Monday and gets a ring with six keys on it. Somebody goes through them with him: main
gate, side gate, the meter room, the terrace, the pump room, and one nobody can identify that has
been on the ring since before anyone currently working here started.

The six are not the interesting part. The interesting part is the sentence that comes with each one
— *"this is for the terrace, and the terrace stays locked after nine"* — and the fact that for the
sixth there is no sentence, so it stays on the ring, opening something, indefinitely.

## The idea in plain language

An agent's capability is the set of tools it can call. Everything else — the model, the prompt, the
guardrails — decides *whether* it calls them; the tool list decides what calling them can do.

So a security review has to enumerate that set from the **code**, not from a document. A tool the
model is told about is a capability whether or not any design note mentions it, and a tool that was
removed from the docs and left in the dispatch table is still a key on the ring.

The check reads two places and joins them:

- **`sutra/tools.py`** — the declarations, which is what the model is told exists. Day 4 built these.
- **`sutra/loop.py`** — the dispatch table and the function bodies, which is what actually runs.

Then for each tool it asks the only question that matters for blast radius: **does the body reach
outside its own process?** A function that reads a dictionary in memory cannot damage anything. A
function that calls `open`, `urlopen` or `subprocess.run` can, and the difference is visible in the
syntax tree without running a line.

And the answer for this desk is that neither tool reaches anything. `lookup_ticket` reads `TICKETS`;
`search_kb` reads `KB`. Both are module-level dictionaries written out by hand in Day 3.

Which makes the second half of the finding the interesting one: **there is no approval step in
`sutra/` at all**, and that is currently *correct*. SEC-05 gates writes; there are no writes. The
control is absent because the capability is absent.

That is a pass with a date on it. The day a `refund` tool arrives, the capability arrives with it and
the control does not.

## Why Sutra needs it

Because this is the one place where an absent control is the right answer, and telling it apart from
the twelve absent controls in part [4.2](4.2-thirteen-taught-three-shipped.md) is exactly the
judgement a review exists to make. A checklist cannot: both look like *"approval gate: not present"*.

And because the repository is about to be public with a build brief that says *add the write tools*.
The next contributor to follow that brief will add a capability into a codebase whose review said
"no ungated writes", truthfully, about a state that no longer holds.

## The mechanism

Declarations come from the syntax tree, not from importing the module:

```python
def declarations() -> list[str]:
    """Tool names as declared to the provider, read from sutra/tools.py."""
    tree = ast.parse((PRODUCT / "tools.py").read_text(encoding="utf-8"))
    names: list[str] = []
    for node in ast.walk(tree):
        if not isinstance(node, ast.Dict):
            continue
        for key, value in zip(node.keys, node.values, strict=False):
            if isinstance(key, ast.Constant) and key.value == "name":
                if isinstance(value, ast.Constant):
                    names.append(value.value)
    return sorted(set(names))
```

**Line by line:**

- `ast.parse` rather than `import`. A security check that imports the code it is auditing runs that
  code, and a module with a side effect at import time has just been executed by the review. Parsing
  reads without running.
- It walks for any `ast.Dict` with a `"name"` key rather than looking up the module-level constants by
  name, so a declaration added as a third dictionary is found without the check being updated.
- `strict=False` on the `zip`: a dict display always has equal keys and values, and `strict=True`
  would raise on the `**spread` form where `keys` carries a `None`. This is the one place the loose
  option is correct.
- `sorted(set(...))` so the report is stable between runs and a duplicate declaration collapses
  instead of appearing twice.

Reach is a walk over each function body:

```python
def reaches(func: ast.FunctionDef) -> set[str]:
    """Everything outside its own process that this function body touches."""
    out: set[str] = set()
    for node in ast.walk(func):
        if isinstance(node, ast.Call):
            target = node.func
            name = ""
            if isinstance(target, ast.Name):
                name = target.id
            elif isinstance(target, ast.Attribute):
                name = target.attr
            if name in REACH:
                out.add(REACH[name])
    return out
```

**Line by line:**

- Two node shapes because a call is written two ways: `open(...)` is an `ast.Name` and
  `path.write_text(...)` is an `ast.Attribute`. Handling only the first misses every method call,
  which is most of the dangerous ones.
- `REACH` maps a name to *what it reaches* — "the filesystem", "the network", "a subprocess" — rather
  than to a boolean, so the report tells a reviewer which blast radius rather than that there is one.
- This is deliberately shallow: it looks at the tool's own body and not at what its callees do. A
  tool that calls a helper which opens a file reports clean. Named in **When it breaks**, because
  pretending otherwise would be the more dangerous error.

**Line by line:**

- No flag. `--declared` counts declarations only and is part

Measured on 2026-09-07:

```text
tools declared to the model: 2
  lookup_ticket
  search_kb

  tool              implemented  reaches               can change things
  lookup_ticket     yes          in-memory data only   no
  search_kb         yes          in-memory data only   no
```

Two tools, both read-only, zero gates needed. The last two lines are the part to carry: this is a
**conditional** pass, and the condition is printed next to it.

## When it breaks

The check is proved able to fail by adding a tool that writes:

```bash
uv run python surface.py --with-write | tail -7; echo "exit: ${PIPESTATUS[0]}"
```

Measured on 2026-09-07:

```text
  tool              implemented  reaches               can change things
  issue_refund      yes          the filesystem        yes
  lookup_ticket     yes          in-memory data only   no
  search_kb         yes          in-memory data only   no

  tools that reach outside the process: 1
  an approval step exists in sutra/:     no

  1 tool(s) can change something and nothing gates them
exit: 1
```

The synthetic tool is defined inside the check and is never declared to a model — it exists so this
criterion can be shown to go red, which part
[1.1](../01-what-a-review-is/1.1-a-check-that-can-fail.md) argued is the difference between a pass
and a silence.

**Three things this check genuinely cannot see**, and a review that does not name them is
overclaiming:

- **Indirect reach.** A tool whose body calls a helper that opens a file reports `in-memory data
  only`. Following calls across modules is a different and much larger program, and every static
  analyser that does it has a false-positive rate to match.
- **Tools that are not in this repository.** An MCP server's tools arrive at runtime from
  `sutra_mcp/` or from somebody else's process entirely. Day 40's allowlist is the control for that
  and it is not in `sutra/` either.
- **What the data can do.** `lookup_ticket` returns ticket text into the model's context. That text
  is untrusted input and is the whole subject of Days 66 and 67 — a read-only tool is not a safe
  tool, it is a tool whose damage arrives as *content* rather than as an action.

The third is the one that matters most here, and it means the pass in this part is narrower than it
sounds: **nothing this desk does can change the world, and something it reads can change what it
says.**

## In production

**What a professional does.** Keeps the tool inventory as a generated artefact rather than a
document: name, what it reads, what it writes, what approval it needs, reviewed by a person when the
list changes. The generated form is what makes the review repeatable; the human sentence attached to
each entry is what stops a key staying on the ring with nobody able to say what it opens.

**What degrades at scale.** Tools arrive from more places. A handful of hand-written functions becomes
an OpenAPI toolset (Day 15), an MCP server's advertised list (Day 33), and tools that another agent
exposes over A2A. Each source has its own lifecycle and only the first is in your repository, so the
inventory has to be taken from the **running agent's** tool list rather than from the code.

**The failure that only shows with real traffic.** A tool that is read-only in staging and not in
production. The same function name backed by a fixture dictionary locally and a live API remotely
reports clean here and can move money there. This check reads the code; what runs is the code plus
its configuration.

**The review comment a senior engineer leaves:** *"Fine today. Put this check in `./m check` with the
approval assertion, so the pull request that adds the first write tool is the one that goes red —
not the review six months later."*

**The interview question:** *"How do you assess an agent's blast radius?"* The answer that shows
experience enumerates tools from the running system and classifies each by what it can change, then
adds the part most people miss — that a read-only tool still admits untrusted content into the
context, which is an attack surface with no write in it.
