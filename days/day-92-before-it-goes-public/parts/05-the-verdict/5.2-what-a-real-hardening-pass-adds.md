# 5.2 — What a real hardening pass adds

## One-line answer

Eight checks that read files, git and installed metadata is a genuine review and it is the cheap
half; the distance between it and one a team can rely on is nine items, two of which must happen
before Day 93 and the rest of which are worthless unless the checks run on every commit.

## The story

The loft nobody has opened.

Every flat has one. A hatch in the ceiling of the passage, a folding ladder, and a space above it
that was full when the previous tenants left. Somebody looked in it once, on the day of moving in,
found boxes, and closed it.

Four years of living underneath it. The house has been cleaned, painted, rewired in one room, and the
loft has not been part of any of it — not through neglect exactly, but because nothing in the routine
of running a house ever routes through the hatch. It is not on the list because it was never on the
list.

The things that go wrong in a house go wrong where you look. The things that surprise you come out of
the loft.

## The idea in plain language

This day's lab does four things properly. It **derives** its target rather than hardcoding it, so the
checks work in any checkout. It **reports locations rather than values**, so the report can be
committed to the repository it audits. It **separates fixtures from findings** by a marker in the
evidence itself. And it **tests its own detector** before believing a clean result.

Here is what stands between that and a review a team could rely on.

**1. Put the checks in `./m check`.** Every finding in this day is a snapshot of one afternoon.
Principle 9 held for eighty-nine days because `.gitignore` enforces it continuously; nothing else here
is enforced at all. This is first because every other item assumes the checks run more than once.

**2. Answer the author-identity question.** Part
[2.2](../02-secrets/2.2-the-channel-no-file-scanner-reads.md): one real address on sixty-nine of
sixty-nine commits. Publish it deliberately or change it now — part
[3.3](../03-what-is-not-a-secret/3.3-what-cannot-be-taken-back.md) is why "now" is load-bearing.

**3. Scrub the fifty-one lines and record the exception.** Part
[3.1](../03-what-is-not-a-secret/3.1-fifty-one-lines.md): a find-and-replace, plus one sentence in
the day-format contract saying transcripts are verbatim except for the home directory. Without the
sentence the next traceback re-introduces it.

**4. `GEMINI_API_KEY` into `.env.example`.** Part [2.3](../02-secrets/2.3-the-template-that-drifted.md).
One line, and it is the first hour of every future contributor.

**5. Map each SEC control to a test, not a symbol.** Part
[4.2](../04-the-control-surface/4.2-thirteen-taught-three-shipped.md): "implemented" is
unfalsifiable and "`test_x` passes" is not. This turns thirteen open controls from an argument into a
list of missing tests.

**6. A vulnerability scan on the nightly.** Part
[4.3](../04-the-control-surface/4.3-six-chosen-one-hundred-and-thirteen-installed.md): a hundred and
seven unreviewed packages. It needs network, so it belongs on the schedule rather than the commit
gate — the split Day 82 arrived at.

**7. The near-miss fixtures.** The credential detector is tested against four synthetic keys that
match. It is not tested against strings that *nearly* match and must not fire, so its false-positive
behaviour is unmeasured.

**8. 🅿️ Parked — scan `sutra_mcp/` and `skills/`.** Both are in scope for publication and neither is
in any haystack in this day. Parked because both are nearly empty today and the check would pass
vacuously, which part [4.2](../04-the-control-surface/4.2-thirteen-taught-three-shipped.md) is about.

**9. 🅿️ Parked — audit the deployed thing, not the repository.** Day 85 measured a guard that is on
for the CLI and off for an embedder. Everything here reads git. Parked because there is nothing
deployed.

## Why Sutra needs it

Because Day 93 is next and items two and three expire with it. The rest can be done in March.

And because item one is what decides whether this day was worth anything. A review performed once,
before a launch, describes a repository that no longer exists the moment somebody merges — and this
repository has ninety-six days planned, most of which paste tracebacks.

## The mechanism

The list, with what each costs, so it can be argued with:

| # | Item | Where | Roughly | Blocks Day 93? |
| --- | --- | --- | --- | --- |
| 1 | the eight checks in `./m check` | `m`, `tests/` | an afternoon | no |
| 2 | decide the author identity | `git config`, one conversation | a morning | **yes** |
| 3 | scrub 51 lines + record the exception | 26 files, CLAUDE.md | an hour | **yes** |
| 4 | `GEMINI_API_KEY` in the example | one line | trivial | no |
| 5 | control-to-test mapping | `tests/`, `docs/TRACEABILITY.md` | a week | no |
| 6 | vulnerability scan on the nightly | outside this repository | needs network | no |
| 7 | near-miss fixtures for the detector | `secrets.py` | an hour | no |
| 8 | 🅿️ scan `sutra_mcp/` and `skills/` | not built | needs content | no |
| 9 | 🅿️ audit the deployment | not built | needs a deployment | no |

**Items 3 and 4 take about an hour between them.** Item 2 is not work; it is a decision that takes a
morning because somebody has to make it.

Item 1's whole implementation is the part worth writing out, since everything waits on it:

```python
CHECKS = (
    Check("1  no live credential, tree or history", "secrets.py", "--naive"),
    Check("2  the detector actually detects", "secrets.py --selftest"),
    ...,
)
```

**Line by line:**

- The tuple is already the interface. Wiring it into `./m check` means running `gate.py` and
  propagating its exit code — there is no new abstraction to design, which is the argument for doing
  it this week rather than scheduling it.
- Each entry stays a script with an exit code, so a check can be added by writing a file rather than
  by editing a framework.
- What is missing from this list is a **date and an owner per check**, which is what Day 82's
  quarantine argument would demand the moment somebody wants to skip one.

## When it breaks

The list breaks by being read as a backlog. A backlog is a place things are put; this is a set with an
order, and two of them expire.

The composite has a shape and this repository has walked most of it before:

```text
1. a review finds eight things and produces a verdict
2. the cheap ones are fixed the same afternoon
3. the rest become tickets, correctly
4. the repository is published on schedule
5. the checks are not in the pipeline, so nothing re-runs them
6. day 94 pastes a traceback with a home directory in it
7. the account-name finding is back and no check notices
8. the review is a document about a repository that no longer exists
```

Step seven is the cost and there is no error text for it. The check exists, in a lab, in a day folder
that is gitignored. It will never run again unless somebody runs it.

That is the same shape as part
[4.2](../04-the-control-surface/4.2-thirteen-taught-three-shipped.md), one level up: **a control that
exists as a lesson rather than as code.** This day's own lab is currently that.

## In production

**What a professional does.** Ships the checks and the fixes in the same change. A review that
produces a list of findings and a review that produces a list of findings plus the automation that
catches them again are different deliverables, and only the second one is still working next quarter.

**What degrades at scale.** The check suite becomes a cost centre. Eight checks over two thousand
files is seconds; the same discipline over a monorepo is minutes on every commit, and the pressure to
move them to a nightly is real and eventually correct. The thing to protect is that the *irreversible*
checks — anything about what gets published — stay on the commit gate whatever else moves.

**The failure that only shows with real traffic.** The review is done by somebody who did not write
the code, once, under time pressure, with no context for which findings are deliberate. Three of this
day's eight checks needed a judgement call that only somebody who knows the project could make: the
two fixture credentials, the seven fictional personas, and the absent approval gate in part
[4.1](../04-the-control-surface/4.1-the-keys-you-hand-over.md) that is currently correct. An outside
reviewer would have flagged all three, and a team that gets three false alarms stops reading the
fourth report.

**The review comment a senior engineer leaves:** *"Items two and three before Wednesday. Item one
before we merge anything else — the checks are written, they are good, and right now they live in a
directory git does not track, which is the most Sutra failure imaginable."*

**The interview question:** *"You have done the security review. What do you hand over?"* The answer
that shows experience hands over the checks rather than the findings — the findings are a snapshot and
the checks are the thing that keeps being true — and then names which findings expire if the handover
is slow.
