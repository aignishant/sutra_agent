# 5.1 — The verdict, and what blocks Day 93

## One-line answer

Three pass and five block: no credential is in this repository or its history, and what stands
between it and publication is one person's account name in fifty-one lines, an identity on every
commit, a stale template, thirteen controls that were taught and never shipped, and a hundred and
seven packages nobody chose.

## The story

The form you sign to say the flat was handed over in good condition.

Both parties walk through it together at the end. Taps run, the geyser is switched on, the wardrobe
doors are opened, somebody notices the burn mark on the kitchen counter that neither of them had
looked at in two years.

Then there is a sheet with a list and two signatures. It records what was found — including the burn
mark, which goes on the list with a note about who pays for it — and once it is signed, it is what
both people have. Everything either of them believed and did not write down stops existing.

The walk is the work. The sheet is the thing that survives.

## The idea in plain language

Here is the review, check by check, with what each found.

| # | Check | Verdict | What it measured |
| --- | --- | --- | --- |
| 1 | no live credential | PASS | 0 in 2,121 files and 69 commits; 2 named fixtures |
| 2 | the detector detects | PASS | 4 of 4 synthetic shapes caught |
| 3 | nothing identifying is published | BLOCKS | 0 in files, 1 on 69 of 69 commits |
| 4 | no account name in a tracked file | BLOCKS | 51 occurrences, 26 files, 15 day folders |
| 5 | the committed template is current | BLOCKS | `.env` has 5 keys, the example has 4 |
| 6 | no ungated tool can change things | PASS | 2 tools, both read-only, nothing to gate |
| 7 | named controls are in the code | BLOCKS | 3 of 16 implemented, 13 taught only |
| 8 | every installed package was chosen | BLOCKS | 6 chosen, 113 installed |

And then the sentence, which matters more than the counts:

> **This repository is not ready to be public. No credential is in it. Everything that blocks is
> something else.**

That shape is worth naming because it is the normal one and it is not what people expect. The control
that was designed, enforced from Day 0 and quoted in eighty-odd days — secrets never touch git — held
completely. Every finding is somewhere nobody had drawn a box.

The five blocking findings sort into three kinds:

**Two are identity.** Checks three and four. Neither is a secret, both are information about a real
person, and one of them cannot be removed after publication.

**Two are drift.** Checks five and seven. Something was true when it was written and the world moved:
a template that stopped describing its file, and a curriculum whose syllabus outran its code.

**One is scope.** Check eight. Nothing is wrong; the surface is simply larger than anybody had
counted, and counting it is the finding.

## Why Sutra needs it

Because this verdict goes into `docs/PROGRESS.md` and will outlive every memory of how it was
produced. Principle 10 applies hardest at the moment when writing `✅` would be easiest and nobody
would ever check.

And because Day 93 is next and is irreversible. Part
[3.3](../03-what-is-not-a-secret/3.3-what-cannot-be-taken-back.md) established the ordering: two of
these five stop being fixable the moment the repository is public, and the plan put the review first
for that reason.

## The mechanism

The gate counts blocking findings separately from passes and never folds them together:

```python
    blocking = [c.label for c, code in results if code == 1]
    passed = len(CHECKS) - len(blocking)
    print(f"\n  {passed} pass, {len(blocking)} blocking")
```

**Line by line:**

- `passed` is derived by subtraction, so a check that exits with some unexpected code cannot be
  counted as a pass by accident. The total stops adding up and somebody notices, which is better than
  a silent absorption.
- `blocking` collects **labels**, not a count, so the verdict block can name them. A number is a
  summary; a name is an address.
- `code == 1` explicitly rather than `!= 0`, leaving room for the third code Day 83's gate used for
  *cannot determine*. Nothing in this review needs it — every check here is answerable — and the
  shape stays compatible.

And the verdict prints every check including the passes:

```python
    for check, code in results:
        print(f"  {VERDICTS[code]:8}{check.label}")
    for script in blind:
        print(f"  {'BLIND':8}{script} stays green with the fault applied")
```

**Line by line:**

- Every check, so the block can be counted against the `CHECKS` list. A verdict listing only failures
  cannot reveal a check that silently stopped running.
- `VERDICTS[code]` raises `KeyError` on an unexpected code rather than printing something vague. A
  gate whose own reporting fails loudly is better than one that describes an unknown state calmly.
- The `blind` loop is the fault pass's output. A check that stays green with its fault applied is
  reported alongside the failures and blocks publication in the same way, because a check that cannot
  fail is worse than one that does.

Run the whole review:

```bash
cd days/day-92-before-it-goes-public/lab
uv run python gate.py | tail -18; echo "exit: ${PIPESTATUS[0]}"
```

**Line by line:**

- `tail -18` for the fault pass and the verdict. Each check's own findings print above it and are the
  subject of parts two, three and four.

Measured on 2026-09-07:

```text
=== the fault pass: a check that passed must be able to fail
  secrets.py            --naive         0 -> 1  goes red
  surface.py            --with-write    0 -> 1  goes red

=== verdict
  PASS    1  no live credential, tree or history
  PASS    2  the detector actually detects
  BLOCKS  3  nothing identifying is published
  BLOCKS  4  no account name in a tracked file
  BLOCKS  5  the committed template is current
  PASS    6  no ungated tool can change things
  BLOCKS  7  named controls are in the code
  BLOCKS  8  every installed package was chosen

  3 pass, 5 blocking

  No credential is in it. Everything that blocks is something else:
  a person's account name, a stale template, and controls that were
  taught and never shipped.
exit: 1
```

Read the fault pass first. Two of the three passes were re-run with a fault applied and both went
red, so `PASS` on those lines means *this check would have caught the thing it is for*. The third —
check two — is itself the fault test for check one.

## When it breaks

A verdict breaks by being rounded, and there are three ways:

**Rounding a blocker into a pass.** Check eight is the tempting one: a hundred and seven transitive
packages is a fact about every Python project and it feels unfair to call it blocking. But *blocking*
here means "somebody must decide before publication", and the decision is whether to add a
vulnerability scan. Downgrading it to a note is how it stops being decided.

**Rounding the sentence into the number.** `3 pass, 5 blocking` invites the reading that this
repository is riddled with security problems. It is not. It has one very good control that worked and
five findings, none of which is a credential, and the sentence is what carries that.

**Rounding the fault pass away.** It is three lines of output and it is what the three passes are
worth. Part [1.3](../01-what-a-review-is/1.3-the-checklist-that-answers-itself.md) measured the
version of this report with those lines removed: two true sentences and `exit: 0`.

The gate mark this produces is `⚠️`, and the ledger row spells out why in words. There is no error
text for a mis-rounded verdict and there never will be — this is the one part of the day where the
check is a person deciding to write down something unwelcome.

**What this review did not look at**, stated so the verdict is not read as wider than it is: the
running deployment as opposed to the repository, `sutra_mcp/` and `skills/`, known vulnerabilities in
the hundred and thirteen packages, anything the hosting platform derives from the repository after
publication, and any channel other than files and commit metadata.

## In production

**What a professional does.** Publishes the criteria before running them and does not edit them
afterwards. The discipline that makes a review mean anything is that the person writing the verdict
may not change the checks in the same sitting — otherwise every review passes, one small
redefinition at a time, and nobody involved ever says anything false.

**What degrades at scale.** Verdicts get summarised upward. Eight lines become one line becomes a
colour, and each compression is a reasonable act by somebody who was not present for the finding. The
countermeasure is that the sentence travels in the same field as the number, so compression cannot
separate them.

**The failure that only shows with real traffic.** The verdict is read months later by somebody
deciding whether to trust the repository. `⚠️` in a ledger means little to a reader planning work that
assumes the security controls exist. That is why the row names the findings explicitly rather than
pointing at this day — a pointer is a thing you follow when you have time.

**The review comment a senior engineer leaves:** *"Do not tick this. And put the five names in the
`PROGRESS.md` row, not just the counts — whoever reads it in March needs to know that three of sixteen
controls are in the code, and `5 blocking` does not say that."*

**The interview question:** *"Your pre-launch security review found five things and none is a
credential. Do you launch?"* The answer that shows experience sorts by reversibility first — which of
the five can still be fixed afterwards — and then makes the launch conditional on the ones that
cannot, because severity is negotiable and permanence is not.
