# 1.2 — The inventory comes before the opinion

## One-line answer

You cannot review what you have not counted, and the counting is the slow honest part: two thousand
one hundred and twenty-one tracked files, sixty-nine commits, one hundred and thirteen installed
packages, sixteen named controls — every later finding in this day is a subset of one of those four
numbers.

## The story

The inventory taken before the movers arrive.

Somebody comes to quote for shifting a flat. They do not stand in the doorway and estimate. They walk
in with a pad and write: one double bed, one mattress, two almirahs, a fridge, eleven cartons of
kitchen things, the cycle on the balcony, the water filter that is fixed to the wall and will need a
plumber.

The list is dull to make and nobody enjoys it. It is also the only reason the quote is a number
rather than a guess, and the only reason that on the day nobody says *"we did not know about the
almirah on the top floor"*. The argument you avoid three weeks later was avoided by the pad.

## The idea in plain language

Every check in this day begins the same way: by enumerating a set, then asking a question about each
member. The order matters, and getting it backwards is how reviews miss things.

**Backwards** looks like: *"are there any secrets in the repository?"* — a question about a set you
have not defined. You grep for what you can think of, in the places you happen to look, and the
answer's quality is the quality of your imagination that afternoon.

**Forwards** looks like: *"here are 2,121 tracked files; for each one, does it contain a string
shaped like a credential?"* Now the answer has a denominator. A clean result means something
specific, and the thing it means can be checked by somebody else.

Four inventories carry this whole day, and each one is a single command:

| Inventory | Size | Command |
| --- | --- | --- |
| files that would become public | 2,121 | `git ls-files` |
| commits that would become public | 69 | `git rev-list --all` |
| distributions installed | 113 | `importlib.metadata.distributions()` |
| security controls the plan names | 16 | the plan's own §12 |

Two of those are worth pausing on because they are the ones people skip.

**The commit inventory is not the file inventory.** A repository publishes its history, and a file
that was deleted in commit forty is still in the repository at commit thirty-nine. Part
[2.1](../02-secrets/2.1-the-scan-that-found-nothing.md) scans both, separately, and says so.

**The package inventory is not the dependency list.** Six lines in `pyproject.toml` produced one
hundred and thirteen installed distributions. Part
[4.3](../04-the-control-surface/4.3-six-chosen-one-hundred-and-thirteen-installed.md) is that
number and what it means.

## Why Sutra needs it

Because "the repository" is a phrase that hides four different sets, and going public exposes all
four. Principle 9 has been enforced against one of them — files — since Day 0, correctly and
successfully. Nothing in this repository has ever enumerated the other three, and two of the five
blocking findings in this day live there.

And because a denominator is what makes a finding arguable. *"There is an account name in the
repository"* is a sentence somebody can shrug at. *"There are fifty-one occurrences of it across
twenty-six files in fifteen day folders"* is a sentence with a decision attached.

## The mechanism

Every inventory in the lab comes from `_repo.py`, so no check invents its own idea of what the
repository is:

```python
def tracked() -> list[str]:
    """Every path git is tracking - which is exactly the set that becomes public."""
    return [line for line in git("ls-files").splitlines() if line]
```

**Line by line:**

- `git ls-files` rather than walking the filesystem with `rglob`. A filesystem walk finds `.env`,
  `.venv/`, every `__pycache__` and every lab directory — none of which become public — and would
  make the denominator wrong in the direction that hides findings among noise.
- The filter on `if line` drops the trailing empty string `splitlines` leaves; without it the count
  is off by one, which is the kind of error that survives forever because nobody re-derives it.

The git helper itself carries a fix that this day earned the hard way:

```python
    done = subprocess.run(
        ["git", *args], cwd=ROOT, capture_output=True, encoding="utf-8", errors="replace"
    )
    return done.stdout or ""
```

**Line by line:**

- `encoding="utf-8"` explicitly. The first version used `text=True`, which decodes with the
  platform's preferred encoding — on this machine cp1252 — and the history scan died partway through
  with `UnicodeDecodeError: 'charmap' codec can't decode byte 0x8f`. **It died after printing a
  clean result for the working tree.**
- `errors="replace"` so an undecodable byte in an old commit is a replacement character rather than
  the end of the audit. A security scan that stops at the first strange byte has scanned the part of
  the history before the strange byte.
- `or ""` so a failed git call returns an empty string rather than `None`. The first version returned
  `done.stdout` and the failure arrived as `AttributeError: 'NoneType' object has no attribute
  'splitlines'` several frames away from the cause.

And the two rules every check obeys, which are worth reading as a pair:

```python
def account() -> str:
    """This machine's account name, read from the home directory rather than written down."""
    return Path.home().name


def mask(text: str, secret: str, label: str = "<account>") -> str:
    """Replace a sensitive string with a label so a finding can be shown without being leaked."""
    return text.replace(secret, label) if secret else text
```

**Line by line:**

- `Path.home().name` — **derive, never hardcode.** The check works in anybody's checkout, and this
  file does not itself contain the string it is hunting for. A scanner with the target written into
  it is one more copy of the target.
- `mask` exists because this report is written into the repository it audits. Printing the finding
  would add an occurrence of the finding. Part
  [3.1](../03-what-is-not-a-secret/3.1-fifty-one-lines.md) is the check that needs this most.
- The default label is a placeholder rather than asterisks, so the masked line still reads as a path
  and a reviewer can see the shape of what leaked.

## When it breaks

An inventory breaks by being nearly right, and the failure is silent because a count is still
produced. Three ways, all of which this day hit while being written:

**Counting the wrong set.** `rglob("*")` over the repository root returns tens of thousands of paths,
most of them inside `.venv/`. Every ratio computed from it is wrong and every one looks plausible.

**Counting lines and calling them files.** The account-name check groups findings by day folder and
the first version printed `9 file(s)` for a day where nine *lines* matched across fewer files. The
number was right and the noun was wrong, which is worse than an obvious error because it survives
review.

**Counting a set that changes while you count it.** `importlib.metadata.distributions()` reports what
is installed in this environment at this moment. Adding a package mid-audit changes the denominator,
and nothing in the output says which environment it described.

None of the three raises. The check runs, prints a number with the right number of digits, and the
report is wrong in a way that reads as precision.

## In production

**What a professional does.** Puts the denominator in the output, always. *"0 of 2,121 files"* and
*"0 findings"* are different reports: the first can be checked against `git ls-files | wc -l` by
somebody who does not trust you, and the second cannot be checked at all.

**What degrades at scale.** Inventories stop being enumerable. At two thousand files you list them;
at two million you sample, and the moment you sample, a clean result stops meaning "nothing" and
starts meaning "nothing in the sample". Reviews at that size report coverage alongside findings, and
a review that reports findings without coverage is describing its own diligence rather than the
system.

**The failure that only shows with real traffic.** The inventory and the deployed thing diverge. This
day counts what git tracks; production runs what was built, which includes files generated at build
time and excludes anything the build dropped. The two are close enough to be confusing and different
enough to matter, and only an inventory taken *from the artefact* closes it.

**The review comment a senior engineer leaves:** *"Print the four denominators at the top of the gate
output, before any check runs. If somebody changes what `tracked()` means, I want to see the number
move in the same diff."*

**The interview question:** *"Where do you start a security review?"* The answer that shows experience
starts with enumeration, not with threats — what is in scope, how many of them there are, and how
that number was obtained — because every threat you can name is a question asked about a set, and
the set is the part people skip.
