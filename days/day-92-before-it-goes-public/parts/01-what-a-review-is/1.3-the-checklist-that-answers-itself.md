# 1.3 — 💥 The checklist that answers itself

## One-line answer

Three of this day's checks have an arm that runs the same code, reads a narrower thing, prints only
true sentences, and exits `0` — and the composite of those three is a security review that reports
`0 errors` over a repository with five blocking findings in it.

## The story

💥 **The bag search at the entrance.**

🎬 **The scene.** A guard at the door of a building with a table in front of him. Every bag is
opened, he looks inside, he waves you through. It is not a formality — he genuinely looks, and he has
turned people away.

😬 **The naive fix.** The queue is long, so the search settles into a routine: unzip the main
compartment, glance, done. Consistent, quick, applied to everybody, and defensible — every bag *was*
searched.

💥 **Why it fails.** Nothing has ever been found in a main compartment. The side pocket is not
opened, the laptop sleeve is not opened, and the bag that is already open is waved past because
there is nothing to unzip. The search has a hundred percent coverage of the place where nobody puts
anything.

💡 **The insight.** **The procedure was narrowed to the part that could be done quickly, and the
narrowing left no trace.** Nobody decided to stop searching. The record says every bag was searched,
and that record is true.

## The idea in plain language

There is a specific failure shape this phase keeps producing, and this day has three instances of it
in one gate. It is not lying, and it is not laziness. It is this:

> **A check reads a narrower thing than its name suggests, reports truthfully about what it read,
> and exits zero.**

Every clause matters. The check runs. The output is accurate. The exit code is honest about the
narrow thing. And the reader takes away a conclusion about the wide thing, because the check's *name*
was about the wide thing.

The three arms in this lab:

| Arm | What it truthfully reports | What the reader concludes |
| --- | --- | --- |
| `metadata.py --files-only` | no real address is in any tracked file | the repository publishes nobody |
| `controls.py --taught` | every security day is written and logged | the controls are in place |
| `gate.py --headline` | eight checks ran, no credential found | the review passed |

Each is a true statement. Each exits `0`. And the repository has one person's account name in
fifty-one lines, three of sixteen controls implemented, and five blocking findings.

The reason this belongs in a security day rather than a reporting day is that **security checks are
unusually easy to narrow without noticing**, because the narrow version is the one that is fast, the
one that is easy to write, and the one that produces the answer everybody wants.

## Why Sutra needs it

Because Day 93 is going to read a verdict and act on it, and the verdict is going into
`docs/PROGRESS.md` where it will outlive everybody's memory of how it was produced.

And because this is the fourth phase running in which the same shape has appeared. Day 79's suite
that could not fail, Day 81's accuracy without a baseline, Day 82's nightly that found a regression
and exited zero, Day 83's gate headline — and now a security review. The consistency is the lesson:
**in a system that reports, the failure mode is a confident number, not a crash.**

## The mechanism

Each narrowing is one branch. Here is the smallest, from `controls.py`:

```python
    if taught_only:
        closed = [i for i, s in status.items() if "closed" in s.lower()]
        print(f"  controls whose day is written and logged: {len(closed)} of {len(status)}")
        print("  every one of those days ends with its own checks passing")
        print("\n  the curriculum has covered its security syllabus")
        return 0
```

**Line by line:**

- It reads `status`, which is the plan's traceability ledger — a record of which *days* are done. That
  is a real fact about the curriculum and the sentence printed about it is true.
- It never touches `product_code()`. The question "is the control in the code" is not asked, so it
  cannot be answered no.
- `return 0` before the comparison the file exists to make. The narrowing is not a filter applied to
  the result; it is a path that never reaches the result.
- The last printed line is the one that does the damage, and it is *still true*: the curriculum has
  covered its syllabus. What it has not done is ship the code, and nothing on this path was asked
  about code.

Run the three arms:

```bash
cd days/day-92-before-it-goes-public/lab
uv run python controls.py --taught; echo "exit: $?"
```

**Line by line:**

- One flag. Same file, same imports, same ledger parse.

Measured on 2026-09-07:

```text
product package: sutra/, 10 files
controls the plan names: 16

  controls whose day is written and logged: 3 of 16
  every one of those days ends with its own checks passing

  the curriculum has covered its security syllabus
exit: 0
```

Note `3 of 16` sitting directly above *"has covered its security syllabus"*. Both are true. The three
are the ones with a ledger row; the other thirteen are days that are written and whose rows are
missing, which Day 83 measured as a separate problem. A reader who wanted reassurance has been given
a number and a sentence that do not contradict each other and do not agree either.

Now the composite:

```bash
uv run python gate.py --headline; echo "exit: $?"
```

**Line by line:**

- The flag makes the runner capture each check's output instead of printing it, and substitute a
  summary. Every check still runs and every exit code is still collected.

Measured on 2026-09-07:

```text
Security review: 8 checks ran, 0 errors.
No credentials found in the repository or its history.
exit: 0
```

**Two sentences, both true, and an exit code of zero over five blocking findings.** `0 errors` is
accurate: not one check raised. The five failures are *results*, and a summary that counts errors is
counting the one thing a working review does not produce.

## When it breaks

It does not break. That is the finding, and there is no error text to quote for the same reason there
was none at the guard's table: the procedure ran, the record is accurate, and the record is about the
main compartment.

What is missing is a list, and it is exactly the list the wide arm prints:

```text
  BLOCKS  3  nothing identifying is published
  BLOCKS  4  no account name in a tracked file
  BLOCKS  5  the committed template is current
  BLOCKS  7  named controls are in the code
  BLOCKS  8  every installed package was chosen
```

Five lines. None of them fits in a status, none of them is an error, and a summary that has no field
for them cannot carry them however carefully it is written.

**The version that is actually dangerous** is not the flag — nobody would run `--headline` on a
pre-publication review on purpose. It is the same narrowing arriving by accident three months from
now: the gate grows to twenty checks, the output runs to four hundred lines, somebody reasonably adds
a summary, and somebody equally reasonably starts reading only the summary. Two good decisions, and
the findings stop travelling.

## In production

**What a professional does.** Makes the summary carry the failures by construction, not by
discipline: the status line is generated *from* the list of non-passing checks, so a check that fails
cannot be absent from it and a check that is deleted shortens a line somebody has to justify in a
diff. The test of a summary is not whether it is accurate; it is whether a real finding can change it.

**What degrades at scale.** The pressure is structural and one-directional. Readers multiply faster
than investigators, every reader wants the report shorter, and nobody ever asks for it longer. So the
format drifts towards the status line on its own, without a decision — which is why the countermeasure
has to be a rule about the format rather than an intention to read carefully.

**The failure that only shows with real traffic.** The summary becomes an interface. Once a dashboard,
a badge, a release gate or another team's automation reads the one-line result, the detail stops being
read at all, and a finding that is not in the summary has stopped existing operationally. Day 82
measured this precisely: a regression named in capitals on standard output, and an exit code of `0`,
because the machine-readable channel was the one that did not carry it.

**The review comment a senior engineer leaves:** *"Generate the headline from the blocking list. Right
now I could delete check four and the headline would not change, and that is the entire test of
whether a summary is doing its job."*

**The interview question:** *"Your security scan is clean and you were breached. What do you check
first?"* The answer that shows experience does not ask whether the scanner was good. It asks what the
scanner *looked at* — which files, which branches, which channel — because a clean result over a
narrow set is the normal way this happens, and it leaves no error behind.
