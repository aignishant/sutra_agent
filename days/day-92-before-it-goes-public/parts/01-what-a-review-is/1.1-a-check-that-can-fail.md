# 1.1 — A review is a set of checks that can fail

## One-line answer

A security review is not a document you produce and it is not a list of questions you answer; it is
a set of commands that run against the repository as it actually is, each of which can come back
red — and this one comes back with three passing and five blocking.

## The story

The house checked room by room before a long trip.

You are leaving for a fortnight. Before locking the front door you walk through: gas off at the
knob, tap in the back bathroom that drips, the window in the small room that never latches
properly, the plug of the fridge staying in and everything else coming out.

That walk takes a few minutes and it is not a feeling. It is a route with a fixed set of stops, and
at every stop there is something you can *find*. The window is either latched or it is not. The gas
is either off or it is not.

The version that does not work is standing at the door with your bag, thinking *"I think it's all
fine"*. That is also a review. It takes no time at all, it is right most of the time, and the once
it is wrong it is wrong about the gas.

## The idea in plain language

Day 83 built a phase gate and made an argument that applies again here, harder: **green is only
evidence if red was reachable.**

A security review is where that argument matters most, because the pressure runs entirely one way.
Nobody is rewarded for finding a problem the week before a launch. The review that finds nothing is
faster, more pleasant, and indistinguishable — from the outside — from the review that could not
have found anything.

So this day is built as eight commands. Each one:

- reads the repository as it is now, not as a document says it is;
- prints what it found, with counts and locations;
- exits `0` or `1`, so the answer survives being piped somewhere.

And one of them is a check on the checks. Criterion two runs the credential detector against
synthetic credentials of each shape it claims to catch, because **a scanner that has never caught
anything has not been shown to work**, and a clean report from an untested scanner is a feeling with
a percent sign on it.

Here is the whole review, which is also §2's map:

| # | Check | Question |
| --- | --- | --- |
| 1 | `secrets.py` | is a live credential in the tree or the history? |
| 2 | `secrets.py --selftest` | would the detector catch one if it were? |
| 3 | `metadata.py` | what does this repository publish that is in no file? |
| 4 | `identity.py` | whose machine does the repository name? |
| 5 | `template.py` | does the committed template still describe the private file? |
| 6 | `surface.py` | can any tool change something without an approval? |
| 7 | `controls.py` | are the named security controls in the code? |
| 8 | `deps.py` | how much code runs here that nobody chose? |

## Why Sutra needs it

Because Day 93 makes this repository public, and public is the one operation with no undo. Every
day of this curriculum has been written on the assumption that Phase 14 arrives — `.gitignore` was
written on Day 0 *"BEFORE `.env` exists"* with a comment saying so, and Principle 9 has been quoted
in eighty-odd days on the strength of it.

This is where that assumption gets tested rather than repeated. And the honest result is that the
part everybody worried about — a leaked key — is clean, and five other things are not.

## The mechanism

The gate is a list of checks and a runner, in the shape Days 78 and 83 established:

```python
CHECKS = (
    Check("1  no live credential, tree or history", "secrets.py", "--naive"),
    Check("2  the detector actually detects", "secrets.py --selftest"),
    Check("3  nothing identifying is published", "metadata.py", "--files-only"),
    Check("4  no account name in a tracked file", "identity.py"),
    Check("5  the committed template is current", "template.py"),
    Check("6  no ungated tool can change things", "surface.py", "--with-write"),
    Check("7  named controls are in the code", "controls.py", "--taught"),
    Check("8  every installed package was chosen", "deps.py", "--direct-only"),
)
```

**Line by line:**

- Each check is a **script**, not a function, so the interface is an exit code. That is what lets
  check seven shell out to a parser over the plan's ledger and check eight read installed package
  metadata without the runner knowing they are different kinds of thing.
- The third field is the fault to apply when the check passes. Checks four and five carry `None`
  because they are already red, and a check that is currently failing does not need to be shown that
  it can.
- Check six's fault adds a synthetic write tool to the inventory rather than to the repository. It is
  the only way to prove that check can fail, because the desk genuinely has nothing to gate.
- The faults are not sabotage of the repository. Each one is *the weaker version of the same check*
  — `--naive` is the credential scan written in a hurry, `--taught` is counting the syllabus instead
  of the code. Applying them and watching the criterion still go red is how you know the criterion
  is reading something.

The runner refuses to stop early:

```python
    for check in CHECKS:
        if not headline:
            print(f"\n=== check {check.label}")
        results.append((check, run(check.script, quiet=headline)))
```

**Line by line:**

- No `break`, no early return, and no `check=True` on the subprocess. A non-zero exit is the expected
  result of five of these eight, and raising on the first one is how the other four ship.
- The heading prints before the run, so a check that crashes is attributable to a line rather than to
  whichever one ran before it.

Run it:

```bash
cd days/day-92-before-it-goes-public/lab
uv run python gate.py; echo "exit: $?"
```

**Line by line:**

- No flag. The `--headline` arm is part [1.3](1.3-the-checklist-that-answers-itself.md)'s subject.

Measured on 2026-09-07 — the tail, after all eight have printed their own findings:

```text
=== the fault pass: a check that passed must be able to fail
  secrets.py            --naive         0 -> 1  goes red
  surface.py            --with-write    0 -> 1  goes red

=== verdict
  PASS    1  no live credential, tree or history
  PASS    2  the detector actually detects
  BLOCKS  3  nothing identifying is published
  BLOCKS  4  no account name in a tracked file
  BLOCKS  5  the committed template is current
  PASS    6  no ungated tool can change things
  BLOCKS  7  named controls are in the code
  BLOCKS  8  every installed package was chosen

  3 pass, 5 blocking

  This repository is NOT ready to be public.
  No credential is in it. Everything that blocks is something else:
  a person's account name, a stale template, and controls that were
  taught and never shipped.
```

Read the last four lines rather than the counts. **The thing the review was built to find is not
there, and five things nobody was looking for are.** That is not a surprising outcome; it is the
normal one, and part [papers/01](../../papers/01-how-systems-actually-fail.md) is a paper about
exactly why.

## When it breaks

A review breaks by being a document. The failure has no error text because nothing runs:

```text
1. somebody is asked to do a security review before launch
2. they open a checklist with eighteen questions on it
3. they answer each from memory, honestly, and mostly correctly
4. the document says "reviewed" and carries a date and a name
5. nothing in it can be re-run against the repository next month
6. by the time it is wrong, the document still says reviewed
```

Every step is done in good faith and the artefact is worthless the day after it is written, because
it records an opinion held once rather than a property that can be re-tested. Part
[1.3](1.3-the-checklist-that-answers-itself.md) measures the version of this that has an exit code
and still tells you nothing.

The second way it breaks is subtler and this day is not immune to it: **a check that reads the wrong
thing.** Check six's first version searched `sutra/` for control vocabulary including comments, and
reported six of sixteen controls present. Stripping comments and docstrings took that to three. The
check ran, exited non-zero, and was wrong by a factor of two in the reassuring direction — part
[4.2](../04-the-control-surface/4.2-thirteen-taught-three-shipped.md) is the whole story.

## In production

**What a professional does.** Writes the review as code in the repository and puts it in the same
pipeline as the tests. The review that matters is the one that runs on every change, because the
security posture of a repository is not a state it was in once; it is a property that a merge can
remove. A review performed by a person, once, before a launch, is a snapshot of a moving thing.

**What degrades at scale.** Seven checks over two thousand files run in a few seconds. Seventy
checks over a monorepo do not, and at that point somebody moves them to a nightly, and then to a
weekly, and the feedback arrives after the change that caused it has been forgotten. The mitigation
is to split by cost the way Day 82 split the eval suite: the ones that read files stay on every
commit, and only the expensive ones ride a schedule.

**The failure that only shows with real traffic.** The review passes and the deployment differs from
the repository. Everything here inspects files in git; nothing inspects what is actually running.
Day 85 measured an `api_server` whose rebinding guard is on for the CLI and off for an embedder —
same code, two postures, and a file-based review sees one of them.

**The review comment a senior engineer leaves:** *"Put the fault pass in the output permanently. If
somebody deletes a check, I want the verdict block to get shorter in a way that shows up in a diff,
not a green run with one fewer line nobody counted."*

**The interview question:** *"How do you do a security review?"* The answer that shows experience does
not describe a document or a framework. It names the commands, says what each one would find, and
then says which of them has ever actually found something — because a check that has never fired is
a check nobody has tested.

## Check yourself

```bash
cd days/day-92-before-it-goes-public/lab
uv run python gate.py | tail -18

```

The second command is the check on the checks. Say what a clean result from the first would be worth
if the second did not exist, and why that is a different question from whether the scanner is
well written.

Now look at the eight labels and sort them into *things an attacker does* and *things we did to
ourselves*. The split is lopsided, and noticing which way is the point of the day.
