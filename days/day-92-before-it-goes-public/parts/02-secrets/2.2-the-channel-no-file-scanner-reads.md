# 2.2 — 💥 The channel no file scanner reads

## One-line answer

Not one address belonging to a real person is in any of two thousand one hundred and twenty-one
tracked files — and the same repository publishes one on every single one of its sixty-nine commits,
because the author identity lives in the commit and no scanner that reads files will ever open it.

## The story

💥 **The photograph with the street sign in it.**

🎬 **The scene.** Somebody posts a picture of a new puppy in the front garden. They look at it before
posting, the way you do: nothing embarrassing, nobody else's child in shot, no documents on the
table.

😬 **The naive fix.** Check the picture. That is the whole procedure and it is applied honestly every
time — look at what you are about to publish, decide whether you mind.

💥 **Why it fails.** Over the gate, slightly out of focus, is the street sign. And under the picture,
attached by the camera and never looked at by anybody, is the location the phone recorded when the
shutter went. Neither is *in* the photograph in the sense the person was checking. Both are
published with it.

💡 **The insight.** **The review covered the content and the exposure was the container.** Nothing in
the procedure was done badly. The procedure was defined over the thing a person can see, and a
published artefact carries more than that.

## The idea in plain language

A git repository publishes at least three things and a secret scanner reads one of them.

**File contents.** What `git ls-files` returns and what every scanner in this day and every scanner
you can buy is pointed at. This repository is clean here.

**Commit metadata.** Author name, author email, committer name, committer email, and two timestamps
with time-zone offsets — on every commit, forever, and reproduced into every clone and every fork.
None of it is in a file. `git log -p` does not show it unless you ask, and no `grep` over the working
tree can reach it.

**Repository structure.** Branch names, tag names, the shape of the history. Usually harmless and
occasionally not — a branch called `fix-for-<customer>` is a customer relationship published by
accident.

The measurement is stark. Fifty-two email-shaped strings appear in tracked files; forty-five are at
domains the standards reserve for exactly this purpose, and the remaining seven were read by a person
and are fictional personas in ticket bodies. **Zero real addresses in file contents.**

And one real address on **sixty-nine of sixty-nine commits.**

This is not a mistake and it is not fixable in the way a leaked key is fixable. It is the git
identity, it is how attribution works, and most public repositories publish it deliberately. The
finding is not *"a secret escaped"*. The finding is that **the check everybody runs cannot see the
channel that is actually carrying something**, so the decision to publish it was never made — it was
inherited from a `git config` line somebody set once.

## Why Sutra needs it

Because CLAUDE.md's own rule is that this repository promotes nobody and names nobody — no
instructor, no author, no creator. Eighty-nine days have been written to that rule, carefully, in
prose. And the commit log has a person's name and personal address on every commit in the repository.

The prose rule was enforced by a person reading prose. The metadata was never in scope for it,
because nobody wrote the rule while thinking about `git log --format=%ae`.

## The mechanism

Two scans over two channels, deliberately in one file so the difference is unmissable:

```python
def is_reserved(address: str) -> bool:
    """True when the domain is one the standards set aside for examples."""
    domain = address.partition("@")[2].lower()
    labels = domain.split(".")
    return labels[-1] in RESERVED_TLDS or "example" in labels
```

**Line by line:**

- `RESERVED_TLDS` is `("test", "invalid", "example", "localhost", "internal")` — names reserved by
  RFC 2606 and RFC 6761 precisely so that documentation can use them and no scanner has to guess. An
  address ending in one of them cannot belong to a person, by standard rather than by convention.
- `"example" in labels` catches `support.example.com` as well as `example.in`, because the reserved
  name can be any label rather than only the first.
- Everything that does not match falls through to a human. The check does not pretend to classify
  what it cannot: it prints the remainder and says a person read them.

Masking, because a finding about published addresses must not itself publish one:

```python
def mask_email(address: str) -> str:
    """Show the shape of an address without republishing it."""
    local, _, domain = address.partition("@")
    return f"{local[0]}{'*' * (len(local) - 1)}@{domain}" if local else address
```

**Line by line:**

- The first character and the length survive, so a reviewer can tell two findings apart and can see
  roughly what shape the local part is.
- The **domain is kept in full**, deliberately. The domain is the part that tells you whether this is
  a corporate address, a personal one or a service account, and that is the part a reviewer needs to
  make a decision. Masking it would produce a finding nobody can act on.

And the second channel, which is four lines and the whole point of the part:

```python
    authors = Counter(a for a in git("log", "--all", "--format=%ae").split() if a)
    names = {n for n in git("log", "--all", "--format=%an").splitlines() if n}
    commits = len(git("rev-list", "--all").splitlines())
```

**Line by line:**

- `--format=%ae` and `%an` are the author's email and name. There are committer equivalents (`%ce`,
  `%cn`) which differ whenever a patch is applied by somebody other than its author — this repository
  has one identity so they agree, and on a project with contributors they would double the finding.
- `--all` again, for the same reason as the credential scan: an identity on an unmerged branch is
  still published.
- `.split()` on the email output rather than `.splitlines()` because an address cannot contain
  whitespace, and this way a blank line cannot become a counted identity.

Read the last three lines together. **`0` and `1`, from the same repository, by the same review**,
and only one of the two channels has ever been scanned by anything.

## When it breaks

The composite is short and every step of it is reasonable:

```text
1. a rule is written: this repository names nobody
2. the rule is enforced by people reading prose, which is where names appear
3. a secret scanner is added, which reads file contents
4. both are clean, for eighty-nine days, correctly
5. the repository goes public
6. every commit carries a name and a personal address, and always did
```

There is no error text at any step, and step six is not a regression — it was true at commit one. The
review never reached it because the review was defined over files, and a repository is not a set of
files.

**The part that is genuinely hard** is that this one is mostly not fixable after the fact, and part
[3.3](../03-what-is-not-a-secret/3.3-what-cannot-be-taken-back.md) is why: changing an author
identity means rewriting every commit, which changes every hash, which breaks every fork, clone and
link that already exists. The realistic options are to decide the identity is fine to publish — which
most people do, knowingly — or to change `git config` now and accept that the history keeps what it
has.

The decision is small. Making it *before* the repository is public rather than after is the whole
value of running this check today.

## In production

**What a professional does.** Enumerates the channels before writing the check. For a git repository
that is: file contents, commit metadata, branch and tag names, and anything the hosting platform
derives — issue text, pull-request titles, CI logs, artefact names. Each is a separate exposure with a
separate owner, and a review that lists them is a review whose gaps are visible.

**What degrades at scale.** More contributors, more identities, and the ones that arrive by accident
are the problem — a build machine committing as `root@buildbox`, a bot with an internal hostname in
its address, a contractor's corporate address on the commits from one sprint. Nobody chose any of
those, and each is a fact about the organisation published to everybody.

**The failure that only shows with real traffic.** The hosting platform adds a channel. Fork counts,
contributor graphs, commit-activity timelines and CI logs are all derived from the repository and
published alongside it, and none of them is in the repository. A green pre-publication review says
nothing about what the platform will render on top of it.

**The review comment a senior engineer leaves:** *"Decide the author identity question before we make
this public, not after. Rewriting sixty-nine commits is a morning; rewriting them once forks exist is
not a thing we get to do."*

**The interview question:** *"Your secret scanner is clean. What is it not looking at?"* The answer
that shows experience lists channels rather than patterns — metadata, history, branch names,
platform-derived data — because every scanner is a set of patterns applied to one channel, and the
channel is chosen once and then forgotten.
