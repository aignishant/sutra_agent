# 2.3 — The template that drifted

## One-line answer

`.env` holds five keys and the committed `.env.example` describes four, so the file a new
contributor copies is missing `GEMINI_API_KEY` — a small finding, found only because the check
compares two files instead of asking whether an example exists.

## The story

The emergency contact list on the fridge.

It went up when the family moved in: the doctor, the plumber, the gas agency, the neighbour with the
spare key, the office landline. Four years later it is still there, held by the same magnet, and
three of the numbers have changed.

Nobody let it go stale on purpose. The doctor moved practice and everyone updated their phone; the
plumber's number is in a chat; the neighbour moved out and the new one's number is in someone's head.
Each change was recorded somewhere, and the *shared* copy — the one that exists precisely for the
person who does not have the number in their phone — is the one nobody updated, because whoever
needed it already knew.

The list is used exactly once, by exactly the person it was written for, on a bad day.

## The idea in plain language

`.env.example` is the shared copy. It exists for one reader: somebody who has just cloned the
repository and has no `.env`. Everybody who works on the project daily has a working `.env` and never
opens the example again.

So the drift is structural rather than careless. A new key gets added to the private file the moment
it is needed — the work does not proceed otherwise — and the committed example is updated only if
somebody remembers a reader who is not in the room.

The check compares the two by **key name**, which is the only comparison that is both useful and
safe:

- **Key names are not secrets.** `GOOGLE_API_KEY` is in the provider's own documentation. Printing
  the names is how the report becomes actionable.
- **Values are.** The check reads the private file's values only to take their length, and prints
  that length rather than the value — which is enough to tell an empty placeholder from a real
  credential, and not enough to be one.

It also asks git two questions that the credential scan in part
[2.1](2.1-the-scan-that-found-nothing.md) answers from the other direction: is `.env` ignored, and is
it tracked. Those are different questions. A file can be listed in `.gitignore` and still be tracked,
if it was committed before the rule was added — `.gitignore` does not apply to files git already
knows about, which is the single most common way this rule is believed and broken at the same time.

## Why Sutra needs it

Because Day 93 publishes this repository and `.env.example` becomes the setup instructions. A
template missing a key does not produce an error at clone time or at install time; it produces one
much later, at the first call that needs the missing key, in a stack trace about an unset variable
that the new reader has no context for.

And because the finding is a good calibration for the rest of the day. It is small, it is real, it
was invisible to every check that looks for secrets, and it took a comparison rather than a search to
find. Most of what a review turns up is that shape.

## The mechanism

Parsing a dotenv file to names and value *lengths*:

```python
def keys(path: Path) -> dict[str, int]:
    """Every assignment in a dotenv file, as name -> length of its value."""
    if not path.is_file():
        return {}
    out: dict[str, int] = {}
    for line in path.read_text(encoding="utf-8").splitlines():
        line = line.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        name, _, value = line.partition("=")
        out[name.strip()] = len(value.strip())
    return out
```

**Line by line:**

- The return type is `dict[str, int]`, not `dict[str, str]`. The value never leaves this function,
  and the type signature is the enforcement — a later change that wanted to print a value would have
  to change the signature, which is a thing a reviewer notices.
- `partition("=")` rather than `split("=")`, because a value can contain `=` and a split would either
  raise on the extra field or silently truncate. `partition` splits on the first occurrence only.
- Comments and blank lines are skipped before the `=` test, so a commented-out key is correctly
  absent rather than counted as present with a strange name.
- `if not path.is_file(): return {}` — a missing `.env` is a legitimate state, for anybody who has
  cloned and not configured yet. The comparison then reports every example key as extra, which is
  the right answer for that person.

The two git questions:

```python
    ignored = git("check-ignore", "-v", ".env").strip()
    tracked_private = bool(git("ls-files", ".env").strip())
```

**Line by line:**

- `check-ignore -v` returns the exact rule that matched, in `file:line:pattern` form, or nothing.
  That is the difference between *"I believe it is ignored"* and a citation a reviewer can look up.
- `ls-files` is the one that actually matters. A tracked file is published whatever `.gitignore`
  says, and this is the check that catches the case where a secret was committed once and the rule
  added afterwards.
- Both are cheap, and the report prints them together so the two states cannot be confused.

Run it:

```bash

```

**Line by line:**

- No flag. The `--values` arm asks a different question and is in **When it breaks**.

Measured on 2026-09-07:

```text
.env         5 keys, untracked
  ignored by: .gitignore:4:.env	.env
.env.example 4 keys, committed

  key                                in .env  in example
  GEMINI_API_KEY                         yes          NO
  GOOGLE_API_KEY                         yes         yes
  GOOGLE_GENAI_USE_VERTEXAI              yes         yes
  GROQ_API_KEY                           yes         yes
  OPENROUTER_API_KEY                     yes         yes

  in .env and missing from the example: 1
    - GEMINI_API_KEY  (value is 53 characters; not read further)

  a contributor who copies the example gets an incomplete environment
  and finds out at the first call that needs the missing key
exit: 1
```

**Five against four, and the one that is missing has a fifty-three character value.** That length is
the whole reason the line is worth printing: an empty placeholder and a real key are the same key
name, and the difference between them is a number the check can report without reading anything it
should not.

Note also `ignored by: .gitignore:4:.env` and `untracked` together. Principle 9 holds here, by rule
and by fact, and the report says which is which.

## When it breaks

The interesting failure is the opposite drift: an example that carries values instead of blanks.

```bash
uv run python template.py --values; echo "exit: $?"
```

That arm counts keys in the committed example whose value is non-empty. A template with values in it
is a file somebody will eventually paste a real credential into — the shape invites it, because the
line already looks like an assignment rather than a prompt. It is also the file least likely to be
re-read before a commit, since it is "just the example".

The second failure has no output at all: **a template nobody checks is a template that stops being a
template.** There is no error when `.env.example` falls behind; the project works perfectly for
everyone who already has the key. The cost lands entirely on a person who is not in the room, at a
moment when they have no way to tell a missing configuration line from a broken project.

And a third, which this check would not catch: an example that is *complete* and *wrong* — a key name
that has been renamed in the code and not in the template. Comparing the two files finds keys that
are missing from one side; finding a key that neither file needs any more requires reading the code,
which is part [4.1](../04-the-control-surface/4.1-the-keys-you-hand-over.md)'s territory.

## In production

**What a professional does.** Generates the template from a schema rather than maintaining it by
hand. If the application declares its configuration — required names, types, whether each is secret —
then the example is emitted from that declaration and cannot drift, and the check becomes "is the
committed file identical to the generated one", which is a diff rather than a comparison.

**What degrades at scale.** Environments multiply. One `.env.example` becomes local, staging and
production, then per-service, and the drift is now between a dozen files that are almost identical.
At that point the thing that keeps them honest is a single source of truth, and hand-maintained
examples become the mechanism by which a service fails in staging for a reason nobody can reproduce.

**The failure that only shows with real traffic.** The template is right and the *documentation* is
wrong. A README that lists three variables while the example lists five sends the reader to the wrong
place; both files are committed, both are read, and no check compares them. Day 93's documentation
pass is where that one belongs.

**The review comment a senior engineer leaves:** *"Add `GEMINI_API_KEY` to the example with an empty
value and put this check in `./m check`. It is thirty lines and it is the only thing standing between
us and a new contributor's first hour."*

**The interview question:** *"How do you keep the example environment file correct?"* The answer that
shows experience does not say discipline. It says the file is generated, or it is compared by a check
that runs on every commit, because a file that only one person ever reads, once, will always drift.
