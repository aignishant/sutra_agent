# 2.1 — The scan that found nothing

## One-line answer

Two thousand one hundred and twenty-one tracked files and sixty-nine commits contain zero live
credentials, the two shaped hits are lesson fixtures that announce themselves, and the result is
worth reporting only because a self-test proves the detector would have caught one.

## The story

The bank statement read line by line for the first time in a year.

You sit down one evening and actually go through it. Every debit, matched to something you
remember. It takes a while and it is boring, and at the end of it everything is accounted for.

The temptation, before you started, was to skip it — you would have noticed something wrong, surely.
And the value of having done it is not that you found something. It is that *"nothing is wrong"* has
stopped being a feeling and become a statement with a page of working behind it, which is a
different thing to be able to say.

The other half of the value is quieter. You now know what the statement looks like when it is fine.
Next month's takes a quarter of the time.

## The idea in plain language

Principle 9 is the oldest live rule in this repository: secrets never touch git. `.gitignore` was
written on Day 0 with a comment saying it was written *before* `.env` existed, precisely so the rule
could never be retrofitted.

This check asks whether it held. It scans two sets, separately, because they are two different
exposures:

**The working tree** — every file `git ls-files` reports, which is exactly what a person who clones
the repository gets.

**The history** — every added line across every commit on every branch. A credential deleted in
commit forty is still in the repository at commit thirty-nine, and `git log -p` is what an attacker
would read. Deleting a secret from a file does not remove it from a repository; only rewriting
history does, and part [3.3](../03-what-is-not-a-secret/3.3-what-cannot-be-taken-back.md) is about
what that costs.

The pattern looks for **shapes**, not for words. A Google API key is `AIza` followed by exactly
thirty-five more characters. Groq is `gsk_` and at least forty. OpenRouter is `sk-or-v1-` and fifty
hex digits. A PEM private key has a header line that is the same in every file that has ever
contained one. Those are the issuer's own formats, and matching on them is the difference between a
scan you read and a scan you close — part [3.2](../03-what-is-not-a-secret/3.2-the-highlighter.md)
measures that difference at twelve thousand lines.

And two hits come back, both in day documents, both containing the string `notarealkey` or a
truncated key in a Kubernetes manifest written as a teaching example. Those are counted separately
and named as fixtures, because **a fake key in a lesson is not a leak**, and a scanner that reports
it as one is a scanner that gets switched off.

## Why Sutra needs it

Because this is the finding everybody expects the day to produce, and it is worth being precise that
it did not. The repository is clean on the axis it was designed to be clean on. Day 0's rule worked,
for eighty-nine days, across sixty-nine commits, with no exception.

Saying that plainly matters as much as the five findings that follow — a review that only reports
problems teaches its readers that the controls do not work, when the truth here is that one control
worked completely and the failures are all somewhere nobody had drawn a box.

## The mechanism

The pattern is four issuer formats and nothing else:

```python
CREDENTIAL = re.compile(
    r"AIza[0-9A-Za-z_-]{35}"  # Google API key
    r"|gsk_[0-9A-Za-z]{40,}"  # Groq
    r"|sk-or-v1-[0-9a-f]{50,}"  # OpenRouter
    r"|-----BEGIN [A-Z ]*PRIVATE KEY-----"  # any PEM private key
)
```

**Line by line:**

- `{35}` exactly, not `{35,}`. The length is part of the format, and a bounded quantifier is what
  stops the pattern matching a long random-looking identifier that happens to start with those four
  letters.
- `[0-9A-Za-z_-]` — the character set the issuer actually uses. Widening it to `.` would match a key
  followed by punctuation and also match prose.
- `[A-Z ]*` in the PEM header covers `RSA`, `EC`, `OPENSSH` and the bare `PRIVATE KEY` form in one
  branch, because the part that never varies is the dashes and the words around them.
- Four alternatives for four providers this repository actually uses, from the zero-budget addendum.
  A pattern for a provider you do not use is a pattern that can only produce false positives.

The two scans are separate functions because they read different things:

```python
def scan_history(pattern: re.Pattern[str]) -> int:
    """Added lines across every commit on every branch. A deleted secret is still a secret."""
    log = git("log", "-p", "--all", "--no-color").splitlines()
    added = [line for line in log if line.startswith("+")]
    return sum(1 for line in added if pattern.search(line) and not is_fixture(line))
```

**Line by line:**

- `--all` covers every branch and tag, not just the checked-out one. A secret committed on a branch
  that was never merged is still in the repository, and this is the flag that is easiest to forget.
- `--no-color` because ANSI escapes inside a matched line would corrupt the offsets and, worse, could
  break a pattern that anchors on characters.
- Only lines starting with `+` — additions. A `-` line is the removal of something that was already
  counted when it was added, and counting both doubles every finding.
- `is_fixture` runs on the history too. A teaching example that was added in a commit is a fixture in
  the history for the same reason it is one in the tree.

Run it:

```bash
cd days/day-92-before-it-goes-public/lab
uv run python secrets.py; echo "exit: $?"
```

**Line by line:**

- No flag: the real arm, over both sets.

Measured on 2026-09-07:

```text
repository: 2121 tracked files, 69 commits
pattern: issuer-shaped credentials

  working tree, real hits:      0
  working tree, known fixtures: 2
  every commit, real hits:      0

  no credential in 2121 files or 69 commits
  the shaped hits are lesson fixtures and are counted above as fixtures
exit: 0
```

**Zero and zero, with the denominators printed.** That is the whole point of part
[1.2](../01-what-a-review-is/1.2-the-inventory-comes-first.md): *"no credential"* is a feeling and
*"no credential in 2,121 files or 69 commits"* is a claim somebody else can reproduce.

And the `.env` file that holds the real keys is untracked, which the template check confirms from the
other direction:

```text
.env         5 keys, untracked
  ignored by: .gitignore:4:.env	.env
```

## When it breaks

A clean scan breaks by never having been tested. The whole report above is worth nothing if the
pattern is subtly wrong — a stray anchor, a bad quantifier, a typo in a prefix — because a broken
pattern and a clean repository produce byte-identical output.

So the detector is tested against a credential of each shape it claims to catch:

```bash
uv run python secrets.py --selftest; echo "exit: $?"
```

Measured on 2026-09-07:

```text
detector self-test: one synthetic credential per issuer shape

  google        39 chars  caught
  groq          44 chars  caught
  openrouter    59 chars  caught
  pem           31 chars  caught

  all 4 shapes caught, so a clean scan means something
exit: 0
```

The synthetic credentials are built from the prefix plus the right number of zeroes, so they match
the format and belong to nobody. This is the check that converts *"the scan found nothing"* into
*"the scan found nothing and the scan works"*, and without it the first sentence is unfalsifiable.

**What the scan still cannot see**, and neither arm reports:

- A credential that is not one of these four shapes — a database URL with a password in it, a session
  cookie, a signed token. The pattern covers the providers this repository uses and nothing else.
- A credential in a file git does not track, which is correct for `.env` and wrong if somebody puts
  one in a lab directory and later removes the ignore rule.
- Anything outside the files entirely, which is part
  [2.2](2.2-the-channel-no-file-scanner-reads.md) and is where this repository actually does publish
  something.

## In production

**What a professional does.** Runs the scan on every commit rather than before every release, because
the cost of finding a committed secret rises with every commit that lands on top of it, and the fix
changes from *amend* to *rewrite the history and rotate the key*. A pre-publication scan is the last
line, not the only one.

**What degrades at scale.** History scanning is the part that stops being free. Sixty-nine commits of
`git log -p` is instant; a hundred thousand is minutes and grows monotonically, so teams scan the
history once, record the result, and scan only new commits after that — which is correct and means
the one-time full scan has to actually have happened.

**The failure that only shows with real traffic.** A secret that is valid and does not look like one.
Providers change key formats, internal services issue tokens with no recognisable prefix, and a
pattern-based scanner is by construction a list of the formats somebody thought of. The industrial
answer is entropy scoring on top of the patterns, which finds more and brings a false-positive rate
that part [3.2](../03-what-is-not-a-secret/3.2-the-highlighter.md) is about.

**The review comment a senior engineer leaves:** *"Good, and add the self-test to the pipeline next to
the scan. The day somebody 'tidies' that regex I want a red build, not a clean report."*

**The interview question:** *"Your secret scanner reports no findings. What do you do?"* The answer
that shows experience asks two things back — what shapes it knows, and when it last caught something
— because a scanner with no true positives in its history has not been shown to be a scanner.
