# 3.2 — The highlighter used on every line

## One-line answer

The same scanner, the same repository, one looser pattern: zero real hits becomes twelve thousand two
hundred and eighty-six lines to read by hand — and a report nobody finishes reading has exactly the
value of a report nobody ran.

## The story

The highlighter used on every line.

Somebody borrows a textbook before an exam and finds it already marked up by the previous owner.
Every line is highlighted. Whole pages of solid yellow, the definitions, the examples, the worked
answers, the paragraph explaining what the chapter will cover.

The previous owner was not careless. They were being thorough — reading with the pen in hand,
marking anything that might matter, and everything might matter. The problem is that a highlight
means *this line and not the others*, and once there are no others it has stopped meaning anything at
all. The book is now slightly harder to read than an unmarked one, because the yellow is noise on
top of the text.

## The idea in plain language

A scanner has two failure directions and only one of them is ever discussed.

**Missing things** — false negatives — is the one everybody worries about, and it is the reason
patterns get widened.

**Finding everything** — false positives — is the one that actually destroys scanners in practice,
because the destruction is social rather than technical. The tool still works. The output is still
correct. Nobody reads it, so nothing is found, and the tool's presence in the pipeline is evidence
that the risk is covered.

The two arms in the lab are the same code with a different pattern:

| Arm | Pattern | Real hits | Usable |
| --- | --- | --- | --- |
| default | four issuer formats — prefix and exact length | 0 | yes |
| `--naive` | the words key, secret, token, password | 12,286 | no |

Twelve thousand two hundred and eighty-six is not a number somebody triages. It is a number somebody
pipes to `wc -l`, notes has gone up since last month, and stops opening.

The precision comes from matching what the **issuer** guarantees rather than what the concept sounds
like. `AIza` followed by exactly thirty-five characters from a known alphabet is a Google API key or a
deliberate imitation of one. The word `key` is a word.

And the residue matters: after the shaped pattern, two hits remain, and both are teaching fixtures
that say so in their own text. The check counts them in a separate column instead of suppressing
them — a suppressed finding is invisible when the fixture stops being a fixture, and a separately
counted one is a number a reviewer can watch.

## Why Sutra needs it

Because this day adds seven checks to a repository that already runs a depth checker, a traceability
checker, a wiki staleness check, a linter and a test suite on every commit. Every one of them
competes for the same scarce thing, which is somebody's attention on a Tuesday.

A check that cries wolf does not merely waste that attention — it spends the credibility of the
checks next to it. Part [1.1](../01-what-a-review-is/1.1-a-check-that-can-fail.md) argued that a
check must be able to fail; this part is the other half of the same argument. **A check must also be
able to pass**, cleanly, most of the time, or its failures carry no information.

## The mechanism

The two patterns, side by side in the same file so the difference is a diff rather than a story:

```python
NAIVE = re.compile(r"(?i)key|secret|token|password")
```

**Line by line:**

- Four words and a case-insensitive flag. This is not a straw man — it is what a scanner looks like
  when it is written in the ten minutes before a release, and it is genuinely better than nothing at
  finding a variable called `SECRET_KEY` with a value beside it.
- `(?i)` doubles the reach: it now matches `Key`, `KEY`, `apiKey`, and the word *token* in every
  sentence this curriculum has written about tokenisation.
- There is no length constraint and no alphabet, so nothing about a match suggests a credential. The
  pattern describes a **topic**, and the repository is a curriculum about that topic.

The fixture column, which is the part most scanners get wrong:

```python
def is_fixture(line: str) -> bool:
    """A teaching fixture announces itself. A real credential never does."""
    return any(marker in line for marker in FIXTURE_MARKERS)
```

**Line by line:**

- The markers are `notarealkey`, `example.com`, `example.in`, `example.net` and one truncated key from
  a manifest — strings that appear *in the line itself*, so the classification travels with the
  evidence rather than living in a separate allowlist file that rots.
- A real credential cannot contain `notarealkey`, so this cannot suppress a true positive by
  accident. That property is what makes it safe; an allowlist of file paths would not have it.
- Fixtures are **counted**, not dropped. The report prints `known fixtures: 2` next to
  `real hits: 0`, so a reviewer sees that the classifier did something and can go and look.

Run both arms:

```bash

uv run python secrets.py --naive | tail -10; echo "exit: ${PIPESTATUS[0]}"
```

**Line by line:**

- `tail -10` because the interesting part is the count and the verdict; the sample above it is the
  first five of twelve thousand, which is itself the point.

Measured on 2026-09-07:

```text

  working tree, known fixtures: 9
```

Note where the first five hits are: skill documentation, a shell template, prose. Not one is a
credential and not one is close to being one. **Twelve thousand two hundred and eighty-one more
follow.**

Against the shaped pattern, the same repository:

```text
  working tree, real hits:      0
  working tree, known fixtures: 2
  every commit, real hits:      0
```

Same files, same code path, same scan. The only variable is what the pattern claims to know about
credentials.

## When it breaks

The failure is not that somebody reads twelve thousand lines badly. It is that the number becomes
furniture:

```text
1. a scanner is added and reports thousands of hits
2. nobody can triage that, so a threshold is set: alert if it grows
3. the growth threshold is tuned until the build stops going red
4. the number is now a property of repository size
5. a real credential is committed; the number goes up by one
6. one is inside the threshold
```

No step is wrong on its own and there is no error text anywhere, because the scanner is working
perfectly at every step. Step six is the whole cost, and the review that added the scanner in step one
would report the risk as covered.

The mirror failure is real too and this day is exposed to it. The shaped pattern knows four issuer
formats. A credential in a fifth format — a database URL with a password, a signed token with no
recognisable prefix, a provider this repository adds next year — produces zero hits and a clean
report, which is exactly what a working repository produces. Part
[2.1](../02-secrets/2.1-the-scan-that-found-nothing.md)'s self-test proves the four shapes are caught
and says nothing about a fifth, and no test can, because the missing pattern is by definition the one
nobody wrote.

**Precision and recall trade against each other and the trade cannot be avoided.** What can be
avoided is making it silently: the default arm here is a deliberate choice of precision, stated, with
its cost named in this section.

## In production

**What a professional does.** Measures the false-positive rate before deploying the scanner, and
treats a rate that a human cannot triage as a blocking defect in the scanner rather than a fact about
the repository. The operational number is not "findings" — it is findings per week that a person
actually looked at, and a tool that produces more than that has been configured wrong.

**What degrades at scale.** Both directions get worse simultaneously. More code means more false
positives from a loose pattern, and more variety means more true negatives from a tight one. The
industrial answer is layering — patterns for known issuers, entropy for unknown ones, and verification
by actually calling the provider to see whether the string is live — with each layer's output routed
to a different urgency.

**The failure that only shows with real traffic.** Alert routing outlives the person who tuned it. A
threshold set in a week when somebody was triaging carefully becomes a permanent property of the
pipeline, and two years later nobody knows why it is nine hundred rather than zero. The mitigation is
that a suppression carries a date and an owner — the same rule Day 82 arrived at for a quarantined
test, for the same reason.

**The review comment a senior engineer leaves:** *"Keep the tight pattern and add an entropy pass that
writes to a file instead of the build log. I want the wide net available when we are investigating
and out of the way when we are not."*

**The interview question:** *"How do you tune a secret scanner?"* The answer that shows experience
starts with the false-positive budget rather than with coverage — how many findings a week a person
will genuinely read — and then fits the patterns to that budget, because the alternative is a tool
whose output is a number nobody opens.
