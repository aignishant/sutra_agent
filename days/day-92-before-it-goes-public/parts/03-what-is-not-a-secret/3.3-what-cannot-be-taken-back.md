# 3.3 — What cannot be taken back

## One-line answer

Publishing is the one operation in this repository with no undo: fifty-one account-name lines can be
scrubbed today with a find-and-replace and sixty-nine commits of author metadata cannot be changed at
all without rewriting every hash — so the ordering of this day and Day 93 is the entire mitigation.

## The story

The invitation already posted.

Five hundred cards went to the printer, came back, were addressed over three evenings and went into
the post box on Sunday. On Monday somebody notices the venue's name is spelled wrong on every one of
them.

Everything before Sunday was cheap. A different card, a corrected proof, a reprint — annoying, an
afternoon, some money. Sunday evening it stops being an afternoon and becomes five hundred separate
conversations, most of which will not happen, and a wrong name that some people will carry to the
venue.

Nothing about the mistake got worse. The *reach* changed, once, at a moment nobody marked.

## The idea in plain language

Every finding in this day has a cost to fix, and the cost is a step function with the step at
publication.

| Finding | Fix before | Fix after |
| --- | --- | --- |
| account name in fifty-one lines | find-and-replace, one commit | same, plus every clone keeps the old blobs |
| `.env.example` missing a key | one line | one line |
| author identity on sixty-nine commits | rewrite history, one morning | not available in any real sense |
| a credential (none found here) | rewrite history and rotate | rotate immediately; assume compromised |

Two rows behave differently from the others and it is worth being exact about why.

**A file can be changed; a commit cannot.** Git's history is a chain of hashes where each commit's
identity includes its parent's. Changing anything in commit one — a file, an author name, a timestamp
— produces a different hash for commit one, therefore for commit two, therefore for all sixty-nine.
The operation exists, it is `git filter-repo` or an equivalent, and it produces a *different
repository* that happens to contain the same work.

**Before anyone has a copy, that is fine.** Afterwards, every fork, clone, mirror, archive link and
commit URL points into the old chain, and the old chain still exists wherever it was copied to. The
rewrite does not delete anything; it publishes a second version and asks everybody to prefer it.

So the real asymmetry is not about difficulty. It is that **before publication the repository has one
copy and you control it, and after publication it has an unknown number and you control one.**

Which makes the ordering of Phase 14 the mitigation, and not an accident: Day 92 is the review and
Day 93 is publication, in that order, and the plan put them that way round.

## Why Sutra needs it

Because five findings are open and each needs a decision *now* rather than a ticket. A ticket assumes
the cost of fixing is roughly constant over time, and for two of these it is not — it collapses to
zero available options the moment Day 93 runs.

And because the temptation on a day like this is to fix the easy ones and defer the rest. Deferring
the `.env.example` key costs nothing; deferring the author-identity question costs the ability to
answer it.

## The mechanism

The check reports both channels and their two different costs, which is why part
[2.2](../02-secrets/2.2-the-channel-no-file-scanner-reads.md) separates them rather than summing
them:

```python
    print("\n  real identities in file contents: 0")
    print(f"  real identities in commit metadata: {len(authors)}, on every commit")
    print("  the file scan is clean and the repository still publishes a person")
```

**Line by line:**

- Two numbers on two lines rather than a total. A total of one would be true and would hide that the
  one is in the channel that cannot be edited.
- `on every commit` rather than a count, because the count is the point: the identity is not in one
  place that could be patched, it is in the structure of all sixty-nine.
- The third line states the conclusion in words, so a reader who skims the numbers still gets the
  finding. Part [1.3](../01-what-a-review-is/1.3-the-checklist-that-answers-itself.md) is what
  happens when a report leaves that line out.

What the reversible fix looks like, from the account-name check:

```python
def scrub(line: str, placeholder: str) -> str:
    """What the line should have said: the shape of the path, without whose machine it was."""
    return line.replace(placeholder, "<user>")
```

**Line by line:**

- One `str.replace`. That is genuinely the whole fix for fifty-one lines across twenty-six files, and
  its cheapness is the argument for doing it before Sunday rather than after.
- It replaces with a placeholder rather than deleting, so the path still reads as a path and the
  teaching survives — part [3.1](3.1-fifty-one-lines.md) measured what is lost.
- There is no equivalent function for commit metadata anywhere in this lab, and the absence is the
  finding. You cannot write `scrub_author()` as a line of Python; it is `filter-repo` and a
  conversation with everybody who has a clone.

Run the check that shows both:

```bash
cd days/day-92-before-it-goes-public/lab
uv run python metadata.py | tail -4; echo "exit: ${PIPESTATUS[0]}"
```

**Line by line:**

- `tail -4` for the two-channel summary; the classification detail is in part 2.2.

Measured on 2026-09-07:

```text
  real identities in file contents: 0
  real identities in commit metadata: 1, on every commit
  the file scan is clean and the repository still publishes a person
exit: 1
```

**Zero in the channel that is easy to fix and one in the channel that is not.** That is the shape
worth carrying: the reversible findings tend to be the ones your tools already look at, because
tools are written for the things people fix.

## When it breaks

The sequence is short, ordinary, and ends somewhere with no options:

```text
1. a review finds five things before publication
2. three are cheap and get fixed in the same afternoon
3. two need a decision, so they become tickets
4. the repository is published on schedule
5. a fork appears within the week
6. ticket four is now "rewrite history and ask a stranger to re-fork"
7. ticket four is closed as won't-fix, having never been decided
```

Step seven is the failure and nobody performed it. The decision was made by step four, silently, by
default — which is the same shape as every other finding in this phase: **the outcome was determined
by an ordering nobody treated as a decision.**

There is no error text. Git will happily rewrite the history at step six and report success; what it
cannot do is reach the copies.

The mirror case is worth naming because it is the one that actually hurts people. If part
[2.1](../02-secrets/2.1-the-scan-that-found-nothing.md) *had* found a credential, the fix would not
have been a history rewrite at all — it would have been **rotate the key first, immediately**, and
then clean the history at leisure. A published credential must be assumed compromised the moment it
is published, because the rewrite is slower than a crawler. This repository did not have that
problem, and knowing what the answer would have been is the reason to have looked.

## In production

**What a professional does.** Sequences the irreversible operation last and treats the review as a
gate on it, which is exactly what Phase 14's day order encodes. The general rule is that any step
with no undo gets a checklist immediately before it and nothing after it in the same batch —
publication, a schema migration that drops a column, a broadcast to customers.

**What degrades at scale.** Reach grows faster than anybody tracks. One fork is a conversation; two
hundred is a broadcast nobody will read, and the number is unknowable from the inside. Teams that
operate at that size stop planning to retract and start planning to rotate, revoke and supersede —
mechanisms that work *forward* — because reaching backwards stops being possible long before anybody
notices it has.

**The failure that only shows with real traffic.** Third-party mirrors. Package indexes, archive
services, search caches and training corpora copy public repositories automatically and on their own
schedule, so "published" is not one event with one audience. By the time a rewrite is proposed, the
content exists in places that have no relationship with the project and no obligation to it.

**The review comment a senior engineer leaves:** *"Answer the author-identity question this week, not
in a ticket. Everything else on this list will still be fixable in March. That one will not be, and
the difference is a `git config` line and one morning."*

**The interview question:** *"You are about to open-source an internal repository. What do you do
first?"* The answer that shows experience sorts the findings by reversibility rather than by severity
— what can still be fixed afterwards, and what cannot — because the severe-but-reversible ones will
wait and the trivial-but-permanent ones will not.
