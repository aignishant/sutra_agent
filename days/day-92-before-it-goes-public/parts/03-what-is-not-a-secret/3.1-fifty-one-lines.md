# 3.1 — 💥 One account name, fifty-one lines

## One-line answer

This machine's account name appears fifty-one times across twenty-six tracked files in fifteen day
folders, every occurrence arrived inside a real pasted traceback, and pasting the traceback verbatim
is what Principle 10 requires — so two of this repository's own principles are in direct conflict and
the review is where that gets noticed.

## The story

💥 **The answer sheet handed in with the rough work on the back.**

🎬 **The scene.** An examination hall. The instruction was clear and everyone followed it: show your
working. So the working is there — the substitutions, the crossings-out, the second attempt at part
(b) that went wrong and was abandoned.

😬 **The naive fix.** Hand in what you were told to hand in. The rules said show the working and the
working is shown, in full, exactly as it happened. Nobody is doing anything other than what was
asked.

💥 **Why it fails.** On the back of the third sheet, in the margin, is a phone number a friend called
out during the break, and a doodle, and the beginning of a note about something else entirely. None
of it is the working. All of it was on the paper when the paper went in, because what was submitted
was the *sheet*, and the instruction was about the *answer*.

💡 **The insight.** **Verbatim is a property of the container, not of the content.** An instruction to
be complete and honest about one thing is also, silently, an instruction to publish everything that
travelled with it.

## The idea in plain language

CLAUDE.md contains this rule, and it is one of the reasons the day documents are worth reading:

> **Every mechanism has a matching "When it breaks"** with the **real error text**, verbatim — the
> traceback, the HTTP status, the JSON-RPC error body — not a paraphrase.

That rule has been followed. Eighty-nine days of real tracebacks, real 429 bodies, real validation
errors, pasted as they arrived. It is why the curriculum's failure sections are useful instead of
plausible.

A Python traceback contains file paths. On this machine those paths begin `C:\Users\<account>\`. So
does `pytest`'s `rootdir` line. So does the header `uv` prints when it resolves an environment.

Fifty-one lines, twenty-six files, fifteen day folders. Not one of them is a mistake. Every one is a
document doing exactly what the standards for these documents require.

That is what makes it a genuine finding rather than sloppiness, and it is why the fix is not "be
more careful". The two rules are:

| Principle | Says |
| --- | --- |
| 10 — fail honestly | paste the real error text, verbatim |
| 9 — secrets never touch git | and the repository goes public |

An account name is not a secret. It is not a credential, nothing can be signed with it and no scanner
in part [2.1](../02-secrets/2.1-the-scan-that-found-nothing.md) is looking for it. It is
**identifying information about a real person**, published on a machine-readable page, which is a
different category with its own reasons for mattering — and this repository's own house style already
takes that category seriously enough to forbid naming any person in prose.

The prose rule was enforced. The tracebacks were not, because nobody enforcing "name no person"
thought of `rootdir:`.

## Why Sutra needs it

Because Day 93 publishes all fifteen of those folders, and because this is the finding that makes the
review worth having: it was invisible to the check that was designed, invisible to the rule that was
written, and it is sitting in the most carefully reviewed prose in the repository.

And because the fix is genuinely a decision rather than a chore. Scrubbing the paths costs a
find-and-replace and slightly weakens the claim that the transcripts are verbatim. Not scrubbing them
publishes a home directory in fifty-one places. Both are defensible; only one of them is a decision
somebody made.

## The mechanism

The check derives its own target and refuses to print it:

```python
def find(name: str) -> list[Finding]:
    """Every tracked line containing this machine's account name."""
    out: list[Finding] = []
    for path in tracked():
        for number, line in enumerate(read(path).splitlines(), start=1):
            hits = line.count(name)
            if hits:
                out.append(Finding(path, number, hits, mask(line.strip()[:78], name)))
    return out
```

**Line by line:**

- `name` comes from `Path.home().name` in `_repo.py` — **derived, never written down.** This file
  does not contain the string it is hunting, so the checker is not itself an occurrence, and the same
  check works unchanged in anybody else's clone.
- `line.count(name)` rather than a boolean, because a single line can carry the path twice — a
  traceback frame and its source line, or two paths in one `pytest` header.
- `mask(...)` before the line is ever stored in a `Finding`. The masking happens at the point of
  capture rather than at the point of printing, so there is no code path on which an unmasked line
  reaches a buffer that something else might log.
- `[:78]` truncates before masking so the sample fits a terminal and a diff. The path shape survives
  and the rest of the line does not need to.

The report is counts, locations and one masked example — never the string:

```python
    print(f"searching {len(tracked())} tracked files for this machine's account name")
    print(f"the name is {len(name)} characters long and is not printed by this check")
```

**Line by line:**

- Printing the **length** is the compromise: it is enough for a reader to confirm the check found a
  real account name rather than an empty string, and not enough to be the account name.
- Saying out loud that the value is withheld matters more than it looks. A report that silently omits
  something reads as a report that found nothing there.
- This is not caution for its own sake: **this report is written into the repository it audits.**
  A check that printed its finding would add occurrence fifty-two.

Look at the sample. `rootdir:` is a `pytest` header — Day 23 pasted it because Day 23 is about how
`pytest` finds a test, and the header is the evidence. There is no version of that part that teaches
the same thing from a paraphrase.

The last line of the count block is the second half of the finding: **six other home directories**,
inherited from `legacy/` material mined into this repository. Those are other people's, from other
machines, and they arrived the same way.

## When it breaks

The scrub is one line and the check will show you what it produces:

```bash
uv run python identity.py --preview; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  what those lines would say after scrubbing:
      rootdir: C:\Users\<user>\OneDrive\Desktop\Projects\sutra

  the path still shows, and whose machine it was does not
  every one of these is a real pasted traceback, which is why they are here
```

The path shape survives, which is what the teaching needs — Day 23's point is *where* `pytest`
anchors, not whose disk it is. So the cost of scrubbing is smaller than it first looks, and the
honest way to describe the result is *"real traceback, one identifier replaced"* rather than
*"verbatim"*.

**Where it actually breaks** is the rule that produced it, and this repository cannot fix that by
editing fifty-one lines. The next real traceback pasted into the next day will carry the same path,
because the instruction still says verbatim and the machine still has a home directory. A one-time
scrub is a cleanup; the thing that keeps it clean is this check running on every commit, which is why
it belongs in `./m check` and not in a day.

And there is a failure the check cannot see. It searches for **this** machine's account name. A
contributor with a different account, whose traceback is pasted into a future day, produces the same
leak and this check reports zero — because `Path.home().name` on the reviewer's machine is not
theirs. The generic `HOME` regex in the same file is what finds those, and it is what reported the
six inherited ones.

## In production

**What a professional does.** Scrubs at the point of capture rather than at review time. If the
transcripts are pasted by hand, the scrub is a habit and habits do not survive; if they are captured
by a script, the script replaces the home directory with a placeholder as it writes, and the leak
cannot recur. The general form is that redaction belongs where data is produced, not where it is
published.

**What degrades at scale.** More contributors means more account names, and the check that looks for
one specific string stops working the moment the repository has two people in it. The pattern-based
version scales and brings false positives with it — `/home/opc` and `/home/site` are real strings in
this repository's `legacy/` tree and belong to nobody, which part
[3.2](3.2-the-highlighter.md) is about.

**The failure that only shows with real traffic.** Correlation. One home directory is a username. A
username plus a personal email from part
[2.2](../02-secrets/2.2-the-channel-no-file-scanner-reads.md)'s commit metadata plus a cloud path
plus a time-zone offset on every commit is a profile, and none of the four is a secret. Reviews that
classify by severity per finding miss this entirely, because the severity is in the join.

**The review comment a senior engineer leaves:** *"Scrub them, and say in the day format doc that
transcripts are verbatim except for the home directory. Then put the check in `./m check`, because
the next traceback somebody pastes will have the same path in it and I would rather find out on the
commit than on the launch."*

**The interview question:** *"What leaks from a public repository that is not a credential?"* The
answer that shows experience names the categories — identity, infrastructure, internal naming,
timing — and then gives an example that arrived through a process that was working correctly, because
the ones that arrived through carelessness are already fixed.
