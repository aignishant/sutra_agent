# 4.1 — What ADK offers

## One-line answer

ADK does have a built-in answer to *what wakes an agent from outside* —
`get_fast_api_app(..., trigger_sources=[...])` — and reading it off the **installed package** rather
than off a tutorial tells you two things a tutorial would not: the accepted values are exactly
`pubsub` and `eventarc`, and both are hosted cloud services that need a project and credentials, so
this curriculum parks them and lets the operating system do the waking instead.

## The story

The flat had an entryphone. It said so in the brochure — *video door entry* — and there is a handset
on the hall wall to prove it, cream plastic, screwed on at head height, with a curly cord.

It has never worked. Push the button downstairs and nothing happens up here, so every visitor still
rings your mobile and you still walk down two flights to open the door.

One evening you actually go and look at the handset instead of walking past it. There is no screen on
it. There is no camera lens either, just a small speaker grille, a button with a bell on it and a
button with a key on it. Whatever the brochure meant by *video*, the thing bolted to your wall is a
speaker and a door release, and that is the entire list of what it can do. You learned more in thirty
seconds of looking at the object than from the page that was written to sell it.

So you ring the letting agent, and that is where the second surprise is. The handset is real and the
wiring is real. Connecting it is a contract with the company that runs the building's door-entry
system, and it comes with a monthly charge per flat. The feature is not broken. It is switched off
because switching it on costs money every month, forever, and nobody has ever wanted it enough to
sign.

You go back to giving visitors your mobile number and walking down two flights. It is not elegant. It
also costs nothing, works today, and does not require anybody's signature.

## The idea in plain language

Everything on this day so far has assumed something starts the nightly job. Part
[3.3](../03-the-morning-after/3.3-nobody-notices-silence.md) leaned on that assumption hard: it
argued that a job which stops being triggered leaves no trace at all. So it is worth asking, plainly,
what the framework offers to do the triggering.

There are two families of answer, and they are genuinely different in kind.

A **clock** wakes the job at a fixed moment. Three in the morning, every morning. It knows nothing
about the world; it only knows the time. That is what section 5 and part
[4.2](4.2-the-scheduler-you-already-have.md) build on.

An **event** wakes the job when something happened. A file landed in a bucket, a row changed, a
message was published to a queue. The job runs *because of the thing*, not on a timetable that
happens to be near it.

ADK supports the second kind directly. Its web-server entry point, `get_fast_api_app`, takes a
`trigger_sources` argument, and the `adk api_server` command has a matching `--trigger_sources` flag.
Give it a source and the server grows an extra way in: not a person typing at a browser, but an
external system delivering an event.

That much a tutorial would tell you. The question this part is actually about is narrower and more
useful: **which sources, exactly, does the version installed in this project accept?** Not which ones
the documentation site describes, not which ones existed at some release, not which ones a blog post
listed. The ones the code in your `.venv` will take without raising.

That is the handset on the wall rather than the brochure, and it is Principle 8 — *never invent an
API; verify it against the package on the day you use it* — turned into a script you can run.

## Why Sutra needs it

Because ADK-51 is *ambient triggers*, and the honest way to close a concept ID about a framework
feature is to look at the feature, not to describe it from memory.

And because the answer decides the rest of the section. If ADK's triggers were something that runs on
a laptop with no account, this day would use them and part 4.2 would be a footnote. If they are not,
then §2's map is right to send you to the operating system's own scheduler and this part has to say
*why* in a way you could defend in a review — with the two accepted values on the page, read off the
package, dated.

There is a third reason, and it is the one that outlives this day. You will hit this exact question
on every framework you ever adopt: *what does this argument actually accept?* The technique below —
signature, then resolved type hints, then peel the annotation — works on any Python library, and it
costs one short script.

## The mechanism

The whole thing is `lab/triggers.py`, and it contacts nothing. It imports the function, looks at it,
and prints what it found.

Start with the two lines that get you the parameter:

```python
    sig = inspect.signature(get_fast_api_app)
    param = sig.parameters["trigger_sources"]
```

**Line by line:**

- `inspect.signature` is the standard library asking a function object to describe itself: its
  parameters, in order, with their defaults and their annotations. It reads the object that was
  imported, so it cannot be out of date with the code that will run.
- An **annotation** is the type written after the colon in a function definition —
  `def f(x: int)` annotates `x` with `int`. Python does not enforce annotations; they are metadata
  attached to the function, which is exactly why they are readable like this.
- `sig.parameters["trigger_sources"]` picks out the one parameter this part is about. If ADK ever
  renames or removes it, this line raises `KeyError` — a loud failure, which is the correct behaviour
  for a check whose job is to tell you the truth about the installed version.
- `param.default` is the other fact worth having, and the script prints it. It is `None`.

Now the part that matters. The obvious next move is to print `param.annotation` and be done. The
script does print it, and here is what comes out — not a type, a **string**:

```text
    annotation  list[Literal['pubsub', 'eventarc']] | None
```

It *looks* like the answer. A person reading the terminal has in fact got the answer. But it is a
line of text: there is nothing in it a program can ask a question of, no way to iterate the values,
no way to compare them against a list you care about. The reason is one line at the top of ADK's
module:

```python
from __future__ import annotations
```

**Line by line:**

- This directive tells Python not to evaluate the annotations in this file. Every annotation in the
  module is stored as the source text you wrote, lazily, and only turned into a real object if
  somebody asks for it.
- It exists for good reasons — it makes forward references work and it avoids paying for imports the
  running code never needs — and it is extremely common in modern libraries. `triggers.py` itself
  starts with the same line.
- The consequence for anyone inspecting the module from outside is the one above: `param.annotation`
  is `str`, not a type.

So the script asks for the resolution explicitly, and that is the interesting block:

```python
    # The module uses `from __future__ import annotations`, so `param.annotation` is the *string*
    # "list[Literal['pubsub', 'eventarc']] | None". Resolving it is what turns a string back into
    # the type, and it is the difference between reading the docs and reading the package.
    hints = typing.get_type_hints(get_fast_api_app)
    inner = typing.get_args(hints["trigger_sources"])[0]
    sources = typing.get_args(typing.get_args(inner)[0])
```

**Line by line:**

- `typing.get_type_hints(get_fast_api_app)` takes those stored strings and evaluates them again, in
  the namespace of the module that defined the function. That namespace is the point: `Literal` and
  every other name in the annotation mean what they meant *inside ADK's file*, not what they might
  happen to mean inside yours. What comes back is a dictionary of real typing objects. This is why
  the two steps are separate — `inspect.signature` gets you the parameter, `get_type_hints` gets you
  its type.
- `hints["trigger_sources"]` is now `list[Literal['pubsub', 'eventarc']] | None` as an object. It has
  three layers, and the next three calls peel them one at a time.
- `typing.get_args(...)` is the standard way to look inside a parameterised type: hand it
  `list[int]` and it gives you `(int,)`. Peel one, on the outermost layer, is the union — the
  `| None` — so `get_args` returns `(list[Literal[...]], NoneType)` and `[0]` takes the half that is
  not `None`.
- Peel two is `typing.get_args(inner)[0]`, which opens the `list[...]` and hands back what the list
  holds: `Literal['pubsub', 'eventarc']`. A **`Literal`** is a type whose members are specific
  *values* rather than a shape — `Literal['pubsub', 'eventarc']` means *this string, or that string,
  and no other*. It is the strongest statement a signature can make about an allowed set, and it is
  precisely the fact this part is trying to extract.
- Peel three is the outer `typing.get_args(...)`, applied to that `Literal`, which returns the values
  themselves: `('pubsub', 'eventarc')`. Three calls, three layers of one annotation — union, then
  list, then literal. Nothing clever is happening; each call removes exactly one pair of brackets.
- The comment sitting above these lines is doing real work and is worth keeping in your own version
  of this script. Six months from now the three nested `get_args` calls look like a puzzle, and the
  comment is the sentence that explains why they are not one call.

Run it:

```bash
cd days/day-73-ambient-agents/lab
uv run python triggers.py
```

**Line by line:**

- `cd` into the lab first, because `triggers.py` is a plain script rather than an installed module.
- `uv run` executes it inside the project's own environment, so the version it reports is the version
  this repository actually pins — not whatever Python happens to be first on your `PATH`.
- The script takes no arguments and makes no network call. Everything it prints comes from the
  package on disk.

Measured on 2026-09-06:

```text
google-adk, installed: 2.7.1

  get_fast_api_app(..., trigger_sources=...)
    annotation  list[Literal['pubsub', 'eventarc']] | None
    default     None
    accepted    ['pubsub', 'eventarc']

  every accepted source is a hosted cloud service:
    pubsub     requires a project and credentials -> parked (Addendum 02)
    eventarc   requires a project and credentials -> parked (Addendum 02)

  what this day uses instead: the operating system's scheduler, which needs no account.
```

Two findings, and they are of different kinds.

**The default is `None`.** The feature is off unless you ask for it. That is the right default for
something whose whole purpose is to open a door into your process from outside: a server that grew an
external entry point because you upgraded a package would be a security incident with a release note
attached. Nothing about the deployment changes until the argument is passed.

**The accepted set is exactly two, and both cost money.** This is where the entryphone is real and
the contract is monthly:

| Source | What it is | What it needs before it can wake anything |
| --- | --- | --- |
| `pubsub` | a hosted publish/subscribe message queue | a cloud project, a topic, a subscription, credentials |
| `eventarc` | a hosted event router that turns other services' events into deliveries | a cloud project, a trigger, an identity to run as, credentials |

🅿️ **Both are parked.** Addendum 02 is the rule — never write code that requires a billing account —
and these are exactly what it is about. They are awareness-level here: you should be able to say in
an interview that ADK's built-in triggers are `pubsub` and `eventarc`, that both are hosted, and why
this project did not use them. You will not build with them on this day. Part
[4.2](4.2-the-scheduler-you-already-have.md) is the free thing bolted to the wall you already own.

## When it breaks

**This tells you what the version accepts, and nothing about how to use it.** That is the honest
limit and it is a sharp one. Two string values are a *shape*, not a manual. Everything that would
actually be needed to run on one of these triggers is unverified by this part, and there is no way to
verify it here, because doing so requires the account this project does not have. At minimum you
would still have to establish: what the delivered payload looks like and how the event body is
handed to your agent; how the server authenticates the delivery, so that not everybody who finds the
URL can wake your job; and what happens on a duplicate delivery, which the next section is entirely
about. This document has checked none of those three. Saying so is the point — a page that implied
otherwise would be a page that invented an API.

**`get_type_hints` can fail where `inspect.signature` does not.** Resolving a string annotation means
evaluating it, and evaluation needs every name in it to be importable at runtime. The classic case
is a module that imports a name only under `if TYPE_CHECKING:` — a block that type checkers read and
the interpreter skips — and then uses that name in an annotation. `inspect.signature` is perfectly
happy, because it hands back text. `get_type_hints` raises `NameError`, because the name genuinely
does not exist while the program is running. If your version of this script ever stops working, that
is the first thing to check, and the workaround is to fall back to reading `param.annotation` as text
and to say in your notes that you did.

**A pinned version is a fact with a date on it.** Everything above is what `google-adk==2.7.1`
accepts on 2026-09-06. It is not what ADK accepts. When the pin moves, the correct response is not to
trust this page — it is to run the script again, look at the two lines it prints, and write down the
new version and the new list with the new date. That is the whole reason the answer is a script and
not a sentence.

## In production

**What an event buys, and what it charges for it.** A clock is a guess about when work will be
needed, and it is almost always wrong in one of two directions: it fires before the thing it was
waiting for, and does nothing useful, or it fires long after, and the work sat there. An event-driven
trigger removes the guess — the job runs because something happened, at the moment it happened. That
is a real gain and it is why hosted triggers exist.

The bill is a change in what your handler must survive. Message delivery systems of this kind
guarantee **at-least-once delivery**: they promise every event arrives, and they explicitly do *not*
promise it arrives only once. A network hiccup between the delivery and your acknowledgement, and the
same event is delivered again — correctly, by design. So the handler has to be safe to run twice on
the same event, which is a property with a name and a paper behind it. Read
[01 — Idempotence Is Not a Medical Condition](../../papers/01-idempotence.md) after the parts; its
demo is the arithmetic of getting this wrong, with a recorded total of 28 against a truth of 10 and
nothing anywhere reporting an error.

Note that a clock does not exempt you. Part
[2.3](../02-when-it-dies-at-three-am/2.3-two-runs-at-once.md) already showed two scheduled runs alive
at once, silently overwriting each other. The event trigger does not create the problem; it makes it
routine rather than occasional.

**An ambient trigger is an entry point, and the payload is untrusted input.** This is the part that
gets skipped. A `trigger_sources` deployment means something outside your process decides when your
agent runs and hands it the material to work on. Day 66 built the injection threat model for exactly
this shape — content that arrives from outside and reaches a model — and Day 67 built the guardrail
callbacks that check it on the way in. Every line of both applies here, with one aggravating factor:
there is nobody watching. An interactive user who sees an agent behave strangely stops it. At three
in the morning the event body goes to the model, the model calls tools, and the first person to read
about it reads the digest. Whatever inspection you would run on a user's message, run on an event
body, and run it before the model sees it.

**The review comment a senior engineer leaves:** *"Good — I like that the accepted values came out of
the installed package rather than a doc page, and I want that script kept in the repo so it re-runs
when we bump the pin. Two things before anyone turns this on for real. First, the default is `None`
and it stays `None` in every environment except the one we deliberately configure; I don't want an
upgrade to open a delivery endpoint on a service that didn't have one yesterday. Second, if we ever
move off the OS scheduler onto a hosted trigger, the handler has to be idempotent before the trigger
is created, not after — at-least-once means duplicates are normal traffic, and I'd rather fix that in
a design review than in an incident. And the event body is untrusted input; it goes through the same
checks a user message does."*

**The interview question:** *"How do you find out what a framework's argument actually accepts?"* An
answer that shows the work: *"I read the installed package rather than the docs. For ADK's ambient
triggers I took `inspect.signature(get_fast_api_app)` and pulled out the `trigger_sources` parameter,
but its annotation came back as a string — the module uses `from __future__ import annotations`, so
every annotation in it is stored as source text and never evaluated. So I had to resolve it:
`typing.get_type_hints` re-evaluates those strings in the defining module's namespace and gives you
real typing objects back. Then it was three `get_args` calls to peel the annotation apart — the
`| None` union, then the `list`, then the `Literal` — and the values fell out: exactly `pubsub` and
`eventarc`, with a default of `None`. That last bit is the whole reason I did it this way. Printing
the annotation would have shown me a string that looks like the answer; resolving it gave me a list I
could actually check things against. And it told me something a tutorial wouldn't have led with —
both accepted sources are hosted services needing a project and credentials, which is why we
scheduled the job with the OS instead. It's one version, on one date; when we bump the pin we run the
script again."*

## Check yourself

```bash
cd days/day-73-ambient-agents/lab
uv run python triggers.py
uv run python -c "import inspect; from google.adk.cli.fast_api import get_fast_api_app as f; print(repr(inspect.signature(f).parameters['trigger_sources'].annotation))"
```

The second command prints `param.annotation` with `repr`, so the quotation marks are visible. Look at
them. That is the finding of this part in one line: the thing that looked like a type is a `str`.

Two exercises.

**One.** Re-run `triggers.py` against whatever ADK version you have installed today, and write down
three things: the version it reported, the accepted values it printed, and the date you ran it. Put
them somewhere you will find them again. That record — not this page — is the answer, because this
page is a measurement of `2.7.1` on 2026-09-06 and yours may not be.

**Two.** Pick any other function in a library this project already depends on, and get one of its
annotations resolved the same way: signature, then `get_type_hints`, then peel. If it comes back as a
plain type with nothing to peel, say why. If `get_type_hints` raises, read the `NameError` and work
out which name it could not find.

**Out loud, without scrolling up:** *why does printing a parameter's annotation sometimes give you a
string instead of a type, and what do you do about it?*
