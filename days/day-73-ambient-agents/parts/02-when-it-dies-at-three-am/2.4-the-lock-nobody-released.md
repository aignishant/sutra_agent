# 2.4 — The lock nobody released

## One-line answer

The lock that fixed part [2.3](2.3-two-runs-at-once.md) is taken in one line and released in none, so
a single run that dies while holding it refuses **every** run after it — measured: the second
`take_lock()` returns `False`, the file is still on disk, and `grep` finds exactly two mentions of the
lock in the whole file, one to name it and one to create it.

## The story

The small meeting room in the office is booked with a paper sheet on the door, ruled into half-hours.

Somebody writes their name against the whole of Thursday afternoon. Then they go home at lunchtime
with a temperature, and Thursday afternoon happens without them.

The room stays empty and stays unusable. Everyone who tries the door reads the sheet, sees a name
against every slot, and walks away — which is the sheet working exactly as designed. It was never
supposed to know whether the person turned up. It only knows what was written on it, and nothing on
the door writes *"actually, they never came"*.

By Friday somebody finally crosses it out. Not because the system detected anything, but because a
person got annoyed enough to overrule a piece of paper.

## The idea in plain language

Part 2.3 introduced a **lock**: a marker one process creates so that a second process can see the work
is already being done. It worked, and the run that lost was refused rather than allowed to overwrite a
newer index.

What part 2.3 did not say is that taking a lock and releasing it are two different problems, and only
the first one is easy.

Taking a lock is one line, and it is atomic — the operating system guarantees that exactly one of two
racing processes creates the file. Releasing it is a promise that some **later** code will run, and
that promise is exactly what a crash breaks. The stronger the failure, the less likely the release:

| How the run ends | Does a `finally:` block run? | Is the lock released? |
| --- | --- | --- |
| finishes normally | yes | yes |
| raises an exception | yes | yes |
| killed with a signal the process can handle | only if a handler was installed | usually not |
| killed outright, or the machine loses power | no | **no** |

The last row is the one that matters, because it is the row part
[2.1](2.1-the-run-that-dies.md) was about. An ambient job's characteristic failure is being killed
without warning, and that is precisely the failure a `finally:` cannot help with.

So the naive lock has a property worth stating baldly: **it converts one bad night into every
subsequent night.** Before the lock, a crash cost you one run. After it, a crash costs you every run
until a person notices — and part [3.3](../03-the-morning-after/3.3-nobody-notices-silence.md) is
about how long that takes when the failure mode is *nothing happening*.

That does not mean the lock was a mistake. It means a lock is not finished when it is taken.

## Why Sutra needs it

Because the build brief in the hub's §4 asks you to write `take_lock()` and — separately — to decide
how it is released, and that second `TODO(me)` is genuinely open. There is no answer this curriculum
can hand you, because the right one depends on what your job does when it is skipped.

And because the gate's fourth check only asks whether `take_lock` **exists**. It cannot ask whether
you thought about release, which makes this one of the places where a green check is not evidence.
Day 72 part 5.2 made the same point about a check that can only read a function signature: a gate
verifies that somebody had to decide, never that they decided well.

## The mechanism

The whole of the lab's lock lifecycle is visible in two `grep` hits:

```bash
cd days/day-73-ambient-agents/lab
grep -n "unlink\|remove\|finally\|LOCK" lock.py; echo "grep exit: $?"
```

**Line by line:**

- The four patterns are the four ways a lock could be released: `unlink` and `remove` delete a file,
  `finally` is the block that would do it on the way out, and `LOCK` catches every mention of the lock
  path itself so nothing can hide.
- `echo "grep exit: $?"` prints grep's exit code — `0` here, because it did find matches. What matters
  is *which* matches, not how many.

Measured on 2026-09-06:

```text
20:LOCK = _state.STATE / "nightly.lock"
31:        with LOCK.open("x", encoding="utf-8") as handle:
grep exit: 0
```

Two lines. One names the file and one creates it. There is no `unlink`, no `remove`, and no `finally`
anywhere in the module — the lock is taken and then simply left, and nothing in the code was ever going
to clean it up.

Now watch what that costs, with the lock file starting from a clean slate:

```bash
uv run python -c "
from lock import LOCK, take_lock

LOCK.unlink(missing_ok=True)
print('first run  takes the lock ', take_lock())
print('second run takes the lock', take_lock())
print('lock file still on disk  ', LOCK.is_file())
"
```

**Line by line:**

- `LOCK.unlink(missing_ok=True)` deletes any lock left by an earlier experiment, so the first call
  below starts from a genuinely unlocked state. `missing_ok=True` means "do not raise if it was
  already absent", which is the right spelling for a cleanup step.
- The first `take_lock()` stands for last night's run, which took the lock and then died.
- The second `take_lock()` stands for tonight's run. Nothing in between released anything, because
  nothing in the module can.
- `LOCK.is_file()` is asked *after* the refusal, because the point is not that the second call failed —
  it is that the file causing the failure is still sitting there, and will still be sitting there
  tomorrow.

Measured on 2026-09-06:

```text
first run  takes the lock  True
second run takes the lock False
lock file still on disk   True
```

`False`, and the file is still there. Tomorrow's run gets `False`. The run after that gets `False`.
The meeting room is booked by somebody who went home, and the sheet has no way of finding out.

One honest note about the lab, because it would otherwise look like this problem does not exist.
Running `lock.py --lock` twice in a row works fine — and it works for a reason that is not a release
strategy. `lock.py`'s `main()` calls `_state.fresh()`, which deletes **every** file under `state/`,
lock included, before it does anything:

```python
def fresh() -> None:
    """Delete every artefact and start again, so a run is reproducible."""
    if STATE.exists():
        for path in STATE.iterdir():
            path.unlink()
    else:
        STATE.mkdir(parents=True)
```

**Line by line:**

- `for path in STATE.iterdir(): path.unlink()` removes everything in the state directory without
  looking at what it is. The lock is a file in that directory, so it goes too.
- That is a **test fixture**, not a lock release. It exists so that a demonstration starts from a known
  state, and it does the one thing a real system must never do: destroy a lock it does not hold.
- If you ever find yourself writing this in production — clearing a lock at startup so the job can get
  going — you have not released the lock, you have removed the mechanism. Every run will then take the
  lock successfully, including the one that should have been refused, and part 2.3's failure is back
  with a lock file on top of it.

## When it breaks

There are three usual answers and each one breaks differently. Choosing between them is the
`TODO(me)`, and the honest position is that none of them is free.

**Release in a `finally:`.** The obvious one, and it handles the ordinary cases — a normal finish, an
exception, a stage raising `StageFailed`. It does nothing for the case ambient jobs actually die of:
the process being killed outright, or the machine going away. It is worth doing anyway, because it
turns the common failures into non-events and leaves only the rare one, but shipping it and believing
the problem is solved is how a stale lock arrives six months later with nobody remembering why.

**Write the owner into the lock and check whether it is alive.** Instead of `"held"`, write the process
id, and on `FileExistsError` read it and ask the operating system whether that process still exists. If
it does not, the lock is stale and may be taken. This is the strongest local answer and it has a real
hole: process ids are reused. A dead run's id can belong to something entirely unrelated by the time
you check, in which case you conclude the lock is live and refuse for no reason — or, worse, the check
races with a genuinely live run. It is also **local to one machine**: a process id means nothing to a
second container.

**Give the lock an expiry — a lease.** Write a timestamp, and treat a lock older than some agreed span
as abandoned. This is what real coordination services do, and it is the only one of the three that
works across machines. Its failure is the interesting one: the expiry has to be longer than the
slowest legitimate run, and you do not know what that is until the night it happens. Set it too short
and the lease expires under a run that is still working, which hands you two concurrent runs *and* a
lock that says everything is fine. Set it too long and a crash costs you that many nights of nothing.

There is a fourth answer that is not a lock at all, and it deserves naming because it is often the
right one: make the stages safe to run twice and stop caring. If two runs can both re-index without
harming each other, the lock becomes an optimisation rather than a correctness requirement. That is
the property the [paper](../../papers/01-idempotence.md) at the end of this day is about, and it is
why it is worth reading after this section rather than before.

## In production

**What a professional writes down next to the lock.** Which of the four answers was chosen and what
its failure mode is. A lock with no comment is a lock nobody will dare touch, and the person who finds
it stale at three in the morning needs to know within one screen whether it is safe to delete. *"Lease,
expires after N; if you are reading this because the job has not run, check the run log for a row with
no matching completion before you clear it"* is worth more than any amount of defensive code.

**What degrades at scale.** A file lock is a statement about one filesystem. Move the job into two
containers, or onto a second machine for redundancy, and both take the lock and both proceed — with no
error, because each one genuinely created a file that did not exist. This is the same class of failure
as part 2.3's silent overwrite, one layer up: the mechanism does not fail, it simply stops being about
what you thought it was about. The replacement is a lease held in something both machines can see, and
the cost is a dependency the single-machine version did not have.

**What monitoring this needs, since the failure is silent.** A stale lock produces no error and no
output — the job simply declines and exits. So the thing to alert on is not an error rate but the
**age of the lock file**, or equivalently the gap since the last successful run in the log. Day 72 part
5.2 arrived at the same conclusion from a different direction: when the failure mode is a system
quietly doing nothing, the signal has to be something you actively look for rather than something that
arrives.

**The review comment a senior engineer leaves:** *"Take the lock, yes, but tell me how it comes off.
A `finally:` covers the boring failures and none of the ones that will actually happen to a scheduled
job. I'd put a timestamp in the lock file and treat it as a lease with an expiry comfortably longer
than the worst run we've seen, and I'd log the age of the lock when we refuse — otherwise the failure
is a process that exits zero and writes nothing, which is indistinguishable from not being scheduled
at all. And take `fresh()` out of anything that runs in production. Deleting the state directory at
startup is fine in a demo and is a way to silently disable the lock everywhere else."*

**The interview question:** *"You added a lock file so two jobs can't run at once. What's the next
question I should ask you?"* An honest answer: *"How it gets released. Taking it is atomic and easy;
releasing it is a promise that later code runs, and the failure ambient jobs actually have is being
killed without warning, which is exactly when later code doesn't run. So the naive version turns one
crash into every subsequent night failing, silently — the job exits cleanly, writes nothing, and looks
identical to not being scheduled. There are three usual fixes and they all cost something. A `finally:`
handles the ordinary cases and not the important one. Writing the process id and checking liveness
works on one machine and breaks when ids are reused or when you add a second machine. A lease with an
expiry is the one that scales, and its risk is that the expiry has to be longer than the slowest
legitimate run, which you don't know yet — too short and you get two concurrent runs believing they're
alone. The fourth option is to make the work idempotent so the lock is an optimisation rather than a
correctness requirement, and that's usually the one I'd argue for."*
