# 2.2 — Stages you can iterate

## One-line answer

Resume is a **skip**, and a skip is only expressible if the stage list is **data you can iterate** —
`STAGES` as a tuple of `(name, callable)` and `DONE` as a map from name to the file that proves it
finished, so the same single `if` skips **one** stage after a death at `evals` and **two** after a
death at `digest`, without being told which.

## The story

You are filling in a long application form on a website. Six pages: your details, your address, your
previous address, the reason for applying, the documents, and then a page that just says *check your
answers*.

You get to page four. The phone rings, you wander off, and by the time you come back the tab has
reloaded itself and you are staring at a login screen. That sinking feeling is familiar: four pages
of typing, gone.

You log back in and the site opens on page four. Pages one to three are filled in, in your own words,
exactly as you left them. Nothing was lost.

It worked because of something you barely noticed at the time. Every page had a **Save and continue**
button at the bottom, and pressing it sent that page to the site before the next one loaded. Your
answers were not sitting in the browser waiting for the end. They were already stored, one page at a
time, somewhere that did not die when your tab did.

And notice what the site did when you came back. It did not remember you — it had no memory of you at
all, because as far as it was concerned you were a brand new visitor. It **looked** at what it had
stored, found three completed pages, and sent you to the fourth. The other site you used last month,
the one that put the whole form on a single page, could not have done that for you no matter how
sympathetic its designers were. There was nothing stored to look at.

## The idea in plain language

Part [2.1](2.1-the-run-that-dies.md) showed the nightly job dying part-way through and leaving half
its artefacts behind. This part is the other half of that: what it takes to **pick up from there**
instead of starting again.

The word for that is **resume** — running the job a second time so that it does the work the dead run
did not do, and does not repeat the work it did.

Say the word out loud and it sounds like a big feature. It is not. Resume is a **skip**: for each
stage, *is this one already done? then don't run it.* That is one question and one branch.

But you can only ask that question if there is something to ask it about. Consider the two ways the
three stages could be written.

- **As three calls in a row.** `reindex()`, then `run_evals()`, then `write_digest()`, one line under
  the next. This is the single-page form. It runs correctly, top to bottom, and there is no way to
  say *start at the second one* without editing the file — because "the second one" is not a thing
  the program can refer to. There is no list. There are three statements, and a statement is not a
  value you can loop over, count, index, or skip.
- **As a list of stages.** Each stage is a pair: a **name** and the **function** that does it. Now
  "the second one" exists. It has a name you can print, a function you can call or not call, and a
  position in a sequence you can walk.

The second shape costs one line more than the first and buys the whole of this part. That is the
whole idea: **make the stage list data, and resume becomes an `if` inside a loop.**

The remaining question is what the `if` asks. It cannot ask a variable, because the variable that
knew belonged to the run that died. It has to ask the same thing the application-form site asked:
*what is stored?* Each stage's output is a file, so the question is *does that file exist?*

## Why Sutra needs it

The build brief in the hub's §4 asks for exactly this, and it is worth reading the reason it gives
rather than the instruction: `STAGES` as data *because* resume is a skip over that list, and
`run(*, resume)` as an explicit flag *because* a job that cannot resume redoes finished work every
time it is retried.

That second cost is the one that bites in this repository. Sutra's nightly job re-indexes an archive
and then runs the **full** eval set. Under a scheduler with a retry policy, a job that dies at the
digest stage and cannot resume will re-run every eval case from the beginning, and the currency this
repository spends is requests per day against a free tier. Redoing finished work is not merely
inelegant here; it is the largest recurring bill the job has, paid twice.

There is also a correctness reason, and it is the one that will not show up on a quota page. Part
[1.2](../01-the-agent-nobody-watches/1.2-three-stages-in-a-forced-order.md) established that each
stage reads the file the previous stage wrote, and that the order is enforced by a check inside each
stage rather than by the order of the lines. Those checks are exactly what makes a partial re-run
safe: a resumed run that starts at `evals` finds `index.json` on disk, and the guard that would have
refused is satisfied. The forced order and the skip are the same design seen from two ends.

## The mechanism

Two module-level definitions carry the entire structure:

```python
STAGES = (("reindex", reindex), ("evals", run_evals), ("digest", write_digest))
DONE = {"reindex": _state.INDEX, "evals": _state.EVALS, "digest": _state.DIGEST}
```

**Line by line:**

- `STAGES` is a **tuple of pairs**, and each pair is `(name, callable)` — a string for the log line
  and the function itself, not its name as text. Storing the function means the loop can call it
  with `stage()`; storing a string would mean looking it up by name at call time, which is one more
  thing that can be wrong.
- The name is in the data rather than derived from `stage.__name__`, because two of them differ:
  the stage is called `evals` in the log, the run record and `DONE`, while the function is
  `run_evals`. The name a person reads is a label the job chooses, not an accident of what the
  function was called in Python.
- A **tuple**, not a list, because the stage list is fixed at import and the order is load-bearing
  (part [1.2](../01-the-agent-nobody-watches/1.2-three-stages-in-a-forced-order.md)). A tuple cannot
  be appended to by accident from somewhere else in the process.
- `DONE` maps each stage name to **the file that proves that stage finished**. Not a boolean, not a
  counter — a `Path`. The artefact *is* the evidence, so there is nothing extra to keep in step with
  it.
- `DONE` and `STAGES` are two structures that have to agree on their names. That is a genuine seam
  and *When it breaks* returns to it.

The flag that decides which kind of run this is comes first, before anything is written:

```python
    resume = "--resume" in sys.argv
    if not resume:
        _state.fresh()
```

**Line by line:**

- `resume = "--resume" in sys.argv` reads the flag once and passes it down, so there is exactly one
  place in the file that decides what kind of run this is.
- `if not resume: _state.fresh()` is the line that makes a normal run start from nothing.
  `_state.fresh()` deletes every artefact under `state/`, so the loop below finds no files and skips
  nothing.
- It matters that this is the *default* arm. Without it, every run would find last night's artefacts
  and silently resume — which sounds harmless and is a considerably worse default: an index built
  from an old archive would satisfy the check for ever, and the nightly job would never rebuild
  anything again. A job that quietly stops doing its work is part
  [3.3](../03-the-morning-after/3.3-nobody-notices-silence.md)'s subject.
- It is the **new application** button on the form site. Starting again has to be possible, and it
  has to be what happens when you did not ask to continue.

And here is resume, in full:

```python
    completed: list[str] = []
    for name, stage in STAGES:
        if resume and DONE[name].is_file():
            print(f"  skip     {name:<9} already on disk")
            completed.append(name)
            continue
```

**Line by line:**

- `for name, stage in STAGES` unpacks each pair as it goes. This loop is the difference between the
  two shapes described above: it exists at all only because the stages are values.
- `resume and DONE[name].is_file()` is the whole feature, and the order of the two halves is
  deliberate. `resume` is checked first so that a normal run never even asks the filesystem, which
  is what keeps the default honest.
- `DONE[name].is_file()` asks **the filesystem**, not a variable. This is the sentence to take away.
  A variable holding "reindex finished" was set by the process that died and went with it; the file
  it wrote did not. The only state that survives a killed process is the state that was written
  down, so the only question a resumed run can usefully ask is a question about the disk.
- `completed.append(name)` happens on the **skip** branch too, and this is the part that is easy to
  get wrong. The run record written at the end lists which stages are complete as of this run
  finishing. If a skipped stage were left out, the log for a successful resumed run would claim the
  index is not built — which is false, and worse than useless, because part
  [3.1](../03-the-morning-after/3.1-the-run-log.md) is about that log being the thing you read when
  you were not there. The line to be careful about is *"this stage is done"*, which is true, rather
  than *"this run did it"*, which is not.
- `{name:<9}` left-pads the name to nine columns so `skip`, `ok` and `DIED` lines form readable
  columns in a terminal at three in the morning. Cosmetic, and worth the character count.
- `continue` moves to the next stage without calling `stage()`. Nothing is undone, nothing is
  checked, nothing is repaired — the stage is simply not run.

Now run it. First, die at the **second** stage and then resume:

```bash
cd days/day-73-ambient-agents/lab
uv run python nightly.py --fail-at evals; echo "exit: $?"
uv run python nightly.py --resume; echo "exit: $?"
```

**Line by line:**

- `--fail-at evals` is the ablation part [2.1](2.1-the-run-that-dies.md) introduced: the job stops at
  the named stage the way a killed process would, having already written what the earlier stages
  wrote.
- The second command carries `--resume` and nothing else. In particular it does **not** name a stage
  to start from — the job works that out from the disk, which is the point.
- `echo "exit: $?"` prints the exit status of the command just before it. A scheduler reads that
  number and nothing else, so it is worth seeing.
- The two commands are separated by `;` rather than `&&`, because the first one is *expected* to fail
  and `&&` would stop there.

Measured on 2026-09-06. The first command:

```text
nightly run, started 2026-09-06T03:00:00+00:00

  ok       reindex   rows=5
  DIED     evals     the process was killed part-way through this stage

  the run log records where it stopped; nothing pretends this run finished
exit: 1
```

The second:

```text
nightly run, started 2026-09-06T03:00:00+00:00  (resume)

  skip     reindex   already on disk
  ok       evals     passed=3 total=5
  ok       digest    failing=2

  index    written
  evals    written
  digest   written
exit: 0
```

One stage skipped, two run, and the three artefacts are all present. Now move the death one stage
later:

```bash
uv run python nightly.py --fail-at digest; echo "exit: $?"
uv run python nightly.py --resume; echo "exit: $?"
```

**Line by line:**

- Only one token changed from the first sequence: `evals` became `digest`. The resume command is
  **byte-for-byte identical** to the one above, which is the argument this part is making.
- The first command does not need `--resume` even though artefacts from the previous sequence are on
  disk, because `if not resume: _state.fresh()` clears them. Each sequence starts from nothing.

The first command:

```text
nightly run, started 2026-09-06T03:00:00+00:00

  ok       reindex   rows=5
  ok       evals     passed=3 total=5
  DIED     digest    the process was killed part-way through this stage

  the run log records where it stopped; nothing pretends this run finished
exit: 1
```

The second:

```text
nightly run, started 2026-09-06T03:00:00+00:00  (resume)

  skip     reindex   already on disk
  skip     evals     already on disk
  ok       digest    failing=2

  index    written
  evals    written
  digest   written
exit: 0
```

**Two** skip lines this time, from the same one `if`, with no code changed and no argument telling it
where to start. That is the finding: the number of stages skipped is not something anybody wrote
down. It fell out of walking a list and asking the filesystem a question per item.

| Run died at | Artefacts already on disk | Skipped on resume | Actually run on resume |
| --- | --- | --- | --- |
| `reindex` | none | 0 | reindex, evals, digest |
| `evals` | `index.json` | 1 — reindex | evals, digest |
| `digest` | `index.json`, `evals.json` | 2 — reindex, evals | digest |

The middle and bottom rows are the two sequences above, measured. The top row follows from the same
branch: a run that died in the first stage wrote nothing, so `DONE["reindex"].is_file()` is false and
the resumed run behaves exactly like a fresh one. Note that the table has three rows and the code has
one `if`. Three hard-coded calls would need three cases, and adding a fourth stage would need a
fourth; the loop needs none, because the cases were never enumerated in the first place.

Skipping is also only *safe* because of a property the stages happen to have: running `reindex` twice
produces the same index as running it once. That property has a name and a paper, and it is the day's
reading — [`papers/01-idempotence.md`](../../papers/01-idempotence.md). Read it last, after the job
is built.

## When it breaks

**The check is existence, not correctness.** `DONE[name].is_file()` asks one question — *is there a
file at this path?* — and it is satisfied by any file at all. A zero-byte `index.json` left behind by
a process killed mid-write is a file. An `index.json` containing half a JSON object is a file. In
both cases the resumed run prints `skip     reindex   already on disk`, moves on, and the *next*
stage is the one that fails, holding a broken index that it is not responsible for and cannot
explain. The guard part 1.2 built into `run_evals` does not save you here, because that guard reads:

```python
        raise StageFailed("evals: no index on disk - reindex has not run")
```

It fires when the index is **absent**. A truncated index is present, so this message never appears
and what surfaces instead is a `json.JSONDecodeError` from inside `_state.read` — a parse error
pointing at a file the reader did not write, several stages away from the run that actually broke it.
Writing to a temporary path and renaming it into place makes the marker atomic, and atomicity is Day
60's subject rather than this day's; `_state.write` says so in its own docstring.

**The check is not freshness either.** A perfectly valid `index.json` from three nights ago is a
file. If something upstream causes `_state.fresh()` not to run — a wrapper script that always passes
`--resume`, a scheduler that was configured for retries and never for a clean nightly run — then
every stage skips, every run exits `0`, the digest is regenerated from stale scores, and there is no
error anywhere. That is precisely the shape of failure part
[3.3](../03-the-morning-after/3.3-nobody-notices-silence.md) is about, and it is the reason this
part's default arm is `fresh()` rather than resume.

**`STAGES` and `DONE` are two structures that must agree.** Adding a fourth stage to `STAGES` and
forgetting `DONE` gives a `KeyError` on the new name the first time a resumed run reaches it — which
is to say, on the first *retry*, potentially long after the change was merged and reviewed. A single
structure carrying the marker path alongside the callable would remove the seam, at the cost of a
slightly heavier definition. The lab keeps them separate because two short lines read better in a
teaching document; a real job should not.

**Resume assumes there is only one runner.** Everything above asks the filesystem what has been done,
and quietly assumes that whatever it finds was put there by a run that is no longer alive. A second
run starting while the first is still working sees half-written evidence of a live process and treats
it as the leftovers of a dead one. That is part [2.3](2.3-two-runs-at-once.md), and it is next
because it is the failure this mechanism creates.

## In production

**The marker stops being a bare file.** At any real scale the question *is this stage done?* is asked
about a specific attempt of a specific scheduled run, not about the job in general, and the answer
lives in a row keyed by a **run identifier** — a database row, an object in a bucket, an entry in a
workflow engine's own store. The shape does not change: it is still a name, a callable and a durable
marker per stage. What changes is that two runs of the same job on the same night no longer share one
set of paths, which is most of what the lock in part [2.3](2.3-two-runs-at-once.md) is standing in
for.

**The marker records what was produced, not just that something was.** A production completion record
carries the run identifier, when the stage finished, and a hash or a row count of the output. That
turns three of the weaknesses above into checks: the resumed run can confirm the marker belongs to
this run rather than last week's, and can confirm the artefact matches the marker rather than merely
existing next to it. It costs a few extra fields on a record that is being written anyway.

**Every skip is a decision worth logging as one.** A resumed run that prints `skip` has chosen not to
do work. That line belongs in the run log with a reason attached, because the first question after a
bad morning is *which of last night's stages actually executed?* and the second is *why did the rest
not?* Getting `completed.append(name)` right on the skip branch is the small version of this; the
production version says which run produced each completed stage.

**Stage lists grow into graphs.** Three stages in a fixed order is the simplest possible task graph.
Real ambient jobs end up with stages that could run in parallel and stages that depend on two others,
and that is the point at which the hand-rolled tuple gets replaced by a workflow engine. The value of
having written the tuple first is Principle 4: the engine's `depends_on` and its "already succeeded,
skipping" log line are then a convenience rather than a mystery, because you have written both.

**The review comment a senior engineer leaves:** *"The list-of-pairs is right and the skip branch is
right — including appending to `completed` on the skip, which people get wrong and which makes the
run log lie. Two things before this goes near a scheduler. First, `is_file()` is an existence check
and we will eventually resume onto a half-written artefact, so write to a temp path and rename, and
put a row count or a hash in the completion marker so a resume can tell a good file from a file.
Second, `DONE` and `STAGES` are two lists that have to stay in step, and the day they don't we get a
`KeyError` on a retry rather than on a normal run, which means we find out during an incident. Fold
the marker path into the stage definition."*

**The interview question:** *"Your nightly job dies half-way. How does the next run know where to
start?"* An honest answer: *"It doesn't know, and that's the design — it works it out from disk.
Every stage writes one artefact, and there's a map from stage name to the file that proves that stage
finished. The stages are a list of name-and-function pairs rather than three calls in a row, so
resume is one `if` inside the loop: if we're resuming and the marker file exists, skip. I measured
it — killing it during the eval stage and re-running skips one stage, killing it during the digest
stage and re-running skips two, and the resume command is identical in both cases because nothing
tells it where to start. Two things I'd flag. The default has to be to start clean, or a stale
artefact never gets rebuilt and the job silently stops doing its job. And the check is existence, not
correctness — a truncated file counts as done — so in production the marker carries a hash and the
run id, and the artefact is written to a temp path and renamed. All of this only works because the
stages are idempotent; a stage that appends rather than replaces cannot be re-run safely at all."*
