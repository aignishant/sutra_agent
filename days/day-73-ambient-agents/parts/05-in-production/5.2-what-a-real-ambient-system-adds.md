# 5.2 — What a real ambient system adds

## One-line answer

The lab is a correct small nightly job, and the distance between it and one you would put on a
schedule is not vague "hardening" — it is a **list of nine specific things**, each cheap to add on
the day the job is written and expensive on the day it is needed, and two of them are deliberately
parked by this curriculum rather than forgotten.

## The story

Somebody at the market asks you to mind their stall for a fortnight while they are away, and they
leave you a folder.

The folder is good. It has the float for the till, the days the bread comes and the days it does
not, the phone number of the man who fixes the awning, and a note saying the card reader has to be
plugged in before it will wake up. You read it once, run the stall on the Monday, and nothing goes
wrong.

On the Sunday night the freezer is still humming. Nobody told you it has to be switched off at the
wall on Sundays, because the compressor sticks otherwise. The person who wrote the folder has done
it every Sunday for six years without once thinking of it as a step. It is not in the folder because
it was never a decision — it is just what they do, in the same movement as locking up.

You do not find out from the folder. You find out on Monday, from the smell.

## The idea in plain language

The lab works. Run it and it re-indexes, scores five eval cases and writes a digest; kill it in the
middle and re-run it and it picks up where it stopped. Nothing in it is wrong.

But "it works" and "I would put this on a schedule" are two different claims, and the gap between
them is a **list**. Not a mood, not a quality bar, not "make it more robust" — an enumerable set of
items, each of which you can point at, cost, and decide about. Here is the whole of it for this job.

| What the lab has | What a real one adds | What it costs |
| --- | --- | --- |
| a stage's output written straight to its final path with `write_text` | an **atomic write** — write a temporary file, then rename it into place | one extra line, and a temp file to clean up |
| a lock that is taken and never released | a **lease with an expiry**, or a liveness check on the holder | a clock you have to trust, and a number you cannot know yet (part [2.4](../02-when-it-dies-at-three-am/2.4-the-lock-nobody-released.md)) |
| artefacts with no date anywhere in them | a **run id and a timestamp** in every artefact | nothing at all, and it is the highest-value line in the build brief (part [3.3](../03-the-morning-after/3.3-nobody-notices-silence.md)) |
| one run-log row, appended when the run stops | a row written when the run **starts**, matched or updated when it ends | a second write, and a schema that can express "started, never finished" |
| stages that happen to be safe to repeat | **idempotency stated per stage**, and an idempotency key wherever an operation names a change | thought, mostly — the [paper](../../papers/01-idempotence.md) is the whole answer |
| whatever `print` puts on standard output | **structured logs** carrying the run id, so one night's lines can be pulled out of a year of them | a logging setup, and somewhere to put the output |
| nothing watching the job at all | an external **staleness check**, on a different trigger | a second thing to run, which has to fail independently (part [3.3](../03-the-morning-after/3.3-nobody-notices-silence.md)) |
| a job that only reads and writes its own files | a decision about whether it may **act** — send, close, delete — and an approval path if it may | the whole of Day 63's approval gate, at a time nobody is awake |
| a job that can only run for tonight | **backfill**: running it deliberately for a night it missed | an argument for the date, and every stage having to accept it |

Three terms in that table are used here for the first time, so they get definitions before anything
else happens.

An **atomic write** is a write that another process can only ever observe as not-done or done, never
as half-done. A **structured log** is a log line written as fields — a run id, a stage name, an
outcome — rather than as an English sentence, so that a machine can filter a year of them without
guessing at the punctuation. And a **backfill** is a deliberate run of the job *for* a date other
than today, done to fill a gap it left.

Two of these deserve more than a table row, because both look trivial and neither is.

## Why Sutra needs it

Because the hub's §4 hands you a build brief for `sutra/nightly.py` and the brief is not this list.
The brief asks for stages-as-data, a resume flag, a lock, an honest digest and a timestamp. It is
what the day teaches, and it is smaller than what you would schedule — deliberately, because a build
brief that contained all nine of these would be a week of work with the teaching buried inside it.

So this part is the page missing from the folder. Everything in the table is something the person
who wrote the job would have known and might never have written down, and the entire point of
writing it as a list is that a list can be argued with. A reader who finishes this day believing the
lab is production-shaped has learned the mechanism and inherited the freezer.

## The mechanism

There is no new code today. The mechanism is two items from the table, argued properly.

### The write that can be interrupted

The lab writes every JSON artefact through one helper, and that helper says out loud what it is not
doing:

```python
def write(path: Path, data: object) -> None:
    """Write a JSON artefact. Small enough that atomicity is Day 60's subject, not this day's."""
    STATE.mkdir(parents=True, exist_ok=True)
    path.write_text(json.dumps(data, indent=2), encoding="utf-8")
```

**Line by line:**

- The docstring is an honest admission, not a decoration: *"Small enough that atomicity is Day 60's
  subject, not this day's."* Day 60 is where durable writes were the subject; here the artefacts are
  a few kilobytes and the day's teaching is elsewhere, so the helper is the simple version and says
  so. A deferred explanation with an address is allowed; a silent one is not.
- `STATE.mkdir(parents=True, exist_ok=True)` makes the state directory if it is missing.
  `exist_ok=True` means a second call is not an error, which is the same property the rest of this
  job is built on.
- `json.dumps(data, indent=2)` builds the **entire** text in memory first. That matters: at this
  point nothing has touched the disk, and if the process died here the old file would still be
  intact.
- `path.write_text(...)` is the line the argument is about. It opens the final path, truncates it to
  zero bytes, and then writes. Between the truncation and the last byte there is a window in which
  the file on disk exists, has exactly the right name, and contains nothing or half of a JSON
  document.

Now put an ambient job's characteristic failure into that window. Part
[2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md) established that this job's normal
way of dying is being killed outright, without warning, with nobody watching. Land that kill inside
`write_text` and the morning looks like this: `index.json` is present, its modification time is
recent, and `_state.read` on it either raises a `json.JSONDecodeError` or — if the truncation
happened to land somewhere valid — returns an index with three tickets in it instead of five.

The second outcome is the one worth being frightened of. A file that fails to parse is a loud
failure and you will fix it. A file that parses to a smaller truth is part
[2.3](../02-when-it-dies-at-three-am/2.3-two-runs-at-once.md)'s silent overwrite arriving by a
different route, and the evals stage will happily score against it and the digest will happily
report the score.

The fix is one extra line and it is worth understanding why it works rather than memorising it:

```python
tmp = path.with_suffix(path.suffix + ".tmp")
tmp.write_text(json.dumps(data, indent=2), encoding="utf-8")
tmp.replace(path)
```

**Line by line:**

- `path.with_suffix(path.suffix + ".tmp")` builds a sibling name — `index.json.tmp` — in the **same
  directory**. Same directory is not a style choice; it is the precondition for the last line, and
  a temporary file in the system temp directory would break it.
- `tmp.write_text(...)` does all the dangerous work under a name nothing reads. A kill here leaves a
  half-written `index.json.tmp` and an untouched `index.json`. The next run finds the old artefact
  exactly as it was, which is the worst outcome this design permits.
- `tmp.replace(path)` is the whole mechanism. `Path.replace` is a rename, and a rename within one
  filesystem is **atomic**: the directory entry points either at the old file or at the new one, and
  there is no instant at which it points at half of either. That is the property you want, and it is
  a genuinely different property from "tidier". You are not making the write faster or less likely
  to be interrupted — the interruption is just as likely. You are moving the interruption to a place
  where it cannot be observed.
- What it costs is the row in the table: one extra line, and a `.tmp` file left behind on the nights
  it does die, which something eventually has to sweep up.

system call, which is not something a document can paste honestly. `TODO(me)`: build the window


**Line by line:**

- The first command produces a complete, correct set of artefacts, so the starting point is a good
  index rather than an absent one.
- The middle command is a **simulation** of the window, not the real thing: it re-reads the index,
  re-serialises it, and writes back only the first 120 characters. That is what a kill part-way
  through `write_text` leaves — a file that exists, has the right name, and stops in the middle.
- The third command asks `_state.read` to load it. Read the error it gives you carefully, and then
  ask the more uncomfortable question: what would have happened if the truncation had landed on a
  closing brace instead of in the middle of a word.

### The job that can only run for tonight

The second item is `backfill`, and it is the one teams meet at the worst possible moment.

A nightly job runs on a date and it runs **for** a date, and in a first version those are the same
value, so nobody separates them. Then a night is missed — the machine was down, the scheduler was
reconfigured, part 2.4's stale lock refused four nights in a row — and somebody asks the reasonable
question: *can you run Tuesday's?* At that point the two dates have to come apart, and the date is
by then hard-coded or implicit in a dozen places: the artefact filenames, the archive query that
decides which tickets are "new", the run-log row, the digest's heading.

The lab has this bug in the most visible form it could possibly take:

```python
started = datetime(2026, 9, 6, 3, 0, tzinfo=UTC).isoformat()
```

**Line by line:**

- Part [3.3](../03-the-morning-after/3.3-nobody-notices-silence.md) already read this line for a
  different reason — that a constant date makes staleness undetectable. The backfill reading is a
  separate problem with the same line.
- Here the objection is not that the value is frozen but that it is **produced inside `main()` at
  all**. Nothing can tell this job which night to work on, because the job decides for itself and
  tells nobody. There is no argument to pass and no parameter to override.
- Fixing the staleness bug by swapping the constant for `datetime.now(UTC)` does not fix this one.
  It makes the date real and leaves it just as un-passable — the job now knows what night it is and
  still cannot be told to do a different one.

The shape of the fix is small and its reach is not. One value, `run_for`, is decided at the edge of
the program — defaulting to tonight, overridable by an argument — and then threaded through every
stage that has an opinion about time. Each stage has to accept it: `reindex` because "the archive"
is really "the archive as of some moment", the run log because a row has to record which night it
was for as well as when it ran, and the digest because a digest headed with the wrong date is worse
than one with no date. That threading is the cost, and it is small while the job is small and
unpleasant afterwards, which is exactly why it belongs in the first version.

## When it breaks

**The shape of this list is the interesting thing about it.** Every item is cheap on the day the job
is written and expensive on the day it is needed. Atomic writes are one line now and a corrupted
index at three in the morning later. A `run_for` argument is a parameter now and a rewrite later. A
run id in every artefact is free now and an unanswerable question later.

And yet almost no first version has them — including this one. That is not laziness and it is not a
skills gap. It is that **each item is individually skippable and only collectively necessary**. Take
any single row of the table on its own and the argument for skipping it is genuinely good: the
artefacts are small, the job runs on one machine, the failure is rare, the team is two people who
would notice. Every one of those arguments is true. What is false is the conclusion you reach by
making all nine of them in a row, which is a job that works perfectly and cannot be operated.

The person who wrote the folder for the stall was not careless. Each thing they left out was, on its
own, obviously not worth writing down.

**Two items are parked by this curriculum, and parked is not the same as forgotten.**

🅿️ **Hosted triggers.** Part [4.1](../04-what-wakes-it/4.1-what-adk-offers.md) read
`trigger_sources` off the installed ADK and found exactly two accepted values, `pubsub` and
`eventarc`, both of which are hosted cloud services needing a project and credentials. Addendum 02
parks anything requiring a billing account, so this repository's job is woken by the operating
system's own scheduler. Be able to describe the difference in an interview: a hosted trigger gives
you delivery guarantees, retries and a record of every invocation, and the local scheduler gives you
none of those and costs nothing. **Build it when** the job's failure to run has a consequence
somebody will pay for.

🅿️ **Anything else with a bill attached.** A managed log store for the structured logs, a hosted
dead-man's-switch service for the staleness check, a coordination service holding the lease from
part 2.4. All three are the standard production answers and all three are out of scope for the same
reason. The honest position is to name them, say what they replace, and write down the condition
that would make them worth the money — never to pretend a file lock on one machine is the same thing
as a lease in a coordination service.

**The remaining risk, once you have the list, is treating it as a checklist.** Nine ticks do not
make a job you should schedule. The row that decides most is the one about acting: a job that only
reads and writes its own files can be wrong and cost you a morning, and a job that may send, close
or delete can be wrong and cost you something you cannot take back. Day 63's approval gate answers
that question for an agent with a person in front of it. An ambient agent asks the same question at
a time when there is nobody to approve, which is why the answer has to be decided in advance and
written into the job rather than into a runbook.

## In production

**The on-call question is who gets woken, by what, and for which failure — and the useful move is to
answer the last part first.** Most of this day's failures should wake nobody.

| This day's failure | Does it need a person *now*? |
| --- | --- |
| a stage dies part-way (part [2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md)) | no — the artefacts are stale, not wrong, and a resumed run in the morning fixes it |
| two runs collide and the index loses a ticket (part [2.3](../02-when-it-dies-at-three-am/2.3-two-runs-at-once.md)) | no, but it needs a person, and today nothing tells one |
| a stale lock refusing every run (part [2.4](../02-when-it-dies-at-three-am/2.4-the-lock-nobody-released.md)) | not on the first night; yes by the third |
| a digest that reassures (part [3.2](../03-the-morning-after/3.2-the-digest-that-reassures.md)) | no — and that is precisely why it is dangerous, because nothing will ever alert on it |
| the job stops being triggered (part [3.3](../03-the-morning-after/3.3-nobody-notices-silence.md)) | not now, but the staleness check has to reach somebody eventually |
| the job acted — sent, closed or deleted — and was wrong | **yes**, and this is the only row where the answer is yes |

The distinction the table is drawing is between *"this needs a person"* and *"this needs a person
**now**"*, and almost every mistake in on-call design comes from collapsing the two. The correct
response to a failed nightly re-index is to look at it over breakfast. Nothing downstream of it is
serving traffic; the worst case is that the digest is a day old and the index is missing a ticket,
and a person woken to fix that at four in the morning fixes it worse than the same person would at
nine. Waking somebody has a cost that is paid every time and a benefit that is only paid when the
thing was urgent.

The rule that falls out of the table is short enough to write on the job itself: **wake somebody
when the job did something, not when it failed to do something.** A run that died did nothing. A run
that was refused by a lock did nothing. A run that sent four emails to the wrong list is the only
row above where the situation gets worse while everybody sleeps.

Everything in the "needs a person, not now" column still needs a route to a person — a queue read in
the morning, a channel somebody checks, a line in the digest. The failure mode of a system with only
one severity is not that the wrong things page; it is that everything below the paging threshold
falls on the floor, and part 3.3's silence problem is that failure at its purest.

**The review comment a senior engineer leaves:** *"The job's fine. Before it goes on a schedule I
want three of these and I don't much mind about the rest. Make the artefact writes atomic —
write-then-rename, same directory — because the failure we actually have is being killed and I'd
rather that leave yesterday's index than half of tonight's. Pass the date in rather than computing
it inside main; the first time we miss a night somebody will ask for a backfill and I don't want
that to be a refactor. And put a run id in every artefact and every log line, because the first real
incident on this job is going to start with somebody asking which run wrote this file. The lease, the
structured logging and the staleness check are all real and I'll take tickets for them. What I want
in writing today is the acting question: this job only reads and writes its own files, and the day
somebody adds a stage that sends anything, it needs an approval path and this review happens again."*

**The interview question:** *"You've written a nightly job that works. What's left before you'd
schedule it?"* An honest answer: *"I'd answer with a list rather than 'make it robust', because the
gap is specific. Atomic writes first — write to a temp file in the same directory and rename, since
a rename within one filesystem is atomic, so a kill mid-write leaves yesterday's file instead of
half of tonight's. Then a run id and a real timestamp in every artefact, which is free and is what
lets you tell a fresh digest from one that's a fortnight old. Then the run log records a start as
well as a finish, so 'started and never came back' is a state you can query rather than an absence.
Then the lock needs a release story — a lease with an expiry, not just a file, because nothing
releases a lock when the process is killed and one crash otherwise refuses every subsequent night.
Then structured logs carrying the run id, and one staleness check running somewhere else on a
different trigger, because the job can't detect its own failure to run. Then backfill: pass the date
the job is running for as an argument, separately from the date it's running on, or the first missed
night becomes a refactor. And the one that isn't code — whether the job may act. Ours only reads and
writes its own files, and that's the reason it's safe to schedule without an approval path. The
moment a stage sends or deletes anything, that decision has to be made deliberately, because there's
nobody awake to approve it. Last thing I'd say is what wakes somebody: almost none of these should
page. A failed nightly re-index is a morning problem. The only one I'd get out of bed for is the job
having done something wrong rather than having failed to do something."*

## Check yourself

```bash
cd days/day-73-ambient-agents/lab
grep -n "write_text\|started = \|now(" _state.py nightly.py; echo "grep exit: $?"
```

Read the hits. For each `write_text`, say what is on disk if the process dies inside it. For the
`started` line, say what you would have to change to run this job for last Tuesday, and count the
other places that change would reach.

Then take the nine-row table and cut it to three. Not the three that are easiest — the three you
would insist on before this job goes on a schedule, with a sentence each saying what goes wrong
without it. If your three do not include one that costs nothing, look again at the timestamp row.

Then, for the two you left out that you feel worst about, write the condition that would move them
back in. A condition somebody can check beats an intention nobody revisits.

Finally, run the day's eval and read what it is actually asking for:

```bash
uv run python gate.py; echo "exit: $?"
```

Six red, because `sutra/nightly.py` is the build brief. Now compare those six checks against this
part's table. Every one of them is a row from the *lab has* column — a stage list, a resume flag, a
lock, a digest that names failures — and **not one of them is from the "what a real one adds"
column**. A gate can check that somebody wrote a function; it cannot check that they decided how the
lock is released, or that the digest carries a date. That gap is why this part is prose rather than
another check, and it is worth remembering the next time a green gate feels like evidence. Part
[5.1](5.1-what-a-nightly-job-spends.md) makes the same point about a budget: the number nobody wrote
down is not caught by anything.

**Out loud, without scrolling up:** why does write-then-rename fix anything, given that the write in
the middle of it is exactly as likely to be interrupted as before?

The day has built a job that three stages deep can be killed, re-run, and come out with the right
artefacts. Every mechanism in it — the resume that skips a finished stage, the retry a scheduler
performs without asking, the run that has to be safe to repeat — stands on one property that has so
far only been assumed. It has a name, it has a 2012 essay, and switching it off in that essay's demo
records a total of 28 where the truth is 10, with nothing anywhere reporting an error.
