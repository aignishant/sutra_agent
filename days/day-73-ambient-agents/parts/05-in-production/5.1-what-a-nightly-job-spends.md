# 5.1 — What a nightly job spends

## One-line answer

A nightly job is the largest **recurring** quota commitment a system makes and a scheduler commits to
it rather than a person, so it has to be priced **before** it is scheduled, in requests per day — and
the lab's `passed=3 total=5` cost zero requests only because its evals never call a model.

## The story

A standing order goes out of an account at some point in the small hours of the first of the month.
Nobody decides anything that morning. Nobody looks. The bank moves the money because somebody, once,
months ago, filled in a form and signed it, and the arrangement has been quietly renewing itself ever
since.

The decision took a minute and was made in a good mood, on a day when the balance was healthy. It is
paid for on every first of the month afterwards, at an hour when nobody is awake to weigh it up
against anything else.

And it is only ever noticed from the far end. The card is declined at lunchtime. Not because lunch
was expensive — lunch was four pounds — but because the money had already left before anyone was
awake, and the balance the card was checked against was the balance *after* a commitment made in
another season.

The bill was not the surprise. The **recurrence** was the surprise.

## The idea in plain language

Two limits govern every free-tier model lane, and they fail on different timescales:

- **RPM** — **requests per minute**. How fast you may go. Exceed it and you are refused now, and the
  window reopens shortly.
- **RPD** — **requests per day**. How much you may use in total. Exceed it and you are refused for the
  rest of the day, and no amount of waiting inside the day gets it back.

A nightly job is dangerous to RPD specifically. A person running an agent by hand spends quota in
proportion to their attention, and attention runs out. A scheduler has no attention to run out of. It
fires on a clock — part [4.2](../04-what-wakes-it/4.2-the-scheduler-you-already-have.md) is exactly
this: a dial on the wall that has done its job every night since somebody set it — and it will spend
the same amount tonight, tomorrow night and on the night nobody remembers the job exists.

So the number to write down is not "what one run costs". It is **requests per day**, standing, next to
the schedule. That is the standing order. The eval set is the amount on the form.

## Why Sutra needs it

Because Addendum 02 denominates every budget in RPM and RPD per provider rather than in money, and
because the nightly job is the first thing in this repository that spends quota **without a person
present to stop it**. Every earlier day's spend ended when you closed the terminal.

And because this lab is quietly cheating, which a part called *In production* has to say out loud. The
job's evals stage does not call a model at all. Look at what it scores:

```python
EVALSET: list[tuple[str, str, bool]] = [
    ("signin", "cannot sign in", True),
    ("billing", "invoice pdf blank", True),
    ("export", "csv export slow", True),
    ("sso", "sso loop mobile", False),
    ("webhooks", "duplicate orders", False),
]
```

**Line by line:**

- Each tuple is `(name, query, expected)`: a case name, the query to run, and whether a hit is the
  right answer. The last two expect `False`, which is how the lab keeps two cases failing on purpose.
- Five cases. Five is small enough to read, and small enough that its cost is invisible — which is the
  trap this part exists to name.
- The type is a plain `list[tuple[...]]` rather than a class, because on this day the eval set is data
  the job iterates, not a thing with behaviour. Day 79 formalises it.

And here is the scoring, which is where the model would have been:

```python
        wanted = set(query.split())
        hit = any(wanted & set(terms) for terms in index.values())
```

**Line by line:**

- `set(query.split())` turns the query into a bag of words. No model, no network, no key.
- `wanted & set(terms)` is a set intersection: do any of the query's words appear in this indexed
  document's words? `any(...)` says yes if any document matches.
- This is a stand-in. A real eval asks a model the question and checks the answer, which is one
  provider request per case — and that single substitution is the whole subject of this part.

## The mechanism

Run the job and read the second line of the output:

```bash
cd days/day-73-ambient-agents/lab
uv run python nightly.py
```

**Line by line:**

- No flags, so no `--resume` and no `--fail-at`: a clean run from an empty `state/` directory.
- Nothing here reads an API key, because nothing here contacts a provider.

Measured on 2026-09-06:

```text
nightly run, started 2026-09-06T03:00:00+00:00

  ok       reindex   rows=5
  ok       evals     passed=3 total=5
  ok       digest    failing=2

  index    written
  evals    written
  digest   written
```

`passed=3 total=5` cost **zero requests**. That line is honest about what it measured and silent about
what it did not spend, and the real version of that one line is everything below.

Now the lanes to price it against. These four are the ones Day 70's quota router carries, recorded on
**Day 70 (2026-09-05)**:

| Lane | Model string | RPM | RPD |
| --- | --- | --- | --- |
| gemini | `gemini-2.5-flash` | 10 | 250 |
| groq | `groq/llama-3.3-70b-versatile` | 30 | 1000 |
| openrouter | `openrouter/deepseek/deepseek-r1:free` | 20 | 50 |
| ollama (local) | `ollama_chat/llama3.1:8b` | 6 | 100000 |

Read that table as **recorded on a date**, not as a fact about the world. Free rosters move — models
are withdrawn, limits are cut, whole tiers are retired — and the correct response to any of these
numbers being load-bearing in your design is to look them up again against the provider's own page and
write down the date you looked.

The arithmetic. Everything in this table is **derived** from the numbers above, not measured, and the
working is shown so you can redo it with your own figures:

| What is running | Working | Requests per night | Against the lane's RPD |
| --- | --- | --- | --- |
| the lab's eval set, one call per case | 5 × 1 | 5 | 5 ÷ 250 = **2%** of gemini's day; 5 ÷ 50 = **10%** of openrouter's |
| a real eval set, one call per case | 200 × 1 | 200 | 200 ÷ 250 = **80%** of gemini's day; 200 ÷ 50 = **4×** openrouter's whole day |
| the same set with a grader | 200 × 2 | 400 | 400 ÷ 250 = **160%** of gemini's day |

Three readings of that table, in order of how badly they hurt.

**Five is free and two hundred is not, and nothing in between announces the change.** Two hundred
cases is not a large eval set; it is a modest one for a system anybody depends on. At 5 requests a
night the job is trivial against every lane. At 200 it is the dominant consumer of the day.

**On openrouter the job does not degrade — it cannot run.** 200 requests against a 50 RPD limit is
four times the entire daily quota. There is no hour of the night that is better, no retry that helps,
and no partial success worth having: the run gets a quarter of the way through, is refused for the
rest of the day, and produces a digest built on 50 of 200 cases. Every night. For ever.

**On gemini the job runs and eats the day.** 80% of 250 spent at the scheduled hour leaves **50
requests** for everything the desk does after breakfast — every ad-hoc question, every demo, every
manual run of anything else in this repository. The job succeeded. The day it was scheduled on did
not.

Then the multiplier nobody prices in. **Model-as-judge** — sometimes written *LLM-as-a-judge* — is the
common pattern where a second model call reads the first call's answer and grades it, because "is this
answer right?" is often not something a string comparison can decide. It is a reasonable thing to
want, and it doubles the job: 200 × 2 = 400, which is 160% of gemini's whole day. Adding a grader is
one line of code and it takes the job from *expensive* to *impossible* on the lane it was fitting on
yesterday.

RPM bites separately, and it bites the wall clock rather than the budget. 200 requests against
gemini's **10 RPM** cannot be delivered in fewer than 200 ÷ 10 = **20 of the provider's one-minute
windows**, whatever the machine does. That is a property of the system, not of you: it means a job scheduled to
finish before anyone arrives has to be scheduled with that runtime in mind, and it means a lock held
for the length of the run (part [2.3](../02-when-it-dies-at-three-am/2.3-two-runs-at-once.md)) is held
for a meaningful stretch rather than an instant.

## When it breaks

**A bad night costs several times the nominal budget.** Day 72's retry ladder is the mechanism: a call
that is refused is retried with a growing wait, up to a budget of attempts. That is correct behaviour
and it is also a multiplier on the number you wrote down. A run that retries each failing call up to
six times spends, on a night when the provider is refusing, several times what its calm-night estimate
said — and Day 70's counting rule is why: the provider counts **attempts**, not successes. So the
night the quota is tightest is precisely the night the job asks for the most of it. A budget computed
from happy-path runs is a budget computed from the case that does not matter.

**The eval set is a multiplier that the person adding a case does not feel.** This is the standing
order again, in its exact shape. Somebody fixes a bug, adds the regression case, and the diff is three
lines and obviously good. At the moment of writing it costs nothing. At the moment of scheduling it is
permanent: it is +1 request per night, for ever, against a per-day quota that nobody re-checked. A
hundred such good decisions is the whole quota, and no single one of them was wrong.

**Nothing in the codebase says the number out loud.** The eval set lives in one file, the schedule
lives in the operating system (part 4.2), the provider limit lives on a vendor page and the retry
budget lives in Day 72's helper. The product of those four is the actual commitment, and it is not
written down anywhere. That is why the job's first failure is usually not a crash but a puzzling
message at eleven in the morning saying somebody's manual run was refused.

**And the failure surfaces at the wrong end.** The declined card at lunchtime is not a lunchtime
problem. A quota exhausted by the nightly job is reported to whoever next tries to use the provider,
who is not the person who scheduled the job and has no reason to suspect it.

## In production

**What changes at scale.** Two things, and they compound. The eval set grows monotonically — sets get
added to and almost never pruned — so the nightly commitment rises without any decision ever being
taken to raise it. And quota is usually shared: Day 70 established that a fleet shares one key's
budget, so the nightly job is not spending *its* quota, it is spending *everyone's*. The number that
matters at scale is the job's share of a pool, and the honest way to hold it is a reservation — this
job may use up to N requests per day — enforced by the job rather than agreed in conversation.

**What a professional adds that this lab does not have.** Three things, in the order they pay off:

| What | Where it lives | What it prevents |
| --- | --- | --- |
| a written budget in requests per day, with the provider and the date its limit was checked | beside the schedule, in the repository | the commitment being implicit in four files that nobody reads together |
| a sampling policy for the eval set | in the eval configuration | the set growing into the quota one good decision at a time |
| a pre-flight check that refuses to start | first line of the job | a run that gets a quarter of the way through and writes a digest built on a quarter of the truth |

The sampling policy is the interesting one because it is a real choice with three honest answers:
**sample** the set — a fixed random subset each night, with the full set weekly, so drift is caught
nightly and completeness monthly; **run the full set less often** — nightly is a habit, not a
requirement, and a set that only changes when someone edits it does not need re-running every night;
or **run it locally**, which is the next paragraph.

The pre-flight check is the one that turns a silent disaster into a loud one. A job that computes
`cases × calls_per_case × retry_budget` and compares it to the remaining quota, and **refuses to
start** if it does not fit, produces a run log line saying "did not start: needs 400, 180 left"
instead of a digest built on partial evals. Part
[3.1](../03-the-morning-after/3.1-the-run-log.md) is why that distinction has to be recorded rather
than merely printed: a run that refused to start and a run that never fired must not look the same.

**The zero-budget answer, and what it costs.** On this curriculum's budget the honest lane for a
nightly eval run is **ollama, local** — an RPD of 100000 in the table above is not really a limit, it
is the absence of one, because the requests never leave the machine. There is no quota to exhaust and
no morning after. That is the recommendation, and it is a trade rather than a free lunch:
`ollama_chat/llama3.1:8b` is a smaller model than `gemini-2.5-flash`, so the scores it produces are
**different scores**. A local nightly run measures **change over time** — did last night's edit make
something worse? — and does not measure absolute quality. If the number you need is "how good is this
system", a local nightly run will not give it to you, and pretending otherwise is the kind of
comfortable lie part [3.2](../03-the-morning-after/3.2-the-digest-that-reassures.md) is about. The
usual shape is both: local every night for drift, the metered lane occasionally and deliberately for a
level.

**The review comment a senior engineer leaves:** *"Before this goes in the scheduler I want the
requests-per-day number in the pull request description, with the provider's limit and the date you
checked it — not 'it's fine', the actual arithmetic. Include the retry budget in the multiplication;
the night this matters is the night everything is being refused. And make the job refuse to start when
the remaining quota can't cover a full run. I'd rather have a run log line saying it didn't start than
a digest built on a third of the eval set, because the second one gets read and believed."*

**The interview question:** *"You're putting a nightly eval run on a scheduler. What do you check
first?"* An honest answer: *"What it costs per day, before it goes anywhere near the scheduler.
Requests, not money — cases times calls per case times the retry budget — measured against the
provider's per-day limit. The reason it's the first thing rather than a later optimisation is that a
scheduled job is a recurring commitment made by a clock, so nobody is present to notice it's
expensive; it shows up as somebody else being refused at lunchtime. On a free tier the numbers are
brutal: a 200-case set is 200 requests, which against a 50-per-day limit can never complete at all,
and against a 250-per-day limit is 80% of the day gone before anyone gets in. Add a model-as-judge
grader and it doubles. So I'd want three things: the budget written down next to the schedule with the
date the limit was checked, a sampling policy so the set can't grow into the quota one test case at a
time, and a pre-flight check that refuses to start rather than producing a partial digest. And for a
nightly job specifically I'd default to running it against a local model — the quota is unbounded, and
I accept that I'm then measuring change over time rather than absolute quality."*

## Check yourself

```bash
cd days/day-73-ambient-agents/lab
uv run python nightly.py
cat state/evals.json
```

**Line by line:**

- The run prints `passed=3 total=5`, and the file behind it is one row per case.
- `cat state/evals.json` shows what the evals stage actually wrote. Count the rows: that count is the
  multiplier in every calculation in this part, and it is the only input to the budget that lives in
  your repository rather than on a vendor's page.

Two exercises.

**Price your own eval set.** Take the set you would actually run — the one for whatever you are
building, not this lab's five — and compute `cases × calls per case`. Add a second call per case if
you would use a grader. Multiply by the retry budget you would give it. Then look up the per-day quota
of the provider you would use, on the provider's own page, and write the number **and the date you
looked it up** in the same note. State whether the job fits, and if it does, what fraction of the day
it leaves for everything else.

**Then pick a policy for the case where it does not fit.** Choose one of: sample the set, run it less
often, or run it locally. Write one sentence on what each of the other two would have cost you, and
one sentence on what your choice cannot measure any more.

**Out loud, without scrolling up:** why is requests-per-day the right unit for a scheduled job, when
requests-per-run is the number you can actually observe?
