# 1.2 — Three stages in a forced order

## One-line answer

The three stages run in that order because **each one reads the file the previous one wrote**, and
that dependency is a check at the top of each stage rather than a comment: `run_evals` refuses
without `index.json`, `write_digest` refuses without `evals.json` — so the order is a fact about the
data, not a preference of whoever typed the list.

## The story

There is a machine in the corner of the room that washes, and another one next to it that dries, and
a table by the window where things get folded.

Somebody in a hurry once put a full basket straight into the dryer. It ran the whole cycle. It made
the noise it always makes, it got warm, and at the end it opened onto a drum of clothes that were as
dirty as when they went in — now warm and dirty, and creased in a way that would not come out. The
machine did not object. It had no way of telling that what was inside it had never been washed. It
was a dryer. It dried what was put in it.

The table by the window is the same. You can stand there and fold something damp. Nobody stops you.
The fold holds for an hour, the shirt goes into a drawer, and four days later the drawer smells.

Nothing here failed loudly. Each machine did exactly its own job, correctly, on the wrong input.

## The idea in plain language

Part [1.1](1.1-nobody-is-watching.md) made the case that an ambient agent — one nobody started, woken
by a scheduler with no person in the loop — cannot ask a question and cannot be corrected mid-run.
This part is the first consequence of that, and it is smaller and more concrete than it sounds.

Sutra's nightly job has three stages:

1. **re-index** — rebuild the retrieval index from the archive,
2. **evals** — score every eval case against that index,
3. **digest** — write the file a person reads in the morning.

They are written in that order in the source. The question this part answers is: *what makes that
order real?*

There are three candidate answers, and only one of them survives.

- **A comment.** `# NOTE: run these in order.` A comment is advice to a reader. The code does not
  read comments, and at three in the morning there is no reader.
- **The order of the lines.** True as long as nobody ever calls a stage on its own — and stages get
  called on their own constantly: from a test, from a `python -c` at a prompt, from a retry that
  restarts at stage two because stage one already finished.
- **A check inside each stage, on its own input.** The stage looks for the thing it needs, and when
  it is not there it stops and says which stage has not run.

The third one is the only answer that keeps holding when the caller is a machine. The dryer is the
model: you cannot fix a dryer by writing *wash first* on a note taped to the lid. You fix it by
giving the dryer a way to notice the clothes are dry already — or in our case, a way to notice they
were never washed.

The word for what each stage needs is a **precondition**: something that must already be true before
the stage is allowed to do any work. In this job the precondition is always a file, because a file is
the only thing that survives a process ending. That choice — output is a file, never a variable — is
what part [2.2](../02-when-it-dies-at-three-am/2.2-stages-you-can-iterate.md) turns into the ability
to resume a half-finished run, and it is why re-running a stage that already ran is safe rather than
frightening (the paper part, [Idempotence](../../papers/01-idempotence.md), is the whole argument).

## Why Sutra needs it

Because the nightly job is the first thing in this repository that a **scheduler** invokes, and a
scheduler has no judgement. It runs a command. If that command's stages can be entered in the wrong
state, they will eventually be entered in the wrong state — after a crash, after a partial run, after
somebody runs one stage by hand to check something and leaves the artefacts half-written.

And the consequence is not a crash. That is the important part, and it is the laundry again. A digest
built from missing eval scores is not an error, it is a *cheerful* file: **0 failing cases**, printed
at the top of a morning summary that somebody trusts. Part
[3.2](../03-the-morning-after/3.2-the-digest-that-reassures.md) is that failure at full size. The
guard in this part is the cheapest place to stop it, because a stage that refuses to run leaves no
misleading output at all.

Principle 10 — fail honestly — is usually read as *do not hide an error*. This is the sharper form:
**do not produce a confident artefact from an input you never checked.**

## The mechanism

The three stages are a tuple of `(name, callable)` pairs:

```python
STAGES = (("reindex", reindex), ("evals", run_evals), ("digest", write_digest))
```

**Line by line:**

- `STAGES` is **data**, not a sequence of three calls in a function body. `reindex()` followed by
  `run_evals()` followed by `write_digest()` would run in the same order tonight and be impossible to
  skip through. A list can be looped over, filtered, and resumed from — which is exactly what part
  [2.2](../02-when-it-dies-at-three-am/2.2-stages-you-can-iterate.md) needs it for.
- Each entry is a `(name, callable)` pair rather than a bare function, because the run log, the skip
  message and the artefact map all key off the **string** `"evals"`. A function object cannot be
  written to a JSON line; a name can.
- `reindex`, `run_evals` and `write_digest` are written **without brackets**. `reindex` is the
  function itself, stored for later; `reindex()` would call it immediately, at import time, before
  the job had decided whether to run at all.
- It is a tuple, not a list, so nothing later in the process can append a fourth stage to it by
  accident. The set of stages is fixed when the module loads.
- The order inside the tuple is the *intended* order. It is not the *enforced* order. Nothing in this
  line stops anybody calling `run_evals` first — which is precisely why the enforcement lives
  somewhere else.

Here is where it actually lives. The first thing the evals stage does is look for its input:

```python
def run_evals() -> dict:
    """Score every eval case against the index. Requires the index to exist."""
    index = _state.read(_state.INDEX)
    if index is None:
        raise StageFailed("evals: no index on disk - reindex has not run")
```

**Line by line:**

- `_state.read(_state.INDEX)` reads `state/index.json` from disk, and returns `None` when the file is
  not there. The stage asks the **disk**, not a variable, not a flag passed in by the caller, and not
  a boolean left over from earlier in the same process. Disk is the only thing that is still true
  after a process dies.
- `if index is None:` is the precondition, and it is the first executable line of the stage. Not
  buried three lines into the scoring loop, where it would have already half-written something.
  Nothing happens before the check.
- `raise StageFailed(...)` stops the stage. It does not return an empty result, and it does not write
  an `evals.json` full of zeros. An empty result would flow onward and become a digest saying nothing
  failed, which is the laundry-dried-dirty outcome: a finished-looking output from an input that was
  never there.
- `"evals: no index on disk - reindex has not run"` names **both** stages — the one that refused and
  the one that should have gone first. A message reading `missing input` would be true and useless at
  three in the morning. This one tells you where to look.
- `StageFailed` is a custom exception rather than `RuntimeError` or `ValueError`, so the runner can
  catch *this job's* stage failures and let a genuine bug in the scoring code go past it uncaught.
  Catching broad exception types to make a job "robust" is how a real bug becomes a silent one.

`write_digest` opens the same way, one link further down the chain: it reads `evals.json`, and raises
`StageFailed("digest: no eval scores on disk - evals has not run")` when it is not there.

Set out flat, the chain is three links and there is no way to shorten it:

| Stage | Reads | Writes | Refuses with |
| --- | --- | --- | --- |
| `reindex` | `_state.ARCHIVE` (in the module) | `index.json` | nothing — it has no file precondition |
| `run_evals` | `index.json` | `evals.json` | `evals: no index on disk - reindex has not run` |
| `write_digest` | `evals.json` | `digest.md` | `digest: no eval scores on disk - evals has not run` |

`reindex` has no precondition because its input is not produced by this job. That is not an oversight
in the design; it is what makes it the first stage. **The stage with nothing to wait for is the stage
that goes first**, and the rest of the order falls out of who reads whose output.

### Watch it refuse

Start from an empty state directory and call the second stage directly:

```bash
cd days/day-73-ambient-agents/lab
uv run python -c "
import _state, nightly
_state.fresh()
nightly.run_evals()
"
```

**Line by line:**

- `cd days/day-73-ambient-agents/lab` — the state directory is resolved relative to the module file,
  but the imports are not, so the commands are run from the lab.
- `uv run` runs against the project's pinned interpreter and dependencies rather than whatever
  `python` happens to mean in this shell. Nothing is installed today; `uv run` is how every command
  in this repository is run.
- `python -c "..."` runs the snippet without creating a file. This is deliberately the *rude* way to
  call a stage — no runner, no ordering, no `STAGES` loop — because the point is to prove the guard
  holds when the tuple above is bypassed entirely.
- `_state.fresh()` deletes every artefact under `state/`, so the run starts from a known empty disk
  rather than from whatever the last experiment left behind.
- `nightly.run_evals()` calls stage two with stage one never having run. A well-behaved runner would
  never do this. A crashed-and-restarted job, a test, or a person at a prompt all do it routinely.

Measured on 2026-09-06:

```text
Traceback (most recent call last):
  File "<string>", line 4, in <module>
  File "C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\days\day-73-ambient-agents\lab\nightly.py", line 40, in run_evals
    raise StageFailed("evals: no index on disk - reindex has not run")
nightly.StageFailed: evals: no index on disk - reindex has not run
```

That is the dryer refusing to start. It is not a crash in the scoring loop; the scoring loop was
never reached.

### The run that proves it is per-stage

The first run is open to a weak reading: *maybe the job just refuses to do anything on an empty
disk.* So run the first stage for real, let it succeed, and then skip straight to the third:

```bash
uv run python -c "
import _state, nightly
_state.fresh()
nightly.reindex()
nightly.write_digest()
"
```

**Line by line:**

- `nightly.reindex()` is a real, successful stage. It reads `_state.ARCHIVE` and writes
  `state/index.json`. After this line the disk is **not** empty and the job has genuinely started.
- `nightly.write_digest()` jumps the queue. Stage two is skipped entirely, so `evals.json` does not
  exist, even though `index.json` does.

Measured on 2026-09-06:

```text
Traceback (most recent call last):
  File "<string>", line 5, in <module>
  File "C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\days\day-73-ambient-agents\lab\nightly.py", line 55, in write_digest
    raise StageFailed("digest: no eval scores on disk - evals has not run")
nightly.StageFailed: digest: no eval scores on disk - evals has not run
```

Compare the two runs and the finding is in the difference:

| Run | `index.json` after | Stage called | Result |
| --- | --- | --- | --- |
| empty disk → `run_evals()` | absent | `evals` | refused: *reindex has not run* |
| `reindex()` → `write_digest()` | **present** | `digest` | refused: *evals has not run* |

The second run had a successful stage behind it and a real file on disk, and the digest **still**
refused. So the check is not a global "has this job started tonight" flag. Each stage is asking one
question about **its own** input, and it is the only stage that could ask it, because it is the only
stage that knows what it needs.

That distinction matters more than it looks. A single job-level flag has to be maintained by the
runner, which means the runner has to know the dependency graph, which means adding a stage means
editing two places and getting them to agree. A per-stage precondition means a new stage arrives
carrying its own answer, and the runner stays a loop over `STAGES` that knows nothing about what any
of them do.

## When it breaks

The guard is `is None`, and `is None` is a question about **existence**, not about contents or about
age. Three ways past it, in increasing order of how much they will cost you.

- **An empty index passes.** If `reindex` writes `{}` — the archive was unreachable, a filter matched
  nothing — then `index.json` exists, `read` returns an empty dict, `index is None` is `False`, and
  the evals stage runs happily against nothing. Every case scores against zero rows. The digest is
  written, it is well-formed, and the numbers in it are all true. This is the laundry table again:
  the fold is perfect and the shirt is damp.
- **A corrupt index does not raise `StageFailed`.** If the file was half-written when the process was
  killed, `_state.read` never reaches the `None` branch — `json.loads` raises first, with
  `json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)`. That is a *better*
  outcome than silence, but it is not the message the guard was written to give, and a runner that
  catches only `StageFailed` will not treat it as a stage failure.
- **A stale index passes and says nothing.** `index.json` from three nights ago is a file. It exists.
  The guard is satisfied, the evals score against an index that predates the last week of tickets,
  and nothing anywhere is wrong enough to print. This is the same shape of bug as the undated digest
  in part [3.3](../03-the-morning-after/3.3-nobody-notices-silence.md), arriving one stage earlier:
  an artefact that is present is not the same as an artefact that is current.

None of these is fixed by making the check stricter in this file. They are fixed by what the stage
writes, not by what it reads — an artefact that carries the run that produced it and when — which is
the production version below.

🎬 **The scene.** The nightly job runs. The digest appears at the usual place, at the usual size.
😬 **The naive fix.** Add `if not index: raise` so an empty index is caught too.
💥 **Why it fails.** It catches one of the three, and the expensive one — the stale index — is still
a perfectly non-empty file that sails through both checks.
💡 **The insight.** Presence is the weakest possible precondition. It is worth having because it
catches the ordering mistake outright, and it is worth being honest that it catches nothing else.

## In production

**What changes at scale.** In this lab all three stages are functions in one process, and the "file"
is a path a few directories down. In a real system they are three separate jobs — often on three
different machines, sometimes hours apart — and the artefact between them is an object in a bucket, a
table, or a partition in a warehouse. Everything in this part survives that translation unchanged:
the stage still asks the store for its input, and still refuses when the answer is empty. What
changes is that the failure is now *remote*, so the message has to travel. `evals: no index on disk`
is a good message when you are at the prompt; in production it wants the location it looked in and
the run identifier it expected, because the person reading it is not on the machine that raised it.

**What a professional adds.** Three things, in this order of value.

| Addition | What it turns the guard into | What it catches |
| --- | --- | --- |
| A timestamp inside the artefact | *is this input fresh?* | the stale index |
| A run identifier inside the artefact | *is this input from the run I am part of?* | last night's leftovers |
| A row count or checksum | *is this input complete?* | the empty and half-written cases |

Notice that all three are written by the **producing** stage and read by the **consuming** one. That
is the general shape: a precondition is only as strong as the metadata the upstream stage bothered to
write. A pipeline where every stage checks `exists()` and no stage writes provenance has a guard that
can only ever catch the one mistake we caught above.

The other production habit worth naming: **the check belongs to the stage, not to the orchestrator.**
Every real workflow engine offers to encode the dependency graph for you, and it is tempting to let
it be the only place the order is written. Do both. The engine's graph is what schedules the work;
the in-stage precondition is what protects you when somebody re-runs a single task by hand from a
web console at three in the morning — which, on any pipeline that has been alive for a year, is how
most out-of-order runs actually happen.

**The review comment a senior engineer leaves:** *"The guards are right and I'd keep them exactly
where they are — first line of the stage, before anything is written. Two things. `is None` only
tells you the file exists, so put the run id and a timestamp inside `index.json` and have the evals
stage check them; right now a three-day-old index passes and produces a digest nobody can tell from a
good one. And the digest stage catching `StageFailed` is fine, but make sure a `JSONDecodeError` from
a truncated artefact isn't quietly landing in the same handler — a corrupt file and a missing file
need different alerts, because one of them means a process died while writing."*

**The interview question:** *"You have a three-stage nightly pipeline. How do you make sure the
stages run in the right order?"* An honest answer: *"I'd make the order a property of the data rather
than of the code layout. Each stage's output is a file, and each stage's first line checks for the
file it needs and refuses by name if it isn't there — 'no index on disk, reindex has not run'. I
tested that by calling stage two on an empty directory, and then separately by running stage one for
real and jumping to stage three; the third stage still refused even though the first had succeeded,
which is how you know the check is per-stage rather than a global started flag. The reason I care is
that the failure mode of not doing this isn't a crash, it's a digest that says zero failures because
it was built from nothing. I'd also be honest that an existence check is the weakest version: an
empty file passes, and a stale one passes, so in production the producing stage writes a run id and a
timestamp into the artefact and the consuming stage checks those. And I'd keep the check in the stage
even if the orchestrator already models the dependency, because the out-of-order runs you actually
get are the manual re-runs of a single task, which bypass the graph entirely."*

```bash
cd days/day-73-ambient-agents/lab
uv run python -c "
import _state, nightly
_state.fresh()
nightly.reindex()
nightly.run_evals()
nightly.write_digest()

"
```

Then change the order of the last three calls to any of the other five permutations and predict which
message you will get *before* running it. The prediction is the exercise; the run only confirms it.

and what would you have to change about the job for it to need one?

refused to run. What does that prove about where the ordering rule lives?
