# 1.3 — The first clean run

## One-line answer

The run prints seven lines and then the process is gone, so the run **is not** those seven lines — it
is `state/index.json`, `state/evals.json` and `state/digest.md`, and the digest says **3 of 5**
passed because two of the eval cases are meant to fail.

## The story

You load the dishwasher after dinner, press the button, and go to bed. You do not watch it. You do
not hear it. Somewhere in the night it fills, washes, drains and stops.

In the morning you come down to a quiet machine and open it. The plates are warm and dry, so it ran.
You cannot say when it started, whether it paused, whether the salt light came on halfway through, or
which cycle it picked. None of that exists any more. What exists is a rack of clean plates, and that
rack is the entire report.

You put them away. And then, right at the back, one glass still has a lipstick mark on the rim.

Nothing failed. The machine finished, the light went off, the cycle completed. The glass is dirty
anyway. If you had judged the night by the fact that the machine stopped without complaining, you
would have put that glass back in the cupboard.

## The idea in plain language

Part [1.2](1.2-three-stages-in-a-forced-order.md) established the three stages and why their order is
forced. This part runs them once and then does the thing that actually matters: **closes the terminal
and goes to look at the disk.**

A run produces two kinds of output.

- **What it prints.** This exists for as long as somebody is looking at the terminal. Under a
  scheduler nobody is, so it exists for no time at all.
- **What it writes.** This is on disk in the morning, and it is what every other part of the system
  reads.

An **artefact** here means the second kind: a file the run leaves behind that outlives the process
that wrote it. Sutra's nightly job leaves three of them, plus an append-only run log that part
[3.1](../03-the-morning-after/3.1-the-run-log.md) is about.

| Artefact | Written by | What reads it |
| --- | --- | --- |
| `state/index.json` | the re-index stage | the eval stage, and every retrieval query afterwards |
| `state/evals.json` | the eval stage | the digest stage |
| `state/digest.md` | the digest stage | a person |

So the way to read a nightly job is not to watch it run. It is to run it once and then go and open
`state/`, the way you open the dishwasher rather than recalling the noise it made.

And when you open it, the interesting number is not that the job succeeded. It is that **two of the
five eval cases fail on purpose**. A nightly job whose evals always pass is a nightly job nobody
would notice breaking: the green light stops carrying information the moment it can only be green.
Those two cases are the lipstick on the glass — the machine finished, and something in the rack is
still wrong.

## Why Sutra needs it

Because everything in section 2 depends on artefacts being the truth. Resume is one line —
`if resume and DONE[name].is_file()` — and that line asks the filesystem, not a variable, whether a
stage happened. A run whose identity lived in the console could not be resumed at all, because the
console died with the process. Part [2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md)
kills the job mid-stage and the only reason that is survivable is what this part establishes here.

It also decides how the day's tests are written. The hub's build brief asks for a test that a resumed
run does not redo a completed stage, and asks for it to **assert on the stage's output rather than on
the log line**. That instruction only makes sense if you already believe the file is the run and the
log line is a courtesy.

And the re-index stage is not a new idea. It rebuilds the retrieval index Days 49 and 50 built by
hand — the same archive of support tickets, reduced here to a reference and some words, so that the
subject of today is the job around the index rather than the index itself.

## The mechanism

Run it once, with nothing left over from any earlier attempt:

```bash
cd days/day-73-ambient-agents/lab
uv run python nightly.py; echo "exit: $?"
```

**Line by line:**

- `cd` into the lab first. `nightly.py` does `import _state` by plain name, so the working directory
  has to be the one holding both files.
- No flags. A bare run calls `_state.fresh()`, which deletes everything under `state/` before the
  first stage — so this is a run from nothing, and it is reproducible. `--resume` is the flag that
  skips that deletion, and it belongs to section 2.
- `; echo "exit: $?"` prints the process exit code. It is separated by `;` rather than `&&` on
  purpose: `&&` would hide the number in exactly the case where you most want it, which is when the
  job failed. Hold on to this number, because it is about to disagree with the digest.

Measured on 2026-09-06:

```text
nightly run, started 2026-09-06T03:00:00+00:00

  ok       reindex   rows=5
  ok       evals     passed=3 total=5
  ok       digest    failing=2

  index    written
  evals    written
  digest   written
exit: 0
```

There are two blocks there and they are not the same kind of statement.

The first block is a **narration**. Each line is printed by the loop as a stage returns, and each one
is the job's own account of what it just did. It is true, and it is gone the moment the terminal is
closed.

The second block is a **directory listing**. It comes from `_state.artefacts()`, which does nothing
but ask three paths whether they are files. It is not a memory of what happened; it is a fresh look
at the disk after everything finished. That distinction is small on a clean run, where both blocks
agree, and it is the whole of part 2.1, where they do not.

Now stop reading the terminal and go and open the first artefact:

```bash
cat state/index.json
```

**Line by line:**

- `state/` is relative to the lab directory, which is where `_state.STATE` resolves to. Nothing put
  it anywhere clever — an artefact you cannot find with `ls` is an artefact nobody will check.
- `cat` rather than a Python one-liner, deliberately. In the morning, on somebody else's machine, the
  tool you will actually have is `cat`, and an artefact that needs a program to be readable is an
  artefact that will not be read.

The first entry, truncated here — the real file carries one of these per ticket:

```json
{
  "ticket:4610": [
    "after",
    "cannot",
    "cookie",
    "in",
    "missing",
    "password",
    "reset,",
    "session",
    "sign"
  ],
```

Read `"reset,"` again. The comma is still attached. That is not a typo in the file, it is the index
being exactly as clever as its source says it is:

```python
def reindex() -> dict:
    """Rebuild the retrieval index from the archive. Pure function of the archive."""
    index = {ref: sorted(set(text.split())) for ref, text in _state.ARCHIVE.items()}
    _state.write(_state.INDEX, index)
    return {"stage": "reindex", "rows": len(index)}
```

**Line by line:**

- `text.split()` splits on whitespace and nothing else, so punctuation stays welded to the word
  before it. `"reset,"` and `"reset"` are two different terms as far as this index is concerned. That
  is the smallest thing that works, and the docstring says so by calling the whole function a pure
  function of the archive rather than pretending it is retrieval.
- `set(...)` drops duplicate words, and `sorted(...)` puts them in a fixed order. The `sorted` is the
  load-bearing one: without it, two runs over identical input could write byte-different files,
  because set iteration order is not something you should rely on. An artefact you cannot diff
  against last night's is an artefact you cannot review.
- `_state.write` before `return`. The stage's real product is the file; the dictionary it returns is
  only what gets printed. If the process were killed between those two lines, the index would still
  be on disk and the narration would not exist — which is the right way round.
- `{"stage": "reindex", "rows": len(index)}` is where `rows=5` in the output came from: five tickets
  in `ARCHIVE`, five keys in the index.

The second stage scores the eval set. An **eval case** here is a named query plus the answer somebody
decided in advance it should get, and the **eval set** is all of them together:

```python
EVALSET: list[tuple[str, str, bool]] = [
    ("signin", "cannot sign in", True),
    ("billing", "invoice pdf blank", True),
    ("export", "csv export slow", True),
    ("sso", "sso loop mobile", False),
    ("webhooks", "duplicate orders", False),
]
```

**Line by line:**

- Each row is `(name, query, expected)`. The name is what the digest will print, which is the reason
  the name is a word a person can act on rather than an index number.
- The first three carry `expected=True`: the archive contains a ticket that answers them, and the
  index should find it.
- `sso` and `webhooks` carry `expected=False`, and this is the deliberate part. The scorer marks a
  case passed when `hit == expected`, so these two only pass if the index finds **nothing**. It finds
  something for both — `"sso"` and `"mobile"` are sitting in one ticket, `"orders"` in another — so
  both cases fail, every night, until the retrieval underneath them gets better.
- The comment above this list in `_state.py` states the intent plainly: a nightly job whose evals
  always pass is one nobody would notice breaking. An eval set with no red in it cannot tell you
  anything by turning red.

Which brings you to the only artefact a person actually opens:

```bash
cat state/digest.md
```

**Line by line:**

- Markdown, not JSON. This one file has a human reader, and the format follows from that; the other
  two have machine readers and are JSON for the same reason.
- Same directory, same `cat`. The digest is not mailed, posted or served anywhere today. What it
  should say once somebody does read it is part
  [3.2](../03-the-morning-after/3.2-the-digest-that-reassures.md), and it turns out to be the most
  dangerous file the job writes.

Measured on 2026-09-06:

```text
# Nightly digest

- index rebuilt: 5 rows
- evals: 3 of 5 passed
- **failing cases: sso, webhooks**
```

Now put the two measurements side by side. The process exited `0`. The digest names two failing
cases. Both are correct, and they are answering different questions.

- **`exit: 0` is the job's verdict on itself.** Three stages ran, none of them raised, three files got
  written. As a job, it worked.
- **`3 of 5` is the job's verdict on the system it was inspecting.** Two eval cases came out wrong,
  and they will come out wrong again tomorrow.

The dishwasher finished its cycle and the glass at the back still has lipstick on it. Anything
watching only the exit code sees a clean night.

## When it breaks

**You judge the run by the scrollback.** Everything in the terminal above is real and none of it is
in the morning. Run the job under a scheduler and the narration goes to a stream nobody is attached
to; part [4.2](../04-what-wakes-it/4.2-the-scheduler-you-already-have.md) is about what cron does
with output you did not explicitly redirect, and the short version is that it is not kept for you.
Any conclusion you can only reach by having watched is a conclusion nobody will reach at three in the
morning.

**A passing case passes for a reason you did not check.** The `"reset,"` token is the demonstration.
`signin` passes because the query word `"cannot"` happens to appear in ticket 4610 — set intersection
on whole words, nothing more. A query for `reset` alone would miss that ticket entirely, because the
only token in the index is `"reset,"` with its comma. The case is green and the retrieval is worse
than green implies, which is the failure mode of every eval you have not read the cases of.

**You treat the two failures as a bug to be silenced.** The tempting fix is to flip `expected` to
`True` for `sso` and `webhooks` and enjoy a clean digest. That does not change one thing about the
system's behaviour; it changes what the job is allowed to tell you about it. An eval set edited until
it is green is an eval set that has been converted from an instrument into a decoration.

**The artefacts you are reading are the ones this run wrote — probably.** `state/` holds no run
identity at all. Three files sit there with no timestamp inside them and no marker saying which run
produced them, so a digest from a run that happened long ago is indistinguishable from this one on
sight. That is a real bug and it is left in the lab on purpose; part
[3.3](../03-the-morning-after/3.3-nobody-notices-silence.md) is where it gets named.

## In production

**What changes at scale.** `state/` is a single directory that gets overwritten, and `_state.fresh()`
deletes every file in it before a non-resume run. That is fine for a lab and wrong for a real job:
the moment tonight starts, last night's evidence is gone, so the question "when did `sso` start
failing?" has no answer anywhere on disk. Real ambient jobs write **one directory per run** — a run
identifier in the path, artefacts inside it, and a `latest` pointer for the thing that wants the most
recent one. Storage is cheap and the history is the only way to see a slow regression rather than a
sudden one.

**The failure mode that only appears with real traffic.** Partial reads. `_state.write` is a plain
`path.write_text`, and its own docstring is honest that atomicity is Day 60's subject and not this
day's. With one process and no readers that is safe. With a query service reading `index.json` while
the nightly job is halfway through rewriting it, the reader gets a truncated file and a JSON parse
error at an hour when nobody deployed anything — the classic three-in-the-morning incident with no
change to blame. The standard fix is to write to a temporary file in the same directory and rename it
over the target, because a rename within one filesystem is atomic and a write is not.

**What a professional adds.** A **manifest** beside the artefacts: the run identifier, the commit the
job ran from, the row counts, and a checksum of each file it wrote. That turns three anonymous files
into three files you can attribute, and it makes "is this index stale?" a question you can answer by
reading rather than by guessing. The eval set gets the same treatment — it lives in version control
and its identity goes in the manifest, because `3 of 5` is only comparable to last night's `3 of 5`
if it was the same five.

**The review comment a senior engineer leaves:** *"Good — the stages write files and the summary at
the bottom re-reads the disk rather than echoing what the loop thought happened. Keep that, it's the
part that makes this resumable. Two changes before this runs on a schedule. First, don't overwrite
`state/` in place: write into a per-run directory and move a `latest` symlink, because right now the
first thing a nightly run does is destroy the only copy of the evidence from the night we'll want to
look at. Second, this exits 0 with two evals failing. That's defensible as long as it's a decision
and not an accident, so please write the decision down next to the exit code — which failures are
'the system is degraded, tell somebody in the morning' and which are 'the job is broken, page now'.
And nobody flips `expected` to make the digest look better without a commit message explaining what
changed in the retrieval."*

**The interview question:** *"Your nightly job exits zero and two of its five checks are failing. Is
that a bug?"* An honest answer: *"Not by itself — those are two different verdicts. The exit code
says whether the job ran: three stages completed and three artefacts got written, so zero is correct.
The eval score says whether the system it inspected is healthy, and two cases failing means it isn't.
They're deliberately failing in our set, because an eval suite that's always green can't tell you
anything by going red. What I'd want to be sure of is that the failure is visible somewhere a person
looks — ours names the two cases in the digest by name rather than just printing a count. The bug I'd
actually flag is a different one: the job's real output is three files on disk and none of them
carries a timestamp or a run identity, so a digest from a run that stopped happening weeks ago looks
exactly like this morning's. That's the failure that survives longest, because nothing about it looks
like an error."*
