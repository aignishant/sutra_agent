# 3.3 — Nobody notices silence

## One-line answer

Every failure this day has covered produces *something* to look at; a job that stops running produces
**nothing**, and the lab makes that undetectable on purpose — three of the four artefacts contain no
date at all, so this morning's digest and one from a fortnight ago are the same file.

## The story

There is a smoke alarm on the ceiling of the hall and it has not made a sound in three years.

That is what you want from a smoke alarm. It is also exactly what a smoke alarm with a flat battery
does. Silence is the correct output of a working alarm and the only output of a broken one, and
standing underneath it looking up tells you nothing at all — the plastic is the same colour either
way.

The only thing that resolves it is pressing the test button, which is a strange little ritual: you
make it fail on purpose, at a moment of your choosing, because the alternative is finding out at a
moment of the fire's choosing.

Almost nobody presses it. Not because they disagree, but because there is never a day on which the
silent alarm becomes a problem, right up until there is.

## The idea in plain language

Sort this day's failures by how loudly they announce themselves.

| Failure | What you find in the morning |
| --- | --- |
| a stage dies (part [2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md)) | missing artefacts, a `died_at` row, a non-zero exit code |
| two runs collide (part [2.3](../02-when-it-dies-at-three-am/2.3-two-runs-at-once.md)) | an index quietly one ticket short |
| a stale lock (part [2.4](../02-when-it-dies-at-three-am/2.4-the-lock-nobody-released.md)) | yesterday's artefacts, unchanged |
| the digest reassures (part [3.2](3.2-the-digest-that-reassures.md)) | a cheerful file with true numbers and no failures named |
| **the job never runs** | **yesterday's artefacts, unchanged** |

Read the last two rows together. A stale lock and a job that was never triggered produce *the same
morning*: the state directory looks exactly as it did before, because nothing touched it. And a state
directory that looks unchanged is also what you get from a job that ran perfectly and had nothing new
to do.

This is the general shape and it is worth naming, because it recurs everywhere in operations:
**absence is not a signal.** Every mechanism built so far reports a thing that happened. None of them
can report a thing that did not, because the code that would have reported it is inside the run that
did not occur.

The consequence is that you cannot detect this failure from the inside. Something **else** has to
notice, and what it has to notice is the passage of time without an event — which is why the standard
answer has an odd name. A **dead man's switch** is a control that acts when it *stops* being held: a
train's brake that engages if the driver lets go, a check that fires when the expected signal fails to
arrive. It inverts the usual logic. Instead of alerting on a bad thing happening, it alerts on a good
thing not happening.

## Why Sutra needs it

Because the hub's §4 has a `TODO(me)` that looks trivial — *put a timestamp in the digest* — and it is
the single highest-value line in the build brief. Without it, no reader and no script can tell a fresh
digest from an ancient one, and every other honesty mechanism on this day is defeated by a file that
simply stopped being updated.

And because this is where Day 72's argument arrives at its conclusion. That day found that a system
which retries successfully reports no errors at all, so the error rate is the wrong signal. This is
the same idea one step further out: a system that is not running reports nothing at all, so **no**
signal produced by the system is the right signal. You have to measure the gap between events, and
the gap is only measurable if the events are dated.

## The mechanism

Here is the whole problem, in one command. Ask each artefact whether it mentions the year at all:

```bash
cd days/day-73-ambient-agents/lab
grep -c "2026" state/index.json state/evals.json state/digest.md state/runs.jsonl; echo "grep exit: $?"
```

**Line by line:**

- `grep -c` counts matching lines per file rather than printing them, so the answer is four numbers
  instead of a wall of JSON.
- `"2026"` is a deliberately generous test. It is not asking for a well-formed timestamp; it is asking
  whether the file contains anything that could conceivably be a date.
- Listing all four files in one command matters, because the interesting result is the **pattern**
  across them rather than any single number.

Measured on 2026-09-06, immediately after a complete run:

```text
state/index.json:0
state/evals.json:0
state/digest.md:0
state/runs.jsonl:2
grep exit: 0
```

Three zeroes. The index, the eval scores and the digest — the three files a person or a script would
actually look at — contain **no date of any kind**. Copy them to a shelf, come back after a fortnight
of the job never firing, and they will still read as a perfectly good morning's work.

Only the run log has anything, and part [3.1](3.1-the-run-log.md) already established why that is not
the rescue it appears to be:

```python
    started = datetime(2026, 9, 6, 3, 0, tzinfo=UTC).isoformat()
```

**Line by line:**

- `datetime(2026, 9, 6, 3, 0, ...)` is a **constant**. It is hard-coded so that every run of this lab
  produces byte-identical output and the day's pasted transcripts stay true — a reproducibility
  device, and it is the right call for teaching material.
- It is also, in a production job, precisely the bug this part is about. Two runs a fortnight apart
  write the same `started` value, so the log records the order of runs and nothing about *when*.
- `tzinfo=UTC` is worth keeping when you replace this with a real clock. A nightly job's timestamps are
  read by people in whatever place they happen to be, and a naive local time that shifts twice a year
  turns "did it run last night" into an argument.
- `.isoformat()` produces a string that sorts correctly as text, which is what makes "the newest row"
  a cheap question rather than a parsing exercise.

So the fix is two changes, neither of them clever: put a real timestamp in every artefact the job
writes, and then have **something outside the job** compare the newest one against now. The first
change makes the failure detectable; the second is what detects it. Doing only the first is the common
half-measure — the date is there, in the file, correct, and nobody is looking at it.

## When it breaks

**A staleness check has to live somewhere the job does not.** If the thing that notices the job did
not run is itself started by the same scheduler, then a scheduler that has stopped takes both of them
with it, and the silence is now two layers deep. The usual answers are an external service that
expects a periodic ping and complains when one does not arrive, or a check that runs on a different
machine on a different trigger. Either way the rule is the same: **the watcher must fail
independently of the watched.**

**And a heartbeat can lie in the other direction.** A job that pings *"I ran"* at the top of `main()`
reports success for every night it started and immediately died. That is a real and common
mis-implementation: the ping is placed where it is easy rather than where it means something. A
heartbeat has to be emitted at the point where the work is genuinely finished, which for this job is
after the digest is written — the same argument part 3.1 made about writing the run-log row.

**The honest limit of the lab.** Nothing in this day's code detects staleness, and this part does not
add it, because a demonstration of a check that fires after a fortnight of nothing is not a
demonstration you can run. What the lab can show is the *precondition* — the missing dates, measured
above — and the build brief asks you to add the timestamp. The check itself is the `TODO(me)`, and
that split is deliberate: this document can prove the artefacts are undated, and it cannot prove
anything about a night that has not happened yet.

## In production

**How this is found the first time, in almost every organisation.** Somebody asks a question the
digest should have answered, notices the answer is wrong, and eventually works out that the file they
have been reading every morning has not changed since some Tuesday. The gap is usually measured in
weeks. It is not a sign of a careless team — it is the direct consequence of a failure that produces
no output, and no amount of care compensates for a signal that does not exist.

**What a professional puts in place before the job is scheduled.** A timestamp in every artefact; an
expected cadence written down somewhere a human and a script can both read; and one external check
comparing the two. That check is small enough to be written in the same sitting as the job, and it is
the difference between an ambient system and a script that happens to be on a timer.

**What degrades at scale.** With one job, "did it run" is a yes-or-no question. With many, the
interesting quantity becomes *which* of them has gone quiet, and a per-job check that pages somebody
becomes a source of noise that gets muted — after which you are back where you started, with the
additional problem that a muted alert looks like a healthy one. Teams that run many scheduled jobs end
up with a single inventory of expected cadences rather than a scattering of individual checks, for
exactly that reason.

**What this shares with the rest of the phase.** Day 72 part 5.2 argued that a working retry policy
hides errors, so you have to watch escalations rather than the error rate. This is the same lesson at
the level of the whole process: the more reliably a system absorbs its problems, the less its own
output tells you, and the more you need a signal that is generated by something other than the system
being watched.

**The review comment a senior engineer leaves:** *"Two things and then I'm happy. Put a real UTC
timestamp in the digest and in the index — right now nothing the job writes has a date on it, so a
month of it not running looks exactly like this morning, and I've been burned by that before. Then add
one check that runs somewhere else and complains if the newest digest is older than we expect. Don't
put the check in the same job or on the same scheduler; if that scheduler stops, both stop, and we
learn nothing. And put the heartbeat after the digest is written, not at the top of main — otherwise
we're reporting that it started, which isn't the thing we care about."*

**The interview question:** *"Your nightly job stops being triggered. How long before anyone finds
out?"* An honest answer: *"With what most people ship, weeks — because that failure produces no output
at all. Every other failure gives you something: a stage dying leaves missing files and a non-zero
exit, a bad run leaves a wrong digest. A job that never fires leaves yesterday's files, which is also
what a perfectly successful quiet night leaves. I checked our artefacts and three of the four had no
date in them anywhere, so nothing on disk could even distinguish the two. The fix has two halves that
people usually only do the first of: put a real timestamp in everything the job writes, and then have
something outside the job compare the newest one against now — a dead man's switch, something that
fires when the expected signal stops arriving. The important detail is that the watcher has to fail
independently of the watched, so it can't be on the same scheduler, and the heartbeat has to be
emitted where the work actually finishes rather than at the top of main, or you're just reporting that
the process started."*

## Check yourself

```bash
cd days/day-73-ambient-agents/lab
grep -c "2026" state/index.json state/evals.json state/digest.md state/runs.jsonl; echo "grep exit: $?"
cat state/digest.md
```

Read the digest and ask yourself, honestly, what you would conclude if somebody handed it to you with
no context. Then write down the one line you would add to it, and where in `write_digest` that line has
to go so that it is written when the work is done rather than when the run began.

Then design the check: what does it read, where does it run, what does it compare against, and what
does it do when the answer is bad. Four short answers. If any of them is "the nightly job", start
again — that is the failure in *When it breaks*.

**Out loud, without scrolling up:** every other failure on this day left evidence. Why does this one
leave none, and what does that force you to build?
