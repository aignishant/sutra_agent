# 3.1 — The run log

## One-line answer

The three artefacts on disk tell you what the job **produced**; only the run log tells you what the
job **did** — and its whole purpose is to keep apart three states that otherwise look identical: a
run that finished, a run that died part-way, and a run that never happened. It manages the first
two, in two lines of JSON. The third leaves no line at all, and that is part
[3.3](3.3-nobody-notices-silence.md)'s subject.

## The story

There is a book on the desk inside the gate of an office building. Anyone who is not a resident
signs it: your name, who you are visiting, the flat, and two columns at the right marked *in* and
*out*. You fill in the *in* column yourself when you arrive. On your way home the person at the
desk fills in the *out* column, or you do, and then you are done with the book forever.

Almost every line in that book is boring, and the boring lines are the point. A line with both
columns filled says somebody came and somebody left, and nobody will ever read it again.

Then there is the interesting kind of line. A name, a flat number, an *in* time, and an empty *out*
box. That line is not boring at all. It says a person came into this building and, as far as the
book knows, is still inside. Maybe they are. Maybe they left through the car park exit where there
is no desk. Maybe the person at the desk was dealing with a delivery and missed them. Whatever the
truth is, the book has told you there is something to check, and it did that with an **absence** —
an empty box — sitting inside a line that exists.

Now the question the book cannot answer. The plumber was due on Tuesday. Was he here?

You look through Tuesday's pages and there is no line for him. And that tells you nothing, because
"no line" is what the page looks like when he never came, and it is also what the page looks like
when he came and nobody handed him the book, and it is also what a brand-new book looks like on the
morning it is opened. An absence *inside* a line is evidence. An absence *of* a line is not
evidence of anything at all.

Hold on to the two kinds of absence. Everything below is one or the other.

## The idea in plain language

Three artefacts are the output of Sutra's nightly job: `index.json`, `evals.json`, `digest.md`. An
**artefact** is a file that outlives the process that wrote it, which part
[2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md) defined. Between them they answer one
question: *what exists right now?*

That is not the question you have in the morning. The question you have in the morning is *what
happened last night?*, and no amount of staring at the artefacts answers it, because an artefact
carries no memory of how it got there. A five-row `index.json` looks exactly the same whether it was
written eight hours ago by a run that then finished, or written eight hours ago by a run that then
died, or written last week by a run whose successors have never fired since.

So the job writes a fourth file whose only content is **what it did**. That is the run log:
`state/runs.jsonl`, one line per run, and the two properties that make it worth having are both
about how it is written rather than what it says.

It is **append-only**. Append-only means the program can add a line to the end of the file and can
do nothing else to it: no rewriting, no editing a previous line, no re-serialising the whole thing.
The visitor book has the same rule, and the rule is why anybody trusts it. A book you can go back
and tidy is a book that tells you what the last person to hold a pen wanted to be true. A file that
is only ever appended to has one failure mode left — somebody deletes it — and that is a failure you
can see, unlike a row that quietly changed.

It is **JSON Lines**: one complete JSON object per line, separated by newlines, rather than one big
JSON array holding all of them. It is a boring format and it exists for one reason, which the next
section takes apart.

Put those together and the log stops being a summary. **A summary is something somebody maintains,
and anything maintained can be wrong about the past.** A log is a fact: this line was appended at the
moment this thing happened, and nothing since has touched it.

## Why Sutra needs it

Because Sutra's nightly job is the first thing in this repository that nobody starts. Every agent
before Day 73 ran because a person typed a command, watched the output, and knew from having been
there whether it worked. Take the person away and the only thing left is what is on disk. The whole
of section 2 was about a run that dies at three in the morning, and the reason it could show you a
death at all is this file: `--fail-at digest` produced a line reading `"died_at": "digest"`, and that
line is why the death was a fact in the morning rather than a guess.

Sutra also needs it because of what section 2 built next. A resumed run **skips** stages it did not
perform, and a run refused by a lock never enters a stage at all. Neither of those is visible in the
artefacts. A resumed run and a clean run leave byte-identical files; a refused run leaves whatever
was already there. The run log is the only place where "this run skipped two stages" and "this run
was refused before it started" can be recorded, and part
[2.4](../02-when-it-dies-at-three-am/2.4-the-lock-nobody-released.md) made that concrete: a night
where every run is refused looks, on disk, exactly like a night where every run succeeded and
changed nothing.

And it is needed for the thing the day ends on. The digest is what a person reads, and part
[3.2](3.2-the-digest-that-reassures.md) is about how comfortable a true digest can be. The run log
is the file nobody reads at breakfast and everybody reads during an incident, which makes it the
only artefact whose audience is a person who has already decided something is wrong.

## The mechanism

Writing is five lines, in `_state.py`, and every one of them is a decision:

```python
def append_run(row: dict) -> None:
    """Append one line to the run log. Append-only, for the reason Day 69 part 6.2 gives."""
    STATE.mkdir(parents=True, exist_ok=True)
    with RUNS.open("a", encoding="utf-8") as handle:
        handle.write(json.dumps(row) + "\n")
```

**Line by line:**

- `row: dict` rather than a set of named parameters, because the shape of a run record grows over
  time and this function has no business knowing what a run is. It knows how to append.
- `STATE.mkdir(parents=True, exist_ok=True)` creates `state/` if it is not there. `exist_ok=True`
  means the second call of the night is not an error. A logging helper that raises because the
  directory already exists has turned the recording of a failure into a second failure.
- `RUNS.open("a", ...)` is the line the whole part turns on. **`"a"` is append: every write goes to
  the end of the file and nothing already in it is touched.** The alternative, `"w"`, truncates the
  file to nothing and starts again, so a program using `"w"` has to hold the entire history in
  memory and write it all back out each time. That is not a log, it is a **summary being
  re-published**, and a summary can be wrong about the past in ways that leave no trace: a bug in
  how the history is loaded, a filter applied on the way out, a crash between the truncate and the
  rewrite. With `"a"` the only way to lose a night is to delete the file.
- `encoding="utf-8"` is stated rather than left to the platform default. On Windows that default is
  not UTF-8, and a run log written by one machine and read by another is exactly the kind of file
  where that difference surfaces as an exception rather than as a wrong character.
- `with` closes the handle, which flushes the buffer. The write is not a fact until it has been
  flushed, and a process that dies with the line still in a buffer has recorded nothing.
- `json.dumps(row) + "\n"` writes **one object on one line**, which is the JSON Lines format. Not a
  JSON array of every run. That choice is worth its own paragraph.

**Why one object per line and not one big array.** Imagine the file as a JSON array: it opens with
`[`, holds every run, and closes with `]`. To append you must remove the closing bracket, add your
object, and put the bracket back — which means the file is briefly invalid, and a process killed in
that window leaves a document that parses as *nothing at all*. Not the last run lost: every run
lost, including the hundred nights before it, because a JSON array is a single value and a single
value is either complete or it is not. JSON Lines has no such window. Each line is a whole document.
A process killed mid-write corrupts **at most the last line**, and every earlier line still parses,
because the parser never had to look at them together. That is the same argument the printer made in
part [2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md): forty finished pages are worth
more than one document that is 40/80ths of the way through.

Reading is four lines:

```python
def runs() -> list[dict]:
    """Every run the log knows about, oldest first."""
    if not RUNS.is_file():
        return []
    return [json.loads(line) for line in RUNS.read_text(encoding="utf-8").splitlines() if line]
```

**Line by line:**

- `-> list[dict]`, oldest first, because that is the order they were appended in and the file is
  never reordered. The order is not a convention the reader maintains; it is a consequence of
  appending.
- `if not RUNS.is_file(): return []` is **the exact ambiguity this part is about**. No file and no
  runs come back as the same value. The caller receives an empty list and cannot tell whether the
  job has never run once, or the log was deleted, or `state/` is a fresh checkout. This is the
  plumber on Tuesday: the absence of a line, which is not evidence. It is left as it is here because
  it is honest about what the file can tell you, and part
  [3.3](3.3-nobody-notices-silence.md) is where it stops being acceptable.
- `.splitlines()` rather than `.split("\n")`, so a trailing newline does not produce a phantom entry
  and both `\n` and `\r\n` endings work. The lab is written on Windows and read on Linux.
- `if line` skips blank lines. In practice there is exactly one: the file ends with a newline, so the
  last split piece is empty. **What this filter does not do is protect you from a half-written
  line.** A truncated line is not blank — it is a real string like `{"started": "2026-09-` — so it
  sails past `if line` straight into `json.loads`, which raises. Being honest about that is the
  point: the guard looks like a robustness measure and is only a tidiness measure.
- `json.loads(line)` inside a comprehension means **one bad line takes down the whole read**. A
  comprehension has no place to put an `except`. A production reader has to pick one of two
  behaviours deliberately: skip unparseable lines and *count* them, so a rising count is a signal
  rather than a silence; or refuse to read a corrupt log at all and say so loudly. Both are
  defensible. What is not defensible is not choosing, and then discovering during an incident that
  your log reader has been silently dropping the interesting nights.

Now look at what the file actually holds after the runs section 2 performed. Part
[2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md) killed a run at the digest stage, and
part 2.2 resumed it:

```bash
cd days/day-73-ambient-agents/lab
cat state/runs.jsonl
```

**Line by line:**

- `cd` into the lab, because everything the job writes is under `lab/state/` relative to `_state.py`.
- `cat` and not a JSON tool, because JSON Lines is designed to be read by line-oriented tools. `grep
  '"ok": false'` works on this file. It would not work on a pretty-printed array, where the field and
  the run it belongs to are on different lines.

Measured on 2026-09-06:

```text
{"started": "2026-09-06T03:00:00+00:00", "completed": ["reindex", "evals"], "died_at": "digest", "ok": false}
{"started": "2026-09-06T03:00:00+00:00", "completed": ["reindex", "evals", "digest"], "died_at": null, "ok": true}
```

Two lines, two nights of history, and neither of them can now be changed by anything the job does
later. The first is the run that died: it got through two stages and stopped in the third. The
second is the resumed run that finished. That is the visitor book working — the first line is the
one with an empty *out* box, and you can see it at a glance.

**One thing in that output is a lie you should know about.** Both lines carry the same `started`
value, because `nightly.py` hard-codes it:

```python
    started = datetime(2026, 9, 6, 3, 0, tzinfo=UTC).isoformat()
```

**Line by line:**

- `datetime(2026, 9, 6, 3, 0, tzinfo=UTC)` is a fixed instant rather than `datetime.now(UTC)`. It is
  there so that every transcript on this day is reproducible: run the lab yourself and you get the
  bytes printed above, character for character.
- `tzinfo=UTC` means the timestamp is unambiguous. A naive `datetime` with no zone is a number whose
  meaning depends on the machine that wrote it, which is a bug waiting for the first time the job
  moves host or the clocks change.
- `.isoformat()` produces `2026-09-06T03:00:00+00:00`, which sorts correctly as a *string*. That is
  the property that makes an ISO 8601 timestamp worth using in a log: sorting the file sorts the
  history.

The consequence is not cosmetic. **The lab's run log cannot order two runs and cannot tell you how
stale one is.** Both lines claim the same instant, so "which of these is the later one?" is answered
only by their position in the file, and "did anything run last night?" cannot be answered at all. A
real job writes `datetime.now(UTC)` and gets both answers for free. This is a teaching simplification
and it is left in deliberately, because it is precisely the gap part
[3.3](3.3-nobody-notices-silence.md) walks into.

Two fields in each line look redundant and are not. `died_at` says **where** the run stopped and `ok`
says **whether** it went well; part [2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md)
argued why the second is stored rather than derived from the first. The reason worth restating here
is a property of the *log* rather than of the run: today, `ok: false` with `died_at: null` is a run
that failed for a reason other than a stage dying, and because the two fields are separate, that case
is **recordable**. A schema that derives `ok` from `died_at` has not merely made the reader do
arithmetic. It has made a real outcome unrepresentable, and an append-only file is exactly the wrong
place to discover that the shape you chose cannot express the thing that happened.

Here is the table the part exists to fill in — the three states, and how each one looks:

| State | Run log | Artefacts on disk |
| --- | --- | --- |
| Finished | a line with `"ok": true` | all three present |
| Died part-way | a line with `died_at` set and `"ok": false` | some present, some absent |
| Never ran | *nothing* | whatever last night left |

The first two rows are the log doing its job: two different nights, two visibly different lines, and
no need to guess. The third row is the problem, and it is a problem of a different kind. There is no
line to read. The artefacts column says "whatever last night left", which on a healthy system is
three perfectly good files with nothing wrong with them.

And **"nothing" is also what a brand-new install looks like**. A fresh clone, a new machine, a
`state/` directory that has never been written to: empty log, and `runs()` returns `[]`. The same
empty list means "this job has never run", "this job stopped running a month ago", and "somebody
deleted the log". That is the plumber on Tuesday, and it is the whole subject of part
[3.3](3.3-nobody-notices-silence.md).

## When it breaks

**The lab writes the row at the end of the run, so a hard kill leaves no row.** Part
[2.1](../02-when-it-dies-at-three-am/2.1-the-run-that-dies.md) established this and it belongs here
too, because it converts a row-two problem into a row-three problem. `--fail-at` is a cooperative
death: the process is alive, it gets to call `append_run`, and the log ends up with the `died_at`
line above. A `SIGKILL`, an eviction or a power loss gets none of that. The run started, some
artefacts appeared, and the log looks exactly as the previous night left it. In the table's terms, a
run that died has silently moved from the second row to the third, which is the row nobody can act
on. The fix is a line written when the run **starts**, so an unpaired opening row is itself the
evidence — the *in* column filled and the *out* column empty.

**A truncated final line breaks the reader, not the file.** If the process is killed in the middle of
`handle.write(...)`, the last line is a fragment of JSON. Every earlier line is untouched and still
parses, which is the whole reason for JSON Lines — but `runs()` as written parses the file
front-to-back inside a comprehension, so the fragment raises `json.decoder.JSONDecodeError` and the
caller gets nothing at all. A file that lost one night has become a file you cannot read. Reproduce
it before you believe it: the Check yourself block below truncates a line by hand so you see the real
message rather than a description of it.

**`_state.fresh()` deletes the log.** A run without `--resume` empties the whole `state/` directory,
`runs.jsonl` included, which is how the transcripts on this day stay reproducible. It is also exactly
backwards for a real job. The run log is the one file you never delete, because every bit of its
value is in rows from nights you have already forgotten, and the moment it becomes deletable it is a
summary again. If you take one thing from the lab into your own code, take the `"a"` and leave the
`fresh()`.

**Appending is not automatically safe from two writers.** Part
[2.3](../02-when-it-dies-at-three-am/2.3-two-runs-at-once.md) put two runs alive at once, and both of
them would call `append_run`. Small appends to a file opened in append mode are usually atomic on
POSIX below the pipe-buffer size, which is why this file is not the one that gets corrupted in
practice — but "usually, below a size, on that platform" is not a guarantee you should be leaning on
without knowing you are leaning on it. Over a network filesystem it is not true at all.

## In production

**What changes at scale is that the log never stops growing.** One line per night is nothing; one
line per run of a job that fires every few minutes across a fleet is a file that becomes the largest
thing in the directory, and the reader above loads all of it into memory with `read_text` before
parsing a single line. Two answers, and they compose. **Rotate**: start a new file on a size or a
date boundary, `runs-2026-09.jsonl`, and delete or archive files older than your retention window.
Rotation is cheap and it has one sharp edge, which is that "read the log" now means "read the right
files", and a reader that only opens the current one will report that nothing happened last month.
**Stream**: read line by line instead of slurping, so memory is bounded by the longest line rather
than by the file.

**Why you would put this in a database instead, and what you would lose.** The moment more than one
machine writes runs, or somebody wants "show me every night in the last quarter where evals dropped",
a file stops being the right shape: you are doing queries by hand with `grep` and you have no way to
merge logs from twenty hosts. A table gives you indexes, a query language, retention policies, and
concurrent writers that were designed for. What you lose is worth naming, because it is not obvious.
You lose the property that the log needs **nothing to be working** in order to record that something
is broken: a file on local disk still accepts a line when the network is down, the credentials have
expired, or the database is itself the thing that failed — and those are exactly the nights you most
want a record of. You also lose greppability on a machine you have just ssh'd into, and you gain a
dependency that has to be provisioned before the job can run at all. The common production answer is
both: append locally, ship asynchronously, and treat the local file as the source of truth for
"did this host run".

**What a professional adds to each row, and the question each field answers during an incident.**

| Field | The question it answers |
| --- | --- |
| `run_id` (a UUID, generated at start) | Which artefacts, log lines and traces belong to *this* run rather than to the one before it |
| `started` and `finished`, both real timestamps | When did it run, how long was it, and has it run at all since the incident began |
| `version` (the commit the code was at) | Did this start when we deployed, and what exactly was running when it did |
| `host` | Is this every machine or one bad one |
| `trigger` (scheduler, manual, retry) | Did a person start this, and is this the third automatic retry of the same failure |

Every one of those exists because somebody, during an outage, could not answer the question in the
right-hand column. `run_id` is the one to add first: without it you cannot join anything to anything,
and the first thing you want during an incident is every line about the run that broke. `version` is
the one people leave out and then regret, because the most common cause of a job that started failing
is a job that started being different.

Back to the book at the gate one last time. A book with only names is a book that tells you who was
in the building at some point. A book with names, times in, times out, which flat and who signed them
in is a book you can actually answer a question with when somebody needs to know what happened on
Tuesday. The fields are not bureaucracy. Each one is a question that was asked once and could not be
answered.

**The review comment a senior engineer leaves:** *"Format and mode are right — append-only JSON
Lines is what I'd want, and I'm glad `ok` is stored rather than derived. Three changes before this
goes near a scheduler. Put a real `datetime.now(UTC)` in `started` and add `finished`, because with a
hard-coded timestamp this log cannot order two runs or tell me if anything ran last night, and that's
the only question I'll actually have at eight in the morning. Add a `run_id` and put it in every log
line the job emits, so I can pull one run's story out of a shared log. And `runs()` blows up on a
truncated last line — one killed process makes the whole history unreadable, which defeats the point
of the format. Skip unparseable lines and count them, and surface the count; don't silently drop
them."*

**The interview question:** *"Your batch job writes its output files. Why does it also write a
log?"* An honest answer: *"Because the output files tell you what exists, not what happened. A
finished run and a run that died after its first stage can leave the same file on disk, and neither
of them looks different from a run that never fired and left last week's file sitting there. So the
job appends one line per run — JSON Lines, one object per line, opened in append mode. Append mode
matters because a log you rewrite is a summary, and a summary can be wrong about the past; one line
per object matters because a process killed mid-write corrupts at most the last line, whereas a
truncated JSON array parses as nothing at all and you lose every night in the file. The line carries
where it stopped and whether it was ok as separate fields, so a run that failed without any stage
dying — refused by a lock, say — is representable rather than being logged as a success. And the
honest limit of the version I built is that it writes the row at the end, so a `SIGKILL` leaves no
row at all, which puts a run that died into the same bucket as a run that never happened. The fix is
to write a row when the run starts as well as when it ends, so an opening row with no closing row is
itself the evidence."*

## Check yourself

```bash
cd days/day-73-ambient-agents/lab
uv run python nightly.py --fail-at evals; echo "exit: $?"
uv run python nightly.py --resume; echo "exit: $?"
cat state/runs.jsonl
```

Before you run it, write down how many lines `runs.jsonl` will hold at the end and what `completed`
will be in each. Then run it. If your prediction was wrong about the *first* line, work out which
call to `_state.fresh()` explains it, and say in one sentence what that means for a real run log.

Then break the reader on purpose. Copy `state/runs.jsonl` somewhere safe, chop the last line of the
original in half with a text editor, and call `_state.runs()`. Paste the real exception message you
get — not a description of it — next to your notes, then write the three-line reader you would ship
instead, and say what it does with the broken line and how anybody finds out it was broken.

**Out loud, without scrolling up:** name the two absences in the visitor book, and say which of the
three states in the table each one corresponds to — and which state has no absence at all to look at.
