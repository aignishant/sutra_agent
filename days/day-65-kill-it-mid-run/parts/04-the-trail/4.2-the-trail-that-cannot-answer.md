# 4.2 — The trail that cannot answer

## One-line answer

Store a pointer to the payload instead of the payload, and the system keeps working perfectly while
two of the four audit questions silently stop having answers — a failure with no error, no alarm and
no symptom until somebody asks.

## The story

You are referred to a specialist. Months later you finally get the appointment, and you hand over the
letter your own doctor wrote.

The specialist reads it out: *"Please see this patient regarding the matter discussed."*

That is the whole letter. It is a real letter, correctly addressed, properly signed, filed in the
right place. Nobody was careless. On the day it was written it was perfectly clear, because the two
doctors had spoken on the phone that morning and both knew exactly what the matter was.

The specialist asks you what the matter is. You are not sure — you had assumed the letter would say.
So the appointment becomes a re-diagnosis from scratch, and the referral has bought you nothing but
a date.

The letter was not wrong. It **pointed at** something instead of containing it, and the thing it
pointed at was a conversation that no longer exists.

## The idea in plain language

When you build an approval store, storing the payload feels redundant. The draft is right there in
the run log. Copying it into the approval record duplicates data, and duplicated data goes stale, and
every instinct a competent engineer has says to store a reference instead.

So the record says *see run t1, stage draft*. It is smaller, it has one source of truth, and it is
wrong.

It is wrong because a **reference is only as good as the thing it points into**, and the two files
have different lifetimes, different owners and different retention rules. Run logs are operational
data: big, noisy, rotated, truncated by whoever is fixing a disk-space alert. Approval records are
compliance data: small, permanent. Storing compliance data as a pointer into operational data means
the answer to your compliance question is deleted on an operational schedule.

The subtle part — the part that makes this a genuine failure rather than an obvious one — is that
**nothing detects it**. There is no error. The run works. The approval works. The close works. The
pointer is even correct, right up until it is not, and on the day it stops being correct nobody is
looking. You find out the first time somebody asks, which by definition is the worst day.

This is the general shape of an audit failure and it is worth naming: audit trails do not break, they
**thin**. Each individual decision to store a little less is defensible on its own, and the trail
stops being able to answer anything long before anyone notices it has.

## Why Sutra needs it

Part 4.1 asserted that the approval store keeps the payload itself, and deferred the argument. This
is the argument, run rather than stated.

It also matters directly for the gate. Criterion 3 in part 5.3 has to be able to go **red**, and a
criterion that cannot fail is decoration — Principle 11. `--thin` is the switch that makes it fail,
which is how you know the check is checking something.

And the failure has a second life on Day 69, where the same instinct — store a pointer, keep the text
somewhere central — collides with a deletion request. The pointer survives the deletion, so the
system believes it still has evidence it no longer has.

## The mechanism

Same audit, same four questions, one difference in how the approval was filed:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python trail.py --thin
```

**Line by line:**

- `--thin` files the approval with a pointer — `<see run t1, stage draft>` — where the payload would
  be, and omits the hash, because you cannot hash a payload you did not keep. That omission is not an
  extra bug bolted on to make the demo worse; it is the direct consequence of the first decision, and
  it is why one shortcut costs two answers.
- Everything else is identical: the same triage run, the same operator, the same close. The run and
  the close do not know or care how the approval was stored.

Measured on 2026-09-06:

```text
approval store: pointer only

  who decided it               answered    operator-a
  what exactly did they read   UNANSWERED  <see run t1, stage draft>  (the text is not here)
  did that text run            UNANSWERED  cannot be checked: no hash was stored
  was it done once             answered    1 close row(s) for key t1:appr-t1

unanswerable from rows alone: 2 of 4
```

Two of four, from one design decision.

Question 1 still works — the decider's name was never a pointer. Question 4 still works — the count
comes from the close ledger, which this change did not touch. It is the two middle questions, the two
that connect a **person** to a **payload**, that are gone.

And notice what the trail prints for question 2. It is not blank and it is not an error. It is
`<see run t1, stage draft>`, which is a perfectly good answer to a different question: *where would I
look?* An auditor reading a dashboard that renders this field sees text, and text looks like an
answer. This is the failure wearing its most dangerous face — not missing data, but a plausible
substitute for it.

Compare the two records side by side:

| Field | stored | `--thin` |
| --- | --- | --- |
| `decided_by` | `operator-a` | `operator-a` |
| `payload` | the draft, in full | `<see run t1, stage draft>` |
| `payload_hash` | `c77a5a66bb50` | absent |
| answers | 4 of 4 | 2 of 4 |

The thin record is smaller, tidier, has no duplicated text and satisfies every instinct about
normalisation. It is also unable to say what a person agreed to.

## When it breaks

The break is what happens when the pointer is followed and the target has moved on, and it is worse
than the target being missing.

Here is the sequence, which needs nothing exotic — just the ordinary passage of time in a system that
retries:

1. The run drafts a reply and parks. The approval records *see run t1, stage draft*.
2. The operator approves it.
3. The run is resumed, and something upstream has changed — a re-classification, a corrected
   neighbour ticket, a redraft after a rejection. The run log now has **two** `draft` stages.
4. The pointer says *stage draft*. There are two. The audit follows it and finds the second one.

Nothing failed. Every file is intact, the pointer resolves, and the text it resolves to is a real
draft produced by the real run. It is simply not the one the operator read, and there is now no way
to discover that, because the only evidence of what they read was the pointer.

That is strictly worse than the missing answer above. An `UNANSWERED` is honest. This produces a
**confident wrong answer**, and an audit that answers wrongly with confidence is more dangerous than
one that admits it cannot answer — Principle 10 applies to the trail exactly as it applies to the
agent.

The defence is the hash, and it is worth being precise about what it does. The hash does not preserve
the text. It preserves the **ability to detect that the text is not the same one**:

```python
def payload_hash(text: str) -> str:
    """The identity of what the approver saw, short enough to read in a table."""
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]
```

**Line by line:**

- `text.encode("utf-8")` — hashing is defined over bytes, not characters, so the encoding has to be
  named. Leaving it to a default means the same draft can hash differently on two machines, which
  turns the check into a source of false alarms and gets it switched off.
- `hexdigest()[:12]` truncates to twelve hex characters. That is a deliberate trade: short enough to
  print in the table above and read aloud in a review, long enough that two different drafts
  colliding is not a practical concern for a ticket desk. A system where a collision is an attack
  rather than an accident keeps the whole digest.
- The function is in `_store.py` and not in the runner, because both the filing of the approval and
  the checking of the close must use the identical definition. Two implementations of "the hash of
  the payload" is a bug waiting for a whitespace change.

## In production

**What a professional writes instead.** They store both: the hash inline in the approval row, always,
and the payload wherever payloads live. The hash is small, permanent, and answers question 3 for
ever; the payload can be in object storage with a retention policy and answers question 2 for as long
as the policy allows. The important part is that the two have **independent lifetimes and the record
knows it** — so when the payload is gone the audit says *the text is no longer retained, and here is
proof that what ran matched what was approved*, which is a real answer rather than a shrug.

**What degrades at scale.** Inlining full payloads is what stops working first. Approval tables with
a document per row grow fast and get slow, and the pressure to normalise is real and correct. The
mistake is not normalising; it is normalising **without** keeping the hash, because the hash is the
part that costs nothing and carries the accountability.

**The failure mode that only appears with real traffic.** Retries and redrafts. In a system where
every run produces exactly one draft, a pointer to "the draft" is unambiguous and works perfectly
through every test anyone writes by hand. The ambiguity appears only when a run has been rejected
once and redrafted, or resumed after a crash mid-draft, which are exactly the paths this day's
section 3 spends its time in — and which are rare enough per run to be common per fleet.

**The review comment a senior engineer leaves:** *"This approval row points at the run log for the
payload. The run log has a thirty-day retention and this table does not, so from day thirty-one we
cannot say what anyone approved. Either put the hash in this row or change the retention, and I would
do both."*

**The interview question:** *"Your approval record references the document rather than copying it.
What is wrong with that?"* The answer that shows experience talks about lifetimes: *"The reference is
only as durable as what it points into, and those two things are almost never governed by the same
retention policy — compliance data outlives operational data by years. Worse, if the target can
change, the pointer keeps resolving and starts returning the wrong version, so instead of losing the
answer you get a confident wrong one. I tested this on my own audit: filing a pointer instead of the
payload took it from four of four questions answered to two of four, with no error anywhere, and the
field still rendered as text so it looked like an answer. The fix that costs nothing is to store the
hash inline even when you store the payload elsewhere."*

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python trail.py; echo "exit: $?"
uv run python trail.py --thin; echo "exit: $?"
```

The two exit codes differ, which is what makes this a criterion. Now say which of the four questions
would still be answerable if the payload were stored but the hash were not.
