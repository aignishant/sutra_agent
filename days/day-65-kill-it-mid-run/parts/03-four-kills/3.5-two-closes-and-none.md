# 3.5 — Two closes, and none: the failure that exits zero

## One-line answer

Both ways of getting the effect window wrong end in a process that exits `0`, prints `close`, and
looks exactly like success — one having closed the ticket twice and the other having closed it never
— which is why the drill counts rows in a file instead of reading exit codes.

## The story

You pay a bill on your phone. The app spins, and then the screen goes white and the app is gone.

You open it again. The payment is not in the list. So you pay it again, and this time it works, and
you get a confirmation. Fine.

Four days later the money has gone twice.

Nothing on your phone ever said anything was wrong. The first attempt showed you a spinner and then
vanished, which you read as "it did not happen". The second showed you a tick. Both screens were
honest about what they knew. Neither of them knew what had actually reached the bank, because the
thing that reached the bank and the thing that drew the screen were not the same event.

The version that goes the other way is quieter still: you get the tick, you close the app, and the
bill is never paid. You find out from a letter.

## The idea in plain language

Part 3.4 named three orders and showed the one that works. This part runs the two that do not, and
the point is not that they are wrong — it is **what being wrong looks like from the outside**.

Here is the whole difficulty in one sentence: a process that has done the effect twice and a process
that has done it once are, from the process's own point of view, identical. It ran the close path. It
appended a row. It printed a line. It returned `0`. Every observation the process can make about
itself is the same in both cases, because the extra close was made by a **different process** that no
longer exists.

That is a general property of durability bugs and it is worth naming, because it determines how you
test them. A failure that a process can detect in itself becomes an exception, and an exception
becomes a stack trace, and a stack trace is easy. These failures are only visible from **outside** the
process, **after** it has exited, by counting something in the world. If your test harness is a
collection of assertions inside the thing being tested, it cannot see them at all.

Two terms, defined once:

- **At-least-once** means the effect will happen, and may happen more than once. That is `unsafe`.
- **At-most-once** means the effect will happen no more than once, and may not happen at all. That is
  `drop`.

You get one of them for free. Getting the thing everyone actually wants — exactly once — is not a
third option you can select; it is at-least-once plus an idempotency key, which is what `keyed` is.
Day 60 makes that argument at length and this part is its most literal demonstration.

## Why Sutra needs it

Criterion 1 of the Phase 9 gate is *it resumes, once*, and the "once" is doing all the work. Part 5.1
turns it into a command that can go red, and this part is the reason that command counts closes
instead of checking exit codes.

It also sets up the whole of section 4. If the failure is invisible from inside the process, then the
only place it can be seen is in the rows left behind — and rows left behind are exactly what an audit
reads. The instrument that catches this bug and the instrument that answers a colleague's question
three months later turn out to be the same instrument.

## The mechanism

Run the do-then-record order and watch it succeed at doing the wrong thing:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python drill.py --kill K4 --mode unsafe
```

**Line by line:**

- `--mode unsafe` changes one argument passed to `apply_effect`. The stages, the approval, the kill
  point and the resume are all identical to the passing run in part 3.4.
- The drill still counts the rows itself at the end, which is the only reason anything below is
  labelled `FAIL`.

Measured on 2026-09-06:

```text

```

Read the final resume block on its own, covering the last four lines with your hand. It is
**identical** to the passing run in part 3.4: five stages reinstated, `close applied`, `spent 0
requests`, `exit 0`. A monitoring system watching exit codes sees a clean recovery. A log search for
errors finds nothing. The only thing that knows is `closes for this intent: 2`, and that number was
produced by the drill reading a file **after** every process had exited.

The rows themselves:

```bash
cat state/closed.jsonl
```

**Line by line:**

- The customer-visible ledger, read directly. Nothing interprets it, because the whole argument of
  this part is that the interpretation available inside the process was wrong.

```text
{"key": "k4:appr-k4", "text": "Ticket 4610: classified auth. See ticket 4588.", "ticket": "4610"}
{"key": "k4:appr-k4", "text": "Ticket 4610: classified auth. See ticket 4588.", "ticket": "4610"}
```

Two rows, byte-identical, **same key**. That is the customer receiving the same reply twice. Note
that the key is not doing nothing here — it is the only reason you can tell this is a duplicate
rather than two legitimate closes. It just was not being *read* from a place that survived the crash.

Now the other order:

```bash
uv run python drill.py --kill K4 --mode drop
```

**Line by line:**

- `--mode drop` records first and acts second. Everything else is again unchanged.

Measured on 2026-09-06:

```text
  draft     reinstated
  review    reinstated
  close     replayed (key k4:appr-k4)
  spent     0 requests
  -> exit 0   [recovered]
  closes for this intent: 0

----------------------------------------------------
kill   final exit  closes  verdict
K4     0           0       FAIL

mode=drop  every kill ends in exactly one close: False
```

`close replayed`. The guard **worked**: it read the record, found the key, and correctly declined to
do the work twice. It is the only one of the three modes where the guard fires at all, and it fires
to prevent an action that never happened.

And the files:

```bash
cat state/closed.jsonl
cat state/effects.jsonl
```

**Line by line:**

- Both files, in this order, because the failure is precisely that they disagree. Reading either one
  alone gives a coherent and false account: `closed.jsonl` says nothing happened, `effects.jsonl`
  says something did.

```text
{"key": "k4:appr-k4", "ticket": "4610"}
```

`closed.jsonl` is **empty** and `effects.jsonl` has a row. The system's internal record says the
ticket was closed. The ticket is open. An operator approved a reply that was never sent, and every
dashboard reading `effects.jsonl` will report that it was.

Put the three side by side:

| mode | final exit | `close` printed | rows in `closed.jsonl` | what the customer got |
| --- | --- | --- | --- | --- |
| `keyed` | 0 | `applied` | 1 | one reply |
| `unsafe` | 0 | `applied` | 2 | two replies |
| `drop` | 0 | `replayed` | 0 | nothing, and we think we sent it |

Three different customer outcomes. One exit code.

## When it breaks

The break in *this* part is the test that would have missed all of it, and it is the test most people
write first.

```python
def test_resume_closes_the_ticket():
    run_id = start_and_kill()
    code = resume(run_id)
    assert code == 0
    assert "close" in output
```

**Line by line:**

- `assert code == 0` passes in all three modes. It is checking that the *process* was happy, and the
  process was happy in every case, including the two that were wrong.
- `assert "close" in output` passes in all three modes as well — `drop` prints `close replayed`,
  which contains the word. A substring check against a log line is a check against wording, and
  wording is not behaviour.
- What is missing is any observation of the world outside the process. There is no count. Nothing
  reads the file the effect landed in, and nothing compares that count to the number of times the
  action was *intended*.
- The test also runs the resume once. Both failures need the killed attempt **and** the resume to be
  considered together, so a test that starts from a clean run and resumes once cannot express the
  bug even if it wanted to.

The version that catches it is the one in `drill.py`, and it is barely longer:

```python
    closes = [row for row in _store.closed() if row["key"].startswith(f"{run_id}:")]
    print(f"  closes for this intent: {len(closes)}")
```

**Line by line:**

- `_store.closed()` re-reads the file from disk. It does not use a number the runner returned,
  because the runner is one of the processes under test and a count kept by the thing being tested is
  not evidence — part 1.2 made that the general rule and this is the case it was written for.
- `row["key"].startswith(f"{run_id}:")` filters to *this intention*. Counting all rows in the file
  would make the check depend on what other runs had done, which is how a real assertion becomes
  flaky and then gets deleted.
- `len(closes)` is compared against `1` by the caller — not `>= 1`. Under-doing and over-doing are
  both failures and they are different failures, and a check written as `>= 1` catches only one of
  them, which is exactly the half that `unsafe` does not have.

## In production

**What a professional writes instead.** The count is a real query against the real store, run by
something that is not the application: a reconciliation job that compares intentions to effects and
alarms on any disagreement. Every serious payments system has one, and it exists precisely because
the application cannot audit itself — the application is the thing that might be wrong.

**What degrades at scale.** At one run you can count rows. At a million you need the count to be a
constraint instead: a unique index on the idempotency key, so the second insert fails at the database
rather than being prevented by a check the application remembered to run. The scan in this drill is
teaching code, and the honest statement of its limit is that it answers the question after the fact
rather than preventing the row.

**The failure mode that only appears with real traffic.** These two bugs are rare per run and certain
per fleet. A window measured in milliseconds is essentially never hit by a developer testing by hand,
and is hit many times a day across enough runs and enough deploys. That is why they are found in
production and not in review: the code looks fine, because it is fine almost always. The only way to
meet them earlier is to do what this drill does and kill the process *in the window on purpose*
rather than waiting for chance to do it.

**The review comment a senior engineer leaves:** *"This test asserts the exit code. Show me the test
that asserts the ticket was closed exactly once, and make it fail on purpose in front of me — if you
cannot make it go red by breaking the idempotency key, it is not testing the idempotency key."*

**The interview question:** *"How would you know if your retry logic was double-charging customers?"*
The answer that shows experience does not start with logging: *"Not from the service, because the
duplicate is made by a process that has already died and the survivor's view of itself is identical
either way — same exit code, same log line. You need something outside it counting effects against
intentions and alarming on the difference. I proved that on my own drill: killed in the effect
window, do-then-record closed the ticket twice and record-then-do closed it never, and **both exited
zero** with a normal-looking log. The only thing that could tell them apart was a row count taken
after every process had exited."*
