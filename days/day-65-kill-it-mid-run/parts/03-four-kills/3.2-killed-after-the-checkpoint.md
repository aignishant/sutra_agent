# 3.2 — K2: killed after the checkpoint, before the gate

## One-line answer

A crash after a stage has been recorded costs nothing to redo, and the resumed run proves it by
reinstating four stages and spending exactly one request on the only stage that had not finished.

## The story

You have written the letter, put it in the envelope, and written the address on the front. It is
sitting on the table by the door.

You do not post it, because you have run out of stamps and the shop is shut.

The next morning you pick it up on the way out. You do not write the letter again. You do not
re-address the envelope, or check whether you spelled the street right, or wonder whether the letter
inside is the one you meant to send. The envelope is finished, visibly, and the only thing left is
the part that did not happen.

The reason you can be that confident is that the finished work is *finished in a way you can see*.
If the address were half-written you would have to think about it. It is not, so you do not.

## The idea in plain language

K2 kills the process at the opposite side of the write from K1. The stage's result has been
recorded; the next stage has not started.

Concretely, the run is killed after `draft` has been written to the log and before `review` runs. So
the resumed process reads a log containing four completed stages and one missing one, and its job is
to do the missing one and nothing else.

This is the boring kill, and it is in the drill for two reasons that are not boring.

**It is the control.** K1 showed a stage running twice. If K2 also showed a stage running twice, the
resume logic would be re-running everything and the log would be decoration. The value of K2 is the
contrast: same system, same kind of crash, one stage apart, and the behaviour is completely
different. Without it you would not know whether the resume was reading the log or ignoring it.

**It is where over-repeating would hide.** A resume that re-runs a completed stage does not fail. It
produces the same answer — research over the same archive finds the same neighbour — and the run
finishes correctly, having quietly spent four extra requests. Nothing goes red. The only symptom is
a bill, and bills are noticed late.

One term, because the rest of the day uses it as though it were obvious. To **reinstate** a stage is
to take its recorded result out of the log and put it back into the run's state without executing
anything. The word matters because it is the thing that distinguishes a resume from a restart: a
restart begins again, a resume reinstates and then continues.

## Why Sutra needs it

Sutra's triage run costs four provider requests, and the free tier this project lives on is measured
in requests per day. Day 59 measured the shape of that budget for the whole graph, and Phase 11 is
going to run this thing on a schedule without anybody watching.

A resume that re-ran everything would turn each crash from a one-request problem into a
four-request problem. On a quota of twenty requests a day, that is the difference between a system
that survives a few crashes and one that stops working after four. The criterion in part 5.4 is
where that arithmetic is checked, and K2 is the experiment that makes the arithmetic true.

## The mechanism

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python drill.py --kill K2
```

**Line by line:**

- `--kill K2` selects `after-draft`, so `_die` fires immediately after the draft stage's result has
  been appended to the log — one line later than K1's kill point in the same loop.
- The ticket is `4633`, a billing ticket, so the run takes a different path through the archive than
  K1's. That is deliberate: reusing the same ticket for every kill would make it easy to mistake a
  cached result for a reinstated one.

Measured on 2026-09-05:

```text

  classify  ran        label=billing

  draft     ran        draft=Ticket 4633: classified billing. No pr...
  [killed at after-draft]
  -> exit 137   [killed]

  classify  reinstated
  research  reinstated

  spent     1 requests
  -> exit 2   [parks]
  appr-k2 approved by operator-a
resume k2: 12 events on disk, stages done ['intake', 'classify', 'research', 'draft', 'review']
  intake    reinstated
  classify  reinstated

```

Compare the middle block with K1's. Both are a resume after a crash. K1's said
`stages done ['intake', 'classify']` and spent three requests. This one says
`stages done ['intake', 'classify', 'research', 'draft']` and spends **one**.

That single number is the point of the kill. Four stages were already paid for and the resumed
process paid for none of them again. The word `reinstated` appears four times and `ran` once, and
the one that ran is the one the log had no result for.

Note `research ran neighbour=None` in the first block. Ticket `4633` is the only billing ticket in
the fixture, so there is no neighbour to find. It is worth seeing at least once that a stage
producing *nothing* is still a completed stage: `None` is a result, it gets recorded, and it gets
reinstated exactly like a useful one. A resume that treated an empty result as a missing one would
re-run this stage for ever.

## When it breaks

The break here is the one that produces no error, so it has to be caught by counting.

Skip the `if stage in done: continue` and the resume becomes a restart. Every kill still ends with
the ticket closed exactly once, every exit code is still `0`, and the drill's headline still says
pass — because the headline counts *closes*, and closes are guarded by the effect key rather than by
the resume. `--no-skip` is that mistake, wired to a flag so it can be run rather than imagined:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python -c "import _store; _store.reset()"
uv run python runner.py start 4633 --run-id z2 --kill-at after-draft > /dev/null
uv run python runner.py resume z2 --no-skip
```

**Line by line:**

- The first two commands recreate K2 exactly: the same ticket, killed at the same point.
- `--no-skip` rebuilds the state from the log as usual and then empties the `done` list, so no stage
  is skipped. The resume is now a restart that happens to know the answers.

Measured on 2026-09-06:

```text
  draft     ran        draft=Ticket 4633: classified billing. No pr...
  review    ran        verdict=needs-approval rubric=v1
  parked    awaiting appr-z2
  spent     4 requests
```

`spent 4 requests` where the honest resume spent `1`, and nothing else moves. There is no traceback
here because there is no error: this failure's entire visible signature is a number being larger
than it should be. That is why the budget is a criterion of its own in part 5.4 rather than a note
at the bottom of the drill.

The related break that *does* raise is worth reaching for once. Reinstating a stage requires its
result to be in the log. The `spent` line and the `stage` line are written at different moments and
a crash lands between them, so if you mark stages done from the `spent` lines, the run skips a stage
whose result it never received:

```bash
uv run python -c "import _store; _store.reset()"
uv run python runner.py start 4610 --run-id z3 --kill-at during-draft > /dev/null
uv run python runner.py resume z3 --done-from-spend; echo "exit: $?"
```

**Line by line:**

- `--kill-at during-draft` dies in the window between the two lines: the log gets
  `{"cost": 1, ... "stage": "draft"}` and never gets the matching `stage` line.
- `--done-from-spend` treats paying for a stage as having finished it, which is the seductive
  version of the bug — it reads as an optimisation, and it is one line.

Measured on 2026-09-06:

```text

  classify  reinstated
  research  reinstated
```

Note **where** it raises. Not in `file_approval`, which is where you would expect a missing draft to
be noticed, but one stage earlier in `review` — the first line of code that reads a key the skipped
stage was supposed to write. The `draft reinstated` line printed happily just above it. The run
announced it had restored a stage and then died on the first attempt to use what it claimed to have
restored, which is the honest signature of this bug and the reason the message names `'draft'` and
not the stage that is actually missing.

That is what an over-eager reinstatement looks like when it is lucky enough to fail loudly: the
draft stage was marked done, its text was never recorded, and the approval cannot be filed because
there is nothing to approve. Loud is the good case. The shortcut in part 3.1 is the same bug being
quiet.

## In production

**What a professional writes instead.** The reinstate path is written once, in the runtime, and
application code never decides whether a step has run. That is exactly what ADK 2.7.1 does, and Day
60 measured its default: on resume the framework **skips** the node that was running when the
process died rather than re-running it, unless the node is declared with
`@node(rerun_on_resume=True)`. That is the opposite trade from this drill's runner, and it is a
legitimate choice — it favours not repeating work over not losing it — but it is a choice you have to
know about, because a node with a side effect and no `rerun_on_resume` is a node that can be skipped
silently.

**What degrades at scale.** The log a resume has to read grows with the run. Four stages is four
lines to fold; a graph with a loop that ran two hundred iterations is two hundred, and the resume
starts spending real time replaying its own history before it does any work. Production systems cap
this with periodic snapshots — a single line that says "the state at iteration 200 was this" — so the
fold starts near the end rather than at the beginning.

**The failure mode that only appears with real traffic.** Two processes resume the same run at once,
both read the same log, both find the same missing stage, and both run it. Every stage before it is
reinstated correctly by both, so the log looks almost right afterwards — two copies of one stage,
interleaved. This drill has no lease and cannot catch that, and it is the largest single gap in the
instrument.

**The review comment a senior engineer leaves:** *"Your resume test asserts that the run finishes.
It would also pass if the resume re-ran every stage from the start. Assert the number of stages
executed, not just the outcome, or you are testing that the code is not catastrophically broken
rather than that it does the thing you designed."*

**The interview question:** *"How do you know your resume is actually resuming?"* The answer that
separates people is a number: *"I count executions, not outcomes. A restart and a resume both
finish, so success proves nothing. On our triage run a crash after the fourth stage should cost one
request on the resume; if it costs four, the log is being ignored and the only symptom would have
been the bill."*
