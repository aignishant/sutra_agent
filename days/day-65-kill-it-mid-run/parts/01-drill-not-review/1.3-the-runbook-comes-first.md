# 1.3 — The runbook comes first

## One-line answer

Write the drill as a numbered list of commands **before** you run it, because a procedure written
while you still have your wits about you is the same procedure you will need on the night you have
none, and every deviation from it during the drill is a finding.

## The story

The removal van comes on Saturday. On Thursday evening you sit in the middle of the front room with
a marker pen and label every box: *kitchen — plates*, *bedroom — winter clothes*, *books — do not
stack*. It takes an hour and it feels like a waste of an hour, because you know what is in the
boxes. They are your boxes.

On Saturday, at the other end, you have carried forty boxes up two flights, you have not eaten since
seven, the van driver wants his paperwork, and the person helping you is asking, for the third time,
which room this one goes in. You can barely remember your own address. And every box says what is in
it, in your handwriting, from Thursday, when you were a calm person with an hour to spare.

The labels were not for Thursday-you. Thursday-you knew. They were for Saturday-you, and
Saturday-you cannot be trusted with anything.

## The idea in plain language

A **runbook** is a numbered list of the exact commands to run, in order, with the expected result of
each one, written so that someone who is not you can follow it without deciding anything.

The rule this part is built on is about *when* it is written: **before the drill, not after.** That
ordering is the entire value, and it buys three separate things.

**It stops the drill from being improvised.** If you write the steps as you go, you write down what
you did, which is not the same as what you meant to do. Anything awkward gets smoothed out in the
retelling, and the awkward parts are the findings.

**It makes deviation measurable.** Once the steps exist on paper, "I had to open a second terminal
that the plan did not mention" and "step 4 did not work so I ran something else" stop being small
inconveniences and become **findings**, recorded with the rest. A drill where you deviated four
times and finished successfully is not a pass; it is a pass and four findings.

**It produces the thing you actually need later.** The drill happens once. The procedure gets used
every time something similar breaks for real, and at that point nobody is going to read a day
document. They are going to want a numbered list. The gate is the excuse to write it while the
system is calm.

There is a term worth defining because it appears in every incident review: a **deviation** is any
step you performed that the written procedure did not contain, or any written step you skipped. It
is not a failure. It is information about the gap between how you think the system works and how it
does.

## Why Sutra needs it

Days 60 to 64 leave behind a system with several moving parts and no single document that says how
to operate it. A run can be started, killed, listed, approved, rejected and resumed, and that
knowledge currently lives in five day documents.

Phase 11 puts Sutra on a schedule — a job that runs without anybody watching — and the first time a
scheduled run parks for an approval that nobody answers, the person who has to sort it out will need
to know three things: how to see what is pending, how to decide it, and how to make the run continue
afterwards. Those are steps 5, 6 and 7 below. Writing them now, while the system is being drilled
deliberately, costs an hour. Writing them at the point of need costs the outage.

## The mechanism

The runbook for this drill. It is written before the first command is run, and it is written in the
imperative, one command per step, with what should happen after each.

```text
PHASE 9 DRILL - kill it mid-run

  0. floor      reset the state directory, so nothing carries over
                  uv run python -c "import _store; _store.reset()"
                expect: no output, state/ exists and is empty

  1. start      begin a run on a real ticket
                  uv run python runner.py start 4610 --run-id d1
                expect: five stages run, "parked awaiting appr-d1", exit 2

  2. kill       run it again from the floor, killed mid-stage
                  uv run python runner.py start 4610 --run-id d2 --kill-at during-research
                expect: "[killed at during-research]", exit 137

  3. resume     continue the killed run in a NEW process
                  uv run python runner.py resume d2
                expect: intake and classify "reinstated", research runs again, exit 2

  4. list       look at what is waiting, as the operator
                  uv run python approve.py list
                expect: one pending row for appr-d2, with the payload visible

  5. decide     approve it, by name
                  uv run python approve.py approve appr-d2 --by operator-a
                expect: "appr-d2 approved by operator-a"

  6. finish     resume once more
                  uv run python runner.py resume d2
                expect: "close applied (key d2:appr-d2)", exit 0

  7. count      count the effect, from the file, not from the output
                  uv run python -c "import _store; print(len(_store.closed()))"
                expect: 1

  findings:     (write them here as they happen, not afterwards)
```

**Line by line:**

- **Step 0 exists** because a drill that starts from whatever was lying around from last time is not
  reproducible. Resetting first is the difference between an experiment and an anecdote.
- **Step 1 and step 2 start separate runs.** Step 1 is the control: what a run looks like when
  nothing goes wrong. Without it, step 3's output has nothing to be compared against.
- **Step 3 says "in a NEW process" in capitals** because that is the whole claim. Resuming inside
  the same interpreter would prove nothing — the state would still be in memory.
- **Step 4 is the operator's step**, and it is deliberately a different command from steps 1 to 3.
  If listing pending approvals were a flag on the runner, the reviewer would need the runner, and
  the pause would stop being free.
- **Step 5 names the approver.** `--by operator-a` is not decoration: the trail in section 4 has to
  answer *who*, and a decision with no name attached cannot answer it.
- **Step 7 counts from `_store.closed()`**, which reads the file, rather than from the runner's
  printed line. Step 6 already printed "applied"; step 7 exists to check that the world agrees.
- **The findings line is part of the document**, not an afterthought. A section that is added later
  gets filled in from memory.

Run it as written:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python -c "import _store; _store.reset()"
uv run python runner.py start 4610 --run-id d2 --kill-at during-research; echo "exit: $?"
```

**Line by line:**

- The `-c` form is used rather than a `reset.py` script because there is no other reason for such a
  script to exist, and an extra file in `lab/` is an extra thing to keep true.
- `echo "exit: $?"` prints the exit code the shell just received. Without it the number is invisible,
  and the number is the criterion (part 1.2).

Measured on 2026-09-05:

```text
start  d2: ticket 4610
  intake    ran        ticket=4610 text=Signed out mid-form. The customer fill...
  classify  ran        label=auth
  [killed at during-research]
exit: 137
```

## When it breaks

The runbook breaks by being written *afterwards*, and the tell is that it is too clean.

A runbook reconstructed from a successful drill has no step for the thing that went wrong, because
by the time you write it you have already fixed the thing that went wrong and it no longer feels
like part of the story. What you get is a document that describes a drill nobody ran.

Here is the concrete version from this day. Step 4 above says the operator lists pending approvals.
The first time that step was executed, it printed:

```text
no approvals on file
```

which was correct and useless: the run in step 2 was killed before it parked, so no approval had
been filed yet, and the runbook's step order had the operator looking before there was anything to
look at. The fix is the resume in step 3, which is now written before step 4 rather than after it.
Had the runbook been written after a successful pass, step 3 and step 4 would have been in the right
order and nobody would ever have known the ordering was a thing you could get wrong.

## In production

**What a professional writes instead.** The runbook lives in the repository next to the code, not in
a document tool, so that it changes in the same commit as the thing it describes. The test people
apply to it is unkind and correct: *can somebody who has never seen this system follow it at three
in the morning without asking anyone a question?* Anything that fails that test gets rewritten.
Part 6.3 goes into what that means in practice.

**What degrades at scale.** A runbook written against one process assumes you can see the output. On
a real deployment step 3 becomes "find the instance that has the run", which is a question with a
different answer every time, so the runbook grows a step that is really a query. Runbooks rot at
exactly the rate the system changes, which is why the gate re-runs them: an untested runbook is a
document with the same reliability as a memory.

**The failure mode that only appears with real traffic.** In the drill, the operator and the runner
are the same person, so step 5 always happens. In production the approval sits in a queue behind
forty others, the person who can decide it is asleep, and the run has been parked for eleven hours.
The runbook needs a step for that — how to find out how long something has been waiting — and this
one does not have it. That is a finding, and it belongs in the day rather than in a footnote.

**The review comment a senior engineer leaves:** *"This drill is described in prose in the ticket. If
it was worth doing, it was worth writing down as commands, and if it was written down as commands
we should be running it every release rather than every phase. Put it in the repository and give it
an exit code."*

**The interview question:** *"Walk me through what you do when a job is stuck."* The answer that
lands is the one with numbered steps and no improvisation in it, and the follow-up that separates
people is *"where is that written down, and when did you last execute it?"* — because everyone has a
procedure and almost nobody has run theirs.

## Check yourself

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python -c "import _store; _store.reset()"
uv run python runner.py start 4610 --run-id d2 --kill-at during-research; echo "exit: $?"
uv run python approve.py list
```

That last command is step 4 executed too early on purpose. Read what it prints, then say which step
of the runbook has to happen first and why.

**Out loud, without scrolling up:** what is a deviation, and why is a drill with four deviations and
a successful outcome not a clean pass?
