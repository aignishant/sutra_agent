# 1.2 — A criterion ends in an exit code

## One-line answer

A gate criterion has to name the input, the path, the cost and the number that counts as failing,
because a criterion two people can interpret differently is a criterion that gets interpreted
generously by whoever wants to be finished.

## The story

You are moving out of a rented flat, and the landlord meets you at the door with a printed sheet.

The first version of that sheet said one thing: *"The flat is returned in good condition."* You both
read it and you both nodded, and then you spent forty minutes disagreeing about a mark on the
kitchen counter. He thinks it is a burn. You think it was there when you moved in. Neither of you
can prove anything, and the argument is not about the counter at all — it is about the word "good".

The second version of the sheet is two pages of boxes. *Counter: mark, 3cm, photographed on the day
of arrival — yes / no.* *Oven: cleaned — yes / no.* *Keys returned: 2 of 2.* You go round the flat
together ticking boxes, and it takes twenty minutes, and there is no argument, because there is
nothing left to have an opinion about.

The second sheet is not stricter than the first. It is the same standard, written so that two people
in a hurry cannot read it two different ways.

## The idea in plain language

The plan writes each phase gate as one sentence, and Phase 9's is *"kill it mid-run; it resumes; a
human approved the write."* That sentence is an excellent **description** and a poor **test**, for
the same reason "good condition" is: three people would check three different things and all three
would be reading it honestly.

Turning a sentence into a criterion means answering four questions, and the fourth is the one that
does the work.

1. **On what input?** Not "a ticket" — ticket `4610`, from a fixture that is in the repository, so
   the run is the same run tomorrow.
2. **Through what path?** Which stages ran, which were reinstated from the log, and in what order.
3. **At what cost?** How many provider requests. Zero is an answer, and it has to be stated rather
   than assumed.
4. **What number counts as failing?** An **exit code**, so that the result of the criterion is a
   fact rather than a paragraph.

Some vocabulary, because two of these words get used loosely. An **exit code** is the small integer
a process hands back to whatever started it when it finishes; by long convention `0` means it
succeeded and anything else means it did not. A **criterion** here is one command plus the exit code
that means it held.

Why the fourth question matters more than the other three: a phase gate exists precisely for the
moment when somebody wants to be finished. That is not a character flaw, it is Friday afternoon. A
criterion that produces a sentence gets read charitably at exactly the moment charity is most
expensive. A criterion that produces `1` cannot be read charitably at all.

## Why Sutra needs it

Day 59 closed Phase 8 with six criteria, and every one of them ended in an exit code for this
reason. This day inherits that discipline and applies it to a harder claim, because Phase 9's
promises are about things that *did not happen*: no work was lost, no work was done twice, no write
happened without a decision.

Absence is hard to test. "The ticket was not closed twice" cannot be observed by watching the run
succeed — it is observed by **counting rows afterwards**, which means the criterion has to say which
rows, in which file, and what the count must be. That is what makes the counting scripts in this day
the criteria rather than an appendix to them.

## The mechanism

Here is the difference between the two ways of writing it, side by side. The bad version first:

```text
Criterion: the triage run survives being killed and eventually closes the ticket.
```

Nothing in that sentence tells you which ticket, where the kill lands, how many closes are allowed,
or how you would know it failed. Every one of those gaps is a place a tired person can be generous.

The version the drill actually enforces:

```python
# One kill, stated as a criterion rather than as a hope.
#
#   input   ticket 4610, from ARCHIVE in _desk.py
#   path    intake, classify -> killed -> resume -> research, draft, review -> parked
#           -> approved by operator-a -> resume -> closed
#   cost    5 provider requests, because research is paid for twice
#   fails   final exit != 0, or the number of close rows for this run != 1
KILLS = {
    "K1": ("during-research", "killed mid-stage, after the work, before the checkpoint"),
    "K2": ("after-draft", "killed after a checkpoint, before the gate is filed"),
    "K3": ("parked", "killed while parked, waiting for the human"),
    "K4": ("window", "killed after the decision, inside the effect window"),
}
```

**Line by line:**

- `KILLS` is a dictionary rather than four functions, so the drill's structure is data. A new kill
  point is a new row, not a new branch, which is what makes part 6.2's advice — rotate the drill —
  something you can actually do.
- The first element of each pair is a string the runner understands as *"stop here"*. It is passed
  through to `runner.py --kill-at`, so the kill point is chosen by the drill and obeyed by the
  process being killed, rather than being simulated by the drill on the outside.
- The second element is the sentence that says why this kill exists. It is printed as the heading of
  each block, so the output explains itself to somebody reading it cold months later.
- Note what is **not** in the dictionary: how many closes are allowed. That is not per-kill, it is
  the invariant that every kill shares, so it lives in one place at the bottom of the drill and
  cannot drift between rows.

And the check that turns four runs into a verdict:

```python
good = row["exit"] == 0 and row["closes"] == 1
```

**Line by line:**

- Two conditions, joined, because either alone is passable while the system is broken. A run can
  exit `0` having closed the ticket twice — that is exactly what part 3.5 shows — and a run can close
  the ticket exactly once and still exit non-zero because it crashed afterwards.
- `row["closes"]` is counted from the effects file on disk **after** the processes have all exited,
  not tallied by the runner as it goes. A count kept by the thing being tested is not evidence.
- `== 1` rather than `>= 1`. Under-doing and over-doing are both failures, and a criterion that only
  catches one of them will pass the day you start retrying.

## When it breaks

The failure mode is a criterion that is technically checkable and checks the wrong thing. Here is a
real one from this day's own drill, caught by running it.

The first version of `budget.py` counted requests by reading the number the runner printed on its
way out. That is checkable, it is automatic, and it is wrong. It is kept runnable rather than
described, because a mistake you can execute teaches more than a mistake you are told about:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python budget.py --naive
```

**Line by line:**

- `--naive` swaps the counter, and nothing else. Same runs, same kills, same order — the only change
  is that the spend is summed from the `spent N requests` lines on stdout instead of read back out
  of the run log.
- It prints only the two scenarios that disagree, because those two are the whole argument.

Measured on 2026-09-06:

```text
counting the first way: adding up what the runner printed

  clean run, approved, closed          4 requests
  killed in research, then resumed     3 requests

  the killed run looks 1 request(s) cheaper than the clean one
  it is not. the process that paid for research died before it could print.
```

The killed run appears to be **cheaper than the clean one**. It is not, obviously; the killed
process paid for a request and then died before it could print anything, so the count silently
dropped the spend it could not see. A criterion built on that number would have reported that
crashing saves money.

The fix was to make the spend durable — written into the run log at the moment it is incurred, so it
survives the process that incurred it — and to count from the log instead of from the output. The
same scenario then reads:

```text
  clean run, approved, closed          4 requests
  killed mid-research, then resumed    5 requests
```

Five against four: the extra request is the one the crash threw away. That is the number the phase
actually costs, and it is only visible because the criterion stopped trusting a report from a
process that was about to die.

## In production

**What a professional writes instead.** Every criterion becomes an executable, and the gate document
holds the command and the expected exit code rather than the prose. The prose is still written — it
has to be, or nobody knows *why* the number is that number — but it sits next to the command instead
of replacing it. The test is that a colleague who was not there can re-run the gate.

**What degrades at scale.** Exit codes are one integer, so a suite of criteria that all return `1`
tells you how many failed and nothing about which. That is fine at seven criteria and useless at
seventy, which is why the aggregate in this day prints the *label* of every failing criterion before
it returns. The moment a gate has more criteria than fit on a screen, the exit code stops being the
whole interface and starts being the summary of a report.

**The failure mode that only appears with real traffic.** Criteria written against a fixture stay
green while the real system drifts away from the fixture. Ticket `4610` will pass this drill for
ever. It says nothing about the ticket that arrived this morning with an attachment nobody planned
for. Part 6.2 is about that decay, and the mitigation is rotation rather than more criteria.

**The review comment a senior engineer leaves:** *"Criterion 3 says 'the audit trail is adequate'.
Adequate for what, judged by whom, and what does the command print when it is not? Give me the four
questions the trail has to answer and the exit code when one of them cannot be answered, and I will
review the criterion. Right now I can only review your confidence."*

**The interview question:** *"How do you write an acceptance criterion for something that is
supposed to* not *happen?"* The honest answer names counting: *"You cannot observe an absence by
watching the happy path, so you count the thing afterwards and assert the count. For our approval
gate the criterion is not 'the write was authorised', it is 'exactly one row exists in the effects
file for this approval id' — and I check it after a kill in the worst place, because that is the
only condition under which the count is ever wrong."*

## Check yourself

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python budget.py
uv run python -c "import _store; _store.reset()"
uv run python runner.py start 4610 --run-id n2 --kill-at during-research > /dev/null
uv run python runner.py resume n2 > /dev/null
grep '"kind": "spent"' state/runs/n2.log
```

Find the line that says how many extra requests a mid-stage kill costs, then find the two lines in
that `grep` output that prove it. The rebuild is necessary because `budget.py` resets the state
directory between scenarios, so no single scenario's log survives the whole run.

**Out loud, without scrolling up:** take the sentence *"the system recovers correctly from a
crash"* and turn it into a criterion by answering the four questions.
