# 2.1 — What has to be on disk before you can kill anything

## One-line answer

The drill can only test what survives the process, so the instrument keeps three separate files —
how far the run got, who decided what, and what actually changed in the world — and anything not in
one of them did not happen.

## The story

Four people share a flat and there is a chore rota stuck to the fridge with a magnet. It is a grid:
names down the side, weeks across the top, a tick in the box when the bins go out.

It is not there because nobody can remember whose turn it is. It is there because the person who
knows whose turn it is went to visit her parents for a fortnight, and the flat has to keep working
while she is gone. The grid holds the state of the flat outside of any one person's head. Whoever is
standing in the kitchen on Tuesday can look at it and know what to do, including the new flatmate
who moved in on Sunday and has never met anybody.

The moment the rota only exists in somebody's memory, the flat has a single point of failure who
sleeps eight hours a night and sometimes goes away.

## The idea in plain language

A process is a memory that goes away. Everything a running program is holding — the variables, the
half-built results, the fact that it was on step three of five — exists only while the process
exists, and when the process ends, all of it ends at the same instant.

So the drill has exactly one question to ask about any piece of state: **is it on disk?** If it is,
it survives the kill and a new process can pick it up. If it is not, it is gone, and no amount of
careful code will bring it back.

This instrument keeps three files, and they are separate because they answer three different
questions and are trusted by different people:

| File | Answers | Read by |
| --- | --- | --- |
| `state/runs/<id>.log` | how far did this run get, and what did each stage produce | the resuming process |
| `state/approvals/<id>.json` | who decided what, seeing exactly what text | the audit, months later |
| `state/closed.jsonl` | what actually changed in the world, and how many times | the person counting |

Two terms, defined once because the rest of the day leans on them.

An **append-only log** is a file you only ever add lines to the end of — you never go back and edit
a line. That constraint is what makes it safe to read after a crash: a half-written last line can be
thrown away, and every line before it is still true. Day 60 built the run's log this way and its
part [2.1](../../../day-60-durable-execution/parts/02-the-log-is-the-run/2.1-the-log-is-the-run.md)
is where the argument lives.

A **checkpoint** is the moment a run writes down enough to be picked up from, and here that is one
line in the run log per completed stage. Day 61 is the day about checkpoints in the framework; this
day only needs the property that they exist and are on disk.

The third file is the one people leave out, and it is the one this day's hardest criterion depends
on. `closed.jsonl` is not a *record* that the ticket was closed — it **is** the ticket being closed.
That distinction is the whole of part 3.4, and it only makes sense if the two things are the same
write.

## Why Sutra needs it

Every kill in section 3 is really a question about one of these three files, and the interesting
kills are the ones that land between two writes rather than inside one.

Section 4's audit then reads only these files, with the session gone and the logs rotated, and
answers four questions a sceptical colleague asks three months later. If a question cannot be
answered from a file, it cannot be answered, and part 4.2 is what that failure looks like from the
inside — a trail that sounds certain and is missing the thing that mattered.

## The paper behind it

> **Distributed snapshots: determining global states of distributed systems** ·
> `doi:10.1145/214451.214456` · 1985 · <https://doi.org/10.1145/214451.214456>

It showed how a system made of separate parts can record a state of the whole that is *consistent* —
one that could really have existed — even though no part can see the others and no two clocks agree.

Taught in
[Day 60's paper part](../../../day-60-durable-execution/papers/01-distributed-snapshots.md).

## The mechanism

The write that everything else depends on:

```python
def _durable_append(path: Path, row: dict) -> None:
    """Append one JSON line and push it to the platter before returning."""
    _ensure()
    with path.open("a", encoding="utf-8") as handle:
        handle.write(json.dumps(row, sort_keys=True) + "\n")
        handle.flush()
        os.fsync(handle.fileno())
```

**Line by line:**

- `path.open("a", ...)` opens for **append**, so two processes writing at once cannot overwrite each
  other's bytes, and a resumed process never has to seek to the right place.
- `json.dumps(row, sort_keys=True)` sorts the keys, which is why every log line in this day has its
  fields in alphabetical order. It costs nothing and it means two runs of the same drill produce
  byte-identical logs, so a `diff` between them is meaningful.
- `handle.write(... + "\n")` — one row, one line. That is what makes a torn final line safe to
  discard: the damage cannot reach the line before it.
- `handle.flush()` moves the bytes out of Python's own buffer into the operating system. Without it,
  a kill loses everything the program thinks it has written but has not handed over.
- `os.fsync(handle.fileno())` moves them out of the operating system's cache onto the disk. This is
  the line people leave out, and leaving it out makes the drill dishonest rather than merely slower:
  the process would report a checkpoint that a hard kill would take with it.

Here is a whole run's log, after being killed mid-stage and resumed:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python drill.py --kill K1 > /dev/null
cat state/runs/k1.log
```

**Line by line:**

- `--kill K1` runs the one kill that lands between a stage's cost and its result, which is the only
  kill whose damage is visible in the log as a duplicated line.
- `> /dev/null` throws the drill's narrative away, because the point here is the file it left rather
  than what it said while running.
- `cat` rather than a script: the log is meant to be readable by a person with no tooling. If it
  needed a viewer, a colleague at 3am would not read it.

Measured on 2026-09-05:


Read the sixth and seventh lines. `{"cost": 1, ... "stage": "research"}` appears **twice**, and there
is only one `{"kind": "stage", ... "stage": "research"}` after them. That pair of lines is the
crash, written down: the first process paid for the research request and died before it could record
what the request produced, so the second process paid for it again. Nobody had to be told that
happened. It is in the file, and part 5.4 counts it.

## When it breaks

Take the `fsync` out and the drill starts lying, quietly and in your favour.

Without it the bytes sit in the operating system's cache. A `os._exit` — which is how this drill
kills — does not flush them, and neither does the operating system if the machine loses power. The
resumed process then reads a log that is missing its last few lines and re-runs stages it had
already completed, which looks like a correctness bug in the resume logic and is actually a
durability bug two layers down.

The version you can produce on purpose is the torn line. Kill a process in the middle of a write and
the log's last line is a fragment:

```bash
uv run python tear.py; echo "exit: $?"
```

**Line by line:**

- `tear.py` runs a real run to completion, then truncates a thirteenth line onto the end of its log
  so the file looks exactly like one a crash interrupted.
- It then reads the log with `_store.read_events`, the strict reader every other script in this day
  uses, so the failure you see is the one the resume path would actually hit.

Measured on 2026-09-05:

Twelve good lines and one bad one, and the reader refuses to hand back any of them. That is the
right instinct applied in the wrong place: the resume is now impossible because of damage to a stage
that never completed.

The smallest fix is not to make the write atomic — you cannot, in general — but to make the reader
tolerant of a **final** line that will not parse, because by construction that is the one the crash
interrupted:

```bash
uv run python tear.py --tolerant; echo "exit: $?"
```

**Line by line:**

- `--tolerant` swaps in a reader that parses line by line and drops a broken line only when it is
  the last one. A broken line anywhere else means something other than a crash damaged the file, and
  that must still raise.

```text
log now holds 12 whole lines and one fragment
  dropped a torn final line (57 bytes)
  tolerant reader recovered 12 events
exit: 0
```

## In production

**What a professional writes instead.** Three files become one database with three tables and a
transaction around each write, and `fsync` becomes the database's problem rather than yours. What
does *not* change is the discipline: the effect and the record of the effect belong in the same
transaction, and everything else is a convenience. Teams that get this wrong usually get it wrong by
putting the run state in a database and the effect somewhere else, which recreates the window part
3.4 measures.

**What degrades at scale.** These files grow without limit. A log per run is fine at one run per
minute and is a problem at a thousand, so real systems truncate: the log holds the recent stages in
full and older ones as a summary, or a compaction job folds a finished run into one row. Compaction
is where audit trails quietly die, because the summary keeps what the *resume* needed and drops what
the *audit* needed, and nobody notices until section 4's questions get asked.

**The failure mode that only appears with real traffic.** Two processes resuming the same run at the
same time both append to the same log, and append-only does not mean conflict-free: you get two
interleaved copies of the same stages, each internally sensible. Nothing in this drill has two
resumers. A real system needs a lease — a claim on the run that only one process can hold — and this
one does not have one. That is a real limitation of this instrument and it is stated here rather
than discovered by the reader.

**The review comment a senior engineer leaves:** *"You are writing the run state and the business
effect to two different places, so there is a moment when one exists and the other does not. Either
put them in one transaction or tell me which of the two failure modes you have chosen, because you
have chosen one."*

**The interview question:** *"What does `fsync` actually buy you?"* The answer that shows experience
is the one that names both layers: *"`flush` gets the bytes from my program to the kernel; `fsync`
gets them from the kernel to the device. If I only flush, my process crashing is survivable but the
machine losing power is not, and on a checkpoint that is the difference between a run that resumes
and a run that repeats work I have already paid for."*
