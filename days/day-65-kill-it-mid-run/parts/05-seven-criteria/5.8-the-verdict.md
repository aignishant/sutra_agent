# 5.8 — The verdict: green, or a named list

## One-line answer

The gate runs all seven criteria, prints the label of every failing one, and refuses to summarise —
because a phase is either green or it is a specific list of things that are not done, and "mostly
green" is not a state anything can act on.

## The story

The rating sticker goes in the restaurant window with a number on it from zero to five.

The inspector does not decide the number by forming an impression. He goes through a list: the fridge
temperature, the handwashing basin, the cleaning records, the pest checks, the staff training log. Each
one gets a mark. The sticker in the window is the *worst* of what he found, not the average of it,
because a kitchen with immaculate records and a warm fridge is a kitchen that will make somebody ill.

The owner already knows which item was the problem before the inspector says it. What he wants is the
number, so he can put it in the window. What he needs is the list, so he can fix the fridge.

The inspector gives him both, in that order, and the list is longer than the number.

## The idea in plain language

Seven criteria have been built, one per part. This is the command that runs them all and produces the
phase's answer.

Two design decisions in it are worth defending, because both are the opposite of what feels natural.

**The verdict is a conjunction, not a score.** There is no "five of seven". A phase gate exists to
answer whether the phase can be built on, and a phase with one broken criterion cannot — the next
phase will lean on it and find out. So the exit code is `0` only when every criterion is `0`, and any
red makes the whole gate red with no partial credit.

**The output is a named list, not a count.** `findings: 3` is useless on its own; three *what*. So the
gate prints the label of every failing criterion, and it runs all seven before reporting rather than
stopping at the first failure. That last part matters more than it looks: a gate that stops at the
first red turns one afternoon of fixing into as many afternoons as there are failures, each ending in
the discovery of the next one.

And one honest consequence, which part 1.1 stated as a warning and this part has to live up to: a gate
that comes out green on its first run has probably not looked hard enough. This one does not.

## Why Sutra needs it

This is the command Phase 9 is judged by, and the row it produces goes into `docs/PROGRESS.md`. What
gets written in that row is the sentence somebody reads a year from now to decide whether durability
in this repository can be trusted.

Principle 10 is the whole of this part. The gate is the last place in the phase where it would be easy
to round up, and the temptation is real: four of the seven criteria are green, the three that are not
are about the repository rather than the running system, and a sentence like *"the durability
machinery all passes"* would be true and would be a lie.

## The mechanism

The aggregate, in full:

```python
def main() -> int:
    print(f"{'criterion':34s} {'exit':5s} verdict")
    findings = []
    for label, args, cwd in CRITERIA:
        code = run(args, cwd)
        verdict = "green" if code == 0 else "RED"
        print(f"{label:34s} {code:<5d} {verdict}")
        if code != 0:
            findings.append(label)
```

**Line by line:**

- The loop runs **every** criterion. There is no early exit, which is the decision described above:
  one report, not a sequence of discoveries.
- It prints the row as it goes rather than collecting and printing at the end, so a criterion that
  hangs still leaves evidence of how far the gate got. A gate that prints nothing until it finishes is
  a gate that tells you nothing when it does not.
- `findings.append(label)` stores the **label**, not the exit code. What a person needs from a red gate
  is the name of the thing to go and look at; the code is already on the row above.
- `code = run(args, cwd)` runs each criterion as a child process, so a criterion that crashes outright
  is reported as red rather than taking the gate down with it.

Then the red-alarm test, which is this day's answer to Principle 11:

```python
    caught = run(["bypass.py", "--trust-state"], HERE) != 0
    print(f"\n{'the red-alarm test':34s} {'':5s} {'passes' if caught else 'FAILS'}")
    if not caught:
        findings.append("the bypass check does not go red when the payload is swapped")
```

**Line by line:**

- This runs criterion 2 **with the check deliberately broken** — executing the live draft instead of
  the approved payload, part 5.2's ablation — and asserts that it goes red.
- `!= 0` is the assertion: the gate is checking that a known-bad system **fails**. Every other line in
  this file checks that a good system passes; this one checks that the checking works.
- If the alarm does not sound, that is itself a finding with its own sentence, because a criterion that
  cannot fail is worse than a missing criterion — it occupies the place where a real check would go.


**Line by line:**

- One command, no arguments. The gate must be runnable by someone who has read none of this day, or it
  is not a gate.

Measured on 2026-09-06:

```text
criterion                          exit  verdict
1 it resumes, once                 0     green
2 the gate cannot be bypassed      0     green
3 the trail answers from rows      0     green
4 the budget is measured           0     green
5 the freshness check              1     RED
6 every day is written             1     RED

findings: 3
  - 5 the freshness check
  - 6 every day is written
  - 7 no open IDs in the phase

phase 9 green: False

```

**Four green, three red, and Phase 9 is not green.** That is the verdict, and the rest of this section
is what it means rather than an argument with it.

The four green criteria are the running system. The triage graph survives all four kills and closes
exactly once; there is no path to the write without a valid decision, including the payload swap; the
audit answers all four questions from rows alone; and the request budget is a counted number with a
measured durability premium of one request per mid-stage kill. The durability machinery works.

The three red criteria are the repository, and they are red for two different reasons.

**Criteria 6 and 7 are red because Phase 9 is not finished.** Days 61 and 64 have 11 and 21 part
documents on disk at the moment this ran, and neither has a hub yet, so neither declares its IDs —
leaving `ADK-44`, `ADK-45`, `ADK-48` and `ADK-76` open. That is not a defect; it is a phase in
progress being measured while in progress, and the correct reading of those two reds is *come back
when the days have landed*. Part 5.7 called that list a worklist rather than a complaint, and this is
the moment the distinction earns its keep — while this day was being written, that same list held
eight identifiers and shrank to four without anybody fixing anything.

**Criterion 5 is red for a reason that will not fix itself**, and it carries the day's most
uncomfortable finding. `google-adk` is pinned at 2.7.1 with 2.8.0 available, which needs a decision
under Principle 14 rather than an upgrade. And `mcp==1.29.1` is pinned with no row in
`docs/PACKAGES.md` — a Principle 7 defect that **Day 52's phase gate found, Day 59's phase gate found,
and this gate has now found for the third time.**

That third finding is the one to write in the ledger. Three consecutive phase gates have reported the
same unfixed defect, which says nothing about the package and something quite specific about the
process: the gates are working and their output is not being acted on. Part 6.2 is about what that
does to a gate over time.

## When it breaks

The way a verdict breaks is by being written as prose after the fact.

Everything above is a machine-readable result, and then a human writes a row in `docs/PROGRESS.md`. The
gap between the two is where phases become green that were not, and it does not take dishonesty — it
takes a summary. *"Phase 9 gate: durable triage with human approval, all recovery criteria pass"* is
composed entirely of true statements. It is also how a reader a year later concludes the phase closed
clean.

The rule that holds the line is that the ledger row records the **verdict**, not the impression, and
that a phase closing amber says so in the gate column with the findings named. This curriculum has a
precedent for exactly that: Day 52's gate and Day 59's gate both closed with findings recorded rather
than resolved, and the `mcp` row is traceable across all three precisely because each of them wrote
down what it found instead of what it hoped.

The second break is subtler and this gate is vulnerable to it: **the red-alarm test only covers
criterion 2.** Criteria 1, 3 and 4 all have ablation switches — `--mode unsafe`, `--thin`, `--naive` —
and every one of them is demonstrated in its own part, but the aggregate gate only asserts that the
bypass check goes red on demand. Criteria 5, 6 and 7 have no ablation at all, and are currently red
anyway, which is a state that hides a check that cannot pass. The honest statement is that this gate
proves one of its seven checks can fail and takes the other six on the evidence of their own parts.

## In production

**What a professional writes instead.** The gate is a pipeline stage that blocks a release, and its
output is a structured artefact — one row per criterion with a name, a verdict and a link to the
evidence — rather than text on a terminal. Findings that are accepted rather than fixed become
recorded exceptions with an owner and an expiry date, so an accepted risk shows up again when the
expiry passes instead of quietly becoming permanent.

**What degrades at scale.** Seven criteria produce a report a person reads. Seventy produce a report a
person scrolls past, and the failure is silent because the gate is still working perfectly. Real
systems group criteria into categories with a rolled-up verdict per category and detail on demand —
which reintroduces the summarisation problem this part warns about, at one level up, and is why the
rolled-up value must be the worst of the group rather than the average.

**The failure mode that only appears with real traffic.** A criterion that has been red for so long
that its red is load-bearing. Somebody writes a filter to hide it, or the pipeline is configured to
allow that stage to fail, and now the gate has a permanent hole that looks like a green build. The
`mcp` finding in this day is three gates into exactly that trajectory.

**The review comment a senior engineer leaves:** *"Your gate reports three findings and your progress
row says the phase is done. Those cannot both be right. Either the findings are not blocking — in
which case say so and record who decided that — or the row is wrong."*

**The interview question:** *"You are asked to sign off a milestone and two checks are failing for
reasons outside your team. What do you do?"* The answer that shows experience refuses the framing:
*"I sign off what is true, which is a list rather than a word. The running system passed everything I
built it to pass — recovery, the approval gate, the audit trail, the budget — and two checks about
completeness are red because the work is genuinely unfinished. Writing 'green' would make the next
team lean on something that is not there, and writing 'red' without the breakdown would hide four
properties that are actually solid. The one thing I will not do is average them, because a gate is the
worst of what it found and not the mean."*
