# 5.7 — Criterion 7: no open IDs in the phase

## One-line answer

Every concept the plan assigns to Phase 9 must be declared by a day that exists, and the check
compares the plan's assignment against each hub's own frontmatter — reporting the difference rather
than asserting that there is none.

## The story

The shop does a stocktake on the last Sunday of the month. The shelf label says there should be
fourteen bottles of the own-brand olive oil. There are eleven.

Nobody is accused of anything. Three bottles is a difference, and a difference has causes: two were
broken and swept up, one was sold and rung up as something else, or the delivery was short and signed
for anyway. The count does not tell you which. What it does is make the difference **exist as a
number**, so that somebody has to account for it.

The alternative is the shop that never counts. Its shelf labels are perfect. Every one of them says
exactly what should be there, and the labels stay perfect no matter what happens to the stock, because
nothing ever compares the two.

## The idea in plain language

Plan §6 gives every concept in this curriculum an ID — `ADK-44`, `AG-23`, `OPS-11` — and §14 assigns
each ID to exactly one day. A day **closes** an ID by declaring it in its hub's frontmatter, and
`docs/TRACEABILITY.md` is generated from those declarations.

An **open ID** is one the plan assigns to a day that no written day declares. Plan §15 rule 2 is
blunt about what that means: a phase is green only when no ID from this phase or any earlier one is
open.

The check is a stocktake. On one side, the plan's assignment for days 60 to 65. On the other, what
each day's hub actually says about itself. Print both, compare, and report the difference.

Two ways it can differ, and they mean different things:

- **the hub declares nothing**, because the day is not written — which is criterion 6's failure showing
  up again, one layer along;
- **the hub declares something different** from what the plan assigns — a day that closed an ID
  belonging to another day, or missed one of its own. That is the one this check exists for, because
  nothing else in the repository would notice.

The second is worth dwelling on. The `day-sutra` skill says a day closes **exactly** the IDs §14
assigns to it — no more, no fewer — and both directions of that are enforceable only by comparing the
two lists. A day that closes an extra ID makes a later day's subject vanish from the traceability
ledger while appearing complete.

## Why Sutra needs it

`docs/TRACEABILITY.md` is the document that says this curriculum covered what it promised to cover.
It is generated, which makes it accurate about what the hubs say and says nothing about whether the
hubs are right.

This criterion is the check on that. It is also the last one before the verdict, deliberately: the
first four criteria test whether the **system** works, criteria 6 and 7 test whether the
**curriculum** is honest about what it has built, and a phase gate that only did the first kind would
pass a working system that had quietly skipped a subject.

## The mechanism

Two sources, read independently, printed side by side:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python ids.py; echo "exit: $?"
```

**Line by line:**

- `ids.py` reads the plan's §14 day map for days 60 to 65 on one side, and each day's hub frontmatter
  on the other. The same independence rule as criterion 6: an expectation and an observation with
  different origins, or the comparison is a tautology.
- It resolves each day's folder **by number**, accepting any slug, so a renamed folder does not read
  as a missing day.
- It prints a row per day whether the two agree or not, then the open list, then the rule it is
  applying. The rule is printed because a red gate is read by somebody who was not there when it was
  designed.

Measured on 2026-09-06, while Phase 9 was still being written:

```text
day  plan says                    hub declares                 agrees
60   AG-22, ADK-43                AG-22, ADK-43                True
61   ADK-44, ADK-45               -                            False
62   AG-23, ADK-46                AG-23, ADK-46                True
63   SEC-05, ADK-47               SEC-05, ADK-47               True
64   ADK-48, ADK-76               -                            False
65   OPS-11                       OPS-11                       True

days with no hub yet   [61, 64]
open IDs               ['ADK-44', 'ADK-45', 'ADK-48', 'ADK-76']

Plan section 15 rule 2: a phase is green only when no ID from this or any
earlier phase is open. The list above is what stands between this repository
and green.
exit: 1
```

Four days agree. Days 61 and 64 declare nothing, because neither has a hub yet — the `-` in the
middle column is the same fact criterion 6 reported as `NO`, seen from the ID side.

The bottom line is the useful one. `open IDs` is not a complaint; it is a **worklist**. Four
identifiers, each a concept the plan promised that no written day has yet claimed.

Watch it empty. When this command was first run for this part, the open list held **eight**
identifiers and only day 60 agreed — days 61 through 65 all declared nothing. Days 62, 63 and 65 then
landed their hubs, and `AG-23`, `ADK-46`, `SEC-05`, `ADK-47` and `OPS-11` left the list without
anybody fixing a defect. When day 61's hub lands, `ADK-44` and `ADK-45` go; when day 64's lands,
`ADK-48` and `ADK-76` go, and the list is empty. That is what makes this a measurement of progress
rather than a verdict on somebody.

That is also why the criterion is phrased as *run it and read it* rather than as an assertion that the
list is empty. A snapshot of a moving repository is exactly what an ID audit is, and a check that goes
red because somebody is halfway through the next day is a check that cries wolf on ordinary progress.
The gate cares about the state at the moment the phase is declared finished; part 5.8 is that moment.

## When it breaks

The break is the one direction this check catches and nothing else does: a hub that declares an ID
belonging to somewhere else.

Suppose day 61's hub, writing about pause and resume, declares `ADK-44, ADK-45, ADK-46`. It is an easy
mistake — `ADK-46` is the human-in-the-loop framework surface, day 61 touches the seam where a run
waits for a person, and a writer with the plan open in another window can reasonably think it belongs.

Now watch what happens to every other signal. `docs/TRACEABILITY.md` regenerates and shows `ADK-46`
closed, with a link to day 61. Criterion 6 passes, because both days exist. Nothing in the repository
is broken. And day 62, whose actual subject `ADK-46` is, now covers a concept the ledger already
believes is done — so if day 62 is ever thinned, or its hub loses the ID in an edit, the loss is
invisible.

This check catches it on the row for day 62, which would read `plan says AG-23, ADK-46` and `hub
declares AG-23`, `agrees False` — while day 61's row would read `False` too, for having one too many.
Two red rows from one mistake, which is the shape you want: the check names both the day that took the
ID and the day that lost it.

The second break is the one this check shares with criterion 6, and it must be said plainly. **A
declared ID is not a taught ID.** `ids.py` reads frontmatter. A hub can declare `ADK-45` in a day whose
parts never mention checkpoints, and this criterion will report `True`. It is checking bookkeeping, not
teaching. `./m depth` checks the shape of the teaching, and only reading it checks the substance —
which is exactly why plan §17 says the depth contract carries judgement no checker can make for you.

## In production

**What a professional writes instead.** This is requirements traceability, and in a regulated setting
it is a matrix generated from a requirements document on one axis and test or design artefacts on the
other. The valuable property is identical: the two axes come from different sources and the tool
reports the cells that are empty. The version that has no value is the one where the artefact list is
derived from the artefacts.

**What degrades at scale.** One-to-one assignment stops holding. This plan assigns each ID to exactly
one day, which makes the comparison a set difference; real requirement sets have partial coverage,
several components contributing to one requirement, and requirements that are deliberately deferred.
The check then needs a state per ID rather than a boolean, and the honest states include *deferred,
with a reason* — which this plan expresses with 🅿️ for parked, awareness-level topics.

**The failure mode that only appears with real traffic.** Drift between the plan and the ledger over
amendments. When a day is added or an ID is reassigned by an addendum, the check has to read the
**amended** assignment; a checker that parses only the original §14 table will report a correct
repository as wrong for months, and the response will be to stop running it. Every amendment in this
curriculum is folded into §14 for exactly that reason, and `ids.py` parses §14 rather than any of the
addenda.

**The review comment a senior engineer leaves:** *"This tells me which IDs no day declares. It does not
tell me which day declares an ID it should not. Print the per-day comparison, not just the open list —
the interesting bug is the one where the total is right and the attribution is wrong."*

**The interview question:** *"How do you know a project covered everything it said it would?"* The
answer that shows experience is about the direction of the check: *"You compare a specification you did
not derive from the code against artefacts you did not derive from the specification, and you report
per-item rather than in aggregate. Aggregate coverage hides misattribution — if one component claims a
requirement belonging to another, your totals are perfect and one requirement is now covered by nobody.
And I keep it honest about what it proves: this checks that something declared the item, not that the
item was done well. Those are different questions and I run different tools for them."*
