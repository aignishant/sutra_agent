# 5.3 — Criterion 3: the trail answers from rows

## One-line answer

Section 4's four questions become a command that exits non-zero when any of them cannot be answered
from files alone, which turns "we have an audit trail" from a claim about intentions into a check
that fails in the build.

## The story

The school trip needs a consent form. It asks for the child's name, the parent's signature, a
contact number for the day, and a box for medical conditions.

At the coach on Friday morning one child has a form with the medical box empty. Not "none" written
in it — empty. The teacher cannot take her, and everyone is standing in the car park while this gets
sorted out.

It looks like bureaucracy right up until you imagine the alternative, which is finding out about the
allergy on a hillside forty miles away. The form is not asking for the information because forms ask
for information. Each line is there because at some point a teacher stood on a hillside and did not
know something.

The empty box is caught at the coach because somebody checks the forms at the coach. If nobody
checked, the form would still be a very good form, and it would be discovered to be incomplete at the
only moment when it is too late to fix.

## The idea in plain language

Part 4.1 wrote the four questions. Part 4.2 showed a design that cannot answer two of them. Part 4.3
turned that into a rule about fields.

None of that is a gate. A rule in a document is checked when somebody remembers to read the document,
and audit trails thin precisely because nobody re-reads it. So this criterion is the check at the
coach: a command that builds a real closed ticket, asks the four questions of the files it left, and
**exits non-zero if any of them is unanswerable**.

The important design decision is what the command is allowed to use. It gets the state directory and
nothing else. It does not import the runner, hold anything over from the run it performed, or accept
an explanation. That restriction is what makes it a proxy for the person asking in three months, who
also has none of those things.

## Why Sutra needs it

The Phase 9 gate claims *a human approved the write*. Criterion 2 proves the write could not have
happened without a decision. This criterion proves the decision can still be **shown** afterwards,
which is a separate property and the one that survives into every later phase.

Day 92's pre-publication security review is where this stops being about tickets. This repository
goes public in Phase 14, and a system whose approval trail cannot answer "who agreed to this" is a
system nobody should publish as an example.

## The mechanism

The criterion is one command, and it carries its own subject with it:

```python
def build(thin: bool) -> None:
    """Produce one finished, approved, closed run for the audit to interrogate."""
    _store.reset()
    sh("runner.py", "start", "4610", "--run-id", "t1")
    if thin:
        strip_payload("appr-t1")
    sh("approve.py", "approve", "appr-t1", "--by", "operator-a")
    sh("runner.py", "resume", "t1")
```

**Line by line:**

- `_store.reset()` wipes the state directory first, so the audit is performed on a run this command
  made and not on whatever the last experiment left behind. A criterion that passes or fails
  depending on what ran before it is a criterion people learn to re-run until it is green.
- Each step is a **child process** (`sh` shells out), so the run under audit is genuinely separate
  from the process auditing it. Nothing can leak from the run into the answers through a shared
  variable.
- `strip_payload` is applied between the filing and the decision, which is where the design choice
  actually lives — the approval is written when the run parks, so the only place to change how it is
  stored is before anyone decides.
- The whole function is four lines because the run is not the point. The point is what it leaves on
  disk.

Then the questions are asked of the files:

```python
    record = _store.read_approval("appr-t1")
    rows = [r for r in _store.closed() if r["key"].startswith("t1:")]
    executed = rows[0]["text"] if rows else None
```

**Line by line:**

- `read_approval` and `closed()` both read files from `state/`. These three lines are the audit's
  entire input, and the fact that they are three lines is the argument: everything below is derived
  from what survived the processes.
- `rows[0]["text"] if rows else None` — `None` when there is no close row, rather than an index
  error. A closed ticket that was never closed is a legitimate audit finding and must be reportable
  as `UNANSWERED`, not as a crash in the auditor.
- The key filter `startswith("t1:")` scopes to this intention, the same way part 3.5's count does.

## When it breaks

The criterion goes red when the record thins, which is part 4.2 run as an ablation:

```bash
uv run python trail.py --thin; echo "exit: $?"
```

**Line by line:**

- `--thin` files a pointer instead of the payload. It is the ablation switch for this criterion: if
  it does not turn the command red, the command is not checking anything.

Measured on 2026-09-06:

```text
approval store: pointer only

  who decided it               answered    operator-a
  what exactly did they read   UNANSWERED  <see run t1, stage draft>  (the text is not here)
  did that text run            UNANSWERED  cannot be checked: no hash was stored
  was it done once             answered    1 close row(s) for key t1:appr-t1

unanswerable from rows alone: 2 of 4
exit: 1
```

Exit `1`, two questions lost, and the run itself completely unaffected: the ticket was closed
correctly, once, by an operator who approved it. Criteria 1 and 2 both still pass on this system.
That independence is the reason the seven criteria are seven commands rather than one — a single
aggregate check would have been green on three of the four properties and told you nothing about
which one moved.

There is a second break worth naming, and this criterion cannot catch it. `trail.py` audits a run it
**created**, in a controlled sequence, with one draft and one decision. It is a test of the record's
**shape**, not of the records your production system actually holds. A real audit runs against real
rows, including the ones written by the admin tool nobody remembered, and part 4.3's *In production*
section is where that gap lives. Passing this criterion means the design can answer the questions; it
does not mean every row does.

## In production

**What a professional writes instead.** The four questions become a test that runs against a
throwaway database seeded by the real approval code path — not by a helper written for the test —
because the failure being guarded against is precisely that the real path stores something different
from what the test assumes. Some teams go further and run the audit continuously against a sample of
real rows, which turns it from a design check into a monitor.

**What degrades at scale.** The audit reads whole files and scans them. That is right for a check
that builds its own single run and wrong for anything pointed at production, where the same four
questions have to be answered by indexed queries against one approval id. The questions survive the
change; the implementation does not, which is the argument in part 4.3 for keeping the questions
written in English rather than only in code.

**The failure mode that only appears with real traffic.** Partial answers that look complete. A
`payload` field truncated to a column limit renders as text and passes every presence check, and the
audit reports `answered` while showing the operator's draft cut off at 255 characters. The check
tests that a field is there; only the hash comparison tests that it is the **whole** thing, which is a
good argument for keeping question 3 even in systems where questions 1 and 2 feel sufficient.

**The review comment a senior engineer leaves:** *"This test audits a run it created itself. Point it
at a row produced by the bulk-approve tool as well — that path was added after the audit was written
and I do not think it stores the hash."*

**The interview question:** *"How do you know your audit trail actually works?"* The answer that shows
experience is about failing it on purpose: *"By writing the questions down as a check that exits
non-zero, and then proving it can go red — I file the approval with a pointer instead of the payload
and watch two of four questions become unanswerable. If breaking the record does not break the check,
the check is decoration. The subtlety is that the run itself is completely unaffected by the change:
the ticket still closes correctly, exactly once, approved by the right person. Only the ability to
prove it afterwards is gone, and nothing in the system notices."*
