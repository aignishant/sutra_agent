# 5.5 — Criterion 5: the freshness check

## One-line answer

Every phase gate re-asks whether the world moved under the code — the framework, the protocol
revision, the free tiers — and reports **findings with dates**, because "we checked and nothing had
changed" is a result and silence is not.

## The story

There is a fire extinguisher in the corridor with a little tag hanging off it, and the tag has dates
on it in biro.

The extinguisher has not changed. It is the same red cylinder it was three years ago and it looks
exactly as ready. What the tag records is that somebody came and **looked** — weighed it, checked the
pin, and wrote the date.

An extinguisher with no tag is not a broken extinguisher. It is an extinguisher nobody can vouch for,
and the difference only matters once. When the building inspector comes, he does not test it. He reads
the tag, because testing every extinguisher is impossible and reading a date is not.

The tag is not evidence that the extinguisher works. It is evidence that the question was asked
recently, and that turns out to be the only thing anyone can practically check.

## The idea in plain language

The plan's §15 requires a **freshness check** at every phase gate, and Principle 14 says that if
reality changes, the plan is amended first. This criterion is where those two meet.

Code rots without being edited. The version you pinned gets superseded, the free tier you budgeted
against changes its limits, the protocol revision you implemented gets a new one. None of that
produces a failing test, because none of it changes your repository — and that is exactly why it needs
a scheduled question rather than a passing check.

Four questions, from §15:

| Question | Why it belongs at a gate |
| --- | --- |
| has the framework moved | a new `google-adk` may change the durability and HITL surfaces this phase is built on |
| has the protocol revision moved | Addendum 01's standing rule: an MCP revision change is amended before it is coded |
| have the free tiers moved | Addendum 02 denominates the budget in RPM/RPD, and rosters move |
| are the skill provenance rows still valid | a third-party skill's source can change under a pinned name |

And the output rule, which is the part people get wrong: **a finding is a result, and so is "no
drift".** A freshness check that prints nothing is indistinguishable from one that was never run, so
this one always prints what it observed, where it observed it, and when.

## Why Sutra needs it

Phase 9 is built directly on framework behaviour that this curriculum has already watched shift. Day
60 measured that ADK 2.7.1 skips the node that was running when a process died unless
`rerun_on_resume` is set, and that the documented `rerunOnResume` is `rerun_on_resume` in the
installed Python. Those are exactly the kind of facts a minor version changes.

If the framework moves and the phase is not re-checked, the day documents keep describing behaviour
the installed package no longer has — and Principle 8 is violated silently, which is the worst way.

## The mechanism

The check holds two things side by side: what this repository pins, read from disk, and what was
observed by opening a page, carried with its URL and its date.

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python fresh.py; echo "exit: $?"
```

**Line by line:**

- `fresh.py` makes **no network call at all**. That is deliberate and worth defending: a gate check
  that silently depends on the network fails on a train for a reason that has nothing to do with the
  repository, and a check that fails for the wrong reason is a check people start skipping.
- Instead it carries the observations as data, each with the URL it came from and the date it was
  taken, and prints the commands to re-take them. The check verifies the **local** half — what is
  pinned — against the recorded observation, and makes the staleness of the observation visible.
- It exits non-zero when there is a finding, so drift is a red gate rather than a paragraph.

Measured on 2026-09-06:

```text
  google-adk latest on PyPI    2.8.0
                               https://pypi.org/pypi/google-adk/json
  MCP spec revision            2026-07-28
                               https://modelcontextprotocol.io/specification/
  Gemini free-tier RPM/RPD     not published without an AI Studio session
                               https://ai.google.dev/gemini-api/docs/rate-limits
  Groq free plan, groq/compound 30 RPM / 250 RPD
                               https://console.groq.com/docs/rate-limits

pinned here: google-adk==2.7.1  mcp==1.29.1

re-take the observations with:
  curl -s https://pypi.org/pypi/google-adk/json | python -c "import json,sys;print(json.load(sys.stdin)['info']['version'])"
  curl -s https://modelcontextprotocol.io/specification/ | grep -o 'schema/[0-9-]*'
  open https://ai.google.dev/gemini-api/docs/rate-limits
  open https://console.groq.com/docs/rate-limits

findings: 2
  - google-adk pinned at 2.7.1, latest is 2.8.0 - read the release notes for durability and HITL changes before upgrading (Principle 14: amend first)
  - mcp==1.29.1 is pinned with no row in docs/PACKAGES.md (Principle 7)

'no drift, checked 2026-09-05' is a valid finding. Silence is not.
exit: 1
```

Read the third observation, because it is the most honest line in the file. **`not published without
an AI Studio session`** — the Gemini rate-limit page does not render its per-model numbers to an
anonymous fetch. That is not a value, and the check does not invent one. A row that says "I could not
read this, here is where I tried" is worth having; a plausible number that nobody actually read is
worth less than nothing, because it will be believed.

Two findings, and they are different in kind.

**`google-adk` is a version behind.** This is drift, not a defect. Nothing is broken; the pin is
deliberate and the observation is that a newer release exists. What the finding demands is a
**decision** — read the release notes for changes to the durability and HITL surfaces this phase is
built on, and either amend and upgrade or record why not. Principle 14 is explicit that the plan is
amended before the code moves, so this finding is an instruction to go and read, not to run
`uv add`.

**`mcp==1.29.1` has no row in `docs/PACKAGES.md`.** This one is a genuine defect against Principle 7:
a pin exists in `pyproject.toml` that no ledger row explains. It has been found before, and part 5.8
is where that fact becomes the day's most uncomfortable finding.

## When it breaks

The failure mode of a freshness check is not that it reports the wrong thing. It is that it reports
**nothing** and everyone reads that as fine.

Consider what this check would look like if it were written the obvious way: compare the pinned
version against the latest, print a warning if they differ, and exit 0 either way. On a day with no
drift it prints nothing. On a day when the network is down it prints nothing. On a day when someone
has commented out the check it prints nothing. Three completely different situations, one output, and
the output is silence.

That is why every observation in this check prints whether or not it is a finding, and why the last
line of the output is a sentence rather than a number:

```text
'no drift, checked 2026-09-05' is a valid finding. Silence is not.
```

The second failure mode is the one this check has right now, and it should be named rather than
excused: **the observations are as old as the last time somebody re-took them.** They are data in a
file. If nobody runs the four commands at the bottom, the check keeps comparing today's pins against
last month's observations and reporting confidently. The date carried alongside each observation is
the mitigation — it makes staleness visible — but visible is not the same as prevented, and a gate
run six months from now would print dates six months old next to a claim about "latest".

The version that would prevent it is a check that refuses to pass when its own observations are older
than the pins they are compared with. That is not built here, and saying so is the honest position.

## In production

**What a professional writes instead.** Dependency drift is a bot that opens a pull request, and the
freshness question becomes "is there an open dependency PR older than the review window". The parts
that no bot handles are the ones that matter here: a protocol revision, a provider's rate-limit page,
a licence change in a vendored skill. Those get a scheduled human task with a written checklist, and
the output of the task is a dated note in a ledger — the same shape as the tag on the extinguisher.

**What degrades at scale.** Four questions is tractable and forty is not. Real systems have hundreds
of pins, and a freshness check that lists them all is one nobody reads. The move is to separate
**pins that are load-bearing for this phase's claims** from the rest: `google-adk` is load-bearing for
Phase 9 because the phase's whole subject is its resumption behaviour, and a JSON parser is not. The
gate checks the first list carefully and delegates the second to automation.

**The failure mode that only appears with real traffic.** A provider changes a free-tier limit
without changing a page you are watching — they announce it in a changelog, or apply it per-account,
or roll it out regionally. The first symptom is 429s in production against a budget that was correct
when it was written. Day 70's router is the structural answer: measure headroom from the responses
rather than from the documentation, because the documentation is an observation and the response is
the truth.

**The review comment a senior engineer leaves:** *"Your freshness check exits zero when it cannot read
the page. That means a scraper break and a clean bill of health look identical from CI. Make
'I could not check' a distinct outcome from 'I checked and it is fine' — they are different facts and
only one of them is reassuring."*

**The interview question:** *"How do you stop a system rotting when nobody is changing it?"* The
answer that shows experience is about scheduling the question: *"You cannot test for it, because
nothing in your repository changed — the world did. So it becomes a scheduled check at a fixed point,
in my case every phase gate, that asks a small fixed list: has the framework moved, has the protocol
revision moved, have the free tiers moved. The rule I care about is that it always reports, including
when nothing has changed, because 'checked on this date, no drift' is a result and an empty output is
indistinguishable from a check that never ran. And it records the URL and the date next to each
observation, so a stale answer is visible as stale rather than passing as current."*
