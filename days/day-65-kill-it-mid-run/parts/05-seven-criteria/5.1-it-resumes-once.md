# 5.1 — Criterion 1: it resumes, once

## One-line answer

The headline criterion of Phase 9 is one command over four kills, and it passes only when every kill
ends in exit `0` **and** exactly one close — two conditions, because either one alone is passable by a
broken system.

## The story

You collect a repeat prescription every month. The pharmacist takes the slip, goes to the back,
comes out with a box, and ticks the slip.

One month the card machine dies mid-payment and the whole thing has to be started again. You are in
the shop for twenty minutes instead of two. At the end of it you walk out with **one** box.

That is the only thing that mattered. Not that the process was smooth — it was not — but that the
interruption did not turn into two boxes of medication, and did not turn into none. The pharmacist
does not congratulate herself on a clean transaction. She checks the slip, sees one tick, and hands
over one box.

The month the machine works perfectly and she hands you two boxes is a far worse month, and it will
not feel like one at the time.

## The idea in plain language

The Phase 9 gate is the sentence *kill it mid-run; it resumes; a human approved the write*, and this
criterion is the first two thirds of it.

Sections 2 and 3 built the instrument and ran the four kills one at a time, reading the output.
Reading output is how you understand a failure. It is not how you gate a phase, because a person
reading output makes a judgement, and part 1.2's whole argument is that a criterion which needs a
judgement is a criterion two people will judge differently.

So the criterion is the drill run as a **command**, and the command's own exit code is the verdict:

> `drill.py` exits `0` when, for every one of the four kills, the final process exited `0` **and**
> exactly one close row exists for that intention.

Both halves are load-bearing, and part 3.5 is why:

- **exit `0` alone** passes a system that closed the ticket twice. Every process in the `unsafe` run
  exited cleanly.
- **one close alone** passes a system that closed the ticket correctly and then crashed on the way
  out, leaving a run that no operator can tell is finished.

A system can satisfy either without satisfying the other, so the criterion is the conjunction, and a
conjunction is what makes it awkward to pass by accident.

## Why Sutra needs it

Everything from Day 60 onwards has been building the machinery this criterion tests: the event log,
the checkpoint, the park, the approval, the idempotency key. None of that is worth anything as a set
of features. It is worth something as a single claim — *a run survives being killed and does its work
once* — and this is the command that decides whether the claim is true today.

It is also the criterion most likely to be quietly weakened later, because it is the slowest one and
the one that fails for the most confusing reasons. Part 6.2 is about what to do when a drill starts
feeling like an obstacle.

## The mechanism

The criterion, in the aggregate gate:

```python
CRITERIA = [
    ("1 it resumes, once", ["drill.py"], HERE),
    ("2 the gate cannot be bypassed", ["bypass.py"], HERE),
    ("3 the trail answers from rows", ["trail.py"], HERE),
    ("4 the budget is measured", ["budget.py"], HERE),
    ("5 the freshness check", ["fresh.py"], HERE),
    ("6 every day is written", ["written.py"], HERE),
    ("7 no open IDs in the phase", ["ids.py"], HERE),
]
```

**Line by line:**

- Each criterion is a **label and an argument list**, not a function. The gate runs them as child
  processes, so a criterion that hangs or crashes is contained rather than taking the gate with it —
  and so each one can be run on its own by a person, which is what makes a red gate diagnosable.
- The labels are numbered in the string itself. That is deliberate: the number appears in the gate's
  output, in this document and in the checklist, and keeping it in one place would mean three places
  that can drift.
- Criterion 1 is first because it is the phase's headline. The ordering is the reading order of this
  section, not an execution dependency — each criterion resets the state directory it needs.

And the verdict inside the drill:

```python
    ok = True
    for row in results:
        good = row["exit"] == 0 and row["closes"] == 1
        ok = ok and good
```

**Line by line:**

- `row["exit"] == 0 and row["closes"] == 1` is the conjunction stated above, in the smallest possible
  form. The two failures it separates are `unsafe` (exit 0, closes 2) and a crash after the close
  (exit non-zero, closes 1).
- `row["closes"]` was counted by re-reading `closed.jsonl` after every child process had exited —
  part 3.5's rule, applied. Nothing here trusts a number a runner reported about itself.
- `ok = ok and good` accumulates across all four kills rather than returning early, so a red gate
  reports **every** failing kill instead of only the first. A gate that stops at the first failure
  turns one afternoon of fixing into four.

Run it as the gate runs it:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python drill.py > /dev/null; echo "exit: $?"
```

**Line by line:**

- `> /dev/null` throws away the narrative and keeps only the verdict, which is exactly how the gate
  consumes it. If the criterion needs its output read to be understood, it is not a criterion yet.

Measured on 2026-09-06:

```text
exit: 0
```

And the summary table it printed on the way, which is what you read when it is **not** zero:

```text
kill   final exit  closes  verdict
K1     0           1       pass
K2     0           1       pass
K3     0           1       pass
K4     0           1       pass

mode=keyed  every kill ends in exactly one close: True
```

## When it breaks

The failure that matters here is not a kill failing. It is the criterion being **narrowed** until it
cannot fail, and that happens by a route that looks like maintenance.

The drill is the slowest thing in the gate — four kills, each starting several real child processes.
So somebody runs only K1 in the pre-commit hook, because K1 is the fastest and catches "most" of it.
Then K4 is the one that stops being run, and K4 is the only kill that tests the effect window, which
is the only place the two failures in part 3.5 live. The gate is now green on a system that can close
a ticket twice.

You can produce that state deliberately and watch the gate stay green:

```bash
uv run python drill.py --kill K1 > /dev/null; echo "K1 only, keyed:  $?"
uv run python drill.py --kill K1 --mode unsafe > /dev/null; echo "K1 only, unsafe: $?"
```

**Line by line:**

- `--kill K1` runs a single kill, which is a legitimate flag for reading one experiment and an
  illegitimate one for gating a phase.
- The second line puts the system into the broken mode from part 3.5 — the one that closes tickets
  twice — and asks K1 alone about it.

Measured on 2026-09-06:

```text
K1 only, keyed:  0
K1 only, unsafe: 0
```

**Both green.** The `unsafe` mode is a real, customer-visible defect, and K1 cannot see it, because
K1's kill lands during research and never reaches the effect window at all. A gate built from K1 is a
gate that passes the bug this phase exists to prevent.

That is the general lesson and it is worth stating in the abstract: **a criterion is only as strong as
the worst case it actually exercises**, and dropping cases for speed silently redefines what the gate
promises. If the four kills are too slow to run on every commit, the answer is to run them on every
merge, not to run one of them on every commit and call it the same check.

## In production

**What a professional writes instead.** This is a chaos test, and in a real system it runs against a
deployed environment on a schedule rather than against local subprocesses in a pre-commit hook. The
kills become pod deletions or process signals delivered by a supervisor, the ledger becomes the real
database, and the count becomes a query. What does not change is the shape: kill at a known point,
resume, count effects, compare to intent.

**What degrades at scale.** Four kills against four points is complete here because this graph has
four interesting moments. A real graph has dozens of stages and every boundary between them is a
candidate, so exhaustive killing stops being possible and you move to sampling — kill at a random
point, many times, and let coverage accumulate. That trade is fine, but it changes the criterion from
*proved* to *not yet disproved*, and the honest version of the gate says which one it is.

**The failure mode that only appears with real traffic.** The drill kills one run at a time. Real
kills take down a process that was running many, and the interesting failures are the ones where two
half-finished runs interact — the shared lease this instrument does not have, named in part 3.3 and
again in 3.4. Passing this criterion says the single-run path is sound and says nothing about
concurrency, and a gate that is read as saying more than it does is worse than no gate.

**The review comment a senior engineer leaves:** *"Your recovery test asserts the process exited
cleanly. Add the count. I have seen this exact test pass for a year on a service that was
double-charging, because a clean exit is what a duplicate looks like from inside."*

**The interview question:** *"How do you test that something recovers from a crash?"* The answer that
shows experience names the moment and the count: *"You have to kill it at the moments that matter,
not at a random one, and the moments are the boundaries — before the checkpoint, after the checkpoint,
while waiting for a human, and inside the window between doing a thing and recording it. Then you
count effects from outside the process after everything has exited, and require exactly one, not at
least one. Exit codes alone will pass a system that did the work twice, because the duplicate was made
by a process that is no longer around to be asked."*
