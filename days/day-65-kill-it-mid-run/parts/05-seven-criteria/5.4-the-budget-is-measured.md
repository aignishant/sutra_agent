# 5.4 — Criterion 4: the budget is measured

## One-line answer

Durability is not free — a kill before a checkpoint costs a repeated request — and the criterion is
that the price is a number somebody counted from the log rather than an assumption, because a cost
nobody measures is a cost that grows.

## The story

The flat has a prepayment meter for the electricity. You put money on a key at the corner shop, and
the meter counts down.

For the first month you have no idea what anything costs. Then one week it runs out on a Wednesday
and you look properly at the little screen, and you find the immersion heater. It is not on all the
time. It is on for an hour a day and it is a third of the bill.

Nothing was broken. Nobody had done anything foolish. It was simply that until the number was in
front of you, the immersion heater cost nothing at all, because cost that is not measured does not
feel like cost — and the meter did not tell you the answer either. It told you the total, and you had
to go and find out which thing the total was made of.

## The idea in plain language

Principle 15 says quota is the currency, and Day 24 built the accounting for it. This phase spends
some of that currency on **durability**, and the spending is invisible unless it is counted.

Here is where it goes. When a process is killed after paying for a stage and before recording what
the stage produced, the resumed process has no result for that stage and must run it again. The
provider was paid twice for one stage. That is not a bug — it is the price of a crash landing in the
window that part 3.1 measured — but it is a price, and it is charged per crash.

So the criterion has two halves, and only the second is unusual:

- what a clean run costs, which anyone would measure;
- what a **killed and resumed** run costs, which almost nobody does.

The gap between them is the durability premium. In this drill it is exactly one request per
mid-stage kill, which sounds negligible and is the number you need before you can argue about
checkpoint frequency at all.

One term, carried forward and defined again because it is the whole mechanism. A **checkpoint** is
the moment a run writes down enough to be picked up from — here, one line per completed stage. Take
more checkpoints and you lose less work per crash while writing more; take fewer and each crash costs
more. That trade cannot be discussed without a measured premium, which is why this is a criterion and
not a note.

## Why Sutra needs it

The desk runs on free tiers. Day 59's gate came out amber on exactly this: the measured cost per
ticket, multiplied by a nightly batch, exceeded the free daily allowance. That finding was only
possible because the cost was a counted number.

The same argument is about to get sharper. Day 70 builds the Quota-Router, which routes work to
whichever provider has headroom — and a router cannot route against a budget nobody has measured. The
number this criterion produces is an input to that day.

## The mechanism

The criterion re-reads the spend from the run log, never from what a process printed:

```python
def spend(run_id: str) -> int:
    """Every request this run has paid for, including the ones a crash threw away."""
    return sum(e["cost"] for e in read_events(run_id) if e["kind"] == "spent")
```

**Line by line:**

- It sums over `read_events`, which reads the log file from disk. That is the entire trick: a process
  that died mid-stage never printed its spend, but it did write the `spent` line before dying, so the
  log knows about a request that no output does.
- `e["kind"] == "spent"` filters to the cost rows. The log interleaves `spent` and `stage` lines
  precisely so that the two can disagree — part 3.1's crash shows `spent research` twice with one
  `stage research`, and that duplication is the durability premium made visible.
- It returns an integer of **requests**, not tokens or currency. Addendum 02 denominates budgets in
  requests per minute and per day, because that is what a free tier actually rations.

And the ordering in the runner that makes the count honest:

```python
        produced = _desk.STAGE_FN[stage](ticket, state, meter)
        meter.charge(stage)
        # The spend is written into the log with the stage, so a request that was paid
        # for and then lost to a crash is still visible in the accounting afterwards.
        _store.append_event(run_id, "spent", stage=stage, cost=_desk.STAGE_COST[stage])
```

**Line by line:**

- The stage function runs first, then the charge is recorded. That order matters: the request has
  already been made by the time we write that it was made, so a crash between them under-counts by at
  most one and never over-counts. Recording the charge first would let a crash bill you for a request
  that never happened.
- The `spent` line is written **before** the `stage` line that carries the result. That is what
  creates the observable gap and is the reason a killed run's cost is recoverable at all.
- The comment is in the shipped code because the ordering looks arbitrary and is not. A future reader
  tidying these two lines into one would destroy the measurement.

Run it:

```bash
cd days/day-65-kill-it-mid-run/lab
uv run python budget.py; echo "exit: $?"
```

**Line by line:**

- Four scenarios, each a real sequence of child processes: clean, killed mid-stage, killed while
  parked, and rejected. The rejected one is included because "we did the work and then a human said
  no" is a real cost that budget estimates always omit.

Measured on 2026-09-06:

```text
what one stage would cost, from _desk.STAGE_COST:
  intake    0
  classify  1
  research  1
  draft     1
  review    1
  total     4

measured, by running it:
  clean run, approved, closed          4 requests
  killed mid-research, then resumed    5 requests
  killed while parked, then resumed    4 requests
  rejected, nothing written            4 requests

  a resume after a mid-stage kill costs 1 extra request(s)
  a resume after a parked kill costs     0 extra request(s)
  a rejection still costs                4 request(s)

  provider requests made by this file:      0
  every number above is a counter, not a call
exit: 0
```

Four findings in that block, and three of them are only visible because the run was killed:

**The premium is 1, not 4.** A mid-stage kill re-runs one stage, not the whole run, because the
earlier stages were checkpointed. This is the number that justifies checkpointing per stage rather
than per run.

**A parked kill costs nothing.** Part 3.3's claim, priced. A run killed while waiting for a human
resumes for free, which is why parking is the cheapest possible place for a process to die and why
"waiting is a state" is an economic argument as well as a correctness one.

**A rejection costs full price.** All four requests are spent before anyone sees the draft, because
the draft has to exist to be judged. Day 63's argument about which actions deserve a gate has this
number underneath it: every gated action is paid for whether or not it is approved.

**Zero provider requests.** The last two lines are the day's own budget statement. Every number above
came from a counter in a deterministic stand-in, so the whole of Phase 9's gate can be re-run as often
as you like without touching a free tier.

## When it breaks

The break is counting from output instead of from the log, which is the natural way to write this
script and produces a number that is confidently wrong in the flattering direction:

```bash
uv run python budget.py --naive
```

**Line by line:**

- `--naive` sums the `spent N requests` lines the runners printed. Same runs, same kills; only the
  source of the number changes.

Measured on 2026-09-06:

```text
counting the first way: adding up what the runner printed

  clean run, approved, closed          4 requests
  killed in research, then resumed     3 requests

  the killed run looks 1 request(s) cheaper than the clean one
  it is not. the process that paid for research died before it could print.
```

The crashed run appears **cheaper** than the clean one. A capacity plan built on that number would
conclude that crashing saves money, and the direction of the error is the dangerous part: an
over-count gets investigated, and an under-count gets believed.

The general rule this is an instance of was stated in part 1.2 and is worth repeating in its harshest
form: **a number reported by the thing being measured is not a measurement**, because the failure you
are measuring is exactly the failure that stops it reporting.

## In production

**What a professional writes instead.** The spend is written to the durable log at the moment the
request is issued, with the provider, the model and the response status, and the budget is summed by
something outside the run. Real systems also record the request id the provider returned, so their
bill can be reconciled against your count — because the only way to find out that your counter has
drifted is to compare it with the invoice.

**What degrades at scale.** A per-stage constant is a fiction. Real cost varies with the prompt, the
retrieved context and the retries inside the client, so a fixed `STAGE_COST` table is a teaching
device and a real one has to sum actual calls. The shape survives — count in the log, sum from
outside — but any *estimate* baked into the code will diverge from reality and be trusted anyway.

**The failure mode that only appears with real traffic.** Crash loops. One kill costs one extra
request; a poison run that crashes on every resume costs one extra request **per attempt, for ever**,
and the budget line grows linearly while every dashboard shows a healthy retry rate. Day 59's
containment guards are what stop it, and this criterion is what makes the cost of not stopping it
visible.

**The review comment a senior engineer leaves:** *"You are counting model calls in a variable that
lives in the process making them. Move it into the same durable write as the work it paid for, or
your cost accounting will be systematically low by exactly the requests that were lost to crashes —
which is the population you most need to know about."*

**The interview question:** *"What does durability cost you?"* The answer that shows experience has a
number in it: *"Re-executed work, charged at the boundary you chose. On my triage graph a crash
between a stage's request and the log line recording its result costs exactly one extra provider
request, because the earlier stages are checkpointed and only that one repeats — I measured five
requests for a killed-and-resumed run against four for a clean one. A crash while parked costs
nothing, which is a good argument for parking. And I count it from the durable log rather than from
what the process printed, because the process that paid and died is the one that never got to print
its number, so counting from output makes crashes look cheap."*
