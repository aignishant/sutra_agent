# 1.2 — An error is a fact, not a sentence

## One-line answer

`"Error: kb timed out"` and `{"kind": "timeout", "retryable": True}` carry the same information, and
only the second one can be asked a question — which is the difference between a failure your code can
act on and one it can only print.

## The story

The garage rings about your car.

*"There's a noise coming from the front."* That is true, and you cannot do anything with it. Is it
safe to drive? Is it the sort of noise that gets worse? Is it going to cost forty pounds or four
hundred? You ring back and ask all three, which is the tell: the first sentence was not information,
it was a *pointer* to information that stayed in the mechanic's head.

Compare the job card he fills in: *front nearside, wheel bearing, worn, safe for short journeys, part
ordered.* Same event. Five things you can act on without ringing anybody.

The difference is not detail. It is that the second one has **fields**.

## The idea in plain language

Once an error is going to travel — and [1.1](1.1-three-parties.md) established that it must — the
next question is what it travels *as*. There are two options and they are not close.

**As prose.** `f"Error: {exc}"`. This is what the swallowed shape produces, and it is what most
tool-level error handling produces even when it does the right thing otherwise. It is human-readable
and machine-opaque.

**As a fact.** A dictionary with named fields: what kind of failure, what it was talking to, whether
it is worth retrying, whether the user should be told. Slightly less pleasant to read; enormously more
useful.

The test that separates them is not "which is more detailed". Both can contain the same words. The
test is: **can code ask it a question and get a reliable answer?**

- *Is it retryable?* Against prose, you are doing `"timed out" in message`, which is a substring
  match against a string somebody else controls and can change in a patch release. Against a fact,
  it is a key lookup.
- *Should the user see this?* Prose cannot answer at all. That is a policy decision, and nobody wrote
  it down.
- *Which dependency failed?* Against prose, you are parsing a hostname out of English.

This is the same rule as
[20.1.4](../../../day-20-context-engineering-compaction/parts/01-notes-not-transcript/1.4-what-must-never-be-summarized.md),
arriving from a different direction. There, the rule was that anything which must survive belongs in
**state** rather than in prose, because prose is what compaction rewrites. Here, anything which must
be **acted on** belongs in fields rather than prose, because prose is what code cannot branch on.
Both are the same underlying claim: *structure is what survives contact with a program.*

There is a second reason, specific to agents, and it is the reason `SEC-02` is a security ID. A fact
has a field for **who is allowed to see it**. `kb.internal:8080` is an internal hostname; a stack
trace can contain a query with a customer's email in it. When the error is a sentence, the choice is
between showing the user everything and showing them nothing. When it is a fact, `detail` goes to the
log and `status` goes to the model, and that separation is a field rather than a hope.

## Why Sutra needs it

Because Sutra's error policy has to be written **once**, and a policy can only be written against
fields.

The whole design of section 2 is a single plugin that decides what happens to every failure in the
system. That plugin cannot contain `if "timed out" in str(error)` for eleven different tools with
eleven different phrasings. It needs to ask two questions — *is this retryable* and *can the user see
it* — and get an answer.

Day 22 is structured logging, and it is the same shape again: a log line is a fact with fields or it
is a sentence somebody greps. Day 24's budget accounting needs to know which failures cost a request
and which did not. Day 79's evals need to score whether Sutra failed *honestly*, which means checking
a field rather than reading a paragraph.

## The mechanism

The same failure in both shapes, asked the three questions a policy actually asks.

```python
# days/day-21-errors-surface-not-swallow/lab/fact_not_sentence.py
"""The same failure as prose and as a fact, put to the test that matters: can you branch on it?"""

AS_SENTENCE = "Error: kb.internal:8080 timed out after 5s"
AS_FACT = {
    "status": "unavailable",
    "kind": "timeout",
    "target": "kb.internal:8080",
    "retryable": True,
    "user_visible": False,
    "detail": "kb.internal:8080 timed out after 5s",
}

QUESTIONS = ("is it retryable?", "should the user see it?", "which dependency failed?")


def ask_sentence(question: str) -> str:
    """Everything you can do with prose is guess at its shape."""
    if question == "is it retryable?":
        return "substring match on 'timed out' - breaks when the wording changes"
    if question == "should the user see it?":
        return "no way to tell; the string carries no policy"
    return "parse a hostname out of English"


def ask_fact(question: str) -> str:
    """A dict answers by lookup, and a missing key is a loud KeyError rather than a wrong guess."""
    if question == "is it retryable?":
        return f"AS_FACT['retryable'] -> {AS_FACT['retryable']}"
    if question == "should the user see it?":
        return f"AS_FACT['user_visible'] -> {AS_FACT['user_visible']}"
    return f"AS_FACT['target'] -> {AS_FACT['target']}"


print(f"as a sentence: {AS_SENTENCE!r}   ({len(AS_SENTENCE)} chars)")
print(f"as a fact:     {len(AS_FACT)} keys, {sum(len(str(v)) for v in AS_FACT.values())} chars\n")

for question in QUESTIONS:
    print(f"  {question}")
    print(f"      prose : {ask_sentence(question)}")
    print(f"      fact  : {ask_fact(question)}")

print("\nboth carry the same information. only one of them can be asked a question.")
```

**Line by line:**

- `AS_FACT` keeps `detail` — the original message, unchanged. Structuring an error does **not** mean
  discarding its text; it means putting the text in a field alongside the decisions, so the operator
  still gets the string they are going to search for.
- `retryable` and `user_visible` are **booleans decided at the point of failure**, where the most
  context exists. That is the crux: the tool knows it was a timeout on an internal host, and the
  policy layer does not. Recording it as a field is how that knowledge travels.
- `status` is the coarse, model-facing value. It is deliberately a small vocabulary —
  `"unavailable"`, `"not_found"`, `"denied"` — because it is the one field the model reads, and a
  model reasons better about three known words than about free text.
- `ask_sentence` returns a *description of the workaround* rather than performing it, because the
  workarounds are the point. Each is a real technique somebody has shipped, and each is a bug waiting
  for a wording change.
- `"substring match on 'timed out'"` is the one to notice. It works, it is one line, and it breaks
  silently the day the library changes `timed out` to `timeout exceeded`. Nothing fails loudly; the
  error simply stops being classified as retryable.
- `sum(len(str(v)) for v in AS_FACT.values())` measures the fact's total text so the size comparison
  is honest rather than rhetorical.


**The size difference is small and it is the whole argument.** 42 characters against 78. The fact is
not a heavyweight object or a schema or a class hierarchy — it is under twice the size of the
sentence, and it is a plain dictionary. Whenever this design is resisted, the objection is that it is
heavier. It is 36 characters heavier.

**The middle question is the one with no prose answer at all.** *Should the user see this?* is not
information the sentence lost; it is information the sentence never had. Nobody decided. So at the
moment a user-facing message is being written, somebody has to guess, and the two available guesses
are "show them the internal hostname" or "show them nothing".

**And the first question is the one that looks solved and is not.** `"timed out" in message` returns
`True` today. It is the most common line of error-classification code in existence, and it is a
dependency on somebody else's copywriting.

## When it breaks

Prose fails quietly. The fact shape fails loudly, and that is the trade:

```text
Traceback (most recent call last):
  File "policy.py", line 22, in decide
    if error["retryable"]:
       ~~~~~^^^^^^^^^^^^^
KeyError: 'retryable'
```

A tool returned a dictionary that did not carry the field the policy needs, and the policy stopped
rather than guessing. That is the correct behaviour and it is the same argument
[17.4.2](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.2-the-brace-that-raises.md)
made about a missing state key: a `KeyError` at the boundary is worth far more than a default that
silently means *"do not retry"*.

The quiet failure is the substring one, and it has no error text at all — which is why it cannot be
shown here. The library updates, the wording changes from `timed out` to `deadline exceeded`,
`is_retryable` starts returning `False`, retries stop happening, and the only symptom is a slow rise
in failed requests that nobody attributes to a dependency bump.

## In production

**Give the fact a type, not just a shape.** A `dict` is the right teaching object and the right first
implementation. In a real codebase it becomes a `dataclass` or a pydantic model with those fields, so
that a tool returning the wrong shape fails at the boundary rather than three layers later. Sutra's
repo convention already prefers `dataclasses` over ad-hoc dicts, and this is exactly the case it was
written for.

**What changes at scale** is that the vocabulary of `status` becomes an interface. Once five agents,
a logger and an eval suite all branch on `status`, adding a sixth value is a change with consumers.
Keep it small and closed; put the variety in `kind` and `detail`, which nothing branches on.

**The failure that only appears with real traffic** is the field that is always the same. `retryable`
gets hardcoded to `True` in one tool during a hurried fix, and from then on that tool's permanent
failures are retried four times each, forever. A field nobody varies is a field that has quietly
become a constant, and the way you find it is by counting the distribution of your own error facts
rather than assuming it.

**The review comment a senior engineer leaves:** *"this returns `f'Error: {e}'`. What is the caller
supposed to do with that? Give it a `kind` and a `retryable` so the policy plugin can decide, and put
the message in `detail`."*

**The interview question:** *"how do you represent an error crossing a boundary in an agent system?"*
The answer that shows you have maintained one: *"as structured data, not a string. The fields are the
decisions — is it retryable, can the user see it, what failed — because those are known where the
error happened and unknowable afterwards. The message goes in a `detail` field so operators still get
the string they will search for."*
