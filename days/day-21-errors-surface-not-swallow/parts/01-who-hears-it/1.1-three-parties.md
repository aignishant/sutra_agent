# 1.1 — Three parties, and the one that must never be nobody

## One-line answer

When something fails inside an agent, three parties could be told — the **model**, the **runtime**
and an **operator** — and the only shape that tells all three is the one that catches the error
somewhere other than where it happened.

## The story

The washing machine stops mid-cycle with water still in the drum.

The engineer comes out, opens the panel, and finds that the drain pump has failed. What he also
finds is a note left by whoever installed it: a small piece of tape over the diagnostic light,
because the light was blinking and the blinking was annoying.

The machine had been telling somebody, for weeks, that the pump was struggling. The tape did not
break the pump. The tape meant that when the pump did break, it broke as a surprise, on a Sunday,
with a full drum.

Nobody covered that light out of malice. They covered it because a blinking light with nowhere to
report to is just an irritation.

## The idea in plain language

Every day so far, Sutra has been asked to be honest about **data** — what is in state, what is in
the window, what is in the record. Today is about being honest about **failure**, and the first move
is to notice that "handled the error" is not one thing. It is a question about *who finds out*.

When the knowledge base times out inside a tool, there are exactly three parties who could be told.

**The model.** It is mid-task, and it is going to write a sentence to the user either way. If it is
not told, it will write that sentence anyway, from whatever it has.

**The runtime.** ADK's `Runner` is what could retry the call, substitute a result, record the failure
in a trace, or stop the invocation. It can do none of those things about an error it never sees.

**An operator.** A human, later, asking *"why did Sutra tell the customer that?"*. They read logs,
traces and alerts, and every one of those is downstream of the runtime being told.

Now the three shapes an error can take in code, and this is the whole of the day in one table:

| Shape | What the code does | Who is told |
| --- | --- | --- |
| **swallowed** | `except Exception as e: return f"Error: {e}"` | the model, and nobody else |
| **raised** | let the exception out | the runtime and an operator, but not the model |
| **substituted** | let it out, catch it one layer up, hand the model a *marked* result | all three |

The middle row is the honest default and it is what ADK 2.x expects. The bottom row is the one you
actually want in production, and the rest of this day is how ADK lets you build it without a
`try`/`except` in every tool.

The top row is the one to be frightened of, and the reason is in the second column: **it is the only
shape where nothing raises and nothing is logged.** A swallowed error is not a handled error. It is a
failure converted into a normal-looking value, and normal-looking values do not set off anything.

## Why Sutra needs it

Because Sutra's whole job is to say something true about a ticket, and every one of its facts comes
through a tool that can fail.

The knowledge-base lookup from [Day 10](../../../day-10-function-tools/LESSON.md) can time out. The
search grounding from [Day 16](../../../day-16-built-in-tools-with-brakes/LESSON.md) can be refused.
The model itself can hand back a 429, which
[Day 20](../../../day-20-context-engineering-compaction/LESSON.md) measured arriving on the twentieth
request of the day. Sutra without an error policy is Sutra with a piece of tape over the light.

It is also the day the safety curriculum starts properly. `SEC-02` is *honest error surfacing*, and it
comes before every other security ID for a reason: you cannot reason about a system's blast radius
([Principle 13](../../../../docs/00_MASTER_PLAN.md)) if the system is capable of failing without
saying so.

## The mechanism

The three shapes, written out, with a column per party.

```python
# days/day-21-errors-surface-not-swallow/lab/three_shapes.py
"""The same outage, written three ways, and who is able to find out in each."""

CALLERS = ("the model", "the runtime", "an operator")


def swallowed() -> dict[str, object]:
    """The 1.x habit: catch it here, hand back a sentence."""
    try:
        raise TimeoutError("kb.internal:8080 timed out after 5s")
    except TimeoutError as exc:
        return {"reaches": {"the model": f"Error: {exc}"}, "raises": False}


def raised() -> dict[str, object]:
    """Let it out. The runtime decides what happens next, and the run fails loudly."""
    return {
        "reaches": {"the runtime": "TimeoutError", "an operator": "TimeoutError"},
        "raises": True,
    }


def substituted() -> dict[str, object]:
    """Caught by policy, one layer up, and marked as a substitute."""
    return {
        "reaches": {
            "the model": {"status": "unavailable", "reason": "TimeoutError"},
            "the runtime": "TimeoutError",
            "an operator": "TimeoutError",
        },
        "raises": False,
    }


print(f"{'shape':<14} {'raises?':<8} " + " ".join(f"{c:<12}" for c in CALLERS))
for name, fn in (("swallowed", swallowed), ("raised", raised), ("substituted", substituted)):
    outcome = fn()
    reaches = outcome["reaches"]
    cells = " ".join(f"{'yes' if c in reaches else 'no':<12}" for c in CALLERS)
    print(f"{name:<14} {str(outcome['raises']):<8} {cells}")

print("\nswallowing is the only shape that tells the model something and nobody else.")
```

**Line by line:**

- Each function **returns a description** of what happened rather than actually doing it. This file is
  a comparison, not a demonstration; the demonstrations are in section 2, against a real runner.
- `swallowed()` contains the `try`/`except` in full, deliberately. It is four lines, it looks
  responsible, and it is the single most common shape in every 1.x tutorial on the internet. Being
  able to recognise it on sight is most of this part.
- `f"Error: {exc}"` — a **string**. That is the detail [1.2](1.2-an-error-is-a-fact.md) is about: the
  moment a failure becomes prose, nothing downstream can branch on it.
- `raised()` reports `"an operator"` as reached, and that is not a technicality. An exception that
  escapes the run fires ADK's run-level error hook and crashes the invocation, both of which land
  somewhere a human can see. [2.3](../02-four-hooks/2.3-the-two-that-can-only-witness.md) is where
  that hook is measured.
- `raised()` does **not** reach the model, and that is its real cost: the user gets nothing at all
  rather than a graceful sentence. Raising is honest but blunt.
- `substituted()` is the only row with all three, and the shape of its payload is the reason — a
  `dict` with a `status` field, not a sentence. That is the design
  [3.2](../03-policy/3.2-a-substitute-must-say-so.md) argues for.
- `c in reaches` is a membership test on the dictionary's keys, which is what makes the table a
  mechanical read of the data above rather than three hand-written rows.

**Line by line:**

- Pure Python. No ADK, no key, no network, no quota.

Measured on 2026-09-03:

```text
shape          raises?  the model    the runtime  an operator 
swallowed      False    yes          no           no          
raised         True     no           yes          yes         
substituted    False    yes          yes          yes         

swallowing is the only shape that tells the model something and nobody else.
```

Read down the `raises?` column first. **Two of the three shapes do not raise**, and they are the two
that reach the model — which is the trap in one observation. "It didn't crash" tells you nothing
about whether anything went wrong, because the shape that hides the most is also the shape that
crashes the least.

Then read across the `swallowed` row. One `yes`, two `no`. The failure reached exactly one party, and
it is the party least able to do anything about it: a language model, mid-sentence, holding a string
that begins with the word `Error`. It cannot retry. It cannot alert anyone. It can only decide what
to say next, and [4.1](../04-failure-lab/4.1-the-swallowed-exception.md) shows what it decides.

And notice that `substituted` does not raise either, yet reaches everyone. That is the point of the
whole day: **honesty is not the same as crashing.** You can degrade gracefully and stay honest, but
only if the error travels somewhere before it is turned into a graceful answer.

## When it breaks

The thing that breaks is a conversation, weeks later, and it goes like this.

🎬 **The scene:** a customer says Sutra told them their ticket had no notes attached, and it had four.
😬 **The naive fix:** you check the model, decide it hallucinated, and add a firmer instruction.
💥 **Why it fails:** the model did not hallucinate. The notes tool timed out, caught its own
`TimeoutError`, and returned `{"error": "Error: db timed out"}`. The model read a dictionary that
said the lookup had happened and produced the most reasonable summary of an empty result. There is no
traceback to find because nothing ever raised, and no log line to find because nothing was ever told.
💡 **The insight:** a system that can fail without saying so cannot be debugged, only guessed at. The
first requirement of error handling is not recovery. It is **arrival**.

## In production

**Grep for the shape, not for the bug.** `except Exception` followed by a `return` is mechanically
findable, and it is worth finding across a whole codebase in one afternoon. Every hit is a place
where a failure has been converted into a value. Some of them will be deliberate and correct; the
point is that somebody decided, rather than that a tutorial did.

**What changes at scale** is that the model gets better at hiding it. A weak model handed
`{"error": "..."}` often blurts the error text at the user, which is ugly and *safe* — somebody
notices. A strong model writes a smooth, plausible sentence that never mentions a failure at all.
Improving your model makes this class of bug quieter, which is the opposite of what you would expect
and the reason it survives so long in mature systems.

**The failure that only appears with real traffic** is the partial outage. In testing, either the
knowledge base is up or you have stubbed it out. In production it is up for 98% of calls, so 2% of
your answers are confidently wrong and 98% are fine, and no aggregate metric moves enough to notice.

**The review comment a senior engineer leaves:** *"this tool catches its own timeout and returns a
string. Let it raise — we have a plugin for this, and right now the retry policy and the trace can't
see this call at all."*

**The interview question:** *"a tool your agent calls fails. What should happen?"* The answer that
shows you have debugged one: *"it depends who needs to know, and the answer is usually all three —
the model needs something it can say, the runtime needs to be able to retry or record it, and a human
needs to be able to find it later. The one thing that must not happen is the tool catching it and
returning a string, because then only the model knows and it is the party that can do the least."*
