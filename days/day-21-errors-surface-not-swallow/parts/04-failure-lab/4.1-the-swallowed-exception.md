# 4.1 — 💥 The swallowed exception

## One-line answer

Four lines of `try`/`except` inside a tool took the error hooks that fired from **three to zero**, the
run from failed to successful, and the user's answer from nothing to *"Here is what I found about
KB-104."* — while the knowledge base was down.

## The story

The smoke detector in the hall has been beeping about its battery for a fortnight.

Somebody takes the battery out. Not out of the smoke detector — out of the *beeping*. They take the
old battery out, the beeping stops, and they mean to buy a new one at the weekend.

The house now has a smoke detector on the ceiling. It is screwed on, it is the right model, it was
professionally installed and it is in the correct position. Everyone who walks past it sees a smoke
detector. There is no way to tell, from the hall, that it is a plastic shell.

Nobody in that house made a decision to live without a smoke alarm.

## The idea in plain language

This is trap #4 from the master plan's §5.1, run as an experiment rather than described as a warning.

The 1.x habit is this, and it appears in more or less every tutorial written before 2026:

```python
def lookup_article(article_id: str) -> dict:
    try:
        return kb.fetch(article_id)
    except Exception as exc:
        return {"error": f"Error: {exc}"}
```

**Line by line:**

- `except Exception` catches **everything** — the timeout it was written for, and also a `KeyError`
  from a typo two lines up. The breadth is not laziness; it is what makes the function feel safe.
- `return {...}` is the whole bug in one keyword. A `return` is how a function reports success, and
  from here on nothing distinguishes this call from one that worked.
- `{"error": ...}` looks like disclosure and is not. The key is only meaningful to code that knows to
  look for it, and no ADK hook does — the runtime reads a tool's result as a result.
- `-> dict` still holds, which is why no type checker and no test notices. The signature is honest;
  the value is not.

Read it charitably, because it deserves charity. It does not crash. It returns a value of the
documented type. It preserves the error message. It even puts it under a key called `error`, so
anybody reading the dictionary can see what happened. Four lines, defensive, no loose ends.

What [2.4](../02-four-hooks/2.4-the-ladder.md) established is why it is catastrophic: the exception is
the *only* thing that starts the climb. No exception, no ladder. Not a reduced ladder, not a
best-effort ladder — the tool-level hook is never called, so nothing above it is either, and there is
no point in the system at which anything knows a failure occurred.

The measurement below counts the hooks in both versions, and the number to watch is zero.

## Why Sutra needs it

Because Sutra has a plugin full of error policy as of today, and this one habit makes all of it dead
code.

The classifier from [3.1](../03-policy/3.1-which-429-is-it.md) never runs. The marked substitute from
[3.2](../03-policy/3.2-a-substitute-must-say-so.md) is never built, and the tool's own unmarked one is
used instead. The redaction from [3.3](../03-policy/3.3-giving-up-honestly.md) never applies, because
nothing is being reported. Day 22's logging sees a successful call. Day 84's traces show a green span.

And the reason it will happen to Sutra specifically is that Sutra's tools are hand-written, one per
day, over months, by somebody learning. The eleventh tool is the one that gets a `try`/`except`,
because on the day it was written something was failing and the fastest way to move on was to catch
it.

## The mechanism

One tool, one environment variable, two shapes — with a plugin recording every hook it is offered.

```python
# days/day-21-errors-surface-not-swallow/lab/who_hears_it.py
"""One failing tool, two ways of writing it. Watch which hooks hear about each."""

HEARD: list[str] = []
SWALLOW = os.environ.get("SWALLOW", "0") == "1"


def lookup_article(article_id: str) -> dict[str, Any]:
    """Fetch a knowledge-base article. The knowledge base is down."""
    if SWALLOW:
        # The 1.x habit: catch it here and hand the model a sentence.
        try:
            raise TimeoutError("kb.internal:8080 timed out after 5s")
        except TimeoutError as exc:
            return {"error": f"Error: {exc}"}
    raise TimeoutError("kb.internal:8080 timed out after 5s")


class Witness(BasePlugin):
    """Records every error hook the runtime fires. Suppresses nothing."""

    async def on_tool_error_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, error: Exception
    ) -> dict[str, Any] | None:
        HEARD.append(f"on_tool_error_callback   {type(error).__name__}: {error}")
        return None

    async def on_model_error_callback(
        self, *, callback_context: Any, llm_request: LlmRequest, error: Exception
    ) -> LlmResponse | None:
        HEARD.append(f"on_model_error_callback  {type(error).__name__}: {error}")
        return None

    async def on_agent_error_callback(
        self, *, agent: Any, callback_context: Any, error: Exception
    ) -> None:
        HEARD.append(f"on_agent_error_callback  {type(error).__name__}: {error}")

    async def on_run_error_callback(self, *, invocation_context: Any, error: Exception) -> None:
        HEARD.append(f"on_run_error_callback    {type(error).__name__}: {error}")

    async def after_tool_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, result: dict[str, Any]
    ) -> dict[str, Any] | None:
        HEARD.append(f"after_tool_callback      result={result}")
        return None
```

**Line by line:**

- The `SWALLOW` branch is written with the `try`/`except` **in full**, including raising the exception
  in order to catch it immediately. That looks contrived and is exactly what the real code does: the
  `kb.fetch` call raises, and the `except` two lines below catches it. Collapsing it to
  `return {"error": ...}` would have hidden the shape this part is about.
- Both branches raise the **same exception with the same message**, so nothing about the failure
  differs between the two runs. The only variable is who catches it.
- `Witness` overrides **all four** error hooks plus `after_tool_callback`, and every one of them
  returns `None`. It is a pure observer: it changes nothing, so the hook count is a measurement of the
  runtime's behaviour rather than of the plugin's.
- `on_model_error_callback` is included even though the model never fails here, and its absence from
  both outputs is itself informative — it proves the recorder is only reporting hooks that actually
  fired.
- `after_tool_callback` is the control. It fires on any *completed* tool call, so it is the one hook
  the swallowed version still triggers, and its output is where the swallowed error turns up.
- `HEARD` is a module-level list rather than plugin state, so the count survives to the end of the run
  and can be printed as a single number.

```bash
cd days/day-21-errors-surface-not-swallow/lab
SWALLOW=1 uv run python who_hears_it.py
SWALLOW=0 uv run python who_hears_it.py
```

**Line by line:**

- `SWALLOW=1` first, because it is the version that looks fine.
- Recording models throughout: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
SWALLOW=1
  hooks that heard about it: 1
    after_tool_callback      result={'error': 'Error: kb.internal:8080 timed out after 5s'}
  the run raised: None
  the user was told: 'Here is what I found about KB-104.'

SWALLOW=0
  hooks that heard about it: 3
    on_tool_error_callback   TimeoutError: kb.internal:8080 timed out after 5s
    on_agent_error_callback  TimeoutError: kb.internal:8080 timed out after 5s
    on_run_error_callback    TimeoutError: kb.internal:8080 timed out after 5s
  the run raised: TimeoutError: kb.internal:8080 timed out after 5s
  the user was told: None
```

**Zero error hooks fired in the swallowed run.** Not one. `on_tool_error_callback` — the hook whose
entire purpose is to be told that a tool failed — was not called, because from the runtime's
perspective the tool did not fail. It was called and it returned a dictionary.

**The one hook that fired is the success hook.** `after_tool_callback`, with
`result={'error': 'Error: kb.internal:8080 timed out after 5s'}`. The error text is right there, in
the payload, going past a hook that has no reason to inspect it — because it is the hook for
*results*. If your logging hangs off `after_tool_callback`, as plenty does, you will have this string
in your logs and no error in your metrics, which is the worst of both.

**And the last line is the one to sit with.** *"Here is what I found about KB-104."* The knowledge base
was unreachable. The model was handed a dictionary whose only key was `error`, and it produced a
confident sentence claiming a successful lookup. Nothing in this run is a bug in the model: it was
given something that looked like a tool result and it summarised it.

Compare the two `the run raised:` lines. `None` against `TimeoutError`. The version that hides the
outage is the version that does not crash — which is why *"we haven't seen any errors"* is not
evidence of anything.

## When it breaks

The swallowed version produces **no error text at all**, and that is the finding rather than a gap in
this section. There is no traceback, no log line, no non-zero exit, no failed span. The only artefact
is a sentence to a user that happens to be untrue.

What you get *when you fix it* is the whole of the `SWALLOW=0` output above, and it is worth noticing
that this is a legitimate reason people revert the fix:

```text
TimeoutError: kb.internal:8080 timed out after 5s
```

An exception reaching the caller looks like a regression. The conversation goes *"it used to work and
now it throws"* — and the honest answer is that it never worked, it returned a lie, and the throw is
the first accurate thing it has done. That answer needs the measurement above to be persuasive, which
is why this part is a lab and not a lecture.

The correct end state is neither of the two runs: raise from the tool, and rescue *in the plugin*
with a marked substitute, which is [2.2](../02-four-hooks/2.2-the-two-that-can-rescue.md) plus
[3.2](../03-policy/3.2-a-substitute-must-say-so.md). Three hooks fire, policy decides, and the user
gets a true sentence.

## In production

**The lint rule is worth more than the code review.** `except Exception` followed by `return` inside
anything registered as a tool is mechanically detectable, and Day 31's `./m check` is where Sutra's
repo-wide rules live. A convention that depends on eleven people remembering is a convention with a
half-life.

**What changes at scale** is that the swallowed error becomes a data-quality problem rather than an
outage. One tool swallowing timeouts, at 2% of calls, produces a steady trickle of confidently wrong
answers indistinguishable from model error. Teams spend months on prompt engineering and model
upgrades against a metric that a `try`/`except` is holding down. This is the single most expensive
version of the bug and it is invisible to every dashboard.

**The failure that only appears with real traffic** is the *partially* swallowed error. A tool catches
`ConnectionError` specifically — narrow, careful, reviewed — and six months later the dependency
starts raising `TimeoutError` instead, which is not caught, and the tool starts raising for the first
time in its life. Now you have an outage that looks like a deploy regression, in a code path nobody
has read since it was written.

**The review comment a senior engineer leaves:** *"delete the try/except. Let it raise. We have a
plugin that classifies, substitutes and logs, and while this is here none of that runs for this tool —
and the model gets a dict with the word `error` in it and cheerfully summarises it."*

**The interview question:** *"why is catching exceptions inside a tool a problem for an agent
framework?"* The answer that shows you have counted the hooks: *"because the exception is what starts
the error path. We measured it: raising fired three plugin hooks and failed the run; catching it and
returning a dict fired zero error hooks, the run reported success, and the agent told the user it had
found the article. The retry policy, the logging and the traces all hang off the exception, so
swallowing it doesn't handle the error, it deletes it."*
