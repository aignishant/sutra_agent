# 4.2 — 💥 The handler that became the error

## One-line answer

A plugin hook that raises while handling a failure gets wrapped by ADK and **replaces** the original
failure: the run reported `'str' object has no attribute 'get'` and the `TimeoutError` that started
it was not named anywhere in what escaped.

## The story

The fire door on the stairwell was propped open with a bin.

There was a reason. The lock had swollen in the heat and the door was jamming, and propping it saved
somebody being shut out twenty times a day while the joiner was booked. Sensible, temporary,
well-intentioned.

Six weeks later there is a small fire on the landing, and the incident report is about the fire door.
Not about the fire — about the door. The investigation, the paperwork, the letter to the insurers and
the conversation everybody remembers are all about a bin. The actual cause of the fire is a line in an
appendix.

The propped door did not start the fire. It replaced it as the story.

## The idea in plain language

Every part of this day has been about making failures travel. This part is about what happens when the
code you added to carry them fails on the way.

The situation is specific and it is common: your plugin has more than one hook. One of them rescues, so
the run continues, so the **success** hooks fire — and one of those reads the rescued value. If the
rescue returned a shape the success hook did not expect, the success hook raises.

ADK does not let that pass silently. It wraps it:

```
RuntimeError: Error in plugin 'policy' during 'after_tool_callback' callback:
'str' object has no attribute 'get'
```

That is a genuinely good error message — it names the plugin and the callback, which is more than most
frameworks manage. But look at what it does to the ladder from
[2.4](../02-four-hooks/2.4-the-ladder.md). The `TimeoutError` was rescued and is gone. What now climbs
to the agent and run hooks is a `RuntimeError` about your plugin. Every downstream consumer — your
log, your alert rule, your exception tracker, the on-call engineer's first five minutes — is told
about a `'str' object has no attribute 'get'`.

The knowledge base is down. Nothing anywhere says so.

Two properties make this worse than an ordinary bug.

**It is centralised.** [5.1](../05-in-production/5.1-one-policy-not-a-hundred.md) is about putting
policy in one plugin, and that is the right design — but one plugin means one place whose bugs affect
every failure in the system, not one tool's.

**It only runs when something else is already wrong.** The handler path is exercised exactly when a
dependency is down, which is the least tested state your system has and the worst moment to discover a
second defect.

## Why Sutra needs it

Because Sutra's error policy is one plugin as of today, and it is about to grow.

Day 22 adds a structured log line to these hooks. Day 24 adds budget accounting. Day 84 adds tracing
spans. Every one of those is code in the error path, reading fields off values other code produced, and
each one is an opportunity for the handler to become the error. The plugin that carries Sutra's honesty
is the code that most needs to be dull.

There is a second reason, and it is about debugging. If Sutra's error hooks can replace the errors they
report, then the log is not a record of what went wrong — it is a record of what went wrong *last*. Day
22's logging and Day 79's evals both assume the opposite.

## The mechanism

The same rescue as [2.2](../02-four-hooks/2.2-the-two-that-can-rescue.md), with the rescue's return
type changed from a dict to a string — the shape the 1.x habit produces — while a success hook goes on
assuming a dict.

```python
# days/day-21-errors-surface-not-swallow/lab/handler_that_broke.py
"""The error handler is the last code you want to be fragile. Here is what it costs when it is."""

HEARD: list[str] = []
SAFE = os.environ.get("SAFE", "1") == "1"


def lookup_article(article_id: str) -> dict[str, Any]:
    """Fetch a knowledge-base article. The knowledge base is down."""
    raise TimeoutError("kb.internal:8080 timed out after 5s")


class Policy(BasePlugin):
    """Rescues the tool, then logs the result - and the logging is where it goes wrong."""

    async def on_tool_error_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, error: Exception
    ) -> dict[str, Any] | None:
        HEARD.append(f"on_tool_error_callback   {type(error).__name__}: {error}")
        # SAFE=0 returns a string, which is the shape the 1.x habit produces.
        if SAFE:
            return {"status": "unavailable", "reason": f"{type(error).__name__}: {error}"}
        return f"Error: {error}"

    async def after_tool_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, result: Any
    ) -> dict[str, Any] | None:
        # Assumes a dict. This is the line that breaks.
        HEARD.append(f"after_tool_callback      status={result.get('status')}")
        return None
```

**Line by line:**

- `SAFE=0` returns `f"Error: {error}"` — a **string** from a hook whose contract is
  `dict[str, Any] | None`. Python does not enforce the annotation, so this is accepted at the hook
  boundary and causes trouble later, which is what makes it realistic. Nobody writes this on purpose;
  it is what a hurried edit produces from muscle memory.
- `result: Any` in `after_tool_callback` is deliberately *looser* than
  [2.2](../02-four-hooks/2.2-the-two-that-can-rescue.md)'s `dict[str, Any]`, because a strict
  annotation would suggest the type is checked. It is not. The annotation documents an assumption and
  the `.get()` call **relies** on it.
- `result.get("status")` is the single fragile line, and it is the sort of line that is written in a
  logging statement without a second thought. There is no `try` around it because nobody puts a `try`
  around a log line.
- The `SAFE=1` branch returns the marked substitute from
  [3.2](../03-policy/3.2-a-substitute-must-say-so.md), so the two arms differ only in the *type* of the
  rescue, not in whether a rescue happens.
- The tool raises unconditionally in both arms. The dependency is equally down in both runs; only the
  handler differs.
- The final print asks whether `TimeoutError` still appears in whatever escaped. That question is the
  whole measurement, and putting it in the script rather than in the prose is what makes it checkable.

```bash
cd days/day-21-errors-surface-not-swallow/lab
SAFE=1 uv run python handler_that_broke.py
SAFE=0 uv run python handler_that_broke.py
```

**Line by line:**

- `SAFE=1` first: the working version, so the difference is visible rather than merely described.
- Recording models throughout: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
SAFE=1
    on_tool_error_callback   TimeoutError: kb.internal:8080 timed out after 5s
    after_tool_callback      status=unavailable
  the run raised: None
  the user was told: 'Reported the outage.'
  is the original TimeoutError still named in what raised? False

SAFE=0
    on_tool_error_callback   TimeoutError: kb.internal:8080 timed out after 5s
    on_agent_error_callback  RuntimeError
    on_run_error_callback    RuntimeError
  the run raised: RuntimeError: Error in plugin 'policy' during 'after_tool_callback' callback: 'str' object has no attribute 'get'
  the user was told: None
  is the original TimeoutError still named in what raised? False
```

**In the broken arm, the exception type changed.** `TimeoutError` went in; `RuntimeError` came out.
Every alert rule, dashboard filter and exception-tracker grouping that keys on the type is now looking
at the wrong thing — and it is not looking at *nothing*, which would at least be suspicious. It is
looking at a confident, specific, wrong answer.

**The rescue succeeded before it broke.** Read the first line of the `SAFE=0` output: the tool hook
fired and returned. The `TimeoutError` was handled. It stopped at rung one, exactly as designed. Then
the *next* hook along raised, and the ladder restarted from the middle with a different exception.

**`is the original TimeoutError still named in what raised? False`** in both arms, and the two `False`s
mean opposite things. In the safe arm nothing raised at all, so there was nothing to name. In the broken
arm something raised and it does not mention the outage anywhere — not in the type, not in the message.
An engineer paged by this has to work backwards from `'str' object has no attribute 'get'` to *"the
knowledge base is down"*, with no thread connecting them.

**And the user got nothing.** The failure the rescue existed to soften went from *"Reported the
outage"* to silence, because the code meant to soften it fell over.

## When it breaks

The error text is the whole point of this part and it is above, but it is worth reading once more with
attention to what is good about it:

```text
RuntimeError: Error in plugin 'policy' during 'after_tool_callback' callback:
'str' object has no attribute 'get'
```

ADK names **the plugin** (`'policy'`) and **the callback** (`'after_tool_callback'`). That is the
difference between a fifteen-minute debug and a two-hour one, and it is the reason to name plugins
something meaningful rather than `Plugin`. A message reading *"Error in plugin 'plugin' during
callback"* would be technically identical and useless.

What the message cannot tell you is what it replaced. Nothing in it says a `TimeoutError` was handled
moments earlier. Python's exception chaining exists for exactly this, and ADK is not using it here —
the wrapped error is a fresh `RuntimeError`, not a `raise ... from error`. So the connection has to
come from your own logging, which means the log line has to be emitted in
`on_tool_error_callback`, **before** the fragile code runs.

## In production

**Log at the entry hook, then do everything else.** The first statement in `on_tool_error_callback`
should be the structured record: exception type, message, tool name. If the rest of the handler then
falls over, you still have the outage in your logs. Every line of policy after that record is a line
whose failure you can survive.

**Make the error path defensive in a way you would not accept anywhere else.** `result.get("status")`
becomes `result.get("status") if isinstance(result, dict) else result`. That is ugly, and it is correct
here: this code runs when the system is already broken, and it must not be the second thing to break.
It is one of the few places where belt-and-braces beats clean.

**What changes at scale** is that the handler's bug rate becomes your *apparent* failure profile. Once
policy is centralised, a defect in it appears on every failing request, so your top exception by volume
becomes a `RuntimeError` from your own plugin and the real dependency problems fall below it. Teams
have spent weeks debugging the wrong signal here.

**The failure that only appears with real traffic** is the field that is usually present. A handler
reading `error.response.status_code` works for every HTTP failure and raises `AttributeError` the first
time a `TimeoutError` arrives without a response — which is a different code path in the same
dependency, hit for the first time during a real outage.

**The review comment a senior engineer leaves:** *"the log line in `after_tool_callback` assumes the
result is a dict. Our own rescue can return other shapes, and if this raises, ADK wraps it and we lose
the original error. Guard the access and move the log to `on_tool_error_callback`."*

**The interview question:** *"what happens if your error handler throws?"* The answer that shows you
have been paged by it: *"in ADK you get a `RuntimeError` naming the plugin and the callback, which is
helpful — but it *replaces* the original exception on the way out, so the type changes and nothing
mentions the real failure. We log the structured record as the first statement in the entry hook, before
any policy runs, so an outage survives a bug in the code that was supposed to report it."*

Now add a log line as the **first** statement of `on_tool_error_callback` that prints the exception

outage is now recorded anyway. That is the fix, and it is one line in the right place.
