# 3.2 — A substitute must say so

## One-line answer

The same outage, rescued two ways: a fallback with a `status` field made the agent say *"I could not
reach the knowledge base"*, and a fallback shaped like an empty result made it say *"KB-104 has no
content recorded"* — which is a false statement about the world.

## The story

The shop is out of the size you wanted.

The assistant who says *"we haven't got that in a 42, sorry"* has told you something true and you go
somewhere else. The one who checks the back, finds nothing, and says *"no, we don't stock that"* has
also said something that sounds like an answer — and now you believe the shop never has it, so you
stop coming.

He was not lying. He filled in the gap in his knowledge with the nearest confident sentence, because
"we have not got it right now" and "we do not stock it" feel like the same information from behind
the counter and are completely different information in front of it.

## The idea in plain language

[2.2](../02-four-hooks/2.2-the-two-that-can-rescue.md) established the mechanism: return a `dict` from
`on_tool_error_callback` and the exception stops, the run resumes, and `after_tool_callback` fires
normally. The framework does not care what is *in* the dict.

This part is about the fact that the dict's **shape** decides what the agent says next, and there are
two shapes that both look reasonable in a code review.

**The marked substitute.** `{"status": "unavailable", "reason": "...", "instruction": "..."}`. Nothing
in it can be mistaken for a result. There is no `title`, no `body`, no `found` — the fields are about
the *failure*, so a model reading it has nothing to summarise and no choice but to report the outage.

**The empty result.** `{"article_id": "KB-104", "title": "", "body": "", "found": False}`. This is the
shape people reach for, and the reasoning behind it is good: *keep the tool's contract stable so
callers do not need a special case.* It is a real engineering principle. Applied here it produces a
value that is indistinguishable from a successful lookup of an empty article, and a model handed it
will say the thing that is true of an empty article.

The distinction that matters, stated once: **`found: False` and `status: "unavailable"` are not the
same claim.** The first says *we looked and there is nothing there.* The second says *we could not
look.* Every downstream decision differs — whether to retry, whether to escalate, whether to tell the
customer their ticket has no notes — and only the second one is true when the knowledge base is down.

This is [1.2](../01-who-hears-it/1.2-an-error-is-a-fact.md) with consequences attached. There the
argument for fields was that code can branch on them. Here it is sharper: **a field is the only place
"this did not happen" can be recorded.** A stable-shaped empty result has nowhere to put it.

## Why Sutra needs it

Because Sutra's answers go to a customer, and *"your ticket has no notes attached"* is a sentence that
gets acted on.

The support engineer reads it and closes the ticket. The customer reads it and believes their
escalation was never recorded. Neither of them has any way to know that a database was briefly
unreachable, because at no point did anything in the system claim a failure had occurred — the tool
was rescued, the run succeeded, and the sentence was a correct summary of the data it was given.

This is also the day's `SEC-02` content in its sharpest form. Honest error surfacing is not only about
exceptions reaching logs. It is about the system being incapable of asserting something it does not
know, and a fallback shaped like a result is precisely how that capability gets built by accident.

## The mechanism

One outage, one hook, two fallback shapes, and the sentence each produces.

```python
# days/day-21-errors-surface-not-swallow/lab/fallback_that_lied.py
"""A rescue is allowed to be a substitute. It is not allowed to look like an answer."""

# HONEST=1 marks the substitute as a substitute. HONEST=0 makes it read like a real result.
HONEST = os.environ.get("HONEST", "1") == "1"

HONEST_FALLBACK = {
    "status": "unavailable",
    "reason": "TimeoutError: kb.internal:8080 timed out after 5s",
    "instruction": "Tell the user the knowledge base is unreachable. Do not guess.",
}
DISHONEST_FALLBACK = {"article_id": "KB-104", "title": "", "body": "", "found": False}


def lookup_article(article_id: str) -> dict[str, Any]:
    """Fetch a knowledge-base article. The knowledge base is down."""
    raise TimeoutError("kb.internal:8080 timed out after 5s")


class Policy(BasePlugin):
    async def on_tool_error_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, error: Exception
    ) -> dict[str, Any] | None:
        return dict(HONEST_FALLBACK if HONEST else DISHONEST_FALLBACK)


class Summariser(BaseLlm):
    """Stands in for a real model: answers from whatever the tool returned."""

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        responses = [
            part.function_response
            for content in llm_request.contents
            for part in (content.parts or [])
            if part.function_response
        ]
        if not responses:
            yield LlmResponse(
                content=types.Content(
                    role="model",
                    parts=[
                        types.Part(
                            function_call=types.FunctionCall(
                                name="lookup_article", args={"article_id": "KB-104"}
                            )
                        )
                    ],
                )
            )
            return
        got = responses[-1].response
        # What a real model does with each shape, written out so the run is deterministic.
        if got.get("status") == "unavailable":
            text = "I could not reach the knowledge base, so I cannot tell you what KB-104 says."
        else:
            text = "KB-104 has no content recorded, so there is nothing to action on this ticket."
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text=text)]))
```

**Line by line:**

- The two fallbacks are **the same length and the same type**. Neither is sloppier than the other, and
  `DISHONEST_FALLBACK` is arguably the more professional-looking of the two: it matches the tool's
  real return shape, which is what a schema-conscious reviewer asks for.
- `DISHONEST_FALLBACK` carries `found: False`, and that field is the trap. It looks like honesty. It
  is a claim about the *article*, when the thing that failed was the *lookup*.
- `dict(...)` copies the constant on every call, so a hook cannot accidentally mutate the module-level
  fallback and poison every later rescue. This is a small habit and it matters in a plugin, which is
  long-lived and shared.
- `Summariser` is a **fake model with the two sentences written out**, and that choice needs
  defending. A live model would produce a different sentence on every run and the comparison would be
  anecdote. These two sentences are what a competent model produces from these two inputs, and writing
  them into the file makes the run deterministic and the point checkable. The claim being tested is
  *what the model is given*, not *what a particular model says*.
- `got.get("status") == "unavailable"` is the branch, and it is one line — which is the argument. A
  model, a logger, a metric and a test can all ask the same question of a marked substitute. None of
  them can ask it of the empty result.
- `if not responses:` handles the first turn, where the model must ask for the tool before there is
  anything to report. The tool-call/response round trip is [Day 4](../../../day-04-tools-by-hand/LESSON.md)'s
  loop, unchanged.

**Line by line:**

- Two runs, one environment variable, everything else identical.
- Recording models throughout: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
HONEST=1
  the substitute handed to the model: {'status': 'unavailable', 'reason': 'TimeoutError: kb.internal:8080 timed out after 5s', 'instruction': 'Tell the user the knowledge base is unreachable. Do not guess.'}
  does it say a failure happened?     True
  the user was told: 'I could not reach the knowledge base, so I cannot tell you what KB-104 says.'

HONEST=0
  the substitute handed to the model: {'article_id': 'KB-104', 'title': '', 'body': '', 'found': False}
  does it say a failure happened?     False
  the user was told: 'KB-104 has no content recorded, so there is nothing to action on this ticket.'
```

**Both runs succeeded.** No exception, no hook beyond the first, no error in any log. The rescue worked
perfectly in both arms — which is the point, and why this cannot be caught by watching for failures.

**The `HONEST=0` sentence is false.** KB-104 may be a four-page article. Nobody looked. And the second
half — *"there is nothing to action on this ticket"* — is a recommendation built on top of the false
premise, which is how a fallback shape turns into a decision.

**The middle line is the whole design in one boolean.** *Does the substitute say a failure happened?*
`True` or `False`, computed by checking for a single field. That is a thing a test can assert, which is
what [5.2](../05-in-production/5.2-testing-the-failure-path.md) does, and it is the cheapest available
guard against this entire class of bug.

**And notice `instruction` in the honest fallback.** *"Do not guess."* It is belt-and-braces: the
absence of result-shaped fields already gives the model nothing to summarise, and the instruction
tells it what to do with that. Both cost nothing, and a substitute is exactly the place to spend a
sentence on being explicit.

## When it breaks

There is no error text. That is the finding, and it is why this part is at `production` level rather
than `working`: the failure is a true-looking sentence, and the only way to catch it is to look at what
the model was handed.

🎬 **The scene:** a customer complains that Sutra told them their escalation had no notes. It has four.
😬 **The naive fix:** you check the notes tool, which works. You check the model, which summarised
correctly. You conclude it was a one-off and add a firmer instruction about not making claims.
💥 **Why it fails:** nothing was wrong with either. The notes lookup timed out for eleven seconds that
afternoon, the plugin rescued it with `{"notes": [], "count": 0}`, and the model reported an empty
list accurately. There is no traceback, because the rescue succeeded. There is no error log, because
nothing escaped the first rung of [2.4](../02-four-hooks/2.4-the-ladder.md)'s ladder. The instruction
you added does nothing, because the model was not guessing.
💡 **The insight:** a substitute that carries no marker has not degraded gracefully — it has
**fabricated a result**, one layer up from the tool, in the place you put to make failures honest.

## In production

**Make the marker structural, not conventional.** One `substitute()` helper that always emits
`status`, `reason` and `at`, used by every rescue, so a fallback without a marker is impossible rather
than merely discouraged. Sutra's repo already prefers `dataclasses` over ad-hoc dicts, and this is a
case where the type is doing real safety work.

**What changes at scale** is that `status` becomes something several systems read, so its values become
an interface. Three of them is usually enough — `unavailable`, `denied`, `not_found` — and the
temptation to add a fourth per dependency is how it stops being checkable. Variety goes in `reason`,
which nothing branches on.

**The failure that only appears with real traffic** is the substitute that becomes normal. If a
dependency is flaky for a month, users see the degraded sentence constantly, learn to work around it,
and stop reporting it. Meanwhile the honest marker means your logs *do* have the data — so this failure
is only invisible if nobody is counting substitutions, which is
[2.4](../02-four-hooks/2.4-the-ladder.md)'s recommendation and the reason it is worth doing.

**The review comment a senior engineer leaves:** *"the fallback returns the tool's normal shape with
empty values. That's the tool saying 'there is nothing there' when it means 'I could not look'. Give it
a `status` and drop the result fields, or the model will summarise the empty one."*

**The interview question:** *"you catch a tool failure and return a fallback so the agent can continue.
What does the fallback look like?"* The answer that shows you have shipped the wrong one: *"it has a
status field and no result fields. If it keeps the tool's normal shape with empty values, the model
can't tell a failure from an empty result — we had exactly that, and the agent told a customer their
ticket had no notes when the notes database had just timed out. `found: False` and `status:
unavailable` are different claims and only one of them was true."*
