# 3.1 — Which 429 is it?

## One-line answer

Two completely different failures arrive as HTTP 429 — a per-minute ceiling that clears on its own and
a per-day ceiling that does not — and retrying the second one spent three of Sutra's twenty daily
requests learning nothing.

## The story

Two red lights on the same dashboard, and they mean opposite things.

One is the engine temperature light coming on in traffic on a hot day. Pull over, let it sit, and in
ten minutes it goes out and you drive home. Waiting is the fix.

The other is the oil pressure light. Same colour, same size, two inches away on the same panel. There
is no amount of sitting that fixes it, and the ten minutes you spend hoping is ten minutes the engine
spends being damaged.

Nobody would design a car this way. Every API is designed this way.

## The idea in plain language

[1.3](../01-who-hears-it/1.3-retry-substitute-escalate.md) said retry is only correct for a failure
that can clear on its own. This part is about the fact that the most common failure in Sutra's life
arrives in two versions — one that clears and one that does not — wearing the same status code.

**A per-minute limit.** You have made too many requests in the last minute. Wait, and the window
slides, and the ceiling lifts. Retrying is exactly right, and the response even tells you how long to
wait.

**A per-day limit.** You have used your allowance for the day. Nothing clears until midnight.
Retrying is not merely useless — it is *actively harmful*, because on a free tier a refused request
still occupies your attention, your latency budget, and in the worst case your allowance.

Both are `429 RESOURCE_EXHAUSTED`. Both say `Please retry in <n>s`.
[Day 20](../../../day-20-context-engineering-compaction/parts/01-notes-not-transcript/1.3-you-spend-calls-to-save-calls.md)
already established, from a live response body, that the `Please retry in 57.99s` on a daily quota is
a **backoff suggestion and not a window reset** — Day 2 tested it by sending 28 requests across a
quarter of an hour, each obeying the stated delay, and every one was refused.

So the classifier cannot key on the status code. What it can key on is the **quota metric name**,
which Google puts in the body:

| Failure | The metric named in the body | Retryable |
| --- | --- | --- |
| per-minute ceiling | `...generate_requests_per_minute` | yes |
| per-day ceiling | `generativelanguage.googleapis.com/generate_content_free_tier_requests` | **no** |

That is a substring match, and [1.2](../01-who-hears-it/1.2-an-error-is-a-fact.md) has already
explained why substring matches on somebody else's prose are fragile. It is fragile here too. The
difference is that a *metric name* is a machine-facing identifier that appears in a `QuotaFailure`
detail block, not a sentence written for humans — which makes it the most stable thing available, and
worth pinning a test to so that a change is loud.

## Why Sutra needs it

Because Sutra has twenty requests a day per model, and this classifier is worth three of them.

That is not a rounding error. It is 15% of the daily budget, spent on the single most likely failure
Sutra meets, and spent at the worst possible moment — after the budget has already run out, when
every remaining request matters more than the ones already used.

It also decides whether Day 24's accounting can be trusted. A budget that counts requests but does not
know which failures cost one will drift from reality on exactly the days the budget matters. And Day
70's quota router cannot route around an exhausted provider if it cannot tell "exhausted" from "busy".

## The mechanism

The two 429 bodies, put through a classifier with the classification switched on and off, against a
twenty-request daily budget.

```python
# days/day-21-errors-surface-not-swallow/lab/retry_made_it_worse.py
"""Retrying is a decision about *which* error. Blind retry spends the budget it is waiting for."""

import os

# The two 429s a free tier can hand you. They read almost identically.
PER_MINUTE = (
    "429 RESOURCE_EXHAUSTED. Quota exceeded for metric: generate_requests_per_minute, "
    "limit: 10. Please retry in 12.4s."
)
PER_DAY = (
    "429 RESOURCE_EXHAUSTED. Quota exceeded for metric: "
    "generate_content_free_tier_requests, limit: 20, model: gemini-3.7-flash. "
    "Please retry in 57.991539991s."
)

CLASSIFY = os.environ.get("CLASSIFY", "1") == "1"
DAILY_QUOTA = 20
MAX_ATTEMPTS = 4


def is_retryable(message: str) -> bool:
    """A per-minute ceiling clears on its own. A daily one does not."""
    if not CLASSIFY:
        return "429" in message  # the blind version: every 429 looks the same
    return "429" in message and "per_minute" in message


def attempt(message: str, budget: int, clears_after: int | None) -> tuple[int, int, bool]:
    """Retry up to MAX_ATTEMPTS. `clears_after` is when the ceiling lifts, or None for never."""
    calls = 0
    for n in range(1, MAX_ATTEMPTS + 1):
        calls += 1
        budget -= 1
        if clears_after is not None and n >= clears_after:
            return calls, budget, True
        if not is_retryable(message):
            return calls, budget, False
    return calls, budget, False


CASES = (
    ("per-minute 429", PER_MINUTE, 3),  # clears on the third attempt
    ("daily 429", PER_DAY, None),  # never clears today
)

for label, message, clears in CASES:
    calls, left, recovered = attempt(message, DAILY_QUOTA, clears)
    print(
        f"CLASSIFY={'1' if CLASSIFY else '0'}  {label:<15} "
        f"calls made: {calls}  daily budget left: {left:>2}  recovered: {recovered}"
    )
```

**Line by line:**

- `PER_MINUTE` and `PER_DAY` are the two bodies written out in full so you can read them next to each
  other. Cover the metric name in each and they are the same message: same status, same phrase, both
  ending in a retry suggestion.
- `PER_DAY` is the real one. Its metric name, its `limit: 20` and its
  `Please retry in 57.991539991s` were captured from a live response on 2026-09-03, and the
  fifty-eight seconds is the number that makes this failure look retryable.
- `if not CLASSIFY: return "429" in message` is the **blind** classifier, and it is written first
  because it is what everybody writes first. It is not stupid code; it is correct for one of the two
  cases and there is no way to tell from the status code that a second case exists.
- `"per_minute" in message` is the classification, and it keys on the **quota metric name** rather than
  on the human sentence. `per_minute` appears in the metric identifier; nothing in the prose
  distinguishes the two.
- `clears_after` is what makes the comparison honest. Without it, retry never succeeds in this
  simulation and the file would be arguing that retry is useless, which is false — the per-minute row
  exists to show retry doing its job.
- `budget -= 1` before the recovery check, because a refused request has already been made. That is
  the accounting point of the whole file: you spend the request and then find out.
- `attempt` returns three numbers rather than a boolean, because "did it work" is the least
  interesting of them. What it cost is the question.

```bash

CLASSIFY=1 uv run python retry_made_it_worse.py
CLASSIFY=0 uv run python retry_made_it_worse.py
```

**Line by line:**

- Two runs, one variable: the classifier on, then off.
- Pure Python arithmetic over two string constants. No key, no network, no quota spent.

Measured on 2026-09-03:

```text
CLASSIFY=1  per-minute 429  calls made: 3  daily budget left: 17  recovered: True
CLASSIFY=1  daily 429       calls made: 1  daily budget left: 19  recovered: False

CLASSIFY=0  per-minute 429  calls made: 3  daily budget left: 17  recovered: True
CLASSIFY=0  daily 429       calls made: 4  daily budget left: 16  recovered: False
```

**The per-minute rows are identical, and that matters.** Classification costs nothing on the case
where retry is right: three calls, recovered, in both arms. Anyone arguing that classification is
premature optimisation is arguing about a row where it changes nothing.

**The daily rows are where the money is.** One call against four. Nineteen requests left against
sixteen. **Three requests of a twenty-request day, burned on an error that could not clear**, and both
arms end with `recovered: False` — the blind version did not buy a worse outcome, it bought the same
outcome three requests later.

**And notice what "gave up" looks like in the classified run: one call.** It made the request, read
the metric name, and stopped. That is the whole of good retry policy in one number, and it is
achieved by a single `and` in a boolean expression.

## When it breaks

The classifier's failure mode is a wording change, and it is silent. Here is the body it is reading,
captured live on 2026-09-03:

```text
{'error': {'code': 429, 'message': 'You exceeded your current quota, please check your plan and
billing details. For more information on this error, head to:
https://ai.google.dev/gemini-api/docs/rate-limits. ... * Quota exceeded for metric:
generativelanguage.googleapis.com/generate_content_free_tier_requests, limit: 20, model:
gemini-3.7-flash Please retry in 57.991539991s.', 'status': 'RESOURCE_EXHAUSTED',
'details': [{'@type': 'type.googleapis.com/google.rpc.QuotaFailure', 'violations':
[{'quotaMetric': 'generativelanguage.googleapis.com/generate_content_free_tier_requests',
'quotaId': 'GenerateRequestsPerDayPerProjectPerModel-FreeTier', ...}]}]}
```

Two useful things in that body that the simplified constant above does not show.

**The `details` block carries a structured `QuotaFailure`** with `quotaMetric` and `quotaId` as
fields. `GenerateRequestsPerDayPerProjectPerModel-FreeTier` says *PerDay* in an identifier, not in a
sentence. Reading the structured detail rather than the message string is the production version of
this classifier, and it is the same argument as
[1.2](../01-who-hears-it/1.2-an-error-is-a-fact.md): prefer the field over the prose.

**And there is no per-minute example here to compare against**, because the day this was written the
daily ceiling was hit first. That is honest and it is a limitation: the `per_minute` half of the
classifier above is written against a plausible metric name and has **not** been confirmed against a
live per-minute refusal. `TODO(me)`: trigger one by sending requests in a tight loop early in the day,
capture the body, and pin the real metric name with a test —

## In production

**Read the structured detail, not the message.** `error.details[].violations[].quotaId` is a machine
identifier with a stable vocabulary. The `message` field is documentation, and documentation gets
rewritten. Pin a test to whatever you key on so a provider change is a red test rather than a quiet
behaviour change.

**What changes at scale** is that the classifier gains a third category: *retryable, but not by you*.
A per-minute ceiling on a shared project is not yours to wait out — every other caller is waiting too,
and all of you retrying at once is the thundering herd that keeps the ceiling pinned. At that point
retry needs jitter and a shared circuit breaker, which is Day 70's quota router rather than a boolean.

**The failure that only appears with real traffic** is the reclassification. A provider changes a
per-minute limit to a per-hour limit, your `per_minute` substring stops matching, and every 429
becomes non-retryable overnight. Availability drops, nothing errors, and the cause is three words in
somebody else's release notes. Alert on the *ratio* of retried to non-retried 429s; a step change in
it is the earliest signal you will get.

**The review comment a senior engineer leaves:** *"`if '429' in str(error)` — which 429? We've got a
per-minute one and a daily one and retrying the daily one costs us three requests every time. Key on
the `quotaId` and add a test with both bodies."*

**The interview question:** *"you get a 429 from your model provider. Do you retry?"* The answer that
shows you have paid for the wrong choice: *"depends which 429. A per-minute ceiling clears, so yes,
with backoff. A daily one doesn't, and the response still says 'please retry in 58 seconds' — we
tested that and it's a suggestion, not a reset. We classify on the quota metric in the error details,
because retrying the daily one was costing us three of twenty daily requests every time it happened."*
