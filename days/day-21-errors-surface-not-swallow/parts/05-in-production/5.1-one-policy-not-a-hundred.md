# 5.1 — One policy, not a hundred try/excepts

## One-line answer

The same error policy written per tool is 154 lines across 11 files that a new tool does not inherit;
written once in a plugin it is 14 lines in one file that every tool gets for free — and the choice of
*which layer* handles a failure is a question the field settled in 1984.

## The story

Every flat in the block used to have its own water tank in the loft.

It worked. Each flat controlled its own supply, each tank was sized for its own household, and when
one leaked it was one flat's problem. Eleven flats, eleven tanks, eleven ballcocks, eleven sets of
pipework that somebody had to remember to lag before winter.

The building was refitted with a single pressurised main. One plant room, one set of valves, one
service contract. Flat nine, which has always been fine, gained nothing it can point to. What the
building gained is that the twelfth flat, built in the loft conversion, is plumbed correctly because
there is only one way to plumb it.

## The idea in plain language

Sections 1 through 4 built a policy: classify the failure
([3.1](../03-policy/3.1-which-429-is-it.md)), retry, substitute with a marker
([3.2](../03-policy/3.2-a-substitute-must-say-so.md)), or escalate with a redacted public message
([3.3](../03-policy/3.3-giving-up-honestly.md)). That policy is roughly fourteen lines of code.

There are two places to put it, and the question is not really about line count.

**In each tool.** Every tool wraps its own work and applies the policy. Nothing new to learn, no
framework knowledge required, and each tool is self-contained — which is a genuine virtue.

**In one plugin on the `App`.** Tools raise; the plugin decides. This is
[Day 14](../../../day-14-plugins-one-layer-up/LESSON.md)'s argument, and it is the same argument as
this part's title: *a rule nobody has to remember is a rule that holds.*

The measurement below counts both, and the interesting row is not the line count. It is the last two:
how many tools can **silently opt out**, and how many new tools get the policy **for free**. Those are
the same number, inverted, and they are the only rows that describe what happens six months from now.

The per-tool version has a specific failure mode, and [4.1](../04-failure-lab/4.1-the-swallowed-exception.md)
already measured it: a tool that handles its own errors is a tool that has opted out of every
cross-cutting concern in the system, and it does so without saying anything. With eleven tools, that is
eleven independent chances for somebody to write four defensive lines on a bad afternoon.

There is one honest argument on the other side and it deserves stating. Policy in the tool has more
*context*: `lookup_article` knows that a 404 from the knowledge base means the article was deleted,
which the plugin cannot know. The resolution is not to move policy back down — it is to have the tool
**raise a specific exception**, and let the plugin classify on the type. The tool contributes
knowledge; the plugin contributes policy. That division is the whole idea, and it is old.

## Why Sutra needs it

Because Sutra will have eleven tools by the end of Phase 5 and forty by the capstone, and it is being
written one day at a time by somebody learning.

That is exactly the condition the per-tool version fails under. The eleven tools are not written in one
sitting by one person with the policy fresh in mind; they are written across months, and tool nine is
written on a day when the knowledge base is flaky and catching the error is the fastest way to get to
the end of the exercise.

It also decides what Day 22, Day 24 and Day 84 can assume. Structured logging, budget accounting and
tracing are all cross-cutting concerns that hang off the same hooks. Each one is cheap if there is a
single error path and impossible if there are eleven.

## The paper behind it

> **End-to-end arguments in system design**
> `doi:10.1145/357401.357402` · ACM Transactions on Computer Systems 2(4), 277–288 · 1984 ·
> <https://doi.org/10.1145/357401.357402>

It argued that a function should be placed at the layer that has the knowledge to do it correctly and
completely, and that implementing it at a lower layer is often redundant, incomplete, or both — which
is the design question this part is asking about error policy.

It is taught in [the paper part](../../papers/01-end-to-end-arguments.md). Read it after the parts.

## The mechanism

The same fourteen-line policy, counted in both placements, over Sutra's realistic tool list.

```python
# days/day-21-errors-surface-not-swallow/lab/where_policy_lives.py
"""Same policy, two placements. Count what each costs to write, to change, and to get wrong."""

TOOLS = [
    "lookup_article",
    "search_tickets",
    "get_ticket",
    "list_notes",
    "post_comment",
    "set_severity",
    "assign_owner",
    "close_ticket",
    "fetch_customer",
    "check_entitlement",
    "search_web",
]

# The policy, as decided in section 1: classify, then retry / substitute / escalate.
POLICY_LINES = 14  # the body of one on_tool_error_callback that does all three


def per_tool() -> dict[str, int]:
    """Every tool handles its own errors."""
    return {
        "places the policy lives": len(TOOLS),
        "lines of policy in the repo": len(TOOLS) * POLICY_LINES,
        "files to edit to change it": len(TOOLS),
        "tools that can silently opt out": len(TOOLS),
        "new tools that get it for free": 0,
    }


def one_plugin() -> dict[str, int]:
    """One plugin on the App handles every tool's errors."""
    return {
        "places the policy lives": 1,
        "lines of policy in the repo": POLICY_LINES,
        "files to edit to change it": 1,
        "tools that can silently opt out": 0,
        "new tools that get it for free": len(TOOLS),
    }


left, right = per_tool(), one_plugin()
width = max(len(k) for k in left)
print(f"{'':<{width}}  {'per tool':>10}  {'one plugin':>11}")
for key in left:
    print(f"{key:<{width}}  {left[key]:>10}  {right[key]:>11}")

print(f"\n{len(TOOLS)} tools. the policy is the same policy; only its address changed.")
```

**Line by line:**

- `TOOLS` is Sutra's actual expected tool surface, not a round number. Eleven is what a support agent
  needs, and the count is what makes the multiplication concrete.
- `POLICY_LINES = 14` is measured, not guessed: it is the body of the `on_tool_error_callback` built
  across [3.1](../03-policy/3.1-which-429-is-it.md) to
  [3.3](../03-policy/3.3-giving-up-honestly.md) — a classification, a retry check, a marked substitute
  and a public message.
- `"tools that can silently opt out"` is the row that matters and the phrasing is deliberate.
  **Silently.** A tool that catches its own errors does not announce it; nothing in the type signature
  changes and no test fails ([4.1](../04-failure-lab/4.1-the-swallowed-exception.md) measured the
  hook count going to zero).
- `"new tools that get it for free"` is the same fact from the other end: with a plugin, tool twelve
  is covered before it is written. That is the property that survives staff turnover.
- Both functions return a **dict with identical keys**, so the printing loop is a mechanical
  side-by-side rather than two hand-written columns that could disagree.
- `width = max(len(k) for k in left)` sizes the label column from the data, so adding a row does not
  require re-aligning the format string.

**Line by line:**

- Pure arithmetic over a list of names. No ADK, no key, no quota.

Measured on 2026-09-03:

```text
                                   per tool   one plugin
places the policy lives                  11            1
lines of policy in the repo             154           14
files to edit to change it               11            1
tools that can silently opt out          11            0
new tools that get it for free            0           11

11 tools. the policy is the same policy; only its address changed.
```

**154 lines against 14** is the row everybody quotes and the least important one. Line count is a
proxy, and a weak one — eleven copies of a good fourteen-line policy would be a perfectly functional
system if they stayed identical.

**"files to edit to change it": 11 against 1** is the row that describes maintenance. When
[3.1](../03-policy/3.1-which-429-is-it.md)'s classifier needs updating because a provider renamed a
quota metric, that is one edit or eleven — and eleven means ten correct edits and one that gets
missed.

**And the last two rows are the argument.** Eleven tools that can silently opt out, against zero.
Zero new tools inheriting the policy, against eleven. Those rows are not about today's code; they are
about the tool somebody adds in Phase 7 without reading this day. With the policy in a plugin, that
tool is covered because there is only one way to plumb it.

## When it breaks

The plugin placement has a real failure mode, and it is the one from
[4.2](../04-failure-lab/4.2-the-handler-that-became-the-error.md), stated as a cost rather than a bug:

```text
RuntimeError: Error in plugin 'policy' during 'after_tool_callback' callback:
'str' object has no attribute 'get'
```

**Centralising policy centralises its defects.** Eleven copies of a policy have eleven independent
bugs affecting one tool each. One copy has one bug affecting everything. That is a better trade —
one bug is findable and eleven divergent ones are not — but it is a trade, and it is why
[4.2](../04-failure-lab/4.2-the-handler-that-became-the-error.md) argues for the error path being the
most defensive code in the repo.

The second failure has no error text: the plugin that is never installed. `Runner(agent=agent, ...)`
instead of `Runner(app=app, ...)` produces a working runner with no plugins, and
[2.1](../02-four-hooks/2.1-the-runtime-owns-the-error.md) already noted that nothing warns. With
per-tool policy this failure cannot happen. With plugin policy it is a single argument, and the
defence is a test that asserts the hooks fire — which is
[5.2](5.2-testing-the-failure-path.md).

## In production

**Let tools raise *specific* exceptions and classify on the type.** This is how you keep the tool's
knowledge without moving policy back into it. `raise ArticleDeleted(article_id)` from the tool, and
`isinstance(error, ArticleDeleted)` in the plugin, is better than either a generic `TimeoutError` the
plugin has to guess about or a full policy in the tool. The tool contributes what only it knows; the
plugin decides what to do about it.

**What changes at scale** is that one policy stops being enough — and the answer is still not
per-tool. It is more than one *plugin*, or one plugin with per-tool rules keyed on `tool.name`, which
the hook signature supports because it is handed the `tool` object. A read-only knowledge-base lookup
and a `close_ticket` that writes to a customer's record should not be substituted with the same
enthusiasm, and that distinction lives in a table in one file rather than in eleven implementations.

**The failure that only appears with real traffic** is the tool that raises something the plugin has
never seen. The policy has branches for timeouts and rate limits, a new dependency raises a library
exception nobody anticipated, and the `else` branch — whatever it is — now governs a failure mode it
was not designed for. A plugin should log the exception type it could not classify, as a metric, so an
unrecognised failure is a signal rather than a default.

**The review comment a senior engineer leaves:** *"three of our tools handle their own errors and eight
don't. Pick one — and it should be the plugin, because the next tool somebody writes will follow
whichever pattern they happen to copy."*

**The interview question:** *"where do you put error handling in an agent?"* The answer that shows you
have maintained both: *"in one place, at the layer that has the policy — a plugin on the App, not in
each tool. The tools' job is to raise something specific; the plugin's job is to classify and decide.
Per-tool handling means every new tool can silently opt out of retries, logging and tracing, and it
will, because the one written on a bad afternoon is the one with a try/except in it."*
