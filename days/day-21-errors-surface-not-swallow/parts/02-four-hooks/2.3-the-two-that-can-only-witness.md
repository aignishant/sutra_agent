# 2.3 — The two hooks that can only witness

## One-line answer

`on_agent_error_callback` and `on_run_error_callback` are declared `-> None` and mean it: the
exception is re-raised after every plugin has been told, and a hook that returns something anyway is
ignored — measured, not assumed.

## The story

The signalman at the level crossing has one job and it is not stopping the train.

He sees the barrier fail, and he logs it, and he phones control, and he flags the road. The train
comes through on schedule because the train was never his to stop — by the time he can see it, the
decision to send it was taken twenty minutes ago at a box he has no line to.

Everybody understands this about him, and nobody thinks his job is pointless. What control does with
his call is the whole reason the call exists.

## The idea in plain language

The other two error hooks return `None`, and ADK's docstrings say what that means in unusually direct
language. From `google/adk/plugins/base_plugin.py` in the installed 2.7.1:

> *"This is a notification-only callback. The exception is always re-raised after all registered
> plugins have been notified. Plugins should NOT suppress the exception."*

That sentence appears verbatim on both `on_agent_error_callback` and `on_run_error_callback`. Three
things follow from it.

**They cannot rescue.** There is no return value that changes the outcome. Not `None`, not a dict, not
an `LlmResponse`. The exception is going to be re-raised.

**They are still called.** Every registered plugin is notified before the re-raise, so this is a
reliable place to hang the things you want to happen on *every* failure that escapes: a log line with
fields, a metric, an alert, a note written into session state.

**And the level tells you something the tool hook cannot.** `on_agent_error_callback` receives the
`agent` — so in a multi-agent system it names which one failed. `on_run_error_callback` receives the
`invocation_context` — the whole invocation, including the session and user ids, which is what an
operator needs to find the conversation afterwards.

The asymmetry with [2.2](2.2-the-two-that-can-rescue.md) is worth stating plainly, because it is a
design decision rather than an oversight:

| Level | Can it rescue? | Why that is the right call |
| --- | --- | --- |
| tool | yes | one call failed; the run has an obvious way to continue without it |
| model | yes | one call failed; a substitute response is a coherent thing to produce |
| agent | **no** | the agent's own control flow is already broken; there is nothing coherent to return |
| run | **no** | the invocation is over; there is nobody left to hand a value to |

By the time an exception has escaped the agent, the flow that would have consumed a substitute no
longer exists. Allowing a rescue there would mean inventing a state for the run to resume into, and
that state would be fiction.

## Why Sutra needs it

Because the run-level hook is where Sutra's honesty becomes *observable*, and everything after this
phase depends on it.

Day 22 builds structured logging. The natural instinct is to log inside each tool, which produces
eleven inconsistent formats and misses every failure that happens outside a tool. The run-level hook
is one place, fires for every escaped exception, and has the invocation context — which is why
tomorrow's logger hangs off it rather than off `try`/`except`.

Day 84's tracing does the same thing with spans, and Day 79's evals need to distinguish *"Sutra
answered wrongly"* from *"Sutra failed and said so"* — a distinction that only exists if failures are
recorded somewhere structured when they escape.

## The mechanism

The plugin from [2.1](2.1-the-runtime-owns-the-error.md), with `on_agent_error_callback` deliberately
trying to do the thing the docstring forbids.

```python
# days/day-21-errors-surface-not-swallow/lab/rescue.py

    async def on_agent_error_callback(
        self, *, agent: Any, callback_context: Any, error: Exception
    ) -> None:
        HEARD.append(f"on_agent_error_callback  {type(error).__name__}")
        # Notification only. Returning anything at all cannot stop the exception.
        return {"status": "i tried to suppress this"}  # noqa: RET500 - deliberately wrong

    async def on_run_error_callback(self, *, invocation_context: Any, error: Exception) -> None:
        HEARD.append(f"on_run_error_callback    {type(error).__name__}")
```

**Line by line:**

- The declared return type is `-> None` and the body returns a dict. That is a **deliberate lie in the
  type annotation**, written to test whether the annotation is documentation or enforcement. It is
  documentation; Python does not check it and neither does ADK.
- `# noqa: RET500` suppresses the lint rule that would otherwise flag returning a value from a
  function annotated `None`. The comment says why, which is the repo's rule for every `noqa`.
- Returning `{"status": "i tried to suppress this"}` is the most optimistic possible attempt at a
  rescue: a dict, exactly the shape that works one level down in
  [2.2](2.2-the-two-that-can-rescue.md). If anything were going to be honoured, it would be this.
- `on_run_error_callback` takes `invocation_context` rather than an agent or a tool, because at this
  level there is no single tool or agent to name — the whole invocation failed.
- Neither hook receives anything it could use to resume. There is no `tool_context` to write a result
  into and no `llm_request` to answer. The signatures themselves say these hooks are terminal.

```bash
cd days/day-21-errors-surface-not-swallow/lab
RESCUE=0 uv run python rescue.py
```

**Line by line:**

- `RESCUE=0` so the tool hook declines to rescue and the exception reaches the two witness hooks.
- Recording models throughout: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
RESCUE=0
    on_tool_error_callback   TimeoutError
    on_agent_error_callback  TimeoutError
    on_run_error_callback    TimeoutError
  the run raised: TimeoutError: kb.internal:8080 timed out after 5s
  the user was told: None
```

**The agent hook returned a dict and the run still raised.** That is the measurement. The docstring
says the exception is always re-raised; this is the run that checks rather than trusting, and the
answer is that the docstring is accurate. `the run raised: TimeoutError` — same type, same message,
unchanged by the attempted suppression.

**Both witness hooks fired before it.** They are not a fallback for when the earlier hooks decline;
they are notifications that happen on the way out, in order, every time. Anything you need to happen
on every escaped failure belongs in one of them.

**And `the user was told: None` is the honest consequence.** Nothing rescued, so nothing was produced.
The whole invocation failed, loudly, which is exactly what
[1.3](../01-who-hears-it/1.3-retry-substitute-escalate.md) calls *escalate* — and the reason the
witness hooks matter is that escalation without a record is just a crash.

## When it breaks

The failure here is not an exception; it is a design mistake with a very quiet symptom.

🎬 **The scene:** you add `on_run_error_callback` to your plugin, and inside it you build a friendly
message for the user and return it.
😬 **The naive fix:** when the user still sees nothing, you assume the hook did not fire, so you add a
`print` — and the `print` appears. The hook definitely fired.
💥 **Why it fails:** the hook fired, ran your code, ignored your return value, and re-raised. The
exception was never yours to stop at that level. Everything you observed was true and your conclusion
was wrong, which is what makes this one expensive.
💡 **The insight:** read the return type. `-> None` in these two signatures is not laziness about
annotations — it is the contract, and ADK's docstring states it in a sentence that begins *"This is a
notification-only callback."*

There is also a real exception available here, and it is the one from
[2.2](2.2-the-two-that-can-rescue.md)'s *When it breaks*: if your witness hook itself raises, ADK wraps
it and the wrapped error replaces the original:

```text
RuntimeError: Error in plugin 'policy' during 'after_tool_callback' callback:
'str' object has no attribute 'get'
```

A logging call that assumes a field exists is the usual culprit. These two hooks run at the worst
moment in the system's life and they must not be the second thing to fail.

## In production

**Put the log line here and nowhere else.** One `on_run_error_callback` that emits a structured record
— invocation id, user id, agent, exception type, message — is worth more than logging scattered
through tools, because it fires for failures that never touched a tool at all. That is Day 22's whole
design, and it starts as four lines in this hook.

**What changes at scale** is that `on_agent_error_callback` becomes the useful one. With a single
agent it is nearly redundant with the run hook. In Phase 8's graphs, several agents run as nodes in
one invocation, and *which node failed* is the first question anybody asks; the run hook cannot answer
it and the agent hook can.

**The failure that only appears with real traffic** is the alert that fires on the wrapped error. Once
a plugin bug can replace the original exception, a monitoring rule keyed on exception type reports
your handler's `AttributeError` and never mentions the dependency outage that triggered it. Alert on
the *presence* of run-level errors first, and on their type second.

**The review comment a senior engineer leaves:** *"this builds a fallback message in
`on_run_error_callback` and returns it. That hook is notification-only — the return value is dropped
and the exception is re-raised. If we want a graceful answer, it has to happen in the tool or model
hook, before it gets this far."*

**The interview question:** *"can you recover from any error in ADK's plugin hooks?"* The answer that
shows you have read the contract: *"only two of the four. The tool and model hooks return a value that
replaces the failed call. The agent and run hooks are notification-only — the docstring says the
exception is always re-raised, and I checked: returning a dict from the agent hook changes nothing.
Those two are for logging, metrics and alerting, which is exactly what you want at that level."*
