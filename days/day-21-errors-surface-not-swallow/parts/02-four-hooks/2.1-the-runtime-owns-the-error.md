# 2.1 — Trap #4 — the runtime owns the error

## One-line answer

In ADK 2.x a tool that raises does not crash your agent by accident — the exception is routed through
the runtime, where **three plugin hooks are offered it in order** before it finally escapes, and
that routing is the thing the 1.x `try`/`except` habit destroys.

## The story

The fire alarm in the office block is not a bell in your room.

When the sensor on the third floor trips, it does not simply make a noise where it is. The signal
goes to a panel in reception, and the panel decides: sound the whole building, sound one floor, or
hold for thirty seconds because this sensor is next to the toaster and has form. The panel also rings
the monitoring company, whatever it decides.

Somebody who dislikes the noise can disconnect the sounder in their own room. The sensor still trips,
the panel still hears it, reception still knows. What they have removed is the noise, not the alarm.

The reverse — a sensor wired to a local bell and to nothing else — looks identical on a quiet day and
is a different building entirely.

## The idea in plain language

This is **trap #4** of the four 1.x → 2.x traps in the master plan's §5.1, and it is worth quoting
what it says, because the wording is precise:

> **Don't swallow exceptions.** 1.x habit: tool/model errors caught and returned as strings, hiding
> failures. 2.x reality: exceptions are surfaced through the runtime so callbacks/plugins can act on
> them.

The mechanism behind that sentence is the part worth learning. When a tool raises inside an ADK 2.x
run, the exception does not travel straight up the Python stack to your `try`. It is intercepted, and
the runtime offers it to plugins at three levels on the way out:

1. **the tool level** — *this specific tool call failed*
2. **the agent level** — *an exception escaped this agent*
3. **the run level** — *an exception escaped the whole invocation*

Only then does it reach your code. Each level is a plugin callback
([Day 14](../../../day-14-plugins-one-layer-up/LESSON.md) built the plugin object; today it grows its
error half), and each is a place where policy can live. That is what "the runtime owns the error"
means: the *path* an exception takes is a framework feature, and it exists so that
[1.3](../01-who-hears-it/1.3-retry-substitute-escalate.md)'s three responses have somewhere to be
written down once.

A tool that catches its own exception opts out of all of it. Not partially — completely. There is no
tool-level hook, no agent-level hook, no run-level hook, because from the runtime's point of view
nothing went wrong: a function was called and it returned a dictionary.

> **Verified against `https://adk.dev/plugins/` on 2026-09-03**, and cross-read against the installed
> `google-adk` 2.7.1 source (`google/adk/plugins/base_plugin.py`, `google/adk/runners.py`). The hook
> names, their keyword-only signatures and their return contracts in this section are the ones that
> package enforces.

## Why Sutra needs it

Because Sutra already has a plugin, and it is currently deaf to the only events that matter.

`sutra/plugins.py` from [Day 14](../../../day-14-plugins-one-layer-up/LESSON.md) wraps every run with
cross-cutting behaviour — the thing you write once instead of remembering in eleven places. Today it
gains the error hooks, and the reason that is the right home rather than a `try` in each tool is
exactly Day 14's argument: **a rule nobody has to remember is a rule that holds.**

It also decides how the rest of the phase behaves. Day 22's structured logging hangs off these hooks —
a log line per failure, with fields, emitted from one place. Day 23 tests tools in isolation and needs
to know what a failing tool is *supposed* to do. Day 64's approval gate is an escalation that resumes,
and it can only be built on a runtime that routes errors rather than one where tools handle their own.

## The mechanism

A tool that raises, a plugin that records every hook it is offered and suppresses nothing, and a run
that is allowed to fail.

```python
# days/day-21-errors-surface-not-swallow/lab/rescue.py  (the RESCUE=0 arm)
"""Two hooks can hand back a result and stop the exception. Two can only watch it go past."""

RESCUE = os.environ.get("RESCUE", "1") == "1"


def lookup_article(article_id: str) -> dict[str, Any]:
    """Fetch a knowledge-base article. The knowledge base is down."""
    raise TimeoutError("kb.internal:8080 timed out after 5s")


class Policy(BasePlugin):
    """The error policy, in one place, instead of in every tool."""

    async def on_tool_error_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, error: Exception
    ) -> dict[str, Any] | None:
        HEARD.append(f"on_tool_error_callback   {type(error).__name__}")
        if not RESCUE:
            return None
        return {
            "status": "unavailable",
            "tool": tool.name,
            "reason": f"{type(error).__name__}: {error}",
            "instruction": "Tell the user the knowledge base is unreachable. Do not guess.",
        }

    async def on_agent_error_callback(
        self, *, agent: Any, callback_context: Any, error: Exception
    ) -> None:
        HEARD.append(f"on_agent_error_callback  {type(error).__name__}")
        return {"status": "i tried to suppress this"}  # noqa: RET500 - deliberately wrong

    async def on_run_error_callback(self, *, invocation_context: Any, error: Exception) -> None:
        HEARD.append(f"on_run_error_callback    {type(error).__name__}")


app = App(name="sutra", root_agent=agent, plugins=[Policy(name="policy")])
```

**Line by line:**

- `raise TimeoutError(...)` in the tool, with **no `try` anywhere in it**. This is the entire 2.x
  contract for a tool: do the work, and if it cannot be done, raise. A tool is not the place error
  policy lives.
- `class Policy(BasePlugin)` — the plugin from [Day 14](../../../day-14-plugins-one-layer-up/LESSON.md),
  now overriding error hooks instead of lifecycle ones.
- `Policy(name="policy")` — `BasePlugin.__init__` takes a **required** `name`. Omitting it fails at
  construction with `TypeError: BasePlugin.__init__() missing 1 required positional argument: 'name'`,
  which is worth knowing because the examples in circulation often show a bare `Policy()`.
- Every hook is `async def` and its parameters are **keyword-only** — note the bare `*` in each
  signature. The runtime calls them by keyword, so the parameter *names* are the contract: rename
  `tool_args` to `args` and the hook is never callable, and you find out three layers down at the
  moment something else has already gone wrong.
- `error: Exception` is the **live exception object**, not a string. `type(error).__name__` and
  `isinstance` both work, which is what makes [1.2](../01-who-hears-it/1.2-an-error-is-a-fact.md)'s
  classification possible at this layer.
- `return None` from `on_tool_error_callback` is the documented way to say *"I have seen this, do not
  stop"*. It is the difference between a plugin that observes and a plugin that intervenes, and
  [2.2](2.2-the-two-that-can-rescue.md) takes the other branch.
- `plugins=[Policy(name="policy")]` on the **`App`**, not the `Runner`. Both are accepted;
  [14.1.2](../../../day-14-plugins-one-layer-up/parts/01-where-a-plugin-lives/1.2-the-app-is-what-plugins-belong-to.md)
  established that the `Runner(plugins=...)` form is deprecated.


**Line by line:**

- `RESCUE=0` turns off the intervention so this run shows the pure routing.
- Recording models throughout: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
RESCUE=0
    on_tool_error_callback   TimeoutError
    on_agent_error_callback  TimeoutError
    on_run_error_callback    TimeoutError
  the run raised: TimeoutError: kb.internal:8080 timed out after 5s
  the user was told: None
```

**Three hooks, one exception, in order.** Tool, then agent, then run. Nobody wired that ordering; it
is the runtime walking the exception outwards through the levels of the system, offering it at each
one. This is the routing that trap #4 is about, and it is invisible until you put a recorder on it.

**And then it still raised.** That is the correct ending. No plugin chose to intervene, so the
exception completed its journey and reached the caller unchanged — same type, same message. ADK did
not absorb it, log it and return `None`; it offered it around and then let it out.

**`the user was told: None`** is the cost, and it is the honest cost. The invocation produced no
answer at all. That is *escalate* from
[1.3](../01-who-hears-it/1.3-retry-substitute-escalate.md), and for a bug in your own code it is
exactly right. For a knowledge base being briefly unreachable it is heavy-handed, which is why the
next part exists.

## When it breaks

**Get a parameter name wrong and it fails at the worst possible moment.** The runtime calls these
hooks by keyword, so the names are the contract. Renaming `tool_args` to `args` — which reads better,
and is the sort of tidy-up that passes review — produces this, observed on 2026-09-03:

```text
TypeError: Policy.on_tool_error_callback() got an unexpected keyword argument 'tool_args'
```

Nothing complains at import. It arrives *while handling another exception*, which is why it reads so
badly in a log: the traceback is about your error handler, and the failure that triggered it is
further down the chain. Copy the signatures from `base_plugin.py` rather than retyping them.

**And the plugin needs a name:**

```text
TypeError: BasePlugin.__init__() missing 1 required positional argument: 'name'
```

Loud, at construction, before anything runs. The good kind.

**The failure with no error text at all** is the one this whole part is about: a tool that catches its
own exception. Nothing in the output above appears — not one of the three lines — and the run reports
success. [4.1](../04-failure-lab/4.1-the-swallowed-exception.md) measures exactly that, and the
measurement is that the hook count goes from three to zero.

## In production

**One plugin, installed on the `App`, is the whole error surface.** The alternative — policy in each
tool — has a failure mode that is not about correctness: it is that the eleventh tool, written in a
hurry six months later by somebody who did not read the other ten, does it differently. A plugin is
the only version of this rule that new code obeys by default.

**What changes at scale** is that the three levels stop being redundant. In a one-agent system a tool
failure and a run failure are nearly the same event. In Phase 8's graphs, where several agents run as
nodes inside one invocation, they are not: one node's tool can fail and be substituted while the
invocation continues, and the agent-level hook is the only place that sees *which* agent it was. The
ladder is built for the system you are going to have.

**The failure that only appears with real traffic** is a hook that itself raises. An error handler
that throws while handling an error produces a chained exception where the original cause is the
second one listed, and monitoring that keys on exception type will report your logging bug rather than
the outage. Error hooks deserve to be the most boring, most defensive code in the repo.

**The review comment a senior engineer leaves:** *"this tool has a `try/except` around the HTTP call
that returns a dict on failure. Delete it — the plugin handles this, and right now this call is
invisible to the retry policy and to the trace."*

**The interview question:** *"what's the fourth ADK 1.x-to-2.x trap and why does it matter?"* The
answer that shows you have measured it: *"don't swallow exceptions. In 2.x a raised error is routed
through plugin hooks at the tool, agent and run levels before it escapes, so retry, substitution and
alerting all live in one place. A tool that catches its own exception opts out of all three — we
measured three hooks firing when it raises and zero when it doesn't."*
