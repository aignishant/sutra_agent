# 2.2 — The two hooks that can rescue

## One-line answer

`on_tool_error_callback` returning a `dict`, and `on_model_error_callback` returning an
`LlmResponse`, both **stop the exception** and hand that value onward as if the call had succeeded —
which is the *substitute* from [1.3](../01-who-hears-it/1.3-retry-substitute-escalate.md), and the
only two places ADK offers it.

## The story

The chemist is out of the exact tablets.

She does not send you away, and she does not hand you a different box and hope. She looks it up, tells
you the generic version is the same drug at the same dose, writes the substitution on the bag, and
asks if that is all right. You leave with something that works and with the knowledge that it is not
what the prescription said.

The bit that makes it safe is the writing on the bag. A substitution nobody records is
indistinguishable from the original, and the next person to look at it — your doctor, in a month —
has no way to know.

## The idea in plain language

Two of ADK's four error hooks have a **return type that is not `None`**, and that is not a detail of
style. It is the framework saying: *this hook is allowed to change the outcome.*

| Hook | Returns | Returning a value means |
| --- | --- | --- |
| `on_tool_error_callback` | `dict[str, Any] | None` | the dict becomes the tool's result; the exception stops |
| `on_model_error_callback` | `LlmResponse | None` | the response becomes the model's answer; the exception stops |

Returning `None` from either means *"I have seen it, carry on failing"* — which is what
[2.1](2.1-the-runtime-owns-the-error.md) measured.

The contract has one more clause that matters more than it looks. From ADK's own documentation for
`on_tool_error_callback`: *"By returning a `dict`, this resumes the execution flow, and
`after_tool_callback` will be triggered normally."* So a rescue does not merely stop the exception —
it puts the run back on the **success path**. Everything downstream that watches for successful tool
calls now sees one. Your metrics see one. Your trace sees one.

That is the power and it is the danger, and it is why this hook and
[3.2](../03-policy/3.2-a-substitute-must-say-so.md) have to be read together. The framework will
happily let you convert a timeout into a result that is indistinguishable from a real one. The
writing on the bag is your job.

Two practical points about where each one applies.

**`on_tool_error_callback` is per tool call.** You get the `tool` object (so `tool.name` tells you
which one), the `tool_args` it was called with, and the `tool_context`. A policy can therefore be
specific: substitute for the knowledge base, never substitute for the billing API.

**`on_model_error_callback` is per model call**, and the thing it is for is the one failure Sutra
meets most: a 429. You get the `llm_request` that failed, which means you know how big the prompt was
and which model it was for — enough to decide between waiting, switching lane, and giving up.

> **Verified against `https://adk.dev/plugins/` on 2026-09-03** and against
> `google/adk/plugins/base_plugin.py` in the installed `google-adk` 2.7.1, whose docstrings state the
> return contract in both directions.

## Why Sutra needs it

Because Sutra's two most likely failures are a knowledge base that is briefly unreachable and a model
that has run out of daily quota, and neither of them should end a conversation.

Escalating a knowledge-base timeout means the engineer typing into Sutra gets nothing at all when
Sutra could have said *"I cannot reach the knowledge base — here is what I know from the ticket
itself."* That answer is worth having, and it needs a tool result to exist in order to be produced.

The model hook is what makes
[Day 20](../../../day-20-context-engineering-compaction/LESSON.md)'s quota arithmetic survivable, and
Day 24's budget work buildable on top of it. When the twentieth request of the day fails, the
difference between Sutra stopping dead and Sutra saying *"I am out of quota until tomorrow"* is one
hook returning one `LlmResponse`.

## The mechanism

The same file as [2.1](2.1-the-runtime-owns-the-error.md), with the rescue branch taken.

```python
# days/day-21-errors-surface-not-swallow/lab/rescue.py  (the RESCUE=1 arm)

    async def on_tool_error_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, error: Exception
    ) -> dict[str, Any] | None:
        HEARD.append(f"on_tool_error_callback   {type(error).__name__}")
        if not RESCUE:
            return None
        # A substitute result, marked as one. Never a fabricated answer.
        return {
            "status": "unavailable",
            "tool": tool.name,
            "reason": f"{type(error).__name__}: {error}",
            "instruction": "Tell the user the knowledge base is unreachable. Do not guess.",
        }

    async def after_tool_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, result: dict[str, Any]
    ) -> dict[str, Any] | None:
        HEARD.append(f"after_tool_callback      result={result.get('status', result)}")
        return None
```

**Line by line:**

- `return {...}` is the rescue. One `return`, and the `TimeoutError` that
  [2.1](2.1-the-runtime-owns-the-error.md) watched travel through three hooks never leaves the first
  one.
- `"status": "unavailable"` is the writing on the bag, and it is first in the dict for the same reason
  it is first in this list: it is the field the model reads, and
  [1.2](../01-who-hears-it/1.2-an-error-is-a-fact.md) argued for a small closed vocabulary there.
- `"tool": tool.name` uses the `tool` object the hook is handed. This is why the hook takes the tool
  rather than just the error: a policy that cannot tell which tool failed cannot have per-tool rules.
- `"reason": f"{type(error).__name__}: {error}"` keeps the original message. The rescue changes what
  the *caller* sees; it must not destroy what happened.
- `"instruction": "...Do not guess."` is unusual and deliberate. The dict goes into the model's
  context as a tool result, so it can carry a directive as well as data — and *"do not guess"* is the
  cheapest available defence against a model smoothing over the gap.
- `after_tool_callback` is included **to prove the documented claim**: a rescued call is back on the
  success path, so the normal after-hook fires. If it did not fire, the rescue would be a special case
  rather than a resumption, and everything downstream would need to know about it.
- `result.get("status", result)` prints the marker if there is one and the whole dict if there is not,
  which is a compact way of showing whether the writing on the bag survived.

```bash
cd days/day-21-errors-surface-not-swallow/lab
RESCUE=1 uv run python rescue.py
```

**Line by line:**

- `RESCUE=1` is the default; it is written out so the two arms can be run back to back.
- Recording models throughout: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
RESCUE=1
    on_tool_error_callback   TimeoutError
    after_tool_callback      result=unavailable
  the run raised: None
  the user was told: "The tool said: {'status': 'unavailable', 'tool': 'lookup_article', 'reason': 'TimeoutError: kb.internal:8080 timed out after 5s', 'instruction': 'Tell the user the knowledge base is unreachable. Do not guess.'}"
```

Compare it line for line with [2.1's output](2.1-the-runtime-owns-the-error.md) and three things
changed from one `return`.

**The ladder stopped at the first rung.** `on_tool_error_callback` fired and `on_agent_error_callback`
and `on_run_error_callback` did not, because there was no longer an exception for them to be offered.
Rescuing early means the outer levels never learn anything, which is a real cost —
[5.1](../05-in-production/5.1-one-policy-not-a-hundred.md) is about paying it deliberately.

**`after_tool_callback` fired**, exactly as the documentation says. The run is genuinely back on the
success path; nothing downstream can tell from the control flow that anything went wrong. Only the
*content* of the result says so, which is the entire argument for marking it.

**And the run did not raise.** `the run raised: None`, and the user got a sentence. That is the
difference between an outage that ends a conversation and one that degrades it.

Now the model-side version, which is the same contract with a different payload type:

```python
# days/day-21-errors-surface-not-swallow/lab/model_error.py

    async def on_model_error_callback(
        self, *, callback_context: Any, llm_request: LlmRequest, error: Exception
    ) -> LlmResponse | None:
        retryable = "429" in str(error)
        LOG.append(f"on_model_error_callback  retryable={retryable}")
        if POLICY == "propagate" or not retryable:
            return None
        return LlmResponse(
            content=types.Content(
                role="model",
                parts=[
                    types.Part(
                        text="I could not reach the model (quota exhausted). Nothing was answered."
                    )
                ],
            )
        )
```

**Line by line:**

- The return type is `LlmResponse | None`, not a dict, because what failed was a model call and
  what the run needs is a model response. The shape of the rescue always matches the shape of the hole.
- `"429" in str(error)` is the classification, and it is deliberately the *naive* version here so that
  [3.1](../03-policy/3.1-which-429-is-it.md) can show why it is not enough. A 429 is not one thing.
- `if POLICY == "propagate" or not retryable: return None` — two independent reasons to decline the
  rescue, and both end at the same `None`. A hook is allowed to be selective; it does not have to
  rescue everything or nothing.
- The substituted text **says what happened**. It does not apologise vaguely; it names quota
  exhaustion, and it says *"nothing was answered"* so the model's own output cannot be mistaken for an
  answer to the user's question.
- `role="model"` because this response stands where the model's would have stood. The user-facing
  layer does not need a special case for it, which is the point.

**Line by line:**

- `FAILURES=1` makes the fake model fail once, so the first call is the interesting one.
- The model here is a local fake that raises a 429-shaped error: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
POLICY=substitute
    model call -> 429 (remaining failures: 0)
    on_model_error_callback  retryable=True
  the run raised: None
  the user was told: 'I could not reach the model (quota exhausted). Nothing was answered.'
```

The model never produced anything, and the user still got a true sentence. That is the shape every
quota-limited system eventually needs, and it is one hook.

## When it breaks

**Return the wrong type and it does not rescue — it fails differently, and later.** Returning a
string rather than a dict is the natural mistake for anyone coming from the 1.x habit. Replacing the
dict above with `return f"Error: {error}"` gives this, observed on 2026-09-03:

```text
    on_tool_error_callback   TimeoutError
    on_agent_error_callback  RuntimeError
    on_run_error_callback    RuntimeError
  the run raised: RuntimeError: Error in plugin 'policy' during 'after_tool_callback' callback:
  'str' object has no attribute 'get'
```

Three things in that are worth having seen. The rescue **worked** — the `TimeoutError` stopped at the
first hook. What then failed was the *next* hook along, `after_tool_callback`, which called `.get()`
on what it assumed was a dict. ADK wrapped that in a `RuntimeError` naming both the plugin and the
callback, which is a genuinely good error message. And the original `TimeoutError` is gone from the
ladder entirely: the agent and run hooks are now being told about a bug in the error handler, not
about the outage that started it.

That is the concrete version of the warning in
[2.1's *In production*](2.1-the-runtime-owns-the-error.md): a hook that raises while handling an error
replaces the real failure with its own.

**And the rescue that rescues too much.** A hook that returns a dict for *every* exception — including
a `KeyError` from a bug in your own tool — has converted your bugs into tool results. The run
succeeds, the model says something plausible, and your exception tracker records nothing. This is
trap #4 rebuilt one layer up, and it is more dangerous there because it is centralised: one careless
`return {...}` silences every failure in the system rather than one tool's.

The defence is the classification from [1.3](../01-who-hears-it/1.3-retry-substitute-escalate.md):
rescue what you have a policy for and return `None` for everything else. A hook that never returns
`None` is not a policy.

## In production

**Make the substitute's shape a constant, not a literal.** One dict, defined once, with a function
that fills in `reason` and `tool`. Two dozen inline literals across a plugin drift, and the day one of
them is missing `status` is the day a substitution stops being marked — which is
[3.2](../03-policy/3.2-a-substitute-must-say-so.md)'s whole subject.

**What changes at scale** is that rescuing hides your dependency's health from your own monitoring.
Once tool failures are substituted, the run-level error rate goes to nearly zero and *stays* there
through an outage. The number that still moves is the count of substitutions, so that has to be
emitted deliberately — from the hook, as a metric — or you have traded an alert for a silence.

**The failure that only appears with real traffic** is the rescue that becomes load-bearing. A
dependency is flaky for a month, the substitution path is exercised constantly, and users adapt to the
degraded answer. Then somebody "fixes" the substitution to be more helpful, and it stops being
obviously degraded, and the dependency is never repaired because nothing hurts any more.

**The review comment a senior engineer leaves:** *"this returns a fallback dict for any exception.
Narrow it — check the type first, and return `None` for anything we don't have a story for. Right now
a `KeyError` in our own tool code comes back to the model as a tool result."*

**The interview question:** *"how do you let an agent keep going when a tool fails?"* The answer that
shows you have shipped it: *"the tool error hook returns a dict, which becomes the tool's result and
puts the run back on the success path — the after-hook fires normally. The important part is that the
dict has to be marked as a substitute, because from that point on nothing in the control flow can tell
it apart from a real result."*
