# 3.3 — A verdict is not an erasure

## One-line answer

Deciding that a memo should be forgotten and actually removing it are two different events, and
everything that reads the store between them still sees the memo.

## The story

A library takes a book out of circulation.

Somebody stamps **WITHDRAWN** on the inside cover and crosses it out of the catalogue. As far as the
library is concerned that book is gone: it will not come up in a search, it cannot be borrowed, and
the record says so.

The book is still on the shelf.

It is on the shelf for good reasons — the trolley comes on Thursdays, the disposal box is full, and
nobody has had a spare hour. And for a while none of that matters, because the way people find books
is the catalogue, and the catalogue does not list it.

Then somebody walks along the shelf reading spines, which is a completely normal way to use a
library. They find the book. They open it. The stamp is on the inside cover, which they do not read,
because why would you. They take it away and use what is in it.

Nobody broke a rule. The withdrawal decision was correct and correctly recorded. It simply was not
the same event as the book leaving the building, and every route into the shelves that was not the
catalogue never learned about it.

## The idea in plain language

`what_to_forget` returns verdicts. It does not delete anything.

That is a deliberate design decision and it is worth defending, because the obvious alternative —
have the policy delete as it decides — sounds simpler and is worse. A function that decides *and*
destroys cannot be run to find out what it would do. It cannot be tested without a store. It cannot
be shown to a reviewer as a dry run. And it can only be run by something with permission to write.

So the system has two halves:

- **The decision.** Pure, cheap, repeatable, based on a date you pass in. Given a store and a date,
  which memos are still the answer? This is `what_to_forget`, and it can be run a thousand times with
  no effect.
- **The sweep.** The thing that actually rewrites the store, removing what the decision condemned. It
  runs on a schedule, it needs write access, and it is the only part that changes anything.

Between those two events there is a window, and the whole of this part is about what lives in it.

During that window a memo is in a strange state: **condemned but present.** Retrieval that goes
through the policy will not return it. Anything that reads the store *without* going through the
policy will. And the list of things that read a store without going through your retrieval path is
longer than it first appears — a backup, a replica, an analytics export, a debugging script, a
support tool, a database console, and the next engineer who writes a query.

The rule that comes out of this is short: **the verdict is a filter, not a deletion, and every path
to the data must apply the filter or the data must be gone.** Any path that does neither is a route
along the shelves.

## Why Sutra needs it

Because section 4 is about obligations, and an obligation is discharged by bytes moving, not by a
function returning a string.

When a customer asks to be forgotten, the honest answer is not *"our retrieval no longer returns your
data"*. It is *"your data is gone"*. Those are different claims and only one of them is what was
asked for. [4.3](../04-privacy-and-erasure/4.3-erasure-is-an-obligation.md) is where that becomes an
obligation rather than a preference, and this part is the mechanism it needs to exist first.

It matters for expiry too, and less obviously. A quote that expired thirty days ago is not a privacy
problem — but it is still sitting in the store, still being backed up nightly, still being counted in
whatever you measure the store's size with, and still being embedded by Day 49's index if that index
reads the store directly rather than through the policy.

## The mechanism

The proof is a file. The script writes a real store to disk, asks the policy what should be
forgotten, and then greps the file for the text the policy just condemned.

```python
# days/day-48-memory-design/lab/sweep.py
def write(memos: list[Memo]) -> None:
    """Persist the store the way Day 47's database-backed sessions persist theirs: as rows."""
    rows = [{**asdict(m), "recorded_on": m.recorded_on.isoformat()} for m in memos]
    for row, memo in zip(rows, memos, strict=True):
        row["expires_on"] = memo.expires_on.isoformat() if memo.expires_on else None
    STORE.write_text(json.dumps(rows, indent=2), encoding="utf-8")
```

**Line by line:**

- `asdict(m)` turns each frozen dataclass into a plain dictionary. It is used rather than hand-writing
  the fields so that adding a column to `Memo` cannot silently stop being persisted.
- The dates are converted to ISO strings explicitly, because `json.dumps` raises
  `TypeError: Object of type date is not JSON serializable` on a `date`. Handling it here rather than
  with a `default=str` argument means the format is the one chosen rather than whatever `str()`
  happens to produce.
- `zip(rows, memos, strict=True)` — the `strict` flag raises if the two lists ever differ in length.
  They cannot today, and it is one word that turns a future silent misalignment into an exception.
- `encoding="utf-8"` on every write, explicitly. On Windows the default encoding is not UTF-8, and a
  memo containing a customer's name in a non-Latin script would be written in one encoding and read in
  another.
- The store is JSON on disk rather than the SQLite database Day 47 uses, because the point being made
  is about bytes persisting and a file you can open in an editor makes that visible. The behaviour is
  identical; the database version simply hides it better.

The comparison itself is three lines:

```python
verdicts = what_to_forget(kept, today=LATER)
if do_sweep:
    write([v.memo for v in verdicts if v.action == "keep"])
on_disk = STORE.read_text(encoding="utf-8")
```

**Line by line:**

- `what_to_forget` is called in **both** arms. The decision is identical either way — that is the
  point. Only the second line differs.
- The sweep rewrites the file with the survivors, which is the simplest possible implementation and
  exactly what a small system does: read all, filter, write all. It is also why the production section
  below talks about what happens when the store no longer fits in memory.
- `STORE.read_text(...)` afterwards reads the file back from disk rather than trusting a variable, so
  the printed answer is about the bytes rather than about the program's belief.
- The needle searched for is `"4800"` — the number from the expired quote. Searching for a
  distinctive substring rather than checking a length makes the result unarguable.

```bash
cd days/day-48-memory-design/lab
uv run python sweep.py
uv run python sweep.py --sweep
cd -
```

**Line by line:**

- The bare run decides and stops, which is what a system with no sweep job does — and a system with no
  sweep job is the default, because nobody writes one until something forces them to.
- `--sweep` adds the second half. The ablation is not "does the policy work" but "did anyone carry
  out the sentence".

Measured on 2026-09-05:

```text
asked on 2026-12-01: 2 memo(s) are no longer live
  superseded Billing email is [REDACTED-EMAIL]
  expired    Business plan is 4800 a year.

swept: False
bytes on disk: 1302
"4800" still present in memory_store.json: True
The policy said forget. The bytes did not move. Retrieval reads the bytes.
```

```text
asked on 2026-12-01: 2 memo(s) are no longer live
  superseded Billing email is [REDACTED-EMAIL]
  expired    Business plan is 4800 a year.

swept: True
bytes on disk: 828
"4800" still present in memory_store.json: False
```

The first four lines of both runs are **identical**. Same verdicts, same reasons, same two memos
condemned. The policy did its job perfectly in both arms.

1302 bytes against 828, and a substring that is there or is not. That is the entire difference between
a decision and an erasure, and it is invisible from anywhere inside the policy.

## When it breaks

The break has no error message, and the way it surfaces is a query written by somebody who did not
know the policy existed.

```python
# a perfectly reasonable analytics query, written six months later
rows = json.loads(STORE.read_text())
prices = [r["text"] for r in rows if "a year" in r["text"]]
```

That code is not wrong. It reads the store, which is where the data is. It has simply walked along the
shelves, and it will return the expired quote alongside the live ones, and the person who wrote it has
no reason to suspect that some rows in the file are not supposed to count.

The second break is the sweep that runs and does not finish. A partially-applied deletion leaves the
store in a state where some condemned memos are gone and some are not, and — because the decision is
recomputed from scratch next time — nothing anywhere records that a sweep was interrupted. The next
run simply condemns them again. That is benign for expiry and it is **not** benign for erasure, where
somebody was told their data was deleted.

The third break is the one that looks like tidiness. Somebody notices the two-phase design and
"simplifies" it:

```python
def what_to_forget(memos, *, today, store):
    """Decide and delete in one pass."""
```

Now the function cannot be run as a dry run, cannot be tested without a store, and cannot be shown to
a reviewer without write permission. Every one of the four dates in
[3.1](3.1-true-on-the-day-it-was-said.md)'s output would have destroyed the store it was asking about.

## In production

**What a professional writes instead:** the same split, with the sweep as a scheduled job that is
**idempotent and resumable**, and that writes a line per deletion to an audit log — memo id, holder,
kind, reason, timestamp. Not the text. The audit log is how you answer "was this actually deleted?"
without reading the store, which is exactly the question the store cannot be trusted to answer about
itself.

The other production reality is **soft delete first**. Real systems mark a row deleted, wait, and then
remove it, because an erasure caused by a bug is otherwise unrecoverable. That is a genuine tension
with section 4: a soft delete is not a deletion, and a customer who asked to be forgotten is entitled
to know that the row still exists for thirty days. The resolution is that the waiting period is
written into the policy as a number with a `why`, not left as an implementation detail.

**What degrades at scale:** read-all-filter-write-all stops working. At a million memos the sweep
becomes a batched delete over an index on `expires_on`, running in chunks, and it will lag — which
means the window between decision and erasure is no longer milliseconds but hours. Everything in this
part gets *more* true as the store grows, not less. Under concurrency the sweep also races the writer:
a memo can be superseded, condemned, and then have its winner deleted by an erasure request before the
sweep reaches it, at which point the "superseded" verdict was computed against a winner that no longer
exists.

**The review comment a senior engineer leaves:** *"The policy returns verdicts and nothing deletes
anything, so today our retention policy is a suggestion. I want the sweep job in this PR or a ticket
with a date on it, and I want to know what reads this store without going through the policy — the
analytics export does, and it will be exporting expired quotes from the day this merges."*

**The interview question:** *"Your retention policy says a record should be gone. Is it gone?"* The
honest spoken answer: *"Not until something deletes it, and those are two separate events with a
window between them. I keep them separate on purpose — a function that decides and destroys in one
pass cannot be run as a dry run, cannot be tested without a store, and needs write access to answer a
question. But the consequence is that between the verdict and the sweep the record is condemned and
still present, and everything that reads the store without going through the policy still sees it:
backups, replicas, analytics exports, the debugging script somebody wrote last year. I demonstrated it
on our desk by writing the store to a file and grepping it — same verdicts in both arms, 1302 bytes
against 828, and the expired price string present in one and absent in the other. For expiry that
window is untidy. For a deletion request it is the difference between what you told the customer and
what is true."*
