# 2.1 — A rule someone else can read

## One-line answer

Write the retention rules as rows of data rather than as branches of code, because the person who
carries the risk of a bad rule is not the person who can read Python.

## The story

A school pins its fee rules on a board by the office door.

Six lines. What the term fee is. What the late fee is and after how many days it starts. Which
families it does not apply to. Who to ask for an exception. Anyone can stand there and read it — a
parent, a new teacher, the person at the desk.

The rules are not simpler than they would be in a rulebook in a drawer. They are the same rules. The
difference is that a parent can point at line four and say *"that one is unfair to families paid
monthly"*, and the conversation is about line four.

Now picture the same school where the rules live only in the head of the person at the desk. The
rules may be excellent. They may be applied perfectly consistently. But a parent who thinks one is
unfair has nothing to point at, so the conversation becomes about the clerk, and the clerk becomes
defensive, and nothing gets changed because nothing was ever proposed.

The board did not make the rules better. It made them **arguable**, and rules that can be argued
with are the only ones that get improved.

## The idea in plain language

There are two ways to write down the same policy.

**As branches.** A function full of `if` and `elif`, one per case. It works, it is testable, and it
lives in a file that only programmers open.

**As rows.** A table, one row per case, with the decision in the columns and a written reason in the
last one. Code reads the table and applies it. Nobody edits code to change a rule; they edit a row.

For most logic in a program the difference does not matter, and choosing rows would be
over-engineering. Retention is one of the places where it matters a great deal, for three reasons.

**The decisions are not technical.** How long to keep a record of what a customer was told is a
question about disputes, obligations and trust. An engineer is not the right person to answer it and
should not be the only person able to see the answer.

**The rules change without the code changing.** "Keep decisions for three years" becomes "keep
decisions for seven years" because of something that happened in a meeting. If that is a code change,
it is a pull request, a review and a deploy, and it gets deferred. If it is a number in a row, it is
a number in a row.

**The reason has to travel with the rule.** A branch can carry a comment. A comment is not part of
the thing; it drifts, it gets deleted in a refactor, and nobody is ever asked to update it. A `why`
column is a field — when you add a row you have to fill it in.

The shape this takes: a small frozen record type per row, a tuple of them called `RETENTION`, and a
lookup dictionary built from it. Adding a kind means adding a row. It never means adding an `if`
somewhere else, and section 2.3 is about what happens when someone forgets.

## Why Sutra needs it

Because [§8.2 of the day-writer contract](../../LESSON.md) says Sutra's memory policy lives in
`sutra/memory/policy.py` and that its retention rules are **data, not code branches** — so that
someone who is not a programmer can review them.

That is not a stylistic preference. Sutra's support desk stores customer text. Section 4 is about
what that obliges you to do, and every one of those obligations is a conversation with somebody who
does not write software: how long is this kept, who can read it, what happens when the customer asks
for it to be gone. Each of those answers has to be readable off a page.

Day 40 made the same argument about a different subject: an allowlist of tools works because it is
a list a human reads and signs off, and its failure mode is a tool being missing rather than a tool
being silently permitted. Retention rows are that argument pointed at storage.

## The mechanism

The row type first. It is deliberately boring.

```python
# days/day-48-memory-design/lab/policy.py
@dataclass(frozen=True)
class Rule:
    """One row of the retention policy. Readable by someone who does not write Python."""

    kind: str
    keep_for_days: int | None
    supersede: bool
    authority: int
    redact: bool
    why: str
```

**Line by line:**

- `@dataclass(frozen=True)` makes each row immutable. A rule that can be mutated at runtime is a rule
  whose value at the moment of a decision is unknown, and the whole point of writing it down is that
  you can say what it was.
- `kind` matches the taxonomy from [1.2](../01-what-a-conversation-leaves/1.2-six-kinds-not-one-bucket.md).
  It is the key everything else is looked up by.
- `keep_for_days: int | None` has three meaningful values and they are all in the type. A number is a
  lifetime in days. `None` is "no expiry date". `0` is "this kind is never written down at all" — and
  putting refusal in the same column as retention, rather than in a separate `store: bool` flag, means
  a reviewer reads one column to see everything about how long something lives.
- `supersede: bool` says whether a newer memo about the same subject replaces this one. `decision`
  sets it `False` because two decisions are two decisions
  ([3.2](../03-expiry-and-supersession/3.2-the-newer-fact-wins.md)).
- `authority: int` is the tiebreak from [1.4](../01-what-a-conversation-leaves/1.4-a-correction-outranks-it.md):
  higher wins when two live memos are about the same subject and were recorded on the same day.
- `redact: bool` is whether personal data is stripped before the text is written
  ([4.1](../04-privacy-and-erasure/4.1-redact-before-you-write.md)). Every row currently sets it
  `True`; it is a column rather than a constant so that the day somebody wants an exception, the
  exception is a visible row rather than an argument.
- `why: str` is required and has no default. That is the design decision in this class. You cannot
  add a rule without writing the reason, because the field has no default value and Python will
  refuse to construct the row.

And the table itself:

```python
RETENTION: tuple[Rule, ...] = (
    Rule(
        kind="customer_fact",
        keep_for_days=None,
        supersede=True,
        authority=2,
        redact=True,
        why="True until the customer changes it. A newer fact about the same subject replaces it.",
    ),
    Rule(
        kind="quote",
        keep_for_days=30,
        supersede=True,
        authority=1,
        redact=True,
        why="A number that was true on a date. Prices move; a stale quote is worse than none.",
    ),
)

RULES: dict[str, Rule] = {rule.kind: rule for rule in RETENTION}
```

**Line by line:**

- `RETENTION` is a `tuple` and not a `list`, so the table cannot be appended to at runtime by
  accident. The policy is what was reviewed, not what some import decided to add.
- Every row is written with **keyword arguments**, never positionally. `Rule("quote", 30, True, 1,
  True, "...")` is the same row and is unreadable, and the whole argument of this part is about who
  can read it.
- The rows are in a deliberate order — the things kept longest first, the things never kept last — so
  that the printed table reads top to bottom as a decreasing commitment.
- `RULES` is built **from** `RETENTION` by comprehension rather than written out a second time. Two
  copies of a policy is two policies, and the one the code uses is whichever one it happened to
  import.
- The dictionary is keyed on `kind`, which means an unknown kind raises `KeyError` on a direct lookup
  and returns `None` from `.get()`. Section 2.3 is entirely about which of those two the calling code
  should use.

Compare the two forms side by side:

```bash
cd days/day-48-memory-design/lab
uv run python branches.py
cd -
```

**Line by line:**

- `branches.py` holds the same policy written as an `if`/`elif` chain, and calls both. It is not a
  strawman: the branch version is correct and produces identical verdicts, which is the point.
- There is no ablation flag because both versions run in one pass. The comparison is the output.

Measured on 2026-09-05:

```text
--- the branch version, asked one candidate at a time ---
  customer_fact keep  no expiry
  correction    keep  no expiry
  customer_fact keep  no expiry
  guess         drop  no expiry
  quote         keep  2026-10-05
  decision      keep  2029-09-04
  transcript    drop  no expiry

--- the same policy, as the rows in policy.py ---
kind            keep for  supersede authority  redact  why
customer_fact    forever  True      2          True    True until the customer changes it. A newer fact about the same subject replaces it.
correction       forever  True      3          True    The customer telling us we had it wrong. Outranks whatever it corrects.
decision       1095 days  False     0          True    What we did and why. Never replaced: a later decision is a second decision.
quote            30 days  True      1          True    A number that was true on a date. Prices move; a stale quote is worse than none.
guess             0 days  False     0          True    A hypothesis nobody confirmed. Stored, it comes back later wearing a fact's clothes.
transcript        0 days  False     0          True    The raw turns. Kept in the session store, never promoted to memory.

rows a reviewer can read: 6
branches a reviewer must read Python to check: 6
Same verdicts. Only one of them can be reviewed by the person who owns the risk.
```

The verdicts match, line for line. Six branches, six rows.

What the branch version cannot print is the `why` column, and that is not a limitation of the demo —
it is a property of the form. The reasons in a branch version live in comments, which are not values,
which is why the second block can be shown to a support lead and the first cannot.

## When it breaks

The table breaks when it stops being the only place decisions are made.

The realistic version is not somebody rejecting the design. It is a hurried patch. A bug report says
`guess` memos are showing up in retrieval, and somebody adds this two files away:

```python
if memo.kind == "guess":
    continue
```

Now there are two policies. The table says one thing, that line says another, and they agree today.
Six months later a reviewer reads the table, sees `guess` already has `keep_for_days=0`, decides the
line is redundant, and deletes it. If the table's row had ever been edited in the meantime, that
deletion changes behaviour and the diff looks like cleanup.

The visible symptom of a split policy is a run where the printed table and the actual verdicts
disagree:

```text
guess             0 days  False     0          True    A hypothesis nobody confirmed...

KEPT
  guess         plan                  no expiry   ticket 4521 turn 4
```

The table says never, the store says here it is. Whenever those two disagree, some code is deciding
retention outside the table, and finding it is a grep for the kind names.

The second break is a `why` column filled with nothing. `why="see ticket JIRA-4410"` compiles, passes
review, and is worthless in three years when the ticket system has been migrated. The field being
required stops the row being *empty*; it cannot stop it being lazy, and that is a review problem
rather than a code one.

## In production

**What a professional writes instead:** the same rows, loaded from a file that lives beside the code
rather than inside it — a YAML or TOML document with a schema, validated at import. That moves the
rules to something a non-engineer can edit through a pull request without touching Python, which is
the last step of the argument this part makes. The reason the lab keeps them in Python is
honesty: a config file needs a loader and a validator, and both would be code the reader has not
written yet.

The other production addition is a **history**. A retention rule that changed last March means memos
written before March were written under a different rule, and the store cannot say which. Real
systems version the policy and stamp each memo with the version that judged it — otherwise
"why is this still here?" has no answer.

**What degrades at scale:** the number of rows. Six is a board by a door. Sixty is a rulebook in a
drawer, and it stops being reviewed for exactly the same reason. When a table grows past what someone
will read in one sitting, the answer is not a bigger table; it is fewer kinds, with the distinctions
that were not load-bearing collapsed.

**The review comment a senior engineer leaves:** *"This is a policy, so it should be readable by the
people who own the policy. Right now it is six `elif` branches and the reasons are in comments, which
means our support lead cannot check it and our comments will be wrong within a year. Make each rule a
row with a mandatory reason field, and make the table printable so it can go in the runbook."*

**The interview question:** *"Where do you put business rules like retention periods?"* The honest
spoken answer: *"In data, with a mandatory reason column, and I would defend that specifically for
retention rather than as a general rule — most logic is fine as branches. Retention is different
because the decisions are not technical. How long we keep a record of what a customer was told is a
question about disputes and obligations, and the person who should answer it does not read Python. On
our desk I wrote both versions and they produce identical verdicts, so this is not about correctness.
It is that the table has a `why` column and the branch version has comments, and a comment is not a
value — nobody is ever forced to fill one in and nobody is ever forced to update one. Making `why` a
required field with no default means you cannot add a rule without saying why it exists."*
