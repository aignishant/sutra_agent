# 5.2 — 💥 The price that changed last year

## One-line answer

A memo with no expiry date does not go quiet when it stops being true — it keeps answering, with the
same confidence it had on the day it was written.

## The story

A laminated price list on the wall behind a counter.

It was printed properly. Somebody took care over it: clear headings, everything in the right column,
laminated so it would not get grubby. That was three years ago and prices have moved twice since.

The staff know. They quote the real prices from memory and nobody thinks about the board.

Then a new person starts. They are helpful, they want to get it right, and there is an authoritative
list on the wall. So they read a number off it and say it out loud to a customer, and the customer
writes it down, because why would you doubt a printed price.

Now there is an argument at the till, and the customer is not being difficult — they were told a
number by somebody who works there, in the shop, off a board that is still on the wall.

The board is not lying. It was accurate when it was made. What it is missing is any way of saying
*when* it was made, so a new person cannot tell the difference between a current price and a
well-laminated old one. And the reason it is still there is the most ordinary reason in the world:
taking it down was never anybody's job.

## The idea in plain language

This is [3.1](../03-expiry-and-supersession/3.1-true-on-the-day-it-was-said.md)'s rule with the rule
switched off, watched all the way to the customer.

The failure has four properties, and it is worth naming them separately because each one defeats a
different defence you might reach for.

**It is not detectable from the memo.** The text is well formed, the source is real, the account is
right. Nothing about the record is malformed. A validator, a schema check, a test that the memo
round-trips through the store — all green.

**It gets *more* likely to be retrieved over time, not less.** Every retrieval scores on relevance, and
a memo that says "Business plan is 4800 a year" is a beautiful match for "what does the Business plan
cost". Age is not part of the score unless somebody put it there. So the stale memo does not fade — it
sits at the top of the results for its subject, forever, because it is the only memo about that
subject.

**Supersession cannot save it.** [3.2](../03-expiry-and-supersession/3.2-the-newer-fact-wins.md) is a
contest between memos about the same subject. If nobody ever quoted that price again, there is no
competitor, and the 2026 number wins by walkover in 2027. Supersession handles facts that get
*replaced*; expiry handles facts that simply *rot*, and the world rotting without telling you is the
common case.

**The output is more confident than the truth.** "The Business plan is 4800 a year" is a better
sentence than "I would need to check the current price". It is specific, it is short, and it is the
one that gets repeated to a customer, written down, and quoted back to you.

## Why Sutra needs it

Because this exact memo is in the day's own ticket. Turn 5 of the support conversation is:

> Business is 4800 a year at the moment.

Read the last three words again. The agent hedged. The agent *knew* it had a shelf life and said so
out loud, in the conversation, at the moment the number was said.

Then it became a memo, and a hedge is not a fact, so there was nowhere to put it. `Business plan is
4800 a year` is what got stored. The knowledge about the shelf life existed for exactly one turn and
then was gone — unless a column in the policy caught it.

That is the whole argument for `keep_for_days` in one example: the information about how long
something lasts is available **once**, at write time, from the person or process that produced it, and
if it is not written down then nobody will ever be able to reconstruct it.

## The mechanism

One memo, built twice, differing in one field.

```python
# days/day-48-memory-design/lab/stale.py
def build(expiring: bool) -> list[Memo]:
    """One memo, written the same way twice, differing only in whether it carries an expiry."""
    days = RULES["quote"].keep_for_days
    return [
        Memo(
            kind="quote",
            holder="acct-88",
            subject="business_plan_price",
            text="Business plan is 4800 a year.",
            source="ticket 4521 turn 5",
            recorded_on=RECORDED,
            expires_on=RECORDED + timedelta(days=days) if expiring and days else None,
        )
    ]
```

**Line by line:**

- `days = RULES["quote"].keep_for_days` reads the number from the policy table rather than writing `30`
  here, so the demo cannot drift from the rules the rest of the day teaches. Change the row, change the
  demo.
- `expires_on=... if expiring and days else None` is the only difference between the two arms.
  Everything else — text, holder, subject, source, recording date — is byte for byte identical.
- `expiring and days` guards against `days` being `None`, which would make the `timedelta` raise. That
  is defensive here and it is the shape the real code needs, because the same expression runs over
  every kind.
- The memo is returned in a list of one, because `what_to_forget` takes a store. A single memo is a
  store of one, and keeping the shape means the demo exercises the real function rather than a special
  case.

```bash
cd days/day-48-memory-design/lab
uv run python stale.py
uv run python stale.py --expiring
cd -
```

**Line by line:**

- The bare arm is the failure: a `quote` written with no expiry date, which is what happens if the
  column does not exist or the row is left as `None`.
- `--expiring` is the fix. The ablation is the retention rule itself, which is the honest thing to
  ablate on a day about retention rules.
- The question is asked on 2027-09-20, which is 380 days after the number was said. That is not an
  extreme interval — it is roughly the point at which the same customer opens a second ticket.

Measured on 2026-09-05:

```text
recorded 2026-09-05, asked 2027-09-20 - 380 days later
expiry on the row: none
  keep       expires never       Business plan is 4800 a year.

what the desk tells the customer:
  "The Business plan is 4800 a year."
  The number is 380 days old and nothing in the reply says so.
```

```text
recorded 2026-09-05, asked 2027-09-20 - 380 days later
expiry on the row: 30 days
  expired    expires 2026-10-05  Business plan is 4800 a year.

what the desk tells the customer:
  "I do not have a current price for the Business plan; let me check."
  Slower, and correct. That is the whole trade this row buys.
```

Read the two quoted sentences at the bottom of each block, and notice which one sounds like a better
support desk.

The first one is faster, more helpful, more specific, and wrong. The second one is slower, admits
ignorance, creates work for somebody, and is correct. **The bad arm produces the better-sounding
reply**, and that is why this failure survives user testing, demos and satisfaction scores. It only
shows up as a problem at the till.

## When it breaks

There is no traceback, and the closest thing to an error message arrives from outside the system:

```text
Your agent told me on the 20th that the Business plan was 4800 a year.
I have just been invoiced 5400. Which is it?
```

That is the error text for this failure. It arrives by email, days later, from the person least
equipped to debug it, and by the time anybody looks, the retrieval that produced it is not in any log
that is still being kept.

The second break is choosing the number badly in the other direction, which produces a different
complaint that is easier to dismiss:

```text
The agent used to know our pricing and now it just says it needs to check.
```

That is what a thirty-day expiry sounds like from the outside when quotes are only refreshed
quarterly. It is a real cost and it is the reason the `why` column has to say what the number is sized
against — *"prices are reviewed quarterly; a quote older than a month has usually been superseded"* is
a claim somebody can check and disagree with. A bare `30` is not.

The third break is the one that hides inside a correct-looking fix. Somebody notices stale quotes,
adds an expiry, and applies it to `customer_fact` as well while they are in there — after all, facts
get stale too. Now a customer's plan expires after ninety days and the desk forgets things the
customer told it once and never repeated. A plan does not rot; it gets **replaced**, and the mechanism
for that is supersession, not expiry. Using the wrong one of the two produces amnesia rather than
staleness.

The fourth is subtle: an expiry that is honoured at retrieval but not at *ingestion into a prompt
template*. If some other code path pastes "known facts about this customer" into the system
instruction by reading the store directly, the expiry never runs — the exact shelf-walking failure
from [3.3](../03-expiry-and-supersession/3.3-a-verdict-is-not-an-erasure.md).

## In production

**What a professional writes instead:** the expiry, plus the date on the way out. A live quote is
returned as `"Business plan is 4800 a year (quoted 5 September 2026)"` rather than as a bare number, so
the model and the human both have something to reason with near the boundary. Expiry is a cliff and a
visible date is a slope, and most of the value is in the slope.

The stronger version, where the source system allows it, is not to store the number at all. A price has
an authoritative source, and a memo that says *"the customer was quoted the Business plan price on 5
September"* plus a tool call to fetch the current one is right forever. **The best retention rule for a
volatile fact is often to store the event rather than the value** — but that only works when there is a
system to ask, which is why the general mechanism still has to exist.

**What degrades at scale:** the proportion of the store that is volatile. A handful of quotes is easy
to reason about. Across thousands of customers, volatile memos accumulate faster than durable ones,
because prices, queue lengths, statuses and estimates are said constantly and plans change rarely. A
store with no expiry drifts towards being mostly stale numbers, and the retrieval quality degrades
smoothly with no event that anybody notices.

**The review comment a senior engineer leaves:** *"Every `quote` in here has `expires_on` of `None`,
which means we are agreeing to quote 2026 prices in 2029. Put the expiry on the row and write in the
`why` what it is sized against — if the answer is that pricing is reviewed quarterly, say that, so the
next person knows they are allowed to change it when the review cycle changes. And return the quote
with its date attached, because a cliff at thirty days is worse than a visible date at twenty-nine."*

**The interview question:** *"Tell me about a bug that only appeared after a long time."* The honest
spoken answer: *"A price quoted from memory more than a year after it was true. The interesting part is
that nothing was broken. The memo was well formed, the source was real, and every test passed —
because there is no way to detect it from the record itself. It also gets *more* likely to be retrieved
over time, not less, since relevance scoring loves an exact subject match and nothing in the score
knows about age. And supersession could not help, because supersession is a contest and there was no
competitor — nobody had quoted that price again, so the old one won by walkover. What made it
persuasive to me was that the broken arm produces the *better* answer. 'The Business plan is 4800 a
year' is specific and confident, and 'I would need to check the current price' sounds like a worse
support desk. That is exactly why the bug survives demos. The fix is a shelf life on the row, and the
thing I would push for beyond that is storing the event rather than the value where there is a system
to ask — a memo that says we quoted a price on a date, plus a tool call for the current one, is right
forever."*
