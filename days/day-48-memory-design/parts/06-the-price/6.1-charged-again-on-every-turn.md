# 6.1 — Charged again on every turn

## One-line answer

A remembered fact is not paid for once when you store it — it is paid for again on every turn that
retrieves it, so retention is priced per turn and not per row.

## The story

There is a bag of sand in the boot of your car from a job last spring.

It went in for one afternoon. It weighs about twenty kilos. It has been there ever since, because
taking it out means finding somewhere to put it, and every time you open the boot you are in the
middle of doing something else.

It has cost you nothing to store. The boot was empty anyway.

What it has done is make every single journey since then slightly more expensive. The school run, the
motorway trip, the drive to the supermarket and back — every one of them, all year, has been carrying
twenty kilos that is doing nothing. No individual trip is noticeably worse. You would not be able to
point at one and say the sand made a difference to it. The bill arrives spread across hundreds of
journeys, in an amount you never see itemised.

The mistake is not putting the sand in the boot. It is thinking of it as *stored*, when it is actually
being *carried*.

## The idea in plain language

There are two ways to think about what a memory costs, and only one of them is right.

**Storage thinking.** A memo is a row. Rows are cheap. A hundred memos per customer is nothing. This
is true and it is not the cost that matters.

**Carrying thinking.** A memo is only useful when a retrieval returns it, and a returned memo is pasted
into the prompt. Day 24 established the property that makes this expensive: **the prompt is paid for
again on every turn**, because a conversation resends its history each time. So a memo retrieved in a
twelve-turn conversation is not paid for once. It is paid for on the turn it arrives and on every turn
after it.

That gives retention an entirely different unit. Not bytes and not rows, but **tokens per turn**, and
the multiplier is the length of the conversation.

Three consequences follow, and they are the reason this part is at the end of the day rather than
alongside the taxonomy.

**A permanent memo is a permanent line item.** `keep_for_days=None` does not mean the memo costs
nothing after the first turn. It means it will be carried on every matching turn, for that customer,
until somebody deletes it. Two of the six kinds in the table have no expiry, and section 6.2 puts a
number on what that commits you to.

**Retrieval width matters more than store size.** A store of a thousand memos where retrieval returns
three is cheap. A store of twenty where retrieval returns all twenty is not, and
[1.1](../01-what-a-conversation-leaves/1.1-the-chat-nobody-can-leave.md) showed ADK's keyword matcher
returning everything it held for a query containing common words.

**Free tier makes this concrete rather than abstract.** Sutra has twenty generations a day. Tokens are
not billed here — they are rationed, and the ration is the constraint
([Day 24](../../../day-24-token-accounting-and-budgets/parts/02-two-ceilings/2.3-denominated-in-quota-not-dollars.md)).
A retention policy that fills the window is a retention policy that shortens every conversation you can
afford to have.

## Why Sutra needs it

Because a design day that produces only opinions cannot be reviewed, and this is the section that turns
the policy into numbers somebody can disagree with.

Every argument earlier in this day was about correctness: is this fact still true, is it the current
one, should it be here at all. Correctness arguments are winnable in a meeting by whoever is more
confident. A number is not.

Concretely, section 2.1 said retention rules belong in data so a non-engineer can review them. This
part is what makes that review possible in the direction that matters most, because the first question
a reviewer asks about a proposed row is *"what does that cost?"* — and until now the answer would have
been a shrug.

Day 49 makes it sharper still: an embedding index returns the top `k` matches, and `k` is a number
somebody chooses. Choosing it without knowing the token cost per memo is choosing a per-turn bill
blindfolded.

## The mechanism

The counting uses the provider's own tokeniser, and the trick that makes it free is worth stating: the
`count_tokens` endpoint is **not** `generate_content`. It sits on its own quota, so measuring costs
none of the day's twenty generations — the same technique Day 24's `count_the_cost.py` uses.

```python
# days/day-48-memory-design/lab/price.py
def counted(text: str) -> int:
    """One count_tokens call, with the 429 handling every model path in this repo carries."""
    for attempt in range(4):
        try:
            return client.models.count_tokens(model=MODEL, contents=text).total_tokens
        except Exception as error:  # noqa: BLE001 - re-raised below if it is not a 429
            if "429" not in str(error) or attempt == 3:
                raise
            delay = getattr(error, "retry_after", None) or 2**attempt
            print(f"  429 from count_tokens; waiting {delay}s then retrying", file=sys.stderr)
            time.sleep(delay)
    raise RuntimeError("unreachable")
```

**Line by line:**

- `count_tokens(model=..., contents=text)` returns an object with `total_tokens`. It is a separate API
  call from generation and the model string still has to be passed, because different models tokenise
  differently — a count is only meaningful for the model that will read it.
- `MODEL` is `gemini-3.7-flash`, the free-tier string this repository uses throughout, with its roster
  re-verified on 2026-09-04 (Addendum 02: never invent a model name).
- The `except` catches broadly and then **re-raises** anything that is not a 429, so a genuine error
  surfaces rather than being retried into silence (Principle 10).
- `attempt == 3` re-raises on the last attempt rather than falling out of the loop with no answer. A
  retry budget that ends in a shrug is worse than no retry.
- `getattr(error, "retry_after", None) or 2**attempt` prefers the server's own instruction and falls
  back to exponential backoff. The server knows when it will be ready and the client is guessing.
- The message goes to `stderr`, so the script's measured output on `stdout` stays clean enough to pipe.
- `# noqa: BLE001` carries its reason inline, which is the repository's rule for suppressing a lint.

And the offline fallback, which matters more than it looks:

```python
def offline_count(text: str) -> int:
    """A character estimate, for a reader with no key or no network. Named as an estimate."""
    return max(1, round(len(text) / CHARS_PER_TOKEN))
```

**Line by line:**

- `CHARS_PER_TOKEN = 4.0` is a rough constant, and the script labels its output *"estimated from
  characters"* rather than presenting it as measured. Comparing the two arms below shows how rough it
  is, which is the honest way to present an estimate.
- `max(1, ...)` because no non-empty string costs zero tokens, and a zero would make the ratios
  divide by zero later.
- It exists so the day runs for a reader with no API key at all. A teaching day that cannot be run
  without credentials is a day half the readers skip.

```bash
cd days/day-48-memory-design/lab
uv run python price.py
uv run python price.py --offline
cd -
```

**Line by line:**

- The bare arm asks the provider. `--offline` uses the estimate. Both are the ablation for the
  *measurement*, not for the policy — comparing them is how you find out whether a character estimate
  is good enough to argue from.

Measured on 2026-09-05, against `gemini-3.7-flash`:

```text
tokens counted by gemini-3.7-flash

what                                      chars  tokens
the whole transcript                        698     176
customer_fact / billing_email                33      11
correction / billing_email                   64      17
customer_fact / plan                         28       8
quote / business_plan_price                  29      12
decision / ticket-4521                      136      25
the whole live store                        294      73

per turn, if every memo is retrieved:      73 tokens
per 12-turn conversation:                   876 tokens
per day, across 20 generations:          1460 tokens
of which never expires by policy:          36 tokens per turn, for one customer
```

Three numbers to hold on to.

**73 tokens per turn** for one customer's whole memory. That is small, and it should be — this is one
ticket. The number that matters is the shape it has, not its size.

**876 tokens for a twelve-turn conversation.** That is the same 73 tokens, twelve times, because the
history is resent. Nothing was added to the store between turn one and turn twelve.

**36 tokens per turn that never expire.** That is the `customer_fact` and `correction` rows — the two
with `keep_for_days=None`. Those 36 tokens are not a cost you pay this month. They are a cost you have
agreed to pay on every matching turn for this customer for as long as the system exists, and section
6.2 multiplies it out.

Now compare against the estimate:

```text
tokens estimated from characters

the whole transcript                        698     174
quote / business_plan_price                  29       7
the whole live store                        294      74
```

The store total is close — 74 against 73 — and the individual rows are not. The quote is estimated at
7 and is actually 12, because `4800` and `a year` tokenise less efficiently than prose. **Character
estimates are fine for a total and wrong for a row**, which matters because the rows are what you
compare when deciding a policy.

## When it breaks

The first break is the quota you spend measuring. `count_tokens` is a separate endpoint but it is not
unlimited, and a naive script that counts every memo individually in a loop over a large store will
find out where its ceiling is:

```traceback
google.genai.errors.ClientError: 429 RESOURCE_EXHAUSTED. {'error': {'code': 429,
'message': 'Resource has been exhausted (e.g. check quota).', 'status':
'RESOURCE_EXHAUSTED'}}
```

That is why the retry handler exists, and why a real system counts once at write time and stores the
number on the memo rather than recounting on every read.

The second break is measuring the wrong string. The number that matters is not the memo's text — it is
the text **as it appears in the prompt**, including whatever wrapper the retrieval adds: a heading, a
date, a source citation, a JSON envelope. A memo of 25 tokens rendered as
`{"kind": "decision", "recorded": "2026-09-05", "text": "..."}` is meaningfully more than 25, and the
overhead is per memo, so it scales with retrieval width rather than with content.

The third break is assuming the price is stable. Tokenisation is a property of the model, and the
model string is pinned but the roster moves — Addendum 02 records that free rosters changed in
December 2025. A policy priced against one model is not priced against its replacement, so the
measurement is dated in the output for the same reason a version pin gets a row in `docs/PACKAGES.md`.

The fourth is the honest limit of the whole exercise: this measures the *cost* of a retention policy
and says nothing about its *value*. A memo that saves one tool call has earned far more than the 25
tokens it costs. Pricing tells you what the bill is, not whether it was worth paying, and anybody who
uses these numbers to argue for a shorter retention without the other half of the argument is doing
[5.3](../05-failure-lab/5.3-the-rule-that-deleted-the-evidence.md) with a spreadsheet.

## In production

**What a professional writes instead:** the token count is computed once, at write time, and stored on
the memo. Retrieval then knows the cost of its result set **before** assembling the prompt, which is
what makes a token budget per retrieval possible rather than aspirational — you can drop the cheapest
marginal memos until the result fits, instead of discovering the overflow when the request fails.

The second production addition is a per-holder measurement that runs on a schedule: tokens per turn per
customer, tracked over time. That number only goes up, silently, as customers have more conversations,
and it is the earliest signal that a retention policy needs a rule it does not have.

**What degrades at scale:** the tail, not the average. Most customers will have a handful of memos and
cost almost nothing. A few — the long-tenured, the frequently-escalating — will have hundreds, and
those are precisely the customers whose conversations matter most. So the average token cost per turn
is a reassuring number that describes nobody, and the number to watch is the ninety-fifth percentile.
Under concurrency there is a second effect: retrieval width is usually a constant, so a store that
grows does not cost more per turn until it crosses the point where the top `k` are all genuinely
relevant, and then quality degrades rather than cost.

**The review comment a senior engineer leaves:** *"This prices the memo text and our retrieval wraps
each one in a JSON envelope with a source citation, so the real per-turn number is higher than what is
on this table and the overhead is per memo rather than per character. Count the rendered form. And
store the count on the memo at write time — recounting at read time is another API call in the request
path, and we will be doing it on every turn."*

**The interview question:** *"How do you budget an agent's memory?"* The honest spoken answer: *"In
tokens per turn, not in rows, and the unit is the whole point. A memo is not paid for once when you
store it — it is retrieved into the prompt and the prompt is resent on every turn, so it is carried
rather than stored. On our support desk one customer's whole memory was 73 tokens, which sounds like
nothing until you multiply it by a twelve-turn conversation and get 876. The number I would put in
front of a reviewer is the one for the rows with no expiry: 36 tokens per turn, for one customer, for
as long as the system exists. That reframes 'keep it forever' from a storage decision into a standing
per-turn commitment. The measuring is free if you use the token-counting endpoint rather than
generation — it is separate quota — and the mistake to avoid is pricing the bare text when what gets
sent is the rendered form with its wrapper, because that overhead is per memo and scales with how many
you return."*
