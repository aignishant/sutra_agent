# 4.4 — The store that must not be committed

## One-line answer

Every retention rule in this policy is undone the moment the store is committed to git, because git
keeps everything forever and this repository goes public.

## The story

Somebody photographs the whiteboard at the end of a meeting and posts it so the people who missed it
can catch up.

It is a good photograph. The diagram is legible, the action list is readable, and everybody who
needed it has it in seconds.

In the bottom right corner, in different handwriting, from a call that happened before the meeting,
there is a customer's name and their mobile number.

Nobody noticed, because nobody was looking there — they were looking at the diagram, which is what
the photograph is *of*. And now the number is in a place with a different audience and a different
lifetime from the whiteboard, which gets wiped on Friday.

Deleting the post does not undo it. The people who have already seen it have seen it. Anything that
mirrored it has mirrored it. The whiteboard's own erasure schedule turned out to be irrelevant the
moment a copy left the room, and the copy left the room because somebody was being helpful.

## The idea in plain language

Everything in this section so far has been about the **store**: what enters it, how long things last,
how they are removed. All of it assumes the store is one place with one lifetime that you control.

Committing the store to git breaks that assumption completely, and it breaks it in a way that cannot
be repaired afterwards.

Three properties of git make this different from an ordinary mistaken copy.

**Git keeps everything.** Deleting a file in a later commit does not remove it from history. It is
still in the object database, reachable by any hash that ever pointed at it, and `git log -p` will
print it.

**Git is distributed.** Every clone is a full copy of the history. Once somebody has pulled, no
action you take in your own repository reaches theirs.

**This repository goes public in Phase 14.** That is not a hypothetical. It is a scheduled event in
the plan, and it means every commit made today is a commit that will be readable by anyone.

Put those together and the consequence is exact: **a memory store committed to git has a retention
period of forever and an access list of everyone.** Every number in the retention table becomes
decoration. The thirty-day expiry on a quote is meaningless when the quote is in a commit from
September. The erasure path from [4.3](4.3-erasure-is-an-obligation.md) cannot reach into history.

This is Principle 9 — secrets never touch git — with the observation that a store of customer text is
in the same category as a credential, and is much easier to commit by accident because it does not look
like one. Nobody commits a file called `password.txt`. People commit `memory.json` all the time,
because it is data their program made and it is sitting in the working tree.

The defence has two halves and both are needed. **The path is ignored before the file exists**, which
is the Day 0 discipline of writing `.gitignore` first. And **a check that can fail**, because an
ignore rule is a promise and a check is evidence.

## Why Sutra needs it

Because this repository already has the rule written down and the memory store is not covered by it.

Read what `.gitignore` says today:

```text
# ── runtime artifacts: never commit a session store ───────
.adk/
*.db
*.sqlite3
```

That comment says *never commit a session store*, and it is enforced for three patterns. Day 47's
database-backed sessions land in a `.sqlite3` file, so they are covered.

The memory store this day designs is JSON. `memory.json` matches none of those three patterns, and the
moment the learner writes it to `sutra/data/`, git will offer it up in `git status` like any other new
file.

That is not a criticism of the existing rule. It is what happens to every ignore list: it covers the
shapes that existed when it was written, and a new shape arrives later. It is the same argument as
[2.3](../02-policy-as-data/2.3-the-kind-with-no-rule.md), pointed at a different list.

## The mechanism

Two questions, both answerable without a model, both answerable in a hook.

```python
# days/day-48-memory-design/lab/gitcheck.py
def ignored(path: Path) -> bool:
    """Ask git itself rather than parsing .gitignore, because git's rules are not a substring."""
    result = subprocess.run(["git", "check-ignore", "-q", str(path)], cwd=ROOT, capture_output=True)
    return result.returncode == 0
```

**Line by line:**

- `git check-ignore` asks **git** whether a path is ignored, rather than reading `.gitignore` and
  matching strings. This matters more than it looks: ignore rules come from several files, they nest by
  directory, later rules override earlier ones, and a leading `!` re-includes. Any home-grown matcher
  gets one of those wrong, and gets it wrong in the direction of reporting safety.
- `-q` suppresses output; the answer is the exit status. `0` means ignored, `1` means not ignored.
- `capture_output=True` keeps git's stderr out of the script's own output, so the printed report is the
  script's.
- `cwd=ROOT` runs the command from the repository root, because `check-ignore` resolves paths relative
  to where it runs.
- The path does **not** have to exist. That is the property that makes this usable before the learner
  has ever run the memory store, and it is why the check can be written on the same day as the design
  rather than after the first file appears.

And the content half:

```python
blob = json.dumps(rows, default=str)

findings: list[str] = []
for kind, pattern in PII_PATTERNS.items():
    if pattern.search(blob):
        findings.append(f"unredacted {kind} in the store")
if not ignored(STORE):
    findings.append(f"{STORE.relative_to(ROOT)} is not ignored by git")
```

**Line by line:**

- The whole store is serialised to one string and searched, rather than each field checked separately.
  A pattern that would only match across a field boundary is a false positive; a field somebody forgot
  to check is a false negative, and the second is the one that hurts.
- `default=str` handles the `date` objects, so the check never crashes on a store shape it did not
  expect.
- `PII_PATTERNS` is imported from `policy.py` rather than redefined. Two copies of a pattern list means
  the check is testing a different rule from the one the writer applies, which is a check that passes
  while the store fills with things it should have caught.
- The findings are **accumulated** rather than returned on the first hit, so one run tells you
  everything that is wrong instead of one thing at a time.
- `return 1 if findings else 0` at the end makes this a gate rather than a report. Principle 11: it can
  go red.

```bash
cd days/day-48-memory-design/lab
uv run python gitcheck.py; echo "exit: $?"
uv run python gitcheck.py --raw; echo "exit: $?"
cd -
```

**Line by line:**

- `--raw` skips redaction, simulating the store as it would be if
  [4.1](4.1-redact-before-you-write.md)'s rule were not applied. It is the ablation: same store, same
  path, one policy column ignored.
- `echo "exit: $?"` prints the exit status of the previous command, because the point is the code
  rather than the text.

Measured on 2026-09-05:

```text
store path: sutra\data\memory.json
git ignores it: False
redaction: applied
  - sutra\data\memory.json is not ignored by git
findings: 1
exit: 1
```

```text
store path: sutra\data\memory.json
git ignores it: False
redaction: skipped (--raw)
  - unredacted EMAIL in the store
  - sutra\data\memory.json is not ignored by git
findings: 2
exit: 1
```

**Both arms are red, and the first one is red for the reason that matters.** `sutra/data/memory.json`
is not ignored by this repository as it stands today. That is a real finding about the real
`.gitignore`, not a staged one, and fixing it is a `TODO(me)` in the build brief.

The second arm shows the two defences are independent. Redaction failing gives you a store with an
email address in it; the ignore rule failing gives you a store in git. You need both, and each one
being green tells you nothing about the other.

## When it breaks

The break that matters has already happened by the time you see it, and it looks like this:

```text
$ git log --oneline -- sutra/data/memory.json
a41f9c2 add memory store fixture for the retrieval tests
```

One commit, made in good faith, probably to make a test reproducible. The file has since been deleted.
It is still there:

```bash
git show a41f9c2:sutra/data/memory.json
```

That command prints the whole store, and it will keep printing it after the file is deleted, after the
branch is merged, and after the repository is made public. Removing it means rewriting history, which
means every clone is now wrong and every collaborator has to be told — and the rewrite does not touch
the clones that already exist.

The second break is the ignore rule that is right about a path nobody uses. `.gitignore` says
`sutra/data/memory.json` and the code writes `sutra/data/memory_store.json`. The check is green, the
rule is correct, and it protects nothing. This is why the check takes the path **from the code** rather
than from a constant typed a second time — the value it tests has to be the value the writer uses.

The third break is scope creep in the wrong direction: adding `*.json` to `.gitignore`. It solves this
problem and quietly stops tracking every fixture, every configuration file and every lockfile in the
project. Broad ignore rules fail silently and in the direction of missing files, and the symptom
arrives weeks later as a checkout that does not work.

## In production

**What a professional writes instead:** the store does not live in the repository at all. It lives in a
database or an object store outside the working tree, and the question stops being *"is this ignored?"*
and becomes *"who can read this?"* — access control, encryption at rest, and an audit of who queried it.
An ignore rule is what protects a store that has no better home yet, and it is worth being clear that
this is what it is.

The check moves too. A script somebody runs is a script somebody forgets, so it becomes a pre-commit
hook and a CI job, with the CI job being the one that counts because a hook can be skipped with
`--no-verify`. Alongside it goes a **secret scanner over the whole history**, not just the working tree,
because the value of scanning the tree is bounded by the fact that the tree is the one place you can
still fix.

**What degrades at scale:** the number of places that write. One code path writing one file is easy to
ignore correctly. A dozen services, each with its own local cache, dump files and debug output, is not,
and the failure is always the new path nobody added a rule for. Under concurrency there is a specific
version of it: a crash dump or a core file written by a process holding customer text in memory lands
wherever the operating system puts it, which is not a path anybody's `.gitignore` anticipated.

**The review comment a senior engineer leaves:** *"The memory store is being written into `sutra/data/`
and it is not in `.gitignore` — our existing rule covers `*.db` and `*.sqlite3`, and this one is JSON.
Add the path before the code that writes it lands, not after, and add the check to `./m check` so we
find out from CI rather than from a repository that has already gone public. And do not fix it with
`*.json`."*

**The interview question:** *"What is the risk of an agent's memory store in a code repository?"* The
honest spoken answer: *"That it makes every retention rule you wrote decorative. Git keeps everything —
deleting the file in a later commit leaves it in history — and git is distributed, so once anyone has
pulled you cannot reach their copy. Our repository is scheduled to go public, so a committed memory
store has a retention of forever and an access list of everyone, and the thirty-day expiry on a quote
means nothing next to that. What makes it likely rather than theoretical is that it does not look
dangerous. Nobody commits a file called `password.txt`, but people commit `memory.json` because it is
output their program made and it is sitting in the working tree. I wrote the check as a gate rather than
a document: it asks `git check-ignore` about the actual path the code writes to, and it greps the
serialised store with the same patterns the writer redacts with. It is currently red on our repo,
because the existing ignore rule covers `*.db` and `*.sqlite3` and the memory store is JSON."*
