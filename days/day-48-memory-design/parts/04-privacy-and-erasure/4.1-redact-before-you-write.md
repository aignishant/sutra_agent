# 4.1 — Redact before you write

## One-line answer

Personal data that never reaches storage cannot leak, cannot be backed up, cannot be exported and
cannot be asked for — so the redaction happens on the way in, not on the way out.

## The story

A parcel arrives and you unpack it. The box goes out with the recycling on Wednesday.

There is a label on the side with your name, your full address and the phone number you gave the shop.
Some people tear that label off before the box leaves the house. Some people mean to and do not. Some
people put the box out whole and think about the label an hour later, when the collection has already
been.

The people who tear it off do it at one specific moment: while the box is still in their hands, before
it goes anywhere. It takes two seconds. Once the box is on the pavement, the label is not a two-second
job any more — it is a walk down the road, and it depends on the box still being there.

Nothing about the label changed. What changed is how many places it might be.

## The idea in plain language

**Redaction** is replacing something sensitive with a marker that records what was there without
recording the value: `asha.k@example.com` becomes `[REDACTED-EMAIL]`.

The interesting question is not *how* to do it. It is **when**, and there are only two answers.

**Redact before the write.** The raw text exists only in memory, inside one function, for the length of
one call. What is written to the store is already clean. Nothing downstream — no backup, no replica,
no export, no log — ever has a chance to see the original.

**Redact after the write.** The raw text is stored, and then a second step cleans it up. The store
ends in exactly the same state. The difference is that for some interval, however short, the raw text
was at rest, and everything that reads a store at rest could have read it.

People choose the second one for sensible-sounding reasons. It is easier to fix mistakes if you kept
the original. It lets you improve the patterns later and re-run them. It means a redaction bug does not
lose data.

Every one of those reasons is an argument for **keeping the personal data**, which is the thing you
were trying not to do.

The principle underneath is the one that makes the rest of this section tractable: **the cheapest
personal data to protect is the personal data you do not have.** Every obligation in this section —
erasure, access requests, retention limits, breach notification — is proportional to what you hold. A
value that was never written is exempt from all of them, permanently, with no code.

One more distinction, because it gets lost. Redaction is not the same as **not storing the memo**. The
memo is stored. The fact that the customer gave a billing address is worth remembering. The address
itself is not, because the desk does not need it in order to be useful — it needs to know that one was
given and corrected. What survives is the shape of the fact without the value.

## Why Sutra needs it

Because Principle 9 says secrets never touch git, and because this repository goes public in Phase 14
with its whole history — which makes a store of customer text the single most dangerous file in it.

And because of a specific rule from Addendum 02 that applies to every day in this curriculum: the free
tiers Sutra runs on **may train on what you send them**. A memo is not just stored; it is retrieved and
pasted into a prompt, on every later turn that matches. A personal email address in a memo is a
personal email address in an outbound request, repeatedly, to a provider whose free-tier terms you do
not control.

That is the argument that survives the objection *"but this is synthetic data"*. It is synthetic. The
discipline is not, because the pipeline is the same one that would carry real data, and a pipeline that
has never redacted anything is a pipeline nobody has tested the redaction of.

## The mechanism

The function is six lines and the design decision is in the return type.

```python
# days/day-48-memory-design/lab/policy.py
PII_PATTERNS: dict[str, re.Pattern[str]] = {
    "EMAIL": re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"),
    "PHONE": re.compile(r"(?<!\d)(?:\+?\d[\s-]?){9,14}\d(?!\d)"),
}


def redact(text: str) -> tuple[str, list[str]]:
    """Replace every PII pattern with a marker. Returns the clean text and the kinds hit."""
    kinds: list[str] = []
    for kind, pattern in PII_PATTERNS.items():
        if pattern.search(text):
            kinds.append(kind)
            text = pattern.sub(f"[REDACTED-{kind}]", text)
    return text, kinds
```

**Line by line:**

- `PII_PATTERNS` is a module-level dictionary rather than a constant inside the function, so it is the
  same reviewable-data argument as `RETENTION`
  ([2.1](../02-policy-as-data/2.1-a-rule-someone-else-can-read.md)): adding a pattern is adding a row.
- The patterns are `re.compile`d once at import rather than compiled on each call. With one call this
  is irrelevant; over a batch of a million memos it is not, and it costs nothing to write it correctly
  the first time.
- The phone pattern's `(?<!\d)` and `(?!\d)` are negative lookarounds: do not match if there is another
  digit immediately before or after. Without them, a nine-digit run inside a longer number matches its
  middle and leaves the ends behind, which is worse than not matching at all because it looks redacted.
- `if pattern.search(text)` before substituting, purely so that `kinds` records what was actually
  found. `sub` alone would clean the text and tell you nothing.
- The return is a **tuple of the clean text and the kinds** — not just the text. That second element is
  the whole logging story: you can record *that* an email address was removed without recording the
  address. `{"event": "memory_write", "redacted": ["EMAIL", "PHONE"]}` is a useful log line and
  contains nothing.
- `text = pattern.sub(...)` rebinds the parameter, so each pattern operates on the output of the last.
  The original string is never mutated — Python strings are immutable — so the caller's value is
  untouched, which matters because the caller still holds the raw candidate.

And where it is called, which is the point of this part:

```python
text = candidate.text
if rule.redact:
    text, _ = redact(text)
kept.append(Memo(kind=rule.kind, text=text, ...))
```

**Line by line:**

- `redact` runs **before** `Memo` is constructed. There is no moment in the process where a `Memo`
  object holds unredacted text, so there is nothing for a serialiser, a logger or a debugger to pick up.
- `if rule.redact` reads the column from the policy table rather than always redacting, so the behaviour
  is visible to a reviewer reading rows rather than buried in a function.
- `text, _ = redact(text)` discards the kinds here because this function returns refusals rather than
  logging. In `sutra/memory/policy.py` that underscore is where the structured log line goes.
- `candidate.text` is left alone. The candidate is the caller's object and the function does not mutate
  its input — but note that the caller still holds the raw text, which is the honest limit of this
  mechanism and is discussed below.

Run both orders:

```bash
cd days/day-48-memory-design/lab
uv run python redact_demo.py
uv run python redact_demo.py --after
cd -
```

**Line by line:**

- The script writes a real file both times and takes a **backup** of it, because a backup is the
  simplest honest stand-in for every process that reads data at rest on a schedule.
- `--after` writes the raw text, takes the backup, and then overwrites with the clean text. That is not
  a caricature: writing first and cleaning in a second pass is exactly what a redaction job bolted on to
  an existing pipeline does.

Measured on 2026-09-05:

```text
logged: {'event': 'memory_write', 'redacted': ['EMAIL', 'PHONE']}
order: redact then write
store now:   Billing contact is [REDACTED-EMAIL], mobile [REDACTED-PHONE], account acct-88.
backup holds: Billing contact is [REDACTED-EMAIL], mobile [REDACTED-PHONE], account acct-88.

personal data that reached disk unredacted: none
```

```text
order: write then redact
store now:   Billing contact is [REDACTED-EMAIL], mobile [REDACTED-PHONE], account acct-88.
backup holds: Billing contact is asha.k@example.com, mobile +91 98765 43210, account acct-88.

personal data that reached disk unredacted: ['EMAIL', 'PHONE']
```

**The `store now:` line is identical in both runs.** Both stores are clean. Any test that inspects the
store passes in both arms, which is precisely why this bug survives review.

The `backup holds:` line is the difference, and the backup did nothing unusual — it copied a file that
existed at the moment it ran.

## When it breaks

The first break is visible in this day's own output, and it is worth pointing at rather than hiding:

```text
  - Billing email is [REDACTED-EMAIL]
```

The original sentence was `Billing email is asha.k@example.com.` with a full stop. The full stop is
gone. The email pattern ends in `[\w.]+`, which matches greedily and eats `com.` including the sentence's
punctuation.

That is a real defect and it has two costs. The visible one is that memos come out with mangled
punctuation. The invisible one is that a greedy pattern can eat more than intended in the other
direction too, and a pattern that over-matches quietly destroys text nobody asked it to touch.
`TODO(me)` in the build brief: tighten the pattern so it stops at the final label and does not consume
trailing punctuation, then write the test that pins it.

The second break is the one that ends careers, and it is under-matching. These two patterns catch
emails and phone numbers. They do not catch a postal address, a national identifier, a card number, a
name, a policy number, or a date of birth. A store that has been through this function is **not**
free of personal data; it is free of two shapes of it.

Nothing warns you about this. The output says `redacted: ['EMAIL', 'PHONE']` and looks like success.

The third break is the honest limit of redaction at write time. The raw text still existed — in the
request, in the session store, and in the caller's `Candidate` object. Redaction protects the *memory
store*, and the memory store is the thing with the longest retention, so it is the right place to
spend the effort. It is not a claim about the whole system, and anybody who says "we redact" without
naming which store they mean has not said anything.

The fourth is subtle and it is why the logging returns kinds rather than a diff. It is very tempting to
log the before and after so that redaction bugs can be debugged. That log line contains the raw value,
lives in a log store with a longer retention than the memory store, and is usually replicated to a
place with wider access. **The debugging aid is a copy of the thing you removed.**

## In production

**What a professional writes instead:** the same call site, with a real detector behind it rather than
two regular expressions. Named-entity recognition for names and addresses, checksum validation for card
and national-identifier formats, and a locale-aware phone parser rather than a digit run. The
architecture does not change at all — it is still one function called before the write, reading a
column from the policy table — and that is why the architecture is the thing this part is about.

Beside it goes a **canary test**: a fixture containing one example of every pattern class, asserted to
survive nowhere. It fails the day somebody adds a code path that writes a memo without redacting, which
is the failure that actually happens.

**What degrades at scale:** the false negative rate becomes a certainty rather than a risk. Over a
million memos, every pattern class you did not think of is present hundreds of times. This is why real
systems pair write-time redaction with a periodic **scanner** over the store at rest — the same
patterns, run against everything, reporting what got through. The scanner does not replace write-time
redaction; it measures how well it is working, and its findings are the input to the next pattern.

Under concurrency there is a narrower issue worth naming: if redaction is ever moved to a separate
worker for throughput, the window from [3.3](../03-expiry-and-supersession/3.3-a-verdict-is-not-an-erasure.md)
opens here too, and the raw text is at rest for however long the queue is deep.

**The review comment a senior engineer leaves:** *"Redaction is running after the insert. The store ends
up clean either way, which is why the test passes, but the raw row is on disk between the two statements
and our nightly backup does not care about our ordering. Move it above the write. And the log line that
prints the before and after has to go — it is a copy of the data we just removed, in a store with a
longer retention than the one we removed it from."*

**The interview question:** *"Where do you redact personal data?"* The honest spoken answer: *"Before
the write, and the reason is that everything else in a privacy programme is proportional to what you
hold. A value that was never written is exempt from erasure requests, access requests, retention limits
and breach notification, permanently, with no code. I proved the ordering matters with a two-arm demo:
both arms end with an identical clean store, so any test that checks the store passes both ways — but
the arm that wrote first and cleaned second had the raw email and phone number in the backup, because
the backup ran between the two statements. The thing I would be careful about claiming is coverage. Two
regular expressions catch two shapes. They do not catch names, addresses or identifiers, and the output
still says 'redacted' and looks like success. So write-time redaction plus a scanner over the store at
rest to measure what got through — the scanner is how you find out what your patterns do not know."*
