# 4.3 — Erasure is an obligation

## One-line answer

A memory system with no delete path is a liability rather than a feature gap, and the framework Sutra
uses does not give you one — so the policy owns it or nobody does.

## The story

You join a gym on your phone in about ninety seconds. Card details, a tick box, done. Turn up
tomorrow.

Eight months later you want to stop. There is no button. The app has a screen for changing your plan,
a screen for freezing your membership and a screen for adding a family member. To cancel you have to
come in during staffed hours and speak to someone, and the someone is not there on the day you go, and
the form has to be countersigned.

Nobody has refused you anything. Every individual step is reasonable on its own. It is simply that
getting in was designed and getting out was not, and the difference between the two is not policy —
it is that somebody built one path and did not build the other.

The thing that makes it a design failure rather than an inconvenience is what it does to the
relationship. You now assume the gym is trying to keep your money, whether or not it is, because a
system that is easy to enter and hard to leave *looks like* one that intends that. And once you assume
it, everything else the gym says reads differently.

## The idea in plain language

Three of the four ways something leaves this system are conveniences. One is not.

**Expiry** is housekeeping. You chose the number and you can change it.

**Supersession** is accuracy. You could turn it off and be wrong rather than illegal.

**Refusal** is prevention. It stops things arriving.

**Erasure on request** is none of those. It is somebody exercising a right, and the correct response is
not a feature you prioritise against other features. It is an obligation you discharge. That difference
shows up in three concrete ways.

**It is not optional and it is not negotiable.** You cannot decide the request is low value. You cannot
put it behind a flag.

**It outranks everything else in the policy.** A `decision` memo has `supersede=False` and a
three-year retention because those serve accuracy and audit. Neither survives an erasure request. So
in the order of checks, erasure is tested **first**, before expiry, before supersession, and the
ordering is a statement about which rules can override which.

**It has to leave a trace that is not the data.** After an erasure you must be able to answer "did this
happen?" — and you cannot answer it from the data, because the data is gone. That is what a
**tombstone** is: the shape of the row with none of the content, so the store can prove something was
removed without holding what was removed.

And here is the finding that makes this part a `production` part rather than a piece of advice. The
memory interface Sutra actually uses **has no delete method at all**. Not a deprecated one, not an
awkward one. There is no method on it whose purpose is to remove a memory. So this is not a case of
using the framework's erasure path carefully. There is no path, and the policy has to be one.

## Why Sutra needs it

Because Sutra's memory holds customer text, and Phase 14 makes this repository public. But more
immediately: because Day 46 wired in `InMemoryMemoryService` and Day 47 put a database behind the
session store, and between them Sutra now has customer data that survives a restart with nothing
anywhere that can remove one person's part of it.

The moment that becomes real is not a legal one. It is a customer emailing to say *"please delete what
you have about me"*, and somebody having to answer. Today the honest answer would be that the memory
store has no way to do it, and the only available action is to delete every memory for everyone.

You meet this again on Day 49, where an embedding index derives vectors from memo text. An erasure has
to reach that index too, and it can only do so if the vectors carry the holder — a decision made on the
day the index is built.

## The mechanism

First, the finding, read out of the installed library rather than assumed:

```python
# days/day-48-memory-design/lab/erase.py
from google.adk.memory import BaseMemoryService, InMemoryMemoryService

public = [name for name in dir(BaseMemoryService) if not name.startswith("_")]
removal = [name for name in public if any(w in name for w in ("delete", "remove", "forget"))]
```

**Line by line:**

- `dir(BaseMemoryService)` on the **class** rather than an instance, because `BaseMemoryService` is
  abstract and cannot be instantiated. Everything on it is the interface every implementation must
  satisfy.
- The `startswith("_")` filter removes private and dunder names, leaving the public contract — the
  methods a caller is meant to use.
- Searching for three different words rather than just `delete`, because a framework might reasonably
  call it `remove_memory` or `forget`. Checking one spelling and concluding a method is absent is the
  kind of shortcut that produces a confident wrong claim.
- This runs against the installed `google-adk==2.7.1` in `.venv`, so the result is a fact about the
  version Sutra actually pins rather than about documentation.

And the erasure itself, which is one branch and one helper:

```python
# days/day-48-memory-design/lab/policy.py
if memo.holder in erased_holders:
    verdicts.append(Verdict(memo, "erased", "the holder asked to be forgotten"))
elif memo.expires_on is not None and memo.expires_on < today:
    ...


def tombstone(memo: Memo) -> Memo:
    """What is left after an erasure: the shape of the row, with no content and no holder."""
    return replace(memo, holder="[ERASED]", subject="[ERASED]", text="[ERASED]", source="[ERASED]")
```

**Line by line:**

- The erasure check is the **first** branch of the chain, before expiry and before supersession. That
  ordering is the code saying which rule wins: a memo can be current, unexpired and the authoritative
  answer about its subject, and it still goes.
- `erased_holders` is a **set of holders**, not a set of memo identifiers. That makes the erasure a
  standing state rather than a one-off pass, which matters for the race in
  [4.2](4.2-you-cannot-delete-what-you-cannot-address.md): a session closing during an erasure writes
  new memos for that holder, and those are caught too because the state is still in force.
- It is a `frozenset` with a default of `frozenset()` in the signature. A mutable default would be
  shared between calls, and a shared mutable set of people to erase is a memorable bug.
- `replace(memo, ...)` is `dataclasses.replace`, which builds a **new** frozen record with those fields
  changed. It does not mutate, because `Memo` is frozen, so a tombstone cannot be mistaken for an
  edited original.
- `holder` is erased along with the text. That is the part people leave out, and it is the point: a
  tombstone that still names the person proves who asked to be forgotten, which is a record about them
  created by their request to have no records.
- What is **kept** is `kind`, `recorded_on` and `expires_on` — that something of this sort existed and
  when. That is enough to prove a deletion happened and not enough to say anything about anyone.

Read the method list. **Three ways to put things in and one way to get them out, and nothing to remove
anything.** `InMemoryMemoryService` adds nothing of its own, so the concrete implementation does not
quietly provide what the interface omits.

Verified against `https://adk.dev/sessions/memory/` on 2026-09-05: that page documents the same four
methods and no removal method of any kind, and it contains no mention of retention, expiry or
deletion. (`https://adk.dev/docs/sessions/memory/` returns **HTTP 404** — the `/docs/` prefix that
older material uses has moved.)

Note the `decision` memo in the middle of the tombstone list. Its row says `supersede=False` and
`keep_for_days=1095`, and it went anyway. That is the ordering doing its job.

## When it breaks

The first break is the one the run above documents: there is no method to call. A reasonable engineer
looks for one, does not find it, assumes they have misread the interface, and reaches for the
implementation's internals:

```python
service._session_events.pop((app_name, user_id), None)
```

That works today. It reaches into a private attribute of a class whose docstring says *"for prototyping
purpose only"*, it is keyed on the user who filed the session rather than the customer the memos are
about ([4.2](4.2-you-cannot-delete-what-you-cannot-address.md)), and it will break on an upgrade with
no deprecation warning because nothing promised it. It is also the only thing available, which is worth
saying honestly rather than pretending the framework has an answer.

The second break is an erasure that returns success and did not finish. Sutra's memory store is not the
only place a holder appears: there is the session store from Day 47, whatever logs exist from Day 22,
any backup, and Day 49's index. Erasing one and reporting success is worse than refusing, because the
customer now believes something untrue and stops asking.

The third break is the tombstone that is not a tombstone:

```text
  customer_fact acct-88     [ERASED]    recorded 2026-09-05
```

The text is gone and the holder is not. That store can now be queried for *"who has exercised an
erasure right?"* and it will answer. The request created a record about the person, which is the
outcome the request existed to prevent.

The fourth is the ordering, and it is a one-word bug. Put the expiry check first and a memo that is
both expired and erased reports `expired`. Everything ends up in the same place, so the store is
correct — but the audit trail now says a customer's data left because of housekeeping rather than
because they asked, and the evidence that the request was honoured has been overwritten by a more
boring explanation.

## In production

**What a professional writes instead:** an erasure **job** rather than a filter argument. A request
lands, is recorded with a timestamp, fans out across every store that holds the holder, and each store
reports rows removed. The standing state matters: `erased_holders` is a table, not a parameter, so that
writes arriving after the request are refused rather than stored and swept later.

Beside it goes the **certificate**: what was searched, what was found, what was removed, when, and a
completeness re-query showing zero. That is the artifact you produce when somebody asks whether it
happened, and producing it is the only reason the tombstones exist.

There is a real tension with [3.3](../03-expiry-and-supersession/3.3-a-verdict-is-not-an-erasure.md)
worth naming rather than smoothing over. Most systems soft-delete first and hard-delete later, because
an erasure caused by a bug is unrecoverable. A soft delete is not a deletion. The resolution is that
the delay is a written number in the policy with a `why`, and the customer is told it — not that the
delay is an implementation detail nobody mentions.

**What degrades at scale:** the fan-out, and specifically the derived data. Deleting rows from a table
is a solved problem. Removing one holder from an embedding index, a search index, a cache, a data
warehouse and last month's backup is not, and the honest answer for backups in most systems is that
they age out rather than being edited — which is a retention period you have to be able to state.

**The review comment a senior engineer leaves:** *"There is no delete in the memory interface, so we
are the delete. I want the erasure check first in the verdict chain, ahead of expiry, because if a
memo is both we need the audit trail to say the customer asked rather than that it timed out. And the
tombstone still carries the holder — take it out. Otherwise we have built a queryable list of everyone
who asked us to forget them."*

**The interview question:** *"A user asks you to delete everything you know about them. Walk me
through it."* The honest spoken answer: *"The first thing I would say is that the framework does not
help. I checked the memory interface we use and it has four public methods — three that add and one
that searches — and nothing that removes anything, and the documentation page confirms it. So erasure
is something the policy owns. In our design it is a standing set of erased holders rather than a
one-off pass, because a session closing during the request would otherwise write new memos for
somebody who has just been erased. It is checked first, before expiry and before supersession, and
that ordering is deliberate — a memo can be current, unexpired and the authoritative answer, and it
still goes, and the audit trail needs to say it went because they asked rather than because it timed
out. What is left behind is a tombstone with the kind and the date and nothing else, including no
holder. That last part gets missed a lot. A tombstone that still names the person is a queryable list
of everyone who asked to be forgotten."*
