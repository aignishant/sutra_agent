# 4.2 — You cannot delete what you cannot address

## One-line answer

Deleting one person's data is only possible if every stored item says whose it is, so the field that
looks like bookkeeping is the field the whole obligation rests on.

## The story

A box of photographs under a bed. Forty years of them, loose, face down, no writing on the back.

Somebody in one of those photographs asks you to take theirs out.

You cannot. Not because you refuse and not because it is hard work, but because the request has no
handle. You would have to look at every photograph, recognise a face across forty years of it
changing, and be sure — and at the end you would have a pile you *believe* is right and no way to
check it. You will miss some. You will also, with total certainty, pull out photographs of somebody
else's cousin who looks similar in one of them.

Now the same request against an album where somebody wrote the names underneath each picture when
they were stuck in. It takes an afternoon and it is exact. You can also *show* the person what you
removed, which is the part that makes them believe you.

The photographs are identical in both boxes. What differs is that somebody spent two seconds per
picture, decades earlier, on a job that had no visible benefit at the time.

## The idea in plain language

An erasure request is a query before it is a deletion.

*"Delete everything you hold about this person"* only means something if the store can answer *"what
do we hold about this person?"* — and that is a completely ordinary lookup **if** every item carries a
field naming who it is about, and impossible if they do not.

That field is `holder`. It is not who typed the message and it is not which session the memo came
from. It is the account or person the memo is **about**, and the distinction matters because those
three are often different: a support agent types a sentence, during a session opened by a colleague,
about a customer's billing arrangement. Only one of those three is the holder.

Two properties make the difference between an album and a box:

**Addressed, not searched.** `holder == "acct-88"` is exact. Searching text for the string `acct-88`
is a guess, and it is wrong in both directions at once — it finds conversations that merely *mention*
the account, and it misses conversations that are about it without naming it.

**One memo, one holder.** A memo about one thing, belonging to one person. Not a blob covering a whole
conversation in which several people appear, because a blob cannot be partly deleted. This is the
second reason for [1.3](../01-what-a-conversation-leaves/1.3-the-transcript-is-exhaust.md)'s rule
about transcripts: a transcript is a photograph with several people in it, and there is no way to
remove one of them.

The consequence is worth stating plainly, because it inverts how this usually gets planned. **Deletion
is not a feature you add later.** It is a property of the shape you chose when you designed the record,
and if the shape is wrong, adding deletion later means migrating every row you have.

## Why Sutra needs it

Because [4.3](4.3-erasure-is-an-obligation.md) says a memory system with no delete path is a
liability, and this part is what makes a delete path possible to write at all.

And because Day 46 wired in a memory service whose filing unit is a **session**, and a session is a
blob. Look at what `add_session_to_memory` actually stores, from the installed source:

```text
self._session_events[user_key][session.id] = [
    event
    for event in session.events
    if event.content and event.content.parts
]
```

The key is `(app_name, user_id)` and then a session id. That is one level of addressing — you can find
everything filed *under* a user. What you cannot do is find everything *about* a customer, because the
user who filed the session is the support agent, and the customer is a name inside the text.

For Sutra's support desk those are different people. Every single time.

## The mechanism

The two stores hold the same information. The question is whether it can be addressed.

```python
# days/day-48-memory-design/lab/address.py
BLOBS = [
    ("session-1", transcript()),
    (
        "session-2",
        "customer: We were told acct-88 had the same bounced-invoice problem last year.\n"
        "agent: I will check what was done for that account.",
    ),
]
```

**Line by line:**

- `session-1` is the ticket that is genuinely **about** `acct-88`, filed as one blob, exactly as
  `add_session_to_memory` files it.
- `session-2` is a different customer's conversation that happens to **mention** `acct-88`. This is not
  contrived: support agents reference other tickets constantly, and it is the case that makes
  string-searching for deletion unsafe rather than merely imprecise.
- The two are stored as `(name, text)` tuples rather than as objects with fields, because the whole
  point is that a blob store has no fields to key on. Giving them a `holder` attribute here would be
  smuggling in the answer.

Against the addressed version:

```python
memos, _ = what_to_keep(CANDIDATES, today=TODAY)
targets = [m for m in memos if m.holder == ERASE]
others = [m for m in memos if m.holder != ERASE]
```

**Line by line:**

- `m.holder == ERASE` is an equality test on a field. In a database that is one indexed `WHERE`
  clause, and it returns the same answer every time it is run.
- `targets` and `others` are computed as two comprehensions over one list, which is the same
  split-rather-than-filter shape as
  [2.2](../02-policy-as-data/2.2-every-verdict-names-its-row.md): the request needs to produce both
  what is going and what is staying, because somebody has to be shown the first list.
- There is no text matching anywhere. The customer's account identifier appears in a field, and
  whether it also appears in some memo's prose is irrelevant to the query.

```bash
cd days/day-48-memory-design/lab
uv run python address.py
uv run python address.py --keyed
cd -
```

**Line by line:**

- The bare run is the blob store. `--keyed` is the addressed store. Same customer, same erasure
  request, same underlying conversation.

Measured on 2026-09-05:

```text
store: session blobs
items held: 2
blobs containing the string 'acct-88': 1 -> ['session-2']

Delete both and you have erased another customer's ticket history.
Delete neither and you have not honoured the request.
Delete session-1 only and the mention in session-2 survives.
Nothing in this store says which blob is *about* acct-88 and which merely names it.
```

```text
store: addressed memos
items held: 5
items whose holder is acct-88: 5
items left after erasure: 0

The query is `holder == 'acct-88'`. It is exact, it is fast, and it is arguable.
```

Read the third line of the first block very carefully, because it is worse than it looks and it is
the real output of the run.

**The string search found `session-2`, and only `session-2`.** The conversation that is actually about
`acct-88` — the ten-turn ticket, the one holding the billing correction and the decision — does **not**
contain the string `acct-88` anywhere. Customers do not say their account numbers out loud; the system
knows which account a session belongs to and the text never mentions it.

So the naive deletion does exactly the wrong thing twice, in one pass. It deletes another customer's
conversation, and it leaves the target's conversation completely intact. Both errors, from one query,
with no warning.

## When it breaks

The break above is the important one and it has no error text, so here is the one that does. A store
where `holder` was added later, so some rows have it and some are `None`:

```traceback
Traceback (most recent call last):
  File "erase.py", line 31, in <listcomp>
    targets = [m for m in memos if m.holder.lower() == holder]
                                   ^^^^^^^^^^^^^^^
AttributeError: 'NoneType' object has no attribute 'lower'
```

That is a lucky failure. It is loud, it happens on the first erasure request, and it makes somebody
look. The unlucky version of the same situation is a plain `==` comparison, which does not raise — it
just silently never matches the rows with a missing holder, and those rows survive an erasure nobody
knows was incomplete.

The second break is the holder that is not stable. If `holder` is an email address and the customer
changes their email, memos written before the change are addressed to a person who no longer exists
under that name. An erasure request then honours half of them. The holder has to be an internal
identifier that never changes, and *the email itself* is a `customer_fact` about that identifier.

The third is a genuine tension rather than a bug. What about a memo that is about **two** people —
"the account was transferred from acct-88 to acct-91"? One `holder` field cannot express it, and
splitting it into two memos loses the relationship that was the whole content. The honest answer is
that this needs a decision recorded in the policy: either such memos are refused, or the field becomes
a list and every erasure removes one name from it rather than deleting the row. Both are defensible.
Neither happens by accident, and a system that has not chosen has chosen the first thing somebody
typed.

## In production

**What a professional writes instead:** the same field, indexed, plus a **registry of every store that
holds a holder-keyed row**. Memos are not the only place: there is a session store, a log store, an
analytics warehouse, a backup, and possibly a vector index by Day 49. An erasure request is a fan-out
across all of them, and the thing that makes it possible to get right is a written list of the stores,
not cleverness in any one of them.

Beside it goes the **completeness check**: after an erasure, re-run the query in every store and assert
zero rows. That is the only evidence you have that the deletion worked, and it is what you show when
somebody asks.

**What degrades at scale:** the derived copies. The memo store is easy — one indexed delete. The
embedding index built on Day 49 is not, because a vector is derived from text and does not carry the
holder unless somebody put it in the metadata. That is a decision made on the day the index is built,
and if it is made wrong the fix is a full re-index. Under concurrency there is a real race: a session
closing *during* an erasure writes new memos for a holder who has just been erased, so the erasure has
to be recorded as a standing state rather than as a one-off pass — which is exactly what the
`erased_holders` set in [4.3](4.3-erasure-is-an-obligation.md) is.

**The review comment a senior engineer leaves:** *"`holder` is nullable and half our fixtures leave it
out, which means an erasure request will silently skip those rows and we will tell a customer their
data is gone when it is not. Make it required at construction. And I want to see the list of stores
this identifier appears in written down somewhere that is not a person's head — deletion is a fan-out
and we will forget the analytics export."*

**The interview question:** *"How do you delete one user's data from an agent's memory?"* The honest
spoken answer: *"The deletion is easy. The addressing is the whole problem, and it is decided when you
choose the record shape rather than when the request arrives. If you file whole conversations as blobs
— which is what the default memory service does — you have nothing to key on, so you end up searching
text for an account identifier. I ran that on our desk and it failed in both directions at once: it
matched a *different* customer's ticket that referenced the account, and it missed the ten-turn
conversation that was actually about it, because customers never say their account number out loud. So
every memo carries a holder — who it is about, which is not who typed it and not whose session it was
— and erasure is one indexed equality query. The part I would push hardest in a design review is that
this is not a feature you add later. It is the shape of the row, and if the shape is wrong you are
migrating everything you have."*
