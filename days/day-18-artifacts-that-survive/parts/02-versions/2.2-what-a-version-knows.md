# 2.2 — What a version knows about itself

## One-line answer

Each version carries a record beside its bytes — the number, a canonical URI, a creation time, the
MIME type and **any custom metadata you pass at save time** — which is what turns a pile of versions
into something you can explain.

## The story

The pencil note inside the cover of a second-hand book.

The book is the same book either way. But somebody has written, in small handwriting on the flyleaf:
a name, a town, and a date in the nineteen-sixties. Under it, in different ink, a price and the word
*"Oxfam"*.

That is four lines and it changes the object. You now know roughly how it travelled, that somebody
owned it long enough to write in it, and what the shop thought it was worth. None of it is in the text
of the book, none of it was required, and the person who wrote the first line was not doing it for you.

## The idea in plain language

Saving an artifact stores more than the bytes. The base service defines an `ArtifactVersion` record,
and every version has one:

| Field | What it holds |
| --- | --- |
| `version` | the integer from [2.1](2.1-every-save-is-a-new-version.md) |
| `canonical_uri` | where this version's payload lives, in the store's own addressing |
| `create_time` | a Unix timestamp, set by the service |
| `mime_type` | the type from the `Blob` ([1.2](../01-not-a-state-key/1.2-a-part-not-a-file.md)) |
| `custom_metadata` | **anything you passed** at save time, as a dictionary |

Two service methods read them: `list_artifact_versions(filename)` returns every record, and
`get_artifact_version(filename, version=...)` returns one. Both are on the **service**, and there is
also a context-level `get_artifact_version` for tools.

The interesting field is the last one. `save_artifact` takes an optional `custom_metadata` dictionary,
and it is stored with the version rather than with the artifact — so two versions of the same file can
carry different notes about themselves. That is the flyleaf: *who wrote this version, and why*.

It is worth noticing what this makes possible, because it is the same shape as Day 17's audit trail
from a different direction. State's history tells you *when a fact changed*
([17.7.3](../../../day-17-state-scopes-and-lifetimes/parts/07-in-production/7.3-state-as-a-trace.md));
an artifact's version list tells you *what the document said at each of those moments, and why it was
rewritten*. Together they are a complete account of a decision.

`canonical_uri` is the other field worth understanding. It is the store's own address for the payload —
`memory://apps/...` for the in-memory service, a `file://` URL for the file service, a `gs://` URL for
cloud storage. It is not a public link and not something to hand a user; it is what a support engineer
follows to find the actual bytes, and what makes an artifact traceable across services.

## Why Sutra needs it

Because the question *"who rewrote the triage note, and why?"* is going to be asked, and the alternative
answer is a shrug.

The concrete design: Sutra's desk saves `triage-4521.md` with
`custom_metadata={"written_by": "desk", "reason": "first pass"}`, and when a human review rewrites it
the metadata says so. Two versions, two authors, two reasons, no extra table and no separate log — which
is exactly the property that makes the state-delta history worth its ceremony on Day 17.

It matters again on Day 62's human approval and Day 92's security review. Both need to know not just
what a document said but which version was seen by whom, and a version with no metadata cannot answer
the second half.

## The mechanism

Two versions of one note, each saved with a note about itself:

```python
# days/day-18-artifacts-that-survive/lab/version_metadata.py
"""What a version records about itself, beyond the bytes. Zero model calls."""

import asyncio
from datetime import datetime, timezone

from google.adk.artifacts import InMemoryArtifactService
from google.genai import types

APP, USER, SESSION = "sutra", "engineer_a", "s1"


def note(body: str) -> types.Part:
    return types.Part(inline_data=types.Blob(data=body.encode(), mime_type="text/markdown"))


async def main() -> None:
    service = InMemoryArtifactService()

    await service.save_artifact(
        app_name=APP,
        user_id=USER,
        session_id=SESSION,
        filename="triage-4521.md",
        artifact=note("severity: normal\n"),
        custom_metadata={"written_by": "desk", "reason": "first pass"},
    )
    await service.save_artifact(
        app_name=APP,
        user_id=USER,
        session_id=SESSION,
        filename="triage-4521.md",
        artifact=note("severity: high\n"),
        custom_metadata={"written_by": "human-review", "reason": "whole team affected"},
    )

    for record in await service.list_artifact_versions(
        app_name=APP, user_id=USER, session_id=SESSION, filename="triage-4521.md"
    ):
        when = datetime.fromtimestamp(record.create_time, tz=timezone.utc).isoformat(
            timespec="seconds"
        )
        print(f"v{record.version}  {when}  {record.mime_type}  {record.custom_metadata}")

    one = await service.get_artifact_version(
        app_name=APP, user_id=USER, session_id=SESSION, filename="triage-4521.md", version=1
    )
    print("canonical_uri:", one.canonical_uri)


asyncio.run(main())
```

**Line by line:**

- `custom_metadata={"written_by": ..., "reason": ...}` — two keys, chosen to answer the two questions
  somebody actually asks. It is a free-form dictionary: nothing validates it, which means a convention
  has to come from your code.
- The two saves carry **different** metadata for the same filename, which is the point: the record
  belongs to the version, not to the artifact.
- `list_artifact_versions(...)` — the metadata for every version, in order. Note that it returns
  records, not bytes: you can survey an artifact's history without loading a single payload, which
  matters when the payloads are large.
- `datetime.fromtimestamp(record.create_time, tz=timezone.utc)` — `create_time` is a Unix float, so
  rendering it in UTC is what makes two records comparable.
- `get_artifact_version(..., version=1)` — one record, fetched by number, and the only line here that
  prints a `canonical_uri`.

**Line by line:**

- No model, no key, no network.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
v0  2026-09-03T08:59:32+00:00  text/markdown  {'written_by': 'desk', 'reason': 'first pass'}
v1  2026-09-03T08:59:32+00:00  text/markdown  {'written_by': 'human-review', 'reason': 'whole team affected'}
canonical_uri: memory://apps/sutra/users/engineer_a/sessions/s1/artifacts/triage-4521.md/versions/1
```

Two lines that read like a changelog, produced by the store rather than written by you. The timestamps
are identical because both saves happen in the same instant in a script; in a real conversation they
are minutes apart, and the gap is often the interesting part.

Read the `canonical_uri` as a map of the store's addressing: app, then user, then **session**, then the
artifact name, then the version. [3.2](../03-two-scopes/3.2-where-it-actually-lives.md) shows the same
path on a real filesystem, and it is where the `session` segment disappears for user-scoped artifacts.

## When it breaks

**`AttributeError: 'NoneType' object has no attribute 'custom_metadata'`**

`get_artifact_version` returns `None` for a version that does not exist, exactly as `load_artifact`
does ([2.1](2.1-every-save-is-a-new-version.md)). The same guard applies.

**The metadata is empty on every version.** No error, and the failure is that nobody added any. Saving
without `custom_metadata` stores `{}`, which is a perfectly valid record with nothing to say. This is
the artifact equivalent of Day 17's `author="user"` problem
([17.3.3](../../../day-17-state-scopes-and-lifetimes/parts/03-three-safe-writes/3.3-writing-from-outside-a-run.md)):
the field exists, it costs nothing to fill in, and the day you want it is not the day you can add it
retroactively.

**Something confidential ends up in the metadata.** No error, and it is stored beside the artifact for
as long as the artifact lives — including in `metadata.json` on disk with the file service
([3.2](../03-two-scopes/3.2-where-it-actually-lives.md)). Metadata is not a scratch pad; the same
rules apply as for state
([17.7.2](../../../day-17-state-scopes-and-lifetimes/parts/07-in-production/7.2-what-belongs-in-state.md)).

## In production

**Write the metadata as a small, fixed schema, and set it at every save.**

The version a professional writes has a helper — one function that saves an artifact and requires the
same three or four keys every time: who produced it, why, and what it was derived from. Free-form
dictionaries decay quickly when several components write them, and this one is worth pinning because
it is what somebody reads under pressure.

**What changes at scale** is that `custom_metadata` becomes the index. Once there are thousands of
artifacts, *"show me every note a human rewrote"* is a query, and the field it queries is this one.
Storage systems with a metadata layer let you filter on it; the in-memory service does not, so the
convention matters more than the capability today.

**What fails only under real traffic** is trusting `create_time` as an ordering key. Timestamps come
from the machine that saved, and two versions written in the same second are indistinguishable by time
— which is exactly what the measurement above shows. The version integer is the ordering; the timestamp
is context.

**The review comment**: *"this saves a new version with no metadata. Six months from now, which
component wrote it and why?"*

**The interview question**: *"how do you know which version of a generated document a user actually
approved?"* The answer that shows the design: *"the artifact store versions every save and records who
wrote each one; the approval stores the filename **and the version number**, because the newest is not
the same thing as the approved."*
