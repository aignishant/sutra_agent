# 3.2 — Where it actually lives

## One-line answer

`FileArtifactService` writes a directory tree you can read with `ls` — app, user, then either a session
or nothing, then the filename, then a numbered version folder holding the bytes and a `metadata.json` —
and the filename you pass becomes part of that path, which is why it is validated.

## The story

The filing drawers at the garage.

Two banks of them behind the counter. The left-hand bank is one folder per customer: the registration
document, the last MOT certificate, the note about which key opens the fuel cap. The right-hand bank is
one folder per job: the estimate, the parts list, the photograph of the sill somebody sent from their
phone.

Nobody in the workshop has ever had to be told which drawer to open, because the arrangement matches
how they think. The customer's things are with the customer. The job's things are with the job. And
when a job is finished and the folder is closed, the customer's folder is untouched — which is why the
next time they come in, the person at the counter already knows about the fuel cap.

## The idea in plain language

[3.1](3.1-the-user-filename.md) showed the two scopes behaving differently. This part is what they
actually are, and the file service is the honest way to see it, because you can look.

`FileArtifactService(root_dir=...)` writes this layout — documented in a comment at the top of the
installed source and measured below:

```text
root/
└── apps/{app_name}/
    └── users/{user_id}/
        ├── artifacts/{filename}/versions/{n}/       ← user-scoped
        │       ├── {filename}
        │       └── metadata.json
        └── sessions/{session_id}/
            └── artifacts/{filename}/versions/{n}/   ← session-scoped
                    ├── {filename}
                    └── metadata.json
```

Four things follow from that picture, and all four are visible in the measurement.

**The `user:` prefix is not part of the path.** `user:signature.txt` is stored as
`users/engineer_a/artifacts/signature.txt/...`, with the prefix stripped, because the prefix *was* the
routing instruction and the directory already encodes it. Exactly the shape Day 17's state stores use
([17.2.3](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.3-where-user-and-app-live.md)).

**Each version is a directory, not a file.** Inside it are the bytes under their original filename and a
`metadata.json` holding the record from [2.2](../02-versions/2.2-what-a-version-knows.md), in camelCase.

**The filename becomes a path.** `sub/dir/report.md` creates nested directories, which is a feature —
and means the filename is being interpreted rather than merely stored.

**Which is why it is validated.** A filename containing `..` is rejected with an
`InputValidationError`, because a filename that walks upwards would write outside the root. The source
comment says so directly: *"path traversal is rejected to keep the layout portable across
filesystems."*

The in-memory and cloud services use the same addressing, which you can read in the `canonical_uri`
from [2.2](../02-versions/2.2-what-a-version-knows.md): `memory://apps/…/sessions/…/artifacts/…` is the
same tree without the disk.

## Why Sutra needs it

Because Phase 3's gate is *state survives restarts*, and this is the artifact half of the answer at
zero cost.

The file service is the reason Sutra does not have to park durable artifacts along with the cloud
storage option ([1.3](../01-not-a-state-key/1.3-a-separate-wire.md)). A directory in the repository —
gitignored, like the session store — gives Sutra artifacts that outlive the process, which is what
[6.3](../06-in-production/6.3-surviving-a-restart.md) demonstrates and what Day 47 will pair with a
database-backed session service.

There is a second reason, and it is the one that matters on Day 66. The filename is user-influenced the
moment a customer attaches a file, and here you can see exactly what a filename *does*: it becomes a
path on your disk. The framework's validation covers the obvious attack; knowing what it is protecting
is what lets you decide whether it covers yours.

## The mechanism

Two saves, then the tree they produced, then two filenames that test the rules:

```python
# days/day-18-artifacts-that-survive/lab/on_disk.py
"""Where a file service actually puts the bytes, and what it refuses. Zero model calls."""

import asyncio
import json
import shutil
from pathlib import Path

from google.adk.artifacts import FileArtifactService
from google.genai import types

ROOT = Path("artifact_store")


def blob(text: str, mime: str) -> types.Part:
    return types.Part(inline_data=types.Blob(data=text.encode(), mime_type=mime))


async def main() -> None:
    if ROOT.exists():
        shutil.rmtree(ROOT)
    service = FileArtifactService(root_dir=ROOT)

    await service.save_artifact(
        app_name="sutra",
        user_id="engineer_a",
        session_id="ticket-4521",
        filename="triage-4521.md",
        artifact=blob("severity: high\n", "text/markdown"),
    )
    await service.save_artifact(
        app_name="sutra",
        user_id="engineer_a",
        session_id="ticket-4521",
        filename="user:signature.txt",
        artifact=blob("Kind regards", "text/plain"),
    )

    print("the tree the service wrote:")
    for path in sorted(p for p in ROOT.rglob("*") if p.is_file()):
        print("  ", path.relative_to(ROOT).as_posix())

    meta = json.loads(
        (
            ROOT
            / "apps/sutra/users/engineer_a/sessions/ticket-4521/artifacts"
            / "triage-4521.md/versions/0/metadata.json"
        ).read_text()
    )
    print("metadata.json keys:", sorted(meta))
    print("mimeType          :", meta["mimeType"])

    for name in ("../../escape.txt", "sub/dir/report.md"):
        try:
            version = await service.save_artifact(
                app_name="sutra",
                user_id="engineer_a",
                session_id="ticket-4521",
                filename=name,
                artifact=blob("x", "text/plain"),
            )
            print(f"{name!r} -> saved as version {version}")
        except Exception as error:  # noqa: BLE001 - the point is which error
            print(f"{name!r} -> {type(error).__name__}: {error}")


asyncio.run(main())
```

**Line by line:**

- `shutil.rmtree(ROOT)` at the start — the script is destructive on its own directory so it can be run
  repeatedly and mean the same thing. Point it at a directory you own.
- `FileArtifactService(root_dir=ROOT)` — the constructor creates the directory if it is missing and
  resolves the path, so a relative root is resolved against the working directory.
- Two saves, one of each scope, into the same session, as in [3.1](3.1-the-user-filename.md).
- `ROOT.rglob("*")` filtered to files — printing the tree is the measurement. There is no API for
  "where did you put it"; the filesystem is the API.
- The `metadata.json` read — deliberately by hand, with `json.loads`, to show the record is a plain
  file rather than something only the service can read.
- The last loop tries a **traversing** filename and a **nested** one, catching whatever comes back so
  both results appear in one output. The broad `except` is a measurement, with the reason written next
  to it, as in
  [16.5.1](../../../day-16-built-in-tools-with-brakes/parts/05-code-that-runs/5.1-an-executor-is-not-a-tool.md).

**Line by line:**

- The second command is the point of the whole part: the store is a directory, so the ordinary tools
  work on it.
- No model, no key, no network.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
the tree the service wrote:
   apps/sutra/users/engineer_a/artifacts/signature.txt/versions/0/metadata.json
   apps/sutra/users/engineer_a/artifacts/signature.txt/versions/0/signature.txt
   apps/sutra/users/engineer_a/sessions/ticket-4521/artifacts/triage-4521.md/versions/0/metadata.json
   apps/sutra/users/engineer_a/sessions/ticket-4521/artifacts/triage-4521.md/versions/0/triage-4521.md
metadata.json keys: ['canonicalUri', 'createTime', 'customMetadata', 'fileName', 'mimeType', 'version']
mimeType          : text/markdown
'../../escape.txt' -> InputValidationError: Artifact filename '../../escape.txt' must not contain parent traversal.
'sub/dir/report.md' -> saved as version 0
```

Read the first two paths against the second two. The user-scoped artifact sits directly under the
user, with **`user:` gone from its name**; the session-scoped one sits under a session directory. Two
drawers, exactly as the story has them.

Then the last two lines: a filename that tries to climb out of the root is refused by name, and a
filename with slashes in it is accepted and becomes directories. Both of those are decisions somebody
made about what a filename is allowed to be, and both matter the moment a filename comes from outside.

## When it breaks

**`InputValidationError: Artifact filename '../../escape.txt' must not contain parent traversal.`**

The framework's guard, verbatim. It fires on the way in, before anything is written. Notice what it
does **not** cover: slashes are fine, so a user-supplied name can still create directories in your
store, and there is nothing here about length, about reserved names on Windows, or about a filename
that collides with an existing one.

**`FileNotFoundError: [Errno 2] No such file or directory: 'C:\\…\\versions\\0\\triage-4521.md'`**

Measured on 2026-09-03, on Windows, with the store under a deep temporary directory. The layout is six
levels deep **before** your filename, so a long root plus a long filename crosses the classic Windows
path limit and the write fails at the last step, with an error that looks like a bug in the service and
is not. Keep the root short, or enable long paths. It is exactly the sort of thing that works on one
developer's machine and not another's.

**The store is in the repository and gets committed.** No error, and an embarrassing one: a directory
of customer attachments in git history. The artifact root belongs in `.gitignore` the moment it exists,
next to the session store — this is Principle 9's neighbourhood, and today's checklist has a box for
it.

## In production

**Treat the artifact root as storage, not as part of the code.**

The version a professional writes puts the root in configuration, not in a constant next to the agent:
a directory on a mounted volume in a container, a bucket in the cloud, a temporary directory in tests.
Nothing else in the system should know where artifacts live, which is what makes
[1.3](../01-not-a-state-key/1.3-a-separate-wire.md)'s swap a one-line change.

**What changes at scale** is that the tree becomes an operational object: it needs a backup policy, a
disk that does not fill, and a deletion story that matches your retention rules
([2.3](../02-versions/2.3-nothing-is-overwritten.md)). It is also the thing an auditor asks to see, and
the fact that it is a plain directory with plain JSON beside each file is a genuine advantage there.

**What fails only under real traffic** is the filename. Real names arrive with spaces, non-ASCII
characters, several dots, hundreds of characters, and occasionally a slash somebody meant literally.
The service normalises what it can and rejects the traversal case; everything else is yours. The
defence is not to sanitise a user's filename into a path — it is to **generate** the storage name
yourself and keep the user's name in metadata
([2.2](../02-versions/2.2-what-a-version-knows.md)), where it cannot become a directory.

**The review comment**: *"this passes the customer's filename straight to `save_artifact`. That name
becomes a path in our store — generate the name and keep theirs in metadata."*

**The interview question**: *"where do your agent's artifacts physically live?"* The answer that shows
you have looked: *"a tree keyed by app, user and then either session or user scope, with one directory
per version holding the bytes and a metadata file — and the filename I pass becomes part of that path,
so it is validated and I do not hand it a name a customer chose."*
