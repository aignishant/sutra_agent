# 6.2 — What belongs in an artifact

## One-line answer

Artifacts are for **bytes somebody would want back**: a file a person uploaded, a document Sutra
produced, an output worth keeping — not scratch data, not secrets, and not anything whose only reader
is the next line of your own code.

## The story

The kitchen bin and the recycling.

Two containers, one decision, made forty times a day without thinking. The card sleeve goes in one, the
foil tray goes in the other, and the thing that makes it automatic is not knowing the rules — it is that
the containers are different shapes and stand in different places.

The households that get it wrong are not careless. They are the ones where somebody put a second bin
in a cupboard "for now", and after a month nobody could say what went in which. The rule survived; the
*shape* that made it obvious did not.

## The idea in plain language

Sutra now has four places a piece of information can live, and this part completes the map that
[17.7.2](../../../day-17-state-scopes-and-lifetimes/parts/07-in-production/7.2-what-belongs-in-state.md)
started:

| Where | For | Example | Cost of getting it wrong |
| --- | --- | --- | --- |
| the transcript | what was said | the customer's wording | tokens on every turn |
| state | small structured facts | `severity`, `note_file` | a session that grows and slows |
| **artifacts** | **bytes somebody wants back** | the uploaded log, the triage note | storage that grows for ever |
| the environment | secrets | `GOOGLE_API_KEY` | a credential with a long life |

Four questions decide where a thing goes, in this order:

1. **Is it a secret?** Environment. Not state, not an artifact, not metadata
   ([2.2](../02-versions/2.2-what-a-version-knows.md) is a real store too).
2. **Is it bytes?** Then it is an artifact or it is nothing. Never a base64 string in a state key.
3. **Will code branch on it?** Then a *fact about* it goes in state — the filename, the version, the
   size — even if the bytes go in the store.
4. **Would anybody want it back?** If no, do not save it at all. This is the question people skip, and
   it is the one that keeps the store small.

That fourth question deserves its own sentence, because artifacts have no `temp:` scope. State has a
prefix that means *this is scratch and will be shredded*
([17.2.4](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.4-why-temp-exists.md)).
Artifacts do not. Every save is permanent until somebody deletes it
([2.3](../02-versions/2.3-nothing-is-overwritten.md)), so the discipline that `temp:` provides
automatically for state must be provided by **judgement** here.

And one rule that comes from the store's shape rather than from taste: **the filename is not a place to
put information you care about.** It becomes a path ([3.2](../03-two-scopes/3.2-where-it-actually-lives.md)),
it is the artifact's identity, and it is the one field that gets truncated, sanitised and collided.
Descriptions, authorship and provenance go in `custom_metadata`
([2.2](../02-versions/2.2-what-a-version-knows.md)); the filename says what the thing is and which
entity it belongs to, and nothing else.

## Why Sutra needs it

Because Sutra's artifacts are about to arrive from two directions with two different risk profiles.

**Files Sutra produces** — the triage note, later a generated report — are small, predictable and safe.
The discipline for them is question four: save on change, not on turn, or the store fills with
identical versions ([2.3](../02-versions/2.3-nothing-is-overwritten.md)).

**Files customers attach** are none of those things. The size is theirs, the type is a claim
([1.2](../01-not-a-state-key/1.2-a-part-not-a-file.md)), the filename is user-supplied
([3.2](../03-two-scopes/3.2-where-it-actually-lives.md)) and the contents are untrusted text that will
end up in a model's context if anything loads it
([4.3](../04-in-the-run/4.3-what-the-model-cannot-see.md)). Every one of those is a Day 66 concern
arriving early, through the door marked *attachments*.

## The mechanism

The map, written where files are created — the module the build brief asks for:

```python
# sutra/artifacts.py - the header a reviewer reads first
"""Sutra's files: the names, their scopes, and the two tools that write and read them.

Scopes (day 18, part 3.1) are chosen by the filename:
    triage-4521.md      -> this conversation only
    user:signature.txt  -> this engineer, every conversation

Bytes live here; the *reference* lives in session state (day 17), because state is
on the critical path of every turn and files are not. Never build a filename from
text a customer supplied - it becomes a path in the store (3.2).
"""

NOTE_MIME = "text/markdown"
SIGNATURE = "user:signature.txt"  # user-scoped: follows the engineer
NOTE_FILE = "note_file"  # state key: which artifact holds the current note
NOTE_VERSION = "note_version"  # state key: which version of it


def note_filename(ticket_id: int) -> str:
    """The artifact name for one ticket's triage note.

    Derived from an identifier Sutra owns, never from user-supplied text.
    """
    return f"triage-{int(ticket_id)}.md"
```

**Line by line:**

- The docstring states the **scope rule**, the **division between the two stores**, and the **one
  prohibition**, because this is the file somebody opens when they want to add an artifact.
- `NOTE_MIME` as a constant — so the type is set in one place and cannot be forgotten at a call site
  ([1.2](../01-not-a-state-key/1.2-a-part-not-a-file.md)).
- `SIGNATURE` carries its `user:` prefix **in the constant**, with the scope in a comment. Exactly the
  convention Day 17 used for state keys, for the same reason: the prefix is the behaviour.
- `NOTE_FILE` and `NOTE_VERSION` are **state** keys living in the artifacts module, deliberately. They
  are the reference to the file, so they belong with the file's definition rather than with the
  unrelated state keys.
- `def note_filename(ticket_id: int) -> str` — a function, not an f-string at the call site, so there
  is exactly one place that knows how a note is named
  ([4.1](../04-in-the-run/4.1-saving-from-a-tool.md) and
  [6.1](6.1-testing-artifacts-without-a-model.md) both depend on that).
- `int(ticket_id)` — the conversion, at the boundary, because ticket ids arrive as strings from email
  subjects and a filename built from `"4521 "` is a different filename.
- The docstring's last sentence is the review rule: it is there so that the person adding attachment
  support reads it before writing `save_artifact(filename=upload.name, ...)`.

There is no output block for this part, because it is a module rather than a script. Its behaviour is
asserted in [6.1](6.1-testing-artifacts-without-a-model.md).

## When it breaks

**The base64 string in a state key.**

```text
TypeError: Object of type bytes is not JSON serializable
```

The honest version of the mistake fails at Day 47 with that message
([17.1.2](../../../day-17-state-scopes-and-lifetimes/parts/01-form-not-story/1.2-what-may-live-in-state.md)).
The dishonest version — base64-encoding first — does **not** fail: it serialises perfectly, and the
session then carries the file on every turn for ever. No error, a slow conversation, and a bill.

**The store that fills with drafts.** No error either. A tool that saves on every turn produces one
version per turn ([2.3](../02-versions/2.3-nothing-is-overwritten.md)), and nothing prunes. This is
question four, unasked.

**The filename that carried the information.** `report-high-2026-09-03-final.md` looks helpful and is
three facts encoded in an identity. Renaming it later breaks every reference; parsing it later is a
regular expression over your own store; and the same three facts in `custom_metadata` are queryable and
harmless.

**The attachment nobody looked at.** A customer's file, saved with their filename, their MIME type and
their bytes, then loaded into a model's context by `load_artifacts`
([4.3](../04-in-the-run/4.3-what-the-model-cannot-see.md)). Every part of that chain is a decision, and
saving it under a name you generated is the cheapest of them to get right.

## In production

**Decide at the moment of saving, and write the decision down in the module.**

The version a professional ships has what the header above has: the scope convention, the split between
stores, the naming function, and the prohibition. Fifteen lines, and they answer the questions that
otherwise get answered differently by three people in one sprint.

**What changes at scale** is that artifacts become the store with real compliance weight. They contain
customer files; they persist; they are exactly what a data-deletion request is about. A system whose
artifact names are derived from identifiers it owns can answer *"delete everything for this ticket"* in
one line; one whose names came from users cannot enumerate them without a scan.

**What fails only under real traffic** is the assumption that a file is what it says it is. Type,
size and name are all attacker-controlled for anything uploaded. The defences are boring and effective:
generate the storage name, cap the size, verify the type before acting on it, and keep the user's
original name in metadata where it is data rather than a path.

**The review comment**: *"this saves the upload under `upload.filename`. Generate the name from the
ticket and keep theirs in `custom_metadata` — that string becomes a directory in our store."*

**The interview question**: *"what would you not put in an artifact store?"* The answer that shows
judgement: *"secrets, obviously. Beyond that: anything nobody would ask for again — the store has no
scratch scope, so every save is permanent until something deletes it — and anything whose only reader
is the next line of code, which is a state key, not a file."*
