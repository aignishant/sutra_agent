# 6.1 — Testing artifacts without a model

## One-line answer

Seven assertions, no key and no network — versioning, the two scopes, the `None` cases, delete
semantics, the tool's two deltas, the derived filename, and **durability across a fresh service** —
which is the one place Phase 3's gate can actually be proved today.

## The story

Weighing the suitcase at home.

The bathroom scales are not the airline's scales, and everybody knows it. You weigh yourself, then
weigh yourself holding the case, and subtract. It is a couple of minutes and it is approximate.

It is also the difference between a calm morning and repacking on the floor at the check-in desk in
front of a queue. The test does not have to be the real one. It has to be good enough to catch the case
that is four kilos over, at a moment when the fix is free.

## The idea in plain language

Artifacts are unusually pleasant to test, for the same reason state was
([17.7.1](../../../day-17-state-scopes-and-lifetimes/parts/07-in-production/7.1-testing-state-without-a-model.md)):
the store is a data structure with rules, and none of the rules involve a model.

Seven claims, seven tests:

| The claim | Where it came from |
| --- | --- |
| the note's filename is derived from the ticket id | [3.2](../03-two-scopes/3.2-where-it-actually-lives.md) |
| saving twice versions rather than replaces | [2.1](../02-versions/2.1-every-save-is-a-new-version.md) |
| a missing artifact is `None`, not an error | [2.1](../02-versions/2.1-every-save-is-a-new-version.md) |
| the `user:` prefix crosses conversations | [3.1](../03-two-scopes/3.1-the-user-filename.md) |
| delete takes every version, and numbering restarts | [2.3](../02-versions/2.3-nothing-is-overwritten.md) |
| the tool writes the file **and** the reference | [4.1](../04-in-the-run/4.1-saving-from-a-tool.md) |
| a file service survives a fresh service object | [6.3](6.3-surviving-a-restart.md) |

The last one is worth pausing on. Yesterday's suite had to **skip** the durability test, because an
in-memory session service cannot survive anything and `DatabaseSessionService` is Day 47's. Artifacts
are different: `FileArtifactService` is available now, so the artifact half of *state survives
restarts* is provable today, with `tmp_path` and two service objects. That test is not a placeholder —
it is the first green assertion in this repository that anything survives a process.

## Why Sutra needs it

Because artifacts are the store where a mistake is expensive and invisible: a wrong scope leaks a
document between conversations, a missing reference orphans a file, and a store that does not persist
loses work that a user believes was saved.

None of those is caught by an integration test that checks a reply came back. All of them are caught by
seven assertions that run in a second.

There is a Phase 3 reason as well. The gate is *state survives restarts; budgets enforced*, and today
supplies half of the first clause with a test rather than a promise.

## The mechanism

One new file. It imports `sutra/artifacts.py`, which is today's build, so **it is red until you write
that module**. The whole file is long enough that the hub's build brief lists what it needs; here are
the three tests that carry the day's findings, and the rest follow the same shape.

```python
# tests/test_artifacts.py  (three of the seven; the others are in the build brief)
"""Day 18 - what can be asserted about artifacts without a model."""

from __future__ import annotations

import asyncio

from google.adk.artifacts import FileArtifactService, InMemoryArtifactService
from google.genai import types

from sutra.artifacts import NOTE_MIME, SIGNATURE, note_filename

APP, USER, SESSION = "sutra", "engineer_a", "ticket-4521"
BODY = "# Triage 4521\nseverity: high\n"


def _blob(body: str) -> types.Part:
    return types.Part(inline_data=types.Blob(data=body.encode(), mime_type=NOTE_MIME))


def test_the_note_filename_comes_from_the_ticket() -> None:
    """3.2: a filename becomes a path, so it is derived and never supplied."""
    assert note_filename(4521) == "triage-4521.md"
    assert note_filename("4521") == "triage-4521.md"


def test_the_user_prefix_crosses_conversations() -> None:
    """3.1: the filename chooses the scope."""
    service = InMemoryArtifactService()
    asyncio.run(
        service.save_artifact(
            app_name=APP,
            user_id=USER,
            session_id=SESSION,
            filename="triage-4521.md",
            artifact=_blob(BODY),
        )
    )
    asyncio.run(
        service.save_artifact(
            app_name=APP,
            user_id=USER,
            session_id=SESSION,
            filename=SIGNATURE,
            artifact=_blob("regards"),
        )
    )
    elsewhere = asyncio.run(
        service.list_artifact_keys(app_name=APP, user_id=USER, session_id="ticket-4598")
    )
    assert elsewhere == [SIGNATURE]


def test_a_file_service_survives_a_new_process(tmp_path) -> None:
    """6.3: Phase 3's gate, for the half of it that is files."""
    first = FileArtifactService(root_dir=tmp_path / "artifacts")
    asyncio.run(
        first.save_artifact(
            app_name=APP,
            user_id=USER,
            session_id=SESSION,
            filename="triage-4521.md",
            artifact=_blob(BODY),
        )
    )
    del first
    second = FileArtifactService(root_dir=tmp_path / "artifacts")
    back = asyncio.run(
        second.load_artifact(
            app_name=APP, user_id=USER, session_id=SESSION, filename="triage-4521.md"
        )
    )
    assert back.inline_data.data.decode() == BODY
```

**Line by line:**

- `note_filename("4521")` in the first test — passing a **string** where an int is documented, because
  real ticket ids arrive from email subjects as strings. The module's `int()` is what makes both
  assertions pass, and it is the same lesson as Day 17's `ticket_id`
  ([17.5.2](../../../day-17-state-scopes-and-lifetimes/parts/05-a-schema-for-state/5.2-what-the-schema-does-not-do.md)).
- `assert elsewhere == [SIGNATURE]` — an **exact list**, and against the constant rather than a
  literal, so changing the constant's prefix is what the test measures.
- `asyncio.run(...)` around each service call — the services are async and the tests are synchronous,
  the same choice as yesterday's suite.
- `tmp_path` — pytest's per-test temporary directory. It is what makes the durability test hermetic:
  the store is created, used and discarded, and no test can see another's files.
- `del first` then a **new** `FileArtifactService` on the same root — the closest honest approximation
  of a restart inside one process. Nothing is shared between the two objects except the directory.
- `back.inline_data.data.decode()` — reading the bytes and turning them back into text, which is the
  round trip that actually matters.

Then break each thing on purpose. These were **measured**, each applied on its own to a green suite, on
2026-09-03:

| Break this | Which tests go red | What it is telling you |
| --- | --- | --- |
| `SIGNATURE = "signature.txt"` (drop `user:`) | 1 — the scope test | the filename chooses the scope (3.1) |
| delete the two `state[...]` writes in `save_note` | 1 — the reference test | an artifact nobody can find (4.1) |
| `note_filename` returns a name with no `.md` | 2 — the filename test and the reference test | the name is an interface (3.2, 4.1) |

The third row is the one to read twice: **two** tests fail, because a filename is used in two places —
where it is built and where it is recorded — and that is exactly the coupling you want a test to notice.

## When it breaks

**The first run fails at collection, and it should.**

```text
ModuleNotFoundError: No module named 'sutra.artifacts'
```

**A test leaves files behind.** Using a fixed directory instead of `tmp_path` writes into the
repository, and the second run of the suite then sees the first run's artifacts — so a test passes for
the wrong reason and fails when run alone. `tmp_path` per test, always, and the artifact root in
`.gitignore` ([3.2](../03-two-scopes/3.2-where-it-actually-lives.md)).

**`FileNotFoundError` deep in the file service on Windows.** The layout is six directories deep before
your filename ([3.2](../03-two-scopes/3.2-where-it-actually-lives.md)), and `tmp_path` on Windows is
already long, so a long filename in a durability test can cross the path limit. Keep test filenames
short; it is a real constraint rather than a curiosity.

**The tests pass and production has no artifact service.** Nothing in this file asserts the wiring,
which is [5.1](../05-failure-lab/5.1-the-artifact-with-no-service.md)'s failure. The two-line test for
that belongs beside these — assert that the application's runner factory produces a runner whose
`artifact_service` is not `None` — and it is in the hub's `TODO(me)` list because Sutra does not have a
runner factory yet.

## In production

**Test the store's rules once, and your use of them everywhere.**

Same division as yesterday: versioning, scopes and delete semantics are the framework's behaviour, and
one test each pins the version you are on and notices an upgrade that changes it. The filename rule and
the save-and-record pattern are *yours*, and they deserve a test per fact because that is where a change
actually breaks something.

**What changes at scale** is that the durability test becomes a contract test across implementations.
The same assertions run against the file service and, later, against whatever a deployment uses — and
they are the cheapest possible smoke test that a storage backend is actually configured, which is a
thing that goes wrong on the day of a deploy rather than the day of a commit.

**What fails only under real traffic** is everything about size and concurrency: a 50-megabyte upload,
two writers on one filename, a disk that fills. Those are load tests rather than unit tests, and their
absence is a decision worth stating rather than an oversight.

**The review comment**: *"this test writes to a fixed directory. Use `tmp_path`, or the second run will
be reading the first run's files."*

**The interview question**: *"how do you test file handling in an agent?"* The answer that shows you
have done it: *"the store is a data structure — versioning, scopes and deletes are assertable in
milliseconds with no model. And the one test worth having beyond that is durability: save with one
service object, throw it away, and read with a new one."*
