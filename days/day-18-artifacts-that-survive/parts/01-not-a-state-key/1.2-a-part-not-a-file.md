# 1.2 — A Part, not a file

## One-line answer

An artifact is a `types.Part` carrying `inline_data` — bytes plus a **MIME type** — which is the same
class the model's own content is made of, and the MIME type is optional in the code and required in
practice.

## The story

The memory stick in the drawer.

There are three of them in there, none labelled. One is definitely the photos from the wedding, one
might be a work backup from a job you left, and one has been in the drawer so long it might be
somebody else's.

The bytes on them are perfect. Nothing has decayed and nothing is corrupt. The information that is
missing is not *in* the files — it is the sentence somebody did not write on the outside, and without
it the only way to find out what you are holding is to plug each one in and look.

The label is not decoration on the data. It is part of what makes the data usable.

## The idea in plain language

An artifact's payload is a `google.genai.types.Part`. That is worth pausing on, because it is the same
`Part` that shows up everywhere else in this curriculum: the model's text comes back in `Part`s
([Day 5](../../../day-05-first-adk-agent/LESSON.md)), a tool call is a `Part`, the program a model
writes and the sandbox's output are `Part`s
([Day 16](../../../day-16-built-in-tools-with-brakes/parts/05-code-that-runs/5.3-reading-the-code-and-its-output.md)).
ADK did not invent a file type; it reused the content type.

For an artifact, the field that matters is `inline_data`, a `Blob` with two fields:

- **`data`** — the bytes. Not a string, not a path: `bytes`. You encode text yourself.
- **`mime_type`** — what kind of bytes: `text/markdown`, `image/png`, `application/pdf`.

Two conveniences worth knowing, both in the installed source:

- `save_artifact` accepts a **plain dictionary** as well as a `Part`. A helper called `ensure_part`
  normalises it — and it accepts both `inline_data` and the camelCase `inlineData`, because the same
  data crosses HTTP in that form.
- A `Part` can hold `file_data` instead of `inline_data`, meaning *the bytes live somewhere else and
  this is a reference*. The base service's docstring says the service then "assumes its content has
  been uploaded separately". Sutra does not use that path — it needs infrastructure Sutra does not have
  — but it explains why the payload is a `Part` rather than a `bytes`: the type can describe a
  reference as well as a payload.

And the thing that is easy to get wrong: **`mime_type` is optional**. Save without it and the artifact
is stored happily, with `mime_type=None`, which is a memory stick with no label. Nothing downstream can
decide whether to render it, whether it is safe to show a model
([4.3](../04-in-the-run/4.3-what-the-model-cannot-see.md)), or what to call it when a person downloads
it.

## Why Sutra needs it

Because the first artifact Sutra saves is a Markdown note and the second is whatever a customer
attached, and those two need to be told apart by something other than a guess about the filename.

The concrete case is [4.3](../04-in-the-run/4.3-what-the-model-cannot-see.md). When an artifact is
loaded into a model's context, ADK's own safety conversion looks at what kind of thing it is — it
extracts text from some formats and replaces binary data with a placeholder description for others.
That decision runs on the MIME type. An artifact saved without one is an artifact the framework cannot
handle intelligently.

There is a plainer reason too. Day 85 puts an API in front of Sutra, and an HTTP response needs a
`Content-Type`. It comes from here or it comes from a guess.

## The mechanism

Three ways to save the same bytes, and what comes back:

```python
# days/day-18-artifacts-that-survive/lab/what_a_part_is.py
"""An artifact is a Part: bytes plus a declared type. Zero model calls."""

import asyncio

from google.adk.artifacts import InMemoryArtifactService
from google.adk.artifacts.base_artifact_service import ensure_part
from google.genai import types

APP, USER, SESSION = "sutra", "engineer_a", "s1"


async def main() -> None:
    service = InMemoryArtifactService()

    typed = types.Part(inline_data=types.Blob(data=b"severity: high\n", mime_type="text/markdown"))
    untyped = types.Part(inline_data=types.Blob(data=b"severity: high\n"))
    as_dict = {"inline_data": {"data": b"severity: high\n", "mime_type": "text/csv"}}

    for name, artifact in (("typed.md", typed), ("untyped.md", untyped), ("dict.csv", as_dict)):
        version = await service.save_artifact(
            app_name=APP, user_id=USER, session_id=SESSION, filename=name, artifact=artifact
        )
        back = await service.load_artifact(
            app_name=APP, user_id=USER, session_id=SESSION, filename=name
        )
        print(
            f"{name:12} v{version}  type={back.inline_data.mime_type!r}  {back.inline_data.data!r}"
        )

    print("ensure_part on a dict:", type(ensure_part(as_dict)).__name__)
    print("a text Part has no inline_data:", types.Part(text="hello").inline_data)


asyncio.run(main())
```

**Line by line:**

- `typed` — the shape you should write: `Part` wrapping a `Blob` with both fields set.
- `untyped` — the same bytes with **no MIME type**, which the constructor accepts without complaint.
  This is the experiment.
- `as_dict` — a plain dictionary with snake_case keys. It is here to prove the convenience exists, not
  because you should prefer it: a `Part` is checked by the type system and a dictionary is checked when
  something breaks.
- The loop saves and immediately loads each one, so the printed type is what came **out** of the store
  rather than what went in.
- `back.inline_data.mime_type!r` — `repr`, so `None` is visible as `None` rather than as a blank.
- `ensure_part(as_dict)` — calling the normaliser directly, to show what the service did with your
  dictionary.
- `types.Part(text="hello").inline_data` — the last line, and the reason artifacts are not "just
  content": a *text* Part has no `inline_data` at all, so saving one as an artifact stores something
  with no bytes in it.

**Line by line:**

- No model, no key, no network.

Measured on `google-adk` 2.7.1 and `google-genai` 2.19.0 on 2026-09-03:

```text
typed.md     v0  type='text/markdown'  b'severity: high\n'
untyped.md   v0  type=None  b'severity: high\n'
dict.csv     v0  type='text/csv'  b'severity: high\n'
ensure_part on a dict: Part
a text Part has no inline_data: None
```

Three saves, three version zeros, identical bytes, and one artifact that does not know what it is. The
store did not object, and nothing will object later either — the `None` simply travels until something
needs it.

## When it breaks

**`AttributeError: 'NoneType' object has no attribute 'data'`**

The commonest artifact error, and it has two very different causes that produce the same message.
Either the artifact does not exist — `load_artifact` returns `None` for a missing filename, measured in
[2.1](../02-versions/2.1-every-save-is-a-new-version.md) — or it exists and holds a `Part` with no
`inline_data`, which is what saving a text `Part` gives you. Check the loaded value for `None` before
reaching into it, and check `inline_data` before reaching into that.

**You pass a string instead of bytes, and it is read as base64.**

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for Blob
data
  Data should be valid base64: Invalid symbol 32, offset 3. [type=bytes_invalid_encoding, input_value='not bytes', input_type=str]
```

Measured on 2026-09-03. `Blob.data` is a bytes field, and pydantic's rule for a string in a bytes field
is *decode it as base64* — so a `str` is not rejected for being a `str`, it is rejected for being bad
base64. Which means the dangerous case is a string that **is** valid base64:

```python
types.Blob(data="high", mime_type="text/plain").data  # b'\x86(!'
```

**Line by line:**

- `"high"` is four characters, all in the base64 alphabet, so it decodes without error.
- The stored bytes are `b'\x86(!'` — three bytes of nothing, measured on 2026-09-03.
- No exception, no warning, and an artifact that is silently not what you saved.
- The rule this makes non-negotiable: **encode explicitly**. `data=NOTE.encode("utf-8")`, every time,
  and never a `str`.

**The artifact with no type, six months later.** No error, ever. It surfaces when a user interface has
to decide whether to render something, when the API server has to set a `Content-Type`, or when
[4.3](../04-in-the-run/4.3-what-the-model-cannot-see.md)'s safety conversion has to decide whether a
model may see it. By then the bytes are old and nobody remembers what they were.

## In production

**Set the MIME type at the moment of saving, from something that knows.**

The version a professional writes never passes a MIME type by hand at a call site. It comes from the
producer — the library that generated the PDF, the upload's declared `Content-Type`, or
`mimetypes.guess_type(filename)` as a last resort — in one helper that every save goes through. The
call sites then cannot forget, because they do not decide.

**What changes at scale** is that the MIME type becomes a trust boundary. For an uploaded file it is
**declared by the uploader**, so it is a claim rather than a fact: a file called `notes.txt` with
`text/plain` on the outside can hold anything. Anywhere that decision matters — rendering in a browser,
handing bytes to a parser, showing them to a model — the type has to be verified rather than believed,
and Day 66's work will treat it exactly like any other user-supplied string.

**What fails only under real traffic** is size. `inline_data` means the bytes travel in memory through
your process, so a 50-megabyte upload is 50 megabytes in the runner. That is the case `file_data` and a
real storage backend exist for, and it is the boundary at which "artifacts" stops being a convenience
and becomes an upload pipeline.

**The review comment**: *"this saves an artifact with no `mime_type`. Whoever loads it will have to
guess, and that guess ends up in an HTTP header."*

**The interview question**: *"what exactly is an artifact in ADK?"* The answer that shows you have read
the types: *"a `types.Part` with `inline_data` — bytes and a MIME type — stored under a filename by a
service, and versioned. The same `Part` type the model's content uses, which is why it can also hold a
reference instead of the bytes."*
