# 5.1 — The chair you are holding for nobody

## One-line answer

Holding an MCP connection between requests used to buy you a session and now buys you nothing, so
what is left is pure cost — a process or a socket per held connection, and a handle that goes on
looking healthy after the thing behind it has been replaced.

## The story

The canteen used to be a scramble, so everybody learned to hold a chair.

You would drape a jumper over the back of one on your way in, or leave a folder on the seat, and then
go and queue. It was not rude; it was what the room required, because there were more people than
chairs at half past one and a table you did not claim was a table you did not get.

Then they changed it. You take a numbered slip at the door now and the number is your table, and it
is held for you whether you are at the counter or halfway across the room. Nobody has to claim
anything.

Most people adapted in a week. A few did not, and you can still see them: jumper over a chair, folder
on a seat, holding something that was already theirs. It costs them nothing they notice. It costs the
room a chair, and it costs *them* the afternoon they come back from the counter to find their table
has been cleared and re-assigned, and they stand there with a tray, genuinely wrong-footed, because
the jumper is still on the chair and the chair is not theirs.

The habit was never the problem. The habit was a correct response to a room that no longer exists.

## The idea in plain language

Under the older MCP model, a connection carried a **session**. You performed an `initialize`
handshake, the server allocated some state for you, and that state lived for as long as the
connection did. The connection was therefore worth protecting: dropping it meant losing the session,
and getting it back meant handshaking again.

The 2026-07-28 revision removed the session. Day 32's
[2.1](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.1-the-call-that-remembered-you.md)
is that reframe in full, and its
[2.3](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.3-every-request-introduces-itself.md)
is the replacement: every request introduces itself. Nothing is remembered between them, so there is
nothing on the connection to lose.

Which means the question changes completely. It used to be *"why would you drop a connection?"* and
it is now *"what is this connection for?"* — and once you ask it that way, the reasons people give
turn out to have all expired:

| Why we held connections | What the 2026 protocol did to that reason |
| --- | --- |
| the session lives on it | there is no session |
| reconnecting means handshaking again | there is no handshake |
| re-fetching the catalogue is expensive | list results carry `ttlMs`; cache them ([5.2](5.2-keep-the-catalogue-not-the-connection.md)) |
| the server knows who we are | it never did; identity travels per request |

So a held connection is now a resource you are occupying rather than a state you are protecting. And
it has three specific costs, none of which are hypothetical:

- **It occupies something.** Over stdio, one held connection is one operating-system process, alive
  and resident, for as long as you hold it. Over HTTP it is a socket and, at the far end, a
  connection slot on a server that has a finite number.
- **It cannot survive the ordinary events of production.** A deploy replaces the process. A load
  balancer closes idle connections. A scale-in event removes the instance. None of those are faults;
  they are Tuesday.
- **It fails silently.** This is the one that costs an afternoon, and it is the demonstration below.

Day 33's [6.1](../../../day-33-client-and-transports/parts/06-in-production/6.1-the-connection-you-must-not-hold.md)
made the first half of this argument: nothing in the protocol *promises* you a connection may be
held, so anything you keep is an optimisation infrastructure is allowed to take away. This part is
the other half — what the thing you are holding actually costs you, and what it looks like when it is
taken.

## Why Sutra needs it

MCP-23 is the day's second ID and this is its statement: **Sutra's client holds no connection between
requests, and no piece of Sutra's code may depend on one.**

That is a rule with teeth, because ADK does not follow it for you. Read
`.venv/Lib/site-packages/google/adk/tools/mcp_tool/mcp_session_manager.py` and you will find
`create_session` keeping a dictionary of sessions keyed by headers, checking whether the stored one
is still connected and on the same event loop, and returning it if so. That is a session pool, and it
is a reasonable thing for a framework to do inside one process.

Sutra's rule is not "defeat the pool". It is narrower and it is what Day 45 will audit: no *state
that matters* lives on a connection, so the pool is free to discard any entry at any moment without
Sutra noticing. Concretely, that means nothing in `sutra/mcp/` may hold a session, a client or a
connection at module scope, and every toolset Sutra constructs must be closed —
`await toolset.close()`, which is what the adk.dev page calls the exit-stack pattern, read on
2026-09-05.

## The mechanism

> 🎬 **The scene:** Sutra opens connections to five MCP servers at startup and keeps them, because
> that is what the tutorial did. It runs happily for a week.
>
> 😬 **The naive fix:** none is applied, because nothing looks wrong. The handles are there, the
> objects are alive, and the health check — which pings on a fresh connection — is green.
>
> 💥 **Why it fails:** two of those servers are redeployed on Thursday morning. Sutra is idle at the
> time, so nothing raises. The handles are now pointing at processes that no longer exist, and Sutra
> has no way to know, because a handle to a dead process is not distinguishable from a handle to an
> idle one until you write to it.
>
> 💡 **The insight:** a connection you are not using is not a connection you have. It is a belief
> about the world that nothing is updating.

Five stdio servers, held, then two of them replaced:

```python
# days/day-44-client-hardening/lab/held.py
ECHO = "import sys\nfor line in sys.stdin:\n    sys.stdout.write(line)\n    sys.stdout.flush()\n"


def open_one() -> subprocess.Popen[str]:
    """Launch one stdio server. On stdio, connecting IS launching (Day 33's 2.1)."""
    return subprocess.Popen(
        [sys.executable, "-c", ECHO],
        stdin=subprocess.PIPE,
        stdout=subprocess.PIPE,
        text=True,
    )


def ask(proc: subprocess.Popen[str], text: str) -> str:
    """Send one line and read one line back."""
    assert proc.stdin and proc.stdout
    proc.stdin.write(text + "\n")
    proc.stdin.flush()
    return proc.stdout.readline().strip()
```

**Line by line:**

- `ECHO` is a whole stdio server in four lines: read a line, write it back, flush. It is not MCP, and
  it does not need to be — the thing being demonstrated is what a held pipe does when the process
  behind it dies, and a real `FastMCP` server would add a handshake and hide the finding behind
  thirty lines of framing.
- `sys.executable` rather than `"python"`, so the child runs the same interpreter as the parent.
  Writing `"python"` picks up whatever is on `PATH`, which on this machine is not the project's
  environment.
- `subprocess.Popen` with both pipes is the stdio transport by hand, which is Day 33's
  [2.1](../../../day-33-client-and-transports/parts/02-stdio/2.1-connecting-is-launching.md):
  connecting is launching, and holding a connection is holding a process.
- `text=True` gives strings rather than bytes, so the JSON layer would not need decoding.
- `flush()` after every write, in both directions. Without it the message sits in a buffer and you
  get a hang that neither side believes it is causing — Day 33's
  [2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md).
- `readline()` has **no timeout**, deliberately. It is the raw behaviour, and this whole day is about
  what you wrap it in.

The replacement, and what the client can see:

```python
# days/day-44-client-hardening/lab/held.py (continued)
    procs = [open_one() for _ in range(5)]
    print(f"processes held open      : {len(procs)}")
    print(f"first call on connection 0: {ask(procs[0], 'tools/list')}")

    # A deploy. Two of the five are replaced while the client is idle.
    for proc in procs[1:3]:
        proc.kill()
        proc.wait()
    print("two of the five were replaced (a deploy, an idle timeout, a scale-in)")
    print(f"what the client's handles report: {[p.poll() for p in procs]}")

    for index in (0, 1):
        try:
            print(f"  connection {index} write+read: {ask(procs[index], 'tools/call')!r}")
        except OSError as err:
            # The write failed. A client that only wrapped the read would not see this.
            print(f"  connection {index} write     : {type(err).__name__}: {err}")
            assert procs[index].stdout
            print(f"  connection {index} read      : {procs[index].stdout.readline()!r}")
```

**Line by line:**

- `procs[1:3]` kills two of five, so the output shows live and dead handles side by side. A run where
  everything died would be much less alarming and much less realistic.
- `proc.kill()` then `proc.wait()`. The `wait()` reaps the child; without it the process is a zombie
  and `poll()` may not have updated yet, which would make the demonstration accidentally wrong.
- `p.poll()` returns `None` for a running process and the exit code for a finished one. This is the
  *most* the client can find out without sending anything — and note that it is available here only
  because this is a local subprocess. **Over HTTP there is no `poll()`.** There is nothing at all: a
  socket to a machine that has gone looks exactly like an idle socket until you write to it.
- The loop tries connection 0 and connection 1, and it deliberately separates the **write** from the
  **read**. A client that wrapped only the read would never see the first failure, and a client that
  wrapped only the write would conclude the call succeeded when the write happened to be buffered.
- `except OSError` and then a read **anyway**. That is not defensive noise; it is the second half of
  the finding, and both halves are printed below.
- `!r` on every value, so an empty string prints as `''` rather than as nothing at all. Without the
  `repr` the most important line of this script's output is a blank space after a colon.

Run both arms:

```bash
cd days/day-44-client-hardening/lab

uv run python held.py --per-call
```

**Line by line:**

- The first arm holds five connections and then survives a deploy.
- `--per-call` is the ablation switch: open what this request needs, use it, close it.
- **Zero model calls.**

Measured on 2026-09-05:

```text
processes held open      : 5
first call on connection 0: tools/list
two of the five were replaced (a deploy, an idle timeout, a scale-in)
what the client's handles report: [None, 1, 1, None, None]
nothing raised. The client has five handles and believes all five.
  connection 0 write+read: 'tools/call'
  connection 1 write     : OSError: [Errno 22] Invalid argument
  connection 1 read      : ''
```

```text
request 0: tools/call
request 1: tools/call
request 2: tools/call
processes held between requests: 0
a deploy between two requests cannot be observed, because nothing spans them.
```

Look at the last two lines of the first run, because they are two different failures on one dead
connection.

The **write** raised `OSError: [Errno 22] Invalid argument` — not `BrokenPipeError`, not
`ConnectionResetError`, and not anything whose name suggests a server. Errno 22 is the operating
system saying that the handle you passed is not usable, and a client that catches `ConnectionError`
specifically will not catch it. On other platforms the same situation produces `BrokenPipeError`
instead, which is why the code catches `OSError` — the parent class of both.

The **read** returned `''`. Not an exception at all. End-of-file on a pipe is reported by
`readline()` as an empty string, and an empty string is exactly what naive code treats as "no
results". Day 33's [2.4](../../../day-33-client-and-transports/parts/02-stdio/2.4-closing-up.md) is
the anatomy of that empty string.

So the failure mode of a held connection is one of two things, neither of which says what happened:
an `OSError` whose name mentions no network and no server, or a silence that parses as an absence.
Which one you get depends on whether your client writes before it reads and on how the operating
system has torn the pipe down — and no client should be branching on that.

The second run has nothing to report, and that is the entire argument. There is no state spanning the
requests, so there is no state for a deploy to invalidate.

```mermaid
sequenceDiagram
    participant C as client
    participant P as server process
    C->>P: launch (connect)
    C->>P: tools/list
    P-->>C: result
    Note over C,P: idle - a deploy happens here
    P--xP: killed and replaced
    Note over C: handle unchanged; poll() only says "exited"
    C->>P: tools/call (write)
    P--xC: OSError [Errno 22]
    C->>P: readline()
    P-->>C: "" (end of file)
    Note over C: an OS error, then a silence - neither names a server
```

## When it breaks

The first break is the second half of the one just shown, and it is worth naming its consequence
rather than only its symptom. Suppose the write happened to be buffered rather than refused — which
it will be, on some platforms and at some moments — so the client never sees the `OSError` and goes
straight to the read. The empty string it gets back does not stay quiet:

```text
Traceback (most recent call last):
  File "client.py", line 22, in <module>
    reply = json.loads(line)
            ^^^^^^^^^^^^^^^^
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

`Expecting value: line 1 column 1 (char 0)` is what "the server is gone" looks like in a stdio
client, and it is a message that sends people looking for a malformed response. There is no response.

The second break is the leak, and it is the reason "close it" is a rule rather than a preference. A
client that opens per request and forgets to close accumulates a process and a pair of pipes every
time, and nothing complains until a limit is reached — the file-descriptor limit on Linux, the
handle count on Windows. When it is reached, the error arrives **in whatever unlucky part of the
program needs a descriptor next**, which is very often something unrelated like opening a log file,
so the traceback points nowhere near the code that leaked. Change `held.py`'s `per_call` arm to
remove the `proc.kill()` in its `finally` and watch the process count climb in Task Manager while the
script reports nothing at all.

This is what `await toolset.close()` prevents, and it is why the adk.dev MCP tools page, checked on
2026-09-05, says the exit-stack pattern is *"crucial for ensuring the connection (and potentially the
server process) is properly terminated when the ADK agent finishes"*.

The third break is the one you cannot see at all, and it is why this rule is about *dependency* and
not only about hygiene. Over HTTP, a load balancer's idle timeout closes the connection from its own
side, and the client learns about it on its next write:

```text
http.client.RemoteDisconnected: Remote end closed connection without response
```

There is no way to prevent this from the client. You can keep the connection warm with pings, and
then you are maintaining a heartbeat to preserve something the protocol says you do not need. The
supported answer is to stop needing it.

## In production

**What a professional writes instead of the teaching version.** Connections are pooled by the HTTP
client library, not by application code, and the pool is allowed to discard entries whenever it
likes. That distinction is the whole rule: pooling is a transport optimisation and is fine; *depending*
on a pooled connection is a design error. In practice it means every toolset is constructed inside a
context manager or closed in a `finally`, nothing under `sutra/mcp/` holds a session at module scope,
and any state that must span two requests travels in the payload as an explicit handle — Day 32's
[3.4](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md)
is the pattern and Day 36's task handles are the worked example.

**What degrades at scale or under concurrency.** Held connections multiply by instances. Ten Sutra
instances holding five stdio servers each is fifty resident processes, all of which have to be
launched at deploy time, all of which count against the machine's process and file-descriptor limits,
and none of which are doing anything most of the time. Over HTTP, a server with a connection limit
counts your idle connections against callers who want to do work. The cost is invisible on one
developer machine and is a capacity line item at ten instances.

**The failure mode that only appears with real traffic.** A held connection that has been *silently
replaced at the far end*. With a load balancer in the path, your socket can remain open while the
instance behind it is drained and replaced, and the next request is served by a different process
entirely — which is fine under the 2026 protocol and catastrophic if any of your code assumed the
first one remembered something. Day 32's
[2.2](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md) is that
scenario; the reason it is harmless for Sutra is precisely this rule.

**The review comment a senior engineer leaves:** *"this opens a toolset at import time and stores it
in a module global. What happens to it when the server is redeployed? Nothing raises — the next call
comes back empty, and we will parse it. Construct it per request, close it in a `finally`, and let
the HTTP pool do the pooling."*

**The interview question:** *"why do modern MCP clients not keep long-lived connections?"* —
*"Because the 2026-07-28 revision removed every reason to. There is no session on the connection and
no handshake to amortise, and list results carry cache hints so the catalogue can be kept without the
socket. What is left is cost: a process per connection on stdio, a connection slot on HTTP, and a
handle that keeps looking healthy after a deploy has replaced the thing behind it. I proved that last
one to myself — killed the process behind a held pipe, and the write raised an `OSError` about an
invalid argument, which mentions no server at all, and the read then returned an empty string rather
than raising, which is worse because empty parses as 'no results'. So the client opens what a request
needs and closes it, and lets the HTTP library pool underneath. Pooling is fine; depending on a
pooled connection is the error."*
