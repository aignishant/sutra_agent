# 1.3 — The line drawn through every call Sutra makes

## One-line answer

The protocol tells you that `tools/list` and `resources/read` may be repeated and says nothing at all
about what any particular tool does, so the repeatable list is something you write by hand, one row
per tool with a reason beside it, and a tool nobody has classified is treated as a write.

## The story

The library on the main road has two counters and they feel completely different.

At the first one there is a screen with the catalogue on it. You type in an author, you get a list,
you decide it is not what you wanted, you type in another. You can do that all afternoon. Nobody
minds, nobody is counting, and the shelves upstairs are exactly as they were when you walked in. If
the screen freezes halfway through a search you hit the button again without a thought.

The second counter is where you actually take a book out. The woman there writes your card number
against the book's number in the register, and now the book is *yours* until you bring it back —
which means it is not on the shelf, and the student who wanted it for an essay this week will be told
it is out.

Same building, same books, same you. One counter you may bother as many times as you like; at the
other, doing the same thing twice by accident means two books against your card and one fewer on the
shelf for somebody else. And there is nothing on either counter that announces which kind it is. You
know because you understand what happens behind each one.

## The idea in plain language

MCP has a small number of **methods**, which is the protocol's word for the kinds of message a client
can send. Some of them are, by their definition, pure reads of the server's own description of
itself:

| Method | What it does | May it be repeated? |
| --- | --- | --- |
| `tools/list` | ask what tools exist | yes — reading a catalogue |
| `resources/list` | ask what resources exist | yes |
| `resources/read` | fetch one resource's content | yes |
| `prompts/list` | ask what prompts exist | yes |
| `prompts/get` | fetch one prompt's text | yes |
| `ping` | ask whether anybody is there | yes |
| `tools/call` | **run a tool** | it depends entirely on the tool |

Six clean answers and one shrug. That last row is not the specification being lazy. `tools/call` is
the one method whose meaning is supplied by somebody else's code, so the protocol cannot possibly
know whether repeating it is safe — it does not know whether the tool sends an email. Day 32's
[1.3](../../../day-32-mcp-stateless-core/parts/01-the-socket/1.3-tools-resources-prompts.md) drew
this line already, from the server's side: resources are reads, tools are the ones that may change
the world.

So the client keeps its own table for `tools/call`, one row per tool. And the table has a default,
which is the whole design decision: **what happens to a tool that is not in the table?**

There are two possible defaults and they are not symmetric.

- **Default repeatable** ("unknown tools are probably fine"). Every new tool anybody adds is
  automatically on the retry path, silently, until somebody notices. The failure is a duplicate write
  in production that nobody can reproduce.
- **Default not repeatable** ("unknown tools are writes"). Every new tool is refused a retry until
  somebody classifies it. The failure is a read that surfaces an error it could have recovered from.

The second failure is visible, immediate, and fixed by adding one line. The first is invisible, slow,
and fixed by a support escalation and an apology. **Choose the default whose failure you would rather
find out about**, which is the same instinct Day 40's allowlist was built on
([1.1](../../../day-40-filtering-and-allowlists/parts/01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md)):
a list that grants permission fails closed, a list that removes permission fails open.

One more thing the table needs, and it is the part people leave out: **a reason column**. A set of
names is unreviewable. `{"lookup_ticket", "search_kb", "start_task"}` tells a reviewer nothing they
can disagree with. `start_task — the server mints one task per idempotency key, so a repeat returns
the same handle` is a claim a reviewer can go and check, and can find false.

## Why Sutra needs it

`with_retries` needs to know, at every call site, whether it is allowed to try again, and the answer
has to come from somewhere that is not the call site. If each caller decides for itself you have
nineteen policies and no policy;
[6.2](../06-the-last-word/6.2-one-policy-not-a-hundred.md) is that argument in full.

Sutra reaches real tools now. `lookup_ticket` and `search_kb` went on the wire on
[Day 34](../../../day-34-building-sutra-mcp-tools/LESSON.md). Day 36 added the task handles
`start_task`, `get_task` and `cancel_task`, and its
[3.3](../../../day-36-long-jobs-and-tasks/parts/03-the-handle/3.3-sutras-handle-policy.md) is
where the handle policy was written down — read it before you classify `start_task`, because whether
that one is repeatable is a property of the policy in that part rather than of the tool's name. Day
39 added SQL-backed tools. Day 41 added declared capabilities. Every one of those is a row you owe a
reason for, and Day 45's audit is going to ask for the table.

## The mechanism

The classifier is deliberately dull. Two frozen sets and one function with four branches:

```python
# days/day-44-client-hardening/lab/repeatable.py
READ_ONLY_METHODS = frozenset(
    {"tools/list", "resources/list", "resources/read", "prompts/list", "prompts/get", "ping"}
)

REPEATABLE_TOOLS = frozenset({"lookup_ticket", "search_kb", "get_task"})


def may_repeat(method: str, tool: str | None, *, optimistic: bool) -> tuple[bool, str]:
    """Return whether this call may be sent twice, and the sentence that decided it."""
    if method in READ_ONLY_METHODS:
        return True, "the method only reads the server's description of itself"
    if method != "tools/call":
        return False, "an unrecognised method is treated as a write"
    if tool in REPEATABLE_TOOLS:
        return True, "on the repeatable list, and the reason is written down beside it"
    if optimistic:
        return True, "not on the list, but the policy assumes unknown tools are safe"
    return False, "not on the list, so it is a write"
```

**Line by line:**

- `READ_ONLY_METHODS` is keyed on the **method name as it appears on the wire**, not on a Python
  function name. That matters because Day 32's
  [3.1](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.1-the-label-on-the-envelope.md)
  put the method into the `Mcp-Method` header, where a gateway can route on it — so this is the same
  string your infrastructure is already keying on, and using a different vocabulary in the client
  would guarantee the two lists drift apart.
- `ping` is on the list because a ping's whole purpose is to be sent again. It is worth having
  explicitly rather than falling through to the default, because a ping that cannot be retried is a
  liveness check that reports every dropped packet as a dead server.
- `REPEATABLE_TOOLS` holds three names and not four. `start_task` is absent even though Day 36's
  handle policy makes it *conditionally* safe, because conditional safety is not something a
  membership test can express. Putting it in would be encoding "safe if the server implements the
  policy we hope it implements".
- `may_repeat` returns a **tuple of the verdict and the reason**. The reason is not decoration; it
  goes into the log line when a retry happens or does not, so that an operator reading the log at
  midnight sees *why* rather than only *what* (Day 22's
  [2.1](../../../day-22-structured-logging/parts/02-wiring-the-run/2.1-one-line-per-happening.md)).
- The second branch — `if method != "tools/call": return False` — is the one that catches the future.
  When a new method is added to the protocol, or when somebody sends `tasks/cancel`, this function
  does not know it and refuses to retry it. That is correct behaviour for a function that has been
  told about a thing it has never heard of.
- `optimistic` is a keyword-only argument (`*` before it) so that no call site can flip the default
  by passing a positional `True` it does not understand. It exists only so the script can run the
  ablation; production code would not have the parameter at all.

Look at the last row of the optimistic arm. `refund_order` is a tool **no server Sutra talks to
offers**. It is in the script precisely to show what the optimistic default does with a name it has
never seen: it grants it a retry. The day somebody connects a payments server, the policy has already
decided, and nobody was asked.

And here is the table Sutra actually keeps, with the reason column that makes it reviewable:

| Tool | Repeatable? | Because |
| --- | --- | --- |
| `lookup_ticket` | yes | pure read of one record; no write path in the tool body |
| `search_kb` | yes | pure read; deterministic for a fixed corpus |
| `get_task` | yes | polling a handle is a read (Day 36's [4.3](../../../day-36-long-jobs-and-tasks/parts/04-the-tasks-extension/4.3-polling-is-a-budget.md)) |
| `start_task` | **no** | mints a task; safe only if the server dedupes on a key, which is the server's promise and not ours |
| `close_ticket` | **no** | emails the customer; the email cannot be recalled |
| anything else | **no** | nobody has classified it |

The last row is the important one and it is not filler. It is the rule that makes the table correct
on the day somebody adds a tool and forgets this file exists.

## When it breaks

The first break is a name collision, and Day 40 already showed you the shape of it in
[6.1](../../../day-40-filtering-and-allowlists/parts/06-the-posture/6.1-two-servers-one-tool-name.md).
Your table says `lookup_ticket` is repeatable. That was true of the `lookup_ticket` on `sutra-mcp`.
A second server is mounted, it also offers a tool called `lookup_ticket`, and that one writes an
access-audit row every time it is called. Your table now grants a retry to a tool it has never
assessed, because the key was a bare name:

```text
audit_log rows for ticket 4521 on 2026-09-05:
  09:14:02  read by sutra-desk
  09:14:03  read by sutra-desk
```

Two rows for one question. The fix is that the key is `(server, tool)` and never `tool` — the same
correction Day 40 made to the allowlist for the same reason.

The second break is a tool whose classification was true and stopped being true. Nothing errors. The
only signal is in a code review of `sutra_mcp/tools.py` that nobody connected to a file under
`sutra/mcp/`. The defence is the reason column: a reviewer reading *"pure read; no write path in the
tool body"* against a diff that adds `notify(...)` to the tool body has been handed the
contradiction.

The third break is the optimistic default applied by omission rather than by decision. Nobody writes
`optimistic=True`; somebody writes `IDEMPOTENT.get(name, True)` because it read better than the
alternative, and a `dict.get` default is a policy decision hiding in a convenience method. Grep for
default arguments in this file specifically.

## In production

**What a professional writes instead of the teaching version.** The table is data, not a set literal:
a mapping from `(server_key, tool_name)` to a record holding `repeatable: bool`, `reason: str` and the
date it was last reviewed. It lives beside Day 40's `REGISTRY` in `sutra/mcp/filtering.py`, because
the allowlist and the retry table are two columns of the same fact — *which tools may we call, and
what may we do to them twice* — and splitting them across two files guarantees one gets updated
without the other. There is a startup assertion that every allowed tool has a row.

**What degrades at scale or under concurrency.** Not the table itself, which is a dictionary lookup.
What degrades is the *review*: at three servers and twelve tools a human keeps the table right, and
at thirty servers and four hundred tools nobody does. That is the point at which the table stops
being maintained by attention and starts being maintained by a check — a test that fails when a
server advertises a tool with no row, so the gap is a red build rather than a discovery.

**The failure mode that only appears with real traffic.** A tool that is idempotent under one caller
and not under two. `close_ticket` implemented as *"if the ticket is open, close it and email"* looks
repeatable in every single-threaded test. Under concurrency, two workers both read `open` and both
email. Nothing about the client's table is wrong; the server's claim was. This is why the reason
column for a write should name the *mechanism* — a unique key, a conditional update, a database
constraint — rather than saying "the server handles it".

**The review comment a senior engineer leaves:** *"this is a set of tool names with no reasons. In
six months nobody will know whether `start_task` is in here because it is genuinely idempotent or
because somebody needed a retry that afternoon. Give me a reason per row and a date, and tell me what
happens to a tool that is not in the list."*

**The interview question:** *"how does your client decide which calls it is allowed to retry?"* —
*"By a table we maintain, not by a heuristic. The protocol methods that only read a catalogue are
retryable by definition, and I take those from the method name, which is the same string our gateway
routes on. Tool calls are one row each, keyed on server and tool rather than tool alone, because two
servers can offer the same name and mean different things. Each row carries a written reason, so a
reviewer can disagree with it. And the default for anything absent is 'do not retry', because that
failure shows up as an error somebody fixes in a line, and the other default's failure shows up as a
customer with two closure emails and a support ticket three months later."*
