# 1.1 — The button you can press twice

## One-line answer

Some actions have the same effect whether you do them once or five times, and some do not, and a
retry is only ever safe for the first kind — so the first question a hardened client asks is not
*how many times* but *may I at all*.

## The story

You press the bell at the front gate and nothing happens.

So you press it again. Nobody thinks twice about this. Two presses, three presses, a long one — the
house is not more visited than before, nobody inside is double-disturbed in some way that matters,
and if somebody eventually comes to the gate you have lost nothing by pressing again. Pressing the
bell a second time is free.

The same afternoon you ring the builders' yard to order a lorry of cement for the back wall. The line
is bad, you get halfway through the address, and it cuts out. You ring again and give the order
properly this time.

Two lorries arrive on Thursday. Two bills.

Nobody was careless. The man at the yard did exactly what he was asked, twice, because from where he
sat there were two orders. And you did exactly what you had done at the gate an hour earlier — the
same reflex, the same "that did not seem to work, try again". The reflex was right at the gate and
expensive at the yard, and nothing about how the two attempts *felt* told you which was which.

The difference was never in you and never in the attempt. It was in what was on the other end.

## The idea in plain language

An action is **idempotent** when doing it more than once leaves the world exactly as doing it once
does. The word is long and the idea is the doorbell: press it again, same house, same state.

Some plain examples, from outside computers:

| Action | Do it twice | Idempotent? |
| --- | --- | --- |
| Ring the bell | the same door, unopened, twice rung | yes |
| Read a page | the page is unchanged | yes |
| Set the thermostat to 22 | it is at 22 | yes |
| Order a lorry of cement | two lorries | no |
| Add ₹500 to a balance | ₹1000 added | no |
| Send a closure email | two emails to one customer | no |

Look at rows three and five together, because that pair is the whole idea. **"Set the temperature
to 22" is idempotent and "add five degrees" is not**, and they can be the same physical dial. What
decides is whether the action names an *end state* or names a *change*. An action that says what the
world should look like can be repeated forever. An action that says what to do to the world cannot.

A **retry** is deliberately doing the same thing again because you are not sure the first attempt
worked. That is the doorbell reflex, written into code. And a retry loop is a machine for pressing
the button as many times as it takes — which is a wonderful thing to point at a page and a terrible
thing to point at a cement order.

So there is an order to these questions, and most people get it backwards. It is not *"how many
times should I retry, and how long should I wait?"* first. It is:

1. **May this call be repeated at all?** If the answer is no, everything below is irrelevant.
2. Only then: how many times, and how long between.

Question 2 is arithmetic. Question 1 is judgement, it is different for every tool, and no library
can answer it for you, because the answer is not in the protocol or in the network. It is in what
the tool *does*.

One more term, because it is the one that gets muddled. **Safe** and **idempotent** are not the same
word. A safe action changes nothing at all — a read. An idempotent action may change something, but
repeating it changes nothing more. Every safe action is idempotent; not every idempotent action is
safe. "Close ticket 4521" is idempotent if the server treats it as *"the state of 4521 should be
closed"* and not idempotent if it treats it as *"do the closing procedure again"* — and the customer
finds out which by counting the emails.

## Why Sutra needs it

Sutra's client makes calls that cross a process boundary, and has done since Day 33 gave it
[`connect_stdio` and `connect_http`](../../../day-33-client-and-transports/parts/01-the-connector/1.2-constructing-is-not-connecting.md).
Every one of those calls can fail in a way that leaves you unsure whether it happened.
[Day 38's failure lab](../../../day-38-failure-and-migration-lab/LESSON.md) made you watch that
happen: [3.2](../../../day-38-failure-and-migration-lab/parts/03-the-quiet-ones/3.2-the-ticket-closed-twice.md)
is a ticket closed twice, and it ends by telling you the fix is a key the server remembers.

Today is the day you write the policy down, in `sutra/mcp/hardening.py`. Before you can write
`with_retries` you have to be able to say which calls it may be pointed at, and the honest answer
is a list you maintain by hand with a reason beside every entry — [1.3](1.3-the-line-through-every-call.md)
is that list. If you skip this part and go straight to backoff and jitter, you will build a very
sophisticated machine for sending two lorries of cement.

## The mechanism

> 🎬 **The scene:** a support agent asks Sutra to close ticket 4521. Sutra calls `close_ticket` over
> MCP. The tool runs, the ticket closes, the customer's email goes out — and the reply is lost on the
> way back, because a load balancer recycled the connection.
>
> 😬 **The naive fix:** the same retry loop that fixed the flaky reads last month. One policy, no
> special cases, a beautiful small diff.
>
> 💥 **Why it fails:** the retry sends the same request to a server that has no reason to think it
> has seen it before. The tool runs a second time. The customer gets a second email. Nothing raises,
> nothing logs an error, and both attempts were correct code doing what it was told.
>
> 💡 **The insight:** you may only retry what you can afford to accidentally do twice.

Here is the whole argument in one script. Two tools, one wire that loses the first reply, and a retry
policy that is either symmetric or asymmetric:

```python
# days/day-44-client-hardening/lab/idem.py
ARCHIVE = {"4521": {"subject": "printer offline", "state": "open"}}
NOTICES_SENT: list[str] = []
READS_SERVED = 0

IDEMPOTENT = frozenset({"lookup_ticket"})


def lookup_ticket(ticket_id: str) -> dict[str, str]:
    """Read one ticket. Called once or called five times, the archive is identical."""
    global READS_SERVED
    READS_SERVED += 1
    return dict(ARCHIVE[ticket_id])


def close_ticket(ticket_id: str) -> dict[str, str]:
    """Close one ticket and email the customer. The email is the part that cannot be undone."""
    ARCHIVE[ticket_id]["state"] = "closed"
    NOTICES_SENT.append(f"ticket {ticket_id} has been closed")
    return {"ticket_id": ticket_id, "state": "closed"}
```

**Line by line:**

- `ARCHIVE` is a plain dictionary standing in for the ticket store. It is deliberately mutable so
  that you can look at it afterwards and see what the two runs did to it. A test that only checks
  return values would pass in both arms of this script.
- `NOTICES_SENT` is the part of the world you cannot take back. The ticket's `state` can be flipped
  back to `open` by anybody with access; an email that has arrived at a customer cannot be recalled.
  When you are deciding whether a tool is repeatable, look for this list — **the irreversible side
  effect is the thing that decides**, not the return value.
- `READS_SERVED` counts reads so that the script can prove the read was genuinely repeated. Without
  the counter you could not tell "we retried and it worked" from "it worked first time".
- `IDEMPOTENT` is a `frozenset` rather than a `list` because it is a membership test and because a
  frozen set cannot be appended to by accident from somewhere else in the process. It holds
  `lookup_ticket` and not `close_ticket`, and that one absence is the entire policy.
- `lookup_ticket` returns `dict(ARCHIVE[ticket_id])` — a **copy**. Handing out the live dictionary
  would let a caller mutate the archive through a function documented as a read, which would make the
  read non-idempotent without anybody editing it.
- `close_ticket` writes to `ARCHIVE` and appends to `NOTICES_SENT` in that order. The append is the
  line that makes this tool un-retryable, and it is one line long. That is normal: the un-retryable
  part of a write is usually small and easy to miss in review.

Now the wire and the policy:

```python
# days/day-44-client-hardening/lab/idem.py (continued)
class Wire:
    """A transport that loses the *reply* to the first call it carries."""

    def __init__(self) -> None:
        self.dropped = False

    def call(self, name: str, ticket_id: str) -> dict[str, str]:
        result = TOOLS[name](ticket_id)  # the server does the work FIRST
        if not self.dropped:
            self.dropped = True
            raise TimeoutError(f"no response to {name} within the deadline")
        return result


def call_with_retries(wire: Wire, name: str, ticket_id: str, *, safe_only: bool) -> dict[str, str]:
    """Call a tool, retrying once. `safe_only` decides whether a write may be retried."""
    may_retry = (not safe_only) or (name in IDEMPOTENT)
    attempts = 2 if may_retry else 1
    last: Exception | None = None
    for attempt in range(1, attempts + 1):
        try:
            return wire.call(name, ticket_id)
        except TimeoutError as err:
            last = err
            print(f"  attempt {attempt} of {attempts}: {err}")
    assert last is not None
    raise last
```

**Line by line:**

- `Wire.call` runs the tool **before** deciding whether to drop the reply. That order is the point of
  the whole class. Real transports work this way: the request arrives, the work is done, and only
  then does the answer have to survive a network that may not carry it. A fake that raised *instead
  of* running the tool would be modelling a different failure entirely, and a much rarer one.
- `self.dropped` is a one-shot flag, so the second attempt succeeds. That makes the two runs
  identical in everything except the policy, which is what an ablation needs.
- `raise TimeoutError(...)` and not a custom exception, because `TimeoutError` is what a real client
  raises and what a real caller will be catching. The lab should teach the type you will actually
  meet.
- `may_retry = (not safe_only) or (name in IDEMPOTENT)` — read it as: *"if we are not being careful,
  everything may retry; if we are, only what is on the list"*. Note which way round the default goes
  in the careful branch: **membership grants permission**, so a tool nobody has thought about is
  refused rather than allowed. [1.3](1.3-the-line-through-every-call.md) is entirely about why that
  direction matters.
- `attempts = 2 if may_retry else 1` makes "no retry" one attempt rather than zero. A write is still
  attempted; it is simply attempted once. There is a real bug people write here, which is treating
  non-idempotent as "do not call", and it turns a hardening change into an outage.
- `last` holds the final exception so the loop can re-raise it after the budget is spent. Losing the
  original error and raising a fresh `RuntimeError("retries exhausted")` throws away the only
  evidence anybody will have (Day 21's
  [2.3](../../../day-21-errors-surface-not-swallow/parts/02-four-hooks/2.3-the-two-that-can-only-witness.md)).
- `raise last` and not `return None`. The failure leaves this function as a failure.
  [6.1](../06-the-last-word/6.1-what-you-say-when-it-all-failed.md) is about what the layer above
  then says to a human.

**Line by line:**

- `cd` into `lab/` first; the scripts in this day are run from that directory.
- The first command is the symmetric policy: one rule, applied to reads and writes alike.
- `--safe` is the ablation switch. Same wire, same failure, same tools — only the policy changes.
- **Zero model calls.** There is no model anywhere in this part.

Measured on 2026-09-05:

```text
policy      : retry everything
read  lookup_ticket('4521')
  attempt 1 of 2: no response to lookup_ticket within the deadline
  caller sees : the ticket
write close_ticket('4521')
  attempt 1 of 2: no response to close_ticket within the deadline
  caller sees : closed

reads served by the server   : 2
closure notices to the customer: 2
  - ticket 4521 has been closed
  - ticket 4521 has been closed
```

```text
policy      : reads may retry, writes may not
read  lookup_ticket('4521')
  attempt 1 of 2: no response to lookup_ticket within the deadline
  caller sees : the ticket
write close_ticket('4521')
  attempt 1 of 1: no response to close_ticket within the deadline
  caller sees : TimeoutError: no response to close_ticket within the deadline

reads served by the server   : 2
closure notices to the customer: 1
  - ticket 4521 has been closed
```

Read the last three lines of each. **Two closure notices against one.** The read was retried in both
runs and served twice in both runs, and no harm came of it, which is the other half of the lesson:
the asymmetry is not timidity. Reads genuinely may be retried, and a policy that refuses to retry
anything is throwing away the recoveries it could have had.

The first run's caller is *happier* than the second run's. It got a result; the careful run got an
exception. That is the trade, stated plainly: **the careful policy hands its caller a problem instead
of handing a customer a second email.** A problem a human can act on is the better of the two, and
[6.1](../06-the-last-word/6.1-what-you-say-when-it-all-failed.md) is about making sure it actually
reaches one.

## When it breaks

The first way this breaks is a tool that looks idempotent and is not.

```text
attempt 1 of 2: no response to append_note within the deadline
  caller sees : ok

notes on ticket 4521:
  - "customer called back, still offline"
  - "customer called back, still offline"
```

`append_note` reads like a small, harmless write. It is not idempotent, because "append" is a change
rather than an end state, and the second copy is now in the ticket history where an agent will read
it and conclude the customer called twice. Nothing errored. The word to look for in a tool's name is
a verb of accumulation — `append`, `add`, `increment`, `send`, `charge`, `create` — against a verb of
assignment: `set`, `put`, `close`, `assign`.

The second way is subtler and it is the one that survives review. A tool is idempotent *today*
because its implementation happens to be, and nobody wrote that down. Somebody adds a notification:

```text
Traceback (most recent call last):
  File "sutra_mcp/tools.py", line 61, in close_ticket
    notify(ticket_id)
  ...
```

There is no traceback, in fact. That is the problem — the change is a one-line addition inside a
tool whose *name* did not change, whose *signature* did not change, and whose client-side entry in
your repeatable list nobody thought to revisit. The tool became un-retryable in a commit that never
mentioned retries. The defence is not vigilance; it is that the list in
[1.3](1.3-the-line-through-every-call.md) carries a written reason per entry, so the reason is a
thing a reviewer can find false.

The third is the opposite mistake. Somebody reads this part, decides retries are dangerous, and turns
them off everywhere:

```text
policy      : retry nothing
read  lookup_ticket('4521')
  attempt 1 of 1: no response to lookup_ticket within the deadline
  caller sees : TimeoutError: no response to lookup_ticket within the deadline
```

Now a single dropped packet on a pure read becomes an incident. The archive was never in danger. This
is the failure mode of a rule remembered as a slogan instead of a distinction.

## In production

**What a professional writes instead of the teaching version.** The list is not a `frozenset` of tool
names alone; it is a record per tool with the reason attached, kept next to the allowlist Day 40 put
in [`sutra/mcp/filtering.py`](../../../day-40-filtering-and-allowlists/parts/04-the-policy-module/4.2-a-policy-you-can-diff.md).
A name with no reason beside it is a name nobody can review. And the classification is asserted at
startup, not consulted at call time only: if a server advertises a tool that is in neither the
repeatable list nor the explicitly-not-repeatable list, that is a startup failure, because the
alternative is discovering the gap during an incident.

**What degrades at scale or under concurrency.** Two things. First, the same request retried from two
worker processes at once is not sequential — a server that "handles" repeats by checking *"is this
ticket already closed?"* has a race between the check and the write, and under load both workers see
`open`. Idempotency that is implemented as a read-then-write is not idempotency; it is a smaller
window. Second, at ten thousand tickets a day, a write that is retried on one call in a thousand is
ten duplicate side effects a day, every day, and they will be reported as unrelated one-off
complaints for months.

**The failure mode that only appears with real traffic.** The duplicate needs a timeout *on a
success*, which is rare, so it survives every test, every code review and the whole of staging. It
detonates in month three as a support escalation nobody can reproduce. This is why the rule is
enforced structurally — by what `with_retries` is allowed to be pointed at — and not by care.

**The review comment a senior engineer leaves:** *"you have added `close_ticket` to the retry path.
A timeout is not a failure, it is an unknown — the first attempt may have succeeded and died on the
way back. What stops the customer getting two emails? If the answer is 'the server checks', show me
where that check is atomic."*

**The interview question:** *"when is it safe to retry a failed call?"* The honest answer starts by
refusing the question's framing. *"'Failed' is the wrong word — most of the time you do not know it
failed, you know you did not hear back, and those are different. So the rule I use is: retry only
what I can afford to have happened twice. Reads and anything phrased as an end state, freely. Writes
that accumulate — sends, charges, appends — never, until they carry an idempotency key the server
deduplicates on. On the last system I did this, the list of retryable tools was a table in code with
a written reason per row, and the default for an unclassified tool was 'do not retry', because the
cost of being wrong in that direction is one visible error and the cost of being wrong in the other
direction is a customer getting two closure emails and nobody finding out for a quarter."*
