# 1.4 — The key that makes a write repeatable

## One-line answer

A write becomes safe to repeat when the caller mints a unique name for the *intention* before the
first attempt and sends the same name every time, so the server can recognise the second request as
the same request rather than a second one — which moves the problem from "may I retry?" to "does the
far side keep that promise?".

## The story

You book two seats for the eight o'clock show on the cinema's website.

The card page spins. It spins for long enough that you start looking for another way, and eventually
you give up, go back, and book the two seats again — bracing yourself for the message about a
duplicate charge that you have had from other sites before.

It does not come. Instead the page says: *you already have booking KJ7742 for this show*.

You did not do anything clever. The thing that saved you is that when you first pressed the button
the site wrote down a name for what you were trying to do — one name, for that attempt, before it
took any money — and when the same attempt came back a second time it recognised the name and showed
you the booking it had already made rather than making another.

Notice where the name came from. Not from the payment. Not from the seats. It was minted at the
beginning, attached to your *intention*, and it stayed the same across both attempts. If the site had
generated a fresh reference each time you pressed the button, it would have had two intentions in
front of it and no way at all to tell they were the same one.

## The idea in plain language

An **idempotency key** is a name the caller invents for one intended operation, sends with every
attempt at that operation, and never reuses for a different one.

The server does two things with it:

1. Before doing the work, it checks whether it has honoured this key already. If it has, it returns
   the result it produced the first time and does no work.
2. After doing the work, it records the key together with the result, in the same transaction as the
   work itself.

That second half is the part that gets skipped, and skipping it turns the whole mechanism into
theatre. If the key is recorded *after* the commit, in a separate step, then a crash between the two
leaves the work done and the key unrecorded — and the retry does the work again. **The key and the
effect must land together or not at all.**

Three properties the key must have:

- **Minted by the caller, not the server.** A server-issued reference cannot help, because to obtain
  one you have to make a call, and that call can time out.
- **Minted before the first attempt.** If you generate it inside the retry loop, each attempt has a
  different key and the server sees a queue of separate intentions.
- **Unique to the intention, not to the request.** "Close ticket 4521 because the agent pressed
  resolve at 09:14" is one intention, however many times it is sent. Closing 4521 again tomorrow for
  a different reason is a different intention and gets a different key.

The last one is where judgement lives. Too specific a key — including a timestamp taken at send time,
say — and every retry is a new intention, which is the bug. Too general a key — the ticket id alone —
and a legitimate second close next month is silently swallowed as a duplicate.

Where does it travel in MCP? In the tool's own arguments, or in the request's `_meta` block. It is
not a protocol feature: the 2026-07-28 revision defines no `Idempotency-Key` header for `tools/call`,
so this is a contract between one client and one server, written down and tested. That is not a
disappointment — it is the [end-to-end argument](../../../day-21-errors-surface-not-swallow/papers/01-end-to-end-arguments.md)
again. Only the two endpoints know what "the same operation" means.

## The mechanism

> 🎬 **The scene:** an agent resolves ticket 4521. `close_ticket` is called, the reply is lost, and
> the client is in [world 3](1.2-a-timeout-is-an-unknown.md) with no way to find out.
>
> 😬 **The naive fix:** ask first. Call `lookup_ticket`, see whether the state is already `closed`,
> and only retry if it is not.
>
> 💥 **Why it fails:** the check and the retry are two calls with a gap. Under any concurrency at all
> the state can change in that gap, and worse, the check itself can time out, which puts you in the
> same position one level deeper. You have made the window smaller and written code that reads like a
> guarantee.
>
> 💡 **The insight:** stop trying to find out what happened. Make it not matter — send something that
> lets the *server* recognise the repeat, in the same transaction as the work.

The server side is nine lines:

```python
# days/day-44-client-hardening/lab/key.py
SEEN: dict[str, dict[str, str]] = {}  # the server's memory of keys it has already honoured


def close_ticket(ticket_id: str, *, key: str | None = None) -> dict[str, str]:
    """Close a ticket. If a key is given and has been seen, replay the first result."""
    if key is not None and key in SEEN:
        print(f"  server: key {key} already honoured; replaying the first result")
        return dict(SEEN[key])
    ARCHIVE[ticket_id]["state"] = "closed"
    NOTICES_SENT.append(f"ticket {ticket_id} has been closed")
    result = {"ticket_id": ticket_id, "state": "closed"}
    if key is not None:
        SEEN[key] = dict(result)
        print(f"  server: key {key} recorded with its result")
    return result
```

**Line by line:**

- `SEEN` maps a key to the **result**, not to a boolean. Storing `True` would let the server say
  "already done" without being able to say *what* was done, and a retry would get an empty success —
  which is a different answer from the first attempt's, and a caller comparing them would be right to
  be alarmed. Replay the original answer.
- The check is the **first** statement in the function, before any mutation. Anything above it that
  touched the world would run twice.
- `key is not None` guards both branches, so a caller that sends no key gets the old behaviour rather
  than an error. That is deliberate for a lab and questionable for production: a server that
  *requires* a key on every write cannot be misused by a client that forgot, and
  [*In production*](#in-production) below argues for making it required.
- `SEEN[key] = dict(result)` stores a **copy**, for the same reason `lookup_ticket` returned one in
  [1.1](1.1-the-button-you-can-press-twice.md): a stored reference that a caller can mutate is not a
  record of what happened.
- The two mutations and the `SEEN` write are three separate statements here and that is the lab's
  one lie. In a real server they must be one transaction — `UPDATE tickets ...` and `INSERT INTO
  idempotency_keys ...` inside a single `BEGIN`/`COMMIT` — because a crash between them is exactly the
  scenario this whole mechanism exists to survive.
- `NOTICES_SENT.append(...)` sits *inside* the transaction in this toy and cannot in reality: an
  email is not transactional. The real pattern is that the tool writes a row to an outbox table in
  the same transaction and a separate worker sends from the outbox, so the email inherits the
  transaction's exactly-once-ness. That is a whole subject, and this is the sentence that names it so
  you can go and read about it.

The caller side is two lines, and both of them matter:

```python
# days/day-44-client-hardening/lab/key.py (continued)
# One key per intention, minted by the CALLER, before the first attempt.
key = "close-4521-a1f3" if use_key else None
print("attempt 1 (the reply to this one is lost on the way back)")
close_ticket("4521", key=key)
print("attempt 2 (the retry, byte for byte the same request)")
close_ticket("4521", key=key)
```

**Line by line:**

- `key` is assigned **once**, above the two attempts. Move that line inside a retry loop and the
  entire mechanism stops working while continuing to look correct, which is the single most common
  way this is got wrong.
- The literal `"close-4521-a1f3"` has two halves on purpose: a human-readable part naming the
  intention, and a random part making it unique. In real code the random half is
  `uuid.uuid4().hex[:8]` or similar; hard-coding it here keeps the transcript stable so that both
  runs of the script are comparable.
- The same `key=key` is passed to both calls. "Byte for byte the same request" is the definition of a
  retry — a retry that differs in any argument is a new request wearing a retry's clothes.
- `close_ticket("4521", key=key)` uses a keyword argument because the key is not part of the
  operation's meaning. Making it positional invites a caller to pass the ticket id twice.

Run both arms:

```bash
cd days/day-44-client-hardening/lab
uv run python key.py
uv run python key.py --key
```

**Line by line:**

- The first arm sends no key, which is where [1.3](1.3-the-line-through-every-call.md) leaves
  `close_ticket` today.
- `--key` is the ablation switch: one argument, everything else identical.
- **Zero model calls.**

Measured on 2026-09-05:

```text
idempotency key: (none)
attempt 1 (the reply to this one is lost on the way back)
attempt 2 (the retry, byte for byte the same request)

closure notices to the customer: 2
  - ticket 4521 has been closed
  - ticket 4521 has been closed
```

```text
idempotency key: close-4521-a1f3
attempt 1 (the reply to this one is lost on the way back)
  server: key close-4521-a1f3 recorded with its result
attempt 2 (the retry, byte for byte the same request)
  server: key close-4521-a1f3 already honoured; replaying the first result

closure notices to the customer: 1
  - ticket 4521 has been closed
```

Two notices against one, and the second run's caller got a *result* rather than an error. That is the
whole promotion: with a key, a write may go back on the retry path and behave like a read.

```mermaid
sequenceDiagram
    participant C as client
    participant S as server
    participant D as store
    C->>C: mint key K (once, before attempt 1)
    C->>S: close_ticket(4521, key=K)
    S->>D: has K been honoured? no
    S->>D: BEGIN; close 4521; record K -> result; COMMIT
    S--xC: reply lost
    Note over C: timeout - an unknown outcome
    C->>S: close_ticket(4521, key=K)
    S->>D: has K been honoured? yes
    S-->>C: the recorded result
```

## When it breaks

The first break is the key minted in the wrong place. It is a one-line move and it is invisible in
review:

```text
idempotency key: close-4521-a1f3
  server: key close-4521-a1f3 recorded with its result
idempotency key: close-4521-9b02
  server: key close-4521-9b02 recorded with its result

closure notices to the customer: 2
```

Two keys, two intentions, two emails. Everything about the mechanism worked; it was pointed at the
wrong thing. A key generated inside the loop is not an idempotency key, it is a request id.

The second is a server that accepts the key and ignores it. There is no error message for this at
all, which is what makes it dangerous — your client is sending the argument, your code review saw the
argument, and the far side drops unknown fields on the floor. The MCP-specific version of this is
worth knowing exactly: a `tools/call` whose arguments include a field the tool's `inputSchema` does
not declare is, on `mcp==1.29.1`, not an error. You will get:

```text
{"content": [{"type": "text", "text": "ticket 4521 closed"}], "isError": false}
```

for both attempts, and two emails. The only defence is a test that sends the same key twice against
the real server and asserts on the side effect, not on the response.

The third is key reuse across genuinely different intentions. A key of `close-{ticket_id}` with no
random half looks tidy and means a ticket can only ever be closed once in the lifetime of the store.
The failure arrives months later when a reopened ticket refuses to close:

```text
  server: key close-4521 already honoured; replaying the first result
```

and the result being replayed is from a closure that happened in March. Keys need an expiry, and the
expiry is a policy decision — long enough to cover every retry a client could make, short enough that
a legitimate repeat operation is not swallowed.

## In production

**What a professional writes instead of the teaching version.** The key is required, not optional:
the tool's `inputSchema` declares `idempotency_key` and the tool refuses the call without it, so a
client that forgets fails loudly on the first request rather than quietly on the first retry. The
stored keys live in their own table with the request's argument hash beside them, so that the server
can detect the other bug — the *same key with different arguments*, which means a client is reusing
keys and must be told so with an error rather than served a replayed answer.

**What degrades at scale or under concurrency.** The dedupe table becomes a hot row. Two workers
retrying the same key at the same moment both check, both see nothing, and both proceed — unless the
check is a unique constraint rather than a `SELECT`. The correct implementation is not "look, then
write"; it is "write and let the database reject the duplicate", because only the constraint is
atomic. And the table grows forever unless somebody sets a retention window, which is a cleanup job
nobody writes until the disk fills.

**The failure mode that only appears with real traffic.** A retry that arrives while the first
attempt is *still running*. The key is not yet recorded, because the transaction has not committed,
so the second request sails past the check and both do the work. The fix is to record the key at the
*start*, in a `pending` state, and have the second request block or return a "in progress" status —
which is the same shape as Day 36's task handle, and is why the two subjects keep meeting.

**The review comment a senior engineer leaves:** *"where is this key generated? If it is inside the
retry helper, every attempt has a different key and this does nothing. Show me the line that mints it
and show me that it is above the loop. And is the key written in the same transaction as the ticket
update, or after it?"*

**The interview question:** *"how would you make a non-idempotent operation safe to retry?"* — *"Give
the caller a way to name the intention. The client mints a key before its first attempt and sends the
identical key on every retry; the server records the key with its result in the same transaction as
the effect, and a repeat gets the recorded result rather than a second execution. The two things I
watch for are where the key is minted — inside the retry loop is the classic bug and it looks fine in
review — and whether the dedupe is a unique constraint or a select-then-insert, because under
concurrency the select-then-insert has a window and the constraint does not. And I make the key
required in the schema, so a client that forgets fails on its first call rather than on its first
timeout."*
