# 2.4 — The numbers your libraries already chose

## One-line answer

`mcp==1.29.1` gives a client session **no read timeout at all** unless you pass one, ADK's HTTP
connection params quietly use `sse_read_timeout` — 300 seconds — as the per-call deadline rather than
the `timeout=5.0` you set, and ADK retries every failed tool call once whether or not the tool is
idempotent, so three of the most important decisions in this day have already been made for you by
code you did not write.

## The story

The sewing machine arrives from the shop with a needle already fitted and the tension dial already
set.

It works. You sew a few straight seams on cotton and everything is fine, and for a couple of months
you never think about either setting, because why would you — the machine came like that and the
machine is working.

Then you try to take up a pair of heavy trousers and the thread starts snapping, and the man at the
shop asks, without much interest, what tension you are running it at. You do not know. You have never
touched it. He turns the machine round, looks, and says: that is the setting it leaves the factory
with. It is a reasonable guess about an average person sewing average cloth, and it was never a
statement about *your* cloth.

The settings were not wrong. They were somebody else's decision, arrived at without knowing anything
about you, and you had been treating them as the absence of a decision.

## The idea in plain language

Every library you call through has already answered the questions this section is about. The answers
are in the source, they are frequently surprising, and a default you have not read is not a default
you have chosen.

There are three questions worth asking of any client library, in this order:

1. **If I set nothing, is there a deadline at all?** Not "what is it" — whether one exists. The
   answer is sometimes no.
2. **Which of my numbers is used for which phase?** A library with a `timeout` and a
   `read_timeout` may not map them onto connect and call the way the names suggest.
3. **Does it already retry?** If it does, your retry policy is being multiplied by a number you did
   not choose, which is [3.4](../03-backing-off/3.4-with-retries.md)'s problem arriving early.

Principle 8 says never invent an API, and this is Principle 8 pointed at behaviour rather than at
symbols. A signature you can guess correctly still leaves you guessing about the default, and the
default is what runs.

The rest of this part is the answers for the two libraries Sutra actually uses, read out of the
installed packages on 2026-09-05. They are not quoted from documentation, because the documentation
does not carry them.

## Why Sutra needs it

`sutra/mcp/hardening.py` is about to state Sutra's timeout policy. If the layers underneath it have
their own, the file will be a comment rather than a policy.

The specific collisions:

- Day 33's `connect_stdio(..., timeout=5.0)` and `connect_http(..., timeout=5.0)` pass that number
  into ADK's connection params. Today you find out that on HTTP it does not become the call deadline.
- Day 40's `sutra/mcp/filtering.py` constructs the toolset. Whatever ADK does about retries happens
  inside a `McpTool` that Sutra's own `with_retries` will then wrap, so the totals multiply.
- Day 45's audit is going to ask what Sutra's per-call deadline is on each transport. "Five seconds"
  is the answer everybody gives and it is wrong for one of the two.

## The mechanism

### What the MCP SDK does about time

The session constructor, read from
`.venv/Lib/site-packages/mcp/client/session.py` on 2026-09-05:

```python
class ClientSession(BaseSession[...]):
    def __init__(
        self,
        read_stream: MemoryObjectReceiveStream[SessionMessage | Exception],
        write_stream: MemoryObjectSendStream[SessionMessage],
        read_timeout_seconds: timedelta | None = None,
        ...
    ) -> None:
```

**Line by line:**

- `read_timeout_seconds` is a `timedelta`, not a float. Passing `5.0` is a type error waiting to
  happen; it is `timedelta(seconds=5)`.
- The default is `None`. That is the headline of this part: **out of the box, a client session has no
  deadline.** Not a long one. None. A call waits until the process is killed.
- It is named `read_timeout_seconds` and it is a *per-request response deadline*, not a socket read
  timeout. The name is the least helpful thing in the file.

And the per-call override, from the same file:

```python
    async def call_tool(
        self,
        name: str,
        arguments: dict[str, Any] | None = None,
        read_timeout_seconds: timedelta | None = None,
        progress_callback: ProgressFnT | None = None,
        *,
        meta: dict[str, Any] | None = None,
    ) -> types.CallToolResult:
```

**Line by line:**

- `read_timeout_seconds` appears again, per call. This is the per-tool deadline
  [2.1](2.1-two-clocks-not-one.md) argued for, and it exists — most people never pass it.
- `meta` is where an idempotency key would ride
  ([1.4](../01-what-may-be-repeated/1.4-the-key-that-makes-a-write-repeatable.md)), keyword-only.
- `progress_callback` is Day 36's
  [2.1](../../../day-36-long-jobs-and-tasks/parts/02-progress/2.1-the-token-you-have-to-ask-for.md).
  Note what it does **not** do: receiving progress does not extend the deadline. A long job that
  reports progress diligently will still be cut off at `read_timeout_seconds`.

The precedence rule, from `.venv/Lib/site-packages/mcp/shared/session.py`:

```python
            # request read timeout takes precedence over session read timeout
            timeout = None
            if request_read_timeout_seconds is not None:
                timeout = request_read_timeout_seconds.total_seconds()
            elif self._session_read_timeout_seconds is not None:
                timeout = self._session_read_timeout_seconds.total_seconds()

            try:
                with anyio.fail_after(timeout):
                    response_or_error = await response_stream_reader.receive()
            except TimeoutError:
                raise McpError(
                    ErrorData(
                        code=httpx.codes.REQUEST_TIMEOUT,
                        message=(
                            f"Timed out while waiting for response to "
                            f"{request.__class__.__name__}. Waited "
                            f"{timeout} seconds."
                        ),
                    )
                )
```

**Line by line:**

- Per-call wins over per-session, and if both are `None` then `timeout` stays `None`.
- `anyio.fail_after(None)` waits **forever**. That is the documented behaviour of `fail_after` with a
  `None` deadline, and it is how "no timeout" is spelled here. So the default path is not a large
  number; it is the absence of a clock, which is exactly Day 38's
  [1.1](../../../day-38-failure-and-migration-lab/parts/01-the-clock/1.1-the-only-clock-is-yours.md).
- The timeout becomes an `McpError` carrying `httpx.codes.REQUEST_TIMEOUT`, which is **408**. Not an
  exception class of its own. So `except TimeoutError` around `call_tool` catches nothing; you have
  to catch `McpError` and inspect the code, or catch broadly and classify.
- `{request.__class__.__name__}` is the sentence that makes the message nearly useless: `request` is
  the `ClientRequest` wrapper, so every timeout says `ClientRequest` regardless of which tool it was.
  This is why `with_timeout` in [2.3](2.3-with-timeout.md) takes a `label`.

Prove all three with the lab's own script:

```bash
cd days/day-44-client-hardening/lab
uv run python sdkclock.py
uv run python sdkclock.py --call
```

**Line by line:**

- The first arm passes nothing at all — the default. The server sleeps for three seconds.
- `--call` passes a session deadline of ten seconds and a per-call deadline of one, which proves the
  precedence rule from the source above.
- **Zero model calls.** The server is `slow_mcp_server.py`, a `FastMCP` instance whose only tool
  sleeps.

Measured on 2026-09-05:

```text

call    read_timeout_seconds : None
elapsed :  3.01s
outcome : ticket 4521: printer offline
```


the finding: the default is not "long", it is "never".

### What ADK does about time

Read from `.venv/Lib/site-packages/google/adk/tools/mcp_tool/mcp_session_manager.py` on
2026-09-05, and quoted exactly as it appears — including its own two-space indentation, which is
why these two blocks are not formatted to this repository's style:

```text
class StdioConnectionParams(BaseModel):
  server_params: StdioServerParameters
  timeout: float = 5.0


class StreamableHTTPConnectionParams(BaseModel):
  url: str
  headers: dict[str, Any] | None = None
  timeout: float = 5.0
  sse_read_timeout: float = 60 * 5.0
  terminate_on_close: bool = True
  httpx_client_factory: CheckableMcpHttpClientFactory = create_mcp_http_client
```

**Line by line:**

- `StdioConnectionParams.timeout` defaults to `5.0` seconds, and this is the number Day 33 passes.
- `StreamableHTTPConnectionParams.timeout` also defaults to `5.0` — and it is the **HTTP** timeout,
  handed to the `httpx` client.
- `sse_read_timeout: float = 60 * 5.0` is 300 seconds, written as a product so the intent is
  legible in the source.
- `terminate_on_close: bool = True` matters for
  [5.1](../05-no-held-connections/5.1-the-chair-you-hold-for-nobody.md): when the connection closes,
  the SDK sends a `DELETE` to tear the session down server-side.

Now the line that decides which of those becomes your per-call deadline, from
`.venv/Lib/site-packages/google/adk/tools/mcp_tool/session_context.py`:

```python
              ClientSession(
                  *transports[:2],
                  read_timeout_seconds=timedelta(seconds=self._timeout)
                  if self._timeout is not None
                  else None,
                  ...
              )
        else:
          # For SSE and Streamable HTTP clients, use the sse_read_timeout
          # instead of the connection timeout as the read_timeout for the session.
              ClientSession(
                  *transports[:2],
                  read_timeout_seconds=timedelta(seconds=self._sse_read_timeout)
                  if self._sse_read_timeout is not None
                  else None,
                  ...
              )
```

**Line by line:**

- The first branch is **stdio**: the session's read timeout is `StdioConnectionParams.timeout`, so
  the `5.0` you set is both the connect budget and the per-call deadline. One number, two jobs — which
  [2.1](2.1-two-clocks-not-one.md) argued against, but at least it is the number you passed.
- The `else` branch is **SSE and Streamable HTTP**, and the comment says exactly what it does: the
  session read timeout comes from `sse_read_timeout`, not from `timeout`. So over HTTP, the
  `timeout=5.0` in Day 33's `connect_http` **is not your call deadline**. Your call deadline is 300
  seconds, by default, and nothing anywhere says so.
- Read that against [2.1](2.1-two-clocks-not-one.md)'s table one more time. Over HTTP a stuck server
  holds an ADK worker for three hundred seconds while your configuration file says five.

And the decision nobody asked for, from `mcp_session_manager.py`, applied to `McpTool._run_async_impl`
in `mcp_tool.py`:

```text
def retry_on_errors(func):
  @functools.wraps(func)
  async def wrapper(self, *args, **kwargs):
    try:
      return await func(self, *args, **kwargs)
    except Exception as e:
      task = asyncio.current_task()
      if task is not None:
        cancelling = getattr(task, 'cancelling', None)
        if cancelling is not None and cancelling() > 0:
          raise
      if _has_cancelled_error_context(e):
        raise
      logger.info('Retrying %s due to error: %s', func.__name__, e)
      return await func(self, *args, **kwargs)

  return wrapper
```

**Line by line:**

- `except Exception as e` catches **everything** that is not a cancellation, including the `McpError`
  a timeout produces. It does not consult the tool's name, its schema or any policy.
- The two cancellation guards are the only exemptions: a task that is being cancelled, and an
  exception whose context holds a cancellation. Those must propagate, or a shutdown would hang.
- `return await func(self, *args, **kwargs)` is a second attempt at the *whole* method — which
  includes `create_session`, so a dead session is replaced. That is the feature: it is a reconnect,
  not a blind repeat.
- But it is also, from Sutra's point of view, **a retry of `tools/call` with no idempotency
  test at all.** Point ADK at a `close_ticket` that times out and it will send it again. Day 38's
  [3.2](../../../day-38-failure-and-migration-lab/parts/03-the-quiet-ones/3.2-the-ticket-closed-twice.md)
  is that failure, and here it is shipped, by default, one layer below anything you write.
- `logger.info(...)` — the only trace this leaves is at INFO. If Sutra's logging is at WARNING, the
  second attempt is invisible.

Summary, as one table, all of it read from the installed source on 2026-09-05:

| Question | `mcp==1.29.1` alone | ADK stdio | ADK Streamable HTTP |
| --- | --- | --- | --- |
| Default per-call deadline | **none** | `timeout` = 5.0s | `sse_read_timeout` = 300.0s |
| Connect budget | your `httpx` client | `timeout` = 5.0s | `timeout` = 5.0s |
| Per-call override available? | yes, `call_tool(read_timeout_seconds=)` | not exposed | not exposed |
| Retries a failed tool call? | no | **once, any exception** | **once, any exception** |
| Timeout error type | `McpError`, code 408 | same | same |

The row that decides Sutra's design is the last-but-one. Because ADK already retries once,
`with_retries(attempts=3)` on top of `McpToolset` is six attempts, and
[3.4](../03-backing-off/3.4-with-retries.md) has to account for it.

## When it breaks

The first break is the one everybody hits and nobody expects: setting a session-wide deadline kills
the handshake. Run the lab's middle arm:

```bash
cd days/day-44-client-hardening/lab
uv run python sdkclock.py --session
```

Measured on 2026-09-05, on Windows:

```text
  |   File "...\mcp\client\session.py", line 183, in initialize
  |     result = await self.send_request(
  |              ^^^^^^^^^^^^^^^^^^^^^^^^
  |   File "...\mcp\shared\session.py", line 294, in send_request
  |     raise McpError(
  | mcp.shared.exceptions.McpError: Timed out while waiting for response to ClientRequest. Waited 1.0 seconds.
  +------------------------------------
```

A one-second session read timeout is perfectly reasonable for a call and completely unreasonable for
`initialize()` on stdio, because `initialize` is preceded by launching a Python interpreter. There is
a **third** clock hiding inside the second one — the handshake — and `read_timeout_seconds` covers
it. The fix is to leave the session deadline generous and set the tight number per call.

The second break is a `float` where a `timedelta` belongs:

```text
AttributeError: 'float' object has no attribute 'total_seconds'
```

It fails at the moment of the first timeout rather than at construction, so it can sit in a codebase
for weeks and then produce an `AttributeError` in the middle of an incident, replacing the timeout
you were trying to diagnose.

The third break is the invisible one, and it is worth a moment because it has no error text at all.
ADK's `retry_on_errors` runs a second attempt and logs at INFO. If your service logs at WARNING and
above, a duplicate `close_ticket` produces **no line anywhere**. You will find it in the customer's
inbox. The mitigation is to raise the log level of `google.adk.tools.mcp_tool` specifically, so that
retry is at least visible, and to keep writes off ADK's tool path entirely until they carry a key.

## In production

**What a professional writes instead of the teaching version.** Nothing relies on a default. Every
connection is constructed with the numbers stated explicitly at the call site — including the ones
that match the default — because an explicit `5.0` survives a library upgrade that changes the
default and an omitted argument does not. And there is a test that asserts the numbers: constructing
Sutra's client and reading back the effective `read_timeout_seconds` is three lines and it is the
only thing that catches a silent default change on the next `uv sync`.

**What degrades at scale or under concurrency.** The 300-second HTTP default is a worker-occupancy
bomb. Under normal traffic it never fires, because everything answers in milliseconds. On the
afternoon a partner's server hangs, every ADK worker that touched it is gone for the full three
hundred seconds, and the service's own dashboards show a healthy process doing nothing. The default was chosen for a
different use — long streamed responses — and inherited by every call.

**The failure mode that only appears with real traffic.** ADK's single retry combining with your
retry policy and with a *server-side* retry, so that one user action becomes eight tool executions.
None of the three layers is wrong on its own. Day 45's audit exists partly to make somebody write
down the product.

**The review comment a senior engineer leaves:** *"you have set `timeout=5.0` on the HTTP connection
params. Read `session_context.py` — on HTTP that is the connect timeout and the call deadline comes
from `sse_read_timeout`, which is three hundred seconds. Either set that too, or pass
`read_timeout_seconds` per call, and add the assertion so the next upgrade cannot move it under us."*

**The interview question:** *"what is the default timeout on the client you use?"* — and the right
answer starts by admitting where you got it. *"I read it out of the installed package rather than the
docs, because the docs did not carry it. For the MCP Python SDK at 1.29.1 the answer is that there is
no default deadline at all — `ClientSession(read_timeout_seconds=None)` ends up in
`anyio.fail_after(None)`, which waits forever. Through ADK it is five seconds on stdio and three
hundred on HTTP, because the HTTP branch reuses `sse_read_timeout` for the session read timeout. And
ADK retries any failed tool call once, regardless of idempotency, which is a thing you want to know
before you put a write behind it."*
