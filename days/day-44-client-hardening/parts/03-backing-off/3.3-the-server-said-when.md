# 3.3 — The server told you when to come back

## One-line answer

A `429` with a `Retry-After` header is the only moment in this whole day when somebody who actually
knows the answer tells you how long to wait, so your backoff ladder is a guess that must give way to
it — and under Addendum 02 every model call path in Sutra must honour it and then escalate rather
than fabricate.

## The story

You take the shoes to the cobbler on the corner because the sole has come away at the toe.

He looks at them for about two seconds, says *"Friday"*, and puts them on the shelf behind him with a
paper tag. That is the entire conversation.

Now: you could come back tomorrow and ask. You could come back on Wednesday and ask again. He would
be polite about it the first time and less polite the second, and both visits would produce the same
sentence, because the shoes need the glue to set and the glue does not care how often you visit.

Nobody does this, because he told you. Friday is not your estimate of how long a sole takes to set;
it is his, from the inside, with the knowledge of what is on the shelf and what he is doing tomorrow.
Any wait you invent is a worse number than the one he gave you, and every visit before Friday costs
you a walk and costs him an interruption.

## The idea in plain language

Almost everything in this section is a client guessing. Backoff is a guess about how long an outage
lasts. Jitter is a guess that other clients exist. A deadline is a guess about how long the work
takes.

`Retry-After` is not a guess. It is the server saying, from the inside, *"there is no point asking
before this."* It usually arrives on one of two responses:

- **`429 Too Many Requests`** — you have exceeded a rate limit. The header says when your window
  reopens.
- **`503 Service Unavailable`** — the server is temporarily unable to serve. The header says when it
  expects to be able to.

The value comes in two spellings, and a client that handles only one will crash on the other:

| Form | Example | Meaning |
| --- | --- | --- |
| delay-seconds | `Retry-After: 120` | wait this many seconds |
| HTTP-date | `Retry-After: Sat, 05 Sep 2026 10:04:07 GMT` | wait until this instant |

The rule that follows is short: **when the server states a delay, that delay wins over your ladder.**
Not `max(retry_after, backoff)`, not "add them together" — the server's number replaces yours,
because yours was a guess about a thing the server knows.

There are two guards on that.

- **Sanity-bound it.** A server that says `Retry-After: 86400` is telling you to come back tomorrow,
  and no request should sleep for a day. If the stated delay exceeds your own deadline, do not sleep
  at all: fail now, honestly, with the stated delay in the error so the layer above can decide.
- **Still jitter it.** Every client that got the same `429` got the same header, so honouring it
  exactly puts the whole fleet back in lockstep at the reopening instant
  ([3.2](3.2-the-same-wait-is-the-wrong-wait.md)). Honour the delay, then add a small random amount
  on top.

And a rate limit is not the same fact as an outage. A `429` says *you asked too often*, which is
information about your own behaviour, and the correct long-term response is to send less rather than
to wait better. [Day 24](../../../day-24-token-accounting-and-budgets/LESSON.md) is where Sutra
learned to count before spending; this part is what to do in the moment you did not.

## Why Sutra needs it

This is not optional in this repository. The zero-budget addendum states it plainly: every model call
path handles HTTP 429 with `retry-after` and backoff, then escalates, and never fabricates a result.
Sutra runs on free tiers — `gemini-3.7-flash` at roughly twenty generate requests per day — which
means 429 is not an exotic failure here. It is the *normal* way the day ends.

Today that rule extends to the MCP path. `sutra_mcp` over Streamable HTTP is an HTTP server, a
gateway in front of it can rate-limit, and a partner's MCP endpoint certainly will. So
`sutra/mcp/hardening.py` owns 429 for MCP the same way Day 21's
[3.1](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.1-which-429-is-it.md) owns it for
models — and that part is worth rereading, because it makes the distinction this one assumes: not
every 429 means the same thing, and the one that means *"your quota for the day is gone"* is not
waitable at all.

## The mechanism

> 🎬 **The scene:** Sutra calls a partner's MCP endpoint during a busy hour. The gateway in front of
> it is rate-limiting, and every response is `429` with `Retry-After` stating exactly how long the
> window has left.
>
> 😬 **The naive fix:** the backoff ladder from [3.1](3.1-waiting-longer-each-time.md). It is a good
> ladder. It was measured.
>
> 💥 **Why it fails:** the ladder's early rungs are much shorter than the window, so every one of
> them is a refused request arriving at a gateway that is already shedding — and the ladder's late
> rungs overshoot, so you wait longer than you needed to. You are both louder and slower than a client
> that simply read the header.
>
> 💡 **The insight:** your ladder is a guess for the case where nobody told you. The moment somebody
> tells you, stop guessing.

A real HTTP server refusing real requests, with the header:

```python
# days/day-44-client-hardening/lab/retry_after.py
WINDOW = 6.0  # the server starts serving this many seconds after it boots


class Handler(http.server.BaseHTTPRequestHandler):
    """Refuses with 429 until the window opens, stating the true seconds remaining."""

    protocol_version = "HTTP/1.1"  # so Content-Length is honoured and the socket is reusable

    def do_POST(self) -> None:  # noqa: N802 - the name is fixed by the base class
        # Read the body even though it is not used. A body left unread stays in the
        # socket and is parsed as the next request line on a keep-alive connection.
        self.rfile.read(int(self.headers.get("Content-Length", "0")))
        REQUESTS_SERVED.append(time.monotonic() - BOOTED)
        remaining = WINDOW - (time.monotonic() - BOOTED)
        if remaining > 0:
            self.send_response(429)
            self.send_header("Retry-After", str(math.ceil(remaining)))
            self.send_header("Content-Length", "0")
            self.end_headers()
            return
```

**Line by line:**

- `protocol_version = "HTTP/1.1"` — the base class defaults to HTTP/1.0, which closes the connection
  after every response and makes `Content-Length` advisory. Keep-alive is what a real gateway does and
  it changes the failure modes, so the lab should use it.
- `self.rfile.read(...)` drains the request body. Skipping it leaves the body in the socket, where
  the server's next `handle_one_request` parses `{}` as a request line and the client gets
  `ConnectionAbortedError: [WinError 10053]`. That was a real half-hour while writing this lab, and
  it is worth knowing because it is the same class of bug as Day 33's
  [5.1](../../../day-33-client-and-transports/parts/05-failure-lab/5.1-the-log-line-that-ate-the-reply.md):
  bytes left in a stream become the next message.
- `remaining = WINDOW - (time.monotonic() - BOOTED)` — the server computes the **true** remaining
  time rather than sending a constant. That is what a real rate limiter does, and it is the reason
  honouring the header lands you at the window's opening instant rather than repeatedly before it.
- `math.ceil(remaining)` because `Retry-After` in delay-seconds form is an integer. Rounding *up*
  rather than down: rounding down guarantees one more refused request.
- `send_header("Content-Length", "0")` on the refusal. A 429 with no body still needs a length under
  HTTP/1.1, or the client waits for a body that is not coming — a timeout produced by an error
  response, which is a genuinely confusing thing to debug.
- `REQUESTS_SERVED` is appended **before** the decision, so it counts refusals too. Counting only
  successes would hide the entire cost being measured.

And the client's one branch:

```python
# days/day-44-client-hardening/lab/retry_after.py (continued)
def attempt(url: str) -> tuple[int, int | None]:
    """Send one request. Return (status, retry_after_seconds_or_None)."""
    request = urllib.request.Request(url, data=b"{}", method="POST")
    try:
        with urllib.request.urlopen(request, timeout=2.0) as response:
            return response.status, None
    except urllib.error.HTTPError as err:
        header = err.headers.get("Retry-After")
        err.read()  # drain the refusal body, or the socket is left half-open
        err.close()
        return err.code, int(header) if header else None
```

**Line by line:**

- `urllib.error.HTTPError` is how urllib reports a `4xx` or `5xx`. It is an exception *and* a response
  object — you can read headers and a body off it — which is unusual and is exactly what you need
  here, because the header you want is on the error.
- `err.headers.get("Retry-After")` is case-insensitive, because `email.message.Message` (which is
  what `headers` is) treats header names that way. Do not lower-case the name yourself; HTTP headers
  are case-insensitive and a hand-rolled comparison is one more thing to get wrong.
- `err.read()` and `err.close()` drain and release the connection. Without them the socket sits in a
  half-open state and the *next* request to the same host can fail for reasons that have nothing to
  do with the server.
- `int(header) if header else None` handles the absent header, and **only** the delay-seconds form.
  The HTTP-date form would raise `ValueError` here. That is a deliberate simplification in a lab and
  a real bug in production — see *When it breaks*.
- `timeout=2.0` on the `urlopen` call, because even a refusal deserves a deadline
  ([2.1](../02-the-deadline/2.1-two-clocks-not-one.md)). A rate limiter that is itself overloaded can
  hang.

The decision is a single expression:

```python
# days/day-44-client-hardening/lab/retry_after.py (continued)
            backoff = 0.5 * (2 ** (attempt_no - 1))
            wait = float(retry_after) if (honour and retry_after) else backoff
```

**Line by line:**

- `backoff` is still computed in both arms, so the transcript can print what the ladder *would* have
  said. Being able to see the guess next to the fact is most of the teaching.
- `retry_after` is checked for truthiness, not just for `None`, so a `Retry-After: 0` falls back to
  the ladder rather than producing a zero-second wait and an immediate hammer.
- The server's number **replaces** the ladder rather than being combined with it. No `max`, no sum.
- In production this line ends with `+ rng.uniform(0, 0.5)`, for
  [3.2](3.2-the-same-wait-is-the-wrong-wait.md)'s reason: every client got the same header.

Run both arms:

```bash
cd days/day-44-client-hardening/lab
uv run python retry_after.py
uv run python retry_after.py --honour
```

**Line by line:**

- The first arm ignores the header and uses the ladder — which is what most clients do, because most
  clients never look.
- `--honour` is the ablation switch.
- **Zero model calls.** The 429 comes from a local `http.server`, not from a provider.

Measured on 2026-09-05:

```text
policy: ignore Retry-After, back off
   0.08s attempt 1: HTTP 429, Retry-After=6
    waiting 0.50s (backoff alone would be 0.50s)
   0.58s attempt 2: HTTP 429, Retry-After=6
    waiting 1.00s (backoff alone would be 1.00s)
   1.59s attempt 3: HTTP 429, Retry-After=5
    waiting 2.00s (backoff alone would be 2.00s)
   3.59s attempt 4: HTTP 429, Retry-After=3
    waiting 4.00s (backoff alone would be 4.00s)
   7.59s attempt 5: HTTP 200, Retry-After=None

answered at            : 7.59s
requests the server saw: 5
of which refused       : 4
```

```text
policy: Retry-After wins
   0.08s attempt 1: HTTP 429, Retry-After=6
    waiting 6.00s (backoff alone would be 0.50s)
   6.08s attempt 2: HTTP 200, Retry-After=None

answered at            : 6.08s
requests the server saw: 2
of which refused       : 1
```

The honouring client is **faster and quieter at the same time**: 6.08s against 7.59s, two requests
against five. There is no trade here. Every one of those three extra requests was sent to a server
that had already said, in writing, that it would refuse — and the ladder's last rung overshot the
window by a second and a half on top of that.

## When it breaks

The first break is the date form. A server that sends `Retry-After` as an HTTP-date — which is
entirely legal and which several CDNs do — meets a client that assumed seconds:

```text
urllib.error.HTTPError: HTTP Error 429: Too Many Requests

During handling of the above exception, another exception occurred:

Traceback (most recent call last):
    status, ra = attempt(url)
                 ^^^^^^^^^^^^
    return err.code, int(header) if header else None
                     ^^^^^^^^^^^
ValueError: invalid literal for int() with base 10: 'Sat, 05 Sep 2026 10:04:07 GMT'
```

Read the first two blocks together. The `429` is still there, in the chained context, and the thing
that reaches your caller is a `ValueError`.

The `ValueError` is raised inside the error-handling path, so it replaces the 429 entirely and
whatever is above sees a `ValueError` where it expected a rate limit. Parse with
`email.utils.parsedate_to_datetime` when the value is not all digits, and treat an unparseable value
as "no header" rather than as a crash.

The second break is honouring a delay that is longer than your own life. A daily quota exhaustion
answers with a delay measured in hours:

```text
   0.05s attempt 1: HTTP 429, Retry-After=39871
    waiting 39871.00s (backoff alone would be 0.50s)
```

The request is now asleep until tomorrow, holding a worker, inside a request that had two seconds.
This is the case that must **not** sleep: when the stated delay exceeds the remaining budget from
[2.2](../02-the-deadline/2.2-the-deadline-never-reached.md), fail immediately and put the delay in
the error, so the caller can tell a human *"the quota is exhausted until tomorrow"* rather than
hanging. This is the shape of the free-tier daily limit Sutra actually lives under, and Day 24's
[2.2](../../../day-24-token-accounting-and-budgets/parts/02-two-ceilings/2.2-reading-the-ceiling-off-a-refusal.md)
is where the two kinds of 429 were told apart.

The third break is honouring it perfectly across a fleet. Every client that was refused got the same
`Retry-After: 6`, so every client returns at the same instant:

```text
second  retries arriving    shed
     6               200     160
```

The window opened and was immediately consumed by the herd that had been politely waiting for it.
Honour the header, then jitter on top of it. The header tells you the earliest useful moment, not the
moment you must arrive.

## In production

**What a professional writes instead of the teaching version.** The header parser handles both forms
and treats anything unparseable as absent. The delay is bounded by the request's remaining budget, and
exceeding it is an immediate honest failure rather than a sleep. A small random amount is added. And
the whole thing is one function, `retry_delay(response, attempt, policy) -> float | None`, returning
`None` for "do not retry at all" — because the same code path also has to handle the `429` that means
*your quota for the day is gone*, which is not a wait, it is a stop.

**What degrades at scale or under concurrency.** The rate limit is usually per key or per account,
not per process. Twenty workers sharing one API key each back off politely and independently, and
between them still exceed the limit — because each one is measuring its own behaviour against a
budget that belongs to all of them. At that point client-side backoff cannot fix it and the answer is
a shared limiter: Day 24's leaky bucket, running once for the whole fleet, in front of the calls.

**The failure mode that only appears with real traffic.** A 429 that is not about you. A gateway
shedding load under a neighbour's traffic returns 429 to everybody, and a client that treats it as
"I am asking too often" reduces its own rate for hours after the neighbour has gone. The distinction
is not always visible in the response, and the practical defence is to recover the rate gradually
after the refusals stop rather than staying at the reduced rate.

**The review comment a senior engineer leaves:** *"you back off on a 429 and never look at
`Retry-After`. The server is telling us when the window reopens and we are guessing. Honour it, cap
it at the remaining request budget, add jitter, and handle the date form — one of our upstreams sends
it."*

**The interview question:** *"how do you handle a 429?"* — *"By reading it. The header is the only
number in a retry policy that is not a guess, so `Retry-After` replaces my backoff rather than being
combined with it — I measured it on a local rate limiter and honouring the header answered sooner,
in 6.08 seconds against 7.59, with two requests instead of five. Three guards, though: parse both the
seconds and the date form, refuse to sleep longer than the request's own remaining budget and fail
honestly instead, and add jitter on top, because every client that was refused got the same number
and will otherwise return in lockstep the instant the window opens. And I distinguish 'you are going
too fast' from 'your daily quota is gone'. The second one is not something you wait out inside a
request."*
