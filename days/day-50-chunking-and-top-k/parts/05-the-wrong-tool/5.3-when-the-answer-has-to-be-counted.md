# 5.3 — When the answer has to be counted

## One-line answer

Ranking visits every row and returns the nearest few; counting has to visit every row and **keep all of
them**, so *"how many tickets are about signing in"* has no answer in a top-k result at all — the true
answer is **12 of 52**, and retrieval returns three tickets and no number.

## The story

There is a function at the weekend and somebody asks how many chairs the house has.

You know the house. You have lived in it for years and you can picture every room, so you start
answering from memory: six around the dining table, two by the window, the plastic ones stacked on the
balcony, four or five of those. You say about fifteen.

Then somebody actually walks round with a notepad. Dining table six. Window two. Balcony seven, not four
or five. Two in the back room you had forgotten entirely because nobody sits in them. One in the
bathroom, which is a chair, whatever you think about it being there.

Eighteen.

You were not being careless. You were doing the thing memory does — retrieving the chairs that come to
mind most readily — and the chairs that come to mind most readily are not all the chairs. Counting is a
different activity from remembering, and the only way to do it is to go round every room.

## The idea in plain language

Retrieval and counting are different operations, and the difference is what happens to the rows that are
not the best.

**Ranking** scores every row, sorts them, and **throws away everything except the top k**. That
discarding is not an implementation detail; it is the point of the operation. You asked for the nearest
few and the nearest few is what you get.

**Aggregation** — counting, summing, averaging, grouping, finding a maximum — has to visit every row and
**keep the result of every visit**. There is no top-k version of *"how many"*. An answer built from the
three nearest rows is not an approximate count; it is not a count at all.

The class of question is bigger than it first looks:

- *"How many tickets mention sign-in?"* — a count.
- *"Which customer has opened the most tickets?"* — a maximum over a grouping.
- *"What is our average time to resolve?"* — a mean.
- *"Has anyone reported this more than twice?"* — a threshold on a count.
- *"What are the top three causes this month?"* — a grouped count, sorted.

Every one of them requires the whole archive and none of them is a similarity search. Day 39 built the
right tool for them: the desk's archive in SQLite, with hand-written queries behind narrow doors
([1.1](../../../day-39-database-tools/parts/01-the-archive/1.1-the-numbers-on-the-back-of-a-bill.md)).
`SELECT count(*) FROM tickets WHERE ...` visits every row by definition. That is not vectors done better;
it is a different operation.

There is a second, subtler thing wrong with asking retrieval to count, and it is the one that catches
people who half-know this already. Even if you set k to the size of the whole archive — retrieve all
fifty-seven rows and let the model count them — you have not fixed it. You have moved the counting into
the model, which counts by reading, which is the least reliable way to count anything, and you have paid
[3.1](../03-the-k-is-a-budget/3.1-k-is-a-budget-not-a-preference.md)'s token bill for the privilege.

## Why Sutra needs it

The support desk is asked to count constantly, because counting is how a team decides what to work on.
*How many of these did we get this week? Is this one customer or twenty? Which failure is most common?*
Those questions arrive in the same box as *"has this happened before"* and they sound similar enough
that nobody separates them.

Sutra has both tools already. Day 39 gave it SQL over the archive; Day 49 gave it retrieval. What it has
not had is a written rule for which question goes where, and
[6.1](../06-in-production/6.1-the-five-questions-in-order.md) writes it. This part is the evidence for
one row of that rule.

## The mechanism

Ask the count question of the index, then count it properly beside it:

```python
# days/day-50-chunking-and-top-k/lab/wrongtool.py
SIGN_IN_WORDS = {"signed", "sign", "cookie", "password", "authenticator", "two", "provider"}


def count(index) -> None:
    query = "how many tickets are about signing in"
    print(f"question: {query!r}\n")
    show(index, query)
    true_count = sum(
        1
        for ref, text in DOCS.items()
        if SIGN_IN_WORDS & set(tokenize(text)) and ref.startswith("ticket:")
    )
    tickets = sum(1 for ref in DOCS if ref.startswith("ticket:"))
    print(f"\n  the answer, by counting: {true_count} of {tickets} tickets")
```

**Line by line:**

- `SIGN_IN_WORDS` is written out as a set, at the top of the module, because *"about signing in"* is a
  judgement and a judgement in a counting question has to be **stated** before it can be counted. That is
  half of what makes counting different: a count is only as defensible as the rule it counted by, and
  the rule has to be visible so somebody can disagree with it.
- `SIGN_IN_WORDS & set(tokenize(text))` is a set intersection, truthy when the document uses any of those
  words. Crude, and stated crudely, which is better than a sophisticated rule nobody can inspect.
- `ref.startswith("ticket:")` restricts the count to tickets, because the question said tickets and the
  archive also contains KB articles. A count that quietly includes the wrong population is the most
  common way an aggregate lies.
- The loop runs over `DOCS` — the **documents** — and not over `index.refs`, which would be chunks. At a
  chunk size of nine hundred a long ticket is two rows, and counting rows would count that ticket twice.
  This is the chunking decision from
  [1.1](../01-the-unit-you-index/1.1-the-unit-you-store-is-the-unit-you-find.md) reaching forward to bite
  an aggregate, and it is exactly the sort of error that makes a number wrong by a plausible amount.
- Both numbers are printed — `12 of 52` — because a count without its denominator is a number that cannot
  be argued with.

Run it:

```bash
cd days/day-50-chunking-and-top-k/lab
uv run python wrongtool.py count
```

**Line by line:**

- Same index, same helper, no floor, exactly like the other three arms of this section.
- The retrieval runs first and the true count second, so the reader forms an impression from the
  retrieval before seeing what the answer actually was.

Measured on 2026-09-05:

```text
question: 'how many tickets are about signing in'

  retrieval, k=3:
    0.122  ticket:4612#0  'Ticket 4612. API returns a rate limit with no retry header. Auto'
    0.118  ticket:4544#0  'Ticket 4544. Dashboard loads blank white. After signing in the d'
    0.114  ticket:4542#0  'Ticket 4542. Mobile app crashes on opening a board. The app clos'

  the answer, by counting: 12 of 52 tickets
  retrieval returned 3 rows and no number. It cannot count, because ranking
  the nearest few rows is not the same operation as visiting every row.
```

**The answer is twelve.** Retrieval returned three rows, and it is worth being precise about how badly
those three rows fail to be an answer:

- **The count is wrong by a factor of four**, if anybody reads "three results" as "three tickets".
- **The three are not even the right three.** `ticket:4612` is about API rate limits and `ticket:4542` is
  about the mobile app crashing. Only `ticket:4544` mentions signing in at all, and it mentions it in
  passing — the ticket is about a blank dashboard.
- **k was the limit, not the archive.** Twelve tickets qualify. Retrieval stopped at three because three
  is what it was asked for, and it would have stopped at three if the answer had been fifty.

Now look at the scores: `0.122`, `0.118`, `0.114`. They are low, and they are almost identical — a spread
of eight thousandths across three results. That flatness is itself a signal, and it is one
[4.2](../04-the-floor/4.2-there-is-no-floor-that-separates-them.md)'s production section named: when the
top score and the rest are indistinguishable, the ranking has not discriminated between anything. Here it
has not, because there is nothing to discriminate — the question is not *about* any document, it is
*about the collection*.

And these scores are below `SIM_FLOOR = 0.20`, so Sutra's shipped rule would return nothing for this
question. That is the right outcome by luck rather than by design: the desk would say *"I found nothing
close enough to be useful"*
([4.3](../04-the-floor/4.3-nothing-is-an-answer.md)), which is honest and is still not the answer. The
answer is twelve, it exists, and it is one line of SQL away.

## When it breaks

The floor catching this question is not something to rely on, and the way to see that is to ask a
counting question with distinctive words in it.

*"How many tickets are about the export failing"* uses `export` and `failing`, both of which are rare
enough to be informative, and it will match export tickets with strong scores. The rule from section 4
passes it. Three export tickets come back with confident scores, and a model asked *"how many"* and
handed three documents will very often answer *"three"* — which is a number, produced from the value of
`k`, presented as a fact about the archive.

That is the failure at its purest: **the answer is the value of a configuration constant**. Change
`TOP_K` to five and the same question returns "five". Nothing in the pipeline is broken, nothing is
logged, and the number is completely fabricated.

There is no error text here, and the absence is the point. Counting failures do not raise. What they
produce is:

```text
    0.122  ticket:4612#0  'Ticket 4612. API returns a rate limit with no retry header. Auto'
```

— three rows, low but present, which a model turns into a paragraph containing a number. The only
defences are structural: route the question elsewhere before it reaches retrieval
([6.1](../06-in-production/6.1-the-five-questions-in-order.md)), or make the retrieval tool's description
say plainly that it cannot count, which is Day 4's lesson that
[1.3](../../../day-04-tools-by-hand/parts/01-the-schema/1.3-the-description-is-the-prompt.md) taught —
the description is the prompt, and a tool that does not say what it cannot do will be asked to do it.

## In production

**What a professional writes instead.** They give the agent both tools and make the boundary explicit in
the tool descriptions. The retrieval tool's description says *"finds passages similar to a question;
cannot count, total or compare across the archive"*, and the query tool's description says *"answers
questions about how many, which is most, and totals over the whole archive"*. Descriptions are how a
model routes ([1.3](../../../day-04-tools-by-hand/parts/01-the-schema/1.3-the-description-is-the-prompt.md)),
and a retrieval tool whose description does not name its limits will be handed every question in the
building.

The pattern that combines the two is worth knowing by name: **retrieve to find, query to count**. Use
retrieval to identify which documents are relevant, then use a real query over identifiers to aggregate
over them. The two are composed, in that order, with the counting always done by something that visits
every row.

**What degrades at scale.** The gap between the top-k answer and the true answer widens with the archive.
At fifty-two tickets, twelve qualify and retrieval returns three; at fifty-two thousand, twelve thousand
qualify and retrieval still returns three. The *wrongness* of the answer grows without limit while the
output looks identical, and there is no size at which the failure becomes visible on its own.

**The failure mode that only appears with real traffic.** Counting questions arrive disguised as
narrative ones. *"Is this a widespread problem?"* is a counting question in ordinary clothes, and so is
*"are we seeing a lot of these?"* and *"is this the first time?"* — that last one especially, because
retrieval returning nothing genuinely does suggest *"first time"*, and it suggests it just as strongly
when the index is stale or the chunking buried the earlier case.

**The review comment a senior engineer leaves:** *"The retrieval tool's description does not say it
cannot count, so the model will use it for counting — it already does. Add the limitation to the
description, and while you are in there, note that `count()` iterates `DOCS` and not `index.refs`; if
somebody 'fixes' that to use the index, every long ticket gets counted twice and the number will be
wrong in a way nobody will spot for months."*

**The interview question:** *"Why can't a vector search answer 'how many'?"* An honest answer: *"Because
ranking throws away everything except the top k, and that discarding is the operation, not a limitation
of the implementation. An aggregate has to visit every row and keep every result. I tested it on my
archive: 'how many tickets are about signing in' has a true answer of twelve out of fifty-two, and
retrieval returned three rows, two of which were not about signing in at all — the top hit was a ticket
about API rate limits. The dangerous version is when the question has distinctive words in it, because
then the scores are strong, the results are genuinely relevant, and a model asked 'how many' will answer
with the number of rows it was given. The answer is then literally the value of your top-k constant. The
fix is routing plus honest tool descriptions: retrieval says it cannot count, a query tool says it can,
and if you need both you retrieve to find the relevant documents and then aggregate over their
identifiers with something that visits every row."*
