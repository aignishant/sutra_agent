# 4.3 — Nothing is an answer

## One-line answer

An empty result is a legitimate, useful and under-used outcome, and it has to be **said** rather than
returned as silence: *"I searched the archive and found nothing close enough to be useful — nobody has
written this one up yet"* is a sentence the desk needs, and it is not the same sentence as *"there is no
past case"*.

## The story

Two students sit the same paper, and the paper has negative marking: a right answer is worth a mark, a
blank is worth nothing, and a wrong answer costs you half.

One of them fills in every box. Where she does not know, she picks the option that looks most like the
others and moves on, because an empty box feels like giving up and a filled one at least has a chance.

The other leaves eleven boxes blank. It feels worse. Handing in a paper with gaps in it feels like
admitting something, and she thinks about it on the way out.

The marks come back and the second paper is higher, and not by a little. Every guess on the first paper
that went wrong took away a mark that a correct answer elsewhere had earned. The blanks cost nothing at
all, and they told the teacher exactly which topics to go over.

The blank was never the absence of an answer. It was an answer: *I do not know this one.*

## The idea in plain language

Retrieval has three possible outcomes and almost every implementation ships two:

1. **Here are the rows.** Implemented everywhere.
2. **An error.** The store is down, the query is malformed. Implemented everywhere.
3. **I searched and there is nothing here.** Usually not implemented at all, because
   [4.1](4.1-cosine-never-says-it-does-not-know.md) showed that ranking cannot produce it, and once
   [4.2](4.2-there-is-no-floor-that-separates-them.md) gives you a rule that *can* produce it, the empty
   list still has to be turned into words.

The third outcome is genuinely valuable, and it is worth being specific about who it is valuable to.

**To the support agent**, it closes a door. *"Nobody has written this up"* means: stop reading old
tickets, start investigating, and when you are done, write it up so the next person does not have to.
That is an instruction. A wrong ticket is an invitation to spend the afternoon in the wrong place.

**To the system**, it is a measurable signal. A rising rate of empty results means the archive has a gap,
or the questions have moved, or somebody is asking this desk about something it does not cover. Every one
of those is worth knowing, and none of them is visible when every question returns three rows.

There is one distinction that has to be got right, and it is the difference between an honest system and
a subtly dishonest one:

- *"I found nothing close enough to be useful"* is a statement about **the search**.
- *"There is no past case like this"* is a statement about **the world**.

The retriever knows the first and cannot know the second. Its index may be stale, its chunking may have
buried the answer ([2.3](../02-measuring-the-cut/2.3-the-cut-that-kept-the-ticket-and-lost-the-fix.md)),
the question may use words no document uses, or the floor may have cut a real answer scoring `0.180`
([4.2](4.2-there-is-no-floor-that-separates-them.md) ships a rule that does exactly this, on purpose).
Saying the second sentence when you only know the first is fabricating a result, which is the failure
Principle 10 exists to forbid, wearing the costume of caution.

Day 46's [4.2](../../../day-46-sessions-vs-memory/parts/04-the-choice/4.2-sutras-memory-policy.md) wrote
this as rule four of Sutra's memory policy — *a miss is reported, not interpreted*. This part is the
mechanism under that rule, and the words that come out of it.

## Why Sutra needs it

The Phase 7 gate is *"Seen anything like this before?" answered at $0*. Everything in Phase 7 so far has
worked on the assumption that the answer is yes. **No is an answer to that question**, it is a correct
answer surprisingly often, and a desk that cannot give it has not answered the gate's question — it has
answered a different, easier one.

There is also a downstream reason. Phase 8 gives Sutra a researcher that holds several tools and chooses
between them per question. A tool that always returns something cannot be routed away from, because
routing needs a failure signal. `retrieve()` returning an empty list is the signal that lets a later
agent try a different tool, and [6.1](../06-in-production/6.1-the-five-questions-in-order.md) is the
procedure that uses it.

## The mechanism

The rule from [4.2](4.2-there-is-no-floor-that-separates-them.md), applied, and then turned into a
sentence:

```python
# days/day-50-chunking-and-top-k/lab/nothing.py
def survivors(index, query: str, floor: float, minimum: int) -> list[tuple[float, str]]:
    """The rows that survive both conditions."""
    return [
        (score, ref)
        for score, ref in search(index, query, TOP_K, floor)
        if shared_informative(index, query, ref) >= minimum
    ]
```

**Line by line:**

- The return type is a `list`, and an empty list is a perfectly ordinary value of that type. No
  `Optional`, no sentinel, no exception. *Nothing found* is not an error condition; it is a result, and
  typing it as one is the first place the design either tells the truth or does not.
- It returns `(score, ref)` pairs rather than text, so the caller can log the scores of what survived —
  and, when nothing survives, the caller can still ask `search` what the top score *was*, which is the
  number you need to tell a stale floor from an empty archive.
- Both conditions are applied in one comprehension, in the order they are cheapest: `search` has already
  dropped everything below the floor, so `shared_informative` runs on at most `TOP_K` rows.
- There is deliberately no `if not rows: raise`. Raising here would force every caller into a `try`, and
  the one thing a caller must never do with this outcome is treat it as an exception to be swallowed —
  Day 21's
  [3.3](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.3-giving-up-honestly.md)
  is the day that argued this out.

And the words:

```python
# days/day-50-chunking-and-top-k/lab/nothing.py
            if rows:
                print(f"    {len(rows)} row(s) survive; best {rows[0][0]:.3f} from {rows[0][1]}")
            else:
                print("    nothing survives. The desk answers:")
                print('    "I searched the archive and found nothing close enough to be useful.')
                print('     Nobody has written this one up yet."')
```

**Line by line:**

- The sentence names the **action taken** — *"I searched the archive"* — so the reader knows a search
  happened rather than that the desk skipped it.
- *"found nothing close enough to be useful"* is a claim about the search and its threshold, which is a
  thing the retriever actually knows.
- *"Nobody has written this one up yet"* is the part the agent can act on, and it is phrased about the
  **archive**, not about the world: nobody has written it up is a statement about documents, where *"this
  has never happened"* would be a statement about reality that no index can support.
- What is **not** in the sentence matters as much. No apology, no "unfortunately", no suggestion that
  something went wrong. Nothing went wrong. And no *"but here are three tickets that might be related"*,
  which is the instinct that undoes the whole part.

Run it:

```bash
cd days/day-50-chunking-and-top-k/lab
uv run python nothing.py --say
```

**Line by line:**

- `--say` runs the shipped rule — floor `0.20`, at least two shared informative terms — over two
  unanswerable questions and one real one, and prints what the desk would say for each.
- Three questions rather than one, because a refusal that fires on everything is not a refusal, it is a
  broken retriever, and the third line is the control.

Measured on 2026-09-05:

```text
  question: 'how do I claim travel expenses for a client visit'
    nothing survives. The desk answers:
    "I searched the archive and found nothing close enough to be useful.
     Nobody has written this one up yet."

  question: 'the office printer jams on thick paper'
    nothing survives. The desk answers:
    "I searched the archive and found nothing close enough to be useful.
     Nobody has written this one up yet."

  question: 'customer bounced back to the sign-in page during single sign-on'
    3 row(s) survive; best 0.380 from ticket:4610#0
```

The printer question scored `0.388` in [4.1](4.1-cosine-never-says-it-does-not-know.md) — higher than
nine of the ten real answers — and it now returns nothing, because the second condition looks at
something the score cannot see. The real question is unaffected: three rows survive, best `0.380`.

That is the whole repair, and it is worth noticing that the two numbers `0.388` and `0.380` are still in
the same order they always were. Nothing about the ranking improved. A different question was asked
about the result.

## When it breaks

**Silence is not the same as saying nothing.** If `retrieve()` returns `[]` and the calling code renders
that as an empty section in the prompt, the model sees a heading with nothing under it and is left to
guess what that means. Models fill gaps. The empty list has to be turned into an explicit sentence
*before* it reaches the model, or the model will supply its own explanation of why the section is empty —
and the explanations it supplies are fluent.

**The refusal can be over-explained into a lie.** The tempting rewrite is *"There is no similar case in
our history"*, which is shorter and reads better and is a claim the system cannot support. The archive is
one store, chunked one way, filtered by a floor that is documented to drop a real answer scoring `0.180`.
Anything that says *"there is no"* rather than *"I did not find"* has crossed from reporting to
interpreting.

**A refusal that nobody counts is a refusal nobody learns from.** The failure with no error text is this:

```text
    nothing survives. The desk answers:
```

If that path is not logged with the query and the top score alongside it, then a floor that has drifted
too high looks identical to an archive with a genuine gap, and both look identical to normal operation.
There is no traceback, no exit code, nothing in the metrics. The system is quietly answering fewer
questions and reporting perfect health.

**And a refusal rate can go wrong in both directions.** Too many refusals and the desk is useless and
agents stop asking. Too few and [4.1](4.1-cosine-never-says-it-does-not-know.md) is back. The rate itself
is the thing to watch, not either number in the rule.

## In production

**What a professional writes instead.** The refusal is not a string in the retrieval layer; it is a
**typed outcome** the caller has to handle. A small result object carrying `rows`, `top_score` and
`reason` — *below floor*, *too few shared terms*, *empty index* — lets the agent's instruction branch on
the reason, lets the logs distinguish the three, and makes it impossible for a caller to silently render
nothing. The user-facing sentence is then written once, in the layer that talks to people, and the
retrieval layer stays a function that returns facts about a search.

They also **give the refusal somewhere to go**. A good empty answer offers the next step: escalate to a
specialist, open a new investigation, or — the one that compounds — prompt the agent to write this case up
when they solve it, so the next occurrence has a neighbour. A retrieval system that reports its own gaps
is a system that gets better; one that hides them stays exactly as good as the day it launched.

**What degrades at scale.** Refusals get rarer as the archive grows, and not because coverage improved.
With more documents there is always something that clears two shared informative terms, so the rule
weakens on its own and the refusal rate drifts down towards zero — which reads on a dashboard as coverage
improving. Watching the refusal *rate* over time, and re-running `floor.py` when the index is rebuilt, is
the defence.

**The failure mode that only appears with real traffic.** People treat the refusal as a bug. The first
time an agent sees *"nobody has written this one up"* they will report it, because every other system they
use answers everything, and an honest system feels broken by comparison. The production answer is partly
copy — the sentence has to sound like a decision rather than a failure — and partly education, and it is
the reason the wording in this part avoids the word "sorry".

**The review comment a senior engineer leaves:** *"Do not return an empty list and let the prompt builder
decide what that means. Return a result object with the reason and the top score, log every refusal with
the query, and put the refusal rate on the dashboard next to the hit rate. And keep the wording as it is —
'I found nothing' is defensible, 'there is no past case' is a claim we cannot make and somebody will
shorten it to that within a month."*

**The interview question:** *"What does your retrieval system do when it has no good answer?"* An honest
answer: *"It says so, in words, and the wording is deliberate. It says 'I searched the archive and found
nothing close enough to be useful — nobody has written this one up yet', and it does not say 'there is no
similar case', because the first is a statement about my search and the second is a statement about the
world that no index can support. Getting there needed a rule that can produce an empty result at all,
because cosine similarity always returns something: a score floor plus a check that the matched row shares
at least two meaningful words with the question. The thing I would emphasise is that the empty result is a
normal return value, not an exception and not silence — if you return an empty list and let the prompt
builder render it as a blank section, the model invents an explanation for the blank. And I log the
refusals with their top score, because a floor that has drifted too high and an archive with a real gap
look identical from the outside."*
