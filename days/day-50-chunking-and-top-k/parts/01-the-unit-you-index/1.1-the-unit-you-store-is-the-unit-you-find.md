# 1.1 — The unit you store is the unit you find

## One-line answer

Retrieval can only ever hand back the pieces you decided to store, so the size of a stored piece —
its **chunk** — is chosen before anybody asks a question, and no amount of clever ranking afterwards
can hand back half of one.

## The story

A friend sends you a voice message with directions to their new flat. It runs on for a while. They
start with how their week has been, then the road works near the bridge, then the name of the turning
you need, then the code for the gate, then a story about the neighbour's dog.

You save it, because you know you will need it.

On the day, you are standing at a junction in the rain with one hand on the handlebars, and you need
one thing: the name of the turning. You press play. You get the week. You get the bridge. You skip
forward too far and land in the dog. You go back and overshoot again.

The message contains the answer. It has contained the answer the whole time. But the thing you saved
was a five-minute recording, and the thing you need is four words, and there is no way to ask the
recording for only the four words. Your friend could have sent five short messages instead — the
week, the bridge, the turning, the gate code, the dog — and you would have found the turning at a
glance.

What you can find later is decided by what you chose to save as one piece.

## The idea in plain language

**Retrieval** is the act of searching your own stored documents by meaning rather than by exact
words, and handing the best few to the model. Day 49 built it: every document is turned into a
**vector** — a list of numbers that stands for the meaning of the text — and a question is turned
into a vector the same way, so the documents whose numbers point in the same direction as the
question's numbers are the ones that come back.

The word for one stored piece is a **chunk**. A chunk is not a document and a document is not a
chunk. A chunk is whatever you decided to turn into one vector and store under one address.

That decision is called **chunking**, and it happens at **index time** — when you build the store —
not at **query time**, when somebody asks something. This is the whole reason it matters. At query
time you can change the question, change how many results you take, change the order you paste them
in. You cannot change what a stored row *is*. If a fact and its explanation went into the store as
one row, they come back together. If a blind cut put them in two different rows, no ranking in the
world reunites them, because ranking chooses between rows and does not build new ones.

Two words that will keep coming back today:

- A **row** is one entry in the index: one chunk of text, one vector, one address. Day 49's index
  had one row per document. Today an index may have several rows per document.
- A **ref** is that address. Day 49 used `ticket:4610` and `kb:KB-104`. Today, when a document is cut
  into pieces, the pieces are `ticket:4610#0`, `ticket:4610#1`, and so on, so that the document a
  piece came from is always recoverable by splitting on the `#`.

Day 46's [1.2](../../../day-46-sessions-vs-memory/parts/01-the-line/1.2-putting-versus-finding.md)
drew the line between an **address** — you know the key, you read the value back, it is either there
or it fails loudly — and a **description**, where you say roughly what you want and something comes
back. Chunking is a decision about what sits behind each address, made before any description is ever
offered.

## Why Sutra needs it

The desk's whole reason for having an archive is the Phase 7 gate: *"Seen anything like this
before?"* answered at $0. Day 49 made that question answerable. It indexed the archive one document
per row, which is the obvious first thing to do and is exactly right for a two-line ticket.

The archive is not made of two-line tickets. It has an incident review in it. Real desks have runbooks,
post-mortems, contract clauses and email threads, and every one of them is many ideas in one file.
The moment one of those goes into the store as a single row, the store starts giving worse answers
for reasons nobody can see from the outside, because nothing in the response says *"this row is
three thousand characters and only two hundred of them were relevant"*.

[1.2](1.2-the-document-that-averages-itself-away.md) measures exactly how much worse, on the archive
you already have. [2.2](../02-measuring-the-cut/2.2-one-table-seven-chunk-sizes.md) turns it into a
table you can act on.

## The mechanism

Start with what the store actually holds. This is Day 49's arithmetic, restated in the lab so today's
measurements run whether or not you have finished typing the project module:

```python
# days/day-50-chunking-and-top-k/lab/_index.py
def chunk(text: str, size: int, overlap: int = 0) -> list[str]:
    """Cut text into overlapping windows of `size` characters."""
    if overlap >= size:
        raise ValueError(f"overlap {overlap} must be smaller than size {size}")
    out: list[str] = []
    start = 0
    while start < len(text):
        out.append(text[start : start + size])
        start += size - overlap
    return out


def split_docs(docs: dict[str, str], size: int | None, overlap: int = 0) -> dict[str, str]:
    """Return the archive as it will be indexed: whole documents, or chunks with `#n` refs."""
    if size is None:
        return dict(docs)
    out: dict[str, str] = {}
    for ref, text in docs.items():
        for n, piece in enumerate(chunk(text, size, overlap)):
            out[f"{ref}#{n}"] = piece
    return out


def parent(ref: str) -> str:
    """The document a chunk came from. `ticket:4610#3` -> `ticket:4610`."""
    return ref.split("#", 1)[0]
```

**Line by line:**

- `chunk` takes a **character** count, not a word count and not a sentence count. Characters are the
  crudest possible unit and that is deliberate: it has exactly two knobs, both knobs are numbers, and
  a number can be swept. A splitter that cuts on paragraph breaks has no knob to sweep, so you cannot
  measure it against itself, which is the whole activity of this day.
- `if overlap >= size: raise ValueError(...)` guards the one input that would never terminate. With
  `overlap == size` the line `start += size - overlap` adds zero and the loop runs forever, filling
  memory with copies of the same window. A loop that hangs is worse than a loop that raises, so it
  raises, and the message names both numbers so the caller can see which one to change.
- `text[start : start + size]` is a plain slice. Python does not mind when `start + size` runs past
  the end of the string, so the final window is simply shorter than the others rather than a special
  case. That is why there is no `min(...)` here.
- `start += size - overlap` is the only line that decides how far the window moves. With
  `overlap = 0` the windows sit end to end and every character is stored exactly once. With
  `overlap = 60` each window starts sixty characters before the previous one ended, so sixty
  characters are stored twice. [1.4](1.4-the-margin-you-pay-for-twice.md) is about what that buys.
- `split_docs` takes `size: int | None` and treats `None` as *"do not cut"*. That is not a special
  case bolted on; it is the setting Day 49 shipped, and it has to stay reachable so today can compare
  against it. An experiment whose control arm is not runnable is not an experiment.
- `f"{ref}#{n}"` builds the chunk ref. The `#` is chosen because no ref in the archive contains one,
  so the split is unambiguous. Choosing a separator that can appear in the data is the classic way to
  make an index that mostly works.
- `parent` splits on the **first** `#` with `split("#", 1)`. Not `split("#")[0]`, which would also
  work here but would quietly do the wrong thing the day a ref contains two of them.

## When it breaks

The two knobs are not independent, and the failure is immediate:

```text
Traceback (most recent call last):
  File "<string>", line 4, in <module>
  File ".../days/day-50-chunking-and-top-k/lab/_index.py", line 60, in chunk
    raise ValueError(f"overlap {overlap} must be smaller than size {size}")
ValueError: overlap 300 must be smaller than size 280
```

The path is elided to its last three segments; on your machine it is absolute and starts at your repo
root. Everything below it is verbatim. That is the guard doing its job on
`chunk(text, size=280, overlap=300)`. It is easy to reach by
accident, because both numbers are usually written as constants at the top of a module and one of
them gets tuned without the other being looked at. The message names both, which is the difference
between a fix that takes one read and a fix that takes a debugger.

The other break has no error text at all, which is why it is worse. Set `size` larger than every
document in the archive — `uv run python fragment.py --size 5000`:

```text
  index rows            57
  hit@3                 10/10
  answered@3            10/10
```

Fifty-seven rows for fifty-seven documents. The chunking code ran, the loop executed, `split_docs`
returned a dictionary — and nothing was cut, because every document fitted inside one window. Every
ref now carries a `#0` that means nothing, the index is identical to Day 49's, and every measurement
you take afterwards will show chunking making no difference whatsoever. It is not making no
difference. It is not happening.

The tell is the row count. If rows equal documents, you have not chunked, whatever the code says.

## In production

**What a professional writes instead.** Nobody ships a character splitter. A production splitter cuts
on **separators**, in a preferred order: try paragraph breaks first, then sentence ends, then word
boundaries, and only fall back to a blind character cut when a single unbroken run is longer than the
budget. The reason is the transcript above — a row that begins `rm now survives` is a row whose
vector was computed from a fragment of a word, and no separator-aware splitter would ever produce
one. A professional also stores, beside each chunk, the ref of its parent document and the character
offsets it covers, so a retrieved chunk can be widened back out to the surrounding text before it is
shown to anybody.

**What degrades at scale.** Row count is what grows, and it grows with the reciprocal of the chunk
size: halving the size roughly doubles the rows, and the rows are what every query is compared
against. Fifty-seven documents at eighty characters is one hundred and eighty-seven rows, which is
nothing. Fifty thousand documents at eighty characters is well over a hundred thousand rows, every
one of them scored on every question. That is the point where a hand-built index stops being viable
and the parked infrastructure in
[6.2](../06-in-production/6.2-rerankers-hybrid-search-and-a-vector-database.md) starts earning its
keep.

**The failure mode that only appears with real traffic.** Re-indexing with a different chunk size
changes every ref in the store. Anything that saved a ref — a citation in a closed ticket, a bookmark,
an audit log saying which row an answer came from — now points at a row that does not exist or, far
worse, at a different row with the same name. `ticket:4610#1` meant one thing at nine hundred
characters and something completely different at eighty.

**The review comment a senior engineer leaves:** *"This re-chunks and re-indexes in place, and the
refs are positional, so `#1` silently changes meaning between builds. Either make the ref content-
addressed — hash the chunk text — or write the chunk size into the index metadata and refuse to
resolve a ref built under a different one. Right now a stale ref resolves to the wrong text and
nothing anywhere raises."*

**The interview question:** *"Why is chunk size an indexing decision rather than a retrieval
parameter?"* An honest answer: *"Because retrieval chooses between rows and cannot build one. Top-k,
the ordering, the similarity floor — those are all query-time knobs and I can change them per
request. What a row contains is fixed when the store is built, so if a fact and its explanation ended
up in different rows I can raise k until both come back, but I can never get them back as one piece
of context. In my own archive I watched fifty-seven documents become sixty-one rows at nine hundred
characters and one hundred and eighty-seven at eighty, with the archive completely unchanged. The
retrieval code was identical in both. The answers were not."*
