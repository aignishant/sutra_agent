# 4.1 — The caller says who they are

## One-line answer

`mallory` listed, read and deleted `alice`'s session by typing `alice` into the URL — three requests,
three `200`s, no credential — because `{user_id}` is a path parameter, and the library's own help
text says so before you start.

## The story

💥 **The visitor register you fill in yourself.**

🎬 **The scene.** The book on the desk in the lobby. Name, flat number, whom you are visiting, time
in. You write it, the guard glances at it, the barrier goes up.

😬 **The naive fix.** Somebody worries about security, so the register is improved: more columns, a
serial number on each page, the guard initials every entry. The book is now thorough.

💥 **Why it fails.** Every entry in it was written by the visitor. The book is a complete and
carefully maintained record of **what people said about themselves**. It has never once established
that anybody is who they wrote down, and the improvements made it look more like it had.

💡 **The insight.** A record of a claim is not a check on the claim. The two look almost identical
from the outside — both produce a name in a box — and the difference is whether anything independent
had to agree. **Identification is what the caller offers. Authentication is what you verify.**

## The idea in plain language

Part [1.2](../01-the-routing-table/1.2-what-the-paths-say-about-the-design.md) read the URL scheme:
fifteen of the twenty-seven routes are shaped `/apps/{app}/users/{user_id}/...`. The scheme is a good
one — it nests sessions under their owner, which is how you would want to store, list and expire
them.

And `{user_id}` is a **string in the URL**. The caller types it. There is no dependency on those
routes that compares it against anything, because there is nothing to compare it against: no route on
this server takes a credential.

That is not hidden. `adk api_server --help` opens with it:

```text
  This server's endpoints are unauthenticated. Run it on a trusted network
  only, and put it behind your own authentication and authorization layer
  before exposing it to untrusted or public networks or serving multiple
  users.
```

So the finding of this part is not "ADK has a hole". It is more uncomfortable than that: **the
library says the layer is missing, and the URL scheme is so natural that everybody reads ownership
into it anyway.** A path that says `users/alice` looks like a fact about alice. It is a request
parameter.

Two ideas need separating, because the whole part turns on the gap between them:

- **Authentication** — establishing who the caller is. A token, a signature, a client certificate;
  something the caller cannot simply assert.
- **Authorization** — deciding whether *that* caller may do *this*. Comparing the authenticated
  identity against the resource's owner.

This server has neither. The path scheme supplies a third thing — **identification**, the caller's
own claim — and identification is what the visitors' book collects.

## Why Sutra needs it

Because the desk's safety story is built on identity and every layer of it is now standing on a URL
segment. Day 63's approval gates ask a specific human to approve a refund; Day 68's least-privilege
tools scope what a particular caller may reach; Day 69's PII boundary exists to stop one person seeing
another's data. All three become decorative the moment the caller picks the name.

And because Phase 14 makes this repository public and puts the desk on a network with other agents.
"Run it on a trusted network only" is a sentence with an owner, and after this day the owner is us.

## The mechanism

The measurement is three ordinary requests. First `alice` creates something:

```python
        created = await http.post(f"/apps/{APP_NAME}/users/{OWNER}/sessions", json={})
        session_id = created.json()["id"]
        owned = f"/apps/{APP_NAME}/users/{OWNER}/sessions/{session_id}"
```

**Line by line:**

- The session id comes from the server, so it is a real version-4 UUID rather than something guessable.
  This matters: the finding must not depend on `mallory` guessing an id.
- `owned` is built from `alice`'s name and `alice`'s session id. Every subsequent request uses that
  exact URL — the stranger is not probing, they are using the same address.

Then the same client sends three more requests, changing nothing:

```python
        steps = [
            ("list " + OWNER + "'s sessions", http.get(f"/apps/{APP_NAME}/users/{OWNER}/sessions")),
            ("read the session", http.get(owned)),
            ("delete the session", http.delete(owned)),
        ]
```

**Line by line:**

- No headers are set anywhere in this script. There is no `Authorization`, no cookie, no API key — the
  point is not that a credential was forged, it is that none was asked for.
- The three verbs are chosen to be increasingly consequential: enumerate, read, destroy. If any layer
  distinguished them, the third would be the one to stop.
- The same `http` client makes all four requests, which is realistic — a single process holding a
  connection, changing only the name in the path.

And then the one line that turns it from a list of status codes into a finding:

```python
        after = await http.get(owned)
```

**Line by line:**

- Asking for the session *after* the delete, as its owner would. A `200` on a DELETE only proves the
  request was accepted; this proves the data is gone.

Run it:

```bash
cd days/day-85-the-api-surface/lab
uv run python whoami.py; echo "exit: $?"
```

**Line by line:**

- No flag. `--trusted-network` is the argument this finding usually loses to, and it is in **When it
  breaks**.

Measured on 2026-09-07:

```text
alice creates a session:
  POST /apps/echo/users/alice/sessions -> 200
  {"id":"<uuid>","appName":"echo","userId":"alice","state":{},"events":[],"lastUpdateTime"

mallory sends the same requests, with no credential of any kind:
  list alice's sessions      -> 200 [{"id":"<uuid>","appName":"echo","userId":"ali
  read the session           -> 200 {"id":"<uuid>","appName":"echo","userId":"alic
  delete the session         -> 200 null

  alice asks for the session back -> 404 {"detail":"Session not found"}

  requests a stranger completed: 3 of 3
  credentials presented: 0
  authentication dependencies on these routes: 0

  mallory read and destroyed alice's session by typing a different name
  the user id is a path parameter: the server is told who the caller is
```

**Three of three, and the last line is the one to sit with.** `alice` asks for her own session and
gets a 404 — the correct answer to a question about data that no longer exists, produced by a server
that did nothing wrong at any step.

Note what was *not* required: no guessing, no timing, no malformed input, no clever encoding. The
attack is typing a different string in a URL, which is the same thing every legitimate client does.

## When it breaks

The finding breaks by being answered rather than fixed, and the answer has a name:

```bash
uv run python whoami.py --trusted-network; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  requests a stranger completed: 3 of 3
  credentials presented: 0
  authentication dependencies on these routes: 0

  the server is bound to loopback, so only this machine can reach it
  no request crossed a network and no credential was needed
```

**Every number is identical and the exit code is `0`.** The three lines of evidence are still printed;
a sentence about the deployment has been added underneath them, and the verdict has flipped.

That argument is not stupid. On a developer's workstation it is completely correct, which is why it
survives — and it has three failure modes, each of which has happened to somebody:

```text
1. loopback becomes 0.0.0.0, because somebody wanted to reach it from a phone
2. the process moves into a container, and "localhost" now means the pod       (day 86)
3. a sidecar or proxy is put in front, and it forwards from anywhere           (day 88)
```

Days 86 and 88 are the next two labs in this phase. The trusted network is dissolved by the ordinary
progress of the project, and nothing about the application changes on the day it happens.

**There is no error text anywhere in this part.** Every request in the measurement returned `200`.
That is the whole shape of an authorization gap: the system's normal, correct, successful behaviour,
performed for the wrong person.

## In production

**What a professional does.** Puts authentication in one place and authorization in one place, and
never in a handler. Concretely, for this server: a dependency that validates a token and yields a
subject, and a second that compares that subject to the `{user_id}` path parameter — applied to all
fifteen routes at the router level, so a new route added next year inherits it instead of forgetting
it.

**What degrades at scale.** Per-handler checks. A codebase where each endpoint remembers to compare
the caller is a codebase where one endpoint does not, and the missing one is invisible in review
because the code that should be there is absent rather than wrong. Centralising the check turns
"did somebody remember" into "is this route on the list".

**The failure that only shows with real traffic.** Multi-tenancy arriving quietly. The first user is
the developer; the second is a colleague; by the tenth there are real people's conversations in the
session store, and no single day was the day it became a multi-user system. The help text's phrase
*"or serving multiple users"* is doing real work: it names a threshold that is crossed without a
deployment.

**The review comment a senior engineer leaves:** *"Before this leaves a laptop: one auth dependency,
applied at the router, comparing the token subject to `{user_id}`. And write a test that a session
created as A returns 403 when read as B — that test is the only thing that will still be true in a
year."*

**The interview question:** *"Your API takes a user id in the path. What do you check?"* The answer
that shows experience separates the three words — identification, authentication, authorization —
and then asks where the check lives, because a check in fifteen handlers is fourteen chances to
forget.
