# 4.2 — Which pages may call it

## One-line answer

With no `allow_origins` the browser refuses a page on another origin with a `403` before your code
sees it; set it to `["*"]` for convenience and any web page anybody visits can drive every route on
this server, which part 4.1 established needs no credential.

## The story

The list at the school gate of who may collect a child.

Three names on it, written by a parent, kept by the guard. Somebody arrives, says they have been sent
to pick up the child, and the guard checks the list. Not on it: the child stays.

The list is short on purpose, and every parent understands why. What is interesting is what happens
when the school grows and the guard finds the checking tedious, and somebody proposes the obvious
simplification: let anyone through who knows the child's name and class.

That is not a small relaxation of the same rule. It is a different rule — one that anybody standing
in the corridor for five minutes can satisfy — and it will feel identical on every ordinary day.

## The idea in plain language

A browser is a program that runs code from strangers. You open a page and it executes whatever
JavaScript that page contains, so the browser has to assume the page is hostile to every *other* site
you use.

Its rule is the **same-origin policy**: script from `https://a.example` may read responses from
`https://a.example`, and not from anywhere else. Origin means scheme, host and port together.

**CORS** — Cross-Origin Resource Sharing — is the mechanism by which a server can opt out of that
restriction for chosen origins. The server sends `Access-Control-Allow-Origin`; the browser reads it
and decides whether to hand the response to the page. Three things follow that people routinely get
wrong:

- **CORS is enforced by the browser, not by the server.** `curl` ignores it entirely. It protects
  users of browsers from pages they visit; it is not a firewall.
- **A preflight is a real request.** For anything beyond a simple GET, the browser first sends
  `OPTIONS` asking whether the real request is permitted, and only then sends it.
- **`allow_origins=["*"]` is not "turn CORS on".** It is "every page on the internet may read my
  responses", which is a decision about who may act as your users.

That last point is where this server's two findings compose. Part
[4.1](4.1-the-caller-says-who-they-are.md) established that every route answers without a credential
and takes the caller's identity from the URL. Add a permissive CORS policy and a page the user
happens to open can list, read and delete sessions — for any user id it likes — from the user's own
browser.

## Why Sutra needs it

Because the desk will have a web front end. That is what `adk web` is for, that is why the factory has
a `web` flag, and the first thing anybody does when the front end is served from a different port is
hit a CORS error and reach for the wildcard. The fix takes ten seconds and is wrong.

And because Day 66's injection threat model was about content the agent reads. This is the same
question one layer out: **which code, running in whose browser, may talk to the desk at all.**

## The mechanism

Two requests, because the browser makes two:

```python
        preflight = await http.options(
            PROBE,
            headers={"Origin": STRANGER, "Access-Control-Request-Method": "GET"},
        )
        simple = await http.get(PROBE, headers={"Origin": STRANGER})
```

**Line by line:**

- `OPTIONS` with `Access-Control-Request-Method` is exactly what a browser sends first. Testing only
  the GET would miss a server that answers the preflight generously and the request strictly, or the
  reverse.
- `Origin` is the header that makes a request cross-origin. A browser sets it; here the script does,
  which is what makes this measurable without a browser.
- `STRANGER` is `http://evil.example`, a name that does not resolve and never needs to. Nothing looks
  it up — the header is a string the server compares.
- The same `PROBE` path for both, `/list-apps`, chosen because it is harmless and unauthenticated, so
  the measurement is about the policy rather than about that route.

The verdict is one header on the response:

```python
    allow = simple.headers.get("access-control-allow-origin")
```

**Line by line:**

- Read from the response, not inferred from configuration. That is the whole point: what matters is
  what the browser will be told, and the browser only reads this header.
- `.get`, so its absence is `None` rather than an exception — and `None` is the interesting value,
  because a missing header is a refusal.

Run the default:

```bash
cd days/day-85-the-api-surface/lab
uv run python cors.py; echo "exit: $?"
```

**Line by line:**

- No flag: `allow_origins` is not passed to the factory, which is its default of `None`.

Measured on 2026-09-07:

```text
a page served from http://evil.example tries to call the desk:

  allow_origins not given (the default)
    OPTIONS /list-apps   Origin: http://evil.example  -> 403  allow-origin: None
    GET     /list-apps   Origin: http://evil.example  -> 403  allow-origin: None

  the browser will not hand the response to that page
  a page on another origin gets a refusal it cannot read past
exit: 0
```

**A `403` on both, and no allow-origin header.** Note what this is *not*: it is not the browser
silently discarding a `200`. This server actively refuses the cross-origin request, which is a
stronger position than the specification requires and a good default.

Now the convenient version:

```bash
uv run python cors.py --open; echo "exit: $?"
```

**Line by line:**

- `--open` builds the same app with `allow_origins=["*"]` and changes nothing else, so the difference
  between the two transcripts is that one argument.

Measured on 2026-09-07:

```text
  allow_origins=['*']
    OPTIONS /list-apps   Origin: http://evil.example  -> 200  allow-origin: http://evil.example
    GET     /list-apps   Origin: http://evil.example  -> 200  allow-origin: http://evil.example

  the browser will hand the response to that page
  and every route on this server answers without a credential, so that page
  can list apps, read sessions and delete them on behalf of whoever is looking
exit: 1
```

**Look at what `*` became.** The response does not say `*` — it says `http://evil.example`, reflecting
back whatever origin asked. That is the middleware resolving the wildcard per request, and it means
the allow-list is effectively "the origin of whoever is calling", which is not an allow-list.

One line separates the two runs, and it is the line somebody adds to make a local front end work.

## When it breaks

The wildcard is usually added for a real reason, and the reasoning is where it breaks:

```text
🎬 the front end runs on :3000, the desk on :8000
😬 the browser console shows a CORS error, so allow_origins=["*"] goes in
💥 it works immediately, and the commit message says "fix CORS"
💡 the fix needed was ["http://localhost:3000"] — one entry, same ten seconds
```

The wildcard and the correct value cost the same to type. The wildcard wins because it is the one
that appears in the first search result, and because there is no feedback of any kind distinguishing
them: both make the error go away.

**What the wildcard cannot do**, and this is worth knowing so the risk is not overstated: with
`allow_origins=["*"]` the middleware does not permit credentialed requests — cookies are not sent
cross-origin under a wildcard. So a cookie-authenticated API is partly protected by that restriction.

This server is not that server. It has **no credentials at all** (part
[4.1](4.1-the-caller-says-who-they-are.md)), so there is nothing for the browser to withhold. The
protection that usually blunts a wildcard does not apply here, which is precisely why these two
findings have to be read together rather than as separate items on a list.

**There is no error text.** Both runs return valid responses; one of them returns them to a page that
should not have had them.

## In production

**What a professional does.** Lists origins explicitly, one per environment, and treats the list as
configuration rather than code. The specific ADK affordance is worth knowing: `--allow_origins`
accepts a `regex:` prefix, so `regex:https://.*\.sutra\.example` covers a fleet of subdomains without
a wildcard. A regular expression anchored to a domain you own is an allow-list; `*` is not.

**What degrades at scale.** Environments multiply — local, review apps, staging, production, a demo
domain — and the list gets long enough that somebody replaces it with a wildcard "temporarily". The
countermeasure is to derive the list from the environment rather than hand-maintain it, so adding an
environment adds an entry automatically.

**The failure that only shows with real traffic.** A CORS policy is not a defence against anything
that is not a browser. Once the desk is reachable from a network — Day 86's container, Day 88's
cluster — every non-browser client ignores these headers entirely. A team that has "handled CORS"
and thinks it has handled access control has handled the one caller that was already restricted.

**The review comment a senior engineer leaves:** *"Replace the wildcard with the actual front-end
origin, and add a comment saying which environment it is for. And do not treat this as the access
control story — CORS is browser-side; the auth dependency from part 4.1 is the one that stops
everything else."*

**The interview question:** *"Your front end gets a CORS error. What do you do?"* The answer that
shows experience asks which origin needs access and adds that one, then says what CORS does and does
not protect — because a candidate who reaches for `*` has told you they think it is a configuration
error rather than a policy decision.
