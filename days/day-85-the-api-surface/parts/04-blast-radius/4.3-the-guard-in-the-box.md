# 4.3 — The guard in the box

## One-line answer

ADK ships a guard that rejects a request addressed to a host this server is not, which is what stops
a web page from reaching your loopback API — and it is off unless you pass `bind_host`, which the
command does and an embedder must remember to.

## The story

The screen guard that came in the box.

A new phone, and in the box under the charger there is a tempered-glass protector. Not an accessory
somebody has to be sold: it is included, it fits exactly, and the manufacturer put it there because
they know what happens to screens.

Most people find it three months later, when they are looking for the SIM tool, and by then the
screen has a scratch across it. Nothing failed. The protection was supplied, correct, and never
applied — and the phone worked perfectly the whole time, which is exactly why nobody applied it.

## The idea in plain language

Here is an attack that surprises people the first time, because it defeats an assumption everybody
holds: *nothing on the internet can reach a server bound to 127.0.0.1.*

That is true of the network and false of the browser.

**DNS rebinding**, step by step:

```text
1. a user opens https://gadgets.example, an ordinary page
2. that name resolves to the attacker's real server; the page loads normally
3. the page's script waits, then fetches https://gadgets.example/apps/... again
4. by now the DNS record for gadgets.example has been changed to 127.0.0.1
5. the browser connects to the user's own machine - and considers it same-origin,
   because the *name* has not changed
6. the response comes back to the page, which can read it
```

The same-origin policy from part [4.2](4.2-which-pages-may-call-it.md) does not help, because as far
as the browser is concerned this *is* the same origin. CORS does not help for the same reason: the
browser will not even ask, since it does not think the request is cross-origin.

What does help is that the request still carries `Host: gadgets.example`. Your server is not
`gadgets.example`. It is on loopback, so the only legitimate values are loopback ones — and a request
naming anything else was sent by something that was tricked about where it was going.

ADK implements exactly that check. It is on when the factory is told which address the app will be
bound to, and off when it is not — and *off* is the default, deliberately, because a library that
guessed would break an app sitting behind a same-machine proxy.

## Why Sutra needs it

Because Sutra will embed the factory rather than run the command — part
[1.3](../01-the-routing-table/1.3-two-ways-to-start-it.md) — and this is one of the two protections
that transfers with the responsibility. Nothing announces the loss.

And because it composes with the rest of section 4 into the worst case in this day. Part
[4.1](4.1-the-caller-says-who-they-are.md): no credential, caller picks the user id. Part
[4.2](4.2-which-pages-may-call-it.md): a permissive CORS policy lets a page read responses. This part:
without the guard, a page can reach the loopback server *at all*. Any one of the three alone is a
finding. Together they are a web page, on a machine belonging to somebody running the desk locally,
reading and deleting that person's sessions.

## The mechanism

The guard is a check on the `Host` header, and the library's own comment says why nothing else will
do. From `google/adk/cli/api_server.py`, read on 2026-09-07:

```text
  # A loopback bind is reachable only from this machine, so a request naming
  # any other host was pointed here by rebound DNS. Origin cannot catch that:
  # browsers omit it on requests they consider same-origin, as a rebound page's
  # are, so callers must apply this to every request, safe methods included.
```

**Line by line:**

- *"reachable only from this machine"* is the premise the whole guard rests on. It is why the check
  only makes sense for a loopback bind, and why passing `bind_host="0.0.0.0"` correctly turns it off
  rather than making it stricter.
- *"Origin cannot catch that"* is the sentence to remember. A rebound page's requests are same-origin
  in the browser's judgement, so no `Origin` header is sent, so any defence keyed on `Origin` sees
  nothing at all.
- *"safe methods included"* — the check must run on `GET`, not only on state-changing verbs. Reading
  somebody's sessions is the attack; nothing has to be written.

The probe is two requests differing only in a header:

```python
async def ask(app, host: str) -> int:
    async with client(app) as http:
        response = await http.get("/health", headers={"Host": host})
```

**Line by line:**

- `Host` is set explicitly, which is why part [2.1](../02-exercising-it-free/2.1-a-client-with-no-socket.md)'s
  `base_url` is `http://desk` rather than `http://localhost` — the reader can see the header is the
  variable rather than a real hostname doing something.
- `/health` because it is the least interesting route on the server. If the guard is doing its job it
  applies to everything, and demonstrating it on a harmless endpoint makes that clear.
- In a browser, `Host` is a **forbidden header**: page script cannot set it. That is what makes the
  check trustworthy — the value is put there by the browser, from the URL, and a rebound page cannot
  forge it.

And the two ways to build the app:

```python
    app = build(bind_host="127.0.0.1") if bound else build()
```

**Line by line:**

- One argument, and it is the only difference between the two runs.
- `"127.0.0.1"` rather than `"localhost"`: the guard tests whether the value is a loopback *address*,
  and a name would have to be resolved, which is the thing being attacked.

Run the default:

```bash
cd days/day-85-the-api-surface/lab
uv run python rebind.py; echo "exit: $?"
```

**Line by line:**

- No flag: the app as the factory returns it, with `bind_host` left at its default of `None`.

Measured on 2026-09-07:

```text
  bind_host not given (the default)

    GET /health   Host: 127.0.0.1:8000           -> 200 {"status":"ok"}
    GET /health   Host: desk.internal.example    -> 200 {"status":"ok"}

  a request addressed to desk.internal.example was served
  the guard is off, because the factory was not told where the app would be bound
  `bind_host` defaults to None, and None means 'do not guess', not 'protect me'
exit: 1
```

And with the one argument:

```bash
uv run python rebind.py --bound; echo "exit: $?"
```

**Line by line:**

- `--bound` passes `bind_host="127.0.0.1"`. Same app, same routes, same requests; one argument.

Measured on 2026-09-07:

```text
  bind_host='127.0.0.1'

    GET /health   Host: 127.0.0.1:8000           -> 200 {"status":"ok"}
    GET /health   Host: desk.internal.example    -> 403 Forbidden: host not allowed

  a request addressed to desk.internal.example was refused
  the guard is on: only a Host that resolves to loopback is answered
exit: 0
```

**Legitimate traffic is unaffected in both runs.** That is the property that makes this cheap: the
`127.0.0.1` request succeeds either way, so turning the guard on costs nothing and breaks nothing —
provided you are actually bound to loopback, which is the thing the argument tells it.

## When it breaks

The guard breaks in the direction of a false alarm, and that is why the default is off. Two real
situations:

**A reverse proxy on the same machine.** The proxy accepts `https://desk.example` and forwards to
`127.0.0.1:8000` with the original `Host` intact. The guard sees `desk.example`, which is not
loopback, and refuses — correctly by its own rule and wrongly for this deployment. Day 88 puts
exactly such a thing in front of the desk.

**A container.** Inside a pod the app is bound to `0.0.0.0` and reached by service name, so the guard
would refuse every request. Passing `bind_host="0.0.0.0"` turns it off, which is right: a non-loopback
bind is not a rebinding target, because the attack depends on the server being unreachable from
outside in the first place.

Both are why the library refuses to infer. Its own comment: *"A bind we were not told about is not
ours to guess: an app embedded behind a same-machine proxy would then reject its own traffic."* That
is a good decision by the library and it hands the embedder a choice they may not know they have.

**The failure has no error text on the wrong side.** When the guard is off, the request succeeds — a
`200` on `/health` for a host this server is not. The only visible artefact of the whole class of
attack is that second line of the first transcript, and it looks exactly like a healthy server.

When the guard is on and misconfigured, it is loud and easy:

```text
403 Forbidden: host not allowed
```

That is the good failure. It is immediate, it names the reason, and it happens on the first request
in the first deployment rather than silently for a year.

## In production

**What a professional does.** Passes `bind_host` explicitly, always, set to the same value the server
is actually bound to, and derives both from one variable so they cannot disagree. When something sits
in front, the answer is not to leave the guard off by accident but to turn it off on purpose with a
comment saying which component is now responsible for host validation.

**What degrades at scale.** The bind address stops being a constant. It comes from an environment
variable, a config map, a platform-injected `PORT` and `HOST`, and the code that passes `bind_host`
gets separated from the code that binds. At that point the guard is configured from one source and
the socket from another, and the two drift.

**The failure that only shows with real traffic.** Rebinding is not a bug you will ever see in a log,
because the requests it produces are well-formed and successful. The only signal is a `Host` header
you did not expect — which is an argument for logging it. That is Day 22's structured logging with a
specific field in mind, and it costs nothing.

**The review comment a senior engineer leaves:** *"Pass `bind_host` even when it equals the default. I
want the diff to show that somebody chose, and when we put the proxy in front I want to find this line
and change it rather than discover it does not exist."*

**The interview question:** *"Why does a service on localhost still need host validation?"* The answer
that shows experience explains that the browser is inside the trust boundary — it runs code from
strangers and it can be redirected to loopback while keeping the name — and then names the one header
the attack cannot forge.

## Check yourself

```bash
cd days/day-85-the-api-surface/lab
uv run python rebind.py; echo "exit: $?"
uv run python rebind.py --bound; echo "exit: $?"
```

Both runs serve the loopback request. Say what that tells you about the cost of turning the guard on.

Now run it a third way: build with `bind_host="0.0.0.0"` and predict what the foreign host gets before
you run it. The answer follows from the premise in the library's comment, not from the code.

page, and what is the one thing about that request the attacker cannot control?
