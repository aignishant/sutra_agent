# 5.1 — Health is not readiness

## One-line answer

`GET /health` returns `{"status":"ok"}` from a two-line function that checks nothing, which is
exactly right for *is this process alive* and useless for *may I send it traffic* — and the second
question is the one a load balancer is actually asking.

## The story

The OPEN board still hanging at nine at night.

The shop closed hours ago. The shutter is half down, the till is counted, the man who runs it is
upstairs having dinner. Hanging on the door, facing the street, is a board that says **OPEN**.

The board is not lying, exactly. It is a piece of painted tin. It says what it said this morning and
what it will say tomorrow, because saying things is not something it does — it is something it *is*.
Anybody who treats it as a report about the shop has mistaken a fixed sign for an observation.

The shop, meanwhile, is fine. It will open tomorrow. Nothing is broken. It is simply not, at this
moment, able to sell you anything, and the board has no way to express that.

## The idea in plain language

Deployment platforms ask a service two different questions, and confusing them is one of the most
common operational mistakes there is.

**Liveness: is this process alive?** If the answer is no, restart it. The check must be trivial — it
must not touch a database, an external service or anything that could hang — because a liveness check
that depends on a dependency will report the process dead when the dependency is slow, and the
platform will restart a healthy process in the middle of an outage, repeatedly.

**Readiness: should traffic be sent here?** If no, take it out of rotation but leave it running. This
check *does* look at dependencies: can I reach the session store, is the agent directory loaded, have
I finished warming up.

The two need different behaviours in the failure case — restart versus withhold traffic — which is why
they need different endpoints.

ADK provides one, and it is the liveness one. Here is the entire handler, from
`google/adk/cli/api_server.py`:

```text
    @app.get("/health")
    async def health() -> dict[str, str]:
      return {"status": "ok"}
```

Nothing is checked, and that is correct. If the process can execute that function and write a
response, the process is alive; that is the whole claim, and it is the claim a liveness probe wants.

What does not exist is the second endpoint. There is no route that says *"I can reach my session
store and my agents load"*, and so a platform configured with `/health` for both probes will send
traffic to a replica whose session store is unreachable, for as long as it takes somebody to notice.

## Why Sutra needs it

Because Day 86 is tomorrow and a container needs both probes configured, and Day 88 puts a load
balancer in front that will use readiness to decide where requests go. Choosing the endpoint is a
line of YAML, and it is written by somebody who has to know the difference.

And because Day 83's Phase 12 gate found the same shape in a different instrument — a suite green
because nothing could go red. A liveness probe used as readiness is that: a check that returns `ok`
under every condition it is asked about, in a place where somebody believes it is checking something.

## The mechanism

The endpoint is free and constant, which is easy to establish from the outside:

```text
    ("GET", "/health", None),
```

**Line by line:**

- One entry in `free.py`'s `FREE` table, alongside `/version` and the discovery routes. It is in that
  list precisely because it touches nothing — the same property that makes it a good liveness check
  makes it a free one.

Run it:

```bash
cd days/day-85-the-api-surface/lab
uv run python free.py | head -6
```

**Line by line:**

- `head -6` for the first rows of the table, which are the two liveness routes and the two discovery
  ones.

Measured on 2026-09-07:

```text
exercising 6 endpoints that answer without a model

  method  path                                         status  body
  GET     /health                                         200  {"status":"ok"}
  GET     /version                                        200  {"version":"2.7.1","language":"python","language_version
  GET     /list-apps                                      200  ["echo"]
```

Three things worth noticing in three lines.

**`/health` is fifteen bytes and constant.** Perfect liveness. It will answer while the session store
is on fire.

**`/version` reports the runtime.** `2.7.1`, `python`, `3.12.12`. Useful for an operator confirming
what is deployed, and an unauthenticated fingerprint for anybody else — which, with section 4's
finding that nothing needs a credential, is one more free fact. Not a vulnerability; an input to
somebody's next question.

**`/list-apps` is the closest thing to a readiness check that exists here.** It reads the agents
directory and returns what loaded. A `200` with a non-empty list means at least one thing this server
exists to serve is present, which is more than `/health` claims — and it still says nothing about the
session store.

The readiness check that is missing would look like this, and it is a `TODO(me)` in the hub:

```text
GET /ready  ->  200 {"ready": true}
            ->  503 {"ready": false, "session_store": "unreachable"}
```

**Line by line:**

- A `503` rather than a `500`, because *"not now"* is a different statement from *"something is
  broken"*, and load balancers treat them the same way only by accident.
- The body names which dependency failed, so the operator does not have to correlate. That body is a
  problem document, part [3.3](../03-when-it-refuses/3.3-an-error-with-a-handle-on-it.md), and the
  same exception handler builds it.
- No model call anywhere in it. A readiness check that ran the agent would be Day 82's cadence
  mistake as an infinite loop: part [2.2](../02-exercising-it-free/2.2-which-endpoints-cost-nothing.md)
  priced a probe on a paid route, and the whole day's quota goes in the first hour.

## When it breaks

The failure needs no error text and it looks like a healthy deployment:

```text
1. a replica starts; its session store connection fails
2. /health returns {"status":"ok"} - the process is alive, which is true
3. the platform marks the replica ready, because /health was configured for both probes
4. the load balancer sends it a share of traffic
5. every request to that replica fails somewhere deeper
6. the dashboard shows healthy replicas and a raised error rate
```

Step 6 is the expensive one. Whoever is paged sees green instances and failing requests, and spends
the first stretch of the incident looking for the cause anywhere except the health check, because the
health check is green and green is what it means.

The opposite mistake is worse and quieter. Make `/health` check the session store, and now:

```text
1. the session store has a slow patch
2. every replica's liveness probe fails
3. the platform restarts every replica
4. the restarts add load to the store, which gets slower
5. the platform restarts them again
```

That is a self-inflicted outage caused by making a liveness check more thorough, and it is the reason
the two-line handler above is right rather than lazy.

## In production

**What a professional does.** Configures liveness against a constant endpoint and readiness against a
dependency check, with different failure semantics, and writes down which is which. The rule of thumb
that survives: **a liveness check must not be able to fail for a reason a restart cannot fix.** If a
restart would not help, it does not belong in liveness.

**What degrades at scale.** Readiness checks accumulate dependencies. Every team adds theirs, and
eventually a replica is taken out of rotation because a service used by one rarely-called endpoint is
down. The discipline is that readiness covers only what *every* request needs, and everything else
degrades in the handler.

**The failure that only shows with real traffic.** Startup. A process that binds its port before it
has loaded its agents is live and not ready, and the window between the two is exactly when a
platform will send it the first request. This server loads agents lazily — part
[1.1](../01-the-routing-table/1.1-a-desk-with-a-street-address.md) established that a broken agents
directory does not fail at startup — so the window is not a moment, it lasts until the first request
per app.

**The review comment a senior engineer leaves:** *"`/health` is fine for liveness. Add `/ready` that
touches the session store and returns 503 when it cannot, and put the two on different probes in the
manifest — with a comment, because the next person will 'simplify' them back into one."*

**The interview question:** *"What is the difference between a liveness and a readiness probe?"* The
answer that shows experience gives the two failure actions — restart versus remove from rotation —
and then says what goes wrong in each direction: a readiness check used for liveness restarts healthy
processes during a dependency outage, and a liveness check used for readiness sends traffic into a
replica that cannot serve it.
