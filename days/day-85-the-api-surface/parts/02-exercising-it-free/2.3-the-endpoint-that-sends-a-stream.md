# 2.3 — The endpoint that sends a stream

## One-line answer

`/run_sse` declares `application/json` in the generated schema and actually sends
`text/event-stream`, so a client built from the document will wait for one object that never
arrives — and `/run_live` is a WebSocket, which is not in the document at all.

## The story

The queue display board and the printed token.

You take a token at the counter: a small slip with `A-47` on it. That is the whole transaction — one
piece of paper, complete when you receive it, and you can put it in your pocket and read it on the
bus.

Above the counter there is a board showing `NOW SERVING: A-31`. It is never complete. It is a thing
that keeps changing while you watch, and it is only useful *because* it keeps changing. Photograph it
and you have destroyed the only property that made it worth having.

The slip and the board carry the same information in the same room, and you would never confuse them
— because one is in your hand and one is on the wall. Over HTTP, both arrive down the same wire, and
the only thing that says which you are getting is a header.

## The idea in plain language

Three routes run the agent, and they are three different shapes of conversation.

**`POST /run` — the slip.** Send a message, wait, get back a JSON array of every event the turn
produced. One request, one response, complete when it arrives. Easy to call, easy to test, and the
user stares at nothing until the whole turn is finished.

**`POST /run_sse` — the board.** Same request, but the response is **Server-Sent Events**: a long-
lived HTTP response whose body arrives in pieces, each one a line beginning `data:` followed by a
blank line. The connection stays open until the server closes it. This is what makes text appear word
by word.

**`/run_live` — the intercom.** A WebSocket. Both sides can send at any time, which is what Day 74
and Day 75's voice work needs, and it is not request-and-response at all.

Now the part that is measurable for nothing. FastAPI generates `/openapi.json` from the handler
signatures, and code generators build clients from that document. So the document is a contract — and
for one of these three routes it is wrong.

The generated schema says `/run_sse` returns `application/json`. The handler returns a
`StreamingResponse` with `media_type="text/event-stream"`. A generated client will call
`response.json()` on a stream and either block until the server finishes or fail to parse.

That is not a bug this repository found in the abstract. It is two facts, each read from a source you
can check, and the whole of part is putting them next to each other.

## Why Sutra needs it

Because the streaming endpoint is the one a user-facing client will actually use, and it is the one
whose declared contract is wrong. Any client generated from this document — and generating clients
from OpenAPI is the normal thing to do — starts from a false statement about the most important
route.

And because Day 74 built the streaming loop by hand and Day 75 the bidirectional one, so this
repository knows exactly what an SSE frame and a WebSocket message are. This part is those two things
seen from the server's side, and the point where their descriptions get published.

## The mechanism

The declared side comes out of the app, not out of documentation:

```python
        spec = (await http.get("/openapi.json")).json()
        ...
        content = spec["paths"][path]["post"]["responses"]["200"]["content"]
        declared = ", ".join(sorted(content))
```

**Line by line:**

- `/openapi.json` is itself a route on this server — one of the four in the `docs` family from part
  [1.1](../01-the-routing-table/1.1-a-desk-with-a-street-address.md) — so the document is fetched
  from the running app rather than generated separately. Whatever a client generator would read, this
  reads.
- `["responses"]["200"]["content"]` is where OpenAPI puts the media types a successful response may
  have. Its keys *are* the content types, which is why `sorted(content)` is the list of them.
- Joining the keys rather than picking the first one, so a route declaring two media types would show
  both instead of silently reporting one.

The implemented side is read from the library and recorded as a constant, with its provenance in the
comment:

```python
# What the handler really returns, read from google/adk/cli/api_server.py on 2026-09-07:
# line 1955 `return StreamingResponse(`, line 1957 `media_type="text/event-stream",`.
IMPLEMENTED = {"/run": "application/json", "/run_sse": "text/event-stream"}
```

**Line by line:**

- A constant with a file, a date and two line numbers, because this half cannot be measured without
  spending a model call — the only way to see the real `Content-Type` is to complete a turn.
- Writing it as a fixture with its source named is the honest form. Pretending to have measured it
  would be a fabricated transcript; leaving it out would drop the finding.
- `/run_live` is absent from this dictionary because it is not an HTTP response at all, and the script
  checks its absence from the document separately.

Run it:

```bash
cd days/day-85-the-api-surface/lab
uv run python stream.py; echo "exit: $?"
```

**Line by line:**

- No flag: compare declared against implemented. `--refusal` is part
  [2.2](2.2-which-endpoints-cost-nothing.md)'s arm.

Measured on 2026-09-07:

```text
what the generated schema says each run endpoint returns:

  path      declared              implemented           agree
  /run      application/json      application/json      yes
  /run_sse  application/json      text/event-stream     NO

  the schema /run_sse declares for its body: {}
  /run_live is a websocket, so it has no entry in paths: True

  1 endpoint declares one media type and sends another
  a client generated from this document will try to parse a stream as one object
exit: 1
```

Three things in that output, and the second is nearly as interesting as the first.

**The media type is wrong.** Declared `application/json`, sends `text/event-stream`.

**The schema is empty.** `{}` — the document says the body is JSON and then declines to say what
JSON. A code generator turns that into `Any` or `object`, so the client compiles, the types are
useless, and nothing complains until runtime.

**`/run_live` is not in `paths` at all.** That is correct behaviour, not an omission: OpenAPI 3.1 has
no way to describe a WebSocket. It does mean the generated document is a complete description of two
of the three ways to talk to this agent, and a reader who treats it as the API has missed one.

## When it breaks

The break is on the client's side and it is quiet. A generated client does the natural thing:

```text
  response = client.run_sse(...)   # typed as returning Any, per the empty schema
  events = response.json()         # blocks until the server closes the stream
```

There is no exception to quote, which is the problem. `response.json()` against an SSE stream does
not fail fast — it waits for the body to end. For a short turn that looks like a slow but working
call; for a long one it looks like a hang; for `/run_live` it never happens at all because the client
was never generated.

The failure is therefore reported as *"the API is slow"*, which sends somebody to look at the model.

**What this part deliberately does not do** is call the endpoint to prove the `Content-Type`. That
would spend provider quota to confirm something the source already states, and Principle 15 says the
budget is the constraint. The hub's build brief carries the exact command for when you want to see it
for yourself, and the honest position is: one half of this comparison is measured and the other is
cited.

## In production

**What a professional does.** Treats the generated document as a deliverable and reviews it, rather
than assuming it is right because it was generated. The specific move for a streaming route is to
declare it — FastAPI lets a route say `response_class=StreamingResponse` and set `responses={200:
{"content": {"text/event-stream": {}}}}` — so the document matches the code. It is a few lines and it
is the difference between a client generator producing something usable and something misleading.

**What degrades at scale.** Every generated client inherits the mistake, in every language, and they
are generated at different times. Fixing the declaration a year later means a fleet of clients built
from two different contracts, and the ones that "worked" did so by not using the route.

**The failure that only shows with real traffic.** Buffering in the middle. An SSE stream that is
correct end to end still arrives in one lump if anything between the two ends buffers it — a reverse
proxy with response buffering on, a compression middleware, a load balancer. Day 88 puts exactly such
a thing in front of this server, and the symptom is identical to the client bug above: a stream that
works locally and is not a stream in the deployment.

**The review comment a senior engineer leaves:** *"Declare the media type on `/run_sse` before anyone
generates a client from this. And put a note in the README that `/run_live` is not in the schema —
somebody is going to read the OpenAPI doc and conclude we do not have a live endpoint."*

**The interview question:** *"How does a client know your endpoint streams?"* The answer that shows
experience says the `Content-Type` and then, without being asked, whether the generated schema agrees
with it — because the header is what the client sees at runtime and the schema is what the client was
built from, and those are two different sources of truth.
