# 1.2 — What the paths say about the design

## One-line answer

Almost every route is shaped `/apps/{app_name}/users/{user_id}/sessions/{session_id}/...`, which
says three true things about how ADK organises state — and one dangerous thing, which is that the
caller's identity is a segment of the URL they type themselves.

## The story

The hostel room numbering.

Block C, second floor, room fourteen: `C-2-14`. Painted on the door, printed on the key tag, written
in the register. Nobody had to be told the scheme; you look at one door and you know how to find any
other.

It works because the numbering matches how the building is actually divided. Blocks really are
separate buildings, floors really are separate landings, rooms really do have one occupant. If the
warden decided that the first digit meant something else — say, which mess you eat at — the number
would still be printed on the door, and it would stop telling you where to go.

A naming scheme is a claim about how the thing is put together. When it is honest, you can navigate
by it. When it is not, you navigate confidently into the wrong place.

## The idea in plain language

Look at the paths from part [1.1](1.1-a-desk-with-a-street-address.md) with the parameters left in:

```text
/list-apps
/apps/{app_name}/app-info
/apps/{app_name}/users/{user_id}/sessions
/apps/{app_name}/users/{user_id}/sessions/{session_id}
/apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts
/apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts/{artifact_name:path}/versions
/apps/{app_name}/users/{user_id}/memory
```

That is a hierarchy, and it says three things.

**An app is the unit of deployment.** One server can serve several; `/list-apps` enumerates them.
Each is a directory under the agents directory, loaded on demand. This is why Day 86's container
question is "which apps ship in this image" rather than "which agent".

**A user owns sessions.** Sessions are nested under a user, not free-floating with a user field. That
is the right shape — it is how you would want to list, expire or delete somebody's conversations —
and it is exactly why the missing check in part
[4.1](../04-blast-radius/4.1-the-caller-says-who-they-are.md) matters so much: the hierarchy promises
ownership and nothing enforces it.

**A session owns artifacts, and artifacts have versions.** Day 47's persistent sessions and Day 36's
long jobs both surface here. `{artifact_name:path}` with that `:path` suffix means the name may
contain slashes, so an artifact can be `reports/august/summary.pdf` — a small decision with a real
consequence, because a path parameter that accepts slashes is the classic place a traversal bug goes.

And one thing sits outside the hierarchy: `PATCH /apps/{app_name}/users/{user_id}/memory` hangs off
the *user*, not the session. That is Day 46's distinction made structural — a session is a
conversation and memory outlives it.

The dangerous reading is the one the story is about. In `/apps/echo/users/alice/sessions`, the
segment `alice` looks like an identity. It is a **string the caller typed**. Nothing in the path
scheme distinguishes "the user this belongs to" from "the user the request claims to be", and the
scheme is so natural that everyone reads the first meaning.

## Why Sutra needs it

Because the desk's whole safety story is built on knowing who is asking. Day 63's approval gates ask
a *specific human* to approve a refund. Day 68's least-privilege tools scope what a *particular
caller* may reach. Day 69's PII boundary is about not showing one person another person's data. All
three assume an identity, and this path scheme is where that identity comes from once the desk is
served over HTTP.

And because it is the map the rest of Phase 13 navigates by. Day 86 mounts a stateless container and
has to ask which of these paths touch local disk; Day 88 puts a proxy in front and has to know which
prefixes to route.

## The mechanism

The hierarchy is not a convention the handlers agree on; it is the function signature. From the
session family, as FastAPI receives it:

```text
GET  /apps/{app_name}/users/{user_id}/sessions/{session_id}
```

**Line by line:**

- Three path parameters, so FastAPI parses them out of the URL and hands the handler three strings.
  Validation is on the *shape* of the URL, not on the caller's right to those values.
- The nesting order is fixed: an app contains users, a user contains sessions. You cannot ask for a
  session by id alone, which is a deliberate design choice — it means every session lookup carries
  its owner, and a store can shard on `user_id`.
- There is no route for "all sessions across users". That absence is a design statement too: this
  API has no administrator view, and a tool that needs one has to walk users it already knows about.

You can read the whole scheme out of the app rather than trusting a document:

```python
    counts = Counter(fam for fam, _m, _p, _k in rows)
```

**Line by line:**

- One `Counter` over the family of each route gives the shape of the surface at a glance: eight
  artifact routes and six session routes against three that run the agent.
- Counting *families* rather than paths is what makes it legible. Twenty-seven paths is a list; eight
  families is a design.

Run it and read the middle of the table:

```bash
cd days/day-85-the-api-surface/lab
uv run python routes.py | grep sessions
```

**Line by line:**

- `grep sessions` because every path in the ownership hierarchy contains that segment, including the
  artifact routes nested inside it — which is itself the point of the exercise.

Measured on 2026-09-07:

```text
  artifacts         DELETE          /apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts/{artifact_name:path}
  artifacts         GET             /apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts
  artifacts         GET             /apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts/{artifact_name:path}
  artifacts         GET             /apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts/{artifact_name:path}/versions
  artifacts         GET             /apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts/{artifact_name:path}/versions/metadata
  artifacts         GET             /apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts/{artifact_name:path}/versions/{version_id}
  artifacts         GET             /apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts/{artifact_name:path}/versions/{version_id}/metadata
  artifacts         POST            /apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts
  sessions          DELETE          /apps/{app_name}/users/{user_id}/sessions/{session_id}
  sessions          GET             /apps/{app_name}/users/{user_id}/sessions
  sessions          GET             /apps/{app_name}/users/{user_id}/sessions/{session_id}
  sessions          PATCH           /apps/{app_name}/users/{user_id}/sessions/{session_id}
  sessions          POST            /apps/{app_name}/users/{user_id}/sessions
  sessions          POST            /apps/{app_name}/users/{user_id}/sessions/{session_id}
    sessions            6
```

The last line is the family count from the summary, which `grep` picks up too. **Fifteen of the
twenty-seven routes carry `{user_id}`** — count them with `routes.py | grep -c user_id`. Every one of
them is an operation on somebody's data, addressed by a name the caller supplies.

Notice the two `POST` routes to the session family: `POST .../sessions` creates one with a
server-chosen id, and `POST .../sessions/{session_id}` creates one with an id the caller picked. Both
are useful — the second lets a client be idempotent about session creation — and the second is also
how a caller collides with, or guesses, somebody else's session id.

## When it breaks

The scheme breaks when a segment means one thing to the designer and another to the caller. There is
no error text, because both readings produce a perfectly well-formed URL.

Here is the shape, with the real one measured in section 4:

```text
  the designer reads:  /apps/echo/users/alice/sessions   "alice's sessions"
  the caller reads:    /apps/echo/users/alice/sessions   "list sessions, as alice"
  the server reads:    /apps/echo/users/{user_id}/sessions   "three strings"
```

The server's reading is the honest one, and it is the one nobody has in mind while writing a client.

**The second way it breaks** is the `:path` converter on `{artifact_name:path}`. It exists so an
artifact name can contain slashes, and it means the parameter also accepts `..` segments. Whether
that reaches disk depends entirely on the artifact service behind it — an in-memory one does not
care, a local-file one might. That is not a finding in this repository, because nothing here has been
tested against it, and naming it as a *place to look* rather than a *bug* is the honest way to leave
it. Day 40's filtering and allowlists is the day that argued for checking rather than assuming.

## In production

**What a professional does.** Reads a path scheme as an ownership diagram and then asks, for each
level, what proves the caller belongs there. In a well-built service that answer is a token whose
subject is compared against the path segment, and the comparison happens in one dependency rather
than in every handler. When the answer is "nothing", as it is here, the path scheme is a convention —
useful for organising storage and useless for protecting it.

**What degrades at scale.** Deep hierarchies get abbreviated. Somebody adds `/sessions/{id}` without
the user prefix "for convenience", a client starts using it, and the ownership information that was
in every URL is now in some URLs. That is how a service ends up with two ways to reach the same
object and a check on one of them.

**The failure that only shows with real traffic.** Session ids that are guessable. Here they are
version-4 UUIDs from the server, which are fine, but `POST .../sessions/{session_id}` lets the client
choose — so a client that picks `user-alice-main` for readability has made every one of its sessions
enumerable, and section 4 has already established there is nothing else in the way.

**The review comment a senior engineer leaves:** *"The hierarchy is right. Add one dependency that
compares the token subject to `{user_id}` and put it on every route that has that parameter — all
fifteen of them — rather than trusting each handler to remember."*

**The interview question:** *"What does this URL scheme tell you about the system?"* The answer that
shows experience reads out the ownership hierarchy, then immediately asks what enforces it, because
a path is a filing system and filing systems do not have locks.
