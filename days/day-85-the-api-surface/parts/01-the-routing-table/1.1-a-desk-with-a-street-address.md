# 1.1 — A desk with a street address

## One-line answer

`adk api_server` turns the agent you have been running from a terminal into twenty-seven HTTP
routes, and the moment it does, the desk stops being a program you run and becomes a service other
people can call — which changes almost nothing about the agent and everything about what can go
wrong.

## The story

The enquiry counter with a numbered window.

For years the office worked by people walking in and finding whoever seemed to know. Then somebody
put up a counter with three windows and painted numbers on them. Window one: new applications.
Window two: status of an existing file. Window three: complaints.

Nothing about the work changed. The same clerks do the same things. What changed is that the office
now has a *surface* — a small number of named places where the outside world touches it — and from
the day the numbers went up, every question anybody asks arrives through one of them.

That is a good thing, mostly. It is also the day the office acquired a queue, opening hours, and the
problem of somebody walking up to window two and asking for another person's file.

## The idea in plain language

Everything so far in this curriculum ran the desk *in process*. Day 3's hand-rolled loop, Day 13's
runner, Day 77's standup agent, Day 79's eval suite — all of them import the agent, call it, and
print. The caller and the agent are the same program.

An **API server** breaks that in two. The agent runs in one process, listening on a port; the caller
is anything that can make an HTTP request — a web page, a mobile app, another agent, `curl`, a
scheduled job. Between them there is nothing but a URL and a JSON body.

ADK ships one, and it is not a toy. Two ways to start it:

- `adk api_server` — the command-line front door.
- `get_fast_api_app(...)` — the factory the command calls, which you can call yourself and embed in
  an application of your own. Part [1.3](1.3-two-ways-to-start-it.md) is what differs between them,
  and the difference turns out to matter.

Either way you get a **FastAPI** application. FastAPI is a Python web framework: you declare
functions with a path and a method, it handles the HTTP, validates the request body against a type,
and generates a machine-readable description of the whole surface at `/openapi.json`. ADK has
already written those functions for you.

What this day does is look at that surface the way a stranger would. Not *does my agent work* — Days
79 to 83 were about that — but **what is now reachable, by whom, and what does it say when it says
no.** Those are different questions, and this is the first day where the answer to any of them is
not "only me".

## Why Sutra needs it

Because Phase 13 is about getting the desk out of the terminal, and this is the first step: Day 86
puts it in a container, Day 88 puts it behind a cluster, and both of those assume there is an HTTP
surface to put anywhere. Every later phase talks to the desk over this.

And because the plan puts a security phase *before* this one on purpose. Days 66 to 69 built an
injection threat model, guardrail callbacks, least-privilege tools and a PII boundary — all of them
about what the agent may do. This day is about what *the world* may ask it to do, which is a
different attack surface entirely, and section 4 is what happens when you serve the default.

## The mechanism

The routing table is not documentation, it is data on the app object. `routes.py` reads it:

```python
    for route in app.routes:
        path = getattr(route, "path", None)
        if path is None:
            continue
        methods = sorted(getattr(route, "methods", None) or [])
        kind = type(route).__name__
        rows.append((family(path), ",".join(methods) or "WEBSOCKET", path, kind))
```

**Line by line:**

- `app.routes` is a plain list on the FastAPI object, populated at construction. Nothing has to run
  and no request has to be made; building the app is enough to know everything it will answer.
- `getattr(route, "path", None)` because not everything in that list is a path. FastAPI mounts static
  file handlers and middleware-ish objects there too, and a mount has no single `path` to print.
- `getattr(route, "methods", None) or []` — a WebSocket route has no `methods` at all, so the `or []`
  turns a `None` into an empty list and the `or "WEBSOCKET"` on the join turns an empty list into a
  label. That is not decoration: `/run_live` is the one route on this server that is not
  request-and-response, and a table that showed it with a blank method column would hide that.
- `type(route).__name__` keeps the class name, because `APIRoute` and `APIWebSocketRoute` are how
  FastAPI itself distinguishes the two.

Grouping them needs one ordering decision that is easy to get wrong:

```python
FAMILIES = (
    ("docs", ("/openapi.json", "/docs", "/redoc")),
    ("artifacts", ("/artifacts",)),
    ("discovery", ("/list-apps", "/app-info")),
    ("sessions", ("/sessions",)),
    ("memory", ("/memory",)),
    ("running the agent", ("/run", "/run_sse", "/run_live")),
    ("identity", ("/agent-identity",)),
)
LIVENESS = frozenset({"/health", "/version"})
```

**Line by line:**

- First match wins, and the order is load-bearing. An artifact path contains `/versions`, and
  `"/version" in "/artifacts/.../versions"` is `True`, so a substring rule for liveness placed first
  would file eight artifact routes under liveness. The first draft of this script did exactly that.
- `LIVENESS` is a `frozenset` of **exact** paths, checked before the substring families, because
  those two really are two specific routes and not a prefix.
- Artifacts come before sessions for the same reason: every artifact path contains `/sessions`.

Run it:

```bash
cd days/day-85-the-api-surface/lab
uv run python routes.py; echo "exit: $?"
```

**Line by line:**

- No flag. `--public` adds a note about credentials, which is section 4's subject.

Measured on 2026-09-07 — the summary, with the full table in the script's own output:

```text
  27 routes in 8 families
    artifacts           8
    sessions            6
    docs                4
    running the agent   3
    liveness            2
    discovery           2
    identity            1
    memory              1

  websocket routes: ['/run_live']
```

**Twenty-seven routes, and three of them run the agent.** The other twenty-four are bookkeeping:
sessions, artifacts, memory, discovery, health, and the four that serve the generated documentation.

That ratio is the first useful thing this table says. An agent server is mostly not about agents. It
is about the state around them — who is talking, what was said before, what files were produced — and
that is the state section 4 finds nobody guarding.

## When it breaks

The routing table breaks by being empty, and an empty table is not an error:

```python
    if not rows:
        print("\n  no routes: the app was built with nothing to serve")
        return 1
```

**Line by line:**

- A FastAPI app with no routes is perfectly valid. It starts, it binds a port, it answers 404 to
  everything, and a liveness probe pointed at it fails while a "is the process up" check passes.
- `return 1` because a server with nothing to serve is a deployment that will look healthy in every
  dashboard until somebody tries to use it.

The failure you actually meet first is upstream of that: the agents directory does not import.

```text
Agent not found: 'echo'. No matching directory or module exists in '<...>/lab/agents/echo'.
```

That is a real 404 body from this server and part
[3.2](../03-when-it-refuses/3.2-the-404-that-reads-out-the-disk.md) is about how much of it a
stranger gets to read. What matters here is when it arrives: **not at startup.** The app builds
happily with a broken agent directory, because agents are loaded when a request asks for one. So the
process starts, the port opens, `/health` says `ok`, and the first real caller gets the 404.

## In production

**What a professional does.** Treats the routing table as a reviewable artefact. `/openapi.json` is
generated from the code, so it can be dumped in continuous integration and diffed against the
previous commit — and a route appearing or disappearing becomes a line in a pull request rather than
a discovery. On a server somebody else wrote, that dump is also the fastest way to know what you have
just agreed to operate.

**What degrades at scale.** Twenty-seven routes is a table a person reads. Behind a gateway with
forty services it is a thousand, and nobody reads it — which is where the interesting exposures live,
because a route nobody has looked at since it was added is a route with the original defaults on it.

**The failure that only shows with real traffic.** A route that exists for the development UI and
ships anyway. This server has four: `/docs`, `/redoc`, `/docs/oauth2-redirect` and `/openapi.json`.
They are enormously useful locally and they publish your entire surface, including parameter names
and body schemas, to anybody who can reach the port. Nothing about them is a vulnerability; together
with section 4's finding that no route needs a credential, they are a map handed to whoever asks.

**The review comment a senior engineer leaves:** *"Dump `/openapi.json` in CI and fail the build when
it changes without a corresponding note. I do not mind which routes we expose — I mind finding out
from a log line."*

**The interview question:** *"You have been handed a running service and no documentation. What do
you do first?"* The answer that shows experience asks the service to describe itself — the routing
table, the generated schema, the health endpoints — before reading a line of source, because the
surface is what other people depend on and the source is merely how it is currently implemented.
