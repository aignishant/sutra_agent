# 3.3 — An error with a handle on it

## One-line answer

Both of section 3's findings have the same fix: decide the error body deliberately, give every kind of
refusal a stable identifier a client can branch on, and put the prose in a field that is allowed to
change — which is a standard, not an invention.

## The story

The medicine strip with a batch code.

Two ways a chemist can label what is in your hand. One is a strip printed at the factory: the name,
the strength, a batch number, an expiry, and a code that resolves to exactly one production run. The
other is a paper envelope with *"2 tablets, morning and night"* written on it in ballpoint.

The envelope is more readable. It is also the one that is useless at three in the morning in a
different city, where somebody needs to know what you actually took and whether it is the batch that
was recalled.

The printed strip does not replace the handwriting — the dosage still gets written on it. What it
adds is a **handle**: something short, stable and meaningless to read, which anybody can look up.

## The idea in plain language

Put section 3's two findings side by side and they are one problem.

Part [3.1](3.1-one-field-two-types.md): `detail` is a string on a 404 and a list on a 422, so a client
cannot write one handler. Part [3.2](3.2-the-404-that-reads-out-the-disk.md): the string it *is*
carries the server's filesystem layout. Both come from the same absence — **nobody decided what an
error body is.** It is whatever the layer that refused happened to produce.

Deciding it means answering three questions:

**What is the shape?** One JSON object, the same for every refusal from every layer, so a client has
one code path.

**What does the client branch on?** Not the prose and not the status code. Status codes are too
coarse — a 409 can mean four things — and prose changes when somebody improves the wording. What is
needed is a **stable identifier per kind of refusal**: a value the server promises not to change,
which the client compares. That is the batch code on the strip.

**Where does the prose go?** In a field of its own, explicitly for humans, explicitly allowed to
change, and explicitly not the thing anybody branches on. That is where the dosage is written.

This is a solved problem with a published answer, and the day's paper is that answer: **Problem
Details for HTTP APIs**, `doi:10.17487/RFC9457`, which defines the `application/problem+json` media
type and five members — `type`, `title`, `status`, `detail`, `instance` — plus any extension members
you need. `type` is the handle. `detail` is the prose. The rest is context.

The whole of part 3.3 in one sentence: **the error body is part of the interface, so design it like
one.**

## Why Sutra needs it

Because Sutra's callers are increasingly not people. Day 88 puts a sidecar in front, Phase 14 puts
other agents on the far side of A2A, and an agent handling a refusal has exactly the problem the
story is about — it can read the prose, and reading prose to decide what to do is how a wording
change becomes an outage.

And because the desk already has kinds of refusal that a caller must tell apart. "This ticket does not
exist" sends the user to search; "this refund is over the limit" sends it to Day 63's approval queue.
Both are legitimate, neither is an error in the server, and they are currently distinguishable only by
reading English.

## The paper behind it

> **Problem Details for HTTP APIs**
> RFC Editor, 2023. `doi:10.17487/RFC9457`

Defines `application/problem+json`: a single JSON object carrying `type` (a URI identifying the kind
of problem — the stable handle), `title` (a short human summary of that kind), `status`, `detail` (a
human explanation of *this* occurrence) and `instance`, plus extension members the API may add. It
obsoletes RFC 7807 and is the standard answer to "what shape is an error body".

Read it after the parts: [papers/01 — An error a client can act
on](../../papers/01-an-error-a-client-can-act-on.md).

## The mechanism

A problem document is built, not derived. The handler in the paper's demo:

```python
        @app.exception_handler(DeskError)
        async def as_problem(request: Request, error: DeskError) -> JSONResponse:
            body = {
                "type": error.type_,
                "title": error.title,
                "status": error.status_code,
                "detail": error.detail,
                "instance": str(request.url.path),
            }
            body.update(error.extra)
            return JSONResponse(
                status_code=error.status_code,
                content=body,
                media_type="application/problem+json",
            )
```

**Line by line:**

- One handler for every refusal of this kind, registered once on the app. That is what makes the shape
  a property of the API rather than of each endpoint — part 3.1's whole complaint.
- Each of the five members is assigned from a field the raiser chose. Nothing is derived from an
  exception's `str()`, which is exactly the discipline part
  [3.2](3.2-the-404-that-reads-out-the-disk.md) argued for: a constructed body cannot leak a message
  nobody reviewed.
- `instance` is the request path, so a support conversation can start from the response rather than
  from a description of what somebody clicked.
- `body.update(error.extra)` adds the extension members — the ticket number, the amount, the limit.
  The standard allows these and they are what turns a refusal into something a client can render
  without a second request.
- `media_type="application/problem+json"` is the part people skip, and it is how a client knows to
  look for `type` at all. Without it the body is a JSON object of unknown provenance.

The client's whole decision becomes one lookup:

```python
def decide(status: int, content_type: str, body: dict) -> str:
    """The client's whole decision. It branches on `type` and nothing else."""
    if content_type.startswith("application/problem+json"):
        return ROUTE_TO.get(body.get("type"), "unknown refusal")
    return "unknown refusal"
```

**Line by line:**

- The content type is checked first, so a response that is *not* a problem document is not searched
  for fields it never promised. This is what makes adoption incremental: an endpoint that has not been
  converted yet falls through to "unknown" rather than being mis-parsed.
- `ROUTE_TO.get(...)` with a default, so a `type` the client has never seen is handled as unknown
  rather than crashing. A server is allowed to add new problem types; a client must not break when it
  does.
- `status` is a parameter and is never consulted. That is deliberate and is the point of the demo: in
  the paid arm both refusals could have shared a status code and the client would still route them
  correctly.

**Line by line:**

- One app, one flag. `--off` removes the exception handler and lets the framework's default shape
  through; nothing else about the routes or the refusals changes.

Measured on 2026-09-07, the two bodies side by side:

```text
  404 application/problem+json
  {"type": "https://sutra.example/errors/no-such-ticket", "title": "No such ticket", "status": 404
  the client sends this to: search screen

  404 application/json
  {"detail": "There is no ticket numbered 0001."}
  the client sends this to: unknown refusal
```

**Same refusal, same status, same information for a person.** One of them a machine can route and one
of them it cannot. The full run, with both refusal kinds and the counts, is in the paper part.

## When it breaks

Three ways, and the first two are the common ones.

**The `type` becomes a URL somebody fetches.** The standard says it is an identifier, and a URI is a
good identifier because it is namespaced. It does not have to resolve. Teams that make it resolve end
up with a documentation site in the critical path of error handling, and a client that hangs on a 404
error because it tried to look up the error.

**The prose gets branched on anyway.** Having added `type`, somebody still writes
`if "limit" in detail`. It works, it ships, and the first rewording breaks it silently. The
countermeasure is not discipline — it is to make `detail` obviously unstable, by varying it, and to
document that only `type` is contractual.

**Only some of the API adopts it.** Two shapes again, and now three including the framework's 422.
The framework's validation errors are the hard part in practice: they are generated before your code
runs, and converting them means overriding the validation exception handler as well. An adoption that
stops before that has left the most common error in production in the old shape — which is exactly
what part [3.1](3.1-one-field-two-types.md) measured.

**The error text when the media type is missed** is not an exception; it is the client's default
branch. In the demo's ablation, that is the line `the client sends this to: unknown refusal`, printed
twice, with an exit code of `1`. A refusal the client cannot classify is not a crash — it is a
customer sent to the wrong screen.

## In production

**What a professional does.** Registers one exception handler, converts the framework's validation
errors in the same change, and keeps a list of `type` values as a real artefact — reviewed like any
other part of the interface, because adding one is adding a case every client may need to handle.

**What degrades at scale.** The `type` vocabulary grows and nobody prunes it. Fifty types means a
client with fifty branches, most of which route to the same place. The useful discipline is a
hierarchy — a small number of `type` values a client must handle, with the specificity in extension
members — so that a new problem type is usually a new *value* of an existing field rather than a new
branch.

**The failure that only shows with real traffic.** Errors from things you do not own. A gateway's 429,
a proxy's 502, a load balancer's 503 — none of them will be problem documents, whatever your
application does. A client written to assume the standard everywhere breaks on the first infrastructure
error, which is why the content-type check in `decide()` is not defensive clutter.

**The review comment a senior engineer leaves:** *"Do the validation handler in the same pull request.
If we only convert our own raises, the 422 stays as it is and it is the error our callers hit most —
we will have added a standard and kept the problem."*

**The interview question:** *"How should an API report an error?"* The answer that shows experience
gives a shape, names the field the client branches on, and says explicitly that the human-readable
part is not contractual — and then mentions that the framework's own validation errors are the ones
that have to be converted, because that is the half most people forget.
