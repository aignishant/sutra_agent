# 3.2 — The 404 that reads out the disk

## One-line answer

Ask this server for an app that does not exist and the refusal comes back with the absolute
filesystem path it looked in, account name included — a hundred and sixty-five characters where
about twenty-six were needed, on a route that requires no credential.

## The story

💥 **The wrong number who tells you the whole address.**

🎬 **The scene.** You dial a number from an old note and a stranger answers. You ask for the person
you were expecting.

😬 **The naive fix.** The stranger is helpful. Very helpful. *"No, no, there's nobody by that name
here — this is 14B Anand Apartments, behind the water tank, the Sharmas' old flat. We moved in in
March. You probably want the family that shifted to Sector 9, near the school."*

💥 **Why it fails.** Nothing bad happened, and nothing about it was rude. But a person who dialled at
random now knows a flat number, a landmark, when it changed hands, and where somebody moved to — all
of it volunteered, in answer to a question that only ever needed the word *"no"*.

💡 **The insight.** The helpfulness is the leak. Every extra fact was offered in good faith to make
the refusal more useful, and the person who benefits most from a detailed refusal is the person who
had no business asking. **The right answer to a wrong question is short.**

## The idea in plain language

Error messages have two audiences and they want opposite things.

**The operator** wants everything: which directory, which configuration, which candidate was tried,
what the resolved path was. Give them less and every incident takes an hour longer.

**The caller** wants one fact: their request was refused, and specifically enough that they can fix
it. Give them more and you are describing the inside of a machine to somebody standing outside it.

An error body sent over HTTP goes to the caller. It is therefore the wrong place for the operator's
version — and it is where the operator's version lands by default, because the natural way to write a
helpful message is to include what you know, and at the point of failure you know the path.

This server does exactly that. Ask for an app that is not there and you get the path it searched,
absolute, from the drive letter down.

Three things make that worse than it first sounds:

- The route needs **no credential** (part [4.1](../04-blast-radius/4.1-the-caller-says-who-they-are.md)).
- The path contains the **account name** the process runs as.
- The message is *correct*, so nothing will ever flag it.

## Why Sutra needs it

Because Day 69 drew a PII boundary around what the desk may say about people, and this is the same
boundary drawn around the machine. An account name and a directory layout are not secrets in the
sense a password is; they are the reconnaissance that makes the next question a better one.

And because the repository goes public in Phase 14 (Principle 9). A day document that pasted this
message verbatim would publish the author's account name in git history for ever — which is why the
lab masks the home directory in the transcript and says so, rather than quietly trimming the line.

## The mechanism

One request, and everything after it is inspection:

```python
    async with client(app) as http:
        response = await http.get("/apps/nope/app-info")
    body = response.json()
    detail = body["detail"]
```

**Line by line:**

- `nope` is not a special name. It is any name that is not a directory under the agents directory,
  which is what a client sends when it has a typo, an old configuration, or is guessing.
- `/app-info` is a discovery route — the polite one, the one a UI calls to find out what it is
  talking to. The refusal is not from a privileged path.

The check is a regular expression for anything path-shaped, plus one exact test:

```python
HOME = str(Path.home())
PATH_LIKE = re.compile(r"(?:[A-Za-z]:\\|[A-Za-z]:/|/)[\w.\-\\/]{8,}")
```

**Line by line:**

- Three alternatives at the front cover a Windows drive with either slash and a POSIX absolute path,
  so the same check works wherever the reader runs it.
- `{8,}` requires a run of at least eight path characters, so a bare `/run` in a message is not
  reported as a filesystem path. The check is deliberately blunt: this is a smell test, and a smell
  test that fires on every mention of a slash gets switched off.
- `HOME` is compared exactly rather than by pattern, because "does this message contain the account's
  home directory" is a stronger and less arguable finding than "this looks like a path".

And the masking, which is presentation and not a fix:

```python
def redact_home(text: str) -> str:
    """Hide this machine's account name in the transcript, not in the finding."""
    return text.replace(HOME, "<home>").replace(HOME.replace("\\", "\\\\"), "<home>")
```

**Line by line:**

- Two replacements because a path can appear raw or JSON-escaped, and the second form is what you get
  if the message has been through a serialiser.
- The docstring says what this is for, because a reader who sees a redaction in a lab is entitled to
  wonder whether the lab is hiding the finding. It is hiding the account name; the finding is the
  next four lines of output.

Run it:

```bash
cd days/day-85-the-api-surface/lab
uv run python leak.py; echo "exit: $?"
```

**Line by line:**

- No flag: the message the server really returns. `--redacted` is the shape it ought to have.

Measured on 2026-09-07:

```text
a caller asks for an app that does not exist:

  GET /apps/nope/app-info
  404 application/json

  Agent not found: 'nope'. No matching directory or module exists in '<home>\OneDrive\Desktop\Projects\sutra\days\day-85-the-api-surface\lab\agents\nope'.

  path-like strings in the message: 1
  the machine's home directory appears in it: True
  characters of message the caller needed: about 26
  characters the caller got: 165
```

**A hundred and sixty-five characters for a question that needed twenty-six.** Where `<home>` appears,
the real response has the account name; run it yourself and you will see yours.

Read what a stranger has learned from one unauthenticated request with a guessed name:

| From the message | What it is worth |
| --- | --- |
| the account name | who the process runs as, which is who to target |
| `OneDrive\Desktop\Projects` | a workstation, not a hardened server |
| `sutra\days\day-85-...\lab` | the repository name and its layout |
| `\agents\nope` | how app names map to directories, so app names are directory names |

The last row is the one with teeth. It converts "app names are opaque identifiers" into "app names are
path segments", which is the beginning of every traversal question — and part
[1.2](../01-the-routing-table/1.2-what-the-paths-say-about-the-design.md) already noted a route
parameter declared as `{artifact_name:path}`.

## When it breaks

The refusal is already the break, so what belongs here is the shape of the fix and the way it goes
wrong.

The wrong fix is to delete the message. Then the operator loses the only line that would have told
them the agents directory was mounted at the wrong path, and the next incident is a long one.

The right fix is that the same failure produces **two** artefacts. What the caller gets:

```bash
uv run python leak.py --redacted; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  {"type":"/errors/app-not-found","title":"No such app",
   "status":404,"detail":"There is no app named 'nope'.",
   "instance":"/apps/nope/app-info","app":"nope"}

  the caller learns the same thing: they asked for something that is not here
  what they no longer learn is where this process keeps its files
```

And what the operator gets is the full path, in a **log line**, with the request id that ties the two
together — which is Day 22's structured logging and Day 84's trace context doing the job they were
built for. The information is not lost. It is sent to the party that has a right to it.

Notice that the redacted body is an RFC 9457 problem document, which is part
[3.3](3.3-an-error-with-a-handle-on-it.md) and the paper. Fixing the leak and fixing the shape turn
out to be the same edit, because both are answered by "decide what the error body is, deliberately".

**There is no error text for the leak itself.** That is worth saying plainly: this is a correct 404
with an accurate message, and no linter, test or monitor in a normal project would ever mention it.
The only thing that finds it is somebody reading the response as a stranger would.

## In production

**What a professional does.** Splits the two audiences at one place: an exception handler that builds
the caller's body from a small set of allowed fields, and logs the exception with everything else. The
rule that makes it stick is that the caller's body is **constructed**, never derived from the
exception's string — because the moment it is derived, every new exception message is a new
disclosure.

**What degrades at scale.** More layers, more messages, more of them written by people who never
thought about the boundary. A database driver's error mentions a connection string; an ORM's mentions
a table; a cloud client's mentions a project id and a bucket. Each is a helpful message from a library
whose author had no idea it would be forwarded to the internet.

**The failure that only shows with real traffic.** Enumeration. One 404 is a curiosity; ten thousand
of them, with different names, is a map — and because these responses differ (a missing app says one
thing, an existing app with a bad session says another), the differences themselves answer questions.
Uniform refusals are not politeness, they are what stops the difference between two errors from being
information.

**The review comment a senior engineer leaves:** *"Never put a caught exception's string into a
response body. Build the body from fields we chose, log the exception with the request id, and put
that rule in the exception handler so nobody has to remember it per endpoint."*

**The interview question:** *"What is wrong with a detailed error message?"* The answer that shows
experience names the two audiences and says that the error body is the caller's channel and the log
is the operator's — then adds the part most people miss, which is that the fix must be a construction
rather than a filter, because a filter has to anticipate every message.
