# 3.1 — One field, two types

## One-line answer

Every refusal from this server has a field called `detail`, and on a 404 it is a string while on a
422 it is a list — so a client that read one refusal and wrote a handler gets
`AttributeError: 'list' object has no attribute 'lower'` the first time somebody sends a bad body.

## The story

💥 **The rejection slip that says only "incomplete".**

🎬 **The scene.** A form goes in at the counter. Ten days later it comes back with a slip stapled to
it: **INCOMPLETE — resubmit**. Nothing else. The clerk who wrote it knew exactly what was missing;
the slip has one box and the box has one word in it.

😬 **The naive fix.** You go back, guess, fill in the two fields you are least sure about, and
resubmit.

💥 **Why it fails.** It comes back again, same slip, same word. The missing thing was a signature on
the second page, which you were confident about and never looked at. Three rounds later somebody
mentions it in passing. Every slip was accurate. None of them was usable.

💡 **The insight.** The problem is not that the office refused. Refusing is its job. The problem is
that the refusal is **not something you can act on** — and the fix is not politeness or more words,
it is a slip with a *field* on it saying which page and which line. A machine could route that. A
person can route it in a second. A paragraph of prose cannot be routed at all.

## The idea in plain language

An API refuses constantly, and a refusal is part of its interface just as much as a success. So the
same question applies to it: can a caller act on this without guessing?

FastAPI has one convention, and this server uses it everywhere: an error body is
`{"detail": <something>}`. That looks like a contract. It is not, because `<something>` has two
different types depending on which layer refused.

**When a handler refuses** — no such session, no such app — it raises `HTTPException(detail="...")`
and `detail` is a **string**, meant for a person to read.

**When validation refuses** — the body is missing a field, or a field is the wrong type — FastAPI
never reaches the handler. It returns a 422 whose `detail` is a **list of objects**, one per
problem, each with `type`, `loc`, `msg` and `input`.

Both are sensible on their own terms. Together they are a field whose type you cannot know without
knowing which layer produced the response, and nothing in the response tells you that.

The consequence is not a style complaint. It is that the natural client code — read one error,
write a handler — is wrong in a way that only shows up on the *other* kind of error, which is
usually the one that happens in production rather than in the developer's first afternoon.

## Why Sutra needs it

Because the desk is about to be called by something other than a person at a terminal: Day 88's
sidecar, Day 90's registry, another agent over A2A in Phase 14. Every one of those has to branch on
failure, and every one of them will meet both kinds.

And because Day 21 is the day this repository decided errors surface rather than being swallowed.
That was about the agent's internals. This is the same principle at the boundary: an error that
crosses a process boundary has to survive the crossing in a form the other side can use, and "a
field that is sometimes a string" does not.

## The mechanism

Four ways of asking wrongly, chosen because each one is refused by a different part of the stack:

```python
WRONG = (
    ("no such route", "GET", "/nosuchroute", None),
    ("no such app", "GET", "/apps/nope/app-info", None),
    ("no such session", "GET", f"/apps/{APP_NAME}/users/{USER}/sessions/missing", None),
    ("body missing fields", "POST", "/run", {}),
)
```

**Line by line:**

- The first is refused by the router before any handler exists. The second and third by handlers, at
  different depths. The fourth by pydantic validation, before the handler is entered.
- Four layers, one field name. That is the point of the sample: if the shape were a property of the
  API it would not depend on which layer answered.

The client is the thing under test, and it is written the way somebody actually writes it:

```python
def client_handler(body: dict) -> str:
    """What a caller writes after reading one 404: pull `detail` out and show it to somebody."""
    return body["detail"].lower()
```

**Line by line:**

- `.lower()` stands in for anything a caller does with a string — log it, match on it, put it in a
  message box. The specific method does not matter; what matters is that it is a string method.
- No type check, because there is nothing in the API's documentation that suggests one is needed. The
  field is called `detail` and the first three responses make it a string.

And the finding is the set of types, not any one response:

```python
        kind = type(body.get("detail")).__name__
        kinds.add(kind)
    ...
    if len(kinds) > 1:
```

**Line by line:**

- `type(...).__name__` rather than `isinstance` checks, so the script reports what is there instead of
  what it expected. A third type appearing in a future version would show up rather than being folded
  into "not a string".
- `body.get("detail")` with `get`, so a response with no `detail` at all yields `NoneType` and is
  counted as a third shape rather than raising inside the measurement.
- The whole verdict is `len(kinds) > 1`. One shape is a contract; two is a coincidence the caller has
  to discover.

- No flag. `--count-only` is the ablation and it is in **When it breaks**.

Measured on 2026-09-07:

**Three refusals the client handles and one that crashes it.** The crash is not in the server; the
server did exactly the right thing. It is in the client, on the fourth of four cases, and it is the
case a caller is least likely to hit while developing and most likely to hit once real callers exist.

Notice also what the three string cases give you: `"Not Found"`, `"Session not found"`, and a
sentence about directories. To branch on those you would have to match on English — and a wording
change on the server, which nobody would think of as a breaking change, silently reroutes a customer.
That is what part [3.3](3.3-an-error-with-a-handle-on-it.md) fixes.

## When it breaks

It breaks by being counted instead of read, and the ablation is the report most services actually
ship:

```bash
uv run python shapes.py --count-only; echo "exit: $?"
```

Measured on 2026-09-07:

```text
4 error responses

  every response carried a status code:      4 of 4
  every response was application/json:       4 of 4
  every response had a `detail` field:       4 of 4

  the error surface is consistent and machine-readable
```

**Every line of that is true, and the exit code is `0`.** Four of four, three times over. The word
*consistent* is doing an enormous amount of work: the responses are consistent in every property
being measured, and the property that matters is not among them.

There is no error text for the ablation, because nothing went wrong. A report was written that had no
slot for the finding — which is the shape Days 79, 81, 82 and 83 each measured in their own
instrument, and this is the fifth.

**The second failure mode** is the client that guards without fixing:

```text
  detail = body.get("detail")
  message = detail if isinstance(detail, str) else "request rejected"
```

That never crashes and it throws the 422's information away — the field names, the reason, the input
— which is exactly the content the caller needed in order to correct the request. A guard that turns
a rich error into "request rejected" is the rejection slip from the story, written by the client
instead of the server.

## In production

**What a professional does.** Fixes it on the server, once, with an exception handler that renders
every refusal in one shape. Doing it in each client means doing it in each client, in each language,
for ever — and the third client will get it wrong. Part [3.3](3.3-an-error-with-a-handle-on-it.md) is
what that one shape should be, and the paper this day reads is the standardised answer.

**What degrades at scale.** More layers, more shapes. Put a gateway in front (Day 88) and its
refusals — rate limits, authentication, upstream timeouts — arrive in the gateway's format, not the
application's. A client that handles two shapes now handles three, and the third one is produced by
something the application team does not own.

**The failure that only shows with real traffic.** The 422 is the *common* error in production and
the *rare* error in development. Developers send the bodies they designed; real callers send bodies
built by other people's code from other people's data. So the untested branch is the one that gets
all the traffic, and it is the branch where the field changes type.

**The review comment a senior engineer leaves:** *"Our error contract is a field that is sometimes a
string and sometimes a list. Pick one shape, put it behind one exception handler, and write it in the
API docs — before we have three clients rather than one."*

**The interview question:** *"What does your API return when it refuses?"* The answer that shows
experience gives one shape and can name every layer that is capable of producing a response — router,
validation, handler, middleware, gateway — because those are the places a second shape comes from.
