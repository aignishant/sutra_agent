# 5.1 — Taught on dry land

## One-line answer

There is no `kubectl`, no `kind`, no `k3d` and no `docker` on this machine, so nine manifest
properties, one topology derivation and one startup race were measured for real and every command
that needs a cluster is written down unrun — which makes the Phase 13 gate's second clause the one
finding this day cannot close.

## The story

The swimming lesson on the bench.

The first sessions happen out of the water. Lie on a bench, arms over the edge, and practise the
stroke: the reach, the catch, the recovery, the breathing on alternate strokes. The coach corrects
your elbow. By the end you can do the whole movement correctly and consistently.

You have not swum. Not one metre. Everything you learned is real and transfers, and the two things
you cannot learn on a bench are the two things that actually make swimming hard: that water pushes
back, and that you have to breathe on its schedule rather than yours.

The lesson is worth having. Calling it swimming is not.

Here is the honest inventory for this day.

Eight commands. Every one is a real command, written out so it can be run on a machine that has the
tooling, and **none of them was run here.** No output from any of them appears anywhere in this day,
because a transcript nobody produced is a fabrication regardless of how confident the author is about
what it would have said.

## Why Sutra needs it

Because Phase 13's gate is *"traced end-to-end; runs in local k8s"* and this is the day that was
supposed to make the second clause true. It does not. The gate closes tomorrow-and-after with that
clause unverified, and the ledger row for this day has to say so rather than implying a cluster ran.

And because Principle 10 is *fail honestly*, and it is addressed to the author as much as to the
agent. The tempting version of this day pastes a plausible `kubectl get pods` showing `2/2 Running`.
It would be indistinguishable from a real one to every reader, it would make the day feel complete,
and it would be a lie in a document whose whole subject is checking claims.

## The mechanism

What makes the honest version tolerable rather than merely honest is that the *deliverable* of a
deployment day is a document, and the document is real and complete. Part
[1.3](../01-what-the-cluster-is-told/1.3-the-document-is-the-artifact.md) argued that; this is the
argument being cashed.

The day's own eval reports the same thing about the product:

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python gate.py; echo "exit: $?"
```

**Line by line:**

- Six checks against `deploy/k8s/`, which is the build brief and does not exist yet, so the failures
  are the assignment rather than a defect.

Measured on 2026-09-07:

```text
checking deploy/k8s/ (exists: False)

  FAIL  1  deploy/k8s/deployment.yaml exists
  FAIL  2  it parses as Kubernetes documents
  FAIL  3  a README carries the cold start
  FAIL  4  no credential literal under deploy/
  FAIL  5  the manifests are committed
  FAIL  6  the sidecar decision is in the file

  0 of 6 checks pass
    - 1  deploy/k8s/deployment.yaml exists: no k8s/deployment.yaml
    - 2  it parses as Kubernetes documents: nothing to parse
    - 3  a README carries the cold start: no k8s/README.md, so there is no cold start to follow
    - 4  no credential literal under deploy/: no deploy/k8s to search
    - 5  the manifests are committed: no deploy/k8s to ask git about
    - 6  the sidecar decision is in the file: no manifest, so no decision is recorded

  deploy/k8s/ is the build brief; the learner writes every line of it

```

Note what checks 4 and 5 report: *"no deploy/k8s to search"* and *"no deploy/k8s to ask git about"*,
rather than *"no credential found"* and *"not gitignored"*. Those would both have been technically
true and would have counted as passes — the vacuous-truth trap from part
[3.1](../03-what-the-manifest-must-say/3.1-checking-what-the-cluster-would-read.md), one directory
up. A check whose subject is missing has to say so.

## When it breaks

The honest inventory breaks by decaying into an excuse. Three ways, and the second is the real risk.

**The unrun list becomes permanent.** Eight commands written down and never executed is a to-do list
on its first day and a fiction after a month. The mitigation is that every one of them is in the
hub's build brief with the tooling install as its own step, so the list has an owner and a first
action.

**The measured half gets over-claimed.** *"The manifest is checked"* quietly becomes *"the deployment
is verified"* in a summary somewhere, and by the time it reaches a status line the distinction is
gone. This is Day 83 part 5.2's finding — a summary with no slot for a caveat drops the caveat — and
the countermeasure is the same: the caveat travels in the same sentence as the claim, so compression
cannot separate them. The ledger row for this day says *the cluster half did not run*, not
*⚠️ see day 88*.

**The parts that only a cluster teaches are skipped.** Everything in the unrun table above is a
learning objective, not a formality. `ErrImageNeverPull`, `Init:0/1`, a Pod that is `2/2 Running`
with one container crash-looping — these are Kubernetes' actual vocabulary of failure, and reading
about them is genuinely not the same as recognising them at speed. That is the water pushing back.

There is no error text for any of this, and that is precisely the difficulty: an incomplete day
produces no signal at all unless somebody writes one.

## In production

**What a professional does.** States the scope of what was verified in the same breath as the result.
*"Manifests pass policy checks; not applied to a cluster"* is a useful sentence that somebody can act
on. *"Deployment ready"* is not, and the difference between them is the difference between a handover
that works and one that produces an outage on somebody else's shift.

**What degrades at scale.** The gap between what CI can check and what only production can. Static
checks scale beautifully — nine properties over four hundred manifests costs nothing — while
end-to-end verification gets slower and flakier as the system grows, so the temptation to lean on the
cheap half increases exactly as the expensive half becomes more necessary. Naming which half a green
build represents is the discipline that survives.

**The failure that only shows with real traffic.** A property that is true of the document and false
of the cluster. The manifest says `runAsNonRoot: true` and the image's default user is root, so the
document is correct, the checker is happy, and the Pod will not start. Two artifacts, each valid, and
the incompatibility exists only where they meet. Nothing on this machine can find that class of
defect, and it is the single strongest argument for the eight unrun commands.

**The review comment a senior engineer leaves:** *"Ship the manifests and the checker. Put the eight
cluster commands in the README as a checklist with a box each, and do not let anybody mark this
'done' until somebody has run them once on a machine that can."*

**The interview question:** *"You could not test in a real environment. What did you do?"* The answer
that shows experience does not apologise. It states what was verified, states what was not, names the
specific defects the untested half would have caught, and says what it would take to close the gap —
because that last part is the difference between a limitation and an excuse.
