# 5.2 — The first night in a new house

## One-line answer

The manifests describe a Pod that would run; the distance between that and a deployment a team can
operate is nine things, and the first two are a namespace and a rollback path, both of which are
five minutes and neither of which is interesting until the night you need them.

## The story

The first night in a new house.

The move went well. The furniture is in, the beds are made, the kettle is on the counter. Everybody
is pleased.

Then it gets dark and you find out which light switch is which. There is no curtain rod in the
bedroom. The geyser needs twenty minutes and nobody knew, so the first bath is cold. The bin goes out
on a day you have not learned yet. None of this is a problem with the house — the house is fine, and
every one of these was five minutes of work that nobody thought to do while the sun was up.

The list is short, it is boring, and it is entirely made of things you only discover by living there.

## The idea in plain language

What the lab has is a Pod description that is correct on nine properties and a topology decision with
its reasons written down. That is more than most first deployments have. Here is what stands between
it and something a team can operate, in the order it should be done.

**1. A Namespace, and everything in it.** Every object in this lab is namespace-less, so it would
land in `default` alongside whatever else is there. A `Namespace` object plus `namespace: sutra` on
each manifest is ten lines, and it is what makes *"delete everything Sutra owns"* a single safe
command rather than a careful one.

**2. A rollback path.** `kubectl rollout undo deployment/sutra-api` works, and it works because the
image tag is pinned (part [3.3](../03-what-the-manifest-must-say/3.3-the-usual.md)) — a `latest` tag
would roll back to the same moving target. The thing to add is not a command but a **line in the
README** saying which command and what it does, because nobody reads a manifest at the moment they
need this.

**3. The Secret creation command, committed; the Secret, not.** Part
[3.2](../03-what-the-manifest-must-say/3.2-the-pin-on-the-back-of-the-card.md) put a `secretKeyRef`
in the manifest and left the other half open. The command — `kubectl create secret generic
sutra-secrets --from-env-file=.env` — belongs in the README, and the rotation caveat belongs with
it: changing the Secret does not restart anything.

**4. A `readinessProbe` that means what it says.** The agent's probe hits `/readyz`; part
[4.2](../04-the-order-nobody-promised/4.2-redial.md) established that a socket answering is not the
same as tools being loaded. `/readyz` returning 200 must mean *the MCP session is established and
the tools are listed*, and that is a change in Sutra's own code, not in the manifest.

**5. A `NetworkPolicy`, even though the sidecar does not need one.** Part
[2.2](../02-the-sidecar-decision/2.2-the-address-is-the-boundary.md) showed the sidecar has no
cluster-visible address, which is why this is fifth rather than first. It is on the list because a
default-deny policy for the namespace is what makes the *next* service's exposure a decision rather
than an accident.

**6. Resource numbers from measurement.** The requests and limits in the manifest are estimates. Part
[3.4](../03-what-the-manifest-must-say/3.4-the-whistle-and-the-limit.md) is why they must exist;
nothing yet says they are right. This needs a running Pod and is therefore blocked on the tooling
part [5.1](5.1-taught-on-dry-land.md) is about.

**7. 🅿️ Parked — an ingress or a port-forward story.** The Service in the split manifest is
`ClusterIP`, so nothing outside the cluster can reach the agent at all. On a local cluster the answer
is `kubectl port-forward` and it is one README line; a real answer needs an Ingress and a
certificate, and Day 85 established the API has no authentication yet, so exposing it is not
something to do quickly.

**8. 🅿️ Parked — `adk deploy gke`.** ADK ships a command that containerises, pushes, generates
manifests and applies them. It needs a project with billing, which Addendum 02 forbids. It goes in
the README with *"never run — no billing account"*, the same discipline Day 87 used for Agent Engine.

**9. 🅿️ Parked — the split topology and its policy.** Part
[2.3](../02-the-sidecar-decision/2.3-what-the-sidecar-costs.md) wrote the expiry condition: split
when a second consumer needs the archive. The manifests for it already exist in the lab, which means
the work when that day comes is the NetworkPolicy and the migration, not the design.

## Why Sutra needs it

Because Phase 14 opens with A2A — other agents talking to Sutra — and items 1, 5 and 7 are all
prerequisites for that conversation being safe rather than merely possible. A namespace-less
deployment with no network policy and no ingress story is not a thing you add external callers to.

And because items 1 to 4 are under an hour between them and are the difference between a deployment
that exists and one somebody else can operate. Item 6 is blocked on tooling; items 7 to 9 are
genuinely later.

## The mechanism

The list with what each costs and what it unblocks, so it can be argued with:

| # | Item | Where it lands | Roughly | Blocked on |
| --- | --- | --- | --- | --- |
| 1 | Namespace object and `namespace:` on each manifest | `deploy/k8s/` | ten lines | nothing |
| 2 | rollback line in the README | `deploy/k8s/README.md` | one line | nothing |
| 3 | Secret creation command + rotation caveat | `deploy/k8s/README.md` | two lines | nothing |
| 4 | `/readyz` means tools are loaded | `sutra/` | half a day | nothing |
| 5 | default-deny NetworkPolicy | `deploy/k8s/` | fifteen lines | a cluster to test it on |
| 6 | resource numbers from measurement | `deploy/k8s/` | one session | the tooling (part [5.1](5.1-taught-on-dry-land.md)) |
| 7 | 🅿️ ingress or port-forward story | `deploy/k8s/README.md` | — | Day 85's missing authentication |
| 8 | 🅿️ `adk deploy gke` walkthrough | `deploy/k8s/README.md` | — | a billing account, so never |
| 9 | 🅿️ the split topology and its policy | already drafted in `lab/k8s/` | — | a second consumer |

**Items 1, 2 and 3 are about twenty minutes together**, and they are the three that turn the
manifests from a description into something a second person can run and undo. Item 4 is the one that
makes the probes honest.

Item 1's whole implementation, since it is the one everything else assumes:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: sutra
  labels:
    app: sutra
```

Five lines, plus `namespace: sutra` under `metadata` on every other object. What it buys is that
`kubectl delete namespace sutra` is complete and safe, that a label selector cannot accidentally
match another team's Pods, and that the split manifest's DNS name —
`sutra-mcp.sutra.svc.cluster.local`, which part
[2.1](../02-the-sidecar-decision/2.1-one-pod-or-two.md) already writes — is actually correct rather
than aspirational.

## When it breaks

The list breaks by being read as polish. The composite failure is short and every step of it is
somebody being reasonable:

```text
1. the manifests are correct and get applied to the default namespace
2. a second project is deployed to the same cluster, also to default
3. a label selector on `app: sutra` is fine; one on `component: api` is not
4. somebody cleans up with `kubectl delete deployment --all`
5. both projects go
6. there is no rollback line, so the recovery is improvised at the worst moment
```

Step 3 is the one that is genuinely surprising: labels are cluster-wide within a namespace, and
`component: api` is a name two teams will independently choose. That is not a hypothetical — it is
the paper's own argument arriving as a hazard, and [papers/01](../../papers/01-labels-over-hierarchies.md)
is where the trade is set out.

There is no error text anywhere in that sequence.

## In production

**What a professional does.** Does items 1 to 3 before the first apply, not after — they are cheap
only while nothing is running, and every one of them is a thing whose absence is discovered during an
incident. Then measures item 6 in the first week, while the traffic is small enough that being wrong
is survivable.

**What degrades at scale.** Item 5. A default-deny NetworkPolicy in a namespace with three workloads
is fifteen lines; in a namespace with thirty it is a full-time negotiation about who may call whom,
and retrofitting it into a running system means discovering the call graph by breaking it. Everybody
who has done this once does it on day one the next time.

**The failure that only shows with real traffic.** Item 4. A `readinessProbe` that checks the wrong
thing does not fail — it passes, early, and the Pod is added to the Service before it can serve. The
symptom is a burst of errors on every deploy, proportional to how many Pods rolled, attributed to
"deploys are flaky" for months. This is the single most valuable item on the list and it is the only
one that is a code change rather than a YAML change.

**The review comment a senior engineer leaves:** *"Namespace, rollback line, secret command — do
those three before this goes anywhere. And put `/readyz` on the sprint: a probe that lies is worse
than no probe, because it makes the Service route to a Pod that cannot answer."*

**The interview question:** *"What would you add before calling a Kubernetes deployment
production-ready?"* The answer that shows experience starts with the boring operational items —
namespace, rollback, secret handling — rather than with autoscaling or service meshes, because the
first three are what a person needs at two in the morning and the rest are what a system needs at
scale.
