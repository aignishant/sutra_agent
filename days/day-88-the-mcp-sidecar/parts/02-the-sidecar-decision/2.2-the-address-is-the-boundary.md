# 2.2 — The address is the boundary

## One-line answer

A thing with no address cannot be called by anything that does not already share its network
namespace, so putting the MCP server in the agent's Pod enforces the data boundary by topology
rather than by policy — and the same fact, read the other way, means the agent has unauthenticated
access to it and always will.

## The story

The unlisted number.

Two ways to keep the wrong people from ringing you. One is to be in the directory and refuse the
calls you do not want: you need a rule about who is allowed, you need to apply it every time, and
the rule is only as good as the last person who updated it.

The other is not to be in the directory at all. Nobody has to be refused, because nobody can look
you up. Only the people you gave the number to can ring, and you gave it to exactly one person.

The second is stronger and narrower. It is stronger because there is no list to get wrong. It is
narrower because the day a second person genuinely needs to reach you, there is no mechanism at all
— you have to change what kind of thing you are.

## The idea in plain language

Principle 13 says every new power arrives with its containment story. A cluster is a new power: it
can run things, restart things, and let things find each other. The containment story for the MCP
server is the shortest one available.

**In the sidecar topology there is no Service selecting the MCP container.** A Service is the only
way a Pod gets a name and an IP that other Pods can use. No Service means no DNS record, no cluster
IP, and nothing for another Pod to connect to. `address.py` derives that from the manifest rather
than asserting it:

```text
  who can reach the archive server:
    nothing except the container sharing its network namespace
    there is no Service, no DNS name and no NetworkPolicy to get right
```

That last clause is the point. In the split topology, keeping other Pods away from the archive
server is a **NetworkPolicy** — a document listing which Pods may talk to which, applied to the
cluster, correct only while somebody maintains it. In the sidecar topology it is not a document at
all. There is nothing to get right.

This is the strongest version of a rule the security phase kept arriving at: **a capability that
does not exist cannot be misconfigured.** Day 40 filtered which tools the agent could see. Day 68
gave each tool the least privilege it needed. Both are policies that live inside Sutra's own process
and are enforced by Sutra's own code. The Pod boundary is enforced by the kernel and by the absence
of a record in a name server.

And now the other direction, which is the part people skip.

**The agent has unauthenticated access to the MCP server, permanently.** They share `127.0.0.1`.
There is no credential between them, no mutual TLS, no token — the connection is trusted because of
where it comes from, and "where it comes from" is a namespace both containers are inside. Anything
running in the agent container can call any port the sidecar listens on. If the agent executes
untrusted code — and Day 71 built a computer-use sandbox precisely because that is a real
possibility — then the sidecar's ports are inside the blast radius with nothing in between.

So the honest statement of the trade is two sentences, not one: the sidecar removes the MCP server
from the cluster's reach entirely, and it places it entirely inside the agent's reach.

## Why Sutra needs it

Because the archive is the thing worth protecting. Day 32 made the MCP server the data boundary;
Day 69 established that the data behind it includes personal information that must not leave. A
topology that gives that server a cluster-wide address is a topology in which every future Pod in
the namespace is a thing that has to be kept away from it.

And because Phase 14 makes this repository public, and one of the things a reader will judge is
whether the deployment's security properties were chosen or inherited. A manifest with no Service is
a design decision if the reasoning is written down and an accident if it is not.

## The mechanism

The claim "nothing else can reach it" is derived from the manifest, not asserted in prose:

```python
    exposing = [
        s["metadata"]["name"]
        for s in svcs
        if s.get("spec", {}).get("selector", {}).get("component") == "mcp"
    ]
```

**Line by line:**

- The question asked is *"is there a Service whose selector matches the MCP Pod's labels"*, because
  that — and only that — is what gives a Pod a cluster address. Looking for a Service *named*
  `sutra-mcp` would be a name check; looking at the selector is the actual mechanism.
- `component == "mcp"` reads the label the manifests use for the role. Labels are the join between
  every object in Kubernetes, which is the paper's whole argument and part
  [papers/01](../../papers/01-labels-over-hierarchies.md) is where it is made.
- Chained `.get(..., {})` calls rather than direct indexing, because a Service with no `spec` or no
  `selector` is legal — a Service can select nothing and be managed by hand — and the checker must
  report on it rather than crash on it.
- The result is a list, not a boolean. The report names which Service exposes the server, because
  "something exposes it" is not actionable and "Service/sutra-mcp exposes it" is.

Both answers, measured:

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python address.py | tail -5; echo "exit: ${PIPESTATUS[0]}"
uv run python address.py --split | tail -5; echo "exit: ${PIPESTATUS[0]}"
```

**Line by line:**

- `${PIPESTATUS[0]}` rather than `$?`, because `$?` after a pipe is `tail`'s status and `tail`
  always succeeds. The script's own code is the one that carries the finding.

Measured on 2026-09-07:

```text
  who can reach the archive server:
    nothing except the container sharing its network namespace
    there is no Service, no DNS name and no NetworkPolicy to get right

  the data boundary is the Pod boundary
exit: 0

  who can reach the archive server:
    every Pod in the cluster that can resolve sutra-mcp.sutra.svc.cluster.local
    Service/sutra-mcp is a ClusterIP, so the default is the whole cluster

  the archive server now has an address, and an address needs a policy
exit: 1
```

**`ClusterIP` is the default Service type, and the default reach is the whole cluster.** Not the
namespace — Kubernetes networking is flat by default, and a Pod in any namespace can resolve and
connect to a Service in any other unless something stops it. That "unless" is a NetworkPolicy, and
in a cluster with no NetworkPolicies at all, the default is *everything can reach everything*.

## When it breaks

Three ways, in increasing order of how much they cost.

**A NetworkPolicy that was never written.** The split topology is chosen, a Service appears, and the
policy is a ticket. There is no error and no symptom: the archive server works, the agent works, and
the only difference is that every Pod in the cluster could read the archive if it asked. This is the
one `address.py` exits `1` about.

**A NetworkPolicy that is written and does nothing.** NetworkPolicies are enforced by the cluster's
network plugin, and a cluster whose plugin does not implement them accepts the object, stores it,
and ignores it. `kubectl get networkpolicy` shows it. Nothing shows that it is inert. The check is
a connectivity test from a Pod that should be denied, and it is a test almost nobody writes.

**The direction nobody checks.** The sidecar's ports are open to the agent container with no
authentication, forever. There is no error text for this because it is the design working. The
mitigation is not network-level — it cannot be, they share the namespace — it is that the MCP server
authorises each call on its own merits: Day 40's allowlist and Day 68's least privilege are doing
this job, and the Pod boundary does not replace them.

That last point is worth stating as a rule, because the sidecar's strength makes it easy to forget:
**topology removes reachability, not authority.** Everything that could already call the MCP server
still can, with everything it could already do.

## In production

**What a professional does.** Chooses the topology for the security property, writes the property
down, and then still authorises inside the server — because topology is a coarse control that
changes when somebody edits a manifest, and authorisation is a fine control that lives with the
thing being protected. Defence in depth here is not paranoia; it is that the two controls fail in
completely different circumstances.

**What degrades at scale.** The number of things that need an address. A cluster starts with clear
boundaries and accumulates consumers: a metrics scraper needs to reach the sidecar, then a debugging
tool, then a batch job. Each is a small reasonable request and each one, granted, converts the
unlisted number into a listed one. The discipline is to notice that the *first* such request is the
architectural decision, not the third.

**The failure that only shows with real traffic.** A shared cluster. The sidecar's guarantee is
about the cluster network, and it holds regardless of who else is in the cluster. The split
topology's guarantee is about a NetworkPolicy, and it holds only while every team's manifests are
correct. On a laptop with one namespace the two look identical; on a shared cluster with forty teams
they are not remotely the same claim.

**The review comment a senior engineer leaves:** *"Good — no Service means nothing to get wrong. Now
write the other half in the same comment: the agent can reach every port that sidecar opens, with no
credential, so the tool allowlist is still load-bearing and nobody should think this replaced it."*

**The interview question:** *"How do you stop other services in the cluster reaching your data
layer?"* The answer that shows experience offers the topology answer first — do not give it an
address — and then immediately concedes the limit: it only works while the thing has exactly one
consumer, and the day it has two you are back to policy.

## Check yourself

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python address.py --split | tail -5
```

That output names a DNS name and a Service. Write the NetworkPolicy that would answer it — you do
not need to apply it, and you cannot here. Say which Pods it must allow and how you would test that
it is actually being enforced rather than merely accepted.

Now argue the other side out loud: name one thing the sidecar topology makes *worse* for security,
and say which two earlier days are the controls that still have to do that job.

**Out loud, without scrolling up:** why is "no address" a stronger control than "an address and a
policy", and what is the exact condition under which it stops being available to you?
