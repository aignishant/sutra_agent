# 2.3 — What the sidecar costs

## One-line answer

A sidecar cannot be scaled, restarted, upgraded or reached independently of the container it rides
with, and every one of those is the same fact — shared lifecycle — which is worth paying for
exactly while the two things genuinely have one lifecycle, and is a trap the moment they do not.

## The story

Two of you in one auto-rickshaw, one fare.

It is cheaper and it is simpler. One negotiation at the start, one payment at the end, no
coordinating about where to meet. For a journey where you are both going to the same place at the
same time, there is no argument for two autos.

The cost shows up on the way back, when one of you needs to stop at the market and the other needs
to be home. Now the arrangement that made the outward trip easy is the thing you are working around:
somebody waits, or somebody pays twice, or one of you does not do the thing they needed to do.

The single fare was never the point. The single *destination* was, and it stopped being true.

## The idea in plain language

The sidecar's benefits and its costs are the same sentence read twice. Shared lifecycle is why the
address is loopback, why there is nothing to expose, and why an upgrade is one atomic document. It
is also every limitation.

**It scales one-for-one and there is no dial.** Four agent Pods means four MCP servers. Not because
four are needed — because `replicas` counts Pods and the sidecar is inside the Pod. There is no
field that says *three of these and one of those*.

**It restarts with its neighbour.** A crash-looping sidecar takes the Pod's readiness with it, so
the agent is removed from service because the archive server is unwell. Sometimes correct. Sometimes
the archive server is optional for most requests and the agent could have served them.

**It upgrades with its neighbour.** One document, one rollout. That is genuinely an advantage —
there is no window in which a new agent talks to an old MCP server — and it is also a constraint: a
one-line fix to the MCP server means rolling the agent.

**It cannot be reached by a second consumer at all.** Part
[2.2](2.2-the-address-is-the-boundary.md) called this the strongest available control. It is also an
absolute ceiling: the second consumer is not hard, it is impossible, until the topology changes.

So the decision needs an **expiry condition** — a sentence describing the observation that would
make it wrong — written where somebody will find it. Sutra's is: *"when a second thing needs the
archive."* Not *"at scale"*, which nobody can notice, and not *"if it becomes a problem"*, which is
a description of already having the problem.

## Why Sutra needs it

Because a decision without its expiry date gets copied. This manifest will be read by somebody
adding a second agent in Phase 14 or Phase 15, and what they will find is a working pattern with no
indication of its assumptions. The comment in the file is the difference between them making a
decision and them following a precedent.

And because the ratio is about to matter. Phase 14 adds A2A, which means other agents talking to
Sutra — and the first question an agent-to-agent architecture asks is which of your internal
services are addressable. The answer today is *none*, deliberately, and that answer will be
challenged within a phase.

## The mechanism

The split manifest is the alternative, written out, so the trade is a diff rather than an argument.
The parts that only exist because the containers separated:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: sutra-mcp
  namespace: sutra
spec:
  type: ClusterIP
  selector:
    app: sutra
    component: mcp
  ports:
    - port: 8000
      targetPort: 8000
```

Twelve lines of new object, and with them: a name in DNS, an IP, a set of endpoints maintained by
another control loop, and a thing to write a NetworkPolicy about. The agent's own configuration
changes by one line, from `http://127.0.0.1:8000/mcp` to
`http://sutra-mcp.sutra.svc.cluster.local:8000/mcp` — and that one line is the visible tip of all of
it.

What the split *buys*, and it is not nothing:

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python address.py --split | sed -n '2,7p'
```

**Line by line:**

- `sed -n '2,7p'` prints the object inventory and the Pod grouping, which is where the independence
  is visible.

Measured on 2026-09-07:

```text
  Deployments: ['sutra-api', 'sutra-mcp']
  Services:    ['sutra-mcp']

  Pod from sutra-api  holds [('sutra-api', 'app')]
  Pod from sutra-mcp  holds [('sutra-mcp', 'app')]
```

**Two Deployments means two `replicas` fields.** The agent can run at four and the archive server at
one. They roll independently, they fail independently, and a second consumer is a configuration
change rather than a redesign. Every one of those is a real benefit and every one of them is
purchased with the Service that part [2.2](2.2-the-address-is-the-boundary.md) exits `1` about.

## When it breaks

The sidecar breaks by outliving its assumption, and the failure is not a crash — it is a growing bill
and a growing awkwardness that nobody attributes to a decision made months earlier.

The sequence, and every step is somebody being sensible:

```text
1. one agent Pod, one sidecar. Correct, cheap, nothing exposed.
2. traffic grows; replicas goes to four. Four archive servers now run.
3. each opens its own connections to the archive and keeps its own cache.
4. the archive sees four times the connections it was sized for.
5. somebody proposes a shared cache. There is no address to put it behind.
6. a Service is added to the sidecar Pod, which now exposes a thing that scales with the agent.
7. the topology is now the worst of both: exposed, and still not independently scalable.
```

Step 6 is the mistake, and it is made because step 5 has no other move. There is no error text
anywhere in that list.

The honest counterweight is that **the sidecar is right at step 1 and stays right for a long time.**
The failure above is not an argument for splitting today; it is an argument for writing the expiry
condition today, so that step 5 is recognised as the moment to split rather than as a plumbing
problem.

There is one failure with a real error, and it belongs here because it is the shared-lifecycle cost
at its sharpest: a sidecar whose liveness probe fails restarts, and while it is restarting the agent
is in a Pod that is not ready. The agent is fine. It is not serving. Whether that is correct depends
entirely on whether the agent can do anything useful without the archive, and that is a question the
manifest cannot answer for you.

## In production

**What a professional does.** Writes the trade in the manifest, next to the thing it explains, in
the form *decision, reason, expiry*. Three lines. The reason it goes in the manifest rather than in
a design document is that the manifest is what gets read at the moment somebody is about to change
it.

**What degrades at scale.** Resource multiplication. The sidecar's `resources.requests` are added to
every Pod, so a 192Mi sidecar on forty Pods is nearly eight gigabytes reserved for a service that
would have fitted in one Pod. This is the single most common reason a sidecar gets split, and it
shows up as a cluster capacity conversation rather than as an architecture one.

**The failure that only shows with real traffic.** Connection multiplication against a downstream
that counts connections. Four sidecars are four connection pools; forty are forty, and the thing at
the far end has a limit. A database or an upstream API that was comfortable at one Pod starts
refusing at scale, and the symptom appears in the agent while the cause is a topology decision two
layers away.

**The review comment a senior engineer leaves:** *"Fine. Put the expiry in the file: 'split this when
a second consumer needs the archive, or when replicas goes above four.' Both are things somebody can
observe. 'When it becomes a problem' is not."*

**The interview question:** *"What is the downside of the sidecar pattern?"* The answer that shows
experience gives one root cause rather than a list: everything a sidecar cannot do independently
follows from sharing a lifecycle, and the interesting engineering question is not the list but the
condition under which shared lifecycle stops being true.

## Check yourself

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python address.py --split | sed -n '2,7p'
grep -c "replicas" k8s/deployment.yaml k8s/deployment-split.yaml
```

The second command counts `replicas` fields in each topology. Say what that count means for the
question *"can I run four agents and one archive server?"*

Now write the three-line expiry comment for `k8s/deployment.yaml` yourself — decision, reason,
condition — using conditions somebody could actually observe. Compare against the resource
multiplication number in **In production** and say whether you would add a second condition.

it, and name the observation that would tell you it is no longer true for Sutra.
