# 2.1 — One Pod or two

## One-line answer

The agent and its MCP server can go in one Pod or in two, and the manifest does not merely record
that choice — it determines the address, the failure mode, the scaling ratio and the upgrade unit,
all four of which fall out of the single fact that one Pod means one network namespace.

## The story

The shop and the workshop behind it.

A tailor's shop on the main road, and a workroom behind it with a door between them. When a customer
wants a hem taken up, the man at the counter walks through the door, hands the garment over, and
comes back. There is no phone call, no docket, and nobody outside knows the workroom exists — from
the road it is one shop.

The alternative, and plenty of shops do it this way, is a workroom two streets away. Now there is a
phone number, a boy on a cycle, and a note pinned to each garment. It also means the workroom can
take work from three shops instead of one, and can stay open when the front shop shuts.

Neither is the right answer in general. They are different businesses, and the difference is not the
sewing.

## The idea in plain language

Sutra has two processes: the agent, which answers requests, and `sutra-mcp`, which is the boundary
between the agent and the archive. Day 32 argued that the MCP server *is* the data boundary. Today
that argument becomes a topology.

**One Pod — the sidecar.** `sutra-mcp` is a second container inside the agent's Pod. They share a
network namespace, so the agent dials `http://127.0.0.1:8000/mcp`. There is no Service, no DNS name,
and nothing in the cluster can reach the MCP server at all.

**Two Pods — separate Deployments.** Each gets its own Pod and its own lifecycle. The MCP server now
needs an address, which means a Service, which means the agent dials
`http://sutra-mcp.sutra.svc.cluster.local:8000/mcp` — and so can anything else in the cluster.

The comparison, with the reason next to each row rather than the row alone:

| | Sidecar (one Pod) | Separate Deployments |
| --- | --- | --- |
| Address the agent uses | `http://127.0.0.1:8000/mcp` | `http://sutra-mcp.sutra.svc.cluster.local:8000/mcp` |
| Reachable from the rest of the cluster | **no** — there is no address to reach | yes, by every Pod that can resolve the name |
| Scaling | always one-for-one with the agent | independent |
| Failure | one container dies, the Pod restarts | independent; the caller needs retries |
| Upgrade | atomic, one document | two lifecycles that must stay compatible |
| Startup order | the kubelet can be made to wait | nothing waits for anything |

Sutra takes the **sidecar**, and for the second row rather than the first. Part
[2.2](2.2-the-address-is-the-boundary.md) is that argument in full.

## Why Sutra needs it

Because the choice is being made either way. A manifest that puts both containers under `containers:`
has chosen the sidecar without choosing it, and a manifest that splits them has taken on a Service
and a retry policy without noticing. Writing the topology down is what turns a default into a
decision.

And because this is the first day where the MCP boundary has a *shape* rather than a rule. Day 40
filtered which tools the agent could call. Day 68 gave the tools least privilege. Both of those are
policies inside the process. The Pod boundary is the first one that is enforced by something other
than Sutra's own code.

## The mechanism

The manifest decides the address, and the address can be derived from the manifest rather than
asserted. That is what `address.py` does:

```python
    api_dep = next(d for d in deps if d["metadata"]["name"] == "sutra-api")
    api = next(c for c in containers(api_dep) if c.name == "sutra-api")
    url = env_of(api)["SUTRA_MCP_URL"]["value"]
    loopback = "127.0.0.1" in url
```

**Line by line:**

- The address is read from the *agent's environment*, not from the MCP container's ports, because
  the question is what the agent will dial. A container can listen on a port nobody calls.
- `env_of(api)["SUTRA_MCP_URL"]["value"]` reaches for `value` specifically. An environment variable
  in Kubernetes arrives either as a literal `value` or as a `valueFrom` reference, and only the
  first is readable from the document — which is the whole subject of part
  [3.2](../03-what-the-manifest-must-say/3.2-the-pin-on-the-back-of-the-card.md), from the other
  direction.
- `"127.0.0.1" in url` is deliberately a substring test rather than a URL parse. The question is not
  *is this a valid URL* but *is this address inside the Pod*, and loopback is the only address that
  is.
- `next(...)` with a generator raises `StopIteration` if the container is missing rather than
  returning `None` and failing three lines later with an unhelpful `TypeError`. A manifest with no
  `sutra-api` container is a broken manifest and should say so where it is noticed.

Run both topologies:

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python address.py; echo "exit: $?"
```

**Line by line:**

- No flag: the sidecar manifest, which is the one this day chooses.

Measured on 2026-09-07:

```text
manifest: k8s/deployment.yaml
  Deployments: ['sutra-api']
  Services:    none

  Pod from sutra-api  holds [('sutra-api', 'app'), ('sutra-mcp', 'sidecar')]

  the agent dials: http://127.0.0.1:8000/mcp
  that is the Pod it is already in

  who can reach the archive server:
    nothing except the container sharing its network namespace
    there is no Service, no DNS name and no NetworkPolicy to get right

  the data boundary is the Pod boundary
exit: 0
```

And the alternative:

```bash
uv run python address.py --split; echo "exit: $?"
```

**Line by line:**

- Same script, same checks, a different document. The exit code changes because the answer changes,
  not because the code did.

Measured on 2026-09-07:

```text
manifest: k8s/deployment-split.yaml
  Deployments: ['sutra-api', 'sutra-mcp']
  Services:    ['sutra-mcp']

  Pod from sutra-api  holds [('sutra-api', 'app')]
  Pod from sutra-mcp  holds [('sutra-mcp', 'app')]

  the agent dials: http://sutra-mcp.sutra.svc.cluster.local:8000/mcp
  that is a name the cluster resolves

  who can reach the archive server:
    every Pod in the cluster that can resolve sutra-mcp.sutra.svc.cluster.local
    Service/sutra-mcp is a ClusterIP, so the default is the whole cluster
```

**Exit `1` on the split topology, and it is not a bug report.** The exit code means *the archive
server has a cluster-visible address*, which is a finding that has to be answered with a
NetworkPolicy rather than a mistake to fix. Part [2.3](2.3-what-the-sidecar-costs.md) is the case
for taking that trade anyway, at a scale Sutra has not reached.

## When it breaks

The decision breaks by being made twice, in two places, differently.

The manifest says the containers are in one Pod. The agent's configuration says which URL to dial.
Nothing connects those two facts except a person, and that is exactly the gap the first check
closes:

```python
def check_one_pod(dep: dict, cs: list[Container]) -> str | None:
    """1 - the agent and the MCP server are in one Pod, so the address is loopback."""
    names = {c.name for c in cs}
    if not {"sutra-api", "sutra-mcp"} <= names:
        return f"both containers must be in this Pod; found {sorted(names)}"
    url = env_of(next(c for c in cs if c.name == "sutra-api")).get("SUTRA_MCP_URL", {})
    if "127.0.0.1" not in url.get("value", ""):
        return f"one Pod, but the agent dials {url.get('value')!r} instead of loopback"
    return None
```

**Line by line:**

- Two separate failures with two separate messages. *"They are not in one Pod"* and *"they are in
  one Pod and the agent dials elsewhere"* are different mistakes with different fixes, and one
  message for both would send somebody to the wrong file.
- `{"sutra-api", "sutra-mcp"} <= names` is a subset test, so a Pod that grows a third container
  still passes. The check is about these two being together, not about nothing else being there.
- `.get("SUTRA_MCP_URL", {})` then `.get("value", "")` — two defaults, because there are two ways
  for the address to be absent: no such variable at all, or a variable that arrives by reference. A
  `KeyError` here would be a crash in the checker rather than a finding about the manifest.
- The failure message quotes the URL with `!r`, so a trailing space or a smart quote is visible
  rather than invisible.

The failure with no error text is the one that survives a refactor: somebody splits the Deployments
for a good reason and leaves the agent dialling `127.0.0.1`. The Pod comes up, the agent starts, and
every MCP call is refused — which looks exactly like part
[4.1](../04-the-order-nobody-promised/4.1-the-clinic-was-not-open-yet.md)'s startup race and is a
completely different problem.

## In production

**What a professional does.** Writes the topology decision and its expiry condition in the manifest,
in a comment, next to the thing it explains. The decision is cheap to make and expensive to revisit
blind, and in six months the only artefact anybody will read is the file.

**What degrades at scale.** The sidecar. One archive server per agent Pod is fine at one Pod and
absurd at forty — you are running forty copies of a thing that exists to guard one archive, each
with its own connection pool and its own cache. The number at which that flips is not a rule of
thumb; it is the point where the MCP server's work stops being proportional to the agent's requests.

**The failure that only shows with real traffic.** A second consumer. The moment a second agent — or
a batch job, or a dashboard — needs the archive, the sidecar topology has no answer: there is no
address to give them. The pressure is then to add a Service to the sidecar Pod, which is the worst
of both worlds, because it exposes an address that scales with the wrong thing. The honest move at
that point is the split, done deliberately, with the NetworkPolicy written at the same time.

**The review comment a senior engineer leaves:** *"Sidecar is right for now and I want the sentence
that says when it stops being right in the file. 'When a second consumer needs the archive' is a
condition somebody can notice; 'at scale' is not."*

**The interview question:** *"When would you use a sidecar rather than a separate service?"* The
answer that shows experience does not list benefits. It names the three tests — same machine, same
scaling, same upgrade — and then names the cost, which is that a sidecar can never be reached by
anything else, and that this is simultaneously the main benefit.
