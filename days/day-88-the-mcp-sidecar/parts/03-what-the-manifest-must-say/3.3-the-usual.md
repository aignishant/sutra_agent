# 3.3 — "The usual"

## One-line answer

`latest` is not a version, it is a subscription to whatever is newest, so a manifest that names it
describes a different system on Tuesday than it did on Monday — and the companion field,
`imagePullPolicy`, decides whether a mistake about images fails loudly or is quietly papered over
with something from the internet.

## The story

"The usual" at the tea stall.

You have been going for two years and you no longer order. You say *the usual* and a glass arrives,
and it is right, and this is one of the small pleasures of a routine.

Then the boy who makes it changes. The new one asks the old one what your usual is, gets a rough
answer, and makes something close. It is still tea. It is slightly sweeter. Nobody told you, because
from the stall's point of view nothing happened: you asked for the usual and you got the usual.

The word never changed. What it pointed at did.

## The idea in plain language

An image reference has two halves: a repository and a tag. `sutra-api:0.1.0` names a repository and
a tag; `sutra-api:latest` names a repository and a tag that happens to be spelled `latest`.

`latest` has no special meaning to the container runtime. It is an ordinary tag with a convention
attached — that whoever publishes the image moves it to point at the newest build. Which means:

- The same manifest, applied twice, can run two different builds.
- A Pod that restarts can come back on a different image than its neighbour that did not.
- A rollback has nothing to roll back to, because the tag does not record what was running.
- The only record of what was actually deployed is the image *digest*, which nobody wrote down.

A **pinned tag** — `0.1.0`, or better a digest — removes all four. The manifest names one image
forever, the diff shows when it changed, and rolling back is editing one line to the previous value.

The second field is the one that catches people on a local cluster, and it is worth understanding as
a pair with the first.

**`imagePullPolicy`** tells the node when to fetch. The default is `Always` when the tag is `latest`
and `IfNotPresent` otherwise. Sutra sets it to **`Never`**, and that is a deliberate choice for a
local cluster where images are loaded into the node by hand rather than pulled from a registry.

The reason is worth its own sentence, because it is a general principle wearing a Kubernetes hat.
With `Never`, an image the node does not have produces `ErrImageNeverPull` immediately: unmistakable,
and the fix is *load the image*. With `IfNotPresent` or `Always`, the node — finding nothing locally
— does the reasonable thing and asks a public registry for something called `sutra-api`. What comes
back is either a confusing `ImagePullBackOff` about credentials for a repository you do not own, or,
much worse, somebody else's image with that name. **Prefer the error that cannot be mistaken for
success.**

## Why Sutra needs it

Because OPS-18 says the deploy artifact is reproducible from a cold start, and a manifest naming
`latest` is not reproducible by construction — two people following the same README on the same day
can end up running different code.

And because Sutra's images are built locally and loaded into the node by hand. There is no registry
in this story at all, so any pull policy that permits a fetch is permitting a fetch from a place
Sutra has never published to.

## The mechanism

Two checks, four lines between them:

```python
def check_pinned(dep: dict, cs: list[Container]) -> str | None:
    """6 - an image tag names one image forever, or it names whatever is newest."""
    bad = [c.name for c in cs if c.tag in ("", "latest")]
    return f"unpinned image tag on {bad}" if bad else None


def check_pull_policy(dep: dict, cs: list[Container]) -> str | None:
    """7 - a locally loaded image must fail loudly rather than be fetched from anywhere."""
    bad = [c.name for c in cs if c.spec.get("imagePullPolicy") != "Never"]
    return f"imagePullPolicy is not Never on {bad}" if bad else None
```

**Line by line:**

- `c.tag in ("", "latest")` catches both failures with one test. The empty string is what
  `Container.tag` returns for an image with no tag at all — `image: sutra-api` — which is *the same
  bug*: an untagged reference means `latest` to every container runtime, silently.
- Both checks collect names into a list rather than returning at the first offender, because a
  manifest with two unpinned images has two lines to fix and naming one of them sends somebody back
  twice.
- `.get("imagePullPolicy")` with no default, compared against `"Never"`. An absent field is not
  `Never`, and treating absence as acceptable would let the manifest inherit a default that depends
  on the tag — which is exactly the coupling this pair of checks exists to remove.
- The two checks are separate functions rather than one, even though they are always wrong together
  in practice, because they have different fixes: one is a version decision and one is a
  registry-topology decision.

Here is how the tag is extracted, which is the fiddly part:

```python
    @property
    def tag(self) -> str:
        _repo, _, tag = self.image.rpartition(":")
        return tag if _repo else ""
```

**Line by line:**

- `rpartition`, not `split(":")`. A real image reference can contain a colon in the registry host —
  `registry.example.com:5000/sutra-api:0.1.0` — and splitting on the first colon returns the port.
  Partitioning from the right takes the tag.
- `return tag if _repo else ""` handles the untagged case. `"sutra-api".rpartition(":")` returns
  `("", "", "sutra-api")`, so an empty left-hand side means there was no colon at all and the thing
  in `tag` is actually the repository name. Without this guard, an untagged image would report its
  own name as its tag and pass the pin check.
- Digest references (`sutra-api@sha256:...`) are not handled here, and that is a real gap: the
  strongest possible pin would be reported as unpinned. It is a `TODO(me)` in the hub rather than a
  silent omission.

Both manifests, measured:

```bash

uv run python check.py --naive | grep -E "image tag|imagePullPolicy"
```

**Line by line:**

- One `grep` for the pair, because these two properties fail together and reading them together is
  the point.

Measured on 2026-09-07:

```text
  FAIL  every image tag pinned
  FAIL  imagePullPolicy: Never
    - every image tag pinned: unpinned image tag on ['sutra-mcp', 'sutra-api']
    - imagePullPolicy: Never: imagePullPolicy is not Never on ['sutra-mcp', 'sutra-api']
```

**Both containers, both properties.** And note what the naive manifest actually says: `image:
sutra-mcp:latest` with no pull policy at all. Because the tag is `latest`, the runtime's default
policy is `Always` — so this Pod would try to pull `sutra-mcp:latest` from a public registry, on
every restart, for an image that has never been published anywhere.

## When it breaks

The failures here are the ones this machine cannot produce, and saying so is part of the lesson.

**`ErrImageNeverPull`** is what the good manifest gives you when the image was not loaded into the
node. It is a Pod status, not an exception, and reproducing it needs a cluster. The exact command
that would produce it is in the hub's build brief; it was **not run here**, because there is no
`kind` and no `docker` on this machine.

**`ImagePullBackOff`** is what the naive manifest gives you. Also a Pod status, also unrunnable here.

Rather than invent either transcript, here is the failure that *is* measurable, and it is the one
that matters more: the checker catching both before anything is applied. That is the argument for
policy checks in the first place — the two statuses above are what the cluster tells you *after* you
have spent the time, and `check.py` tells you in the pull request.

There is one break with no status code at all and it is the worst of the three. `latest` on an image
that *does* exist in a public registry under a name somebody else controls does not error. It runs.
The Pod is healthy, the probes pass, and the thing serving your traffic is not your code. Naming
your images after something generic and leaving the tag at `latest` is how that happens, and
`imagePullPolicy: Never` is the one-line control that makes it impossible on a local cluster.

## In production

**What a professional does.** Pins by digest for anything that matters — `sutra-api@sha256:…` — and
lets the pipeline write the digest into the manifest at build time. A tag is a mutable pointer even
when it is `0.1.0`, because nothing stops a publisher from moving it; a digest is the image.

**What degrades at scale.** Digest churn. Every build produces a new digest, so the manifest changes
on every deploy and the repository fills with one-line commits. That is the cost, it is real, and the
standard answer is that the pipeline owns those commits and humans own everything else in the file.

**The failure that only shows with real traffic.** Partial rollout. Ten Pods on `latest`, a new image
published, and three Pods restart for unrelated reasons. Now three are on the new build and seven on
the old, serving the same traffic, with no field anywhere that says so. Debugging this is
memorable — the same request succeeds and fails depending on which Pod answered — and the cause is a
tag that moved.

**The review comment a senior engineer leaves:** *"Pin it. And if you are keeping `Never` for the
local cluster, put a comment saying the production overlay uses `IfNotPresent` with a digest —
otherwise the first person to deploy this for real will delete the line and not know what it was
protecting."*

**The interview question:** *"What is wrong with `image: myapp:latest`?"* The answer that shows
experience does not stop at reproducibility. It names the rollback problem — the tag does not record
what was running, so there is nothing to roll back *to* — and the partial-rollout problem, which is
the one that costs a night.
