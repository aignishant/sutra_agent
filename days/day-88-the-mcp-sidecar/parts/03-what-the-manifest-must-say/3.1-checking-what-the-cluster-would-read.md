# 3.1 — Checking what the cluster would read

## One-line answer

Nine properties decide whether this manifest is worth applying, every one of them is a thing a
careful reviewer could check by reading, and turning them into a script is what makes them true
every time rather than on the days somebody was paying attention.

## The story

Proofreading the card before five hundred are printed.

Somebody reads it out loud in the front room: the names, the date, the day of the week, the address,
the time. It takes a couple of minutes and it feels slightly silly, because everybody has already
looked at it.

The reason it is done anyway is arithmetic. A mistake caught now costs a correction. The same
mistake caught after printing costs five hundred cards, and after posting it costs five hundred
phone calls. Nothing about the mistake changed; what changed is how many copies of it exist.

Note what is actually being checked. Not whether the design is nice — whether the *facts* are right.
Those are different reviews, and only one of them can be done from a list.

## The idea in plain language

A manifest can be wrong in three different ways, and they need three different tools.

| Wrong how | Caught by | Available here |
| --- | --- | --- |
| not valid YAML | a parser | yes |
| valid YAML, not a valid Kubernetes object | the API server's schema | **no — needs a cluster** |
| a valid object describing something you did not want | a policy check you write | yes |

The third row is the interesting one, and it is the only one that is about *your* system. A
`latest` tag is a perfectly valid Kubernetes object. So is a Pod with no resource limits, a
credential written in plain text, and a sidecar with no startup gate. The API server accepts all
four without comment, which is exactly right — they are legal — and every one of them is a defect.

So `check.py` is nine assertions about the document, chosen because each one is a mistake this
repository would actually make:

| # | Property | Why it is here |
| --- | --- | --- |
| 1 | one Pod, loopback address | the sidecar decision, recorded in the file (part [2.1](../02-the-sidecar-decision/2.1-one-pod-or-two.md)) |
| 2 | sidecar declared as an initContainer | the only way to get an ordering guarantee (part [4.3](../04-the-order-nobody-promised/4.3-what-kubernetes-actually-promises.md)) |
| 3 | every sidecar has a startupProbe | what "started" means (part [4.3](../04-the-order-nobody-promised/4.3-what-kubernetes-actually-promises.md)) |
| 4 | every container has a livenessProbe | a dead container that is not restarted (part [3.4](3.4-the-whistle-and-the-limit.md)) |
| 5 | no credential literals | Principle 9, in the file that goes public (part [3.2](3.2-the-pin-on-the-back-of-the-card.md)) |
| 6 | every image tag pinned | `latest` is not a version (part [3.3](3.3-the-usual.md)) |
| 7 | `imagePullPolicy: Never` | prefer the error that cannot be mistaken for success (part [3.3](3.3-the-usual.md)) |
| 8 | every container has resources.limits | one container should not be able to take the node (part [3.4](3.4-the-whistle-and-the-limit.md)) |
| 9 | runs as a non-root user | Principle 13, at the container boundary (part [3.4](3.4-the-whistle-and-the-limit.md)) |

## Why Sutra needs it

Because OPS-18 is a claim about an artifact, and an artifact you can check is an artifact you can
make a claim about. "The deploy directory is reproducible from a cold start" is not verifiable by
inspection at three in the morning; "nine properties hold" is.

And because this is the entire measurable content of a deployment day on a machine with no
deployment tooling. Part [5.1](../05-what-did-not-run/5.1-taught-on-dry-land.md) is honest about what
that leaves out. What it leaves *in* is every property above, and those are the ones a review would
have caught anyway — which makes them exactly the ones worth automating.

## The mechanism

Each check is a function that returns `None` when the property holds and a sentence when it does
not. The runner is short enough to read in one go:

```python
    for label, check in CHECKS:
        problem = check(dep, cs)
        if isinstance(problem, NotApplicable):
            skipped.append((label, str(problem)))
            mark = "n/a "
        elif problem:
            failures.append((label, problem))
            mark = "FAIL"
        else:
            mark = "ok  "
        print(f"  {mark}  {label}")
```

**Line by line:**

- Three outcomes, not two. `NotApplicable` is a check that had nothing to check, and **When it
  breaks** below is entirely about why that has to be a separate category.
- `problem` is a sentence, not a boolean, so the report can say *what* is wrong. `FAIL  every image
  tag pinned` sends somebody to the right property; `unpinned image tag on ['sutra-mcp',
  'sutra-api']` sends them to the right line.
- Every check runs. There is no early return, because a manifest with two problems should produce
  two findings — stopping at the first is how the second one survives to the next review.
- The mark is padded to four characters so the labels line up, which is not decoration: a column of
  aligned marks is scannable and a ragged one is not.

**One of nine, and the last line is the finding.** Every defect in that list is a legal Kubernetes
object. A cluster handed the naive manifest would accept it, schedule it, and report success.

## When it breaks

The checker's own most interesting bug is in that output, and it was found by running it rather than
by reasoning about it.

Look at the `?` line. *"Every sidecar has a startupProbe"* is **true** of a manifest with no
sidecars in it — vacuously, in the way that every statement about the members of an empty set is
true. The first version of this checker printed `ok` there and counted it towards the passes, which
means the manifest with the *worst* sidecar problem in the lab scored better on the sidecar check
than it deserved.

That is the same defect this repository has now found three times: Day 79's eval case that passed
because it asserted nothing, Day 83's round trip that lost nothing because nothing was written, and
this. The shape is always identical — **a check with no subject reports success** — and it is always
invisible in a run where everything passes.

The fix is a third outcome rather than a cleverer condition:

```python
def check_startup_probe(dep: dict, cs: list[Container]) -> str | None:
    """3 - every sidecar has a startupProbe, which is what "started" means."""
    if not sidecars(cs):
        return NotApplicable("this manifest declares no sidecar, so there is nothing to probe")
    bad = [c.name for c in sidecars(cs) if "startupProbe" not in c.spec]
```

**Line by line:**

- The emptiness test comes **first**, before the property is evaluated at all. Any other order and
  the vacuous truth has already been computed.
- `NotApplicable` subclasses `str`, so it carries its reason and can still be printed like any other
  message — but `isinstance` distinguishes it, which is what lets the runner count it separately.
- It is **not** a pass. The run exits `1` when anything is `n/a`, because a checker that could not
  evaluate one of its properties has not checked the manifest.

There is no error text for the original bug, and there never could have been. It was a `9 of 9`
that should have been `8 of 9`.

## In production

**What a professional does.** Runs the policy checks in the same pipeline as the tests, on every
change, and keeps them in the repository next to the manifests rather than in a platform team's
cluster-side admission controller — because a check that runs at apply time tells you after the pull
request was approved, and a check that runs in the pipeline tells you in the pull request.

**What degrades at scale.** The list grows and the signal thins. Nine properties over one manifest is
readable; sixty over four hundred manifests produces a wall that people learn to skim. The
countermeasure is to keep failures loud and passes quiet — print the failing properties in full and
the passing ones as a count — and to delete checks that have never fired.

**The failure that only shows with real traffic.** A check that stops matching reality. `component:
mcp` is the label part [2.2](../02-the-sidecar-decision/2.2-the-address-is-the-boundary.md)'s
exposure check keys on; rename
that label in the manifests and the check keeps passing, because a Service selecting a label nobody
uses selects nothing. The check has become vacuous in exactly the way the startupProbe check was, and
this time nothing prints a `?`. The mitigation is the one the whole repository keeps arriving at: a
known-bad fixture that must fail, checked in alongside the known-good one — which is precisely what
`deployment-naive.yaml` is.

**The review comment a senior engineer leaves:** *"Keep the naive manifest in the repository and make
the pipeline assert it fails. A policy checker that has never rejected anything is indistinguishable
from one that cannot."*

**The interview question:** *"How do you keep bad Kubernetes manifests out of production?"* The
answer that shows experience separates the three layers — parser, schema, policy — and says that only
the third is about your system, then names two policy checks by hand. Anybody can say "we use a
linter"; naming *no credential literals* and *pinned image tags* shows you have read a manifest in
anger.

Now break the good manifest on purpose: delete the single line `restartPolicy: Always` from the
sidecar and run `check.py` again. **Two** properties change and they change in different ways —
predict both before you run it, then put the line back. The measured answer is `7 of 9 properties
hold, 1 had nothing to check`, and working out which one went `n/a` rather than `FAIL` is the
exercise.
