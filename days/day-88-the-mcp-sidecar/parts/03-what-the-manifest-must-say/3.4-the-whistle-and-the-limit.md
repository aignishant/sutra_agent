# 3.4 — The whistle and the limit

## One-line answer

Three fields decide whether a Pod is a controlled thing or a hopeful one: a probe so the cluster can
tell working from present, a limit so one container cannot take the machine down with it, and a
non-root user so a container that is compromised did not also inherit the node.

## The story

The cooker and its whistle.

The whistle is not decoration and it is not an alarm about something going wrong. It is the only
signal from inside a sealed vessel that the thing inside it has reached the state you wanted.
Without it, the cooker still works — you simply have no idea when, so you either open it early or
you guess long and overcook.

The safety valve is the other half, and it is a different kind of thing. The whistle tells you what
is happening. The valve makes sure that what happens next is a hiss rather than a ceiling.

Two devices, two jobs. One reports; one bounds. A cooker with a whistle and no valve is an
instrument. A cooker with a valve and no whistle is safe and useless.

## The idea in plain language

**Probes are the whistle.** A container that is running is not necessarily working. Kubernetes asks
it, on a schedule, using one of three probes:

| Probe | The question it asks | What happens on failure |
| --- | --- | --- |
| `startupProbe` | *has it finished starting?* | the other probes do not begin yet; if it never passes, the container is restarted |
| `readinessProbe` | *can it take traffic right now?* | the Pod is removed from Services; nothing is restarted |
| `livenessProbe` | *is it wedged?* | the container is restarted |

The distinction between the last two is the one people collapse, and collapsing it is expensive.
Readiness failing means *stop sending work*; liveness failing means *this is beyond saving, kill it*.
A liveness probe that is really a readiness probe restarts a container that was merely busy, under
load, which is the exact moment restarting makes everything worse.

Sutra's manifest gives the sidecar a `startupProbe` and a `livenessProbe`, and the agent a
`readinessProbe` and a `livenessProbe`. The sidecar has no readiness probe because nothing routes
traffic to it — there is no Service, which is part
[2.2](../02-the-sidecar-decision/2.2-the-address-is-the-boundary.md)'s whole point — so *ready* has
no meaning for it. Its `startupProbe` is doing a completely different job, and section
[4](../04-the-order-nobody-promised/4.3-what-kubernetes-actually-promises.md) is that job.

**Limits are the safety valve.** `resources.requests` is what the scheduler reserves when choosing a
node; `resources.limits` is the ceiling the container is held to. Memory over the limit means the
container is killed — `OOMKilled` — and CPU over the limit means it is throttled rather than killed.
A container with no memory limit can grow until the *node* runs out, at which point the kernel starts
killing processes that had nothing to do with it.

**Non-root is the containment.** `runAsNonRoot: true` on the Pod and `allowPrivilegeEscalation:
false` on each container are the two lines that make a compromised process a compromised process
rather than a foothold. Day 68 argued least privilege for tools; this is the same argument one layer
down, where the subject is the container rather than the function it calls.

## Why Sutra needs it

Because Principle 13 says every new power arrives with its containment story, and running on a
cluster is a new power: Sutra is now a thing that can be scheduled onto a machine shared with other
work. These three fields are the containment story, and all three are absent by default — Kubernetes
will happily run a root container with no limits and no probes and report it healthy.

And because the sidecar makes the probes matter more than they would otherwise. Two containers in
one Pod share a memory limit's consequences: a leaking archive server gets the whole Pod killed, and
the agent — which was fine — goes with it. Bounding each container separately is what keeps that from
being a Pod-wide event.

## The mechanism

Two checks, and the second one is subtler than it looks:

```python
def check_liveness(dep: dict, cs: list[Container]) -> str | None:
    """4 - every long-running container can be found dead."""
    bad = [c.name for c in cs if c.kind != "init" and "livenessProbe" not in c.spec]
    return f"no livenessProbe on {bad}" if bad else None


def check_limits(dep: dict, cs: list[Container]) -> str | None:
    """8 - a container without a limit is a container that can take the node down."""
    bad = [c.name for c in cs if not c.spec.get("resources", {}).get("limits")]
    return f"no resources.limits on {bad}" if bad else None
```

**Line by line:**

- `c.kind != "init"` excludes ordinary init containers from the liveness check, and that exclusion is
  correct rather than convenient: an init container is *supposed* to exit, so a liveness probe on one
  would restart a container that had succeeded. Sidecars are not excluded, because `kind` is
  `"sidecar"` for them — the classification in part
  [1.2](../01-what-the-cluster-is-told/1.2-the-pod-is-the-unit.md) is what makes this one line
  possible.
- `.get("resources", {}).get("limits")` chains two defaults, because there are two ways to have no
  limit: no `resources` block at all, or a `resources` block with only `requests` in it. The second
  is more common and looks more responsible.
- The truthiness test rather than `is not None` catches `limits: {}` — an empty mapping, which is
  legal YAML and means nothing is limited.
- Neither check looks at the *values*. A memory limit of one megabyte passes. That is deliberate: the
  right number is a question about this workload, and a checker that guessed would be wrong in both
  directions. The check asserts that somebody made a decision, not that the decision was good.

And the containment check, which has two halves at two levels:

```python
def check_non_root(dep: dict, cs: list[Container]) -> str | None:
    """9 - the Pod does not run as root, and no container can climb back."""
    if not pod_spec(dep).get("securityContext", {}).get("runAsNonRoot"):
        return "pod securityContext does not set runAsNonRoot: true"
    bad = [c.name for c in cs if c.spec.get("securityContext", {}).get("allowPrivilegeEscalation")]
    return f"allowPrivilegeEscalation not disabled on {bad}" if bad else None
```

**Line by line:**

- `runAsNonRoot` is read from the **Pod's** security context, because setting it there applies to
  every container including ones added later. A per-container setting is a thing somebody forgets on
  the next container.
- `allowPrivilegeEscalation` is read **per container**, because it is a per-container field. The
  Pod-level and container-level security contexts are different objects with overlapping but not
  identical fields, and treating them as one is a common source of settings that appear to be applied
  and are not.
- The container check tests for *truthiness* of `allowPrivilegeEscalation`, so both `false` and an
  absent field pass. That is a real weakness — absent is not the same as explicitly false, and the
  Kubernetes default depends on other settings — and the stricter version is one word. It is left as
  written so that the naive manifest's failure is attributable to the Pod-level line rather than to
  nine container-level ones.

Measured against the naive manifest on 2026-09-07:


**Line by line:**

- Three properties in one `grep`, because in practice they are absent together — the manifest that
  skipped one skipped all three.

```text
  FAIL  every container has a livenessProbe
  FAIL  every container has resources.limits
  FAIL  runs as a non-root user
    - every container has a livenessProbe: no livenessProbe on ['sutra-mcp', 'sutra-api']
    - every container has resources.limits: no resources.limits on ['sutra-mcp', 'sutra-api']
    - runs as a non-root user: pod securityContext does not set runAsNonRoot: true
```

**All three, both containers.** And every one of those is a legal object that a cluster would run
without comment — a root container, with no ceiling, that nothing ever asks whether it is alive.

## When it breaks

**The liveness probe that restarts a healthy container.** A probe with a short timeout against an
endpoint that does real work will fail under load, and the response to failure is a restart, which
removes capacity, which increases load on what remains. This is a genuine outage pattern and it is
caused by a safety feature. The fix is that a liveness endpoint must be trivial — it answers whether
the process is wedged, not whether the system is well — and anything expensive belongs behind
readiness.

**The memory limit discovered in production.** A Python process with ADK, an OTel exporter and an
`httpx` connection pool does not live in a small limit, and the failure is not gradual: the container
is killed with `OOMKilled` and restarted, repeatedly, which looks like a crash loop caused by
whatever it was doing at the time. This machine cannot reproduce it — it needs a cgroup and therefore
a container runtime — and the exact command to observe it is a `TODO(me)` in the hub, **not run
here**.

**The `runAsNonRoot` that stops the Pod starting.** This one fails loudly and correctly, and it is
worth expecting: if the image's default user is root and the manifest says `runAsNonRoot: true`, the
kubelet refuses to start the container rather than silently running as root. The Pod sits in
`CreateContainerConfigError`. The fix is in the image — a `USER` line — which is Day 86's file, not
this one. Two days' artifacts have to agree, and this is the field where they meet.

## In production

**What a professional does.** Sets requests and limits from measurement rather than from a guess —
run it, watch the actual usage, set the limit above the observed peak with headroom — and revisits
them when the workload changes. The number that gets copied from another service's manifest is the
number that causes the incident.

**What degrades at scale.** Requests, not limits. Requests are what the scheduler reserves, so a
cluster full of workloads asking for more than they use has plenty of free memory and no room to
schedule anything. This shows up as *"the cluster is full"* on a cluster that is visibly idle, and the
cause is a hundred manifests each padded by somebody being careful.

**The failure that only shows with real traffic.** The probe that is right in every environment but
the busy one. Every timeout and threshold in the probe stanza is a bet about latency under load, made
on a machine that was not under load. `periodSeconds: 1` with `failureThreshold: 30` — the sidecar's
startup gate in this manifest — is a bet that the archive server starts within thirty seconds. On a
cold node pulling a cold image that may be optimistic, and the symptom is a container that is
restarted just before it would have succeeded.

**The review comment a senior engineer leaves:** *"Liveness on `/healthz` is fine as long as
`/healthz` does not touch the archive. If it does, a slow archive will make us restart a healthy
agent, and we will spend the outage looking at the wrong service."*

**The interview question:** *"What is the difference between a readiness and a liveness probe?"* The
answer that shows experience gives the mechanism in one line each and then the failure: using
liveness where readiness belonged turns a slow dependency into a restart storm, and it does it
precisely when you can least afford it.

node that had to pull the image first.
