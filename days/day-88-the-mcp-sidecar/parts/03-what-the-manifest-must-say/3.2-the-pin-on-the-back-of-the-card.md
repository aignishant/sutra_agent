# 3.2 — The PIN on the back of the card

## One-line answer

A manifest is a file that gets committed, reviewed, pasted into chat and — in this repository's case
— published, so a credential written into it as a literal has been handed to everybody who will ever
read the deployment, and the fix is one field name.

## The story

The PIN written on the back of the card.

It solves a real problem. You have four cards and a memory that is not what it was, and the number
is right there when the machine asks for it. Nobody set out to be careless; somebody set out to be
able to withdraw money.

What it also does is make the card and the secret one object. Lose the card and you have not lost a
card, you have lost the account. Lend the card to somebody for one purchase and you have lent them
everything. And there is no moment at which this goes wrong loudly — the card works perfectly, every
single time, right up until it is somewhere you did not intend.

The fix is not a better place on the card. It is that the number lives somewhere else entirely.

## The idea in plain language

Kubernetes gives a container an environment variable in one of two shapes:

```yaml
          env:
            - name: SUTRA_MCP_URL
              value: http://127.0.0.1:8000/mcp
            - name: GOOGLE_API_KEY
              valueFrom:
                secretKeyRef:
                  name: sutra-secrets
                  key: google-api-key
```

**`value`** is a literal. It is in the file, in the diff, in the repository, in every copy anybody
ever made of the repository, and — from Phase 14 — on the public internet.

**`valueFrom.secretKeyRef`** is a pointer. It names a Secret object and a key inside it. The
manifest says *where the value comes from*; the value itself is created separately, from `.env`, by
a command that is not committed.

The distinction is Principle 9 with a field name attached: secrets never touch git. Every earlier day
enforced it in Python — `os.environ`, `python-dotenv`, a `.gitignore` line. Today it has to be
enforced in YAML, and the mechanism is a different key in a dictionary.

Two things are worth being precise about, because both are commonly overstated.

**A Kubernetes Secret is not encrypted by default.** It is base64-encoded, which is an encoding, not
a cipher — anybody who can read the Secret object can read the value. What a Secret buys is that the
value lives in the cluster's datastore under separate access control rather than in your repository.
That is a real and worthwhile boundary, and it is not confidentiality at rest unless the cluster was
configured for it.

**The pointer is safe to commit and that is the whole point.** `name: sutra-secrets, key:
google-api-key` tells a reader that a credential is needed and where it will come from. That is
information a reviewer *wants*.

## Why Sutra needs it

Because this repository goes public in Phase 14, and a key committed once is a key that is in the
history forever — rotating it is the only remedy, and the rotation has to happen before publication
rather than after somebody notices.

And because a deploy directory is exactly where this mistake gets made. Every other file in the
project has been Python, where the habit of reading `os.environ` is established. A manifest is a new
file type with a new syntax, written under time pressure, by somebody who has just watched a Pod
fail to start for want of a variable. The literal works immediately. That is why it happens.

## The mechanism

The check is short because the two shapes are structurally different:

```python
def check_secrets(dep: dict, cs: list[Container]) -> str | None:
    """5 - credentials arrive by reference, never as a literal."""
    for c in cs:
        for name, entry in env_of(c).items():
            if any(marker in name.upper() for marker in SECRET_NAMES) and "value" in entry:
                return f"{c.name}: {name} is a literal in the manifest, {len(entry['value'])} chars"
    return None
```

**Line by line:**

- The test is on the *shape*, not on the content. `"value" in entry` asks whether the value was
  written inline; there is no attempt to recognise a key by what it looks like, because a check that
  matches key formats will always be one provider behind.
- `SECRET_NAMES` is `("API_KEY", "TOKEN", "SECRET", "PASSWORD")` — a substring match on the variable
  *name*, upper-cased. This is a heuristic and it is the weak half of the check: a credential called
  `SUTRA_ARCHIVE_CREDENTIAL` passes. **When it breaks** is about exactly that.
- The message reports the *length* of the literal, never the literal. A checker that prints the
  secret it found has copied it into the build log, which on a public repository is a second
  disclosure.
- It returns on the first finding rather than collecting all of them, which is the one place in this
  checker where stopping early is right: one credential in the file is already a rotation, and the
  remedy does not change if there are two.
- `env_of(c)` reads the container's `env` list into a dict keyed by name — a container with no `env`
  at all yields an empty dict rather than raising, which is what makes this safe to run over the
  sidecar as well.

The naive manifest carries exactly the mistake:

```yaml
            - name: GOOGLE_API_KEY
              value: "AIzaSyD-ThisIsNotARealKeyItIsThePointOfTheLesson"
```

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python check.py --naive | grep "credential"
```

**Line by line:**

- `grep` for the one property, because the naive manifest fails seven and the point here is one of
  them.

Measured on 2026-09-07:

```text
  FAIL  no credential literals
    - no credential literals: sutra-api: GOOGLE_API_KEY is a literal in the manifest, 48 chars
```

**Forty-eight characters, and the checker never printed one of them.** The finding is complete —
which container, which variable, how big — and reading the build log tells you nothing you could
use.

## When it breaks

**The heuristic misses.** `SECRET_NAMES` matches four substrings. A variable called
`ARCHIVE_CONNECTION_STRING`, `GH_PAT` or `SIGNING_KEY_B64` sails through, and the last of those
contains neither `SECRET` nor `KEY`… except it does contain `KEY`, which is a good illustration of
how arbitrary the boundary is. There is no error text; the check passes and the credential is in the
file.

The honest mitigations are two, and neither is a longer word list. One is a secret **scanner** that
matches value shapes rather than names, run over the whole repository rather than over manifests —
which is a different tool with a different failure mode, and it is a `TODO(me)` in the hub. The
other is inverting the rule: assert that **no** `env` entry in the deploy directory uses `value` for
anything except a small allowlist of known-harmless variables. That is stricter, noisier, and
catches the thing this check misses.

**The Secret gets committed instead.** The literal moves out of the Deployment and into a
`secret.yaml` with a base64 blob in it, which feels like progress and is not — base64 is not
encryption, and the blob is now in the repository with a filename that says what it is. The correct
shape is that the Secret object is *created by a command*, from `.env`, and only the command is
committed. That command is in the hub's build brief as an unrun `TODO(me)`.

**The value leaks sideways.** An environment variable is visible in `kubectl describe pod` output, in
crash dumps, in a process listing inside the container, and in any log line that prints the
environment. The Secret keeps it out of the repository; it does nothing about the other five places,
and the control for those is Day 22's structured logging discipline and not touching them.

## In production

**What a professional does.** Keeps the secret material out of the repository entirely and lets the
platform inject it — a Secret created from a vault, a cloud provider's secret manager, or an
identity the workload has rather than a credential it carries. Day 87's parked walkthrough is the
version of this Sutra cannot use: a managed platform hands the workload an identity and there is no
key anywhere. Knowing why that is better than what you have is worth as much as having it.

**What degrades at scale.** The number of places a variable can be set. One Deployment is one place;
a real system has a base manifest, an overlay per environment, a ConfigMap, a Secret and a
pipeline-injected variable, and the effective value is the last writer in an order nobody can recite.
The discipline that survives is to be able to print the fully resolved Pod spec and check *that*.

**The failure that only shows with real traffic.** A rotated key that only rotated in one place. The
Secret is updated, and the Pods keep running with the old value, because an environment variable is
read once at process start and Kubernetes does not restart Pods when a Secret changes. Everything
looks correct — the Secret holds the new key, the Deployment references it — and the running system
is using the old one until something forces a rollout. This is the single most common surprise about
Secrets and it has no error text at all.

**The review comment a senior engineer leaves:** *"Ship the `secretKeyRef` and add the rotation
runbook line in the same change: rotating this key requires a rollout, because env vars are read at
start. Otherwise we will rotate it in an incident and wonder why nothing changed."*

**The interview question:** *"How do you get a database password into a Pod?"* The answer that shows
experience gives the mechanism and then the two caveats without being asked: a Secret is not
encrypted by default, and changing it does not restart anything.

## Check yourself

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python check.py --naive | grep "credential"
grep -n "valueFrom" -A 3 k8s/deployment.yaml
```

The second command shows the shape that is safe to commit. Say what a reviewer learns from those
four lines that they would not learn if the variable were simply absent.

Now defeat the check on purpose: in `k8s/deployment-naive.yaml`, rename `GOOGLE_API_KEY` to
`GOOGLE_CREDENTIAL` and run `check.py --naive` again. The credential is still there in plain text and
the check now passes it. Say what you would change — and why "add more words to the list" is the
wrong answer.

**Out loud, without scrolling up:** two true statements about Kubernetes Secrets that people
routinely get wrong.
