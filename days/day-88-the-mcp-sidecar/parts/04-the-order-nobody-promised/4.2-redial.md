# 4.2 — Redial

## One-line answer

The caller's half of the fix is a bounded retry with backoff around the first connection, which
turns a startup race from a fatal error into six-tenths of a second nobody notices — and it works
whether or not the platform underneath ever promises anything about ordering.

## The story

Pressing redial.

The call does not connect. There is a click and then nothing, and you look at the screen to check
you dialled the right number.

Nobody's first conclusion is that the number is wrong. You press redial, because a call that fails
once and a number that does not exist are different things, and one attempt cannot tell them apart.
The second attempt connects and you have already forgotten about the first.

What makes this sensible rather than superstitious is that it is bounded. You press redial twice,
maybe three times. At some point the failure stops being noise and starts being information, and you
go and find out whether the number changed. Somebody who redials for an hour has stopped
distinguishing the two cases in the other direction.

## The idea in plain language

The agent has to connect to the MCP server before it can do anything. That connection may fail
because the server has not bound yet, and that condition **resolves on its own**.

So the caller's correct behaviour is: try, and if it fails in a way that could be transient, wait a
little and try again, up to a bound. Three parameters and one decision:

| Parameter | Value here | Why |
| --- | --- | --- |
| per-attempt timeout | 0.5s | short, because a wrong answer costs one more attempt rather than the whole call |
| backoff | 0.05s, doubling, capped at 1.0s | cheap early attempts when it is likely about to work; no busy loop if it is not |
| deadline | 10s | after this the condition is not transient and pretending otherwise hides a real fault |

The decision is the deadline, and it is the one people leave out. A retry loop with no bound is not
resilience — it is a program that hangs, and a Pod that hangs at startup never becomes ready, never
gets restarted by a liveness probe that has not begun, and sits there looking almost fine. **A retry
without a deadline converts a loud failure into a silent one.**

Note also what the per-attempt timeout can be here, and why. Part
[4.1](4.1-the-clinic-was-not-open-yet.md) argued for a *long* timeout so that the true error
surfaces. Inside a retry loop the opposite is right: half a second is plenty, because if the answer
was going to be *refused* it does not matter which name the failure has — the loop's response is
identical. The long timeout is for the call that has to produce a diagnosis; the short one is for the
call that has another attempt behind it.

## Why Sutra needs it

Because this control belongs to Sutra and nothing else can supply it. Part
[4.3](4.3-what-kubernetes-actually-promises.md) is the platform's ordering guarantee, and it is real
— but it applies only when the sidecar is declared in the right list with the right field, only on a
cluster new enough to implement it, and not at all when the same two processes are run under compose
or by hand in two terminals. The retry works everywhere.

And because Day 44 already argued this for MCP clients in general: retries, timeouts, no held
connections. This is that day's rule meeting the one situation where the transient condition is
guaranteed rather than possible.

## The mechanism

```python
def wait_until_ready() -> tuple[int, float]:
    """Retry with backoff until the sidecar answers. Day 44's client hardening, locally."""
    started = time.monotonic()
    wait = GATE_FIRST_WAIT_SECONDS
    attempt = 0
    while True:
        attempt += 1
        try:
            dial(GATE_TIMEOUT_SECONDS)
        except OSError:
            if time.monotonic() - started > GATE_DEADLINE_SECONDS:
                raise
            time.sleep(wait)
            wait = min(wait * 2, 1.0)
            continue
        return attempt, time.monotonic() - started
```

**Line by line:**

- `time.monotonic()` rather than `time.time()`. A clock adjustment — an NTP correction, a container
  starting on a host whose clock has just been set — can move wall-clock time backwards, and a
  deadline computed from it would either fire immediately or never. Monotonic time cannot go
  backwards.
- `except OSError` is the right width. `ConnectionRefusedError` and `TimeoutError` are both `OSError`
  subclasses, and part [4.1](4.1-the-clinic-was-not-open-yet.md) measured that which one arrives
  depends on the timeout — so catching either specifically would work on this machine and not on the
  next one.
- The deadline is checked **inside** the handler, before sleeping, and re-`raise`s the original
  exception rather than a new one. The traceback that escapes is the real failure, with the real
  reason, not a `TimeoutError("gave up")` that has thrown away what actually happened.
- `wait = min(wait * 2, 1.0)` — exponential backoff with a cap. Doubling from fifty milliseconds
  means the first few attempts are nearly free, which matters because the likely case is that it
  works almost immediately; the cap means a ten-second wait is at most ten-ish attempts rather than a
  thousand.
- No jitter, and that is a deliberate omission with a reason: jitter exists to stop many clients
  retrying in lockstep against one server, and there is exactly one client here, inside the same Pod.
  Day 72's backoff day is where jitter belongs.
- The return value is `(attempts, elapsed)` rather than nothing, because a caller that connected on
  attempt seven should be able to log that. A gate that hides how long it waited is a gate that hides
  a degrading dependency.

**Line by line:**

- Same sidecar, same five-second startup, same port. The only difference is that the agent retries.

Measured on 2026-09-07:

```text

the sidecar binds 127.0.0.1:8931 after 5.0s of startup work
the agent retries, 0.5s per attempt, until it answers

```

**Seven attempts, five and a half seconds, exit `0`.** The same race that produced part
[4.1](4.1-the-clinic-was-not-open-yet.md)'s `ConnectionRefusedError` produced a startup that worked,
and the difference is fourteen lines.

Note the number the gate reports. Five point five nine seconds against a sidecar that binds at five —
so the loop cost about six-tenths of a second beyond the unavoidable wait. That is the price of the
backoff's granularity, and it is the right thing to have measured, because it is the number somebody
will want when they ask whether to tighten the loop.

## When it breaks

**The retry with no deadline.** Delete the two lines that check `GATE_DEADLINE_SECONDS` and the loop
becomes `while True` around a failing call. If the sidecar never binds — wrong port, crashed on boot,
wrong container — the agent waits forever. There is no error, no exit code and no log line: a
process, running, doing nothing, in a Pod that never becomes ready. Everything about this is worse
than the original failure, because the original failure at least said what was wrong.

**Retrying what will not resolve.** A retry loop is correct only for conditions that fix themselves.
`ConnectionRefusedError` at startup is one. `ConnectionRefusedError` because the URL names port 9000
and the server listens on 8000 is not, and the loop will spend its whole deadline discovering that.
The deadline is what converts the second case back into a diagnosable failure, which is a second
reason it is not optional.

**The gate that runs in the wrong place.** Putting `wait_until_ready` in the agent's startup path is
right. Putting it inside every tool call is not — that turns a five-second startup cost into a
per-request cost and hides a dead dependency behind latency. Day 44's *no held connections* rule and
this one are in tension, and the resolution is that the gate runs once, at startup, and ordinary
per-call retries stay short.

**The one this lab cannot show.** In a cluster, the retry interacts with the restart policy: an agent
that exhausts its deadline exits, the kubelet restarts it, and the retry begins again — so the
effective deadline is the loop's deadline multiplied by however many restarts happen before the
backoff gets long. Observing that needs a kubelet. The command is in the hub's build brief and was
**not run here.**

## In production

**What a professional does.** Makes the startup dependency check explicit and logs it: one line
saying which dependency, how many attempts and how long. That line is worth more than it looks —
when the number creeps from two attempts to twenty over three months, it is the earliest possible
warning that something downstream is getting slower.

**What degrades at scale.** Retry storms, which is the failure jitter exists for. This gate has one
client, so it does not have the problem; a gate copied from here into a service with forty replicas,
all restarting together after a node failure, all retrying in lockstep, does. The line that has to be
added at that point is jitter, and Day 72 is the argument.

**The failure that only shows with real traffic.** The gate that succeeds and lies. Connecting to a
port proves something is listening; it does not prove the MCP server has loaded its tools. A server
that binds early and finishes initialising later will accept the connection and then answer the first
`tools/list` with an empty set — and an agent that started with no tools looks like a
misconfiguration rather than a race. The fix is that the readiness check must exercise the thing you
actually depend on, which for MCP means listing tools rather than opening a socket.

**The review comment a senior engineer leaves:** *"Put a deadline on it and log the attempt count. And
check tools, not the port — we will otherwise ship an agent that starts successfully with zero tools
and nobody will notice until a ticket comes in."*

**The interview question:** *"How do you handle a dependency that is not ready when your service
starts?"* The answer that shows experience gives the retry and then immediately gives the two bounds
that make it safe: a deadline, and a readiness test that checks the capability rather than the
socket.
