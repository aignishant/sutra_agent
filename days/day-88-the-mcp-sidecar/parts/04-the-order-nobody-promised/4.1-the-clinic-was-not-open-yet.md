# 4.1 — The clinic was not open yet

## One-line answer

💥 Two containers in one Pod start at the same time, so an agent that dials its MCP server on boot
dials a process that exists and is not yet listening — and the error it gets back depends on a
timeout it chose, which means the same failure arrives wearing two different names and only one of
them points at the truth.

## The story

💥 **The clinic at ten past nine.**

🎬 **The scene.** The board says the doctor sits from nine. You arrive at ten past, and the shutter
is down. There is a light on inside and you can hear a kettle.

😬 **The naive fix.** You conclude the clinic has moved. The board is old, the shutter is down, and
you have somewhere to be — so you go to the other clinic, twenty minutes away, and wait there.

💥 **Why it fails.** The doctor was inside the whole time, having tea, and opened at quarter past.
Nothing was wrong with the clinic. What was wrong was your test: you checked whether the shutter was
up and concluded something about whether the clinic exists. Those are different questions and one of
them was not the one you needed answered.

💡 **The insight.** *Present* and *open* are not the same state, and there is no way to tell them
apart from outside without either waiting or being told. The board said nine. The board is a
statement about intent; the shutter is the only statement about readiness.

## The idea in plain language

Containers in a Pod are started by the kubelet. The plain ones, listed under `containers:`, are
started **together** — there is no ordering between them, and none is promised.

So consider what the agent does at boot. It reads `SUTRA_MCP_URL`, which is
`http://127.0.0.1:8000/mcp`, and connects, because that is what a client does when it starts: it
establishes its session with the MCP server and lists the tools.

At that moment the MCP server is a process that has existed for a few milliseconds. It is importing
its toolset, opening the archive and reading its configuration. It has not called `bind()` yet.
There is nothing listening on port 8000, and the operating system says so.

**The sidecar is running. It is not listening. Those are different.**

This is not an exotic race. It is the ordinary case: any two processes started at the same instant,
where one calls the other immediately, will hit it whenever the callee's startup is slower than the
caller's. An agent that loads a small config and dials, against an MCP server that imports a machine
learning framework, loses that race every single time.

## Why Sutra needs it

Because Sutra's MCP client has connected at startup since Day 33, and until today it always
connected to a server somebody had already started in another terminal. The human was the ordering
guarantee. A Pod has no human in it.

And because the failure looks exactly like a configuration error. `ConnectionRefusedError` on
`127.0.0.1:8000` is what you also get from a wrong port, a wrong host, a server that crashed on boot,
and a container that is not in this Pod at all. Four causes, one symptom, and the one that is
actually happening is the only one that fixes itself two seconds later — which is why it is so often
diagnosed as something else.

## The mechanism

The lab runs it for real: two processes on `127.0.0.1`, which is what two containers in one Pod are.
`serve.py` is the sidecar, and its first line is the whole point:

```python
def main() -> int:
    time.sleep(STARTUP_SECONDS)

    listener = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    try:
        listener.bind(("127.0.0.1", PORT))
    except OSError:
        return 2  # something else holds the port; race.py reports this rather than hanging
    listener.listen(8)
```

**Line by line:**

- `time.sleep(STARTUP_SECONDS)` **before** the socket is created, not after. That ordering is the
  entire fidelity of the model: a real server does its startup work first and binds last, so for the
  whole of that window the process is up and the port is closed.
- `STARTUP_SECONDS` is five, which is not an exaggeration for this workload. Importing ADK, opening
  an archive and reading configuration is seconds of work, and a cold container adds to it.
- `SO_REUSEADDR` before `bind` so a rerun immediately after a previous run does not fail on a socket
  in `TIME_WAIT` — an unrelated failure that would muddy the measurement.
- `bind` is inside a `try` returning `2`, so a port genuinely held by something else is
  distinguishable from the race. Reporting *"the port was taken"* as *"the sidecar was slow"* would
  teach the wrong lesson from a real run.
- `listen(8)` only after all of that. Everything above this line is time during which a client gets
  refused.

And `race.py` is the agent that dials immediately:

```python
def dial(timeout: float) -> bytes:
    """One connection attempt. Raises exactly what the operating system says."""
    with socket.create_connection(("127.0.0.1", PORT), timeout=timeout) as sock:
        return sock.recv(64)
```

**Line by line:**

- No retry, no catch, no wrapping. The whole value of this function is that it raises what the
  kernel said, so the transcript below is the operating system's own words rather than a paraphrase.
- `create_connection` with an explicit `timeout` — and that argument turns out to be the second
  finding of this part.
- The `with` block closes the socket even when `recv` raises, which matters when this is called in a
  loop by part [4.2](4.2-redial.md).

Run it:

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python race.py; echo "exit: $?"
```

**Line by line:**

- No flag: the agent dials once, as soon as it starts, exactly as an MCP client does.

Measured on 2026-09-07:

```text
Pod: sutra-api (app) + sutra-mcp (sidecar), one network namespace
the sidecar binds 127.0.0.1:8931 after 5.0s of startup work
the agent dials once, 3.0s timeout, as soon as it starts

  the agent's first call to the MCP server:

    ConnectionRefusedError: [WinError 10061] No connection could be made because the target machine actively refused it

  the sidecar is running. It is not listening. Those are different.
exit: 1
```

**That is the failure, in the operating system's own words.** No traceback from Sutra, no ADK error,
no MCP protocol error — the connection never happened, so nothing above the socket layer had anything
to say.

## When it breaks

Now the second finding, which was discovered by running this rather than by reasoning about it, and
which is worth more than the first.

**The timeout you chose decides which error you see.**

```bash
uv run python race.py --impatient; echo "exit: $?"
```

**Line by line:**

- `--impatient` changes exactly one number: the connect timeout, from three seconds to one. The
  sidecar, the port, the ordering and the code path are identical.

Measured on 2026-09-07:

```text
the agent dials once, 1.0s timeout, as soon as it starts

  the agent's first call to the MCP server:

    TimeoutError: timed out

  the sidecar is running. It is not listening. Those are different.
```

Same race, same machine, same second — and the error is now `TimeoutError: timed out`.

The reason is that a refused connection on this machine takes between one and three seconds to come
back: the kernel retries the connection attempt before it surfaces the reset. A client that gives up
at one second never receives the refusal, so it reports the only thing it knows, which is that it
waited and nothing happened.

Those two errors send an engineer to two different places. `ConnectionRefusedError` says *nothing is
listening on that port* — the right diagnosis, pointing at startup order. `TimeoutError` says
*something is there and it is slow, or the network is dropping packets* — and on a loopback address
inside one Pod, both of those are impossible, so the person now doubts their model of the whole
system.

This is Day 44's client-hardening argument arriving from an unexpected direction: a timeout is not
only a bound on waiting, it is a **filter on which failures you are able to observe.** Too short a
timeout does not just fail faster; it fails less informatively.

## In production

**What a professional does.** Assumes no ordering between containers in a Pod and makes the caller
tolerant, then adds the platform's ordering guarantee on top as defence rather than as the only
control. Part [4.2](4.2-redial.md) is the caller half and part
[4.3](4.3-what-kubernetes-actually-promises.md) is the platform half; a system with only one of them
is one platform upgrade or one refactor away from this transcript.

**What degrades at scale.** The window widens. Cold nodes pull images, busy nodes start containers
slower, and a sidecar that binds in five seconds on a laptop can take considerably longer on a
contended node. A race that is lost occasionally in development is lost reliably in production and
then intermittently again after somebody adds capacity, which is the worst possible bug rhythm.

**The failure that only shows with real traffic.** The restart. The Pod comes up, the agent fails to
connect, and — because a failed startup connection usually means the process exits — the container
restarts. Now it is competing with a sidecar that is *already* running, so the second attempt
succeeds, and the Pod eventually becomes healthy with one restart on its record. Nobody investigates
one restart. The bug is invisible until the day the sidecar is slower than the agent's restart
backoff and the Pod crash-loops instead.

**The review comment a senior engineer leaves:** *"Connection refused on loopback inside a Pod is
almost always startup order, not configuration. Before changing the port, check whether the callee
had bound yet — and set the client timeout long enough that we actually see the refusal, because a
one-second timeout will tell you it was a network problem and there is no network."*

**The interview question:** *"Your app cannot reach its sidecar on localhost. Where do you look?"*
The answer that shows experience asks *when* rather than *where* — at startup only, or continuously?
— because startup-only is an ordering problem and continuous is a configuration problem, and the two
have nothing in common except the error message.

## Check yourself

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python race.py; echo "exit: $?"
uv run python race.py --impatient; echo "exit: $?"
```

One number of difference and two different errors. Say which of the two you would rather be handed at
two in the morning, and what that implies about picking client timeouts.

Now change `STARTUP_SECONDS` in `serve.py` from five to one, run `race.py` again, and explain the
result. It is not the result you would predict from the numbers alone — the reason is in **When it
breaks**. Put it back to five afterwards.
