# 4.3 — What Kubernetes actually promises

## One-line answer

Kubernetes will start a sidecar before the app container and wait for it — but only if the sidecar is
declared as an `initContainers` entry with `restartPolicy: Always`, and "wait for it" means *a
process is running* unless you also give it a `startupProbe`, which is the difference between the
guarantee people think they have and the one they do.

## The story

The ambulance and the paramedic.

The ambulance does not leave when the driver arrives. It leaves when the crew is aboard, and there is
a procedure for establishing that: somebody confirms it, out loud, before the doors close. Not
because anybody doubts the paramedic is coming — because "coming" and "aboard" are different states
and the vehicle can physically depart during either one.

The interesting failure is not the paramedic being late. It is a confirmation that checks the wrong
thing. If the rule were *"leave once the paramedic is in the yard"*, the ambulance would sometimes
leave with a paramedic jogging behind it, and every part of the procedure would have been followed.

## The idea in plain language

Part [4.1](4.1-the-clinic-was-not-open-yet.md) established that containers in `containers:` start
together with no ordering. Kubernetes does have a mechanism for ordering, and its spelling is
surprising.

**A sidecar is an init container that does not exit.** Verified on 2026-09-07 from
`kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/`:

> *"Kubernetes implements sidecar containers as a special case of init containers; sidecar containers
> remain running after Pod startup."*

There is no `sidecars:` list. You put the container in `initContainers:` and give it `restartPolicy:
Always`, and those two facts together are the whole declaration. The same page records the feature's
history: it is **stable since Kubernetes v1.33**, was first available in **v1.28**, and has been
**active by default since v1.29**, with the feature gate now locked.

What that buys is ordering. Init containers run before app containers, in list order, and a
sidecar-style init container is considered done — so the next one may start — once the kubelet marks
it as **started**.

And here is the sentence the whole day turns on, from the same page:

> *"That status either becomes true because there is a process running in the container and no
> startup probe defined, or as a result of its `startupProbe` succeeding."*

Read it twice. **With no `startupProbe`, "started" means a process exists.** The kubelet forks the
container, sees a process, marks it started, and proceeds to the app container — which then dials a
server that has not bound yet, and gets part [4.1](4.1-the-clinic-was-not-open-yet.md)'s transcript.

The ordering guarantee is real. The condition it waits on is, by default, almost nothing.

So the correct declaration has three parts, not two:

| Field | Without it |
| --- | --- |
| the container is in `initContainers:` | no ordering at all; both start together |
| `restartPolicy: Always` | it is an ordinary init container: it must exit before the app starts, so a server would block the Pod forever |
| `startupProbe` | ordering is enforced against *a process existing*, which is the failure this day measured |

## Why Sutra needs it

Because two of Sutra's nine manifest checks exist entirely to enforce the second and third rows, and
without this part they look like fussiness. Check 2 fails a sidecar declared under `containers:`;
check 3 fails a sidecar with no `startupProbe`. Both are one line in a file and both are the
difference between an ordering guarantee and the appearance of one.

And because Sutra's MCP client connects at startup. This is precisely the workload the mechanism was
designed for, and precisely the workload where the default meaning of *started* is wrong.

## The mechanism

The manifest, with the three parts adjacent:

```yaml
      initContainers:
        - name: sutra-mcp
          image: sutra-mcp:0.1.0
          imagePullPolicy: Never
          restartPolicy: Always
          ports:
            - containerPort: 8000
          startupProbe:
            httpGet:
              path: /healthz
              port: 8000
            periodSeconds: 1
            failureThreshold: 30
```

The `startupProbe` is doing something a `readinessProbe` could not, and the distinction is worth
being exact about: readiness controls whether a Pod receives traffic from Services, and this
container is behind no Service at all. Its readiness is meaningless. What matters is *when the
kubelet considers it started*, and `startupProbe` is the only field that answers that question.

`periodSeconds: 1` with `failureThreshold: 30` gives the archive server thirty seconds to answer on
`/healthz` before the kubelet gives up and restarts it. That is a bet, and part
[3.4](../03-what-the-manifest-must-say/3.4-the-whistle-and-the-limit.md) is where bets like it are
discussed.

The checks that enforce all this:

```python
def check_sidecar_declared(dep: dict, cs: list[Container]) -> str | None:
    """2 - the MCP server is an initContainer with restartPolicy: Always."""
    mcp = next((c for c in cs if c.name == "sutra-mcp"), None)
    if mcp is None:
        return "no sutra-mcp container at all"
    if mcp.kind != "sidecar":
        return (
            "sutra-mcp is a plain app container, so the kubelet gives it no ordering"
            " guarantee; a sidecar is an initContainers entry with restartPolicy: Always"
        )
    return None
```

**Line by line:**

- `next((...), None)` with a default rather than bare `next(...)`, because "there is no such
  container" is a finding this check should report rather than a `StopIteration` it should raise.
- `mcp.kind != "sidecar"` leans on the classification from part
  [1.2](../01-what-the-cluster-is-told/1.2-the-pod-is-the-unit.md), where `kind` was computed as
  `"sidecar"` only for an `initContainers` entry carrying `restartPolicy: Always`. Both conditions
  are already folded into that one word.
- The failure message states the remedy, not just the fault. A reviewer reading `FAIL sidecar
  declared as an initContainer` in a pipeline should not have to go and find out what the fix is.

Both properties, measured against the manifest that gets them wrong:

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python check.py --naive | grep -E "sidecar|startupProbe"
```

**Line by line:**

- The two properties are read together because they fail together and their fixes are two adjacent
  lines in the same file.

Measured on 2026-09-07:

```text
  FAIL  sidecar declared as an initContainer
  n/a   every sidecar has a startupProbe
    ? every sidecar has a startupProbe: this manifest declares no sidecar, so there is nothing to probe
    - sidecar declared as an initContainer: sutra-mcp is a plain app container, so the kubelet gives it no ordering guarantee; a sidecar is an initContainers entry with restartPolicy: Always
```

**`FAIL` and `n/a`, not two failures.** The naive manifest has no sidecar in the Kubernetes sense at
all, so the question *"does its sidecar have a startup probe"* has no subject. Part
[3.1](../03-what-the-manifest-must-say/3.1-checking-what-the-cluster-would-read.md) is why that had
to be a third outcome rather than a pass.

## When it breaks

**`restartPolicy: Always` omitted.** The container is now an ordinary init container, which must
**exit** before the app containers start. An MCP server does not exit; it serves. So the Pod sits in
`Init:0/1` forever — a state that looks like a hung image pull and is actually a semantics mistake.
This is a Pod status and cannot be reproduced on this machine; the exact command to observe it is in
the hub's build brief and was **not run here.**

**`startupProbe` omitted.** The guarantee degrades to *a process exists*, which is the sentence
quoted above, and the symptom is part [4.1](4.1-the-clinic-was-not-open-yet.md)'s transcript — which
this lab did produce, for real, because two local processes model it exactly.

**The cluster is too old.** Below v1.29 the behaviour is behind a feature gate; below v1.28 the field
does not exist. On a cluster that does not implement it, `restartPolicy: Always` on an init container
is either rejected or ignored, and the manifest that expresses the guarantee correctly does not get
it. This is the strongest argument for part [4.2](4.2-redial.md)'s retry existing regardless: it is
the only control that does not depend on the platform's version.

**Nothing here helps a restart mid-life.** The ordering guarantee is about Pod *startup*. If the
sidecar is restarted later — liveness failure, `OOMKilled` — the app container is not restarted with
it and is not paused. It simply starts getting connection errors from a neighbour that is coming
back. Every long-lived caller therefore still needs reconnection logic, and the startup gate does not
replace it.

## In production

**What a professional does.** Uses both controls and says why. The platform guarantee is declarative,
visible in the manifest and reviewable; the client retry is portable and survives platform changes.
Relying only on the manifest means a version downgrade or a copy of the workload into compose
silently loses the property; relying only on the retry means every future caller has to remember.

**What degrades at scale.** The chain. One sidecar is one ordering edge. Three sidecars in `list
order` is a startup sequence, and the Pod's time-to-ready becomes the sum of them — with the app
container waiting on all three. Startup latency is rarely budgeted and shows up during an incident,
when a rolling restart of forty Pods takes far longer than anybody predicted.

**The failure that only shows with real traffic.** The probe that passes before the service is
useful. `/healthz` returning 200 usually means "the HTTP server is up", which is a much weaker claim
than "the archive is open and the tools are loaded". So the kubelet marks the sidecar started, the
agent connects successfully, and lists zero tools. Every layer reported success. The fix is that the
startup probe must check the thing the caller depends on — the same argument part
[4.2](4.2-redial.md) makes about the retry, arriving from the platform's side.

**The review comment a senior engineer leaves:** *"`restartPolicy: Always` plus a `startupProbe`, and
keep the client retry. And make `/healthz` on the MCP server mean 'tools are loaded', because right
now it means 'a socket is open' and those are the two states this whole section is about."*

**The interview question:** *"How do you guarantee a sidecar is ready before your app starts?"* The
answer that shows experience names the declaration — `initContainers` plus `restartPolicy: Always` —
and then, unprompted, the qualification: without a `startupProbe`, *started* means a process exists,
so the guarantee is real and nearly empty.
