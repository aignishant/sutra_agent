# 1.1 — Adjectives, not verbs

## One-line answer

Every deployment tool up to now took an instruction and carried it out once; a cluster takes a
description of what should be true and spends the rest of its life closing the gap — so you stop
writing what to do and start writing what should be the case.

## The story

The standing instruction at the bank.

There are two ways to move money. One is to log in on the first of the month, type an amount, and
press send. You did a thing, the thing happened, and next month you have to remember again.

The other is a sentence you write once at the counter: *keep five thousand in the current account,
and sweep anything above it into savings.* Nobody presses anything after that. The balance goes up
because a salary landed, and the sweep happens. A cheque clears and the balance drops below five
thousand, and money comes back the other way. You did not authorise either movement individually.
You described a condition, and something else is responsible for the difference between that
condition and the truth, for as long as the instruction stands.

The second one is harder to set up and impossible to forget. It also fails differently: if you write
the wrong number, it is wrong every day, quietly and reliably.

## The idea in plain language

Everything this curriculum has used to run Sutra so far has been the first kind.

`uv run python -m sutra` starts a process. If it dies, it is dead. A container run by hand is the
same instruction with more packaging. Even a restart policy is only *"if this exits, start it
again"* — a rule about an event, attached to a thing you already started.

A **Kubernetes cluster** is the second kind. You hand it a document that says: there should be one
Pod running these two images, it is healthy when this URL answers, it gets at most this much memory,
and its credential comes from this named secret. Then a set of control loops compares that document
to reality, forever, and does whatever closes the gap. Delete the Pod and another appears — not
because deletion was blocked, but because the document still says one should exist and now none
does.

Two consequences follow immediately, and they are the reason the rest of this day is about a file
rather than about commands.

**The document is the deployment.** Not a script that produces the deployment — the document
*is* it. Which means the deployment can be read, reviewed, diffed and checked before it is applied,
and that is what makes the whole of section
[3](../03-what-the-manifest-must-say/3.1-checking-what-the-cluster-would-read.md) possible on a
machine with no cluster on it.

**A wrong document is obeyed perfectly.** There is no step at which somebody notices you meant
something else. `replicas: 2` on a desk that keeps approval state in a session store is not an
error; it is an instruction, and the cluster will maintain exactly two of them.

## Why Sutra needs it

Because the Phase 13 gate is *"traced end-to-end; runs in local k8s"*, and the second half of that
sentence is what this day is for. Day 86 made Sutra an image and Day 87 wrote down what a managed
platform would have done with it. Today is the first time anything describes the *desired state* of
the running system rather than the steps to get there.

And because the MCP server has been a separate process since Day 33, and a cluster is the first
thing that forces an explicit answer to a question that has been implicit for fifty days: how close
does the data boundary live to the agent that calls it? Part
[2.1](../02-the-sidecar-decision/2.1-one-pod-or-two.md) is that question, and it is only askable
because the topology now has to be written down.

## The mechanism

Here is the desired state, as this day writes it. The whole of `k8s/deployment.yaml` is in part
[1.3](1.3-the-document-is-the-artifact.md); this is the skeleton, with everything that is not
structure removed:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sutra-api
spec:
  replicas: 1
  selector:
    matchLabels:
      app: sutra
      component: api
  template:
    metadata:
      labels:
        app: sutra
        component: api
    spec:
      initContainers:
        - name: sutra-mcp
          restartPolicy: Always
      containers:
        - name: sutra-api
```

Read it as a sentence rather than as configuration.

- `kind: Deployment` names which control loop is responsible. There is a loop whose whole job is
  Deployments, and handing it this document is how you enlist it.
- `replicas: 1` is the adjective. Not *start one*, but *there is one*. The difference shows up the
  moment something kills the Pod.
- `selector.matchLabels` is how the loop finds the Pods it is responsible for: not by remembering
  what it created, but by asking *which Pods carry these labels right now.* That indirection is the
  paper's argument and part [papers/01](../../papers/01-labels-over-hierarchies.md) is where it
  comes from.
- `template` is the Pod that should exist. Everything under it is a description of a thing, not a
  command that makes one.
- `initContainers` with `restartPolicy: Always` is how Kubernetes spells *sidecar*, and part
  [4.3](../04-the-order-nobody-promised/4.3-what-kubernetes-actually-promises.md) is why those two
  lines are the most load-bearing in the file.

**Why a `selector` at all**, when the template is right there: because the loop and the Pods are
connected by a query rather than by a pointer. A Pod that carries the right labels counts, whoever
made it. That is what lets you take a Pod out of a Deployment's control by editing its labels — a
real debugging technique — and it is why a typo in `matchLabels` produces a Deployment that
creates Pods forever, each one immediately not matching, rather than an error.

## When it breaks

The failure that belongs here is the wrong adjective, obeyed correctly, and this repository already
has the finding that makes it concrete.

`replicas` is one character. Raise it to `2` and the cluster will maintain two desks — and Day 47
established that the desk holds approval state in a session store, so two of them means an approval
requested on one and granted on the other. The manifest carries the reason next to the number for
exactly this reason:

```yaml
  # 1, and the reason lives next to the number: the desk holds approval state in a session
  # store, so a second replica splits it. Day 47 is the finding; raising this is a decision,
  # not a tidy-up.
  replicas: 1
```

There is no error text to quote and there never will be. Two replicas is a valid document, the
control loop will report success, and the symptom appears later as an approval that seems to have
vanished.

The general shape is worth naming, because it is what changes when you move from verbs to
adjectives: **a mistake stops being an event and becomes a condition.** An imperative script with a
bug fails once, loudly, at a moment you can point to in a log. A declarative document with a bug is
true every second until somebody edits it.

## In production

**What a professional does.** Keeps the manifests in the repository, reviews them like code, and
treats `kubectl edit` on a live cluster as an incident tool rather than a workflow — because an edit
that is not in the file will be reverted the next time somebody applies the file, at a time nobody
chose.

**What degrades at scale.** The number of loops. One Deployment is one loop and is easy to reason
about; a real cluster has loops for Deployments, ReplicaSets, Pods, Services, endpoints, autoscalers
and half a dozen controllers somebody installed, all reacting to each other's output. Almost every
confusing thing that happens after that point yields to one question: *which loop is trying to make
which sentence true?*

**The failure that only shows with real traffic.** Two sources of truth. Somebody scales a
Deployment by hand during an incident, it helps, and the change lives only in the cluster. Weeks
later a routine apply from the repository silently undoes it, because the file still says the old
number and the file is what the loop believes. The fix is not discipline; it is that the emergency
change must land in the file before the incident is closed.

**The review comment a senior engineer leaves:** *"Put the reason for `replicas: 1` in the file, not
in the pull request. The pull request will be unfindable in six months and the file is what somebody
will be looking at when they decide to raise it."*

**The interview question:** *"What is the difference between declarative and imperative
deployment?"* The answer that shows experience does not stop at *"you describe the end state"*. It
says what that costs: a wrong description is enforced rather than executed, so the blast radius of a
typo is measured in time rather than in one failed run.

## Check yourself

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python check.py | head -4
```

That command reads the same document a cluster would be handed. Say what it can tell you and what it
cannot — there is a whole category of thing it will never catch, and part
[3.1](../03-what-the-manifest-must-say/3.1-checking-what-the-cluster-would-read.md) names it.

Now open `k8s/deployment.yaml` and find every line that is an adjective and every line that is a
noun. There are no verbs in the file at all. That is not a stylistic observation; say what it
implies about how a mistake in it behaves.

**Out loud, without scrolling up:** what changes about a bug when it moves from a script into a
declarative document?
