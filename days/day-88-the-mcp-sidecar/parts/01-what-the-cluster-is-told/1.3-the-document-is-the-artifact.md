# 1.3 — The document is the artifact

## One-line answer

The thing you ship to a cluster is a YAML file, which means the deployment can be read, reviewed and
checked before anything runs — and on a machine with no cluster at all, that file is still the whole
deliverable rather than a description of one.

## The story

The care label sewn into a shirt.

Nobody who washes that shirt will ever speak to whoever made it. The label is the entire
conversation: cold wash, do not tumble dry, iron on the reverse. It travels with the garment, it is
readable by a person and by a laundry, and it is what actually gets acted on.

Which is why a wrong label is worse than no label. *Machine wash warm* on something that shrinks
does not produce an argument or a warning. It produces a smaller shirt, six weeks later, done
correctly by somebody following instructions.

## The idea in plain language

`kubectl apply -f deployment.yaml` sends a document to an API server. That is the whole interaction.
There is no build step, no compilation and no interpretation of intent: the file is parsed, the
objects in it are created or updated, and the control loops take over.

Three things follow, and together they are the reason this day has something to teach on a laptop
with no cluster on it.

**The file is reviewable.** It is text, it goes in the repository, and a person can read it in a
pull request. Every property that matters — which containers, which images, which secrets, which
limits — is visible in the diff.

**The file is checkable by a program.** It is YAML, and YAML has parsers. Any property a reviewer
could check by reading, a script can check every time. That is section
[3](../03-what-the-manifest-must-say/3.1-checking-what-the-cluster-would-read.md).

**The file is the thing that is wrong when something is wrong.** Not the cluster's state, which is
downstream of it. Debugging a Kubernetes deployment nearly always ends at a line in a document.

There is one honest limit, and it is worth stating before the rest of the day leans on this. A
parser tells you the document is *well formed*. It does not tell you the API server would *accept*
it: that needs the schema, and the schema lives in the cluster. `kubectl apply --dry-run=server`
is the command that asks, and it needs a cluster, and there is not one here.

## Why Sutra needs it

Because OPS-18 says the deploy artifact must be reproducible from a cold start — somebody with this
repository and the two binaries gets a running system by following one document. That is a claim
about a file, and it is checkable without running anything.

And because of what this machine does not have. There is no `kubectl`, no `kind`, no `k3d` and no
`docker` here, which part [5.1](../05-what-did-not-run/5.1-taught-on-dry-land.md) is entirely about.
If the deliverable of a deployment day were a running cluster, this day would have nothing to show.
The deliverable is the document, and the document is real, complete, and checkable — so most of the
day's work is genuinely done, and the part that is not is named rather than faked.

## The mechanism

Reading the file the way the cluster reads it is three lines:

```python
def load(path: Path) -> list[dict]:
    """Every document in one file, in order, the way `kubectl apply -f` reads it."""
    return [d for d in yaml.safe_load_all(path.read_text(encoding="utf-8")) if d]
```

**Line by line:**

- `safe_load_all`, not `safe_load`. A Kubernetes file holds several objects separated by `---`, and
  `safe_load` on a multi-document file raises `yaml.composer.ComposerError`. The split manifest in
  this lab has three objects in it, so this is not a hypothetical.
- `safe_load_all` rather than `load_all`: the unsafe loader can construct arbitrary Python objects
  named in the document, which is a remote code execution primitive when the document came from
  anywhere but your own hands. There is no reason to ever use it on a manifest.
- `if d` drops the `None` that a trailing `---` or a comment-only document produces. A file that
  ends with a separator is legal and common, and without this the checker would trip over an empty
  object.
- `encoding="utf-8"` explicitly, because on Windows `read_text` defaults to the system code page and
  a manifest containing a non-ASCII annotation would round-trip differently depending on the
  machine.
- The return type is a list of plain dicts. There is no Kubernetes schema here and none is pretended
  — every check downstream is a statement about a nested dictionary, which is exactly as much as a
  parser can honestly give you.

And here is the document itself — the Pod that this day is about. This is the complete container
list from `k8s/deployment.yaml`, with the two containers side by side:

```yaml
      initContainers:
        - name: sutra-mcp
          image: sutra-mcp:0.1.0
          imagePullPolicy: Never
          restartPolicy: Always
          ports:
            - containerPort: 8000
          startupProbe:
            httpGet:
              path: /healthz
              port: 8000
            periodSeconds: 1
            failureThreshold: 30
      containers:
        - name: sutra-api
          image: sutra-api:0.1.0
          imagePullPolicy: Never
          ports:
            - containerPort: 8080
          env:
            - name: SUTRA_MCP_URL
              value: http://127.0.0.1:8000/mcp
            - name: GOOGLE_API_KEY
              valueFrom:
                secretKeyRef:
                  name: sutra-secrets
                  key: google-api-key
```

Six decisions are visible in that fragment without running anything: the MCP server is a sidecar
(`initContainers` plus `restartPolicy: Always`), it is gated on a `startupProbe`, both images are
pinned and never pulled, the agent dials loopback, and the credential arrives by reference. Each of
those is a check in part
[3.1](../03-what-the-manifest-must-say/3.1-checking-what-the-cluster-would-read.md), and each is a
thing a reviewer could have caught by reading — which is exactly why it is worth making a program do
it every time.

## When it breaks

The failure is a document that parses perfectly and describes something else. Two flavours, both
real.

**The one the parser catches.** A multi-document file read with the wrong function:

```text
yaml.composer.ComposerError: expected a single document in the stream
  in "k8s/deployment-split.yaml", line 5, column 1
but found another document
  in "k8s/deployment-split.yaml", line 67, column 1
```

Loud, immediate, and it even names both line numbers. Not interesting except that it is the reason
`safe_load_all` is there.

**The one nothing catches.** A field name that is not a field. Kubernetes objects are validated
against a schema *by the API server*, so `restartPolicy: always` — lower case — or
`startUpProbe` instead of `startupProbe` is caught there. But this machine has no API server, so:

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python check.py | head -4
```

Measured on 2026-09-07:

```text
manifest: k8s/deployment.yaml
1 document(s); Deployment/sutra-api
containers: [('sutra-api', 'app'), ('sutra-mcp', 'sidecar')]
```

The checker read the file, found the Deployment, and classified both containers. It would have done
exactly the same on a file with `startUpProbe` in it — the key would simply be absent from the dict,
the startupProbe check would fail, and the message would say *"no startupProbe"* rather than *"you
typed the name wrong"*. That is a real limitation of checking a schema-less parse, and the honest
answer to it is a `TODO(me)` in the hub with the exact command: `kubectl apply --dry-run=server -f
deploy/k8s/deployment.yaml`, **not run here, because there is no server to dry-run against.**

## In production

**What a professional does.** Puts the manifests under version control next to the code, runs a
schema validator in the same pipeline as the linter, and treats a manifest change as a code change —
same review, same tests. The tooling for this is mature and the names change every eighteen months;
the practice does not.

**What degrades at scale.** Repetition. The same Deployment for three environments becomes three
almost-identical files, then a templating layer, then a templating layer nobody can read. The
pressure is real and the failure mode is that the artifact stops being the thing you can read — you
are now reviewing a template and guessing at its output. Whatever tool wins, the rule that survives
is: **be able to print the document that will actually be applied,** and check that.

**The failure that only shows with real traffic.** Drift. The file says one thing, the cluster
contains another, because somebody edited live during an incident. Nothing reports this until the
next apply silently reverts it. The mitigation is a periodic diff of the cluster against the
repository, and treating a non-empty diff as an alert rather than as normal.

**The review comment a senior engineer leaves:** *"This is a deployment, so review it like one. I
want the image tag, the resource limits and where the secret comes from visible in the diff — if I
have to run a template to find out, the artifact is the wrong shape."*

**The interview question:** *"How do you test a Kubernetes manifest?"* The answer that shows
experience gives three layers and says what each catches: a parser catches malformed YAML, a schema
validator catches fields the API server would reject, and a policy check catches the things that are
valid and wrong — no limits, a `latest` tag, a secret in plain text. Only the third one is about
your system.

## Check yourself

```bash
cd days/day-88-the-mcp-sidecar/lab
uv run python check.py | head -4
uv run python -c "import yaml; print(len(list(yaml.safe_load_all(open('k8s/deployment-split.yaml')))))"
```

The second command counts the objects in the split manifest. Say why that number is not one, and
what `yaml.safe_load` would have done with the same file.

Now introduce a deliberate typo: change `startupProbe` to `startUpProbe` in `k8s/deployment.yaml`,
run `check.py`, read the message it gives, and say what it would have taken to get a message that
named the real mistake. Then put it back.

**Out loud, without scrolling up:** three layers of manifest checking, and which of them this
machine can run.
