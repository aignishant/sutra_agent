# 3.2 — 💥 The handle anyone can guess

## One-line answer

A task id that counts upwards is a directory of every other customer's jobs, and the server that hands
one out has built an access-control hole that no authentication in front of it can close.

## The story

You collect a parcel from one of those metal lockers outside a supermarket.

The screen asks for a code, you type the six digits from the text message, and door 14 pops open. While
you are getting your box out you notice the number on the screen was just *your locker number* with two
digits in front of it, and out of idle curiosity you type the number one higher.

Door 15 opens. There is a parcel in it. It is not yours.

Nothing here was hacked. You did not break a lock or steal a code. The system worked exactly as
designed — you asked for a locker by its number and it opened the locker with that number. The mistake
was made long before you arrived, by whoever decided that the way to name a locker was to count.

## The idea in plain language

Part [3.1](3.1-a-name-the-server-mints.md) said a handle must be **server-minted** and **opaque**. Those
two words are in the specification. A third word is not, and it is the one that matters most in
practice: **unguessable**.

The specification says the handle is minted by the server and must not be interpreted by the client. It
does not say it has to be hard to guess, because that is not a protocol property — it is your
implementation's job. Which means a fully compliant server can hand out `task-1041`, `task-1042`,
`task-1043`, and the protocol has no complaint at all.

Two separate mistakes produce the hole, and they are often made together:

**A sequential id.** If ids count upwards, then holding one id tells you where all the others are. You
do not need to break anything; you enumerate. This has a name in web security — an insecure direct
object reference — and it is one of the oldest bugs there is, because counting is the most natural way
in the world to name things.

**No ownership check.** Even a perfectly random id is only a secret, and secrets leak: into browser
history, into shared logs, into a screenshot in a support ticket. The row has to record **who** the task
belongs to, and every read has to check that the caller is that party. Without the check, possession of
the string is the whole of the authorisation.

The two defences are different in kind, which is why you need both. Randomness makes ids hard to
*find*. Ownership makes a found id useless. A system with only randomness is one leaked log away from a
breach; a system with only ownership is fine right up until the owner field is compared against
something the caller controls.

And the third defence, which costs nothing and is skipped surprisingly often: **the error message for
"not yours" must be identical to the error message for "does not exist"**. If they differ, the difference
is an oracle. A caller can walk the id space and learn which ids are real without ever reading one, and
"which ids are real" is most of what an attacker wants to know.

The word for the situation this protects is **multi-tenancy**: one deployment serving several
independent customers, whose data must not meet. A support desk running Sutra for two client companies
is multi-tenant whether or not anybody used the word when it was built.

## Why Sutra needs it

Because the handle is about to be a public argument on a public tool, and once it is, guessing it is a
supported operation.

**Day 40** builds tool filtering and allowlists, and states the posture: a tool is a capability handed
to a model, and the model's input is partly attacker-controlled. A model that can be steered into
calling `tasks/get` with an id it invented is a model with an enumeration primitive, and the only thing
standing between that and someone else's data is the shape of the id.

**Day 37** adds authentication. It is worth being precise about what that will and will not fix:
authentication establishes *who is calling*. It does nothing about *what they may name*. A correctly
authenticated caller asking for `task-1042` is still asking for someone else's task, and only the
ownership check refuses.

**Day 45** audits the whole MCP surface as the Phase 6 gate. A sequential task id is exactly the finding
that audit exists to catch, and it is much cheaper to not write it today.

## The mechanism

Two stores, two naming schemes, and an attacker doing the least sophisticated thing available:

```python
# days/day-36-long-jobs-and-tasks/lab/tenancy.py  (extract)
TENANTS = ["acme", "globex"]
PER_TENANT = 5


def sequential_store() -> dict[str, str]:
    """taskId -> owner, with ids handed out in order."""
    counter = itertools.count(1041)
    return {f"task-{next(counter)}": tenant for tenant in TENANTS for _ in range(PER_TENANT)}


def random_store() -> dict[str, str]:
    return {
        f"tsk_{secrets.token_urlsafe(16)}": tenant for tenant in TENANTS for _ in range(PER_TENANT)
    }
```

**Line by line:**

- `TENANTS` is two customers of one deployment. The whole point of the demo is that they are in the same
  store, because that is what shared infrastructure means.
- `itertools.count(1041)` starts at an arbitrary number rather than at 1, because that is what a real
  sequence looks like after a few weeks and it removes the temptation to think "well, ours starts high
  so it is fine". Starting high buys nothing: the attacker starts from an id they legitimately hold.
- The dict comprehension interleaves the tenants — five for `acme`, then five for `globex` — so their
  ids are **adjacent**. That is not a contrivance; it is what happens when two customers use a service
  on the same afternoon.
- `secrets.token_urlsafe(16)` in the second store is the only difference between the two functions.
  Same rows, same owners, same count, different naming scheme.
- Neither function stores anything about the task itself. The demo needs only `taskId -> owner`, because
  the question being asked is "who can reach which row", and the contents are irrelevant to it.

```python
def probe(store: dict[str, str], attacker: str, guesses: list[str], check_owner: bool) -> int:
    """How many of the attacker's guesses return somebody else's task."""
    leaked = 0
    for guess in guesses:
        owner = store.get(guess)
        if owner is None:
            continue
        if check_owner and owner != attacker:
            continue
        leaked += 1
    return leaked
```

**Line by line:**

- `guesses` is a plain list of strings. There is no cleverness here at all — no timing attack, no
  cryptography, no fuzzing. Someone types a number one higher.
- `store.get(guess)` is the server's lookup, unchanged from part 3.1. The vulnerability is not in this
  line and never is; it is in what the ids look like and in what happens next.
- `if check_owner and owner != attacker: continue` is the **entire fix**, expressed as a flag so both
  worlds can be measured. In `sutra_mcp` it is an `and` in a conditional and it is two lines of code.
- `leaked += 1` counts rows the attacker successfully reached. It is a count rather than a boolean
  because "how many" is the number that makes a security finding land in a review; "yes" is arguable
  and "ten of ten" is not.
- The function deliberately does not distinguish *the attacker's own* rows from *other people's*. The
  main routine does that afterwards, which keeps this function honest about what it measures: reachable
  rows, not stolen ones.

```python
def main() -> int:
    seq = sequential_store()
    mine = [h for h, owner in seq.items() if owner == "acme"][0]
    base = int(mine.split("-")[1])
    guesses = [f"task-{n}" for n in range(base - 5, base + 10)]
    leaked_seq = probe(seq, "acme", guesses, check_owner=False)
```

**Line by line:**

- `mine` is a handle the attacker **legitimately holds**. This is the realistic starting position: not a
  stolen credential, just a customer who has used the service once.
- `base = int(mine.split("-")[1])` is the client parsing an opaque handle — the thing part 3.1 said
  clients must not do. Here it takes one line, which is the practical measure of how strong that "must
  not" is when the string is a number.
- `range(base - 5, base + 10)` is fifteen guesses, chosen to be small enough to type by hand. There is
  nothing to stop it being fifteen million.
- `check_owner=False` runs the version of the server that trusts possession of the string. This is the
  arm that fails, and it fails without a single error being raised.
- `main` returns an `int` so the script has an **exit code**: this is an eval that can go red, and red is
  its correct state while the sequential store exists.

Run it:

```bash

```

**Line by line:**

- From the repository root. **Zero model calls**, no network. `echo "exit: $?"` prints the exit code,
  because the finding is the exit code and not the prose.

Measured on 2026-09-04:

```text
sequential handles, no owner check
  attacker holds     : task-1041
  guesses tried      : 15
  tasks reachable    : 10 of 10
  belonging to globex: 5

random handles, owner checked
  guesses tried      : 15
  tasks reachable    : 0 of 10

findings: 1
exit: 1
```

**Ten of ten.** Fifteen guesses, typed by a customer with one legitimate handle, reached every task in
the deployment — including all five belonging to the other company. The second arm made the same fifteen
guesses against a store the same size and reached nothing.

The scene format, because this is the failure lab of the day:

> 🎬 **The scene:** two customers, one `sutra_mcp` deployment, task ids that count upwards.
> 😬 **The naive fix:** "the ids are internal, nobody will see them" — and later, "we will add
> authentication".
> 💥 **Why it fails:** the ids are not internal, they are returned to the client and passed back as an
> ordinary tool argument, which is exactly where a model or a user can see and change them. And
> authentication answers *who is calling*, not *what they may name*: a properly authenticated `acme`
> asking for `task-1046` is still asking for `globex`'s job.
> 💡 **The insight:** a name that can be guessed is a name that will be, so an identifier does two jobs
> — it locates a row, and it must not locate anybody else's. Randomness makes ids hard to find;
> ownership makes a found id useless. Neither one alone is a control.

## When it breaks

In the wild this does not surface as an error. It surfaces as a support ticket in the wrong voice:

```text
Subject: why can I see a re-index for "globex"?
The status page showed a job I don't recognise after I refreshed. Screenshot attached.
```

No exception, no `500`, nothing in the error dashboard. The server did what it was asked. The only
signal is a human being confused, and by the time that human writes in, the audit question — *how many
times has this already happened?* — usually has no answer, because a successful read of another
tenant's row logs exactly like a successful read of your own.

If the ownership check is added but the messages are left different, the failure changes shape rather
than going away:

```text
{"error": {"code": -32602, "message": "task tsk_9Fq2mR7wZk4bT1cs belongs to another tenant"}}
```

That message refuses the read and confirms the id is real, which is most of the value of a probe. The
correct message is the one part 3.1 used for both cases: `unknown task <id>`, identical whether the row
is missing or forbidden.

## In production

**What a professional writes instead:** `secrets.token_urlsafe(16)` or a UUID version 4, an `owner`
column written at creation, an ownership predicate in the query itself rather than in an `if` after it
— `WHERE task_id = ? AND owner = ?` — and one not-found error for both misses. The predicate belongs in
the query because an `if` after the read is a check somebody can forget to copy into the next handler,
while a `WHERE` clause travels with the statement.

**What degrades at scale and under concurrency:** enumeration gets cheaper as you get bigger. More
customers means denser id space, so a random guess in a sequential scheme is more likely to hit
something real. Rate limiting helps and does not solve it: the attacker with one valid handle needs a
handful of guesses, not a flood, and a handful of requests looks exactly like normal use. The only
thing that scales is making the space too large to walk — 128 bits of randomness — and making a hit
useless without ownership.

**The review comment a senior engineer leaves:** *"`task_id` is sequential and there is no owner column.
Two separate problems: the ids are enumerable, and nothing stops one tenant reading another's job.
Random token, owner on the row, ownership in the `WHERE` clause, and the same not-found message for both
misses. 'Our own client would never do that' is not a control — the client is not the only thing that
can send us a string."*

**The interview question:** *"what makes a task id safe?"* An honest answer: *"two things, and people
usually only say the first. It has to be unguessable — a cryptographically random token, not a counter —
because otherwise holding one id gives you every id. And the row has to record an owner that is checked
on every read, because an id is only a secret and secrets end up in logs and screenshots. I would add a
third that costs nothing: the 'not yours' error and the 'does not exist' error must be the same message,
or the difference between them tells an attacker which ids are real. I measured the bad version — one
legitimate handle, fifteen guesses by hand, every task in the deployment reachable including the other
customer's."*
