# 3.3 — Sutra's handle policy

## One-line answer

Sutra's handles are `tsk_` plus 128 bits of `secrets` randomness, owned by the caller who created them,
written with an expiry, and missing in exactly one way — and the policy is written as a check with an
exit code so that the code cannot drift away from it silently.

## The story

You take a used car to a mechanic before you buy it, and he gives you back a sheet of paper.

It is not an opinion. It is a list with a box beside each item and two of the boxes are red: the rear
tyres are below the legal tread depth, and one of the brake discs is worn past its limit. Everything
else is ticked. He does not say the car is bad and he does not say it is good. He says *here is what
does not meet the standard, and here is the standard it does not meet.*

That sheet is worth more than an opinion for two reasons. You can hand it to the seller. And you can
bring the car back next month, run the same sheet, and know whether anything has moved — which you
cannot do with a conversation you had in a car park.

## The idea in plain language

Day 32's part
[3.4](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md)
ended with a `TODO(me)`: decide Sutra's handle policy — how it is generated, who owns it, when it
expires, and what error an unknown handle returns. Parts [3.1](3.1-a-name-the-server-mints.md) and
[3.2](3.2-the-handle-anyone-can-guess.md) gave you the evidence. This part is the decision, and the
form the decision takes.

**Sutra's handle policy, in five rules.**

| # | Rule | What it says |
| --- | --- | --- |
| 1 | **Unguessable** | A handle is `tsk_` followed by `secrets.token_urlsafe(16)` — at least 128 bits of randomness. Never a counter, never derived from the arguments, never chosen by the client. |
| 2 | **Owned** | Every row carries an `owner`, recorded at creation from the caller's authenticated identity. Every read and every write filters on it. |
| 3 | **Expiring** | Every row is written with a `ttl_ms` at creation. Nothing is stored without an end date, and a sweep deletes rows past theirs. |
| 4 | **The miss is the client's fault** | An unknown handle returns JSON-RPC `-32602`, *Invalid params* — never `-32603`, *Internal error*, and never an HTTP 500. |
| 5 | **The miss says nothing** | Not-found, not-yours and expired return **byte-identical** errors. The message names the handle the caller supplied and nothing else. |

Four of those five have already been argued for in this section. The one that has not is rule 3, and it
is the one people leave out, so it is worth stating why it is not optional.

A session used to end. When a connection dropped, everything hanging off it was garbage. A handle has
no such event: nothing tells the store that a client has lost interest, gone home, or been uninstalled.
So without an expiry the task table has exactly one behaviour — it grows, forever, and the failure
arrives as a disk alert on a machine nobody associates with a decision taken in a tool signature.

**What `ttl_ms` actually promises.** It is not a countdown to deletion of the work. It is the period for
which the server promises the handle will still resolve, and it is the same field the Tasks extension
calls `ttlMs` and returns to the client so the client knows how long its stored id is worth keeping.
Two rows deserve different values, and choosing them is a real decision rather than a constant:

- an **unfinished** task's handle only has to outlive a plausible client outage;
- a **terminal** task's handle has to outlive however long the client might take to come back and read
  the result, which is longer.

**Where the policy lives.** Not in a comment, and not in this document. A rule that exists only in prose
is a rule that quietly stops being true, because nothing ever fails when someone breaks it. So the
policy is written as a script with an exit code — five checks over the real minting and fetching
functions — and it is **red as shipped**, because two of the five rules are deliberately unimplemented.
Making it green is the build brief.

That is the same instinct as Day 31's `./m check`: a standard you can run is a standard, and a standard
you can only quote is a preference.

## Why Sutra needs it

Because three later days will each assume a different one of these rules and none of them will say so.

**Day 37** adds authentication, which is where rule 2's `owner` finally has something real to hold. Until
then it is a string in a demo; after Day 37 it is the authenticated caller. Writing the column now means
Day 37 fills a field rather than migrating a table.

**Day 43** deploys `sutra_mcp` statelessly, which is where rule 3 stops being tidiness. Instances come
and go; the store persists across all of them and is the only thing that accumulates.

**Day 45** is the Phase 6 audit, and it audits the files these days built. A policy that already has a
runnable check is a policy that audit can call rather than re-derive.

## The mechanism

The implementation under test, deliberately incomplete:

```python
# days/day-36-long-jobs-and-tasks/lab/policy.py  (extract)
CHECK_OWNER = False  # rule 2: not implemented yet
TTL_MS: int | None = None  # rule 3: not decided yet
HANDLE_BYTES = 16
UNKNOWN_CODE = -32602

STORE: dict[str, dict[str, object]] = {}


def mint(owner: str) -> str:
    handle = f"tsk_{secrets.token_urlsafe(HANDLE_BYTES)}"
    STORE[handle] = {"owner": owner, "ttl_ms": TTL_MS, "status": "working"}
    return handle


def fetch(handle: str, caller: str) -> dict[str, object]:
    row = STORE.get(handle)
    if row is None:
        return {"error": {"code": UNKNOWN_CODE, "message": f"unknown task {handle}"}}
    if CHECK_OWNER and row["owner"] != caller:
        return {"error": {"code": UNKNOWN_CODE, "message": f"unknown task {handle}"}}
    return {"status": row["status"]}
```

**Line by line:**

- `CHECK_OWNER = False` and `TTL_MS = None` are the two unimplemented rules, hoisted to the top as
  named constants so that the gap is visible rather than buried. A missing feature that has a name is a
  decision; a missing feature with no name is an oversight.
- `HANDLE_BYTES = 16` is rule 1 as a number you can change. Sixteen bytes of `token_urlsafe` is 128
  bits, and the checker below computes that rather than trusting the comment.
- `UNKNOWN_CODE = -32602` is rule 4, also as a constant, so the check can compare against the policy
  instead of against a literal buried in two places.
- `mint` writes `owner` and `ttl_ms` into the row **even though `ttl_ms` is `None`**. Writing the field
  with a null is what makes the gap detectable; leaving the key out entirely would make the check ask a
  question about a schema instead of about a value.
- The two `return` statements in `fetch` are **character-for-character identical**. That is rule 5, and
  it is the reason they are not factored into a helper — a reader has to be able to see that they are
  the same without following an indirection.
- `fetch` takes `caller` and currently ignores it unless `CHECK_OWNER` is on. The parameter is there
  first, on purpose: adding a parameter later means changing every call site, and a signature that
  already asks for the identity is a signature that invites the check.

The policy itself, as five checks:

```python
def entropy_bits(handle: str) -> float:
    """Bits of randomness in the part of the handle after the prefix."""
    random_part = handle.split("_", 1)[1]
    return len(random_part) * math.log2(64)  # token_urlsafe is base64url


def findings() -> list[str]:
    out: list[str] = []
    mine = mint("desk@sutra")
    theirs = mint("other@corp")

    # 1 - unguessable: at least 128 bits, so the space cannot be walked
    if entropy_bits(mine) < 128:
        out.append(f"rule 1: handle carries {entropy_bits(mine):.0f} bits, policy wants >= 128")

    # 2 - owned: a handle minted for one caller is unknown to any other
    if "error" not in fetch(theirs, "desk@sutra"):
        out.append("rule 2: a caller can read a handle it does not own")

    # 3 - expiring: every row is written with a ttl, in milliseconds
    if STORE[mine]["ttl_ms"] is None:
        out.append("rule 3: handles are minted with no ttl_ms - the table only grows")
```

**Line by line:**

- `entropy_bits` counts the characters **after** the prefix and multiplies by `log2(64)`, because
  `token_urlsafe` emits base64url — sixty-four possible characters, so six bits each. It measures the
  handle rather than trusting `HANDLE_BYTES`, which is the difference between a check and a comment:
  someone shortening the token later will be caught.
- `mine` and `theirs` are minted for two different owners, which is the smallest possible multi-tenant
  situation and the one part 3.2 measured at scale.
- Rule 2's check reads **`theirs` as `desk@sutra`** and asserts that an error comes back. It is written
  as "there must be an error", not "there must be the right data", because the correct behaviour is a
  refusal and refusals are easy to forget to test.
- Rule 3 inspects the stored row rather than the return value, because a TTL is a property of what was
  **written**, and a server that returns a `ttlMs` it never persisted has told the client a comfortable
  lie.
- Each finding is a sentence naming the rule number and what is wrong. A findings list that says
  `False` is a check; a findings list that says *"handles are minted with no ttl_ms — the table only
  grows"* is a check somebody can act on without opening the file.

```python
    # 4 - the miss is the client's fault, not the server's
    code = fetch("tsk_nope", "desk@sutra")["error"]["code"]  # type: ignore[index]
    if code != -32602:
        out.append(f"rule 4: unknown handle returns {code}, policy wants -32602")

    # 5 - the miss says nothing a prober can use
    message = fetch(theirs, "desk@sutra").get("error", {}).get("message", "")  # type: ignore
    if "other@corp" in str(message):
        out.append("rule 5: the not-found message leaks the real owner")

    return out
```

**Line by line:**

- Rule 4 fetches a handle that was never minted — `tsk_nope` — which is the honest way to produce a
  miss. Asserting on `-32602` rather than "some error" matters because `-32603` would page an on-call
  engineer for a client typing the wrong string.
- `# type: ignore[index]` appears because the return type is a loose dict and the checker cannot know
  the `"error"` key is present here. It carries a reason, which is the only way a suppression is
  allowed: the alternative is a `TypedDict` for a fifteen-line demo, which is more machinery than the
  idea needs.
- Rule 5 checks the **message** rather than the code, and it looks for the other tenant's identifier
  specifically. It passes today only because rule 2 is off and the message never mentions an owner; it
  is written now so that it is already there when somebody implements rule 2 with a helpful error
  string.
- `return out` — a list, not a boolean. The count is what `main` turns into an exit code, and the
  sentences are what a human reads.

**Line by line:**

- From the repository root. **Zero model calls**, no network. The exit code is the result; the printed

Measured on 2026-09-04:

```text
  rule 2: a caller can read a handle it does not own
  rule 3: handles are minted with no ttl_ms - the table only grows
findings: 2
exit: 1
```

**Red, on purpose, and red for exactly the two rules that are unimplemented.** Rules 1, 4 and 5 pass
because the minting function already uses `secrets`, already returns `-32602`, and already has two
identical error messages. That is what a good policy check looks like on a half-finished system: it is
specific about what is missing and silent about what is fine.

## When it breaks

The interesting break is the one where the check goes green and the system is still wrong. Set
`CHECK_OWNER = True` and `TTL_MS = 3_600_000` and the script prints `findings: 0`, `exit: 0` — and the
production server can still lose every task, because a `ttl_ms` written into a row does nothing on its
own. Something has to read it and delete.

That failure is quiet for weeks and then loud:

```text
sqlite3.OperationalError: database or disk is full
```

The disk fills, every write fails, and the traceback points at whatever happened to be writing when the
last byte went. Nothing in it mentions tasks. The TTL was recorded faithfully in every row and never
enforced, which is the difference between **writing a policy down** and **implementing it**.

The second break is rule 5 undone by helpfulness. Somebody implements ownership and, wanting a useful
error, writes:

```text
{"error": {"code": -32602, "message": "task tsk_9Fq2mR7wZk4bT1cs is owned by other@corp"}}
```

The check catches it, which is the entire reason rule 5 is in the script rather than in a comment.
Without the check, that message ships, and it is a better enumeration oracle than the sequential ids
part 3.2 measured — it confirms the handle exists *and* names the customer.

## In production

**What a professional writes instead:** the policy is a test, not a script — it lives in `tests/` and
runs in CI on every commit, against the real `sutra_mcp/tasks.py` rather than against a copy of it. The
five rules become five test functions with names that read as sentences, so a failure in CI says
`test_unknown_handle_is_invalid_params` rather than `assert -32603 == -32602`. The sweep that enforces
rule 3 is a scheduled job with its own alert, because a cleanup that silently stops running is
indistinguishable from a cleanup that is working.

**What degrades at scale and under concurrency:** every rule here costs something once there is real
traffic. The ownership predicate adds a column to an index. The TTL sweep is a delete over a large table
and will lock rows if written naively, so it runs in batches. And the expiry itself becomes a
negotiation with users: too short and a client that was offline overnight loses a result it was
promised; too long and the table is the biggest thing you own. The number is a product decision wearing
an engineering hat, which is why the build brief asks you to write down the reasoning, not just the
value.

**The review comment a senior engineer leaves:** *"The policy is in a doc, so in three months it will be
whatever the code happens to do. Turn those five rules into tests in `tests/` and wire them into
`./m check`. And separate the two TTL cases — an abandoned unfinished task and a completed result a
client has not collected are not the same row and should not have the same lifetime."*

**The interview question:** *"how do you decide how long a task handle lives?"* An honest answer: *"first
by noticing that you have to decide at all — a session ended when the connection dropped, and a handle
has no equivalent event, so if you write no expiry the table grows forever and you find out through a
disk alert. Then I would split it: an unfinished task's handle needs to outlive a plausible client
outage, and a completed task's result needs to outlive however long a client might take to come back
and read it, which is longer. The part I would emphasise is that writing a TTL into the row is not the
same as enforcing it — you need a sweep, and the sweep needs an alert, because a cleanup job that quietly
stops running looks exactly like one that is working."*
