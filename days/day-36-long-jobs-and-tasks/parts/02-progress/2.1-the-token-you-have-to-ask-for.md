# 2.1 — The token you have to ask for

## One-line answer

A server may only send progress updates for a request whose `_meta` carried a `progressToken`, so
progress is something the **caller opts into** — and a caller that forgets gets silence that looks
exactly like success.

## The story

You register at a clinic and the receptionist turns the screen towards you.

There is a box on the form marked *mobile number, for updates*. You are in a hurry, the queue behind
you is long, and it is not marked as required, so you skip it and sit down.

Two hours later you are still sitting there. Everyone who came in after you seems to know something you
do not: one of them got up and walked to room four without being called, another checked her phone and
said "twenty minutes" to her husband. Yours never buzzed, because there is no number to send anything
to. Nobody made a mistake. The clinic is not broken. Your appointment is going to happen exactly as it
would have anyway.

The only difference between you and the woman who knew is one empty box on a form, filled in before any
of it started.

## The idea in plain language

MCP has a message whose only job is to say *"still going, this far along"*. It is a **notification** —
a JSON-RPC message with no id, which means no reply is expected and none is possible — and it is
called `notifications/progress`.

The rule that decides whether you ever see one is in the specification, and it is worth reading before
the mechanism (`https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/progress`,
read 2026-09-04):

> *"When a client wants to receive progress updates for a request, it includes a `progressToken` in the
> request metadata."*
>
> *"Progress tokens **MUST** be a string or integer value."*
>
> *"Progress tokens can be chosen by the client using any means, but **MUST** be unique across all
> active requests."*

Three things follow from those sentences, and all three surprise people.

**The client decides, not the server.** A server cannot volunteer progress. It has no address to send
it to unless the caller supplied one, and the address *is* the token — the notification carries the
token back so the client knows which of its in-flight requests the update belongs to.

**The token is the client's to invent.** It is not issued by the server, not derived from anything, and
not meaningful to anyone but the client. The only constraint is uniqueness among the requests that
client currently has open, because otherwise two jobs' updates would be indistinguishable.

**Everything about it is optional on the server's side.** The specification says the server **MAY** send
notifications, **MAY** send them at whatever frequency it likes, and **MAY** omit the total. A server
that receives a perfectly good token and sends nothing at all is fully compliant.

Where the token goes matters, and it is the same `_meta` block Day 32 part
[2.3](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.3-every-request-introduces-itself.md)
introduced: `_meta` sits **inside `params`**, beside `name` and `arguments`, and it is the open
extension point where per-request metadata rides. `progressToken` is one key in it.

A word on **notification** versus **response**, because the difference is what makes progress cheap. A
response has an id and answers exactly one request; a notification has no id, expects nothing back, and
can be sent any number of times. Progress is a stream of notifications flowing back while one request
is still unanswered — which is only possible because the request's reply has not been sent yet.

And that is the sentence to hold on to for the next two parts: progress exists **inside the lifetime of
one request**. It is not a thing you can go and look at later.

## Why Sutra needs it

Because Sutra is going to have exactly one tool where the difference between "slow" and "hung" matters
to a person watching.

**Day 49** builds the embedding index. When somebody triggers that from a desk interface, the honest
answer to *"is it working?"* is either a progress bar or a shrug, and a shrug makes people press the
button again — which is the duplicate-work problem from part
[1.3](../01-the-blocking-call/1.3-work-with-no-name.md) arriving through the user rather than through
the network.

**Day 73** runs that index build on a schedule, unattended. Nobody is watching, so nobody wants
progress — and a client that sends no token means the server does no notification work at all. The same
tool serves both callers because the caller decides.

And on this day, immediately: `sutra_mcp/tasks.py` has to decide whether its status reporting goes
through progress notifications, through a pollable handle, or both. Part
[2.3](2.3-progress-is-narration-not-state.md) is where that decision gets made, and it cannot be made
until you know what progress can and cannot do.

## The mechanism

The same tool call, twice, with and without the box on the form filled in:

```python
# days/day-36-long-jobs-and-tasks/lab/progress.py
def call_request(request_id: int, token: str | None) -> dict:
    """The tools/call a client sends, with or without asking for progress."""
    meta: dict[str, object] = {"io.modelcontextprotocol/protocolVersion": "2026-07-28"}
    if token is not None:
        meta["progressToken"] = token
    return {
        "jsonrpc": "2.0",
        "id": request_id,
        "method": "tools/call",
        "params": {
            "name": "reindex_archive",
            "arguments": {"archive": "tickets"},
            "_meta": meta,
        },
    }
```

**Line by line:**

- `token: str | None` is the whole experiment expressed as a parameter. `None` is not an error state
  and not a degraded mode — it is the ordinary case for every tool call you have written so far.
- `meta` always carries `io.modelcontextprotocol/protocolVersion`, because since the 2026-07-28
  revision every request introduces itself. `progressToken` is added *beside* it, which is the point:
  `_meta` is a bag of independent per-request keys, not a fixed struct.
- `if token is not None:` — the key is **absent**, not null, when there is no token. That distinction is
  real: a JSON `null` would be a value the server has to reason about, while an absent key is simply
  nothing to see.
- `"_meta": meta` sits **inside `params`**, next to `name` and `arguments`. Putting it beside `params`
  instead is the single most common mistake with `_meta`, and it fails silently — the server sees a
  request with no metadata and carries on.
- The `id` is here too, and it is worth noticing that the token and the id are different things. The id
  names the message; the token names the *update channel* the client wants opened for it.

```python
def report_progress(request: dict, progress: float, total: float, message: str) -> None:
    """What the server does at each chunk. Mirrors mcp's Context.report_progress."""
    token = request["params"]["_meta"].get("progressToken")
    if token is None:
        return  # the SDK returns here too, and says nothing about it
    delivered.append(
        {
            "jsonrpc": "2.0",
            "method": "notifications/progress",
            "params": {
                "progressToken": token,
                "progress": progress,
                "total": total,
                "message": message,
            },
        }
    )
```

**Line by line:**

- The first thing the function does is **look for the token**, because without one there is nowhere to
  send anything. This is the server's side of the opt-in, and it is a lookup rather than a decision.
- `if token is None: return` is the behaviour to remember. Not an exception, not a warning, not a log
  line — a silent early return. Part [2.2](2.2-reporting-from-inside-a-tool.md) shows that the real SDK
  does exactly this, in the real source.
- The notification has **no `id` field**. That is what makes it a notification rather than a request:
  nothing will answer it, and nothing is waiting for it to be answered.
- `progressToken` is echoed back verbatim. The client matches it against the token it invented, which
  is how it knows which of its five in-flight jobs this update belongs to.
- `progress` and `total` are floats in the schema, not integers, so `0.4 / 1.0` is as valid as
  `4 / 10`. The specification requires `progress` to **increase** with every notification, even when
  the total is unknown — a bar that goes backwards is a protocol violation, not a cosmetic bug.
- `message` is the human-readable half and is optional. It is the field that makes a progress bar
  useful rather than decorative: *"indexed chunk 2 of 4"* tells a support engineer where the job is
  stuck, and `0.5` does not.

Both runs returned `'re-indexed'`. Both were successful tool calls. One produced four notifications and
one produced none, and **nothing in either result says which**. That is the shape of every bug in this
area: the tool works, the answer is right, and the thing that is missing is missing quietly.

## When it breaks

The break that costs an afternoon is not a crash. It is this, in a server's log, and nothing else:

```text
INFO:     127.0.0.1:52344 - "POST /mcp HTTP/1.1" 200 OK
```

A `200 OK`, a correct result, and no progress. You added `await ctx.report_progress(...)` to the tool,
you can see the line in the source, you have put a `print` next to it and watched it execute — and the
client shows nothing. The tool is fine. The client never asked.

Three causes produce that same silence, and they are distinguished by where you look:

| Cause | Where to look | What you will see |
| --- | --- | --- |
| the client sent no `progressToken` | the request's `params._meta` | the key is simply absent |
| `_meta` was put beside `params` instead of inside it | the raw request JSON | `_meta` at the wrong nesting level, no error |
| the client received the notifications and does not display them | the wire, not the server | the notifications are there |

The second row is the one that wastes the most time, because the request is still valid JSON-RPC and
the server still answers it. `_meta` is an open extension point, so an unknown or misplaced key is not
an error — it is just something nobody read.

There is a fourth failure that is louder and rarer, and it comes from the uniqueness rule:

```text
McpError: Received progress notification for an unknown token
```

That is what a client says when a server quotes a token it is not currently waiting on — either because
the request already completed (the specification says notifications **MUST** stop after completion) or
because two in-flight requests were given the same token and the client cannot tell them apart. The fix
for the second is a counter, not a constant.

## In production

**What a professional writes instead:** the token is generated per call from a counter or a UUID, never
hard-coded, and it is logged next to the request id so that a support engineer reading the log can join
a progress update to a job. The tool itself is written so that reporting progress is a **no-op it never
checks the result of** — the work must not branch on whether anybody is listening, or you have two code
paths and only one of them is tested.

**What degrades at scale and under concurrency:** progress notifications are unbounded. A tool that
reports once per ticket over a hundred thousand tickets sends a hundred thousand messages down one
stream, and on stdio they interleave with everything else on the same pipe. The specification says both
parties **SHOULD** implement rate limiting for exactly this reason. The practical rule is to report on
a **fraction of the total** — every one per cent, say — rather than on every unit of work, so that the
message count is bounded by a constant instead of by the size of the archive.

**The review comment a senior engineer leaves:** *"`progressToken` is the string `'reindex'` on every
call. The moment two of these run at once the client cannot tell whose progress is whose, and the spec
says tokens must be unique across active requests. Make it a per-call value and log it beside the
request id — otherwise the first time this matters is an incident."*

**The interview question:** *"how does an MCP server tell a client that a long call is still alive?"* An
honest answer: *"it sends `notifications/progress` on the response stream of that request — but only if
the client put a `progressToken` in the request's `_meta`. That is the part people miss: progress is
opt-in by the caller, and a server with no token silently sends nothing. So a missing progress bar is
usually a missing token, not a broken server. I would also say that progress is advisory: it MAY be
sent, at any frequency, and it stops the moment the request completes, so I would never build anything
load-bearing on top of it."*
