# 2.2 — Reporting from inside a tool

## One-line answer

A tool reports progress by asking for a `Context` parameter and calling `report_progress` on it, and
the installed SDK's implementation of that call **returns silently when the caller sent no token** —
so the reporting code you write is correct whether or not anybody is listening.

## The story

In the back of a warehouse there is a clipboard by the door with a sheet on it, and the rule is that
you tick a box every time a pallet is finished.

You tick the boxes. It costs you two seconds each time and you have never thought about it. What
happens to the sheet afterwards is not your problem: some mornings the supervisor takes a photograph of
it and sends it to the customer, and most mornings she does not, because most customers never asked to
be told.

That arrangement is why the sheet is any use at all. If you had to check, before each tick, whether
today's customer wanted photographs, you would sometimes get it wrong and there would be two ways of
working. Instead there is one way of working and somebody else's decision about what to do with the
result.

## The idea in plain language

Part [2.1](2.1-the-token-you-have-to-ask-for.md) established the protocol half: a client puts a
`progressToken` in `_meta`, and the server may answer with `notifications/progress` messages carrying
that token back. This part is the code half — how a Python tool function actually emits one.

The `mcp` SDK does it through an object called a **`Context`**. A `Context` is the tool's handle on
everything about the current request that is not an argument: which client is calling, what the request
id is, and the channels back to the caller. You do not construct one and you do not fetch one. You
declare that you want it, by adding a parameter annotated with the type, and the SDK fills it in.

The SDK's own docstring says exactly this, in the installed package
(`.venv/Lib/site-packages/mcp/server/fastmcp/server.py`, read 2026-09-04):

> *"It gets injected into tool and resource functions that request it via type hints."*
>
> *"The context parameter name can be anything as long as it's annotated with `Context`. The context is
> optional — tools that don't need it can omit the parameter."*

Two consequences worth stating plainly, because they are the difference between a tool that works
everywhere and one that works on your laptop.

**The parameter is not part of the tool's schema.** The model never sees `ctx`, the client never sends
it, and it does not appear in `inputSchema`. It is filled in by the framework on the server side, which
is why adding it does not change the tool's contract with the outside world.

**The reporting call is safe to make unconditionally.** This is the part people do not believe until
they read the source. When there is no token, `report_progress` returns before it sends anything. It
does not raise, does not warn, and does not log. Your tool therefore has **one** code path rather than
a fast path and a reporting path, and the one path is the one that gets tested.

The cost of that convenience is the failure mode from part 2.1: silence is indistinguishable from
success. The SDK chose the trade, and it is the right trade, but you have to know it was made.

## Why Sutra needs it

Because the tool this day is preparing — `sutra_mcp/tasks.py` — is going to be written by you, in a
file that other days depend on, and the shape of its reporting decides whether it can be tested.

## The mechanism

First, the tool. This is the shape `sutra_mcp/tasks.py` will use, written against the installed SDK:

```python
# the shape - do not paste this into sutra_mcp yet; the hub's build brief says when
from mcp.server.fastmcp import Context, FastMCP

mcp = FastMCP("sutra-mcp")


@mcp.tool()
async def reindex_archive(archive: str, ctx: Context) -> str:
    """Re-index one archive, reporting progress as it goes."""
    chunks = load_chunks(archive)
    for done, chunk in enumerate(chunks, start=1):
        index(chunk)
        await ctx.report_progress(done, len(chunks), f"indexed chunk {done} of {len(chunks)}")
    return f"re-indexed {len(chunks)} chunks"
```

**Line by line:**

- `from mcp.server.fastmcp import Context, FastMCP` — both names come from the same module. Verified
  present in `mcp==1.29.1` by reading `.venv/Lib/site-packages/mcp/server/fastmcp/server.py` on
  2026-09-04, where `Context` is defined at class level and `report_progress` is one of its methods.
- `async def` rather than `def`, because `report_progress` is a coroutine and must be awaited. A
  synchronous tool cannot report progress, which is a real constraint on how you write the work loop.
- `ctx: Context` is the whole injection mechanism. The **annotation** is what matters, not the name:
  call it `context` or `c` and it still works, and drop the annotation and it becomes an ordinary tool
  argument the model is asked to supply.
- `archive: str` comes before `ctx` here for readability only. The SDK identifies the context parameter
  by its type, so position is free.
- `enumerate(chunks, start=1)` counts from one because `progress` is a count of work **completed**.
  Starting at zero would send an opening notification saying nothing has happened, and the
  specification requires `progress` to increase on every notification — a leading zero wastes the first
  slot.
- `await ctx.report_progress(done, len(chunks), ...)` passes `progress`, `total` and `message` in that
  order, matching the SDK's signature. The message is not decoration: it is what a person reads when
  they are trying to work out where a job stalled.
- There is **no `if` around the report call.** That is the design decision this part exists to justify,
  and the justification is in the SDK's own source below.

Now the source that makes that safe. This is the installed implementation, copied from
`.venv/Lib/site-packages/mcp/server/fastmcp/server.py` on 2026-09-04:

```python
async def report_progress(
    self, progress: float, total: float | None = None, message: str | None = None
) -> None:
    """Report progress for the current operation."""
    progress_token = self.request_context.meta.progressToken if self.request_context.meta else None

    if progress_token is None:  # pragma: no cover
        return

    await self.request_context.session.send_progress_notification(
        progress_token=progress_token,
        progress=progress,
        total=total,
        message=message,
        related_request_id=self.request_id,
    )
```

**Line by line:**

- The signature is on one line in the installed file and is wrapped here to fit this repository's
  hundred-character limit. Nothing else about the block is changed.
- `progress: float, total: float | None = None, message: str | None = None` — only `progress` is
  required, which mirrors the specification exactly: the total **MAY** be omitted when it is unknown,
  and the message is optional.
- `self.request_context.meta.progressToken if self.request_context.meta else None` reads the token out
  of the current request's `_meta`. Note the guard on `meta` itself: a request may carry no `_meta` at
  all, and the SDK treats that the same as a request whose `_meta` has no token.
- `if progress_token is None: return` is the line from part 2.1's demo, in the real library. **Nothing
  is raised and nothing is logged.** A tool that reports progress into the void behaves exactly like a
  tool that does not report at all.
- `# pragma: no cover` on that line is a small confession worth reading: the SDK's own test suite marks
  the no-token branch as deliberately unmeasured. The library authors know it is the quiet path.
- `send_progress_notification` is what actually puts a message on the wire, and it is reached only when
  a token exists. Everything above it is the opt-in check.
- `related_request_id=self.request_id` is the important argument and the reason part
  [2.3](2.3-progress-is-narration-not-state.md) exists. The notification is tied to **the request that
  is still open**, so it travels on that request's own response stream. Progress is scoped to a
  request, not broadcast to a connection.

## When it breaks

The first break is the annotation, and its error message is one of the more confusing ones you will
meet, because it blames the model:

```text
McpError: Invalid arguments for tool reindex_archive: 1 validation error for reindex_archiveArguments
ctx
  Field required [type=missing, input_value={'archive': 'tickets'}, input_type=dict]
```

That is what happens when you write `def reindex_archive(archive: str, ctx)` with no annotation, or
misspell the type. The SDK does not recognise `ctx` as the context parameter, so it treats it as an
ordinary tool argument, publishes it in `inputSchema`, and then rejects every call that does not supply
it. The fix is one word: annotate the parameter with `Context`.

The second break is the `await`:

```text
RuntimeWarning: coroutine 'Context.report_progress' was never awaited
```

A warning, not an error. The tool completes, the result is correct, and no notification is ever sent —
the coroutine object is created and discarded. This is the same failure shape as the missing token,
arriving from your own code instead of from the caller, and it is why a warning filter that turns
`RuntimeWarning` into an error is worth having in a test run.

The third is not an error at all and is the one to watch for in review: a report call inside a `try`
that swallows exceptions. If sending a notification fails because the client has gone, that failure is
information — and a bare `except Exception: pass` around it turns a dead client into a tool that keeps
working for nobody.

## In production

**What a professional writes instead:** progress is reported on a **schedule of work, not a schedule of
loop iterations**. Reporting once per item is fine for a hundred items and absurd for a million, so the
loop reports every `max(1, total // 100)` items, giving at most a hundred notifications whatever the
size of the job. The call stays unconditional; the *rate* is what gets controlled.

**What degrades at scale and under concurrency:** notifications share the response stream with
everything else that request is doing, and on stdio they share one pipe with every other request on the
server. A chatty tool can starve the pipe. Worse, `await` on a send means the tool's own work is paced
by how fast the client drains the stream — a slow client can therefore slow down the indexing, which is
a coupling nobody expects. The mitigation is the same as above: report rarely and never inside the
tightest loop.

**The review comment a senior engineer leaves:** *"This awaits `report_progress` once per ticket. At a
hundred thousand tickets that is a hundred thousand awaits on a stream we do not control the drain rate
of, and the indexer's throughput now depends on the client. Report on a percentage, not on each row —
and while you are in there, drop the `if ctx:` guard, the SDK already returns silently when nobody
asked."*

**The interview question:** *"how does a tool function get access to the request it is serving?"* An
honest answer: *"in the Python SDK you add a parameter annotated with `Context` and the framework
injects it — the name does not matter, the annotation does, and it never appears in the tool's input
schema so the model is not asked for it. From there you get the request id, the client info and
`report_progress`. The detail I would mention is that `report_progress` returns silently when the caller
sent no progress token; I read that in the SDK source rather than guessing, and it is the reason a
missing progress bar so often has nothing wrong with it on the server side."*
