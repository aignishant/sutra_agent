# 1.2 — The timeout ladder

## One-line answer

Raising your timeout never fixes a long job, because the deadline that ends the call is the smallest
one on the path and most of the deadlines on the path are not yours to set.

## The story

You park in the pay-and-display bay outside the office and buy a ticket for as long as the machine
will sell you.

The meeting overruns. You slip out, feed the machine again, and go back in. It overruns again. You go
down and top it up again, and this time the machine refuses, because the sign on it says the maximum
stay in this bay is three hours and you have used them. So you move the car to the multi-storey around
the corner and buy a ticket there instead. That works, until you come down at closing time and find
the barrier down and a laminated notice giving a number to ring.

At every step you did the obvious thing: buy more time. And at every step somebody else's rule — the
council's maximum stay, the car park's closing time — decided when your car had to be somewhere else.
You never once had the power to buy your way out, because the rules were not being sold to you. They
were the conditions under which you were allowed to park at all.

## The idea in plain language

A **timeout** is a rule of the form "if no answer arrives before this deadline, stop waiting and treat
it as failed". Every piece of software that waits for something has one, because the alternative is
waiting forever.

The thing people miss is that a single tool call passes through several pieces of software that each
have one, and they were configured by different people at different times for different reasons:

| Layer | Whose deadline it is | Why it exists |
| --- | --- | --- |
| the MCP client in Sutra | yours, in code | so one bad server cannot hang the agent |
| an HTTP library underneath it | the library author's default | so a socket cannot leak |
| a reverse proxy in front of the server | the platform team's | so one slow backend cannot exhaust the proxy |
| a cloud load balancer | the cloud provider's, often capped | so idle connections are reclaimed |
| the host that runs the agent | whoever wrote the host | so a browser tab stays responsive |

They form a **ladder**: several deadlines stacked on one path. And a ladder made of deadlines has one
property that decides the argument — **the shortest rung wins**. Whichever layer runs out of patience
first ends the call, and every other layer's generosity is irrelevant.

So "just raise the timeout" is not one change. It is a change you can make at one rung, after which
the *next* rung becomes the one that fires — and usually with a different error message, from a
component you have less control over, that says less about what happened. You have not bought time.
You have swapped a clear failure you own for a vague one you do not.

There is a second half to this, and it is the part that turns an annoyance into a design rule. Even if
you somehow controlled every rung, holding a connection open for the length of a long job re-creates
the exact problem the 2026 protocol revision removed. Day 32's part
[2.2](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md) showed
what happens when a conversation is pinned to one instance: with three instances behind a dispatcher,
two of four requests are refused on the happy path with nothing broken. A held connection is a
pin by another name. It is not stored in a session table, but the work is still stuck to one process,
and that process cannot be redeployed, drained or restarted without destroying it.

## Why Sutra needs it

Because the platform Sutra is heading for has rungs you cannot reach.

**Day 43** deploys `sutra_mcp` behind a managed HTTP front end. Its idle and request deadlines belong
to the provider, are often capped, and change without asking you. Any design whose correctness depends
on a number in that layer is a design that breaks during somebody else's maintenance window.

**Day 44** is the day Sutra's client grows retries and timeouts on purpose. That day needs a rule for
choosing them, and the rule cannot be "make them big enough", because this part is the proof that
there is no such number. The rule it gets instead is: deadlines are for *transport*, and long work is
never transport.

And it settles the question this day opens with. Before you write `sutra_mcp/tasks.py` you have to be
convinced that the simpler option — keep the blocking tool, raise the deadline — is not on the table.
This is that argument, in numbers.

## The mechanism

The ladder, and what happens when you climb one rung of it:

```python
# days/day-36-long-jobs-and-tasks/lab/timeout_ladder.py
# (name, patience in ms, what the caller sees when this layer is the one that fires)
LADDER = [
    ("mcp client read timeout", 30_000, "McpError: Timed out while waiting for response"),
    ("reverse proxy", 60_000, "HTTP 504 Gateway Time-out"),
    ("cloud load balancer idle", 240_000, "HTTP 502 upstream connect error or disconnect/reset"),
    ("browser/agent host", 300_000, "connection closed by peer"),
]

JOB_MS = 420_000  # a real re-index of the ticket archive


def weakest(ladder: list[tuple[str, int, str]], job_ms: int) -> tuple[str, int, str] | None:
    """The first layer whose patience the job outlasts - the one the caller blames."""
    candidates = [layer for layer in ladder if layer[1] < job_ms]
    return min(candidates, key=lambda layer: layer[1]) if candidates else None
```

**Line by line:**

- The tuple is `(name, patience, message)` rather than a class because the whole model is three facts
  per rung. A `dataclass` would be tidier and would not teach anything extra here.
- Patience is in **milliseconds**, spelled `30_000` with an underscore separator. This is not
  decoration: `pollIntervalMs` and `ttlMs` in the Tasks extension are milliseconds too, and the single
  most common mistake with them is reading `3600` as an hour. Writing the underscore forces you to
  count the digits.
- The messages are the **real** strings each layer emits, not summaries. That matters because in
  practice you identify which rung fired by pasting its message into a search box, and a paraphrase is
  unsearchable.
- `weakest` filters to the rungs the job outlasts and returns the **minimum** of those. The `min` is
  the claim of the whole part: not "a timeout fires" but "the *smallest* one fires", and everything
  above it never gets a say.
- It returns `None` when the job fits inside every rung. That case exists so the function can express
  "nothing fires", which is what a correctly-designed short call looks like.

```python
def main() -> None:
    report(LADDER, JOB_MS, "as shipped")

    patient = [("mcp client read timeout", 600_000, LADDER[0][2]), *LADDER[1:]]
    report(patient, JOB_MS, "after 'just raise the client timeout'")
```

**Line by line:**

- `patient` rebuilds the ladder with **only the first rung changed**, which is precisely the change a
  developer is able to make on their own: your client's timeout is in your code, and the other three
  rungs are in somebody else's configuration.
- `*LADDER[1:]` splices the untouched rungs back in, so the comparison is honest — nothing else moved.
- Calling `report` twice with the same `JOB_MS` is what makes the output an argument rather than an
  illustration: same job, same rungs, one number changed, and the failure simply relocates.

Run it:

```bash
uv run python days/day-36-long-jobs-and-tasks/lab/timeout_ladder.py
```

**Line by line:**

- From the repository root. **Zero model calls**, no network — it is arithmetic over a list.

Measured on 2026-09-04:

```text
as shipped: job 420s
  mcp client read timeout          30s  gives up
  reverse proxy                    60s  gives up
  cloud load balancer idle        240s  gives up
  browser/agent host              300s  gives up
  -> caller sees: McpError: Timed out while waiting for response

after 'just raise the client timeout': job 420s
  reverse proxy                    60s  gives up
  cloud load balancer idle        240s  gives up
  browser/agent host              300s  gives up
  mcp client read timeout         600s  would hold
  -> caller sees: HTTP 504 Gateway Time-out
```

The second block is the point. Your rung now holds. Three rungs still do not, and the error the user
gets has become *worse*: `HTTP 504 Gateway Time-out` arrives from a component that is not in your
repository, carries no MCP context, and looks to a support engineer like a network incident rather
than a design decision.

## When it breaks

The dangerous case is the one where raising the timeout appears to work.

You bump the client, the job now finishes inside every rung on your laptop, and the tool is shipped.
The rung that eventually fires in production is the one nobody tested, and it produces this:

```text
httpx.RemoteProtocolError: Server disconnected without sending a response
```

That is not a timeout message at all. Nothing in it contains the word "timeout", nothing names a
deadline, and nothing says which hop gave up. It is what a client sees when an intermediary closes a
connection it has decided is idle — because from the load balancer's point of view a connection with
no bytes flowing *is* idle, whatever the server thinks it is doing.

Two things make this expensive rather than merely annoying. First, it is **load-dependent**: the job
gets slower when the archive grows or when the machine is busy, so it starts failing on the days you
can least afford to investigate. Second, it is **retried**: a disconnection looks transient, so the
client tries again, and now two copies of the same long job are running — which part
[1.3](1.3-work-with-no-name.md) counts and part
[6.2](../06-in-production/6.2-the-job-that-ran-twice.md) prevents.

The smallest fix is not a number. It is to stop putting the work inside the request, so that no rung
on the ladder is ever asked to be patient in the first place.

## In production

**What a professional writes instead:** deadlines are set for what they are actually for — detecting a
dead peer — and are deliberately kept *short*. A tool call that returns a handle answers in
milliseconds, so a two-second client deadline is generous, and every rung above it is irrelevant. The
long job's duration then has nothing to do with any timeout anywhere, which is the property you are
buying. Teams that have been bitten write it as a rule in the service's own documentation: *no
request handler waits for work it started.*

**What degrades at scale and under concurrency:** timeouts interact badly with retries in a way that
gets worse as load rises. When a slow layer starts firing, every client retries, which adds load,
which makes everything slower, which makes more layers fire. This is a retry storm, and it is why
Day 44 pairs every timeout with a backoff and a cap rather than treating them as separate settings.
The blocking-call design makes a storm more likely, because a long call gives the storm somewhere to
accumulate.

**The review comment a senior engineer leaves:** *"You raised `read_timeout` to 600 seconds to make
this pass. Our ingress caps a request at 240 and the platform team will not change it for us, so what
you have actually shipped is the same failure with a worse error message and no MCP error code. Put
the work behind a handle; then set the timeout back to something that tells us when a server is
dead."*

**The interview question:** *"a tool call keeps timing out. What do you change?"* An honest answer:
*"first I find out which layer is timing out, because the fix is different for each and the error text
usually tells you — `McpError` is mine, `504` is the proxy's, a bare disconnect is usually a load
balancer's idle rule. But if the answer is that the work genuinely takes longer than the deadlines,
I do not raise anything, because the deadlines are not all mine and the shortest one always wins.
I change the shape: the call returns a handle immediately and the client polls. I have measured this —
raising my own client's deadline just moved the failure to the reverse proxy and turned a clear MCP
timeout into an HTTP 504 from a box I do not own."*
