# 1.3 — Work with no name

## One-line answer

A JSON-RPC request id names a **message**, not a job, so when the stream carrying that message breaks
the id is spent and the client's only remaining move is to send a brand new request — which the server
has no way of recognising as the same errand.

## The story

You ring the bank about a payment that went out twice.

You get through, and the man on the line starts working on it. He asks for your date of birth, your
last three transactions, the name of the shop. He puts you on hold twice while he checks something.
You can hear him typing. Ten sentences into the problem, the line goes dead.

You ring back. A different person answers, and the first thing she says is *"do you have a reference
number?"* You do not, because nobody gave you one. So you start again: date of birth, last three
transactions, the name of the shop.

Somewhere in that building there is a screen with your half-finished case on it, and the man who was
typing has moved on to the next call. Nothing was lost through carelessness. The problem is that the
only thing joining you to that work was **the call itself**, and the call is exactly the part that
ended.

The fix is not a better phone line. The fix is the sentence *"your reference is 4-8-2-1-9"*, said at
the beginning, before anything can go wrong.

## The idea in plain language

Every request Sutra sends over MCP carries an **id**: a number or a string the client picks so that,
when an answer comes back, the client can tell which question it is the answer to. Day 33's part
[2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md) showed the
messages themselves — one JSON object per line, each with `"id": 1`, `"id": 2` and so on.

It is very tempting to treat that id as the name of the work. It is not, and the difference is the
subject of this part.

The id names a **message pair**: one request going out, one response coming back. Its whole life is
that round trip. The moment the response arrives, or the moment the stream carrying it dies, the id is
finished. It was never a name for the *thing the server is doing*, only for the *envelope the question
travelled in*.

That distinction used to be softer than it is now. Older revisions of MCP let a client resume a broken
stream: the server tagged each event with an identifier and the client could reconnect and say "carry
on from the last one I saw". The 2026-07-28 revision deleted that, deliberately and in writing
(`https://modelcontextprotocol.io/specification/2026-07-28/changelog`, read 2026-09-04):

> *"Remove SSE stream resumability and message redelivery (the `Last-Event-ID` header and SSE event
> IDs) from the Streamable HTTP transport. A broken response stream loses the in-flight request;
> clients **MUST** re-issue it as a new request with a new request ID."*

Read the last clause twice, because it is the whole part. **A new request with a new request id.** Not
"reconnect to the old one". Not "ask what happened to id 7". The protocol says, in as many words, that
a broken stream loses the request, and that the client's only correct behaviour is to ask again from
scratch.

For a dictionary lookup that is exactly right and costs nothing: asking `lookup_ticket` twice is two
cheap reads. For a re-index it is a disaster with three separate faces.

**You cannot ask how it is going.** There is nothing to ask *about*. `tasks/get` needs a `taskId`, and
you have none.

**You cannot stop it.** `tasks/cancel` needs the same identifier. The work will run to the end,
consuming whatever it consumes, and deliver its answer into a connection that closed.

**You cannot recognise your own retry.** From the server's side, request 1 and request 2 are two
unrelated messages that happen to carry the same arguments. Requests carrying the same arguments are
normally *supposed* to be different jobs — two people can both ask to re-index — so the server cannot
safely assume they are one. It starts a second re-index, and now two workers are writing to the same
index at the same time.

The word for what is missing is **identity**. Not "an identifier" in the loose sense — the request had
one of those. Identity in the sense of a name that belongs to the *work*, is minted before anything can
go wrong, and outlives every connection the work is discussed over. A reference number, said at the
beginning of the call.

## Why Sutra needs it

Because two later days are built on the assumption that Sutra's work has names, and neither of them can
be written if it does not.

**Day 44** hardens the client with retries. A retry is a decision, and the decision needs an input:
*is the thing I am about to send a repeat of something already running?* Without a job name that
question has no answer, so Day 44's retry policy would be a coin toss dressed as engineering. Part
[6.2](../06-in-production/6.2-the-job-that-ran-twice.md) is where the answer gets built.

**Day 60** builds durable execution — work that survives a process restart. Durability starts with
being able to say *which* work survived, and that is a name written down before the work began.

And immediately: the tool signature you are about to design in `sutra_mcp/tasks.py` either returns a
name or it does not, and everything else on this day follows from that one decision.

## The mechanism

Two requests, one errand, and a server that cannot tell:

```python
# days/day-36-long-jobs-and-tasks/lab/no_name.py
started: list[str] = []


def server_call(request_id: int, tool: str, arguments: dict[str, str]) -> str:
    """A server with no notion of a job: every request is new work."""
    started.append(f"req#{request_id} {tool}{arguments}")
    return "working"
```

**Line by line:**

- `started` is the server's record of what it actually began. It exists only so the demo can count at
  the end; a real server would show you the same number as CPU on a graph.
- `server_call` takes the `request_id` and **does nothing with it except log it**. That is not
  laziness in the demo, it is a faithful model of a normal tool handler: the id belongs to the
  transport layer, and the code that does the work never sees it.
- `arguments` is a plain dict, and it is the only thing the second request shares with the first.
  Notice how little that is: two callers asking to re-index the same archive at the same moment is a
  legitimate situation, so identical arguments cannot be taken as proof of a duplicate.
- The return value is the string `"working"` rather than a result, because in this shape there is
  nothing else honest to return — the server has started something and has no name to give back.

```python
def main() -> None:
    args = {"archive": "tickets"}

    server_call(1, "reindex_archive", args)
    print("client   : request 1 sent, stream open")
    print("client   : stream broken (proxy closed the connection)")
    print("client   : the answer to request 1 can never arrive - the id is spent")

    server_call(2, "reindex_archive", args)
    print("client   : retried as request 2, because that is all a client can do")
```

**Line by line:**

- `server_call(1, ...)` is the original tool call. It succeeds. The work is under way.
- The three printed lines in between are the whole failure, and they are printed rather than raised
  because nothing here is an exception: a closed connection is an ordinary event that the client
  handles.
- `the id is spent` is the line that matters. Request 1 cannot be revived, cannot be asked about, and
  cannot be referred to. The specification is explicit that a re-issue must carry a **new** id, so the
  client is not even permitted to reuse the old number and hope.
- `server_call(2, ...)` is the retry. `because that is all a client can do` is not resignation — it is
  the correct behaviour under this design. The client has no worse option available and no better one.

```text
           req#2 reindex_archive{'archive': 'tickets'}

```

`jobs started : 2` is the cost, and the last three lines are the reason it could not have gone any
other way. Every one of them is a question about a *job*, asked of a system that only has *messages*.

Here is the same thing as a picture, because the shape of the problem is that one arrow is missing:

```mermaid
sequenceDiagram
    participant C as Sutra (client)
    participant S as sutra-mcp (server)
    C->>S: tools/call id=1 reindex_archive
    activate S
    S->>S: job A starts
    C--xS: stream broken; id 1 is spent
    C->>S: tools/call id=2 reindex_archive
    activate S
    S->>S: job B starts - identical, unrecognised
    Note over C,S: nothing in either message names job A
    deactivate S
    deactivate S
```

The two `activate` bars overlapping is the whole picture: two jobs, one intention, and no message
anywhere that could have joined them up.

## When it breaks

In production this does not announce itself as "the client retried". It announces itself as a
correctness problem in whatever the job writes, and the log line has nothing to do with requests:

```text
sqlite3.IntegrityError: UNIQUE constraint failed: index_chunks.ticket_id
```

Two workers re-indexing the same archive concurrently reach the same ticket and both try to write its
row. One wins, one raises, and the traceback points at the indexing code — which is correct, tested,
and not the problem. The problem is two levels up and was caused by a connection closing.

The second shape is worse because nothing raises at all. If the writes happen to be idempotent — an
upsert rather than an insert — the two workers quietly finish, the index is fine, and you have simply
paid twice. That version can run for a year. You find it when somebody asks why the nightly job's cost
does not match the number of nightly jobs.

The smallest fix is not error handling. It is a name: mint an identifier for the work, hand it to the
client in the first response, and give the client something to ask with. Part
[3.1](../03-the-handle/3.1-a-name-the-server-mints.md) does exactly that, and part
[6.2](../06-in-production/6.2-the-job-that-ran-twice.md) closes the remaining gap — what happens when
the very first response is the one that gets lost.

## In production

**What a professional writes instead:** any operation that is expensive, slow or has side effects gets
an identity before it gets a worker. In practice that means the handler's first action is a write —
create the row, mint the id, return it — and only then does anything begin. The rule people say out
loud is *"the job exists before the work does"*, and it is the same instinct as the bank giving you a
reference number at the start of the call rather than the end.

**What degrades at scale and under concurrency:** duplicated work is not linear in the number of
failures, because failures are correlated. A proxy restart drops every in-flight stream at once, so
every client retries at once, and a system that was running ten long jobs is suddenly running twenty —
at the exact moment it is least healthy. The retry storm from part
[1.2](1.2-the-timeout-ladder.md) and the missing name from this part combine into an outage that looks
like a capacity problem and is really a naming problem.

**The review comment a senior engineer leaves:** *"There is no job id anywhere in this handler, so I
cannot tell from a log line which run of the indexer a message belongs to, and neither can the client.
Mint an id first, log it on every line, and return it in the response. Right now if this fires twice we
will never find out."*

**The interview question:** *"your long tool call fails halfway. What can the client do?"* An honest
answer: *"under the 2026 revision of MCP, exactly one thing — send it again with a new request id,
because stream resumability was removed and a broken stream loses the request. That is fine for a read
and dangerous for a job with side effects, so the real answer is that the client should never have been
holding an unnamed job in the first place. If the first response hands back a task id, the client's
recovery is to poll that id instead of re-running the work. I have measured the version without it: two
requests, two full re-indexes, and nothing in either message that could have told the server they were
the same errand."*
