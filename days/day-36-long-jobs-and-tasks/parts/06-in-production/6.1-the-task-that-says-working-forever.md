# 6.1 — 💥 The task that says working forever

## One-line answer

A task row says `working` because somebody wrote `working` into it, not because anything is working —
so when the process holding the job dies, the row goes on claiming progress forever, and only a lease
that has to be renewed can tell a slow job from a dead one.

## The story

The board at the station says the 18:40 is on time.

It said so ten minutes ago and it says so now, and there is no train. The platform fills up. Somebody
checks their phone and finds nothing, because the app reads the same board. A man with a lanyard walks
past and says he has heard something about a fault at the depot, and forty people believe him over the
sign, which is the first sensible thing that has happened.

Eventually somebody in an office notices and the board flips to *cancelled*. What changed was not the
train — the train was never coming, for the whole of that half hour. What changed was that a person
found out and typed it in.

The board was never lying. It was displaying the last thing it had been told, which is all any board
ever does. The failure was that nothing was watching for the *absence* of news.

## The idea in plain language

Everything in section 3 turned on one write: the server records the task row, and the row is the truth.
That works beautifully until the truth stops being maintained.

Here is the sequence. A tool call creates a row with status `working` and hands the work to a worker.
The worker is a thread, a process, or a container. It starts. And then the container is evicted during
a deploy, or the machine is reclaimed by the platform, or the process is killed for using too much
memory.

Nobody writes anything. The worker did not fail — it **stopped existing**, which is a different thing
and produces no exception, no log line and no final status. The row still says `working`, because
`working` is what was written and nothing has written anything since.

From the client's side this is indistinguishable from a job that is simply taking a while. It polls,
gets `working`, polls again, gets `working`, and part
[4.3](../04-the-tasks-extension/4.3-polling-is-a-budget.md)'s backoff means it will do so patiently and
cheaply for a very long time. There is no terminal status coming. The polling loop from part
[4.2](../04-the-tasks-extension/4.2-five-statuses-and-the-terminal-rule.md), whose stopping condition is
"a terminal status", has become an infinite loop.

The tempting fix is a deadline: if a task has been `working` for longer than some limit, call it
failed. It is wrong for a reason worth internalising — **you do not know how long the job should take.**
The archive grows. The machine is busy. A legitimate re-index that is slower than usual would be killed
by that rule, and the limit would then be raised, and you are back on part
[1.2](../01-the-blocking-call/1.2-the-timeout-ladder.md)'s ladder with a different name on it.

The mechanism that works does not measure the job. It measures **whether anyone is still alive to
report on it**, and it is called a **lease**.

A lease is a timestamp on the row saying *"trust this row until here"*. The worker's job is to push
that timestamp forward as it goes — a heartbeat. A live worker renews it every batch; a dead worker
renews nothing. Then a separate sweep, the **reaper**, looks for rows whose lease has expired and marks
them `failed` with a message that says what actually happened.

The property that makes this correct is that the lease is renewed by **the same code that does the
work**. A slow job renews, so it survives. A dead job cannot renew, whatever the reason it died, because
renewal is an action and a dead process performs no actions. There is no cleverness in it and no
guessing about durations.

Two design consequences fall out immediately. The lease has to be **shorter than a client's patience**,
or the reaper is not helping anybody. And the reaper's write is a terminal write, so it obeys the
terminal rule: it may only fail a row that is still `working`, never one that has already finished.

## Why Sutra needs it

Because Sutra's tasks are about to live on infrastructure that removes processes as a matter of routine.

**Day 43** deploys `sutra_mcp` as a stateless service that scales up and down. Scaling down is a process
being killed on purpose. If a worker lives inside a request handler — which is exactly what part
[3.1](../03-the-handle/3.1-a-name-the-server-mints.md)'s demo thread is — then every scale-down event
silently orphans whatever it was running.

**Day 44** writes the client's polling loop. That loop needs to be able to end, and the only thing that
guarantees an end is that every task eventually reaches a terminal status. The reaper is what makes that
guarantee true.

**Day 84** builds tracing. A task that is `working` forever is invisible in an error dashboard and
obvious in a table sorted by lease age, which is the sort of thing you want to have built before you
need it.

## The mechanism

A worker with a heartbeat, a plug pulled, and a sweep that notices:

```python
# days/day-36-long-jobs-and-tasks/lab/reaper.py
LEASE_S = 0.30  # how long a row is trusted without a heartbeat
TICK_S = 0.05

row = {"taskId": "tsk_demo", "status": "working", "done": 0, "lease_until": 0.0}
alive = threading.Event()


def worker() -> None:
    """Do a chunk, renew the lease, repeat - until somebody pulls the plug."""
    while alive.is_set():
        time.sleep(TICK_S)
        row["done"] = int(row["done"]) + 1
        row["lease_until"] = time.perf_counter() + LEASE_S
```

**Line by line:**

- `LEASE_S` is how long the row is trusted **without news**, and it is six ticks long here so that a
  healthy worker renews it several times over before it could ever expire. In production the ratio
  matters more than either number: a lease that is only slightly longer than the heartbeat interval will
  reap live workers during a slow moment.
- `lease_until` is stored on the row, not in the worker. That is the whole design — the fact that has to
  survive the worker's death has to live where the worker is not.
- `alive` is a `threading.Event` standing in for the platform. Clearing it is how the demo evicts the
  container, and it is deliberately **not** a graceful shutdown: nothing gets a chance to write a
  status.
- The worker renews the lease **after** doing a chunk, not before. Renewing first would extend trust on
  the strength of an intention; renewing after extends it on the strength of work actually done.
- `time.perf_counter() + LEASE_S` is a monotonic clock, which is what a lease needs: a wall-clock
  timestamp can jump backwards when the machine syncs its time, and a lease that jumps backwards
  reaps live work.
- There is no `try`/`finally` writing a terminal status on the way out, and that is faithful. A killed
  process does not run its cleanup, which is precisely why the lease has to exist.

```python
def reap(now: float) -> str:
    """What a sweep decides about this row."""
    if row["status"] != "working":
        return row["status"]
    if float(row["lease_until"]) < now:
        row["status"] = "failed"
        row["statusMessage"] = "worker lease expired; the process holding this task is gone"
        return "failed"
    return "working"
```

**Line by line:**

- `if row["status"] != "working"` is the terminal rule, first, before anything else. A reaper that can
  overwrite a `completed` row is a reaper that turns a successful job into a failure because a sweep ran
  at an awkward moment.
- `float(row["lease_until"]) < now` is the entire test. Not "how long has this been running", not "is
  this longer than expected" — only *has anybody reported in recently*.
- `status = "failed"` rather than `"cancelled"`: nobody asked for it to stop, so `cancelled` would be
  wrong under part [4.2](../04-the-tasks-extension/4.2-five-statuses-and-the-terminal-rule.md)'s
  vocabulary. It failed, and the client should treat it as a failure — which usually means retrying it
  as a new task.
- The `statusMessage` names the cause in words a human can act on. `"failed"` alone sends somebody to
  the indexer's logs, where they will find nothing, because the indexer did not fail; it disappeared.
- `reap` takes `now` as an argument rather than calling the clock itself, which is what makes it
  testable: a test can pass a time far in the future and assert the row was reaped, with no sleeping.

Run it:

```bash
uv run python days/day-36-long-jobs-and-tasks/lab/reaper.py
```

**Line by line:**

- From the repository root. **Zero model calls**, no network. The script runs a worker, kills it, and
  asks the reaper twice — before and after the lease runs out.

Measured on 2026-09-04:

```text
t=0.15s  worker alive   status='working' done=2
t=0.20s  worker gone    status='working' done=3
t=0.30s  no reaper      status='working' <- still lying
         reaper says    'working'
t=0.60s  reaper says    'failed'
         statusMessage  'worker lease expired; the process holding this task is gone'
```

The second and third lines are the bug, in the state it ships in. The worker is **gone** and the row
still reads `working`, and a client polling at that instant is told the job is fine. The fourth line is
the reaper being correctly cautious — the lease has not expired yet, so it says nothing, because a sweep
that reaps eagerly is worse than no sweep at all.

Only on the last two lines does the truth arrive, and notice what produced it: not the worker, not the
client, not an error. A third party, looking at the absence of news.

The scene format:

> 🎬 **The scene:** a re-index is running when the platform rolls the deployment.
> 😬 **The naive fix:** nothing, because nothing looks wrong. The tool returned a handle, the row was
> written, the client is polling politely.
> 💥 **Why it fails:** the worker was inside the process that went away. It wrote no terminal status
> because it was not given the chance, and the row keeps its last value forever. The client's polling
> loop has a stopping condition that will never be met, and the job silently did not happen.
> 💡 **The insight:** a status is a claim somebody made at a moment, not a fact about the present. If the
> only thing that can update it is the thing that died, the row is a memorial. Make liveness something
> that must be **renewed**, and let a separate sweep act on its absence.

## When it breaks

The break has no error text on the day it happens, which is the whole problem. It has one weeks later,
when somebody finally looks at the table:

```text
sqlite3.OperationalError: database or disk is full
```

That is part [3.3](../03-the-handle/3.3-sutras-handle-policy.md)'s rule 3 failing for a second reason.
Rows expire by TTL — but a TTL is usually applied to *finished* tasks, and these never finished. Every
orphan accumulates, and if the sweep only deletes terminal rows, the `working` ones are exactly the
subset it never touches.

The break the client experiences is quieter still and produces nothing at all:

```text
tasks/get tsk_9Fq2mR7wZk4bT1cs -> {"status": "working"}
tasks/get tsk_9Fq2mR7wZk4bT1cs -> {"status": "working"}
tasks/get tsk_9Fq2mR7wZk4bT1cs -> {"status": "working"}
```

Three polls, correct responses, no errors — and the agent that started this job is now waiting on
something that will never answer. If that agent is inside a user-facing loop, the user sees a spinner;
if it is a scheduled job, tomorrow's run starts a second one beside it.

And the break caused by fixing this badly is worth stating: a reaper with a lease shorter than the
heartbeat interval will fail perfectly healthy tasks, at random, under load — because load is exactly
when a worker takes longer than usual to get round to renewing. The symptom is intermittent `failed`
tasks whose work completed, which is one of the harder things to debug because the evidence contradicts
itself.

## In production

**What a professional writes instead:** the lease is a column with an index on it, renewed by the worker
inside the same transaction that records progress, so a worker cannot record work without also proving
it is alive. The reaper is a scheduled job — every so often, `UPDATE tasks SET status = 'failed',
status_message = ? WHERE status = 'working' AND lease_until < now()` — and it emits a metric for how
many rows it reaped, because a reaper that suddenly reaps a lot is telling you something about the
platform, and a reaper that reaps zero forever is possibly not running at all.

**What degrades at scale and under concurrency:** the reaper is the piece that fails silently. It runs
on a schedule, and a schedule that stops firing looks exactly like a system with no orphans, so it needs
an alert on *not having run* rather than on failing. Under load the lease-renewal write becomes real
traffic — one write per worker per heartbeat — which is why renewal piggybacks on the progress write
rather than being its own round trip. And at scale you will meet the resurrection case: the "dead"
worker was only paused, comes back, and tries to write `completed` to a row the reaper already marked
`failed`. The terminal-status guard in the update is what makes that a no-op instead of an argument.

**The review comment a senior engineer leaves:** *"If the pod running this task is evicted, the row stays
`working` and the client polls it forever. Add a lease column the worker renews every batch and a
sweep that fails expired rows with a message naming the cause. And make the sweep's guard part of the
`WHERE` clause — a reaper that can overwrite a completed task is worse than no reaper."*

**The interview question:** *"a task is stuck in `working`. What is your first move?"* An honest answer:
*"work out whether it is slow or dead, and I would want that answer from the data rather than by
guessing. That means a lease — a timestamp the worker renews as it makes progress — because a live
worker renews and a dead one cannot, whatever killed it. A deadline on the job's total duration does not
work: you do not know how long the job should take, the archive grows, and you end up raising the limit
forever. Then a sweep fails the expired rows with a message saying the worker is gone, guarded so it can
only touch rows still in `working`. The subtle part is picking a lease comfortably longer than the
heartbeat interval — I have seen a lease set too tight fail healthy jobs under load, and that is much
harder to debug than an orphan, because the work completed and the row says it failed."*
