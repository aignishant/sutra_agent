# 4.4 — 💥 Which dialect your SDK speaks

## One-line answer

The `mcp` package pinned in this repository ships a tasks API that the specification **removed** — the
right five statuses, two of the three verbs, two verbs that no longer exist, and field names spelt
`ttl` and `pollInterval` instead of `ttlMs` and `pollIntervalMs` — and the package says so itself, in a
deprecation warning you have to go and read.

## The story

The timetable at the bus stop is printed, laminated and screwed to the pole.

It says the 41 comes at eighteen past. You stand there. It does not come at eighteen past. It does not
come at twenty past either, and by the time a 41 finally appears you have missed the thing you were
going to.

The timetable is not lying. It was accurate when it was printed. The route was changed in the spring
and the new one is on the council's website and on a paper notice that somebody stuck to the shelter
and somebody else peeled off. The screwed-down board is simply older than the service it describes, and
because it is screwed down it looks more authoritative than the piece of paper that was right.

## The idea in plain language

Part [4.1](4.1-four-messages-on-the-wire.md) taught the Tasks extension against the specification. This
part asks a different question: **what does the library on your disk actually implement?**

They are not the same question, and Day 32's part
[5.1](../../../day-32-mcp-stateless-core/parts/05-failure-lab/5.1-the-tutorial-from-four-months-ago.md)
already found one gap of this kind — the pinned `mcp` package reports
`LATEST_PROTOCOL_VERSION = "2025-11-25"` while the specification is at `2026-07-28`. That was the
protocol core. This is the extension, and the gap here is stranger, because the SDK does have tasks in
it. They are just **the wrong tasks**.

The history explains the shape of it. Tasks began life *inside* the core protocol as an experimental
feature. The 2026-07-28 revision moved them out
(`https://modelcontextprotocol.io/specification/2026-07-28/changelog`, read 2026-09-04):

> *"Move experimental tasks out of the core protocol and into an official extension
> (`io.modelcontextprotocol/tasks`). The redesigned extension replaces the blocking `tasks/result`
> method with polling via `tasks/get` and a new `tasks/update` for client-to-server input, removes
> `tasks/list`, and allows servers to return task handles unsolicited without per-request opt-in."*

So a library written before that revision has an experimental core tasks API: `tasks/result`,
`tasks/list`, and no `tasks/update`. A library written after it has an extension. The pinned one is the
former, and it is honest about being the former — the deprecation notice is attached to the property you
have to touch to use it at all (`.venv/Lib/site-packages/mcp/server/lowlevel/server.py`, read
2026-09-04):

> *"The experimental tasks API is deprecated and will be removed in mcp 2.0: tasks (SEP-1686) were
> removed from the MCP specification and are expected to return as a separate MCP extension."*

The rule this part exists to install is Principle 8 pointed at a package instead of at a website: **the
installed library is the authoritative API surface, and you read it rather than remembering it.** A
document tells you what the protocol says. Only the package tells you what your code can do this
afternoon.

And the way you read it is not by opening files and hoping. It is by asking the package questions —
`dir()`, `model_fields`, the warnings it raises — so that the answer is produced by the thing being
described.

## Why Sutra needs it

Because the day after tomorrow somebody has to write code against this, and the honest boundary has to
be drawn before they do.

to write lands in that server, so what the SDK can and cannot express is a constraint on the file, not
a footnote.

**Day 38** is the failure and migration lab, and dating a server by which verbs it speaks is precisely
its skill. A server offering `tasks/result` or `tasks/list` is speaking the pre-2026 dialect, and today
you learn to recognise that from the inside.

it" is an audit question, and this part produces the row that answers it.

## The mechanism

The probe reads the package rather than describing it:

```python
# days/day-36-long-jobs-and-tasks/lab/sdk_tasks.py  (extract)
SPEC_METHODS = ["tasks/get", "tasks/update", "tasks/cancel"]
REMOVED_IN_2026 = ["tasks/result", "tasks/list"]


def methods_in_sdk() -> set[str]:
    """Every literal method string the SDK's request classes declare."""
    found = set()
    for name in dir(types):
        cls = getattr(types, name)
        field = getattr(cls, "model_fields", {}).get("method") if isinstance(cls, type) else None
        if field is not None and isinstance(field.default, str):
            found.add(field.default)
    return found
```

**Line by line:**

- `SPEC_METHODS` is what the 2026-07-28 extension defines; `REMOVED_IN_2026` is what it took away.
  Naming both lists is what turns the output into a **dating test** rather than a feature checklist:
  the presence of the second list is as informative as the absence of the first.
- `dir(types)` walks every name the SDK's `types` module exports. This is deliberately blunt — it cannot
  miss a class because nobody thought to look for it.
- `isinstance(cls, type)` filters out everything that is not a class, because `dir` returns constants
  and functions too and `getattr(..., "model_fields")` on a string would be meaningless.
- `.get("method")` looks for the `method` field that every JSON-RPC request model declares. In this SDK
  every request class pins its method as a `Literal` with a default, so the default **is** the wire
  string.
- `isinstance(field.default, str)` guards against a field with no default. A request class that did not
  pin its method would be a different shape of surprise and is worth not crashing on.
- The function returns a `set` of wire strings — `"tools/call"`, `"tasks/get"` and the rest — read out of
  the package. Nothing in it is typed from memory, which is the whole point.

```python
def main() -> None:
    print(f"mcp version                : {version('mcp')}")
    print(f"LATEST_PROTOCOL_VERSION    : {types.LATEST_PROTOCOL_VERSION}")
    print(f"TaskStatus                 : {types.TaskStatus}")

    task_fields = list(types.Task.model_fields)
    print(f"Task fields                : {task_fields}")
    print(f"  ttlMs present            : {'ttlMs' in task_fields}")
    print(f"  pollIntervalMs present   : {'pollIntervalMs' in task_fields}")
```

**Line by line:**

- `version('mcp')` comes from `importlib.metadata` and reads the **installed distribution**, not a
  constant in the source. If someone has a different version than `pyproject.toml` claims, this is the
  line that catches it.
- `types.TaskStatus` is printed rather than described, because a `Literal` type prints as its own list of
  allowed values and that list is exactly the answer to "which statuses does this SDK know".
- `types.Task.model_fields` is Pydantic's own map of a model's fields. Listing it beats reading the class
  source because it includes anything inherited and excludes anything commented out.
- The two `in task_fields` checks look for the **extension's** spelling specifically. This is the
  sharpest question in the file: a field called `ttl` and a field called `ttlMs` hold the same number and
  are different names on the wire, so a server built on one and a client built on the other exchange
  JSON that validates and means nothing.

```python
    with warnings.catch_warnings(record=True) as caught:
        warnings.simplefilter("always")
        from mcp.server.lowlevel import Server

        Server("probe").experimental  # noqa: B018 - reading it is what raises the warning
    print("what the SDK says about its own tasks API")
    for warning in caught:
        print(f"  {warning.category.__name__}: {warning.message}")
```

**Line by line:**

- `catch_warnings(record=True)` captures warnings into a list instead of printing them, so the script can
  show them as data under a heading rather than have them appear at some arbitrary point in the output.
- `simplefilter("always")` is necessary because Python deduplicates warnings by default and a
  `DeprecationWarning` is hidden entirely outside `__main__` in normal runs. Without this line the most
  important sentence in the whole probe is invisible.
- `Server("probe").experimental` touches the property and does nothing with the value. The
  `# noqa: B018` says why: ruff's "useless expression" rule is right in general and wrong here, because
  **reading the attribute is the action** — the deprecation is attached to the property getter.
- Printing `warning.category.__name__` alongside the message distinguishes a `DeprecationWarning` from a
  `UserWarning`, which is the difference between "this will be removed on a schedule" and "you are
  holding it wrong".

Read that output as a dating exercise rather than a scorecard:

| Evidence | What it dates the SDK to |
| --- | --- |
| `TaskStatus` holds the right five values | the concept is stable across both eras |
| `tasks/get` and `tasks/cancel` present | the parts that survived the redesign |
| `tasks/update` absent | pre-2026: client-to-server input did not exist yet |
| `tasks/result` and `tasks/list` present | pre-2026: both were removed by the redesign |
| `ttl` and `pollInterval`, not `ttlMs` / `pollIntervalMs` | pre-2026 field names |
| the deprecation warning naming SEP-1686 | the SDK knows, and says so |

**So which half of this day could actually be run against the installed package?** The honest answer,
and it belongs in the ledger rather than in a footnote:

- **Runnable today:** the five statuses and the terminal rule (the `Literal` matches the extension
  exactly), the handle mechanism from section 3 (it needs no extension support at all — it is ordinary
  tool arguments), progress notifications from section 2 (`Context.report_progress` is core, not an
  extension), and `tasks/get` and `tasks/cancel` as method names.
- **Not runnable today:** `tasks/update`, the `ttlMs` and `pollIntervalMs` field names, and the
  per-request extension capability negotiation. These are taught against the specification and
  implemented by hand in `lab/wire_shapes.py`, which builds the messages as dictionaries precisely so
  that the shapes can be read without a library that has them.

**And the pin does not move today.** PyPI's `mcp` is further along — Day 32 recorded `2.1.1` speaking
`2026-07-28` — but bumping a pinned dependency is a plan decision with a `docs/PACKAGES.md` row behind
it (Principle 14), not something a lesson does on its way past.

## When it breaks

The break is writing to the field name you read in the specification, against the SDK that has the other
one. Pydantic's `Task` is configured with `extra="allow"`, so it accepts the unknown key without
complaint and the wrong-named field is simply never read:

```text
Traceback (most recent call last):
  File "<string>", line 3, in <module>
  File "...\.venv\Lib\site-packages\pydantic\main.py", line 732, in model_validate
    return cls.__pydantic_validator__.validate_python(
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
pydantic_core._pydantic_core.ValidationError: 1 validation error for Task
ttl
  Field required [type=missing, input_value={'taskId': 'tsk_9Fq2mR7wZ... '2026-09-04T10:00:00Z'}, input_type=dict]
    For further information visit https://errors.pydantic.dev/2.13/v/missing
```

Note what that error names. It complains about `ttl` being **missing**, not about `ttlMs` being wrong,
because `ttlMs` was quietly accepted as an extra field. The value you sent is somewhere in that
truncated `input_value` and is being ignored. This is the most confusing shape a naming mismatch can
take: the data is present, visible in the error, and unused. Reproduce it with:

```bash
uv run python -c "
from mcp.types import Task
Task.model_validate({'taskId':'tsk_9Fq2mR7wZk4bT1cs','status':'working','ttlMs':3600000,'createdAt':'2026-09-04T10:00:00Z','lastUpdatedAt':'2026-09-04T10:00:00Z'})
"
```

**Line by line:**

- `model_validate` on a plain dict is what the SDK does to every incoming message, so this is the real
  code path rather than a simulation of it.
- The dict spells the field `ttlMs`, the specification's name, and supplies every other required field
  so that `ttl` is the only thing missing. That isolation is what makes the error readable.
- `createdAt` and `lastUpdatedAt` are required by this SDK's `Task` and are not in the extension's
  documented task object — one more difference between the two dialects, found by being forced to
  supply them.

The second break is the deprecation you never see:

```text
Traceback (most recent call last):
  File "<string>", line 1, in <module>
  File "...\.venv\Lib\site-packages\typing_extensions.py", line 3139, in wrapper
    warnings.warn(msg, category=category, stacklevel=stacklevel + 1)
DeprecationWarning: The experimental tasks API is deprecated and will be removed in mcp 2.0: tasks (SEP-1686) were removed from the MCP specification and are expected to return as a separate MCP extension.
```

That is the output of:

```bash
uv run python -W error::DeprecationWarning -c "from mcp.server.lowlevel import Server; Server('x').experimental"
```

**Line by line:**

- `-W error::DeprecationWarning` promotes the warning to an exception, which is the only way to make it
  stop the program and therefore the only way to be sure you have seen it.
- `Server('x').experimental` touches the deprecated property and nothing else — no server is started and
  nothing listens.

Without `-W error::DeprecationWarning` — or the `catch_warnings` block above — that message does not
appear at all in a normal run, because Python hides `DeprecationWarning` outside `__main__`. A whole
feature can be built on a deprecated API and the only notice is one Python decided you did not need to
see.

## In production

**What a professional writes instead:** a test that asserts the dependency's surface, not a comment
recording it. One test that reads `mcp.types.LATEST_PROTOCOL_VERSION` and compares it against the
revision the project targets; one that asserts the method names the code relies on are present. Both go
red on a dependency bump, which is exactly when you want to be told. Day 31's `./m check` is where such
a check belongs, and Day 45's audit is where it gets institutionalised.

**What degrades at scale and under concurrency:** this one does not degrade with load, it degrades with
**time and team size**. The gap between the specification and a pinned library grows quietly, and the
people who join later read the documentation rather than the package — so the newest engineer is the
most likely to write `ttlMs` against a library that wants `ttl`. The mitigation is that the constraint
lives in a test rather than in the memory of whoever pinned the version.

**The review comment a senior engineer leaves:** *"You are calling `server.experimental` for tasks. That
property is deprecated in this version and the API behind it was removed from the spec — we are building
on something that is scheduled to disappear. Either implement the extension shapes ourselves, which is
about thirty lines, or raise a plan amendment to move the pin. Do not silently depend on the
experimental one."*

**The interview question:** *"how do you know your MCP SDK supports the feature you are about to use?"*
An honest answer: *"I ask the package, not my memory. `dir()` over the types module gives every method
string the request classes declare, `model_fields` gives the exact field names, and `catch_warnings`
around the import surfaces the deprecations Python hides by default. On our pinned version that turned
up something I would not have guessed: the SDK does have tasks, but it is the *experimental* pre-2026
version — `tasks/result` and `tasks/list` are there, `tasks/update` is not, and the fields are `ttl` and
`pollInterval` rather than `ttlMs` and `pollIntervalMs`. The SDK's own deprecation warning says the
feature was removed from the spec and will come back as an extension. So we implemented the extension's
message shapes by hand and wrote down which half we could actually run, rather than pretending the
library covered it."*
