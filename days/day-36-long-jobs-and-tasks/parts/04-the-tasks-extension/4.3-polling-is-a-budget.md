# 4.3 — Polling is a budget

## One-line answer

`pollIntervalMs` is the server telling you how often it is worth asking, and a client that ignores it
turns one long job into thousands of requests that buy nothing — so the cadence is a spending decision,
multiplied by every task and every client.

## The story

You put a cake in the oven and the recipe says leave it alone.

You cannot leave it alone. You open the door to look at it, and again, and again, because looking feels
like doing something. Every time you open it the heat drops, the temperature has to climb back, and the
cake takes longer than it would have if you had never looked. Eventually you get a cake that is fine and
took longer than it should have, and you have learned nothing that you would not have learned by
looking twice.

The recipe's timing was not a suggestion to be polite about. It was the person who wrote it telling you
the smallest number of times you need to look, which is the same as telling you the largest number of
times looking is free.

## The idea in plain language

A `CreateTaskResult` carries `pollIntervalMs`: the server's suggestion for how often the client should
call `tasks/get`. The extension's client instructions put it plainly
(`https://modelcontextprotocol.io/extensions/tasks/overview`, read 2026-09-04):

> *"Call `tasks/get` with the returned `taskId`, respecting the `pollIntervalMs` value. Continue polling
> until the task reaches a terminal status."*

It is a hint, not a rule. Nothing rejects a client that polls faster. Which is exactly why it needs
thinking about, because the cost of ignoring it does not land on the person ignoring it.

**Polling is the only universal mechanism.** The extension does allow servers to push updates —
`notifications/tasks` over `subscriptions/listen` — and the overview says a client may rely on those
instead. But push is optional on the server side, so every client must be able to poll, and polling is
what you should design against.

**Every poll is a real request.** It goes over the network, through the gateway, into a server process,
and reaches the store for a read. Day 32's part
[3.3](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md) already
did this arithmetic for tool listings and turned sixty requests into one; this is the same arithmetic
with a different multiplier, and the multiplier here is *the length of the job*.

**The number multiplies twice.** Once by the number of tasks running concurrently, and once by the
number of clients. A cadence that looks harmless for one job is a load test when a hundred are in
flight.

So what should a client actually do? Three strategies, and the third is the one that ships:

- **Fixed and impatient.** Ask constantly. Maximum freshness, absurd cost, and the answer arrives no
  sooner — the job finishes when it finishes.
- **Fixed at the server's hint.** Ask at exactly `pollIntervalMs`. Reasonable, obedient, and still
  linear in the length of the job.
- **Backoff from the hint, with a cap.** Start at `pollIntervalMs`, double the wait each time, stop
  doubling at a ceiling. Cost becomes roughly logarithmic in the length of the job, and the only thing
  you lose is freshness at the end — you might learn about the finish a little after it happened.

That last trade is the one to be able to defend, because it is a genuine loss and it is usually the
right one. A job that runs for a long time is a job nobody is watching second by second.

## Why Sutra needs it

Because Sutra's budget is denominated in requests, and this is the first thing it has built whose
request count is not bounded by what the user asked for.

**Day 24** built token accounting and budgets, and made the point that a budget you do not measure is a
number you hope about. Polling is the first mechanism in this curriculum where the *client's* politeness
decides the *server's* load, and it deserves the same treatment.

**Day 44** hardens the client with retries, timeouts and backoff. The backoff loop written there is the
same loop as the one here, and it should not be written twice — this part is where the shape is chosen.

**Day 73** runs the nightly re-index unattended. Nobody is watching, so freshness is worth nothing, so
the cap can be high. Deciding that deliberately is the difference between a scheduled job that costs
eighteen requests and one that costs two thousand.

## The mechanism

The arithmetic, for one job of a known length:

```python
# days/day-36-long-jobs-and-tasks/lab/poll.py
JOB_MS = 420_000
SERVER_POLL_INTERVAL_MS = 2_000
CAP_MS = 30_000


def fixed(interval_ms: int, job_ms: int) -> tuple[int, int]:
    """Ask on a metronome. Returns (requests, ms of staleness at the end)."""
    requests = job_ms // interval_ms + 1
    return requests, interval_ms
```

**Line by line:**

- `JOB_MS = 420_000` is the same job as part
  [1.2](../01-the-blocking-call/1.2-the-timeout-ladder.md)'s ladder, so the two parts are talking about
  one thing. Underscores again, because every field in this extension is milliseconds and the digit
  count is what people get wrong.
- `SERVER_POLL_INTERVAL_MS = 2_000` is what the server suggested in the `CreateTaskResult` from part
  [4.1](4.1-four-messages-on-the-wire.md).
- `CAP_MS = 30_000` is the ceiling for the backoff arm. It exists because unbounded doubling eventually
  produces a client that would not notice the job finishing until long after it did.
- `job_ms // interval_ms + 1` counts the polls: one per interval, plus the final one that returns the
  terminal status. The `+ 1` matters — it is the poll that actually collects the result, and forgetting
  it is how people undercount by exactly the number that ends the loop.
- The second element of the tuple is **staleness**: how long the answer could have been sitting there
  before you asked. For a fixed loop it is the interval itself, which is the honest way to describe what
  a cadence buys.

```python
def backoff(start_ms: int, cap_ms: int, job_ms: int) -> tuple[int, int]:
    """Double the wait each time, up to a ceiling. Returns (requests, final gap)."""
    elapsed = 0
    wait = start_ms
    requests = 1
    while elapsed < job_ms:
        elapsed += wait
        requests += 1
        wait = min(wait * 2, cap_ms)
    return requests, wait
```

**Line by line:**

- `requests = 1` starts at one because the client has already been told `working` by the
  `CreateTaskResult` — the handle arrived with a status, so the first poll is not needed just to learn
  that the job started.
- `elapsed += wait` before `requests += 1` models the client sleeping and *then* asking, which is the
  right order: a client that asks and then sleeps has made one pointless request at the start.
- `wait = min(wait * 2, cap_ms)` is the entire policy. Doubling is not sacred — any growth factor works
  — but doubling is what everybody writes, and the `min` is the part that must not be forgotten.
  Without the cap this loop eventually waits longer than the job's own TTL and asks about a handle the
  server has already swept.
- The loop condition uses the job's length, which a real client does not know. That is fine here
  because the demo is measuring **cost for a job of this length**; a real client loops until the status
  is terminal and gets the same count.
- Returning `wait` as the final gap is the price tag: this is how stale the answer can be by the end,
  and it is the number to put next to the request saving when somebody asks whether backoff is worth it.

Run it:

```bash
uv run python days/day-36-long-jobs-and-tasks/lab/poll.py
```

**Line by line:**

- From the repository root. **Zero model calls**, no network, no sleeping — it is arithmetic, so it
  finishes instantly and you can change the constants and re-run freely.

Measured on 2026-09-04:

```text
job: 420s, server suggests pollIntervalMs=2000

  ignore the hint, poll every 200ms   :  2101 requests, worst staleness 200ms
  obey pollIntervalMs                 :   211 requests, worst staleness 2000ms
  backoff from the hint, cap 30000ms  :    18 requests, worst staleness 30000ms

  eager costs 9x the obedient loop for the same answer
  100 concurrent tasks, eager         :  210100 requests
  100 concurrent tasks, backoff       :    1800 requests
```

**2101 against 18.** Same job, same result, same moment of completion. The eager client spent a hundred
and sixteen times as many requests to learn the answer a little sooner, and the last two lines are what
that looks like on a server with a hundred jobs running: two hundred and ten thousand requests against
eighteen hundred.

The three cadences, side by side:

| Strategy | Requests | Worst staleness | What it buys |
| --- | --- | --- | --- |
| every `200ms`, ignoring the hint | 2101 | `200ms` | the answer a fraction sooner |
| every `2000ms`, obeying the hint | 211 | `2000ms` | politeness, still linear in the job |
| backoff from the hint, cap `30000ms` | 18 | `30000ms` | a bounded cost, at the price of the last gap |

All three learn the answer at the same moment, because the job finishes when it finishes. That is the
argument: the job's length is fixed, and the only thing the cadence changes is what you paid to watch
it.

## When it breaks

The break is a server that starts refusing, and the refusal arrives at the *polling* client rather than
at the one doing anything wrong:

```text
HTTP 429 Too Many Requests
Retry-After: 30
```

A gateway counting requests per client per minute does not know that two thousand of them were polls
about one job. It sees an abusive client and throttles it — which then also throttles the ordinary tool
calls that client needed to make, so the agent stops working for a reason that has nothing to do with
the tool it was trying to use.

The second break is the one caused by *fixing* the first badly. Someone reads the 429, adds backoff with
no cap, and the client eventually waits longer than the handle's `ttlMs`:

```text
{"error": {"code": -32602, "message": "unknown task tsk_9Fq2mR7wZk4bT1cs"}}
```

The task completed, the result was written, the row was swept when its TTL expired, and the client
arrived after the sweep. It looks identical to the not-found error from part
[3.2](../03-the-handle/3.2-the-handle-anyone-can-guess.md) — deliberately, since a server must not
distinguish its misses — so the only way to know which happened is to have capped the backoff below
`ttlMs` in the first place. That is the rule worth writing down: **the cap belongs under the TTL, and
the TTL is a number the server sent you.**

## In production

**What a professional writes instead:** the polling loop is one function, shared by every caller, that
takes the `pollIntervalMs` and `ttlMs` the server sent and derives its own schedule from them —
starting at the hint, doubling, capping well below the TTL, and adding a small random jitter so that a
hundred clients that started together do not all ask at the same instant. The loop stops on a terminal
status, not on a timeout, because part [4.2](4.2-five-statuses-and-the-terminal-rule.md) guaranteed
there is one.

**What degrades at scale and under concurrency:** polling load is **synchronised** by default, which is
the failure mode nobody predicts. A nightly job that starts a hundred tasks at the same moment produces
a hundred clients polling in lockstep, so the server sees spikes with quiet gaps rather than steady
load, and it must be sized for the spike. Jitter is what turns a spike back into a line, and it costs
one call to `random.uniform`. The other thing that degrades is the store: every poll is a read on the
same hot row, and a hundred lockstep clients are a hundred simultaneous reads of one primary key.

**The review comment a senior engineer leaves:** *"This polls every two hundred milliseconds and ignores
`pollIntervalMs` entirely. For a seven-minute job that is two thousand requests to learn one string, and
when this runs for a hundred tickets at once we will rate-limit ourselves out of our own API. Use the
server's hint, back off, cap under `ttlMs`, and add jitter."*

**The interview question:** *"the server told you to poll every two seconds. Do you?"* An honest answer:
*"I start there and then back off, doubling up to a cap, because the cost is linear in the length of the
job and the benefit is not. I measured it for a seven-minute job: obeying the hint is two hundred and
eleven requests, backing off with a thirty-second cap is eighteen, and both learn the answer at the same
moment. What I would not do is remove the cap — the backoff has to stay comfortably under the handle's
`ttlMs`, or you come back after the row has been swept and get an unknown-task error that looks exactly
like the job never existed. And I would add jitter, because a hundred tasks started by one nightly job
otherwise poll in lockstep and turn steady load into spikes."*

all three strategies converge: for a short job the cadence hardly matters, which is why this only ever
becomes a problem once something gets slow.
