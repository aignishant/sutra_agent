# 5.2 — 💥 The checkpoint that makes cancel real

## One-line answer

A cancel can only take effect where the work stops to look, so a job with no checkpoint is a job that
cannot be cancelled — and from the outside it is **indistinguishable** from one that simply had not got
there yet.

## The story

Your neighbour is cutting his grass with headphones on.

You need to tell him the gate is open and the dog is out, so you wave from the fence. He does not see
you. He is walking away from you up the garden, and he will not look in your direction until he gets to
the top, turns the mower round, and starts back down.

So you wait at the fence for the length of one stripe. Then he turns, sees you, stops the mower and
pulls the headphones off.

The gap between you waving and him stopping had nothing to do with how loudly you waved. It was set
entirely by how often he turns round. If he mowed in one continuous spiral he would never face you at
all, and you could stand at that fence all afternoon.

## The idea in plain language

Part [5.1](5.1-cancel-is-a-request-not-a-switch.md) established what `tasks/cancel` promises: the
message is delivered and the intent is recorded, and the specification is explicit that the server is
not obligated to stop. This part is about what makes a server able to stop at all.

The answer is a **checkpoint**: a point in the work where the code puts the job down, looks at the
cancel flag, and decides whether to pick it up again. Not an interrupt, not a signal, not a
`Thread.stop`. A voluntary look.

Three things follow, and they are the design rules.

**No checkpoint, no cancellation.** Code that does not look cannot be told. A tool whose whole body is
one long call into a library — a single query, a single large read, a single sleep — has no place to
look, so a cancel arriving during it can do nothing whatever until it returns.

**The checkpoint interval is the cancellation latency.** How long a cancel takes to take effect is
exactly how long until the next look. Checking once per ticket in a hundred-thousand-ticket re-index
means a cancel takes effect almost immediately. Checking once per *archive* means it never does.

**Checkpoints must sit between units of work, not inside them.** The work between two checkpoints has
to be a thing that either happened or did not. Stopping halfway through writing a row leaves the row
half-written, and now cancellation has become a data-corruption feature.

There is a fourth point which is really the reason this part is in the failure lab. **A server that
ignores cancels looks exactly like a server that is being slow about them.** From the client's side you
sent `tasks/cancel`, you got an acknowledgement — which is what a compliant server sends — and the
status is still `working`. Is the worker about to notice, or is there no checkpoint in that code at
all? You cannot tell from the outside, and you cannot tell from the protocol, because both are legal
and both look identical. The only way to know is to read the server's code or to watch the task run to
`completed` after you asked it to stop.

That is why the ablation switch in the demo matters. It turns the checkpoint off and leaves every
message unchanged, so you can see for yourself that the wire traffic does not distinguish the two.

## Why Sutra needs it

Because Sutra's expensive work is a loop, and where the check goes in that loop is a decision somebody
makes once and nobody revisits.

**Day 49's** re-index reads the ticket archive one chunk at a time. That loop is the natural checkpoint,
and it is natural only because the work is chunked — if the index build were one library call over the
whole archive there would be nowhere to look, and the honest answer would be that the tool cannot be
cancelled.

**Day 39** puts SQL behind MCP tools. A single long-running query is the canonical uncancellable unit:
your Python is blocked inside the driver, not in your loop. The database has its own cancellation
mechanism, and reaching it is a different piece of work from setting a flag.

**Day 16** built code execution with brakes, and Principle 13 says every new power arrives with its
containment story. A tool you can start and cannot stop has a containment story with a hole in it, and
the checkpoint is how the hole gets closed.

## The mechanism

One switch, two runs, identical protocol traffic. The switch:

```python
# days/day-36-long-jobs-and-tasks/lab/cancel.py  (extract)
CHECKPOINTS = os.environ.get("CHECKPOINTS", "1") != "0"


def worker() -> None:
    """Index the archive one chunk at a time."""
    for _ in range(CHUNKS):
        time.sleep(CHUNK_S)
        with lock:
            if CHECKPOINTS and task["cancel_requested"]:
                task["status"] = "cancelled"
                task["statusMessage"] = f"stopped after {task['done']} of {CHUNKS} chunks"
                return
            task["done"] = int(task["done"]) + 1
    with lock:
        if task["status"] == "working":
            task["status"] = "completed"
            task["statusMessage"] = f"re-indexed {task['done']}/{CHUNKS} chunks"
```

**Line by line:**

- `os.environ.get("CHECKPOINTS", "1") != "0"` defaults to **on**, because the correct version should be
  what you get if you type nothing. An ablation switch that defaults to the broken arm teaches the
  wrong reflex.
- `CHECKPOINTS and task["cancel_requested"]` is the ablation, and it is the **only** difference between
  the two arms. `tasks_cancel` is untouched, the flag is still set, the acknowledgement is still sent —
  the work simply never looks.
- `time.sleep(CHUNK_S)` before the check models one unit of work. Put the check before the sleep instead
  and the demo's latency changes by one chunk, which is a small illustration of the rule that the
  checkpoint interval *is* the cancellation latency.
- The check is inside `with lock:` and immediately before the `done` increment, so the worker never
  stops between reading the flag and updating its own progress. Those two facts have to move together
  or the `statusMessage` can be off by one.
- `return` — not `break`, not a flag that gets checked later. Leaving the function is the stop, and
  everything after the loop is skipped, including the completion write.
- `if task["status"] == "working"` at the end is the guard from part 5.1, and in this file it is what
  stops the ablated arm from being *ambiguous*: with checkpoints off, the status is still `working` when
  the loop ends, so the completion path fires and you see `completed` rather than something confusing.

Run **both** arms. That is the point of the part:

```bash
CHECKPOINTS=1 uv run python days/day-36-long-jobs-and-tasks/lab/cancel.py
CHECKPOINTS=0 uv run python days/day-36-long-jobs-and-tasks/lab/cancel.py
```

**Line by line:**

- From the repository root. **Zero model calls**, no network. The environment variable is read once at
  import, so each arm is a separate process — which is also how one deployment differs from another:
  the switch is a property of how the server was started, not something you can flip mid-run.

Measured on 2026-09-04, checkpoints **on**:

```text
checkpoints in the worker : True
client sends tasks/cancel : {'resultType': 'complete', 'taskId': 'tsk_cancel_demo', 'status': 'working'}
final status              : 'cancelled'
statusMessage             : 'stopped after 2 of 8 chunks'
chunks actually indexed   : 2 of 8
```

And checkpoints **off**:

```text
checkpoints in the worker : False
client sends tasks/cancel : {'resultType': 'complete', 'taskId': 'tsk_cancel_demo', 'status': 'working'}
final status              : 'completed'
statusMessage             : 're-indexed 8/8 chunks'
chunks actually indexed   : 8 of 8
```

**The second line is identical in both runs.** Same acknowledgement, same fields, same `status:
'working'`. A client capturing the wire traffic at that moment cannot tell which server it is talking
to. The difference appears only in the terminal status, several polls later — `cancelled` with two
chunks done, or `completed` with all eight.

The scene format, because this is a failure part:

> 🎬 **The scene:** somebody starts a full re-index on the wrong archive and immediately clicks stop.
> 😬 **The naive fix:** implement `tasks/cancel`, set the flag, return the acknowledgement, ship it. The
> protocol is satisfied and the tests pass, because the tests assert on the acknowledgement.
> 💥 **Why it fails:** nothing in the worker ever reads the flag. The intent is recorded perfectly and
> acted on by nobody, and the job runs to completion using every bit of the quota it was going to use.
> The wire traffic is byte-for-byte what a working implementation sends, so no test that looks at
> messages can catch it.
> 💡 **The insight:** cancellation lives in the **work**, not in the protocol. The verb delivers an
> intention; only a checkpoint can act on one. So the test that matters is not "does cancel return a
> result" but "does the job stop", and the only way to write that test is to count how much work
> actually happened.

## When it breaks

The most common uncancellable shape is not a missing `if`. It is a checkpoint that exists and never
gets reached, because the work between two checks is one long blocking call:

```python
def reindex(archive: str) -> str:
    for chunk in load_chunks(archive):  # one call, the whole archive
        index(chunk)
        if cancel_requested:  # never reached until load_chunks returns
            return "cancelled"
    return "done"
```

**Line by line:**

- `load_chunks(archive)` is written as though it streams, and if it returns a list rather than a
  generator it reads the entire archive before the loop body runs once. The check is inside a loop that
  has not started.
- `index(chunk)` may itself be a long library call — a database write, an HTTP request, a model call —
  and while it is running the flag cannot be read no matter how many checks surround it.
- `if cancel_requested` looks like a checkpoint and is one. The bug is not the line; it is the
  **distance between two of them**, which is decided by what is above it.
- The fix is not another `if`. It is making the work smaller: a generator instead of a list, a batch
  instead of a whole archive, a timeout on the library call so control comes back.

The version that produces an actual error is worse and is worth naming so you do not write it. Somebody
loses patience with cooperative cancellation and reaches for force:

```text
AttributeError: 'Thread' object has no attribute 'stop'. Did you mean: '_stop'?
```

The suggestion at the end of that message is a trap worth naming: `_stop` exists, it is private, and it
marks the thread as stopped without stopping anything at all.

Python has no way to stop a thread from outside, on purpose, and the reason is exactly the data-integrity
one from the rules above: a thread killed at an arbitrary instruction leaves whatever it was holding in
an arbitrary state. The absence of that method is a design decision, not a gap.

And the failure with no error text at all is the one the demo measures: `final status: 'completed'` for
a task the user cancelled. No exception, no log line, no protocol violation. Just work that happened
after somebody asked for it not to.

## In production

**What a professional writes instead:** the cancel check is part of the loop's contract, not an
afterthought — a helper the worker calls every batch, which reads the row and raises a specific
`TaskCancelled` exception. Raising rather than returning means the stop propagates out of nested
helpers without every one of them needing to understand cancellation, and a single `except
TaskCancelled` at the top writes the terminal status and the partial-progress message. The batch size
is chosen so the check happens often enough to matter and rarely enough not to hammer the store.

**What degrades at scale and under concurrency:** the checkpoint reads shared state, so a naive
implementation reads the task row on every iteration and turns a hundred-thousand-item loop into a
hundred thousand extra reads — the polling arithmetic from part
[4.3](../04-the-tasks-extension/4.3-polling-is-a-budget.md), arriving from inside the server this time.
The usual answer is to check every batch rather than every item, and to accept that cancellation
latency is then bounded by a batch. Under concurrency there is a second effect: a mass cancellation —
somebody stopping fifty jobs at once — produces fifty workers all reading their rows and all writing
terminal statuses in the same instant, which is a write spike on a table that is otherwise read-mostly.

**The review comment a senior engineer leaves:** *"There is no cancel check inside the indexing loop, so
`cancel_task` sets a flag that nothing reads. Our tests pass because they assert on the acknowledgement,
which is exactly the thing that is correct in the broken version. Add the check per batch, and change
the test to assert on the number of chunks indexed after a cancel — that is the only assertion that can
tell the two implementations apart."*

**The interview question:** *"you have implemented `tasks/cancel` and jobs still run to completion. What
is wrong?"* An honest answer: *"almost certainly there is no checkpoint. Cancellation in MCP is
cooperative: the verb records an intent, and the only thing that can act on it is the code doing the
work, at a point where it stops to look. If the work is one long call — a big query, a whole-archive
read — there is nowhere to look and the cancel cannot land until it returns. So I would chunk the work
and check between chunks, and I would size the chunk deliberately, because the checkpoint interval *is*
the cancellation latency. The thing I would flag in review is that this bug is invisible on the wire:
the acknowledgement a broken server sends is identical to the one a working server sends, so the test
has to count work done, not messages returned."*

## Check yourself

```bash
CHECKPOINTS=0 uv run python days/day-36-long-jobs-and-tasks/lab/cancel.py
CHECKPOINTS=1 uv run python days/day-36-long-jobs-and-tasks/lab/cancel.py
```

Now move the `if CHECKPOINTS and task["cancel_requested"]` block to **after** the `done` increment and
run the on-arm again: the `statusMessage` changes, because the worker now records one more chunk before
noticing. Then move the check outside the `for` loop entirely — a checkpoint that exists and is reached
once, at the end — and watch the on-arm behave exactly like the off-arm.
