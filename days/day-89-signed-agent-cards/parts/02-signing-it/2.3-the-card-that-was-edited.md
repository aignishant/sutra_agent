# 2.3 — The card that was edited

## One-line answer

Change one character of the advertised url after signing — `127.0.0.1` to `127.0.0.9` — and the card
is still 952 bytes, still valid JSON, still carries a real signature made by a real key, and
verification raises `InvalidSignature`, which is the entire value of the exercise.

## The story

The cheque with the amount altered.

A cheque is written for two thousand and signed. Somewhere between the hand that wrote it and the
counter that pays it, a nought is added. Now it says twenty thousand.

Everything about the cheque is still genuine. The paper is the bank's. The account number is right.
The signature is a real signature, made by the real person, and it has not been touched — it is
exactly the ink they put there.

What is no longer true is the *relationship* between the signature and the amount. The signature was
given in exchange for one document and it is now attached to a different one, and the only reason
anybody can tell is that the two are checked against each other rather than separately.

## The idea in plain language

A signature does not protect a document. It **binds** a key to a specific byte string. Verification
asks one question — *were these exact bytes signed by the key I am checking against?* — and the only
answers are yes and no.

That is a narrow guarantee and it is worth being precise about what it does and does not give you:

**What it gives you.** Nobody without the private key produced these bytes. If the card verifies
against a key you trusted in advance, then the holder of that key stands behind every field in it:
the url, the skills, the version, all of it.

**What it does not give you.** Anything about whether the claims are *true*. A signature over a card
saying `"skills": ["can approve refunds up to a million"]` is a perfectly valid signature. It proves
who said it, not whether they should have.

**And what it specifically does not give you** is protection against an edit — it gives you
*detection* of one. The bytes can be changed by anybody. What they cannot do is produce a signature
that still matches, so the change becomes visible at the moment somebody checks.

The interesting part is which field an attacker would edit. Not the skills — those are advertising.
The url. A card that verifies is a card a peer will dial, and the url is the one field that decides
*where* the work goes.

## Why Sutra needs it

Because "verified hands-on" in the plan's day title means seeing a verification fail on purpose, once,
so that a passing verification later means something. Day 79 established the rule for the eval suite
and it is the same rule here: a check that has never been observed to fail is not evidence.

And because the specific edit matters for Sutra. The card advertises the desk's rpc url; the desk
handles refunds and escalations. A peer that follows an edited url sends ticket contents and approval
requests to whoever chose it.

## The mechanism

The tamper is one character in the field that decides where work goes:

```python
    if tamper:
        was = card["supportedInterfaces"][0]["url"]
        card["supportedInterfaces"][0]["url"] = was.replace("127.0.0.1", "127.0.0.9")
```

**Line by line:**

- `supportedInterfaces[0]["url"]` is the address a peer dials — one of the eight fields ADK filled
  in part [1.1](../01-the-card/1.1-the-card-is-the-interface.md).
- One character: `1` to `9`. The card stays the same length, so anything checking size sees nothing.
- The edit happens **after** `payload` was computed and signed, and **before** `checked` is computed.
  That ordering is the whole experiment: same signature, different document.
- `.replace(...)` on the string rather than assigning a literal, so the printed before-and-after lines
  cannot drift from what was actually changed.

Verification is the same call as in part [2.2](2.2-signing-the-card.md), against the re-derived bytes:

```python
    try:
        key.public_key().verify(signature, signing_input(protected, checked))
    except InvalidSignature:
```

**Line by line:**

- `signing_input(protected, checked)` rebuilds the input from the card **as presented**, which is
  what a verifier has. It never sees `payload`.
- `verify` returns `None` on success and raises on failure — it does not return a boolean. Writing
  `if key.public_key().verify(...)` is therefore always falsy and always wrong, and it is a mistake
  that turns every card into a rejected card, which at least fails safe.
- Catching `InvalidSignature` specifically, not `Exception`. A malformed base64 payload raises
  something else entirely and should not be reported as a forgery.

Run both arms:

```bash
cd days/day-89-signed-agent-cards/lab
uv run python sign.py; echo "exit: $?"
uv run python sign.py --tamper; echo "exit: $?"
```

**Line by line:**

- Same key, same card, same code path. `--tamper` inserts one character between signing and checking.

Measured on 2026-09-07:

```text
  one character of the advertised url changed after signing:
    http://127.0.0.1:8931 -> http://127.0.0.9:8931

  bytes signed:   952
  bytes verified: 952

  cryptography.exceptions.InvalidSignature
  the card presented is not the card that was signed
exit: 1
```

**952 and 952.** Identical lengths, valid JSON both times, a genuine signature by a genuine key — and
`InvalidSignature`. Every check that is not the signature passes: the card parses, the schema is
satisfied, the url is a well-formed url pointing at a reachable host. Only the binding between the
key and the bytes noticed.

## When it breaks

The check itself is reliable. What breaks is everything around it, and there are three ways.

**The verifier does not run.** Overwhelmingly the most common. The card is fetched, parsed and used;
`signatures` is empty or ignored; nothing fails, because nothing looked. This is the state Sutra is in
today, measured in part [1.1](../01-the-card/1.1-the-card-is-the-interface.md) as `signatures: 0`.

**The verifier runs and the result is discarded.** Verification is called inside a `try` that catches
broadly, logs a warning, and carries on — because the first integration failed for a
canonicalisation reason (part [2.1](2.1-a-signature-is-over-bytes.md)) and somebody made it stop
blocking. The log line exists. Nobody reads a warning that fires on every card.

**The verifier runs, fails, and the caller does not know what to do.** This is the honest one. A
failed signature is ambiguous — wrong key, wrong bytes, or an attack — and if the only handling is
`raise`, then a peer rotating a key takes your integration down. That is a real operational cost and
it is why the answer is not "verify harder" but Day 90's registry, where key rotation is an event you
can survive.

There is no error text for the first two, which is the point: a signature check that is not wired to
a refusal is a comment.

## In production

**What a professional does.** Verifies before parsing, and refuses on failure with a distinct,
countable outcome — not an exception that looks like every other exception. The number of cards that
failed verification, per peer, is a metric worth having on the same dashboard as the request counts,
because a peer that starts failing verification is either compromised or has rotated a key, and both
need a person.

**What degrades at scale.** The ambiguity gets expensive. Ten peers and a human can chase a
verification failure; a thousand and you need the failure to say which of the three causes it was,
which means recording the `kid`, the digest, and whether that `kid` is known — so that "rotated" and
"forged" are different rows rather than the same alert.

**The failure that only shows with real traffic.** A middlebox that rewrites. A proxy that
canonicalises JSON, a CDN that minifies, a gateway that injects a header into a body — anything on
the path that touches the bytes turns every card into a forgery. It is indistinguishable from an
attack at the verifier and it is almost always infrastructure, which is why the digest belongs in the
log.

**The review comment a senior engineer leaves:** *"Verification failure needs its own return, not an
exception. Right now a peer rotating a key and a peer being impersonated produce the same traceback,
and we will treat both as noise within a week."*

**The interview question:** *"What does a valid signature on a document tell you?"* The answer that
shows experience is narrow and immediate — that the holder of a specific key produced these exact
bytes — and then says the two things it does not tell you: whether the claims are true, and whether
the key is one you should trust. The second of those is tomorrow.
