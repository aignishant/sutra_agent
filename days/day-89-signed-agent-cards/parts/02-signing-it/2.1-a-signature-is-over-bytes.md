# 2.1 — A signature is over bytes

## One-line answer

You cannot sign an object, only a byte string, so before any cryptography happens both sides must
agree on exactly one way to write the card down — sorted keys and no spaces gives the same 952 bytes
whatever order the card was built in, and `indent=2` gives two different digests for the same card.

## The story

Reading out an account number.

You are transferring money and you read the number over the phone. The person at the other end reads
it back. You both agree, and you both know why the reading-back happens: what matters is not that you
each *have* the number but that you each have the same one, character for character.

So people develop habits. Some read digit by digit. Some group in pairs. Some say "double four".
Whichever it is, the two of you have to be doing the same thing or the read-back proves nothing —
"four four" and "double four" are the same number and a different sentence, and if you are checking
sentences you will disagree about a number you both got right.

## The idea in plain language

A signing algorithm takes a private key and a **sequence of bytes**, and returns a signature over
those exact bytes. It has no idea what a JSON object is. Change one byte and the signature no longer
matches; the algorithm cannot tell whether the change was meaningful.

That is a problem for a document like an agent card, because the same card can be written down many
ways and they are all valid JSON:

- keys in the order the builder produced them, or sorted
- `{"a": 1}` or `{"a":1}` — a space after the colon is legal and changes the bytes
- indented for a human, or minified for the wire

A peer that fetches your card, parses it into a dictionary, and then serialises it again to check the
signature will produce whatever its own JSON library produces. If that differs from what you signed
by a single space, verification fails and the card looks forged.

So the two sides need one rule. This lab uses the simplest one that works:

```text
json.dumps(card, sort_keys=True, separators=(",", ":"))
```

Sorted keys make ordering irrelevant. The tight separators remove every optional space. Encode that
as UTF-8 and you have the byte string both sides can reach independently.

That is a **canonicalisation**: a rule that maps many equivalent documents to exactly one byte
string. It is not glamorous and it is where signature schemes actually fail.

## Why Sutra needs it

Because part [2.2](2.2-signing-the-card.md) is about to sign the card and part
[2.3](2.3-the-card-that-was-edited.md) about to verify it, and both are meaningless unless the bytes
are pinned first. A verification failure caused by serialisation looks identical to one caused by
tampering, and the two need opposite responses.

And because the card is built by ADK from a protobuf message and converted to JSON by
`MessageToDict`. Sutra does not control the key order it comes back in, and does not need to, as long
as the rule makes order irrelevant.

## The mechanism

The rule, in one function:

```python
def card_bytes(card: dict) -> bytes:
    """The exact bytes a signature is taken over."""
    return json.dumps(card, sort_keys=True, separators=(",", ":")).encode("utf-8")
```

**Line by line:**

- `sort_keys=True` sorts every object's keys, at every level of nesting, so the ordering of the
  dictionary that came out of `MessageToDict` stops mattering.
- `separators=(",", ":")` removes the space Python otherwise puts after each `:` and `,`. Two
  characters per field is not the point — determinism is.
- `.encode("utf-8")` makes it bytes rather than a string. A signing call given a `str` raises, and
  on a card containing a non-ASCII character the encoding is not a formality: the same text encoded
  two ways is two different byte strings.
- No timestamp, no nonce, nothing generated. Everything in the input is a function of the card, so
  the same card always produces the same bytes on any machine.

The test is whether two orderings of the same card land on one digest:

```python
    card = card_dict()
    shuffled = dict(reversed(list(card.items())))
    first, second = encode(card), encode(shuffled)
```

**Line by line:**

- `dict(reversed(list(card.items())))` rebuilds the dictionary with its top-level keys in the
  opposite order. Python dictionaries preserve insertion order, so this is a genuinely different
  object that means the same thing.
- The comparison is `first != second` on the bytes rather than on a parsed structure, because the
  bytes are what gets signed and structural equality is exactly the thing that is not being tested.

```text
  bytes as built:    1315  sha256 be00c09596b5fcfe52c24d9a79ca2b78

  a peer that re-serialises before verifying computes a different digest

```

**Identical digests, then two different ones.** Note that the pretty arm's two byte strings are the
same *length* — 1315 both times. Nothing is missing from either; the same content is arranged
differently, and that is enough. A length check, a field count, even a deep equality check on the
parsed objects would all say these two documents are the same. The signature says they are not.

Note also the size: 952 canonical bytes against 1315 pretty ones. Almost a third of the readable form
is whitespace, which is a reasonable argument for the tight separators on the wire and no argument at
all about signing.

## When it breaks

There is no exception here — that is the difficulty. Verification returns `False` and the caller has
to work out which of two very different things happened:

- somebody changed the card, or
- both sides are honest and are writing the same card differently

The second is the common one in a first integration and it produces a security-shaped alarm for a
formatting reason. The cheapest way to tell them apart is to log the digest and the byte length on
both sides — matching lengths with different digests, as in the pretty arm above, is the signature of
a canonicalisation mismatch rather than an edit.

The deeper trap is that the naive rule above is not the standardised one. `sort_keys` plus tight
separators is fine as long as *both sides run this exact code*, which is true inside one repository
and not true across an ecosystem. Two independent implementations can still disagree about how to
write a floating-point number, about escaping non-ASCII characters, and about Unicode normalisation.
There is a published canonicalisation scheme for JSON that pins all of that, and the honest position
is that this lab has pinned enough for one repository and not enough for the internet.

## In production

**What a professional does.** Signs the bytes that were actually transmitted, and stores them. The
strongest version of this problem is avoided rather than solved: keep the card as a byte string from
the moment it is signed, serve those bytes, and let the peer verify the bytes it received before it
parses them. Canonicalisation only becomes load-bearing when something in the middle re-serialises,
and the fix is usually to stop doing that.

**What degrades at scale.** Every additional implementation is another chance to disagree. One
service signing and one verifying with shared code is safe; a published card verified by clients in
four languages is a canonicalisation problem whether anybody planned for one or not, and that is when
a specified scheme stops being pedantry.

**The failure that only shows with real traffic.** A card containing a non-ASCII character. Every
test fixture is ASCII, so encoding and escaping never differ, and the first agent whose provider name
carries an accent produces verification failures for one peer's JSON library and not another's.

**The review comment a senior engineer leaves:** *"Do not re-serialise before verifying. Hold the
bytes you fetched, verify those, and parse afterwards — then none of this matters."*

**The interview question:** *"You sign a JSON document. What goes wrong?"* The answer that shows
experience goes straight to serialisation rather than to keys or algorithms, and names the tell:
verification failures that correlate with the client rather than with the document.
