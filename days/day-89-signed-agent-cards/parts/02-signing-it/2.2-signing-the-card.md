# 2.2 — Signing the card

## One-line answer

The specification says an `AgentCardSignature` is a JWS in JSON form, and it has exactly three
fields — `protected`, `signature`, `header` — so signing a card is: build a protected header, join it
to the card's canonical bytes with a dot, sign that, and base64url everything.

## The story

The specimen signature card at a bank counter.

When the account was opened, somebody signed a small card and it went into a drawer. Nothing about
that signature is secret; the whole point is that it can be looked at. What it establishes is a
reference — *this is the shape this person's hand makes* — held by the bank, not by the customer.

Years later a cheque arrives. The clerk does not ask the cheque whether it is genuine. He pulls the
card out of the drawer and compares. The cheque can say anything it likes about who wrote it; the
drawer is what decides.

Two things make that work, and only two. The bank got the specimen from a source it trusted, once, in
advance. And the comparison is against the drawer, never against something the cheque brought with
it.

## The idea in plain language

The A2A specification does not invent a signature format. Fetched from the specification page on
2026-09-07, section 4.4.7 says:

> *AgentCardSignature represents a JWS signature of an AgentCard. This follows the JSON format of an
> RFC 7515 JSON Web Signature (JWS).*

with three fields:

| Field | Required | What it is |
| --- | --- | --- |
| `protected` | yes | the JWS protected header, base64url-encoded JSON |
| `signature` | yes | the computed signature, base64url-encoded |
| `header` | no | the *unprotected* header — data outside the signature |

That is JWS's **JSON serialisation with a detached payload**. The payload is not in the signature
object, because the payload is the card the signature sits inside. A verifier reconstructs it.

The whole operation is four steps:

1. Write the card as canonical bytes — part [2.1](2.1-a-signature-is-over-bytes.md).
2. Build a protected header naming the algorithm and the key, and base64url it.
3. Join `protected` and the base64url payload with a `.` — this is the **signing input**.
4. Sign that byte string, base64url the result.

Step 3 is the one that carries the weight, and it is the paper's contribution rather than an
implementation detail: the header is *inside* what gets signed. Part
[papers/01](../../papers/01-a-signature-over-its-own-header.md) measures what happens when it is not.

**base64url**, throughout, is base64 with `-` and `_` instead of `+` and `/`, and the `=` padding
stripped — so the result survives being put in a url or a header without further escaping.

## Why Sutra needs it

Because part [1.1](../01-the-card/1.1-the-card-is-the-interface.md) measured `signatures: []` and
this is the part that fills it. ADK will not sign the card, correctly, so "verified hands-on" means
these four steps, written by the learner, over the card ADK actually produced.

And because the same four steps are what Day 90 builds a registry around. A signature is only half of
identity; the other half is the drawer, and that is tomorrow.

## The paper behind it

> **JSON Web Signature (JWS)**
> RFC Editor, 2015. `doi:10.17487/RFC7515`
>
> Defines a compact, JSON-based structure for a signature over arbitrary content, in which the
> signing input is the protected header and the payload joined together — so the parameters
> describing the signature are covered by it.

The A2A specification names this RFC directly rather than describing a format of its own, which is
why the field list above has exactly the shape it does. Read it after the parts:
[papers/01 — A signature over its own header](../../papers/01-a-signature-over-its-own-header.md).

## The mechanism

The protected header first:

```python
    protected = b64u(
        json.dumps({"alg": "EdDSA", "kid": KEY_ID}, sort_keys=True, separators=(",", ":")).encode()
    )
```

**Line by line:**

- `alg` names the algorithm. `EdDSA` is Ed25519 here — a modern signature scheme with small keys, no
  parameter choices to get wrong, and no random number needed at signing time.
- `kid` is a key identifier. It does not prove anything; it tells the verifier *which* of the keys it
  already holds to try, which is part [3.2](../03-the-verifier-decides/3.2-which-key.md).
- The same canonicalisation as the card, for the same reason. The verifier does not re-serialise this
  — it uses the string as transmitted — but signing and re-signing the same header should produce the
  same bytes.
- These two parameters go in the **protected** header, which is what makes them tamper-evident. Put
  `alg` in the unprotected `header` field instead and an attacker can change it freely.

Then the signing input, which is the RFC's step 5:

```python
def signing_input(protected: str, payload: bytes) -> bytes:
    """ASCII(BASE64URL(protected) || '.' || BASE64URL(payload)) - RFC 7515 section 5.1 step 5."""
    return f"{protected}.{b64u(payload)}".encode("ascii")
```

**Line by line:**

- `protected` is already a base64url string, so it is concatenated as-is; the payload is encoded
  here. Encoding `protected` twice is a real and easy mistake that produces a signature nobody else
  can verify.
- The `.` is a separator that cannot appear in base64url output, which is why base64url rather than
  base64: `/` and `+` would still be unambiguous here, but the alphabet is chosen so the whole
  structure survives in a url.
- `.encode("ascii")` rather than UTF-8 — deliberately. base64url output is ASCII by construction, so
  if anything non-ASCII has crept into `protected`, this raises `UnicodeEncodeError` at signing time
  instead of producing bytes the verifier will silently disagree with.

And the signature itself:

```python
    signature = key.sign(signing_input(protected, payload))
    entry = {"protected": protected, "signature": b64u(signature), "header": {"kid": KEY_ID}}
```

**Line by line:**

- `key.sign(...)` on an `Ed25519PrivateKey` takes the message and returns 64 raw bytes. There is no
  hash argument and no padding argument, because Ed25519 has no choices to make — which is most of
  the reason to prefer it here.
- `header` repeats the `kid` in the unprotected part. That is a convenience for a verifier choosing a
  key before it does any work, and it is **not** trustworthy: the protected copy is the one that
  counts, and part [3.1](../03-the-verifier-decides/3.1-the-algorithm-the-card-chose.md) is about
  what happens when a verifier forgets which is which.
- The key is generated per run in `_desk.py` and never written to disk. A lab that committed a
  private key would be teaching the opposite of Principle 9.

Run it:

```bash

```

**Line by line:**

- No flag: sign the card ADK built, then verify the signature against the same card.

**952 bytes signed, 952 verified, and one public key that fits on a line.** The public half is 44
base64 characters — an Ed25519 public key is 32 bytes — which is small enough to paste into a config
file, and that matters more than it sounds: a trust anchor people can read and compare by eye is one
they will actually check.

## When it breaks

The failure that costs the most time is not cryptographic. It is signing the wrong bytes, and its
symptom is a signature that verifies on the machine that made it and nowhere else.

Three ways to get there, in order of how often they happen:

- **Re-serialising before verifying.** The verifier parses the card, dumps it again with its own
  library, and gets different bytes — part [2.1](2.1-a-signature-is-over-bytes.md)'s pretty arm, with
  matching lengths and different digests.
- **Encoding `protected` twice.** The signing input becomes
  `BASE64URL(BASE64URL(header)) || '.' || ...`, which is internally consistent, signs happily, and is
  not what any other implementation computes.
- **Signing the payload alone.** No error at all, and it is the failure the paper part exists for.

When the key is genuinely wrong, `cryptography` is blunt about it:

```text
cryptography.exceptions.InvalidSignature
```

That exception carries no message and no detail, deliberately — a verifier that explained *why*
verification failed would be a small oracle for whoever is probing it. It means one of "wrong key",
"wrong bytes" or "forged", and distinguishing them is the caller's job with the caller's logs.

## In production

**What a professional does.** Keeps the private key out of the process that serves the card. Signing
is a rare, offline-ish operation — a card changes when the agent's interface changes — so the key
lives in a key manager or an HSM and the signing step runs in the build, not in the request path. An
agent server that holds a signing key can be made to sign whatever it is tricked into describing.

**What degrades at scale.** Nothing about the signing cost — it is microseconds. What grows is key
management: rotation, revocation, and the number of places the public half has to be published before
a rotation is safe. That is Day 90 and it is the genuinely hard half.

**The failure that only shows with real traffic.** A card signed at build time and edited at deploy
time. Something injects the real hostname, or a sidecar rewrites a url, and the signature — still
present, still well formed — no longer matches. Every peer that verifies starts rejecting, and every
peer that does not verify carries on, so the symptom is that your most careful integrators break
first.

**The review comment a senior engineer leaves:** *"Sign in the build and ship the bytes. If the
serving process can sign, then anything that can talk to the serving process can get a valid
signature over a card it chose."*

**The interview question:** *"How would you sign a JSON document for a third party to verify?"* The
answer that shows experience names an existing format rather than designing one, and then spends its
time on the two things that are actually hard — canonicalisation and key distribution — rather than
on the algorithm.
