# 3.1 — The algorithm the card chose

## One-line answer

💥 A verifier that reads `alg` out of the card and does what it says will accept `alg: "none"` with
an empty signature — measured here, a forged card advertising `http://attacker.example/` verified
`True` — and the fix is not better cryptography but an allowlist the card cannot widen.

## The story

💥 **The guard who asks which ID you would like to show.**

🎬 **The scene.** A building with a security desk. Visitors sign in and show identification, and the
guard has a laminated sheet listing what counts: a company badge, a driving licence, a passport.

😬 **The naive fix.** The sheet is a nuisance. People turn up with all sorts of things and get turned
away and complain, and the desk is a bottleneck at nine in the morning. So the instruction becomes
simpler and friendlier: *ask the visitor for identification, and accept what they present.*

💥 **Why it fails.** A visitor presents a gym membership card. The guard, following instructions,
accepts it — it is identification, the visitor said so. The next one presents a printed sheet with
his own photograph on it. The one after that says he does not have any on him, which is a kind of
answer to the question too, and the register now says *"ID: none"* in the visitor's own handwriting
and he is upstairs.

💡 **The insight.** **The person being checked was allowed to choose what counted as a check.** No
individual decision was unreasonable; the guard applied the rule at every step. The rule moved the
decision from the desk to the visitor, and once it is there, no amount of diligence at the desk can
get it back.

## The idea in plain language

JWS is deliberately general. The protected header carries an `alg` parameter naming the algorithm,
so one format can carry Ed25519 signatures today and something else in ten years without a new
specification. That is **algorithm agility** and it is a genuine engineering virtue.

It also means the document tells the verifier how to check the document.

The obvious implementation reads `alg`, dispatches on it, and verifies. Written out, it looks
correct — it is doing exactly what the format says. And the format defines a value called `"none"`,
which means *unsecured*: a JWS with no signature at all, intended for cases where integrity is
provided by something else entirely.

So an attacker who can put a card in front of your verifier does not need a key. They rewrite the
card however they like, set `alg` to `"none"`, leave `signature` empty, and hand it over. A verifier
that trusts the header dispatches to the `none` branch, finds the empty signature it was told to
expect, and reports success.

The fix is one line and it is not cryptographic:

```text
the verifier decides which algorithms it accepts, before it looks at the header
```

The verifier's allowlist is policy. The card's `alg` is a hint about which of the accepted algorithms
was used. Once those two are the right way round, `"none"` is rejected before any code that could
accept it is reached.

## Why Sutra needs it

Because Sutra is the verifier. Phase 14's gate is "A2A peer verified", and the peer's card is a
document supplied by the party being checked. Every trust decision after this point rests on a
function that is about to be written in `sutra/a2a.py`, and this is the shape it must not have.

And because the pattern is not confined to JWS. Day 37's auth day met the same structure in OAuth
metadata; Day 66's injection day met it as "instructions arriving inside data". This is that failure
in its purest form: **the input choosing how it is validated.**

## The paper behind it

> **JSON Web Signature (JWS)**
> RFC Editor, 2015. `doi:10.17487/RFC7515`
>
> Defines the protected header, the `alg` parameter, and the unsecured `"none"` algorithm — and
> requires that a recipient decide, from its own policy rather than from the input, which algorithms
> are acceptable.

The `"none"` value is in the specification on purpose and the failure is not the format's. What the
field has demonstrated repeatedly is that generality plus a permissive default equals a bypass. Read
it after the parts: [papers/01 — A signature over its own
header](../../papers/01-a-signature-over-its-own-header.md).

## The mechanism

Both policies live in one function; the difference is whether `accepted` is `None`:

```python
def verify(entry: dict, payload: bytes, public_key, accepted: tuple[str, ...] | None) -> bool:
    """Check one signature entry. `accepted=None` means 'believe the protected header'."""
    header = json.loads(unb64u(entry["protected"]))
    alg = header.get("alg")
    if accepted is not None and alg not in accepted:
        raise ValueError(f"alg {alg!r} is not in this verifier's allowlist {accepted}")
    if alg == "none":
        return entry["signature"] == ""
```

**Line by line:**

- The allowlist check comes **before** the `alg == "none"` branch. Order is the whole mechanism: with
  the check second, the `none` branch has already been taken.
- `accepted is not None` rather than a truthiness test, so that an empty tuple means "accept nothing"
  rather than silently meaning "accept everything". A falsy allowlist that disables checking is how
  this bug gets reintroduced.
- `raise ValueError` rather than `return False`. A rejected *algorithm* is a policy violation and a
  failed *signature* is a cryptographic result; collapsing them into one boolean loses the
  distinction the logs need.
- `header.get("alg")` returns `None` for a card with no `alg` at all, which is not in the allowlist
  and so is refused — the missing case handled by the same line as the wrong case.
- The `alg == "none"` branch is written out rather than omitted. It exists so the default arm can
  demonstrate the failure; a real verifier reaches it only if somebody has put `"none"` in the
  allowlist, which is a thing you would see in review.

The forged entry costs the attacker nothing:

```python
def forged() -> dict:
    """A card entry that claims to be signed and carries no signature."""
    protected = b64u(json.dumps({"alg": "none", "kid": KEY_ID}, separators=(",", ":")).encode())
    return {"protected": protected, "signature": "", "header": {"kid": KEY_ID}}
```

**Line by line:**

- No key is generated and none is needed. This is base64 of a small JSON object and an empty string.
- `kid` is copied from the real card, so the entry *looks* like the genuine one to anything that
  reports which key was used. A log line saying "verified with sutra-desk-2026-09" would be produced
  by this forgery.
- `signature: ""` — the empty string, which is what the `none` branch is checking for.

Run both arms:

```bash
cd days/day-89-signed-agent-cards/lab
uv run python alg.py; echo "exit: $?"
uv run python alg.py --strict; echo "exit: $?"
```

**Line by line:**

- Default is "believe the header"; `--strict` supplies the allowlist. The card, the forgery and the
  key are identical in both.

Measured on 2026-09-07:

```text
verifier policy: whatever the card says
the card presented advertises: http://attacker.example/

  protected header: {"alg":"none","kid":"sutra-desk-2026-09"}
  signature:        ''  (0 characters)

  verified: True

  a card signed by nobody was accepted, and the peer will now be dialled
  at an address the attacker chose
exit: 1
```

```text
verifier policy: allowlist ('EdDSA',)

  ValueError: alg 'none' is not in this verifier's allowlist ('EdDSA',)

  the verifier refused before doing any cryptography, which is the only
  place this decision can safely be made
exit: 0
```

**`verified: True`, on a zero-character signature.** The card says the agent lives at
`http://attacker.example/` and the verifier has just confirmed it. Note what the strict arm does *not*
do: it never calls `verify`, never touches the key, never computes a digest. The refusal is a
comparison against a tuple, which is why it cannot be got around by anything in the card.

## When it breaks

The allowlist itself becomes the failure, in two ways.

**It gets widened to fix an outage.** A peer starts sending `ES256`, verification fails, somebody
adds `ES256` to the tuple to unblock the integration. That is often the right call — but it is a
security decision made under time pressure by whoever was on call, and the tuple is now a list that
grows and never shrinks. The countermeasure is that the allowlist lives in reviewed configuration
rather than in a caller's argument.

**It gets widened all the way.** The genuinely dangerous version is a helper whose signature invites
it:

```text
def verify_card(card, key, accepted=None):   # None means "whatever the card says"
```

A default that means "accept everything" is a bypass reachable by forgetting an argument. Written the
other way round — the allowlist required, with no default — the bypass has to be typed on purpose.
That is worth more than any amount of documentation, and it is why `sutra/a2a.py`'s build brief lists
`accepted_algs` as its own function rather than a parameter with a default.

The failure has no traceback in the arm that matters. `verified: True` is the whole of it.

## In production

**What a professional does.** Pins one algorithm and treats a second as a migration project. Agility
is a property of the *format*, not something you have to exercise: a deployment that accepts exactly
`EdDSA` is simpler to reason about, and adding an algorithm becomes a dated change with a reviewer
rather than a runtime negotiation with a stranger.

**What degrades at scale.** More peers means more implementations means more algorithms, and the
pressure is always to widen. The mitigation that survives is publishing what you accept — in your own
card, in your documentation — so a peer discovers the constraint before an integration fails, rather
than during one.

**The failure that only shows with real traffic.** A verifier that accepts `none` for one code path
only. Testing fixtures, a health check, a fallback for "cards from our own registry" — some path
where the card is considered trusted and the check is relaxed. The attacker's problem is then reduced
to reaching that path, and paths of this kind are rarely documented as trust boundaries.

**The review comment a senior engineer leaves:** *"`accepted=None` cannot mean 'accept anything'.
Make the allowlist a required argument, and if we ever need `none`, that needs to be a separate
function with a name somebody would be embarrassed to call."*

**The interview question:** *"What is the `alg: none` attack?"* The answer that shows experience does
not stop at the mechanism. It generalises: the input was allowed to specify how the input is
validated, and the fix is always to move that decision to the verifier — then names the same shape
somewhere else, like a request choosing its own authentication scheme.
