# 3.3 — The field the spec made optional

## One-line answer

The specification lists `signatures` as **Required: No**, so a card with none is fully conformant —
which means "does this card verify?" and "is this card valid?" are different questions, and only one
of them has an answer the protocol will give you.

## The story

The form field marked *optional*.

Halfway down an application form: **Alternate contact number (optional)**. Almost nobody fills it in,
because the word in brackets is doing exactly what it was put there to do — telling you that leaving
it blank is a legitimate way to complete the form.

Then something goes wrong with somebody's application and the office needs to reach them. Their
mobile is off. And the field that would have solved it is blank on ninety percent of forms, correctly,
because the form said it did not matter.

Nobody was careless. The form said optional, people believed it, and the person who marked it
optional was not the person who later needed it.

## The idea in plain language

Read the specification's table for the card, fetched on 2026-09-07:

> *signatures — array of AgentCardSignature — Required: No — JSON Web Signatures computed for this
> AgentCard.*

**Required: No.** A card with an empty `signatures` list satisfies the protocol completely. Any
conformance checker will pass it. `a2a-sdk` will parse it. ADK produces exactly this, measured in part
[1.1](../01-the-card/1.1-the-card-is-the-interface.md) as `signatures: 0`.

That is a reasonable decision by the specification. Signing requires key management, and requiring it
would have meant no agent could publish a card until it had a key distribution story — which would
have made the easy case impossible in order to make the hard case safer.

The consequence is that **conformance and trustworthiness are different properties**, and only the
first is checkable by a library. A verifier therefore has three outcomes, not two:

| The card | What it means | What Sutra should do |
| --- | --- | --- |
| carries a signature that verifies | a key you trust stands behind these claims | proceed |
| carries a signature that fails | the bytes changed, or the key is wrong | refuse, loudly |
| carries no signature at all | conformant, and nobody is standing behind it | refuse, and say which |

Collapsing rows two and three into one "invalid" loses the distinction an operator needs. Collapsing
rows one and three into "not a failure" is the mistake, and it is the easy one to make because the
absence of a signature produces no error anywhere.

## Why Sutra needs it

Because the gate says "A2A peer verified", and an unsigned card cannot be verified — not "fails
verification", *cannot be verified*, which is a different sentence and needs a different branch in
`sutra/a2a.py`.

And because Sutra publishes a card too. Part [1.1](../01-the-card/1.1-the-card-is-the-interface.md)
found ADK leaves `signatures` empty, so today Sutra is on row three of that table from a peer's point
of view. A repository that refuses unsigned cards while publishing one is a repository that has not
finished the day.

## The mechanism

The rule is a policy decision written as a table, and the only interesting thing about the code is
that it has three branches rather than two:

```python
    if not card.signatures:
        print("\n  the protocol has a signatures field and ADK never writes to it")
        print("  an unsigned card is a list of claims with nobody standing behind them")
        return 1
```

**Line by line:**

- `not card.signatures` on a protobuf repeated field is an emptiness test, and an empty repeated
  field is indistinguishable from an absent one on the wire. There is no way to tell "signed by
  nobody" from "the field was never written", and no reason to want to.
- `return 1` rather than a warning. This is the choice the whole part is about: an unsigned card is
  reported as a failed check even though it is a conformant document.
- The message names *what is missing* rather than saying "invalid", so a reader who is publishing an
  unsigned card learns what to do next rather than that something is wrong.

Run it against the card ADK builds:

```bash
cd days/day-89-signed-agent-cards/lab
uv run python card.py --fields | tail -6; echo "exit: ${PIPESTATUS[0]}"
```

**Line by line:**

- `${PIPESTATUS[0]}` rather than `$?`, because `$?` after a pipe is `tail`'s status and `tail` always
  succeeds. The exit code being tested belongs to `card.py`.

Measured on 2026-09-07:

```text
  name:        sutra_desk
  version:     0.0.1
  skills:      4
  signatures:  0  []

  the protocol has a signatures field and ADK never writes to it
  an unsigned card is a list of claims with nobody standing behind them
exit: 1
```

**A conformant card, and exit 1.** Nothing in the protocol was violated. The refusal is Sutra's
policy, applied to a document the specification is content with, and that gap — between what a format
permits and what a deployment accepts — is where most real security policy lives.

## When it breaks

The policy breaks in the direction of permissiveness, and the argument for it is good every single
time.

The first peer with an unsigned card is a real integration somebody wants. Refusing it means telling
a partner to build key management before a demo. The pressure is immediate and concrete; the risk is
abstract and deferred. So a flag appears — `allow_unsigned=True`, for this one peer — and it is the
right call that week.

What makes it dangerous is that it is invisible afterwards. A verifier with an unsigned-allowed peer
behaves identically to one without, until the day it matters. There is no error text, no log line
that fires in the normal case, and nothing that decays. Day 82's quarantine measured the same shape
in the eval suite: five checks switched off, the oldest two hundred and three days, every one added
for a good reason.

If unsigned peers must be allowed, the thing that makes it survivable is the same as it was there —
**an entry with a date on it**, listed by name, that expires and fails the build. Not a boolean.

The second break is more interesting and it is Sutra's own. Refusing unsigned cards from peers while
publishing one yourself is a position that lasts exactly until a peer runs this same check. It is the
reason `card_for_peers` is in the build brief alongside `verify_card`: both halves or neither.

## In production

**What a professional does.** Writes the three outcomes into the code as three outcomes, with
distinct, countable results — verified, failed, unsigned — and reports the counts separately.
"Unsigned" trending upward is a business fact about who you are talking to; "failed" trending upward
is an incident. One counter for both hides the difference.

**What degrades at scale.** The unsigned population is sticky. Peers who published unsigned cards
have no incentive to change while you accept them, so the number never goes down on its own. The only
mechanism that moves it is a published date after which unsigned cards are refused — which is a
product decision with a migration, not a code change.

**The failure that only shows with real traffic.** A peer that signed yesterday and does not today.
A deployment loses its key mount, the card is rebuilt without signatures, and a verifier that treats
unsigned as merely "not verified" carries on talking to it. The signal was there — the card changed
shape — and nothing was watching the shape, only the outcome.

**The review comment a senior engineer leaves:** *"Three counters, not two. And if we ship
`allow_unsigned`, it takes a peer name and an expiry date, not a boolean — otherwise we will find it
in the config in two years and nobody will know who it was for."*

**The interview question:** *"The spec says this field is optional. Do you require it?"* The answer
that shows experience separates the two systems: conformance is what the format demands, and policy is
what your deployment demands, and a deployment is allowed to be stricter than the specification as
long as it says so where integrators will read it.
