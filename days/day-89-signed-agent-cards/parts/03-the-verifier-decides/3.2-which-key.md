# 3.2 — Which key

## One-line answer

A signature verifies against *a* key, so the only question that matters is where that key came from —
and when the card names a `kid` the verifier has never seen, the honest report is not "invalid" but
"this proves somebody held a key", which is not identity.

## The story

The number in your contacts, and the number in the message.

A message arrives saying it is from your bank, and it gives a number to call. You call it and speak
to somebody helpful who knows your name.

The alternative habit costs ten seconds. You ignore the number in the message, open your contacts,
and call the one you saved from the back of the card years ago. Same conversation if the message was
genuine; a completely different one if it was not.

Nothing about the first call is detectably wrong while it is happening. The person is polite, the
hold music is right, the details check out. The difference is not in the call — it is in **where the
number came from**, and that was decided before the message arrived.

## The idea in plain language

Part [2.3](../02-signing-it/2.3-the-card-that-was-edited.md) established what a signature proves:
these exact bytes were signed by the holder of a particular private key. Every word of that is
conditional on knowing *which* key you are checking against.

A JWS protected header carries `kid` — a key identifier. It is a label, not a credential. Its job is
to let a verifier that holds several keys pick the right one to try, which matters during rotation
when two are valid at once.

What `kid` must never be is a way for the card to supply the key. If the card brings its own key —
inline, or as a url the verifier fetches — then the signature proves only that *whoever wrote the
card also generated a keypair*, which anybody can do in a millisecond. The check passes and
establishes nothing.

So the verifier needs a **key set it trusted before the card arrived**. There are three ways to get
one, in increasing order of operational cost and decreasing order of fragility:

| Where the key comes from | What it costs | What it is worth |
| --- | --- | --- |
| pinned in configuration | a deployment per rotation | strongest; the number in your contacts |
| a registry the verifier trusts | running or trusting a registry | rotation without redeploying every peer |
| the card, or a url in the card | nothing | nothing |

Day 90 is the middle row. Today's job is to make the third row impossible.

**Rotation** is what makes this more than a lookup. Keys are replaced — on a schedule, or because one
was exposed — and during the changeover, cards signed by the old key are still in flight and in
caches. A key set is therefore a *set*: the current key plus the recently retired ones, with the
retired ones removed on a date somebody chose.

## Why Sutra needs it

Because `sutra/a2a.py` is about to have a `trusted_keys` function and its whole design is the
question "loaded from where". A verifier that falls back to the card when a `kid` is unknown has
undone every other check on this day.

And because rotation is the thing that turns a correct verifier into an outage. Day 82's regression
discipline made the point in a different domain: the failure that gets a check switched off is the
one that fires for a legitimate reason. A verifier that cannot survive a peer rotating a key is a
verifier somebody will disable.

## The mechanism

The key set is built before the card is read, and the card contributes nothing to it:

```python
    trusted = {RETIRED: old.public_key()}
    if not rotate:
        trusted[KEY_ID] = new.public_key()
```

**Line by line:**

- A dictionary from `kid` to public key. Two entries in the default arm: the current key and one
  retired key that is still accepted.
- `RETIRED` is `sutra-desk-2026-03` and `KEY_ID` is `sutra-desk-2026-09` — the identifier carries the
  date it came into use, which is a convention that makes a stale key visible in a log line without a
  lookup.
- The `--rotate` arm omits the current key. That is not an attack; it is the ordinary state of a
  verifier that has not yet been told about a rotation, which is the most common real cause of a
  failure here.
- Only public halves. A verifier never holds a private key, and a structure that could accidentally
  contain one is worth not having.

The lookup is a membership test, and its failure branch is the part worth reading:

```python
    if kid not in trusted:
        print(f"\n  {kid} is not a key this verifier has ever seen")
```

**Line by line:**

- `kid not in trusted` — a plain dictionary lookup with no fallback, no fetch and no `except` that
  reaches for the card. The absence of an `else` that recovers is the security property.
- The `kid` comes from the **protected** header, decoded from `entry["protected"]`, not from the
  unprotected `header` field that carries a copy. Part
  [2.2](../02-signing-it/2.2-signing-the-card.md) noted the duplication; this is where it matters,
  because only the protected copy is covered by the signature.
- Reporting the unknown `kid` by name is deliberate. It is not secret, and it is the one piece of
  information that tells an operator whether this is a rotation they have not applied or a `kid` that
  has never existed.

Run both arms:

uv run python kid.py --rotate; echo "exit: $?"

**Line by line:**

- Default: the verifier already trusts the key the card names. `--rotate`: the desk has moved to a new
  key and this verifier has not been told.

**Two keys trusted, one used, and one that is only there for the changeover.** The second arm is the
important one and it is not an attack — it is Tuesday. Somebody rotated a key and this verifier's
configuration has not caught up, and the correct behaviour is to refuse and say which `kid` was
missing, because the alternative — fetching the key the card points at — turns an operational problem
into a silent bypass.

## When it breaks

The failure mode is the temptation, and it arrives with a good argument attached.

Unknown `kid` produces a support ticket. The obvious fix is to let the card carry its key, or a
`jku` url pointing at one, and fetch it. Every peer's rotation then works without anybody being
told. The system becomes self-configuring, the tickets stop, and verification now proves nothing at
all — because the attacker generates a key, signs their card with it, and serves the key at the url
their card supplies.

There is no error text for that. Verification returns success. The measurable symptom is that the
failure rate goes to zero, which reads as the fix having worked.

The narrower version is **trust on first use**: remember whichever key a `kid` first appeared with,
and require it thereafter. That is genuinely better than nothing — it detects a change — and its
weakness is the first contact, which is the moment an attacker would choose.

## In production

**What a professional does.** Publishes keys somewhere with a different failure mode from the agent
itself, and pins the trust anchor. Concretely: the key set is fetched from a location the verifier was
configured with — never from the document being verified — cached with a deliberate lifetime, and
signed or served over a channel whose authenticity does not depend on the thing being checked.

**What degrades at scale.** Rotation stops being an event and becomes a background process. With ten
peers, an unknown `kid` is a phone call; with a thousand, some peer is always mid-rotation, and the
verifier needs overlap windows, an expiry per key and an alert that distinguishes "one peer's kid is
unknown" from "every peer's kid is unknown", because the second is your own configuration.

**The failure that only shows with real traffic.** Cached cards outliving keys. A peer rotates,
retires the old key on schedule, and a proxy somewhere is still serving a card signed by it. The card
is genuine, the signature is genuine, the key is correctly gone, and the verification fails — which
is right, and looks exactly like an attack.

**The review comment a senior engineer leaves:** *"There is no path from a card to a key. If someone
adds a `jku` fetch to fix the unknown-kid tickets, that is a security change and it needs to be
argued for in a design note, not merged as a bug fix."*

**The interview question:** *"How do you know which public key to verify against?"* The answer that
shows experience says "from somewhere the document cannot influence", then talks about rotation —
because everyone knows the first half and the people who have run this in production are the ones who
immediately raise overlap windows and unknown-`kid` alerting.
