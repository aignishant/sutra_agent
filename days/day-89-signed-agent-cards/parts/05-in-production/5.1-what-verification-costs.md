# 5.1 — What verification costs

## One-line answer

Signing and verifying an agent card is arithmetic over a thousand bytes and costs nothing measurable
and no provider requests at all — the entire cost of card verification is **key distribution**, which
is a process with people in it, and that is why teams that skip verification did not skip it to save
time.

## The story

The counterfoil at the ticket gate.

A gate with a person at it, tearing tickets in half. The tear takes under a second. There is no
machinery, no queue caused by the tearing itself, and the marginal cost of checking one more ticket
is nothing you could measure.

What costs is everything that had to exist before the tear means anything: the tickets had to be
printed somewhere controlled, distributed to sellers, the design changed when the old one got
copied, and somebody had to decide what a genuine one looks like and tell every gate.

Nobody who has run this would describe it as "the cost of checking tickets". The checking is free.
The system that makes checking meaningful is the whole job.

## The idea in plain language

Here is the honest cost model for card verification, and it has one interesting row.

**The cryptography is free.** An Ed25519 signature over a thousand-byte card is on the order of
microseconds, on a laptop, single-threaded. There is no scenario in an agent system where this is
the bottleneck, because the same request is about to make a model call that costs a hundred thousand
times more.

**The provider cost is zero.** Nothing in this day made a single request to Google, Groq, OpenRouter
or anything else. Signing and verifying are local computation over local bytes — which is why this
entire day, uniquely among the recent ones, has no allowance question in it at all.

**The bytes are free.** The card is 952 canonical bytes; a signature entry adds a base64url header
and a 64-byte signature, so a signed card is a little over a kilobyte. It is fetched once and cached.

**The key distribution is the whole bill**, and it is not denominated in requests. It is denominated
in coordination: somebody has to publish the public key somewhere peers can get it, tell peers where
that is, agree what happens when it rotates, and be reachable when a rotation goes wrong. None of
that is code, and all of it is why an unsigned card is the default in the field.

That last row is why the shape of this part is the same as Day 82's regression discipline: the
comparison is free and having something to compare against is the entire cost. Here, the check is
free and having something to check against is the entire cost.

## Why Sutra needs it

Because the argument against verification is never "it is slow". It is "we do not have anywhere to
put the keys", and being able to say that plainly is what turns a vague reluctance into a small,
concrete piece of work — which is Day 90.

And because Sutra's budget is denominated in requests per day against a free tier, with a measured
allowance of twenty on the lane Day 78 burned. Card verification is one of the very few things this
repository has built that does not touch that number at all, and it is worth knowing which of your
controls are free.

## The mechanism

The measurement is the absence of one. Every command in this day is local:

```bash
cd days/day-89-signed-agent-cards/lab
uv run python sign.py > /dev/null; echo "sign+verify exit: $?"
uv run python canon.py > /dev/null; echo "canonicalise exit: $?"
uv run python alg.py --strict > /dev/null; echo "policy check exit: $?"
```

**Line by line:**

- All three redirect to `/dev/null` because the output is not the point here; the exit codes and the
  absence of any network are.
- Not one of these imports a provider client, reads an API key, or opens a socket. `_desk.py`
  constructs an `LlmAgent` with a model string and that string is never dialled — part
  [1.1](../01-the-card/1.1-the-card-is-the-interface.md) established that the card builder reads the
  Python object.
- `alg.py --strict` is included deliberately: the *policy* check is even cheaper than the
  cryptographic one, because it refuses before computing anything.

Measured on 2026-09-07:

```text
sign+verify exit: 0
canonicalise exit: 0
policy check exit: 0
```

And the sizes, from the runs already taken:

| Thing | Size | From |
| --- | --- | --- |
| the card, canonical | 952 bytes | part [2.1](../02-signing-it/2.1-a-signature-is-over-bytes.md) |
| the card, indented | 1,315 bytes | same |
| an Ed25519 public key, base64 | 44 characters | part [2.2](../02-signing-it/2.2-signing-the-card.md) |
| a signature, raw | 64 bytes | Ed25519, fixed |

**A trust anchor that fits on one line.** The public key being forty-four characters is not a
curiosity — it is the reason a pinned-key deployment is practical at all. A trust anchor somebody can
paste into a config file and compare by eye is one that gets checked; a two-kilobyte certificate chain
is one that gets copied without reading.

## When it breaks

The cost model breaks by being right about the wrong thing. Three ways, in the order teams hit them.

**Verification is free per card and cards are fetched per call.** A client that re-fetches and
re-verifies a peer's card on every request has turned a free local check into a network round trip
against somebody else's availability. The card is a slowly changing document; the fix is a cache with
a deliberate lifetime, and the failure is that the protocol has no expiry field to tell you what that
lifetime should be — part [1.2](../01-the-card/1.2-where-the-card-lives.md) named the gap.

**Key distribution is not free and gets budgeted as if it were.** The row above says the cost is
coordination, and coordination has a failure mode that arrives as an outage rather than a bill: a
rotation goes out, a peer has not updated, and every card from that peer fails verification at once.
Day 90's registry exists to make that survivable.

**The free thing gets skipped anyway.** The genuinely common outcome, and the reason to be precise
about the numbers. Nobody sits down and decides to accept unsigned cards; the check simply never gets
written, because the peer works without it. The cost that was avoided was not compute — it was the
afternoon spent deciding where the keys live.

There is no error text for any of these, and for the third there is not even an event.

## In production

**What a professional does.** Verifies once per fetch, caches the result with the card, and spends
the actual engineering effort on the key set — its location, its rotation procedure, and the alert
that fires when a `kid` goes unknown. The compute budget for verification does not appear in any
serious design document, because it is not a number anybody needs.

**What degrades at scale.** Not the cryptography. What grows is the number of peers whose key
material you are tracking and the number of rotations in flight at any moment, and that grows
linearly with peers while the operational attention available stays flat. The scaling limit of card
verification is a human one.

**The failure that only shows with real traffic.** Verification on the hot path. A design that
verifies at fetch time is fine; one that verifies inside the request handler, with a fetch behind it,
means every peer's availability is now yours — and it will be discovered during their incident, not
yours. This is Day 44's client-hardening lesson arriving through a security control.

**The review comment a senior engineer leaves:** *"Do not put the cost of verification in the design
doc, it is microseconds. Put in where the public keys live and who rotates them, because that is the
part that will take a week."*

**The interview question:** *"Why do so few systems verify signed metadata?"* The answer that shows
experience says immediately that it is not performance, gives the rough numbers to prove the point,
and then names the real reason — that verification requires a trust anchor, and a trust anchor
requires a decision, an owner and a rotation procedure that nobody wants to own.
