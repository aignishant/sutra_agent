# 5.2 — What a real A2A deployment adds

## One-line answer

The lab signs a real card with a real key and verifies it against a key set the card cannot
influence — and the distance between that and something you would expose to a stranger is nine
items, the first of which is authentication on the endpoint and is the only one that is urgent.

## The story

The checklist a new branch works through before it opens.

The premises are ready. The sign is up, the stock is in, the staff are hired and trained, and if you
walked past you would think it was open. It is not, because there is a list taped inside the door and
four things on it are unticked: the card machine has not been tested with a real transaction, the
alarm is not connected to the monitoring service, nobody has the second key, and the insurance
certificate has not arrived.

None of the four is about whether the shop works. All four are about what happens on a bad day, and
the list exists because the person who wrote it has had bad days.

## The idea in plain language

The lab does five things properly, and it is worth being precise about which, because the gap is the
subject.

It builds a card from a real ADK agent through ADK's own builder. It canonicalises it to bytes both
sides can reproduce. It signs it with a real Ed25519 key and verifies it with the real library. It
refuses an `alg: none` forgery by policy rather than by cryptography. And it refuses a card whose
`kid` it has not seen before, instead of reaching for the key the card offers.

Here is what goes on the door.

**1. Authentication on the JSON-RPC route.** Part
[4.1](../04-the-peer/4.1-a-peer-can-send-you-work.md) measured two routes and one of them executes the
agent, with nothing asking who the caller is. This is first because it is the only item on the list
that is dangerous today, and because on a free tier the first symptom is not a breach but an
exhausted allowance and a desk that stops answering its own users.

**2. `securitySchemes` filled in, in the same change.** ADK leaves it empty, which currently
describes the endpoint accurately. Once item 1 exists, an empty schemes list is a *lie* in the
published card, and a peer trying to integrate has no way to discover the credential they need.

**3. The card signed in the build, not in the server.** Part
[2.2](../02-signing-it/2.2-signing-the-card.md): a process that can sign is a process that can be
made to sign something it was tricked into describing. Sign where the artefact is produced, ship the
bytes, and let the serving process hold no key at all.

**4. Serve the signed bytes, do not re-serialise.** Part
[2.1](../02-signing-it/2.1-a-signature-is-over-bytes.md) measured 952 canonical bytes against 1,315
indented ones for the same card. Holding the bytes from signing to serving makes canonicalisation
stop mattering, which is a better outcome than getting canonicalisation right.

**5. Three outcomes, three counters.** Part
[3.3](../03-the-verifier-decides/3.3-the-field-the-spec-made-optional.md): verified, failed,
unsigned. Merging failed and unsigned loses the difference between an incident and a business fact
about who you talk to.

**6. `version` set deliberately.** Part [1.1](../01-the-card/1.1-the-card-is-the-interface.md)
measured `0.0.1` — a default nobody chose, published as a fact, which a peer will pin against.

**7. A curated public card.** Part [1.3](../01-the-card/1.3-what-the-card-gives-away.md) measured
three tool names and three docstrings verbatim on an unauthenticated path. The specification's
extended-card mechanism exists for exactly this: a public card with the skills you want work routed
to, and the full list behind authentication.

**8. 🅿️ Parked — the key registry.** Part
[3.2](../03-the-verifier-decides/3.2-which-key.md) established that a key set has to come from
somewhere the card cannot influence, and that rotation is what makes it hard. That is Day 90 and it
is parked here only because it is tomorrow.

**9. 🅿️ Parked — a card cache with a deliberate lifetime.** Part
[1.2](../01-the-card/1.2-where-the-card-lives.md) named the gap: the protocol has a version field and
no expiry, so how long a fetched card stays good is a decision each deployment makes silently.
Parked because it needs item 8 first — a cache that outlives a key rotation is worse than no cache.

## Why Sutra needs it

Because Phase 14's gate is "A2A peer verified; repo public", and items 1, 2 and 7 are the ones that
decide whether the second half of that sentence is safe. A public repository plus a published tool
inventory plus an unauthenticated execution endpoint is three individually reasonable states that
compose into one bad one.

And because items 3 and 4 are cheap now and expensive later. Moving signing out of the server once
the server holds a key is a migration; never putting it there is a decision.

## The mechanism

The list, with what each costs, so it can be argued with rather than admired:

| # | Item | Where it lands | Roughly |
| --- | --- | --- | --- |
| 1 | auth on the JSON-RPC route | ASGI middleware | half a day |
| 2 | `securitySchemes` in the card | the card builder call | one line |
| 3 | sign in the build | build script + key manager | half a day |
| 4 | serve the signed bytes | the card handler | an hour |
| 5 | three outcomes, three counters | `sutra/a2a.py` | an hour |
| 6 | `version` set deliberately | one argument | one line |
| 7 | curated public card | a written card, not a generated one | half a day |
| 8 | 🅿️ key registry | not built | Day 90 |
| 9 | 🅿️ card cache with a lifetime | not built | needs item 8 |

**Items 2, 5 and 6 are about two hours between them** and they are the ones that make the system
*legible* — the card stops lying about its security, the counters stop merging two different events,
and the version stops being an accident.

Item 1 is the whole security posture and it is the one to do first. Its implementation is not ADK's
concern at all — `to_a2a` returns a Starlette application, so this is ordinary ASGI middleware:

```python
app = to_a2a(desk(), host="127.0.0.1", port=8931)
app.add_middleware(RequireBearerToken, token_env="SUTRA_A2A_TOKEN")
```

**Line by line:**

- `to_a2a` returns a `Starlette` instance — part [4.1](../04-the-peer/4.1-a-peer-can-send-you-work.md)
  printed the type — so every ASGI middleware pattern applies unchanged. Nothing about A2A requires a
  special authentication mechanism.
- `token_env` rather than a literal. The credential comes from the environment, never from the
  repository, which is Principle 9 and is the same rule Day 86 enforced for container secrets.
- `RequireBearerToken` is not written here on purpose: it is the build brief's job, and the card's
  `securitySchemes` must then declare the same scheme in the same change, which is item 2.
- What this does **not** do is exempt the well-known path. That is a real decision with two defensible
  answers — a public card aids discovery, an authenticated one reveals nothing to strangers — and
  item 7 is what makes the public answer safe.

## When it breaks

The list breaks by being read as improvements rather than as a sequence, and the composite has been
measured piece by piece across this day:

```text
1. to_a2a gives a working server in one line               (part 4.1)
2. the card lists every tool and its docstring             (part 1.3, 3 of 3 verbatim)
3. securitySchemes is empty, so nothing asks who is calling (part 1.1, 8 of 14 filled)
4. signatures is empty, and that is conformant             (part 3.3, Required: No)
5. a peer verifies nothing, because there is nothing to verify
6. the repository goes public, and the implementation is readable too
7. the endpoint is an open agent with a published tool list and a free-tier quota
```

Seven steps, no error at any of them, every step either a library default or a reasonable decision.
Step 7 is not an attack — it is the resting state of the shortest path from `to_a2a` to something
running.

## In production

**What a professional does instead of building all nine.** Item 1, before the endpoint is reachable
from anything but a laptop, because it is the only one that is urgent. Then 2 and 6, which are lines
rather than work. Then 7, which is a conversation about what you want routed to you rather than an
implementation. Items 3, 4 and 5 belong in the same change as the first real peer.

**What degrades at scale.** Item 7 gets harder and item 8 gets unavoidable. A curated card is a
document somebody maintains, so it drifts from the implementation the moment nobody owns it — the
mirror image of the generated card's problem, and the reason the extended card exists rather than a
choice between the two.

**The failure that only shows with real traffic.** A peer that behaves. Every item on this list is
about the peer that does not, and a deployment whose only integration is a friendly one accumulates
none of the evidence that any of this matters — until the endpoint is discovered by something that is
not a peer at all, which on a public repository with a well-known path is a matter of scanning.

**The review comment a senior engineer leaves:** *"Item 1 before this leaves the laptop, and item 2
in the same commit. The rest can wait for the first real peer, but do 3 now while it is a choice
rather than a migration."*

**The interview question:** *"What would you add before exposing an agent over A2A?"* The answer that
shows experience starts with authentication on the execution route rather than with signatures —
because verifying their card is about who you talk to, and the endpoint is about who talks to you,
and only one of those is reachable by a stranger today.

## Check yourself

```bash
cd days/day-89-signed-agent-cards/lab
uv run python served.py --lifespan | grep routes
uv run python card.py --fields | grep -E "security|signatures"
```

The first is the surface, the second is the two fields that would describe how it is protected. Say
what the second output would look like after items 1 and 2, and what a peer could then work out
before calling you.

Now map the seven-step sequence in **When it breaks** onto the nine items and find the step that no
item on the list would have caught. It exists, and naming it is the exercise.

**Out loud, without scrolling up:** three items on this list take about two hours between them and
one of them is the only urgent one. Name the urgent one, and say what it costs you today to not have
it.
