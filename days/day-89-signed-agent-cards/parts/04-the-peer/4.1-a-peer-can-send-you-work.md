# 4.1 — A peer can send you work

## One-line answer

`to_a2a` turns the desk into a server in one call, and the two routes it mounts are not symmetrical:
`/.well-known/agent-card.json` hands out a description, and `/` accepts instructions from whoever
reached it — so verifying a peer's card protects you from talking to the wrong agent, and nothing
about it protects you from the wrong agent talking to you.

## The story

The neighbour you let park in your compound.

It starts as a favour and it is a small one. The gate is open in the day anyway, there is room, and
they only need it for a fortnight while their own place is being repaired.

What has actually changed is not the parking. It is that a vehicle now comes and goes through your
gate on somebody else's schedule, and the watchman has stopped asking about it because it is
expected. The favour was about space. The thing you gave away was the gate.

## The idea in plain language

Everything up to here has been about **you as a client**: fetching a peer's card, checking its
signature, deciding whether to send it work. That is one direction, and it is the direction
signatures help with.

`to_a2a` opens the other one. Part [1.2](../01-the-card/1.2-where-the-card-lives.md) measured the
route table after startup:

```text
routes after startup:  ['/.well-known/agent-card.json', '/']
```

Two routes doing completely different jobs. The first is a read: it hands out a document. The second
is the JSON-RPC endpoint — it is where a peer sends a message that becomes an agent invocation, with
your tools, your model quota and your escalation path behind it.

So the day's security question splits in two, and only one half has been answered:

| Direction | The risk | What a signed card does |
| --- | --- | --- |
| Sutra calls a peer | you talk to an impersonator, or a real peer at an edited url | this is what parts 2 and 3 were for |
| a peer calls Sutra | a stranger runs your agent, spends your quota, reaches your tools | **nothing** |

A card signature is a claim by the *card's owner* about the card. It says nothing about whoever is
currently making a request to you, because the request does not carry the card — and even if it did,
possession of a public document proves nothing.

The thing that answers the second row is the card's other field: `securitySchemes`, which part
[1.1](../01-the-card/1.1-the-card-is-the-interface.md) measured as one of the six ADK leaves empty.
That field is where an agent declares how a caller must authenticate, and an empty one is an
accurate description of an endpoint that requires nothing.

## Why Sutra needs it

Because Day 85 measured the identical shape on the other API surface: twenty-seven routes, fifteen
carrying a `user_id`, and not one asking for a credential — and a stranger read and deleted another
user's session in three requests. A2A is that again with a protocol on top, and the protocol's own
answer is a field ADK does not fill.

And because the tools behind that `/` route are the ones Day 68 spent a day constraining and Day 63
put an approval gate in front of. The blast radius of an open A2A endpoint is not "someone chats to
the model"; it is every capability in the skills list that part
[1.3](../01-the-card/1.3-what-the-card-gives-away.md) just published.

## The mechanism

One call produces the server:

```python
    app = to_a2a(desk(), host="127.0.0.1", port=8931)
```

**Line by line:**

- `to_a2a` returns a Starlette application. It is not started here; something else — uvicorn, or a
  test — has to run it, and part [1.2](../01-the-card/1.2-where-the-card-lives.md) is what happens in
  between.
- `host` and `port` do **not** bind anything. They are copied into the card so it can advertise where
  it lives, which means the address a peer dials and the address the process actually listens on are
  two independent facts that nothing reconciles.
- There is no `auth`, no `security_schemes`, and no middleware parameter in this call. Not an
  oversight — the signature has ten parameters and none of them is a credential — because
  authentication for an ASGI app is middleware you add, and ADK is right not to guess.
- `127.0.0.1` here is the whole reason this lab is safe. On `0.0.0.0` the same line publishes the desk
  to every interface on the machine.

The route table is the security surface, and it is worth printing rather than assuming:

```python
def paths(app) -> list[str]:
    return [getattr(route, "path", "?") for route in app.routes]
```

**Line by line:**

- `route.path` is the registered pattern. Two entries is the whole A2A surface, which is small enough
  that a person can hold it — and small surfaces are the ones that get assumed rather than read.
- `getattr(..., "?")` because not every Starlette route type has `path`; a mount or a websocket route
  would need different handling, and returning `"?"` makes an unexpected route visible instead of
  raising.

The important measurement is the asymmetry, and it is in the two lines of output already taken in
part [1.2](../01-the-card/1.2-where-the-card-lives.md):

```bash
cd days/day-89-signed-agent-cards/lab
uv run python served.py --lifespan | grep routes
```

**Line by line:**

- `grep routes` narrows to the surface; the card body is part 1.2's subject and not this one's.

Measured on 2026-09-07:

```text
  routes before startup: []
  routes after startup:  ['/.well-known/agent-card.json', '/']
```

**One of those two routes is a read and the other is an execution endpoint**, and they are protected
identically, which is to say not at all. That is the correct default for a library — and it is a
finding about what has to be added before this is reachable from anywhere.

## When it breaks

There is no error text. The endpoint works, which is the problem.

The realistic sequence, and every step is something a competent person does on purpose:

```text
1. to_a2a gives a working A2A server in one line, so it is used for a demo
2. the demo needs to be reachable from a colleague's machine, so host becomes 0.0.0.0
3. it works, so it stays up
4. the card at the well-known path lists every tool (part 1.3)
5. securitySchemes is empty, so nothing asks the caller who they are
6. anything that can route to the host can invoke the agent
```

Step 2 is the only one anybody would question in review, and it is the one with the best
justification attached. Day 85 part 4.3 measured the neighbouring version of this: ADK's own
`api_server` passes a `bind_host` guard that a direct embedder does not get, so the CLI path is
protected and the library path is not.

The failure that *does* raise is worth knowing because it is the good outcome. With authentication
middleware in front of `/`, an unauthenticated peer gets a 401 and the agent never runs — no model
call, no tool, no quota. The cheapest security control here is also the cheapest performance control,
which is unusual and worth using as the argument when somebody asks whether it is needed yet.

## In production

**What a professional does.** Puts the A2A endpoint behind the same authentication as any other
service, and then fills in `securitySchemes` so the card *describes* that requirement — because a
peer reading your card is trying to work out how to call you, and an empty schemes list tells them
"no credential needed", which is either false or alarming. The two have to move together: the control
and the description of the control.

**What degrades at scale.** Peer count. One peer is a shared secret; a dozen is a decision about
whether you are issuing credentials, and a hundred is an identity system — which is Day 90. The
threshold where this stops being ad hoc arrives earlier than people expect, because the second peer
is already the moment you need to be able to revoke one without disturbing the other.

**The failure that only shows with real traffic.** Quota. An open A2A endpoint is somebody else's
free model access, and the first symptom is not a security alert — it is Day 78's 429, or a bill.
Sutra runs on a free tier with a measured daily allowance of twenty requests, so an open endpoint
does not get expensive; it gets **exhausted**, and the desk stops answering its own users.

**The review comment a senior engineer leaves:** *"Two routes and one of them executes the agent. Put
the auth middleware in before this leaves a laptop, and fill in `securitySchemes` in the same change
so the card is not advertising an open door."*

**The interview question:** *"You have exposed your agent over A2A. What did you just give away?"*
The answer that shows experience separates the directions — verifying their card is about who you
talk to, and authenticating their request is about who talks to you — and then names the concrete
loss, which is tool access and quota rather than data.
