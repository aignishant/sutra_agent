# 1.3 — What the card gives away

## One-line answer

ADK turns every tool into a published skill, so the card served at a well-known path with no
credential lists all three of this desk's tool names **and their docstrings verbatim** — an
inventory of every lever the agent has, written in the words you wrote for the model.

## The story

The visiting card that lists every machine in the workshop.

A fabricator gets cards printed. On the front, the name and the number. On the back — because the
printer had space and it seemed a shame to waste it — the equipment: *lathe, milling machine, plasma
cutter, 3-tonne press, TIG and MIG welding.*

It is a good card. Customers like it, because they can tell at a glance whether their job is one this
shop can take.

It is also a shopping list. It went into a few hundred hands, and it tells anyone who reads it
exactly what is inside the shed, how much it is worth, and — for the one reader in a thousand who is
thinking about it that way — which night to come.

The information is completely accurate and the shop chose to publish it. What the shop did not do is
decide, separately, whether each line needed to be on there.

## The idea in plain language

An A2A card carries a `skills` list: things this agent can do, each with an id, a name, a
description and tags. It is the useful half of the card — it is what lets a peer decide whether to
route work here rather than somewhere else.

ADK fills it automatically, and the rule it uses is the direct one: **one skill for the agent, plus
one skill per tool.** The tool's Python function name becomes the skill's name. The tool's docstring
becomes the skill's description.

That is a good default for discovery and it has a consequence worth stating plainly. Your tool
docstrings were written for a model — Day 4 established that a tool's docstring is its
specification, and Day 16 that a vague one is how a model picks the wrong tool. They are careful,
complete descriptions of every capability the agent has, and they are now on a page that:

- lives at a path fixed by the protocol, so nobody has to find it;
- is fetched before any authentication, because it is what tells you *how* to authenticate;
- is served to anyone who can reach the host.

Nothing here is a defect. The protocol wants agents to be discoverable and ADK implemented that. But
"what my agent can do" and "what I publish to strangers" are two different lists, and by default they
are the same list.

## Why Sutra needs it

Because Sutra's tools are not neutral. `request_approval` names the escalation path. `refund_limit`
tells a reader that a limit exists and that this agent knows it. Day 68 spent a whole day on least
privilege for tools; publishing the tool inventory does not grant anybody a privilege, and it does
tell them precisely which ones to go looking for.

And because Phase 14 makes the repository public. A published card and a public repository are
different exposures that compose: the card says which tools exist, the repository says how they are
implemented, and either alone is much less useful to somebody than both together.

## The mechanism

The card's skills, as ADK builds them, against the tools they came from:

```python
    leaked = [t.__name__ for t in TOOLS if any(t.__name__ == s["name"] for s in skills)]
    docs = [t.__name__ for t in TOOLS if any(t.__doc__.strip() == s.get("description") for s in skills)]
```

**Line by line:**

- The first list asks whether the *function name* reached the card. That is the inventory: three
  names a reader now knows to ask about.
- The second asks whether the **docstring is byte-identical** to the published description. Not
  paraphrased, not summarised — the same sentence. `.strip()` is the only transformation, because
  that is the only one ADK applies.
- Both compare against `TOOLS`, the actual function objects, so the check cannot drift from the
  agent's real tool list the way a hand-written expectation would.

The contrast arm builds the same agent without handing the builder its tools:

```python
    bare = LlmAgent(
        name=desk().name,
        model="gemini-2.5-flash-lite",
        description="Triages support tickets and refunds within a stated limit.",
    )
```

**Line by line:**

- Same name, same description, no `tools=`. This is not a crippled agent — it is what you would
  publish if the card were written for discovery rather than generated from the implementation.
- The description still tells a peer what the desk is for, which is what a peer needs in order to
  route to it. What it stops telling them is how the desk is built.
- In a real deployment this is a *separate card object*, not a second agent. The point of the arm is
  to measure what the tool list contributes to the published document, not to suggest deleting your
  tools.

that reveals the agent name is a prefix, which is a small thing and is the sort of small thing
enumeration is built out of.

## When it breaks

There is no error and nothing raises. The card is correct, the protocol is satisfied, and the
information is exactly what discovery is for.

The composite failure is a sequence, and every step in it is a good decision:

```text
1. a tool gets a careful docstring, because a vague one makes the model choose wrong (day 16)
2. the agent is exposed over A2A so a peer can route work to it
3. ADK builds the card, one skill per tool, docstrings included
4. the card is served without a credential, because it says how to authenticate
5. the repository goes public, so the implementation of each named tool is readable too
6. an inventory of every lever, and its source, is available to anyone who knows the host
```

Step 6 is not an attack. It is a *starting position*, and the thing to notice is that no single step
was wrong and nobody ever made the decision that step 6 describes.

The version of this that does have an error text is the one further along, and Day 66 has it: a card
listing `request_approval` tells an injection attempt exactly which tool name to try to get called.
Day 67's guardrail callbacks are what stand between that knowledge and a write.

## In production

**What a professional does.** Publishes a card written for peers, not generated from the
implementation. In practice that means a curated skills list — the two or three capabilities you
actually want routed to you, described in the terms a peer would search for — and it means the
generated card is a starting draft that a person edits, exactly like an OpenAPI document.

**What degrades at scale.** The gap widens automatically. Every tool added to the agent adds a
published skill, so the card grows in the direction of the implementation rather than the direction
of the interface, and it does so in commits whose subject is "add tool". Nobody reviews a card
diff that nobody generates.

**The failure that only shows with real traffic.** An internal tool published to the internet. The
extended-card mechanism in the specification exists for exactly this — a public card with the safe
subset, and an authenticated extended card with the rest — and using it requires deciding which
skills are which. A default that publishes everything means the decision has been made by omission.

**The review comment a senior engineer leaves:** *"The card lists `request_approval` with the
docstring. Before this is reachable from outside, split it: a public card with the two skills we want
work routed to, and the full list behind the extended card."*

**The interview question:** *"What are the risks of agent discovery?"* The answer that shows
experience does not say "information disclosure". It says that the discovery document is generated
from the implementation, so it grows with the code and is published before authentication, and then
names the specific thing it reveals — the tool inventory, in the developer's own words.
