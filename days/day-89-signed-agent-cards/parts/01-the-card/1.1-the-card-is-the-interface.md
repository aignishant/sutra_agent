# 1.1 — The card is the interface

## One-line answer

An A2A Agent Card is the document another agent reads before it decides to talk to you — ADK builds
one from your agent object for nothing, filling eight of the protocol's fourteen fields, and the
field it never fills is `signatures`.

## The story

The board outside a workshop.

Painted on a sheet of tin above the door: *Lathe work. Welding. Radiator repair. Estimates free.*
That board is doing a job before anybody walks in. A driver with a cracked radiator reads it from
across the road and decides, without asking anyone, that this is the right place and the place two
streets down is not.

The board is not the workshop. It is a set of claims about the workshop, and everything that happens
next — the driver crossing the road, the conversation, the money — starts from a stranger deciding
to believe it.

Nobody signs a tin board. Nobody needs to, because the board is bolted to the building it describes
and you can see both at once. That is the property a network does not have.

## The idea in plain language

**A2A** is the Agent2Agent protocol: a way for one agent to be a client of another over HTTP. The
first thing a client does is fetch a document called the **Agent Card** — a JSON object saying what
this agent is, where to reach it, which transports it speaks, what it can do, and how you are
expected to authenticate.

The card is the interface. Not the code, not the model, not the tools: the card. A peer that has
never seen your repository reads this one document and, from it alone, decides what to send you.

ADK builds one for you. `AgentCardBuilder` takes an ADK agent object and walks it — the name, the
description, the tool list — and returns an `AgentCard`. That costs nothing, because it reads the
Python object rather than asking the model anything. The model string in your agent is copied into
the card as text and never dialled.

Two things about that card are worth knowing before anything else, and both are measured below.

**It is not complete, and it is not supposed to be.** The protocol defines fourteen fields; ADK
fills eight. The gaps are things only you know — who provides this agent, where its documentation
lives, what security schemes a caller must satisfy.

**One of the gaps is `signatures`, and that gap is different in kind.** The others are descriptive
and their absence costs nothing. `signatures` is what turns a set of claims into a set of claims
somebody is standing behind, and a card without it is a tin board that is not bolted to anything.

## Why Sutra needs it

Because Phase 14's gate is **"A2A peer verified; repo public"**, and the word doing the work in the
first half is *verified*. Sutra is about to be reachable by agents nobody in this repository wrote,
and the card is the first and cheapest thing either side can check about the other.

And because it is the natural end of the arc that started at Day 42, when Sutra first served
capability over MCP. MCP exposed tools to a client that already trusted the server. A2A exposes the
whole desk to a peer that has no reason to.

## The mechanism

ADK's builder takes the agent and an RPC url, and nothing else that matters:

```python
def build_card():
    """The A2A agent card ADK produces for that agent, as a protobuf message."""
    builder = AgentCardBuilder(agent=desk(), rpc_url=RPC_URL)
    return asyncio.run(builder.build())
```

**Line by line:**

- `AgentCardBuilder(agent=..., rpc_url=...)` — keyword-only, because its constructor is declared
  with a bare `*` before the parameters. Passing the agent positionally raises `TypeError`.
- `build()` is a coroutine, so it needs an event loop even though nothing in it awaits a network.
  `asyncio.run` is the honest way to say "this is async and there is no server here".
- `rpc_url` is where the card will tell peers to send work. It is a claim about the future: nothing
  is listening on it at the moment the card is built, and nothing checks that anything ever will.
- What is *not* here is a key, a signing parameter, or a place to put one. That absence is the
  finding, and it is confirmed below.

The card that comes back is a protobuf message, not a pydantic model — `a2a-sdk` 1.1.2 generates its
types from a `.proto`, and the descriptor is the most reliable statement of what the protocol has:

```python
        print(f"the protocol defines {len(AgentCard.DESCRIPTOR.fields)} fields on an agent card\n")
        for field in AgentCard.DESCRIPTOR.fields:
            camel = field.camelcase_name
            mark = "yes" if camel in filled else "-"
            print(f"  {field.name:<24}{field.number:>3}  {mark}")
```

**Line by line:**

- `AgentCard.DESCRIPTOR.fields` is the generated schema itself, so this table cannot drift from the
  installed protocol the way a hand-written list would.
- `field.camelcase_name` because the JSON form uses camel case (`defaultInputModes`) while the
  descriptor uses snake case (`default_input_modes`). Comparing the wrong one reports every field as
  missing, which is a five-minute mistake worth naming once.
- `field.number` is the protobuf field number and it is a fact about the wire format, not a
  presentation detail. `signatures` being number 13 means it has been in this schema since it was
  designed — it is not a late addition somebody forgot.

**Eight of fourteen, and `signatures: 0`.** That is not a bug report. ADK cannot sign your card,
because signing needs a private key and a framework that took one would be a framework asking you to
hand it your identity. The gap is correct and it is yours to fill, which is what the rest of this
day does.

Two smaller things in that output are worth carrying forward. `version` is `0.0.1` — a default
nobody chose, published to peers as a fact. And `skills: 4` for an agent with three tools, which
part [1.3](1.3-what-the-card-gives-away.md) is about.

## When it breaks

Constructing the builder warns, and the warning is the API contract. Measured on 2026-09-07:

```text
[EXPERIMENTAL] AgentCardBuilder: ADK Implementation for A2A support (A2aAgentExecutor,
RemoteA2aAgent and corresponding supporting components etc.) is in experimental mode and is
subject to breaking changes. A2A protocol and SDK are themselves not experimental. Once it's
stable enough the experimental mode will be removed. Your feedback is welcome.
```

Note where the line is drawn: **the integration is experimental and the protocol is not.** That is
an unusually precise thing for a warning to say, and it tells you which half of your code is exposed
— anything calling `AgentCardBuilder` or `to_a2a` may break on an ADK upgrade, while anything
reading and writing cards to the specification will not.

Note also *when* it fires. The warning is on the `@a2a_experimental` decorator, so it arrives at
**construction**, not at import — a suppression filter installed after the import line still works,
which is why `_desk.py` can silence it and a reader can still see it by constructing the builder in
a shell.

Importing the module warns about something else entirely:

```text
BaseAgentConfig is deprecated and will be removed in future versions. Config is now loaded via
reflection so the separate config class is no longer needed.
```

Four times, on one import. That one is not about A2A at all — it is ADK's own configuration layer
moving underneath, and it is the kind of noise that trains people to stop reading warnings, which is
the condition under which the first warning gets missed.

The other failure is quieter and arrives before any of this. On a checkout without the protocol
library:

```text
ModuleNotFoundError: No module named 'a2a'
```

ADK ships the *integration* and not the protocol library, so `google.adk.a2a` imports fine as a
package path and every module inside it fails. The fix is the `docs/PACKAGES.md` row for
`a2a-sdk==1.1.2` and nothing else — but the error names `a2a`, which is not a package anybody typed,
so the first search is usually for the wrong thing.

## In production

**What a professional does.** Treats the card as a published API document and reviews it like one.
Its contents are a commitment to strangers: the url will keep working, the skills list is accurate,
the version means something. In particular `version` gets set deliberately, because `0.0.1` is what
a peer will pin against and complain about later.

**What degrades at scale.** One agent, one card, no problem. A fleet of agents each publishing a
card generated from its own code means the fleet's public surface changes whenever anybody adds a
tool — silently, in a deployment nobody reviewed as an interface change. That is the point at which
card generation moves into the build and the diff gets read.

**The failure that only shows with real traffic.** A card that is right and stale. Peers cache it —
they must, or every call pays for a fetch — so a url change propagates at the speed of whatever
cache lifetime nobody set. The protocol has a version field and no freshness field, which means
expiry is a deployment decision that looks like it has already been made for you.

**The review comment a senior engineer leaves:** *"Set `version` before this ships. `0.0.1` is not a
version, it is the absence of one, and someone will pin to it."*

**The interview question:** *"How does one agent discover what another can do?"* The answer that
shows experience names the card and then immediately asks the second question — how the reader knows
the card is genuine — because discovery without verification is just a document a stranger handed
you.
