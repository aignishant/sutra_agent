# 1.2 — Where the card lives

## One-line answer

The card is served at one path every A2A client already knows — `/.well-known/agent-card.json` — and
💥 the Starlette app ADK hands you has **no routes at all** until its lifespan runs, so a test that
uses the app directly gets a 404 for the card and every other path.

## The story

💥 **The hall booked, the address printed, and the gate chained.**

🎬 **The scene.** A function hall is booked. The address goes on five hundred printed cards and the
cards go out. Everybody knows exactly where to be and when.

😬 **The naive fix.** Somebody asks whether it is all arranged. It is: the booking is confirmed, the
address is right, the cards are correct. Nothing about the *information* is wrong and that is what
the question was about.

💥 **Why it fails.** On the day, the gate is chained. The caretaker unlocks it when the hall opens
for a function, and nobody told him this one was starting early. Guests arrive at a correct address
and stand outside a correct building, and the first person to work out what has happened spends
twenty rings of an unanswered phone assuming they have the wrong place.

💡 **The insight.** **A correct address and an open door are two different facts**, and only one of
them is written on the card. The failure looks like a wrong address to everybody standing in front
of it, which is why it takes so long to diagnose.

## The idea in plain language

A2A does discovery by convention. Rather than an agent telling you where its description lives, the
protocol fixes the path: fetch `/.well-known/agent-card.json` from the host and you get the card.
That is the same trick a browser uses to find a site's certificate policy or an identity provider's
configuration, and it works for the same reason — everybody agreed once, so nobody negotiates.

The SDK states it as a constant rather than a convention you retype:

- `AGENT_CARD_WELL_KNOWN_PATH` is `/.well-known/agent-card.json`
- `PROTOCOL_VERSION_CURRENT` is `1.0`, with `PROTOCOL_VERSION_0_3` still present beside it
- `VERSION_HEADER` is `A2A-Version`

ADK gives you a server for this in one call. `to_a2a(agent)` returns a **Starlette application** with
the card route and the JSON-RPC route on it, ready to hand to uvicorn.

Except that it does not, quite. The routes are not on the app when `to_a2a` returns. They are added
during **startup** — the lifespan — because building the card is a coroutine and the app has to be
constructed synchronously. Under uvicorn you never notice, because uvicorn runs the lifespan before
it accepts a connection.

Under a test you notice, and the way you notice is a 404 on a path you can see in the source.

## Why Sutra needs it

Because this is exactly how Sutra's A2A endpoint will be tested. Day 85 established the pattern:
exercise the ASGI app in-process with `httpx.ASGITransport`, no socket, no port, no cost. That
pattern is right and it has this one sharp edge, and meeting it here is much cheaper than meeting it
in a test that "cannot find the card" the day before a demo.

And because the well-known path is a **blast-radius** fact, not just a convenience. It means every
agent on the internet knows where to look, and part [1.3](1.3-what-the-card-gives-away.md) is about
what they find when they do.

## The mechanism

The client is four lines and never opens a socket:

```python
async def fetch(app) -> tuple[int, dict | None]:
    transport = httpx.ASGITransport(app=app)
    async with httpx.AsyncClient(transport=transport, base_url="http://127.0.0.1:8931") as client:
        response = await client.get(AGENT_CARD_WELL_KNOWN_PATH)
        body = response.json() if response.status_code == 200 else None
        return response.status_code, body
```

**Line by line:**

- `httpx.ASGITransport(app=app)` speaks ASGI to the application object directly. No port is bound,
  nothing is listening, and the request never reaches the operating system's network stack.
- `base_url` still has to be a valid absolute url because httpx builds a real `Request` — but the
  host in it is never resolved. It shows up in the app as the `Host` header and nothing more.
- `AGENT_CARD_WELL_KNOWN_PATH` imported from the SDK rather than typed. A hand-typed
  `/.well-known/agent_card.json` — underscore instead of hyphen — is a 404 that looks exactly like
  the one this part is about, and the two have completely different fixes.
- The `if response.status_code == 200` guard exists because `response.json()` on a 404 raises
  `json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)`, which is a confusing
  first error to meet: the real problem is the status, and the traceback is about parsing.

And the two ways of driving the same app:

```python
    print(f"  routes before startup: {paths(app)}")
    if not started:
        status, body = await fetch(app)
    else:
        async with app.router.lifespan_context(app):
            print(f"  routes after startup:  {paths(app)}")
            status, body = await fetch(app)
```

**Line by line:**

- `app.router.lifespan_context(app)` is Starlette's own startup and shutdown, entered by hand. This
  is what uvicorn does for you and what `ASGITransport` does not.
- The route table is printed on both sides of that boundary, because the whole finding is the
  difference between the two lines and a status code alone would not show it.
- `paths(app)` reads `route.path`, which is the registered pattern rather than a matched url. An
  empty list is therefore a statement about the app, not about the request.

Run both arms:

```bash
cd days/day-89-signed-agent-cards/lab
uv run python served.py; echo "exit: $?"
uv run python served.py --lifespan; echo "exit: $?"
```

**Line by line:**

- No flag is the test-shaped client; `--lifespan` is the server-shaped one. Nothing else differs.

Measured on 2026-09-07:

```text
the well-known path: /.well-known/agent-card.json
protocol version:    1.0   (header: A2A-Version)
client: test-style, app used directly

  routes before startup: []

  GET /.well-known/agent-card.json -> 404

  the app was returned with an empty route table and the routes are added at startup
  a client that never runs the lifespan gets 404 for every path, including this one
exit: 1
```

```text
client: server-style, lifespan run

  routes before startup: []
  routes after startup:  ['/.well-known/agent-card.json', '/']

  GET /.well-known/agent-card.json -> 200
  the card names itself sutra_desk at http://127.0.0.1:8931
  binding JSONRPC, protocol 1.0

  the card is where the protocol says it is
exit: 0
```

**`routes before startup: []`.** Not "the card route is missing" — *no routes at all*. Two of them
appear during startup and one of them is the entire JSON-RPC surface, so an app used without its
lifespan is not a partially working agent. It is an HTTP application that answers 404 to everything
and looks, from the outside, exactly like a misconfigured path.

## When it breaks

The 404 is the mild version. The sharp version is the one that arrives when the card *is* fetched
and the reader assumes what it says is checkable:

```text
  the card names itself sutra_desk at http://127.0.0.1:8931
  binding JSONRPC, protocol 1.0
```

Every one of those is a claim the card makes about itself, served over a path that asks for no
credential, from a host that anybody can stand up. The well-known convention means a client knows
where to look; it does not mean what it finds is true. A card fetched over plain HTTP from a host an
attacker controls is a well-formed, correctly located, entirely fictitious description of an agent —
and part [3.1](../03-the-verifier-decides/3.1-the-algorithm-the-card-chose.md) is what happens when
the client then trusts the card to tell it how to check itself.

The second failure has no error text at all. `to_a2a` accepts `rpc_path` to mount everything under a
prefix, and its own docstring warns that a caller-supplied card's advertised url is **not** rewritten
to match. So the card can be served at one path while advertising another, both correct
independently, and the peer follows the advertised one.

## In production

**What a professional does.** Runs the lifespan in tests, using the same mechanism the server uses —
`lifespan_context`, or a client fixture that enters it — so that what is tested is the app as it will
actually run. The tell of a test suite that skipped this is a set of tests that pass against an
application with no routes.

**What degrades at scale.** Well-known paths are a single namespace per host. Two agents on one
hostname cannot both own `/.well-known/agent-card.json`, so a fleet needs either a host per agent or
the prefix mounting — and the prefix mounting is exactly the feature whose docstring warns about the
url mismatch. That is the point at which card generation and routing have to be one decision.

**The failure that only shows with real traffic.** Caching. The card lives at a stable path, so
proxies and clients cache it; the protocol carries a version field and no expiry. A url change ships
instantly on your side and arrives on the peer's side whenever their cache decides, which means a
migration has a tail nobody in your repository can see or measure.

**The review comment a senior engineer leaves:** *"Your A2A tests never run the lifespan, so they are
asserting against an app with an empty route table. Use `lifespan_context` in the fixture and watch
how many of them still pass."*

**The interview question:** *"Your ASGI app works under uvicorn and 404s in tests. Where do you
look?"* The answer that shows experience asks what runs at startup, because the whole class of bug is
things a framework does during the lifespan that a direct transport skips — routes, connection pools,
background tasks and warm caches.
