# 5.2 — Degrading, not failing

## One-line answer

With the allowance gone there are three things the desk can say, and the run shows all three: a
`RuntimeError` that helps nobody, a `degraded` answer from the handbook that says where it came from,
and an `ok` answer marked `source: model` that came from a lookup table and is a lie.

## The story

The restaurant has run out of the fish and there are two ways the evening goes.

In the first, the waiter comes back and says so. *"The sea bass is finished, I'm sorry — the same
sauce comes with the chicken if you'd like, or I can bring the menu back."* You are mildly
disappointed and you order something else. Nothing about the evening is spoiled.

In the second, nobody says anything. Something arrives that is white and has the sauce on it, and it
is fine, and you eat it thinking it is what you ordered. You would probably never notice. But you have
been told something untrue about your own dinner, by a restaurant that decided you would rather not be
bothered — and if you ever do find out, what you will remember is not the substitution. It is that
they did not say.

## The idea in plain language

The allowance runs out. That is not an exceptional event, it is a scheduled one: a fixed number of
requests per day means there is a moment every day when the number is reached, and the system's
behaviour after that moment is a design decision that somebody makes either deliberately or by
default.

There are exactly three exits.

**Fail.** Raise, and let the caller deal with it. Honest, and often the wrong choice for a
user-facing path, because a large fraction of what a support desk does does not need a model at all.

**Degrade.** Answer with something you can produce without the model — a handbook entry, a cached
answer, a template, a plain database lookup — and **mark it** as a substitute. The user gets something
useful and knows what it is.

**Pretend.** Answer with the fallback and present it as though the model produced it. This is the one
that looks like the best user experience and is the only one of the three that is unacceptable.

[Day 21](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.2-a-substitute-must-say-so.md)
established the rule this rests on: **a substitute must say so.** The reason is not politeness. A
result marked `degraded` is a result that everything downstream can reason about — the model composing
a reply can hedge, a log line can be counted, a dashboard can alert, and a human reading the answer
knows how much to trust it. A result marked `ok` when it is not has removed all of that, permanently,
and has done so silently.

There is a second reason, specific to a quota tier. Degrading is only possible if you know the budget
is gone **before** you commit to using it, which is
[3.2](../03-counting-before-spending/3.2-refusing-before-the-call.md)'s local check earning its keep a
second time. A system that discovers the ceiling from a `429` has already spent a request and is now
choosing what to say; a system that checks first still has the choice and has spent nothing.

## Why Sutra needs it

Because Sutra's desk answers two kinds of question, and only one of them needs a model.

*"What is our refund window?"* is a lookup. The answer is in the handbook, it is the same for every
customer, and the model's contribution is phrasing. *"Why is ticket 4521 stalled?"* is not a lookup —
it needs the ticket, the history and a judgement, and there is no honest substitute for it.

So when the allowance is gone, a desk that fails outright refuses to answer questions it could answer
perfectly. And a desk that answers everything from the handbook will confidently produce *"I do not
have information about that"* for the second question, presented as a considered answer, which is
worse than a refusal because it looks like one.

The distinction has to be per question, and the answer has to carry its provenance. That is a small
amount of code and it is the difference between a system that is unavailable for an afternoon and one
that is quietly wrong for an afternoon.

## The mechanism

Three modes over the same two questions, after the day's twenty requests are gone.

```python
# days/day-24-token-accounting-and-budgets/lab/degrade_dont_fail.py
MODE = os.environ.get("MODE", "degrade")

CANNED = {
    "refund window": "Refunds are issued to the original payment method within 30 working days.",
    "password reset": "Use the 'forgot password' link; the reset email arrives within 10 minutes.",
}


def answer(question: str, ledger: Ledger, now: float) -> dict[str, str]:
    """One question, answered by the model if there is budget and by the rules if there is not."""
    why = ledger.refusal(now)
    if why is None:
        ledger.spend(now)
        return {"status": "ok", "source": "model", "text": f"[model answer to {question!r}]"}

    if MODE == "fail":
        raise RuntimeError(why)

    if MODE == "pretend":
        canned = CANNED.get(question, "I do not have information about that.")
        return {"status": "ok", "source": "model", "text": canned}

    canned = CANNED.get(question)
    if canned is None:
        return {"status": "unavailable", "source": "policy", "text": why}
    return {"status": "degraded", "source": "handbook", "text": canned}
```

**Line by line:**

- `why = ledger.refusal(now)` is the **first** line of the function, before anything is spent. The whole
  page depends on knowing the budget is gone in advance rather than discovering it
  ([3.2](../03-counting-before-spending/3.2-refusing-before-the-call.md)).
- The happy path returns `"source": "model"` — every answer says where it came from, not only the
  degraded ones. A provenance field that appears only on failures is a field nothing downstream can
  rely on, because its absence would be ambiguous.
- `MODE == "fail"` raises `RuntimeError(why)`, carrying the ledger's sentence. Even the version this
  part argues against is honest: it does not invent a reason.
- `MODE == "pretend"` returns `"status": "ok", "source": "model"` for something the model never saw.
  **Both fields are lies**, and it is worth noticing that the lie is two fields rather than one: the
  status says the request succeeded and the source names a component that was never called.
- The `degrade` path splits on whether a canned answer exists. That split is the actual content of this
  page: `CANNED.get(question)` returning `None` is the system finding out it has nothing honest to say,
  and the correct response is `"unavailable"`, not a shrug dressed as an answer.
- `"status": "unavailable"` and `"source": "policy"` — the refusal is attributed too. An operator
  reading a log wants to know that this was Sutra's own budget policy rather than a provider outage,
  because those need different responses.
- The `text` on the unavailable branch is `why` — `gemini-3.7-flash: 20/20 per day - does not clear`.
  That is fine for an operator and is **not** what a customer should see; turning it into a public
  sentence is
  [21.3.3](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.3-giving-up-honestly.md)'s job,
  and leaving the raw string here is a deliberate gap the build brief asks you to close.
- `CANNED` is a dict of two entries because two is enough to show the split. In Sutra it is the
  handbook, and the interesting engineering question — which questions have honest non-model answers —
  is a content question rather than a code one.

```bash
cd days/day-24-token-accounting-and-budgets/lab
MODE=degrade uv run python degrade_dont_fail.py
MODE=fail    uv run python degrade_dont_fail.py
MODE=pretend uv run python degrade_dont_fail.py
```

**Line by line:**

- `MODE` is the ablation, with three positions rather than two, because the third one is the failure
  this part exists to name. No key, no network, **0** generations.

Measured on 2026-09-04:

```text
MODE=degrade  (the day's 20 requests are gone)
  'refund window'                    degraded     via handbook  Refunds are issued to the original payment method wi
  'why is ticket 4521 stalled'       unavailable  via policy    gemini-3.7-flash: 20/20 per day - does not clear

MODE=fail  (the day's 20 requests are gone)
  'refund window'                    RuntimeError: gemini-3.7-flash: 20/20 per day - does not clear
  'why is ticket 4521 stalled'       RuntimeError: gemini-3.7-flash: 20/20 per day - does not clear

MODE=pretend  (the day's 20 requests are gone)
  'refund window'                    ok           via model     Refunds are issued to the original payment method wi
  'why is ticket 4521 stalled'       ok           via model     I do not have information about that.
```

**Compare the first row of each block.** All three produce something for *"refund window"*, and the
text of the answer is identical in the first and the third. The only difference is the two words in
front of it: `degraded via handbook` against `ok via model`.

That difference is everything. In the first case a log line can be counted, an alert can fire on the
rate, and the model composing the customer's reply knows to say *"according to our published policy"*.
In the third, nothing anywhere can tell that the model was never called.

**Now compare the second row.** This is the question that has no honest substitute, and the three modes
diverge completely:

- `degrade` says **unavailable**, and says why. The user is told to come back; nobody is misled.
- `fail` raises, which for this question is nearly as good, and for the first question was
  unnecessary.
- `pretend` answers *"I do not have information about that"* with `status: ok` and `source: model`.

Read that last one carefully, because it is the worst outcome available and it does not look like one.
The sentence is a plausible thing for a model to say. It will be logged as a successful request. It
will appear in any quality review as *"the model did not know"*, and somebody will spend an afternoon
improving the prompt for a question that never reached a model. **The lie is not the sentence; it is
the two metadata fields around it.**

## When it breaks

The `fail` mode is honest and produces a real error, which is the easy case:

```text
RuntimeError: gemini-3.7-flash: 20/20 per day - does not clear
```

Everything an operator needs is in that line: the model, both numbers, and the fact that waiting is
futile. It is the right thing to raise and the wrong thing to show a customer, and Day 21 has the part
about the difference.

The `pretend` mode produces **no error at all, ever**, and that is the finding. There is no traceback
to catch, no status to alert on, no metric that moves. The system reports a hundred percent success on
a day it answered half its questions from a two-entry dictionary.

The way it eventually surfaces is a mismatch between two numbers that nobody thought to compare: the
provider says twenty requests were made, and the application says it answered forty questions
successfully. That comparison is the only detector, and it exists only if both numbers are being kept —
which is [4.2](../04-failure-lab/4.2-the-counter-that-counted-the-wrong-thing.md)'s counter, used for
something other than budgeting.

There is a subtler failure inside the honest mode too. A degraded answer whose text is *identical* to
the model's usual answer is indistinguishable to the customer, and over time the handbook entry drifts
away from what the model would say. The marking makes it detectable; it does not make it correct. Which
is why the substitute's content deserves the same review as any other user-facing text.

## In production

**Degradation is designed, not discovered.** The useful exercise is to go through the system's
functions and label each one: *needs the model*, *nice to have the model*, *does not need the model at
all*. Most systems find that the third category is larger than anybody assumed, and every item in it is
a feature that keeps working when the budget is gone. That list is more valuable than any amount of
retry logic.

**Cache before you degrade.** A cached answer to a question that was asked an hour ago is a better
substitute than a handbook entry, because it *is* the model's answer. On a per-request tier a cache is
also the single most effective budget measure available — every hit is a request not spent — and it is
the reason Day 51's caching day exists.

**Shed load in priority order.** When capacity is short, the question is not only *what do we say* but
*to whom*. A production system with the workload classes from
[5.1](5.1-whose-budget-is-it.md) degrades the batch path long before the interactive one, so the
allowance that remains goes to the requests a person is waiting for.

**What changes at scale** is that degradation needs to be announced upward as well as downward. A
customer sees a marked answer; an operator needs a metric. The pair that works is a counter on
`status == "degraded"` with an alert on the **rate** rather than on any single occurrence — a
substitute firing occasionally is the system working as designed, and the same substitute firing on a
third of requests is an outage being concealed by your own fallback.

**The failure that only appears with real traffic** is the fallback that becomes the product. A
degradation path that works well enough stops being noticed, and six months later a third of answers
come from the handbook, the quality has quietly halved, and the dashboard is green because every one of
those responses was a success. The rate alert is what prevents it, and the reason it works is that the
answers were marked.

**The review comment a senior engineer leaves:** *"the fallback returns the same status as a real
answer. Mark it — otherwise we can't count it, can't alert on it, and the model can't tell the customer
where the answer came from."*

**The interview question:** *"what does your system do when it runs out of quota?"* The answer that
shows you have thought past the exception: *"it depends on the question. Anything that has an honest
non-model answer — a policy lookup, a cached response — gets served from that, marked as degraded so
the status field says where it came from. Anything that genuinely needs the model gets an honest
'unavailable', not a plausible-sounding filler. The thing I'd never do is return the fallback with a
success status, because then nothing downstream can count it and you find out six months later that
most of your answers aren't coming from the model at all."*
