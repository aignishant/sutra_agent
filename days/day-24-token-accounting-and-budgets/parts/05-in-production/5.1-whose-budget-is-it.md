# 5.1 — Whose budget is it?

## One-line answer

One project ceiling of twenty, three engineers, and one of them triaging a backlog: sharing it served
**20 of 22** arrivals but refused the two light users four times, while giving each a sixth of it
refused nobody except the heavy user — and served only **14**. Neither is free; the question is which
failure you would rather explain.

## The story

The apartment block has one tank on the roof and a pump that fills it in the morning.

Nobody thinks about it until the flat on the second floor decides to wash the car, water the plants and
run the washing machine, all before nine. By the time the family on the fourth floor gets up there is
air in the taps, and their morning is ruined by a decision they were not present for and cannot see.

The committee's answer is a meter on each flat and a monthly allocation. It stops the second floor
emptying the tank. It also means that on a quiet week, when the tank is full and nobody else wants
anything, the second floor is refused water that would otherwise have run to waste.

Both arrangements have a bad day. The committee is not choosing between a fair system and an unfair
one; it is choosing which complaint it would rather receive.

## The idea in plain language

The provider's ceiling is enforced at **one level**, and the refusal names it:
`GenerateRequestsPerDayPerProjectPerModel-FreeTier`
([2.2](../02-two-ceilings/2.2-reading-the-ceiling-off-a-refusal.md)). **Per project.** Everything
inside your project draws on the same twenty.

But a project usually contains more than one *thing that deserves an answer*. Several users. Several
features. A batch job. Staging. And the provider has no opinion about any of them — it sees one project
making requests, in the order they arrive, and starts refusing when the count is reached.

So the allowance is spent **first come, first served**, and that is a policy. Nobody chose it, it is
simply what happens when nothing else is chosen, and it has a well-known failure: one heavy consumer
takes everything and everybody else experiences an outage they did not cause. In distributed systems
this is called the **noisy neighbour** problem, and it appears anywhere a shared resource has no
internal division.

The fix is to divide the ceiling internally: one ledger per user, per tenant, per feature — whatever
the unit of fairness is — each with a share, all of them bounded by the project ceiling above.

And the trade is exact and unavoidable: **an internal share protects the light users and wastes
capacity.** If a user's share is unused, and the shared ceiling has room, a strict per-user limiter
refuses work it could have done. The middle path is a **share plus a spillover** — guarantee a
minimum, allow use of the surplus if it is there — which is more code and is what real systems do.

The thing to be clear about before choosing: **which failure you are buying.** First-come-first-served
buys "one user can ruin everybody's day". Fixed shares buy "we refused work we could have done". There
is no third option that costs nothing.

## Why Sutra needs it

Because Sutra's desk is going to have more than one engineer using it, and its ceiling is twenty.

At eight requests per conversation ([1.2](../01-what-a-request-costs/1.2-charged-again-every-turn.md))
one person having one thorough conversation about one ticket uses forty percent of the day. Two of them
and the desk is done before lunch, for everyone. That is not an edge case; it is Tuesday.

It also decides what Phase 8's Quota-Router is routing *for*. A router that maximises total throughput
will happily let one caller have everything; a router that guarantees each caller a share will refuse
that caller. Those are different products, and the choice belongs in the design rather than in whichever
loop happened to get written first.

## The mechanism

The same morning, twice: one ledger for everybody, or one ledger each.

```python
# days/day-24-token-accounting-and-budgets/lab/budget_per_what.py
PER_USER = os.environ.get("PER_USER", "1") == "1"

# Arrival order through one morning: the first engineer is triaging a backlog.
ARRIVALS = ["asha"] * 14 + ["ben", "chi", "ben", "chi", "ben", "chi", "ben", "chi"]


def main() -> None:
    share = FREE.rpd // 3 if PER_USER else FREE.rpd
    ledgers = {
        name: Ledger(ceiling=Ceiling(name=f"{FREE.name}/{name}", rpm=FREE.rpm, rpd=share))
        for name in {"asha", "ben", "chi"}
    }
    shared = Ledger(ceiling=FREE)

    for i, who in enumerate(ARRIVALS):
        now = i * 60.0
        book = ledgers[who] if PER_USER else shared
        if book.refusal(now) or shared.refusal(now):
            refused[who] += 1
            continue
        book.spend(now)
        if PER_USER:
            shared.spend(now)
        served[who] += 1
```

**Line by line:**

- `ARRIVALS` puts all fourteen of Asha's requests **first**, which is the realistic shape: somebody
  sitting down to clear a backlog does not interleave politely with other people's occasional
  questions. Ordering is the whole experiment — the same twenty-two requests in a different order give
  a different answer, and that dependence is itself the argument for having a policy.
- `share = FREE.rpd // 3` divides the ceiling by the number of users, using integer division so the
  shares can never sum to more than the ceiling. Six each, and the two left over are unallocated —
  which is a real, small waste and honest to leave visible.
- `Ceiling(name=f"{FREE.name}/{name}", ...)` gives each user's ceiling a **distinct name**, so a
  refusal sentence says `gemini-3.7-flash/asha` and a log line can be grouped by who was refused. A
  per-user limiter whose refusals are indistinguishable is a limiter nobody can debug.
- The per-user ceilings keep the **same `rpm`** and only divide `rpd`. That is a deliberate choice
  rather than an omission: the per-minute limit is about protecting the provider from bursts and is
  meaningfully a project-level concern, while the daily limit is about fairness between people.
- `if book.refusal(now) or shared.refusal(now)` checks **both** — the user's share and the project
  ceiling above it. The second check is what stops the shares from over-committing if they were ever
  set too generously, and it is the reason `shared` is spent in the `PER_USER` branch too.
- `shared.spend(now)` inside `if PER_USER` keeps the project-level ledger accurate in both arms, so the
  two runs are comparable. Forgetting it would make the per-user arm blind to the ceiling it lives
  under.
- `continue` on refusal, so nothing is spent — the same before-not-after rule as
  [3.2](../03-counting-before-spending/3.2-refusing-before-the-call.md).

```bash
cd days/day-24-token-accounting-and-budgets/lab
PER_USER=1 uv run python budget_per_what.py
PER_USER=0 uv run python budget_per_what.py
```

**Line by line:**

- `PER_USER` is the ablation. No key, no network, **0** generations.

Measured on 2026-09-04:

```text
PER_USER=1  (project ceiling 20/day, 6/day each)
  asha  served  6   refused  8
  ben   served  4   refused  0
  chi   served  4   refused  0
  total served 14 of 22 arrivals

PER_USER=0  (project ceiling 20/day)
  asha  served 14   refused  0
  ben   served  3   refused  1
  chi   served  3   refused  1
  total served 20 of 22 arrivals
```

**Read the totals first, because they are the opposite of what the argument for fairness leads you to
expect.**

Sharing served **20 of 22**. Dividing served **14 of 22**. The fair arrangement did *less work* — six
requests' worth — and it did so while the project ceiling had capacity left, because Asha's share was
exhausted and nobody else wanted it.

**Now read the per-person rows, which is where the fairness lives.** Under sharing, Ben and Chi were
each refused once, at the end of the morning, for reasons entirely created by Asha. Under division,
neither of them was refused at all: they got everything they asked for, and the person who absorbed
every refusal was the one generating the load.

So the honest summary is:

| | Total served | Light users refused | Heavy user refused |
| --- | --- | --- | --- |
| Shared | **20** | 2 | 0 |
| Per user | 14 | **0** | 8 |

**Neither column is "better".** The shared arrangement maximises work done and lets one person's
backlog become everyone's outage. The divided arrangement protects everyone else completely and leaves
six requests of a scarce allowance unspent. The choice is a product decision — is this desk for
throughput or for predictability? — and the only wrong move is making it by accident.

The middle path, which is what production systems build, is in *In production* below.

## When it breaks

The failure of the shared arrangement has no error message from your system; it has a message from the
provider, delivered to the wrong person:

```text
429 RESOURCE_EXHAUSTED. {'error': {'code': 429, ... 'limit: 20, model: gemini-3.7-flash' ...}}
```

Chi sees that at eleven in the morning, having asked four questions all day. Every fact in it is true
and none of it explains what happened, because what happened is in somebody else's session.

The failure of the divided arrangement is quieter and more annoying to explain. A refusal that says:

```text
gemini-3.7-flash/asha: 6/6 per day - does not clear
```

while the project has fourteen requests unspent. That sentence is correct, and the person reading it
can see — on the same dashboard — that there is capacity. Fixed shares without spillover generate
exactly this complaint, and it is a good complaint: it means the policy is working and the parameters
are wrong.

The failure that is genuinely a bug, rather than a trade, is dividing without keeping the project
ledger. Shares that sum to more than the ceiling — three users at ten each against a ceiling of twenty
— behave correctly until two of them are busy at once, and then the provider starts refusing requests
your own limiter approved. The `or shared.refusal(now)` in the mechanism above is the line that
prevents it.

## In production

**The unit of fairness is rarely the user.** For a SaaS product it is the tenant; for an internal tool
it is the team; for a system with a batch pipeline and an interactive path it is the **workload class**,
and that last one is usually the most valuable division of all: interactive requests get a guaranteed
share and batch work gets whatever is left, so a nightly job can never make the morning slow.

**Guarantee a floor, share the surplus.** The arrangement that avoids both failures above gives each
consumer a reserved minimum and lets anyone use the unreserved remainder first-come-first-served. Asha
would have got her six guaranteed plus whatever Ben and Chi did not want — twenty served *and* nobody
starved. It costs one more ledger and a priority rule, and it is what makes the difference between the
two columns disappear.

**Priority beats fairness for some work.** Not every request deserves an equal share. A paying
customer's question, a health check, and a background summarisation are three different things, and a
production limiter usually has two or three priority classes with the lowest one shed first. That is
the same idea as the workload split, made explicit.

**What changes at scale** is that the shares need to be dynamic. Fixed division by the number of users
stops working the moment the number of users changes — twenty divided by three is six, twenty divided
by fifty is zero — and the system that survives allocates proportionally to some measured demand, or
uses a weighted fair queue rather than fixed slices. The fixed version in this lab is right for three
engineers and wrong for three hundred.

**The failure that only appears with real traffic** is the consumer nobody modelled. Every division
scheme allocates among the consumers you know about, and the quota is **per project**: a colleague's
notebook, a staging deployment and a demo are all spending the same twenty and appear in nobody's
share. The local ledger is honest about what it can see, which is why its output should always be
phrased as *"what we spent"* rather than *"what remains"*.

**The review comment a senior engineer leaves:** *"one ledger for the whole service means the batch job
and the customer-facing path compete for the same allowance, and the batch job always wins because it
starts first. Split by workload class before splitting by user."*

**The interview question:** *"you have one API quota and many users. How do you divide it?"* The
answer that shows you have made the trade: *"first I'd ask what the unit of fairness is — usually
tenant or workload class rather than user, because a batch job starving the interactive path is the
failure that actually hurts. Then a guaranteed floor per class plus a shared surplus, not fixed slices,
because fixed slices refuse work while the ceiling has room. We measured it once: strict per-user
shares protected the light users completely and left about thirty percent of the allowance unspent."*
