# 1.1 — A ticket id costs five tokens

## One-line answer

Asking the provider rather than guessing gives **4.55 characters per token for English prose, 2.21
for a JSON log line, and 0.80 for the string `"4521"`** — so the four characters of a ticket id cost
five tokens, and any estimate based on word count is wrong in a direction that depends on what you
are sending.

## The story

You take a small parcel to the post office: one metal bracket, wrapped, about the size of a matchbox.

The clerk does not weigh it first. She puts it in a plastic frame with slots cut in it, finds the
smallest slot it will pass through, and reads a price off a chart. It costs more than you expected,
because the bracket is inside a padded envelope and the padding put it in the next slot up.

Beside you, someone is posting a cushion. It is enormous. It is also, by the chart, cheaper, because
it squashes flat enough to go through a slot the bracket could not.

Neither of you could have guessed the price by looking. There is a rule, it is written down, and the
only reliable way to know what something costs is to put it in the frame.

## The idea in plain language

A language model does not read characters and it does not read words. It reads **tokens**: chunks of
text produced by a fixed procedure that was decided when the model was trained.
[Day 2](../../../day-02-llm-mechanics/LESSON.md) taught what a token is and why the word "token"
does not mean "word"; this part is about what that costs you.

Everything you send is converted into tokens before the model sees it, and everything it sends back
is tokens too. Providers count them, and their limits are stated in them. So "how big is this
request" is a question with a numeric answer — and the answer is **not proportional to characters**,
and **not proportional to words**, and cannot be worked out by looking.

Three things vary the ratio, and all three show up in Sutra:

**Ordinary prose is efficient.** Common English words were given tokens of their own during training,
so a sentence of everyday language packs several characters into each token.

**Machine output is not.** JSON, timestamps, identifiers and log lines are full of punctuation and
unusual character sequences, and each of those tends to become its own token. The same information
costs more as JSON than as a sentence.

**Digits are the worst case.** Numbers are split into small pieces, so a short numeric string can
cost more tokens than it has characters. This is the one that surprises people, and it is the reason
the title of this part is what it is.

None of this needs to be believed. Every provider exposes a **counting endpoint** that runs the same
procedure the model would and returns the number, and it is a different endpoint from the one that
generates text — which means you can measure all of this without spending any of the day's
generations.

## Why Sutra needs it

Because from today Sutra has a budget, and a budget over a quantity you cannot estimate is a wish.

[Day 19](../../../day-19-context-engineering-selection/LESSON.md) built `weigh(request)` and measured
Sutra's request in **characters**, and said so plainly at the time: characters were chosen because
they need no model call, and the module's docstring names the limit. Today the limit is removable.
`count_tokens` costs no generation, so the same measurement can be taken in the unit the provider
actually charges in.

And the ratios matter for a decision Sutra has already made. Day 22 writes structured logs, and Day 20
compacts conversation history. If a log line ever reaches the model's context — as an error detail, as
a tool result, as a summary — it costs **twice** what the same information would cost as a sentence.
That is not an argument against JSON logs, which exist for machines to query. It is an argument for
knowing which of your data is expensive before you put it in a prompt.

## The mechanism

Ask the provider. Five samples that represent the actual kinds of text Sutra sends.

```python
# days/day-24-token-accounting-and-budgets/lab/count_the_cost.py
from dotenv import load_dotenv
from google import genai

MODEL = "gemini-3.7-flash"  # free tier; roster re-verified 2026-09-04

SAMPLES = {
    "one short sentence": "Refunds are issued to the original payment method.",
    "the same, as JSON": '{"status": "ok", "policy": "Refunds are issued to the original '
    'payment method."}',
    "a Sutra log line": '{"ts": "2026-09-04T10:15:03Z", "level": "WARNING", "logger": "sutra", '
    '"event": "tool_error", "invocation_id": "e-abc123", "tool": "search_kb", '
    '"kind": "TimeoutError"}',
    "a ticket id": "4521",
    "the desk instruction": (
        "You are a support desk assistant. Read the ticket before answering. "
        "Never invent a ticket that does not exist. If a tool fails, say so plainly."
    ),
}


def main() -> None:
    load_dotenv()
    client = genai.Client()
    print(f"{'sample':<24}{'chars':>7}{'words':>7}{'tokens':>8}{'chars/token':>13}")
    for name, text in SAMPLES.items():
        tokens = client.models.count_tokens(model=MODEL, contents=text).total_tokens
        words = len(text.split())
        print(f"{name:<24}{len(text):>7}{words:>7}{tokens:>8}{len(text) / tokens:>13.2f}")
```

**Line by line:**

- `client.models.count_tokens(...)` is a **different endpoint** from `generate_content`. It runs the
  tokenizer and returns a count; it does not run the model, does not produce text, and — verified on
  2026-09-04, on a key whose daily generation allowance was already exhausted — **still works when
  `generate_content` is refusing with a 429**. That is the fact that makes this whole part free.
- `.total_tokens` is the field. The response object also carries `cached_content_token_count`, which
  is `None` here because nothing was cached; it becomes interesting only with explicit context
  caching, which Sutra does not use yet.
- `MODEL` is named because **the tokenizer belongs to the model**. The same string counted against a
  different model can give a different number, so a token count without a model name beside it is
  incomplete.
- The samples are five real shapes rather than a poem and a paragraph: a policy sentence a tool would
  return, the same wrapped in JSON, one of Day 22's log lines, an identifier, and Sutra's own
  instruction. The point is to compare the kinds of text *this system* sends.
- `len(text) / tokens` rather than `tokens / len(text)`. Characters-per-token is the number worth
  carrying in your head, because you can look at a string, guess its length, and divide.
- `load_dotenv()` reads the key from `.env` rather than requiring it to be exported, which is Day 1's
  arrangement and the reason no key ever appears on a command line.


**Line by line:**

- Needs `GOOGLE_API_KEY`, spends **0** generations. Five counting calls, which are on their own quota.

Measured on 2026-09-04 against `gemini-3.7-flash`:

```text
sample                    chars  words  tokens  chars/token
one short sentence           50      8      11         4.55
the same, as JSON            80     11      22         3.64
a Sutra log line            166     14      75         2.21
a ticket id                   4      1       5         0.80
the desk instruction        143     26      32         4.47
```

**Four readings, and the last one is the one to remember.**

**Prose is about four and a half characters per token.** The sentence and the instruction agree —
4.55 and 4.47 — which is why "roughly four characters per token" is the rule of thumb everybody
quotes. It is a good rule of thumb *for English prose* and for nothing else.

**Wrapping the same sentence in JSON doubled the token count**: 11 became 22. The information did not
change. The braces, the quotes, the colons and the key names did. If a tool returns a policy string
inside a JSON envelope, the envelope is not free.

**A log line is 2.21 characters per token** — half the density of prose. Sutra's own log format, which
is exactly right for `grep` and for a dashboard, is the most expensive possible way to put information
in front of a model. That is the same finding
[19.1.2](../../../day-19-context-engineering-selection/parts/01-the-binder/1.2-three-costs-in-one-scene.md)
reached from the other direction, now in the provider's own units.

**And `"4521"` — four characters — costs five tokens.** Fewer than one character per token. A ticket
id, an invocation id, a timestamp, an order number: every identifier Sutra passes around is
disproportionately expensive, and a request full of ids costs far more than its length suggests.

The practical consequence is one sentence: **any estimate of size based on words is wrong, and wrong
by a factor that depends on what kind of text it is.** There is a counting endpoint. Use it.

## When it breaks

Count against a model that does not exist and the provider says so rather than guessing:

```text
google.genai.errors.ClientError: 404 NOT_FOUND. {'error': {'code': 404, 'message': 'models/gemini-9.9-flash is not found for API version v1beta, or is not supported for countTokens. Call ModelService.ListModels to see the list of available models and their supported methods.', 'status': 'NOT_FOUND'}}
```

`is not found ... or is not supported for countTokens` — two conditions in one message, which matters
because a model can exist and not offer this endpoint. `Call ModelService.ListModels` is the instruction, and it is
also how Addendum 02's "look up the current free list" is carried out in practice.

The failure with no error at all is more common and worse: **counting the wrong thing**. Counting the
user's message gives a number that has almost nothing to do with the size of the request, because the
request is the instruction plus the tool declarations plus the whole history plus the message. That is
[1.2](1.2-charged-again-every-turn.md), and it is where the real number lives.

## In production

**Nobody counts every request in production; they sample and they cache.** Calling a counting endpoint
before every generation doubles your request count against a different quota and adds a round trip to
the hot path. The mature arrangement measures the *shapes* — an average instruction, a typical tool
result, a p95 history — and then uses the ratios to estimate in code, checking against reality on a
schedule.

**Better still, use the number the provider already gave you.** Every generation response carries
usage metadata: prompt tokens, output tokens, and on some providers cached tokens. That is the
authoritative count, it arrives for free with a call you were making anyway, and it is what a
production budget should be built on. `count_tokens` is for the calls you have **not** made yet —
deciding whether to send something, and how much of the history to include.

**What changes at scale** is that the ratio becomes a monitored number rather than a fact. Tokenizers
change between model versions, and a provider that migrates you from one model to another can change
your token bill without changing a line of your code. Teams that have been through this keep a
canary: a fixed corpus, counted daily, alerting when the ratio moves.

**The failure that only appears with real traffic** is the identifier-heavy request. Everything is
fine while users ask questions in prose, and then a batch job starts feeding in lists of order numbers,
and the token count per request quadruples because digits tokenize badly. The estimate built from
English prose was never wrong; it was answering a question about different data.

**The review comment a senior engineer leaves:** *"this budget is in characters. Characters were the
right call on Day 19 because counting was expensive — it isn't any more. Use `count_tokens` for the
estimate and the response's usage metadata for the actual."*

**The interview question:** *"how do you estimate what a prompt will cost?"* The answer that shows you
have measured: *"I don't estimate from word count, because the ratio depends entirely on the text —
English prose runs about four and a half characters per token, JSON about three and a half, and log
lines closer to two. Identifiers are the outlier: a four-digit ticket number cost five tokens when I
measured it. So I count with the provider's endpoint for anything I haven't sent yet, and I read the
usage metadata off the response for anything I have."*
