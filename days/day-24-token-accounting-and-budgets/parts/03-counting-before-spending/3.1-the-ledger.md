# 3.1 — The ledger, with the clock as a parameter

## One-line answer

The whole budget is a list of timestamps and two windows over it — and **`now` is an argument on every
method**, never read from the system clock, which is what makes a ceiling that only bites after
twenty-four hours testable in six milliseconds.

## The story

The tea shop at the end of the lane has a wall with names on it and a row of pencil strokes beside
each one.

You come in, you get a cup, he makes a mark. There is no receipt, no card machine, no app. On Saturday
he reads down the wall and you settle up. The whole system is a list of marks, in order, with a rule
about when they get cleared.

Two things make it work and neither of them is clever. The mark goes on the wall **when the cup is
poured**, not when it is paid for, so the wall is never behind reality. And everyone can see it — you
can look up and count your own strokes before deciding whether to have another.

## The idea in plain language

A quota ledger is a list of the moments at which you spent something, plus a rule for reading it.

That is genuinely all it is, and stating it plainly matters because the instinct is to reach for a
counter — one integer, incremented on each call, reset on a schedule. A counter cannot answer the
per-minute question, because "how many in the last sixty seconds" needs to know **when** the requests
happened, not just how many there were. A list of timestamps answers both questions and needs no
resetting: old entries simply fall out of the window.

The second idea in this part is smaller on the page and larger in consequence: **the current time is a
parameter, not something the ledger fetches.**

Written the obvious way, a ledger calls `time.time()` inside its own methods. That is one line shorter
and it makes the whole thing untestable, because the only way to test a daily ceiling is to wait a day.
People work around this by mocking the clock — patching `time.time` for the duration of a test — which
works and is a considerably heavier tool than passing a number in.

Written with `now` as an argument, the ledger is a **pure function of its inputs**. The test says
`ledger.refusal(now=86401.0)` and finds out what happens after a day, immediately, with no patching
and no waiting. And the production caller says `ledger.refusal(now=time.time())`, which puts the one
impure line in exactly one place where it can be seen.

This is [1.1](../../../day-23-testing-tools-and-callbacks/parts/01-where-the-line-falls/1.1-the-nondeterminism-excuse.md)'s
warning from yesterday, arriving as promised: a function that reads a clock is not deterministic, and a
budget module is the most clock-dependent code in the system. Yesterday named the problem; today is
where it would have bitten.

## Why Sutra needs it

Because every later day that spends a request has to ask this object first, and it is going to be asked
in places where a clock is inconvenient.

Phase 8's Quota-Router asks it once per provider, in a loop, to choose a lane. Day 73's ambient nightly
job asks it at a time nobody is watching. Phase 12's eval runs ask it hundreds of times in a batch,
where "now" advances during the run. Every one of those is easier to reason about — and to test — if
the answer depends only on what was passed in.

And the alternative has a specific, expensive failure. A ledger that reads the clock cannot be tested
across a reset boundary, so nobody tests it there, so the reset logic is the least-verified code in the
module — and it is the code that runs exactly once a day, unattended, when nobody is looking.

## The mechanism

The whole thing, in about thirty lines.

```python
# days/day-24-token-accounting-and-budgets/lab/quota.py
from collections import deque
from dataclasses import dataclass, field

MINUTE = 60.0
DAY = 24 * 60 * 60.0


@dataclass
class Ledger:
    """Every request this process has made to one model, as timestamps, oldest first."""

    ceiling: Ceiling
    spent: deque[float] = field(default_factory=deque)

    def _forget_older_than(self, now: float, window: float) -> int:
        """Drop timestamps outside the window and return how many remain inside it."""
        while self.spent and now - self.spent[0] > DAY:
            self.spent.popleft()
        return sum(1 for t in self.spent if now - t <= window)

    def used(self, now: float) -> tuple[int, int]:
        """Requests in the last minute and in the last day, as of `now`."""
        return self._forget_older_than(now, MINUTE), self._forget_older_than(now, DAY)

    def spend(self, now: float) -> None:
        """Record one request. Called for every attempt, including the ones that fail."""
        self.spent.append(now)
```

**Line by line:**

- `field(default_factory=deque)` and **not** `spent: deque = deque()`. The factory is called **once
  per instance**, so every `Ledger` gets its own list of timestamps and the four per-provider budgets
  in [2.3](../02-two-ceilings/2.3-denominated-in-quota-not-dollars.md) stay four budgets. Writing the
  bare default instead raises at import time — dataclasses refuse any unhashable default — which is a
  friendlier version of the mutable-default trap that
  [23.3.2](../../../day-23-testing-tools-and-callbacks/parts/03-testing-tools/3.2-the-fake-tool-context.md)
  meets in a plain `__init__`, where nothing protects you.
- `now: float` on **every** public method. No `import time` anywhere in the module — grep it and see.
  That absence is the design.
- `MINUTE` and `DAY` are floats in **seconds**, matching `time.time()`, so a caller never has to
  convert anything and no unit mismatch can hide in the arithmetic.
- `spend(now)` takes the time rather than calling for it, for the same reason, and because a caller
  that already knows `now` — because it just checked `refusal(now)` — must use the **same** value for
  both. Two separate clock reads a few milliseconds apart is a small inconsistency, and it is the sort
  that produces a test that fails once a fortnight.
- The docstring on `spend` says *"including the ones that fail"* because that is the rule that is easy
  to get wrong and expensive to get wrong.
  [4.2](../04-failure-lab/4.2-the-counter-that-counted-the-wrong-thing.md) measures the drift.
- `deque` for O(1) removal from the left; a `list` would copy on every `pop(0)`.
- The pruning `while` loop uses `DAY` regardless of the window asked for, which is subtle enough to be
  worth a second look: the list is the **daily** history, and the minute count is a view over it. Prune
  to the minute and the daily count is destroyed.
- `used()` returns both numbers so that a caller wanting to display usage asks once, and so that the
  two ceilings never get collapsed into one concept by accident.

The rolling window is a deliberate choice with a trade-off, and it is worth naming rather than
discovering. Sutra's `DAY` is a **rolling twenty-four hours**, not a calendar day. The provider resets
on its own schedule, in its own timezone, which this code does not know. A rolling window is therefore
**stricter** than the provider: it may refuse a request the provider would have served, shortly after
the provider's reset. That is the safe direction to be wrong in, and the honest alternative — modelling
the provider's reset — requires knowing a fact nobody has captured.

## When it breaks

The failure with an error message is the one you want, and it appears the moment somebody adds a
default:

```text
TypeError: Ledger.refusal() missing 1 required positional argument: 'now'
```

Every call site is forced to supply the time. That is not friction, it is the mechanism: a caller that
has to write `now=` is a caller that has noticed time is an input, and the one place `time.time()` gets
called is visible in a grep.

Try to write the shared `deque` **as a dataclass field** and the language stops you at import time,
which is the pleasant surprise here:

```text
ValueError: mutable default <class 'collections.deque'> for field spent is not allowed: use default_factory
```

Dataclasses reject any default that is unhashable, so `list`, `dict`, `set` and `deque` all raise
rather than being shared. That is a real protection and it is the reason `field(default_factory=deque)`
exists.

**The version that does slip through is a plain class attribute**, and it produces no error at all:

```text
>>> class Ledger:
...     spent = deque()          # class attribute, not per instance
>>> a, b = Ledger(), Ledger()
>>> a.spend(now=0.0)
>>> b.used(now=0.0)
(1, 1)
```

`b` has never been spent from and reports one request used. Every provider's ledger is every other
provider's ledger, the four independent allowances of
[2.3](../02-two-ceilings/2.3-denominated-in-quota-not-dollars.md) become one, and the router built on
top of it exhausts all four at the speed of one. The dataclass version is worth using partly because
it makes this mistake impossible to write.

And the failure that has no symptom at all until it matters: the ledger lives in memory, so it dies with
the process. Restart Sutra and the day's spending is forgotten while the provider's count is not. That
is a real gap, it is the difference between a lab exercise and a system, and it is a `TODO(me)` in the
hub rather than a solved problem — because where the state lives is a decision about your deployment,
not about this module.

## In production

**The ledger moves out of the process.** One counter per process is wrong the moment there are two
processes, and there are always two eventually. The production shape is a shared store — a Redis key
with an expiry, a small table, a sidecar — and the same two-window logic runs against it. The interface
stays exactly the same; the storage does not.

**The clock stays a parameter even then**, and it earns its keep for a second reason: in a distributed
system the question *"which clock"* has a real answer, and it is usually the store's rather than the
caller's. Passing `now` in makes that substitutable. Reading `time.time()` inside the ledger hard-codes
the answer to "whichever machine happened to run this".

**What degrades under concurrency** is the gap between `refusal()` and `spend()`. Two coroutines can
both be told `None` and both send, which over-spends by exactly the number of concurrent workers. The
fix is a single atomic operation — check-and-take, returning a permit or a refusal — and in a shared
store that means one script or one transaction rather than two round trips. It is one of the
`TODO(me)` items, and it is the first thing to fix if Sutra ever runs two requests at once.

**The failure that only appears with real traffic** is memory. A rolling twenty-four-hour window on a
service doing thousands of requests a minute holds millions of timestamps, and the naive `sum(...)`
scan in `used()` walks all of them on every check. At Sutra's scale this is free; at that scale it is a
CPU profile with your budget check at the top of it. The standard answer is not a cleverer list but a
different structure — bucketed counters per second, or the token bucket the
[paper](../../papers/01-the-leaky-bucket.md) describes, which keeps one number instead of a history.

**The review comment a senior engineer leaves:** *"this reads the clock inside the class, so the only
way to test the daily reset is to patch `time.time`. Take `now` as an argument and the test is one
line."*

**The interview question:** *"how would you implement a rate limiter?"* The answer that shows you have
tested one: *"a list of timestamps with the window computed at read time, and — the part people leave
out — the current time passed in rather than read inside. Otherwise every test of the reset behaviour
needs clock patching, so nobody writes them, and the reset is the one path that runs unattended. At
scale the list becomes a token bucket, because holding a day of timestamps to answer one question is
the wrong data structure."*
