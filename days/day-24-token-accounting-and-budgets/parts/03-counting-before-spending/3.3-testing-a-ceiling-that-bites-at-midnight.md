# 3.3 — Testing a ceiling that only bites at midnight

## One-line answer

Eight assertions cover a per-minute window, a per-day window, both of them clearing, and the ordering
between them — and they run in **0.06 seconds** with no key, no network and no sleeping, because every
`now` is a number the test chose.

## The story

The oven has a timer on the front and the first thing you do with a new oven is wind it forward.

You are not baking anything. You turn the dial to two hours, then keep turning until it clicks past
the end, because what you actually want to know is whether the bell works — and waiting two hours to
find out is not a plan, it is a hope.

The alarm goes. Now you know. It cost four seconds and you did it on the day you got the oven rather
than on the day you needed it.

## The idea in plain language

Time-dependent code has a testing problem that is worse than it looks, and the reason is not
technical. It is that the honest test is *inconvenient*, so it does not get written, so the paths that
run rarely are the paths that were never checked.

A daily ceiling's reset runs once a day, unattended, when nobody is watching. It is the most important
behaviour in the module and the least observed. If testing it requires waiting a day, nobody tests it,
and the first time anybody finds out whether it works is in production, at whatever hour the provider
resets.

There are three ways out, and they are not equal.

**Sleep.** Write the test with a shorter window and `time.sleep`. It works for a per-minute ceiling if
you are patient and it cannot work at all for a daily one. It also makes the suite slow, which
[23.6.2](../../../day-23-testing-tools-and-callbacks/parts/06-in-production/6.2-the-suite-that-has-to-stay-fast.md)
shows is how a suite stops being run.

**Patch the clock.** `unittest.mock.patch("time.time")` replaces the function for the duration of the
test. This works, it is common, and it has two costs: the test now depends on *where* the code imports
`time` from, so a refactor breaks tests that have nothing to do with the change; and patching is
global, so anything else running concurrently sees the fake clock too.

**Pass the time in.** The ledger takes `now` as an argument
([3.1](3.1-the-ledger.md)), so the test simply says what time it is. No patching, no sleeping, no
import-path coupling. `ledger.refusal(now=86401.0)` is a question about tomorrow, asked now.

The third is not a trick; it is the design decision from
[3.1](3.1-the-ledger.md) paying for itself, and this part is where the payment arrives. Yesterday's
[23.1.1](../../../day-23-testing-tools-and-callbacks/parts/01-where-the-line-falls/1.1-the-nondeterminism-excuse.md)
named `datetime.now()` inside a business rule as the classic hidden nondeterminism; this is what
avoiding it buys.

## Why Sutra needs it

Because the budget is now load-bearing, and the two behaviours that matter most are the two that are
hardest to observe.

The per-minute ceiling must **clear**, or Sutra stops working sixty seconds into a busy morning and
never restarts. The per-day ceiling must **not** clear after a minute, or Sutra cheerfully retries into
a ceiling that is not moving and spends the remaining allowance discovering it
([4.1](../04-failure-lab/4.1-the-retry-that-spent-the-budget.md)). Those two sentences are the whole
module, and neither of them is visible in a normal run.

And there is one more that only a test can express, because it has no symptom: **which refusal is
reported when both ceilings are breached.** Get that wrong and the system tells the user to wait
fifty-two seconds for something that will still be refused tomorrow morning.

## The mechanism

Eight cases. Every `now` is chosen, and `MINUTE` and `DAY` are imported from the module under test so
the arithmetic in the test matches the arithmetic in the code.

```python
# days/day-24-token-accounting-and-budgets/lab/test_quota_demo.py
import pytest
from quota import DAY, MINUTE, Ceiling, Ledger

FREE = Ceiling(name="gemini-3.7-flash", rpm=5, rpd=20)


@pytest.fixture
def ledger() -> Ledger:
    """A fresh ledger per test: it is mutable, so function scope is the only safe scope."""
    return Ledger(ceiling=FREE)


def test_the_per_minute_ceiling_refuses_the_sixth_request(ledger: Ledger) -> None:
    for i in range(FREE.rpm):
        ledger.spend(now=float(i))
    refusal = ledger.refusal(now=5.0)
    assert refusal is not None
    assert "per minute" in refusal, refusal


def test_the_per_minute_ceiling_clears_on_its_own(ledger: Ledger) -> None:
    for i in range(FREE.rpm):
        ledger.spend(now=float(i))
    assert ledger.refusal(now=MINUTE + 1.0) is None, "a per-minute ceiling must clear with time"


def test_the_per_day_ceiling_does_not_clear_after_a_minute(ledger: Ledger) -> None:
    for i in range(FREE.rpd):
        ledger.spend(now=i * MINUTE)
    assert ledger.refusal(now=FREE.rpd * MINUTE + MINUTE) is not None


def test_the_per_day_ceiling_clears_after_a_day(ledger: Ledger) -> None:
    for i in range(FREE.rpd):
        ledger.spend(now=i * MINUTE)
    assert ledger.refusal(now=DAY + 1.0) is None


def test_the_day_refusal_is_reported_before_the_minute_refusal(ledger: Ledger) -> None:
    """Both ceilings are breached; the message must name the one that will not clear."""
    for i in range(FREE.rpd):
        ledger.spend(now=DAY - 10.0 + i * 0.1)
    refusal = ledger.refusal(now=DAY)
    assert refusal is not None
    assert "per day" in refusal, refusal
```

**Line by line:**

- `from quota import DAY, MINUTE` — the test imports the module's own constants rather than writing
  `86400`. If the module's idea of a day ever changes, the tests follow it instead of silently testing
  a different rule.
- `@pytest.fixture def ledger()` is **function-scoped by default**, and the docstring says why: the
  ledger is mutable, so a shared one would carry one test's spending into the next
  ([23.2.3](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.3-fixtures.md)).
- `range(FREE.rpm)` and `range(FREE.rpd)` rather than `range(5)` and `range(20)`. The loop bounds are
  derived from the ceiling under test, so changing the ceiling changes the tests with it and no
  hard-coded number can drift out of step.
- `now=float(i)` spends five requests in the first five seconds, which is inside one minute — so the
  per-minute ceiling is the one that fires. `now=i * MINUTE` in the daily tests spreads twenty requests
  over twenty minutes, so the per-minute ceiling is *not* breached and the daily one is tested alone.
  **Choosing the spacing is how you choose which ceiling you are testing**, and it is the part that
  takes a moment's thought.
- `assert refusal is not None` before `assert "per minute" in refusal`. Without the first line, a
  ledger that returned `None` would fail with `TypeError: argument of type 'NoneType' is not iterable`
  — true, and a description of the test rather than of the bug.
- `assert "per minute" in refusal, refusal` passes **the refusal itself** as the message, so a failure
  prints the sentence that was produced instead of just saying the substring was absent. That is what
  makes the broken-on-purpose output in [2.1](../02-two-ceilings/2.1-two-ceilings-one-clears.md)
  readable.
- `now=MINUTE + 1.0` is the clearing test, and the `+ 1.0` matters: at exactly `MINUTE` the oldest
  request is `60.0` seconds old and `now - t <= window` is still true, so it still counts. One second
  past is unambiguous, and being deliberate about the boundary is the difference between a test that
  documents behaviour and one that accidentally pins an off-by-one.
- `now=DAY - 10.0 + i * 0.1` in the last test crams all twenty requests into two seconds just before
  the day boundary, so that **both** ceilings are breached at once. That is the only way to test the
  ordering, and it is a state that would be tedious to reach with a real clock and is one arithmetic
  expression here.
- The docstring on that test states the requirement in words — *the message must name the one that will
  not clear* — because the assertion alone (`"per day" in refusal`) does not explain why anybody cares.

- Eight cases, no key, no network, no sleeping. The whole module's time-dependent behaviour, checked.

Measured with `pytest` 9.1.1 on 2026-09-04:


**Six hundredths of a second to verify a daily reset.** Two of those cases simulate a full day passing.
One of them simulates the exact moment when both ceilings are breached simultaneously — a state that
happens perhaps once in the life of a real deployment, at whatever hour the provider resets, with
nobody watching.

## When it breaks

Delete the per-day branch from `refusal()` and two of the eight go red, with the message doing the
work:

```text
>       assert "per day" in refusal, refusal
E       AssertionError: gemini-3.7-flash: 20/5 per minute - 52s
E       assert 'per day' in 'gemini-3.7-flash: 20/5 per minute - 52s'

=========================== short test summary info ===========================
FAILED test_quota_demo.py::test_the_per_day_ceiling_does_not_clear_after_a_minute
FAILED test_quota_demo.py::test_the_day_refusal_is_reported_before_the_minute_refusal
2 failed, 6 passed in 0.13s
```

The other six stay green, which is correct: the per-minute behaviour genuinely still works. A change
that breaks one ceiling should break the tests for that ceiling and no others, and a suite where
everything goes red on any change is testing one thing repeatedly.

The failure the suite **cannot** see is the one worth naming. Every test here calls the ledger
directly. All eight pass in a system where nothing ever calls `refusal()` before sending — where the
budget module is correct, complete, tested, and not wired in. That is exactly
[23.4.3](../../../day-23-testing-tools-and-callbacks/parts/04-testing-hooks/4.3-testing-that-a-hook-returns-none.md)'s
shape of blind spot, and the test that closes it runs one invocation and asserts the ledger moved.

## In production

**Time is injected everywhere it matters, not just here.** Once a codebase has one clock parameter it
tends to grow a convention — a `Clock` protocol with a `now()` method, a real one in production and a
fake one in tests — which is worth adopting when several modules need it and is over-engineering for
one. Sutra has one; a parameter is right.

**Boundaries get their own tests.** The interesting values in a window are not "inside" and "outside"
but exactly-on, one-before and one-after. Most rate-limiter bugs live within one unit of a boundary,
and the way to find them is a parametrized test over those three positions
([23.2.4](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.4-parametrize.md))
rather than a comfortable value in the middle.

**What changes at scale** is that the clock stops being one thing. Distributed rate limiting means
several machines with several clocks, and "now" becomes a question with a wrong answer available —
which is [Day 22](../../../day-22-structured-logging/papers/01-time-clocks-ordering.md)'s paper
arriving in a new context. The production answer is to make the *store's* clock authoritative and pass
it in, which is only possible if `now` was a parameter to begin with.

**The failure that only appears with real traffic** is the timezone. A ledger with a rolling window has
none; a ledger that tries to model the provider's calendar reset has one, and it will be wrong for
somebody. Sutra chose the rolling window partly for this reason
([3.1](3.1-the-ledger.md)) and the choice is worth restating whenever anyone proposes "just reset at
midnight" — midnight where?

**The review comment a senior engineer leaves:** *"there's no test for the day boundary. Add one at
exactly `DAY`, one at `DAY - 1` and one at `DAY + 1` — that's where this kind of bug lives."*

**The interview question:** *"how do you test something that depends on the time?"* The answer that
shows you have done it without ceremony: *"pass the time in. Then a test for the daily reset is one
line and runs in milliseconds, instead of patching the clock globally or sleeping. Patching works but
it couples the test to how the module imports `time`, and it can't run in parallel with anything else
that cares about the clock. And I test the boundary specifically — on it, just before, just after —
because that's where rate limiters break."*
