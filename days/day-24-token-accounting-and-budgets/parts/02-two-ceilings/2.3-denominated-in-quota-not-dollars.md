# 2.3 — Denominated in quota, not dollars

## One-line answer

A budget in money assumes you can buy more, and on a free tier you cannot — so Sutra's budget is
written in **requests per minute and per day, per provider**, and the interesting consequence is that
"spend more" is not an available move, which forces every decision to be about *which* provider and
*whether at all*.

## The story

The phone in your bag is on a prepaid plan and it has minutes on it, not money.

There is a difference, and you find it out on a Sunday when the top-up shop is shut and you are on
hold with somebody's helpline. It is not that you cannot afford more minutes. It is that there is no
mechanism, at that moment, to convert wanting them into having them. The plan is a number that goes
down.

So you behave differently from someone on a monthly bill. You send a message instead of calling. You
ring the landline instead. You decide, before dialling, whether this particular call is worth what it
costs — not in rupees, in minutes, which is a thing you have a fixed number of.

## The idea in plain language

A **budget** is a limit you set on yourself, expressed in whatever unit the thing is measured in. The
unit is not a formatting choice; it decides which options are available to you.

**A budget in money has an escape hatch.** If the number is too small, you raise it. Every decision
becomes a trade between cost and quality, and "spend more" is always on the table — which is why
per-token pricing produces engineering conversations about model tiers and prompt length.

**A budget in quota has no escape hatch.** Twenty requests a day is not a number you can decide to
exceed. There is no field to raise, no card to add. Which removes an entire category of solution and
leaves three:

1. **Use fewer requests** — batch, cache, do not call the model for things that are not model
   problems.
2. **Use a different provider** — the ceiling is per project *and per model*
   ([2.2](2.2-reading-the-ceiling-off-a-refusal.md)), so a second model is a second allowance.
3. **Do the work later** — the daily ceiling clears; the question is whether the user can wait.

That is Principle 15, *zero budget is a feature*, stated as engineering rather than as thrift. A team
with a credit card reaches for option zero — spend more — and never learns the other three. A team
that cannot reach for it builds a router, a cache and a degradation path, and those three things are
what the system needs anyway on the day traffic multiplies.

The practical form of the rule, from Addendum 02: **budgets are denominated in RPM/RPD per provider,
not dollars.** Two numbers, per provider, and the word *provider* is doing as much work as the
numbers.

## Why Sutra needs it

Because Sutra has four providers ([Day 9](../../../day-09-four-free-providers/LESSON.md)) and one of
the things this day builds is the arithmetic that Phase 8's Quota-Router will run on.

The router's decision is not *"which model is best"*. It is *"which model is best **among the ones
that still have requests left**"*, and that question has no meaning without a per-provider ledger. A
single global "requests used today" counter cannot answer it, because the ceilings are independent:
being out on Gemini says nothing about Groq.

It also decides what Sutra can honestly promise. Twenty requests a day, at eight requests per
conversation ([1.2](../01-what-a-request-costs/1.2-charged-again-every-turn.md)), is **two and a half
conversations** on one model. Across four providers with different ceilings it is considerably more —
and working out how much more is arithmetic that has to happen before anybody designs a feature around
it.

## The mechanism

The budget is a table, one row per provider, and every number in it needs a provenance.

| Provider | Model | RPM | RPD | Where the number came from |
| --- | --- | --- | --- | --- |
| Gemini | `gemini-3.7-flash` | `TODO` | **20** | read off a live `429` — `quotaValue: '20'`, 2026-09-04 |
| Groq | open-weight, per Addendum 02 | ≈30 | ≈1000 | **Addendum 02 estimate**, not yet captured from a refusal |
| OpenRouter | any `:free` model | ≈20 | ≈50 | **Addendum 02 estimate**, not yet captured from a refusal |
| Ollama | local | unlimited | unlimited | no provider; bounded by your machine |

**Three things about that table are more important than the numbers in it.**

**Only one cell is a measured fact.** The Gemini RPD is the value the provider itself stated in a
refusal. Everything marked *estimate* came from Addendum 02's planning figures, and the addendum's own
Gemini row says *"a few hundred RPD"* — which the live refusal contradicts with **20**. That is not a
criticism of the addendum; it is what a planning estimate is for. It is a demonstration that
**a captured refusal outranks a written estimate**, and that the difference can be an order of
magnitude.

**The RPM column has a `TODO` in the row we know most about**, and it stays a `TODO` until somebody
captures it. [2.2](2.2-reading-the-ceiling-off-a-refusal.md) carries the exact command. Writing a
plausible number there would make the table look finished and make the router wrong.

**Ollama has no ceiling and is therefore the answer to a different question.** A local model is
unlimited in requests and limited in everything else — quality, speed, the fact that your laptop is
doing it. In budget terms it is the overflow lane, and any router worth building routes to it when the
others are exhausted rather than failing.

Here is the arithmetic that turns that table into a statement about the product:

```python
# days/day-24-token-accounting-and-budgets/lab/quota.py
@dataclass(frozen=True)
class Ceiling:
    """What one provider will serve before it starts refusing. Read off a 429, never guessed."""

    name: str
    rpm: int
    rpd: int
```

**Line by line:**

- One `Ceiling` **per provider-and-model pair**, never one per provider. The refusal's `quotaId` said
  `PerProjectPerModel`, so two models from one provider are two independent allowances and modelling
  them as one would waste half of what you have.
- `name` is the full model string — `gemini-3.7-flash`, not `gemini` — because that is the key the
  provider counts against and the key a log line has to carry to be groupable.
- Still no currency field, and still no token field. The type contains exactly what the provider
  meters, which is the whole of [1.3](../01-what-a-request-costs/1.3-the-unit-that-gets-rationed.md)
  made structural.
- `frozen=True` means a ceiling cannot be edited at runtime. If the provider's limit changes, the
  constant changes and the change appears in `git log` with a date beside it — which is the only way a
  number like this stays trustworthy over ninety-seven days.

And the statement, using the one number that is real: **20 requests per day ÷ 8 requests per
conversation = 2.5 conversations per day on Gemini.** Add the estimated ceilings for Groq and
OpenRouter and it is perhaps a hundred and thirty — enough to develop against, nowhere near enough to
run a support desk, and exactly the constraint that makes every later day's caching, batching and
routing a necessity rather than an optimisation.

## When it breaks

The failure mode of a money-denominated budget on a free tier is that it never fires. A limit of "five
dollars a day" against an API that charges nothing is a check that is always green while the thing you
actually run out of is unguarded. The system stops working, the budget dashboard reads `$0.00 / $5.00`,
and the two facts never meet.

The failure mode of a **single global** quota budget is more interesting, because it fires at the wrong
time. One counter across four providers hits twenty and refuses everything — including Groq, which had
nine hundred and eighty requests left. Nothing errors; the system simply does a fraction of the work it
could have.

And the failure mode of an **estimated** ceiling is the one this part is really warning about. Sutra's
own planning document says Gemini Flash offers *"a few hundred RPD"*. The provider says:

```text
* Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests, limit: 20, model: gemini-3.7-flash
```

A router built on "a few hundred" will cheerfully send the twenty-first request, and the twenty-second,
and every one of them costs a request that was already gone. **An estimate that is high is not a
conservative error; on a per-request tier it is a spend.**

## In production

**Budgets are per tenant as well as per provider.** A production system has a provider ceiling above it
and customers below it, and the interesting limit is usually the one you impose on a customer rather
than the one the provider imposes on you. That is [5.1](../05-in-production/5.1-whose-budget-is-it.md),
and the structure is the same: a ledger, keyed by something, with two numbers.

**Money comes back, and when it does the unit changes.** On a paid tier the meter is per token and the
budget is per month, and every conclusion in this section inverts: prompt length becomes the bill,
compaction becomes a saving, and "spend more" reappears as an option. Code that survives that
transition keeps a **cost function** — one small function that turns a planned request into a number —
and a ledger that merely sums it. Sutra's cost function currently returns `1`.

**What changes at scale** is that the budget acquires a time dimension. A daily ceiling spent evenly is
a working system; the same ceiling spent in the first twenty minutes is an outage for the rest of the
day. Production budgets therefore carry a **pace** as well as a total — a target burn rate, with an
alert when the projection says you will run out before the reset — which is the same arithmetic a
prepaid phone user does without noticing.

**The failure that only appears with real traffic** is the shared project. The `quotaId` said **per
project**, and a project usually has more in it than one service: a batch job, someone's notebook, a
staging environment and a demo all draw on the same twenty. The ledger inside one process is honest
about that process and blind to everything else, which is why the number it reports should always be
described as *"what we spent"* and never as *"what remains"*.

**The review comment a senior engineer leaves:** *"this budget is in dollars and our tier is free.
What does it stop us doing?"*

**The interview question:** *"how do you budget for an LLM on a free tier?"* The answer that shows you
have run out: *"in requests, per provider and per model, because that's what's actually rationed and
because you can't buy more. Money budgets assume an escape hatch that doesn't exist there. The
practical effect is that it forces three specific designs early — batching, a per-provider router, and
a degradation path for when the allowance is gone — and those are the same three things you want later
anyway when traffic grows."*
