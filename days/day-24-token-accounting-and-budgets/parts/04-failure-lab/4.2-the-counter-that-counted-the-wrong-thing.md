# 4.2 — 💥 The counter that counted the wrong thing

## One-line answer

Counting answered questions instead of attempted requests made a day of twelve questions look like
**11 requests used** when the provider had counted **16** — so the system believed **9 remained** when
**4** did, and the ceiling arrived five requests before anybody expected it.

## The story

The shop counts what it sells and does not count what comes back.

At the end of the month the book says four hundred and twenty units. The shelf says something else,
and the gap is a fortnight of returns that were handed over the counter, refunded from the till, and
put back on the shelf without anybody writing a line for them.

Nobody was dishonest. The book records sales, and every entry in it is a real sale. It is just that
"how many did we sell" and "how many are on the shelf" turned out to be different questions, and the
book only ever answered the first one while everybody read it as though it answered the second.

## The idea in plain language

A budget counter has to answer one question: **how much of the allowance is gone?**

The allowance is spent by **requests that reached the provider**. Not by questions asked, not by
answers received, not by successful calls. The provider counts an arrival; whether it then returned an
answer, an error, a refusal or a timeout does not enter into it.

So there are four plausible places to increment a counter and only one of them is right:

| Increment when | Counts | Correct? |
| --- | --- | --- |
| the user asks a question | questions | no — one question can be several requests |
| the request is sent | **requests** | **yes** |
| a response comes back | requests that answered | no — misses errors and timeouts |
| the call succeeds | successes | no — misses errors, timeouts *and* refusals |

The last two are the ones people write, and for an understandable reason: the natural place to put a
counter is beside the code that handles the result, because that is where you already are.

The drift they produce has a specific shape. It is **always in the same direction** — the local count
is lower than the provider's — and it **grows with the failure rate**. On a quiet day when everything
works, the two agree perfectly and the bug is invisible. On a bad day, when timeouts and retries are
frequent, the counter is most wrong exactly when the budget matters most.

And the symptom is not an error. It is a system that runs out of allowance earlier than its own
dashboard says it should, which reads as *"the provider's limits are wrong"* — and gets escalated as
such, which is how an afternoon disappears.

## Why Sutra needs it

Because Sutra now has a retry policy, an error policy and a substitution policy, and each one creates
requests that produce no answer.

Day 21's ladder makes up to three attempts for one question
([4.1](4.1-the-retry-that-spent-the-budget.md)). A tool timeout produces a request that was made and
returned nothing usable. A safety-filtered response is a request with no content. Every one of those is
a real arrival at the provider, charged, and every one of them is invisible to a counter that
increments on success.

And the number Sutra is guarding is twenty. A drift of five is a quarter of the day's allowance
unaccounted for — enough to make [3.2](../03-counting-before-spending/3.2-refusing-before-the-call.md)'s
local check useless, since it will happily approve requests the provider will refuse.

## The mechanism

One working day at the desk, counted two ways.

```python
# days/day-24-token-accounting-and-budgets/lab/counted_the_wrong_thing.py
COUNT_ATTEMPTS = os.environ.get("COUNT_ATTEMPTS", "1") == "1"

# One working day at the desk: some questions answered first time, some retried, one abandoned.
DAY = [
    ("ok", 1),
    ("ok", 1),
    ("timeout then ok", 2),
    ("ok", 1),
    ("ok", 1),
    ("timeout, timeout, then ok", 3),
    ("ok", 1),
    ("ok", 1),
    ("blocked by safety filter", 1),
    ("ok", 1),
    ("timeout then ok", 2),
    ("ok", 1),
]


def main() -> None:
    ledger = Ledger(ceiling=FREE)
    provider_count = 0
    our_count = 0

    for i, (what, attempts) in enumerate(DAY):
        for attempt in range(attempts):
            provider_count += 1  # the provider charges every attempt it received
            if COUNT_ATTEMPTS:
                our_count += 1
                ledger.spend(now=i * 60.0 + attempt)
        if not COUNT_ATTEMPTS and what != "blocked by safety filter":
            our_count += 1  # only the answered questions were counted
            ledger.spend(now=i * 60.0)
```

**Line by line:**

- `DAY` is a list of `(what happened, how many attempts it took)`. Twelve questions, sixteen attempts —
  a failure rate that is unremarkable for a system talking to a network.
- `provider_count += 1` sits **inside** the attempts loop and is incremented unconditionally. It is the
  ground truth in this simulation, and it is placed to mirror where the real provider's meter sits: at
  arrival, before any decision about the outcome.
- The `COUNT_ATTEMPTS` branch is the correct implementation, and note what it does: increments
  **per attempt**, in the same place as `provider_count`. Correct code and ground truth end up looking
  identical, which is the point.
- The `not COUNT_ATTEMPTS` branch increments **once per question**, outside the attempts loop, and
  skips the safety-filtered one entirely — because that question produced no answer, so a
  success-counting implementation would not have counted it. That is not a strawman; it is what
  `if response.ok: used += 1` does.
- `"blocked by safety filter"` is in the list on purpose. It is a request that reached the provider,
  was charged, and returned no usable content — the exact case that a success counter misses and that a
  developer testing on happy paths will never generate.
- The ledger is spent in both branches, so `ledger.used()` reflects whichever counting rule is in force,
  and the two arms can be compared on the ledger's own output rather than on a separate variable.
- `now=i * 60.0 + attempt` keeps every attempt at a distinct timestamp, so nothing is lost to the
  per-minute window and the daily total is exactly the number of `spend` calls.

```bash
cd days/day-24-token-accounting-and-budgets/lab
COUNT_ATTEMPTS=1 uv run python counted_the_wrong_thing.py
COUNT_ATTEMPTS=0 uv run python counted_the_wrong_thing.py
```

**Line by line:**

- `COUNT_ATTEMPTS` is the ablation: `1` counts every attempt, `0` counts answered questions. No key, no
  network, **0** generations.

Measured on 2026-09-04:

```text
COUNT_ATTEMPTS=1
  questions asked            12
  requests the provider saw  16
  requests our ledger says   16
  disagreement               0

  we believe 4 requests remain today
  4 actually remain
  the provider agrees

COUNT_ATTEMPTS=0
  questions asked            12
  requests the provider saw  16
  requests our ledger says   11
  disagreement               5
```

```text
  we believe 9 requests remain today
  4 actually remain
  the provider will refuse before we expect it
```

**Twelve questions cost sixteen requests.** That number is worth sitting with on its own: four extra
requests, a third more than the question count, produced by three retried timeouts. Nothing went
wrong that a support desk would consider unusual.

**The correct counter agrees exactly.** Sixteen and sixteen, disagreement zero, and four remaining is
four remaining.

**The success counter says eleven.** It missed the four retry attempts, because those were failures,
and it missed the safety-filtered question entirely, because that produced no answer. Five requests
gone from the books.

**And the last block is where the cost lands.** *We believe 9 requests remain today. 4 actually
remain.* Every one of those five phantom requests is one that
[3.2](../03-counting-before-spending/3.2-refusing-before-the-call.md)'s local check will wave through,
straight into a provider that refuses it — and on a per-request tier each of those refusals is itself
charged, so the drift makes itself worse.

## When it breaks

There is no error text, which is the whole difficulty. Every number involved is a plausible number and
every increment is in a plausible place.

The nearest thing to a signal is the shape of the disagreement, and it is worth memorising because it
is diagnostic: **the local count is always lower, and the gap grows with the failure rate.** A system
whose local count matches the provider on quiet days and drifts on bad days is not suffering from
flaky provider accounting. It is counting successes.

The way it actually surfaces is a `429` arriving when the local check said there was room:

```text
429 RESOURCE_EXHAUSTED. {'error': {'code': 429, ... 'limit: 20, model: gemini-3.7-flash' ...}}
```

with a dashboard beside it reading `11 / 20`. Two facts that cannot both be true, and the instinct is
to disbelieve the provider — which is exactly backwards.

There is a second, smaller version of this bug that is worth naming because it is even easier to write:
counting **questions** rather than requests. That one is off by the retry factor alone, so it agrees
with the provider on any question that succeeds first time and drifts only under retry — which makes it
correct in every test anybody writes and wrong every afternoon the network is bad.

## In production

**Count at the boundary, in one place.** The increment belongs immediately beside the code that makes
the outbound call — not in the handler, not in the caller, not in three places that must agree. One
wrapper around the client, incrementing before the call returns, is the shape that cannot drift,
because there is nowhere else for a request to be made from.

**Reconcile against the provider.** Local counting is an estimate, however carefully done, because your
process is not the only thing spending
([2.2](../02-two-ceilings/2.2-reading-the-ceiling-off-a-refusal.md): the quota is *per project*). The
mature arrangement compares the local count with the provider's usage dashboard or API on a schedule
and alerts on the divergence — and the divergence itself becomes the interesting metric, because a
sudden gap means somebody else has started spending your allowance.

**What changes at scale** is that the counter and the limiter separate. A counter is for reporting; a
limiter is for enforcement, and the limiter's count has to be atomic and shared while the counter's can
be eventually consistent. Conflating them gives you either a slow limiter or an inaccurate report, and
the version that works has both, deliberately, with different guarantees.

**The failure that only appears with real traffic** is the streaming response. A streamed generation is
one request that returns many chunks over a period, and a counter incremented on completion counts it
late — or, if the stream is abandoned halfway, not at all. The provider counted it at the start. Any
system doing streaming needs the increment at request time for this reason alone.

**The review comment a senior engineer leaves:** *"this increments in the success branch. What happens
to the three attempts a retried question makes, and to the one that gets safety-filtered? Move it next
to the call."*

**The interview question:** *"how do you track API usage against a quota?"* The answer that shows you
have reconciled one: *"count attempts at the point the request leaves, not responses and definitely not
successes — the provider charges for arrival, so retries, timeouts and filtered responses all count.
The tell that you've got it wrong is a local count that matches on good days and drifts on bad ones,
always low. And I reconcile against the provider's own numbers periodically, because my process isn't
the only thing in the project spending the quota."*
