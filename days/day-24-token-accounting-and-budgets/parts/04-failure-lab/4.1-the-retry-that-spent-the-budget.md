# 4.1 — 💥 The retry that spent the budget

## One-line answer

One question arriving after the day's allowance is gone costs **1 request** when the policy reads the
`quotaId` and **3** when it does not — and the three-attempt version is the same code that makes a
system reliable against a per-minute ceiling, which is why the bug looks like good engineering.

## The story

The number is out of service and the recorded message is very polite about it.

You dial. A voice tells you the number you have dialled is not in service. You hang up, because
obviously something went wrong, and you dial again. The same voice says the same thing. You try once
more, slightly slower, pressing each digit deliberately, as though the machine had misheard you.

Three calls. One fact, which was completely available after the first.

And the reason you did it is not stupidity. It is that redialling *works* — for a crossed line, a
network blip, a call that drops halfway. The habit is correct for most failures and wrong for this
one, and nothing about the experience of failing tells you which kind you are in.

## The idea in plain language

Retrying is the standard response to a failed request, and it is usually right. A timeout, a dropped
connection, a momentary overload: try again and it works.

[Day 21](../../../day-21-errors-surface-not-swallow/parts/01-who-hears-it/1.3-retry-substitute-escalate.md)
established the three responses to a failure — retry, substitute, escalate — and that retries run out.
This part is what happens when the wrong one is chosen, measured in the currency of
[1.3](../01-what-a-request-costs/1.3-the-unit-that-gets-rationed.md).

Here is the thing that makes it expensive rather than merely wasteful. On a per-request tier, **the
retry costs the same as the original question.** There is no discount for a request that returned an
error. So a three-attempt retry ladder does not cost "a bit more"; it costs exactly three times as
much, and it spends that on a failure it has already been told about.

And the two ceilings behave in opposite ways under retry
([2.1](../02-two-ceilings/2.1-two-ceilings-one-clears.md)):

- Against a **per-minute** ceiling, retrying with backoff is correct. Capacity is returning; waiting
  and asking again is exactly the right move, and giving up would abandon work that could be done.
- Against a **per-day** ceiling, retrying is worse than useless. Capacity is not returning. Each
  attempt is a request spent to receive the same sentence, and it is spent out of an allowance that is
  already exhausted — so the retries are literally borrowing against tomorrow.

Both arrive as `429 RESOURCE_EXHAUSTED`. The only reliable discriminator is the `quotaId` in the
body — `...PerMinute...` against `...PerDay...` — which
[2.2](../02-two-ceilings/2.2-reading-the-ceiling-off-a-refusal.md) extracts.

This is a failure lab rather than a warning because the two versions of the code differ by one
condition, both look responsible, and only one of them is measured.

## Why Sutra needs it

Because Day 21 already found this, in requests, with a real provider, and this is the part that puts a
ledger under it.

`docs/PACKAGES.md` records the finding: *"28 requests across a quarter of an hour, each obeying the stated
`Please retry in ~53s`, were all refused"*. That is a whole afternoon's allowance spent by a retry
policy behaving exactly as designed, against a ceiling that was never going to move, guided by a
`retryDelay` that sounded like a promise. `ADR-0007` is the decision record.

What was missing then was a ledger that could show the cost as a number. Now there is one.

## The mechanism

The same question, asked after the allowance is gone, with the classifier switched on and off.

```python
# days/day-24-token-accounting-and-budgets/lab/retry_spent_the_budget.py
CLASSIFY = os.environ.get("CLASSIFY", "1") == "1"
MAX_ATTEMPTS = 3


class Refused(RuntimeError):
    """A 429, carrying the metric the provider named - which is how you tell the two apart."""

    def __init__(self, metric: str) -> None:
        super().__init__(f"429 RESOURCE_EXHAUSTED: {metric}")
        self.metric = metric


def provider_call(ledger: Ledger, now: float) -> str:
    """Refuses on either ceiling, and names which one, exactly as the real body does."""
    per_minute, per_day = ledger.used(now)
    ledger.spend(now)
    if per_day >= FREE.rpd:
        raise Refused("GenerateRequestsPerDayPerProjectPerModel-FreeTier")
    if per_minute >= FREE.rpm:
        raise Refused("GenerateRequestsPerMinutePerProjectPerModel-FreeTier")
    return "ok"


def is_retryable(metric: str) -> bool:
    """A per-minute ceiling clears on its own. A per-day one does not (Day 21, 3.1)."""
    return "PerMinute" in metric


def ask(ledger: Ledger, now: float) -> str:
    """One logical question, with however many requests the retry policy decides to spend."""
    for attempt in range(MAX_ATTEMPTS):
        try:
            return provider_call(ledger, now + attempt)
        except Refused as exc:
            if CLASSIFY and not is_retryable(exc.metric):
                print(f"  attempt {attempt + 1}: {exc.metric} -> not retryable, giving up")
                raise
            print(f"  attempt {attempt + 1}: {exc.metric} -> retrying")
    raise RuntimeError(f"gave up after {MAX_ATTEMPTS} attempts")
```

**Line by line:**

- `Refused` carries `.metric` as an attribute, not just in the message text. That is
  [21.1.2](../../../day-21-errors-surface-not-swallow/parts/01-who-hears-it/1.2-an-error-is-a-fact.md)'s
  rule — an error is a fact, not a sentence — and it is the difference between a policy that can ask a
  question and one that has to do string matching on prose.
- `provider_call` spends **before** it raises, again, because that is what the provider does. Every
  line of this script depends on that ordering being right.
- `is_retryable` keys on `"PerMinute" in metric` and not on the HTTP status, because the status is
  `429` in both cases. It is one line, and it is the entire difference this part measures.
- The two ceilings are checked **day first**, matching
  [2.1](../02-two-ceilings/2.1-two-ceilings-one-clears.md): when both are breached, the caller must be
  told about the one that will not clear.
- `raise` with no argument inside the `except` re-raises **the original exception**, preserving its
  traceback and its `.metric`. `raise exc` would work and would restart the traceback; `raise
  Refused(...)` would throw away the original. This is the small form that matters when the exception
  reaches a log line.
- `now + attempt` advances the clock by a second per attempt, so the retries are distinguishable in the
  ledger rather than landing on one timestamp.
- `MAX_ATTEMPTS = 3` is a constant at module level rather than a literal in the loop, because it is the
  number this part is about — and because Day 21's build brief already asked you to derive it from the
  daily budget rather than from taste.

```bash
cd days/day-24-token-accounting-and-budgets/lab
CLASSIFY=1 uv run python retry_spent_the_budget.py
CLASSIFY=0 uv run python retry_spent_the_budget.py
```

**Line by line:**

- `CLASSIFY` is the ablation: `1` reads the `quotaId` before retrying, `0` retries anything. No key, no
  network, **0** generations.

Measured on 2026-09-04:

```text
CLASSIFY=1  (the day's 20 requests are already spent)
one more question arrives:
  attempt 1: GenerateRequestsPerDayPerProjectPerModel-FreeTier -> not retryable, giving up
  result: Refused

  requests before this question: 20
  requests after  this question: 21
  spent on one refusal:          1

CLASSIFY=0  (the day's 20 requests are already spent)
one more question arrives:
  attempt 1: GenerateRequestsPerDayPerProjectPerModel-FreeTier -> retrying
  attempt 2: GenerateRequestsPerDayPerProjectPerModel-FreeTier -> retrying
  attempt 3: GenerateRequestsPerDayPerProjectPerModel-FreeTier -> retrying
  result: RuntimeError

  requests before this question: 20
  requests after  this question: 23
  spent on one refusal:          3
```

**One request against three, for the same question, with the same outcome.**

Both arms end with the caller being told no. Both raise. Nothing about the *result* differs. The only
difference is the last line of each block, and it says that the second arm spent three of the day's
twenty requests to arrive at a fact the first attempt had already stated in full.

Read the attempt lines to see how ordinary the bug looks. In the second arm each line says
`-> retrying`, which is what a well-behaved client does. The policy is not broken; it is applying a
correct rule to the wrong case, and the only thing that could have told it so is the `quotaId` it
never read.

On the free tier three requests is **15% of a day's allowance**, spent on a single refusal. And Day 21
measured the real version rather than the simulated one: **28 requests across a quarter of an hour**,
each obeying the delay the provider suggested, all refused. That is more than a whole day's allowance,
spent by a policy behaving exactly as it was written to.

## When it breaks

The failure in production has no error message of its own, because every individual piece is working.
What it looks like is an allowance that empties faster than the work done can explain.

The real bodies are the ones from
[2.2](../02-two-ceilings/2.2-reading-the-ceiling-off-a-refusal.md), and the tell is in the field the
naive policy never reads:

```text
'quotaId': 'GenerateRequestsPerDayPerProjectPerModel-FreeTier', 'quotaValue': '20'
...
{'@type': 'type.googleapis.com/google.rpc.RetryInfo', 'retryDelay': '26s'}
```

**`retryDelay: '26s'` next to a per-day quota id.** The provider is suggesting a backoff and the naive
policy reads it as a window reset. Day 21 tested that reading directly: twenty-eight requests, each
waiting the suggested delay, all refused. The delay is a hint about how hard to push, not a statement
about when capacity returns, and on the daily ceiling those are entirely different claims.

There is a second, sneakier version. A policy that classifies correctly but **retries the
classification** — catching the refusal, deciding it is not retryable, and then letting an outer
retry loop have a go anyway — spends exactly as much as the naive one. Retry ladders compose, and two
layers of three attempts is nine requests. The defence is to have the budget check
([3.2](../03-counting-before-spending/3.2-refusing-before-the-call.md)) in front of *all* of them, so
that whatever the retry policy decides, the ledger refuses locally and nothing is spent.

## In production

**Retry policy is a budget decision, not just a reliability one.** The number of attempts should be
derived from the allowance and the expected failure rate, not chosen because three feels right. On
twenty requests a day, three attempts means a single failing question can consume fifteen percent of
the day — and Day 21's build brief asked for exactly this arithmetic for exactly this reason.

**Never retry a limit that does not refill.** The general rule, of which the per-day ceiling is one
instance: classify the failure by whether the condition that caused it is *changing*. A timeout,
yes. A per-minute ceiling, yes. A daily quota, an invalid argument, a 400, an authentication failure —
no. Each of those will be identical on the next attempt.

**What changes at scale** is that retries become the load. A dependency slows down, every caller
retries, and the retry traffic is now several times the original traffic arriving at a system that was
already struggling — the retry storm. The standard defences are a **circuit breaker** (stop calling
entirely for a while after N consecutive failures) and **jitter** (randomise the backoff so retries
from many clients do not synchronise). On a quota tier the circuit breaker is even more valuable than
usual, because the thing it protects is not a server's CPU but an allowance you cannot buy more of.

**The failure that only appears with real traffic** is the retry budget shared across many callers.
Each caller's three attempts is reasonable; a hundred callers' three attempts is three hundred
requests against a ceiling of twenty, and the ledger refuses two hundred and eighty of them locally
— which is the correct outcome and looks alarming on a dashboard until you know what you are looking
at.

**The review comment a senior engineer leaves:** *"this retries any 429. Half of those are the daily
ceiling, and on this tier each retry is a real request out of twenty. Classify on the `quotaId` before
deciding."*

**The interview question:** *"when should you not retry?"* The answer that shows you have paid for the
lesson: *"when the condition won't have changed by the next attempt. A daily quota is the obvious one
— it arrives as the same 429 as a per-minute limit, so you have to read the quota id rather than the
status code. We measured it: retrying a daily ceiling three times cost three requests out of twenty and
returned the same sentence each time. And I don't trust the `retryDelay` field on that path; it's a
backoff hint, and obeying it for a quarter of an hour still gets you refused."*
