# 1.3 — Counting what it actually spends

## One-line answer

Phase 11 commits **62 requests a day** to a lane this repository has observed holding **20**, and
**60 a day** to a lane nobody has measured at all — and the second of those two numbers is the more
serious finding, because a plan against an unknown allowance is not a plan.

## The story

The electricity bill arrives and it is larger than usual. Not enormous, just wrong-feeling.

The first instinct is to guess. Somebody says it must be the air conditioner. Somebody else says the
new geyser. Somebody says the meter is faulty. Everyone is confident, nobody is checking, and the
argument could run all evening because there is nothing in it that can be settled.

Then somebody turns the bill over. On the back is the itemised part: the previous reading, this
reading, the difference, the units, the slab rate for each band, and the total. It takes two minutes
to read and it ends the argument — not because it agrees with anyone, but because it is a *count*
rather than an opinion. Sometimes it says the air conditioner. Sometimes it says a lot of small
things nobody suspected. Once in a while it says the previous reading was an estimate and this bill
is two months of a normal amount.

The useful habit is not being right about the geyser. It is turning the bill over.

## The idea in plain language

Part [1.2](1.2-a-schedule-is-a-spending-plan.md) said a schedule is a spending plan. This part turns
Phase 11's plan over and reads the itemised side.

Three words first, because the count is meaningless without them.

- **Demand** is what the schedule commits to: the sum of every job's `cost × runs per day`, per lane.
  It is arithmetic over the plan and it is always knowable.
- **Allowance** is what the provider will actually give you in the window. It is a fact about
  somebody else's system and it is **only knowable if somebody looked it up or measured it**.
- A **verdict** is the comparison, and it has **three** possible values, not two: *fits*, *over*, and
  **cannot say**.

That third verdict is the one this part is really about, and it is not a cop-out. Day 74's
free-quota check reached the same shape from the other side and
[part 4.2 of that day](../../../day-74-live-api-streaming/parts/04-the-bill-for-voice/4.2-the-free-quota-check.md)
put it plainly: a check has three outcomes — free, not free, and could not determine — and writing the
third one down honestly is worth more than a confident guess at the first.

Here it costs more than honesty points. If a scheduler treats *cannot say* as *fits*, it will happily
plan sixty requests a night against a number nobody has ever seen, and it will look exactly as
confident doing that as it does when the number is real. The output will be indistinguishable. That
is the failure this part exists to make visible, and part
[4.4](../04-the-gate/4.4-criterion-3-the-phase-fits.md) turns it into a gate criterion whose exit code
is `2` rather than `0` or `1`.

## Why Sutra needs it

Because the phase gate's sentence is *"nightly job + voice standup within free quota"*, and until this
count exists there is no number to hold that sentence against. A gate criterion that cannot be
computed is not a strict criterion, it is a sentence in a document.

It is also the input to everything in section 2. You cannot ask "can I afford this run?" — part
[2.1](../02-asking-before-spending/2.1-ask-before-you-spend.md) — until there is an allowance to ask
against, and you cannot argue about which job gets refused — part
[2.4](../02-asking-before-spending/2.4-the-job-that-ran-anyway.md) — until you know the schedule is
over.

And it is what Day 82 will inherit. Addendum 02 tells days 79–83 to keep dev evalsets to 10–15 cases
and run the full 60 only at phase gates, on the nightly. Every one of those numbers is a spending
decision that only makes sense against this count.

## The paper behind it

> **Scheduling Algorithms for Multiprogramming in a Hard-Real-Time Environment**
> Journal of the ACM 20(1), 1973, pp. 46–61 · `doi:10.1145/321738.321743`
> <https://doi.org/10.1145/321738.321743>

It showed that a set of jobs, each with a fixed cost and a fixed period, can be checked against a
shared resource by one number — the sum of `cost ÷ period` — before any of them is run.

Taught in this day's paper part: [Does it fit? — the 1973 utilisation test](../../papers/01-schedulability.md).

## The mechanism

The count is `spend.py`, and its verdict function is four lines:

```python
def verdict(lane: tuple[str, str]) -> str:
    allowance = ALLOWANCE.get(lane)
    if allowance is None:
        return UNKNOWN
    return FITS if demand(lane) <= allowance else OVER
```

**Line by line:**

- `ALLOWANCE.get(lane)` returns `None` for a lane nobody has measured. That `None` is a **deliberate
  value**, not an oversight: `_phase.py` writes `("gemini", "gemini-2.5-flash-lite"): None` out in
  full rather than leaving the key out, so the absence of a number is itself recorded. A missing key
  and a key set to `None` are the same to `.get()` and completely different to a reader.
- The `None` branch comes **first**, before any comparison. Reversing those two lines is the entire
  bug this part warns about: `demand(lane) <= allowance` with `allowance = None` raises a
  `TypeError` in Python, which is at least loud — but the version people actually write is
  `allowance or 1000`, which is silent and reports *fits*.
- `demand(lane) <= allowance` uses `<=` and not `<`. Spending exactly the allowance is inside it; the
  refusal starts at one more.
- Three return values, not a boolean. A function returning `True`/`False` here would have to encode
  "I don't know" as one of them, and whichever one it picked would be wrong half the time.

The allowance table itself is the other half, and it carries its sources:

```python
ALLOWANCE: dict[tuple[str, str], int | None] = {
    ("gemini", "gemini-3.7-flash"): 20,
    ("gemini", "gemini-2.5-flash-lite"): None,
    ("groq", "groq/compound"): 250,
}

ALLOWANCE_SOURCE: dict[tuple[str, str], str] = {
    ("gemini", "gemini-3.7-flash"): "read off a live 429, 2026-08-25 (docs/PACKAGES.md)",
    ("gemini", "gemini-2.5-flash-lite"): "not published without an AI Studio session; not measured",
    ("groq", "groq/compound"): "observed 2026-09-05, day 65 §8",
}
```

**Line by line:**

- `int | None` in the annotation is doing real work. It tells a reader — and a type checker, when
  this repository adopts one — that every consumer must handle the missing case. A `dict[..., int]`
  with a hole in it would type-check and then crash.
- `20` for `gemini-3.7-flash` is **not from a table**. No public table publishes it. It was read off a
  live 429 on 2026-08-25 and recorded in `docs/PACKAGES.md` the same day, which is what Principle 7
  asks for when a number cannot be looked up: observe it, date it, write it down.
- `None` for Flash-Lite is the honest entry. Both pages that would answer it were fetched on
  2026-09-06 while writing this day — `ai.google.dev/gemini-api/docs/rate-limits` says limits *"can be
  viewed in Google AI Studio"* and publishes no free-tier table, and `console.groq.com/docs/rate-limits`
  says the same about its own numbers. Neither refused to load. Both simply do not put the answer
  anywhere a script can read it.
- `ALLOWANCE_SOURCE` is a **second dictionary rather than a tuple in the first**. Keeping them apart
  means the arithmetic can never accidentally depend on the prose, and it means a reader scanning for
  numbers is not wading through sentences. The cost is that the two can drift; the check is that
  `spend.py` prints every source it used, so a lane with a number and no story shows up immediately.

Run it:

```bash
cd days/day-78-inside-free-quota/lab
uv run python spend.py; echo "exit: $?"
```

**Line by line:**

- `echo "exit: $?"` because the exit code is the point. This script is a criterion in waiting: `0`
  fits, `1` over, `2` cannot say, and part [4.4](../04-the-gate/4.4-criterion-3-the-phase-fits.md)
  runs the same logic under `gate.py`.

Measured on 2026-09-06:

```text
  lane                         demand/day  allowance/day  verdict
  gemini/gemini-3.7-flash              62             20  over
  gemini/gemini-2.5-flash-lite         60        unknown  cannot say

  where the allowances came from:
  gemini/gemini-3.7-flash       read off a live 429, 2026-08-25 (docs/PACKAGES.md)
  gemini/gemini-2.5-flash-lite  not published without an AI Studio session; not measured

  exit 2
exit: 2
```

**Read the two rows differently, because they are two different problems.**

The first row is a **budgeting** problem and it is solvable with arithmetic. 62 against 20 is over by
42, and every option for fixing it is a decision somebody can make this afternoon: run the desk on a
different model, cut the re-index to changed tickets only, move the digest into the evals stage. It is
uncomfortable and it is tractable.

The second row is a **knowledge** problem, and no amount of arithmetic touches it. 60 requests a night
are committed to a lane whose limit nobody in this repository has ever seen. It might be 1,500 and
completely fine. It might be 50 and the eval stage fails every night in three weeks' time when the
suite grows. The plan cannot tell you which, and — this is the part worth being uncomfortable about —
**the plan has been unable to tell you since Day 73**, silently, because nobody asked it.

Where the 62 comes from, itemised:

| Job | Runs/day | Requests/run | Requests/day | Basis |
| --- | --- | --- | --- | --- |
| `triage` | 12 | 4 | 48 | the daytime desk, 12 tickets a day in Day 73's fixture |
| `reindex` | 1 | 12 | 12 | one embedding request per changed ticket |
| `digest` | 1 | 1 | 1 | one summarising request over `evals.json` |
| `standup` | 1 | 1 | 1 | one request per morning to word Day 77's `lines()` |
| **total** | | | **62** | against an observed allowance of 20 |

The daytime desk is **77% of the bill**, and it is not the job anybody would have suspected. The
nightly feels expensive because it is the thing this phase built; the desk feels free because it was
built in Phase 8 and nobody has thought about it since. Turning the bill over is what tells you that.

## When it breaks

Ask this count for something it cannot give and it answers confidently anyway. Two specific ways.

**The count is over a day, and a day is not a window.** Every number on this page is a
requests-per-day figure, and Phase 11's jobs are spread across a day, so the arithmetic is honest. Put
all 62 requests in the same minute and the schedule is still 62 a day and will still be refused — by
the *rate* limit, from part [1.1](1.1-an-allowance-not-a-speed-limit.md), which this count says
nothing at all about. `spend.py --rpm` prints the other pricing and the two must be read together.

**The costs are per-run constants, and a real cost is a function of the data.** `reindex` is priced at
12 because Day 73's fixture has 12 changed tickets. Nothing in `_phase.py` knows that this number is a
count of something that grows. Run the real system against a thousand tickets and the plan still says
12, with no error and no warning, because the plan is a fixture and the fixture does not move.

There is no traceback for either. That is what makes them worth naming: the observable behaviour of a
count that is wrong in these two ways is **exactly** the observable behaviour of a count that is
right. Compare with what the provider says when the plan turns out to be wrong, which is Day 2's
recorded refusal:

```text
429 RESOURCE_EXHAUSTED
generativelanguage.googleapis.com/generate_content_free_tier_requests
Please retry in ~53s
```

That message arrives at 00:31 in a log nobody reads, and it does not mention the schedule.

## In production

**What a professional writes instead of a fixture.** The costs come from **last night's run log**, not
from a constant. Day 73 already writes `state/runs.jsonl` with a line per run; the small change is to
put a request count in that line and have the planner read the last N runs. The plan then reports two
numbers side by side — planned and observed — and the day they diverge is the day something changed
that nobody committed.

**What degrades at scale.** Estimated costs are optimistic in a very specific, systematic way: they are
written on the day the job is written, against the smallest realistic input, by the person most
familiar with the happy path. They omit retries, they omit the second call the summariser makes when
the first response is too long, and they omit the requests spent on runs that failed and were re-run.
The gap between the estimate and the bill is not random; it grows.

**The failure that only shows with real traffic.** Two jobs whose costs are individually fine, whose
inputs are the *same growing thing*. The re-index and the evals both scale with the corpus, so the
plan has one number that moves and the schedule has two, and the demand grows faster than anybody's
mental model of it. Nothing in a per-job estimate can show that, because the correlation is between
jobs.

**The review comment a senior engineer leaves:** *"Two things. First: this reports 'cannot say' for
Flash-Lite and then exits 2, which is good — please make sure whatever consumes it does not collapse 2
into 'not zero, so it failed'. 'We don't know' and 'we're over' need different follow-up actions and
different people. Second: 48 of the 62 requests are the daytime desk, and that job has no owner in this
table. Before we optimise the nightly, somebody should ask whether four requests per ticket is still
four."*

**The interview question:** *"You have a scheduled job and no published rate limit for the model it
uses. What do you do?"* The answer that shows experience does not start with an estimate. It says:
measure it once, deliberately, in a controlled burn — send requests until you are refused, record the
number and the date, and cache it — and then admits the honest limitation, which is that the number is
per project and somebody else's usage will move it, so the measurement needs re-taking and the system
needs to behave sanely when it turns out to be wrong.
