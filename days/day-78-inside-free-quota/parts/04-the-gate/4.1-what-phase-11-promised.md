# 4.1 — What Phase 11 promised

## One-line answer

The gate sentence — *"nightly job + voice standup within free quota"* — is not one promise but three,
and reading it as three is what turns a phrase in a plan into five commands with exit codes.

## The story

Getting a vehicle through its fitness check.

You arrive expecting a general opinion. Somebody will look at the vehicle, form a view, and either
approve it or not. That is not what happens. What happens is that a man with a clipboard goes down a
list, and each line on the list is a specific thing done in a specific way: the brakes are tested on a
machine that measures the stopping force on each wheel, the headlights are aimed at a board with a
marked target, the emissions probe goes in the exhaust and a number comes out.

He is not deciding whether the vehicle is good. He is asking a fixed set of questions that each have a
measurable answer, and the certificate at the end is nothing more than "every one of these came back
within limits."

The first time you watch this, the surprising part is what he does **not** look at. He does not
comment on the paintwork, or the noise the door makes, or the fact that the seat is torn. Not because
those do not matter, but because they are not on the list, and a check that is a list can be repeated
next year by a different man and give the same answer.

## The idea in plain language

A **phase gate** is the point where a phase's claim gets tested rather than asserted. Sutra's plan
gives each of its sixteen phases a one-line gate, and Phase 11's is:

> **Nightly job + voice standup within free quota**

Twelve words. Read casually, it is a summary. Read the way the man with the clipboard reads, it is
three separate claims joined by two conjunctions, and each one needs its own test:

1. **"nightly job"** — there is an ambient job that runs on a schedule, completes, and behaves
   sensibly when it does not. Days 73 built it. Criterion 1.
2. **"voice standup"** — there is a spoken report delivered over a live session that a listener can
   interrupt. Days 75, 76 and 77 built it. Criterion 2.
3. **"within free quota"** — the whole of it fits inside what the providers give away. Nothing before
   today tested this. Criterion 3.

Two more criteria are not in the sentence and belong to every gate in the plan, from §15:

4. **the freshness check** — did the world move under our pins while we were building? Criterion 4.
5. **no open IDs, every day written** — the plan and the disk still agree. Criterion 5.

The move from a sentence to five commands is the whole method, and
[Day 65 part 1.2](../../../day-65-kill-it-mid-run/parts/01-drill-not-review/1.2-a-criterion-ends-in-an-exit-code.md)
argued why it is not pedantry: a criterion that ends in an exit code is a thing two people cannot
disagree about, and a criterion that ends in a judgement is a thing two people will.

There is one thing worth saying before the criteria start, because a gate day invites the wrong
feeling. **A green gate is not the goal.** A gate is an attempt to find something, and one that finds
nothing has either genuinely finished a phase or failed to look. Today's finds three things, and the
three findings are the useful output of the day.

## Why Sutra needs it

Because Phase 11 is over, and "over" has to mean something more than "the days are written". Six days
built an ambient job, a streaming architecture, a bidirectional voice loop, VAD configuration, a
non-blocking tool layer and a standup agent. Each day ended green on its own terms. None of them ran
the *others*, and none of them added up the bill.

Phase 12 starts tomorrow and inherits all of it: Day 82 will put the eval suite on Day 73's nightly,
which means Day 82 is about to add the largest single line to a spending plan that part
[1.3](../01-the-allowance/1.3-counting-what-it-actually-spends.md) has already shown is over budget.
Whatever is wrong here does not stay here.

## The mechanism

The gate is a list, and the list is data:

```python
@dataclass(frozen=True)
class Criterion:
    label: str
    script: str
    fault: str | None = None


CRITERIA = (
    Criterion("1  the nightly runs, dies honestly and resumes", "c1_nightly.py", "--break-it"),
    Criterion("2  the voice standup delivers and can be stopped", "c2_voice.py", "--break-it"),
    Criterion("3  the phase fits a free-tier allowance", "c3_quota.py", "--assume-generous"),
    Criterion("4  the pins still have ledger rows", "c4_fresh.py"),
    Criterion("5  every day written, no ID left open", "c5_written.py"),
)
```

**Line by line:**

- `label` is a sentence a person can read in a verdict table, and `script` is a file that can be run on
  its own. Both are needed: the label is what goes in the ledger row, the script is what somebody runs
  next quarter without reading any of this.
- Each criterion is **one file**. That is what makes the list appendable — Phase 12's gate adds a row
  and a file, and does not touch the other four — and it is what lets a failing criterion be re-run in
  isolation while you fix it.
- `fault` is the flag that **injects the failure this criterion exists to catch**. It is optional
  because two of the five are already failing today and have therefore proved they can. Part
  [4.7](4.7-the-verdict.md) explains why a criterion with no demonstrated red is not yet a criterion.
- The tuple is ordered and the order is meaningful — the two criteria about the running system come
  first, then the budget, then the two about the repository — but nothing depends on it. Every
  criterion runs regardless of what the ones before it did, which is the next point.

```python
def main() -> int:
    results: list[tuple[Criterion, int]] = []
    for criterion in CRITERIA:
        print(f"\n=== criterion {criterion.label}")
        results.append((criterion, run(criterion.script)))
```

**Line by line:**

- No early exit and no `break`. A gate that stops at the first failure finds one thing per run, so
  fixing that one thing reveals the next one, and a gate that takes five rounds to enumerate five
  findings will be abandoned after two.
- The result is collected as a `(criterion, code)` pair rather than a boolean, because part
  [4.4](4.4-criterion-3-the-phase-fits.md) has a criterion whose answer is neither pass nor fail, and
  collapsing exit codes to `bool` at collection time would throw that away before anybody could report
  it.

## When it breaks

The way a gate breaks is not a traceback. It is a criterion that has quietly stopped checking anything,
and it produces this:

```text
  PASS              2  the voice standup delivers and can be stopped
```

— from a criterion that would print exactly the same line if the standup had been deleted. A check
that cannot fail is indistinguishable, in the verdict table, from a check that passed.

That is why `gate.py` runs a second pass after the criteria. Every criterion that came back green is
re-run with its `fault` flag, and the gate requires the answer to change:

```text
=== the red-alarm test: a criterion that passed must be able to fail
  c1_nightly.py   --break-it          0 -> 1  goes red
  c2_voice.py     --break-it          0 -> 1  goes red
```

A criterion whose fault-injected run also exits 0 is reported as `BLIND`, and a blind criterion fails
the gate exactly as a red one does. Principle 11 says evals are tests; this is the part of the gate
that tests the tests.

## In production

**What a professional writes instead of a phrase in a plan.** Acceptance criteria written **before**
the work, in the form of commands, with the expected exit code beside each. Writing them first is not
process ceremony — it is the only way to be sure the criterion is not shaped around what the
implementation happens to do, which is what happens when you write it afterwards while looking at the
code.

**What degrades over time.** Criteria rot in one direction: they get weaker. A criterion fails, somebody
is under pressure, and the smallest change that makes it pass is to narrow what it asks. Each narrowing
is defensible on the day. After four of them the criterion is green and means nothing, and there is no
commit anywhere that says "we reduced what this checks". The defence is the red-alarm test above,
because a criterion narrowed far enough eventually stops being able to fail at all.

**The failure that only shows with real traffic.** Gates test the system in a state nobody else ever
puts it in: quiet, alone, at a known moment. A criterion that runs the nightly on an idle machine with
the whole allowance available is not testing the thing that will break, which is the nightly at 00:30
after a busy day. Criterion 3 exists precisely because a criterion that only runs the code does not
check the conditions the code will run under.

**The review comment a senior engineer leaves:** *"Five criteria is a good number. Two questions. Can
each one be run alone, by somebody who has not read the day document — because that is the only version
that survives to next quarter. And for each one, show me the run where it fails. A criterion nobody has
seen go red is a criterion nobody has tested."*

**The interview question:** *"How do you know a phase of work is actually finished?"* The answer that
shows experience turns the vague claim into a fixed set of checks that a colleague could re-run, and
then admits the uncomfortable half: says what the checks do **not** cover, because a list of criteria
is also a list of everything you have decided not to look at.
