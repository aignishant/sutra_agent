# 4.5 — Criterion 4 — the freshness check

## One-line answer

Every pinned package must have a dated row saying where its version came from, and `mcp==1.29.1` still
does not — a finding this repository's gates have now reported **four times** without it being fixed,
which is a fact about the process rather than about the package.

## The story

The medicine box in the cupboard.

Somebody has a headache and you go and look. There is a strip of tablets, half used, and it is
obviously the right kind. You press one out and hand it over.

The date on the strip is on the back, in small grey print, and you did not turn it over.

The thing about medicine that has quietly gone out of date is that it does not look any different. The
tablet is the same colour and the same shape. Nothing about the moment of handing it over feels
different from any other time. If it does nothing, you will not connect the two — you will think it
was a bad headache.

The habit that fixes this is not being suspicious of the box. It is turning it over. And it is a habit
precisely because there is no moment at which the box asks you to.

## The idea in plain language

A **freshness check** asks whether the world moved while you were building against it. Plan §15 makes
it part of every phase gate and lists four questions:

- did `google-adk` release something with a breaking change?
- did the MCP specification revision change?
- did any provider's free limits move, or did a pinned model lose its free tier?
- did the skills or registry ecosystem shift enough to invalidate a provenance row?

All four need the network, and a gate criterion that needs the network is a criterion that fails on a
train. So this one splits the work in two, and the split is the design:

**The half that can be checked offline is checked, and its failure is a real failure.** Every package
pinned in `pyproject.toml` must have a row in `docs/PACKAGES.md`. That is Principle 7 made
mechanical — *never invent a version number; every pin gets a dated row* — and it needs no network at
all, because both files are in the repository.

**The half that needs the network is printed as questions with the exact command that answers each.**
Not skipped, not assumed, not marked "manual". Printed, with the command, so that the person running
the gate either runs them or knowingly does not.

That second half is worth defending, because printing a question and calling it a check looks like
cheating. It is not, for one reason: **an unasked question is not a pass**. The alternative designs are
worse. Silently skipping the network questions produces a green gate that has not looked. Failing the
gate because there is no network produces a criterion people disable. Printing the commands makes the
unanswered part visible in the gate's own output, where it is uncomfortable, which is where it belongs.

## Why Sutra needs it

Because six days of Phase 11 were written against `google-adk==2.7.1`, and the freshness question for
this phase is not academic. On 2026-09-06, `pypi.org/pypi/google-adk/json` reported `2.8.0` as the
latest release. This repository pins `2.7.1`. That gap was recorded at Day 65's gate as a finding and
**not** acted on, which is the correct behaviour under Principle 14 — an ecosystem shift is amended in
the plan first, not silently adopted — but it only stays correct if somebody keeps looking.

And because the offline half has found something real and keeps finding it.

## The mechanism

Two small readers and a comparison:

```python
def pins() -> list[tuple[str, str]]:
    text = PYPROJECT.read_text(encoding="utf-8")
    return re.findall(r'"([a-z0-9\-]+)==([^"]+)"', text)


def ledger_packages() -> set[str]:
    rows = [r for r in PACKAGES.read_text(encoding="utf-8").splitlines() if r.startswith("|")]
    return {r.split("|")[1].strip() for r in rows[2:]}
```

**Line by line:**

- `pins()` reads `pyproject.toml` with a regular expression rather than a TOML parser. That is a
  deliberate trade for a gate script: it catches `dependencies` and `[dependency-groups]` in one pass
  without knowing the file's schema, and it will keep working if the schema moves. What it gives up is
  precision — a `==` inside a comment would match — and the check that keeps it honest is that a false
  positive shows up immediately as a package with no ledger row, which somebody then investigates.
- `[^"]+` for the version rather than a version-shaped pattern, because a pin may carry a local
  segment, a build tag or a marker, and a criterion that silently skips the unusual pins is checking
  the easy ones.
- `rows[2:]` drops the ledger's header row and its `| --- |` separator. Two lines, hard-coded, which is
  the kind of thing that breaks quietly if somebody reformats `PACKAGES.md` — and breaks in the safe
  direction, since a dropped real row shows as a missing ledger entry rather than a spurious pass.
- `ledger_packages()` returns a **set of names**, not versions. The criterion asks "is this package
  written down at all", not "does the ledger agree with the pin". The stricter check is the right one
  eventually and is in the build brief; the looser one is here because it is the one that finds
  something today.

And the questions the file cannot answer:

```python
ONLINE_QUESTIONS = [
    ("google-adk release notes", "curl -s https://pypi.org/pypi/google-adk/json | head -c 200"),
    (
        "MCP spec revision",
        "curl -s https://modelcontextprotocol.io/specification/ | grep -o '20..-..-..'",
    ),
    ("Gemini free-tier limits", "open https://ai.google.dev/gemini-api/docs/rate-limits"),
]
```

**Line by line:**

- Each entry is a question **and the command that answers it**, together. A checklist item that says
  "check the ADK release notes" gets skipped; one that hands you a command to paste gets run.
- The third is `open` rather than `curl`, because part
  [4.4](4.4-criterion-3-the-phase-fits.md) established that this page does not put its numbers anywhere
  a script can read. Writing `curl` there would be pretending. The command a human must run is the
  honest one to print.

The three online questions were run by hand on 2026-09-06 while this day was written, and the answers
are in the hub's §8: `google-adk` latest is `2.8.0` against this repository's `2.7.1`, the MCP
specification revision is `2026-07-28` and unchanged, and neither provider publishes its free-tier
numbers without a signed-in session.

**`mcp 1.29.1 NO LEDGER ROW` is the finding, and its age is the interesting part.** That package is
pinned transitively through `google-adk`, which declares `mcp<2,>=1.24`, so nobody chose `1.29.1`
deliberately — a resolver did, on some afternoon, and `uv` wrote it into `pyproject.toml`. Day 52's
gate reported the missing row. Day 59's gate reported it. Day 65's gate reported it and its §11 printed
the exact row to paste. This gate reports it.

Four gates. The fix is one line in a file. That gap is not about the package.

## When it breaks

The criterion itself has a failure mode and it is the mirror image of the one it catches: **a ledger row
that exists and is wrong**. `ledger_packages()` compares names only, so a row saying
`google-adk | 2.6.3 | 2026-08-12` satisfies this check while the pin says `2.7.1`. The criterion goes
green on a ledger that disagrees with the repository.

You can see it by editing a version in `docs/PACKAGES.md` and re-running: nothing changes. Nothing is
printed. There is no error text for this at all, which is why it is named here rather than left as an
exercise — the honest statement of what this criterion checks is *"every pin is mentioned"*, and
anybody reading `criterion 4: PASS` will read it as *"every pin is recorded correctly"*.

The smallest fix is to compare the pair rather than the name:

```python
def ledger_pins() -> set[tuple[str, str]]:
    rows = [r for r in PACKAGES.read_text(encoding="utf-8").splitlines() if r.startswith("|")]
    return {(r.split("|")[1].strip(), r.split("|")[2].strip()) for r in rows[2:]}
```

**Line by line:**

- Returns `(name, version)` pairs, so a row whose version has drifted from the pin no longer satisfies
  the check.
- It needs care that the loose version does not: `PACKAGES.md` is **append-only**, so a package
  upgraded twice has three rows and only the newest should count. A set of pairs handles that correctly
  by accident — the current pin matches its own row — but a reader should know why, which is that the
  older rows are simply pairs that nothing asks about.

## In production

**What a professional writes instead.** The dependency file *is* the ledger, and provenance lives in
the lock file — which records not just versions but hashes and where each came from. `uv.lock` is
committed in this repository for exactly that reason. `PACKAGES.md` earns its place by holding the one
thing a lock file cannot: **why**, in a sentence, on a date. The reason a human-written ledger survives
alongside a machine-written one is that "we pinned 1.62.0 rather than the sample's 1.52.0, deliberately,
on this date" is not derivable from any tool.

**What degrades at scale.** Transitive pins outnumber direct ones by an order of magnitude, and nobody
writes a row for four hundred packages. The rule has to be scoped: direct dependencies get a row, plus
any transitive one that a day document actually names or a lesson depends on the behaviour of — which
is precisely the case `mcp` is in, since Phase 5 taught against its behaviour.

**The failure that only shows with real traffic.** A freshness check run at gates is run rarely, which
means a breaking upstream release can sit undetected for a whole phase. Real projects move the
mechanical half into CI — a scheduled job that opens a pull request when a pin is behind — and keep the
gate for the judgement half: whether the change matters, and whether the plan needs amending before the
code does.

**The review comment a senior engineer leaves:** *"This has been reported at four gates now, so stop
reporting it. Either fix it or record it as accepted with a reason and an expiry, and have the criterion
respect that. A finding that recurs and is never actioned trains everybody to skim the gate output,
which costs you the next finding — the one that matters."*

**The interview question:** *"How do you know your dependencies are still the right versions six months
after you pinned them?"* The answer that shows experience separates two questions — *is there a newer
version* (a machine answers this, continuously) and *should we take it* (a person answers this, at a
decision point) — and then names the artefact where the second answer is written down, because a
decision that is not recorded gets re-litigated every time somebody notices the gap.
