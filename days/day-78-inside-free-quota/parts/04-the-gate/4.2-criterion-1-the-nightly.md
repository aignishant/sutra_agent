# 4.2 — Criterion 1 — the nightly runs, dies honestly and resumes

## One-line answer

The criterion is not "the nightly works" but three separate assertions in one command — a clean run
produces all three artefacts, a killed run keeps exactly one and says where it died, and a resume
finishes — and the middle one is the only one that could not be faked.

## The story

The night watchman's register in the guardhouse of a building.

There is a book on the desk with the rounds written in it: 11pm, 1am, 3am, 5am, and a column for a
signature. The watchman signs each one as he does it. In the morning somebody glances at the book.

Four signatures means four rounds happened. Nobody thinks about this — it is a book with four ticks
in it and everything is fine.

What makes the book worth anything is what happens on the night it is *not* four. Suppose the 3am
round is blank. That blank is now the most informative thing in the building: it says somebody was
here at 1am, and something happened between 1am and 3am. If instead the watchman had gone home at
midnight and signed all four before leaving, the book would look identical to a perfect night, and it
would be worth nothing at all — not just on that night, but on every night, because you could never
again treat four signatures as evidence.

The value of the register is entirely in whether it is capable of showing a gap.

## The idea in plain language

Criterion 1 asks whether Day 73's ambient job is really an ambient job. Three checks, and they are
deliberately not the same check three times.

**A clean run finishes.** Run it from an empty state directory; expect exit `0` and all three
artefacts — `index.json`, `evals.json`, `digest.md`. This is the weakest of the three and the easiest
to satisfy. Almost anything passes it.

**A killed run keeps exactly what it earned and says where it stopped.** Kill it in the eval stage;
expect exit `1`, exactly `['index.json']` on disk, and `"died_at": "evals"` in the run log. This is the
watchman's blank line. It is the only one of the three that a broken system cannot accidentally pass,
because passing it requires the job to be *incomplete in a specific way* rather than complete.

**A resume finishes what the death left.** Run again with `--resume`; expect exit `0` and all three
artefacts. This tests that the leftover is **progress** rather than mess —
[Day 73 part 2.1](../../../day-73-ambient-agents/parts/02-when-it-dies-at-three-am/2.1-the-run-that-dies.md)
made exactly that argument, and this is the assertion that keeps it true.

The word that ties the three together is **honestly**. A job that dies and exits `0` has lied. A job
that dies and leaves all three artefacts has lied in a worse way, because the next thing to read them
cannot tell. And a job that dies and leaves *nothing* has not lied, but has thrown away work it had
already paid for, which under a quota is the same as spending twice — the connection back to part
[3.1](../03-when-you-cannot-afford-it/3.1-three-things-a-job-can-do.md)'s defer strategy.

## Why Sutra needs it

Because everything the rest of this phase does with the night assumes the night can be trusted to
report itself. Day 77's standup reads `state/digest.md` and says a sentence about it. Part
[2.4](../02-asking-before-spending/2.4-the-job-that-ran-anyway.md) showed what happens when the night
does not run at all. This criterion covers the case in between, which is far more common: the night
half-ran.

It is also the criterion Phase 12 will lean on hardest. Addendum 02 tells days 79–83 to put the full
eval run on this nightly, so the eval suite's results are about to become one of the three artefacts
that this criterion checks the presence of.

## The mechanism

The criterion is one file that shells out to another day's lab:

```python
LAB = Path(__file__).resolve().parents[2] / "day-73-ambient-agents" / "lab"
STATE = LAB / "state"
ARTEFACTS = ("index.json", "evals.json", "digest.md")


def nightly(*args: str) -> subprocess.CompletedProcess[str]:
    return subprocess.run(
        [sys.executable, "nightly.py", *args], cwd=LAB, capture_output=True, text=True
    )
```

**Line by line:**

- `Path(__file__).resolve().parents[2]` walks up from `.../day-78-.../lab/c1_nightly.py` to `days/`,
  then names Day 73's folder. It is computed from the file's own location rather than from the working
  directory, so the criterion works whether it is run directly or by `gate.py`.
- `subprocess.run` rather than importing Day 73's module. That is the important choice: a criterion
  must test the **thing as it is deployed**, and the nightly is deployed as a command a scheduler runs.
  Importing it would test a function that happens to share a file with the command, and would silently
  skip everything that happens under `if __name__ == "__main__":`.
- `cwd=LAB` because Day 73's scripts import their siblings by plain name, exactly as this day's do.
- `capture_output=True` keeps the child's chatter out of the criterion's own output, so the verdict
  lines are readable. The exit code is what is being asserted on, not the text.

The kill and its assertions:

```python
    clean()
    dead = nightly("--fail-at", "evals")
    left = [name for name in ARTEFACTS if (STATE / name).is_file()]
    died_at = last_run().get("died_at")
    print(f"  died at evals            exit {dead.returncode}, kept {left}, log says {died_at!r}")
    if dead.returncode == 0:
        failures.append("a nightly that died exited 0")
    if left != ["index.json"]:
        failures.append(f"a death at evals left {left}, expected ['index.json']")
    if died_at != "evals":
        failures.append(f"the run log says died_at={died_at!r}, expected 'evals'")
```

**Line by line:**

- `clean()` first, always. A criterion that runs against leftover state from the previous check is
  measuring the previous check. This is why `clean()` exists as a function rather than as a line at the
  top of `main`.
- `left != ["index.json"]` uses **equality against an exact list**, not `"index.json" in left`. The
  containment version passes when the death left all three artefacts, which is the exact failure this
  assertion is here to catch. Getting this one line wrong turns the criterion blind, and part
  [4.7](4.7-the-verdict.md)'s red-alarm test is what catches that.
- `ARTEFACTS` is a tuple in a fixed order, so `left` is deterministic and comparing it to a literal is
  meaningful. Built from `STATE.iterdir()` instead, the order would come from the filesystem and the
  comparison would be flaky on somebody else's machine.
- Three separate `failures.append` calls rather than one combined condition, so the output names
  **which** of the three assertions failed. A criterion that prints "criterion 1 failed" has told you
  to go and re-run it by hand.
- `died_at` is read from the last line of `runs.jsonl` — Day 73's run log. The exit code says something
  went wrong; only the log says where, and a job that exits 1 with no `died_at` has failed the
  honesty half of the criterion while passing the arithmetic half.

Run it:

```bash
cd days/day-78-inside-free-quota/lab
uv run python c1_nightly.py; echo "exit: $?"
```

**Line by line:**

- No flag runs all three checks in order: clean, kill, resume. Each one resets the state directory it
  needs.

Measured on 2026-09-06:

```text
  clean run                exit 0, produced 3/3 artefacts
  died at evals            exit 1, kept ['index.json'], log says 'evals'
  resumed                  exit 0, now 3/3 artefacts

  criterion 1: PASS
exit: 0
```

Three lines and the middle one is the whole criterion. `kept ['index.json']` is the blank line in the
register: the job stopped, it stopped somewhere specific, and what it had already earned is still
there. `log says 'evals'` is the signature that was not forged.

## When it breaks

Inject the fault this criterion exists to catch — a stage that writes its artefact **before** it
finishes, so a death leaves a file claiming work that did not complete:

```bash
uv run python c1_nightly.py --break-it; echo "exit: $?"
```

**Line by line:**

- `--break-it` creates `evals.json` immediately after the killed run, simulating a stage that wrote its
  output too early. Nothing else changes; the clean run and the resume are untouched.

Measured on 2026-09-06:

```text
  clean run                exit 0, produced 3/3 artefacts
  died at evals            exit 1, kept ['index.json', 'evals.json'], log says 'evals'
  resumed                  exit 0, now 3/3 artefacts
    - a death at evals left ['index.json', 'evals.json'], expected ['index.json']

  criterion 1: FAIL
exit: 1
```

Notice what is **still green** in that run: the clean run passed, the resume passed, the exit code of
the dead run was 1, and the log correctly said `evals`. Four of the five things this criterion looks at
are fine. The system with this fault would run every night, resume correctly after every crash, and
produce an `evals.json` describing evals that never happened — which Day 73's own resume logic would
then read as "the eval stage is done, skip it".

That is what the exact-list comparison buys, and it is why the assertion is `!=` on a list rather than
a friendlier membership test.

## In production

**What a professional writes instead of a script per criterion.** The same three assertions, but the
kill is a real signal rather than a flag — `SIGKILL` to the process at a chosen moment, the way
[Day 65 part 2.2](../../../day-65-kill-it-mid-run/parts/02-the-instrument/2.2-a-process-you-can-actually-kill.md)
argued, because `--fail-at` runs the `finally` blocks and a real crash does not. `--fail-at` is honest
enough for a criterion about *artefacts*; it is not honest enough for a criterion about durability, and
the difference matters the day somebody adds a buffered writer.

**What degrades at scale.** Three artefacts is checkable by name. Thirty is not, and the criterion
drifts into checking that *some* files appeared. The fix is that the job declares what it produces —
Day 73's `DONE` map from stage name to the file that proves it finished is already exactly this — and
the criterion reads the declaration rather than a hard-coded tuple.

**The failure that only shows with real traffic.** The clean-run check is done on an empty state
directory. Real nights start from last night's state, and the interesting bugs live there: an
artefact from a previous run that is not overwritten, a stage that appends where it should replace, a
resume that skips a stage because yesterday's file is still on disk. A criterion that always starts
clean will never see any of them.

**The review comment a senior engineer leaves:** *"The middle assertion is the only one earning its
keep — please say so in a comment, so nobody 'simplifies' it to a containment check. And `--fail-at`
is a flag inside the job, which means we are testing the job's idea of dying. Add one variant that
kills the process from outside, even if it only runs at gates."*

**The interview question:** *"How would you test that a batch job recovers correctly from a crash?"*
The answer that shows experience does not describe a unit test. It kills the process at a chosen
moment, inspects what is on disk from **outside** the process, and asserts on the exact set — because
the interesting failure is a job that leaves too much, not one that leaves too little, and only an
exact comparison notices the difference.

cd days/day-78-inside-free-quota/lab

Before running the third command, say which files you expect to find and why the criterion left the

Now change `left != ["index.json"]` to `"index.json" not in left` in `c1_nightly.py` and re-run the
`--break-it` arm. It goes green. That is a criterion going blind in one line, and it is the reason part
[4.7](4.7-the-verdict.md) makes the gate re-run every green criterion with its fault injected.
