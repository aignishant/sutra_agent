# 4.6 — Criterion 5 — every day written, no ID left open

## One-line answer

Three independent sources — the plan's day map, each day's own frontmatter, and the progress ledger —
must agree, and today they agree on the first two and disagree on the third for **all six days of the
phase**.

## The story

The attendance register and the class list.

The teacher has a register with a row per student and a column per day, and she ticks it every
morning. Separately, the office has a list of who is enrolled. Two documents, two people maintaining
them, one reality.

Most of the time nobody compares them. The teacher ticks her register, the office files its list, and
everything is fine because everything is fine.

Then, once a term, somebody does compare them, and it is always slightly interesting. A student who
left in August is still on the office list, so the class is officially one bigger than it is. A student
who joined in September has been in the room for three weeks and has no row in the register, so on
paper she has never attended. Nobody did anything wrong. Two records, both maintained honestly, drifted
apart because nothing in either of them points at the other.

The comparison is the only thing that finds it, and it has to be a comparison of things that were
written down **independently**. Copying the office list into the register would make them agree for
ever and would tell you nothing.

## The idea in plain language

Criterion 5 is plan §15 items 1, 2 and 4 in one command. It reads three sources that are maintained
separately and checks that they say the same thing about days 73 to 78:

- **The plan's §14 day map** — one row per day, giving the IDs that day must close. Written once, when
  the curriculum was designed.
- **Each day's hub frontmatter** — the `ids:` line in `LESSON.md`. Written on the day the day was
  written.
- **`docs/PROGRESS.md`** — a row per completed day. Appended by the learner when the day is finished
  and committed.

Those three are independent in the way that matters: no tool generates one from another. If a day
closes the wrong IDs, the plan and the hub disagree. If a day is written but never finished, the hub
and the ledger disagree. Neither disagreement is visible from inside either file.

The third source is the one carrying today's finding, and it is worth being clear about what a missing
`PROGRESS.md` row **means** rather than just that it is missing. Plan §16 makes that ledger the record
of completion, and `scripts/trace.py` computes open IDs from it. A day with parts, a hub and no
progress row is a day whose IDs are, by the repository's own definition, **still open** — regardless of
how finished the documents look.

## Why Sutra needs it

Because a phase gate that only tests the running system tests half the phase. The other half is the
repository: six days of documents, twelve IDs, and a plan that claims they are closed.

It matters more here than usual because of what §15 says a gate is: *"no open IDs from this or any
earlier phase."* Open IDs do not stay in their phase. An ID left open in Phase 11 is still open at the
Phase 12 gate, and at Phase 13's, accumulating — which means this criterion is the one that stops a
small bookkeeping lapse becoming a permanent one.

## The mechanism

Three readers, one per source, and each one reads the file in the format that file is actually in:

```python
def plan_ids() -> dict[int, set[str]]:
    """day -> the IDs §14 assigns it, read from the phase tables."""
    out: dict[int, set[str]] = {}
    for row in PLAN.read_text(encoding="utf-8").splitlines():
        match = re.match(
            r"^\|\s*(\d{1,2})\s*\|.*\|\s*([A-Z]{2,3}-\d+(?:,\s*[A-Z]{2,3}-\d+)*)\s*\|$", row
        )
        if match:
            out[int(match.group(1))] = {i.strip() for i in match.group(2).split(",")}
    return out
```

**Line by line:**

- It parses the plan's Markdown tables directly. That is deliberate: §14 **is** the authority, and a
  criterion that read a generated summary of it would be checking the generator.
- `^\|\s*(\d{1,2})\s*\|` anchors on a row whose first cell is a bare day number, which is what the §14
  phase tables look like and what nothing else in the plan looks like.
- `[A-Z]{2,3}-\d+` matches an ID like `ADK-51`, `AG-24` or `OPS-14`, and the `(?:,\s*...)*` group takes
  a comma-separated list of them. Anchoring the whole cell with `\s*\|$` means a row whose last cell is
  prose rather than IDs simply does not match, rather than matching partially.
- It returns **sets**, so `{"AG-24", "ADK-51"}` compares equal to `{"ADK-51", "AG-24"}`. Order in a
  frontmatter list is presentation; the claim is about membership.

```python
def hub_ids(day: int) -> set[str] | None:
    folders = sorted(DAYS.glob(f"day-{day:02d}-*"))
    if not folders or not (folders[0] / "LESSON.md").is_file():
        return None
    text = (folders[0] / "LESSON.md").read_text(encoding="utf-8")
    match = re.search(r"^ids:\s*\[(.*?)\]", text, re.M)
    return {i.strip().strip('"') for i in match.group(1).split(",")} if match else set()
```

**Line by line:**

- `glob(f"day-{day:02d}-*")` resolves a day by **number**, accepting whatever slug follows, which is
  the rule plan §17.2 states: the number is the identity and the slug is a label on it. A criterion
  that hard-coded folder names would fail the first time somebody renamed a day to a better slug.
- Returning `None` for a missing hub, rather than an empty set, keeps "no hub" distinguishable from "a
  hub that closes no IDs". They are different failures and they print differently.
- `.strip().strip('"')` because frontmatter writes `ids: ["ADK-51", "AG-24"]` and the values arrive
  with their quotes attached.

```python
def progress_days() -> set[int]:
    rows = PROGRESS.read_text(encoding="utf-8").splitlines()
    return {int(m.group(1)) for r in rows if (m := re.match(r"^\|\s*(\d{1,3})\s*\|", r))}
```

**Line by line:**

- Only the day number is read. This criterion asks whether the row **exists**; whether its gate column
  says green is `./m check`'s business, and conflating the two would give one failure two meanings.
- The walrus `:=` binds the match once inside the comprehension so the filter and the extraction share
  it. Without it the regular expression runs twice per line, which is harmless and reads worse.

**Read the first two columns before the third.** They agree, six times out of six. Every day of Phase
11 closes exactly the IDs §14 assigns it — no extras, no omissions, no drift between what the plan
asked for and what was written. That is the check that would have caught a day quietly closing an ID
that belonged to another day, and it is green.

The third column is a different kind of statement. Six days are written and none of them is
**finished**, because finishing is an act — `./m done N`, a ticked checklist, a commit, a ledger row —
and that act has not happened for any day since day 50. Twelve IDs across this phase are open by the
repository's own definition, and every one of them will still be open at the Phase 12 gate.

This is not a defect in the documents. It is the difference between writing and completing, and the
value of the criterion is that it will not let the two be confused.

## When it breaks

The criterion is a comparison, so its failure mode is a comparison that has stopped being independent.

The clearest way to break it is to have `plan_ids()` read a generated file. `docs/TRACEABILITY.md` is
produced by `scripts/trace.py` **from** the hubs, so a criterion comparing hub frontmatter against
`TRACEABILITY.md` would compare the hubs against themselves and pass eternally. It would look like a
check. It would have the same output shape. It would find nothing, ever.

There is a subtler version already present in the code above. `hub_ids` returns `set()` — not `None` —
for a hub with no `ids:` line at all, so a day whose frontmatter is malformed compares as "closes
nothing" and fails with a confusing message rather than an accurate one:

```text
    - day 78 closes [], §14 assigns ['OPS-14']
```

That message reads as *the day closed the wrong IDs* when what happened is *the frontmatter could not
be parsed*. The smallest fix is to distinguish the two — `hub_ids` returning a sentinel for
unparseable, the way it already returns `None` for missing — and the reason to name it here rather than
patch it silently is that `./m depth` already refuses a hub with missing frontmatter keys, so this
criterion is protected by a different tool and should say so rather than duplicating it.

## In production

**What a professional writes instead.** The same three-source comparison, run in CI on every commit
rather than once a phase, because its inputs are all files in the repository and it takes
milliseconds. A gate is the wrong place for a check this cheap; it belongs where the drift is
introduced. The gate then only has to look at what CI cannot: the questions needing judgement.

**What degrades at scale.** Six days is a table a person reads. Ninety-seven is not, and the criterion
must summarise: how many days disagree, and which. There is a trap in that summarisation — the
temptation to report a percentage. *"94 of 97 days consistent"* is a number that will be accepted;
*"3 days inconsistent: 51, 52, 53"* is a number somebody fixes.

**The failure that only shows with real traffic.** A ledger written by a person and a plan written
months earlier drift most when the work is going well, because that is when nobody stops. Every one of
the twenty-seven missing rows in this repository was missed on a day the writing went fine. The
mechanical answer — `./m done N` refusing to commit until the checklist is ticked — exists precisely
because the human answer does not survive a good week.

**The review comment a senior engineer leaves:** *"Three sources is right and one of them is doing all
the work. The plan-versus-hub check has been green for 78 days; keep it, but move it to CI where it
costs nothing. The ledger check is the one finding things, and 27 consecutive missing rows is not 27
oversights — it is a workflow where the finishing step is optional. Fix the workflow, not the rows."*

**The interview question:** *"How do you know your documentation matches what was actually shipped?"*
The answer that shows experience does not say "we review it". It names two artefacts written by
different people at different times for different reasons, and a check that compares them — and can
explain why comparing a generated file against its own source proves nothing.
