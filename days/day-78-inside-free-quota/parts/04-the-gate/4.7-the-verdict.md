# 4.7 — The verdict

## One-line answer

**Two green, two red, one that cannot be determined** — and the gate refuses to call itself green not
because three criteria failed, but because a gate whose green criteria have not been shown to be
capable of failing has not measured anything.

## The story

The driving test result slip.

You come back from the test and the examiner writes on a form. There is no conversation about how it
went, no *"you were a bit nervous at the roundabout but overall"*. There is a box that is either ticked
or not, and if it is not, there is a list underneath with specific lines on it: *failed to check
mirror before signalling. Mounted the kerb during the reverse.*

The list is short and it is not an assessment of you. It is a set of named events with a place and a
time. You can argue with an item — you can say the kerb was not mounted — and that argument has an
answer, because the item is about a thing that either happened or did not.

The part people misremember afterwards is the shape of the outcome. It is not a score. There is no
seventy-two per cent. You either drive away with the licence or you drive away with a list, and the
list is worth having, because it is the only version of "you are not ready" that tells you what to do
on Tuesday.

## The idea in plain language

A gate has **no partial credit**. Four of five criteria passing is not eighty per cent of a phase; it
is a phase that is not finished, plus a list. The reason is not strictness for its own sake — it is
that a percentage invites the question *is that good enough?*, which is a question with no answer,
while a list invites the question *who fixes which line?*, which has one.

Today's verdict has three shapes on it and they are three different things:

- **PASS** — the criterion ran and the property held.
- **FAIL** — the criterion ran and the property did not hold. Somebody has to change something.
- **CANNOT DETERMINE** — the criterion ran and could not decide, because an input it needs does not
  exist. Nobody has to change anything; somebody has to go and **measure**. Part
  [4.4](4.4-criterion-3-the-phase-fits.md) is the whole argument for keeping this separate.

And there is a fourth outcome that is not in the verdict table but fails the gate all the same:

- **BLIND** — a criterion that came back green and stayed green when the fault it exists to catch was
  injected. It is not passing; it has stopped looking. The gate treats a blind criterion exactly as it
  treats a red one, and it is the more dangerous of the two, because a red criterion is being read and
  a blind one is being trusted.

That last one is why `gate.py` has a second pass. Principle 11 says evals are tests; a gate is a set of
evals about a phase, and a test nobody has seen fail is not yet a test.

## Why Sutra needs it

Because this is the sentence that goes into `docs/PROGRESS.md` and into the plan's phase table, and
once it is written it is what Phase 12 inherits. A gate rounded up to green means Day 79 starts on top
of an unmeasured quota lane, a ledger row missing for the fourth time, and twenty-eight days of open
IDs — with nothing in the repository saying so.

[Day 65](../../../day-65-kill-it-mid-run/LESSON.md) faced the same choice at the Phase 9 gate and made
the same call: four green, three red, written down as such. Two of that day's three findings closed
when the missing days landed. One of them — the `mcp` ledger row — did not, and part
[4.5](4.5-criterion-4-the-freshness-check.md) is reporting it again today. That is the evidence for
this part's whole argument: an honest red is the only thing that survives long enough to be embarrassing
enough to fix.

## The mechanism

The verdict is printed from the collected results, with the blind list beside it:

```python
    print("\n=== verdict")
    for criterion, code in results:
        print(f"  {VERDICTS[code]:<18}{criterion.label}")
    failed = [c.label for c, code in results if code != 0]
    for script in blind:
        print(f"  {'BLIND':<18}{script} stays green with the fault injected")

    if failed or blind:
        print(f"\n  Phase 11 is NOT green: {len(failed)} of {len(CRITERIA)} criteria are not PASS.")
        return 1
    print("\n  Phase 11 is green.")
    return 0
```

**Line by line:**

- `VERDICTS[code]` maps the exit code to a word: `0` PASS, `1` FAIL, `2` CANNOT DETERMINE. The mapping
  is a module-level dictionary rather than an `if` chain so that adding a fourth outcome later is a
  line rather than a refactor.
- `code != 0` is what counts as failing, which means **exit 2 fails the gate**. That is correct and it
  is worth being explicit about why it does not contradict part
  [4.4](4.4-criterion-3-the-phase-fits.md): an undetermined criterion cannot let a phase be declared
  green, because "we do not know" is not evidence that it fits. What part 4.4 insists on is that the
  *word* stays distinct in the output, so the person reading knows to go and measure rather than to go
  and optimise.
- `if failed or blind` — a blind criterion fails the gate on its own, even with every verdict green.
  The two conditions are separate because they are separate findings.
- The summary counts `failed`, not `failed + blind`, which is a small honesty: the count is of
  criteria that did not pass, and a blind criterion did pass. It is listed on its own line so the
  reader sees both facts rather than an aggregated one.

And the pass that earns the right to print PASS at all:

```python
    for criterion, code in results:
        if criterion.fault is None or code != 0:
            continue
        broken = run(criterion.script, criterion.fault, quiet=True)
```

**Line by line:**

- `code != 0: continue` — only criteria that **passed** are re-run with a fault. A criterion that is
  already red has demonstrated it can go red; asking it again would be ceremony.
- `criterion.fault is None: continue` — criteria 4 and 5 have no fault flag because both are failing
  today and have therefore proved themselves. The day they go green, they will need one, and the gate
  will silently stop checking them until somebody notices. That is a real weakness of this design and
  it is named here rather than hidden: a `None` fault is a promise nobody is holding.
- `quiet=True` swallows the child's output, because the criterion has already printed its findings once
  in the first pass and only its exit code is being compared here.

Run the whole thing:

```bash
cd days/day-78-inside-free-quota/lab
uv run python gate.py; echo "exit: $?"
```

**Line by line:**

- No arguments. Every criterion runs, in order, regardless of what the ones before it did — part
  [4.1](4.1-what-phase-11-promised.md) is the argument for no early exit.

Measured on 2026-09-06, the last two blocks of the output:

```text
=== the red-alarm test: a criterion that passed must be able to fail
  c1_nightly.py   --break-it          0 -> 1  goes red
  c2_voice.py     --break-it          0 -> 1  goes red

=== verdict
  PASS              1  the nightly runs, dies honestly and resumes
  PASS              2  the voice standup delivers and can be stopped
  CANNOT DETERMINE  3  the phase fits a free-tier allowance
  FAIL              4  the pins still have ledger rows
  FAIL              5  every day written, no ID left open

  Phase 11 is NOT green: 3 of 5 criteria are not PASS.
exit: 1
```

**Read the two PASS lines through the red-alarm block above them.** `0 -> 1 goes red` is what makes
those two lines evidence rather than assertion. Criterion 1 was re-run with a stage writing its artefact
too early, and noticed. Criterion 2 was re-run with the standup reordered so the urgent lines come last,
and noticed. Without those two lines, `PASS` means only that a script exited zero.

Now the three findings, and they are three different jobs for three different people:

| Criterion | Verdict | What it means | Who acts |
| --- | --- | --- | --- |
| 3 | CANNOT DETERMINE | 60 requests a night committed to a lane whose allowance nobody measured | whoever owns the quota: one controlled burn, one dated row |
| 4 | FAIL | `mcp==1.29.1` pinned with no `docs/PACKAGES.md` row — reported by four gates now | one line in a ledger, and a look at why four reports did not produce it |
| 5 | FAIL | no day since 50 has a `PROGRESS.md` row, so twenty-eight days of IDs are open | the finishing step, `./m done N`, on every written day |

**None of those three is a bug in the running system.** Criteria 1 and 2 are the criteria about code,
and both are green, with their red-alarm runs to back it. The phase built what it said it would build.
What it did not do is measure what that costs, record what it pinned, or finish what it wrote — and
those are the three findings, in that order of seriousness.

Criterion 5 is worth one more sentence, because it is the one that looks like paperwork. Twenty-seven
consecutive missing rows is not twenty-seven oversights; it is a workflow in which the finishing step
is optional. Part [4.6](4.6-criterion-5-every-day-written.md) makes the point and it is the same shape
as criterion 4's: a finding that recurs is a fact about the process.

## When it breaks

The way a verdict breaks is by being rounded. The three specific roundings, each of which produces a
green gate over exactly this state:

**Rounding "cannot determine" up to "pass".** The criterion's exit code is `2`, and any consumer
written as `if code == 1: fail` treats it as success. That is one character away from correct and it
converts the day's largest finding into silence.

**Rounding a blind criterion up to "pass".** Delete the red-alarm pass and this gate prints two PASS
lines that mean nothing more than "a script exited zero". Part
[4.2](4.2-criterion-1-the-nightly.md)'s check-yourself does this deliberately: change one comparison
from `!=` on a list to a containment test, and criterion 1 goes green with the fault injected.

**Rounding an old finding down to "known".** This is the one that actually happens, and criterion 4 is
living evidence of it. A finding reported at four gates stops being read as a finding and starts being
read as furniture. The output is identical each time, so nothing marks the fourth report as different
from the first — and the correct fix is not to try harder, it is to make the gate able to record an
**accepted** finding with a reason and an expiry, so that an unaccepted one stays loud.

Day 65 built exactly that idea into its build brief and it is still a `TODO(me)`:

```text
TODO(me): an `accepted` field, so a finding that has been decided rather than fixed can be
recorded with a reason and stop being red.
```

Three gates later, the finding it was designed for is still red and still ignored, which is a fairly
complete demonstration of why the field was needed.

## In production

**What a professional writes instead of a verdict table.** The same table, plus an **owner and a date**
per finding, written into the place where work is tracked rather than into the output of a script. A
finding with no owner is a finding nobody has agreed to fix, and the gate output is not a work-tracking
system — it is where a finding is *born*, and it needs somewhere to go.

**What degrades over time.** The number of criteria only ever grows, one per phase, and gates get
slower and eventually get run less. The pressure that follows is to sample — run the fast criteria on
every commit and the slow ones at gates — which is fine, and is the same shrink strategy part
[3.1](../03-when-you-cannot-afford-it/3.1-three-things-a-job-can-do.md) named, with the same obligation
attached: the report must say which subset ran, or part
[3.2](../03-when-you-cannot-afford-it/3.2-the-shrunken-run-that-reports-as-full.md) happens to your
gate.

**The failure that only shows with real traffic.** Gates run on a quiet machine, alone, at a chosen
moment. Criterion 1 kills a nightly that has the whole allowance available; criterion 2 talks to a
scripted listener with no network delay. Every one of the phase's real failure modes — contention,
latency, another team's spending — is outside what any of these five criteria can see. A green gate is
evidence about the code, and only weak evidence about the system.

**The review comment a senior engineer leaves:** *"Verdict looks right and I want two things before it
goes in the ledger. Put an owner against each of the three findings, including the one that is just
'measure it' — that one has no owner today and that is exactly why it has no answer. And criteria 4 and
5 have no fault flag; they are red so it does not matter, but the day they go green they will silently
stop being checked. Add the flags now, while somebody is thinking about it."*

**The interview question:** *"Your release gate is green. How much does that tell you?"* The answer that
shows experience does not say "a lot" or "not much". It asks what the gate has been *seen to fail on* —
because a check nobody has watched go red is a check that has never been calibrated, and a green result
from an uncalibrated check is a sentence with no information in it.
