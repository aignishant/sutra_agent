# 4.2 — The dependency you inherit

## One-line answer

Deploying to the managed platform adds `google-cloud-aiplatform[adk,agent_engines]` to your
requirements and freezes the ADK version at whatever is installed on the machine that typed the
command — two dependencies you did not choose, one of which is decided by a laptop.

## The story

The gym membership that came with the flat.

The place is let with a card for the gym in the basement, included in the service charge. Very
convenient, and for a while it is used.

What was not obvious at signing is that the card is the reason the service charge is what it is, that
it renews with the tenancy rather than with any decision, and that leaving means either keeping the
flat or finding a gym. The membership is not expensive. It is simply not separable — it arrived
attached to something else, and it will leave the same way.

The people who are annoyed about this in year three are not annoyed about the gym. They are annoyed
that a recurring commitment was made by a document about something else.

## The idea in plain language

Two things attach themselves to your project the moment you take the deploy path, and neither is in
the config file you reviewed.

**A heavyweight dependency.** ADK ensures the staged requirements include a specific package:

```text
google-cloud-aiplatform[adk,agent_engines]
```

That is the Vertex AI client library with two extras. It is not a small package, it pulls a large
transitive tree of cloud client libraries, and it is now part of what your agent's image contains —
added by the deploy path, not by your `pyproject.toml`.

**A version pin decided by a machine.** Part
[1.3](../01-what-you-hand-over/1.3-reading-the-deploy-surface.md) found `--adk_version` defaulting to
"the version in the dev environment", printed as `2.7.1` because that is what is installed here. The
library version that runs your production agent is therefore chosen by whichever laptop ran the
command.

Put those together and the interesting property is not either one on its own. It is that **both are
invisible in a diff.** Your repository does not change. The config file does not change. Two
colleagues deploying the same commit on the same day can produce two different runtimes, and the
only record is in output nobody kept.

This is the paper's obstacle arriving early, and it has a name the field settled on: lock-in is
rarely a decision somebody makes. It is a set of small attachments, each individually reasonable,
that are discovered together on the day somebody proposes leaving.

## Why Sutra needs it

Because Principle 7 is *never invent a version number* and every pin gets a dated row in
`docs/PACKAGES.md`. A dependency added by a deploy path has no row, and a version chosen by an
environment has no row either — so the deploy path introduces exactly the two things this repository
has a rule against, and does it without touching a file the rule watches.

And because Phase 14 makes the repository public. A reader cloning it will get this repository's
pins from `uv.lock`; they will not get the ADK version somebody deployed with, because it was never
written down anywhere.

## The mechanism

The dependency is a module-level constant, so the lab reads it rather than quoting it:

```python
AGENT_ENGINE_REQUIREMENT = cli_deploy._AGENT_ENGINE_REQUIREMENT
```

**Line by line:**

- Read from the installed library at import. If ADK changes the package or its extras, this day's
  claim changes with it rather than becoming a confident sentence about a previous release.
- The constant is private. Reaching for it is the same trade part
  [2.2](../02-the-config/2.2-what-the-cli-adds.md) made: accept that an upgrade may break the
  reading, in exchange for a reading that is true today and checkable.
- ADK writes it into a `requirements.txt` it stages, after checking that file exists — so the
  dependency is added to a copy of your requirements, in a temporary folder, at deploy time.

And the version default, from the CLI's own help:

```text
  --adk_version TEXT              Optional. The ADK version used in Agent
                                  Engine deployment. (default:  the version in
                                  the dev environment)  [default: 2.7.1]
```

**Line by line:**

- Two defaults in one entry, which is the confusing part. The prose default is *the version in the
  dev environment*; the bracketed `[default: 2.7.1]` is click rendering what that resolves to **on
  this machine, right now**.
- A reader on a different machine sees a different number in the same help page. That is unusual
  enough to be worth stopping on: the documentation is machine-specific.
- The fix is one line in the config file — pin `adk_version` explicitly — and part
  [2.1](../02-the-config/2.1-the-config-file-adk-reads.md) noted its absence from both fixtures.

The whole inherited set, in one place:

| What | Where it comes from | Where it is recorded |
| --- | --- | --- |
| `google-cloud-aiplatform[adk,agent_engines]` | ADK's deploy path | nowhere in your repository |
| the ADK version | the deploying machine's environment | nowhere, unless you pin it |
| the generated Dockerfile | a template in `cli_deploy.py` | your current directory, after the fact |
| the thirteen published methods | a constant in `cli_deploy.py` | nowhere |

Four inheritances, one of which you can fix with a line of JSON.

## When it breaks

None of this raises. The failure is a difference between two deployments that no diff explains, and
the three shapes it takes are:

**Two machines, two runtimes.** Somebody who has not run `uv sync` has an older ADK, deploys the same
commit, and the resource runs on a different library version. Behaviour differs; the repository is
identical. This is the one the config pin fixes.

**A transitive conflict at deploy time, not at develop time.** The Vertex client library brings its
own pinned dependencies, and they meet yours in the staged `requirements.txt` rather than in
`pyproject.toml`. A conflict there surfaces during the deploy, in a build log, on a resource that has
already been created — which part [5.1](../05-in-production/5.1-the-failure-path-nobody-tests.md) is
about.

**The extras change.** `[adk,agent_engines]` is two extras chosen by ADK. If a future version adds a
third, your image grows and nothing in your project mentioned it.

There is no error text to quote for any of these, and that absence is the finding. The one thing that
*would* have caught the first shape is a line in the config, and the reason it is not there by
default is that nothing forces it.

## In production

**What a professional does.** Pins the platform version explicitly in the reviewed config, and
records it wherever the project's other pins live — for this repository, a dated row in
`docs/PACKAGES.md`. The rule is that anything which can change what runs in production has a
recorded version, and "whatever was installed" is not a version.

**What degrades at scale.** The inherited set grows with the platform and never shrinks. Each release
adds a capability, a capability needs a dependency, and the dependency arrives with the deploy rather
than with a decision. After a few years the honest answer to "what is in our image" requires reading
someone else's source, which is where the effort of leaving comes from — not from the code you wrote,
but from the accumulated attachments around it.

**The failure that only shows with real traffic.** The version that was fine and is not. A platform
version bump changes a default — a timeout, a serialisation, a session behaviour — and the deployment
that picks it up is the next one anybody happens to run, from whichever machine. The symptom appears
in production and the change is not in any commit.

**The review comment a senior engineer leaves:** *"Pin `adk_version` in the config and put it in
PACKAGES.md with today's date. I do not want our production runtime decided by whoever last ran the
deploy."*

**The interview question:** *"What did adopting that platform add to your dependencies?"* The answer
that shows experience names at least one package the platform added rather than the team, and knows
whether the version is pinned by them or inherited. It is a question almost nobody has looked into,
and it is the whole of what lock-in means in practice.
