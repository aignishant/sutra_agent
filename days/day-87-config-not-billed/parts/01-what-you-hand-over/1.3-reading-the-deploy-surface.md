# 1.3 — Reading the deploy surface

## One-line answer

`adk deploy agent_engine --help` is twenty-five options long, nine of them deprecated, and reading
it properly answers three questions no tutorial will: which flags are load-bearing, which are
already on their way out, and which quietly decide something you would want to decide yourself.

## The story

The application form with more boxes than you expected.

You sit down to renew something. The form is four sides. Most of it is name, address, the obvious
things — and then on the third side there is a box you have to tick, with small print underneath,
and it turns out to be the one that decides whether your existing number is kept or a new one
issued.

Nobody at the counter mentioned it. It is not hidden; it is simply the fourteenth box on a form
where the first thirteen were boring, and by then you were signing rather than reading. The people
who end up with the right outcome are the ones who read the whole form once, slowly, before filling
in any of it.

## The idea in plain language

A CLI's `--help` is the closest thing a tool has to a specification you can trust, because it is
generated from the code that runs. It is also the last place anybody looks, because it is long and
unstructured and a tutorial is shorter.

Reading it properly means sorting the flags into four groups. For `adk deploy agent_engine` in
`google-adk==2.7.1`:

**Where it goes.** `--project` and `--region` name a cloud project, or `--api_key` uses what ADK
calls Express Mode. These are mutually exclusive in a specific way: the help says `--project` "will
be ignored if api_key is set", so passing both does not fail — it silently picks one.

**What it is called there.** `--display_name` and `--description`, both defaulting to the empty
string. An unnamed resource in a console beside forty others is the sort of thing that seems fine
on the day and is unusable in a month.

**What goes with it.** `--extra_packages` stages local code alongside the agent, and its help
carries a warning worth quoting in full: entries land at `/app/<basename>` with `/app` on the
Python path, "so a top-level name that matches an installed dependency will shadow it at runtime;
pick distinct names." A package called `types` or `json` in your repository would shadow the real
one, on the platform, at runtime, and nowhere else.

**What it decides for you.** This is the group that matters and it is the one nobody reads:

| Flag | Default | What it quietly decides |
| --- | --- | --- |
| `--adk_version` | `2.7.1` — whatever is installed here | the library version that runs in production |
| `--session_service_uri` | unset | which session store the deployed desk uses |
| `--otel_to_cloud` | off | whether traces leave your machine, and what is in them |
| `--agent_engine_config_file` | `.agent_engine_config.json` beside the agent | the file that supplies everything else |

`--adk_version` defaulting to the version in the development environment is the one to sit with.
Whatever is on the machine that typed the command becomes the runtime, so a colleague who has not
run `uv sync` deploys a different platform version than you do, from the same repository, with no
diff to show for it.

And then the ninth group, which is not a group so much as a weather report: **nine of the
twenty-five options are marked deprecated in their own help text.**

## Why Sutra needs it

Because Principle 8 is *never invent an API*, and a deploy surface is the easiest place in a project
to invent one. Deployment is the step people copy from a blog post, and a blog post about a
fast-moving platform is stale by construction — nine of these flags would already mislead a reader
who found them written down last year.

And because the checkable version of "we read the docs" is a test. Part
[1.1](1.1-what-you-hand-over.md) showed `surface.py` counting the flags; the reason it also asserts
on the eight flags this day quotes is that a day which quotes a flag is making a claim, and a claim
that nothing checks is a claim that rots.

## The mechanism

The parser is the interesting part, because the first version got it wrong in a way worth showing.
Click starts each option at column two and wraps its description underneath, so a naive regex that
looks for "deprecated" near a flag name reads *the next flag's* description:

```python
def options(text: str) -> dict[str, str]:
    starts = [(m.group(1), m.start()) for m in re.finditer(r"^ {2}(--[a-z_][a-z_-]*)", text, re.M)]
    bounds = [s for _name, s in starts] + [len(text)]
    return {name: text[bounds[i] : bounds[i + 1]] for i, (name, _s) in enumerate(starts)}
```

**Line by line:**

- `^ {2}(--...)` with `re.M` — exactly two spaces then a long flag, at the start of a line. Click's
  wrapped continuation lines are indented much further, so this matches option starts and nothing
  else.
- `m.start()` keeps the *position*, not just the name. The names alone would be enough to count
  flags and not enough to attribute descriptions, which is where the first attempt went wrong.
- `bounds` appends `len(text)` so the last option's block runs to the end of the page rather than
  being dropped.
- The dictionary maps each flag to its own slice of the help text. Everything downstream — counting
  deprecations, checking a quoted flag still exists — is then a question about one block, and cannot
  bleed into the neighbouring one.

The first version of that check reported five deprecated flags, and it was wrong in both
directions at once: it called `--description` deprecated, which it is not, because the flag
underneath it is — and it missed five that genuinely are, including `--staging_bucket` and
`--env_file`. One false positive and five false negatives out of nine. The corrected version
reports nine, and the gap between the two is not a rounding: it is the difference between "a few
legacy flags" and "more than a third of this surface is on its way out".

```bash

uv run python surface.py | sed -n '3,14p'
```

**Line by line:**

- `sed -n '3,14p'` for the flag census; the target list is in part
  [1.1](1.1-what-you-hand-over.md) and does not change.

Measured on 2026-09-07:

```text
  adk deploy agent_engine: 25 options besides --help
  of those, 9 are marked deprecated in their own help text:
    --absolutize_imports
    --adk_app
    --adk_app_object
    --env_file
    --requirements_file
    --skip-agent-import-validation
    --staging_bucket
    --trace_to_cloud
    --validate-agent-import
```

Read that list as a history. `--adk_app`, `--adk_app_object`, `--absolutize_imports` and
`--validate-agent-import` are the remains of an older packaging model; `--env_file` and
`--requirements_file` were once how you told the deploy what to include and are now inferred;
`--staging_bucket` is a storage requirement that went away. Six of the nine are not features being
removed — they are **decisions the platform took back**, which is part
[1.1](1.1-what-you-hand-over.md)'s trade, visible in a help page.

## When it breaks

The surface moves and the day does not. That is the failure this check exists for, and it has a
real exit code:

```python
    missing = [f for f in QUOTED if f not in names]
```

**Line by line:**

- `QUOTED` is the eight flags this day names in prose. Naming a flag is a claim; this is the claim's
  test.
- A missing flag exits 1 with the flag printed, so the failure names the part that has to be fixed
  rather than saying the day is stale.
- What it deliberately does not check is *behaviour*. A flag that still exists and now means
  something else passes this check and breaks the teaching, and no local test can catch that.

There is a second failure with no check at all, and it is the one that would actually bite. Consider
`--adk_version`:

```text
  --adk_version TEXT              Optional. The ADK version used in Agent
                                  Engine deployment. (default:  the version in
                                  the dev environment)  [default: 2.7.1]
```

Two machines, same repository, same command, different production runtime — and the only evidence is
a default printed in a help page that neither person read. There is no error, no warning and no
diff. The fix is one line in the config and part
[2.1](../02-the-config/2.1-the-config-file-adk-reads.md) is where it goes.

## In production

**What a professional does.** Reads `--help` once, in full, before the first deploy, and writes down
the flags that have defaults — because a flag you pass is a decision you made and a flag you omit is
a decision somebody else made. Then pins the ones that matter explicitly, even where the default is
currently right, because a default is a value that is allowed to change.

**What degrades at scale.** Twenty-five options is a page. A mature platform's deploy surface is
hundreds, spread across a CLI, a config file and a web console, and nobody reads any of it — which is
why the config file becomes the only readable artefact and why part
[2.1](../02-the-config/2.1-the-config-file-adk-reads.md) is the centre of this day rather than the
CLI.

**The failure that only shows with real traffic.** `--extra_packages` shadowing. The help warns
about it, the warning is one clause in a long paragraph, and the symptom is an import resolving to
your file instead of the library's — on the platform only, at runtime only, in a process you cannot
attach a debugger to. This is exactly the class of bug that is trivial locally and expensive
remotely, and the mitigation is the boring one: distinct top-level names, checked before deploy.

**The review comment a senior engineer leaves:** *"Pin `adk_version` in the config. Right now
whichever laptop runs the deploy decides our production runtime, and that is not a thing we should
be discovering from a help page."*

**The interview question:** *"How do you know which deployment flags matter?"* The answer that shows
experience sorts them by who decides: the flags you must pass, the flags with defaults you are
accepting, and the flags that are deprecated. The middle group is the one that causes incidents, and
most people have never separated it out.
