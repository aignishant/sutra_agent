# 1.1 — What you hand over when you hand it over

## One-line answer

A managed platform is a trade rather than a service: you stop operating a thing and you start
depending on one, and the whole of this day is about looking hard at the second half of that
sentence before signing, because the first half is the half everybody reads.

## The story

The locker at the railway station.

You are carrying a heavy bag and you have four errands to run. There is a counter that will take
the bag, give you a numbered token, and keep it until evening. It costs a little and it is
obviously worth it.

What you have actually done is swap one problem for three smaller ones you now have no control
over. The counter closes at a time printed on a board you did not read. The token is now the only
thing standing between you and your bag. And if the counter is shut when you come back — power cut,
staff shortage, a queue that does not move — there is nothing you can do about it, because the bag
is on the other side of a shutter.

None of that makes the locker a bad idea. It makes it a **trade**, and the person who checks the
closing time before handing the bag over is not being difficult. They are reading the half of the
deal that is not on the poster.

## The idea in plain language

Everything Phase 13 has built so far, the desk runs itself. Day 84 put spans in a tracer this
repository configures. Day 85 served the desk from a process this repository starts. Day 86 put it
in a container this repository builds, with secrets this repository injects and a health check this
repository defines.

A **managed platform** — the thing this day is about — takes all of that. You hand over an agent and
a configuration file; the platform runs the process, restarts it, scales it, holds the sessions,
and hands you back a resource name. The operational work goes away.

What arrives in its place is a set of dependencies that did not exist yesterday:

| What you stop doing | What you start depending on |
| --- | --- |
| running the process | the platform's idea of healthy, and its restart policy |
| scaling it | its scaling behaviour, which you observe rather than set |
| storing sessions | its session service, reachable by a URI you do not control |
| choosing the runtime | the library version frozen at deploy time |
| deciding when it exists | a resource that bills while it exists, whether or not it is asked anything |

That last row is the one that changes how you budget, and part
[4.1](../04-what-it-costs/4.1-priced-in-requests.md) is what happens when you try to write it into
this repository's ledger.

None of this is an argument against managed platforms. The argument *for* them is real, it is
economic, and it is old enough to have a paper — which is why this day has one. The argument is
also conditional, and knowing the condition is the difference between choosing a platform and
being defaulted into one.

## Why Sutra needs it

Because the desk is nearly finished and somebody is going to ask where it runs. The honest answer
has to name what is being given up, and "we did not want to operate it" is only half of a decision.

And because this repository has a constraint that makes the trade unusually legible: Principle 15,
zero budget. A platform that bills by existence cannot be run here at all, so the choice is forced
and the only useful thing to do with it is to understand it thoroughly enough to make it later, on
purpose. That is what part [1.2](1.2-why-this-day-is-parked.md) is about.

## The mechanism

The trade is not abstract; ADK writes it down. `adk deploy` advertises three places to hand the
desk over, and the lab reads that list off the CLI rather than off a page that might be stale:

```python
TARGETS = ("agent_engine", "cloud_run", "gke")
```

**Line by line:**

- Three targets, in increasing order of how much you keep. `gke` is a cluster you still operate;
  `cloud_run` is a container the platform runs; `agent_engine` is the whole agent handed over,
  sessions and all.
- The names are hard-coded in the lab so that the check can *fail*. If ADK adds or removes a
  target, `surface.py` notices, which is the difference between reading documentation and testing
  it.

```bash
cd days/day-87-config-not-billed/lab
uv run python surface.py; echo "exit: $?"
```

**Line by line:**

- No flag: the target list, the flag count, and whether the flags this day quotes still exist.

Measured on 2026-09-07:

```text
adk deploy advertises 3 targets: agent_engine, cloud_run, gke

  adk deploy agent_engine: 25 options besides --help
  of those, 9 are marked deprecated in their own help text:
    --absolutize_imports
    --adk_app
    --adk_app_object
    --env_file
    --requirements_file
    --skip-agent-import-validation
    --staging_bucket
    --trace_to_cloud

```

**Nine of twenty-five options are deprecated in the version you would deploy with today.** That is
not a criticism of ADK — a fast-moving surface is what a young platform looks like — but it is a
measurement of what "depending on it" currently means, and it is the sort of number that never
appears in a decision meeting.

## When it breaks

The trade breaks when only the first half of it was ever written down, and the shape is always the
same: the operational work disappears, the dependency is never named, and then one day the
dependency does something.

There is no error text for this, because the trade is not an error. What there is, in ADK's own
help, is the vocabulary problem arriving early:

```bash
uv run python surface.py --names; echo "exit: $?"
```

**Line by line:**

- `--names` prints the names one product answers to, each with the place it was read.

Measured on 2026-09-07:

```text
one product, 5 names, all live in google-adk==2.7.1 on 2026-09-07:

  Agent Engine          the plan section 14 row, and the CLI subcommand adk deploy agent_engine
  Agent Platform        cli_deploy.py's own echo strings
  Agent Runtime         adk.dev/deploy/agent-runtime/, which /deploy/agent-engine/ redirects to
  agent_engine_config   the config file ADK reads: .agent_engine_config.json
  reasoningEngines      the resource path segment: projects/*/locations/*/reasoningEngines/*
exit: 0
```

**Five names, one product, one version, one day.** The CLI subcommand says one thing, the code it
runs prints another, the documentation page has been renamed to a third, the config file keeps the
old name, and the resource path keeps a name older than any of them.

Every one of those is correct in its own place. Together they are the clearest available evidence
of what depending on a young platform costs: not downtime, but the steady work of keeping up with
a thing that is still deciding what it is called.

## In production

**What a professional does.** Writes the dependency half of the trade down, in the same document
that justifies the platform. Not as a risk register — as a list of specific things that are now
somebody else's decision, with a note against each saying what you would do if it changed. The
exercise takes an afternoon and it is the difference between a choice and a drift.

**What degrades at scale.** The trade gets better and the exit gets worse, at the same rate. A
platform is most valuable exactly when you are running many agents, and that is exactly when the
configuration, the session store, the resource naming and the deployment scripts have grown roots.
The paper this day reads named that as one of its obstacles, and part
[papers/01](../../papers/01-the-bill-that-follows-the-load.md) is what happened to that prediction.

**The failure that only shows with real traffic.** The platform's idea of healthy is not yours. It
restarts on its own signal, scales on its own signal, and the first time those disagree with what
the desk actually needs is the first time you discover you cannot change either. Day 86's health
check is a thing this repository defines; on a managed platform it becomes a thing you declare and
hope is interpreted the way you meant.

**The review comment a senior engineer leaves:** *"Fine, but write down the five things we can no
longer change, and what we would do about each one. If we cannot answer that for at least three of
them, we are not choosing this platform, we are just tired of operating."*

**The interview question:** *"Why not just use a managed agent platform?"* The answer that shows
experience does not argue about features. It names what the platform decides on your behalf —
restarts, scaling, session storage, runtime version — and asks which of those the system in
question actually has an opinion about, because if it has none then the platform is obviously right.
