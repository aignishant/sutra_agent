# 1.2 — 🅿️ Why this day is parked

## One-line answer

🅿️ means the configuration gets written, reviewed and checked and the deploy command never gets
typed — not because deploying is hard, but because the command is the only part of this that costs
money and the only part that teaches nothing.

## The story

The builder's quotation you do not accept.

You want the kitchen done. A builder comes, measures, and leaves a sheet of paper: the work broken
into items, the materials, what is included, what is extra, when payment falls due. It sits on the
table for a fortnight.

In that fortnight the quotation does most of the work a quotation can do. You find out that the
thing you thought was one job is eleven. You notice that moving the sink is not on the sheet and
ask why. You discover the phrase "subject to condition of existing pipework", which is where the
real risk lives. You compare it against a second sheet from a second builder and learn that one of
them has assumed something the other has not.

You end up understanding your own kitchen considerably better, and you have not spent anything. The
signature at the bottom is what costs — and the signature is not where the learning was.

## The idea in plain language

**🅿️ is this curriculum's marker for parked**: a topic taken to awareness level and interview
readiness, deliberately not built. It is not a shortcut and it is not a gap. It is a decision, made
once, about where the learning actually is.

For a managed platform the decision is unusually clear, because the work splits cleanly:

| The part that teaches | The part that bills |
| --- | --- |
| what the platform decides on your behalf | creating the resource |
| what the configuration file has to contain | keeping it alive |
| what travels with your agent when it goes | serving traffic from it |
| what the bill is denominated in | tearing it down again |
| what you would check before typing the command | — |

Everything in the left column can be done on an empty wallet, this afternoon, and it is all of the
judgement. Everything in the right column needs a billing account and teaches you that the command
works, which you already believed.

So the rule for this day, stated plainly rather than apologetically: **nothing here requires a
credit card, and the deploy command appears only as a `TODO(me)` the learner may choose never to
run.** Addendum 02 wins over the plan on this and says so directly — never write code that requires
a billing account.

There is one thing parked days get wrong, and this day guards against it. A day can *say* it is
parked and quietly contain a step that needs an enabled project — an import, a helper, a script
somebody committed. Part [3.3](../03-checking-locally/3.3-the-parked-day-that-billed.md) is a check
that makes the marker enforceable instead of decorative.

## Why Sutra needs it

Because the repository goes public in Phase 14, and a curriculum that claims zero budget while
containing a day nobody can complete for free would be making a promise it does not keep. The
marker is a promise; a promise that is not checked is a wish.

And because "we did not build it" is a sentence that has to be defensible in an interview. Part
[5.2](../05-in-production/5.2-before-you-would-actually-deploy.md) is the list that makes it
defensible: not *we skipped this*, but *here is exactly what we would do, here is what we checked,
and here is the one step we chose not to pay for*.

## The mechanism

The parked promise is a property of the day's own files, so it can be checked like any other
property. The whole rule is one distinction:

```python
SPAWNERS = ("run", "Popen", "system", "check_call", "check_output", "call")
```

**Line by line:**

- The six ways this lab could start a process. A billable command is only a requirement if
  something *runs* it; a billable command in a docstring is the day doing its job.
- `call` and `run` are deliberately broad. A false positive here is cheap — you read one line and
  dismiss it — while a false negative is a day that quietly bills.
- The list is a constant rather than a regex over source text, because part
  [3.3](../03-checking-locally/3.3-the-parked-day-that-billed.md) measures what happens when this
  check is written as a text search instead: it flags its own documentation eleven times.

```bash
cd days/day-87-config-not-billed/lab
uv run python parked.py; echo "exit: $?"
```

**Line by line:**

- No flag: scan the lab as it stands and report anything that would need a billing account to run.

Measured on 2026-09-07:

```text
scanning 5 file(s); counting: only strings that reach a process call
markers: adk deploy, agent_engines.create, aiplatform, gcloud, vertexai


  billable requirements found: 0
  the parked marker holds: everything here runs on an empty wallet
exit: 0
```

Zero, and the zero is checked rather than asserted. The day mentions `adk deploy` throughout — that
is the subject — and not once does it run it.

## When it breaks

Parked breaks in two directions and only one of them is obvious.

**The loud direction** is a day that says parked and needs a card. That is what part
[3.3](../03-checking-locally/3.3-the-parked-day-that-billed.md) catches, and the failure looks like
this when somebody commits a convenience script:

```text
  sloppy_deploy.sh:4  gcloud - the Cloud SDK, which needs an enabled project
  sloppy_deploy.sh:5  gcloud - the Cloud SDK, which needs an enabled project
  sloppy_deploy.sh:6  adk deploy - a deploy, which creates the resource above

  billable requirements found: 3
  this day is marked parked and would not run without a credit card
```

**The quiet direction** is worse and has no check: a day that is parked *and hollow*. The marker
becomes a licence to write four paragraphs of description, mark it 🅿️, and move on — and the reader
ends up with a vocabulary rather than a judgement. Nothing in this repository's tooling can tell
those apart, because the difference is whether the day contains a decision somebody could act on.

The test to apply, and it is a question rather than a script: **could a reader who has done this day
review somebody else's deployment config and find something wrong with it?** If not, the day is
hollow, and the marker is covering for it. Part
[3.1](../03-checking-locally/3.1-a-config-checker-that-fails.md) exists to make the answer yes.

## In production

**What a professional does.** Separates *deciding* from *doing*, and does the deciding in cheap
artefacts. A configuration reviewed before it is applied, a plan printed before it is run, a change
described before it is made. Every mature deployment tool has grown this idea — the dry run, the
diff, the plan — because the expensive half is applying it and the useful half is reading it.

**What degrades at scale.** Parked topics accumulate, and unlike a backlog nobody grooms them. Ten
of them are a coherent set of decisions; forty are a list of things somebody once decided not to
learn, and by then nobody remembers which were deliberate. The discipline is that a parked item
carries the reason it is parked and the condition that would unpark it, both of which live in the
hub's ledger rather than in memory.

**The failure that only shows with real traffic.** The first real deploy is done by somebody who
did not read the parked day. The configuration was written carefully, reviewed, and then applied six
months later by a person who typed the command from a wiki — and every judgement in the left-hand
column above was made again from scratch, badly, under pressure. The mitigation is that the config
and its checker live in the repository, so the judgement is executable rather than remembered.

**The review comment a senior engineer leaves:** *"Good, but the marker needs a check. Right now
'this day needs no billing account' is a sentence in a document, and sentences in documents are how
we ended up with a deploy script in `scripts/` that nobody can run."*

**The interview question:** *"You have never deployed this to a managed platform. Why should I
believe you understand it?"* The answer that shows experience does not get defensive. It offers the
config, names the two things in it that a reviewer should object to, and says which single step was
skipped and exactly what it would have cost.

## Check yourself

```bash
cd days/day-87-config-not-billed/lab
uv run python parked.py; echo "exit: $?"
uv run python parked.py --sloppy; echo "exit: $?"
```

Two arms, two exit codes. Say what `--sloppy` adds and why a file like that ends up in a repository
without anybody deciding to put it there.

Now apply the hollowness test to this day, honestly. List the three things you could point at in
somebody else's deployment config after reading it. If you cannot get to three by the end of
section 3, say so — that is a real finding about the day, not about you.

**Out loud, without scrolling up:** what did the fortnight with the quotation on the table actually
teach, and which part of the builder's job was the part that cost money?
