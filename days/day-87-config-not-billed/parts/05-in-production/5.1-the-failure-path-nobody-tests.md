# 5.1 — The failure path nobody tests

## One-line answer

ADK creates the resource first, configures it second, and deletes it if the second step throws — a
correct design with one gap: a deploy that is interrupted between those two calls leaves a created,
unconfigured, billing resource that nothing will ever tidy up.

## The story

The locker key you still have at closing time.

Back to the station from part [1.1](../01-what-you-hand-over/1.1-what-you-hand-over.md), and this
time the errand runs long. The counter has a procedure for everything: a ticket when the bag goes
in, a receipt when it comes out, a log at the end of the shift. It is a well-run counter and the
procedure works.

What the procedure covers is bags arriving and bags leaving. What it does not cover is the state in
between at the moment the shutter comes down — a numbered space, occupied, with a customer
somewhere in the city holding the only token, and a shift handover that records neither. Nothing has
gone wrong. Everybody followed the steps. The space is simply unavailable now, to everybody,
including the people whose job it is to know what is in it.

## The idea in plain language

The deploy is not one operation. Reading ADK's own path, it is a sequence, and the order matters:

1. `client.agent_engines.create()` — a new resource exists, and starts costing.
2. A Dockerfile is generated and written.
3. `client.agent_engines.update(name=..., config=agent_config)` — the resource is told what it is.

And there is a failure branch around the third step, which is genuinely well designed:

```text
try:
  client.agent_engines.update(name=resource_name, config=agent_config)
except Exception as e:
  if agent_engine_id is None:
    client.agent_engines.delete(name=resource_name)
  raise e
```

If the configure step fails **and** the resource was created by this run, it is deleted. That
`agent_engine_id is None` test is the careful part: it means an update to an *existing* resource that
fails does not delete somebody's live deployment. Somebody thought about this.

The gap is not in the branch. It is that the branch only runs if the process is alive to run it.

**Between step 1 and step 3 there is a window** in which a resource exists and is unconfigured. Any
interruption in that window — a laptop lid, a lost network, `Ctrl-C`, a CI job hitting its time
limit, a container being evicted — leaves the resource created and nothing running to clean it up.
It is not in your repository, it is not in the deploy output you kept, and it does not appear in
anything you would think to check. It bills, quietly, in the unit part
[4.1](../04-what-it-costs/4.1-priced-in-requests.md) could not express.

## Why Sutra needs it

Because Principle 13 is blast radius before capability, and the blast radius of a deploy is
usually described as "it might not work". The honest description is that it might not work *and
leave something behind*, and the second half is the one with a recurring cost.

And because this is the shape of failure this repository keeps meeting. Day 82's nightly found a
regression and exited zero. Day 83's history was written correctly into a directory git ignores.
Every one of these is a system doing exactly what it was told, with a gap between what was told and
what was meant, and no error anywhere.

## The mechanism

The order of operations is the whole finding, so it is worth reading as a sequence rather than as
code:

```text
1. create()          -> a resource exists; billing starts
2. create_dockerfile -> local file written
3. update(config)    -> the resource becomes the thing you configured
   on exception, if we created it this run: delete()
```

**Line by line:**

- Step 1 has no configuration in it. The resource that exists after `create()` is an empty one, which
  is why step 3 is needed and why the window between them is a real state rather than a theoretical
  one.
- Step 2 is local work happening *after* a remote resource exists. Anything that can go wrong with
  writing a file — a read-only directory, a full disk — goes wrong with the meter already running.
- The `delete()` is inside `except`, not inside `finally`. That is correct: a successful deploy must
  not delete its own resource. It also means the cleanup is reachable only through an exception the
  process survives long enough to handle.
- `raise e` after the delete, so the failure still surfaces. Principle 10 in somebody else's code.

What ADK does *not* have, and cannot reasonably have, is a way to survive its own process dying.
Cleanup that depends on the failing process still running is the general form of this, and it is
unfixable from inside — which is why the mitigation is external and why part
[5.2](5.2-before-you-would-actually-deploy.md) lists it as a thing to arrange rather than a thing to
code.

## When it breaks

Three ways, in increasing order of how long they take to notice.

**The interrupted deploy.** The window above. A resource exists, has no display name — because
`display_name` is applied in step 3 — and is therefore, per part
[2.1](../02-the-config/2.1-the-config-file-adk-reads.md), unfindable by name in a console listing.
The one artefact that would let you find it is the resource id printed to a terminal that has since
been closed.

**The failed deploy that cleaned up correctly.** This one works as designed and still costs
something: the resource was created, existed briefly, and was deleted. On a per-existence charge that
is small. On a deploy that is retried in a loop by a CI job, it is not.

**The successful deploy that replaced nothing.** Without `--agent_engine_id`, every run **creates a
new instance**. Deploy three times to check something and there are three resources, two of them
orphaned by intent rather than by accident, all three billing. The flag that prevents it is optional
and its default is to create.

That last one deserves emphasis because it is the common case and it does not feel like a failure at
all:

```text
  --agent_engine_id TEXT          Optional. ID of the Agent Engine instance to
                                  update if it exists (default: None, which
                                  means a new instance will be created).
```

**Default: create a new one.** Three iterations of a config fix is three resources unless somebody
passed a flag that is not required and is easy not to know about.

## In production

**What a professional does.** Arranges cleanup outside the process that might die. In practice that
is one of three things: a scheduled sweep that lists resources and reports any without an expected
label; a tagging convention applied at creation so an orphan is identifiable; or a deployment tool
that records intent to a durable store before acting, so a later run can reconcile. All three are
the same idea — the record of what *should* exist lives somewhere other than in the process
creating it.

**What degrades at scale.** Orphans accumulate silently and are individually cheap, which is exactly
the profile that defeats attention. Nobody investigates a small line item. The number is noticed
during a cost review, at which point the question is not "delete this" but "is anything using it",
and for an unnamed resource created eight months ago by a deploy that failed, nobody can answer.

**The failure that only shows with real traffic.** The retry loop. A CI pipeline configured to retry
a failed deploy three times, against a transient error, creates and abandons resources at whatever
rate the pipeline runs — and looks, from the pipeline's own logs, like a job that is flaky rather
than one that is leaving things behind.

**The review comment a senior engineer leaves:** *"Pass `--agent_engine_id` from the config, always.
And before this goes in CI, tell me what sweeps up a deploy that dies halfway, because right now the
answer is nothing and the failure mode is invisible."*

**The interview question:** *"What happens if your deploy is interrupted?"* The answer that shows
experience does not say it retries. It names the window in which a remote resource exists and no
local process is responsible for it, and then says what outside the deploy would notice — because
if the answer is nothing, the system has a leak rather than a failure mode.
