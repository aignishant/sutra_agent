# 3.3 — 💥 The parked day that quietly required a credit card

## One-line answer

A day can claim it needs no billing account and contain a script that does, so the claim needs a
check — and the first version of that check flagged eleven things, every one of them a mention in
this day's own documentation, which is precisely how a policy check gets switched off.

## The story

💥 **The gate at the shop door that beeps at library books.**

🎬 **The scene.** A small shop with security gates at the entrance. They exist to catch unpaid
stock, and they work: a tagged item goes through and the alarm sounds.

😬 **The naive fix.** The gates are sensitive enough to catch anything with a magnetic strip. Good —
better to catch too much than too little.

💥 **Why it fails.** Library books have strips. So do some train passes, some other shops' bags, and
one particular brand of umbrella. The gate goes off perhaps a dozen times a day and eleven of those
are somebody carrying a novel. Within a fortnight the staff have stopped looking up. They have not
disabled anything and nobody decided to ignore the alarm; they have simply learned, correctly, what
the sound means, and what it means is *a customer is walking past the door*.

💡 **The insight.** **A detector's usefulness is set by its false positives, not its true ones.** A
gate that catches every theft and also every library book catches no thefts at all, because the
signal it produces has been trained into background noise by people acting entirely reasonably.

## The idea in plain language

Part [1.2](../01-what-you-hand-over/1.2-why-this-day-is-parked.md) made 🅿️ a promise: everything in
this day runs with no billing account. A promise nothing checks is a wish, so the day checks it.

The check is a scan for the things that only work once billing is enabled: `gcloud`, `vertexai`,
`aiplatform`, `agent_engines.create`, `adk deploy`. If any of them is required, the promise is
broken.

Written the obvious way — search every line of every file — the check produced this:

```text
  _deploy.py:36  adk deploy - a deploy, which creates the resource above
  parked.py:11  adk deploy - a deploy, which creates the resource above
  parked.py:30  gcloud - the Cloud SDK, which needs an enabled project
  parked.py:31  vertexai - Vertex AI, which is billed per call
  parked.py:32  aiplatform - the Vertex AI SDK
  parked.py:33  agent_engines.create - creating a managed resource, billed while it exists
  parked.py:34  adk deploy - a deploy, which creates the resource above
  surface.py:35  adk deploy - a deploy, which creates the resource above
  surface.py:66  adk deploy - a deploy, which creates the resource above
  surface.py:73  adk deploy - a deploy, which creates the resource above
  validate.py:10  adk deploy - a deploy, which creates the resource above

  billable requirements found: 11
```

Eleven findings, every one a false positive. Five of them are **the check's own list of things to
look for** — `parked.py:30` through `parked.py:34` are the marker table matching itself. The rest are
docstrings: a day about deployment says `adk deploy` in its help text, because that is the subject.

Nothing here is billable. The scanner is correct about every string it found and wrong about every
conclusion it drew, and a report of eleven findings with zero real ones is a report nobody reads
twice.

## Why Sutra needs it

Because the repository goes public in Phase 14 and 🅿️ appears throughout it. If the marker means
anything, something has to enforce it, and this is the day where enforcement is hardest — a day
whose subject is a billable command, sitting in a curriculum that promises none.

And because the false-positive lesson is worth more than the check. Days 79 to 83 established that a
check which cannot fail is decoration; this is the other end of the same problem. A check that fails
constantly is also decoration, and it takes longer to notice because it looks like diligence.

## The mechanism

The distinction that fixes it is between a billable command being **executed** and one being
**discussed**. A Python file has a syntax tree, so the question is answerable precisely:

```python
def spawned_strings(source: str) -> list[tuple[int, str]]:
    """Every string constant that is an argument to a process-spawning call, with its line."""
    found: list[tuple[int, str]] = []
    for node in ast.walk(ast.parse(source)):
        if not isinstance(node, ast.Call):
            continue
        func = node.func
        name = func.attr if isinstance(func, ast.Attribute) else getattr(func, "id", "")
        if name not in SPAWNERS:
            continue
        for inner in ast.walk(node):
            if isinstance(inner, ast.Constant) and isinstance(inner.value, str):
                found.append((inner.lineno, inner.value))
    return found
```

**Line by line:**

- `ast.parse` then `ast.walk` — the file as structure rather than as text. Comments are gone before
  the loop starts, which removes a whole class of false positive for free.
- `func.attr if isinstance(func, ast.Attribute) else getattr(func, "id", "")` handles both
  `subprocess.run(...)` (an attribute) and a bare `run(...)` (a name). The `getattr` default of `""`
  covers the case where the thing being called is neither — a call on a subscript, say — without
  raising.
- `if name not in SPAWNERS: continue` is the whole idea. A string only counts if it is inside a call
  that starts a process.
- The inner `ast.walk(node)` collects constants anywhere *within* the call, so a command assembled as
  a list literal, or nested in an f-string's parts, is still seen.
- `inner.lineno` is kept so the report points at a line. A finding without a location is a finding
  somebody has to go looking for.
- What this deliberately does not do is follow variables. A command built up in a variable and then
  passed to `subprocess.run` is invisible here, and that is a known hole, documented rather than
  hidden.

Shell files have no such distinction — every line that is not a comment is a line that runs — so
they get the simple treatment, and that asymmetry is the correct one rather than an inconsistency.

```bash
cd days/day-87-config-not-billed/lab
uv run python parked.py; echo "exit: $?"
```

**Line by line:**

- No flag: scan the lab's Python files, counting only strings that reach a process call.

Measured on 2026-09-07:

```text
scanning 5 file(s); counting: only strings that reach a process call
markers: adk deploy, agent_engines.create, aiplatform, gcloud, vertexai


  billable requirements found: 0
  the parked marker holds: everything here runs on an empty wallet
```

**Eleven to zero, and the zero is the true answer.** The day mentions the billable commands
constantly and runs none of them.

## When it breaks

The check has to still catch a real violation, or the fix has just been a way of making the alarm
quiet. So the day keeps one committed on purpose — a deploy script of the kind that ends up in a
repository because somebody wrote it once and it worked:

```bash
uv run python parked.py --sloppy; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  sloppy_deploy.sh:4  gcloud - the Cloud SDK, which needs an enabled project
  sloppy_deploy.sh:5  gcloud - the Cloud SDK, which needs an enabled project
  sloppy_deploy.sh:6  adk deploy - a deploy, which creates the resource above

  billable requirements found: 3
  this day is marked parked and would not run without a credit card
exit: 1
```

Three findings, all real, in one file, with line numbers. That is a report somebody acts on.

And the ablation keeps the failure visible rather than deleting it:

```bash
uv run python parked.py --grep; echo "exit: $?"
```

It reproduces the eleven false positives and exits 1 with the reason printed. Keeping the broken
version runnable is deliberate: the finding of this part is not "we fixed a bug", it is "the obvious
implementation of this check is unusable", and a reader should be able to see that for themselves
rather than take it on trust.

**What the fixed check still misses**, stated plainly:

- A command in a variable, assembled before the call.
- A billable action taken through a Python client rather than a subprocess — `client.agent_engines.create()`
  is caught by name here, but only because it is in the marker list.
- Anything in a notebook, a Makefile, or a CI configuration. This scans `.py` and one `.sh`.

Each of those is a real hole. They are listed because a security-shaped check that implies more
coverage than it has is worse than one that states its edges.

## In production

**What a professional does.** Tunes for precision before coverage on any check that runs constantly.
The first question about a new lint is not "what does it catch" but "how often will it be wrong",
because the second number determines whether the first one ever gets acted on. A check at ninety
percent false positives is not a partial success; it is a check that will be muted within a month.

**What degrades at scale.** Every scanner meets more code, and more code means more legitimate uses
of whatever it looks for. A rule that is precise across five files is noisy across five hundred, and
the usual response — an ever-growing list of suppressions — moves the problem rather than solving
it. The durable version narrows what counts as a hit, as this one did, rather than listing what to
ignore.

**The failure that only shows with real traffic.** The suppression that outlives its reason.
Somebody adds an exemption for a file that legitimately needed one, the file changes, and the
exemption stays — so the one place the check was disabled is the one place nobody is looking. This
is Day 82's quarantine finding in a different tool, and the mitigation is the same: exemptions carry
a date and expire.

**The review comment a senior engineer leaves:** *"Before this goes in CI, run it over the whole
repository and count the findings. If it is more than a handful and they are not real, it does not
go in — we will just be teaching everyone to ignore it."*

**The interview question:** *"Your static check has a lot of false positives. What do you do?"* The
answer that shows experience does not add suppressions and does not lower the severity. It narrows
the rule until the findings are real, accepts the coverage it loses, and writes down what it now
misses — because a precise check with known gaps is usable and a noisy one is not.

Three arms: eleven false positives, zero, three real ones. Say which two of those three exit `1`,
