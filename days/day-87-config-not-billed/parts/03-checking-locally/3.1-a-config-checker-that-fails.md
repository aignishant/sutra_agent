# 3.1 — A config checker that can go red

## One-line answer

The config file has no schema and the platform will accept whatever you send it, so the only thing
standing between a bad deployment and a good one is a checker you write yourself — and it is worth
writing precisely because it runs where the config is written rather than where it is applied.

## The story

The electrician who tests before switching on.

The new sockets are in, the wall is made good, and the board is still off. Before flipping the
breaker, the electrician goes round with a meter: continuity on each circuit, insulation
resistance, polarity at every outlet. It takes a while and nothing happens, which is the point.

If a live wire were touching a metal back box, there are two ways to find out. One of them is the
meter, on a dead circuit, in a quiet room. The other is the breaker, and it involves a bang and a
conversation with the homeowner.

Both find the fault. Only one of them finds it before it is a fault.

## The idea in plain language

Part [2.1](../02-the-config/2.1-the-config-file-adk-reads.md) established that
`.agent_engine_config.json` is loaded with `json.load` and nothing else. No schema, no required
keys, no validation. Whatever parses as JSON is accepted, and the platform on the far end is
similarly relaxed — it is designed to take a wide range of valid configurations, not to enforce
yours.

So the checking has to be yours, and there are exactly four things worth checking before a config
is handed to a deploy command:

| Check | Why it is worth a line of code |
| --- | --- |
| the required fields are there | `display_name` defaults to `""`, and a nameless resource is unfindable |
| no credential is written into the file | part [2.3](../02-the-config/2.3-your-env-travels.md); it travels, and it is one careless commit from being public |
| no model outside the free tier is named | Addendum 02, and part [3.2](3.2-the-zero-budget-lint.md) |
| the model is pinned at all | ADK-73; an unpinned model runs on whatever the default is that week |

Four checks is not many, and the smallness is the argument. This is not a schema validator; it is
the four things that have actually gone wrong, encoded so that they cannot go wrong quietly.

The important property is the one in the title: **it can go red.** Day 83's whole gate was built on
the observation that a check which cannot fail is decoration, and a config checker is unusually
prone to it — most configs are fine most of the time, so a checker written against a good config and
never tested against a bad one passes forever without ever having been a check.

## Why Sutra needs it

Because the checker is what makes this day non-hollow. Part
[1.2](../01-what-you-hand-over/1.2-why-this-day-is-parked.md) set the test: could a reader who has
done this day find something wrong in somebody else's deployment config? A list of things to watch
for is a hope. A script that exits 1 and names the key is an answer.

And because it is the one artefact from this day that survives into the product. The build brief
asks for `sutra/deploy.py` with a `validate` function, and it is the same four checks with the
repository's own settings behind them.

## The mechanism

The check for a credential in the file is deliberately shape-based rather than value-based:

```python
def secrets_in(config: dict) -> list[str]:
    """Env var names whose value is being carried in the config file itself."""
    env = config.get("env_vars") or {}
    return [k for k in env if any(marker.lower() in k.lower() for marker in FORBIDDEN_LITERALS)]
```

**Line by line:**

- It matches on the **name**, not the value. A credential detector that looks for high-entropy
  strings is cleverer and misses `SUTRA_DB_PASSWORD=hunter2`, which is exactly the kind of weak
  secret that ends up in a `.env` and exactly the kind that matters.
- `FORBIDDEN_LITERALS` is `("api_key", "GOOGLE_API_KEY", "password", "token", "secret")` — five
  substrings, case-insensitively. It will miss a key called `CREDS`, and that is a known and
  accepted hole rather than a hidden one.
- `config.get("env_vars") or {}` handles both a missing key and an explicit `null`. A config with
  no `env_vars` is legitimate and must not raise here.
- The function returns names, never values. A checker that prints the secret it found in order to
  complain about it has put the secret in a log.

And the report is assembled so that the exit code cannot disagree with the text:

```python
    print(f"\n  {len(findings)} finding(s)")
    if findings:
        for line in findings:
            print(f"    - {line}")
        print("\n  this config is not ready to hand to a deploy command")
        return 1
```

**Line by line:**

- One list, `findings`, appended to by every check. The count, the detail and the exit code are all
  derived from it, so there is no way to print zero findings and exit 1, or the reverse.
- The findings are printed *after* the count, so a reader who sees `0 finding(s)` has already seen
  the number before deciding whether to keep reading.
- `return 1` rather than `sys.exit` inside the function, so the script is importable — the build
  brief's `sutra/deploy.py` will want to call this from a test.

```bash
cd days/day-87-config-not-billed/lab
uv run python validate.py; echo "exit: $?"
```

**Line by line:**

- No flag: the config as somebody first writes it, which is the version with the key in it.

Measured on 2026-09-07:

```text
config: fixtures/.agent_engine_config.json
keys: description, display_name, env_vars

  display_name            present   an unnamed resource is unfindable in a console with forty of them
  description             present   the next person needs to know what this is without reading the code

  secret-shaped env vars carried in the file: 1
    - GOOGLE_API_KEY
  model strings this repository will not deploy: 0
  model pinned explicitly: gemini-2.5-flash-lite

  1 finding(s)
    - GOOGLE_API_KEY is a credential written into a file on disk

  this config is not ready to hand to a deploy command
exit: 1
```

One finding, named, with an exit code. That took a few milliseconds and no billing account, and the
alternative way to discover it is a key in a deployed resource's environment.

## When it breaks

The checker breaks by being written and never tested against something bad. This one has a second
fixture for that reason:

```bash
uv run python validate.py --fixed; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  secret-shaped env vars carried in the file: 0
  model strings this repository will not deploy: 0
  model pinned explicitly: gemini-2.5-flash-lite

  0 finding(s)
  nothing in this config would surprise a reviewer, and none of it has been deployed
exit: 0
```

Two fixtures, two exit codes. That pairing is the minimum for a check to be worth anything — the
same discipline Day 83's criterion 2 applied to the eval suite, with a config instead of a desk.

**What this checker does not catch** is more interesting than what it does, and there are three:

**A key called something unexpected.** `CREDS`, `AUTH`, `PRIVATE_KEY_ID` — the substring list is
five entries long and the space of names is not. This is a floor, not a ceiling.

**A wrong value in a right-shaped field.** `SUTRA_MODEL` set to a model that exists, is free, and is
not the one the desk was evaluated against. Every check here passes. Phase 12 spent four days
building the thing that would catch it, and nothing connects the two.

**Everything ADK adds.** Part [2.2](../02-the-config/2.2-what-the-cli-adds.md) counted three keys
reviewed against seven sent. The checker reads the file, and the file is not the document.

There is no error text for any of those, which is the honest summary of a config checker: it turns
four known failures into loud ones and leaves the unknown ones exactly where they were.

## In production

**What a professional does.** Runs the config check in the same job that runs the tests, on every
change to the config, and treats it as a blocking failure rather than a warning. The check lives
beside the config; a validator in a separate repository that has to be manually invoked is a
validator that is invoked after the incident.

**What degrades at scale.** Checks accumulate and stop being read. Four findings printed in full are
a report; forty are a wall, and the response to a wall is a flag that suppresses it. The mitigation
is to keep the checker small and specific — one entry per failure that has actually happened here —
rather than growing it towards a general-purpose schema validator, which is a different tool with a
different job.

**The failure that only shows with real traffic.** The config passes and the *environment* it will
run in does not match. A pinned model that this project has quota for and the production project
does not; a session service URI that resolves from a laptop and not from inside the platform's
network. Nothing local can check those, and the honest response is to say so in the checker's output
rather than to let a green run imply more than it measured.

**The review comment a senior engineer leaves:** *"Good. Now add the bad fixture to the test suite so
this check is exercised on every commit — right now it only goes red when somebody remembers to run
it with the broken file."*

**The interview question:** *"Your deployment config has no schema. What do you do?"* The answer that
shows experience does not reach for a schema language. It names the two or three failures that have
actually happened, writes a check for each, and — the part that separates it — keeps a deliberately
broken example so the check is proven to work.

## Check yourself

```bash
cd days/day-87-config-not-billed/lab
uv run python validate.py; echo "exit: $?"
uv run python validate.py --fixed; echo "exit: $?"
```

Now break the good fixture: open `fixtures/.agent_engine_config.fixed.json` and delete the
`SUTRA_MODEL` line. Predict which check fires and what the exit code becomes, run it, then put it
back.

Add a fifth check of your own to `validate.py` — that `adk_version` is pinned, which part
[1.3](../01-what-you-hand-over/1.3-reading-the-deploy-surface.md) argued for and neither fixture
has. Both fixtures should go red. Say why that is the correct outcome rather than a bug in your
check.

**Out loud, without scrolling up:** why does the secret check match on the variable's name instead
of its value, and what does that choice deliberately give up?
