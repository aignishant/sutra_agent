# 2.3 — 💥 Your .env travels

## One-line answer

The deploy path reads your `.env` with `dotenv_values`, which returns every key in it, and assigns
the whole dictionary to the config that is uploaded — so the one file this repository has kept out
of git since Day 0 is the file that goes to the platform in its entirety, including the database
password nobody remembered was in it.

## The story

💥 **The drawer you emptied into the box.**

🎬 **The scene.** Somebody is moving flats and doing it properly. Books boxed by shelf, kitchen
things wrapped, everything labelled. Then it is the last evening, the van comes in the morning, and
there is the drawer in the hall — the one with the spare keys, the old passport, three chargers, a
letter from the bank and about forty pence in coins.

😬 **The naive fix.** Tip the whole drawer into a box, tape it, write **HALL DRAWER** on the side.
It takes four seconds and nothing is lost.

💥 **Why it fails.** Nothing *is* lost. That is the problem. The box goes into a van, then into a
shared storage unit for a fortnight because the new place is not ready, and in that box is a
passport and a bank letter with an account number on it. The person was careful about the books and
completely uncareful about the only thing in the flat that mattered — because the careful decisions
were made per-item and the drawer was handled as a container.

💡 **The insight.** **The unit of care has to match the unit of risk.** Everything that got a
decision was safe. The thing that got moved as a bundle was the thing with the passport in it, and
it got moved as a bundle *because* nobody had ever looked inside it item by item.

## The idea in plain language

Principle 9 says secrets never touch git. This repository has followed it since Day 0: `.env` holds
the keys, `.gitignore` holds `.env`, and the repository can go public in Phase 14 without anybody
sweating.

That principle is about **git**. It says nothing about deployment, and the deploy path does this:

```text
env_file = os.path.join(agent_folder, '.env')
env_vars = dotenv_values(env_file)
agent_config['env_vars'] = env_vars
```

Three lines, read from the installed library. The `.env` beside the agent is found by default;
`dotenv_values` parses the whole file into a dictionary; the whole dictionary is assigned into the
config that gets uploaded.

There is no allowlist. There is no filter. There is no prompt. Every key in that file becomes an
environment variable set on the deployed resource — and the file was designed, from Day 0, to be the
place you put things you do not want anyone to see.

The specific irony is worth stating slowly: **the file that is gitignored precisely because it holds
secrets is the file that is uploaded without inspection.** The care taken over git is real and it
does not transfer, because the two mechanisms have nothing to do with each other and nobody wrote
the second one down.

## Why Sutra needs it

Because this repository's `.env` does not hold one key. Over eighty-odd days it has accumulated:
the Google key, the flag that keeps it off Vertex, a model pin, and whatever else was needed on the
day it was needed. Nobody has ever pruned it, because there was never a reason to — it is
gitignored, so its contents were nobody's business.

The moment a deploy path reads it, its contents become everybody's business.

And because Phase 14 makes the repository public. A day that teaches deployment without teaching
this would be teaching a route from a private file to a hosted resource, in a curriculum whose whole
security posture is that the private file stays private.

## The mechanism

The lab checks ADK's three lines against the installed source before it says anything about them,
so the claim goes red when ADK changes rather than going stale:

```python
SOURCE_CLAIMS = (
    ("the .env beside the agent is the default", "env_file = os.path.join(agent_folder, '.env')"),
    ("the whole file is read, key by key", "env_vars = dotenv_values(env_file)"),
    ("and the whole thing goes into the config", "agent_config['env_vars'] = env_vars"),
)
```

**Line by line:**

- Each entry is a sentence and the exact source substring that justifies it. A claim in a teaching
  document with its evidence attached is checkable; a claim without one is a memory.
- The substrings are matched against `CLI_DEPLOY_SRC`, which is `Path(cli_deploy.__file__).read_text()`
  — the file that is actually installed, not a copy in this repository.
- If any one is missing the script exits 1 saying so, which means this part cannot silently describe
  a version of ADK nobody runs.

And the leak itself is demonstrated with **the same function ADK uses**:

```python
    env = dict(dotenv_values(fixture(".env.sample")))
    shipped = {k: v for k, v in env.items() if k in NEEDED} if curated else env
```

**Line by line:**

- `dotenv_values` imported from `dotenv`, which is what `cli_deploy.py` imports. Reimplementing the
  parse would risk the demonstration disagreeing with the thing demonstrated.
- `fixture(".env.sample")` — a fixture, not the real `.env`. The lab must not read the learner's
  actual credentials to prove a point about credentials.
- `NEEDED` is the allowlist: the two variables the desk genuinely needs. Everything else is along
  for the ride, and the `--curated` arm is that sentence as code.

```bash
cd days/day-87-config-not-billed/lab
uv run python envleak.py; echo "exit: $?"
```

**Line by line:**

- No flag: the default behaviour, which is ADK's behaviour.

The desk does not need it — it is in the fixture because it is the kind of thing that ends up in a
`.env` and stays there. It travels anyway, because the selection rule is *the file*.

## When it breaks

It does not break. It works exactly as designed, and that is the whole of the finding: there is no
error text, no warning, and no line in the deploy output that lists what was uploaded. ADK prints
this and nothing more:

```text
Reading environment variables from <path>/.env
```

One line, naming the file, not its contents. Everything you would need in order to notice is
available and none of it is shown.

The fix is an allowlist, and it is small:

```bash
uv run python envleak.py --curated; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  .env holds 4 keys
  selection: an explicit allowlist
  variables that would be set on the deployed resource: 2

  key                         shipped   value
  GOOGLE_API_KEY              no        
  GOOGLE_GENAI_USE_VERTEXAI   yes       FALSE
  SUTRA_MODEL                 yes       gemi...
  SUTRA_DB_PASSWORD           no        

  secret-shaped keys among them: 0

  only what the desk needs travels, and the credentials stay where they were
exit: 0
```

Two keys instead of four, and the two that stayed behind are the two that mattered.

Two things that allowlist does **not** solve, and both belong in the same conversation:

**The desk still needs a key to call a model.** Moving `GOOGLE_API_KEY` out of the config does not
conjure credentials on the platform; it means they have to arrive some other way — a secret manager,
a platform-level binding, an identity the resource carries. Day 86 made exactly this argument about
containers and env-injected secrets, and the managed platform version of it is the same argument
with a different injection point.

**There is one more deploy flag in this neighbourhood** and it is worth knowing about. When
`--otel_to_cloud` is passed, the deploy path sets `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS` to `false`
unless you have already set it. That default is the right way round — conversation content does not
leave by accident — and it is a default, which means somebody can turn it the other way and ship
customer sentences to a trace backend. Day 84 configured the tracer; this is the flag that decides
what is in the spans once they are somebody else's.

## In production

**What a professional does.** Enumerates what leaves. Any step that moves configuration out of the
repository gets an explicit list of what is included, never a directory or a file treated as a
bundle — the same reason a `.dockerignore` exists and the same reason it is reviewed. The rule is
that bundles are for things you have looked inside.

**What degrades at scale.** `.env` files grow and nobody prunes them, because pruning has no
immediate benefit and a small risk of breaking something. After a year a `.env` is an archaeological
record of every integration anybody tried, and the deploy that uploads it wholesale uploads all of
it. The countermeasure is that the allowlist lives next to the deploy config and is reviewed when it
changes, which makes adding a variable a decision rather than an accident.

**The failure that only shows with real traffic.** The variable that was fine to ship and then was
not. A key rotates, a staging credential is replaced with a production one, a colleague adds
something to their local `.env` for an afternoon's debugging — and the next deploy from that machine
carries it. Nothing about the deployment changed; the file did, and the file is not in the diff
because the file is not in git.

**The review comment a senior engineer leaves:** *"We are shipping the whole `.env`. Put an explicit
allowlist in the deploy path and make the deploy print what it is sending — I want the variable
names in the log even if the values are masked."*

**The interview question:** *"How do secrets get to your deployed service?"* The answer that shows
experience names the path, and then names what *else* takes that path. Most people can describe how
the key gets there. Very few have checked what travels alongside it.
