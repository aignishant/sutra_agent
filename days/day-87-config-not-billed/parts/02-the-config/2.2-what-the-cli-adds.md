# 2.2 — What the CLI adds that you did not write

## One-line answer

The config you wrote is a starting point: before it is sent, ADK adds the source packages, an image
spec, a framework name, a generated Dockerfile and thirteen published methods — five of which are
deprecated the moment they arrive, including the one that runs the agent — so the resource you get
is described by a document you have only partly authored.

## The story

The form the clerk fills in beside you.

You hand over your details at a counter and the person behind it starts typing. They ask you four
things and type for considerably longer than four things take. Reference numbers, a category code,
a branch identifier, today's date, a flag that means something internal.

At the end they turn the screen round for a signature. What you are signing is your four answers
plus about fifteen fields you have never seen, all of them correct, all of them consequential, none
of them yours. Most people sign. The ones who read it discover that "category" was set to the
default and the default is not what they wanted.

## The idea in plain language

Part [2.1](2.1-the-config-file-adk-reads.md) showed ADK loading your JSON into a dictionary called
`agent_config`. What happens next is that the deploy path keeps writing to that dictionary. By the
time it is sent, five keys you did not write are in it.

**`source_packages`** — the agent's own directory, the generated Dockerfile, and anything staged
via `--extra_packages`. This is the answer to "what actually gets uploaded", and it is computed
rather than declared.

**`image_spec`** — set to an empty object, which is ADK's way of saying *use the Dockerfile*. An
empty dictionary carrying a decision is the kind of thing you only ever learn by reading source.

**`agent_framework`** — the string `google-adk`. Harmless, and it is the platform learning what it
is running, which is the shape of the trade from part
[1.1](../01-what-you-hand-over/1.1-what-you-hand-over.md).

**`env_vars`** — your environment, and part [2.3](2.3-your-env-travels.md) is entirely about this
one.

**`class_methods`** — the interface the deployed resource exposes to the world. Thirteen methods,
listed in ADK's source, and this is the one worth reading properly because it is the API your
deployment offers whether or not you wanted to offer it.

There is also a Dockerfile. ADK generates one and writes it into the working directory:

```text
Creating Dockerfile...
Dockerfile created at <cwd>/Dockerfile.
```

Day 86 wrote a Dockerfile deliberately, with decisions in it. This one is generated from a template
at deploy time, and it lands in whatever directory you happened to be standing in.

## Why Sutra needs it

Because "what gets deployed" has to be answerable before deploying, and half of the answer is not in
the file you wrote. A review of the config alone reviews the half you authored.

And because the thirteen published methods are a security surface. Day 68 was least-privilege tools
and Day 63 was approval gates; a deployment that publishes `async_delete_session` to anybody who can
reach the resource has made an access-control decision, and it made it by default.

## The mechanism

The five additions, from the installed `google/adk/cli/cli_deploy.py`, in the order they are
written:

```text
agent_config['source_packages'] = ['agents/<app>', 'Dockerfile', *staged_extra_packages]
agent_config['image_spec'] = {}  # Use the Dockerfile
agent_config['class_methods'] = _AGENT_ENGINE_CLASS_METHODS
agent_config['agent_framework'] = 'google-adk'
```

**Line by line:**

- `source_packages` is a list of paths relative to a staging directory ADK builds in a temporary
  folder. The Dockerfile in that list is the generated one, not one you wrote.
- `image_spec = {}` with the comment in the source itself. An empty object is meaningful here, which
  means an empty object is *not* an absent value, which is the kind of distinction that makes
  hand-editing a config risky.
- `class_methods` is assigned from a module-level constant, so it is identical for every agent
  deployed with this ADK version. It is not derived from your agent.
- `agent_framework` is a literal string. It is how the platform routes the request to the right
  runtime.

The lab reads the method list out of the installed library rather than transcribing it:

```python
CLASS_METHODS = [m["name"] for m in cli_deploy._AGENT_ENGINE_CLASS_METHODS]
```

**Line by line:**

- Reaching into a private constant, deliberately. The alternative is copying thirteen names into a
  document where they cannot go stale loudly, and Principle 8 prefers the version that breaks when
  ADK changes. Writing this part, a first pass pulled the names with a regex and got eleven; the
  library says thirteen, and the two it missed were the two that matter most in the list below.
- `m["name"]` — each entry is a full method descriptor with a JSON-schema parameter block; the name
  is what this part needs and the schema is what the platform needs.

All thirteen, in ADK's own order, with the deprecation read from each entry's own description.
Measured on 2026-09-07:

```text
get_session                       DEPRECATED
list_sessions                     DEPRECATED
create_session                    DEPRECATED
delete_session                    DEPRECATED
async_get_session
async_list_sessions
async_create_session
async_delete_session
async_add_session_to_memory
async_search_memory
stream_query                      DEPRECATED
async_stream_query
streaming_agent_run_with_events
```

Three things to take from that list.

**Five of the thirteen are deprecated on arrival.** Their descriptions in the source begin with the
word "Deprecated" — they are published anyway, because something out there calls them.

**Ten of the thirteen are about sessions and memory.** The deployed resource's interface is
overwhelmingly a session store with an agent attached. That tells you where the platform thinks its
value is, and it tells you what you are handing over.

**Three of them run the agent, and the famous one is deprecated.** `stream_query` is the name every
example uses, and it is marked deprecated in this version; `async_stream_query` and
`streaming_agent_run_with_events` are the replacements. A reader who learned this platform from a
tutorial written last year would build against the one entry point on that list that is on its way
out.

## When it breaks

The failure here is not an error; it is a review that reviewed the wrong document.

```bash
cd days/day-87-config-not-billed/lab
uv run python validate.py --fixed; echo "exit: $?"
```

**Line by line:**

- `--fixed` reads the config with the credential removed — the version that passes.

Measured on 2026-09-07:

```text
config: fixtures/.agent_engine_config.fixed.json
keys: description, display_name, env_vars

  display_name            present   an unnamed resource is unfindable in a console with forty of them
  description             present   the next person needs to know what this is without reading the code

  secret-shaped env vars carried in the file: 0
  model strings this repository will not deploy: 0
  model pinned explicitly: gemini-2.5-flash-lite

  0 finding(s)
  nothing in this config would surprise a reviewer, and none of it has been deployed
exit: 0
```

**Three keys reviewed. Seven in the document that gets sent.** The checker is honest about what it
looked at — it prints the keys — and a reader who does not notice that line will believe the whole
configuration has been approved.

That is the general shape of reviewing generated artefacts, and it has bitten this repository
before: Day 82 found ADK writing eval results into a directory this repository ignores. Same
pattern, different key. A tool that fills in fields on your behalf produces a document with two
authors and one signature.

There is no error text for it, and the smallest honest fix is a line in the checker's output saying
how many keys the deploy path will add — which is a `TODO(me)` in the hub rather than something this
lab does, because getting it right means tracking ADK's source across versions.

## In production

**What a professional does.** Reviews the *rendered* artefact, not the source of it. Every
infrastructure tool worth using can print what it is about to send — the plan, the manifest, the
diff — and the discipline is to look at that rather than at the inputs. Where a tool cannot print
it, the professional finds the code that assembles it and reads that once, which is what this part
is.

**What degrades at scale.** The generated portion grows faster than the authored portion. Your
config stays at half a dozen keys while the platform adds features, and after a few releases most of
what describes your deployment is template output. At that point the only review that means anything
is a diff between two rendered artefacts, which requires having kept the previous one — the same
argument Day 82 made about eval history.

**The failure that only shows with real traffic.** A published method somebody uses. `stream_query`
is the intended door; `async_delete_session` is a door too, and it is open. The first time this
matters is when a client that should only be asking questions deletes a session, and the access
model that would have prevented it was never written because nobody knew the method was published.

**The review comment a senior engineer leaves:** *"Before this goes anywhere, print the assembled
config and put it in the ticket. I want to see the thirteen methods we are exposing, hear why
`async_delete_session` is one of them, and confirm we are not calling the deprecated
`stream_query`."*

**The interview question:** *"What exactly gets deployed when you run that command?"* The answer that
shows experience distinguishes what they wrote from what the tool adds, and can name at least one
thing in the second category. Almost nobody can, and it is the difference between operating a tool
and understanding it.

```bash
cd days/day-87-config-not-billed/lab
uv run python -c "from _deploy import CLASS_METHODS; print(len(CLASS_METHODS)); print(CLASS_METHODS)"
```

Thirteen names, read out of the installed library. Sort them yourself into *the agent*, *session
management* and *deprecated*, then say which group you would want behind an access control — and
notice that the three groups overlap.

Now count the keys in `fixtures/.agent_engine_config.fixed.json` and the keys in the document that
