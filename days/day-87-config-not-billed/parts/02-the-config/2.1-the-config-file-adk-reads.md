# 2.1 — The config file ADK actually reads

## One-line answer

`.agent_engine_config.json`, sitting beside the agent, is the artefact this whole day is about: a
plain JSON file that ADK loads before it does anything, that flags then override, and that is
therefore the one place a deployment decision can be written down, reviewed and disagreed with
before it costs anything.

## The story

The packing list taped to the inside of the case.

Somebody in the house travels for work, and there is a laminated card inside the suitcase lid.
Charger, adaptor, the spare pair, the folder with the printouts. It is not a clever system. What it
does is move the thinking from the night before the trip, when the person is tired and hurrying, to
a quiet afternoon months ago when they were not.

The value is not that the list is comprehensive. It is that it exists as a *thing*, on the lid,
where somebody else in the house can look at it and say — you have not got the plug for the other
country on there.

A decision you can point at is a decision somebody can improve. A decision that lives in the moment
of packing gets made again, worse, every trip.

## The idea in plain language

ADK's deploy path reads a JSON file before it reads anything else. The lookup is exactly this: if
you pass `--agent_engine_config_file` it uses that path, and if you do not, it looks for
`.agent_engine_config.json` in the agent's own directory.

Whatever it finds becomes the starting dictionary. Flags passed on the command line are then merged
over the top — and ADK tells you when that happens, which is a small kindness worth noticing:

```text
Overriding display_name in agent platform config with <value>
```

So there are two places a deployment decision can live, and they behave differently:

| | The config file | A command-line flag |
| --- | --- | --- |
| where it lives | in the repository, beside the agent | in somebody's shell history |
| who can review it | anybody, before it runs | nobody |
| what a diff shows | the change and its reason | nothing |
| who wins | loses to the flag | overrides the file |

The flag wins the argument at run time. The file wins every other argument — the review, the
onboarding, the incident six months later when somebody asks why the session store is what it is.

That is the whole case for writing this day's config file even though nobody here will deploy it:
**the file is the reviewable artefact, and reviewing it is free.**

## Why Sutra needs it

Because the desk's deployment has to be a decision the repository records, not a command somebody
remembers. Principle 2 is one day, one commit, and a config file is committable in a way a shell
invocation is not.

And because of `--adk_version`. Part [1.3](../01-what-you-hand-over/1.3-reading-the-deploy-surface.md)
found its default is whatever ADK is installed on the machine that types the command. A pin in the
config file is the fix, and it is a fix that only exists if there is a file.

## The mechanism

The lookup, from the installed `google/adk/cli/cli_deploy.py`:

```text
if not agent_engine_config_file:
  agent_engine_config_file = os.path.join(agent_folder, '.agent_engine_config.json')
if os.path.exists(agent_engine_config_file):
  with open(agent_engine_config_file, 'r') as f:
    agent_config = json.load(f)
```

**Line by line:**

- The default path is built from `agent_folder`, so the file belongs to the agent rather than to the
  repository root. Two agents in one repository get two configs, which is right.
- `os.path.exists` and nothing else: **a missing config file is not an error.** The deploy proceeds
  with an empty dictionary and every value comes from flags and defaults. There is no warning, and a
  typo in the filename produces exactly the same silence.
- `json.load` — a plain JSON object, no schema, no validation. Anything you put in it that ADK does
  not recognise travels along quietly, which part [2.2](2.2-what-the-cli-adds.md) has more to say
  about.
- Note what is *not* here: no defaulting, no merge with a template, no required keys. The file is
  the whole starting state or there is no starting state.

Here is the desk's config as somebody first writes it:

```json
{
  "display_name": "sutra-desk",
  "description": "The refund desk: triage, lookup, escalate before any write.",
  "env_vars": {
    "GOOGLE_API_KEY": "AIzaSyD-notarealkey-000000000000000000000",
    "GOOGLE_GENAI_USE_VERTEXAI": "FALSE",
    "SUTRA_MODEL": "gemini-2.5-flash-lite"
  }
}
```

**Line by line:**

- `display_name` and `description` are the two fields whose absence costs you nothing on the day and
  everything in a month. The console lists resources by display name; a resource called `""` is
  findable only by its id.
- `env_vars` is the variables the deployed agent will see. Everything the desk needs to run has to
  be in here or come from the platform.
- `GOOGLE_API_KEY` written into the file is the defect, and it is the natural thing to write —
  the key is what the desk needs, so it goes where the desk's settings go. Part
  [3.1](../03-checking-locally/3.1-a-config-checker-that-fails.md) is the check that objects, and
  part [2.3](2.3-your-env-travels.md) is why the objection matters more than it looks.
- `GOOGLE_GENAI_USE_VERTEXAI` is `FALSE` because Addendum 02 says the free tier, not Vertex. It is a
  string, not a boolean, because that is how it is read from an environment.
- `SUTRA_MODEL` pinned explicitly to `gemini-2.5-flash-lite` rather than left to a default. That is
  ADK-73 and it has been the phase's refrain since Day 79.
- What is missing and should be here: `adk_version`. Nothing in ADK requires it, and without it the
  runtime is decided by whichever machine deploys.

## When it breaks

The file breaks by not being read, and there is no message when that happens. Three ways, all
silent:

**The filename is wrong.** `agent_engine_config.json` without the leading dot, or the file one
directory up. `os.path.exists` returns `False`, the deploy proceeds from an empty dictionary, and
every carefully reviewed value is replaced by a default. The resource comes up. It is simply not the
one you configured.

**The file is right and a flag overrides it.** This one at least announces itself, and the
announcement is easy to miss in a wall of deploy output:

```text
Overriding display_name in agent platform config with sutra-desk-test
```

**The file has a key ADK does not know.** No error. JSON has no schema here, so a misspelled key —
`display-name` for `display_name` — is carried along as an unrecognised entry and the real field
stays empty.

The general shape is worth naming because it recurs: **this file has no validator.** Every one of
those three failures is caught by reading, and none is caught by running. That is precisely the gap
part [3.1](../03-checking-locally/3.1-a-config-checker-that-fails.md) fills, and it is why a
checker you write yourself is not redundant with a platform that will happily accept the file.

## In production

**What a professional does.** Treats the deployment config as source code: reviewed, diffed,
required to change through a pull request, and validated in the same job that validates everything
else. The rule of thumb is that if a value can change what runs in production, its history should be
readable, and a shell command has no history anybody can read.

**What degrades at scale.** One config file is a document. Twenty are a directory in which they have
drifted apart, and the drift is invisible because each one is individually plausible. That is where
the pattern of one template plus per-agent overlays comes from — and where the second-order problem
of a template nobody reviews comes from too.

**The failure that only shows with real traffic.** The config was right and the *environment* it was
rendered from was not. A file containing `${PROJECT_ID}` interpolated by a pipeline is only as good
as the pipeline's variables, and a variable that is empty renders as an empty string rather than an
error. Everything downstream of that reads as configured and points nowhere.

**The review comment a senior engineer leaves:** *"Pin `adk_version` here, and take the API key out
of this file entirely — it is committed the moment somebody stops thinking about it, and the file
gets uploaded either way."*

**The interview question:** *"Where do your deployment settings live?"* The answer that shows
experience distinguishes settings that are reviewed from settings that are typed, and can say which
of theirs are which. Most systems have both and most teams have never separated them.

## Check yourself

```bash
cd days/day-87-config-not-billed/lab
cat fixtures/.agent_engine_config.json
uv run python validate.py; echo "exit: $?"
```

The checker finds one thing. Before you run it, predict what — and then say which of the three
silent failures in **When it breaks** it would *not* have caught.

Now rename `fixtures/.agent_engine_config.json` to drop the leading dot and re-run `validate.py`.
It ends in a `FileNotFoundError` naming the exact path it wanted — ugly, loud, and impossible to
miss. The real deploy path, given the same mistake, prints nothing and carries on. Say which of
those two behaviours you would rather have, and then rename the file back.

**Out loud, without scrolling up:** what happens when ADK cannot find the config file, and what
would you have to do to notice?
