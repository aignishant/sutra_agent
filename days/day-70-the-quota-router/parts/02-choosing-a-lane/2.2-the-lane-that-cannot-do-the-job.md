# 2.2 — The lane that cannot do the job

## One-line answer

A quota router is not a load balancer, because its servers are not interchangeable: the same fleet
offers four lanes for classification and only two for reasoning, so capability filters the set
*before* headroom ranks it.

## The story

Your child has a fever on a Sunday evening and you need a specific antibiotic that the doctor has
written down.

There are four shops open on the main road. The general store has a queue of nobody. The stationers
is empty too. The pharmacy has eleven people waiting and one person serving.

You join the pharmacy queue. Not because you have failed to notice the other queues, and not because
you enjoy waiting, but because the length of a queue is only worth comparing between places that can
sell you the thing. The general store's zero-minute wait is not an alternative. It is not on the same
list.

Nobody would need this explained. It becomes worth explaining when the queues are inside a program,
because a program will happily hand your prescription to the stationers if you sorted the shops by
waiting time and forgot to check what they sell.

## The idea in plain language

The standard load-balancing story assumes **interchangeable backends**: any server can serve any
request, so the only question is which is least busy. Almost every routing algorithm you will read
about assumes this, including the one in this day's paper.

Model providers are not interchangeable, and
[Day 9](../../../day-09-four-free-providers/parts/04-the-benchmark/4.3-three-shops-three-closing-times.md)
measured why. They differ in what they are good at, in context window, in whether they support tool
calling or structured output reliably, and in how they behave on long reasoning. A local Ollama model
that answers a classification well may be hopeless at drafting a customer reply.

So the router's decision has two stages that must not be merged:

1. **A hard filter.** Which lanes are *permitted* to serve this kind of request? This is a fact about
   capability, decided in advance, and no amount of headroom overrides it.
2. **A soft ranking.** Among those, which should be used now? This is the scheduling question from
   [2.1](2.1-headroom-is-not-a-preference.md).

The word for what stage 1 needs is a **skill** — a label naming a kind of work, attached both to the
request and to each lane. Sutra uses three: `classify`, `draft`, `reason`. They are deliberately
coarse. A taxonomy with thirty entries would be more precise and nobody would maintain it, and an
out-of-date capability table is worse than a coarse one because it is believed.

Making capability a hard filter has a consequence that feels wrong the first time: **the router will
refuse while lanes sit idle.** In [4.3](../04-when-a-lane-says-no/4.3-every-lane-dry.md) the fleet
runs out of reasoning capacity while Groq and Ollama are completely free. That is correct behaviour,
and [4.4](../04-when-a-lane-says-no/4.4-the-part-that-will-do.md) is what happens when you decide it
is not.

## Why Sutra needs it

Sutra's triage flow does three kinds of work with very different requirements. Classification is
short, structured and high-volume, so a fast cheap lane is ideal. Drafting a customer reply needs
fluency. The reasoning step — working out *why* a ticket looks like an earlier one — is the one that
genuinely needs a capable model.

The fleet reflects that, and the asymmetry is the whole point:

| Lane | `classify` | `draft` | `reason` |
| --- | --- | --- | --- |
| gemini | yes | yes | yes |
| groq | yes | yes | — |
| openrouter | yes | yes | yes |
| ollama | yes | — | — |

Four lanes for classification, three for drafting, **two** for reasoning. The scarcest work has the
fewest options, which is the usual shape and the reason a router that ignores capability looks fine
in testing: classification is most of the traffic, and for classification every lane really is
available.

## The mechanism

Capability lives on the lane as a set, and the test is one method:

```python
def can(self, skill: str) -> bool:
    """Whether this lane is allowed to answer this kind of request at all."""
    return skill in self.skills
```

**Line by line:**

- `skills` is a `frozenset`, so it is hashable and cannot be mutated after the lane is constructed. A
  capability table that some other part of the program can edit at runtime is a capability table you
  cannot reason about, and this is the cheapest possible way to prevent that.
- Membership on a set is constant time, which matters because this runs on every lane on every
  request — the innermost loop of the whole day.
- The word is `can`, not `should`. This method answers permission, never preference. Keeping those
  in different vocabulary is what stops them being merged later.

The fleet declares them where the lanes are declared, so the table above is a real object:

```python
Lane("gemini", "gemini-2.5-flash", 10, 250, frozenset({"classify", "draft", "reason"}), clock)
Lane("groq", "groq/llama-3.3-70b-versatile", 30, 1000, frozenset({"classify", "draft"}), clock)
Lane("openrouter", "openrouter/deepseek/deepseek-r1:free", 20, 50,
     frozenset({"classify", "draft", "reason"}), clock)
Lane("ollama", "ollama_chat/llama3.1:8b", 6, 100000, frozenset({"classify"}), clock)
```

**Line by line:**

- The OpenRouter string ends in `:free`, and it must. Addendum 02 makes this a hard rule — a missing
  `:free` suffix selects the paid variant of the same model and bills it — and Day 31's lint enforces
  it repo-wide. This is the one place in the day where a typo costs money rather than quota.
- Ollama has `100000` as a daily ceiling, which is not a real limit: it runs on your own machine and
  the constraint is hardware, not quota. A very large number is more honest here than `None`, because
  it keeps `headroom()` returning an `int` and keeps the comparison in
  [1.5](../01-what-headroom-is/1.5-twelve-left-means-two-different-things.md) working without a
  special case. Its `rpm` of 6 is the real constraint and reflects throughput on a laptop.
- Ollama is `classify` only. That is a judgement about an 8B local model's drafting, and it is
  exactly the kind of entry that should be revisited when the model changes — which is why it lives
  in one visible place rather than being implied by an `if` somewhere.
- Gemini and OpenRouter are the only lanes carrying `reason`, which is what makes them the pair that
  [1.4](../01-what-headroom-is/1.4-two-windows-and-the-one-that-bites-last.md) fights over.

Ask the fleet what it can do:

```bash
cd days/day-70-the-quota-router/lab
uv run python headroom.py --arrivals
```

**Line by line:**

- `--arrivals` describes the workload rather than running it, and prints which lanes are eligible for
  each skill by calling `can` on a fresh fleet.

Measured on 2026-09-06:

```text
270 requests from 170 tickets over 300s
  classify   170   lanes that can do it: gemini, groq, openrouter, ollama
  draft       85   lanes that can do it: gemini, groq, openrouter
  reason      15   lanes that can do it: gemini, openrouter
```

Note the inversion, because it is the reason this is a real constraint rather than a formality. The
work with the **most** volume has the **most** options; the work with the least volume has the
fewest. Fifteen reasoning calls out of 270 sounds negligible, and those fifteen are competing for a
pair of lanes that the other 255 requests are also allowed to use.

## When it breaks

Skip the filter and the failure is not an exception — it is an answer:

```python
from _lane import Clock, fleet

clock = Clock(0.0)
lanes = fleet(clock)
roomiest = max(lanes, key=lambda ln: ln.headroom())
print("roomiest lane:", roomiest.name)
print("can it reason?", roomiest.can("reason"))
```

**Line by line:**

- `max` on headroom alone is the load-balancer instinct: the roomiest lane wins.
- Note which lane that turns out to be, and why it is not the one you would guess. Ollama has the
  largest *daily* allowance by far, but `headroom()` is `min(minute, day)` from
  [1.1](../01-what-headroom-is/1.1-a-ceiling-is-a-window-not-a-number.md), and Ollama's six per
  minute is the tightest ceiling in the fleet. The minimum is what ranks it, so the winner is Groq
  on thirty a minute.
- Groq cannot reason. Nothing here raises; the router would simply send the request.

Measured on 2026-09-06:

```text
roomiest lane: groq
can it reason? False
```

The roomiest lane in the fleet is the one that cannot do the hardest job — and it is not the local
model you might have expected to be the odd one out, it is the fastest cloud provider Sutra has. A
router sorted on headroom alone sends **every** reasoning request to it and reports complete success,
because a wrong answer and a right answer are the same shape.

That is worth stating as the general rule: **capability failures are silent.** Quota failures announce
themselves with a `429`; capability failures come back as text, and the only thing that catches them
is an eval.

## In production

**What a professional writes instead.** The capability table is data, not code — usually YAML or a
database row — with a column for who last verified each entry and when. It gets versioned, and it
gets a test that fails when a lane is used for a skill it does not declare. Some teams go further and
attach the *evidence*: the benchmark run and date that justified the entry, so that a claim like
"ollama cannot draft" can be re-checked rather than inherited.

**What degrades at scale.** Capability is not binary in reality, and pretending it is has a cost. A
model may handle eighty per cent of drafts well and fail on the long ones. Mature systems replace the
boolean with a **tier** and route by difficulty as well as kind, which means the request now needs a
difficulty estimate, which is itself a model call. That tradeoff — spend a call to route better, or
route worse for free — is a real one, and on a free tier the answer is usually to route worse.

**The failure that only appears with real traffic.** Capability drift. The table is written once,
correctly, and then a provider silently swaps the model behind a name, or deprecates it, or your
prompts grow past a context window. Nothing in the router notices, because `can()` returns `True`
exactly as it always did. The only defence is an eval that runs the real skills against the real
lanes on a schedule.

**The review comment a senior engineer leaves:** *"`skills` is a set literal in the fleet
constructor, so the only record of why Ollama cannot draft is that somebody typed it. Move this to
config with a `verified_on` date and add a nightly eval that actually asks each lane to do each
skill. Otherwise we will find out it is wrong from a customer."*

**The interview question:** *"Why can't you just load-balance across model providers?"* The answer
that shows you have built one: *"Because the backends are not interchangeable, which is the
assumption every load-balancing algorithm makes. My fleet has four providers that can classify, three
that can draft and two that can do the reasoning step, so capability has to filter the candidate set
before any availability ranking happens. If you rank on headroom first, the most attractive lane is
the local model with an effectively unlimited allowance, and it is the one least able to do the hard
job — and it will not error, it will just answer badly. Quota failures are loud, capability failures
are silent."*
