# 6.1 — One till, two cashiers

## One-line answer

Run the router in two workers and each one stays comfortably inside the limit it can see — **13 and
13 against a ceiling of 20** — while the provider counts the sum and refuses the last six, because
the allowance is shared and the counters are not.

## The story

A market stall on a Saturday. Two people are serving from one cash box: the owner and her nephew,
who has come to help because it is busy.

They are both careful. Each of them keeps a running total in their head of what they have taken out
of the box for change — the owner because she has done this for years, the nephew because she told
him to. Neither of them is being sloppy, and if you asked either one at four o'clock how much change
they had given out, both would tell you a number and both numbers would be right.

At six they cash up and there is not enough left for the float. Not because anyone took anything, and
not because either total was wrong. There was one box and two people counting, and nobody was
counting the box.

## The idea in plain language

Part [5.2](../05-failure-lab/5.2-the-counter-that-starts-full.md) showed the router's headroom
disappearing across the *time* axis — a restart hands it a full allowance while the provider's
window has not moved. This part is the same root cause on the other axis: **more than one process**.

The root cause is one sentence: **the router's counter lives in the process, and the allowance does
not.** A second worker is a second counter over the same allowance, and neither can see the other.

That is worth stating carefully, because the failure has a property that makes it hard to find. Each
worker is *correct*. Each one reads its own headroom honestly, applies part
[2.1](../02-choosing-a-lane/2.1-headroom-is-not-a-preference.md)'s rule honestly, and stays inside the
ceiling it knows about. There is no bug in either. The arithmetic is wrong only in a place neither of
them is looking, which is the sum — and the provider is the only party that computes it.

Everything the day has built so far assumed one router. Section 1's windows, section 2's choice,
section 3's plugin, section 4's cold lanes: all of it is correct for a single process holding all
four counters, and part [2.3](../02-choosing-a-lane/2.3-with-perfect-information-greedy-is-fine.md)
was explicit that greedy routing is fine **given perfect information**. Two workers is the moment
that condition stops holding.

## Why Sutra needs it

Because one worker is the development configuration and not the deployed one. The moment the desk
runs behind anything that scales — two containers, a worker pool, a restart overlapping with the
process it replaces — the router is replicated and the allowance is not.

It is also the condition part
[2.4](../02-choosing-a-lane/2.4-everyone-read-the-same-board.md) was pointing at from the other
direction. That part taught the shared board and the herd that reads it; the question it left open was
what has to be true before sampling two lanes is worth anything instead of choosing the best. The
answer is here: **sampling two only earns its place once complete information is unavailable**, and
this is the deployment that makes it unavailable. The paper this day ends with is about exactly that
condition.

## The mechanism

There is no lab script for this one, because the whole point is a configuration rather than an
algorithm: two routers, one allowance. Build it from the modules the day already has.

```bash
cd days/day-70-the-quota-router/lab
uv run python -c "
from _lane import Clock, Refused, fleet
from _router import Router

clock = Clock(0.0)
workers = {'A': Router(lanes=fleet(clock), clock=clock), 'B': Router(lanes=fleet(clock), clock=clock)}
provider = {}

for _ in range(30):
    for router in workers.values():
        lane = router.choose('classify')
        if lane is None:
            continue
        provider[lane.name] = provider.get(lane.name, 0) + 1
        try:
            lane.call()
        except Refused:
            pass

limits = {ln.name: ln.rpm for ln in fleet(clock)}
print(f'  {\"lane\":<12}{\"limit/min\":>10}{\"A sent\":>8}{\"B sent\":>8}{\"provider saw\":>14}{\"over\":>6}')
for name in sorted(provider):
    a = workers['A'].spread().get(name, 0)
    b = workers['B'].spread().get(name, 0)
    over = max(provider[name] - limits[name], 0)
    print(f'  {name:<12}{limits[name]:>10}{a:>8}{b:>8}{provider[name]:>14}{over:>6}')
print()
print('  each worker stayed inside the limit it could see; the provider saw the sum')
"
```

**Line by line:**

- `clock = Clock(0.0)` and then **one** clock passed to both routers. That is what makes this two
  workers rather than two days: the windows are the same windows, moving at the same rate, so the
  minute both workers are spending is the same minute.
- `Router(lanes=fleet(clock), ...)` is called **twice**, and `fleet()` builds fresh `Lane` objects each
  time. Two fleets is exactly the deployment being modelled — each process constructs its own lanes at
  start-up, so each gets its own `Sliding` counters. Nothing is shared but the clock.
- `provider[lane.name] = ...` is the counter neither worker has. It is incremented outside both
  routers, before the call, because it stands in for the provider's own meter — and the provider counts
  the request when it arrives, not when it succeeds, which is part
  [5.1](../05-failure-lab/5.1-the-tally-that-counts-only-sales.md)'s rule.
- `router.choose('classify')` rather than `router.send(...)`: the demonstration needs the lane the
  router picked so it can be attributed to the provider's tally, and `choose` returns it. `None` means
  this worker's own view says there is no headroom, and it is skipped.
- `except Refused: pass` swallows the refusal deliberately, because the refusals are not the finding
  here — the **counts** are. A refusal in this run is the provider telling one of the workers what the
  table is about to show.
- `router.spread()` is the router's own record of what it sent, per lane. Printing A's and B's side by
  side against the provider's total is the entire argument in one row.

Measured on 2026-09-06:

```text
  lane         limit/min  A sent  B sent  provider saw  over
  gemini              10       4       4             8     0
  groq                30      13      13            26     0
  openrouter          20      13      13            26     6

  each worker stayed inside the limit it could see; the provider saw the sum
```

Read the `openrouter` row across. The limit is 20 a minute. Worker A sent 13, which is inside it.
Worker B sent 13, which is inside it. The provider saw 26, and **six of those requests were over the
line**.

Neither worker did anything wrong, and this is the part that makes the bug expensive to diagnose. If
you go to worker A's logs after the incident, they show 13 requests against a limit of 20 and a
router behaving correctly. Worker B's logs show the same. The only place the problem exists is in a
sum that nothing in your system computes, and the only party that computes it answers with a 429 and
no explanation of why it disagrees with you.

Note also the two rows that are fine, because they say something about how this failure surfaces.
`groq` has a limit of 30 and took 26 — over-provisioned enough to absorb the doubling. `gemini` has
the tightest ceiling at 10 and took only 8, because both routers correctly avoided it. **The lane
that breaks is not the tightest one; it is the one with the most headroom**, because that is where a
headroom-seeking router sends, and two of them send there twice as hard.

## When it breaks

The obvious fix is to divide the allowance: two workers, so give each one half. It works, it is one
line, and it is worth understanding exactly what it costs before reaching for it.

Half the allowance each means neither worker can ever use the other's idle share. On bursty traffic —
which is what a support desk has — one worker is busy while the other is quiet, and the busy one now
refuses at half the real ceiling. You have traded an overshoot for a lower effective limit, and the
loss is proportional to how uneven the load is.

It also breaks when the number of workers changes, which it does silently: an autoscaler adds a third
worker and each one's static share is now wrong in the other direction. Static division needs to know
the worker count, and the worker count is exactly the sort of thing that changes without anybody
editing a config file.

So the honest ladder of options, cheapest first:

| Approach | What it costs | When it is right |
| --- | --- | --- |
| **Static division** | idle share is unusable; breaks on scaling | fixed worker count, even load |
| **Shared counter** (one store both workers read and write) | a network round trip per decision, and a new dependency on the critical path | the general answer |
| **Lease a block** (each worker takes 5 from the shared store, spends locally, takes more) | some allowance stranded in an idle worker's lease | high request rates, where a round trip per call is too slow |
| **Read the provider's own remaining-quota headers** | only works if the provider sends them | always worth doing *as well* |

The last row is the one to notice, and part
[5.2](../05-failure-lab/5.2-the-counter-that-starts-full.md) made the same point about restarts: every
counter you keep is an estimate of a number the provider already knows. Where the provider tells you
what is left, that reading beats any arithmetic you do — and it is the only source that is correct
across workers, restarts and everything else you did not think of.

## In production

**What degrades at scale.** The overshoot grows with the worker count and the failure gets *quieter*,
not louder. With two workers the sum is double and something visibly breaks. With twelve workers each
one is sending a twelfth of the traffic, comfortably inside every limit it can see, and the 429 rate
becomes a steady low percentage that reads as provider flakiness. Teams live with that for a long
time, because a small constant error rate looks like weather rather than like a bug.

**The failure mode that only appears with real traffic.** Deploys. A rolling restart runs old and new
workers at once, so the effective worker count is briefly higher than the configured one — and if you
divided the allowance statically by the configured count, every deploy overshoots. It also lands
exactly where part 5.2's restart bug lands, so a deploy produces both symptoms at once: fresh counters
*and* extra workers. That is the moment worth setting an alert for, and it is the moment nobody is
watching quota because they are watching the deploy.

**What a professional does first, before any of the ladder above.** They find out what the pool
actually is. Part [5.3](../05-failure-lab/5.3-two-cards-one-household.md) established that the limit
attaches to a project, an organization or an account rather than to a model — and if two workers use
two different projects, this problem does not exist for them and a shared counter would be the wrong
fix. The question *what is the pool key, and how many processes share it* has to be answered before
choosing a mechanism, and it is answered by reading the provider's page rather than by inspecting your
own deployment.

**The review comment a senior engineer leaves:** *"The router is correct for one process and we run
four. Before we build a shared counter, two things: confirm the pool key from the provider's docs so
we know these four actually share an allowance, and check whether the responses carry
remaining-quota headers — if they do, reading them is better than anything we compute, and it fixes
the restart case for free. If we do need a counter, I'd rather lease blocks than do a round trip per
decision; put the lease size in config and log the stranded share so we can see what it costs."*

**The interview question:** *"Your rate limiter works in testing and you get 429s in production. What
happened?"* An honest answer: *"Almost always that the limiter is per process and the limit is per
account. I've measured it: two workers each stayed inside a ceiling of twenty — thirteen requests each
— and the provider counted twenty-six and refused six. The uncomfortable part is that neither worker is
wrong, so neither one's logs show anything, and the only party computing the sum is the one sending
you 429s. The lane it breaks on is the one with the most headroom, not the tightest, because that is
where a headroom-seeking router sends. The fixes go: read the provider's remaining-quota headers if
they send them, because that beats any counter you keep and also fixes restarts; otherwise a shared
counter, or leased blocks if a round trip per call is too slow. Static division works and quietly
costs you the idle worker's share, and it breaks the moment an autoscaler changes the worker count."*
