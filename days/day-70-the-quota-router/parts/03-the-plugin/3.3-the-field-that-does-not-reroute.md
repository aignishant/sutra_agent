# 3.3 — The field that does not reroute

## One-line answer

`llm_request.model` looks like the field that picks the provider, so rewriting it in a plugin looks
like a two-line router — and it is not one: the model **object** was bound to the agent before the
request existed, the field is data that object *receives*, and changing it changes what the model is
told rather than which model is asked.

## The story

You leave a pair of trousers at the tailor's to be taken in at the waist.

He writes a slip and pins it to the bundle: what has to be done, and a box near the bottom for which
table does the work. There are two tables in the shop. The one by the counter takes hems and buttons.
The one at the back has the heavy machine that can handle a waistband.

Your bundle is sitting on the front table, because the front table is where the counter is and that
is where he put it down.

You lean over and change the slip. You cross out *front* and write *back*, because the job needs the
heavy machine and you want it done properly. He nods. The slip now says back table.

Your trousers do not move.

The front table does the work. Somebody there reads the slip — reads it properly, reads the word
*back* — and does the job anyway, because the bundle is on their table and the slip is a piece of
paper. You collect the trousers with your own slip still pinned on, saying *back table*, in your own
handwriting.

Nothing about the paperwork is wrong. If somebody came in the following week and audited every slip
in the shop, every slip would say the right thing.

## The idea in plain language

Here is the two-line router that everybody writes first, and it is a completely reasonable thing to
write. You are inside `before_model_callback`. You have `llm_request` in your hand. It has a field
called `model` on it. Set the field, and surely the request goes to that model.

The reason it does not is that there are two different things wearing the same word.

- **The model object** is a live thing: a class instance with a client, credentials, a base URL and
  a quota pool behind it. It is what actually performs the call. In ADK it is a `BaseLlm`.
- **The model field on the request** is a **string**. It is one of the things the runtime fills into
  the request before handing it over, and it exists so the object it is handed to knows which of its
  own model names to ask for.

The field is downstream of the object, and you can read that in the source of google-adk 2.7.1
rather than take it on trust. In `google/adk/flows/llm_flows/basic.py`, where the request is first
populated:

```
model = agent.canonical_model
llm_request.model = model.model
```

The object is fetched from the agent, and the field is then **copied out of the object**. So the
sequence is: agent holds an object, runtime asks the agent for the object, runtime writes the
object's own name into the request, runtime calls the object. A plugin that edits the field is
editing a copy that was made from the thing it wants to replace.

`agent.canonical_model` is the binding, and it is in `google/adk/agents/llm_agent.py`: if the agent's
`model` is already a `BaseLlm` instance it *is* the object, and if it is a string it is resolved once
through the model registry and cached on the agent. Either way the answer is decided by the agent,
before any request exists, and nothing on the request can change it.

This is the fourth time this day has met the same shape and it is worth naming, because it is the
whole reason section 3 exists. A configuration value that was read once cannot be argued with later.
[2.1](../02-choosing-a-lane/2.1-headroom-is-not-a-preference.md) said it about the model name in an
agent constructor; [3.1](3.1-where-a-router-has-to-stand.md) said it about where a scheduler must
stand; this part says it about the one field that looks like an exception and is not.

## Why Sutra needs it

If rewriting the field worked, Sutra would not need a `Router` object at all. The plugin would
compute a lane name, assign it, return `None`, and the runtime would do the rest. Section 2's whole
policy would collapse into one line, and this day would be four parts long.

It does not work, and the consequence is structural rather than cosmetic: **the router has to hold
the lane objects itself**. That is why `lab/_router.py` keeps a `list[Lane]` and calls `lane.call()`
directly, and why [3.2](3.2-observe-block-answer-instead.md)'s "answer instead" is the only outcome
that can serve. A router that cannot make the call cannot route.

There is a second reason, and it is the one that bites later. This is a bug that **passes**. Nothing
crashes, no exception is raised, the field really does change, and the run really does produce an
answer. It ships. [5.1](../05-failure-lab/5.1-the-tally-that-counts-only-sales.md) is about a counter
that lies; this is about a *decision* that lies, and it lies in the direction that matters most,
because the lane the router believes it protected is the lane that has been spending all along.

## The mechanism

`lab/modelfield.py` does exactly what the naive router would do, and then measures which object
served the call. The hook it uses is the one <https://adk.dev/plugins/> documents, checked on
2026-09-06; the binding it fails to override is read from the installed google-adk 2.7.1 source,
quoted above. Here is the whole plugin:

```python
class Rewriter(BasePlugin):
    """Sets `llm_request.model` to another lane, the way a naive router would."""

    def __init__(self, target: str) -> None:
        super().__init__(name="rewriter")
        self.target = target
        self.saw: list[str] = []

    async def before_model_callback(
        self, *, callback_context: CallbackContext, llm_request: LlmRequest
    ) -> LlmResponse | None:
        self.saw.append(llm_request.model or "<unset>")
        llm_request.model = self.target
        return None
```

**Line by line:**

- `self.saw.append(llm_request.model or "<unset>")` records the value **before** the rewrite, on the
  way in. Without this line the experiment could not tell "the runtime never set the field" apart
  from "the runtime set it and my change was overwritten", and those are different bugs with
  different fixes.
- `or "<unset>"` covers the case where the field arrives as `None`. It does not, in this run, and
  the output proves it — but a measurement that would silently print `None` and let you read it as
  an empty answer is not a measurement.
- `llm_request.model = self.target` is the naive router, complete. One assignment. This is the line
  the whole part is about.
- `return None` is the *edit* outcome from [3.2](3.2-observe-block-answer-instead.md): mutate the
  request, hand back nothing, and the edited request is what goes. The plugin is deliberately not
  using the third outcome here — the point is to find out whether the second one is enough.
- There is no `try` and no validation. `llm_request.model` is an ordinary attribute and assigning to
  it is an ordinary assignment: nothing in the runtime is watching it, which is exactly why this
  looks like it works.

The fake model in `lab/_fake.py` prints the field it was handed alongside its own identity, and that
pairing is the whole experiment:

```python
        text = f"answered by {self.lane} (llm_request.model={llm_request.model!r})"
```

**Line by line:**

- `self.lane` is a property of the **object** — set when the model instance was constructed and never
  touched again. It answers *who did the work*.
- `llm_request.model` is read from the **request** the object was just handed. It answers *what the
  paperwork said*.
- `!r` prints the repr, so an empty string, `None` and the string `'None'` are all distinguishable.
- Printing both in one line, from inside the call, is what makes this evidence rather than
  inference. Nothing outside the model is being asked to report on what the model did.

Run it:

```bash
cd days/day-70-the-quota-router/lab
uv run python modelfield.py
```

**Line by line:**

- No flags. The plugin rewrites the field on every model call, and the script prints the four facts
  that have to be compared: what the agent was built on, what the plugin wrote, what the field held
  on entry, and which object answered.

Measured on 2026-09-06:

```text
the agent was built on lane   : gemini
the plugin rewrote model to   : fake/groq
llm_request.model on entry    : ['fake/gemini']

lane that actually answered   : ['gemini']

  model saw -> answered by gemini (llm_request.model='fake/groq')

rerouted by setting the field : False
```

The single most important line in this day is the sixth one.

```text
  model saw -> answered by gemini (llm_request.model='fake/groq')
```

Read it slowly, because it is saying two things at once and both of them are true.

**The field really did change.** The value that reached the model is `'fake/groq'` — not
`'fake/gemini'`, not `None`, not an error. The assignment was not ignored, not overwritten, not
rejected. The plugin did precisely what it set out to do.

**And gemini really did answer.** The report is printed from inside the gemini model object, by the
gemini model object, about itself.

So the rewrite worked and the reroute did not, and there is no contradiction between those two
sentences once you have separated the object from the field. The gemini object read the slip that
said `fake/groq`, and did the work, because the bundle was on its table.

The third line is the control. `llm_request.model on entry: ['fake/gemini']` proves the runtime had
already filled the field in from the agent's own model before the hook ran — which is
`llm_request.model = model.model` from `basic.py`, observed from the outside. One entry in the list
also means the hook ran exactly once, so no second call quietly reset anything.

`rerouted by setting the field: False` is the script comparing `NamedLlm.answered` to `["groq"]` and
finding they differ. It is one boolean, and it is the answer to the question in the file's docstring.

## When it breaks

The break is not a traceback. There is no traceback anywhere in this part, and that is the subject.

**This bug passes every unit test you would think to write.** Sit down to test the naive router and
you write, honestly and in good faith, a test that builds an `LlmRequest`, awaits the hook, and
finishes with `assert llm_request.model == "fake/groq"`.

That test passes. It will pass forever, on every version of the framework, because what it is
actually checking is that a Python attribute assignment assigned. The assertion is on the field
because the field is what the code under test touches, and testing what the code touches is what
everybody is taught to do.

What the test never asks is **which object served the call** — and it does not ask because asking is
expensive. Answering that question needs a Runner, an agent, a model that reports its own identity,
and a run to observe it in. That is the entire apparatus `lab/_fake.py` exists to provide, and nobody
builds it for a one-line change.

So this is the honest reason the mistake survives code review. The diff is one line, the test is
green, the field really is set, and the only thing that could have caught it is a measurement no one
had a reason to take.

There is one narrow case where rewriting the field does something, and it is worth knowing so you can
say why it does not rescue the idea. Read `google/adk/models/google_llm.py` in google-adk 2.7.1 and
the Gemini class takes the model id it sends from `llm_request.model`. So rewriting the field can
change *which model name is asked for within one provider's client* — this lab does not measure that,
and it is a source reading rather than a result. It still does not reroute anything, because the
client, the credentials and the quota pool all belong to the object, and the object is the agent's.
For a quota router that is the end of the matter: [1.1](../01-what-headroom-is/1.1-a-ceiling-is-a-window-not-a-number.md)
established that free tiers meter the **pool**, so a "different model" inside the same pool has
exactly the same headroom as the one you were trying to escape.

## In production

**How you would detect this in a real deployment.** Attribute every response to the thing that
produced it, never to the request that asked for it. That means the identity in your log line comes
back from the call — the object that served it, the endpoint that was hit, the account the bill lands
on — rather than being read off the request you built beforehand. The two agree in a system with no
router, which is why nobody notices the difference until there is one, and by then every dashboard in
the building is drawing the wrong picture. The concrete test is one line in the log: if you cannot
tell from your own telemetry which provider served a given turn *without* consulting the code that
built the request, you cannot detect this class of bug at all.

**Why a router must hold the lane objects itself.** Once the field is ruled out, only one shape is
left. The router owns a list of lane objects, it chooses one, it calls that one, and it returns the
result through [3.2](3.2-observe-block-answer-instead.md)'s third outcome. That is not an
implementation preference, it is what the mechanism above forces. It also has a consequence people
find surprising and should not: the router now owns retries, timeouts, error mapping and the `429`
handling for the lane it called, because it made the call, and nothing in the framework is in that
path any more. Section 4 is that bill arriving.

**What degrades at scale.** Nothing about this changes with load, which is precisely what makes it
expensive. A bug that degrades under traffic gets found in a load test. This one behaves identically
at one request and at a million: the field is set, the wrong lane serves, and the system's reports
are consistent with each other and wrong. It is found when a provider bill or a quota page disagrees
with the dashboard — that is, from outside the system, by someone who is not looking for it.

**The review comment a senior engineer leaves:** *"This sets `llm_request.model` and returns `None`,
which sets a string on a request that was already built from the agent's own model object. The call
still goes to whatever the agent was constructed with. Add a test that runs a real Runner with two
model objects that report their own identity and assert on which one answered — if that test is hard
to write, that is the finding, not an excuse."*

**The interview question:** *"You want your framework to send a request to a different provider than
the agent was configured with. What is the first thing you would try, and what is wrong with it?"* An
answer that has measured it: *"The first thing I tried was rewriting the model field on the request
inside a plugin hook, because it is one line and it looks like the field that selects the provider.
It is not. The runtime copies that field out of the agent's model object before the hook runs, and
then calls the object — so my change altered what the model was told and not which model was asked. I
only caught it because I ran it with two model objects that each report their own identity: the field
said one thing and the other one answered. The uncomfortable part is that the obvious unit test —
assert the field was set — passes, so nothing but an end-to-end measurement finds it."*
