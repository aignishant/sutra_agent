# 1.3 — The counter that remembers when

## One-line answer

Storing the **time of each request** instead of a running total turns the boundary burst from twenty
requests into ten, because a limiter that knows when things happened can answer questions about any
span rather than only about the span it happens to be in.

## The story

The security desk in an office building keeps a register. Every visitor writes their name and the
time they came in, and signs out on the way past at the end.

There is a fire rule: no more than forty visitors in the building at once. The guard does not keep a
tally on a scrap of paper that he clears at shift change. He keeps the register, and when he needs to
know how many people are inside he runs his finger down the page and counts the rows that have an
entry time and no exit time.

It is more work than a tally. He is reading a list instead of glancing at a number. What he gets for
that work is that the question "how many are inside **now**" has a real answer at every instant, and
it does not matter when his shift started or whether the previous guard cleared anything.

A tally answers *how many since I last reset*. The register answers *how many right now*, and those
are only the same question if nobody ever resets at an awkward moment.

## The idea in plain language

The structure is called a **sliding window log**. Instead of a count, keep the timestamp of every
request in the current span. To answer "how much headroom", first throw away the timestamps that
have aged out, then subtract what is left from the limit.

The rule it enforces is the rule you meant in
[1.1](1.1-a-ceiling-is-a-window-not-a-number.md): *no span of sixty seconds contains more than ten
requests*. It enforces it at every instant, not at boundaries, because there are no boundaries any
more. The window's edge is always "sixty seconds before now", and "now" moves continuously — which
is what "sliding" means.

The costs are honest and worth naming:

1. **Memory is proportional to the limit**, not to traffic. Ten per minute means at most ten
   timestamps. A thousand per day means at most a thousand. For free-tier ceilings this is nothing.
   For a limit of a million per minute it is not nothing, which is why large systems use the
   approximation named in [1.2](1.2-the-burst-every-counter-approved.md).
2. **Expiry is work you do on read.** Every query walks off the front of the queue. Amortised this is
   constant per request, because each timestamp is added once and removed once.
3. It gives you something the tally could not: **when the next slot opens**. That is the oldest
   timestamp plus the span, and it is exactly the `retry-after` value that
   [4.1](../04-when-a-lane-says-no/4.1-reading-the-refusal.md) needs. A tally cannot produce that
   number at all — it knows how many, never when.

## Why Sutra needs it

Point 3 is the one that makes this not merely a correctness upgrade. The router does not only need to
know *whether* a lane is full; when every lane is full it has to tell the caller **how long to
wait**, and it must not guess. [4.3](../04-when-a-lane-says-no/4.3-every-lane-dry.md) raises an error
carrying `soonest headroom in 60s`, and that sixty comes straight out of the front of one of these
queues. Build section 1 on a tally and section 4 has nothing truthful to say.

## The mechanism

The whole structure is three methods in `lab/_lane.py`:

```python
class Sliding:
    def __init__(self, limit: int, span: float, clock: Clock) -> None:
        self.limit = limit
        self.span = span
        self.clock = clock
        self.stamps: deque[float] = deque()

    def _expire(self) -> None:
        while self.stamps and self.clock.now - self.stamps[0] >= self.span:
            self.stamps.popleft()

    def remaining(self) -> int:
        """Requests still available across any window of `span` ending now."""
        self._expire()
        return self.limit - len(self.stamps)

    def take(self) -> None:
        """Consume one request, or raise with the time until the oldest one falls out."""
        if self.remaining() <= 0:
            wait = self.stamps[0] + self.span - self.clock.now
            raise Refused("sliding", f"{self.span:.0f}s", wait)
        self.stamps.append(self.clock.now)
```

**Line by line:**

- `deque` rather than `list`, because every expiry removes from the **front**. `list.pop(0)` is
  linear in the length of the list, so a busy limiter would spend its time shuffling memory;
  `deque.popleft()` is constant.
- `_expire` uses `while`, not `if`. After a quiet period many timestamps have aged out at once, and
  a single `if` would drop one per call and under-report headroom for the next several requests.
- The comparison is `>= self.span`, not `>`. A request made exactly sixty seconds ago is outside a
  sixty-second window: the window is the half-open interval `(now - span, now]`. Using `>` would
  keep it one moment too long and make the limiter one request stricter than the provider at every
  boundary — a difference nobody would notice until they were quietly wasting a request per minute.
- `remaining()` calls `_expire()` first, so no caller can read a stale answer. Expiry is never
  scheduled and there is no background task; the structure is correct whenever it is asked, and
  costs nothing when it is not.
- `take()` calls `remaining()` rather than checking `len(self.stamps)` directly, which means it
  cannot forget to expire. The alternative — checking the length and expiring separately — is two
  lines that must agree for ever, and they will not.
- `wait = self.stamps[0] + self.span - self.clock.now` is the line the tally cannot write. The
  oldest live request, plus the span, is the instant a slot frees. This is a **fact**, not a policy:
  it is not a backoff choice, it is arithmetic about when the window edge passes.

**Line by line:**

- `--sliding` swaps the class and changes nothing else — same burst times, same limit, same loop.
  That is what makes the two outputs comparable.

Measured on 2026-09-06:

```text
limit 10 requests per 60s, sliding window

  t=59s   asked 10   allowed 10
  t=61s   asked 10   allowed  0
  allowed across the 2s from t=59 to t=61:  10
  the limit for any 60s window:              10
  within the limit: the second burst was refused
```

Ten, then **zero**. The second burst is refused entirely, because at t=61 there are still ten
timestamps inside the last sixty seconds — the ones written at t=59. They will start falling out at
t=119, and not before.

Set that beside the fixed window's `20` and the difference is the whole point of the part: same
limit, same traffic, same instant, and one of them is enforcing the rule.

## When it breaks

The failure mode of a sliding log is not incorrectness, it is **cost**, and it arrives as memory
rather than as an exception. A limit of ten costs ten floats. A limit of a million costs a million,
per pool, and if you keep one of these per user you have built a memory leak with a limit on it.

The break you can reach on purpose is more interesting, and it comes from the clock rather than the
counter. Move the clock **backwards** — which happens in real systems on an NTP correction — and the
structure quietly stops working:

```python
clock.now = 100.0
w = Sliding(3, 60.0, clock)
w.take()
clock.now = 40.0  # the clock stepped back
print(w.remaining())
```

**Line by line:**

- The timestamp written at `100.0` is now in the future relative to `clock.now`.
- `_expire` computes `40.0 - 100.0 = -60.0`, which is not `>= 60.0`, so the entry never ages out on
  this comparison.
- Worse, it will not age out until the clock passes `160.0` — so a one-minute window has become a
  two-minute window for that entry, and the limiter is now stricter than it should be for a while.

Run it and the printed value is `2`, which is not wrong, but the recovery time is. This is the reason
production limiters use a **monotonic** clock for spans and a wall clock only for reporting.
`time.monotonic()` never goes backwards; `time.time()` does. Sutra's `Clock` is a stand-in for the
monotonic one, which is why it only ever moves forward in the lab.

## In production

**What a professional writes instead.** For a shared limiter, the deque becomes a sorted set in
Redis keyed by the pool, with the score as the timestamp: `ZREMRANGEBYSCORE` to expire, `ZCARD` to
count, `ZADD` to take, all inside one `MULTI` or a small Lua script so the three steps cannot
interleave with another process. The logic is line for line what is above; only the storage moves.
The reason it must be one script rather than three round trips is
[6.1](../06-in-production/6.1-one-till-two-cashiers.md).

**What degrades at scale.** The memory story above, and one subtler thing: the expiry cost is paid by
whoever asks first after a quiet period. A limiter that has been idle for an hour hands its next
caller a walk over every stale entry. With a limit of ten this is invisible. With a large limit and a
bursty pattern it is a latency spike in a code path nobody thinks of as doing work, and it shows up
in a p99 with no obvious cause.

**The failure that only appears with real traffic.** Clock skew between processes. Two machines
sharing a Redis-backed window write timestamps from their own clocks, and if one is a second ahead
its entries expire a second late everywhere. Nobody notices until the limit is tight and the
symptoms are a handful of unexplained refusals a day. The fix is to take the timestamp from the
**store** rather than from the caller — in Redis, from `TIME` — so there is one clock, whatever the
machines think.

**The review comment a senior engineer leaves:** *"`take()` calls `remaining()` which calls
`_expire()` — good, one path. But this is per-process, and we run four replicas, so the effective
limit is four times what this file says. Either move it to a shared store or divide the limit by the
replica count and accept the waste. Right now we are advertising ten and permitting forty."*

**The interview question:** *"How do you tell a caller when to retry?"* A weak answer picks a
constant. A strong one: *"From the limiter, not from a policy. A sliding log knows the oldest live
request, so the next slot opens at that timestamp plus the window — that is arithmetic and it is
exact. A plain counter cannot answer the question at all, because it knows how many happened and
never when, so anything it tells you is a guess. I return that value as `retry-after` and the caller
sleeps on it instead of on a ladder it invented."*
