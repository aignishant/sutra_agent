# 2.2 — The command that adds no rules

## One-line answer

`tools/lint_skills.py` is about forty lines that import Day 30's `check_shelf`, print one line per
skill folder, and return `0` or `1` — and the discipline that makes it worth having is that it
contains no `if` about what a valid skill is.

## The story

At the hospital there is a woman who sits beside the doctor and translates.

She is very good, and the thing that makes her good is what she refuses to do. The doctor says the
scan shows a small fracture and the patient should keep weight off it for now. She says exactly that,
in the patient's language, including the *for now*. She does not soften it. She does not add that her
cousin had the same thing and it healed quickly. When the patient asks whether they can drive, she
turns to the doctor and asks, rather than answering.

A worse interpreter would be more helpful in the moment and dangerous over time. Once she starts
adding, the patient is receiving medical advice from two people and can no longer tell which is
which — and neither can the doctor, who thinks he has said one thing and has been heard saying
another.

Her whole value is that she carries the words across a boundary and changes nothing on the way.

## The idea in plain language

`tools/lint_skills.py` is the interpreter. On one side is `tools/skill_checks.py`, which knows what a
valid skill is and speaks in `Finding` records. On the other side is a shell, which understands
printed lines and one integer. The lint carries findings from one to the other and adds nothing.

It has exactly three jobs.

**Find the shelf.** Decide which directory holds the skill folders, defaulting to `skills/` and
accepting an argument so a test or a curious human can point it somewhere else.

**Format.** Turn the flat list of `Finding` records that `check_shelf` returns into lines a person
can read and a `grep` can find — one line per finding, prefixed so the failures are greppable, and
one line per healthy skill folder so you can see what was actually looked at.

**Decide the number.** Return `0` when there were no findings and `1` when there were, so the shell
can act on it.

Everything else is a rule, and rules live in `skill_checks.py`.

The one genuinely interesting design question is not in that list, and it is this: **what should the
lint do when it finds no skills at all?** `check_shelf` returns a flat list of findings, so a clean
shelf gives back an empty list — and so does a shelf with nothing on it. That is the subject of the
next part ([2.3](2.3-the-exit-code-is-the-api.md)) and it matters more than it sounds, because "I
checked four skills and all four were fine" and "I found nothing to check" are completely different
facts that arrive here as the same empty list.

## Why Sutra needs it

Because the gate is a shell script and a shell script cannot call a Python function.

Day 30's rules are perfectly good and completely unreachable from `./m check` as they stand. The test
suite reaches them, but the test suite is one stage among several and it can be filtered, deselected
or skipped — and the whole point of SK-20 is that the shelf gets validated *even when nobody runs
pytest*. This file is the adapter that makes the rules reachable from a shell, and it is the smallest
adapter that can do it.

There is also a second reader, later. Day 45 adds `tools/mcp_audit.py` to this same gate, and Phase
14 makes this repository public, at which point the linters are the first thing a stranger runs. A
lint whose output is one line per finding, with the skill named first, is a lint a stranger can act
on without reading its source.

## The mechanism

The whole file. It is short on purpose, and every line that is not formatting or path handling is a
line to be suspicious of.

```python
# tools/lint_skills.py
"""The command-line front door onto Day 30's skill rules (SK-20).

The rules themselves live in tools/skill_checks.py and are not restated here: this module
turns Findings into printed lines and an exit code, and nothing else. If you find yourself
writing an `if` about what makes a skill valid, it belongs in skill_checks.py, where the
test suite will see it too (part 2.1).

Run it as a module, never as a path - see part 4.2 for why:

    uv run python -m tools.lint_skills
    uv run python -m tools.lint_skills tests/fixtures/skills/sourced-pack
"""

from __future__ import annotations

import sys
from pathlib import Path

from tools.skill_checks import Finding, check_shelf

SHELF = Path("skills")


def shelf_folders(shelf: Path) -> list[Path]:
    """The folders check_shelf will look at, so the report can say how many were examined."""
    if not shelf.is_dir():
        return []
    return sorted(p for p in shelf.iterdir() if p.is_dir())


def report(shelf: Path, findings: list[Finding]) -> int:
    """Print one line per skill folder and one per finding; return how many skills had findings."""
    by_skill: dict[str, list[Finding]] = {}
    for finding in findings:
        by_skill.setdefault(finding.skill, []).append(finding)
    for folder in shelf_folders(shelf):
        problems = by_skill.pop(folder.name, [])
        if problems:
            for problem in problems:
                print(f"FAIL {problem}")
        else:
            print(f"OK   {folder.name}")
    for orphaned in by_skill.values():
        for problem in orphaned:
            print(f"FAIL {problem}")
    return len({f.skill for f in findings})


def main(argv: list[str] | None = None) -> int:
    """Lint every skill folder on the shelf. Return 0 when all are spec-shaped, else 1."""
    args = sys.argv[1:] if argv is None else argv
    shelf = Path(args[0]) if args else SHELF
    findings = check_shelf(shelf)
    bad = report(shelf, findings)
    examined = len(shelf_folders(shelf))
    print(f"lint_skills: {examined} skill folder(s) examined, {bad} with findings")
    if findings:
        return 1
    if examined == 0:
        print(f"lint_skills: nothing was checked - {shelf} holds no skill folders")
        return 1
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

**Line by line:**

- The docstring names the rule this file lives under, in the file, rather than only in this document.
  A future reader who opens `lint_skills.py` with an idea for a new check needs to be told there and
  then that the check goes elsewhere.
- `from __future__ import annotations` makes every annotation a string at runtime. It costs nothing
  and it lets `dict[str, list[Finding]]` and `list[str] | None` be written plainly.
- `import sys` is here for `sys.argv` only. Note what is *not* imported: no `argparse`. One optional
  positional argument does not earn a parser, and a gate stage should start instantly.
- `from tools.skill_checks import Finding, check_shelf` is the load-bearing line of the whole file.
  It is an absolute import of a sibling module through the package, which is what forces the `-m`
  invocation ([4.2](../04-wiring-the-gate/4.2-the-module-the-script-cannot-find.md)). `Finding` comes
  along because the annotations name it, and importing the type rather than re-declaring it is the
  same one-definition rule as importing the checks.
- `SHELF = Path("skills")` is a module-level constant, relative to the working directory. Relative,
  not absolute, because the gate always runs from the repository root and a hard-coded absolute path
  would break on every other machine. Naming it as a constant means a test can see the default
  without re-typing the string.
- `shelf_folders` exists for **one** reason, and it is worth being clear about it, because at a
  glance it looks like duplicated enumeration. `check_shelf` returns findings only, so a clean shelf
  and an empty shelf both come back as an empty list — and those are different facts
  ([2.3](2.3-the-exit-code-is-the-api.md)). This function answers *how many folders were there*,
  which is a display and exit-code concern rather than a rule, and it deliberately uses the same
  `sorted(p for p in shelf.iterdir() if p.is_dir())` that `check_shelf` walks, so the two counts
  cannot disagree.
- `if not shelf.is_dir(): return []` keeps the helper total. `check_shelf` already handles a missing
  shelf properly, by returning a `no-shelf` finding, and this file must not raise on the way to
  printing it.
- `report` is separated from `main` so it can be called with a hand-made list of `Finding` records in
  a test, without touching the filesystem. It returns a count rather than a verdict, because counting
  and deciding are different jobs and the decision belongs to `main`.
- `by_skill.setdefault(finding.skill, []).append(finding)` groups the flat list by folder name. This
  is the whole reason `Finding` carries a `skill` field rather than being a plain string: a caller
  can reassemble the per-folder view without the checker having to produce it.
- `for folder in shelf_folders(shelf)` iterates folders rather than findings, which is what lets a
  healthy skill get an `OK` line at all. The sorting comes from the helper, so the output is stable —
  directory order differs between machines, and stable output is what lets you diff two runs.
- `by_skill.pop(folder.name, [])` takes the findings for this folder **and removes them**, so that
  whatever is left in `by_skill` afterwards is exactly the findings that belong to no folder.
- The `orphaned` loop prints those leftovers, and there is a real case for it: `check_shelf` returns
  a `no-shelf` finding whose `skill` is the shelf's own name rather than a folder inside it. Without
  this loop the most important finding of all would be silently dropped.
- `print(f"FAIL {problem}")` relies on `Finding.__str__`, which Day 30 wrote to lay out the three
  columns. Formatting the record here instead would put the layout in two places.
- `print(f"OK   {folder.name}")` — three spaces, so `OK` and `FAIL` line the names up in a column.
  Printing the healthy skills at all is a deliberate cost: it is how you see that four skills were
  examined rather than none.
- `len({f.skill for f in findings})` counts *skills*, not findings. One skill with six findings is
  one failure with six reasons, and the summary line should say so. A set comprehension, because the
  same skill name appears once per finding.
- `argv: list[str] | None = None` with `args = sys.argv[1:] if argv is None else argv` is the
  standard testable-entry-point shape. Called from the command line it reads the real arguments;
  called from a test it takes a list, so the test does not have to patch `sys.argv` and can run in
  the same process.
- The final summary line prints the count even when everything passed. `2 skill folder(s) examined, 0
  with findings` is a much stronger green than silence, because silence is also what a broken lint
  produces.
- `if findings: return 1` comes **before** the empty check, because a `no-shelf` finding is a finding
  and deserves to be reported as one rather than as "nothing was checked".
- `if examined == 0: return 1` is the empty-shelf decision, argued out in
  [2.3](2.3-the-exit-code-is-the-api.md). Nothing is broken, which is precisely the trap.
- `raise SystemExit(main())` under `if __name__ == "__main__":` is the idiom, and it is deliberately
  not `sys.exit()` inside `main`. `main` returns a number; the module boundary turns that number into
  a process exit code. That separation is what makes `main` callable from a test that then asserts on
  the number instead of catching `SystemExit`.

Run it against a shelf that is not the real one, to see the shape of the output without needing the
real skills to exist:

```bash
uv run python -m tools.lint_skills tests/fixtures/skills/sourced-pack
```

**Line by line:**

- `uv run` puts the project's pinned Python and its dependencies on the path.
- `python -m tools.lint_skills` runs the module through the package machinery, which is what makes
  `from tools.skill_checks import ...` resolve.
- The positional argument overrides `SHELF`. Day 29 built `tests/fixtures/skills/sourced-pack/` as
  four clean-but-colliding skills, which makes it a good, safe target: the folders are real, they are
  spec-shaped, and nothing in `sutra/` can load them.

## When it breaks

**The shelf is empty, and the lint says so.** In the reference checkout on 2026-09-04, `skills/`
contains exactly one file — `.gitkeep` — because Day 27's two skill folders are the learner's own
work and have not been created yet. `check_shelf` finds no directories, so it returns no findings at
all, and without the count guard that would be a clean green. Your first honest run is:

```text
lint_skills: 0 skill folder(s) examined, 0 with findings
lint_skills: nothing was checked - skills holds no skill folders
exit: 1
```

That is not the lint failing. That is the lint working: the shelf Day 27 specified does not exist in
this tree, and a gate that reported green on a missing shelf would be worse than no gate at all.
Build `skills/ticket-triage/` and `skills/kb-answer-style/`, then run it again.

**The import fails and you have not written a line of it wrong:**

```text
Traceback (most recent call last):
  File "tools/lint_skills.py", line 18, in <module>
    from tools.skill_checks import Finding, check_shelf
ModuleNotFoundError: No module named 'tools'
```

You ran `python tools/lint_skills.py` instead of `python -m tools.lint_skills`.
[4.2](../04-wiring-the-gate/4.2-the-module-the-script-cannot-find.md) is that failure in full,
because it will happen to you at least once and the traceback points at the wrong culprit.

**Day 30 is not finished and the module is genuinely absent:**

```text
ModuleNotFoundError: No module named 'tools.skill_checks'
```

Note the difference from the previous one — `tools` resolved, `tools.skill_checks` did not. That is
the real missing-file error, and it means today cannot proceed: there are no rules to wrap.

**A skill folder exists and the lint never mentions it.** No `OK` line and no `FAIL` line — it is
simply absent, and the count is one lower than you expected:

```text
OK   kb-answer-style
OK   ticket-triage
lint_skills: 2 skill folder(s) examined, 0 with findings
```

on a shelf you know holds three. Something is not a directory, or is nested one level too deep. This
is why the summary prints the count: the silent omission is invisible in a list of `OK` lines and
obvious in a number.

## In production

**What a professional writes instead.** Three differences, all of them about being called by other
programs. Findings go to standard output and diagnostics go to standard error, so a caller can
capture one without the other. There is usually a `--format json` flag, because the moment a lint is
useful somebody wants to post its findings as review comments. And the exit codes get finer: many
production linters use `0` for clean, `1` for findings, and `2` for "the lint itself broke" — so a
caller can tell "your code has problems" from "my tool crashed", which are very different messages to
put in front of a developer at midnight.

**What degrades at scale.** Printing every healthy skill is right at two skills and wrong at two
hundred, where the signal drowns. The professional version prints failures always and healthy lines
only under `--verbose`, keeping the summary count so the "nothing was checked" case stays visible.
Reading every skill folder from disk on every invocation also stops being free eventually; that is
when caching by content hash starts to pay — and Day 30 already wrote `folder_digest`, which is
exactly the hash you would key that cache on.

**The failure mode that only appears with real traffic** is output that some other program has come
to depend on. Once a bot posts your `FAIL` lines into pull requests, the format is an interface: change
the prefix and something downstream silently stops matching. Professionals treat lint output as a
public contract and version it, which is the strongest argument for adding `--format json` early —
the human format is then free to improve.

**The review comment a senior engineer leaves:** *"`main` calls `sys.exit` in three places. Make it
return an int and do the exiting in the `__main__` guard — right now I can't call it from a test
without catching `SystemExit`, and that's the only way I'd want to test it."*

**The interview question:** *"Walk me through a linter you have written."* The honest spoken answer:
*"It's about forty lines and the interesting thing about it is what's missing. The rules aren't in it
— they're pure functions in a separate module that also back the pytest suite, so there's one
definition of valid. The linter finds the directory, formats findings as one greppable line each,
prints how many things it actually examined, and returns an integer that the `__main__` guard turns
into an exit code. That last split matters: `main` returning an int rather than calling `sys.exit`
means a test can assert on the number instead of catching an exception. And it prints the count of
what it checked, because the most dangerous output a linter can produce is silence — silence is what
you get from a clean run and from a run that found nothing to look at, and those are completely
different facts."*
