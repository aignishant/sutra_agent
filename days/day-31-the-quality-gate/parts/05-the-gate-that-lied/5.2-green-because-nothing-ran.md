# 5.2 — 💥 Green because nothing ran

## One-line answer

`pytest` returns exit code **5** when it collected no tests, `./m check` deliberately forgives a 5,
and a single mistyped character in the marker expression turns "every test passed" and "no test ran"
into the same green — which is the same class of bug as a linter returning 0 for an empty shelf, one
level up.

## The story

The van did the whole round and came back with the best numbers of the month.

Eleven stops, the usual route, back before four. The driver hands in the day sheet and it says zero
failed deliveries, zero refusals, zero complaints. Nobody has ever had a day like it.

The parcels were still in the depot. The loading bay had been moved that morning and the van was
signed out from the wrong bay, and a van with nothing in it drives the route perfectly, because
nothing about driving the route requires there to be anything in the back.

The day sheet is not wrong. Zero failed deliveries is exactly what happened. It is just that the
sheet has a column for failures and no column for *how many did you attempt*, and without that second
number the best day of the month and the worst one produce the same piece of paper.

## The idea in plain language

`pytest` communicates through exit codes, and it uses more than the usual two:

| Code | Name | Means |
| --- | --- | --- |
| `0` | OK | every collected test passed |
| `1` | TESTS_FAILED | tests ran, some failed |
| `2` | INTERRUPTED | the run was stopped — often a collection error |
| `3` | INTERNAL_ERROR | something broke inside pytest |
| `4` | USAGE_ERROR | you invoked it wrongly |
| `5` | NO_TESTS_COLLECTED | it ran, and found nothing to run |

Code `5` is the interesting one and it exists precisely because `0` would be a lie. The pytest
authors decided "I collected nothing" deserves its own signal, and that decision is why this bug is
catchable at all.

Now look at the line in `./m check`:

```bash
uv run python -m pytest -q -m "not live" || [ $? -eq 5 ]
```

**Line by line:**

- The command runs the suite with `live`-marked tests deselected.
- `||` fires only if pytest returned non-zero.
- `[ $? -eq 5 ]` asks whether that non-zero code was exactly 5, and succeeds if so — which satisfies
  `set -e` and lets the gate continue.
- So the gate passes on `0` and on `5`, and stops on `1`, `2`, `3` and `4`.

The comment above it in `m` explains why, and the explanation was correct when it was written:

> pytest exits 5 for "no tests collected". Before Day 23 there are none, and an empty suite is not a
> failure - so 0 and 5 pass and everything else stops the gate.

That was true up to Day 22. From Day 23 the repository has tests, and the forgiveness has quietly
changed meaning: it no longer covers "we have not written any yet", it covers "we ran nothing, for
whatever reason". The reason can be a typo, a renamed directory, a broken `conftest.py`, or a `-m`
expression that matches nothing — and every one of those sends the van out empty.

## Why Sutra needs it

Because today the gate acquires two more stages that can also be green for nothing
([2.3](../02-a-lint-is-a-test/2.3-the-exit-code-is-the-api.md) is the same problem for
`lint_skills`), and because this specific forgiveness is now a live hazard rather than a historical
convenience.

Count what is protected by that stage. `tests/test_agent.py`, `test_config.py`, `test_desk.py`,
`test_loop.py`, `test_mechanics.py`, `test_persona.py`, and from Day 30 `test_skills.py` and
`test_skill_couplings.py`. On 2026-09-04 that is 32 passing tests and 2 deselected. Every one of them
disappears silently if the collection ever returns nothing, and the gate says `OK all green`
afterwards.

It matters more from tomorrow, not less. Phase 5 adds `tests/test_mcp_failures.py`, Phase 6 adds an
audit, and the test suite becomes the main evidence that a protocol implementation still works. A
protocol failure that is silently not being tested is exactly the kind of thing that surfaces in
production and nowhere else.

## The mechanism

Reproduce it. The typo is one hyphen, in a place where nothing checks spelling:

```bash
uv run python -m pytest -q -m "not live"; echo "exit: $?"
uv run python -m pytest -q -m "not-live"; echo "exit: $?"
```

**Line by line:**

- The first is the gate's real invocation. `not live` is a marker *expression* — the word `not`
  applied to the marker `live`.
- The second has a hyphen instead of a space. `not-live` is no longer an operator and a name; it is
  a single expression that matches no test at all, so everything is deselected.
- `--strict-markers` is in this project's `addopts`, and it does **not** save you here. That flag
  rejects a `@pytest.mark.typo` on a test — an unregistered marker in the *code* — and says nothing
  about the expression you type on the command line.
- `; echo "exit: $?"` after each, because the printed output of the two runs is nearly identical and
  the number is the only reliable difference.

Measured on 2026-09-04. The correct expression:

```text
................................                                         [100%]
============================== warnings summary ===============================
<frozen abc>:106
  <frozen abc>:106: DeprecationWarning: BaseAgentConfig is deprecated and will be removed in future versions. Config is now loaded via reflection so the separate config class is no longer needed.

-- Docs: https://docs.pytest.org/en/stable/how-to/capture-warnings.html
exit: 0
```

The typo:

```text
============================== warnings summary ===============================
<frozen abc>:106
  <frozen abc>:106: DeprecationWarning: BaseAgentConfig is deprecated and will be removed in future versions. Config is now loaded via reflection so the separate config class is no longer needed.

-- Docs: https://docs.pytest.org/en/stable/how-to/capture-warnings.html
exit: 5
```

Look at those two blocks and notice how little separates them. Same warnings section, same footer,
same absence of any word like `error` or `failed`. The **only** visible difference is a missing row of
dots — and `-q` is what removed the line that would have said so. Without `-q`:

```text
34 deselected, 1 warning in 1.75s        <- the typo
32 passed, 2 deselected, 1 warning in 1.93s   <- correct
```

`34 deselected` with no `passed` at all. That is the *how many did you attempt* number the day sheet
did not have a column for, and `-q` hides it.

Now put the typo through the gate and watch the forgiveness do its work:

```bash
sed 's/not live/not-live/' m > days/day-31-the-quality-gate/lab/m_broken
bash days/day-31-the-quality-gate/lab/m_broken check; echo "exit: $?"
```

**Line by line:**

- `sed 's/not live/not-live/' m` prints a copy of the driver with the marker expression broken, and
  the redirect writes it into the day's `lab/`, which is scratch space. The real `m` is not touched — never edit the driver
  to demonstrate a failure in the driver.
- `bash days/day-31-the-quality-gate/lab/m_broken check` runs the broken copy explicitly with `bash`,
  so it does not need to be executable. It resolves `m`'s relative paths against your working
  directory, which is why you still run it from the repository root.
- The gate reaches the pytest stage, pytest returns 5, `[ $? -eq 5 ]` forgives it, the remaining
  stages run, and the script finishes with `OK all green` and `exit: 0` — on a run where **not one
  test executed**.

The fix is to narrow the forgiveness to the thing it was actually for. Two shapes, and the second is
better:

```bash
    # A suite that collects nothing is a failure from Day 23 onward: the tests exist, so
    # "nothing ran" means something ate them - a typo in the marker, a moved directory,
    # a broken conftest. Only an unwritten suite justified forgiving 5, and that was Day 22.
    uv run python -m pytest -q -m "not live"
```

**Line by line:**

- The forgiveness is simply removed. Any non-zero code — including 5 — now stops the gate.
- The comment above it changes with the code, because a comment explaining a clause that no longer
  exists is worse than no comment.
- This works because the suite is never legitimately empty any more. That is a fact about this
  repository from Day 23, and it should be stated where the decision lives.

Refusing 5 catches the empty run. It does not catch a suite that has merely *shrunk*, and pytest has
no built-in floor under the test count — so deciding what this repository should do about that is
your `TODO(me)`. The two honest options are to assert a minimum count in a test of your own, or to
print the count somewhere a human reads every run, and each has a cost worth writing down beside the
choice.

## When it breaks

**The marker expression matches nothing.** Shown above: `exit: 5`, and a gate that forgives it.

**The test directory moves and the gate does not notice.**

```text
no tests ran in 0.01s
```

`testpaths = ["tests"]` in `pyproject.toml` points at a directory. Rename it, and pytest has nowhere
to look. With the forgiveness clause in place this is a green gate on a repository with no test suite
at all.

**A broken `conftest.py`, which is a different code and much louder:**

```text
ImportError while loading conftest '.../tests/conftest.py'.
```

That exits `4` — a usage error — and the gate stops. Worth knowing because it is the reassuring case:
the noisy failures were never the problem, and the quiet one is the only one that needed a part
written about it.

**A file renamed out of the default pattern.** `test_desk.py` becomes `desk_test.py`, and pytest's
default `python_files = test_*.py` no longer matches it. No error. The file is simply never
collected, and the count drops from 32 to 27 without a word:

```text
27 passed, 2 deselected, 1 warning in 1.71s
```

This one is not caught by refusing exit 5 either, because the suite is not empty — it is *smaller*.
The only thing that catches a shrinking suite is somebody looking at the count, which is the argument
for printing it and, at scale, for tracking it.

## In production

**What a professional writes instead.** No forgiveness clause at all, and a coverage or count floor
that fails the build when the number drops. Most continuous-integration systems have this built in
under a name like *minimum tests* or *coverage threshold*, and the reason it is standard is exactly
this failure: a suite that silently stops running is indistinguishable from a suite that passes, and
it is the single most common way a project loses its safety net without noticing. The professional
habit that goes with it is to publish the test count in the build output where a human sees it every
time.

**What degrades at scale.** The empty-run failure gets easier to hit as the invocation gets more
complicated. A suite split by marker, by directory, by parallel worker and by shard has many more
places for a filter to match nothing, and a sharded run where shard 7 collects zero tests looks
exactly like a shard with nothing to do. That is why large suites report per-shard counts and fail
when a shard is unexpectedly empty — the aggregate green hides it completely.

**The failure mode that only appears with real traffic** is a filter that matches nothing *sometimes*.
A marker expression selecting by environment, or a path filter based on which files changed, can be
correct for months and then match nothing on the one commit where it mattered. There is no error and
no red build; there is just a change that went out untested, and the only trace is a number in a log
nobody read.

**The review comment a senior engineer leaves:** *"This stage passes on exit 5. That made sense when
we had no tests — it doesn't now. If pytest collects nothing today, something ate our suite, and I'd
rather find out from a red build than from production. Drop the `|| [ $? -eq 5 ]` and update the
comment above it."*

**The interview question:** *"How would you know if your test suite stopped running?"* The honest
spoken answer: *"Honestly, in a lot of setups you wouldn't, and that's the point of the question.
pytest returns a distinct exit code — 5 — for 'collected nothing', which exists precisely because
returning 0 would be a lie. But plenty of build scripts forgive a 5, usually for a good reason early
on, like the suite not existing yet, and the forgiveness outlives the reason. Then one hyphen in a
marker expression, or a renamed directory, deselects everything and the build is green with zero
tests executed — and quiet mode hides the summary line that would have shown it. So: don't forgive 5
once you have tests, print the count in the output where somebody sees it, and put a floor under it
in CI. The subtler version is a suite that shrinks rather than empties — a file renamed out of the
collection pattern — and only the count catches that one."*
