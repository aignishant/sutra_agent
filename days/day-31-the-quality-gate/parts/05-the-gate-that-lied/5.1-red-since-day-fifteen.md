# 5.1 — 💥 Red since Day 15

## One-line answer

`./m check` in this repository exits 1 on a single un-sorted import block in `tests/test_persona.py`
and has done since Day 15 — seven progress rows were written as ✅ over it before anybody noticed,
and the reason anybody eventually did is that one person wrote ⚠️ and explained why instead of
ticking the box.

## The story

The register is marked at the start of the afternoon and everybody is present.

Nobody is lying. The teacher looks up, sees a room that is obviously full, and marks the class in
one movement, because doing it name by name takes a while and there has never once been a discrepancy.
The register goes to the office and the office files it, and if anybody ever asks who was in the
building that afternoon, that piece of paper is the answer.

One Thursday a child goes home at lunch because they feel unwell, and the note that would have said so
does not get written, and the register says present. Nothing happens. The child is fine, they are back
on Friday, and the register is wrong in the office drawer for a year.

The thing that goes wrong is not the marking. It is that the register has stopped being a record of
what somebody checked and become a record of what somebody expected. And from the outside those two
documents are identical — same box, same tick — which is why the drift can run for a very long time
before it costs anything, and why when it finally costs something, it costs a lot.

## The idea in plain language

This repository has a ledger, `docs/PROGRESS.md`, with one row per completed day and a column headed
*Gates green?*. Every day ends by writing that row. It is the project's memory: the plan says the last
row is where we are, and a stranger picking this repository up has that column and nothing else.

The column has been wrong.

`tests/test_persona.py` was last edited in commit `4029771`, which is Day 15's commit. The edit left
its import block un-sorted, and `ruff` — stage one of `./m check` — has rejected it ever since. That
means:

- Rows **16 to 22** say ✅. They are wrong. Every one of those days was committed on a repository
  where `./m check` exited 1 at the first stage.
- Rows **23 to 29** say ⚠️. They are right, and there is a note under the table explaining exactly
  what is red and why, including the one-line fix.

Fourteen day-rows in total were written over a failing gate. Seven of them recorded it and seven did
not.

What went wrong is worth being precise about, because the interesting version is not "somebody was
careless". Nobody skipped the check. What happened is that on those days the person running things
ran `./m depth`, `./m trace` and `./m wiki --check`, saw all three green, and wrote ✅ — and ✅ in that
column means the whole gate, not the three parts of it that happened to get run. The scope crept by
one word ([1.4](../01-what-a-gate-is/1.4-what-green-does-not-mean.md)), the tick was written from an
expectation instead of a measurement, and the register was wrong for a year.

The recovery is the part worth copying. Somebody could have run `ruff --fix` and written ✅ across the
board and nobody would ever have known. What they did instead was write ⚠️, explain the cause in the
ledger, name the file, give the fix, and record that history was **not** rewritten to make the
commits look compliant. That note is now the most valuable paragraph in the file, because it is the
one that proves the other rows mean something.

## Why Sutra needs it

Because today you are extending this gate, and if you extend it without looking at it you will build
on a failure.

Try it and see. Add the two lines from
[4.1](../04-wiring-the-gate/4.1-two-lines-in-the-driver.md), run `./m check`, and your new stages do
not run at all — stage one aborts the script and stages three and four are never reached. You could
finish the entire day, tick every box, and have no evidence whatsoever that either linter works,
because the gate never got as far as them. That is a genuinely easy mistake to make and it is why the
day's §3 tells you to run the gate *before* you write anything.

There is a second reason and it is larger. This is the Phase 4 gate day, and condition three of the
plan's §15 is *"`./m check` passes on the whole repo"*
([6.1](../06-the-phase-gate/6.1-six-things-that-must-be-true.md)). Phase 4 cannot be green while this
is red. So the ⚠️ rows are not a footnote; they are the thing standing between this repository and a
closed phase, and closing the phase honestly means either fixing them or writing down that you did
not.

## The mechanism

Run the gate on the repository as it stands. This is the measurement, and it was taken on 2026-09-04:

```bash
./m check; echo "exit: $?"
```

**Line by line:**

- `./m check` starts at stage one, `uv run ruff check .`.
- `ruff` finds one error and returns 1.
- `set -e` aborts the script immediately, so stages two through eight never execute.
- `echo "exit: $?"` prints `1` — `ruff`'s exit code, travelling out of `m` unchanged, exactly as
  [1.3](../01-what-a-gate-is/1.3-the-line-that-makes-it-stop.md) describes.

The output, verbatim:

```text
I001 [*] Import block is un-sorted or un-formatted
  --> tests\test_persona.py:7:1
   |
 5 |   # Marked "live" so `pytest -m "not live"` (the default gate) skips it: it spends
 6 |   # quota, and a suite that silently makes network calls is a suite people stop running.
 7 | / import asyncio
 8 | |
 9 | | import pytest
10 | | import re
11 | | from sutra.desk.run_once import ask_with
12 | | from sutra.desk.agent import root_agent, INSTRUCTION
   | |____________________________________________________^
help: Organize imports
   |
7  | import asyncio
8  + import re
9  |
10 | import pytest
   - import re

12 + from sutra.desk.agent import INSTRUCTION, root_agent
13 | from sutra.desk.run_once import ask_with
   - from sutra.desk.agent import root_agent, INSTRUCTION
   -

   |

Found 1 error.
[*] 1 fixable with the `--fix` option.

```

Read what the rule is actually complaining about, because "un-sorted imports" undersells it. `I001`
comes from the `I` rule group — `isort`, selected in `pyproject.toml` alongside `E`, `F`, `UP`, `B`
and `SIM` — and it wants imports grouped: the standard library first, then third-party packages, then
the project's own modules, with a blank line between the groups and each group alphabetised. Here
`import re` (standard library) sits below `import pytest` (third-party), and the two `from
sutra.desk…` lines are in the wrong order relative to each other. The `+` and `-` lines in the help
output are the exact edit `ruff` would make.

It is a small, boring, completely mechanical complaint, and that is the point of the story. The
failure that runs longest is never a dramatic one.

Now confirm the scale of it, which is the part the ledger got wrong:

```bash
git log --oneline -1 -- tests/test_persona.py
grep -n "^| 1[6-9] \|^| 2[0-9] " docs/PROGRESS.md
```

**Line by line:**

- `git log --oneline -1 -- tests/test_persona.py` shows the last commit that touched the file — the
  `-- <path>` limits the history to that one file. It prints `4029771 Add Day 15 content on toolsets
  and OpenAPI`, which dates the breakage.
- `grep -n "^| 1[6-9] \|^| 2[0-9] " docs/PROGRESS.md` prints the ledger rows from 16 to 29 with their
  line numbers. `\|` is alternation in basic regular expressions, and the trailing space in each
  branch stops `| 2` from matching a two-digit continuation.
- Read the last column. Seven ✅ then seven ⚠️, with the breakage sitting under all fourteen.

**The fix is one command, and it is yours, not this document's:**

```bash
uv run ruff check --fix tests/test_persona.py
```

**Line by line:**

- `uv run` again, so the `ruff` that edits the file is the pinned `0.16.4` and not some other version
  with a different idea of import order.
- `ruff check --fix` applies the automatically-fixable findings rather than only reporting them. The
  `[*]` marker in the earlier output is `ruff` telling you in advance that this particular finding is
  one of them.
- The path narrows the fix to one file. Running `--fix` over the whole repository would work here and
  is the wrong habit: a fixer pointed at everything makes a diff you did not read.
- Read the diff afterwards with `git diff tests/test_persona.py` before you commit it. An automatic
  fix is still your change once it is in your tree.

`tests/test_persona.py` is the learner's own file. No generated day edits project code — every line
under `sutra/` and `tests/` is typed by the person doing the curriculum — so this stays a
`TODO(me)`. Run it, read the diff, run `./m check` again, and watch the gate fail *later* rather than
pass. That is the correct outcome: the `:free` lint you wrote today is red on ten teaching lines
([3.3](../03-the-free-suffix-lint/3.3-the-alarm-that-fires-on-toast.md)), and a gate that moves its
failure forward one stage at a time is a gate that is working.

## When it breaks

**You fix it and write ✅ everywhere, including the old rows.** This is the tempting version and it
is the one to refuse. The old rows are not a scoreboard; they are a record of what was true when the
commit was made, and on those days the gate was red. Editing them turns a ledger into a story. The
plan calls `PROGRESS.md` append-only for exactly this reason, and the existing note in it is explicit
that history was **not** rewritten to make the commits look compliant.

**You write ✅ today because the gate "basically" passes.** The gate does not do "basically". If
`./m check` did not exit 0 in front of you, the row is ⚠️ and the note underneath says which stage
and why. That sentence takes a moment and it is the entire mechanism by which this failure was ever
caught.

**You fix the import block and the gate is still red:**

```text
free-suffix: 10 model string(s) missing ':free' (Addendum 02 section 7)
exit: 1
```

Expected. You have moved the failure from stage one to stage four, which means stages one, two and
three now pass — genuine progress that looks like none. Keep going: the ten `:free` findings are a
triage exercise, not a bug ([3.3](../03-the-free-suffix-lint/3.3-the-alarm-that-fires-on-toast.md)).

**You "fix" it by narrowing the rule set.** Removing `I` from `select` in `pyproject.toml` makes the
error disappear in one edit and is the worst available move: it silences the rule everywhere,
permanently, for the whole repository, to avoid one file's diff. If a rule is genuinely wrong for a
project, removing it is a decision that gets discussed and written down. If it is being removed to
turn a light green, it is the register again.

## In production

**What a professional writes instead.** They do not rely on somebody remembering to run the gate at
all. The check runs automatically on every push, on a machine nobody has customised, and the result
is attached to the change rather than written down afterwards by the person who made it. That single
move removes the entire failure in this part, because the tick and the measurement become the same
artefact. Everything else here — the honest ⚠️, the note in the ledger — is what you do while you do
not have that yet, and it is what you keep doing for the checks a build server cannot run
([6.2](../06-the-phase-gate/6.2-the-freshness-check-that-fired.md)).

**What degrades at scale.** A red build that stays red is the most expensive state a repository can
be in, and its cost is not the broken thing — it is that every *other* failure becomes invisible
behind it. Once the gate is red for a reason people have learned to expect, a second failure arrives
and looks the same, and nobody can tell them apart without reading. Teams that survive this treat a
red main branch as a stop-the-line event, and the reason is not ceremony: it is that the value of a
signal collapses to zero the moment it is usually on.

**The failure mode that only appears with real traffic** is normalisation of the exception. Somebody
says *"ignore the ruff error, it's a known one"* — which is true, helpful, and the beginning of the
end, because it converts a failing check into a piece of oral tradition that new people have to be
told. The tell is when the onboarding instructions include a sentence about which failures to ignore.
The countermeasure is to make known-broken things *green with a recorded exemption* rather than red
and remembered — a skip with a ticket number, an exemption marker with a reason
([3.3](../03-the-free-suffix-lint/3.3-the-alarm-that-fires-on-toast.md)) — so the gate's red always
means something new.

**The review comment a senior engineer leaves:** *"The description says all checks pass. I ran the
gate on this branch and it fails at the first stage on a file you didn't touch. That's not yours to
fix in this PR, but please don't claim green — either fix it in a separate change or say in the
description that the gate is red and why."*

**The interview question:** *"Tell me about a time your build was broken and nobody noticed."* The
honest spoken answer: *"Our gate had been failing at the first stage — one un-sorted import block in
a test file — for about a fortnight of work, while the progress ledger recorded seven commits as
having green gates. Nobody skipped the check. What happened was narrower and more interesting: people
ran the three checks they'd changed things for, saw green, and ticked a box that meant the whole gate.
The scope of the word 'green' quietly shrank. We found it because one person wrote a warning instead
of a tick and explained in the ledger exactly which stage was red and what the fix was, and we
deliberately did not rewrite the earlier rows, because a ledger you edit to look consistent isn't a
ledger. The real fix is that the gate should run on a machine nobody has customised and attach its
result to the change, so the tick and the measurement are the same artefact — but the habit that
caught it was somebody being willing to write down a failure that wasn't theirs."*
