# 1.3 — The line that makes it stop

## One-line answer

`set -euo pipefail`, the fourth line of the `m` script, is what turns a list of commands into a gate:
without `-e` the shell runs cheerfully past a failed stage and prints `OK all green` at the bottom of
a broken run, and the other three flags close the three remaining ways a failure can go unnoticed.

## The story

You are building the flat-pack wardrobe and the booklet has twenty steps.

Step six says the side panel should sit flush against the base. It does not. There is a gap you could
put a coin in, and you know it is wrong, and you say so out loud to nobody. Then you carry on,
because there are fourteen steps left and the booklet is a list of steps and the way you get through
a list of steps is by doing the next one.

Twenty is the last page. The last page has a picture of a finished wardrobe and the word **Done**.
The thing in front of you stands up. It has two doors, and one of them will never close, and the only
way back to step six is all the way back through the other fourteen.

The booklet was not wrong about anything. It simply had no way of saying *stop* — it printed **Done**
because you reached the last page, and reaching the last page is the only thing it was ever
measuring.

## The idea in plain language

A shell script is, by default, a list of commands that runs to the end. If command three fails,
command four runs anyway. The script's own exit code is the exit code of the **last** command it ran,
which in the gate would be `echo "OK all green"` — and `echo` almost always succeeds.

So a shell script without protection is the flat-pack booklet: it has no way of saying *stop*, and it
prints **Done** because it reached the last page.

`set` is the shell builtin that changes those defaults, and `set -euo pipefail` sets four of them at
once. Read it as four separate decisions that happen to share a line.

| Flag | Long name | What it changes | What it prevents |
| --- | --- | --- | --- |
| `-e` | `errexit` | the script aborts the moment any command returns non-zero | running on past a failed stage and printing `OK all green` |
| `-u` | `nounset` | using an unset variable is an error, not an empty string | a typo in a variable name silently expanding to nothing |
| `-o pipefail` | — | a pipeline's exit code is the first non-zero in it, not the last command's | a failure being swallowed by the command you piped into |

That is three rows for four letters because `-o pipefail` is written as a separate option with a name
rather than a single letter. `-euo pipefail` is `-e`, `-u`, and `-o pipefail` combined into one word,
which is idiom rather than requirement.

`-e` is the one that makes the gate a gate. The other two are the ways a failure can still slip
past **even with `-e` on**, which is why they travel together as a set.

## Why Sutra needs it

Because the last line of `./m check` is `echo "OK all green"`, and that line is either a claim or a
lie depending on one word four lines from the top of the file.

Look at what those three words are actually promising. Every day of this curriculum ends by running
the gate and writing a row in `docs/PROGRESS.md` saying whether the gates were green. That row is the
project's memory — the last row is where we are, and a stranger picking up this repository in six
months has nothing else. If `OK all green` can print on a run where stage two failed, then the
progress ledger is a record of what the shell felt like saying, and the whole append-only-history
discipline (Principle 2) is built on sand.

You will also add two stages to this script today. Both of them signal failure the only way a
command-line program can: a non-zero exit code
([2.3](../02-a-lint-is-a-test/2.3-the-exit-code-is-the-api.md)). If `-e` were not set, both of your
new stages would print their findings and then be ignored, and you would have spent the day building
two programs whose output nobody acts on.

## The mechanism

The top of the repository's `m` script, verbatim:

```bash
#!/usr/bin/env bash
# Project Sutra daily driver. Replaces `make` (which is not installed on Windows).
# Written on Day 0; every later day assumes it. See days/day-00/parts/03/.
set -euo pipefail
```

**Line by line:**

- `#!/usr/bin/env bash` is the shebang: the first two bytes tell the operating system which
  interpreter to run the file with. `/usr/bin/env bash` finds `bash` on the `PATH` rather than
  assuming it lives at `/bin/bash`, which is what makes the same script work on Linux, macOS and Git
  Bash on Windows.
- `set -euo pipefail` applies to everything below it in the file, including every branch of the
  `case` statement, so the `check)` target inherits it without saying so.
- `-e` — abort on the first non-zero exit code.
- `-u` — treat an unset variable as an error. This is why the script says `DAY="${2:-}"` on the next
  line: `${2:-}` means "the second argument, or empty if there isn't one", and without that explicit
  default `-u` would abort every invocation that passes no day number.
- `-o pipefail` — make a pipeline report the first failure in it rather than the last command's
  result. Nothing in `check)` uses a pipe today, which is exactly why this flag is easy to leave out
  and expensive to have left out later ([5.3](../05-the-gate-that-lied/5.3-the-swallowed-exit-code.md)).

Now prove `-e` does what the table says, with a script that fakes two failures. Write this into the
day's lab so nothing in the gate is disturbed:

```bash
# days/day-31-the-quality-gate/lab/errexit_demo.sh
set -euo pipefail

fake() { echo "fake exit $1"; return "$1"; }

fake 5 || [ $? -eq 5 ]
echo "survived 5"

fake 1 || [ $? -eq 5 ]
echo "NEVER PRINTED"
```

**Line by line:**

- `set -euo pipefail` reproduces the gate's own environment. Without it the whole demonstration
  proves nothing, because everything below would run regardless.
- `fake() { ...; }` defines a shell function standing in for a stage. It prints what it is about to
  do and then `return "$1"` hands back whatever exit code you asked for, which is how you get a
  failing command on demand without breaking anything real.
- `fake 5 || [ $? -eq 5 ]` is the gate's own pytest line with a fake in place of pytest. `||` runs the
  right side only when the left side failed. Crucially, a command on the left of `||` is **exempt
  from `-e`** — that is the rule, and it is the only reason this construction is possible at all: `-e`
  does not abort on a command whose failure is already being handled.
- `[ $? -eq 5 ]` is the test command. `$?` here is still `fake`'s exit code, because `||` has not run
  anything else yet. `-eq` is numeric equality. The whole compound succeeds, so `-e` is satisfied.
- `echo "survived 5"` therefore runs.
- `fake 1 || [ $? -eq 5 ]` fails on both sides: `fake` returns 1, and `[ 1 -eq 5 ]` is false. The
  compound command's exit code is 1, nothing is handling it, and `-e` aborts the script on the spot.
- `echo "NEVER PRINTED"` is named for what it does. If you ever see that string, `-e` is off.

Run it:

```bash
bash days/day-31-the-quality-gate/lab/errexit_demo.sh; echo "exit: $?"
```

**Line by line:**

- `bash <path>` runs the file with `bash` explicitly, so you do not need to make it executable first.
- `; echo "exit: $?"` prints the script's own exit code. A `;` runs the second command
  unconditionally, which is what you want here — you are measuring the failure, not reacting to it.

Measured on 2026-09-04:

```text
fake exit 5
survived 5
fake exit 1
exit: 1
```

Three lines, then the abort. `NEVER PRINTED` is absent, the script's exit code is `1`, and that `1`
came from `fake` and travelled out of the script untouched. That is the whole mechanism of the gate
in four lines of output.

## When it breaks

**`-e` is missing and the gate signs Pass on a failed run.** Delete `set -euo pipefail` from a copy of
the demo and you get:

```text
fake exit 5
survived 5
fake exit 1
NEVER PRINTED
exit: 0
```

`NEVER PRINTED` printed, and the script exited `0` — because with `-e` off, the script's exit code is
the exit code of its last command, and its last command was a successful `echo`. This is the gas
certificate. Every human reading the output sees `fake exit 1` and knows something failed; every
program reading the exit code is told everything is fine.

**`-u` catches a typo you would otherwise never see.** With `set -u`:

```text
m: line 12: DYA: unbound variable
```

Without it, `$DYA` would have expanded to the empty string and the script would have carried on with
a missing day number, doing something subtly wrong to a day you did not name.

**`-e` does not fire where you assumed it would.** This is the flag's genuinely surprising behaviour
and it costs people evenings. `-e` is suppressed for any command whose failure is *already being
tested*: the left side of `&&` or `||`, the condition of an `if`, and anything negated with `!`. So

```bash
if some_check; then echo yes; fi
```

does not abort when `some_check` fails, and that is correct — you asked a question, and "no" is an
answer, not a failure. The trap is the reverse case: a stage written as `lint_something && report`
inside a gate looks like two stages and is one, and `-e` will not save you if the last thing in the
chain succeeds.

**A function's failure disappears inside a command substitution.**

```bash
result="$(failing_command)"
```

Under `-e` this does abort, but the common variant `echo "$(failing_command)"` does not, because the
`echo` succeeds. Any time you wrap a check in something else, check whether you have wrapped its exit
code away too.

## In production

**What a professional writes instead.** `set -euo pipefail` at the top of every shell script that is
not a one-liner, without discussion, plus a `trap` for cleanup when the script creates temporary
state. The trap matters precisely *because* of `-e`: the script can now abort at any line, so
anything it created has to be removed by a handler rather than by a tidy-up line at the bottom that
may never be reached.

```bash
trap 'rm -rf "$TMPDIR_LOCAL"' EXIT
```

**Line by line:**

- `trap '<command>' EXIT` registers a command the shell runs when the script exits, however it
  exits — normal end, `-e` abort, or an interrupt.
- `rm -rf "$TMPDIR_LOCAL"` is the cleanup. Quoting the variable matters here more than anywhere else
  in the script: unquoted and empty, this line becomes `rm -rf`, and with a stray path it becomes
  something much worse.
- The single quotes around the command are deliberate. They stop the variable expanding *now*, at
  registration, so it expands when the trap fires, with whatever value it holds then.

**What degrades at scale.** `-e` becomes uncomfortable once a script legitimately needs to continue
past a failure — for instance a gate that genuinely wants to collect several linters' findings before
reporting. The correct answer is not to remove `-e`; it is to capture the code explicitly, one stage
at a time, and re-raise at the end:

```bash
rc=0
lint_a || rc=1
lint_b || rc=1
exit "$rc"
```

**Line by line:**

- `rc=0` starts an accumulator at success.
- `lint_a || rc=1` runs the stage, and on failure sets the accumulator. The `||` exempts it from `-e`,
  which is the whole reason this pattern is safe to write.
- `exit "$rc"` is the load-bearing line, and it is the one people forget. Without it the script ends
  with whatever the last command returned and the accumulator was theatre — the same bug as the gas
  certificate, rebuilt by hand.

**The review comment a senior engineer leaves:** *"This script has no `set -e`. Every command in it
runs regardless of the one before, and the last line is an `echo`, so it can only ever exit zero.
Right now it's a log, not a check."*

**The interview question:** *"What does `set -euo pipefail` do, and which of those flags would you
refuse to give up?"* The honest spoken answer: *"`-e` aborts on the first non-zero exit code, `-u`
makes an unset variable an error instead of an empty string, and `pipefail` makes a pipeline report
the first failure in it rather than the last command's. `-e` is the one I'd never give up, because
without it a script's exit code is just whatever its last command returned — and the last line of a
gate is usually an `echo` saying everything passed, which always succeeds. So without `-e` the gate
can print a failure and still exit zero. The thing I make sure people know is where `-e` doesn't
fire: the left side of `&&` or `||`, an `if` condition, anything negated. That's correct behaviour —
you asked a question and got an answer — but it means a stage written as part of a chain isn't
protected the way it looks."*
