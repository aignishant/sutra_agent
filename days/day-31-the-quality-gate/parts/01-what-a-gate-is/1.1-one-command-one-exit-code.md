# 1.1 — One command, one exit code

## One-line answer

A quality gate is one command that runs every check the project has and answers with a single number
— zero for green, anything else for red — and in this repository that command is `./m check`, which
already exists, already runs six stages, and today gains two more.

## The story

A small shop closes at nine. Behind the counter there is one switch.

It was not there when the shop opened. For the first year the owner did the round himself: back door,
fridge, till, extractor fan, shutter. Five things, in the same order, every night. He is not careless.
He did it correctly hundreds of times.

Then there was the evening his daughter called from the hospital, and he locked up in ninety seconds
flat, and the extractor fan ran until Monday morning. Nothing burned. The bill was unpleasant and the
smell was worse.

So he had an electrician wire the shutter motor through the other four circuits. Now the shutter will
not come down while the fan is running. He still walks the round — he likes walking the round — but
the round is no longer the thing that protects him. **One action now tells him the truth about all
five, and it tells him by refusing to work.**

The important detail is what the switch does *not* do. It does not print a friendly note about the
fan. It does not light an amber lamp somebody might notice. It refuses to lower the shutter. The
answer is not advice, it is a state, and you cannot leave the shop while it is wrong.

## The idea in plain language

A **quality gate** is one command that runs every automatic check a project has, in order, and
finishes with a single verdict. In this repository it is `./m check`.

Two words in that sentence carry all the weight.

**One.** Not "run ruff, then run the tests, then remember the depth check". One thing to type, one
thing to remember, one thing a new person can be told. The moment there are two commands, the second
one is optional, and the optional one is the one that finds the problem.

**Verdict.** A command-line program finishes by handing the operating system a small whole number
called an **exit code** (also called an exit status or a return code). By long convention, `0` means
success and any other value means failure. It is not text and it is not a summary — it is one integer
that every other program can read without understanding a word of the output.

That distinction is the whole subject. Your printed output has one audience: you. The exit code has
every other audience there will ever be — the shell that decides whether to run the next line, a
continuous-integration server, a scheduled job, a `git` hook, another script. If the printout says
FAILED and the exit code says `0`, then you have been told the truth and every machine has been lied
to.

In a shell you read that number out of the special variable `$?`, which always holds the exit code of
the command that just finished:

```bash
./m check
echo "exit: $?"
```

**Line by line:**

- `./m check` runs the gate. The `./` matters: it tells the shell to run the file named `m` in the
  current directory, rather than searching your `PATH` for a program called `m`. Without it, most
  shells report `m: command not found`.
- `echo "exit: $?"` prints the exit code of the *immediately preceding* command. `$?` is overwritten
  by every command, including `echo` itself, so this line has to come first and be alone. Put another
  command between the two and you will be reading that command's exit code instead.
- The quotes are not decoration. Without them the shell would still work here, but quoting a string
  that contains a variable is the habit that saves you when the value contains a space.

## Why Sutra needs it

Because by the end of Phase 4 this repository has roughly a dozen invariants and no single place that
enforces them.

Some are enforced by `ruff`: import order, unused names, line length. Some by `pytest`: the desk
agent still builds, the loop still calls a tool. Some by `scripts/depth_check.py`: every day document
carries its required sections. And two of them, both invented during Phase 4, are enforced by nothing
at all — a skill folder's shape ([Day 30's](../../../day-30-skill-testing-and-versioning/LESSON.md)
check functions, wired up in [2.2](../02-a-lint-is-a-test/2.2-the-cli-that-adds-no-rules.md)) and the
`:free` suffix on OpenRouter model strings
([3.1](../03-the-free-suffix-lint/3.1-five-characters-that-bill.md)).

Adding a check to the gate is how a rule stops being a thing people know and becomes a thing the
repository knows. That is the difference between a convention and an invariant, and it is the whole
of OPS-08.

You also need it because Phase 5 starts tomorrow and Phase 5 is a protocol. Protocol code fails in
ways that look fine — a response that parses, with the wrong field in it. The projects that survive
that are the ones where a single command already tells them whether anything has moved.

## The mechanism

Here is the gate as it stands on 2026-09-04, copied out of the repository's own `m` script. This is
not a design sketch; it is the file.

```bash
  check)
    uv run ruff check .
    uv run ruff format --check .
    # pytest exits 5 for "no tests collected". Before Day 23 there are none, and an empty suite
    # is not a failure - so 0 and 5 pass and everything else stops the gate.
    uv run python -m pytest -q -m "not live" || [ $? -eq 5 ]
    uv run python scripts/depth_check.py
    uv run python scripts/trace.py
    uv run python scripts/wiki.py
    echo "OK all green"
    ;;
```

**Line by line:**

- `check)` opens one branch of a `case` statement — the dispatcher Day 0 built, which turns the first
  word you type after `./m` into a block of shell to run. `;;` closes the branch. Everything between
  them is the gate.
- `uv run ruff check .` runs the linter over the whole project. `uv run` is what puts the project's
  own pinned tools on the path: it resolves `pyproject.toml` and the lockfile first, so the `ruff`
  that runs is `ruff==0.16.4` from `uv.lock` and never whatever version happens to be installed
  globally. That is Principle 7 at the level of the gate — the check itself is pinned, so a green
  result today means the same thing as a green result in six months.
- `uv run ruff format --check .` asks the formatter whether anything *would* change, without changing
  it. `--check` is the difference between a gate and an edit: a gate reports, it does not reach into
  your files. It is a separate stage from `ruff check` because they answer different questions —
  "is this code wrong?" and "is this code formatted the way we agreed?".
- The comment above the pytest line is doing real work, and
  [5.2](../05-the-gate-that-lied/5.2-green-because-nothing-ran.md) is entirely about whether it is
  still right.
- `uv run python -m pytest -q -m "not live"` runs the test suite. `-q` is quiet output. `-m "not
  live"` deselects every test marked `live`, which is how the suite stays free: the `live` marker is
  on the tests that spend model quota, and the gate must be affordable enough to run constantly.
- `|| [ $? -eq 5 ]` is a forgiveness clause. `||` runs the right side only when the left side failed,
  and `[ $? -eq 5 ]` then asks whether the failure code was exactly `5`, which pytest returns for "I
  collected no tests at all". It succeeds when the code was 5 and fails otherwise, so 0 and 5 both
  pass the gate and 1, 2, 3 and 4 stop it.
- The three `scripts/` lines are the documentation guardians: `depth_check.py` enforces the day
  format, `trace.py` regenerates the traceability ledger, `wiki.py` regenerates the compact index.
  They come after the code checks because they are about `days/` and `docs/`, and a broken repo is
  worth knowing about before a badly-formatted document is.
- `echo "OK all green"` runs **only if every line above it succeeded**. Not because anybody wrote an
  `if` — because of `set -euo pipefail` at the top of the file, which
  [1.3](1.3-the-line-that-makes-it-stop.md) takes apart. That one line is what makes the last `echo`
  a claim rather than a decoration.

There is also a `Makefile` at the repository root. Read it, because it is two lines and it is not
what you think:

```makefile
check:
	@bash ./m check
```

**Line by line:**

- `check:` declares a target named `check`, so `make check` finds it.
- The indented line is the recipe, and it must be indented with a **tab**, not spaces — the one rule
  of `make` syntax that catches everyone.
- `@` suppresses echoing the command before running it.
- `bash ./m check` runs the real gate. So `make check` is not an alternative implementation with its
  own list of stages; it is a shim that forwards to `./m`. There is exactly one gate, and this file
  cannot drift from it because it contains no stages to drift.
- And it only works where `make` is installed, which on a Windows machine it generally is not. That
  is why every day in this curriculum says `./m check` and never `make check`.

## When it breaks

**You run it and read the last line instead of the number.**

```text
$ ./m check
I001 [*] Import block is un-sorted or un-formatted
  --> tests\test_persona.py:7:1
Found 1 error.
[*] 1 fixable with the `--fix` option.
```

There is no `OK all green` there, and if you scrolled past you might assume the rest ran. It did not.
The gate stopped at stage one. The five stages after it — including every test — were never
executed. A gate that stops early tells you one thing is wrong and nothing about the rest, and that
is the correct behaviour ([1.2](1.2-six-stages-cheapest-first.md) explains why).

**You forget the `./` and the shell looks in the wrong place:**

```text
$ m check
bash: m: command not found
```

The file `m` is in the current directory, and the current directory is not on your `PATH` — which is
a security feature, not an oversight.

**You are in PowerShell and the script never starts:**

```text
PS> ./m check
Program 'm' failed to run: An error occurred trying to start process ... The specified executable is not a valid application for this OS platform.
```

`m` is a `bash` script. In PowerShell it needs `bash ./m check`, or run it from Git Bash, which is
the shell every day document in this curriculum assumes.

## In production

**What a professional writes instead.** In a real project the gate is not only a local script; it is
also the exact command a continuous-integration job runs, on a clean checkout, on every pull request.
The script stays in the repository and the CI configuration is one line that calls it. That is
deliberate and it is the same single-source rule you will meet again in
[2.1](../02-a-lint-is-a-test/2.1-two-front-doors-one-rulebook.md): if the CI configuration lists the
stages itself, then CI and your laptop are two implementations of "green" and they will disagree
within a month, always at the worst moment.

**What degrades at scale.** One command that runs everything is exactly right at this size and stops
being right when the suite takes long enough that people avoid it. The professional answer is not to
delete stages; it is to split the gate into a fast tier that runs on every save and a full tier that
runs before a merge, with the full tier still being *one* command. The failure to avoid is a gate
that quietly becomes advisory because it is inconvenient — a check people skip is a check you do not
have, and it is worse than no check because it appears on the status page.

**What only appears with real traffic.** Concurrency. The moment two jobs run `./m check` on the same
machine, the stages that *write* files — `trace.py` and `wiki.py` regenerate ledgers — can interleave
and produce a diff that belongs to neither run. A mature gate separates checking from generating:
generators run with a `--check` flag in the gate and write only when a human asks. `ruff format
--check` is already the good example in the list above; the two ledger generators are the ones that
will need it, and that is a genuine piece of technical debt in this repository today.

**The review comment a senior engineer leaves:** *"You added the check to the CI config. Add it to
the gate script instead and have CI call the script. Otherwise I can't reproduce a red build on my
machine, and you've just made every failure a conversation with the build server."*

**The interview question:** *"What does 'green' mean in your repository, and how is it enforced?"*
The honest spoken answer: *"One command — `./m check` — that runs the linter, the formatter check,
the offline test suite and three documentation checks, in that order, stopping at the first failure
and propagating a non-zero exit code. The exit code is the contract, not the output: humans read the
text, but the shell, CI and any hook read exactly one integer, so a gate that prints errors and exits
zero is worse than no gate because it launders red into green. We drill the red path deliberately —
plant a break, watch the right stage stop with the right file named, remove the break — because a
gate you have never seen fail is a gate you cannot trust."*
