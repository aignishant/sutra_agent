# 4.1 — Two lines in the driver

## One-line answer

The whole of OPS-08's build is two lines added to the `check)` target in `m`, placed after the
formatter check and before the test suite so that the cheap checks run before the expensive one, and
they need no `if`, no error handling and no summary because `set -euo pipefail` already does all
three.

## The story

There is a recipe card taped inside the cupboard door, above the kettle.

Four people use that kitchen and none of them owns the card. It says how much water goes in the rice,
because that is the thing everybody gets wrong and nobody wants to re-derive at seven in the evening.
When somebody works out that the new bag needs a little less, they do not send a message about it and
they do not remember to mention it. They take a pen and they change the card.

The card is short, which is why it still works. Somebody once wrote a paragraph on the back about why
the measurement changed, and within a month the card was something you read rather than something you
glanced at, and people started going back to guessing. It got copied out, short again, and the
paragraph went into a notebook in the drawer.

The card holds the *decision*. The reasoning lives somewhere you can find it and do not have to walk
past every evening.

## The idea in plain language

The gate is a shared card on a cupboard door. Everything that has to be true before a commit is on
it, one line each, in order.

So adding a check to the gate is a two-part job and only one part is code.

The **decision** goes on the card: one line in `m`, in the right position. It has to be short,
because the `check)` target is read by every person and every future agent working in this repository
and its value comes from being scannable.

The **reasoning** goes here, in this document, and in the linter's own docstring. Why these stages,
why this position, what the exemption markers mean — none of that belongs in the shell script, for
exactly the reason the paragraph came off the recipe card.

Three things the new lines do *not* need, and each absence is worth understanding rather than
copying.

**No `if`.** The stage either exits zero or it does not, and `set -e` handles the second case by
aborting the script ([1.3](../01-what-a-gate-is/1.3-the-line-that-makes-it-stop.md)). A shell `if`
around a gate stage almost always means somebody is about to swallow its exit code.

**No error message.** The linter already printed one, with a file and a line number
([3.2](../03-the-free-suffix-lint/3.2-what-the-lint-must-read.md)). A wrapper that adds *"skills lint
failed"* on top has added a line of noise above the useful output.

**No `&&` or `;` chaining.** One command per line. Chained commands hide which half failed, and under
`-e` they can change *whether* the failure aborts at all — the left side of `&&` is exempt from
`-e` ([1.3](../01-what-a-gate-is/1.3-the-line-that-makes-it-stop.md)).

## Why Sutra needs it

Because this is the moment SK-20 actually closes. Everything before it — Day 30's rules, today's two
linters — is machinery that nothing calls.

It is also the shape every later gate change follows. Day 45 adds `tools/mcp_audit.py` and one more
line here, as the Phase 6 gate. Whoever writes that day will open `m`, see two lines in the same
shape, and add a third without needing to be told the convention. A gate that is easy to extend
correctly is a gate that gets extended correctly, and consistency in a nine-line block is what makes
that true.

And there is a smaller, sharper reason to be careful with the edit itself: `m` is the one project
file today changes, and it is the file every other command in this repository runs through. A
mistake here does not fail the new stage, it fails `./m depth`, `./m done` and everything else. Read
the diff before you type it.

## The mechanism

The diff, exactly:

```diff
   check)
     uv run ruff check .
     uv run ruff format --check .
+    uv run python -m tools.lint_skills
+    uv run python -m tools.lint_free_suffix
     # pytest exits 5 for "no tests collected". Before Day 23 there are none, and an empty suite
     # is not a failure - so 0 and 5 pass and everything else stops the gate.
     uv run python -m pytest -q -m "not live" || [ $? -eq 5 ]
     uv run python scripts/depth_check.py
     uv run python scripts/trace.py
     uv run python scripts/wiki.py
     echo "OK all green"
     ;;
```

**Line by line:**

- The two `+` lines are the entire change. Nothing else in the target moves, and the leading
  four-space indentation matches the lines around it — `m` is a shell script, so the indentation is
  cosmetic, but a target that is aligned is a target people read.
- `uv run` on both, like every other stage. This is what guarantees the linters run under the
  project's Python 3.12 and can see the project's dependencies, rather than under whatever `python`
  happens to be first on the `PATH`. On a machine with three Pythons installed — which is most
  machines — this is the difference between a stage that works and a stage that fails with an import
  error nobody can reproduce.
- `python -m tools.lint_skills`, not `python tools/lint_skills.py`. The `-m` form is not a style
  choice; the path form cannot import `tools.skill_checks` and fails with `ModuleNotFoundError`.
  [4.2](4.2-the-module-the-script-cannot-find.md) is that failure and why the flag fixes it.
- `tools.lint_free_suffix` uses `-m` too, even though that module has no intra-package import and
  would run either way. Two stages in the same block should be invoked identically; an inconsistency
  here is a small thing somebody has to hold in their head every time they read the file, and the
  next person to add a stage will copy whichever line they happen to look at.
- **Position: after the formatter check, before pytest.** Both linters read a few hundred small text
  files and import nothing but the standard library; the test suite imports `google-adk`. Cost
  ordering says the cheap decisive checks go first
  ([1.2](../01-what-a-gate-is/1.2-six-stages-cheapest-first.md)), so a run that is going to fail on a
  missing `:free` suffix fails before it pays for the framework import.
- **Order between the two:** skills lint first, `:free` lint second. This one is genuinely arbitrary
  — they are independent and neither can fail because of the other — and the reason it is written
  down at all is that a reader will wonder. The tiebreak used here is that they are in the same order
  as the day's sections and the same order as the phase gate's checklist, so three lists agree.
- No line was removed. In particular the pytest comment stays exactly where it is, because it
  explains the `|| [ $? -eq 5 ]` on the line below it and separating them would strand it.

After the edit, the target's stage list reads:

| # | Stage | Added on |
| --- | --- | --- |
| 1 | `ruff check .` | Day 0 |
| 2 | `ruff format --check .` | Day 0 |
| 3 | `python -m tools.lint_skills` | **today** |
| 4 | `python -m tools.lint_free_suffix` | **today** |
| 5 | `python -m pytest -q -m "not live"` | Day 0, populated from Day 23 |
| 6 | `scripts/depth_check.py` | Day 0 |
| 7 | `scripts/trace.py` | Day 0 |
| 8 | `scripts/wiki.py` | Day 0 |

Now verify the edit did what you meant, before you rely on it:

```bash
grep -n "lint_" m
./m check; echo "exit: $?"
```

**Line by line:**

- `grep -n "lint_" m` prints the two new lines with their line numbers, which confirms they landed in
  the file and — by their position relative to the other stages — that they landed in the right
  place. Reading the file back after editing a shared script is a small ritual worth having.
- `./m check` runs the whole gate with the new stages in it.
- `; echo "exit: $?"` because the number is the thing you are checking
  ([2.3](../02-a-lint-is-a-test/2.3-the-exit-code-is-the-api.md)).

Then drill the red path, which is the only way to know the wiring works. The offending string is
assembled by `printf` rather than typed, because `m` is itself scanned by the `:free` lint and a bad
string written literally into the repository would be a finding
([3.3](../03-the-free-suffix-lint/3.3-the-alarm-that-fires-on-toast.md)):

```bash
printf '_OOPS = "openrouter/%s"\n' "some-vendor/some-model" >> tools/lint_skills.py
./m check; echo "exit: $?"
```

**Line by line:**

- `printf '_OOPS = "openrouter/%s"\n' "some-vendor/some-model"` builds the line with the vendor and
  model supplied as an argument, so this document never contains the complete offending string.
- `>>` appends rather than overwrites. `>` here would erase the linter you just wrote.
- The gate then stops at stage 4 with the file, the line number and the string named, and returns 1.
  Stage 5 — the test suite — never runs, which is the cost ordering paying for itself in front of
  you.
- Remove the line afterwards. `git diff tools/lint_skills.py` should be empty before you commit.

## When it breaks

**The stage is there and the gate is still green.** You added the lines to the wrong branch of the
`case` statement — `done)` calls `"$0" check` and looks similar enough to skim past. The tell:

```text
$ ./m check
...
OK all green
$ grep -n "lint_" m
118:    uv run python -m tools.lint_skills
```

One line where there should be two, and its number is well past the end of `check)`.

**The gate dies before the linters with a shell error.**

```text
m: line 92: syntax error near unexpected token `)'
```

An edit that broke the `case` statement — usually a missing `;;` or a stray parenthesis. Because `m`
is the driver, *everything* stops working, including `./m depth`. Recover with `git diff m` and read
what you actually changed.

**`ModuleNotFoundError` from the new stage.**

```text
ModuleNotFoundError: No module named 'tools'
```

You wrote `python tools/lint_skills.py`. This is the single most likely thing to go wrong today and
it has a part of its own: [4.2](4.2-the-module-the-script-cannot-find.md).

**The linters run and the gate ignores their answer.** Symptom: the lint prints `FAIL` lines and
`OK all green` appears anyway.

```text
FAIL ticket-triage: SKILL.md has no description
OK all green
```

Two possible causes, and both are worth checking in order. Either the stage was written with a
trailing `|| true`, or `set -euo pipefail` has been removed from the top of the file. Under `-e`
neither of those outputs can coexist ([1.3](../01-what-a-gate-is/1.3-the-line-that-makes-it-stop.md),
[5.3](../05-the-gate-that-lied/5.3-the-swallowed-exit-code.md)).

## In production

**What a professional writes instead.** Once a gate has more than a handful of stages, the stage list
moves out of a `case` branch and into data — a list of `(name, command)` pairs read by a small
runner, so each stage can be named in the output and skipped by name during debugging. That is the
right move at fifteen stages and the wrong move at eight, because the runner is code that can have
bugs and the shell script cannot have many. The rule of thumb is that the list becomes data at the
point where you want to *address* a stage, not before.

**What degrades at scale.** Two things. The gate's total cost grows with every line added, and
because the cost is paid on every commit, a gate grows until somebody stops running it — which is
why new stages get scrutinised for cost, not just correctness. And ordering becomes a real
maintenance surface: each new stage's position encodes an assumption about relative cost, and nobody
re-measures. Mature setups print each stage's duration, which turns the ordering question into an
observation rather than an argument.

**The failure mode that only appears with real traffic** is a stage that is fast on the author's
machine and slow on everyone else's — a check that walks the whole tree is quick on a warm cache and
slow on a cold one, and slower still on a network filesystem or a synced folder. This repository
already lives on a cloud-synced directory, which is precisely the environment where a whole-tree walk
costs the most, and it is why the pruning in
[3.2](../03-the-free-suffix-lint/3.2-what-the-lint-must-read.md) is not premature optimisation.

**The review comment a senior engineer leaves:** *"Two new gate stages and no drill in the PR. Please
show me the output of the gate failing on each of them — I want to see the right stage stop with the
right file named. A stage nobody has watched go red is a stage we're assuming works."*

**The interview question:** *"How do you add a check to your build so that it actually gates?"* The
honest spoken answer: *"One line in the gate script, positioned by cost — cheap static checks before
the test suite — and then I prove it. The proving is the part people skip: I plant a violation, run
the gate, and confirm it stops at the right stage, names the file and line, and exits non-zero, and
that the stages after it didn't run. That last detail matters because it's evidence the fail-fast
ordering is working. The line itself needs no error handling or `if`, because the script runs under
`set -euo pipefail` and the check already prints a good message — a wrapper that catches and re-prints
is just noise above the useful output, and it's usually how an exit code gets lost."*
