# 3.3 — The test for the checker

## One-line answer

A green shelf lane cannot tell you whether your shelf is clean or whether your checks do nothing, so
every rule needs a second test that hands it something broken and demands the finding — otherwise the
suite is measuring your skills' silence, not your checks' vigilance.

## The story

The smoke alarm in the hallway has been silent for two years, and everyone in the flat is pleased
about that.

They are right to be. Two years without a fire is exactly what you want. But silence is also what a
dead alarm sounds like, and a dead alarm sounds like it from the first day of the two years to the
last. The battery went flat, or the sensor clogged with dust, or somebody knocked the plug half out
when they were painting — and from the corridor, all four of those look identical to a working alarm
in a house that is not on fire.

That is why the alarm has a button on it. Press it and it screams. It is the only way anybody can tell
the difference between *nothing is burning* and *this thing stopped working*, and it takes one press.

The households that never press it are not being reckless. They are making a very ordinary mistake:
treating the absence of an alarm as evidence that the alarm works.

## The idea in plain language

Your shelf lane asserts `check_shelf(SHELF) == []`. When it passes, exactly two things could be true:

1. every skill on the shelf breaks no rule; or
2. your checks do not fire on anything.

The test cannot distinguish them, and the second one is not a silly hypothetical. A regular expression
that never matches, a comparison written the wrong way round, a function that returns `[]` before it
reaches the `if` — all of them produce a check that is permanently, quietly happy, and all of them
make the suite greener rather than redder, so nothing draws your attention to them.

The fix is the alarm's button: **for every rule, one test that gives it something broken and asserts
that it produces the specific finding.** Not "produces some findings" — that would pass if the check
had latched on to the wrong thing — but the exact rule tag, which is why
[3.2](3.2-a-failure-must-name-the-file.md) insisted the tag be a stable identifier rather than prose.

This is a general property with a name worth carrying: a test suite that has only ever been seen to
pass has demonstrated that some code ran. It has not demonstrated that the code would notice a
problem. [Day 23, 5.2](../../../day-23-testing-tools-and-callbacks/parts/05-failure-lab/5.2-the-fake-that-could-not-fail.md)
met the same idea from the other end — a test double built so that it could not produce the failure the
test claimed to check — and this is the same disease in the checker rather than in the fake.

## Why Sutra needs it

Because five of Sutra's six rules are ones you wrote this morning, and a rule that has never fired is
a rule you have never seen work.

`check_references` is the sharpest case. Its regular expression has a character class with a
deliberate restriction on its final character
([2.4](../02-checks-as-functions/2.4-pointers-that-go-nowhere.md)), and the version of it that
swallows the sentence's full stop and the version that does not are one character apart. The shelf
lane passes identically under both, because Sutra's own references all resolve. Only a test that
plants a broken pointer tells the two apart.

The second reason is Day 31. Tomorrow the same functions become a merge gate
(`days/day-31-the-quality-gate/`), and a gate that cannot go red is a gate in name only — it is
Principle 11 exactly: an eval is a test, and a test that cannot fail is not a test.

## The paper behind it

> **Hints on Test Data Selection: Help for the Practicing Programmer**, `doi:10.1109/C-M.1978.218136`,
> 1978. `https://doi.org/10.1109/C-M.1978.218136`

The claim: you can judge a test suite by making small, deliberate errors in the program — mutants —
and counting how many of them the suite notices, because a suite that cannot tell a broken program
from the real one is not testing the program however much of it it executes.

Read it after the parts: [Hints on Test Data Selection](../../papers/01-hints-on-test-data-selection.md).

## The mechanism

The pattern is one test per rule, each holding a case that must produce a finding. The cases here are
built in memory rather than on disk, and how that works is [4.1](../04-skills-built-in-code/4.1-a-skill-without-a-folder.md)'s
subject — for now, read `a_skill(...)` as *a valid skill with these fields*.

```python
@pytest.mark.parametrize(
    ("version", "rule"),
    [
        (None, "no-version"),
        (1.1, "unquoted-version"),
        ("v1", "bad-version"),
        ("1", "bad-version"),
        ("1.2.3.4", "bad-version"),
    ],
)
def test_check_version_names_the_rule_it_broke(version: object, rule: str) -> None:
    skill = a_skill() if version is None else a_skill(version=version)
    assert [f.rule for f in check_version(skill)] == [rule]


@pytest.mark.parametrize("version", ["1.0", "1.1", "2.0.1"])
def test_check_version_accepts_a_quoted_version(version: str) -> None:
    assert check_version(a_skill(version=version)) == []


def test_check_description_wants_a_when() -> None:
    broken = a_skill(description="Handles ticket triage.")
    assert [f.rule for f in check_description(broken)] == ["no-when"]
```

**Line by line:**

- `@pytest.mark.parametrize` runs the same test body once per row and reports each as its own case
  ([Day 23, 2.4](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.4-parametrize.md)).
  Five broken versions become five named failures, so a report says *which* input stopped being caught
  rather than "the version test failed".
- The rows are a **table of the rule's behaviour**, and reading them top to bottom is the fastest
  documentation of `check_version` there is: missing, unquoted, unparseable, too few fields, too many.
  A reader who wants to know what the rule accepts reads the parameters, not the function.
- `(1.1, "unquoted-version")` passes a **float**, deliberately, because that is what YAML produces from
  an unquoted `version: 1.10` — and `1.10` becomes `1.1`, losing a digit on the way
  ([5.1](../05-versioning/5.1-a-name-for-the-text-that-ran.md)). The test encodes a real trap rather
  than a hypothetical type error.
- `assert [f.rule for f in check_version(skill)] == [rule]` compares the **list of tags**, so it
  asserts three things at once: that a finding was produced, that there was exactly one, and that it
  was the right rule. `assert check_version(skill)` alone would pass if the wrong rule fired.
- The second test is the mirror and it matters as much: the good inputs produce **no** finding. A rule
  that fires on everything also passes every test in the first block. Both directions, always.
- `test_check_description_wants_a_when` uses `"Handles ticket triage."` — the exact string from
  [Day 28's](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.4-the-crowded-shelf.md)
  worked example of a description that stops routing. Using the real regression rather than
  `"xyz"` means the test doubles as a record of what went wrong once.

Run just this lane and watch each case listed:

```bash
uv run python -m pytest tests/test_skills.py -k "check_" -v
```

**Line by line:**

- `-k "check_"` selects the tests whose names contain `check_` — the checker lane — and skips the shelf
  lane, so you are looking only at the alarm-button tests.
- `-v` prints one line per case with its parameters, which is what turns five parametrized rows into
  five readable names in the output. Without it you get five dots and no way to tell which row is
  which.

## When it breaks

**The check that could never fire.** Suppose `check_version` had been written with the comparison
inverted, so it returns `[]` for everything. The shelf lane still passes — every skill on the shelf has
a version, so no finding was expected. The checker lane does this instead:

```text
_____________ test_check_version_names_the_rule_it_broke[None-no-version] _____________

    def test_check_version_names_the_rule_it_broke(version: object, rule: str) -> None:
        skill = a_skill() if version is None else a_skill(version=version)
>       assert [f.rule for f in check_version(skill)] == [rule]
E       AssertionError: assert [] == ['no-version']
E         Right contains one more item: 'no-version'
```

`assert [] == ['no-version']` is the whole point of this part in one line: the check was asked to
complain and said nothing.

**A test that asserts too loosely.** `assert check_version(skill)` passes as long as *some* finding
came back. A check that reported `no-when` for a missing version would sail through it, and you would
believe you had coverage on a rule you do not. Assert on the tag.

**Testing the checker by breaking the real shelf.** It is tempting: edit `skills/ticket-triage`, watch
the test go red, put it back. It works once, by hand. It cannot live in the suite, because a test that
mutates the repository leaves the shelf broken whenever it fails partway, and two such tests running
in any order interfere with each other. The cases have to be constructed, not borrowed — which is why
section 4 exists.

## In production

**What a professional writes instead** of hand-picked broken cases, on a mature codebase, is a
mutation run: change one token in the checker itself, re-run the suite, and see whether anything went
red ([the paper](../../papers/01-hints-on-test-data-selection.md)). It is the smoke-alarm button
applied to every line at once, and it answers the question this part opened with — *do my checks
actually notice things* — without anyone guessing which broken cases to write. It is not free, and the
paper part is honest about why full mutation runs stayed a research technique for decades.

**What degrades at scale** is the ratio of shelf tests to checker tests. With six rules you can hold
in your head which ones have a firing test. With thirty rules, added by five people over two years,
some of them have never fired since the day they were written, and there is no way to tell by reading.
The teams that stay honest about this either run mutation on the checker module on a schedule, or make
the firing test a required part of the pull request that adds a rule — the second is cheaper and
almost as good.

**The review comment a senior engineer leaves:** *"you added a rule and one test that a good skill
passes it. That test would still pass if the function returned an empty list unconditionally. Add the
case that must produce the finding, and assert on the rule tag rather than on truthiness."*

**The interview question:** *"your validation suite is green. How do you know the validators work?"*
The honest spoken answer: *"A green run over real data proves either that the data is clean or that
the checks do nothing, and it cannot tell you which — it is a silent smoke alarm. So every rule has a
second test that hands it a case that must fail and asserts on the specific rule identifier, plus its
mirror asserting that good input produces no finding. Both directions, because a check that fires on
everything passes the first half. Beyond that, the real answer is mutation testing: change one token in
the checker, re-run the suite, and if nothing goes red the suite was not testing that line. That is a
1978 idea and it is still the only honest measure of whether a suite would notice a bug."*
