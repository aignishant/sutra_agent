# 3.2 — A failure must name the file

## One-line answer

A red test over a whole shelf has to print the folder, the rule and the offending text, because the
person reading the failure is usually not the person who caused it and has no idea which of forty
files to open.

## The story

The plumber leaves a note through the door: *"leak somewhere upstairs, will need access."*

Every word of it is true. There is a leak. It is upstairs. Access will be needed. And the person who
comes home to that note has three bedrooms, a bathroom and an airing cupboard, and no idea which one
to look in, so they look in all five, find nothing, and wait for the plumber to come back and point at
it.

The note that works costs the plumber the same effort and says: *"leak from the cold feed under the
bathroom basin, left-hand joint."* Now the homeowner can put a bucket under it tonight.

Both notes were written by somebody standing right beside the problem. The difference is only whether
they wrote down what they were looking at.

## The idea in plain language

A test that checks one thing can afford a vague message, because the test's name already says what
broke. `test_lookup_ticket_returns_none_for_unknown_id` failing tells you everything.

A test that checks a **collection** cannot. `test_every_skill_on_the_shelf_passes_every_check` failing
tells you that one of an unknown number of skills broke one of six rules, which is the plumber's first
note. The information exists — the check function knew the folder, the rule and the exact string — and
the only question is whether the assertion carries it out.

There are three things a good collection failure carries, and they map exactly onto `Finding`'s three
fields ([2.1](../02-checks-as-functions/2.1-a-finding-is-a-return-value.md)):

| The reader asks | The field | Example |
| --- | --- | --- |
| Which one? | `skill` | `ticket-triage` |
| What kind of problem? | `rule` | `dead-pointer` |
| What exactly? | `detail` | `body points at references/severity-rubric.md` |

The third one is where most messages fail. A `detail` of *"a reference is missing"* is the plumber's
first note again: correct, useless. A `detail` that quotes the offending string lets the reader fix it
without opening the file, and — this matters more than it sounds — lets them **search the repository
for it**, which is what a person actually does when a name is unfamiliar.

## Why Sutra needs it

Because the person who reads this failure is often not the person who wrote the skill.

The failure appears in continuous integration on somebody's pull request. It might be a pull request
about something else entirely that happened to rebase onto a change to `skills/`. The reader has no
context, no memory of the rubric being renamed, and about one minute of patience before they conclude
the pipeline is flaky and hit re-run. What is printed in those first lines decides whether the problem
gets fixed or gets ignored.

It matters again on Day 31 (`days/day-31-the-quality-gate/`), where the same findings become the
output of `./m check`. A message written for a person staring at a terminal is the same message that
works in a pull request comment, which is why the format is fixed in `Finding.__str__` rather than
formatted at each call site.

## The mechanism

First, the two remaining shape rules, chosen here because their messages are the whole lesson.

```python
def check_description(skill: Skill) -> list[Finding]:
    """House rule: a description says what the skill does AND when to reach for it."""
    text = skill.description.lower()
    if not any(word in text for word in WHEN_WORDS):
        return [Finding(skill.name, "no-when", "description never says when to use the skill")]
    return []


def check_body_length(skill: Skill) -> list[Finding]:
    """The spec recommends keeping SKILL.md under 500 lines."""
    lines = len(skill.instructions.splitlines())
    if lines > MAX_BODY_LINES:
        return [Finding(skill.name, "long-body", f"{lines} lines, over {MAX_BODY_LINES}")]
    return []
```

**Line by line:**

- `WHEN_WORDS` is the module constant from
  [2.1](../02-checks-as-functions/2.1-a-finding-is-a-return-value.md):
  `("use when", "use for", "when a", "when the", "when you", "when someone")`. It is a fixed list of
  phrases, which keeps this firmly in the shape column
  ([1.2](../01-testing-prose/1.2-shape-and-sense.md)) — the check asks *does the string contain one of
  these*, never *is the clause any good*.
- `.lower()` once, before the loop, rather than lowercasing inside the comparison. It reads better and
  it means the phrase list can be written in lower case only, which removes a whole class of
  "why did this not match" confusion.
- `any(... for ...)` short-circuits on the first match. On a description that starts with a *when*
  clause the check does one substring search.
- The `no-when` detail says *what is absent*, not *what the rule is*. `"description never says when to
  use the skill"` sends the reader to
  [Day 28, 2.1](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.1-a-description-is-a-routing-row.md)'s
  what-and-when shape; a detail of `"fails WHEN_WORDS check"` would send them to your source code.
  Write the message for the person who has not read the checker.
- `check_body_length`'s detail is `f"{lines} lines, over {MAX_BODY_LINES}"` — both numbers. *"body too
  long"* would make the reader count the file. *"640 lines, over 500"* tells them how much to move and
  is enough to decide whether this is a trim or a refactor.
- `splitlines()` on `skill.instructions`, which is the body **after** the frontmatter, so the count is
  of the part the specification's 500-line recommendation is about. Counting the whole file would
  include the frontmatter and be quietly wrong by a handful of lines.

Now the assertion that carries all of it out. This is the line from
[3.1](3.1-enumerate-never-list.md), read for its message rather than its logic:

```python
def test_every_skill_on_the_shelf_passes_every_check() -> None:
    findings = check_shelf(SHELF)
    assert findings == [], "\n" + "\n".join(str(f) for f in findings)
```

**Line by line:**

- The second argument to `assert` is the message `pytest` prints when the assertion fails, and it is
  the only place the findings can be rendered. Without it, `pytest` shows you the repr of a list of
  dataclasses, truncated in the middle, which is the plumber's first note with extra punctuation.
- `"\n" + ...` puts the first finding on its own line. `AssertionError: ticket-triage  dead-pointer …`
  with the first row welded to the exception name is measurably harder to scan, and every subsequent
  row would line up against nothing.
- `"\n".join(str(f) for f in findings)` uses `Finding.__str__`, so a failure in the test suite and a
  report from Day 31's linter print byte-for-byte the same rows. One format to learn, not two.
- `findings == []` rather than `not findings`: on failure `pytest` prints both sides of a comparison,
  and the left side is your list of findings. You get the rendered message *and* the structured diff.

What a real red run looks like. Measured on 2026-09-04, after renaming a reference file and leaving
the body alone:

```text
______________ test_every_skill_on_the_shelf_passes_every_check _______________

    def test_every_skill_on_the_shelf_passes_every_check() -> None:
        findings = check_shelf(SHELF)
>       assert findings == [], "\n" + "\n".join(str(f) for f in findings)
E       AssertionError:
E         ticket-triage            dead-pointer     body points at references/severity-rubric.md
E       assert [Finding(skil...y-rubric.md')] == []

E         Use -v to get more diff

tests\test_skills.py:40: AssertionError
```

A reader who has never seen this repository can fix that. They know the folder, they know the rule,
and they have the exact string to search for.

And the same assertion when a whole skill is wrong in three ways at once, measured the same day after
dropping an unfinished skill onto the shelf:

```text
E       AssertionError:
E         sla-breach-check         no-when          description never says when to use the skill
E         sla-breach-check         dead-pointer     body points at references/clock.md
E         sla-breach-check         no-version       metadata.version is missing
```

Three rows, one folder, in cheapest-first order. That is the payoff from
[2.3](../02-checks-as-functions/2.3-one-bad-folder-must-not-stop-the-shelf.md): every problem in one
run, so the fix is one commit.

## When it breaks

**The assertion with no message.** Somebody writes `assert not check_shelf(SHELF)` and `pytest` gives
you this:

```text
E       assert not [Finding(skill='ticket-triage', rule='dead-pointer', detail='body points at re...
E        +  where [Finding(skill='ticket-triage', rule='dead-pointer', detail='body points at re...] = check_shelf(...)
```

Truncated exactly where the useful part starts. The information was in the process and did not reach
the screen.

**A detail that names the checker instead of the problem.** `detail="WHEN_WORDS not matched"` is a
sentence about your implementation. Six months later, `WHEN_WORDS` has been renamed and the message
refers to something that does not exist. Details describe the skill; rule tags describe the checker.

**A rule tag written as prose.** If `rule` held `"the description does not say when to use this
skill"`, then the report cannot group, the assertion `[f.rule for f in findings] == ["no-when"]` in
[3.3](3.3-the-test-for-the-checker.md) becomes a test of your wording, and improving the wording
breaks tests that have nothing to do with the change. Tags are an interface; details are prose.

## In production

**What a professional writes instead** of a single collection assertion is often a **parametrized**
test — one `pytest` case per skill, generated by walking the shelf at collection time
([Day 23, 2.4](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.4-parametrize.md)).
Then the report says `FAILED test_skill[ticket-triage]` and a reader sees which skills are red in the
summary line without expanding anything. The cost is that parametrizing over a directory walk means
the walk happens at import time, and a missing directory becomes a collection error rather than a
readable failure. Sutra keeps the single assertion because four skills fit on a screen; a team with
forty should parametrize, and should keep the same `Finding` rendering inside each case.

**What degrades at scale** is the length of the message, and it degrades into unreadability rather
than into error. Forty skills each missing a version is forty identical rows, and the useful output is
*"38 skills missing `metadata.version`; 2 will not load: `x`, `y`"*. The fixed `rule` tag is what makes
that summary two lines of `collections.Counter`, which is the argument for the tag being an
identifier, made concrete.

**The review comment a senior engineer leaves:** *"the assertion is right but the message is the
default repr, so the failure in CI is truncated at the point where it starts being useful. Pass a
message that renders one finding per line — the check already knows the folder and the rule, and it is
free to say them."*

**The interview question:** *"what makes a good test failure message?"* The honest spoken answer:
*"That the person who reads it is usually not the person who broke it. For a test over one function
the test name is enough. For a test over a collection it is not — 'one of your forty config files is
wrong' is a note that says there is a leak somewhere upstairs. So each check returns a record with
three fields: which item, which rule as a stable tag, and the exact offending text. The assertion
renders one row per finding, so the reader gets the folder, the rule and a string they can search the
repository for. Keeping the rule as a tag rather than a sentence matters twice: assertions can compare
on it without depending on wording, and a hundred findings can be grouped into a summary."*

## Check yourself

```bash
uv run python -m pytest tests/test_skills.py -k shelf
```

Now rename `skills/ticket-triage/references/severity-rubric.md` to `references/rubric.md`, run it
again, and read the failure. Cover the screen after the first two lines and ask yourself whether you
could fix the problem from what you have seen. Rename the file back.

**Out loud, without scrolling up:** name the three questions a collection failure must answer and the
field that answers each, explain why the rule tag is an identifier rather than a sentence, and say what
`assert findings == []` gives you that `assert not findings` does not.
