# 3.1 — Enumerate the shelf, never a list

## One-line answer

The test must ask the filesystem what is on the shelf every time it runs, because any list of skills
written into the test is a copy of the truth that stops being true the first time somebody adds a
skill — and it stops being true silently, while the suite stays green.

## The story

Your neighbour waters the plants while you are away, from the note you left her last year.

She does it properly. The note lists five pots and how much water each one gets, so she goes down the
list, pot by pot, and every item is done before she leaves. There is no mistake in it anywhere. She
comes back on Thursday and does the same five.

Since you wrote that note, three more pots have gone in along the wall by the back door.

They are not on the list, so they are not watered, and because they are not on the list nothing about
the visit feels unfinished. The note is completed correctly, every single time, and it describes a
garden that no longer exists.

The first time it happens you notice, because you can see the dry soil when you get home. By the
fourth trip, the note has quietly become the definition of what is in the garden, and nobody involved
believes anything is going wrong.

## The idea in plain language

There are two ways to write a test over a collection of things on disk.

**Name them.** `SKILLS = ["ticket-triage", "kb-answer-style"]`, then loop over the list. It is
explicit, it is readable, and the diff when you add a skill shows exactly which one you added.

**Enumerate them.** Ask the directory what is in it, at the moment the test runs.

The first is the watering note, and it has one fatal property: **the failure mode is a pass**. Add a
third skill, forget the list, and the suite goes green while checking two thirds of the shelf. Nothing
tells you. There is no error, no warning, no line in the output that says *"2 of 3 skills checked"*.
The test is now making a claim — *the shelf is clean* — that it has no evidence for.

Compare that to the honest failure. If enumeration is wrong, it is wrong loudly: the directory is
missing, or empty, and the test says so.

The rule that comes out of this is worth stating in one line, because it generalises far past skills:

> **A test's list of inputs must come from the same place production's list comes from.**

Production loads `skills/` by walking it. Your test must walk it too. Any other list is a second
definition of *the shelf*, and two definitions of one thing drift — that is the same argument
[2.2](../02-checks-as-functions/2.2-let-the-loader-be-the-oracle.md) made about re-implementing the
specification, applied to the input set instead of to the rules.

## Why Sutra needs it

Because `skills/` is going to grow, and it is going to grow by people who are not thinking about
tests.

That is the whole design. Day 27 put the triage procedure into a Markdown file so it could be edited
by someone who writes no Python, and Day 29 established a process for bringing skills in from outside.
Both of those add folders. A hardcoded list means the person who adds a folder must also edit a Python
file they have never opened, in a directory they have no reason to look at, and be right about it.
They will not, and there is no reason they should have to.

There is a second reason, and it is the one that bites in continuous integration. A test that
enumerates catches the *absence* of a skill as well as a broken one. If a rebase drops
`skills/kb-answer-style/`, `test_the_shelf_is_not_empty` and the desk agent's own behaviour are the
only things that would notice — and the desk agent notices at runtime.

## The mechanism

Create the test file and point it at the shelf. This is the first half of `tests/test_skills.py`:

```python
"""The skills shelf under test - three lanes, zero model calls.

The shelf lane: every folder in skills/, enumerated live, breaks no rule.
The checker lane: the checks run against skills built in memory, so each rule can be
proved to fire without a broken folder ever existing on disk.
The boundary lane: one test that states, in code, what these checks cannot know.
"""

from __future__ import annotations

import pathlib

import pytest
from google.adk.skills import Frontmatter, Resources, Skill
from pydantic import ValidationError

from tools.skill_checks import check_description, check_shelf, check_version

SHELF = pathlib.Path(__file__).resolve().parents[1] / "skills"


def test_the_shelf_is_not_empty() -> None:
    assert [p for p in SHELF.iterdir() if p.is_dir()], "skills/ holds no skill folders"


def test_every_skill_on_the_shelf_passes_every_check() -> None:
    findings = check_shelf(SHELF)
    assert findings == [], "\n" + "\n".join(str(f) for f in findings)
```

**Line by line:**

- The module docstring names the three lanes before any code, so a reader who opens this file knows
  what it does and does not cover. That is [1.2](../01-testing-prose/1.2-shape-and-sense.md)'s boundary
  written where it will actually be read.
- `pathlib.Path(__file__).resolve().parents[1] / "skills"` computes the shelf path **from the test
  file's own location**, not from the current working directory. `__file__` is this file,
  `.resolve()` turns it into an absolute path with symlinks followed, and `parents[1]` is the
  repository root because the file is at `tests/test_skills.py`. Written as `Path("skills")` instead,
  the test would pass when run from the repository root and fail when `pytest` is invoked from
  anywhere else — a class of flakiness that always shows up first in continuous integration and is
  always blamed on the wrong thing.
- `test_the_shelf_is_not_empty` is the guard on the guard. Without it, an empty or missing `skills/`
  makes `check_shelf` return one `no-shelf` finding, which is fine — but a `skills/` directory that
  exists and contains nothing would make the main test pass with zero skills checked. Two lines to
  close the one hole enumeration still has.
- The assertion in that test is a list comprehension used as a truth value: a non-empty list is truthy,
  an empty one is not. The message after the comma is what `pytest` prints when it fails, and it says
  what is wrong rather than restating the expression.
- `check_shelf(SHELF)` is the whole shelf lane. There is no list of skill names anywhere in this file,
  and that absence is the part of the design worth defending in review.
- `assert findings == []` compares against the empty list rather than using `assert not findings`,
  because on failure `pytest` shows both sides — and `Finding` is a frozen dataclass with value
  equality ([2.1](../02-checks-as-functions/2.1-a-finding-is-a-return-value.md)), so the comparison is
  meaningful and the diff is readable.
- The message argument builds a block of one line per finding using `Finding.__str__`, and starts with
  `"\n"` so the first row is not jammed onto the end of `AssertionError:`. [3.2](3.2-a-failure-must-name-the-file.md)
  is entirely about why that formatting is not a nicety.

Now prove the enumeration is real, rather than believing it:

```bash
mkdir -p skills/temporary-proof
printf -- '---\nname: temporary-proof\ndescription: Nothing.\n---\nBody.\n' > skills/temporary-proof/SKILL.md
uv run python -m pytest tests/test_skills.py -k shelf
rm -rf skills/temporary-proof
```

**Line by line:**

- `mkdir -p skills/temporary-proof` adds a folder the test file has never heard of. If enumeration
  works, the suite finds it without any edit to the test.
- `printf -- '---\n…'` writes a minimal `SKILL.md` in one command. The `--` stops `printf` from reading
  the leading `---` as options, which it otherwise would, with an unhelpful error.
- The skill is deliberately incomplete: the description has no *when* clause and there is no
  `metadata.version`, so it should produce findings. A folder that passes would prove nothing.
- `-k shelf` selects only the tests whose names contain `shelf`, so you see the shelf lane without the
  rest of the suite's output. `-k` is pytest's name filter, established on
  [Day 23, 2.1](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.1-how-pytest-finds-a-test.md).
- `rm -rf skills/temporary-proof` puts the shelf back. Do it in the same command block so it cannot be
  forgotten, and confirm with `git status` that `skills/` is clean before you commit.

## When it breaks

**The hardcoded list, staying green.** Here is what that failure actually looks like, measured on
2026-09-04 with a broken folder on the shelf and two suites pointed at it — one enumerating, one
holding a list of names:

```text
1 failed, 13 passed in 0.27s
```

`test_the_shelf_passes` — the one with the list — is among the thirteen that passed. It ran, it
checked two skills, both were clean, and it reported success on a shelf with a folder that will not
load. The single failure is the enumerating test. Two suites, one shelf, opposite answers, and the
comforting one is the one that is wrong.

**The enumeration that walks the wrong directory.** The test passes and checks nothing, because
`SHELF` points somewhere empty:

```text
E       AssertionError: skills/ holds no skill folders
E       assert []
```

That is `test_the_shelf_is_not_empty` doing its only job. Without it you would get a green run and no
message at all.

**The enumeration that picks up things that are not skills.** `skills/README.md` is a file, so
`is_dir()` skips it. `skills/.gitkeep` likewise. But a `__pycache__/` under `skills/` is a directory,
and produces:

```text
__pycache__              not-a-skill      folder has no SKILL.md
```

which is a true statement and pure noise. It is the counterpart of the false alarm in
[2.4](../02-checks-as-functions/2.4-pointers-that-go-nowhere.md): enumeration buys completeness and
pays in noise, and the noise has to be handled where it appears rather than by going back to a list.

## In production

**What a professional writes instead** is enumeration plus a guard on the count. At Sutra's size,
*not empty* is enough. On a larger shelf the useful guard is a floor: *"we have at least the skills
this deployment is supposed to have"*, checked against the deployment manifest rather than against a
list in a test. The principle is unchanged — the list comes from the same place production's list
comes from — but now production's list is a manifest rather than a directory walk, and the test follows
it there.

**What degrades at scale** is run time, and it degrades in a way worth planning for. Enumeration means
every commit checks every skill, and `check_skill` loads each folder in full including its references
and assets ([2.2](../02-checks-as-functions/2.2-let-the-loader-be-the-oracle.md)). Four skills is
instant. Four hundred, each with a megabyte of assets, is a suite people start skipping — and a
skipped suite is worse than a slow one
([Day 23, 6.2](../../../day-23-testing-tools-and-callbacks/parts/06-in-production/6.2-the-suite-that-has-to-stay-fast.md)).
The fix is not a hardcoded list; it is checking the folders a commit touched on every push and the
whole shelf on a schedule, which the split between `check_skill` and `check_shelf` already allows.

**The review comment a senior engineer leaves:** *"this test iterates a list of skill names. Add a
skill and the suite stays green while covering less of the shelf — the failure mode is a pass, which
is the worst kind. Walk the directory, and add a separate assertion that the directory is not empty so
the walk itself is guarded."*

**The interview question:** *"how do you make sure a test suite keeps up with the thing it tests?"* The
honest spoken answer: *"By never writing down the list of things it tests. Our skills live as folders
under `skills/`, production loads them by walking that directory, and the test walks the same
directory at the moment it runs. If somebody adds a skill, the suite covers it with no edit; with a
hardcoded list, adding a skill silently reduces coverage and the suite stays green, which is the
failure mode you never find. The only extra piece is a guard that the directory is not empty, because
enumeration of nothing is vacuously clean. It costs you some noise — a stray `__pycache__` shows up as
a finding — and that trade is worth it."*

## Check yourself

```bash
uv run python -m pytest tests/test_skills.py -k shelf
```

Then add an empty directory `skills/nothing-here/` and run it again. Read which of the two shelf tests
fired and what it said, then remove the directory.

**Out loud, without scrolling up:** state the rule about where a test's list of inputs comes from,
explain why a hardcoded list fails by passing, and say what the *not empty* test protects that
enumeration alone does not.
