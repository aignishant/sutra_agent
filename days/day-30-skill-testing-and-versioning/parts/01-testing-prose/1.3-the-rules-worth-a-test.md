# 1.3 — The rules worth a test

## One-line answer

A rule earns a place in the suite when breaking it changes behaviour, a machine can decide it without
argument, and nothing else in the toolchain already catches it — which leaves Sutra with six rules,
three from the open specification and three from the house.

## The story

The list taped to the back of the shop shutter has six things on it, and the owner wrote it after
losing a night's takings.

*Till drawer open and empty. Back door bolted. Fridge on. Sign off. Shutter down. Keys in the pouch.*

Six. Not twenty. The owner tried twenty once — it had *wipe the counter* and *straighten the stock*
on it — and within a fortnight the staff were ticking the whole list at the door without walking the
shop, because a list you cannot honestly complete is a list you learn to lie to. The six that
survived have two things in common. Every one of them cost real money the night it was missed. And
every one of them is a thing you can stand and look at and say yes or no, without deciding anything.

*Straighten the stock* failed both tests. It never cost anybody a night's takings, and two people will
disagree about whether the stock is straight.

## The idea in plain language

You could write fifty checks over a skill folder. Most of them would be noise. A rule belongs in an
always-on suite when it passes three tests, in this order:

**Does breaking it change behaviour?** If a skill can break the rule and the agent behaves exactly the
same, the rule is a style preference. Style preferences are fine in a review and poisonous in a gate,
because the first time one blocks an urgent fix, somebody adds a skip and the gate has learned that it
can be skipped.

**Can a machine decide it without argument?** This is [1.2](1.2-shape-and-sense.md)'s shape column. If
the answer depends on what the words mean, the rule goes to a human or to an eval, not to `pytest`.

**Does anything already catch it?** A rule that ADK's own loader enforces does not need a second
implementation in your repository. Duplicating it costs you a line of code that can drift out of
agreement with the framework, and drift in a checker is worse than no checker: it produces confident,
wrong findings.

Run Sutra's candidate rules through that filter and six survive. Three come from the open
specification at `https://agentskills.io/specification` (read 2026-09-04), and three are Sutra's own —
house rules that the spec has no opinion about and this project does.

| Rule | Where it comes from | Breaking it does what | Who catches it today |
| --- | --- | --- | --- |
| `name` is kebab-case, 1–64 characters | spec | the skill will not load | ADK's `Frontmatter` model |
| `name` equals the folder name | spec | the skill will not load | ADK's `load_skill_from_dir` |
| `description` is 1–1024 characters, non-empty | spec | the skill will not load | ADK's `Frontmatter` model |
| the description says **when** to use the skill | house | the router stops finding it | nothing yet |
| every `references/` path in the body resolves | house | the agent reads a file that is not there | nothing yet |
| `metadata.version` is present and quoted | house | you cannot say which text answered | nothing yet |

The first three are already enforced, so your checker's job for them is not to re-implement the rule
but to **report** it — [2.2](../02-checks-as-functions/2.2-let-the-loader-be-the-oracle.md) is how a
raised exception becomes a line in a findings list. The last three are yours to write, and they are
the reason this day exists.

Two more rules join later in the day and belong on this list for completeness: the body stays under
the specification's recommended 500 lines, and the folder's content digest still matches the one
recorded beside the version ([5.3](../05-versioning/5.3-the-change-the-version-missed.md)). Both pass
all three tests above.

## Why Sutra needs it

Because [Day 25, 5.1](../../../day-25-skills-the-open-spec/parts/05-in-production/5.1-validating-before-you-ship.md)
ran the reference validator, `skills-ref`, over the shelf by hand and left the obvious question open:
if the validation is worth doing before you ship, why is it a thing a person remembers to do?

The answer that day gave was honest — the reference implementation describes itself as being for
demonstration rather than production use, so wiring it into a gate would be wiring in a tool that says
it is not for gates. But the *rules* it checks are public and stable, and three of them are enforced
for free by the library Sutra already depends on. So Sutra's gate is built from ADK's enforcement plus
three house rules, and `skills-ref` stays where Day 25 put it: a useful cross-check you run by hand,
never the thing standing between a change and `main`.

You also need the list itself, written down, because Day 31 turns it into a command-line linter and
Day 45 does the same exercise for MCP tools. A rule list you can point at is what makes the second
one cheap.

## The mechanism

Here is the filter applied to a rule you might reasonably want and should not have — worked through so
you can run the same argument on your own candidates.

```text
CANDIDATE: "the description must be at least 80 characters"

1. Does breaking it change behaviour?
   Partly. A very short description routes worse (Day 28, 2.2). But 79 characters
   is not worse than 80, and the real threshold depends on the other skills on the
   shelf, not on this skill alone.

2. Can a machine decide it without argument?
   It can count characters. It cannot defend the number. The first skill that
   genuinely needs a 60-character description gets an exemption, and the rule is
   now advisory.

3. Does anything already catch it?
   Yes, and better: the routing gate (Day 28, 2.3) measures the margin between
   this description and every other one, which is the thing the character count
   was a poor proxy for.

VERDICT: not a gate rule. It belongs in the routing gate, where it is measured
         against the shelf rather than against a number somebody picked.
```

**Line by line:**

- Step 1 is where most candidates die, and it dies here in an instructive way: the rule is *directionally* true and has no defensible threshold. Directionally true with no threshold is the exact signature of a rule that will collect exemptions.
- Step 2 is the shape-and-sense test from [1.2](1.2-shape-and-sense.md), phrased as *can two people disagree*. Counting characters is mechanical; choosing 80 is a judgement wearing a number's clothes.
- Step 3 is the one people skip, and it is the one that produces the useful answer here. The candidate is not simply rejected — it is **redirected** to the tool that already measures the real property. A rejected rule with nowhere to go comes back next quarter; a redirected one does not.
- The verdict is written in the same place as the rule. Sutra keeps this reasoning in `skills/README.md` beside the four-container table Day 28 put there, so the next person to propose the rule finds the answer before they open an editor.

Now the same filter on one that passes:

```text
CANDIDATE: "every references/ path in the body resolves to a file that exists"

1. Does breaking it change behaviour?
   Yes, and silently. The agent asks for the file, gets nothing, and answers
   without the rubric. There is no error and no log line (Day 27, 1.7).

2. Can a machine decide it without argument?
   Yes. The path is either a file on disk or it is not. Nobody disagrees.

3. Does anything already catch it?
   No. ADK loads references/ into the Skill object but never compares them
   against the paths the body mentions - it has no reason to, because the body
   is free-form Markdown.

VERDICT: a gate rule. Implemented as check_references in 2.4.
```

**Line by line:**

- Step 1's *silently* is what makes this rule valuable rather than merely correct. A failure that announces itself does not need a gate; you will find it the first time you run the thing. A failure that degrades an answer with no signal will live in your system for as long as nobody happens to notice.
- Step 2 is a genuine yes here: `(folder / "references/severity-rubric.md").is_file()` returns `True` or `False` and there is no third answer.
- Step 3's reasoning matters more than its conclusion. ADK reads the `references/` directory into `Skill.resources` and reads the body into `Skill.instructions`, and never relates the two. That is a correct decision by the framework — the body is Markdown and could mention a path for any reason — and it is exactly the gap a project-specific check is for.
- The verdict names the function that implements it. A rule list whose rows do not name their implementation drifts from the code within two releases.

## When it breaks

**A rule that fires on something correct.** You write the reference check, run it, and get:

```text
ticket-triage            dead-pointer     body points at references/severity-rubric.md
```

on a skill where the file is plainly there. The cause is almost always the path being relative to the
wrong root: the body writes paths from the skill folder, so the check must join them onto the *skill
folder*, not onto `skills/` and not onto the repository root. A checker that is wrong once is
disbelieved forever, so the first false finding is the most expensive bug in the whole day.

**A rule nobody can fix.** You add *"the body must be under 500 lines"* and a skill is at 640. The
rule is right — it is the specification's own recommendation, and
[Day 28, 1.3](../../../day-28-progressive-disclosure-design/parts/01-the-price-list/1.3-weight-flows-down.md)
explains what those extra lines cost on every activation — but the fix is a refactor, not an edit, and
the gate is now blocking work that is not related to the change in front of it. The move is to fix the
skill first and add the rule second, in that order, always. A gate introduced red is a gate that
teaches people to skip it on its first day.

**A rule that duplicates the framework and drifts.** You write your own kebab-case regular expression
because it is four lines. ADK's `Frontmatter` normalises the name with Unicode NFKC before matching,
and yours does not, so on the one skill whose name contains a full-width character your check and the
loader disagree — one says fine and the other refuses to load. Two checkers that disagree is worse
than one checker, because now nobody knows which to believe.

## In production

**What a professional writes instead** of a long rule list is a short one with the filter written
beside it, so the list can grow by argument rather than by accretion. The artefact that matters is not
the checks; it is the paragraph explaining why a proposed check was rejected, because that paragraph
is what stops the same conversation happening every quarter with a different person.

**What degrades at scale** is the third test, *does anything already catch it*. On a small repository
you know your whole toolchain. At forty skills and a real continuous-integration pipeline, the same
property ends up checked by the framework, by your linter, and by a schema in the deployment
templates, all slightly differently, and the day they disagree is the day somebody spends an evening
finding out which one is authoritative. Naming the owner of each rule — this one is ADK's, this one is
ours — is the cheap fix, and it belongs in the rule table itself.

**The review comment a senior engineer leaves:** *"three of these six rules are already enforced by
`load_skill_from_dir`. Do not re-implement them; call the loader and report what it says. Otherwise
we own a second copy of the specification and it will drift, and the version that drifts is always the
one in our repository."*

**The interview question:** *"how did you decide what your linter checks?"* The honest spoken answer:
*"Three tests, in order. Does breaking it change behaviour — if not it is a style preference and style
preferences in a gate get skip-flags. Can a machine decide it without an argument — if two reasonable
people disagree, it goes to review or to an eval, not to CI. And does something already catch it —
three of our rules are enforced by the framework's own loader, so we call the loader and report its
error instead of writing a second copy of the spec that can drift. That left six rules. The rules we
rejected are written down with the reason, because otherwise somebody proposes them again every few
months."*

## Check yourself

```bash
uv run python -c "
from pathlib import Path
from google.adk.skills import load_skill_from_dir
skill = load_skill_from_dir(Path('skills/ticket-triage'))
print('references ADK loaded :', skill.resources.list_references())
print('paths the body mentions:', [w for w in skill.instructions.split() if 'references/' in w])
"
```

Compare the two lists. They are produced by the same library from the same folder and nothing anywhere
compares them — which is rule four on your list and part [2.4](../02-checks-as-functions/2.4-pointers-that-go-nowhere.md).

**Out loud, without scrolling up:** state the three tests a rule must pass, name one rule you would
like to have that fails the second test, and say which of Sutra's six rules ADK already enforces for
free.
