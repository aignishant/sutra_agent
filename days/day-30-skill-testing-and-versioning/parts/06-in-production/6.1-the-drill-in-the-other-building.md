# 6.1 — 💥 The drill in the other building

## One-line answer

A suite whose input list is a copy of the shelf keeps passing while the real shelf breaks, and this
part builds that suite on purpose, runs it beside the honest one, and watches the wrong one report
success on a shelf with a skill that will not load.

## The story

🎬 **The scene:** the office runs a fire drill every quarter and the record is spotless. Everyone knows
where the stairs are, the roll is called in the car park, the sheet is signed and filed. Twelve
consecutive drills, no problems.

The team moved to the second floor of the building next door eighteen months ago. The drill is still
run in the old building, because that is where the drill was set up, with the assembly point and the
warden's list and the route printed on the laminated card. Nobody decided to keep it there. It just
never moved, and every drill since has gone perfectly.

😬 **The naive fix:** *"we have a fire drill, it passes every quarter, we are covered."*

💥 **Why it fails:** the drill is a real drill. People really do walk down real stairs and really do
assemble. Everything in the record is true. What is false is the sentence nobody wrote down — *this
drill covers our building* — and it became false on a day when nothing about the drill changed at all.
That is why nobody noticed: the change happened on the other side of the comparison.

💡 **The insight:** a check is a claim about *something*, and the claim can rot without the check
changing a line. The dangerous failures are not the ones where a test breaks. They are the ones where
the test keeps working and quietly stops being about you.

## The idea in plain language

[3.1](../03-the-suite/3.1-enumerate-never-list.md) argued for live enumeration and named the failure
mode: a hardcoded list of skills stops covering the shelf as soon as the shelf grows, and it stops
covering it **by passing**. This part makes that concrete, because an argument you have read is not the
same as a green tick you have watched be wrong.

There are two shapes of the same disease, and both look like diligence:

**The stale list.** `SKILLS = ["ticket-triage", "kb-answer-style"]` at the top of the test file. It was
correct the day it was written. A third skill arrives — from Day 29's sourcing process, or because
somebody split an overloaded skill along Day 28's axes — and the list does not, so the suite now covers
two thirds of the shelf and says so nowhere.

**The copied fixture.** The test copies `skills/` into a temporary directory in its setup, then checks
the copy, usually because somebody wanted the test to be safe to run in parallel. The copy is made from
the real shelf, so it is never stale — and it is made *before* the test runs, so a check that compares
a body's pointer against a file is comparing two things that were copied together and therefore always
agree. The drill in the other building, with a photograph of your building on the wall.

Both produce the same output, which is the only output a broken safety net can produce:

```text
1 failed, 13 passed in 0.27s
```

That line was measured on 2026-09-04, with a folder named `Bad--Name` sitting on the shelf. Thirteen
tests passed and one failed. The one that failed is the honest shelf test from
[3.1](../03-the-suite/3.1-enumerate-never-list.md). Among the thirteen that passed is a test called
`test_the_shelf_passes`, which iterated a list of two names, checked them both, found them clean, and
reported success on a shelf holding a skill that ADK refuses to load.

Two suites, one shelf, opposite verdicts, and the comforting one is the wrong one.

## Why Sutra needs it

Because Sutra's shelf is designed to grow through routes that do not touch `tests/`.

Day 27 made skills editable by people who write no Python. Day 28 gave a procedure for splitting an
overloaded skill into two, which adds a folder. Day 29 gave a procedure for bringing a skill in from
outside, which adds folders. Every one of those is a path to a bigger shelf that never passes through
the test file, and each one is a chance for a list to fall behind.

And the consequence is not abstract. Day 31 (`days/day-31-the-quality-gate/`) turns this suite into the
Phase 4 gate. From tomorrow, "the skills tests pass" is the sentence that lets a change merge. A gate
built on a stale list is a gate that waves through exactly the changes it was installed to stop.

## The mechanism

Build the broken suite yourself. It is nine lines and it goes in a file you will delete:

```python
"""The suite that goes green on a broken shelf. Written to be deleted."""

import pathlib

from tools.skill_checks import check_skill

SHELF = pathlib.Path(__file__).resolve().parents[1] / "skills"
SKILLS = ["ticket-triage", "kb-answer-style"]


def test_the_shelf_passes() -> None:
    assert [f for name in SKILLS for f in check_skill(SHELF / name)] == []
```

**Line by line:**

- `SKILLS = [...]` is the whole bug, and it is worth noticing how reasonable it looks. It is explicit,
  it is greppable, a reviewer can see at a glance which skills are covered, and the diff when somebody
  adds one is beautifully clear — on the day somebody remembers.
- `check_skill(SHELF / name)` is the **correct** function, from
  [2.3](../02-checks-as-functions/2.3-one-bad-folder-must-not-stop-the-shelf.md), doing exactly the
  right thing to each folder it is given. Nothing here is a bad check. The defect is entirely in which
  folders it is given, which is why no amount of improving the checks would help.
- The nested comprehension flattens the per-skill findings into one list, so the assertion is the same
  shape as the honest test's. The two tests are as similar as they could possibly be, differing in one
  line, which is the point: this is not a straw man.
- The docstring says the file is written to be deleted, because a file like this left in a repository
  is a trap for the next person, who will reasonably assume it is the real skills test.

Now run them together against a broken shelf:

```bash
mkdir -p skills/Bad--Name
printf -- '---\nname: Bad--Name\ndescription: Does things.\n---\nBody.\n' > skills/Bad--Name/SKILL.md
uv run python -m pytest tests/test_stale.py tests/test_skills.py
rm -rf skills/Bad--Name tests/test_stale.py
```

**Line by line:**

- `skills/Bad--Name/` breaks the specification's name rule two ways at once — a capital letter and two
  consecutive hyphens — so `load_skill_from_dir` refuses it and `check_shelf` reports `will-not-load`
  ([2.2](../02-checks-as-functions/2.2-let-the-loader-be-the-oracle.md)). It is the least subtle break
  available, deliberately: if the stale suite misses *this*, it misses everything.
- `printf --` stops the leading `---` from being read as options.
- Both test files are named on one `pytest` invocation, so the two verdicts appear in one summary line
  and you cannot mistake one run for the other.
- The cleanup is in the same block, and `git status` afterwards should show `skills/` unchanged. A
  deliberately broken folder left on a shelf is a real hazard, not a joke — Day 29 quarantined its
  poisoned skill under `tests/fixtures/` for the same reason
  ([Day 29, 3.2](../../../day-29-sourcing-and-auditing-skills/parts/03-the-poisoned-skill/3.2-the-poisoned-skill-and-the-audit.md)).

Measured on 2026-09-04, this is what the pair reports:

```text
E       AssertionError:
E         Bad--Name                will-not-load    ValidationError: 1 validation error for Frontmatter name Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading, trailing, or consecutive delimiters [type=value_error, input_value='Bad--Name', input_type=str] For further information visit https://errors.pydantic.dev/2.13/v/value_error
E       assert [Finding(skil...value_error")] == []

tests\test_skills.py:40: AssertionError
=========================== short test summary info ===========================
FAILED tests/test_skills.py::test_every_skill_on_the_shelf_passes_every_check
1 failed, 13 passed in 0.27s
```

`test_the_shelf_passes` is not in the failure list. It passed.

## When it breaks

**The stale suite alone.** If `tests/test_skills.py` had never been written and only the list-driven
version existed, the whole output would be:

```text
1 passed in 0.05s
```

on a shelf that will not load. The desk agent would fail at startup on the next deploy, and the first
thing anybody would say is *"but the tests are green"* — and they would be right, and the tests would
be green, and the shelf would still be broken.

**Discovering it during an incident.** The realisation almost never arrives on a quiet afternoon. It
arrives while something is down, when somebody grep-searches for what the skills test actually checks
and finds a two-item list from last year. At that moment the team loses confidence in every other
suite at once, which is a cost far bigger than the incident, and it is why this failure is worth
staging deliberately rather than meeting.

**The half-fix.** Somebody adds the missing skill to the list. The suite is correct again, for now, and
the mechanism that made it wrong is untouched. A fix that restores the current answer without changing
what will happen next time is not a fix; the same failure is scheduled for the next skill anybody adds.

## In production

**What a professional writes instead** is enumeration, and then goes looking for the same shape
everywhere else. Once you have seen it here it is visible all over a mature repository: a linter with a
hand-maintained list of directories, a deployment check that reads a copy of the manifest, a
dashboard whose alert list was written when there were six services. The general form is worth carrying
away — **a check whose inputs are enumerated from the same source production uses cannot go stale, and
any other check can** — and it is the same argument as
[2.2](../02-checks-as-functions/2.2-let-the-loader-be-the-oracle.md)'s about rules, applied to inputs.

**What degrades at scale** is the chance anybody notices. On a four-skill shelf, a missing skill in a
list is visible to anyone who opens the file. On a forty-skill shelf nobody reads the list, because
lists of forty things are not read, they are scrolled past. The failure mode does not get more likely
with scale — it gets more likely to survive, which is worse.

**The review comment a senior engineer leaves:** *"this test's coverage is a list that has to be
maintained by hand, and nothing fails when somebody forgets. Enumerate the directory. And while you
are in there, add the assertion that the directory is not empty, so that walking nothing is not
mistaken for finding nothing wrong."*

**The interview question:** *"tell me about a time a green test suite was lying to you."* The honest
spoken answer: *"The one I stage deliberately for new people is a validation suite that iterates a
hardcoded list of the things it validates. We put a folder on the shelf that the framework outright
refuses to load, ran two suites against it, and the list-driven one passed — thirteen passed, one
failed, and the one that failed was the version that walks the directory. Nothing was wrong with the
checks; the defect was in which inputs they were given, so improving the checks would not have helped.
The general lesson is that a check is a claim about something, and the something can change while the
check does not, which means the failure mode is a pass. So we enumerate inputs from the same place
production enumerates them, and we guard the enumeration with an assertion that it found anything at
all."*

## Check yourself

Write `tests/test_stale.py` exactly as given above, plant `skills/Bad--Name/`, run both test files in
one command, and read the summary line. Then delete both.

```bash
uv run python -m pytest tests/test_stale.py tests/test_skills.py
```
