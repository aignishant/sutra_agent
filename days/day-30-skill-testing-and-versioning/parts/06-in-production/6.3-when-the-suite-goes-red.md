# 6.3 — Fix the skill, never the check

## One-line answer

When the suite goes red the decision is always the same and always made in the same order — read the
rule tag, fix the skill, and only then ask whether the rule itself was wrong — because a check bent to
accommodate the thing it was checking has stopped being a check.

## The story

The thermometer in the fridge reads six degrees, which is two too warm, so somebody moves it to the
back of the bottom shelf where it reads four.

The reading is now correct. It is genuinely cooler at the back of the bottom shelf — the thermometer
is not lying and nobody has tampered with anything. What has happened is that the question changed
without anyone saying so. It used to be *how warm is the fridge?* and it is now *how warm is the
coldest corner of the fridge?*, and only the first question has anything to do with whether the milk
lasts.

The seal is still going. The milk still turns on Thursday. And now there is a thermometer reading four
degrees to argue with anybody who says the fridge is a problem.

## The idea in plain language

A red suite presents a fork, and the fork has a correct order.

**First, read the rule tag.** Every finding carries one — `will-not-load`, `dead-pointer`, `no-when`,
`no-version`, `unquoted-version`, `bad-version`, `stale-digest`, `not-a-skill`
([2.1](../02-checks-as-functions/2.1-a-finding-is-a-return-value.md)) — and the tag maps to a remedy
before you have opened anything:

| Tag | What happened | The fix |
| --- | --- | --- |
| `will-not-load` | the frontmatter breaks a spec rule, or the name does not match the folder | fix `SKILL.md` or rename the folder |
| `dead-pointer` | the body names a file that is not there | restore the file, or update the body |
| `no-when` | the description lost its trigger clause | restore it, and re-run the routing gate |
| `no-version` / `unquoted-version` / `bad-version` | the version field is absent, unquoted or malformed | write it as a quoted `N.N` string |
| `stale-digest` | something in the folder changed | decide the bump, then re-stamp |
| `not-a-skill` | a directory under `skills/` has no `SKILL.md` | remove it, or make it a skill |

**Second, fix the skill.** Not the check. In every row above, the artefact that is wrong is the skill,
and the check is doing what it was asked to.

**Third — and only third — ask whether the rule was wrong.** Sometimes it genuinely is. A rule can be
too broad ([2.4](../02-checks-as-functions/2.4-pointers-that-go-nowhere.md)'s pattern matching an
example path), or built on a threshold nobody can defend
([1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md)'s rejected candidate). When that is the
answer, the fix is a change to the rule **with the reason written down**, argued on its own terms, in
its own commit — not a quiet loosening inside a commit that was about something else.

The reason for the order is that the third step is the one everybody wants to take first, because it is
the fastest way to green. Moving the thermometer takes a moment; the fridge takes a callout.

Then there is the part that only exists because of [5.1](../05-versioning/5.1-a-name-for-the-text-that-ran.md)
and [5.3](../05-versioning/5.3-the-change-the-version-missed.md). Two of those tags — `stale-digest`
and, indirectly, `no-when` — do not just say *this is broken*. Combined with the version, they say
**which text was in the folder when it broke**. `ticket-triage@1.1` with a stale digest is a specific
claim: the folder no longer matches the state that number named, so the diff you want is
`git diff -- skills/ticket-triage/` and the obligation you owe is whichever row of
[5.2](../05-versioning/5.2-the-bump-rule.md)'s table that diff falls into. A red check with no version
tells you something is wrong; a red check with a version tells you what changed and what you now have
to re-run.

## Why Sutra needs it

Because from tomorrow this suite is a gate, and every gate is under permanent, reasonable pressure to
be loosened.

Day 31 (`days/day-31-the-quality-gate/`) wires these checks into `./m check`, and from that moment a red
finding stands between somebody and a merge. Most of the time that somebody is in a hurry, is fixing
something unrelated, and did not write the skill that is red. The loosening will not arrive as
sabotage. It will arrive as a one-line pull request with a sincere justification, and the only defence
is a rule about the order of the decision, agreed before anyone is in a hurry.

Sutra has already been through this once from the other side. Day 29's audit was built so it could
report `REJECT` on a skill somebody wanted to install, and the discipline that made it worth anything
was that a rejection is recorded rather than argued away
([Day 29, 4.1](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.1-no-row-no-run.md)).
Same principle, pointed at your own shelf.

## The mechanism

The triage, as commands, in the order the fork demands. Start by turning the failure into a list you
can read without `pytest` in the way:

```bash
uv run python -c "
import collections, pathlib
from tools.skill_checks import check_shelf
findings = check_shelf(pathlib.Path('skills'))
for rule, count in collections.Counter(f.rule for f in findings).most_common():
    print(f'{count:>3}  {rule}')
print()
for f in findings:
    print(f)
"
```

**Line by line:**

- `collections.Counter(f.rule for f in findings)` groups by rule tag, which is the payoff for making
  `rule` a fixed identifier rather than prose
  ([3.2](../03-the-suite/3.2-a-failure-must-name-the-file.md)). On a shelf with one problem the summary
  is redundant; on a shelf with forty findings it is the only part you read first.
- `.most_common()` puts the biggest group at the top, because a rule firing thirty times is usually one
  cause and a rule firing once is usually one skill. Those get handled differently, and seeing which
  is which comes before opening anything.
- The blank `print()` then the full list: summary for the decision, detail for the fix. Both, in that
  order, in one command.
- This is deliberately a probe rather than a function in `tools/skill_checks.py`. Grouping and printing
  are a *caller's* job — the module returns values and says nothing
  ([2.1](../02-checks-as-functions/2.1-a-finding-is-a-return-value.md)) — and Day 31's linter is the
  caller that will own this properly.

Then, for a `stale-digest`, the two commands that turn a tag into a decision:

```bash
git diff -- skills/ticket-triage/
git log --oneline -1 -- skills/ticket-triage/
```

**Line by line:**

- `git diff -- <folder>` shows exactly what changed since the last commit, across `SKILL.md` and every
  reference file. Read it against [5.2](../05-versioning/5.2-the-bump-rule.md)'s four questions: did a
  step change, did a tool change, did the description change, did the resources change. The first
  *yes* gives you the bump.
- `git log --oneline -1 -- <folder>` names the last commit that touched the folder, which is what tells
  you whether the diff in front of you is *your* change or something that arrived in a rebase. Those
  are the same red check and two very different conversations.
- Only after the bump is decided do you touch the frontmatter: move the version, re-stamp the digest,
  and do both in the same commit as the content change
  ([5.3](../05-versioning/5.3-the-change-the-version-missed.md)). Re-stamping first is the move this
  part exists to name.

## When it breaks

**The check bent to fit the skill.** Somebody's description genuinely does not need a *when* clause —
they think — so the fix goes into the checker:

```python
WHEN_WORDS = ("use when", "use for", "when a", "when the", "when you", "when someone", "handles")
```

**Line by line:**

- `"handles"` is added to the phrase list, and now `"Handles ticket triage."` passes. The suite is
  green, the description is exactly the string
  [Day 28, 2.4](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.4-the-crowded-shelf.md)
  measured as routing mush, and the rule has been redefined to match the thing it was catching.
- The tell is that the change makes the rule *weaker* and was made inside a commit about something
  else. A genuine improvement to a rule can survive its own pull request with a paragraph attached; a
  loosening cannot, which is why the order of the decision is the defence.

**Re-stamping a digest to clear the red.** The single most likely bad move on this suite, because it is
one command and it works. The result is a green suite, a version that still says `"1.1"`, and a folder
that no longer matches what `"1.1"` meant — the version's whole purpose, defeated, silently. It is the
same error as re-pinning a dependency to silence a drift check
([Day 29, 4.2](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.2-the-pin-is-the-promise.md)).

**A skip added under time pressure.** The pull request adds `@pytest.mark.skip` with a comment saying
*"unrelated, will fix"*:

```text
1 skipped, 12 passed in 0.22s
```

Nothing in that output says the shelf is unchecked. `1 skipped` is a line people's eyes pass over, and
it will still be there in six months. If a check genuinely has to be turned off, the honest form is to
delete it in a commit that says so, so that turning it back on is somebody's obvious job rather than a
line nobody reads.

## In production

**What a professional writes instead** of a rule about not weakening checks is a **process** that makes
weakening visible: rule changes go in their own pull request, with the reason in the commit message,
and the rule table in `skills/README.md` is updated in the same change. The rule alone is a good
intention; the process is what makes the loosening cost more than the fix, which is the only thing that
reliably changes behaviour under pressure.

**What degrades at scale** is the signal-to-noise ratio, and it degrades into exactly this failure. A
gate that is red for a good reason gets fixed. A gate that is red for a bad reason — a false positive,
a rule with an indefensible threshold, a check that fires on generated files — gets worked around, and
the workaround is reused on the next red, including the ones that were real. Keeping the rule list
short and every rule defensible ([1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md)) is not
minimalism for its own sake; it is what preserves the team's willingness to take a red seriously.

**The review comment a senior engineer leaves:** *"this pull request changes a skill and also adds a
word to `WHEN_WORDS`. Split it. If the rule is wrong, that is its own change with its own reasoning and
its own reviewer — and if it is not wrong, then this description needs a `when` clause and a routing
re-run, which is a minor bump."*

**The interview question:** *"a lint rule you own is failing on a change that has to ship today. What do
you do?"* The honest spoken answer: *"Read the tag first, because our findings carry a fixed rule
identifier that maps to a remedy before I open anything. Then fix the artefact, not the rule — the
default assumption is that the check is right, because it was written when nobody was in a hurry. Only
after that do I ask whether the rule itself is wrong, and if it is, that is its own commit with the
reason written down and the rule table updated, never a quiet loosening inside a commit about
something else. The two moves I watch for on my own team are re-stamping a content hash to clear a
staleness check, and adding a skip marker with 'will fix' in the comment — both produce a green run and
leave the thing the check was protecting completely unprotected. And where a finding is about content
changing, the version is what turns 'something is wrong' into 'this changed since 1.1, so here is the
diff and here is what I now have to re-run'."*
