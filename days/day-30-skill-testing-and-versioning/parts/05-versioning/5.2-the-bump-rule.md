# 5.2 — The bump rule

## One-line answer

The size of the bump is not a description of how much text changed — it is a **declaration of which
checks have to be re-run**, so a patch obliges nothing, a minor obliges the routing gate, and a major
obliges a full re-read as though the skill had arrived from a stranger.

## The story

Your landlord repaints the flat and tells you afterwards. Your landlord moves a wall and has to tell
you first.

Nobody wrote that rule down and everybody follows it. The paint changes the flat and changes nothing
you agreed to, so a message on Saturday saying *"the hallway is done"* is the whole process. Moving
the wall between the second bedroom and the living room changes what you are renting: the room you
sleep in is a different room, the rent you agreed was for a two-bedroom, and there is a conversation
before anybody picks up a hammer.

The interesting part is that the tenant does not judge the *amount of work*. Repainting three rooms is
days of work and needs no conversation. Moving one wall is a weekend and needs a signature. What
decides is not effort — it is **what has to be checked again**.

## The idea in plain language

Version numbers get argued about because people try to make them describe the change. *"Is renaming a
step a minor or a patch?"* has no answer, because the question is about the text.

Ask a different question and the answer arrives immediately: **what now has to be re-checked?** The
bump is the label you put on that answer, so that the person reading the commit knows what they owe.

Sutra's rule, three rows, and it fits in `skills/README.md`:

| Change | Bump | What it obliges |
| --- | --- | --- |
| wording, typos, formatting; no step, tool or trigger word changed | patch — `"1.1"` → `"1.1.1"` | nothing beyond the usual suite |
| a new edge case, a new reference file, a **description** that gains or loses a trigger word | minor — `"1.1"` → `"1.2"` | re-run the routing gate ([Day 28, 2.3](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.3-measuring-routing-without-a-model.md)) |
| a step changes, a tool is added or removed, `allowed-tools` moves, the procedure's outcome changes | major — `"1.1"` → `"2.0"` | re-run the routing gate **and** re-read the whole skill as if it had arrived from outside ([Day 29's five passes](../../../day-29-sourcing-and-auditing-skills/parts/02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md)) |

The third row is the one that carries weight, and its justification is one sentence:
**a procedure change is a new skill wearing an old name.** The thing your agent will obey is different
now. Day 29 built a five-pass audit for text you did not write, and the reason to point it at your own
skill after a major change is that the previous audit was of a document that no longer exists.

Two consequences fall out of the rule, and both are worth stating because both get argued.

**A description edit is at least a minor.** It is one line, it is often shorter than a typo fix, and it
changes which tasks reach the skill — which is the largest behavioural change a skill can undergo
without touching a single step ([Day 28, 2.1](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.1-a-description-is-a-routing-row.md)).
Sizing it by the diff would make it a patch. Sizing it by what has to be re-checked makes it a minor,
correctly.

**There is no changelog file.** The specification has no changelog field, and inventing a parallel
`CHANGELOG.md` per skill means a second place to forget. `git log -- skills/ticket-triage/` is the
changelog, with the diffs attached, and the version is the label the history hangs off. This is
Principle 2 — one day, one commit — collecting its interest: the repository is the memory.

**Third-party skills are not bumped by you.** A sourced skill's version is upstream's, and its identity
in Sutra is the pinned hash in `docs/SKILL_PROVENANCE.md`. A new hash is a new audit and an updated
row, never a number you increment
([Day 29, 4.2](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.2-the-pin-is-the-promise.md)).

## Why Sutra needs it

Because Day 27 left the rule unwritten on purpose and pointed at this day.

Its build brief said: *decide Sutra's version rule in one sentence and put it in `skills/README.md`*.
That was the right place to leave it, because a version rule with no checks behind it is a
convention, and Sutra had no skill checks until today. Now there are checks, and there is a routing
gate from Day 28 and an audit from Day 29 — so the rule can be written the useful way, as a mapping
from a change to a set of things that must be re-run.

It matters next on Day 31 (`days/day-31-the-quality-gate/`), which turns the checks into a merge gate.
A gate can enforce *that* the version moved, and can never decide *how far* it should have moved. The
written rule is what a reviewer points at in the pull request, and a rule that is not written is a rule
that gets settled by whoever argues longest.

## The mechanism

The rule is a decision, so its mechanism is a decision procedure and a place to keep the evidence.
Start with the evidence, which you already have:

```bash
git log --oneline -- skills/ticket-triage/
git show --stat HEAD -- skills/ticket-triage/
git diff HEAD~1 HEAD -- skills/ticket-triage/SKILL.md
```

**Line by line:**

- `git log -- <path>` limits the history to commits that touched that path. The `--` separates paths
  from revisions, and without it git will guess — and guess wrong the day a skill is named the same as
  a branch. This one command is the changelog for the skill, in reverse chronological order, and it is
  why no `CHANGELOG.md` is needed.
- `--oneline` gives one commit per line: the short hash and the subject. Because every day's commit
  message follows the same form — `day NN: <title> — closes <IDs>` — the log reads as a list of which
  days touched this skill, which is exactly the index an audit wants.
- `git show --stat HEAD -- <path>` shows what the most recent commit changed under that path, with a
  line count per file but no content. It is the fastest way to answer *"did this commit touch the
  body, or only a reference file?"* — which is the question the bump rule turns on.
- `git diff HEAD~1 HEAD -- skills/ticket-triage/SKILL.md` is the content of that change. Read the
  description line and the numbered steps: a change to either is a minor at least, and a change to a
  step is a major.
- None of these three commands is a check and none can fail. They are how a human answers the bump
  question, and the reason to write them down is that a rule whose evidence takes a search is a rule
  people guess at instead.

Then the decision itself, applied to the two changes Sutra's own skills have already had:

```text
CHANGE: Day 28 moved ticket-triage's worked example from the body into
        references/example-4390.md, and the body gained one line naming it.

  Did a step change?              no
  Did a tool change?              no
  Did the description change?     no
  Did the resources change?       yes - one new reference file
  ->  MINOR.  "1.0" -> "1.1"
  Obligation: re-run the routing gate. The description did not move, so the
              margins should not move either - and confirming that is the point.

CHANGE: a typo in step 2, "sevrity" -> "severity".

  Did a step change?              the wording, not the instruction
  Did a tool change?              no
  Did the description change?     no
  Did the resources change?       no
  ->  PATCH.  "1.1" -> "1.1.1"
  Obligation: none beyond the suite that runs anyway.
```

**Line by line:**

- The four questions are asked in order and the first *yes* that reaches a step or a tool ends the
  decision at major. That ordering is deliberate: it means the expensive answer is reached quickly and
  cannot be argued down by the three cheap questions after it.
- The first case is the interesting one, because *nothing about the agent's instructions changed* —
  the same content is in the same skill, one rung further down
  ([Day 28, 1.4](../../../day-28-progressive-disclosure-design/parts/01-the-price-list/1.4-moving-the-example.md)).
  It is still a minor, because the shape of what gets loaded when has changed, and the obligation is a
  re-run that is expected to be boring. An obligation you expect to pass is not wasted work; it is the
  difference between believing and knowing.
- The second case shows what a patch is for: a change you would be comfortable making without telling
  anybody. If you would want to tell somebody, it is not a patch.
- The decision is written into the commit message, not into a separate document. `day 30: ... bumped
  ticket-triage to 1.2 (minor: description gained a trigger word; routing gate re-run, worst margin
  unchanged at 2)` is a sentence a future audit can read directly out of `git log`.

## When it breaks

**Sizing by the diff.** A one-word change to a description looks like a patch and is a minor, and the
cost of getting it wrong is that nobody re-runs the routing gate. The failure appears later as
[Day 28, 2.4](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.4-the-crowded-shelf.md)'s
crowded shelf: margins that dropped, one word at a time, over several "patches" that each looked
trivial.

**The bump in a follow-up commit.** Somebody edits the skill, forgets the version, notices in review,
and pushes a second commit that bumps it. For as long as those two commits are apart, the repository
contained a `ticket-triage@1.1` that was not the `1.1` anybody else has, and if anything ran in
between, its log line names a version that no longer means what it said. The version moves in the same
commit as the change.

**A major that skips the re-read.** The rule's third row is the expensive one and it is the one that
gets quietly dropped, because re-reading a skill you wrote yourself feels absurd. It is not: the
argument is Day 29's, and it does not care who the author was. What you audited was a different
document. If the re-read genuinely is not warranted, then the change was not a major, and the honest
move is to argue about the row rather than to skip the obligation.

**A rule that lives only in a day document.** This one is real and it is why the build brief puts the
paragraph in `skills/README.md`. Nobody editing a skill in six months will open
`days/day-30-skill-testing-and-versioning/`. They will open the folder they are editing, and the
README beside it is the only document that is in their way.

## In production

**What a professional writes instead** of a version policy is a version policy **with the obligation
column**, and that column is the entire value. Semantic versioning is famous for its promise about
compatibility, and a skill has no compatibility to promise — so a policy copied from a package manager
brings the arguments and none of the benefit. Reframing the bump as *what has to be re-checked* gives
you a rule people can apply without a meeting, because the question has a factual answer.

**What degrades at scale** is enforcement of the third row. At five skills, a major bump is rare and
everybody notices. At forty, majors happen weekly, the re-read obligation is a person-afternoon each
time, and the pressure to call things minors becomes structural rather than lazy. Teams that survive
this either shrink the obligation — a diff-based re-read against the last audited version, which is
only sound because the version and digest pin what was audited
([5.3](5.3-the-change-the-version-missed.md)) — or accept that majors need scheduling. Pretending the
obligation is cheap is how it stops happening.

**The review comment a senior engineer leaves:** *"you changed step 3 from 'ask the customer' to
'refund automatically under fifty' and bumped the patch digit. That is a different procedure — the
agent now does something nobody has approved it doing. Major, and it goes back through the audit read
before it merges."*

**The interview question:** *"how do you version prose that nothing resolves?"* The honest spoken
answer: *"By making the bump mean an obligation rather than a size. A patch is wording and obliges
nothing. A minor is a new edge case, a new reference file, or any change to the description, and it
obliges a re-run of our routing gate — the description is the router, so a one-word edit there is a
bigger behavioural change than rewriting three steps. A major is a change to a step, a tool or the
outcome, and it obliges a full re-read as if the skill had come from a stranger, because a changed
procedure is a new skill wearing an old name and the previous review was of a document that no longer
exists. No changelog file — `git log` on the skill folder is the changelog and the version is the
label the history hangs off. And the rule lives in the README beside the skills, because nobody reads
a policy document while editing a Markdown file."*
