# 5.3 — The change the version missed

## One-line answer

The version lives in `SKILL.md` and the skill is a whole folder, so editing only a reference file
changes what the agent reads while the version sits still — and the fix is a short hash of the folder,
recorded next to the version, so any content change forces the frontmatter to move.

## The story

The box that arrives is the box you were expecting, and what is inside it is not.

Same courier, same size, same label with your name and the right order number, same tape. You signed
for it without a thought, because everything you could see was exactly right. It is only when you open
it that the wrong thing is in there — a different item, from a different order, packed into a box
whose outside was never touched.

Nothing about the outside was a lie. The label was printed for this parcel and describes it
accurately. The label describes the *parcel*, and what you cared about was the *contents*, and those
are two different things that agree with each other only because somebody was careful at the packing
bench.

## The idea in plain language

`metadata.version` is a line inside `SKILL.md`. The skill the agent uses is a **folder**: `SKILL.md`
plus everything under `references/`, `scripts/` and `assets/`
([Day 25, 3.2](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.2-scripts-references-assets.md)).

So there is a whole category of change that alters what the agent will read while leaving the version
untouched:

- Somebody rewrites the severity thresholds in `references/severity-rubric.md`.
- Somebody edits the worked example that Day 28 moved out of the body.
- Somebody adds a paragraph to an asset the body points at.

Every one of those changes the agent's behaviour. None of them touches `SKILL.md`, so the version
still says `"1.1"`, and every log line, every audit note and every bug report continues to name a
`ticket-triage@1.1` that no longer means what it meant last week.

[Day 27, 6.2](../../../day-27-authoring-first-skills/parts/06-in-production/6.2-versioning-a-procedure.md)
named this hole and stated the principle that closes it: **the version lives on the skill, not on the
file** — a reference-file change is a change to the skill and must move the number. That is a rule
about people, and a rule about people that nothing checks is a rule that holds for about a quarter.

The mechanism that makes it hold is borrowed straight from Day 29. There, a sourced skill was pinned
by hashing its bytes, so one changed character turned the check red
([Day 29, 4.2](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.2-the-pin-is-the-promise.md)).
Point the same idea at your own folder and record the hash **beside the version**, and the loop
closes: change any file, the hash moves, the recorded hash is stale, the check goes red, and the only
way to make it green is to edit the frontmatter — at which point you are looking at the version and
have to decide what it should be.

The digest does not decide the bump. It cannot, and [5.2](5.2-the-bump-rule.md) is where a human
does. What it guarantees is that the decision **gets made**, which is the part that was silently being
skipped.

## Why Sutra needs it

Because Sutra deliberately moves weight out of `SKILL.md` and into reference files, and every move
makes this hole bigger.

That is the whole design of progressive disclosure
([Day 28, 1.3](../../../day-28-progressive-disclosure-design/parts/01-the-price-list/1.3-weight-flows-down.md)):
detail flows down out of the body so activation stays cheap. The better a shelf follows that rule, the
more of its actual content lives outside the file the version sits in. A perfectly disclosed skill is
a two-line body and four reference files, and its version covers almost nothing.

It also makes an existing ledger honest. `docs/SKILL_PROVENANCE.md` records a pin per sourced skill.
First-party skills have had no equivalent, so *"the text you audited is the text that runs"* has been a
promise about a folder with nothing behind it. The digest is the behind-it.

## The mechanism

Two functions in `tools/skill_checks.py`: one that hashes the folder, one that compares.

```python
def folder_digest(folder: Path) -> str:
    """A short hash over SKILL.md and every file under references/, scripts/ and assets/.

    The `digest:` line is removed before hashing, so the digest can be written back into
    the file it covers without ever chasing its own tail.
    """
    parts = [_without_digest_line((folder / "SKILL.md").read_text(encoding="utf-8"))]
    for name in RESOURCE_DIRS:
        directory = folder / name
        if not directory.is_dir():
            continue
        for path in sorted(p for p in directory.rglob("*") if p.is_file()):
            parts.append(path.relative_to(folder).as_posix())
            parts.append(path.read_bytes().decode("utf-8", "replace"))
    joined = "\n".join(parts).replace("\r\n", "\n")
    return hashlib.sha256(joined.encode("utf-8")).hexdigest()[:DIGEST_LENGTH]


def _without_digest_line(text: str) -> str:
    """SKILL.md with the indented `digest:` line inside `metadata:` taken out."""
    prefix = f"{DIGEST_KEY}:"
    return "\n".join(
        line
        for line in text.splitlines()
        if not (line.startswith((" ", "\t")) and line.strip().startswith(prefix))
    )
```

**Line by line:**

- The digest excludes its own line, and that is not a nicety — it is the difference between a working
  mechanism and an impossible one. Write the digest into the file and the file changes, so the digest
  changes, so the value you just wrote is already wrong. Removing the line first gives the hash a
  **fixed point**: the same value before and after it is written down.
- `_without_digest_line` only drops a line that is **indented** and starts with `digest:`, because the
  digest lives under `metadata:` and is therefore indented. A body line that happened to begin
  `digest: ...` at column zero is left in the hash, where it belongs. Matching on the bare word
  anywhere would silently exclude real content from the digest, which is the worst kind of bug here —
  a check that quietly covers less than it claims.
- `RESOURCE_DIRS` is the same tuple `check_references` uses
  ([2.4](../02-checks-as-functions/2.4-pointers-that-go-nowhere.md)). One definition of *what counts as
  part of the skill*, shared, so the check that says a pointer resolves and the check that says the
  content is unchanged can never disagree about scope.
- `rglob("*")` walks subdirectories, so `references/legal/refunds.md` is covered. `if p.is_file()`
  drops the directory entries `rglob` also yields.
- `sorted(...)` is what makes the hash reproducible. `rglob` yields in filesystem order, which differs
  between machines, so an unsorted walk gives your laptop and continuous integration two different
  digests for identical folders — a red check nobody can explain.
- `path.relative_to(folder).as_posix()` puts the **filename** into the hash as well as the contents.
  Without it, renaming `severity-rubric.md` to `rubric.md` leaves the digest unchanged, and a rename is
  exactly the change [2.4](../02-checks-as-functions/2.4-pointers-that-go-nowhere.md) is about.
  `as_posix()` forces forward slashes so a Windows machine and a Linux runner agree.
- `read_bytes().decode("utf-8", "replace")` reads any file, including a PNG in `assets/`, without
  raising on bytes that are not valid text. `"replace"` substitutes a placeholder character rather
  than failing — the goal is a stable fingerprint of the bytes, not a faithful decoding, and any change
  to the bytes still changes the result.
- `.replace("\r\n", "\n")` normalises line endings, so the same folder checked out on Windows and on
  Linux hashes the same. Without it, git's `core.autocrlf` decides your digests, which is a bug that
  only appears when a second person joins the project.
- `sha256(...).hexdigest()[:DIGEST_LENGTH]` truncates to twelve hex characters. Twelve is short enough
  to sit in frontmatter and be read aloud, and long enough that an accidental collision between two
  versions of one small folder is not a thing that happens. This is not a security control — a
  determined author could construct a collision — it is a change detector, and the threat model is a
  colleague editing a rubric, not an attacker.

And the comparison, which is four lines because the hard part is above:

```python
def check_digest(folder: Path, skill: Skill) -> list[Finding]:
    """The digest recorded in the frontmatter still covers what is in the folder."""
    recorded = skill.frontmatter.metadata.get(DIGEST_KEY)
    if recorded is None:
        return [Finding(skill.name, "no-digest", f"metadata.{DIGEST_KEY} is missing")]
    actual = folder_digest(folder)
    if recorded != actual:
        return [
            Finding(
                skill.name,
                "stale-digest",
                f"folder hashes to {actual}, frontmatter says {recorded} - "
                "content changed and the version did not",
            )
        ]
    return []
```

**Line by line:**

- Two tags again, for the same reason as
  [5.1](5.1-a-name-for-the-text-that-ran.md)'s three: `no-digest` means *this skill has not adopted the
  rule yet* and `stale-digest` means *somebody changed something*. In a migration those need different
  handling, and a single tag would make them indistinguishable in a report.
- The detail prints **both** hashes, in the order actual-then-recorded, and then says what it means in
  words. Two twelve-character strings on their own would tell a reader nothing they could act on; the
  clause after the dash is the instruction.
- `check_digest` takes the folder, so it is one of the three folder-bound rules from
  [4.3](../04-skills-built-in-code/4.3-what-memory-cannot-test.md) and lives in the shelf lane. There
  is no in-memory version of this check and there should not be one.

Writing the value in is a one-off per skill, and it belongs in the same commit as the change that made
it stale:

```bash
uv run python -c "
from pathlib import Path
from tools.skill_checks import folder_digest
for folder in sorted(p for p in Path('skills').iterdir() if p.is_dir()):
    print(f'{folder.name:<24} {folder_digest(folder)}')
"
```

**Line by line:**

- It prints the digest for every skill and writes nothing. Editing the frontmatter is deliberately
  manual today, because the point of the check is to put a human in front of the version field — an
  auto-fixing script would restore the exact hole this part exists to close. Day 31's linter may grow
  a `--fix` flag, and if it does, it must refuse to touch the digest unless the version also moved.
- The digest depends on your files, so the value you get is yours. There is no correct hash to copy
  from this document, and a shelf whose digests match a document's would mean somebody pasted rather
  than ran.

## When it breaks

**The intended failure: only a reference file changed.** Measured on 2026-09-04, after appending one
line to a rubric and touching nothing else:

```text
______________ test_every_skill_on_the_shelf_passes_every_check _______________

E       AssertionError:
E         ticket-triage            stale-digest     folder hashes to 4b6c1ac1988c, frontmatter says 3f87c32d8f4f - content changed and the version did not
```

`SKILL.md` was not opened. The version still says `"1.1"`. The check caught it anyway, which is the
whole point of the part in one line of output.

**Re-stamping instead of deciding.** The check goes red, and the fastest way to green is to run the
command above and paste the new hash in. That produces a green suite and a version that still lies —
it is the same mistake as re-pinning to clear a red drift check
([Day 29, 4.2](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.2-the-pin-is-the-promise.md)),
and it deserves the same rule: **red means decide the bump, then re-stamp.** Never re-stamp first. The
digest cannot enforce this and neither can any check; it is what the review comment is for.

**A digest that changes when nothing did.** Somebody checks the repository out on a machine with
different line-ending settings, or a build step drops a `.DS_Store` into `references/`, and the check
goes red on a folder nobody touched. The line-ending case is handled by the normalisation above; the
stray-file case is not, deliberately — a file that appears in `references/` **is** a change to the
skill, and the honest answer is to keep it out of the folder rather than to teach the digest to ignore
things.

**A binary asset that keeps moving.** A `.png` regenerated by a design tool differs byte-for-byte every
time it is exported, even with no visible change. Its folder's digest then moves on every export and
the check becomes noise. There is no clever fix; there is a choice. Either the asset is content and
its churn is real, or it does not belong under the skill folder at all.

## In production

**What a professional writes instead** is this exact pattern with a name they will recognise: a
**manifest**. A version plus a hash of what the version covers is what a lock file is, what a container
digest is, and what a signed bill of materials is. The insight each of those encodes is the same one
this part is about: a declared version is a claim by whoever last edited it, and a hash is a fact
anything can re-derive. Where a real team differs from this teaching version is that the hash is
usually computed by the build and stored outside the artefact; keeping it in the frontmatter is the
cheapest thing that works for a folder a human edits by hand, and it has the useful side effect of
putting the version in front of that human.

**What degrades at scale** is the cost and the noise. Hashing every file of every skill on every commit
is nothing at Sutra's size and is real work at four hundred skills with binary assets, so the mature
version hashes only the folders a commit touched. And the noise grows faster than the cost: every
generated file, every editor artefact, every tool that rewrites a file on save produces a red check
that is not about anything, and a check that is red for no reason is a check people learn to re-stamp
without reading. Keeping the folder free of generated files is what keeps the mechanism trustworthy.

**The review comment a senior engineer leaves:** *"the digest moved and the version did not, and you
updated the digest. That is backwards — the digest is not the thing to fix, it is the thing telling
you the version is wrong. Which row of the bump table is this change, and did you run what that row
obliges?"*

**The interview question:** *"your version number lives in one file and the thing it names is a whole
directory. How do you keep them honest?"* The honest spoken answer: *"We record a short content hash
of the whole folder next to the version, and a check compares it on every commit. Editing a reference
file changes the hash, the recorded hash goes stale, the check fails, and the only way to fix it is to
edit the frontmatter — which puts a person in front of the version field, which is the part that was
being skipped. Two details make it work: the digest line is excluded from its own hash so it has a
fixed point, and filenames go into the hash as well as contents so a rename is detected. It does not
decide the bump — a human does, against a written rule — it just guarantees the decision gets made.
The failure mode to watch for is people re-stamping the hash to clear the red, which is the same
mistake as re-pinning a dependency to silence a drift check."*
