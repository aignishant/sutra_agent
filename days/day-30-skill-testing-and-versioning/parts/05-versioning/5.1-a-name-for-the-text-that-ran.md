# 5.1 — A name for the text that ran

## One-line answer

A skill version is not a release number and buys you no compatibility — it is a **name for one exact
version of the text**, so that an audit, a log line and a bug report can all say which one, and the
check that enforces it is short because the field is inert everywhere else.

## The story

Two timetables are pasted at the bus stop, one over the corner of the other, and neither has a date on
it.

The top one says the last bus is at nine. Under its torn corner you can see a different number on the
one underneath. Somebody pasted the new one up without taking the old one down, or somebody pasted an
old spare over the new one — you cannot tell which, because nothing on either sheet says when it was
printed.

Now a woman who missed the last bus on Tuesday complains at the depot. The clerk looks at the current
timetable and says the last bus is at nine, so she should have been there. She says the board said
half past. Both of them are looking at a real sheet of paper with a real number on it, and neither can
prove anything, because the sheets have no names.

A date in the corner of each sheet costs nothing to print and settles the argument completely.

## The idea in plain language

You have been carrying `metadata.version` since Day 27, and
[Day 27, 6.2](../../../day-27-authoring-first-skills/parts/06-in-production/6.2-versioning-a-procedure.md)
was exact about what it is not. ADK never reads it. The activation register records skill **names**,
not versions. It is inert: a few tokens sent to the model on every activation and used by nothing.

So why keep it? Because three separate disciplines all need to name a specific version of a specific
skill, and there is nothing else to name it with:

- **The audit.** Day 29's whole discipline is *"the text you audited is the text that runs"*
  ([Day 29, 4.2](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.2-the-pin-is-the-promise.md)).
  For a sourced skill the name is a commit hash. For a first-party skill, the version is the label the
  audit's verdict attaches to.
- **The log.** Day 27's `log_versions.py` writes `ticket-triage@1.1` into a run's record, so the
  question *"which rubric answered ticket 4390 in March?"* has an answer.
- **The bug report.** *"Triage got this wrong"* is unactionable. *"`ticket-triage@1.1` got this
  wrong"* points at a diff.

Notice what a skill version is **not**, because the word carries baggage from package managers. It is
not a compatibility contract. Nothing resolves it, nothing depends on a range of it, and no installer
will refuse anything. Semantic versioning's promise — *"a major bump means your code might break"* —
has no mechanism behind it here. What the number gives you is an **identity**, and
[5.2](5.2-the-bump-rule.md) attaches obligations to the size of the change so the number still means
something to a human.

That makes the check genuinely simple. There is one thing to enforce — the field is there, and it is a
string of the right shape — and one trap, which is the reason the shape matters.

The trap is YAML. Write `version: 1.10` without quotes and YAML parses it as a **number**, and the
number `1.10` is the number `1.1`. Your `1.10` release, the tenth patch after `1.0`, silently becomes
`1.1` in every log line and every audit note. Run on 2026-09-04:

```text
{'metadata': {'version': 1.1}}
```

That is `yaml.safe_load("metadata:\n  version: 1.10\n")`, and it is why the rule is *present **and
quoted*** rather than just present. It was flagged as a trap on
[Day 25, 2.4](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.4-the-optional-fields.md);
today a test enforces it.

## Why Sutra needs it

Because the shelf is about to have two kinds of skill on it — first-party skills you write, and
third-party skills you audited and pinned — and both need to be nameable in the same ledger.

`docs/SKILL_PROVENANCE.md` ([Day 29, 4.1](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.1-no-row-no-run.md))
has a pin column, and for a sourced skill that pin is a commit hash from somebody else's repository.
Your own skills have no upstream, so their pin is the version, and a version that is absent — or that
is silently a float — makes a row in that ledger unwriteable.

It also matters for the check that comes next. The digest rule in
[5.3](5.3-the-change-the-version-missed.md) is built on the version being a stable string that a human
chose. If the field can be a float, or can drift between `1.1` and `"1.1"` depending on who edited the
file, there is nothing solid to hang the rest of the discipline on.

## The mechanism

One check, in `tools/skill_checks.py`, with three outcomes because there are three distinct ways this
goes wrong and each needs a different fix.

```python
def check_version(skill: Skill) -> list[Finding]:
    """Sutra house rule: every first-party skill carries a quoted `metadata.version`."""
    raw = skill.frontmatter.metadata.get("version")
    if raw is None:
        return [Finding(skill.name, "no-version", "metadata.version is missing")]
    if not isinstance(raw, str):
        return [
            Finding(
                skill.name,
                "unquoted-version",
                f"metadata.version parsed as {type(raw).__name__} {raw!r}, not a string",
            )
        ]
    fields = raw.split(".")
    if not (2 <= len(fields) <= 3 and all(f.isdigit() for f in fields)):
        return [Finding(skill.name, "bad-version", f"metadata.version {raw!r} is not N.N or N.N.N")]
    return []
```

**Line by line:**

- `skill.frontmatter.metadata` is the free-form mapping the specification allows and ADK stores
  untouched — the framework only reads `adk_additional_tools` and `adk_inject_state` out of it
  ([Day 26, 1.2](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.2-the-skill-object.md)).
  That inertness is what makes a house rule possible: nothing else has an opinion about the key.
- `.get("version")` rather than `["version"]`, because a missing key is a finding, not a `KeyError`.
  This is [2.1](../02-checks-as-functions/2.1-a-finding-is-a-return-value.md)'s contract applied to a
  dictionary lookup.
- Three tags, not one, and this is the design decision worth defending. `no-version` means *add the
  field*. `unquoted-version` means *put quotes round the value you already have* — a one-character fix
  that a single generic message would not have told anyone about. `bad-version` means *this is not a
  version number*. Different fixes deserve different tags, because a report grouped by tag then groups
  by remedy.
- `isinstance(raw, str)` before anything else touches the value, because `"1.10".split(".")` and
  `(1.1).split(".")` do not both work — the second is an `AttributeError`. Type first, shape second,
  always, when the source is a YAML file you did not parse yourself.
- `type(raw).__name__` in the detail prints `float`, which is the word that makes the penny drop. A
  message saying *"version must be a string"* leaves the reader wondering how it became anything else;
  *"parsed as float 1.1"* tells them YAML did it and roughly when.
- `2 <= len(fields) <= 3` accepts `1.0` and `2.0.1` and rejects `1` and `1.2.3.4`. Two fields is
  Sutra's normal form and three is allowed for a patch, which matches the bump table in
  [5.2](5.2-the-bump-rule.md). The rule is Sutra's, not the specification's — the spec has no version
  field at all and only shows one in an example — so it goes in `skills/README.md` beside the other
  house rules rather than being presented as something external.
- `all(f.isdigit() for f in fields)` rejects `v1.0`, `1.0-beta` and `latest`. `isdigit()` on an empty
  string is `False`, which is what makes `"1."` fail without a special case.
- The final `return []` is the only path with no finding, and it is at the bottom, so reading the
  function top to bottom is reading the three failures in the order they are checked.

And the value in `SKILL.md`, quoted, with the date beside it that Day 27 established:

```yaml
metadata:
  version: "1.1"
  changed: "2026-09-03"
```

## When it breaks

**The unquoted version, caught.** Run on 2026-09-04 against a folder whose frontmatter says
`version: 1.10`:

```text
float-version            unquoted-version metadata.version parsed as float 1.1, not a string
```

Read what the finding is telling you and what it is not. It is not saying the version is wrong. It is
saying the version you wrote is not the version that arrived, and the digit you lost is gone from
every log line the skill has ever produced.

**The version that never moves.** Six edits to a skill and the field still says `"1.0"`. No check
catches this, because the check can only see the file in front of it. It is the failure
[5.3](5.3-the-change-the-version-missed.md) exists to close for content changes, and for everything
else it is a habit: the version moves in the same commit as the change, or not at all.

**Two skills at `"1.0"` that are not the same skill.** Versions are per-skill, so
`ticket-triage@1.0` and `kb-answer-style@1.0` share a number and nothing else. That is fine and worth
saying out loud, because somebody will eventually propose a single version for the whole shelf. It
would be wrong: the unit that changes is one skill, the unit an audit covers is one skill, and a shelf
version would move whenever any skill moved, which makes it useless for naming any of them.

## In production

**What a professional writes instead** of a bare version is a version plus the thing that makes it
verifiable. On a package that is a lock file with a hash; here it is
[5.3](5.3-the-change-the-version-missed.md)'s digest. A version number by itself is a claim by whoever
last edited the file, and it is worth exactly as much as their attention that afternoon. The number
plus a hash of what it covers is a claim anything can check.

**What degrades at scale** is the meaning of the number. With one author, `"1.1"` means what that
author decided it means. With five authors and forty skills, three of them are using the middle field
for anything at all and two are treating it as a date, and the number stops carrying information
across a team. The fix is not a stricter regular expression; it is the written bump rule in
[5.2](5.2-the-bump-rule.md), in `skills/README.md`, where somebody editing a skill will meet it.

**The review comment a senior engineer leaves:** *"`version: 1.10` — quote it. YAML reads that as a
float and your tenth patch becomes 1.1 in every log we have. And while you are there, move the version
in the same commit as the change; a version bumped in a follow-up commit is a version that was wrong
for however long the two commits were apart."*

**The interview question:** *"why version a Markdown file that nothing resolves?"* The honest spoken
answer: *"Not for compatibility — nothing depends on a range of it and no installer will refuse
anything. It is an identity. Three things need to name one exact version of the text: the audit trail
says which text was reviewed, the run log says which one produced an answer, and a bug report says
where it broke. Without a version, 'the triage skill' is not one thing over time and none of those
three can be written down. The check is short — present, a string, two or three numeric fields — and
the string part is not pedantry: unquoted, YAML turns 1.10 into the float 1.1, so you silently lose a
digit in every record. And the number on its own is only a claim by whoever last saved the file, so we
pair it with a content digest that anything can verify."*
