# 2.1 — A finding is a return value

## One-line answer

Every check in `tools/skill_checks.py` takes a skill and returns a list of `Finding` — it never
prints, never exits and never raises because a skill is bad — because the same function has to serve a
test that asserts on it today and a command-line linter that turns it into an exit code tomorrow.

## The story

The meter reader who comes round the flats writes the number on a card and leaves.

They do not cut anybody off. They are standing right beside the box, they can see the reading is
absurd, they could very reasonably reach up and pull the switch — and they do not, because that is not
their job and they do not have the rest of the information. Maybe the flat has a new tenant. Maybe the
old reading was wrong. Maybe there is a dispute open.

So the reading goes on the card and the card goes to the office, and the office decides. And because
the reader's job is only to produce a number, the same reading feeds the monthly bill, the annual
audit and the leak investigation, without the reader knowing or caring which. If they had pulled the
switch, there would be no number for any of the three, and the flat would be dark.

## The idea in plain language

A check function has to decide what to do when it finds something wrong. There are four options and
only one of them is any good.

**Raise an exception.** Natural in Python and wrong here, because an exception stops the walk. Your
shelf has four skills, the second is broken, and you learn nothing about the third and fourth until
you have fixed the second. Three round trips to find three problems.

**Print the problem.** Convenient and untestable. A test cannot assert on something that went to
standard output without capturing it, and a linter that wants to sort findings, count them, or print
them as JSON now has to parse its own output back.

**Call `sys.exit`.** This is a decision about the *program*, made inside a function that knows about
one skill. Import that function into a test and the test run dies.

**Return the problem as a value.** The caller — a test, a linter, a report, an editor plugin — decides
what a finding means. This is the meter reader's card.

That fourth option has a name in this repository already. Day 29's audit passes each returned a small
immutable record rather than raising
([Day 29, 2.1](../../../day-29-sourcing-and-auditing-skills/parts/02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md)),
for exactly the same reason. Today's `Finding` is the same idea pointed at first-party skills, with
one deliberate difference in its fields, and part of this document is explaining that difference.

A **pure function**, in the sense this module uses the word, is one that reads its arguments, touches
no global state, changes nothing on disk, and returns a value. The checks here read files, so they are
not pure in the strict mathematical sense — but they have no side effects a caller can be surprised
by, and that is the property that matters: you can call them in any order, twice, from a test, without
setting anything up or cleaning anything after.

## Why Sutra needs it

Because Day 31 exists and cannot be allowed to write these rules a second time.

Tomorrow (`days/day-31-the-quality-gate/`) adds `tools/lint_skills.py`, a command-line linter with a
`main() -> int` that `./m check` runs on every commit. If today's checks printed and exited, tomorrow
would have to either shell out to a script and parse its text, or copy the rules into a second module.
Both of those produce two implementations of one specification, and
[1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md) already explained what happens when two
checkers disagree.

`tools/` is a new top-level package and today is the day it is created. Day 31 adds modules to it and
Day 45 adds `tools/mcp_audit.py` for the MCP phase gate. All three are the same shape: pure check
functions in one module, a thin front door in another.

## The mechanism

The package first. `tools/` needs an `__init__.py` so that `from tools.skill_checks import ...` works
from anywhere in the repository:

```bash
mkdir -p tools
touch tools/__init__.py
```

**Line by line:**

- `mkdir -p tools` creates the directory at the repository root, beside `sutra/` and `tests/`. `-p`
  makes it a no-op if the directory already exists, so the command is safe to re-run.
- `touch tools/__init__.py` creates an empty file. It stays empty deliberately: `tools` is a namespace
  for repository tooling, not a library with an API, so there is nothing to re-export. Without the
  file, `import tools.skill_checks` works only when the current directory happens to be the repository
  root, and fails in continuous integration for reasons that take an evening to find.
- `tools/` is not `sutra/`. Nothing in `tools/` ships as part of the product; it is the machinery that
  checks the product. `pyproject.toml` lists only `sutra` and `sutra_mcp` as wheel packages, so
  `tools/` is present in the repository and absent from anything you build.

Now the record every check returns. This is the first code in `tools/skill_checks.py`:

```python
"""Mechanical checks over a skill folder, as pure functions that return findings.

Every function here takes a path or a loaded skill and returns a list of `Finding`.
Nothing prints, nothing calls `sys.exit`, and nothing raises because a skill is bad:
a check that raises stops the shelf scan at the first broken folder, and a check that
prints cannot be asserted on. That is what lets `tests/test_skills.py` use these
functions today and `tools/lint_skills.py` reuse them unchanged on Day 31.

There is no model call anywhere in this module.
"""

from __future__ import annotations

import hashlib
import re
from dataclasses import dataclass
from pathlib import Path

from google.adk.skills import load_skill_from_dir
from google.adk.skills.models import Skill

MAX_BODY_LINES = 500
RESOURCE_DIRS = ("references", "scripts", "assets")
WHEN_WORDS = ("use when", "use for", "when a", "when the", "when you", "when someone")
DIGEST_KEY = "digest"
DIGEST_LENGTH = 12

RESOURCE_PATH_RE = re.compile(rf"(?:{'|'.join(RESOURCE_DIRS)})/[A-Za-z0-9._/-]*[A-Za-z0-9_-]")


@dataclass(frozen=True)
class Finding:
    """One rule a skill folder breaks. A value the caller decides what to do with."""

    skill: str
    rule: str
    detail: str

    def __str__(self) -> str:
        return f"{self.skill:<24} {self.rule:<16} {self.detail}"
```

**Line by line:**

- The module docstring states the contract in the file, not in a design document. Anyone who opens
  `skill_checks.py` to add a rule reads *nothing raises, nothing prints* before they write a line, and
  the review comment when they forget writes itself.
- `from __future__ import annotations` makes every annotation a string at runtime, which is what lets
  `Skill | None` be written on Python 3.12 without importing `Optional`, and keeps the annotations
  cheap to evaluate.
- `dataclass(frozen=True)` gives three fields, value equality and immutability. Value equality is the
  property the tests lean on hardest: `assert check_version(skill) == []` and
  `assert [f.rule for f in findings] == ["no-version"]` both work because two findings with the same
  three strings *are* the same finding. Frozen because a finding is evidence, and evidence that a
  later pass can edit is not evidence.
- The three fields answer the three questions a reader has, in the order they have them. `skill` is
  *which folder*, `rule` is *what kind of problem* — a short tag you can group and count — and
  `detail` is the specific text, enough to act on without opening the file.
- `rule` is a fixed vocabulary (`no-version`, `dead-pointer`, `will-not-load`) rather than a sentence.
  That is what makes `[f.rule for f in findings] == ["no-version"]` a readable assertion. If `rule`
  held prose, every test would be asserting on wording and would break the first time somebody
  improved a message.
- Day 29's `Finding` had `where`, `rule`, `detail`, where `where` was a `file:line` address inside a
  possibly hostile skill. Here the first field is `skill` — the folder name — because these are your
  own skills and the unit you act on is the whole skill, not a line. Same idea, different grain, and
  the two are deliberately separate types: the audit pipeline is lab code for reading strangers'
  skills, and this is project code for guarding your own.
- `__str__` fixes the three-column layout once, so a test's failure message and a linter's report look
  identical and you learn to read one format instead of two.
- `MAX_BODY_LINES`, `RESOURCE_DIRS` and `WHEN_WORDS` are module constants rather than literals buried
  in functions, because Day 31's linter imports them to print its own help text, and a rule whose
  threshold is a magic number inside a function cannot be documented from outside.

## When it breaks

**A check that raises anyway.** You add a rule and write it the natural way:

```text
tests/test_skills.py:36: in test_every_skill_on_the_shelf_passes_every_check
    findings = check_shelf(SHELF)
tools/skill_checks.py:57: in check_shelf
    findings.extend(check_skill(folder))
tools/skill_checks.py:44: in load
    return load_skill_from_dir(folder), []
E   pydantic_core._pydantic_core.ValidationError: 1 validation error for Frontmatter
E   name
E     Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading,
E     trailing, or consecutive delimiters [type=value_error, input_value='Bad--Name', input_type=str]
```

Read what that costs. The test failed with an exception rather than with a list, so the message tells
you about `Bad--Name` and nothing about the other three skills. Worse, the failure is now an *error*
rather than an assertion, so a reader's first instinct is that the test is broken, not that the shelf
is. [2.2](2.2-let-the-loader-be-the-oracle.md) is where that exception is caught and turned into a
row.

**A check that prints.** Nothing fails. The finding appears in the terminal during the test run, the
test passes because nothing was asserted, and the suite is now a program that reports problems while
claiming everything is fine. This is the most expensive mistake in the module because it looks like it
is working.

**A check that returns `None` for "no problem".** Then every caller has to write
`findings = check(skill) or []`, and the first one that forgets crashes on
`TypeError: 'NoneType' object is not iterable` at the point where the results are combined, several
frames away from the check that returned it. Always return the empty list. A function that returns a
list returns a list.

## In production

**What a professional writes instead** of a check that decides, is a check that reports and a caller
that decides — and the reason is that the decision differs by caller. In a pull request, one finding
should block the merge. In a nightly report over a hundred skills, findings are grouped by rule and
counted so the team can see that thirty skills are missing a version and one is unloadable. In an
editor, a finding is a squiggly line. Same function, three policies. That only works if the function
returns data.

**What degrades at scale** is the message, not the mechanism. At four skills you print every finding.
At four hundred you have a report where the same rule fires two hundred times, and the useful output
is *which rule, how many, and the three worst folders*. Because `rule` is a fixed tag, that grouping
is two lines of `collections.Counter`; if `rule` had been prose, it would be a text-mining exercise.
The field that looks like over-engineering at four skills is the one that saves the report at four
hundred.

**The review comment a senior engineer leaves:** *"`check_version` calls `sys.exit(1)` when the field
is missing. That means importing this module into a test can kill the test run, and it means Day 31's
linter cannot decide that a missing version is a warning during the migration. Return the finding and
let the caller pick the policy."*

**The interview question:** *"why do your lint checks return values instead of raising?"* The honest
spoken answer: *"Because the same rules have three consumers with three different policies — the test
suite asserts on them, the merge gate turns them into an exit code, and a nightly report groups and
counts them. If the check raises, the first bad skill hides every skill after it and you get one
problem per run instead of all of them. If it prints, nothing can assert on it. So each check returns
a list of small frozen records with a folder, a fixed rule tag and a detail string, and the caller
decides what a finding means. The fixed tag rather than a sentence is what makes both the assertions
and the grouped report possible."*
