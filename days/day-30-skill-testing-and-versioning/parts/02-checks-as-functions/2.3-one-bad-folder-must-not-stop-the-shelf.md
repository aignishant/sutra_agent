# 2.3 — One bad folder must not stop the shelf

## One-line answer

`load_skills_from_dir` raises on the first broken folder and tells you nothing about the rest, so the
checker walks the shelf itself and loads each folder separately — one bad skill becomes one row, not a
dead run.

## The story

The queue at the bill counter stops because the third person's card will not go through.

There are eleven people behind them. Every one of those eleven has a card that works and a bill that
is fine, and none of them will find that out for a while, because the clerk is on the phone to the
bank about somebody else's card. The counter has one lane and the lane is blocked.

The counter next door does it differently. If a card fails, the clerk sets that bill aside with a
note, calls the next person, and comes back to the set-aside pile at the end. Same failures, same
clerk, same number of problems — and everybody who could be served has been served, and the pile at
the end tells the manager how many card failures there were today, which the first counter never
learns because it never got past the third one.

## The idea in plain language

ADK ships two loaders. They have almost the same name and completely different behaviour when
something is wrong.

`load_skill_from_dir(folder)` loads **one** folder. It either returns a `Skill` or raises. That is the
one [2.2](2.2-let-the-loader-be-the-oracle.md) wraps.

`load_skills_from_dir(shelf)` loads **every** folder under a directory and returns a list. You met it
on [Day 26, 1.4](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.4-the-whole-shelf.md).
Reading the installed package on 2026-09-04, its loop is a plain `for` with an `append`: the first
folder that raises takes the whole call with it. Its own docstring says so —
*"Raises … ValueError: If skills_dir is not a directory, or if any skill fails validation."*

For your **runtime** that is arguably correct behaviour, and
[Day 26, 4.1](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.1-one-bad-folder.md) is
the part that showed what it feels like: one malformed folder and the desk agent will not start at
all. Failing loudly at startup beats starting with a shelf that is quietly missing a skill.

For your **checker** it is exactly wrong, for the reason the queue is wrong. A checker exists to
produce a complete list of what is broken. A checker that stops at the first problem gives you one
problem per run, so fixing four problems takes four runs, and each run is a commit-push-wait cycle if
the checker lives in continuous integration.

So the checker enumerates the shelf itself, and calls the single-folder loader once per folder inside
its own loop. Same rules, same oracle, different failure policy — and the policy is the whole point of
this part.

## Why Sutra needs it

Because a shelf that will not load is the failure Day 31's gate exists to stop, and the gate is only
useful if it tells you everything that is wrong in one go.

There is a second, sharper reason. `sutra/desk/skills.py` calls `load_shelf`, which calls the ADK shelf
loader, at startup. If two skills are broken, production fails on the first one, you fix it, deploy,
and production fails on the second one. Your checker is the thing that is supposed to have told you
about both before either reached a deploy. A checker with the same all-or-nothing policy as the
runtime is not adding anything the runtime was not already going to tell you — just earlier.

## The mechanism

Two functions. `check_skill` runs every rule over one folder, and `check_shelf` walks the directory.

```python
def check_skill(folder: Path) -> list[Finding]:
    """Every check, over one skill folder, cheapest first."""
    skill, findings = load(folder)
    if skill is None:
        return findings
    return [
        *check_description(skill),
        *check_references(folder, skill),
        *check_version(skill),
        *check_body_length(skill),
        *check_digest(folder, skill),
    ]


def check_shelf(shelf: Path) -> list[Finding]:
    """Every check, over every skill folder on the shelf, enumerated live."""
    if not shelf.is_dir():
        return [Finding(shelf.name, "no-shelf", f"{shelf} is not a directory")]
    findings: list[Finding] = []
    for folder in sorted(p for p in shelf.iterdir() if p.is_dir()):
        if not (folder / "SKILL.md").is_file() and not (folder / "skill.md").is_file():
            findings.append(Finding(folder.name, "not-a-skill", "folder has no SKILL.md"))
            continue
        findings.extend(check_skill(folder))
    return findings
```

**Line by line:**

- `if skill is None: return findings` is the early exit, and it is the only place in the module where
  a check stops early. It has to: every rule after this one takes a `Skill` object, and there is not
  one. Returning the load finding alone is honest — *this folder will not load, so nothing else could
  be checked* — rather than inventing four more findings about fields you could not read.
- The `*` unpacking builds one flat list from five lists. `[*a, *b]` rather than `a + b + …` because
  the star form reads as *these five checks, in this order*, and adding a sixth is one line with no
  operator to get wrong.
- The order is cheapest first, the same discipline as Day 29's five-pass audit
  ([2.1](../../../day-29-sourcing-and-auditing-skills/parts/02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md)).
  `check_description` is a substring search over one string; `check_digest` hashes every file in the
  folder. On a shelf with a problem in the first rule, you see it in the first row of the report.
- `check_shelf` handles a missing `skills/` directory as a **finding**, not an exception, because the
  contract from [2.1](2.1-a-finding-is-a-return-value.md) applies to the shelf function too. A repo
  checked out without `skills/` should get a readable row, not a traceback in continuous integration.
- `sorted(p for p in shelf.iterdir() if p.is_dir())` gives a stable order. `iterdir()` yields in
  whatever order the filesystem hands over, which differs between machines, so an unsorted report
  produces a different diff on every developer's screen for the same shelf.
- The `SKILL.md` / `skill.md` pair mirrors what the loader itself accepts — the installed package tries
  both names in that order — so a folder the loader would skip produces a `not-a-skill` finding rather
  than a confusing `will-not-load`. A `.git` directory or a `__pycache__` under `skills/` lands here
  too, which is why the rule is a separate tag: it usually means *this is not a skill*, not *this
  skill is broken*.
- `continue` after the `not-a-skill` finding, so the walk carries on. That single keyword is the whole
  difference between this and the shelf loader.

The difference in one run. Both of these were measured on 2026-09-04, on a shelf holding two good
skills and one folder named `Bad--Name`:

```text
load_skills_from_dir:
  ValidationError - the whole shelf failed
check_shelf:
  Bad--Name                will-not-load    ValidationError: 1 validation error for Frontmatter name Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading, trailing, or consecutive delimiters [type=value_error, input_value='Bad--Name', input_type=str] For further information visit https://errors.pydantic.dev/2.13/v/value_error
```

Read the second line carefully: it names one folder, which means the other two were checked and were
clean. The first line tells you a shelf failed and nothing else at all.

## When it breaks

**The checker inherits the runtime's policy by accident.** Somebody writes the obvious thing:

```text
tests/test_skills.py:36: in test_every_skill_on_the_shelf_passes_every_check
    findings = check_shelf(SHELF)
tools/skill_checks.py:52: in check_shelf
    for skill in load_skills_from_dir(shelf):
E   pydantic_core._pydantic_core.ValidationError: 1 validation error for Frontmatter
E   name
E     Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading,
E     trailing, or consecutive delimiters [type=value_error, input_value='Bad--Name', input_type=str]
```

It is not obviously wrong. The test does fail, on a real problem, with a real message. What you have
lost is invisible: the other three skills were never looked at, and you will find their problems one
commit at a time.

**A hidden folder counted as a skill.** `skills/.DS_Store` is a file, so it is skipped by `is_dir()`.
`skills/.ipynb_checkpoints/` is a directory and produces `not-a-skill: folder has no SKILL.md`, which
is a true statement and useless noise. The fix is a rule about what counts as a candidate folder — for
example, skipping names that start with a dot — and the reason it is not in the code above is that
Sutra does not have the problem yet. Adding a filter for a case you have never seen is the kind of
guessing [1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md) argues against; adding it the day the
noise appears is right.

**A findings list that is complete and unreadable.** Ten skills, four rules each, and the report is
forty rows. That is not a bug in `check_shelf` — it is what completeness costs — but it is the point
where the caller has to start grouping. This is why `Finding.rule` is a fixed tag
([2.1](2.1-a-finding-is-a-return-value.md)): forty rows collapse to *"three skills will not load, six
are missing a version"* with two lines in the caller.

## In production

**What a professional writes instead** is exactly this shape, with one addition: an option to check a
subset. In a large repository the linter runs against the folders a commit touched, and against the
whole shelf on a schedule. `check_shelf` already makes that trivial, because the per-folder function
is public — a caller with a list of changed paths calls `check_skill` on each. That is a property of
the design, not a feature: the walk and the check are separate functions, so the caller can supply its
own walk.

**What degrades at scale** is the ordering guarantee. `sorted()` on `Path` objects sorts by the
platform's path semantics, which puts `Bad--Name` before `a-skill` on a case-sensitive filesystem and
somewhere else on Windows. On a two-person project nobody notices; on a team whose continuous
integration runs Linux and whose developers run Windows, the same shelf produces reports in two orders
and somebody wastes an afternoon diffing them. Sorting by `p.name.lower()` costs nothing and removes
the class of problem.

**The review comment a senior engineer leaves:** *"`check_shelf` calls `load_skills_from_dir`. That
means our linter has the same all-or-nothing failure as our runtime, and the whole reason to have a
linter is to learn about every problem before the runtime learns about the first one. Walk the
directory here and call the single-folder loader per folder."*

**The interview question:** *"your framework's bulk loader raises on the first bad item. What do you do
in your validation tool?"* The honest spoken answer: *"I do not use the bulk loader in the tool. The
runtime should fail fast — I would rather the agent refuse to start than start with a silently missing
skill — but a checker exists to produce the complete list, and a checker that stops at the first
problem gives you one problem per commit-push-wait cycle. So the checker walks the directory itself,
calls the single-item loader inside the loop, catches the documented exceptions and turns each into a
row. Same rules, same oracle, different failure policy. The single-folder function stays public too,
so continuous integration can check only the folders a commit touched."*

```bash
uv run python -c "
from pathlib import Path
from tools.skill_checks import check_shelf
findings = check_shelf(Path('skills'))
print(f'{len(findings)} finding(s)')
for f in findings:
    print(' ', f)
"
```

folder afterwards.
