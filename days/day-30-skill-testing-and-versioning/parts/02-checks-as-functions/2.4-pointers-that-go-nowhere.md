# 2.4 — Pointers that go nowhere

## One-line answer

A skill body that names `references/severity-rubric.md` is making a promise about a file, nothing in
ADK checks that the promise holds, and a broken promise costs you a worse answer with no error — so
the checker extracts every resource path the body mentions and asks the filesystem.

## The story

The notice on the clinic wall says *"for the list of documents you need, see the poster in the
lobby."*

There is no poster in the lobby. There was one. It came down when the lobby was painted, and whoever
took it down did not know that a notice two corridors away pointed at it. Everybody who reads the
notice walks to the lobby, looks at a blank wall, and then does the sensible thing: they guess which
documents they need, and about a third of them guess wrong and have to come back another day.

The notice is not wrong exactly. It was true when it was written. And nobody complains about the
notice, because the people who read it do not know that the poster ever existed — they only know they
looked and there was nothing there.

## The idea in plain language

[Day 27, 1.7](../../../day-27-authoring-first-skills/parts/01-extraction/1.7-what-goes-behind-a-link.md)
established the rule Sutra follows: heavy detail does not sit in the body, it sits in a file under
`references/` and the body **names the file**. That is what keeps the body small, and a small body is
what keeps every activation cheap
([Day 28, 1.3](../../../day-28-progressive-disclosure-design/parts/01-the-price-list/1.3-weight-flows-down.md)).

The mechanism has one weak joint. The body says `references/severity-rubric.md` in ordinary prose.
Nothing anywhere connects that string to a file:

- **ADK does not.** It reads the `references/` directory into `Skill.resources.references` and the
  body into `Skill.instructions`, and never relates the two. Confirmed by reading `_load_skill_from_dir`
  in the installed `google-adk==2.7.1` on 2026-09-04: the two are loaded independently and there is no
  cross-check, which is correct behaviour for a framework, because the body is free-form Markdown and
  a path in it could mean anything.
- **The specification does not.** It recommends keeping file references one level deep and says
  nothing about verifying them (`https://agentskills.io/specification`, read 2026-09-04).
- **Your editor does not**, because `references/severity-rubric.md` inside a sentence is not a
  Markdown link.

So the failure is exactly the clinic notice. The agent, following the body, asks to read a file that
is not there. It does not stop; it answers anyway, without the rubric, and the answer is worse in a
way that looks like the model being unreliable rather than like a missing file.

This is the third of Sutra's six rules from
[1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md), and it passes all three tests cleanly:
breaking it changes behaviour silently, the filesystem decides it without argument, and nothing else
catches it.

## Why Sutra needs it

Because Sutra's flagship skill points at a file, and the day it stops pointing at that file is the day
triage quietly gets worse.

`skills/ticket-triage/SKILL.md` names `references/severity-rubric.md`, and Day 28 deliberately moved
its worked example out to a reference file as well
([Day 28, 1.4](../../../day-28-progressive-disclosure-design/parts/01-the-price-list/1.4-moving-the-example.md)).
Every one of those moves added a pointer, and pointers are what breaks when somebody tidies a folder.

The same check has a second life on Day 29's territory: a sourced skill whose body points at a file
that is not in the pack is either a packaging mistake or a skill that expects to fetch something at
runtime, and both are worth a row in a report
([Day 29, 2.5](../../../day-29-sourcing-and-auditing-skills/parts/02-the-five-pass-audit/2.5-the-files-it-points-at.md)
did this as an audit pass). Today it becomes a permanent check on your own shelf rather than a
one-time read of somebody else's.

## The mechanism

Two functions: one that finds the paths, one that asks the filesystem.

```python
RESOURCE_DIRS = ("references", "scripts", "assets")
RESOURCE_PATH_RE = re.compile(rf"(?:{'|'.join(RESOURCE_DIRS)})/[A-Za-z0-9._/-]*[A-Za-z0-9_-]")


def _resource_paths(body: str) -> list[str]:
    """Every references/, scripts/ or assets/ path the body names, in order, deduplicated."""
    seen: dict[str, None] = {}
    for match in RESOURCE_PATH_RE.finditer(body):
        seen.setdefault(match.group(0), None)
    return list(seen)


def check_references(folder: Path, skill: Skill) -> list[Finding]:
    """Every resource path the body mentions resolves to a file that exists."""
    return [
        Finding(skill.name, "dead-pointer", f"body points at {token}")
        for token in _resource_paths(skill.instructions)
        if not (folder / token).is_file()
    ]
```

**Line by line:**

- `RESOURCE_DIRS` is the specification's three conventional directories, in one tuple, used by both
  this check and the digest in [5.3](../05-versioning/5.3-the-change-the-version-missed.md). One
  definition means the two can never disagree about what counts as a resource.
- The regular expression is built from that tuple with an f-string, so adding a fourth convention is
  one edit. `(?:…)` is a non-capturing group: it groups the alternatives without creating a capture,
  which keeps `match.group(0)` — the whole match — the only thing anyone reads.
- The character class ends with `[A-Za-z0-9_-]` rather than allowing a trailing dot, and this is the
  detail that took a real bug to find. A body that says *"then run `scripts/check.py`."* ends the
  sentence with a full stop, and a pattern allowing a trailing `.` captures `scripts/check.py.` — a
  path that does not exist, so the checker reports a dead pointer at a file that is perfectly fine.
  A checker that is wrong once is disbelieved forever
  ([1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md)), so the last character is constrained to
  something that cannot be sentence punctuation.
- `dict[str, None]` with `setdefault` is a deduplicating set that keeps insertion order. A plain `set`
  would lose the order, and the order matters: findings should appear in the order a reader would meet
  them when reading the body downwards. A body that names the rubric three times produces one finding,
  not three.
- `(folder / token).is_file()` joins onto the **skill folder**, because the specification says
  references are relative to the skill root. Joining onto `skills/` or onto the repository root is the
  false-positive machine described in [1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md)'s
  *When it breaks*, and it is worth saying out loud that `folder` is a parameter for exactly this
  reason rather than being derived from `skill`, which has no path on it.
- `.is_file()` rather than `.exists()`. A directory named `references/rubric.md` would satisfy
  `exists()` and cannot be read as a file, and the check is about whether the agent can read it.
- The list comprehension returns `[]` when everything resolves, which is the contract from
  [2.1](2.1-a-finding-is-a-return-value.md) — no `None`, no special case.

What the check sees on a body that lost a file. Measured on 2026-09-04, after renaming
`references/severity-rubric.md` to `references/rubric.md` and leaving the body alone:

```text
ticket-triage            dead-pointer     body points at references/severity-rubric.md
```

One row, naming the skill, the rule and the exact string in the body. That is enough to fix the
problem without opening the folder.

## When it breaks

**The over-eager match.** Your body contains an example of what *not* to do, or a sentence about
another skill's layout, and the checker reports it:

```text
kb-answer-style          dead-pointer     body points at references/EXAMPLE.md
```

The rule is doing exactly what it was asked to. The body mentioned a path and the path does not exist.
The honest fixes, in order of preference: do not put example paths in a body, or create the file, or —
last and only if the first two genuinely do not fit — narrow the pattern to Markdown link syntax so
only `[text](references/x.md)` counts. That last one trades false alarms for missed pointers, because
Sutra's own bodies name files in plain prose, so it is a real loss and not a free win.

**The pointer that escapes the folder.** A body that says `../shared/header.md` is not matched by this
pattern at all, because the pattern starts at one of the three conventional directory names. That is a
deliberate gap and it has a name: an escaping reference is outside the skill's own folder, so it is
also outside the folder digest ([5.3](../05-versioning/5.3-the-change-the-version-missed.md)) and
outside anything Day 29's pin covers
([Day 29, 4.2](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.2-the-pin-is-the-promise.md)).
Sutra's answer is a rule rather than a regular expression: skills do not point outside themselves. A
check for that rule is a good `TODO(me)`.

**The file that exists and is empty.** `.is_file()` is `True` for a zero-byte file, so a rubric
somebody truncated passes. The check is about the promise the body made — *there is a file here* — and
that promise is kept. Whether the file says anything useful is sense, not shape
([1.2](../01-testing-prose/1.2-shape-and-sense.md)), and it belongs to the human reviewing the change.

## In production

**What a professional writes instead** at scale is the same check plus its mirror image: a report of
files under `references/` that **no** body mentions. A dead pointer is a body pointing at nothing; an
orphan is a file nothing points at, and orphans are how a skill folder grows from four files to
thirty over two years, each one loaded into memory at startup by
`load_skill_from_dir` and read by nobody. The two checks share `_resource_paths` and differ only in
which side of the comparison they walk.

**What degrades at scale** is the false-alarm rate, and it degrades faster than you expect. At four
skills, all written by you, every mention of `references/x.md` is a real pointer. At forty skills
written by five people, bodies contain example paths, paths belonging to other skills, and paths
inside fenced code blocks that are illustrations rather than instructions. The rate at which people
believe a linter is set by its false alarms, not by its true findings, so the professional version
either excludes fenced code blocks from the search or is prepared to defend every finding it makes.

**The review comment a senior engineer leaves:** *"this joins the path onto the repository root, so it
passes today only because you happen to run it from the root. Join onto the skill folder — that is
what the spec says references are relative to — and it will keep working when the linter runs from
continuous integration with a different working directory."*

**The interview question:** *"you have Markdown files that reference other files by path. How do you
stop the references rotting?"* The honest spoken answer: *"A check that extracts every path the body
mentions and asks the filesystem whether it is a file. Nothing else does it — the framework loads the
references directory and the body independently and never relates them, and that is the right call for
a framework because the body is free-form. So it is a project rule. Two details bit us: the pattern
must not swallow the full stop at the end of a sentence, because one false finding costs you the
linter's credibility permanently, and the path must be joined onto the skill folder rather than the
working directory, because the spec says references are relative to the skill root. The mirror check —
files nothing points at — is worth having too, since those are loaded at startup and read by nobody."*

## Check yourself

```bash
uv run python -c "
from pathlib import Path
from google.adk.skills import load_skill_from_dir
from tools.skill_checks import _resource_paths, check_references
folder = Path('skills/ticket-triage')
skill = load_skill_from_dir(folder)
print('paths in the body:', _resource_paths(skill.instructions))
print('files on disk    :', skill.resources.list_references())
print('findings         :', [str(f) for f in check_references(folder, skill)])
"
```

Rename one file under `skills/ticket-triage/references/`, run it again, and read the finding. Rename
it back.
