# 2.2 — Let the loader be the oracle

## One-line answer

Do not re-implement the specification's rules — call the loader your agent will use at runtime, catch
what it raises, and turn the exception into a finding, because then your check and your runtime can
never disagree about whether a skill is valid.

## The story

The shopkeeper weighs your vegetables on the shop's scale, not on the one you brought from home.

You could bring one. Some people do, and some of them are right — home scales can be perfectly
accurate. But the price is settled by the shop's scale, so a disagreement between the two is not a
disagreement about the weight. It is an argument, and the argument always ends the same way, because
the number that decides what you pay is the one on the counter.

The sensible customer does not bring a scale. They watch the shop's needle. If the needle is wrong,
that is worth knowing — but you find that out by watching the needle that matters, not by trusting a
second one nobody has agreed to.

## The idea in plain language

Your checker needs to answer *is this skill valid?* There are two ways to get an answer.

**Write your own rules.** Read the file, parse the frontmatter, apply a regular expression to the
name, count the description. It works, it is a few dozen lines, and it is a second copy of the
specification living in your repository. The moment ADK's rules move — a new field, a normalisation
step, a relaxed pattern — your copy is stale and confidently wrong.

**Ask the thing that decides.** At runtime, the skill is loaded by
`google.adk.skills.load_skill_from_dir`
([Day 26, 1.1](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.1-load-skill-from-dir.md)).
If that function returns a `Skill`, the skill is valid *by the only definition that matters to your
program*. If it raises, the skill will not load in production either, and the exception's message is
already the explanation.

That second approach has a name worth knowing: the loader is your **oracle** — the authority that
decides whether an answer is right. Testing against the real oracle rather than a replica of it is why
your check can never drift out of agreement with your runtime.

Reading the installed package on 2026-09-04, `load_skill_from_dir` fails in four situations and raises
exactly three types between them, all documented in its own docstring:

| What is wrong | What it raises | Message shape |
| --- | --- | --- |
| the folder or `SKILL.md` is missing | `FileNotFoundError` | `SKILL.md not found in '<path>'.` |
| the frontmatter is not valid YAML, or has no `---` fence | `ValueError` | `SKILL.md must start with YAML frontmatter (---)` |
| a field breaks a spec rule | `pydantic.ValidationError` | `1 validation error for Frontmatter …` |
| the `name` does not match the folder | `ValueError` | `Skill name 'x' does not match directory name 'y'.` |

One detail makes the catch clause short. `pydantic.ValidationError` **is a subclass of `ValueError`** —
verified on the installed `pydantic` on 2026-09-04 — so `except (FileNotFoundError, ValueError)`
covers every documented failure and nothing else. Anything that is not on that list is a genuine
surprise and should surface, which is Principle 10: errors surface, they are not swallowed.

## Why Sutra needs it

Because three of the six rules in [1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md) are already
enforced by the loader, and re-implementing them is the mistake that day's third test exists to
prevent.

There is also a second, quieter benefit. Sutra's shelf is loaded at startup by `load_shelf` in
`sutra/desk/skills.py` ([Day 27](../../../day-27-authoring-first-skills/parts/03-procedure-and-capability/3.3-two-skills-one-toolset.md)),
which calls the same ADK loader. So a green `check_loads` is a real promise about startup: not *"we
believe this is well-formed"* but *"this exact function returned a `Skill` object for this exact
folder"*. That is the promise Day 31's gate needs, because the thing the gate is protecting against is
a broken shelf taking the desk agent down on the next deploy.

## The mechanism

One function. It is the smallest in the module and it does the most work, because all the rules live
in ADK.

```python
def load(folder: Path) -> tuple[Skill | None, list[Finding]]:
    """Load one skill folder. Returns the skill, or None plus one finding saying why."""
    try:
        return load_skill_from_dir(folder), []
    except (FileNotFoundError, ValueError) as exc:
        message = " ".join(str(exc).split())
        return None, [Finding(folder.name, "will-not-load", f"{type(exc).__name__}: {message}")]
```

**Line by line:**

- The return type is a **pair**, not a `Skill` and not a list. It has to be, because there are two
  outcomes and both carry information: either you have a skill to run the remaining checks against, or
  you have a finding explaining why you never will. A function that returned only the findings would
  force every caller to load the skill a second time.
- `load_skill_from_dir` is the exported name in `google/adk/skills/__init__.py` — it is a public
  re-export of the private `_load_skill_from_dir`, so importing it from `google.adk.skills` is the
  supported path and importing the underscore name is not. Verified against `https://adk.dev/skills/`
  and against the installed `google-adk==2.7.1` on 2026-09-04.
- `except (FileNotFoundError, ValueError)` is the whole documented failure surface, as the table above
  shows, and `ValidationError` arrives through `ValueError` because it inherits from it. Writing
  `except Exception` here would also catch a `PermissionError`, a `UnicodeDecodeError` or a bug in
  your own code, and report all three as "this skill is invalid" — which is a lie, and the kind of lie
  that costs a whole evening.
- `" ".join(str(exc).split())` collapses a multi-line pydantic message onto one line. A
  `ValidationError` prints across four lines with indentation; a finding is one row in a table, and a
  four-line row destroys the layout `Finding.__str__` establishes. `str.split()` with no argument
  splits on any run of whitespace including newlines, so this is the shortest correct way to flatten
  it.
- `type(exc).__name__` goes into the detail rather than the rule tag. The rule is always
  `will-not-load` because that is the *consequence* and the consequence is what a reader triages on;
  the exception class is a detail that helps you fix it. Keeping the tag stable is what lets a report
  count "three skills will not load" without caring how.
- `folder.name` rather than the loaded skill's name, because there is no loaded skill. This is the one
  check where the frontmatter cannot be trusted to identify the folder — and the mismatch between the
  two is one of the failures being reported.

Here is what the two most common failures actually look like when they come back as findings, run on
2026-09-04 against a reconstruction of the shelf:

```text
Bad--Name                will-not-load    ValidationError: 1 validation error for Frontmatter name Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading, trailing, or consecutive delimiters [type=value_error, input_value='Bad--Name', input_type=str] For further information visit https://errors.pydantic.dev/2.13/v/value_error
renamed-folder           will-not-load    ValueError: Skill name 'ticket-triage' does not match directory name 'renamed-folder'.
```

Both rows carry the framework's own words. You did not write either message, which means neither can
disagree with what happens at startup.

## When it breaks

**The `except` clause that is too wide.** Somebody writes `except Exception` because it is shorter,
and one day a reference file is saved in a non-UTF-8 encoding. What you get is:

```text
ticket-triage            will-not-load    UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0: invalid start byte
```

The skill is fine. The frontmatter is fine. The name matches the folder. A reader spends the evening
staring at `SKILL.md` because the finding said the skill will not load, when the actual problem was a
file in `references/`. Catch what is documented and let the rest surface.

**Catching the wrong thing because you guessed the API.** The docstring in the installed package is the
source of truth for what a function raises, and it is two lines of reading:

```bash
uv run python -c "
from google.adk.skills import load_skill_from_dir
print(load_skill_from_dir.__doc__)
"
```

**Line by line:**

- `load_skill_from_dir.__doc__` prints the function's own docstring, which lists its `Raises:` section.
  This is Principle 8 at its cheapest: the installed package is on your disk, it is the exact version
  your program runs, and reading it takes one command. A guess about which exceptions to catch is the
  same class of error as a guess about a version pin, except that it fails on a Tuesday in production
  rather than immediately.

**A skill that loads and is still broken.** This is not a failure of the function; it is the boundary
from [1.2](../01-testing-prose/1.2-shape-and-sense.md) restated. `load` returning a `Skill` means the
shape is legal. Sutra's three house rules — a `when` clause, resolving pointers, a version — are
entirely invisible to it, which is why `check_skill` runs four more functions after this one.

## In production

**What a professional writes instead** of a hand-rolled validator is a thin adapter over the real
loader, and the reason is upgrade cost. When `google-adk` moves from 2.7 to 2.8 and the frontmatter
model gains a field or relaxes the name pattern, this function needs no change at all, and your
findings change to match the new rules on the next `uv sync`. A hand-rolled parser needs a diff read
and a patch, by somebody who notices — and nobody notices, because nothing fails.

**What degrades at scale** is the cost of loading. `load_skill_from_dir` reads `SKILL.md` *and*
recursively reads every file under `references/`, `scripts/` and `assets/` into memory
(`_load_dir` in the installed package does an `rglob("*")` and a `read_text` per file). At four skills
with small rubrics that is nothing. At four hundred skills with a megabyte of assets each, a linter
that loads every skill on every commit is reading a lot of bytes it does not look at. The professional
version caches by folder modification time, or checks only the folders a commit touched — and neither
of those is worth building until the check is actually slow, which it is not at Sutra's size.

**The review comment a senior engineer leaves:** *"you wrote a regular expression for the kebab-case
name rule. ADK normalises the name with Unicode NFKC before it matches, so on any name with a
full-width character your check and the runtime disagree — and the one that decides is the runtime.
Call the loader and report what it says."*

**The interview question:** *"how do you validate a config format your framework already parses?"* The
honest spoken answer: *"I do not re-parse it. I call the framework's own loader and catch the
documented exceptions, so the check and the runtime can never disagree — if the loader accepts it, it
will load in production, and if it raises, the message the framework wrote is already the best
explanation I could give. Two things make that work: catching only the documented exception types so a
`PermissionError` is not reported as an invalid skill, and flattening the multi-line pydantic message
onto one line so a finding stays one row. And when the library upgrades and its rules move, my checker
follows for free, which is the actual argument — a hand-written validator goes stale silently."*

## Check yourself

```bash
uv run python -c "
from pathlib import Path
from tools.skill_checks import load
skill, findings = load(Path('skills/ticket-triage'))
print('loaded:', skill is not None, '| findings:', findings)
skill, findings = load(Path('skills/does-not-exist'))
print('loaded:', skill is not None, '| findings:', [str(f) for f in findings])
"
```

The second call names a folder that is not there. Read the finding and say which of the four rows in
the exception table produced it.

**Out loud, without scrolling up:** say why calling the loader beats writing your own validator, name
the two exception types the catch clause needs and the third one it gets for free by inheritance, and
explain why the rule tag is `will-not-load` rather than the exception's class name.
