# 4.3 — What memory cannot test

## One-line answer

A `Skill` built in memory has no folder, so every rule that is about the folder — the name matching
the directory, a pointer resolving to a file, a digest over what is on disk — is untestable that way,
and those rules keep their evidence on the real shelf.

## The story

The first driving lesson happens in an empty car park on a Sunday, and it is the right place for it.

You learn the clutch there. You learn what the mirrors show and what the biting point feels like and
that the car does not move the instant you turn the key. Nobody is behind you, so a stall costs
nothing, and you can stall eleven times in a row and learn something from each one. Every single thing
you learn there is real and transfers.

And you cannot learn a roundabout in a car park. Not because the car park is a bad car park — because
a roundabout is made of other people, and there are no other people. The learner who spends six weeks
in the car park has genuinely mastered the clutch and has not begun the part of driving that involves
anybody else.

The instructor's job is to know which lesson belongs where, and to move you to the road on the day the
car park has nothing left to teach.

## The idea in plain language

[4.1](4.1-a-skill-without-a-folder.md) and [4.2](4.2-the-model-is-the-spec.md) built skills in memory
and got a lot for it: fast tests, no filesystem, cases the loader would refuse to load, and one line
per rule. That is the car park, and it is the right place for most of the checker lane.

Now the limits, stated exactly. A `Skill` object holds three things — `frontmatter`, `instructions`
and `resources` — and **not a path**. There is a private `_uri` attribute that
`load_skill_from_dir` sets for telemetry, and it is not part of the public model. So anything a check
needs the folder for cannot be reached from the object:

| Rule | Needs | Testable in memory? |
| --- | --- | --- |
| name is kebab-case, description non-empty | the frontmatter | yes — [4.2](4.2-the-model-is-the-spec.md) |
| the description says *when* | the description string | yes |
| `metadata.version` is present and quoted | the metadata dict | yes |
| the body is under 500 lines | the instructions string | yes |
| **the name matches the folder** | a folder | **no** |
| **every `references/` path resolves** | a folder | **no** |
| **the digest matches what is on disk** | a folder | **no** |

Look at the signatures and the split is already visible in the code:
`check_description(skill)`, `check_version(skill)` and `check_body_length(skill)` take a skill;
`check_references(folder, skill)` and `check_digest(folder, skill)` take a folder as well. A function
that needs a path says so in its parameters, and that is the honest signal of which lane it belongs
to.

There is a subtler trap in the same area. `Resources` in memory is a **dictionary of names to
content**, not a view of a directory:

- On disk, `load_skill_from_dir` reads `references/` into that dictionary, so a key exists exactly
  when a file exists.
- In memory you write the dictionary yourself, so `Resources(references={"rubric.md": "..."})` gives
  you a skill whose resources look complete and which is backed by no file anywhere.

An in-memory test of `check_references` would therefore be testing your own dictionary against your
own dictionary. It would pass, permanently, and prove nothing — the exact disease
[3.3](../03-the-suite/3.3-the-test-for-the-checker.md) is about.

## Why Sutra needs it

Because the three rules in bold are the three that catch the failures Sutra has actually met.

A renamed reference file is [2.4](../02-checks-as-functions/2.4-pointers-that-go-nowhere.md)'s clinic
notice and produces a worse answer with no error. A folder renamed without its `name` is the one
failure ADK announces loudly, and it stops the desk agent starting
([Day 26, 4.1](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.1-one-bad-folder.md)). A
reference file edited without a version bump is [5.3](../05-versioning/5.3-the-change-the-version-missed.md)'s
whole subject. All three are about the *folder*, and a suite that lived entirely in memory would have
no evidence for any of them.

So Sutra keeps two lanes on purpose, and the shelf lane is not a convenience. It is the only lane that
touches the filesystem, and the filesystem is where three of the six rules live.

## The mechanism

The division, made explicit. This is the part of `tests/test_skills.py` that carries evidence memory
cannot give:

```python
def test_the_shelf_is_not_empty() -> None:
    assert [p for p in SHELF.iterdir() if p.is_dir()], "skills/ holds no skill folders"


def test_every_skill_on_the_shelf_passes_every_check() -> None:
    findings = check_shelf(SHELF)
    assert findings == [], "\n" + "\n".join(str(f) for f in findings)
```

**Line by line:**

- These two tests, and only these two, read the disk. Everything else in the module runs on objects
  built in memory. Keeping that split visible — two tests at the top, the constructed cases below — is
  what stops somebody adding a third disk test in the middle and losing track of what the suite
  touches.
- `check_shelf(SHELF)` exercises the three folder rules against real folders. It cannot exercise them
  against *broken* folders, because the shelf is supposed to be clean, so what it proves is narrower
  than the checker lane's proofs: it proves the rules are silent on good input, not that they fire on
  bad.
- That narrowness is why [3.3](../03-the-suite/3.3-the-test-for-the-checker.md)'s alarm-button tests
  are the ones that matter for the four in-memory rules, and why the three folder rules get their
  firing evidence a different way — by hand, once, deliberately, which the *Check yourself* below is.

And the shape of a check that betrays which lane it is in:

```python
def check_body_length(skill: Skill) -> list[Finding]:
    """Takes a Skill. Testable in memory - no folder anywhere in the signature."""


def check_references(folder: Path, skill: Skill) -> list[Finding]:
    """Takes a folder too. Only testable against a real directory."""
```

**Line by line:**

- The parameter list is the specification of what a check can see, and reading it is faster than
  reading the body. A reviewer deciding whether a new rule can be tested in memory only has to look at
  the signature.
- `folder: Path` first, `skill: Skill` second, consistently across both folder-taking checks. Argument
  order is not important logically and is very important for readability: the same order everywhere
  means nobody has to check.
- There is a real temptation to pass the folder path *into* the skill object — a subclass, or a wrapper
  dataclass holding both — so every check has one parameter. Resist it. The wrapper would let a check
  that does not need the disk take it anyway, and within a year one of the in-memory-testable rules
  would quietly start reading a file, and the split this part is about would be gone.

## When it breaks

**A test that proves nothing, cheerfully.** Somebody writes the in-memory version of the reference
check:

```python
skill = Skill(
    frontmatter=Frontmatter(name="probe", description="Do it. Use when needed."),
    instructions="Read references/rubric.md first.",
    resources=Resources(references={"rubric.md": "S1 - production down."}),
)
```

**Line by line:**

- The body names `references/rubric.md` and the resources dictionary has a `rubric.md` key, so this
  looks like a skill whose pointer resolves.
- `check_references(folder, skill)` cannot be called on it at all — there is no folder — and a version
  of the check rewritten to compare against `skill.resources.list_references()` would pass here while
  saying nothing about the disk, because both sides of the comparison were written in this test.
- The tell is that the test's author had to choose both sides. A check is only evidence when one side
  of the comparison comes from somewhere the test does not control.

**Reaching for the private attribute.** You notice `_uri` on the model and think you have found the
path after all. Here is what the two kinds of skill actually give you, run on 2026-09-04:

```text
built in memory, _uri = None
loaded from disk, _uri = 'file:///C:/.../skills/ticket-triage'
```

It is worse than an error. A skill loaded from disk carries a `file://` URI; a skill built in memory
carries `None`, silently, so a check written against `_uri` would work in the shelf lane and hand
`None` to `Path()` in the checker lane — a `TypeError` three frames away from the cause. And `_uri` is
a private, underscore-prefixed field documented in the model as being for telemetry, so it can change
without a release note. The public answer is the one already in the code: pass the folder as an
argument.

**Two lanes that drift.** The checker lane grows to thirty cases, the shelf lane stays at two tests,
and one day somebody deletes the shelf lane because "the checks are already tested". The suite is
still green, still fast, and no longer looks at the filesystem at all — so a renamed reference file
passes. Naming the lanes in the module docstring, as
[3.1](../03-the-suite/3.1-enumerate-never-list.md) does, is what makes that deletion an obvious mistake
rather than a tidy-up.

## In production

**What a professional writes instead**, once the folder rules need firing tests too, is a small set of
**fixture folders** committed to the repository — a directory of deliberately broken skills that the
suite points `check_skill` at and asserts the expected findings for. Day 29 already established where
those live and why: `tests/fixtures/skills/`, quarantined so nothing under `sutra/` can load them
([Day 29, 3.2](../../../day-29-sourcing-and-auditing-skills/parts/03-the-poisoned-skill/3.2-the-poisoned-skill-and-the-audit.md)).
That is the road after the car park, and it is deliberately not built today: three folder rules and a
clean shelf do not yet justify a fixture tree, and a fixture tree nobody needs rots faster than the
code it tests.

**What degrades at scale** is the honesty of the in-memory lane. As the suite grows, the pressure is
always toward memory, because those tests are faster and easier to write. A team that follows that
pressure ends up with four hundred fast tests and no evidence about the filesystem, and finds out on
the day a deploy ships a skill folder missing its references — the packaging step dropped them, and
nothing in a suite made of dictionaries could have known.

**The review comment a senior engineer leaves:** *"this test builds the resources dictionary and then
checks the body against the resources dictionary. Both sides come from the same three lines, so it
passes whatever the check does. If the rule is about files on disk, the test needs files on disk."*

**The interview question:** *"you test mostly with in-memory objects. What are you not covering?"* The
honest spoken answer: *"Anything about the filesystem. Our model holds frontmatter, instructions and
resources and does not hold a path, so the rules about the folder — the name matching the directory
name, a reference path resolving to a real file, a content digest over the folder — simply cannot be
exercised in memory. Worse, they can be *faked*: resources in memory is a dictionary you write
yourself, so a test comparing the body against that dictionary compares two things the test author
chose and passes forever. So we keep a small lane that reads the real shelf, and the signature is the
tell — a check that takes a folder as a parameter is a check that needs the disk. When the folder
rules need firing tests, they get committed fixture folders, not more dictionaries."*

## Check yourself

```bash
uv run python -m pytest tests/test_skills.py -k shelf
mv skills/ticket-triage skills/triage
uv run python -m pytest tests/test_skills.py -k shelf
mv skills/triage skills/ticket-triage
```

The middle run fails with a `will-not-load` finding naming the mismatch. That failure is evidence no
in-memory test could have produced, and it took a `mv` to get it — which is the argument for the shelf
lane in one command.
