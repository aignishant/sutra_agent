# 4.1 — One valid skill, one changed field

## One-line answer

The checker lane needs a skill that is valid in every way except the one being tested, so the suite
gets a single builder — `a_skill(...)` — that returns a good `Skill` in memory and lets a test change
exactly one field, which makes every failure attributable to that field and nothing else.

## The story

You fill the bank form in pencil on a photocopy before you touch the real one.

The photocopy is not precious. If you get a box wrong you take another copy and start again, and
nobody at the counter ever sees it. Then, when your brother needs the same form for the same joint
account, you do not start from a blank page — you copy the one you already got right and change the
one box that differs, the account number, and leave the other twenty-two boxes alone.

That habit is doing something specific. It means that if the second form is rejected, you know it is
about the account number, because the account number is the only thing that changed. Start both forms
from blank and a rejection could be any of twenty-three boxes, and you are back to guessing.

## The idea in plain language

[Day 26, 1.3](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.3-building-a-skill-in-code.md)
showed that a `Skill` does not need a folder: `Skill(frontmatter=Frontmatter(...), instructions=...,
resources=...)` builds the same object the loader builds, and it said this would be Day 30's main use.
This is that use, and it adds the piece Day 26 did not need: a **builder with defaults**.

A test in the checker lane wants to say *"a skill exactly like a good one, except the version is a
float"*. Writing the whole constructor out in each test buys you two problems. It is four lines of
noise around the one line that matters, and — worse — each test now sets every field itself, so two
tests can drift apart and a failure stops being attributable. If `test_check_version` uses a
description that happens to lack a *when* clause, and one day you change what `check_version` returns,
you will spend an hour finding out that the fixture was always slightly wrong.

So the suite defines one function that returns a **valid** skill, with every field good, and takes
keyword arguments for the fields a test wants to move. Everything a test does not mention is known to
be fine. That is the photocopy: one form that is right, copied, with one box changed.

Two words to be exact about, because they are used loosely everywhere:

- A **fixture** is any prepared input a test runs against. In `pytest` it often means the decorated
  `@pytest.fixture` kind ([Day 23, 2.3](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.3-fixtures.md)),
  but a plain function that returns a value is a fixture too, and is simpler when there is no setup or
  teardown to manage.
- A **factory** is a fixture that takes arguments, so each test gets a variant rather than the same
  object. `a_skill()` is a factory, and the reason it is a plain function rather than a `pytest`
  fixture is that a fixture returning a function is more machinery than the job needs.

## Why Sutra needs it

Because [3.3](../03-the-suite/3.3-the-test-for-the-checker.md) demands a firing test for every rule,
and every one of those tests needs a skill that is broken in exactly one way.

There is a second reason, and it is why this is `Skill` in memory and not a folder in `tmp_path`.
Writing a broken skill to a temporary directory works and costs you: a file write and a read on every
case, a directory to lay out, and an object that is only reachable through the loader — which means a
case the loader **rejects**, like a name with two hyphens, cannot be built at all. In memory,
`Frontmatter(name="Bad--Name", …)` raises where you can catch it, which is exactly what
[4.2](4.2-the-model-is-the-spec.md) needs. What the in-memory route genuinely cannot do is
[4.3](4.3-what-memory-cannot-test.md)'s subject, and Sutra keeps the shelf lane on disk for precisely
that reason.

## The mechanism

One function, at the top of `tests/test_skills.py`, under the imports:

```python
def a_skill(
    description: str = "Do the thing. Use when the thing needs doing.",
    **metadata: object,
) -> Skill:
    """A valid skill built in memory - no folder, no file, no I/O."""
    return Skill(
        frontmatter=Frontmatter(name="probe", description=description, metadata=dict(metadata)),
        instructions="1. Do the thing.\n",
        resources=Resources(),
    )
```

**Line by line:**

- `Skill`, `Frontmatter` and `Resources` come from `google.adk.skills`, which re-exports all three from
  `models.py`. Verified against `https://adk.dev/skills/` and against the installed
  `google-adk==2.7.1`'s `google/adk/skills/__init__.py` on 2026-09-04, where all three appear in
  `__all__`.
- The default `description` deliberately contains *"Use when"*, so a skill built with no arguments
  passes `check_description`. Every default in this function is a **valid** value; that is the whole
  contract, and a default that quietly broke a rule would make every test that does not mention it
  lie.
- `**metadata: object` collects any other keyword as a metadata entry, so `a_skill(version="1.1")`
  becomes `metadata={"version": "1.1"}`. The annotation is `object` rather than `str` because the tests
  deliberately pass a float to reproduce the unquoted-YAML trap
  ([5.1](../05-versioning/5.1-a-name-for-the-text-that-ran.md)), and annotating it `str` would be a
  claim the tests contradict.
- `metadata=dict(metadata)` makes a fresh dictionary per call. Passing the collected kwargs mapping
  straight through would be fine here because `**kwargs` is already a new dict each call, but writing
  `dict(...)` states the intent and survives someone later changing the signature to take a
  `metadata` parameter directly, where a shared mutable default would be a real bug.
- `metadata` is a free-form mapping on `Frontmatter`, with only two keys the framework itself reads —
  `adk_additional_tools` and `adk_inject_state`
  ([Day 26, 1.2](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.2-the-skill-object.md)).
  Everything else, including `version`, is yours. That is what makes a house rule about `version`
  possible at all.
- `instructions="1. Do the thing.\n"` is a body with no resource paths in it, so `check_references`
  finds nothing to look up. A default body mentioning `references/x.md` would make every test that
  never thinks about references depend on a file that does not exist.
- `Resources()` with no arguments is an empty resources object — no references, no scripts, no assets.
  The default has to be *something*, because `Skill` requires the field; empty is the value that
  cannot surprise a test.
- The name is `probe`, not `ticket-triage`. Using a real skill's name in a synthetic fixture is how a
  finding in a test report ends up being blamed on a real skill; `probe` appears nowhere on disk and is
  obviously synthetic in any output.

Using it is the payoff — the whole broken case is one keyword:

```python
def test_check_description_wants_a_when() -> None:
    broken = a_skill(description="Handles ticket triage.")
    assert [f.rule for f in check_description(broken)] == ["no-when"]
```

**Line by line:**

- One argument moves, and the reader can see at a glance what is being tested. The version, the body,
  the resources and the name are all known-good, so the finding can only be about the description.
- The variable is named `broken` rather than `skill`. A reader skimming the file sees which side of the
  test each object is on without reading the assertion.
- Compare this to the version with a `tmp_path` folder: a `mkdir`, a `write_text` with an embedded
  frontmatter string, a `load_skill_from_dir`, and then the assertion. Four times the code for the
  same claim, and three of the four lines are about the filesystem rather than about the rule.

## When it breaks

**A default that is not valid.** Somebody sets the default description to `"A test skill."` because it
is shorter. Now `test_check_version_names_the_rule_it_broke` still passes — it only looks at
`check_version` — but the day anybody writes a test that calls `check_skill(...)` on the factory's
output, they get a finding they did not ask for and spend a while assuming their new rule is wrong.
The rule for a factory is absolute: **the zero-argument call must be clean under every check in the
module.**

**Building a case the model refuses.** You try to build a broken name the same way:

```text
E   pydantic_core._pydantic_core.ValidationError: 1 validation error for Frontmatter
E   name
E     Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading,
E     trailing, or consecutive delimiters [type=value_error, input_value='Bad--Name', input_type=str]
```

That is not a bug in the factory. It is `Frontmatter` refusing to hold an invalid name at all, and it
is the subject of [4.2](4.2-the-model-is-the-spec.md) — a case you cannot construct is a case you
assert on with `pytest.raises` instead.

**A shared mutable default.** The classic Python trap, one edit away: change the signature to
`def a_skill(metadata: dict = {})` and every call now shares one dictionary, so a test that adds a key
changes the fixture for every test that runs after it, and the suite starts depending on order. The
`**metadata` form avoids it structurally, which is a better defence than remembering.

## In production

**What a professional writes instead** at scale is the same builder, moved to `tests/conftest.py` so
several test modules share it, and often returning a *set* of related objects rather than one. The
shape does not change: defaults that are all valid, keywords for the one thing under test, no
filesystem. The move to `conftest.py` happens the second time a test module needs it, not the first —
a helper with one caller belongs beside its caller.

**What degrades at scale** is the honesty of the defaults. A factory written when there were three
rules keeps its defaults while rules five, six and seven are added, and one day the zero-argument call
quietly violates rule seven. Nothing announces this, because most tests only call one check. The cheap
guard is one test that runs every `Skill`-taking check over `a_skill(version="1.0")` and asserts the
result is empty — the factory
checking itself, which is [3.3](../03-the-suite/3.3-the-test-for-the-checker.md)'s smoke-alarm button
pointed at the fixture instead of at the rule.

**The review comment a senior engineer leaves:** *"three tests each construct their own `Skill` with
slightly different descriptions. That means a failure in any of them could be about the field under
test or about the fixture, and eventually will be. One builder, valid defaults, one keyword per
test."*

**The interview question:** *"how do you build test data for a validation suite?"* The honest spoken
answer: *"One factory that returns a fully valid object, with every default known to pass every rule,
and keyword arguments for the single field a test wants to break. Then any failure is attributable to
that field, which is the property you actually want — if each test constructs its own object from
scratch, they drift and you lose it. For agent skills we build the framework's `Skill` model directly
rather than writing folders to a temporary directory: it is faster, there is no I/O, and the test
reads as one line about the rule instead of four about the filesystem. The cases we cannot build that
way are the ones the model itself rejects, and those get a `pytest.raises` instead — which is arguably
a better test, because it proves the framework is enforcing the rule for us."*

skill = Skill(
