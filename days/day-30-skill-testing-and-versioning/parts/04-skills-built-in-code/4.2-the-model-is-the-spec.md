# 4.2 — The model is the spec

## One-line answer

`Frontmatter` refuses to hold an invalid name or an empty description at construction time, so the
specification's rules are testable as `pytest.raises` cases against the model itself — and a rule you
cannot even build an object to break is a rule you do not need to re-implement.

## The story

The turnstile at the station does not ask you whether your ticket is valid.

There is no conversation. You put the ticket in, and either the barrier turns or it does not, and if it
does not, nothing you say to it changes anything. That is not rudeness — it is the design. The rule
about who may pass has been moved out of a person's judgement and into a machine that has only one
behaviour.

Compare it with the gate at a smaller station, where a member of staff glances at your ticket and waves
you through. The rule is the same rule, written in the same conditions of carriage. But now the rule
lives in somebody's head, and one morning a different person is on the gate and interprets it slightly
differently, and neither of them is doing anything wrong.

The turnstile's real property is not strictness. It is that there is exactly one implementation of the
rule and nobody can hold a different opinion about it.

## The idea in plain language

`Frontmatter` is a **pydantic model** — a class that validates its fields when you build it. If a
value breaks a rule, the constructor raises rather than producing an object holding a bad value. There
is no valid `Frontmatter` with an empty description anywhere in memory, at any point, ever.

Reading the installed `google-adk==2.7.1` on 2026-09-04, `Frontmatter` enforces four things at
construction, each with a message you could paste into a bug report:

| Field | Rule | The message |
| --- | --- | --- |
| `name` | at most 64 characters | `name must be at most 64 characters` |
| `name` | lowercase kebab-case, no leading, trailing or consecutive hyphens | `name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading, trailing, or consecutive delimiters` |
| `description` | not empty | `description must not be empty` |
| `description` | at most 1024 characters | `description must be at most 1024 characters. Description length: 1025` |

Every one of those is a line from `https://agentskills.io/specification`, read the same day. The
specification says a name is 1–64 characters of lowercase letters, digits and single inner hyphens,
and a description is 1–1024 characters and non-empty. The model is that paragraph, executable.

So the question *"does our system enforce the spec's name rule?"* has an answer you can run. Not *"we
wrote a regular expression that we believe matches"* —
[2.2](../02-checks-as-functions/2.2-let-the-loader-be-the-oracle.md) already argued against that — but
*"here is a test that tries to build an invalid one and proves it cannot exist"*.

One property is worth knowing because it surprises people, and it is a real gap rather than a
strictness you can rely on. `Frontmatter` is declared with `extra="allow"`, so an **unknown key is
kept, not rejected**. Write `licence: MIT` instead of `license: MIT` and the model accepts it
happily, storing it as an extra field that nothing will ever read. The turnstile checks the ticket it
was told about and is indifferent to a second ticket you posted through the slot.

## Why Sutra needs it

Because SK-18 is the in-code skill path, and this is what the in-code path is *for* in a test suite:
proving the framework enforces what you think it enforces, on the day you write the check that depends
on it.

[1.3](../01-testing-prose/1.3-the-rules-worth-a-test.md)'s third filter said not to re-implement a
rule something already catches. That filter is a promise about the framework, and a promise nobody
verifies is a guess. Three of Sutra's six rules rest on `Frontmatter` and `load_skill_from_dir` behaving
a certain way, and the cost of writing that down as a test is four lines.

The day it pays is an upgrade. `google-adk` moves to 2.8, `uv sync` runs, and if a validator was
relaxed — or the snake-case feature flag the model already carries becomes the default — this test
goes red and tells you before a skill with an unexpected name reaches the shelf. Nothing else in the
suite would notice, because your own checks never touched the name.

## The mechanism

```python
def test_the_frontmatter_model_is_the_spec() -> None:
    with pytest.raises(ValidationError, match="lowercase kebab-case"):
        Frontmatter(name="Bad--Name", description="x")
    with pytest.raises(ValidationError, match="must not be empty"):
        Frontmatter(name="ok-name", description="")
```

**Line by line:**

- `pytest.raises(...)` as a context manager asserts that the block raises. If `Frontmatter` ever
  *accepts* one of these, the test fails with `DID NOT RAISE`, which is precisely the upgrade signal
  this test exists to give.
- `ValidationError` is imported from `pydantic`. It is worth knowing that it inherits from `ValueError`
  — verified on the installed pydantic on 2026-09-04 — which is what lets
  [2.2](../02-checks-as-functions/2.2-let-the-loader-be-the-oracle.md)'s catch clause be short. Here
  the specific class is used because the test is about *this* validator, not about any value error.
- `match="lowercase kebab-case"` is a regular expression searched against the exception's string form.
  It is the difference between *"something rejected it"* and *"the name rule rejected it"*. Without
  `match`, a typo in the description argument would also make the test pass, for the wrong reason.
- The matched fragment is short and taken from the middle of the message. Matching the whole message
  would break on the next release that rewords it, which would be a false alarm about wording rather
  than a real signal about behaviour; matching one distinctive phrase is the balance.
- `"Bad--Name"` breaks two rules at once — uppercase and consecutive hyphens — deliberately, because it
  is the same string used as a broken folder name in
  [2.3](../02-checks-as-functions/2.3-one-bad-folder-must-not-stop-the-shelf.md), and one memorable
  bad value used everywhere is easier to recognise in output than three forgettable ones.
- `description="x"` in the first case is a valid description doing nothing but keeping the constructor
  happy, so the only thing under test is the name. Same discipline as
  [4.1](4.1-a-skill-without-a-folder.md): change one field.
- Both assertions live in one test because they are one claim — *the model enforces the spec's two
  required fields*. Splitting them into two tests would be defensible; keeping them together makes the
  test read as the row of a table, and the name says what the table is.

You can see the same rules from the other side, without `pytest`:

```bash
uv run python -c "
from google.adk.skills import Frontmatter
from pydantic import ValidationError
for name in ['ticket-triage', 'Ticket-Triage', 'ticket--triage', '-triage', 'a' * 65]:
    try:
        Frontmatter(name=name, description='x')
        print(f'{name[:20]:<22} accepted')
    except ValidationError as exc:
        print(f'{name[:20]:<22} rejected: {str(exc).splitlines()[2].strip()[:60]}')
"
```

**Line by line:**

- The list walks one good name and four bad ones, each breaking a different clause of the same rule:
  uppercase, consecutive hyphens, a leading hyphen, and 65 characters.
- `name[:20]` truncates the display so the 65-character case does not wreck the column alignment. The
  value passed to `Frontmatter` is the full string; only the printout is trimmed.
- `str(exc).splitlines()[2]` is the third line of a pydantic error, which is where the human-readable
  `Value error, …` sentence lives. Line 0 is the count, line 1 is the field name. This is fine in a
  throwaway probe and is exactly what the module-level `load` avoids by flattening the whole message
  instead ([2.2](../02-checks-as-functions/2.2-let-the-loader-be-the-oracle.md)) — indexing into
  somebody else's error format is a thing you do at a prompt, not in code you keep.

## When it breaks

**The test that passes for the wrong reason.** Drop the `match` argument and misspell the keyword:

```python
with pytest.raises(ValidationError):
    Frontmatter(nmae="Bad--Name", description="x")
```

This passes. `nmae` is an extra field, so `name` is missing, so the model raises `Field required` — a
validation error, just not the one the test claims to be about. `match` is what closes that hole, and
it is the reason every `pytest.raises` in this repository carries one.

**The extra key that is silently kept.** Try to prove the model rejects a typo and watch it not:

```text
{'name': 'ok-name', 'description': 'd', 'license': None, 'compatibility': None, 'allowed_tools': None, 'metadata': {}, 'wat': 1}
```

That is `Frontmatter.model_validate({"name": "ok-name", "description": "d", "wat": 1}).model_dump()`,
run on 2026-09-04. `wat` is there, held, ignored. So a skill with `licence:` instead of `license:`
loads perfectly and has no licence as far as anything that reads the field is concerned — which is a
real problem for Day 29's provenance rules
([Day 29, 4.1](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.1-no-row-no-run.md)),
and a good candidate for a seventh house rule.

**A `match` that is too specific.** `match="name must be lowercase kebab-case \\(a-z, 0-9, hyphens\\), with no leading, trailing, or consecutive delimiters"`
passes today and fails on the release that adds a comma. The failure looks like a behaviour change and
is a wording change, and after the second one somebody deletes the assertion. Match a phrase, not a
paragraph.

## In production

**What a professional writes instead** of a broad suite over somebody else's library is a short one
over exactly the guarantees their own code depends on. There is no value in testing pydantic; there is
real value in a test that says *"we rely on `Frontmatter` rejecting these two things, and here is the
proof for the version we have pinned"*. The distinction is whose promise is under test: not the
library's correctness, but your assumption about it.

**What degrades at scale** is that this test is invisible until it saves you, and invisible tests get
deleted during a tidy-up. The defence is the name and the docstring: a test called
`test_the_frontmatter_model_is_the_spec` with one line saying *"three of our lint rules assume this;
if it goes red after an upgrade, read the changelog before touching anything"* survives a cleanup that
a test called `test_frontmatter_validation` does not.

**The review comment a senior engineer leaves:** *"we are one library upgrade away from this
assumption changing silently, and three of our checks are built on it. Keep the test, add the `match`,
and say in the docstring what depends on it — otherwise the next person deletes it as a test of
somebody else's code."*

**The interview question:** *"do you write tests against your dependencies?"* The honest spoken answer:
*"Not against their correctness — that is their job. But yes against the specific guarantees my code
leans on. We skip re-implementing three spec rules because the framework's frontmatter model enforces
them at construction, and that decision is only sound if the model really does. So there is a short
test that tries to build an invalid name and an empty description and asserts each raises, matching on
a phrase from the message rather than the whole sentence so a reword is not a false alarm. It costs
four lines and it turns a library upgrade from a silent behaviour change into a red test. The gap we
document rather than test is that the model allows extra keys, so a misspelled field name is kept and
ignored."*
