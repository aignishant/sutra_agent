# 2.3 — Criterion 3: every rubric line is exercised both ways

## One-line answer

A rubric line that every conversation in the set is supposed to earn cannot tell a judge that read it
from a judge that answers yes to everything — so before spending a single request on grading, check
the labels a person already wrote and require at least one yes and one no on every line.

## The story

The mango sorter's frame.

A wooden board with holes in it sits over three crates. Fruit goes on, gets pushed along, and drops
through the first hole it fits: small, medium, large. The man who made the board drilled the holes by
eye, from one basket of fruit he had that morning.

Come the main season, everything falls through the first hole. Not because the fruit is small —
because the holes were sized against a basket that happened to hold nothing big. The frame is
working perfectly. It has been sorting all day. Every crate but the first one is empty, and nobody
has looked in the crates.

The frame can only tell you apart what it has been given something to tell apart.

## The idea in plain language

A **rubric** is a list of yes-or-no claims about a conversation. Day 80 built four of them for the
refund desk, and Day 80 part 3.2 found the failure that matters: a line written vaguely — *"the agent
behaved safely"* — gets a `yes` on everything, so it produces a number and separates nothing.

That was a finding about how a line is *written*. This criterion is about a different half of the
same problem, and it is checkable without any judge at all: a rubric line only discriminates if the
**case set** contains a conversation that is supposed to fail it.

Here is the check, in one sentence. For each rubric line, look at the labels a person wrote down for
each conversation before any grading happened. If the line is `yes` everywhere, then a judge that
reads the conversation carefully and a judge that answers `yes` reflexively produce identical scores,
and the suite has no way to tell them apart. The line is in the rubric and it is not being tested.

Three things make this worth doing before the expensive check rather than after:

- It costs nothing. It reads a dictionary.
- It is a property of the **set**, not of the judge, so no amount of judge improvement fixes it.
- The remedy is a new case, which is the slowest thing to produce, so finding out early matters.

The labels this reads are the ones Day 80 calls the reference: what a person said about each
conversation, line by line, written before any model saw it.

## Why Sutra needs it

Because Day 81 part 3.3 measured the consequence in the other instrument. A coin-flip judge agreed
with the human labels 83.3% of the time because 83.3% was the base rate of the label set — a set that
was one-sided. The same shape, one level up: when the answer is nearly always the same, agreeing is
free.

And because this criterion is the cheap guard on the expensive one. Part
[2.4](2.4-criterion-4-the-rubric-can-see.md) and part
[3.1](../03-judge-and-bill/3.1-criterion-5-the-judge-beats-baseline.md) are both about whether the
judge is doing anything. If a line is one-sided, neither of those checks can produce a meaningful
answer about it however carefully they are run.

## The mechanism

The whole check is a counter over the reference labels:

```python
    for rubric in RUBRICS:
        counts = Counter(case[rubric.rubric_id] for case in labels.values())
        both = counts["yes"] > 0 and counts["no"] > 0
        blind += [] if both else [rubric.rubric_id]
```

**Line by line:**

- `labels` is `HUMAN` from `_phase.py`: conversation name → rubric id → `"yes"` or `"no"`, written by
  a person. Nothing in this loop touches a model, a prompt or a score.
- `Counter` over one rubric id across every conversation. The unit is the **line**, not the case —
  a set can be perfectly balanced overall and still have one line that nothing fails.
- `counts["yes"] > 0 and counts["no"] > 0` is the whole test. Not a ratio, not a balance threshold:
  at least one of each. A stricter rule would be arguing about how balanced is balanced, and one of
  each is the difference between a line that can discriminate and one that provably cannot.
- `counts["no"]` on a `Counter` that never saw `"no"` returns `0` rather than raising, which is why
  this is a `Counter` and not a `dict`.
- `blind` collects ids rather than a count, because the report has to name the lines. "One line is
  one-sided" sends nobody to the right place.

Run it:

```bash

```

**Line by line:**

- No flag: all three of Day 80's conversations.

Measured on 2026-09-06:

```text
rubric: 4 lines, graded over 3 conversations
cases: by_the_book, refunded_first, read_everything

  rubric line               yes   no  exercised
  escalated_before_write      2    1  both ways
  checked_the_limit           2    1  both ways
  one_ticket_only             2    1  both ways
  told_the_customer           1    2  both ways

  4 of 4 lines are exercised both ways
  every line has a conversation that earns it and one that does not
exit: 0
```

Four lines, three conversations, and every line has at least one of each. Notice how thin the margin
is: three of the four lines are `2 yes, 1 no`, which is **one conversation** away from being
one-sided. Delete `refunded_first` from the set — the conversation where the desk refunded before
asking — and `escalated_before_write` and `checked_the_limit` both stop discriminating at once,
because it is the only conversation in the set that fails either of them.

That is not hypothetical, because a harsher version of it is the fault the red-alarm test injects.

## When it breaks

```bash
uv run python c3_separates.py --one-sided; echo "exit: $?"
```

Measured on 2026-09-06:

```text
rubric: 4 lines, graded over 1 conversation
cases: by_the_book

  rubric line               yes   no  exercised
  escalated_before_write      1    0  ONE WAY ONLY
  checked_the_limit           1    0  ONE WAY ONLY
  one_ticket_only             1    0  ONE WAY ONLY
  told_the_customer           1    0  ONE WAY ONLY

  0 of 4 lines are exercised both ways
    - escalated_before_write: no conversation in the set is supposed to fail it
    - checked_the_limit: no conversation in the set is supposed to fail it
    - one_ticket_only: no conversation in the set is supposed to fail it
    - told_the_customer: no conversation in the set is supposed to fail it

  a judge that answered yes to those lines would score the same as a judge
  that read them, so the suite cannot tell the two apart
exit: 1
```

`--one-sided` keeps only the conversation where the desk did everything right, which is exactly what a
case set looks like when the cases were written by recording the system working. That is the normal
way a suite is built — Day 79 part 2.2 is about recording a session rather than writing one — and it
produces a set where every rubric line is `yes` everywhere.

The failure has no error text. It is a rubric with four lines, a judge that grades all four, and a
score of 4/4 that would have been 4/4 for any judge at all.

**What this criterion cannot see.** It reads human labels, so it inherits whatever is wrong with
them. If the labels were produced by the judge — a shortcut somebody takes when labelling is slow —
then every line is exercised both ways by construction and the criterion passes while proving
nothing. Nothing in this repository enforces that separation, and part
[1.1](../01-reading-the-gate/1.1-a-gate-on-the-instruments.md)'s **In production** section names it
as the way a calibration suite stops being one.

## In production

**What a professional does.** Treats coverage of the *rubric* as a first-class property of the case
set, alongside coverage of the code. The report that goes with a rubric-based suite is not just the
scores; it is a matrix of line against case, with the empty column highlighted, because an empty
column is a claim being made about the system that nothing is testing.

**What degrades at scale.** Rubrics grow faster than case sets. A new safety requirement is one line
of text and the case that fails it is an afternoon of writing, so the natural drift is towards a long
rubric over a short set — which is exactly the direction that produces one-sided lines. At forty
lines and twelve cases, a majority of the rubric is untested and the summary score still looks like a
percentage of forty.

**The failure that only shows with real traffic.** A line that used to be exercised and is not any
more. Cases get deleted, quarantined (Day 82 part 4.2) or fixed, and fixing the desk so a case now
passes a line it used to fail removes the only `no` for that line. The suite gets *more* green and
*less* discriminating in the same commit, and this criterion is the only thing in the gate that would
notice.

**The review comment a senior engineer leaves:** *"Three of these four lines are one case away from
being untestable. Before we add a fifth rubric line, write the conversation that fails the four we
have — twice each."*

**The interview question:** *"How do you know your rubric is doing anything?"* The answer that shows
experience starts with the case set rather than with the judge: name a line, then name the case that
is supposed to fail it. If the second half of that sentence does not exist, no judge can rescue the
first.
