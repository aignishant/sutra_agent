# 2.2 — Criterion 2: the suite goes red against a stub desk

## One-line answer

Point the suite at a desk that calls no tools and returns an empty string; if it refuses all three
cases, the metrics can produce a failure, and if it does not, every green run the suite has ever
produced means nothing.

## The story

The torch tested before you go down to the basement.

The power has gone and there is a torch on the shelf by the door. You press the switch in the
hallway, where there is still some light from the window, and a weak circle appears on the wall.
Then you go down.

Pressing the switch upstairs is not about lighting the hallway, which you can already see. It is
about finding out, while it is still cheap to find out, whether the thing you are about to depend on
does anything at all. Nobody discovers a dead torch usefully at the bottom of the stairs.

## The idea in plain language

A **stub** is a deliberately empty implementation: something with the right shape and no behaviour.
The stub desk in this criterion is one turn long, calls no tools, and answers with an empty string.

Running the suite against it answers a question the suite cannot answer about itself: *is a failing
score reachable?* A metric that is broken — wrong field, wrong comparison, an exception swallowed
somewhere — usually fails in the direction of agreement, because agreement is what an empty
comparison produces. Two empty lists match. An empty set of assertions is satisfied. So a broken
metric looks exactly like a well-behaved desk.

The stub is the known-bad input. If the metric refuses it, the metric can refuse. If it does not, the
metric cannot say no about anything, and the green results in the ledger were stamp impressions.

This is a check on **the two free metrics only**:

| Metric | What it compares | From |
| --- | --- | --- |
| `tool_trajectory_avg_score` | the list of tool names called against the list recorded | day 79 part 3.1 |
| `response_match_score` | ROUGE-1 over the words of the answer against the words recorded | day 79 part 3.3 |

The judged metrics are not in this criterion, because running them costs requests and because they
have their own check — part [3.1](../03-judge-and-bill/3.1-criterion-5-the-judge-beats-baseline.md)
is the equivalent test for a judge, and it is a baseline rather than a stub.

## Why Sutra needs it

Because the phase's own history says so. Day 79 part 2.3 found a case that passed whatever the desk
said, by hand, by reading the evalset. That finding is exactly this criterion, discovered once and
never made repeatable — and a finding that is not a check is a thing you have to be lucky enough to
notice again.

And because this is the cheapest possible protection against the worst possible outcome. Every claim
this repository makes after Phase 12 depends on these two metrics being able to say no. The check
costs three comparisons and no requests, and it runs in the time it takes to import ADK.

## The mechanism

The stub is one line in `_phase.py`:

```python
STUB = (("I want a refund on 4688.", (), ""),)
```

**Line by line:**

- A one-turn conversation: the question, an empty tuple of tool calls, an empty answer. It is the
  smallest thing that is still a valid `Invocation`.
- The question is kept identical to the real cases' first turn, so the only difference between the
  stub and a real desk is what the desk did. If the question differed too, a failure would not be
  attributable.
- Empty string rather than `None`. `None` would be a different test — it would find out what the
  metric does with a missing answer, which is a real question and not this one.

Both metrics are the real ADK evaluators, constructed the way the suite constructs them:

```python
    trajectory = TrajectoryEvaluator(threshold=trajectory_threshold)
    response = RougeEvaluator(
        EvalMetric(metric_name="response_match_score", threshold=response_threshold)
    )
```

**Line by line:**

- Two different constructor shapes for two evaluators in the same library. `TrajectoryEvaluator`
  takes a bare `threshold`; `RougeEvaluator` takes a whole `EvalMetric`. That is not a mistake in the
  lab — it is what `google-adk==2.7.1` exposes, and Day 79 part 3.3 is where it was first met.
- `metric_name="response_match_score"` is the name ADK's config uses, and it is the name that has to
  appear in `test_config.json` for the metric to be selected. Getting it wrong there produces a suite
  that runs one metric instead of two, silently.

And each case is evaluated with the stub as the *actual* and the recorded conversation as the
*expected*:

```python
        t = trajectory.evaluate_invocations(actual_invocations=stub, expected_invocations=wanted)
```

**Line by line:**

- Keyword arguments, not positional. The two lists have the same type, and swapping them produces a
  run that scores the recorded answer against the stub — which for ROUGE is a different number,
  because recall and precision are not symmetric.
- `wanted` is one turn, and so is `stub`. ADK's evaluators zip the two lists, so comparing a
  three-turn expectation against a one-turn actual raises rather than scoring partial credit.

Run it:

```bash
cd days/day-83-eval-suite-green/lab
uv run python c2_stub.py; echo "exit: $?"
```

**Line by line:**

- No flag: the criterion's real arm, at ADK's default thresholds.

Measured on 2026-09-06:

```text
the desk under test: calls no tools, answers with an empty string
thresholds: tool_trajectory_avg_score 1.0, response_match_score 0.8

  case                trajectory  response  status
  by_the_book               0.00      0.00  FAILED
  refunded_first            0.00      0.00  FAILED
  read_everything           0.00      0.00  FAILED

  the stub desk passed 0 of 3 cases
  the suite refused a desk that does nothing, so it can go red
exit: 0
```

**Zero of three.** Both metrics score `0.00` and both refuse. The suite can go red, which is all this
criterion claims and is more than the suite could claim about itself yesterday.

## When it breaks

The criterion breaks when the thresholds move, and part
[1.3](../01-reading-the-gate/1.3-green-is-not-evidence.md) measured that arm in full: at `0.0` the
same three cases with the same `0.00` scores come back `PASSED`, and the criterion exits 1 to say so.

The subtler break is the one worth naming here, because it is the criterion's real limitation. A stub
that fails is not evidence that a *nearly right* desk fails, and the near-misses behave differently
from the stub in a way the criterion cannot see. Three of them against `by_the_book`, measured on
2026-09-06:

```text
extra tool     trajectory 0.00 FAILED  response 1.00 PASSED
paraphrase     trajectory 1.00 PASSED  response 0.61 FAILED
wrong ticket   trajectory 0.00 FAILED  response 1.00 PASSED
```

Every one of them is refused, so the suite is doing its job — and **each is refused by exactly one of
the two metrics, and the other one gives it full marks.** The desk that called an extra tool wrote a
word-perfect answer. The desk that took exactly the right path was refused for paraphrasing, at 0.61
against a threshold of 0.8, which is Day 79 part 3.3's finding arriving as a false alarm on a good
answer.

The stub check cannot distinguish any of that, because against the stub both metrics score `0.00` and
agree. A stub establishes that the floor is reachable. It says nothing about the shape of the suite
between the floor and the ceiling, and a check whose only fixture is nothing-at-all is a heartbeat.

There is no error text for that. It is a `PASSED` in one column next to a `FAILED` in the other, and
nothing in the suite reports that the two metrics disagreed.

## In production

**What a professional does.** Keeps a permanent known-bad fixture in the suite and asserts that it
fails — usually called a *canary* or a *negative control*, and in mutation-testing terms it is the
cheapest possible mutant. The important discipline is that it lives with the tests and runs on every
commit, so that a change which breaks the metric is caught by the same run that made it, rather than
six weeks later.

**What degrades at scale.** One stub against three cases is three comparisons. One stub against four
hundred is four hundred, still free, still instant, and now producing four hundred lines of `FAILED`
that nobody reads. The output has to collapse to a count with the exceptions named, and the
exceptions — cases the stub *passed* — are the entire report.

**The failure that only shows with real traffic.** A metric that degrades rather than breaks.
ROUGE-1 against an empty string is 0.00 and obvious; ROUGE-1 against a plausible paraphrase is 0.62,
and a suite whose threshold has drifted to 0.5 is now accepting paraphrases while still refusing the
stub. The canary is green and the suite has stopped discriminating. The mitigation is a second
fixture — a *nearly right* desk that must also fail — and this repository does not have one.

**The review comment a senior engineer leaves:** *"Good, keep it. Now add the near-misses as
permanent fixtures with their expected verdicts, because the interesting number is not that they
fail — it is which metric fails them, and right now the two disagree on every one and we do not
report it."*

**The interview question:** *"How do you test a test?"* The answer that shows experience gives it a
known-bad input and requires a failure, then immediately concedes the limit — that a passing canary
proves the floor is reachable and nothing about the cases in between.
