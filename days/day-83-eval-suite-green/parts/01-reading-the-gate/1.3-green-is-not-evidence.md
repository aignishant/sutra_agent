# 1.3 — Green is not evidence

## One-line answer

A suite reports green in two situations that look identical from outside — it measured the desk and
the desk was fine, or it never measured anything — and this phase's suite is in the second one, twice
over: once because a threshold can be set where nothing fails, and once because the judged half has
never been run at all.

## The story

💥 **The stamp on the counter.**

🎬 **The scene.** A window at a government office. Forms go in on the left, come out on the right with
a purple `APPROVED` across the middle and a date. There is a queue, it moves, and everybody leaves
holding a stamped form.

😬 **The naive fix.** Somebody senior worries about quality and asks for a count. How many forms were
processed this week? Eleven hundred, and every one of them approved. Excellent — the process is
working.

💥 **Why it fails.** The clerk has not read a form in four years. The stamp comes down on whatever is
placed under it, including the one with the wrong address, the one with no signature and the one that
is a photocopy of a different form altogether. Eleven hundred approvals is a count of stamp
impressions. It is not a statement about eleven hundred applications, and no amount of counting
turns it into one.

💡 **The insight.** *Approved* means something only if there was a way to be refused. The number that
would have told the story is not how many were approved; it is **how many were sent back** — and it
is zero, and zero has been read as good news for four years.

## The idea in plain language

Green is a report. Like the stamp, it is produced by a process, and the interesting question is never
what the report says but what the process would have had to see to produce something else.

There are exactly two ways for a suite to be green while having measured nothing.

**The threshold is set where nothing fails.** The metric runs, produces real numbers, and every
number clears the bar because the bar is on the floor. This is the stamp: the machinery all works,
and refusal is not reachable.

**The run never happened.** The suite is green because nothing was red, and nothing was red because
nothing ran. This is subtler than it sounds and is where this repository actually is: six of Phase
12's eight checks cost nothing and run happily, the two that need a judge cost 270 requests, and the
nightly that would spend them has never been wired to a schedule. A dashboard reading "evals: green"
would be telling the truth about the six and saying nothing about the desk.

Both are measurable, and both are measured below. Neither produces an error. That is the family
resemblance with every other finding in this phase: the failure mode of a measuring system is a
confident number, not a traceback.

## Why Sutra needs it

Because Phase 12's gate sentence is the word *green*, and this part is why that word cannot be the
evidence. The eight criteria in part [1.1](1.1-a-gate-on-the-instruments.md) exist because green is
cheap and *"green, and here is the case that would have gone red"* is not.

And because the ledger row is about to be written. Principle 10 says errors surface rather than being
covered, and it applies to a phase gate as hard as it applies to a tool call: a `✅` in `PROGRESS.md`
for a phase whose suite has never run in full would be the stamp, applied by me, to my own work.

## The mechanism

**Green because the bar is on the floor.** The same three cases, the same stub desk that calls no
tools and returns an empty string, two thresholds:

```python
    trajectory_threshold = 0.0 if lenient else TRAJECTORY_THRESHOLD
    response_threshold = 0.0 if lenient else RESPONSE_THRESHOLD
```

**Line by line:**

- Two floats, and they are the only difference between a red suite and a green one. Nothing about the
  desk, the cases or the metrics is touched by the `--lenient` flag.
- `TRAJECTORY_THRESHOLD` is 1.0 and `RESPONSE_THRESHOLD` is 0.8, and both are ADK's own defaults from
  `google.adk.evaluation.eval_config` rather than numbers this repository chose. Day 79 part 3.4 is
  where they were read off.
- `0.0` is not an absurd value somebody would never type. It is what you get by writing a threshold
  into `test_config.json` and mistyping it, and it is what a team reaches for when a suite is noisy
  and somebody wants the build to go green today.

```bash
cd days/day-83-eval-suite-green/lab
uv run python c2_stub.py --lenient | tail -6
```

**Line by line:**

- `tail -6` for the status column and the verdict; the scores are in part
  [1.2](1.2-what-full-evalset-green-asks.md) and they do not change.

Measured on 2026-09-06:

```text
  read_everything           0.00      0.00  PASSED

  the stub desk passed 3 of 3 cases
  a suite that green-lights a desk which does nothing measures nothing
```

**A desk that calls nothing and says nothing, at 3 of 3.** The score printed next to `PASSED` is
`0.00`. Everything needed to catch this is on the same line as the mistake, and the `status` column
is still the one people read.

**Green because it never ran.** This one has no flag, because it is the state of the repository:

```bash
cd days/day-83-eval-suite-green/lab
uv run python c6_fits.py | tail -6; echo "exit: ${PIPESTATUS[0]}"
```

**Line by line:**

- `${PIPESTATUS[0]}` rather than `$?`, because `$?` after a pipe is `tail`'s exit code and `tail`
  always succeeds. The criterion's own code is the one that matters and it is the one the pipe hides.

Measured on 2026-09-06:

```text
  its daily allowance: unmeasured since day 78, five days ago
  the only allowance this repository has observed: 20/day,
  on gemini-2.5-flash, read off a live 429 on 2026-08-25

  270 requests against an unknown number is not a comparison
  this criterion cannot be determined, and saying so is the result
exit: 2
```

The two judged checks — `rubric_based_multi_turn_trajectory` and `final_response_match_v2` — have
never been executed against a live judge in this repository. Six of eight checks are free, run
instantly, and pass. A report that says "the eval suite is green" would be an accurate summary of
those six and would carry no information about the desk at all.

## When it breaks

The two ways compose, and the composite is what a team actually ends up with. It has a shape and this
repository has walked most of it:

```text
1. the judged half is expensive, so it goes on the nightly     (day 82, part 3.1)
2. the nightly is not wired up yet, so the judged half never runs
3. the free half runs on every commit and is green
4. the dashboard says "evals: green"
5. a case starts failing intermittently, so it is quarantined  (day 82, part 4.2)
6. a threshold is lowered to stop a noisy case failing
7. a year later the suite is green over cases nothing can fail
```

Seven steps, no error at any of them, every step defensible on the day it happened. There is no
traceback to quote for the same reason there is none in the story: nothing went wrong. A stamp came
down.

The only mechanism that interrupts that sequence is a check that has to *see something go red* — step
7 is caught by criterion 2, and step 2 is caught by criterion 6 refusing to say green about a run
that has not happened.

## In production

**What a professional does.** Reports the refusals, not the approvals. A suite's health is the number
of cases that have ever gone red, the date of the last red build, and the size of the quarantine —
and a suite that has never been red since it was written is reported as *unverified*, not as
*passing*. That inverts the dashboard everybody actually has, which is why it has to be a deliberate
decision.

**What degrades at scale.** The two failure modes get easier, not harder. More cases means more
noise, which means more pressure on thresholds; more expense means more of the suite moves to a
cadence that runs less often, which means more of it is green by not running. Both pressures point
the same way and neither announces itself.

**The failure that only shows with real traffic.** The threshold that was lowered for a good reason.
A flaky judged case is genuinely noisy, and lowering its threshold genuinely stops the false alarms —
and it also stops the true ones, and the person who lowered it has left. The mitigation is not a rule
against lowering thresholds; it is that every threshold carries a date and a reason in the file next
to it, so the diff is a decision rather than a number.

**The review comment a senior engineer leaves:** *"Your CI badge says green and your judged metrics
have never executed. Either wire up the nightly or make the badge say `6/8 checks`, because right now
it is making a claim we cannot support."*

**The interview question:** *"Your test suite is green. What does that tell you?"* The answer that
shows experience asks two questions back — when did it last go red, and what would it take to make it
go red now — because a suite that cannot answer either is a stamp.
