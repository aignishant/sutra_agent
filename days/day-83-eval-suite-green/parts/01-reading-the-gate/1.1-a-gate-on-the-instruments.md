# 1.1 — A gate on the instruments

## One-line answer

Every other phase gate asked whether the thing the phase built works; this one cannot, because what
Phase 12 built is the measuring equipment — so the gate has to measure the ruler, and a ruler is
checked by asking what it says about something whose length you already know.

## The story

The clinic thermometer that always reads normal.

A nurse takes four temperatures in a row and gets 98.6, 98.6, 98.6, 98.6. The first three are
unremarkable. The fourth is from a child whose mother brought her in because she is burning up.

Nobody looks at a thermometer and asks whether it is right. You look at the *reading*. And the only
way anyone ever finds out that the instrument is broken is by putting it against something whose
answer is already known — a glass of iced water, or a child who is obviously running a fever — and
seeing whether it moves.

The reading is what people want. The check is the boring thing you do first, and it is the only
reason the reading means anything.

## The idea in plain language

A **phase gate** is a short sentence in the plan that says what has to be true before the curriculum
moves on. Phase 11's was about a nightly job and a voice loop, and Day 78 turned it into five
commands with exit codes. Phase 12's is:

```text
Full evalset green; rubric trajectories pass
```

That sentence has a shape all the earlier gates had: *does the thing work?* And this time the thing
is a set of measuring instruments — an evalset, two deterministic metrics, a rubric, a judge and a
comparison between two runs. So *does it work* splits into two very different questions, and only
the second one is answerable today.

**Does the desk pass the suite?** This is what the sentence sounds like it is asking, and it is the
question nobody can answer here, because running the judged half costs 270 provider requests on a
lane whose daily allowance has never been measured. The suite has never been run in full.

**Can the suite be believed if it were?** This one costs nothing, because every check that answers it
compares recorded data or reads a file. And it is the question that has to be settled first anyway:
a green run from an instrument nobody has checked is a reading from the thermometer in the story.

So the gate splits into eight criteria, and the split falls out of what each one costs.

| # | Criterion | What it checks | Requests |
| --- | --- | --- | --- |
| 1 | the evalset survives a round trip | the data | 0 |
| 2 | the suite goes red against a stub desk | the metrics | 0 |
| 3 | every rubric line is exercised both ways | the rubric | 0 |
| 4 | the rubric can see the tool calls | the rubric | 0 |
| 5 | the judge beats its baseline | the judge | 0 |
| 6 | the phase fits a free-tier day | the bill | 0 |
| 7 | there is a previous run to compare against | the history | 0 |
| 8 | every day written, no ID left open | the ledger | 0 |

Eight checks, no provider requests, and not one of them asks whether the desk is any good. That is
not a compromise forced by the budget. It is what a gate on a measuring instrument *is*.

## Why Sutra needs it

Because Phase 13 is two days away and inherits these instruments. Every claim made after this point
— that a change is safe, that a regression happened, that a rubric line is satisfied — is a reading
from equipment this gate is the only check on.

And because the alternative has a name and this repository has already met it. Day 79 part 2.3 found
a case that passed whatever the desk said, Day 80 part 3.2 found a rubric that gave every
conversation the same score, and Day 81 part 3.3 found 83.3% agreement that was the base rate. Three
instruments, three ways of reading normal on a patient with a fever, all found by hand, one day at a
time. This day is those checks turned into something that runs.

## The mechanism

`gate.py` runs each criterion as a separate process and collects its exit code:

```python
VERDICTS = {0: "PASS", 1: "FAIL", 2: "CANNOT DETERMINE"}
```

**Line by line:**

- Three codes rather than two, which is Day 78's gate design carried forward. A criterion that
  depends on a number nobody has measured is neither a pass nor a failure, and collapsing it into
  either one is a false statement in whichever direction you choose.
- `2` is a real exit code, so a shell and a CI job can both act on it. The distinction survives the
  process boundary, which is the whole reason it is an exit code and not a printed word.

Each criterion is a separate file, run with `subprocess`:

```python
def run(script: str, *args: str, quiet: bool = False) -> int:
    sys.stdout.flush()
    return subprocess.run(
        [sys.executable, script, *args], capture_output=quiet, text=True
    ).returncode
```

**Line by line:**

- `sys.executable` rather than `"python"` — the criterion runs under the same interpreter as the
  gate, which is the one `uv run` selected. A bare `"python"` would find whatever is first on `PATH`,
  which on this machine is not the project's environment.
- `capture_output=quiet`: when the gate runs a criterion for the verdict it lets the output through,
  because the findings are the point. When it re-runs one with a fault injected it swallows the
  output, because only the exit code is being compared and the findings have already been printed
  once.
- `sys.stdout.flush()` before the child starts. The parent's buffered output and the child's go to
  the same terminal, and without the flush the parent's heading can appear after the output it
  introduces.
- `.returncode` is the whole interface. A criterion is anything that can be run and exits with 0, 1
  or 2, which is why criterion 8 can be a repository check and criterion 4 an ADK method call
  without the gate knowing the difference between them.
- No `check=True`. A non-zero exit is the expected outcome of half these criteria, and raising on it
  would stop the gate at the first finding.

That last point is the design decision worth naming, and it is in the loop:

```python
    for criterion in CRITERIA:
        print(f"\n=== criterion {criterion.label}")
        results.append((criterion, run(criterion.script)))
```

**Line by line:**

- No `break` and no early return. A gate is an attempt to find things, and stopping at the first
  finding is how the second one survives into the next phase.
- The heading is printed *before* the run, so a criterion that crashes is still attributable to a
  line in the output rather than to whichever one ran before it.

## When it breaks

The gate itself can be wrong in exactly one interesting way: a criterion that cannot fail. That is
the same defect as Day 79 part 2.3's always-green case, one level up, and it is invisible in a run
where everything passes.

So the gate tests its own passing criteria. After the eight runs it re-runs each *passing* one with a
fault injected and checks that it goes red:

```text
=== the red-alarm test: a criterion that passed must be able to fail
  c1_roundtrip.py   --drop-tools    0 -> 1  goes red
  c2_stub.py        --lenient       0 -> 1  goes red
  c3_separates.py   --one-sided     0 -> 1  goes red
```

Three passes, three faults, three reds. Criteria 4 through 8 are not in that list because they are
already failing, and a check that is currently red does not need to be shown that it can be.

A criterion that stayed green with its fault injected is reported as `BLIND`, and the gate fails on a
blind criterion exactly as it fails on a red one:

```python
    if failed or unknown or blind:
```

**Line by line:**

- Three ways of not being green, and `blind` is the one that would otherwise have been counted as a
  pass. A criterion that cannot fail is worse than one that fails, because it is reported as
  evidence.
- Any of the three is enough; the order is for reading, not for logic.

## In production

**What a professional does.** Gates on instruments are a real category with a real name —
calibration — and in every field that measures things for money it is scheduled, recorded and
audited separately from the measurements themselves. A test laboratory does not get to say its scales
are fine; a certificate says so, with a date on it. Teams that run model evaluations seriously end up
rebuilding a thin version of the same thing: a small set of cases with known answers, run against the
evaluator rather than against the model.

**What degrades at scale.** Eight criteria is small enough that a person reads all the output. At
forty, nobody does, and the gate becomes a single line that says `3 pass, 4 fail`. That is the exact
shape part [5.2](../05-the-verdict/5.2-what-a-green-phase-12-would-mean.md) measures, and the
mitigation is not fewer criteria but a verdict block that names every non-passing one in full.

**The failure that only shows with real traffic.** A calibration check that is itself calibrated
against the thing it is checking. Criterion 3 reads labels a person wrote; if those labels had been
produced by the judge, the criterion would pass by construction and prove nothing. Nothing in this
repository currently enforces that separation, and at scale it is how a calibration suite quietly
stops being one.

**The review comment a senior engineer leaves:** *"Fine, but say in the output that none of these
eight run the desk. Somebody is going to read `3 pass` and think we tested the agent."*

**The interview question:** *"How do you know your evals are any good?"* The answer that shows
experience does not describe the metrics. It describes a check that the metrics can fail — a stub
that must be refused, a rubric line that must separate — and then names which of those checks the
team does not have.
