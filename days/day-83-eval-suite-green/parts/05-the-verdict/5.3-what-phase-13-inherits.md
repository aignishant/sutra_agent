# 5.3 — What Phase 13 inherits

## One-line answer

Five open items cross the phase boundary, and the order to fix them in is not the order they failed
in: the ledger rows and the history directory are an hour between them and unblock everything else,
the trajectory conversion is a small function with a large blast radius, and the two that need
measurements need somebody to spend an afternoon rather than to write code.

## The story

The handover note when somebody leaves the job.

The last day, and there is an hour to write down what the next person needs. The temptation is to
describe everything: the systems, the history, how it all fits together. That note gets skimmed once
and never opened again.

The note that actually gets used is short and unglamorous. The printer needs the manual tray for
letterhead. The Tuesday report has to go before eleven or the finance system locks. The thing on the
second shelf is nobody's and can be thrown away. Five things, each one a small piece of knowledge that
would otherwise cost the next person a bad afternoon to rediscover.

The difference is not length. It is that the second note is written from the next person's position
rather than from the leaver's.

## The idea in plain language

Phase 13 is observability and deployment: tracing with `AutoTracingPlugin`, the API surface, a
container, a Kubernetes pattern. None of it is evaluation. So the question this part answers is not
*what is left to build in Phase 12* but **what does the next phase hit if these stay open**.

Five items, in the order they should be done rather than the order they failed:

**1. The ledger rows.** Criterion 8. Thirty-three days of written work with no `PROGRESS.md` rows, so
`./m brief` refuses to run and `./m trace` cannot tell unfinished work from unrecorded work. This is
first because it is the one that blocks a *tool*, and Phase 13 opens with a day whose brief will
refuse exactly as this one's did. The information is in `git log` today.

**2. The history directory.** Criterion 7. One config line pointing `LocalEvalSetResultsManager`
somewhere outside `.adk/`, and that directory committed. Day 82 part 5.2 priced it at half an hour and
put it first for the same reason: eight other items assume there is a yesterday. It is second here
only because the ledger blocks a tool and this blocks a comparison nobody is running yet.

**3. The trajectory conversion.** Criterion 4. A function that turns an `IntermediateData` into an
`InvocationEvents` when a case is loaded for a trajectory rubric — plus, and this is the half that
matters, the assertion that the assembled dialogue contains every recorded tool call. The fix is
small; the assertion is what stops the next person's change from undoing it.

**4. The Flash-Lite allowance.** Criterion 6. One controlled burn against a free-tier key, a count, a
dated row in `docs/PACKAGES.md`. Five days, five blocked lists, one afternoon.

**5. The calibration set.** Criterion 5. Fifty answers, roughly half of them wrong, labelled by two
people, with the human-to-human agreement recorded as the ceiling. Parked on Days 79, 80, 81 and now
83. This is last because it is the only one that needs two people's time, and it is the one that will
still be open in a month if nobody schedules it.

## Why Sutra needs it

Because Phase 13 makes the system observable and then deployable, and both of those raise the cost of
a wrong measurement rather than lowering it. Day 84 puts every node, tool call and model call into a
trace tree; Day 86 puts the desk in a container. After that, "did this change make things worse" is
asked about a system running somewhere else, and the instrument that answers is the one this gate has
just found four holes in.

And because items 1 and 2 have a property the other three do not: they get harder every day. A
missing ledger row is reconstructible from `git log` today and a judgement call in six months. A
history that starts accumulating tonight is five nights deep by the weekend; one that starts on the
morning of the incident starts empty.

## The mechanism

The five items with what each costs and what it unblocks:

| # | Item | Where | Roughly | Unblocks |
| --- | --- | --- | --- | --- |
| 1 | backfill the ledger rows | `docs/PROGRESS.md` | an hour | `./m brief`, `./m trace`, criterion 8 |
| 2 | history outside `.adk/`, committed | one config line | half an hour | Day 82's comparison, criterion 7 |
| 3 | trajectory conversion + assertion | `sutra/` and `tests/` | an hour | criterion 4, every rubric score |
| 4 | measure the Flash-Lite allowance | `docs/PACKAGES.md` | an afternoon | criterion 6, four other lists |
| 5 | the calibration set | `evals/` | two people, a session | criterion 5 |

**Items 1, 2 and 3 are two and a half hours between them** and they turn three of the four failures
into passes. Items 4 and 5 are not code and will not happen unless somebody puts them in a week.

Item 3 is the only one with an interesting shape, so here is its whole implementation:

```python
def as_events(source: Invocation) -> Invocation:
    """The same turn, with its tool calls stored the way the assembler reads them."""
    parts = [
        genai_types.Part(function_call=call) for call in source.intermediate_data.tool_uses or []
    ]
    return source.model_copy(
        update={
            "intermediate_data": InvocationEvents(
                invocation_events=[
                    InvocationEvent(
                        author="desk",
                        content=genai_types.Content(parts=parts, role="model"),
                    )
                ]
            )
        }
    )
```

**Line by line:**

- `model_copy(update=...)` rather than mutating the invocation. The loaded case is what the rest of
  the suite compares against, and rewriting it in place would mean the trajectory metric and the
  trajectory rubric were looking at different objects with the same name.
- One `InvocationEvent` per turn holding every tool call, rather than one per call. The assembler
  iterates parts inside an event's content, so both shapes render — and one event per turn keeps the
  author, which the assembler also reads for the agent's name.
- `author="desk"` is a decision the conversion has to make and the file format does not record. The
  fallback the assembler uses is the literal string `"agent"`, so a conversion that leaves the author
  blank produces `AGENT (agent)` and a rubric line about *which* agent acted becomes ungradeable. In
  the product this comes from the app's own agent name, not from a constant.
- `or []` for a turn with no tool calls, which is most turns in a real conversation.
- What is not here is the assertion, because the assertion belongs in `tests/`, and part
  [2.4](../02-instrument-criteria/2.4-criterion-4-the-rubric-can-see.md)'s review comment is why it is
  the more important half.

## When it breaks

The list breaks by being read as a backlog. A backlog is a place things are put; this is a set of
things with an order and two of them expire.

The failure has a shape and Phase 12 has already demonstrated four of its steps:

```text
1. a phase gate produces findings and a ⚠️ row
2. the next phase starts, because the findings are not blockers
3. the findings become tickets and the tickets age
4. the ledger gap grows from 33 rows to 60, and git log gets murkier
5. Phase 13 asks "did tracing make it slower?" and there is no baseline run to compare
6. somebody proposes measuring it, and the eval suite is the instrument
7. the instrument still has the four holes this gate found
```

Step 5 is the one to watch for, because it is where Phase 13's own work runs into Phase 12's open
items — and it will arrive as a performance question, not as an evals question, so nobody will connect
it to this list.

There is no error text. Every step is a reasonable decision by somebody who has not read this page.

## In production

**What a professional does.** Converts findings into scheduled work before the phase closes, with an
owner and a date, and distinguishes the ones that decay. "Backfill the ledger" and "start keeping
history" are both cheap now and expensive later; "write a calibration set" costs the same next month
as it does today. Only the first kind belongs in this week.

**What degrades at scale.** Handover lists get longer and less ordered. Five items with an argued
order is a page somebody reads; twenty items sorted by the day they were found is a backlog nobody
does. The discipline is to keep the list short by *closing* things rather than by leaving them out.

**The failure that only shows with real traffic.** The next phase changes what the open items mean.
Once the desk is in a container (Day 86), item 2's "commit the history directory" is wrong — a
container's filesystem does not survive the run, so the history has to go somewhere the container can
write and the repository cannot. That is a different fix, it is more work, and it is cheaper to do the
simple version now and migrate than to wait and do the complicated one.

**The review comment a senior engineer leaves:** *"Do items 1 and 2 before we start Day 84 — they are
ninety minutes and they both get worse with time. Items 4 and 5 go on next week's plan with names
against them, or they will still be here at Day 96."*

**The interview question:** *"You are moving to the next phase with known gaps. How do you hand them
over?"* The answer that shows experience sorts them by decay rather than by severity: what gets more
expensive if we wait, what stays the same, and what the next phase will hit first without knowing it
is related.
