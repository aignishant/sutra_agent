# 5.1 — The verdict

## One-line answer

Three pass, four fail, one cannot be determined — and the honest headline is not the arithmetic but
the sentence underneath it: the suite has never been run in full, and four of the eight checks say it
could not yet be believed if it had.

## The story

The result sheet with three columns.

Pinned to the board outside the office: names down the left, and across the top **PASS**, **FAIL**,
and a third column headed **RESULT WITHHELD**. Most people scan for their name and find it in one of
the first two. A few find it in the third, and the third is the one nobody knows how to read.

It does not mean fail. It does not mean pass. It means the paper is somewhere, or a mark is missing,
or a piece of the process did not complete — and the office cannot say which way it would have gone.

The temptation, for whoever prints the sheet, is to drop the third column and put those names
somewhere. It would make the sheet easier to read and it would make it wrong.

## The idea in plain language

Here is Phase 12's gate, criterion by criterion, with the reason for each verdict.

| # | Criterion | Verdict | Why |
| --- | --- | --- | --- |
| 1 | the evalset survives a round trip | PASS | 9 tool calls out, 9 back, in order |
| 2 | the suite goes red against a stub desk | PASS | 0 of 3 cases pass for a desk that does nothing |
| 3 | every rubric line is exercised both ways | PASS | 4 of 4 lines have a yes and a no |
| 4 | the rubric can see the tool calls | FAIL | 3 recorded, 0 rendered into the judge's transcript |
| 5 | the judge beats its baseline | FAIL | margin +0.0%, kappa +0.00, never calibrated |
| 6 | the phase fits a free-tier day | CANNOT DETERMINE | 270 requests against an unmeasured allowance |
| 7 | there is a previous run to compare against | FAIL | 0 tracked result files; 2 on disk, both ignored |
| 8 | every day written, no ID left open | FAIL | days 79–83 written, no `PROGRESS.md` rows |

Three, four and one. And then the sentence that is the actual verdict, because the arithmetic on its
own would be misleading in a specific way:

> **The gate asked whether the eval suite is green. The suite has never been run in full, and four of
> these eight checks say it could not yet be believed if it had.**

That distinction is worth being pedantic about, because *"4 of 8 failed"* invites the reading that
the desk failed half its tests. Nothing here tested the desk. Every criterion is about the equipment,
and the four failures split into two kinds:

**Two are defects in the instruments.** Criterion 4 is a rubric judge grading a trajectory it cannot
see, and criterion 5 is a judge whose margin over a coin has never been established. Both are
findings about Phase 12's own product, and both are fixable inside the phase.

**Two are absences.** Criterion 7 is a history that nothing keeps and criterion 8 is a ledger with no
rows. Neither is a bug in anything; both are steps nobody has taken. They fail because a gate that
only checks code lets a phase through with its record-keeping undone.

And criterion 6 is neither, which is why the third column exists.

## Why Sutra needs it

Because this row goes into `PROGRESS.md` and stays there. Principle 10 is that errors surface rather
than being covered, and it applies hardest at the moment when covering one would be easiest and
nobody would ever check. A `✅` here would be a claim, made by me, about my own work, in the one place
a future reader will trust without re-deriving.

And because Phase 13 starts from this list. Part [5.3](5.3-what-phase-13-inherits.md) is what each
open item costs the next phase, and the list is only useful if it is complete.

## The mechanism

The gate counts the three outcomes separately rather than folding them together:

```python
    failed = [c.label for c, code in results if code == 1]
    unknown = [c.label for c, code in results if code == 2]
    passed = len(CRITERIA) - len(failed) - len(unknown)
```

**Line by line:**

- `passed` is derived by subtraction, so a criterion that exits with some fourth code cannot be
  counted as a pass by accident. If a script ever exits `3`, the total stops adding up and somebody
  notices, which is preferable to it being silently absorbed.
- `failed` and `unknown` collect labels, not counts, so the verdict block can name them. A number is
  a summary; a name is an address.
- Explicit `== 1` and `== 2` rather than `!= 0`. The two conditions mean different things and the
  code says so.

And the verdict is printed in full before the exit code is decided:

```python
    for criterion, code in results:
        print(f"  {VERDICTS[code]:<18}{criterion.label}")
```

**Line by line:**

- Every criterion, including the passes. A verdict block that lists only failures cannot be checked
  against the criteria list, and a criterion that silently stopped running would leave no gap.
- `VERDICTS[code]` will raise `KeyError` on an unexpected exit code rather than printing something
  vague. A gate whose own reporting fails loudly is better than one that describes an unknown state
  in soothing language.

Run the whole thing:

```bash
cd days/day-83-eval-suite-green/lab
uv run python gate.py; echo "exit: $?"
```

**Line by line:**

- No flag. The `--headline` arm is part [5.2](5.2-what-a-green-phase-12-would-mean.md)'s subject and
  is the same eight runs with the findings removed.

Measured on 2026-09-06 — the tail, after the eight criteria have each printed their own output:

```text
=== the red-alarm test: a criterion that passed must be able to fail
  c1_roundtrip.py   --drop-tools    0 -> 1  goes red
  c2_stub.py        --lenient       0 -> 1  goes red
  c3_separates.py   --one-sided     0 -> 1  goes red

=== verdict
  PASS              1  the evalset survives a round trip
  PASS              2  the suite goes red against a stub desk
  PASS              3  every rubric line is exercised both ways
  FAIL              4  the rubric can see the tool calls
  FAIL              5  the judge beats its baseline
  CANNOT DETERMINE  6  the phase fits a free-tier day
  FAIL              7  there is a previous run to compare against
  FAIL              8  every day written, no ID left open

  3 pass, 4 fail, 1 cannot be determined

  Phase 12 is NOT green.
  The gate asked whether the eval suite is green. The suite has never been run in
  full, and four of these eight checks say it could not yet be believed if it had.
exit: 1
```

The red-alarm block is the part to read first, because it is what makes the three passes worth
anything. Each of them was re-run with a fault injected and each went red, so `PASS` on those three
lines means *this check would have caught the thing it is for*, not merely *this check did not
complain*.

## When it breaks

A verdict breaks by being rounded. There are three ways and each has a name:

**Rounding the third column into a pass.** Criterion 6 becomes a `PASS` on the grounds that 270
requests is probably fine, and the phase is `4 pass, 4 fail`. Part
[3.2](../03-judge-and-bill/3.2-criterion-6-the-phase-fits.md)'s `--assume-generous` arm is exactly
this, and it exits `0` while printing `<- assumed, not measured` in a line nobody reads.

**Rounding the third column into a fail.** Kinder-looking and equally wrong: it puts a
`5 fail` in the ledger for something nobody measured, and the next person spends a day investigating
a capacity problem that may not exist.

**Rounding the sentence into the number.** `3 pass, 4 fail` invites the reading that the desk was
tested and half-failed. The number is arithmetic; the sentence is the finding, and the sentence is
the part that has to survive into `PROGRESS.md`.

The gate mark this produces is `⚠️`, and the ledger row says what it means in plain words. There is no
error text for a mis-rounded verdict, and there never will be: this is the one part of the day where
the check is a person deciding to write down something unwelcome.

## In production

**What a professional does.** Publishes the criteria before the run and the verdict without editing
it afterwards. The discipline that makes a gate mean anything is that the person who writes the
verdict is not permitted to change the criteria in the same session — otherwise every gate passes,
one small redefinition at a time, and nobody involved ever tells a lie.

**What degrades at scale.** Verdicts get summarised upwards. Eight lines become one line becomes a
colour on a dashboard, and each step is a reasonable act of compression performed by somebody who was
not present for the finding. The mitigation is that the sentence travels with the number, in the
same field, so the compression cannot separate them.

**The failure that only shows with real traffic.** The verdict is read by somebody deciding whether to
depend on the thing. A `⚠️` in a ledger means little to a person who reads it six months later while
planning work that assumes the eval suite catches regressions. That is why the row names the two
carried-forward findings explicitly rather than pointing at this day — a pointer is a thing you
follow if you have time.

**The review comment a senior engineer leaves:** *"Do not put a green tick on this. And put the
sentence in the row, not just the counts — whoever reads it in March needs to know the suite has
never run in full, and `3/8` does not say that."*

**The interview question:** *"Your release gate has one criterion you cannot evaluate. What do you
ship?"* The answer that shows experience does not pick a default. It says what the criterion was for,
what it would take to determine it, and who decides whether to proceed without it — because the
decision is a person's and the engineer's job is to make sure it is being made rather than assumed.
