# 4.2 — Criterion 8: every day written, no ID left open

## One-line answer

Three independent sources have to agree about what this phase closed — the plan's assignment, the
hub frontmatter of each day, and the ledger row — and the first two agree perfectly over Days 79 to
82 while the third has no rows at all, so nine concept IDs are open in a phase whose work is
finished.

## The story

The maintenance receipts nobody entered in the book.

A housing society collects a monthly charge. Money comes in, a receipt book gets torn, and once a
week somebody is supposed to write the amounts into the ledger. For a while somebody does. Then the
person who did it moves out, the receipts keep being written, and the ledger does not.

Nine months later the treasurer needs to know who has paid. Every flat has its receipt, and every
receipt is genuine, and the ledger says nobody has paid anything since March. The money is not
missing. The *record* is missing, and a record is the only thing anybody can act on: you cannot chase
arrears from a stack of receipts in twelve different flats.

Nothing was stolen and nothing was forgotten. A step that was somebody's job stopped being anybody's.

## The idea in plain language

Principle 2 is *one day, one commit*, and the artefact it produces is a row in `docs/PROGRESS.md`:
the day number, the date, the IDs it closed, the part count, the commit hash and a gate mark. That
row is what `./m trace` reads to decide whether a concept ID is closed.

So a day's work exists in three places, and this criterion compares them:

| Source | What it says | Who wrote it |
| --- | --- | --- |
| the plan's §14 table | which IDs day N is *supposed* to close | the plan, months ago |
| the day's hub frontmatter | which IDs the day *says* it closes | whoever wrote the day |
| `docs/PROGRESS.md` | that day N is *done* | whoever committed it |

Agreement between the first two means the day was written to its assignment. The third is what makes
the IDs closed. A day can be perfectly written, fully checked, depth-green — and if the row is
missing, every ID in it is open, because the ledger is the only thing anybody queries.

This is Day 78's criterion 5 pointed at a different phase, and it is here for the same reason: a gate
that only checks the code is a gate that lets a phase through with its paperwork undone.

## Why Sutra needs it

Because the verdict this day writes is itself a ledger row, and writing one while eight others are
missing would be the clearest possible demonstration of the problem.

And because the finding is not new and has not been fixed. `./m brief 83` refuses to run at all: it
reports that the last row in `PROGRESS.md` is day 50 and that N must therefore be 51. Thirty-two days
of written, checked, committed work sit above a ledger that stops at day 50 — and every one of those
days flagged it and continued, which is exactly how the receipts pile up.

## The mechanism

Three readers, one comparison. The plan:

```python
match = re.match(r"^\|\s*(\d{1,2})\s*\|.*\|\s*([A-Z]{2,3}-\d+(?:,\s*[A-Z]{2,3}-\d+)*)\s*\|$", row)
```

**Line by line:**

- Anchored at both ends, so it matches a whole table row and not a fragment of prose that happens to
  contain an ID.
- `[A-Z]{2,3}-\d+` is the ID shape — `AG-28`, `ADK-62`, `OPS-15` — and the repeat group allows the
  comma-separated list a day with two IDs has.
- The day number is capped at two digits, which is correct for a 97-day curriculum and is the kind of
  assumption worth writing down rather than discovering at day 100.

The hub:

```python
    match = re.search(r"^ids:\s*\[(.*?)\]", text, re.M)
    return {i.strip().strip('"') for i in match.group(1).split(",")} if match else set()
```

**Line by line:**

- `re.M` so `^` matches the start of a frontmatter line rather than only the start of the file.
- A `set`, not a list. The comparison against the plan is about *which* IDs, not their order, and a
  set comparison prints a readable difference.
- `.strip('"')` because the frontmatter is YAML and the IDs are quoted. This is the same brittleness
  as reading YAML with a regex generally, and it is deliberate here: the checker must not depend on a
  YAML parser being installed, because it runs before anything else does.
- The `else set()` matters. A hub with no `ids:` line returns an empty set, which will not equal the
  plan's set, so a missing declaration fails rather than being skipped.

The ledger:

```python
    return {int(m.group(1)) for r in rows if (m := re.match(r"^\|\s*(\d{1,3})\s*\|", r))}
```

**Line by line:**

- Only the day number is read from `PROGRESS.md`. The criterion asks whether a row *exists*; whether
  its contents are right is a different check and Day 78 part 4.5 is the one that reads the pins.
- The walrus `:=` binds the match inside the comprehension's condition so the body can use it without
  matching twice.

## When it breaks

There is no error text, and the absence is instructive: the *only* thing in the repository that
notices is a checker somebody wrote for the purpose. `./m depth 82` is green. `./m trace` runs. The
day folders are complete, the labs run, the links resolve. Every automated check passes over a phase
whose ledger has no rows in it, because a missing row is not a syntax error in anything.

The one tool that does complain is the brief:

```text
**STOP.** The last PROGRESS row is day 50, so N must be 51, not 83. Fix the ledger or the day
number before writing (P2).
```

That is the guard working exactly as designed, and it has been fired and overridden on every day from
51 to 83 — thirty-three consecutive times. Which raises the question this part has to be honest
about: **a guard that is overridden thirty-three times running is not a guard.** It is a message. The
first override was a judgement call, the tenth was a habit, and by the thirtieth the check has been
retrained to mean *"carry on"*.

Day 82 part 4.2 measured the same shape in a quarantine list: five checks switched off, the oldest
203 days, every entry added for a good reason and none of them ever a decision to stop checking. This
is that, applied to a ledger, with the repository's own tooling as the thing being quarantined.

The composite is short and every step of it is here:

```text
1. a day is written, checked and complete
2. the row is not appended, because the commit has not happened yet
3. the next day starts; the brief says STOP; the writer overrides it
4. steps 1-3 repeat
5. thirty-three days later, ./m trace reports 113 of 199 IDs closed
6. nothing in the repository can tell "not done" from "done, not recorded"
```

Step 6 is the one that costs something. `./m trace` cannot distinguish work that has not happened
from work that has not been written down, and neither can anybody reading it.

## In production

**What a professional does.** Makes the record a side effect of the work rather than a step after it.
The reason `./m done N` exists is precisely this: a command that refuses to commit until the
checklist is ticked and appends the row itself is a ledger that cannot fall behind, because the only
way to finish is through it. A step that depends on somebody remembering is a step that stops when
that person is busy.

**What degrades at scale.** The gap compounds silently. One missing row is an afternoon to
reconstruct from `git log`; thirty-three missing rows over four phases is a reconstruction job with
judgement calls in it — which date, which hash, which gate mark — and every day that passes makes it
slightly harder to do accurately.

**The failure that only shows with real traffic.** The ledger is used to answer a question nobody
anticipated. This one is not hypothetical either: `./m brief` reads `PROGRESS.md` to decide whether
day N is allowed, so a stale ledger disables the tool whose job is to keep the days in order. A record
kept for one purpose is always eventually queried for another, and that is when its gaps become
somebody's problem.

**The review comment a senior engineer leaves:** *"Backfill the rows from `git log` before starting
Phase 13. It is thirty-three rows and the information is all there today; it will still be there in
six months and it will take four times as long to be sure of."*

**The interview question:** *"Your team's changelog is three months behind. Does it matter?"* The
answer that shows experience does not argue about documentation discipline. It asks what reads the
changelog — a release process, an audit, a tool — and points out that every one of those now cannot
distinguish *not done* from *not recorded*.
