# 2.3 — `load_skill`: what activation actually costs

## One-line answer

`load_skill` returns the body **and the entire frontmatter**, so activating `ticket-triage` costs 334
tokens rather than the 184 the body is worth — and 118 of the difference is metadata the model has no
use for.

## The story

You go to the chemist for the leaflet.

Somebody in the family has been prescribed a tablet, and you want to read the part about what not to
take with it. The chemist does not hand you the leaflet. He hands you the box: the outer carton with
the brand name in four colours, the barcode, the batch number, the little sticker the shop puts on
with its own price and its own reference, and inside, folded eight times, the leaflet.

You wanted six lines about interactions. You are holding a carton with fourteen printed things on it,
thirteen of which are addressed to somebody who is not you — the warehouse, the till, the auditor.

None of it is wrong. It is just that if you were paying by the printed word, you would notice.

## The idea in plain language

`load_skill` is rung 2. The model calls it with `skill_name="ticket-triage"` and gets back the
procedure it is supposed to follow.

Day 25 established what the body costs: the whole `SKILL.md` body enters the context on activation and
stays there for the rest of the conversation
([25.3.1](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.1-the-body-is-loaded-whole.md)).
That is still true. What Day 25 could not know — because it was measuring the format rather than a
client — is that ADK sends **more than the body**.

The tool returns a dictionary with three keys:

| Key | What is in it | Measured, `gemini-3.7-flash`, 2026-09-04 |
| --- | --- | --- |
| `skill_name` | the name again | a handful of tokens |
| `instructions` | the whole Markdown body | 184 tokens |
| `frontmatter` | **every field, dumped** | 118 tokens |
| the whole payload as JSON | | **334 tokens** |

The `frontmatter` key is the one to look at. It is the pydantic model dumped whole: `name`,
`description`, `license`, `compatibility`, `allowed_tools`, and the entire `metadata` dictionary —
including keys ADK put there for its own use. So the model receives, as part of the procedure it is
about to follow:

- the description, which it has **already seen** in the `list_skills` result;
- `allowed_tools: null`, a field nothing enforces
  ([1.2](../01-loading-a-folder/1.2-the-skill-object.md));
- `license: Apache-2.0`, addressed to a lawyer;
- `compatibility`, addressed to an operator;
- whatever internal keys your team invented.

That is 118 tokens of the 334, or a little over a third of the activation cost, spent on material
written for humans and tooling rather than for the model. It is not a bug and there is no flag to turn
it off. It is a fact to know, because it changes the arithmetic of "should this go in the body or in
`references/`?" — the body is only 55 per cent of what activation costs.

One field in that dictionary is not inert. If `metadata` contains `adk_inject_state: true`, ADK runs
the body through session-state templating before returning it: `{ticket_id}` in the Markdown is
replaced with the value from state, `{ticket_id?}` substitutes an empty string when the key is absent
rather than raising, and `{artifact.name}` injects an artifact's contents. That is the same templating
Day 6 met on the instruction field
([6.4.1](../../../day-06-instructions-and-personas/parts/04-state-templating/4.1-the-instruction-is-a-template.md)),
now available inside a skill body — and it carries the same trap Day 6 documented, where a stray brace
raises instead of printing.

## Why Sutra needs it

Because the whole reason Sutra is adopting skills is to move procedure out of the system instruction,
and that trade only pays if you know the real price on both sides.

The system instruction costs its tokens on **every** request of the conversation. An activated skill
costs its tokens on every request **after activation** — which, in a five-turn triage conversation
where the skill fires on turn one, is four out of five. The saving is real but it is smaller than
"only when needed" makes it sound, and it is 334 rather than 184 per turn.

The Day 25 build brief asked the learner to take one thing out of the body and put it in
`references/`, then measure. That exercise now has a floor: no amount of moving material out of the
body gets activation below about 150 tokens, because the frontmatter dump does not move. Knowing where
the floor is stops the optimisation from continuing past the point where it helps.

## The mechanism

Same double, same direct call, one rung up.

```python
# days/day-26-loading-skills-into-adk/lab/rung_two.py
"""Call load_skill directly and take the returned payload apart, key by key."""

import asyncio
import json
import os
import pathlib

from fake_skill_context import FakeSkillContext
from google import genai
from google.adk.skills import load_skill_from_dir
from google.adk.tools import skill_toolset

from sutra.config import load_env

MODEL = "gemini-3.7-flash"
SHELF = pathlib.Path("days/day-26-loading-skills-into-adk/lab/skills")


async def main() -> None:
    """Activate one skill by hand and price every key of the result."""
    skill = load_skill_from_dir(SHELF / "ticket-triage")
    toolset = skill_toolset.SkillToolset(skills=[skill])
    tools = {tool.name: tool for tool in await toolset.get_tools()}

    context = FakeSkillContext()
    payload = await tools["load_skill"].run_async(
        args={"skill_name": "ticket-triage"}, tool_context=context
    )

    print("keys        :", list(payload))
    print("frontmatter :", json.dumps(payload["frontmatter"]))
    print("state after :", context.state)

    load_env()
    client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])

    def cost(text: str) -> int:
        """Tokens for one string, on the pinned model. Costs 0 generations."""
        return client.models.count_tokens(model=MODEL, contents=text).total_tokens

    print("body        :", cost(payload["instructions"]))
    print("frontmatter :", cost(json.dumps(payload["frontmatter"])))
    print("whole reply :", cost(json.dumps(payload)))


asyncio.run(main())
```

**Line by line:**

- `args={"skill_name": "ticket-triage"}` — the parameter is `skill_name`, and getting that wrong is
  the most common way to copy this call incorrectly, because a tool that loads a skill "by name"
  invites you to write `name=`. Read off the tool's own JSON schema on 2026-09-04: one required
  property, `skill_name`, a string.
- `payload` is a **plain dictionary**, not an object. That is the ADK convention for a tool result and
  the reason a tool can report a failure without raising
  ([10.2.3](../../../day-10-function-tools/parts/02-what-a-tool-returns/2.3-a-failed-tool-is-still-a-result.md)).
- `json.dumps(payload["frontmatter"])` before counting, because the model does not receive a Python
  dictionary — the runtime serialises the tool result. Counting the `repr` would flatter the number by
  using single quotes, and counting the object would not work at all.
- `context.state` is printed **after** the call, because `load_skill` writes to it. What it writes is
  [3.3](../03-wiring-the-toolset/3.3-activation-is-a-line-in-state.md)'s subject; here it is enough to
  see that a "read" tool is not read-only.
- `cost()` is a nested function rather than a module-level one because it closes over `client`, and it
  exists so that the three measurements read as three lines rather than three long expressions. Its
  docstring records the quota fact so nobody has to re-derive it.
- `count_tokens` again spends **0** generations, on the separate endpoint Day 24 verified stays
  available even while `generate_content` is refusing
  ([24.2.1](../../../day-24-token-accounting-and-budgets/parts/02-two-ceilings/2.1-two-ceilings-one-clears.md)).

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/rung_two.py
```

**Line by line:**

- Needs `GOOGLE_API_KEY` for the three token counts and spends **0** of the twenty daily generations.

Measured on 2026-09-04 against `google-adk` 2.7.1 and `gemini-3.7-flash`:

```text
keys        : ['skill_name', 'instructions', 'frontmatter']
frontmatter : {"name": "ticket-triage", "description": "Assign a severity to a support ticket and record it, using the desk's published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.", "license": "Apache-2.0", "compatibility": "Requires the Sutra desk tools and Python 3.12", "allowed_tools": null, "metadata": {"author": "sutra-desk", "version": "1.0"}}
state after : {'_adk_activated_skill_desk': ['ticket-triage']}
body        : 184
frontmatter : 118
whole reply : 334
```

Read the `frontmatter` line as the model reads it. The description appears for the **second** time in
this conversation — the model already had it from `list_skills` — and `"allowed_tools": null` is a
field the model is told about and cannot act on.

## When it breaks

**A skill name that is not on the shelf.** The tool does not raise; it returns an error dictionary:

```text
{'error': "Skill 'nope' not found.", 'error_code': 'SKILL_NOT_FOUND'}
```

That is deliberate and it is the right shape. A raised exception would end the turn; a returned error
goes back to the model as a tool result, and the preamble's rule 1 gives it something to do about it.
It is also the shape Day 10 argued for — a failed tool is still a result, with a status the model can
read
([10.2.3](../../../day-10-function-tools/parts/02-what-a-tool-returns/2.3-a-failed-tool-is-still-a-result.md)).
Note what it means operationally: **a skill that is missing produces no exception anywhere in your
process.** If you are not logging tool results, a shelf that failed to load is invisible.

**The argument spelled `name`.** The tool checks for its own parameter and reports rather than
crashing:

```text
{'error': "Argument 'skill_name' is required.", 'error_code': 'INVALID_ARGUMENTS'}
```

**A brace in the body with state injection switched on.** Set `adk_inject_state: true` in the skill's
metadata, write a JSON example in the body containing `{"severity": "high"}`, and the templating tries
to resolve `"severity"` as a state key. Day 6 met this exact failure on the instruction field
([6.4.2](../../../day-06-instructions-and-personas/parts/04-state-templating/4.2-hard-and-soft-contracts.md)),
and the fix is the same: use the `{var?}` form where a missing key is acceptable, and keep literal
braces out of a body that has templating switched on. The wider lesson is that `adk_inject_state` is
opt-in for a reason — turning it on changes what every brace in the document means.

**The model that loads the skill and stops.** Rule 7 of the preamble exists because of this: some
models treat a successful tool call as the end of a turn and produce an empty response. If you see a
`load_skill` call followed by nothing, the failure is not in your skill.

## In production

**Keep the frontmatter thin, because the model pays for it.** This is the practical instruction that
falls out of the measurement. `compatibility` and `license` are for people; every character of them is
also sent to the model on every activation. A skill whose `metadata` has accumulated an owner, a
review date, a ticket link, a changelog note and three internal identifiers is a skill whose
activation is mostly bookkeeping. Put the bookkeeping in `SKILL_PROVENANCE.md`, where Day 29 wants it
anyway, and keep `metadata` to keys that change behaviour.

**Measure activation, not the body.** A team optimising skill cost by counting body tokens is
measuring 55 per cent of the thing. The number that belongs on a dashboard is the size of the
`load_skill` result, and it is available for free: the tool returns it, so a callback on the tool
result can count it without a model call.

**Count activations per skill and per conversation.** A skill activated twice in one conversation has
put its 334 tokens in twice, and the second one bought nothing — the first copy is still in the
context. Day 22's log line and Day 13's `after_tool_callback` between them give you the hook
([13.3.3](../../../day-13-callbacks-four-doors/parts/03-the-tool-doors/3.3-the-result-on-its-way-back.md)),
and a repeated activation is a signal worth acting on: usually the body did not actually answer the
question, which is a skill-design problem rather than a cost problem.

**What changes at scale** is that the second-order cost dominates. Activation is a one-off charge, but
the activated body rides along on every subsequent turn of the conversation
([24.1.2](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.2-charged-again-every-turn.md)).
A ten-turn conversation that activates two skills early carries about 670 tokens of skill payload for
eight turns. That is the number to put next to the system instruction you were trying to shrink.

**The review comment a senior engineer leaves:** *"the activation payload includes the full
frontmatter, so our four internal metadata keys are being sent to the model on every skill load. Move
them to the provenance ledger — the model has never used them and never will."*

**The interview question:** *"what does the model actually receive when a skill activates?"* The
answer that shows you have measured: *"the tool result is a dictionary with the skill name, the whole
Markdown body, and the complete frontmatter dumped as JSON. For our smallest skill that is 334 tokens
where the body alone is 184, so about a third of activation is metadata the model cannot use —
including the description it already saw in the index. And it stays in the context for the rest of the
conversation, so the real cost is that number times the remaining turns."*
