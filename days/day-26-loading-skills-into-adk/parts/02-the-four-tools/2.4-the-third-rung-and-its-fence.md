# 2.4 — `load_skill_resource`: the third rung, and the fence around it

## One-line answer

`load_skill_resource` fetches one file out of a skill's own folders and refuses any path that does not
begin `references/`, `assets/` or `scripts/` — and it counts failed lookups per invocation so that the
second miss comes back with an order to stop.

## The story

The reference room of an old library has a counter across it and no public shelves.

You fill in a slip: the title, the shelf mark, your reader number. The librarian goes behind the
counter and comes back with the one volume. You read it at the desk. You do not go behind the counter,
and neither does anybody else, and that is not because the books back there are secret. It is because
a room where two hundred people wander among the stacks is a room where books stop coming back.

Ask for something that is not in the catalogue and you are told so, politely. Ask a second time, with
a shelf mark you have clearly invented, and the tone changes: *"there is no such volume — please check
the catalogue before you fill in another slip."*

The counter is not there to stop you reading. It is there so that everything you read is something the
library agreed to lend.

## The idea in plain language

Rung 3. The skill's body is in context, and the body links to something —
`[references/SEVERITY.md](references/SEVERITY.md)`. Following that link is a tool call:
`load_skill_resource(skill_name="ticket-triage", file_path="references/SEVERITY.md")`.

The tool returns a dictionary with `skill_name`, `file_path` and `content`. That is the whole happy
path, and it is what makes the split Day 25 recommended actually pay
([25.3.2](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.2-scripts-references-assets.md)):
the severity table costs **62 tokens**, and they are spent only when a triage is ambiguous enough that
the model goes to look.

Three rules sit around that happy path, and each one is a design decision worth understanding.

**The prefix fence.** `file_path` must start with `references/`, `assets/` or `scripts/`. Anything
else is refused before any lookup happens. That is not path sanitising in the usual sense — there is no
filesystem access to sanitise, because [1.1](../01-loading-a-folder/1.1-load-skill-from-dir.md) already
read every file into dictionaries. The fence is a **namespace** rule: those three prefixes are the
three dictionaries, and a path outside them names nothing that exists. The effect is the same as a
containment control, and it is worth being precise about why, because "it cannot read `../../.env`"
and "there is no code path that opens a file" are different guarantees. This is the second.

**The three prefixes are stripped before lookup.** `references/SEVERITY.md` becomes the key
`SEVERITY.md`, which is exactly how the loader keyed it. A nested file at `references/api/errors.md`
is asked for by its full relative path, and its key is `api/errors.md`.

**The miss counter.** A resource that is not found returns an error — and increments a counter stored
in state under `temp:_adk_skill_resource_not_found_count_<invocation_id>`. On the second miss in the
same invocation, the error code changes from `RESOURCE_NOT_FOUND` to `RESOURCE_NOT_FOUND_FATAL` and
the message tells the model to stop.

That counter is a small piece of engineering worth admiring. It uses the `temp:` prefix Day 17 taught
([17.2.4](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.4-why-temp-exists.md)) so
it is never written to durable session storage, and it keys on the invocation id so two concurrent
runs cannot poison each other's count. It exists because a model that has invented one path will
invent another, and the escalation is what breaks the loop.

## Why Sutra needs it

Because Sutra's triage skill is built on exactly this link, and because Day 29 will have to say what a
third-party skill can reach.

The severity table lives in `references/` precisely so that it is not paid for on every activation.
That design is only real if the model can actually fetch it, and this is the call that does it. When
Day 28 designs progressive disclosure properly, the unit it is designing with is one
`load_skill_resource` call and its 62 tokens.

The fence matters for a different reason. Day 29 audits skills that Sutra did not write, and the first
question about any such skill is *what can it reach?* Part of that answer is here and is
reassuring — a skill's resource tool can only name the skill's own three folders. The other part is
the next rung, and it is not reassuring at all.

## The mechanism

Same double, same direct call, one rung further.

```python
# days/day-26-loading-skills-into-adk/lab/rung_three.py
"""Fetch one resource, then probe the fence and the miss counter."""

import asyncio
import pathlib

from fake_skill_context import FakeSkillContext
from google.adk.skills import load_skill_from_dir
from google.adk.tools import skill_toolset

SHELF = pathlib.Path("days/day-26-loading-skills-into-adk/lab/skills")


async def main() -> None:
    """Four calls: one hit, one refused path, and two misses in one invocation."""
    skill = load_skill_from_dir(SHELF / "ticket-triage")
    toolset = skill_toolset.SkillToolset(skills=[skill])
    fetch = {tool.name: tool for tool in await toolset.get_tools()}["load_skill_resource"]
    context = FakeSkillContext()

    async def ask(file_path: str) -> object:
        """One call, with the skill name filled in."""
        return await fetch.run_async(
            args={"skill_name": "ticket-triage", "file_path": file_path},
            tool_context=context,
        )

    print("hit       :", await ask("references/SEVERITY.md"))
    print("outside   :", await ask("../../.env"))
    print("miss 1    :", await ask("references/NOPE.md"))
    print("miss 2    :", await ask("references/OTHER.md"))
    print("state     :", context.state)


asyncio.run(main())
```

**Line by line:**

- `ask()` is a nested helper so that four calls read as four lines. The skill name is the same every
  time; the file path is the variable being explored.
- `"references/SEVERITY.md"` is written **with** the prefix, because the fence checks it. Asking for
  `SEVERITY.md` alone is refused, even though that is the dictionary key ADK will use after stripping.
- `"../../.env"` is the probe that matters. It is the path an injected instruction inside a skill body
  would try, and it is written here so that the refusal is observed rather than assumed.
- Two misses, **not one**, and both in the same `context`. One miss shows you the ordinary error; the
  second shows the escalation, and the escalation is only visible because the double kept its state
  dictionary between calls. A fresh context per call would have hidden the whole mechanism.
- `context.state` at the end prints the counter, which is how you see that a read-only-sounding tool
  wrote to session state.
- Still **zero model calls**.

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/rung_three.py
```

**Line by line:**

- Needs no key at all. Nothing here talks to a provider.

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text
hit       : {'skill_name': 'ticket-triage', 'file_path': 'references/SEVERITY.md', 'content': '# Severity table\n\n| Severity | The ticket says |\n| --- | --- |\n| high | money moved, data lost, or nobody can log in |\n| normal | one feature is wrong for one customer |\n| low | a question, a typo, or a feature request |\n'}
outside   : {'error': "Path must start with 'references/', 'assets/', or 'scripts/'.", 'error_code': 'INVALID_RESOURCE_PATH'}
miss 1    : {'error': "Resource 'references/NOPE.md' not found in skill 'ticket-triage'.", 'error_code': 'RESOURCE_NOT_FOUND'}
miss 2    : {'error': "Resource 'references/OTHER.md' not found in skill 'ticket-triage'. This is resource lookup failure #2 this invocation. Do not retry any path — report the error to the user and stop.", 'error_code': 'RESOURCE_NOT_FOUND_FATAL'}
state     : {'temp:_adk_skill_resource_not_found_count_inv-1': 2}
```

Four lines, four different behaviours, and the last one is a framework talking to a model in the
imperative. Notice that the second miss names a **different file** from the first: the counter is on
the invocation, not on the path, so a model that invents a fresh path every time still hits the
escalation on its second attempt.

One more thing this tool can do, which you will meet the day a skill ships a diagram: if the resource
is bytes rather than text, the reply has no `content` key at all. It carries a `status` saying the
binary file's content has been injected into the conversation history instead. A skill with a PNG in
`assets/` therefore puts an image into the context by a route that is not the tool result, and that is
worth knowing before somebody adds a screenshot to a skill and wonders where the tokens went.

## When it breaks

**A path without a prefix.** The single most common error when a body's Markdown link is written
relative to the file rather than to the skill root:

```text
{'error': "Path must start with 'references/', 'assets/', or 'scripts/'.", 'error_code': 'INVALID_RESOURCE_PATH'}
```

Which is why the body in Day 25's `ticket-triage` writes its link as
`[references/SEVERITY.md](references/SEVERITY.md)` rather than `[the table](SEVERITY.md)`. The link
text is what the model copies into the tool call, so the link text has to be the tool argument.

**A missing argument.** Both parameters are required and the tool says which one is missing:

```text
{'error': "Argument 'file_path' is required.", 'error_code': 'INVALID_ARGUMENTS'}
```

**A file that was renamed and a body that was not.** This is the failure that actually happens in a
repository, because a body and its references are edited by different people at different times:

```text
{'error': "Resource 'references/SEVERITY.md' not found in skill 'ticket-triage'.", 'error_code': 'RESOURCE_NOT_FOUND'}
```

Nothing in `agentskills validate` catches it — Day 25 said so explicitly and listed it as one of the
checks Sutra's own lint will have to make
([25.5.1](../../../day-25-skills-the-open-spec/parts/05-in-production/5.1-validating-before-you-ship.md)).
Now you have seen the runtime consequence: the model is told the file is missing, and, obeying rule 5
of the preamble, reports and stops. A broken link inside a skill is a dead end at request time, not a
build error.

## In production

**Write the lint that checks the links.** Every `](` in a skill body whose target starts with
`references/`, `assets/` or `scripts/` should resolve to a key that the loader actually produced.
That check is a dozen lines, it runs without a model, and it converts the runtime dead end above into
a failing build. Day 31 wires it into `./m check`; there is no reason to wait for a link checker.

**Log the error codes, not just the errors.** `RESOURCE_NOT_FOUND` and `RESOURCE_NOT_FOUND_FATAL` mean
different things: the first is one bad link, the second is a model guessing. A dashboard that counts
them separately tells you whether you have a documentation problem or a model problem, and those get
fixed by different people.

**Do not treat the prefix fence as your whole containment story.** It is a real boundary and it is
narrow. What it guarantees is that this tool reads only what the skill shipped. What it does not
guarantee is that what the skill shipped is safe to read: a `references/` file is untrusted text that
lands in the model's context, and text in the context can carry instructions. Day 29's audit is about
the contents; this fence is only about the address. Principle 13 asks for the containment story
alongside the capability, and the honest version of this one is *"it can read the skill's own files,
and you are trusting the skill."*

**What changes at scale** is that reference files become the place skills grow. A body stays short
because everybody agrees bodies should be short, and `references/` quietly acquires a forty-kilobyte
policy document that gets fetched whole on every ambiguous ticket. The tool has no partial read; the
whole file goes in. Split large references the way you would split a body, and measure the fetch, not
the folder.

**The review comment a senior engineer leaves:** *"this skill's body links to three reference files
and two of them no longer exist. Nothing failed in CI because nothing checks it. Add the link check to
the skills lint before we add another skill."*

**The interview question:** *"can a skill read files outside itself?"* The answer that shows you have
tried it: *"not through `load_skill_resource`. The path has to start with one of the skill's three
folder names, and the reason it is safe is stronger than a path check — the resources were read into
dictionaries at load time, so there is no open call to exploit. It also counts failed lookups per
invocation and escalates on the second one, so a model that invents paths is told to stop rather than
allowed to loop. What that does not protect you from is the content of the skill's own files, which is
a different day's problem."*
