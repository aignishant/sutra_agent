# 2.5 — `run_skill_script`: the rung that ships switched off

## One-line answer

The fourth tool is declared to the model, appears in every skills-enabled agent, and refuses to do
anything — `NO_CODE_EXECUTOR` — until you deliberately attach a code executor or an environment, which
is the containment story arriving with the capability instead of after it.

## The story

The flat you have just rented has a gas point in the kitchen and a metal cap screwed onto it.

The pipe is there. The kitchen was built expecting a stove. But the cap is on, and it stays on until
somebody from the gas company comes, checks the fitting, and signs a form with your name on it. Until
then you can turn any knob you like and nothing happens, because there is nothing behind the cap.

That is not a broken kitchen. It is a kitchen where the dangerous thing requires an appointment. The
day you want a stove you make the appointment, somebody qualified looks at the pipe, and the
responsibility for what happens next is written down against a name.

## The idea in plain language

Rung 4. `run_skill_script` executes a file from a skill's `scripts/` folder.

Its declaration is generous: `skill_name` and `file_path` are required, and it also accepts `args` —
either an object of long options or a plain list of strings — plus `short_options` and
`positional_args`. That is a tool designed for a model to drive a command-line program.

And out of the box it does nothing at all:

```text
{'error': 'Neither Environment nor CodeExecutor is configured. An environment or code executor is required to run scripts.', 'error_code': 'NO_CODE_EXECUTOR'}
```

There are two ways to lift the cap, and they are different shapes:

**A code executor.** The `code_executor=` argument on `SkillToolset`, or the agent's own
`code_executor` — the toolset falls back to the agent's if its own is unset. Day 16 met these objects
in full and drew the line Sutra now lives behind
([16.6.1](../../../day-16-built-in-tools-with-brakes/parts/06-blast-radius/6.1-the-executor-that-runs-it-here.md)):
`UnsafeLocalCodeExecutor` runs code in **this** process, with your keys and your repository.

**An environment.** The `environment=` argument, which is a separate machine or container with a
filesystem of its own. Hand the toolset one and the behaviour changes shape: the skill's resources are
written into the environment's `skills/<name>/` folder the first time a script is needed, and the
tool then requires a `command` argument rather than building the invocation for you. That is the
design intended for real use, and it is exactly the sandbox Day 16 spelled out
([16.6.2](../../../day-16-built-in-tools-with-brakes/parts/06-blast-radius/6.2-what-a-sandbox-has-to-be.md)).

Both are opt-in, and neither is configured by default. There is a third rule tucked in the
constructor: `script_timeout` defaults to 300 seconds for shell execution, and — read from the
docstring on 2026-09-04 — **does not apply** to Python scripts executed through a code executor's
`exec()` path. A timeout that covers one of two execution routes is a timeout you should not assume
protects you.

Sutra does not lift the cap today. Nothing in this day's build configures an executor or an
environment, and the `NO_CODE_EXECUTOR` result is the observation, not a problem to fix.

## Why Sutra needs it

Because Principle 13 says every new power arrives with its containment story, and this is a power that
arrived while you were reading about something else.

The moment an agent gets a `SkillToolset`, it has a tool whose name is `run_skill_script`. It is in
the tool declarations. The model can call it. That is a capability you did not ask for and would not
have found without looking, and the only reason it is harmless today is that somebody else decided the
default. Knowing *why* it is harmless — and what one keyword argument would change — is the difference
between a system that is safe and a system that is safe by accident.

It also sets up Day 29 precisely. Day 25 already flagged that `scripts/` is the part of a skill you
cannot audit by reading the `SKILL.md`
([25.3.2](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.2-scripts-references-assets.md)).
Now you know the runtime consequence: a downloaded skill's scripts are inert in Sutra's current
configuration, and one constructor argument makes them live.

There is one distinction worth drawing carefully, because it decides how SEC-01 applies here. Day 16's
rule is *model-generated code never runs in a process that holds our credentials*
([16.6.3](../../../day-16-built-in-tools-with-brakes/parts/06-blast-radius/6.3-the-rule-sutra-writes-down.md)).
A skill's script is **not** model-generated — a person wrote it and committed it. So SEC-01 does not
forbid running it. What it does not cover is the case Day 29 is about: a script written by a person
you have never met, in a folder somebody added to `skills/` last Thursday. That is not model-generated
either, and it is not reviewed. The rule Sutra will need is the neighbouring one, and today is the day
to notice that it does not exist yet.

## The mechanism

The double needs one more member for this tool, and the member is an underscore.

```python
# days/day-26-loading-skills-into-adk/lab/rung_four.py
"""Probe the fourth tool: its schema, its refusal, and its miss counter."""

import asyncio
import pathlib

from fake_skill_context import FakeSkillContext
from google.adk.skills import load_skill_from_dir
from google.adk.tools import skill_toolset

SHELF = pathlib.Path("days/day-26-loading-skills-into-adk/lab/skills")


class NoExecutorAgent:
    """The one attribute run_skill_script looks for on the agent."""

    code_executor = None


class InvocationContextDouble:
    """Stands in for the private context object the script tool reaches through."""

    agent = NoExecutorAgent()


async def main() -> None:
    """One real script with no executor, then two scripts that do not exist."""
    skill = load_skill_from_dir(SHELF / "ticket-triage")
    toolset = skill_toolset.SkillToolset(skills=[skill])
    run = {tool.name: tool for tool in await toolset.get_tools()}["run_skill_script"]

    context = FakeSkillContext()
    context._invocation_context = InvocationContextDouble()

    schema = run._get_declaration().parameters_json_schema
    print("accepts  :", sorted(schema["properties"]))
    print("required :", schema["required"])

    async def ask(file_path: str) -> object:
        """One call, with the skill name filled in."""
        return await run.run_async(
            args={"skill_name": "ticket-triage", "file_path": file_path},
            tool_context=context,
        )

    print("real     :", await ask("scripts/severity_table.py"))
    print("missing 1:", await ask("scripts/a.py"))
    print("missing 2:", await ask("scripts/b.py"))
    print("state    :", context.state)


asyncio.run(main())
```

**Line by line:**

- `NoExecutorAgent` exists because of one line in ADK: when the toolset has no executor of its own, it
  looks at `tool_context._invocation_context.agent.code_executor`. The double therefore needs an agent
  with that attribute, set to `None` — which is what a real agent with no executor has.
- `context._invocation_context = ...` assigns to a **private** attribute, and the underscore is the
  point. Day 23's rule was that a double declares what the code under test touches
  ([23.3.2](../../../day-23-testing-tools-and-callbacks/parts/03-testing-tools/3.2-the-fake-tool-context.md)),
  and here the code under test touches a private member. That is a signal, not a defeat: a test that
  reaches through an underscore is a test that will break on an upgrade, and it should carry a comment
  saying so. This one is a probe rather than a test, which is why it is in the lab and not in `tests/`.
- `run._get_declaration()` reads the tool's own JSON schema — the same object the model receives. It is
  underscore-private too, and it is read here for the same reason: to state a fact about the tool
  rather than repeat a claim from a page.
- Three calls with the same `context`, so the miss counter accumulates — the identical mechanism to
  [2.4](2.4-the-third-rung-and-its-fence.md), under a different state key.
- The first call names a script that **does exist**, so the refusal you see is about execution and not
  about lookup. Ordering that call first is deliberate: the two failures are easy to confuse.
- **Zero model calls**, and nothing is executed.

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/rung_four.py
```

**Line by line:**

- Needs no key. Nothing here reaches a provider or a shell.

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text
accepts  : ['args', 'file_path', 'positional_args', 'short_options', 'skill_name']
required : ['skill_name', 'file_path']
real     : {'error': 'Neither Environment nor CodeExecutor is configured. An environment or code executor is required to run scripts.', 'error_code': 'NO_CODE_EXECUTOR'}
missing 1: {'error': "Script 'scripts/a.py' not found in skill 'ticket-triage'.", 'error_code': 'SCRIPT_NOT_FOUND'}
missing 2: {'error': "Script 'scripts/b.py' not found in skill 'ticket-triage'. This is script lookup failure #2 this invocation. Do not retry any script path — report the error to the user and stop.", 'error_code': 'SCRIPT_NOT_FOUND_FATAL'}
state    : {'temp:_adk_skill_script_not_found_count_inv-1': 2}
```

Five accepted arguments, two of them required, and a tool that will not run anything. The lookup
happens **before** the executor check, which is why a missing script reports as missing rather than as
unconfigured — worth knowing when you are reading somebody else's log.

## When it breaks

**The refusal read as a bug.** `NO_CODE_EXECUTOR` looks like something to fix, and the fix that comes
to hand first is `code_executor=UnsafeLocalCodeExecutor()`, because it is the one that needs no
infrastructure. That single line hands a skill's scripts your process, your environment variables and
your repository. Day 16 spent a whole section on why
([16.6.1](../../../day-16-built-in-tools-with-brakes/parts/06-blast-radius/6.1-the-executor-that-runs-it-here.md)),
and the reason it belongs here too is that the prompt to do it arrives inside an error message.

**The environment configured without a folder.** `skills_folder=` is only meaningful alongside an
environment, and the constructor says so rather than ignoring you:

```text
ValueError: Cannot specify skills_folder without an environment
```

Behind that one, reachable only once an environment is attached, the constructor also insists the path
be absolute — read from its source on 2026-09-04 rather than run, because Sutra attaches no
environment today:

```text
ValueError: `skills_folder` must be an absolute path: 'skills'
```

Both are refusals at construction time, on your machine, which is where you want configuration
mistakes to land.

**The missing member on the double.** Drop `_invocation_context` and the tool reaches for it:

```text
AttributeError: 'FakeSkillContext' object has no attribute '_invocation_context'
```

The message names your class, so it is legible. It is also a reminder that this particular tool is the
only one of the four that goes through a private attribute, which is exactly the kind of coupling that
does not survive a framework upgrade quietly.

## In production

**Write the rule down before you need it.** Day 16 wrote SEC-01 on a day when obeying it cost nothing,
and the argument was that a rule written when it is easy is available when it is not
([16.6.3](../../../day-16-built-in-tools-with-brakes/parts/06-blast-radius/6.3-the-rule-sutra-writes-down.md)).
Today is that day for skills, and the rule has a shape: *a skill script runs only if the skill is
first-party or audited, and only in an environment, never in the agent's process.* Write it in the
same place SEC-01 lives, and it will be there on the afternoon somebody wants a skill that generates a
chart.

**Assume the tool is visible to the model even when it is disabled.** The declaration is sent whether
or not an executor exists, which means a model can call it, get `NO_CODE_EXECUTOR`, and try something
else — and a model that has been told scripts exist may write worse answers when it cannot run them.
If you are certain you will never execute a skill script, remove the tool with the toolset's
`tool_filter` rather than relying on the refusal. That is the same filter Day 15 met on toolsets
([15.3.1](../../../day-15-toolsets-and-openapi/parts/03-the-filter/3.1-a-filter-you-have-to-apply-yourself.md)),
and applying it here is a two-line decision that removes both a capability and a token cost.

**The timeout does not cover everything.** 300 seconds by default, applied to shell execution through
`subprocess.run`, and not applied to Python executed through a code executor's `exec()`. A skill
script with an infinite loop in the un-timed path is a hung invocation. If you ever enable this,
enable it with an environment, where the timeout is real.

**What changes at scale** is that skills arrive from more places than you can read. Ten first-party
skills can each be reviewed by a person who cares. A hundred, half of them from a registry, cannot.
The decision that has to be made once — and made structurally rather than per skill — is whether
script execution is available at all, and the honest default for most systems is that it is not.

**The review comment a senior engineer leaves:** *"we do not run skill scripts, so filter
`run_skill_script` out of the toolset. Right now the model can see a tool it will always be refused
by, and we are paying for its declaration on every request."*

**The interview question:** *"what stops a skill from running arbitrary code on your server?"* The
answer that shows you have read it rather than assumed it: *"nothing in the skill — it is the client's
configuration. ADK ships `run_skill_script` disabled: with no code executor and no environment it
returns `NO_CODE_EXECUTOR` and does nothing. Enabling it is one constructor argument, and the easy
argument is the unsafe one that runs code in your own process. We have a written rule that scripts run
only in an environment and only for skills we have audited, and if we are not going to run them we
filter the tool out rather than relying on the refusal."*
