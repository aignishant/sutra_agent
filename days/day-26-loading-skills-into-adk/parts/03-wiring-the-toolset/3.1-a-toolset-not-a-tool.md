# 3.1 — A toolset, not a tool: wiring `SkillToolset` into an agent

## One-line answer

`SkillToolset` goes into `Agent(tools=[...])` as a single entry, and that one entry contributes four
tools and rewrites your system instruction — which is why it is a **toolset** and not a tool.

## The story

The child goes to school with one bag.

You do not hand over four books at the door, count them, and hope they arrive in the right order. You
hand over the bag. Inside it are the four books, the water bottle and the note for the class teacher,
and the bag is the thing that gets picked up, carried, put down and picked up again.

The reason it works is that the bag knows what is in it. On Wednesday it has the drawing folder as
well, and nobody at the door has to be told. What is handed over stays one object; what is inside is
allowed to change.

The day it goes wrong is the day two people pack the same bag and both put in a water bottle.

## The idea in plain language

Day 15 introduced the distinction and Sutra has been living with it since
([15.1.1](../../../day-15-toolsets-and-openapi/parts/01-crate-not-list/1.1-one-line-many-tools.md)): a
**tool** is one callable the model can invoke; a **toolset** is one object that *contributes several
tools* when the runtime asks it to. `SkillToolset` is the second kind, and it is a
`BaseToolset` in the ordinary way — Day 15's one required method, `get_tools`, is the same method
[2.2](../02-the-four-tools/2.2-the-index-is-a-tool-call.md) called by hand.

So the wiring is one line:

```python
agent = Agent(model=..., name=..., instruction=..., tools=[toolset])
```

**Line by line:**

- `tools=[toolset]` is the whole integration. Not `tools=toolset.get_tools()`, not a registration call
  somewhere else — the toolset object itself goes in the list, and ADK asks it for its tools when it
  needs them.
- The three `...` are filled in properly in **The mechanism** below. They are elided here so that the
  one argument this part is about is the only thing on the line.

`tools=` takes a mixed list. A bare function, a `FunctionTool`, a toolset — ADK sorts them out. Sutra
has been passing plain functions since Day 10
([10.1.1](../../../day-10-function-tools/parts/01-the-form-fills-itself/1.1-the-declaration-you-no-longer-write.md)),
and adding a toolset alongside them changes nothing about how they are declared.

What the toolset contributes is now fully known, and it is worth writing out as one list because this
is the moment all of it lands on one agent:

1. `list_skills`, `load_skill`, `load_skill_resource`, `run_skill_script` — four tool declarations, in
   the request's tool menu, on every request.
2. 479 tokens of preamble in the system instruction, on every request
   ([2.1](../02-the-four-tools/2.1-the-preamble-you-did-not-write.md)).
3. Whatever `additional_tools` resolves to, which is **conditional** and is
   [3.2](3.2-tools-that-appear-after-activation.md).

Two of those three are unconditional costs of the line you just wrote. That is the honest accounting,
and it is the reason this part exists rather than being a footnote: attaching a toolset is not a
neutral act, and "one line" is a statement about typing rather than about cost.

One more property, inherited from `BaseToolset` and worth remembering: `get_tools` is **asked**, not
read. ADK calls it, and it can return a different list each time — which Day 15 flagged as the thing
that makes a toolset more than a list
([15.2.2](../../../day-15-toolsets-and-openapi/parts/02-when-asked/2.2-asked-once-a-run.md)). Nothing
in this part uses that. The next part is entirely about it.

## Why Sutra needs it

Because this is the line that ends Day 25's cliffhanger: the binder is finally handed to somebody who
can read it.

Until now Sutra's desk agent has had tools and an instruction and nothing else. Everything it knows
about *how to do a job* has been in the instruction string, paid for on every request, and edited by
whoever edits Python. After this line, the procedure is a folder, the folder is on a shelf, and the
agent has four tools for reaching it.

It also matters that this is the **whole** integration. There is no registration step, no plugin, no
change to the runner, and no change to the session service. That is the payoff of the format being
client-agnostic: ADK's support for it is one toolset class, and swapping ADK for another client that
reads the same format would leave `skills/` untouched.

## The mechanism

The agent, assembled.

```python
# days/day-26-loading-skills-into-adk/lab/desk_with_skills.py
"""Assemble a desk agent whose shelf is a folder, and show what it was given."""

import asyncio
import pathlib

from google.adk.agents import Agent
from google.adk.skills import load_skills_from_dir
from google.adk.tools import skill_toolset

MODEL = "gemini-3.7-flash"
SHELF = pathlib.Path("days/day-26-loading-skills-into-adk/lab/skills")

INSTRUCTION = (
    "You are Sutra's support desk. "
    "Answer the engineer's question about a ticket. "
    "If a skill matches the task, follow it exactly."
)


def build_agent() -> Agent:
    """Build the desk agent with every skill on the shelf available to it."""
    toolset = skill_toolset.SkillToolset(skills=load_skills_from_dir(SHELF))
    return Agent(model=MODEL, name="desk", instruction=INSTRUCTION, tools=[toolset])


async def main() -> None:
    """Print what the agent will be given, without asking a model anything."""
    agent = build_agent()
    tools = await agent.canonical_tools()
    print("agent      :", agent.name)
    print("model      :", agent.model)
    print("tool count :", len(tools))
    for tool in sorted(tools, key=lambda t: t.name):
        print(f"  - {tool.name}")


asyncio.run(main())
```

**Line by line:**

- `Agent` from `google.adk.agents` is the import Sutra has used since Day 5, and it is the 2.x name.
  Anything on the internet that says `from google.adk import Agent` with a 1.x example around it is a
  1.x example.
- `MODEL = "gemini-3.7-flash"` is the one pinned free-tier model string, recorded in
  `docs/PACKAGES.md` with the date it was verified. Addendum 02's rule is that model names are looked
  up and never remembered, and this one has a dated row.
- `load_skills_from_dir(SHELF)` puts the whole folder on the shelf in one call
  ([1.4](../01-loading-a-folder/1.4-the-whole-shelf.md)) — with the all-or-nothing behaviour that part
  documented, which [4.1](../04-failure-lab/4.1-one-bad-folder.md) then makes you deal with properly.
- `tools=[toolset]` — a **list with one element**, and that element is not a callable. This is the line
  the part is about.
- The instruction is three short sentences. It stays short on purpose: the procedure now lives in the
  skill, and Day 6's argument that every line of the handbook is a tax
  ([6.1.5](../../../day-06-instructions-and-personas/parts/01-writing-the-handbook/1.5-every-line-is-a-tax.md))
  applies with more force once 479 tokens of framework preamble are landing in the same field.
- Note the last sentence of the instruction: *"if a skill matches the task, follow it exactly."* It
  agrees with the preamble rather than contradicting it, which is deliberate — a handbook that says
  "do not use tools unless asked" beside a preamble that says "you MUST use the skill tools" is a
  contradiction, and Day 6 showed that a contradiction produces variance rather than an error
  ([6.1.4](../../../day-06-instructions-and-personas/parts/01-writing-the-handbook/1.4-contradictions-are-randomised-behaviour.md)).
- `agent.canonical_tools()` is ADK's own resolution of the `tools=` list into actual tools — it expands
  toolsets, wraps bare functions, and hands back what the model will be shown. Calling it is how you
  check your wiring **before** spending a request.
- `build_agent()` is a function rather than module-level code so that importing this file does nothing.
  That has been the house rule since Day 5, and it is what makes the same file usable from a test.

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/desk_with_skills.py
```

**Line by line:**

- **Zero model calls.** `canonical_tools()` resolves the toolset locally.

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text

tool count : 4
  - list_skills
  - load_skill
  - load_skill_resource
  - run_skill_script
```

One entry in `tools=`, four tools on the agent. That is the whole claim of this part, and everything
after it is about the fifth and sixth tools that are not there yet.

## When it breaks

**The daily quota, in the middle of a run.** Asking this agent a real question is the day's eval, and
on the afternoon this part was written the twenty free generations were already spent. ADK's own
exception type carries the provider's body through:

```text
google.adk.models.google_llm._ResourceExhaustedError:
On how to mitigate this issue, please refer to:

https://google.github.io/adk-docs/agents/models/google-gemini/#error-code-429-resource_exhausted

429 RESOURCE_EXHAUSTED. {'error': {'code': 429, 'message': 'You exceeded your current quota, please check your plan and billing details. ... Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests, limit: 20, model: gemini-3.7-flash\nPlease retry in 8.061283385s.', 'status': 'RESOURCE_EXHAUSTED', 'details': [... {'@type': 'type.googleapis.com/google.rpc.QuotaFailure', 'violations': [{'quotaMetric': 'generativelanguage.googleapis.com/generate_content_free_tier_requests', 'quotaId': 'GenerateRequestsPerDayPerProjectPerModel-FreeTier', 'quotaDimensions': {'location': 'global', 'model': 'gemini-3.7-flash'}, 'quotaValue': '20'}]}]}}
```

Two things in that body are worth reading rather than skipping. `quotaId` ends in
**`PerDayPerProjectPerModel`**, which is the per-day ceiling Day 24 identified by reading a live
refusal
([24.2.2](../../../day-24-token-accounting-and-budgets/parts/02-two-ceilings/2.2-reading-the-ceiling-off-a-refusal.md)),
and `Please retry in 8.061283385s` is the hint Day 24 proved is **not** a window reset — waiting eight
seconds and retrying is refused again. Day 21's ladder is what handles this properly
([21.3.1](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.1-which-429-is-it.md)).

**Because that quota was spent, this document does not contain a pasted event stream.** Inventing one
would be undetectable and would break Principle 10, so the live run is the day's eval instead: the hub
§5 gives the exact command, and what you should see is a `list_skills` call, then a `load_skill` call,
then the answer. Run it and paste your own transcript into your notes.

**A toolset passed as a function.** `tools=[toolset.get_tools]` is a natural slip and produces a tool
called `get_tools` that the model can call and that returns tools:

```text
tool count : 1
  - get_tools
```

No exception. Read the output of `canonical_tools()` rather than trusting the line you wrote.

**Two toolsets contributing the same name.** Two `SkillToolset` instances on one agent both contribute
`list_skills`. Day 15 met this as two crates with one name
([15.2.3](../../../day-15-toolsets-and-openapi/parts/02-when-asked/2.3-two-crates-one-name.md)), and the
fix is the same: `tool_name_prefix=` on one of them. Note the prefix also rewrites the preamble, which
grows by a few tokens for every prefixed tool name it mentions — measured at 2054 characters
unprefixed and 2089 with `tool_name_prefix="desk"`.

## In production

**Check `canonical_tools()` in a test.** One assertion — the agent has exactly these tool names — costs
nothing to run and catches three real problems: a toolset that failed to load, a name collision, and a
framework upgrade that added a fifth tool you did not ask for. Day 15 made the same argument about
toolsets in general
([15.7.2](../../../day-15-toolsets-and-openapi/parts/07-in-production/7.2-testing-a-toolset-without-a-model.md));
the reason to repeat it here is that a skills toolset's contribution is the one most likely to change
under you, because the feature is experimental.

**Build the agent in a function, and build it once.** Every call to `build_agent()` re-walks the shelf
([1.1](../01-loading-a-folder/1.1-load-skill-from-dir.md)). In a service, build the agent at startup and
keep it; if you need skills to change without a restart, `clone_with_updated_skills` on the toolset
exists for exactly that, and it copies the rest of the configuration for you.

**Keep the agent's own instruction in agreement with the preamble.** You cannot edit the preamble, so
the only lever is yours. Read it once, then read your instruction next to it and remove anything that
argues with it. This is a five-minute exercise that prevents a class of bug which presents as "the
model sometimes ignores skills" and is very hard to diagnose from the outside.

**What changes at scale** is that `tools=[...]` becomes a list of toolsets rather than a list of
functions, and nobody can tell you what the agent can do by reading it. The answer is to print
`canonical_tools()` at startup into the structured log
([22.2.1](../../../day-22-structured-logging/parts/02-wiring-the-run/2.1-one-line-per-happening.md)), so
that the question "what tools did this deployment actually have?" is answered by a log line rather than
by reconstructing an import graph.

**The review comment a senior engineer leaves:** *"`tools=[toolset]` reads like one tool and is six.
Add the `canonical_tools()` assertion to the test file so the count is written down somewhere, and log
it at startup."*

**The interview question:** *"what is the difference between a tool and a toolset in ADK?"* The answer
that shows you have wired one: *"a tool is one callable; a toolset is one object that contributes
several tools when the runtime asks, through `get_tools`. `SkillToolset` is the clearest example —
one entry in `tools=` gives the agent four tool declarations and also appends about 480 tokens to the
system instruction through `process_llm_request`. So a toolset is not just packaging: it can change
the request as well as the tool menu, and you should check what it actually contributed rather than
counting the entries you wrote."*
