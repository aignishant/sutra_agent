# 3.3 — Activation is a line in session state

## One-line answer

`load_skill` writes `_adk_activated_skill_<agent_name>` into session state, so "this skill is active"
is a durable, readable, per-agent fact — and the same session state also carries two `temp:` counters
you did not put there.

## The story

The register at the front desk has your name in it and a badge number beside it.

You signed in, they gave you a plastic badge on a lanyard, and the register now has a line: name, who
you are visiting, time in. The badge itself says almost nothing — a number, the word VISITOR. All the
meaning is in the register.

That line is why the security guard on the third floor lets you through without a conversation, and it
is why, when somebody asks at six o'clock whether everyone has left the building, there is an answer.
It is also why, if you walk out without signing back in, the line is still there tomorrow morning
saying you are inside.

The badge is what you carry. The register is what the building knows.

## The idea in plain language

[2.3](../02-the-four-tools/2.3-what-activation-actually-costs.md) printed the state dictionary after a
`load_skill` call and one key had appeared:

```text
{'_adk_activated_skill_desk': ['ticket-triage']}
```

That line is the register. `load_skill` writes it every time a skill is loaded, appending the skill's
name to a list if it is not there already, and it is what
[3.2](3.2-tools-that-appear-after-activation.md) reads to decide which extra tools to hand over.

Four things about it are worth being exact about, and Day 17 gave you the vocabulary for all four
([17.2.1](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.1-the-prefix-is-the-lifetime.md)).

**It has no prefix, so it is session-scoped.** Not `temp:`, not `user:`, not `app:`. It lives as long
as the conversation does and is written to the session service, which means it survives across turns
and is visible to anything that can read the session.

**The key ends in the agent's name.** `_adk_activated_skill_desk` for an agent called `desk`. In a
multi-agent system each agent keeps its own register, so a skill activated by a triage sub-agent does
not silently grant tools to the agent that delegated to it. That is a good decision and an easy one to
miss.

**It is a list, and it only grows.** There is no deactivation. Once a skill is loaded in a
conversation, it stays in the list until the session ends. That matches what actually happened: the
body is in the context and cannot be taken out
([25.3.1](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.1-the-body-is-loaded-whole.md)),
so the tools that go with it staying available is consistent rather than sloppy.

**The leading underscore is a convention, not a mechanism.** ADK is telling you *do not write this
yourself*. Nothing stops you. Which is exactly why Day 17's advice to declare a schema for state
([17.5.1](../../../day-17-state-scopes-and-lifetimes/parts/05-a-schema-for-state/5.1-declaring-the-boxes.md))
now needs a footnote: your schema describes the boxes you chose, and the framework has quietly added
three of its own.

The other two are the invocation-scoped counters from
[2.4](../02-the-four-tools/2.4-the-third-rung-and-its-fence.md) and
[2.5](../02-the-four-tools/2.5-the-rung-that-ships-switched-off.md):

| Key | Scope | Written by | Meaning |
| --- | --- | --- | --- |
| `_adk_activated_skill_<agent>` | session | `load_skill` | which skills are live in this conversation |
| `temp:_adk_skill_resource_not_found_count_<invocation>` | invocation | `load_skill_resource` | failed resource lookups this invocation |
| `temp:_adk_skill_script_not_found_count_<invocation>` | invocation | `run_skill_script` | failed script lookups this invocation |

Two lifetimes, chosen deliberately: the register outlives the turn because the knowledge does; the
miss counters die with the invocation because a model's confusion should not follow it into the next
question.

## Why Sutra needs it

Because this is the answer to *"did the skill actually fire?"*, and until now Sutra has had no answer
that did not involve reading a transcript.

Day 17 argued that state is a trace as well as a store
([17.7.3](../../../day-17-state-scopes-and-lifetimes/parts/07-in-production/7.3-state-as-a-trace.md)),
and this is the clearest example yet. A session whose state contains
`_adk_activated_skill_desk: ["ticket-triage"]` is a session where the procedure was loaded. A session
where that key is absent is a session where the desk improvised. That is a **queryable** distinction,
after the fact, with no logging in place at all — and Day 25's build brief already asked for a `skill`
field in the log line to count activations per skill. This is where that number comes from.

It also matters for Day 30's tests. A test that asserts "the skill was used" does not need to inspect
the model's words; it can assert on this key. That is the difference between a test of behaviour and a
test of prose, and only one of them stays green when the wording changes.

## The mechanism

Activate a skill by hand and watch the register fill in, then read it back the way a test would.

```python
# days/day-26-loading-skills-into-adk/lab/the_register.py
"""Activate two skills through the real tool and read the state key afterwards."""

import asyncio
import pathlib

from fake_skill_context import FakeSkillContext
from google.adk.skills import load_skills_from_dir
from google.adk.tools import skill_toolset

SHELF = pathlib.Path("days/day-26-loading-skills-into-adk/lab/skills")


def activated_skills(state: dict, agent_name: str) -> list[str]:
    """The skills this agent has loaded in this session, or an empty list."""
    return list(state.get(f"_adk_activated_skill_{agent_name}") or [])


async def main() -> None:
    """Load one skill twice and another once, then read the register."""
    toolset = skill_toolset.SkillToolset(skills=load_skills_from_dir(SHELF))
    load = {tool.name: tool for tool in await toolset.get_tools()}["load_skill"]
    context = FakeSkillContext(agent_name="desk")

    print("before      :", activated_skills(context.state, "desk"))

    for name in ("ticket-triage", "ticket-triage", "vague-description"):
        await load.run_async(args={"skill_name": name}, tool_context=context)
        print(f"after {name:18}:", activated_skills(context.state, "desk"))

    print("raw state   :", context.state)
    print("other agent :", activated_skills(context.state, "billing"))


asyncio.run(main())
```

**Line by line:**

- `activated_skills()` is written as a named helper rather than inlined because it is the function
  Sutra will actually keep. It is the read half of this mechanism, and it belongs somewhere both the
  logger and the tests can import.
- `state.get(key) or []` handles two cases in one expression: the key is absent, and the key is present
  but empty. `state.get(key, [])` would only handle the first, and an empty list stored by something
  else would then leak through as the same value — harmless here, and the habit is what matters.
- `list(...)` **copies**. Handing out the framework's own list would let a caller append to ADK's
  state by accident, which is the class of bug that takes a day to find.
- The loop loads `ticket-triage` **twice** on purpose. The second load costs another 334 tokens
  ([2.3](../02-the-four-tools/2.3-what-activation-actually-costs.md)) and adds nothing to the register,
  which is the observation this part contributes to the cost story.
- `FakeSkillContext(agent_name="desk")` names the agent explicitly rather than leaning on the default,
  because the last line is about the name being part of the key.
- `activated_skills(context.state, "billing")` reads the register for an agent that never ran, and gets
  an empty list rather than an error — which is what makes the per-agent key safe to read anywhere.
- **Zero model calls.**

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/the_register.py
```

**Line by line:**

- Needs no key.

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text
before      : []
after ticket-triage     : ['ticket-triage']
after ticket-triage     : ['ticket-triage']
after vague-description : ['ticket-triage', 'vague-description']
raw state   : {'_adk_activated_skill_desk': ['ticket-triage', 'vague-description']}
other agent : []
```

The second load left the register unchanged and spent the tokens anyway. That is the cheapest
demonstration you will get of why "was it already activated?" is a question worth asking in a callback.

## When it breaks

**Nobody wrote the key, so nothing appeared.** If `_adk_activated_skill_<agent>` is absent at the end
of a conversation, no skill was ever loaded. The failure is upstream — the model never called
`load_skill` — and [4.3](../04-failure-lab/4.3-the-manual-nobody-opened.md) is about why. What this
part contributes is that the *absence of a key* is the cheapest possible detector, and it needs no
event stream.

**The wrong agent name.** Reading `_adk_activated_skill_desk` in a system whose agent is called
`support_desk` returns an empty list forever, with no error:

```text
other agent : []
```

Build the key from `agent.name` rather than from a literal, and the mistake becomes impossible.

**A state schema that does not know about it.** Day 17's schema declares the keys Sutra expects
([17.5.1](../../../day-17-state-scopes-and-lifetimes/parts/05-a-schema-for-state/5.1-declaring-the-boxes.md)).
A strict schema that rejects unknown keys will now reject ADK's own. Day 17 already warned that the
schema does not do what people hope
([17.5.2](../../../day-17-state-scopes-and-lifetimes/parts/05-a-schema-for-state/5.2-what-the-schema-does-not-do.md));
the practical instruction today is to treat any key beginning `_adk_` as reserved and let it through.

**A session store that chokes on the key name.** Session state is serialised by whatever session
service you are using, and a leading underscore is fine for JSON and for every store Sutra will meet.
It is worth knowing the keys exist before you write a store of your own, though: three framework keys
you did not declare, one of them per agent, two of them per invocation.

## In production

**Log the register at the end of every invocation.** One field —
`"skills_activated": ["ticket-triage"]` — on the line Day 22 already writes
([22.2.1](../../../day-22-structured-logging/parts/02-wiring-the-run/2.1-one-line-per-happening.md)) is
the whole observability story for skills. It gives you activations per skill, the ratio of
conversations that used any skill at all, and the list of skills that have never once fired. That last
number is the one that pays: a skill nobody activates is pure fixed cost, and Day 25 measured what
that costs.

**Assert on it in tests instead of on wording.** *"After this conversation, `ticket-triage` is in the
register"* is a behavioural assertion that survives a rewrite of the skill's prose. *"The answer
contains the word high"* does not. Day 30 will need both kinds; this is the durable one.

**Guard against re-activation if you care about tokens.** A `before_tool_callback` on `load_skill` can
check the register and refuse a second load of a skill already in it, returning a short note instead
of 334 tokens — that is the refusal shape Day 13 built
([13.3.2](../../../day-13-callbacks-four-doors/parts/03-the-tool-doors/3.2-refusing-a-tool-call-honestly.md)).
Whether it is worth doing depends on how often it happens, which is a question the log answers first.
Do not write the guard before you have the number.

**What changes at scale** is that the register becomes the join key between your skills and everything
else you measure. Cost per conversation, satisfaction, escalation rate, latency — all of them split by
"which skills were active" once this list is in your logs, and none of them do without it. Teams that
add this field late spend a quarter unable to answer whether skills helped.

**The review comment a senior engineer leaves:** *"we have skills in production and no way to say which
ones fired. Read `_adk_activated_skill_<agent>` off the session at the end of the invocation and put it
on the log line. It is one field and it is the difference between managing this and guessing."*

**The interview question:** *"how do you know whether a skill was used?"* The answer that shows you
have looked at the session rather than at the transcript: *"ADK records it in session state under
`_adk_activated_skill_<agent_name>` — a list, per agent, session-scoped, appended by `load_skill`. So
'was the procedure followed?' is a state read rather than a text search, and it is what the toolset
itself uses to decide which extra tools to expose. We put that list on the structured log line, which
gives us activations per skill and, more usefully, the skills that never fire."*
