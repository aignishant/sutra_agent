# 1.2 — The `Skill` object: three fields, and what each one is for

## One-line answer

A loaded skill has exactly three fields — `frontmatter`, `instructions` and `resources` — and they
correspond one for one to the three rungs of progressive disclosure: what is advertised, what is
loaded on activation, and what is fetched only if asked for.

## The story

A passport is three documents stapled into one booklet, and you hand over a different part of it
depending on who is asking.

The first page has your photograph, your name and your date of birth. That is the page the hotel clerk
photocopies. It is small, it identifies you, and it is the part that gets shown most often.

Behind it are the visa pages: the stamps, the entry permissions, the conditions of your stay. Nobody
looks at those at a hotel. The immigration officer does, and reads them carefully, because that is
where the actual rules of what you may do are written.

And then there is the pocket at the back where you keep the folded printout of your return ticket and
the address of the place you are staying. Not part of the passport at all, strictly, but travelling
with it, and produced only when somebody specifically asks for it.

Three levels of detail, in one object you carry around whole, disclosed one level at a time.

## The idea in plain language

`load_skill_from_dir` hands back a `Skill`. Probe it and you find three fields and nothing else:

| Field | Type | What it holds | Which rung |
| --- | --- | --- | --- |
| `frontmatter` | `Frontmatter` | `name`, `description` and four optional fields | the card |
| `instructions` | `str` | the whole Markdown body, frontmatter stripped | the body |
| `resources` | `Resources` | `references`, `assets` and `scripts`, each a dictionary | the files |

That is the same three-level structure Day 25 measured
([25.3.3](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.3-progressive-disclosure.md)),
now expressed as Python attributes. It is worth pausing on how well those two things line up, because
it is not a coincidence: the object model was designed to match the format, so a folder that follows
the spec produces an object whose fields are the disclosure rungs.

**`frontmatter`** is a pydantic model with six declared fields: `name`, `description`, `license`,
`compatibility`, `allowed_tools` and `metadata`. The first two are required. The last one,
`metadata`, is a free dictionary, and today it stops being decoration — section 3 shows two keys ADK
reads out of it that change what the agent can do.

**`instructions`** is a plain string. Not a parsed document, not a list of steps: the body as written,
with the frontmatter removed. Whatever structure you put in the Markdown is structure the model reads,
not structure the framework understands.

**`resources`** is three dictionaries. `references` and `assets` map a relative filename to its
contents. `scripts` maps a relative filename to a small `Script` object whose `.src` is the source
text. The keys are relative to their own folder, so a file at `references/api/errors.md` has the key
`api/errors.md`.

One field name is worth memorising because the error messages use it: `skill.name` is a shortcut for
`skill.frontmatter.name`. When ADK says `Skill 'x' not found`, `x` is that value — not the folder, not
the file. The folder happens to be forced to match it (1.1), which is exactly why that rule exists.

## Why Sutra needs it

Because every remaining part of this day reads one of these three fields, and section 2 charges
different amounts for each.

The card is what section 2 puts in front of the model when it asks what is available. The
`instructions` string is what section 2 sends when the model activates the skill. The `resources`
dictionaries are what the third tool reaches into. If those three are one blur in your head, the token
measurements in section 2 will look arbitrary, and the failure lab in section 4 will look like magic.

There is also a practical reason. Day 30 tests skills, and a test that asserts on a skill asserts on
these fields: *the description mentions the word triage*, *the body names both tools*, *the reference
table has three rows*. Those are three assertions against three fields, and they can all be written
without a model, a runner or a network.

## The mechanism

Print the object one field at a time.

```python
# days/day-26-loading-skills-into-adk/lab/inspect_skill.py
"""Show the three fields of a loaded Skill, and the six frontmatter fields inside one of them."""

import pathlib

from google.adk.skills import load_skill_from_dir

SKILL_DIR = pathlib.Path("days/day-25-skills-the-open-spec/lab/skills/ticket-triage")
skill = load_skill_from_dir(SKILL_DIR)

print("--- frontmatter ---")
for field in ("name", "description", "license", "compatibility", "allowed_tools", "metadata"):
    print(f"{field:14}: {getattr(skill.frontmatter, field)!r}")

print("\n--- instructions ---")
print(f"chars         : {len(skill.instructions)}")
print(f"first line    : {skill.instructions.strip().splitlines()[0]!r}")

print("\n--- resources ---")
print(f"references    : {sorted(skill.resources.references)}")
print(f"assets        : {sorted(skill.resources.assets)}")
print(f"scripts       : {sorted(skill.resources.scripts)}")
print(f"one reference : {skill.resources.get_reference('SEVERITY.md')!r}")
```

**Line by line:**

- The tuple of six field names is written out rather than discovered, because writing them out is the
  point: these six are the whole of the frontmatter model, and a seventh does not exist. Anything else
  you put in the YAML lands in `metadata` or is refused — [1.4](1.4-the-whole-shelf.md) has the refusal.
- `getattr(skill.frontmatter, field)` reads by name so the loop can cover all six. Note the Python
  attribute is `allowed_tools` with an underscore while the YAML key is `allowed-tools` with a hyphen;
  the model declares an alias so both spellings load, and `!r` on the value is what shows you it came
  back as `None` rather than as an empty string.
- `!r` — `repr`, not `str`, everywhere. The difference matters here: `str(None)` prints `None` and so
  does a string containing the four letters. `repr` shows the quotes, so an absent field and a field
  set to the text `"None"` cannot be confused.
- `skill.instructions.strip().splitlines()[0]` — `strip()` first, because the body begins with the
  newline that followed the frontmatter's closing `---`, and without it the "first line" is empty.
- `sorted(...)` on the three dictionaries, because dictionary order is insertion order, and insertion
  order here comes from a filesystem walk. Sorting makes the output stable enough to paste into a
  document and compare against later.
- `skill.resources.get_reference('SEVERITY.md')` — the accessor rather than `references['SEVERITY.md']`.
  It returns `None` for a missing key instead of raising, which is what you want in a place where the
  filename came from a model.

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/inspect_skill.py
```

**Line by line:**

- Same working-directory rule as [1.1](1.1-load-skill-from-dir.md), for the same reason.
- **Zero model calls.** This is pure object inspection.

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text
--- frontmatter ---
name          : 'ticket-triage'
description   : "Assign a severity to a support ticket and record it, using the desk's published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear."
license       : 'Apache-2.0'

allowed_tools : None
metadata      : {'author': 'sutra-desk', 'version': '1.0'}

--- instructions ---

--- resources ---

```

Two things in that output are worth stopping on.

`allowed_tools` is `None`, and Day 25 already warned that the field is experimental and advisory
([25.2.4](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.4-the-optional-fields.md)).
Here is the harder version of that warning, read from the installed package on 2026-09-04:
**`allowed_tools` is parsed and then never read again.** Searching `google/adk/` for the name finds the
field definition, the loader's list of accepted keys, and nothing else — no check, no filter, no
enforcement anywhere in the toolset. A field that loads and does nothing is worse than a missing one,
because it looks like a control.

`metadata` came back with the two keys Day 25 put in it and no others. That dictionary is about to
matter: [3.2](../03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md) puts a key in it that
changes which tools the agent has.

## When it breaks

**A key the loader accepts and nothing ever reads.** Put `version: 2` at the top level of the
frontmatter, beside `name`, instead of inside `metadata`. There is no error at all:

```text
loaded. extra key -> 2
model_extra: {'version': 2}
```

The `Frontmatter` model is declared with `extra="allow"`, so an unrecognised key is kept in pydantic's
`model_extra` rather than refused. `skill.frontmatter.version` even works. It is also entirely inert:
no code in `google/adk/` looks at it, so the effect of adding it is that a number is carried around in
memory forever. Day 25's validator, run against exactly the same folder, is the one that objects:

```text
Validation failed for ...\extra\ticket-triage:
  - Unexpected fields in frontmatter: version. Only ['allowed-tools', 'compatibility', 'description', 'license', 'metadata', 'name'] are allowed.
```

Two tools, two verdicts, one folder. The spec validator enforces the closed list of six; ADK's loader
does not. That is the whole argument for keeping `agentskills validate` in the loop even though the
runtime is more forgiving — the forgiving one is the one that will not tell you.

**A frontmatter field that breaks its own rule.** This one does raise, and it is the shape every real
frontmatter failure takes:

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for Frontmatter
name
  Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading, trailing, or consecutive delimiters [type=value_error, input_value='Ticket--Triage', input_type=str]
    For further information visit https://errors.pydantic.dev/2.13/v/value_error
```

That is day 25's deliberately broken `bad-name` specimen, loaded through ADK rather than through the
validator. Read it from the bottom up: `input_value` is what you wrote, the line above it is the rule,
and the line above that is the field.

**An attribute that does not exist.** `skill.frontmatter.version` looks reasonable and is not a field:

```text
AttributeError: 'Frontmatter' object has no attribute 'version'
```

The version lives at `skill.frontmatter.metadata["version"]`, and it is a **string** because Day 25
quoted it. Unquoted, YAML would have read `1.10` as the float `1.1`, and the failure would have been
silent rather than an `AttributeError`.

**A reference that is not there.** `skill.resources.references["SEVERITY.MD"]` on a file actually named
`SEVERITY.md`:

```text
KeyError: 'SEVERITY.MD'
```

Windows will not save you here. The dictionary keys come from the filesystem walk, and the comparison
is an exact string match on the key, whatever the underlying filesystem thinks about case.

## In production

**Treat `frontmatter.metadata` as a namespace you share with the client.** ADK reads keys beginning
`adk_` out of it. Another client will read its own. Your own conventions — an owner, a review date, a
version — should be prefixed too, which is the advice Day 25 gave before there was a reason for it and
this is the reason. An unprefixed `version` key in a skill from a vendor pack and an unprefixed
`version` key in yours are the same key.

**The three fields are the natural unit of a skill test.** A test that loads a skill and asserts on
`frontmatter.description`, on a substring of `instructions`, and on `sorted(resources.references)` runs
in milliseconds, needs no key, and catches the three things that actually break: somebody softened the
description, somebody deleted a step, somebody moved a file. Day 30 builds this properly; the shape is
already available today.

**What changes at scale** is that `resources` becomes the field people abuse. It is a dictionary of
whole files held in memory, and it grows silently as a skill's `references/` folder grows. A hundred
skills each carrying two hundred kilobytes of reference material is twenty megabytes of resident
memory that exists so that a model can occasionally ask for one table. Measure it at startup and log
it, or the first time you find out is when the process is restarted under memory pressure.

**The review comment a senior engineer leaves:** *"you are asserting on `skill.instructions` with an
exact string. That test breaks the next time somebody fixes a typo in the skill. Assert that the body
names both tools and mentions the reference file — that is the contract; the wording is not."*

**The interview question:** *"how would you unit-test a skill?"* The answer that shows you have done
it: *"load it with `load_skill_from_dir` and assert on the three fields. The description has to carry
the trigger words, the body has to name the tools it tells the model to call, and the references it
links to have to exist as keys in `resources.references`. None of that needs a model, so it runs in
the fast suite. What it cannot tell you is whether the model will actually select it, and that needs a
different kind of check."*
