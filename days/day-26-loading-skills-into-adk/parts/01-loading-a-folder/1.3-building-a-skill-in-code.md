# 1.3 — Building a skill in code, and when that is the right call

## One-line answer

`models.Skill(frontmatter=..., instructions=..., resources=...)` builds the same object the loader
builds, without a folder — which is exactly right for a test and exactly wrong for knowledge anybody
is meant to review.

## The story

The week the babysitter is coming, there is a sheet of paper stuck to the fridge with a magnet.

Bedtime is 8:30. The inhaler is in the second drawer. Do not let the small one near the stairs after a
bath. Our number, then the neighbour's number. It is in handwriting, it is not filed anywhere, and on
Sunday evening it comes down and goes in the bin.

The family calendar hangs in the same kitchen and is a different kind of object entirely. It is
written on by everybody, it is corrected, it is consulted for months, and if somebody rubbed a week
off it there would be an argument. Nobody would ever put the babysitter's sheet on the calendar, and
nobody would ever run the household off a sheet that is thrown away on Sunday.

They are both instructions on paper in the same kitchen. The difference is not the format. It is how
long they need to live and how many people need to agree about them.

## The idea in plain language

A `Skill` does not have to come from a folder. All three of its fields are ordinary constructor
arguments, so you can build one in Python:

- **`frontmatter=models.Frontmatter(name=..., description=...)`** — the same six-field model as
  [1.2](1.2-the-skill-object.md), with the same validation. A bad name raises here exactly as it does
  when read from disk.
- **`instructions="..."`** — the body, as a string. No file, no parser.
- **`resources=models.Resources(references={...})`** — dictionaries you write by hand. Optional
  entirely: leave it out and you get three empty dictionaries.

The object is indistinguishable from a loaded one afterwards. Hand it to a `SkillToolset` and the
toolset cannot tell, because the toolset only ever reads the three fields.

So the question is never *"can I?"*. It is *"where should this knowledge live?"*, and the answer is
almost always **a folder**, for three reasons that have nothing to do with Python:

1. **A folder is reviewable.** A procedure written in a file shows up in a diff, gets a comment, and
   is approved by the person who actually knows how triage works. A procedure written as a Python
   string literal is reviewed by whoever reviews Python.
2. **A folder is portable.** The whole argument for an open format
   ([25.1.3](../../../day-25-skills-the-open-spec/parts/01-what-a-skill-is/1.3-an-open-spec.md)) is that
   another client can read it. A string in your source is readable only by your program.
3. **A folder is versioned by the repository**, and Principle 2 makes the repository the memory.

Which leaves a real, narrow set of cases for the in-code form:

- **Tests.** A test that needs a skill should not need a fixture directory, a temporary folder, or
  cleanup. Three lines build one, and the test reads top to bottom. This is Day 30's main use.
- **Generated skills.** A skill assembled from a database row, a form, or another agent's output has
  no file until you decide to write one.
- **Demonstrating a difference.** Two skills that differ only in their description, so you can watch
  which one gets chosen, are easier to build in code than to keep as two nearly-identical folders —
  which is what Day 28's design work will need.

This is Principle 4 turned around, and it is worth naming: you have built the folder by hand, so the
in-code form is a convenience rather than a shortcut past understanding. Somebody who met
`models.Skill(...)` first would not know that `name` has to match a directory, because in code there
is no directory to match.

## Why Sutra needs it

Because Day 30 tests skills, and a test suite that reads fixture folders off disk is a test suite that
breaks when somebody reorganises the folders.

Day 23 established the shape of a fast test: no network, no runner, no filesystem if you can avoid it
([23.1.2](../../../day-23-testing-tools-and-callbacks/parts/01-where-the-line-falls/1.2-fast-isolated-specific.md)).
A skill built in three lines inside the test file satisfies all three. The test that asserts *"a skill
whose description does not say when to use it is not selected"* wants two skills that differ in one
sentence, and it wants them in front of the reader's eyes, not in a `fixtures/` directory two folders
away.

Today it earns its place immediately: section 4's failure lab needs skills that are deliberately
wrong, and building them in code keeps the wrongness on the same screen as the failure it causes.

## The mechanism

The whole in-code form, and the same object built two ways.

```python
# days/day-26-loading-skills-into-adk/lab/skill_in_code.py
"""Build a Skill without a folder, and show it is the same object the loader returns."""

import pathlib

from google.adk.skills import load_skill_from_dir, models

built = models.Skill(
    frontmatter=models.Frontmatter(
        name="echo-test",
        description=(
            "A throwaway skill built in memory. Use when a test needs a skill and not a folder."
        ),
    ),
    instructions="# Echo test\n\nRepeat the user's words back, in capitals.\n",
    resources=models.Resources(references={"NOTE.md": "one line of reference text"}),
)

loaded = load_skill_from_dir(
    pathlib.Path("days/day-25-skills-the-open-spec/lab/skills/ticket-triage")
)

for skill in (built, loaded):
    print(f"{skill.name:16} {type(skill).__name__:6} refs={list(skill.resources.references)}")

bare = models.Skill(
    frontmatter=models.Frontmatter(name="bare", description="A skill with nothing but a card."),
    instructions="Do the obvious thing.",
)
print("resources when omitted:", bare.resources)
```

**Line by line:**

- `models` is imported as a module rather than by symbol, because you need three names out of it —
  `Skill`, `Frontmatter`, `Resources` — and `models.Frontmatter` at the call site says where the type
  came from. In a file that also has `google.genai.types`, that matters.
- The `description` is built by adjacent string literals across two lines. Python joins them at parse
  time, so there is no runtime cost, and it keeps the line inside the width the repository formats to
  without introducing a `\` or a `+`.
- `instructions=` takes `\n` escapes because it is a Markdown document written as a Python string. In
  a test, prefer a triple-quoted string; here the escapes keep the whole object on one screen, which
  is the point being made.
- `resources=models.Resources(references={...})` — the dictionary is keyed exactly as the loader would
  key it: **relative to `references/`**, so `NOTE.md` and not `references/NOTE.md`. A double at this
  seam that keys it differently is the kind of fake that passes and lies
  ([23.5.2](../../../day-23-testing-tools-and-callbacks/parts/05-failure-lab/5.2-the-fake-that-could-not-fail.md)).
- The loop over `(built, loaded)` is the actual claim of this part. Both are `Skill`. Nothing
  downstream branches on where they came from.
- `bare` omits `resources` entirely. That is legal, and the last line shows what you get.

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/skill_in_code.py
```

**Line by line:**

- Same working-directory rule as [1.1](1.1-load-skill-from-dir.md), because one of the two skills is
  still loaded from a relative path.
- **Zero model calls.**

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text
echo-test        Skill  refs=['NOTE.md']
ticket-triage    Skill  refs=['SEVERITY.md']
resources when omitted: references={} assets={} scripts={}
```

The validation is not skipped just because there is no file. Both of these raise:

```text
ValidationError: description
  Value error, description must be at most 1024 characters. Description length: 1100
```

```text
ValidationError: name
  Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading, trailing, or consecutive delimiters [type=value_error, input_value='ticket_triage'
```

The second one is worth a note, because the package contradicts itself about it. The docstring on
`Frontmatter` says *"Skill name in kebab-case or snake_case"*; the validator on the same class rejects
the underscore. Read on 2026-09-04 in the installed `google-adk` 2.7.1, in one file, twelve lines
apart. When a docstring and a validator disagree, believe the validator —
[5.2](../05-in-production/5.2-experimental-means-experimental.md) is the general form of that advice.

## When it breaks

**The folder rule does not apply, and that is a trap.** In code there is no directory, so nothing
checks the name against anything. A skill built as `name="ticket_triage"` fails on the underscore, but
a skill built as `name="triage"` and later written to a folder called `ticket-triage/` loads happily
in memory and fails the moment it is saved and reloaded:

```text
ValueError: Skill name 'triage' does not match directory name 'ticket-triage'.
```

The failure is in the code that writes the folder, and it appears in the code that reads it. If you
generate skills, generate the folder name from `frontmatter.name` and never the other way round.

**Two objects with the same name.** Build a skill in code with the name of a skill already loaded from
disk, hand both to one toolset, and the toolset refuses at construction time:

```text
ValueError: Duplicate skill name 'ticket-triage'.
```

This is the good failure — at wiring time, on your machine, before anything runs. Section 4 has the
one that is not.

**A body that is not a string.** `instructions=pathlib.Path("SKILL.md")` is a natural slip, and
pydantic catches it, but the message points at a type rather than at what you meant:

```text
ValidationError: instructions
  Input should be a valid string [type=string_type, input_value=WindowsPath('SKILL.md'), input_type=WindowsPath]
```

Read `input_value` first, as always: it is a path where a document should be. The fix is
`.read_text(encoding="utf-8")` — and at that point you should ask why you are not calling
`load_skill_from_dir`.

## In production

**In-code skills belong in tests and in generators, and nowhere else.** The rule that survives contact
with a real team is simple: if a non-engineer should be able to correct it, it is a file. Triage
severity thresholds, escalation wording, refund policy — those are files, and the reason they are
files is that the person who knows the answer should not have to open a Python module to fix them.

**A generated skill still needs provenance.** Day 29 builds the audit trail for third-party skills,
and a skill assembled at runtime from a database row is exactly as unreviewed as one downloaded from a
registry. If Sutra ever generates one, the row in `SKILL_PROVENANCE.md` says *generated*, names what
generated it, and records when — otherwise the ledger describes only the skills that were easy to
record.

**What changes at scale** is that in-code skills stop being visible. A folder is discoverable: someone
can `ls skills/` and see everything the agent might do. A skill constructed inside a function three
imports deep is invisible to that person and to every audit that walks the filesystem. If you build
them in code in production, keep a registry of them and make it printable, or accept that nobody can
answer "what can this agent do?" without reading the source.

**The review comment a senior engineer leaves:** *"this builds the skill from a string literal in the
service. That means the triage procedure ships on our release cadence and cannot be corrected by the
people who own it. Put it in `skills/` and load it."*

**The interview question:** *"you can define a skill in code or load it from a folder — which do you
use and why?"* The answer that shows judgement rather than preference: *"folders for anything that is
real knowledge, because it gets reviewed, versioned and read by other clients. In code for tests and
for anything generated at runtime. The object is identical either way, so it is not a technical
decision — it is a decision about who is allowed to change the text and how you would know they had."*
