# 1.1 — `load_skill_from_dir`: one call, and the whole folder is in memory

## One-line answer

`load_skill_from_dir(path)` turns the folder you validated yesterday into a Python object in a single
call — and it reads **everything** in that folder while it does so, including every reference file and
the full source of every script.

## The story

You go to the hardware shop for one screw.

You hold it up and describe it: round head, about this long, the kind that goes into a wall plug. The
shopkeeper does not go and find you one screw. He reaches under the counter, lifts the whole drawer
out, and puts it on the counter in front of you. Fifty compartments. Screws, washers, wall plugs, a
few things that are not screws at all.

You take the one you came for. The drawer stays on the counter until you leave.

Nothing about that is wrong. It is faster for him, and it means that when you say *"actually, give me
two of the longer ones as well"*, the answer is already in front of you. But if somebody asked you
afterwards *"how much did the shopkeeper move?"*, the honest answer is not "one screw". It is "one
drawer".

## The idea in plain language

Yesterday's skill is a folder on disk
([25.1.1](../../../day-25-skills-the-open-spec/parts/01-what-a-skill-is/1.1-a-skill-is-a-folder.md)):
a `SKILL.md` with YAML frontmatter and a Markdown body, and optionally `references/`, `scripts/` and
`assets/` beside it. Nothing in Python knows it exists.

`load_skill_from_dir` is the function that changes that. You give it a path; you get back a `Skill`
object. That is the whole of the interface, and it is deliberately small — the folder format is the
contract, so the loader has nothing to configure.

The word that matters in the one-line answer is **everything**. When people first meet skills they
hear "progressive disclosure" and assume the loader is lazy: that it reads the frontmatter now and
goes back to disk for the body later. It does not. `load_skill_from_dir` reads the `SKILL.md`, walks
`references/`, walks `assets/`, walks `scripts/`, and holds all of it in memory as strings and bytes.

Both things are true at once, and holding them together is the point of this part:

- **From disk into memory, the loading is eager.** The drawer comes out from under the counter whole.
- **From memory into the model's context, the loading is lazy.** Only what the model asks for is ever
  sent, and asking is a tool call — which is sections 2 and 3 of today.

Progressive disclosure is a statement about the **context window**, not about the filesystem. It saves
tokens, not disk reads. Once you have that straight, the rest of the day is mechanical. Without it,
every measurement in section 2 looks like a contradiction.

One more detail from the loader, because it is the kind of thing that bites late at night: the file
may be called `SKILL.md` **or** `skill.md`, and the loader tries them in that order. The specification
names only the uppercase form, so write the uppercase form. But if you are ever staring at a skill
that loads on your machine and not on a colleague's, the case of the filename is a place to look.

## Why Sutra needs it

Because `skills/ticket-triage/` is currently a folder that nothing reads.

Day 25 built it, validated it and measured what it would cost. That is a binder written and shelved.
Every line of it — the steps, the severity table, the edge case about a ticket that matches no row —
is knowledge Sutra's desk agent does not have, because the only thing the desk agent has ever been
given is its instruction string
([6.1.5](../../../day-06-instructions-and-personas/parts/01-writing-the-handbook/1.5-every-line-is-a-tax.md)).

This one function is the first half of the bridge. The second half is `SkillToolset`, in section 3.
Between them they answer the question Day 25 deliberately left open: *how does a folder become

## The mechanism

One import, one call.

```python
# days/day-26-loading-skills-into-adk/lab/load_one.py
"""Load yesterday's skill folder and report what came back with it."""

import pathlib

from google.adk.skills import load_skill_from_dir

SKILL_DIR = pathlib.Path("days/day-25-skills-the-open-spec/lab/skills/ticket-triage")

skill = load_skill_from_dir(SKILL_DIR)

print("name        :", skill.name)
print("body chars  :", len(skill.instructions))
print("references  :", list(skill.resources.references))
print("scripts     :", list(skill.resources.scripts))
print("assets      :", list(skill.resources.assets))
print("script bytes:", len(skill.resources.scripts["severity_table.py"].src))
```

**Line by line:**

- `from google.adk.skills import load_skill_from_dir` — the import path named on `adk.dev/skills/`,
  fetched 2026-09-04, and confirmed against the installed `google-adk` 2.7.1 on the same day. The
  package re-exports it from a private `_utils` module, so `google.adk.skills` is the public address
  and `google.adk.skills._utils` is not. Import the public one and the underscore becomes somebody
  else's problem when it moves.
- `pathlib.Path(...)` rather than a string — the loader accepts either, and immediately calls
  `.resolve()` on it. A relative path is therefore resolved against the **current working directory**,
  not against the file you wrote it in. That is the most common way this call surprises people, and it
  is why every command in this day says which directory to run it from.
- `skill.name` reads through to `skill.frontmatter.name`. Both work; `.name` is what the toolset uses
  internally, so it is the one that will match error messages.
- `skill.instructions` is the Markdown body **as a string**, with the frontmatter already stripped.
  `len()` of it is a character count, not a token count. Section 2 does the token arithmetic.
- `skill.resources.references` is a dictionary keyed by the file's path **relative to `references/`**
  — so `SEVERITY.md`, not `references/SEVERITY.md`. The value is the file's text.
- `skill.resources.scripts` is also a dictionary, but its values are `Script` objects rather than
  strings, and `.src` is the source. The extra layer exists because a script has more than content: it
  has an interpreter, and eventually an execution result.
- The last line is the one to stare at. **The Python source of the script is already in memory**,
  before any model has been asked anything and before anybody has decided the skill is relevant. This
  call read it.

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/load_one.py
```

**Line by line:**

- Run it **from the repository root**, because of the `.resolve()` note above. From anywhere else the
  path in `SKILL_DIR` points at nothing, and you get a `FileNotFoundError` naming a directory you did
  not expect.
- `uv run` puts the project's virtual environment on the path, which is where `google-adk` 2.7.1 is
  installed. A bare `python` may find a different interpreter with no ADK in it.
- **Zero model calls.** Nothing here talks to a provider, so it costs nothing from the twenty-a-day
  budget Day 24 established
  ([24.2.1](../../../day-24-token-accounting-and-budgets/parts/02-two-ceilings/2.1-two-ceilings-one-clears.md)).

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text
name        : ticket-triage
body chars  : 724
references  : ['SEVERITY.md']
scripts     : ['severity_table.py']
assets      : []
script bytes: 686
```

Seven hundred and twenty-four characters of body, and six hundred and eighty-six characters of Python
that nobody has asked to run. Both are in the process. Neither has been sent anywhere.

## When it breaks

Three failures, and all three are the loader refusing rather than guessing. That is the good case:
every one of them fails at load time, on your machine, before a model is involved.

**The directory is not there.**

```text
FileNotFoundError: Skill directory 'C:\Users\you\sutra\skills\nope' not found.
```

The message prints the **resolved absolute path**, which is the loader telling you what your relative
path actually meant. When the path looks wrong in that message, the fix is your working directory and
not the string.

**The directory is there and the `SKILL.md` is not.**

```text
FileNotFoundError: SKILL.md not found in 'C:\Users\you\sutra\days\day-25-skills-the-open-spec'.
```

A different message for a different mistake, which is worth appreciating. Pointing at a parent folder
instead of a skill folder is an easy slip, and a loader that said "not found" for both cases would
leave you unsure which one you had made.

**The name in the file does not match the folder.** Copy a skill folder, rename the copy, forget to
edit the `name:` line:

```text
ValueError: Skill name 'ticket-triage' does not match directory name 'renamed-folder'.
```

Day 25 met this rule as a validator finding
([25.2.2](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.2-the-name-field.md)). Here
it is again, enforced by the runtime rather than by a linter, which means it is a real constraint and
not a style preference. Both values are named in the message, so the fix is visible without opening
anything.

## In production

**A skill folder is untrusted input, and its size is your problem.** The loader walks `references/`
recursively and reads every file it finds. A skill that someone added a forty-megabyte PDF to is a
skill that puts forty megabytes into your process on load, at startup, before any request arrives.
Nothing warns you. The toolset has an internal ceiling of sixteen megabytes on a single payload it
sends onward, but the read itself is unbounded. On a small container this is how a service that has
worked for months dies on deploy day, and the change that killed it added a diagram to a skill.

**Load at startup, not per request.** `load_skill_from_dir` does filesystem work, and the object it
returns does not change afterwards. Calling it inside a request handler pays for the whole folder on
every request and puts a filesystem dependency in your hot path. Load once, keep the objects, and
reload deliberately — which also gives you somewhere to put the "reload the skills" operation you will
eventually want.

**The `.resolve()` behaviour is a deployment bug waiting to happen.** Relative paths work on a laptop
where the working directory is the repository root, and fail in a container where the process starts
in `/app` or wherever the base image put it. Build the path from a module anchor —
`pathlib.Path(__file__).resolve().parents[2] / "skills"` — rather than from the process's idea of
where it is standing.

**The review comment a senior engineer leaves:** *"this loads inside the request. Move it to module
scope or an app-startup hook, and log the names and sizes it loaded, so that when a skill goes missing
in production we can see it in the log instead of inferring it from the answer."*

**The interview question:** *"if skills are loaded progressively, why does loading a skill read its
scripts?"* The answer that shows you have looked: *"because the two loadings are different things.
Disk to memory is eager and happens once, at load. Memory to context is lazy and happens per tool
call. Progressive disclosure is about the context window and the token bill, not about I/O — so the
script source sits in the process from startup, and only reaches the model if the model asks for it."*
