# 5.2 — Experimental means experimental: when the page and the package disagree

## One-line answer

The documentation page and the installed package disagree in four places on this feature, the package
disagrees with **itself** in a fifth, and the discipline that makes that survivable is the one Sutra
already has: pin the version, name the page and the date, and believe the code.

## The story

The timetable at the bus stop says the 14 comes at ten past and twenty-five past.

It has said that for a long time. The plastic is a little faded and there is a sticker in one corner
with a phone number. And the 14 comes at quarter past and about ten to, which everybody who waits at
that stop knows, and which the timetable does not say.

Nobody at the stop is confused. They have all worked it out by standing there. The person who gets
caught is the one who read the timetable, arrived at eight minutes past, and is now twenty minutes
early for a bus that has already gone.

The timetable is not lying. It was true, it was printed, and the buses changed.

## The idea in plain language

`adk.dev/skills/` was fetched on 2026-09-04, the day this was written. The installed `google-adk`
2.7.1 was read on the same day. They disagree in four places, and every one of them changes what you
would build:

| The page says | The package does | Where today measured it |
| --- | --- | --- |
| three tools: `load_skill`, `load_skill_resource`, `run_skill_script` | **four**, with `list_skills` first | [2.2](../02-the-four-tools/2.2-the-index-is-a-tool-call.md) |
| the toolset "provides a default system instruction" describing the skills | the preamble names **no skill**; the branch that would add the index never runs | [2.1](../02-the-four-tools/2.1-the-preamble-you-did-not-write.md) |
| `additional_tools` is a constructor argument, shown in the examples | those tools appear only after activation, and only if the skill's `metadata` names them under `adk_additional_tools`, which the page does not mention | [3.2](../03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md) |
| "Supported in ADK Python v1.25.0" | this project is on the **2.x** line, and the feature is present in 2.7.1 | the version note itself |

And a fifth, inside one file of the package. `Frontmatter`'s docstring says *"Skill name in kebab-case
or snake_case"*. The validator twelve lines below rejects an underscore
([1.3](../01-loading-a-folder/1.3-building-a-skill-in-code.md)):

```text
ValidationError: name
  Value error, name must be lowercase kebab-case (a-z, 0-9, hyphens), with no leading, trailing, or consecutive delimiters [type=value_error, input_value='ticket_triage'
```

None of this is scandalous. The page carries the word **Experimental** at the top, and that word is
doing exactly what it is there for: it says the surface may move, and it has moved faster than the
prose. The v1.25.0 note is the clearest tell — it is a version number from before the 2.0 renumbering,
sitting on a page describing a feature that works fine on 2.7.1.

The rule that falls out is not "distrust documentation". It is narrower and more useful:

**For behaviour, the installed package is authoritative. For intent, the page is.** The page tells you
what the feature is *for* — that is why the `additional_tools` examples are still worth reading even
though they are incomplete. The package tells you what will happen when you run it. When they
disagree about what happens, the code wins, and the disagreement gets written down with a date.

## Why Sutra needs it

Because Principle 8 says never invent an API, and this is the day it costs something to obey.

The easy reading of Principle 8 is "check the docs". Sutra has met the harder version twice already.
Day 15 found a page and a package disagreeing about an OpenAPI toolset
([15.5.1](../../../day-15-toolsets-and-openapi/parts/05-where-it-bites/5.1-the-page-and-the-package-disagree.md)),
and Day 25 found the Agent Skills specification naming a command that does not exist — the package is
`skills-ref` and the command it installs is `agentskills`, read from the package's own entry points
([25.5.1](../../../day-25-skills-the-open-spec/parts/05-in-production/5.1-validating-before-you-ship.md)).
Three days, three disagreements, three times the package was right.

That is now a pattern rather than an anecdote, and it deserves a habit: **ask the package**. Not "read
the source" as a heroic act, but a handful of one-liners that make a page's claim checkable in under a
minute — which is what every "Measured on 2026-09-04" block in this day is.

There is also a Principle 14 question to answer honestly, and the answer is no. Principle 14 says that
when reality changes, the plan is amended before any code is written. Nothing here contradicts the
plan: §14 assigns Day 26 `SkillToolset`, and `SkillToolset` is what today taught. What moved is a
**documentation page against an implementation**, which is a fact to record in the day rather than an
amendment to the contract. Reaching for an addendum here would devalue the mechanism for the day it is
actually needed.

## The mechanism

The habit, as four commands. Each one takes seconds and each one replaces a sentence you would
otherwise have believed.

```bash
uv run python -c "import google.adk; print(google.adk.__version__)"
uv run python -c "from google.adk.tools import skill_toolset; print(sorted(vars(skill_toolset)))"
uv run python -c "from google.adk.skills import models; print(list(models.Frontmatter.model_fields))"
uv run python -c "import inspect, google.adk.tools.skill_toolset as m; print(inspect.signature(m.SkillToolset.__init__))"
```

**Line by line:**

- The first is the only version number that matters. Not the pin in `pyproject.toml`, not the row in
  `PACKAGES.md` — what is actually importable in this environment. Everything else in this day is
  qualified by it.
- The second lists what the module exports, which is how the fourth tool was found. A page that names
  three and a module that defines four classes ending in `Tool` is a discrepancy you can see in one
  line.
- The third prints the frontmatter fields the loader will accept. That is the closed list from
  [1.2](../01-loading-a-folder/1.2-the-skill-object.md), obtained by asking rather than by reading.
- The fourth prints the constructor signature — every keyword argument, in order, with its default.
  It is how `tool_name_prefix`, `script_timeout` and `registry` were found, none of which the page
  mentions.
- Every one of these is **zero generations** and needs no key.

And then the thing that makes it stick, which is a test rather than a note:

```python
# tests/test_skill_toolset_surface.py
"""Pin the parts of ADK's experimental skills surface that Sutra depends on."""

import pytest
from google.adk.skills import load_skill_from_dir
from google.adk.tools import skill_toolset

from sutra.desk.skills import SHELF


@pytest.mark.asyncio
async def test_the_four_tools_are_still_four() -> None:
    """A fifth tool, or a renamed one, is a change we want to be told about."""
    toolset = skill_toolset.SkillToolset(skills=[load_skill_from_dir(SHELF / "ticket-triage")])
    names = sorted(tool.name for tool in await toolset.get_tools())
    assert names == ["list_skills", "load_skill", "load_skill_resource", "run_skill_script"]
```

**Line by line:**

- The assertion is an **equality against a literal list**, not a subset check. A subset check would
  pass when ADK adds a fifth tool, and being told about a fifth tool is the entire purpose.
- `sorted(...)` because the order is an implementation detail and pinning it would produce a test that
  fails for a reason nobody cares about.
- `@pytest.mark.asyncio` and an `async def`, the shape Day 23 established for testing an async surface
  without a runner
  ([23.3.3](../../../day-23-testing-tools-and-callbacks/parts/03-testing-tools/3.3-the-async-tool-without-a-runner.md)).
- It imports `SHELF` from Sutra rather than hard-coding a path, so a move of the skills directory
  breaks the test loudly instead of leaving it green against a folder that no longer exists.
- **No `live` marker**, because it spends nothing: it belongs in the default `-m "not live"` run that
  Day 23 defined
  ([23.2.5](../../../day-23-testing-tools-and-callbacks/parts/02-pytest-house-rules/2.5-markers-and-the-not-live-line.md)).
  A surface test that only runs when somebody remembers to run it is not a surface test.

Measured on 2026-09-04 — the first one-liner, then the test's assertion:

```text
2.7.1
names == ['list_skills', 'load_skill', 'load_skill_resource', 'run_skill_script']  # passed
```

The second one-liner is the one that found the discrepancy. Among what `skill_toolset` exports are
`ListSkillsTool`, `LoadSkillTool`, `LoadSkillResourceTool`, `RunSkillScriptTool` **and**
`SearchSkillsTool` — five tool classes where the page names three, the fourth active by default and
the fifth only when a registry is configured.

## When it breaks

**The upgrade that changes the preamble.** It is a string literal in the package. A minor version can
lengthen it, and every request in your system gets more expensive with no line of your code changing.
The only defence is a measurement in a test with a ceiling on it, and it is worth two lines.

**The upgrade that changes the state key.** `_adk_activated_skill_<agent_name>` is undocumented and
underscore-prefixed. If it becomes `_adk_skills_active_<agent_name>`, the detector from
[4.3](../04-failure-lab/4.3-the-manual-nobody-opened.md) starts returning an empty list — and returning
an empty list is precisely what it does when nothing was activated. The failure of your monitoring
looks exactly like the thing your monitoring exists to detect. That is the most dangerous shape a bug
can have, and it is why 4.3's test asserts the **positive** case too.

**The tutorial that was right last year.** Anything on the internet showing three skill tools was
correct against some version, and reproducing it will leave you wondering why the model never lists
anything. Day 5's rule about 1.x tutorials applies unchanged here: check the version the example was
written against before you copy the shape.

**Reading a docstring as a specification.** The `snake_case` line is the reminder. A docstring is
prose written by a person; the validator is behaviour. When the two are in the same file and disagree,
the one that runs is the one that decides.

## In production

**Pin exactly, and record the date.** `google-adk==2.7.1` in `pyproject.toml`, a dated row in
`docs/PACKAGES.md`, and `uv.lock` committed. Sutra already does all three. What this day adds is a
reason to care about the *date* on the row: every measurement in this document is qualified by it, and
a row with no date is a claim with no expiry.

**Re-verify at the phase gate, not at the upgrade.** Plan §15 makes freshness a gate step, and
experimental surfaces are exactly what it is for. Phase 4's gate is the natural place to re-run the
four one-liners above and re-read the page — with a written expectation, so that "the tools are still
four" is checked rather than assumed.

**Write the disagreement down where the next person will look.** A comment beside the code, naming the
page, the date and what the package actually does, is worth more than a note in a wiki. The next
person to read `SkillToolset(...)` in Sutra should not have to rediscover that `additional_tools`
needs a metadata key.

**What changes at scale** is that experimental surfaces accumulate. One is a note; six is an upgrade
that takes a week and a team that stops upgrading. The discipline that keeps that manageable is a
small, honest set of surface tests — one per experimental feature, asserting the two or three facts you
actually depend on — so that an upgrade produces a list of specific failures instead of a vague fear.

**The review comment a senior engineer leaves:** *"this comment says 'three tools, per adk.dev'. It is
four, and the fourth is the one that matters. Fix the comment, add the date you checked, and put the
tool-name assertion in the test file so the next upgrade tells us."*

**The interview question:** *"how do you work with a framework feature marked experimental?"* The
answer that shows judgement rather than caution: *"pin the exact version and commit the lock file,
record the doc page and the date I verified against, and then verify against the installed package
rather than the page — on this feature they disagreed in four places, including the number of tools.
Then I write one small surface test asserting the two or three facts we actually depend on, so an
upgrade produces a specific failure instead of a mystery. And I re-check at every phase gate rather
than when something breaks."*
