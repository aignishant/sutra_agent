# 4.1 — 💥 One bad folder, and the shelf came back empty

## One-line answer

`load_skills_from_dir` raises on the first skill it cannot parse, so one capital letter in one
frontmatter takes down every other skill and the agent that was built from them — and the exception
does not name the folder.

## The story

🎬 **The scene.** The trip is on Friday and the coach is booked. On Thursday afternoon the office
tells the class that nobody is going, because one consent form has not come back. Twenty-nine forms
are in the folder, signed. The trip is off for all thirty.

😬 **The naive fix.** Somebody says *just check the folder before Friday*. Everyone agrees, nobody
writes down who does it, and the following term it happens again with a different form.

💥 **Why it fails.** The check is not the problem. The problem is that the rule is "all or nothing"
and the process gives you no way to find out **which** form is missing without going through all
thirty by hand. On Thursday afternoon, that is thirty minutes you do not have.

💡 **The insight.** When a batch operation fails atomically, the first thing to build is not the
check — it is the **naming**. A failure that says *which* item broke turns a crisis into a
correction.

## The idea in plain language

[1.4](../01-loading-a-folder/1.4-the-whole-shelf.md) established the behaviour and this part is where
you feel it. `load_skills_from_dir` walks the subdirectories and calls `load_skill_from_dir` on each,
letting the first exception out. Nothing is caught, nothing is collected, and nothing is named.

Here is what that means for [3.1](../03-wiring-the-toolset/3.1-a-toolset-not-a-tool.md)'s agent. The
shelf is loaded inside `build_agent()`. So the failure is not "a skill is missing" — it is
**`build_agent()` raised**, which in a service means the process did not start, and in a script means
the traceback is the whole output.

The traceback is the second half of the problem. It goes from your call, into
`_load_skills_from_dir`, into `_load_skill_from_dir`, into pydantic — and at no point does it print a
path. You get the rule that was broken and the value that broke it. With three skills you can guess.
With fifty you are running `agentskills validate` in a loop to find out what your own program already
knew and threw away.

The fix is four lines and it is not clever. Loop yourself, catch per folder, and log the name.

## Why Sutra needs it

Because `skills/` is going to be a folder that people other than you add things to, and that is the
entire point of the format.

Day 25's argument was that a skill is a folder a non-engineer can write
([25.1.1](../../../day-25-skills-the-open-spec/parts/01-what-a-skill-is/1.1-a-skill-is-a-folder.md)).
The consequence, which nobody says out loud on the day they adopt the format, is that a non-engineer
can also **break the whole service** with a capital letter — not because their skill fails, but because
the loader is atomic.

This is also the day's Principle 10 exercise. There are two honest behaviours and one dishonest one:

- **Refuse to start**, naming the folder. Correct when a missing skill changes the answers.
- **Skip it, name it, count it.** Correct when a missing skill only removes an option.
- **Load nine of ten and say nothing.** Never correct, and it is what you get if you catch the
  exception without logging.

Choosing between the first two is a design decision. The third is the failure this part exists to
prevent.

Now the fix.

```python
# days/day-26-loading-skills-into-adk/lab/load_shelf_safely.py
"""Load a shelf one skill at a time, so a bad folder is named instead of fatal."""

import logging
import pathlib

from google.adk.skills import load_skill_from_dir, models

logger = logging.getLogger("sutra.skills")


def load_shelf(shelf: pathlib.Path) -> tuple[list[models.Skill], list[str]]:
    """Every skill under `shelf`, plus the folder names that would not load.

    Returns:
        (skills, rejected) - `rejected` holds folder names, not paths, because that
        is what a person types when they go to fix one.
    """
    skills: list[models.Skill] = []
    rejected: list[str] = []
    for folder in sorted(p for p in shelf.iterdir() if p.is_dir()):
        if not (folder / "SKILL.md").exists() and not (folder / "skill.md").exists():
            continue
        try:
            skills.append(load_skill_from_dir(folder))
        except (ValueError, OSError) as exc:
            rejected.append(folder.name)
            logger.error("skill rejected", extra={"skill_folder": folder.name, "why": str(exc)})
    return skills, rejected


if __name__ == "__main__":
    logging.basicConfig(level=logging.ERROR, format="%(levelname)s %(message)s")
    loaded, bad = load_shelf(pathlib.Path("days/day-26-loading-skills-into-adk/lab/skills"))
    print("loaded  :", [s.name for s in loaded])
    print("rejected:", bad)
```

**Line by line:**

- `sorted(p for p in shelf.iterdir() if p.is_dir())` — sorted so the log order is stable across
  machines, and directories only, because a stray file on the shelf is not a candidate.
- The `SKILL.md` / `skill.md` check reproduces ADK's own silent-skip rule
  ([1.1](../01-loading-a-folder/1.1-load-skill-from-dir.md)) deliberately. Without it, a `notes/`
  folder would be *rejected* rather than *ignored*, and the rejected list would fill with things that
  were never meant to be skills — a report that cries wolf is a report nobody reads.
- `except (ValueError, OSError)` and **not** `except Exception`. Both are real: `ValueError` covers the
  name-mismatch and the pydantic `ValidationError` that subclasses it, and `OSError` covers a folder
  that vanished between `iterdir` and the read. Anything else is a bug in ADK or in this function, and
  Principle 10 says it should surface
  ([21.4.1](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.1-the-swallowed-exception.md)).
- `rejected.append(folder.name)` stores the **name**, not the path. It is what somebody types into
  `cd`, and it is what fits on a log line.
- `logger.error(..., extra={...})` uses the structured form Day 22 built
  ([22.1.2](../../../day-22-structured-logging/parts/01-a-line-you-can-query/1.2-one-json-object-per-line.md)),
  so `skill_folder` is a **field** you can filter on rather than words inside a sentence.
- The function **returns** the rejects rather than deciding what to do about them. That is the whole
  design: the loader reports, and the caller — who knows whether a missing skill changes the answers —
  decides between refusing to start and degrading. Baking the decision in here would put a policy in a
  utility.
- `if __name__ == "__main__":` keeps the import side-effect-free, as every Sutra module has been since
  Day 5.

**Line by line:**

Measured on 2026-09-04:


Two skills instead of an exception, and the broken folder named. Note the log line itself prints only
`skill rejected` under the default formatter — the `extra` fields are attached to the record and are
rendered by a JSON formatter, which is exactly the point Day 22 made about why a formatter is part of
the logging setup rather than an optional nicety
([22.1.2](../../../day-22-structured-logging/parts/01-a-line-you-can-query/1.2-one-json-object-per-line.md)).

Then the caller's decision, in the agent builder:

```python
skills, rejected = load_shelf(SHELF)
if rejected:
    raise RuntimeError(f"refusing to start: unloadable skills {rejected}")
```

**Line by line:**

- This is the **fail-fast** branch, written out because it is what Sutra chooses today: with two skills
  and one of them the triage procedure, a desk that starts without its skills is a desk that improvises
  severities.
- `RuntimeError` with the list in the message, rather than a bare `raise` of the original — the
  original said which rule was broken, this says which folder, and the log line from `load_shelf`
  already carried the detail.
- The alternative branch is one line — `logger.warning("starting without skills", extra={"rejected":
  rejected})` — and the hub's build brief asks you to decide which one Sutra keeps and write down why.

## When it breaks

**The fix that swallows.** `except Exception: pass` in place of the logged `except` turns a loud
failure into a quiet one, and the agent starts with a shelf that is missing a procedure nobody notices
for a week. This is Day 21's swallowed exception, in a new costume
([21.4.1](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.1-the-swallowed-exception.md)),
and it is the most likely thing to be written under time pressure because it makes the traceback go
away.

**The fix that rejects everything.** Drop the `SKILL.md` existence check and the rejected list fills
with `.git`, `__pycache__` and every folder anyone put on the shelf:

```text
rejected: ['.git', '__pycache__', 'bad-name', 'notes']
```

The signal is still in there and nobody will find it.

**A skill folder that vanished mid-walk.** Rare, and real on a machine where skills are synced:

```text
FileNotFoundError: Skill directory '...\skills\ticket-triage' not found.
```

`OSError` in the `except` clause is what keeps this from being fatal — `FileNotFoundError` is a
subclass of it.

**The exception you cannot catch per folder at all.** If the shelf directory itself is missing,
`shelf.iterdir()` raises before the loop:

```text
FileNotFoundError: [WinError 3] The system cannot find the path specified: 'days\\...\\lab\\skills'
```

That one **should** be fatal. A shelf that is not there is a configuration error, not a bad skill, and
the two deserve different treatment.

## In production

**Report loaded and rejected as two numbers at startup.** `skills_loaded=2 skills_rejected=1` on one
structured line is the whole of what an operator needs, and it makes the question "did the deploy lose
a skill?" a query rather than an investigation. Day 22 built the line
([22.4.1](../../../day-22-structured-logging/parts/04-in-production/4.1-what-to-log-and-what-to-count.md));
this is a field for it.

**Validate in CI so this never reaches startup.** `agentskills validate` over every folder under
`skills/`, in the same job as the tests, turns a startup failure into a pull-request failure. Day 25
established the command and its exit codes
([25.5.1](../../../day-25-skills-the-open-spec/parts/05-in-production/5.1-validating-before-you-ship.md));
Day 31 wires it into `./m check`. There is nothing stopping you running it by hand in the meantime.

**Decide the policy per skill class, not globally, once you have more than a handful.** The rule that
survives is usually: first-party skills that a procedure depends on are fatal if missing; sourced or
optional skills are skipped and logged. That distinction needs somewhere to live, and
`SKILL_PROVENANCE.md` — which Day 25 started and Day 29 fills — is the obvious place, because it is
already the file that says where a skill came from.

**What changes at scale** is that the shelf is edited by people who never see your logs. A skill author
who breaks a frontmatter needs the feedback **in the pull request**, not in a service log they have no
access to. Every hour spent on the CI check buys back a day of somebody being told "the desk is down"
and having to work out that it was their file.

**The review comment a senior engineer leaves:** *"one bad skill takes the whole shelf down and the
traceback does not name the folder. Load them individually, log the folder on failure, and decide
explicitly whether we start without it — right now we would not start, and nobody would know why."*

**The interview question:** *"what happens when someone adds a broken skill to your skills directory?"*
The answer that shows it has happened to you: *"with ADK's bulk loader, nothing loads — it raises on
the first bad folder and the traceback names the pydantic rule, not the path. So we load them one at a
time, catch `ValueError` and `OSError` per folder, log the folder name as a structured field, and
return the rejects to the caller. The caller decides: we fail startup, because our triage skill
changes the answers. And we run the spec validator in CI so it usually never gets that far."*
