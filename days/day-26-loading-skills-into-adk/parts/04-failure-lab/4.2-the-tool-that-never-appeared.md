# 4.2 — 💥 The tool that was passed in and never appeared

## One-line answer

`additional_tools` fails silently in three different ways that look identical from outside — never
activated, not declared in the skill's metadata, or the name does not match — and none of them
produces an error, a warning or a log line.

## The story

🎬 **The scene.** The electrician comes to fit a new light. You watch him carry in a bag, a ladder and
a box of fittings, and then spend twenty minutes doing everything except the one job you called about.
When you ask, he says the drill is in the van. It is a good drill, it is right outside, and it is not
coming in, because the work order says *replace fitting* and drilling a new hole is a different line
that nobody wrote.

😬 **The naive fix.** You say *well, just go and get it.* He does, and it is fine this time, and the
next visit has the same problem because the work order is still where the mistake lives.

💥 **Why it fails.** Nothing was broken. The drill existed, the electrician was willing, and the
customer was standing right there. The failure was a piece of paper that did not name the tool — and
paper does not raise an exception when it is incomplete.

💡 **The insight.** When capability is granted by a **declaration** rather than by possession, the
declaration is the thing that breaks, and its failure mode is absence. You will not find it by looking
at the tool.

## The idea in plain language

[3.2](../03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md) established the two
conditions: a skill must be activated, and that skill's `metadata.adk_additional_tools` must name the
tool. Miss either and `get_tools` returns four instead of six.

Now the part that makes it a failure lab rather than a footnote. There are **three** distinct causes,
they occur in three different files, and they produce **byte-identical** output:

| Cause | Lives in | What you see |
| --- | --- | --- |
| the skill was never activated | the conversation | four tools |
| `adk_additional_tools` missing or misspelled | `SKILL.md` | four tools |
| the name does not match the function | `SKILL.md` and your Python | four tools |

There is no fourth column, because there is no error message for any of them. ADK's own logging says
nothing: the collision case logs at `ERROR`
([3.2](../03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md)) and a broken additional
*toolset* logs at `WARNING`, but a name that simply matches nothing is not an event. The resolver
collects the names the activated skills asked for, looks each one up in the candidates, and quietly
keeps the ones it finds.

That is a defensible design — the alternative is a framework that refuses to start because a skill
mentions a tool you deliberately did not pass — and it means the diagnosis is yours to build.

The order to check is the cheapest first:

1. **Read the register.** `_adk_activated_skill_<agent>` in session state
   ([3.3](../03-wiring-the-toolset/3.3-activation-is-a-line-in-state.md)). Absent means the skill never
   loaded, and this is not the failure you are looking at — it is
   [4.3](4.3-the-manual-nobody-opened.md).
2. **Read the metadata.** `skill.frontmatter.metadata.get("adk_additional_tools")`. `None` means the
   declaration is missing or the key is misspelled.
3. **Compare the names.** The set of names the skill asks for, against the set of names the toolset
   was given. The difference is your answer.

Step 3 is worth writing down as code, because it is also the lint.

## Why Sutra needs it

Because Sutra is about to bind a Markdown file to a Python function by string, and nothing in the
language, the framework or the test suite will notice when the two drift apart.

`ticket-triage`'s frontmatter says `adk_additional_tools: ["lookup_ticket", "remember_triage"]`. Those
names live in a YAML file. The functions live in `sutra/`. A refactor that renames `lookup_ticket` to
`fetch_ticket` will update every call site in Python, pass every test, and silently remove a tool from
a procedure. The desk will then activate the triage skill, read a body that says *"read the ticket with
`lookup_ticket`"*, and have no such tool — at which point it will improvise, because that is what
models do when a step is impossible.

That is a data-integrity problem with a twenty-line answer, and the answer belongs in the Day 31
skills lint next to the link check from
[2.4](../02-the-four-tools/2.4-the-third-rung-and-its-fence.md).

## The mechanism

Reproduce all three causes from one script, so that the identical output is undeniable.

```python
# days/day-26-loading-skills-into-adk/lab/the_missing_tool.py
"""Three ways for an additional tool to go missing, and the check that finds them."""

import asyncio
import pathlib

from fake_skill_context import FakeSkillContext
from google.adk.skills import load_skill_from_dir, models
from google.adk.tools import skill_toolset

SHELF = pathlib.Path("days/day-26-loading-skills-into-adk/lab/skills")
ACTIVE = {"_adk_activated_skill_desk": ["ticket-triage"]}


def lookup_ticket(ticket_id: str) -> dict:
    """Return the text of a support ticket."""
    return {"status": "ok", "ticket_id": ticket_id}


def remember_triage(ticket_id: str, severity: str) -> dict:
    """Record the chosen severity for a ticket."""
    return {"status": "recorded", "ticket_id": ticket_id, "severity": severity}


async def names(skill: models.Skill, state: dict) -> list[str]:
    """The tool names an agent would be shown, for this skill and this state."""
    toolset = skill_toolset.SkillToolset(
        skills=[skill], additional_tools=[lookup_ticket, remember_triage]
    )
    context = FakeSkillContext()
    context.state.update(state)
    return sorted(tool.name for tool in await toolset.get_tools(context))


def missing_tools(skill: models.Skill, provided: set[str]) -> list[str]:
    """Names this skill asks for that nobody passed in. This is the lint."""
    asked = set(skill.frontmatter.metadata.get("adk_additional_tools") or [])
    return sorted(asked - provided)


async def main() -> None:
    """Three sabotages, one output, and one check that tells them apart."""
    provided = {"lookup_ticket", "remember_triage"}

    good = load_skill_from_dir(SHELF / "ticket-triage")
    print("healthy         :", await names(good, ACTIVE))

    print("not activated   :", await names(good, {}))

    no_key = load_skill_from_dir(SHELF / "ticket-triage")
    no_key.frontmatter.metadata.pop("adk_additional_tools", None)
    print("no declaration  :", await names(no_key, ACTIVE))

    typo = load_skill_from_dir(SHELF / "ticket-triage")
    typo.frontmatter.metadata["adk_additional_tools"] = ["lookup_tickets", "remember_triage"]
    print("name mismatch   :", await names(typo, ACTIVE))

    print()
    for label, skill in (("healthy", good), ("no declaration", no_key), ("mismatch", typo)):
        print(f"lint {label:16}: missing {missing_tools(skill, provided)}")


asyncio.run(main())
```

**Line by line:**

- `ACTIVE` is the register written by hand, exactly as
  [3.2](../03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md) did. Writing it rather than
  earning it through a `load_skill` call is what lets the "not activated" case be a one-word change.
- `names()` builds a **fresh toolset per call**, because the toolset caches nothing here and a shared
  one would invite the question of whether the previous case leaked into this one. In a probe about
  three near-identical failures, that question is worth spending an object to avoid.
- `context.state.update(state)` rather than assigning `context.state = state`, so the double keeps its
  own dictionary and two cases cannot share one.
- `no_key.frontmatter.metadata.pop(...)` mutates the **loaded object**, not the file on disk. The
  skill folder is left alone, so running this script twice gives the same answer — a sabotage that
  edits your repository is a sabotage you will forget to undo.
- `typo` misspells one name and leaves the other correct. That is the realistic version: a rename
  touches one function, not all of them, so the failure is usually partial and therefore harder to see.
- `missing_tools()` is the whole lint, in three lines. It takes the **provided** names as a set rather
  than reading them from anywhere, because in the real check that set comes from the same place the
  toolset is built and there should be exactly one source of it.
- `asked - provided` is a set difference and the direction matters. The other direction — tools you
  passed that no skill asks for — is not an error; it is a tool waiting for a skill.
- **Zero model calls.**

Run it from the repository root:

```bash
uv run python days/day-26-loading-skills-into-adk/lab/the_missing_tool.py
```

**Line by line:**

- Needs no key. Requires `adk_additional_tools` to be present in the shelf copy of `ticket-triage`, as
  added in [3.2](../03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md).

Measured on 2026-09-04 against `google-adk` 2.7.1:

```text
healthy         : ['list_skills', 'load_skill', 'load_skill_resource', 'lookup_ticket', 'remember_triage', 'run_skill_script']
not activated   : ['list_skills', 'load_skill', 'load_skill_resource', 'run_skill_script']
no declaration  : ['list_skills', 'load_skill', 'load_skill_resource', 'run_skill_script']
name mismatch   : ['list_skills', 'load_skill', 'load_skill_resource', 'remember_triage', 'run_skill_script']

lint healthy         : missing []
lint no declaration  : missing []
lint mismatch        : missing ['lookup_tickets']
```

Two of the three failures print the identical four-tool line. The third prints five, which is worse:
it is a partial failure, and a partial tool set is exactly the situation in which a model produces a
confident answer with a step quietly skipped.

And read the lint rows carefully, because they contain the honest limitation. The lint catches the
**mismatch** and says `lookup_tickets`. It reports `missing []` for the **no declaration** case,
because a skill that asks for nothing is not missing anything. Those two need different checks: a name
lint, and a review habit that asks whether a body naming a tool also declares it.

## When it breaks

**The lint that reads the wrong list.** `missing_tools` compares against a set you pass in. If that set
is built by hand in the lint rather than imported from wherever the toolset is constructed, the two
drift and the lint passes while production is missing a tool. Import the same list; do not retype it.

**The body that names a tool the metadata does not.** Day 25's `ticket-triage` body says *"read the
ticket with `lookup_ticket`"* in prose. Nothing connects that sentence to the metadata key. A skill
can name a tool in its steps, never declare it, and read as complete to a human reviewer. The check
for that is a grep of the body for backticked names against the declared list, and it is a good
`TODO(me)` because the false-positive rate is a judgement call.

**A tool added to `additional_tools` and never asked for by anyone.** Harmless, invisible, and pure
dead weight — the object is constructed and held for the life of the process. Worth a line in the same
lint, at warning level rather than error.

## In production

**Make the lint part of the shelf loader, not a separate script.** The function that loads skills
already knows the folder names and the caller already knows the tool list. Checking `asked - provided`
at load time, once, means a mismatch is caught at startup with the skill named rather than discovered
in a conversation. That is the same argument as [4.1](4.1-one-bad-folder.md), applied to a different
kind of brokenness.

**Log the resolved tool names per request, not just at startup.** Because the tool set is dynamic
([3.2](../03-wiring-the-toolset/3.2-tools-that-appear-after-activation.md)), a startup log tells you
the cold set only. The line that answers "what could the model call when it made this decision?" has to
be written at the moment of the decision.

**Treat `adk_additional_tools` as an interface and version it with the code.** The names in that list
are as much a public interface of your tool module as its function signatures. Renaming one is a
breaking change to every skill that names it, and the only reason it does not feel like one is that
the compiler cannot see the other side. Teams that get bitten twice end up with a constant —
`TOOL_LOOKUP_TICKET = "lookup_ticket"` — and a test that the skill files and the constants agree.

**What changes at scale** is that skills and tools are owned by different people. The procedure author
adds a tool name to a YAML file; the platform team renames a function. Neither is wrong, neither
notices, and the failure surfaces as a support agent that stopped doing one step. The only structural
fix is a check that runs where both sides are visible, and the only place both sides are visible is
CI.

**The review comment a senior engineer leaves:** *"this rename removes a tool from `ticket-triage`, and
nothing in the test suite covers it because the binding is a string in a Markdown file. Add the name
check to the skills lint in the same pull request."*

**The interview question:** *"a skill in your system stopped using one of its tools and nothing failed
— how do you find out why?"* The answer that shows you have debugged it: *"three causes, all silent:
the skill was never activated, the metadata does not declare the tool, or the declared name no longer
matches the function. I check them in that order because they get cheaper going up — the register in
session state, then the skill's metadata, then a set difference between what the skills ask for and
what we pass in. The last one is a twenty-line lint and it belongs in CI, because the two sides of that
binding are owned by different people."*
