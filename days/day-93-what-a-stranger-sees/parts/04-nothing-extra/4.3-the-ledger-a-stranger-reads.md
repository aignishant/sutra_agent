# 4.3 — The ledger a stranger reads

## One-line answer

Ninety-four day folders exist and `docs/PROGRESS.md` has fifty-one rows, so forty-three days are
written, checked and green with nothing recording it — and a reader cannot tell those apart from
forty-three days that were never started.

## The story

The immunisation card with the last three doses unrecorded.

A small folded card, filled in at each visit: date, vaccine, a signature. It works perfectly for the
first year and then the family moves, and the next two visits happen at a clinic that keeps its own
register and does not ask for the card.

Years later the child needs the card for a school. The last three entries are blank. The doses were
given — the mother remembers the afternoons, remembers which arm — and none of that is admissible.
The school needs the card, the clinic that gave the doses has closed, and the only remedy available
is to give some of them again.

Nothing was neglected. Somebody just stopped writing on the card, and the card was the only thing
that counted.

## The idea in plain language

Principle 2 is *one day, one commit*, and what it produces is a row in `docs/PROGRESS.md`: the day
number, the date, the IDs it closed, the part count, the commit hash, a gate mark.

That row is not a summary of the work. It **is** the work, as far as every tool and every reader is
concerned:

- `./m brief N` reads it to decide whether day N is allowed to be written yet.
- `./m trace` reads it to decide whether a concept ID is closed.
- `./m status` reads it to say how far along the project is.
- A stranger reads it to answer *is this finished, and where is it up to?*

So a day with no row is, to all four, a day that did not happen. The folder can be complete,
depth-checked, ruff-clean and green; none of those facts is reachable from the ledger.

The gap has a second cost that only appears in a public repository. A stranger cannot distinguish
**not done** from **not recorded**, and they will assume the first, because that is what a ledger
stopping means everywhere else. Ninety-three days of work reads as fifty.

## Why Sutra needs it

Because `./m brief` refuses while the gap exists. It is not a warning; the tool declines to produce a
brief, saying the next day must be fifty-one. Every day since then has been written past that
refusal, which means the guard has been overridden more than forty consecutive times — and Day 83
part 4.2 already made the argument that a guard overridden that often has been retrained to mean
*carry on*.

And because this is the repository's own headline claim. The README says the memory is the repo, not
the chat, and that *"any capable CLI agent — or you, six months from now — can pick up exactly where
the last session stopped, from the last row of `docs/PROGRESS.md` alone."* Today, that row is day
fifty, and following that sentence literally would restart work that is already done.

## The mechanism

Both numbers come from the tree, so the check cannot go stale:

```python
def progress_rows() -> list[int]:
    """Day numbers that have a row in docs/PROGRESS.md."""
    text = (ROOT / "docs" / "PROGRESS.md").read_text(encoding="utf-8")
    return [
        int(m.group(1))
        for line in text.splitlines()
        if (m := re.match(r"^\|\s*(\d{1,3})\s*\|", line))
    ]
```

**Line by line:**

- Anchored at the start of the line with `^\|`, so a day number mentioned in prose elsewhere in the
  file is not counted as a row.
- `\d{1,3}` allows three digits. The curriculum stops at ninety-six, and a checker that assumed two
  would silently miss a hundredth day — the same assumption Day 83's criterion 8 made and wrote down.
- The walrus binds the match inside the condition so the body does not re-run the regex.
- Only the **number** is read. Whether the row's contents are right — the hash, the ID list, the gate
  mark — is a different check, and conflating them would make this one's failure ambiguous.

The other side is the directory listing:

```python
def days_written() -> list[int]:
    """Day numbers that have a folder under days/."""
    return sorted(int(p.name.split("-")[1]) for p in (ROOT / "days").glob("day-*") if p.is_dir())
```

**Line by line:**

- `p.name.split("-")[1]` takes the number out of `day-NN-<slug>`, which works because the format is
  fixed by plan §17.2 and enforced by `./m depth`.
- `if p.is_dir()` because a stray file named `day-something` would otherwise crash the `int()`.
- A folder counts as "written". That is a deliberately generous definition — it does not check that
  the day is complete — and it is the right one here, because the finding is about the *gap*, and a
  generous left-hand side makes the gap a lower bound.

Run it:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python ledger.py; echo "exit: $?"
```

**Line by line:**

- No flag: both numbers and the difference between them.

Measured on 2026-09-07:

```text
  day folders written        : 94  (day 0-93)
  rows in docs/PROGRESS.md   : 51  (last = day 50)
  written with no row        : 43
  the gap                    : days 51-93

  what a reader cannot tell apart, for each day in the gap:
    - the day was never written
    - the day is written, checked and green, and nobody appended a row

  43 days are in that ambiguity, and ./m brief refuses while they are
exit: 1
```

**Forty-three days in the gap**, a contiguous run from fifty-one to ninety-three. Contiguity is
itself informative: this is not days going missing here and there, it is a single point at which the
recording stopped while the work continued.

## When it breaks

The comfortable report is the one a status update naturally produces:

```bash
uv run python ledger.py --count; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  51 days complete

  true, and it is the number a stranger repeats
exit: 0
```

`51 days complete` is **true**. Fifty-one days do have rows. It is the number `./m status` would put
in a badge, the number that goes into a summary, and the number a stranger repeats to somebody else —
and it understates the work by forty-three days while being factually correct and exiting zero.

The break that has no output at all is what the gap does to the tooling. `./m trace` reports
IDs-closed against the ledger, so every ID assigned to days fifty-one onwards reads as open. The
traceability index — the thing a stranger consults to find where a concept is taught — points at days
whose teaching exists and whose rows do not, and reports the concept as unfinished.

And the gap is not static. Every day written without a row makes it one longer and makes the eventual
backfill slightly harder, because reconstructing a row means recovering the commit hash and date for
work that has receded further into the log.

## In production

**What a professional does.** Makes the record a side effect of the work rather than a step after it.
`./m done N` already exists for precisely this: it refuses to commit until the checklist is ticked and
the checks are green, and it appends the row itself. A ledger that can only fall behind if somebody
takes a different path is a ledger that does not fall behind — and the failure here is not
indiscipline, it is that a different path existed and was easier.

**What degrades at scale.** Reconstruction cost grows faster than the gap. One missing row is a
`git log` lookup; forty-three is a reconciliation with judgement calls in it — which commit, which
date, which gate mark — and every one of those judgement calls is a small opportunity to record
something that is not quite true.

**The failure that only shows with real traffic.** The ledger gets read for a purpose nobody
anticipated. It was written as a progress log; `./m brief` turned it into a gate, so a stale ledger
now disables the tool whose job is keeping the days in order. Any record kept long enough acquires
readers it was not designed for, and its gaps become their problem rather than its author's.

**The review comment a senior engineer leaves:** *"Backfill from `git log` before this goes public.
The information is all there today and it will still be there in six months, at four times the
effort — and until it is done, our own README's headline claim about picking up from the last row is
false."*

**The interview question:** *"Your changelog is three months behind. Does it matter?"* The answer that
shows experience does not argue about documentation discipline. It asks what **reads** the changelog —
a release process, an audit, a tool, a newcomer — and observes that every one of them has lost the
ability to distinguish *not done* from *not recorded*, which is a different and worse failure than
being out of date.
