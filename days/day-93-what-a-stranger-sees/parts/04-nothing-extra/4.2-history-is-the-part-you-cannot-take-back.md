# 4.2 — History is the part you cannot take back

## One-line answer

Publishing a repository publishes every commit in it, so the question is never what the files contain
now but what they have **ever** contained — and scanning all two thousand three hundred and sixty-one
blobs in this repository's history finds the same two placeholders, already committed, already
permanent.

## The story

The photocopy of your ID at the hotel desk.

You hand it over at check-in because that is how it works. Somebody photocopies it, staples it to a
form, and puts it in a drawer. You get the original back and think nothing more about it.

The copy is not yours any more. You cannot ask for it back in any meaningful sense — you do not know
how many were made, which drawer it is in, whether the drawer is locked, or what happens to the file
when the hotel changes hands. Nothing has gone wrong and there is nothing to fix. It is simply out,
and *out* is a one-way state.

The only decision you ever really had was at the desk, before you handed it over.

## The idea in plain language

Git stores every version of every file. A commit is not a snapshot that replaces the last one; it is
an addition, and everything that came before remains reachable.

This has a consequence that surprises people the first time and costs them the second: **deleting a
secret does not remove it.** A key committed on Monday and deleted on Tuesday is in Monday's commit
forever. The file at `HEAD` is clean, every scan of the working tree is green, and the string is
three keystrokes away for anybody who has the repository.

Making a repository public publishes all of it — every commit, every branch, every blob. So the
scan in part [4.1](4.1-the-scan-before-the-door-opens.md) answers the wrong question on its own. It
asks *is there a key in the files?* The question that decides whether you can safely publish is
**was there ever one?**

Those two questions have different answers often enough that the second one is the whole reason
history scanning exists. And they have a third property worth stating plainly: once the answer to the
second is yes and the repository is public, **rewriting history is not a remedy**. You can rewrite it,
and you should, and the string has already been cloned, cached, indexed and mirrored. The only
remedy that works is rotating the key.

## Why Sutra needs it

Because sixty-nine commits of this repository exist and none of them has ever been examined. Every
`.gitignore` rule was written to prevent a key entering a commit; nothing has ever verified that the
prevention worked on the commits that already happened.

And because the two hits from part [4.1](4.1-the-scan-before-the-door-opens.md) are not in the
working tree only. They are committed. That is the difference between *"fix the placeholders before
publishing"* and *"the placeholders are in the history regardless"*, and it changes what fixing them
means.

## The mechanism

Walking history means asking git for every object, not for every file:

```python
    paths = {}
    for line in git("rev-list", "--all", "--objects").splitlines():
        parts = line.split(maxsplit=1)
        if len(parts) == 2:
            paths[parts[0]] = parts[1]
```

**Line by line:**

- `rev-list --all --objects` lists every object reachable from **every** ref — branches, tags, the
  lot — as `<sha> <path>` pairs. Scanning only the current branch would miss a key committed on a
  branch that was merged, or one that still exists unmerged.
- `split(maxsplit=1)` because paths contain spaces. Splitting on all whitespace truncates any path
  with a space in it, and the first version of this loop did exactly that and died with
  `ValueError: not enough values to unpack` on the commit objects, which have a sha and no path.
- The `len(parts) == 2` guard is that same fix stated positively: commits and trees appear in this
  listing with no path, and they are not what is being scanned.

Reading the contents is one subprocess rather than thousands:

```python
    out = subprocess.run(
        ["git", "cat-file", "--batch"],
        cwd=ROOT,
        input="\n".join(paths).encode(),
        capture_output=True,
    ).stdout
```

**Line by line:**

- `cat-file --batch` takes a list of shas on stdin and streams back `<sha> <type> <size>\n<content>\n`
  for each. Three and a half thousand separate `git show` calls would take a noticeable while and
  produce identical output; this is one process.
- The output is bytes and is parsed by **walking the size headers**, not by splitting on newlines —
  blob contents contain newlines, so any line-based parse of this stream is wrong on the first text
  file it meets.
- Blobs only. Trees and commits come back in the same stream and are skipped by type.

Run it:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python secrets.py --history; echo "exit: $?"
```

**Line by line:**

- `--history` swaps the working-tree walk for the object walk. Everything downstream — the patterns,
  the masking, the exit code — is identical, so the two arms are comparable.

Measured on 2026-09-07:

```text

    AIzaSyD-...(39 chars)
  google api key    days/day-88-the-mcp-sidecar/parts/03-what-the-manifest-must-say/3.2-the-pin-on-the-back-of-the-card.md
    AIzaSyD-...(39 chars)

```

**The same two, and that is the good news.** History holds nothing the working tree does not — no key
was ever committed and later removed. Ninety-three days, sixty-nine commits, and Principle 9 held
throughout.

It also settles what the placeholders now are. They are not *about to be published*; they are
**already committed**, so editing them at `HEAD` improves every future scan and changes nothing about
what a stranger can recover. For a placeholder that is entirely fine — there is nothing to protect —
and it is worth being clear that the same sentence about a real key would be a serious problem.

The scale, for orientation:

```bash
cd "$(git rev-parse --show-toplevel)"
echo "commits: $(git rev-list --all --count)"
echo "objects: $(git rev-list --all --objects | wc -l)"
```

**Line by line:**

- Two numbers a person can hold: how many commits, and how many objects those commits reference.

Measured on 2026-09-07:

```text
commits: 69
objects: 3503
```

Sixty-nine commits, three and a half thousand objects, of which two thousand three hundred and sixty-
one are blobs the scan actually read. That is a small repository, and the scan is quick. It gets
slower with age, which is the argument for scanning per commit rather than per audit.

## When it breaks

The composite failure here is the most expensive one in this whole day, and every step is ordinary:

```text
1. a key is pasted into a config file while debugging
2. it is committed, because `git add -A` takes everything
3. it is noticed and deleted in the next commit
4. every scan of the working tree is green from then on
5. the repository is made public
6. the key is live, in a commit, in a public repository
```

Step 4 is the trap. A working-tree scan is not merely incomplete here — it is **actively
reassuring**, and its green result is what stops anybody looking further.

The second break is believing a rewrite fixes step 6. It does not, and the honest sequence after a
real key reaches a public repository is short and in this order: **rotate the key first**, then
rewrite the history if you want to, then assume the old value is compromised regardless. Automated
scrapers watch public repositories for exactly these patterns and act on them faster than a person
can.

There is no error text for any of it. Git is behaving perfectly; keeping everything is what it is for.

## In production

**What a professional does.** Scans at the point of commit, because that is the last moment the
remedy is cheap. A pre-commit hook that refuses the commit costs a second; a CI scan on the branch
costs a rebase; a scan before release costs a rotation and an incident. The controls are the same
patterns at three different prices, and organisations that have been burned move them earlier rather
than making them cleverer.

**What degrades at scale.** History only grows, so a full-history scan gets slower every month and is
eventually run less often — which is exactly backwards, because the risk accumulates in the same
direction. The usual resolution is to scan incrementally on every push and keep the full sweep for
occasional audits.

**The failure that only shows with real traffic.** A repository that was public, made private, and
made public again. Forks, mirrors and caches taken during the public window persist, and people
reason about the current visibility rather than the union of every visibility it has ever had. The
same applies to a repository whose owner changes: what the previous owner published is not
retractable by the new one.

**The review comment a senior engineer leaves:** *"History scan is clean, which is what we needed to
know before flipping this public. Add it to CI as a full sweep on a schedule and a diff scan on every
push, and write the rotate-first rule into SECURITY.md while we are creating that file anyway."*

**The interview question:** *"You committed an API key and pushed. What do you do?"* The answer that
shows experience says **rotate it first** and explains why the order matters: a rewrite takes minutes
during which the key is live, and a scraper does not wait. Everything else — force-push, contact the
forge, purge caches — is cleanup after the exposure has already been ended by rotation.
