# 4.1 — The scan before the door opens

## One-line answer

Two thousand one hundred and twenty-one tracked files, six key shapes, two hits — and both hits are
teaching placeholders shaped exactly like a real key, which is the result a pre-publication scan
actually produces and the reason triage is a person's job rather than the scanner's.

## The story

Turning out your pockets before the laundry.

Everybody has a version of this. You do it because once, a long time ago, a note went through the
wash and came out grey and pulped and stuck to a shirt, and since then the check takes a moment and
happens every time.

Most days there is nothing. Some days there is a receipt, a bus ticket, a coin. Occasionally there is
something that would have mattered.

What makes the habit work is not that it finds things often — it almost never does. It is that it
happens **before**, and that the cost of doing it is so small that there is no argument to have. A
check you would skip when busy is not a habit; this one survives because it is free.

## The idea in plain language

Principle 9 has been in force since Day 0: *secrets never touch git, and this repository goes public
in Phase 14*. Every `.gitignore` line, every `.env.example` with names and no values, every day that
read a key from the environment rather than a literal — all of it was written for the moment the
repository becomes visible.

This is that moment, and the question is no longer *did we intend to keep keys out?* It is **is there
one in there?**

A scan for that has a shape worth understanding before running it. It does not look for "secrets",
because there is no such thing to look for. It looks for the **specific string shapes** that specific
vendors issue: a Google API key starts `AIza` and runs thirty-nine characters; a Groq key starts
`gsk_`; an OpenRouter key starts `sk-or-v1-`; a PEM private key opens with a line nobody types by
accident.

That shape-matching has two consequences and both matter:

**It misses anything not on the list.** A password, a session cookie, a customer's email address, a
key from a vendor you did not think of — invisible. The scan proves nothing about them.

**It hits things that are not secrets.** Anything shaped like a key is a key to a regular expression,
including an example in a lesson about not committing keys.

So the honest description is: this finds a known list of high-value shapes, cheaply, and every hit
needs a human. The scanner's job is to **stop the merge**, not to decide.

## Why Sutra needs it

Because ninety-three days of teaching material contain a great deal of configuration, and
configuration is where keys live. Days 87 and 88 both show a config file with an API key field in it,
because that is what the field looks like — and a lesson that writes `<your key here>` teaches less
than one that shows the shape a reader will actually see.

And because this is the last check before the promise made on Day 0 is either kept or broken, and it
has never been run. Every previous day's `.gitignore` line was a precaution. This is the measurement.

## The mechanism

The patterns are the whole design, and they are grouped by issuer:

```python
SECRET_PATTERNS = {
    "google api key": re.compile(rb"AIza[0-9A-Za-z_\-]{35}"),
    "groq key": re.compile(rb"\bgsk_[0-9A-Za-z]{40,}"),
    "openrouter key": re.compile(rb"\bsk-or-v1-[0-9a-f]{48,}"),
    "openai key": re.compile(rb"\bsk-[A-Za-z0-9]{40,}"),
    "aws access key id": re.compile(rb"\bAKIA[0-9A-Z]{16}\b"),
    "private key": re.compile(rb"-----BEGIN [A-Z ]*PRIVATE KEY-----"),
}
```

**Line by line:**

- Byte patterns (`rb"..."`), not text. Files get read as bytes so that a file which is not valid
  UTF-8 — an image, a lockfile with odd encoding, a partially written blob — is scanned rather than
  skipped or crashed on.
- `AIza` plus exactly thirty-five characters, because that is the shape Google issues. A looser
  pattern would match half the base64 in the repository.
- `\b` word boundaries on the prefixed ones so `gsk_` inside a longer identifier does not match.
- The dictionary is keyed by **the vendor's name**, because that is what a person doing triage needs
  first: knowing it is a Google key tells you which console to go and rotate it in.
- The list is deliberately short and high-value. A pattern for "anything that looks random" would
  find hundreds of hashes and teach everybody to ignore the output.

The rule that matters more than the patterns:

```python
def mask(value: bytes) -> str:
    """Enough to recognise the vendor, never enough to use."""
    text = value.decode("utf-8", errors="replace")
    return f"{text[:8]}...({len(text)} chars)"
```

**Line by line:**

- Eight characters is the vendor prefix and nothing else — enough to say *this is a Google key*, not
  enough to authenticate with.
- The length is reported because it is the other half of triage: a thirty-nine character string
  matching `AIza` is the right length for a real key, and a fifteen-character one is obviously a
  fragment.
- A scanner that printed the value would publish it into a terminal, into CI logs, and into whatever
  ships those logs — **the report becomes the leak**. The `--loud` arm exists in the lab only to make
  that concrete, and it says so when you use it.

Run it:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python secrets.py; echo "exit: $?"
```

**Line by line:**

- No flag: the working tree, as git tracks it. Untracked files are irrelevant — they are not going
  anywhere.

Measured on 2026-09-07:

```text
scanned: 2121 tracked files
patterns: google api key, groq key, openrouter key, openai key, aws access key id, private key

  google api key    days/day-87-config-not-billed/parts/02-the-config/2.1-the-config-file-adk-reads.md
    AIzaSyD-...(39 chars)
  google api key    days/day-88-the-mcp-sidecar/parts/03-what-the-manifest-must-say/3.2-the-pin-on-the-back-of-the-card.md
    AIzaSyD-...(39 chars)

  secret-shaped hits: 2
  every one needs a person to say real or placeholder, and the answer is not
  in the string - it is in what the string was for
```

**Two hits, both thirty-nine characters, both the right shape.** From the report alone they are
indistinguishable from real keys. Opening the files settles it in seconds — one ends in a run of
zeroes, the other ends in the words *OfTheLesson* — and both are illustrations inside lessons about
configuration.

So: **zero real secrets across two thousand one hundred and twenty-one tracked files and ninety-three
days.** That is Principle 9 held, and it is the headline. The two false positives are the second
finding, and they are worth fixing — a placeholder that matches a vendor's pattern will fire this
scan forever, and every future run will cost somebody the same minute of triage. Making the examples
obviously fake (`AIza-EXAMPLE-NOT-A-KEY`) costs nothing and retires the noise permanently.

## When it breaks

The scanner breaks in three ways and only the first is loud.

**It reports what it found.** The lab has a `--loud` arm for exactly one purpose: to make it obvious
that a scanner which prints values has published them. It prints an extra line saying so. Nobody
should ever run it on a repository they care about, and it is in the lab because the mistake is
common enough in home-made tooling to be worth seeing once.

**It finds only what is on the list.** Two hits does not mean two secret-shaped strings exist; it
means two matched **these six patterns**. A password in a fixture, a bearer token in a recorded HTTP
transcript, a customer's real email in a test case — none of those are on the list, and the green
half of any run says nothing about them.

**Its false positives train people to skip it.** Both hits here are placeholders. If that stays true
for six months, the scan becomes a step people click through — which is Day 87's shop-door gate
beeping at library books, arriving in a different tool. The defence is not a better regex; it is
fixing the placeholders so the alarm goes back to meaning something.

There is no error text for any of these. Every arm exits cleanly and prints something true.

## In production

**What a professional does.** Runs the scan on every commit rather than before every release, because
a secret committed on Monday and found on Friday has been in the history for four days and is already
unrecoverable — which is part [4.2](4.2-history-is-the-part-you-cannot-take-back.md). Mature setups
also run it as a pre-commit hook so the key never enters a commit at all, and treat the CI scan as
the backstop for the hook somebody bypassed.

**What degrades at scale.** False positives grow with the repository and true positives do not, so
the signal-to-noise ratio of a fixed pattern list falls monotonically. That is why real scanners
carry an allowlist of known-benign matches, reviewed like code — an allowlist entry is a person
saying *"I looked at this one"*, with their name on it.

**The failure that only shows with real traffic.** A key in a place nobody scans. Scans cover tracked
text files; keys reach the world through a screenshot in an issue, a log pasted into a chat, a
recorded terminal session in a demo video, or a notebook's saved output cell. This repository has an
untracked `experiment.ipynb` at its root, ignored by `.gitignore` line 37 — which is the correct
treatment, and it is correct precisely because notebook output cells are a classic leak.

**The review comment a senior engineer leaves:** *"Zero real hits is the right result and I would
still fix the two placeholders. Make them obviously fake so the scan stays meaningful, and put this
in CI before we flip the repository public, not after."*

**The interview question:** *"How do you stop secrets getting into a repository?"* The answer that
shows experience puts the controls in order — `.gitignore` and environment variables first, a
pre-commit hook second, a CI scan third — and then makes the point that all three are prevention, and
that once a key is committed the only real remedy is rotation.
