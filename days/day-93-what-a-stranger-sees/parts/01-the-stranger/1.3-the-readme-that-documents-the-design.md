# 1.3 — 💥 The README that documents the design

## One-line answer

Three claims in this repository's README are checkable against the thing that enforces them, and all
three have drifted — the section count is wrong three different ways, two driver commands are
undocumented, and the day-folder diagram omits a directory the README's own Status paragraph
announces.

## The story

💥 **The wedding invitation with the venue left off.**

🎬 **The scene.** The card is beautiful. Thick paper, the names, the date, the time, a line of
verse. Five hundred of them, printed and distributed, and everybody who receives one is pleased.

😬 **The naive fix.** It was proofread. Three people read it before it went to the printer, and all
three read it carefully.

💥 **Why it fails.** All three knew where the wedding was. Their eyes passed over the block where an
address would go and found nothing missing, because nothing was missing *for them* — the information
was in their heads, supplied silently, every time they read the card. The proofreaders were the
worst possible readers for that specific defect, and they were chosen because they cared most.

💡 **The insight.** **A document cannot be proofread by anybody who already knows what it says.** The
only reliable check is one that does not know: read the card back against the venue booking, field
by field, and let the mismatch be a mismatch rather than a thing a mind smooths over.

## The idea in plain language

A README makes claims. Most are prose and unfalsifiable — *"nothing here is a toy demo"* is a
statement of intent. But some are **facts about the repository**, and a fact has an owner: something
in the tree that decides whether it is true.

Three of this README's claims have such an owner:

| The claim | Who owns the truth |
| --- | --- |
| "Every part runs the same ten sections" | `scripts/depth_check.py`, which enforces the list |
| the `./m` subcommand list | the `m` driver, which implements them |
| the day-folder tree diagram | plan §17, and any real day folder |

Each of those can be checked mechanically, and none of them ever had been. What the check finds is
not three unrelated errors. It is **one event, showing up in three places** — the plan version that
added a `papers/` directory to the day format — and the README records that event in its own Status
section while three other sections still describe the format from before it.

That is the characteristic shape of documentation rot. Not neglect: the README was updated. It was
updated *in the place the author was looking*, and the other places kept their old, confident,
carefully-written sentences.

## Why Sutra needs it

Because a stranger who trusts this README is wrong about the day format before they open their first
day. They will look for ten sections in a document that has eleven, not find the two about papers,
and conclude the document is inconsistent — when the README is.

And because `./m brief` and `./m wiki` are the two commands `CLAUDE.md` describes as the first thing
to run, *"Always, before anything"*. Neither appears in the README's driver list. The repository's
own instructions to its agent and its instructions to a human have diverged, and only one of them
gets read by a stranger.

## The mechanism

The check does not compare the README against a copy of the truth. It imports the enforcer:

```python
def enforced_sections() -> list[str]:
    """The section list depth_check.py actually requires, imported from the checker itself."""
    spec = importlib.util.spec_from_file_location(
        "depth_check", ROOT / "scripts" / "depth_check.py"
    )
    module = importlib.util.module_from_spec(spec)
    # depth_check defines a @dataclass at import time, and dataclasses resolves annotations by
    # looking the module up in sys.modules. Without this line the import dies with
    # AttributeError: 'NoneType' object has no attribute '__dict__'.
    sys.modules["depth_check"] = module
    spec.loader.exec_module(module)
    return [name for name, _pattern in module.PART_SECTIONS]
```

**Line by line:**

- Loading `depth_check.py` by path rather than importing a hard-coded list. A check that carries its
  own copy of the answer drifts exactly like the README does, and then two documents disagree with
  a third.
- `sys.modules["depth_check"] = module` **before** `exec_module`. `depth_check.py` declares a
  `@dataclass`, and `dataclasses` resolves the class's annotations by looking its module up in
  `sys.modules`; if it is not registered yet the lookup returns `None` and the import dies. That
  traceback is quoted in **When it breaks** — it cost a run to find and it is the sort of thing that
  makes people give up on dynamic imports.
- `PART_SECTIONS` is a list of `(name, pattern)` pairs, so the names come out by discarding the
  regexes. The names are what the README is compared against.

The README's own list wraps across lines, which matters more than it sounds:

```python
    flat = re.sub(r"\s+", " ", sentence.group(2)).lower() if sentence else ""
    listed = len(re.split(r"·", flat)) if sentence else 0
```

**Line by line:**

- The whitespace is flattened **before** anything is compared. Without this, `"the idea in plain
  language"` fails a substring test purely because the README breaks the line between *idea* and
  *in* — and the check reports two sections missing that are plainly there. That was the first
  version's output and it is a false positive of exactly the kind Day 87 part 3.3 warned about: a
  checker whose noise trains people to ignore it.
- Splitting on `·` counts what the README *lists*, which is a different number from what it *says*.
  Keeping them separate is the whole point; a check that only compared the claimed number against
  the enforced one would have missed that the sentence disagrees with itself.

eleven are enforced. The two the list omits are `the paper behind it` and `the paper in one demo` —
precisely the two sections that arrived with the `papers/` directory, which is the same change the
README's Status paragraph describes in its own words a few screens further down.

## When it breaks

**The way the check itself broke first**, before the `sys.modules` line existed:

```text
  File "C:\...\scripts\depth_check.py", line 175, in <module>
    @dataclass
  File "...\dataclasses.py", line 749, in _is_type
    ns = sys.modules.get(cls.__module__).__dict__
AttributeError: 'NoneType' object has no attribute '__dict__'
```

A traceback pointing at `dataclasses.py` for a mistake that is three frames up, in how the module
was loaded. Worth recognising: it means *this module is not in `sys.modules`*, and it is what you
get whenever a file containing a dataclass is loaded by path.

**The way the README breaks**, which produces no traceback at all:

```bash
uv run python readme_contract.py --prose; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  read as prose, every sentence above is a confident description of a real system
exit: 0
```

That is what proofreading does. Read as prose, the README is good: well written, confident,
internally plausible. Every drifted claim is a fluent sentence about a format that existed once. The
`--prose` arm exits `0` because reading cannot fail, and that is the whole finding — the invitation
was proofread three times.

The third break is the one this check cannot see: a claim with **no** owner. *"Nothing here is a toy
demo"* cannot be checked by anything, so it can be as wrong as it likes for as long as it likes. The
checkable claims are the minority, and a green run over them is not a correct README.

## In production

**What a professional does.** Makes the checkable claims checked, in CI, and keeps the unfalsifiable
ones short. The practical form is that any number in a README either comes out of the code at build
time or has a test asserting it — and if neither is affordable, the number is deleted, because a
wrong number costs more than a missing one.

**What degrades at scale.** README drift is monotone: it only ever gets worse, because every change
to the system is an opportunity to forget the document and no change is an opportunity to remember
it. The rate is roughly proportional to how many places the same fact is written, which is the
argument for writing it once and generating the rest — the paper part is about exactly that.

**The failure that only shows with real traffic.** Strangers act on the wrong claim and produce work
you then have to reject. Someone writes a part with nine sections because the README said so, `./m
depth` refuses it, and they conclude the tooling is broken rather than the document. You lose a
contributor and never learn why.

**The review comment a senior engineer leaves:** *"Do not fix the number by hand — that is how it got
wrong. Generate the section list from `depth_check.PART_SECTIONS` into the README, and add the two
missing driver commands while you are there."*

**The interview question:** *"How do you keep documentation from going stale?"* The weak answer is
review discipline. The answer that shows experience separates claims that have an owner from claims
that do not, puts the first kind under a check, and shortens the second kind — because a document
nobody can falsify is a document nobody can maintain.
