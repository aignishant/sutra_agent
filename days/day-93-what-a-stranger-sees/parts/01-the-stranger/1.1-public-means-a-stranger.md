# 1.1 — Public means a stranger with no context

## One-line answer

Making a repository public does not publish the code — the code was always there — it publishes
**everything you assumed**, to somebody who shares none of your assumptions and will not ask.

## The story

Giving directions to your own house.

Somebody is coming for the first time and rings from the main road. You say: *"take the left after
the big tree, go past the temple, and it's the third gate — you'll see the blue water tank."*

Every word of that is true. You have said it to a dozen people and it has always worked.

It works because everyone who has come before had been in the area, or had somebody with them who
had. The stranger on the phone has not seen the tree, does not know which of the four turnings you
mean by *the left*, and is standing in front of a temple that is not the temple you mean.

You did not give bad directions. You gave directions **from inside**, and the whole difficulty is
that from inside, they are indistinguishable from good ones.

## The idea in plain language

For ninety-two days this repository has had exactly one reader, and that reader wrote it. Every
document has been checked against a mind that already knows what `./m` is, why `.env` is not
committed, what a "part" is, and that the product code is deliberately absent.

Making it public swaps that reader for one who knows none of it. And the swap has three properties
that make it harder than it sounds.

**The stranger will not ask.** A colleague stuck on your setup instructions sends a message. A
stranger closes the tab. You never find out which sentence lost them, so the feedback loop that
would fix the documentation does not exist.

**The stranger starts at a file you did not choose.** You think of the repository as beginning at
the README. They may arrive from a search result pointed at one part of one day, with no idea that
there are ninety-three of them.

**Everything is published at once, including the things you meant to tidy.** Not just the code:
the commit history, the half-finished ledger, the working notes you dot-prefixed so your own `ls`
would stop showing them. Git does not distinguish between what you are proud of and what you left.

So the work of this day is not writing. It is **reading the repository as somebody who has never
seen it**, and the only reliable way to do that is to stop reading and start running: a check has no
context to fill the gap with.

## Why Sutra needs it

Because Principle 9 has been a promise since Day 0 — *secrets never touch git, and the repo goes
public in Phase 14* — and this is the day the promise is tested rather than stated. Every
`.gitignore` line written on Day 0 was written for today.

And because this repository's whole claim is that the repo is the memory. Day 82 part 5.2 argued
that a record is only worth keeping if somebody can act on it; a public repository is that argument
with the audience widened from *you, six months from now* to *anybody*. If the ledgers, the README
and the day documents cannot orient a stranger, they will not orient you either — you just have not
noticed, because you keep filling the gaps from memory.

## The mechanism

The unit of this day is a **check**: something that reads the repository and exits non-zero when a
stranger would be stuck. Seven of them, and `gate.py` runs the lot:

```python
CHECKS = (
    Check("1  the front door answers a stranger", "firstfiles.py", "--readme-only"),
    Check("2  the README describes what exists", "readme_contract.py", "--prose"),
    Check("3  every relative link resolves", "links.py", "--naive"),
    Check("4  broken links have an owner", "owners.py", "--one-pile"),
    Check("5  nothing secret-shaped is tracked", "secrets.py"),
    Check("6  the ledger matches the day folders", "ledger.py", "--count"),
    Check("7  the cold-start demo runs", "demo.py", "--pretend"),
)
```

**Line by line:**

- Seven checks, each a separate script with its own exit code — the same shape as Day 78's and Day
  83's phase gates, for the same reason: a check that can only be read is not a check.
- The third field is a **fault flag**, and here it means something different from the earlier gates.
  On Day 83 the fault made a passing check go red. Here the flag makes a failing check go
  *green* — `--readme-only`, `--prose`, `--count`, `--pretend` are each the comfortable version of
  the same question, and the gate runs them to show what the comfortable version costs.
- None of the seven runs the agent, opens a network connection or spends a request. Everything a
  stranger meets before the system runs is checkable for nothing.

Run the whole thing:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python gate.py | tail -14
```

**Line by line:**

- `tail -14` for the verdict block; each check prints its own findings above it, and those are what
  you act on.

Measured on 2026-09-07:

```text
=== verdict
  FAIL              1  the front door answers a stranger
  FAIL              2  the README describes what exists
  FAIL              3  every relative link resolves
  FAIL              4  broken links have an owner
  FAIL              5  nothing secret-shaped is tracked
  FAIL              6  the ledger matches the day folders
  FAIL              7  the cold-start demo runs

  0 pass, 7 fail

  This repository is NOT ready to be public.
```

**Zero of seven.** Not because the repository is bad — ninety-three days of it are depth-checked and
green — but because not one of these seven questions had ever been asked. That is the shape of the
finding and it is worth sitting with: the work was fine and nobody had looked at it from outside.

## When it breaks

The failure mode of this day is reading the checks instead of running them, and it has a specific
signature: you look at check 1, think *"well, we know there is no LICENSE"*, and move on. That is
the directions problem again — the gap is filled from inside, and filling it is exactly what the
stranger cannot do.

There is no error text, because nothing errors. Here is what the same seven checks report when each
is asked its comfortable version instead:

```text
  firstfiles.py       --readme-only 1 -> 0  GOES GREEN
  readme_contract.py  --prose       1 -> 0  GOES GREEN
  links.py            --naive       1 -> 1  still red
  owners.py           --one-pile    1 -> 1  still red
  ledger.py           --count       1 -> 0  GOES GREEN
  demo.py             --pretend     1 -> 0  GOES GREEN
```

Four of the six flip to green, and every sentence those green runs print is true. This is the fourth
phase running in which the arm that hides the finding is the arm that exits zero — Day 79's suite
that could not fail, Day 81's accuracy with no baseline, Day 82's nightly that reported it ran, Day
83's gate that counted checks. The pattern is not a coincidence: a reassuring report is always
cheaper to produce than a useful one.

## In production

**What a professional does.** Hands the repository to somebody who has not seen it and watches them,
without helping. Ten minutes of that finds more than a day of self-review, because the thing being
measured is precisely the context you cannot switch off in your own head. Where no such person is
available — which is most of the time — the substitute is a check, because a script has no context
either.

**What degrades at scale.** The gap between what a repository assumes and what it states grows with
every commit, and only ever in one direction. Every day you work in it, you learn something that
does not get written down, and that knowledge silently becomes a prerequisite. Ninety-two days is
long enough that the author of Day 0 and the author of Day 92 are effectively different people, and
only one of them left notes.

**The failure that only shows with real traffic.** A stranger arriving at a deep link. Search
engines index a repository file by file, so the first page somebody reads may be
`days/day-57-orchestrator-and-critic/parts/03-.../3.2-....md`, which opens mid-argument and links
sideways. Every day document in this repository is written to be readable cold — that is plan §17's
standalone test — but nothing has ever verified that the *links out* of a cold-read part land
somewhere that orients the reader, and this day does not verify it either.

**The review comment a senior engineer leaves:** *"Before we flip it public, run the checks as a
gate rather than reading them as a list. And do not fix the findings by editing the checks."*

**The interview question:** *"What changes when a repository goes from private to public?"* The
answer that shows experience does not say "people can see the code". It says that everything the
team knew and never wrote down becomes a defect, and that the history goes public too — so the
question is not what is in it now, but what was ever in it.
