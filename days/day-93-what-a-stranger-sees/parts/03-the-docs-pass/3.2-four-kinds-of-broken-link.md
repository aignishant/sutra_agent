# 3.2 — Four kinds of broken link

## One-line answer

The fifty broken links are not fifty tasks — three need a person to edit a day document, twenty-two
are a generator bug that will come back if you edit the file instead, seven are stale output a re-run
repairs, and eighteen are in a frozen archive nobody should touch.

## The story

The complaint register where every entry is another department.

A ledger on a counter, and people write in it: the tap on the second floor, the lift, the light
outside, the parking. By the end of the month there are forty entries and the manager is asked why
nothing has been done.

The honest answer is that "forty complaints" was never a task. The tap is plumbing. The lift is an
annual contract with an outside firm. The light belongs to the municipality and no amount of
internal effort will fix it. The parking is a rule, not a repair — nothing is broken, people are
parking wrongly.

Four entries, four completely different actions, and the number forty concealed all of it. What the
manager needed was not a shorter list. It was the same list with a column saying **whose**.

## The idea in plain language

Part [3.1](3.1-seventeen-thousand-links.md) produced a number. A number is where a docs pass usually
stops, and it is the least useful form the information takes, because it invites the question *"can
we get it to zero?"* when the right question is *"which of these is mine?"*

Sorting the fifty by the path they live in gives four groups, and the groups have nothing to do with
each other:

**Rot in the teaching.** A day document links to a part that was renamed or never written. A person
has to open the file, work out what was meant, and fix it. This is the only group that is a writing
task.

**Stale output.** `docs/CURRICULUM_INDEX.md` is regenerated by `./m trace`, and its seven bad links
point at days that did not exist when it was last generated. Editing the file is pointless — the next
run overwrites it — but nothing is wrong with the generator, and a re-run repairs all seven.

**A generator bug.** `docs/wiki/` is regenerated by `./m wiki`, and its twenty-two bad links come
back on every run, because the generator produces them. Same "do not edit the file" rule, opposite
conclusion: this one needs a code change, and part
[3.3](3.3-the-index-that-regenerates-broken.md) finds it.

**A frozen archive.** `legacy/` is the previous run of this project, kept read-only and explicitly
never linked from a current day. Its internal links point at documents that were not carried over.
Nothing should be edited here — the choice is to exclude the directory from the check or to accept
the count.

That gives four distinct pieces of work from one number, and only one of them is writing.

## Why Sutra needs it

Because the difference between three and fifty is the difference between an afternoon and a project,
and the number that goes into a hand-over note decides whether anybody starts. Day 83 part 5.3 made
the same argument about phase findings: a list that is not ordered by owner is a backlog, and a
backlog is where things go to age.

And because two of the four groups would be *actively harmed* by the obvious fix. Editing a
generated file to correct a link produces a green check, a satisfied reviewer, and a file that
reverts the next time anybody runs the generator — leaving the original cause in place and one more
person convinced it was already handled.

## The mechanism

The classifier is a table of path prefixes, in priority order:

```python
OWNERS = (
    ("legacy/", "the archive", "read-only first run; exclude it or leave it alone"),
    ("docs/wiki/", "the wiki generator", "a generator bug: re-running reproduces these"),
    ("docs/CURRICULUM_INDEX.md", "the trace generator", "stale output: re-running fixes these"),
    ("days/", "the day that wrote it", "real rot in the teaching; a person edits the part"),
)
```

**Line by line:**

- Ordered, and the first match wins. `docs/wiki/` has to be tested before any broader `docs/` rule
  would be, or every generated page lands in the wrong bucket.
- Each row carries **what to do**, not just who owns it. "The wiki generator" tells you whose it is;
  "re-running reproduces these" is the sentence that stops somebody editing the file by hand — and it
  is deliberately different from the trace row's "re-running fixes these", because the same advice
  would be wrong for one of them.
- `days/` is last and broadest, so anything under a day that is not more specifically claimed counts
  as teaching rot — the safe default, because that group is the one a person must actually read.
- The table is data rather than a chain of `if`s so that adding a group later is a row, not a code
  change. There will be more groups: `skills/` and `sutra_mcp/` will have documentation eventually.

The fallthrough matters as much as the table:

```python
def owner_of(path: str) -> tuple[str, str]:
    for prefix, who, what in OWNERS:
        if path.startswith(prefix):
            return who, what
    return "unclassified", "somebody has to decide"
```

**Line by line:**

- An explicit `unclassified` bucket rather than silently dropping the entry or crashing. A classifier
  that cannot classify something must say so — an unclassified row is a prompt to add a rule, and
  discarding it would make the group counts quietly wrong.
- The default text is *"somebody has to decide"*, which is accurate: an unclassified path has no
  owner precisely because nobody has thought about it yet.

Run it:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python owners.py; echo "exit: $?"
```

**Line by line:**

- Same fifty links as part [3.1](3.1-seventeen-thousand-links.md), grouped rather than listed.

Measured on 2026-09-07:

```text
50 broken links, grouped by who fixes them

  owner                  count  what to do
  the wiki generator        22  a generator bug: re-running reproduces these
  the archive               18  read-only first run; exclude it or leave it alone
  the trace generator        7  stale output: re-running fixes these
  the day that wrote it      3  real rot in the teaching; a person edits the part

  a person must edit a day document  : 3
  a generator must be fixed           : 22
  a generator need only be re-run     : 7
  nobody: the archive is frozen       : 18

  the same 50 links, and four completely different pieces of work
```

**Three, twenty-two, seven, eighteen.** The largest group is the one nobody should touch, and the
smallest is the only one that is a documentation task. A docs pass that started at the top of an
alphabetical list of fifty would spend most of its effort in `legacy/`, achieve nothing, and stop
before reaching the three that matter.

Note that the two generated groups are **not** the same job either, which part
[3.3](3.3-the-index-that-regenerates-broken.md) is about: seven of them are stale output that a
re-run repairs, and twenty-two are a bug a re-run reproduces.

## When it breaks

The check breaks by reporting the total, which is the form the information naturally takes:

```bash
uv run python owners.py --one-pile; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  50 broken links

  one number, one backlog ticket, and nobody knows whose it is
exit: 1
```

True, red, and unactionable. It is the same fifty and it will produce a ticket titled *"fix broken
documentation links"* which will be estimated once, deferred twice, and closed as stale.

The subtler break is a classifier that is **confidently wrong**, and this one has a real exposure to
it. `legacy/` is treated as frozen because `CLAUDE.md` says the archive is read-only and never linked
from a day. If that rule ever changes — if some legacy document becomes a live reference — eighteen
broken links silently become somebody's problem and the classifier will keep saying nobody's. The
rule is in a document; the classifier encodes it; nothing connects the two.

There is no error text for any of this. Every arm of this check exits `1` and prints something true.

## In production

**What a professional does.** Routes findings before counting them. Any check that produces a list
over a large tree gets an owner column, because the first question in any review is *"is this mine?"*
and a report that cannot answer it gets read once. The corollary is that the owner rules live beside
the check and get reviewed with it, rather than in somebody's head.

**What degrades at scale.** The groups multiply and the boundaries blur. Four prefixes is readable;
twenty is a routing table that itself needs testing, and the failure mode becomes a rule that shadows
another — the reason this table is ordered and the ordering is commented. Beyond that, ownership
usually stops being derivable from a path at all and has to come from a manifest.

**The failure that only shows with real traffic.** The generated groups regenerate. Twenty-nine of
these fifty come back on the next `./m wiki` or `./m trace` unless the generator changes, and a team
that fixed them by hand will see them reappear and conclude the check is flaky. That is how a working
check gets switched off, and part [3.3](3.3-the-index-that-regenerates-broken.md) is that group in
full.

**The review comment a senior engineer leaves:** *"Do the three under `days/` this week. Open one
ticket per generator for the twenty-nine and put the file paths in it as evidence, not as the task.
And decide about `legacy/` — either exclude it in the checker with a comment saying why, or stop
saying it is read-only."*

**The interview question:** *"Your audit found fifty issues. What do you report?"* The answer that
shows experience does not report fifty. It reports the groups, names who owns each, and says which
ones will come back on their own — because the second half is what turns a number into a plan.
