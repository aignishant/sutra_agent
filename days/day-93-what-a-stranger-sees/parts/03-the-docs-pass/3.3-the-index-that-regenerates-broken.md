# 3.3 — 💥 The index that regenerates broken

## One-line answer

Twenty-two of the wiki's links are broken by one line of the generator, which copies a paragraph out
of a day part and into `docs/wiki/` — and a paragraph containing a relative link does not survive
being moved to another directory.

## The story

💥 **The wall calendar with the same wrong date, every year.**

🎬 **The scene.** A shop gives out a calendar each January. Same layout, same festivals marked in
red, printed fresh. People hang it in the kitchen and use it all year.

😬 **The naive fix.** Somebody notices one festival is on the wrong date. They correct their own copy
in pen and mention it at the shop, and the shopkeeper says thank you, we will fix it.

💥 **Why it fails.** The next January's calendar has the same wrong date, because the error is not in
the calendar. It is in the list the printer types from, which nobody has looked at in eleven years.
Every copy that was ever corrected was corrected downstream, one kitchen at a time, and every
correction was thrown away in December.

💡 **The insight.** **A generated artefact cannot be repaired.** Fixing it feels like fixing the
problem, produces a correct object, and guarantees the error returns — while consuming the attention
that would have gone to the list.

## The idea in plain language

`docs/wiki/` is generated. `CLAUDE.md` is explicit about it: the wiki is *"a generated index over the
days, never a substitute for them"*, every line copied from a source file, and *"if an index ever
disagrees with the day it indexes, the day is right and the index is stale — run `./m wiki`"*.

That instruction is right about staleness and it does not cover this. Twenty-two links in
`docs/wiki/` are broken, and running `./m wiki` again produces them again, because they are not
stale — they are **manufactured**.

Here is the mechanism, and it is one sentence: the generator copies each part's one-line answer into
the wiki page, and a one-line answer often contains a link to a sibling part, written relative to the
part's own folder. Move that sentence from
`days/day-73-ambient-agents/parts/02-when-it-dies-at-three-am/` to `docs/wiki/`, and
`[2.3](2.3-two-runs-at-once.md)` now points at `docs/wiki/2.3-two-runs-at-once.md`, which does not
exist and never will.

Nothing was typed wrongly. The link was correct where it was written, the copy is faithful, and the
result is broken — because **a relative link is not a property of the text, it is a property of the
text's location**, and copying moves the text without moving what it means.

## Why Sutra needs it

Because the wiki exists to be the cheap way in. It is the index a stranger uses to find which day
teaches what, and every one of these twenty-two dead ends is in the one-sentence summary that is
supposed to orient them.

And because part [3.2](3.2-four-kinds-of-broken-link.md) put twenty-two links in a group labelled
*"do not edit the file"*, which is only useful advice if somebody then edits the right thing. This
part is that thing.

## The mechanism

Finding the cause takes two steps and no guessing. First, what does the generator actually emit for a
part?

```python
    for doc in day.parts:
        level, ids = doc.front.get("level", "?"), ", ".join(doc.ids) or "-"
        lines += [
            f"### {doc.number} - {doc.title}",
            f"`{doc.rel}` · level `{level}` · ids {ids}",
            "",
            doc.answer or "_(no one-line answer found - the part is incomplete)_",
            "",
        ]
```

**Line by line:**

- `` f"`{doc.rel}`" `` — the path to the part is emitted as **inline code**, not as a link. So the
  generator is not writing any links to parts at all, and the first hypothesis (that it builds a
  wrong path) is wrong. Worth noticing early: it saves an hour.
- `doc.answer` is the part's one-line answer, **copied verbatim**. That is the only free prose on the
  page, so it is the only place a link can come from — which makes it the whole of the suspect list.
- The fallback string for a missing answer is prose too, but it is a constant with no link in it.

Second, look at one of the broken links in place:

```bash
cd "$(git rev-parse --show-toplevel)" && sed -n '37,40p' docs/wiki/day-73.md
```

**Line by line:**

- Four lines around one known-broken link, rather than the whole file.

Measured on 2026-09-07:

```text
### 2.4 - The lock nobody released
`days/day-73-ambient-agents/parts/02-when-it-dies-at-three-am/2.4-the-lock-nobody-released.md` · level `production` · ids AG-24, ADK-51

The lock that fixed part [2.3](2.3-two-runs-at-once.md) is taken in one line and released in none, so a single run that dies while holding it refuses every run after it — measured: the second take_lock() returns False, the file is still on disk, and grep finds exactly two mentions of the lock in the whole file, one to name it and one to create it.
```

There it is. The path on the second line is inline code and correct. The link on the fourth line —
`[2.3](2.3-two-runs-at-once.md)` — is inside the copied answer, is correct in the source part, and is
broken here.

And the class is checkable rather than assumed:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python -c "
from _repo import ROOT, links_in, resolves, tracked
bad = [(p, t) for p in tracked('docs/wiki/*.md') for _n, t in links_in(p) if not resolves(p, t)]
found = sum(1 for _p, t in bad if list((ROOT / 'days').rglob(t.split('/')[-1])))
print(f'broken in docs/wiki/: {len(bad)}')
print(f'whose target exists somewhere under days/: {found}')
"
```

**Line by line:**

- `rglob(t.split("/")[-1])` searches `days/` for a file with the link's **basename**. If the target
  exists under `days/` but not beside the wiki page, the link was written for a different directory —
  which is precisely the copied-prose hypothesis.
- Counting rather than listing, because the claim being tested is *"all of them"*, and a count
  answers that in one line.

Measured on 2026-09-07:

```text
broken in docs/wiki/: 22
whose target exists somewhere under days/: 22
```

**Twenty-two of twenty-two.** Not a sample, not a majority — every single one. One cause, one fix.

## When it breaks

The tempting fix is to correct `docs/wiki/day-73.md`. It works, the link resolves, the check goes
green, and the next `./m wiki` deletes the edit and restores the broken link. That is the calendar.

The second tempting fix is to delete the links from the parts' one-line answers, which would work and
would damage the parts — the link is *right* where it is written, and plan §17's standalone test is
the reason it is there.

The actual fix is in the generator, and it has to rewrite each link as it copies:

```text
copying doc.answer from days/<day>/parts/<section>/  into  docs/wiki/
  [2.3](2.3-two-runs-at-once.md)
    -> [2.3](../../days/<day>/parts/<section>/2.3-two-runs-at-once.md)
```

**Line by line:**

- The rewrite is mechanical: the generator already knows `doc.rel`, the part's path from the
  repository root, so the destination-relative form is derivable without guessing.
- Twelve of the twenty-two are sibling-style (`2.3-....md`) and ten are parent-relative
  (`../01-.../1.2-....md`), so the rewrite has to resolve against the part's folder rather than
  string-concatenate.
- Stripping the link instead — emitting `2.3` as plain text — is a legitimate simpler option, and it
  is a product decision rather than a bug fix.

**This is the third generated artefact in this repository to be quietly wrong.** Day 82 found ADK
writing eval results into a directory `.gitignore` swallowed; Day 83 found a rubric evaluator reading
a transcript the file format could not carry; this is a wiki reproducing broken links on every run.
The shape is the same each time: **two correct components, composed across a boundary neither one
owns.** The part is right. The generator is right. The directory between them is nobody's.

There is no error text for any of it. The generator exits `0` and prints `wiki: 89 days, 1591 parts,
65 papers indexed`, which is true.

## In production

**What a professional does.** Never edits generated output, and makes that impossible to do by
accident — a banner at the top of the file, a check that fails if a generated file is dirty, or both.
This repository already does the first: `scripts/wiki.py`'s own docstring says *"Never edit these by
hand - the next `./m check` overwrites you."* What it does not have is the check that enforces it.

**What degrades at scale.** Generators multiply and each one acquires its own version of this bug,
because copying content between locations is what a generator is for. The general defence is that any
generator moving prose between directories must **rewrite or strip** relative references as it goes,
and that this is a property worth testing once per generator rather than discovering once per index.

**The failure that only shows with real traffic.** Readers arrive through the index. The wiki is the
cheap entry point, so its links are disproportionately the first links a stranger clicks — which
means a generated index with a three-in-a-thousand global failure rate can still be the source of the
first two dead ends anybody meets.

**The review comment a senior engineer leaves:** *"Fix `render_day` to rewrite relative links against
`doc.rel`, add a test with a part whose one-line answer contains a sibling link, and add a check that
fails if `./m wiki` leaves the tree dirty — otherwise we will find this again in six months."*

**The interview question:** *"A generated file has a bug. Where do you fix it?"* Everybody answers
"the generator". The follow-up that separates people is *"how do you stop somebody fixing the file?"*,
and the answer is a check that regenerates and diffs, because a banner is a request and a failing
build is a rule.
