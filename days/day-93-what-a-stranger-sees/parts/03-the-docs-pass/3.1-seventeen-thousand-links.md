# 3.1 — Seventeen thousand links

## One-line answer

Two thousand and eighty-one tracked markdown files hold seventeen thousand six hundred and seventy-
seven relative links, fifty of which point at nothing — and the checker that finds them has to know
what a code block is, or it reports eighty-four and trains everybody to ignore it.

## The story

The index at the back of a book.

Somebody has compiled it: two thousand entries, each with a page number. It looks authoritative
because it is long, and nobody has ever read it front to back — an index is not for reading, it is
for jumping.

Then you jump. *Sedimentation, 214.* Page 214 is about rainfall. You try two more and they are
fine, so you assume you misread. The fourth is wrong too.

What happened is ordinary: a chapter was added late and everything after it moved by six pages, and
the index was compiled before. Nothing in the book looks wrong. The index is confidently, silently,
partially false, and the only way anyone finds out is by following an entry — which is the one thing
nobody does systematically.

## The idea in plain language

This repository is mostly links. A day's hub links to every one of its parts; every part links to
its neighbours, to its prerequisites, and back to ideas taught weeks earlier; the wiki links to the
days; the traceability index links to the wiki. That cross-linking is the design — plan §17's
standalone test says a part must name and link its prerequisite — and it means the documentation is
a graph, not a pile.

A graph has dangling edges. A **dangling edge is a stranger's dead end**: they click, get nothing,
and now distrust the next link too.

Counting them sounds trivial and has exactly one hard part. Markdown link syntax is `[text](target)`,
and that pattern occurs constantly inside code blocks where it is not a link at all:

```text
reply.tool_args[0](arg)          a Python expression
genai.Client(...)                a call, with brackets nearby
list[str](value)                 a type annotation and a call
```

A checker that does not know what a fenced code block is will report every one of those as a broken
link. It will be *technically* reporting what it found, and it will be useless, because the noise
buries the signal — which is the same failure Day 87's parked-day check hit and the same reason Day
83's rubric check needed a third outcome.

So the check has two jobs: find the links, and know what is not one.

## Why Sutra needs it

Because a broken link in a public repository is worse than a missing document. A missing document is
absent; a broken link is a **promise that something exists**, made by the author, and then not kept.
Part [1.1](../01-the-stranger/1.1-public-means-a-stranger.md)'s stranger has no way to tell a typo
from a page that was deliberately removed.

And because nothing has ever checked them. `./m depth` checks a day's structure and its sections;
`./m trace` checks that IDs are closed; `./m wiki` regenerates an index. None of the three follows a
link to see whether it lands.

## The mechanism

The extractor is the whole of the difficulty:

```python
def links_in(path: Path) -> list[tuple[int, str]]:
    out: list[tuple[int, str]] = []
    in_fence = False
    for number, raw in enumerate(
        path.read_text(encoding="utf-8", errors="replace").splitlines(), 1
    ):
        if FENCE.match(raw):
            in_fence = not in_fence
            continue
        if in_fence:
            continue
        for match in LINK.finditer(INLINE_CODE.sub("", raw)):
            target = match.group(1).strip()
            if target.startswith(("http://", "https://", "mailto:", "#")):
                continue
            out.append((number, target))
    return out
```

**Line by line:**

- `in_fence` toggles on every fence line and the fenced lines are skipped entirely. A counter would
  be wrong — nested fences are not a thing in the flavour of markdown used here, and a toggle is
  what the renderer does.
- `FENCE` matches both ``` and `~~~` with leading whitespace allowed, because a fence indented
  inside a list item is still a fence.
- `INLINE_CODE.sub("", raw)` strips single-backtick spans **before** looking for links, which is the
  second half of the same problem: `` `list[str](value)` `` is inline code on an otherwise ordinary
  prose line, so fence-skipping alone would not catch it.
- `errors="replace"` because two thousand files written over months are not guaranteed to be clean
  UTF-8, and a checker that dies on one file has checked none of them.
- The line number is carried with the target. A report that names a file but not a line makes the
  reader search, and a report that makes the reader search is one they run once.

Resolution is deliberately dumb:

```python
def resolves(source: Path, target: str) -> bool:
    return (source.parent / target.split("#")[0]).exists()
```

**Line by line:**

- Relative to `source.parent`, which is how a markdown renderer resolves it. Resolving relative to
  the repository root is the single commonest bug in a home-made link checker and it produces
  confident nonsense.
- `split("#")[0]` drops the anchor. Whether an anchor exists *within* a file is a different and
  harder question, and this check does not claim to answer it — the section names in a heading are
  not mechanically derivable without a markdown parser.
- `.exists()`, not `.is_file()`, because a link to a directory is legitimate.

Run it:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python links.py; echo "exit: $?"
```

**Line by line:**

- No flag: fence-aware, over every markdown file git is tracking. Untracked files are excluded on
  purpose — they are not going public.

**Fifty broken out of seventeen thousand six hundred and seventy-seven** — a failure rate of about

rate says the linking discipline is working, the count says a stranger will hit one.

## When it breaks

The checker breaks by not knowing what a code block is:

```bash
uv run python links.py --naive; echo "exit: $?"
```

Measured on 2026-09-07:

```text
    -> **reply.tool_args
  days/day-02-llm-mechanics/parts/01-first-contact/1.4-the-first-interaction.md:173
    -> genai.Client(
  ... and 78 more

  fence-aware count for the same tree: 50
  34 of these 84 are markdown-shaped text inside code
  a checker that cries wolf about its own examples gets switched off
```

**Eighty-four against fifty: thirty-four false positives, forty percent of the report.** And they are
not random — they cluster in exactly the days that teach with the most code, which are the days most
worth linking correctly. A reviewer handed that report reads three entries, sees `genai.Client(`,
concludes the tool is broken, and never reads entry four, which is real.

Note what the two arms share. Same files, same link regex, same resolution rule; the *only*
difference is whether fenced and inline code are skipped. That is a controlled comparison, and it is
why the thirty-four can be attributed to the fence handling rather than to anything else.

The break this check cannot see has no output either: a link that resolves to the **wrong** file. A
part that links to `1.2-the-story.md` when it meant `1.3-the-story.md` is green here and wrong for a
reader, and nothing mechanical distinguishes them.

## In production

**What a professional does.** Runs a link check in CI over the whole documentation tree, on every
change, and treats a broken internal link as a build failure rather than a warning. Internal links
are cheap to check and always decidable; external links are a different policy — they break for
reasons outside your repository and a hard failure on them makes the build depend on somebody else's
uptime, which is why this checker skips `http://` entirely rather than pretending.

**What degrades at scale.** The number of links grows faster than the number of files, because each
new document links backwards into everything before it. Seventeen thousand links across two thousand
files is roughly eight per file and rising; at that rate the interesting number is not the total but
the rate of *new* breakage per change, which needs the check to run per commit rather than per audit.

**The failure that only shows with real traffic.** Renaming. A single directory rename breaks every
inbound link at once, and because the renamer is looking at the moved files rather than at the files
pointing to them, the damage is entirely outside their diff. That is what a link check in CI is
really for — not typos, which are rare, but refactors, which are not.

**The review comment a senior engineer leaves:** *"Wire this into `./m check` before it goes public.
Fifty is fixable today; it will not be after the next rename, because nobody will know which fifty
were already broken."*

**The interview question:** *"How would you check the links in a documentation site?"* The answer
that shows experience mentions code blocks in the first breath — because everybody writes the naive
version first, and the person who has actually done it remembers the report that was forty percent
noise.
