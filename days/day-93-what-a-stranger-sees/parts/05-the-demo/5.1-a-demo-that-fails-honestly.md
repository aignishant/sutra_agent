# 5.1 — A demo that fails honestly

## One-line answer

Fifty-two modules are promised by the day documents and five exist, because the product code is
deliberately the reader's work — so the only truthful demo script is one that names what is missing
and exits non-zero, and writing the version that prints success would be describing a different
repository.

## The story

The model flat, shown while the building is still going up.

A hoarding, a lift that works, and one apartment on the fourth floor finished to the last handle:
tiles, fittings, a made bed, curtains. Buyers walk through it and get a real sense of the place,
because everything in that flat is exactly what they will get.

What makes it honest is the sentence the person showing it says on the way in: *"the rest of the
building is at fourth-slab stage — this is the sample flat."* With that sentence it is a
demonstration. Without it, it is the same room and it is a lie, and the lie is discovered on
possession day, when the buyer has no leverage left.

The finished room is not the problem. The missing sentence is.

## The idea in plain language

A demo script is the thing a stranger runs after the README convinces them. It answers *does this
actually work?* — and for this repository the answer has to be carefully stated, because the
repository is deliberately incomplete.

Sutra's product code is the reader's. Every day document ends with a build brief leaving
`sutra/<module>.py` as a `TODO(me)`, and the README says so plainly: *"You type every line. No
product code is pre-written in this repo."* That is a design decision, argued on Day 0 and honoured
for ninety-three days, and it is the sample-flat sentence.

Which leaves the demo script in an unusual position. It cannot run the desk end to end, because the
desk is not built. It has exactly three options:

**Pretend.** Print a plausible transcript. This is fabrication, it is what Principle 10 exists to
forbid, and it fails on the reader's first attempt to reproduce it.

**Not exist.** Then the README's claim has nothing behind it and a stranger has no way to find out
what state the repository is in except by reading ninety-three days.

**Report.** Attempt each stage, find the missing module, and say precisely which file to write. The
run goes red, the output is a task list, and every line of it is true.

The third is the only honest one, and it turns out to be the most *useful* as well — which is the
part worth noticing. A demo that fails with a precise list is a better first experience than one that
succeeds vaguely, because it tells a reader where they are.

## Why Sutra needs it

Because a stranger cannot otherwise tell "not built yet" from "broken". Those produce identical
symptoms — nothing runs — and completely different decisions: one is an invitation, the other is a
reason to leave.

And because the size of the gap is a fact the repository has never stated. The README says no product
code is pre-written; it does not say that fifty-two modules are named across the days. That number is
the scope of the work a reader is signing up for, and it belongs in front of them.

## The mechanism

The stages are the product's spine, each with the module it needs:

```python
STAGES = (
    ("configuration loads", "sutra/config.py"),
    ("a ticket reaches the desk", "sutra/desk/agent.py"),
    ("the graph routes it", "sutra/graph.py"),
    ("a write waits for a human", "sutra/hitl.py"),
    ("the run is traced", "sutra/tracing.py"),
    ("the suite can grade it", "sutra/evals.py"),
)
```

**Line by line:**

- Six stages, in the order a ticket moves through the system, so the output reads as a journey and
  the first `MISSING` is the point the journey stops.
- Each stage names **one** module. A stage that needed three would report a blocked stage without
  telling the reader which file to write, which is the difference between a report and a task.
- The stage names are what the system *does*, not what the module is called. `"a write waits for a
  human"` is meaningful to somebody who has not read Day 62; `"hitl"` is not.

The promised total is counted from the day documents themselves, rather than maintained by hand:

```python
def promised() -> set[str]:
    """Every sutra/<module>.py any day's build brief names."""
    found = set()
    for hub in (ROOT / "days").glob("day-*/LESSON.md"):
        found |= set(re.findall(r"`(sutra/[a-z_]+\.py)`", hub.read_text(encoding="utf-8")))
    return found
```

**Line by line:**

- Reading every hub means the number cannot go stale. A day added tomorrow with a new build brief
  raises the count without anybody editing this script — the same reasoning as part
  [1.3](../01-the-stranger/1.3-the-readme-that-documents-the-design.md)'s import of the enforcer.
- The backtick in the pattern is doing real work: build briefs write module names in code spans, and
  matching bare `sutra/x.py` would also catch prose mentions and file paths in output blocks.
- A `set`, because most modules are named in more than one day — the day that builds it and the days
  that extend it — and the question is how many distinct modules exist, not how many mentions.

Run it:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python demo.py; echo "exit: $?"
```

**Line by line:**

- No flag: the honest arm.

Measured on 2026-09-07:

```text
  stage                         needs                     status
  configuration loads           sutra/config.py           ok
  a ticket reaches the desk     sutra/desk/agent.py       ok
  the graph routes it           sutra/graph.py            MISSING
  a write waits for a human     sutra/hitl.py             MISSING
  the run is traced             sutra/tracing.py          MISSING
  the suite can grade it        sutra/evals.py            MISSING

  modules the build briefs promise : 52
  modules that exist               : 5

  the demo cannot run. 4 stage(s) have no module:
    - the graph routes it: write sutra/graph.py
    - a write waits for a human: write sutra/hitl.py
    - the run is traced: write sutra/tracing.py
    - the suite can grade it: write sutra/evals.py

  this is the correct output for this repository today: the product code is the
  reader's work, and a demo that printed success would be describing a different repo
exit: 1
```

**Five of fifty-two, and two of six stages.** The first two stages pass, which is not nothing: the
configuration loads and a ticket reaches a real agent. The demo stops at the graph, which is Day 53's
build brief, and it says which file to write.

## When it breaks

The pretending arm is one flag away and it is what a demo script becomes under pressure:

```bash
uv run python demo.py --pretend; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  modules the build briefs promise : 52
  modules that exist               : 5

  Demo complete. Sutra is ready.
exit: 0
```

**The two true numbers are still printed, immediately above a false conclusion.** That is what makes
this arm worth showing rather than merely describing: nothing was deleted, the evidence is right
there, and the summary line contradicts it. A reader who reads the last line — which is what a last
line is for — takes away the opposite of what the run found.

Exit `0` is the operative part. A pipeline, a badge or a smoke test consumes the code and never sees
the numbers, so the machine-readable channel now says the system is ready. Day 82 part 3.3 measured
exactly this on a nightly job and Day 83 part 5.2 on a phase gate; this is the third instance, and it
is the same lesson each time: **the finding and the exit code have to agree, or only one of them
travels.**

The break with no output at all is a demo that runs and proves nothing. If `sutra/graph.py` existed
but did nothing, the file check would pass, the stage would report `ok`, and the demo would be green
about a module that routes no tickets. `Path.is_file()` is a weak test and this script does not
pretend otherwise — the honest next version imports each module and calls one function, which is a
`TODO(me)` in the hub rather than something claimed here.

## In production

**What a professional does.** Ships a demo that is runnable from a clean clone and honest about
preconditions, and makes it the thing CI runs. The rule that matters is that the demo's exit code is
load-bearing: if it can only succeed, it is a script, not a demo. Teams that do this well tend to have
a demo that degrades in stages — this much works, this much needs credentials, this much needs the
service — rather than one that is all-or-nothing.

**What degrades at scale.** The gap between what the documentation promises and what exists grows
with the documentation, not with the code. Fifty-two promised modules is a number produced by
ninety-three days of build briefs, and it will keep rising as days are written, whether or not
anybody writes a module. A demo that reports both numbers keeps that visible; one that reports only
failures makes the trend invisible.

**The failure that only shows with real traffic.** The demo works on the author's machine because of
something the author has and never declared — a `.env`, a cached model, a service still running from
yesterday. This one is unusually safe from that, since it only touches the filesystem, and that
safety is also its limit: a demo that cannot fail for environmental reasons is a demo that is not
exercising the environment.

**The review comment a senior engineer leaves:** *"Keep it red and keep the module count in the
output — that is the most honest sentence in the repository. When you get to importing the modules,
make sure a module that imports and does nothing still fails."*

**The interview question:** *"Your demo cannot run because half the system is not built. What do you
ship?"* The answer that shows experience does not ship a mock. It ships the thing that reports what
is missing, argues that a precise red is more useful to a newcomer than a vague green, and notes that
the alternative is discovered by the first person who trusts it.

## Check yourself

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python demo.py; echo "exit: $?"
uv run python demo.py --pretend; echo "exit: $?"
```

Both print `52` and `5`. Say which line of the second run is false, and why printing the true numbers
directly above it makes the run more misleading rather than less.

Now pick the first `MISSING` stage and find the day whose build brief owns it. The day number is
recoverable from the repository without searching the web.

**Out loud, without scrolling up:** fifty-two promised, five present. Is that a defect in this
repository, and what one sentence in the README decides the answer?
