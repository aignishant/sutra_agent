# 2.1 — A README is a test you can run

## One-line answer

A README is a list of instructions, and instructions have an exit code — so instead of reading this
one, run every command in it, which is the only form of reading that cannot quietly supply the
missing step from memory.

## The story

The instruction sheet for a gift you assembled yourself.

You bought the toy, opened it, put it together over an evening, and it works. Then you wrap it, and
because you are thorough you write a note for the child's parents: *"the batteries go in the back,
and the switch on the underside turns the sound off."*

Both sentences are true and neither is the one that matters. What you have forgotten is the small
plastic tab under the battery cover that has to be pulled out before anything happens, because you
pulled it out in the first minute without registering that it was a step. You did the thing; you did
not experience it as an instruction, so it did not become one.

The only way to have caught that was to put the toy back in the box and take somebody else through
it — or to follow your own note, from the start, doing nothing that is not written down.

## The idea in plain language

Part [1.3](../01-the-stranger/1.3-the-readme-that-documents-the-design.md) checked the README's
*claims*. This part checks its **commands**, and they are a different kind of thing: a claim needs an
owner to compare against, whereas a command already carries its own verdict. It runs or it does not.

So the check is simple to state: take every command the README tells a stranger to type, type it,
and record the exit code.

The complication is that not every command is safe to run. This README contains eleven, and they
fall into three groups:

| Group | Examples | What the check does |
| --- | --- | --- |
| read-only | `./m status`, `./m depth 0` | runs them |
| slow but safe | `uv sync`, `./m check` | runs them |
| changes the repository | `cp .env.example .env`, `./m done 0` | lists them, and says why not |

That third group matters more than it looks. `cp .env.example .env` would overwrite a live `.env`
holding real keys; `./m done 0` commits. A check that ran them would not be a check, it would be
damage — so it names them and declines, which is itself information a reader needs: **the README
contains five commands nobody can safely verify on a working repository**, and they are exactly the
ones a stranger runs on a fresh clone where they are harmless.

## Why Sutra needs it

Because the README is the only document in this repository that has never been checked by anything.
Every day document is enforced by `./m depth`; the ledgers are regenerated by `./m trace` and
`./m wiki`; the code is linted and tested by `./m check`. The README sits outside all of it, and it
is the file a stranger reads first.

And because Principle 11 — *evals are tests* — has never been pointed at documentation. A day is not
done until something can go red. Applying the same rule to the README is the whole of this part, and
it turns out to go red immediately.

## The mechanism

The command table is data, so that "we do not run this one" is recorded rather than implied:

```python
COMMANDS = (
    ("./m status", True, ""),
    ("./m start 0", True, ""),
    ("./m parts 0", True, ""),
    ("./m depth 0", True, ""),
    ("uv sync", True, ""),
    ("./m check", True, ""),
    ("cp .env.example .env", False, "would overwrite a live .env"),
    ("./m scaffold 0", False, "creates directories in a day folder"),
    ("./m trace", False, "regenerates tracked files under docs/"),
    ("./m tracker", False, "regenerates tracked files under docs/"),
    ("./m done 0", False, "commits"),
)
```

**Line by line:**

- Three fields: the command, whether to run it, and **why not**. The third field is the one that
  earns its place — a bare `False` would leave the next reader guessing whether the command is
  dangerous or merely slow.
- `./m trace` and `./m tracker` are excluded not because they are destructive but because they
  rewrite tracked files under `docs/`, which would make this check leave the repository dirty. A
  check with a side effect gets run less often.
- The order is the README's order, so the output reads down the document.

Running each one has one Windows-specific trap in it, and it is worth the comment it carries:

```python
        # Run through bash explicitly. `shell=True` on Windows dispatches to cmd.exe, which
        # cannot execute `./m` and answers "not recognized as an internal or external command,
        # operable program or batch file" - a failure of the harness that reads as a failure of
        # the repository. The README says Git Bash; the check has to use it.
        proc = subprocess.run(
            ["bash", "-lc", command], cwd=ROOT, capture_output=True, text=True, timeout=900
        )
```

**Line by line:**

- `["bash", "-lc", command]` rather than `shell=True`. The first version of this check used
  `shell=True` and reported **six of six commands failing**, which would have been a spectacular and
  completely false finding about this repository. The traceback is in **When it breaks**.
- `cwd=ROOT` because `./m` is relative to the repository root and the lab is three levels down.
- `timeout=900` because `./m check` runs ruff, the offline test suite and the depth contract over
  ninety-odd days. A check with no timeout is a check that hangs a pipeline.
- `capture_output=True` so the six sub-runs do not bury the table; only the last line of a failing
  command is shown.

Run it:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python runnable.py; echo "exit: $?"
```

**Line by line:**

- No flag: everything runnable actually runs, which takes a while because `./m check` is in there.

Measured on 2026-09-07:

```text
  command                     result  note
  ./m status                  exit 0
  ./m start 0                 exit 0
  ./m parts 0                 exit 0
  ./m depth 0                 exit 0
  uv sync                     exit 2  error: failed to remove directory `C:\Users\nisha_gn
  ./m check                   exit 1  [*] 1 fixable with the `--fix` option.
  cp .env.example .env       not run  would overwrite a live .env
  ./m scaffold 0             not run  creates directories in a day folder
  ./m trace                  not run  regenerates tracked files under docs/
  ./m tracker                not run  regenerates tracked files under docs/
  ./m done 0                 not run  commits

  runnable commands executed : 6
  commands that failed       : 2

```

**Four of six work and the four are the ones in the README's "Start here" block.** That is genuinely
good news and worth stating plainly: a stranger who follows the first section of this README gets a
working orientation. The two failures are both in the **Setup** block, which is the section a fresh
clone runs before anything else — and part [2.2](2.2-the-setup-block-that-fails.md) is what each one
turns out to mean.

## When it breaks

**The check broke first, and lied about the repository.** With `shell=True` on Windows:

```text
  ./m status                  exit 1  operable program or batch file.
  ./m start 0                 exit 1  operable program or batch file.
  ./m parts 0                 exit 1  operable program or batch file.
  ./m depth 0                 exit 1  operable program or batch file.
  ./m check                   exit 1  operable program or batch file.
```

Five commands, five identical failures, and a report that would have said the repository's driver
does not work at all. The give-away is the uniformity: a real defect rarely takes out five unrelated
subcommands in exactly the same way, and `operable program or batch file` is cmd.exe's phrasing, not
bash's. **A checker's own failures look exactly like findings**, and the only defence is that a
result too dramatic to be true usually is not.

**The README breaks in the opposite direction** when it is read instead of run:

```bash
uv run python runnable.py --list; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  11 commands, all present, none executed
  every one of them looks right, which is what reading a README establishes
exit: 0
```

Eleven commands, all present, correctly spelled, in a sensible order, exiting `0`. That is what a
documentation review produces, and it is the plastic tab in the story: everything written down is
right, and the thing that is missing was never written down because the author never experienced it
as a step.

The third break has no output at all. Five of the eleven commands **cannot** be checked here, so the
green half of this report covers six commands and the README has eleven. A stranger's very first
command, `cp .env.example .env`, is in the unchecked group.

## In production

**What a professional does.** Puts the README's happy path in CI, on a clean container, from clone
to first successful command — the thing usually called a *smoke test of the docs*. It is cheap, it
runs on every change, and it is the only mechanism that catches the instruction nobody wrote down,
because the container has no memory to fill the gap with.

**What degrades at scale.** The number of unrunnable commands grows. Anything that needs a
credential, a cloud project or a paid service cannot be exercised in a check, so the fraction of the
README under test falls as the system gets more real — and it falls fastest in exactly the sections a
new person needs most. The honest response is to report the fraction rather than the pass rate.

**The failure that only shows with real traffic.** The command works and does the wrong thing. An
exit code of zero says a process ended, not that a stranger got what the sentence promised — Day 82
part 3.3 measured that distinction on a nightly job and it applies here unchanged. `./m start 0`
exits `0`; whether what it printed orients somebody who has never seen this repository is not
something an exit code can answer.

**The review comment a senior engineer leaves:** *"Run the README in CI on a fresh container, not on
your laptop. Your laptop has the plastic tab already pulled out."*

**The interview question:** *"How would you test documentation?"* The answer that shows experience
separates claims from commands: commands get executed, claims get an owner and a check, and the
prose that is neither gets shortened — because the alternative is a document that is reviewed
forever and verified never.

## Check yourself

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python runnable.py --list; echo "exit: $?"
uv run python runnable.py; echo "exit: $?"
```

The first is a documentation review and the second is a test. Say what the second one knows that the
first cannot, and name the five commands neither of them checks.

Now look at the `not run` column and pick the one you would most want covered. Then say what a check
would have to set up to run it safely — the answer is the reason it is not covered.

**Out loud, without scrolling up:** the first version of this check reported six of six commands
failing. What was the tell that the checker was wrong rather than the repository?
