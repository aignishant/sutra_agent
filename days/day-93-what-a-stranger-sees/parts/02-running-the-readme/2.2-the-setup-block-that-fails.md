# 2.2 — The setup block that does not work here

## One-line answer

Both failures are in the three-command Setup block, and they are not the same kind of thing: one is
this machine's storage layer and belongs in a precondition the README never states, the other is a
single lint error in the repository and belongs in a fix.

## The story

The **OPEN 9 to 5** sign on a door that is locked.

Somebody arrives at ten past ten. The board says the office opens at nine, the lights are on, and
the door does not move. They wait, try again, knock, and eventually a neighbour says: *"oh, the
front door sticks — you have to go round the side."*

Everybody who works there knows about the side door. It has been like that for a year. The board is
not lying about the hours and nobody put up a wrong sign; there is simply a fact about this
particular building that never made it onto the board, because the people who could have written it
stopped noticing it.

The visitor's experience is not "the hours are wrong". It is "this place is closed", and they leave.

## The idea in plain language

Part [2.1](2.1-a-readme-is-a-test.md) ran the README's eleven commands and found two failing. Both
are in the Setup block, which the README introduces with *"For a machine that already has the
toolchain"* and which reads:

```bash
uv sync                                   # materialise the environment from uv.lock
cp .env.example .env                      # then fill in your own free-tier keys
./m check                                 # should print: OK all green
```

**Line by line:**

- Quoted verbatim from `README.md`, comments included, because the comments are the promises. The
  third one — *"should print: OK all green"* — is the falsifiable claim this part is testing.
- `uv sync` first, because everything after it needs the environment. That ordering is why a failure
  here stops a stranger rather than inconveniencing them.
- `cp .env.example .env` is the command no check can safely run on a working repository, so it is the
  one command in this block whose behaviour is untested here.

Three commands. One cannot be checked safely, and the other two fail. But the two failures are
different in a way that decides who fixes them, and getting that wrong wastes a day:

**`uv sync` fails because of this machine.** The repository lives inside a synchronising cloud
folder, which holds file handles open, so removing a package directory is refused by the operating
system. Nothing in `uv.lock` or `pyproject.toml` is wrong. A stranger cloning to an ordinary path
would very likely not see it.

**`./m check` fails because of the repository.** One file has an import-order error. Any clone
anywhere reproduces it. It is one command to fix.

The first is a **missing precondition** — a fact about where the repository can live that the README
never states. The second is a **defect**. Both present as a red exit code in the same block, and the
instinct to treat them as one problem is exactly what makes environment bugs expensive.

## Why Sutra needs it

Because the README ends that block with *"should print: OK all green"*, and it does not. That
sentence is the first promise the repository makes that a stranger can falsify, and falsifying it in
the first minute costs more trust than a missing `LICENSE` ever will.

And because the precondition is real, recurring and undocumented. This repository has hit the cloud-
folder file-locking problem before, in a form serious enough that the environment directories had to
be moved outside the synchronised tree to get `uv` working at all. That was solved once, in a
session, and never written down anywhere a stranger would look.

## The mechanism

The first failure, in full:

```bash
cd "$(git rev-parse --show-toplevel)" && uv sync
```

**Line by line:**

- `git rev-parse --show-toplevel` rather than a relative path, because `uv sync` resolves the project
  from the working directory and this lab is three levels down.

Measured on 2026-09-07:

```text
Resolved 92 packages in 2ms
warning: Failed to uninstall package at .venv\Lib\site-packages\asttokens-3.0.2.dist-info due to missing `RECORD` file. Installation may result in an incomplete environment.
error: failed to remove directory `C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\.venv\Lib\site-packages\comm-0.2.3.dist-info\licenses`: Access is denied. (os error 5)
```

Read the path in that error rather than the words: `...\OneDrive\Desktop\Projects\sutra\.venv\...`.
The environment is inside a folder a sync client is actively watching, and `Access is denied
(os error 5)` on a directory removal is that client holding a handle. `uv` is behaving correctly and
reporting honestly; there is nothing for it to do about a file another process will not release.

The second failure, in full:

```bash
cd "$(git rev-parse --show-toplevel)" && ./m check
```

**Line by line:**

- The same root-relative invocation. `./m` is a bash script, so on Windows this needs Git Bash — part
  [2.1](2.1-a-readme-is-a-test.md)'s harness bug is the same fact arriving from the other side.

Measured on 2026-09-07, the tail:

```text
 7 | / import asyncio
 8 | |
 9 | | import pytest
10 | | import re
11 | | from sutra.desk.run_once import ask_with
12 | | from sutra.desk.agent import root_agent, INSTRUCTION
   | |____________________________________________________^
help: Organize imports
Found 1 error.
[*] 1 fixable with the `--fix` option.
```

**One error, in one file, automatically fixable.** `tests/test_persona.py` is a file the *reader*
writes on Day 15 — it is their work, not the curriculum's — which is why it has been left alone by
every day since. That is a defensible decision and it has a cost this part is measuring: the
repository's own headline gate has been red for the whole of the second half of the curriculum, and
the README promises it is green.

The two failures side by side, which is the useful view:

| | `uv sync` | `./m check` |
| --- | --- | --- |
| reproduces on a fresh clone elsewhere | probably not | yes |
| cause | the storage this copy lives on | one file's import order |
| owner | whoever chooses where to clone | whoever owns `tests/` |
| fix | clone outside the synchronised folder | one command |
| belongs in the README as | a stated precondition | nothing — it should just be green |

## When it breaks

The failure this part is about is **treating both rows as one row**. The composite runs like this,
and every step is reasonable:

```text
1. a stranger clones, runs uv sync, and it fails
2. they try ./m check anyway, and it fails too
3. two failures in three commands reads as "this repository does not work"
4. they do not report it, because there is no CONTRIBUTING.md and no issue seems worth it
5. nobody ever learns that one of the two was a one-command fix
```

No error text exists for step 5, which is the expensive one. Part
[1.1](../01-the-stranger/1.1-public-means-a-stranger.md)'s point arrives here as a cost: the
stranger's silence means the repository cannot tell the difference between *nobody tried* and
*everybody who tried gave up in the first minute*.

There is a second, quieter break. `uv sync` did not merely fail — it failed **partway**, after
resolving and while removing. An interrupted environment sync can leave a virtual environment that
imports some things and not others, which is a far worse state than a clean failure. Checking that
the environment still works afterwards is not paranoia:

```bash
cd "$(git rev-parse --show-toplevel)" && uv run python -c "import google.adk, fastapi; print('ok')"
```

**Line by line:**

- Two imports that come from different packages, so a half-removed environment shows up as an
  `ImportError` rather than as silence.

Measured on 2026-09-07: `ok`. This time it was fine. The warning in the output — *"Installation may
result in an incomplete environment"* — is `uv` saying that it might not have been.

## In production

**What a professional does.** States preconditions the README's audience cannot guess, and states
them as *facts about the environment* rather than as apologies. One line — that the repository should
not live inside a synchronising cloud folder, and why — converts a mysterious `os error 5` into a
sentence a reader can act on before they hit it. Preconditions are cheap to write and are almost
never written, because the person writing has already satisfied them.

**What degrades at scale.** The set of environments a README implicitly assumes grows every time
somebody's machine works. Nobody adds a precondition when things go right, so the document's
implicit requirements accumulate silently and are only ever discovered by somebody who fails.

**The failure that only shows with real traffic.** The first-minute failure is the one that decides
adoption, and it is invisible from inside. Everybody already set up experiences the README as
correct, because they never run it again. The only signal is people who quietly do not come back,
and that signal never reaches a dashboard.

**The review comment a senior engineer leaves:** *"Fix the lint — it is one command and our own
README says this gate is green. And add the storage precondition to Setup; we have hit that twice
now and it is still not written down anywhere a new person would look."*

**The interview question:** *"Setup fails for a new joiner. How do you tell an environment problem
from a repository problem?"* The answer that shows experience reaches for reproducibility first —
does it fail on a clean container, or only on their machine — and then notes that the two need
different owners and different fixes, and that bundling them is how a one-command fix sits unfixed
for months behind a scary-looking environment error.
