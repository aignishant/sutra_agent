# 2.3 — What a README owes, and what it does not

## One-line answer

A README owes a stranger five answers — what this is, what it costs, the first command, what it will
not do, and where to go next — and the commonest failure is not omitting one of them but answering a
sixth question nobody asked, at length, above the five.

## The story

The clinic noticeboard listing doctors who left.

A board by the entrance, glass-fronted, neatly typed. Eleven names, each with a speciality and
consulting days. It has been there for years and it is nobody's job.

Four of the eleven no longer work there. One retired, two moved, and one comes in only on referral.
The board does not say so, so people wait for a doctor who is not coming, and the receptionist
explains it eight times a day and has stopped finding it strange.

Here is the part that matters: the board is not too short. It is too long. If it listed the three
doctors who are definitely in today, it would be right, and it would be right for far longer,
because a short list is one somebody can keep true.

## The idea in plain language

A README is read by somebody deciding whether to spend the next portion of their attention on your
repository. They are answering one question — *is this for me?* — and they will decide in about the
time it takes to scroll one screen.

Five answers serve that decision.

**What is this, in a sentence a stranger can repeat.** Not the architecture; the thing it does.

**What it costs.** Money, keys, a machine, an account. Cost is the commonest silent disqualifier and
the cheapest to state.

**The first command.** One. Copy-pasteable. The reader's next physical action.

**What it will not do.** The scope boundary. This is the answer most often omitted and the one that
saves the most wasted time, because it lets the wrong reader leave happy.

**Where to go next.** One link, chosen, not a directory listing.

This README answers four of the five well, and the fourth is worth crediting precisely because this
day has been listing its faults: **"You type every line. No product code is pre-written in this
repo."** That is a clear, prominent scope boundary, and it is exactly the sentence that stops a
stranger cloning this expecting a working triage system. Part
[5.1](../05-the-demo/5.1-a-demo-that-fails-honestly.md) measures how large that boundary is — fifty-
two modules promised, five present — and the README having said so up front is the difference
between a design and a disappointment.

What it owes and does not deliver is **cost stated as a precondition**. It says "zero budget, by
construction", which is the money answer and a good one. It does not say what a machine must be —
which is how part [2.2](2.2-the-setup-block-that-fails.md)'s `os error 5` reaches a stranger with no
warning.

And what a README does **not** owe: the architecture, the rationale, the history, the roadmap, or a
tour of the directory tree. Every one of those has a better home, and every one of them pushes the
five answers below the fold.

## Why Sutra needs it

Because this repository has a plan, two addenda, a wiki, a traceability index and ninety-three day
documents. Every one of those is a better home for something than the README is, so the README's job
is almost entirely **routing** — and a routing document that grows stops routing.

And because the README is about to become the entry point for readers who will never meet its
author. Ninety-three days of careful teaching sit behind one screen of text, and the screen decides
whether any of it gets read.

## The mechanism

The five answers, against this README, judged by reading it as a stranger:

| The answer | Where this README gives it | Verdict |
| --- | --- | --- |
| what it is | first two paragraphs — a triage desk, and a curriculum that builds it | clear |
| what it costs | "Zero budget, by construction", free tiers named | clear on money, silent on machine |
| the first command | `./m status` under **Start here** | clear, and it works |
| what it will not do | "You type every line. No product code is pre-written" | clear and prominent |
| where next | a five-row table, and a highlighted Day 0 link | clear |

That is a good README, and this day has been hard on it. The faults found in part
[1.3](../01-the-stranger/1.3-the-readme-that-documents-the-design.md) are drift in the *details*
below those five answers — the section count, the driver list, the folder diagram — which is a
different problem from failing the reader's decision.

The check for the five answers is a person reading, not a script, and it is worth being honest about
why:

```bash
cd days/day-93-what-a-stranger-sees/lab
uv run python readme_contract.py 2>&1 | tail -6
```

**Line by line:**

- This is the checkable half, and it is the *details* half. Nothing in it evaluates whether the first
  paragraph tells a stranger what the project is.

Measured on 2026-09-07:

```text
  claim 3  the day-folder tree
    README shows papers/ : NO
    a real day contains  : ['lab', 'papers', 'parts']

  0 of 3 claims match what enforces them
  drifted: section count, driver commands, day-folder tree

```

Zero of three checkable claims, and five of five reader answers present. **Those two results are
about different things**, and a day that reported only the first would have described this README as
much worse than it is.

## When it breaks

A README breaks by growing. The mechanism is that every addition is individually justified: somebody
is confused about the phases, so a paragraph about phases goes in; somebody asks about the legacy
directory, so a row is added. Nothing is ever removed, because removing something is the only edit
that requires an argument.

The end state has a shape:

```text
1. the five answers are on the first screen
2. a section explaining a design decision is added above them
3. a table of contents is added, because the document now needs one
4. the first command is on the third screen
5. new readers ask, in issues, the question the first screen used to answer
6. a paragraph is added answering it
```

There is no error text. The document is accurate at every step and progressively less useful, and
step 6 makes it worse in the name of making it better.

The measurable symptom is where the first command sits. In this README:

```bash
cd "$(git rev-parse --show-toplevel)" && grep -n "./m status" README.md | head -2
```

**Line by line:**

- Line number as a proxy for how far a reader scrolls before their first physical action.

Measured on 2026-09-07:

```text
23:./m status          # where am I
94:./m status         # one line: how many days are written / complete
```

**Line twenty-three of a hundred and thirty-nine.** Still on the first screen, which is the answer
you want. That number is the one to watch: when it passes forty, something above it should come out.

## In production

**What a professional does.** Writes the README last and keeps it short enough that keeping it true
is cheap. The discipline that actually works is a size budget — one screen to the first command — 
because it forces the question *"what comes out?"* every time something goes in, and that question is
the only thing standing between a README and the noticeboard.

**What degrades at scale.** Every document a repository gains makes the README's job easier and its
temptation worse: there is now somewhere better for each new paragraph, and also more material that
somebody will want summarised at the top. Projects that stay readable tend to have an explicit rule
about what the README is not for.

**The failure that only shows with real traffic.** Readers stop reading it. Once a README is long
enough to skim, people scan for a code block and run it, which means every sentence of context above
that block is doing nothing — including the ones that matter, like a precondition or a scope
boundary. You cannot see this happening; you only see the questions that arrive as if the document
did not exist.

**The review comment a senior engineer leaves:** *"Add the machine precondition to Setup, fix the
three drifted claims, and then do not add anything else — if it needs explaining, it goes in `docs/`
and gets one row in the table."*

**The interview question:** *"What belongs in a README?"* The answer that shows experience gives a
short list and then, unprompted, the harder half — what does *not* belong, and where each of those
things goes instead — because anybody can name things to add.

## Check yourself

```bash
cd "$(git rev-parse --show-toplevel)"
grep -n "./m status" README.md | head -2
wc -l README.md
```

Work out what fraction of the document a reader passes before their first command. Then find the one
section you would delete, and say where its content should live instead.

Now write the five answers for this repository in five sentences, from memory, without opening the
README. Compare. The gaps are what a stranger would have had to guess.

**Out loud, without scrolling up:** which of the five answers does this README give best, and which
does it not give at all?
