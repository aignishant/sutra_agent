# 5.4 — The estimate and the measurement

## One-line answer

A model producing a number is predicting the next token, not calculating, so the fix is not a better
prompt but a change of instrument: the model writes the program and an interpreter produces the
number.

## The story

The flat was advertised as "about eighty square metres".

The agent was not lying. They had walked it, they had seen a hundred flats that year, and eighty was a
good guess from someone with a good eye. The measurement in the brochure came from the same place —
somebody stood in the room and estimated it.

The survey came back at seventy-one. Not a scandal, and not far off, and enough to change the price
per square metre in a way that mattered to the person paying it. The surveyor had a laser measure and
a floor plan and produced a number by a process where being wrong would have been a mistake rather
than a bad guess.

Both people gave you a number in the same units, in the same confident tone, and only one of them had
measured anything.

## The idea in plain language

[Day 2](../../../day-02-llm-mechanics/LESSON.md) established the mechanism: a language model produces
text one token at a time, each token chosen from a probability distribution over what usually follows.
That process is indifferent to the *kind* of thing being produced. A word, a name and a number are all
just tokens, and `43.45` is generated the same way `probably` is.

This is why "do the arithmetic carefully" is not a fix. There is no arithmetic to do carefully. Asking
the model to show its working, which is what chain-of-thought prompting does, genuinely helps —
laying out the steps makes each next token easier to predict — and it still ends with a *predicted*
number rather than a computed one. The steps can be perfectly reasoned and the final division still
wrong.

The change that fixes it is a change of instrument. Let the model do the part it is good at — reading
a messy question and deciding what needs computing — and hand the computing to something that
computes. That something is a Python interpreter, and code execution
([5.2](5.2-the-executor-that-executes-nothing.md)) is how it reaches one.

Notice what moves and what does not. The model still reads the ticket, still decides that the question
is about percentiles, still writes the expression. What it stops doing is the last step, and the last
step is the only one where being approximately right is worthless.

## Why Sutra needs it

Because Sutra's answers get acted on, and a number in a triage note is the part that gets acted on
hardest.

*"The 95th percentile response time in this batch is forty-one minutes"* is the kind of sentence that ends up
in an escalation, a customer email or a decision to page somebody. If that number came out of a
distribution over plausible tokens, then everything built on it — the escalation, the email, the page
— rests on an estimate wearing a measurement's clothes. Principle 10 says Sutra never fabricates a
result, and an unexecuted number is a fabricated result that happens to often be right.

There is a practical follow-on for Day 79's evals. A computational answer is *checkable*: you can run
the same computation and compare. That makes it one of the few things in an agent system with a hard
pass or fail, and evals with hard verdicts are worth more than evals with rubrics.

## The paper behind it

> **PAL: Program-aided Language Models**
> `arXiv:2211.10435` · 2022
> <https://arxiv.org/abs/2211.10435>

It claimed that a language model should read a natural-language problem and generate a **program** as
its reasoning steps, offloading the actual solving to a Python interpreter — and that doing so beat
much larger models that reasoned in prose.

That is the idea this whole section runs on, four years before the platform made it a switch. It is
taught in [the paper part](../../papers/01-program-aided-language-models.md) — read it after the
parts.

## The mechanism

The mechanism of *this* part is not code the model runs; it is the ground truth you keep beside it, so
that a computed answer can be checked rather than believed:

```python
# days/day-16-built-in-tools-with-brakes/lab/expected.py
"""The ground truth for compute.py's question, so a model's answer can be checked."""

import math
import statistics

RESPONSE_TIMES = [4, 7, 3, 9, 12, 5, 6, 41, 8, 5, 7, 90, 6, 4, 11, 5, 38, 7, 6, 9]

ordered = sorted(RESPONSE_TIMES)
print("n            :", len(ordered))
print("mean         :", statistics.mean(RESPONSE_TIMES))
print("median       :", statistics.median(RESPONSE_TIMES))

# Two defensible 95th percentiles, because "the 95th percentile" is not one definition.
nearest_rank = ordered[math.ceil(0.95 * len(ordered)) - 1]
interpolated = statistics.quantiles(RESPONSE_TIMES, n=100, method="inclusive")[94]
print("p95 (nearest rank) :", nearest_rank)
print("p95 (interpolated) :", interpolated)
```

**Line by line:**

- `import statistics` — the standard library, not numpy. Sutra adds a dependency on the day it is
  needed and not before, and the mean and median of twenty numbers do not need one.
- `RESPONSE_TIMES` — the identical list from
  [5.3](5.3-reading-the-code-and-its-output.md)'s `compute.py`, so the two scripts are answering the
  same question and the outputs can be compared line for line.
- `math.ceil(0.95 * len(ordered)) - 1` — the **nearest-rank** percentile: sort, take the value at 95%
  of the way up, no interpolation. `- 1` because the rank is one-based and Python is zero-based.
- `statistics.quantiles(..., n=100, method="inclusive")[94]` — the **interpolated** percentile: cut
  the data into a hundred pieces and read the boundary, inventing a value between two observations if
  necessary. `[94]` is the 95th cut point, again because of zero-based indexing.
- Two percentiles on purpose. There is no single definition of "the 95th percentile", and different
  libraries pick different defaults.

**Line by line:**

- No model, no key, no request. This is the ruler you hold up against

Measured with the pinned Python 3.12 on 2026-09-03:

```text
n            : 20
mean         : 14.15
median       : 7.0
p95 (nearest rank) : 41
p95 (interpolated) : 43.45
```

Now the point. When `compute.py` answers, its number will be one of these two, or something else
entirely. If it says `41` or `43.45`, the program computed it and the two of you disagree only about
methodology. If it says `40` or `42.7`, no percentile definition produces that, and what you are
looking at is a number that was *written* rather than run — which is exactly the failure the whole
section exists to remove.

Notice the second thing that block shows, which surprises people more than the first: the mean is
`14.15` and the median is `7.0`. Two of the twenty tickets are dragging the average to double the
typical case. A model estimating "the average response time" from a list would very plausibly say
"about seven", because seven is what the list *looks like*, and it would be wrong about the mean and
right about the experience. Computation does not save you from asking the wrong question; it only
guarantees that the question you asked was answered exactly.

## When it breaks

**The model answers without running anything.** No error. The tell is in
[5.3](5.3-reading-the-code-and-its-output.md)'s output: no `executable_code` part in the stream, just
prose with a number in it. Code execution is a permission, not a compulsion — the model may decide the
arithmetic is easy — and "easy" is exactly where the mistakes are, because easy means it will guess.

The lever is the instruction, and it has to be forceful: *"You answer numeric questions by WRITING AND
RUNNING Python code, never by doing arithmetic in your head."* The lever after that is a check: an
answer containing a number and no program is a result you do not use.

**The program is right and the prose rounds it.** Also no error, covered in
[5.3](5.3-reading-the-code-and-its-output.md), and worth repeating here because this part is where you
would notice: the code printed `43.45` and the sentence says "about 43". Harmless in a note to a
colleague and not harmless in a service-level report.

**The two percentiles disagree and somebody calls it a bug.**

```text
p95 (nearest rank) : 41
p95 (interpolated) : 43.45
```

Neither is wrong. This is the trap that follows the fix: once the number is computed, people trust it
completely, and the remaining disagreements are about definitions rather than arithmetic. An answer
that says which method it used is worth more than one that does not.

## In production

**Ask for a program, store the program, and pin the definition.**

The version a professional writes does three things this section has now covered: it instructs the
model to compute rather than to answer, it keeps the code and the output
([5.3](5.3-reading-the-code-and-its-output.md)), and it states in the instruction which definition of
an ambiguous statistic to use — because "p95" is under-specified and a model asked twice may pick
differently.

**What changes at scale** is that computation becomes the cheap part and the input becomes the risk.
Twenty numbers pasted into a ticket are twenty numbers. Ten thousand rows are a file, and a model that
tries to inline them into its program will produce something that neither fits the context window nor
finishes inside the sandbox's deadline. That is the boundary where an agent writing throwaway code
stops being the right design and a real data pipeline starts.

**What fails only under real traffic** is unit confusion. Response times in minutes and response times
in seconds look identical in a list of integers, and a model reading a ticket will infer the unit from
context that may be wrong. The program will be executed perfectly on the wrong units, and no amount of
code execution catches it. State units in the question.

**The review comment**: *"this asks the model for a percentile. Ask it for a program that computes the
percentile, say which definition, and store both."*

**The interview question**: *"why not just tell the model to be careful with arithmetic?"* The answer
that shows you understand the mechanism: *"because it is not doing arithmetic — it is predicting
tokens, and a number is a token like any other. You do not fix that with instructions, you fix it by
moving the last step to an interpreter."*
