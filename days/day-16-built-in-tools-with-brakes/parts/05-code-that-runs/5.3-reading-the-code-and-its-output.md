# 5.3 — Reading the code and its output

## One-line answer

A code-execution answer arrives as **three things in the event stream** — the program the model wrote,
the sandbox's output with an outcome code, and the prose written around them — and printing the first
two is the only way to know whether the third is arithmetic or a story about arithmetic.

## The story

The parcel said "out for delivery" for two days.

On the tracking page there is one line at the top in large type, and under it a list of scans with
times and depot names. Most people read the large line and close the tab. It is written to be read on
its own: *arriving today*, *delayed*, *at your local depot*.

When the parcel did not come, the list underneath turned out to be the thing worth reading. Accepted
at the origin, scanned into the hub, scanned out, scanned into a hub again — the same hub, four hours
later, and then nothing. The summary at the top had been generated from the last scan and the last
scan was a lie of omission: it said where the parcel had been, and the useful fact was that it had
been there twice.

The scans were on the page the whole time, under the summary, in small type.

## The idea in plain language

When a model with code execution answers a numeric question, its response is not one blob of text. It
is a sequence of **parts** on the events coming out of the run, and today two new kinds of part
appear.

`part.executable_code` is the program the model wrote. It carries:

- `code` — the source, as a string;
- `language` — an enum whose only real value is `PYTHON`, documented in the SDK as *"Python >= 3.10,
  with numpy and simpy available"*;
- `id` — an identifier the server uses to match this program to its result.

`part.code_execution_result` is what the sandbox got back. It carries:

- `outcome` — an enum: `OUTCOME_OK`, `OUTCOME_FAILED`, or `OUTCOME_DEADLINE_EXCEEDED`;
- `output` — documented as *"stdout when code execution is successful, stderr or other description
  otherwise"*;
- `id` — matching the `executable_code` part it belongs to.

And `part.text` is the model's prose, which is what an unmodified example prints and what a user
would see.

The reason to print all three is Principle 10 with a sharp edge. A model that has run code can still
write prose that disagrees with the code's output — it can round, it can transcribe wrongly, it can
summarise "the 95th percentile is 41" as "most tickets were answered quickly". The code and the
output are the evidence; the prose is the summary at the top of the tracking page. During
development, read the scans.

There is a second reason, and it is the one that matters on Day 66: the program is also the clearest
statement of **what the model decided to do**. A question about response times that produces code
reading an environment variable is a very different event from one that produces `numpy.percentile`,
and the only place that difference is visible is the `executable_code` part.

## Why Sutra needs it

Because the whole justification for switching code execution on is that arithmetic becomes checkable,
and it is only checkable if somebody prints it.

Sutra's use is concrete: a ticket arrives with a batch of measurements pasted into it, and the
engineer wants the median and the outliers. Today's answer is the coder agent, and tomorrow's is the
same agent inside the Phase 8 graph. In both cases the value of the answer depends on the reader being
able to see the two lines of Python that produced it — which is the difference between a tool a
support team trusts and one it quietly stops using.

It is also Sutra's first look at an artefact the model *made* rather than said. Day 60's durability
work and Day 84's traces both have to decide whether such artefacts are stored, and knowing they exist
as their own part type is where that decision starts.

## The mechanism

The day's second script that spends requests. It asks one numeric question, prints the program, the
sandbox's outcome and output, and only then the answer:

```python
# days/day-16-built-in-tools-with-brakes/lab/compute.py
"""One numeric question, and the program the model wrote to answer it.

Spends 1-3 model requests (free tier: 20 per day) and no search requests.

    cd days/day-16-built-in-tools-with-brakes/lab
    uv run python compute.py
"""

from __future__ import annotations

from google.adk.agents import Agent
from google.adk.code_executors import BuiltInCodeExecutor
from google.adk.events import Event
from google.adk.runners import InMemoryRunner
from google.genai import types
from google.genai.errors import ClientError

from sutra.config import load_env, require_free_tier

MODEL = "gemini-3.7-flash"

# Synthetic response times in minutes. Synthetic always: real customer data never
# rides a free endpoint (Addendum 02 section 7).
RESPONSE_TIMES = [4, 7, 3, 9, 12, 5, 6, 41, 8, 5, 7, 90, 6, 4, 11, 5, 38, 7, 6, 9]

coder = Agent(
    name="sutra_coder",
    model=MODEL,
    description="Answers numeric questions by writing and running Python.",
    instruction=(
        "You answer numeric questions by WRITING AND RUNNING Python code, never by "
        "doing arithmetic in your head. State the numbers the code printed, exactly "
        "as it printed them. If the code fails, say so and show the error."
    ),
    code_executor=BuiltInCodeExecutor(),
)

QUESTION = (
    f"These are ticket response times in minutes: {RESPONSE_TIMES}. "
    "Compute the mean, the median and the 95th percentile, and say which values are outliers."
)


def show(event: Event) -> None:
    """Print the program, the sandbox's verdict, and the prose - in that order."""
    if not event.content or not event.content.parts:
        return
    for part in event.content.parts:
        if part.executable_code is not None:
            print("--- the program the model wrote ---")
            print(part.executable_code.code)
        if part.code_execution_result is not None:
            result = part.code_execution_result
            print("--- the sandbox said ---")
            print("outcome:", result.outcome)
            print(result.output)


def main() -> None:
    load_env()
    require_free_tier()

    runner = InMemoryRunner(agent=coder)
    session = runner.session_service.create_session_sync(app_name=runner.app_name, user_id="day16")
    try:
        for event in runner.run(
            user_id="day16",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=QUESTION)]),
        ):
            show(event)
            if event.is_final_response() and event.content:
                answer = "".join(part.text or "" for part in event.content.parts).strip()
                print("\nANSWER:", answer)
    except ClientError as error:
        if error.code == 429:
            print("429: the free tier is spent for today. No answer, and none invented.")
            raise SystemExit(1) from error
        raise


if __name__ == "__main__":
    main()
```

**Line by line:**

- `RESPONSE_TIMES` with two obvious outliers (41 and 90) — chosen so that a model doing arithmetic in
  its head has somewhere to go wrong, and so that the answer is checkable by eye.
- The instruction's three sentences do three jobs: force the tool (*write and run code*), pin the
  reporting (*state the numbers the code printed, exactly*), and pre-authorise honesty (*if the code
  fails, say so*). The middle one is the anti-fabrication clause and it is the one people leave out.
- `part.executable_code is not None` — checking the part **kind** rather than assuming a shape. A
  single event can carry text and code and a result, in any combination.
- `print(part.executable_code.code)` — printed raw, unformatted, before anything else. This is the
  evidence, and it goes first in the output for the same reason the scans matter more than the
  summary.
- `result.outcome` printed as-is — an enum member, so `Outcome.OUTCOME_OK` or
  `Outcome.OUTCOME_FAILED`. Printing the enum rather than a boolean keeps the deadline case visible,
  which is the one you will not think to handle.
- `result.output` — stdout on success and stderr on failure, in the same field. That is why the
  outcome has to be printed next to it: the string alone does not tell you which it is.
- `event.is_final_response()` — the prose, printed last, after the reader has already seen what it is
  a summary of.
- The `except ClientError` block — identical to
  [3.1](../03-receipts/3.1-where-the-sources-are.md)'s. One 429 handler, the same shape, in every
  script that spends a request.

## When it breaks

**`AttributeError: 'NoneType' object has no attribute 'parts'`**

An event with no content — the first event of a run is your own message, and streaming runs emit
events with empty content. The guard is the first line of `show`.

**The outcome is `OUTCOME_FAILED` and the output is a traceback.**

This is the sandbox reporting honestly, and it is the case the instruction's third sentence exists
for. It commonly means the model imported something the sandbox does not have: the documented library
set is Python 3.10 or later with numpy and simpy, so pandas code fails there even though it would run
on your laptop. Left unhandled, the model will often try again with different code — `BaseCodeExecutor`
documents `error_retry_attempts: 2` for local executors, and for the built-in the retrying happens on
the far side, which you observe as extra parts in the stream rather than as extra calls in your code.

**The outcome is `OUTCOME_DEADLINE_EXCEEDED`.** The sandbox has a time bound you did not set and
cannot change ([5.2](5.2-the-executor-that-executes-nothing.md)). There may or may not be partial
output. The honest answer to the user is that the computation did not finish, and the fix is a smaller
question rather than a retry.

**The prose disagrees with the output.** No exception, and the most important failure in this part. The
sandbox printed `p95 = 41.2` and the answer says "around 40". That is usually harmless and occasionally
not, and you will only ever see it if the program and its output are printed next to the prose. If you
find it happening on real questions, the instruction is the lever — *state the numbers exactly as
printed* — and a Day 13 `after_model_callback` that compares them is the mechanism when the instruction
is not enough.

## In production

**Log the program, keep the outcome, and never show prose that contradicts the output.**

The version a professional ships stores three fields per computational answer: the code, the outcome
enum and the raw output. It costs almost nothing and it converts an unanswerable support question —
*"why did it say 41?"* — into a lookup. It also gives you a corpus: the programs a model writes for
your questions are the most direct evidence you will ever get about how it understands them.

**What changes at scale** is that the code becomes an audit surface. Someone will eventually ask what
the model has been executing, and "we do not keep it" is a bad answer in any regulated setting. The
same log is what makes a Day 66 injection visible after the fact, because an injected instruction that
changed what the code does is *in the code you stored*.

**What fails only under real traffic** is the assumption that there is one program per answer. A model
can write, run, read the error, and write again, several times in one turn. Code that keeps only the
last `executable_code` part shows a clean final program and hides the three failures before it, which
is exactly the history you want when something goes wrong.

**The review comment**: *"we print the answer but not the program. When a number is wrong we will have
no way to tell whether the model computed it or wrote it."*

**The interview question**: *"an agent tells you the 95th percentile is 41. How do you know it did not
make that up?"* The answer names the parts: the program is in the response, the sandbox's stdout is in
the response, and if you are not printing both, you do not know.
