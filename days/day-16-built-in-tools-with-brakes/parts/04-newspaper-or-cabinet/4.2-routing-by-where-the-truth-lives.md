# 4.2 — Routing by where the truth lives

## One-line answer

The four things that differ between grounding and retrieval — freshness, privacy, the meter they
spend and the way they fail — are what a routing decision is actually made of, and in Sutra today
that decision is written in one place: the sentence describing the search specialist.

## The story

You ring the helpline about a charge on your own bill.

There is a menu, then a wait, then a person, and they are perfectly nice. You read out the line from
the bill. They ask for your account number, your postcode, the name on the account, and the date, and
then they say what everyone on that team says: *"I can see the charge, but I can't see why it was
applied — that would be on the paperwork we sent you."*

The paperwork is in the drawer under the kettle. It has been there the whole time. You have spent
part of your afternoon giving your details to a stranger to be told to look in your own drawer, and
the strangest part is that nothing went wrong: everyone was helpful, the system worked, and the answer
was always in the house.

## The idea in plain language

[4.1](4.1-two-questions-that-sound-the-same.md) drew the distinction. This part is about the four
practical differences that follow from it, because those are what you actually weigh when you decide
where a question goes.

| | Grounding | Retrieval |
| --- | --- | --- |
| **Source** | the live public web | a collection you keep |
| **Freshness** | this minute | as fresh as your last index run |
| **Privacy** | the query leaves your building | can stay entirely local |
| **Meter** | search requests, a separate allowance ([4.4](4.4-two-meters-one-call.md)) | your own compute, roughly free at the margin |
| **Fails by** | finding a plausible wrong page | finding a plausible near-match, or nothing |

Read the rows as a checklist rather than a description, because each one is a reason to route a
question one way and not the other:

- **Freshness** decides it when the answer changed today. Nothing in your index knows about an
  incident that started an hour ago.
- **Privacy** decides it when the question contains anything of yours — a customer name, a ticket
  body, a stack trace with your hostnames in it. That is [4.3](4.3-the-question-that-left-the-building.md),
  and it is a hard rule rather than a preference.
- **The meter** decides it when the volume is high. A question asked on every ticket should not be
  spending a metered external allowance if a local index can answer it.
- **The failure mode** decides how much you trust the answer without checking. A grounded answer comes
  with URLs a human can open in seconds; a retrieval answer comes with a document from your own
  archive, which is easier to trust and harder to notice being stale.

Where does the decision physically live? In a big system it becomes a routing node in a graph
(Phase 8). Today, in Sutra, it lives in the **description of the search specialist**, because that
description is what the desk's model reads when deciding whether to refer a question outwards
([2.3](../02-one-at-a-time/2.3-the-specialist-you-write-yourself.md)). One sentence of English, doing
the job a routing table will do later, and worth writing as carefully as you would write an API
contract.

## Why Sutra needs it

Because the desk is about to be able to reach the public internet, and the desk's model decides on
each ticket whether to do so.

Without a routing rule, that decision is made by whatever the model finds most helpful in the moment,
which for a ticket that mentions a vendor is *almost always* "search the web". That is how a triage
desk ends up sending customer text to a search engine because the ticket happened to mention a product
name, and how a free allowance of 5,000 searches a month gets spent on questions that never needed
one.

The routing rule is also what makes Phase 7's work land cleanly. When retrieval arrives on Day 46,
Sutra will hold both organs, and the description written today is where the second one gets added.
A system that never wrote the rule down has to invent it under pressure, with two capabilities already
live.

## The mechanism

The rule, written as the specialist's description and instruction. This is the same agent as
[2.3](../02-one-at-a-time/2.3-the-specialist-you-write-yourself.md), with the routing sentences
filled in:

```python
# days/day-16-built-in-tools-with-brakes/lab/routing.py
"""The routing rule as the desk's model actually receives it. Zero model calls."""

import asyncio

from google.adk.agents import Agent
from google.adk.tools import google_search
from google.adk.tools.agent_tool import AgentTool

RESEARCHER_DESCRIPTION = (
    "Answers questions about the CURRENT PUBLIC state of the internet: vendor status "
    "pages, outages, published release notes, advisories. "
    "NOT for anything about our own tickets, customers, systems or history. "
    "Returns a short answer with its sources."
)

researcher = Agent(
    name="sutra_researcher",
    model="gemini-3.7-flash",
    description=RESEARCHER_DESCRIPTION,
    instruction=(
        "Search before answering. Report what the sources say. "
        "If the question is about the asker's own systems, tickets or customers, "
        "say that you cannot answer it and that it belongs to internal records."
    ),
    tools=[google_search],
)


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its identifier."""
    return {"id": ticket_id, "status": "open"}


desk = Agent(
    name="sutra_desk",
    model="gemini-3.7-flash",
    instruction="Triage tickets for support engineers.",
    tools=[lookup_ticket, AgentTool(agent=researcher, propagate_grounding_metadata=True)],
)


async def main() -> None:
    for tool in await desk.canonical_tools():
        declaration = tool._get_declaration()
        print(f"--- {tool.name} ---")
        print(None if declaration is None else declaration.description)


asyncio.run(main())
```

**Line by line:**

- `RESEARCHER_DESCRIPTION` as a **named module constant** rather than an inline string. The same move
  Day 15 made with its allowlist: a rule a reviewer needs to find should have a name they can grep
  for.
- *"CURRENT PUBLIC state"* in capitals — the positive half of the rule. Models weigh emphasis, and this
  is the sentence that has to survive being read alongside twenty other tokens of tool descriptions.
- *"NOT for anything about our own tickets, customers, systems or history."* — the negative half, and
  the more important one. A description that only says what a tool is *for* is a description that gets
  used for everything adjacent.
- *"Returns a short answer with its sources."* — the return contract. The desk's model behaves
  differently when it knows a tool returns citations: it is more likely to pass them on.
- The `instruction` repeats the boundary **inside** the specialist. Belt and braces on purpose: the
  description governs whether the desk refers, and the instruction governs what the specialist does
  when it is referred something it should not have been. Two layers, because each catches what the
  other misses.
- `desk.canonical_tools()` and printing each declaration's description — the check that the rule
  actually reaches the model. It is easy to write a beautiful description on an agent and attach a
  different agent.

Run it:

```bash
cd days/day-16-built-in-tools-with-brakes/lab
uv run python routing.py
```

**Line by line:**

- No key, no request. Everything here is about what would be *sent*, and that is decided before any
  call.

The output is the two descriptions the desk's model will weigh against each other — Sutra's own tool
on one side and the referral on the other. If the referral's block is empty, the rule you wrote is not
in the request, and the routing you think you configured does not exist.

## When it breaks

**The desk refers everything.**

No error. The tell is in the request budget and in the search meter: a run of tickets where nearly
every one made a referral. The cause is nearly always a description with no negative half. *"Answers
questions about the internet"* matches any ticket that mentions any product, and the model is doing
exactly what it was told.

**The desk refers nothing**, and answers vendor questions from memory — which for a model with a
training cutoff means confidently describing an incident that was resolved months ago. Same lack of
error, opposite cause: an empty or vague description
([2.3](../02-one-at-a-time/2.3-the-specialist-you-write-yourself.md)'s failure).

**The specialist answers a question it should have refused.**

The description is a hint, not a gate. A desk model can and will occasionally refer *"why is this
customer's integration failing?"* outwards, because the sentence contains the word "integration" and the
model is trying to help. When that happens, the second layer is what catches it: the specialist's own
instruction tells it to decline questions about internal systems. Neither layer is a guarantee, which
is why [4.3](4.3-the-question-that-left-the-building.md) treats the disclosure as something you have
to design for rather than prevent by wording.

## In production

**Write tool descriptions as routing rules: what it is for, what it is not for, what it returns.**

That three-part shape is the version a professional writes, and the middle part is the one that gets
left out. It is worth being concrete in it — naming the categories that must not be sent outwards, in
the vocabulary your own tickets use — because a generic "not for internal data" is a rule the model
cannot apply to a specific ticket.

**What changes at scale** is that the description stops being sufficient. When there are six
specialists and forty tools, the descriptions compete for attention in a single request, and routing
by prose becomes unreliable in a way you can measure. That is the point at which routing becomes a
node: a cheap classifier, or an explicit graph edge, deciding before the expensive model is asked.
Phase 8 is where Sutra makes that move, and the reason it can wait until then is that Sutra currently
has one specialist.

**What fails only under real traffic** is the multilingual ticket. A description written in English
routes an English ticket well and a German one less well, and the drop is invisible in tests written
in English. If tickets arrive in more than one language, the routing rule needs testing in each.

**The review comment**: *"this description says what the tool is for and not what it is not for. Add
the boundary, or expect the model to use it for anything adjacent."*

**The interview question**: *"how does your agent decide between searching the web and searching your
own data?"* A weak answer describes the two systems. A strong one says where the decision is written,
how you would notice it going wrong, and what you would replace it with when prose stops scaling.
