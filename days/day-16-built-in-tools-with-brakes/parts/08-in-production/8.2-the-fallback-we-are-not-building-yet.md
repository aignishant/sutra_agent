# 8.2 — The fallback we are not building yet

## One-line answer

Addendum 02 planned for the grounding allowance shrinking, with an open-source search server as the
escape hatch; the allowance was re-checked today and has not shrunk, so the escape hatch stays
🅿️ **parked** — and knowing exactly what it would cost you is the point of parking it deliberately.

## The story

The 27 goes past the end of the road every twenty minutes, and you know the walk anyway.

It is thirty-five minutes on foot, along the canal, and you have done it enough times to know which
gate is locked after dark. You do not walk it when the bus is running. But on the evening the app
shows nothing for an hour, you are not standing at the stop refreshing it and getting steadily later —
you turn round and start walking, because the walk was already a thing you knew rather than a thing
you had to work out.

Knowing the walk is not the same as walking it. The value is entirely in having thought about it on a
day when it did not matter.

## The idea in plain language

Addendum 02 §5 wrote today's contingency down before today existed. Its row for Day 16 says grounding
has a limited free allowance that changes, that the pricing page must be checked **on the day**, and
that if the allowance has shrunk the fallback is *"a free open-source web-search MCP server (Phase 5
skill arriving early) so research still cites sources at $0"*.

So the first thing this part does is the check. From `ai.google.dev/gemini-api/docs/pricing`, read on
2026-09-03: **5,000 free grounding-with-Google-Search requests per month, shared across the Gemini 3.x
models**, then $14 per 1,000. That is not a shrunken allowance, and
[4.4](../04-newspaper-or-cabinet/4.4-two-meters-one-call.md)'s arithmetic showed Sutra's free tier
cannot get near it. **The fallback is not needed today**, and that sentence has a date on it.

The second thing this part does is describe the walk, because a parked option nobody has thought about
is not an option.

An MCP server is a separate process that publishes tools over a protocol, and Sutra builds one in
Phase 5 (Days 32–38). A web-search MCP server would publish something like `search(query) -> results`.
Wiring it into an agent turns web search into an **ordinary function tool** in Sutra's own process —
and that changes every single property this day has measured:

| | Today: `google_search` | The fallback: a search tool over MCP |
| --- | --- | --- |
| Who searches | the platform, on their machines | your process, calling a search backend |
| The exclusivity rule | applies: this tool and nothing else (2.1) | does not apply: it is a normal tool |
| The query | composed by the model, seen only afterwards (4.3) | **an argument you can inspect and block** (Day 13) |
| Citations | come back as grounding metadata (3.1) | whatever the server returns — yours to build |
| Meter | the search allowance (4.4) | the backend's, plus your own compute |
| Answer quality | the platform's own retrieval and ranking | the backend's, usually a search API with a free floor |

Read the third row twice. The fallback is worse on quality and integration, and **better on control**:
a `before_tool_callback` can read the query, redact it, refuse it, or log it, which is exactly the door
[4.3](../04-newspaper-or-cabinet/4.3-the-question-that-left-the-building.md) said does not exist for a
built-in. That is a real trade, not a consolation prize, and there are systems whose privacy
requirements make it the right choice even when the built-in is available.

## Why Sutra needs it

Because Principle 14 says that when reality changes the plan is amended first, and this is the day that
would trigger it.

If the pricing page had said something else this morning, the correct sequence would not have been
"start building an MCP server". It would have been: record the observation with its date, write a
dated addendum row, log it in `docs/CHANGELOG_PLAN.md`, and *then* change what the days build. This
part exists so that sequence is visible on a day when it did not fire, because a process only ever
practised in an emergency is not a process.

There is also a Phase 5 reason. When MCP arrives on Day 32, the first honest question is *"why does
this exist?"*, and one of the best answers is in this table: MCP is how a capability that lives in
somebody else's process becomes a tool in yours, with all the inspection and logging that implies.
Today's built-in is the contrast that makes the answer land.

## The mechanism

There is no code to write, because the decision is to write none. What there is, is a check you can
run again and a record of what it said:

```bash
# the freshness check for today's assumption - run it on the day, not from memory
open https://ai.google.dev/gemini-api/docs/pricing     # or paste it into a browser
```

**Line by line:**

- `open` is macOS; use `xdg-open` on Linux, `start` on Windows, or just paste the URL. This is
  deliberately a *human* check: the page is prose and a table, it moves, and reading it is the check.
- What you are looking for is the row for **Grounding with Google Search** and the free-tier column
  beside your model family. Record what you find with the date, in `docs/PACKAGES.md`, the same way a
  version is recorded.

What that check found on 2026-09-03, written the way a ledger row is written:

```text
| google_search grounding (allowance) | 5,000 requests/month free, shared across Gemini 3.x models,
  then $14 per 1,000 (ai.google.dev/gemini-api/docs/pricing) | 2026-09-03 | 16 | The day's second
  meter. Re-verify at every phase gate: Addendum 02 flagged this allowance as volatile. |
```

🅿️ **Parked, and here is exactly what is parked.** Not "web search" — Sutra has that. What is parked
is the *second* implementation of it: an MCP client in Sutra pointed at a search server, with a tool
whose arguments Sutra can see. Nothing about it is built today, the `mcp` package is **not installed**
today, and both of those are on purpose: packages arrive on the day they are first used, and Phase 5 is
where the protocol gets taught properly rather than smuggled in as a workaround.

The trigger to un-park it, written now so it is not a judgement call later:

1. the pricing page's free grounding allowance disappears, or drops below what
   [4.4](../04-newspaper-or-cabinet/4.4-two-meters-one-call.md)'s arithmetic needs; **or**
2. a privacy requirement makes an inspectable query mandatory
   ([4.3](../04-newspaper-or-cabinet/4.3-the-question-that-left-the-building.md)); **or**
3. Sutra needs search on a non-Gemini provider — which is
   [7.1](../07-failure-lab/7.1-the-spare-that-does-not-fit.md)'s failure, and the only real cure for
   it.

Any of the three, and the order is: observe, date it, amend the addendum, log it in
`CHANGELOG_PLAN.md`, then build.

## When it breaks

**The check is skipped, and the assumption ages.**

There is no error text, because nothing fails. The allowance is a number in a document written on one
day, and a document that is not re-read is a document that is slowly becoming false. Addendum 02's own
warning is explicit — quotas shrank in December 2025 with little notice — and the mechanism that
catches it is the freshness check at every phase gate (plan §15), which today's gate runs.

**The fallback is built early, in a hurry, and quietly becomes the design.** The opposite failure, and
the more common one in real teams: a workaround shipped under pressure never gets removed, and two
implementations of web search exist for a year, with different citation formats and different failure
modes. Parking is a decision to have one, and the trigger list above is what stops the decision being
made by whoever is on call.

**The trigger fires and nobody notices**, because the alert was on model quota and this is a different
meter ([4.4](../04-newspaper-or-cabinet/4.4-two-meters-one-call.md)). If the search allowance ever
becomes the binding constraint, the first sign is not an error — it is a bill.

## In production

**A parked option is only parked if somebody can describe it in a meeting.**

The version a professional writes is not a design document for the thing they are not building. It is
three lines in the place the decision lives: what the alternative is, what it would cost, and what
would have to be true to switch. That fits in an ADR, and it converts "we should look into MCP search"
from an idea somebody had into a decision somebody made.

**What changes at scale** is that these trade rows become a portfolio. A large system has several
capabilities that could come from a platform or from a component you run, and the answer is different
per capability and changes over time. The teams that handle this well keep the comparison current;
the ones that do not end up with every capability from whichever vendor was convenient the quarter it
was added.

**What fails only under real traffic** is the assumption that the fallback is equivalent. It is not:
the table above has six rows and only one of them favours the fallback outright. A switch made in an
emergency will change answer quality, citation format and latency all at once, and the people who
notice will be users rather than engineers.

**The review comment**: *"we are depending on a free allowance. Where is the number recorded, when was
it last checked, and what do we do the week it changes?"*

**The interview question**: *"what happens if the provider changes the free tier under you?"* The answer
that shows process rather than panic: *"we record the number with the date it was observed, we re-check
it at every phase gate, and the alternative is written down with its trade-offs before we need it."*
