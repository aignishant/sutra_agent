# 8.1 — Testing a built-in without spending a request

## One-line answer

You cannot fake a built-in tool, so you do not test the searching: you test the **request** — which
tools resolved, which permission it carries, which model it refuses and which executor is nowhere in
the package — and all of it runs with no key, no network and no quota.

## The story

The fire alarm gets tested on the first of the month.

Nobody lights anything. Somebody with a key opens the panel, presses the test button, and for a few
seconds the building is unbearable. Then it stops, and a line goes in a book by the door with a date
and a signature.

What the test proves is small and exact: the sounders work, the panel drives them, the wiring between
them is intact. It does not prove that people will leave the building, or that the fire door on the
second floor is not wedged open with a chair. Those need a drill, and a drill costs an afternoon of
everyone's time, so it happens twice a year and not on the first of every month.

The building has both, and the reason it has both is that the cheap test runs often enough to catch
the thing that actually breaks — which is a sounder, quietly, in a corridor nobody walks down.

## The idea in plain language

Sutra's tests have always been able to avoid model calls. Day 13 introduced a scripted model, a test
double that returns whatever the test tells it to return, and days 13 to 15 drove whole runs with it.

That trick does not work today, and the reason is the whole shape of a built-in
([1.2](../01-switched-on/1.2-an-object-with-a-placeholder-name.md)): the searching happens inside the
platform, on the far side of a call your fake model replaces. A scripted model cannot search, cannot
produce grounding metadata, and cannot run code — so there is nothing to script.

What is left is better than it sounds, because everything that actually goes wrong on this day is
decided **before** any call is made:

- which tools an agent resolved to ([2.1](../02-one-at-a-time/2.1-one-built-in-and-nothing-else.md));
- what the outgoing request carries ([1.3](../01-switched-on/1.3-the-request-that-leaves-your-process.md));
- which models the built-ins refuse ([7.1](../07-failure-lab/7.1-the-spare-that-does-not-fit.md));
- whether the referral keeps its citations ([2.3](../02-one-at-a-time/2.3-the-specialist-you-write-yourself.md));
- whether an empty source list renders an empty heading ([3.3](../03-receipts/3.3-the-receipt-you-must-show.md));
- and whether anyone has put local execution in the package ([6.3](../06-blast-radius/6.3-the-rule-sutra-writes-down.md)).

Six claims, no requests. That is the alarm test on the first of the month. The drill — an actual
grounded call, checked for actual sources — is one skipped test with a `TODO(me)` on it, because it
needs quota and it needs the internet, and both are things a test suite should not need.

## Why Sutra needs it

Because Principle 11 says evals are tests and a day ends with at least one check that can go red, and
because today's two most expensive mistakes are both invisible at run time.

The exclusivity rule is the first. An agent that grows a second tool goes from working to refused, and
nothing in ADK says so ([2.1](../02-one-at-a-time/2.1-one-built-in-and-nothing-else.md)). A test that
asserts the exact resolved tool list turns that into a red build on the commit that causes it, instead
of a 400 in production on the day somebody deploys.

SEC-01 is the second. A policy that lives only in an ADR is a preference
([6.3](../06-blast-radius/6.3-the-rule-sutra-writes-down.md)). The three-line test that greps the
package is what makes it a rule, and it is the first security control in this curriculum that can
fail a build.

## The mechanism

One new file. It imports `sutra/builtin_tools.py`, which is today's build brief, so **it is red until
you write that module** — which is the point.

```python
# tests/test_builtins.py
"""Day 16 - what can be asserted about a built-in without spending a request."""

from __future__ import annotations

import asyncio
from pathlib import Path

import pytest
from google.adk.code_executors import BuiltInCodeExecutor
from google.adk.models.llm_request import LlmRequest
from google.genai import types

from sutra.builtin_tools import MODEL, coder, referral, render_sources, researcher

NON_GEMINI = "groq/llama-3.3-70b-versatile"


def _resolved(agent) -> list:
    return asyncio.run(agent.canonical_tools())


def test_researcher_holds_the_built_in_and_nothing_else() -> None:
    """The exclusivity rule (2.1), asserted where it can go red: at commit time."""
    assert [tool.name for tool in _resolved(researcher)] == ["google_search"]


def test_request_carries_the_search_permission_and_no_declarations() -> None:
    """A built-in sends a permission, never a function declaration (1.2)."""
    request = LlmRequest(model=MODEL)
    for tool in _resolved(researcher):
        asyncio.run(tool.process_llm_request(tool_context=None, llm_request=request))
    assert [t.model_dump_json(exclude_none=True) for t in request.config.tools] == [
        '{"google_search":{}}'
    ]


def test_coder_carries_code_execution_and_holds_no_tools() -> None:
    """An executor is not a tool (5.1), and the coder holds only the executor."""
    assert coder.tools == []
    assert isinstance(coder.code_executor, BuiltInCodeExecutor)
    request = LlmRequest(model=MODEL)
    coder.code_executor.process_llm_request(request)
    assert request.config.tools[0].model_dump_json(exclude_none=True) == '{"code_execution":{}}'


def test_built_ins_refuse_a_non_gemini_model() -> None:
    """The failure lab (7.1): a provider swap does not carry a built-in."""
    with pytest.raises(ValueError, match="not supported for model"):
        BuiltInCodeExecutor().process_llm_request(LlmRequest(model=NON_GEMINI))


def test_the_referral_keeps_its_sources_and_says_what_it_is_for() -> None:
    """propagate_grounding_metadata defaults to False, and an empty description is never used (2.3)."""
    tool = referral()
    assert tool.propagate_grounding_metadata is True
    assert "NOT for" in tool.description


def test_no_sources_renders_nothing_at_all() -> None:
    """An empty heading reads as a bug (3.3)."""
    assert render_sources(None) == ""
    assert render_sources(types.GroundingMetadata(web_search_queries=["x"])) == ""
    populated = types.GroundingMetadata(
        grounding_chunks=[
            types.GroundingChunk(web=types.GroundingChunkWeb(title="t", uri="https://e.invalid/"))
        ]
    )
    assert render_sources(populated).startswith("Sources:")


def test_no_local_execution_in_the_package() -> None:
    """SEC-01 (ADR-0009): generated code never runs where Sutra's credentials live."""
    offenders = [
        path
        for path in Path("sutra").rglob("*.py")
        if "UnsafeLocalCodeExecutor" in path.read_text(encoding="utf-8")
    ]
    assert offenders == [], f"SEC-01 (ADR-0009): local code execution in {offenders}"


@pytest.mark.skip(reason="TODO(me): needs a live call and one of the day's 20 free requests")
def test_a_grounded_answer_carries_sources() -> None:
    """The only claim in this file that a scripted model cannot check."""
    raise AssertionError("write me on a day with quota")
```

**Line by line:**

- `from sutra.builtin_tools import MODEL, coder, referral, render_sources, researcher` — the import
  that makes the file red before the module exists. Five names, and they are the build brief.
- `def _resolved(agent)` with `asyncio.run(agent.canonical_tools())` — resolution is `async`, and
  wrapping it once keeps every test that needs it readable. Calling ADK's own resolution method rather
  than reading `agent.tools` is the lesson Day 15 paid for: `agent.tools` shows what you *wrote*, and
  `canonical_tools()` shows what the model is *offered*
  ([15.2.1](../../../day-15-toolsets-and-openapi/parts/02-when-asked/2.1-the-wrapper-adk-actually-calls.md)).
- `assert [...] == ["google_search"]` — an **exact list**, not a membership check. `in` would pass on
  the day somebody adds a second tool, which is precisely the failure this test exists to catch.
- `t.model_dump_json(exclude_none=True)` — comparing the serialised form rather than the object,
  because that string is what crosses the network and it is stable enough to assert on.
- `assert coder.tools == []` — the coder holds an executor and no tools. Two assertions in one test,
  which is allowed here because they are two halves of one claim: an executor is not a tool.
- `pytest.raises(ValueError, match="not supported for model")` — matching a fragment, not the whole
  message. The model name in the message would change with the provider, and the fragment is the part
  the library owns.
- `assert "NOT for" in tool.description` — asserting on the **negative half** of the routing rule
  ([4.2](../04-newspaper-or-cabinet/4.2-routing-by-where-the-truth-lives.md)), which is the half that
  gets edited away when somebody shortens a description.
- `types.GroundingMetadata(...)` built by hand — the fixture from
  [3.3](../03-receipts/3.3-the-receipt-you-must-show.md). It is not a captured response and does not
  pretend to be one; it exists so the rendering rule can be checked without a call.
- `Path("sutra").rglob("*.py")` — a string search over the package. Crude on purpose: it catches the
  import, the comment and the half-finished experiment alike.
- `@pytest.mark.skip(reason="TODO(me): ...")` — the drill, not the alarm test. It is skipped with a
  reason that names what it needs, and if the summary line ever reads `8 passed`, somebody deleted a
  `TODO(me)` instead of doing it.

Watch it go red, then green:

```bash
uv run python -m pytest tests/test_builtins.py -q -m "not live"   # RED: sutra/builtin_tools.py is empty
# ... write the module from the hub's build brief ...
uv run python -m pytest tests/test_builtins.py -q -m "not live"   # 7 passed, 1 skipped
```

**Line by line:**

- `-m "not live"` — the marker convention from Day 13, kept even though nothing in this file is marked
  live, so that the command is the same one every day uses.
- The first run fails at **collection**, not in a test: the import cannot resolve. A collection error is
  a legitimate red and it is the most honest possible statement of "the module does not exist yet".

Then break each thing on purpose. These were **measured**, each mutation applied on its own to a green
suite, on 2026-09-03:

| Break this | Which tests go red | What it is telling you |
| --- | --- | --- |
| add a second tool to `researcher` | 2 — the exact-list test and the request test | the exclusivity rule (2.1) |
| drop `propagate_grounding_metadata=True` | 1 — the referral test | the citations die at the boundary (2.3) |
| set `description=""` on `researcher` | 1 — the referral test | a specialist nobody refers to (2.3) |
| import `UnsafeLocalCodeExecutor` in `sutra/` | 1 — the SEC-01 test | the policy is a test, not a memo (6.3) |

The first row is the one to read twice: **two** tests fail, and one of them is the request test, which
means the failure is visible in the thing that actually goes over the network rather than only in a
list you assembled.

## When it breaks

**The first run fails at collection, and it should.**

```text
ImportError while importing test module 'tests/test_builtins.py'.
...
ModuleNotFoundError: No module named 'sutra.builtin_tools'
```

That is the red you are looking for before you write the module. It is not a broken test, it is an
unwritten feature.

**`AttributeError: 'coroutine' object has no attribute ...` plus a `RuntimeWarning: coroutine
'BaseTool.process_llm_request' was never awaited`.**

The tool's `process_llm_request` is `async` and the executor's is not
([5.2](../05-code-that-runs/5.2-the-executor-that-executes-nothing.md)). Forgetting `asyncio.run` on
the tool version leaves a coroutine object that never ran, and the assertion afterwards fails for a
reason that has nothing to do with what it was testing.

**The SEC-01 test passes on a machine where it should not.** It resolves `Path("sutra")` relative to the
working directory, so running pytest from somewhere other than the repository root makes it check an
empty glob and pass. That is a real weakness of the crude approach, worth knowing about, and the reason
`./m check` always runs from the root.

## In production

**Test the request, not the provider.**

The rule that generalises from today is worth carrying to every platform capability you ever switch
on: assert on what your process is *about* to send, because that is the part you own and the part that
regressions actually break. Testing the provider's behaviour requires the provider, costs quota, needs
the network, and fails for reasons that are not your fault — so it belongs in a small, separate,
deliberately-skipped set, run on purpose rather than on every commit.

**What changes at scale** is that this file becomes the specification of your agents' shape. Teams that
write these assertions end up with a test that reads like a description of the system: this agent holds
exactly this, that request carries exactly that, this class appears nowhere. New people read it before
they read the code, and it stays true because it fails when it stops being true.

**What fails only under real traffic** is everything this file cannot see — whether the model actually
chooses to search, whether the sources are any good, whether the answer matches the sandbox's output.
That is the drill, and the honest position is that it runs occasionally, deliberately, by a person, and
that its absence from CI is a decision rather than an oversight.

**The review comment**: *"this asserts `google_search in tools`. Assert the exact list — the failure we
care about is a tool being **added**."*

**The interview question**: *"how do you test an agent that uses a provider's built-in tool?"* The
answer that shows you have done it: *"you cannot fake it, so you do not try. You assert the resolved
tool list and the outgoing request, which is where every regression we ever had actually showed up, and
you keep one live check that a person runs."*
