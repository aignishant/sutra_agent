# 8.3 — What you review now

## One-line answer

Across Phase 2 the thing you review changed three times — from code, to somebody else's document, to a
switch and its output — and the last of those is the hardest, because there is nothing to read and
everything to decide.

## The story

The end of a tenancy is an argument about a boundary.

You are handing back the keys, and the inventory from two years ago is on the table between you and
the agent. The marks on the wall behind the sofa: yours. The window that never closed properly: not
yours, it was in the notes on the day you moved in. The boiler that stopped in February: theirs, and
you have the email where they said so.

Nobody is being unreasonable. It is simply that "the flat" is not one thing anybody is responsible
for; it is a list of things, each of which belongs to one of you, and the whole tense hour is about
finding the line item by item. The tenants who have a good afternoon are the ones who wrote the list
down at the start, when nothing was at stake.

## The idea in plain language

Phase 2 gave Sutra hands, and it moved the boundary of what you are responsible for three times.

**Days 10 to 13 — you reviewed code.** `lookup_ticket` is a function in your repository. Review is
reading it, and the question is *is this correct*.

**Days 14 and 15 — you reviewed a document, and a boundary.** A plugin covers agents nobody has
written yet; a generated toolset comes from a vendor's OpenAPI description. There is code, but nobody
wrote it, so the review moved to *do we trust the document, and what can this reach*.

**Day 16 — you review a switch and an output.** One line adds web search. One field decides where
generated code runs. There is no artefact, and the questions are entirely about consequence.

Here is Sutra's capability list at the end of the phase, with the honest blast radius of each:

| Capability | Whose machine | What it can reach | What you review |
| --- | --- | --- | --- |
| `lookup_ticket`, `search_kb` (Day 10) | yours | what the function reaches | the function |
| generated vendor tools (Day 15) | yours | the vendor's API, with your key | the spec, the endpoint, the allowlist |
| `google_search` (today) | the provider's | the public web; your query leaves | the routing rule, and every answer's sources |
| `BuiltInCodeExecutor` (today) | the provider's | a sandbox with numpy and simpy | the policy, and the code the model wrote |
| `UnsafeLocalCodeExecutor` (**not used**) | yours | your keys, your repo, your network | why the exception was granted |

The last row is in the table on purpose. A capability you have decided not to use is part of the
system's design, and the review question for it is different from all the others: not *is it correct*
but *is it still off*.

So the review checklist for a built-in is not a code review at all. Seven questions, in the order they
bite:

1. **What else does this agent hold?** A built-in cannot share ([2.1](../02-one-at-a-time/2.1-one-built-in-and-nothing-else.md)).
2. **What decides when it is used?** A description with a negative half, or a graph edge ([4.2](../04-newspaper-or-cabinet/4.2-routing-by-where-the-truth-lives.md)).
3. **What leaves the building when it runs?** And can anything inspect that first ([4.3](../04-newspaper-or-cabinet/4.3-the-question-that-left-the-building.md))?
4. **Which meters does it spend, and on what period?** ([4.4](../04-newspaper-or-cabinet/4.4-two-meters-one-call.md))
5. **What does the output have to carry before a person sees it?** Sources, or the code and its stdout ([3.3](../03-receipts/3.3-the-receipt-you-must-show.md), [5.3](../05-code-that-runs/5.3-reading-the-code-and-its-output.md)).
6. **Where does anything it generates execute?** ([6.3](../06-blast-radius/6.3-the-rule-sutra-writes-down.md))
7. **What happens when the provider cannot serve it?** ([7.1](../07-failure-lab/7.1-the-spare-that-does-not-fit.md))

None of those is answered by reading a diff. All of them are answered by the day's parts, which is
what makes them reviewable at all.

## Why Sutra needs it

Because Phase 2's gate is *"four free providers benchmarked; built-in tools contained"*, and
**contained** is a claim somebody has to be able to check.

The checklist above is that check, and it is also the handover to Phase 3. From tomorrow the subject is
state — scopes, lifetimes, and what survives a restart — and two of today's findings arrive there
immediately: the citations that travel through `temp:_adk_grounding_metadata`
([2.3](../02-one-at-a-time/2.3-the-specialist-you-write-yourself.md)), and the question of what a
session should remember about an answer that was grounded. Day 24's budgets inherit the second meter.
Day 66's injection work inherits point 6 of SEC-01. Phase 8's graph inherits the specialist agents that
today's exclusivity rule forced into existence.

## The mechanism

The mechanism of a review is a question asked at the right moment, so this one lives where the change
is made: at the top of the module that holds the capabilities.

```python
# sutra/builtin_tools.py - the header a reviewer reads first
"""Sutra's built-in capabilities: search grounding and code execution (Day 16).

Blast radius:
    google_search       - the query leaves the building; nothing of ours goes with it (4.3).
                          Spends the search meter: 5,000/month, shared (4.4).
    BuiltInCodeExecutor - generated code runs on the provider's machines, never here (5.2).

Rules this module is under:
    SEC-01 (docs/adr/ADR-0009-code-execution-policy.md) - no local execution.
    One built-in per agent - the Gemini API refuses an agent holding both (2.1).
    Neither capability survives a provider swap (7.1) - excluded from quota routing.

Adding a capability here means answering the seven questions in day 16, part 8.3.
"""
```

**Line by line:**

- `Blast radius:` first, before anything about how to use the module. A reviewer's first question is
  what escapes, and the answer should not be below the fold.
- Each line pairs a capability with **what leaves** and **what it costs**, with a part number so the
  claim is checkable rather than asserted.
- `Rules this module is under:` — the constraints, in one place, including the one that is easy to
  forget because it is about something that does *not* happen: neither capability survives a provider
  swap, so the quota router must skip these agents.
- The last line is the review trigger: it names the checklist by address, so the next person adding a
  capability has somewhere to go. A docstring that only describes the present is a docstring that stops
  being read.

```bash
grep -rn "Blast radius" sutra/
```

**Line by line:**

- One command that lists every module in Sutra that has declared what escapes from it. Today it finds
  one. The number should only ever go up, and a module that reaches outside the process without a
  `Blast radius:` block is the review comment writing itself.

## When it breaks

**The review that reads the diff and misses the change.**

No error text; this is a process failure with a code shape. The diff is `+ tools=[google_search]`, four
words, approved in a minute by somebody who read four words. Everything in the seven questions was
decided by that line and none of it was discussed.

The countermeasure is not a stricter reviewer. It is that the questions have answers *in the
repository* — a routing rule with a name
([4.2](../04-newspaper-or-cabinet/4.2-routing-by-where-the-truth-lives.md)), a policy with an ADR
([6.3](../06-blast-radius/6.3-the-rule-sutra-writes-down.md)), a test with an assertion
([8.1](8.1-testing-a-built-in-without-spending-a-request.md)) — so that the review is a check against
written things rather than an act of memory.

**The capability that was contained and then quietly was not.** The failure with the longest fuse. A
built-in is contained by an arrangement — one agent, one capability, a policy, a test — and every one of
those can be undone by an ordinary change made for a good reason. That is exactly what the tests in
[8.1](8.1-testing-a-built-in-without-spending-a-request.md) exist to catch, and why the SEC-01 check
greps for a class name rather than trusting anybody's intent.

## In production

**Write the boundary down while nothing is at stake.**

Every mechanism in this part is the same move: record the responsibility split before there is an
argument about it. The docstring, the ADR, the test, the ledger row with a date. None of them is
clever, and all of them are cheap on the day the capability is added and expensive to reconstruct
later.

**What changes at scale** is that the boundary becomes a shared document rather than a personal
understanding. On a team, "we do not run generated code locally" is either written and tested or it is
folklore, and folklore has a half-life of about one person leaving.

**What fails only under real traffic** is the review's blind spot. The seven questions are all about
the capability. The thing that actually breaks first, in most systems, is the *interaction*: an agent
that gained a built-in and a toolset in the same month, where each change was reviewed correctly and
the combination was reviewed by nobody. Reviewing resolved tool lists rather than diffs
([8.1](8.1-testing-a-built-in-without-spending-a-request.md)) is the only defence that scales.

**The review comment** worth leaving on somebody else's built-in, and the one that survives being asked
of you: *"which of the seven does this change move, and where is the new answer written down?"*

**The interview question**: *"how do you review a change that adds a platform capability to an agent?"*
The answer that sounds like a practitioner is not "carefully". It is a list — what else the agent holds,
what decides when it runs, what leaves, what it costs, what the output must carry, where code runs, and
what happens when the provider cannot serve it.

```bash
grep -rn "Blast radius" sutra/ && ls docs/adr/ && uv run python -m pytest tests/test_builtins.py -q -m "not live"
```

Three artefacts: a module that declares what escapes, an ADR that names the rule, and a test that fails
if either stops being true.
