# 1.1 — A power you switch on

## One-line answer

A **built-in tool** is not code in your process at all: it is a mode you switch on inside the model
call, run on the provider's machines, and the only two things left for you to review are the switch
you flicked and the output that came back.

## The story

You used to keep a small torch in the drawer by the door.

It was a torch and nothing else. Two batteries, one switch, a bulb you could unscrew. When it stopped
working there were three things it could be, and you could check all three at the kitchen table.

Then your phone had a torch. Same job, brighter, always in your pocket, and you never bought it. You
did not choose the bulb. You cannot unscrew anything. There is a button on the screen, and behind the
button is a phone you did not design.

It is better in every way until the evening the power goes out and you have been on the phone all
afternoon. The torch is not on its own two batteries any more. It is on the phone's battery, along
with the maps and the messages and the camera, and when that battery is flat, the thing you would
have reached for in a drawer is flat as well.

Nothing broke. You just stopped owning the light.

## The idea in plain language

Sutra has gained a new power on three separate days, and each time it arrived a different way.

**Day 10 — you wrote it.** `lookup_ticket` is a Python function in Sutra's own package. You typed
every line of it, you can read it, you can step through it in a debugger, and it runs in your
process, on your machine, under your account. If it is wrong, it is wrong in a file you own.

**Day 15 — a machine wrote it from somebody else's document.** The tools inside an `OpenAPIToolset`
were generated from a vendor's OpenAPI description
([15.4.2](../../../day-15-toolsets-and-openapi/parts/04-machine-packed/4.2-spec-in-tools-out.md)).
You did not write them, but they still run in your process: when the model calls one, your `httpx`
makes the request from your laptop, with a key you hold.

**Today — you switch one on.** `google_search` is not a function and never becomes one. Putting it on
an agent's `tools` list adds one line to the request Sutra sends to Gemini, and that line says: *for
this call, you may search the web.* The searching happens inside Google's own machinery, before the
answer comes back. Your process never opens a socket to a search engine. There is nothing to step
through, because on your side there is nothing running.

That is what **built-in** means here. Not "included in the library". Not "a tool with the batteries
already in it". It means the capability lives in the model and the platform behind it, and the
library gives you a switch.

Three terms, defined once, because the rest of the day leans on them:

- a **tool**, since [Day 4](../../../day-04-tools-by-hand/LESSON.md), is a thing the model may
  *choose* to call, described to it in the request;
- a **toolset**, since
  [Day 15](../../../day-15-toolsets-and-openapi/parts/01-crate-not-list/1.1-one-line-many-tools.md),
  is one entry on the `tools` list that ADK asks for its contents, so one line can become forty tools;
- a **built-in tool** is an entry on the same list that is neither of those. It contributes no
  function for the model to call. It changes the *kind of call* being made.

Here is the whole difference in one table, and the last column is the one that matters for the rest
of the day:

| How Sutra got the power | Example | Whose computer runs it | What you review |
| --- | --- | --- | --- |
| You wrote the function | `lookup_ticket` (Day 10) | yours | every line of the function |
| A machine generated it from a spec | `incidents_get` (Day 15) | yours | the vendor's document, and the endpoint |
| **You switched it on** | `google_search` (today) | **the provider's** | **the switch, and the output** |

Reading down that last column is the day in one movement. The amount of code you can review goes to
zero, and the amount of judgement you have to apply goes up, because the only evidence you will ever
get about a built-in tool is what came back.

## Why Sutra needs it

Because two of the questions Sutra exists to answer cannot be answered by anything Sutra owns.

The first is *"is this vendor broken right now?"*. Day 15 built a vendor status tool, but the vendor
in it was `vendor.py`, a stub on `127.0.0.1` that says whatever you wrote. No hand-written function
knows what happened on the public internet this morning, because the fact did not exist when the
function was written.

The second is *"what is the 95th percentile of these response times?"*. That is not a lookup. It is
arithmetic on numbers that arrived in the ticket, and a language model doing arithmetic in its head is
the failure you already watched on [Day 2](../../../day-02-llm-mechanics/LESSON.md): it predicts a
plausible next token, and a plausible number is not a correct one.

Both powers exist as built-ins, and both arrive today. Phase 8's Researcher node (Days 53–59) is the
first agent in the graph that will hold one permanently, and Day 24's accounting has to count what
they spend — which, as [4.4](../04-newspaper-or-cabinet/4.4-two-meters-one-call.md) shows, is not
counted in the same currency as everything else you have spent so far.

## The mechanism

Two imports, two agents, and the asymmetry you have to be able to explain out loud:

```python
# days/day-16-built-in-tools-with-brakes/lab/two_switches.py
"""The two built-ins of Day 16, side by side. Zero model calls: nothing is run."""

from google.adk.agents import Agent
from google.adk.code_executors import BuiltInCodeExecutor
from google.adk.tools import google_search

MODEL = "gemini-3.7-flash"  # Sutra's pin since Day 2; free tier, 20 requests per day

searcher = Agent(
    name="sutra_searcher",
    model=MODEL,
    instruction="Answer questions about the current public web, and cite what you found.",
    tools=[google_search],  # a TOOL: an entry on the list, and the whole list
)

coder = Agent(
    name="sutra_coder",
    model=MODEL,
    instruction="Answer numeric questions by writing and running Python, never in your head.",
    code_executor=BuiltInCodeExecutor(),  # an EXECUTOR: not on the list at all
)

print("searcher tools    :", [type(t).__name__ for t in searcher.tools])
print("searcher executor :", searcher.code_executor)
print("coder tools       :", coder.tools)
print("coder executor    :", type(coder.code_executor).__name__)
```

**Line by line:**

- `from google.adk.tools import google_search` — the import that works. `google_search` is
  re-exported from the package root, unlike `BaseToolset` yesterday
  ([15.1.2](../../../day-15-toolsets-and-openapi/parts/01-crate-not-list/1.2-one-method-and-the-import.md)),
  so the obvious path is the right one this time. Verified against
  `adk.dev/grounding/google_search_grounding/` on 2026-09-03, which gives exactly this line.
- `from google.adk.code_executors import BuiltInCodeExecutor` — a **different package**.
  `google.adk.tools` does not have it, and asking for it there fails in a way worth seeing; *When it
  breaks* has the message.
- `MODEL = "gemini-3.7-flash"` — pinned, never defaulted. ADK's own default is a preview model with a
  tighter free quota (Addendum 02 §5), and every day since Day 5 has written the string out.
- `tools=[google_search]` — one entry, and deliberately the only entry. The reason it is alone is
  section 2, and it is the single most surprising rule in today's subject.
- `code_executor=BuiltInCodeExecutor()` — a **constructor argument of its own**, not a member of
  `tools`. Search is something the model may choose per turn; code execution is a property of the
  agent, like its model or its instruction. Put the executor on the `tools` list and pydantic refuses
  it, which is the second error in *When it breaks*.
- `print(...)` four times — the point of the script. One agent has a tool and no executor, the other
  has an executor and no tools, and neither field can stand in for the other.

Run it, and nothing goes over the network:

```bash
cd days/day-16-built-in-tools-with-brakes/lab
uv run python two_switches.py
```

**Line by line:**

- `cd .../lab` — every script today runs from inside `lab/`, the same rule as Day 15, because the
  later ones import each other by bare name.
- `uv run python two_switches.py` — `uv run` puts the pinned environment in front of the script, so
  the `google-adk` you are reading about is the one that runs.

The output, measured on `google-adk` 2.7.1 on 2026-09-03:

```text
searcher tools    : ['GoogleSearchTool']
searcher executor : None
coder tools       : []
coder executor    : BuiltInCodeExecutor
```

Two agents were constructed, a key was never read, and no request was sent. **Constructing an agent
with a built-in tool costs nothing**, because the switch is not thrown until a call is made.

## When it breaks

**You call it, because everything else on the `tools` list was a function.**

```text
TypeError: 'GoogleSearchTool' object is not callable
```

`google_search` is not a function and not a class. It is a **single already-built object** — the last
line of `google_search_tool.py` in the installed package is `google_search = GoogleSearchTool()`. You
pass the object itself, with no brackets. Yesterday's trap was the opposite way round: a *class*
passed without brackets got silently wrapped as a tool
([15.1.1](../../../day-15-toolsets-and-openapi/parts/01-crate-not-list/1.1-one-line-many-tools.md)).
Today, brackets on the object are the mistake, and this one at least fails loudly.

**You look for the code executor in the tools package.**

```text
AttributeError: module 'google.adk.tools' has no attribute 'BuiltInCodeExecutor'
```

Not an `ImportError` — an `AttributeError`, because `google.adk.tools` resolves lazily-loaded names
through a `__getattr__` and yours is not one of them. The fix is the import path in the mechanism
above: `google.adk.code_executors`. The two capabilities live in different packages because they are
different kinds of thing, and the package layout is telling you so before the documentation does.

## In production

**What you review changes shape, and it gets smaller in a way that should make you uncomfortable.**

For a hand-written tool, review is code review: someone reads the function. For a generated tool it
is document review: someone reads the vendor's spec and decides whether that endpoint should be
reachable at all. For a built-in there is no artefact to read. The pull request that adds web search
to an agent is **one line**, and that line is the entire change: what it can reach, what it costs,
what leaves the building, and what comes back are all decided somewhere you cannot see.

So the review comment a senior engineer leaves on that one-line diff is never about the line. It is
three questions:

1. *Which agent is this on, and what else does that agent hold?* (Section 2 makes this a hard
   constraint rather than a preference.)
2. *What does the output have to carry before we show it to anyone?* (Section 3: a grounded answer
   without its sources is not an answer.)
3. *Which meter does this spend?* (Section 4: not the one you have been watching.)

**What changes at scale** is that the switch is the only thing you can version. A hand-written tool
changes when you change it. A built-in changes when the provider changes it, which means a behaviour
your evals depended on can move without a single commit in your repository. This is the same shape as
Day 15's frozen spec, one layer further away: there, a vendor could change a document under you;
here, a vendor can change the *capability* under you. Principle 14 is the answer in both cases — if
reality moves, the plan is amended first — and the mechanism is the freshness check at every phase
gate, which is why today's gate re-reads the provider's own pages rather than trusting this document.

**The interview question** is *"how would you give an agent web search?"*, and the answer that shows
you have done it is not the import line. It is: *"one line, and then the three things the one line
does not tell you — the tool cannot share an agent with our own tools, the answer is not usable
without its citations, and it spends a second quota nobody was watching."*
