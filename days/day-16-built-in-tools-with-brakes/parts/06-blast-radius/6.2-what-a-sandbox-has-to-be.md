# 6.2 — What a sandbox has to be

## One-line answer

A sandbox is not "a place where code runs"; it is five specific denials — no credentials, no reach,
no persistence, a bound on how long, and a boundary that survives the code trying to leave — and an
executor is a sandbox only for the ones it actually enforces.

## The story

The exam hall.

Everything about it is a removal. The tables are apart, so nobody can see a neighbour's paper. There
is nothing on the desk except the paper, a pen and your candidate number; bags go along the wall,
phones go in a box at the front. You cannot leave and come back. When the invigilator says stop, you
stop, and you leave with nothing — the question paper is collected too, and even the rough working
goes in the pile.

None of that is about trusting you. The same removals apply to the person who has never cheated at
anything, because the room is designed so that the question of trust does not have to be answered at
all. That is why the arrangement works, and it is why an exam "at home, on your honour" is a different
thing with the same name.

## The idea in plain language

[6.1](6.1-the-executor-that-runs-it-here.md) showed model-written code reading five API keys out of a
`.env`. The natural response is *"run it in a sandbox"*, and that phrase is where the thinking usually
stops. It should not, because a sandbox is a list of specific denials and different runners enforce
different subsets.

Five things, each of which fails independently:

| The denial | What it means | What it stops |
| --- | --- | --- |
| **No credentials** | the environment is empty; no `.env`, no service account, no mounted secret | code that reads your keys and posts them somewhere |
| **No reach** | the filesystem is a scratch space; the network is closed, or narrow and named | code that reads your repository or calls your internal services |
| **Disposable** | the environment is destroyed after use and never reused | one execution planting something the next execution finds |
| **Bounded** | a limit on how long it may run, and on what it may consume | an infinite loop taking the agent down with it |
| **Contained** | a real boundary — a separate machine, kernel or VM — not a convention | code that walks out of the box it was put in |

Now grade the two executors Sutra can actually reach today, against that list.

`BuiltInCodeExecutor` — the provider's sandbox — passes all five as far as your process is concerned,
and the reason is structural rather than configured: the code never arrives on your machine
([5.2](../05-code-that-runs/5.2-the-executor-that-executes-nothing.md)). There is no environment
because there is no process of yours involved. The SDK's own type definitions say the environment is
Python 3.10 or later with numpy and simpy, and that the outcome can be
`OUTCOME_DEADLINE_EXCEEDED` — so there is a bound, and it is theirs.

`UnsafeLocalCodeExecutor` passes **one and a half**. It is a separate process, which is half of
*contained* — no shared Python objects, no shared file handles — and it inherits your environment and
your working directory, which fails *no credentials* and *no reach* outright. It is not disposable in
any meaningful sense, because the things it can touch outlive it. And its bound is off by default:
`timeout_seconds` is `None`, which the executor passes straight to `queue.get(timeout=None)`, which
waits for ever.

That last one is the part worth measuring, because it is the failure that does not need an attacker.

## Why Sutra needs it

Because "we will sandbox it" is exactly the kind of sentence that passes review and means nothing, and
Sutra is about to write a policy that has to mean something
([6.3](6.3-the-rule-sutra-writes-down.md)).

The five denials are the vocabulary that makes the policy checkable. A rule that says *"generated code
runs in a sandbox"* cannot be reviewed. A rule that says *"generated code runs where there are no
credentials, no path to our network, a time bound, and nothing that survives the run"* can be checked
against any proposal in a few minutes, including proposals that arrive years from now with product
names attached.

Sutra needs the vocabulary again on Day 71, where sandbox providers are drilled properly alongside
computer use, and on Day 88, where the local Kubernetes work makes *contained* a thing with a
manifest. Today is where the words are defined.

## The mechanism

Two measurements: the bound that is off by default, and the executors that are not installed.

```python
# days/day-16-built-in-tools-with-brakes/lab/no_timeout.py
"""The bound the local executor does not have unless you ask. Zero model calls."""

from google.adk import code_executors as ce
from google.adk.code_executors import UnsafeLocalCodeExecutor
from google.adk.code_executors.code_execution_utils import CodeExecutionInput

FOREVER = "while True:\n    pass\n"


def main() -> None:
    print("default timeout_seconds:", UnsafeLocalCodeExecutor().timeout_seconds)

    bounded = UnsafeLocalCodeExecutor(timeout_seconds=2)
    result = bounded.execute_code(None, CodeExecutionInput(code=FOREVER))
    print("stdout:", repr(result.stdout))
    print("stderr:", result.stderr.strip())

    for name in (
        "ContainerCodeExecutor",
        "GkeCodeExecutor",
        "VertexAiCodeExecutor",
        "AgentEngineSandboxCodeExecutor",
    ):
        try:
            print(f"{name}: available as {getattr(ce, name).__name__}")
        except ImportError as error:
            print(f"{name}: {str(error).splitlines()[0]}")


if __name__ == "__main__":
    main()
```

**Line by line:**

- `UnsafeLocalCodeExecutor().timeout_seconds` — the default, printed rather than described. It is
  inherited from `BaseCodeExecutor`, where the field is documented as *"The fallback timeout in
  seconds for the code execution"*, and its default value is `None`.
- `FOREVER` — the smallest program that never ends. Not an attack, just a bug: a model writing a loop
  over a list it thought was finite produces this by accident.
- `timeout_seconds=2` — a bound, set explicitly, because the point of the script is that the bound only
  exists when you ask for it. Two seconds is short enough to keep the lab pleasant.
- `bounded.execute_code(None, ...)` — the same direct call as
  [6.1](6.1-the-executor-that-runs-it-here.md), with the invocation context unused.
- `for name in (...)` with `getattr(ce, name)` — the package's `__getattr__` resolves these lazily, so
  asking for one is what triggers its import. This is the cheapest possible survey of what else ADK can
  run code in.
- `except ImportError` — the four executors are not all installed, and the message tells you what to
  install. Catching it is how the script reports the landscape instead of dying on the first gap.
- The `__main__` guard again, for the same `spawn` reason as
  [6.1](6.1-the-executor-that-runs-it-here.md).

- One deliberate infinite loop, bounded, and a survey. No key, no request, no network.

Three findings in eight lines. The bound is `None` unless you set it. When you set it, the executor
does kill the run and says so plainly. And ADK ships four more executors — Docker, Kubernetes, and two
Google Cloud ones — of which two need an extras install and all four need infrastructure Sutra does not
have and, under Addendum 02, will not pay for.

🅿️ **Parked, deliberately:** the sandbox *providers*. `ContainerCodeExecutor` needs Docker,
`GkeCodeExecutor` needs a cluster, and the two Vertex-family executors need a Google Cloud project with
billing. They are named here so you know they exist and can say what each one buys you. Day 71 drills
them properly, and Day 88 builds the Kubernetes half locally on kind or k3d, which is where
`GkeCodeExecutor` stops being an awareness item.

## When it breaks

**The loop that has no bound.**

```text
stderr: Code execution timed out after 2 seconds.
```

That is the message *with* a bound. Without one there is no message: the run hangs, the agent hangs,
and the request that started it hangs behind them. A timeout is not a nicety, it is the difference
between one bad answer and an unresponsive service.

**The bound that was not enough.** A `timeout_seconds` on the executor limits the *execution*, not the
damage. Code that opens a socket and posts your environment somewhere finishes in well under a second
and reports `OUTCOME_OK`. The bound is one of five denials, and the four others are not covered by any
number you can put in that argument.

**The extras that are not there.**

```text
ContainerCodeExecutor requires additional dependencies. Please install with: pip install "google-adk[extensions]"
```

Worth reading as a signal rather than as an obstacle: the executors that provide real isolation are the
ones with dependencies and infrastructure behind them. Isolation costs something to run. An executor
that installs with nothing and needs nothing is telling you what it does not do.

## In production

**Grade a proposal against the five denials, one at a time, and write the answers down.**

The practical form is a short table in a design document — what credentials exist in the sandbox, what
it can reach, what survives it, what bounds it, and what the boundary actually is. Most proposals fail
on *reach*: the container is isolated from your laptop and sits inside your network, where the
interesting services are. That is the question worth asking first.

**What changes at scale** is that the sandbox becomes shared. One disposable environment per execution
is expensive, so systems reuse them, and reuse is where *disposable* quietly stops being true. If two
customers' code runs in the same environment, the second one can read what the first one left, and the
denial you thought you had is now a scheduling policy.

**What fails only under real traffic** is resource exhaustion. A time bound does not stop memory being
filled, disk being filled or a fork bomb; those need the container's own limits. ADK's local executor
kills the process group on timeout — the installed source signals `SIGTERM` to the group, waits, then
escalates to `SIGKILL` — which is more care than most homemade runners take and still not a resource
limit.

**The review comment**: *"the design says 'runs in a sandbox'. Which of the five does it enforce, and
which are we accepting?"*

**The interview question**: *"what makes something a sandbox?"* A weak answer names a technology. A
strong one names the denials and then says which of them the technology in question actually gives
you — because that is the same answer for a container, a microVM and a provider's execution service,
and it is the only version that transfers.
