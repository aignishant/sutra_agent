# 6.3 — The rule Sutra writes down

## One-line answer

SEC-01 is Sutra's first written security rule — *model-generated code never runs in a process that
holds our credentials* — and it is worth writing today precisely because today it costs nothing to
obey.

## The story

The note on the fridge says: shoes off at the door.

It has been there for years, in somebody's handwriting, held on with a magnet from a plumber. Nobody
in the house needs it. They take their shoes off without thinking, and the note is not for them.

The note is for the evening somebody arrives carrying a box in both hands and says "I'll only be a
second". It is for the friend who genuinely does not know, and for the child who genuinely does not
care. In those moments nobody has to be the person with an opinion about shoes, and nobody has to
invent a rule while holding a door open with their foot. You point at the note, and the note has been
right about this since long before anyone was standing in the hall.

A rule written when it was easy is a rule available when it is not.

## The idea in plain language

Everything in section 6 leads here. `UnsafeLocalCodeExecutor` gives model-written code your keys and
your repository ([6.1](6.1-the-executor-that-runs-it-here.md)). A sandbox is five specific denials,
and executors differ in how many they enforce ([6.2](6.2-what-a-sandbox-has-to-be.md)). Sutra's
current default enforces all five by construction, because the code runs on the provider's machines
and never arrives here.

So the risk today is zero, and that is exactly why the rule gets written today. The moment a rule like
this is genuinely needed is the moment it is hardest to write: somebody has a plotting library the
sandbox does not have, a deadline, a working branch, and a one-word change that makes it all go away.
A rule invented in that conversation is a negotiation. A rule that already exists is a fact.

**SEC-01 — Sutra's code execution policy:**

> **1.** Model-generated code is untrusted, always. Not because the model is hostile, but because its
> inputs are: a ticket is text a stranger wrote, and from Day 66 Sutra treats it as an attack surface.
>
> **2.** Model-generated code never executes in a process that holds Sutra's credentials, its
> repository, or a position inside a private network. In practice: `UnsafeLocalCodeExecutor` is never
> used in `sutra/`, in any test that runs in CI, or in any demo that reads `.env`.
>
> **3.** Today's execution runs provider-side, via `BuiltInCodeExecutor`. The containment is
> structural — the code is never on our machine — and it is stated here so that the day it changes,
> the change is visible.
>
> **4.** Any other executor requires a written exception in an ADR, naming which of the five denials
> ([6.2](6.2-what-a-sandbox-has-to-be.md)) it enforces and which it does not, and what compensates for
> each gap.
>
> **5.** The policy is enforced by a test, not by memory
> ([8.1](../08-in-production/8.1-testing-a-built-in-without-spending-a-request.md)). A rule with no
> failing check is a preference.
>
> **6.** Output from generated code is data, never instruction. Whatever the sandbox prints is
> reported, stored and shown; it is never fed back as if it were a command from an operator.

Point 6 is the one people leave out, and it is the bridge to Day 66. A sandbox stops code from
*doing* things. It does nothing about what the code *says*, and text that comes back from a sandbox
is on its way into the model's next turn.

## Why Sutra needs it

Because Phase 10's entire safety curriculum assumes a written baseline to build on, and because
Phase 14 makes this repository public.

The public part is worth dwelling on. When the repository is read by strangers, an ADR that says *"we
thought about where generated code runs, here is the rule, here is the test"* is the difference
between a project that looks careful and one that looks lucky. It is also the first entry in what
becomes a real security posture: SEC-02 is honest error surfacing, SEC-03 onwards is the injection
work, and every one of them reads better standing on a rule that was written before it was needed.

The nearer reason is Day 71, which drills sandbox providers with computer use — the largest blast
radius in the plan. That day's work is a series of exceptions to this policy, and an exception process
needs a policy to be an exception to.

## The mechanism

The mechanism of a policy is where it lives and what enforces it. Sutra writes it as an ADR, in the
repository's existing machinery, and as a docstring on the module that could break it.

```python
# sutra/builtin_tools.py - the module docstring, written before the code under it
"""Sutra's built-in capabilities: search grounding and code execution (Day 16).

Blast radius:
    google_search      - the query leaves the building; nothing of ours goes with it (4.3).
    BuiltInCodeExecutor - generated code runs on the provider's machines, never here (5.2).

SEC-01 (docs/adr/ADR-0009-code-execution-policy.md):
    Model-generated code never executes in a process holding Sutra's credentials.
    UnsafeLocalCodeExecutor is not used in this package, in tests, or in any demo
    that reads .env. Changing the executor requires an ADR naming which of the five
    sandbox denials the replacement enforces.

Two agents, one capability each, because a built-in cannot share an agent with
another tool on the Gemini API (2.1).
"""
```

**Line by line:**

- `Blast radius:` as a named section of the docstring — the same convention Day 15 introduced with
  `Layer:` and `Trust:`. It answers the question a reviewer actually has when they open a module that
  can reach outside the process.
- Each capability gets **one line naming what escapes**, with the part number that proves it. A
  docstring that says "uses Google Search" is a comment; one that says "the query leaves the building"
  is a warning.
- `SEC-01 (docs/adr/...)` — the rule quoted where it can be broken, with a path to the full text. A
  policy that lives only in `docs/` is read once, at review time, by whoever remembers it exists.
- *"in this package, in tests, or in any demo that reads .env"* — the scope written precisely, because
  a vague rule is unenforceable. The lab script in
  [6.1](6.1-the-executor-that-runs-it-here.md) *does* use the unsafe executor, deliberately, and it is
  outside all three scopes: it is a teaching artefact in a day folder, and it is the one place the rule
  bends by design.
- The last paragraph explains the two-agent shape, so the next person to open the file does not try to
  merge them.

The ADR itself is yours to write, and the day's build brief carries it as a `TODO(me)`. What it must
contain is not a mystery: the six numbered points above are the decision, and an ADR wraps them in the
repository's standard shape — context, decision, consequences.

```bash
touch docs/adr/ADR-0009-code-execution-policy.md
```

**Line by line:**

- `docs/adr/` — where the previous eight live. `ADR-0009` is the next free number; check with
  `ls docs/adr/` before writing, because a number used twice is worse than no number.
- The slug says what the decision is about, matching the existing files.

## When it breaks

**A policy with no test is a preference, and preferences lose to deadlines.**

There is no error text here, because the failure is organisational. It looks like this: a
`code_executor=UnsafeLocalCodeExecutor()` in a branch, with a comment saying `# temporary, for the
chart`, merged on a Friday. Nothing fails. The tests pass. The agent works better than it did, because
the local sandbox has every library on the machine.

The check that turns this into a red build is three lines and it lives in
[8.1](../08-in-production/8.1-testing-a-built-in-without-spending-a-request.md):

```python
def test_no_unsafe_executor_in_the_package() -> None:
    """SEC-01: model-generated code never runs where Sutra's credentials live."""
    offenders = [
        p for p in Path("sutra").rglob("*.py") if "UnsafeLocalCodeExecutor" in p.read_text()
    ]
    assert offenders == [], f"SEC-01 (ADR-0009): local execution in {offenders}"
```

**Line by line:**

- `Path("sutra").rglob("*.py")` — the package only. Day folders are teaching material and are
  deliberately out of scope.
- `"UnsafeLocalCodeExecutor" in p.read_text()` — a string search, not an import graph. Crude, and crude
  is the point: it catches the comment, the import, the commented-out line and the half-finished
  experiment, and it cannot be defeated by accident.
- The assertion message names **the rule and the ADR**, not just the file. A failing test that says
  *"SEC-01 (ADR-0009)"* sends the reader to the reasoning; one that says *"assert [] == [PosixPath(...)]"*
  sends them to a search engine.
- It is a test, so it runs in `./m check` with everything else, and a policy that runs on every commit
  is a policy that is still true in March.

**The exception that never got written.** The other failure mode is a team that follows the rule and
never records the one time it did not. Day 71 will legitimately need local or containerised execution.
If that arrives without an ADR, the policy quietly becomes untrue, and the next person cannot tell
which of the two states the system is in.

## In production

**Write the rule when it is free, enforce it with a test, and make the exception path real.**

All three are needed. A rule with no test decays. A test with no written rule is cargo — someone will
delete it because "we do not use that class anyway". And a rule with no exception path gets broken
silently instead of amended openly, which is worse than either.

**What changes at scale** is who the policy is for. On a solo project it is a note to yourself. In a
team it is what makes a review possible without an argument, because the reviewer is pointing at a
document rather than expressing a preference. In a regulated setting it is evidence, and the test is
the evidence that the evidence is true.

**What fails only under real traffic** is point 6. Sandboxed code is contained, and its *output* is
not: it flows into the model's next turn as ordinary text. A sandbox with perfect isolation happily
prints an instruction that the next turn reads. That is the whole of Day 66's subject, and it is in
this policy today so that the day the injection work starts, the rule was already there.

**The review comment**: *"this changes the code executor. Which ADR is the exception in?"*

**The interview question**: *"how do you decide where an agent's generated code runs?"* The answer that
sounds like experience is not a technology. It is *"we wrote the rule down before we needed it, the
default is the safest thing available, anything else needs a written exception naming what it gives
up, and there is a test that fails if someone changes it."*

## Check yourself

```bash
ls docs/adr/ && grep -rn "UnsafeLocalCodeExecutor" sutra/ || echo "clean: no local execution in the package"
```

The first command tells you the next free ADR number; the second is the policy check by hand, before
the test exists.
