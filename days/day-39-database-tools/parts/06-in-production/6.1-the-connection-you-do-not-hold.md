# 6.1 — The connection you do not hold

## One-line answer

A database tool opens its connection inside the call and closes it before returning, because a
connection kept between calls is state living in one process — and on SQLite a read connection with
an open transaction blocks every writer with `database is locked`.

## The story

The tap in the kitchen has been running while you fill glasses for four people.

It is easier. You fill one, hand it over, fill the next, and the water is there each time without
turning anything. Nobody would call it wrong.

Then somebody in the bathroom turns on the shower and gets a trickle, because the pressure in this
building is shared and the kitchen tap is holding most of it. They shout. You cannot hear them over
the running water. When you finally turn it off, the shower comes back immediately and there was
never anything wrong with the plumbing.

The convenience was real. It was just not free, and the person paying was not the person choosing.

## The idea in plain language

The obvious way to write a database tool is to open the connection once, when the module loads, and
reuse it. Opening a file is not free, and doing it on every call feels wasteful.

For a tool on an MCP server, it is the wrong shape, for two separate reasons.

**A held connection is state in one process.** Everything
[Day 32](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md)
established about the 2026-07-28 revision applies: a request should be answerable by any instance,
and anything a server remembers between requests is a reason it cannot be. A module-level connection
is not as bad as a session — it holds no per-caller state — but it is a resource whose lifetime is
the process rather than the request, and it makes "how many connections does this server have open"
a question with a surprising answer.

**On SQLite, a held connection holds locks.** This is the sharp one, and it is specific to a
file-backed engine. SQLite coordinates access through locks on the file. A connection that has begun
a read transaction — which happens implicitly the moment you run a statement and do not finish with
it — holds a shared lock, and a writer needs an exclusive one. The writer waits, up to its timeout,
and then fails.

The rule that comes out of both is short: **the connection's lifetime is the call's lifetime.** Open
in the function, use it, close it in a `finally`. On SQLite, opening a local file is measured in
tens of microseconds, so what you save by holding it is nothing and what you cost somebody else is
their write.

## Why Sutra needs it

Because `sutra_mcp/db_tools.py` runs inside a server that
[Day 43](../../../day-43-stateless-by-default/LESSON.md) will deploy in a shape where any instance
answers any request, and a module-level connection is exactly the kind of thing that works on one
instance and behaves strangely on three.

And because Sutra will have a writer. The archive is seeded by a script today; tomorrow it is fed by
an ingestion job, and [Day 47](../../../day-47-persistent-sessions/LESSON.md) puts sessions in a
database beside it. The moment there is a writer, every read connection's lifetime becomes somebody
else's problem.

## The mechanism

The shape, and the reason each line is where it is:

```python
def lookup_ticket(ticket_id: str) -> dict:
    """Return one ticket by id, or an honest not_found."""
    con = connect_readonly()
    try:
        row = con.execute(
            "SELECT id, title, body, status FROM tickets WHERE id = ?", (ticket_id,)
        ).fetchone()
    finally:
        con.close()
    if row is None:
        return {"status": "not_found", "message": f"No ticket with id {ticket_id!r}."}
    return {"status": "ok", "ticket": dict(zip(("id", "title", "body", "status"), row))}
```

**Line by line:**

- `connect_readonly()` is called **inside** the function, so the connection is created per call and
  cannot outlive it. There is no module-level connection object anywhere in the file, which is the
  property you want to be able to state in one sentence.
- `try/finally` closes on every path, including the one where `execute` raises. Without the `finally`,
  a query that errors leaves a connection — and its locks — until garbage collection gets round to
  it, which is a timing-dependent bug and the worst kind.
- `.fetchone()` inside the `try` drains what is needed before the close. Returning a cursor and
  reading it after `close()` raises `sqlite3.ProgrammingError: Cannot operate on a closed database`,
  which is the trap in "just return the cursor and let the caller iterate".
- The not-found check is **after** the `finally`, on a plain Python value. The connection is already
  gone by the time any business logic runs, so no branch can accidentally hold it.
- `row is None` returning `not_found` as data rather than raising is
  [Day 21's](../../../day-21-errors-surface-not-swallow/LESSON.md) rule: a ticket that does not exist
  is an answer, not an error.
- `dict(zip(...))` names the columns in the result, so a caller — and a model — is not indexing into
  a tuple. Adding a column to the `SELECT` without adding it here is a silent mismatch, which is why
  the column list appears once as a tuple rather than twice as prose.

What holding it looks like instead, and what the reader must not copy:

```python
_CON = connect_readonly()  # module level: one connection for the life of the process


def lookup_ticket(ticket_id: str) -> dict:
    row = _CON.execute("SELECT id FROM tickets WHERE id = ?", (ticket_id,)).fetchone()
    return {"status": "ok" if row else "not_found"}
```

**Line by line:**

- `_CON` is created at import time. If the archive file is missing at import, the whole module fails
  to load and the server does not start — a failure at the worst possible moment, and one that a
  per-call connection would have reported as a single tool error.
- There is no `close` anywhere, so the connection lives until the process exits.
- `sqlite3` connections are not safe to share across threads by default. A threaded server calling
  this from two threads raises `sqlite3.ProgrammingError: SQLite objects created in a thread can only
  be used in that same thread`, and the usual "fix" — passing `check_same_thread=False` — removes the
  error and keeps the race.
- Every statement run on `_CON` begins a transaction that stays open until something commits or
  rolls back. On a read-only connection nothing ever commits, so the transaction is open more or less
  permanently — which is the lock in the output below.

Run the demonstration:

```bash
cd days/day-39-database-tools/lab && uv run python hold.py
```

**Line by line:**

- Arm A opens, reads and closes per call, then runs a writer — the nightly archiver a real desk has.
- Arm B leaves a read transaction open, exactly as a held connection leaves one, and runs the same
  writer.
- Arm C runs the writer again after the held connection has let go, to show that nothing was broken.
- The writer uses `timeout=0.5`, so it waits half a second for the lock and then reports rather than
  hanging the script.
- Zero model calls, one file, two connections.

## When it breaks

Real output, on 2026-09-04:

```text
seeded archive.sqlite3: 5 tickets, 2 kb articles
A - nothing held between calls
  read_once     -> 5 tickets
  nightly_write -> wrote 1 row

B - one read transaction left open, exactly as a held connection leaves it
  held read     -> 5 tickets
  nightly_write -> OperationalError: database is locked

C - the same write, once the held connection has let go
  nightly_write -> wrote 1 row
```

The error in full:

```text
sqlite3.OperationalError: database is locked
```

Five words, and they are misleading in a specific way. Nothing is locked in the sense of being
protected. There is no lock file to delete, no permission to fix, and nothing wrong with the
database. Another connection in this same process is holding a read transaction, and the writer
waited its half second and gave up.

Three things make this hard to find in a real system.

**Arm A and Arm C are identical.** The write succeeds before the held connection exists and after it
lets go. Any test that does not have both a reader and a writer alive at once passes.

**The failure is on the writer.** The component that is doing something wrong — the tool holding a
connection — reports nothing at all. The error surfaces in the nightly job, which is correct, and
whose logs are read by somebody else.

**It is timing-dependent.** Lengthen the timeout and it succeeds; shorten it and it fails. Which
makes it exactly the kind of bug that is "fixed" by raising the timeout, converting a fast failure
into a slow one.

## In production

**What a professional writes instead:** a connection **pool**, on a server database. Nobody opens a
new TCP connection to Postgres per query — the handshake and authentication are genuinely expensive
— so a pool holds a small number open and lends one out for the duration of a call. The principle is
unchanged and that is the point: the *call* borrows a connection and returns it, and no connection is
associated with a caller between calls. On SQLite the pool is unnecessary because opening a local
file is cheap, so the same principle collapses to `connect` and `close`.

**What degrades at scale or under concurrency:** SQLite's one-writer rule. Many readers are fine;
one writer at a time is the ceiling, and every reader that holds a transaction extends how long the
writer waits. The standard mitigation is `PRAGMA journal_mode=WAL`, which lets readers continue
during a write and removes most of this — worth knowing, and worth knowing that it does not make
SQLite multi-writer.

**The failure mode that only appears with real traffic:** the connection leak. A tool without the
`finally` closes on the happy path and not on the error path. Error rates are low, so connections
leak slowly, and a week later a long-running server has hundreds of them and is failing on file
handles. The traceback names the resource limit, not the missing `finally`.

**The review comment a senior engineer leaves:** *"the connection is created at import and never
closed. That is a lock held for the life of the process, and it is why the nightly job started
failing with `database is locked` last week. Open it in the function and close it in a `finally`."*

**The interview question:** *"where do you open the database connection in an agent tool?"* *"Inside
the call, closed in a `finally`. Two reasons and they are separate. The architectural one is that
anything a server holds between requests is a reason it cannot be answered by any instance, which is
the whole point of a stateless MCP server. The concrete one is that on SQLite a held read connection
keeps a transaction open, and we watched a nightly writer fail with `database is locked` against a
tool that was doing nothing wrong and reported nothing at all — the error lands on the writer, so the
component at fault is silent. On a server database the answer looks different but is the same
principle: a pool, because the handshake really is expensive, and the call borrows a connection for
its duration and gives it back."*
