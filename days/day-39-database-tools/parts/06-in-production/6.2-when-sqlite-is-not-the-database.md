# 6.2 — When SQLite is not the database

## One-line answer

Moving the archive to a server database changes the connection helper and three of the five brakes,
and leaves every `SELECT` untouched — which is the whole practical payoff of having written
declarative queries against named relations instead of code that knows where the data sits.

## The story

The road to the new part of town used to be one lane each way with a ditch on both sides.

It worked for years. Then the flats went up and the traffic did not fit, so they widened it: four
lanes, a divider down the middle, proper drains, and a signal where there used to be a place where
you waited for a gap.

The route did not change. Same start, same end, same turning by the temple, same shops. If you had
written down directions for a friend ten years ago — *left at the temple, straight past the school,
right after the petrol pump* — those directions still work, because you wrote down the route and not
which part of the tarmac to drive on.

## The idea in plain language

Sooner or later the archive outgrows a file. The triggers are specific and they are not "it got big":

| Trigger | Why SQLite stops fitting |
| --- | --- |
| more than one machine reads it | a file is on one filesystem |
| concurrent writers | SQLite serialises writes; one at a time is the ceiling |
| a write that must not be lost | you want replication, and a file has none |
| separate credentials per client | SQLite has no users, so it has no `GRANT` |

When that day comes, the question is how much of today's work survives. The answer is: almost all of
it, and the parts that do not are the parts that were about the *storage* rather than about the
*questions*.

Here is the honest audit, tool by tool and brake by brake:

| Piece | Moving to Postgres |
| --- | --- |
| the `SELECT` statements | **unchanged** — `SELECT`, `WHERE`, `LIKE`, `LIMIT`, `substr` are all standard |
| the `?` placeholders | **spelling change** — `psycopg` uses `%s`, the concept is identical |
| the tool signatures and return shapes | **unchanged** |
| the docstrings | **unchanged** |
| `connect_readonly()` | **rewritten** — a connection string and a pool, not a file path |
| brake 1, parameter binding | unchanged in principle, new placeholder syntax |
| brake 2, `mode=ro` | **replaced** — a database role with `SELECT` granted and nothing else |
| brake 3, the authorizer | **replaced** — the same role; there is no authorizer callback |
| brake 4, `LIMIT` | unchanged |
| brake 5, the step budget | **replaced** — `statement_timeout` on the role, enforced by the server |

Three brakes move **into the database**, and every one of them is better there. A role is enforced by
a server your application cannot reconfigure; a `set_authorizer` call is enforced by a line of Python
that a refactor can delete. The migration is a security upgrade disguised as an operations task.

What does not survive is the assumption that a connection is free. Everything in
[6.1](6.1-the-connection-you-do-not-hold.md) about opening per call stays true as a *principle* and
changes as a *mechanism*: a TCP connection with authentication is genuinely expensive, so the call
borrows from a pool instead of opening its own.

And this is the point where [4.2](../04-toolbox-parked/4.2-who-writes-the-sql.md)'s decision expires.
On Postgres, MCP Toolbox for Databases is providing pooling, credentials handling and metrics that
you would otherwise write — the exact features that bought nothing against a local file. The decision
recorded today has a trigger written into it for that reason.

## Why Sutra needs it

Because [Day 47](../../../day-47-persistent-sessions/LESSON.md) points ADK's
`DatabaseSessionService` at a database URL, and
[Day 43](../../../day-43-stateless-by-default/LESSON.md) deploys a server where any instance answers
any request. "Any instance" and "one file on one filesystem" are in tension, and the day that tension
resolves is the day this part describes.

Writing down what survives *now*, while the archive is still a file, is what makes that migration a
task rather than a rewrite. A team that discovers at migration time that its tools were full of
SQLite-specific behaviour rewrites its tools; a team that wrote declarative queries changes a
connection helper.

## The paper behind it

> **A Relational Model of Data for Large Shared Data Banks** · `doi:10.1145/362384.362685` · 1970 ·
> `https://doi.org/10.1145/362384.362685`

It argued that programs should be protected from changes in how data is physically stored, by asking
questions about named relations rather than navigating a stored representation.

Everything in the table above is that argument being cashed in — the queries survive a change of
engine because they never described the storage. Read it after the parts:
[`../../papers/01-relational-model.md`](../../papers/01-relational-model.md).

## The mechanism

The whole migration, at the level of code, is one function. Today:

```python
def connect_readonly() -> sqlite3.Connection:
    """Open the archive so that no statement can change it."""
    con = sqlite3.connect(f"file:{ARCHIVE.as_posix()}?mode=ro", uri=True)
    con.set_authorizer(authorizer)
    return con
```

**Line by line:**

- The path, the mode and the authorizer are all here, in one place, which is what makes the next
  version a replacement rather than an edit spread over four modules.
- `mode=ro` and `set_authorizer` are the two brakes that will not exist on the other side. Both are
  in this function and nowhere else, so their disappearance is visible in one diff.
- The return type is `sqlite3.Connection`. Note that nothing outside this function should mention
  that type — a tool that annotates its parameters with it has made the storage engine part of its
  own signature.

After, in shape — and the field names here come from the driver, not from this document, so treat
them as the thing to verify:

```python
def connect_readonly():
    """Borrow a read-only connection from the pool."""
    return POOL.connection()
```

**Line by line:**

- `POOL` is created once, at startup, from a connection string held in the environment. The pool is a
  process-level object; the **connection** is still per call, which is
  [6.1](6.1-the-connection-you-do-not-hold.md)'s principle surviving the change of mechanism.
- There is no `mode=ro` and no authorizer, because the credentials in that connection string belong
  to a role that was granted `SELECT` on two tables. The brakes did not disappear; they moved to the
  server and stopped being your code's responsibility.
- The statement timeout is set on the role too, so brake 5 is gone from the application as well.
- **TODO(verify: read the connection-pool API of whichever Postgres driver is pinned at that time —
  `uv run python -c "import psycopg_pool; help(psycopg_pool.ConnectionPool)"` — before writing this
  function).** The shape above is the pattern, not a verified API, and no Postgres driver is
  installed in this repository today.

The queries, for comparison, need this much editing:

```sql
SELECT id, title, substr(body, 1, 160) FROM tickets
WHERE status = 'open' AND body LIKE ?
LIMIT ?
```

**Line by line:**

- `SELECT`, `FROM`, `WHERE`, `LIKE` and `LIMIT` are in the SQL standard and behave the same way.
- `substr` is standard too, though the standard spells it `SUBSTRING`; both Postgres and SQLite
  accept `substr`, which is the kind of detail worth checking rather than assuming.
- The `?` placeholders are the only thing that must change, to `%s` for `psycopg`. That is a
  find-and-replace, and it is the entire syntactic cost of the migration.
- What is *not* here is any mention of a file, a page, a row id or an order the rows happen to be
  stored in. That absence is the reason the rest of the line survives, and it is what the day's paper
  is about.

## When it breaks

**No Postgres is installed in this repository**, so this section describes the two failures rather
than quoting transcripts of them. An invented error string is worse than a missing one (Principle
10), and both of these are things you will meet on the day you actually migrate.

The migration's characteristic failure is not the SQL. It is the thing the SQL never said, and the
commonest one is **row order**. `SELECT id FROM tickets WHERE status = 'open' LIMIT 3` asks for three
open tickets and does not say which three. Two engines are each free to pick a different three, and
each is correct. What breaks is the test suite, which has been asserting for two years on whichever
three SQLite happened to return — so a query that is still right starts failing, and the failure
looks like a data bug rather than a missing clause. The fix is the `ORDER BY` that
[2.4](../02-the-five-brakes/2.4-a-ceiling-the-caller-cannot-raise.md) said to add, for exactly this
reason, on the day it did not seem to matter.

The second is the **placeholder**, and there are two versions of it. The loud version is a driver
that rejects `?` outright and raises about a parameter count mismatch — a good failure, on the first
call, in your own terminal. The quiet version is a `?` that survives inside a `LIKE` pattern as a
literal question mark, so the search compiles, runs, matches nothing and reports success. That is
why the placeholder change is done as one mechanical replacement across the whole file rather than
statement by statement: a partial migration is exactly the state in which the quiet version hides.

## In production

**What a professional writes instead:** the tools are written against a **repository layer** from the
start — a module whose functions take domain arguments and return domain dicts, and which is the only
code that knows what engine is underneath. The tools call that; the tools never import a driver. The
migration then touches one module, and it can be done behind a flag with both engines live.

**What degrades at scale or under concurrency:** what changes is which problems you have. SQLite's
ceiling is one writer; Postgres removes that and hands you connection limits, lock contention on hot
rows and replication lag instead. Replication lag is the one that surprises agent systems: a tool
writes, a second tool reads a replica, and the read does not see the write. Nothing in SQLite
prepares you for a store that is briefly inconsistent with itself.

**The failure mode that only appears with real traffic:** the pool size. It is set to a number that
was fine in testing, the traffic doubles, and every tool call waits for a connection. The symptom is
tool calls timing out with a healthy database and idle CPU, which sends people to look at the query.

**The review comment a senior engineer leaves:** *"these tools import `sqlite3` directly and annotate
with `sqlite3.Connection`. The day we move, that is not a connection helper change, it is every tool.
Put the driver behind one module."*

**The interview question:** *"you built on SQLite. What happens when you outgrow it?"* *"We wrote
down what survives before we needed to know. The `SELECT` statements, the tool signatures and the
docstrings are unchanged — they describe questions about named tables, not storage. The placeholder
spelling changes from `?` to `%s`. The connection helper is rewritten around a pool, because a TCP
connection with authentication is genuinely expensive where opening a local file is not. And three of
our five brakes move into the database and get better on the way: read-only becomes a role with
`SELECT` granted, the SQLite authorizer becomes the same role, and the step budget becomes
`statement_timeout`. Server-enforced beats application-enforced, because a role survives a refactor
that deletes a line of Python. The trap I would watch for is row order — `LIMIT` with no `ORDER BY`
is 'some of them', and two engines pick different ones, so tests that never asserted an order start
failing on a query that is still correct."*
