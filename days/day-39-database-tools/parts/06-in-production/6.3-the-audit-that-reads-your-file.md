# 6.3 — The audit that reads your file

## One-line answer

The day's eval opens `sutra_mcp/db_tools.py`, looks for each of the five brakes by its source shape,
and **parses** the file to prove no statement is built by string formatting — so it is red until you
write the tools and stays red for every brake you leave out.

## The story

There is a laminated card inside the lift with a date on it.

It lists what was checked — the ropes, the emergency brake, the alarm, the door sensor — and it is
signed, and there is a date next to the signature. Everybody who rides the lift has seen it and
nobody reads it, until one day the doors close on somebody's bag and does not spring back, and then
four people are looking at the card.

The date is the whole point of the card. The list of things checked was true on the day it was
signed. What the date tells you is whether anybody has looked since.

## The idea in plain language

Section 2 tested five brakes by attacking them. That test ran against `lab/brakes.py`, which is a
script written to have all five. It proves the brakes work. It proves nothing at all about the file
you are actually going to ship.

So the day needs a second check, pointed at `sutra_mcp/db_tools.py`, and it has to work by reading
that file rather than by running it — because at the moment you first run this check, the file does
not exist.

That constraint turns out to be a feature. A check that reads source can say *"this brake is not
present"* about a tool nobody has called yet, which is exactly the thing a reviewer cannot reliably
do and a runtime test cannot do at all.

There are two ways to read source, and this check uses both, for different questions:

**Pattern matching** answers "is this thing present?" — is there a `?` in an `execute` call, is there
a `mode=ro`, is there a `set_authorizer`. Presence is a question a regular expression can answer
honestly, because a false positive requires somebody to write the exact brake and not mean it.

**Parsing** answers "is this thing absent?" — is there anywhere in this file where SQL is built by
formatting. Absence is a question a regular expression cannot answer, because the word `SELECT`
appears in comments, in docstrings, in a variable name and in a log message. You have to look at the
program's structure, and Python's `ast` module hands you exactly that.

The rule underneath is worth stating on its own: **to check that something is there, search; to check
that something is nowhere, parse.**

## Why Sutra needs it

Because [Principle 11](../../../../docs/00_MASTER_PLAN.md) says every day ends with a check that can
go RED, and today's capability is a database tool. The check has to be about the brakes, or it is
checking the wrong thing.

Because [Day 45](../../../day-45-the-mcp-audit/LESSON.md) is the Phase 6 gate and audits every MCP
surface Sutra has built. A day that hands that audit an executable check has contributed something;
a day that hands it a paragraph has not.

And because of the failure mode [2.6](../02-the-five-brakes/2.6-which-brakes-actually-held.md) named:
brakes are added once and then quietly removed by a refactor that meant no harm. The connection
helper gets tidied, `uri=True` is dropped, and every brake below it is gone with nothing failing. A
check that reads the file catches that on the next run.

## The mechanism

The presence half is a table of patterns, and the table **is** the specification:

```python
BRAKES = [
    ("parameter binding", re.compile(r"execute\(\s*[\"'][^\"']*\?")),
    ("read-only connection", re.compile(r"mode=ro")),
    ("authorizer allowlist", re.compile(r"set_authorizer")),
    ("a LIMIT the caller cannot remove", re.compile(r"LIMIT\s+\?")),
    ("a step budget or timeout", re.compile(r"set_progress_handler|interrupt\(")),
]
```

**Line by line:**

- Each entry is a human-readable name and the shape that proves it. The name is what prints when it
  is missing, so it has to say what to do rather than what is wrong — *"a LIMIT the caller cannot
  remove"* is an instruction; *"limit check failed"* is not.
- `execute\(\s*["'][^"']*\?` looks for an `execute` call whose first argument is a string literal
  containing a `?`. It deliberately requires the **literal**: a variable passed to `execute` might be
  a bound statement or might be a formatted one, and this check will not vouch for what it cannot see.
- `mode=ro` and `set_authorizer` are literal substrings, because there is exactly one way to spell
  each and a looser pattern would only add false positives.
- `LIMIT\s+\?` requires the placeholder after `LIMIT`, so a hard-coded `LIMIT 5` does not satisfy it.
  That is a judgement call worth defending: a constant limit is genuinely safe, and requiring the
  bound form pushes toward the clamped version from
  [2.4](../02-the-five-brakes/2.4-a-ceiling-the-caller-cannot-raise.md) that can also report
  truncation.
- The fifth accepts either `set_progress_handler` or a call to `interrupt(`, because
  [2.5](../02-the-five-brakes/2.5-the-query-that-never-ends.md) showed those are two legitimate ways
  to bound work.
- Every one of these is a check for **presence**, and every one of them can be satisfied by a brake
  that is present and wrong. The check is a floor, not a proof, and saying so is part of shipping it.

The absence half needs the parser:

```python
SQL_WORDS = re.compile(r"\b(select|insert|update|delete|drop|attach)\b", re.I)


def formatted_sql(tree: ast.AST) -> list[int]:
    """Line numbers where SQL-looking text is built by formatting."""
    hits = []
    for node in ast.walk(tree):
        if isinstance(node, ast.JoinedStr):
            text = "".join(p.value for p in node.values if isinstance(p, ast.Constant))
            if SQL_WORDS.search(text):
                hits.append(node.lineno)
        elif isinstance(node, ast.BinOp) and isinstance(node.op, (ast.Add, ast.Mod)):
            left = node.left
            if isinstance(left, ast.Constant) and isinstance(left.value, str):
                if SQL_WORDS.search(left.value):
                    hits.append(node.lineno)
    return hits
```

**Line by line:**

- `ast.walk(tree)` visits every node in the parsed program. Comments and docstrings are not nodes in
  the way that matters here — a comment is discarded by the parser entirely — which is precisely why
  parsing beats grepping for this question.
- `ast.JoinedStr` is the node type for an **f-string**. Its `values` alternate between literal pieces
  (`ast.Constant`) and the expressions interpolated into it.
- `"".join(p.value for p in node.values if isinstance(p, ast.Constant))` reassembles only the literal
  halves. That is deliberate: `f"SELECT ... {term}"` is caught by the word `SELECT` in the literal
  part, and the variable's name is irrelevant.
- `ast.BinOp` with `ast.Add` catches `"SELECT ..." + term`, and with `ast.Mod` catches
  `"SELECT ... %s" % term`. Three ways to build a string, three node shapes, one check.
- Only `node.left` is examined, because a SQL statement built by concatenation starts with the
  literal. `term + "..."` is a different and much rarer shape and is honestly not covered — worth
  knowing, and a reasonable `TODO(me)`.
- `SQL_WORDS` with `\b` on both sides avoids matching `select` inside `selected`, and `re.I` catches
  the lower-case spelling people use in f-strings.
- The return is **line numbers**, not a boolean. A check that says "there is formatted SQL somewhere
  in this file" is a check you cannot act on.

Run it:

```bash
cd days/day-39-database-tools/lab && uv run python brake_audit.py; echo "exit: $?"
```

**Line by line:**

- The script resolves the repository root from its own location and looks for
  `sutra_mcp/db_tools.py`. It does not import that module — importing it would run it, and the point
  is to check a file that may not be importable yet.
- The exit code is 1 when there are findings and 0 when there are none, so this is a test rather than
  a report and can be wired into `./m check` later.
- Zero model calls, zero network, one file read.

## When it breaks

It is red today. Real output, on 2026-09-04, before `sutra_mcp/db_tools.py` exists:

```text
  - sutra_mcp/db_tools.py does not exist yet
  - brake missing: parameter binding
  - brake missing: read-only connection
  - brake missing: authorizer allowlist
  - brake missing: a LIMIT the caller cannot remove
  - brake missing: a step budget or timeout
findings: 6
exit: 1
```

Six findings and exit 1, which is what an eval that can fail looks like before the work is done. Each
line is a thing to go and write. When the file exists with all five brakes it goes to `findings: 0`
and `exit: 0`, and the day's build brief is complete.

Then break it on purpose, which is the more instructive run. Replace one bound statement with an
f-string and the check finds it by line:

```text
  - SQL built by formatting at line 16
findings: 1
exit: 1
```

That finding survives a comment saying `# safe, term is validated`, because the comment is not in the
parse tree. It also survives the variable being renamed, the string being split across lines, and the
statement being lower-case.

And here is the limit of it, stated rather than hidden. This passes the audit:

```python
sql = "SELECT id FROM tickets WHERE id = ?"
con.execute(sql % term)
```

The literal has a `?`. The formatting happens on a variable whose value the parser cannot know, and
`node.left` is a `Name`, not a `Constant`. **The check does not catch it.** A source check is a floor
under review, not a replacement for it, and the honest way to ship one is with its blind spot written
next to it.

## In production

**What a professional writes instead:** this check as a linter rule rather than a bespoke script.
Established Python security linters already carry a rule for string-built SQL, and using one buys
maintenance and a much larger pattern set. The bespoke version earns its place for the brakes that
are **specific to this codebase** — `mode=ro`, our authorizer, our `LIMIT ?` convention — which no
general linter knows about. The split is: generic rules from a tool, house rules from a script.

**What degrades at scale:** the pattern list rots. Somebody legitimately introduces a second
connection helper, or a query builder, and the patterns stop matching code that is perfectly correct.
The check then fails on good code, someone adds an exception, and the exceptions accumulate until the
check means nothing. The countermeasure is that a check like this is scoped to **one file** by name,
not to a package.

**The failure mode that only appears with real traffic:** the check passes on a file where all five
brakes are present and one of them is dead — an authorizer installed on a connection that is never
used, a `LIMIT ?` bound to a value that came from the caller unclamped. Presence is not correctness,
which is why [2.6](../02-the-five-brakes/2.6-which-brakes-actually-held.md) attacks the brakes and
this check only counts them. **Both, or neither is worth much.**

**The review comment a senior engineer leaves:** *"this greps for `SELECT` to find formatted SQL. Our
docstrings contain the word `SELECT` and so does the comment three lines above. Parse it — an `ast`
walk over `JoinedStr` and `BinOp` is fifteen lines and does not have opinions about comments."*

**The interview question:** *"how do you stop a security rule from quietly disappearing from a
codebase?"* *"Make it a check that fails, and point the check at the file rather than at the running
system. Ours reads `db_tools.py` and looks for five brakes by their source shape, and it goes red for
each one that is missing — including when the file does not exist yet, which is how it stayed useful
as a to-do list. The part I would call out is that presence and absence need different tools:
searching is fine for 'is the read-only connection here', but 'is there any formatted SQL anywhere'
cannot be grepped, because `SELECT` appears in comments and docstrings and variable names. That one
is a fifteen-line `ast` walk over f-string and binary-operator nodes, which the parser has already
stripped comments out of. And I ship it with its blind spot written down — it cannot see formatting
applied to a variable — because a check whose limits are not stated gets trusted past them."*
