# 1.1 — The numbers on the back of a bill

## One-line answer

Sutra's ticket archive has been a Python dictionary since Day 3, and a dictionary stops being an
archive the moment somebody else needs to write to it, the moment it outgrows one screen, and the
moment losing the process means losing the data.

## The story

You wrote a plumber's number on the back of an old electricity bill.

It worked. When the tap dripped again you found the bill, found the number, and called. So the next
useful number went on the same bill. Then the gas man, then the school van driver, then the person
who fixes the inverter, squeezed sideways up the margin because the flat part was full.

Then three things happened in one month.

Your sister needed the van driver's number and you were not at home, so you read it out over the
phone and she wrote it on her own bill. The plumber changed his number, and you corrected it on your
copy, and nobody corrected hers. And somebody cleared the drawer.

Nothing here was carelessness. Every single number was written down correctly, by a careful person,
at the moment it mattered. The bill failed for three reasons that have nothing to do with the
numbers on it: only one person could reach it, there was no way to change one entry everywhere at
once, and it lived exactly one accident away from being gone.

## The idea in plain language

A **dictionary**, in Python, is a lookup table held in memory: you give it a key, it gives you a
value. `TICKETS["4521"]` returns the text of ticket 4521. It is fast, it is obvious, and it is what
[Day 4](../../../day-04-tools-by-hand/LESSON.md) used when the point being taught was how a tool
call works rather than where the data lives.

A **database** is a store that outlives the program reading it. The facts sit in a file (or on a
server), several programs can read them at once, one of them can change a fact and everybody else
sees the change, and a crash loses nothing that was already written down.

The difference is not size. You can put ten thousand tickets in a dictionary and it will work. The
difference is the three properties the bill did not have:

| Property | The dictionary | A database |
| --- | --- | --- |
| **Shared** | one process, one copy | many readers at once, one copy of the truth |
| **Durable** | gone when the process exits | on disk, survives the crash |
| **Updatable in place** | edit `loop.py`, restart, redeploy | one statement, everybody sees it |

There is a fourth difference that matters more than any of them and is easy to miss. A dictionary
can only be read the way you wrote it. `TICKETS["4521"]` works; *"every open ticket about logging
out, newest first"* does not, unless you write the loop that does it. A database answers questions
you did not anticipate, because the questions are written in a language of their own —
[1.2](1.2-one-file-one-engine.md) is where you meet it.

And that fourth difference is where today's real subject appears. A store that answers questions you
did not anticipate will also answer questions you did not **want** answered. That is the whole of
sections 2 and 5.

## Why Sutra needs it

Because `sutra_mcp` currently serves a lie.

[Day 34](../../../day-34-building-sutra-mcp-tools/LESSON.md) put `lookup_ticket` and `search_kb` on
the wire as MCP tools. Any client can call them. The tool descriptions say "the ticket archive". The
archive is five entries in a Python file, and the only way to add a ticket is to edit source code,
commit it, and redeploy the server. A support desk that cannot take a new ticket without a `git
push` is not a support desk.

Today the archive becomes a real one, and today is also the day the tool that reads it grows brakes.
The order matters: [Day 40](../../../day-40-filtering-and-allowlists/LESSON.md) builds the general
machinery for filtering tools, and [Day 47](../../../day-47-persistent-sessions/LESSON.md) puts
sessions in a database too. Both of them assume the archive already moved.

## The mechanism

Here is the shape the dictionary has today, and the shape it takes tomorrow, side by side. First,
what Day 3 wrote:

```python
TICKETS = {
    "4521": "I keep getting logged out of the dashboard every few minutes.",
    "4522": "Exporting my project as CSV gives an empty file.",
}


def lookup_ticket(ticket_id: str) -> dict:
    """Return one ticket by id."""
    body = TICKETS.get(ticket_id)
    if body is None:
        return {"status": "not_found", "message": f"No ticket with id {ticket_id!r}."}
    return {"status": "ok", "body": body}
```

**Line by line:**

- `TICKETS` is a module-level dict, so it is built once when Python imports the module and lives for
  the lifetime of the process. Two server instances have two copies, and neither knows about the
  other's edits — which is exactly the sister with her own electricity bill.
- The key is the ticket id as a string. There is no other way in. There is no index on the body
  text, because there is no index at all; a search means looping over every value yourself.
- `TICKETS.get(ticket_id)` returns `None` for a miss rather than raising `KeyError`. That choice is
  Day 21's rule showing up early: a ticket that does not exist is **data**, not an exception.
- The return is a dict with a `status` key. That shape is the tool contract every later day depends
  on, and it does **not** change today. Only the storage under it does.

Now the same two facts as a table:

```sql
CREATE TABLE tickets (
    id        TEXT PRIMARY KEY,
    title     TEXT NOT NULL,
    body      TEXT NOT NULL,
    status    TEXT NOT NULL,
    opened_on TEXT NOT NULL
);
```

**Line by line:**

- `CREATE TABLE tickets` names a **relation**: a set of rows that all have the same named fields. The
  name is how every later statement refers to it, and it is a name, not a file position — a
  distinction that turns out to be the whole subject of the day's paper.
- `id TEXT PRIMARY KEY` says two things at once. The values are text, and no two rows may share one,
  so the engine will refuse a duplicate insert rather than silently overwriting the way
  `TICKETS["4521"] = ...` does.
- `title` and `body` are separated, where the dict crammed both into one string with a `Title:`
  prefix. Once they are separate columns you can search one without the other, and you can return a
  title without paying for a body — which [5.1](../05-failure-lab/5.1-forty-thousand-rows.md) turns
  out to care about a great deal.
- `status` and `opened_on` are columns the dict never had. They are not decoration: `status` is what
  makes *"only open tickets"* expressible, and `opened_on` is what makes *"since August"*
  expressible. The dict could hold these facts only by pasting them into the body text, where
  nothing can filter on them.
- `NOT NULL` on four columns is a rule the **engine** enforces on every future insert, by anybody,
  forever. A dict has no equivalent. This is the first appearance of today's real theme: a rule the
  storage enforces beats a rule your code remembers.

## When it breaks

The dictionary does not break loudly. It breaks by being edited, which is worse. Here is the
smallest version of it, and it is a real thing people do:

```text
>>> from sutra.loop import TICKETS
>>> TICKETS["4521"] = "resolved: user switched to https"
>>> lookup_ticket("4521")
{'status': 'ok', 'body': 'resolved: user switched to https'}
```

No error. The archive changed, the change is in memory only, and the next process to start reads the
old text from `loop.py` as if nothing had happened. Two workers now disagree about ticket 4521 and
neither can tell.

The loud version arrives when you restart:

```text
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
KeyError: '4610'
```

`4610` is a ticket that a colleague added on their machine. It is in their copy of `loop.py` and not
in yours, because "adding a ticket" and "editing source code" were the same action.

## In production

**What a professional writes instead:** nothing like either of these. A production ticket store is a
database with a schema in version control, migrations applied by a tool, and application code that
never contains the data itself. The literal test is whether adding a row requires a deployment. If it
does, the store is source code wearing a data hat.

**What degrades at scale:** the dictionary degrades at the second reader, not at the millionth row.
One process with a 200 MB dict of tickets is a memory number you can afford; two processes that must
agree about the contents is a problem no amount of memory solves. This is the same shape as
[Day 32's](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md)
held session: state that lives inside one process is state that pins you to one process.

**The failure mode that only appears with real traffic:** a dict-backed store looks perfect in tests
because tests run one process and start clean. The bug appears the first afternoon two instances are
up and a customer sees a stale ticket from whichever one answered — and it is unreproducible on the
laptop, forever.

**The review comment a senior engineer leaves:** *"the seed data and the application are the same
artefact here. Anyone who wants to add a ticket has to open a pull request against `loop.py`. Move
the rows into a store and leave the module holding code."*

**The interview question:** *"when do you move from an in-memory structure to a database?"* Answer
honestly, and do not say "when it gets big": *"Size is the last reason, not the first. I move when a
second reader appears, because that is when 'the data' stops being one process's private variable
and starts needing one copy of the truth. I move when losing the process would lose a write. And I
move when people start asking questions I did not write a function for — a dict answers exactly the
lookups you coded, a query language answers the ones you did not think of. In our case all three
landed at once: two server instances, tickets arriving faster than deployments, and a support desk
that wanted 'open tickets about logging out since August', which is one line of SQL and a
hand-written loop otherwise."*
