# 1.2 — One file, one engine

## One-line answer

SQLite is a complete SQL engine that ships inside Python's standard library and stores an entire
database in one ordinary file, so Sutra gets a real query language, real constraints and real
transactions without installing anything, running a server, or opening a billing account.

## The story

The tea stall at the end of the street runs on a portable gas stove.

It is a small steel thing with two burners and its own cylinder underneath, and it goes in the back
of a van at night. There is no gas pipeline to the pavement. There is no meter, no connection
charge, and nobody had to come and fit anything.

What it burns is the same gas the big hotel kitchen burns. The flame does the same thing to water
that a fitted range does. A cook who learned on this stove can walk into that kitchen and cook,
because the skill is heat and timing, not plumbing.

The stall owner is not making do with a toy. He is running the real thing, at the size he needs, in
a form that fits in a van.

## The idea in plain language

**SQL** — you can say the letters, or say "sequel"; both are normal — is a language for asking a
database questions. You do not tell it how to find the answer. You describe the answer you want, and
the engine works out how to get it. That is why it is called a **declarative** language: you declare
what, not how.

**SQLite** is one particular SQL engine. Three facts about it are the whole reason it is the right
choice here.

**It is a library, not a server.** Postgres and MySQL are programs you start, which listen on a
port, which your program then connects to over a network. SQLite is code that runs inside your
process. There is nothing to start and nothing to connect to. "Opening the database" means opening a
file.

**The database is one file.** `sutra/data/tickets.sqlite3` is the tables, the indexes, the schema and
the data. Copy the file, you copied the database. Delete the file, the database is gone. This is a
property with a sharp edge, and [2.2](../02-the-five-brakes/2.2-the-connection-that-cannot-write.md)
is where the edge shows.

**It is already installed.** `import sqlite3` works in a bare Python 3.12 with no packages at all,
because the driver and the engine ship with the standard library. No `uv add`, no version pin, no
row in `docs/PACKAGES.md`, and — the point that matters under
[Addendum 02](../../../../docs/02_ADDENDUM_ZERO_BUDGET_MODELS.md) — no managed cloud database and no
billing account.

What SQLite is not is a toy version of SQL. It has transactions, foreign keys, indexes, views,
triggers and a query planner. The parts of it this day uses — `SELECT`, `WHERE`, bound parameters,
`LIMIT`, views — are spelled and behave the same way in Postgres. That is
[6.2](../06-in-production/6.2-when-sqlite-is-not-the-database.md)'s subject and it is the reason
learning on this stove transfers.

## Why Sutra needs it

Because the zero-budget rule is not a limitation to be worked around today; it is the reason today
is buildable at all.

Every other honest way to teach "a production data source behind MCP" needs a database you can
reach, which needs either a server on your machine or an account with a card behind it. SQLite
removes the choice: the archive is a file in the repository's `sutra/data/` directory, generated by a
script, ignored by git, and identical on every machine that runs the script.

It also keeps the comparison in section 4 fair. The MCP Toolbox for Databases speaks SQLite, so the
hand-written tools and the generated ones can be pointed at **the same file** and judged on what they
expose rather than on what they connect to.

## The paper behind it

> **A Relational Model of Data for Large Shared Data Banks** · `doi:10.1145/362384.362685` · 1970 ·
> `https://doi.org/10.1145/362384.362685`

It argued that a user of a data bank should be shielded from knowing how the data is physically
arranged, by presenting every fact as a **relation** — a named table of named columns — and letting
questions be asked about relations rather than about storage.

The `CREATE TABLE` you just read and the `SELECT` below are that proposal, fifty-six years on.
Read it after the parts: [`../../papers/01-relational-model.md`](../../papers/01-relational-model.md).

## The mechanism

Everything SQLite needs from you is a path and a statement. Here is the whole of "open the archive
and ask it something":

```python
import sqlite3

con = sqlite3.connect("sutra/data/tickets.sqlite3")
rows = con.execute(
    "SELECT id, title FROM tickets WHERE status = ? ORDER BY opened_on DESC LIMIT ?",
    ("open", 3),
).fetchall()
con.close()
```

**Line by line:**

- `import sqlite3` pulls in the standard library module. There is no package to install and no
  version to pin, which is why this day adds no row to `docs/PACKAGES.md`.
- `sqlite3.connect(path)` opens the file, and **creates it if it does not exist** — a convenience
  that is also a trap, because a typo in the path gives you a working connection to a brand new empty
  database rather than an error. [1.3](1.3-a-door-not-a-hallway.md) closes that door deliberately.
- `con.execute(sql, params)` compiles the statement and runs it. It returns a **cursor**, which is a
  handle you pull rows out of, not the rows themselves.
- The `?` marks in the SQL are **placeholders**. The tuple `("open", 3)` supplies their values, in
  order. The values travel beside the statement and are never part of its text. That single design
  decision is the subject of [2.1](../02-the-five-brakes/2.1-the-argument-that-became-syntax.md), and
  it is the most important line in this block.
- `ORDER BY opened_on DESC` sorts newest first. Note what is absent: you did not write a sort, and
  you did not say how to find the matching rows. You described the answer.
- `LIMIT ?` caps how many rows come back. Bound, like everything else, so the cap is a value the
  server chooses rather than text a caller could rewrite —
  [2.4](../02-the-five-brakes/2.4-a-ceiling-the-caller-cannot-raise.md).
- `.fetchall()` drains the cursor into a list of tuples. For five rows that is fine. For forty
  thousand it is the mistake [5.1](../05-failure-lab/5.1-forty-thousand-rows.md) measures.
- `con.close()` releases the file handle. Leaving it open is not free —
  [6.1](../06-in-production/6.1-the-connection-you-do-not-hold.md) shows exactly what it costs
  somebody else.

The archive Sutra builds has two tables, and the script that builds it is the day's first lab file:

```python
SCHEMA = """
CREATE TABLE tickets (
    id        TEXT PRIMARY KEY,
    title     TEXT NOT NULL,
    body      TEXT NOT NULL,
    status    TEXT NOT NULL,
    opened_on TEXT NOT NULL
);
CREATE TABLE kb (
    id    TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    body  TEXT NOT NULL
);
"""


def seed(path, flood: int = 0):
    """Rebuild the archive from scratch; add `flood` synthetic rows on top."""
    path.unlink(missing_ok=True)
    con = sqlite3.connect(path)
    try:
        con.executescript(SCHEMA)
        con.executemany("INSERT INTO tickets VALUES (?, ?, ?, ?, ?)", SEED)
        con.commit()
    finally:
        con.close()
    return path
```

**Line by line:**

- `SCHEMA` is two `CREATE TABLE` statements in one string, which is why it needs `executescript`
  rather than `execute`: `execute` compiles **one** statement and refuses more, a restriction that
  turns out to be a free brake in [2.1](../02-the-five-brakes/2.1-the-argument-that-became-syntax.md).
- `path.unlink(missing_ok=True)` deletes the file first, so re-running the seed rebuilds rather than
  duplicating. `missing_ok=True` means the first run does not fail on a file that was never there.
- `flood` exists so [5.1](../05-failure-lab/5.1-forty-thousand-rows.md) can ask for forty thousand
  rows without a second script. A test corpus you can resize is worth more than a fixed one.
- `executemany` runs the same statement once per row of the sequence. It compiles the SQL once, which
  is why it is much faster than a loop of `execute` calls, and it uses the same `?` placeholders, so
  a ticket body containing an apostrophe cannot break anything.
- `con.commit()` makes the writes permanent. Without it, the `finally` closes the connection and
  SQLite rolls the whole thing back — you get a valid, empty, correctly-shaped archive and no error
  message at all.
- `try/finally` closes the file even when a statement raises. A leaked handle on Windows is a file
  you cannot delete on the next run.

## When it breaks

The commonest SQLite failure is not a crash. It is `connect()` cheerfully creating the wrong file:

```text
>>> con = sqlite3.connect("sutra/data/ticket.sqlite3")   # note the missing 's'
>>> con.execute("SELECT COUNT(*) FROM tickets").fetchone()
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
sqlite3.OperationalError: no such table: tickets
```

Read that message carefully, because it misdirects. It says *no such table*, and the instinct is to
go and look at the schema. The schema is fine. The **file** is new and empty, because `connect` made
it on the spot. The fix is to open read-only, where a missing file is an error instead of an
invitation — which is one of the reasons
[2.2](../02-the-five-brakes/2.2-the-connection-that-cannot-write.md) exists.

The second is the missing commit, and it has no error text at all:

```text
seeded archive.sqlite3: 0 tickets, 0 kb articles
```

Zero rows, exit code 0, nothing in the log. The transaction was open when `close()` ran, so SQLite
did what a database is supposed to do with an uncommitted transaction and threw it away.

## In production

**What a professional writes instead:** a connection helper that takes the path from configuration
rather than a literal, opens with a URI so the mode is explicit, and is the only place in the
codebase that calls `sqlite3.connect`. One function, one place to add the brakes to.

**What degrades at scale or under concurrency:** SQLite allows many readers at once but only one
writer at a time, and by default a writer takes a lock on the whole file rather than on a row. On a
read-mostly archive that is invisible. Add a nightly job that writes while the desk reads and you
meet `database is locked` — measured, with the real text, in
[6.1](../06-in-production/6.1-the-connection-you-do-not-hold.md). The usual first fix is
write-ahead logging (`PRAGMA journal_mode=WAL`), which lets readers continue during a write; the
usual second fix is that you have outgrown SQLite, which is
[6.2](../06-in-production/6.2-when-sqlite-is-not-the-database.md).

**The failure mode that only appears with real traffic:** a file-backed database on a network share
or a container volume that is remounted. SQLite's locking depends on the filesystem honouring locks,
and some do not. It works for months and corrupts on the day the storage layer changes underneath it.

**The review comment a senior engineer leaves:** *"`sqlite3.connect` appears in four modules. Each
one will grow its own idea of read-only, its own timeout and its own idea of where the file is. Give
it one function and make every caller go through it."*

**The interview question:** *"why SQLite and not Postgres?"* *"Because for a single-writer,
read-mostly archive the operational cost of Postgres buys nothing. SQLite is the same SQL, in
process, in one file — no server, no port, no credentials, no cloud bill, and the driver is in the
standard library. The honest limits are that it is one writer at a time and it lives on one
filesystem, so the day we need concurrent writes or more than one machine reading, we move. The
migration is cheap precisely because we kept the tools declarative: the SQL our tools send is
standard, so what changes is the connection helper, not the queries."*
