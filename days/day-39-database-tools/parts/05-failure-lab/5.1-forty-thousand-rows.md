# 5.1 — 💥 Forty thousand rows

## One-line answer

A correct, safe, injection-proof, read-only query with no `LIMIT` returned a result **173% the size
of the model's entire input window**, which means the tool worked perfectly and the request could not
be sent.

## The story

You ask the tanker driver for water because the tap has been dry for two days.

You have a bucket. He has a tanker, and a hose the width of your arm, and he is doing exactly what
you asked — the tanker is full and the water is clean and he is not overcharging you. He puts the
hose in the bucket and opens the valve.

The bucket is full in about a second. Then the water is on the floor, and in the corridor, and going
down the stairs, and you are shouting and he cannot hear you over the pump.

Nothing was wrong with the water. Nothing was wrong with the tanker. What was missing was any
agreement about **how much**, and neither of you thought to mention it, because you were thinking
about a bucket and he was thinking about a tanker.

## The idea in plain language

A model has an **input window**: a maximum number of tokens it can be sent in one request. A token is
roughly a few characters of English — [Day 2](../../../day-02-llm-mechanics/LESSON.md) measured the
real ratio for this repository's model. Everything goes in that window: the system instruction, the
tool declarations, the conversation so far, and **every tool result**.

Which means a tool result is not "data returned to your program". It is text that will be pasted into
the next request, and it has to fit.

The gap that catches people is that nothing warns you. A database query returning forty thousand rows
is a perfectly ordinary database query. It completes, it is fast, it is correct, the connection was
read-only and the parameters were bound. Every brake in section 2 except one held. The result is
still unusable, because a support desk archive of a size any real desk would have does not fit inside
a sentence.

Three things make the number worse than people expect:

- **Rows are not the cost; bytes are.** Forty thousand ticket ids would be small. Forty thousand
  ticket *bodies* is not.
- **JSON is not free.** Serialising rows into `{"id": ..., "title": ..., "body": ...}` adds the key
  names again on every single row.
- **The model reads all of it.** Even where it fits, the middle of a very long context is where
  attention is worst — the effect
  [Day 19](../../../day-19-context-engineering-selection/LESSON.md) taught. A result that fits is not
  the same as a result that works.

## Why Sutra needs it

Because until today Sutra's archive had five entries, and every tool in it has been returning
everything it found. That was correct and it was correct only because the archive was a toy.

A support desk that has been running for two years has a hundred thousand tickets. The word "login"
appears in a great many of them. `search_tickets("login")` is the most obvious question anybody will
ever ask this system, and it is the query that ends the conversation.

This is also the part that makes [2.4](../02-the-five-brakes/2.4-a-ceiling-the-caller-cannot-raise.md)
concrete rather than sensible-sounding. The ceiling is not tidiness. It is the difference between a
tool that answers and a tool that cannot be called.

## The mechanism

Measure it rather than reasoning about it. The lab seeds forty thousand extra tickets and runs the
same query with four different ceilings:

```python
CHARS_PER_TOKEN = 4  # rough for English prose; Day 2 measured the real ratio
CONTEXT = 1_000_000  # gemini-3.7-flash input window
TERM = "%log%"

con = sqlite3.connect(f"file:{ARCHIVE.name}?mode=ro", uri=True)
for limit in (None, 200, 20, 5):
    sql = "SELECT id, title, body FROM tickets WHERE body LIKE ?"
    args: tuple = (TERM,)
    if limit is not None:
        sql += " LIMIT ?"
        args = (TERM, limit)
    rows = con.execute(sql, args).fetchall()
    payload = json.dumps([dict(zip(("id", "title", "body"), r)) for r in rows])
    tokens = len(payload) // CHARS_PER_TOKEN
    share = 100 * tokens / CONTEXT
```

**Line by line:**

- `CHARS_PER_TOKEN = 4` is an approximation and is labelled as one. It is right within a factor that
  does not matter here: the answer is 173%, and being wrong by 30% would still make it impossible.
- `CONTEXT = 1_000_000` is the input window of `gemini-3.7-flash`, the model this repository pins.
  The percentage is against that number, so a different model gives a different percentage and the
  same conclusion.
- `limit=None` is the arm with no ceiling at all — the tool as it would be written by somebody who
  had not thought about this. The other three are ceilings a reasonable person might pick.
- The SQL is built by **appending a clause**, not by formatting a value: `sql += " LIMIT ?"` adds
  fixed text and the number is still bound. That distinction is
  [2.1](../02-the-five-brakes/2.1-the-argument-that-became-syntax.md)'s, and it is worth seeing that
  varying the *shape* of a statement is fine while varying its *values* by formatting is not.
- `json.dumps(...)` is the honest measurement, because JSON is what actually crosses to the model. A
  count of rows or a `sys.getsizeof` on the list would both understate it.
- `dict(zip(...))` builds `{"id": ..., "title": ..., "body": ...}` per row. Those three key names are
  repeated forty thousand times, and that repetition is a real part of the number.
- `.fetchall()` materialises every row in Python before anything is measured. On the unbounded arm
  that is the whole table in memory — the cost you paid before you found out you could not use it.

Then the fix that costs nothing, in the engine:

```sql
SELECT id, title, substr(body, 1, 120) FROM tickets WHERE body LIKE ? LIMIT ?
```

**Line by line:**

- `substr(body, 1, 120)` takes the first 120 characters of the body. SQLite's `substr` is 1-indexed,
  so the first argument is `1` and not `0`.
- Doing it in SQL rather than in Python means the full body never leaves the engine. On five rows
  that is irrelevant; the habit is what matters, because the same tool will one day run without the
  `LIMIT` while somebody debugs something.
- `LIMIT ?` after the `WHERE` caps the row count, and the two together cap rows **and** bytes — the
  pair [2.4](../02-the-five-brakes/2.4-a-ceiling-the-caller-cannot-raise.md) argued for.
- What this does not do is tell the caller it happened. That is what the `truncated` flag is for, and
  it is why the fix is three things and not one.

Run it:

```bash
cd days/day-39-database-tools/lab && uv run python flood.py
```

**Line by line:**

- Seeding forty thousand rows takes a moment and is done once, at the top of the script.
- Zero model calls. Nothing here sends anything anywhere; it counts characters. That is the point —
  you can measure a context overflow without spending a request on it.

## When it breaks

Real output, run on 2026-09-04:

```text
seeded archive.sqlite3: 40005 tickets, 2 kb articles
no LIMIT  ->  40001 rows,   6920156 chars, ~1730039 tokens, 173.0% of the window
LIMIT 200 ->    200 rows,     34583 chars, ~   8645 tokens,   0.9% of the window
LIMIT 20  ->     20 rows,      3443 chars, ~    860 tokens,   0.1% of the window
LIMIT 5   ->      5 rows,       848 chars, ~    212 tokens,   0.0% of the window
+ snippet ->      5 rows,       863 chars, ~    215 tokens
```

**173.0% of the window.** Not slow. Not expensive. Impossible — the request cannot be constructed at
all.

And note where the failure will be reported. Nothing above raised. SQLite returned forty thousand
rows without complaint, the tool serialised them and answered `status: ok`, and the thing that breaks
is the **next model call**, one layer away, with a provider error about token counts rather than
anything mentioning a query. That distance is why this takes an evening to diagnose the first time:
the traceback points at the generation, and the component that misbehaved reported success.

Now read the rest of the table, because the interesting result is not the first row.

`LIMIT 200` is **0.9%** of the window. Two hundred rows — a generous answer by any standard — costs
under one percent. The ceiling did not cost you the ability to answer questions; the missing ceiling
cost you the ability to ask them.

`LIMIT 5` is 848 characters. And the snippet row is the one worth staring at: `+ snippet` is 863
characters for the same five rows, which is **fifteen characters more**, because the bodies in this
synthetic corpus are already short. On a real archive with 40 KB bodies that row would be the
difference between 848 characters and 200 000. The snippet is insurance whose premium is zero.

## In production

**What a professional writes instead:** a ceiling on rows, a ceiling on characters per field, an
explicit `truncated` flag, and a hard cap on the serialised payload size checked **after**
serialisation — because the first three can all be satisfied and still produce something too big
when one field is a stack trace somebody pasted into a ticket. The last check is a `len(payload)`
and a refusal, and it is the one that saves you from the case nobody predicted.

**What degrades at scale:** the archive does, silently, from underneath. The tool is written when
the table has ten thousand rows and `LIMIT 200` is comfortable. Nobody edits the tool. Two years
later the same search matches ten times as many rows and the `LIMIT` still holds — but the *work* to
find them has grown tenfold, which is [2.5](../02-the-five-brakes/2.5-the-query-that-never-ends.md)'s
brake, not this one. Ceilings on output do not age; ceilings on work do.

**The failure mode that only appears with real traffic:** one enormous row. A customer pastes a
100 000-line log file into a ticket. Your `LIMIT 5` is perfectly satisfied and one of the five rows
is 4 MB. Row caps are not byte caps, and the day this happens is the day somebody adds `substr`.

**The review comment a senior engineer leaves:** *"this returns every matching row. On my machine
that is four. On production it is forty thousand, and the failure will be a 400 from the model API
that names a token count, three layers away from this line. Cap it, trim the body in SQL, and return
a flag saying you did."*

**The interview question:** *"what happens when a database tool returns too much?"* *"You do not get
a database error — you get a 400 from the model provider about token count, several layers away from
the query, on a tool call that reported success. We measured ours: forty thousand matching tickets
serialised to about 6.9 million characters, roughly 1.7 million tokens, which is 173% of the window,
so the request could not be sent at all. The number that changed my mind was the other end of the
table: two hundred rows is under one percent of the window. The ceiling costs you nothing and its
absence costs you the whole conversation. So we cap rows in the SQL, trim text columns with `substr`
in the engine rather than in Python, return a `truncated` flag so the model does not tell the
customer there are five when there are two hundred, and check the serialised size as a last
backstop — because a row cap is not a byte cap and somebody will eventually paste a log file into a
ticket."*
