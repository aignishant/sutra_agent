# 5.3 — 💥 The write with no undo

## One-line answer

A write tool that is correct, parameterised and read-only-proof can still be uncallable-back: one
wrong argument closed 203 tickets when 200 were wanted, and nothing in the system could say which
three were the mistake.

## The story

You asked the barber to take a little off the sides.

He heard you. He is not careless and he is not new. But "a little" is a word, and the word he heard
and the word you said were about a centimetre apart, and the machine was already on.

You watch it happen in the mirror. There is a moment where you can see that it has gone further than
you meant, and there is nothing to say, because the thing that would fix it is putting hair back.

He will say it will grow, and he is right, and that is not the same as undoing it. You are going to a
wedding on Saturday.

## The idea in plain language

Every brake in section 2 protects the archive from a **read** going wrong. This part is about the
other side: a tool that is supposed to write, doing exactly what it was asked, to the wrong rows.

Call the tool `close_stale(before)`: close every open ticket opened on or before a date. It is a
reasonable tool for a support desk. It is bound, so no injection. There is no `LIMIT` because closing
things is the job. There is nothing to filter, and no brake in section 2 applies.

And it has four properties that together make a small mistake permanent:

- **It is bulk.** One call touches many rows, so the mistake is not one row's worth.
- **It is not idempotent in a useful way.** Running it again does not fix anything; the second run
  simply finds nothing left to close.
- **It destroys the information needed to undo it.** After the call, a wrongly-closed ticket and a
  rightly-closed ticket are byte-for-byte identical. The set of rows you changed is gone with the
  change.
- **It has already committed.** A transaction can be rolled back until it is committed. A tool that
  returns has committed, because the caller is entitled to believe the change happened.

The fix is not "be careful", and it is not "add a confirmation" — although a confirmation is worth
having. It is that **a write tool must write down what it is about to change, in the same transaction
that changes it**. Not a log line: a row, in a table, saying what the old value was. That turns "the
tool cannot be undone" into "the undo is a query".

## Why Sutra needs it

Because Sutra's database tools are read-only today and that is a decision with an expiry date. A
support desk that can only read is a research assistant; the moment somebody wants the agent to
actually close a ticket, [Day 34's](../../../day-34-building-sutra-mcp-tools/LESSON.md) server grows
a write path, and every property above arrives with it.

This is the part that decides what that day looks like. If a write tool ships without an undo table,
the undo has to be built later — after the incident, by somebody reconstructing intent from a log
that was not designed for it.

It is also where [3.2](../03-the-adk-side/3.2-a-database-server-through-mcptoolset.md)'s
`require_confirmation` argument on `McpToolset` finds its purpose: a human gate in front of the tool.
Worth having, and worth being clear-eyed about — a gate reduces how often the wrong call happens and
does nothing about what happens after it does.

## The mechanism

The tool as it is usually written. There is nothing wrong with this code:

```python
def close_stale(con: sqlite3.Connection, before: str) -> int:
    """Close every open ticket opened on or before `before`. Bound, and final."""
    cur = con.execute(
        "UPDATE tickets SET status = 'closed' WHERE opened_on <= ? AND status = 'open'",
        (before,),
    )
    con.commit()
    return cur.rowcount
```

**Line by line:**

- `before` is bound with `?`. Section 2's first brake is present and correct.
- `AND status = 'open'` means the statement only touches tickets that are actually open, so running
  it twice changes nothing the second time. That is a real safety property and it is not undo.
- `cur.rowcount` is how many rows the `UPDATE` changed. A **number**. Not a list of ids — and the
  difference between those two things is the entire part.
- `con.commit()` makes it permanent. From here, `rollback()` has nothing to roll back: the
  transaction is over.
- The return value is that number, so the tool's own answer contains no information about which rows
  it touched. Even a caller who immediately realised the mistake has nothing to work with.

The same write, with the old values recorded first, in the same transaction:

```python
def close_stale_logged(con: sqlite3.Connection, before: str) -> int:
    """The same write, with the old value recorded in the same transaction."""
    con.execute(
        "CREATE TABLE IF NOT EXISTS status_log (ticket_id TEXT, was TEXT, became TEXT, at TEXT)"
    )
    con.execute(
        "INSERT INTO status_log "
        "SELECT id, status, 'closed', datetime('now') FROM tickets "
        "WHERE opened_on <= ? AND status = 'open'",
        (before,),
    )
    cur = con.execute(
        "UPDATE tickets SET status = 'closed' WHERE opened_on <= ? AND status = 'open'",
        (before,),
    )
    con.commit()
    return cur.rowcount
```

**Line by line:**

- `INSERT ... SELECT` copies the rows **about to change** into the log, choosing them with the same
  `WHERE` clause the `UPDATE` will use. Same clause, same parameter, so the two sets are identical by
  construction rather than by care.
- The order matters absolutely: the `INSERT` runs **before** the `UPDATE`. Afterwards the old value
  is gone and there is nothing to record — that inversion is the commonest way this pattern is
  written wrong.
- Both statements are in one transaction, ended by the single `con.commit()`. A crash between them
  rolls back both, so you can never end up with a change nobody logged or a log entry for a change
  that did not happen.
- `was` and `became` are separate columns. Storing only `became` tells you nothing; storing only
  `was` leaves you guessing what happened.
- `datetime('now')` is computed by the engine, in UTC. Using Python's clock here would put the
  application server's timezone into the archive and make two writers disagree.
- `CREATE TABLE IF NOT EXISTS` inside the tool is expedient and is exactly what a migration is for.
  In `sutra_mcp/db_tools.py` this belongs in the schema, and leaving it here is a `TODO(me)`.

**Line by line:**

- The script seeds an archive with 200 old July tickets the desk genuinely wants closed and five from
  this week that it does not.
- It calls `close_stale` with the wrong month — `2026-09-30` instead of `2026-07-30`, one character
  different — and then reseeds and calls it with the right one, so the two row counts can be
  compared.
- It then reseeds a third time and runs the logged version, so you can watch the undo actually work.
- Zero model calls. The wrong argument is supplied directly, because the point is what happens after
  a wrong argument, not how one is produced.

## When it breaks

Real output, on 2026-09-04:

```text
seeded archive.sqlite3: 205 tickets, 2 kb articles
open tickets before the call : 203
the call the desk asked for  : close_stale('2026-07-30')
the call the model made      : close_stale('2026-09-30')
rows the tool reports changed: 203
open tickets after the call  : 0

seeded archive.sqlite3: 205 tickets, 2 kb articles
rows the desk actually wanted: 200
rows closed by mistake       : 3

the desk asks for those rows back:
  which ones      : unknown - a closed ticket looks the same either way
  rollback        : the transaction committed; there is nothing to roll back
  the return value: a count, not a list of ids
```

Sit with the three-line block at the bottom, because each line closes a door somebody would try.

**Which ones?** There is no answer in the database. A ticket closed by mistake and a ticket closed
correctly have identical rows. The only distinguishing fact — that one of them was open a moment ago
— was overwritten by the statement that closed it.

**Roll it back?** There is no transaction. `commit()` ran, because the tool returned, because the
caller had to be told something. Rollback is a window that closes the instant a tool is honest about
having finished.

**Use the return value?** It is `203`. A number cannot be un-applied.

And the tool did nothing wrong. It was handed `2026-09-30` and it closed every open ticket opened on
or before that date, which is precisely and only what it promised. There is no error message in this
part because there is no error. That is what makes it the worst failure in the day.

Now the same wrong call against the logged version:

```text
seeded archive.sqlite3: 205 tickets, 2 kb articles
the same write, with the old value written down first:
  rows changed    : 203
  rows restorable : 203
  rows put back   : 3
  open after undo : 3
```

Same mistake, same 203 rows changed. But `rows restorable: 203` means every one of them has its old
value on record, so the three that should not have been touched can be identified and returned —
`rows put back: 3`, and the archive is back to three open tickets from this week with the 200 July
ones correctly closed. The undo is a `SELECT` and an `UPDATE`, and it exists because one `INSERT`
ran first.

## In production

**What a professional writes instead:** append-only history, not in-place mutation. The tickets table
gets a `status_history` table, and "closing a ticket" is a row inserted rather than a column
overwritten, so the current status is derived from the newest row. Undo becomes "insert the previous
state again" and nothing is ever destroyed. Where in-place updates are unavoidable, the write-ahead
log pattern above is the minimum — and every bulk write tool returns the **ids** it touched, not a
count.

**What degrades at scale or under concurrency:** the log table. It grows faster than the data does,
because it gets a row per change rather than per entity, and nobody plans its retention. It also
becomes a second write on every write, which on a busy single-writer database is a real cost — one of
the honest reasons a team reaches for something with row-level locking, which is
[6.2](../06-in-production/6.2-when-sqlite-is-not-the-database.md).

**The failure mode that only appears with real traffic:** the bulk write with a parameter derived
from a model's arithmetic. "Close everything older than two months" requires a date, the date is
computed, and a computed date is wrong in exactly the way `2026-09-30` is wrong here — plausible,
well-formed, and off by a unit. A confirmation gate helps only if the human reads the date rather
than the sentence, and on the tenth approval of the day nobody does.

**The review comment a senior engineer leaves:** *"this tool returns `rowcount`. When it does the
wrong thing — and a bulk write with a date parameter will — that number is everything we will have.
Return the ids, and write the previous status into a log row inside the same transaction."*

**The interview question:** *"how do you make a write tool safe for an agent?"* *"Confirmation gates
first, because they reduce how often the wrong call happens — but they do not help afterwards, so the
real answer is undo. We ran the demonstration: a `close_stale(before)` tool, correctly written and
fully parameterised, called with a date one character wrong, closed 203 tickets when 200 were
intended. Nothing failed. There was no way to identify the three, because a wrongly-closed ticket and
a rightly-closed one are the same row; there was nothing to roll back, because the tool had
committed; and the return value was a count. The fix is one statement: an `INSERT ... SELECT` that
records the previous value of every row the update is about to touch, in the same transaction, using
the same `WHERE` clause. Then undo is a query. Beyond that I would rather the write were append-only
so nothing is ever overwritten, and every bulk tool returned ids rather than a number."*
