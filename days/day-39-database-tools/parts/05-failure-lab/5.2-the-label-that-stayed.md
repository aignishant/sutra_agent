# 5.2 — 💥 The label that stayed

## One-line answer

A tool's description is an interface, so renaming a column is an interface change — and because
nothing in the toolchain compares the description against the schema, the tool keeps promising a
column that no longer exists until a query fails at runtime.

## The story

The switchboard by the kitchen door has four switches and somebody wrote what they do on masking
tape underneath.

*Kitchen light. Porch light. Fan. Geyser.* It has been like that for years, and everybody in the
house uses it without thinking.

Then the wiring was redone when the extension was built. The electrician moved the porch light onto a
new circuit and put the bathroom exhaust fan where the porch used to be. He was there for two days
and he did excellent work, and he did not touch the masking tape, because the masking tape was not
part of the wiring.

Now guests flick the switch marked *Porch light* on their way out at night, and the bathroom fan
comes on, and the porch stays dark. Nobody is being careless. Every person in that hallway is doing
exactly what the label told them to do.

## The idea in plain language

[3.1](../03-the-adk-side/3.1-what-the-model-is-told.md) established that a tool's docstring is all
the model knows about it. This part is the consequence nobody plans for: **the docstring can go out
of date, and nothing will tell you.**

There are two directions the drift can run, and they fail differently:

**The description promises something that is gone.** It says the tool returns `priority`; a migration
renamed that column to `severity` last quarter. The model plans a question about priority, and the
query fails — loudly, at runtime, on a customer's request.

**The schema has something the description never mentions.** A migration added `opened_on` and nobody
updated the docstring. Nothing fails. The model simply never asks about dates, and the desk quietly
loses the ability to answer *"has this been open long?"* — a capability that exists in the data and
not in the interface.

The reason this drift is invisible is worth naming precisely. A schema change is a **migration**: it
has a file, a review, a rollout plan and a rollback. A tool description is a **docstring**: it lives
in a different file, in a different pull request, reviewed by whoever was on rotation. Nothing
mechanically connects them. There is no compiler that reads both, no type checker that spans the gap,
and no test — unless you write the one this part ends with.

## Why Sutra needs it

Because `sutra_mcp/db_tools.py` puts a description on the wire, and the wire is the point. A tool
description travelling over MCP is read by clients that are not yours — the whole reason
[Day 34](../../../day-34-building-sutra-mcp-tools/LESSON.md) built a server rather than a library.

And because [Day 32](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md)
taught that `tools/list` results are **cacheable**, with a TTL. A stale description is not just
stale in your process; it can be sitting in a client's cache, being planned against, after you have
fixed it. Correcting a description is two deployments, exactly like deleting a tool.

## The mechanism

The check is short, which is the argument for having it: ask the description what it promises, ask
the engine what exists, and compare the two sets.

```python
DESCRIPTION = (
    "Search the ticket archive. Returns id, title, body, status and priority "
    "for each matching ticket. status is one of 'open' or 'closed'."
)

BACKTICKED = re.compile(r"\b(id|title|body|status|priority|opened_on|severity)\b")


def promised(text: str) -> set[str]:
    """Column names a reader - or a model - would take from the description."""
    return set(BACKTICKED.findall(text))


def actual(con: sqlite3.Connection, table: str) -> set[str]:
    """Column names the table really has, asked of the engine."""
    return {row[1] for row in con.execute(f"PRAGMA table_info({table})")}
```

**Line by line:**

- `DESCRIPTION` is a copy of the docstring the server actually publishes. In real use it is read from
  the tool object rather than pasted, so the check cannot pass against a description nobody ships —
  that is a `TODO(me)` in the build brief.
- `BACKTICKED` is a list of the words that are column names in this domain. It is a deliberately
  crude parser: prose is prose, and there is no reliable way to extract "the columns this sentence
  promises" from free text. Crude and running beats perfect and unwritten.
- `\b` on both sides matches whole words, so `status` in the description does not also match
  `statuses` and the word `id` does not match inside `valid`.
- `PRAGMA table_info(table)` asks SQLite for the table's real columns. Row index `1` is the column
  name; index `0` is its position, `2` its declared type. This is the engine answering, not your
  model of the engine.
- The table name is formatted into the `PRAGMA` because **an identifier cannot be bound** — `?`
  placeholders stand for values, never for names. That is the one place
  [2.1](../02-the-five-brakes/2.1-the-argument-that-became-syntax.md)'s rule cannot be applied, and
  the discipline is that the name must come from a constant or an allowlist in your code, never from
  a caller.
- Both functions return **sets**, so the comparison is two set differences and the answer says which
  direction the drift runs.

Then the comparison, with an exit code so it can be a test:

```python
missing = sorted(want - have)
unmentioned = sorted(have - want)
sys.exit(1 if missing or unmentioned else 0)
```

**Line by line:**

- `want - have` is "promised but absent" — the loud failure, the one that raises at runtime.
- `have - want` is "present but undocumented" — the quiet one, a capability the model cannot reach.
- Reporting both and failing on either is the choice that matters. A check that only reported the
  loud direction would pass on the archive that has been quietly missing a feature for a year.
- `sys.exit(1 ...)` makes this a check rather than a report, which is Principle 11: an eval is a test
  that can go red.

Run it:

```bash
cd days/day-39-database-tools/lab && uv run python drift.py; echo "exit: $?"
```

**Line by line:**

- The script seeds the five-ticket archive and compares it against a description that was written
  against a different schema — so it is red by construction, which is the honest way to demonstrate
  a check.
- It then runs the query the description implies, so you see the runtime failure rather than being
  told about it.
- Zero model calls, zero network.

## When it breaks

Real output, on 2026-09-04:

```text
seeded archive.sqlite3: 5 tickets, 2 kb articles
columns the description promises : ['body', 'id', 'priority', 'status', 'title']
columns the table actually has   : ['body', 'id', 'opened_on', 'status', 'title']
  - promised but absent: priority
  - present but undocumented: opened_on

what the model does with a promised column that is not there:
  OperationalError: no such column: priority
findings: 2
exit: 1
```

Both directions in one run, and they read very differently.

`promised but absent: priority` ends in this, verbatim:

```text
sqlite3.OperationalError: no such column: priority
```

That is a good error. It is specific, it names the column, and it happens the first time anybody
asks. What makes it expensive is *where* it happens: not in a test, not in a migration, but inside a
tool call, on a customer's question, because the model read a description that said `priority` and
planned accordingly. The migration that renamed the column passed every test it had.

`present but undocumented: opened_on` produces **nothing**. No error, no log line, no degraded
metric. The archive has known when every ticket was opened since the day it was created, and the
desk cannot answer *"how long has this been open?"* because the only description of the tool does not
mention that the data exists. That failure has no error text because it is not an error; it is a
capability that was never offered.

## In production

**What a professional writes instead:** a test in the suite that runs this comparison against the
**live** tool object and the **live** schema, so a migration that renames a column fails CI in the
same pull request that renames it. That is the only place the two artefacts are ever in the same
process at the same time, and it is why the check has to be a test rather than a review checklist.

**What degrades at scale or under concurrency:** with one table and one tool this is a small
problem. With twenty tools over eight tables it is a matrix, and the drift is never in the tool
somebody was thinking about. Teams that get this right generate the column list into the description
rather than writing it twice — the description is built at import time from `PRAGMA table_info`, so
it cannot disagree.

**The failure mode that only appears with real traffic:** the cached description. You fix the
docstring and deploy. A client that fetched `tools/list` with a TTL still has the old text and will
keep planning against `priority` until its cache expires, so the errors continue after the fix and
the person who fixed it cannot reproduce them. Two deployments, again — the shape
[Day 32](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md)
warned about for tool deletion applies to tool *descriptions* too.

**The review comment a senior engineer leaves:** *"this migration renames `priority` to `severity`
and touches no docstrings. The tool description is a published interface — it went out over MCP and
somebody's client has it cached. Rename it in the description in this pull request, or do not rename
it."*

**The interview question:** *"what happens to your agent when the database schema changes?"*
*"Usually nothing good, and the reason is structural: the schema change is a migration with a review
and a rollback, and the tool description is a docstring in a different file, and no tool in the
toolchain reads both. So it drifts in two directions. If the description promises a column that was
renamed, the model plans against it and you get `no such column` inside a live tool call — a clear
error in the worst possible place. If the schema gained a column the description never mentions,
nothing fails at all and the agent simply cannot answer a question the data supports, which is the
one that survives for years. We wrote a test that reads the published description and the real
`PRAGMA table_info` and fails on either direction, because that is the only moment both exist in the
same process. And because MCP tool lists are cacheable, fixing a description is two deployments —
clients keep planning against the old one until the TTL expires."*
