# 3.1 — What the model is told

## One-line answer

ADK builds the tool declaration from your function's name, signature and docstring, so the docstring
is not documentation about the tool — it **is** the tool, as far as the model is concerned, and a
table it does not describe is a table the model will guess about.

## The story

You leave the scooter at the repair shop and the man at the counter writes a job card.

He does not write down everything he can see. He writes what you told him: *starts hard when cold,
noise from the back*. That card goes to whoever is free, and that person has never spoken to you.
They work from the card.

If you mentioned the brakes and he did not write it down, the brakes do not get looked at. If you
said "noise from the back" and meant the exhaust, and the card says the same three words, the
mechanic checks the wheel bearing — reasonably, because that is what the card supports.

The card is not a record of the conversation. It is the conversation, everywhere past the counter.
And the man writing it is you.

## The idea in plain language

When you hand ADK a Python function as a tool, it does not send the model your code. It sends a
**declaration**: a JSON description of the function's name, what it does, and what arguments it
takes. That declaration is built by inspecting the function — its name, its parameters, their type
hints, their default values, and its docstring.

The adk.dev documentation states it plainly (`https://adk.dev/tools-custom/function-tools/`, read
2026-09-04): *"The ADK framework automatically inspects your Python function's signature—including
its name, docstring, parameters, type hints, and default values—to generate a schema."* And about
the docstring specifically: *"The docstring of your function serves as the tool's **description** and
is sent to the LLM."*

So four things about your source become the model's entire knowledge of your database:

| What you write | What the model receives |
| --- | --- |
| the function name | the tool name it must emit to call you |
| the docstring | the description it chooses the tool from |
| type hints | the JSON types of each argument |
| default values | which arguments are required and which are optional |

The last row is a rule worth stating exactly, because it is not obvious: *"A parameter is considered
**required** if it has a type hint but **no default value**"*, and optional when a default is given.
There is no separate `required=` switch. You express it by whether you wrote `= 3`.

What is **not** in the declaration is everything else. Your table names, your columns, the fact that
you filter to open tickets, the clamp on `limit`, the read-only connection — none of it travels. The
model plans against the description alone, which means that anything true about your data that the
description does not say is something the model will either ignore or invent.

## Why Sutra needs it

Because the whole of section 2 was about limits the model cannot argue with, and this part is the
other half: the limits the model needs to **know about** in order to behave sensibly.

The clamp in [2.4](../02-the-five-brakes/2.4-a-ceiling-the-caller-cannot-raise.md) makes `limit=99`
harmless. The docstring line *"from 1 to 5"* is what stops it being asked for. One is enforcement,
one is routing, and a database tool needs both — a tool that silently ignores half its arguments
teaches the model nothing and wastes a call every time.

It also decides what happens on Day 40 and beyond. Descriptions are how a model picks between
`search_tickets` and `search_kb`, which is
[Day 28's](../../../day-28-progressive-disclosure-design/LESSON.md) crowded shelf, now with a schema
behind it.

## The mechanism

The declaration is not a mystery you have to reason about. You can print it:

```python
import json

from google.adk.tools import FunctionTool  # verified: adk.dev/tools-custom/function-tools


def search_tickets(term: str, limit: int = 3) -> dict:
    """Search the ticket archive for a symptom and return matching tickets.

    Args:
        term: words from the symptom, for example "logged out".
        limit: how many tickets to return, from 1 to 5.

    Returns:
        {"status": "ok", "tickets": [{"id", "title", "snippet"}], "truncated": bool}
    """


tool = FunctionTool(func=search_tickets)
declaration = tool._get_declaration()  # noqa: SLF001 - inspecting what ADK publishes
print(json.dumps(json.loads(declaration.model_dump_json(exclude_none=True)), indent=2))
```

**Line by line:**

- `FunctionTool(func=...)` is the wrapper ADK puts around a plain Python function. Verified against
  `https://adk.dev/tools-custom/function-tools/` on 2026-09-04.
- `term: str` with no default makes `term` required; `limit: int = 3` with a default makes `limit`
  optional and carries the `3` into the schema. Those two lines are the entire "required" logic.
- The docstring's first line is the summary the model reads first, and it names both the subject (the
  ticket archive) and the action (search). A first line reading *"Query the DB"* is a tool the model
  will reach for when it should not and skip when it should.
- The `Args:` block describes each parameter **including an example value**. `for example "logged
  out"` tells the model that `term` takes words from the symptom, not a ticket id and not SQL.
- `limit: how many tickets to return, from 1 to 5` states the ceiling in the only place the model can
  read it. The clamp in the code is what happens when it asks for more anyway.
- The `Returns:` block describes the shape. This is what stops a model treating an empty `tickets`
  list as an error, and it is where the `truncated` flag earns its place — a flag the model is never
  told about is a flag it will not mention to the user.
- `_get_declaration()` has a leading underscore, so it is ADK-internal and may change between
  versions. That is fine for a lab whose entire job is looking inside; it is not something to build
  a tool on. The `noqa` says so out loud, per house style.
- `exclude_none=True` drops the fields ADK left unset, so what prints is what is actually sent rather
  than a wall of nulls.

Run it:

```bash

```

**Line by line:**

- The lab's version of the function has a real body — it opens the read-only archive, runs the bound
  query with the clamped limit, and returns the dict — so the script prints both the declaration and
  the result of one real call.
- Zero model calls. Building a declaration is inspection, not generation, so this costs nothing from
  the day's quota.

## When it breaks

Here is the real declaration, printed on 2026-09-04 against `google-adk==2.7.1`:

```text
{
  "description": "Search the ticket archive for a symptom and return matching tickets.\n\nArgs:\n    term: words from the symptom, for example \"logged out\".\n    limit: how many tickets to return, from 1 to 5.\n\nReturns:\n    {\"status\": \"ok\", \"tickets\": [{\"id\", \"title\", \"snippet\"}], \"truncated\": bool}",
  "name": "search_tickets",
  "parameters_json_schema": {
    "properties": {
      "term": {
        "title": "Term",
        "type": "string"
      },
      "limit": {
        "default": 3,
        "title": "Limit",
        "type": "integer"
      }
    },
    "required": [
      "term"
    ],
    "title": "search_ticketsParams",
    "type": "object"
  }
}
```

Three things in there are worth stopping on.

**`description` is the whole docstring, verbatim** — `Args:` block, `Returns:` block, newlines and
all. It is not parsed into per-parameter descriptions. Look at `"term"`: it has a `type` and a
`title` and **no description**. Everything the model knows about what `term` means, it reads out of
that one long string. So the docstring is not a nice-to-have next to a structured schema; it is the
structured schema's only prose.

**`"required": ["term"]`** — exactly as the rule predicted, because `term` had no default and `limit`
did.

**`title: "Term"`** is generated from the parameter name, not written by you. It is noise, and it is
the only place a parameter's name appears in human-readable form. Name your parameters as if the
model will read them, because it will.

Run the same script and you also get this, on stderr:

```text
UserWarning: [EXPERIMENTAL] feature FeatureName.JSON_SCHEMA_FOR_FUNC_DECL is enabled.
```

That is ADK telling you the `parameters_json_schema` key above is behind an experimental feature
flag in this version. It is not an error and nothing is broken, but it is exactly the kind of line
worth reading rather than filtering out of your logs: the shape of the declaration is subject to
change, so anything you build that **parses** a declaration is building on a moving surface.

And the failure that has no message at all — a docstring that describes columns the table does not
have. The declaration is generated happily, the model plans against it, and the query fails at
runtime with `sqlite3.OperationalError: no such column: priority`. That whole failure mode is
[5.2](../05-failure-lab/5.2-the-label-that-stayed.md).

## In production

**What a professional writes instead:** a docstring reviewed as carefully as the SQL, and a test that
asserts on the declaration. If the description is the interface, it belongs in the test suite: pin
the tool name, pin the required list, and assert that the description mentions the ceiling. Tools
whose descriptions drift silently are the commonest cause of an agent that "got worse" with no code
change anyone can point at.

**What degrades at scale:** the description is tokens, sent on **every** request, for every tool the
agent has. A generous docstring on twelve tools is a fixed tax on every turn of every conversation —
[Day 24's](../../../day-24-token-accounting-and-budgets/LESSON.md) accounting applies directly. The
answer is not to write terse docstrings; it is to give each agent fewer tools, which is
[Day 40](../../../day-40-filtering-and-allowlists/LESSON.md).

**The failure mode that only appears with real traffic:** two tools whose descriptions overlap.
`search_tickets` and `search_kb` both say "search" and both take a `term`, and the model picks
whichever reads closer to the user's phrasing — which on a support desk means "logged out" goes to
whichever description happens to contain the word "login". It is invisible in testing because your
test questions were written by somebody who knew which tool they wanted.

**The review comment a senior engineer leaves:** *"this docstring says 'Search the archive'. Search
which archive, for what, returning what? The model has this sentence and nothing else — there is no
code for it to read."*

**The interview question:** *"how does the model know what your tool does?"* *"From a declaration
ADK generates by inspecting the function: the name, the type hints, the defaults, and the docstring.
What surprised me the first time I printed one is that the docstring goes across whole, as one string
— there is no per-parameter description field being populated, so the `Args:` block is prose the
model reads, not structured data anything parses. Required versus optional is decided purely by
whether the parameter has a default. Which means the docstring is the interface: if it does not
mention that `limit` maxes out at five, the model asks for a hundred; if it does not mention the
`truncated` flag, the model never tells the user the answer was cut. We test the declaration for that
reason — same as testing any other public contract."*
