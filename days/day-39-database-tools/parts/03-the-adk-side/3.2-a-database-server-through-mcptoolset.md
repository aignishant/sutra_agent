# 3.2 — A database server through McpToolset

## One-line answer

`McpToolset` is the ADK object that turns "a database MCP server" into tools an agent can use, and
building one starts no process and opens no connection — it is a launch spec plus a filter, which
means the decision about what a database server may expose is inspectable before anything runs.

## The story

The electrician arrives with his own bag.

You did not buy a multimeter. You do not own a crimping tool and you are not going to. He opens the
bag on your floor, takes out the four things this job needs, and everything else stays in the bag.

The useful part is not that he has tools. It is that the bag is his, packed for the work he does, and
what comes out of it is decided at your door rather than in your house. When he leaves, none of it
stays behind. If he comes back next month for a different job, a different four things come out.

## The idea in plain language

[Day 33](../../../day-33-client-and-transports/LESSON.md) built Sutra's own MCP client in
`sutra/mcp/client.py` — `connect_stdio`, `connect_http`, `list_tools` — because the way to understand
a protocol is to speak it by hand. `McpToolset` is the framework's version of that same job, and
Principle 4 says you meet it in this order deliberately: you already know what it is doing.

What it does is three things:

1. **Launch or reach a server.** For a stdio server it runs a command as a subprocess and talks over
   its standard input and output; for an HTTP server it holds a URL.
2. **Ask the server what tools it has**, and turn each one into an ADK tool with a name, a
   description and a JSON schema — the same shape [3.1](3.1-what-the-model-is-told.md) printed for a
   local Python function.
3. **Keep or drop tools** according to a filter you supply.

The third one is the one that matters for a database. A database MCP server can offer a great deal,
and what your agent gets is the intersection of what the server offers and what your filter allows.

The property that makes this inspectable is that **constructing the toolset does none of that yet**.
`McpToolset(connection_params=..., tool_filter=[...])` builds an object holding a description of a
subprocess. Nothing is spawned, no socket opens, and the database file named in the environment need
not exist. You can print the whole decision — what will be run, with what environment, and which
tools survive — before any of it happens.

## Why Sutra needs it

Because there are exactly two ways to put Sutra's archive behind MCP, and today chooses between
them.

The hand-written way is `sutra_mcp/db_tools.py`, registered into the server
[Day 34](../../../day-34-building-sutra-mcp-tools/LESSON.md) built — your SQL, your brakes, your
tool names. The other way is to point `McpToolset` at a database MCP server somebody else wrote,
which is [section 4's](../04-toolbox-parked/4.1-the-server-you-did-not-write.md) subject.

`McpToolset` is how both are reached from the agent side, which is why the ADK half of today is one
class and one argument. And `tool_filter` is where
[Day 40](../../../day-40-filtering-and-allowlists/LESSON.md) will build the general machinery;
today you meet it as the last line of defence in front of a server whose tool list you did not
choose.

## The mechanism

The imports first, because they come from three different places and people get them wrong:

```python
from google.adk.tools.mcp_tool import McpToolset
from google.adk.tools.mcp_tool.mcp_session_manager import StdioConnectionParams
from mcp import StdioServerParameters
```

**Line by line:**

- `McpToolset` — the class. Verified in the installed package at
  `.venv/Lib/site-packages/google/adk/tools/mcp_tool/__init__.py` on 2026-09-04, and against
  `https://adk.dev/tools-custom/mcp-tools/` the same day. Note the spelling: there is also an
  `MCPToolset` in the same module and it is deprecated — the failure section shows what it says.
- `StdioConnectionParams` — ADK's wrapper describing a stdio connection. It lives in
  `mcp_session_manager`, and it is also re-exported from `google.adk.tools.mcp_tool` itself; the
  adk.dev page uses the longer path, so this day does too.
- `StdioServerParameters` comes from the **`mcp` package**, not from ADK. That is the one import
  people guess wrong, because it looks like it should be an ADK class and it is the MCP SDK's.
- That whole `mcp_tool` package sits inside a `try/except ImportError` that logs *"MCP Tool is not
  installed"*. If the `mcp` package is missing, these names simply do not exist and you get an
  `ImportError` naming the class rather than anything about MCP — see *When it breaks*.

Now the launch spec:

```python
PARAMS = StdioConnectionParams(
    server_params=StdioServerParameters(
        command="uv",
        args=["run", "python", "-m", "sutra_mcp.server", "--stdio"],
        env={"SUTRA_ARCHIVE": "sutra/data/tickets.sqlite3"},
    ),
    timeout=5.0,
)

ALLOWED = ["lookup_ticket", "search_tickets"]

toolset = McpToolset(connection_params=PARAMS, tool_filter=ALLOWED)
```

**Line by line:**

- `command` and `args` are a command line split into a program and its arguments. They are passed to
  the operating system as a list, so nothing is run through a shell and a path containing a space
  needs no quoting.
- `env` sets environment variables for the **child** process. This is how the archive path reaches
  the server, and it is the right place for it: the connection spec says which database, and the
  server code says how to read one.
- Nothing here checks that `sutra/data/tickets.sqlite3` exists. `StdioServerParameters` is a
  description; the file is opened much later, by a different process, and a wrong path shows up as a
  tool error rather than a construction error.
- `timeout=5.0` is how long ADK waits to **establish** the connection, in seconds. Its default is
  `5.0` — read from the class in the installed package on 2026-09-04. It is not a per-call timeout
  and it is not the step budget from
  [2.5](../02-the-five-brakes/2.5-the-query-that-never-ends.md); those are three different clocks and
  a slow query is not a slow connection.
- `tool_filter=ALLOWED` is a plain list of names. A tool the server offers whose name is not in the
  list never becomes an ADK tool, is never described to the model, and cannot be called. The
  parameter also accepts a predicate function, which is what
  [Day 40](../../../day-40-filtering-and-allowlists/LESSON.md) needs.
- `McpToolset(...)` returns immediately. No subprocess, no handshake, no network. Everything above is
  data.

There is one more constructor argument worth knowing about today, read from the installed class on
2026-09-04: `require_confirmation`, which takes a `bool` or a callable. It is the hook for a human
approval gate in front of a toolset — the natural home for "ask before any write" once
[5.3](../05-failure-lab/5.3-the-write-with-no-undo.md) has convinced you that you want one. Sutra
does not build it today; it is named here so you know where it lives.

```bash
cd days/day-39-database-tools/lab && uv run python toolset_shape.py
```

**Line by line:**

- The script builds the objects above and prints them. It launches nothing, so it works on a machine
  where `sutra_mcp/server.py` does not exist yet — which is the whole point of separating the
  description from the connection.
- It then applies `ALLOWED` to a four-tool list by hand, to show the filter's effect without needing
  a server to offer four tools.
- Zero model calls, zero network, no subprocess.

## When it breaks

The run, on 2026-09-04:

```text
what this toolset will launch
  command      : uv
  args         : ['run', 'python', '-m', 'sutra_mcp.server', '--stdio']
  env          : {'SUTRA_ARCHIVE': 'sutra/data/tickets.sqlite3'}
  connect timeout (s): 5.0
  tool_filter  : ['lookup_ticket', 'search_tickets']
  confirmation required: False

what a server offering four tools would be reduced to
  offered      : ['lookup_ticket', 'search_tickets', 'execute_sql', 'list_tables']
  kept         : ['lookup_ticket', 'search_tickets']
  dropped      : ['execute_sql', 'list_tables']

the old spelling of the same class
  DeprecationWarning: MCPToolset class is deprecated, use `McpToolset` instead.
```

Two of those lines are the day's argument in miniature. `dropped: ['execute_sql', 'list_tables']` is
the hallway from [1.3](../01-the-archive/1.3-a-door-not-a-hallway.md) being closed at the client, by
a list of two names — and the fact that it *can* be closed there is exactly why section 4 does not
end with "never use a generated server".

And the deprecation is real and worth catching now:

```text
DeprecationWarning: MCPToolset class is deprecated, use `McpToolset` instead.
```

Both spellings are exported, both work, and Python hides `DeprecationWarning` by default — so a
tutorial written a year ago will run silently on the old name until the day it is removed. The lab
turns warnings on explicitly to make it visible.

The import failure is the other one you will meet, and its message misdirects:

```text
Traceback (most recent call last):
  File "toolset_shape.py", line 15, in <module>
    from google.adk.tools.mcp_tool import McpToolset
ImportError: cannot import name 'McpToolset' from 'google.adk.tools.mcp_tool'
```

Nothing in that message mentions MCP being missing, because the `mcp_tool` package caught its own
`ImportError`, logged *"MCP Tool is not installed"* at debug level where you will not see it, and
left `__all__` empty. The usual cause is not a missing package at all — it is running with the wrong
interpreter, one that does not have this project's dependencies. Run it with `uv run`, which is what
the command above does.

## In production

**What a professional writes instead:** the toolset is built once, at module import, and the filter
is not optional. A production agent lists the tools it may use by name, and a server that grows a new
tool tomorrow does not silently gain access to your model's context — the new tool is dropped until
somebody adds it to the list deliberately. That is the same allowlist argument as
[2.3](../02-the-five-brakes/2.3-the-statements-you-allow.md), one layer up.

**What degrades at scale or under concurrency:** a stdio toolset launches a **subprocess per
connection**. That is fine for a desktop client and wrong for a server handling many sessions, where
you want one long-lived HTTP server and `StreamableHTTPConnectionParams` instead — the shape
[Day 43](../../../day-43-stateless-by-default/LESSON.md) deploys. A database server is exactly the
case where this bites, because each subprocess opens its own connections to the same file.

**The failure mode that only appears with real traffic:** the tool list is fetched from the server,
and a server can change it. A deployment on their side adds `execute_sql` to a toolset you have been
using for months, and without a filter your agent picks it up on the next `tools/list` — no code
change on your side, no review, no deploy. `tool_filter` is what turns that from an event into a
no-op.

**The review comment a senior engineer leaves:** *"there is no `tool_filter` on this toolset. That
means our agent's capabilities are whatever the other team ships next Tuesday. Name the tools we
actually use."*

**The interview question:** *"how do you connect an ADK agent to a third-party MCP server?"*
*"`McpToolset` with connection params — `StdioConnectionParams` wrapping the MCP SDK's
`StdioServerParameters` for a subprocess, or `StreamableHTTPConnectionParams` for a URL. The part I
would underline is that constructing it does nothing: it is a launch spec, so you can print exactly
what will be run and with which environment before anything starts. And I always pass `tool_filter`.
Without it, my agent's tool list is whatever that server offers today, and that is a list somebody
else can change without telling me — we watched a filter drop `execute_sql` and `list_tables` from a
four-tool server, which is the difference between a search tool and a database credential."*
