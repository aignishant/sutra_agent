# 4.1 — 🅿️ The server you did not write

## One-line answer

MCP Toolbox for Databases is a single binary that turns a database into an MCP server from a YAML
file, in two modes — a prebuilt recipe that hands you `execute_sql`, or a config where you declare
each tool's statement yourself — and Sutra parks it because every required step in this curriculum
must run with no installed server and no account.

## The story

There are two ways to get a cupboard into the back bedroom.

The shop on the main road sells a steel almirah. It arrives on a handcart on Thursday, two men carry
it up, and by Thursday evening you are putting clothes in it. It comes in three widths. Yours is the
middle one, and the shelf spacing is what the shelf spacing is.

The carpenter down the lane takes three weeks and asks a lot of questions. He measures the alcove,
which is not square, and builds to the wall. The shelves are where your things are. It costs more and
you have to be there for the measuring.

Neither of these is the right answer. The right answer depends on whether the alcove is square, how
long you can wait, and whether you will still be in this flat next year. What is not in doubt is
that both are real cupboards and both hold clothes.

## The idea in plain language

**MCP Toolbox for Databases** is an open-source server, published by Google, whose job is to turn a
database into an MCP server. It is a single compiled binary. You point it at a database, give it a
configuration, and it serves MCP tools that a client such as ADK's `McpToolset` can connect to.

Its configuration has three kinds of entry, and understanding them is most of understanding the
tool:

| Kind | What it declares |
| --- | --- |
| `source` | a database: its type and how to reach it |
| `tool` | one tool: its name, its description, and — for most types — the statement it runs |
| `toolset` | a named group of tools, so a client can ask for a subset |

There are two ways to supply that configuration, and the difference between them is the whole of
[4.2](4.2-who-writes-the-sql.md).

**Prebuilt.** You run the binary with a recipe name and it uses a configuration that ships inside it.
For SQLite, that recipe is two tools, and they are generic on purpose: one lists the tables, one runs
whatever SQL it is given.

**Custom.** You write the configuration yourself. Each `tool` entry carries its own SQL statement and
its own declared parameters, so the tools are exactly the questions you chose — narrow, in the sense
[1.3](../01-the-archive/1.3-a-door-not-a-hallway.md) meant.

The project is real, current and broad: version **1.9.0**, released 2026-08-14, with integrations for
Postgres, MySQL, BigQuery, Spanner, SQL Server, Oracle, MongoDB, Neo4j, Redis, Snowflake, ClickHouse
and many more (`https://mcp-toolbox.dev/`, read 2026-09-04). On the ADK side, the `toolbox` extra
pulls in the `toolbox-adk` package — version **1.4.0**, released 2026-09-01, described on PyPI as
*"Agent Development Kit Integration for MCP Toolbox"*.

## Why Sutra needs it

Because a curriculum that only ever shows you the hand-rolled version has taught you a habit rather
than a decision. Principle 4 says build the mechanism first and then compare — and the comparison is
worthless if the alternative is a straw man you never looked at.

Toolbox is also the thing an interviewer will name. "Why did you write your own database tools when
Google ships a server for that?" is a fair question, and the only answer that survives follow-up is
one where you can describe what the alternative actually generates.

🅿️ **What parked means here.** Toolbox is documented, interview-ready, and **not built**. No step of
this day downloads a binary or requires one to be running. Two reasons, and both are rules rather
than preferences. Addendum 02 says no required step may need an installed server or an account. And
`docs/PACKAGES.md` exists so that every installed thing is pinned and dated — installing a binary to
run once and delete is exactly the habit that ledger prevents. If Sutra's archive ever moves to
Postgres, this is the first thing to re-evaluate, and
[6.2](../06-in-production/6.2-when-sqlite-is-not-the-database.md) says why.

## The mechanism

This is the SQLite prebuilt configuration, read on 2026-09-04 from
`https://raw.githubusercontent.com/googleapis/mcp-toolbox/main/internal/prebuiltconfigs/tools/sqlite.yaml`.
It is quoted rather than described, because the point is what it actually says:

```yaml
kind: source
name: sqlite-source
type: sqlite
database: ${SQLITE_DATABASE}
---
kind: tool
name: execute_sql
type: sqlite-execute-sql
source: sqlite-source
description: Use this tool to execute SQL.
---
kind: toolset
name: sqlite_database_tools
tools:
- execute_sql
- list_tables
```

The `list_tables` entry is omitted above only for length; it is a `sqlite-sql` tool carrying a long
statement that reads `sqlite_master` and the `pragma_table_info` views to produce the full
information schema.

Three things to see in it.

**`database: ${SQLITE_DATABASE}`** — the source takes the file path from an environment variable, so
the same binary and the same recipe point at any SQLite file. That is the `env` dictionary from
[3.2](../03-the-adk-side/3.2-a-database-server-through-mcptoolset.md), arriving at its destination.

**`type: sqlite-execute-sql`** is a tool type with no `statement` field, because the statement is the
caller's argument. Compare it with `list_tables`, whose type is `sqlite-sql` and which carries a
fixed statement in the YAML. The two types are the door and the hallway, named.

**`description: Use this tool to execute SQL.`** Six words, and they are accurate. Every scrap of
guidance the model gets about this tool is that sentence. Whatever the model sends, the tool runs.

The custom mode is the same file with your statements in it. This is the shape — and it is a shape,
not a copy of a documented example, so treat the field names as the thing to verify:

```yaml
kind: tool
name: search_tickets
type: sqlite-sql
source: sqlite-source
description: Search the ticket archive for a symptom and return matching tickets.
statement: |
  SELECT id, title, substr(body, 1, 160) FROM tickets
  WHERE status = 'open' AND body LIKE '%' || ? || '%'
  LIMIT 5
parameters:
- name: term
  type: string
  description: words from the symptom, for example "logged out"
```

**Line by line:**

- `type: sqlite-sql` is the narrow type: it carries a `statement`, so the SQL is in the configuration
  rather than in the request.
- `statement` holds the SQL with a `?` placeholder, which means the value is bound —
  [2.1](../02-the-five-brakes/2.1-the-argument-that-became-syntax.md)'s brake, provided by the server
  rather than by your Python.
- `'%' || ? || '%'` builds the `LIKE` pattern in **SQL**, concatenating the wildcards around the
  bound value. This is the YAML equivalent of `f"%{term}%"` in Python and it is where a hand-written
  version has an advantage: it is easier to get subtly wrong in a string in a config file.
- `LIMIT 5` is a constant in the statement, so the ceiling is the server's and no caller can raise it.
  Note what is missing next to it: there is no `truncated` flag, because the tool returns rows and the
  YAML has nowhere to compute one.
- `parameters` declares the arguments, with a description each. This is Toolbox generating the same
  declaration ADK generated from your docstring in
  [3.1](../03-the-adk-side/3.1-what-the-model-is-told.md) — from YAML instead of Python.

  parameters block of a `sqlite-sql` tool before writing a real `tools.yaml`).** The prebuilt file
  above is quoted from the repository and is exact; this custom shape is illustrative, and its field

## When it breaks

The failure Toolbox is most often reported for is not a crash. It is the prebuilt recipe doing
exactly what it says:

```text
tool call: execute_sql
  sql: SELECT * FROM tickets

result: 40001 rows
```

No error. No limit. `sqlite-execute-sql` has no `statement` and therefore no `LIMIT`, so the ceiling
from [2.4](../02-the-five-brakes/2.4-a-ceiling-the-caller-cannot-raise.md) does not exist on this
path — it lived in a statement nobody wrote. What that costs is measured in
[5.1](../05-failure-lab/5.1-forty-thousand-rows.md).

The loud failure is the one from misreading the recipe as a configuration you control:

```text
sqlite3.OperationalError: unable to open database file
```

or from the server itself when the environment variable is unset — the source declares
`${SQLITE_DATABASE}` and nothing supplies a default, so the binary starts and fails on the first
tool call rather than at boot.

Both of these are worth noticing for what they are: this is a well-built server behaving correctly.
The prebuilt recipe is not careless. It is a recipe for **exploration**, and it is being used as a
production tool surface.

## In production

**What a professional writes instead:** if the team is going to use Toolbox, they use `tools.yaml`
with declared statements, not the prebuilt recipe, and the YAML is reviewed in pull requests exactly
like SQL in code. Prebuilt mode has a legitimate home — a developer poking at an unfamiliar database
from their own client, with their own credentials — and it is not the agent's tool list.

**What degrades at scale:** nothing about Toolbox degrades; that is genuinely its selling point. It
is a compiled server with connection pooling, and it will out-serve a hand-written Python tool on a
busy database without you thinking about it. What degrades is your ability to answer "what can this
agent do?", because the answer is now spread across a YAML file, a binary version, and whichever
recipe was in that binary.

**The failure mode that only appears with real traffic:** the binary is a version. Toolbox is at
1.9.0 today; the prebuilt recipes ship **inside** it, so upgrading the binary can change what tools
your agent has without a line of your configuration changing. That is a supply-chain surface with the
same shape as [Day 29's](../../../day-29-sourcing-and-auditing-skills/LESSON.md) sourcing problem,
and it wants a pinned version and a `docs/PACKAGES.md` row rather than "install the latest".

**The review comment a senior engineer leaves:** *"we are running `--prebuilt sqlite`, which means our
tool surface is defined by whatever recipe is compiled into the binary we happened to download. Pin
the version, or move to a `tools.yaml` we own."*

**The interview question:** *"there is a first-party MCP server for databases. Why did you write your
own tools?"* *"I looked at it properly first. MCP Toolbox for Databases is a Go binary that serves a
database over MCP from a YAML file with three kinds of entry — sources, tools and toolsets — and it
supports about fifty databases with pooling and auth built in. It has two modes and they are very
different products. The prebuilt recipe for SQLite is two tools, and the main one is `execute_sql`,
whose entire description is 'Use this tool to execute SQL' — that is a hallway, and it has no row
limit because the statement comes from the caller. The custom mode is genuinely good: you declare
each tool's statement in YAML with bound parameters, so it is narrow, and you get the serving layer
for free. The reason we did not adopt it is specific to us — our archive is one SQLite file, so
pooling and auth buy us nothing, and adding a compiled binary to a project that ships as a Python
package costs more than the two functions it replaces. On Postgres I would re-run that comparison and
I expect the answer would flip."*
