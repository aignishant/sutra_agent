# 4.3 — 🅿️ The extras map

## One-line answer

ADK ships twenty-three optional dependency bundles called extras, each one a doorway to a capability
the framework has grown, and the professional skill is being able to place every one of them on a map
without having installed any of them.

## The story

The accessories aisle at the appliance shop is three shelves of jars and blades for a mixer-grinder.

There is a tall jar for making batter, a small dry-grinding jar, a juicer attachment, a food
processor bowl with four blades, a coconut scraper, and a slicing disc. All of them fit your machine.
None of them came with it.

You are not going to buy six of them. You will buy the small jar, because you grind spices, and you
will look at the rest. What you get from the ten minutes in that aisle is not purchases. It is
knowing that the attachment for the thing you are struggling with **exists** — so that in a year,
when you are grating coconut with a hand tool and swearing, you remember there is a part for that.

The aisle is a map. You walk it once and buy one thing.

## The idea in plain language

`uv add google-adk` installs the core. An **extra** is a named bundle of optional dependencies you
can ask for alongside it — `google-adk[toolbox]` installs the core plus whatever `toolbox` pulls in —
and it exists because forcing every user to install fifty database drivers to use one of them would
be absurd.

Extras matter for two reasons that are not about installing anything.

**They are a map of where the framework is growing.** A framework's extras list is the honest version
of its roadmap: each one is a capability somebody built and shipped. Reading it tells you what ADK
thinks it is for this year.

**Each one is a decision you have not made.** An extra that pulls in a cloud SDK is an extra with a
billing account behind it. Under Addendum 02 that makes several of these permanently 🅿️ parked for
Sutra — documented, not built.

Here is the list, read on 2026-09-04 from the installed distribution's metadata
(`google_adk-2.7.1.dist-info/METADATA`), which is a better source than any web page because it is the
version actually in this repository:

```text
a2a · agent-identity · all · antigravity · benchmark · bigquery-analytics · community ·
daytona · db · dev · docs · e2b · eval · extensions · gcp · mcp · oci · otel-gcp ·
redis · slack · test · toolbox · tools
```

Twenty-three. The ones this curriculum has an opinion about:

| Extra | What it pulls in | What it is for | Where in this plan |
| --- | --- | --- | --- |
| `mcp` | the MCP SDK | the client and server glue Phase 5 has been using | Days 33–45 |
| `toolbox` | `toolbox-adk>=1,<2` | ADK's client for MCP Toolbox for Databases | today, 🅿️ parked |
| `db` | `sqlalchemy>=2,<3`, `sqlalchemy-spanner` | database-backed sessions | Day 47 |
| `redis` | `redis>=4.2` | a Redis backend for sessions and memory | Day 47 territory |
| `e2b`, `daytona` | `e2b>=2,<3`, `daytona>=0.191` | disposable sandboxes for agent-written code | concept, later phases |
| `extensions` | `toolbox-adk`, `k8s-agent-sandbox` | the sandbox and toolbox integrations together | 🅿️ |
| `agent-identity` | two Google Cloud credential SDKs | machine identity for agents | 🅿️ — needs an account |
| `a2a` | the agent-to-agent protocol support | agent as peer, rather than agent as tool | Phase 13 |
| `eval`, `benchmark` | evaluation harnesses, `google-benchmark` | scoring behaviour rather than output | Phase 12 |
| `slack` | `slack-bolt>=1.22` | Slack-shaped intake for an agent | survey only |
| `antigravity` | `google-antigravity`, `protobuf>=6` | an integration with Google's agentic IDE | survey only |
| `otel-gcp` | OpenTelemetry export to Google Cloud | traces leaving the machine | 🅿️ — local OTel is free |
| `all` | everything above | never what you want in a project | — |

Three of those rows are worth a sentence more than the table gives them.

**`toolbox` is one package**, `toolbox-adk`, currently at version 1.4.0 (released 2026-09-01, PyPI,
read 2026-09-04). It is the ADK-side client, **not** the Toolbox server —
[4.1](4.1-the-server-you-did-not-write.md)'s binary is a separate download. Installing the extra
gives you a way to talk to a server you do not have.

**`db` is SQLAlchemy**, which is what `DatabaseSessionService` runs on. Nothing today needs it —
today's archive is `sqlite3` from the standard library, and `sqlite3` is not SQLAlchemy. Day 47 is
the day that row becomes real.

**`all` is a trap** and worth naming as one. It pulls in every cloud SDK, every sandbox provider and
every driver, which is a very large install, a very large supply-chain surface, and a `uv.lock` that
churns on somebody else's release schedule. It exists for the project's own test matrix.

## Why Sutra needs it

Because ADK-78 is an **awareness** row in the plan — the whole ID is "know these exist" — and because
an engineer who cannot place a framework's optional surface reaches for the wrong thing under
pressure.

The concrete version, today: when you decide in [4.2](4.2-who-writes-the-sql.md) not to adopt
Toolbox, `toolbox` is the extra you did not install, and knowing that it is one small package rather
than a large commitment is part of making that decision honestly. And when
[Day 47](../../../day-47-persistent-sessions/LESSON.md) needs a database-backed session service, `db`
is where it comes from — not from anything you write today, even though today is the database day.

## The mechanism

The list above is not something to trust from a document, including this one. It comes out of the
installed package:

```bash
grep -i "^Provides-Extra" .venv/Lib/site-packages/google_adk-2.7.1.dist-info/METADATA
```

**Line by line:**

- `Provides-Extra` is the metadata field a Python distribution uses to declare each extra it offers.
  Every extra appears on its own line, so the count is a `wc -l` away.
- The path names the **exact version**, `2.7.1`. That is deliberate: extras change between releases,
  so a list without a version attached is a list you cannot check.
- Reading it from `.venv` rather than from PyPI answers a different and better question — not "what
  does ADK offer" but "what does the ADK **in this repository** offer".

To see what an extra actually installs, read the requirements that are conditional on it:

```bash
grep -i "^Requires-Dist:.*extra ==" .venv/Lib/site-packages/google_adk-2.7.1.dist-info/METADATA \
  | grep -Ei "toolbox|db|redis|slack"
```

**Line by line:**

- `Requires-Dist` lines carry a marker after a semicolon. `; extra == "toolbox"` means *"install this
  only if the toolbox extra was requested"*.
- The second `grep` narrows to the four extras this part claims things about, so the output is
  checkable against the table rather than a wall.
- `-E` turns on extended regular expressions so `|` means alternation, and `-i` makes it
  case-insensitive because the field names are capitalised and the extra names are not.

That command, run on 2026-09-04, is where every entry in the "What it pulls in" column came from —
including the fact that `toolbox` is exactly one package and `db` is two.

🅿️ **Parked means parked.** Nothing in this part installs anything. `pyproject.toml` is unchanged by
today and `git diff pyproject.toml uv.lock` must be empty when the day ends. An extra becomes real on
the day something load-bearing needs it, and on that day it gets a pinned version and a dated row in
`docs/PACKAGES.md`.

## When it breaks

The failure mode of an extra is silence, and the way to see it is to ask the metadata about one that
does not exist:

```text
$ grep -i "^Provides-Extra: toolboxx" .venv/Lib/site-packages/google_adk-2.7.1.dist-info/METADATA
$ echo "exit: $?"
exit: 1
```

Nothing printed, exit code 1 — there is no such extra. That is the check, and the reason to run it
**before** typing the name into `pyproject.toml`: an extra name is a string in a bracket, nothing in
your editor spells it for you, and a name that matches nothing installs nothing extra while the
install itself succeeds. You then find out later, from an `ImportError` that names a class rather
than a missing extra — which is exactly the misdirection
[3.2](../03-the-adk-side/3.2-a-database-server-through-mcptoolset.md) met:

```text
ImportError: cannot import name 'McpToolset' from 'google.adk.tools.mcp_tool'
```

The other failure is `all`, and it is loud in a different way. It resolves, it installs, and your
lockfile now pins several cloud SDKs whose releases will show up in your dependency updates forever —
along with any advisory filed against any of them, on a project that uses none of them.

## In production

**What a professional writes instead:** extras named one at a time in `pyproject.toml`, each with a
comment saying which feature needs it, and a rule that adding one is a pull request with a ledger
row. The reviewable question is *"what stopped working without this?"*, and it should always have an
answer.

**What degrades at scale:** the dependency surface. Each extra is transitive dependencies you did not
choose, and on a team with several services the same extra gets added in three places at three
versions. The usual outcome is a monthly security scan reporting findings in an SDK nobody can
explain the presence of.

**The failure mode that only appears with real traffic:** an extra that only matters in the
deployment environment. `otel-gcp` is the classic — it is installed for production, not for local
work, so a mistake in its configuration cannot fail on a laptop. It fails on deploy, or worse, it
does not fail and simply exports nothing.

**The review comment a senior engineer leaves:** *"this adds `google-adk[all]`. That is fifty
packages to get one, and every one of them is now ours to patch. Name the extra you need."*

**The interview question:** *"how do you keep up with a framework that ships new capabilities every
month?"* *"With a map, not an install habit. I read the extras list off the installed distribution's
metadata rather than a blog post, because it is the honest statement of what this version offers —
ADK 2.7.1 has twenty-three. I can place them: `mcp` for the protocol work, `db` and `redis` for
session persistence, `e2b` and `daytona` for sandboxed code execution, `a2a` for agent-to-agent,
`eval` and `benchmark` for scoring behaviour, `toolbox` for the database server. What I do not do is
install them speculatively. An extra arrives the day something load-bearing needs it, pinned, with a
row in the package ledger saying which feature it is for — and `all` never arrives at all, because
that is fifty transitive dependencies I would then be responsible for patching."*

## Check yourself

```bash
grep -ci "^Provides-Extra" .venv/Lib/site-packages/google_adk-2.7.1.dist-info/METADATA
git diff --stat pyproject.toml uv.lock
```

The first prints how many extras your installed ADK offers. The second must print nothing at all —
today installs no package.
