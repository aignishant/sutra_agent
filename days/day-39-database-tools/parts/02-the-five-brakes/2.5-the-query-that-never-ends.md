# 2.5 — The query that never ends

## One-line answer

A row limit caps the answer and not the work, so a statement that has to look at a billion
combinations before returning five rows needs a separate brake — a budget the engine checks as it
runs, which aborts the statement rather than waiting for it.

## The story

The washing machine has a dial with numbers on it, and the numbers are the length of the cycle.

You put the clothes in, turn it to the short cycle, and it stops when the short cycle is over. Not
when the clothes are clean. If you overloaded it, or the stain was worse than you thought, it stops
anyway and hands you back damp, still-marked clothes, and you decide what to do next.

That sounds like a flaw and it is the most useful property the machine has. It means the bathroom is
free at a predictable time, the next person can plan, and a bad load costs you one cycle instead of
the whole evening. A machine that ran until the clothes were clean would be a machine that sometimes
never stopped, and you would find out which kind of load you had by waiting.

## The idea in plain language

`LIMIT 5` says *"stop giving me rows after five"*. It does not say *"stop working after five"*.

The gap between those is where a database gets stuck. Consider a query that joins a table to itself
three times. The archive has 205 rows. The engine has to consider 205 × 205 × 205 combinations —
about 8.6 million — and it does that work whether you asked for five rows or all of them, because it
cannot know which combinations produce the first five until it has produced them. Add a `WHERE`
clause that matches nothing and it will look at all 8.6 million and return zero.

This is not an exotic attack. It is what happens when a `JOIN` condition is written wrong, when a
`LIKE '%...%'` pattern cannot use an index, or when a table grew from a thousand rows to a million
and a query that was fine became quadratic.

So the brake has to be on **work**, not on output, and it has to be checked *during* the statement
rather than before it — you cannot tell how long a query will take by looking at it.

SQLite gives you two ways to do that, and they are different tools:

| Mechanism | What it counts | Who calls it |
| --- | --- | --- |
| `set_progress_handler(fn, n)` | virtual-machine steps, in batches of `n` | the engine, on the thread running the query |
| `Connection.interrupt()` | nothing — it is a signal | you, from another thread |

`set_progress_handler` is the one a tool wants, because it is self-contained: the statement carries
its own budget and enforces it without anybody watching. `interrupt()` is what you use when the
decision to stop comes from outside — a request that was cancelled, a shutdown.

A word on the phrase **virtual-machine step**. SQLite compiles a statement into a small program of
its own instructions, and executes that program. A step is one instruction. It is not a row, not a
comparison, and not a unit of clock time; it is a unit of work whose relationship to a second depends
on the machine. That has a consequence you have to state honestly: a step budget gives you a
*bounded* query, not a query bounded to a known duration.

## Why Sutra needs it

Because [Day 34's](../../../day-34-building-sutra-mcp-tools/LESSON.md) server answers over stdio and
Streamable HTTP, and a tool call that never returns is worse than one that fails. The caller sits
there. The client's own timeout eventually fires, the request is abandoned — and on a plain
connection, the query in the server **keeps running**, because nobody told it. You now have a server
burning a core on an answer nobody is waiting for, and the client retrying.

A step budget converts that into an error the tool can report, which is
[Day 21's](../../../day-21-errors-surface-not-swallow/LESSON.md) rule at the storage layer: the
failure surfaces rather than hanging.

## The mechanism

A counter, a callback, and a threshold:

```python
STEP_BUDGET = 1000
steps = 0


def budget() -> int:
    """Called every N virtual-machine steps; a non-zero return aborts the statement."""
    global steps
    steps += 1
    return 1 if steps > STEP_BUDGET else 0


con = sqlite3.connect("file:archive.sqlite3?mode=ro", uri=True)
con.set_progress_handler(budget, 1000)
```

**Line by line:**

- `set_progress_handler(budget, 1000)` asks the engine to call `budget` once every 1000 steps. The
  second argument is the sampling interval: smaller means finer control and more Python calls,
  larger means cheaper and coarser. It is not the budget.
- `budget` therefore fires at most `STEP_BUDGET` times before it starts refusing, so the real ceiling
  is `STEP_BUDGET × 1000` steps — a million here. Two numbers multiply, and confusing which is which
  is the commonest mistake with this API.
- The return value is inverted from what most people expect: **zero means continue**, non-zero means
  abort. A handler that forgets to return anything returns `None`, which is falsy, which means
  "continue" — so a broken budget silently does nothing.
- `steps` is a module-level counter reset by nothing, which is fine in a one-shot script and wrong in
  a server. In `sutra_mcp/db_tools.py` the counter belongs to the call, not to the module — a closure
  created per statement, so two concurrent calls do not share a budget. That is left as a
  `TODO(me)` in the build brief.
- The handler runs **on the thread executing the statement**, in between engine instructions. It must
  be cheap. Anything that logs, allocates or takes a lock in here is paid a thousand times a query.

The attack it is there for is one line:

```sql
SELECT a.id FROM tickets a, tickets b, tickets c
```

**Line by line:**

- Three table names separated by commas is a **cross join**: every row of `a` paired with every row
  of `b` paired with every row of `c`. It is legal, standard SQL, and nothing about it looks alarming.
- There is no `WHERE`. Nothing constrains the pairing, so the result is 205³ rows — about 8.6
  million — from a table of two hundred.
- There is no `LIMIT` either, but adding one would not help much: the engine still has to generate
  rows to return the first five, and a `WHERE` clause matching nothing would make it generate all of
  them.
- `SELECT a.id` returns one small column. The size of the *answer* tells you nothing about the size
  of the *work*, which is the whole reason this brake is separate from
  [2.4](2.4-a-ceiling-the-caller-cannot-raise.md).

## When it breaks

The budget fires and the statement dies. Real output from the day's brake lab:

```text
  5  step budget                     HELD    OperationalError: interrupted
```

The exception, verbatim:

```text
sqlite3.OperationalError: interrupted
```

One word. It does not say which statement, how many steps it used, or that a budget was involved at
all — and it is the **same** message `Connection.interrupt()` produces, so from the traceback alone
you cannot tell whether your budget fired or somebody cancelled the request. If you want to know,
you have to record it yourself in the handler before returning non-zero.

The failure that is worse than the exception is the handler that does nothing:

```text
  5  step budget                     FAILED  attack returned 8615125
```

Eight and a half million rows, returned successfully, after a long wait. That is what a handler
returning `None` gives you — and it is what you get by writing `if steps > STEP_BUDGET: return 1`
with no `else`, which is a shape reviewers read straight past.

## In production

**What a professional writes instead:** on a server database this is a **server-side timeout**, not
a client-side callback. Postgres has `statement_timeout`, set per role or per session, and the
database kills the query itself — which is strictly better, because it also protects against the
client that has crashed and cannot cancel anything. The SQLite progress handler exists because SQLite
has no server to do it.

**What degrades at scale or under concurrency:** a fixed step budget is a fixed budget on a machine
whose speed varies. The same number is generous on a developer laptop and tight on a throttled
container, so a query that always passed starts intermittently returning `interrupted` after a
deployment to smaller instances. Budgets need to be measured against the slowest machine you deploy
to, and reviewed when that changes.

**The failure mode that only appears with real traffic:** the timeout fires and the **retry** does
not have one. A client sees `interrupted`, retries the same expensive query, and now there are two of
them. Three retries later the database is doing four copies of the work that was already too much.
Any budget on the server needs a matching rule on the client that an expensive failure is not
retried unchanged — which is
[Day 44's](../../../day-44-client-hardening/LESSON.md) subject.

**The review comment a senior engineer leaves:** *"the progress handler returns 1 past the threshold
and falls off the end otherwise, so it returns None, which SQLite reads as continue. Return 0
explicitly. And the counter is module-level — two requests will share it."*

**The interview question:** *"you have a `LIMIT` on your database tool. Is that enough?"* *"No,
because `LIMIT` bounds the answer and not the work. A self-join over a small table is millions of
combinations and returns five rows, and a `LIKE '%x%'` on an unindexed column scans everything before
it can stop. So there are two brakes: a row cap for what comes back, and a work budget for what the
engine does. On SQLite that is `set_progress_handler`, which the engine calls every N instructions
and which aborts when it returns non-zero — the gotcha being that zero means continue, so a handler
that forgets to return says 'keep going'. On Postgres it is `statement_timeout` on the role, which is
better because the server enforces it even when the client is gone. And whatever the brake is, the
client must not retry the same expensive query, or one timeout becomes four."*
