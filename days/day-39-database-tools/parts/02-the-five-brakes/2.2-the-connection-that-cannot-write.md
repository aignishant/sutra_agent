# 2.2 — The connection that cannot write

## One-line answer

Opening the archive with `file:...?mode=ro` makes every write impossible at the engine level, which
means the refusal comes from the database rather than from your code, your prompt or anybody's good
intentions.

## The story

The office has one shared computer near the door, and it has two logins.

Yours has your files on it. The other one is called Guest, and it has no password, because the whole
point is that the courier can use it to print a docket without waiting for somebody to come and
unlock a machine.

Guest can open things. Guest can print. What Guest cannot do is save into the shared folder, install
anything, or delete a file — not because there is a note taped to the monitor asking people not to,
but because the account does not have permission and the machine simply says no.

Nobody has to trust the courier. Nobody has to watch. Nobody has to remember to check afterwards.
The limit is not a rule about behaviour; it is a property of the account, and it holds on the days
when everyone is careless and in a hurry.

## The idea in plain language

`sqlite3.connect("archive.sqlite3")` opens the file for **reading and writing**, always. That is the
default, and it is the only mode that plain path form offers.

SQLite also accepts a path in **URI form**: a string starting with `file:` that can carry options
after a `?`, the way a web address carries query parameters. The option that matters here is
`mode=ro`.

- `mode=ro` — read-only. The engine refuses every statement that would change the file.
- `mode=rw` — read and write, but the file must already exist.
- `mode=rwc` — read, write, and create if missing. This is what the plain path form does, and it is
  why [1.2](../01-the-archive/1.2-one-file-one-engine.md)'s typo silently produced an empty database.

The important word is **engine**. This is not your function checking the statement and deciding to
decline. The check happens inside SQLite, below every statement, on a connection that was opened
without the capability in the first place. There is no argument, no prompt, no clever phrasing and
no model behaviour that gets past it, because there is nothing there to persuade.

That is the shape of a real brake, and it is worth naming the general rule, because the rest of the
day is applications of it: **a limit enforced by the thing being limited beats a limit enforced by
the thing doing the asking.** [Day 16](../../../day-16-built-in-tools-with-brakes/LESSON.md) made
the same argument about built-in tools; this is what it looks like with a database behind it.

One thing `mode=ro` does not do, and it matters: it does not stop a read from being wrong or huge.
The `OR` attack in [2.1](2.1-the-argument-that-became-syntax.md) returned closed tickets through a
read-only connection quite happily, because reading is exactly what it was allowed to do. Brakes are
not interchangeable. Each one stops one class of thing.

## Why Sutra needs it

Because `sutra_mcp/db_tools.py` serves reads to callers you do not control, and the archive is one
file that a `DELETE` would empty in a single statement.

There is a second reason that is easy to miss. A read-only connection turns a whole category of
future mistakes into loud failures at development time. The day somebody adds a "helpful" write to a
read tool, it does not quietly work — it raises, in their own test run, with a message that names
exactly what happened. The brake is also a design constraint, and it holds the design in place after
you have stopped watching it.

## The mechanism

Two lines, and the second one is the whole feature:

```python
import sqlite3
from pathlib import Path

ARCHIVE = Path("sutra/data/tickets.sqlite3")


def connect_readonly() -> sqlite3.Connection:
    """Open the archive so that no statement can change it."""
    return sqlite3.connect(f"file:{ARCHIVE.as_posix()}?mode=ro", uri=True)
```

**Line by line:**

- `f"file:{...}"` builds a URI rather than a path. The `file:` prefix is what tells SQLite to parse
  the rest as a URI with options, instead of treating the whole thing as a filename that happens to
  contain a question mark.
- `ARCHIVE.as_posix()` writes the path with forward slashes even on Windows. A URI is not a Windows
  path: backslashes are not separators in it, and `file:sutra\data\tickets.sqlite3` fails to resolve.
- `?mode=ro` is the option. Everything after the `?` is parsed by SQLite, not by your filesystem.
- `uri=True` is the argument people forget, and forgetting it is silent. Without it, `sqlite3` treats
  the entire string — `file:`, `?mode=ro` and all — as a **filename**, creates a file with that
  literal name in your working directory, and hands you a connection to an empty database. No error.
  Your tools then return zero rows forever and you go looking at your data.
- The function returns the connection and nothing else. Making this the only place in the module that
  calls `sqlite3.connect` is what makes the brake auditable — one line to read, rather than four
  call sites to keep consistent.

The archive builder is the one place that must still write, so it opens the plain way:

```python
def build_archive(path: Path = ARCHIVE) -> Path:
    """Create the archive. The only writer in the module, and it is not a tool."""
    path.parent.mkdir(parents=True, exist_ok=True)
    con = sqlite3.connect(path)  # read-write on purpose; never reachable from a tool
    try:
        con.executescript(SCHEMA)
        con.commit()
    finally:
        con.close()
    return path
```

**Line by line:**

- `sqlite3.connect(path)` with no URI is read-write-create, which is correct here: something has to
  make the file.
- The comment is doing real work. The next person to read this file needs to know that the
  asymmetry is deliberate, or they will "fix" the inconsistency.
- `build_archive` is **not** registered as a tool. That is the actual containment: the writing
  capability exists in the module but has no path to the wire. A capability nothing can call is not a
  capability an agent has.
- `mkdir(parents=True, exist_ok=True)` creates `sutra/data/` on a fresh clone, where it does not
  exist because the directory only ever held a generated file and git does not track empty
  directories.

## When it breaks

Ask a read-only connection to write, and the engine answers. This is real output from the day's
brake lab:

```text
  2  connection mode=ro              HELD    OperationalError: attempt to write a readonly database
```

The full exception, verbatim:

```text
sqlite3.OperationalError: attempt to write a readonly database
```

Three things about that message. It comes from SQLite itself, not from `sqlite3` and not from your
code. It says *readonly database*, not *readonly connection*, which misleads people into checking
file permissions — the file is perfectly writable, the connection is not. And it is raised at
`execute` time, not at `connect` time, so a read-only connection opens successfully and fails on the
first write, which is exactly what you want in a tool and exactly what surprises people in a script.

The other failure has no message at all. Forget `uri=True`:

```text
>>> con = sqlite3.connect("file:archive.sqlite3?mode=ro")
>>> con.execute("SELECT COUNT(*) FROM tickets").fetchone()
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
sqlite3.OperationalError: no such table: tickets
>>> import os; [p for p in os.listdir('.') if p.startswith('file:')]
['file:archive.sqlite3?mode=ro']
```

There is now a file on disk whose name is the URI. It is a valid, empty, writable database, and every
tool pointed at it returns nothing and reports success.

## In production

**What a professional writes instead:** on a real database, the brake is not a connection flag — it
is a **database role**. The agent's tools connect as a user that was granted `SELECT` on two tables
and nothing else, with a separate connection string kept in a secret manager, and the read-write role
is used only by migrations and the ingestion job. Same principle, enforced by the server, and it
survives a code change in a way a connection argument does not.

**What degrades at scale or under concurrency:** read-only is not read-*cheap*. A read-only
connection can still hold a read transaction that blocks a writer — measured in
[6.1](../06-in-production/6.1-the-connection-you-do-not-hold.md) — and it can still run a query that
scans the whole table. Teams that add `mode=ro` and then remove the row limit have swapped a
data-loss risk for an availability risk.

**The failure mode that only appears with real traffic:** a maintenance script run by hand, from a
laptop, at 2am, with the read-write connection string in the shell history because "it's just this
once". The brake is on the tool path and the incident comes through the human path, which is why the
role and the audit log matter more in the long run than the flag.

**The review comment a senior engineer leaves:** *"`connect_readonly` is right, and there are three
other `sqlite3.connect` calls in this file. Every one of them is a place someone will forget. One
connection helper, and the writer gets a name that says it is not a tool."*

**The interview question:** *"your agent has a database tool. How do you stop it writing?"* *"Not in
the prompt, and not with a check inside the tool — both of those are code I have to keep correct
forever. I take the capability away at the connection: read-only URI on SQLite, or a database role
with SELECT on two tables and nothing else on a real server. Then the refusal comes from the engine,
with `attempt to write a readonly database`, on a path that no prompt and no clever argument can
reach. The thing I would flag is that it is one brake, not the brake — it stops writes and it does
nothing at all about a read that returns the wrong rows or forty thousand of them. Those need
different brakes, and we counted five."*
