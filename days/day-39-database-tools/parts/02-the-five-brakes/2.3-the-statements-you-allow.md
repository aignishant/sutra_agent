# 2.3 — The statements you allow

## One-line answer

SQLite lets you install a callback the engine consults **while compiling** every statement, so you
can name the small set of operations a read tool is allowed to perform and have everything else —
including reads of files you never mentioned — refused before a single row is touched.

## The story

The hotel gives you a plastic card at check-in.

It opens your room. It opens the gym on the second floor, because that came with the rate. Held
against the reader on the fourth floor it produces a red light and a small unhappy beep, and held
against the door marked *Staff Only* it does the same.

The reader is not deciding whether you look like the kind of person who should be on the fourth
floor. It has a list of what this card opens, the list has two things on it, and the fourth floor is
not one of them. A card that opened everything except a short list of forbidden doors would be a
different and much worse arrangement, because the day somebody builds a new door, it opens.

## The idea in plain language

An **allowlist** — sometimes called a whitelist — names what is permitted and refuses everything
else. A **denylist** names what is forbidden and permits everything else. They sound symmetrical and
they are not: a denylist has to be complete to be correct, and it is never complete, because
tomorrow there is a new thing nobody wrote down.

`mode=ro` from [2.2](2.2-the-connection-that-cannot-write.md) is already an allowlist of a coarse
kind: reads yes, writes no. But "reads" is a big word. A read-only connection will still happily let
a statement do things a search tool has no business doing:

- `ATTACH DATABASE 'other.sqlite3' AS other` — open a **second** database file and query across it.
- `SELECT * FROM sqlite_master` — read the whole schema, including tables your tool never mentions.
- `PRAGMA database_list` — report where the file actually is on disk.

None of those is a write. All of them are reads. A statement that attaches another file and selects
from it is, on a read-only connection, entirely legal.

SQLite's answer is the **authorizer**: a Python function you register on a connection, which the
engine calls once for every operation it is about to compile into a statement. It is handed an
integer action code — `SQLITE_SELECT`, `SQLITE_READ`, `SQLITE_ATTACH`, `SQLITE_DROP_TABLE` and about
thirty more — plus the names involved. You return one of three constants:

| Return | Meaning |
| --- | --- |
| `sqlite3.SQLITE_OK` | allow this operation |
| `sqlite3.SQLITE_DENY` | refuse, and fail the whole statement |
| `sqlite3.SQLITE_IGNORE` | allow the statement but blank out this piece — a column reads as `NULL` |

The word **compile** is the important one. The authorizer runs while the statement is being prepared,
before any row is read, so a denied statement never executes at all rather than being stopped halfway
through.

## Why Sutra needs it

Because the read-only brake and the binding brake between them still leave a hole exactly the size of
"a read you did not intend".

Sutra's archive lives in `sutra/data/`. On the same machine there will eventually be a sessions
database ([Day 47](../../../day-47-persistent-sessions/LESSON.md)) and whatever else a deployment
puts beside it. A tool that can `ATTACH` is a tool whose blast radius is the whole directory, not the
one file you pointed it at — and no amount of parameter binding narrows it, because `ATTACH` needs no
injection to be reached. It only needs a tool that accepts SQL, which is precisely what
[4.2](../04-toolbox-parked/4.2-who-writes-the-sql.md) asks you to decide about.

## The mechanism

The callback, and the set it enforces:

```python
import sqlite3

ALLOWED = {sqlite3.SQLITE_SELECT, sqlite3.SQLITE_READ, sqlite3.SQLITE_FUNCTION}


def authorizer(action, arg1, arg2, db_name, trigger):
    """SQLITE_OK for the allowed operations, SQLITE_DENY for everything else."""
    return sqlite3.SQLITE_OK if action in ALLOWED else sqlite3.SQLITE_DENY


con = sqlite3.connect("file:archive.sqlite3?mode=ro", uri=True)
con.set_authorizer(authorizer)
```

**Line by line:**

- `ALLOWED` is a set of three integer constants, and it is short on purpose. `SQLITE_SELECT`
  authorises a `SELECT` statement as a whole; `SQLITE_READ` authorises reading one specific column of
  one specific table; `SQLITE_FUNCTION` authorises calling a function such as `substr` or `COUNT`.
  Between them, a search tool can do its entire job.
- Everything not in that set is denied — including operations that do not exist yet, in a SQLite
  version you have not installed. That is the property a denylist cannot have.
- The callback takes exactly five arguments and their meaning depends on the action. For
  `SQLITE_READ`, `arg1` is the table name and `arg2` is the column; for `SQLITE_ATTACH`, `arg1` is
  the filename. This is why a stricter authorizer can allow reads of `tickets` and deny reads of
  everything else, which is the natural next step once you have the shape.
- `db_name` is the attached database the operation touches (`main` for the file you opened) and
  `trigger` is the name of the trigger or view it came from, or `None`. Both are how you would refuse
  an operation that arrives through a view rather than directly.
- `set_authorizer` installs it on **one connection**. It is not global, so a maintenance script with
  its own connection is unaffected — and a second connection you forgot about is unguarded, which is
  the argument for having exactly one place that opens connections.
- Returning `SQLITE_DENY` fails the statement with an exception. Returning `SQLITE_IGNORE` is
  quieter and much more dangerous for a tool: the statement succeeds and a column silently reads as
  `NULL`, so the model gets an answer that is wrong rather than an error it can report.

To turn it off — for a maintenance path, never for a tool — pass `None`:

```python
con.set_authorizer(None)
```

**Line by line:**

- Passing `None` removes the callback entirely, restoring the default of allowing everything the
  connection mode permits. There is no "temporarily relax" option, which is a good thing: relaxing is
  a decision that should be visible in a diff.

## When it breaks

Ask the guarded connection to open a second database. Real output from the day's brake lab:

```text
  3  authorizer allowlist            HELD    DatabaseError: not authorized
```

The exception in full:

```text
sqlite3.DatabaseError: not authorized
```

That is the entire message. It does not say which operation was refused, which table it involved, or
which line of your allowlist was responsible. When a legitimate query starts failing with it — and
it will, the first time somebody adds a `JOIN` onto a table you did not think about — the only way to
find out what happened is to log from inside the callback:

```python
def authorizer(action, arg1, arg2, db_name, trigger):
    ok = action in ALLOWED
    logging.getLogger("sutra.db").debug("authorizer action=%s arg1=%s allow=%s", action, arg1, ok)
    return sqlite3.SQLITE_OK if ok else sqlite3.SQLITE_DENY
```

**Line by line:**

- The log line goes in **before** the return, so it records the denials as well as the allowances.
  A callback that only logs failures cannot tell you which of six operations in a statement was the
  one that stopped.
- `action` is printed as a bare integer, because that is what SQLite passes. Look it up against the
  `sqlite3.SQLITE_*` constants; there is no built-in name lookup, and writing one is a reasonable
  `TODO(me)`.
- `logging` rather than `print`, because on a stdio MCP server anything written to standard output is
  a protocol message — the rule
  [Day 33](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md) spent a
  part on.
- `debug` rather than `info`: this fires several times per statement, and at `info` it will bury
  every other line in your log within a day of real traffic.

## In production

**What a professional writes instead:** on Postgres or MySQL there is no authorizer callback, and
you do not want one — the equivalent is done properly by the server. You `GRANT SELECT` on exactly
the tables the tool needs to a role that owns nothing, and you `REVOKE` everything else. The
authorizer is SQLite's way of getting the same property in a database that has no user accounts,
because the whole engine is running inside your process.

**What degrades at scale:** the callback is Python, and it is called several times per statement —
once for the statement, once per column read, once per function. On a query touching many columns in
a tight loop this is measurable. It is not a reason to skip it on a tool path serving a handful of
requests; it is a reason not to leave it installed on a bulk import connection.

**The failure mode that only appears with real traffic:** the allowlist is written against the
queries that exist today. Somebody adds a `JOIN` on the knowledge-base table, the authorizer denies a
`SQLITE_READ` on a column nobody listed, and the tool starts returning `not authorized` for one
question in twenty — reported by a customer, not by a test, because the test corpus does not contain
that question.

**The review comment a senior engineer leaves:** *"`SQLITE_IGNORE` is not a softer `SQLITE_DENY`. If
you return it, the query succeeds and the column comes back NULL, and the model will report that as
a fact. Deny loudly or allow."*

**The interview question:** *"read-only is not enough. What else?"* *"Read-only stops writes and
nothing else, and 'reads' is a much bigger set than people picture — a read-only connection will
still attach a second database file and query across it, and it will still read the whole schema. On
SQLite I install an authorizer, which is a callback the engine consults while compiling each
statement, and I allow three operations: SELECT, READ and FUNCTION. Everything else is denied,
including operations that do not exist yet, which is the point of allowing rather than forbidding.
On a real server I would not do this in the client at all — it is a database role with GRANT SELECT
on two tables. The thing to watch is that the error text is just `not authorized`, with no detail, so
you log the action code from inside the callback or you will be guessing."*
