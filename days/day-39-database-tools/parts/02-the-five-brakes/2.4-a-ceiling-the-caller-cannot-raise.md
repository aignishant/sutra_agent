# 2.4 — A ceiling the caller cannot raise

## One-line answer

The row limit must be applied in the SQL the server owns and clamped in the server's own code, so
that a caller asking for a thousand rows gets your maximum and a correct answer rather than an
argument about it.

## The story

The parcel counter at the post office has a scale bolted to the desk.

You bring your box, the clerk puts it on the scale, and the number on the display decides which
service you are allowed to use. There is a printed sheet taped to the glass with the limits on it,
and above a certain weight the counter simply does not accept the parcel for that service.

You cannot explain your way past the scale. You cannot ask the clerk to enter a lighter figure. You
can repack the box, which is a real option and the one the sheet is quietly encouraging, but the
number in the system is the number the scale produced.

The scale is not there because customers lie about weight. It is there because a number that anybody
can type is not a measurement, and a limit that anybody can raise is not a limit.

## The idea in plain language

`LIMIT` in SQL caps how many rows a statement returns. `SELECT id FROM tickets LIMIT 5` gives you at
most five rows, whatever the table holds.

The question that matters is not whether you use `LIMIT`. It is **who decides the number**, and there
are three answers with very different consequences.

**The caller decides, in the SQL.** This is the hallway tool from
[1.3](../01-the-archive/1.3-a-door-not-a-hallway.md): the limit is part of the statement the caller
supplied, so there is no limit — a caller who does not want one simply does not write one.

**The caller decides, as an argument.** `search_tickets(term, limit)` where `limit` goes straight
into the query. Better, because the caller cannot remove the clause, but they can still pass 50 000,
and a model that has decided it needs "all of them" will.

**The server decides, using the caller's number as a request.** The tool takes `limit`, clamps it
into a range the server chose, and binds the clamped value. The caller's number is an input to the
decision and not the decision. This is the only version that is a brake.

The subtlety worth being precise about: the clamp goes in **two** places, and they do different jobs.
`min(limit, MAX_ROWS)` in Python stops a huge number from ever reaching the engine. `LIMIT ?` in the
SQL stops the engine from building a huge result in the first place. Doing only the Python clamp on a
statement with no `LIMIT` means the engine still materialises every matching row and you throw most
of them away — you paid the cost and got the protection nobody asked for.

There is a third thing the tool should return and almost nobody does: a **truncation flag**. If the
answer was cut, the caller needs to know that, or a model will confidently report "there are five
such tickets" when there are two hundred.

## Why Sutra needs it

Because [5.1](../05-failure-lab/5.1-forty-thousand-rows.md) measures what one missing ceiling costs:
a single unbounded search over a forty-thousand-row archive produces a result that is **173% of the
model's entire input window**. Not slow — impossible. The request cannot be sent.

And because the caller here is not a person. It is a model, filling in an integer field of a JSON
schema, having read a docstring that said "from 1 to 5". It will sometimes send 99. That is not
misbehaviour, it is a probability distribution, and a system that only works when the number is
sensible does not work.

## The mechanism

The clamp, the bound limit, and the flag that tells the truth about both:

```python
MAX_ROWS = 5


def search_tickets(term: str, limit: int = 3) -> dict:
    """Search the ticket archive for a symptom and return matching tickets.

    Args:
        term: words from the symptom, for example "logged out".
        limit: how many tickets to return, from 1 to 5.
    """
    capped = max(1, min(int(limit), MAX_ROWS))
    con = connect_readonly()
    try:
        rows = con.execute(
            "SELECT id, title, substr(body, 1, 160) FROM tickets "
            "WHERE body LIKE ? OR title LIKE ? LIMIT ?",
            (f"%{term}%", f"%{term}%", capped + 1),
        ).fetchall()
    finally:
        con.close()
    return {
        "status": "ok",
        "tickets": [{"id": r[0], "title": r[1], "snippet": r[2]} for r in rows[:capped]],
        "truncated": len(rows) > capped,
    }
```

**Line by line:**

- `MAX_ROWS = 5` is a module constant, so the ceiling is one name in one place and shows up in a diff
  when it moves. A magic number inside the function is a ceiling nobody can find.
- `max(1, min(int(limit), MAX_ROWS))` clamps from both ends. `min` handles 99. `max(1, ...)` handles
  0 and -3, which produce a `LIMIT` of zero or an error respectively, neither of which is what
  anybody meant.
- `int(limit)` is not paranoia. The value arrives from a JSON payload, and a model that emits
  `"limit": "5"` as a string is a thing that happens; without the cast, `min("5", 5)` raises
  `TypeError: '<' not supported between instances of 'int' and 'str'` and the tool fails on a request
  that was almost right.
- `LIMIT ?` puts the cap in the statement, so the engine stops after that many rows rather than
  finding them all and letting Python discard the rest.
- `capped + 1` asks for **one row more than you will return**. That extra row is the entire truncation
  detector: if it came back, there was more.
- `rows[:capped]` throws the probe row away before it reaches the caller. Forgetting this slice is a
  quiet off-by-one that returns six rows from a tool documented to return five.
- `"truncated": len(rows) > capped` is the honest flag. It is `True` exactly when the probe row
  arrived, and it is the difference between a model saying *"there are five"* and *"here are five of
  them"*.
- `substr(body, 1, 160)` trims each body to 160 characters in the **engine**, not in Python. Cutting
  in Python means the whole body crossed the process boundary before you shortened it, which on
  forty thousand rows is exactly the cost you were trying to avoid.
- `try/finally` closes the connection on every path, including the one where the statement raises —
  the discipline [6.1](../06-in-production/6.1-the-connection-you-do-not-hold.md) explains the reason
  for.

What the docstring says about `limit` matters as much as the clamp, and it is the part reviewers
skip. `from 1 to 5` is what a model reads before choosing a number; the clamp is what happens when it
chooses anyway.

## When it breaks

Ask for more than the ceiling and watch the ceiling hold. Real output from the day's brake lab,
against an archive of 205 tickets:

```text
  4  server-side LIMIT               HELD    201 matched, 5 returned
```

Two hundred and one rows matched the search term. Five came back. There is no error, no warning and
no complaint — a brake that holds correctly is invisible, which is why it needs a test that can go
red rather than a reviewer's memory.

Now the version that breaks. Pass the caller's number through without clamping, and let a model send
its favourite large integer:

```text
>>> search_tickets("log", limit=99)
{'status': 'ok', 'tickets': [ ... 99 entries ... ], 'truncated': True}
```

Still no error. That is the point. It is 99 tickets, each with a 160-character snippet, arriving in a
model's context because an integer field had no ceiling — roughly twenty times the payload the tool
was designed around, reported as a success.

And the failure that is genuinely loud, from forgetting `int()`:

```text
Traceback (most recent call last):
  File "sutra_mcp/db_tools.py", line 41, in search_tickets
    capped = max(1, min(limit, MAX_ROWS))
                    ^^^^^^^^^^^^^^^^^^^^
TypeError: '<' not supported between instances of 'str' and 'int'
```

The tool call fails, the model sees an error it cannot fix by rephrasing, and the request is burnt.
A string where an integer was declared is not a rare event when the caller is a language model.

## In production

**What a professional writes instead:** a ceiling plus a **cursor**. Real tools do not just truncate,
they return an opaque continuation token so a caller that genuinely needs the next page can ask for
it — the same shape as
[Day 32's](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md)
state handles, and for the same reason: the caller carries the position, the server holds nothing.
Truncation without a way forward is a tool that quietly cannot answer some questions.

**What degrades at scale:** `LIMIT` without `ORDER BY` is not stable. SQLite is free to return any
five matching rows and to return different ones next time, because you never said which five you
wanted. On a small archive it looks deterministic and it is not; the fix is to order by something
unique — `ORDER BY opened_on DESC, id` — and to accept that ordering a large unindexed result costs
more than the scan did.

**The failure mode that only appears with real traffic:** the ceiling is fine and the **snippet** is
not. Five rows of a 40 KB body each is 200 KB, which is a ceiling on rows doing nothing about a
ceiling on bytes. Production tools cap both, and the byte cap is the one people add after an
incident.

**The review comment a senior engineer leaves:** *"`LIMIT 5` with no `ORDER BY` means 'five of them,
we don't say which'. Add the order, and add the flag — a truncated result that does not say so is a
model telling a customer there are five tickets when there are two hundred."*

**The interview question:** *"how do you keep a database tool from flooding the context window?"*
*"The ceiling has to be the server's, not the caller's. The caller's `limit` is a request: I clamp it
into a range in code, bind the clamped number into `LIMIT ?` so the engine stops early rather than
building the whole result, and I ask for one row more than I return so I can tell the caller
honestly that it was truncated. Two details people miss. Trim the text columns in SQL with `substr`,
because a row cap is not a byte cap and a body can be forty kilobytes. And put an `ORDER BY` on it —
`LIMIT` without one means 'some of them', which is not reproducible. We measured the version with no
ceiling: forty thousand rows serialised to about 1.7 million tokens, which is 173% of the window, so
the request could not be sent at all."*
