# 2.1 — 💥 The argument that became syntax

## One-line answer

If a tool argument is pasted into a SQL string, the caller is no longer supplying a value — it is
supplying part of the statement — and the first thing that buys an attacker is not a deleted table
but a **silently wrong answer** that walks straight past your filters.

## The story

You hand your clothes over the counter at the laundry with a list.

The list is a scrap of paper: *3 shirts, 2 trousers*. The man behind the counter reads it out as he
counts the pile, and whatever is written on the line, he does. That is the arrangement, and it has
worked for years, because a laundry list is a list of clothes and everyone knows it.

One afternoon somebody hands in a list that reads: *3 shirts, 2 trousers, and the bag from rack 4*.

He reads the line out. He counts three shirts. He counts two trousers. He fetches the bag from rack
4 and puts it on the counter, because it was on the line, and the line is what he does.

He was not tricked into breaking a rule. There was no rule. The paper was always a set of
instructions, and everybody had simply assumed it would only ever contain clothes.

## The idea in plain language

**SQL injection** is what happens when text that was meant to be a *value* ends up being read as
*syntax*.

Every SQL statement is text. If you build that text by pasting a caller's argument into it, then the
caller's argument is text in your statement, and the engine has no way to tell the two apart — it
does not know which characters came from you and which came from a stranger. It just parses what it
was handed.

The word "attacker" makes this sound like a rare, targeted event. It is not. For a support desk, the
text arriving in a tool argument comes from three places, and two of them are outside your control:

- what a user typed into the chat;
- what a model decided to pass along, having read a ticket somebody else wrote;
- what a previous tool returned, which was also text somebody else wrote.

So the failure does not need a villain. It needs a ticket body with an apostrophe in it — *"the
customer's export"* — and your statement stops parsing.

The fix has been the same since the 1990s and has nothing to do with escaping quotes. **Send the
value beside the statement rather than inside it.** You write the SQL with a `?` where the value
goes, hand the value over separately, and the engine compiles the statement first and then binds the
value into the finished plan. A bound value cannot become syntax, because by the time it arrives,
parsing has already happened.

## Why Sutra needs it

Because `sutra_mcp/db_tools.py` is a tool on a wire, and the whole point of
[Day 34's](../../../day-34-building-sutra-mcp-tools/LESSON.md) server is that other people's clients
call it. The `term` argument of `search_tickets` is, by design, a string chosen by somebody who is
not you.

And because the eval you write today —
[6.3](../06-in-production/6.3-the-audit-that-reads-your-file.md) — refuses to go green while any
statement in that file is built by formatting. This is the one brake the audit checks by parsing
your source rather than by pattern-matching it, precisely because it is the one people
re-introduce when they are in a hurry.

## The mechanism

Two functions, same argument, same database. Only the way the argument reaches the engine differs:

```python
def formatted(con, term: str) -> list[tuple[str, str]]:
    """Build the SQL by pasting the argument into it. This is the bug."""
    sql = (
        "SELECT id, status FROM tickets WHERE status = 'open' AND body LIKE '%" + term + "%'"
    )
    return con.execute(sql).fetchall()


def bound(con, term: str) -> list[tuple[str, str]]:
    """Send the argument beside the SQL, never inside it."""
    sql = "SELECT id, status FROM tickets WHERE status = 'open' AND body LIKE ?"
    return con.execute(sql, (f"%{term}%",)).fetchall()
```

**Line by line:**

- In `formatted`, `term` is concatenated into `sql`. By the time `execute` sees it there is one
  string, and nothing in it records which characters came from the caller. An f-string, a `%` format
  and a `+` are all the same bug; the audit in
  [6.3](../06-in-production/6.3-the-audit-that-reads-your-file.md) looks for all three.
- Look at where the quotes are in `formatted`: the caller's text lands **between two single
  quotes** that you wrote. So a single quote inside `term` closes your string early, and everything
  after it is parsed as more SQL.
- In `bound`, the SQL contains `?` and nothing else. That string is a constant — it is identical on
  every call, whatever the caller sends.
- `con.execute(sql, (f"%{term}%",))` passes a **tuple** of values. The `%` wildcards are added in
  Python, around the value, before it is handed over. That matters: the wildcards belong to the
  `LIKE` pattern, which is a value, so they go in the value and not in the statement.
- The trailing comma in `(f"%{term}%",)` makes it a one-element tuple. Without it Python has a plain
  string, and `sqlite3` raises `ValueError: parameters are of unsupported type`.
- Both functions filter `status = 'open'`. Hold on to that. It is the filter the attack is going to
  walk through.

Now the arguments. The honest one is what a user types; the hostile one is what a string of text can
be:

```python
HONEST = "logged out"
HOSTILE = "zz%' OR id LIKE '%"
STACKED = "zz'; DROP TABLE tickets; --"
```

**Line by line:**

- `HONEST` is what the tool was built for. Both functions handle it identically, which is what makes
  the bug survive review: on the happy path there is no difference to see.
- `HOSTILE` is the interesting one and it destroys nothing. `zz%'` closes the string you opened,
  `OR id LIKE '%` starts a new condition and re-opens a string that your own trailing `%'` closes.
  The result is a syntactically perfect statement whose `WHERE` clause is now
  `status = 'open' AND body LIKE '%zz%' OR id LIKE '%%'` — and in SQL, `AND` binds tighter than `OR`,
  so the whole thing means *"(open and matches zz) **or** (id matches anything)"*. Every row
  qualifies.
- `STACKED` is the one everybody pictures: a second statement smuggled in behind a semicolon, with
  `--` starting a comment so the rest of your line is ignored. It is also the least dangerous of the
  three here, for a reason the run below makes obvious.

## When it breaks

This is the real output, run on 2026-09-04:

```text
seeded archive.sqlite3: 5 tickets, 2 kb articles
tickets: 5 total, 2 of them closed and out of scope

honest argument: 'logged out'
  formatted -> 1 rows [('4521', 'open')]
  bound     -> 1 rows [('4521', 'open')]

hostile argument: "zz%' OR id LIKE '%"
  formatted -> 5 rows [('4521', 'open'), ('4522', 'open'), ('4610', 'closed'), ('4633', 'open'), ('4701', 'closed')]
  bound     -> 0 rows []

and a second statement smuggled into the same argument:
  formatted -> ProgrammingError: You can only execute one statement at a time.
  bound     -> 0 rows
```

Four things in that transcript are worth reading slowly.

**The honest argument proves nothing.** One row, both ways, identical. Every test you would think to
write passes against the broken function.

**The hostile argument did not error.** It returned five rows and an exit code of zero. The tool
reported success. A model reading that result has no way to know anything went wrong, and neither
does your log.

**Two of those five rows say `closed`.** The function's SQL says `status = 'open'`, in your source,
in git. The filter is still there. It was simply outvoted by an `OR` that a caller supplied, and the
tool handed a model two tickets it was written to hide. **That** is the ordinary shape of injection:
not destruction, but a filter quietly stopping applying.

**The stacked statement was blocked by the driver, not by your care.** The error text is exact:

```text
sqlite3.ProgrammingError: You can only execute one statement at a time.
```

`sqlite3.Connection.execute` compiles a single statement and refuses a second one. That is a real
protection and it is worth almost nothing, because it stops only the loudest attack while the quiet
one — the `OR` that changes an answer — sails through. Do not let it comfort you: `executescript`
has no such limit, and neither does the equivalent call in most other drivers.

## In production

**What a professional writes instead:** every statement a constant, every value bound, no exceptions
and no "just this once for the table name". Where an identifier genuinely must vary — a table name,
a sort column — it is chosen from a hard-coded allowlist in Python and never interpolated from
caller text, because identifiers **cannot** be bound and that is exactly why they are the remaining
soft spot.

**What degrades at scale:** nothing degrades — and that is the problem. A formatted statement is
just as fast and just as correct on the happy path forever. There is no performance signal, no error
rate, and no alert. The only thing that finds it is reading the code, which is why
[6.3](../06-in-production/6.3-the-audit-that-reads-your-file.md) parses the file instead of trusting
a reviewer to catch it on a Friday.

**The failure mode that only appears with real traffic:** the apostrophe. Long before anyone attacks
you, a customer writes *"the export won't open"* into a ticket, a search passes that text to a
formatted statement, and you get `sqlite3.OperationalError: near "t": syntax error` on one row in
ten thousand. Teams patch that by stripping quotes from user input, which fixes the crash, keeps the
vulnerability, and corrupts the data.

**The review comment a senior engineer leaves:** *"this f-string builds a WHERE clause out of a tool
argument. It is not the DROP TABLE I mind — the driver blocks that. It is that `status='open'` in
this function is now advisory. Bind the value."*

**The interview question:** *"walk me through SQL injection in an agent tool."* *"The mechanism first:
if the argument is concatenated into the statement, the engine cannot tell your text from the
caller's, so a value becomes syntax. What I would emphasise is what it actually buys, because people
picture DROP TABLE and that is the rare case — most drivers only compile one statement anyway. We
ran it: a search tool that filtered to open tickets, given one crafted term, returned every row in
the table including the closed ones, with no error and a success status. The filter was still in the
source; it had just been outvoted by an OR the caller supplied. And the trigger in a support system
is not usually an attacker, it is a ticket body with an apostrophe in it. The fix is binding, the
statement stays a constant, and we enforce it by parsing our own source for formatted SQL rather
than trusting review."*
