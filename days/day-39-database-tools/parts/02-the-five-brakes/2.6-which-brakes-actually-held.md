# 2.6 — Which brakes actually held

## One-line answer

Each of the five brakes was handed the attack it exists to stop, and all five held — while the thing
most teams reach for first, the sentence *"this tool is read-only"* in the description, stopped
nothing at all.

## The story

You are buying a used car, and the mechanic you brought along does not look at the brakes.

He drives it. He takes it up the service road, gets it to a decent speed and puts his foot down
hard, and again on the gravel, and once more from slow with the wheel turned. Then he pulls the
handbrake on the slope outside the shop and lets go of everything to see whether it holds.

The seller had already told you the brakes were serviced last month, and produced a bill for it. The
mechanic did not argue with the bill. He simply did not treat it as evidence, because a bill is a
claim about the past and a slope is a test in the present.

Four separate systems, four separate tests. Not because he distrusts the seller, but because each
one fails in its own way and a car with three working brakes and one that has quietly seized is a
car that feels perfect until the one day it does not.

## The idea in plain language

The five brakes from this section are not five versions of one idea. Each stops exactly one class of
thing and is useless against the other four:

| # | Brake | Stops | Does nothing about |
| --- | --- | --- | --- |
| 1 | parameter binding | a value becoming syntax | how many rows come back |
| 2 | `mode=ro` connection | any write | a read that returns the wrong rows |
| 3 | authorizer allowlist | operations you did not authorise | a legal query that is too big |
| 4 | server-side `LIMIT` | a flood of rows | a query that is expensive to run |
| 5 | step budget | unbounded work | anything about correctness |

Read the right-hand column, because it is the part people skip. Adding `mode=ro` to a tool with a
formatted statement gives you a tool that cannot be made to delete anything and can still be made to
return every closed ticket in the archive. Adding `LIMIT 5` to a tool with no work budget gives you
five rows after a very long wait. **Brakes do not substitute for each other.**

And then there is the one that is not a brake. Almost every tutorial-grade database tool carries a
line like *"This tool is read-only. Only run SELECT statements."* — in the docstring, in the system
prompt, or in the MCP tool description. It is worth being precise about what that sentence is: it is
a **request**, addressed to the model, about behaviour. It is documentation. It is often good
documentation, because it helps the model choose the right tool. It is not a limit, because nothing
enforces it, and the way to find out which of those two things you have is to test it — which is
what "brake 0" in the lab does.

## Why Sutra needs it

Because [6.3](../06-in-production/6.3-the-audit-that-reads-your-file.md) turns this table into an
eval that reads `sutra_mcp/db_tools.py` and goes red for every brake you left out, and an eval is
only worth having if the thing it checks was itself checked.

Because [Day 45](../../../day-45-the-mcp-audit/LESSON.md) audits every MCP surface Sutra has built,
and "the database tool has five brakes" is a claim that audit will want evidence for rather than a
paragraph.

And because this is Principle 13 — blast radius before capability — with a number attached. The
capability arriving today is *an agent can read the ticket archive*. The containment story is a table
with five rows and a script that runs it.

## The mechanism

The lab builds each brake alone, hands it its own attack, and judges it by whether the attack got
what it wanted:

```python
def guard(fn):
    """Run an attack and report (attack_succeeded, one line of evidence)."""
    try:
        return True, f"attack returned {fn()!r}"
    except sqlite3.Error as exc:
        return False, f"{type(exc).__name__}: {exc}"
```

**Line by line:**

- The function takes a callable rather than a result, so the attack runs **inside** the `try`. Passing
  `fn()` would have run it before `guard` was even called.
- Returning `True` when nothing was raised is the deliberately awkward polarity: `True` means *the
  attack succeeded*, which means the brake failed. Naming it after the attack rather than after the
  brake keeps the test honest, because it stops you writing a check that passes when nothing happened.
- `except sqlite3.Error` catches the engine's whole exception hierarchy —
  `OperationalError`, `DatabaseError`, `ProgrammingError` and the rest — because the five brakes
  refuse in four different classes and a narrower catch would let one through as a crash.
- The evidence string carries `type(exc).__name__` **and** the message. `OperationalError:
  interrupted` and `DatabaseError: not authorized` come from different brakes and you need to be able
  to tell which one spoke.
- Nothing here asserts. `guard` reports; the caller decides. That separation is what lets one script
  test five brakes without stopping at the first failure — a test that stops at the first failure
  tells you about one brake.

Brake 0 is tested first, and it is tested exactly like the others:

```python
rw = sqlite3.connect(ARCHIVE)
got, why = guard(lambda: rw.execute("UPDATE tickets SET status='closed'").rowcount)
results.append(('0  "read only" in the description', not got, why))
rw.rollback()
```

**Line by line:**

- The connection is opened **read-write**, on purpose. This is the world where the only thing standing
  between the model and the archive is a sentence, which is the world a great many deployed tools are
  actually in.
- The attack is one `UPDATE` with no `WHERE`: close every ticket. It is the smallest destructive
  statement there is and it is exactly what a helpful model writes when asked to tidy up.
- `.rowcount` is read so the attack has to actually execute rather than just compile. A statement that
  is prepared and never stepped proves nothing.
- `not got` inverts the polarity for the results table: the brake **held** when the attack did not
  succeed.
- `rw.rollback()` undoes the update so the rest of the script runs against an unchanged archive. Note
  what this means: the attack worked, and only the test harness put it back.

Run all six:

```bash
cd days/day-39-database-tools/lab && uv run python brakes.py; echo "exit: $?"
```

**Line by line:**

- The script seeds an archive with 200 extra rows so brakes 4 and 5 have something to strain against;
  five rows would let a broken limit look fine.
- The exit code is the number of real brakes that did not hold, so this is an eval that can go red in
  the Principle 11 sense rather than a report you read.
- Zero model calls, zero network, one file on disk.

## When it breaks

The whole run, on 2026-09-04:

```text
seeded archive.sqlite3: 205 tickets, 2 kb articles

archive: archive.sqlite3 (201 rows match '%log%')

  0  "read only" in the description  FAILED  attack returned 205
  1  parameter binding               HELD    0 rows leaked past status='open'
  2  connection mode=ro              HELD    OperationalError: attempt to write a readonly database
  3  authorizer allowlist            HELD    DatabaseError: not authorized
  4  server-side LIMIT               HELD    201 matched, 5 returned
  5  step budget                     HELD    OperationalError: interrupted

of the five real brakes, 5 held and 0 did not
exit: 0
```

`attack returned 205` is the line to sit with. Two hundred and five tickets closed, in one statement,
against a tool whose description said read-only. No exception, no warning, a row count and a
success. The description was not ignored — it was never consulted, because a description is text sent
to a model and the `UPDATE` went to a database.

Now break one on purpose. Add `sqlite3.SQLITE_ATTACH` to `ALLOWED` and run it again:

```text
  3  authorizer allowlist            FAILED  attack returned -1

of the five real brakes, 4 held and 1 did not
exit: 1
```

`attack returned -1` is the `ATTACH` succeeding. The `-1` is `rowcount` for a statement that changed
no rows — SQLite reports "not applicable" rather than zero — and that unremarkable number is a second
database file now readable through your search tool.

And raise the step budget to ten million:

```text
  5  step budget                     FAILED  attack returned 8615125

of the five real brakes, 4 held and 1 did not
```

8 615 125 is 205 cubed: every combination of three tickets, generated in full, by a tool that was
asked to search. You wait for that one, which is the other half of what the brake is for.

## In production

**What a professional writes instead:** this table, in the repository, next to the tool — with a
column saying **where** each brake is enforced. Ours are all in application code today, and that is
worth writing down honestly, because a brake in the code you deploy is one refactor away from
absence. On a real database, brakes 2 and 3 move into the database as a role, and that is a
strictly better place for them.

**What degrades at scale:** brake 5. A step budget tuned on a laptop is wrong on a smaller production
instance, and the symptom is intermittent `interrupted` errors on queries that used to work. Brakes
1 to 4 are size-independent; the work budget is the one that needs re-measuring when the fleet
changes.

**The failure mode that only appears with real traffic:** brakes are added in an incident and never
tested again. Six months later a refactor moves the connection helper, the read-only URI is
reconstructed slightly differently, `uri=True` is dropped, and every brake below it is silently
absent. Nothing fails — the tool still returns rows. This is precisely why the brake table has to be
an executable check rather than a document, and why
[6.3](../06-in-production/6.3-the-audit-that-reads-your-file.md) reads the source rather than the
comment above it.

**The review comment a senior engineer leaves:** *"the tool description says read-only in three
places and the connection is read-write. Pick one to be true. And whichever way you go, the test that
proves it should fail if somebody changes it — right now nothing here fails."*

**The interview question:** *"you said your database tool is read-only. How do you know?"* *"Because
we attacked it. Five brakes, five separate attacks, one script with an exit code equal to the number
that did not hold: parameter binding against a crafted search term, a write against the read-only
connection, an ATTACH against the authorizer, a broad search against the row limit, and a
three-way self-join against the step budget. All five held. The interesting result was the control:
we also tested the sentence 'this tool is read-only' in the description against an UPDATE on a
read-write connection, and it closed 205 tickets and reported success. That is the whole lesson —
the description is how the model chooses the tool, and it is not a limit. And they do not substitute
for each other: read-only says nothing about a query returning the wrong rows, and a row limit says
nothing about a query that runs for a very long time."*
