# 2.2 — Editing the request in place

## One-line answer

The `llm_request` you are handed is the **real object**, not a copy, so a `before_model_callback`
changes what the model sees by **mutating it and still returning `None`** — returning a value would
cancel the call instead of shaping it.

---

## The story

"No onions" on the order slip.

The counter takes your order and writes it on a slip. Before the slip goes through the hatch you say
"and no onions in that". The person does not tear up the slip and start again, and they do not hand
you a plate of food over the counter. They write two words on the slip that is already there and push
it through.

Everything downstream still happens. The kitchen still cooks. You still wait. The only difference is
one line on a piece of paper that was going to the kitchen anyway.

Now imagine you had instead been handed a plate over the counter at the moment you said "no onions".
You would have got food, quickly, and the kitchen would never have cooked anything. That is a
completely different outcome from the one you asked for, and it is exactly the mistake this part
exists to prevent.

---

## The idea in plain language

There are two ways a callback can affect a model call, and they are not variations of each other.

**Mutate and return `None`** — change the request object, then let the call proceed. The model runs,
on your modified input. This is *shaping*.

**Return an `LlmResponse`** — the call does not proceed at all, and your object is used as the reply.
This is *replacing*, and it is [2.3](2.3-the-call-that-never-happened.md).

The reason mutation works is that Python passes objects by reference. The `llm_request` in your
function and the `llm_request` ADK is about to send are the same object in memory, so changing an
attribute changes what is sent. ADK's own field documentation is explicit about this being intended
rather than an accident: *"llm_request: LlmRequest, The raw model request. Callback can mutate the
request."*

The word **raw** is doing work there. You are not being handed a view or a validated copy. There is
no undo.

What is worth mutating, in the order you will reach for them:

| Change | How |
| --- | --- |
| add a rule to the system instruction | `llm_request.append_instructions(["..."])` |
| trim the history | reassign or slice `llm_request.contents` |
| set a generation parameter | `llm_request.config.temperature = 0.0` |
| swap the model for this one call | `llm_request.model = "gemini-3.7-flash-lite"` |

`append_instructions` is worth knowing by name because it is the only one of the four that is a
method rather than an assignment. It exists because appending to a system instruction is fiddly: the
field may be `None`, may be a string, or may be a `Content` object, and the method handles all three.
Writing `llm_request.config.system_instruction += "..."` by hand works right up until the first agent
that had no instruction, and then raises `TypeError: unsupported operand type(s) for +=: 'NoneType'
and 'str'`.

---

## Why Sutra needs it

**A rule in the agent's `instruction` is static; a rule added here can depend on the situation.** The
desk's handbook, written on
[Day 6](../../../day-06-instructions-and-personas/parts/01-writing-the-handbook/1.1-handbook-not-a-wish.md),
is the same text on every turn. A callback can add "this session has already made three knowledge-base
searches, do not make a fourth" — a sentence that is only true sometimes, and that reads session state
to find out.

**Day 20 is context engineering, and this is its only lever.** Trimming a long history, summarising
the middle of a conversation, injecting retrieved documents: all of them are mutations of
`llm_request.contents` from this hook. Today you learn that the mutation is legal and how to make one;
Day 20 is about which mutation to make.

**Day 12's persona question gets a second answer here.** With an output schema, most of Sutra's
instruction now applies to one field. Some of what was cut from the instruction may belong in a
per-turn append rather than in the static handbook.

## The mechanism

The same agent run twice: once untouched, once with a rule appended and the history trimmed. The
scripted model prints what it was actually given, which is the only trustworthy witness.

```python
# lab/shaping.py - mutate and return None. The model sees the change; the call still happens.
import asyncio

from google.adk.agents import LlmAgent
from google.adk.runners import InMemoryRunner
from google.genai import types
from scripted import ScriptedModel, text


class ReportingModel(ScriptedModel):
    """A scripted model that first prints what it was handed."""

    async def generate_content_async(self, llm_request, stream=False):
        instruction = llm_request.config.system_instruction or ""
        print(f"    model got {len(llm_request.contents)} turns")
        print(f"    model got instruction: {instruction!r}")
        async for response in super().generate_content_async(llm_request, stream=stream):
            yield response


def add_a_rule(callback_context, llm_request):
    """Shape the request: append one sentence, keep the last two turns, carry on."""
    llm_request.append_instructions(["POLICY: never repeat a credential back to the user."])
    llm_request.contents = llm_request.contents[-2:]
    # No return: the call proceeds, on the object we just edited.


def build(callback) -> LlmAgent:
    return LlmAgent(
        name="desk",
        model=ReportingModel(model="scripted", replies=[[text("understood")]]),
        instruction="You are Sutra.",
        before_model_callback=callback,
    )


async def drive(agent: LlmAgent) -> None:
    runner = InMemoryRunner(agent=agent)
    session = await runner.session_service.create_session(app_name=runner.app_name, user_id="u")
    history = [f"message {n}" for n in range(1, 4)]
    for message in history:
        async for _ in runner.run_async(
            user_id="u",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=message)]),
        ):
            pass


async def main() -> None:
    print("without a callback:")
    await drive(build(None))
    print("with add_a_rule:")
    await drive(build(add_a_rule))


asyncio.run(main())
```

**Line by line:**

- `class ReportingModel(ScriptedModel)` — the witness. A callback that claims to have changed the
  request has to be checked at the far end, and the model is the far end. Subclassing keeps
  `lab/scripted.py` unchanged.
- `async for response in super().generate_content_async(...)` — delegating to the parent's generator
  and re-yielding, rather than reimplementing it. An async generator cannot be `return`ed from another
  async generator; it has to be iterated and re-yielded.
- `llm_request.append_instructions([...])` — a **list** of strings, even for one string, because the
  method's other accepted form is a `types.Content` and the list is how it tells them apart.
- `llm_request.contents = llm_request.contents[-2:]` — reassigning the attribute, which is a mutation
  of the request even though it is an assignment to a slice-copy. Keeping the last two turns is the
  crudest possible trimming policy and it is deliberately crude: Day 20 is where the policy gets
  interesting, and a clever one here would hide the mechanism.
- The comment `# No return` is load-bearing documentation, not decoration. A future reader adding a
  line to this function needs to know that ending it with a `return` changes what kind of callback it
  is.
- `build(None)` — passing `None` for the callback field is how you get the unmodified baseline, and
  it works because `None` is the field's default.
- Three messages in one session, so the third call has a history worth trimming.

The output:

```text
without a callback:
    model got 1 turns
    model got instruction: 'You are Sutra.\n\nYou are an agent. Your internal name is "desk".'
    model got 3 turns
    model got instruction: 'You are Sutra.\n\nYou are an agent. Your internal name is "desk".'
    model got 5 turns
    model got instruction: 'You are Sutra.\n\nYou are an agent. Your internal name is "desk".'
with add_a_rule:
    model got 1 turns
    model got instruction: 'You are Sutra.\n\nYou are an agent. Your internal name is "desk".\n\nPOLICY: never repeat a credential back to the user.'
    model got 2 turns
    model got instruction: 'You are Sutra.\n\nYou are an agent. Your internal name is "desk".\n\nPOLICY: never repeat a credential back to the user.'
    model got 2 turns
    model got instruction: 'You are Sutra.\n\nYou are an agent. Your internal name is "desk".\n\nPOLICY: never repeat a credential back to the user.'
```

Three things worth reading slowly.

**The history stopped growing.** Without the callback the turn count goes 1, 3, 5 — every exchange
adds the user's message and the model's reply. With the trim it goes 1, 2, 2. That is what
[2.1](2.1-what-is-actually-in-the-request.md)'s quadratic growth looks like when somebody finally puts
a lid on it.

**The policy sentence is at the end**, after ADK's own identity line, joined with a blank line.
`append_instructions` really does append; it does not replace, and it does not get to go first.

**The model still ran, every time.** The callback shaped six requests and cancelled none of them.
That is the difference between mutation and a return value, and it is the whole part.

Verified against the installed `google-adk` 2.7.1 (`LlmRequest.append_instructions` in
`google/adk/models/llm_request.py`, and the `before_model_callback` field docstring in
`google/adk/agents/llm_agent.py`) on 2026-08-29.

## When it breaks

**💥 The `+=` on an instruction that was `None`.**

```text
TypeError: unsupported operand type(s) for +=: 'NoneType' and 'str'
```

You wrote `llm_request.config.system_instruction += "POLICY: ..."` on an agent built with no
`instruction`. Use `append_instructions`, which handles the unset case, the string case and the
`Content` case.

**💥 The instruction appended on every turn of the same session.** No error, and a system instruction
that grows without bound. Your callback fires once per **model call**, not once per session, so a
five-turn conversation with tool calls appends the same sentence a dozen times. It works — the model
tolerates repetition — and it silently spends context on a sentence it already had. If the append is
conditional, guard it on a value in `callback_context.state`, not on a variable in your module.

**💥 The trim that cut a tool result off its call.**

`contents[-2:]` is safe in this demo because the demo has no tool calls. In a real conversation a
function call and its function response are a **pair**, and a slice that lands between them sends the
provider a response to a call it cannot see. Trimming a transcript is not the same operation as
trimming a list, which is a large part of why Day 20 is a day rather than a paragraph.

The error for this one comes from the provider rather than from ADK, so this document does not print
it: a paraphrased traceback is worse than none (§18.3 rule 8), and the wording is Gemini's to change.

## In production

**What a professional writes instead of the teaching version** makes the mutation conditional and
records that it happened:

```python
def add_search_budget_rule(callback_context, llm_request) -> None:
    """Append a rule only when the session has actually spent its search budget."""
    used = callback_context.state.get("kb_searches", 0)
    if used < 3:
        return None
    llm_request.append_instructions(
        [f"POLICY: {used} knowledge-base searches already made. Answer from what you have."]
    )
```

**Line by line:**

- `callback_context.state.get("kb_searches", 0)` — the counter lives in session state, written by the
  tool door in [3.1](../03-the-tool-doors/3.1-the-chokepoint-restored.md), which is
  [Day 11, part 2.1](../../../day-11-tool-context/parts/02-state-from-a-tool/2.1-writing-on-the-carbon-copy.md)'s
  mechanism being read from a different door. A module-level counter would be shared across every user
  on the process — [Day 11, part 5.1](../../../day-11-tool-context/parts/05-failure-lab/5.1-the-previous-patients-file.md)'s
  failure, exactly.
- `return None` on the cheap path, written explicitly. This function has a branch, so the annotation
  `-> None` and the early return together say *"still an observer on both paths"*.
- The appended sentence includes the number. A model reasons better about "3 searches already made"
  than about "you have made enough searches", and a human reading a trace can tell which branch fired.

**What degrades at scale** is instruction drift. Every callback that appends is competing for the
same system instruction with every other callback, with the agent's own handbook, with ADK's identity
line, and on Sutra with the output-schema instruction from
[Day 12, part 3.2](../../../day-12-structured-output/parts/03-schema-and-tools-together/3.2-the-tool-adk-injects.md).
Six appenders and nobody can say what the model is being told any more. The discipline that survives:
one appender per agent, and it logs what it appended.

**The failure that only shows with real traffic** is the mutation that was fine on a short
conversation. A trim of `contents[-6:]` is harmless in testing, where nobody has six turns. In
production it silently drops the ticket ID the user gave in turn one, and the agent starts asking
customers to repeat themselves — reported as "the bot forgets things", with no error anywhere.

**The review comment a senior engineer leaves:** *"This appends unconditionally, so on a ten-call
invocation the model gets the same policy sentence ten times. Gate it on state, and log when it
fires."*

**The interview question:** *"How would you inject a rule that depends on what has happened so far in
the conversation?"* The answer that shows you have wired one: "A before-model callback that mutates
the request and returns `None`. The request object is passed by reference — ADK's own docstring says
the callback can mutate it — so I append to the system instruction with `append_instructions` and let
the call proceed. The important distinction is that mutating and returning are different operations:
mutate and the model still runs on your edited input, return an `LlmResponse` and the model never runs
at all. And the condition has to come out of session state rather than a variable in my module, or
it's shared across every user on the process."
