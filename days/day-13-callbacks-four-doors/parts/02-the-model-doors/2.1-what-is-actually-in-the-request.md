# 2.1 — What is actually in the request

## One-line answer

`before_model_callback` hands you the complete `LlmRequest` a fraction of a second before it is sent —
the model name, the system instruction, every turn of history and every tool declaration — which makes
it the first place in this curriculum where you can *see* what a model call actually costs.

---

## The story

The itemised bill at the till.

You put four things on the counter. The total comes to more than you expected, and the person behind
the till, without being asked, turns the printed slip around so you can read it. Milk. Bread. Two
things you do not remember picking up. A bag charge. A rounding line.

Nothing on that slip is a surprise in the sense of being *wrong*. Every line is something that
genuinely happened. The surprise is that you had been carrying a number in your head — three items,
roughly this much — and the slip is the first time the number in your head met the number in the
system.

Most people who work with language models carry a number in their head too. "I'm sending one question."
The request object is the printed slip.

---

## The idea in plain language

A **request** is the object that goes to the model. Until today you have never held one. On
[Day 2](../../../day-02-llm-mechanics/parts/01-first-contact/1.4-the-first-interaction.md) you
sent one by hand and it was small; since [Day 5](../../../day-05-first-adk-agent/parts/04-the-runner/4.1-the-runner-is-your-run-loop.md)
ADK has assembled it for you and you have seen only what came back.

In ADK the class is `LlmRequest`, and it is a plain Pydantic object with a handful of fields:

| Field | What is in it |
| --- | --- |
| `model` | the model string, resolved — the pin from your agent, or the default |
| `contents` | the conversation, as a list of `Content` objects: user turns, model turns, tool calls and tool results |
| `config` | a `GenerateContentConfig`, which holds the **system instruction**, the **tool declarations**, temperature, and the response schema if there is one |
| `tools_dict` | a name → tool mapping, so a callback can look up the actual tool object by its name |

Two of those deserve a sentence each, because they are where the surprises live.

**`contents` is the whole conversation, resent every turn.** A language model has no memory between
calls, so every call carries the entire history —
[Day 3, part 1.2](../../../day-03-loop-hand-rolled/parts/01-loop-anatomy/1.2-the-transcript-is-the-world.md)
established this and today you can measure it. On a five-exchange conversation with two tool calls, a
single "next question" from the user is a request carrying a dozen `Content` objects.

**`config.system_instruction` is not exactly what you wrote.** ADK appends to it. Your instruction is
in there, and so is an identity line ADK adds, and so is anything a tool or a schema contributed. On
Sutra, [Day 12, part 3.2](../../../day-12-structured-output/parts/03-schema-and-tools-together/3.2-the-tool-adk-injects.md)
showed 297 characters of instruction that nobody on your team wrote. This is where you can read them.

The callback that gives you all of this is the plainest one there is: take the request, look at it,
return nothing.

---

## Why Sutra needs it

**You cannot manage what you cannot see, and the request is what you are billed for.** Sutra runs on
20 free Gemini requests per day (`docs/PACKAGES.md`, 2026-08-25), and the size of each one decides how
much of the context window is left for the answer. Today's audit callback is the instrument.

**Day 20 is context engineering** — trimming, summarising and re-ordering `contents` before it is
sent. That day is entirely about editing this object. Today is about reading it, which has to come
first.

**Day 34's cost tracking and Day 84's tracing both hang off this hook**, because it is the only place
that sees a request *before* it becomes a network call.

## The mechanism

One callback, one print, and a run with two model calls in it so you can watch the request grow:

```python
# lab/the_request.py - what a model call actually carries. Zero real model calls.
import asyncio

from google.adk.agents import LlmAgent
from google.adk.runners import InMemoryRunner
from google.genai import types
from scripted import ScriptedModel, call, text


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id in the ticket system."""
    return {"status": "ok", "ticket_id": ticket_id, "body": "Charged twice in March."}


def inspect_request(callback_context, llm_request):
    """Observer at the model door. Prints the bill, changes nothing."""
    config = llm_request.config
    instruction = config.system_instruction or ""
    declared = [
        fn.name for tool in (config.tools or []) for fn in (tool.function_declarations or [])
    ]
    print(f"  call to {llm_request.model} from agent {callback_context.agent_name}")
    print(f"    contents .......... {len(llm_request.contents)} turns")
    for content in llm_request.contents:
        kinds = [
            "text" if part.text else "function_call" if part.function_call else "function_response"
            for part in content.parts or []
        ]
        print(f"      {content.role:<6} {kinds}")
    print(f"    system_instruction  {len(instruction)} chars")
    print(f"    declared tools .... {declared}")
    print(f"    tools_dict ........ {sorted(llm_request.tools_dict)}")


agent = LlmAgent(
    name="desk",
    model=ScriptedModel(
        model="gemini-3.7-flash",
        replies=[[call("lookup_ticket", ticket_id="4521")], [text("Billing. Refund issued.")]],
    ),
    instruction="You are Sutra, a support-ticket triage assistant.",
    tools=[lookup_ticket],
    before_model_callback=inspect_request,
)


async def main() -> None:
    runner = InMemoryRunner(agent=agent)
    session = await runner.session_service.create_session(app_name=runner.app_name, user_id="u")
    async for _ in runner.run_async(
        user_id="u",
        session_id=session.id,
        new_message=types.Content(
            role="user", parts=[types.Part(text="why was ticket 4521 charged twice?")]
        ),
    ):
        pass


asyncio.run(main())
```

**Line by line:**

- `config = llm_request.config` — one local name, because every interesting thing except `contents`
  and `model` lives under `config`. `LlmRequest` is a thin envelope; `GenerateContentConfig` is where
  the provider's actual parameters are.
- `config.system_instruction or ""` — the field is optional and is genuinely `None` on an agent with
  no instruction, so `len()` on it directly would raise on exactly the agent you were debugging.
- The `declared` comprehension walks `config.tools`, then each tool's `function_declarations`. That
  two-level shape is the provider's, not ADK's: one `Tool` object can carry many function
  declarations, which is why [Day 4, part 1.2](../../../day-04-tools-by-hand/parts/01-the-schema/1.2-declaring-a-tool.md)'s
  hand-written JSON had the same nesting.
- `for part in content.parts or []` — `parts` is optional on `Content` for the same reason it is
  optional on an event.
- The conditional expression that produces `kinds` classifies each part as text, a function call or a
  function response. That is the only classification you need to read a conversation, and it is the
  same three shapes [Day 7, part 1.4](../../../day-07-events-and-streaming/parts/01-the-event-object/1.4-the-half-that-is-not-text.md)
  found inside an event.
- `f"{content.role:<6}"` — left-aligned to six characters so `user` and `model` line up and the shape
  of the conversation is visible as a column rather than as prose.
- `sorted(llm_request.tools_dict)` — sorting a dict iterates its keys, so this prints the tool names.
  `tools_dict` is the lookup table [3.1](../03-the-tool-doors/3.1-the-chokepoint-restored.md) uses to
  turn a name from the model into the tool object.
- No `return` — this is an observer, per [1.3](../01-the-four-doors/1.3-none-means-carry-on.md).

The output:

```text
  call to gemini-3.7-flash from agent desk
    contents .......... 1 turns
      user   ['text']
    system_instruction  98 chars
    declared tools .... ['lookup_ticket']
    tools_dict ........ ['lookup_ticket']
  call to gemini-3.7-flash from agent desk
    contents .......... 3 turns
      user   ['text']
      model  ['function_call']
      user   ['function_response']
    system_instruction  98 chars
    declared tools .... ['lookup_ticket']
    tools_dict ........ ['lookup_ticket']
```

Read the two blocks against each other and three facts fall out.

**One user question produced two model calls.** Nothing in the user's message said so; the tool call
did. Every tool your agent uses is a multiplier on the request count, which is
[Day 10, part 3.3](../../../day-10-function-tools/parts/03-the-dispatch-you-deleted/3.3-the-brakes-still-matter.md)'s
point arriving as a number.

**The second request carries the first one inside it.** Three turns where there was one: the question,
the model's request for a tool, and the tool's result. The tool result is `role="user"`, which
surprises everyone the first time — from the provider's point of view, anything that is not the model
speaking is the user speaking.

**`system_instruction` is 98 characters and your instruction is 49.** The difference is ADK's
appended identity line. On an agent with an output schema it is hundreds of characters more, and none
of them are yours.

Verified against `adk.dev/callbacks/types-of-callbacks/` and the installed `google-adk` 2.7.1
(`google/adk/models/llm_request.py`) on 2026-08-29.

## When it breaks

**💥 The instruction that was `None`.**

```text
TypeError: object of type 'NoneType' has no len()
```

`config.system_instruction` is unset on an agent built without an `instruction`. Guard it, as above.
The same applies to `config.tools`, `content.parts` and `llm_response.content` — the whole request
graph is optional fields, because a request is assembled in stages and a callback can run at a moment
when a stage has not contributed anything.

**💥 The print that ran on every turn of a long conversation.** No error, and a terminal that is
unusable. Printing `contents` in full is fine on turn one and unreadable on turn forty. Print
*shapes* — counts, roles, kinds — and reach for the full object only when a shape looks wrong.

**💥 The secret in the log.** No error, and the worst outcome on this page. `contents` holds
everything the user typed and everything your tools returned, which on Sutra includes ticket bodies.
A callback that logs the request logs all of it, into whatever your logs go into.
[Day 11, part 2.3](../../../day-11-tool-context/parts/02-state-from-a-tool/2.3-what-not-to-put-on-the-noticeboard.md)
made this argument about session state; it applies with more force here, because a request is bigger
than state and a log is easier to forget about than a database.

## In production

**What a professional writes instead of the teaching version** logs one structured line per model call
and no payload at all:

```python
import logging

logger = logging.getLogger(__name__)


def audit_model(callback_context, llm_request) -> None:
    """One structured line per model call. Shapes only - never content."""
    logger.info(
        "model_call",
        extra={
            "agent": callback_context.agent_name,
            "invocation": callback_context.invocation_id,
            "model": llm_request.model,
            "turns": len(llm_request.contents),
            "tools": len(llm_request.tools_dict),
        },
    )
```

**Line by line:**

- `logging`, not `print` — the house rule for library code, and here it also means the audit obeys
  whatever level the application configured rather than shouting into stdout.
- `"model_call"` as the message with the data in `extra` is **structured logging**: the message is a
  constant you can group by, and the fields are queryable. A formatted f-string message is a sentence
  you have to write a regular expression to search.
- `callback_context.invocation_id` is the value that ties this line to every other line from the same
  run, including the tool-door lines from [3.1](../03-the-tool-doors/3.1-the-chokepoint-restored.md).
  Without it you have a pile of events and no way to reassemble a single request's story.
- `len(llm_request.contents)` rather than the contents. The count answers "is the history growing
  unboundedly?", which is the question you actually have, without putting a customer's ticket body in
  a log aggregator.

**What degrades at scale** is `contents` itself. It grows every turn, every turn resends it, and the
token cost of a conversation is quadratic in its length rather than linear. This audit line is how you
find that out from a dashboard rather than from a bill, and it is why `turns` is the field worth
alerting on.

**The failure that only shows with real traffic** is the request that grew past the context window. In
development a conversation is four turns. In production somebody has a fifty-turn session with six
tool calls each, and the provider returns an error about input length that is reported to you as "the
bot stopped working for one customer". A `turns` metric with a percentile makes that visible before it
is an incident.

**The review comment a senior engineer leaves:** *"Don't log `llm_request.contents`. That's the
customer's message plus every tool result, and it'll sit in the log store for ninety days. Log the
count."*

**The interview question:** *"What's actually in a request to the model on turn ten of a
conversation?"* The answer that shows you have looked: "Everything. The model is stateless, so the
whole transcript is resent — every user turn, every model turn, every tool call and every tool result
— plus the system instruction and the full tool declarations, every single time. I've printed it from
a before-model hook: one user question with one tool call produced two requests, and the second
carried three turns where the first carried one. That's why context management is a real engineering
concern rather than a tuning knob, and why the request hook is the place I'd put cost instrumentation
— it's the last point before it becomes a network call."
