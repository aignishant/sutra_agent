# 5.1 — 💥 The note that became the result

## One-line answer

Add one `return` to a logging callback and every tool in the agent stops running: the log record
becomes the tool's result, the model reasons over it confidently, and nothing anywhere raises,
prints a warning or looks different — which is why this is the day's deliberate failure.

---

## The story

The reminder scribbled on the form.

The office runs on a paper form: fill it, sign it, drop it in the tray, and somebody upstairs acts on
it. You are filling one in when you remember you need to call the electrician. There is white space at
the bottom of the form, so you write *call electrician re: 2nd floor sockets* there, meaning to tear
that strip off before you file it.

Then the phone rings, and you drop the form in the tray.

Upstairs, somebody reads the form. Every field is filled. There is one extra line at the bottom, in
your handwriting, on an official form, in the tray for processed work. They have no reason to think it
is a note to yourself. They act on it.

Nothing went wrong at any step. The form was valid, the handwriting was yours, the tray was the right
tray. The only thing that happened is that a private note ended up in a channel that carries
instructions, and a channel does not know what its contents were *meant* to be.

---

## The idea in plain language

[1.3](../01-the-four-doors/1.3-none-means-carry-on.md) stated the rule and this part is what happens
when you forget it under ordinary circumstances.

The circumstances are these. You have an audit callback — [3.1](../03-the-tool-doors/3.1-the-chokepoint-restored.md)'s
register. It works. Somebody asks for richer logs, so you build a summary of the call, and because you
are a tidy programmer who likes a function to hand back what it computed, you end it with
`return summary`.

It is *just logging*. Logging cannot break anything.

Except that at this door, `return` is not punctuation. It is a decision, and you just made it. Your
summary dict is now the tool's result. `search_kb` did not run. `lookup_ticket` did not run. The model
receives your log record in a `function_response`, sees a well-formed object where a ticket should be,
and does what a good model does with data: it reasons over it and answers.

The three properties that make this the worst failure in the day:

**It is silent.** No exception, no warning, no `WARNING` line, nothing in the trace that is red. The
run completes. The agent answers. The tests that check "does the agent respond" pass.

**It is total.** Not one tool — every tool, on every call, for as long as the line is there. A
one-character-class edit disables the agent's entire ability to touch the world.

**It looks like a model problem.** The symptom that reaches you is *"the agent is hallucinating ticket
details"*. Every instinct then points at the prompt, the model, the temperature, the schema. The cause
is a `return` statement in a function whose name contains the word "log".

---

## Why Sutra needs it

**Sutra attaches its first observer today.** The register in `sutra/desk/callbacks.py` is exactly the
function this failure happens to, and it will be edited — by you, in a month, when the log line needs
one more field.

**It is the reason [1.3](../01-the-four-doors/1.3-none-means-carry-on.md)'s house rule exists.** An
observer ends with no `return` statement at all. That rule looks fussy until you have watched this
run, which is why the plan requires every day to break something on purpose (§17.7).

**Every later containment day inherits the hazard.** Day 21's error hooks, Day 30's security
callbacks, Day 67's guardrails: all of them are functions at a door where the return value is
load-bearing, and all of them will one day be edited by somebody adding a log line.

## The mechanism

Run it and watch the agent triage a ticket it never read.

```python
# lab/poisoned.py - the same callback, one line apart. Zero model calls.
import asyncio

from google.adk.agents import LlmAgent
from google.adk.runners import InMemoryRunner
from google.genai import types
from scripted import ScriptedModel, call, text


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id in the ticket system."""
    print("      >> lookup_ticket actually ran")
    return {
        "status": "ok",
        "ticket_id": ticket_id,
        "body": "Charged twice for the March renewal.",
        "opened": "2026-03-04",
    }


def audit_observer(tool, args, tool_context):
    """The version that works. Builds a summary, prints it, returns nothing."""
    summary = {"tool": tool.name, "args": args, "agent": tool_context.agent_name}
    print(f"      [audit] {summary}")


def audit_with_a_return(tool, args, tool_context):
    """The same function with one extra line. Spot it."""
    summary = {"tool": tool.name, "args": args, "agent": tool_context.agent_name}
    print(f"      [audit] {summary}")
    return summary


def build(callback) -> LlmAgent:
    return LlmAgent(
        name="desk",
        model=ScriptedModel(
            model="scripted",
            replies=[
                [call("lookup_ticket", ticket_id="4521")],
                [text("(the model answers from whatever it was given)")],
            ],
        ),
        instruction="Triage the ticket. Never state a fact no tool gave you.",
        tools=[lookup_ticket],
        before_tool_callback=callback,
    )


async def drive(label: str, callback) -> None:
    print(f"  {label}")
    runner = InMemoryRunner(agent=build(callback))
    session = await runner.session_service.create_session(app_name=runner.app_name, user_id="u")
    async for event in runner.run_async(
        user_id="u",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="ticket 4521")]),
    ):
        for part in (event.content.parts if event.content else []) or []:
            if part.function_response:
                print(f"      the model was told: {part.function_response.response}")


async def main() -> None:
    await drive("a. audit_observer - no return", audit_observer)
    await drive("b. audit_with_a_return - one extra line", audit_with_a_return)


asyncio.run(main())
```

**Line by line:**

- The two callbacks are **character-for-character identical** except for the last line of the second.
  That is the whole design of the script: any other difference would give you something else to blame.
- `summary` is built in both, so the "expensive" work is identical too. The failure is not about what
  the function computes; it is about what it hands back.
- `lookup_ticket` returns a ticket with a `body` and an `opened` date — real-looking fields that the
  model would repeat to a customer. A tool returning `{"ok": True}` would make the failure much less
  frightening than it should be.
- The instruction says *"Never state a fact no tool gave you"* — Day 6's honesty rule, still in place.
  It does not help, and it cannot: from the model's point of view a tool **did** give it those facts.
- The tool's own `print` is the instrument again. Its absence in case **b** is the finding.
- Both cases run in the same script, one after the other, so you see the working version first and
  have something to compare against.

The output:

```text
  a. audit_observer - no return
      [audit] {'tool': 'lookup_ticket', 'args': {'ticket_id': '4521'}, 'agent': 'desk'}
      >> lookup_ticket actually ran
      the model was told: {'status': 'ok', 'ticket_id': '4521', 'body': 'Charged twice for the March renewal.', 'opened': '2026-03-04'}
  b. audit_with_a_return - one extra line
      [audit] {'tool': 'lookup_ticket', 'args': {'ticket_id': '4521'}, 'agent': 'desk'}
      the model was told: {'tool': 'lookup_ticket', 'args': {'ticket_id': '4521'}, 'agent': 'desk'}
```

Look at what is **missing** from **b**.

`>> lookup_ticket actually ran` is not there. The ticket system was never asked. And the line
underneath it — the one that says what the model was told — is your log record, word for word, sitting
in the place where a ticket used to be.

The audit line printed identically in both runs. Your logging worked perfectly. It is the only thing
that did.

Now put yourself in the model's position on its next turn. It asked for ticket 4521. It received a
well-formed object containing the tool's name, the arguments it had itself supplied, and the agent's
name. There is no `status` field it recognises, no `body`, no error. It has no mechanism for
suspecting that a `function_response` is anything other than what the tool produced —
[3.2](../03-the-tool-doors/3.2-refusing-a-tool-call-honestly.md)'s merge point, doing its work
against you this time. So it does the reasonable thing and answers from what it has, which is nothing
about the ticket at all.

And notice the instruction is still in place: *"Never state a fact no tool gave you."* It does not
help. It cannot help. From where the model stands, a tool **did** give it this.

## When it breaks

**💥 The traceback there isn't.** There is no error text to reproduce here, and that is the finding.
Every other *When it breaks* section in this day has a real string in it. This one cannot, because the
framework did exactly what it was told: you returned a value, and the rule says a value is a result.

The nearest thing to a symptom is the transcript. In a poisoned run the `function_response` part
carries your log record instead of a ticket, and the only way to notice is to look at it — which is
why [3.1](../03-the-tool-doors/3.1-the-chokepoint-restored.md)'s register logs the *arguments* and why
a trace that shows tool results is worth having before you need it.

**💥 The second-order symptom.** What actually reaches you is a bug report:

> *"The agent is inventing ticket details. It told a customer ticket 4521 was opened last March and it
> was opened in June."*

Everybody investigates the model. Nobody investigates the logger.

## In production

**What a professional writes instead of the teaching version** is the same function with two changes
that both cost nothing:

```python
def audit_tool_calls(tool, args, tool_context) -> None:
    """Observer. Returns nothing, by construction and by annotation."""
    logger.info(
        "tool_call",
        extra={
            "invocation": tool_context.invocation_id,
            "tool": tool.name,
            "arg_names": sorted(args),
        },
    )
```

**Line by line:**

- `-> None` is the annotation, and with a type checker in the build it makes `return summary` a
  compile-time error rather than a production incident. This is the strongest argument this curriculum
  has yet met for the type-checker decision waiting at the Day 31 quality gate.
- There is no local `summary` variable at all. The data goes straight into the log call, so there is
  nothing lying around that a future edit could be tempted to return. The failure mode was *"I have a
  value, I should hand it back"*; the defence is not having the value.
- The docstring says **Observer** as its first word. Six months later, the person adding a field reads
  that word before they read the body.

**What degrades at scale** is review attention. A diff that adds `return summary` to a logging
function is one line, in a file nobody considers risky, with a commit message like *"richer tool
audit"*. It will be approved. The controls that actually work are structural — the annotation, the
type checker, and a test that asserts the tool ran — because none of them depend on a reviewer being
alert on a Friday.

**The failure that only shows with real traffic** is the partial version. A logging callback that
returns a value only on one branch — say, only for calls it considers interesting — vetoes only those
calls. The agent works for most requests and silently stops using its tools for a particular shape of
request, which will be reported as a quality regression on a segment and investigated as a prompt
problem for a week.

**The review comment a senior engineer leaves:** *"This is an observer — drop the `return` and
annotate it `-> None`. As written it replaces every tool result in the desk with a log record, and
nothing will error."*

**The interview question:** *"What's the sharpest edge you've hit in a callback system?"* The answer
that shows you have been bitten: "Return-value semantics on hooks that also serve as observers. In ADK
the same field takes a logger and a policy, and the only thing distinguishing them is whether the
function returns something — so a stray `return` in an audit callback silently substitutes debug data
for real tool results. No exception, no warning, and the agent keeps answering confidently from
whatever your log record contained. It surfaces as 'the model is hallucinating'. My rules since:
observers end with no return statement at all and are annotated `-> None`; overrides return an
unmistakably-labelled shape; and there's a test that asserts the tool actually ran on the ordinary
path, because that's the only assertion that fails when this happens."
