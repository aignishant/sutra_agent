# 1.2 — The names are the contract

## One-line answer

ADK calls your callback **by keyword**, so the parameter names in your `def` line are not yours to
choose: rename `llm_request` to `request` and the run dies with a `TypeError` that names your own
function.

---

## The story

The name on the boarding pass and the name on the ID.

You booked the flight yourself. You typed your own name. At the counter the agent looks at the
passport, looks at the pass, and stops — because the pass says *Sunil Kumar* and the passport says
*Sunil Kumar Reddy*. It is the same person. Everyone in the queue can see it is the same person. The
agent is not confused about who you are.

It does not matter. The system that has to accept the two documents does not compare *people*, it
compares *strings*, and the two strings are not equal. You are sent to the ticketing desk.

The lesson is not that the airline is being difficult. It is that in some systems the name is not a
label on the thing — the name **is** the way the thing is found. When that is true, close enough is
not a category that exists.

---

## The idea in plain language

Python lets you pass arguments to a function two ways.

**Positionally**, where the order decides which parameter gets which value:

`f(a, b)` — the first value goes to the first parameter, whatever that parameter is called.

**By keyword**, where the *name* decides:

`f(second=b, first=a)` — order is irrelevant, and a name that does not exist in the function is an
error.

For ordinary code you rarely have to think about which one a caller will use. For a callback you do,
because the caller is ADK and you never see the call. ADK has picked one: **it calls every callback
by keyword.** Your parameter names are therefore part of an interface, exactly like the name of a
function you export from a module.

The names, and they are the complete list:

| Callback | Parameter names ADK passes |
| --- | --- |
| `before_model_callback` | `callback_context`, `llm_request` |
| `after_model_callback` | `callback_context`, `llm_response` |
| `on_model_error_callback` | `callback_context`, `llm_request`, `error` |
| `before_tool_callback` | `tool`, `args`, `tool_context` |
| `after_tool_callback` | `tool`, `args`, `tool_context`, `tool_response` |
| `on_tool_error_callback` | `tool`, `args`, `tool_context`, `error` |

Two details in that table are worth pausing on, because they trip people who think they have
memorised it.

The model callbacks take **`callback_context`**; the tool callbacks take **`tool_context`**. They are
the same class in ADK 2.7.1 — `CallbackContext` and `ToolContext` are both aliases of `Context`, which
is [Day 11, part 1.3](../../../day-11-tool-context/parts/01-the-extra-parameter/1.3-one-card-several-doors.md)'s
one card, several doors. Same object, two names, and you must use the right *name* in the right place
even though the *type* is identical.

And the tool callbacks call the argument dictionary **`args`**, not `arguments` and not `tool_args`.
The plugin equivalents on Day 14 use `tool_args`, which is exactly the kind of near-miss that costs an
evening.

---

## Why Sutra needs it

**Every callback you write for the rest of the curriculum starts with this line.** Getting the names
wrong is not a subtle bug that shows up later; it is a `TypeError` on the first run. Knowing the
failure by sight turns a puzzling ten minutes into a five-second fix.

**Day 14's plugins use different names for the same values.** When you write a plugin tomorrow and
copy a callback into it, the names will not match. Knowing *why* they are load-bearing is what stops
you from copying and hoping.

**Day 39's `NodeTool` and Day 64's resumption hooks follow the same convention.** ADK is consistent
about this, which means the habit generalises: in this framework, read the parameter names off the
documentation and type them exactly.

---

## The mechanism

Here is the framework's own call site, from `google/adk/flows/llm_flows/base_llm_flow.py` in the
installed 2.7.1, with the comment ADK's authors wrote above it:

> ```
>     # The callback type aliases are declared positionally, but the framework
>     # has always invoked them by keyword.
>     agent_response = callback(  # type: ignore[call-arg]
>         callback_context=callback_context, llm_request=llm_request
>     )
> ```

That comment is unusually candid and it explains a real confusion. If you read ADK's type aliases you
will see `Callable[[CallbackContext, LlmRequest], ...]`, which is the notation for a **positional**
signature. The types say positional; the code says keyword. **The code is what runs.**

You can see it without a model. This script calls two functions the way ADK calls them:

```python
# lab/names.py - why the parameter names in your def line are not yours to choose.


def right(callback_context, llm_request):
    """The documented names. ADK's keyword call finds both parameters."""
    return f"ok: agent={callback_context}, model={llm_request}"


def wrong(context, request):
    """The same two values, renamed to taste. Same body, same order."""
    return f"ok: agent={context}, model={request}"


for fn in (right, wrong):
    try:
        # Exactly how google/adk/flows/llm_flows/base_llm_flow.py calls it.
        print(fn.__name__, "->", fn(callback_context="desk", llm_request="gemini"))
    except TypeError as exc:
        print(fn.__name__, "-> TypeError:", exc)
```

**Line by line:**

- `def wrong(context, request)` — the parameters are in the same order, hold the same values and have
  perfectly reasonable names. Nothing about the function's *logic* is wrong. That is the point: this
  is not a bug you can find by reading the body.
- The two functions are put in a tuple and looped over, so both are called with **identical**
  arguments. If the call differed between them the demo would prove nothing.
- `fn(callback_context="desk", llm_request="gemini")` — keyword arguments, copied from ADK's call
  site rather than invented. The values are strings because this part is about how the call is made,
  not about what is in the objects; [2.1](../02-the-model-doors/2.1-what-is-actually-in-the-request.md)
  opens the real `LlmRequest`.
- `except TypeError` catches only `TypeError`, because that is the specific failure being
  demonstrated. A bare `except` here would also swallow a typo in the script and print a misleading
  result.

The output:

```text
right -> ok: agent=desk, model=gemini
wrong -> TypeError: wrong() got an unexpected keyword argument 'callback_context'
```

Note *which* name the error complains about. Python reports the first keyword it could not place, so
the message says `callback_context` — the name you did **not** write. Read the message as *"you never
declared a parameter called this"*, not as *"this argument is bad"*.

## When it breaks

**💥 The real thing, inside a run.** Attach `wrong` to an agent and start it. The `TypeError` is
raised deep in ADK's flow and comes out through the workflow runtime:

```text
  File "...\google\adk\flows\llm_flows\base_llm_flow.py", line 268, in _handle_before_model_callback
    agent_response = callback(  # type: ignore[call-arg]
                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
TypeError: wrong() got an unexpected keyword argument 'callback_context'
Root node p failed.
google.adk.workflow._errors.DynamicNodeFailError: Dynamic node p failed
```

Three things to read out of that. The last frame names **your** function (`wrong()`), so the fix is
in your file even though every frame above it is ADK's. The `DynamicNodeFailError` underneath is the
graph runtime reporting that the node died — it is a wrapper, not the cause, so do not go looking for
a graph problem. And the run **stopped**: a callback that raises does not get skipped, it takes the
turn down with it. That is 1.x → 2.x **trap #4** working as designed — ADK 2.x surfaces exceptions
through the runtime instead of swallowing them (plan §5.1) — and it is the behaviour you want. A
policy hook that silently vanished would be worse than one that crashes loudly.

**💥 The extra parameter with no default.**

```text
TypeError: audit() missing 1 required positional argument: 'threshold'
```

You added a configuration parameter to your callback. ADK passes exactly the documented names and
nothing else, so anything extra must have a default value — or, better, be closed over:

```python
def make_audit(threshold: int):
    """Return a callback that already knows its threshold."""

    def audit(callback_context, llm_request):
        if len(llm_request.contents) > threshold:
            print("long history")

    return audit
```

**Line by line:**

- `make_audit` is a **factory**: it is not the callback, it *returns* the callback. You attach
  `make_audit(20)`, not `make_audit`.
- The inner `audit` has exactly the two documented parameters, so ADK's keyword call fits it.
- `threshold` is captured from the enclosing scope — a closure. This is the standard way to configure
  a callback, and it keeps the configuration out of the signature where ADK would trip over it.

## In production

**What a professional writes instead of the teaching version** is a callback whose parameters are
**type-annotated with ADK's own classes**, so an editor autocompletes `llm_request.contents` and a
type checker catches a misspelling before the run does:

```python
from google.adk.agents.callback_context import CallbackContext
from google.adk.models import LlmRequest


def audit_model(callback_context: CallbackContext, llm_request: LlmRequest) -> None:
    """Watch outgoing model traffic. Never interferes."""
    print(f"[audit] agent={callback_context.agent_name} turns={len(llm_request.contents)}")
```

**Line by line:**

- `CallbackContext` is imported from `google.adk.agents.callback_context` and `LlmRequest` from
  `google.adk.models` — the two import paths ADK's own flow module uses. In 2.7.1 `CallbackContext` is
  an alias of `Context`; importing the alias keeps the code readable and survives if the alias moves.
- `-> None` is the return annotation, and it is a small act of honesty: this function is an
  **observer**, and the type says it can never accidentally override anything. A reviewer reading only
  the signature knows what door this is.
- The body has no `return`, which is what makes the annotation true. [1.3](1.3-none-means-carry-on.md)
  is why that matters more than it looks.

**What degrades at scale** is the copy-paste. Six hooks, three of them sharing `tool`/`args`, two
sharing `callback_context`/`llm_request`, and a plugin API tomorrow that renames `args` to
`tool_args`. Once a codebase has a dozen callbacks, the failures stop being "I misnamed a parameter"
and become "I pasted the tool signature into a model hook". The defence is annotations plus a type
checker, which is exactly the decision waiting at the Day 31 quality gate.

**The failure that only shows with real traffic** is the error-hook typo. `before_tool_callback` fires
on every run and you find a bad signature in seconds. `on_tool_error_callback` fires only when a tool
raises — which may be never in staging — so a misnamed parameter there sits quietly until the first
production outage, and then turns a handled error into a crash **inside the error handler**. Test the
error hooks deliberately; [6.1](../06-in-production/6.1-testing-a-callback-without-a-model.md) shows
how, for free.

**The review comment a senior engineer leaves:** *"Annotate these with `CallbackContext` and
`LlmRequest`. The names are an interface here, and right now nothing but a full run will tell us if
one of them is wrong."*

**The interview question:** *"How does the framework know which argument is which in your callback?"*
The answer that shows you have wired one: "It doesn't infer anything — it calls by keyword, so my
parameter names are the interface. ADK's own source has a comment saying the type aliases look
positional but the framework has always invoked them by keyword, which is why a perfectly sensible
rename produces `TypeError: got an unexpected keyword argument`. Practically that means I copy the
names off the docs, annotate them with ADK's classes so the editor helps, and configure a callback
with a closure rather than by adding a parameter."
