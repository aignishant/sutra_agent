# 1.3 — `None` means carry on

## One-line answer

Every one of the six doors obeys one rule: return `None` and the thing behind the door happens
normally; return anything else and **your value replaces it**, so the model call or the tool call
never occurs at all.

---

## The story

The pharmacy counter, and what happens after you hand over the prescription.

You put the slip on the counter. The pharmacist reads it. Most of the time she says nothing, turns
around, walks to the shelves and comes back with a box. The slip did its job and the shelf visit
happened.

But sometimes she reads it, and without moving from the counter she hands you something back — a
different box, or the slip itself with "we don't stock this, try the one across the road" written on
it. And notice what did *not* happen: she never went to the shelf. The moment she put something in
your hand, the trip behind the counter was cancelled.

You cannot tell from where you stand which of the two she is about to do. The only signal is whether
something comes back across the counter *immediately*. Nothing back means the shelf. Something back
means no shelf.

That is the entire return-value rule, and it is why an absent-minded pharmacist who hands you her
notepad because she was holding it is a real problem.

---

## The idea in plain language

A Python function always returns something. If you write no `return`, or a bare `return`, the value
is `None` — a real object meaning *nothing here*.

ADK reads that value as an answer to one question: **did you handle this?**

- `None` means *"I did not handle it. Carry on."* The model gets called. The tool gets run. Your
  function was an **observer**.
- Anything else means *"I have handled it. Here is the result."* The model does **not** get called.
  The tool does **not** get run. Your function was an **override**.

One rule, six doors:

| Door | Return `None` | Return a value |
| --- | --- | --- |
| `before_model_callback` | the model is called | your `LlmResponse` is used and **the model is never called** |
| `after_model_callback` | the real reply is used | your `LlmResponse` **replaces** the real reply |
| `before_tool_callback` | the tool function runs | your `dict` is the result and **the tool never runs** |
| `after_tool_callback` | the real result is used | your `dict` **replaces** the real result |
| `on_model_error_callback` | the exception is re-raised | your `LlmResponse` is used and the error is swallowed |
| `on_tool_error_callback` | the exception is re-raised | your `dict` is used and the error is swallowed |

ADK's own field documentation says it in one sentence per door. For `before_tool_callback`:

> *"The tool response. When present, the returned tool response will be used and the framework will
> skip calling the actual tool."*

Two consequences follow immediately, and they are the reason this part exists.

**An observer must return nothing.** Not `return args`, not `return summary`, not `return True`. A
logging function that ends with a `return` has stopped being a logging function; it is now an
override that silently substitutes its debug data for a real result. That is
[5.1](../05-failure-lab/5.1-the-note-that-became-the-result.md), and it is today's deliberate failure
because it produces no error whatsoever.

**An override must be honest about what it is.** If you veto a tool call, the value you return is
handed to the model *as if the tool had produced it*. Returning `{"result": "ok"}` is not a refusal;
it is a lie your own agent will then reason over. Principle 10 applies to the code you write about
your agent, not only to the agent. [3.2](../03-the-tool-doors/3.2-refusing-a-tool-call-honestly.md) is
the shape of an honest refusal.

There is one wrinkle in the rule as stated, and it is genuinely surprising: ADK does not test your
return value against `None`, it tests it for **truthiness**, so an empty dictionary is not the "carry
on" value you would expect. That has a part of its own —
[4.1](../04-where-the-rule-bites/4.1-truthy-is-not-the-same-as-not-none.md) — because it deserves the
space and because you need the ordinary rule solid before the exception makes sense.

---

## Why Sutra needs it

**It is the difference between watching Sutra and controlling it.** Today's build attaches one
observer and one override to the desk agent. If you cannot say which is which from the `return`
statements, the two behave identically right up until the day the observer eats a knowledge-base
result.

**Day 51's cache is this rule and nothing else.** A response cache is a `before_model_callback` that
returns `None` on a miss and an `LlmResponse` on a hit. The cache logic is the interesting part; the
mechanism is one `if`.

**Day 67's guardrails are the same rule at the other door.** Return `None` when the reply is fine,
return a replacement when it is not.

---

## The mechanism

The clearest demonstration needs no model at all, because you can call the callback yourself and read
what it returned. But it is much more convincing to watch ADK act on the value, so this script drives
a real run against a **scripted model** — a local model object that reads its replies off a list
instead of calling an API. It costs nothing and needs no key.

You will write `lab/scripted.py` once and every later script imports it:

```python
# lab/scripted.py - a model that reads its replies off a list. No network, no key, no quota.
from __future__ import annotations

from collections.abc import AsyncGenerator

from google.adk.models import BaseLlm, LlmRequest, LlmResponse
from google.genai import types


class ScriptedModel(BaseLlm):
    """Yields pre-written replies, one turn at a time, and counts the calls."""

    replies: list[list[types.Content]] = []
    calls: int = 0

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        turn = self.replies[min(self.calls, len(self.replies) - 1)]
        self.calls += 1
        for content in turn:
            yield LlmResponse(content=content)


def call(name: str, **args: object) -> types.Content:
    """A model turn that asks for one tool call."""
    return types.Content(
        role="model",
        parts=[types.Part(function_call=types.FunctionCall(name=name, args=args))],
    )


def text(body: str) -> types.Content:
    """A model turn that is plain text."""
    return types.Content(role="model", parts=[types.Part(text=body)])
```

**Line by line:**

- `class ScriptedModel(BaseLlm)` — ADK's model layer is an abstract class, not a hard-coded provider,
  so a subclass is a first-class model everywhere a model string would go. This is the seam that makes
  today's entire lab free.
- `replies: list[list[types.Content]]` — a list **of turns**, each turn a list of `Content`. The outer
  list is "what the model says on call 1, call 2, …"; the inner list exists because one model call can
  yield several responses, which is
  [2.5](../02-the-model-doors/2.5-the-door-that-fires-on-every-chunk.md)'s whole subject.
- `calls: int = 0` — declared as a Pydantic field rather than set in an `__init__`, because `BaseLlm`
  is a Pydantic model and an undeclared attribute would be rejected. It is the counter that proves a
  short-circuit really skipped the model.
- `async def generate_content_async(...)` with `yield` — the one abstract method `BaseLlm` requires,
  and it is an **async generator**. Yielding rather than returning is 1.x → 2.x **trap #3** (plan
  §5.1): components stream events as they happen instead of collecting a list and returning it. A
  fake that returned a list would not fit the runtime at all.
- `min(self.calls, len(self.replies) - 1)` — clamps to the last scripted turn, so a run that makes one
  more model call than you planned repeats the last reply instead of raising `IndexError`. A test
  double should fail on the thing you are testing, not on its own bookkeeping.
- `stream: bool = False` — part of the abstract signature; the scripted model ignores it because it
  yields whatever the script says regardless.
- `call()` and `text()` are two-line helpers so the scripts below read as *what the model said*
  rather than as `types.Content` construction. `**args: object` takes the tool arguments as keywords.

Now the rule itself, watched three times:

```python
# lab/one_rule.py - None carries on; a value replaces. Zero model calls billed anywhere.
import asyncio

from google.adk.agents import LlmAgent
from google.adk.models import LlmResponse
from google.adk.runners import InMemoryRunner
from google.genai import types
from scripted import ScriptedModel, call, text


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by id."""
    print("    the tool actually ran")
    return {"status": "ok", "ticket_id": ticket_id, "body": "charged twice"}


def observe(callback_context, llm_request):
    """An observer. No return statement, so it returns None: carry on."""
    print(f"    observer saw a request to {llm_request.model}")


def override(callback_context, llm_request):
    """An override. Returns a reply, so the model is never called."""
    return LlmResponse(content=text("pong - the desk is up."))


def veto(tool, args, tool_context):
    """An override at the tool door. The tool never runs."""
    return {"status": "blocked", "message": "not today"}


async def drive(agent: LlmAgent) -> list[str]:
    """Run one message through an agent and collect what came back."""
    runner = InMemoryRunner(agent=agent)
    session = await runner.session_service.create_session(app_name=runner.app_name, user_id="u")
    out: list[str] = []
    async for event in runner.run_async(
        user_id="u",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="ticket 4521")]),
    ):
        for part in (event.content.parts if event.content else []) or []:
            if part.function_response:
                out.append(f"tool result: {part.function_response.response}")
            elif part.text:
                out.append(f"text: {part.text}")
    return out


def build(**callbacks) -> tuple[ScriptedModel, LlmAgent]:
    """A fresh agent and a fresh counter for each experiment."""
    model = ScriptedModel(
        model="scripted",
        replies=[[call("lookup_ticket", ticket_id="4521")], [text("Billing. Refund issued.")]],
    )
    agent = LlmAgent(
        name="desk",
        model=model,
        instruction="Triage the ticket.",
        tools=[lookup_ticket],
        **callbacks,
    )
    return model, agent


async def main() -> None:
    print("1. observer at the model door (returns None)")
    model, agent = build(before_model_callback=observe)
    print("   ", await drive(agent), "| model calls:", model.calls)

    print("2. override at the model door (returns an LlmResponse)")
    model, agent = build(before_model_callback=override)
    print("   ", await drive(agent), "| model calls:", model.calls)

    print("3. override at the tool door (returns a dict)")
    model, agent = build(before_tool_callback=veto)
    print("   ", await drive(agent), "| model calls:", model.calls)


asyncio.run(main())
```

**Line by line:**

- `from scripted import ScriptedModel, call, text` — a plain module import, which works because the
  script is run from inside `lab/`. The hub's §3 gives the exact command.
- `observe` has **no `return` statement at all**. That is deliberate and it is the house style for an
  observer: an explicit `return None` is also correct, but a function with no `return` cannot acquire
  one by accident during a later edit.
- `override` returns `LlmResponse(content=text("..."))`, reusing the `text` helper. An `LlmResponse`
  is what the model layer produces, so handing one back is handing the flow a ready-made reply.
- `veto` returns a dict with a `status` key rather than a bare string, which is
  [Day 10, part 2.1](../../../day-10-function-tools/parts/02-what-a-tool-returns/2.1-return-a-dict-with-a-status.md)'s
  rule applied to a value that is *pretending* to be a tool result.
- `drive` uses `run_async`, not `run`. The synchronous `run` is deprecated in 2.7.1 and prints
  `Deprecated. Please migrate to the async method.` — [Day 5, part 4.3](../../../day-05-first-adk-agent/parts/04-the-runner/4.3-read-the-signature-not-the-tutorial.md)'s
  rule about reading the installed signature instead of a tutorial.
- `(event.content.parts if event.content else []) or []` — events legitimately arrive with no content,
  and `parts` is itself optional. Two guards, because a `TypeError` here would be blamed on the
  callback.
- `build(**callbacks)` returns **both** the model and the agent, because `model.calls` is the evidence
  and a shared model object between experiments would carry its count across.
- Each experiment builds a fresh agent, so experiment 2's zero is really zero.

The output:

```text
1. observer at the model door (returns None)
    observer saw a request to scripted
    the tool actually ran
    observer saw a request to scripted
    ["tool result: {'status': 'ok', 'ticket_id': '4521', 'body': 'charged twice'}", 'text: Billing. Refund issued.'] | model calls: 2
2. override at the model door (returns an LlmResponse)
    ['text: pong - the desk is up.'] | model calls: 0
3. override at the tool door (returns a dict)
    ["tool result: {'status': 'blocked', 'message': 'not today'}", 'text: Billing. Refund issued.'] | model calls: 2
```

Read the three results against each other.

In **1**, the observer fired twice — once for each model call — and changed nothing. The tool ran. The
answer is the scripted one. An observer is invisible in the output, which is exactly what makes a
stray `return` in one so dangerous.

In **2**, `model calls: 0`. Not "the reply was ignored": the model layer was never entered. On a real
provider that is a request that was never sent, a token that was never spent and a rate limit that was
never touched. [2.3](../02-the-model-doors/2.3-the-call-that-never-happened.md) is what that is worth.

In **3**, `the tool actually ran` is **absent** from the output, and the refusal dict is sitting where
the tool's result would have been — and the model then went on to produce a final answer from it.
The tool did not run. The model does not know that.

## When it breaks

**💥 The refusal that reads as success.** No error, no traceback.

Return `{"result": "no matching articles"}` from a `before_tool_callback` and the model receives a
tool result saying the knowledge base was searched and found nothing. It was not searched. The model
now believes a fact about the world that came from your policy code, and it will tell the user so, in
its own confident voice. There is nothing in the logs to distinguish this from a genuine empty
search.

**💥 The observer with a return.** Also no error. Covered in full in
[5.1](../05-failure-lab/5.1-the-note-that-became-the-result.md), because a failure with no error
message deserves a document rather than a paragraph.

**💥 The override that returned the wrong type.**

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for LlmResponse
```

You returned a plain string from a `before_model_callback` because the docstring says *"the content to
return to the user"*. It wants an `LlmResponse`. The model doors trade in `LlmResponse` objects; the
tool doors trade in dicts. Mixing them is the one shape error the framework catches for you.

## In production

**What a professional writes instead of the teaching version** is a callback whose return type
annotation states which kind it is, every time:

| Intent | Signature ends with | Body |
| --- | --- | --- |
| observer | `-> None` | no `return` at all |
| override | `-> LlmResponse \| None` or `-> dict \| None` | `return None` on the paths that carry on |

The `| None` on an override is not decoration. An override that can only override is a policy with no
default, and the first request that does not match its condition falls off the end of the function —
returning `None`, which happens to be right, but by accident rather than by design.

**What degrades at scale** is auditability. Once several people are adding callbacks, "is this an
observer or an override?" becomes a question you cannot answer by reading the attachment site, only by
reading every branch of the function body. Teams that run a lot of these end up enforcing the
annotation in review or with a linter, because the failure mode is silent and the fix is a habit.

**The failure that only shows with real traffic** is the conditional override. A callback that
returns a value on one branch and falls off the end on all the others is correct on the branch you
tested. In production the rare branch fires, returns a half-built dict, and the model reasons over it.
The defence is a test per branch, which costs nothing —
[6.1](../06-in-production/6.1-testing-a-callback-without-a-model.md).

**The review comment a senior engineer leaves:** *"This one is annotated `-> None` but has a `return
result` on line 14. Either it's an override and the annotation is wrong, or that line replaces every
tool result in the system with a log record."*

**The interview question:** *"How does a callback tell the framework to block something?"* The answer
that shows you have wired one: "By returning a value instead of `None`. There's a single rule across
all the hooks: `None` means 'I didn't handle this, carry on' and anything else means 'here's the
result, don't do the underlying thing'. So a before-tool hook that returns a dict vetoes the tool —
the function genuinely never executes, and the dict is handed to the model as though it were the
tool's output. The sharp edge is that observers and overrides look identical at the attachment site,
so a stray `return` in a logging hook silently substitutes debug data for real results with no error
anywhere."
