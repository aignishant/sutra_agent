# 3.1 — The chokepoint, restored

## One-line answer

`before_tool_callback` runs immediately before every tool call with the tool object, the parsed
arguments and the session context in hand — which makes it the single place in an ADK agent where
every tool call can be seen, counted and decided on, no matter which entry point started the run.

---

## The story

The store room register.

A workshop with a locked store room and one storekeeper. Nobody takes a part off a shelf. You walk to
the window, say what you need and which job it is for, and he writes a line in a register: date, part,
quantity, job number, your name. Then he hands it over.

The register is not there to slow anybody down. It is there because on the day a job goes wrong,
somebody will ask *what went into it*, and the only honest answer comes from a book where every
withdrawal is a line. A workshop where anybody can reach a shelf has no such book, and nobody notices
this until the day they need one.

And because there is exactly one window, the storekeeper can also say no. Not often — but the ability
exists, and it exists because of the window, not because of a rule on a poster.

---

## The idea in plain language

On [Day 3](../../../day-03-loop-hand-rolled/parts/02-tools-and-dispatch/2.2-the-dispatch-table-is-the-boundary.md)
you wrote the loop yourself, and every tool call went through one dictionary lookup you owned. That
line was the window. On [Day 10](../../../day-10-function-tools/parts/03-the-dispatch-you-deleted/3.1-what-the-courier-took.md)
ADK took over dispatch and the window closed.

`before_tool_callback` is the window, reopened — and it sees more than the dictionary did. It is
handed three things:

| Parameter | What it is | What you can do with it |
| --- | --- | --- |
| `tool` | the `BaseTool` object about to run | `tool.name`, `tool.description`, and its declaration |
| `args` | a `dict` of the arguments **the model chose** | inspect, validate, or edit them in place |
| `tool_context` | the same `Context` object a tool receives | read and write session state, get `agent_name`, `invocation_id` |

The third one is what makes this genuinely more powerful than Day 3's dictionary. Policy can be
**state-aware**. "This session has already searched the knowledge base three times" is a sentence a
dispatch table cannot express and this callback can, because `tool_context.state` is the same session
state [Day 11, part 2.1](../../../day-11-tool-context/parts/02-state-from-a-tool/2.1-writing-on-the-carbon-copy.md)
taught you to write from inside a tool.

`args` deserves one more sentence. These are the arguments **after** the model produced them and
**before** the tool validates them, which means this is the earliest point in the program where you
can see what the model actually decided to ask for. On
[Day 4, part 4.1](../../../day-04-tools-by-hand/parts/04-the-limits/4.1-validated-is-not-correct.md)
you learned that a schema checks shape and not sense; this hook is where a human's judgement about
sense gets to run.

And `args` is a real dictionary, passed by reference, exactly like
[2.2](../02-the-model-doors/2.2-editing-the-request-in-place.md)'s request. Mutating it changes what
the tool receives, while still returning `None` so the tool runs.

---

## Why Sutra needs it

**Sutra's audit trail moves inside the agent today.** Day 11's prints live in `run_once`, so an `adk
web` session produces no record at all. Moving them here means the register is written no matter who
opened the door.

**The search budget from [2.2](../02-the-model-doors/2.2-editing-the-request-in-place.md) is counted
here.** That part's `state["kb_searches"]` has to be incremented by somebody, and this is the door
that sees every search.

**Every containment day from here leans on it.** Day 21's error handling, Day 30's SEC work, Day 64's
human-in-the-loop approval — all of them need one place that sees a tool call before it happens, and
this is that place.

## The mechanism

```python
# lab/register.py - one window, every tool call, written in a book. Zero model calls.
import asyncio

from google.adk.agents import LlmAgent
from google.adk.runners import InMemoryRunner
from google.genai import types
from scripted import ScriptedModel, call, text


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id in the ticket system."""
    return {"status": "ok", "ticket_id": ticket_id, "body": "Charged twice in March."}


def search_kb(query: str) -> dict:
    """Search the knowledge base for articles matching a query."""
    return {"status": "ok", "hits": ["KB-104: duplicate charge on renewal"]}


def register(tool, args, tool_context):
    """Observer at the tool door. Writes the line, counts the searches, carries on."""
    if tool.name == "search_kb":
        used = tool_context.state.get("kb_searches", 0)
        tool_context.state["kb_searches"] = used + 1
    print(
        f"    [register] invocation={tool_context.invocation_id[:8]} "
        f"agent={tool_context.agent_name} tool={tool.name} args={args}"
    )


agent = LlmAgent(
    name="desk",
    model=ScriptedModel(
        model="scripted",
        replies=[
            [call("lookup_ticket", ticket_id="4521")],
            [call("search_kb", query="duplicate charge renewal")],
            [call("search_kb", query="refund policy")],
            [text("KB-104 covers this. Refund issued.")],
        ],
    ),
    instruction="Triage the ticket.",
    tools=[lookup_ticket, search_kb],
    before_tool_callback=register,
)


async def main() -> None:
    runner = InMemoryRunner(agent=agent)
    session = await runner.session_service.create_session(app_name=runner.app_name, user_id="u")
    async for _ in runner.run_async(
        user_id="u",
        session_id=session.id,
        new_message=types.Content(
            role="user", parts=[types.Part(text="ticket 4521, charged twice")]
        ),
    ):
        pass
    after = await runner.session_service.get_session(
        app_name=runner.app_name, user_id="u", session_id=session.id
    )
    print(f"    session state afterwards: {dict(after.state)}")


asyncio.run(main())
```

**Line by line:**

- Two tools, because a register with one tool in it does not show that `tool.name` is the thing you
  branch on. The counting applies to `search_kb` only.
- `tool_context.state.get("kb_searches", 0)` then assignment — read, add, write. This is
  [Day 11, part 2.1](../../../day-11-tool-context/parts/02-state-from-a-tool/2.1-writing-on-the-carbon-copy.md)'s
  mechanism unchanged: the write goes into `event_actions.state_delta` and the session service applies
  it when the event is appended. **There is no separate callback state.**
- `tool_context.invocation_id[:8]` — the run's identity, truncated for a readable line. It is the
  field that lets a log line from this door be joined to one from
  [2.1](../02-the-model-doors/2.1-what-is-actually-in-the-request.md)'s model door.
- `args={args}` prints the whole argument dict. In production this is the line that needs thinking
  about, because arguments contain whatever the model put in them — see *In production*.
- No `return` — the register is an observer, and the tool runs.
- The four scripted turns are one lookup, two searches, then the answer, so the counter has something
  to count and the session state at the end is checkable.
- `get_session` **after** the run, rather than reading `session.state` on the object we already have.
  State is applied when events are appended, so the object from before the run is stale — the
  session has to be fetched again, which is
  [Day 8, part 2.2](../../../day-08-sessions-and-services/parts/02-the-run/2.2-the-complaint-book.md)'s
  point about the log being the record.

The output:

```text
    [register] invocation=e-4678da agent=desk tool=lookup_ticket args={'ticket_id': '4521'}
    [register] invocation=e-4678da agent=desk tool=search_kb args={'query': 'duplicate charge renewal'}
    [register] invocation=e-4678da agent=desk tool=search_kb args={'query': 'refund policy'}
    session state afterwards: {'kb_searches': 2}
```

Three lines, one invocation id, and a counter that survived the run. Your invocation id will be a
different random string; it is the *sameness* down the column that matters.

The invocation id is the same on all three because they are one user request. Every log line from this
door can be joined to every other line from the same request, which is what turns a pile of prints
into a trace.

And `kb_searches: 2` is in **session state**, not in a variable in your module. The next turn of this
same conversation can read it. A different user's session has its own. That is the difference between
a counter and a global, and it is the whole reason `tool_context` is a parameter.

Verified against `adk.dev/callbacks/types-of-callbacks/` and the installed `google-adk` 2.7.1
(the `for before_callback in agent.canonical_before_tool_callbacks:` loop in
`google/adk/flows/llm_flows/functions.py`) on 2026-08-29.

## When it breaks

**💥 The argument that was not there.**

```text
KeyError: 'query'
```

You wrote `args["query"]` in a callback attached to an agent with two tools, and it fired for
`lookup_ticket`, which has no `query`. Branch on `tool.name` **first**, or use `args.get("query", "")`.
A tool-door callback sees *every* tool, including ones added after you wrote it — and including one
you did not write at all, which is
[4.3](../04-where-the-rule-bites/4.3-the-tool-you-did-not-write.md).

**💥 The counter that counted every user.** No error, and wrong numbers. You wrote
`SEARCHES += 1` against a module-level integer. It is shared by every session on the process, so two
users searching once each produce a count of two for both of them. This is
[Day 11, part 5.1](../../../day-11-tool-context/parts/05-failure-lab/5.1-the-previous-patients-file.md)'s
failure arriving through a new door.

**💥 The register that logged a password.** No error. `args` for `search_kb` is whatever the model
decided to search for, and if the customer's ticket contained a credential the model may well have put
it in the query. Printing `args` unconditionally puts it in your logs.

## In production

**What a professional writes instead of the teaching version** logs the *shape* of the arguments and
not their values, unless a specific argument has been reviewed as safe:

```python
SAFE_TO_LOG = {"ticket_id", "article_id", "page"}


def register(tool, args, tool_context) -> None:
    """One structured line per tool call. Values only for reviewed argument names."""
    logger.info(
        "tool_call",
        extra={
            "invocation": tool_context.invocation_id,
            "agent": tool_context.agent_name,
            "tool": tool.name,
            "arg_names": sorted(args),
            "args": {k: v for k, v in args.items() if k in SAFE_TO_LOG},
        },
    )
```

**Line by line:**

- `SAFE_TO_LOG` is an **allow-list**, not a deny-list. A deny-list of forbidden argument names fails
  open: the first tool somebody adds with an argument called `credential` is logged in full. An
  allow-list fails closed, which is the direction you want a mistake to fall.
- `sorted(args)` gives the argument **names** always, because knowing that `search_kb` was called with
  a `query` is useful and knowing what the query said is a liability.
- `tool.name` rather than `type(tool).__name__` — the name is what the model used, what the
  declaration advertises, and what a policy branches on. The class is an implementation detail.
- `-> None` and no `return`: an observer, stated in the signature.

**What degrades at scale** is the log volume. One line per tool call sounds small until an agent makes
six tool calls per turn across thousands of turns. The cost is real and the usual answer is sampling —
but sample the *ordinary* calls and keep every refusal, because the refusals are the lines somebody
will come looking for.

**The failure that only shows with real traffic** is the tool added later. Your callback branches on
two tool names and does nothing for anything else, which is correct until the day somebody adds a
third tool and it is not audited. Nothing fails. The register is simply incomplete, and it looks
complete. A callback that logs *every* call and branches only for extra behaviour does not have this
problem.

**The review comment a senior engineer leaves:** *"Don't log `args` wholesale. The `query` argument is
model-generated from customer text and we've already had one ticket with a password pasted into it.
Log the argument names, allow-list the values."*

**The interview question:** *"Where does an agent's audit trail come from?"* The answer that shows you
have built one: "The before-tool hook, because it's the one place every tool call passes through
regardless of entry point — a script, the dev UI, a scheduled run. It gets the tool object, the parsed
arguments and the session context, so a line has the invocation id to correlate on and the session
state to make the policy stateful. The two things I'd get right: log argument *names* by default and
allow-list any values, because those arguments are model-generated from customer text; and log every
call, branching only for extra behaviour, so a tool somebody adds next year is audited without anybody
remembering to update the callback."
