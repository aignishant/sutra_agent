# 1.2 — Who can change the text after you read it

## One-line answer

The property that orders the trust gradient is mutability — whether the exact text you audited can
change after you audit it — and the whole reason to pin a skill to an exact revision is to convert a
source that *can* change under you into one that *cannot*.

## The story

The doctor writes a prescription, signs it, and hands it to you to take to the pharmacy.

The pharmacist reads it and gives you exactly what is written — this medicine, this dose, this many.
The signature is what makes that safe: it fixes the instruction at the moment the doctor took
responsibility for it. What the pharmacist dispenses is what the doctor signed.

Now imagine the paper could be edited on the walk to the pharmacy. Someone changes the dose, or adds a
line, and the signature still sits at the bottom looking exactly as trustworthy as before. The
pharmacist reads a signed prescription and dispenses something the doctor never approved. The
signature has not been forged — it is real — it just no longer refers to the text above it, because the
text moved after it was signed.

That is the difference between a prescription and a shouted instruction across a waiting room. Not who
said it. Whether it can change between the moment it was approved and the moment it is acted on.

## The idea in plain language

Every door in [1.1](1.1-the-four-doors.md) hands your agent some text. The audit ([Section 2](../02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md))
is you reading that text and deciding it is safe to obey. That decision is only worth something if the
text your agent obeys is the same text you read. The property that decides whether that holds is
**mutability**: can the exact bytes change after you have read them, without you reading them again?

Line the four doors up against that one question:

- **Your repository:** immutable unless *you* change it, and when you do it is a commit with your name
  on it. The text your agent runs is the text in your last commit.
- **A community repository, installed from a branch:** mutable by the maintainer at any time. `main`
  today is not `main` next week. You read one thing; your next `git pull` runs another, silently.
- **A community repository, pinned to a commit:** immutable. A commit hash names an exact snapshot of
  every byte. The maintainer can publish a hundred new commits and the one you pinned does not move.
- **A managed registry:** fetched at runtime, so the text arrives *after* your last read by definition
  ([5.1](../05-the-registry/5.1-search-fetch-and-parked.md)). This is the un-pinnable case, and it is
  why the registry is a different problem from the other three.

The move that saves you is **pinning**: recording the exact revision you audited so that the audited
text is the text that runs. A **commit hash** — a long string like `8b78b53...` that names one exact
snapshot of a repository — is the pin. Pinning turns the shouted instruction back into the signed
prescription. It is not a nicety; it is the thing that makes an audit mean anything at all, because an
audit of text that can change afterwards is an audit of nothing.

## Why Sutra needs it

Because Sutra's own provenance ledger has lived this rule since before it had a single runtime skill.

Open `docs/SKILL_PROVENANCE.md`. The driver skills that Claude Code itself uses each carry a note like
`Pinned @ 8b78b53` — a commit hash, recorded at audit time, so the text that was read is the text that
runs. That discipline exists precisely because those skills came through the community door, and the
only way to make a community skill safe to obey is to freeze the exact revision you checked.

Day 29 makes the rule explicit and then leans on it twice. The provenance row you draft in
[4.1](../04-provenance/4.1-no-row-no-run.md) carries the pin. The drift check in
[4.2](../04-provenance/4.2-the-pin-is-the-promise.md) *proves* the pin — it hashes the files on disk and
compares them to the recorded pin, going red the moment a single byte differs. And the reason the
managed registry is parked rather than merely audited ([5.1](../05-the-registry/5.1-search-fetch-and-parked.md))
is this exact property: a runtime fetch cannot be pinned, so it cannot be audited in the sense this day
means.

## The mechanism

A pin is a content hash. You do not need a registry or even git to see why it works — you need the fact
that a hash of the bytes changes when the bytes change. Here is the idea reduced to what the drift check
([4.2](../04-provenance/4.2-the-pin-is-the-promise.md)) will build on:

```python
import hashlib
import pathlib


def pack_digest(root: pathlib.Path) -> str:
    """One hash over every path and every byte in a skill folder, in sorted order."""
    running = hashlib.sha256()
    for path in sorted(p for p in root.rglob("*") if p.is_file()):
        running.update(path.relative_to(root).as_posix().encode())
        running.update(path.read_bytes())
    return running.hexdigest()
```

**Line by line:**

- `hashlib.sha256()` starts a running hash. Feeding it the same bytes always yields the same digest, and
  changing any byte changes the digest completely. That is the property a pin needs: it is a fingerprint
  of the exact text.
- `sorted(...)` fixes the order files are fed in, so the digest depends only on the *content* of the
  folder and not on the order the filesystem happened to list it. Without this, two identical folders
  could hash differently and the pin would be useless.
- `path.relative_to(root).as_posix()` feeds the **name** into the hash as well as the bytes, so a file
  being renamed — or a new empty file appearing — changes the digest. A pin has to notice a file added,
  not only a file edited.
- `path.read_bytes()` reads raw bytes, not decoded text, so a change to line endings or an invisible
  character is caught. The pin is byte-exact on purpose.
- The digest this returns is the pin. Recorded at audit time, it answers one question later: is the text
  on disk still the text I read? A commit hash answers the same question for a whole git repository; this
  answers it for a vendored folder with no git history of its own.

## When it breaks

**Pinning to a branch instead of a commit.** `@main` is not a pin — it is a *name* that points at
whatever the latest commit happens to be, and it moves every time the maintainer pushes. It looks like a
pin in a config file and behaves like a live subscription to someone else's changes. Pin to the hash the
branch pointed at, not to the branch.

**A pin recorded but never checked.** A hash in a ledger that nothing verifies is a comment. The whole
value appears only when something compares the recorded pin to the bytes on disk and can go red — which
is why [4.2](../04-provenance/4.2-the-pin-is-the-promise.md) is a runnable check, not a paragraph.

**Trusting a signature over the mutability question.** A signed or starred repository still fails if you
install from its moving branch: the signature was true of the commit it was made on, exactly like the
prescription's signature was true of the dose the doctor wrote. Signing and pinning answer different
questions — *who produced this* versus *is this still what they produced* — and you need both. The
paper this day teaches makes the deeper version of the same point: even a correct read of correct source
does not tell you what the build produced ([the paper](../../papers/01-reflections-on-trusting-trust.md)).

## In production

**A professional pins with a hash and verifies the hash in CI.** A dependency in a real system is not
"the latest version of X"; it is "X at exactly this hash, and the build fails if the hash on disk does
not match the lockfile". This is the same discipline `uv.lock` already gives Sutra's Python packages —
an exact version and a content hash per dependency — applied to skills, which have no package manager of
their own yet.

**What changes at scale** is that mutability becomes a fleet property, not a per-skill one. With one
skill you can eyeball the pin. With forty, you need the equivalent of a lockfile: a single file that
records the audited revision of every sourced skill, checked on every build, so that a maintainer
force-pushing over a tag turns a green pipeline red instead of quietly changing what your agents obey.
That is where this day's small `pack_digest` grows into infrastructure.

**The failure mode that only appears with real traffic** is the account takeover. A community
repository you trusted for a year gets its maintainer account compromised, and one force-push flips
every unpinned install hostile on the next fetch — with no diff for you to review, because you were
tracking a branch, not a commit. Pinning is the only defence that was in place *before* the takeover,
which is the only time defences count.

**The review comment a senior engineer leaves:** *"you pinned this to `@main`. That's not a pin, it's a
subscription — resolve it to the commit hash you actually audited and put that in the lockfile, so a
force-push upstream fails our build instead of changing our agent's behaviour behind our backs."*

**The interview question:** *"what does it mean to pin a dependency, and why does an audit need it?"*
The honest spoken answer: *"Pinning records the exact revision — a commit hash, a content hash — so the
thing you audited is the thing that runs. An audit is a claim about specific bytes; if those bytes can
change after you read them, the claim is void. Branches move, so `@main` isn't a pin, it's a live feed
of someone else's changes. The subtle part is that signing and pinning are different: a signature tells
you who produced a revision, a pin tells you you're still on that revision. You need both, and you need
the pin checked in CI so drift turns the build red rather than changing behaviour silently."*

```bash
uv run python -c "
import hashlib, pathlib
def digest(root):
    h = hashlib.sha256()
    for p in sorted(x for x in pathlib.Path(root).rglob('*') if x.is_file()):
        h.update(p.relative_to(root).as_posix().encode()); h.update(p.read_bytes())
    return h.hexdigest()[:16]
print(digest('skills/ticket-triage'))
"
```

Run it, note the digest, then add a single space to the skill's `SKILL.md` and run it again. One
character, a completely different digest — that is what a pin detects.
