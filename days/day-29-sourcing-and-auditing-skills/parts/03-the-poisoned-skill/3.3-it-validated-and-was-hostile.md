# 3.3 — 💥 It validated, and it was hostile

## One-line answer

Mechanical validation and human audit answer different questions — *"is this a well-formed skill?"*
versus *"should this agent obey it?"* — and only the second is security, which is why the poisoned
fixture passes the spec validator cleanly and fails the audit on three counts.

## The story

The kettle has the safety mark stamped on the base, and the safety mark is telling the truth.

It means a laboratory checked that the kettle is a kettle: the plug is wired correctly, the element is
insulated, it switches off when it boils, it will not give you a shock under the conditions the standard
tests. That is a real check and a valuable one, and a kettle without the mark is one you should not buy.

It does not mean the kettle is safe on *your* wiring. It says nothing about the extension lead you will
plug it into, the socket that runs warm, the outlet already carrying the fridge and the microwave. The
mark answers *"is this a properly made kettle?"* — a question about the object in isolation — and you
are asking *"is it safe in my kitchen?"*, which is a question about the object plus everything around it.
Both questions are worth answering. They are not the same question, and the mark only answers the first.

## The idea in plain language

A skill goes through two checks that are easy to confuse because both produce a green result.

**Validation** is mechanical and automatable. The `skills-ref` validator
([Day 25](../../../day-25-skills-the-open-spec/parts/05-in-production/5.1-validating-before-you-ship.md))
checks the *shape*: is the frontmatter well-formed, does `name` obey the naming rules, does `description`
fit its length limit, does the folder match its declared name. It answers **"is this a valid skill?"**
and it is exactly the kettle's safety mark — a real check of the object in isolation.

**Audit** is a human reading in the agent's voice ([2.1](../02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md)).
It checks the *sense*: if my agent obeys these instructions, next to my data and my tools, what happens?
It answers **"should THIS agent obey it?"** — the object plus everything around it, which is the only
one of the two that is security.

The gap between them is not a weakness in the validator; it is a category difference. A validator that
tried to judge sense would be a model, and feeding it the skill is the one thing the audit forbids
([2.1](../02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md)). You have met this
exact boundary before, on Day 4: **schemas constrain shape, never sense.** The pipeline that follows
from it has four stages, in order, and skipping any one checks a different artifact than the one you
will run:

1. **validate** — cheap, automated, the safety mark ([Day 31](../04-provenance/4.1-no-row-no-run.md) wires it in);
2. **audit** — eyes, capabilities-first, a written verdict ([Section 2](../02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md));
3. **pin** — the text you audited is the text that runs ([4.2](../04-provenance/4.2-the-pin-is-the-promise.md));
4. **row, then wire** — the permission slip before the capability ([4.1](../04-provenance/4.1-no-row-no-run.md)).

## Why Sutra needs it

Because the failure this part stages is the most common one in practice: a teammate finds a popular
skill, runs the validator, sees green, and ships it.

> 🎬 **The scene.** A colleague finds a reply-formatting skill. Healthy star count, active commits, a
> clean `SKILL.md`, an MIT licence. They run `agentskills validate`, it prints `Valid skill`, and they
> vendor it and move on to the next ticket.
>
> 😬 **The naive fix.** *"It validates, and thousands of people use it. Validation plus popularity is
> the audit."*
>
> 💥 **Why it fails.** You proved it in [3.2](3.2-the-poisoned-skill-and-the-audit.md): `evil-helper`
> validates too. Valid frontmatter, tidy folder, plausible description — and three traps that are
> invisible to a validator, invisible to a star count ([1.3](../01-the-doors/1.3-freshness-is-not-trust.md)),
> and worst of all invisible in operation, because the replies still look great and the script still
> prints its cheerful line. Validation checks the *shape* of a skill; the attack lives in the *sense*.
> Popularity adds nothing: stars are farmable, and a maintainer account takeover flips a trusted repo
> hostile in one force-push, which an unpinned install inherits silently on the next fetch
> ([1.2](../01-the-doors/1.2-who-can-change-the-text.md)).
>
> 💡 **The insight.** **Validation and audit answer different questions, and only the second is
> security.** So the order is validate, audit, pin, row, wire — and skipping any stage means the stages
> after it are checking a different artifact than the one you will run.

## The mechanism

Run both checks on the poisoned fixture, one after the other, and watch them disagree. On 2026-09-04:

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate tests/fixtures/skills/evil-helper
uv run python days/day-29-sourcing-and-auditing-skills/lab/audit.py tests/fixtures/skills/evil-helper
```

**Line by line:**

- The first command is [Day 25](../../../day-25-skills-the-open-spec/parts/05-in-production/5.1-validating-before-you-ship.md)'s
  validator, run with `uv run --no-project --with` so nothing is added to `pyproject.toml`. It reads the
  frontmatter and checks the shape rules.
- The second is the five-pass audit from [3.2](3.2-the-poisoned-skill-and-the-audit.md). Same folder,
  same bytes, a completely different question. **Both are zero model calls.**

```text
Valid skill: tests/fixtures/skills/evil-helper
```

```text
...
agenda: 10 items
```

The same folder is a **valid skill** and a **ten-finding reject**, and neither tool is wrong. The
validator correctly reports that the shape is fine; the audit correctly reports that the sense is
hostile. The disagreement is the entire lesson: a green validator is a necessary gate you must not
mistake for the security review, because it was never asking the security question.

Put the two side by side as a table, because the columns are the point:

| Question | Answered by | On `evil-helper` | Is it security? |
| --- | --- | --- | --- |
| Is the frontmatter well-formed? | validator | pass | no |
| Does `name` match the folder? | validator | pass | no |
| Is `description` within limits? | validator | pass | no |
| Does the body exfiltrate data? | audit | **fail** | yes |
| Does it claim authority and hide? | audit | **fail** | yes |
| Does a script steal credentials? | audit | **fail** | yes |

Every row the validator answers is a shape question, and every one it passes. Every row that is a
security question is one the validator never asks, and every one the audit fails. That is not a bug in
`skills-ref`; it is the boundary from Day 4 drawn through a real skill.

## When it breaks

**"It validates, so it's safe."** This is the scene above, and it is the single most common way a
hostile skill gets in. The validator's `Valid skill` is a true statement about the shape and a silent
statement about the sense — and a reader who hears "valid" as "safe" has been told nothing about the
three traps, because the validator was never looking for them.

**"It's popular, so someone must have audited it."** Popularity is a freshness signal, not a trust
signal ([1.3](../01-the-doors/1.3-freshness-is-not-trust.md)). Ten thousand installs is ten thousand
people who mostly also ran the validator and shipped, and any audit that was done was of a revision that
is not the one you are about to install. Usage is not review, and old review is not review of new bytes.

**"We validate in CI, so we're covered."** Validation in CI is exactly right and exactly not enough. It
belongs in `./m check` from Day 31 as the cheap automated gate, and it catches the malformed skill in
seconds — but it will pass `evil-helper` every time, because the CI job is checking shape. The audit is
the human stage the CI job cannot replace, and a team that reports "our pipeline validates every skill"
has described half the pipeline.

## In production

**A professional runs validation as the machine gate and audit as the human gate, and never lets one
stand in for the other.** Validation is fast, deterministic and belongs in CI on every change; audit is
slow, needs judgement, and produces a written verdict a person signs ([3.2](3.2-the-poisoned-skill-and-the-audit.md)).
The two live at different points in the process — validate on every push, audit once per pinned revision
— and the provenance row records that *both* happened ([4.1](../04-provenance/4.1-no-row-no-run.md)).

**What changes at scale** is that the temptation to collapse the two grows with the backlog. At forty
skills a quarter, "it validates and it's popular" becomes the path of least resistance, and the discipline
that survives is the one wired into the tooling: the CI job validates *and* refuses to merge a skill
whose provenance row has no audit date and no pin. The human audit cannot be automated, but the
*requirement* for it can be, so that a green validator alone can never be the thing that ships a skill.

**The failure mode that only appears with real traffic** is the validated, popular, audited-last-year
skill whose new pinned revision was never re-audited. Every automated signal is green — it validates, it
has stars, there is an audit date in the ledger — and the audit date is eighteen months and forty commits
stale. The pipeline has to treat "audited" as a claim about a *revision*, not about a skill, or the green
row is a lie the tooling is telling you ([4.2](../04-provenance/4.2-the-pin-is-the-promise.md)).

**The review comment a senior engineer leaves:** *"the PR says 'passes agentskills validate'. Good — that
means it's a well-formed skill. It doesn't mean we should run it. Where's the audit verdict and the pin?
Validation is the safety mark; I'm asking whether it's safe on our wiring."*

**The interview question:** *"you can validate a skill automatically — why do you still need a human to
review it?"* The honest spoken answer: *"Because validation and audit answer different questions.
Validation checks the shape — well-formed frontmatter, legal name, description in limits — and it's the
right automated gate. Audit checks the sense: if my agent obeys this next to my data and tools, what
happens? Only the second is security, and a validator can't do it, because to judge the sense you'd have
to feed the skill to a model, which is the exact thing the audit exists to prevent. Our poisoned test
fixture validates cleanly and fails the audit on three counts — exfiltration, an authority-plus-silence
injection, and a credential-stealing script — which is the whole point: schemas constrain shape, never
sense. So the order is validate, audit, pin, record, wire, and skipping the audit means every later stage
is checking a different thing than the one that runs."*
