# 4.2 — The pin is the promise

## One-line answer

A pin is only worth something if something checks it, so the day's drift check hashes the files on disk
and compares them to the digest in the ledger row — matching means the audited text is the text that
runs, and one changed byte turns it red.

## The story

The medicine bottle has a foil seal under the cap, and the pharmacist told you to check it.

Not the cap — anyone can screw a cap back on. The foil. If the foil is intact, the contents are the
contents that were sealed at the factory, and nobody has been into the bottle since. If the foil is torn,
peeled, or missing, you do not take the medicine, however normal the cap looks and however full the
bottle seems. The seal is not there to tell you the medicine is good. It is there to tell you it is the
*same* medicine that was checked when it was good.

The clever part is that the seal makes tampering *visible*. Without it, someone could open the bottle,
change the contents, and close it, and you would have no way to know. With it, any interference leaves a
mark you can see before you swallow anything. The seal does not prevent tampering. It removes the ability
to tamper *undetectably*, which turns out to be almost as good.

## The idea in plain language

[1.2](../01-the-doors/1.2-who-can-change-the-text.md) established that a pin — a commit hash or a content
digest — records the exact revision you audited. [4.1](4.1-no-row-no-run.md) put that pin in the
provenance row. This part closes the loop: a pin in a row that nothing verifies is a foil seal nobody
looks at. The value appears only when something **compares the recorded pin to the bytes on disk** and
can go red.

That comparison is the **drift check**. Drift is the gap between what you audited and what is actually
there now, and it opens for ordinary, non-malicious reasons as much as hostile ones: someone edits a
vendored skill to fix a typo, a merge brings in a change nobody re-read, an automated bump moves a
dependency. Every one of those makes the ledger's promise false — the row vouches for bytes that are no
longer on disk — and the drift check is what converts that silent falsehood into a failing build.

The mental model is exactly the seal: the pin does not stop anyone editing a skill. It removes the
ability to edit it **undetectably**. After a pin is recorded, any change to the audited text is visible
as a digest mismatch, which is the property that lets you audit *diffs* forever after auditing the whole
thing once ([2.1](../02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md)) — the diff
is only trustworthy because the base cannot have moved without the check noticing.

## Why Sutra needs it

Because every earlier part of this day quietly assumes the pin holds, and this is the part that makes it
hold.

The audit reads specific bytes ([2.1](../02-the-five-pass-audit/2.1-read-it-like-the-thing-that-will-obey-it.md)).
The verdict names a pin ([3.2](../03-the-poisoned-skill/3.2-the-poisoned-skill-and-the-audit.md)). The
row records it ([4.1](4.1-no-row-no-run.md)). None of that is worth anything if the bytes can change
afterwards without a signal — which is precisely the account-takeover and the silent-edit failures from
[1.2](../01-the-doors/1.2-who-can-change-the-text.md), and precisely the limit the day's paper draws
around reading ([the paper](../../papers/01-reflections-on-trusting-trust.md)): a clean read is a claim
about specific bytes, void the moment the bytes move. The drift check is how Sutra keeps the claim true
between audits.

## The mechanism

The check reuses `pack_digest` from [1.2](../01-the-doors/1.2-who-can-change-the-text.md) — the hash over
every path and every byte — and compares it to the recorded pin:

```python
# lab/pinned.py
import pathlib
import sys

from pack import pack_digest


def main(root, recorded):
    """Compare the digest in the ledger row against the bytes on disk right now."""
    now = pack_digest(root)[:16]
    print(f"recorded: {recorded}")
    print(f"on disk : {now}")
    if now != recorded:
        print("DRIFT - the text you audited is not the text that will run")
        return 1
    print("match - the audited text is the text that will run")
    return 0


if __name__ == "__main__":
    sys.exit(main(pathlib.Path(sys.argv[1]), sys.argv[2]))
```

**Line by line:**

- `recorded` is the pin from the provenance row, passed in as an argument. The check does not read the
  ledger itself — it takes the recorded value and the folder and compares them, which keeps it a pure
  function of its inputs and trivial to wire into CI later.
- `pack_digest(root)[:16]` recomputes the digest of the folder as it is *right now*, truncated to the
  same sixteen characters the row records. Full and truncated digests both work; sixteen hex characters
  is short enough to paste in a table and long enough that an accidental collision is not a real concern.
- `now != recorded` is the entire test. Equal means every path and every byte is what it was at audit
  time; unequal means something changed, and the check does not care what or why — any drift is a
  re-audit.
- The two outcomes return `1` and `0`, so this is a **gate**, not a report. It belongs beside the other
  gates in `./m check` ([Day 31](../03-the-poisoned-skill/3.3-it-validated-and-was-hostile.md)) so a
  drifted skill fails the build rather than being noticed by luck.
- **Zero model calls.** Hashing bytes and comparing two strings.

Run it against the pinned fixture, first when nothing has changed. On 2026-09-04:

```bash
uv run python days/day-29-sourcing-and-auditing-skills/lab/pinned.py tests/fixtures/skills/evil-helper 493ea089684fd0c3
echo "exit: $?"
```

**Line by line:**

- Folder and recorded pin in, verdict and exit code out. **Zero generations, no key.**

```text
recorded: 493ea089684fd0c3
on disk : 493ea089684fd0c3
match - the audited text is the text that will run
```

The seal is intact. Now change one line of the skill — add a single instruction to the body, the kind of
edit an account takeover or a careless merge would make — and run the identical command:

```text
recorded: 493ea089684fd0c3
on disk : 49b49a37238a6998
DRIFT - the text you audited is not the text that will run
```

One appended line, a completely different digest, exit 1. The audit you did is now an audit of a file
that no longer exists on disk, and the check said so instead of letting the changed bytes run under the
old verdict. That is the foil seal torn, seen before anything was swallowed.

## When it breaks

**A pin recorded but never checked.** The most common failure is not a wrong pin — it is a right pin that
nothing compares against, a foil seal in a drawer. A digest in a Markdown table is a comment until a
runnable check reads it, which is why this part is code and not a paragraph, and why the check returns an
exit code.

**Re-pinning to make the check pass.** The check goes red, and the tempting fix is to update the recorded
pin to the new digest and move on. That silences the alarm by throwing away exactly the information it
was giving you: the text changed, and *nobody re-audited it*. The correct response to drift is to audit
the diff and then re-pin, in that order. Re-pinning first is disabling the seal because it beeped.

**Pinning to a branch and calling it done.** A branch name in the version column looks like a pin and is
a subscription ([1.2](../01-the-doors/1.2-who-can-change-the-text.md)). The drift check cannot even run
against `@main`, because `@main` is not a fixed set of bytes — there is nothing stable to compare to.
Resolve the branch to the commit hash it pointed at, and pin that.

## In production

**A professional puts the drift check in CI and treats a red result as a required re-audit, never as a
re-pin.** The mature shape is the lockfile pattern Sutra already uses for Python: `uv.lock` records an
exact version and content hash per dependency and the build fails when the installed bytes disagree. A
skill lockfile is the same idea — a file of recorded pins, checked on every build — and the discipline is
identical: drift is a signal to look, not a nuisance to suppress.

**What changes at scale** is that drift stops being rare. With one vendored skill you might never see a
mismatch; with forty, edits, merges and bumps make drift a weekly event, and the process has to make
re-auditing a diff cheap enough to do weekly. That is only possible because the pin guarantees a real
diff exists — audit the eleven changed lines, not the whole skill again — which is the payoff of having
pinned in the first place.

**The failure mode that only appears with real traffic** is the drift that arrives through a shared
reference outside the folder ([2.5](../02-the-five-pass-audit/2.5-the-files-it-points-at.md)). If a skill
links `../shared/header.md`, `pack_digest` over the skill folder does not cover that file, so an edit to
the shared file changes what the skill does and the drift check stays green. The pin has to cover
everything the skill actually loads, which is the concrete reason [2.5](../02-the-five-pass-audit/2.5-the-files-it-points-at.md)
treats an escaping reference as a finding: it is a hole in the seal.

**The review comment a senior engineer leaves:** *"the drift check went red and you updated the pin in
the same commit. That's not a fix, that's muting the alarm — the whole point is that the audited text
changed and nobody looked. Revert the pin, audit the diff, then re-pin with the audit date bumped. And
make sure the digest covers the reference this skill links outside its folder, or the seal has a hole in
it."*

**The interview question:** *"you've pinned and recorded a skill. What keeps the pin honest?"* The honest
spoken answer: *"A check that compares the recorded pin to the bytes on disk and fails the build on any
difference — a drift check. The pin doesn't stop anyone editing the skill; it makes editing it
*detectable*, like a foil seal. One changed byte, a different digest, red build. The trap is re-pinning
to make it green, which throws away the one thing it's telling you: the text changed and nobody
re-audited it. So red means audit the diff, then re-pin — and the pin has to cover everything the skill
loads, including references outside its folder, or you've sealed the bottle and left the base open. It's
the same discipline as a lockfile: an exact hash per dependency, checked every build."*

## Check yourself

```bash
uv run python days/day-29-sourcing-and-auditing-skills/lab/pinned.py skills/ticket-triage $(uv run python -c "
import hashlib, pathlib
h = hashlib.sha256()
for p in sorted(x for x in pathlib.Path('skills/ticket-triage').rglob('*') if x.is_file()):
    h.update(p.relative_to('skills/ticket-triage').as_posix().encode()); h.update(p.read_bytes())
print(h.hexdigest()[:16])
")
```

That pins your own skill to its current digest and immediately checks it — a match. Now edit the skill
and run the same line: watch it go red, and say what the *correct* next step is and what the tempting
wrong one is.
