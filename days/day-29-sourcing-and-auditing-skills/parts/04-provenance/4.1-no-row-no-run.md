# 4.1 — No row, no run

## One-line answer

A third-party skill runs only after its row exists in the provenance ledger — source, version, licence,
who audited it and when, and what it is permitted to touch — because the row *is* the permission, and a
rejected audit gets a row too, since a rejected audit is provenance as much as an accepted one.

## The story

The office has a visitors' book at the front desk, and the rule about it is absolute.

Nobody gets past the desk without a line in the book: name, who they are here to see, the time in. It is
thirty seconds of writing and it feels like a formality right up to the afternoon a contractor is found
on the third floor and nobody can say who let them in or what they were there to do. Then the book is
the only thing that answers the question, and on that day the thirty seconds were the cheapest insurance
the building ever bought.

The book is not a character judgement. Honest visitors sign it and so would a dishonest one — that is
not its job. Its job is that months later, when something is wrong, there is one place that says who was
here, when, and vouched for by whom. A building that lets people in on trust has no such place, and
discovers it needs one at the worst possible moment.

## The idea in plain language

Sutra keeps a **provenance ledger** at `docs/SKILL_PROVENANCE.md`. Provenance means the recorded origin
and history of a thing — where it came from and what has happened to it since. The ledger is the
visitors' book for skills, and it carries one rule, stated in the file's own header: **every
third-party skill gets a row before it is ever run.** No row, no run.

The row is small on purpose — small enough that there is no excuse to skip it, complete enough to answer
the questions that matter later. Its columns:

| Column | What it records | Answered by |
| --- | --- | --- |
| Skill | the name | the folder |
| Source | which door it came through | [1.1](../01-the-doors/1.1-the-four-doors.md) |
| Version | the pin — a commit hash or content digest | [1.2](../01-the-doors/1.2-who-can-change-the-text.md) |
| Licence | the terms you may use it under | pass 1 ([2.2](../02-the-five-pass-audit/2.2-pass-one-will-it-load.md)) |
| Audited on | the date the read happened | the audit |
| Audited by | who read it | the audit |
| Permitted scope | what it is allowed to touch | passes 2 and 5 ([2.3](../02-the-five-pass-audit/2.3-the-capability-inventory.md), [2.6](../02-the-five-pass-audit/2.6-the-scripts-read-never-run.md)) |

Two rules about the row make it a permission rather than a note. First, **the row exists before the
skill is wired into anything** — you draft it the moment the audit is done, not when you get around to
it, because a capability that arrives before its permission slip is exactly the contractor on the third
floor. Second, **a rejected skill gets a row too.** A REJECT verdict is provenance: it records that you
looked at this thing, on this date, and decided against it, so the next person who finds the same
tempting repository does not repeat your afternoon. The row for a rejected skill says REJECTED in the
scope column and why.

There is a matching rule for the licence, and it is the same shape as the row rule: **no licence, no
run** ([2.2](../02-the-five-pass-audit/2.2-pass-one-will-it-load.md)). A skill you have no recorded
right to use is unwired for the same reason a skill with no row is: the permission is missing.

## Why Sutra needs it

Because the ledger has carried this discipline since before Sutra had a single runtime skill, and
Day 29 is the day it earns its first real entries.

Open `docs/SKILL_PROVENANCE.md`. The rows already there are the **driver skills** — the tooling Claude
Code itself uses, each pinned to a commit, licence recorded, read in full before use. Those were never
runtime skills for the agent; they are the house living its own rule. Day 27 added the first two
first-party runtime rows, for `ticket-triage` and `kb-answer-style`
([27.6.2](../../../day-27-authoring-first-skills/parts/06-in-production/6.2-versioning-a-procedure.md)).
Day 29 is the first day a *third-party* skill is audited, and so the first day the ledger records a
sourced skill — accepted or, as it turns out for both of today's, rejected.

The payoff is the one the visitors' book gives. When a headline says a popular skill repository was
compromised at some commit, the ledger is the difference between a five-minute `grep` — *do we run
anything from that repository, pinned to what?* — and a repository-wide archaeology dig through every
agent's configuration. The row is cheap now and decisive later, which is the whole economics of
provenance.

## The mechanism

There is no new code here — the ledger is a Markdown table you append to, and the day's tooling already
produced everything a row needs: the audit's findings ([3.2](../03-the-poisoned-skill/3.2-the-poisoned-skill-and-the-audit.md))
and the pin ([1.2](../01-the-doors/1.2-who-can-change-the-text.md)). The mechanism is the discipline of
writing the row from those outputs. Here is the row for the sourced pack you audit in
[6.1](../06-in-production/6.1-run-the-pack-against-the-routing-gate.md), which is clean on security and
fails the routing gate:

```markdown
| support-pack | (fixture) tests/fixtures/skills/sourced-pack | pin 16f367812482f4c6 | MIT | 2026-09-04 | you | REJECTED - audit clean (0 findings) but the routing gate fails: adding it drops the worst margin from 1 to 0. Not wired. See days/day-28-.../2.4. |
```

**Line by line:**

- **Skill** is `support-pack` — the pack audited as one unit, because a sourced pack is rarely one skill
  and the decision to install is made about the pack ([6.1](../06-in-production/6.1-run-the-pack-against-the-routing-gate.md)).
- **Source** names the door. Here it is a fixture you built to stand in for a sourced pack; a real one
  would be its `github.com/...` URL, which is what a future `grep` searches
  ([1.1](../01-the-doors/1.1-the-four-doors.md)).
- **Version** is the pin — the pack digest `pack_digest` computes ([1.2](../01-the-doors/1.2-who-can-change-the-text.md)),
  so the row refers to exact bytes. A row without a pin records that you audited *a* version and cannot
  say which.
- **Licence** is `MIT`, read off the frontmatter in pass 1. Present, so this gate is passed; absent
  would have been *no licence, no run* on its own.
- **Audited on** and **Audited by** are the date and the person. Months later these answer *"is this
  audit stale, and who do I ask about it?"* — which is why the audit date is a claim about a revision,
  not about the skill ([4.2](4.2-the-pin-is-the-promise.md)).
- **Permitted scope** carries the verdict and the reason. REJECTED, with the specific finding — the
  routing regression, not a security one — so the next reader knows *why* and does not re-run the same
  analysis. `Not wired` states the disposition explicitly.

And the rule that `evil-helper` gets **no** row, which is worth stating because it looks like an
exception and is not:

```text
evil-helper: first-party test data, not an installed skill. No provenance row.
```

**Line by line:**

- The poisoned fixture is something *you* built as a test ([3.2](../03-the-poisoned-skill/3.2-the-poisoned-skill-and-the-audit.md)),
  not a third-party skill you sourced. The ledger records third-party origins; a fixture has none. It
  lives under `tests/fixtures/`, it is never wired, and it is not provenance because there is no external
  provenance to record.

## When it breaks

**Wiring first, row later.** The row is drafted after the audit and before the wiring, and reversing
that order is the whole failure the rule prevents. A skill running without a row is a capability with no
permission slip — and the day you need the ledger is a day nobody has time to reconstruct it from memory.
Draft the row when the verdict is written, in the same sitting.

**Rejecting a skill and recording nothing.** It feels natural: you looked, you said no, you moved on. But
the next person finds the same repository, is tempted the same way, and repeats your whole audit — or
worse, reaches a different verdict and installs it. A REJECTED row is a signpost that saves the next
audit, and it is why rejected audits go in the ledger too.

**A licence of `TODO` treated as done.** If pass 1 could not confirm the licence, the row carries a
`TODO` naming the exact command to resolve it, and the skill **stays unwired** until it is resolved — no
licence, no run, exactly as no row, no run. A `TODO` in the licence column is not a formality to clear
later; it is an open gate.

## In production

**A professional makes the ledger a merge gate, not a habit.** The mature version of "no row, no run" is
CI that refuses to merge a change adding a skill to `skills/` unless a provenance row for it exists with
a non-empty pin, licence, audit date and scope. The discipline that survives turnover and deadline
pressure is the one a machine enforces; a rule that lives only in people's heads is a rule that lapses
the first busy week ([Day 31](../03-the-poisoned-skill/3.3-it-validated-and-was-hostile.md) is where the
gate lands).

**What changes at scale** is that the ledger becomes the thing you query in an incident, not the thing
you write in a review. At forty sourced skills, "which of ours come from the repository in this CVE, and
pinned to which revision" has to be one `grep`, which means the source URL and the pin have to be in a
consistent, machine-readable shape in every row. The ledger stops being documentation and becomes an
inventory — the software bill of materials the day's paper's descendants made standard practice
([the paper](../../papers/01-reflections-on-trusting-trust.md)).

**The failure mode that only appears with real traffic** is the row that drifts from the skill. Someone
bumps a vendored skill to a new revision and forgets to update the pin, so the ledger vouches for bytes
that are no longer on disk. The row now lies, and it lies in the reassuring direction — everything looks
recorded. The drift check ([4.2](4.2-the-pin-is-the-promise.md)) exists precisely to turn that silent
lie into a red build.

**The review comment a senior engineer leaves:** *"this PR wires the skill but there's no provenance row.
No row, no run — draft it before this merges, with the pin you audited at, the licence, and the permitted
scope. And if you rejected the other two you looked at, they get rows too; a rejection nobody recorded is
an audit the next person has to redo."*

**The interview question:** *"walk me through what you record before running a community skill."* The
honest spoken answer: *"A provenance row, before it runs — that's the rule, no row no run. It's small on
purpose: the skill name, the source URL so I can grep it in an incident, the pin I audited at, the
licence, who audited it and when, and the permitted scope from the capability and script passes. The row
is the permission, not a note about it, so it exists before the skill is wired into anything. Rejected
skills get a row too, because a rejection nobody recorded is an audit the next person repeats — the row
says REJECTED and why. Same shape for the licence: no licence, no run. At scale the ledger stops being
documentation and becomes the bill of materials you grep when a repository you depend on gets
compromised."*
