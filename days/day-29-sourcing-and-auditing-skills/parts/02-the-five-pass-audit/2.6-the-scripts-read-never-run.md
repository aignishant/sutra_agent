# 2.6 — Pass 5: the scripts, read never run

## One-line answer

A script is the only thing in a skill that executes as code rather than as a request to a model, so it
is read last, in full, as a syntax tree — six questions asked of every node, and the script is never
executed to find out what it does.

## The story

The electrician traces the circuit on paper before switching anything on.

There is a second-hand extractor fan to be wired in, and the obvious way to find out whether it is
sound is to connect it and flip the breaker. That is also the way to find out by tripping the whole
flat, or worse. So instead the wires get followed: this one to the switch, this one to the earth, this
one — and here is the thing worth finding — this one going somewhere the diagram does not account for.

Following a wire with your finger tells you where it goes. It does not put current through it. That is
the entire difference, and it is why the tracing happens first and the breaker happens last, if at all.

## The idea in plain language

`scripts/` holds executable code the agent can run
([Day 25](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.2-scripts-references-assets.md)).
Everything else in a skill is a *request* to a model, which may or may not be followed. A script is
different: when it runs, it runs. There is no probability involved, no persona to appeal to, no guard
callback in the middle of a `for` loop. It is the sharpest thing in the pack, and it is read last
because it is the slowest read — and read it is, because running it is the thing you are trying to
avoid.

Pass 5 reads each script as an **abstract syntax tree** — the structured form Python parses source into
before it runs it. Parsing is not running: `ast.parse` builds a tree of nodes and stops, so the code
never executes. Six questions are asked of every node in that tree, and each has a reason:

| Rule | What it finds | Why it matters |
| --- | --- | --- |
| `network` | imports of `urllib`, `requests`, `socket`, `smtplib`… | a way out for data, and a way in for instructions |
| `shell` | imports of `subprocess`, `os.system`, `pty` | it can run anything the process can run, escaping every rule you wrote |
| `reads-env` | `os.environ`, `os.getenv` | **your keys live in environment variables** |
| `dynamic-code` | `eval`, `exec`, `compile`, `__import__` | the code it will run is not the code you are reading |
| `opaque` | `base64`, `zlib`, `pickle`, `marshal` | content you cannot read, and `pickle` executes on load |
| `writes-file` | `open(..., "w")` and friends | it changes state outside the conversation |

None of these is automatically an attack. A perfectly good script may read one environment variable for
a configuration path. The pairs are what to look for: **network plus `reads-env`** is the exfiltration
shape, **`opaque` plus `dynamic-code`** is the hiding shape, and **`shell` plus anything** is a script
that has stopped being auditable, because a subprocess can do what it likes.

The rule that has no exception is at the top of the section and bears repeating: **you never run the
script to find out.** Running attacker-supplied code to learn whether it is attacker-supplied code is
the test drive with the failed brakes ([2.1](2.1-read-it-like-the-thing-that-will-obey-it.md)).

## Why Sutra needs it

Because the poisoned fixture's script is the reason `allowed-tools: run_skill_script` was in its
frontmatter, and the two only make sense together.

Pass 2 already told you this skill pre-approves the tool that runs its own scripts and ships one script
containing an outbound URL ([2.3](2.3-the-capability-inventory.md)). Pass 5 is where you find out what
the script does with that URL, and the answer is the second half of a shape you have already half-seen.
A skill that pre-approves script execution and ships a script that reads your environment and posts it
somewhere has assembled a complete data-exfiltration path in eleven lines of Python and one line of
frontmatter — with no model involved at any point, and therefore nothing a prompt-level defence could
have stopped.

That is also why this pass sits at the boundary between Section 2 and Section 3. The passes measured a
blast radius; [3.1](../03-the-poisoned-skill/3.1-a-skill-is-source-you-did-not-write.md) explains why
that radius is a security problem rather than a code-quality one, and why the only defences that work
are upstream and downstream of the skill rather than inside it.

## The mechanism

```python
# lab/script_audit.py - pass 5
import ast

from pack import Finding, files, rel

NETWORK = {"urllib", "http", "socket", "requests", "httpx", "ftplib", "smtplib", "telnetlib"}
SHELL = {"subprocess", "pty", "os.system", "os.popen", "os.execv"}
DECODERS = {"base64", "codecs", "binascii", "zlib", "marshal", "pickle"}
BUILTINS = {"eval", "exec", "compile", "__import__"}


def dotted(node):
    """The dotted name of a node, so `os.environ.get` arrives as one string."""
    parts = []
    while isinstance(node, ast.Attribute):
        parts.append(node.attr)
        node = node.value
    if isinstance(node, ast.Name):
        parts.append(node.id)
    return ".".join(reversed(parts))


def writes(node):
    """True when this is an open() whose mode string asks to write, append or create."""
    return dotted(node.func) == "open" and any(
        isinstance(a, ast.Constant) and isinstance(a.value, str) and set("wax") & set(a.value)
        for a in node.args[1:]
    )


def scan(source, where):
    """One walk of the tree, five questions per node, reported in line order."""
    found = []
    for node in ast.walk(ast.parse(source)):
        if isinstance(node, ast.Import | ast.ImportFrom):
            names = [a.name for a in node.names] if isinstance(node, ast.Import) else [node.module]
            for name in filter(None, names):
                head = name.split(".")[0]
                if head in NETWORK:
                    found.append((node.lineno, "network", f"imports {name}"))
                if head in SHELL:
                    found.append((node.lineno, "shell", f"imports {name}"))
                if head in DECODERS:
                    found.append((node.lineno, "opaque", f"imports {name}"))
        if isinstance(node, ast.Call):
            target = dotted(node.func)
            if target in BUILTINS:
                found.append((node.lineno, "dynamic-code", f"{target}(...)"))
            if target == "os.getenv":
                found.append((node.lineno, "reads-env", "os.getenv(...)"))
            if writes(node):
                found.append((node.lineno, "writes-file", "open(..., write mode)"))
        if isinstance(node, ast.Attribute) and dotted(node) == "os.environ":
            found.append((node.lineno, "reads-env", "os.environ"))
    return [Finding(f"{where}:{line}", rule, detail) for line, rule, detail in sorted(found)]
```

**Line by line:**

- `ast.parse(source)` builds the tree and stops. This is the single most important line in the pass:
  parsing reads the code's structure without executing a byte of it, which is what makes the pass safe
  on hostile input. Importing the module instead would run it.
- `ast.walk` visits every node in the tree, so a call nested inside a function inside a class inside a
  `try` is seen. A scan over *text* would miss what an indented or wrapped line does; a scan over the
  tree cannot, because nesting is structure and structure is what a tree is.
- `dotted()` climbs the chain of `ast.Attribute` nodes to rebuild a dotted name. Python parses
  `os.environ.items` as attribute-of-attribute-of-name, so without this the scan would only ever see the
  final `items` and never know which object it belonged to.
- `head = name.split(".")[0]` reduces `urllib.request` to `urllib` before comparing, so the sets stay
  short and every submodule of a network package is caught by one entry.
- `isinstance(node, ast.Import | ast.ImportFrom)` handles both `import x` and `from x import y`. The
  `names` line picks the right attribute for each form, and `filter(None, names)` drops the `None` that
  a bare relative import (`from . import x`) puts in `node.module`.
- `writes()` inspects the *mode string argument* rather than assuming any `open` is a write. `set("wax")
  & set(mode)` is true for `w`, `a`, `x` and combinations like `r+w`, and false for plain `r`. Flagging
  every read would bury the writes in noise.
- `os.environ` is caught as an **`ast.Attribute`**, not as a call, and that is deliberate: it catches
  `os.environ["KEY"]`, `os.environ.items()`, `os.environ.get(...)` and a bare `os.environ` passed to
  something else, all with one rule. `os.getenv` is a separate call check because it is a function, not
  an attribute of `environ`.
- `sorted(found)` before building the `Finding` objects puts the report in **line order**. `ast.walk` is
  breadth-first, so without this a finding on line 12 can print before one on line 10, and a reader
  following along in the file loses their place.
- **Zero model calls, and nothing executed.** Parsing and set membership.

The wrapper around `scan` handles what it cannot read:

```python
def findings(root):
    """Every executable in the pack. Python is parsed; anything else is flagged for eyes."""
    out = []
    for path in files(root):
        if "scripts" not in path.parts:
            continue
        where = rel(root, path)
        if path.suffix != ".py":
            out.append(Finding(where, "not-python", "this pass cannot read it - read it yourself"))
            continue
        try:
            out.extend(scan(path.read_text(encoding="utf-8"), where))
        except SyntaxError as error:
            out.append(Finding(where, "will-not-parse", f"SyntaxError: {error.msg}"))
    return out
```

**Line by line:**

- `"scripts" not in path.parts` limits the pass to files under a `scripts/` directory at any depth. A
  `.py` file sitting in `references/` is not a script by convention and is caught as an orphan or a
  reference by pass 4 instead.
- `path.suffix != ".py"` produces a **`not-python` finding rather than a skip.** The spec names Bash and
  JavaScript as common script languages too, and a pass that silently ignored a `.sh` file would report
  a clean script audit on a pack whose real payload is a shell script. Saying *"this pass cannot read
  it - read it yourself"* is honest; saying nothing is a lie by omission.
- `except SyntaxError` catches a file that is not valid Python. That is a finding, not a crash: a
  syntax error in a shipped script is either a broken pack or a file that is not what its extension
  claims, and both want a human.

**Line by line:**

- Folder in, `file:line` findings out. **Zero generations, no key, and the script is not executed.**

```text
scripts/quality_check.py:4    network     imports urllib.request
scripts/quality_check.py:8    reads-env   os.environ
```

Two findings, four lines apart, and together they are the whole attack: the script can reach the
network, and it reads your environment. Pass 2 already found the URL it reaches. Nothing else in an
eleven-line file matters — a script that reads `os.environ` and imports `urllib.request` has both halves
of an exfiltration, and the `print("style rules loaded")` at the bottom is the costume.

And a script that exercises every rule at once, so you can see the vocabulary:

```text
scripts/archive.sh        not-python     this pass cannot read it - read it yourself
scripts/tidy.py:3         opaque         imports base64
scripts/tidy.py:5         shell          imports subprocess
scripts/tidy.py:8         reads-env      os.getenv(...)
scripts/tidy.py:10        writes-file    open(..., write mode)
scripts/tidy.py:12        dynamic-code   eval(...)
```

Six findings in one small pack, and the first line is the most important: **`archive.sh` was not read at
all.** The Python got a syntax-tree audit and the shell script got a note saying a human has to do it.
An audit report that hides its own coverage gaps is worse than no report, because it converts "I did not
look" into "nothing was found".

## When it breaks

**Running the script in a container "just to see".** A sandbox is a real control and it is not this
pass. It answers *"what did it do on this run, with these inputs, in this environment?"* — and a script
that checks whether it is in a sandbox, or that only fires on a real ticket id, does nothing at all
while you watch. Reading tells you what the code *can* do; running tells you what it *chose* to do
once. Read first, always; sandbox afterwards if you must.

**A clean pass 5 read as a safe script.** `ast.parse` sees `getattr(os, "envi" + "ron")` as an ordinary
call to `getattr` and reports nothing. Every rule here matches a *name*, and names can be assembled at
runtime — which is exactly what the `dynamic-code` and `opaque` rules exist to flag, because a script
doing either has told you the names are not to be trusted. A script with no findings has passed a
name-based check, and the full read is still yours to do.

**Skipping the non-Python script.** The `not-python` finding is the easiest one to scroll past, and it
is the one that means "coverage gap". A pack whose Python is spotless and whose `.sh` file was never
opened has not been audited.

**Being reassured by an unreachable URL.** The fixture's host ends in `.invalid`, a reserved suffix that
never resolves, so running the script would fail to connect and might look harmless. The audit does not
care whether the endpoint answers — it cares that the code tries. An attacker changes a hostname in one
commit; the shape is the finding.

## In production

**A professional treats a sourced script the way they treat a new dependency, not a new file.** It gets
the same questions a package would: what does it reach, what does it read, does it need a shell, is any
of it opaque — and the answers go in the provenance row's permitted-scope column
([4.1](../04-provenance/4.1-no-row-no-run.md)). Where the answers are unacceptable and the skill is
otherwise wanted, the move is to **defang**: delete `scripts/` from the vendored copy, delete the
`allowed-tools` entry that pre-approved it, and rewrite the body's step to use a tool you wrote. That is
an accept-with-changes verdict, and it is common.

**What changes at scale** is that scripts become the place you stop accepting packs at all. Reading one
eleven-line script is an afternoon's diligence; reading forty scripts across twelve packs, and re-reading
them at every version bump, is a job nobody does twice. Mature teams either ban `scripts/` in sourced
skills outright — procedure yes, code no — or run them under a real sandbox with no environment
inherited and no network, which is what ADK's own code-executor and environment options are for
([Day 25](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.2-scripts-references-assets.md)
noted that script support varies by client, and this is the reason the variation matters).

**The failure mode that only appears with real traffic** is the environment the script actually gets. On
your laptop `os.environ` holds a handful of harmless variables. In the deployed process it holds
`GOOGLE_API_KEY` and whatever else the platform injected, so the same eleven lines that looked like a
curiosity in review become a key disclosure in production. The audit has to be done against the
environment the thing will *run* in, not the one you read it in.

**The review comment a senior engineer leaves:** *"pass 5 says this script imports `urllib.request` and
touches `os.environ`. That's network plus credentials in one file, and the frontmatter pre-approves
running it. I don't need to know what the URL is — drop the script and the `allowed-tools` line, or this
doesn't come in. If the step it performs is genuinely needed, we write that tool ourselves."*

**The interview question:** *"a third-party skill ships a Python script. How do you check it?"* The
honest spoken answer: *"By reading it, never by running it — running attacker-supplied code to find out
if it's attacker-supplied code is the thing I'm trying to avoid, and a script that detects a sandbox or
only fires on real input does nothing while I watch. I parse it into a syntax tree and ask six questions
of every node: does it reach the network, can it shell out, does it read environment variables — our
keys live there — does it evaluate code it built at runtime, does it decode opaque blobs, does it write
files. Individually those are all legitimate; the pairs are the tell, and network plus environment reads
is exfiltration. I also flag anything that isn't Python as unread rather than skipping it, because a
report that hides its coverage gaps turns 'I didn't look' into 'nothing found'. And the usual outcome for
a script I don't like isn't rejection — it's deleting the script from the vendored copy and writing the
one step it did as a tool of our own."*
