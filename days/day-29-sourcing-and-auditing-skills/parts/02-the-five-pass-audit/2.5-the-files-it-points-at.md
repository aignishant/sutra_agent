# 2.5 — Pass 4: the files it points at

## One-line answer

A clean body can point at a file that is not clean, so pass 4 follows every link out of `SKILL.md` and
asks four questions — does the target exist, does it stay inside the skill folder, is it more than one
level down, and is there any file the body never points at — because a reference is text that arrives
*after* the body has already been trusted.

## The story

The recipe says *"make the sauce as on page 40"*, and page 40 is where the trouble is.

Sometimes page 40 has been torn out, and you are standing over a pan realising the recipe you are
halfway through does not actually contain a sauce. Sometimes page 40 says *"as in the green book"*, and
you do not own the green book, and now the recipe depends on something that was never in your kitchen.
Sometimes page 40 says *"see page 88"*, and page 88 says *"see page 112"*, and by then you have lost the
thread of what you were cooking.

And sometimes the opposite happens: you find a loose sheet tucked in the back of the book, clearly
printed by the same publisher, that nothing in the book refers to. It may be an errata slip. It may be
someone else's shopping list. Either way, it is in the book and nothing accounts for it, and that is its
own kind of odd.

The recipe on the front page can be perfect in every one of those cases. The problem is never on the
page you are reading.

## The idea in plain language

[Day 25](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.2-scripts-references-assets.md)
established the three conventional subdirectories and, more importantly, how each is consumed:
`references/` is **read** on demand, `assets/` is **used**, `scripts/` is **run**. Pass 4 is about the
first two — the files the body points at that are loaded *later*, only if the agent follows the link.

That "later" is the whole reason this pass exists. The body is loaded whole the moment the skill is
activated ([25.3.1](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.1-the-body-is-loaded-whole.md)),
so pass 3 reads exactly what the agent reads. A reference file is different: it enters the model's
context at a *different moment*, on a fetch the agent chooses to make, after the body has already been
accepted as sanctioned procedure. A hostile sentence in `references/style.md` arrives with the same
authority as the body and was never in the text you spent your careful read on.

Four questions, and each maps to one of the recipe's failures:

- **Does the target exist?** A **dead link** is the torn-out page. Usually sloppiness, occasionally a
  file the publisher forgot to ship, and always a step the agent cannot complete.
- **Does it stay inside the folder?** A link like `../shared/header.md` **escapes the folder** — the
  green book. The skill now depends on something outside the boundary you audited and pinned, which
  means your pin covers less than you thought.
- **Is it more than one level down?** The spec is explicit: *"keep file references one level deep from
  `SKILL.md`. Avoid deeply nested reference chains."* A **deep chain** is page 88 pointing at page 112:
  each hop is a decision the agent may not make, and each hop is a file a reviewer may not read.
- **Is any shipped file never pointed at?** An **orphan** is the loose sheet. A file in the pack that no
  link reaches is a file that nothing in your read accounts for — and a file you did not read because
  you were following links.

## Why Sutra needs it

Because Sutra's own shelf already runs on a reference and the day's poisoned fixture already ships one.

`ticket-triage` keeps its severity rubric in `references/severity-rubric.md` for a reason argued in
detail on Day 28: something needed sometimes and likely to grow belongs behind a link
([28.1.3](../../../day-28-progressive-disclosure-design/parts/01-the-price-list/1.3-weight-flows-down.md)).
That is good design, and it means Sutra has normalised the pattern of *"the body says go and read that
file"*. A sourced skill using the same pattern looks completely ordinary — which is exactly why the
files behind the links have to be audited as part of the skill, not as attachments to it.

The poisoned fixture's `references/style.md` is deliberately innocent, and that is a teaching choice:
pass 4 comes back **empty** on it. Its links resolve, stay inside the folder, are one level deep, and
nothing is orphaned. A pack can be tidy in every structural way and hostile in its sense, and finding
that out here rather than at the end of the audit keeps the two judgements separate.

## The mechanism

```python
# lab/links.py - pass 4
import re

from pack import Finding, files, rel, skill_dirs

LINK = re.compile(r"\[[^\]]*\]\(([^)]+)\)|`(references/[^`]+|assets/[^`]+|scripts/[^`]+)`")


def targets(body):
    """Every path the body points at, whether written as a Markdown link or in backticks."""
    return [inline or fenced for inline, fenced in LINK.findall(body)]


def findings(root):
    """Three questions per link, and one about the files nothing links to."""
    out = []
    for folder in skill_dirs(root):
        path = folder / "SKILL.md"
        where = rel(root, path)
        linked = set()
        for target in targets(path.read_text(encoding="utf-8")):
            if target.startswith(("http://", "https://", "mailto:", "#")):
                continue
            resolved = (folder / target).resolve()
            if not resolved.is_relative_to(folder.resolve()):
                out.append(Finding(where, "escapes-folder", target))
                continue
            if not resolved.exists():
                out.append(Finding(where, "dead-link", target))
                continue
            if target.count("/") > 1:
                out.append(Finding(where, "deep-chain", f"{target} is more than one level down"))
            linked.add(resolved)
        for other in files(folder):
            if other.name == "SKILL.md" or other.resolve() in linked:
                continue
            out.append(Finding(rel(root, other), "never-linked", "shipped but nothing opens it"))
    return out
```

**Line by line:**

- `LINK` has two alternatives because skills write paths two ways. The first, `\[[^\]]*\]\(([^)]+)\)`,
  is a Markdown link `[text](target)`. The second matches a backticked path that begins with one of the
  three conventional directories, which is how a body names a script it wants run
  ([Day 25](../../../day-25-skills-the-open-spec/parts/03-the-body-and-the-folders/3.2-scripts-references-assets.md)).
  Missing the backtick form would leave every `scripts/…` mention unchecked.
- `targets()` collapses the regex's two capture groups with `inline or fenced` — exactly one of them is
  non-empty per match, so this yields a flat list of paths regardless of which form was used.
- The `startswith` guard skips `http://`, `mailto:` and in-page anchors. Outbound URLs are already
  pass 2's business ([2.3](2.3-the-capability-inventory.md)); pass 4 is about files, and reporting a URL
  twice under two names would make the combined report harder to read, not easier.
- `resolved.is_relative_to(folder.resolve())` is the containment check, and the order matters: it runs
  **before** the existence check. A path escaping the folder is a boundary finding whether or not the
  target happens to exist, and calling it a dead link when it points at a real file outside the pack
  would describe the wrong problem.
- `.resolve()` on both sides is what makes the check real. Without it, `../shared/header.md` is just a
  string that starts with two dots, and `references/../../shared/header.md` slips through. Resolving
  turns both into absolute paths so the comparison is about where the file actually is.
- `target.count("/") > 1` implements the spec's one-level rule: `references/format.md` has one slash and
  is fine, `references/deep/tone.md` has two and is a chain.
- The final loop inverts the question. `linked` accumulated every file the body reached; every other
  file in the folder — except `SKILL.md` itself — is an orphan. Checking in both directions is the same
  discipline Day 27's preflight used, where one renamed file produced both a dead link and an orphan
  ([27.4.3](../../../day-27-authoring-first-skills/parts/04-the-authoring-loop/4.3-sharpening-without-a-model.md)).
- **Zero model calls.** Path arithmetic and `exists()`. Nothing is opened for content and nothing is
  run.

## When it breaks

**An orphan waved through as "probably an asset".** A file nothing links to is a file that will never be
loaded — so a reviewer reasons it is harmless and skips it. Two problems. It is dead weight in a pack you
are about to vendor, and more importantly it is the one file your link-following read never reached, so
"nothing loads it" is a claim you are making about a file you did not open. Open it or delete it.

**A dead link treated as a security finding.** `references/severity.md` missing is almost always a rename
nobody propagated. The consequence is a step the agent cannot complete, and what the model does then is
[Day 27](../../../day-27-authoring-first-skills/parts/05-failure-lab/5.1-the-drill-at-a-locked-gate.md)'s
locked gate: refuse, improvise, or substitute, and you do not choose which. That is a quality problem
with a real behavioural cost, not an attack.

**Following the escaping link and auditing that file too.** It is the instinctive fix and it is the wrong
one, because it silently redefines what you audited. Your provenance row names a folder and a pin
([4.1](../04-provenance/4.1-no-row-no-run.md)); a dependency outside that folder is not covered by
either. Either the shared file comes inside the skill and the pin covers it, or the skill does not come
in.

## In production

**A professional resolves references at build time, not at run time.** The mature version of this pass
is a vendoring step: copy the pack in, rewrite or inline any escaping reference, fail the build on a dead
link, and delete orphans — so that the folder in `skills/` is self-contained and its digest means
something ([4.2](../04-provenance/4.2-the-pin-is-the-promise.md)). A skill that cannot be made
self-contained is a skill that cannot be pinned, and that is a merge blocker rather than a note.

**What changes at scale** is that shared references become the norm and the boundary erodes. A pack of
twelve skills with one `shared/` directory is a sensible thing for a publisher to build and a hostile
thing for a consumer to audit, because a single edit to one shared file changes twelve skills at once.
The pin has to cover the whole pack rather than each skill, which changes what the provenance row names:
the unit of audit becomes the pack, not the skill.

**The failure mode that only appears with real traffic** is the reference that is fetched rarely. A file
loaded on one triage in twenty is a file a reviewer never sees in testing and a file that survives in a
pack long after the body stopped needing it. The audit is the only time anyone reads it, because the
runtime almost never does — and *almost never* is not never.

**The review comment a senior engineer leaves:** *"step 4 links `../shared/header.md`. That's outside the
folder we're pinning, so our digest doesn't cover it and vendoring this skill will break the step. Either
inline it or bring the whole pack in as one pinned unit — I'm not approving a skill whose behaviour lives
partly outside the thing we audited."*

**The interview question:** *"a skill's SKILL.md is clean. Are you done reading?"* The honest spoken
answer: *"No, because the body is only what loads at activation. Anything behind a link loads later, on a
fetch the agent chooses, and it arrives with the same authority as the body — so a clean body and a
hostile reference is a real shape. I follow every link and ask four things: does it exist, does it stay
inside the folder, is it more than one level deep, and is there any shipped file nothing links to. The
one people miss is the reference that escapes the folder: it usually resolves fine on the publisher's
machine and it means the thing I pinned isn't the whole thing that runs. And I check orphans in the other
direction, because a file no link reaches is exactly the file my link-following read never opened."*
