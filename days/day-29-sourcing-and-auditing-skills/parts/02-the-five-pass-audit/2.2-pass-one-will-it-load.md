# 2.2 — Pass 1: will it load, and may you keep it

## One-line answer

The first pass is the cheapest and most decisive: does the folder load as a valid skill, is its name
the one the folder claims, and does it carry a licence — and if the answer to any of these is no, the
audit stops here, because a publisher who cannot manage the frontmatter has not earned a deeper read.

## The story

The courier hands you a box and a screen to sign, and before you sign you check three things at the
door.

Is the name on the label yours? If it says someone else's flat, it is not your parcel and you do not
sign for it. Is the box actually sealed, or has it been opened and taped shut again? A reopened box is a
different conversation from a sealed one. And is there any paperwork at all — a delivery note, a return
address — or is it a plain box with nothing to say where it came from?

None of this involves opening the box. It is thirty seconds at the threshold, and it decides whether the
box comes inside at all. You would feel foolish carrying a stranger's parcel up three flights, unpacking
it, and only then reading the label. The cheap checks come first because they are the ones that can send
the whole thing back before you have invested anything.

## The idea in plain language

Pass 1 asks the questions that need no interpretation and can end the audit outright. There are three,
and they map onto the three checks at the door:

- **Does it load?** ADK's loader, `load_skill_from_dir` from [Day 26](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.1-load-skill-from-dir.md),
  parses the frontmatter and enforces the format's rules. If it raises, the skill is malformed and there
  is nothing to audit yet.
- **Is it what it claims?** The `name` in the frontmatter must equal the folder name — the spec requires
  it and the loader enforces it. A mismatch is the label naming the wrong flat.
- **May you keep it?** A skill with no `license` field is a skill you have no recorded permission to use.
  No licence is the same rule as no provenance row: **no licence, no run** ([4.1](../04-provenance/4.1-no-row-no-run.md)).

There is a fourth thing pass 1 notices without stopping for it: the optional `compatibility` field,
which the spec says is where a skill declares environment needs like *"requires network access"*. That
is not a failure — it is the skill telling you its blast radius in its own words, and it belongs on the
agenda for [2.3](2.3-the-capability-inventory.md) to weigh.

The reason this pass is first is stated plainly in [2.1](2.1-read-it-like-the-thing-that-will-obey-it.md):
cheap and decisive before slow and thorough. A skill that fails pass 1 never costs you the careful read
of pass 3 or the syntax-tree read of pass 5.

## Why Sutra needs it

Because two of pass 1's three checks are permission gates, not quality checks, and Sutra's provenance
discipline runs on both. The licence check is *no licence, no run* in its earliest form
([4.1](../04-provenance/4.1-no-row-no-run.md)): a skill you have no recorded right to use is one you do
not wire in, however good it looks. The load check is what lets every later pass assume a well-formed
skill object exists to read — `capabilities.py`, `red_flags.py` and the rest all call
`load_skill_from_dir` or read the files it validated, so a skill that fails to load has nothing for them
to inspect.

You meet pass 1 again on Day 31, where it stops being a script you run by hand and becomes part of the
quality gate: `./m check` will load and licence-check every skill on the shelf before the suite runs, so a
malformed or unlicensed skill fails the build in seconds rather than surfacing as a mystery at activation
time ([3.3](../03-the-poisoned-skill/3.3-it-validated-and-was-hostile.md) is where validation and this
gate are drawn together).

## The mechanism

```python
# lab/identity.py - pass 1
from google.adk.skills import load_skill_from_dir
from pack import Finding, rel, skill_dirs


def findings(root):
    """Four cheap questions per skill. Any of them failing ends the audit here."""
    out = []
    for folder in skill_dirs(root):
        where = rel(root, folder)
        try:
            skill = load_skill_from_dir(folder)
        except (ValueError, OSError) as error:
            out.append(Finding(where, "will-not-load", f"{type(error).__name__}: {error}"))
            continue
        front = skill.frontmatter
        if front.name != folder.name:
            out.append(Finding(where, "name-mismatch", f"declares {front.name!r}"))
        if not front.license:
            out.append(Finding(where, "no-licence", "no licence field - no licence, no run"))
        if front.compatibility:
            out.append(Finding(where, "declares-needs", front.compatibility))
    return out
```

**Line by line:**

- `skill_dirs(root)` (a helper in `pack.py`) returns every folder under `root` that holds a `SKILL.md`,
  so one pack containing several skills is audited skill by skill. A sourced pack is rarely one skill
  ([6.1](../06-in-production/6.1-run-the-pack-against-the-routing-gate.md)).
- `load_skill_from_dir(folder)` is [Day 26](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.1-load-skill-from-dir.md)'s
  loader, verified against the installed `google-adk` 2.7.1 on 2026-09-04. Loading is safe here — it
  parses YAML and reads text; it does **not** run scripts or call a model, so it is fine on untrusted
  input. This is the one place the audit lets ADK touch the skill, and it touches only its metadata.
- `except (ValueError, OSError)` catches both a malformed skill (`ValueError`) and an unreadable folder
  (`OSError`), turns each into a finding, and `continue`s. A pass that crashes on the first bad skill
  audits nothing after it; a pass that records and moves on audits the whole pack. This is the same
  fail-soft-per-folder decision `sutra/desk/skills.py` made on [Day 27](../../../day-27-authoring-first-skills/parts/03-procedure-and-capability/3.2-honouring-the-contract.md).
- `front.name != folder.name` is checked even though the loader already enforces it, because a future
  loader might not, and an audit states its own invariants rather than trusting another layer's. In
  practice the loader raises first, so this branch reports a mismatch only if a laxer loader ever lets
  one through — belt and braces on the identity claim.
- `not front.license` is the licence gate. An empty or absent field is a finding, because a skill with
  no declared licence is one you have no right to run, however good it looks.
- `front.compatibility` is recorded when present. It is not a failure — it is a declared need, surfaced
  so the capability pass can weigh it against what the scripts actually do.

## When it breaks

**A malformed skill read as a hostile one.** `ValueError: ... does not match directory name` is not an
attack — it is usually a publisher who renamed a folder and forgot the frontmatter. The finding is
`will-not-load`, and the right response is to fix or reject on quality grounds, not to reach for the
security vocabulary. Pass 1 sorts the broken from the suspicious so later passes are not wasted on
typos.

**Treating a clean pass 1 as a clean skill.** This is the failure the empty output above is designed to
teach. The poisoned fixture sails through pass 1 — valid frontmatter, matching name, a licence — and is
still the most dangerous skill in the day. A validator checks that pass 1 passes and calls the skill
"valid"; that is exactly the gap [3.3](../03-the-poisoned-skill/3.3-it-validated-and-was-hostile.md) is
about.

**Accepting "no licence" as "probably fine".** A missing licence is easy to wave through — the code
looks harmless, surely nobody minds. But the rule is not about the code being harmful; it is about you
having no recorded right to run it, which is a provenance failure ([4.1](../04-provenance/4.1-no-row-no-run.md)),
and provenance failures are the ones that surface as legal problems long after the technical review
passed.

## In production

**A professional makes pass 1 a machine gate, not a human step.** Loading, name-matching and
licence-presence are mechanical and deterministic, so they belong in `./m check` alongside the spec
validator, failing the build before a human is asked to read anything. Human attention is scarce and
belongs on the passes that need judgement; pass 1 needs none, so it should never reach a person as
manual work.

**What changes at scale** is that the licence check grows teeth. One skill with a missing licence is a
question; forty skills across a dozen repositories with a spread of licences is a compliance surface,
and "no licence, no run" becomes "no *approved* licence, no run" — a copyleft licence on a skill you
ship in a proprietary product is a different failure from a missing one, and the ledger's licence column
is what a later audit greps ([4.1](../04-provenance/4.1-no-row-no-run.md)).

**The review comment a senior engineer leaves:** *"pass 1 is green, so this is cleared to *audit*, not
cleared to *merge*. The frontmatter being valid tells me it's a well-formed skill; it tells me nothing
about whether we should run it. Where are passes 2 through 5?"*

**The interview question:** *"what's the first thing you check on a sourced skill, and why that first?"*
The honest spoken answer: *"Whether it loads, whether its declared name matches the folder, and whether
it has a licence — the cheapest, most decisive checks, so a malformed or unlicensed skill is rejected in
seconds before I spend a careful read on it. It's also where I separate broken from suspicious: a load
error is usually a typo, not an attack. The trap is thinking a clean pass 1 means a clean skill — the
worst skill I've audited passed all of pass 1 and was caught only by reading the body and the scripts.
Valid frontmatter is a starting line, not a finish line."*
