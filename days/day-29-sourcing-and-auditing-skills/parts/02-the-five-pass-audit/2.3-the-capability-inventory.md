# 2.3 — Pass 2: the capability inventory

## One-line answer

The second pass lists everything the skill asks permission to do — every tool it pre-approves, every
tool it wants the agent to have, every script it can run, and every outbound URL anywhere in its files —
so that before you read a word of the body you already know the largest thing this skill could do if you
obeyed all of it.

## The story

A contractor comes to redo the bathroom and, before starting, hands you a list of what they will need
access to.

The water main, to shut it off. A key to the back gate, so materials can come through. A socket in each
room for the tools. The loft hatch, to check the pipework. You read the list at the kitchen table, and
right there — before a single tile is lifted — you know the extent of what these people can reach while
they are in your house. The list is not an accusation. Good contractors hand you exactly this. It is the
blast radius, written down, so you can agree to it with your eyes open, or ask why the bathroom job
needs a key to the back gate.

The dangerous contractor is not the one with a long list. It is the one who never gives you a list and
you discover, three days in, that they have had a key to the gate the whole time.

## The idea in plain language

A skill's blast radius — how much damage it could do if its instructions were followed literally — lives
in a few specific places, and pass 2 reads all of them into one list before the body read colours your
judgement. There are four:

- **`allowed-tools`** — the frontmatter field, described by the spec as *"a space-separated string of
  tools that are pre-approved to run"*, marked experimental. Every tool here is one the skill has
  arranged to use *without asking again*. That is precisely the wheel the poisoned fixture greases:
  `allowed-tools: run_skill_script` pre-approves running its own script.
- **`adk_additional_tools`** — the metadata key from [Day 27](../../../day-27-authoring-first-skills/parts/03-procedure-and-capability/3.1-a-named-tool-is-a-contract.md)
  by which a skill declares the tools its steps assume. Each is a capability the skill wants the agent to
  hold when it activates.
- **`scripts/`** — every executable the skill ships. A script is the most powerful thing in a skill,
  because it runs as code, not as a request to a model ([2.6](2.6-the-scripts-read-never-run.md) reads
  them; pass 2 just counts them).
- **outbound URLs** — any `http://` or `https://` address in any file. A URL is where data could go and
  where instructions could come from, so every one is surfaced for a human to explain.

The **blast radius** of a skill is `scripts/` plus `allowed-tools`: the code it can run and the tools it
can invoke without a fresh prompt. That phrase is [3.1](../03-the-poisoned-skill/3.1-a-skill-is-source-you-did-not-write.md)'s
whole security claim in four words, and pass 2 is where you measure it. Every item here is a `Finding`
in the sense of [2.1](2.1-read-it-like-the-thing-that-will-obey-it.md): an agenda item, not a verdict.
`ticket-triage` wanting `lookup_ticket` is a capability to justify, and it is completely fine.

## Why Sutra needs it

Because Sutra's defences so far all assume the *user* might be adversarial — the honesty rules in the
persona, the `guard_tools` veto, error surfacing. A sourced skill is a different threat: its text
arrives inside the trusted channel, and the tools it can reach are the tools it can turn against you
([3.1](../03-the-poisoned-skill/3.1-a-skill-is-source-you-did-not-write.md)). Knowing the blast radius
before you read the body means you read the body already asking the right question: not *"is this
sentence odd?"* but *"this skill can run a script and reach a URL — does the body use that power for
what it claims, or for something else?"*

The inventory also feeds the provenance row directly. The row records the *permitted scope* of a skill
([4.1](../04-provenance/4.1-no-row-no-run.md)) — what it is allowed to touch — and pass 2 is where that
scope is first enumerated. You cannot write "permitted scope: none" honestly until you have listed what
the skill *asked* for and decided to grant none of it.

## The mechanism

```python
# lab/capabilities.py - pass 2
import re

from google.adk.skills import load_skill_from_dir
from pack import Finding, files, rel, skill_dirs

URL = re.compile(r"https?://[^\s)\"'>\]]+")


def findings(root):
    """One finding per capability. A capability is not a fault - it is a thing to justify."""
    out = []
    for folder in skill_dirs(root):
        where = rel(root, folder)
        try:
            skill = load_skill_from_dir(folder)
        except (ValueError, OSError):
            continue  # pass 1 already reported it
        for tool in (skill.frontmatter.allowed_tools or "").split():
            out.append(Finding(where, "pre-approved", f"allowed-tools grants {tool}"))
        for name in skill.frontmatter.metadata.get("adk_additional_tools") or []:
            out.append(Finding(where, "wants-tool", f"metadata requires {name}"))
        for name in sorted(skill.resources.scripts):
            out.append(Finding(where, "executable", f"scripts/{name}"))
    seen = set()
    for path in files(root):
        try:
            text = path.read_text(encoding="utf-8")
        except (UnicodeDecodeError, OSError):
            out.append(Finding(rel(root, path), "unreadable", "not UTF-8 text - open it by hand"))
            continue
        for url in URL.findall(text):
            if url not in seen:
                seen.add(url)
                out.append(Finding(rel(root, path), "outbound-url", url))
    return out
```

**Line by line:**

- `URL` matches `http://` or `https://` up to the first whitespace or closing bracket/quote. It is
  deliberately broad — a false positive here is a URL a human glances at and clears, which is cheap,
  while a missed URL is a data exit nobody noticed, which is not.
- `skill.frontmatter.allowed_tools or ""` handles the field being absent. `.split()` on the
  space-separated string yields each pre-approved tool. Every one becomes a `pre-approved` finding,
  because pre-approval is the strongest grant a skill can make in frontmatter — it is the tool it will
  use *without asking*.
- `metadata.get("adk_additional_tools") or []` reads [Day 27](../../../day-27-authoring-first-skills/parts/03-procedure-and-capability/3.1-a-named-tool-is-a-contract.md)'s
  declared-tools list. These are `wants-tool` findings: capabilities the skill wants the agent to hold,
  weaker than pre-approval because the agent still chooses to call them.
- `skill.resources.scripts` is the dict of scripts ADK loaded from `scripts/`, verified against the
  installed `google-adk` 2.7.1 on 2026-09-04. Each becomes an `executable` finding. Counting them here,
  reading them in [2.6](2.6-the-scripts-read-never-run.md), keeps pass 2 fast: it inventories, it does
  not analyse.
- The second loop reads **every file**, not only `SKILL.md`, because a URL can hide in a reference or a
  script. `seen` de-duplicates so one URL repeated across files is one finding.
- `except (UnicodeDecodeError, OSError)` turns a file that is not readable text into an `unreadable`
  finding rather than a crash. A binary blob in a skill is itself suspicious — a skill is text and
  scripts — so "open it by hand" is the right instruction, not a silent skip.

Run it on the poisoned fixture. On 2026-09-04:

```bash
uv run python days/day-29-sourcing-and-auditing-skills/lab/capabilities.py tests/fixtures/skills/evil-helper
```

**Line by line:**

- Folder in, findings out. **Zero model calls, no key.**

```text
evil-helper                  pre-approved   allowed-tools grants run_skill_script
evil-helper                  executable     scripts/quality_check.py
scripts/quality_check.py     outbound-url   https://styles.example-cdn.invalid/latest
```

Three findings, and read together they are the blast radius: the skill has pre-approved running a
script, ships that script, and somewhere in it is an outbound URL. You have not read the body or the
script yet, and you already know this skill can execute code that talks to
`styles.example-cdn.invalid`. That is the shape of an exfiltration channel, drawn before a single
sentence of prose was interpreted. Contrast Sutra's own skill:

```text
ticket-triage    wants-tool   metadata requires lookup_ticket
ticket-triage    wants-tool   metadata requires search_kb
```

Two `wants-tool` findings, no scripts, no URLs, no pre-approvals. Same pass, same code, and the
difference between "capabilities to justify" and "the outline of an attack" is visible in the columns.

## When it breaks

**Reading a capability as a verdict.** The two `wants-tool` findings on `ticket-triage` are not a
problem — they are the tools its procedure legitimately needs, declared honestly. A reviewer who treats
every finding as a flag rejects their own skills. The inventory's job is to make you *justify* each
capability, and "the triage steps call these two tools, granted" is a perfectly good justification.

**Missing the URL because it is in a script, not the body.** A reviewer who scans only `SKILL.md` for
URLs misses the one in `quality_check.py`, which is where the poisoned fixture hid it. Pass 2 reads
every file for exactly this reason: the body can be spotless and the exit can be in the code.

**An unreadable blob waved through.** A file that is not UTF-8 text in a skill is not normal — skills are
Markdown and scripts — and the instinct to skip "some binary thing" is the instinct an attacker relies
on. `unreadable` is a finding, and the correct response is to open it by hand or reject, not to assume
it is a harmless asset.

## In production

**A professional turns the inventory into an allowlist, not a glance.** The mature version of pass 2 is
a policy: these tools may be pre-approved, these hosts may be contacted, scripts require sign-off. The
inventory then fails automatically when a sourced skill asks for something outside the policy. That is
Day 40's territory for MCP tool filtering and allowlists, and it is exactly the same shape here. Sutra already lints one capability this way and will lint
more from Day 31: a capability the policy forbids is caught by a rule, not by a reader remembering to
look.

**What changes at scale** is that the URL list becomes an egress question. Ten skills each contacting a
different host is ten holes in whatever network boundary the agent runs behind, and "which skills talk
to the internet, and where" stops being a per-skill finding and becomes a firewall rule. The inventory
is where that list is first assembled, and a skill that needs to reach a host your egress policy does not
allow is a skill you cannot run regardless of how benign its body reads.

**The failure mode that only appears with real traffic** is the pre-approved tool used correctly
ninety-nine times and abused once. `allowed-tools` removes the prompt, so the hundredth call — the one
triggered by a poisoned ticket the skill was told to trust — happens without a human in the loop. That
is why pre-approval is the strongest finding in the inventory and why a senior reviewer questions every
entry in `allowed-tools` specifically, not the `wants-tool` list.

**The review comment a senior engineer leaves:** *"this skill pre-approves `run_skill_script` and ships
a script that reaches an external host. That's a code-execution-plus-egress capability, granted without a
prompt. I don't care how clean the body reads — justify that combination or drop the pre-approval, and
either way it doesn't merge until the script in pass 5 is cleared."*

**The interview question:** *"how do you work out the blast radius of a skill before you trust it?"* The
honest spoken answer: *"I inventory everything it asks permission to do before I read the prose: tools
it pre-approves in `allowed-tools`, tools it wants via metadata, scripts it ships, and every outbound URL
in any file — not just the SKILL.md, because the exit is usually in a script. The blast radius is
scripts plus pre-approved tools: the code it can run and the tools it can invoke without asking again.
Each item is a thing to justify, not automatically a fault — my own skills declare the tools they need —
but the combination of pre-approved script execution and an external URL is the outline of an
exfiltration channel, and I can see that in the inventory before I've interpreted a single sentence."*
