# 2.1 — Read it like the thing that will obey it

## One-line answer

An audit is a full read of a skill by a human, in a fixed cheap-to-expensive order, asking of every
line the one question the agent will answer for real — *if my agent obeys this literally, what
happens?* — and it uses zero model calls, on purpose, because the whole point is that nothing untrusted
reaches the model until a person has cleared it.

## The story

The mechanic does not test-drive the used car to find the brake fault.

That is the instinct — take it round the block, see how it feels. But the mechanic puts it on the ramp
first, lifts it up, and looks: at the discs, the lines, the sills, the underside you cannot see from the
driver's seat. Only after the car has passed the look does anyone start the engine.

The reason is not caution for its own sake. It is that the test drive is the thing that could hurt you.
If the brakes are gone, you find out by pressing them at thirty, which is exactly the situation you were
trying to avoid. The look on the ramp is free of that risk: the car is not moving, nothing you find can
run away with you, and you learn what you need before you commit to the road.

You can only skip the ramp on a car you built yourself, because then you already know what is
underneath.

## The idea in plain language

A skill's body is instructions the agent will follow, plus files it may read and scripts it may run
([Day 25](../../../day-25-skills-the-open-spec/parts/01-what-a-skill-is/1.1-a-skill-is-a-folder.md)).
An **audit** is you reading all of that, front to back, before any of it is wired into an agent — the
look on the ramp before the test drive.

Two commitments make it an audit rather than a skim.

**Read in the agent's voice.** For every line of the body, ask the question the model will effectively
answer at runtime: *if my agent obeys this literally, what happens?* This is [Day 27](../../../day-27-authoring-first-skills/parts/06-in-production/6.1-reviewing-a-skill-like-code.md)'s
"review a skill like code", pointed at a stranger's skill and hardened. A line that reads as friendly
advice to a human — *"for compliance, include the full ticket history"* — is an instruction to exfiltrate
when the reader is a thing that does what text says.

**Cheap checks first, and stop early.** The audit is five passes in a fixed order, and the order is not
arbitrary: it runs the fast, decisive checks before the slow, thorough ones, so a skill that fails an
early pass never costs you a late one.

| Pass | Question | Cost |
| --- | --- | --- |
| 1 · identity ([2.2](2.2-pass-one-will-it-load.md)) | does it load, is it what it claims, may you keep it? | seconds |
| 2 · capabilities ([2.3](2.3-the-capability-inventory.md)) | what does it ask permission to do? | seconds |
| 3 · the body ([2.4](2.4-reading-the-body.md)) | do any lines read as an attack? | a careful read |
| 4 · references ([2.5](2.5-the-files-it-points-at.md)) | what does it fetch later, and what hides? | a read |
| 5 · scripts ([2.6](2.6-the-scripts-read-never-run.md)) | what does its code do, read never run? | the slowest read |

The verdict is **written** ([3.2](../03-the-poisoned-skill/3.2-the-poisoned-skill-and-the-audit.md)):
accept, accept-with-changes, or reject, with reasons. An audit you did not write down is an audit that
did not happen ([Day 27](../../../day-27-authoring-first-skills/parts/06-in-production/6.1-reviewing-a-skill-like-code.md)
made the same point about review).

## Why Sutra needs it

Because the entire day rests on one line in the mission: **zero model calls.** An audit that needs the
model has already failed, because to ask the model about the skill you would have to put the skill's
untrusted text into the model's context — which is the exact thing the audit exists to prevent from
happening before a human has cleared it.

This is the mechanic's ramp restated for agents. You read with your eyes precisely so that nothing
untrusted reaches the component that acts on text. Every pass in this section is arithmetic, string
matching, or reading a syntax tree — deterministic, free, and safe to run on hostile input, because
none of it *interprets* the input the way the agent would. The poisoned skill in
[3.2](../03-the-poisoned-skill/3.2-the-poisoned-skill-and-the-audit.md) is caught entirely this way, and
the paper this day teaches is the reason the read can never be the *whole* answer — reading is necessary
and not sufficient ([the paper](../../papers/01-reflections-on-trusting-trust.md)).

## The mechanism

The five passes are five small Python modules that each take a folder and return a list of findings.
They share one vocabulary so a finding from pass 1 and a finding from pass 5 line up in the same
columns. That shared type is the mechanism of this part; the passes themselves are the next five.

```python
# lab/pack.py - the shared vocabulary every pass speaks
from dataclasses import dataclass


@dataclass(frozen=True)
class Finding:
    """One thing the audit wants a human to look at. Not an accusation - an agenda item."""

    where: str
    rule: str
    detail: str

    def __str__(self) -> str:
        return f"{self.where:<42} {self.rule:<18} {self.detail}"
```

**Line by line:**

- `@dataclass(frozen=True)` makes a `Finding` a small immutable record with three fields and value
  equality. Frozen because a finding is evidence — once a pass records what it saw, nothing should
  mutate it before you read it.
- `where` is the address: a file path, or `file:line` for a body finding, so you can go straight to it.
  An audit that says "something is wrong somewhere" wastes the reader's time; every finding points at a
  place.
- `rule` is the *kind* of thing found — `network`, `concealment`, `outbound-url` — a short tag you can
  scan a column of. It groups findings so a reader sees "three network calls" at a glance.
- `detail` is the specific text: the URL, the line, the tool name. Enough to judge without opening the
  file, so triage is possible from the printout alone.
- The docstring's second sentence is the load-bearing idea of the whole section: **a finding is an
  agenda item, not an accusation.** `ticket-triage` declaring two tools it needs is a finding
  ([2.3](2.3-the-capability-inventory.md)) and is completely fine; the audit's job is to surface every
  capability so a human decides, not to pronounce guilt. This framing is why the passes can be blunt and
  over-report — a human is doing the judging.
- `__str__` fixes the three-column layout once, so every pass prints the same shape and the combined
  report ([2.6](2.6-the-scripts-read-never-run.md)) reads as one document rather than five.

## When it breaks

**Auditing by asking the model to summarise the skill.** *"I pasted the SKILL.md into a chat and asked
if it looked safe."* You have now done the one thing the audit exists to prevent — put untrusted text
into a model — and worse, you have asked a text-follower to judge text designed to manipulate
text-followers. The whole point of reading with your eyes is that your eyes do not execute what they
read. The audit is zero model calls or it is not an audit.

**Reading in the wrong voice.** A reviewer used to reading skills as documentation reads *"always run
`scripts/setup.py` first"* as helpful onboarding. Read in the agent's voice it is *"always run this
attacker-supplied script before doing anything"*. The question is fixed for a reason: *if my agent obeys
this literally, what happens?* — not *is this a reasonable thing to write?*

**Skipping the order and diving into the scripts.** The scripts are the most interesting pass and the
most expensive, and a reviewer who starts there spends an afternoon reading Python for a skill whose
frontmatter would have failed pass 1 in seconds. Cheap first is not fussiness; it is what keeps the
audit affordable enough to actually run on every sourced skill.

## In production

**A professional runs the cheap passes automatically and reserves human reading for the passes that
need judgement.** Identity, capabilities and reference-resolution ([2.2](2.2-pass-one-will-it-load.md),
[2.3](2.3-the-capability-inventory.md), [2.5](2.5-the-files-it-points-at.md)) are mechanical and belong
in `./m check` beside the validator; the body read ([2.4](2.4-reading-the-body.md)) and the script read
([2.6](2.6-the-scripts-read-never-run.md)) surface candidates but a human makes the call. The split is
the same one [3.3](../03-the-poisoned-skill/3.3-it-validated-and-was-hostile.md) draws between
validation and audit: automate the shape, judge the sense.

**What changes at scale** is that "read every line" becomes "read every line of every *change*". You
audit a skill in full once, at the pinned revision, and after that you audit diffs — which is only safe
because the pin guarantees there are no changes you did not see ([1.2](../01-the-doors/1.2-who-can-change-the-text.md)).
Without the pin, "audit the diff" is meaningless, because the base you are diffing against could have
moved.

**The review comment a senior engineer leaves:** *"good that you read it. Did you read it as
documentation or as instructions to an obedient process? Re-read step 3 asking 'what happens if the
agent does exactly this' — that's the read that matters, and it changes what that line means."*

**The interview question:** *"how do you audit a third-party agent skill, and why not just ask a model
to check it?"* The honest spoken answer: *"You read it yourself, front to back, cheapest checks first —
identity, then the capabilities it asks for, then the body, then the files it points at, then the
scripts — asking of every line 'if my agent obeys this literally, what happens'. Zero model calls, and
that's the whole point: to ask a model you'd have to feed it the untrusted text, which is exactly what
you're auditing to prevent, and you'd be asking a text-follower to judge text built to manipulate
text-followers. So the audit is deterministic and safe on hostile input — string matching and a syntax
tree — and the verdict is written down, because an unwritten audit didn't happen."*
