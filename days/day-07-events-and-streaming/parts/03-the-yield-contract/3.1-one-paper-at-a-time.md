# 3.1 — One paper at a time

## One-line answer

An ADK agent **yields** each event as it happens and stops there until the runner has processed it —
this is trap #3 from the plan's §5.1, and the pause is not a cost, it is the promise that everything
the event asked for has been done before your code continues.

---

## The story

You are at a government counter renewing something. There is a clerk behind the glass with a rubber
stamp and an ink pad, and you have a folder of documents.

The way it goes: you slide one paper under the glass. The clerk looks at it, stamps it, writes
something in a register, and puts it in a tray. Then they look up at you, and you slide the next one
across.

You cannot push the whole folder through at once. There is not enough room under the glass, and more
to the point, the clerk will not take it. One paper, one stamp, one register entry, then the next.

It feels slow. It is not slow — it is *sequenced*, and there is a reason for the sequence that
becomes obvious the moment you imagine the alternative.

Suppose you handed over the whole folder and walked away. Now: which papers were stamped? If the
clerk got halfway and the office closed, what state is your application in? If the third paper turned
out to need something the second one was supposed to have, when did anyone find out? Nobody knows,
including the clerk. The folder went in as a lump and whatever happened inside is not recoverable
from the outside.

The one-at-a-time version answers all three questions by construction. Every paper that went across
has a stamp on it and a line in the register. Every paper still in your hand does not. There is no
in-between state, because you were standing there the whole time.

That counter is the ADK runtime, and this part is about why your agent has to stand there too.

---

## The idea in plain language

The plan's §5.1 lists four ways an ADK 1.x habit breaks on 2.x. **Trap #3 is this one:**

> *1.x habit: custom agents collected events into a list and returned them. 2.x reality: custom
> agents and nodes **yield** events as they happen. Appending-then-returning breaks streaming and
> ordering guarantees.*

Some vocabulary, because "yield" is the whole subject and it is worth being exact.

A normal function computes something and **returns** it. It runs from top to bottom, once, and then
it is finished.

A **generator** is a function containing the word `yield` instead. When you call it, nothing runs at
all — you get an object back. Each time somebody asks that object for the next item, the function
body runs until it reaches a `yield`, hands over that value, and then **freezes exactly where it is**,
with all its local variables intact. When somebody asks again, it thaws and carries on from the line
after the `yield`.

An **async generator** is the same thing where the pauses can also be waiting for input or output —
a network call, a disk read — without blocking everything else in the program. That is what
`_run_async_impl` is, and what `runner.run_async` is, and it is why every loop over one is written
`async for` rather than `for`.

Now the part that matters. Because the agent *freezes* at the yield, the runner gets a window in
which nothing else in the agent is running. adk.dev's event-loop page describes what it does with
that window:

> *"The `Runner` receives this `Event`, processes any associated actions (like saving state changes
> via `Services`), and forwards the event onwards... The `Agent`'s logic **resumes** from where it
> paused only *after* the `Runner` has processed the event."*
> (adk.dev/runtime/event-loop/, checked 2026-08-26)

So the sequence for one event is: agent yields → runner applies its actions → runner saves it →
runner passes it to you → agent thaws and continues.

That ordering is a **guarantee you can build on**, and it is worth naming what it gives you, because
"the framework does it in a specific order" sounds like trivia until you list the four things that
depend on it:

1. **State is committed before the agent continues.** Whatever the last event asked to be stored is
   stored by the time the next line of agent code runs.
2. **Streaming works at all.** A chunk that is returned at the end of the run arrives at the end of
   the run, which is not streaming.
3. **Order is real.** The events reach you in the order they happened, not in the order somebody
   assembled a list.
4. **A run can be stopped in the middle and still make sense.** Everything yielded is committed;
   everything not yielded never happened. There is no half-state, exactly as at the counter.

Collect-then-return breaks all four, and the reason it is a *trap* rather than merely a mistake is
that it looks tidier. Building a list and returning it is what most people would write, and it is
what a year of 1.x tutorials shows.

---

## Why Sutra needs it

**Phase 8, from Day 53**, is the graph Workflow Runtime, where you write nodes of your own. A node
that collects events is a node that cannot stream, cannot be cancelled cleanly, and cannot have its
state relied upon by the node after it.

**Phase 9, from Day 60**, is durability: kill Sutra mid-run and watch it resume. Resumption is
possible precisely because the yield boundary is a commit boundary. An agent that returns a list has
one commit, at the end, and there is nothing to resume from.

**Day 64** brings human-in-the-loop approval: a run pauses, waits for a person, and continues later.
That pause is a yield boundary that stayed frozen for a while. Once you have seen `yield` as "stop
here until somebody says go", a run that waits for a human is not a new mechanism, it is the same one
with a longer pause.

Today, immediately: [3.3](3.3-your-own-emitter.md) has you write a small agent that emits its own
events, and [5.1](../05-failure-lab/5.1-the-mechanic-who-billed-at-the-end.md) has you break it on
purpose.

## The mechanism

The smallest custom agent that yields — no model, no key, no cost, and therefore something you can
run fifty times while you get a feel for it:

```python
# lab/yielding.py - a custom agent that emits its own events, one at a time.
import asyncio
from collections.abc import AsyncGenerator

from google.adk.agents import BaseAgent
from google.adk.agents.invocation_context import InvocationContext
from google.adk.events import Event, EventActions
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

from sutra.desk.events import describe


def note(author: str, text: str, **kwargs) -> Event:
    """A plain text event from a named author."""
    return Event(
        author=author,
        content=types.Content(role="model", parts=[types.Part(text=text)]),
        **kwargs,
    )


class Counter(BaseAgent):
    """Yields three events and records how far it got in state, as it goes."""

    async def _run_async_impl(self, ctx: InvocationContext) -> AsyncGenerator[Event, None]:
        for step in (1, 2):
            yield note(self.name, f"step {step}", actions=EventActions(state_delta={"step": step}))
            print(f"    [agent] resumed; state now says {ctx.session.state.get('step')}")
        yield note(self.name, "done")


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name="probe", user_id="u")
    runner = Runner(agent=Counter(name="counter"), app_name="probe", session_service=service)

    message = types.Content(role="user", parts=[types.Part(text="go")])
    async for event in runner.run_async(user_id="u", session_id=session.id, new_message=message):
        print(describe(event))

    stored = await service.get_session(app_name="probe", user_id="u", session_id=session.id)
    print("stored events:", len(stored.events))
    print("stored state :", stored.state)


asyncio.run(main())
```

**Line by line:**

- `class Counter(BaseAgent)` — `BaseAgent`, not `LlmAgent`. `LlmAgent` is the one that talks to a
  model; `BaseAgent` is the bare contract, and subclassing it is how you write an agent that does
  something other than prompt a model. That is the entire reason this demonstration is free.
- `async def _run_async_impl(self, ctx)` — the one method you must implement. The leading underscore
  says it is called by the framework, not by you: you call `run_async`, and ADK's `BaseAgent.run_async`
  sets up the context and then drives this. Overriding `run_async` itself is how people accidentally
  remove the setup they needed.
- `-> AsyncGenerator[Event, None]` — the declared return type, and it is a promise the whole runtime
  is built on. `AsyncGenerator[Event, None]` means "yields `Event`s, and nothing is ever sent back
  in". A function whose body contains `yield` becomes a generator whatever you annotate, but the
  annotation is what tells a reader — and a type checker — which contract this method is honouring.
- `ctx: InvocationContext` — everything the agent is allowed to see about the current run: the
  session, the run id, the services. You are given it rather than reaching for a global, which is
  what makes two runs in the same process safe.
- `yield note(...)` inside the loop — the event goes out here, and this line is where the agent
  freezes.
- `print(f"    [agent] resumed; ...")` on the line **after** the yield — the whole demonstration.
  This line only runs once the runner has finished with the event, so what it prints is proof of the
  ordering rather than a claim about it.
- `ctx.session.state.get("step")` — read *after* resuming, so the value it finds is the one the
  runner committed. Reading it before the yield would show you the old value, which is
  [3.2](3.2-saved-is-not-submitted.md)'s subject.
- `actions=EventActions(state_delta={"step": step})` — the change from
  [1.4](../01-the-event-object/1.4-the-half-that-is-not-text.md), travelling in the event as it must.
- `Counter(name="counter")` — `BaseAgent` requires a `name`, and it becomes the `author` on every
  event this agent produces, exactly as [1.5](../01-the-event-object/1.5-which-run-which-agent-which-branch.md)
  described.
- `async for ... : print(describe(event))` — your own reader from
  [1.5](../01-the-event-object/1.5-which-run-which-agent-which-branch.md), earning its keep on the
  first day it exists.

Running it produces this, and the interleaving is the finding:

```text
         counter      text    final=True  'step 1'
    [agent] resumed; state now says 1
         counter      text    final=True  'step 2'
    [agent] resumed; state now says 2
         counter      text    final=True  'done'
stored events: 4
stored state : {'step': 2}
```

Read the first three lines in order. Your loop printed `step 1` **before** the agent printed
`resumed`. The event reached you, was committed, and only then did the agent's next line run. That is
the counter and the stamp, in a terminal.

Three smaller findings in the same output.

`stored events: 4` — three from the agent plus the user's message, which the runner appended before
the agent ever started.

Every event says `final=True`, because none of them has a function call and none is partial, which is
[1.3](../01-the-event-object/1.3-is-final-response-is-not-the-last-one.md)'s point arriving without
being asked for.

And the first column is **blank**. That is the `invocation_id`, and it is empty because `note()` never
set one — the runner stamps a run id on the user's message and does **not** put one on events your
agent yields. It is the exact failure
[1.5](../01-the-event-object/1.5-which-run-which-agent-which-branch.md) named under *the empty
`invocation_id`*, here by accident, in code you just wrote. The fix is one keyword,
`invocation_id=ctx.invocation_id`, and Day 8 makes you add it and watch the grouping change.


## When it breaks

**💥 The agent that implements nothing.**

Subclass `BaseAgent`, forget the method, and the framework tells you precisely what is missing:

```text
NotImplementedError: _run_async_impl for <class '__main__.Counter'> is not implemented.
```

Worth meeting once, because the name in that message is the name you have to search the docs for. It
also tells you something about the base class: the default implementation exists purely to raise
this, with a bare `yield` after it that never runs, because a function with no `yield` anywhere is
not a generator at all and the framework needs it to be one.

**💥 `for` instead of `async for`.**

```text
TypeError: 'async_generator' object is not iterable
```

An async generator cannot be walked with an ordinary `for` loop. The fix is one word, and the reason
to name the error is that its text does not contain the word `async for`, so the first instinct is
usually to go looking at what `run_async` returns rather than at your own loop.

**💥 Breaking out of the loop.**

Covered in [1.3](../01-the-event-object/1.3-is-final-response-is-not-the-last-one.md) and worth
restating here, where the mechanism explains it: `break` abandons a frozen generator. The agent is
paused mid-run and is never resumed, so everything it had left to do — the tool result it was about
to yield, the state change on the event after this one — simply never happens. No error, no warning.
The counter closed the window while your papers were still in your hand.

## In production

**What a professional writes instead of the teaching version** is an agent that yields at every point
where an outside observer would want to know something, not just where the code happens to have a
value ready. Each yield is a commit point, a trace span boundary and a place a run can be resumed
from, so the granularity of your yields *is* the granularity of your observability and your
durability. Yielding once at the end is a run you cannot watch and cannot resume; yielding after
every trivial internal step is a session full of noise. The judgement is real and it is made per
agent.

**What degrades at scale** is doing work between yields. The runner is waiting for you the whole time
the agent is thawed, so anything slow between two yields is time nothing else can proceed. A
synchronous network call or a large file read in that gap will stall the invocation and, in a server
with one event loop, contribute to stalling others. ADK gives `RunConfig.tool_thread_pool_config` for
the tool case; the general habit is to make the gaps between yields short and awaitable.

**The failure that only shows with real traffic** is a partially-consumed generator under
cancellation. When a client disconnects mid-run, the loop consuming events goes away, and a generator
frozen at a yield has to be closed properly for its cleanup to run. ADK does this for you — its own
code wraps the agent's generator in an `Aclosing` helper for exactly this reason — but code *you*
write that consumes `run_async` and exits early does not get that for free. It shows up as resources
held after a disconnect, which at low traffic is invisible and at high traffic is a leak.

**The review comment a senior engineer leaves:** *"This node builds the whole result and yields once
at the end. That means no streaming, one commit point, and nothing to resume from if we're killed
halfway. Yield each step as you produce it — and don't do the HTTP call between two yields
synchronously, it stalls the invocation."*

**The interview question:** *"why do agent frameworks make you yield events instead of returning
them?"* The answer that shows you have written one: "Because the yield is a synchronisation point.
The agent freezes there, and the runtime uses that window to commit whatever the event asked for and
forward it on, before letting the agent continue. That single ordering buys you four things:
streaming, real ordering, state that's guaranteed committed before the next line of agent code runs,
and a run that can be killed anywhere and still be in a consistent state — because everything yielded
is durable and everything not yielded never happened. Collecting into a list and returning it
compiles fine and loses all four, which is why it's the first thing people get wrong when they come
from an older version."
