# 1.3 — `is_final_response()` is not "the last one"

## One-line answer

`is_final_response()` means **"this event is complete enough to show a person"**, not "this is the
last event of the run" — several events in one run can answer `True`, and the last event of a run can
answer `False`.

---

## The story

You call the customer-care number about a bill. After the menu and the hold music, a person picks up.

You explain the problem. They say: "Okay sir, so I have checked your account."

And then there is a gap.

You do not know what that gap is. It could be the end of the sentence, in which case they are waiting
for you and every second you stay quiet is awkward. It could be a pause while they read something, in
which case if you start talking you will talk over them. It could be them typing.

So you do what everybody does: you say "hello?" — and of course they were mid-sentence, and now you
have both spoken at once, and one of you says sorry, and you have lost ten seconds.

Notice what you were actually trying to work out. Not "is this the last thing they will ever say" —
obviously not, the call is not over, there is a whole bill to sort out. You were trying to work out
something much smaller: **is this piece of speech finished, so that it is my turn?**

Those are two different questions and they have two different answers, and the entire confusion in
this part comes from a method whose name sounds like the first one and whose meaning is the second.

---

## The idea in plain language

The method is called `is_final_response()`. Almost everyone reads that as "is this the final
response", which sounds like "is this the last one".

It is not. It answers: **would it be correct to show this event to a user as a complete answer from
the agent?**

The difference matters as soon as a run produces more than one displayable thing, which happens
constantly:

- An agent that says something, calls a tool, and then says something else produces **two** events
  that answer `True`.
- A multi-agent system where a dispatcher speaks and then a specialist speaks produces one `True` per
  agent. ADK's own docstring says exactly that: *"there could be one event has `is_final_response()`
  as True for each participating agent."*
- A streaming run produces many events that answer `False` — the chunks — and then one that answers
  `True`.
- And the **last** event of a run is often a bookkeeping event carrying no content at all, which
  answers `False` while being, plainly, the last one.

So `is_final_response()` is a **display filter**, not a loop terminator. The loop terminates when the
generator is exhausted, which in Python means when the `async for` ends. Nothing else ends it.

The actual rule, from the installed package, is short enough to hold in your head. An event is a
final response when **either** of two shortcuts applies:

1. `actions.skip_summarization` is set — a tool result that has been marked as "show this as-is,
   don't ask the model to write it up";
2. `long_running_tool_ids` is non-empty — a background job has been started, and what you have is the
   acknowledgement, which is the most complete thing that exists right now.

Otherwise it is a final response when **all four** of these hold:

- it contains no function call (nobody is being asked to do anything);
- it contains no function response (this is not a tool reporting back);
- it is not `partial` (it is not one chunk of something still arriving);
- its last part is not a code-execution result (there is more coming after the code ran).

Read that list as one sentence and it becomes obvious: *nothing about this event implies that
something else has to happen next.* Which is precisely what "safe to show a person" means.

Two terms defined, since they will be everywhere from Day 10:

- A **function call** is the model asking for one of your tools to be run. You built these by hand on
  [Day 4, part 2.2](../../../day-04-tools-by-hand/parts/02-the-round-trip/2.2-the-call-comes-back-parsed.md).
- A **function response** is your program handing the tool's result back, which you built on
  [Day 4, part 2.3](../../../day-04-tools-by-hand/parts/02-the-round-trip/2.3-the-tool-result-turn.md).

---

## Why Sutra needs it

**Day 10** puts a real `FunctionTool` on Sutra, and from that day on every run has events in it that
are not answers. Code that treats each event as an answer will print the tool call as though the
agent said it, which looks to a user like the assistant babbling JSON at them.

**Day 53 onwards** is multi-agent, and that is where the "one `True` per agent" clause stops being
trivia. A dispatcher hands off to a researcher; both produce a final response; a UI that assumes one
final response per run shows the wrong one.

**Day 79 onwards** is evals, and an eval has to decide what "the answer" was in order to score it.
That decision is this method, and an eval that picks the wrong event scores the wrong text — which
is worse than no eval, because it is confidently wrong.

Right now: `sutra/desk/run_once.py` already contains

> `if event.is_final_response(): answer = event.content.parts[0].text`

which quietly assumes there is one. It survives today because Sutra has no tools yet. Part of today's
build brief is making that assumption visible instead of accidental.

---

## The mechanism

Three events, built by hand, and the method asked about each. No agent, no model, no cost:

```python
# lab/finality.py - which events are showable, and why.
from google.adk.events import Event, EventActions
from google.genai import types


def spoke(text: str, **kwargs) -> Event:
    """A plain text event from the agent."""
    return Event(
        author="sutra_desk",
        invocation_id="run-1",
        content=types.Content(role="model", parts=[types.Part(text=text)]),
        **kwargs,
    )


plain = spoke("Ticket 4521 looks like a session bug.")
chunk = spoke("Ticket 4521 loo", partial=True)
asking = Event(
    author="sutra_desk",
    invocation_id="run-1",
    content=types.Content(
        role="model",
        parts=[
            types.Part(function_call=types.FunctionCall(name="kb_search", args={"q": "logout"}))
        ],
    ),
)
acknowledged = Event(
    author="sutra_desk",
    invocation_id="run-1",
    content=types.Content(role="model", parts=[types.Part(text="Started the reindex.")]),
    long_running_tool_ids={"call-1"},
)
noted = Event(
    author="sutra_desk",
    invocation_id="run-1",
    actions=EventActions(state_delta={"ticket_id": "4521"}),
)

for label, event in [
    ("plain text        ", plain),
    ("streaming chunk   ", chunk),
    ("asking for a tool ", asking),
    ("long-running ack  ", acknowledged),
    ("state change only ", noted),
]:
    print(f"{label} final={event.is_final_response()!s:<5} calls={len(event.get_function_calls())}")
```

**Line by line:**

- `def spoke(...)` — a small helper, because five events built inline would bury the one line that
  differs between them. The thing this part is teaching is the *difference*, so the code makes the
  difference the only visible variation.
- `**kwargs` on the helper — lets `partial=True` and `long_running_tool_ids=...` be passed through
  without a parameter for each. This is the one place a `**kwargs` earns its keep: a pass-through to
  a constructor you do not want to re-declare.
- `partial=True` on `chunk` — the field from [1.1](1.1-an-event-is-a-line-in-a-ledger.md), set
  explicitly. A chunk is *not* showable as an answer, because more of it is coming.
- `types.FunctionCall(name="kb_search", args={"q": "logout"})` — the same shape Day 4 parsed by hand.
  Note it goes inside a `Part`, not on the event: **the kind of an event lives in its content**,
  which is why [1.2](1.2-the-fields-that-were-renamed.md) said there is no `type` field.
- `long_running_tool_ids={"call-1"}` — a `set`, not a list, and that is the declared type. It means
  "these tool calls will finish later"; the event you are holding is the acknowledgement, so it is
  the most complete thing that exists and counts as final.
- `noted` has **no content at all** — only `actions`. Events like this are how state changes travel,
  and [1.4](1.4-the-half-that-is-not-text.md) is about them.
- `event.get_function_calls()` — a helper on the event that digs through `content.parts` and returns
  the function calls it finds. Using it beats writing the loop yourself, because ADK can change how
  parts are laid out and this method changes with it.
- `{event.is_final_response()!s:<5}` — `!s` converts the boolean to its string form before padding,
  because `:<5` on a raw `bool` is a formatting error. A small thing, and the kind of small thing
  that costs ten minutes when you meet it in a hurry.

The output:

```text
plain text         final=True  calls=0
streaming chunk    final=False calls=0
asking for a tool  final=False calls=1
long-running ack   final=True  calls=0
state change only  final=True  calls=0
```

Look at the last row. An event carrying **nothing but a state change** is reported as a final
response, because none of the four disqualifying conditions applies to it: no calls, no responses,
not partial, no code result. That is the sharpest illustration of what the method actually means. It
is not saying "this is the answer". It is saying "nothing about this event implies more is coming" —
and for an empty bookkeeping event, that is technically true and practically useless.

Which is why the filter you actually want in a display loop is two conditions, not one:

```python
# The pattern that survives Day 10.
async for event in runner.run_async(user_id=USER_ID, session_id=session_id, new_message=message):
    if event.is_final_response() and event.content and event.content.parts:
        text = "".join(part.text or "" for part in event.content.parts)
        if text:
            print(text)
```

**Line by line:**

- `event.is_final_response()` — with the parentheses, and first, because it is the cheapest check and
  rules out the majority.
- `and event.content and event.content.parts` — the guard from
  [1.1](1.1-an-event-is-a-line-in-a-ledger.md), which is what stops the empty state-change event from
  reaching the print.
- `"".join(part.text or "" for part in ...)` — all the parts, skipping the ones with no text, for the
  reasons 1.1 gave.
- `if text:` — a final, showable event whose parts are all non-text produces an empty string, and
  printing a blank line for it looks like a bug to the user. Three guards, and every one of them is
  there because of a specific thing that will exist in Sutra by Day 10.
- `print(text)` rather than assigning to a single `answer` variable — because there can be more than
  one, which is the whole point of this part. `sutra/desk/run_once.py`'s current shape keeps only the
  last; today's build brief asks you to decide, deliberately, whether that is what you want.

## When it breaks

**💥 Using it as a loop terminator.**

```python
async for event in runner.run_async(...):
    if event.is_final_response():
        break
```

There is no error. What happens instead is worse: `break` out of an `async for` abandons the
generator, so the runner never gets to finish. Any event that would have come after — the tool result
you were about to receive, the bookkeeping event that commits a state change — never happens, and any
cleanup the runtime had queued does not run. The symptom is a state value that is set in your code
and missing from the session, appearing only sometimes, because it depends on which event happened to
be final first.

**Let the loop end on its own.** If you genuinely need to stop early, that is a *cancellation*, which
is a different thing with its own machinery, and Phase 9 is where it belongs.

**💥 Assuming exactly one.**

```python
answer = "(no final response)"
async for event in runner.run_async(...):
    if event.is_final_response():
        answer = event.content.parts[0].text
```

This is the shape in `sutra/desk/run_once.py` today, and today it is correct, because with no tools
there is exactly one. On Day 10 it silently starts meaning "the **last** final response", which for a
tool-using agent is usually right and occasionally throws away the sentence the agent said *before*
it went and looked something up. Nothing errors. A user just gets half an answer, sometimes.

**💥 Forgetting the parentheses.** Covered in [1.1](1.1-an-event-is-a-line-in-a-ledger.md), repeated
here because it is the single most common way this method goes wrong and it produces no error text at
all:

```text
# with `if event.is_final_response:` every event prints, including the chunks and the tool calls
Ticket 4521 loo
Ticket 4521 looks like a session
Ticket 4521 looks like a session bug.
```

Three lines where one was wanted, each a prefix of the next — that output *is* the diagnosis.

## In production

**What a professional writes instead of the teaching version** is a small function with a name that
says what it is for — `showable(event)` — wrapping the three guards above, used by the CLI, the API
server and the tests alike. The naming matters more than usual here: `is_final_response` is a
framework method whose name has already misled you once, and wrapping it is the cheapest way to stop
it misleading the next person who reads your loop.

**What degrades at scale** is the "exactly one" assumption, and it degrades in a specific direction.
A single-agent system with no tools has one final response. Add tools: usually one, occasionally two.
Add sub-agents: one per agent, reliably. Every system evolves along that path, and code written at
the first stage keeps compiling at the third. Nobody rewrites it, because nothing broke. It just
stops showing everything.

**The failure that only shows with real traffic** is streaming plus tools together. In SSE mode the
chunks answer `False`, the aggregated text answers `True`, and the tool call answers `False`, so a
naive display loop that filters on finality shows the answer twice — once as chunks and once
aggregated — and shows nothing at all while the tool runs, which reads as a freeze.
[2.3](../02-the-stream/2.3-the-board-and-the-printed-sheet.md) is that failure in full.

**The review comment a senior engineer leaves:** *"`is_final_response()` isn't 'the last event' —
there can be one per agent, and an empty state-delta event passes it too. This `break` is going to
abandon the generator and drop the state commit. Take the guard out into `showable()`, drop the
break, and let the loop end."*

**The interview question:** *"in an agent framework, how do you know which output to show the user?"*
The answer that shows you have shipped one: "You don't take the last event — you filter for events
that are complete and have displayable content. The framework's helper answers 'is this complete',
which is not the same as 'is this the end', and there can be several per run: one per agent in a
multi-agent setup, and one before and one after a tool call. The two failures I watch for are
breaking out of the loop on the first one, which abandons the generator and drops whatever the
runtime still had to commit, and keeping only the last one, which throws away what the agent said
before it used a tool."
