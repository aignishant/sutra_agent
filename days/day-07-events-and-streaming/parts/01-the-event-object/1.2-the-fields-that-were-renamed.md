# 1.2 — The fields that were renamed

## One-line answer

ADK 2.0 renamed and restructured the event fields, so **every event-handling snippet you find on the
internet is probably 1.x and will fail on names that no longer exist** — this is trap #2 from the
plan's §5.1, and the only defence is to print the field list from the package you have installed.

---

## The story

A friend of yours needs a new copy of a document, so you go with them to the office. You have done
this before. You know the form.

You fill it in at the counter from memory, the way you did the last time: name in the first box,
father's name below it, address, the reason for the request, sign at the bottom. You hand it over
feeling quite pleased with yourself.

The clerk looks at it for about two seconds and pushes it back. "Purana form hai. New one is the blue
one."

You look at the blue one. It is the same form. The same information, more or less, in the same order.
But "Reason for request" is now "Purpose", and there is a new box near the top called "Application
type" that has to be ticked, and the signature box has moved from the bottom to the middle. Nothing
you knew is *wrong*. It is just no longer where you put it, and one box you never had to think about
is now compulsory.

The worst part is not the twenty minutes of refilling. The worst part is the two people behind you in
the queue who watched you do it confidently and are about to do exactly the same thing, because they
also learned the form from somebody who learned it before the change.

That queue is the internet, right now, on the subject of ADK events. Version 1.x ran for a year and
produced thousands of blog posts, videos and Stack Overflow answers. Version 2.0 changed the form.
The old answers still rank well, still read fluently, and still do not work.

---

## The idea in plain language

The plan's [§5.1](../../../../docs/00_MASTER_PLAN.md) lists four ways a habit picked up from ADK 1.x
breaks on 2.x. **Trap #2 is the event fields.** Its one-line statement is: *event fields were renamed
and restructured in 2.0; never copy event-handling code from a 1.x tutorial; check the 2.x event
reference the day you touch events.*

That is a rule about where you get your information, so it is worth being precise about what "check"
means, because there are three sources and they are not equally trustworthy.

1. **A tutorial.** Written at some point in the past, against some version, usually unstated. This is
   the least reliable source there is, and it is the one search engines hand you first.
2. **The documentation page.** Written by the people who made the thing, and usually correct — but
   documentation is written once and the code keeps moving, and a page can describe a field your
   installed version renamed last month.
3. **The package on your own disk.** Cannot be out of date with itself. If your program is going to
   run against `google-adk` 2.7.1, then 2.7.1's field list is the truth, and everything else is a
   claim about it.

Principle 8 says *never invent an API* and asks you to name the adk.dev page you checked. This part
adds the step after that: **check the page, then check the package, and when they disagree, the
package wins and the document you are writing says so.** That is not disrespect for the
documentation. It is the same reason Day 2 read a rate limit off a live 429 instead of a table: a
dated observation of the real thing beats an undated description of it.

The practical shape of the defence is one line of Python that no tutorial can be wrong about:

> `print(sorted(Event.model_fields.keys()))`

`model_fields` is a dictionary that Pydantic — the data-validation library ADK's models are built on
— puts on every model class, listing exactly the fields that class declares. It is generated from the
class you have imported, so it cannot describe a different version.

One more thing this part is about, because it is the same mistake wearing different clothes. An event
has **two spellings**: the Python one and the wire one. In Python you write `invocation_id`. When the
event is turned into JSON — to be stored, sent to the dev UI, or written to a log — it comes out as
`invocationId`. Same field, two names, and which one you must type depends entirely on whether you
are holding a Python object or looking at JSON. People who have only ever seen the JSON go looking
for `invocationId` in Python and conclude the field does not exist.

---

## Why Sutra needs it

**Today**, immediately: `sutra/desk/events.py` reads fields off an event, and a field name that does
not exist is an `AttributeError` at the worst possible moment — inside a loop, halfway through a run
you already paid for.

**Day 13** (callbacks) and **Day 14** (plugins) both hand you objects whose fields changed in 2.0 in
exactly the same way. The habit you build today — print the field list, trust the package — is the
one that makes those days short instead of long.

**Day 84** writes events into OpenTelemetry attributes, where the wire spelling matters and the
Python spelling does not. A day spent confused about which is which is a day spent looking at an
empty trace.

And structurally: Principle 14 says that if reality changes, the plan is amended first. You cannot
notice that reality changed if your source of truth is a tutorial, because a tutorial does not change
when the library does. **Checking the package is how Principle 14 gets its input.**

## The mechanism

The whole defence is a script you can run in a second, and it is worth keeping for the rest of the
ninety-seven days:

```python
# lab/fields.py - what the installed package actually declares. No network, no key, no cost.
import google.adk
from google.adk.events import Event, EventActions

print("adk version:", google.adk.__version__)
print()
print("Event fields:")
for name in sorted(Event.model_fields.keys()):
    print("   ", name)
print()
print("EventActions fields:")
for name in sorted(EventActions.model_fields.keys()):
    print("   ", name)
```

**Line by line:**

- `import google.adk` then `google.adk.__version__` — printed **first**, on purpose. Any output you
  paste into a document or a bug report is worthless without the version it came from, and putting it
  at the top means you cannot forget.
- `Event.model_fields` — a dictionary on the **class**, not on an instance, so no event has to be
  built. It exists because ADK's models subclass Pydantic's `BaseModel`; this is a Pydantic feature,
  not an ADK one, which is why the same trick works on `LlmAgent`, `RunConfig` and `Session`.
- `sorted(...)` — alphabetical rather than declaration order, because you are going to scan this list
  looking for a specific name, and a list you can binary-search by eye beats one in the order somebody
  happened to type it.
- `EventActions` imported alongside — because half of what a 1.x snippet reaches for lives on
  `event.actions` rather than on the event, and [1.4](1.4-the-half-that-is-not-text.md) is about
  that half.
- Nothing here touches the network, so it costs no request quota and works on a plane.

Thirty-four fields is a lot, and that is the second finding: **most of an event is not for you.**
`voice_activity`, `input_transcription` and `go_away` belong to the Live API and arrive on Day 76.
`node_info`, `output`, `route` and `end_of_agent` belong to the graph Workflow Runtime and arrive in
Phase 8. `isolation_scope` carries a warning in ADK's own source that says, in capital letters, not
to use it directly.

The seven that matter today are the ones part 1.1 printed: `author`, `invocation_id`, `id`,
`timestamp`, `content`, `partial`, `actions`. The rest is a map of days you have not reached yet.

Now the two spellings. The same event, serialised:

```python
# lab/two_spellings.py - the field names change when the event leaves Python.
import json

from google.adk.events import Event
from google.genai import types

event = Event(
    author="sutra_desk",
    invocation_id="run-1",
    content=types.Content(role="model", parts=[types.Part(text="hello")]),
)

print("in Python :", event.invocation_id)
print("on the wire:")
print(json.dumps(json.loads(event.model_dump_json(exclude_none=True, by_alias=True)), indent=2))
```

**Line by line:**

- `event.invocation_id` — the Python spelling, snake_case, which is the only one that works as an
  attribute.
- `model_dump_json(...)` — Pydantic's serialiser. This is what the dev UI, the session store and any
  log line are all built on, so what it prints is what those things see.
- `exclude_none=True` — drops the twenty-odd fields that are `None` on a plain text event. Without it
  the output is mostly nulls and the shape is hard to see.
- `by_alias=True` — the switch that produces the **wire** spelling. ADK's event model sets
  `alias_generator=alias_generators.to_camel`, which means every field has a camelCase alias, and
  passing `by_alias=True` asks for those instead of the Python names.
- `json.loads(...)` then `json.dumps(..., indent=2)` — a round trip purely to pretty-print. Pydantic
  emits compact JSON; two lines of standard library make it readable, and no dependency was added to
  achieve it.

Which prints:

`invocationId`, `stateDelta`, `artifactDelta`, `nodeInfo`. Same object, different alphabet.

There is one more line worth knowing about, from the same model configuration:

> `model_config = ConfigDict(extra='ignore', ...)`

`extra='ignore'` means **an event silently drops any keyword it does not recognise.** Construct an
`Event(is_final=True)` and you get an event with no `is_final` on it, no error and no warning. That
is generous behaviour when reading old JSON off a disk, and it is a trap when writing new code, which
is [4.2](../04-the-brakes/4.2-the-note-the-machine-refuses.md)'s subject — because `RunConfig` next
door made the opposite choice.

## When it breaks

**💥 The 1.x field that is gone.**

A snippet that looks completely reasonable, from a tutorial written against 1.x:

```text
>>> if event.is_final_response and event.type == "message":
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
  File ".venv\Lib\site-packages\pydantic\main.py", line 991, in __getattr__
    raise AttributeError(f'{type(self).__name__!r} object has no attribute {item!r}')
AttributeError: 'Event' object has no attribute 'type'
```

There is no `type` field on a 2.x event, and there never will be, because the *kind* of an event is
not a label — it is derived from what the content holds. An event is a tool call because it contains
a `function_call` part, not because something wrote "function_call" into a field.
[1.3](1.3-is-final-response-is-not-the-last-one.md) shows how to ask.

**💥 The camelCase attribute.**

```text
AttributeError: 'Event' object has no attribute 'invocationId'
```

This one has a specific origin: you were looking at the dev UI's event JSON, saw `invocationId`, and
typed what you saw. The fix is the two-spellings rule above. The reason it is worth naming rather
than just fixing is that the same confusion comes back on Day 84, where you have to write the
**wire** name into a span attribute and the Python name will be silently wrong.

**💥 The keyword that vanished.**

```python
>>> from google.adk.events import Event
>>> e = Event(author="a", invocation_id="i", is_final=True)
>>> e.is_final
AttributeError: 'Event' object has no attribute 'is_final'
```

No error on the way in, because `extra='ignore'`. The event you built is not the event you thought
you built, and you find out one line later, or — far worse — three days later when an assertion that
was always trivially true stops being checked.

## In production

**What a professional writes instead** is a pinned version and a test. The pin is already yours:
`google-adk==2.7.1` in `pyproject.toml`, with its dated row in `docs/PACKAGES.md`. The test is the
new part — one cheap unit test that asserts the fields your code reads actually exist:

> `assert {"author", "invocation_id", "partial", "actions"} <= set(Event.model_fields)`

That looks like testing the framework, which is usually a smell. It is not, and the reason is worth
being able to say out loud: you are not testing that ADK works, you are **testing your assumption
about ADK**, and pinning that assumption is what turns a future upgrade from a mystery into a failing
test with a name.

**What degrades at scale** is not the fields — it is the number of places that read them. One file
reading `event.author` is a rename away from a five-minute fix. Forty files reading it across three
services is a migration. This is the second argument for the single reader function from
[1.1](1.1-an-event-is-a-line-in-a-ledger.md): it gives a framework rename exactly one place to land.

**The failure that only shows with real traffic** is a version skew between two processes. Your API
server serialises events with one version of ADK; a worker written six months ago deserialises them
with another. `extra='ignore'` means the worker will not complain about a field it does not know — it
will just drop it, and the data will be quietly incomplete. Nothing errors. A dashboard is simply
missing a column that nobody notices for a fortnight.

**The review comment a senior engineer leaves:** *"Where did this field list come from? If it's from a
blog post, replace it with the output of `Event.model_fields` on the version we pin, and put the
version in the comment. And add the assertion test — I want an upgrade to break the build, not the
dashboard."*

**The interview question:** *"how do you keep up when a framework makes a breaking change?"* The
answer that shows judgement rather than enthusiasm: "I keep the version pinned and dated, so 'what
are we running' is never a question. When I touch an area, I read the installed package rather than a
tutorial, because the package can't be out of date with itself and a tutorial has no version on it at
all. And I write one assertion per assumption I'm depending on, so the upgrade fails loudly in CI
instead of quietly in production. The specific case I hit was an event model that renamed its fields
between major versions — the old snippets still rank first in search, still read perfectly, and throw
`AttributeError` on a field name that no longer exists."
