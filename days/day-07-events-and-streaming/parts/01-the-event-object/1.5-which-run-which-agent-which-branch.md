# 1.5 — Which run, which agent, which branch

## One-line answer

Four identifying fields — `id`, `invocation_id`, `author` and `branch` — are what turn a flat list of
events into something you can actually read, and every one of them answers a different question you
will ask at 11pm.

---

## The story

You are in a family group on a messaging app. Forty-one people. Somebody's daughter got into college,
somebody else is asking for a plumber's number, an aunt has forwarded a video, and three of these
conversations are happening in the same scroll at the same time.

You come back after two hours and there are ninety new messages.

Now try to answer one question: **did anyone give the plumber's number?**

You scroll. You find the request. Below it are eleven messages about the college admission and a
photograph of a cake. Somewhere there is a message that just says "9845…" with no other words, and
you have no idea whether that is the plumber, the electrician somebody asked about yesterday, or an
office number a cousin was sharing.

Then somebody uses the reply feature — quoting the plumber question and answering it — and suddenly
that one message is unambiguous. Nothing about the text changed. What changed is that the message now
carries **which conversation it belongs to**, and you can pull the thread out of the noise.

That reply arrow is the entire content of this part. A list of things that happened is close to
useless without markers saying which of the several things going on at once each one belongs to. Text
alone will not tell you. The identifiers will.

---

## The idea in plain language

Four fields on an event answer four different questions.

| Field | The question it answers | Shape |
| --- | --- | --- |
| `id` | Which event is this, exactly? | a unique string, minted automatically |
| `invocation_id` | Which **run** is it part of? | a string shared by every event of one run |
| `author` | Who produced it? | `"user"`, or the agent's `name` |
| `branch` | Which parallel path is it on? | a dotted path like `agent_1.agent_2`, or `None` |

They are not interchangeable, and the two people usually confuse are `id` and `invocation_id`.

- **`id` is per event.** Two events made a microsecond apart have different ids, even if their text is
  identical. It is what you use to say "this exact line, not that one" — deduplicating, referencing,
  telling two retries apart.
- **`invocation_id` is per run.** Ask a question, get an answer: every event in between shares one
  `invocation_id`. Ask a second question and a new one begins. It is the reply arrow. Grouping a
  session's events by it turns a scroll into turns.

**`author`** is the agent's `name` from
[Day 5, part 2.2](../../../day-05-first-adk-agent/parts/02-the-agent-object/2.2-name-and-description.md),
or the literal string `"user"`. Today Sutra has exactly one agent, so every event is either `"user"`
or `"sutra_desk"` and the field looks pointless. From Day 53 there are several, and it is the only
thing that says which of them spoke.

**`branch`** is the one you can safely park. In a **parallel** workflow — two agents working on the
same question at the same time, which arrives in Phase 8 — each path gets its own branch string, and
ADK uses it to stop one agent seeing the other's working. The field is `None` for everything you will
build before Day 57. It is listed here so that when you eventually see a dotted string in an event
you do not think something has gone wrong. 🅿️

There is a fifth field, `node_info`, which carries a path like `wf/A@1/B@1`. That belongs to the
graph Workflow Runtime — trap #1 territory, the composition layer ADK 2.0 introduced — and it is
Phase 8's subject, from Day 53. 🅿️

The practical reason to learn all this today rather than on the day you need it: **`sutra/desk/events.py`
is written today**, and a one-line-per-event formatter that omits the identifiers is a formatter you
will rewrite the first time two things happen at once.

---

## Why Sutra needs it

**Day 22** writes Sutra's structured log. A log line without a run identifier cannot be correlated
with anything, which means the log is a diary rather than a tool. `invocation_id` is the field that
makes `grep` work.

**Day 53 onwards** is multi-agent, and `author` becomes the difference between "the system said
something odd" and "the researcher agent said something odd, and here is its instruction".

**Day 84** maps events into OpenTelemetry spans, where `invocation_id` becomes the trace id — the
thing that lets one request be followed across processes. The mapping works because the identifier is
already there and already means the right thing.

**Phase 9** resumes an interrupted run. To resume a run you must be able to say which events belong
to it, which is `invocation_id`, and where in it you were, which is the order of the events carrying
that id.

## The mechanism

Sutra's one-line event reader, and the first file today that goes into the product package rather
than the lab:

```python
# sutra/desk/events.py - one readable line per event. No model call, no I/O.
from google.adk.events import Event


def text_of(event: Event) -> str | None:
    """The event's text, or None when it carries something that is not text."""
    if not event.content or not event.content.parts:
        return None
    joined = "".join(part.text or "" for part in event.content.parts)
    return joined or None


def kind_of(event: Event) -> str:
    """What sort of event this is, derived from its content - there is no `type` field."""
    if event.get_function_calls():
        return "call"
    if event.get_function_responses():
        return "result"
    if event.partial:
        return "chunk"
    if text_of(event) is not None:
        return "text"
    if event.actions.state_delta:
        return "state"
    return "other"


def describe(event: Event) -> str:
    """One line: who, which run, what kind, and whether it is showable."""
    body = text_of(event) or ""
    if len(body) > 60:
        body = body[:57] + "..."
    return (
        f"{event.invocation_id[:8]:<8} {event.author:<12} {kind_of(event):<7} "
        f"final={str(event.is_final_response()):<5} {body!r}"
    )
```

**Line by line:**

- `text_of` — the guard from [1.1](1.1-an-event-is-a-line-in-a-ledger.md), now with a home. It lives
  in the product package because the CLI, the tests and every later day need the same answer, and two
  copies of this function will disagree within a month.
- `return joined or None` — the extra step 1.1 did not have. An event whose parts are all function
  calls joins to `""`, and returning `None` for it keeps the promise the type makes: `None` means
  "no text here", never "empty text".
- `kind_of` — the answer to [1.2](1.2-the-fields-that-were-renamed.md)'s missing `type` field. The
  kind is **derived**, and the order of these checks is the design decision in the function.
- `if event.get_function_calls()` **first** — because an event can carry text *and* a function call
  together, and when it does, the interesting fact is the call. Put the text check first and every
  tool call with a preamble is mislabelled as ordinary chatter.
- `if event.partial` before the text check — a chunk is text, so the more specific label has to win.
  This is the same rule as the line above it: order your checks from most specific to least.
- `if event.actions.state_delta` last among the real kinds — because the contentless state event from
  [1.4](1.4-the-half-that-is-not-text.md) has nothing else to identify it by. Note `event.actions` is
  never `None`; it defaults to an empty `EventActions`, so no guard is needed.
- `return "other"` — an honest label rather than a crash. Thirty-four fields exist and this function
  knows about five of them; the rest are days you have not reached, and printing `other` says so.
- `event.invocation_id[:8]` — eight characters is enough to tell two runs apart by eye and short
  enough to keep the line readable. You are not using it as a key here, you are using it as a colour.
- `event.author:<12` — left-aligned in a fixed width so that the columns line up down the page. A
  reader scanning fifty lines is looking for the one that is different, and misaligned columns are
  what stop that working.
- `body[:57] + "..."` — truncation, because a long model answer turns one line into forty and
  destroys the shape you were reading for. Sixty characters and a marker.
- `{body!r}` — `repr`, not `str`, so a trailing space or a stray newline is visible as `'hello\n'`
  rather than silently reflowing your output. When you are debugging whitespace, this is the
  difference between seeing it and not.

Wire it into the runner you already have. `sutra/desk/run_once.py` currently prints
`f"[event] {type(event).__name__}"`, which says `Event` every time and is therefore worth exactly
nothing:

```python
# sutra/desk/run_once.py - inside say(), replacing the placeholder trace line
from sutra.desk.events import describe

async for event in runner.run_async(user_id=USER_ID, session_id=session_id, new_message=message):
    if trace:
        print(describe(event))
    if event.is_final_response():
        answer = event.content.parts[0].text
```

**Line by line:**

- `from sutra.desk.events import describe` — a real import inside the package, not a lab script. This
  is the first time today's teaching lands in code that ships.
- `print(describe(event))` replacing `print(f"[event] {type(event).__name__}")` — the old line printed
  the class name, which is `Event` for every event ever produced. It told you an event happened and
  nothing else, which felt like tracing without being tracing.
- The `is_final_response()` block is left **unchanged for now**, on purpose. It still keeps only the
  last final response, which [1.3](1.3-is-final-response-is-not-the-last-one.md) showed is a decision
  rather than a fact. The hub's build brief asks you to make that decision deliberately; changing it
  here would take the decision away from you.

A run through it, with three events made by hand:

```text
run-1    user         text    final=True  'why does ticket 4521 log people out?'
run-1    sutra_desk   call    final=False ''
run-1    sutra_desk   result  final=False ''
run-1    sutra_desk   text    final=True  'Ticket 4521 looks like a session bug. The logout happen...'
```

Four lines, one column of identifiers, and you can read the shape of the turn without knowing
anything about the code that produced it. That is the whole return on the twenty lines above.

## When it breaks

**💥 The empty `invocation_id`.**

Build an event by hand and forget the field, and `describe` produces:

```text
         sutra_desk   text    final=True  'hello'
```

Eight spaces where the run id should be. It is not an error — `invocation_id` defaults to `""` — but
it is the field that makes the whole line useful, and its absence is easy to skim past. ADK's own
source says the field *"should be non-empty before appending to a session"*, and the reason is
exactly this: an event with no run id can never be grouped with anything again.

**💥 Grouping by `id` instead of `invocation_id`.**

```python
by_run = {}
for event in session.events:
    by_run.setdefault(event.id, []).append(event)
```

No error, and the output looks superficially sane: a dictionary of runs, each with one event in it.
Every group has exactly one member, because `id` is unique per event. The bug announces itself only
if you notice that the number of runs equals the number of events, which nobody notices while
debugging something else.

**💥 Assuming `author` is a person.**

`author` is `"user"` for anything the human sent and the **agent's name** for everything else. It is
never a user id, never an email, never `"assistant"`. Code that does `if event.author == "assistant"`
is silently never true, so a filter meant to show the agent's replies shows nothing at all — and an
empty list looks like "nothing happened" rather than "you asked the wrong question".

## In production

**What a professional writes instead of the teaching version** is a `describe` that returns a
dictionary and a separate formatter that turns it into a line. The reason is Day 22: the moment logs
become structured, you want `{"invocation_id": ..., "author": ..., "kind": ...}` as fields, not a
string somebody has to parse back apart. Formatting at the last possible moment is the general rule;
today's version formats early because today there is exactly one consumer and inventing the second
layer now would be an abstraction for something used once.

**What degrades at scale** is truncation, of all things. `body[:57]` is fine on a terminal. Feed the
same function a log aggregator and you have permanently thrown away the content of every event over
sixty characters, which you discover on the day you need to know what the agent actually said. The
production rule is: **truncate at the display, never at the record.** Keep the full text in the
structure and let the terminal formatter cut it.

**The failure that only shows with real traffic** is identifier collision across processes. In one
process, `invocation_id` values are unique. Run four workers behind a queue, all writing to one log,
and you are relying on a random id being unique across all of them — which it is, until somebody
seeds a test harness or copies a fixture, and then two genuinely different runs share an id and the
grep that used to work returns an interleaved transcript that reads like an agent contradicting
itself. The fix is boring and worth doing before you need it: log the worker identity alongside the
run id.

**The review comment a senior engineer leaves:** *"`describe` is fine for the CLI but don't build the
logger on it — return the fields and format at the edge. And the truncation is in the wrong layer:
right now we can never recover the full text of a long answer from the logs, which is the one thing
we'll want during an incident."*

**The interview question:** *"you've got a log of thousands of agent events and a user complaining
about one bad answer. Walk me through finding it."* The answer that shows you have done it: "I'd find
the user's session first, then group by the run identifier — every event from one question shares
one, and that's what turns a flat list into turns. Inside the run I'd read it in order, using the
author to see which agent spoke and the derived kind to see where the tool calls sit. What I'm
looking for is the gap between what the tool returned and what the agent said next, because that's
where most 'wrong answer' complaints actually live. And the reason any of that is possible is that
the identifiers are on the record itself — if the framework had only returned the final string, I'd
be reconstructing this from timestamps and hope."
