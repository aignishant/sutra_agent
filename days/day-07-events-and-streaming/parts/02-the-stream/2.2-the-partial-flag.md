# 2.2 — The `partial` flag

## One-line answer

Streaming is switched on per call with `RunConfig(streaming_mode=StreamingMode.SSE)`, and once it is
on, `event.partial` is the field that tells you whether the event in your hand is a **piece still
arriving** or a **finished thing**.

---

## The story

A cricket match is on and you are not near a television, so you have the score page open on your
phone.

It updates ball by ball. `47.2 — dot ball.` `47.3 — single, 218/6.` Each line appears on its own, a
few seconds after the thing happened. You are not reading a report; you are watching a feed.

At the end of the over there is a different kind of line. `End of over 47 — 9 runs. India 224/6.`
That line is not new information exactly. Every run in it was already on your screen, one ball at a
time. It is a **summary of the six lines above it**, published as its own line because it is the form
you actually want when you look away and come back.

Now imagine you were writing a program to keep a running total from that page, and you did not know
about the difference between the two kinds of line. You would add up all the ball-by-ball lines,
which is right. Then you would hit the over summary and add nine more, and your total would be wrong
by nine runs every over, in a way that looks plausible enough to survive for a while.

Both kinds of line are real, both are correct, and one of them contains the other. Deciding which of
the two you are looking at is the entire job. On an ADK event stream, the field that tells you is
called `partial`, and the next part is about what happens to people who ignore it.

---

## The idea in plain language

By default, ADK does **not** stream. `RunConfig`'s `streaming_mode` starts as `StreamingMode.NONE`,
which the enum's own docstring describes as: *"The runner returns one single content in a turn"* and
*"No partial/intermediate events are produced"*. That is what every run you have done so far did, and
it is why `event.partial` has been `None` in everything you printed.

To turn it on you pass a `RunConfig` to the call:

> `run_config=RunConfig(streaming_mode=StreamingMode.SSE)`

Three terms, defined properly:

- **`RunConfig`** is a settings object for **one call**, not for the runner and not for the agent. You
  build it and hand it to `run_async`. The same runner can serve a streaming call and a non-streaming
  one in the same program, which is exactly what you want when a chat window and a batch job share an
  agent.
- **SSE** stands for **Server-Sent Events**. It is an ordinary HTTP response that the server keeps
  open and dribbles text into, rather than closing when it has one complete body. There is nothing
  exotic about it — no second protocol, no socket library. `StreamingMode.BIDI` is the third value,
  and it belongs to the Live API on Day 76; the enum's docstring says plainly that it *"is not used in
  the standard execution path"* and that `run_live()` is the door for it. 🅿️
- **`partial`** is the field on the event. Three values, and the third is the one people miss:

| `partial` | Meaning |
| --- | --- |
| `None` | This event was never part of a stream. Everything you have seen so far. |
| `True` | A chunk. More of this is still coming. Do not treat it as an answer. |
| `False` | The finished, assembled version. This is the over summary. |

That last row is the whole content of the section. With progressive streaming on — which is the
default — you receive **both**: the chunks as they arrive, `partial=True`, and then one aggregated
event with `partial=False` carrying the complete text again. ADK's own enum docstring names this and
calls it the *"Duplicate text issue"*, listing three ways out of it, which is a fairly clear signal
that it catches people.

There is a second, quieter consequence of `partial=True`, and it matters more than the display
problem: **a partial event changes nothing.** It is not appended to the session, and its actions are
not applied. [2.4](2.4-nothing-is-credited-until-the-receipt.md) is that rule in full, and it is the
reason the duplicate is not simply a bug ADK could delete.

## Why Sutra needs it

**Day 76** is live voice, where `partial` stops being optional. A spoken response is generated in
chunks and played in chunks; there is no batched mode that would even make sense.

**Day 85** puts Sutra behind an API server. Whether that server streams to its clients is a decision,
and the decision is made in exactly this object — which means it is made per request, so one
deployment can serve a streaming chat endpoint and a non-streaming batch endpoint without a second
service.

**Day 68** is guardrails, and this is where [2.1](2.1-the-number-read-out-loud.md)'s tension gets
paid: a guard that inspects the finished answer can run on the `partial=False` event, but by then the
chunks are already on the user's screen. Knowing which event carries the complete text is what makes
that conversation precise instead of hand-waving.

Today, immediately: the build brief asks for `sutra/desk/stream.py`, the first file in Sutra that
passes a `RunConfig` at all.

## The mechanism

Sutra's streaming entry point. It reuses the runner and session plumbing you wrote on
[Day 5, part 4.1](../../../day-05-first-adk-agent/parts/04-the-runner/4.1-the-runner-is-your-run-loop.md)
and adds exactly one new object:

```python
# sutra/desk/stream.py - one question, printed as it arrives (Day 7).
#
#     uv run python -m sutra.desk.stream "why does ticket 4521 log people out?"
#
# Verified against adk.dev/runtime/runconfig/ and the installed google-adk 2.7.1 on 2026-08-26:
#     RunConfig.streaming_mode defaults to StreamingMode.NONE
#     StreamingMode is exported from google.adk.agents.run_config
#     run_async takes run_config as a keyword-only argument

import asyncio
import sys

from google.adk.agents.run_config import RunConfig, StreamingMode
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

from sutra.config import load_env, require_free_tier
from sutra.desk.agent import root_agent
from sutra.desk.events import describe
from sutra.desk.run_once import APP_NAME, USER_ID


async def stream_once(question: str, *, trace: bool = False) -> str:
    """Ask one question with streaming on; print the chunks as they arrive."""
    service = InMemorySessionService()
    session = await service.create_session(app_name=APP_NAME, user_id=USER_ID)
    runner = Runner(agent=root_agent, app_name=APP_NAME, session_service=service)

    message = types.Content(role="user", parts=[types.Part(text=question)])
    config = RunConfig(streaming_mode=StreamingMode.SSE)

    complete = "(no final text)"
    async for event in runner.run_async(
        user_id=USER_ID,
        session_id=session.id,
        new_message=message,
        run_config=config,
    ):
        if trace:
            print(describe(event), file=sys.stderr)
            continue
        if event.partial and event.content and event.content.parts:
            sys.stdout.write("".join(part.text or "" for part in event.content.parts))
            sys.stdout.flush()
        elif event.partial is False and event.content and event.content.parts:
            complete = "".join(part.text or "" for part in event.content.parts)
    print()
    return complete


def main() -> int:
    if len(sys.argv) < 2:
        print('usage: uv run python -m sutra.desk.stream "<question>"')
        return 2
    load_env()
    require_free_tier()
    asyncio.run(stream_once(" ".join(sys.argv[1:]), trace="--trace" in sys.argv))
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

**Line by line:**

- `from google.adk.agents.run_config import RunConfig, StreamingMode` — the import path checked
  against the installed package on the day this was written, not copied from a page. `StreamingMode`
  is re-exported here from a private module (`_streaming_mode`), and importing it from `run_config`
  is what keeps you out of the private name — the same rule
  [Day 6, part 3.1](../../../day-06-instructions-and-personas/parts/03-the-instruction-fields/3.1-where-your-instruction-lands.md)
  applied to the lab's render harness.
- `from sutra.desk.run_once import APP_NAME, USER_ID` — imported rather than redefined. Two files
  disagreeing about `app_name` is a session nobody can find, which Day 8 turns into a whole failure
  lab; importing the constant makes that impossible here.
- `from sutra.desk.events import describe` — today's reader from
  [1.5](../01-the-event-object/1.5-which-run-which-agent-which-branch.md), reused rather than
  reimplemented.
- `config = RunConfig(streaming_mode=StreamingMode.SSE)` — **the only new object in this file.**
  Everything else is Day 5's code. That is worth noticing: switching to streaming is one argument,
  and all the difficulty is in the loop that consumes it.
- `run_config=config` passed to `run_async` — keyword-only, like every other argument on that method.
  Per call, so a second call from the same runner can leave it off and get the old behaviour.
- `print(describe(event), file=sys.stderr)` under `--trace` — the trace goes to **standard error** so
  that the answer on standard output stays pipeable. This is the one thing that makes a streaming CLI
  usable inside a shell pipeline instead of only in a terminal.
- `if event.partial and ...` — the chunk branch. Note it is `if event.partial`, which is true only
  for `True` and false for both `None` and `False`, so a non-streaming event can never reach it.
- `sys.stdout.write(...)` with `flush()` rather than `print` — for the reason
  [2.1](2.1-the-number-read-out-loud.md) demonstrated: `print` adds a newline after every chunk, and
  an unflushed buffer un-streams you.
- `elif event.partial is False` — `is False`, spelled out, and this is the single most important line
  in the file. Writing `elif not event.partial` would also catch `None`, which is every event in a
  non-streaming run and several bookkeeping events in a streaming one. Three-valued fields need
  three-valued tests.
- `complete = ...` on that branch rather than printing it — because it has **already been printed**,
  as chunks. This function chose "display the partials, keep the aggregate", which is option A of the
  three ADK's docstring lists. [2.3](2.3-the-board-and-the-printed-sheet.md) is what happens when you
  choose none of them.
- `print()` after the loop — one newline to close the streamed line, because the chunks never carried
  one.
- `trace="--trace" in sys.argv` — a crude flag check rather than `argparse`. One optional flag does
  not earn a parser, and the plan's simplicity rule says so.

Run it, and the shape of a streaming turn appears:

```bash
uv run python -m sutra.desk.stream "why does ticket 4521 log people out?"
uv run python -m sutra.desk.stream --trace "why does ticket 4521 log people out?"
```

**Line by line:**

- The first form prints the answer character by character and nothing else — what a user would see.
- The second prints one `describe` line per event to standard error instead, which is what you look
  at when you want to count the chunks and find the aggregated event.
- Both cost **one request**. Streaming does not multiply the request count; it multiplies the
  *events*, which are free.

## When it breaks

**💥 The `RunConfig` that was silently ignored.**

You build the config, you feel good, and nothing streams:

```python
runner = Runner(agent=root_agent, app_name=APP_NAME, session_service=service)
runner.run_config = RunConfig(streaming_mode=StreamingMode.SSE)  # does nothing
```

`Runner` has no `run_config` attribute, and Python lets you attach an arbitrary attribute to most
objects without complaint. There is no error. The run is simply not streaming, and you spend twenty
minutes reading the model provider's documentation about a setting that never reached it. **The
config belongs to the call.**

**💥 `not event.partial` instead of `is False`.**

```python
elif not event.partial:
    print(text)
```

Now every ordinary event — every one where `partial` is `None` — takes the aggregate branch too. In a
non-streaming run that is harmless. In a streaming run you get the chunks *and* the aggregate *and*
whatever else came through, and the output is the duplicate from
[2.3](2.3-the-board-and-the-printed-sheet.md) with extra helpings.

**💥 The provider that does not stream.**

Not every model behind every provider streams, and the failure is not always an exception — sometimes
you simply receive one event with `partial=False` and nothing before it. Your code is correct, the
config is correct, and there is one chunk because that is all the provider sent. This becomes real on
Day 9, when the same agent is pointed at four different providers; the check is to count the
`partial=True` events, and if the count is one, the provider batched you.

## In production

**What a professional writes instead of the teaching version** is a consumer that never assumes the
shape of the stream: it handles zero chunks, one chunk, many chunks, and a stream that ends without
ever producing an aggregated event, because a dropped connection produces exactly that. The teaching
version above returns `"(no final text)"` in that case, which is honest; the production version logs
it as an incomplete generation rather than returning it to a user as though it were an answer.

**What degrades at scale** is the writing, not the reading. `sys.stdout.write` per chunk is fine for
one terminal. Per chunk over a websocket to five hundred browsers, it is five hundred syscalls per
token, and the usual fix is to coalesce chunks on a short timer so the network sees a sensible packet
size. Notice this is the same buffering that ruined the demo in
[2.1](2.1-the-number-read-out-loud.md) — deliberately, in small amounts, is the difference.

**The failure that only shows with real traffic** is a proxy that buffers. Your service streams
correctly, your tests pass, and users report that answers appear all at once — because something
between you and them collects the response before forwarding it. It is invisible locally because
there is no proxy locally. The tell is that time-to-first-byte at the browser equals total time at
the server, and the fix is a header on the response rather than a change to any of your code.

**The review comment a senior engineer leaves:** *"`not event.partial` also matches `None`, so this
takes the aggregate branch on every non-streaming event too. Use `is False`. And put the trace on
stderr — right now you can't pipe this into anything."*

**The interview question:** *"how do you consume a streaming response from an agent framework?"* The
answer that shows you have done it: "You get two kinds of event: chunks marked partial, and a final
aggregated event that repeats the whole text. You have to pick one to display — normally the chunks,
for the typewriter effect — and use the other for whatever needs the complete string, like logging or
a guardrail. The bug everybody writes first is testing the flag as a boolean when it's three-valued:
`None` for a non-streaming event, `True` for a chunk, `False` for the assembled one. Testing truthily
gets you the same answer printed twice."
