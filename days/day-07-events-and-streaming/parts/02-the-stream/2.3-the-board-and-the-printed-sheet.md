# 2.3 — The board and the printed sheet

## One-line answer

With streaming on you receive the answer **twice** — once as chunks and once assembled — and since
ADK will not choose for you, every streaming consumer must pick one of three rules and apply it
everywhere.

---

## The story

A teacher is doing a chapter on the board. You are copying it down as it goes, keeping up, more or
less.

At the end of the class she says: "I have made a printed sheet of all this, take one on the way out."

Now you have the same chapter twice. In your notebook, in your handwriting, with the two lines you
missed while sharpening a pencil. And on a clean sheet, complete.

Nobody has done anything wrong here. The board was for following along; the sheet is for keeping. But
you now have to decide something, because there is no version of this where you sensibly use both.
Either you rely on your notes and put the sheet in a folder you never open, or you accept that the
sheet is the real record and stop copying so carefully.

The bad outcome is not choosing. That is the student who copies everything from the board *and* then
copies the sheet into the same notebook, and ends up with the chapter written twice, back to back,
looking exactly like the teacher taught it twice.

That doubled notebook is what a streaming consumer produces when it does not pick a rule. And unlike
the notebook, it goes to a user.

---

## The idea in plain language

[2.2](2.2-the-partial-flag.md) established the two kinds of event. This part is about the fact that
you get **both**, always, and about the fact that ADK considers this normal rather than a bug.

The enum's own docstring for `StreamingMode.SSE` names it under the heading *"Duplicate text issue"*:

> *"With Progressive SSE Streaming enabled (default), you will receive both partial text chunks AND a
> final aggregated text event. To avoid displaying text twice: Option A: Only display partial text
> events, skip final text events. Option B: Only display final events, skip all partial events.
> Option C: Track what's been displayed and skip duplicates."*

That is a framework telling you, in its own source, that it has handed you a decision. So make it
deliberately, and write down which one you took.

**Option A — display the chunks, ignore the assembled event.** The typewriter effect, which is what
users expect from a chat window. The assembled event is still useful, just not for display: it is
where you get the complete string for logging, for a guardrail, or for storing. This is what
`sutra/desk/stream.py` chose in [2.2](2.2-the-partial-flag.md).

**Option B — ignore the chunks, display the assembled event.** No typewriter effect, so you have
given up the reason you turned streaming on for a human-facing surface. It is the right choice
everywhere a human is *not* watching: a batch job, a queue consumer, a test.

**Option C — track what you have shown and skip duplicates.** Sounds clever, is worst. It means
holding the displayed text and comparing it against the aggregate, which is string comparison against
a model's output, and models are perfectly capable of producing an aggregate that differs from the
concatenated chunks by a space. Then your deduplication misses and the user sees it twice anyway,
occasionally, in a way you cannot reproduce.

**Take A for anything a person watches, B for anything they do not, and never C.** That is a rule you
can defend in a review, and the reason to state it as a rule is that this decision gets remade badly
every time somebody adds a new surface.

There is one more wrinkle, and it is the one that actually catches people, because it is not about
text at all. When the model is asking for a **tool**, the arguments stream too. You will receive
partial events carrying an incomplete `function_call` — half-built arguments, progressively filled in
— and ADK's docstring says of them that they *"are typically NOT displayed to end users"*. If your
display loop filters only on "is this partial", you will happily print half a JSON object into a chat
window. From Day 10, when Sutra has tools, that is not hypothetical.

There is also an environment variable, `ADK_ENABLE_PROGRESSIVE_SSE_STREAMING`, which the docstring
says is on by default and which controls exactly this behaviour: on, you get partials plus an
aggregate and original part ordering is preserved; off, you get *"simple text accumulation"* which
*"may lose some information"*. It is worth knowing it exists so that a colleague's machine behaving
differently from yours has a suspect. Do not turn it off to fix a display bug — that is treating a
decision you have not made as a framework problem. 🅿️

---

## Why Sutra needs it

**Day 10** puts a `FunctionTool` on Sutra, at which point the partial-function-call events appear in
every run that uses it. Code written today that filters only on `partial` starts leaking argument
fragments then, and the symptom — a chat window showing `{"q": "log` — reads as a framework bug
rather than as your filter.

**Day 22** is structured logging, and this is where option A's other half pays off: the aggregated
event is where the complete answer comes from. A logger that reassembles the chunks itself is
duplicating work the runtime already did, and will drift from it.

**Day 85** puts Sutra behind an API server that streams to a browser. Whatever rule you pick today
becomes that server's contract with its clients, and changing it later is a breaking change for
everyone who wrote a client against it.

## The mechanism

The diagnosis first, because you cannot pick a rule for a stream whose shape you have not seen. This
one counts rather than prints:

```python
# lab/count_chunks.py - what actually arrives in one streaming turn.
import asyncio
import sys
from collections import Counter

from google.adk.agents.run_config import RunConfig, StreamingMode
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

from sutra.config import load_env, require_free_tier
from sutra.desk.agent import root_agent
from sutra.desk.run_once import APP_NAME, USER_ID


async def main(question: str) -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name=APP_NAME, user_id=USER_ID)
    runner = Runner(agent=root_agent, app_name=APP_NAME, session_service=service)

    tally: Counter[str] = Counter()
    chunk_text = ""
    aggregate_text = ""

    async for event in runner.run_async(
        user_id=USER_ID,
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text=question)]),
        run_config=RunConfig(streaming_mode=StreamingMode.SSE),
    ):
        body = "".join(p.text or "" for p in (event.content.parts if event.content else []))
        if event.partial is True:
            tally["partial"] += 1
            chunk_text += body
        elif event.partial is False:
            tally["aggregated"] += 1
            aggregate_text += body
        else:
            tally["neither"] += 1

    print("events by kind :", dict(tally))
    print("chunks joined  :", len(chunk_text), "characters")
    print("aggregate      :", len(aggregate_text), "characters")
    print("identical      :", chunk_text == aggregate_text)


load_env()
require_free_tier()
asyncio.run(main(" ".join(sys.argv[1:]) or "Summarise ticket 4521 in two sentences."))
```

**Line by line:**

- `Counter` from the standard library — the plan's *prefer the stdlib* rule. A dictionary with
  `+= 1` that does not need initialising is exactly what `collections` is for, and it is three fewer
  lines than doing it by hand.
- `event.content.parts if event.content else []` — the guard from
  [1.1](../01-the-event-object/1.1-an-event-is-a-line-in-a-ledger.md) inlined, because this script
  wants to count *all* events including the ones with no content, so it cannot skip them.
- Three branches on `partial`, testing `is True`, `is False` and falling through to `else` — the
  three-valued test from [2.2](2.2-the-partial-flag.md), written out fully so the `neither` count is
  visible. Those are the bookkeeping events, and seeing how many there are is half the value of
  running this.
- `chunk_text +=` and `aggregate_text +=` kept separate — so the final comparison is possible. In a
  real consumer you would never accumulate both; here the whole point is to compare them.
- `chunk_text == aggregate_text` — the line that tells you whether option C could ever have worked.
  If this prints `False`, deduplication by comparison is already broken on your very first run.
- `sys.argv[1:] or "..."` — a default question, so the script runs with no arguments. One request
  either way, and the default is deliberately short to keep it cheap.

Now the rule, written down where the code can see it. This is the display filter that survives Day
10, and the comment above it is not decoration — it is the decision:

```python
# sutra/desk/stream.py - the display rule, stated once.
#
# Option A (adk StreamingMode.SSE docstring, checked 2026-08-26): show the chunks, keep the
# aggregate for logging. Chosen because a person is watching this surface. The batch paths in
# Sutra (Day 73's nightly job) use option B and do not stream at all.


def is_displayable_chunk(event) -> bool:
    """True for a text chunk a user should see; False for everything else."""
    if not event.partial or not event.content or not event.content.parts:
        return False
    if event.get_function_calls():
        return False
    return any(part.text for part in event.content.parts)
```

**Line by line:**

- The comment block above the function — the decision and its date, in the file that implements it.
  A reader six months from now asking "why do we not show the aggregate?" gets an answer without a
  git blame.
- `if not event.partial` — here truthiness is *correct*, unlike in
  [2.2](2.2-the-partial-flag.md)'s `elif`, because this function is asking "is this a chunk", and
  both `None` and `False` mean no. The rule is not "never use truthiness on `partial`"; it is "know
  which of the three values you are excluding".
- `if event.get_function_calls(): return False` — **the line this part exists for.** A partial event
  carrying a half-built tool call is still partial, still has content, and must not reach a user's
  screen.
- `any(part.text for part in event.content.parts)` — a partial event can carry parts with no text at
  all, and returning `True` for one produces an empty write, which shows up as a stutter in the
  typewriter effect.
- No `str` return, no formatting — this function answers one question. The caller does the joining,
  which keeps the filter testable with hand-built events and no model.

## When it breaks

**💥 The answer printed twice.**

```text
Ticket 4521 looks like a session bug. The logout happens because the token is not refreshed.Ticket 4521 looks like a session bug. The logout happens because the token is not refreshed.
```

No newline between them, because the chunks never carried one and the aggregate came straight after.
That run-on is the signature: two identical halves, joined mid-line. It is not the model repeating
itself and it is not a retry — it is the board and the printed sheet, in one notebook.

**💥 The half-written tool call in the chat window.**

From Day 10 onward, a display loop that filters only on `partial`:

```text
{"q": "logo
{"q": "logout tok
{"q": "logout token refresh
```

Three lines of JSON fragments where the user expected a sentence. The arguments were streaming, and
the filter let them through. This one is worth recognising on sight, because the instinct is to
suspect the model's output format, and the model is behaving perfectly.

**💥 Option C, missing.**

```python
if text not in shown:
    print(text)
```

Works on every test you write, because your test question produces a short answer and the aggregate
happens to match the concatenation exactly. Then a real answer contains a spacing difference between
the chunk boundary and the assembled string, the comparison fails, and one user in fifty sees the
answer twice. You cannot reproduce it, because reproducing it requires the model to make the same
choice again.

## In production

**What a professional writes instead of the teaching version** is the rule as a named function used
by every surface, exactly as above — and, more importantly, a test that feeds a hand-built stream
through it. You can construct partial events, aggregated events and partial function-call events with
no model at all (part [1.3](../01-the-event-object/1.3-is-final-response-is-not-the-last-one.md)
showed how), which means the duplicate bug is catchable for **zero requests**. Teams that only test
this against a live model test it rarely, and this is a bug that needs testing often.

**What degrades at scale** is not the duplication, it is the discipline. One surface picks option A.
Six months later somebody adds a Slack integration and picks C because it seemed safest, and a
websocket endpoint that picks B because they copied the batch job. Now "does Sutra stream" has three
answers depending on where you ask, and the guardrail that was written against option A's aggregate
event never runs on two of them. The fix is organisational, not technical: **one function, imported,
and a review comment on any new consumer that reimplements it.**

**The failure that only shows with real traffic** is chunk boundaries inside multi-byte characters
and inside markdown. A chunk can end in the middle of a `**bold**` marker or between the two halves
of an emoji, and a renderer that formats each chunk independently will show a stray asterisk or a
replacement character that vanishes on the next chunk. It never happens in English test prompts with
plain text, and it happens immediately in production with real users. The fix is to render the
accumulated string rather than the chunk.

**The review comment a senior engineer leaves:** *"This filter only checks `partial`, so once we add
tools it will print streaming function-call arguments to the user. Add the function-call check, and
pull the whole thing into one predicate — I don't want the Slack path making its own decision about
this."*

**The interview question:** *"you turned on streaming and users report seeing the answer twice. What
happened?"* The answer that shows you have shipped it: "The framework is sending both the chunks and
a final aggregated event carrying the whole text, which is documented behaviour rather than a bug —
it exists because the aggregate is what gets committed and what a guardrail can inspect. So you pick
one for display: chunks for anything a person watches, the aggregate for anything they don't. What
you don't do is deduplicate by comparing strings, because the aggregate isn't guaranteed to be
character-identical to the concatenated chunks, and that gives you a bug that shows up for one user
in fifty and never in your tests."
