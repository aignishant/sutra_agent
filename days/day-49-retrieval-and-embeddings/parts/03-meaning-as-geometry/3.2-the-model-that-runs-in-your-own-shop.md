# 3.2 — The model that runs in your own shop

## One-line answer

`POST http://localhost:11434/api/embed` with a model name and a list of texts returns one vector per
text, at zero quota and zero cost, from a model running on your own machine — twenty-eight lines of
standard-library Python and no new package.

## The story

The shop on the corner has a generator out the back.

It was not cheap. It takes up space, it needs fuel, and once a month somebody has to start it and let
it run for a while to make sure it still will. On a good day it does nothing at all and looks like a
waste of money.

Then the power goes at four in the afternoon on the busiest day of the month, and the shop next door
puts up a hand-written sign and closes, and this shop keeps the lights on and the freezer cold and
serves the queue that was going to the other shop.

The owner did not buy a generator because generators are interesting. He bought it because the supply
was **not his** — somebody else decided when it was available and how much of it he got — and he had
a job that could not wait for somebody else's decision.

## The idea in plain language

There are two places an embedding model can run, and the choice is not about quality.

**A hosted service.** You send text over the network, you get vectors back. Somebody else runs the
hardware. Every call is a request against a rate limit, and under the free tiers this curriculum uses
([Addendum 02](../../../../docs/02_ADDENDUM_ZERO_BUDGET_MODELS.md)) the number of requests you get in
a day is small and is the currency [Day 24](../../../day-24-token-accounting-and-budgets/LESSON.md)
taught you to count.

**Locally.** The model file sits on your disk, a small server process loads it, and you talk to that
process over `localhost`. There is no rate limit because there is nobody to enforce one. It works
with the network unplugged. The text never leaves the machine.

**Ollama** is the local option this curriculum has used since
[Day 9](../../../day-09-four-free-providers/parts/03-local/3.1-cooking-at-home.md), where it was one
of the four free lanes for *generating* text. Today it gets a second job: embedding. It is the same
daemon, the same `ollama pull`, the same `localhost:11434` — only a different endpoint and a much
smaller model.

The reason the plan chose local for *this* job specifically is in the arithmetic, and
[1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md) already set it up. Index time touches
**every document**. Query time touches **one string**. If a vector costs a request, then building the
index for a five-thousand-ticket archive costs five thousand requests, and the free tier this
curriculum is designed against gives twenty a day.
[3.4](3.4-the-embedder-we-park.md) does that sum properly. Local costs zero requests, whatever the
archive size, which is why it is not a compromise here but the correct instrument.

## Why Sutra needs it

Because Sutra is a zero-budget project and this is the day where a careless choice would end that.

Every other day in this curriculum spends model requests one at a time: an agent turn, a tool call, a
judged evaluation. Retrieval is the first mechanism whose cost scales with the size of **your data**
rather than with the number of things you ask. That is a different shape of cost and it needs a
different answer, and the answer is that the embedder does not touch a quota at all.

It matters for a second reason that has nothing to do with money. Indexing means sending **the entire
archive** somewhere. A support ticket archive contains customer names, email addresses, error dumps
and whatever a frustrated person typed at eleven at night. Keeping the embedder on the machine turns
a data-governance conversation into a non-event, structurally, rather than by a promise in a terms
document.

## The mechanism

First, the model. Verified live on **2026-09-05** against
`https://ollama.com/search?q=embed`, which lists `nomic-embed-text` among the embedding models
alongside `embeddinggemma`, `qwen3-embedding`, `mxbai-embed-large`, `all-minilm`,
`snowflake-arctic-embed` and `granite-embedding`; and against
`https://ollama.com/library/nomic-embed-text`, which gives the tags `latest`, `v1.5` and
`137m-v1.5-fp16`, states a **2K context window**, and gives the pull command exactly as below.

```bash
# 1 - is the daemon there at all?
ollama --version

# 2 - pull the embedding model (a few hundred megabytes, once)
ollama pull nomic-embed-text

# 3 - confirm it is on disk, and record the digest for docs/PACKAGES.md
ollama list
```

**Line by line:**

- `ollama --version` first, because everything below fails with a connection error rather than a
  useful message if the daemon is not running. On most installs it runs as a service; if not,
  `ollama serve` starts it.
- `ollama pull nomic-embed-text` with no tag pulls `latest`. Pin the tag explicitly in a real
  deployment — `nomic-embed-text:v1.5` — for the same reason every package in `pyproject.toml`
  carries `==`: a model that changes under you changes every vector you have stored.
- `ollama list` prints the tag **and the digest**, and the digest is the thing that belongs in
  `docs/PACKAGES.md`. A tag can be re-pointed; a digest cannot.
- **The dimension of the vectors is not stated on the model page**, so this document does not claim
  one. You read it off your own first run — the script below prints it — and that is the number that
  goes in the ledger. `TODO(verify: uv run python days/day-49-retrieval-and-embeddings/lab/embed.py
  and record `numbers per vector` plus the `ollama list` digest in docs/PACKAGES.md)`.

Now the client. Twenty-eight lines, standard library only.

```python
# days/day-49-retrieval-and-embeddings/lab/embed.py
EMBED_URL = "http://localhost:11434/api/embed"  # current; see docs.ollama.com
LEGACY_URL = "http://localhost:11434/api/embeddings"  # retired, kept here to fail loudly
MODEL = "nomic-embed-text"  # verified on ollama.com/library/nomic-embed-text, 2026-09-05
TIMEOUT_S = 60.0


def embed(texts: list[str], *, url: str = EMBED_URL, attempts: int = 3) -> list[list[float]]:
    """Turn texts into vectors with the local model. Raises rather than inventing one."""
    payload = json.dumps({"model": MODEL, "input": texts}).encode("utf-8")
    for attempt in range(1, attempts + 1):
        request = urllib.request.Request(
            url, data=payload, headers={"Content-Type": "application/json"}
        )
        try:
            with urllib.request.urlopen(request, timeout=TIMEOUT_S) as response:
                return json.load(response)["embeddings"]
        except urllib.error.HTTPError as error:
            if error.code != 429 or attempt == attempts:
                raise
            wait = float(error.headers.get("retry-after") or 2**attempt)
            print(f"  429 from the embedder, waiting {wait:.0f}s (attempt {attempt})")
            time.sleep(wait)
    raise RuntimeError("unreachable")
```

**Line by line:**

- `EMBED_URL` ends in `/api/embed`, singular. Verified on 2026-09-05 against
  `https://docs.ollama.com/capabilities/embeddings`, which documents the path, the request body
  `{"model": ..., "input": ...}`, and states that *"The `/api/embed` endpoint returns L2-normalized
  (unit-length) vectors."* `https://docs.ollama.com/api/embeddings` returns **HTTP 404**.
- `LEGACY_URL` is kept in the file on purpose. `/api/embeddings` is the older endpoint and it took a
  different field name — `prompt` rather than `input` — so hitting it with today's body fails in two
  ways at once. It is the single most common Ollama embedding bug and *When it breaks* reproduces
  it.
- `MODEL` is a module constant with the verification date beside it, which is Principle 7 in one
  line. Never a string literal at the call site.
- `"input": texts` takes a **list**, and the endpoint embeds the whole batch in one request. That is
  what makes indexing cheap: one call for the archive rather than one per row. Read that beside
  [1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md)'s index-time/query-time split — batching
  is the reason index time is one request and not eight.
- `urllib.request` and not `requests` or `httpx`. Adding a dependency to avoid ten lines is an
  anti-pattern this project names explicitly, and `pyproject.toml` must not move today.
- `timeout=TIMEOUT_S` at sixty seconds. It is a local call, so sixty is generous; the point is that
  **there is a timeout at all**. [Day 44](../../../day-44-client-hardening/LESSON.md) established
  that a call with no deadline is a call that can hang a turn forever, and `localhost` is not an
  exception — a model still loading into memory can take a long time on the first request.
- The `429` branch exists even though a local daemon will never send one. It is here because
  [3.3](3.3-the-scale-does-not-know-what-it-weighs.md) makes this function swappable and
  [3.4](3.4-the-embedder-we-park.md) names the hosted alternative, and Addendum 02 requires **every**
  model call path to handle `429` with `retry-after` and backoff. `error.headers.get("retry-after")`
  reads the server's own instruction; `2**attempt` is the fallback when it does not send one.
- `if error.code != 429 or attempt == attempts: raise` — every other HTTP error is re-raised
  immediately and unchanged. A 404 must not be retried three times before failing; it must fail now,
  loudly, with its own status. That is Principle 10.
- The function **returns vectors or raises**. There is no `except Exception: return []` anywhere,
  because an empty list would flow into `cosine` and produce a score of `0.0`, and a fabricated
  `0.0` is indistinguishable from an honest one.

## When it breaks

**The daemon is not running.** This is the failure this machine actually has, and here is the real
tail of it, reproduced on 2026-09-05:

```text
  File "C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\sutra\days\day-49-retrieval-and-embeddings\lab\embed.py", line 33, in embed
    with urllib.request.urlopen(request, timeout=TIMEOUT_S) as response:
  File "...\Lib\urllib\request.py", line 1347, in do_open
    raise URLError(err)
urllib.error.URLError: <urlopen error [WinError 10061] No connection could be made because the target machine actively refused it>
```

`WinError 10061` — *actively refused* — means nothing is listening on port 11434. On Linux or macOS
the same condition reads `ConnectionRefusedError: [Errno 111] Connection refused`. Note what it is
**not**: it is not a timeout and not a DNS error. Something answered immediately and said no, which
means the address is right and the process is absent. Start the daemon with `ollama serve`.

**The retired endpoint.** Run `uv run python embed.py --legacy` with the daemon up and the body this
code sends no longer matches what that path expects. The reason it is worth reproducing is that the
failure is *not* a clean 404 in every version — an endpoint that still exists but takes `prompt`
instead of `input` will accept the request and return something unhelpful, and you will spend an
evening on it. Check the URL first, always.

**The model is not pulled.** With the daemon running but no `ollama pull`, the endpoint answers with
an HTTP error naming the missing model. The `except urllib.error.HTTPError` branch re-raises it
untouched, because a missing model is a setup problem and retrying three times will not pull it.

**The first request is slow.** The model has to be loaded into memory. On a cold daemon that can take
long enough to look like a hang, which is precisely why `TIMEOUT_S` is sixty and not five. If you set
a tight timeout and only ever test warm, your first request in production will be the one that fails.

## In production

**What a professional writes instead of the teaching version.** They do not put a raw `urlopen` call
in the retrieval path. They put the embedder behind a small interface with three things this version
lacks: a **connection pool**, so a thousand documents do not open a thousand sockets; a **circuit
breaker**, so a dead embedder fails fast instead of making every search wait sixty seconds — the
state machine [Day 44](../../../day-44-client-hardening/LESSON.md) built; and a **batch size limit**,
because `"input": texts` with ten thousand strings will exhaust memory on the server rather than
returning an error you can read.

They also decide **what happens when the embedder is down**, and write it down. There are only three
answers and each is defensible: fail the search loudly, fall back to the sparse index from
[section 1](../01-text-as-numbers/1.5-the-work-you-do-once.md), or serve from cache. What is not
defensible is not choosing, because the default is a sixty-second hang inside a tool call.

In a hosted deployment the local model becomes a **sidecar** — the same daemon, in a container beside
the application, with the model baked into the image so that startup does not download half a
gigabyte. The `localhost` in the URL becomes a service name and nothing else in the code changes.

**What degrades at scale or under concurrency.** A single Ollama process embedding one batch at a
time is a queue, and under real traffic the queue is the latency. Embedding throughput is bounded by
the machine, so the honest capacity planning question is *how many documents per second do we need to
index*, and the answer decides whether one sidecar is enough. The second thing that degrades is
**memory on re-index**: holding the whole archive's vectors in Python while building the file is fine
at eight rows and is 117 MB at twenty thousand dense vectors
([6.1](../06-in-production/6.1-the-store-we-did-not-build.md) measures it).

**The review comment a senior engineer leaves:** *"The model string is pinned but the tag is `latest`,
so the next `ollama pull` on a rebuilt image can silently change every vector in the index while the
index file still claims to be valid. Pin the tag, put the digest and the dimension in the index file,
and make the search path refuse to run when they do not match."*

**The interview question:** *"How did you choose between a hosted embedding API and a local model?"*
An honest answer: *"By what the workload does to the constraint rather than by quality. Indexing
embeds every document and then re-embeds as the corpus grows, so the cost scales with the size of my
data, not with how many questions people ask. My hosted lane is a free tier with about twenty
requests a day, so a five-thousand-row archive is fifty batched requests — two and a half days of the
entire budget for one rebuild, before anybody searches anything. Local is zero requests at any size,
it works offline, and it means the ticket archive never leaves the machine, which turns a data
governance conversation into a non-issue. The trade is a quality ceiling and an extra process to
operate, and because the vectoriser sits behind one function, swapping to a hosted model later is a
one-file change."*
