# 3.4 — 🅿️ The embedder we park

## One-line answer

The Gemini embedding API exists, works, and is probably better than the local model — and indexing a
five-thousand-row archive through it costs **fifty batched requests** against a free tier of about
twenty a day, so Sutra names it, prices it, and spends **zero** requests on it today.

## The story

Your plan includes a hundred free messages a month.

For eleven months that is more than enough. You send perhaps forty, you never think about it, and the
hundred might as well be a thousand.

Then there is a wedding, and somebody hands you the guest list and asks you to send everyone the
directions to the hall. Four hundred and thirty people.

Nothing about the plan changed. Nothing about your phone changed. What changed is that the job in
front of you is not *messages you send during a month* — it is *messages proportional to the size of
a list somebody handed you*, and a list has no reason to be smaller than your allowance.

You do not send four hundred and thirty messages and find out at number one hundred and one. You
count first.

## The idea in plain language

Retrieval has two costs and they behave completely differently. This is
[1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md)'s index-time/query-time split, now with
prices on it.

**Query cost is per question.** One search embeds one string: one request. That scales with how busy
the desk is, which is a number you understand and control.

**Index cost is per document.** Building the index embeds every row, and rebuilding it embeds every
row again. That scales with **how much data you have**, which is a number that only ever goes up and
which nobody on the team decided.

Every other model call in this curriculum has been of the first kind. This is the first mechanism
whose cost is set by the size of the archive, and a free tier of about twenty requests per day —
read off a live 429 on [Day 2](../../../day-02-llm-mechanics/LESSON.md) and recorded in
`docs/PACKAGES.md` — is a ceiling that data walks straight through.

Being parked (🅿️) in this curriculum means: understood, priced, defensible in an interview,
deliberately not built. It does not mean ignored. The Gemini embedding models are real, current, and
the right answer for a great many systems.

## Why Sutra needs it

Because "we used the local one" is not an engineering answer, and an interviewer will not accept it.
The answer is a number, and this part produces the number.

It also matters because the seam from [3.3](3.3-the-scale-does-not-know-what-it-weighs.md) makes the
hosted lane a genuinely available option — one builder function away. A decision you *could* reverse
in one line deserves to be written down properly, with the condition that would reverse it, rather
than left as a habit.

## The mechanism

First, what is actually on offer. Verified live on **2026-09-05** against
`https://ai.google.dev/gemini-api/docs/embeddings`:

| Model | What the page says |
| --- | --- |
| `gemini-embedding-2` | the latest, multimodal — text, images, video, audio, PDFs — 8,192 token limit |
| `gemini-embedding-001` | text only, still available, 2,048 token limit |

The call shape on the same page is `client.models.embed_content(model="gemini-embedding-2",
contents="What is the meaning of life?")` — the same `google-genai` client this project already pins
at `2.19.0`, so **no package would need to be added**. The obstacle is not the SDK.

The page does not publish free-tier limits for embeddings; it links to a separate rate-limits page,
and the per-project numbers live in the console rather than in the documentation.

Now the arithmetic:

```python
# days/day-49-retrieval-and-embeddings/lab/priced.py
FREE_GENERATE_RPD = 20
ARCHIVE_SIZES = (8, 500, 5_000, 50_000)
BATCH = 100  # how many texts one embed request may carry, if the endpoint batches
REINDEXES_PER_MONTH = 4  # the archive grows; the index is rebuilt


def requests_for(rows: int, batch: int) -> int:
    return -(-rows // batch)  # ceiling division, no import needed
```

**Line by line:**

- `FREE_GENERATE_RPD = 20` is the measured number, with its provenance in the comment beside it. It
  is the *generate* budget, and using it for embeddings is an assumption stated openly rather than a
  fact — which is exactly what the `TODO(verify: ...)` above exists to replace.
- `BATCH = 100` is the optimistic assumption, and it is optimistic on purpose. Batching is the
  strongest argument the hosted lane has, so the comparison gives it to them for free. If the real
  limit is smaller the case gets worse, never better.
- `REINDEXES_PER_MONTH = 4` is the line that turns a one-off cost into a running one. An index is not
  built once ([1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md)); it is rebuilt whenever the
  tokenizer changes, the model changes, the chunking changes — which is
  [Day 50](../../../day-50-chunking-and-top-k/LESSON.md)'s entire subject — or the weights drift far
  enough to matter.
- `-(-rows // batch)` is ceiling division written without importing `math`. Floor division rounds
  down, so negating both sides rounds up. It matters here because 5,001 rows is fifty-one requests
  and not fifty.

Run it:

```bash
cd days/day-49-retrieval-and-embeddings/lab
uv run python priced.py
```

**Line by line:**

- Pure arithmetic over four archive sizes. Nothing is sent anywhere.
- **Zero model calls**, which is the point being made as well as the way it is made.

Measured on 2026-09-05:

```text
free-tier budget this day is designed against: 20 per day

 archive rows   embed requests   batched by 100   days of budget
            8                8                1              0.1
          500              500                5              0.2
        5,000            5,000               50              2.5
       50,000           50,000              500             25.0

and the index is not built once.
    5,000 rows, rebuilt 4 times a month
    = 200 embed requests a month
    = 0.3 days of the free budget, every day

query side, for comparison:
    one search = one embed request for the query text
    20 searches a day and the desk is out of quota

local lane, same numbers:
         8 rows -> 0 provider requests
       500 rows -> 0 provider requests
     5,000 rows -> 0 provider requests
    50,000 rows -> 0 provider requests
```

Three rows decide this.

**A 5,000-row archive is 2.5 days of the entire daily budget for a single rebuild**, batched a
hundred at a time. Not 2.5 days of the embedding budget — 2.5 days of *everything*, because it is the
same key and the same project as the desk's generation lane. During those two and a half days the
desk cannot answer anybody, because it has no requests left to think with.

**Twenty searches and the desk is done.** Look at the query line. Even with a pre-built index, every
question embeds its query, so twenty questions in a day exhausts the free tier. A support desk that
can answer twenty questions a day is not a support desk.

**Zero, at every size.** The local column does not have a slope. That is the property being bought,
and it is worth more here than any quality difference, because the alternative is not "slightly worse
retrieval" — it is "no retrieval after the twentieth question".

**Requests spent by this part: 0.** Nothing above required a call, because request arithmetic is
arithmetic. That is the same discipline
[Day 24](../../../day-24-token-accounting-and-budgets/parts/03-counting-before-spending/3.2-refusing-before-the-call.md)
established: count before you spend, and the count is free.

## When it breaks

The parked option breaks in three ways, and every one of them has been the subject of a real incident
somewhere.

**The quota arrives as a 429 in the middle of an index build.** Not at the start, where you would see
it — at row 3,100 of 5,000, forty minutes in. What you have then is a **half-built index**: three
thousand rows embedded with the hosted model and nineteen hundred missing, in a file that parses
perfectly. Searches will run, they will return only the rows that made it, and nothing anywhere says
so. The real error text from this project's own free tier, recorded on Day 2, is an HTTP `429` with a
`retry-after` header, and the client in [3.2](3.2-the-model-that-runs-in-your-own-shop.md) handles it
— but *handling* a 429 during a five-thousand-row build means sleeping through it, and the build now
takes as long as the quota window.

**The roster moves.** Model names in this ecosystem are not stable; this curriculum's own Addendum 02
exists because a free roster changed in December 2025 and broke pinned strings. A hosted embedder
whose model is retired leaves you with an index full of vectors from a model you can no longer call,
which means the *query* cannot be embedded compatibly, which means the index is dead. The local model
file on your disk does not get retired.

**The data leaves the building.** Indexing means transmitting the entire ticket archive to a third
party — every customer name, every email address, every angry paragraph. That is a decision somebody
senior must make knowingly, and the fact that it happens inside a loop called `build_index` is how it
usually gets made unknowingly.

## In production

**What a professional writes instead of the teaching version.** With a paid account, most teams use
a hosted embedder and are right to: the quality is good, there is nothing to operate, and at
commercial rates embedding is one of the cheapest things in the stack. The decision flips on budget,
not on architecture, which is precisely why the seam in
[3.3](3.3-the-scale-does-not-know-what-it-weighs.md) matters more than the choice.

What a professional adds regardless of lane is a **cache keyed by the hash of the text**. Documents
do not change most of the time, so a rebuild should re-embed only what actually changed. On the
hosted lane that turns a 50-request rebuild into a 2-request one; on the local lane it turns forty
minutes of CPU into ten seconds. It is the single highest-value line of code in an indexing pipeline
and it is almost always missing from the first version.

They also **separate the keys**. Running embeddings and generation through one project's quota means
an index rebuild silently starves the user-facing path, which is the failure the table above
describes. Two keys, two budgets, and an alert on each.

**What degrades at scale.** The hosted lane degrades at the moment the archive outgrows the window in
which you can rebuild it. That is a cliff rather than a slope: everything is fine until a rebuild
takes longer than the interval between rebuilds, and then you never have a current index again. The
number to watch is not cost, it is **rebuild duration against rebuild frequency**, and it is the same
shape as any queue that is fed faster than it drains.

**The review comment a senior engineer leaves:** *"This uses the same API key as the agent. One
re-index and the desk stops answering customers for two days, and the first anyone will know is a
429 on a user request. Separate the key, put a cache in front of the embedder so we only pay for
changed rows, and make the build refuse to start unless the remaining quota covers the whole run."*

**The interview question:** *"How do you decide between a local embedding model and a hosted API?"*
An honest answer: *"By which side of the workload the cost sits on. Query cost scales with traffic
and you control it; index cost scales with the size of your corpus and you do not. I costed my case
out: a five-thousand-row archive batched a hundred at a time is fifty requests, against a free tier of
about twenty a day — two and a half days of the whole budget for one rebuild, and the same key serves
the agent, so the product stops working while it runs. Even with an index already built, every search
embeds its query, so twenty questions a day exhausts it. Local was zero requests at any size, works
offline, and keeps the ticket archive on the machine. With a paid account I would use the hosted
model — the quality is better and there is nothing to operate — and the thing I would do in either
case is cache embeddings by content hash, because most documents do not change between rebuilds."*
