# 3.3 — The scale does not know what it weighs

## One-line answer

Put the vectoriser behind one function that takes a list of texts and returns a list of vectors, and
the ranking, the cap and the memory service never learn which lane produced the numbers — which is
why swapping tf-idf for an embedding model is one line and not a rewrite.

## The story

The scale on the counter has a flat pan, a display, and a button that sets it back to zero.

In the morning it weighs rice. At noon somebody weighs a box of screws on it, and in the afternoon a
child stands on it to settle an argument. It weighs all three the same way and it is right every
time, and it has no opinion whatsoever about what is on the pan.

That is not an accident of design; it is the design. The scale was built to answer exactly one
question — *how heavy is the thing on the pan* — and it was built to answer that question without
knowing anything else about the thing.

Which is why nobody has to buy a new scale when the shop starts selling something new.

## The idea in plain language

Everything in this day after the vectors is one pipeline: score, sort, cut, hand to the agent. None
of those steps has any business knowing whether the numbers came from counting words or from a model.

So the code draws a line in exactly one place. On one side is a function with this shape:

```
vectorise(texts: list[str]) -> list[dict[str, float]]
```

Texts in, vectors out. On the other side is everything else — `cosine`, `rank`, the cap, the ADK
memory service in [section 4](../04-the-adk-socket/4.1-two-methods-and-a-list.md) — and it only ever
sees vectors.

Two lanes fill that shape today.

**The tf-idf lane** builds the weights from the archive and returns a sparse dictionary per text,
keyed by word. Offline, instant, and it fails the meaning test
([2.1](../02-the-meaning-test/2.1-the-score-that-came-back-zero.md)).

**The embedding lane** posts the texts to the local model
([3.2](3.2-the-model-that-runs-in-your-own-shop.md)) and returns a dense list of numbers per text. It
needs a daemon, and it is the only thing in this day that can score two texts with no shared words
above zero.

The trick that makes both fit through one hole is small and worth naming: the embedding lane turns
its list of numbers into a dictionary keyed by **position** — `{"0": 0.13, "1": -0.02, ...}`. That is
the same vector written differently, and it means `cosine` works on it unchanged. In a real system
you would keep dense vectors as lists and write a second `cosine` for them; here, one scoring
function over both lanes is worth more than the microseconds, because it is what proves the point.

This is not a design flourish. It is the same move
[Day 47](../../../day-47-persistent-sessions/LESSON.md) made for storage — swap
`InMemorySessionService` for `DatabaseSessionService` behind `BaseSessionService` and the agent never
notices — and the same move
[Day 46](../../../day-46-sessions-vs-memory/parts/02-the-interface/2.2-the-silence-that-lets-you-swap.md)
identified as the *valuable* part of `BaseMemoryService`: the interface promises nothing about
matching quality, and that silence is what lets you change the brain.

## Why Sutra needs it

Because this machine has no Ollama on it, and the day still has to work.

That is not a limitation being apologised for; it is the strongest possible argument for the seam. A
project where the vectoriser is a boundary can run every part of the pipeline — index, score, rank,
cap, memory service, the gate — with the lane that needs nothing, and swap in the lane that needs a
daemon when the daemon is there. A project where the embedding call is buried inside `search` cannot
run at all without it, cannot be tested without it, and cannot fall back when it is down.

And it is what [Day 50](../../../day-50-chunking-and-top-k/LESSON.md) needs. Day 50 changes what a
*row* is (chunking) and how many rows come back (top-k). Neither of those is a change to the
vectoriser, and neither should require touching it. The seams have to be in the right places before
the next day arrives.

## The mechanism

Two builders with one shape.

```python
# days/day-49-retrieval-and-embeddings/lab/lanes.py
Vectorise = Callable[[list[str]], list[dict[str, float]]]


def tfidf_lane() -> Vectorise:
    """Build a vectoriser that weights term counts by rarity across this archive."""
    weights = idf([text for _, text in ARCHIVE])

    def vectorise(texts: list[str]) -> list[dict[str, float]]:
        return [tfidf(text, weights) for text in texts]

    return vectorise


def embedding_lane() -> Vectorise:
    """Build a vectoriser that asks the local model where each text belongs."""
    from embed import embed  # imported here so the tf-idf arm needs no network at all

    def vectorise(texts: list[str]) -> list[dict[str, float]]:
        return [
            {str(position): value for position, value in enumerate(vector)}
            for vector in embed(texts)
        ]

    return vectorise
```

**Line by line:**

- `Vectorise = Callable[[list[str]], list[dict[str, float]]]` names the shape once so that both
  builders and every consumer agree on it. It is a type alias, not a class: there is no base class to
  inherit and no registry to register with, because the contract is one function signature.
- The functions are **builders**, returning a vectoriser rather than being one. That is what lets
  `tfidf_lane` compute the archive's weights **once** and close over them
  ([1.4](../01-text-as-numbers/1.4-the-word-that-tells-you-nothing.md)'s rule), while
  `embedding_lane` carries no state at all. Two lanes with completely different setup costs, one
  interface.
- Both take **a list of texts and return a list of vectors**, never one at a time. That is the shape
  the batching in [3.2](3.2-the-model-that-runs-in-your-own-shop.md) needs: the embedding lane makes
  **one** HTTP request for the whole archive. A per-text signature would have forced one request per
  row and quietly made indexing eight times more expensive.
- `from embed import embed` sits **inside** `embedding_lane`, not at the top of the file. That is
  deliberate and it is the line that lets this machine run the tf-idf arm: nothing to do with network
  code is even imported unless the embedding lane is asked for.
- `{str(position): value for position, value in enumerate(vector)}` turns `[0.13, -0.02, ...]` into
  `{"0": 0.13, "1": -0.02, ...}`. The keys are strings because the index is written as JSON and JSON
  object keys are strings anyway. This is the adapter that lets one `cosine` serve both lanes.

And the consumer, which is the same eight lines whichever lane it was handed:

```python
# days/day-49-retrieval-and-embeddings/lab/lanes.py
    vectorise = embedding_lane() if embeddings else tfidf_lane()

    vectors = vectorise([text for _, text in ARCHIVE] + [INCOMING])
    index = list(zip([ref for ref, _ in ARCHIVE], vectors[:-1]))
    results = rank(vectors[-1], index)
```

**Line by line:**

- The lane is chosen on **one line**, at the top, and nothing below it branches. That is the test of
  whether a seam is real: if the consumer has to ask which lane it got, the abstraction has failed.
- `[text for _, text in ARCHIVE] + [INCOMING]` embeds the archive and the query **in one call**,
  which is only possible because the signature takes a list. The query is appended last so it can be
  pulled off with `vectors[-1]`.
- `rank(vectors[-1], index)` is the function from `_archive.py`, unchanged from
  [1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md). It has no idea what lane produced its
  arguments and it never will.
- In the real `sutra/retrieval.py` the archive is embedded at index time and only the query is
  embedded at query time ([1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md)'s split). This
  script embeds both together so that the two arms are exactly comparable, and it is the one
  simplification in the file.

Run both arms:


**Line by line:**

- The default arm is tf-idf: no daemon, no network, always runs.
- `--embeddings` is the switch, and it changes the one line above and nothing else.
- **Zero provider quota in either arm.** The second arm talks to `localhost`.

`axes per vector: 19` — the incoming ticket used nineteen distinct words, so its sparse vector has

The embedding arm on **this** machine, which has no Ollama, ends like this — real output from
2026-09-05:

```text
  File "...\Lib\urllib\request.py", line 1347, in do_open
    raise URLError(err)
```

That is the correct behaviour, and it is worth being precise about why. The lane **raised**. It did
not return an empty vector, it did not fall back silently to tf-idf, and it did not return a score of
`0.0`. Principle 10: a retrieval system that quietly substitutes a different method when its
preferred one is unavailable is a system whose results cannot be interpreted.

## When it breaks

The seam has two failure modes and they are both about **mixing**.

**Two lanes, one index file.** Build the index with tf-idf, then search it with the embedding lane.
Nothing raises. `cosine` receives a sparse dictionary keyed by words on one side and a dense one
keyed by `"0"`, `"1"`, `"2"` on the other, the key intersection is empty, and every score is exactly
`0.000` for every document. A retrieval system that returns the entire archive tied at zero looks
exactly like an archive with nothing relevant in it.

That is why the index file from [1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md) carries a
`"vectoriser"` field and `search` reads it rather than assuming. The dense version of the same guard
needs more: the model name, the tag and the dimension, because two *different* embedding models both
produce dense vectors of plausible shape and mixing those produces scores that are wrong rather than
zero — which is far harder to notice.

**A fallback nobody asked for.** The tempting repair, when the daemon is down, is to catch the
`URLError` and quietly use tf-idf. Do not do it silently. The two lanes have different score scales
and different failure characteristics; a search that returns `0.270` from one lane and `0.270` from
the other has not returned comparable things. If you fall back, the response must say so — Day 21's
[3.2](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.2-a-substitute-must-say-so.md) is
exactly this rule, and it applies here without modification.

## In production

**What a professional writes instead of the teaching version.** They make the seam a **protocol** (or
an abstract base class) with two methods rather than a bare callable — `embed_documents` and
`embed_query` — because several real embedding models want to be told which of the two they are
doing, and prepend a different instruction internally. That is a genuine asymmetry, not ceremony, and
a codebase with one `vectorise` function has to grow the distinction later at the worst time.

They also **store the lane's identity in the index**, as above, and add a startup assertion. The
cheapest version is a single canary: embed one fixed sentence at startup, compare its vector against
the one stored when the index was built, and refuse to serve if they differ. That catches a model
change, a tag re-point and a wrong endpoint in one check, before any user sees a wrong answer.

**What degrades at scale or under concurrency.** The two lanes degrade differently, which is the
whole reason to keep both reachable. tf-idf degrades in **quality** as vocabulary drifts, and never
in availability — it is arithmetic on data you own. The embedding lane's quality is stable and its
**availability** is not: it is a process that can be down, slow, or mid-restart. Under concurrency
the sparse lane scales with CPU and the dense lane scales with whatever the embedder can serve, and
they queue in completely different places.

**The review comment a senior engineer leaves:** *"The lane is chosen from an environment variable at
import time and never recorded anywhere. When retrieval was bad last Tuesday nobody could tell which
lane had answered. Put the lane, the model and the dimension in the index file and in the log line
for every search, and make the fallback path say in the response that it is a fallback."*

**The interview question:** *"How would you structure a retrieval system so you can change the
embedding model later?"* An honest answer: *"Put the vectoriser behind one function that takes a list
of texts and returns a list of vectors, and let nothing downstream know what it is. In mine the
scoring, ranking, capping and the ADK memory service all sit on the far side of that line, so
switching between a tf-idf lane and a local embedding model is one line at the top of the call. The
part people miss is that it is not enough to be able to swap — the index has to record which lane
built it, because searching a sparse index with a dense query does not error, it returns every
document tied at zero. And a model swap means a full re-index, so the model name, tag and dimension
belong in the index file with an assertion at startup."*
