# 4.1 — Two methods and a list

## One-line answer

`BaseMemoryService` demands exactly two methods and gives you back a response object with **one**
field — a plain list of `MemoryEntry` with no score, no rank and no distance anywhere — so a
retrieval-backed implementation has to carry its own scores in a shape ADK does not provide.

## The story

The office will take the form, and it will only take it on their form.

You have the information. All of it, correct, and you have written it out neatly on a sheet of paper.
The clerk does not want the sheet of paper. She hands you their form, which has eleven boxes on it,
and says fill this in.

What goes *inside* each box is entirely up to you — they do not check your spelling and they do not
care how you phrase the reason. What is not up to you is the boxes. There are eleven, in that order,
with those labels, and there is no twelfth box.

And here is where it costs you something. You have one thing to say that does not fit anywhere:
*this application replaces the one I submitted in March.* There is no "replaces" box. So you write it
into the box marked "reason", because that is the only box with room for a sentence, and you hope
whoever reads it notices.

## The idea in plain language

That is the shape of an interface, and `BaseMemoryService` is a small one.

An **interface** — in Python, an abstract base class — is a list of methods a class must provide,
with nothing said about how. Day 46's
[2.2](../../../day-46-sessions-vs-memory/parts/02-the-interface/2.2-the-silence-that-lets-you-swap.md)
called that silence the valuable part: because `BaseMemoryService` says nothing at all about *how*
searching should work, an implementation is free to keyword-match, to rank by cosine, or to call a
managed service, and the calling code is identical for all three.

Day 46 filled in the boxes with `InMemoryMemoryService`. Today you fill in the same boxes with
something that ranks. Nothing in
[section 1](../01-text-as-numbers/1.5-the-work-you-do-once.md) or
[section 3](../03-meaning-as-geometry/3.3-the-scale-does-not-know-what-it-weighs.md) changes; it
gets a wrapper.

But the form has no box for a score, and that is the thing to understand before writing a line.
`search_memory` returns a `SearchMemoryResponse`, which has exactly one field: `memories`, a list.
Each item is a `MemoryEntry` with five fields, none of which is a number saying how good the match
is. So a retrieval service that has computed a score — the whole point of today — has to write it
into a box meant for something else. That is
[4.3](4.3-the-score-has-to-be-written-down.md), and this part is where you see the form.

## Why Sutra needs it

Because ADK-30 is precisely this: not "build a retriever" — that was
[sections 1 to 3](../01-text-as-numbers/1.1-the-counter-that-takes-a-description.md) — but **put the
retriever behind the interface the desk already uses**, so that the agent, its instruction, and the
`load_memory` tool Day 46 chose all continue to work untouched.

That is Principle 4 arriving at its payoff. You hand-rolled cosine, weighting and an index, and now
you meet `VertexAiRagMemoryService` and its `similarity_top_k` and `vector_distance_threshold`
arguments and you know exactly what both of them do, because you wrote them. Day 46 parked those
managed services in
[6.2](../../../day-46-sessions-vs-memory/parts/06-in-production/6.2-the-two-services-we-park.md) so
that this day could explain their arguments rather than accept them.

## The mechanism

Read the installed package rather than the documentation, then check the documentation against it.
Verified on **2026-09-05** against `.venv/Lib/site-packages/google/adk/memory/base_memory_service.py`
in `google-adk==2.7.1`, and against `https://adk.dev/sessions/memory/`, which is live and describes
`BaseMemoryService` as *"the interface for managing this searchable, long-term knowledge store"*,
`search_memory` as the method that *"lets an agent (typically via a `Tool`) query the knowledge store
and retrieve relevant snippets or context based on a search query"*, and `add_session_to_memory` as
one that *"takes a completed `Session` and adds relevant information to the long-term knowledge
store"*. The path `https://adk.dev/docs/sessions/memory/` returns **HTTP 404** — the live paths carry
no `/docs` segment, as Days 33, 40, 44 and 46 all found.

```python
# days/day-49-retrieval-and-embeddings/lab/surface.py
class Nothing(BaseMemoryService):
    """A subclass that implements neither abstract method."""


def main() -> None:
    abstract = sorted(BaseMemoryService.__abstractmethods__)
    print(f"abstract methods you must write: {abstract}")
    ...
    print("search_memory signature:")
    print(f"    {inspect.signature(BaseMemoryService.search_memory)}\n")

    try:
        Nothing()
    except TypeError as error:
        print(f"TypeError: {error}\n")
```

**Line by line:**

- `BaseMemoryService.__abstractmethods__` is a `frozenset` Python fills in itself from the
  `@abstractmethod` decorators. Reading it is better than reading the source, because it is what the
  runtime will actually enforce, and it cannot drift from the truth the way a comment can.
- `Nothing` is deliberately empty. Instantiating it is how you find out what the interface demands
  without guessing, and the error message names the missing methods for you.
- `inspect.signature(BaseMemoryService.search_memory)` prints the real signature including the `*`,
  which is the detail that catches people: **every argument is keyword-only**.
- The `try/except TypeError` catches the failure and prints it rather than letting it end the script,
  because the message is the finding.

**Line by line:**

- One arm, no flags. It reads the installed class and prints what it finds.
- **Zero model calls.** Nothing here constructs an agent or a runner.

Measured on 2026-09-05, against `google-adk==2.7.1`:

```text
abstract methods you must write: ['add_session_to_memory', 'search_memory']
concrete methods you inherit  : ['add_events_to_memory', 'add_memory']

search_memory signature:
    (self, *, app_name: 'str', user_id: 'str', query: 'str') -> 'SearchMemoryResponse'

TypeError: Can't instantiate abstract class Nothing without an implementation for abstract methods 'add_session_to_memory', 'search_memory'

SearchMemoryResponse fields: ['memories']
MemoryEntry fields         : ['content', 'custom_metadata', 'id', 'author', 'timestamp']
an empty response is        : SearchMemoryResponse(memories=[])
there is no score field, no rank field and no distance field.
```

Take that output apart, because it is the whole contract.

**Two methods, and only two.** `add_session_to_memory(session)` puts a finished conversation in, and
`search_memory(*, app_name, user_id, query)` gets things out. That is the entire required surface.
Everything today's service does — the index, the vectoriser, the cap, the floor — lives behind those
two names.

**`add_events_to_memory` and `add_memory` are inherited, not required.** They are concrete on the
base class and their bodies `raise NotImplementedError` with a message naming what to call instead —
Day 46's
[2.1](../../../day-46-sessions-vs-memory/parts/02-the-interface/2.1-two-promises-and-two-refusals.md)
quotes both messages in full. **A subclass that does not override them inherits a defined refusal,
which is correct behaviour**, not an omission.

**Every argument of `search_memory` is keyword-only.** The `*` in the signature means
`search_memory("sutra_desk", "agent_riya", "invoice")` raises `TypeError`. Match it exactly in your
override or the framework's call will not bind.

**`SearchMemoryResponse` has one field.** Not `memories` plus `scores`. Not a `total`. One list. Day
46's [5.1](../../../day-46-sessions-vs-memory/parts/05-failure-lab/5.1-the-past-that-matched-on-nothing.md)
found that ADK's own implementation appends to that list in iteration order, so the list arrives
unranked — but that is a property of *that* implementation, not of the type. **The list is ordered;
nothing says what the order means.** Which is exactly the freedom today needs: put them in score
order and the same field becomes a ranking.

**`MemoryEntry` has five fields and none is a score.** `content`, `custom_metadata`, `id`, `author`,
`timestamp`. Day 46's
[2.3](../../../day-46-sessions-vs-memory/parts/02-the-interface/2.3-what-comes-back-is-not-a-session.md)
established that it carries no session identity — no ticket number unless the ticket number is in the
text — and re-reading the field list today confirms nothing has been added. There is no box for a
number, and [4.3](4.3-the-score-has-to-be-written-down.md) is about which box you use instead.

## When it breaks

Delete one method from your subclass and Python stops you at construction:

```text
TypeError: Can't instantiate abstract class Nothing without an implementation for abstract methods 'add_session_to_memory', 'search_memory'
```

That is a **good** failure: it happens at the moment you build the object, before any request, and it
names exactly what is missing.

The bad failure is the one that has no error at all: a subclass that implements both methods and gets
`search_memory`'s signature subtly wrong. Write `async def search_memory(self, app_name, user_id,
query)` without the `*` and it will still be a valid subclass, still construct, and still be accepted
by `Runner` — and then the framework's keyword call binds fine anyway, so it works, until somebody
calls it positionally in a test and the two paths disagree about what is allowed. Copy the signature
from `inspect.signature`, exactly.

The third break is forgetting `async`. Both abstract methods are coroutines. A synchronous
`def search_memory` returning a `SearchMemoryResponse` will be awaited by the framework and fail
with:

```text
TypeError: object SearchMemoryResponse can't be used in 'await' expression
```

Read that message carefully when you meet it — it names the *return value*, not the method, which is
why it is confusing the first time.

## In production

**What a professional writes instead of the teaching version.** They keep the adapter thin. The
class that subclasses `BaseMemoryService` should contain almost no logic: it translates ADK's
arguments into a call to a retrieval module and translates the results back into `MemoryEntry`
objects. Every decision worth testing — the vectoriser, the cap, the floor, the index format — lives
in the module, where it can be tested without constructing a `Session` or a `Runner`. An adapter with
the ranking logic inside it can only be tested through the framework, and framework tests are slow
and awkward.

They also write **characterisation tests** for what the framework does rather than what it promises.
Day 46's
[6.1](../../../day-46-sessions-vs-memory/parts/06-in-production/6.1-eight-things-that-must-stay-true.md)
built exactly that: assertions pinning behaviour nobody documented, each with the ADK version it was
observed against. The two facts today's service leans on — that `SearchMemoryResponse.memories`
preserves the order you put things in, and that `MemoryEntry.custom_metadata` survives serialisation
— are both undocumented and both belong in that file with a version comment.

**What degrades at scale or under concurrency.** The interface is `async`, so `search_memory` will be
awaited inside an event loop that is also serving other turns. A synchronous linear scan inside it
**blocks the loop** for its whole duration — 64 ms at twenty thousand sparse rows, 876 ms dense
([6.1](../06-in-production/6.1-the-store-we-did-not-build.md)) — and during that time nothing else
progresses. The correct production shape is either a real store that is genuinely awaited over the
network, or `asyncio.to_thread` around the scan. The teaching version does neither, and at eight rows
it does not matter.

**The review comment a senior engineer leaves:** *"The service is `async` and everything inside it is
blocking CPU work. At our index size that is most of a second on the event loop per search, which
will show up as unrelated turns timing out. Either move the scan off the loop or put the index behind
something that is actually I/O."*

**The interview question:** *"How do you plug your own retrieval into an agent framework?"* An honest
answer: *"You implement the framework's memory interface rather than calling your retriever from the
agent. In ADK that is `BaseMemoryService`, which has exactly two abstract methods — one to file a
finished session and one to search — and returns a response object with a single list of entries. The
interesting part is what is *not* in it: there is no score field, no rank and no distance, so a
ranked retriever has to carry its own scores inside the entry text or in `custom_metadata`. The
payoff is that the agent, the instruction and the `load_memory` tool do not change at all; the
deployment decides which service stands behind them. The trap is that the interface is async and a
linear scan inside it blocks the event loop."*
