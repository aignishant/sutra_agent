# 4.3 — The score has to be written down

## One-line answer

`MemoryEntry` has no score field, so the similarity has to be written into the text — and the reason
the text and not `custom_metadata` is that what reaches the model is
`{'result': LoadMemoryResponse(...)}`, the Python **repr** of a pydantic object, complete with
`id=None` and `timestamp=None`.

## The story

The second-hand shop has a rail of shirts and every shirt has a small cardboard tag on a string.

The tag says the size and the price. That is all it says. There is a box on it for the size and a box
for the price and no box for anything else.

You hold up three shirts and ask the woman which is the best of them. She knows — she sorted the rail
herself this morning, she remembers which ones came from the good bag, and she can tell you in a
second. But if she is not there, you are holding three shirts with three identical-looking tags and
nothing on any of them says *this one is nearly new and that one has a mark under the arm*.

So the shops that care about this write it on the tag. In biro, in the corner, in their own
shorthand. Not because the tag was designed for it, but because a judgement that is not written down
does not survive the walk to the till.

## The idea in plain language

[4.1](4.1-two-methods-and-a-list.md) established the form: `MemoryEntry` has five fields — `content`,
`custom_metadata`, `id`, `author`, `timestamp` — and none of them is a score.

Your service has computed one. It is the single most useful number in the response, it is what makes
`memories[0]` mean something, and it is what any downstream check would look at. It has to go
somewhere, and there are exactly two candidates:

**The text.** Prefix each entry's content with something like `[ticket 4402 | similarity 0.589]`.
The model sees it, a human reading the transcript sees it, and it costs a few tokens per result.

**`custom_metadata`.** A `dict[str, Any]` that exists for precisely this sort of thing. Structured,
parseable by a program, and — the question this part answers — *does the model actually receive it?*

The answer turns out to depend on something nobody documents, which is how ADK serialises a tool's
return value into the function response. So this part does not reason about it. It runs a turn and
reads what the model was sent.

## Why Sutra needs it

Because Day 46's policy has a rule that depends on it. Rule 4 of
[4.2](../../../day-46-sessions-vs-memory/parts/04-the-choice/4.2-sutras-memory-policy.md) says a
miss is *reported, not interpreted* — the desk must say *"nothing matched"* rather than *"there is no
past case"*. Today adds the other half: a **weak** hit must be reported as weak. `0.089` and `0.780`
are both hits and they mean completely different things, and if the number does not reach the reader
then the desk presents them identically.

It also matters for the review comment Day 46 recorded, which asked that the agent be made to **quote
the ticket it is relying on** so a human can catch a mismatch. A ticket id in the text is what makes
that instruction possible to follow.

## The mechanism

The service writes the score twice — once into the text and once into `custom_metadata` — and then
the script goes and looks at what actually arrives.

```python
# days/day-49-retrieval-and-embeddings/lab/entrytext.py
async def replay() -> dict:
    """Run one scripted turn and hand back the function response the model was sent."""
    quiet()
    model = ScriptedModel(turns=[calls("load_memory", query=EASY_QUERY), says("ok")], seen=[])
    agent = Agent(name="desk", model=model, instruction="You are Sutra.", tools=[load_memory])
    ...
    for content in model.seen[1].contents:
        for part in content.parts or []:
            if part.function_response:
                return part.function_response.response
    raise AssertionError("no function response in the second request")
```

**Line by line:**

- `ScriptedModel` **keeps every request it was sent** in `seen`. That is the whole trick: the tool
  result is not something you can print from outside, because it is assembled by the framework and
  handed to the model. The only way to see it is to be the model.
- `model.seen[1]` is the **second** request — the one sent after the tool ran. `seen[0]` is the turn
  where the model decided to call `load_memory`, and it contains no result yet.
- `part.function_response.response` is the payload. Not the event, not the tool's Python return
  value: the thing that will be serialised towards the provider.
- `raise AssertionError` rather than `return {}` if nothing is found. An empty dict would flow on and
  print something plausible, which is the class of quiet failure this whole day is about.

Run it:

```bash

```

**Line by line:**

- One arm. It prints one `MemoryEntry` field by field, then the JSON the response object serialises
  to, then the thing the model was actually handed.
- **Zero model calls.** The one turn is driven by `ScriptedModel`.

Measured on 2026-09-05:

```text
one MemoryEntry, every field:
    content          '[ticket 4467 | similarity 0.270] Dashboard blank after the upgrade because the cached bundle is stale. Fix KB-402.'
    custom_metadata  {'ref': '4467', 'score': 0.2696}
    id               None
    author           'archive'
    timestamp        None

the score is written in two places:
    in the text        : '[ticket 4467 | similarity 0.270] Dashboard b'
    in custom_metadata : {'ref': '4467', 'score': 0.2696}

the response object serialises to JSON cleanly:
{
  "content": {
    "parts": [
      {
        "text": "[ticket 4467 | similarity 0.270] Dashboard blank after the upgrade because the cached bundle is stale. Fix KB-402."
      }
    ],
    "role": "model"
  },
  "custom_metadata": {
    "ref": "4467",
    "score": 0.2696
  },
  "author": "archive"
}
```

So far it looks tidy. `model_dump_json(exclude_none=True)` gives clean JSON, `custom_metadata` is in
there, and it would be reasonable to conclude that structured metadata is the right place for the
score.

Now the part that is not documented anywhere:

```text
but this is what the model is actually sent:
    keys                 : ['result']
    type of ['result']   : LoadMemoryResponse
    first 300 characters :
      memories=[MemoryEntry(content=Content(
  parts=[
    Part(
      text='[ticket 4402 | similarity 0.589] Cannot print an invoice from the portal; the PDF opens empty. Fix KB-201.'
    ),
  ],
  role='model'
), custom_metadata={'ref': '4402', 'score': 0.5888}, id=None, author='archive', timestamp=None

the tool's own note in its source, quoted verbatim:
    NOTE: Currently this tool only uses text part from the memory.

4521's real match is 4188: 'Login loop on the staff portal. Session cook'
```

Four things in that block, and they change how you would write the service.

**The response is one key, `result`, holding a `LoadMemoryResponse` object.** Not a dict, not JSON —
the pydantic model itself, which the provider layer will render by taking `str()` of it.

**That rendering is a Python repr, not JSON.** Look at it: `memories=[MemoryEntry(content=Content(`,
with newlines and indentation, `role='model'`, and at the end `id=None, author='archive',
timestamp=None`. Every entry carries three fields that are always empty in this service, spelled out
in full, in the prompt, for every result.

**`custom_metadata` does arrive.** It is right there — `custom_metadata={'ref': '4402', 'score':
0.5888}`. So the honest answer to "does the model see it?" is yes. But it arrives inside a repr blob,
in Python dict syntax, next to `id=None`, and it is `0.5888` rather than the three-decimal `0.589`
that was carefully formatted for the text.

**The tool's own source warns you.** `LoadMemoryTool`'s docstring in
`.venv/Lib/site-packages/google/adk/tools/load_memory_tool.py` says, verbatim: *"NOTE: Currently this
tool only uses text part from the memory."* That note and the observed behaviour do not agree, and
when a docstring and an observation disagree, **the docstring is telling you what you are allowed to
rely on**. What arrives today is an implementation detail of how a pydantic object stringifies. What
the tool promises is the text.

So the rule is: **write the score into the text, because that is the only channel the tool promises.**
Keep `custom_metadata` as well — it costs nothing, it is where a program should read from, and it is
what a log line or an eval should key on — but never make the agent's correctness depend on it.

## When it breaks

**The repr is expensive and nobody counts it.** Every result carries `id=None`,
`timestamp=None`, `role='model'` and the pydantic class names, spelled out. Three results is three
copies of that furniture, in the prompt, and Day 46's
[4.1](../../../day-46-sessions-vs-memory/parts/04-the-choice/4.1-pricing-both-in-tokens.md) already
established the sting: a tool result is an event, so it is written into the session and **re-sent on
every later turn**. Noise you send once is noise you pay for all afternoon.

**The score in the text can be read as part of the ticket.** `[ticket 4402 | similarity 0.589]` is
plain text to a model, and a model that is quoting the result back to a support agent may include it,
or — worse — may treat `0.589` as a number from the ticket. Brackets and a separator make it look
like metadata; nothing enforces that. The defence is in the instruction, and writing that instruction
is a `TODO(me)` in the hub.

**Formatting a raw float.** Write `text=f"[{score}] ..."` instead of `{score:.3f}` and every result
carries something like `0.5888147159...`. That is fifteen or so extra characters per result, in a
prompt, on every turn, saying nothing. Day 46's
[4.1](../../../day-46-sessions-vs-memory/parts/04-the-choice/4.1-pricing-both-in-tokens.md) found a
six-thousand-character measurement error from exactly this family of mistake — weighing a prompt with
`str()` instead of `model_dump_json()` — and the lesson generalises: **look at the bytes**.

## In production

**What a professional writes instead of the teaching version.** They write a **deliberate rendering
function** rather than letting a framework's repr decide what the model reads. One function that
takes the retrieval results and returns a compact block — reference, score, snippet, nothing else —
and a tool that returns that string. Then the prompt content is a decision with a test on it, rather
than a consequence of which pydantic version is installed.

They also **band the score rather than printing it**. A model handed `0.589` has no idea whether that
is good; a model handed `strong match` or `weak match — verify before using` does. The bands are
chosen from measured data, which is exactly what
[5.1](../05-when-retrieval-lies/5.1-nearest-is-not-near.md) and
[Day 50](../../../day-50-chunking-and-top-k/LESSON.md) are for. Keep the raw number in
`custom_metadata` and in the logs, where a program reads it, and give the model the word.

**What degrades at scale or under concurrency.** The prompt. More results and longer snippets mean a
tool result that is re-sent on every subsequent turn, and the growth is silent because nothing counts
it for you. [Day 24](../../../day-24-token-accounting-and-budgets/LESSON.md)'s ledger is the
instrument; the metric worth having is *characters returned per search*, which
[4.4](4.4-the-cap-that-finally-means-something.md) measures for both services.

**The review comment a senior engineer leaves:** *"We are relying on `custom_metadata` reaching the
model, and the tool's own docstring says it only uses the text part. That is an undocumented
behaviour we would find broken by a minor version bump, silently. Put everything the model needs in
the text, keep the metadata for our own logging, and add a characterisation test with the ADK version
in a comment."*

**The interview question:** *"Your retriever produces a relevance score. How does it reach the
model?"* An honest answer: *"It has to be written into the text, because the framework's memory entry
type has no score field — it has content, metadata, id, author and timestamp, and that is all. I put
it in both the text and `custom_metadata`, then printed the actual function response the model was
sent, and found that ADK hands the tool's pydantic object through and it renders as a Python repr,
so the metadata does arrive but wrapped in `id=None, timestamp=None` noise that is re-sent on every
subsequent turn. The tool's own docstring says it only uses the text part, so relying on the metadata
would be relying on an implementation detail. In production I would render the block myself rather
than letting a repr decide, and I would give the model a band — strong, weak, verify — instead of a
bare float, because a model has no calibration for 0.589."*
