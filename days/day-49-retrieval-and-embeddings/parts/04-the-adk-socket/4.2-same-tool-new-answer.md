# 4.2 — The same tool, a new answer

## One-line answer

Subclass `BaseMemoryService`, rank inside `search_memory`, pass the object to
`Runner(memory_service=...)`, and Day 46's `load_memory` tool — the same agent, the same instruction,
not one line changed — starts returning three scored results instead of eight unranked ones.

## The story

You have had the same helpline number in your phone for six years.

You call it when the connection drops, and somebody answers, and it gets sorted. You have never
thought about who that somebody is.

Last year they moved the whole support operation. Different building, different city, different
people, new system on their screens. You did not hear about it, you were not asked, and you did not
have to do anything. The number is the number.

The only way you would ever find out is by noticing that the answers got better — that the person on
the line now pulls up your last three complaints before you finish explaining, where the old one used
to ask you to repeat the account number twice.

What made that possible is that the thing you hold — the number — was never the thing that does the
work. It was a stable name pointing at whatever is standing behind it that week.

## The idea in plain language

`load_memory` is the number.

Day 46 chose it over `preload_memory` in
[4.2](../../../day-46-sessions-vs-memory/parts/04-the-choice/4.2-sutras-memory-policy.md), knowing it
was the more expensive option, on the grounds that the query and the result both land in the
transcript where you can read them. That choice is unchanged today and it is what makes today's work
observable.

Behind that tool sits whatever object was passed to `Runner(memory_service=...)`. Day 46 passed
`InMemoryMemoryService`, which keyword-matches and returns an unranked list. Today you pass a
subclass of your own, which vectorises, scores, sorts and cuts. **The agent, the instruction, the
tool and the runner call are byte-identical in both cases.**

Three things move, and it is worth being precise about which:

| What | Day 46 | Today |
| --- | --- | --- |
| the tool the agent carries | `load_memory` | `load_memory` — unchanged |
| the argument to `Runner` | `InMemoryMemoryService()` | `RetrievalMemoryService(...)` |
| what comes back | 8 of 8, unranked, insertion order | 3 of 8, sorted by score, scores attached |

That single-line change is what ADK-30 means, and it is the concrete payoff of the interface's
silence about matching quality
([2.2](../../../day-46-sessions-vs-memory/parts/02-the-interface/2.2-the-silence-that-lets-you-swap.md)).

## Why Sutra needs it

Because a retriever that the desk cannot reach is a script, not a feature.

Sections 1 to 3 built the machinery. This part is where it becomes something the agent can actually
use during a conversation, through the tool the agent already has, without the model being told
anything new. And it is where Day 46's promise finally comes true: the phase gate for Phase 7 is
*"Seen anything like this before?" answered at $0*, and answering it means a ranked list arriving
inside a tool result.

## The paper behind it

> **Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks** · `arXiv:2005.11401` · 2020 ·
> `https://arxiv.org/abs/2005.11401`

It put a retriever in front of a generator so that the model answers from documents fetched at
question time rather than from what was frozen into its weights, and named the pattern the industry
now runs on.

Read it after the parts:
[`papers/02-retrieval-augmented-generation.md`](../../papers/02-retrieval-augmented-generation.md).

## The mechanism

The whole subclass, which is short because
[4.1](4.1-two-methods-and-a-list.md) said it should be:

```python
# days/day-49-retrieval-and-embeddings/lab/service.py
class RetrievalMemoryService(BaseMemoryService):
    """A memory service whose search_memory ranks by cosine similarity."""

    def __init__(self, rows: list[tuple[str, str]], *, top_k: int = TOP_K) -> None:
        self._rows = rows
        self._top_k = top_k
        self._weights = idf([text for _, text in rows])
        self._index = [(ref, tfidf(text, self._weights)) for ref, text in rows]

    async def add_session_to_memory(self, session: Session) -> None:
        """Not what this demo is about. Day 48's policy decides what gets filed."""
        return None
```

**Line by line:**

- `rows: list[tuple[str, str]]` — the service is handed `(reference, text)` pairs and does not read
  a file, a database or an environment variable. Everything it needs arrives through the
  constructor, which is what makes it testable without a fixture and what lets
  [Day 50](../../../day-50-chunking-and-top-k/LESSON.md) hand it chunks instead of whole tickets
  without touching the class.
- `top_k: int = TOP_K` is keyword-only with a named-constant default. Day 46's build brief made
  `TOP_K` a module constant *"with a comment saying what it was sized against"*, and the same rule
  holds here: the cap is a decision with a reason, not a literal.
- `self._weights` and `self._index` are built **once, in the constructor**. That is
  [1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md)'s index-time/query-time split expressed as
  object lifetime: the expensive work happens when the service is created, and every later search
  reuses it.
- `add_session_to_memory` returns `None` and files nothing, and the docstring says so plainly rather
  than pretending. Deciding *what* is worth filing is
  [Day 48](../../../day-48-memory-design/LESSON.md)'s `sutra/memory/policy.py`, and quietly filing
  everything here would silently undo that day's work. It is a stub with a reason, which is not the
  same as an omission.

```python
# days/day-49-retrieval-and-embeddings/lab/service.py
    async def search_memory(
        self, *, app_name: str, user_id: str, query: str
    ) -> SearchMemoryResponse:
        del app_name, user_id  # this demo has one bucket; the real service checks them
        scored = rank(tfidf(query, self._weights), self._index)
        bodies = dict(self._rows)
        return SearchMemoryResponse(
            memories=[
                MemoryEntry(
                    content=types.Content(
                        role="model",
                        parts=[
                            types.Part(
                                text=f"[ticket {ref} | similarity {score:.3f}] {bodies[ref]}"
                            )
                        ],
                    ),
                    author="archive",
                    custom_metadata={"ref": ref, "score": round(score, 4)},
                )
                for score, ref in scored[: self._top_k]
            ]
        )
```

**Line by line:**

- The signature is copied exactly from `inspect.signature` in
  [4.1](4.1-two-methods-and-a-list.md), `*` included. Keyword-only, `async`, returning
  `SearchMemoryResponse`.
- `del app_name, user_id` is an honest marker rather than a silent ignore. This demo has one archive
  and one bucket. **The real `sutra/retrieval.py` must not do this** — Day 46's
  [5.3](../../../day-46-sessions-vs-memory/parts/05-failure-lab/5.3-another-customers-memory.md)
  showed one bucket serving two companies returning one company's billing contact on the other's
  ticket, and a retrieval service that ignores `user_id` reproduces that failure with better ranking.
  A `TODO(me)` in the hub's build brief covers it.
- `tfidf(query, self._weights)` weights the query with the **stored** weights, never freshly computed
  ones ([1.4](../01-text-as-numbers/1.4-the-word-that-tells-you-nothing.md)).
- `rank(...)` then `[: self._top_k]` — **sort first, cut second.** Reversing those two lines is
  exactly the failure Day 46's
  [5.1](../../../day-46-sessions-vs-memory/parts/05-failure-lab/5.1-the-past-that-matched-on-nothing.md)
  named: you cannot take the top three of a list that has no top.
- The result list is built in score order, so `memories[0]` is genuinely the best match. That is the
  one-sentence description of what this whole day changed, and it is a property of *this*
  implementation rather than of the type ([4.1](4.1-two-methods-and-a-list.md)).
- `text=f"[ticket {ref} | similarity {score:.3f}] {bodies[ref]}"` writes the reference and the score
  **into the text**, because [4.1](4.1-two-methods-and-a-list.md) established there is no field for
  either. `{score:.3f}` and not the full float: three decimals is all a reader or a model can use, and
  a long float in a prompt is tokens spent on noise.
- `custom_metadata={"ref": ref, "score": round(score, 4)}` puts the same two facts somewhere a
  *program* can read without parsing a string. Which of the two actually reaches the model is
  [4.3](4.3-the-score-has-to-be-written-down.md), and the answer is surprising.
- `author="archive"` labels where the memory came from. It costs nothing and it is the field a log
  line or a filter would key on.

Now the wiring, which is the part with nothing new in it:

```python
# days/day-49-retrieval-and-embeddings/lab/wired.py
    agent = Agent(name="desk", model=model, instruction="You are Sutra.", tools=[load_memory])
    sessions = InMemorySessionService()
    runner = Runner(
        agent=agent, app_name=APP, session_service=sessions, memory_service=service
    )
```

**Line by line:**

- `tools=[load_memory]` — Day 46's choice, imported from `google.adk.tools`, unmodified. The agent
  is not told that retrieval got better, and the instruction is the same four words in both arms.
- `memory_service=service` on the **`Runner`**, not on the `Agent`. Day 46's
  [3.1](../../../day-46-sessions-vs-memory/parts/03-three-wires/3.1-the-service-rides-the-runner.md)
  established that seam and the `ValueError: Memory service is not available.` you get for putting it
  in the wrong place. It is also why this swap is a deployment decision rather than an agent change.
- `service` is the only name in this block that differs between the two arms. That is the finding.
- The model is `ScriptedModel` from `_script.py`, which yields pre-written turns and spends nothing —
  the same helper Day 46 used, so both arms of this comparison cost **zero generations**.

Read those two blocks side by side, because the trap in them is the best thing in this part.

**The two arms returned the same three tickets in the same order.** On this query, exactly three
tickets in the archive contain any of the words `invoice`, `pdf`, `opens` or `empty`, so ADK's
one-shared-word matcher found three, and the ranked service's top three were the same three. The two
services agree completely on a question written in the archive's own words, which is why nobody
notices the difference in testing.

The only visible difference is the `| similarity 0.589` in the first block and its absence in the
second. That is not decoration: the keyword arm has no scores because it computed none, so there is
nothing to sort on and no way for a reader to tell a strong match from a weak one. The order it gave
is insertion order, and it agreed with the right order by luck.

And notice the accident: `4188`, the right answer, is **first** in the keyword arm. Not because it was
matched well — it scores `0.000` — but because it was filed first and the list is insertion order.
Reorder `ARCHIVE` and it moves. An unranked list that happens to be right is not a working retriever;
it is a coin that landed the right way up.

**The socket works. The vectoriser behind it is what decides whether the answer is any good**, and
that is the correct separation, because the vectoriser is the swappable part
([3.3](../03-meaning-as-geometry/3.3-the-scale-does-not-know-what-it-weighs.md)).

## When it breaks

**The service is on the agent instead of the runner.** Day 46 pinned this and it is worth repeating
because it is the first thing anyone does:

```text
ValueError: Memory service is not available.
```

Raised from inside the framework when `load_memory` fires with no service on the invocation. Loud,
immediate, and it names the problem.

**The cut happens before the sort.** No error at all. Swap the two operations in `search_memory` and
the service returns three arbitrary rows with scores attached, which is worse than Day 46's version,
because the scores make the arbitrary rows look measured.

**The archive changes and the service does not.** `self._index` is built in `__init__`. A ticket
filed after the service was constructed is invisible to it, forever, with no error —
[5.2](../05-when-retrieval-lies/5.2-the-index-nobody-rebuilt.md) is that failure in full.

## In production

**What a professional writes instead of the teaching version.** They do not build the index in
`__init__`. A long-lived service reads a shared index that something else maintains — a file it
watches, a table it queries, a vector store it connects to — because index building and index serving
have completely different lifetimes and completely different failure modes. Building at construction
time means the only way to refresh is a restart, and it means startup time grows with the corpus.

They also **log every search**: the query, the number of results, the top score, and the identity of
the index. Day 46's argument for `load_memory` over `preload_memory` was that the query lands in the
transcript; a log line is that argument extended to the half of the system that is not the model. When
somebody says retrieval was bad on Tuesday, those four fields are the entire investigation.

**What degrades at scale or under concurrency.** Two things. `search_memory` is `async` and the scan
inside it is not, so at real index sizes it blocks the event loop
([4.1](4.1-two-methods-and-a-list.md)). And constructing one service per request re-reads and
re-vectorises the whole archive per request — an easy mistake when the service is created inside a
request handler rather than once at startup, and one that turns a 1-millisecond search into a
300-millisecond one at twenty thousand rows.

**The review comment a senior engineer leaves:** *"`search_memory` takes `app_name` and `user_id` and
deletes them. That is the isolation boundary; a customer's ticket archive must not be searchable from
another customer's session. Filter the index by the bucket before you rank, and add the test that
proves a query from user B cannot see user A's rows."*

**The interview question:** *"You swapped the retrieval engine underneath a running agent. What did
the agent have to change?"* An honest answer: *"Nothing. The agent carried the framework's
`load_memory` tool and the instruction was four words in both arms; the only difference was the object
passed to the runner's `memory_service` argument. That is the payoff of implementing the framework's
memory interface rather than calling a retriever from the agent — the agent stays portable and the
deployment decides what store stands behind it. The measurement I would quote is that on an easy
query both services returned the same three tickets in the same order, which is why nobody notices the
difference in testing, and on a hard query the keyword one returned all eight tied on the word 'the'
while the ranked one returned three with scores. The catch is that ranking fixed the ordering and not
the matching — my ranked service still put a caching ticket first for an authentication question,
because the vectoriser behind it was still counting words."*
