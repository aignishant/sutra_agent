# 1.5 — The work you do once

## One-line answer

An **index** is the vectors computed once, ahead of time, and written to a file, so that answering a
question is arithmetic over numbers you already have instead of re-reading every document.

## The story

The night before the exam you do not read the textbook. You read the six pages of notes you made
from it over the last month.

Making those notes was slow. You went chapter by chapter, decided what mattered, wrote it down in
your own shorthand, and the whole thing took far longer than reading the chapter would have. But you
did it once, when you had time.

Now, the night before, you can find anything in seconds. And in the hall the next morning, when a
question asks about something from chapter four, you are not turning pages — you are looking at one
line you wrote yourself.

Two things about those notes are worth noticing, because they are exactly the two things about an
index.

They are **derived**. If you lost them, nothing is gone: the textbook still has everything, and you
could make the notes again. Painful, not fatal.

And they can go **out of date**. If the syllabus changed after you wrote them, your notes are
confidently wrong about a chapter that no longer exists, and there is nothing in the notes
themselves that says so.

## The idea in plain language

An index is the answer to a cost problem.

Scoring a query against a document means vectorising both and taking a cosine. Vectorising a
document — tokenising, counting, weighting — is far more expensive than the cosine itself. If you do
it at query time you pay it for every document on every question, and you pay it again for the same
documents on the next question.

So you split the work in two:

**Index time**, which happens once: read every document, vectorise it, and write the vectors out —
along with the idf weights, because [1.4](1.4-the-word-that-tells-you-nothing.md) showed that a query
cannot be weighted without them.

**Query time**, which happens per question: vectorise only the query, load the stored vectors, take
one cosine per row, sort, and cut.

Three properties of an index follow from that split, and every one of them turns up later in this
day.

**An index is derived data.** Everything in it can be rebuilt from the documents. That is why it does
not belong in version control — it is output, not source — and why losing it is an inconvenience
rather than a loss.

**An index has a version.** It was built by one tokenizer, one weighting scheme and one set of
weights. Searching it with different ones produces numbers that mean nothing, and nothing warns you.

**An index goes stale.** The documents move on and the file does not.
[5.2](../05-when-retrieval-lies/5.2-the-index-nobody-rebuilt.md) is that failure, measured.

The word "index" is unfortunately overloaded, so one clarification. A database index is a data
structure that lets the engine *avoid* looking at most rows — a B-tree, a hash. What you are building
here is not that. It is a **precomputed table that you still read in full on every query**. That
distinction is invisible at eight rows, costs 64 milliseconds at twenty thousand, and is the entire
subject of [6.1](../06-in-production/6.1-the-store-we-did-not-build.md).

## Why Sutra needs it

Because the desk answers a question in the middle of a conversation, while a support agent waits, and
because [Day 24](../../../day-24-token-accounting-and-budgets/LESSON.md) established that everything
Sutra does has a price that must be counted before it is spent.

The split also decides where the *money* goes in [section 3](../03-meaning-as-geometry/3.2-the-model-that-runs-in-your-own-shop.md).
Index time touches every document; query time touches one string. If vectorising costs a request to a
rate-limited service, then index time is where the whole budget disappears, and
[3.4](../03-meaning-as-geometry/3.4-the-embedder-we-park.md) does that arithmetic. Getting the split
clear now is what makes that argument obvious later.

And the file itself is the object [Day 50](../../../day-50-chunking-and-top-k/LESSON.md) picks up:
chunking changes what a *row* is, and the whole point of building `build_index` around a list of
`(ref, text)` rows is that changing what produces those rows does not touch anything else.

## The mechanism

Three functions: build, load, search.

```python
# days/day-49-retrieval-and-embeddings/lab/index.py
INDEX_PATH = Path(__file__).with_name("archive_index.json")


def build_index(rows: list[tuple[str, str]], *, weighted: bool) -> dict:
    """Vectorise every row once and return a JSON-shaped index."""
    weights = idf([text for _, text in rows]) if weighted else {}
    vectors = {ref: (tfidf(text, weights) if weighted else counts(text)) for ref, text in rows}
    return {
        "vectoriser": "tfidf" if weighted else "counts",
        "built_at": "fixed-for-the-transcript",
        "weights": weights,
        "rows": [{"ref": ref, "vector": vectors[ref]} for ref, _ in rows],
    }
```

**Line by line:**

- `rows: list[tuple[str, str]]` — the input is `(reference, text)` pairs and nothing else. The
  function does not know where the text came from, does not read a database, and does not split
  anything. That is deliberate: [Day 50](../../../day-50-chunking-and-top-k/LESSON.md) changes what
  produces these rows, and it must be able to do so without touching this function.
- `*, weighted: bool` is keyword-only. A bare `True` at a call site would be unreadable, and this
  flag decides what every number in the file means.
- The returned dictionary carries **four** things, and only one of them is the vectors.
  `"vectoriser"` records how the numbers were made, so a reader can tell whether the file matches the
  code. `"weights"` travels **with** the vectors because a query scored with different weights is
  scored against nothing. `"built_at"` is where a real build stamps a timestamp — this day fixes the
  string so the transcripts are identical on every machine, and
  [5.2](../05-when-retrieval-lies/5.2-the-index-nobody-rebuilt.md) is where its absence bites.
- `"rows"` is a **list**, not a dictionary keyed by reference. Insertion order is preserved, so a run
  against this index can be compared directly with Day 46's insertion-order behaviour.
- The whole index is built in memory and returned, rather than written line by line. At eight rows
  that is obviously fine; the reason it stays fine is that the caller writes it in **one** operation,
  so a crash leaves the old file intact rather than half of a new one.

```python
# days/day-49-retrieval-and-embeddings/lab/index.py
def search(query: str, index: dict, k: int) -> list[tuple[float, str]]:
    """Vectorise the query the same way the rows were vectorised, then rank."""
    weights = index["weights"]
    query_vector = tfidf(query, weights) if index["vectoriser"] == "tfidf" else counts(query)
    rows = [(row["ref"], row["vector"]) for row in index["rows"]]
    return rank(query_vector, rows)[:k]
```

**Line by line:**

- `weights = index["weights"]` reads the weights **out of the file**, never recomputing them. This is
  the line that makes the query comparable to the documents.
- `if index["vectoriser"] == "tfidf"` asks the file how it was built rather than assuming. If you
  ever change the default and forget to rebuild, this branch keeps the query honest instead of
  silently scoring counts against weighted vectors.
- `rank(...)` is the sort from `_archive.py`: one cosine per row, sorted best first with ties broken
  by ticket id so the transcripts are reproducible.
- `[:k]` is the cap, applied **after** the sort. Day 46's
  [5.1](../../../day-46-sessions-vs-memory/parts/05-failure-lab/5.1-the-past-that-matched-on-nothing.md)
  capped before there was an order and got three arbitrary rows;
  [4.4](../04-the-adk-socket/4.4-the-cap-that-finally-means-something.md) measures what the same cap
  is worth once there is one.
- Note what is **not** here: no threshold. `search` returns `k` rows whatever their scores are, which
  is honest to what the code does and is the failure
  [5.1](../05-when-retrieval-lies/5.1-nearest-is-not-near.md) takes apart.

Run it:

```bash
cd days/day-49-retrieval-and-embeddings/lab
uv run python index.py
uv run python index.py --counts
```

**Line by line:**

- The first arm builds a tf-idf index and searches it.
- `--counts` builds the same index with weighting off, so the two files can be compared — including
  their sizes, which differ for a reason worth spotting.
- **Zero model calls in either arm.** Both write `archive_index.json` in the lab folder.

Measured on 2026-09-05:

```text
query: 'invoice pdf opens empty'
   0.589  4402  Cannot print an invoice from the portal; the PDF opens emp
   0.100  4508  Nightly export finishes but the file is empty. Fix KB-512.
   0.081  4533  Invoice total disagrees with the plan price; rounding in t

```

```text
built 8 rows with the counts vectoriser
wrote archive_index.json: 1.8 KB, built in 0.6 ms

query: 'invoice pdf opens empty'
   0.500  4402  Cannot print an invoice from the portal; the PDF opens emp
   0.151  4508  Nightly export finishes but the file is empty. Fix KB-512.
   0.118  4533  Invoice total disagrees with the plan price; rounding in t
```

**It works.** A question written in the archive's own vocabulary returns the right ticket first, with
a clear gap: `0.589` against `0.100`, which is nearly six times the second-best score. Hold on to
that gap — it is what a *good* retrieval result looks like, and it is the thing
[2.1](../02-the-meaning-test/2.1-the-score-that-came-back-zero.md) will not be able to produce.

Two details in the numbers.

**5.2 KB against 1.8 KB.** The weighted index is nearly three times the size for the same eight
tickets, because `1.0` is short to write and `1.3862943611198906` is not, and because the weights are
stored as well. Precision costs bytes, and at scale it costs a lot of them
([6.1](../06-in-production/6.1-the-store-we-did-not-build.md) measures the file at 20,000 rows).

**The second and third results are the same tickets in both arms, in the same order.** The weighting
changed the *scores* and not the *ranking* here, because this query happens to be made of words that
are rare in this archive already. That is normal, and it is why a change to the scoring must always be
evaluated on a set of queries rather than on the one you happened to try.

## When it breaks

Query the index with a vectoriser it was not built with. It does not raise; it lies.

Build the raw-counts index and then score a query with tf-idf weights taken from elsewhere and every
number is meaningless — the document vectors are counts, the query vector is weighted, and the cosine
between them is a real number computed from two incompatible things. The guard in `search` above is
the `index["vectoriser"]` check, and it exists because this failure produces no error at all.

The other break is the one that gets people at three in the afternoon, and it is a file:

```bash
cd days/day-49-retrieval-and-embeddings/lab
rm -f archive_index.json
uv run python -c "from index import load_index; load_index()"
```

```text
FileNotFoundError: [Errno 2] No such file or directory: 'C:\\Users\\nisha_gnzw\\OneDrive\\Desktop\\Projects\\sutra\\days\\day-49-retrieval-and-embeddings\\lab\\archive_index.json'
```

A missing index is a **loud** failure, and that is the good case. Compare it with
[5.2](../05-when-retrieval-lies/5.2-the-index-nobody-rebuilt.md), where the file exists and is
out of date: no traceback, no warning, and answers from last quarter. Of the two, the crash is the
one you want.

## In production

**What a professional writes instead of the teaching version.** They write the index **atomically**:
to a temporary file in the same directory, then `os.replace` it over the old one. `os.replace` is
atomic on the same filesystem, so a reader either sees the whole old index or the whole new one and
never a half-written file. Writing straight over the live file, as the teaching version does, means a
crash mid-write leaves an index that parses as invalid JSON — or, worse, one that parses fine and is
truncated.

They also **put a version and a fingerprint in the file**: the tokenizer version, the weighting
scheme, the embedding model name and dimension if there is one, the number of source rows, and when
it was built. Then the search path asserts that the fingerprint matches what the running code
expects, and refuses rather than scoring nonsense. That check costs one comparison per search and it
is the difference between a bug that is caught at startup and a bug that is caught by a customer.

**What degrades at scale or under concurrency.** Two things, and they arrive in this order. First,
build time: this day's index takes 1.5 ms at eight rows and 0.30 s at twenty thousand, which is
still nothing, but a rebuild that reads and re-embeds every document is not something you can do on
every write. Real systems index **incrementally** — new row in, one vector out — and accept that the
idf weights drift until the next full rebuild. Second, concurrency: one writer replacing a file while
several workers read it is fine with `os.replace` and corrupt without it, and a system with more than
one writer needs a real store rather than a JSON file.

**The review comment a senior engineer leaves:** *"The index is written with `write_text` straight
over the live path, so a crash during the rebuild takes retrieval down until someone re-runs it by
hand. Write to a temp file and `os.replace`. And add the tokenizer version to the file — we changed
the tokenizer last month and nobody rebuilt, which is why the December scores are not comparable with
the January ones."*

**The interview question:** *"Walk me through what happens between a document being written and it
being findable."* An honest answer: *"Two phases. At index time the document is read, split into
whatever unit you index — a whole ticket in my case, chunks in a bigger system — turned into a vector,
and written to the index along with the weights or the model identity the vectors depend on. At query
time only the query is vectorised, with the same scheme, and scored against the stored vectors. The
gap between the two phases is where every staleness bug lives: the document is written, and it is not
findable until something rebuilds or incrementally updates the index. I would want a visible lag
metric on that gap, because the failure is silent — a search for a ticket filed this morning just
quietly returns older ones."*
