# 6.2 — The seams Day 50 opens

## One-line answer

`sutra/retrieval.py` is written so that tomorrow's changes — chunking, and choosing `TOP_K` and
`SIMILARITY_FLOOR` from evidence — touch **what produces the rows** and **two constants**, and
nothing else; the gate in `lab/gate.py` is what holds those seams open.

## The story

The house is still bare brick, and the electrician is asking where you want the sockets.

You say: one there, two by the window, one behind where the fridge goes. Then he asks about the wall
opposite, where there is nothing at all right now, and you say you might put a desk there one day.

So he runs a wire to that wall and leaves it coiled in a box in the plaster, capped off, doing
nothing. It costs a little more today and it takes twenty seconds of his time.

Two years later there is a desk there. Adding the socket is an hour's work by somebody who cuts a
small square out of the plaster and connects two wires. Without the box in the wall it is a day, a
mess, and a decision about which existing circuit to butcher.

The wire in the wall is not a prediction that you will definitely put a desk there. It is the
observation that **you know roughly where change is likely**, and that leaving room is cheap while the
walls are open and expensive afterwards.

## The idea in plain language

Today built a retriever. Tomorrow changes two things about it, and both changes are already known:

**Chunking.** Today one archive row is one whole ticket. That is a choice, and often the wrong one: a
long document should be split into pieces so that a query matches the paragraph that answers it
rather than being diluted across pages of unrelated text. Splitting is the subject of
[Day 50](../../../day-50-chunking-and-top-k/LESSON.md), and it changes **what produces the rows** —
not how they are vectorised, scored, sorted or returned.

**Choosing `TOP_K` and the floor from evidence.**
[4.4](../04-the-adk-socket/4.4-the-cap-that-finally-means-something.md) used three because three is a
reasonable number. [5.1](../05-when-retrieval-lies/5.1-nearest-is-not-near.md) used `0.20` because
the output looked like that was about right. Both of those are placeholders with a measurement
missing, and Day 50 supplies the measurement, along with `tests/test_retrieval_tuning.py`.

So the design rule for today is one sentence: **`build_index` takes rows and does not make them, and
every number a tuning day would want to move is a named module constant.**

## Why Sutra needs it

Because Day 50 is being written alongside this one and cannot read it. The contract has to be in the
code, and it has to be obvious enough that a change lands in the right place without a conversation.

It is also the last thing this day owes the reader. Sections 1 to 5 built a mechanism and broke it
four times; this part says which of the breaks are *deliberately* left open, where the repair goes,
and how you will know if somebody puts it in the wrong place.

## The mechanism

Here is `sutra/retrieval.py`'s public surface — the module the hub's build brief asks you to write —
with the seam marked on each line.

| Symbol | Shape | Who changes it |
| --- | --- | --- |
| `tokenize`, `counts`, `cosine`, `idf`, `tfidf` | pure functions over text and dicts | nobody; frozen today |
| `embed` | `(list[str]) -> list[list[float]]` | swapped for a different provider, never edited |
| `tfidf_vectoriser`, `embedding_vectoriser` | builders returning a `Vectorise` | a third lane is added beside them |
| `build_index` | `(rows, *, vectorise) -> dict` | **never** — Day 50 changes what produces `rows` |
| `search` | `(query, index, *, k, floor) -> list[Hit]` | **never** — Day 50 changes the two defaults |
| `TOP_K` | `int` | **Day 50 moves this**, with the evidence in the comment |
| `SIMILARITY_FLOOR` | `float` | **Day 50 moves this**, with the evidence in the comment |
| `SutraRetrievalMemoryService` | `BaseMemoryService` subclass | nobody; it is an adapter |
| `build_memory_service` | `() -> BaseMemoryService` | the one place construction happens |

Read the two `never` rows together with the two `Day 50 moves this` rows. That pairing is the whole
design: the functions are stable and the numbers are not, so a tuning day edits constants and a
chunking day edits the thing upstream of `build_index`.

The most important single decision is the one from
[1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md), and it is worth restating as a rule:

```python
# the shape sutra/retrieval.py must keep
def build_index(rows: list[tuple[str, str]], *, vectorise: Vectorise) -> dict:
    """Vectorise pre-cut rows. This function never splits anything."""
```

**Line by line:**

- `rows: list[tuple[str, str]]` — `(reference, text)` pairs, already cut. Today the caller passes one
  row per ticket. Tomorrow it passes one row per chunk, with references like `4188#2`, and
  `build_index` does not notice.
- **The docstring says what the function does not do.** That is not padding; it is the seam, written
  where somebody about to add a `chunk_size` parameter will read it. A comment that prevents a wrong
  change is worth more than one that explains a right one.
- `*, vectorise: Vectorise` is keyword-only and injected, from
  [3.3](../03-meaning-as-geometry/3.3-the-scale-does-not-know-what-it-weighs.md). The lane is the
  caller's decision, so `build_index` never imports `embed` and never needs a network to be tested.

And the gate that holds it. This is the day's eval
and it is red as shipped, because `sutra/retrieval.py` does not exist until you write it.

```python
# days/day-49-retrieval-and-embeddings/lab/gate.py
    # rule 3 - the cap is a named constant, so Day 50 can move one line.
    if not isinstance(getattr(retrieval, "TOP_K", None), int):
        finding("rule 3", "TOP_K is not an int constant on sutra.retrieval")

    # rule 4 - the floor exists, so 'nothing found' is expressible.
    if not isinstance(getattr(retrieval, "SIMILARITY_FLOOR", None), float):
        finding("rule 4", "SIMILARITY_FLOOR is not a float constant")
```

**Line by line:**

- `getattr(retrieval, "TOP_K", None)` and then `isinstance` — the check is that the name exists **and**
  is the right type. A `TOP_K` that is a string read from an environment variable would pass a
  bare `hasattr` and fail at the slice.
- `isinstance(..., float)` for the floor and not `int`, deliberately. A floor of `0` would be an
  integer and would also be a floor that never fires; requiring a float is a small nudge towards
  writing an actual number.
- Rule 4 exists because [5.1](../05-when-retrieval-lies/5.1-nearest-is-not-near.md) showed that
  *"nothing found"* is a decision the caller has to make, and a decision with no constant behind it
  is a decision nobody made.
- Each check appends a **finding** rather than raising, so one run reports everything that is wrong
  instead of the first thing.

```python
# days/day-49-retrieval-and-embeddings/lab/gate.py
    # rule 6 - what comes back is sorted, best first. This is the Day 46 fix.
    factory = getattr(retrieval, "build_memory_service", None)
    if callable(factory):
        service = factory()
        found = await service.search_memory(
            app_name="sutra_desk", user_id="agent_riya", query="invoice pdf opens empty"
        )
        scores = [
            entry.custom_metadata.get("score")
            for entry in found.memories
            if entry.custom_metadata
        ]
        if len(scores) != len(found.memories):
            finding("rule 6", "a returned memory carries no score in custom_metadata")
        elif scores != sorted(scores, reverse=True):
            finding("rule 6", f"results are not sorted best first: {scores}")
```

**Line by line:**

- This is the **behavioural** rule, and it is the one that closes Day 46's finding. Rules 1 to 5 check
  shapes; this one runs a search and asserts something about the answer.
- It reads the score from `custom_metadata` rather than parsing it out of the text, because a
  *program* should read the structured field even though the *model* reads the text
  ([4.3](../04-the-adk-socket/4.3-the-score-has-to-be-written-down.md)). Both are written, for
  exactly this reason.
- `scores != sorted(scores, reverse=True)` is the assertion in one line: **the list must be in
  descending score order**. That single comparison is the difference between today and Day 46, and it
  is the thing a future refactor could silently break by capping before sorting.
- `build_memory_service()` and not the class, because the factory is where the cap, the lane and the
  index path are decided, and the gate should test the object the desk actually gets.

**Line by line:**

- From the root, not from `lab/`, because it imports `sutra.retrieval` and needs the project on the

- `echo "exit: $?"` prints the exit code, which is what `./m check` would look at.


Red, as it should be. When it prints `findings: 0` and `exit: 0`, six statements are true: the four
public names exist; `cosine` returns `1.0` for a vector against itself and `0.0` for two sharing
nothing; `TOP_K` is a named integer; `SIMILARITY_FLOOR` is a named float; the service is a genuine
`BaseMemoryService` with the right signature; and **what comes back is sorted best first with a score
on every entry**.

Then break exactly one on purpose — replace `TOP_K` with the literal `3` at its use site — and watch
rule 3 appear. An eval that has never been seen red is not an eval (Principle 11).

## When it breaks

**The seam is bypassed by a helpful addition.** Somebody adds `chunk_size: int = 500` to
`build_index` because it is convenient. Nothing fails. The function now does two jobs, Day 50's
chunking logic has two possible homes, and the tests for chunking need an index to exist. The
docstring above is the only thing standing between the codebase and that change, which is why it is
phrased as a prohibition rather than a description.

**The constant becomes a literal.** Somebody writes `scored[:3]` inside `search` because it reads
more clearly there. The gate catches it — rule 3 fires — and that is precisely why the rule exists:
the cost of a literal is invisible until the day somebody needs to change it and finds three copies.

**The cap moves in front of the sort.** No error, and the gate catches this one too, on rule 6. It is
worth naming again because it is the single mistake this whole day exists to prevent, and it is one
line-order change away at all times.

**The factory grows arguments.** `build_memory_service(top_k=5, lane="embeddings", path=...)` looks
like flexibility and is the end of having one place where construction happens. Day 46's build brief
made `build_memory_service()` take nothing for the same reason, and the reason is that a factory with
arguments is called from several places with different arguments, and then nobody can say what the
desk is actually running.

## In production

**What a professional writes instead of the teaching version.** They put the tuning constants in
**configuration rather than in code**, once there is more than one deployment — but they keep the
default in the module, with the comment recording what it was sized against. A number with no
provenance gets changed by the next person on a hunch; a number with `# 3, from the hit@3 sweep on
2026-09-06, see tests/test_retrieval_tuning.py` beside it does not.

They also add an **architecture test**: a check that the retrieval module does not import the
framework's memory types outside the adapter, and that the adapter contains no scoring logic. That is
the machine-readable version of the table at the top of this part, and it survives the person who
wrote it leaving.

The wider principle is the one this project has now applied four times.
[Day 47](../../../day-47-persistent-sessions/LESSON.md) swapped storage behind `BaseSessionService`.
[Day 48](../../../day-48-memory-design/LESSON.md) put retention rules in `policy.py` as data rather
than as branches. [3.3](../03-meaning-as-geometry/3.3-the-scale-does-not-know-what-it-weighs.md)
swapped the vectoriser. Today swaps the whole retriever behind `BaseMemoryService`. Each time the
question was the same: **what is likely to change, and is it behind a line?**

**What degrades at scale or under concurrency.** Seams degrade through **exceptions**. The first
caller who needs `build_index` to also chunk, just this once, adds a flag; the second adds another;
and eighteen months later the function has six parameters and no clear owner. The defence is a gate
that fails, which is what `lab/gate.py` is, promoted into `tests/` by the hub's build brief.

**The review comment a senior engineer leaves:** *"`TOP_K` is defined in the module and also
hard-coded as a default in two function signatures, so there are three places to change it and the
gate only checks one. One definition, referenced everywhere, and put the sweep that chose it in the
comment."*

**The interview question:** *"How do you design a component so the next change is cheap?"* An honest
answer: *"By deciding what is likely to change and putting it behind a line, and then writing a check
that fails when somebody crosses the line. In my retrieval module the vectoriser is injected, so
switching from term counts to an embedding model is one line at the call site; the index builder takes
pre-cut rows and its docstring says it never splits anything, so adding chunking changes what produces
the rows and not the builder; and the two numbers a tuning day wants — the result cap and the
similarity floor — are named module constants with the evidence for their values in the comment. The
part people skip is the check. I have a gate script with six rules, one of which runs an actual search
and asserts the results come back in descending score order, because the specific mistake I am most
afraid of is somebody capping before sorting, and that produces no error at all."*
