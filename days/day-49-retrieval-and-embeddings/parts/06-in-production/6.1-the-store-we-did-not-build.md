# 6.1 — The store we did not build

## One-line answer

A linear scan is 0.1 ms at eight rows and **876.6 ms** at twenty thousand dense vectors, holding
**117 MB** in memory — which is where a hand-written index stops being an engineering choice and a
real vector store starts being one.

## The story

The cupboard in the back room has two shelves and you can find anything in it in seconds.

There is no system. There is no labelling. There is a shelf with the paper and the pens and a shelf
with the tape and the spare parts, and you know where everything is because there are perhaps forty
things in there and you put most of them there yourself.

The warehouse across town holds ten thousand boxes, and it has aisles with letters, bays with
numbers, a shelf height, and a code on every box that says exactly which of those it lives in. When a
new person starts, they can find box `C14-3-07` on their first morning without ever having seen it.

The warehouse system would be absurd in the back room. Nobody paints `A1-2` on a two-shelf cupboard.
And the back room's system — *I know where it is* — does not survive the first thousand boxes, and it
does not survive the person who knew leaving.

The interesting part is that neither is wrong. They are answers to different sizes of the same
question, and the mistake is only ever using one where the other belongs.

## The idea in plain language

Everything this day built is the back room. Eight rows in a JSON file, scored with a loop.

That is the correct choice for this project, and the reason to say so with a measurement rather than
with a shrug is that the same code, unchanged, becomes a serious problem at a size that arrives
sooner than people expect.

Here is what a hand-written index does **not** have, and the words are worth knowing because they are
what a vector store is selling:

**An approximate nearest neighbour index.** [1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md)
warned that the word "index" here is not the database word. A database index lets the engine avoid
looking at most rows; this one is a precomputed table you read in full on every query. Real vector
stores build a structure — usually **HNSW**, a graph you walk towards the query, or **IVF**, which
clusters the vectors and searches only nearby clusters — that finds *almost* the nearest neighbours
while looking at a small fraction of the rows. They trade a little accuracy for a large amount of
speed, and the trade is adjustable.

**Filtering.** *"Find similar tickets, but only this customer's, and only from the last year."* A
loop can do it by checking each row, which costs the same as the scan. A store does it as part of the
search. This is not a performance nicety — Day 46's
[5.3](../../../day-46-sessions-vs-memory/parts/05-failure-lab/5.3-another-customers-memory.md) showed
one bucket serving two companies returning one company's billing contact on the other's ticket, and
filtering by `user_id` is the fix.

**Concurrent writes.** One process replacing a JSON file is fine. Two are not, and there is no lock
in this day's code anywhere.

**Persistence and recovery.** A store that survives a crash mid-write, which
[1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md)'s production section had to arrange by hand
with `os.replace`.

The named ones, and what each is actually for:

| Store | What it is | When it is the answer |
| --- | --- | --- |
| **FAISS** | a library, not a server — HNSW and IVF indexes in your own process | one machine, you own the lifecycle, no filtering needed |
| **pgvector** | a Postgres extension: a `vector` column type and index operators | you already run Postgres and want filtering, joins and transactions in the same query |
| **Qdrant**, **Chroma**, **Weaviate**, **Milvus** | purpose-built vector databases | vectors are the main workload and you want filtering, sharding and an API |
| **Elasticsearch** / **OpenSearch** | full-text engines with k-nearest-neighbour search added | you want BM25 and dense retrieval in one place — the hybrid search of [2.1](../02-the-meaning-test/2.1-the-score-that-came-back-zero.md) |
| **`VertexAiRagMemoryService`** | the managed version, inside ADK | you have a billing account; 🅿️ parked by Addendum 02 |

The last row is worth pausing on. Day 46 parked it in
[6.2](../../../day-46-sessions-vs-memory/parts/06-in-production/6.2-the-two-services-we-park.md), and
its constructor takes `similarity_top_k` and `vector_distance_threshold`. After
[4.4](../04-the-adk-socket/4.4-the-cap-that-finally-means-something.md) and
[5.1](../05-when-retrieval-lies/5.1-nearest-is-not-near.md) you know exactly what both of those
arguments do, and what happens when each is set wrong. That is Principle 4 paying out: the managed
service is now a convenience rather than a mystery.

## Why Sutra needs it

Because "we did not use a vector database" needs to be a decision with a number behind it, and
because the number is what tells you when the decision expires.

Sutra's archive is eight tickets. `./m check` must run in seconds on a laptop with no daemon, no
container and no service. Adding a vector store would add an operational dependency to a curriculum
whose entire premise is that everything runs at zero cost, and it would hide the mechanism this day
exists to teach.

What this part supplies is the **threshold**: the archive size at which that reasoning stops holding.

## The paper behind it

> **Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks** · `arXiv:2005.11401` · 2020 ·
> `https://arxiv.org/abs/2005.11401`

It paired a generator with a **non-parametric** memory — an index of documents that can be swapped or
updated without retraining anything — which is the architectural idea every store in the table above
exists to serve.

Read it after the parts:
[`papers/02-retrieval-augmented-generation.md`](../../papers/02-retrieval-augmented-generation.md).

## The mechanism

Measure it rather than assert it.

```python
# days/day-49-retrieval-and-embeddings/lab/stores.py
def synthetic(n: int, rng: random.Random) -> list[tuple[str, str]]:
    """n tickets built by reshuffling the real archive's vocabulary."""
    vocabulary = sorted({word for _, text in ARCHIVE for word in tokenize(text)})
    rows = []
    for i in range(n):
        words = rng.sample(vocabulary, k=min(14, len(vocabulary)))
        rows.append((f"{10_000 + i}", " ".join(words)))
    return rows
```

**Line by line:**

- The synthetic tickets are built from the **real archive's vocabulary**, so the vectors have a
  realistic number of non-zero entries. Generating random strings would produce a vocabulary of
  hundreds of thousands of unique words and measure the wrong thing entirely.
- `rng.sample(..., k=14)` gives every row fourteen distinct words, matching the real tickets' length.
  Uniform row length is a simplification, stated here rather than hidden: real length varies and the
  scan cost varies with it.
- `random.Random(SEED)` rather than the module-level `random`, so both the sparse and dense
  measurements draw from a stream the caller controls and the numbers are reproducible.

```python
# days/day-49-retrieval-and-embeddings/lab/stores.py
def dense_scan(n: int, width: int = 768) -> float:
    """Time one cosine scan over n dense vectors of `width` random numbers."""
    rng = random.Random(SEED)
    rows = [[rng.random() for _ in range(width)] for _ in range(n)]
    query = [rng.random() for _ in range(width)]
    started = time.perf_counter()
    scored = [
        (sum(q * v for q, v in zip(query, row)), position) for position, row in enumerate(rows)
    ]
    scored.sort(reverse=True)
    return (time.perf_counter() - started) * 1000
```

**Line by line:**

- **The numbers are random, not learned.** Nothing about retrieval quality is being measured here —
  only the cost of the arithmetic, which does not care what the numbers mean.
- `width=768` is a common embedding dimension and is used as a representative figure. The dimension
  of `nomic-embed-text` is not stated on its model page, so this document does not claim it is that
  model's ([3.2](../03-meaning-as-geometry/3.2-the-model-that-runs-in-your-own-shop.md) leaves reading
  the real number as a `TODO(verify: ...)`). Halve the width and halve the time.
- `sum(q * v for q, v in zip(query, row))` is a **dot product, not a cosine**, because the division
  by lengths is a constant factor and because a real store keeps normalised vectors
  ([1.3](../01-text-as-numbers/1.3-direction-not-size.md)). This measures the best case.
- Lists, not dictionaries. Dense vectors in a dict would be slower still; this is the fastest pure
  Python can go without `numpy`, which this project does not install.
- The timer starts **after** the vectors are built, so the measurement is the query cost alone.

Run it:

```bash
cd days/day-49-retrieval-and-embeddings/lab
uv run python stores.py
```

**Line by line:**

- Three archive sizes for the sparse index, then two for the dense one.
- `--big` adds a 200,000-row measurement; it is slow and shows the same shape.
- **Zero model calls.** The dense vectors are random numbers, not embeddings.

Measured on 2026-09-05, on one laptop. Read the **shape**, not the millisecond: these numbers move
with the machine, and the ratios do not.

```text
     rows     build   index file    one query
        8     0.00s         0.0M        0.1ms
    1,000     0.01s         0.4M        3.6ms
   20,000     0.30s         8.3M       64.3ms

the same scan over dense 768-number vectors, which is what an embedder gives:
    1,000 rows ->     37.0ms per query,    5.9M held in memory
   20,000 rows ->    876.6ms per query,  117.2M held in memory

every query reads every row. There is no index in the database sense here:
no tree, no inverted list, no approximate neighbour graph. A loop.
vocabulary of the real archive: 80 words
a dense vector of the same width would be 18 non-zero numbers out of that.
```

**The sparse index is fine for far longer than you would guess.** Twenty thousand tickets, 8.3 MB on
disk, 64 ms per query. That is a real support archive and it is answered in less time than a network
round trip. If Sutra's archive were sparse-only, this code would serve it honestly for years.

**The dense index is a different animal.** The same twenty thousand rows take **876.6 ms per query** —
nearly a full second of one CPU, for one search — and hold **117 MB** resident. Two facts multiply
here: every vector went from about eighteen non-zero numbers to seven hundred and sixty-eight, and
every one of those is a Python float in a Python list.

**876 ms inside an `async` method is the sentence that matters.**
[4.1](../04-the-adk-socket/4.1-two-methods-and-a-list.md) established that `search_memory` is a
coroutine, awaited on an event loop that is also serving other turns. Blocking CPU work in there stops
*everything* for its duration. The first symptom is not a slow search; it is an unrelated turn timing
out, which is the hardest kind of bug to trace back to its cause.

So the honest threshold, for this code, on this shape of data:

| Archive size | Sparse, hand-written | Dense, hand-written |
| --- | --- | --- |
| under ~1,000 | fine | fine |
| ~20,000 | fine — 64 ms | **no** — 876 ms and 117 MB |
| beyond that | measure it | a vector store, not a loop |

The dense column crosses over an order of magnitude earlier than the sparse one, which is the
non-obvious result. **The moment you adopt embeddings you have moved much closer to needing a real
store**, and that cost belongs in the decision alongside the quality gain.

## When it breaks

The break is not an error. It is a slow search that becomes a queue.

At 876 ms per query on one loop, five concurrent searches means the fifth waits over four seconds
before it starts, and everything else the agent was doing waits with it. What surfaces to the user is
[Day 44](../../../day-44-client-hardening/LESSON.md)'s territory — a timeout in some other tool call —
and the traceback points at the innocent party.

The memory failure is louder and arrives without warning. 117 MB at twenty thousand rows is 1.2 GB at
two hundred thousand, held as Python floats, in every process that constructs the service. Two workers
means twice that. The end of it is:

```text
MemoryError
```

with no other information at all, from whichever line happened to allocate last.

The third break is the one that gets shipped: adopting a vector store and **not** adopting the
filtering. A store gives you `user_id` filtering as part of the query, and a team migrating from a
loop often ports the loop's behaviour faithfully — including the missing filter. Day 46's
[5.3](../../../day-46-sessions-vs-memory/parts/05-failure-lab/5.3-another-customers-memory.md) is what
that costs.

## In production

**What a professional writes instead of the teaching version.** They start with what they already
run. If there is a Postgres in the stack, pgvector is almost always the right first answer: one
system to operate, filtering and joins in the same query, transactions, and a backup story that
already exists. Reaching for a dedicated vector database first is a common and expensive mistake,
because it adds an operational dependency to solve a problem the existing database can solve until
the corpus is genuinely large.

They also **keep the interface**. Everything in this day sits behind `search(query, index, k)` and
`BaseMemoryService`, and a store swap should touch one module. That is
[6.2](6.2-the-seams-day-50-opens.md)'s subject, and it is what makes the threshold table above a
plan rather than a warning.

And they **measure recall against the exact answer**. Approximate nearest neighbour search is
*approximate*: HNSW and IVF have parameters that trade accuracy for speed, and the default is not
always what you want. The check is to run a brute-force scan over a sample and compare — the loop in
this day is exactly that check, which is a genuinely useful thing to keep after you stop serving from
it.

**What degrades at scale or under concurrency.** Everything above, plus one that only appears with
several workers: each one holding its own copy of the index. Four workers at 117 MB is 468 MB of the
same data, and the fix is a shared store rather than a bigger machine.

**The review comment a senior engineer leaves:** *"Sixty-four milliseconds of blocking CPU per search
on the event loop is already too much and the archive triples this year. Before we add embeddings —
which take this to nearly a second — put the vectors in pgvector; we already run Postgres, and it
gives us the `customer_id` filter we currently do not have at all."*

**The interview question:** *"When would you introduce a vector database?"* An honest answer: *"When
the scan stops being free, and I would want the measurement rather than a rule of thumb. On my own
code a sparse index over twenty thousand documents was 64 milliseconds and an 8 MB file, which is
fine — but the same twenty thousand as dense 768-dimension vectors was 876 milliseconds per query and
117 MB resident, and that is inside an async method on the event loop, so it stalls every other turn.
The crossover is an order of magnitude earlier once you adopt embeddings, which is a cost people
forget to count against the quality gain. The other two triggers are needing filtered search — 'similar
tickets, this customer only', which a loop can only do by checking every row — and more than one
writer. When it is time, I would reach for pgvector first if there is already a Postgres, because it
is one fewer system to run and it gives filtering and transactions for free."*
