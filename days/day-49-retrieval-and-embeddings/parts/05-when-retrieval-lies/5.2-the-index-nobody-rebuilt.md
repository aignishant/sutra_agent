# 5.2 — 💥 The index nobody rebuilt

## One-line answer

A ticket closed after the index was written is **unreachable** — `is 4602 reachable at all? False` —
with no error, no warning and no empty result, and adding that one row also moved the weight of `app`
from `2.079` to `1.504`, which changes the score of every other row in the archive.

## The story

The price list is painted on a board on the wall behind the counter, and it has been there for years.

In March the supplier put his prices up, so the shopkeeper wrote the new numbers in a notebook under
the till and started charging from the notebook. The board stayed on the wall. It is a nice board.
Repainting it is a Sunday job and Sunday has been busy.

A customer comes in, reads the board, and asks for two of the thing at the price on the board. The
board is not lying to him — it is simply the price from before March, presented exactly the way a
current price is presented, on the wall, in paint, with no date on it anywhere.

The argument at the counter is not about the price. It is about the fact that there was no way for
the customer to tell.

## The idea in plain language

[1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md) established that an index is **derived
data**: everything in it can be rebuilt from the documents, so losing it is an inconvenience rather
than a loss. That property has a shadow, and the shadow is this part.

Derived data is a **copy**, and a copy has a moment at which it was made. From that moment on it
disagrees with its source, a little more every day, and nothing about the copy announces this.

Two separate things go stale, and it is worth keeping them apart because they have different fixes.

**Missing rows.** A document written after the index was built has no vector, so it cannot be scored,
so it can never be returned. It is invisible — not ranked low, not returned with a poor score:
absent. There is no query that reaches it.

**Drifted weights.** This one is specific to tf-idf and it surprises people. The idf weights are a
property of the **whole collection** ([1.4](../01-text-as-numbers/1.4-the-word-that-tells-you-nothing.md)),
so adding one document changes the weight of every word that document contains, which changes the
score of every stored vector that also contains those words. A correct new row does not just add
itself; it invalidates the arithmetic of everything already there.

The dense lane has the same problem in a different form. Embeddings do not drift with the corpus —
one text always produces the same vector from the same model — but the **model** can change under
you: a re-pulled tag, an upgraded image, a hosted model retired. Then the stored vectors and the
query vector come from two different models and the scores are meaningless rather than merely
outdated ([3.3](../03-meaning-as-geometry/3.3-the-scale-does-not-know-what-it-weighs.md)).

## Why Sutra needs it

Because the desk's whole value is answering *"has anything like this happened before?"*, and the case
most likely to be asked about is the case that happened **most recently**.

The staleness window sits exactly over the highest-value documents. Nobody asks whether a two-year-old
fault has come up before; they ask about the one from last Tuesday, which is the one the index does
not have. A retrieval system that is stale by a week is not 5% worse — it is missing the specific
documents people are asking for.

It also matters because of how Sutra builds the service.
[4.2](../04-the-adk-socket/4.2-same-tool-new-answer.md)'s `RetrievalMemoryService` builds its index in
`__init__`, which is the tidiest possible way to write this bug: a long-lived service object holds a
snapshot taken at process start, and the only way to refresh it is a restart.

## The mechanism

One ticket, closed after the index was written.

```python
# days/day-49-retrieval-and-embeddings/lab/stale.py
NEW = (
    "4602",
    "Barcode scanner in the warehouse app crashes on Android 15. Fix KB-611.",
)
QUESTION = "warehouse barcode scanner crash"


def main() -> None:
    rebuild = "--rebuild" in sys.argv
    live = ARCHIVE + [NEW]  # what the ticket system holds right now
    indexed = live if rebuild else ARCHIVE  # what the index was built from
```

**Line by line:**

- `NEW` is deliberately the subject that
  [5.1](5.1-nearest-is-not-near.md) asked about and the archive could not answer. The team **did**
  handle a barcode scanner crash; they handled it yesterday. That is the realistic case, and it is
  what makes the failure sting: the archive has the answer and the index does not.
- `live` against `indexed` is the whole model of the bug, in two lines. The ticket system has nine
  rows. The index has eight. Nothing in the code compares those two numbers, which is exactly the
  problem.
- `rebuild = "--rebuild" in sys.argv` — the ablation is *"did anybody rebuild the index"*, which is
  an operational act and not a code change. That is where this class of bug lives.
- `bodies = dict(live)` (further down the file) reads text from the **live** archive so that a result
  can be printed for any row. If it read from `indexed`, the script would raise `KeyError` instead of
  showing the miss, and hiding the miss behind a crash would defeat the point.

Run both arms:

```bash
cd days/day-49-retrieval-and-embeddings/lab
uv run python stale.py
uv run python stale.py --rebuild
```

**Line by line:**

- The first arm searches an index built before 4602 existed.
- `--rebuild` builds the index from all nine rows, which is the only difference.
- **Zero model calls in either arm.**

Measured on 2026-09-05, the stale arm:

```text
tickets in the system : 9
rows in the index     : 8
ticket 4602 closed after the index was built: Barcode scanner in the warehouse app crashes on Android 15. Fix KB-611.

query: 'warehouse barcode scanner crash'
   0.000  4188  Login loop on the staff portal. Session cookie written w
   0.000  4239  Password reset mail never reaches the customer. Their ga
   0.000  4402  Cannot print an invoice from the portal; the PDF opens e

is 4602 reachable at all? False
no error, no warning, no empty result. Just an answer from the wrong year.

idf weights that moved when one ticket was added: {'app': (2.079, 1.504), 'on': (2.079, 1.504)}
adding a row changes the score of every other row. The index is one object.
```

And the rebuilt arm:

```text
tickets in the system : 9
rows in the index     : 9
ticket 4602 closed after the index was built: Barcode scanner in the warehouse app crashes on Android 15. Fix KB-611.

query: 'warehouse barcode scanner crash'
   0.597  4602  Barcode scanner in the warehouse app crashes on Android 
   0.000  4188  Login loop on the staff portal. Session cookie written w
   0.000  4239  Password reset mail never reaches the customer. Their ga

is 4602 reachable at all? True

idf weights that moved when one ticket was added: {'app': (2.079, 1.504), 'on': (2.079, 1.504)}
adding a row changes the score of every other row. The index is one object.
```

**`0.000` against `0.597`.** The same query, the same code, the same archive on disk. The only
difference is whether anybody rebuilt the file.

Three things in that pair of runs.

**`is 4602 reachable at all? False`.** Not "ranked low". The script checks the *entire* ranked list,
not just the top three, and 4602 is not in it, because it has no vector. There is no cap to raise and
no threshold to lower that reaches it. This is a different failure from
[5.1](5.1-nearest-is-not-near.md)'s: there, the archive had nothing and the retriever returned
something anyway; here, the archive **has** the answer and the retriever cannot see it.

**The stale arm returned three results, all scoring `0.000`.** Which is exactly the shape
[2.2](../02-the-meaning-test/2.2-the-repairs-that-fix-one-pair.md) warned about: a rank of one at a
score of zero is a tie broken by ticket id, not a match. If this were wired into
[4.2](../04-the-adk-socket/4.2-same-tool-new-answer.md)'s service, the desk would report *"the
closest past case is ticket 4188, login loop"* to somebody asking about a barcode scanner.

**`{'app': (2.079, 1.504), 'on': (2.079, 1.504)}`.** This is the drift, and it is the part that is
easy to miss. Adding one ticket moved the weight of `app` from `log(8/1) ≈ 2.079` to
`log(9/2) ≈ 1.504`, because `app` now appears in two tickets out of nine instead of one out of eight.
Every vector in the file that contains `app` is now weighted wrongly — including 4571, the mobile-app
ticket, which is the one
[5.1](5.1-nearest-is-not-near.md) already showed being returned to the wrong question. **A partially
updated index is not "mostly right". It is arithmetically inconsistent**, and the inconsistency is
invisible.

## When it breaks

The break is that there is no break. That is the entire finding, and it is worth listing what you do
*not* get:

- no exception;
- no warning on any logger;
- no empty result set;
- no field anywhere in `SearchMemoryResponse` or `MemoryEntry` that carries a date
  ([4.1](../04-the-adk-socket/4.1-two-methods-and-a-list.md) enumerated the five fields, and
  `timestamp` is the memory's own timestamp, not the index's);
- and no difference in the shape of the response.

Compare that with the **loud** version of the same family, from
[1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md):

```text
FileNotFoundError: [Errno 2] No such file or directory: 'C:\\Users\\nisha_gnzw\\OneDrive\\Desktop\\Projects\\sutra\\days\\day-49-retrieval-and-embeddings\\lab\\archive_index.json'
```

A **missing** index takes the desk down and somebody fixes it within the hour. A **stale** index
serves confident answers from last quarter until a customer notices. Of the two, the crash is the one
you want, and that is worth saying out loud because it runs against instinct.

The nastiest version is the **partial** build, and it is the one
[3.4](../03-meaning-as-geometry/3.4-the-embedder-we-park.md) predicted: a hosted embedder returns
`429` at row 3,100 of 5,000, the build stops, and what is on disk parses perfectly as JSON. Every
search now runs against sixty per cent of the corpus, correctly, quickly, and wrongly. This is why
[1.5](../01-text-as-numbers/1.5-the-work-you-do-once.md)'s production section insists on writing to a
temporary file and using `os.replace`: a half-written index must never become the live one.

## In production

**What a professional writes instead of the teaching version.** They put a **freshness stamp inside
the index** and expose it. The minimum is three fields: when the build ran, how many source rows it
covered, and the identity of the highest-numbered or most-recently-modified source row. Then two
things become possible that are impossible today — a **lag metric** (`now - built_at`) with an alert
on it, and a **coverage check** (`rows in index` against `rows in the source`) that runs on a
schedule and fails loudly.

They also make the index **incrementally updatable**. New ticket in, one vector out, appended. That
keeps the missing-row problem to seconds rather than to whatever the rebuild interval is. The idf
drift is then handled separately and deliberately: accept that the weights are slightly stale between
full rebuilds, because the drift on a large corpus from one new document is tiny — `log(50001/n)`
against `log(50000/n)` — and schedule a full rebuild for when it is not. On this eight-row archive the
drift was 28%; at fifty thousand rows it is invisible. **The small-corpus case is the one where drift
matters most, which is the opposite of where people look for it.**

And they **version the index against the code**. The tokenizer, the weighting scheme, the model name
and the dimension go in the file, and the search path refuses to run when they do not match what the
running code expects. That single assertion catches a tokenizer change, a model swap and a
half-migrated deployment.

**What degrades at scale or under concurrency.** The rebuild window. A full rebuild that takes longer
than the interval between rebuilds means you never have a current index again, and that is a cliff
rather than a slope — everything is fine until it is permanently not. Under concurrency, a rebuild
running while searches are served is fine with an atomic replace and corrupt without it; and with
more than one writer, a JSON file is the wrong data structure entirely, which is
[6.1](../06-in-production/6.1-the-store-we-did-not-build.md)'s argument.

**The review comment a senior engineer leaves:** *"The service builds its index in `__init__`, so the
only way to pick up a new ticket is a restart, and nothing anywhere records when the index was built.
Put `built_at` and the source row count in the file, expose the lag as a metric, and add a check that
compares the index's row count with the ticket table's. Right now a failed nightly rebuild is
completely invisible to us."*

**The interview question:** *"How do you know your retrieval index is up to date?"* An honest answer:
*"You do not, unless you build it in. A document added after the index was written has no vector, so
it cannot be scored and cannot be returned — it is not ranked low, it is absent — and nothing errors.
I reproduced it: a ticket closed after the build returned `reachable: False`, and the search still
returned three results, all scoring 0.000, so the desk would have quoted an unrelated login ticket.
The second half of it caught me out: because tf-idf weights are a property of the whole collection,
adding that one row moved the weight of a word from 2.079 to 1.504, so every stored vector containing
that word was now scored inconsistently. So the index carries `built_at`, a source row count and the
tokenizer or model identity, I alert on the lag between the newest document and the newest indexed
row, and the search path refuses to run when the fingerprint does not match. And the staleness window
sits over exactly the documents people ask about most, which are the newest ones."*
