# 5.3 — 💥 The question you actually asked

## One-line answer

Five ways of asking for the same ticket give five different results — `0.456`, `0.372` and three
`0.000`s — and under `load_memory` the wording is chosen by the **model**, not by you, so the
retrieval quality you measured is not the retrieval quality you ship.

## The story

*"Do you remember that thing, at my cousin's place, with the — you know — the thing that happened?"*

Your friend has no idea. Not because their memory is bad, but because you have handed them nothing to
search with. Every word in that sentence could point at a hundred evenings.

So you try again. *"Last year, in the rain, when the car would not start."* Now they are there
instantly — they can tell you who was there, what you ate, and what the mechanic said the next
morning.

Nothing about their memory changed between the two sentences. The whole difference was in what you
handed them. And notice that you were describing the same evening both times, and that the first
attempt was the one you produced naturally, without thinking.

## The idea in plain language

Every part of this day so far has treated the query as fixed. It is not. It is a string somebody
typed, or — worse for your peace of mind — a string a **model** composed.

Day 46 chose `load_memory` over `preload_memory` in
[4.2](../../../day-46-sessions-vs-memory/parts/04-the-choice/4.2-sutras-memory-policy.md), and the
reason was visibility: with `load_memory` the query lands in the transcript where you can read it.
That was the right choice and it does not remove the underlying fact, which is that the model writes
the query. It might send the user's whole message. It might send three words. It might send a
greeting. Day 46's
[3.4](../../../day-46-sessions-vs-memory/parts/03-three-wires/3.4-the-past-pushed-in-before-the-turn.md)
found that the *other* tool, `preload_memory`, sends `user_content.parts[0].text` — the user's raw
message, greeting and all — which is the same problem with the observability removed.

So the honest statement of what you have built is this: **the retriever is one half of the system and
the query writer is the other half, and you only tested one of them.**

## Why Sutra needs it

Because [4.4](../04-the-adk-socket/4.4-the-cap-that-finally-means-something.md) measured hit@1 at 6
out of 7 using seven queries **written by hand, by someone who had read the archive**. That number is
real and it is an upper bound. Nobody in production writes queries like that.

It also decides where a fix goes. If retrieval is bad and the query is bad, changing the vectoriser
is the expensive repair and changing the instruction is the cheap one — and you cannot tell which you
need without logging the query. That is one line of code and it is the difference between a week of
investigation and an afternoon.

## The mechanism

Five phrasings, one archive, one right answer.

```python
# days/day-49-retrieval-and-embeddings/lab/words.py
# All five mean "the customer cannot get past the sign-in page". 4188 is the right answer.
PHRASINGS = [
    "auth redirect bug",
    "Hi, quick one - has anything like this come up before? Thanks!",
    "Auth redirect bug: after the identity provider hands control back, our user "
    "lands at a blank sign-in screen.",
    "login loop",
    "session cookie SameSite",
]
ANSWER = "4188"
```

**Line by line:**

- The five are not five different questions. They are **five things a support agent or a model might
  send while meaning the same thing**, ordered from the terse to the expert.
- Row 1, `"auth redirect bug"`, is what a model summarising the ticket would plausibly extract: short
  and in the incoming ticket's vocabulary.
- Row 2 is the one nobody puts in a test set and everybody sees in production: a **greeting with no
  content at all**. A model that passes the user's message through gets this whenever the user is
  polite.
- Row 3 is the incoming ticket's full text — the query from
  [2.1](../02-the-meaning-test/2.1-the-score-that-came-back-zero.md).
- Rows 4 and 5, `"login loop"` and `"session cookie SameSite"`, are written in the **archive's**
  vocabulary rather than the asker's. Nobody with today's ticket in front of them would type either,
  because you would have to already know the answer.
- The script also prints the **tie count** at each score, because
  [2.2](../02-the-meaning-test/2.2-the-repairs-that-fix-one-pair.md) established that a rank without
  a score behind it is not a rank.

Run it:

```bash
cd days/day-49-retrieval-and-embeddings/lab
uv run python words.py
```

**Line by line:**

- One arm, five rows. The archive, the weights and the ranking code are identical for all five; only
  the string changes.
- **Zero model calls** — which is the irony of this part, since the thing being studied is what a
  model would send.

Measured on 2026-09-05:

```text
every row below asks for ticket 4188. Only the wording changes.

  score   rank  tied   top hit  query
  0.000    1/8     7      4188  auth redirect bug
  0.000    1/8     7      4188  Hi, quick one - has anything like this come up before? T
  0.000    5/8     3      4467  Auth redirect bug: after the identity provider hands con
  0.372    1/8     0      4188  login loop
  0.456    1/8     0      4188  session cookie SameSite

a rank of 1 at a score of 0.000 is a tie broken by ticket id, not a match.
same archive, same code, same intent, five different answers.
under load_memory the query is whatever the model decided to type.
```

Five rows, and every one of them says something different.

**Rows 1 and 2 look like successes and are not.** `rank 1/8` on both — and `tied 7`, meaning the
entire archive scored `0.000` and 4188 came first because `4188` sorts before `4239`. The greeting
row is the alarming one: *"Hi, quick one - has anything like this come up before? Thanks!"* contains
no information whatsoever, and the system confidently returns ticket 4188 as the top hit. A dashboard
counting hit@1 would score that as a win.

**Row 3 is the only one that genuinely ranks, and it ranks wrongly.** The full ticket text has enough
rare words to produce real scores, and those scores put the caching ticket 4467 first
([2.1](../02-the-meaning-test/2.1-the-score-that-came-back-zero.md)). More query text produced a
*worse* answer than no query text, because the extra words matched other documents.

**Rows 4 and 5 work, and you could not have written them.** `0.372` and `0.456`, rank 1, no ties.
Both are phrased in the vocabulary of the *answer*. To type `"session cookie SameSite"` you would need
to already know that 4188 is about a cookie flag, which is the thing you were asking the archive to
tell you. **The query that retrieves the answer is the query you can only write after you have the
answer.** That is the whole of the vocabulary mismatch problem, stated as a practical joke.

Now put row 2 beside row 3 and look at what it means for measurement. The greeting scored `0.000`,
which is honest. The full ticket scored `0.000` on the right answer and `0.270` on a wrong one, which
is worse than honest. A summary metric that says *"hit@1 is 3/5"* over these five rows is arithmetic
performed on nonsense.

## When it breaks

The break has three shapes and you will meet all three.

**The model sends the user's greeting.** Row 2. `load_memory`'s declaration is a single `query`
string, and the paragraph ADK appends to the system instruction is generic —
`.venv/Lib/site-packages/google/adk/tools/load_memory_tool.py` contains it verbatim:

```text
You have memory. You can use it to answer questions. If any questions need
you to look up the memory, you should call load_memory function with a query.
```

That is all the guidance the model gets about what a good query looks like. It says nothing about
extracting the technical terms, nothing about dropping pleasantries, and nothing about trying a second
phrasing when the first returns nothing. Day 46's build brief already flagged this as a `TODO(me)`:
*"ADK's appended paragraph is generic; a model that never asks retrieves nothing and nothing warns
you."* Today adds the other half — a model that asks badly retrieves rubbish, and nothing warns you
about that either.

**The query is nowhere to be found.** Under `load_memory` the query is in the transcript, which is
why Day 46 paid extra for it. Under `preload_memory` it is not an event at all, and the search that
produced a bad answer leaves no trace. If you are debugging retrieval on a system using automatic
injection, the first thing to do is add the logging that should have been there.

**Nobody measures the queries that were actually sent.** This is the quiet one. Your judgement set has
seven queries you wrote; production has ten thousand the model wrote, and the two populations do not
resemble each other. The fix is not clever: log the query on every search, sample fifty of them a
month, and put them in the judgement set.

## In production

**What a professional writes instead of the teaching version.** Three things, and the first is nearly
free.

**Write the query-writing instruction.** Do not rely on the framework's generic paragraph. Tell the
model what a good query is for *your* archive: the technical terms and error strings, not the
greeting; the symptom in the user's words *and* any product terms; three to eight words. That
instruction is the highest-leverage text in the whole retrieval system and it costs a few dozen
tokens per request.

**Log the query, the top score and the result count on every search.** Four fields. This is the same
argument Day 46 used to choose `load_memory` in the first place, extended past the transcript into
your own telemetry, and it is what makes the difference between *"retrieval was bad on Tuesday"* and
*"on Tuesday the model was sending the user's full message, including the signature block"*.

**Rewrite the query before you use it.** The standard production shape is a small step in front of
retrieval that turns a conversational message into a search query — sometimes a model call, often
just extraction of the technical terms and removal of pleasantries. A stronger version, and the one
that fixes rows 4 and 5 above, is **multi-query retrieval**: generate two or three phrasings of the
same question, retrieve for each, and fuse the ranked lists. That is what buys you the *"login loop"*
phrasing when the user typed *"auth redirect bug"*, and it is worth its cost precisely because a
single phrasing is such a lottery.

**What degrades at scale.** Query variety, and it grows faster than the archive does. Ten users
produce ten phrasings; ten thousand produce every phrasing, including empty ones, ones in other
languages, and ones that are entire pasted stack traces. The average retrieval quality falls even
though nothing about the retriever changed, and the only way to see it is to measure on **sampled real
queries** rather than on the set you wrote when you built it.

**The review comment a senior engineer leaves:** *"We do not log the query. When retrieval is bad we
cannot tell whether the index is wrong or the model sent 'hi can you help'. Log query, result count
and top score on every search, and add ten real queries from last month's logs to the judgement set —
including the ones that are just greetings, because the current behaviour on those is to confidently
return the first ticket in the archive."*

**The interview question:** *"Your retrieval evaluation looks good. What would you check before
believing it?"* An honest answer: *"Whether the queries in the evaluation resemble the queries in
production. Mine did not. I wrote seven queries by hand, knowing the archive, and measured hit@1 at
six out of seven. Then I asked the same archive the same question five different ways and got five
different answers — two of them scored 0.000 for everything and appeared to rank the right ticket
first purely because of a tie-break on the ticket id, and one of those two was a bare greeting with no
content at all. The two phrasings that genuinely worked were written in the archive's vocabulary,
which means you would have to already know the answer to type them. Under a tool-calling agent the
model composes the query, so the thing I would fix first is not the retriever — it is the instruction
that tells the model what a good query looks like, plus logging the query on every search, and then
re-measuring on sampled real queries."*
