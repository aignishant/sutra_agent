# 2.4 — 💥 The bytes that arrived, not the object they became

## One-line answer

A signature covers bytes, and parsing JSON and re-serialising it produces different bytes carrying
identical meaning — so a verifier that hashes `json.dumps(json.loads(body))` refuses every genuine
request, and the fix is to read the body once, as bytes, before anything else touches it.

## The story

💥 **The retyped copy.**

🎬 **The scene.** An office asks for a copy of a certificate. Somebody photographs the original,
and somebody else — being helpful, and finding the photograph slightly crooked — retypes it neatly
into a document with the same fields and the same values.

😬 **The naive fix.** The retyped version is *better*. It is legible, correctly aligned, no shadow
across one corner. Every word is the same. It gets sent.

💥 **Why it fails.** The office is not reading the words. It is checking the seal, the paper, the
registrar's handwriting in the margin — the physical artefact. The retyped copy contains all of the
information and none of the evidence, and it is rejected by somebody who never even read it.

💡 **The insight.** **The thing being verified was never the meaning.** Anything that reconstructs
the content from the meaning destroys exactly the property that was being checked, and it does it
while making the content look better.

## The idea in plain language

JSON has slack in it. These two are the same object and different bytes:

```text
{"a":1,"b":2}
{"a": 1, "b": 2}
```

Whitespace after the colons, whitespace after the commas, the order of keys, how non-ASCII
characters are escaped, how many digits a float keeps. A parser throws all of that away, because for
a parser it does not mean anything. That is the parser's job.

A signature is computed over bytes and is therefore sensitive to every one of those choices. So
the moment a request body has been through `json.loads`, the original bytes are gone, and
`json.dumps` gives you back *a* serialisation, not *the* serialisation.

Vendors send compact JSON — no space after the colon — because it is smaller. Python's `json.dumps`
defaults to a space after both the colon and the comma. So the reconstruction is not subtly
different; it is different on nearly every field.

This is the single most common way a webhook verifier is written wrong, and the reason is structural
rather than careless: web frameworks are built to give you the parsed object. Asking for the parsed
body is the natural, documented, one-line thing to do. Asking for the raw bytes is the unusual
request, and it has to be made *first*, because in some frameworks reading the body consumes the
stream and the second reader gets nothing.

## Why Sutra needs it

Because the endpoint in this day is a FastAPI route, and FastAPI's whole design is that you declare
a Pydantic model and receive a parsed, validated object. That is excellent for every route in Day
85's API surface and it is exactly wrong for this one — this handler must take the body as `bytes`
and do its own parsing after the check.

And because the failure is the worst possible shape for debugging: it refuses everything, including
the requests that are correct, and the vendor's console shows a signature error that points at your
secret. Whole afternoons are lost to rotating a secret that was never wrong.

## The mechanism

The endpoint has a switch for this, so the two behaviours can be measured side by side:

```python
            body = json.dumps(json.loads(raw)).encode() if reparse else raw
            expected = sign(body, timestamp, SIGNING_SECRET)
```

**Line by line:**

- `raw` is what `await request.body()` returned: the exact bytes, untouched. That is the correct
  branch and it is the shorter one.
- `json.dumps(json.loads(raw)).encode()` is the bug, written out in full so it can be run. Nobody
  writes this line deliberately — it appears as `payload = await request.json()` at the top of a
  handler, and then `sign(json.dumps(payload).encode(), ...)` fifteen lines later, and between them
  it looks entirely reasonable.
- Both branches feed the same `sign()`. The difference is only ever the input bytes, which is what
  makes the measurement clean.

Run both, on a body shaped the way a vendor actually sends one:

```bash
cd days/day-91-slack-shaped-intake/lab
uv run python raw.py; echo "exit: $?"
```

**Line by line:**

- The fixture is built with `json.dumps(APP_MENTION, separators=(",", ":"))` — compact, as it would
  arrive on the wire — and then signed. So the request is genuine in every respect.

Measured on 2026-09-07:

```text
the endpoint signs: the raw body

  bytes that arrived:     331  {"token":"Jhj5dZrVaK7ZwHHjRyZWjbDl","t...
  bytes after a parse:    355  {"token": "Jhj5dZrVaK7ZwHHjRyZWjbDl", ...
  identical:            False
  first 331 bytes differing: 309

  a correctly signed post: 200 ok
  reached the desk: 1   refused: []

  accepted: the bytes checked are the bytes that arrived
exit: 0
```

**331 bytes against 355, and 309 of the first 331 differ.** The two strings carry identical
information. As far as the hash is concerned they have nothing whatever in common.

## When it breaks

Turn the switch and the same genuine request is refused:

```bash
uv run python raw.py --reparse; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  a correctly signed post: 401 bad signature
  reached the desk: 0   refused: ['bad signature']

  the request was signed correctly and refused anyway
  the endpoint hashed bytes the vendor never sent
exit: 1
```

`401 bad signature`. That is the real error text and it is the most misleading string in this day,
because every word of it is wrong about what happened: the signature was fine, the secret was fine,
the sender was genuine. The endpoint hashed something the vendor never sent.

Two properties make this expensive to debug:

**It fails closed and it fails totally.** Not some requests — all of them. So it looks like a
configuration problem, and configuration is where everybody looks first.

**Your own tests pass.** If the test signs a body created with `json.dumps` at default settings,
then the test's bytes *are* the reparsed bytes, and both sides match. The test suite is green and
production refuses everything, which is part
[2.3](2.3-checked-against-the-vendor.md)'s point arriving from a different direction.

The tell, once you know it, is quick: print `len(raw)` and `len(json.dumps(json.loads(raw)))`. If
they differ, you have found it in under a minute.

There is one more variant worth knowing because it fails the *other* way. Some frameworks let you
read the body as `str` rather than `bytes`, decoding it for you. For ASCII payloads that round-trips
fine and everything works — until a message contains an emoji, and then encoding it back produces
different bytes for that one message. A verifier with that bug refuses roughly the messages a chat
integration exists to receive, and only those.

## In production

**What a professional does.** Reads the raw body as the first statement of the handler, verifies,
and parses afterwards — and treats "the framework will hand me the parsed object" as the thing to
resist on this one route. In FastAPI that means the handler signature takes `Request`, not a model,
and the Pydantic validation happens by hand after the check.

**What degrades at scale.** Reading the whole body into memory before doing anything is fine at
chat-message sizes and becomes a decision at large payloads. Signature schemes that anticipate this
sign a *hash* of the body rather than the body, so a receiver can stream and hash simultaneously.
Knowing which kind of scheme you are implementing is the difference between a small buffer and an
unbounded one, and an unbounded one on a public endpoint is a way to be knocked over.

**The failure that only shows with real traffic.** An intermediary that rewrites the body. Some
proxies normalise JSON, some compress, some strip a trailing newline. Every signature then fails,
your code is correct, and the vector from part [2.3](2.3-checked-against-the-vendor.md) is what
tells you so — green vector plus failing traffic means the bytes changed in transit.

**The review comment a senior engineer leaves:** *"This handler takes `Request` and not a model, and
that is deliberate. Put a comment saying so, because it is the only route in the codebase like that
and somebody will 'fix' it."*

**The interview question:** *"Your webhook verification rejects every request from the vendor. Where
do you look?"* The answer that shows experience does not start with the secret. It compares the
length of the raw body with the length of the body after a parse-and-dump round trip, because that
single comparison separates the two whole families of cause.
