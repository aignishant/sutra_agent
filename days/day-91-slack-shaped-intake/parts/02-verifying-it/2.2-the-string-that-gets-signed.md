# 2.2 — The string that gets signed

## One-line answer

The signature is an HMAC-SHA256 over one exact string — a version marker, the timestamp and the raw
body, joined by colons — and every part of that sentence is load-bearing, because the same three
values assembled any other way produce a digest that is correct and useless.

## The story

The combination lock where the same three numbers open nothing.

Twelve, thirty-one, seven. You know all three. You are certain of all three. And the lock does not
open, because the numbers go in as seven, twelve, thirty-one, and knowing the set is not knowing the
combination.

There is nothing to work out here and no cleverness available. The mechanism does not care that you
have the right information; it cares that you present it in the one order it was built around. A
person standing there with all three numbers and the wrong order is in exactly the same position as
a person with no numbers at all.

## The idea in plain language

**HMAC** is a way of proving that a message came from somebody who knows a shared secret. You take
the message, mix it with the secret in a specific way, run a hash function over the result, and send
the output alongside the message. The receiver, who knows the same secret, does the same arithmetic
and compares. Anyone who does not know the secret cannot produce the output, and the output does not
reveal the secret.

**SHA-256** is the hash function: any input, a fixed-size output, and no practical way to work
backwards or to find two inputs that collide.

What makes this a real engineering problem rather than a library call is the word *message*. HMAC
signs a byte string. It does not sign "the request" — a request is a structure with a URL, headers
and a body, and somebody had to decide which of those the signature covers and in what order they
are laid out.

For this vendor, verified from their own documentation on 2026-09-07, the decision is:

```text
v0:<timestamp>:<raw request body>
```

Three fields, colon-delimited. Then HMAC-SHA256 with the signing secret as the key, take the hex
digest, and prefix it with `v0=` to make the header value.

Each of the three earns its place:

- **`v0`** is a version marker. It exists so the scheme can change without every receiver breaking
  at once — a receiver can be taught `v1` while still accepting `v0`. It is inside the signed string
  as well as on the header, so an attacker cannot downgrade the version by editing the header alone.
- **The timestamp** is what makes the signature perishable. It appears in the header *and* in the
  signed string, so it cannot be edited without invalidating the digest. Part
  [3.1](../03-three-ways-it-goes-wrong/3.1-the-signature-that-never-expires.md) is what it is for.
- **The raw body** is the message itself, exactly as it arrived on the wire. Part
  [2.4](2.4-the-bytes-that-arrived.md) is about how easy it is to lose that word *raw*.

The delimiter is a colon, and the reason it is worth naming is that it is chosen to be a character
that cannot appear ambiguously across the join — the timestamp is digits, so there is exactly one
way to read `v0:1531420618:{...}` back into three fields.

## Why Sutra needs it

Because this is the first cryptographic check this repository performs on inbound data, and it is
the pattern every other one follows. Day 89's signed agent cards and Day 90's registry are the same
shape: assemble a defined byte string, run a keyed hash, compare in constant time.

And because the failure mode is silent and total. A verifier that assembles the string slightly
wrong — wrong delimiter, wrong order, body read after parsing — produces a digest that never matches
anything. In development you will see refusals and reach for the debugger. In production, if you get
it wrong in the *other* direction and skip a field, you have a check that passes and proves less
than you think.

## The mechanism

The base string, built exactly once, in one function:

```python
def base_string(timestamp: str, raw_body: bytes) -> bytes:
    """The three fields the signature covers, joined by colons, exactly as documented."""
    return b"%s:%s:%s" % (VERSION.encode(), timestamp.encode(), raw_body)
```

**Line by line:**

- The return type is `bytes`, not `str`, and the whole function works in bytes. HMAC signs bytes, and
  the body arrives as bytes; converting to `str` and back means picking an encoding, and a wrong
  guess corrupts any message containing a character outside it. A chat message is exactly where an
  emoji or a non-Latin script shows up.
- `b"%s:%s:%s" %` — percent-formatting works on `bytes` and f-strings do not. That is a small Python
  fact with a large consequence here: the natural way to write this line does not compile, and the
  natural fix is to decode the body, which is the bug.
- `VERSION.encode()` rather than a literal `b"v0"`, so the constant is defined once beside the
  header names it belongs with.
- One function, used by both the signer and the verifier. That matters more than it looks: if the
  two sides assembled the string separately, a change to one would produce a mismatch that looks
  like an attack.

And the signature itself:

```python
def sign(raw_body: bytes, timestamp: str, secret: str = SIGNING_SECRET) -> str:
    """The header value the vendor would send for this exact body at this exact timestamp."""
    digest = hmac.new(secret.encode(), base_string(timestamp, raw_body), hashlib.sha256).hexdigest()
    return f"{VERSION}={digest}"
```

**Line by line:**

- `hmac.new(key, msg, digestmod)` — the argument order is key first, and getting it backwards
  produces a perfectly valid digest of the wrong thing. There is no error; there is a number that
  never matches.
- `hashlib.sha256` is passed as the function, not called. Passing `hashlib.sha256()` — an instance —
  is a common slip that raises, which is the good outcome.
- `.hexdigest()` rather than `.digest()`, because the header carries hex characters. A raw-bytes
  comparison against a hex string fails for a reason that has nothing to do with the secret.
- `f"{VERSION}={digest}"` — the header value is `v0=` plus the hex, so the prefix appears with an
  equals sign in the header and with a colon inside the signed string. Two separators, two places,
  and mixing them up is a genuinely easy mistake.
- The default argument on `secret` is a convenience for a lab where every script signs with the same
  fixture secret. In `sutra/intake.py` it must not have a default — the build brief says the secret
  comes from the environment, and a default is how a fixture secret reaches production.

## When it breaks

It breaks by producing a digest, always. That is the character of this failure: there is no
exception, no warning, and no partial credit. Assemble the string with a comma instead of a colon
and you get sixty-four hex characters that are wrong in the same way that a random number is wrong.

Which means the debugging question is never "why did the hash fail" — hashes do not fail. It is
**"which of the three fields is not what I think it is"**, and there are only three, so the check is
to print each one's length and first bytes before hashing:

```bash
cd days/day-91-slack-shaped-intake/lab
uv run python vector.py | head -6
```

**Line by line:**

- `head -6` for the three inputs; the digests are part [2.3](2.3-checked-against-the-vendor.md)'s
  subject.

Measured on 2026-09-07:

```text
the vendor's documented example
  timestamp:      1531420618
  body:           362 bytes
  base string:    376 bytes, starts 'v0:1531420618:to'
```

362 and 376. The difference is fourteen: `v0` is two, the timestamp is ten, and the two colons are
two. Anyone who has assembled the string correctly can do that arithmetic in their head, and it is
the fastest check available — if your base string is not exactly fourteen bytes longer than your
body, you have the wrong string and no amount of staring at the secret will help.

## In production

**What a professional does.** Writes the base-string assembly once, in a function with a docstring
naming the documentation page and the date it was read, and never inlines it. Every signature scheme
has this shape and every one of them defines the canonical string differently — some include the
method and path, some include selected headers, some include a hash of the body rather than the body
— and the differences are invisible at the call site.

**What degrades at scale.** Version markers earn their keep. `v0` looks like ceremony until the day
a vendor ships `v1` with the path included, and receivers have to accept both for a migration
window. A verifier that ignores the prefix and just compares digests cannot participate in that
migration, and finds out on the day the old scheme is switched off.

**The failure that only shows with real traffic.** A body that is not ASCII. Every fixture in this
lab is, and a verifier that decodes to `str` somewhere in the middle will pass every test here and
fail on the first message containing an emoji — which, on a chat integration, is roughly the first
message. The mitigation is the type annotation: keep it `bytes` end to end, and the failure becomes
impossible rather than untested.

**The review comment a senior engineer leaves:** *"Put the documentation URL and the date you read
it in the docstring of `base_string`. When this breaks in two years it will be because the scheme
changed, and the first question will be which version we implemented."*

**The interview question:** *"Walk me through verifying a webhook signature."* The answer that shows
experience spends its time on the canonical string — which fields, in what order, with what
delimiter, and where the version marker lives — because that is where the bugs are. The HMAC call is
one line and nobody gets it wrong.
