# 2.1 — The three things a vendor sends

## One-line answer

A chat intake receives exactly three kinds of thing — a one-time handshake proving you control the
URL, ordinary events, and retries of events you did not acknowledge — and the endpoint has to answer
all three correctly before any of it reaches an agent.

## The story

The courier who will not hand over the package without a code.

He is standing at the door with the box. You can see it. He can see you. And he will not give it to
you until you read out four digits that were sent to the phone number on the order.

The first time this happens it is faintly insulting — you are *obviously* the person who lives here.
Then you think about it from his side. He has never met you. The address on the box is the only
thing connecting you to it, and an address is a fact anybody can know. The four digits are the only
part of the exchange that proves you are the person the order was placed by, rather than somebody
who happened to be standing in a doorway.

He is not checking whether you are trustworthy. He is checking whether this delivery is the one he
was sent to make.

## The idea in plain language

An intake endpoint is a URL you give to somebody else's system so it can post to you. That single
sentence contains the whole security problem: the URL is on the public internet, anybody can post to
it, and nothing about a POST arriving says who sent it.

So the vendor signs. And before it will send anything at all, it checks that you control the URL you
gave it. The traffic that arrives falls into three kinds:

**The handshake.** Once, when the URL is first saved, the vendor posts a payload of type
`url_verification` containing a random `challenge` string, and expects it echoed straight back. It
proves you own the endpoint — that somebody has not typed your URL into *their* app's settings and
pointed a stranger's events at you.

**Events.** The ordinary traffic. A JSON envelope with `type: "event_callback"`, an `event` object
inside it describing what happened, and identifiers for the workspace, the app and the event itself.
This is the one that reaches an agent.

**Retries.** If the endpoint does not answer quickly, the vendor assumes delivery failed and sends
the same event again. That makes the endpoint's contract *acknowledge first, work afterwards* — and
it makes duplicate delivery normal rather than exceptional, which is Day 73's idempotence problem
arriving through a new door.

Everything in this section is about the second and third of those, because the first is four lines
and the interesting question is what you do *before* you trust the payload enough to read it.

## Why Sutra needs it

Because this is the desk's first inbound door from a system this repository does not run. Day 85's
API surface was reachable by anyone who could route to it, and the answer there was *bind it
somewhere private*. That answer is unavailable here by construction: a chat vendor's servers must be
able to reach this URL, so it is public, and the only thing standing between the public internet and
the desk is the signature check.

And because a message arriving here is untrusted text on its way to a model. Part
[3.3](../03-three-ways-it-goes-wrong/3.3-signed-is-not-safe.md) is that argument in full, and it
starts from the fact established here: the signature answers exactly one question, and it is not
*"is this message safe?"*.

## The mechanism

The endpoint reads the raw body first and asks every question in order:

```python
    @app.post("/intake")
    async def intake(request: Request) -> Response:
        raw = await request.body()
        timestamp = request.headers.get(TIMESTAMP_HEADER, "")
        supplied = request.headers.get(SIGNATURE_HEADER, "")
```

**Line by line:**

- `await request.body()` returns `bytes`, and it is the first line of the handler for a reason
  developed in part [2.4](2.4-the-bytes-that-arrived.md): the signature covers those exact bytes, so
  anything that reads the body as parsed JSON first has already lost the thing it needs.
- `request.headers.get(..., "")` with a default rather than indexing. A missing header is a request
  to refuse, not a `KeyError` that becomes a `500` — and a `500` on a malformed request tells the
  sender your endpoint is fragile, which is information you did not mean to give.
- The header names are constants from `_events.py` rather than literals, because the vendor's own
  documentation warns that header names are case-insensitive and the case should not be assumed.
  Starlette's `request.headers` is already case-insensitive, which is why this works — that is a
  property of the framework, not of the code, and it is worth knowing it is doing that for you.

Then the handshake, answered before anything reaches the desk:

```python
        if payload.get("type") == "url_verification":
            return Response(
                status_code=200,
                media_type="application/json",
                content=json.dumps({"challenge": payload["challenge"]}),
            )
```

**Line by line:**

- `.get("type")` rather than `payload["type"]`. This runs after the signature check, so the payload
  is authentic — and authentic is not the same as well-formed, and a vendor is allowed to add a
  message type you have never seen.
- The challenge is echoed and **nothing else happens**: no session, no agent, no record. The
  handshake is not a message and must not become one.
- This branch sits *after* verification. Putting it before — which is tempting, because during
  setup the handshake is the one request you are trying to make succeed — creates an unauthenticated
  endpoint that will echo any string you post to it.

Run it:

```bash
cd days/day-91-slack-shaped-intake/lab
uv run python intake.py; echo "exit: $?"
```

**Line by line:**

- No flag: both payloads signed correctly, as the vendor would send them.

Measured on 2026-09-07:

```text
signature header: sent

  payload              status  what came back
  url_verification        200  {"challenge": "3eZbrw1aBm2rZgRNFdxV2595E9CY...
  app_mention             200  ok

  reached the desk: 1
  refused:          0  []

  the handshake was answered and the mention reached the desk
```

**Two requests, two `200`s, and only one of them reached the desk.** That asymmetry is the design:
the handshake is answered by the endpoint itself and stops there.

## When it breaks

Take the signature away and everything still has the right shape — same URL, same JSON, same
handler — and nothing gets in:

```bash
uv run python intake.py --unsigned; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  payload              status  what came back
  url_verification        401  bad signature
  app_mention             401  bad signature

  reached the desk: 0
  refused:          2  ['bad signature']
```

Note that the **handshake is refused too**, and that is correct and counter-intuitive enough to be
worth sitting with. During setup, the handshake is the request you are desperately trying to make
succeed, the vendor's console is showing a red cross, and the fastest way to a green tick is to move
the `url_verification` branch above the signature check.

Do that and you have shipped an endpoint that will echo any string any stranger posts to it. It will
also pass the vendor's setup check, permanently, so nothing will ever remind you.

The failure mode of the third kind of traffic — retries — has no error text at all, because it is
not an error. The vendor's contract is that a slow answer means a failed delivery, so an endpoint
that calls a model before acknowledging will be sent the same message again while it is still
thinking about the first copy. The desk then does the work twice. Day 73 part 4.2's idempotence
argument is the fix, and the shape of it here is: acknowledge immediately, queue the work, and make
the work idempotent on the vendor's own `event_id`.

That is left as a `TODO(me)` in the hub rather than built, because a queue is a Phase 8 mechanism and
this day's subject is the door.

## In production

**What a professional does.** Answers within the vendor's timeout, always, by making the handler do
nothing except verify, enqueue and return. Every intake that has ever been written the other way —
verify, call the model, return the answer — works perfectly in testing, because a test message gets
a fast answer, and degrades into duplicate work exactly when the system is slow, which is exactly
when duplicate work hurts most.

**What degrades at scale.** Retries compound. One slow model call produces a retry, the retry
produces a second slow model call, and both of them are now competing for the same quota. Day 78's
allowance arithmetic is what decides whether that spiral is survivable, and the answer for a
free-tier lane is that it is not.

**The failure that only shows with real traffic.** An event type you have never seen. Vendors add
them, and a handler written as `if type == "url_verification": ... else: treat as a message` will
route a workspace administration event into an agent as though it were something a person said. The
mitigation is an allowlist of event types rather than an else branch — which is Day 40's filtering
argument, applied to an envelope instead of a tool call.

**The review comment a senior engineer leaves:** *"The handshake branch is below the signature check
and it must stay there. Put a comment on it saying why, because the next person to set this up in a
new workspace is going to want to move it."*

**The interview question:** *"How does your webhook endpoint know the request is really from the
vendor?"* The answer that shows experience names the signature, and then — the half most people miss
— says what the signature does *not* establish: not that the message is safe, not that it is fresh,
and not that it has not been sent before.
