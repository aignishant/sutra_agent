# 2.3 — Checked against the vendor, not against a belief

## One-line answer

A verifier you wrote and a signer you wrote will always agree with each other, whatever they both
get wrong — so the only test worth anything is against the vendor's own published example, and this
one reproduces its digest to all sixty-four characters.

## The story

The worked example at the back of the textbook.

You have done the problem. You have an answer, and it is a clean number, and the working looks
right. Then you turn to the back and the book says something else.

The value of that page is not that it teaches you anything — it contains no method and no
explanation. Its value is that it was produced by somebody who is not you, before you started, and
it cannot be talked into agreeing with your arithmetic. Everything else you could check your answer
against is downstream of the same misunderstanding that produced it.

The student who works the problem twice and gets the same answer twice has learned that they are
consistent.

## The idea in plain language

Here is the trap this part exists to name, and it catches experienced people because it looks like
testing.

You write `sign()`. You write `verify()`. You write a test: sign a body, verify it, assert it passes.
The test is green. You ship.

The test proves that your two functions agree. It cannot prove that either one implements the
vendor's scheme, because both were written by the same person from the same reading of the same
page. Get the delimiter wrong in `base_string` and both sides get it wrong identically, and every
test you own stays green while nothing the vendor ever sends will verify.

This is not a hypothetical class of bug. It is the *default* outcome of writing a signature verifier
from prose, and it is invisible until the first real request arrives.

The fix is a **test vector**: an input and its expected output, produced by the other side. This
vendor publishes one on the same page as the algorithm — a signing secret, a timestamp, a request
body and the hex digest they compute from them. Four values, and together they are the only thing in
the loop that your own misunderstanding cannot have produced.

## Why Sutra needs it

Because nothing else in this repository can check this. The lab has no network, there is no
workspace, and no real signed request will ever arrive during this day. The vendor's worked example
is, quite literally, the only independent evidence available at zero cost.

And because Phase 14 has two more days of cryptographic checks in it. Day 89 verifies signed agent
cards; Day 92 reviews the lot before the repository goes public. A habit of testing signature code
against vectors rather than against itself is the thing being installed here, and the signature
scheme is just where it happened to get installed.

## The mechanism

The vendor's example, copied field by field into a frozen record:

```python
DOC_EXAMPLE = Example(
    secret=SIGNING_SECRET,
    timestamp="1531420618",
    body=(
        "token=xyzz0WbapA4vBCDEFasx0q6G&team_id=T1DC2JH3J&team_domain=testteamnow"
        "&channel_id=G8PSS9T3V&channel_name=foobar&user_id=U2CERLKJA&user_name=roadrunner"
        "&command=%2Fwebhook-collect&text=&response_url=https%3A%2F%2Fhooks.slack.com%2F"
        "commands%2FT1DC2JH3J%2F397700885554%2F96rGlfmibIGlgcZRskXaIFfN"
        "&trigger_id=398738663015.47445629121.803a0bc887a14d10d2c447fce8b6703c"
    ),
    digest="a2114d57b48eac39b9ad189dd8316235a7b4a8d21a10bd27519666489c69b503",
)
```

**Line by line:**

- The body is form-encoded, not JSON. That is the vendor's own example and it is worth not
  "improving": the scheme signs bytes and does not care what they mean, and a vector using a
  different content type than your traffic is *stronger* evidence, because it cannot accidentally
  agree with an assumption about JSON.
- It is split across string literals with no separators between them — adjacent literals concatenate
  in Python, so this is one string with no added whitespace. Getting that wrong by putting a comma
  between the lines makes it a tuple, and the failure is loud.
- `%2F` and `%3A` are percent-encoded slashes and colons, left exactly as the vendor wrote them.
  Decoding them "to be tidy" changes the bytes and therefore the digest.
- The secret is the vendor's documentation example, which is why it can sit in a tracked file. A
  real one is an environment variable (Principle 9), and part
  [4.2](../04-blast-radius/4.2-the-secret-itself.md) is about what happens when that slips.
- `frozen=True` on the dataclass: a test vector that code can modify is not a test vector.

The check recomputes and compares:

```python
    base = base_string(DOC_EXAMPLE.timestamp, body.encode())
    ours = hmac.new(DOC_EXAMPLE.secret.encode(), base, hashlib.sha256).hexdigest()
```

**Line by line:**

- It calls the same `base_string` the endpoint uses. A vector that exercises a separate copy of the
  assembly logic tests the copy.
- `hmac.new(...)` is spelled out here rather than calling `sign()`, so the comparison is against the
  raw hex digest the documentation publishes, not against the `v0=`-prefixed header value. Those are
  different strings and confusing them is a five-minute detour.

Run it:

```bash
cd days/day-91-slack-shaped-intake/lab
uv run python vector.py; echo "exit: $?"
```

**Line by line:**

- No flag: our digest against theirs.

Measured on 2026-09-07:

```text
the vendor's documented example
  timestamp:      1531420618
  body:           362 bytes
  base string:    376 bytes, starts 'v0:1531420618:to'

  documented:     a2114d57b48eac39b9ad189dd8316235a7b4a8d21a10bd27519666489c69b503
  ours:           a2114d57b48eac39b9ad189dd8316235a7b4a8d21a10bd27519666489c69b503

  identical: the implementation agrees with the vendor's own worked example
exit: 0
```

**Sixty-four characters, all of them.** That is the strongest statement available about this
implementation at zero cost, and it is a statement no test of `sign()` against `verify()` could have
made.

## When it breaks

Change one character of the body and the digest is unrecognisable:

```bash
uv run python vector.py --tamper; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  documented:     a2114d57b48eac39b9ad189dd8316235a7b4a8d21a10bd27519666489c69b503
  ours:           3303844103122b1230487687d1bd08b6a76968df6a90232ccd409c137a4e3119

  56 of 64 hex characters differ
  the signature does not survive a one-character change to the body
exit: 1
```

One character in a channel id — `G8PSS9T3V` to `G8PSS9T3W` — and **fifty-six of sixty-four** hex
characters change. That is the avalanche property doing its job, and it is why "the signature nearly
matched" is not a sentence anybody ever says.

The eight characters that happen to coincide are coincidence, not partial credit. Sixteen values per
position, sixty-four positions: a handful of accidental matches is exactly what chance predicts, and
reading them as "we are close" is the misunderstanding this output is designed to prevent.

**The failure this check cannot catch** is a vendor whose documentation example is wrong or stale.
It happens, and when it does you get a red vector and correct code. The tell is that real traffic
verifies and the vector does not, which is why a vector is a starting point and the first real
signed request is the confirmation. That request has not happened here and is a `TODO(me)` in the
hub, marked as needing an account rather than budget.

## In production

**What a professional does.** Keeps the vector as a permanent test, not a one-off script. It costs
nothing to run, it never flakes, and it is the check that catches a well-meaning refactor of the
base-string assembly — which is the change most likely to break this and least likely to look
dangerous in review.

**What degrades at scale.** One vendor's vector becomes five vendors' vectors, and they will not
share a shape: different canonical strings, different digest encodings, some signing headers as
well as the body. The temptation is a generic `verify(vendor, request)` with the differences in
configuration, and it is usually wrong — this is part [1.1](../01-what-an-integration-is/1.1-somebody-elses-shape.md)'s
argument again, and the decision that varies is the whole algorithm rather than a parameter of it.

**The failure that only shows with real traffic.** A proxy that rewrites the body. Compression,
charset normalisation, a load balancer that re-serialises JSON — any of them and every signature
fails at once, with the vector still green, which is genuinely useful information: green vector plus
failing traffic means the bytes changed in transit, and that is a different investigation from a
wrong implementation.

**The review comment a senior engineer leaves:** *"Move this out of a script and into
`tests/test_intake.py`. It is the only test in the file that is testing us against somebody else,
and it is the one I would keep if I could keep only one."*

**The interview question:** *"Your signature verification has full test coverage. What might still
be wrong?"* The answer that shows experience is that the tests may only prove the signer and
verifier agree — and then asks for a vector from the other side, which is the question the
interviewer was waiting for.
