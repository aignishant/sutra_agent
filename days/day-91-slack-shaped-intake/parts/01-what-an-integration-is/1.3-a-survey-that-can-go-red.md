# 1.3 — A survey that can go red

## One-line answer

A survey is a set of claims, so every row that says *built* has to name a path and the check is
that the path exists — which turns a document that quietly ages into one that fails a build, and
takes five lines to write.

## The story

The notice board at the entrance, listing services.

Eleven of them, painted on, with counter numbers. Passport renewal, counter four. Birth
certificates, counter six. Pension verification, counter nine.

Counters six and nine have not been staffed in two years. That work moved online, or to another
office, or simply stopped. The board is still perfect — the paint is fine, the lettering is neat,
the numbering is consistent. It is just no longer a description of the building.

And it is worse than no board at all, because a board is believed. Somebody joins the queue at
counter nine on the strength of it.

## The idea in plain language

Principle 11 says an eval is something that can go RED. That principle is usually pointed at code.
It applies at least as hard to documents, and a survey is the clearest case: it is a table of
claims about a repository, written once, read for years.

The trick is to find, for each kind of claim, something checkable that stands in for it. For this
survey:

- A row marked **built** claims something exists. Make it name the thing, and check the path is
  there. That is one `Path.exists()` per row.
- A row marked **🅿️ requires budget** claims something is *not* built, and that is not checkable by
  looking — an absence is not evidence. What it can carry instead is a sentence naming what is
  missing, so a reader can tell "we decided not to" from "we forgot".

Those are different strengths of check and the difference is worth being honest about. The first is
a test. The second is a discipline, and it holds only as long as somebody writes the sentence.

What this buys is not correctness on the day it is written — it is correct on the day it is written
by construction, because the author just looked. What it buys is the day eighteen months later when
somebody deletes `sutra_mcp/` during a reorganisation and a check nobody remembers goes red and
says: the survey said this existed.

## Why Sutra needs it

Because Phase 14's gate is *"A2A peer verified; repo public"*, and this survey is going into a
public repository in two days. Every row is a claim a stranger will read as a capability.

And because this repository has been round this loop before. Day 83's gate found four instruments
whose claims nobody had checked, and its part 1.3 established the rule this part applies to prose:
**green is not evidence.** A survey with ten confident rows and no check is exactly the shape that
day was about, in a different file format.

## The mechanism

The whole check is one branch per row:

```python
    for surface in rows:
        if surface.status == BUILT:
            present = (ROOT / surface.evidence).exists()
            mark = "yes" if present else "NO SUCH PATH"
            if not present:
                unproven.append(surface)
        else:
            mark = f"n/a - needs {surface.evidence}"
```

**Line by line:**

- `ROOT / surface.evidence` — the path is stored relative to the repository root, not to the lab, so
  a row can point at `sutra_mcp/` or at another day's file. `ROOT` is computed with
  `Path(__file__).resolve().parents[3]`, which is the same walk-up the other days' repository checks
  use.
- `.exists()` rather than `.is_file()`, because two of the four rows point at a package directory
  and one points at a module file. Being permissive here is deliberate: the claim is "there is
  something behind this row", not "there is a file".
- The `else` branch does not check anything, and says so in its output with `n/a`. That is the
  honest rendering of an unverifiable claim, and it matters that the report distinguishes it from a
  pass — Day 88's checker found the same shape and gave it a third outcome for the same reason.
- `unproven` collects rows rather than counting them, so the failure can name the row and the
  missing path. A count sends nobody anywhere.

And the verdict:

```python
    if unproven:
        for surface in unproven:
            print(f"    - {surface.name}: claimed built, {surface.evidence} is not there")
        print("\n  a survey that claims more than the repository contains is a wish list")
        return 1
```

**Line by line:**

- Every unproven row is named, not just the first. A tidy-up that removed two things should report
  two lines.
- `return 1` puts the verdict in the exit code, so this can sit in the same gate as everything else.
  Day 82 part 3.3 is why that matters: a finding printed on stdout and not encoded in an exit code
  is a finding a scheduler discards.

## When it breaks

Point the check at a claim it cannot see, and it passes while the claim rots. That is the ablation,
and it is what `--optimistic` demonstrates by marking every row `built`:

```bash
cd days/day-91-slack-shaped-intake/lab
uv run python survey.py --optimistic | tail -10; echo "exit: ${PIPESTATUS[0]}"
```

**Line by line:**

- `--optimistic` changes only the `status` field, which is exactly the edit an enthusiastic
  contributor makes to a roadmap.

Measured on 2026-09-07:

```text
    - chat intake (live workspace): claimed built, a workspace and a public HTTPS URL is not there
    - email intake: claimed built, a mailbox and an app password is not there
    - ticketing platform: claimed built, a paid plan and an API token is not there
    - SMS or messaging gateway: claimed built, per-message billing is not there
    - voice telephony: claimed built, per-minute billing is not there
    - managed agent platform: claimed built, an enabled billing account (day 87) is not there

  a survey that claims more than the repository contains is a wish list
exit: 1
```

Six rows caught. Notice what the failure message reads like: *claimed built, a paid plan and an API
token is not there*. That is the `evidence` field's double meaning from part
[1.2](1.2-the-ways-in.md) showing through in the output — the sentence is grammatically odd because
the field is holding two different kinds of thing.

That is a real flaw in the check and worth naming rather than smoothing over. The clean version has
two fields — `path` for built rows and `missing` for parked ones — and the awkward sentence is the
type telling you so.

**The failure the check cannot see** is a row that names a path which exists and does not do what
the row says. `sutra_mcp/` exists; whether it is a working MCP server is not something `Path.exists`
can answer. A stronger version runs the thing rather than looking for it, and the honest description
of what is implemented here is *the weakest check that is still better than nothing* — which is a
real category, and is how most documentation checks start.

## In production

**What a professional does.** Attaches every claim in a document to something executable, and
accepts that most of those attachments will be weak. A link checker does not verify that the linked
page is correct; it verifies that it is there. A survey checker does not verify that an integration
works; it verifies that the thing it names exists. Both catch the failure that actually happens,
which is deletion and rename, not subtle wrongness.

**What degrades at scale.** Ten rows check instantly. A hundred rows pointing at a hundred paths is
still instant, but the maintenance cost moves to the rows themselves — every rename now edits two
places, and a check that makes routine refactoring annoying is a check somebody deletes. That is the
point at which the evidence stops being a path and becomes a test id or a module import.

**The failure that only shows with real traffic.** The survey and the README drift apart. Both list
integrations; only one is checked. A reader trusts whichever they found first, and the public README
is always the one they found first — which is why part
[5.2](../05-in-production/5.2-what-a-real-integration-layer-adds.md) puts *generate the README table
from the survey* on the list rather than *keep them in step*.

**The review comment a senior engineer leaves:** *"Split `evidence` into `path` and `missing`. Right
now the failure message reads like broken English because one field is doing two jobs, and that is
the type telling us something."*

**The interview question:** *"How do you stop documentation going stale?"* The answer that shows
experience does not say review cadence. It picks the claims that can be attached to something a
build already runs, attaches those, and is explicit that the rest are maintained by discipline —
because pretending otherwise is how a review cadence becomes a rubber stamp.
