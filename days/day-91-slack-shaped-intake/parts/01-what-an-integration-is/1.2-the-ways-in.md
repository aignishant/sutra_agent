# 1.2 — The ways in, and what each one costs

## One-line answer

Ten ways something outside this repository could reach the desk, and the useful column is not
"how hard is it to build" but **what it can see and what it can do** — because four of the ten are
already built, two need an account, and four need a billing account and are therefore parked.

## The story

The letterbox with a slot too narrow for parcels.

It takes letters perfectly. It has taken letters for thirty years. And because it exists and works,
nobody in the house ever thought of it as a *decision* — until the day a parcel came, and the
courier stood outside holding something that would not go through, and the whole arrangement had to
be reconsidered on the doorstep.

The slot was never neutral. It quietly decided, for three decades, what kind of thing could arrive
without somebody being home. That was mostly a good decision. It was still a decision, and nobody
made it on purpose.

## The idea in plain language

Every channel into a system is a slot. It admits some shapes and not others, it admits them from
some senders and not others, and once it exists it decides — quietly, for years — what can reach you
without anybody being asked.

So a survey of integrations is not a shopping list. It is three questions per row:

**What can it see?** A chat intake sees one channel's messages. An HTTP API sees whatever the caller
chooses to send. A ticketing integration sees every ticket in the project, including the ones nobody
meant to share with an agent.

**What can it do?** Not what you plan to let it do — what the connection makes possible. A chat bot
that can call desk tools can do everything the desk can do, and Day 68's least-privilege work is
about the gap between those two sentences.

**What does it cost?** Not effort. Money and accounts. This repository runs on Principle 15, so an
integration that needs a paid plan is not a harder task, it is a **different category**: parked,
mapped, understood, not built.

That last split is what turns a survey into a decision. The ten rows below sort into four that exist
today, two that need an account somebody must create, and four that need a billing account and are
therefore 🅿️ for the whole of this curriculum.

## Why Sutra needs it

Because the plan's assignment for this day is the word *survey*, and a survey written as prose is
a paragraph nobody checks. The version in `lab/survey.py` is a table with a rule attached, and part
[1.3](1.3-a-survey-that-can-go-red.md) is the rule.

And because Phase 14 ends with the repository going public. A public repository that lists ten
integrations has made ten claims about what this system can do, and every one of them will be read
as a promise by somebody deciding whether to depend on it.

## The mechanism

Each row is a small record with the three questions as fields:

```python
@dataclass(frozen=True)
class Surface:
    name: str
    sees: str
    can_do: str
    status: str
    evidence: str  # a path, for `built`; what is missing, otherwise
```

**Line by line:**

- `sees` and `can_do` are separate fields because they answer different questions and people
  routinely give one answer for both. A read-only ticketing token *sees* every ticket and *can do*
  nothing, and that is a completely different risk from the reverse.
- `status` is one of four values, not a boolean. "Built", "buildable", "needs an account", "needs
  budget" are four different conversations, and collapsing them to done/not-done is what makes a
  roadmap useless.
- `evidence` carries two different meanings depending on `status`, which is a small dishonesty in
  the type and is called out in part [1.3](1.3-a-survey-that-can-go-red.md) — for a built row it is
  a path that must exist, and for a parked row it is a sentence naming what is missing.
- `frozen=True` so the survey cannot be edited by the code that reports it. A survey that a report
  can rewrite is a report.

**Four built, two blocked on an account, four blocked on money.** Read the first four together and a
pattern falls out: every one of them is a channel where *this repository owns both ends*. The moment
a third party owns the other end, the row stops being an engineering question.

And read the `sees` column for the parked rows, because it is the argument for why they are worth
mapping rather than forgetting. The ticketing row sees every ticket in the project. That is the
largest data surface in the whole survey, and it is attached to the row that costs the least effort
to enable — a token, a base URL, an afternoon. The cheapest integration to build has the widest
blast radius, and knowing that before somebody has budget is the entire point of a survey.

## When it breaks

The survey breaks by ageing, and it does it silently, because nothing in a table knows what the
repository is doing.

The specific failure has a shape: a row says `built`, the thing was built, and then it was deleted
or renamed six months later during a tidy-up. Nobody edits the survey, because nobody remembers the
survey exists. The document keeps making a claim that stopped being true.

There is no error text. That is precisely why part [1.3](1.3-a-survey-that-can-go-red.md) exists —
the rule that a `built` row must name a path that is present turns the ageing into an exit code.

The second way it breaks is optimism about the middle category. "Requires an account" reads as
*nearly free*, and for the email row that is roughly honest. For the live chat workspace it hides
two more requirements: a public HTTPS URL, which on a laptop means a tunnel, and an application
review process for anything beyond a private workspace. Neither is money and neither is nothing, and
a row that says only "an account" has under-described the job.

## In production

**What a professional does.** Sorts integrations by data surface, not by effort, and builds the
narrowest one first. That order is usually the reverse of what is asked for, because the widest
integration is the one that demos best — connect the agent to the whole ticket system and it looks
capable immediately. It is also the one you cannot unwind after it has been running for a month.

**What degrades at scale.** The survey becomes the interface. Once a table like this is in a public
README, other teams plan against it, and a row's `status` starts carrying weight it was never
measured for. The mitigation is that the status values stay honest and ugly — `requires budget` is a
better row in a public document than a green tick with a footnote.

**The failure that only shows with real traffic.** Two integrations that are individually scoped and
jointly not. Chat intake can read one channel; the ticketing integration can read every ticket. Wire
both into the same agent and a message in the one channel can ask about any ticket, which is neither
integration's stated surface. Day 68's confused deputy, arriving through a door marked survey.

**The review comment a senior engineer leaves:** *"Sort this by the `sees` column before we agree
which to build. The one at the top is a token and an afternoon, and it is the one I would want a
security review on."*

**The interview question:** *"We want the agent in our chat tool, our ticket system and our inbox.
Where do you start?"* The answer that shows experience asks what each can see before asking what
each would cost, and then proposes the narrowest one — because the cheap wide one is the one that is
hard to take back.
