# 1.1 — An integration is somebody else's shape

## One-line answer

Every integration is a decision that somebody else owns and can change without telling you, so the
job is never "connect to the vendor" — it is to put that decision in exactly one place, and the
measurement of whether you did is how many files a rename touches.

## The story

The two-pin plug and the three-pin socket.

The appliance works. The socket works. Between them is a small white adaptor that cost almost
nothing and does nothing except change the shape of the thing on one side into the shape the other
side expects.

Nobody thinks of the adaptor as part of the appliance, and that is exactly right — it belongs to
neither. When you move house and the sockets are different, you buy a different adaptor and the
appliance is untouched. When you replace the appliance, the adaptor stays in the drawer.

The mistake, the one that makes people cut plugs off cables, is to decide that the appliance should
just *have* the right pins on it. It works, once, in that house.

## The idea in plain language

An **integration** is a connection between this system and one somebody else runs. Chat, email,
ticketing, a webhook, another agent. From the outside they all look like plumbing.

From the inside there is one thing they have in common, and it is the only thing that matters: the
shape of what arrives is a decision made by somebody who is not you, who did not ask you, and who
can change it in a release note you will not read.

That gives a rule for where the seams go, and it is not the obvious one. The obvious decomposition
of an intake is the sequence of things that happen:

```text
receive  →  verify  →  parse  →  decide  →  act  →  reply
```

Six boxes, drawn left to right, each becoming a module. It reads beautifully and it is wrong, and
the paper this day rests on explains why in one sentence: a flowchart tells you what happens *in
time*, and modules exist to contain what changes *independently*. The vendor renaming a field is one
change. In the layout above it lands in every box that touches the payload, which is most of them.

The alternative is to name the decision — *this vendor's payload shape* — and give it a module of
its own whose whole job is to hold it. Everything downstream then works on a shape this repository
defines and controls.

That is the adaptor in the drawer. It belongs to neither side, it is the cheapest thing in the
system, and it is the reason a vendor's release is a small edit instead of an afternoon.

## Why Sutra needs it

Because Phase 14 is where the desk stops being something you run and starts being something other
systems talk to. Day 89 gave it a protocol peer and Day 90 gave it an identity; today it gets an
inbound door that a chat platform posts to, and the platform's payload is the first shape in this
repository that this repository does not define.

And because the survey in part [1.2](1.2-the-ways-in.md) lists ten ways in. If each one is wired
directly into the desk, ten vendors own ten decisions inside the code that does the work. If each
one gets an adaptor, the desk has one inbound shape and ten small files that translate into it.

## The paper behind it

> **On the criteria to be used in decomposing systems into modules**
> Communications of the ACM, volume 15, issue 12, 1972, pp. 1053–1058.
> `doi:10.1145/361598.361623`

The claim: a module should be built around a **design decision that is likely to change**, and the
decision should be hidden from every other module. Decomposing by the steps of a flowchart looks
natural and distributes each changeable decision across all of them.

Read it after the parts: [The module that owns the vendor](../../papers/01-the-module-that-owns-the-vendor.md).

## The mechanism

The two decompositions, written out as real code in `lab/papers/modules/`, and then measured rather
than argued about. First the flowchart one — a module per step:

```python
def authorize(event: dict) -> str:
    """Step two: decide whether this sender may ask for anything."""
    sender = event["user"]
    if sender not in ALLOWED:
        raise PermissionError(sender)
    return sender
```

**Line by line:**

- `event: dict` — the module's input is the vendor's object. That single type annotation is the
  whole problem in miniature: the parameter is not "a message", it is "whatever the vendor posted".
- `event["user"]` is a vendor decision written inside a module about permissions. The two have
  nothing to do with each other, and a rename of the first breaks the second.
- Nothing here is badly written. It is four lines, it is clear, and it is the version everybody
  writes first.

Now the same step, in the decomposition that hides the decision:

```python
def authorize(message: Message) -> str:
    if message.sender not in ALLOWED:
        raise PermissionError(message.sender)
    return message.sender
```

**Line by line:**

- `message: Message` — a type this repository owns, defined three lines away, containing four fields
  the desk actually needs.
- `message.sender` instead of `event["user"]`. Same behaviour, same length, and there is no longer a
  vendor's word anywhere in it.
- The vendor's names have not vanished. They moved into one module, `adapt`, whose entire purpose is
  to know them.

And the measurement, which is the point:

```bash
cd days/day-91-slack-shaped-intake/lab/papers/modules
uv run python demo.py; echo "exit: $?"
```

**Line by line:**

- The demo reads its own source with `ast` and counts, per module, how many of the vendor's field
  names appear in it. It is a count of what is written, not an opinion about it.

Measured on 2026-09-07:

```text
  modules that know the vendor's field names: 4 by step, 1 by hidden decision
  rewriting only `adapt` for the new payload: refunds@G8PSS9T3V re 1531420618.000200 in G8PSS9T3V
  the same answer as before: True
```

**Four modules against one.** The two implementations are the same length and produce identical
answers on the old payload. When the vendor renames four fields, one of them needs a four-line edit
and the other needs four.

## When it breaks

The rule breaks when the "decision that is likely to change" is guessed wrong, and then the adaptor
is ceremony — an extra file, an extra type, an extra hop, protecting against a change that never
comes.

There is a cheap test for that, and it is historical rather than clever: has this thing changed
before? A chat vendor's event payload has versions and migration guides, which is evidence. An
internal function you wrote last week does not, which is why wrapping it in an adaptor is the
anti-pattern in this repository's own guidelines — *no abstractions for something used once*.

The more common failure is subtler and this repository is one careless commit from it. The adaptor
exists, and then something downstream needs a field the neutral `Message` does not carry, and the
quickest fix is to pass the original payload through alongside it:

```text
Message(sender=..., words=..., place=..., at=..., raw=payload)
```

Nothing raises. The tests pass. And the vendor's shape is now reachable from every module that has a
`Message`, so the next rename touches four files again, and the adaptor is still there, still
looking like it is working.

There is no error text for that one. The check is a review question — *does anything outside `adapt`
mention `raw`?* — and part [5.2](../05-in-production/5.2-what-a-real-integration-layer-adds.md) puts
it in the build brief as a test rather than a habit.

## In production

**What a professional does.** Writes the neutral type first, before looking at any vendor's
documentation, from the question *what does the desk need in order to act?* Doing it in that order
produces a `Message` with four fields. Doing it the other way — starting from the vendor's payload
and deleting what you do not need — produces a `Message` with the vendor's field names and their
nesting, which is the same coupling with an extra file.

**What degrades at scale.** Adaptors multiply and start to disagree. Ten vendors, ten adaptors, and
two of them differ on what to do when a message has no text. The neutral type has to grow a rule for
that, and the honest place for it is the type itself rather than each adaptor, which is the moment
`Message` stops being a `dataclass` and starts being a small domain model with validation in it.

**The failure that only shows with real traffic.** A field that is optional in the documentation and
present in every message you have ever seen. The adaptor reads it directly, works for a year, and
then a message arrives without it. The mitigation is that an adaptor's job includes deciding what
absence means — a default, or a refusal — and that decision belongs in the one module that knows the
vendor, not in a `KeyError` at three in the morning.

**The review comment a senior engineer leaves:** *"Nothing outside `adapt` should mention a vendor's
field name. Add the test that greps for them — it is five lines and it is the only thing that keeps
this true after we are both off the project."*

**The interview question:** *"How do you structure an integration with a third-party API?"* The
answer that shows experience does not describe layers. It names the decision the third party owns,
says which single module holds it, and then gives the test that proves no other module has learned
it.
