# 4.1 — What a forged request reaches

## One-line answer

Principle 13 asks what a new capability can reach before asking whether it works, and the honest
answer for this endpoint is: whatever the desk can do, because a message that passes the checks is
handed to an agent with the desk's tools — so the containment has to be on the far side of the
handler, not in it.

## The story

The delivery hatch that opens onto the strongroom.

A small door at the back of a building, at waist height, so deliveries do not have to come through
the front. Sensible. It has a good lock and only the delivery firm has the key.

The problem is not the hatch and not the lock. It is that somebody, years ago, put the hatch on the
wall of the room where the valuables are kept, because that happened to be the wall facing the lane.
Every conversation about security since has been about the lock, because the lock is the part that
looks like security.

Nobody has asked the only question that matters: *once this opens, what is on the other side of it?*

## The idea in plain language

Principle 13 is **blast radius before capability**. Every new power arrives with its containment
story, and the containment story is written before the power is switched on.

So, before congratulating this endpoint on its signature check, the question is: a request that
passes every check reaches *what*?

Today, in this lab, it reaches a list. `seen.accepted` is a Python list and nothing more, which is
why this day is safe to run. In `sutra/intake.py` — the build brief — it reaches an agent, and the
agent has the desk's tools: reading tickets, checking refund limits, requesting approval, issuing
refunds.

That means the blast radius of this door is **the whole desk**, and the signature does not reduce
it. What the signature does is control *who* can open the door, which is a different axis. A
correctly verified message from a compromised account gets the full radius, as part
[3.3](../03-three-ways-it-goes-wrong/3.3-signed-is-not-safe.md) measured.

There are three places to put containment, and only one of them is on this day's side of the line:

**At the door.** Signature, timestamp, event-type allowlist, size limits. This day builds these, and
they bound *what arrives*, not what it can do.

**Between the door and the desk.** Which tools this channel's messages may reach. A chat intake
almost never needs the refund tool directly — it needs to read and to request approval, and Day
68's least-privilege work is exactly this. An intake that hands messages to a full-powered agent has
chosen the widest option by not choosing.

**At the action.** The approval gate from Day 63. Even a fully authorised, fully trusted request to
move money stops and waits for a person.

The useful discipline is that these are independent. A team that has built the first and calls it
done has bounded who knocks, not what happens when the door opens.

## Why Sutra needs it

Because this endpoint is public by construction. Part
[2.1](../02-verifying-it/2.1-what-a-vendor-sends.md) established that the vendor's servers must
reach it, so Day 85's answer — bind it somewhere private — is unavailable. The only remaining
controls are the checks in the handler and the scoping behind it.

And because Day 92 is a full security review before this repository goes public, and an intake with
no documented blast radius is exactly what that day will find. Writing it down now is cheaper than
being told.

## The mechanism

The containment that exists in the lab is one line, and it is worth being explicit that it is a
lab-only line:

```python
        seen.accepted.append(payload)
        return Response(status_code=200, content="ok")
```

**Line by line:**

- `seen.accepted` is a list on a dataclass. Nothing downstream of the endpoint exists in this day,
  which is why running every arm of this lab — including the hostile message in
  [3.3](../03-three-ways-it-goes-wrong/3.3-signed-is-not-safe.md) — is safe.
- The `200` is returned immediately, before any work. Part
  [2.1](../02-verifying-it/2.1-what-a-vendor-sends.md)'s retry contract requires that, and it also
  happens to be the shape that makes containment possible: acknowledging first means the work
  happens somewhere you control the scope of, rather than inline in an HTTP handler.
- What is *not* here is the interesting part. There is no agent, no tool, no session. In
  `sutra/intake.py` this line becomes a call into the desk, and that call is where the blast radius
  is decided.

The build brief's version of the same line, from the hub:

```text
accept(message) -> queued for a runner whose toolset is the chat scope, not the desk scope
```

**Line by line:**

- `queued` rather than called, so the HTTP handler returns in milliseconds and the work is bounded
  somewhere it can be rate-limited and retried idempotently.
- `the chat scope, not the desk scope` is the whole containment decision, and it is a decision about
  which tools exist in that runner rather than about what the message says.

## When it breaks

It breaks by being answered optimistically, and the shape of that is a sentence everybody has heard:
*"it is fine, it is behind signature verification."*

Here is the same sentence with the blast radius filled in, which is what Principle 13 asks for:

```text
  who can reach the endpoint        anyone on the internet
  who can pass the checks           anyone the workspace relays for
  who that includes                 members, guests, apps, a compromised account
  what a passing message reaches    an agent with the desk's tools
  what the desk's tools can do      read tickets, request approval, move money
```

Every row is true today. The gap between row two and row five is the finding, and no amount of work
on the signature narrows it.

There is no error text for this one and there is no run to show, because it is a design property
rather than a behaviour. That is precisely why it needs writing down: it cannot go red.

The related failure that *can* be measured is a missing size limit. This endpoint reads the whole
body into memory before doing anything, which part
[2.4](../02-verifying-it/2.4-the-bytes-that-arrived.md) noted is required by the signature scheme.
On a public endpoint with no maximum, that is an unbounded allocation driven by a stranger — and it
is not in this lab, which is an honest gap rather than a decision. It sits in the hub's build brief
as a `TODO(me)`.

## In production

**What a professional does.** Writes the blast-radius table above into the module docstring of the
handler, and keeps it current. It is five lines, it takes minutes, and it is the artefact that makes
a security review a conversation about rows rather than an interrogation. The version that gets
written is always the one written before anybody asks.

**What degrades at scale.** The scope drifts upward, one reasonable request at a time. Somebody asks
whether the chat bot can also close tickets. It can, technically, because the runner has the desk's
tools. Nobody widens the scope — it was already wide — so there is no change to review, and the
blast radius grows by use rather than by decision. Narrow scopes are what make widening visible.

**The failure that only shows with real traffic.** Volume. One message is one agent run; a busy
channel is many, and an endpoint that acknowledges and queues without a rate limit will happily
enqueue faster than the desk can drain. Day 78's allowance arithmetic then decides what breaks
first, and on a free-tier lane the answer is that the quota goes and the nightly eval fails for
unrelated reasons.

**The review comment a senior engineer leaves:** *"Give the chat runner its own toolset. Not because
we distrust the channel — because when somebody asks next quarter whether the bot can issue refunds,
I want the answer to be a diff rather than a shrug."*

**The interview question:** *"You have added a chat integration to an agent with production tools.
What is the risk?"* The answer that shows experience does not talk about the signature at all — it
goes straight to what a valid message can reach, and proposes a reduced toolset before proposing
better verification.
