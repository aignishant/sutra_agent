# 4.2 — The secret itself

## One-line answer

The signing secret is the only thing separating this endpoint from anyone on the internet, and the
lab holds it in a tracked file on purpose — because it is the vendor's own documentation example,
which is a distinction that has to be deliberate rather than lucky.

## The story

The duplicate key cut for the watchman.

There is one key to the side gate, and the watchman needs it on his shift, and the shifts change. So
somebody has a second one cut. Then the day watchman needs one too. Then a spare is left in the
drawer in the office, for when somebody forgets.

None of these decisions is wrong. Each was made for a real reason by somebody solving a real problem
on a Tuesday. But there is no longer any answer to the question *how many keys exist*, and the day
somebody has to change the lock, nobody can say who to tell.

The lock was never the weak part.

## The idea in plain language

Everything in this day rests on a shared secret. The vendor has it, this endpoint has it, and
possession of it is the whole of what a signature proves. So it is worth being precise about four
things.

**Where it lives.** Principle 9: `.env`, gitignored, never a literal in tracked code. This
repository is about to go public, and a secret in git history is public even after it is deleted,
because history is what git keeps.

**What it is not.** It is not a password and not a token. Nobody logs in with it and it never travels
— it is used on both sides to compute something, and the something is what travels. That means it
leaks differently: not by being sent, but by being *stored* somewhere it should not be.

**How long it lives.** For ever, unless somebody rotates it. There is no expiry and no renewal, so
the only thing that ever changes it is a decision.

**What rotating it costs.** A window where old signatures fail. Rotating properly means accepting
both secrets for a period, which the version marker in part
[2.2](../02-verifying-it/2.2-the-string-that-gets-signed.md) hints at — a verifier that can hold two
keys is a verifier that can be rotated without downtime, and one that holds a single string is not.

And then the specific thing about this lab, which is the reason this part exists at all: the secret
in `_events.py` is written in plain text, in a file this repository tracks.

That is correct here, exactly once, for one reason: it is the vendor's published documentation
example. It is already public, in their docs, deliberately. It secures nothing.

The reason to make a whole part of that is that "it is only a test secret" is one of the most
reliable ways real secrets get committed. The distinction between *a fixture that was always public*
and *a real value somebody decided was low-risk* is invisible in a diff.

## Why Sutra needs it

Because Day 92 is a hardening pass and Day 93 makes the repository public, in that order, which
means every secret-shaped string in this repository is about to be looked at by a check and then by
the internet.

And because this day introduces the first shared secret in the whole curriculum. Everything before
it was an API key belonging to this project — bad to leak, and revocable from a console you control.
A shared secret with a vendor is different: rotating it is a coordinated change on somebody else's
system, and until it completes, every message either fails or is unverified.

## The mechanism

The fixture, with the justification written where the value is:

```python
# A signing secret is per-app and shared out of band. This one is the vendor's documentation
# example, so it is public by construction and safe to write down. A real one goes in .env
# (Principle 9) and never in a file that git tracks.
SIGNING_SECRET = "8f742231b10e8888abcd99yyyzzz85a5"
```

**Line by line:**

- The comment is three lines for one assignment, and the ratio is the point. A tracked secret needs
  its justification adjacent to it, because the reviewer who finds it in six months has no other way
  to tell this case from the bad one.
- `abcd99yyyzzz` in the middle of the value is the vendor's own doing — it is visibly not a real hex
  secret, which is a small piece of good design in their documentation and worth copying when you
  write examples of your own.
- The name is `SIGNING_SECRET`, matching the vendor's vocabulary, so a search for the term finds
  both this and the place it should come from.

And the shape the build brief requires instead:

```text
secret() -> os.environ["SLACK_SIGNING_SECRET"]   # no default, raises when unset
```

**Line by line:**

- Indexing rather than `.get(...)`, so a missing secret is a `KeyError` at startup rather than a
  signature that never matches at run time. Failing loudly at boot is the whole argument.
- **No default.** A default is how a fixture secret reaches production, and the sequence is always
  the same: a default is added to make a test convenient, the environment variable is missed in one
  deployment, and the endpoint runs happily verifying against the example value.
- A function rather than a module-level constant, so it is read when needed rather than at import —
  which matters for anything that reloads configuration, and makes the failure land in a request
  rather than in an import somewhere in a stack trace.

## When it breaks

There is no run to paste here, and that is worth saying plainly: this part measures nothing, because
the failure is a value in a file rather than a behaviour. It is a design and review property, like
part [4.1](4.1-what-a-forged-request-reaches.md).

What can be checked is the surrounding discipline, and this repository already does one half of it:

```bash
cd days/day-91-slack-shaped-intake/lab
git check-ignore -v ../../../.env
```

**Line by line:**

- The path walks up to the repository root's `.env`, which is the file a real secret would live in.
  Asking git rather than looking is the same technique Day 88 used for its manifests: a rule
  citation, not an impression.

The failure that has no check is the one to name: a real secret committed with a comment saying it
is only a test value. Nothing distinguishes it from the fixture in this lab except the truth of the
comment, and no tool can evaluate that.

Day 92's hardening pass is where a scan for high-entropy strings belongs, and it will find this
fixture and have to be told about it. That is the correct outcome — a scan that finds it and a
comment that explains it is a working system; a scan tuned until it stays quiet is the beginning of
the alarm nobody looks at, which Day 82 part 4.2 measured in a different form.

**The rotation failure**, which is real and has an error text, is worth knowing in advance. Rotate
the secret at the vendor and not here, and every subsequent request produces:

```text
401 bad signature
```

Every request. Immediately. With correct code, a correct base string, and a correct comparison —
which is the same symptom as part [2.4](../02-verifying-it/2.4-the-bytes-that-arrived.md)'s
re-serialisation bug and has an entirely different cause. The way to tell them apart in under a
minute is the vector from part [2.3](../02-verifying-it/2.3-checked-against-the-vendor.md): it uses
the documented secret, so it stays green when the deployment's secret is stale, and goes red when the
assembly logic is wrong.

That is a genuinely useful property of keeping the vector as a test, and it is not the reason anybody
adds one.

## In production

**What a professional does.** Keeps the secret in the platform's secret store rather than in a file
at all, reads it through one accessor, and writes down who can read it. The second half is the part
that gets skipped: a secret in a store that eleven people and four services can read has eleven
people and four services in its blast radius, which is the watchman's key with better paperwork.

**What degrades at scale.** One secret becomes several — per environment, per workspace, per tenant
— and the accessor becomes a lookup. That is the point at which "which secret verified this request"
becomes a question worth logging, because a request failing verification against the wrong tenant's
secret is indistinguishable from an attack unless the log says which key was tried.

**The failure that only shows with real traffic.** A rotation with no overlap. The vendor's console
changes the value instantly; the deployment picks it up on the next restart. Between those two
moments every request fails, and if the endpoint is the only way work arrives, the work is simply
lost — the vendor retries for a while and then gives up. A verifier that accepts two secrets during a
window turns that outage into a non-event, and it is ten lines.

**The review comment a senior engineer leaves:** *"`secret()` must not take a default. I do not care
how convenient it makes the tests — a default is how the example value ends up verifying production
traffic, and it will not fail, which is the problem."*

**The interview question:** *"How do you rotate a webhook signing secret with no downtime?"* The
answer that shows experience accepts both values for a window and says which order the two changes
happen in — new secret accepted here first, then switched at the vendor, then the old one removed —
because getting that order backwards is the outage.

## Check yourself

```bash
cd days/day-91-slack-shaped-intake/lab
git check-ignore -v ../../../.env
grep -rn "SIGNING_SECRET" . --include=*.py | head
```

Every hit is either the fixture or a reference to it. Say what a reviewer would need in order to tell
this fixture apart from a real secret committed by mistake, and whether any tool could do it.

Now write `secret()` as the build brief describes it, then try to write a test for the endpoint
without adding a default. What you have to do instead is the point of the exercise.

**Out loud, without scrolling up:** why is a shared secret harder to rotate than an API key you own,
and what does a verifier need to be able to hold in order to rotate one without an outage?
