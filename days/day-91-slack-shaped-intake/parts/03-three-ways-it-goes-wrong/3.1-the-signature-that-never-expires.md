# 3.1 — 💥 The signature that never expires

## One-line answer

A valid signature stays valid for ever, so anyone who ever saw one genuine request can send it again
whenever they like — and the only thing standing between that and a duplicated refund is a check on
the timestamp, which costs one comparison and is the guard people skip.

## The story

💥 **The photocopied gate pass.**

🎬 **The scene.** A visitor arrives at an office, is signed in, and gets a paper gate pass with the
date, the floor, and an authorising signature. It works exactly as designed: the guard glances at
the signature, recognises it, and waves them through.

😬 **The naive fix.** The signature is the security. It is hard to forge, the guard knows it well,
and nobody can produce one without going through reception. So checking the signature is checking
the pass.

💥 **Why it fails.** The visitor photocopies it on the way out. The copy has the same signature —
a real one, not a forgery — and the guard, who is checking exactly the thing he was told to check,
waves the copy through next Tuesday. And the Tuesday after.

💡 **The insight.** **The signature proved the pass was issued. Nobody was checking whether it was
issued for today.** Those are different questions, the second one needs a date, and the date is
useless unless somebody actually looks at it.

## The idea in plain language

A **replay attack** is the simplest attack there is: capture a valid request, send it again. Nothing
is forged. Nothing is modified. The attacker needs no secret and no cleverness — only a copy of one
request that worked.

It defeats signatures completely, because a signature answers *"was this produced by somebody
holding the secret?"* and the answer for a replayed request is genuinely yes. It was. Once.

The defence is to put something perishable inside the signed string, and the perishable thing is the
timestamp from part [2.2](../02-verifying-it/2.2-the-string-that-gets-signed.md). Because it is
*inside* the signature, an attacker cannot change it — editing the header breaks the digest. So the
receiver can trust the timestamp exactly as much as it trusts the body, and can refuse anything too
old.

This vendor's documentation is explicit about it, verified on 2026-09-07: check that the timestamp
"does not differ from local time by more than five minutes", written in their example as `60 * 5`.

That window is a trade. Too tight and clock skew between two machines starts refusing real traffic.
Too loose and the replay window is exactly that wide. Three hundred seconds is a deliberate,
publishable choice, and the important property is that it is *finite*.

What the window does not give you is protection within it. A request replayed twice inside the
window passes twice, and that is where idempotence — Day 73's subject — takes over. The timestamp
bounds the exposure; it does not eliminate it.

## Why Sutra needs it

Because the desk moves money. Day 63's approval gate exists because a refund is not an idempotent
operation, and a replayed *"refund ticket 4688"* that reaches the desk twice is a second refund
unless something downstream refuses it.

And because the attacker for this one does not have to be an attacker. A vendor retrying a delivery
it thinks failed sends a byte-identical request with the same signature, which is the same event
from the endpoint's point of view. Part
[2.1](../02-verifying-it/2.1-what-a-vendor-sends.md) established that retries are normal traffic, so
this endpoint will receive replays whether or not anybody is attacking it.

## The mechanism

The check runs before the signature, and the ordering is the interesting part:

```python
            if window:
                try:
                    skew = abs(time.time() - int(timestamp))
                except ValueError:
                    seen.refused.append("unreadable timestamp")
                    return Response(status_code=400, content="bad timestamp")
                if skew > MAX_SKEW_SECONDS:
                    seen.refused.append("stale timestamp")
                    return Response(status_code=400, content="stale")
```

**Line by line:**

- `abs(...)` — the comparison is two-sided. A timestamp from the future is as suspicious as one from
  the past, and a one-sided check is trivially defeated by sending a timestamp dated next year.
- `int(timestamp)` inside a `try`, because the header is attacker-controlled text at this point and
  `int("banana")` raises. This runs *before* the signature check, so it is the one place in the
  handler where unvalidated input is parsed, and it must not be able to produce a `500`.
- `MAX_SKEW_SECONDS` is `60 * 5`, written that way in `_events.py` because that is how the vendor
  writes it, with a comment naming the page and the date it was read.
- The status is `400`, not `401`. The request is not unauthorised — it may be perfectly authentic —
  it is unusable. Different cause, different code, and a client can tell "retry with a fresh
  timestamp" from "your secret is wrong".
- The refusal is recorded in `seen.refused` before returning, so a script can assert on *why*
  something was refused rather than parsing stdout.

**Why the timestamp check comes first.** It is the cheaper of the two — one subtraction against a
keyed hash over the whole body — so a flood of stale requests is rejected without hashing anything.
That ordering is a small denial-of-service consideration on a public endpoint, and it costs nothing
to get right.

**Line by line:**

- The script signs a request as of a moment well outside the window, then sends it twice, exactly as
  captured. Nothing is modified, so the signature is genuine throughout.

Measured on 2026-09-07:

```text
timestamp window: 300 seconds
the captured request is replayed exactly: same bytes, same header, same signature

  signed at:      <epoch>
  replayed:       420 seconds later
  signature:      v0=<digest>  (still valid: it covers the body, not the clock)

  first send:     400 stale
  replay:         400 stale
  reached the desk: 0   refused: ['stale timestamp']

  refused: the signature is genuine and the request is too old to act on
exit: 0
```

The epoch and the digest are masked because they move on every run and this transcript is quoted;
everything else is as printed. Note the phrase in the refusal: **the signature is genuine**. The
endpoint is not doubting the sender. It is refusing to act on a request whose freshness it cannot
establish.

## When it breaks

Remove the window and keep everything else — same signature check, same secret, same bytes:

```bash
uv run python replay.py --no-window; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  first send:     200 ok
  replay:         200 ok
  reached the desk: 2   refused: []

  2 copies of one refund request reached the desk
  the signature is valid forever, so anyone who ever saw it can send it again
exit: 1
```

**Two copies of one refund request.** The endpoint verified the signature correctly, twice, and was
right both times.

There is no error text, and there is no anomaly to detect downstream either — the two events are
byte-identical, so a log shows two well-formed authentic requests. The only difference from
legitimate traffic is the timestamp, which is precisely the field nobody looked at.

Now consider who can do this. A signature is not secret — it travels in a header on every request.
Anyone who can see one request can replay it: a proxy, a log aggregator, an error tracker that
captured the headers, a browser extension on somebody's machine, an archived `curl -v` in a support
ticket. The attack requires no compromise of the secret at all, and this is the practical reason the
window matters more than it sounds: signatures leak into places secrets never go.

**What the window still does not fix.** Replay *inside* three hundred seconds. Two copies within the
window both pass, so a vendor's own retry will deliver twice. The endpoint needs idempotence on the
vendor's `event_id` for that, and this repository does not have it yet — it is a `TODO(me)` in the
hub, pointing at Day 73's mechanism.

## In production

**What a professional does.** Checks the timestamp *and* keeps short-lived state keyed on the
message identifier, and treats those as two separate defences with two separate jobs. The window
bounds how long a captured request is useful; the identifier check stops the duplicates that arrive
inside it. Neither substitutes for the other, and shipping only the second is a memory leak, while
shipping only the first is this part.

**What degrades at scale.** Clock skew becomes real. Three hundred seconds is generous for two
machines with working time synchronisation and not generous at all for a container whose clock
drifted, and the failure is a slow trickle of refusals that look like signature problems. Any
service refusing on a timestamp should log the observed skew, so the pattern is visible before it is
an incident.

**The failure that only shows with real traffic.** A vendor that queues during an outage and
delivers a backlog when you come back. Every message in it is genuine and every one is outside the
window, so a correct implementation refuses the lot. That is the right call and it is not obviously
the right call at the time, which is why the refusal must say `stale` rather than `bad signature` —
the operator needs to tell "we are under attack" from "we were down".

**The review comment a senior engineer leaves:** *"Log the skew value on every stale refusal, not
just the fact. When this fires at three in the morning the first question is whether it is one
second over or six hours over, and those are completely different incidents."*

**The interview question:** *"Your webhook checks the signature. Is that enough?"* The answer that
shows experience says no and names replay first — then, before being asked, concedes that the
timestamp window only bounds the problem and that duplicate delivery inside the window is normal
traffic, not an attack.
