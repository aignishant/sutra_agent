# 3.3 — What happens when it asks anyway

## One-line answer

A tool that is absent does not produce a polite refusal — the ADK runtime raises `ValueError` and
the run ends, which is correct and is not free, so the denial has to be designed rather than
discovered.

## The story

You go to the shop at the end of the lane for a particular brand of tea. The shopkeeper does not
stock it.

What happens next depends entirely on him. A good one says *"I don't keep that one, but this is the
same strength"*, and you leave with tea. A busy one says *"Not available"* and turns to the next
customer, and you leave with nothing — not because he was rude, but because answering properly was
not his job in that moment.

Either way you did not get the brand you asked for. The difference is whether you got tea.

## The idea in plain language

Sections 3.1 and 3.2 removed tools. This part is about the other side of that decision: what the
system does when the model asks for one anyway, which it will, because a model that has read a
poisoned ticket does not know your tool list changed.

There are three possible behaviours, and they are genuinely different designs rather than
implementation details:

| behaviour | what the model sees | what the run does |
| --- | --- | --- |
| **raise** | nothing — the run is over | ends with an exception |
| **refuse** | a tool result saying no | continues, and may adapt |
| **ignore** | a result that looks like success | continues, wrongly |

The third is never acceptable and is listed because people build it by accident, usually by catching
an exception and returning `{"ok": true}` to keep things moving. That is plan §5.1 **trap #4** — 2.x
surfaces exceptions through the runtime precisely so this cannot be done quietly — and it is
Principle 10 in one line: never fabricate a result to cover an error.

Between the first two, ADK has made a choice for the "tool not registered" case, and it is **raise**.
That is defensible: a model asking for a tool that was never offered is, in the ordinary case, a bug
in your agent configuration rather than a runtime condition, and bugs should be loud.

It is also, in the security case, a cost. The run that was going to answer a customer does not
answer them. An attacker who cannot make your desk do something harmful can still reliably make it
stop, by including a request for a tool that does not exist — which is a small denial-of-service with
no cleverness required.

So the design question this part exists to force is: **for each denied tool, is stopping the run the
outcome you want?** Sometimes yes. For a refund, ending the run and escalating is exactly right. For
a tool the model reached for speculatively, ending the run throws away work that was going fine.

## Why Sutra needs it

[1.1](../01-the-deputy/1.1-the-errand-and-the-keys-that-went-with-it.md) already showed the cost
without dwelling on it: in the narrow arm the desk read the ticket and then stopped, so `send_reply`
never ran and the customer got nothing. The attack was contained and the errand also failed.

The triage graph has five stages and Day 59 put containment guards around it. This is the same
question at the tool boundary, and the answer feeds the hub's build brief: the fence in
`sutra/permissions.py` decides, per tool, between raising and refusing, and that decision belongs in
the permission table next to the grant.

## The mechanism

The full error, produced by asking a filtered toolset for `refund`. This is the verbatim tail of the
traceback, measured on 2026-09-06:

```traceback
  File "C:\Users\...\google\adk\flows\llm_flows\functions.py", line 596, in _execute_single_function_call_async
    raise tool_error
  File "C:\Users\...\google\adk\flows\llm_flows\functions.py", line 580, in _execute_single_function_call_async
    tool = _get_tool(function_call, tools_dict)
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "C:\Users\...\google\adk\flows\llm_flows\functions.py", line 1223, in _get_tool
    raise ValueError(error_msg)
ValueError: Tool 'refund' not found.
Available tools: read_ticket, send_reply

Possible causes:
  1. LLM hallucinated the function name - review agent instruction clarity
  2. Tool not registered - verify agent.tools list
  3. Name mismatch - check for typos

Suggested fixes:
  - Review agent instruction to ensure tool usage is clear
  - Verify tool is included in agent.tools list
  - Check for typos in function name
```

Three things in that text are worth reading carefully.

**`Available tools: read_ticket, send_reply`.** The error names your allowlist. In a log this is
useful; in anything that reaches a user it is a disclosure — you have just told the caller exactly
what this agent can do, which is the first thing an attacker wants to know. Nothing here reaches a
user by default, and it is one careless `except ValueError as e: return str(e)` away from doing so.

**The three "possible causes" are all developer-facing**, and none of them is *"the tool was
deliberately withheld"*. The framework is telling you what it assumes: a missing tool is a
misconfiguration. That assumption is right most of the time and wrong on exactly the runs this day
is about.

**It is a `ValueError`, raised through the runtime.** It is catchable, which matters, because the
alternative design — refuse instead of raise — is something you build on top rather than a flag you
set:

```python
class DeniedFence(BasePlugin):
    """Turn an ungranted tool into a refusal the model can read, instead of an ended run."""

    def __init__(self, name: str, granted: set[str]) -> None:
        super().__init__(name)
        self.granted = granted

    async def before_tool_callback(
        self, *, tool: BaseTool, tool_args: dict[str, Any], tool_context: ToolContext
    ) -> dict[str, Any] | None:
        if tool.name not in self.granted:
            return {"error": f"{tool.name} is not available to this desk", "retry": False}
        return None
```

**Line by line:**

- This only fires for tools that **are** on the agent, because `before_tool_callback` runs after the
  runtime has resolved the tool. So it is not a replacement for
  [3.1](3.1-deny-by-default-at-the-toolset.md)'s filter — it is the second layer, for tools you keep
  registered deliberately so that you can refuse them informatively.
- `"retry": False` is a hint to the model that trying again will not help. Without it a model will
  often call the same tool a second time, which costs a request against a free-tier quota and
  changes nothing.
- Returning a dict stops the tool and becomes its result — the same mechanism
  [2.3](../02-three-questions/2.3-how-many-times-rate.md) used for rate, verified against
  `adk.dev/plugins/` on 2026-09-06 and against the installed docstring.

The two designs side by side, from the arms already run:

| design | tool on the agent? | model's experience | `send_reply` still happened? |
| --- | --- | --- | --- |
| filtered out ([3.1](3.1-deny-by-default-at-the-toolset.md)) | no | run ends | no |
| registered and refused | yes | a result saying no | yes, if it adapts |

Neither is correct in general. The filtered version is stronger, because the tool cannot be called
even by a bug in the fence. The refusing version is kinder to the errand. A desk that wants both
uses the filter for tools it never grants and the fence for tools it grants conditionally.

## When it breaks

The break is the fix somebody reaches for when this error appears in production for the first time.

The run ended, a customer did not get an answer, and the traceback says `Tool 'refund' not found.
Available tools: ...`. The obvious reading of that message — reinforced by its own "suggested fixes"
— is *the tool is missing from the agent's list*. And the obvious fix is to add it back.

That is the moment the day is about. The message is written for the case where the omission was an
accident. When the omission was a decision, the message is actively misleading, and there is nothing
in the traceback to say which situation you are in.

The defence is to leave a record where the person debugging will be standing. A comment in the
toolset construction, naming the table:

```python
# The desk's tools come from permissions.json, deny-by-default (day 68, part 3.1).
# A "Tool 'x' not found" error may be correct: check the table before adding anything here.
DESK = DeskToolset(tool_filter=granted_tools("desk"))
```

**Line by line:**

- The comment is doing security work, which is unusual and justified here: it is the only thing
  standing between a 2am traceback and somebody widening a grant to make an error go away.
- `granted_tools("desk")` reads the table, so the list in code cannot be edited without editing the
  table — the widening has to happen where it will be reviewed.

## In production

**What a professional writes instead.** They catch the error at the graph boundary and turn it into a
recorded outcome rather than a crash: the run ends, the ticket is marked as needing a human, and the
event log says *denied tool: refund* rather than *unhandled exception*. That is the difference
between an incident and a queue item. Day 59's containment work is the same instinct — fail-stop
rather than continue-wrong — and this is the tool-level version of it.

**What degrades at scale.** Denials are rare and therefore untested. The path that handles a denied
tool is executed once a month, which means it is the path most likely to be broken, and it is broken
in a way nobody notices because the run that exercises it was already failing. Denials belong in the
test suite as a first-class case, not as an edge case.

**The failure mode that only appears with real traffic.** A model that hits a denial often retries,
and a retry is a request. On a free tier, a poisoned ticket that reliably triggers a denial-and-retry
loop costs quota per attempt. `"retry": False` in the refusal and a cap on retries per run are the
two lines that stop it; Day 59's guards catch the general case and this is the specific one.

**The review comment a senior engineer leaves:** *"When this tool is denied, the run raises and the
customer gets nothing. Is that the behaviour you want for this tool? Write the answer in the
permission table — `deny: raise` or `deny: refuse` — so the next person does not have to infer it
from a traceback. And do not put that error text anywhere a caller can read it; it lists your tool
names."*

**The interview question:** *"What happens when your agent tries to use a tool it is not allowed to
use?"* The answer that shows you have run it: *"In ADK 2.7 the runtime raises `ValueError: Tool 'x'
not found`, and the run ends — it is not a soft refusal. That is the right default, because a
missing tool is usually a misconfiguration, but it means a denial is also a small denial-of-service
and it throws away the rest of the errand. So I decide per tool: for anything irreversible, ending
the run and escalating is what I want; for tools the model reaches for speculatively, I keep them
registered and refuse in a `before_tool_callback` with a `retry: False` hint, so the run can adapt.
The other thing I do is leave a comment at the toolset construction, because that error message
suggests adding the tool back and sometimes the absence was the point."*
