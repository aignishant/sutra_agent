# 2.3 — How many times? Rate is a permission too

## One-line answer

A grant that answers *may it?* and not *how much of it?* is a grant with no upper bound, and on a
free tier the upper bound is the only thing standing between one run and a dry quota.

## The story

The photocopy shop near the college gives regulars a card. You take a copy, they tick a box. Ten
boxes, one card, and when the boxes are full you buy another card.

The shop next door tries something friendlier: no card, just a register. Take what you need, write
your name, settle at the end of the month.

It works for a year. Then somebody's project needs four hundred pages the night before submission,
and they take four hundred pages, and they write their name, and they are not doing anything wrong.
The shopkeeper's problem is not that a rule was broken. It is that there was no rule — just a
reasonable expectation that nobody would ever need four hundred.

The card had a number on it. The register had a hope.

## The idea in plain language

The third question a permission answers is *how many times?*, and it is the one people leave out
because it does not feel like a security question. It feels like a performance question, or a
billing question, or something the infrastructure team handles.

It is a security question, for two separate reasons:

1. **Volume changes the nature of an action.** One reply sent to the wrong address is a mistake. Two
   hundred replies sent in a minute is an incident, and the tool that did it is the same tool.
2. **Exhaustion is an outcome an attacker wants.** If a poisoned ticket cannot make your desk move
   money, it can still make your desk spend every request you have. On this project that is not
   theoretical: Addendum 02 denominates the whole budget in **requests per minute and requests per
   day**, so a tool called eight times when it was granted three is a tool that has taken something
   from you.

The word for the second one is **quota exhaustion**, and it belongs in a threat model next to the
more dramatic outcomes. It is cheap to attempt, it needs no cleverness, it leaves the system
technically working, and it takes the desk off the air for the rest of the day.

Rate limiting is not new — [Day 24](../../../day-24-token-accounting-and-budgets/LESSON.md) built
token accounting and taught the leaky bucket. What is new here is the framing: a rate is not a
protection wrapped around a permission, it is **part of the permission**, and it belongs in the same
row of the same table as the capability and the scope. A row that says `write, outbound` and nothing
else has not finished describing what was granted.

## Why Sutra needs it

The desk's `send_reply` reaches a customer. Day 59 measured what a runaway costs in requests and put
guards around loops; this is the same argument aimed at a single tool rather than at a control flow,
and it catches the case Day 59's guards do not: a run that is not looping at all, that calls one
tool many times, entirely within its iteration budget.

It also sets up Day 70. The Quota-Router routes requests to whichever provider has headroom, and a
router is only useful if something upstream is counting. A rate on a tool is the first counter in
that chain.

## The mechanism

`rate.py` grants `send_reply` at three per run — and then does not enforce it anywhere, which is the
default state of every permission table nobody wired up.

```bash
cd days/day-68-least-privilege-tools/lab
uv run python rate.py
```

**Line by line:**

- The script scripts the model to attempt `send_reply` eight times, to eight different addresses. It
  is not looping in the Day 59 sense; it is one straight run making eight calls.
- `LIMIT = 3` matches the `10/min` spirit of the permission table, scaled down so the demonstration
  fits on a screen.
- `AUDIT.names()` counts the calls whose **body actually ran**, which is the number that matters. A
  refusal that still executes the tool is not a refusal.

Measured on 2026-09-06:

```text
granted rate: 3 per run  (not enforced anywhere)
model attempted: 8
tool body ran:   8
refused:         0
```

Eight, against a grant of three. Nothing errored, nothing warned, and the permission table on disk
still says `10/min` — which is now a sentence about intentions.

The enforcement is a plugin, which is to say a check **outside** every tool:

```python
class RateFence(BasePlugin):
    """A per-run counter, outside the tool, refusing past the granted rate."""

    def __init__(self, name: str, limit: int) -> None:
        super().__init__(name)
        self.limit = limit
        self.seen: dict[str, int] = {}

    async def before_tool_callback(
        self, *, tool: BaseTool, tool_args: dict[str, Any], tool_context: ToolContext
    ) -> dict[str, Any] | None:
        self.seen[tool.name] = self.seen.get(tool.name, 0) + 1
        if self.seen[tool.name] > self.limit:
            return {"error": f"rate: {tool.name} granted {self.limit} per run"}
        return None
```

**Line by line:**

- `BasePlugin` and `before_tool_callback` are the ADK 2.x plugin surface, verified against
  `adk.dev/plugins/` on 2026-09-06 and against the installed `google-adk==2.7.1`. Day 14 introduced
  plugins as a concept; this is one doing load-bearing work.
- **Returning a dict stops the tool and becomes its result.** The installed docstring says so —
  *"If a dictionary is returned, it will stop the tool execution and return this response
  immediately"* — and the run below is the measurement.
- `self.seen` counts per tool name, so a limit on `send_reply` does not consume the allowance for
  `read_ticket`. Counting all tools together is a common and wrong simplification: it makes reads
  compete with writes for the same budget.
- The refusal is returned, not raised. That is the opposite choice from a missing tool
  ([3.3](../03-absent-not-forbidden/3.3-what-happens-when-it-asks-anyway.md)), and it is deliberate:
  a rate refusal is a *normal* condition the model can be told about and can react to, whereas an
  ungranted tool is a programming error.

```bash
uv run python rate.py --capped
```

**Line by line:**

- `--capped` adds `RateFence` to the runner's `plugins=` list. The agent, the tools and the eight
  attempts are unchanged, so the drop from eight to three is the plugin and only the plugin.

```text
granted rate: 3 per run
model attempted: 8
tool body ran:   3
refused:         5
```

Three ran, five were refused, and the tool's own code is unchanged between the two arms.

## When it breaks

Rate limits break in a way that is specific and easy to get wrong: **the counter's lifetime is part
of the permission, and almost nobody writes it down.**

`RateFence` counts per *run*, because `self.seen` lives on a plugin instance held by one runner. Read
the permission table again: it says `10/min`. Those are different limits. A run that finishes in a
second and is started twenty times in that minute passes the per-run check twenty times and blows
the per-minute grant, and every individual check was correct.

Three lifetimes, three different guarantees:

| counter lives for | stops | does not stop |
| --- | --- | --- |
| one run | a single run going berserk | many runs doing it together |
| one process, one window | that process exceeding the window | the other four processes |
| a shared store | the whole system exceeding the window | nothing, if the store is slow or down |

Sutra runs one process today, so per-run and per-process are close enough to be useful and the
distinction is still worth writing in the table. The moment there are two processes the counter has
to move to a shared store, and then the store's own failure becomes a decision: if the counter is
unreachable, do you fail open and serve, or fail closed and stop? For a rate protecting a **free-tier
quota**, fail closed — the thing you are protecting is not a service level, it is your ability to
run at all tomorrow.

## In production

**What a professional writes instead.** They use a proper algorithm rather than a counter — Day 24's
leaky bucket, or a sliding window — because a fixed counter reset at the top of each minute lets
through twice the limit at a window edge. They also make the refusal informative to the *caller*
rather than only to the log: a `retry_after` in the returned dict lets a well-behaved agent wait
instead of retrying immediately and consuming the next window too.

**What degrades at scale.** Per-tool rates interact. Ten replies a minute and sixty reads a minute
sound independent, until the reply path reads three tickets first and the read limit becomes the
binding constraint on replies. Nobody notices because both dashboards are green; the symptom is that
replies plateau at a number nobody chose.

**The failure mode that only appears with real traffic.** Rates are set from an average and broken by
a burst. A desk that handles two hundred tickets a day averages one every seven minutes, and a rate
set from that average will be tripped by the perfectly ordinary Monday morning when forty arrive at
once. Then somebody raises the limit under pressure, during an incident, without changing the table
— and the grant on disk and the grant in the code have diverged, which is
[5.2](../05-failure-lab/5.2-the-tool-that-arrived-without-a-row.md)'s failure in a different costume.

**The review comment a senior engineer leaves:** *"The table says `10/min` and the code counts per
run. Those are not the same limit, and the one in the code is the one that is true. Decide which one
you meant, put the window in the table, and say what happens when the counter store is unavailable."*

**The interview question:** *"Is a rate limit a security control?"* The answer that shows judgement:
*"Yes, for two reasons that get confused. It bounds the damage of a correct-but-repeated action —
one wrong email is a mistake, two hundred is an incident, same tool — and it makes exhaustion an
attack you have already priced. On a free tier that second one is the real threat: an attacker who
cannot make my agent do anything harmful can still make it spend the day's quota. So I treat the
rate as part of the grant rather than as infrastructure, I write the window down next to the
capability, and I fail closed when the counter is unreachable, because the thing being protected is
my ability to run tomorrow."*
