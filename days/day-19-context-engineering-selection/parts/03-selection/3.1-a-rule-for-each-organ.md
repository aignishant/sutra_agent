# 3.1 — A rule for each organ

## One-line answer

Six organs, six different selection rules — and the reason there is not one rule is that each organ
has a different owner, a different growth behaviour and a different way of going wrong.

## The story

Packing the day bag for a walk.

There is no single principle. Water goes in because you will want it and there is no tap on a hill:
always, every time, no thought required. The waterproof goes in because of the forecast, which means
somebody looked at the forecast. The big camera goes in only if you are actually going to use it,
which is a different question from whether you would like to have it. The map goes in because you know
the route badly.

Four items, four completely different reasons, and the person who packs by one rule — *"take
everything useful"* — arrives with a bag they will not carry up the second hill.

## The idea in plain language

Here is the whole of context selection, one line per organ. Each rule is short because each rule is
about one owner's decision.

| Organ | Selection rule | Because |
| --- | --- | --- |
| **System instruction** | only what would be true on a call you have not thought of yet | it is re-sent on every call for ever ([2.4](../02-anatomy/2.4-a-subscription-not-a-purchase.md)) |
| **Tool declarations** | the smallest menu that lets this agent do its job | every tool costs tokens *and* a harder decision ([2.3](../02-anatomy/2.3-the-menu-costs-more-than-the-handbook.md)) |
| **Templated facts** | facts, never blobs — and only the ones this step needs | a state key becomes prompt text the moment you name it ([3.2](3.2-facts-not-blobs.md)) |
| **Conversation history** | keep what changes the answer, summarise the rest | it is the only organ that grows by itself ([1.3](../01-the-binder/1.3-the-organ-that-grows-by-itself.md)); Day 20 does the summarising |
| **Documents** | the slice that answers the question, not the file | one paste is worth 138 curated prompts ([1.1](../01-the-binder/1.1-room-is-not-free.md)) |
| **The current message** | untouched | everything else exists to serve it |

Two things about this table are worth more than the table.

**The rules are not interchangeable.** *"Keep it short"* applied to the instruction produces a good
instruction. Applied to the user's message it produces a system that ignores what people say. Applied
to history it is wrong — the fix there is not shortening but *summarising*, which is a different
operation with a different failure mode.

**Five of the six are yours.** The user's message is not negotiable, and the other five are all
decisions somebody made, usually once, often by default. Context engineering is mostly the practice of
noticing that a default was a decision.

And one rule that spans all six, which is the day's real thesis: **ask per call, not per system.** The
same agent answering *"what is this ticket about?"* and *"rewrite the note in one paragraph"* needs
different things in the window, and a system that packs the same way for both is optimised for
neither.

## Why Sutra needs it

Because Sutra now has something to put in every one of these organs, and no rule yet for any of them.

Concretely, today's inventory: an instruction that has been growing since Day 6, a tool list that grows
every phase, two stores full of facts (Days 17 and 18), artifacts that can be loaded into a request
([18.4.3](../../../day-18-artifacts-that-survive/parts/04-in-the-run/4.3-what-the-model-cannot-see.md)),
and a history that grows on its own. Without rules, the default is *all of it, every time*, and that
default is what the free tier's twenty requests a day will find first.

The rules also decide what Phase 8 can build. A graph node that receives *the whole conversation* is a
node that costs the whole conversation; a node that receives the two facts it needs is a node you can
afford to call three times.

## The mechanism

The rules become code in one place: a function that assembles the context for a step, taking each organ
deliberately rather than by default.

```python
# days/day-19-context-engineering-selection/lab/selection.py
"""Assembling a step's context on purpose, organ by organ. Zero model calls."""

from dataclasses import dataclass, field


@dataclass
class Package:
    """What one model call will carry, with each organ named."""

    instruction: str
    tools: list[str] = field(default_factory=list)
    facts: dict[str, str] = field(default_factory=dict)
    history: list[str] = field(default_factory=list)
    documents: list[str] = field(default_factory=list)
    message: str = ""

    def sizes(self) -> dict[str, int]:
        return {
            "instruction": len(self.instruction),
            "tools": sum(len(t) for t in self.tools),
            "facts": sum(len(k) + len(v) for k, v in self.facts.items()),
            "history": sum(len(h) for h in self.history),
            "documents": sum(len(d) for d in self.documents),
            "message": len(self.message),
        }

    def total(self) -> int:
        return sum(self.sizes().values())


STANDING = "You are Sutra, the triage desk. Say 'I don't know' when you do not know."
STATE = {"severity": "high", "ticket_id": "4521", "note_file": "triage-4521.md"}
HISTORY = [f"turn {i}: an exchange about the login problem" for i in range(1, 9)]
LOG = "2026-09-03T09:12:41Z INFO auth session refreshed tenant=northwind-prod\n" * 40


def everything() -> Package:
    """The default: every organ at full size."""
    return Package(
        instruction=STANDING + " Always check the vendor. Use British spelling.",
        tools=["lookup_ticket(...)", "search_kb(...)", "check_vendor(...)", "send_email(...)"],
        facts=STATE,
        history=HISTORY,
        documents=[LOG],
        message="Write the triage note for this ticket.",
    )


def for_this_step() -> Package:
    """The same step, packed by the rules in this part."""
    return Package(
        instruction=STANDING,
        tools=[],  # writing a note needs no tools
        facts={"severity": STATE["severity"], "ticket_id": STATE["ticket_id"]},
        history=HISTORY[-2:],  # the last exchange is what the note is about
        documents=[line for line in LOG.splitlines() if "WARN" in line or "ERROR" in line],
        message="Write the triage note for this ticket.",
    )


for label, package in (("everything", everything()), ("for this step", for_this_step())):
    print(f"--- {label} ---")
    for organ, size in package.sizes().items():
        print(f"  {organ:12} {size:>6}")
    print(f"  {'TOTAL':12} {package.total():>6}")
```

**Line by line:**

- `Package` is a plain dataclass, not an ADK object. This part is about the *decision*, and modelling it
  as data makes the decision inspectable and testable
  ([6.1](../06-in-production/6.1-testing-what-goes-in-the-window.md) asserts against exactly this
  shape).
- `sizes()` returns a number per organ rather than a total, because a total cannot be acted on
  ([2.2](../02-anatomy/2.2-six-organs-and-who-packed-them.md)).
- `everything()` is not a straw man: it is what you get by wiring an agent the obvious way — all the
  tools, all of state templated, the whole history, the pasted log.
- `for_this_step()` applies the six rules to **one** step, *write the note*: no tools because writing
  needs none, two facts instead of three because the filename is not needed to write the note, the last
  two exchanges rather than eight, and the WARN and ERROR lines rather than the whole log
  ([3.2](3.2-facts-not-blobs.md) is that move on its own).
- The filtering of `LOG` is deliberately crude — a substring test — because the point is that even a
  crude selection beats no selection.

## When it breaks

**The rules are applied once, at design time, and never per step.**

No error. An agent built with a fixed context assembly does the same packing for a question that needs
tools and a question that needs none, and the second kind pays for the first kind's menu. It is the
most common shape of over-packing there is, because *"the agent has these tools"* feels like a property
of the agent rather than a per-call decision.

**A rule is applied to the wrong organ.** Truncating history to the last two messages is reasonable;
truncating the *user's message* to its first two hundred characters is a bug that will look like the
model ignoring people. The rules are per organ because the organs are not alike.

**Selection removes the thing the step needed.** The real risk of this whole day, and it has no error
text either: an over-eager filter drops the one line that mattered, and the model answers confidently
from what is left. This is why [6.1](../06-in-production/6.1-testing-what-goes-in-the-window.md)
asserts on what *is* in the window as well as on its size, and why summarising beats truncating for
history (Day 20).

## In production

**Make the assembly a function, and make it take the step as an argument.**

The version a professional writes has one place that builds the context for a call and knows what kind
of call it is. It is boring code and it is where every cost decision in the system ends up living. The
alternative — assembly spread across an agent definition, a callback and a tool — is a system where
nobody can answer *"why is this prompt big?"* without reading four files.

**What changes at scale** is that selection becomes retrieval. Choosing five lines from a log is a
filter; choosing five documents from ten thousand is a search problem with embeddings and a ranking
model, which is Day 49. The rule does not change — *only what earns a place* — but the mechanism does,
and it is worth knowing that today's crude filter and Phase 7's retrieval are the same idea at two
scales.

**What fails only under real traffic** is the assumption that steps are similar. Real traffic contains
the question that needs the whole history, the ticket with a fifty-line stack trace, and the user who
asks six things in one message. A packing rule with no escape hatch will handle two of those three
badly.

**The review comment**: *"this assembles the same context for every step. What does the note-writing
step actually need — and does it need the tools?"*

**The interview question**: *"how do you decide what goes into a prompt?"* The answer that shows the
craft rather than the slogan: *"per organ and per call. Standing rules in the instruction, the smallest
useful tool menu, facts rather than blobs, a summarised history, the slice of the document that answers
the question — and the user's message untouched."*
