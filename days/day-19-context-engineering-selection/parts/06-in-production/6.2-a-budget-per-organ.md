# 6.2 — A budget per organ

## One-line answer

One total tells you something is wrong and nothing about whose it is: **a limit per organ** turns
prompt growth into a failing test that names the owner, and it is the shape Day 24 will fill with
quota.

## The story

The household budget that is one number.

*"We spend too much."* Everybody agrees, and nothing changes, because the sentence has no handle on it.
The next month is the same and the argument is the same, and now it is also an argument about who is
being blamed.

Then somebody splits it: rent, food, transport, the subscriptions nobody has looked at since 2023. Two
minutes later the conversation is completely different, because it is about the subscriptions — which
are eleven per cent of the total and one hundred per cent of the fixable part.

The number did not change. The number became four numbers, and four numbers can be acted on.

## The idea in plain language

A budget is only useful if a failure tells you what to do. That means one limit per organ
([2.2](../02-anatomy/2.2-six-organs-and-who-packed-them.md)), because the organs have different
owners and different remedies:

| Organ | If it is over | Who fixes it, and how |
| --- | --- | --- |
| instruction | the handbook has been growing | delete sentences, or move situational rules to templated facts ([2.4](../02-anatomy/2.4-a-subscription-not-a-purchase.md)) |
| tools | the menu is too long | fewer tools, or a specialist agent ([2.3](../02-anatomy/2.3-the-menu-costs-more-than-the-handbook.md)) |
| history | the conversation is long | compaction — tomorrow ([6.3](6.3-the-heaviest-organ.md)) |
| message | somebody pasted something | distil at the boundary ([3.2](../03-selection/3.2-facts-not-blobs.md)) |

Four organs, four different remedies, and a single total would have pointed at none of them.

Two design choices make a budget survivable rather than annoying.

**Set it from the healthy shape, not from a round number.** Measure what a normal request for this step
looks like ([4.2](../04-measuring/4.2-curated-against-kitchen-sink.md)) and set the limit at a multiple
of it. A limit chosen because it looks tidy will either never fire or fire constantly.

**Denominate it in something free to measure.** Characters, because they cost nothing and can run on
every request and in every test ([4.1](../04-measuring/4.1-a-scale-for-prompts.md)). Tokens are the
real currency, and they are converted at the boundaries where a number has to be exact — which is Day
24's job.

Sutra's first budget is deliberately generous. The point today is not to be tight; it is to have a
detector that exists, so that a change which quadruples a prompt fails a test rather than a bill.

## Why Sutra needs it

Because Phase 3's gate is *state survives restarts; **budgets enforced***, and this is the first
enforcement that can fail.

It is also the last piece of scaffolding Day 24 needs. That day converts budgets into quota — requests
per day, per provider — and the structure it needs is exactly this: a measurement per organ, a limit
per organ, and a place where exceeding one is a decision rather than a surprise.

## The mechanism

The budget, and the function that checks it:

```python
# sutra/context.py - the second half of today's build
ORGANS = ("instruction", "tools", "history", "message")

# Characters, per model call, per organ. Deliberately generous and deliberately finite:
# a budget nobody can hit is a budget nobody reads (day 24 turns these into quota).
BUDGET: dict[str, int] = {
    "instruction": 1_200,
    "tools": 4_000,
    "history": 20_000,
    "message": 8_000,
}


def over_budget(sizes: dict[str, int]) -> list[str]:
    """The organs that exceeded their budget, in the order they are declared."""
    return [organ for organ in ORGANS if sizes.get(organ, 0) > BUDGET[organ]]
```

**Line by line:**

- `BUDGET` is a **module constant**, so a change to it is a diff somebody reviews. A limit computed at
  run time from something else is a limit that can move without anybody noticing.
- The comment above it states the intent — generous, finite, and the reason both matter. A number with
  no rationale gets raised the first time it is inconvenient.
- `instruction: 1_200` — about eight times Sutra's current instruction
  ([2.1](../02-anatomy/2.1-opening-the-envelope.md) measured 145), which is room to grow and not room
  to sprawl.
- `tools: 4_000` — roughly a dozen small tools at the measured rate of 235 to 383 characters each
  ([2.3](../02-anatomy/2.3-the-menu-costs-more-than-the-handbook.md)). A limit that says *this is a
  desk, not a toolbox*.
- `history: 20_000` — the loosest, because history is expected to grow and the remedy is compaction
  rather than refusal. It is a *trigger* more than a limit: crossing it is the signal that Day 20's
  machinery should run.
- `message: 8_000` — the paste detector. A human question is a few hundred characters; eight thousand
  means a document arrived ([4.2](../04-measuring/4.2-curated-against-kitchen-sink.md)).
- `over_budget` returns **names**, in a fixed order, so a failing test says `['message']` rather than
  `False`.
- `sizes.get(organ, 0)` — tolerant of a scale that does not report an organ, because a missing
  measurement should not read as an infinite one.

The check in the suite is one line
([6.1](6.1-testing-what-goes-in-the-window.md)):

```python
assert over_budget(weigh(request)) == []
```

**Line by line:**

- Comparing against `[]` rather than using `not` — so a failure prints the offending organ names in the
  assertion message, which is the entire reason for returning a list.

```bash
uv run python -m pytest tests/test_context.py -q -m "not live"
```

**Line by line:**

- Free: characters, a recording model, no key.

The two budget tests measured on 2026-09-03 pass and fail as designed: a short question with one tool
is inside every limit, and a four-times-repeated log blows the `message` limit and names it. Raising
`message` to eight million makes that test go green, which is the mutation in
[6.1](6.1-testing-what-goes-in-the-window.md)'s table and the reason a budget has to be reviewed rather
than adjusted.

## When it breaks

**The budget fires on a legitimate request.**

No error text — a red test on a change that was fine. It happens, and the response is a decision rather
than an edit: either the request should be smaller, or the limit was wrong. Raising a limit is
allowed; raising it without a sentence in the commit saying why is how budgets die.

**The budget never fires.** Worse, and quieter. A limit set so high that nothing reaches it is a test
that always passes and a false sense of control. If a limit has never fired in three months, either
your discipline is excellent or the number is decorative — and there is a cheap way to tell: put a
deliberately enormous message through it and check that it complains.

**The budget is in the wrong unit.** Characters and tokens differ by a factor of 2.4 to 3.6 depending on
the text ([4.1](../04-measuring/4.1-a-scale-for-prompts.md)), so a character budget derived from a
token limit needs the conversion done deliberately and written down. Sutra's are set in characters and
described as characters, which is the honest version of not having done the conversion yet.

## In production

**Alert on the budget, do not enforce it in the request path.**

The version a professional runs measures every request and reports when an organ is over — and does
**not** refuse to send it. Blocking a user's request because it is large is a worse outcome than an
expensive answer; the budget exists to make the growth visible and to fail a build, not to fail a
customer. The one exception is a hard provider limit, where the choice is refusing or erroring anyway.

**What changes at scale** is that budgets become per agent and per step. A researcher node and a writer
node have completely different healthy shapes, and one shared set of numbers will be wrong for both.
The structure survives — a limit per organ per step — and the constants multiply.

**What fails only under real traffic** is the distribution. A budget checked against the median never
fires; the interesting request is the ninety-ninth percentile
([1.2](../01-the-binder/1.2-three-costs-in-one-scene.md)). Recording sizes in production and looking at
the tail is what tells you whether your limits are set anywhere near reality.

**The review comment**: *"this raises the tools budget from 4,000 to 12,000 with no explanation. What
changed — did we add tools, or did we stop wanting the limit?"*

**The interview question**: *"how would you stop prompt bloat in a system that several people work
on?"* The answer that shows the mechanism: *"a measured limit per organ, asserted in CI, generous
enough to be believable and finite enough to fire — so growth becomes a failing build with the owner's
name on it rather than a bill three months later."*
