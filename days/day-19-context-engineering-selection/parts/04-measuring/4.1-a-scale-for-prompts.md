# 4.1 — A scale for prompts

## One-line answer

Characters are free to measure and good enough for ratios; tokens are what the provider counts and
cost one API call that generates nothing — so Sutra weighs in characters continuously and converts to
tokens when a number has to be exact.

## The story

Getting the kitchen scales out.

You can bake without them. People did for centuries, and *a cup of flour, a knob of butter* produces
bread most of the time. Then it produces something dense and wrong, and you cannot say why, because
nothing in the process was ever a number.

The scales do not make you a better baker. They make the thing repeatable and the failure explainable,
which is most of what being better means: when it goes wrong you can compare it to the time it went
right.

## The idea in plain language

There are two units for measuring a prompt, and knowing when to use which is the whole of this part.

**Characters** are free. `len(text)` costs nothing, needs no network, and can run on every assembled
request in your test suite. They are wrong in an interesting way — a token is roughly 3.5 characters of
English prose but 2.4 characters of log output
([1.1](../01-the-binder/1.1-room-is-not-free.md) measured both) — so they are excellent for *ratios
within one kind of text* and misleading for comparing prose against machine output.

**Tokens** are what the provider actually counts, bills and limits. Getting them means asking the
provider: `client.models.count_tokens(model=..., contents=...)`. That call is unusual and worth
understanding — it **generates nothing**. It runs the tokeniser and returns a number, so it does not
spend the generation quota that everything else in this curriculum is careful about
([Addendum 02](../../../../docs/02_ADDENDUM_ZERO_BUDGET_MODELS.md)); it is still an API call, so it is
not free of rate limits, and it still needs a key and a network.

Sutra's rule follows from that split:

- weigh in **characters** on every request, always, in code and in tests
  ([6.1](../06-in-production/6.1-testing-what-goes-in-the-window.md));
- convert to **tokens** when the number has to be exact — when you are setting a budget, comparing two
  different kinds of text, or explaining a cost to somebody.

And the scale itself is one small function, because measuring by organ is what makes a number
actionable ([2.2](../02-anatomy/2.2-six-organs-and-who-packed-them.md)).

## Why Sutra needs it

Because every rule in section 3 is a claim about size, and a claim about size without an instrument is
an opinion.

Concretely: Sutra is about to assert in its test suite that the desk's prompt stays inside a budget
([6.2](../06-in-production/6.2-a-budget-per-organ.md)). That assertion needs a function that takes an
assembled request and returns a number per organ. It has to be free — because it runs on every test —
which means characters, and it has to be honest about what it is measuring.

Day 24 then denominates the budget in the currency that matters (requests, and eventually tokens), and
the conversion factor comes from this part's second instrument.

## The mechanism

The scale, as Sutra's module:

```python
# sutra/context.py - the shape today's build brief asks for
"""Sutra's scale: what is in a model call, organ by organ (day 19)."""

from __future__ import annotations

from google.adk.models.llm_request import LlmRequest

ORGANS = ("instruction", "tools", "history", "message")


def weigh(request: LlmRequest) -> dict[str, int]:
    """The size of each organ of one assembled request, in characters."""
    instruction = str(request.config.system_instruction or "") if request.config else ""
    tools = "".join(
        tool.model_dump_json(exclude_none=True)
        for tool in ((request.config.tools if request.config else None) or [])
    )
    contents = request.contents or []
    history = "".join(str(content) for content in contents[:-1])
    message = str(contents[-1]) if contents else ""
    return {
        "instruction": len(instruction),
        "tools": len(tools),
        "history": len(history),
        "message": len(message),
    }
```

**Line by line:**

- `ORGANS` as a constant tuple — four measured organs rather than the six named in
  [2.2](../02-anatomy/2.2-six-organs-and-who-packed-them.md), because two of the six live *inside*
  others: templated facts are part of the instruction, and documents arrive inside a message or a tool
  result. Naming that limitation in the code is better than pretending to a resolution the data does
  not have.
- `str(request.config.system_instruction or "")` — the instruction after templating, which is what was
  actually sent ([17.4.1](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.1-state-steers-the-next-turn.md)).
- `tool.model_dump_json(exclude_none=True)` — serialising each declaration rather than `str()`-ing the
  list, because the pydantic repr elides and silently understates a long tool list
  ([2.3](../02-anatomy/2.3-the-menu-costs-more-than-the-handbook.md)).
- `contents[:-1]` and `contents[-1]` — history against the current message. Crude, and correct for the
  common case: the last content is what was just asked.
- Returning a **dictionary** rather than a total: the whole argument of
  [2.2](../02-anatomy/2.2-six-organs-and-who-packed-them.md) is that a total cannot be acted on.
- Everything is `len(...)` — no network, no key, no quota, so this can run in a unit test and on every
  request in production if you want it to.

And the second instrument, when the number has to be exact:

```python
# days/day-19-context-engineering-selection/lab/to_tokens.py
"""Converting a measured prompt from characters to the provider's own count."""

from google import genai

from sutra.config import load_env

MODEL = "gemini-3.7-flash"

PROSE = "You are Sutra, the triage desk. Say 'I don't know' when you do not know."
MACHINE = "2026-09-03T09:12:41Z INFO auth session refreshed tenant=northwind-prod\n" * 10


def main() -> None:
    load_env()
    client = genai.Client()
    for label, text in (("prose", PROSE), ("machine output", MACHINE)):
        tokens = client.models.count_tokens(model=MODEL, contents=text).total_tokens
        print(
            f"{label:16} {len(text):>6} chars  {tokens:>5} tokens  {len(text) / tokens:.2f} chars/token"
        )


main()
```

**Line by line:**

- Two texts of deliberately different **kind**, because the conversion factor is a property of the text
  and not a constant.
- `count_tokens(model=MODEL, ...)` — the tokeniser belongs to the model, so the count is only meaningful
  with the model string beside it.
- `.total_tokens` — the field on the response. The response also carries
  `cached_content_token_count`, which is `None` here and becomes interesting on Day 51.
- Two calls, and **no generations**: this is the instrument, not the model.

```bash

```

**Line by line:**

- Needs a key and a network. Costs no generation quota.

Measured against `gemini-3.7-flash` on 2026-09-03 — the same measurement as
[1.1](../01-the-binder/1.1-room-is-not-free.md), on two texts:

```text
the question          69 chars      20 tokens  (3.5 chars/token)
kitchen sink       15071 chars    6220 tokens  (2.4 chars/token)
```

Same tokeniser, same model, and a conversion factor that differs by nearly fifty per cent depending on
what the text is. Which is why Sutra weighs in characters for **ratios inside one organ** and converts
to tokens before quoting a number to anybody.

## When it breaks

**You compare characters across kinds of text and reach the wrong conclusion.**

No error. A 10,000-character instruction and a 10,000-character log are not the same cost: the log is
roughly 4,100 tokens and the instruction roughly 2,900. Character budgets are per organ for this
reason, and comparing organs to each other is where the conversion is needed.

**`count_tokens` fails without a key.**

```text
ValueError: No API key was provided. Please pass a valid API key. Learn how to create an API key at https://ai.google.dev/gemini-api/docs/api-key.
```

Measured on 2026-09-03 by constructing a client with the key removed from the environment. The same
failure as any other client call: `count_tokens` needs the SDK configured; it just does not need the
model to think.

**You put `count_tokens` in a unit test.** It works, and then the suite needs a key, a network and a
rate limit. Keep the network instrument in the lab and in the occasional deliberate measurement; keep
the free instrument in the tests
([6.1](../06-in-production/6.1-testing-what-goes-in-the-window.md)).

## In production

**Weigh every call, cheaply, and record the number.**

The version a professional runs computes the character sizes on every request — it costs nothing —
and logs them next to the model call. Once that exists, prompt-size questions become graphs, and the
graph that matters is the distribution rather than the average
([1.2](../01-the-binder/1.2-three-costs-in-one-scene.md)).

**What changes at scale** is that the provider gives you the real number for free, after the fact.
Every response carries usage metadata with the input token count, so a production system should record
*that* rather than estimate: the estimate is for the tests and the decisions before the call, and the
measurement is for the ledger afterwards. Day 24's accounting is built on the second.

**What fails only under real traffic** is the assumption that your test's ratio holds. Real prompts mix
prose, JSON, logs and occasionally base64, and each has its own factor. A character budget calibrated
on English will be generous for prose and tight for machine output, which is the right way round but
worth knowing.

**The review comment**: *"we are estimating prompt size in characters and reporting it as tokens. Pick
one, and say which in the field name."*

**The interview question**: *"how do you measure what a prompt costs before you send it?"* The answer
that shows the trade-off: *"characters for free, on every call, per organ — and the provider's
`count_tokens` when the number has to be exact, which is a call that runs the tokeniser and generates
nothing."*
