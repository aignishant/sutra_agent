# 1.1 — Room is not free

## One-line answer

A context window is a **budget you spend on every call**, not a container you fill once — so the
question that matters is never *"will it fit?"* but *"what does the model need to answer this
step?"*.

## The story

The notice in the lift.

*8 persons — 630 kg.* Nobody has ever read that and thought *"excellent, we must get to 630"*. It is
a limit, not a target, and everybody in the building understands the difference without being told.

What people do get wrong is the other half. Eight is the number the lift can carry, and it is not the
number that makes the lift *good*. Eight people means a slower ride, more stops, a longer wait for the
person on the fourth floor, and somebody standing in front of the buttons. The lift works fine at
eight and works better at three.

The capacity was never the goal. It was the ceiling.

## The idea in plain language

Since [Day 2](../../../day-02-llm-mechanics/LESSON.md) you have known the mechanism: a model has no
memory between calls, and its entire universe is the request you send. Everything the model appears
to "know" about this conversation is text you put in front of it, this time, along with everything you
put in front of it last time.

That package has a maximum size — the **context window** — and modern windows are enormous. Gemini's
are measured in hundreds of thousands of tokens, sometimes a million. Which produces a very natural
and completely wrong conclusion: *there is plenty of room, so put everything in.*

Three things make room expensive, and only one of them is obvious:

- **Every token is spent on every call.** Not once — every call. The loop you hand-rolled on
  [Day 3](../../../day-03-loop-hand-rolled/LESSON.md) re-sends the whole conversation at every step,
  so a fact you added on turn one is paid for again on turn forty.
- **Every token costs time.** The model has to read the input before it can produce the first word of
  output, and on a multi-step run that delay is multiplied by the number of steps.
- **Every token costs attention.** This is the one people do not believe until they measure it: a
  relevant fact in a big document is *harder* for the model to use than the same fact in a small one,
  and the position of that fact in the request changes the answer
  ([3.3](../03-selection/3.3-position-is-not-presence.md), and the paper this day cites).

So the discipline this day teaches has a name — **context engineering** — and one sentence:
**decide what earns a place in the window, per call, on purpose.** It is the closest thing agent
engineering has to a core craft, and it is not a performance optimisation. It is what stops an agent
becoming slower and worse as a conversation becomes more valuable.

Today is the selection half: what goes in, and how to weigh it. Tomorrow (Day 20) is the removal half:
what to do about the organ that grows on its own.

## Why Sutra needs it

Because Sutra runs on a free tier of **20 requests per day**
(`docs/PACKAGES.md`, 2026-08-25), and because the shape of Sutra's work makes the problem worse than
average.

A support conversation grows. Each turn adds a question, an answer, and often a tool result. By turn
ten the request carries the whole history, and Sutra has spent ten requests to get there. The quota is
not the only ceiling — the phase gate says *budgets enforced* — but it is the one you meet first, and
it arrives sooner the more you pack.

There is a nearer reason. Days 17 and 18 gave Sutra two stores full of facts, and the natural next
thought is *"put them in the prompt so the model knows"*. Some of that is right and most of it is
wrong, and the difference is the whole of section 3.

## The mechanism

The smallest honest demonstration: the same question, weighed twice.

```python
# days/day-19-context-engineering-selection/lab/weigh.py
"""Two packages for the same question, weighed on the provider's own scale."""

from google import genai

from sutra.config import load_env

MODEL = "gemini-3.7-flash"
QUESTION = "Ticket 4521: users keep getting logged out. What is the likely cause?"
CURATED = (
    "Known context: severity=high. KB-104: a SameSite cookie change logs users out on redirect."
)
LOG_LINE = "2026-09-03T09:12:41Z INFO auth session refreshed for tenant northwind-prod\n"
KITCHEN_SINK = LOG_LINE * 200


def weigh(client: genai.Client, label: str, text: str) -> None:
    tokens = client.models.count_tokens(model=MODEL, contents=text).total_tokens
    print(
        f"{label:16} {len(text):>7} chars  {tokens:>6} tokens  ({len(text) / tokens:.1f} chars/token)"
    )


def main() -> None:
    load_env()
    client = genai.Client()
    weigh(client, "the question", QUESTION)
    weigh(client, "curated", f"{CURATED}\n\n{QUESTION}")
    weigh(client, "kitchen sink", f"{KITCHEN_SINK}\n\n{QUESTION}")


main()
```

**Line by line:**

- `client.models.count_tokens(...)` — the provider's own tokeniser, over the network, and it **does not
  generate anything**. It is the one API call in this curriculum that produces no text, and it is why
  today can be measured without spending the generation quota
  ([4.1](../04-measuring/4.1-a-scale-for-prompts.md) says more about what it does and does not cost).
- `model=MODEL` — a tokeniser belongs to a model, so the count is only meaningful next to the model
  string. A different model can count the same text differently.
- `QUESTION` is identical in both packages. That is the experiment: same task, same model, different
  packing.
- `CURATED` is what Day 17's state templating would inject
  ([17.4.1](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.1-state-steers-the-next-turn.md)):
  two facts, chosen.
- `LOG_LINE * 200` — a fake log, cheaply. Real logs are **harder** than this, not easier: repeated text
  compresses well and varied noise does not.
- `len(text) / tokens` — the ratio, printed because it is not a constant and the difference between the
  two lines is a finding of its own.


**Line by line:**

- Three `count_tokens` calls and **zero** generations. Today's whole budget is in
  [§6 of the hub](../../LESSON.md).

Measured against `gemini-3.7-flash` on 2026-09-03:

```text
the question          69 chars      20 tokens  (3.5 chars/token)
curated              161 chars      45 tokens  (3.6 chars/token)
kitchen sink       15071 chars    6220 tokens  (2.4 chars/token)
```

Same question, same model. **45 tokens against 6,220** — a factor of 138 — and the kitchen-sink version
does not contain a single fact the curated one lacks. It contains two hundred copies of a line that
answers nothing.

Read the ratios too. Prose runs about 3.5 characters per token; the log line runs 2.4, because
timestamps, identifiers and punctuation fragment into many small tokens
([Day 2's subword-units paper](../../../day-02-llm-mechanics/papers/01-subword-units.md) is why).
**Machine-generated text is the most expensive text you can paste**, per character, and it is exactly
what people paste most.

## When it breaks

**Nothing errors. That is the whole difficulty of this day.**

A request that is too big does not usually fail. It costs more, takes longer, and answers slightly
worse, and every one of those is invisible unless somebody measures. The failures that *do* have error
text arrive much later and look like something else:

```text
429 RESOURCE_EXHAUSTED. {'error': {'code': 429, 'message': 'You exceeded your current quota, ...'}}
```

That is the free tier's daily ceiling — measured on
[Day 16](../../../day-16-built-in-tools-with-brakes/parts/07-failure-lab/7.1-the-spare-that-does-not-fit.md)
— and it arrives sooner the heavier each call is. The connection between "we paste the whole log" and
"we run out at lunchtime" is real and nobody experiences it as causal.

**The window that actually fills.** When it does happen, the model or the SDK refuses the request
rather than truncating it silently, and the message names a token limit. If Sutra ever sees that, the
cause is nearly always one pasted document rather than an accumulation of turns.

## In production

**Ask the question per call, not per system.**

The habit that separates people who have done this: before adding anything to a prompt, ask *what does
the model need to answer **this** step?* Not "what do we have" — the answer to that is always
"everything" — and not "what might be useful", because everything might be useful.

**What changes at scale** is that context becomes the dominant cost line. Output tokens are usually a
few hundred; input tokens are however many you packed, multiplied by every step of every run. Teams
that measure this are surprised by the ratio the first time, and it changes what they build.

**What fails only under real traffic** is the long conversation. Development sessions are three turns.
Real ones are forty, and the cost of turn forty is the sum of everything before it
([1.3](1.3-the-organ-that-grows-by-itself.md)). A system that is fine in testing can be unusable — or
unaffordable — at the length users actually reach.

**The review comment**: *"this pastes the whole file into the prompt. Which part of it answers the
question, and can we send only that?"*

**The interview question**: *"the model has a million-token window. Why not use it?"* The answer that
shows judgement names three costs — quota, latency, attention — and adds the one that surprises
people: *a fact is harder to use in a big context than in a small one, so packing more can make the
answer worse.*
