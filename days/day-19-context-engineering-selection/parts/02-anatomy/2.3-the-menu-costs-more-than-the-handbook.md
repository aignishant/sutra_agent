# 2.3 — The menu costs more than the handbook

## One-line answer

Each tool on an agent's list costs a few hundred characters of declaration **on every call** — six
small tools measured at 1,855 characters, against an instruction of 145 — and it costs the model a
decision as well.

## The story

The laminated menu with two hundred dishes.

You have eaten in that restaurant. Eight pages, plastic sleeves, photographs of about a third of the
items, and four sections that overlap in ways nobody can explain. There is a good meal in there
somewhere.

What actually happens is that you read three pages, lose confidence, and order the thing you always
order — or worse, you ask the waiter, they say *"the noodles are good"*, and you order noodles. The
menu did not help you choose. It made choosing harder, and the size of it is exactly why.

The place across the road has nine dishes on a card. Everybody who eats there orders something they
wanted.

## The idea in plain language

Every tool an agent holds is described to the model on every single call: its name, its description,
and the full JSON schema of its arguments. That description is written from your function's signature
and docstring ([Day 10](../../../day-10-function-tools/LESSON.md)), which is why docstrings are not
documentation there — they are prompt text.

Two costs follow, and they are different in kind.

**The token cost is fixed, repeated and larger than people expect.** The measurement below puts six
small tools at 1,855 characters of declaration — twelve times the instruction in
[2.1](2.1-opening-the-envelope.md). Every call, whether the model uses a tool or not.

**The decision cost is not measurable here and is the bigger one.** A model choosing between six tools
makes a harder choice than one choosing between two, and the wrong choice is expensive: a call to the
wrong tool spends a request, produces a result the model has to reconcile, and often produces a second
wrong call. [Day 11](../../../day-11-tool-context/LESSON.md) taught tool design as a clarity
discipline; this is the same discipline with a number attached.

There is one more thing worth knowing, because it changes how you measure. The serialised declarations
grow steadily per tool, but `str(request.config.tools)` — the obvious way to look — **stops growing**
once the list gets long, because a pydantic repr elides. Measuring the repr says six tools cost the
same as five. Serialising each declaration says otherwise, and it is right. The mechanism below shows
both numbers so the trap is visible rather than described.

## Why Sutra needs it

Because Sutra's tool list is going to grow, and every future day adds candidates.

Today the desk has two or three. Phase 5 adds MCP toolsets that can expand to dozens
([Day 15](../../../day-15-toolsets-and-openapi/LESSON.md) built the mechanism that makes forty tools a
one-line change). Phase 8 adds agents-as-tools. Without a cost per tool, "add it, it might be useful"
is a free-looking decision, and it is not free: it is a permanent line item on every call plus a
harder choice for the model.

The design answer Sutra already reached for on Day 16 was **specialists**: an agent that holds one
capability and nothing else
([16.2.3](../../../day-16-built-in-tools-with-brakes/parts/02-one-at-a-time/2.3-the-specialist-you-write-yourself.md)).
That was forced by a platform rule. This part is the token-and-attention argument for the same shape,
which is the more general one.

## The mechanism

Six realistic tools, added one at a time, with the declaration size measured after each:

```python
# days/day-19-context-engineering-selection/lab/the_menu.py
"""What each tool on the list costs, on every call. Zero generate calls."""

import asyncio

from google.adk.agents import Agent
from google.adk.models.llm_request import LlmRequest


def lookup_ticket(ticket_id: int) -> dict:
    """Look up a support ticket by its identifier."""
    return {}


def search_kb(query: str) -> dict:
    """Search the internal knowledge base for an article."""
    return {}


def check_vendor(vendor: str, region: str) -> dict:
    """Check a vendor's published status page for the given region."""
    return {}


def escalate(ticket_id: int, reason: str, to_team: str) -> dict:
    """Escalate a ticket to another team, with a reason the receiving team will read."""
    return {}


def close_ticket(ticket_id: int, resolution: str) -> dict:
    """Close a ticket with a short resolution note."""
    return {}


def send_email(to: str, subject: str, body: str) -> dict:
    """Send an email to the customer on behalf of the support desk."""
    return {}


TOOLS = [lookup_ticket, search_kb, check_vendor, escalate, close_ticket, send_email]


async def declarations_for(count: int) -> int:
    agent = Agent(name="desk", model="gemini-3.7-flash", tools=TOOLS[:count])
    request = LlmRequest(model="gemini-3.7-flash")
    for tool in await agent.canonical_tools():
        await tool.process_llm_request(tool_context=None, llm_request=request)
    tools = request.config.tools or []
    return sum(len(t.model_dump_json(exclude_none=True)) for t in tools)


async def main() -> None:
    print("tools  declaration characters  cost of the last one")
    previous = 0
    for count in range(0, len(TOOLS) + 1):
        size = await declarations_for(count)
        print(f"{count:>5}  {size:>22}  {size - previous:>20}")
        previous = size


asyncio.run(main())
```

**Line by line:**

- Six tools with **realistic docstrings and arguments** — the kind of tools a support desk actually
  grows. A one-word docstring would understate the cost by a factor of two.
- `declarations_for(count)` builds a fresh agent with the first `count` tools, so each row is an
  independent measurement rather than a running mutation.
- `await agent.canonical_tools()` then `process_llm_request` on each — doing by hand what ADK does
  before every call ([16.2.1](../../../day-16-built-in-tools-with-brakes/parts/02-one-at-a-time/2.1-one-built-in-and-nothing-else.md)),
  so the request ends up holding exactly the declarations a real call would carry.
- `sum(len(t.model_dump_json(exclude_none=True)) ...)` — **the honest measurement**. Using
  `len(str(request.config.tools))` instead gives 460, 867, 1408, 2087, 2634 and then **2662** for six
  tools: the repr elides, so the sixth tool appears to cost 28 characters. It does not.
- `size - previous` — the marginal cost of each tool, which is the number that matters when somebody
  proposes adding one.

**Line by line:**

- No runner, no session, no model call: declarations are assembled before anything is sent.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
tools  declaration characters  cost of the last one
    0                       0                     0
    1                     276                   276
    2                     511                   235
    3                     818                   307
    4                    1201                   383
    5                    1514                   313
    6                    1855                   341
```

Six tools, 1,855 characters, and a marginal cost of roughly 235 to 383 characters each — driven mostly
by the docstring and the number of arguments. Compare that with the instruction from
[2.1](2.1-opening-the-envelope.md): **145 characters**. The menu is twelve times the handbook, and
neither number changes with the length of the conversation.

## When it breaks

**You measure with `str()` and conclude tools are free.**

```text
tools  declaration characters (via str)
    5                    2634
    6                    2662
```

That is the repr, and it says the sixth tool cost 28 characters. It did not; the repr stopped printing
the whole list. This is a measurement bug rather than a framework bug, and it is worth meeting once,
because *"the number stopped growing"* is a plausible-looking result that is completely false.

**The agent calls the wrong tool.** No error text — a tool call that succeeds and answers the wrong
question. This is the decision cost, and it grows with the number of similar-sounding tools. When it
happens, the fix is nearly always fewer or better-separated tools rather than a longer instruction
telling the model which to use.

**The model invents a tool name**, which happens more often with a long list of similar ones. ADK's
message for it is unusually helpful — this is its template from `flows/llm_flows/functions.py` in the
installed 2.7.1, with a name and a tool list filled in to show the shape:

```text
Tool 'lookup_ticket_by_id' not found.
Available tools: lookup_ticket, search_kb, check_vendor

Possible causes:
  1. LLM hallucinated the function name - review agent instruction clarity
  2. Tool not registered - verify agent.tools list
  3. Name mismatch - check for typos
```

Read cause 1 as this part's argument written by the framework's authors: a hallucinated tool name is a
symptom of the menu, not of the model.

## In production

**Give each agent the smallest menu that lets it do its job.**

The version a professional writes has agents with three to six tools, not fifteen. When the list grows
past that, the answer is another agent — a specialist, composed as a tool
([16.2.3](../../../day-16-built-in-tools-with-brakes/parts/02-one-at-a-time/2.3-the-specialist-you-write-yourself.md)) —
so each model call chooses between a handful of clearly different options rather than fifteen
overlapping ones.

**What changes at scale** is that toolsets make this invisible. One entry on the `tools` list can
expand to forty declarations at run time
([15.1.1](../../../day-15-toolsets-and-openapi/parts/01-crate-not-list/1.1-one-line-many-tools.md)),
so the source shows one line and the request carries thousands of characters. Measuring the resolved
declarations rather than the written list is the only way to see it, which is why the script above
resolves through `canonical_tools()`.

**What fails only under real traffic** is the description that was written for a human. Docstrings
written as documentation are long, and they are in every request. A tool description is prompt text
with a token cost, and the discipline is the same as for the instruction: say what it does, when to use
it, and stop.

**The review comment**: *"this adds a fourth tool with a nine-line docstring. That is on every call for
this agent, for ever — is it a tool, or is it a specialist?"*

**The interview question**: *"what does adding a tool to an agent cost?"* The answer that shows you have
measured it: *"a few hundred characters of declaration on every call, plus a harder decision for the
model. The token cost is the smaller half."*
