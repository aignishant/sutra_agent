# 2.2 — Six organs and who packed them

## One-line answer

A request has six recognisable parts, and the useful question about each is not *what is it* but
**who put it there** — because that tells you which dial you are allowed to turn.

## The story

The tray at airport security.

Everything you were carrying, laid out flat under a light: laptop, keys, the belt, a bag of liquids in
a see-through pouch, the coat you were wearing, and the boarding pass you have been holding since the
car park.

The interesting thing about the tray is not that it holds your possessions. It is that each item got
there for a *different reason*. The laptop is out because there is a rule about laptops. The liquids
are in a pouch because there is a rule about liquids. The coat is off because somebody told you at the
front of the queue. The keys are there because you put them there, and the boarding pass is there
because you did not want to put it down.

Six things in a tray, four different reasons, and if you want to travel lighter next time you have to
know which is which.

## The idea in plain language

[2.1](2.1-opening-the-envelope.md) printed the request in four fields. Those four fields hold six
distinguishable **organs**, and each has a different owner and a different growth behaviour:

| Organ | What it is | Who put it there | How it grows |
| --- | --- | --- | --- |
| **System instruction** | the persona and standing rules ([Day 6](../../../day-06-instructions-and-personas/LESSON.md)) | you, on the agent | fixed, and paid on every call ([2.4](2.4-a-subscription-not-a-purchase.md)) |
| **Tool declarations** | name, description and argument schema per tool ([Day 10](../../../day-10-function-tools/LESSON.md)) | your `tools=[…]` | fixed per tool, and larger than you think ([2.3](2.3-the-menu-costs-more-than-the-handbook.md)) |
| **Templated facts** | `{key}` values from state ([Day 17](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.1-state-steers-the-next-turn.md)) | you, by writing the placeholder | as big as the values you chose |
| **Conversation history** | prior messages, tool calls and results | the framework, from session events | **by itself, every turn** ([1.3](../01-the-binder/1.3-the-organ-that-grows-by-itself.md)) |
| **Documents** | pasted file contents, search results, loaded artifacts ([Day 18](../../../day-18-artifacts-that-survive/parts/04-in-the-run/4.3-what-the-model-cannot-see.md)) | a tool, or you | in jumps, and the jumps are large |
| **The current message** | what the user actually asked | the user | it is what it is |

Two of those rows deserve a sentence each, because they are the ones people misplace.

**Templated facts are not state.** Only the keys you named in the instruction reach the model.
[2.1](2.1-opening-the-envelope.md) measured it: `severity` was templated and arrived, `note_file` sat
in state and did not. State is your code's memory; the templated subset is the model's.

**Documents arrive in jumps.** Every other organ changes by tens or hundreds of characters. A pasted
log or a loaded artifact changes the request by thousands — [1.1](../01-the-binder/1.1-room-is-not-free.md)
measured 45 tokens against 6,220 for the same question. One organ is responsible for almost every
prompt that got out of hand.

The reason to learn the ownership column is that it is a list of the dials you can actually turn. You
cannot shrink the user's message. You can absolutely shrink the tool list, the instruction, the
templated set and — with tomorrow's compaction — the history.

## Why Sutra needs it

Because Sutra now has facts in two stores, tools on an agent, an instruction with placeholders and
artifacts on disk, and the question *"why is this prompt so big?"* has six possible answers.

Having the anatomy means the diagnosis is a measurement rather than an argument: print the four
numbers ([2.1](2.1-opening-the-envelope.md)), find the organ that is large, and go to the owner of
that organ. Day 24's budgets will be per organ for exactly this reason — a total tells you there is a
problem and nothing about whose it is.

## The mechanism

The organs, side by side, in one request. This script builds a deliberately over-packed call and
prints each organ's contribution:

```python
# days/day-19-context-engineering-selection/lab/organs.py
"""One request, six organs, one number each. Zero generate calls."""

import asyncio
from collections.abc import AsyncGenerator

from google.adk.agents import Agent
from google.adk.events import Event, EventActions
from google.adk.models import BaseLlm, LlmRequest, LlmResponse
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

LOG = "2026-09-03T09:12:41Z INFO auth session refreshed for tenant northwind-prod\n" * 20


class Recorder(BaseLlm):
    seen: list = []

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        self.seen.append(llm_request)
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text="noted")]))


def lookup_ticket(ticket_id: int) -> dict:
    """Look up a support ticket by its identifier."""
    return {"id": ticket_id}


model = Recorder(model="recorder")
agent = Agent(
    name="desk",
    model=model,
    instruction="You are Sutra, the triage desk. Severity is {severity?}.",
    tools=[lookup_ticket],
)


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="u1")
    await service.append_event(
        session=session,
        event=Event(author="intake", actions=EventActions(state_delta={"severity": "high"})),
    )
    runner = Runner(app_name="sutra", agent=agent, session_service=service)

    async for _ in runner.run_async(
        user_id="u1",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="first question")]),
    ):
        pass
    async for _ in runner.run_async(
        user_id="u1",
        session_id=session.id,
        new_message=types.Content(
            role="user", parts=[types.Part(text=f"here is the log:\n{LOG}\nwhat happened?")]
        ),
    ):
        pass

    request = model.seen[-1]
    instruction = str(request.config.system_instruction or "")
    tools = "".join(t.model_dump_json(exclude_none=True) for t in (request.config.tools or []))
    history = "".join(str(c) for c in request.contents[:-1])
    current = str(request.contents[-1])

    for label, text in (
        ("system instruction", instruction),
        ("tool declarations", tools),
        ("history (earlier turns)", history),
        ("the current message", current),
    ):
        print(f"{label:26} {len(text):>7} chars")
    print(f"{'of which, the pasted log':26} {len(LOG):>7} chars")


asyncio.run(main())
```

**Line by line:**

- `LOG` — twenty lines of machine output, pasted into the **second** question. That is the document
  organ, arriving the way it always does: inside a user's message.
- The first turn is short and boring, so that on the second turn there is a real history to separate
  from the current message.
- `request.contents[:-1]` against `request.contents[-1]` — splitting the conversation into *what came
  before* and *what was just asked*. Those are two different organs with two different owners, and
  they live in the same field.
- `"".join(t.model_dump_json(...))` — the tool declarations, serialised rather than `repr`'d, for the
  reason [2.1](2.1-opening-the-envelope.md) explains.
- The templated fact does not get its own line, deliberately: it is **inside** the instruction, which is
  the point of the row in the table above. Its cost is part of your instruction's cost.
- The last line separates the pasted log from the message that carried it, which is the number that
  matters in the diagnosis.

## When it breaks

**You optimise the wrong organ.**

No error, just wasted effort. Somebody spends an afternoon shortening the instruction from 145
characters to 90 while every call carries a 15,000-character pasted log. The instruction was 1% of the
problem, and it was the only organ that felt like writing.

**You cannot find the organ at all, because it is inside another one.** Templated facts hide in the
instruction; documents hide in the current message or in a tool result inside the history; an artifact
loaded by `load_artifacts`
([18.4.3](../../../day-18-artifacts-that-survive/parts/04-in-the-run/4.3-what-the-model-cannot-see.md))
appears as an extra content block that looks like conversation. Splitting `contents` by index, as this
script does, is the crude version; a real breakdown walks the parts and classifies them.

**The history contains a document.** The most expensive combination on this page: a pasted log enters
as a message, and then — because history is re-sent every turn
([1.3](../01-the-binder/1.3-the-organ-that-grows-by-itself.md)) — it is paid for again on every
subsequent call, for ever. A document that arrives once costs once; a document that arrives *in the
conversation* costs for the rest of it.

## In production

**Instrument per organ, not per request.**

The version a professional builds records four or five numbers per call rather than one. It costs
almost nothing and it turns every future prompt-size discussion into a lookup. The alternative — a
single total — tells you that something grew and gives you six suspects.

**What changes at scale** is that the organs decouple. In a graph, different nodes have different
instructions and different tool lists but share one history, so the fixed organs vary per node and the
growing one is common. Attributing cost per node without attributing it per organ produces numbers
that look like nonsense.

**What fails only under real traffic** is the document organ's variance. Instructions and tool lists
are the same size for every user; documents are whatever somebody pasted. That single organ is
responsible for nearly all the spread between a median request and a ninety-ninth-percentile one.

**The review comment**: *"the prompt got bigger. Which organ? If we do not know, we are guessing at the
fix."*

**The interview question**: *"a request to your model is 20,000 tokens. Where do you look?"* The answer
that shows method: *"I break it into organs — instruction, tool declarations, templated facts, history,
documents, the user's message — because each has a different owner and only two of them can plausibly
be that big."*
