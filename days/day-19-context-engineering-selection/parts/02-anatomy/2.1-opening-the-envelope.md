# 2.1 — Opening the envelope

## One-line answer

You can read the exact request your agent sends without any provider by putting a recording model in
its place — and the first thing the recording shows is that **the tool declarations are three and a
half times the size of the instruction** you spent an afternoon writing.

## The story

The first time you read an itemised phone bill.

You know roughly what you pay, because it is the same every month and it comes out of the account on
the same day. Then one month it is different, so you actually open it, and there are eleven lines on
it.

Some of them you expected. Some are small and constant and you have been paying them for four years —
an insurance thing, a service charge, a number you cannot remember agreeing to. And one line, which is
the reason the bill changed, is a single call to a number you do not recognise.

Nothing on that bill was hidden. It was itemised the whole time. You had simply never looked at what
you were buying.

## The idea in plain language

Every model call Sutra makes is a request object, and until now the framework has assembled it and you
have not looked. This part is looking.

The trick is the one Day 17 used for instructions
([17.4.1](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.1-state-steers-the-next-turn.md)):
a **recording model**. `BaseLlm` is a small interface — one async method that takes an `LlmRequest` and
yields responses — so you can write a stand-in that saves what it was given and answers something
trivial. No key, no network, no quota, and the exact object the provider would have received.

What is in it:

- `request.config.system_instruction` — your instruction, with `{placeholders}` already filled
  ([17.4.1](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.1-state-steers-the-next-turn.md)),
  plus a line ADK adds about the agent's own name.
- `request.config.tools` — the tool declarations: for each tool, its name, its description and its
  argument schema, as JSON.
- `request.contents` — the conversation: a list of messages, alternating user and model, including
  tool calls and their results.
- `request.model` — the model string, which is how the built-ins from Day 16 decide whether they are
  allowed ([16.7.1](../../../day-16-built-in-tools-with-brakes/parts/07-failure-lab/7.1-the-spare-that-does-not-fit.md)).

Measuring those four is the whole of context engineering's diagnostic half. You cannot decide what
earns a place until you can see what is currently in the room, and most people have never looked.

## Why Sutra needs it

Because every claim in the rest of this day is checkable this way, and because the alternative is
guessing.

It matters immediately for the failure lab
([5.1](../05-failure-lab/5.1-in-state-and-not-in-the-window.md)): the belief that "the model knows
what is in state" is extremely common, and one line of this script settles it. And it matters for Day
24's budgets, which need a number per organ rather than a total.

There is a testing reason as well. Day 79's evals will want to assert things about prompts — that a
policy sentence is present, that a customer's raw text is not — and those assertions are made against
exactly this object.

## The mechanism

A four-turn conversation with an instruction, a templated state key and two tools, recorded:

```python
# days/day-19-context-engineering-selection/lab/envelope.py
"""What ADK actually puts in a model call. Zero generate calls."""

import asyncio
from collections.abc import AsyncGenerator

from google.adk.agents import Agent
from google.adk.events import Event, EventActions
from google.adk.models import BaseLlm, LlmRequest, LlmResponse
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types


class Recorder(BaseLlm):
    """Answers one short sentence and keeps every request it was sent."""

    seen: list = []

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        self.seen.append(llm_request)
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text="noted")]))


def lookup_ticket(ticket_id: int) -> dict:
    """Look up a support ticket by its identifier."""
    return {"id": ticket_id, "status": "open"}


def search_kb(query: str) -> dict:
    """Search the internal knowledge base for an article."""
    return {"article": "KB-104"}


model = Recorder(model="recorder")
agent = Agent(
    name="desk",
    model=model,
    instruction=(
        "You are Sutra, the triage desk. Answer in at most three sentences. "
        "This ticket is severity {severity?}."
    ),
    tools=[lookup_ticket, search_kb],
)


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="u1")
    await service.append_event(
        session=session,
        event=Event(
            author="intake",
            actions=EventActions(state_delta={"severity": "high", "note_file": "triage-4521.md"}),
        ),
    )
    runner = Runner(app_name="sutra", agent=agent, session_service=service)

    print("turn  instruction  tools  contents  messages")
    for turn, question in enumerate(
        ["users keep getting logged out", "what did you say?", "and the vendor?", "summarise"],
        start=1,
    ):
        async for _ in runner.run_async(
            user_id="u1",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=question)]),
        ):
            pass
        request = model.seen[-1]
        instruction = str(request.config.system_instruction or "")
        tools = "".join(t.model_dump_json(exclude_none=True) for t in (request.config.tools or []))
        print(
            f"{turn:>4}  {len(instruction):>11}  {len(tools):>5}  "
            f"{len(str(request.contents)):>8}  {len(request.contents):>8}"
        )

    first = model.seen[0]
    print()
    print("the system instruction, verbatim:")
    print(str(first.config.system_instruction))
    print("is note_file (a state key) anywhere in the request?")
    print("note_file" in str(first.config.system_instruction) + str(first.contents))


asyncio.run(main())
```

**Line by line:**

- `class Recorder(BaseLlm)` — the whole stand-in is six lines. `BaseLlm` requires one method, and
  yielding a single short response is enough to let the run complete.
- `self.seen.append(llm_request)` — keeping **every** request, because the comparison between turns is
  the measurement.
- Two ordinary function tools, each with a docstring and typed arguments — Day 10's shape. They are
  here to be counted, not called.
- `{severity?}` in the instruction, with `severity` written into state before the run — so the printed
  instruction shows the substitution having happened
  ([17.4.2](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.2-the-brace-that-raises.md)
  is why it carries the question mark).
- `note_file` is also in state and **not** in the instruction: it is the control, and the last two
  lines of output are about it.
- `t.model_dump_json(exclude_none=True)` for each tool, rather than `str(request.config.tools)` —
  because the pydantic **repr** elides long lists, so `str()` stops growing once there are several
  tools and silently understates them. Serialising each declaration is the honest measurement, and
  finding that out was worth the ten minutes ([2.3](2.3-the-menu-costs-more-than-the-handbook.md)
  depends on it).
- The four questions are short and boring on purpose, so the growth in `contents` is the accumulation
  rather than the content.

**Line by line:**

- Four turns, zero requests to a provider.

Measured on `google-adk` 2.7.1 on 2026-09-03 (framework log lines removed):

```text
turn  instruction  tools  contents  messages
   1          145    511       101         1
   2          145    511       268         3
   3          145    511       433         5
   4          145    511       592         7

the system instruction, verbatim:
You are Sutra, the triage desk. Answer in at most three sentences. This ticket is severity high.

You are an agent. Your internal name is "desk".
is note_file (a state key) anywhere in the request?
False
```

Four findings, and three of them are surprises.

**The tool declarations are the biggest fixed cost.** 511 characters against the instruction's 145 —
**three and a half times** — for two small tools with one argument each. Nobody budgets for this, and
it is paid on every call for as long as the tools are on the agent
([2.3](2.3-the-menu-costs-more-than-the-handbook.md)).

**The instruction is constant, and it is constant *per call*.** 145 characters, four times, and it
would be 145 characters on turn four hundred ([2.4](2.4-a-subscription-not-a-purchase.md)).

**ADK adds a line you did not write** — *"You are an agent. Your internal name is `desk`."* — after
your instruction. Small, and worth knowing it exists when you are counting.

**And the state key is not in the request.** `severity` reached the model because the instruction
templated it. `note_file` is sitting in state, perfectly readable by your code, and completely absent
from the model's universe. That is [5.1](../05-failure-lab/5.1-in-state-and-not-in-the-window.md), and
it is the most common wrong belief about agent memory there is.

## When it breaks

**`TypeError: Can't instantiate abstract class Recorder with abstract method generate_content_async`**

The one error you meet writing a recording model: `BaseLlm` declares the method abstract, and the
signature has to match — `async def generate_content_async(self, llm_request, stream=False)`, yielding
`LlmResponse` objects. It is a generator, so the body must `yield` rather than `return`.

**The recorder answers and the run never ends.** If the stand-in yields a response with no text, or
with a function call for a tool that does not exist, the runtime may keep going. Yield one short text
part and the turn completes.

**You measure the wrong request.** `model.seen[-1]` after a multi-step turn is the **last** model call
of that turn, not the first. A turn with a tool call makes two, and their contents differ — the second
one contains the tool's result. When a number looks wrong, check how many requests the turn actually
made.

## In production

**Keep a way to see the request, and use it before arguing about prompts.**

The version a professional keeps is exactly this: a recording model in the test suite, and a debug flag
in the real system that logs the assembled request. Prompt arguments end quickly when somebody prints
what was actually sent, and they last for hours when nobody can.

**What changes at scale** is that this becomes a privacy surface. The assembled request contains
everything the model sees — customer text, templated facts, tool results — so a log line that dumps it
is a log line containing personal data. That is worth deciding deliberately: log the **sizes** by
default, and the contents only behind a flag that somebody has to turn on.

**What fails only under real traffic** is the assumption that requests look like your test's. Real ones
carry longer histories, larger tool results and occasionally an artifact
([18.4.3](../../../day-18-artifacts-that-survive/parts/04-in-the-run/4.3-what-the-model-cannot-see.md)).
The recorder tells you the shape; only production tells you the size.

**The review comment**: *"we are guessing about what the model sees. Put a recorder in front of it and
print the four numbers."*

**The interview question**: *"how do you know what your agent actually sends to the model?"* The answer
that shows you have done it: *"a stand-in model that records the request — no key, no quota — and then
you look at the instruction, the tool declarations and the contents separately, because they have
completely different growth behaviour."*
