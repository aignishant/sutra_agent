# 4.1 — Where the config goes

## One-line answer

Context caching is configured once on the `App`, not on each agent — `App(context_cache_config=
ContextCacheConfig(...))` — and that placement is the 2.x composition model showing through:
cross-cutting behaviour is attached to the thing that runs the graph, never to the nodes inside it.

## The story

A family moves into a rented flat and the geyser trips the power. The landlord's man comes, looks at
the geyser, and shrugs. They call an electrician, who does not look at the geyser at all. He goes
straight to the small grey box by the front door, opens it, and points at one switch.

The family had been thinking about the problem as *the geyser's problem*. The electrician thinks
about it as *the flat's problem*, because the thing that decides how much current anything in the
flat may draw is not in any appliance. It is in a box that every appliance is downstream of.

The useful part of this is not that he was right. It is that he knew where to look **before** he knew
what was wrong, because he knew which decisions live in a box and which live in a device. Ask him and
he will tell you the rule in one sentence: *anything that is true for the whole flat is in the box.*

## The idea in plain language

ADK 2.x has three levels of thing, and knowing which level a setting belongs to is most of knowing
where to find it.

| Level | What it is | What belongs here |
| --- | --- | --- |
| `App` | the whole deployment: the root agent, the plugins, the runtime policies | anything true for every request |
| a **node** in the workflow graph | one step: an agent, a tool call, a branch | that step's behaviour |
| `LlmRequest` | one call to a model | that call's payload |

**`ContextCacheConfig` goes on the `App`.** Not on an agent, not on a tool, not per request. When you
set it there it applies to every agent in the app, including sub-agents and anything the workflow
graph runs.

That placement is not arbitrary and it is worth understanding rather than memorising. A cache is
shared state on the provider's side, keyed by a fingerprint over the request prefix. If two agents
in the same app could set different caching policies, then two requests with an identical prefix
could have different cache lifetimes, and the entry either gets shared with the wrong policy or
duplicated for no reason. Making it an `App`-level setting removes the question.

## Why Sutra needs it

**This is 1.x → 2.x trap #1 wearing a small hat, and it is worth naming.**

Trap #1 (plan §5.1) is the node model: in ADK 1.x, composition happened by nesting agents in
`sub_agents` trees, and it was natural to look for every setting on an agent, because an agent was
the only container there was. In 2.x the graph Workflow Runtime is the composition layer and the
`App` is the thing that owns cross-cutting policy.

A reader who has been following 1.x tutorials will look for `cache_config=` on `LlmAgent`, not find
it, and conclude that ADK does not support caching. It does; the setting is one level up. Sutra meets
this shape repeatedly from Day 53 onwards, and caching is a cheap first encounter with it because
getting it wrong produces a clean `TypeError` rather than a subtle behaviour change.

Sutra also has a concrete reason to care about "applies to every agent in the app". From Day 57 the
desk will be several agents — an orchestrator, a writer, a critic — and they do **not** share a system
instruction. Each has its own prefix, so each gets its own fingerprint and its own cache, all under
one policy. Setting the policy once and getting three caches is the correct behaviour, and it is only
obvious once you know the setting is not per agent.

## The mechanism

Verified against `adk.dev/context/caching/` on 2026-09-05, and against the installed
`google-adk==2.7.1` — `App.model_fields` carries `context_cache_config: Optional[ContextCacheConfig]`,
alongside `plugins`, `resumability_config` and `events_compaction_config`, which is good company for
it and tells you what kind of setting it is.

```python
from google.adk.agents.context_cache_config import ContextCacheConfig
from google.adk.apps.app import App

app = App(
    name="sutra-desk",
    root_agent=root_agent,
    context_cache_config=ContextCacheConfig(
        min_tokens=4096,
        ttl_seconds=1800,
        cache_intervals=10,
    ),
)
```

**Line by line:**

- `from google.adk.agents.context_cache_config import ContextCacheConfig` — note the module path says
  `agents`, not `apps`, which is a leftover from where the class lives rather than where it is used.
  Importing it from `google.adk.apps` fails; this is the path that works in 2.7.1.
- `App(...)` — the container. `name` is what appears in traces and in the dev UI; `root_agent` is the
  entry node.
- `context_cache_config=` — one setting, applied to every agent under `root_agent`. There is no
  per-agent override and looking for one is the trap above.
- `min_tokens=4096` — **not** the default. The default is `0`, which means every request walks all the
  way to the provider's floor check before being refused
  ([3.1](../03-the-floor-we-never-reach/3.1-two-floors-and-a-first-turn-rule.md)). Setting it to the
  model's own floor makes the refusal yours, in your logs, at your gate.
- `ttl_seconds=1800` — the default, written explicitly. A default that is written down is a default
  someone has decided to keep; a default that is absent is one nobody has read.
- `cache_intervals=10` — also the default, and by
  [2.4](../02-the-context-cache/2.4-the-three-ways-a-cache-dies.md) it is very likely the limit that
  actually binds. Written explicitly for the same reason.

The three fields, with their real defaults, read from `ContextCacheConfig.model_fields` in 2.7.1 on
2026-09-05:

| Field | Type | Default | What it means |
| --- | --- | --- | --- |
| `cache_intervals` | `int` | `10` | how many invocations one cache may serve |
| `ttl_seconds` | `int` | `1800` | how long the provider holds it |
| `min_tokens` | `int` | `0` | your own floor, below which do not bother |
| `create_http_options` | `HttpOptions \| None` | `None` | timeout for the create call itself |

The fourth field is easy to skip and worth a sentence. `create_http_options` puts a timeout on the
cache-creation call. adk.dev's page states the behaviour if it fires: *"If HTTP timeout occurs during
cache creation, the request proceeds uncached."* That is the correct design — a caching optimisation
must never fail the request it was optimising — and it is also why a provider having a bad afternoon
shows up as a caching outage rather than as an error, which nobody will notice unless they are
counting.

Sutra's own placement, once `sutra/cache.py` exists, is the build brief's `context_cache_config()`
function returning this object, so the numbers live in one module with their measurements beside them
and the `App` construction stays readable.

## When it breaks

The break is the trap, and it is loud, which is the good news:

```python
from google.adk.agents.llm_agent import LlmAgent

agent = LlmAgent(
    name="desk",
    model="gemini-3.7-flash",
    context_cache_config=ContextCacheConfig(min_tokens=4096),
)
```

**Line by line:**

- Everything here is plausible. `LlmAgent` is the right class, the model string is right, the config
  object is right.
- `context_cache_config=` on an agent is the 1.x habit: in a world where agents were the only
  container, this is where it would go.
- Pydantic models reject unknown fields, so this does not silently do nothing.

```traceback
    For further information visit https://errors.pydantic.dev/2.13/v/extra_forbidden
```

`Extra inputs are not permitted` is the message to recognise. It does not say "this belongs on the
App" — no framework says that — but it does say, unambiguously, that the field does not exist here,
which is better than a silently ignored keyword. The smallest fix is to move the argument to the
`App`.

The quieter break is the one with no traceback: **forgetting the `App` entirely.** Plenty of ADK code
constructs a `Runner` around a root agent without an `App` wrapper, and in that shape there is nowhere
for the config to live, so caching is simply off. No error, no log line, no cache. The tell is that
`event.cache_metadata` is `None` on every event, which is [4.2](4.2-what-the-metadata-says.md)'s
subject.

## In production

**What a professional writes instead.** They construct the `App` in one place and pass the config from
a named function rather than inline. `context_cache_config=cache.context_cache_config()` reads better
than three literals, and more importantly it gives the numbers a home where their measurements can sit
beside them as comments. A config object built inline in an `App` constructor is a config object with
nowhere to write down why.

**What degrades at scale.** One policy for every agent stops fitting once the agents diverge. A cheap
classifier node with a 200-token prompt and an expensive drafting node with a 6,000-token prompt want
different `min_tokens`, and ADK 2.7.1 gives you one number for both. The workaround is not a
per-agent config — it does not exist — but separate `App`s, which is a deployment decision. Worth
knowing before Day 57 builds a multi-agent desk, so that the constraint is discovered at design time
rather than at tuning time.

**The failure mode that only appears with real traffic.** `create_http_options` left at `None` means
the cache-creation call uses the client's default timeout. Under provider stress, cache creation is
the first thing to slow down, and every request that would have created a cache now waits on that
call before proceeding uncached. The result is added latency on precisely the requests that were
already slow, and it is invisible unless the create call is timed separately from the generate call.

**The review comment a senior engineer leaves:** *"`context_cache_config` on the App is right, but
you've left `min_tokens` at the default 0 and pinned a gemini-3 model. That means every sub-4096-token
request produces a provider-floor log line instead of ours. Set it to 4096 with a comment citing where
4096 comes from, so the day we change models we re-read the line."*

**The interview question:** *"Where do you configure caching in ADK, and why there?"* An honest
answer: *"On the `App`, not on the agent — `App(context_cache_config=ContextCacheConfig(...))`. It
sits with plugins and the resumability config, which tells you what kind of setting it is:
cross-cutting policy for the whole deployment. The reason it can't be per-agent is that the cache is
shared provider-side state keyed on a hash of the request prefix, so two agents with different
lifetimes on the same prefix would either share an entry under the wrong policy or duplicate it. It's
also the 1.x-to-2.x trap in miniature — people who learned the sub-agent tree model go looking for the
setting on `LlmAgent` and get `Extra inputs are not permitted`."*
