# 1.3 — A key is a promise about sameness

## One-line answer

A cache key is not an identifier for a stored thing; it is a claim that any two lookups producing
the same key deserve the same answer, and every serious caching bug is that claim turning out to be
false.

## The story

The dry cleaner writes a number on a paper slip, tears it in half, staples one half to your shirt
and hands you the other. When you come back you give him the number and he brings the shirt.

Now think about what the number is actually doing. It is not describing the shirt. It says nothing
about the colour, the size, the stain on the left cuff. It is a much smaller claim than that. It
says: *whoever brings me this number should receive what is stapled to its twin.*

The system works because the number is unique to a garment and because the person holding it is the
person who left it. Weaken either of those and it stops working in a very specific way — not by
losing the shirt, but by **confidently handing over the wrong one**. The shop does not slow down. It
does not error. It cheerfully gives a man his neighbour's trousers, because as far as the paper slip
is concerned that is exactly what it was asked to do.

There is a dry cleaner in every town that writes the number in pencil and reuses it after a month.
Everybody who has collected the wrong garment from that shop has met a cache key that dropped a
field.

## The idea in plain language

A **cache key** is a value you compute from a request, before you know the answer, such that:

> two requests with the same key are entitled to the same answer.

That is the whole definition, and notice what it is not. It is not "a label for the entry". It is
not "a hash of the input". Those describe how it is implemented. The definition is a **promise about
the world**, and it is the only part a program cannot check for you.

Three consequences follow immediately.

**1. Every field you leave out of the key is a claim that the field does not affect the answer.**
Leave the customer account out and you have claimed the answer is the same for every customer. Leave
the date out and you have claimed the answer does not change over time. These are claims, they are
often wrong, and they are invisible in the code — the key is a short expression and the claims it
makes are not written anywhere near it.

**2. Every field you put in reduces the hit rate.** A key with the account in it cannot be shared
across accounts, so the same question asked by three accounts is three misses. Correctness costs
hits. There is no configuration where it does not.

**3. A wrong key does not look like a bug.** It looks like a *better* cache. More collisions means
more hits, and the hit-rate graph goes up.
[5.3](../05-the-response-cache/5.3-the-key-that-dropped-the-field.md) measures exactly this, and it
is the most uncomfortable table in this day.

The two caches from [1.2](1.2-two-caches-wearing-one-name.md) each have a key, and they differ in
who writes it:

- The **context cache**'s key is computed by ADK. It is called a **fingerprint**, it is a SHA-256
  hash over the system instruction, the tools, the tool config, the model and the first N contents,
  truncated to sixteen hex characters. You do not choose it, but you do choose what goes into the
  things it hashes, which turns out to be the same power with a longer fuse
  ([2.3](../02-the-context-cache/2.3-the-fingerprint-is-the-key.md)).
- The **response cache**'s key is written by you, in `sutra/cache.py`, and nothing in the framework
  has an opinion about it.

## Why Sutra needs it

Day 44 built idempotency keys for MCP writes — part
[1.4](../../../day-44-client-hardening/parts/01-what-may-be-repeated/1.4-the-key-that-makes-a-write-repeatable.md)
— and it is worth naming the relationship, because the two ideas look alike and pull in opposite
directions.

An **idempotency key** says *"if you see this key again, do not do the work twice."* Its failure mode
is doing something twice that should have happened once.

A **cache key** says *"if you see this key again, do not do the work again, and hand back what you
got last time."* Its failure mode is handing back something that was never right for this asker.

The first protects the world from your retries. The second protects your quota, and it does it by
taking a small, deliberate risk with correctness. Sutra needs both and must not confuse them: a
support desk that hands agent B an answer generated for agent A's customer has done something worse
than run out of quota.

The day's gate, `lab/gate.py`, has one finding entirely about this — finding 4 checks that
`cache_key("what is this account's api rate limit", "acme")` and the same question for `"borex"`
produce different strings.

## The mechanism

The key is a function. Here is the shape of the one the build brief asks you to write, with the
decision points marked rather than solved:

```python
def cache_key(question: str, tenant: str) -> str:
    """The promise: two asks with this key deserve the same answer.

    Every argument is here because leaving it out would be a claim about the
    world, and the docstring is where that claim gets written down.
    """
    normalised = " ".join(question.lower().split()).rstrip("?!. ")
    return f"{tenant}|{normalised}"
```

**Line by line:**

- `question: str, tenant: str` — the two arguments *are* the promise. A reader can see the entire
  claim being made without reading the body: the answer depends on the words and on whose account
  they were asked about, and on nothing else.
- `question.lower()` — a claim that case does not change the answer. True for a support desk; false
  for a cache in front of a case-sensitive code search.
- `" ".join(... .split())` — collapses runs of whitespace, so `"error 4403 "` and `"error  4403"`
  agree. `_log.py` contains both, because real agents type both.
- `.rstrip("?!. ")` — a claim that trailing punctuation carries no meaning. The log has
  `"how do I reset a customer's password"` and `"how do I reset a customer's password?"` from two
  different agents.
- `f"{tenant}|{normalised}"` — the tenant is a **prefix**, not appended, so that a key can be scanned
  by account without parsing it. The `|` is a separator that cannot appear in a tenant slug; if it
  could, two different pairs could produce one key and the promise would break in the separator
  rather than in the fields.
- The docstring is not decoration. It is the only place the claim exists in prose, and the review
  comment in *In production* is about exactly that.

The context cache's key is not a function you write, but it is a function you can call, and calling
it is the fastest way to understand what it promises:

```bash
cd days/day-51-caching-the-quota-lifeline/lab
uv run python fingerprint.py
```

**Line by line:**

- `fingerprint.py` asks ADK's own `_generate_cache_fingerprint` for the hash under six small edits to
  the request, so the boundary is discovered rather than described.
- It prints `same` or `MOVED` beside each, which is the only fact that matters: a moved fingerprint
  means the cached prefix is abandoned and a new one is created.
- The full walkthrough of what each edit means is
  [2.3](../02-the-context-cache/2.3-the-fingerprint-is-the-key.md); here it is only evidence that a
  key exists and is computable.

Measured on 2026-09-05:

```text
baseline                           834f3574ce20ab7b
rebuilt from scratch, identical    834f3574ce20ab7b  same
one trailing space added           dcce4e94bdb626e0  MOVED
retrieved rows pasted in           e7555594cb4dc3cc  MOVED
same request, prefix of 2 not 4    61e329bf7006dbc8  MOVED
the newest question edited         834f3574ce20ab7b  same
the tool list reversed             834f3574ce20ab7b  same
```

Both keys are on this page, and they read very differently. Yours is five lines you can argue about
in review. ADK's is a hash you cannot argue with — you can only change what goes into it.

## When it breaks

The break to feel here is the one where **the promise is false and nothing complains**. Take the
build brief's `cache_key` and delete one argument:

```python
def cache_key(question: str) -> str:  # the tenant is gone
    return " ".join(question.lower().split()).rstrip("?!. ")
```

**Line by line:**

- The signature changed and the body got shorter. That is the entire diff, and it will pass every
  type check, every linter and every test that does not know about tenants.
- The function still returns a string. It still produces stable keys. Its hit rate goes **up**.
- What it no longer does is keep the promise, and there is no syntax for a broken promise.

Now the actual failure, from `lab/collide.py`, run against twelve asks of one question whose answer
genuinely differs per account:

```text
2. the same question, three accounts  (12 asks)
key recipe                    hits  hit rate  wrong  wrong of hits
tenant dropped from key         11      92%      8            73%
tenant kept in key               9      75%      0             0%
```

Ninety-two per cent against seventy-five. The broken key wins on the only metric anybody puts on a
dashboard, and **seventy-three per cent of the answers it served were another company's**.

There is no traceback for this. There is no log line, no warning, no slow request. The first symptom
is a support agent quoting a rate limit that belongs to somebody else's contract.

## In production

**What a professional writes instead.** The key function carries a docstring that states the promise
in one sentence and lists the fields deliberately excluded and why. Something like *"excludes the
agent's identity: two agents on the same account must get the same answer, and if they must not, this
line is the bug."* That sentence is the thing a reviewer can disagree with. A key expressed as an
inline f-string in the middle of a service method has no such sentence and is therefore unreviewable.

**What degrades at scale.** Keys accumulate dimensions. A cache that starts keyed on the question
ends up keyed on question, tenant, locale, product version, feature flags and model name, because
each of those turned out to change the answer once. Each addition is correct and each one costs hit
rate, so the cache silently converges on doing nothing while still costing memory and complexity. The
discipline is to make each dimension's arrival a decision with a measured hit-rate cost beside it,
which is what `hitrate.py` is for.

**The failure mode that only appears with real traffic.** A key that omits the model name is
harmless right up until the day someone changes the model. Then every entry in the store is an answer
from the previous model, served as if it came from the new one, and the A/B comparison that was
supposed to evaluate the change is reading stale output. Day 9 taught that a model is a string in a
config field; a cache key that does not include that string has quietly promised that the choice does
not matter.

**The review comment a senior engineer leaves:** *"This key is `hash(question)`. Write down, in the
docstring, what you are promising by leaving out the account, the locale and the model. If you can't
write the sentence, the field belongs in the key. And add a test that two accounts get different
keys — right now nothing in this repo would notice if that broke."*

**The interview question:** *"How would you choose a cache key?"* An honest answer: *"I'd start from
what the key promises rather than from what's convenient to hash. The key says any two requests
producing it deserve the same answer, so every field I leave out is a claim that the field doesn't
affect the answer, and I write those claims into the docstring so a reviewer can disagree with them.
The trap is that a worse key looks like a better cache — I measured a key that dropped the tenant on
my own traffic and it had a 92% hit rate against 75% for the correct key, and 73% of its hits were
another account's answer. So I never review a hit rate on its own; I want a correctness column beside
it, even if that column is only sampled."*
