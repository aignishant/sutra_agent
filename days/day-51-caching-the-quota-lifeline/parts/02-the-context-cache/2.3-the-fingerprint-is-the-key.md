# 2.3 — The fingerprint is the key

## One-line answer

ADK decides whether a cached prefix still applies by hashing the model, the system instruction, the
tools, the tool config and the first N contents into sixteen hex characters — so one trailing space
in the instruction abandons the cache, while reversing the whole tool list does not.

## The story

You lose a house key and take the spare to the locksmith at the end of the lane. He clamps it beside a
blank, runs the cutter along it, and hands you a copy.

Two things about that man are worth noticing, and they pull in opposite directions.

He is **unbelievably strict**. The copy is right or it is not. A cut a fraction of a millimetre too
shallow on one notch and the key goes into the lock, turns a little, and stops. It does not almost
work. There is no explaining to the lock that you live there.

And he is **completely uninterested** in everything else. He does not ask your name. He does not care
which house it is, what colour the door is, or whether you have three of these already. Those are all
genuinely facts about your key, and none of them is on the metal, so none of them can stop it turning.

Everyone who has had a key cut has met both surprises. Something you were sure was trivial ruined it;
something you were sure mattered turned out to be nothing to do with the lock at all.

## The idea in plain language

A **fingerprint** is a short string computed from a larger thing, such that the same input always
gives the same string and a different input almost always gives a different one. ADK's is a SHA-256
hash cut down to its first sixteen hex characters.

It is a cache key in exactly the sense of
[1.3](../01-two-caches-two-currencies/1.3-a-key-is-a-promise-about-sameness.md), and it makes exactly
the same kind of promise: *two requests with this fingerprint may share a cached prefix.* The
difference is that you do not write it. You can only change what goes into it.

What goes into it, in ADK 2.7.1:

| Cut into the key | Not on the key |
| --- | --- |
| the model name | the fresh tail — the current question |
| the cache scope (which backend) | anything after `contents[:count]` |
| the system instruction, in full | how many requests have used the cache |
| every `types.Tool`, canonicalised | the wall clock |
| the tool config | your session or user identity |
| `contents[:cache_contents_count]` | |

Two entries in that table do surprising work.

**"in full"** means byte for byte. A trailing space is a different instruction.

**"canonicalised"** means ADK sorts before it hashes: the function declarations inside each tool are
sorted by name, and the tools themselves are sorted by their JSON dump. So a tool registry that
returns its tools in a different order on each process start — a set, a dict iteration in a language
without ordering guarantees, a plugin load order — produces the **same** fingerprint. That is a
deliberate design decision in `_generate_cache_fingerprint`, and without it a caching agent would
lose its cache on every restart.

And the entry that is *not* on the key and matters most: **the number of contents cached**. The
fingerprint is computed over `contents[:count]`, and `count` is an argument. Hash the same
conversation with `count=2` instead of `count=4` and you get a different string, because you hashed
less of it. This is why `CacheMetadata` stores `contents_count` — validation has to hash the same
prefix length that creation hashed, or every check would fail.

## Why Sutra needs it

Sutra edits its own system instruction constantly and will keep doing so. Day 6 wrote it; Day 19
selected what goes into context; Day 20 built compaction; Day 40 added a filtering posture; Day 49
appended retrieved rows to it. Every one of those is a change to the most heavily weighted thing
the fingerprint is cut from.

Two of those are the point of this part:

- **Retrieved rows in the instruction** change the fingerprint on **every question**, because the
  rows are per-question. A cache that is recreated every request has cost two API calls to save one
  payload.
- **Compaction**, from Day 20, rewrites conversation history. That is `contents[:count]` changing
  underneath a live cache, which invalidates it — for every session, at whatever moment the
  compaction threshold happens to be crossed.

Neither of those produces an error. Both produce a bill.

## The mechanism

The recipe, from `google/adk/models/gemini_context_cache_manager.py` in `google-adk==2.7.1`, verified
on 2026-09-05 against `adk.dev/context/caching/` — which describes the fingerprint's *purpose* but
not its ingredients, so the ingredients are read from the installed source:

```python
fingerprint_data = {"model": llm_request.model, "cache_scope": self._cache_scope()}
if llm_request.config and llm_request.config.system_instruction:
    fingerprint_data["system_instruction"] = llm_request.config.model_dump(
        mode="json", include={"system_instruction"}, exclude_none=True
    )["system_instruction"]
if llm_request.config and llm_request.config.tools:
    tools_data = []
    for tool in llm_request.config.tools:
        if isinstance(tool, types.Tool):
            tool_data = tool.model_dump(mode="json", exclude_none=True)
            declarations = tool_data.get("function_declarations")
            if declarations:
                declarations.sort(key=lambda fd: fd.get("name") or "")
            tools_data.append(tool_data)
    tools_data.sort(key=lambda t: json.dumps(t, sort_keys=True))
    fingerprint_data["tools"] = tools_data
fingerprint_str = json.dumps(fingerprint_data, sort_keys=True, separators=(",", ":"))
return hashlib.sha256(fingerprint_str.encode()).hexdigest()[:16]
```

**Line by line:**

- `"model": llm_request.model` — the model is cut into the key, so switching from one Gemini model to
  another abandons every cache. Correct: a stored prefix belongs to the model that processed it.
- `"cache_scope": self._cache_scope()` — which backend this would talk to. A cache created against
  the AI Studio endpoint must not be reused against Vertex.
- `include={"system_instruction"}` inside a `model_dump` — the instruction is serialised through the
  SDK's own JSON rules rather than `str()`, so a structured instruction and a plain string that look
  the same in a terminal can still differ here.
- `declarations.sort(key=...)` then `tools_data.sort(key=...)` — the canonicalisation. Two sorts, not
  one: declarations within a tool, then tools within the list. This is what makes a reordered
  registry harmless.
- `separators=(",", ":")` and `sort_keys=True` — canonical JSON. Without `sort_keys` a dict that
  happened to be built in a different order would hash differently, and the whole thing would be
  unstable for no reason.
- `[:16]` — sixteen hex characters is 64 bits. Enough that two different prefixes colliding is not a
  practical concern; short enough to log on every line.

Now find the boundary by pushing on it:

```bash
cd days/day-51-caching-the-quota-lifeline/lab
uv run python fingerprint.py
```

**Line by line:**

- `fp(req, count)` calls ADK's real `_generate_cache_fingerprint`, so every row below is ADK's
  opinion and not a reimplementation of it.
- Each arm rebuilds the request from scratch and makes exactly one edit, so a moved hash has exactly
  one cause.
- The `same` / `MOVED` column is the only thing that matters operationally: `MOVED` means the stored
  prefix is abandoned and the next turn pays a create.

Measured on 2026-09-05:

```text
baseline                           834f3574ce20ab7b
rebuilt from scratch, identical    834f3574ce20ab7b  same
one trailing space added           dcce4e94bdb626e0  MOVED
retrieved rows pasted in           e7555594cb4dc3cc  MOVED
same request, prefix of 2 not 4    61e329bf7006dbc8  MOVED
the newest question edited         834f3574ce20ab7b  same
the tool list reversed             834f3574ce20ab7b  same
```

Six rows, and the two at the bottom are the ones worth arguing about.

**`the newest question edited ... same`.** The current question was changed completely and the
fingerprint did not move — because the question is in the fresh tail, outside `contents[:4]`. This is
the whole design working: the thing that changes every request is deliberately not cut into the key.

**`the tool list reversed ... same`.** The tool registry was reversed and nothing moved, because of
those two `sort` calls. Most readers predict `MOVED` here. If your agent builds its tool list from a
`set`, or from plugin discovery, or from a dict that gets rebuilt on each start, this line is the
reason your cache survives a restart.

**`one trailing space added ... MOVED`.** One character. A whole cache abandoned. There is no
normalisation, no strip, no tolerance — and there should not be, because a system instruction is
text the model reads and ADK has no business deciding which whitespace in it is meaningful.

**`retrieved rows pasted in ... MOVED`.** This is Sutra's actual configuration after Day 49, and it
moves the fingerprint on every single question.

**`same request, prefix of 2 not 4 ... MOVED`.** The same conversation, hashed over a shorter prefix.
Nothing about the request changed; only how much of it was hashed. This is why `contents_count` is
stored alongside the fingerprint.

## When it breaks

The break has no error text, so it has to be caught by counting. Run the lifecycle with an
instruction that drifts:

```bash
uv run python lifecycle.py --drift 1
```

**Line by line:**

- `--drift 1` changes the fingerprint on every single turn, which is what "retrieved rows in the
  instruction" does to a real desk.
- The script walks 200 turns through ADK's own three validity conditions and counts which one killed
  each cache.
- `caches created` counts creates; `extra API calls` adds the matching deletes.

Measured on 2026-09-05:

```text
caches created          : 200
  died, expired         : 0
  died, used up         : 0
  died, fingerprint     : 199

extra API calls (create + delete): 399
turns served per cache           : 1.0
```

Two hundred turns, two hundred caches, **399 extra API calls**, and every cache served exactly one
turn. Every one of those creates is a request against the same quota the caching was supposed to
protect. Compare with the stable-instruction run, which is
[2.4](2.4-the-three-ways-a-cache-dies.md)'s default and produces 19 caches and 37 extra calls.

There is a second break, and it is a design smell that shows up as a fingerprint that will not
stabilise: anything time-varying in the instruction. `"Today is 2026-09-05."` in a system prompt is a
fingerprint that moves at midnight, every night, for every session. It is defensible if the model
genuinely needs the date — and if it does, the date belongs in the fresh tail, not the instruction.

## In production

**What a professional writes instead.** They log the fingerprint on every request. Sixteen hex
characters is a cheap field, and a graph of *distinct fingerprints per hour* is the single most
useful caching metric there is: it should be a small number, roughly the count of distinct agent
configurations you deploy. If it tracks your request rate, the prefix is not stable, and no amount of
TTL tuning will help. `ops.py`'s `key_recipe` field is the response-cache equivalent of the same idea.

**What degrades at scale.** Every feature that personalises the system instruction multiplies your
distinct-fingerprint count. A per-user tone preference, a per-tenant policy paragraph, an A/B prompt
experiment — each is one axis, and they multiply. Ten tenants times three prompt variants is thirty
distinct prefixes, each needing its own cache and its own minimum size. The architectural answer is
to push personalisation into the fresh tail wherever the model does not need it as a standing
instruction.

**The failure mode that only appears with real traffic.** Restart behaviour. A tool registry built
from unordered iteration would, without ADK's canonicalisation, produce a different fingerprint per
process — so a single-instance deployment would look perfect and a six-replica deployment would show
a hit rate near zero, with the exact shape of "it works on staging". ADK sorts, so this specific bug
is closed; the general one is not. Anything you interpolate into the instruction that varies by
process — a hostname, a build id, a start timestamp — reopens it.

**The review comment a senior engineer leaves:** *"This PR adds the current date to the system
instruction. That's inside the cache fingerprint, so every deployment's caches now die at midnight
together, and we'll see a create storm. If the model needs the date, put it in a content just before
the user's message."*

**The interview question:** *"What invalidates a context cache?"* An honest answer: *"Anything inside
the hashed prefix. In ADK that's the model name, the backend, the system instruction byte for byte,
the tool declarations and the first N contents. I measured it on my own agent: adding one trailing
space to the instruction moved the fingerprint and abandoned the cache; changing the current question
did not, because that's outside the hashed prefix; and reversing the tool list did not either,
because the framework sorts tools before hashing, which is what keeps a cache alive across restarts.
The trap I actually hit was appending RAG results to the system instruction — that's per-question
text inside the hashed prefix, so I was creating and deleting a cache on every call. Two hundred
turns, two hundred caches, 399 extra API calls to save payload on 200 requests."*
