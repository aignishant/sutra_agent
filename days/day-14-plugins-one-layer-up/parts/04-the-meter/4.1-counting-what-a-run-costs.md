# 4.1 — Counting what a run costs

## One-line answer

Two hooks — `before_model_callback` and `before_tool_callback` — are the only two places where quota is
actually spent, so counting there gives you the true cost of a request, and a question needing two
tools costs **three** model calls rather than one.

---

## The story

A rented room with a prepaid electricity meter on the wall.

For the first month you have no idea where the units go. You top it up, it runs down, and your only
information is that it runs down faster than you expected. You start being vaguely careful about
everything — the lights, the fan, the kettle — which is exhausting and does not work, because being
vaguely careful about everything is the same as being careful about nothing.

Then one evening you actually watch the dial. You switch the geyser on and the dial visibly speeds up.
You switch it off, and it slows. You do the same with the lights and nothing measurable happens.

That is the end of the vague carefulness. It turns out one appliance is most of the bill, and the
answer was never "use less electricity" — it was "the geyser is the geyser". You could not have
reasoned your way to that. You had to watch the dial while you changed one thing.

---

## The idea in plain language

Sutra's currency is not money. Addendum 02 is explicit: the budget is **requests per minute and
requests per day, per provider**, because every model Sutra is allowed to use is free and the ceiling
is a rate limit rather than a bill.

So "what did this request cost?" means "how many provider requests did it make?" — and there are
exactly two kinds of thing in a run that can spend quota:

**A model call.** Every one is an HTTP request to Gemini, Groq or OpenRouter, and every one counts
against that provider's RPM and RPD. The door is `before_model_callback`.

**A tool call.** A tool does not spend *model* quota, but it is the other thing a run does that costs
something — time, a database query, a call to somebody else's API. The door is
`before_tool_callback`.

Everything else in a run is free: the events, the session writes, the callbacks. If you count those
two doors, you have counted the run.

Count at the **before** doors, not the after ones, for a reason worth stating. `after_model_callback`
fires once per *yielded response*, and with streaming on that is several times per model call
([13/2.5](../../../day-13-callbacks-four-doors/parts/02-the-model-doors/2.5-the-door-that-fires-on-every-chunk.md)).
A counter there measures reply length, not requests. `before_model_callback` fires once per call, full
stop.

Now the number that surprises people, and it is the whole reason to measure rather than assume.
[2.4](../02-the-fourteen-doors/2.4-fifteen-firings-one-run.md) showed one tool call costing **two**
model calls. The rule generalises: **each tool call adds a model call**, because the result has to go
back for the model to decide what to do next. So:

| the model uses | model calls | why |
| --- | --- | --- |
| no tools | 1 | ask, answer |
| one tool | 2 | ask, tool, answer |
| two tools in sequence | 3 | ask, tool, ask again, tool, answer |
| *n* tools in sequence | *n* + 1 | one per decision point, plus the final answer |

A triage question that looks up a ticket and then searches the knowledge base — Sutra's most ordinary
request — is three model calls, not one. On a free tier of a few hundred requests per day, guessing
one when the answer is three is the difference between a budget that holds and one that runs out
mid-afternoon.

---

## Why Sutra needs it

**Because Day 70's quota router cannot exist without this.** Addendum 02 §6.2 defines the router as
tracking *"requests-remaining per provider per window"* and sending each call to whoever has headroom.
Every word of that presupposes a counter. This is the counter.

**Because the hub's request budget stops being a guess.** Every day so far has stated a budget —
*"0 of 20"*, *"6 of 20"* — worked out by reading the day's scripts. From today it can be measured, and
a day whose stated budget and measured budget disagree is a day with a bug in it.

**Because Day 79's evals run hundreds of these.** Addendum 02 §5 sends the eval suite to Flash-Lite
for its higher daily allowance and keeps dev evalsets to a handful of cases. Sizing an evalset against
a daily quota needs a per-case cost, and a per-case cost is what this plugin prints.

## The mechanism

```python
# lab/metering.py - counting at the two doors that cost quota. Zero model calls.
import asyncio
from collections import Counter

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.plugins import BasePlugin
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types
from stateless import ReactiveModel


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    return {"status": "ok", "ticket_id": ticket_id, "body": "charged twice"}


def search_kb(query: str) -> dict:
    """Search the knowledge base."""
    return {"status": "ok", "hits": ["KB-104"]}


class Meter(BasePlugin):
    """Counts the two things that cost quota, per agent."""

    def __init__(self) -> None:
        super().__init__(name="meter")
        self.counts: Counter[str] = Counter()

    async def before_model_callback(self, *, callback_context, llm_request):
        self.counts["model"] += 1
        self.counts[f"model:{callback_context.agent_name}"] += 1
        print(f"      model call #{self.counts['model']} from {callback_context.agent_name}")

    async def before_tool_callback(self, *, tool, tool_args, tool_context):
        self.counts["tool"] += 1
        self.counts[f"tool:{tool.name}"] += 1
        print(f"      tool call  #{self.counts['tool']} -> {tool.name}")


async def main() -> None:
    meter = Meter()
    agent = LlmAgent(
        name="desk",
        model=ReactiveModel(model="scripted", chain=["lookup_ticket", "search_kb"]),
        instruction="x",
        tools=[lookup_ticket, search_kb],
    )
    app = App(name="sutra", root_agent=agent, plugins=[meter])
    runner = Runner(app=app, session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name=app.name, user_id="u")
    async for _ in runner.run_async(
        user_id="u",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="ticket 4521")]),
    ):
        pass

    print("\n  what the run cost:")
    for key in sorted(meter.counts):
        print(f"    {key:24} {meter.counts[key]}")


asyncio.run(main())
```

**Line by line:**

- `from collections import Counter` — a `dict` subclass where a missing key reads as `0`, so
  `self.counts["model"] += 1` works on the first call without any setup. `CLAUDE.md` says prefer the
  stdlib over a dependency, and this is the stdlib doing exactly the job.
- `self.counts: Counter[str] = Counter()` in `__init__` — the state that makes this a class rather
  than a function. It is also the bug in
  [4.3](4.3-one-instance-every-run.md), planted here in plain sight: one counter on the instance, and
  the instance outlives the run.
- Two keys per event — `"model"` and `f"model:{agent_name}"` — so the same pass produces both the
  total and the per-agent breakdown. With one agent the breakdown is redundant; with Phase 8's graph
  it is the only interesting half, and adding it now costs one line.
- `callback_context.agent_name` — which agent is about to call the model. This is why a plugin can
  produce a per-agent breakdown that no agent could produce for itself: it is standing outside all of
  them and being told which one each time.
- `tool.name` rather than `tool` — `tool` is a `BaseTool` object, and its `name` is the string the
  model used. For a `FunctionTool` that is the Python function's name
  ([Day 10](../../../day-10-function-tools/LESSON.md)); from Day 39 it will be a name chosen by an MCP
  server.
- Both hooks **print and return nothing**. They are observers, and
  [3.1](../03-the-rule-at-this-layer/3.1-is-not-none-and-this-time-it-means-it.md) is why that matters
  more here than it did yesterday: a stray `return` in this class disables every tool in every agent.
- `meter = Meter()` held in a local variable rather than constructed inline in the `plugins=[...]`
  list — because `main` needs to read `meter.counts` afterwards. Constructing it inline would leave
  the only reference inside the `App`, reachable via `runner.plugin_manager.get_plugin("meter")` but
  not directly.
- `chain=["lookup_ticket", "search_kb"]` — two tools, in order, so the run is the three-model-call
  shape from the table above rather than the two-call one.
- `f"{key:24}"` — fixed-width keys so the counts line up in a column and the totals are readable
  against the breakdown.

The output:

```text
      model call #1 from desk
      tool call  #1 -> lookup_ticket
      model call #2 from desk
      tool call  #2 -> search_kb
      model call #3 from desk

  what the run cost:
    model                    3
    model:desk               3
    tool                     2
    tool:lookup_ticket       1
    tool:search_kb           1
```

**Three model calls for one question.** Read the interleaving: model, tool, model, tool, model. The
last model call is the one that writes the answer, and it exists because the second tool's result had
to go somewhere.

If your instinct was that this run cost one request, that instinct has been costing you quota all
week.

Verified against the installed `google-adk` 2.7.1 on 2026-08-29 by running this script.

## When it breaks

**💥 You counted at `after_model_callback` and the numbers inflate under streaming.** No error, and it
agrees with `before_model_callback` on every scripted test in this day, because the scripted model
yields once per call. Against a real model with streaming on, `after_model_callback` fires per
fragment. The symptom is a model-call count that grows with reply length.

**💥 You counted in the tool function instead.** No error either, and it works — until Day 39, when
half the tools come from an MCP server and you cannot edit them. A plugin counts tools you did not
write, which is the entire argument for counting here.

**💥 The typo that reads as zero.**

```text
    model                    0
```

`Counter` returns `0` for a key it has never seen, which is what makes `+= 1` work without setup — and
it is the same property that makes `meter.counts["modl"]` a silent zero rather than a `KeyError`. A
meter reporting `0` looks like a run that cost nothing, which is a plausible enough number that nobody
questions it. If you want the strictness back, read with `meter.counts` in an assertion that the key
exists, which is what [7.2](../07-in-production/7.2-testing-a-plugin-without-a-model.md)'s test does.

**💥 You counted at `after_tool_callback` and a short-circuited tool went uncounted.** No error. If a
plugin or an agent callback returns a value at the *before* door, the tool never runs — but the after
door still fires with the substituted result, so an after-door counter counts refusals as tool calls.
Yesterday's [13/3.2](../../../day-13-callbacks-four-doors/parts/03-the-tool-doors/3.2-refusing-a-tool-call-honestly.md)
refusals would all appear in your ledger as work that happened. The before door counts *attempts*,
which is what quota is spent on.

## In production

**What a professional writes instead of the teaching version** counts the provider, not just the call.
A model call to Groq and a model call to Gemini come out of different buckets with different limits,
and a single `model: 3` cannot be compared against any quota:

```python
async def before_model_callback(self, *, callback_context, llm_request) -> None:
    self.counts[f"model:{llm_request.model}"] += 1
```

**Line by line:**

- `llm_request.model` is the resolved model string for **this** call — `gemini-3.7-flash`, or a
  LiteLLM string like `groq/llama-3.3-70b-versatile`. Since Day 9 Sutra has had four providers behind
  one interface, and the moment more than one is in play, "three model calls" is not a number you can
  do anything with.
- Keying on the model string rather than a provider name you derive yourself keeps the plugin honest:
  it reports what was actually sent, so a misconfigured agent that silently fell back to a different
  model shows up in the ledger instead of hiding in it.
- Note there is still no `return` and the annotation is still `-> None`.

**What degrades at scale** is unbounded key growth. A `Counter` keyed by model, agent and tool name is
fine. A `Counter` keyed by anything containing a user id, a session id or a ticket number grows
without limit for the life of the process, and the leak is invisible because it is "just a dict of
integers" until it is two million entries.

**The failure that only shows with real traffic** is retries counted as one call. If Day 72's backoff
retries a 429 three times, that is **four** HTTP requests against your RPM, and a counter that
increments once per `before_model_callback` sees one — because the retry happens inside the model
layer, below the door. A meter that reports optimistically during a rate-limit incident is a meter
that is wrong exactly when it matters.

**The review comment a senior engineer leaves:** *"`model: 3` with four providers configured is not a
number anyone can act on. Key the counter by `llm_request.model` — and say in the docstring whether
retries are included, because right now they are not."*

**The interview question:** *"How would you find out what a multi-agent request actually costs?"* — "A
plugin on the application, counting at `before_model_callback` and `before_tool_callback`. Not inside
any agent, because no single agent sees the whole request, and not in the tools, because half of them
will eventually come from an MCP server I cannot edit. I count at the *before* doors specifically:
`after_model_callback` fires per streamed response rather than per call, so it measures reply length.
The thing that surprises people is the arithmetic — each tool call adds a model call, because the
result has to go back for the model to decide what is next, so a two-tool triage is three model calls,
not one. And I key by the resolved model string rather than a bare total, because with several
providers a single number cannot be compared to any quota."
