# 4.3 — One instance, every run

## One-line answer

A plugin is constructed once and reused for the lifetime of the application, so a counter stored on
`self` accumulates across every request — reporting `2, 4, 6` for three identical runs in sequence,
and `6, 6, 6` for three at the same time.

---

## The story

One notebook on the counter of a busy phone-repair stall.

The owner writes each job in it as it comes in: name, handset, what is wrong. At the end of the day he
adds up the line items and that is the day's takings. It works.

Then his brother starts helping on Saturdays, and they both write in the same notebook, because there
is one notebook.

Nothing dramatic goes wrong. No page is torn, no ink is spilled. But now a customer asks what they owe
and whoever answers reads down the page and finds — someone else's lines mixed in with theirs, in
order of arrival rather than in order of customer. There is no line saying which job belongs to whom,
because when there was one person writing, it was obvious.

The notebook was never wrong. It was answering a different question from the one being asked, and
nobody noticed while there was only ever one job at a time.

---

## The idea in plain language

Look again at how a plugin gets installed:

```text
App(name="sutra", root_agent=agent, plugins=[Ledger()])
```

`Ledger()` runs **once**. The object it produces goes into the `App`, the `App` goes into the
`Runner`, and the `Runner` serves every request for as long as the process lives. There is one
`Ledger`, and `self.counts` is one `Counter`.

So the counter from [4.1](4.1-counting-what-a-run-costs.md) is not a per-run counter. It is a
per-process counter that [4.2](4.2-the-bill-at-the-exit-door.md) prints at the end of each run, with
a label saying `RUN`. It has been wrong since the moment it was written, and a single run cannot
show you, because with one run the two are the same number.

That is why this part exists at this position. **The bug is invisible until the second request**, and
every script in this day until now has made exactly one.

There are two distinct failures inside it and they need separate names.

**Accumulation.** Three runs in sequence, each costing two model calls, report `2`, then `4`, then
`6`. Every report is the lifetime total. The first one is right by coincidence.

**Interleaving.** Three runs at the same time report `6`, `6`, `6`. Nobody's report is their own, and
none of the three is right, not even the first. This is the notebook with two people writing in it.

The fix is one idea: **keep per-run state keyed by the run**. The key is `invocation_id`, which every
context carries — `callback_context.invocation_id` at the model door, `tool_context.invocation_id` at
the tool door, `invocation_context.invocation_id` at the run doors — and which is the same string
across all three for one request.

And the fix has a second half people forget: **remove the entry when the run ends**. A dictionary
keyed by request id that is only ever added to is a memory leak with a slow fuse.

---

## Why Sutra needs it

**Because Sutra will serve concurrent requests from Day 85.** The API server does not process one
request at a time. Every plugin Sutra owns has to be correct under concurrency from the day it is
written, because the day the server arrives is not the day anyone re-reads the plugins.

**Because Day 70's router reads these numbers to make decisions.** A meter that over-reports under
concurrency tells the router that a provider is exhausted when it is not, so the router sheds load to
a slower provider for no reason. A wrong meter is worse than no meter, because a wrong meter gets
acted on.

**Because this is the shape of every stateful plugin, not just this one.** A cache, a rate limiter, a
tracer: all of them hold state on `self`, and all of them face the same question — is this state
per-process or per-run? Getting it right once here is the pattern for all of them.

---

## The mechanism

Both meters, side by side, in the same runs.

```python
# lab/shared_state.py - the same counter, sequential and concurrent. Zero model calls.
import asyncio
from collections import Counter

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.plugins import BasePlugin
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types
from stateless import ReactiveModel


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    return {"status": "ok", "ticket_id": ticket_id}


class Naive(BasePlugin):
    """One counter on the instance. The instance outlives the run."""

    def __init__(self) -> None:
        super().__init__(name="naive")
        self.model_calls = 0

    async def before_model_callback(self, *, callback_context, llm_request):
        self.model_calls += 1

    async def after_run_callback(self, *, invocation_context):
        print(f"      naive  : model={self.model_calls}")


class Keyed(BasePlugin):
    """One counter per invocation, removed when that invocation ends."""

    def __init__(self) -> None:
        super().__init__(name="keyed")
        self.runs: dict[str, Counter[str]] = {}

    async def before_model_callback(self, *, callback_context, llm_request):
        self.runs.setdefault(callback_context.invocation_id, Counter())["model"] += 1

    async def after_run_callback(self, *, invocation_context):
        bill = self.runs.pop(invocation_context.invocation_id, Counter())
        print(f"      keyed  : model={bill['model']}  (still open: {len(self.runs)})")


AGENT = LlmAgent(
    name="desk",
    model=ReactiveModel(model="scripted"),
    instruction="x",
    tools=[lookup_ticket],
)


async def one(runner: Runner, app: App, user: str) -> None:
    session = await runner.session_service.create_session(app_name=app.name, user_id=user)
    async for _ in runner.run_async(
        user_id=user,
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="hi")]),
    ):
        pass


async def main() -> None:
    for label, mode in (
        ("a. three runs, one after another", "sequential"),
        ("b. three runs at the same time", "concurrent"),
    ):
        print(f"  {label}   (every run is exactly 2 model calls)")
        app = App(name="sutra", root_agent=AGENT, plugins=[Naive(), Keyed()])
        runner = Runner(app=app, session_service=InMemorySessionService())
        if mode == "sequential":
            for index in range(3):
                await one(runner, app, f"{mode}{index}")
        else:
            await asyncio.gather(*(one(runner, app, f"{mode}{index}") for index in range(3)))


asyncio.run(main())
```

**Line by line:**

- `Naive` and `Keyed` are installed **together**, in the same `App`, so both see identical traffic.
  Running them separately would leave room to argue the two runs differed.
- `self.model_calls = 0` in `Naive.__init__` — an integer on the instance. This is the most natural
  thing to write and it is the bug.
- `self.runs: dict[str, Counter[str]] = {}` in `Keyed.__init__` — a dictionary **of** counters,
  keyed by invocation id. The state is still on the instance, because it has to be; what changed is
  that the instance now holds one entry per run rather than one number for all of them.
- `self.runs.setdefault(callback_context.invocation_id, Counter())["model"] += 1` — `setdefault`
  creates the entry on the first door of a run and returns the existing one afterwards, so there is
  no separate "start of run" bookkeeping. The run is created by its first spend, which means a run
  that spends nothing never allocates anything.
- `callback_context.invocation_id` — the same string the run doors see. That is the whole reason this
  works: the id is minted once per request and every context carries it.
- `self.runs.pop(invocation_context.invocation_id, Counter())` — read **and** remove, in one
  operation. The `Counter()` default means a run that never spent anything still reports cleanly
  instead of raising `KeyError`. This line is the leak fix.
- `len(self.runs)` printed as `still open` — the diagnostic that makes the leak visible. In the
  sequential case it drains to `0` every time; in the concurrent case it counts down `2, 1, 0` as the
  overlapping runs finish. If it ever climbed instead, the `pop` would not be running.
- `AGENT` built once at module level and shared — deliberately, because the plugins are the subject
  and a shared agent is what a real server has. `ReactiveModel` is safe to share precisely because
  [2.2](../02-the-fourteen-doors/2.2-the-four-doors-an-agent-cannot-have.md) made it stateless; Day
  13's counter-based `ScriptedModel` would have scrambled its own script here and the concurrent case
  would have measured the wrong thing.
- `asyncio.gather(*(...))` — starts all three and waits for all three. This is the smallest honest
  model of two users pressing send at the same moment.

The output:

```text
  a. three runs, one after another   (every run is exactly 2 model calls)
      naive  : model=2
      keyed  : model=2  (still open: 0)
      naive  : model=4
      keyed  : model=2  (still open: 0)
      naive  : model=6
      keyed  : model=2  (still open: 0)
  b. three runs at the same time   (every run is exactly 2 model calls)
      naive  : model=6
      keyed  : model=2  (still open: 2)
      naive  : model=6
      keyed  : model=2  (still open: 1)
      naive  : model=6
      keyed  : model=2  (still open: 0)
```

Every run in that output cost exactly two model calls. The keyed meter says `2` six times.

The naive meter says `2, 4, 6` sequentially — each report is the running total, and only the first is
accidentally right. Then it says `6, 6, 6` concurrently, where **not even the first is right**,
because by the time any of the three finished, all three had spent.

`still open` draining `2 → 1 → 0` in the concurrent case is the leak fix working. Three runs were in
flight, and each `pop` removed exactly its own.

Verified against the installed `google-adk` 2.7.1 on 2026-08-29 by running this script.

## When it breaks

**💥 The numbers only look wrong on the second request.** No error, ever. This is a correctness bug
with no failure signal, and the reason it survives review is that the reviewer, like the author, ran
it once.

**💥 The leak, if you forget the `pop`.** Replace `self.runs.pop(...)` with `self.runs[...]` and the
`still open` line climbs forever: `0, 1, 2, 3, …`. In a server that is one dictionary entry per
request for the life of the process, and it will be found by a memory graph months later rather than
by anything that looks like a bug.

**💥 The leak you cannot fix with `pop` alone.** A run that **fails** never reaches
`after_run_callback` ([5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md)), so its
entry is never popped. So the `pop` closes the leak on the happy path and leaves it open on exactly
the path that happens under stress. The complete fix needs `on_run_error_callback` too, and that is
the next section.

**💥 `KeyError` if you drop the default.**

```text
RuntimeError: Error in plugin 'keyed' during 'after_run_callback' callback: 'e-8f21…'
```

`self.runs.pop(key)` without the second argument raises when a run reaches the exit door having never
called a model — an agent that answered from a plugin cache, or a request short-circuited at the tool
door. Rare, real, and it takes the whole request down by
[3.3](../03-the-rule-at-this-layer/3.3-a-plugin-that-raises-takes-the-run-with-it.md)'s rule.

## In production

**What a professional writes instead of the teaching version** stops the dictionary from being able to
grow without bound, whatever happens to individual runs:

```python
from collections import Counter, OrderedDict

MAX_OPEN_RUNS = 10_000


class RunLedger(BasePlugin):
    def __init__(self, name: str = "run_ledger") -> None:
        super().__init__(name=name)
        self._runs: OrderedDict[str, Counter[str]] = OrderedDict()

    def _open(self, invocation_id: str) -> Counter[str]:
        if invocation_id not in self._runs and len(self._runs) >= MAX_OPEN_RUNS:
            self._runs.popitem(last=False)
        return self._runs.setdefault(invocation_id, Counter())
```

**Line by line:**

- `OrderedDict` rather than `dict` — a plain `dict` preserves insertion order but has no cheap way to
  drop the *oldest* entry. `OrderedDict.popitem(last=False)` does exactly that in one call.
- `MAX_OPEN_RUNS` as a module constant — the ceiling is a decision, so it gets a name and a place a
  reviewer can find it. Ten thousand concurrent in-flight requests is far past anything Sutra will
  see, which is the point: crossing it means something is wrong, not that traffic is high.
- `popitem(last=False)` — evicts the oldest open run. This is deliberately **lossy**: the ledger would
  rather forget the oldest abandoned run than grow forever. A meter is not load-bearing
  ([3.3](../03-the-rule-at-this-layer/3.3-a-plugin-that-raises-takes-the-run-with-it.md)), so trading
  completeness for a bounded footprint is the right trade here and would be the wrong one for an audit
  log.
- `_runs` and `_open` with leading underscores — internal. `CLAUDE.md` asks for type hints on public
  functions; marking these private says the supported surface is the hooks and the report, not the
  dictionary.
- The `if` checks `not in` **before** checking the size, so an existing run is never evicted by its
  own activity.

**What degrades at scale** is that this is a per-process ledger. Run four containers behind a load
balancer and you have four meters, each seeing a quarter of the traffic and none seeing the quota,
which is enforced per project or per organisation by the provider. That is Day 70's real problem and
the reason its router needs shared state rather than a plugin attribute — the plugin becomes the
*reporter* and something outside becomes the *ledger*.

**The failure that only shows with real traffic** is the one measured above: the sequential case looks
plausible enough to ship. `2, 4, 6` in a log could easily read as three progressively more expensive
requests, which is a story that makes sense, and nobody investigates a number that makes sense.

**The review comment a senior engineer leaves:** *"`self.model_calls` on the plugin is process-wide,
not per-run — the plugin instance is constructed once. Key it by `invocation_id` and pop it in
`after_run`. And add the `on_run_error` path, or failed runs leak an entry each."*

**The interview question:** *"A plugin holds a counter and the numbers are wrong. What do you check
first?"* — "Whether the state is per-process or per-run. A plugin is constructed once when the `App` is
built and then serves every request, so anything on `self` is shared across all of them. Sequentially
that shows up as a running total mislabelled as a per-request number; concurrently every in-flight run
reads everyone else's. The fix is to key the state by `invocation_id` — every context carries the same
one for a given request — and to remove the entry when the run ends. The part people miss is that
removing it in `after_run_callback` alone leaks, because that hook does not fire on failed runs, so
the error hook needs the same cleanup."
