# 2.4 — Fifteen firings, one run

## One-line answer

One question that causes one tool call fires ten distinct plugin hooks **fifteen** times, and the
order is not the order they are listed in — the model doors fire twice, `on_event_callback` fires
three times, and the run-level pair brackets everything.

---

## The story

The bakery two streets over puts its oven room behind a window, and one morning you stand and watch.

You have eaten their bread for years. You know what happens: flour goes in, bread comes out. If
somebody asked you to describe it you would say they mix it and they bake it.

Then you actually watch. They mix, and then it sits in a tub doing nothing for a long time. They knead
it, and it sits again. They knock the air out of it — you did not know anyone did that — divide it,
shape it, and let it rise a **second** time. Only then does it go in the oven, and even after it comes
out it is not finished, because it cools on a rack before anyone touches it. Two rises, not one.

Nothing about your old description was wrong. It was a summary, and the process is not a summary. You
had never needed the count, and now that you have watched it you can walk past the window and tell
from what is on the bench which part of the morning they are in.

## The idea in plain language

You have the list of doors from [2.1](2.1-fourteen-doors-six-you-already-know.md) and you know what
each is for from [2.2](2.2-the-four-doors-an-agent-cannot-have.md). Neither tells you **when** they
fire, or **how often**, and both of those decide what a hook costs and where a piece of logic belongs.

The subject here is one measurement, and it is the window into the oven room: instrument every hook,
run one ordinary question, print the order they actually fire in.

The question is *"hi"*, the model asks for one tool call, the tool answers, the model writes a reply.
That is the smallest interesting run — a real tool round trip — and it is the shape of most of Sutra's
traffic.

Two facts to hold before you read the output, because they are the ones people guess wrong.

**A tool call costs two model calls, not one.** The first asks the model what to do and gets back a
request for a tool. The second sends the tool's result back so the model can write an answer.
Yesterday's [13/2.1](../../../day-13-callbacks-four-doors/parts/02-the-model-doors/2.1-what-is-actually-in-the-request.md)
measured this at the agent layer; the plugin layer sees the same two.

**`on_event_callback` fires more often than anything else.** Every event that reaches you passes
through it — the tool call, the tool result, and the final text are three separate events for one
question.

---

## Why Sutra needs it

**Because the meter in section 4 has to pick a door, and the count decides which one.**
[4.1](../04-the-meter/4.1-counting-what-a-run-costs.md) counts what a run costs, and a counter is only
as honest as the firing rate of the hook it sits on. `before_model_callback` fires once per model call
and `after_model_callback` fires once per yielded response; put the meter on the wrong one and the
number is right on a scripted model and wrong the moment a real reply streams. This part is where that
difference is measured rather than assumed.

**Because the request budget in every hub is currently arithmetic done by hand.** Each day so far has
stated *"0 of 20"* or *"6 of 20"* by reading its own scripts and adding up. The number that makes that
budget checkable is the one this part establishes: one question with one tool call is **two** model
calls, not one. A budget written against the wrong multiplier does not fail — it quietly plans for
half the quota the day actually spends, and the free tier is 20 requests per day.

**Because a hook that fires fifteen times is a different engineering decision from one that fires
once.** Everything Sutra hangs on a plugin from here — the meter today, the tracing in Phase 9, the
prompt-injection check in Phase 10 — is paid for per firing, across every agent in the app. Knowing
that `on_event_callback` already fires three times for the smallest interesting run, before streaming
is even switched on, is what stops an expensive check being put there by accident.

## The mechanism

```python
# lab/firing_order.py - every hook, one run, in the order they actually fire. Zero model calls.
import asyncio

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.plugins import BasePlugin
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types
from stateless import ReactiveModel

SEQUENCE: list[str] = []


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    SEQUENCE.append(">> the tool itself ran")
    return {"status": "ok", "ticket_id": ticket_id}


class Doorbell(BasePlugin):
    """Overrides every hook that fires on a successful run, and only records."""

    def __init__(self) -> None:
        super().__init__(name="doorbell")

    async def on_user_message_callback(self, *, invocation_context, user_message):
        SEQUENCE.append("on_user_message")

    async def before_run_callback(self, *, invocation_context):
        SEQUENCE.append("before_run")

    async def before_agent_callback(self, *, agent, callback_context):
        SEQUENCE.append("before_agent")

    async def before_model_callback(self, *, callback_context, llm_request):
        SEQUENCE.append("before_model")

    async def after_model_callback(self, *, callback_context, llm_response):
        SEQUENCE.append("after_model")

    async def before_tool_callback(self, *, tool, tool_args, tool_context):
        SEQUENCE.append("before_tool")

    async def after_tool_callback(self, *, tool, tool_args, tool_context, result):
        SEQUENCE.append("after_tool")

    async def after_agent_callback(self, *, agent, callback_context):
        SEQUENCE.append("after_agent")

    async def on_event_callback(self, *, invocation_context, event):
        SEQUENCE.append("on_event")

    async def after_run_callback(self, *, invocation_context):
        SEQUENCE.append("after_run")


async def main() -> None:
    agent = LlmAgent(
        name="desk",
        model=ReactiveModel(model="scripted"),
        instruction="x",
        tools=[lookup_ticket],
    )
    app = App(name="sutra", root_agent=agent, plugins=[Doorbell()])
    runner = Runner(app=app, session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name=app.name, user_id="u")
    async for _ in runner.run_async(
        user_id="u",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="hi")]),
    ):
        pass

    for position, name in enumerate(SEQUENCE, 1):
        print(f"{position:3}. {name}")
    print(f"\n{len(SEQUENCE)} firings, {len(set(SEQUENCE)) - 1} distinct hooks, 1 question")


asyncio.run(main())
```

**Line by line:**

- `SEQUENCE: list[str] = []` at module level rather than on the plugin — the tool function also
  appends to it, and the tool is a plain function with no access to the plugin instance. A shared
  module-level list is the simplest way to interleave both in one timeline. In real code this would be
  state on the plugin; here the point is the interleaving.
- Every hook records **and returns nothing**. That is deliberate and it is yesterday's one rule: a
  hook that returned a value would change what happens next, and this script must not change anything
  it is measuring. An observer that alters the thing it observes is
  [13/5.1](../../../day-13-callbacks-four-doors/parts/05-failure-lab/5.1-the-note-that-became-the-result.md)'s
  entire failure.
- The four error hooks are **not** overridden, because this run succeeds. Their absence from the
  output is information: on a clean run they never fire, which is
  [5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md)'s starting point read backwards.
- `SEQUENCE.append(">> the tool itself ran")` inside the tool — the marker that anchors the tool doors
  to the actual work, so `before_tool` and `after_tool` are visibly on either side of something real
  rather than adjacent to each other.
- `enumerate(SEQUENCE, 1)` — numbering from one so the count is readable directly off the last line.
- `len(set(SEQUENCE)) - 1` — the distinct hook count, minus one for the tool's own marker, which is
  not a hook.

The output:

```text
  1. on_user_message
  2. before_run
  3. before_agent
  4. before_model
  5. after_model
  6. on_event
  7. before_tool
  8. >> the tool itself ran
  9. after_tool
 10. on_event
 11. before_model
 12. after_model
 13. on_event
 14. after_agent
 15. after_run

15 firings, 10 distinct hooks, 1 question
```

Six things in that list are worth saying out loud:

| Observation | Why it matters |
| --- | --- |
| `before_model` fires at 4 and again at 11 | one tool call costs two model calls, so a per-model-call counter counts two |
| `on_event` fires at 6, 10 and 13 | the tool call, the tool result and the final text are three events |
| the tool's own work is at 8 | `before_tool` and `after_tool` genuinely bracket it |
| `after_model` at 5 comes **before** `before_tool` at 7 | the model's request for a tool is a completed model response first |
| `before_agent` at 3 is inside `before_run` at 2 | the request starts, then the agent starts |
| `after_run` at 15 is last, after `after_agent` | the agent finishing is not the request finishing |

The one to carry forward is row 1. Section 4's meter counts at `before_model_callback`, and if you
expected one question to cost one model call, its report will look wrong when it is right.

Verified against the installed `google-adk` 2.7.1 on 2026-08-29 by running this script. No
documentation page states this order; it is measured, and if your run differs, **your terminal wins**
and this table is what needs fixing.

## When it breaks

**💥 You expected `after_run` and got nothing.** On a run that raises, positions 14 and 15 never
happen. The script above cannot show you that because it succeeds; run
[5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md)'s version, which fails on
purpose, and watch the last two lines disappear.

**💥 You put a `return` in one of these hooks and the sequence changed.** For example, returning a
dict from `before_tool_callback` removes positions 8 and 9 — the tool never runs, so there is nothing
to run `after_tool` on. That is not a bug in the measurement; it is the return rule doing its job, and
it is [3.1](../03-the-rule-at-this-layer/3.1-is-not-none-and-this-time-it-means-it.md).

**💥 Your numbers are bigger than these and you are using a real model.** Streaming splits one reply
into several responses, so `after_model` fires per **yielded response** rather than per model call,
exactly as it does at the agent layer
([13/2.5](../../../day-13-callbacks-four-doors/parts/02-the-model-doors/2.5-the-door-that-fires-on-every-chunk.md)).
The scripted model yields once per call, which is why this table is clean. A live run against
`gemini-3.7-flash` will not be.

## In production

**What a professional writes instead of the teaching version** does not instrument fourteen doors to
find out where something happens. They instrument fourteen doors **once**, on a scratch script exactly
like this one, look at the order, and then write the real plugin against three of them. The script is
a measuring instrument, not a component.

**What degrades at scale** is anything hung on the doors that fire per-event or per-response. On this
run the ratio is mild — three `on_event` to one `after_run`. Under streaming with a real model it is
tens of `on_event` firings per request, and a plugin that does a hundred microseconds of work in that
hook has added milliseconds per request, on every agent, for the life of the application.

**The failure that only shows with real traffic** is a counter at `after_model_callback` used as a
model-call counter. It agrees with `before_model_callback` on every scripted test and diverges the
moment streaming is on, because one is per call and the other is per yielded response. Two dashboards,
both labelled "model calls", disagreeing by a factor that varies with reply length.

**The review comment a senior engineer leaves:** *"You are counting model calls in `after_model`. That
fires per streamed response, not per call — move it to `before_model`, and add a test with a
multi-yield scripted model so the difference is caught."*

**The interview question:** *"How many times does a plugin's `before_model_callback` fire for one user
message?"* — "Once per model call, and one user message is not one model call. A question answered
directly is one; a question that needs one tool is two, because the tool result has to go back for the
model to write the answer; a chain of three tools is four. So any per-request budget expressed in
model calls has to be measured, not assumed — which is exactly why the meter reports at
`after_run_callback` rather than incrementing a number somebody guessed."
