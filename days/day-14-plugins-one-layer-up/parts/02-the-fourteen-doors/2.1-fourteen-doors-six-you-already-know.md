# 2.1 — Fourteen doors, and six you already know

## One-line answer

A plugin in `google-adk` 2.7.1 can override **fourteen** hooks — the six an agent already has, four
that only exist at this layer, two more error hooks, and two that are notification-only — and the
published documentation still lists twelve.

## The story

Your first week at a new job, somebody hands you a key ring.

It has fourteen keys on it. Six you recognise immediately, because you used the same ones at your last
place: the store cupboard, the back door, the meter box. You could open those blindfolded.

The other eight are new. Nobody walks you round. And the honest thing you notice, standing there with
the ring in your hand, is that you do not know what most of them are for — but you can already tell
that having them means you are responsible for more than you were before.

Then you find the induction sheet in the drawer. It lists twelve keys. It was printed a while ago.

The sheet is not lying, exactly. It is just older than the key ring, and the ring is what actually
opens things. So you keep the sheet, and you check the ring.

---

## The idea in plain language

A **hook** is a named method you can override on your plugin class. If you override it, ADK calls it
at that point in a run. If you do not, ADK calls the base class's version, which does nothing — so
unused hooks cost you nothing and you never write a hook you do not need.

The fourteen, grouped by what they wrap:

| Group | Hook | Fires |
| --- | --- | --- |
| **run** | `on_user_message_callback` | once, on the incoming message, before anything runs |
| | `before_run_callback` | once, at the start of the request |
| | `on_event_callback` | on every event, before it is saved and handed to you |
| | `after_run_callback` | once, at the end of a **successful** request |
| **agent** | `before_agent_callback` | before an agent's own logic |
| | `after_agent_callback` | after an agent's own logic |
| **model** | `before_model_callback` | before each request to the model |
| | `after_model_callback` | after each response from the model |
| | `on_model_error_callback` | when a model call raises |
| **tool** | `before_tool_callback` | before each tool call |
| | `after_tool_callback` | after each tool call |
| | `on_tool_error_callback` | when a tool raises |
| **notification** | `on_agent_error_callback` | when an exception escapes an agent |
| | `on_run_error_callback` | when an exception escapes the runner |

Six of these you met yesterday as agent callbacks: the model pair, the tool pair, and the two error
hooks. `before_agent_callback` and `after_agent_callback` also exist on agents, so strictly the
overlap is eight. The four **run**-level hooks have no agent equivalent at all, and
[2.2](2.2-the-four-doors-an-agent-cannot-have.md) is why.

There is also a fifteenth method, `close`, which is not a hook. It runs when the runner is closed, and
it is where a plugin releases whatever it opened — a file handle, a network connection, a flush of
buffered metrics. It has a five-second timeout per plugin.

**Now the part that matters more than the list.** The live page at `adk.dev/plugins/` documents
**twelve** hooks. The installed `google-adk` 2.7.1 has **fourteen**. The two the page does not mention
are `on_agent_error_callback` and `on_run_error_callback`, and they behave differently from every
other hook on the list, which is [3.2](../03-the-rule-at-this-layer/3.2-the-two-hooks-that-cannot-stop-anything.md)'s
subject.

This is not a trap and it is not a bug. Documentation lags a release; that is normal. What matters is
the habit it forces, and it is Principle 8 with teeth: **the page tells you the intent, the installed
package tells you the behaviour, and when they disagree the package is what runs.** The way to settle
it is one command, given in *Check yourself* below, and it takes less effort than reading the page did.

## Why Sutra needs it

**Because today's build needs a door that is not in the documented twelve — and one that is.** The
meter counts at `before_model_callback` and `before_tool_callback`, which are documented, and reports
at `after_run_callback`, which is documented. But
[5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md) shows that the reporting door
does not fire on a failed run, and the hook that tells you a run failed is `on_run_error_callback` —
one of the two the page does not list. Sutra's meter is incomplete without a hook you cannot read
about.

**Because Day 84's tracer uses nearly all of them.** `AutoTracingPlugin` (ADK-74) has to open and
close a span at every level — run, agent, model, tool — which is exactly why the hook list is shaped
in pairs. Seeing the shape now makes that day a configuration change rather than a new concept.

**Because Day 72's backoff lives at `on_model_error_callback`.** Addendum 02 requires every model call
path to handle HTTP 429 with `retry-after` and backoff. At the plugin layer that is one hook, applied
to every agent, which is the only way to make "every model call path" a true statement rather than an
aspiration.

## The mechanism

The list is not worth memorising. It is worth **printing**, from the package you actually have.

```python
# lab/doors.py - ask the installed package what the doors are. Zero model calls.
import inspect

from google.adk.plugins import BasePlugin
from google.adk.plugins.plugin_manager import PluginCallbackName
from typing import get_args

hooks = [
    name
    for name, _ in inspect.getmembers(BasePlugin, inspect.isfunction)
    if name.endswith("_callback")
]

print(f"BasePlugin defines {len(hooks)} hooks:")
for name in hooks:
    signature = inspect.signature(getattr(BasePlugin, name))
    parameters = [p for p in signature.parameters if p != "self"]
    print(f"  {name:32} ({', '.join(parameters)})")

dispatched = list(get_args(PluginCallbackName))
print(f"\nPluginManager dispatches {len(dispatched)}:")
print(" ", ", ".join(sorted(dispatched)))

print("\nDefined but never dispatched:", sorted(set(hooks) - set(dispatched)) or "none")
print("Dispatched but not defined:  ", sorted(set(dispatched) - set(hooks)) or "none")
```

**Line by line:**

- `inspect.getmembers(BasePlugin, inspect.isfunction)` — reads the methods off the class itself rather
  than off an instance, so no plugin has to be constructed. This is the answer to "what does my
  version actually have", and it cannot be out of date.
- `if name.endswith("_callback")` — the filter that separates hooks from everything else on the class.
  It is why `close` does not appear: `close` is lifecycle, not a door, and the naming convention is
  load-bearing enough to filter on.
- `PluginCallbackName` — a `typing.Literal` inside `plugin_manager.py` listing every hook name the
  manager will dispatch. It is the second, independent answer to the same question, which is why the
  script reads both.
- `get_args(...)` — pulls the strings back out of the `Literal`. A `Literal["a", "b"]` stores its
  members in `__args__`, and `get_args` is the supported way to read them.
- The two set differences at the end are the real output. If a hook is **defined but never
  dispatched**, overriding it does nothing and you would never find out. If one is **dispatched but
  not defined**, the manager would call something the base class does not have. Both are empty here,
  which is what "the list is consistent" looks like when you check instead of assume.
- `f"  {name:32}"` — a fixed-width field so the signatures line up and the argument-name differences
  in [2.3](2.3-the-names-moved.md) are visible by eye rather than by reading.

## When it breaks

**💥 You misspelled a hook, and nothing happened.** There is no error text to quote, which is the
problem. `BasePlugin` is a plain class, not a registry — a method called `before_tool_calback` is just
a method nobody calls. Your plugin registers, the run succeeds, the hook never fires.

The one-line check:

```python
assert hasattr(BasePlugin, "before_tool_callback"), "not a real hook"
```

**💥 You implemented the same hook twice in one class.** Python keeps the second definition and
silently discards the first — normal class-body behaviour, and exactly what `BasePlugin`'s own
docstring warns about when it says a plugin *"should not implement the same method of callback for
multiple times."* No error. Half your logic is gone. A linter catches this; `ruff` reports it as
`F811 redefinition of unused 'before_tool_callback'`, which is one of the reasons `./m check` runs
`ruff` before it runs anything else.

**💥 You overrode `close` expecting it on every run.**

```text
(no output, no error)
```

`close` runs when the **runner** is closed, not at the end of each request. A plugin that flushes its
metrics in `close` flushes them once per process, not once per run. The per-run door is
`after_run_callback`, with the caveat in [5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md).

## In production

**What a professional writes instead of the teaching version** is a plugin that overrides the fewest
hooks that answer its question. Every hook you override runs on every agent, on every request,
forever. The meter in section 4 uses three of the fourteen and that is not minimalism for its own
sake — it is three places to audit when the numbers look wrong instead of fourteen.

**What degrades at scale** is `on_event_callback`. Look again at the firing table in
[2.4](2.4-fifteen-firings-one-run.md): the model and tool doors fire a handful of times per run, but
`on_event_callback` fires for **every event**, including the partial ones that streaming produces. A
plugin doing real work there — a regex over the text, a JSON parse, a synchronous write — is doing it
once per token chunk under streaming. It is the single easiest way to make an ADK application slow,
and it looks completely innocent in review.

**The failure that only shows with real traffic** is a hook that is correct for one agent shape and
wrong for another. `before_model_callback` receives an `LlmRequest` whose `contents` may be empty on
an agent invoked without a user message. A plugin that reads `llm_request.contents[0]` works for
eighteen months and then raises `IndexError` the week somebody adds a scheduled agent that starts from
a tool result. The hook applied to the new agent automatically — which was the feature — so the crash
is in a file the new agent's author has never opened.

**The review comment a senior engineer leaves:** *"This overrides `on_event_callback` to count model
calls. Count them in `before_model_callback` — you are running this on every partial event to learn
something the model door already tells you once."*

**The interview question:** *"What can a plugin hook into that an agent callback cannot?"* — "Four
run-level points: the user's message before anything runs, the start of the request, every event on
its way out, and the end of a successful request. Agents do not have those because a request can pass
through several agents and none of them is the request. In 2.7 there are fourteen hooks in total; the
docs still say twelve, because two notification-only error hooks landed since the page was written. I
check the installed class rather than the page, because the package is what runs."
