# 3.3 — A plugin that raises takes the run with it

## One-line answer

An exception in any of the twelve non-notification hooks is re-raised as a `RuntimeError` naming the
plugin and the hook, killing the whole request for **every** agent — so a plugin's error handling is
application-wide error handling whether you wrote it that way or not.

---

## The story

The queue at a small grocery shop on a Saturday.

Seven people, baskets full, and the card machine stops connecting. Not the till — the till is fine, the
scanner is fine, the shopkeeper is fine. One small device that most people use but nobody thinks of as
the shop.

The queue stops. Completely. The people paying cash are also stuck, because the person at the front is
not paying cash and there is one counter. A device that was there to make paying convenient has become
the thing that decides whether anyone can buy anything.

The shopkeeper's mistake, if there is one, was never thinking of that machine as load-bearing. It was
added to help. Nobody re-classified it when the whole shop started depending on it.

---

## The idea in plain language

A plugin hook that raises does not fail quietly and it does not fail locally.

`PluginManager._run_callbacks` wraps every hook call in a `try/except`. On an exception it logs the
error and then does this:

```text
raise RuntimeError(error_message) from e
```

Three consequences, and the third is the one people miss.

**The exception is replaced.** What propagates is a `RuntimeError`, not your `ValueError`. The original
is preserved as `__cause__`, which is what the `The above exception was the direct cause of the
following exception` block in the traceback is showing you — but any `except ValueError:` you have
written upstream will not catch it.

**The message is genuinely useful**, which is unusual enough to point out. It contains the plugin's
name and the hook's name:

```text
Error in plugin 'meter' during 'before_model_callback' callback: <the original message>
```

That is [1.3](../01-where-a-plugin-lives/1.3-a-name-and-only-one-of-it.md)'s name earning its keep. With
four plugins installed, this line is the difference between knowing and bisecting.

**The blast radius is the application.** This is the part that separates today from yesterday. A
callback that raises breaks one agent's turn. A plugin that raises breaks the same door for *every
agent in the application*, so a bug in a hook that fires on every model call is a total outage, not a
degraded feature.

That asymmetry deserves stating plainly, because it is the price of the thing that made plugins
attractive in the first place. Yesterday's argument for the plugin layer was **coverage**: write it
once and every agent gets it, including agents you have not written. This is the same sentence read in
the other direction. Write a bug once and every agent gets it, including agents you have not written.

---

## Why Sutra needs it

**Because the meter runs on every model call of every agent.** Section 4's plugin is exactly the shape
described above: a hook at the highest-frequency door in the application. An `AttributeError` in it
takes down the desk, and later the whole Phase 8 graph.

**Because Sutra's plugins will do I/O eventually.** Today's meter prints. Day 84's tracer talks to an
OpenTelemetry exporter, and Day 70's router reads quota state. Every one of those can fail in ways a
`print` cannot, and each of them sits at a door on the critical path of every request.

**Because a `RuntimeError` at the top defeats a specific `except`.** Sutra's entry points
(`sutra/desk/run_once.py`, and later the API server on Day 85) catch what they expect. A plugin
failure arrives as something they do not expect, which is the correct outcome — it should be loud —
but only if you know why the type changed.

## The mechanism

```python
# lab/plugin_raises.py - one bad line in a plugin, and nobody gets served. Zero model calls.
import asyncio
import logging

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.plugins import BasePlugin
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types
from stateless import ReactiveModel

logging.disable(logging.CRITICAL)


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    print("      >> the tool ran")
    return {"status": "ok", "ticket_id": ticket_id}


class Meter(BasePlugin):
    """A meter with one plausible bug: it assumes there is always a first content."""

    def __init__(self, *, guarded: bool) -> None:
        super().__init__(name="meter")
        self.guarded = guarded

    async def before_model_callback(self, *, callback_context, llm_request):
        if self.guarded and not llm_request.contents:
            return None
        first = llm_request.contents[0]
        print(f"      metered a call whose first content is {first.role!r}")


async def drive(label: str, guarded: bool, contents: bool) -> None:
    print(f"  {label}")
    agent = LlmAgent(
        name="desk",
        model=ReactiveModel(model="scripted"),
        instruction="x",
        tools=[lookup_ticket],
    )
    app = App(name="sutra", root_agent=agent, plugins=[Meter(guarded=guarded)])
    runner = Runner(app=app, session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name=app.name, user_id="u")
    message = (
        types.Content(role="user", parts=[types.Part(text="hi")])
        if contents
        else types.Content(role="user", parts=[])
    )
    try:
        async for _ in runner.run_async(user_id="u", session_id=session.id, new_message=message):
            pass
        print("      the run finished")
    except RuntimeError as error:
        print(f"      RuntimeError: {error}")
        print(f"      __cause__:   {type(error.__cause__).__name__}: {error.__cause__}")


async def main() -> None:
    await drive("a. an ordinary question", guarded=False, contents=True)
    await drive("b. a message with no parts, unguarded", guarded=False, contents=False)
    await drive("c. the same message, guarded", guarded=True, contents=False)


asyncio.run(main())
```

**Line by line:**

- `Meter(guarded=...)` — one class, two behaviours, so cases **b** and **c** differ by exactly the
  guard clause and nothing else. Writing two classes would leave room to wonder what else changed.
- `if self.guarded and not llm_request.contents: return None` — the fix, and it is three words long.
  Returning `None` is the carry-on value from [3.1](3.1-is-not-none-and-this-time-it-means-it.md), so
  guarding costs nothing except the metering of a request there was nothing to meter.
- `llm_request.contents[0]` unguarded — the bug, and it is deliberately a *plausible* one rather than
  an obviously silly one. Reading the first content is a reasonable thing for a meter to want, and the
  case where there is none is rare enough to never appear in a test.
- `types.Content(role="user", parts=[])` — a message with no parts. It is the smallest way to reach
  an empty `contents` without inventing an exotic agent, and it stands in for the real-world versions:
  a scheduled run started from a tool result, a resumed invocation, an agent invoked by another agent.
- `except RuntimeError` specifically, then printing `error.__cause__` — the two halves of what actually
  happened. The `RuntimeError` is ADK's wrapper; the `__cause__` is your bug. A reader who only ever
  looks at the top-level type learns nothing about their own code.
- `print("      >> the tool ran")` inside the tool — so the output shows whether anything got as far
  as doing work. In case **b** it does not: the failure is at the first model call, before any tool.

The output:

```text
  a. an ordinary question
      metered a call whose first content is 'user'
      >> the tool ran
      metered a call whose first content is 'user'
      the run finished
  b. a message with no parts, unguarded
      RuntimeError: Error in plugin 'meter' during 'before_model_callback' callback: list index out of range
      __cause__:   IndexError: list index out of range
  c. the same message, guarded
      >> the tool ran
      metered a call whose first content is 'model'
      the run finished
```

Case **b** is a total failure of the request caused by one subscript in an observer. The meter was
never meant to be able to stop anything. It has no `return` statement at all. It stopped everything.

Note also what is *not* in case **b**: `>> the tool ran` is absent, and so is the second metering
line. The run died at the first door it reached.

Case **c** is worth a second look, because the guard did not merely prevent a crash — it revealed what
the request actually was. The first model call is skipped by the guard, exactly as intended. Then the
tool runs, and the **second** model call does have contents, so it is metered — and its first content
has `role='model'`, not `'user'`. That is the empty user message doing what it says: there was never
any user content, so the earliest thing in the conversation is the model's own function call. A meter
that assumed `contents[0]` was always the user's question would have been quietly wrong here even if
it had not crashed.

Verified against the installed `google-adk` 2.7.1 — `PluginManager._run_callbacks` catches
`Exception`, logs it, and does `raise RuntimeError(error_message) from e` — on 2026-08-29.

## When it breaks

**💥 The wrapper, in full.** This is what you will actually see, with logging enabled:

```text
RuntimeError: Error in plugin 'meter' during 'before_model_callback' callback: list index out of range
```

Read it right to left. The last clause is your bug. The middle names the door. The first names the
plugin. Three facts, and you have not opened a file yet.

**💥 Your `except` stopped catching.**

```python
try:
    ...run the agent...
except IndexError:
    ...                      # never fires: the IndexError arrived wrapped
```

The wrapping is why. If you must branch on the original, branch on `error.__cause__`, and remember
that a `RuntimeError` from ADK might also be a genuine `RuntimeError` from somewhere else.

**💥 The plugin that fails only in production.** No error text here either, because the error text is
the point: it appears in production and nowhere else. A hook reading `os.environ["OTEL_ENDPOINT"]`
raises `KeyError` on any machine where that variable is unset. Every developer has it in their `.env`.
The build server does not.

## In production

**What a professional writes instead of the teaching version** decides, per hook, whether this plugin
is allowed to break the request — and writes the decision down:

```python
async def before_model_callback(self, *, callback_context, llm_request) -> None:
    """Metering must never be the reason a request fails."""
    try:
        self._count(callback_context.invocation_id)
    except Exception:
        logger.exception("meter failed; continuing")
```

**Line by line:**

- The docstring states the policy, because the `except Exception` below it looks exactly like the
  anti-pattern `CLAUDE.md` bans — *"catching exceptions just to swallow"* — and it is only defensible
  with the reason attached. A meter is not load-bearing. A credential filter is, and would never get
  this treatment: if the filter cannot run, the request must not proceed.
- `logger.exception(...)` and not `logger.error(...)` — `exception` records the traceback, so the
  swallowed failure is still fully diagnosable. Swallowing without logging is what Principle 10
  forbids; swallowing *with* a traceback and a stated policy is a deliberate availability trade.
- The annotation `-> None` and no `return` in either branch — the hook cannot accidentally short-circuit
  the model call while trying to be safe.
- `self._count(...)` extracted rather than inlined, so the `try` block is one line and it is obvious
  exactly what is being protected. A wide `try` block eventually swallows something you did not mean
  to protect.

**What degrades at scale** is that this trade has to be made per plugin, and the answer differs. Split
your plugins by whether they are load-bearing: observers — meters, tracers, loggers — guard themselves
and degrade to nothing. Enforcers — filters, quota gates, auth checks — must be allowed to raise,
because an enforcer that fails open is worse than an outage.

**The failure that only shows with real traffic** is the plugin whose hook is fine on every request
shape you tested and raises on the one you did not. Case **b** above is a miniature of it. Real
versions: a `llm_response.content.parts[0]` on a response that was blocked by a safety filter and has
no parts; a `tool_args["ticket_id"]` on a call where the model omitted the argument. Both are one
subscript, both are invisible in review, and both take the application down rather than one agent.

**The review comment a senior engineer leaves:** *"This is an observer on the hottest door in the app
and it indexes into `contents` without a guard. Either guard it or wrap the body — right now a
malformed request is a full outage."*

**The interview question:** *"What happens if a plugin throws?"* — "The plugin manager catches it, logs
it, and re-raises it as a `RuntimeError` whose message names the plugin and the hook, with the original
as `__cause__`. So it kills the whole invocation, and because a plugin applies to every agent, it kills
it for every agent — a bug in one observer is an application-wide outage rather than one degraded
agent. Which is why I split plugins by whether they are load-bearing: metering and tracing wrap their
own bodies and log-and-continue, because they should never be the reason a request fails, while
anything enforcing a policy is deliberately left able to raise, since an auth check that fails open is
worse than downtime. The notification-only error hooks are the exception — those get their exceptions
swallowed by the framework so they cannot mask the real failure."
