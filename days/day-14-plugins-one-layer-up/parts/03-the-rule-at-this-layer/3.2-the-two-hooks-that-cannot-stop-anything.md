# 3.2 — The two hooks that cannot stop anything

## One-line answer

`on_agent_error_callback` and `on_run_error_callback` are **notification-only**: every plugin is
always told, their return values are discarded, the original exception is always re-raised, and a
plugin that raises inside one of them has its own error swallowed so it cannot mask the real failure.

---

## The story

The smoke alarm in a rented flat.

It goes off at two in the morning because somebody burned toast. It is loud, it is unmissable, and it
does exactly one thing: it tells you. It does not open a window, it does not turn off the toaster, and
it does not put out a fire.

That is not a limitation somebody forgot to fix. An alarm that also tried to intervene would be an
alarm you could not trust, because now there are two questions — did it detect the smoke, and did its
intervention work — and you only ever hear the answer to one of them.

There is a second thing about it worth noticing. If the alarm's battery dies mid-beep, the fire does
not stop being a fire. The alarm failing is a bad day. The alarm failing *quietly, in a way that made
you think there was no fire* would be a much worse one.

---

## The idea in plain language

Twelve of the fourteen hooks share the rule from
[3.1](3.1-is-not-none-and-this-time-it-means-it.md): return `None` and things proceed, return anything
else and your value replaces something.

Two do not. `on_agent_error_callback` and `on_run_error_callback` are dispatched through a completely
different method inside `PluginManager` — `_run_notification_callbacks` rather than `_run_callbacks` —
and it behaves in three deliberately different ways.

**Every plugin is always called.** There is no early exit. One plugin returning something does not
stop the next from being told, because "who else needs to know about this failure?" has no sensible
first-answer-wins semantics.

**Return values are discarded.** The method's return type is `None` and it never inspects what your
hook gave back. You may return a dict; it goes nowhere.

**Exceptions from the hook are logged and swallowed.** If your notification hook raises, ADK logs it
and carries on to the next plugin, then re-raises the *original* error. Your broken notifier cannot
replace the real failure with itself.

ADK's own docstring is unusually direct about it:

> *"This is a notification-only callback. The exception is always re-raised after all registered
> plugins have been notified. Plugins should NOT suppress the exception."*

So the error hooks split into two kinds, and knowing which is which is the whole part:

| Hook | Can it substitute a result? | On a raise inside it |
| --- | --- | --- |
| `on_model_error_callback` | **yes** — return an `LlmResponse` and the error is suppressed | wrapped as `RuntimeError` |
| `on_tool_error_callback` | **yes** — return a dict and it becomes the tool result | wrapped as `RuntimeError` |
| `on_agent_error_callback` | no — return value discarded | logged, swallowed, original re-raised |
| `on_run_error_callback` | no — return value discarded | logged, swallowed, original re-raised |

The design is 1.x → 2.x **trap #4** made structural. Plan §5.1 says 2.x *"surfaces exceptions through
the runtime so callbacks/plugins can act on them"*, and the 1.x habit it is correcting is catching an
error and returning a string so the failure disappears. ADK's answer is to give you two hooks where
recovery is genuinely possible — a model call and a tool call are both things that can sensibly be
retried or substituted — and two where it is not, and to make the second pair *structurally incapable*
of hiding the failure. You cannot swallow an exception you were only ever told about.

That is Principle 10 — **fail honestly** — enforced by the framework rather than by your discipline.

---

## Why Sutra needs it

**Because the meter's bill has to print on failed runs too, and `after_run_callback` will not.**
[5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md) is that gap;
`on_run_error_callback` is the only hook that closes it. A run that failed after four model calls
still spent four model calls of quota, and Addendum 02 counts quota, not successes.

**Because Day 72's escalation lives here.** The backoff ladder retries at
`on_model_error_callback`, and when the ladder is exhausted something has to record that the request
died rather than silently returning a plausible answer. That recording is a notification hook, and it
being unable to suppress the error is the feature.

**Because Day 84's tracing needs failed traces most.** A trace tree that only closes its root span on
success loses exactly the requests anyone wants to look at. `on_run_error_callback` is where the span
gets its error status.

## The mechanism

```python
# lab/error_hooks.py - two hooks that fix things, two that only watch. Zero model calls.
import asyncio
import logging

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.plugins import BasePlugin
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types
from stateless import ReactiveModel

logging.disable(logging.CRITICAL)


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id. Today the database is down."""
    raise ConnectionError("ticket database unreachable")


class Substitute(BasePlugin):
    """Handles the tool failure honestly, at the hook that is allowed to."""

    def __init__(self) -> None:
        super().__init__(name="substitute")

    async def on_tool_error_callback(self, *, tool, tool_args, tool_context, error):
        print(f"      on_tool_error saw {type(error).__name__}; substituting")
        return {
            "status": "unavailable",
            "reason": "lookup is down",
            "next": "try again shortly",
        }


class TriesToStop(BasePlugin):
    """Returns values from the notification hooks. They are discarded."""

    def __init__(self) -> None:
        super().__init__(name="tries")

    async def on_agent_error_callback(self, *, agent, callback_context, error):
        print("      on_agent_error returns a value")
        return {"status": "handled"}

    async def on_run_error_callback(self, *, invocation_context, error):
        print("      on_run_error returns a value")
        return {"status": "handled"}


class Raises(BasePlugin):
    """A broken notifier. Its own failure must not replace the real one."""

    def __init__(self) -> None:
        super().__init__(name="raises")

    async def on_run_error_callback(self, *, invocation_context, error):
        raise ValueError("the notifier itself is broken")


async def drive(label: str, plugins: list[BasePlugin]) -> None:
    print(f"  {label}")
    agent = LlmAgent(
        name="desk",
        model=ReactiveModel(model="scripted"),
        instruction="x",
        tools=[lookup_ticket],
    )
    app = App(name="sutra", root_agent=agent, plugins=plugins)
    runner = Runner(app=app, session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name=app.name, user_id="u")
    try:
        async for event in runner.run_async(
            user_id="u",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text="hi")]),
        ):
            for part in (event.content.parts if event.content else []) or []:
                if part.function_response:
                    print("      the model was told:", part.function_response.response)
        print("      the run finished")
    except Exception as error:
        print(f"      the run raised {type(error).__name__}: {error}")


async def main() -> None:
    await drive("a. on_tool_error substitutes - the run survives", [Substitute()])
    await drive("b. the notification hooks return values", [TriesToStop()])
    await drive("c. the notification hook itself raises", [Raises()])


asyncio.run(main())
```

**Line by line:**

- `logging.disable(logging.CRITICAL)` — ADK logs the full traceback of a failing run at error level,
  and this script is about three short lines of output. Silencing the logger here is a **teaching**
  choice; doing it in an application would be deleting exactly the evidence Principle 10 exists to
  preserve. It is at the top of the file so it is impossible to copy the plugin classes without
  noticing it.
- `raise ConnectionError(...)` inside the tool rather than returning an error dict — trap #4. A tool
  that catches its own failure and returns `{"status": "error"}` gives the error hooks nothing to act
  on, because from ADK's point of view the tool succeeded.
- `Substitute.on_tool_error_callback` returning a three-field dict — the honest refusal shape from
  [13/3.2](../../../day-13-callbacks-four-doors/parts/03-the-tool-doors/3.2-refusing-a-tool-call-honestly.md):
  a `status` the model can branch on, a `reason` it can relay, and a `next` so it does not simply
  retry. `{"status": "ok", "results": []}` here would be a lie the agent tells a customer.
- `TriesToStop` returning dicts from both notification hooks — case **b** exists to prove those
  returns do nothing. The `print` fires, so the hook definitely ran; the run still dies.
- `Raises` — case **c**, the broken alarm. The `ValueError` it raises never reaches you.
- `except Exception as error` at the call site rather than a specific type, because the whole question
  of the script is *which* exception arrives.

The output:

```text
  a. on_tool_error substitutes - the run survives
      on_tool_error saw ConnectionError; substituting
      the model was told: {'status': 'unavailable', 'reason': 'lookup is down', 'next': 'try again shortly'}
      the run finished
  b. the notification hooks return values
      on_agent_error returns a value
      on_run_error returns a value
      the run raised ConnectionError: ticket database unreachable
  c. the notification hook itself raises
      the run raised ConnectionError: ticket database unreachable
```

Case **b** is the one to read twice. Both hooks ran — you can see their lines. Both returned a dict.
The run raised anyway, with the original `ConnectionError`, unchanged.

Case **c** is the one that should reassure you. A plugin raised `ValueError` inside a notification
hook, and the error you got is still `ConnectionError: ticket database unreachable`. The framework
refused to let a broken observer become the story.

Note also the ordering in **b**: `on_agent_error` fires before `on_run_error`. The exception escapes
the agent first, then the runner, and both are told on the way out.

Verified against the installed `google-adk` 2.7.1 — `_run_notification_callbacks` iterates all
plugins, ignores return values, and wraps each call in `try/except` that logs and continues; the
runner's `_notify_run_error` helper additionally suppresses anything `on_run_error_callback` raises
*"so the original run error propagates"* — on 2026-08-29.

## When it breaks

**💥 You tried to recover in the wrong hook.**

```text
(no error, no effect - the run dies exactly as it would have)
```

There is no message telling you that a return value was ignored. A plugin author who writes recovery
logic in `on_run_error_callback` gets a hook that runs, does its work, returns a perfectly good
fallback, and changes nothing. If you need to substitute, the tool and model error hooks are where it
is possible.

**💥 Your notification hook raises and you never find out.** The swallowing that protects the original
error also hides your bug. The only evidence is a log line at error level:

```text
Error in plugin 'raises' during 'on_run_error_callback' callback: the notifier itself is broken
```

If your application filters logs below `CRITICAL`, or a teaching script disables logging the way this
one does, that line does not appear and the hook is silently dead.

**💥 You expected `on_tool_error_callback` and the tool never raised.** The most common version of
this: your tool catches its own exception and returns a string. The error hooks are not called,
because there was no error — the tool returned a value, and that value is now on its way to the model
as if it were a result. Trap #4, and the fix is in the tool, not the plugin.

## In production

**What a professional writes instead of the teaching version** treats the two kinds as different jobs.
Substitution hooks carry an allow-list; notification hooks carry no logic at all:

```python
TRANSIENT = (ConnectionError, TimeoutError)


async def on_tool_error_callback(self, *, tool, tool_args, tool_context, error):
    if not isinstance(error, TRANSIENT):
        return None
    return blocked(reason=f"{tool.name} is unavailable", next_step="retry shortly")


async def on_run_error_callback(self, *, invocation_context, error):
    self._emit(invocation_context.invocation_id, type(error).__name__)
```

**Line by line:**

- `TRANSIENT` as a module constant — the list of failures it is honest to paper over. A network blip
  is one. `KeyError` in your own code is not: substituting for your own bug converts a loud crash into
  a wrong answer, which is the exact trade Principle 10 forbids.
- `if not isinstance(error, TRANSIENT): return None` **first** — returning `None` re-raises, so the
  default is to let the failure through and the allow-list is the exception. Written the other way
  round, a new exception type added next year is silently swallowed by default.
- `self._emit(...)` and nothing else in the notification hook — no branching, no recovery, no return.
  The hook's only job is to record, and giving it one statement makes "does this hook suppress
  anything?" answerable at a glance.
- `invocation_context.invocation_id` as the key — the same id the meter uses in
  [4.3](../04-the-meter/4.3-one-instance-every-run.md), so a failed run's partial bill and its error
  record join up.

**What degrades at scale** is a notification hook doing I/O. It fires on the failure path, which is
the path that is already slow and is often slow because a downstream service is struggling. A hook
that writes synchronously to that same service during an incident turns a failure into a slower
failure, for every request, at exactly the wrong moment.

**The failure that only shows with real traffic** is the substitution hook with too wide an allow-list.
`except Exception` in `on_tool_error_callback` means every bug in every tool becomes
`{"status": "unavailable"}`, and the agent politely tells thousands of customers to try again later
while the actual cause is a `TypeError` you introduced on Tuesday. Your error rate looks fine. Your
success rate looks fine. The answers are wrong.

**The review comment a senior engineer leaves:** *"`on_tool_error_callback` catches everything. Narrow
it to transient network failures — right now a `KeyError` in our own tool is being reported to users
as a temporary outage."*

**The interview question:** *"How does ADK stop a plugin from hiding a failure?"* — "It splits the
error hooks. The model and tool error hooks can return a substitute, because those are the two places
where retrying or degrading is genuinely reasonable. The agent and run error hooks are
notification-only: every plugin is told, return values are discarded, and the original exception is
always re-raised. On top of that, if a notification hook raises, ADK logs and swallows *that* so the
real error still propagates. So the framework makes it structurally impossible to accidentally
swallow a run failure in an observer, which is the 1.x habit that 2.x's breaking-changes list
specifically calls out."
