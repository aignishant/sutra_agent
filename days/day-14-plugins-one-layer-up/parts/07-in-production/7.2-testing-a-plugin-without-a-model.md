# 7.2 — Testing a plugin without a model

## One-line answer

A plugin cannot be tested by calling its hooks directly the way an agent callback can, because every
interesting thing about it — that it is installed, that it covers every agent, that it cleans up on
failure — is a fact about a **whole run**, so the suite drives a real `Runner` against a scripted
model and asserts on outcomes rather than on hooks having fired.

---

## The story

A torch in a kitchen drawer, kept for power cuts.

There is one way to find out whether it works and one way that feels like finding out. The way that
feels like it: you look at it, you remember buying batteries at some point, you note that it is where
it should be, and you close the drawer satisfied.

The way that works: you press the switch.

It takes a second, and it is the only thing that distinguishes a torch from a torch-shaped object. The
trouble with the first method is not that it is lazy — it is that it produces exactly the same feeling
of confidence as the second, right up until the night you need it.

---

## The idea in plain language

Yesterday's callbacks were easy to test. `block_forbidden_queries` is a plain function: build three
keyword arguments, call it, assert on the return value. Four of Day 13's five tests did exactly that
([13/6.1](../../../day-13-callbacks-four-doors/parts/06-in-production/6.1-testing-a-callback-without-a-model.md)).

A plugin resists that, and it is worth being precise about why rather than just asserting it.

**You can call `await ledger.before_model_callback(callback_context=..., llm_request=...)` directly.**
It will work. It will increment the counter. And it proves almost nothing, because everything that can
actually go wrong with a plugin is about its relationship to the run:

| The real risk | Can a direct hook call detect it? |
| --- | --- |
| the plugin is not installed at all ([1.2](../01-where-a-plugin-lives/1.2-the-app-is-what-plugins-belong-to.md)) | **no** — you called it yourself |
| a parameter name is wrong ([2.3](../02-the-fourteen-doors/2.3-the-names-moved.md)) | **no** — you passed the names you wrote |
| the bill is missing on failed runs ([5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md)) | **no** — no run, no failure |
| per-run state leaks ([4.3](../04-the-meter/4.3-one-instance-every-run.md)) | **no** — one call, one entry |
| the arithmetic is right | yes |

Four of the five say no. So the suite is built the other way round: **drive a real `Runner` over a
real `App` with a scripted model, and assert on what the plugin recorded.** That is not an integration
test in disguise — it costs nothing, needs no key, and runs on a fresh clone — because the model is a
`BaseLlm` subclass reading from a script
([2.2](../02-the-fourteen-doors/2.2-the-four-doors-an-agent-cannot-have.md)).

One principle runs through all five tests: **assert the outcome, never that the hook fired.** A hook
that runs and does nothing is
[5.1](../05-where-the-layer-bites/5.1-the-door-documented-to-stop-the-run.md)'s entire failure, and a
test asserting `hook_was_called is True` would have passed happily on it.

---

## Why Sutra needs it

**Because `./m check` has to stay green on a fresh clone.** Principle 11 says every day ends with a
check that can go RED, and Addendum 02 says nothing may require a key. A plugin suite that needs
Gemini satisfies neither.

**Because the plugin is now the thing between Sutra and its quota.** From today, the number Day 70's
router will act on comes out of this class. A wrong meter that nobody tests is a router making
confident decisions on fiction.

**Because Day 31's quality gate will run this suite on every change.** OPS-08's lint-and-test gate is
where a signature typo in a plugin gets caught before it is an application-wide outage.

## The mechanism

```python
# tests/test_plugins.py - the run ledger. No API key, no network, no model.
from __future__ import annotations

import asyncio

import pytest
from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

from sutra.plugins import RunLedger
from tests.scripted import ReactiveModel


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    return {"status": "ok", "ticket_id": ticket_id}


def explode(ticket_id: str) -> dict:
    """A tool whose backend is down."""
    raise ConnectionError("ticket database unreachable")


def build(tool, ledger: RunLedger) -> App:
    """One agent, one tool, the ledger installed on the App."""
    agent = LlmAgent(
        name="desk",
        model=ReactiveModel(model="scripted", chain=[tool.__name__]),
        instruction="x",
        tools=[tool],
    )
    return App(name="sutra", root_agent=agent, plugins=[ledger])


async def drive(app: App) -> None:
    """Run one question through the app."""
    runner = Runner(app=app, session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name=app.name, user_id="u")
    async for _ in runner.run_async(
        user_id="u",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="ticket 4521")]),
    ):
        pass


def test_the_plugin_is_actually_installed() -> None:
    ledger = RunLedger()
    runner = Runner(
        app=build(lookup_ticket, ledger), session_service=InMemorySessionService()
    )
    assert runner.plugin_manager.get_plugin(RunLedger.NAME) is ledger


def test_a_one_tool_run_costs_two_model_calls() -> None:
    ledger = RunLedger()
    asyncio.run(drive(build(lookup_ticket, ledger)))
    ((_, outcome, bill),) = ledger.closed
    assert outcome == "ok"
    assert bill["model:scripted"] == 2
    assert bill["tool:lookup_ticket"] == 1


def test_a_failed_run_is_still_billed() -> None:
    ledger = RunLedger()
    with pytest.raises(ConnectionError):
        asyncio.run(drive(build(explode, ledger)))
    ((_, outcome, bill),) = ledger.closed
    assert outcome == "error:ConnectionError"
    assert bill["model:scripted"] == 1


def test_no_run_state_is_left_behind() -> None:
    ledger = RunLedger()
    asyncio.run(drive(build(lookup_ticket, ledger)))
    with pytest.raises(ConnectionError):
        asyncio.run(drive(build(explode, ledger)))
    assert ledger.runs == {}


def test_each_run_is_billed_separately() -> None:
    ledger = RunLedger()
    app = build(lookup_ticket, ledger)
    for _ in range(3):
        asyncio.run(drive(app))
    assert [bill["model:scripted"] for _, _, bill in ledger.closed] == [2, 2, 2]


@pytest.mark.skip(reason="TODO(me): check the ledger against the provider's own count")
def test_the_ledger_agrees_with_the_provider() -> None:
    """Every number above comes from our own hooks. Nothing has checked them
    against what the provider actually recorded, and a retry inside the model
    layer is invisible from `before_model_callback`."""
```

**Line by line:**

- `asyncio.run(drive(...))` inside a **synchronous** test, rather than `@pytest.mark.asyncio` — that
  marker needs `pytest-asyncio`, which is not in `pyproject.toml`, and Principle 7 says a package
  arrives on the day it is first used. This is the convention Day 13 set for the same reason
  ([13/6.1](../../../day-13-callbacks-four-doors/parts/06-in-production/6.1-testing-a-callback-without-a-model.md)).
- `from tests.scripted import ReactiveModel` — the lab's `stateless.py`, moved into `tests/` so the
  suite does not import from a day folder. Day 13 left a `TODO(me)` about where the shared test double
  should live; this is the day it needs an answer, and the hub's build brief asks you to make it.
- `build(tool, ledger)` taking the **tool function** and deriving the chain from `tool.__name__` —
  the happy-path and failure tests then differ by one argument. A helper whose parameters are exactly
  the things that vary is what keeps five tests readable.
- `test_the_plugin_is_actually_installed` uses `get_plugin(RunLedger.NAME) is ledger` — identity, not
  equality. It asserts that **this object** is the one registered, which is what fails if somebody
  swaps `Runner(app=...)` for `InMemoryRunner(agent=...)`
  ([1.2](../01-where-a-plugin-lives/1.2-the-app-is-what-plugins-belong-to.md)). It is also the only
  test that does not run anything, because installation is a fact about construction.
- `((_, outcome, bill),) = ledger.closed` — tuple unpacking with a trailing comma, which asserts the
  list has **exactly one** entry. If a run were billed twice this raises `ValueError` rather than
  quietly reading the first. The `_` discards the invocation id, which is a fresh `uuid4` per run and
  therefore cannot be asserted on.
- `bill["model:scripted"] == 2` — the arithmetic from
  [4.1](../04-the-meter/4.1-counting-what-a-run-costs.md), pinned. If ADK ever changes how many model
  calls a tool round trip takes, this is the test that says so.
- `with pytest.raises(ConnectionError)` in the failure test — the exception is **expected**, so the
  test asserts it arrives. Letting it escape would fail the test for the right reason by accident,
  which is not the same thing.
- `assert ledger.runs == {}` — the leak test, and it runs one successful and one failed run precisely
  because [5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md) showed the failure path
  is the one that leaks. A leak test that only runs the happy path passes on a plugin with the bug.
- `[bill["model:scripted"] for _, _, bill in ledger.closed] == [2, 2, 2]` — three runs, one `App`, one
  ledger instance. This is [4.3](../04-the-meter/4.3-one-instance-every-run.md)'s `2, 4, 6` written as
  an assertion; a shared counter makes this list `[2, 4, 6]` and the test red.
- The skipped sixth test has a **docstring rather than a comment**, so `pytest -rs` prints why it is
  skipped without anybody opening the file.

Watch it go RED before it goes green:

```bash
uv run python -m pytest tests/test_plugins.py -q -m "not live"   # RED: sutra/plugins.py is empty
# ... write the module from the hub's build brief ...
uv run python -m pytest tests/test_plugins.py -q -m "not live"   # 5 passed, 1 skipped
```

Then break each one on purpose. These are the measured results, not predictions:

| Break this | Which tests go red | What it is telling you |
| --- | --- | --- |
| delete `on_run_error_callback` | `a_failed_run_is_still_billed`, `no_run_state_is_left_behind` | failed runs are unbilled **and** leak ([5.2](../05-where-the-layer-bites/5.2-the-bill-that-never-prints.md)) |
| `self.runs.get(...)` instead of `.pop(...)` | `no_run_state_is_left_behind` | the entry is read but never removed |
| key the counter on `"all"` instead of `invocation_id` | `no_run_state_is_left_behind`, `each_run_is_billed_separately` | one counter for the process ([4.3](../04-the-meter/4.3-one-instance-every-run.md)) |
| rename `tool_args` to `args` | **four of the five** | the names are the contract ([2.3](../02-the-fourteen-doors/2.3-the-names-moved.md)) |

Only the last breaks nearly everything, which is what makes the first three useful: they say *what*
broke, not merely *that* something did.

**And one thing left undone deliberately.** The sixth test is skipped with a `TODO(me)`, because every
number in this file was produced by the plugin being tested. Nothing here has compared the ledger with
what a provider actually recorded — and
[4.1](../04-the-meter/4.1-counting-what-a-run-costs.md) already named a case where they must differ: a
retry inside the model layer is one more HTTP request and zero more `before_model_callback` firings. A
green suite that implied otherwise would be claiming a guarantee it cannot make.

Verified against the installed `google-adk` 2.7.1 and `pytest` 9.1.1 on 2026-08-29 by running the
suite and each of the four breakages.

## When it breaks

**💥 The five tests pass and the plugin does nothing in production.**

```text
5 passed, 1 skipped
```

This is the outcome if you write the whole suite against `InMemoryRunner`. Every test constructs its
own runner, so every test would exercise
[1.2](../01-where-a-plugin-lives/1.2-the-app-is-what-plugins-belong-to.md)'s case **c** — a different
`App`, no plugins — and the assertions on `ledger.closed` would fail immediately, which is the good
news. The bad version is subtler: a suite that only asserts *"the hook incremented the counter"* by
calling hooks directly passes under any wiring at all.

**💥 `ValueError` from the unpacking.**

```text
ValueError: too many values to unpack (expected 1)
```

`ledger.closed` has more than one entry. Either a run was billed twice — which would mean
`after_run_callback` and `on_run_error_callback` both fired, and they should be mutually exclusive —
or you reused a `RunLedger` across tests. Each test constructs its own for exactly this reason.

**💥 `RuntimeError` about the event loop.**

```text
RuntimeError: asyncio.run() cannot be called from a running event loop
```

You added `pytest-asyncio` later and marked one of these tests `async def` while leaving the
`asyncio.run` inside it. Pick one style per test: either the marker and a bare `await`, or a sync test
with `asyncio.run`.

## In production

**What a professional writes instead of the teaching version** adds one test nobody thinks of, which
is that the plugin covers an agent it was never told about:

```python
def test_the_ledger_covers_an_agent_it_was_not_written_for() -> None:
    ledger = RunLedger()
    app = build(lookup_ticket, ledger)
    app.root_agent = LlmAgent(
        name="faq", model=ReactiveModel(model="scripted", chain=[]), instruction="x"
    )
    asyncio.run(drive(app))
    assert ledger.closed, "a plugin must cover agents added after it was written"
```

**Line by line:**

- Replacing `app.root_agent` after construction rather than building a second `App` — the point is
  that the **same** application, with the same plugin list, now has a different agent in it. That is
  what "somebody adds an agent next quarter" looks like as a test.
- The new agent has **no tools**, and `chain=[]` so the scripted model does not ask for one. It
  exercises a shape the ledger was never run against — a run that spends one model call and nothing
  else — and a plugin that assumed a tool call would be caught here.
- `assert ledger.closed` with a message rather than a count — the claim is coverage, not arithmetic,
  and the message states the claim so a failure reads as a sentence.
- This is the test that would have caught
  [6.1](../06-failure-lab/6.1-the-rule-that-broke-an-agent-nobody-was-looking-at.md)'s failure lab if
  it had asserted the *second* agent still worked rather than only that the plugin fired. Coverage is
  the feature; the same test shape checks the feature and its blast radius.

**What degrades at scale** is that the scripted model diverges from the real one. Everything here is
pinned to a double that yields once per call, so nothing in this suite would notice streaming making
`after_model_callback` fire per fragment. Suites like this need one live test, marked and excluded
from the default run — which is what the `-m "not live"` marker in `./m check` exists for.

**The failure that only shows with real traffic** is concurrency. Every test here is sequential.
[4.3](../04-the-meter/4.3-one-instance-every-run.md) showed the naive meter passing a sequential eye
test and failing badly under `asyncio.gather`, and `test_each_run_is_billed_separately` catches the
sequential half of that only. A `gather`-based test is worth adding the day Sutra actually serves
concurrent traffic, and worth knowing you have not written yet until then.

**The review comment a senior engineer leaves:** *"Every test drives one agent. Add one that swaps the
root agent for a different one — coverage of agents we did not write is the entire reason this is a
plugin, and nothing here tests it."*

**The interview question:** *"How do you test a framework plugin?"* — "Not by calling its hooks. Almost
everything that goes wrong with a plugin is about its relationship to the run — whether it is actually
registered, whether the parameter names match what the framework passes, whether it cleans up when the
run fails — and a direct hook call proves none of those, because you supplied the arguments and the
wiring yourself. So I drive a real runner over a real app with a scripted model, which costs nothing
and needs no key, and assert on what the plugin recorded rather than that a hook fired. That
distinction matters: a hook that runs and has no effect is a real failure mode, and 'was it called' is
green on it. The tests I insist on are one that the plugin is the registered instance, one that a
failed run is still recorded, one that no per-run state is left behind afterwards, and one that a
second agent nobody told the plugin about is still covered."
