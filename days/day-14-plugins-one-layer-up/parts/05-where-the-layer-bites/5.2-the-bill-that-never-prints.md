# 5.2 — The bill that never prints

## One-line answer

`after_run_callback` fires only when the request **succeeded**, so a meter built on it reports nothing
for failed runs — which still spent their quota — and leaks one dictionary entry each; the fix is to
report from `on_run_error_callback` as well.

---

## The story

A call to a helpline that drops after four minutes.

You dialled, you waited on hold, you explained the problem twice, and then the line went dead before
anything was resolved. From your point of view the call failed. Nothing was achieved. You will have to
call again.

Your balance does not agree. Those four minutes are gone. The network billed you for connection time,
not for outcomes, and there is no refund for a call that did not work — you were using the line the
whole time.

The uncomfortable version of this is not the money. It is that if you were keeping a note of what your
calls cost you, and you only wrote down the ones that ended properly, your note would say this month
was cheap. It would be a careful, honest note, kept diligently, and completely wrong — and wrong in
the direction that stops you asking questions.

---

## The idea in plain language

[4.2](../04-the-meter/4.2-the-bill-at-the-exit-door.md) built the bill at `after_run_callback`. That
hook has a property no documentation page mentions and the runner's own source comment states twice:

> *"This does NOT emit any event. Only runs on success."*

> *"Success path (also caller early-stop via GeneratorExit, which is not an Exception): run after_run
> and compaction."*

So the ledger you have is a ledger of successes. And a failed run is not a run that spent nothing — it
is very often a run that spent *more*, because it got some way through before it broke.

Two things go wrong at once, and they compound.

**The numbers are wrong, low, and plausible.** Your quota meter under-reports by exactly your failure
rate. A day with a 5% error rate reads 5% cheap. That is a small enough discrepancy to never be
noticed and a large enough one to matter when you are near a daily limit — and it is wrong in the
direction that makes the dashboard look healthy, which is the direction nobody investigates.

**The per-run state leaks.** [4.3](../04-the-meter/4.3-one-instance-every-run.md) fixed accumulation
by keying state on `invocation_id` and popping it in `after_run_callback`. On a failed run the `pop`
never happens, so the entry stays forever. The leak rate is your failure rate, and it grows fastest
during an incident — precisely when the process is already under stress.

The hook that closes both is `on_run_error_callback`, from
[3.2](../03-the-rule-at-this-layer/3.2-the-two-hooks-that-cannot-stop-anything.md). It is
notification-only, which is exactly right here: reporting a bill and cleaning up a dictionary are both
things you want done on the way out, and neither should be able to suppress the failure.

Note that this is one of the two hooks `adk.dev/plugins/` does not document
([2.1](../02-the-fourteen-doors/2.1-fourteen-doors-six-you-already-know.md)). **The gap in the
documented hook is closed by an undocumented hook**, which is as clear an argument as this day has for
reading the installed package rather than the page.

---

## Why Sutra needs it

**Because quota is spent whether or not the run succeeds.** Addendum 02 makes RPM and RPD the
currency. A provider counts the request when it is made; it does not refund it because your agent
raised afterwards. A meter that only counts successes is measuring a different quantity from the one
the rate limiter is measuring.

**Because Day 72's failures are the interesting ones.** The backoff-and-escalate ladder exists for
runs that hit 429. Those are exactly the runs `after_run_callback` never sees, so a naive meter is
blind in the region Day 72 is about.

**Because a leak that scales with the failure rate is the worst kind.** It is invisible in
development, invisible under normal load, and accelerates during an outage.

---

## The mechanism

Two meters, the same two runs: one that works and one that fails after spending.

```python
# lab/never_prints.py - the bill does not print for the runs that failed. Zero model calls.
import asyncio
import logging
from collections import Counter

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.plugins import BasePlugin
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types
from stateless import ReactiveModel

logging.disable(logging.CRITICAL)


def lookup_ticket(ticket_id: str) -> dict:
    """Look up a support ticket by its id."""
    return {"status": "ok", "ticket_id": ticket_id}


def search_kb(query: str) -> dict:
    """Search the knowledge base. Today it is down."""
    raise ConnectionError("search backend unreachable")


class HappyPathOnly(BasePlugin):
    """Reports at the exit door only. Leaks an entry per failed run."""

    def __init__(self) -> None:
        super().__init__(name="happy")
        self.runs: dict[str, Counter[str]] = {}

    async def before_model_callback(self, *, callback_context, llm_request):
        self.runs.setdefault(callback_context.invocation_id, Counter())["model"] += 1

    async def after_run_callback(self, *, invocation_context):
        bill = self.runs.pop(invocation_context.invocation_id, Counter())
        print(f"      happy : model={bill['model']}  (still open: {len(self.runs)})")


class Complete(BasePlugin):
    """Reports at both exits: success and failure."""

    def __init__(self) -> None:
        super().__init__(name="complete")
        self.runs: dict[str, Counter[str]] = {}

    async def before_model_callback(self, *, callback_context, llm_request):
        self.runs.setdefault(callback_context.invocation_id, Counter())["model"] += 1

    def _report(self, invocation_id: str, outcome: str) -> None:
        bill = self.runs.pop(invocation_id, Counter())
        print(f"      total : model={bill['model']} {outcome}  (still open: {len(self.runs)})")

    async def after_run_callback(self, *, invocation_context):
        self._report(invocation_context.invocation_id, "ok")

    async def on_run_error_callback(self, *, invocation_context, error):
        self._report(invocation_context.invocation_id, f"FAILED {type(error).__name__}")


async def drive(label: str, chain: list[str], plugins: list[BasePlugin]) -> None:
    print(f"  {label}")
    agent = LlmAgent(
        name="desk",
        model=ReactiveModel(model="scripted", chain=chain),
        instruction="x",
        tools=[lookup_ticket, search_kb],
    )
    app = App(name="sutra", root_agent=agent, plugins=plugins)
    runner = Runner(app=app, session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name=app.name, user_id="u")
    try:
        async for _ in runner.run_async(
            user_id="u",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text="hi")]),
        ):
            pass
        print("      the run finished")
    except Exception as error:
        print(f"      the run raised {type(error).__name__}")


async def main() -> None:
    happy, complete = HappyPathOnly(), Complete()
    await drive("a. a run that succeeds", ["lookup_ticket"], [happy, complete])
    await drive(
        "b. a run that fails after spending",
        ["lookup_ticket", "search_kb"],
        [happy, complete],
    )
    print(
        f"\n  leaked entries after two runs: happy={len(happy.runs)} complete={len(complete.runs)}"
    )


asyncio.run(main())
```

**Line by line:**

- `happy, complete = HappyPathOnly(), Complete()` constructed **once** and passed to both runs — the
  realistic shape from [4.3](../04-the-meter/4.3-one-instance-every-run.md), and the only way the
  final leak count means anything. Fresh instances per run would reset the evidence.
- `search_kb` raising `ConnectionError` rather than returning an error dict — trap #4 again. A tool
  that catches its own failure produces a *successful* run with a bad result, and this part is about
  runs that genuinely fail.
- `chain=["lookup_ticket", "search_kb"]` in case **b** — the failing tool is the **second** one, so the
  run spends a model call, a successful tool call, and another model call *before* it dies. That is
  the whole point: the failure is not free, and a failure at the very first step would have hidden it.
- `Complete._report` as a plain method called from both hooks — one implementation, two doors. Writing
  the body twice is how the two reports drift apart, and drift here means the failure path is the one
  that silently stops matching.
- `self.runs.pop(invocation_id, Counter())` in `_report` — the same read-and-remove from
  [4.3](../04-the-meter/4.3-one-instance-every-run.md), now reachable from both exits, which is what
  actually closes the leak.
- `f"FAILED {type(error).__name__}"` — the exception's class name, not `str(error)`. A message may
  contain a ticket id, a query or a URL; a class name is safe to put in a log line that will be
  aggregated. Yesterday's
  [13/3.2](../../../day-13-callbacks-four-doors/parts/03-the-tool-doors/3.2-refusing-a-tool-call-honestly.md)
  made the same argument about not echoing a query into a refusal.
- `logging.disable(logging.CRITICAL)` at the top, for the same teaching reason as
  [3.2](../03-the-rule-at-this-layer/3.2-the-two-hooks-that-cannot-stop-anything.md): ADK logs the
  full traceback of the failing run and this script is about six short lines.
- The final `print` reads `len(...)` on both dictionaries **after** both runs. That number is the
  leak, stated as a number.

The output:

```text
  a. a run that succeeds
      happy : model=2  (still open: 0)
      total : model=2 ok  (still open: 0)
      the run finished
  b. a run that fails after spending
      total : model=2 FAILED ConnectionError  (still open: 0)
      the run raised ConnectionError

  leaked entries after two runs: happy=1 complete=0
```

Case **b** has **no `happy :` line at all.** The run spent two model calls and the happy-path meter
said nothing — not zero, not an error, nothing. If you were adding up that column, this request would
be absent from your day.

`complete` reported `model=2 FAILED ConnectionError`, which is the true and useful record: this
request cost two model calls and did not work.

And the last line is the leak, counted: `happy=1`. One failed run, one entry that will never be
removed. Multiply by a real failure rate over a real uptime.

Verified against the installed `google-adk` 2.7.1 on 2026-08-29, by running this script and by reading
`runners.py`, where `run_after_run_callback` sits inside `if run_error is None:` in the `finally`
block, and `_notify_run_error` is called on every exception path.

---

## When it breaks

**💥 The silence.** There is no error and no partial output. The absence of a line is the entire
symptom, and absence is the hardest thing to notice in a log.

**💥 The leak, found much later.**

```text
MemoryError
```

Or, more usually, no error at all — just a container restarting on its memory limit every few days,
which gets attributed to "the framework" because the plugin holding a dictionary of integers is the
last place anyone looks.

**💥 You added `on_run_error_callback` and now report twice.** Not in ADK — the two hooks are mutually
exclusive per run, as case **a** and case **b** demonstrate between them. But if you also try to clean
up in `close`, or in a `finally` around your own runner call, you will double-count. The `pop` makes
this safe by construction: the second reader finds nothing and reports zero, which is a wrong row
rather than a crash. If a double row would be worse than a missing one, check membership first.

## In production

**What a professional writes instead of the teaching version** treats "the run ended" as one event
with an outcome field, and refuses to let the two paths drift:

```python
async def after_run_callback(self, *, invocation_context) -> None:
    self._close_run(invocation_context.invocation_id, outcome="ok", error=None)


async def on_run_error_callback(self, *, invocation_context, error) -> None:
    self._close_run(invocation_context.invocation_id, outcome="error", error=error)
```

**Line by line:**

- Both hooks are one line and delegate to the same `_close_run`. The only difference between them is
  data, which means a change to what a ledger row contains cannot land on one path and miss the other.
- `outcome="ok"` / `"error"` as an explicit field rather than a missing row — a query for "requests
  that failed" is then a filter, not an anti-join against a different table. Absence is not a value
  you can aggregate.
- `error=error` passed through so `_close_run` can record the type. It takes the exception object
  rather than a string so the decision about what is safe to log lives in one place.
- Both annotated `-> None`, both with no `return` — notification-only hooks discard returns anyway
  ([3.2](../03-the-rule-at-this-layer/3.2-the-two-hooks-that-cannot-stop-anything.md)), and the
  annotation stops a future reader from expecting otherwise.

There is one gap this still does not close, and it is worth knowing you have it: a process killed
mid-request — an out-of-memory kill, a container eviction, a deploy — runs neither hook. Nothing
in-process can close that gap. If the ledger must survive that, the row is opened at
`before_run_callback` and written somewhere durable, and unclosed rows are reconciled by age.

**What degrades at scale** is that the failure path is the busy path during an incident. Whatever
`_close_run` does — a log write, a metric increment — happens for every request when everything is
failing, at the moment the process is least able to afford it. Keep it cheap and local; buffer, do not
flush.

**The failure that only shows with real traffic** is a quota meter that reads comfortably under the
limit while the provider is returning 429s. Every 429 fails a run, every failed run is missing from
the ledger, so the ledger's confidence increases exactly as the real headroom disappears. You will
trust the meter and look for the problem somewhere else.

**The review comment a senior engineer leaves:** *"`after_run_callback` is success-only. As written
this meter under-reports by our error rate and leaks a map entry per failure. Add
`on_run_error_callback` calling the same close path, with an outcome field."*

**The interview question:** *"Your per-request metrics look lower than the provider's numbers. Where
do you look?"* — "Whether the reporting path covers failures. In ADK, `after_run_callback` only fires
on success, so a meter built solely on it silently drops every failed run — and failed runs still made
their requests, so the provider counted them and I did not. It also leaks whatever per-run state I was
popping in that hook, at exactly my error rate. The fix is `on_run_error_callback` calling the same
close path with an outcome field, so 'ended' is one event with a result rather than a row that exists
or does not. The residual gap is a process killed mid-request, which no in-process hook can cover —
that needs a durable row opened at the start and reconciled by age."
