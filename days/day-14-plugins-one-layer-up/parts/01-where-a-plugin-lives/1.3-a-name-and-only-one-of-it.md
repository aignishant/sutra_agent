# 1.3 — A name, and only one of it

## One-line answer

Every plugin carries a required `name`, no two plugins in one application may share one, and the
check happens when the `Runner` is built rather than when the `App` is — so the error arrives one
line later than you expect.

---

## The story

A small clinic keeps its patient files in a rack behind the desk, one folder per person, labelled by
name.

Two patients called Anita Sharma register in the same month. Nobody notices, because nobody is
looking for a collision — they are just writing a label the way they always do. Now there are two
folders reading *Anita Sharma* and the receptionist picks whichever is nearer.

The prescriptions get mixed for six weeks. Nothing crashes. The system works exactly as designed; the
design just assumed the label picked out one person.

When they fix it, the fix is not "be careful". It is a rule at the point of filing: the rack will not
accept a second folder with a label that is already in it. You find out at the desk, in the first ten
seconds, instead of in a consulting room six weeks later.

---

## The idea in plain language

`BasePlugin.__init__` takes exactly one argument and it is required:

```text
def __init__(self, name: str)
```

The name is not a label for humans. Three things use it.

**Uniqueness.** ADK refuses to register two plugins with the same name in one application. This is the
clinic's rack rule: a collision is caught at the moment of filing rather than discovered later.

**Lookup.** `plugin_manager.get_plugin("quota_meter")` returns the registered instance by name. That
is how one part of a system reaches a plugin it did not construct — and it is how
[7.2](../07-in-production/7.2-testing-a-plugin-without-a-model.md)'s test gets hold of the meter to
assert on it.

**Errors and traces.** When a plugin raises, ADK puts the plugin's name in the message. You saw the
shape in [1.1](1.1-the-rule-nobody-has-to-remember.md): `Error in plugin 'sync' during
'before_model_callback' callback: ...`. With four plugins installed, that name is the difference
between a five-minute fix and an afternoon.

The detail worth knowing is **where** the uniqueness check runs. `App` does not check. It is a
Pydantic model with a plain `list[BasePlugin]` field, and it will hold two identically-named plugins
without complaint. The check lives in `PluginManager.register_plugin`, and the `PluginManager` is
built by the **`Runner`**. So the line that raises is not the line that made the mistake.

That gap is worth a sentence of its own, because it changes how you read the traceback: **the object
that accepted the bad value and the object that rejected it are different objects**, and only the
second one is in your stack trace.

---

## Why Sutra needs it

**Because the day after tomorrow Sutra has more than one plugin.** Today installs the run ledger. Day
84 adds `AutoTracingPlugin` (ADK-74), and Day 70 adds the quota router. Three plugins in one
application is where names start doing work.

**Because the failure lab needs a findable culprit.** [6.1](../06-failure-lab/6.1-the-rule-that-broke-an-agent-nobody-was-looking-at.md)
is about a block that comes from infrastructure an agent cannot see. The single thing that makes that
debuggable is that the refusal carries the plugin's name, and the plugin has one because ADK insisted.

**Because a name is how a test reaches into a running application.** You cannot assert on a plugin you
cannot get hold of, and constructing a second instance to inspect tells you nothing about the one that
actually ran.

## The mechanism

```python
# lab/names.py - the name is required, unique, and checked by the Runner. Zero model calls.
from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.plugins import BasePlugin
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from scripted import ScriptedModel, text


class Meter(BasePlugin):
    """Two instances of this, both called 'meter', is the collision."""

    def __init__(self, name: str = "meter") -> None:
        super().__init__(name=name)


def make_agent() -> LlmAgent:
    return LlmAgent(
        name="desk",
        model=ScriptedModel(model="scripted", replies=[[text("done")]]),
        instruction="x",
    )


print("a. the App accepts two plugins with the same name")
app = App(name="sutra", root_agent=make_agent(), plugins=[Meter(), Meter()])
print("   App built. plugins:", [p.name for p in app.plugins])

print("b. the Runner is what rejects them")
try:
    Runner(app=app, session_service=InMemorySessionService())
except ValueError as error:
    print(f"   ValueError: {error}")

print("c. two names, no collision - and lookup by name")
ok = App(name="sutra", root_agent=make_agent(), plugins=[Meter("meter"), Meter("tracer")])
runner = Runner(app=ok, session_service=InMemorySessionService())
print("   registered:", [p.name for p in runner.plugin_manager.plugins])
print("   get_plugin('tracer') ->", runner.plugin_manager.get_plugin("tracer"))
print("   get_plugin('absent') ->", runner.plugin_manager.get_plugin("absent"))
```

**Line by line:**

- `def __init__(self, name: str = "meter")` — the plugin takes its own name as a parameter with a
  default. That is the production shape rather than a hard-coded string: it lets one plugin class be
  installed twice under two names, which is how you would run two quota meters against two providers.
- `App(..., plugins=[Meter(), Meter()])` followed by a successful `print` — case **a** exists to prove
  a negative. The `App` was built. No exception. Both plugins are in the list, both called `meter`.
- `except ValueError as error` around the `Runner` construction — case **b**. The `Runner` builds a
  `PluginManager`, which calls `register_plugin` once per plugin, and the second call finds the name
  already taken. Catching `ValueError` specifically rather than `Exception` is the house rule from
  `CLAUDE.md`: catch the exception you expect, let anything else surface (Principle 10).
- `runner.plugin_manager.plugins` — the registered list, in registration order. That order is the
  order they run in, which matters the moment two plugins can both answer at the same door
  ([3.1](../03-the-rule-at-this-layer/3.1-is-not-none-and-this-time-it-means-it.md)).
- `get_plugin("absent")` is included deliberately: it returns `None` rather than raising, so a lookup
  for a plugin that was never installed is silent. If a test asserts on `get_plugin(...)` without
  checking for `None` first, a typo in the name passes as "nothing to assert".

The output:

```text
a. the App accepts two plugins with the same name
   App built. plugins: ['meter', 'meter']
b. the Runner is what rejects them
   ValueError: Plugin with name 'meter' already registered.
c. two names, no collision - and lookup by name
   registered: ['meter', 'tracer']
   get_plugin('tracer') -> <__main__.Meter object at 0x000001C2C1FF7B90>
   get_plugin('absent') -> None
```

Verified against the installed `google-adk` 2.7.1 — `PluginManager.register_plugin` raises
`ValueError` on a duplicate name and `get_plugin` is a `next(..., None)` over the list — on
2026-08-29. The object address in your output will differ; that is the point of an address.

## When it breaks

**💥 The duplicate.**

```text
ValueError: Plugin with name 'meter' already registered.
```

Almost always caused by installing the same plugin twice from two places — a `build_app()` that adds
the ledger and a caller that adds it again "to be sure". The fix is one place that assembles the
application, which is [1.2](1.2-the-app-is-what-plugins-belong-to.md)'s production section.

**💥 The missing name.**

```text
TypeError: BasePlugin.__init__() missing 1 required positional argument: 'name'
```

`super().__init__()` with empty parentheses. There is no default.

**💥 The typo in a lookup, which is not an error at all.**

```python
meter = runner.plugin_manager.get_plugin("quota-meter")   # registered as "quota_meter"
meter.report()
```

```text
AttributeError: 'NoneType' object has no attribute 'report'
```

The message names `NoneType` and not the plugin, because the lookup already succeeded at returning
nothing. When you see `'NoneType' object has no attribute` after a `get_plugin`, check the spelling
before you check the plugin.

## In production

**What a professional writes instead of the teaching version** puts the name on the class as a
constant and defaults to it, so the string exists once:

```python
class RunLedger(BasePlugin):
    NAME = "run_ledger"

    def __init__(self, name: str = NAME) -> None:
        super().__init__(name=name)
```

**Line by line:**

- `NAME = "run_ledger"` as a class attribute — tests and lookups say `RunLedger.NAME` instead of
  retyping a string, so a rename is one edit and a typo is a `NameError` at import rather than a
  `None` at runtime.
- `def __init__(self, name: str = NAME)` — the default is the constant, and the parameter is still
  there, so the same class can be installed twice under different names when you genuinely want two
  instances.
- The bare `NAME` inside the class body works because the default is evaluated while the class body
  is still the enclosing namespace. Written as `RunLedger.NAME` it would fail — the class does not
  exist yet at that moment.

**What degrades at scale** is name collision across teams. Once plugins come from more than one
codebase — yours, a shared internal library, ADK's own `LoggingPlugin` — an unqualified name like
`"logging"` or `"metrics"` is a landmine, and the explosion happens at startup in whichever
environment happens to install both. Teams that hit this once move to prefixed names:
`"sutra.run_ledger"`.

**The failure that only shows with real traffic** is the plugin installed twice with two names by
accident — `meter` and `quota_meter`, from a half-finished rename. No error, because the names differ.
Every model call is counted twice, the quota budget appears to be exhausted at half the real traffic,
and the router starts shedding load that was never there.

**The review comment a senior engineer leaves:** *"This name is a bare string in three files. Make it
a class constant and have the tests reference that, or the next rename half-lands."*

**The interview question:** *"What is a plugin's name for?"* — "It has to be unique within the
application, so it is the thing that makes a double-install fail loudly instead of double-counting.
It is the key for looking a plugin up on the plugin manager, which is how a test gets hold of the
instance that actually ran rather than a fresh one. And it is what ADK puts in the error message when
a plugin raises, which with several plugins installed is the difference between knowing which one
broke and bisecting. The detail that catches people is that the uniqueness check is in the runner's
plugin manager, not on the `App` — so you can build an `App` with two identically-named plugins and
the failure surfaces one line later."
