# 1.1 — The rule nobody has to remember

## One-line answer

A **plugin** is a rule you attach to the whole application instead of to one agent, so it applies to
every agent in it — including the agents nobody has written yet.

---

## The story

A tailor's shop with three sewing machines.

The owner has a rule: write the customer's name and the date on a slip, and pin the slip to the cloth
before you start cutting. Without it, two half-finished shirts on the same table are the same shirt.

For a while she tells each tailor the rule when they join. Three tailors, three tellings. It works.

Then she hires a fourth for the festival season. It is a busy week, she is at the front counter, and
nobody tells him. He is a good tailor. He cuts beautifully. He just does not pin slips, because
nobody said to, and there is nothing in the shop that would tell him.

The mix-up happens eleven days later and costs her two customers.

What she does after that is not "remember to tell people". She nails a box of slips and a pen to the
wall beside the cutting table, at the only place anyone can pick up cloth, and paints the rule on the
wall above it. Now the rule is not carried by whoever remembered to say it. It is part of the room.
The fifth tailor gets it on their first morning without a conversation, and so does the tenth.

The rule did not change. Where it lives changed, and that is the whole difference between a rule
people follow and a rule that holds.

## The idea in plain language

Yesterday you attached functions to **one agent**.

[Day 13](../../../day-13-callbacks-four-doors/LESSON.md) gave you six places where ADK calls a
function of yours — before and after the model, before and after a tool, and one each for when those
raise. You wrote `before_tool_callback=[audit_tool_calls, block_forbidden_queries]` on
`sutra/desk/agent.py`, and from then on the desk audited its own tool calls.

That is a **callback**: a function attached to one agent, which is the tailor being told the rule.

A **plugin** is the same idea attached one level higher. It is a class — a subclass of `BasePlugin` —
whose methods are hooks with the same names, and you register it on the **application** rather than
on an agent. ADK's own docstring draws the line in one sentence:

> *"While agent callbacks apply to a particular agent, plugins applies globally to all agents added
> in the runner."*

Three words define the difference, and it is worth being slow about each one.

**Scope.** A callback covers one agent. A plugin covers every agent in the application — the ones you
wrote today, and the ones somebody adds next quarter without reading your file.

**Precedence.** At every shared door, ADK runs the plugins *first*. If a plugin returns a value, the
agent's callbacks are not run at all. You measured this yesterday in
[13/4.2](../../../day-13-callbacks-four-doors/parts/04-where-the-rule-bites/4.2-the-plugin-goes-first.md):
`2 agent before_tool_callback` was simply absent from the output. Not overruled. Not consulted. Never
executed.

**Reach.** A plugin has doors an agent does not have at all — the beginning and the end of a whole
request, and every event on its way to the caller. No single agent can see those, because a request
may pass through several agents and none of them is the request. That is section 2.

A term from yesterday, restated so you do not have to go back for it: a **door** is a fixed point in
ADK's execution where the framework will call your code if you have supplied any, and a **hook** is
the named slot you supply it in. The word *callback* means the function you hang on an agent's hook.
The word *plugin* means the object you hang on the application's hooks. Same doors, two layers.

The one sentence to keep: **a callback is what one agent does; a plugin is what the system does.**

---

## Why Sutra needs it

**Because Sutra is about to stop being one agent.** Right now the desk is a single `LlmAgent`. Phase 8
(Days 53–59) builds a graph of them — a researcher, a writer, a critic — and every one of them will
call a model and most will call tools. A credential filter attached to one of those is a filter with a
hole in it, and the hole is shaped exactly like whichever agent was added last.

**Because the thing today builds cannot be built as a callback at all.** The question *"what did this
whole request cost?"* has no answer inside any single agent, because no single agent is the request.
Section 4 builds the meter that answers it, and section 4 is only possible at this layer.

**Because Day 70 needs the meter before it can route.** Addendum 02 replaces the plan's dollar budget
with a **quota** budget: requests-per-minute and requests-per-day, per provider. The Quota-Router on
Day 70 sends each call to whichever provider still has headroom — and it cannot do that until
something is counting. Today you build the counter. Day 70 reads it.

**Because Day 84 turns on tracing with one line.** `AutoTracingPlugin` (ADK-74, Addendum 01 Part 4)
instruments every node, tool call and model call in the application for OpenTelemetry. It is one
plugin because it has to be: a trace with a gap in it is worse than no trace, and a per-agent
instrument gaps the moment somebody adds an agent.

## The paper behind it

> **Aspect-oriented programming** · `doi:10.1007/BFb0053381` · 1997 ·
> ECOOP'97 — Object-Oriented Programming, Lecture Notes in Computer Science ·
> <https://doi.org/10.1007/BFb0053381>

It named the problem this whole day is about: some concerns — logging, auditing, timing, access
control — **cut across** the units a program is decomposed into, so no matter how you organise the
code they end up scattered through every module and tangled with the actual work. Its answer was to
write such a concern once, in a module of its own, and have a separate mechanism apply it at named
points in the program.

The paper is taught in full at
[papers/01-aspect-oriented-programming.md](../../papers/01-aspect-oriented-programming.md) — read it
**after** the parts, not before. You will recognise more of it having built the mechanism first.

## The mechanism

The smallest complete plugin, and the one line that installs it.

```python
# lab/hello_plugin.py - the smallest plugin that does anything. Zero model calls.
import asyncio

from google.adk.agents import LlmAgent
from google.adk.apps import App
from google.adk.plugins import BasePlugin
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types
from scripted import ScriptedModel, text


class Announce(BasePlugin):
    """Says so, every time any agent in the application calls a model."""

    def __init__(self) -> None:
        super().__init__(name="announce")

    async def before_model_callback(self, *, callback_context, llm_request):
        print(f"      the plugin saw a model call from agent {callback_context.agent_name!r}")


def make_agent(name: str) -> LlmAgent:
    """Two agents, neither of which mentions the plugin anywhere."""
    return LlmAgent(
        name=name,
        model=ScriptedModel(model="scripted", replies=[[text("done")]]),
        instruction="x",
    )


async def drive(agent: LlmAgent) -> None:
    app = App(name="sutra", root_agent=agent, plugins=[Announce()])
    runner = Runner(app=app, session_service=InMemorySessionService())
    session = await runner.session_service.create_session(app_name=app.name, user_id="u")
    async for _ in runner.run_async(
        user_id="u",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="hi")]),
    ):
        pass


async def main() -> None:
    print("  a. the desk")
    await drive(make_agent("desk"))
    print("  b. an agent written later, by somebody else")
    await drive(make_agent("faq"))


asyncio.run(main())
```

**Line by line:**

- `class Announce(BasePlugin)` — a plugin is a **class**, not a function. That is the first visible
  difference from yesterday: a callback is a plain function you pass by name, a plugin is an object
  you construct. The reason is state — a plugin usually has something to remember between doors, and
  section 4's meter is exactly that.
- `def __init__(self) -> None: super().__init__(name="announce")` — `BasePlugin.__init__` takes one
  required argument, `name`, and forgetting the `super()` call leaves the object without one. The name
  is not decoration; [1.3](1.3-a-name-and-only-one-of-it.md) is about what it is for.
- `async def before_model_callback(self, *, callback_context, llm_request)` — three differences from
  the agent-level version in one line. It is a **method**, so it takes `self`. It is **`async`**,
  always, even when it does nothing awaitable. And the `*` makes every following argument
  **keyword-only**, which matters because ADK calls these by keyword — yesterday's
  [13/1.2](../../../day-13-callbacks-four-doors/parts/01-the-four-doors/1.2-the-names-are-the-contract.md)
  rule, still in force one layer up. [2.3](../02-the-fourteen-doors/2.3-the-names-moved.md) is the
  list of names that changed between the two layers.
- No `return` statement — so the method returns `None`, so the model call proceeds. Yesterday's one
  rule survives the move up: `None` carries on. What "anything else" means at this layer is
  [3.1](../03-the-rule-at-this-layer/3.1-is-not-none-and-this-time-it-means-it.md), and it is not
  quite the rule you learned yesterday.
- `App(name="sutra", root_agent=agent, plugins=[Announce()])` — **the whole installation**. The
  plugin is named once, in one place, and it is not mentioned anywhere in `make_agent`. That absence
  is the entire point of the day: look at the agent, and there is nothing to see.
- `Runner(app=app, session_service=InMemorySessionService())` — the explicit runner. You cannot use
  `InMemoryRunner` here, because it builds its own `App` internally and there would be nowhere to hang
  the plugin. [1.2](1.2-the-app-is-what-plugins-belong-to.md) is that object.
- `make_agent(name)` builds a **new agent each time** rather than reusing one, so case **b** is
  genuinely a second agent and not the same object twice. The plugin instance is also new each time
  here, which keeps this part simple; [4.3](../04-the-meter/4.3-one-instance-every-run.md) is what
  happens when it is not.
- `async for _ in runner.run_async(...)` with a discarded loop variable — the events are not the
  subject of this script. Draining the generator is what makes the run happen.

Run it:

```text
  a. the desk
      the plugin saw a model call from agent 'desk'
  b. an agent written later, by somebody else
      the plugin saw a model call from agent 'faq'
```

Two agents. One rule, written once. Neither agent file contains the word `announce`.

Verified against the installed `google-adk` 2.7.1 and `adk.dev/plugins/` on 2026-08-29.

## When it breaks

**💥 You forgot the name.**

```text
TypeError: BasePlugin.__init__() missing 1 required positional argument: 'name'
```

You wrote `super().__init__()` with no arguments, or left out `__init__` and called `Announce()`.
`name` is required and has no default. One argument fixes it.

**💥 You used `InMemoryRunner` and the plugin never fired.** No error at all — the run works perfectly
and your plugin is simply never called, because `InMemoryRunner` constructs its own `App` from the
agent you gave it and your `App` is not the one being run. This is the quietest mistake in the day and
it is [1.2](1.2-the-app-is-what-plugins-belong-to.md)'s subject.

**💥 You wrote the method without `async`.**

```text
RuntimeError: Error in plugin 'sync' during 'before_model_callback' callback: object NoneType can't
be used in 'await' expression
```

`PluginManager` awaits the result of every hook. A plain `def` returns `None` rather than something
awaitable, and the await fails. Every plugin hook is `async def`, with no exceptions.

Read that message carefully, because you will meet its shape again all day. The `RuntimeError` is a
**wrapper** ADK puts around anything your plugin raises, and the useful half is at the end after the
colon. The original `TypeError` is still there as the exception's `__cause__`, which is what the
`During handling of the above exception` block in the traceback is showing you.
[3.3](../03-the-rule-at-this-layer/3.3-a-plugin-that-raises-takes-the-run-with-it.md) is that
wrapper, on purpose.

## In production

**What a professional writes instead of the teaching version** is a plugin that takes its
configuration in `__init__` rather than reading the environment inside a hook. A hook runs on every
model call of every agent; a hook that calls `os.environ.get` or reads a file is doing that work
thousands of times for an answer that was fixed at startup. Construct expensive things once, in
`__init__`, and let the hooks be cheap.

**What degrades at scale** is the plugin that logs unconditionally. `before_model_callback` fires once
per model call, and a run with two tool calls makes three model calls — so an application serving
real traffic multiplies your one `print` by every model call of every agent. On Day 13 you learned
that a callback covers one agent; the corollary here is that a plugin's blast radius for *volume* is
the whole application, not just its blast radius for *policy*.

**The failure that only shows with real traffic** is the plugin that is fine on one agent and wrong on
another. You write a hook that reads `llm_request.contents[0]` because the desk always has a user
message first. Six months later somebody adds an agent that is invoked with a tool result as its
first content, and your plugin raises `IndexError` on an agent you have never opened. The plugin
applied to it. That was the point, and it is also the risk.

**The review comment a senior engineer leaves:** *"This is a class with one method and no state — why
is it a plugin and not a callback on the agent that needs it? Put the mechanism where the policy's
scope is, and write down the scope you decided."*

**The interview question:** *"When would you write a plugin instead of an agent callback?"* The answer
that shows you have wired both: "When the rule has to hold for agents that do not exist yet. A
callback is attached to one agent, so adding it to a new agent is something a person has to remember,
and the failure mode is silent — the new agent just is not covered and nothing tells you. A plugin is
registered on the application, so coverage is a property of the system rather than of somebody's
memory. The test I use is one question: if somebody adds an agent next quarter and forgets this rule,
is that a bug or a choice? If it is a bug, it belongs in a plugin. The other reason is reach — plugins
have run-level hooks that no agent has, so anything that has to know about the whole request, like
what it cost, can only live there."
