# 1.3 — What the judge is shown

## One-line answer

The judge receives 5,029 characters of which the actual case is three lines — question, answer,
reference — inside a template that tells it the agent *"is going to call an API"*, so a rater grading
Sutra's plain-text desk is being briefed for a different job than the one it is doing.

## The story

The complaint form at a service centre has one box, three lines high, headed *"Describe the issue."*

You have been having trouble for six weeks. It started after the last service, it is worse when the
engine is cold, somebody already looked at it once and changed a sensor, and there is a receipt for
that. You write in the box: *"Noise from engine when cold. Was serviced 6 wks ago."*

That is what the person at the workshop will read. Not the six weeks, not the previous visit, not the
sensor, not the receipt — those exist, they are true, and there is nowhere on the form for them.

The form is not badly designed. It was designed for the common case, which is a scratch or a flat
battery, and for that it is exactly right. What it cannot do is tell you when it is the wrong form,
because a filled-in form looks complete.

## The idea in plain language

Day 80 part 2.2 established a rule that applies to every judged metric: **the rater does not receive
your case, it receives a prompt the evaluator wrote**. That part measured a rubric metric losing four
tool calls in the assembly. This is the same discipline applied to `final_response_match_v2`, and what
it finds is different and worth knowing before you use the metric.

The v2 prompt has three parts and only the third is yours:

- **A long fixed template.** A job description, instructions about hedging and rounding and tables,
  and a required output format. It is most of the prompt.
- **A worked framing.** The template opens: *"You are an expert rater for an AI agent. The AI agent is
  going to call an API to answer the user query and generate API tool use code based for the choice of
  the API and API arguments."* It goes on to say the ideal response is *"a function call that fulfills
  user query, or a natural language response [that] hedges or asks users for further clarification."*
- **The case.** Three labelled values at the end: the user prompt, the agent response, the reference
  response.

Two consequences, and the second is the one that costs you.

**Only three things about your case reach the rater.** Not the conversation history, not the tool
calls, not the session state. `final_response_match_v2` is a **final-answer** metric and its name says
so; if a claim depends on anything else, this is the wrong metric and Day 80's rubric is the right
one.

**The framing may not match your agent.** Sutra's desk answers in prose. The template briefs the rater
for an agent that emits function calls and Python. That framing is not wrong for the systems it was
written for, and it is a mismatch here, and the mismatch is invisible: the rater will answer, fluently,
having been told it is looking at something it is not.

There is one field that changes what is included, and it is easy to miss.
`LlmAsAJudgeCriterion.include_intermediate_responses_in_final` — on the installed
`google-adk==2.7.1` — controls whether intermediate agent responses are folded into the text that is
compared. Left at its default, they are not.

## Why Sutra needs it

Because a metric's blind spots are only knowable by reading its prompt, and this is the metric Day 83's
gate leans on for the question *"did the desk answer correctly?"*.

It also settles a question that will otherwise be argued about: **which metric answers which claim.**
Day 79's `tool_trajectory_avg_score` is about the path. Day 80's rubric is about the whole
conversation. This one is about one final answer against one reference, and nothing else is available
to it. Writing that down now prevents somebody trying to express *"escalated before any external
write"* as a v2 case in three weeks.

## The mechanism

The prompt is built by the evaluator from three values. From
`google.adk.evaluation.final_response_match_v2` on 2.7.1:

```python
    reference = get_text_from_content(
        expected_invocation,
        include_intermediate_responses_in_final=include_intermediate,
    )
    response = get_text_from_content(
        actual_invocation,
        include_intermediate_responses_in_final=include_intermediate,
    )
    user_prompt = get_text_from_content(expected_invocation.user_content)
    return self._auto_rater_prompt_template.format(
        prompt=user_prompt,
        response=response or "",
        golden_response=reference or "",
    )
```

**Line by line:**

- Three values go into the template: `prompt`, `response`, `golden_response`. That is the complete
  list of what your case contributes. Everything else in the 5,029 characters is fixed.
- `user_prompt` is taken from the **expected** invocation, not the actual one. On a well-formed case
  they are the same question; on a case where they differ, the rater is shown the reference's question
  and the actual's answer, which is a subtle way to grade the wrong thing.
- `include_intermediate_responses_in_final` threads through to both. Set it on the criterion and any
  intermediate agent text becomes part of what is compared — which is occasionally what you want and
  is off by default.
- `response or ""` and `reference or ""` convert a missing answer to an empty string rather than
  letting `None` reach `str.format`. An empty response is graded, not skipped, and a rater shown an
  empty agent response will usually say invalid — which is the right answer for the wrong reason.

Read the prompt the evaluator actually built:

```bash
cd days/day-81-llm-as-judge/lab
PYTHONIOENCODING=utf-8 uv run python -c "
import asyncio, _judge
from _cases import INVALID, invocation
from bias import build
ev = build()
_judge.script(_judge.always('valid'))
a = INVALID[0]
asyncio.run(ev.evaluate_invocations(
    actual_invocations=[invocation(a.said, a.question)],
    expected_invocations=[invocation(a.reference, a.question)]))
p = _judge.prompts[0]
print('length:', len(p))
print(p[-420:])"
```

**Line by line:**

- `PYTHONIOENCODING=utf-8` because the template contains a `→` and Windows' default console codepage
  raises `UnicodeEncodeError: 'charmap' codec can't encode character '→'` on it. That is a real
  thing you will hit, and it is a property of the terminal rather than of the metric.
- `_judge.script(_judge.always("valid"))` installs a rater that always says valid — the answer does
  not matter here, because the prompt is recorded before the answer is produced.
- `_judge.prompts[0]` is the recording. `_judge.py` appends every prompt it is handed, which is the
  only reason the prompt is inspectable at all.
- `p[-420:]` prints the tail, because that is where the case is. The first 4,600 characters are the
  same on every call.

Measured on 2026-09-06:

```text
length: 5029
ast two decimal places (e.g., 0.798 → 0.80 is acceptable,  but 0.7 is not).

Below are the inputs:
{
  "User prompt": how old is 4740?,
  "Agent response": 4740 has not been open eleven days.,
  "Reference response": Eleven days.,
}

The answer should be a json alone which follows the json structure below:
{
  "reasoning": [reasoning],
  "is_the_agent_response_valid": [valid or invalid],
}
Answer with assertiveness:
```

**Five thousand and twenty-nine characters, of which the case is three.** Everything the rater knows
about this particular grading is in those three lines, and the ratio is worth carrying: over ninety
per cent of what the judge reads is the same on every call.

Two details in that block are worth pausing on.

The values are **not quoted or escaped** — `"User prompt": how old is 4740?,` is not valid JSON, and
an agent answer containing a `}` or a newline will produce a block that reads oddly to the rater.
It works because a language model is forgiving about this, and it is a thing to know when an answer
contains code.

And the last line is `Answer with assertiveness:`. The template asks the rater to be decisive. That is
a reasonable instruction for a metric that wants a clean label, and it is also an instruction that
discourages exactly the hedging that would have told you the case was borderline — the hedge that,
per part [1.1](1.1-a-judge-is-a-model-with-a-job.md)'s label table, would have been recorded as
`invalid` anyway.

And the framing, from the top of the same template:

```text
You are an expert rater for an AI agent. The AI agent is going to call an API to answer the user
query and generate API tool use code based for the choice of the API and API arguments.
```

Sutra's desk does call tools — but this metric is not shown any of them, and the answers it grades
are plain sentences about ticket ages. The rater is being told to expect function calls and Python
that it will never see.

## When it breaks

The break has no error and it looks like a metric that is slightly too harsh, or slightly too kind,
in a way nobody can pin down.

Concretely, three shapes:

**A claim that needs the conversation.** Somebody writes a v2 case whose reference answer is
*"asked for approval before refunding"*. The rater sees one answer and one reference and grades the
sentence, not the behaviour. It will return a confident label about something it cannot see. Day 80's
rubric metric is the one that can.

**An answer containing a brace or a newline.** The interpolation is unescaped, so the input block
stops looking like the structure the template promised. The rater still answers.

**A reference that is a fragment.** `"Eleven days."` is a fine reference for `"4740 has been open
eleven days."` and a strange one for a two-paragraph answer that is also correct. The template
anticipates this — it tells the rater to *"be flexible to allow the agent response to contain more
information than the reference response"* — and how flexible is a property of the rater, which is part
[2.2](../02-the-judge-has-biases/2.2-verbosity.md)'s subject.

The smallest fix is a habit rather than a patch, and it is the same one Day 80 part 2.2 asked for:
**print the prompt once, on one real case, and read it.** Ten minutes, before trusting any number this
metric produces.

## In production

**What a professional checks before adopting a judged metric.** The template, in full, from the
installed version — not from the documentation page. Templates are prose, prose gets edited between
releases, and a metric whose framing changed in a minor version will move your scores without moving
your code. Read it, and write down in one sentence what the rater was told it was looking at.

**What degrades at scale.** The fixed part of the prompt is a constant cost per call, and here it is
over ninety per cent of the tokens. At twenty-four cases and five samples that is 120 copies of the
same 4,600 characters. Requests are what Addendum 02 budgets in, so this is invisible in Sutra's
accounting and is the dominant term in anybody's token bill.

**The failure that only shows with real traffic.** Real answers are longer and more varied than
fixture answers, so the ratio inverts: the case grows from three lines to thirty, the fixed template
stays the same, and the rater's attention is now spread over material the template's worked examples
do not resemble at all. Whatever a judge's reliability is on a one-line answer, it is different on a
long one, and nothing in the score records which you had.

**The review comment a senior engineer leaves:** *"Paste the template into the ADR when we adopt this
metric, with the version it came from. When our scores shift after an ADK upgrade I want to be able to
diff the prompt rather than guess. And note that the framing talks about API calls — we should decide
whether that mismatch matters before somebody spends a week on it."*

**The interview question:** *"How do you know what your LLM judge is actually being asked?"* The answer
that shows experience says: read the assembled prompt from the installed library, on a real case —
and can then say what fraction of it was the case, because that ratio is the thing that surprises
people and the thing that decides how much the template's framing matters.
