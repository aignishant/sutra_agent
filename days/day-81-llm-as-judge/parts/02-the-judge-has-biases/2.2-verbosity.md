# 2.2 — Verbosity

## One-line answer

💥 Append one polite sentence to four answers a person marked **wrong** — changing no fact — and a
judge that rewards length turns **0 of 4** into **4 of 4** valid.

## The story

The viva at the end of a practical, and two students asked the same question.

The first one says: *"Sodium chloride."* Correct, complete, three syllables, done.

The second one says: *"So what I did first was I looked at the colour of the precipitate, and then I
considered the possibilities, and given the flame test result and the fact that it dissolved readily,
I would conclude that this is sodium chloride."* Also correct. Also, in substance, exactly the same
answer.

The examiner marks the second one higher. Not because of a rule — there is no rule that says longer is
better — but because the second answer *feels* like more work, and because it displays reasoning,
and because after forty vivas a short answer is hard to distinguish from a lucky guess.

The student who says "sodium chloride" learns this within a week and starts padding. Everyone does.
And a year later the examiner is marking a room full of people who have learned to sound thorough,
and the mark has quietly stopped being about chemistry.

## The idea in plain language

**Verbosity bias** is the tendency of a judge to prefer a longer answer over a shorter one that says
the same thing. The paper behind this day names it alongside position and self-enhancement.

It is worth separating two things that look alike, because only one of them is a bug.

- A longer answer that contains **more correct information** deserves to score higher, and the v2
  template says so explicitly: it tells the rater to *"be flexible to allow the agent response to
  contain more information than the reference response"*. That is a feature.
- A longer answer that contains **the same information plus padding** deserves the same score, and a
  judge that rewards it is measuring length.

The template's instruction is exactly what makes the second case possible. A rater told to tolerate
extra material has been told, in effect, that length is not evidence against an answer — and the step
from *not evidence against* to *evidence for* is one nobody instructs and every rater seems to take.

Two consequences, and the second is the one that ends up in a system.

**Your metric now has a lever on it that has nothing to do with correctness.** If the desk's answers
get longer for any reason — a prompt change, a new model, somebody adding "let me know if you need
anything else" — the judged score moves.

**The lever is one an agent will find.** This is the part that makes verbosity bias different from
the other two. Position and self-enhancement are properties of the judge that the thing being judged
cannot exploit. Verbosity is a property the *agent* can act on, and any process that optimises against
this metric — a prompt someone tunes until the score goes up, a model fine-tuned on judged
preferences — will discover that padding works. The student learns to pad.

## Why Sutra needs it

Because Day 77 spent an entire day arguing that Sutra's standup should be **short and ordered**, and
measured the case for it: attention-first delivered 3 of 3 urgent sentences where queue order delivered
0 of 2, and

made the point that shorter is not the goal but earlier is.

A judged metric with verbosity bias points the other way. If Sutra's answers are optimised against it,

supposed to be measuring correctness.

## The mechanism

The padding is one sentence, applied to the answer and nothing else. From `lab/_cases.py`:

```python
# A padded rewrite of each answer: the same facts, three times the words. Part 2.2 uses these.
PADDING = (
    " I checked the queue for you just now and this is what the record shows, so you can rely on"
    " it; do let me know if you would like me to look into anything else at all."
)


def padded(answer: Answer) -> str:
    return answer.said + PADDING
```

**Line by line:**

- The padding is **appended**, so the original answer survives verbatim. Every fact the person marked
  wrong is still there, in the same words, followed by more words. That is what makes this an ablation
  of length rather than of content.
- The sentence contains no claim about the ticket. *"I checked the queue for you just now"* is about
  the desk, not about the answer, and *"do let me know"* is about the future. Nothing in it could
  change a verdict on correctness.
- It is a module constant applied by one function, so the two arms of the experiment differ by exactly
  this string and nothing else.

And the judge, which reads the length out of the prompt the evaluator built:

```python
def response_in(prompt: str) -> str:
    """The agent's answer, pulled back out of the prompt the evaluator built.

    The v2 template ends with a block of inputs; the line wanted is the one labelled
    "Agent response". Read off google-adk==2.7.1's _FINAL_RESPONSE_MATCH_V2_PROMPT.
    """
    marker = '"Agent response": '
    start = prompt.find(marker)
    if start < 0:
        return ""
    return prompt[start + len(marker) :].split("\n")[0]


def by_length(prompt: str, _call: int) -> str:
    """A judge that calls an answer valid when it is long, and invalid when it is short."""
    return "valid" if len(response_in(prompt)) > LONG_ENOUGH else "invalid"
```

**Line by line:**

- `response_in` locates the answer inside the 5,029-character prompt from part
  [1.3](../01-the-judge-is-a-system/1.3-what-the-judge-is-shown.md), using the `"Agent response": `
  label the template writes. Measuring the length of the whole prompt instead would be dominated by
  the fixed template and would say "long" every time — which is exactly the bug the first draft of
  this lab had.
- `.split("\n")[0]` takes the rest of that line. The template puts each input on its own line, so
  this recovers the answer and stops at the newline before `"Reference response"`.
- `if start < 0: return ""` rather than raising. If the template changes and the marker moves, the
  judge sees an empty answer and calls everything invalid — a loud, wrong-in-one-direction failure
  rather than a silent one.
- `by_length` ignores the reference entirely. It is not comparing anything; it is measuring one
  string, which is the caricature that makes the effect legible.
- `LONG_ENOUGH = 120` characters, a module constant. The unpadded answers are all well under it and
  the padded ones all well over, so the arm is not sensitive to where exactly the line sits.

**Line by line:**

- `--verbosity` grades the four answers a person marked **invalid**, twice: as written, and padded.
  Same evaluator, same references, same judge.

Measured on 2026-09-06:

```text
metric: final_response_match_v2 (real), num_samples 1
judge: says valid when the response is longer than 120 characters

  arm                     valid  of   what a person says
  as written                  0   4   all 4 are wrong
  padded, same facts          4   4   all 4 are wrong

  padding turned 4 wrong answers into passes, changing no fact

```

**Zero to four.** The four answers are `x01` to `x04` from the fixture — *"4740 has **not** been open
eleven days"*, *"There are **twenty** open"*, *"Yes, I have refunded it"*, *"Nothing needs you today"*.
Every one of them is wrong in a way that matters, every one of them is still wrong after padding, and
all four now pass.

Note what the metric reports for the padded arm: `overall_score == 1.0`, `PASSED`, on all four. There
is nothing in the result about length. The only reason you can see the cause here is that the lab ran
the same four cases twice and printed both.

## When it breaks

There is no error and no drift in any input. The desk did not change. The references did not change.
One sentence of politeness was appended to four answers and a metric that is supposed to measure
correctness reversed itself.

The way this reaches a real system is worth spelling out, because it is not a bug anybody introduces:

```text
1. the judged score is on a dashboard
2. somebody tunes the desk's prompt to raise it
3. one of the things that raises it is answering at more length
4. the score goes up
5. Day 77's ordering property quietly degrades, and nothing measures that
```

Five steps, every one of them somebody doing their job, and the end state is a desk that scores better
and serves worse. It is the general hazard of optimising against a proxy, and this is the specific form
it takes here.

Two defences, and they are different in kind:

**Measure length alongside the score.** One number per case — the answer's length — reported next to
the verdict. If the mean answer length is climbing while the judged score climbs, those two facts
belong on the same page. It costs nothing and it is the cheapest thing on this list.

**Test for it directly.** The command above *is* the test: pad a set of known-wrong answers and require
the judged verdict not to move. Run it whenever the judge model changes, which is the moment the bias
can change without anything else changing.

## In production

**What a professional does about verbosity.** Puts a length constraint in the **rubric**, not in the
judge. A rubric line — Day 80's mechanism — saying *"the answer says only what was asked"* is a claim
a rater can check, and it pushes back against padding from inside the evaluation rather than hoping
the judge is immune. Trying to instruct a judge to ignore length works less well than asking it a
separate question about length.

**What degrades at scale.** Answers get longer over time in every deployed system — more edge cases
handled, more caveats added, more helpful closing sentences — so a verbosity-biased metric drifts
upwards on its own. A judged score that has improved by four points over six months, on a system
nobody changed the logic of, is a result to be suspicious of rather than pleased about.

**The failure that only shows with real traffic.** Real answers vary in length for legitimate reasons:
a complicated ticket needs more words than a simple one. So length is genuinely correlated with the
question, and a naive correction — penalising long answers — makes the metric wrong in the other
direction on exactly the hard cases. There is no clean fix, which is why the honest move is to
**measure** length rather than to try to neutralise it.

**The review comment a senior engineer leaves:** *"Log the character count of every graded answer next
to its score. And add the padding test to whatever we run when we change the judge model — it is four
cases and thirty seconds, and it is the difference between knowing our judge rewards length and
suspecting it."*

**The interview question:** *"Your model's judged quality score went up after a prompt change. What
would you check?"* The answer that shows experience asks whether the answers got longer, and can say
why that matters — because a judge that rewards length gives you a lever the optimiser will find, and
the score can rise while the thing you cared about falls.
