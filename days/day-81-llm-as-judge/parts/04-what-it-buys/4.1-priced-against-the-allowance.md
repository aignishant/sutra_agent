# 4.1 — Priced against the allowance

## One-line answer

Twenty-four cases cost **240 requests** — twelve times the only daily allowance this repository has
measured — and the three multipliers that get you there are the three controls that make the number
mean anything: five samples, two runs, and two orderings.

## The story

The coaching centre that charges by the question.

The parent asks what it costs and is told a hundred rupees a question. That sounds like nothing. A
hundred rupees for a doubt cleared is obviously worth it.

Then the term starts. There are five subjects. The child has three or four doubts a week in each.
There are sixteen weeks. Nobody did that multiplication at the counter, because at the counter there
was one number and it was small.

The price per question was never misleading. What was missing was the *shape of the usage* — how many
questions, how often, for how long — and that is a number the parent had to bring, not the centre.

## The idea in plain language

Day 79 part 4.1 gave the formula for a judged metric: `cases × num_samples × num_runs`. Day 80 part
5.1 applied it to a rubric and found rubric lines are free. This part applies it to
`final_response_match_v2` and adds the term that is new today.

- **cases** is the number of graded answers. One call each, per sample.
- **num_samples** defaults to **5** on `google-adk==2.7.1`, and part
  [1.2](../01-the-judge-is-a-system/1.2-the-judge-disagreed-with-itself.md) is why cutting it is the
  wrong lever: it turns a majority into a single draw.
- **num_runs** defaults to **2** on `AgentEvaluator.evaluate`, averaging the agent's own
  non-determinism.
- **the swap control** is **×2** and applies only to pairwise comparisons — part
  [2.1](../02-the-judge-has-biases/2.1-position.md), where twelve confident verdicts became zero once
  each pair was shown both ways round.

Multiplied out, the three controls are a factor of **twenty**. That is the number to hold: a judged
evaluation done honestly costs twenty times a judged evaluation done once, and the twenty is not
overhead. Each factor buys something specific:

| Control | Factor | What it buys | What you lose without it |
| --- | --- | --- | --- |
| `num_samples` 5 | ×5 | a majority instead of one draw | flickering verdicts (part 1.2) |
| `num_runs` 2 | ×2 | the agent's variance averaged | a regression that was a coin |
| swap control | ×2 | a preference about the answers | 12 of 12 decided by ordering (part 2.1) |

And the thing that makes this day's arithmetic different from Day 80's: **there is no free lever
here.** Day 80's rubric lines multiplied the prompt rather than the calls, so the cheapest improvement
available to that metric was a better rubric. This metric has nothing analogous. Every quantity in it
is a multiplier on requests, so every honest improvement costs money and the only reduction available
is fewer cases.

## Why Sutra needs it

Because Day 78 measured the one allowance this repository has ever observed — **20 requests per day**
for `gemini-3.7-flash`, read off a live 429 on 2026-08-25 — and Day 78's criterion 3 returned *cannot
determine* for the Flash-Lite lane Addendum 02 recommends for eval volume. That criterion is now open
for a fourth day, and three separate lists are blocked on it: Day 78 part 5.2 item 9, Day 79 part 5.3
item 3, Day 80 part 5.2 item 8.

This part is what makes that blocking concrete. 240 requests is not a number you can schedule against
an unknown allowance, and the sentence *"run it on Flash-Lite instead"* is a plan resting on a
parenthesis in an addendum.

## The mechanism

The constants carry their provenance. From `lab/cost.py`:

```python
NUM_SAMPLES = 5  # JudgeModelOptions.num_samples default on google-adk==2.7.1
NUM_RUNS = 2  # AgentEvaluator.evaluate's default on the same version
SWAP = 2  # a pairwise verdict is asked twice, once each way round (papers/mtbench)
```

**Line by line:**

- Each constant names where the number came from and the version it was read from. A default copied
  from a library is still a number that needs a source — Principle 7 applied to arithmetic, the same
  discipline Day 78 part 1.1 asked for on job costs.
- `SWAP = 2` cites the paper's demo rather than a library, because it is not a library default at all.
  It is a methodological requirement, and writing it as a constant next to the two library defaults is
  the honest way to say that all three are multipliers even though only two are ADK's.
- They are module constants, not arguments, so the script cannot be run with assumptions different
  from the ones it prints.

And the arithmetic, written as three lines rather than one product so the terms are visible:

```python
    graded = cases * NUM_SAMPLES * NUM_RUNS
    print("  final_response_match_v2, one answer at a time:")
    print(f"    {cases} cases x {NUM_SAMPLES} samples x {NUM_RUNS} runs{'':<8}{graded:>7} calls")

    arena = pairs * NUM_SAMPLES * NUM_RUNS * SWAP
```

**Line by line:**

- `graded` and `arena` are separate totals because they are separate metrics with separate shapes —
  one grades an answer against a reference, the other compares two answers. Adding them into one
  number before printing would hide which half the cost is in.
- The `x` in the printed line is a literal, so the output reads as the multiplication rather than as a
  result. A reader can check it.
- `arena` has `SWAP` in it and `graded` does not, which is the difference part
  [2.1](../02-the-judge-has-biases/2.1-position.md) established: a single-answer grader has no ordering
  to control for.

Run it for this day's suite:

```bash
cd days/day-81-llm-as-judge/lab
uv run python cost.py
```

**Line by line:**

- No flag: the twenty-four cases in `_cases.py`, single-answer grading only.

Measured on 2026-09-06:

```text
suite: 24 single-answer cases
num_samples 5, num_runs 2

  final_response_match_v2, one answer at a time:
    24 cases x 5 samples x 2 runs            240 calls

  requests for one evaluation:        240
  a day's observed flash allowance:   20
  flash-lite allowance:               unmeasured

  that is 12x a whole day on the measured lane

  what each control costs, and what it buys:
    num_samples 5   x5   a stable verdict instead of one draw
    num_runs 2      x2   the agent's own non-determinism averaged
    swap control    x2   a preference that is not just the ordering

  none of the three is decoration, and together they are a factor of twenty
```

**Two hundred and forty requests for twenty-four answers.** Ten calls per answer, and every one of
the ten is a default somebody at Google chose as sensible.

Now the size a real suite reaches, with a pairwise arena on top:

```bash
uv run python cost.py --grow
```

**Line by line:**

- `--grow` takes it to sixty single-answer cases and sixty pairwise comparisons — the "full 60+ only
  at phase gates" figure from Addendum 02, plus an arena of the kind part
  [2.1](../02-the-judge-has-biases/2.1-position.md) needs.

Measured on 2026-09-06:

```text
  pairwise, with the position-swap control:
    60 pairs x 5 x 2 x 2 orderings          1200 calls
    the swap control is the x2, and it is not optional (papers/mtbench)

  requests for one evaluation:        1800
  a day's observed flash allowance:   20
  flash-lite allowance:               unmeasured

  that is 90x a whole day on the measured lane
```

**One thousand eight hundred.** Two-thirds of it is the arena, and half of *that* is the swap control
— six hundred requests spent entirely on finding out whether the judge's preferences are about the
answers or about the order.

That is the number worth arguing about in a design review, because it is the one that will be cut.
And part [2.1](../02-the-judge-has-biases/2.1-position.md) measured what cutting it buys you: twelve
of twelve verdicts, every one of them the ordering.

## When it breaks

The arithmetic under-counts, in the same direction Day 79 part 4.1 warned about and for one additional
reason that is specific to a judge.

**Retries.** A 429 in the middle of a five-sample loop is answered by Day 72's backoff, and the retry
is a request. Under quota pressure the real cost exceeds the plan by an amount that depends on how bad
the pressure is — and quota pressure is highest exactly when the nightly is running alongside
everything else.

**Partial samples.** Worse than the extra cost: if some samples land and some are refused, the
aggregator votes over **whatever arrived**. A case that got three samples instead of five has a
majority computed from three, and nothing in the result records that. So a quota squeeze silently
reduces the effective `num_samples` on the runs where the system was busiest, and part
[1.2](../01-the-judge-is-a-system/1.2-the-judge-disagreed-with-itself.md)'s flickering gets worse on
exactly those runs.

What you would see is Day 78's recorded refusal, part-way through:

```text
429 RESOURCE_EXHAUSTED
generativelanguage.googleapis.com/generate_content_free_tier_requests
Please retry in ~53s
```

and a results file where some cases are scored, some are `NOT_EVALUATED`, and some are scored from
fewer samples than you asked for — with only the middle category visible.

The smallest fix is to record the sample count actually used, per case, alongside the score. It costs
nothing, it is available at the point the aggregator runs, and it is the only way to distinguish
"this case is borderline" from "this case only got two opinions".

## In production

**What a professional does about the bill.** Reduces **cases**, not controls. A judged metric on a
representative subset with all three controls intact is worth more than a judged metric on everything
with `num_samples=1` — because the first has a known margin of error and the second has an unknown
one. Sampling is a decision you can defend; weakening the controls is a decision that makes every
subsequent number harder to interpret.

**What degrades at scale.** Judged evaluation is sequential against a rate limit, so cost and
*duration* rise together. A nightly run that took twenty minutes at twenty-four cases takes hours at
six hundred, and it stops fitting in the window — which is Day 73's ambient job hitting Day 78's
scheduling problem, and the pressure that follows lands on `num_samples` first.

**The failure that only shows with real traffic.** Cost is not uniform across cases. Long answers make
long prompts, and part [1.3](../01-the-judge-is-a-system/1.3-what-the-judge-is-shown.md) measured that
the fixed template is over ninety per cent of a short case's prompt — so token cost per case varies by
an order of magnitude while request cost does not. On a per-request free tier that is invisible; on a
paid tier the bill is dominated by a handful of cases nobody identified.

**The review comment a senior engineer leaves:** *"240 requests against an allowance of 20 means this
does not run nightly on the lane we have measured, full stop. Before anybody writes the scheduling
code, somebody measures Flash-Lite's daily allowance — it has been blocking three separate lists since
day 78. And record the sample count per case; when we start getting throttled I want to know which
scores were computed from three opinions instead of five."*

**The interview question:** *"An LLM-as-judge evaluation is too expensive. What do you cut?"* The
answer that shows experience cuts the number of items judged and protects the sampling and the swap —
and can say why: the controls are what make the remaining numbers interpretable, so cutting them does
not give you a cheaper measurement, it gives you a cheaper number.
