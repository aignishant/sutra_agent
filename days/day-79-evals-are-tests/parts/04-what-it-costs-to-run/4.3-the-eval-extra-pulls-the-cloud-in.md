# 4.3 — The eval extra pulls the cloud in

## One-line answer

💥 `pip install "google-adk[eval]"` is not one package — it is ten, including
`google-cloud-aiplatform[evaluation]`, the whole Vertex AI SDK — and the two metrics this day needs
required exactly **one** of them, which is the difference between a dependency you chose and a
dependency tree you accepted.

## The story

Ordering one part for a scooter.

The chain guard has cracked. It is a piece of pressed metal that costs almost nothing, and you ring
the parts shop and ask for one.

What turns up is a crate. Inside is the chain guard, and also the chain, both sprockets, the cover
plate, the fixings and a gasket set — because the part number you were given is a kit, and the kit is
what the catalogue sells. Nobody misled you. The chain guard is in there.

Now it is in your house. You did not want the sprockets. You have to store them, you have to decide
what to do with them, and the next person who looks at your shelf will reasonably assume you needed
them for something.

The question that would have avoided this is not "how much does it cost". It is *"what exactly is in
that part number?"* — and it is a question almost nobody asks, because a part number looks like a part.

## The idea in plain language

An **extra** is an optional group of dependencies a package declares. `google-adk[eval]` is one, and
what it contains was read from PyPI on 2026-09-06:

```text
gepa>=0.1
google-cloud-aiplatform[evaluation]>=1.148
google-cloud-texttospeech>=2.37
jinja2>=3.1.4,<4
nltk!=3.10.1
openpyxl>=3.1.5,<4
pandas>=2.2.3
rouge-score>=0.1.2
tabulate>=0.9
xlrd>=2,<3
```

Ten entries, and the second one is the interesting one: `google-cloud-aiplatform[evaluation]` is
Google Cloud's Vertex AI SDK, itself a large tree, itself with an extra. Also in the list:
text-to-speech, two spreadsheet libraries, and a templating engine.

None of that is wrong. The extra covers **everything** ADK's evaluation package can do — the Vertex AI
evaluation service, the audio user simulator, the spreadsheet export of results — and a group that
covers everything necessarily installs everything.

The point is that a curriculum with a zero-budget constraint has to know **which member of the group it
actually needs**. Part [4.1](4.1-the-metrics-that-spend-nothing.md) established that this day's two
metrics are deterministic. One of them, ROUGE, needs `rouge-score`. The other needs nothing at all. So
the honest install for this day is one package, not ten, and the way to find that out is to import each
module and see what breaks.

There is a second thing this exercise reveals, and it is more useful than the package list: **which
parts of `google.adk.evaluation` are importable without the extra tells you which parts are local and
which are cloud.** A module that imports cleanly on a base install does its work in your process. A
module that needs `pandas` or `vertexai` at import time is a module wired to something bigger.

## Why Sutra needs it

Because Addendum 02 is a hard constraint: *never write code that requires a billing account, a paid
model, or a paid API*. `google-cloud-aiplatform` does not require one to install, and it is a strong
signal about what the code path expects — and a curriculum that installs the Vertex AI SDK on the day
it teaches evals has taught the reader that evals need Google Cloud, which is false.

It also matters for `uv.lock` and for every future `uv sync`. A ten-package extra is ten more version
resolutions, ten more things that can conflict, and a much larger environment to rebuild — on a machine
where [OneDrive has already caused install failures](../../../day-00-toolchain-skeleton-driver/LESSON.md) once.

## The mechanism

The probe is a loop over module names with the exception type as the result:

```python
    for name, purpose in MODULES:
        try:
            importlib.import_module(f"google.adk.evaluation.{name}")
            result = "ok"
        except Exception as exc:  # noqa: BLE001 - the exception type is the finding
            result = f"{type(exc).__name__}: {exc}"
            if name in REQUIRED:
                missing += 1
        print(f"  {name:<28}{result}")
        print(f"  {'':<28}{purpose}")
```

**Line by line:**

- `importlib.import_module` with a string rather than a top-level `import`, because the whole point is
  to attempt imports that may fail and keep going. A file of thirteen `import` statements stops at the
  first one.
- `except Exception` with a `# noqa: BLE001` and a reason attached. Principle 10 says errors surface
  rather than being swallowed, and this is the narrow case where catching broadly is the measurement:
  the **type and message of the exception is the output of the script**. The comment says so, which is
  what the `noqa` rule requires.
- `f"{type(exc).__name__}: {exc}"` prints the class and the message. `ModuleNotFoundError: No module
  named 'pandas'` names the missing package exactly, which is what makes this probe actionable rather
  than merely informative.
- `REQUIRED` is a set of the two modules this day genuinely needs, so the exit code is about **this
  day's** requirements and not about the completeness of the install. A missing `safety_evaluator` is a
  fact; a missing `trajectory_evaluator` is a broken day.
- Each module's purpose prints on its own line beneath it rather than in a column, because the error
  messages are long and a column wide enough for them wastes the width on every passing row.

Run it:

```bash
cd days/day-79-evals-are-tests/lab
uv run python deps.py; echo "exit: $?"
```

**Line by line:**

- No flag and no arguments. It imports thirteen modules and reports what happened to each.

Measured on 2026-09-06, against this repository's environment — `google-adk==2.7.1` plus
`rouge-score==0.1.2`, and **not** the `eval` extra:

**Ten of thirteen import on a base install plus one small package.** Both of this day's metrics, the
whole case and evalset vocabulary, the config machinery, the pytest entry point, and even the
LLM-as-judge harness that Day 81 needs.

Three do not, and the three are informative rather than arbitrary:

- `metric_evaluator_registry` is the name-to-evaluator table. It imports **every** prebuilt evaluator
  at module load, so it inherits the heaviest one's dependencies. That is why this day constructs its
  two evaluators directly rather than looking them up by name.
- `local_eval_service` is what the `adk eval` CLI and the dev UI run on, which means **the CLI needs
  the extra even for metrics that do not**. That is worth knowing before you conclude the CLI is
  broken.
- `safety_evaluator` genuinely is a Vertex-backed metric.

Trace one of them by hand to see how far the chain goes:

```bash
uv run python -c "import google.adk.evaluation.metric_evaluator_registry" 2>&1 | tail -5
```

**Line by line:**

- Imports the failing module directly so the full traceback is visible. `tail -5` because the chain is
  long and the last few frames are the ones that name the packages.

Measured on 2026-09-06:

```text
  File "...\google\adk\evaluation\metric_evaluator_registry.py", line 46, in <module>
    from .multi_turn_task_success_evaluator import MultiTurnTaskSuccessV1Evaluator
  File "...\google\adk\evaluation\multi_turn_task_success_evaluator.py", line 27, in <module>
    from .vertex_ai_eval_facade import _MultiTurnVertexiAiEvalFacade
  File "...\google\adk\evaluation\vertex_ai_eval_facade.py", line 26, in <module>
    import pandas as pd
ModuleNotFoundError: No module named 'pandas'
```

**Read the middle frame.** The registry does not want `pandas`; it wants
`multi_turn_task_success_evaluator`, which wants `vertex_ai_eval_facade`, which wants `pandas` — and,
two lines further into that same file, `vertexai`. Three hops from a name lookup to Google Cloud, all
of them at import time, none of them conditional.

And the counterpart — how ROUGE gets in, from `google/adk/dependencies/rouge_scorer.py` in its
entirety after the licence header:

```python
from rouge_score import rouge_scorer as rouge_scorer
from rouge_score import tokenizers as tokenizers
```

**Line by line:**

- Two re-export lines and nothing else. The shim exists so that everything inside ADK imports
  `..dependencies.rouge_scorer` rather than `rouge_score` directly, which gives the library one place
  to change if the dependency moves.
- `as rouge_scorer` on a same-named import is the explicit re-export form: it tells a type checker that
  the name is intentionally part of this module's public surface rather than an incidental import.
- What this means practically: `final_response_match_v1` needs **one** package from the ten-item extra,
  and installing that one package is enough.

## When it breaks

The error is clear and the conclusion people draw from it is wrong. What you see first is:

```text
ModuleNotFoundError: No module named 'pandas'
```

and ADK has a message ready for exactly this moment, defined in
`google/adk/evaluation/constants.py` on 2.7.1:

```text
Eval module is not installed, please install via `pip install "google-adk[eval]"`.
```

That instruction is correct and it installs ten packages including the Vertex AI SDK. For a project
that needs `response_match_score`, the right command is:

```bash
uv add "rouge-score==0.1.2"
```

**Line by line:**

- Version looked up on `pypi.org/pypi/rouge-score/json` on 2026-09-06: `0.1.2`, uploaded 2022-07-22.
  Principle 7 — the pin is a version somebody observed, on a date, and it gets a row in
  `docs/PACKAGES.md`.
- `rouge-score` declares no dependencies in its PyPI metadata but pulls `absl-py`, `nltk`, `numpy` and
  `six` at install time from its `setup.py`. On this repository that resolved to ten installed packages
  — still fewer than the extra, and none of them a cloud SDK.

The failure this part is really about is not the error. It is **following the instruction without
reading it**, and ending up with `google-cloud-aiplatform` in `uv.lock` on a project whose second
principle is that it never needs a billing account. Nothing breaks. The tests pass. The environment is
now four times larger and somebody, later, will reasonably conclude that Sutra's evals run on Vertex.

The smallest fix is a question before every extra: **which member of this group do I need?** The probe
in this part answers it in one command, and the answer is usually one or two.

## In production

**What a professional does with an extra.** Reads its contents before installing it —
`pip download --no-deps` and the PyPI JSON both show `requires_dist` — and installs the specific
packages when the group is broad. The judgement call is real: taking the extra is one line and is
easier to maintain, taking the members is smaller and is one more thing to keep in step with upstream.
The rule that resolves it is whether anything in the group would be a lie about the system, and a cloud
SDK in a zero-budget project is exactly that.

**What degrades at scale.** Transitive trees compound. `google-cloud-aiplatform` brings its own
dependencies, each of which brings more, and a year later a security scan flags a package four levels
down that arrived because somebody wanted a ROUGE score. Every extra you take is a set of version
constraints you have agreed to honour for as long as the project lives.

**The failure that only shows with real traffic.** Import-time dependencies fail at import time, which
is deployment time, which is the worst time. The three failing modules above would break a container
that built fine locally, if the local machine happened to have `pandas` from something else. Day 86's
containerisation is where that lands, and the defence is that a build runs the probe rather than
trusting that the environment resembles the laptop.

**The review comment a senior engineer leaves:** *"We need one package out of that extra. Add
`rouge-score` explicitly with the dated row rather than taking `[eval]`, and put `deps.py` in CI —
three of those modules are one upstream refactor away from becoming required, and I would rather find
out from a red build than from a container that will not start."*

**The interview question:** *"You need one function from a library and it lives behind an optional
extra that installs a cloud SDK. What do you do?"* The answer that shows experience finds out what the
extra actually contains, installs the minimum, and then names the trade-off honestly: the narrow
install can break when upstream reorganises, so it needs a check that catches that — which is the
difference between a decision and a shortcut.

## Check yourself

```bash
cd days/day-79-evals-are-tests/lab
uv run python deps.py; echo "exit: $?"
uv run python -c "import google.adk.evaluation.metric_evaluator_registry" 2>&1 | tail -5
```

Follow the traceback and name the three files it passes through. Say which one is the boundary between
"local evaluation" and "Google Cloud", and what that tells you about which metrics you can run offline.

Now fetch the extra's contents yourself and count them:

```bash
curl -s https://pypi.org/pypi/google-adk/json | python -c "
import json, sys
rows = [r for r in json.load(sys.stdin)['info']['requires_dist'] if 'extra == \"eval\"' in r]
print(len(rows)); print(*rows, sep='\n')"
```

It printed `10` on 2026-09-06. Say which one of the ten this day needed, and how you would have found
that out without the probe.
