# 4.2 — Flash-Lite is the workhorse, and why

## One-line answer

An eval run is high volume and low stakes per call, which is the exact profile the cheapest,
highest-allowance model is for — and the honest state of that recommendation today is that
`gemini-2.5-flash-lite`'s daily allowance is **unmeasured**, so choosing it is a defensible bet rather
than a calculation.

## The story

Two ways to get to work.

There is the fast bus. It stops four times, it has a seat, and it costs what it costs. If you have to
be somewhere at nine for something that matters, you take it, and the fare is not the point.

There is the local. It stops everywhere, it takes half an hour longer, and it is a fraction of the
price. It is not a worse bus in any absolute sense. It is a worse bus for a nine o'clock meeting and a
better bus for the days you are just going in.

The thing people get wrong is not choosing between them. It is choosing *once* and then applying that
choice to every journey for a year — always the fast one because "it's better", or always the local
because "it's cheaper" — instead of asking, each time, what this particular journey needs.

An eval run is a journey you make every night, alone, with nobody waiting at the other end.

## The idea in plain language

Different model calls have genuinely different requirements, and two axes cover most of it.

**Volume.** How many calls, per unit of time. A user's question is one call. An eval run is
`cases × samples × runs` calls — part [4.1](4.1-the-metrics-that-spend-nothing.md) measured 180 for six
cases and 1,800 for sixty.

**Stakes per call.** What one bad answer costs. A wrong answer to a customer is a wrong answer to a
customer. A wrong judgement on one eval case, out of five samples that get aggregated, moves a number
slightly.

Those two put eval traffic in a specific corner: **high volume, low stakes per call**. And an
allowance-limited world has a model shaped for that corner. Addendum 02 §5's row for days 79–83 says
it directly:

> Run evals on **Flash-Lite** (highest RPD); keep per-run evalsets small (10–15 cases dev, full 60+
> only at phase gates); schedule full runs as the Day 73 ambient *nightly* job so daily quota resets
> work for you.

Three instructions, and each is a different lever on the same arithmetic from part
[4.1](4.1-the-metrics-that-spend-nothing.md):

- **the model** changes which allowance you are spending — a different `(provider, model)` lane, in
  Day 78's vocabulary, with its own bucket;
- **the suite size** changes the `cases` term;
- **the schedule** changes *when* the spending lands, so it falls in a window where the interactive
  desk is not competing for it.

Now the part that has to be said plainly, because it is the difference between advice and a
measurement. Addendum 02's parenthesis is *"(highest RPD)"* — highest daily allowance. That is the
whole justification for the choice, and **this repository has never measured it.** Day 78's criterion
3 returned `cannot determine` for exactly this lane, and the two pages that would answer it were
fetched on 2026-09-06:

- `ai.google.dev/gemini-api/docs/rate-limits` says limits *"can be viewed in Google AI Studio"* and
  publishes no free-tier table;
- `console.groq.com/docs/rate-limits` says the same about its own numbers.

So the honest statement of this part's advice is: **use Flash-Lite for eval traffic because it is a
separate bucket from the desk's and is documented as having a higher daily allowance, and go and
measure that allowance, because until you do, the plan rests on a number nobody has seen.**

There is a second reason for the choice that does not depend on any number, and it is worth having
because it survives the measurement coming back badly: putting evals on a different model **isolates**
them. Even if Flash-Lite's allowance turned out to be identical to Flash's, spending it would not take
requests away from the desk that customers are waiting on — which is
[Day 78 part 5.1](../../../day-78-inside-free-quota/parts/05-in-production/5.1-the-nightly-competes-with-the-day.md)'s
whole argument.

## Why Sutra needs it

Because Day 82 is going to put this suite on Day 73's nightly, and the nightly already has a lane
problem. Day 78 part 1.3 counted the whole of Phase 11 at 62 requests a day against an observed
allowance of 20 on the Flash lane, and the eval stage's 60 sit on the Flash-Lite lane precisely so they
are not part of that 62.

That separation is load-bearing for the entire phase, and it is currently resting on an unmeasured
number. Naming that here — rather than in a footnote on Day 82 — is what stops it becoming an
assumption.

## The mechanism

The model choice is a field in the config, not a global setting. From `JudgeModelOptions` on the
installed `google-adk==2.7.1`:

```python
class JudgeModelOptions(EvalBaseModel):
    """Options for an eval metric's judge model."""

    judge_model: str = Field(
        default="gemini-2.5-flash",
        description="The judge model to use for evaluation. It can be a model name.",
    )
    judge_model_config: SkipJsonSchema[Optional[genai_types.GenerateContentConfig]] = Field(
        default=None, description="The configuration for the judge model."
    )
    num_samples: int = Field(default=5, description=...)
```

**Line by line:**

- `judge_model` defaults to **`gemini-2.5-flash`** — not Flash-Lite. So a config that says nothing about
  the judge model is running evals on the ordinary Flash lane, which is the same lane the desk uses.
  That default is the thing Addendum 02's advice is overriding, and it is silent.
- This is `ADK-73`'s trap in a new place: since ADK 2.2 the default model is a preview whose free quota
  is tighter, and the plan's answer is that **every agent pins its model explicitly**. A judge is a
  model call like any other, and it needs the same treatment.
- `num_samples: int = 5` is the multiplier part
  [4.1](4.1-the-metrics-that-spend-nothing.md) priced. It sits on the same object as the model, which
  is convenient: both terms of `cases × samples` are configured in one place.
- `judge_model_config` takes a full `GenerateContentConfig`, so temperature and max tokens are settable
  — worth knowing, because a judge at a high temperature is a judge whose five samples disagree more.

Naming Flash-Lite in `test_config.json`, using the object form of a criterion from part
[3.4](../03-two-metrics-that-cost-nothing/3.4-the-threshold-is-the-test.md):

```json
{
  "criteria": {
    "tool_trajectory_avg_score": 1.0,
    "response_match_score": 0.8,
    "final_response_match_v2": {
      "threshold": 0.5,
      "judge_model_options": {
        "judge_model": "gemini-2.5-flash-lite",
        "num_samples": 5
      }
    }
  }
}
```

**Line by line:**

- The first two keys are the deterministic metrics and cost nothing, so they stay listed — part
  [3.4](../03-two-metrics-that-cost-nothing/3.4-the-threshold-is-the-test.md)'s rule that a config file
  replaces the defaults rather than merging with them.
- `final_response_match_v2` takes an **object** rather than a bare float, because it needs to carry the
  judge options. `get_eval_metrics_from_config` handles both forms.
- `"judge_model": "gemini-2.5-flash-lite"` is the whole of Addendum 02's model advice, in one string.
  Leaving it out silently uses `gemini-2.5-flash`.
- `"num_samples": 5` is written out even though it is the default, for the same reason the thresholds
  are: this file should be the complete answer to "what did that run cost", and a reader should not
  have to know a library default to work it out.
- **This config is not used by today's lab**, and that is deliberate: running it would spend requests
  this curriculum's own gate could not confirm were available. It is here as the thing Day 81 turns on
  once the allowance has been measured.

The three levers, applied to part [4.1](4.1-the-metrics-that-spend-nothing.md)'s arithmetic:

| Lever | Addendum 02's instruction | Effect on `cases × samples × runs` |
| --- | --- | --- |
| model | Flash-Lite | changes **which allowance** is spent, not the count |
| suite size | 10–15 in dev, 60+ at gates | changes **cases**, the only term that is yours |
| schedule | on the Day 73 nightly | changes **which window** the spend lands in |

**Only one of the three reduces the number of requests.** The other two move them — to a different
bucket and to a different time — which is the actual shape of quota management: you rarely make work
cheaper, you make it land somewhere it fits.

## When it breaks

The failure is a judge model that was never named, and it announces itself as a quota error on a lane
nobody expected to be spending.

Leave `judge_model` out, run a judged metric, and the requests go to `gemini-2.5-flash`. On a
project whose Flash allowance is the 20 measured on 2026-08-25, a six-case run of one judged metric
wants 60 — three times the day — and what arrives is:

```text
429 RESOURCE_EXHAUSTED
generativelanguage.googleapis.com/generate_content_free_tier_requests
Please retry in ~53s
```

part-way through the run. The desk stops working for the rest of the window, because the eval run has
spent the lane the desk uses.

**Nothing in the eval output says which model it used.** The results file has scores; the config has a
missing key. The only way to find out is to read the default in the library, which is why this part
quotes it.

There is a second break that has no message at all: **changing the judge model changes the scores.**
Two judges disagree about borderline cases, so a suite tuned at 0.5 on Flash may need a different
number on Flash-Lite. Switching the model for cost reasons and keeping the thresholds is a silent
recalibration, and the honest procedure is to re-derive the thresholds from a fresh score distribution
after any judge change — part
[3.4](../03-two-metrics-that-cost-nothing/3.4-the-threshold-is-the-test.md)'s rule, applied to a
different trigger.

The smallest fix is one line in the config, and a habit: **pin the judge model everywhere, and record
it in the results.** A results file that does not say which model judged it cannot be compared with
last month's.

## In production

**What a professional writes.** The judge model pinned by name in the config, its version recorded in
every results file, and a note saying when the thresholds were last derived and against which judge.
Those three facts are what make a score from March comparable with a score from September, and without
them an eval suite's history is a series of unrelated numbers.

**What degrades at scale.** Cheap models are cheap for a reason, and the reason shows up on the hard
cases. A judge that agrees with a human 95% of the time on clear-cut answers may agree 70% of the time
on the borderline ones — which are exactly the cases near the threshold, which are exactly the cases
that decide pass or fail. So the cheap judge is least reliable precisely where it matters most, and the
mitigation is not a better model everywhere: it is a cheap judge for the bulk and a second opinion for
cases that land near the line.

**The failure that only shows with real traffic.** Free rosters move. Addendum 02 records a December
2025 precedent for exactly this, and Sutra's own ledger has a model repin on 2026-08-24. A judge model
that loses its free tier turns a nightly eval run into either a billing event or a silent failure,
depending on how the key is configured — and the eval suite is the last place anybody looks when
something starts costing money.

**The review comment a senior engineer leaves:** *"Pin the judge model in the config, and put the model
string in the results file. Right now if somebody asks why the score moved between March and September
we cannot answer, because we do not record what did the judging. And add a `TODO` with a date for
measuring Flash-Lite's actual RPD — we are betting the whole nightly on a number from a sentence in an
addendum."*

**The interview question:** *"You need to run an LLM-as-judge evaluation on a budget. What do you
change?"* The answer that shows experience names three levers and says which ones actually reduce cost:
a cheaper model moves the spend to a different quota, a schedule moves it to a different window, and
only reducing the number of judged cases reduces the count. The tell is whether they then say the
uncomfortable part — that a cheaper judge is least reliable on the cases nearest the threshold.
