# 3.2 — Why exact match is the right default and the wrong metric

## One-line answer

Exact match is the correct **default** because it demands that somebody state the intended path, and
it is the wrong **metric** for most cases because it fails identically for a bug, a rename and an
optimisation — so the useful assertion is usually a property of the trajectory rather than the
trajectory itself.

## The story

Somebody asks you to take a parcel to an address across town, and you write down the route.

Down the main road, left at the petrol pump, past the school, right after the temple, third gate. It
is a good route. It is the route you would take.

The next morning the person you sent comes back and says the road past the school was closed for
digging, so they went round by the market and got there ten minutes earlier. The parcel is delivered.

Now: did they follow the instructions? No. Did they do the job? Yes, and better.

The written route was never really the point. What you actually wanted was: *do not go through the
narrow lane where the van does not fit, and do not take the long way round the ring road.* You wrote a
route because a route is easy to write and those two conditions are not.

The problem is that a route can be checked in a second, and the two conditions cannot be checked at
all unless somebody thinks about how to phrase them. So people write routes.

## The idea in plain language

Part [3.1](3.1-tool-trajectory-avg-score.md) showed `tool_trajectory_avg_score` failing two cases in a
faulty desk. This part is about the other times it fails.

The metric answers one question: *is this list of calls the same as that list of calls?* That question
conflates at least four situations that need different responses:

| What happened | Should the suite go red? | Score |
| --- | --- | --- |
| The desk called an extra tool it did not need | **yes** — cost, and least privilege | 0.00 |
| The desk called the right tools in the wrong order | **yes** when order is the specification | 0.00 |
| Somebody renamed a tool | no — nothing changed | 0.00 |
| The desk got faster and skipped a now-unnecessary call | no — it improved | 0.00 |

Four different situations, one score. The metric is not wrong; it is answering a narrower question than
the one the suite is being asked, and the last two rows are where a real suite spends its maintenance
budget.

So why is it the right default? Two reasons, and the first is not about correctness at all.

**It forces somebody to state the intended path.** Writing `tools=(("ticket", {"ticket_id": "4652"}),)`
requires deciding what the desk should do. There is no vague version of that field. Compare it with a
threshold like 0.8, which can be typed without any thought about what 0.8 means. A default that cannot
be filled in vaguely is a good default.

**It is free and deterministic.** Zero requests, same answer every run, and a failure you can reproduce
on a laptop. Every other property of a metric is negotiable; those two are what let a suite run on
every commit.

The alternative it should give way to for most cases is a **property assertion**: not *this exact
sequence*, but a statement about the sequence that survives refactoring.

- *at most one call to `ticket`* — the cost claim from Day 78, without naming the order;
- *no call to any tool that writes* — Day 68's least privilege, without naming the tools;
- *`open_tickets` called before `category_counts`* — Day 77's ordering claim, without forbidding a
  third call in between;
- *at least one tool called* — the anti-stub check from part
  [2.3](../02-the-evalset-file/2.3-the-case-that-cannot-fail.md), as an assertion rather than an
  exercise.

Each of those is the thing the case actually meant. Each of them survives a rename, a split, and a
cache. And each of them takes a sentence of thought to write, which is why the exact sequence is what
people write instead.

ADK supports this and the support is worth knowing: `EvalConfig.custom_metrics` maps a metric name to a
`code_config` naming a function of yours. So the property assertions above are not a fight against the
framework; they are the framework's intended extension point.

## Why Sutra needs it

Because Sutra's tool layer is going to change. Phase 13 adds tracing, Phase 14 adds A2A, and the
capstone rebuilds the desk end to end. A suite whose six cases each name an exact call sequence will go
red on every one of those, and each time somebody will have to decide between updating six references
and deleting the assertion.

Two of the six cases genuinely are about the path, and their notes say so. The other four are about
*what the desk knows* and merely happen to have a trajectory. That distinction is what this part is
asking you to make explicit before the suite grows.

## The mechanism

The exact-match assertion, as part [3.1](3.1-tool-trajectory-avg-score.md) uses it, is the evaluator
call. The property assertion is a function you write, and this is the shape ADK expects:

```python
def at_most_one_lookup(actual, expected) -> float:
    """1.0 when the desk called `ticket` at most once, 0.0 otherwise.

    The cost claim from day 78 part 1.3, stated without naming an order or a sequence.
    """
    lookups = sum(1 for call in actual.intermediate_data.tool_uses if call.name == "ticket")
    return 1.0 if lookups <= 1 else 0.0
```

**Line by line:**

- It reads `actual` and ignores `expected` entirely. That is the tell of a property assertion: it does
  not need a reference, because it is checking a rule rather than a match. The signature keeps
  `expected` so the function fits where a metric fits.
- `sum(1 for ... if call.name == "ticket")` counts one tool by name. A rename breaks this too — but it
  breaks **one line in one place** rather than a reference inside every affected case.
- It returns a `float` in `[0, 1]` because that is what a metric returns, even when the underlying
  question is a yes-or-no. The threshold for it would be `1.0`, exactly as for the built-in.
- It is deliberately not written as a `TrajectoryEvaluator` subclass. `EvalConfig.custom_metrics` takes
  a `code_config` naming a *function path*, so a plain function is what the config wants.

And how a config would name it — the shape documented in `EvalConfig`'s own docstring on the installed
`google-adk==2.7.1`:

```json
{
  "criteria": {
    "tool_trajectory_avg_score": 1.0,
    "at_most_one_lookup": 1.0
  },
  "custom_metrics": {
    "at_most_one_lookup": {
      "code_config": { "name": "sutra.evals.at_most_one_lookup" }
    }
  }
}
```

**Line by line:**

- `criteria` holds the threshold, exactly as it does for a built-in metric. From the config's own
  documentation: *"the key of the dictionary is the name of the eval metric and the value is the
  criterion to be used"*, and a bare number is a threshold.
- `custom_metrics` maps the same name to where the code lives. Both entries are needed — a name in
  `custom_metrics` with no threshold in `criteria` is never run.
- `"name": "sutra.evals.at_most_one_lookup"` is an import path, so the function must be importable
  from the environment the eval runs in. That is why the build brief puts it in `sutra/evals.py` and
  not in the lab.
- The two built-in defaults would be lost if this file replaced them, because
  `get_evaluation_criteria_or_default` returns the file's config **instead of** the default, not merged
  with it. Anything you still want has to be listed.

Now measure what the exact-match metric cannot distinguish. The `--buggy` arm from part
[3.1](3.1-tool-trajectory-avg-score.md) contains one genuine cost bug and one genuine ordering bug:

```bash
cd days/day-79-evals-are-tests/lab
uv run python trajectory.py --buggy
```

**Line by line:**

- Same command as part [3.1](3.1-tool-trajectory-avg-score.md). What is new here is reading the score
  column as a source of information rather than as a verdict.

Measured on 2026-09-06:

```text
  one_lookup         0.00  FAILED   ['open_tickets', 'ticket']
  order_matters      0.00  FAILED   ['category_counts', 'open_tickets']
```

Now simulate a non-bug: a tool is renamed in the **desk**, and the references — which live in a JSON
file no refactoring tool touches — are left alone. Add one line to the end of `answer()` in `_desk.py`:

```python
    tools = [("list_open_tickets" if n == "open_tickets" else n, a) for n, a in tools]
    return invocation(case.question, tools, said)
```

**Line by line:**

- The comprehension renames one tool on its way out of `answer()`, which is exactly what a rename in
  the real desk would do: the behaviour changes, the case definitions do not.
- It sits immediately before the existing `return`, so nothing else in the fixture moves. Delete the
  line to undo it — `days/*/lab/` is gitignored, so there is no committed version to restore.

Then run the **good** arm, with no fault injected at all:

```bash
uv run python trajectory.py; echo "exit: $?"
```

**Line by line:**

- No `--buggy`. This is the arm that was 6 of 6 a moment ago, and the only thing that has changed since
  is a tool's name.

Measured on 2026-09-06:

```text
  case              score  status   tools called
  counts             1.00  PASSED   ['category_counts']
  age_4740           1.00  PASSED   ['ticket']
  needs_person       0.00  FAILED   ['list_open_tickets']
  one_lookup         1.00  PASSED   ['ticket']
  order_matters      0.00  FAILED   ['list_open_tickets', 'category_counts']

  2 case(s) took a different path from the one written down

```

**`4 of 6`, exit 1 — the same headline the two real bugs produced.** Same score, same status, same
sentence at the bottom. The only thing separating a rename from a defect is the `tools called` column,
and only for a reader who happens to know what the tool used to be called.

## When it breaks

There is no error message for any of this, which is the difficulty. Every one of these situations
produces `0.00 FAILED`, and the four rows of the table at the top of this part are indistinguishable
in the output.

The rename measured above is the mildest of the three. A tool **split in two** — `ticket(id)` becoming
`ticket_meta(id)` plus `ticket_body(id)` — fails every case that used it, with a `tools called` column
listing two entries where the reference has one; a **cache** that skips a repeated call fails every
case whose reference has that call twice. In both, the score is `0.00`, the status is `FAILED`, and the
bottom line is the same sentence. You can reproduce either with the same one-line edit to `answer()`
that the rename used.

The fastest way to green is always to edit the references. Then somebody adds the cache and three more
go red, and by the fourth round the discussion is about whether the trajectory metric is worth having.

That discussion has a right answer and it is not "keep it" or "drop it". It is: **keep exact match for
the cases whose subject is the path, and use property assertions everywhere else.** Sutra's two are
`one_lookup` and `order_matters`, and they are the two with notes in the fixture explaining why the path
is the specification. Four of the six cases would be better served by *at least one tool was called*
plus their answer assertion — which is a smaller claim, honestly stated, that will survive Phase 13.

## In production

**What a professional writes.** A small vocabulary of trajectory properties, defined once, used across
many cases: call count bounds, tool allow-lists and deny-lists, ordering constraints between named
pairs, and "at least one call". Five or six functions in one module, wired in through
`custom_metrics`. It looks like more work than exact match on the day you write it and is less work by
the second refactor.

**What degrades at scale.** Exact-match brittleness compounds with suite size, because a rename touches
every case that mentions the tool. At six cases that is a two-minute edit. At four hundred it is a
migration, and migrations get deferred, and a deferred migration means a permanently red suite, and a
permanently red suite is a suite nobody reads. The failure is not the brittleness — it is what a team
does after the third occurrence.

**The failure that only shows with real traffic.** Real agents are non-deterministic about paths in a
way this lab cannot show. The same question can produce two calls in one run and one in the next
because the model made a different choice, and neither is wrong. That is exactly the situation property
assertions are for — *at most two calls* is true of both runs, *this exact sequence* is true of one —
and it is why `AgentEvaluator.evaluate` runs each case twice by default on `google-adk==2.7.1`.

**The review comment a senior engineer leaves:** *"Exact-match on all six is going to hurt in Phase 13.
Keep it on the two cases whose notes say the path is the point, and write three property metrics for
the rest — call count, a deny-list for write tools, and a before/after ordering pair. Put them in
`sutra/evals.py` and wire them through `custom_metrics`, so when a tool gets renamed we fix one line
rather than six references."*

**The interview question:** *"Your integration tests assert on an exact sequence of calls and they
break every refactor. What do you change?"* The answer that shows experience does not say "make the
tests less strict". It identifies **which property each test was actually protecting** — cost, order,
permissions — and asserts that instead, keeping the exact sequence only where the sequence is genuinely
the contract. The tell is whether they can name a case where exact match is still right.
