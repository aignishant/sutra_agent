# 3.4 — The threshold is the test

## One-line answer

`test_config.json` is a dictionary from metric name to threshold, ADK's defaults are
`tool_trajectory_avg_score: 1.0` and `response_match_score: 0.8`, and the file **replaces** those
defaults rather than adding to them — so a config listing one metric has silently switched the other
one off.

## The story

The pass mark written at the top of a question paper.

It says 35. Nobody in the exam hall chose that number and nobody in the exam hall can change it. It
came from somewhere — a committee, a board, a rule that has been the same for years — and it decides
who passes.

The interesting thing about a pass mark is that it is doing far more work than the questions are, and
almost nobody looks at it. Two boards with identical papers and pass marks of 33 and 40 produce
completely different results from the same students. The paper is what people argue about; the mark is
what determines the outcome.

And when a pass mark does change, the change is one number in one document. There is nothing in the
paper to show it moved. A student comparing this year's paper with last year's would find them
identical and would have no way to know that the line under them had shifted.

## The idea in plain language

Every metric returns a score; the threshold turns it into a verdict. That means **the threshold is
where the test actually lives**, and it deserves the same care as the cases.

ADK keeps thresholds in a file called `test_config.json`, in the same folder as the eval file. The
shape, from `adk.dev/evaluate/`:

```json
{
  "criteria": {
    "tool_trajectory_avg_score": 1.0,
    "response_match_score": 0.8
  }
}
```

Three things about it that a reader should know before writing one.

**Those two numbers are also the defaults.** On the installed `google-adk==2.7.1`, if no config file is
found, `get_evaluation_criteria_or_default` returns `_DEFAULT_EVAL_CONFIG`, which is exactly
`{"tool_trajectory_avg_score": 1.0, "response_match_score": 0.8}`. So a suite with no config file is
not unconfigured — it is configured with those two, which is a reasonable default and is worth knowing
you are relying on.

**The dictionary keys are the metric list.** There is no separate "which metrics to run" setting. The
metrics that run are the keys of `criteria`, so adding a metric means adding a key and **removing a
metric means removing a key**. That makes the file compact and it makes the failure in the next section
possible.

**A value can be a number or an object.** A bare float is a threshold. An object is a fuller
`criterion` — `final_response_match_v2` takes `{"threshold": 0.5, "judge_model_options": {...}}`,
which is how Day 81 will name Flash-Lite as the judge. Both forms are handled by
`get_eval_metrics_from_config`, which wraps a bare float in a `BaseCriterion` so that everything
downstream sees the same shape.

Now the part that is a judgement rather than a fact: **how to choose a number.** Two honest rules.

For a metric with no middle values — the trajectory metric from part
[3.1](3.1-tool-trajectory-avg-score.md), which returns 1.0 or 0.0 — the threshold is not a dial. Any
value in `(0, 1]` behaves identically. Write `1.0`, because it says what you mean.

For a metric with a real range, the threshold has to come from **looking at the distribution of scores
on answers you have judged by hand**. Part [3.3](3.3-response-match-and-the-word-not.md) did exactly
that and found something worth carrying: correct answers scored 0.353 to 0.600 and wrong answers scored
0.750 to 0.941. There is no threshold that separates them, and the honest conclusion is not "pick 0.8"
— it is that this metric cannot do this job, and the number is irrelevant.

That is the general shape of the rule. A threshold is only meaningful if the scores of good and bad
outputs actually separate. Choose it by measuring, and if they do not separate, the finding is about
the metric.

## Why Sutra needs it

Because Day 82 puts this suite in CI and on the nightly, and a threshold in a config file is the one
part of an eval suite that can be changed without touching a test. It is therefore the part that gets
changed when a suite is inconvenient — part
[5.2](../05-evals-are-tests/5.2-the-suite-that-only-goes-green.md) is about what that does over time.

It is also what the `adk eval` CLI reads. On `google-adk==2.7.1` the command is:

```text
adk eval <AGENT_MODULE_FILE_PATH> <EVAL_SET_FILE_PATH_OR_ID>...
         [--config_file_path=<PATH>] [--print_detailed_results]
```

and without `--config_file_path` it uses the defaults above. So *"we ran the evals"* means *"we ran
them at 1.0 and 0.8"* unless somebody says otherwise.

## The mechanism

How ADK resolves the config, from `agent_evaluator.py` on the installed 2.7.1:

```python
@staticmethod
def find_config_for_test_file(test_file: str) -> EvalConfig:
    """Find the test_config.json file in the same folder as the test file."""
    test_folder = os.path.dirname(test_file)
    config_path = os.path.join(test_folder, "test_config.json")
    return get_evaluation_criteria_or_default(config_path)
```

**Line by line:**

- The config is found by **location**, not by name in an argument: `test_config.json` in the same
  directory as the eval file. That is convention over configuration, and it means moving an evalset to
  another folder silently changes which thresholds it runs at.
- `os.path.dirname(test_file)` on a bare filename returns `""`, so a relative path with no directory
  looks for `test_config.json` in the current working directory. Running the same suite from two
  different directories can therefore pick up two different configs.
- It always returns an `EvalConfig` — never `None`, never raises for a missing file. A missing config
  is a silent fall back to the defaults.

And the fall-back itself:

```python
def get_evaluation_criteria_or_default(eval_config_file_path: Optional[str]) -> EvalConfig:
    """Returns EvalConfig read from the config file, if present.

    Otherwise a default one is returned.
    """
    if eval_config_file_path and os.path.exists(eval_config_file_path):
        with open(eval_config_file_path, "r", encoding="utf-8") as f:
            content = f.read()
            return EvalConfig.model_validate_json(content)

    logger.info("No config file supplied or file not found. Using default criteria.")
    return _DEFAULT_EVAL_CONFIG
```

**Line by line:**

- `return EvalConfig.model_validate_json(content)` — the file's config is returned **instead of** the
  default, not merged with it. This single line is the failure in the next section.
- The fall-back is logged at `info`, which in a default logging setup is not printed. A run that
  silently used the defaults looks identical to a run that used your config.
- `model_validate_json` means a malformed file raises a pydantic `ValidationError` naming the line —
  which is the friendly failure. The unfriendly one is a file that is valid and incomplete.

Converting the config into runnable metrics:

```python
if isinstance(criterion, float):
    eval_metric = EvalMetric(
        metric_name=metric_name,
        threshold=criterion,
        criterion=BaseCriterion(threshold=criterion),
        custom_function_path=custom_function_path,
    )
```

**Line by line:**

- A bare float in the JSON becomes both `threshold` and a `BaseCriterion` wrapping the same number, so
  downstream code can read either. That redundancy is why part
  [3.1](3.1-tool-trajectory-avg-score.md)'s `TrajectoryEvaluator(threshold=1.0)` and part
  [3.3](3.3-response-match-and-the-word-not.md)'s `RougeEvaluator(EvalMetric(...))` both work.
- `custom_function_path` is threaded through here — the hook part
  [3.2](3.2-exact-match-right-default-wrong-metric.md) uses for property assertions.
- The `else` branch of this function raises `ValueError("Unexpected criterion type...")`, so a config
  with a string or a list where a number belongs fails loudly rather than being coerced.

Write Sutra's config:

```bash
cd days/day-79-evals-are-tests/lab
cat > test_config.json <<'JSON'
{
  "criteria": {
    "tool_trajectory_avg_score": 1.0,
    "response_match_score": 0.8
  }
}
JSON
```

**Line by line:**

- Both metrics listed explicitly, even though these are the defaults. Writing them out costs nothing
  and makes the file the answer to "what are we running at", instead of the reader having to know that
  a missing file means something specific.
- `1.0` for the trajectory metric because it has no middle values, and `0.8` for ROUGE because that is
  the default — and part [3.3](3.3-response-match-and-the-word-not.md) has already shown that no value
  of this particular number would make that metric trustworthy.

Verify what a given config actually resolves to:

```bash
uv run python -c "
from google.adk.evaluation.eval_config import get_evaluation_criteria_or_default
print(get_evaluation_criteria_or_default('test_config.json').criteria)"
```

**Line by line:**

- Prints the resolved criteria dictionary. Run it with a path that does not exist and it prints the
  defaults instead, with no complaint — which is the check that turns the next section's failure from
  invisible into visible.

## When it breaks

The failure is a config file that is **valid and incomplete**, and it produces no message at all.

Somebody wants to loosen the answer metric for one suite, so they write:

```json
{
  "criteria": {
    "response_match_score": 0.5
  }
}
```

That is well-formed JSON, it validates as an `EvalConfig`, and it does what they intended — and it also
**removes `tool_trajectory_avg_score` entirely**, because the returned config replaces the default
rather than merging with it and the metrics that run are the keys of this dictionary.

The suite now asserts nothing about the path. Every trajectory failure that part
[3.1](3.1-tool-trajectory-avg-score.md) measured — the extra whole-queue read, the wrong ordering —
passes silently. The run output is shorter by one column and nothing says a metric was dropped.

You can see it in one command:

```bash
uv run python -c "
from google.adk.evaluation.eval_config import get_evaluation_criteria_or_default
print(get_evaluation_criteria_or_default('test_config.json').criteria)"
```

**Line by line:**

- Run against a config listing one metric, this prints a one-key dictionary. Run with no config file,
  it prints both defaults. The difference between those two outputs is the entire bug.

The smallest fix is a habit rather than a patch: **list every metric you want in every config file**,
and treat the file as the complete statement rather than as an override. If a suite has a config at
all, it should name all of its metrics, including the ones at their default values.

## In production

**What a professional writes instead of a bare threshold.** A threshold with a **comment next to it**
saying which case prompted the current value and when. JSON has no comments, which is a real problem
here; the usual answers are a sibling `test_config.md`, or a generator that emits the JSON from an
annotated source. Either is better than a number nobody can date.

**What degrades over time.** Thresholds move in one direction. A case fails, the failure is judged
acceptable, the number goes down. Each step is reviewable and defensible and none of them is recorded
as "the suite got weaker", because the diff is `0.8` becoming `0.7` and no reviewer can tell whether
that is a fix or a surrender. The measurable defence is part
[2.3](../02-the-evalset-file/2.3-the-case-that-cannot-fail.md)'s stub check: whatever the thresholds
are, the suite must still fail against an agent that does nothing.

**The failure that only shows with real traffic.** A threshold tuned on a fixture is tuned on a
distribution that does not exist. Real answers are longer, more varied and more often partially
correct, so the scores cluster differently — usually lower and wider — and a number chosen against six
handwritten cases will be wrong for four hundred real ones. The number has to be re-derived from real
scores the first time you have any.

**The review comment a senior engineer leaves:** *"This config lists one metric, which means we have
switched the trajectory metric off. List both. And for the ROUGE threshold, put the measurement that
justified the number somewhere findable — right now 0.8 is there because it is the library default,
which is a fine reason as long as we say so rather than implying somebody measured it."*

**The interview question:** *"Where does the number in your pass/fail threshold come from?"* The answer
that shows experience describes looking at the score distribution over hand-judged good and bad
outputs, and can say what it did when the two distributions overlapped — because that is the case that
actually happens, and the right answer there is to change the metric rather than the number.
