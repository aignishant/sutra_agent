# 2.1 — The evalset is a file, and the file is data

## One-line answer

ADK's evalset is a plain JSON file with a fixed shape — `eval_set_id`, `eval_cases`, and one
`conversation` per case — and the whole point of it being a file rather than code is that the person
who knows what the right answer is does not have to be the person who can write Python.

## The story

The shopping list on the fridge, and the shopping list in somebody's head.

For years one person did the shopping, and the list was in their head. It worked. They knew that the
small packet of one thing and the large packet of another, that the shop on the corner has the good
one, that you skip the eggs if the ones at home are still fine. Nobody wrote any of it down because
nobody needed to.

Then that person was away for a week.

What actually helps in that week is not a description of how they shop. It is the magnet on the fridge
with the pad under it, where anybody in the house can add a line when they use the last of something.
The child can add a line. The grandmother can add a line. Nobody has to know how the shopping is done
to say what is needed.

The list being *on the fridge* rather than *in a head* is not about storage. It is about who is
allowed to contribute.

## The idea in plain language

An **evalset** is a file holding a set of cases. In ADK it has a specific shape and a specific
filename ending, and both are worth knowing exactly.

The filename ends in **`.evalset.json`**. That is not a convention this curriculum invented — the
installed `google-adk==2.7.1` has it as a module constant:

```text
_EVAL_SET_FILE_EXTENSION = ".evalset.json"
```

in `google/adk/evaluation/local_eval_sets_manager.py`, and the manager derives an evalset's **id**
from the filename by stripping that suffix. So `triage.evalset.json` is the evalset whose id is
`triage`, and the `adk eval` CLI will accept either the path or the id.

The shape, as documented on `adk.dev/evaluate/` and as produced by the installed package:

- **`eval_set_id`** — the id, also derivable from the filename;
- **`name`** and **`description`** — for people;
- **`eval_cases`** — a list, each with:
  - **`eval_id`** — the case's name, from part
    [1.3](../01-a-test-with-a-score/1.3-the-case-is-the-unit.md);
  - **`conversation`** — a list of turns, each with `user_content`, `final_response` and
    `intermediate_data`;
  - **`session_input`** — the state the case starts from;
  - **`final_session_state`** — the state it should end in.

Two things follow from it being a file, and the second is the one that matters.

**It can be version-controlled and diffed.** A change to a reference answer shows up in a pull request
as a changed line, which somebody reviews. A reference answer buried in a Python fixture also shows
up in a diff, so this half is real but not remarkable.

**It can be edited by somebody who does not write code.** The person who knows what the desk *should*
have said about a refund is the person who handles refunds. They can open a JSON file, find the case,
and fix the wording. They cannot open `test_desk.py`. That asymmetry is the entire reason the format
exists, and it is why ADK's dev UI can add cases to an evalset from a session you just ran.

There is an honest counterweight and it belongs here rather than in a footnote: **JSON is a bad
editing surface for prose.** Escaped quotes, no line breaks inside strings, no comments. A reference
answer three sentences long is one very long line that a non-programmer will break in the wrong place.
The format optimises for machines reading it and for the dev UI writing it, and hand-editing is
tolerable rather than pleasant.

## Why Sutra needs it

Because everything in Phase 12 reads this file. Day 80's rubric evaluation adds `rubrics` to these
cases. Day 82 puts the file in CI and on Day 73's nightly. The `adk eval` CLI takes it as an argument.
If the cases live only in a Python fixture, none of that works without a conversion step nobody
maintains.

It is also the format the dev UI writes. `adk web` can save a session you have just had as a case,
which is part [2.2](2.2-recording-a-case-or-writing-one.md)'s subject, and it writes it into exactly
this shape. Reading the shape by hand once means the recorded cases are not magic afterwards.

## The mechanism

Building the file is one model dump. From `lab/cases.py`:

```python
def build() -> EvalSet:
    """The six cases as one EvalSet, in the shape ADK reads."""
    return EvalSet(
        eval_set_id=EVAL_SET_ID,
        name="Sutra triage desk",
        description="What the desk is supposed to get right. One case per behaviour.",
        eval_cases=[
            EvalCase(eval_id=case.eval_id, conversation=[expected(case)]) for case in CASES
        ],
    )
```

**Line by line:**

- `EvalSet` and `EvalCase` come from `google.adk.evaluation.eval_set` and
  `google.adk.evaluation.eval_case`. Verified against `adk.dev/evaluate/` on 2026-09-06 and against
  the installed `google-adk==2.7.1`, where `EvalSet.model_fields` is exactly `['eval_set_id', 'name',
  'description', 'eval_cases', 'creation_timestamp']`.
- `conversation=[expected(case)]` — a list with one `Invocation` in it. Every case here is a single
  turn; a multi-turn case is the same structure with more elements, which is what Day 80's
  `RubricBasedMultiTurnTrajectoryEvaluator` is named after.
- `EvalCase` is constructed with only `eval_id` and `conversation`. The other five fields have
  defaults, and `final_session_state` defaulting to `{}` is the gap part
  [1.2](../01-a-test-with-a-score/1.2-three-surfaces-you-can-assert-on.md) named.
- These are pydantic models, so building them here validates the shape immediately. A malformed case
  raises at construction rather than when something tries to score it.

Writing and reading back:

```python
    eval_set = build()
    PATH.write_text(eval_set.model_dump_json(indent=2, exclude_none=True), encoding="utf-8")
    ...
    loaded = load_eval_set_from_file(str(PATH), EVAL_SET_ID)
```

**Line by line:**

- `model_dump_json(indent=2)` — indented, because this file is meant to be read and diffed by people.
  A minified evalset shows up in a pull request as one changed line thousands of characters long.
- `exclude_none=True` drops fields nobody set, so the file carries what the cases actually say rather
  than a full skeleton of every optional field. It makes the file shorter and the diffs smaller, at
  the cost of a reader not seeing which fields exist — which is why this part lists them above.
- `encoding="utf-8"` explicitly. On Windows, `write_text` without it uses the system code page, and a
  reference answer with a rupee sign or an em dash in it comes back mangled on somebody else's
  machine.
- `load_eval_set_from_file` is **ADK's own loader**, from `local_eval_sets_manager`. Reading the file
  back with `json.load` would prove the file is valid JSON; reading it back with the loader proves it
  is a valid *evalset*, which is a different and much more useful claim.

Run it:

```bash
cd days/day-79-evals-are-tests/lab

```

**Line by line:**

- No flag writes the file and round-trips it. `--show` additionally prints one case's JSON, which is
  the block below.

```json
  "creation_timestamp": 0.0,

```

**Read that block as a person who does not write Python.** The question is there in plain text. The
expected answer is there in plain text. The tool it should call, and with what argument, is there. A
support lead could change "eleven days" to "eleven days — I'll chase it" and be confident they had
changed the right thing.

Note the fields the round-trip preserved and the ones it did not have to: `tool_responses` and
`intermediate_responses` are present and empty, because this fixture records what the desk *called*
and not what came back. That is a real limitation — a case cannot assert on what a tool returned — and
it is a consequence of building invocations by hand rather than capturing them, which is part
[2.2](2.2-recording-a-case-or-writing-one.md).

## When it breaks

Get the filename wrong and nothing tells you. The suffix is `.evalset.json`, and a file named
`triage.eval.json` or `triage_evalset.json` is simply **not listed** by the manager:

```python
if file.endswith(_EVAL_SET_FILE_EXTENSION):
```

That is the whole check, in `local_eval_sets_manager.py`. A file that does not match is skipped
silently — no warning, no error — so `adk eval` reports zero evalsets and the natural conclusion is
that something is wrong with the agent path.

The other common break is real and produces a real message. Hand-edit the JSON, leave a trailing
comma, and the pydantic loader refuses:

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for EvalSet
  Invalid JSON: trailing comma at line 42 column 5
```

That one is friendly: it names the line. The smallest fix for both is the same habit — **round-trip
the file after editing it**, which is what `cases.py` does on every run and what a pre-commit hook
should do:

```bash
uv run python -c "from google.adk.evaluation.local_eval_sets_manager import load_eval_set_from_file as l; print(len(l('triage.evalset.json','triage').eval_cases), 'cases load')"
```

**Line by line:**

- Loads the file with ADK's own loader and prints the case count. If it prints a number, the file is a
  valid evalset; if it raises, the message names the line.

## In production

**What a professional does with this file that a tutorial does not.** Splits it. One evalset per
capability — `refunds.evalset.json`, `signin.evalset.json` — rather than one file with four hundred
cases, because the `adk eval` CLI takes several files and because merge conflicts in a single shared
JSON file are miserable. The CLI's own syntax anticipates this: it accepts one or more paths, and
`file.json:eval_1,eval_2` runs a named subset.

**What degrades at scale.** The file gets large and stops being reviewable. A 5,971-byte file with six
cases extrapolates to roughly a megabyte at a thousand, and at that size no reviewer reads the diff —
they read the line count. The mitigation is the split above plus a rule that a pull request touching
reference answers has to say which case and why, in the message.

**The failure that only shows with real traffic.** Reference answers written from a fixture do not
contain what real inputs contain: customer names, order numbers, occasionally an email address that
somebody pasted into a ticket. The moment cases are recorded from real sessions — part
[2.2](2.2-recording-a-case-or-writing-one.md) — the evalset becomes a file full of customer data,
committed to a repository that Phase 14 makes public. Day 69's PII boundaries apply to this file and
nothing about its format enforces them.

**The review comment a senior engineer leaves:** *"Good — it round-trips through ADK's loader rather
than through `json.load`, which is the check that actually means something. Two asks. Split it before
it is one file: one per capability, matching how we would run a subset. And add a check that no case
contains an email address or an order number before this goes near the public repo, because the day
somebody records a case from a real session that check is the only thing standing between us and a
data leak in git history."*

**The interview question:** *"Why keep test cases in a data file rather than in the test code?"* The
answer that shows experience gets past "separation of concerns" to the real reason: the person who
knows the correct answer is usually not the person who writes the tests, and a data file is the only
format both of them can edit. The follow-up tell is whether they name the cost — no comments, no
logic, awkward for prose — rather than presenting it as free.
