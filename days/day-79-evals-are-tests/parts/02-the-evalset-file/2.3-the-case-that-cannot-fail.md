# 2.3 — The case that cannot fail

## One-line answer

💥 An agent that calls no tools at all and answers everything with one stock sentence **passes 2 of 3**
cases in a plausibly-written evalset — because a case with an empty expected trajectory and a generic
reference answer is not an assertion, it is a shape.

## The story

An exam paper with a question everybody gets right.

It is not a trick question and it is not badly written. It is something like *"State the capital of the
country."* Every single person in the hall writes the same three words, and every single one of them
gets the mark.

The examiner looks at the results afterwards and the column for that question is entirely full marks.
It has told him nothing whatsoever. He cannot use it to separate the person who studied from the person
who did not, which is the only thing an exam is for. Three minutes of everybody's time and one line of
everybody's paper, spent producing no information.

The paper is not wrong. Nothing about the question is incorrect. It just does not **discriminate**, and
a question that cannot separate anybody is not doing the job of a question, however true it is.

The uncomfortable part is that on the results sheet it looks exactly like a question everybody happened
to do well on.

## The idea in plain language

A case earns its place by being able to **fail against something worse than the real system**. If it
cannot, it is occupying a line in the suite and contributing nothing to any decision.

Two shapes make a case unable to fail, and both are things people write in good faith.

**An empty expected trajectory.** `tools=()` means "the agent should call nothing". That is a real,
useful assertion when it is deliberate — Sutra's `no_tool_needed` case is exactly this, and it exists
to catch a desk that reaches for a tool to answer "who are you?". It is *also* what you get when
somebody wrote a case for a question they did not think needed a tool, or captured a session where the
agent happened not to call one. Against an agent that calls nothing ever, an empty expected trajectory
scores **1.00**, every time. `tool_trajectory_avg_score` is an exact match and empty matches empty.

**A generic reference answer.** The metric on the answer is word overlap — part
[3.3](../03-two-metrics-that-cost-nothing/3.3-response-match-and-the-word-not.md) — so a reference made
of the words every answer contains scores high against almost anything. *"I can tell you what is
open"* is a reference that a stub matching those words passes at 1.00.

Put them together and you have a case that a completely inert process passes on both metrics. Its row
in the results is green, its presence in the file makes the suite look bigger, and it will never once
move.

The test that catches this has a name in ordinary testing and it is worth borrowing: **mutation
testing** — deliberately break the thing under test and check that the tests notice. Sutra met the
idea on [Day 30](../../../day-30-skill-testing-and-versioning/LESSON.md), and it is the same argument
Day 78's gate made with its red-alarm pass: *a criterion that passed must be able to fail*. Here the
mutation is not subtle. It is the most broken agent that can exist.

## Why Sutra needs it

Because Principle 11 says evals are tests, and a test that cannot go red is not one. Day 78 built that
check into its gate and found the design flaw it was looking for; this is the same check aimed at the
suite that Phase 12 is about to run every night for five days and then keep running for the rest of
the curriculum.

It matters most for cases that arrive later. Six hand-written cases with stated reasons are unlikely
to be vacuous. The seventieth case, added in a hurry after an incident, recorded from a session,
merged on a Friday — that is where this comes from, and by then nobody is re-reading the first six.

## The mechanism

The agent under test is one line, and it is the point:

```python
STUB_ANSWER = "I can tell you what is open."
...
stub = invocation("anything", [], STUB_ANSWER)
```

**Line by line:**

- `[]` for the tools: the stub calls nothing. Not "calls the wrong thing" — calls nothing at all. This
  is the worst agent that can exist while still returning something.
- `STUB_ANSWER` is a single sentence reused for every question, which is the other half of doing
  nothing: no lookup, no branching, no dependence on the input.
- It is built with the same `invocation` helper as everything else in the lab, so nothing about the
  scoring path is special-cased for it. The evaluators cannot tell it is a stub.

Two versions of the same three behaviours:

```python
LOOSE = [
    ("greeting", (), "I can tell you what is open."),
    ("capabilities", (), "I can tell you what is open and what needs you."),
    ("fallback", (), "I can tell you what is open, ask me anything."),
]

STRICT = [
    ("greeting", (), "I am the triage desk. Twelve tickets are open right now."),
    ("capabilities", (("category_counts", {}),), "Four sign-in, four billing, four export."),
    ("fallback", (("open_tickets", {}),), "Two tickets need you: 4688 and 4740."),
]
```

**Line by line:**

- `LOOSE` is not a strawman. Every one of those three reference answers is something a real desk might
  reasonably say, and somebody writing cases quickly would produce them. What makes them vacuous is
  not that they are wrong — it is that they contain no **fact the agent had to go and get**.
- `STRICT` keeps the same three case names and the same three behaviours, and changes the references so
  that answering requires a lookup. `"Twelve tickets are open right now"` needs a number. `"Four
  sign-in, four billing, four export"` needs the counts. `"4688 and 4740"` needs the queue.
- Two of the three `STRICT` cases also gain a **non-empty expected trajectory**, which is the other
  half of the fix. `greeting` deliberately keeps `()` — because a greeting genuinely should not call a
  tool — and is rescued by its reference answer alone. That asymmetry is worth noticing: the two
  defences are independent and a case needs at least one of them.

And the check itself:

```python
        both = t.overall_score >= 1.0 and r.overall_score >= 0.8
        verdict = "PASSED by the stub" if both else "goes red, as it should"
```

**Line by line:**

- A case survives only if the stub passes **both** metrics. Failing either is enough to make it a real
  case, which is a deliberately generous bar — the point is to find cases that assert nothing at all,
  not to grade them.
- The thresholds are ADK's own defaults, `1.0` and `0.8`, read from
  `google.adk.evaluation.eval_config`'s `_DEFAULT_EVAL_CONFIG` on the installed 2.7.1. Using the real
  defaults matters: a check like this run at made-up thresholds proves something about the check.

Run it against the loosely-written cases:

```bash
cd days/day-79-evals-are-tests/lab
uv run python always_green.py; echo "exit: $?"
```

**Line by line:**

- No flag uses `LOOSE` — the three cases as somebody first wrote them.

Measured on 2026-09-06:

```text
agent under test: no tools, always answers "I can tell you what is open."
cases: as somebody first wrote them

  case              traj  rouge  verdict
  greeting          1.00   1.00  PASSED by the stub
  capabilities      1.00   0.78  goes red, as it should
  fallback          1.00   0.82  PASSED by the stub

  2 of 3 cases are passed by an agent that does nothing
  a green suite made of these is a green suite about nothing
exit: 1
```

**Look at the `traj` column: 1.00 on all three.** The trajectory metric contributed nothing at all
here, because all three references expect no tools and the stub calls no tools. Every bit of
discrimination in this run came from the ROUGE column, and it only rescued one case — by 0.02, at
0.78 against a threshold of 0.80. That is not a defence, that is luck.

Now the same three behaviours, written so that answering them requires doing something:

```bash
uv run python always_green.py --strict; echo "exit: $?"
```

**Line by line:**

- `--strict` swaps `LOOSE` for `STRICT`. Same stub, same metrics, same thresholds, same case names.

Measured on 2026-09-06:

```text
cases: written so they can fail

  case              traj  rouge  verdict
  greeting          1.00   0.22  goes red, as it should
  capabilities      0.00   0.00  goes red, as it should
  fallback          0.00   0.14  goes red, as it should

  0 of 3 cases are passed by an agent that does nothing
  every case can tell the desk apart from a stub
exit: 0
```

`greeting` still scores **1.00 on the trajectory** — its reference legitimately expects no tools — and
is caught entirely by the answer, 0.22 against 0.80. The other two are caught by both. Three cases,
three different combinations of which metric did the work, and every one of them now separates the desk
from an empty process.

## When it breaks

There is no error and no traceback. What a vacuous case produces is this, in a suite of forty:

```text
  greeting           1.00  PASSED   []
```

— indistinguishable, in every column, from a case that passed because the desk is good.

The specific way it gets worse over time is worth naming, because it is not neglect. A case fails on a
Tuesday for a reason somebody judges acceptable. The fastest way to make it pass is to relax the
reference — take out the specific number, generalise the wording — and each relaxation is a small,
defensible edit made by somebody trying to unblock a deploy. The case does not become vacuous in one
step. It erodes, and there is no commit anywhere that says "this case now asserts nothing".

The smallest fix is to run this check as part of the suite rather than as an exercise:

```bash
uv run python always_green.py; echo "exit: $?"
```

Exit `1` means at least one case would be passed by a stub. Wired into CI, that is a build failure with
a name attached, and it fires on the commit that relaxes the case rather than six months later.

## In production

**What a professional writes instead of trusting the case set.** A stub agent in the test harness — the
smallest possible thing that returns a well-formed response — and an assertion that the full suite
**fails** against it. It is three lines of setup and it is the only structural defence against a suite
that has quietly stopped asserting. Some teams go further and keep two or three stubs: one that says
nothing, one that always calls every tool, one that echoes the question. Each catches a different shape
of vacuous case.

**What degrades at scale.** The bar rises. A stub that answers with one stock sentence is caught by
almost any specific reference, so a suite that passes this check is not thereby good — it is merely not
empty. The harder version, and the one worth building second, replaces the stub with **last month's
agent**: the suite should be able to distinguish the current system from the previous one, and a case
that cannot is a case that has stopped tracking anything.

**The failure that only shows with real traffic.** Vacuous cases cluster around the parts of the system
nobody understands well. The behaviours people can specify precisely get specific cases; the ones they
cannot get vague references — and those are exactly the behaviours most likely to break. So the suite's
weakest assertions sit over the system's least understood surface, which is the opposite of what anyone
would design on purpose.

**The review comment a senior engineer leaves:** *"Add the stub check to CI now, not later. And when a
case fails and we decide the new behaviour is fine, the rule is that we change the reference to the new
**specific** answer, never to a vaguer one — if we cannot state what the answer should be, that is a
signal to talk about the feature, not to soften the test."*

**The interview question:** *"How do you know your tests are actually testing anything?"* The answer
that shows experience names a deliberate mutation — break the code, or run against a stub, and check
the suite goes red. The tell is whether they have actually run it, because everybody who has can name
which of their tests survived, and it is always more than they expected.
