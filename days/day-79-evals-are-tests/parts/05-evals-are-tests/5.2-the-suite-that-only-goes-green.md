# 5.2 — The suite that only goes green

## One-line answer

💥 An eval suite has four independent ways to become permanently green — vacuous cases, a threshold
that drifted, a metric removed from a config, and a `live` marker nobody runs — and every one of them
produces the same reassuring line, so the only defence is a check that the suite can still fail.

## The story

The weighing scale at the front of the chemist's shop.

It has been there for years. You step on, put in a coin, and it prints a slip. People use it. It is
part of the routine — one of those things you do while waiting for the prescription.

At some point, and nobody knows when, it stopped weighing. The needle rests where it rests, the
mechanism prints, and the number on the slip is always about the same. Nobody noticed, because the
number it prints is plausible. It is not zero, it is not four hundred; it is roughly what a person
weighs, and if it is a kilo off from what you expected, well, scales differ.

The thing to sit with is that this scale is worse than no scale at all. A shop with no scale sends you
to find one. A shop with a broken scale sends you home reassured, and does it every single time, and
the more you trust it the more that costs.

You could find out in ten seconds. Step off it and see whether it goes back to zero.

## The idea in plain language

Part [2.3](../02-the-evalset-file/2.3-the-case-that-cannot-fail.md) showed one way an eval suite stops
asserting: a case whose reference is so loose that a stub passes it. That is one of four, and the four
are worth enumerating because they arrive by different routes and are fixed by different things.

**Vacuous cases.** An empty expected trajectory and a generic reference answer. Measured in part
[2.3](../02-the-evalset-file/2.3-the-case-that-cannot-fail.md): 2 of 3 plausibly-written cases passed
by an agent that calls nothing and says one stock sentence.

**A threshold that drifted.** Part
[3.4](../03-two-metrics-that-cost-nothing/3.4-the-threshold-is-the-test.md)'s subject. Each individual
lowering is defensible; the cumulative effect is not recorded anywhere. Part
[3.3](../03-two-metrics-that-cost-nothing/3.3-response-match-and-the-word-not.md) measured the extreme
case: at a `response_match_score` threshold of 0.35, every one of six correct rewordings passes — and
so does every one of six answers that say the opposite.

**A metric removed from a config.** Also part
[3.4](../03-two-metrics-that-cost-nothing/3.4-the-threshold-is-the-test.md)'s, and the most invisible
of the four: `get_evaluation_criteria_or_default` returns the file's config **instead of** the
defaults, so a `test_config.json` listing one metric has switched the other off. Verified on
`google-adk==2.7.1` — a config containing only `response_match_score` resolves to
`{'response_match_score': 0.5}` and nothing else.

**A suite nobody runs.** Part [5.1](5.1-running-them-from-pytest.md)'s live marker. `./m check` runs
`pytest -m "not live"`, so a `@pytest.mark.live` eval is skipped every time and reports as skipped,
which in a `-q` summary is a number most people do not read. And an `async def` test with no async
plugin — this repository has no `pytest-asyncio`, confirmed by
`ModuleNotFoundError: No module named 'pytest_asyncio'` on 2026-09-06 — may not run at all while still
not failing.

Four routes, one destination, and the destination looks like this:

```text
  6 of 6 cases at or above 1.0
```

That line is what a healthy suite prints. It is also what all four of these print. **There is no
observation you can make of a passing run that distinguishes them**, which is why the defence cannot be
vigilance. It has to be an experiment.

The experiment is the one from the story: **step off the scale and check it returns to zero.** Make
the system worse on purpose and require the suite to notice. It has three names depending on who you
learned it from — mutation testing, fault injection, a red-alarm test — and Sutra has now met it three
times: [Day 30](../../../day-30-skill-testing-and-versioning/LESSON.md) for skills, Day 78's gate for
phase criteria, and here for evals.

## Why Sutra needs it

Because this suite is about to be scheduled. Day 82 puts it in CI and on Day 73's nightly, and a
scheduled suite is the exact circumstance in which nobody looks at a green result — which is what
[Day 73 part 3.2](../../../day-73-ambient-agents/parts/03-the-morning-after/3.2-the-digest-that-reassures.md)
called the digest that reassures: its failure mode is not being wrong, it is being reassuring.

There is also a specific, current risk. Every arm of this day's lab that goes red does so because
somebody wrote an ablation flag. Take those away — as a real project would, since `--buggy` is not
something a production desk has — and there is nothing left that has been *seen* to fail. Part
[5.1](5.1-running-them-from-pytest.md)'s recorded-invocation test asserts on the failure path for
exactly this reason.

## The mechanism

The check is one command per suite, and Sutra's is already written. From `always_green.py`:

```python
    stub = invocation("anything", [], STUB_ANSWER)
    ...
        both = t.overall_score >= 1.0 and r.overall_score >= 0.8
        verdict = "PASSED by the stub" if both else "goes red, as it should"
```

**Line by line:**

- `invocation("anything", [], STUB_ANSWER)` builds the worst agent that still returns something: no
  tools, one stock sentence, no dependence on the input. It is deliberately not "an agent with a bug" —
  a bug is specific and a stub is general, and a suite that cannot beat a stub cannot beat anything.
- The stub is scored by **both** metrics, at ADK's real defaults, and survives only if it passes both.
  A generous bar on purpose: the check is looking for cases that assert nothing at all.
- The verdict string is written from the case's point of view — `"goes red, as it should"` — because
  this script inverts the usual reading. A red case here is a healthy case.

Run it against the deliberately loose cases:

```bash
cd days/day-79-evals-are-tests/lab
uv run python always_green.py; echo "exit: $?"
```

**Line by line:**

- No flag: three cases written the way somebody writes them in a hurry.

Measured on 2026-09-06:

```text
  case              traj  rouge  verdict
  greeting          1.00   1.00  PASSED by the stub
  capabilities      1.00   0.78  goes red, as it should
  fallback          1.00   0.82  goes red, as it should

  2 of 3 cases are passed by an agent that does nothing
  a green suite made of these is a green suite about nothing
exit: 1
```

Now the four routes, each demonstrated by a command that already exists in this lab. This is the whole
section in one block:

```bash
uv run python always_green.py; echo "vacuous cases:    $?"
uv run python respmatch.py --negated; echo "loose threshold:  $?"
uv run python -c "
from google.adk.evaluation.eval_config import get_evaluation_criteria_or_default
print(get_evaluation_criteria_or_default('test_config.json').criteria)"
uv run python -m pytest -q -m 'not live' 2>&1 | tail -1
```

**Line by line:**

- `always_green.py` exits `1` when a case would be passed by a stub — route one, as a command.
- `respmatch.py --negated` exits `1` when wrong answers score above the threshold — route two, measured
  in part [3.3](../03-two-metrics-that-cost-nothing/3.3-response-match-and-the-word-not.md) at 5 of 6.
- The `get_evaluation_criteria_or_default` line prints exactly which metrics a config resolves to —
  route three, and the only way to see a metric that has been dropped.
- The last line is Sutra's own default test command; its summary counts skipped tests, which is where a
  `live`-marked eval hides — route four.

Measured on 2026-09-06, the last two of those:

```text
{'tool_trajectory_avg_score': 1.0, 'response_match_score': 0.8}
32 passed, 2 deselected, 1 warning in 2.08s
```

**Read `2 deselected`.** Two tests in this repository are marked `live` and were not run. That number
is in the summary of every single test run and is one of the least-read numbers in software. It is not
a problem today — those two tests genuinely need a model — and it is exactly where an eval suite goes
to become permanently green.

## When it breaks

The check itself can go green while meaning nothing, and it is worth being explicit about the limit.

`always_green.py` compares the suite against **a stub**, which is a very low bar. A suite that beats a
stub has proved it is not empty; it has not proved it can detect a subtle regression. The harder
version — and the second thing to build — replaces the stub with **last month's agent**, and requires
the suite to distinguish the two. A case that cannot tell this month's desk from last month's has
stopped tracking anything, and no stub check will ever say so.

There is also a route this section does not cover and part
[2.2](../02-the-evalset-file/2.2-recording-a-case-or-writing-one.md) does: a suite whose references
were **recorded from the system's own output** passes by construction on the day it is made and
thereafter fails only on change. That is a fifth way to be permanently green, and it is not detectable
by any check on the suite — only by asking where the cases came from.

The smallest fix for all of it is one line in CI, next to the suite it guards:

```bash
uv run python always_green.py || exit 1
```

**Line by line:**

- Exits the build when any case would be passed by a stub. Placed **before** the eval run in the CI
  script, so the question "can this suite fail?" is answered before the question "did it?".

## In production

**What a professional writes instead of trusting a green board.** A scheduled adversarial run: the
suite executed against a deliberately degraded system, on a cadence, with the **expected** result being
red. Some teams do it weekly with a stub; the good ones keep a small library of degraded agents — one
that skips tools, one that truncates answers, one that is last quarter's model — and assert that each
is caught by at least one case. It is the same idea as a fire drill and it is run for the same reason.

**What degrades over time.** All four routes are one-way. Thresholds go down, never up. Cases get
looser, never tighter. Metrics get removed from configs and not added back. Tests get marked `live` and
not unmarked. There is no natural pressure in the other direction, because every individual loosening
unblocks somebody and every tightening blocks somebody. Only a periodic check pushes back, and it has
to be automated, because the manual version is the thing that has already failed.

**The failure that only shows with real traffic.** A suite that has genuinely never gone red might be
correct. Sutra's desk is small and well-specified, and six cases passing might mean six behaviours
work. The honest signal is not "has it ever failed" but "**can** it fail", and the only way to answer
that is to make it fail on purpose. Teams conflate the two and reason from the first, which is why a
suite that has been green for a year gets described as reliable rather than as unexamined.

**The review comment a senior engineer leaves:** *"Put `always_green.py` in CI in front of the eval run.
And whenever we lower a threshold, the pull request has to name the case that prompted it, in the
message — not because anybody will read it later, but because having to write the sentence is what makes
somebody notice they are doing it for the fourth time."*

**The interview question:** *"Your evaluation suite has never failed. What do you do?"* The answer that
shows experience does not celebrate and does not panic — it runs the suite against something known to
be broken and reports what happened. The tell is whether they name what they would break: a stub, an
older model, a deliberately wrong tool call. A candidate who says "that's a good sign" has not had a
green suite lie to them yet.
