# 1.1 — A test that answers how much

## One-line answer

An eval is an ordinary test with one thing changed: the comparison returns **a number between 0 and
1** instead of true or false, and the assertion is a **threshold** you had to choose — which means
somebody made a judgement, once, and wrote it down where it can be argued with.

## The story

The milk collection centre at half past six in the morning.

Everybody brings their can. There is a man with a machine, and the machine is not asking whether the
milk is good. That is not a question it can answer. What it does is measure the fat — a number,
printed on a slip, something like 4.2.

The rate is decided by that number. Above a line, you get one rate. Below it, another. The line is
written on a board on the wall and everybody in the queue knows it.

Two things about this arrangement are worth noticing, and they are the whole of this part.

The first is that nobody argues about the *measurement*. The machine says 4.2 and that is what it
says. People do sometimes argue about the line — whether it should be where it is, whether it is fair
on the buffalo milk versus the cow milk — and that is a completely different kind of argument, held
with the society, in the evening, not with the man and his machine at six in the morning.

The second is that the line had to come from somewhere. Somebody chose it. It is not a property of
milk. It could have been higher and it could have been lower, and wherever it is, it is a decision
that somebody has to be able to defend.

## The idea in plain language

Sutra has had tests since [Day 23](../../../day-23-testing-tools-and-callbacks/LESSON.md). A test
does one thing: it runs some code and asserts something. The assertion is a boolean —
`assert result == expected` — and it is either satisfied or it is not.

That works when the correct answer is one exact thing. `parse_ticket_id("#4740") == "4740"` has
exactly one right answer, and anything else is wrong.

It stops working the moment the thing under test can be **right in more than one way**. There is no
single correct sentence for *how long has 4740 been open?* — "Ticket 4740 has been open for eleven
days", "It's been eleven days", "Since the eleventh" are all correct, and an equality assertion
against any one of them fails the other two.

An **eval** is the shape you reach for then. Three words, and the third is the one people skip:

- a **case** is one thing the system is supposed to get right: an input, and what a correct response
  looks like. It is the eval word for what a test calls a test.
- a **metric** is a function that takes what the system actually did and what the case said, and
  returns **a score** — a number, conventionally between 0 and 1, where 1 is a perfect match.
- a **threshold** is the score at or above which the case counts as passed. It turns the number back
  into a boolean, which is what lets an eval suite have an exit code.

The threshold is where the judgement lives, and it is worth being blunt about that. `assert x == y`
contains no opinion. `assert score >= 0.8` contains somebody's opinion about how close is close
enough, and that opinion is now a line in a config file that will outlive the person who typed it.
This is not a weakness of evals — it is the honest form of a decision that was being made anyway,
usually silently, by whoever wrote the test.

A second difference follows from the first, and it changes how you read results. A boolean test is
green or red. An eval suite has a **distribution**: six cases with six scores, and the interesting
information is often not the pass count but which case scored 0.79 and which scored 0.12. Part
[3.4](../03-two-metrics-that-cost-nothing/3.4-the-threshold-is-the-test.md) is about reading that.

| | A test | An eval |
| --- | --- | --- |
| The comparison returns | true or false | a score, usually 0 to 1 |
| The assertion is | equality, or a predicate | a threshold somebody chose |
| A near-miss looks like | a failure, identical to any other | 0.79 against a line at 0.8 |
| It can go red because | the code changed | the code changed, **or the model did** |
| What ages | the code it tests | the threshold, and the reference answers |

The last row is the one that catches teams out. Evals are the only tests in the repository whose
correct answer can drift without anybody editing anything, because one of their inputs is a model
that somebody else updates.

## Why Sutra needs it

Because Principle 11 says **evals are tests** — every day ends with at least one check that can go
red — and until now Sutra's checks have all been the boolean kind. The desk's tool functions, the MCP
handlers, the graph nodes and the quota ledger are all things with exactly one right answer, and
`assert` has been enough.

The desk's *answers* are not. Nothing in this repository currently asserts anything about what the
triage desk actually says to a person, because there was no shape to assert it in. This day is that
shape, and the next four days build on it: Day 80 adds rubric-based trajectory evaluation, Day 81
adds an LLM as the judge, and Day 82 puts the whole suite in CI.

It also matters for the gate you have just come from. Day 78's criterion 3 could not decide whether
Phase 11 fits inside a free-tier allowance, and part
[4.1](../04-what-it-costs-to-run/4.1-the-metrics-that-spend-nothing.md) shows why an eval suite is the
thing that makes that question urgent: the suite is about to become the largest scheduled consumer of
requests in the whole system.

## The mechanism

An evaluator is a function from *(what happened, what should have happened)* to a score. Here is one,
run against Sutra's desk, with no model anywhere:

```python
evaluator = TrajectoryEvaluator(threshold=THRESHOLD)
result = evaluator.evaluate_invocations(
    actual_invocations=[actual], expected_invocations=[expected(case)]
)
```

**Line by line:**

- `TrajectoryEvaluator` is one of ADK's built-in evaluators, imported from
  `google.adk.evaluation.trajectory_evaluator`. Verified against `adk.dev/evaluate/` on 2026-09-06
  and against the installed `google-adk==2.7.1`, where its constructor is
  `__init__(self, threshold: Optional[float] = None, eval_metric: Optional[EvalMetric] = None)`.
- `threshold=THRESHOLD` is the line on the board. It is a constructor argument rather than a global,
  because the same metric is used with different lines in different places — part
  [3.4](../03-two-metrics-that-cost-nothing/3.4-the-threshold-is-the-test.md).
- `evaluate_invocations` takes **two lists**: what the agent did, and what the case says it should
  have done. Both are lists because a case may be a multi-turn conversation; today every case is one
  turn, so both lists have one element.
- The keyword arguments are named in the call rather than passed positionally. That is not style: the
  two arguments are the same type and swapping them silently produces a different, plausible-looking
  score.
- Nothing here is `await`ed and nothing here has a network client in it. This evaluator compares two
  recorded structures, which is why the whole of today costs zero requests.

What comes back is not a number:

```python
print(f"  {case.eval_id:<16}{result.overall_score:>7.2f}  {status:<8} {called}")
```

**Line by line:**

- `result` is an `EvaluationResult`, whose fields on `google-adk==2.7.1` are `overall_score`,
  `overall_eval_status`, `per_invocation_results` and `overall_rubric_scores`.
- `overall_score` is the number. `overall_eval_status` is the number already compared against the
  threshold, as an `EvalStatus` — `PASSED`, `FAILED` or `NOT_EVALUATED`. **Both are returned**, which
  is the library making the same point this part is making: the score and the verdict are different
  things and a caller may want either.
- `NOT_EVALUATED` being a third status is worth noticing on the day after Day 78 spent a whole part
  arguing that "cannot determine" deserves its own value. The library agrees.

Run it:

```bash

```

**Line by line:**

- `cd` first: every script in this lab imports `_desk` by plain name, the same convention days 73 to
  78 use.

Measured on 2026-09-06:

Six scores and six statuses. The scores happen to be 1.00 here because this metric is an exact match —
part [3.1](../03-two-metrics-that-cost-nothing/3.1-tool-trajectory-avg-score.md) — but the shape is
the general one, and part [3.3](../03-two-metrics-that-cost-nothing/3.3-response-match-and-the-word-not.md)

## When it breaks

The characteristic failure of an eval is not an exception. It is a **score you did not look at**.

Run the same suite against a desk with two real faults injected:

```bash
uv run python trajectory.py --buggy; echo "exit: $?"
```

**Line by line:**

- `--buggy` makes the desk read the whole queue before answering a question about one ticket, and say
  the standup's two facts in the wrong order. Both are changes a reasonable person might make.

Measured on 2026-09-06:

```text
  case              score  status   tools called
  counts             1.00  PASSED   ['category_counts']
  age_4740           1.00  PASSED   ['ticket']
  needs_person       1.00  PASSED   ['open_tickets']
  one_lookup         0.00  FAILED   ['open_tickets', 'ticket']
  order_matters      0.00  FAILED   ['category_counts', 'open_tickets']
  no_tool_needed     1.00  PASSED   []

  4 of 6 cases at or above 1.0
  2 case(s) took a different path from the one written down
exit: 1
```

`4 of 6` is the number a summary reports, and a team watching a pass rate would see it move from
100% to 67% and open a ticket. What tells you what actually happened is the **score column**, and the
two zeros in it: this metric scores 0.00 for a trajectory that differs at all, so a case that made one
extra tool call and a case that made the same two calls in the wrong order are indistinguishable in
the number. Only the `tools called` column separates them.

The general error to name: **an aggregated eval result destroys the information you needed.** Six
scores became "4 of 6" became "67%", and by the third form there is nothing left to act on. Whatever
you build, keep the per-case scores.

## In production

**What a professional writes instead of a pass count.** A results file with one row per case per
metric — case id, metric, score, threshold, verdict, and the run's date and model version — and a
dashboard that shows the *scores over time*, not the pass rate. The reason is that a case drifting
from 0.95 to 0.84 over three months is a real signal and is invisible in any boolean view of the same
data, right up to the day it crosses 0.8 and looks like a sudden regression.

**What degrades at scale.** Thresholds get tuned, always in the same direction. A case fails, somebody
looks at it, decides the answer was actually fine, and lowers the threshold. Each decision is
reasonable. Nothing records that the suite got weaker, because the diff shows a number changing from
0.8 to 0.7 and no reviewer can tell whether that is a fix or a surrender. The defence is to make a
threshold change require a sentence — in the config, next to the number — saying which case prompted
it.

**The failure that only shows with real traffic.** The reference answers age. A case written when the
desk said "eleven days" keeps expecting "eleven days" after somebody improves the desk to say "since
the 26th of August". Every score drops, nothing is broken, and the suite reports a regression on the
day the product got better. Evals fail in this direction far more often than they catch real bugs, and
a team that has not been warned about it stops trusting the suite in about a month.

**The review comment a senior engineer leaves:** *"Two things. Print the score next to the verdict
everywhere, including in CI — 'FAILED' on its own sends people to run it locally, and '0.79 against
0.8' sends them to the right place. And put the threshold in a config file rather than in the
constructor call, so that changing it shows up in a diff somebody reviews rather than inside a
function nobody reads."*

**The interview question:** *"How do you test something that can be right in more than one way?"* The
answer that shows experience does not jump to LLM judges. It says: score it, choose a threshold,
**and be able to defend the threshold** — and then names what the score cannot see, because every
scoring function has a blind spot and the useful engineer knows theirs. Part
[3.3](../03-two-metrics-that-cost-nothing/3.3-response-match-and-the-word-not.md) is Sutra's.
