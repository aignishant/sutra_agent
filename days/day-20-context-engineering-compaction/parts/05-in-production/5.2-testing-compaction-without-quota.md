# 5.2 — Testing compaction without spending quota

## One-line answer

Both models can be fakes, so compaction is fully testable with **no key, no network and no quota** —
and the suite goes RED the moment the config is dropped, which is the only way you will ever notice
that it was.

## The story

The building does a fire drill on the first Wednesday of the month.

Nothing is on fire. That is the entire point. You find out that the stairwell door sticks, that the
new starter on the second floor did not know where the assembly point was, and that the alarm on the
top floor is quieter than it should be — and you find all of it out on a Wednesday morning, with
everyone holding a coffee.

The alternative is finding out the same three things during a fire.

## The idea in plain language

Compaction is unusually easy to test properly, and the reason is a design detail from
[2.1](../02-the-config/2.1-one-config-on-the-app.md): both models involved are ordinary `BaseLlm`
objects that you supply.

The chat model can be a **recorder** — it answers instantly with a fixed string and keeps every
request it was sent, which is what lets a test assert on the window rather than on the reply. That is
yesterday's technique
([19.6.1](../../../day-19-context-engineering-selection/parts/06-in-production/6.1-testing-what-goes-in-the-window.md)).

The summarizer can be a **fixed** model — it always writes the same summary. That is today's
addition, and it matters more than it looks: a real summarizer is non-deterministic, so a test built
on one is a test that fails occasionally for reasons unrelated to your code. A fixed summary makes the
whole mechanism deterministic while leaving every structural fact — where the summary lands, what it
replaces, what the archive does — completely real.

What you can then assert falls into three groups, and the third is the one people miss.

1. **That it happened.** A compaction event exists, the window is smaller, the archive is bigger.
2. **That it has the right shape.** The summary is in `actions.compaction`, not in `content`; the
   author is `user`; the config with half a trigger is refused.
3. **That the loss you accepted is the loss you got.** The constraint is in the window without
   compaction and absent with it — the failure from
   [4.2](../04-failure-lab/4.2-the-fact-that-was-true-and-is-now-gone.md), pinned as a test so it is a
   documented trade rather than a surprise.

The third group is the interesting one because the assertion is `not in`. It is a test that something
is **missing**, and those are exactly the tests that pass for the wrong reason — a typo in the probe
makes it pass forever. The defence is to assert the presence in the same test, on the uncompacted run,
so the probe is proved to match before it is asked to fail to match.

## Why Sutra needs it

Because compaction is the first feature Sutra has that is **invisible when it silently stops working**.

Every previous failure in this phase announced itself. A missing artifact service raises
([18.5.1](../../../day-18-artifacts-that-survive/parts/05-failure-lab/5.1-the-artifact-with-no-service.md)).
A missing state key raises
([17.4.2](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.2-the-brace-that-raises.md)).
Compaction that stops happening produces correct answers, slightly slower and more expensive, until a
quota runs out. There is no error to catch; there is only a test that used to pass.

And it is the cheapest possible test to run, which decides whether it stays in the suite. `./m check`
runs on every change, and any test needing a key or a network call gets marked `live` and skipped —
so it never runs and never protects anything. These run in the default suite, every time.

## The mechanism

Five tests, and the fifth is parametrised over three broken configs.

```python
# days/day-20-context-engineering-compaction/lab/test_compaction_demo.py
"""Compaction, asserted rather than eyeballed - and with no key and no network."""


async def _converse(compact: bool):
    """Run TURNS once and return (the recorded requests, the session's events)."""
    SENT.clear()
    agent = Agent(name="desk", model=Recorder(model="recorder"), instruction="You are Sutra.")
    app = (
        App(
            name="sutra",
            root_agent=agent,
            events_compaction_config=EventsCompactionConfig(
                compaction_interval=2,
                overlap_size=1,
                summarizer=LlmEventSummarizer(llm=Fixed(model="minute-taker")),
            ),
        )
        if compact
        else App(name="sutra", root_agent=agent)
    )
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=app, session_service=service)
    for turn in TURNS:
        await asyncio.sleep(0.05)
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=turn)]),
        ):
            pass
    record = await service.get_session(app_name="sutra", user_id="priya", session_id=session.id)
    return list(SENT), record.events


def test_compaction_shrinks_the_window() -> None:
    """The saving is real: the last request is smaller with compaction than without."""
    plain, _ = asyncio.run(_converse(compact=False))
    compacted, _ = asyncio.run(_converse(compact=True))
    assert len(compacted[-1].contents) < len(plain[-1].contents)


def test_a_summary_event_is_appended_not_substituted() -> None:
    """The archive grows: compaction adds events, it never removes them."""
    _, plain_events = asyncio.run(_converse(compact=False))
    _, compacted_events = asyncio.run(_converse(compact=True))
    summaries = [e for e in compacted_events if e.actions and e.actions.compaction]
    assert summaries, "no compaction event was produced at all"
    assert len(compacted_events) == len(plain_events) + len(summaries)


def test_the_summary_is_not_in_the_event_content() -> None:
    """The trap from 3.1, pinned so a refactor cannot quietly reintroduce it."""
    _, events = asyncio.run(_converse(compact=True))
    summary = next(e for e in events if e.actions and e.actions.compaction)
    assert summary.content is None
    assert summary.author == "user"
    assert SUMMARY in summary.actions.compaction.compacted_content.parts[0].text


def test_the_constraint_leaves_the_window() -> None:
    """The failure from 4.2, asserted: present without compaction, absent with it."""
    plain, _ = asyncio.run(_converse(compact=False))
    compacted, _ = asyncio.run(_converse(compact=True))
    assert FACT in str(plain[-1].contents), "the probe does not match the text as written"
    assert FACT not in str(compacted[-1].contents)


@pytest.mark.parametrize("bad", [{"compaction_interval": 3}, {"token_threshold": 4000}, {}])
def test_half_a_trigger_is_refused(bad: dict) -> None:
    """Each trigger is a pair, and an incomplete config must not be constructible."""
    with pytest.raises(ValueError):
        EventsCompactionConfig(**bad)
```

**Line by line:**

- `_converse(compact)` is the **one** place the two worlds differ, so no test can accidentally compare
  two things that also differ in some other way. It returns both the requests and the events, because
  half the assertions are about the window and half are about the archive.
- `asyncio.run(_converse(...))` from a synchronous test rather than `pytest.mark.asyncio`. It keeps the
  file free of a plugin dependency, and each call gets a clean event loop, which suits a test that
  builds a fresh runner anyway.
- `assert len(compacted[-1].contents) < len(plain[-1].contents)` — a **relative** assertion. Asserting
  an exact message count would break on any change to the turns, and the claim is not "four messages",
  it is "fewer".
- `assert summaries, "no compaction event was produced at all"` — the guard before the real assertion.
  Without it, a run where compaction never fired would make `summaries` empty, the arithmetic in the
  next line would read `len(plain) == len(plain) + 0`, and the test would **pass while measuring
  nothing**.
- `len(compacted_events) == len(plain_events) + len(summaries)` is the append claim from
  [3.3](../03-reading-the-record/3.3-the-archive-is-still-whole.md) stated exactly: every summary is an
  addition, and nothing was removed to make room for it.
- `assert FACT in str(plain[-1].contents)` before `assert FACT not in ...` — the presence check that
  makes the absence check trustworthy, with a message that says what a failure means.
- `@pytest.mark.parametrize` over three broken configs, so each one is a separately named test and a
  failure says which config stopped being rejected.
- `pytest.raises(ValueError)` rather than `pydantic.ValidationError` — `ValidationError` subclasses
  `ValueError`, and asserting the more general type keeps the test from breaking on a pydantic upgrade
  that is not the thing under test.

**Line by line:**

- Sixteen turns and several summaries across the five tests, all against fakes: no key, no network,
  no quota.

Measured on `google-adk` 2.7.1 with `pytest` 9.1.1 on 2026-09-03:

```text
.......                                                                  [100%]
7 passed
```

Seven, because the parametrised test counts as three.

**Now make it fail.** Change `if compact` to `if False` in `_converse`, so the compacted run quietly
gets a plain `App` — which is exactly what happens when somebody constructs the `Runner` with `agent=`
instead of `app=`:

```text
FFFF...                                                                  [100%]
test_compaction_demo.py:82: AssertionError: assert 7 < 7
test_compaction_demo.py:90: AssertionError: no compaction event was produced at all
test_compaction_demo.py:97: StopIteration
test_compaction_demo.py:108: assert 'do not close the ticket' not in "[Content(\n...e='user'\n)]"

FAILED test_compaction_demo.py::test_compaction_shrinks_the_window
FAILED test_compaction_demo.py::test_a_summary_event_is_appended_not_substituted
FAILED test_compaction_demo.py::test_the_summary_is_not_in_the_event_content
FAILED test_compaction_demo.py::test_the_constraint_leaves_the_window
```

**Four red, three green,** and the three that stayed green are the config-validation ones — correctly,
because they never touch the `App`. A suite where *everything* goes red on one change is a suite that
is testing one thing several times.

Three of the four messages are excellent. `assert 7 < 7` says the window did not shrink. *"no
compaction event was produced at all"* says precisely what happened. The `not in` assertion failing
says the constraint is still in the window, which — read carefully — is the *good* outcome for the
user and the correct failure for a test that is checking a documented trade-off.

**And one message is bad, which is worth keeping.** `StopIteration` at line 97 is
`next(e for e in events if ...)` running out of events, and it tells you nothing about what was
expected. The fix is `next((e for e in ... ), None)` and an assertion with a message — and the reason
to leave it here rather than silently correct it is that this is the second time in two days that
breaking a passing test on purpose has exposed a weak assertion. Yesterday's
[19.6.1](../../../day-19-context-engineering-selection/parts/06-in-production/6.1-testing-what-goes-in-the-window.md)
found two of them. **Running the suite red is how you review the suite.**

## When it breaks

**The fake summarizer drifts from the real one.** These tests prove the plumbing: that compaction
fires, where the summary lands, what it replaces. They prove **nothing** about summary quality,
because the summary is a constant. A test suite that is entirely green here is compatible with a
summarizer that produces useless summaries in production, and it is important to be honest about which
half of the problem this covers.

**And the timestamp hazard from [2.2](../02-the-config/2.2-the-turn-count-trigger.md) shows up here
first**, because a test suite is precisely where models answer instantly. Without the
`await asyncio.sleep(0.05)`, event timestamps collide, compaction fires an unpredictable number of
times, and the suite becomes intermittently red for a reason that has nothing to do with the code
under test. A flaky test gets deleted, and deleting this one removes the only thing that notices when
compaction stops happening.

## In production

**Put these in the default suite, never behind a `live` marker.** They need no key, and that is a
deliberate design property rather than a happy accident: the two seams that could have required a
network — the chat model and the summarizer — are both injectable. When a feature is hard to test
without a network, the first question is whether the seam is in the wrong place.

**What changes at scale** is that you also want the other half: a small, separately-marked suite that
runs the *real* summarizer against a handful of fixed transcripts and checks that named facts survive.
That one costs quota and belongs on a schedule rather than on every commit, which is Day 79's eval
work. The split — structure tested for free on every change, quality tested with real models on a
schedule — is the shape most mature agent test suites end up with.

**The failure that only appears with real traffic** is still the summary-quality one, and no amount of
this kind of test will find it. What these tests buy is the guarantee that when you go looking for a
quality problem, the plumbing underneath is known-good.

**The review comment a senior engineer leaves:** *"good tests, but `test_the_constraint_leaves_the_window`
is asserting our data-loss behaviour is still happening. Rename it so nobody 'fixes' it — it's a
documented trade, not a bug we've accepted quietly."*

**The interview question:** *"how do you test a feature that only triggers after several turns and
calls an LLM to do its work?"* The answer that shows you have written it: *"inject fakes at both
seams. A recording model for the conversation so I can assert on the request, and a fixed-text
summarizer so the run is deterministic. That makes every structural claim testable with no key and no
quota — and then I break the config on purpose and check the suite actually goes red, because the
failure mode here is silence."*
