# 1.4 — What must never be summarized

## One-line answer

Anything that must still be true on turn forty belongs in **state** or an **artifact**, not in the
conversation, because the conversation is the only part of the window that compaction is allowed to
rewrite.

## The story

The pharmacist reads the prescription back to you at the counter.

Not all of it. They do not read the doctor's letterhead or the date or the scribble about the
follow-up appointment. They read one thing exactly as written: *one tablet, twice a day, after
food*.

Everything else on that page can be paraphrased, shortened, or left out entirely and nobody is
harmed. That one line is copied character for character every time it moves — from the doctor's pad
to the label on the box to the words said out loud at the counter — because a paraphrase of a dose
is not a dose.

The skill is not "be careful with the whole page". It is knowing which line is the dose.

## The idea in plain language

By now Sutra has three places to keep something, and until today the difference between them was
mostly about lifetime and size. Compaction adds a sharper reason to choose correctly, because it
treats the three places completely differently.

| Where it lives | Introduced | What compaction does to it |
| --- | --- | --- |
| **the conversation** — said in a turn | [Day 3](../../../day-03-loop-hand-rolled/LESSON.md) | may be replaced by a summary at any point |
| **session state** — a key in `session.state` | [Day 17](../../../day-17-state-scopes-and-lifetimes/LESSON.md) | untouched; re-rendered into the instruction on every call |
| **an artifact** — bytes with a name and a version | [Day 18](../../../day-18-artifacts-that-survive/LESSON.md) | untouched; never in the window unless a tool fetches it |

The middle row is the one to internalise. A state key reaches the model through a **placeholder** in
the instruction — the `{key}` templating from
[17.4.1](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.1-state-steers-the-next-turn.md)
— and the instruction is *rebuilt from scratch before every single call*. It is not history. It was
never in the event log. Compaction cannot reach it, because compaction only ever rewrites events.

So the rule that governs the rest of Sutra's design is:

> **If losing it would make Sutra do the wrong thing, it does not live in prose.**

Three tests to apply to any fact, in order:

1. **Will it still matter in twenty turns?** If yes, it is not conversation. A browser version
   mentioned once, an escalation flag, an account tier, a promise made to the customer.
2. **Would a paraphrase change what Sutra does?** If yes, it is a dose. *Do not close* and *close
   when resolved* paraphrase into each other very easily.
3. **Is it bigger than a sentence?** Then it is an artifact, not a state key — the log file, the
   uploaded screenshot, the config dump. State holds facts; artifacts hold bytes
   ([18.1.1](../../../day-18-artifacts-that-survive/parts/01-not-a-state-key/1.1-the-thing-state-cannot-hold.md)).

Everything that passes all three tests can stay in the conversation, be summarized, and be partly
lost, and none of it will hurt. That is what conversation is *for*: the narrative that makes the
facts make sense.

## Why Sutra needs it

Because this is the design decision that makes the rest of Phase 3 hold together, and it is the one
a reader is most likely to skip.

Day 17 built state and Day 18 built artifacts, and at the time the honest answer to *"why not just
say it in the conversation?"* was "tidiness". Today there is a real answer: the conversation is
lossy by design from now on, and the other two are not.

Day 21 makes it sharper still. When a tool fails and the error has to survive to the end of the
turn, it goes in state, because an error message that got summarized into "there was a problem" is
an error message that cannot be acted on. Day 64's approval gate depends on it absolutely: a pending
human approval that a summarizer decided was not the gist is an approval that silently stops
existing.

## The mechanism

Say the same fact twice — once in the conversation, once in a state key templated into the
instruction — then run enough turns to trigger a compaction and look for both.

```python
# days/day-20-context-engineering-compaction/lab/never_summarized.py
"""The same fact, said two ways: once in the conversation, once in state. Only one survives."""

import asyncio
from collections.abc import AsyncGenerator

from google.adk.agents import Agent
from google.adk.apps.app import App, EventsCompactionConfig
from google.adk.apps.llm_event_summarizer import LlmEventSummarizer
from google.adk.models import BaseLlm, LlmRequest, LlmResponse
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

SENT: list[LlmRequest] = []
TIDY = "Conversation Language: English. Ticket 4521: customers logged out, suspected cookie change."


class Recorder(BaseLlm):
    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        SENT.append(llm_request)
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text="Noted.")]))


class Tidy(BaseLlm):
    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text=TIDY)]))


agent = Agent(
    name="desk",
    model=Recorder(model="recorder"),
    instruction="You are Sutra, the triage desk. Standing rule for this account: {handling}",
)

app = App(
    name="sutra",
    root_agent=agent,
    events_compaction_config=EventsCompactionConfig(
        compaction_interval=2,
        overlap_size=1,
        summarizer=LlmEventSummarizer(llm=Tidy(model="minute-taker")),
    ),
)

TURNS = [
    "Ticket 4521: customers logged out. Do not close this ticket - refund is awaiting sign-off.",
    "Is it the SameSite cookie change in KB-104?",
    "What severity would you assign?",
    "Can we close it now?",
]


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(
        app_name="sutra",
        user_id="priya",
        state={"handling": "Managed customer. Escalate; never close without finance sign-off."},
    )
    runner = Runner(app=app, session_service=service)
    for turn in TURNS:
        await asyncio.sleep(0.05)  # distinct timestamps; see 2.2 'When it breaks'
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=turn)]),
        ):
            pass

    final = SENT[-1]
    history = str(final.contents)
    instruction = str(final.config.system_instruction)

    print(f"last call: {len(final.contents)} messages of history\n")
    print("the fact said once, in the conversation:")
    print(f"  'Do not close this ticket' still in the history? {'Do not close' in history}")
    print("\nthe same fact held in state and templated into the instruction:")
    print(
        f"  'never close without' still in the instruction? {'never close without' in instruction}"
    )
    print(f"\ninstruction sent on the last call:\n  {instruction.strip()}")


asyncio.run(main())
```

**Line by line:**

- `instruction="... Standing rule for this account: {handling}"` — the placeholder from
  [17.4.1](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.1-state-steers-the-next-turn.md).
  ADK replaces `{handling}` with `session.state["handling"]` when it builds the request, on **every**
  call, from whatever the value is at that moment.
- `state={"handling": ...}` is passed to `create_session`, so the fact exists before the first turn.
  It could equally have been written by a tool mid-conversation
  ([17.3.1](../../../day-17-state-scopes-and-lifetimes/parts/03-three-safe-writes/3.1-writing-from-inside-a-tool.md));
  what matters is that it lives in the dictionary and not in a sentence.
- The first turn says *"Do not close this ticket"* **in the conversation**, deliberately duplicating
  what the state key says. Two copies of one fact, in two different places, so the run compares them
  under identical conditions.
- `compaction_interval=2, overlap_size=1` with four turns guarantees compaction fires before the last
  call. [2.2](../02-the-config/2.2-the-turn-count-trigger.md) explains both numbers.
- `Tidy` is a fixed summarizer, so the summary is the same on every run and the result is
  reproducible. It writes a truthful summary that happens not to mention the instruction — which is
  precisely what a real summarizer did in [1.2](1.2-summaries-are-lossy.md), five times out
  of eight.
- `final.contents` is the **history** organ; `final.config.system_instruction` is the **instruction**
  organ. They are separate fields of the request, which is the structural reason compaction can touch
  one and not the other
  ([19.2.2](../../../day-19-context-engineering-selection/parts/02-anatomy/2.2-six-organs-and-who-packed-them.md)).
- The probes are substring tests on the assembled request, not on the session. The question being
  asked is *what did the model actually receive*, and nothing else counts.

**Line by line:**

- Four conversational turns and two summaries, all against recording models: no key, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
last call: 4 messages of history

the fact said once, in the conversation:
  'Do not close this ticket' still in the history? False

the same fact held in state and templated into the instruction:
  'never close without' still in the instruction? True

  You are Sutra, the triage desk. Standing rule for this account: Managed customer. Escalate; never close without finance sign-off.

```

One fact, said twice, in two places. **The conversational copy is gone and the state copy is intact**,
on the same call, in the same run.

Two details in that output are worth pausing on.

The instruction is not merely present — it is present **word for word**, including the negation.
Nothing paraphrased it, because nothing was asked to: templating is string substitution, not
summarization.

And ADK has appended a line of its own, `You are an agent. Your internal name is "desk".`, after your
instruction. That is the framework adding to an organ you thought you owned, which is a small useful
reminder that "the instruction" is what ADK assembles rather than what you typed.

## When it breaks

The failure has no exception attached, and it is a *state* failure rather than a compaction one: the
placeholder is in the instruction and the key is not in the state.

```text
KeyError: 'handling'
```

That is the loud version, and it is the good outcome — Day 17's
[4.2](../../../day-17-state-scopes-and-lifetimes/parts/04-state-in-the-prompt/4.2-the-brace-that-raises.md)
covers exactly this and why raising is correct.

The quiet version is worse and is specific to today: you move the fact into state, feel safe, and
never add the placeholder. The key sits in `session.state` where you can see it in a debugger, the
compaction dutifully removes the conversational copy, and the model is now working from a window that
has neither. Nothing raises, because nothing is wrong — the instruction has no `{handling}` in it to
fail on. This is yesterday's
[19.5.1](../../../day-19-context-engineering-selection/parts/05-failure-lab/5.1-in-state-and-not-in-the-window.md)
with compaction turned on, which is to say it is the same bug with its safety net removed.

## In production

**Write the placeholder and the state key in the same commit.** They are one feature. A key with no
placeholder is a variable nobody reads; a placeholder with no key is a crash. Reviewing them
separately is how systems end up with a `session.state` full of facts that never reach a model.

**What changes at scale** is that the instruction stops being small. Every fact promoted out of the
conversation lands in the instruction, and the instruction is sent in full on every call, uncompacted
and undiscounted. Promote enough and you have moved the cost rather than removed it — and moved it to
the organ compaction cannot help with. Yesterday's budget per organ
([19.6.2](../../../day-19-context-engineering-selection/parts/06-in-production/6.2-a-budget-per-organ.md))
is what stops that becoming invisible.

**The failure that only appears with real traffic** is the stale fact. A state key is re-rendered
every call whether or not it is still true, so a `handling` note set in January is still being
asserted in March with total confidence. Conversation goes out of date honestly, because it is
visibly old; state goes out of date silently, because it always looks current. Anything promoted to
state needs an owner and a way to be cleared.

**The review comment a senior engineer leaves:** *"this depends on the user's earlier 'don't close
it' message surviving in the history. With compaction on that's a coin flip — promote it to a state
key and template it."*

**The interview question:** *"how do you make sure an agent doesn't forget a constraint the user gave
it twenty turns ago?"* The answer that shows you have built it: *"I don't rely on the transcript.
Constraints go into session state and get templated into the system instruction on every call, so
they're rebuilt from the source of truth rather than remembered. The transcript is narrative and I
treat it as lossy."*
