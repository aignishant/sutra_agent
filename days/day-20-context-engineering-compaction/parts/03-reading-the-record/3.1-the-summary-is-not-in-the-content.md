# 3.1 — The summary is not in the event's content

## One-line answer

A compaction event has `author='user'` and `content=None`; the summary text lives in
`event.actions.compaction.compacted_content`, so every reasonable-looking way of finding it fails
silently.

## The story

The parcel arrives and the label on the outside says *1 of 2, books*.

You open it and there is no note inside. Nothing on the packing slip says what is in the box either —
the slip is about payment. The only description of the contents is the thing stuck to the outside,
which you have already thrown in the recycling with the packaging.

The information existed. It was attached to the delivery, not to the goods. And every place you
looked for it — inside the box, on the invoice, in the email — was a sensible place to look and the
wrong one.

## The idea in plain language

Every event in an ADK session has the same shape, and by
[Day 7](../../../day-07-events-and-streaming/LESSON.md) it is familiar: an `author` saying who
produced it, and a `content` holding what they said.

A compaction event breaks both of those expectations, and it does so quietly.

| Field | What you would expect | What it actually is |
| --- | --- | --- |
| `event.author` | something like `"compactor"` | `'user'` |
| `event.content` | the summary text | `None` |
| `event.actions.compaction` | — | the whole thing: two timestamps and the summary |

The summary is not lost and it is not encrypted. It is in `event.actions`, the field
[Day 13](../../../day-13-callbacks-four-doors/LESSON.md) introduced as the place an event carries the
*side effects* it caused — state changes, transfers, escalations — rather than the words that were
said. A compaction is modelled as a side effect on the session, and its payload is
`EventCompaction`: a `start_timestamp`, an `end_timestamp`, and a `compacted_content` holding the
actual text.

That design makes sense once you see it. A summary is not a turn. Nobody said it; it did not happen in
the conversation; it is a note *about* a range of the conversation, and the range is part of the
information. Putting it in `content` would make it indistinguishable from a model reply, and the next
compaction would summarize it as though it were one.

The practical consequence is a rule, and it is the only reliable one:

> **Detect a compaction with `event.actions and event.actions.compaction`. Never by author, never by
> content, never by a substring.**

## Why Sutra needs it

Because every tool Sutra has for looking at a session walks the event list, and all of them are about
to encounter events of a shape they were not written for.

Day 22 builds structured logging: one log line per event, with the author and a snippet of the text.
Run that over a compacted session and every summary logs as an empty message from the user, which is
both wrong and the kind of wrong that makes an incident harder rather than easier.

Day 23 writes tests over event lists. Day 79 onwards builds evals that replay sessions and score what
happened. Both need to count turns, and both will count a summary as a user turn unless they are told
not to. The bug is a one-line fix and an afternoon to find, which is exactly the kind this curriculum
exists to spend a page on in advance.

## The mechanism

Run four turns, take the first compaction event out of the session, and look in the three obvious
places before looking in the right one.

```python
# days/day-20-context-engineering-compaction/lab/find_the_summary.py
"""Open a compaction event and find out where the summary text is actually kept."""

import asyncio

from compact import QUESTIONS, app
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=app, session_service=service)
    for question in QUESTIONS:
        await asyncio.sleep(0.05)
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=question)]),
        ):
            pass

    record = await service.get_session(app_name="sutra", user_id="priya", session_id=session.id)
    summary = next(e for e in record.events if e.actions and e.actions.compaction)

    print("the three places you would look first:")
    print(f"  event.author            = {summary.author!r}")
    print(f"  event.content           = {summary.content!r}")
    print(f"  'compact' in the author = {'compact' in summary.author.lower()}")

    compaction = summary.actions.compaction
    print("\nwhere it actually is:")
    print(f"  event.actions.compaction.start_timestamp   = {compaction.start_timestamp:.6f}")
    print(f"  event.actions.compaction.end_timestamp     = {compaction.end_timestamp:.6f}")
    print(f"  ...compacted_content.role                  = {compaction.compacted_content.role!r}")
    print(
        f"  ...compacted_content.parts[0].text         = "
        f"{compaction.compacted_content.parts[0].text!r}"
    )


asyncio.run(main())
```

**Line by line:**

- `from compact import QUESTIONS, app` reuses the configured `App` from
  [2.1](../02-the-config/2.1-one-config-on-the-app.md) rather than restating it. This is why that file
  has an `if __name__ == "__main__":` guard — without it, importing would run four turns.
- `next(e for e in record.events if e.actions and e.actions.compaction)` is the correct detector,
  written as the generator expression you would actually use. The `e.actions and` half is not
  defensive noise: `actions` can be absent, and `e.actions.compaction` on a missing `actions` is an
  `AttributeError` in the middle of a loop over somebody's session.
- `{summary.author!r}` — the `!r` matters here. Printing `user` and printing `'user'` look different in
  a terminal, and the point of this line is that the value is a real string that happens to be exactly
  the string every user message carries.
- `'compact' in summary.author.lower()` is included because it is the heuristic people reach for, and
  the run prints it so you can watch it return `False`. A detector that works on the day you write it
  and silently stops working is worse than one that never worked.
- `compaction.start_timestamp` and `end_timestamp` are the **range this summary stands in for**. They
  are not decoration: they are how ADK later decides which raw events this summary replaces, which is
  [3.2](3.2-what-the-model-sees-after-a-compaction.md).
- `compacted_content.role` is printed because it is not the same as `event.author`, and the difference
  is the whole shape of the object.

**Line by line:**

- Four turns and two summaries against recording models: no key, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
the three places you would look first:
  event.author            = 'user'
  event.content           = None
  'compact' in the author = False

where it actually is:
  event.actions.compaction.start_timestamp   = 1788437197.480906
  event.actions.compaction.end_timestamp     = 1788437197.585263
  ...compacted_content.role                  = 'model'
  ...compacted_content.parts[0].text         = 'Conversation Language: English. User reported ticket 4521 (logout loop). Cause: cookie.'
```

Three failures and one success, in the order anybody would try them.

**`author` is `'user'`.** Not a special author, not the agent's name — the same string a real user
message carries. Anything grouping a session by author files the summaries under the human.

**`content` is `None`.** Not an empty string, which at least would survive a `.strip()`. `None`, which
is why the compaction rows in [2.1's output](../02-the-config/2.1-one-config-on-the-app.md) printed a
blank text column: the code there guards with `if event.content and event.content.parts`, and that
guard is the only reason it did not raise.

**And the role inside is `'model'`**, while the author outside is `'user'`. That is not a
contradiction; it is the two objects doing different jobs. The event's author records who produced the
event in the session's stream. The content's role is what the *model* will be told the message is when
this summary is assembled into a prompt — and a summary is presented to the model as though it had
said it, which is what makes it read as recollection rather than as instruction.

## When it breaks

Reach for `event.content` on a compaction event without a guard and you get the flattest possible
traceback:

```text
Traceback (most recent call last):
  File "read_session.py", line 12, in <module>
    print(event.content.parts[0].text)
          ^^^^^^^^^^^^^^^^^^^^
AttributeError: 'NoneType' object has no attribute 'parts'
```

That is the good outcome, because it happens immediately and points at the line. The bad outcome is
the code that already guards — `if event.content:` — and therefore **skips** every summary without
comment. Your session viewer shows the conversation with the summaries invisible, so a compacted
session looks like a conversation with a hole in it, and the hole is exactly where the explanation of
the missing turns would have been.

The version of this that reaches production is a turn counter. `len([e for e in events if e.author ==
"user"])` was correct for twenty days and is now wrong by one per compaction, and it is wrong in a
metric rather than in a crash.

## In production

**Write the detector once and put it in `sutra/`.** A one-line helper — *is this event a compaction,
and if so what is its text* — used by the logger, the session viewer, the tests and the evals. Four
copies of `event.actions and event.actions.compaction` scattered across a codebase is four places to
update when this experimental API changes a field name, and it is going to.

**What changes at scale** is that other things start appearing in `actions` too. State deltas,
transfers, escalations, requested tool confirmations — `EventActions` is a growing object, and
compaction is one member of it. Code that treats an event as *author plus content* is not slightly
incomplete; it is missing an entire channel of what the session records, and it will keep being
surprised.

**The failure that only appears with real traffic** is the analytics drift. Turn counts, messages per
session, user-message rates: every one of them shifts the day compaction is switched on, by an amount
that depends on the interval. It looks like user behaviour changed. Nobody connects it to a
configuration change made for cost reasons three weeks earlier.

**The review comment a senior engineer leaves:** *"this counts events by author to get turns. With
compaction on, summaries are authored `user` — filter them out explicitly or the number is wrong and
we won't notice."*

**The interview question:** *"how would you tell, from a session's event log, that summarization had
happened?"* The answer that shows you have looked: *"not by the author — the compaction event is
authored `user` and its `content` is `None`. You check `event.actions.compaction`, which holds the
timestamp range it covers and the summary text. Anything keying off author or content silently misses
them."*
