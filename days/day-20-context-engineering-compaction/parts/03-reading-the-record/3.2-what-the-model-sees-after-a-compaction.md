# 3.2 — What the model sees after a compaction

## One-line answer

When the next prompt is assembled, every raw event inside a kept summary's timestamp range is
**dropped** and the summary is inserted in their place as a single `model` message — so the model
reads its own past as one sentence it appears to have said.

## The story

The bank statement replaces the receipts.

For the first fortnight after you start keeping receipts you have a drawer full of them, and if
somebody asks what you spent on the trip you go through the drawer. Then the statement arrives, and
from that point on nobody looks at the drawer. One line per transaction, in order, on one page.

What is on the statement is true. It is also the only version anybody consults, so from then on the
statement *is* what happened, and the two coffees that appear as one card payment at the same café
are, for every practical purpose, one coffee.

The receipts are still in the drawer. Nobody is going to the drawer.

## The idea in plain language

[3.1](3.1-the-summary-is-not-in-the-content.md) found where the summary is stored.
This part is about what happens to it on the way into the next request, which is a separate step
performed by a different piece of ADK: the part that assembles `contents` before every call
([19.2.1](../../../day-19-context-engineering-selection/parts/02-anatomy/2.1-opening-the-envelope.md)
opened that envelope yesterday).

The rule it applies has three steps.

1. **Find the compaction events that are still in force.** A later summary can completely cover an
   earlier one's timestamp range — that is what `overlap_size` arranges — and when it does, the
   earlier one is *subsumed* and ignored. Only the surviving summaries are used.
2. **Drop the raw events inside those ranges.** Every user message and model reply whose timestamp
   falls inside a kept summary's `start`–`end` range is removed from the prompt.
3. **Insert each summary where its range ended**, as a message with role `model`.

So the model's view of its own history becomes: a summary, then whatever raw events came after it, in
order. Everything is in the right sequence; it is just that a stretch near the beginning has been
replaced by a paragraph.

The detail with the most consequences is step 3's **role**. The summary is presented as a `model`
message — as if the assistant had said it. Not as a system note, not as a user instruction, not
labelled as a summary at all. From inside the call there is nothing to distinguish *"I previously
established that this is a cookie problem"* from having actually established it.

That has an upside and a downside, and both are real. The upside is that it reads naturally and the
model treats it as its own established context rather than as an instruction to be weighed. The
downside is that **the model cannot tell a summary from a memory**, so it cannot hedge, cannot say
"I only have a summary of that part", and cannot ask you to re-supply what was dropped. It has no
signal that anything is missing.

## Why Sutra needs it

Because this is where Sutra's answers stop matching Sutra's transcript, and someone will eventually
ask about the gap.

When a support engineer says *"Sutra told the customer we had ruled out the cache — where did that
come from?"*, the answer is in one of two places. Either it is in the raw events, in which case it is
a normal conversation, or it is in a summary that a model wrote about the raw events, in which case
the sentence Sutra acted on was written by a model and never said by anybody. Day 22's logging and
Day 84's tracing both have to make that distinction visible or the investigation goes in circles.

It also sets up Phase 7 directly. Memory retrieval (Day 46 onwards) injects recalled text into the
window in exactly this way, with exactly this problem: the model cannot tell recalled text from
remembered text, and every design decision there is downstream of understanding it here.

## The mechanism

Print every message of every request, so the substitution is visible rather than inferred.

```python
# days/day-20-context-engineering-compaction/lab/what_the_model_sees.py
"""Print every message of every request, so you can watch the summary replace the turns."""

import asyncio

from compact import SENT, main

asyncio.run(main())

print("\n\n=== what the chat model actually saw, call by call ===")
for n, request in enumerate(SENT, start=1):
    print(f"\n--- call {n}: {len(request.contents)} messages ---")
    for content in request.contents:
        text = " ".join(p.text for p in (content.parts or []) if p.text)
        print(f"  [{content.role}] {text[:96]}")
```

**Line by line:**

- `from compact import SENT, main` — the recorded requests and the run function from
  [2.1](../02-the-config/2.1-one-config-on-the-app.md). `SENT` is the list the `Recorder` appends to,
  so it holds the exact `LlmRequest` objects ADK built, not a reconstruction.
- `asyncio.run(main())` runs the same four turns. Because `compact.py` guards its own run with
  `if __name__ == "__main__":`, importing it does not run them a second time.
- `request.contents` is the **history** organ of the request. The instruction is elsewhere
  (`request.config.system_instruction`, as
  [1.4](../01-notes-not-transcript/1.4-what-must-never-be-summarized.md) used), and that separation
  is why compaction can rewrite one and not the other.
- `content.role` rather than an author: at this point the events have become `Content` objects for the
  provider, and a provider knows only `user` and `model`. Whatever ADK knew about who produced what is
  gone by here, which is precisely why the summary's role is the thing to look at.
- `" ".join(p.text for p in (content.parts or []) if p.text)` — a message can have several parts and
  some carry no text at all (a function call, an inline blob). Filtering on `p.text` avoids joining
  `None` into the string.
- `[:96]` truncates for reading. The summary is short enough to fit; a real one would not be, and the
  first line of a real summary is usually enough to recognise it.

**Line by line:**

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
=== what the chat model actually saw, call by call ===

--- call 1: 1 messages ---
  [user] Ticket 4521: users keep getting logged out. Likely cause?

--- call 2: 3 messages ---
  [user] Ticket 4521: users keep getting logged out. Likely cause?
  [model] Noted, checking that.
  [user] Is that the SameSite cookie change in KB-104?

--- call 3: 2 messages ---
  [model] Conversation Language: English. User reported ticket 4521 (logout loop). Cause: cookie.
  [user] What severity would you assign it?

--- call 4: 4 messages ---
  [model] Conversation Language: English. User reported ticket 4521 (logout loop). Cause: cookie.
  [user] What severity would you assign it?
  [model] Noted, checking that.
  [user] Draft a one-line status update.
```

**Calls 1 and 2 are the world you already knew.** History accumulates; nothing is removed.

**Call 3 is the substitution, and it is total.** The four events of turns one and two — two user
messages and two model replies — are not shortened, not merged, not marked. They are **absent**. In
their place is one `[model]` message, and then the current question. Three messages became one.

**Call 4 shows the pattern holding.** The same summary is still first, and the two turns since it was
written follow verbatim. This is the shape every later call will have: one paragraph standing for the
old part, raw turns for the recent part, growing again until the next compaction resets it.

And note what call 4 does *not* contain: a second summary. The compaction written after turn 4 exists
in the session — [2.1's event table](../02-the-config/2.1-one-config-on-the-app.md) shows it at index
9 — but there was no fifth call for it to affect. **A summary is written after the turn that triggers
it and is used from the next turn onwards.** Off-by-one confusion here is common enough to be worth
saying twice.

Finally, read the `[model]` tag on the summary line and take it seriously. From the model's side of
the wire, that sentence is indistinguishable from something it said. There is no marker, no
attribution, and no way for it to know that four turns of detail used to be there.

## When it breaks

The visible failure is a model contradicting the transcript with complete confidence:

```text
reply: As I noted earlier, we ruled out the cache, so this is a cookie issue and I have
closed the ticket.
```

Nobody ruled out the cache. A summarizer compressed *"I tried clearing the cache and it did not
help"* into *"cache ruled out"*, the summary went into the window as a `model` message, and the model
read its own apparent words and built on them. The phrase **"as I noted earlier"** is the tell: the
model is quoting a summary back at you as memory, because from inside the call that is exactly what
it is.

There is a structural failure too, and ADK works to prevent it. If a compaction range split a function
call from its response, the assembled prompt would contain a tool result with no matching call, and
providers reject that. The library guards it by only ever compacting a **balanced prefix** of events —
`_longest_self_contained_prefix` in `google/adk/apps/compaction.py`, read on 2026-09-03 — so a window
with an unclosed tool call is trimmed back to the last point where nothing was outstanding. The
consequence is worth knowing:
[4.1](../04-failure-lab/4.1-the-minute-taker-you-did-not-hire.md) and Day 64's approval work both meet
the case where that prefix is empty, and compaction then does nothing at all, quietly.

## In production

**Log the summary text where an operator can read it, keyed to the session.** When somebody
investigates a strange answer, the first question is *what was actually in the window*, and after
compaction that is no longer answerable from the transcript alone. The summaries are the missing
half, and they are in `event.actions.compaction.compacted_content`
([3.1](3.1-the-summary-is-not-in-the-content.md)).

**What changes at scale** is that summaries start summarizing summaries. Over a long enough session,
a compaction range includes an earlier summary — ADK's default prompt template even accounts for it,
opening with *"It may or may not start from a compacted history"*. Each pass is lossy, so error
compounds: the account of turn three that survives to turn ninety has been through several
rewritings, and nothing in the window records how many.

**The failure that only appears with real traffic** is the confident false memory above, and it is
rare per turn and inevitable per thousand sessions. It is also the hardest class of bug to reproduce,
because reproducing it needs the whole session, the exact summary that was generated, and a
non-deterministic summarizer. Storing the summaries is what makes it investigable at all.

**The review comment a senior engineer leaves:** *"if the model can't tell a summary from its own
memory, don't let the summary assert conclusions. Constrain the summarizer prompt to facts and open
questions, and keep decisions in state."*

**The interview question:** *"what does the model actually receive after summarization?"* The answer
that shows you have printed it: *"the raw events in the compacted range are dropped and the summary is
inserted where the range ended, as a `model` message. It is not labelled as a summary, so the model
treats it as its own recollection — which is why summaries that assert conclusions are dangerous in a
way summaries that state facts are not."*
