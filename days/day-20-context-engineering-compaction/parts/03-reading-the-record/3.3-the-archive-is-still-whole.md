# 3.3 — The archive is still whole — and bigger

## One-line answer

Compaction **appends**: the same eight turns produced a 42% smaller final request and a session that
holds four more events and three and a half times as much stored text.

## The story

The shop keeps the till roll in a box in the back office.

At the end of the day the manager writes the day's takings on a card and pins it to the wall by the
door, because nobody wants to add up a till roll to know whether it was a good Saturday. The card is
short. The card is what everybody looks at.

The till roll goes in the box. It does not go in the bin, because the accountant wants it in April
and once, memorably, the card was wrong and the roll was how they found out.

So the box gets fuller every week, and the wall by the door stays readable. Both of those are on
purpose, and the second one is not paid for by the first.

## The idea in plain language

[1.1](../01-notes-not-transcript/1.1-archive-and-briefing.md) claimed that compaction changes the
briefing and not the record. That was stated as a principle. This part measures it, and the
measurement is more pointed than the principle: the record does not merely stay the same size. **It
gets bigger.**

The reason is in [3.1](3.1-the-summary-is-not-in-the-content.md). A summary is a new event, appended
to the session like every other event. Nothing is deleted, because deleting from an append-only log
is not something ADK does at all — the log is the audit trail Day 17 built session state on top of
([17.7.3](../../../day-17-state-scopes-and-lifetimes/parts/07-in-production/7.3-state-as-a-trace.md)).

So the accounting runs in two directions at once:

| | without compaction | with compaction |
| --- | --- | --- |
| what the model is sent | grows every turn | resets at every summary |
| what the session stores | *n* events | *n* events **plus one per summary** |

That is the correct trade and it is worth stating as a cost rather than discovering as a surprise:
you are buying a smaller prompt with a larger database.

For Sutra today the larger database is free, because `InMemorySessionService` throws it away when the
process ends. It stops being free the moment sessions are persisted, and it stops being small the
moment a summary is long — a summary that stands in for six turns is not short.

## Why Sutra needs it

Because Sutra's repo is going public in Phase 14 and its sessions will be persisted long before that.

Day 8 introduced session services as a swappable component
([Day 8](../../../day-08-sessions-and-services/LESSON.md)), and the day Sutra moves off the in-memory
one, every stored byte becomes a byte somebody keeps. If the team's mental model is "compaction makes
conversations smaller", the storage estimate will be wrong in the wrong direction, and the retention
policy will have been written against a number that does not exist.

There is a compliance edge too. A summary is *new text about a user's conversation, generated by a
model, and stored*. Under a data-deletion request it is as much part of the record as the messages,
and it is the part nobody remembers to include because nobody typed it.

## The mechanism

The same eight turns, run twice through the same code, with compaction as the only difference — and
both quantities counted.

```python
# days/day-20-context-engineering-compaction/lab/archive_grows.py
"""The window got smaller. Count the archive and find out which way it went."""


def build(compact: bool) -> App:
    agent = Agent(name="desk", model=Recorder(model="recorder"), instruction="You are Sutra.")
    if not compact:
        return App(name="sutra", root_agent=agent)
    return App(
        name="sutra",
        root_agent=agent,
        events_compaction_config=EventsCompactionConfig(
            compaction_interval=2,
            overlap_size=1,
            summarizer=LlmEventSummarizer(llm=Fixed(model="minute-taker")),
        ),
    )


async def run(compact: bool) -> None:
    SENT.clear()
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=build(compact), session_service=service)
    for n in range(1, 9):
        await asyncio.sleep(0.05)
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=f"question {n}")]),
        ):
            pass

    record = await service.get_session(app_name="sutra", user_id="priya", session_id=session.id)
    stored = sum(
        len(p.text or "")
        for e in record.events
        if e.content and e.content.parts
        for p in e.content.parts
    )
    stored += sum(
        len(p.text or "")
        for e in record.events
        if e.actions and e.actions.compaction
        for p in (e.actions.compaction.compacted_content.parts or [])
    )
    print(
        f"COMPACTION={'on ' if compact else 'off'}  "
        f"archive: {len(record.events):>2} events, {stored:>4} chars stored   |   "
        f"last request: {len(SENT[-1].contents)} messages, {len(str(SENT[-1].contents)):>4} chars"
    )


asyncio.run(run(compact=False))
asyncio.run(run(compact=True))
```

**Line by line:**

- `build(compact)` returns an `App` **with or without** the compaction config, and changes nothing
  else. That is the ablation switch: one boolean, one difference, two runs.
- `if not compact: return App(name="sutra", root_agent=agent)` — an `App` with no
  `events_compaction_config` at all, rather than one with a config that never fires. The field is
  optional, and leaving it out is the honest "off".
- `range(1, 9)` — eight invocations, so an interval of 2 fires several times and the difference is
  large enough to read without squinting.
- The first `stored` sum walks `e.content.parts` — the ordinary events, the user messages and model
  replies.
- The second sum is the one that makes this measurement honest. Summary events have `content=None`
  ([3.1](3.1-the-summary-is-not-in-the-content.md)), so counting only `e.content` would score every
  summary as **zero bytes** and produce a table showing storage unchanged. The summaries are counted
  where they actually live, in `e.actions.compaction.compacted_content`.
- `len(p.text or "")` — a part may carry no text, and `len(None)` raises. The `or ""` is what lets one
  expression cover both event shapes.
- `SENT[-1]` is the final request, which is the fair comparison point: the *last* call is where the
  saving has accumulated.

**Line by line:**

- Sixteen turns and several summaries across the two runs, all against recording models: no key, no
  quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
COMPACTION=off  archive: 16 events,  128 chars stored   |   last request: 15 messages, 1209 chars
COMPACTION=on   archive: 20 events,  444 chars stored   |   last request: 6 messages,  699 chars
```

Read it as two columns going in opposite directions.

**The request got much smaller.** Fifteen messages became six; 1,209 characters became 699. That is a
42% reduction on the last call, and it grows with every further turn, exactly as
[1.3](../01-notes-not-transcript/1.3-you-spend-calls-to-save-calls.md) predicted.

**The archive got bigger both ways.** Sixteen events became twenty — four summaries appended — and the
stored text went from 128 characters to 444. That is **three and a half times as much stored text**,
for the identical conversation.

The ratio is exaggerated here because the fake turns are tiny (`"question 4"`, `"Noted."`) and the
fixed summary is a full sentence, so each summary outweighs the turns it describes. With realistic
turns the multiple is much smaller. **The direction is not exaggerated at all**, and the direction is
the finding: there is no configuration of compaction under which the archive shrinks.

## When it breaks

Nothing raises. This is a budgeting failure and it surfaces somewhere else entirely — usually as a
storage alert on the session table, weeks after the change:

```text
ERROR: could not extend file "base/16384/24591": No space left on device
HINT: Check free disk space.
```

The commit that caused it is a compaction config added for cost reasons, and nothing links the two.

There is a second, sharper version. A deletion request comes in for a user, the code deletes their
events by author, and the summaries — authored `'user'`, per
[3.1](3.1-the-summary-is-not-in-the-content.md) — happen to be caught by that filter and removed too.
That is the lucky case. Filter by `content` instead, or by anything that requires a non-`None`
content, and the summaries survive the deletion. Text generated from a user's conversation remains in
the store after that user's data was deleted, and every test of the deletion path passes.

## In production

**Estimate storage from turns plus summaries, and measure the summary length.** The number that
matters is average summary characters times expected compactions per session, and the second factor
comes straight from your interval and your session-length distribution. It is a five-minute
calculation that is never done, because the feature was introduced under the heading of making things
smaller.

**What changes at scale** is that summaries stop being small. A summary standing in for six tool-heavy
turns is a paragraph, and ADK's default summarizer prompt explicitly asks for tool names to be listed,
so tool-heavy sessions produce longer summaries. The sessions that trigger compaction most are the
sessions whose summaries cost most to keep.

**The failure that only appears with real traffic** is the deletion path above, and it is the one to
take seriously, because it is quiet and it is regulatory. Anything that enumerates a session's content
for export, redaction or deletion must handle both event shapes. Test it with a compacted session, not
a clean one.

**The review comment a senior engineer leaves:** *"the GDPR delete walks events and clears
`content`. Compaction summaries keep their text in `actions.compaction.compacted_content` — this
misses them. Add a case and a test with a compacted session."*

**The interview question:** *"does summarization reduce your storage?"* The answer that shows you have
counted: *"no — it increases it. Summaries are appended events; nothing is deleted. It reduces what
you send to the model, which is a different budget. On our measurement the last request dropped 42%
while the session grew by four events."*
