# 2.3 — The size trigger: threshold and retention

## One-line answer

`token_threshold` compacts when the last prompt was **bigger than a number** rather than when a turn
count was reached, and `event_retention_size` says how many raw events survive at the end untouched.

## The story

The bin by the back door is emptied when it is full.

Not on Tuesdays. Nobody wrote a rota for it, because a rota would be wrong in both directions: in a
quiet week you would be walking an empty bin down the drive, and in the week somebody clears out the
shed you would be stepping over it for four days waiting for Tuesday.

The rule that works is the one attached to the thing you actually care about. Look at the bin. Is it
full? Then empty it.

## The idea in plain language

The turn-count trigger from [2.2](2.2-the-turn-count-trigger.md) counts doorbell presses, and its
weakness is that a doorbell press is not a fixed amount of anything. Three turns of *"yes"*, *"ok"*,
*"thanks"* count exactly as much as three turns in which somebody pasted a stack trace, a config file
and a log excerpt.

So ADK offers a second trigger that watches the thing you actually care about — how big the prompt
got — and it is configured as a pair, exactly like the first one.

**`token_threshold` — how big is too big.** After an invocation completes, ADK looks at the most
recently observed prompt token count. If it meets or exceeds this number, a compaction runs.

**`event_retention_size` — how much stays raw.** When that compaction runs, this many events at the
end of the log are kept un-compacted, word for word. It is the verbatim window from
[1.1](../01-notes-not-transcript/1.1-archive-and-briefing.md), counted in **events** rather than in
invocations, which is a real difference: two events is often one turn, not two.

Where the token count comes from is worth knowing, because it decides how accurate the trigger is.
ADK prefers the **real number the provider reported** — the `prompt_token_count` in the usage metadata
of a recent event, which is the model's own tokeniser talking. If no event carries one, it falls back
to an estimate: it assembles what the next prompt's contents would be and divides the character count
by four.

That fallback matters in two directions. It is why this trigger works at all against a fake model in a
test, and it is why the number it compares is an approximation whenever your model or your transport
does not report usage. Four characters per token is a decent average for English prose and a poor one
for JSON, code, or the log lines a support agent gets pasted
([19.4.1](../../../day-19-context-engineering-selection/parts/04-measuring/4.1-a-scale-for-prompts.md)
measured that gap yesterday).

## Why Sutra needs it

Because Sutra's whole job involves people pasting things.

A support engineer does not type "the login is broken" and stop. They paste the failing request, the
response headers, thirty lines of log, and a screenshot description. One invocation, and the window
went from small to enormous. An interval-based trigger has no opinion about that at all — it is
waiting for its third doorbell press, and the third press may be several turns away.

This is also the trigger that protects against the hard failure rather than the expensive one. Running
out of quota is annoying; exceeding the model's context limit is a request that cannot be made. A
threshold set below the model's real limit is the difference between degrading and stopping, and Day
21's error work is where that distinction gets built into Sutra properly.

## The mechanism

Four turns, one of which pastes a log, with a threshold and no interval at all.

```python
# days/day-20-context-engineering-compaction/lab/by_size.py
"""The other trigger: compact when the window gets big, not when a turn count is reached."""

TURNS = [
    "hi",
    "what is the severity of ticket 4521?",
    "Here is the log the customer pasted: " + "ERROR redirect loop at /auth/callback; " * 12,
    "and what should I tell them?",
]

app = App(
    name="sutra",
    root_agent=agent,
    events_compaction_config=EventsCompactionConfig(
        token_threshold=100,
        event_retention_size=2,
        summarizer=LlmEventSummarizer(llm=Fixed(model="minute-taker")),
    ),
)


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=app, session_service=service)

    print("turn  chars sent  est. tokens  compactions in archive")
    for n, turn in enumerate(TURNS, start=1):
        await asyncio.sleep(0.05)  # distinct timestamps; see 2.2 'When it breaks'
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=turn)]),
        ):
            pass
        record = await service.get_session(app_name="sutra", user_id="priya", session_id=session.id)
        done = sum(1 for e in record.events if e.actions and e.actions.compaction)
        chars = len(str(SENT[-1].contents))
        print(f"{n:>4}  {chars:>10}  {chars // 4:>11}  {done:>22}")


asyncio.run(main())
```

**Line by line:**

- The imports, the `Recorder` and the `Fixed` summarizer are identical to
  [2.1](2.1-one-config-on-the-app.md) and are elided here rather than repeated; the full file is in
  `lab/by_size.py`.
- `"ERROR redirect loop at /auth/callback; " * 12` is the pasted log, and multiplying a string is the
  cheapest way to make one turn much larger than its neighbours without pretending to realism it does
  not need.
- `token_threshold=100` with **no `compaction_interval` at all**. This is the point of the file: the
  turn-count trigger is switched off entirely, so anything that fires, fires because of size.
- `event_retention_size=2` — two raw events survive each compaction. With one user message and one
  model reply per turn, that is the last turn kept verbatim.
- `100` is a deliberately tiny threshold. A real one is thousands; this one is small enough that four
  short turns can cross it, which is what makes the behaviour visible in a file you can run instantly.
- `chars // 4` is **my own rough proxy**, printed so the table has a size column, and it is computed
  over `request.contents` only. ADK computes its own number over the effective contents it would
  assemble, so the two are close but not identical, and the trigger fires on ADK's, not on mine.
- `sum(1 for e in record.events if e.actions and e.actions.compaction)` is read after every turn
  rather than at the end, because *when* the count changes is the entire result.

**Line by line:**

- Four turns against recording models: no key, no quota.

One representative run, measured on `google-adk` 2.7.1 on 2026-09-03:

```text
turn  chars sent  est. tokens  compactions in archive
   1          74           18                       0
   2         261           65                       0
   3         786          196                       2
   4         309           77                       3
```

**Turns 1 and 2 do nothing**, and that is the trigger behaving correctly: the window is small, so
there is nothing worth spending a call on. An interval of 2 would have fired here. This did not.

**Turn 3 is the pasted log**, and it is the whole point. That single invocation takes the prompt from
65 to 196 by the crude measure — past the threshold — and compaction appears immediately after it.
Nobody had to predict that turn 3 would be the big one, which is exactly what a turn count cannot do.

**Turn 4's request is 309 characters**, down from 786. The log has been replaced by a summary and the
retained events, and the window is back under control after a single oversized turn rather than
several turns later.

### One honest caveat: this table is not identical on every run

Run it six times and you will not get six identical tables. Across six runs on the day this was
written, turns 1 and 2 were **always** `74/18/0` and `261/65/0`, turn 3 **always** crossed the
threshold and produced compaction, and turn 4 **always** came back down sharply. What moved was turn
3's own request size — `707` in two runs, `786` in four — and the compaction count after it, `1` or
`2`. One run also finished at `230` rather than `309`.

That variation is in the token-threshold path, not in this script. ADK's own source describes
post-invocation compaction as **best-effort**: `_run_post_invocation_compaction` in
`google/adk/runners.py` documents that a summary is discarded rather than retried if a newer turn has
updated the session while summarization was running, and the token check has two places it can fire —
during an invocation and after it, with the runner passing a `skip_token_compaction` flag between
them. That is consistent with what was observed. **The exact interleaving was not pinned down**, and
this document is not going to pretend otherwise.

Two things follow, and both are worth more than a stable table would have been.

**The claims this part makes are the stable ones.** A size trigger fires on the turn the trouble
arrives, and the turn after it is small again. Neither of those moved in any run.

**And compaction is not a guarantee.** It is a best-effort background tidy-up that may be skipped on
any given turn. Anything that *depends* on a compaction having happened — a test asserting an exact
event count, a budget assuming a fixed number of summarizer calls — is depending on something the
framework does not promise. That is a production fact, and it is
[5.2](../05-in-production/5.2-testing-compaction-without-quota.md)'s reason for asserting *fewer* and
*at least one* rather than exact numbers.

## When it breaks

**The pair is a pair, and half of it is refused at construction:**

```text
ValidationError: 1 validation error for EventsCompactionConfig
  Value error, token_threshold and event_retention_size must be set together. [type=value_error,
  input_value={'token_threshold': 4000}, input_type=dict]
```

**A threshold near the model's real limit does not save you.** The check happens *after* an
invocation completes, so the oversized request has already been sent. If a single pasted document is
larger than the window on its own, compaction never gets the chance to help and the provider refuses
the call outright. Compaction manages accumulation; it is not a guard against one enormous message,
and that guard has to be a length check before the call.

**And the retention number is in events, which is the quiet one.** `event_retention_size=1` sounds
like "keep the last turn" and means "keep the last event", which is usually the model's reply with the
user's question already summarized away. The window then contains an answer whose question is gone.
Count what a turn costs in your own event log before choosing this number — Day 7's event work
([Day 7](../../../day-07-events-and-streaming/LESSON.md)) is what tells you whether a turn is two
events or twelve.

## In production

**Set the threshold as a fraction of the model's context limit, not as a round number.**
`gemini-3.7-flash` reports an input limit of 1,048,576 tokens (read from the live model listing on
2026-09-03), and a threshold somewhere well below that leaves room for the summary, the instruction,
the tool declarations and the next message. The number that matters is the headroom, and a threshold
chosen without reference to the limit is a number with no meaning.

**What changes at scale** is that the estimate and the truth diverge for exactly the workloads that
need the trigger most. Prose is close to four characters per token; pasted JSON and stack traces are
denser, so the estimate *under*-counts precisely when somebody has pasted something large. Where usage
metadata is available the real count is used and this goes away, which is a good reason to make sure
your model path reports it.

**The failure that only appears with real traffic** is the pathological session that sits just under
the threshold forever. Every turn is 95% of the limit, nothing ever triggers, and every single call is
enormous. A threshold is a ceiling, not a target, and a system with only a ceiling has no opinion
about the space just underneath it.

**The review comment a senior engineer leaves:** *"the threshold is 4000 and the model's limit is a
million — is that deliberate? If we're optimising cost, say so in the comment, because it reads like
somebody thought 4000 was the context limit."*

**The interview question:** *"when would you trigger summarization on size instead of on turn count?"*
The answer that shows you have hit it: *"whenever turns aren't uniform. One pasted log can be worth
twenty conversational turns, and a turn counter has no way to know. Size triggers on the thing you
actually care about — with the caveat that it fires after the big request has already been sent."*
