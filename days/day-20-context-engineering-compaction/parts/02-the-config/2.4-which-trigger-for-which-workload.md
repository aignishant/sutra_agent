# 2.4 — Which trigger for which workload

## One-line answer

Use the **interval** when your turns are all much the same size, use the **threshold** when any single
turn might be enormous, and set **both** when you have one application that has to survive both kinds
of conversation — which is most applications.

## The story

The light on the stairwell has a timer switch.

You press it, you get enough light to reach the top, and it goes off. It is the right switch for a
stairwell, because everyone who presses it is doing the same thing for about the same length of time.

The same switch on the back porch is wrong, and everyone who has carried shopping in from the car in
the dark knows why. Some trips are one bag. Some trips are the whole boot, twice, plus the dog. The
porch wants the other kind of switch: the one that watches for something happening and stays on while
it does.

Neither switch is better. They are answers to different questions about how uniform the thing you are
lighting is.

## The idea in plain language

Both triggers do the same job — decide when to spend a call on a summary — and they disagree about
what evidence to use.

| | **`compaction_interval` + `overlap_size`** | **`token_threshold` + `event_retention_size`** |
| --- | --- | --- |
| watches | how many invocations have completed | how big the last prompt was |
| good when | turns are roughly uniform | any turn could be huge |
| the failure it has | one pasted log slips through until the count is reached | it fires only after the big request has been sent |
| what stays verbatim | `overlap_size` **invocations**, re-read into the next summary | `event_retention_size` **events**, left raw |
| predictable? | yes — you can say when it will fire | no — it depends on what the user types |

The unit mismatch in the fourth row is the detail that catches people. `overlap_size` counts
invocations; `event_retention_size` counts events. They sound like the same setting and they are not,
and a turn is usually two events but can be twelve
([Day 7](../../../day-07-events-and-streaming/LESSON.md)).

**You can set both**, and for a real application you usually should. The interval gives you a floor —
the window gets tidied regularly whatever happens — and the threshold gives you a ceiling for the day
somebody pastes a log. ADK checks them in a defined order: after each invocation, if the token
threshold is configured and has been crossed, that compaction runs and the sliding-window check is
skipped for that turn; otherwise the invocation count is checked as normal. Verified by reading
`google/adk/apps/compaction.py` in `google-adk` 2.7.1 on 2026-09-03, where
`_run_compaction_for_sliding_window` begins with exactly that test.

Which means: **the threshold is the emergency, the interval is the routine.** They are not competing;
one pre-empts the other on the turns where it matters.

## Why Sutra needs it

Because Sutra has exactly the two workloads in the table above, and they arrive through the same door.

Half of Sutra's traffic is conversational triage: short questions, short answers, uniform turns. That
is a stairwell, and an interval handles it perfectly.

The other half starts the moment an engineer pastes the failing request and thirty lines of log. That
is the back porch, and an interval handles it badly — the count is unmoved, and the next two turns are
paid at the new, much larger size.

Day 24 has to produce a budget that holds for both, and Day 70's quota router has to decide which
provider each of them goes to. Neither is possible if the compaction policy only works for one shape
of conversation.

## The mechanism

One config with both triggers armed, and two conversations of six turns each: one of short messages,
one containing a single pasted log.

```python
# days/day-20-context-engineering-compaction/lab/both_triggers.py
"""Set both triggers and run two different conversations through the same config."""

CHATTY = ["hi", "any update?", "ok", "thanks", "one more thing", "what severity?"]
PASTED = [
    "hi",
    "Here is the log: " + "ERROR redirect loop at /auth/callback; " * 12,
    "ok",
    "thanks",
    "one more thing",
    "what severity?",
]


def build() -> App:
    """One config with BOTH triggers armed."""
    agent = Agent(name="desk", model=Recorder(model="recorder"), instruction="You are Sutra.")
    return App(
        name="sutra",
        root_agent=agent,
        events_compaction_config=EventsCompactionConfig(
            compaction_interval=4,
            overlap_size=1,
            token_threshold=100,
            event_retention_size=2,
            summarizer=LlmEventSummarizer(llm=Fixed(model="minute-taker")),
        ),
    )


async def run(label: str, turns: list[str]) -> None:
    SENT.clear()
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=build(), session_service=service)

    fired_after = []
    seen = 0
    for n, turn in enumerate(turns, start=1):
        await asyncio.sleep(0.05)
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=turn)]),
        ):
            pass
        record = await service.get_session(app_name="sutra", user_id="priya", session_id=session.id)
        done = sum(1 for e in record.events if e.actions and e.actions.compaction)
        if done > seen:
            fired_after.append(n)
            seen = done
    print(
        f"{label:<22} compactions after turns {fired_after},  "
        f"last request {len(str(SENT[-1].contents))} chars"
    )


asyncio.run(run("six short turns", CHATTY))
asyncio.run(run("one pasted log", PASTED))
```

**Line by line:**

- The imports, `Recorder` and `Fixed` are the ones from [2.1](2.1-one-config-on-the-app.md); the full
  file is in `lab/both_triggers.py`.
- **All four trigger fields are set on one config.** This is the configuration the validator was
  guarding in 2.1 and 2.3: each pair complete, so both are armed.
- `compaction_interval=4` is deliberately *longer* than the six-turn conversation needs, so the
  interval fires at most once. It makes the two triggers easy to tell apart in the output.
- `token_threshold=100` is the same tiny threshold as 2.3, for the same reason: a file you can run
  instantly has to cross it.
- `CHATTY` and `PASTED` **differ in exactly one element** — the second turn. Everything else about the
  two runs is identical, which is what makes the comparison mean anything.
- `build()` returns a **fresh `App` per run**, because ADK attaches a derived summarizer to the config
  object when one is missing and because sharing an `App` across two independent conversations would
  blur the experiment. Note this is the opposite of what
  [2.1's *In production*](2.1-one-config-on-the-app.md) recommends for real code, and it is a
  deliberate test-only choice.
- `fired_after` records the **turn number** after which the compaction count went up, rather than the
  total. When it fired is the question; how many is a detail.
- `seen` carries the previous count so each increase is recorded once.

```bash
cd days/day-20-context-engineering-compaction/lab
uv run python both_triggers.py
```

**Line by line:**

- Twelve turns and four summaries across the two runs, all against recording models: no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
six short turns        compactions after turns [4],  last request 332 chars
one pasted log         compactions after turns [2, 3, 5],  last request 167 chars
```

**Same configuration, and the two conversations behaved nothing like each other.**

The chatty run compacted **once, after turn 4** — the interval, firing on schedule. The threshold was
never approached, because six short messages never got near it. This is the routine.

The pasted run compacted **after turns 2, 3 and 5** — starting immediately after the paste, three turns
before the interval would have said anything. This is the emergency, and it did its job on the turn
the trouble arrived rather than two turns later.

And the last line is the one to notice: **the conversation that contained a large pasted log ended with
a smaller request than the one that did not.** 167 characters against 332. Not because the log was
small, but because the trigger that watches size reacted to it and then kept reacting, while the chatty
conversation was left alone by everything except a single scheduled tidy-up.

One caveat, the same one as [2.3](2.3-the-size-trigger.md). The chatty row is stable — four runs on
the day this was written all gave `[4]` and 332 characters. The pasted row varied: three runs gave
`[2, 3, 5]` and 167 characters, one gave `[2, 3, 6]` and 642. What never varied is the thing this part
claims: the size trigger fired on **turn 2**, the turn the log arrived, in every run, while the
interval never fired before turn 4 in any of them. Compaction on the token path is a best-effort
background tidy-up rather than a promise, and 2.3 has the detail.

If you take one setting away from this day, take this one: arm both, set the interval from your typical
session and the threshold from your model's real limit, and the two failure modes cover each other.

## When it breaks

**All four fields, but only one pair complete, is a `ValidationError` at construction** — the same
messages as [2.1](2.1-one-config-on-the-app.md) and [2.3](2.3-the-size-trigger.md), and it is the good
outcome, because it happens at startup rather than at turn nine.

**Both armed, and the threshold set low, means the interval effectively never runs.** If your threshold
is crossed on nearly every turn, the size check pre-empts the sliding window every time and the
interval and overlap you configured are dead settings. Nothing reports this. The symptom is a
summarizer call count much higher than your interval predicts, which is worth alerting on and is
exactly the accounting Day 24 builds.

**And the reverse:** a threshold set far too high with a long interval is a configuration where neither
trigger fires in a normal session, so compaction is enabled, validated, warned about, and inert. Both
of these are configurations that look thorough in code review and do nothing.

## In production

**Derive the two numbers from two different sources and say so in the comment.** The interval comes
from your session-length distribution; the threshold comes from the model's context limit minus the
room the rest of the window needs. A comment naming the source is what stops the next person tuning
one of them for the other's reason.

**What changes at scale** is that a single `App` stops being able to serve both workloads well, even
with both triggers. The chat widget and the batch classifier want different intervals, and this config
is per-`App`. The production answer, as in [2.1](2.1-one-config-on-the-app.md), is more than one `App`
rather than a compromise in one.

**The failure that only appears with real traffic** is a change of user behaviour rather than of code.
A new integration starts forwarding email threads into Sutra, average turn size triples overnight, and
a threshold that used to fire rarely now fires constantly. Summarizer spend triples with no deploy, and
the only place it shows up is the provider's request count.

**The review comment a senior engineer leaves:** *"we've got an interval and a threshold, and the
threshold is going to win on basically every turn with our current prompt sizes. Either raise it or
drop the interval, but don't ship a setting that never runs."*

**The interview question:** *"you have both a turn-based and a size-based compaction trigger available.
Which do you use?"* The answer that shows you have run both: *"both. The interval is the routine tidy-up
and it's predictable; the threshold is the safety net for the turn where someone pastes a log. In ADK
the threshold pre-empts the interval on any turn it fires, so they compose rather than fight — the
thing to watch is the threshold being so low that the interval never gets a turn."*
