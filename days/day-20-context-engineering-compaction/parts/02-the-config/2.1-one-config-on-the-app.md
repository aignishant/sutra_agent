# 2.1 — One config, and it belongs to the App

## One-line answer

ADK does compaction for you when you attach an `EventsCompactionConfig` to the **`App`** — not to the
agent — and hand that `App` to the `Runner`; the agent's code does not change by a single line.

## The story

The heating in the office block is set in the plant room.

There is a thermostat down there, and it governs the whole building. Every room gets what the
building decided. Nobody on the third floor has a dial that means anything, and the argument about
whether it is too warm is an argument to have with the building manager, not with your radiator.

The reason it is arranged that way is not that rooms do not differ. It is that heating one room
properly requires knowing about the boiler, the pipes and the other rooms, and none of that fits
inside a room.

## The idea in plain language

Compaction is a building-level decision, and ADK's API says so by where it puts the setting.

An **`Agent`** is one participant: an instruction, a model, some tools. It handles one turn at a
time and it has no idea how long the conversation has been running.

An **`App`** is the thing that wraps a root agent along with the concerns that span the whole
application — plugins ([Day 14](../../../day-14-plugins-one-layer-up/LESSON.md)), context caching,
resumability, and compaction. It is the object that can reasonably ask *"how many invocations has
this session had?"*, because that question is about the session and not about any one agent's turn.

So compaction is configured in exactly one place:

```
App(name=..., root_agent=..., events_compaction_config=EventsCompactionConfig(...))
```

and then the `App` — rather than the agent — is what the `Runner` is built from. Everything else
follows automatically. After each completed invocation the Runner checks whether the trigger you
configured has fired, and if it has, it calls the summarizer and appends the resulting summary to the
session.

Three consequences worth stating plainly, because each one catches somebody out.

**Your agent code does not change.** No new import in the agent, no wrapper, no callback. This is
worth noticing after [Day 13](../../../day-13-callbacks-four-doors/LESSON.md) and
[Day 14](../../../day-14-plugins-one-layer-up/LESSON.md), where every new behaviour arrived as a hook
you attached yourself. Compaction is a framework service, not a hook.

**It applies to the whole app.** Every agent under that root, every session, every user. There is no
per-agent override, which is the correct default and is occasionally the wrong thing —
[2.4](2.4-which-trigger-for-which-workload.md) is where that starts to bite.

**It runs after the turn, not during it.** The user has their answer before the summarizer starts
work. That is a deliberate and good choice — it keeps summarization off the latency path — and it has
a consequence [5.1](../05-in-production/5.1-budgeting-the-minute-taker.md) has to deal with: the
summarizer's requests are not visible in the request that caused them.

> **Verified against `https://adk.dev/context/compaction/` on 2026-09-03**, and cross-read against the
> installed `google-adk` 2.7.1 source (`google/adk/apps/_configs.py`, `google/adk/apps/compaction.py`,
> `google/adk/runners.py`). The field names, the import paths and the validation rules in this section
> are the ones that package enforces, not a paraphrase of the page.

⚠️ **This API is marked experimental.** Constructing the config prints a warning, quoted in full in
*When it breaks* below. Principle 14 applies: when it changes, the plan is amended before the code
is.

## Why Sutra needs it

Because Sutra is about to grow an `App` object anyway, and this is the day it earns one.

Everything so far has been built with `Runner(app_name="sutra", agent=..., session_service=...)` —
the shortcut form, where ADK wraps your agent in an `App` internally and you never see it. From today
Sutra constructs its own, because there is finally something to put in it.

That matters beyond compaction. Phase 8's graph work (Day 53 onwards) is built on the `App` object;
Day 84's tracing plugin attaches there; Day 60's resumability is another field on the same class.
Today is the cheapest possible introduction to the object all of those need, because compaction is
one field and the rest of the code is unchanged.

## The mechanism

The whole day in one file, with no quota spent: a recording chat model, a fixed-text summarizer, and
four short turns.

```python
# days/day-20-context-engineering-compaction/lab/compact.py
"""Compaction with no quota at all: a recording chat model and a fixed-text minute-taker."""

import asyncio
from collections.abc import AsyncGenerator

from google.adk.agents import Agent
from google.adk.apps.app import App, EventsCompactionConfig
from google.adk.apps.llm_event_summarizer import LlmEventSummarizer
from google.adk.models import BaseLlm, LlmRequest, LlmResponse
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

SENT: list[LlmRequest] = []
SUMMARY = "Conversation Language: English. User reported ticket 4521 (logout loop). Cause: cookie."


class Recorder(BaseLlm):
    """Replies with one fixed sentence and keeps every request it was sent."""

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        SENT.append(llm_request)
        yield LlmResponse(
            content=types.Content(role="model", parts=[types.Part(text="Noted, checking that.")])
        )


class FixedSummarizer(BaseLlm):
    """A minute-taker that always writes the same minutes, so the run is deterministic."""

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text=SUMMARY)]))


agent = Agent(name="desk", model=Recorder(model="recorder"), instruction="You are Sutra.")

app = App(
    name="sutra",
    root_agent=agent,
    events_compaction_config=EventsCompactionConfig(
        compaction_interval=2,
        overlap_size=1,
        summarizer=LlmEventSummarizer(llm=FixedSummarizer(model="minute-taker")),
    ),
)

QUESTIONS = [
    "Ticket 4521: users keep getting logged out. Likely cause?",
    "Is that the SameSite cookie change in KB-104?",
    "What severity would you assign it?",
    "Draft a one-line status update.",
]


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=app, session_service=service)

    for question in QUESTIONS:
        await asyncio.sleep(0.05)  # distinct timestamps; see 2.2 'When it breaks'
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=question)]),
        ):
            pass

    record = await service.get_session(app_name="sutra", user_id="priya", session_id=session.id)
    print(f"{len(record.events)} events in the archive after {len(QUESTIONS)} invocations\n")
    print(" #  author  compaction?  text")
    for i, event in enumerate(record.events):
        compaction = event.actions.compaction if event.actions else None
        text = ""
        if event.content and event.content.parts and event.content.parts[0].text:
            text = event.content.parts[0].text[:44]
        print(f"{i:>2}  {event.author:<6}  {'YES' if compaction else '-':<11}  {text}")

    print(f"\nrequests the chat model was sent: {len(SENT)}")
    for i, request in enumerate(SENT, start=1):
        print(f"  call {i}: {len(request.contents)} messages, {len(str(request.contents))} chars")


if __name__ == "__main__":
    asyncio.run(main())
```

**Line by line:**

- `from google.adk.apps.app import App, EventsCompactionConfig` — both come from the same module.
  `EventsCompactionConfig` is defined in `google/adk/apps/_configs.py` and re-exported here, so import
  it from `apps.app` as the documentation does; the underscore module is private and may move.
- `from google.adk.apps.llm_event_summarizer import LlmEventSummarizer` — a separate module, because
  it is a separate decision. The config says *when*; the summarizer says *who*.
- `class Recorder(BaseLlm)` — the recording model from
  [19.2.1](../../../day-19-context-engineering-selection/parts/02-anatomy/2.1-opening-the-envelope.md).
  It answers instantly, identically, and for free, which is what makes every measurement in this day
  reproducible.
- `SENT` is a **module-level list**, not an attribute on the model. `BaseLlm` is a pydantic model, and
  a mutable class attribute on one is a trap worth avoiding rather than reasoning about.
- `class FixedSummarizer(BaseLlm)` — the summarizer is just another `BaseLlm`. `LlmEventSummarizer`
  takes any of them, so a fake one is a first-class option rather than a hack, which is what makes
  [5.2](../05-in-production/5.2-testing-compaction-without-quota.md) possible.
- `App(name="sutra", ...)` — the name must start with a letter and contain only letters, digits,
  underscores and hyphens, and it may not be `"user"`. ADK validates it and raises on construction.
- `events_compaction_config=EventsCompactionConfig(compaction_interval=2, overlap_size=1, ...)` — the
  whole feature, in one argument. `2` and `1` are explained in
  [2.2](2.2-the-turn-count-trigger.md); the important thing here is that they are on the **`App`**.
- `Runner(app=app, session_service=service)` — this is the wiring that matters. `Runner.__init__` is
  keyword-only and takes **exactly one** of `app`, `agent` or `node`; passing `app` is the form ADK's
  own docstring calls "the recommended way to create a runner". Passing `agent=` instead would build
  an `App` internally with no compaction config, and nothing would warn you.
- `record.events` is read **after** all four turns, from the session service rather than from the run
  loop, because the summary is appended by the Runner after an invocation finishes and is not one of
  the events yielded to you during it.
- `event.actions.compaction` is how a summary event is recognised. It is not the author and not the
  content — [3.1](../03-reading-the-record/3.1-the-summary-is-not-in-the-content.md) is entirely about
  why that surprises people.
- `await asyncio.sleep(0.05)` is not part of the mechanism and has no place in real code. These fake
  models answer faster than the operating system's clock ticks, and the compaction trigger compares
  event timestamps — so without it, successive invocations can share a timestamp and the results stop
  being reproducible between runs. [2.2](2.2-the-turn-count-trigger.md) shows the raw event log where
  that happens, and why it is a real hazard on a fast path rather than only a lab annoyance.
- `if __name__ == "__main__":` guards the run, so the later scripts in this day can import `app` and
  `QUESTIONS` from this file without four turns happening as a side effect of the import.

## When it breaks

**Constructing the config prints this, every time:**

```text
UserWarning: [EXPERIMENTAL] EventsCompactionConfig: This feature is experimental and may change or
be removed in future versions without notice. It may introduce breaking changes at any time.
```

That is not noise to suppress. It is the framework telling you that this API is not covered by ADK's
stability promise, and Principle 14 says what to do about it: when it changes, amend the plan first,
then the code. Pin the ADK version, and re-read `https://adk.dev/context/compaction/` on any upgrade.

**A config with half a trigger refuses to be built.** The two triggers are pairs, and each half is
useless alone:

```text
ValidationError: 1 validation error for EventsCompactionConfig
  Value error, compaction_interval and overlap_size must be set together. [type=value_error,
  input_value={'compaction_interval': 3}, input_type=dict]
```

```text
ValidationError: 1 validation error for EventsCompactionConfig
  Value error, token_threshold and event_retention_size must be set together. [type=value_error,
  input_value={'token_threshold': 4000}, input_type=dict]
```

**A config with no trigger at all is also refused**, which is a good design decision — a compaction
config that never compacts would be a silent no-op:

```text
ValidationError: 1 validation error for EventsCompactionConfig
  Value error, At least one compaction trigger must be configured: the token-threshold pair or the
  sliding-window pair. [type=value_error, input_value={}, input_type=dict]
```

All three were produced on 2026-09-03 by `lab/bad_config.py`, which builds four deliberately wrong
configs and prints what each one says.

**And the failure with no error text at all** is the one to actually watch for: writing
`Runner(agent=agent, app_name="sutra", session_service=service)` out of habit. That is still a valid
Runner, it still runs, and your `App` — with its compaction config — is simply not part of it. Nothing
warns. The only symptom is that no summary ever appears in the events, which you will not notice
unless you look.

## In production

**Build the `App` once, at module scope, and pass it around.** It is configuration, not per-request
state. Constructing a new `App` per request re-runs its validators, and worse, an `App` whose
compaction config has no explicit summarizer gets one *attached to it* on first use — ADK mutates the
config object — so a fresh `App` each time quietly re-derives that every request.

**What changes at scale** is that this one setting is now global to the application, and applications
grow more than one kind of conversation. A support thread and a one-shot classification call have
completely different compaction needs, and they share this config because they share an `App`. The
production answer is usually more than one `App` — one per workload — rather than one `App` with a
compromise setting in it.

**The failure that only appears with real traffic** is the upgrade. This is an experimental API, and
the warning says field names may change. A pinned version is not optional here in the way it is
merely advisable elsewhere: an upgrade that renames a field turns a running compaction into a
`ValidationError` at import, which at least is loud — or, if a field simply stops being read, into
silence.

**The review comment a senior engineer leaves:** *"we're constructing the Runner with `agent=` in
three places and `app=` in one. The three with `agent=` don't get compaction and nothing says so —
make the App the only entry point."*

**The interview question:** *"where does context compaction get configured in ADK, and why there?"*
The answer that shows you have wired it: *"on the App, not the agent, because the trigger is a
question about the session — how many invocations, how big the last prompt was — and an agent only
sees one turn. You pass the App to the Runner and the agent code is untouched."*
