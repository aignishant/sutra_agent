# 2.2 — The turn-count trigger: interval and overlap

## One-line answer

`compaction_interval` says **how many completed invocations** must pass before a summary is written,
and `overlap_size` says **how many earlier invocations get re-read** when it is written, so that two
consecutive summaries share a seam instead of butting up against each other.

## The story

The shop does a stock count every third delivery.

That is the rule, and it works. What the manager added after the first bad month is the second half
of the rule: when you count, you also recount the shelf you finished on last time.

The reason is what kept happening at the join. A box arrived, went half onto the old shelf and half
onto the new one, and got counted at neither end — once as "already done" by the person finishing the
old count, once as "before my bit" by the person starting the new one. Nothing was stolen. It simply
fell in the gap between two accurate counts.

One shelf of deliberate double-counting, and the gap closes.

## The idea in plain language

The turn-count trigger is two numbers, and the second exists to fix a problem the first one creates.

**`compaction_interval` — how often.** After every *n* completed invocations, write a summary. An
**invocation** is one press of the doorbell: one user message and everything the agent does in
response, however many events that turns into
([17.2.2](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.2-an-invocation-is-not-a-session.md)).
It counts invocations, not events, which is why a turn with six tool calls in it counts the same as a
turn with none.

**`overlap_size` — how far back to reach.** When a summary is written, start it this many invocations
*before* the new block rather than exactly where the last summary ended.

Without overlap, consecutive summaries cover strictly separate stretches: turns 1–2, then 3–4, then
5–6. Each is accurate about its own stretch and blind to the others. The thing that gets lost is
whatever spanned the join — a question asked at the end of turn 2 and answered at the start of turn
3, a decision that only makes sense with the reason that preceded it. Each summary sees half of it,
and half of a two-part thing usually summarizes to nothing.

With `overlap_size=1`, the new summary is handed the last invocation of the previous block as well.
It reads the seam. It also re-reads material a previous summary already covered, which costs
characters and is the point: **overlap buys continuity with duplication.**

ADK's own worked example, from the `google-adk` 2.7.1 source, with interval 2 and overlap 1:

| After invocation | What happens |
| --- | --- |
| 2 | first summary, covering invocations 1–2 |
| 3 | nothing: only one new invocation since the last summary |
| 4 | second summary, covering invocations **2**–4 — it reaches back one |

Note what the second row means in practice. Compaction does not fire on a schedule of wall-clock
time or on every turn. It fires when the count is reached, so between summaries the window grows
exactly as it always did.

## Why Sutra needs it

Because Sutra's conversations have joins in them, and the joins are where the meaning is.

A triage thread is a chain of question and answer: *"which browser?"* / *"Safari 17"*. Those two are
one fact spread across two invocations. A summary boundary that lands between them produces one
summary that says the agent asked about the browser and another that says the user said "Safari 17",
which is the shape of an answer with no question attached.

Day 53's graph work makes it worse, because a node boundary is another place a related pair can be
split. Getting the habit now — *the interval decides cost, the overlap decides coherence* — is what
stops that being a mystery later.

## The mechanism

Run the same six turns three times, with three settings, and record how many events each summarizer
call was actually handed.

```python
# days/day-20-context-engineering-compaction/lab/overlap.py
"""What each summary actually covered: the same six turns at three interval/overlap settings."""

import asyncio
from collections.abc import AsyncGenerator

from google.adk.agents import Agent
from google.adk.apps.app import App, EventsCompactionConfig
from google.adk.apps.llm_event_summarizer import LlmEventSummarizer
from google.adk.events.event import Event
from google.adk.models import BaseLlm, LlmRequest, LlmResponse
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

COVERED: list[int] = []


class Recorder(BaseLlm):
    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text="Noted.")]))


class Fixed(BaseLlm):
    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text="Summary.")]))


class CountingSummarizer(LlmEventSummarizer):
    """Exactly LlmEventSummarizer, plus a note of how many events each call was handed."""

    async def maybe_summarize_events(self, *, events: list[Event]) -> Event | None:
        COVERED.append(len(events))
        return await super().maybe_summarize_events(events=events)


async def run(interval: int, overlap: int) -> None:
    COVERED.clear()
    agent = Agent(name="desk", model=Recorder(model="recorder"), instruction="You are Sutra.")
    app = App(
        name="sutra",
        root_agent=agent,
        events_compaction_config=EventsCompactionConfig(
            compaction_interval=interval,
            overlap_size=overlap,
            summarizer=CountingSummarizer(llm=Fixed(model="minute-taker")),
        ),
    )
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=app, session_service=service)
    for n in range(1, 7):
        await asyncio.sleep(0.05)  # see 'When it breaks': events need distinct timestamps
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=f"question {n}")]),
        ):
            pass

    record = await service.get_session(app_name="sutra", user_id="priya", session_id=session.id)
    summaries = sum(1 for e in record.events if e.actions and e.actions.compaction)
    print(
        f"interval={interval} overlap={overlap}:  {summaries} summaries, "
        f"events handed to each = {COVERED},  {len(record.events)} events in the archive"
    )


asyncio.run(run(interval=2, overlap=0))
asyncio.run(run(interval=2, overlap=1))
asyncio.run(run(interval=3, overlap=1))
```

**Line by line:**

- `class CountingSummarizer(LlmEventSummarizer)` is the honest way to measure this. Rather than
  guessing from the prompt text how many events went in, it overrides the one method the framework
  calls and records `len(events)` before delegating with `super()`. The summarizer is a normal class
  with a normal extension point, which is worth knowing on its own.
- `maybe_summarize_events(self, *, events)` — keyword-only, matching the base class exactly. Getting
  that signature wrong produces a `TypeError` at compaction time rather than at import, which is a
  long way from where you made the mistake.
- `COVERED.clear()` at the top of `run` rather than a fresh list, so the three runs are directly
  comparable and one global holds the answer.
- `await asyncio.sleep(0.05)` is **not** part of the mechanism and would not appear in real code. The
  recording models answer faster than the operating system's clock ticks, so without it several
  invocations get identical timestamps and the trigger's arithmetic — which compares timestamps —
  quietly miscounts. *When it breaks* below shows exactly that, because it is a real thing that can
  happen to a real fast path.
- `range(1, 7)` — six invocations, chosen so that interval 2 fires three times and interval 3 fires
  twice, making the difference visible in one run.
- `summaries` counts events carrying `actions.compaction`; `COVERED` counts what went *into* each
  summarizer call. They are different questions and the interesting answer is the second one.

**Line by line:**

- Eighteen conversational calls and six summaries across the three runs, all against recording
  models: no key, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
interval=2 overlap=0:  3 summaries, events handed to each = [4, 4, 4],  15 events in the archive
interval=2 overlap=1:  3 summaries, events handed to each = [4, 6, 6],  15 events in the archive
interval=3 overlap=1:  2 summaries, events handed to each = [6, 8],  14 events in the archive
```

Every number in that output is the arithmetic above, made visible. Each invocation here produces two
events — one user message, one model reply — so events divided by two is invocations.

**Row 1, no overlap.** Three summaries, each handed exactly four events: invocations 1–2, 3–4, 5–6.
Disjoint, tidy, and blind at both joins.

**Row 2, overlap 1.** The first summary still gets four events, because there is nothing before
invocation 1 to reach back to. Every summary after it gets **six** — three invocations' worth — because
it re-reads the last invocation of the previous block. That is the seam being covered, and the extra
two events are what it costs.

**Row 3, interval 3.** Two summaries instead of three, so a third fewer summarizer calls, and the
second one is handed **eight** events: invocations 3–6, reaching back one from a block of three. The
larger interval saves calls and hands the summarizer more to compress each time, which is a harder
job and — per [1.2](../01-notes-not-transcript/1.2-summaries-are-lossy.md) — a lossier one.

The trade in one sentence: **a bigger interval costs fewer calls and loses more detail per summary; a
bigger overlap costs more characters and loses less at the joins.**

## When it breaks

**The clock is not fine enough, and the trigger under-counts.** This is what the `asyncio.sleep`
above is holding off. Without it, on Windows, six invocations against instant fake models produced
this event log — note the timestamps:

```text
0 1788436887.750882 73f83a  
1 1788436887.785808 73f83a  
2 1788436887.785808 1fee29  
3 1788436887.785808 1fee29  
4 1788436887.785808 6641a8 COMPACTION 1788436887.750882-1788436887.785808
5 1788436887.785808 49f06d  
6 1788436887.785808 49f06d  
```

Six events share one timestamp, because the system clock's resolution is coarser than the time these
models take to answer. The trigger decides which invocations are "new" by comparing each one's latest
timestamp against the end of the last summary with a strict `>`, so invocations that tie are not
counted as new. The measured effect was **two summaries instead of three**, with no error and nothing
in the logs.

You will not hit this with a real model, which takes far longer than a clock tick to answer. You can
hit it in tests, in replayed sessions, and anywhere events are constructed in a tight loop — which is
exactly where a fake model belongs, so it is worth recognising rather than debugging from scratch.

**And the interval never fires at all** if your conversations are shorter than it. An interval of 5 in
an application whose sessions average three turns is a feature that is configured, validated, warned
about, and never once invoked. Nothing reports this either; the only symptom is that the token numbers
never improve.

## In production

**Set the interval from the session-length histogram, not from taste.** The useful question is what
fraction of sessions ever reach the interval at all. If it is small, you are paying the validation and
the reasoning overhead for a feature that mostly does not run; if it is nearly all of them, check the
break-even from [1.3](../01-notes-not-transcript/1.3-you-spend-calls-to-save-calls.md) before going
smaller.

**Overlap 1 is the sane default and 0 is a false economy.** Zero saves a couple of invocations' worth
of characters per summary and buys a class of bug that is very hard to see: an answer whose question
has been summarized away in a different summary. The people who set it to 0 are usually optimising a
number they can see against a failure they cannot.

**What changes at scale** is that invocations stop being uniform. One invocation with a long tool
chain can be twenty events; another is two. An interval counted in invocations therefore controls
cost only loosely, and a session full of tool-heavy turns can grow enormous between two compactions
that are firing exactly as configured. That is the specific gap
[2.3](2.3-the-size-trigger.md) exists to close.

**The review comment a senior engineer leaves:** *"overlap 0 with an interval of 2 means every
question-and-answer pair that straddles a boundary gets split across two summaries. Set overlap to 1
unless we have measured that we cannot afford it."*

**The interview question:** *"what does the overlap setting on a sliding-window summarizer buy you?"*
The answer that shows you have run it: *"continuity across the seam. Without it consecutive summaries
cover disjoint ranges and anything spanning the boundary — a question in one range, its answer in the
next — is summarized by two summarizers that each only saw half. It costs one invocation's worth of
duplicated text per summary."*
