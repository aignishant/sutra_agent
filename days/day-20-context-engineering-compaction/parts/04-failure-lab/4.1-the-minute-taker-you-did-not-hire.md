# 4.1 — 💥 The minute-taker you did not hire

## One-line answer

Leave `summarizer` out of the config and ADK does not skip summarizing — it quietly appoints **your
chat model** to do it, so four conversational turns became six requests to the expensive model.

## The story

You ring the agency and ask for someone to come in and do the filing.

You do not say who. You say *"someone from your side, whoever's free"*, because the filing is filing
and it did not seem worth a conversation.

What turns up is the consultant. The one on the day rate. He is perfectly willing, he does the filing
competently, and at the end of the month you get an invoice that is four times what you had in your
head — not because anybody did anything wrong, but because you left the choice open and the default
was expensive.

Nobody hid anything from you. You did not ask.

## The idea in plain language

`EventsCompactionConfig` has a `summarizer` field, and it is **optional**. Leaving it out is legal, the
config validates, and compaction works.

What ADK does when it is missing is the part worth knowing. On the first compaction it looks at the
`App`'s root agent, takes that agent's model, wraps it in an `LlmEventSummarizer`, and **writes it back
into your config object**. From then on your chat model is the summarizer, permanently, for the life of
that `App`.

That is a defensible default — a working summarizer beats a crash, and the root agent's model is the
one thing ADK is certain exists — and it is the wrong choice for essentially every real application,
for three separate reasons.

**It is the most expensive model you own.** The chat model is chosen for reasoning quality on the hard
task. Summarizing a transcript is not the hard task.

**It spends the wrong quota.** On Gemini's free tier the daily request limit is per model
([1.3](../01-notes-not-transcript/1.3-you-spend-calls-to-save-calls.md) has the live 429 that says
so). Summaries written by the chat model come out of the chat model's allowance, which is the exact
allowance you need for answering users.

**It is invisible.** There is no warning, no log line at default level, and no field to inspect until
after the first compaction has already happened. The only way to find out is to count requests, which
is what this part does.

This is the same reflex as **ADK-73**, the trap from
[Day 5](../../../day-05-first-adk-agent/LESSON.md): ADK 2.2 changed the *default model* for agents
without an explicit `model=`, and Sutra's rule since then has been that every agent pins its model
explicitly. The summarizer is an agent's model by another name, and it deserves the same rule.

## Why Sutra needs it

Because Sutra runs on 20 requests per day per model, and this bug spends them on notes.

The measurement below is four conversational turns costing six requests. Scale that to Sutra's daily
allowance and the arithmetic is brutal: a 20-request budget becomes about 13 usable turns, and the
seven that vanished went to summarizing the thirteen. On a metered free tier that is not an
inefficiency, it is a third of the day.

Day 24 builds the budget accounting that would have caught this, and Day 70's quota router depends on
knowing which model each call is charged to. Neither works if a whole category of calls is being made
by a component nobody configured.

## The mechanism

Configure compaction with **no summarizer**, point the chat model at a recorder that classifies every
request it receives, and count.

```python
# days/day-20-context-engineering-compaction/lab/who_writes_the_minutes.py
"""Leave `summarizer` out of the config and find out who ends up doing the summarizing."""

CALLS: list[str] = []


class Recorder(BaseLlm):
    """The expensive chat brain. Records whether each call was a chat or a summarization."""

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        first = llm_request.contents[0].parts[0].text or ""
        CALLS.append("SUMMARIZE" if "conversation history" in first else "chat")
        yield LlmResponse(content=types.Content(role="model", parts=[types.Part(text="Noted.")]))


agent = Agent(
    name="desk", model=Recorder(model="expensive-chat-model"), instruction="You are Sutra."
)

app = App(
    name="sutra",
    root_agent=agent,
    events_compaction_config=EventsCompactionConfig(compaction_interval=2, overlap_size=1),
)


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=app, session_service=service)
    for question in ["first question", "second question", "third question", "fourth question"]:
        await asyncio.sleep(0.05)  # distinct timestamps; see 2.2 'When it breaks'
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=question)]),
        ):
            pass

    print(f"calls made to '{agent.model.model}': {len(CALLS)}")
    for i, kind in enumerate(CALLS, start=1):
        print(f"  {i}: {kind}")
    print(f"\nsummarizer actually used: {type(app.events_compaction_config.summarizer).__name__}")
    print(f"its llm: {app.events_compaction_config.summarizer._llm.model}")


asyncio.run(main())
```

**Line by line:**

- `EventsCompactionConfig(compaction_interval=2, overlap_size=1)` — **no `summarizer` argument.** This
  is the whole bug, and it is what the field being optional looks like in code that someone wrote in a
  hurry.
- `model="expensive-chat-model"` is a label, not a real model string. Naming it this way means the
  final line of output states the problem in words rather than leaving you to infer it.
- `"conversation history" in first` classifies each request. That phrase is from ADK's own default
  summarization prompt, which begins *"The following is a conversation history between a user and an
  AI agent"* — read from `google/adk/apps/llm_event_summarizer.py` in `google-adk` 2.7.1 on
  2026-09-03. A chat turn never contains it; a summarization request always does.
- `llm_request.contents[0]` — the summarization prompt is a single message, so the first one is the
  whole thing. For a chat turn it is the oldest message in the history, which never matches either.
- `app.events_compaction_config.summarizer` is read **after** the run, and this is the point of the
  file: before the first compaction that field is `None`. ADK fills it in on first use by mutating the
  config you built.
- `._llm` is a private attribute, and using one in teaching code deserves a note. There is no public
  accessor for the model behind a summarizer, and the question *"which model is about to be billed"*
  is worth reaching past a convention to answer. In production code you would not read it — you would
  set the summarizer yourself and never need to ask.

**Line by line:**

- Everything is a recording model, so this counts what *would* have been spent without spending it.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
calls made to 'expensive-chat-model': 6
  1: chat
  2: chat
  3: SUMMARIZE
  4: chat
  5: chat
  6: SUMMARIZE

summarizer actually used: LlmEventSummarizer
its llm: expensive-chat-model
```

**Four turns. Six requests.** Fifty per cent more traffic to the expensive model than the conversation
required, from a config that is one field short and that validates without complaint.

**Calls 3 and 6 are summarizations**, and they land immediately after the second and fourth
invocations — the interval firing exactly as configured. The feature is working perfectly. It is the
staffing that is wrong.

**And the last line names the culprit**: `its llm: expensive-chat-model`. That field was `None` when
the `App` was constructed. ADK derived it from `app.root_agent` on the first compaction and stored it
back, which is why you can read it afterwards and cannot read it before.

The fix is one argument:

```python
EventsCompactionConfig(
    compaction_interval=2,
    overlap_size=1,
    summarizer=LlmEventSummarizer(llm=Gemini(model="gemini-3.5-flash-lite")),
)
```

**Line by line:**

- `summarizer=` — the field that was missing. Present, it is never derived, and nothing is decided for
  you.
- `Gemini(model="gemini-3.5-flash-lite")` — a lite-lane model, pinned explicitly. It was confirmed
  present on the live model listing on 2026-09-03, supporting `generateContent`; see
  [5.1](../05-in-production/5.1-budgeting-the-minute-taker.md) for why it is *that* string and not the
  one you would guess.
- Both numbers stay as they were. Nothing about the trigger changes — only who does the work.

## When it breaks

**With no summarizer and a root that is not an `LlmAgent`,** the derivation has nothing to derive from
and you get the one loud version of this failure:

```text
ValueError: No LlmAgent model available for event compaction summarizer.
```

That message is only ever seen by people whose root is a workflow node rather than an agent, which
from Phase 8 onwards is a normal thing to have. It is worth recognising, because the fix is not
obvious from the wording: the missing thing is not an agent, it is the `summarizer` field you did not
set.

**And the quiet version is the one above**, with no error at all: a request count that is half as
large again as your conversation count, discovered — if at all — on the provider's dashboard rather
than in your logs.

## In production

**Make it a lint rule, not a habit.** An `EventsCompactionConfig` constructed without `summarizer` is
mechanically detectable, and Day 31's `./m check` is where Sutra's repo-wide rules of this shape live —
alongside the `:free` suffix check from
[Addendum 02](../../../../docs/02_ADDENDUM_ZERO_BUDGET_MODELS.md). A rule that runs beats a convention
that is remembered.

**What changes at scale** is that summarizer traffic becomes a meaningful fraction of total traffic
and nothing in your instrumentation separates it. Both kinds of call go to the same model, on the same
client, with the same credentials, and appear on the same line of the provider's usage page. Pointing
the summarizer at a different model is not only cheaper — it makes the spend *visible*, which is worth
something on its own.

**The failure that only appears with real traffic** is latency-shaped rather than cost-shaped. The
summarizer runs after the invocation completes, so it does not delay the user's answer, but it does
occupy a slot in whatever concurrency limit your provider applies. Under load, summaries and user
turns compete, and the requests that get rate-limited are whichever arrive second.

**The review comment a senior engineer leaves:** *"the compaction config has no summarizer, so it'll
inherit the root agent's model. That's our most expensive model doing note-taking — pin the lite model
explicitly."*

**The interview question:** *"what happens if you don't specify a summarizer for context
compaction?"* The answer that shows you have measured it: *"ADK derives one from the root agent's
model and writes it into your config, so your chat model summarizes. On a four-turn conversation with
an interval of 2 that took us from four requests to six, all on the expensive model, with no warning.
Always pin the summarizer."*
