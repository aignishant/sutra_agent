# 4.2 — 💥 The fact that was true and is now gone

## One-line answer

Turn compaction on and the user's instruction *"do not close the ticket"* leaves the window
completely — no error, no warning, a 32% smaller request, and an agent that has never been told.

## The story

Somebody takes a phone message for you while you are out.

They write it on the pad by the phone, and what they write is accurate: *"Ravi called about the
delivery, ring him back."* You ring him back. He is confused, because what he actually said was
*"tell them not to send the second pallet until I confirm the address"*, and that is now in nobody's
head.

The person who took the message did not do it badly. They wrote down what the call was about. The
instruction inside the call was not what the call was about — it was a detail — and details are what
a message loses.

You would only ever find out by asking Ravi.

## The idea in plain language

This is [1.2](../01-notes-not-transcript/1.2-summaries-are-lossy.md) with the safety off.
There the loss was measured against a summary sitting in a file. Here it happens inside a running
agent, at the point it actually matters, and the measurement is the same one an operator would have
to make to notice: **is the fact still in the request being sent?**

The failure has four properties, and each one makes it harder to catch than the last.

**It is silent.** No exception, no warning, no log line at default level. The turn succeeds.

**It is invisible from the transcript.** The instruction is still in the session's event log, exactly
where the user typed it. Anyone reviewing the conversation afterwards sees the user say *"do not close
this ticket"* and the agent close it, and concludes the model disobeyed. The model was never asked.

**It is intermittent.** Whether a given fact survives depends on what the summarizer judged
important, which varies with the model, the temperature, the other turns, and the prompt template. The
same conversation can pass a hundred times and fail on the hundred and first.

**And it looks like a model quality problem.** The natural response — a stronger chat model, a firmer
instruction, an eval on the answer — fixes nothing, because the chat model is behaving correctly given
its input. The bug is upstream of the model, in what the window contained.

The ablation below is the diagnostic that separates the two. Run the same conversation with compaction
off and on, and probe the final request for the fact. If it is present in one and absent in the other,
the model was never the problem.

## Why Sutra needs it

Because *"do not close the ticket"* is not a hypothetical for Sutra — it is the shape of most
instructions a support engineer gives it.

Sutra's triage flow ends in an action: close, escalate, reply, assign. The constraints on those
actions arrive conversationally, early, and once. *This is a managed customer. The refund is not
signed off. Do not contact them before Monday.* Every one of them is a detail rather than a subject,
and every one changes the ending.

Day 21 builds error surfacing, Day 64 builds the human approval gate, and Day 66 onwards is the safety
phase. All three assume that a constraint, once given, holds. Today is the day that assumption is
shown to be false by default, and [1.4](../01-notes-not-transcript/1.4-what-must-never-be-summarized.md)
is the fix.

## The paper behind it

> **MemGPT: Towards LLMs as Operating Systems**
> `arXiv:2310.08560` · 2023 · <https://arxiv.org/abs/2310.08560>

It claimed that an agent should be able to **page a fact back in** when it turns out to be needed,
rather than depending on having guessed correctly, when the summary was written, about what would
matter later.

That is the direct answer to the failure this part demonstrates, and it is taught in
[the paper part](../../papers/01-memgpt.md).

## The mechanism

The same four turns, twice, with compaction as the only difference, probing the last request for two
phrases the user actually typed.

```python
# days/day-20-context-engineering-compaction/lab/lost_in_the_minutes.py
"""A true, tidy summary that drops one fact - and the proof that the fact left the window."""

TIDY_SUMMARY = (
    "Conversation Language: English. The user reported ticket 4521: customers are being logged "
    "out. The cause was identified as the SameSite cookie change in KB-104."
)

TURNS = [
    "Ticket 4521: customers logged out. Note the refund for this customer is still awaiting "
    "sign-off from finance - do not close the ticket.",
    "Is that the SameSite cookie change in KB-104?",
    "What severity would you assign it?",
    "Can we close the ticket now?",
]


def build_app(compact: bool) -> App:
    agent = Agent(name="desk", model=Recorder(model="recorder"), instruction="You are Sutra.")
    if not compact:
        return App(name="sutra", root_agent=agent)
    return App(
        name="sutra",
        root_agent=agent,
        events_compaction_config=EventsCompactionConfig(
            compaction_interval=2,
            overlap_size=1,
            summarizer=LlmEventSummarizer(llm=TidySummarizer(model="minute-taker")),
        ),
    )


async def run(compact: bool) -> None:
    SENT.clear()
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="priya")
    runner = Runner(app=build_app(compact), session_service=service)
    for turn in TURNS:
        await asyncio.sleep(0.05)  # distinct timestamps; see 2.2 'When it breaks'
        async for _ in runner.run_async(
            user_id="priya",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text=turn)]),
        ):
            pass

    final = SENT[-1]
    window = str(final.contents)
    print(
        f"COMPACTION={'on ' if compact else 'off'}  last call: {len(final.contents)} messages, "
        f"{len(window)} chars"
    )
    print(f"   'sign-off from finance' still in the window? {'sign-off' in window}")
    print(f"   'do not close the ticket' still in the window? {'do not close' in window}")


asyncio.run(run(compact=False))
asyncio.run(run(compact=True))
```

**Line by line:**

- `TIDY_SUMMARY` is the villain, and it is worth reading twice: **every clause in it is true.** It
  names the ticket, the symptom and the cause correctly. It is exactly what a competent summarizer
  produces, and it is exactly what a competent summarizer leaves out — the constraint, which was not
  what the conversation was about.
- It is a fixed string rather than a live model for two reasons. It makes the run reproducible, and it
  makes the point unarguable: this is not a bad summarizer having a bad day, it is a good summary doing
  its job.
- `TURNS[0]` carries the instruction **inside a longer message**, the way a real user types it, rather
  than as a message of its own. A fact buried mid-sentence is exactly the fact a summary drops.
- `build_app(compact)` is the ablation switch: the same agent, the same turns, one `App` with the
  config and one without.
- `'sign-off' in window` and `'do not close' in window` are the probes, deliberately short and
  lowercase-matched against text that contains them verbatim. A probe that is too specific fails for
  the wrong reason and teaches nothing.
- `str(final.contents)` flattens the whole history organ to one string. Crude, and correct for this
  question: if the phrase is nowhere in the assembled history, the model cannot have read it.
- `SENT[-1]` — the **last** request. Earlier ones still contain the fact, which is why the bug survives
  casual testing: it only appears once enough turns have passed for a compaction to have covered turn
  one.


**Line by line:**

- Eight turns and two summaries across the two runs, all against recording models: no key, no quota,
  and a failure you can reproduce on a plane.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
COMPACTION=off  last call: 7 messages, 767 chars
   'sign-off from finance' still in the window? True
   'do not close the ticket' still in the window? True
COMPACTION=on   last call: 4 messages, 518 chars
   'sign-off from finance' still in the window? False
   'do not close the ticket' still in the window? False
```

Four probes, and the pattern is as clean as this kind of failure ever gets.

**With compaction off, both facts are in the window.** The reason the ticket is open and the
instruction not to close it are both sitting in the final request, in the words the user typed, on the
call where the model is asked whether to close it.

**With compaction on, both are gone.** Same conversation, same code, one boolean different — and the
summary that replaced them is entirely true and mentions neither.

**And the window is 32% smaller** — 767 characters down to 518, seven messages down to four. That is
the saving, and it is real, and those two facts are the price.

The last turn is *"Can we close the ticket now?"*. With compaction off, the model has the reason not
to, in the window, where it can read it. With compaction on, the honest answer to that question, given
what the model can see, is **yes**.

One note on the probes themselves, because it is the mistake this kind of test invites. `'sign-off' in
window` is a substring match on a flattened string, and a probe like that can report `False` because
the fact is gone or because the *phrasing* moved — a different case, a line break, an escape. Yesterday's
[19.6.1](../../../day-19-context-engineering-selection/parts/06-in-production/6.1-testing-what-goes-in-the-window.md)
made the same point about an assertion that passes for the wrong reason; this is the version that fails
for the wrong reason. The uncompacted run is what rules it out here: both probes return `True` there,
so they are known to match the text as written, and only then does `False` on the compacted run mean
what it appears to mean. **An absence probe is only trustworthy standing next to a presence probe.**

## When it breaks

There is no traceback. The failure is a reply that is correct given the window and wrong given the
conversation:

```text
reply: Yes - the cause is identified and documented in KB-104, so I have closed ticket 4521
and notified the customer.
```

And the second failure is the investigation that follows. An engineer opens the session, reads the
user's message saying not to close it, reads the agent closing it, and files a bug against the model's
instruction-following. Everything in that reasoning is sound except the assumption that the model saw
the transcript.

The diagnostic that ends the argument is the one above: probe the assembled request, not the session.
If the phrase is absent from `llm_request.contents`, the model's behaviour was never in question.

## In production

**Store the assembled request, or at least a hash and a size, for a sample of calls.** Without it,
*"what was actually in the window"* is unanswerable after the fact, and every incident of this class
becomes an argument about the model. This is the same recommendation as
[3.2](../03-reading-the-record/3.2-what-the-model-sees-after-a-compaction.md), reached from the other
direction, which is a reasonable sign it is the right one.

**What changes at scale** is that the failure rate becomes a function of the summarizer, not of your
code. A model upgrade, a temperature change, or a change to the prompt template moves it, silently
and in either direction. It is the only bug in this day whose frequency you do not control by
configuration.

**The failure that only appears with real traffic** is the constraint given once, early, in a long
session — which is precisely the profile of the most important instructions users give. Short test
conversations never compact, so this class of bug has no way to appear in testing at all.
[5.2](../05-in-production/5.2-testing-compaction-without-quota.md) is how to make it appear on
purpose.

**The review comment a senior engineer leaves:** *"this test asserts the model refuses to close the
ticket, and it passes because the conversation is too short to compact. Add a variant that runs past
the interval and assert on the request contents, not the reply."*

**The interview question:** *"an agent ignored an instruction the user clearly gave it. How do you
find out why?"* The answer that shows you have debugged it: *"first I check whether the instruction
was in the window on the call that ignored it, rather than whether it was in the transcript. With
summarization on, those are different things — I've had a constraint drop out of the window entirely,
with a 32% smaller prompt and no error. If it was in the window, then it's a model problem; if it
wasn't, no model would have got it right."*
