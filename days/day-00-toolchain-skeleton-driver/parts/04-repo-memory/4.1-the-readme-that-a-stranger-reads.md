# 4.1 — The README a stranger reads

## One-line answer

A README is not a description of your project — it is the **first thirty seconds** of someone else's
experience of it, and its job is to answer *what is this, why would I care, and what do I type
first* before they decide to close the tab.

---

## The story

Somebody is looking for a piece of software that does a specific thing. They find three
repositories that might.

The first one's README opens with a logo, six badges, and a paragraph that begins *"A modern,
flexible, extensible framework for..."*. They read it twice. It is not clear what the software
actually does, only what adjectives its author would like associated with it. They scroll, find an
installation section, and close the tab.

The second one's README is a wall of API documentation — every function, every parameter, complete
and correct. It never says what problem the library solves. They close the tab.

The third one's README opens with one sentence saying what it is, one short block showing it in use,
and one command to try it. They try it. It works. They read further.

None of the three projects is better software than the others. The third one is simply the only one
that treated the README as **the reader's first thirty seconds** rather than as *a place to put
information about the project*.

Now change one detail, because it is the version that matters more here. The stranger is **you, in
eight months**, opening a repository you have not touched since spring — with no memory of where you
were, what was working, or what you were about to do next.

---

## The idea in plain language

**A README answers four questions, in this order.** The order matters more than the content,
because a reader stops as soon as they have what they came for — or as soon as they conclude they
will not get it.

| # | Question | If it is missing |
| --- | --- | --- |
| 1 | **What is this?** In one or two sentences, in concrete nouns. | The reader cannot tell whether to keep reading. |
| 2 | **Why would I care?** What problem it solves, what makes it different. | They read on with no reason to. |
| 3 | **What do I type first?** One command, that works. | They have to reverse-engineer the entry point. |
| 4 | **Where do I go next?** Links, laid out by intent. | They read the whole file looking for the part meant for them. |

Two failures follow from getting the order wrong, and both are common:

**Opening with abstractions.** *"A modern, flexible framework for orchestrating..."* is a sentence
about a category, not about a thing. Concrete nouns beat adjectives: *"an autonomous support-ticket
triage desk"* tells you more in six words than a paragraph of "flexible" and "extensible" ever will.

**Confusing a README with documentation.** A README is a *front door*, not a house. Its job is to
get the reader to the right room quickly. When it tries to be the whole documentation it becomes
long, and when it becomes long the first thirty seconds are spent scrolling.

### Sutra's README has an unusual second audience

Most READMEs are written for a stranger who might use the software. Sutra's is written for **three**
readers, and they want different things:

- **A stranger evaluating it** — an interviewer, a hiring manager, someone who found the repository.
  They want to know what it is and whether it is any good, in under a minute.
- **You, returning after a gap.** You want `./m status` and the last row of `docs/PROGRESS.md`.
- **A CLI agent picking up where the last session stopped.** This is the plan's second commitment —
  *the repo is the memory, not the chat* — and it is unusual enough to state. An agent reads the
  README, then `CLAUDE.md` ([4.2](4.2-claude-md-the-standing-contract.md)), then the ledgers, and
  from those alone it must be able to continue. There is no conversation to inherit.

That third reader is why the README's link table is organised **by intent** — *"you want X → read Y"*
— rather than as a list of files. A list of files makes a human scan; a table of intents makes both
a human and a machine land in one hop.

> 💡 **The mental model:** the README is the **entry point**, in exactly the sense `./m` is
> ([3.2](../03-the-m-driver/3.2-the-case-dispatcher.md)). One place that routes every arrival to the right
> destination, so nobody has to guess where to start.

## The mechanism

Write `README.md` in the project root. This is the skeleton; fill it with Sutra's actual content.

````bash
cat > README.md <<'EOF'
# 🧵 Sutra

**Sutra** (Sanskrit सूत्र) means *thread* — the thread that strings concepts together, and the
thread of execution that runs through a multi-agent system.

Sutra is two things at once:

1. **A product** — an autonomous support-ticket triage desk. Tickets arrive; a graph of agents
   classifies, researches, drafts and reviews a response; anything that writes to the outside
   world waits for a human. It runs on **$0** of model spend.
2. **A 97-day curriculum that builds it**, one day at a time — Google **ADK 2.x**, **MCP**,
   **Agent Skills** and **A2A**.

## Start here

```bash
./m status          # where am I
./m start 0         # open Day 0's hub and list its parts
```

| You want | Read |
| --- | --- |
| The contract — what this is and how it is built | `docs/00_MASTER_PLAN.md` |
| How to read a day | `days/README.md` |
| Where I am | `docs/PROGRESS.md` · `docs/TRACKER.md` |

## The driver

`make` is not used. `./m` is: `status` · `start N` · `depth [N]` · `check` · `done N`.
EOF
````

**Line by line:**

- The outer fence uses **four** backticks so the three-backtick block inside it survives. This is the
  standard way to show a Markdown file that itself contains code — and if you have ever wondered why
  a nested block breaks, this is the reason and the fix.
- `cat > README.md <<'EOF'` — the heredoc from [2.2](../02-repo-skeleton/2.2-gitignore-before-secrets-exist.md),
  with `'EOF'` quoted so the `$` in `$0` stays literal instead of being expanded by bash.
- `# 🧵 Sutra` then a one-sentence definition — question 1, answered before anything else. The name's
  meaning is included because it makes the project memorable, which is worth two lines.
- **"Sutra is two things at once"** — question 2. The numbered pair is doing real work: this
  repository is genuinely a product *and* a curriculum, and a reader who only sees one of those will
  misjudge everything else in it.
- **"an autonomous support-ticket triage desk"** — concrete nouns. Compare against *"a flexible
  agent framework"*, which is the sentence the story was about.
- **`$0` of model spend** — the constraint stated up front, because it is one of the more
  interesting things about the project rather than an apology for it.
- `## Start here` with a runnable block — question 3. It appears **above** the link table, because
  someone who wants to try it should not have to read a table first.
- The table is keyed on **"You want"**, not on filenames — question 4, organised by intent so both a
  human and an agent land in one hop.
- `## The driver` — the one non-obvious convention in the repository, stated early. A reader who
  expects `make` needs to be told once, not left to discover it.

Then check every command in it actually works — a README with a broken first command is worse than
no README, because it spends the reader's trust before anything else does:

```bash
grep -oE '\./m [a-z]+' README.md | sort -u
```

**Line by line:**

- `grep -o` — print **only** the matching part of each line, not the whole line. Without it you get
  surrounding prose and cannot see the commands.
- `-E` — extended regular expressions, so `+` means "one or more" without needing a backslash.
- `'\./m [a-z]+'` — a literal `./m` (the `.` is escaped, since an unescaped dot matches any
  character) followed by a space and a lowercase word.
- `sort -u` — sort and remove duplicates, giving the distinct set of commands the README promises.
- **Run each one.** Every command a README shows is a promise, and every broken promise in the first
  thirty seconds costs more than the content it was trying to deliver.

## When it breaks

**The command that no longer exists:**

```text
$ ./m verify
usage: ./m <command> [day]

  status         one line: how many days are written / complete
  ...
```

The README said `./m verify`; the script's verb is `check`. Nothing crashed — the `*)` catch-all from
[3.2](../03-the-m-driver/3.2-the-case-dispatcher.md) printed the menu, which is the friendliest possible failure —
but the reader has just learned that the documentation and the code disagree, and that is the piece
of information they will carry into everything else they read here. **The fix** is the `grep` above,
run whenever the driver changes.

**The relative link that works on your disk and not on the web:**

```text
404 — This is not the web page you are looking for.
```

A link written as `[the plan](/docs/00_MASTER_PLAN.md)` with a leading slash resolves to the *host's*
root, not the repository's. **Use repository-relative links** — `[the plan](docs/00_MASTER_PLAN.md)`
— which work both in an editor's preview and on a git host. Check them before Day 93, when the
repository goes public and every broken link is visible.

**The nested code fence that swallows the rest of the file.** If you write the README with a
three-backtick heredoc containing three-backtick blocks, the first inner fence closes the outer one
and the remainder of your intended file is interpreted as shell commands:

```text
$ cat > README.md <<'EOF'
> # Sutra
> ```bash
> ./m status
> ```
> EOF
$ bash: ./m status: command not found
```

The shell has started executing your README. **The fix** is the four-backtick outer fence used in
*The mechanism* above — the closing fence must be **at least as long** as the opening one, so a
shorter inner fence cannot end it.

**The README that grew into documentation.** No error message, and the symptom is that people stop
reading it — you notice because they ask questions the README answers on line 240. **The fix is
structural, not editorial:** move the detail to `docs/` or `days/README.md` and leave a link. The
README's length is a feature of its job, not a limitation.

## In production

**The README is the highest-traffic file in any repository, by a wide margin.** It is what a search
result shows, what a package page renders, and what a reviewer opens first. Time spent on it has a
better return than time spent on almost any other document — and it is the file most often written
once, at the start, and never revisited.

**Keep it honest about status.** A README describing features that do not exist yet is the fastest
way to lose a reader's trust permanently, because they will discover it by trying something. Sutra's
README has a short **Status** section stating that days are being regenerated and pointing at
`./m status` for the live number. **A project that says where it actually is reads as more
trustworthy than one that implies it is finished**, and the cost of saying so is two sentences.

**Badges are a tool, not decoration.** A build-status badge is genuinely useful: it tells a stranger
whether the tests pass *right now*, without them cloning anything. Six badges for things nobody
checks are visual noise ahead of the sentence that says what the project is. **The test: would a
reader make a different decision based on this badge?**

**Automate the parts that can go stale.** Any command shown in a README should ideally be one that CI
also runs — which is exactly why the README says `./m check` rather than listing the five steps
([3.2](../03-the-m-driver/3.2-the-case-dispatcher.md)). Some projects go further and *execute* their README's code
blocks in CI. That is worth doing when the README shows usage examples of an API; it is overkill for
a project whose README shows two commands, and knowing where that line is stops you building a test
harness for a table of contents.

**What degrades at scale.** In a monorepo, one root README cannot serve twelve packages, so each
package gets one and the root becomes a *map*. The failure mode there is the root README that lists
every package with no indication of which one you want — a directory listing with extra steps.
**The fix is the same as the table above: organise by intent, not by inventory.**

**The review comment a senior engineer leaves.** On a pull request adding a feature with no README
change: *"This adds a new command — does the README still describe how to use this project? A
feature nobody can discover is a feature that doesn't exist."* The point is that documentation is
part of the change, not a follow-up task, because a follow-up task is a task that does not happen.

**The interview question.** *"Send me a repository you're proud of."* Nobody says it out loud, but
the README is being evaluated before the code is — because it is the only artifact that reveals
whether you think about the person on the other side. A README that opens with what the thing is,
shows one command that works, and honestly states where the project has got to tells a reviewer more
about how you would behave on a team than a thousand well-formatted lines of source.
