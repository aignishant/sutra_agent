# 3.2 — The `case` dispatcher: one script, one entry point

## One-line answer

A `case` statement turns one file into a **menu of verbs** — `./m check`, `./m depth 0`,
`./m done 0` — so that every repeated command in the project has exactly one definition, in one
place, that a person and a machine can both run.

---

## The story

A team has a README with a section titled "Common commands". It lists nine of them. Every one is
correct on the day it is written.

Three months later the test command has grown a flag. Somebody updates it in the CI configuration,
because that is where it was failing. The README still says the old thing. A new joiner copies the
README version, gets a different result from CI, and spends an hour deciding which of them is
broken.

Then the linter is added. It goes into CI, and into a pre-commit hook, and into the README — three
copies of one command, each of which can drift independently. The formatter arrives with a
`--check` flag in CI and without it locally, so CI reformats nothing and complains, while a
developer's machine reformats silently and produces a diff nobody asked for.

Nobody made a bad decision. Every copy was added by somebody solving a real problem in the place
they were standing. But the project now has **four sources of truth about what "run the checks"
means**, and they only agree by coincidence.

The alternative is boring and works. One file holds the definition. The README says `./m check`. CI
runs `./m check`. The hook runs `./m check`. When the command needs a flag, it changes in one place
and everybody gets it — including CI, including the new joiner, including you in six months.

---

## The idea in plain language

**`case` is bash's pattern-matching branch.** It takes a value, compares it against a list of
patterns, and runs the first block that matches:

```text
case "$WORD" in
  hello)   echo "a greeting" ;;
  good*)   echo "starts with good" ;;
  a|b|c)   echo "one of three letters" ;;
  *)       echo "anything else" ;;
esac
```

**Reading it:**

- `case "$WORD" in` — the value being matched, quoted so that a value containing a space stays one
  value.
- `hello)` — a pattern, followed by `)`. These are **glob patterns**, the same wildcards the shell
  uses for filenames — *not* regular expressions. `*` matches anything, `?` matches one character,
  `[abc]` matches one of a set.
- `;;` — ends a branch. Unlike C-style switches, bash does **not** fall through to the next branch,
  so there is no `break` to forget.
- `a|b|c)` — several patterns for one branch, separated by `|`.
- `*)` — matches everything, and because branches are tried in order, a `*)` placed last is the
  default case. Placed first, it would swallow everything — order is the only thing that makes a
  catch-all safe.
- `esac` — `case` spelled backwards, which is how bash closes several of its blocks (`if`/`fi`).

### Arguments

A bash script receives its arguments as numbered variables: `$1`, `$2`, and so on. `./m depth 0`
gives `$1="depth"` and `$2="0"`.

Under `set -u` from [3.1](3.1-set-euo-pipefail.md), reading `$2` when it was not supplied is an
error — which is correct behaviour and needs handling rather than switching off:

```text
DAY="${2:-}"
```

That is the default-value expansion: *the value of `$2`, or an empty string if there is not one*.
Optionality is now declared instead of accidental.

### Why not `make`

`make` is the traditional answer, and it is a good tool with a specific job: rebuilding files when
the files they depend on have changed. Sutra's commands are not that — nothing here produces a file
from another file — so `make`'s central feature is unused, while its costs remain: a syntax where a
tab and a space mean different things, and a program that **is not installed on Windows**.

That last point is decisive. A gate nobody can run is not a gate. Git Bash
([1.2](../01-toolchain/1.2-git-and-the-unix-shell.md)) gives every contributor bash; nothing gives every
contributor `make`. So `./m` is a bash script, and a two-line `Makefile` shim exists only so that
`make check` still reaches it for anyone with the muscle memory.

```mermaid
flowchart TB
    U["you"] --> M["./m &lt;verb&gt; [day]"]
    CI["CI"] --> M
    H["a git hook"] --> M
    M --> C{case "$1"}
    C -->|check| A["ruff · pytest · depth · trace"]
    C -->|depth| B["uv run scripts/depth_check.py"]
    C -->|start| D["print the hub, list the parts"]
    C -->|done| E["gate, then commit"]
    C -->|anything else| H2["print usage"]
    style M fill:#1f6feb,color:#fff
```

> 💡 **The mental model:** `./m` is the project's **front door**. Everything a human or a machine
> repeatedly does to this repository goes through it, so there is exactly one definition of each
> action and no way for two of them to drift apart.

## Why Sutra needs it

- **Every day ends with `./m check` and `./m done N`.** Ninety-seven days of a command that must
  mean the same thing each time.
- **Principle 6 — verify the whole project after every step.** *"Each day ends with the full check
  suite green, not just today's snippet."* That is only enforceable if "the full check suite" is one
  name rather than a description someone reassembles from memory.
- **Day 31 is the quality gate** (SK-20, OPS-08). `./m check` grows a skills lint and a lint
  asserting every `openrouter/` model string ends in `:free`. When it grows, it grows once — CI, the
  README and your terminal all get it at the same moment.
- **Day 82 puts evals in CI** (OPS-15, ADK-62). CI running `./m check` rather than its own list is
  what guarantees a green build means the same thing as a green terminal.
- **The repo is the memory, not the chat.** A stranger cloning this repository needs one command to
  find out whether it is healthy. `./m status` and `./m check` are that command.

## The mechanism

Continue the file you started in [3.1](3.1-set-euo-pipefail.md). First the two helpers everything
else uses:

```bash
DAY="${2:-}"
pad() { printf "%02d" "$1"; }

daydir() {
  local n d
  n="$1"
  for d in "days/day-$(pad "$n")-"*; do
    [ -d "$d" ] && { echo "$d"; return; }
  done
  if [ -d "days/day-$(pad "$n")" ]; then echo "days/day-$(pad "$n")"
  elif [ -d "days/day-$n" ]; then echo "days/day-$n"
  else echo ""; fi
}
```

**Line by line:**

- `DAY="${2:-}"` — the optional second argument, made explicitly optional so `set -u` is satisfied
  ([3.1](3.1-set-euo-pipefail.md)).
- `pad() { ...; }` — a shell function. `printf "%02d"` formats a number to at least two digits with
  a leading zero, so `0` becomes `00` and `12` stays `12`. Every day folder starts `day-00`,
  `day-01` … `day-96`, and zero-padding is what makes them sort correctly in every listing.
- `daydir()` — resolve a day number to its folder. It exists because you type `./m start 5` and the
  folder is `days/day-05-tools-by-hand/`; the script absorbs that mismatch once, rather than every
  verb handling it. **This is the function that makes the folder slug safe.** A day folder is
  `day-NN-<slug>` (plan §17.2) — the number is the day's identity and the slug is a label on it, so
  every tool looks up the number and takes whatever slug it finds. Rename a folder to a better slug
  and nothing here notices.
- `local n d` — **`local` scopes both variables to this function.** Without it, bash variables are
  global, and a function that quietly overwrites a caller's variable is a bug that takes a long time
  to find. Declaring the names on one line and assigning on the next is deliberate: `local n="$1"`
  would work here, but combining `local` with a command substitution hides that command's exit
  status behind `local`'s own, which is always 0.
- `for d in "days/day-$(pad "$n")-"*` — **glob for the slugged folder.** The `*` is expanded by the
  shell into every matching path. Note what happens when nothing matches: bash leaves the pattern
  *unexpanded*, so `d` becomes the literal string `days/day-05-*`, which is why the `[ -d "$d" ]`
  test inside the loop is not optional — it is what tells a real match from an unmatched pattern.
- `{ echo "$d"; return; }` — print the first match and leave the function immediately. There should
  only ever be one folder per day number; taking the first and returning means a stray duplicate
  produces a consistent answer rather than two lines of output.
- `[ -d "path" ]` — test whether a directory exists. `[` is genuinely a command, which is why the
  spaces around it are mandatory: `[-d "x"]` is the shell trying to run a program called `[-d`.
- The two `elif`/`if` branches — fall back to a bare `day-05` or `day-5`. Nothing in this repo is
  named that way any more, but a resolver that accepts more spellings than it produces costs two
  lines and turns a whole class of "folder not found" into a non-event.
- `$(pad "$n")` — command substitution ([2.3](../02-repo-skeleton/2.3-git-init-and-what-a-repo-is.md)): run `pad`
  and paste its output here.
- `echo ""` in the `else` — return an empty string rather than failing, so the caller can decide what
  a missing day means. A helper that exits the whole script on a normal condition is a helper you
  cannot reuse.

Now the dispatcher:

```bash
case "${1:-help}" in
  start)
    [ -z "$DAY" ] && { echo "usage: ./m start <day>"; exit 1; }
    D="$(daydir "$DAY")"
    [ -n "$D" ] || { echo "no day $DAY yet - see docs/TRACKER.md for what is written"; exit 1; }
    if [ -f "$D/LESSON.md" ] && [ -d "$D/parts" ]; then
      echo "-> open $D/LESSON.md   (the hub - read its §2 map, then the parts in order)"
      find "$D/parts" -name '*.md' | sort | sed "s|^$D/|     |"
    else
      echo "day $DAY has no hub + parts/ - it is not written (plan §17.2)"; exit 1
    fi
    ;;
```

**Line by line:**

- `case "${1:-help}" in` — the verb, defaulting to `help` when the script is run with no arguments.
  Running `./m` alone therefore prints usage rather than erroring, which is what a person exploring
  the repository will do first.
- `[ -z "$DAY" ] && { ...; exit 1; }` — `-z` tests for an **empty** string. The `&&` runs the right
  side only if the test passed ([1.2](../01-toolchain/1.2-git-and-the-unix-shell.md)), and the braces group
  two commands into one unit. This is the compact bash idiom for "if this is missing, complain and
  stop".
- `exit 1` — a **non-zero** status, because a usage error is a failure. Getting this right is what
  lets CI and `./m done` trust the result ([3.1](3.1-set-euo-pipefail.md)).
- `[ -n "$D" ] || { ...; }` — `-n` is "non-empty", the mirror of `-z`; `||` runs the right side only
  when the test *fails*. Read as: "must be non-empty, otherwise complain".
- `[ -f ... ] && [ -d ... ]` — the day is only written if it has **both** a hub file and a `parts/`
  directory. That is plan §17.2's definition, encoded: a day without `parts/` is not a day.
- `find "$D/parts" -name '*.md' | sort` — list the part documents in order. `find` walks the section
  folders; `sort` makes the output stable, since `find`'s natural order is filesystem-dependent and
  therefore not reproducible.
- `sed "s|^$D/|     |"` — strip the day-folder prefix from each line and indent it instead. `sed`'s
  substitute command is normally written `s/old/new/`, but the paths contain `/`, so `|` is used as
  the delimiter — any character works, and choosing one absent from your data avoids a wall of
  backslashes.
- `;;` — end of the branch.

The simplest verbs are one line each:

```bash
  depth)
    if [ -n "$DAY" ]; then uv run python scripts/depth_check.py "$DAY"
    else uv run python scripts/depth_check.py; fi
    ;;
  trace)   uv run python scripts/trace.py ;;
  tracker) uv run python scripts/tracker.py ;;
  status)  uv run python scripts/tracker.py --summary ;;
  scaffold)
    [ -z "$DAY" ] && { echo "usage: ./m scaffold <day>"; exit 1; }
    D="$(daydir "$DAY")"
    [ -n "$D" ] || { echo "no day $DAY yet - the day is written before its lab"; exit 1; }
    mkdir -p "$D/lab"
    echo "-> created $D/lab"
    ;;
```

**Line by line:**

- `depth` — with a day number, check one day; without, check every written day. The Python program
  handles both, so the branch only has to choose which way to call it.
- `uv run python scripts/...` — **every** Python invocation goes through `uv run`
  ([2.5](../02-repo-skeleton/2.5-the-venv-you-never-activate.md)). A script has no shell to have activated
  anything, so this is not a stylistic preference; it is the only version that works from CI and
  from a scheduler.
- `trace`, `tracker`, `status` — thin wrappers. **The logic lives in Python, not in bash.** This is
  the boundary that keeps `./m` under a hundred lines: bash orchestrates, Python decides.
- `scaffold` — it asks `daydir` where the day lives rather than assembling the path itself. That
  matters: the folder is `day-01-bootstrap-and-map`, not `day-01`, and a `mkdir -p` built from the
  number alone would silently create a *second*, empty `days/day-01/` beside the real one. Building
  a path you could have looked up is how a tool ends up disagreeing with the repository.
- `mkdir -p` is safe to re-run ([1.2](../01-toolchain/1.2-git-and-the-unix-shell.md)), so scaffolding
  twice is harmless rather than an error to handle.

And the catch-all, which is where the usage text lives:

```bash
  *)
    cat <<'USAGE'
usage: ./m <command> [day]

  status         one line: how many days are written / complete
  tracker        regenerate docs/TRACKER.md
  trace          regenerate docs/TRACEABILITY.md from the day hubs vs plan §14
  start N        point at day N's hub and list its parts/
  parts N        list day N's sub-topic documents
  depth [N]      check day N (or every written day) against plan §17, the depth contract
  scaffold N     create days/day-NN-<slug>/lab/
  check          ruff + ruff format + offline pytest + depth contract + traceability
  done N         refuse unless the checklist is ticked and checks are green, then commit
USAGE
    ;;
esac
```

**Line by line:**

- `*)` — matches any verb not handled above, **including** the `help` default and including typos.
  A mistyped verb printing the menu is exactly the right behaviour.
- `cat <<'USAGE'` — a heredoc, with the delimiter named `USAGE` for readability. Any word works.
- The quoted `'USAGE'` keeps the body literal, which matters because usage text is full of `$`
  and `<`.
- **The usage text is the documentation.** It is next to the code it describes, so it is the one
  copy that cannot drift — which is the entire point of the story at the top of this page.
- `esac` — closes the `case`.

Try it:

```bash
./m
./m status
./m start 0
```

**Line by line:**

- `./m` with no arguments prints the menu, because of the `help` default.
- `./m status` runs the tracker's one-line summary. It will report zero days written until this one
  is finished.
- `./m start 0` will say day 0 has no hub yet — which is true while you are reading this, and will
  stop being true when you finish [4.3](../04-repo-memory/4.3-the-first-commit-and-breaking-it.md).

## When it breaks

**A missing `;;`**, which produces the strangest symptom in this part:

```text
$ ./m status
Sutra: 0/97 days in the v2.0.0 shape (0 sub-topic docs), 0 completed, ...
-> created days/day-00-toolchain-skeleton-driver/lab
```

Two branches ran. Bash does not fall through between `case` branches — but a missing `;;` makes the
two blocks a *single* branch, so both bodies belong to the first pattern. **The fix** is to add the
missing `;;`, and the way to catch it before it ships is `bash -n m`, which parses the script
without running it.

**Unquoted `$1` and a path with a space:**

```text
$ ./m start "day 5"
./m: line 21: [: too many arguments
```

`[ -d $D ]` with `D="day 5"` becomes `[ -d day 5 ]` — three arguments where `[` expected two.
**The fix is the one that is always the fix:** quote every expansion, `[ -d "$D" ]`. Windows paths
routinely contain spaces (`Program Files`, `OneDrive - Company`), so this is not a theoretical
concern here.

**`$?` after a `case`, which is subtler than it looks:**

```text
$ ./m depth 0
FAIL day   0  2 problems
$ echo $?
1
```

That is correct, and it is what `./m done` ([3.4](3.4-the-done-gate.md)) depends on: the `case`
takes on the exit status of the last command in the branch it ran, so a failing Python program fails
the whole script. But note the trap: if you *add* a friendly `echo` at the end of a branch, that
`echo` succeeds and the branch now exits `0` regardless. **A trailing `echo` after a command that
can fail silently converts a failure into a success** — which is exactly the story from
[3.1](3.1-set-euo-pipefail.md), arriving through a different door.

**Line endings, again:**

```text
$ ./m check
./m: line 4: $'\r': command not found
```

Carriage returns ([1.2](../01-toolchain/1.2-git-and-the-unix-shell.md)). `sed -i 's/\r$//' m` fixes the file;
`git config core.autocrlf input` stops it recurring.

## In production

**This pattern has a name and it is everywhere.** A single task-runner entry point — `make`,
`just`, `task`, `npm run`, or a hand-rolled `./m` — is standard practice, and the reason is always
the same: **the set of things you do to a repository should be discoverable and defined once.** The
strongest signal that a project has it right is that its CI configuration is boring: a checkout, a
setup step, and `./m check`. Anything more in CI is logic that only exists there, which means it is
logic you cannot run locally, which means it will break and you will debug it by pushing commits.

**Keep the logic out of bash.** The rule this file follows is that bash *dispatches* and Python
*decides*. `depth_check.py` is 350 lines of parsing and validation; expressing that in bash would be
possible and awful. The signal for the boundary: **the moment a branch needs to parse something or
branch on data rather than orchestrate commands, it belongs in a program.**

**Make it obvious when it is not being used.** A `Makefile` shim is worth two lines:

```make
check:
	@bash ./m check
```

**Line by line:**

- `check:` — a make target. The command beneath it **must** be indented with a real tab; make is the
  only common tool where a tab and four spaces are different, which is one of the reasons it was not
  chosen as the primary driver.
- `@` — suppress echoing the command itself, so the output is the script's and not make's.
- `bash ./m check` — delegate. There is still one definition; this is a redirect, not a copy.

**What degrades at scale.** With forty verbs, a flat `case` becomes a wall, and the usual next step
is subcommands (`./m day check`, `./m day new`) or a real CLI in Python. The signal is when the
usage text stops fitting on a screen. Sutra has nine verbs and will not reach that; knowing where
the ceiling is stops you building for it prematurely — which is itself the lesson.

**The review comment a senior engineer leaves.** On a pull request adding a test command to the CI
config that differs slightly from the local one: *"Put this in `./m check` instead — otherwise CI is
testing something we can't reproduce locally, and the first time it goes red we'll be debugging by
pushing commits."* The principle underneath: **CI should run the same entry point a developer runs**,
so a green build and a green terminal are the same statement.

**The interview question.** *"How do you make sure everyone on a team runs the same checks?"* A weak
answer is "documentation". A strong answer is a single entry point that CI, hooks and humans all
invoke, so there is exactly one definition and no opportunity to drift — and then the honest
follow-up: it only works if the entry point is genuinely runnable everywhere, which is why the
choice between `make` and a shell script is a real decision on a mixed-platform team rather than a
matter of taste.
