# 2.2 — `.gitignore`, written before any secret exists

## One-line answer

`.gitignore` stops git from ever *noticing* a file — which only works if the rule exists **before**
the file does, because git has no memory of ignoring something it already tracked, and no way at all
to un-know something it once committed.

---

## The story

Someone builds a small service over a weekend. It needs an API key, so they put the key in a file
called `config.py` next to the code, because that is the fastest thing that works. They commit
often, because committing often is a good habit.

On Monday they realise the key should not be in the repository. They delete the line, commit the
deletion, and push. The file on the current branch no longer contains the key. The problem is solved.

The problem is not solved.

Git does not store the *current* state of a project. It stores **every** state, chained together
([1.2](../01-toolchain/1.2-git-and-the-unix-shell.md)). The key is still sitting in Saturday's commit, and
Saturday's commit is still in the chain, and anyone who clones the repository receives the entire
chain. Deleting a secret in a later commit removes it from *view*, not from *history* — in the same
way that tearing a page out of the second half of a book does not remove it from the first half.

Some weeks later they get an email from their provider: unusual usage, from a region they have never
been to. The repository had gone public in the meantime, and there are automated systems whose entire
job is to scan public repositories for credential-shaped strings. Those systems read history, because
history is where people forget to look.

The fix was never going to be a deletion. Once a secret has been committed and pushed, the **only**
honest response is to treat it as compromised and rotate it: generate a new key at the provider,
revoke the old one, and update the places that used it. Everything else is theatre.

And the fix that would have prevented all of it was one line in one file, written before the secret
existed.

---

## The idea in plain language

**`.gitignore` is a list of patterns describing files git should not notice.** It sits at the root
of the repository, it is itself committed — which is the point, since it must travel with the
project — and it changes git's behaviour in one specific way:

> A file matching a pattern in `.gitignore` is **not shown as untracked**, so it never appears in
> `git status`, and `git add .` will not pick it up.

That sentence contains the whole mechanism, and also the whole limitation. Read it again and notice
what it does **not** say:

- It does not say "git will stop tracking this file". If a file is **already tracked**, `.gitignore`
  has no effect on it whatsoever. Git will keep noticing every change to it forever, because you
  already told git to care.
- It does not say "git will remove this file from history". Nothing removes a file from history
  except rewriting history — which changes every subsequent commit's identity and breaks every
  existing clone.

Which gives the rule this part exists for:

> ⚠️ **`.gitignore` is a preventive measure, not a corrective one.** It must be written before the
> file it protects against exists. Afterwards is too late, in a way that costs a credential.

### The pattern language

The syntax is small. These six rules cover everything Sutra needs:

| Pattern | Matches |
| --- | --- |
| `.env` | any file or folder named exactly `.env`, at any depth |
| `*.db` | any file ending in `.db`, at any depth |
| `.venv/` | a **directory** named `.venv` (the trailing slash means "directory only") |
| `/build` | `build` **only at the repository root** (a leading slash anchors it) |
| `days/*/lab/` | a `lab` directory one level inside any `days/<something>` |
| `!.env.example` | **un-ignore** this, even though an earlier pattern matched it |

The last one matters more than it looks. Sutra ignores `.env*` — a wide net that catches `.env`,
`.env.local`, `.env.production` and anything else in that family — and then explicitly rescues
`.env.example` back out of it. That is deliberate:

- **`.env` holds the values.** Never committed. Never, under any circumstance.
- **`.env.example` holds only the *names*.** Always committed. It is documentation: it tells the
  next person which variables the project expects, without telling them anything secret. A blank
  `GOOGLE_API_KEY=` is a useful artifact; a filled-in one is an incident.

> 💡 **The mental model:** `.env` is the key. `.env.example` is the **shape of the keyhole**. One
> travels with the repository; the other never leaves your machine.

### Why an ignore list also covers boring things

Secrets are the reason this part is at `production` level, but most `.gitignore` lines are about
something quieter: **committing what can be regenerated is a slow-acting mistake.** A `.venv`
directory is thousands of files that `uv sync` can rebuild exactly from `uv.lock`
([1.3](../01-toolchain/1.3-uv-the-one-binary.md)). Committing it makes clones slow, makes diffs unreadable,
and makes the repository grow forever — because git keeps every version of every file it has ever
been shown.

The dividing line is the one from [2.1](2.1-the-folder-skeleton.md): **if committed code can rebuild
it, do not commit it.**

## Why Sutra needs it

The plan's Principle 9 says *secrets never touch git*, and then makes it real with a fact that turns
the discipline from hygiene into consequence:

> **In Phase 14, Day 93, this repository goes public.**

That is not a hypothetical about someone else's repo. Every decision you make in this file today is
a decision about what a stranger will be able to read in three months, including in history.

- **Day 1 creates `.env` and puts three free API keys in it** — Gemini, Groq, OpenRouter (OPS-02).
  Today's file is what makes that safe. The order is the entire point: the rule exists first, so the
  file arrives already invisible.
- **Day 47 makes sessions database-backed**, which puts a `.db` file on disk holding conversation
  history. Ignored today.
- **Day 49 builds a local embedding index** over the ticket archive — a large generated artifact
  that is rebuildable from committed code and must never be committed.
- **Day 69 covers PII and data boundaries** (SEC-12, SEC-13). Sutra's company data is synthetic
  *always*, precisely because free-tier endpoints may use prompts for improvement — and the
  repository being public is the second half of that same reasoning.
- **Day 92 is the hardening pass** before the repo goes public (SEC-16). That day audits everything
  ever committed. A `.gitignore` written on Day 0 is what makes Day 92 an audit rather than an
  incident response.

## The mechanism

Write the file **now**, before Day 1 creates `.env`, and before `git init` in
[2.3](2.3-git-init-and-what-a-repo-is.md) gives git anything to notice.

```bash
cat > .gitignore <<'EOF'
# ── secrets ───────────────────────────────────────────────
# Written on Day 0, BEFORE .env exists. Principle 9: secrets never touch git,
# and this repository goes public in Phase 14.
.env
.env.*
!.env.example
.envrc
*.pem
*.key

# ── the environment (rebuildable from uv.lock) ────────────
.venv/
__pycache__/
*.py[cod]

# ── tool caches ───────────────────────────────────────────
.pytest_cache/
.ruff_cache/
.mypy_cache/
.coverage
htmlcov/

# ── runtime artifacts: never commit a session store ───────
.adk/
*.db
*.sqlite3

# ── build output ──────────────────────────────────────────
build/
dist/
*.egg-info/

# ── scratch ───────────────────────────────────────────────
days/*/lab/
.ipynb_checkpoints/
.DS_Store
EOF
```

**Line by line:**

- `cat > .gitignore <<'EOF'` — a **heredoc**: everything up to the line reading `EOF` becomes the
  file's content. The quotes around `'EOF'` are essential — they tell bash to treat the body as
  *literal text*. Without them, bash would try to expand `$` and backticks inside the block, which
  in a file full of patterns is a quiet way to corrupt it.
- `.env` and `.env.*` — the values file and its whole family. Two patterns because `.env` alone does
  not match `.env.local`.
- `!.env.example` — the negation. **Order matters:** a `!` rule must come *after* the pattern it is
  rescuing from, and it cannot rescue a file whose *parent directory* is ignored. Here the parent is
  the repository root, so it works.
- `.envrc` — used by direnv, another way of holding environment variables. Ignored for the same
  reason as `.env`.
- `*.pem`, `*.key` — certificate and private-key extensions. Sutra does not use them today; the
  lines cost nothing and close a door before it can be opened by accident.
- `.venv/` — the trailing slash restricts the match to a directory. Rebuildable with `uv sync`.
- `__pycache__/` and `*.py[cod]` — compiled bytecode. `[cod]` is a character class matching `.pyc`,
  `.pyo` and `.pyd` in one pattern.
- `.adk/` — ADK's local runtime directory. It appears from Day 8, when sessions become real. **The
  previous run of this project committed a session database from here by accident**, which is why
  the line exists with a comment attached.
- `*.db`, `*.sqlite3` — the same protection from the other direction, by extension rather than by
  location.
- `days/*/lab/` — the scratch folder `./m scaffold N` creates. Your experiments while working a day
  are yours; the *documents* are the artifact.
- `.DS_Store` — macOS folder metadata. Harmless, universally annoying, always ignored.

### Prove it works

The test is worth doing **before** you have a real key, so that the first time you see this
behaviour it costs nothing:

```bash
echo "GOOGLE_API_KEY=not-a-real-key-just-testing" > .env
git status --porcelain --ignored | grep -E "\.env"
```

**Line by line:**

- `echo ... > .env` — create the file with a fake value. This is the only time you will deliberately
  write something key-shaped into `.env` before Day 1.
- `git status --porcelain` — the machine-readable form of `git status`: one short line per file,
  stable across git versions and easy to grep.
- `--ignored` — **also** list ignored files, which normal `git status` hides. Without this flag the
  successful case prints nothing at all, and "nothing" is an ambiguous result — you want to see
  *why* it is nothing.
- The output should be `!! .env`. The `!!` prefix means **ignored**. That is the confirmation.
- `.env.example` should not appear as ignored — you have not created it yet, and when Day 1 does,
  the `!` rule will keep it visible.

Clean up the fake:

```bash
rm .env
```

**Line by line:**

- Remove it. Day 1 creates the real one, and by then the rule protecting it will already be
  committed.

## When it breaks

**The failure this part exists to prevent, in full.** Suppose the file had been created *before* the
rule:

```text
$ git add -A
$ git commit -m "day-01: keys"
$ git log --oneline
9c1f0aa day-01: keys

$ cat .gitignore
.env

$ git status --porcelain
 M .env
```

Read that last line carefully. `.gitignore` contains `.env`, and git is **still reporting changes to
it**. Nothing is broken. `.gitignore` only governs files git has not been told about, and this one
was committed a moment ago, so git will now report it forever.

**The fix, for the tracking:**

```text
$ git rm --cached .env
rm '.env'
$ git commit -m "stop tracking .env"
```

**Line by line:**

- `git rm --cached .env` — remove the file **from git's index** while leaving it on your disk.
  Without `--cached` it would delete your actual file, which for a real key would turn a bad
  afternoon into a worse one.
- The commit records the removal. From here on `.gitignore` applies, because git no longer tracks
  it.

**And the fix for the secret itself, which is the part people skip:**

The key is still in commit `9c1f0aa`. It is still in every clone. It is still in every fork.
`git rm --cached` did not touch it. **Rotate the key at the provider.** Generate a new one, revoke
the old one, put the new one in `.env`. Anything else leaves a live credential in a chain of
snapshots you no longer fully control.

**The `!` rule that does not work:**

```text
$ cat .gitignore
config/
!config/example.toml

$ git status --porcelain --ignored | grep config
!! config/
```

`example.toml` is still ignored despite the negation. **Why:** git does not descend into an ignored
directory at all, so it never gets far enough to consider the rule about a file inside it. You
cannot un-ignore a file whose parent directory is excluded. **The fix** is to ignore the contents
rather than the directory:

```text
config/*
!config/example.toml
```

**A pattern that is too greedy.** `*.key` also matches `translations.key`, and `build/` also matches
`sutra/build/` if you ever have one. Both are usually fine, occasionally not. When a file you want
is mysteriously invisible, ask git why:

```text
$ git check-ignore -v somefile.key
.gitignore:12:*.key     somefile.key
```

**How to read it:** the answer names the **file, the line number, and the exact pattern** that
matched. This command turns "why is git ignoring my file?" from guesswork into a lookup, and it is
worth remembering — it is the single most useful `.gitignore` debugging tool and almost nobody knows
it exists.

## In production

**Prevention, detection, response — you need all three.** `.gitignore` is prevention, and prevention
alone is not a security posture, because it only stops the mistakes you anticipated.

- **Detection** is a *pre-commit hook* that scans staged changes for credential-shaped strings and
  refuses the commit, plus a repository-side scanner that watches history. Most hosts offer secret
  scanning; several providers participate, so a pushed key can trigger automatic revocation within
  minutes. That is a safety net, not a plan.
- **Response** is a written runbook, because during an incident nobody invents a good process: revoke
  first, rotate second, then assess what the key could reach while it was live, then decide whether
  history needs rewriting. **Revocation comes first** — it is the only step that actually stops the
  bleeding, and it works even if you never manage to clean the history.

**"Just rewrite history" is more expensive than it sounds.** Tools exist that strip a file from every
commit. They work. They also change the hash of every commit from the leak onward, which means every
existing clone, fork, branch and open pull request now disagrees with the remote about what the
project's history is. On a solo repository that is an inconvenience. On a team repository it is a
coordinated migration. **Rotating a key takes two minutes and always works; rewriting history takes
an afternoon and only helps if nobody has cloned.**

**Where secrets actually live in production.** A `.env` file is right for a laptop and wrong for a
deployment. Real systems inject secrets as **environment variables at runtime**, from a secret
manager, so that the value exists in the process's memory and nowhere on disk. That is why Day 86's
container is described as "Cloud-Run-shaped": a stateless container that receives its configuration
from the environment, never one that bakes a key into an image layer. **A secret in a Docker image is
the same mistake as a secret in git** — layers are immutable and distributable, so `RUN rm secret.txt`
does not remove it from the layer above.

**The blast-radius question, which is the one that actually reduces risk.** Principle 13 says name
what a capability can destroy before granting it. For a key that means: what is the *smallest* scope
this credential can have, and how would we notice it being abused? For Sutra's free tiers the answer
is comfortable — the keys are free, scoped to one project, and rate-limited — which is a genuinely
useful property of the zero-budget constraint. A leaked free-tier key costs you quota and
embarrassment, not money. That is worth appreciating, and worth *not* relying on: the discipline you
build here is the one you will carry to a repository where the key is attached to a billing account.

**The review comment a senior engineer leaves.** On a pull request adding a config file with a real
value in it: *"This value can't be in the repo — move it to an env var and add the name to
`.env.example`. And if this key has ever been pushed, rotate it before we merge, not after."* The
second sentence is the professional part: the reviewer is separating *fixing the file* from
*containing the exposure*, because those are different jobs and only one of them is urgent.

**The interview question.** *"You accidentally committed and pushed an API key. Walk me through what
you do."* The answer they are listening for starts with **revoke and rotate the credential**, not
with git commands. Then: remove it from tracking, add the ignore rule, assess what it could access
and check the provider's logs for use during the exposure window, and only then consider whether
history rewriting is worth the coordination cost. A candidate who leads with `git filter-repo` has
told you they think the problem is the file. A candidate who leads with rotation has told you they
understand the problem is the *credential*.
