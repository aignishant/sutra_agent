# 1.5 — The editor, and the interpreter trap

## One-line answer

Your editor runs its own copy of Python to power autocomplete, error squiggles and the Run button —
and **if that copy is not the project's `.venv`, the editor will confidently lie to you** about code
that runs perfectly, or bless code that does not.

---

## The story

Someone has done everything right. They installed one tool to own the environment. They pinned the
interpreter. They ran `uv sync` and watched it finish. They open the project in their editor,
create a file, and type the first import.

A red squiggle appears under it. Hovering says: *Import could not be resolved.*

They go back to the terminal and run the same line. It works. They run it again, slower, watching.
It works.

So now there are two truths on one screen. The terminal says the package is installed. The editor
says it is missing. And because the editor is the thing they are *looking at* while they write, the
editor's opinion is the one that shapes the next hour — they start doubting the install, re-running
`uv sync`, reading the lockfile, wondering whether the package name is spelled differently than they
remember.

Nothing is wrong with the project. The editor simply picked a different Python. It scanned the
machine when it opened, found one of the four interpreters from
[1.1](1.1-why-one-tool-owns-the-environment.md), and has been describing *that* interpreter's world
ever since — a world in which the package genuinely is not installed.

The trap is not that the editor is wrong. It is that the editor is **wrong with great confidence,
in the place you are most likely to believe it.**

---

## The idea in plain language

An editor that understands Python is not just colouring text. To offer autocomplete, jump-to-
definition, type errors and inline documentation, it runs a **language server** — a background
program that reads your code and the code of everything you import, and answers questions about
them.

That language server needs to know **which interpreter** the project uses, because that is what
determines which `site-packages` folder it should read. Point it at the wrong interpreter and every
answer it gives is about the wrong world:

| What you see | What is actually happening |
| --- | --- |
| `Import "google.genai" could not be resolved` on code that runs | The editor's interpreter has no `google-genai` installed. Yours does. |
| Autocomplete offers nothing after a package name | It cannot read that package's contents, because it cannot find the package. |
| The Run button fails but the terminal succeeds | The Run button launches the editor's interpreter, not `uv run`. |
| Autocomplete offers a method that does not exist at runtime | The editor is reading an **older version** of the package from a different environment. |

That last row is the dangerous one, and it is the reverse of the story above. A missing import is
loud and gets fixed. A *stale* one is silent: the editor happily completes a function signature that
was removed two versions ago, you write code against it, and the failure arrives at runtime. For
Sutra this matters more than usual, because the plan's §5.1 lists four ways ADK 1.x and 2.x differ —
and an editor pointed at a 1.x install would autocomplete the 1.x shape of exactly the code you are
trying to write in 2.x.

**The fix has two halves, and both are worth doing:**

1. **Tell the editor to use the project's `.venv`.** One setting, once per project.
2. **Do not trust the Run button.** Run through `uv run` in the terminal, which cannot be pointed at
   the wrong thing. The editor is for reading and writing code; the terminal is for running it.

> 💡 **The mental model:** the editor is a *very well-informed opinion about a Python installation*.
> Your job is to make sure it holds an opinion about **the right one**.

---

## Why Sutra needs it

- **Day 5 onwards, every day imports ADK.** ADK 2.x's API differs from 1.x in the node model, the
  event field names, whether custom agents yield or append, and how exceptions travel (plan §5.1).
  An editor reading a stale environment will autocomplete 1.x shapes into your 2.x code, and the
  error will not appear until the code runs. That is the single most expensive version of this
  mistake in this curriculum.
- **Day 7 is the event model**, the trap that has the most 1.x-era tutorials attached to it. You
  want your editor showing you the real 2.x field names on that day, not a plausible-looking older
  set.
- **Day 23 introduces tests.** A test that passes in the editor's runner and fails in `./m check`
  (or vice versa) is a very confusing afternoon. The runner in [3.3](../03-the-m-driver/3.3-the-check-gate.md) is
  `uv run python -m pytest` for exactly this reason: one entry point, one environment.
- **Every part of this curriculum shows a command, not a button.** That is deliberate. A command is
  reproducible, quotable in a document, runnable in CI and runnable in a container. A button is
  none of those things.

## The mechanism

Any editor works. The instructions below are for the most common one; the principle transfers
directly.

### Install the editor and its Python support

Install a code editor, then add two extensions: the **Python** extension (which brings the language
server) and **Ruff** (the linter and formatter this project uses, pinned in
[2.4](../02-repo-skeleton/2.4-pyproject-and-the-lockfile.md)).

### Point it at the project's interpreter

The `.venv` folder is created inside the project by `uv`
([2.5](../02-repo-skeleton/2.5-the-venv-you-never-activate.md)). Most editors detect it automatically when you
open the project folder — *most*, and *usually*, which is not the same as always. Make it explicit.

Open the command palette and run **Python: Select Interpreter**, then choose the entry whose path
begins with your project folder and contains `.venv`. On Windows that is:

```text
.\.venv\Scripts\python.exe
```

On macOS and Linux:

```text
./.venv/bin/python
```

**How to read those paths:**

- `.venv` — the environment folder, sitting *inside the project*. If the path you selected does not
  start with your project's folder, you have picked one of the machine-wide interpreters and the
  problem is not fixed.
- `Scripts` on Windows versus `bin` elsewhere — the same folder with two names, a historical
  difference. Knowing both saves confusion when reading documentation written for the other
  platform.

You can also record the choice in the project so it survives, and so a colleague inherits it. In
`.vscode/settings.json`:

```json
{
  "python.defaultInterpreterPath": "${workspaceFolder}/.venv/Scripts/python.exe",
  "python.terminal.activateEnvironment": false,
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff",
    "editor.formatOnSave": true
  }
}
```

**Line by line:**

- `python.defaultInterpreterPath` — the interpreter the language server should describe.
  `${workspaceFolder}` is expanded by the editor to the project's own folder, which keeps the
  setting portable rather than hard-coding a path from your machine.
- `python.terminal.activateEnvironment: false` — stops the editor from auto-activating the venv in
  every terminal it opens. Sutra runs things with `uv run`
  ([2.5](../02-repo-skeleton/2.5-the-venv-you-never-activate.md)), and a half-activated shell is a state you have
  to reason about. Turning it off means the terminal inside the editor behaves exactly like the one
  outside it.
- `editor.defaultFormatter` set to Ruff, with `formatOnSave` — so the formatter that runs while you
  type is the same one `./m check` runs. If those two differ, every save creates a diff the gate
  will reject, and you will spend the curriculum fighting your own editor.
- The `[python]` wrapper scopes both settings to Python files only, leaving Markdown and JSON alone.

Whether you commit `.vscode/settings.json` is a judgement call: it makes the setup reproducible for
anyone who clones the repo, at the cost of imposing one editor's configuration on them. Sutra does
not commit it — the same guarantees are enforced by `./m check`, which every contributor runs
regardless of editor.

### Verify it from inside the editor

Open a terminal *inside* the editor and run:

```bash
uv run python -c "import sys; print(sys.executable)"
```

**Line by line:**

- This is the same probe from [1.1](1.1-why-one-tool-owns-the-environment.md), asked in a new place.
  `uv run` guarantees the project environment regardless of what the editor thinks.
- The printed path must contain your project folder and `.venv`. Compare it against what the editor
  shows in its status bar as the selected interpreter. **Those two strings must match.** If they do
  not, the editor is describing a different world than the one your code runs in, and you have found
  the trap before it found you.

## When it breaks

**The false negative — the story at the top:**

```text
Import "google.genai" could not be resolved  Pylance(reportMissingImports)
```

The word to notice is **Pylance**, or whatever your language server is called. That prefix tells you
the *editor's analyser* produced this, not Python. Python has not run. Confirm which side is wrong:

```text
$ uv run python -c "from google import genai; print('import works')"
import works
```

If the terminal prints that and the editor still complains, the editor is on the wrong interpreter.
Re-run **Python: Select Interpreter** and pick the `.venv` entry. If the `.venv` entry is not
offered, the environment does not exist yet — run `uv sync` first, then reload the editor window so
it rescans.

**The false positive — the expensive one.** Your editor autocompletes a method, you write the call,
and at runtime:

```text
Traceback (most recent call last):
  File "sutra/agent.py", line 12, in <module>
    ...
AttributeError: module 'google.adk.agents' has no attribute 'SomeOldThing'
```

Nothing is misspelled. The editor was reading an *older version* of the package from a different
environment, where that name existed. The terminal is reading the version you actually pinned. **The
editor was not lying about the code; it was telling the truth about the wrong installation.** Same
fix, and the same reason to prefer `uv run` for anything that must be true.

**The Run button that runs the wrong Python:**

```text
PS C:\Users\me\sutra> & C:/Python312/python.exe c:/Users/me/sutra/sutra/agent.py
Traceback (most recent call last):
  File "c:\Users\me\sutra\sutra\agent.py", line 1, in <module>
    from google import genai
ModuleNotFoundError: No module named 'google'
```

Read the **first line of that output**, which is the command the editor actually ran. It launched
`C:/Python312/python.exe` — a machine-wide interpreter — not `.venv`. The button is a convenience
that hides which interpreter it chose, which is the one thing you need to see. **Run it properly:**

```text
$ uv run python sutra/agent.py
```

## In production

**Editor configuration is not part of the contract; the gate is.** Two people on a team will use
different editors, different extensions, and different settings, and none of that should change
whether the code is correct. That is why the definition of done in this project is `./m check`
([3.3](../03-the-m-driver/3.3-the-check-gate.md)) and not "no squiggles in my editor". The professional habit is
to make the *command line* the source of truth and let each person configure their editor to agree
with it — never the other way round.

**The formatter must be the same one, at the same version.** If your editor formats on save with one
version of a formatter and CI checks with another, every commit produces churn: your editor reformats
lines you did not touch, the diff fills with noise, and reviewers stop reading it. This is why Ruff
is pinned exactly in `pyproject.toml` and why `./m check` runs `ruff format --check` rather than
trusting anyone's editor. A pinned formatter is a small thing that removes a permanent source of
friction from a team.

**A type checker is a different question, and Sutra defers it.** The editor's red squiggles come
from a language server making a best effort. A *type checker* run as a gate is a deliberate
commitment: it will reject code, so adopting one is a decision about how much annotation the project
is willing to carry. Sutra leaves this as an open question until the Day 31 quality gate (OPS-08),
and `CLAUDE.md` records it as an explicit `TODO` rather than a silent omission. **Noticing what you
have not decided yet is part of doing this properly.**

**What degrades at scale.** In a monorepo with several packages, each with its own environment, "the
project's interpreter" stops being a single answer, and editors get it wrong far more often. Teams
solve it with committed workspace configuration and a `make`-style entry point that everyone uses
regardless of editor — which is precisely the role `./m` plays here, at a much smaller scale.

**The review comment a senior engineer leaves.** On a pull request whose diff includes forty
reformatted lines nobody touched: *"Your formatter disagrees with the pinned one — check the version
in `pyproject.toml`. This diff is unreviewable as is."* The point behind the comment is that a diff
is a communication medium, and noise in it costs every future reader, not just this one.

**The interview question.** *"Your editor says an import is unresolved but the code runs fine. What
is going on?"* This is a real screening question because it separates people who understand the
model from people who restart things until they work. The strong answer: the editor's language
server is analysing a different interpreter than the one that runs the code, so it is reading a
different `site-packages`; confirm with `sys.executable` in both places, then point the editor at the
project's environment. A very strong answer adds the *reverse* case — a stale environment producing
autocomplete for methods that no longer exist — because that is the one that actually costs people
time.

## Check yourself

Run this in the editor's integrated terminal, then compare with what the editor's status bar shows:

```bash
uv run python -c "import sys; print(sys.executable)"
```

The two must name the same file, and it must be inside your project's `.venv`.

**Answer out loud, without scrolling up:**

> Your editor underlines an import in red, but the same line runs without error in the terminal.
> Which of the two is wrong, how do you prove it in one command, and which failure is more dangerous
> — the editor saying an import is missing, or the editor autocompleting a method that does not
> exist?
