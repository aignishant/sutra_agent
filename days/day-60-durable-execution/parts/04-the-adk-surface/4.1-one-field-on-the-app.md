# 4.1 — One field on the App

## One-line answer

ADK's entire durable-execution surface is one boolean on the `App` —
`ResumabilityConfig(is_resumable=True)`, default `False` — and the class's own docstring states
the guarantee in two sentences that between them contain everything section 3 spent five parts
establishing.

## The story

The new socket in the back room does not work.

You plug the lamp in, nothing. You try a different lamp, nothing. You check the switch, you
check the plug, and you are starting to think about the wiring when somebody who knows the
house says: go and look at the board by the front door.

There is a row of small switches on it, one per circuit, and one of them is down. You push it
up. The socket works.

The wiring was fine the whole time. Somebody had run the cable, fitted the socket, tested it,
and left the circuit switched off — sensibly, because the room was not finished. Everything
needed for the socket to work already existed and one switch stood between it and working.

It is a small annoyance and it teaches something: the difference between *not built* and *not
turned on* is invisible from the socket, and the two have completely different fixes.

## The idea in plain language

Everything sections 1 to 3 built by hand — the event log, the fold, the resume that starts at
the first missing step — ADK already has. It has had it since the session existed, because a
session's event list *is* an append-only log and
[2.1](../02-the-log-is-the-run/2.1-the-log-is-the-run.md)'s argument applies to it unchanged.

What ADK adds is the decision to *use* that log as a recovery plan, and that decision is a
single field.

**`ResumabilityConfig`** is a small configuration object with one meaningful attribute,
`is_resumable`, defaulting to `False`. You attach it to the **`App`** — the object that wraps
your root agent along with the rest of the application-level configuration. Day 51 attached
`ContextCacheConfig` to the same object; this is the same shape, one field along.

The default being `False` is worth pausing on, because it is a deliberate design choice and not
an oversight. Resumability changes what the runtime writes into the session and changes what
happens when you call the runner without a message, so it is opt-in: an application that has
not thought about idempotency should not silently acquire at-least-once semantics.

And the class documents its own limits, which is unusual enough to be worth reading carefully
rather than skimming. Two of them:

- **tool calls to be resumed must be idempotent**, because the guarantee once resumed is
  at-least-once;
- **any temporary or in-memory state is lost** on resumption.

Those are the two conclusions section 3 reached by measurement, printed by the framework about
itself. That agreement is the reason this day built the mechanism first: you can now read the
framework's caveats as familiar statements rather than as warnings about something you have not
seen.

## Why Sutra needs it

Day 58's triage graph runs under a `Runner` inside an `App`. Today's build brief turns this
field on, which is what makes Day 61's checkpoints and Day 64's human-in-the-loop resumption
available at all — both of those are built on the same machinery.

It also matters that this is a **framework** ID. ADK-43 is closed by knowing what the framework
gives you and what it explicitly does not, and the docstring is where the second half is
written down. A day that showed the config and skipped the caveats would have taught the switch
and not the circuit.

## The mechanism

`adk.py --arm config` constructs both versions of the object and prints the class's own
documentation.

*Verified against `adk.dev/runtime/resume/` on 2026-09-05, and against the installed
`google-adk==2.7.1` — the docstring below is read out of the installed class with
`inspect.getdoc`, not copied from the website.*

```bash
cd days/day-60-durable-execution/lab
uv run python adk.py --arm config
```

**Line by line:**

- `ResumabilityConfig()` with no arguments is constructed first, to show the default rather than
  assert it.
- `inspect.getdoc(ResumabilityConfig)` reads the docstring off the installed class. Printing it
  from the package rather than quoting the docs page is deliberate: the page and the package can
  disagree, and the package is what runs.
- The last block reads `EventActions.model_fields` for the three marker fields, which
  [4.3](4.3-what-adk-writes-into-the-log.md) is about.

Measured on 2026-09-05:

```text
arm: config   google-adk 2.7.1   model calls: 0

  ResumabilityConfig()                  -> is_resumable=False
  ResumabilityConfig(is_resumable=True) -> is_resumable=True

  the class docstring, verbatim:
    The config of the resumability for an application.

    The "resumability" in ADK refers to the ability to:
    1. pause an invocation upon a long-running function call.
    2. resume an invocation from the last event, if it's paused or failed midway
    through.

    Note: ADK resumes the invocation in a best-effort manner:
    1. Tool call to resume needs to be idempotent because we only guarantee
    an at-least-once behavior once resumed.
    2. Any temporary / in-memory state will be lost upon resumption.

  the markers ADK writes into the session's event log:
    EventActions.agent_state                  default=None
    EventActions.end_of_agent                 default=None
    EventActions.rewind_before_invocation_id  default=None
```

Read the docstring's second half slowly, because it is the whole of section 3 in four lines.

*"we only guarantee an at-least-once behavior once resumed"* — that is
[3.5](../03-doing-it-twice/3.5-exactly-once-is-about-effects.md)'s claim, made by the framework
about itself. It is not hedging. It is the strongest thing anything can guarantee, and saying so
plainly is the correct behaviour.

*"Tool call to resume needs to be idempotent"* — that is the framework telling you which half of
the problem is yours. ADK will re-run the step; making the re-run harmless is your job, with the
key from [3.3](../03-doing-it-twice/3.3-the-key-names-the-intention.md) and the atomicity from
[3.4](../03-doing-it-twice/3.4-the-ledger-and-the-atomic-window.md).

*"Any temporary / in-memory state will be lost"* — that is
[2.2](../02-the-log-is-the-run/2.2-replay-is-not-re-execution.md)'s in-memory guard, sending two
replies. And it has a very concrete consequence in the graph runtime that
[4.4](4.4-the-node-that-dies-is-the-node-that-does-not-run.md) measures.

Turning it on is three lines:

```python
app = App(
    name="sutra_durable",
    root_agent=Workflow(name="triage", edges=[("START", classify, research, draft)]),
    resumability_config=ResumabilityConfig(is_resumable=True),
)
```

**Line by line:**

- `App` is the application wrapper, not the agent. The config is application-level because
  resumability applies to every agent in the app — the field's own docstring says *"If enabled,
  the feature will be enabled for all agents in the app."* There is no per-agent opt-out.
- `root_agent=Workflow(...)` is the 2.x composition model that Day 53 established: a graph of
  nodes, not a tree of agents. This is **trap #1** from plan §5.1, and it matters here because a
  1.x tutorial will show you `sub_agents` and there is no resumability story attached to it.
- `resumability_config=` is the only new argument. Everything else about the app is unchanged,
  which is the point: this is a switch, not a rewrite.

ADK also announces itself when you use it:

```text
UserWarning: [EXPERIMENTAL] ResumabilityConfig: This feature is experimental and may change
or be removed in future versions without notice. It may introduce breaking changes at any time.
```

That warning is real and it is printed on first use. The lab silences it with
`warnings.simplefilter("ignore")` so the measured blocks stay readable, which is a decision you
should reverse in anything you ship: an experimental API that changes under you is exactly the
thing you want to be reminded about at every startup.

## When it breaks

The break is forgetting the switch and blaming the wiring, which is the story at the top of this
part.

The symptom is that a resume does not resume — the run starts from the beginning, or refuses
outright — and everything you inspect looks correct. The event log is there. The invocation id
is there. The stages did write their events. And none of it is used, because
`resumability_config` was never set and defaults to `False`.

`adk.py --arm refuse` shows the refusing version, and the important part is what the two lines
have in common:

```text
  is_resumable=False ValueError: Running an agent requires either a new_message or an invocation_id to resume a previous invocation. Session: s, User: u
  is_resumable=True  ValueError: Running an agent requires either a new_message or an invocation_id to resume a previous invocation. Session: s, User: u
```

**The same error either way.** That is worth knowing before you spend an evening on it: this
particular error does not tell you whether resumability is on. It is raised earlier, for a
different reason — the call gave the runner neither a message nor an invocation id — and
[4.2](4.2-the-invocation-id-is-the-claim-ticket.md) is about which error you get when you supply
one but not the other.

The way to find out whether the switch is on is to ask the object rather than to infer from
behaviour:

```python
print(app.resumability_config and app.resumability_config.is_resumable)
```

**Line by line:**

- `app.resumability_config` is `None` when it was never set, which is a different falsy value
  from `is_resumable=False`, and distinguishing them tells you whether somebody configured it
  off on purpose or never configured it at all.
- The `and` short-circuits so this is safe on an app with no config, and prints `None` rather
  than raising — which is the honest answer to "is it on?" when nobody has said.

## In production

**What a professional writes instead.** The flag is not written inline in three places. It is
part of one application factory that builds the `App`, so that the dev server, the tests and the
deployed worker all get the same configuration — because a system that is resumable in
production and not in tests has an untested recovery path, which is the one path you cannot
afford to have untested. The factory also asserts the flag rather than assuming it, because a
config that silently defaults to off is exactly the failure this part is about.

**What degrades at scale.** Turning resumability on changes what the runtime writes: extra
events carrying `agent_state` on top of the events you already had, as
[4.3](4.3-what-adk-writes-into-the-log.md) shows. Sessions get bigger, session storage gets
bigger, and the compaction story from Day 20 becomes load-bearing rather than optional. The
switch is free to flip and not free to run.

**The failure mode that only appears with real traffic.** The experimental warning coming true.
`ResumabilityConfig` is marked `@experimental` in 2.7.1, and the warning says the API may change
or be removed without notice. On a curriculum that pins versions and re-verifies on the day
(Principle 7), that is manageable. On a system that upgrades `google-adk` on a schedule, it is a
recovery path that can break on a minor version bump — so the mitigation is a test that actually
kills a run and resumes it, running in CI against the pinned version, which is what Day 65 will
build.

**The review comment a senior engineer leaves:** *"`resumability_config` is set in the worker
and not in the test harness, so every test we have runs against the non-resumable path. The
first time we exercise resume is in production. Move it into the app factory."*

**The interview question:** *"How do you make an ADK app resumable?"* An honest answer: *"One
field — `ResumabilityConfig(is_resumable=True)` on the `App`, which defaults to off. The
interesting part is not the switch, it is what the class documents about itself: it guarantees
at-least-once once resumed, so tool calls to be resumed must be idempotent, and any in-memory
state is lost. Those two sentences are the contract, and they mean the framework hands you
recovery and hands you back the idempotency problem. It is also marked experimental in 2.7.1, so
I would pin the version and have a test that genuinely kills a run and resumes it rather than
trusting the flag across upgrades."*
