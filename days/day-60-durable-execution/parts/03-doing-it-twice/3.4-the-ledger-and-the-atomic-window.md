# 3.4 — The ledger and the atomic window

## One-line answer

A correct key written in a **separate transaction** from the effect it protects still allows
**two closures for one ticket**, because the crash lands between the two commits — the key and
the effect must be one write or the fix has a gap of its own.

## The story

At the post office counter, the parcel gets a stamp and the clerk writes a line in the
register: date, destination, weight, receipt number.

The order matters, and every clerk who has done the job for a week knows it. If the parcel is
stamped and put in the sack before the register line is written, and the clerk is called away,
there is now a parcel in the sack that the register knows nothing about. If it is entered in
the register and the clerk is called away before it is stamped, the register claims a parcel
that is sitting on the counter.

Which is why the good ones do not treat these as two jobs. The stamp comes down on the parcel
and the pen is already moving, and the parcel is not in the sack until the line is finished.
One motion, not two. If you interrupt them, you interrupt the whole thing, and the parcel is
either fully handled or fully not.

The clerk has no clever trick for the middle. **They have arranged not to have a middle.**

## The idea in plain language

[3.3](3.3-the-key-names-the-intention.md) built the key: a name for an intention, remembered by
the receiver so a repeat can be recognised. The remembering happens in a table — call it the
**ledger** — with one row per honoured key.

That gives the receiver two writes to perform:

1. the **effect** — the closure row;
2. the **ledger entry** — the key, so a future attempt is recognised.

And two writes have a gap between them, which is
[3.1](3.1-the-uncertainty-gap.md)'s problem reappearing one level down, inside the fix. A crash
between the effect and the ledger entry leaves an effect that no key claims, so the next attempt
looks up its key, finds nothing, and does the effect again. The key was correctly derived and
correctly checked, and it still did not prevent the duplicate.

The repair is not another key. It is **atomicity**: making the two writes one indivisible
operation, so no crash can land between them. That word has a precise meaning, and Day 47
taught it from a paper —
[3.1 — the ticket torn in two](../../../day-47-persistent-sessions/parts/03-writes-that-survive/3.1-the-ticket-torn-in-two.md)
introduced transactions and the guarantee that a transaction happens completely or not at all.
Today is the payoff: **atomicity is what lets a fix for a gap not have a gap.**

The condition under which this works is worth stating, because it is also the condition under
which it does not:

> The effect and the ledger entry must live in **one store that can commit them together**.

When the effect is a row in your database, that is a single transaction and it is easy. When
the effect is somewhere else — an email provider, a partner's API — you cannot put their write
and your ledger row in one transaction, and no amount of care recovers the guarantee. That case
is [3.5](3.5-exactly-once-is-about-effects.md), and the answer there is different in kind.

## Why Sutra needs it

`_effects.py` holds both tables — `closures` and `honoured` — in the same SQLite database. That
is not an accident of the lab; it is the design decision this part is about, and the reason
Day 43's task rack and today's ledger live in the same file rather than in two.

If Sutra had put the ledger in one store and the closures in another — a Redis set of seen
keys, say, in front of a SQL table of closures, which is a very common arrangement — the two
writes could not be committed together and the gap would be permanent. It would also be
invisible in testing, because the window is small.

Day 64 makes this sharper still. An approval gate records *"a human approved this write"* and
then performs the write. Those are the same two-writes-one-gap shape, with the added property
that the audit record is the thing a reviewer will later rely on. An approval logged for a write
that never happened, or a write that happened with no approval logged, are both audit failures
rather than merely bugs.

## The mechanism

`atomic.py` performs the keyed close twice, with the effect and the key committed either
separately or together, and crashes in between.

```bash
cd days/day-60-durable-execution/lab
uv run python atomic.py
```

**Line by line:**

- The key is correct and derived, exactly as [3.3](3.3-the-key-names-the-intention.md) built
  it. Nothing about the key is the problem here, which is the point.
- The default arm commits the closure, *then* raises, *then* would have written the key. The
  raise sits exactly in the window between two `commit()` calls.
- `closures` and `honoured keys` are printed after each attempt, so the disagreement between
  the world and the ledger is visible rather than argued.

Measured on 2026-09-05:

```text
effect and key in one transaction: False

  attempt 1: died between committing the effect and committing the key
             closures=1  honoured keys=0
  attempt 2: closed
             closures=2  honoured keys=1

  Two closures for one ticket. The key was written after the effect, and the
  crash landed in between, so attempt 2 found no key and closed it again.
```

`closures=1  honoured keys=0` is the state the crash leaves behind, and it is the most
instructive line in this section. The ticket is closed. Nothing knows it. The ledger — the
entire mechanism built to prevent a second close — is empty, so the second attempt is not a
repeat as far as any code can tell.

Then commit them together:

```bash
uv run python atomic.py --atomic
```

**Line by line:**

- `--atomic` removes the intermediate `commit()`, so both `INSERT`s land in one transaction and
  the raise has nowhere to happen — there is no moment at which one is durable and the other is
  not.
- Attempt 2 now finds the key and refuses, returning the original result rather than performing
  a second close.

```text
effect and key in one transaction: True

  attempt 1: closed. There is no point between the two commits to die at,
             because there are not two commits.
             closures=1  honoured keys=1
  attempt 2: refused: this key was already honoured
             closures=1  honoured keys=1
```

One closure, one key, and the second attempt correctly recognised. The code that changed is one
line — a `commit()` that is not there.

Here is the shape in `_effects.py`, which does it correctly:

```python
cursor = conn.execute("INSERT INTO closures (ticket_id, note) VALUES (?, ?)", (ticket_id, note))
result: dict[str, object] = {
    "status": "closed",
    "ticket_id": ticket_id,
    "closure_seq": cursor.lastrowid,
}
if request_id is not None:
    conn.execute(
        "INSERT INTO honoured (request_id, result) VALUES (?, ?)",
        (request_id, json.dumps(result)),
    )
conn.commit()
```

**Line by line:**

- Two `execute` calls, **one** `commit`. That is the entire mechanism, and it is easy to miss
  precisely because the important thing is the commit that is absent between them.
- `json.dumps(result)` stores the answer the first attempt got, so a later replay returns the
  same `closure_seq` rather than a fresh one. Storing the *result* and not just the key is what
  makes a retry indistinguishable from the original from the caller's side.
- The ledger row is written inside the same transaction as the effect it describes, so the
  ledger can never claim less than the world contains — which is the direction that matters.
  The opposite direction is survivable: a ledger claiming a key whose effect rolled back means
  a legitimate write is refused once, which is loud and recoverable.

```mermaid
sequenceDiagram
    participant W as worker
    participant DB as one database
    Note over W,DB: two commits — a window exists
    W->>DB: INSERT closure; COMMIT
    Note over W: 💥 crash here
    W--xDB: INSERT key (never happens)
    Note over DB: closures=1, keys=0<br/>the next attempt closes again
    Note over W,DB: one commit — no window
    W->>DB: INSERT closure; INSERT key; COMMIT
    Note over DB: both, or neither
```

## When it breaks

The break worth reaching is the one where the transaction is *there* and does not cover what you
think it covers, because the effect left the database.

Somebody adds a notification inside the transaction:

```python
conn.execute("INSERT INTO closures (ticket_id, note) VALUES (?, ?)", (ticket_id, note))
notify_customer(ticket_id)  # an HTTP call, inside the transaction block
conn.execute("INSERT INTO honoured (request_id, result) VALUES (?, ?)", (request_id, blob))
conn.commit()
```

**Line by line:**

- The two database writes are still atomic with respect to each other. That much is unchanged.
- `notify_customer` is not, and cannot be, because it is not in the database. If the commit
  fails or the process dies after it, the transaction rolls back — closure gone, key gone — and
  the customer has still been notified. The rollback restores your database and does nothing at
  all about the email.
- It is also holding a transaction open across a network call, which is a lock-duration problem
  quite separate from correctness, and the one a reviewer will spot first.

The visible symptom in the lab is the ledger and the world disagreeing in the *other* direction,
which `atomic.py --race` from [3.3](3.3-the-key-names-the-intention.md) reaches:

```text
sqlite3.IntegrityError: UNIQUE constraint failed: honoured.request_id
```

and the symptom in production is a customer who was told their ticket was closed looking at a
ticket that is open. There is no error anywhere for that one. The rule it teaches is short:
**an external call does not belong inside a transaction**, and if the external call is the
effect you are trying to make idempotent, you are in [3.5](3.5-exactly-once-is-about-effects.md)
and this part's mechanism does not apply.

## In production

**What a professional writes instead.** The ledger row and the effect are written by the same
statement wherever the store allows it — `INSERT ... ON CONFLICT DO NOTHING` on the key, with
the effect in the same statement or the same transaction, so there is one round trip and no
application-level check at all. The lookup in
[3.3](3.3-the-key-names-the-intention.md) becomes an optimisation rather than the guard: it
saves a wasted write in the common case, and the constraint is what actually holds under
concurrency.

**What degrades at scale.** The ledger is on the write path of every write, so it is a hot
table with a unique index, and it grows for ever unless somebody sets a retention rule. The
retention rule is genuinely hard to get right and it is worth stating the reasoning: a key may
be deleted once no attempt carrying it could still arrive, which means the key's lifetime is
the maximum age of a resumable run plus the maximum retry window. Get it wrong in one direction
and the table outgrows the data it protects; get it wrong in the other and an old resume
duplicates an effect that everybody had stopped worrying about.

**The failure mode that only appears with real traffic.** Two stores that were one store. The
system starts with closures and keys in one database and, a year later, closures move to a
service. Nobody notices that the atomicity guarantee lived in the fact that they were in the
same file, because nothing in the code says so — the `commit()` still commits, the tests still
pass, and the window reopens silently. The defence is a comment on the transaction saying what
it is protecting and why both tables must stay together.

**The review comment a senior engineer leaves:** *"There is a `commit()` between the effect and
the key. That is not a keyed write, it is an unkeyed write with a key written afterwards — the
crash window is exactly the thing the key was added to close. Drop the first commit and let both
inserts land together."*

**The interview question:** *"Where do you store the idempotency key?"* An honest answer: *"In
the same transaction as the effect, which matters more than where. I measured the alternative: a
correctly derived key, correctly looked up, written in its own commit after the effect — a crash
between the two commits left one closure row and zero keys, so the retry found no key and closed
the ticket a second time. The fix was deleting one `commit()`. The constraint that makes it
work is that the effect and the ledger have to live in a store that can commit them together, so
the interesting question is really what happens when they cannot — when the effect is an email —
and there the answer is not a better transaction, it is putting something you own in front of
the thing you do not."*
