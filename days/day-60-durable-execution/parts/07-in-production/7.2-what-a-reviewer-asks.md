# 7.2 — What a reviewer asks

## One-line answer

Six questions decide whether a durable system is durable — where the state lives, what is
replayed versus re-executed, which steps have effects, what the key is derived from, whether the
key is written atomically with the effect, and what happens on a version mismatch — and a design
that cannot answer all six has a gap somewhere specific.

## The story

You are buying a second-hand scooter and you take the mechanic with you.

He does not look at the paint. He walks round it once, and then he does five or six things that
take a minute each. He starts it cold and listens. He looks at the oil. He puts it on the stand
and spins the back wheel with his ear near it. He looks at the chain, and then at the two sprockets
rather than the chain. He pushes down hard on the front, twice, and watches how it comes back up.

Then he says: it is fine, but you will be doing the fork seals within the year, and knock two
thousand off for that.

He was not being clever. He has a short list of things that are expensive to fix and easy to hide,
and he checked each of them. The seller had polished the scooter, which tells you nothing, and had
not replaced the fork seals, which tells you everything — and the reason the mechanic found it in
a minute is that he was not forming an impression. He was working through a list.

## The idea in plain language

Everything this day built comes down to a list of that kind. Six questions, each with a specific
failure behind it, each answerable in a sentence by anybody who has done the work and by nobody
who has not.

**1. Where does the state of an in-flight run live?**
Wrong answer: *in the process*. That is
[1.1](../01-what-a-run-is/1.1-the-run-is-not-the-process.md), and the cost was five model calls
for a run that needs three.

**2. Which parts of a resume replay, and which re-execute?**
Wrong answer: *the recovery code calls the stage functions again*. That is
[2.2](../02-the-log-is-the-run/2.2-replay-is-not-re-execution.md), and it is how a guard kept in
memory sends a customer two identical replies while running correctly both times.

**3. Which steps have effects outside the process?**
Wrong answer: *I would have to look*. If the answer is not immediate and short,
[1.3](../01-what-a-run-is/1.3-what-is-safe-to-resume.md)'s sort has not been done, and the resume
policy is a guess.

**4. What is the idempotency key derived from?**
Wrong answer: *a UUID at the call site*. That is
[3.3](../03-doing-it-twice/3.3-the-key-names-the-intention.md) — three attempts, three keys, three
closure rows, with the deduplication machinery working perfectly throughout.

**5. Is the key written in the same transaction as the effect?**
Wrong answer: *the key is written after the write succeeds*. That is
[3.4](../03-doing-it-twice/3.4-the-ledger-and-the-atomic-window.md): a crash between the two
commits leaves one closure and zero keys, and the retry closes it again.

**6. What happens when a resume meets a log written by different code?**
Wrong answer: *it has not come up*. That is
[6.1](../06-failure-lab/6.1-the-resume-that-met-different-code.md) — the fold succeeds, the shape is wrong, and the
run drafts against `None`.

Six questions. Each of them has a measured number behind it earlier in this day, which is what
makes them a checklist rather than an opinion.

## Why Sutra needs it

Day 65 is the phase gate for durability and human approval, and a gate needs criteria that can be
checked rather than felt. These six are the durability half of that list, and they are stated here
so that Day 65 can run them rather than invent them.

The list also has a shape worth noticing: **questions 1, 2 and 6 are about the record, and 3, 4
and 5 are about the effect.** Those are the two halves of the day, and a system usually fails on
one half or the other rather than both — teams that come from a data background get the record
right and forget the key, and teams that come from a payments background get the key right and
keep their run state in memory.

## The mechanism

The list, applied to Sutra as it stands at the end of this day, with the evidence rather than the
verdict:

| # | Question | Sutra's answer | Evidence |
| --- | --- | --- | --- |
| 1 | Where is run state? | the session's event log, folded on demand | [2.1](../02-the-log-is-the-run/2.1-the-log-is-the-run.md): 5 fields from 3 lines |
| 2 | Replay or re-execute? | replay above the log's end, re-execute below it | [2.2](../02-the-log-is-the-run/2.2-replay-is-not-re-execution.md): 0 requests, 7/7 fields identical |
| 3 | Which steps have effects? | one — `review` | [1.3](../01-what-a-run-is/1.3-what-is-safe-to-resume.md): 4 pure, 1 effectful |
| 4 | Key derived from? | `{invocation_id}/{step}/{subject}` | [3.3](../03-doing-it-twice/3.3-the-key-names-the-intention.md): 3 rows → 1 row |
| 5 | Atomic with the effect? | yes — one `commit` for both inserts | [3.4](../03-doing-it-twice/3.4-the-ledger-and-the-atomic-window.md): 2 closures without it |
| 6 | Version mismatch? | **not yet** — `TODO(me)` in the build brief | [6.1](../06-failure-lab/6.1-the-resume-that-met-different-code.md): drafts against `None` |

Row 6 is honest and it is the state of the repository at the end of today: the schema stamp is
demonstrated in `version.py` and is not yet in `sutra/durable.py`, because the build brief leaves
it for the learner. A table that reported six greens on the day the sixth was unwritten would be
the exact dishonesty Principle 10 forbids.

The whole day's evidence, in one command:

```bash
cd days/day-60-durable-execution/lab
uv run python kills.py && uv run python kills.py --keyed
```

**Line by line:**

- `kills.py` answers questions 3, 4 and 5 in one table, because a missing key or a non-atomic
  write both show up as `closures: 2` on the `inside review` row.
- `&&` runs the keyed arm only if the first exits `0`. Both arms exit `0` here — the sweep
  *reports* rather than asserting, which is
  [6.2](../06-failure-lab/6.2-four-kills-four-answers.md)'s deliberate choice so that the bad row
  is readable rather than fatal. Turning that into an assertion is the eval Day 65 will want.
- Questions 1, 2 and 6 need `replay.py` and `version.py`, which is why the checklist is six
  questions and not one script.

And the eval that goes red until the build brief is done:

```bash
uv run python gate.py; echo "exit: $?"
```

**Line by line:**

- `gate.py` checks `sutra/durable.py` for the four functions today asks for, and checks that
  `idempotency_key` returns the **same** value twice for the same intention — question 4, made
  mechanical.
- `echo "exit: $?"` prints the exit code, because a check that goes red is only useful if you can
  see that it did.

```text
  FAIL  sutra/durable.py does not exist - the build brief's first TODO(me) is unwritten

1 finding(s). Day 60's build brief is not done.
exit: 1
```

## When it breaks

The checklist breaks when it is answered about the design rather than about the code.

All six questions have a version that sounds right and is about intent: *we use idempotency keys*,
*state is in the event log*, *we replay rather than re-execute*. Every one of those can be true of
the design and false of the branch you are reviewing, and the difference is exactly the gap the
whole day has been about — the code between the effect and the record, the key that is minted at
the call site by one caller out of six, the recovery path that nothing exercises.

So each question has a follow-up that cannot be answered from intent:

| Question | The follow-up that finds the truth |
| --- | --- |
| 1 | show me a run's state, read out of the store, by a process that did not create it |
| 2 | show me the recovery function; does it import any stage? |
| 3 | show me the list; when was it last checked against the code? |
| 4 | show me two attempts' keys, printed |
| 5 | show me the `commit` calls between the effect and the key |
| 6 | show me a resume of a log written before the last deploy |

There is a second, subtler break: a checklist that is complete and stops being applied because it
keeps passing. The six questions above pass trivially on a system whose recovery path has never
run, because there is nothing there to be wrong. That is why
[6.2](../06-failure-lab/6.2-four-kills-four-answers.md)'s sweep belongs in CI: the checklist is
the design review, and the sweep is what stops the design review from being about a path nobody
executes.

## In production

**What a professional writes instead.** Nothing — at this stage they stop writing and start
buying. Everything this day built by hand exists as a product: **durable execution engines** that
own the log, the replay, the determinism capture and the retry policy, and hand you an
programming model where an ordinary-looking function is transparently resumable. ADK ships
integrations with two of them, documented at `adk.dev/integrations/temporal/` and
`adk.dev/integrations/restate/` (both fetched 2026-09-05), whose own summary is that if an agent
crashes or stalls the system recovers from the last successful step without manual session
resumption.

🅿️ **Parked, deliberately.** Those integrations are awareness-level for this curriculum: they
need a server to run against, which Addendum 02's zero-budget rule puts outside what Sutra can
require. The reason to know they exist is that *"we should use a durable execution engine"* is
the correct answer to most of this day in a company, and being able to say what such an engine
does for you — and what it still does not, which is question 3, because no engine can tell you
which of your steps have effects — is the difference between adopting one and cargo-culting one.

**What degrades at scale.** The checklist stops being answerable by one person. Six questions
about one graph is a conversation; six questions about forty services is an audit, and the answer
is to push each question down into something enforceable — a lint that fails a write tool without
a `request_id` parameter, a test that fails a stage declared pure that touches a store, a schema
version that is derived rather than typed. A checklist that scales is a checklist that has been
turned into checks.

**The failure mode that only appears with real traffic.** Durability that was true and stopped
being true. Every one of these six answers is a property of code that people keep editing, and
nothing about a normal change makes the recovery path fail visibly — because the recovery path
does not run in normal operation. The half-life of an unexercised durability guarantee is about
one quarter, and the only thing that changes that is the sweep running on every commit.

**The review comment a senior engineer leaves:** *"The design doc answers all six. The branch
answers four — `close_ticket` still has `request_id: str | None = None`, so five of the six call
sites are safe and the sixth is whichever one somebody adds next. Make it required."*

**The interview question:** *"Walk me through making an agent workflow durable."* An honest
answer: *"I would go through six questions in order, because each one has a specific failure
behind it. Where does run state live — ours is the session's event log, folded on demand, and a
recovering process rebuilt five fields from three lines. What replays versus re-executes — replay
everything above the log's end, re-execute below it; the replay cost zero requests and reproduced
all seven fields exactly. Which steps have effects — four pure, one effectful, and I sorted them
by running each twice and counting rows rather than by reading the code. What the idempotency key
is derived from — the invocation id, the step and the subject, because a key minted per attempt
left three closure rows where a derived one left one. Whether the key is written in the same
transaction as the effect — one commit, not two, because a crash between two commits leaves an
effect with no key. And what happens on a version mismatch, which is the one people have not
thought about: a resume reads events written by older code, and a fold does not type-check, so
the answer has to be a schema stamp and a refusal. If a design cannot answer all six, the gap is
in whichever one it cannot answer, and it is usually the last two."*
