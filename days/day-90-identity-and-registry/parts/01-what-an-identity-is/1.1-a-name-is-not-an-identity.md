# 1.1 — A name is not an identity

## One-line answer

The `name` field in an agent card is something the sender typed about itself, so it can only ever be
a claim — the identity is the **key**, and the name is a label somebody attached to that key.

## The story

The electoral roll at a polling booth.

You arrive and say your name. Nobody writes it down and nobody acts on it. The officer turns to a
printed list, finds a line, and looks at the photograph and the number beside it. Then they look at
you.

Saying your name is how you *point at* the entry. It is not how you prove you are the person in it.
If it were, the queue would move much faster and the roll would be pointless — and the whole
apparatus of a list, a photograph and a serial number exists because everybody understands, without
ever discussing it, that a name spoken aloud is an assertion and nothing more.

## The idea in plain language

An **agent card** is the document one agent sends another to introduce itself. Day 89 is where its
shape and its signature are taught. It carries a name, a description, a version, a list of skills,
an address to call.

Every one of those fields was written by the sender.

That sounds obvious and it is worth saying slowly, because the whole day follows from it. When a
peer sends a card saying `"name": "refund-desk"`, what has been established is that **something
claiming to be the refund desk sent you a document**. Not that it is the refund desk. Not that a
refund desk exists. Not that anybody has ever heard of it.

So identity needs something the sender cannot simply type. That thing is a **key pair**: two matched
numbers, one kept secret and one published, with the property that a message signed by the secret
half can be checked by anyone holding the public half, and cannot be produced by anyone else. The
public half is a value you can compare — and comparing values is something a computer can do
honestly.

The shift is small and total:

| The naive reading | The one that survives |
| --- | --- |
| the peer is called `refund-desk` | the peer holds the key `gTl3Dqh9F19W` |
| its name identifies it | its name labels a key that identifies it |
| two peers with one name is a coincidence | two peers with one name is a fork in the road |
| the card says what it may do | the card says what it *wants* to do |

The key is the identity. Everything else on the card is metadata about it, and metadata is
negotiable.

## Why Sutra needs it

Because Phase 14's gate is **"A2A peer verified; repo public"** and the word doing the work is
*verified*. Sutra is about to accept work from, and hand tickets to, agents it did not write. The
desk can move money under an approval gate (Day 63) and can read a customer's tickets (Day 39). A
peer that talks its way into either of those has done more damage than any prompt injection in
Phase 10.

And because the failure here is silent by construction. A peer that lies about its name produces no
error, no warning and no anomaly. It produces a conversation that goes well.

## The mechanism

Here is a card as this lab builds one, and the thing that makes it more than a claim:

```python
@dataclass(frozen=True)
class Card:
    """What a peer sends about itself. Every field in it is a claim until something checks it."""

    name: str
    url: str
    skills: tuple[str, ...]
    signatures: tuple[dict, ...] = field(default_factory=tuple)

    def payload(self) -> dict:
        """The part a signature covers: everything except the signatures themselves."""
        return {"name": self.name, "url": self.url, "skills": list(self.skills)}
```

**Line by line:**

- `name`, `url` and `skills` are the claims. They are ordinary strings because that is all they are —
  nothing about their type makes them true.
- `signatures` is a tuple and defaults to empty, because **an unsigned card is a legal card**. That
  default is not a convenience; it is the situation part [1.3](1.3-the-sticker-anyone-can-print.md)
  measures in ADK.
- `payload()` returns everything *except* the signatures, and that is the only interesting line in
  the class. A signature cannot cover itself, so a card splits into a signed part and an unsigned
  wrapper — and anything outside `payload()` is a field an attacker may change without invalidating
  anything.
- `frozen=True`: once a card has been checked, nothing in the process should be able to edit it. A
  verified card that is then mutated is a verified card about a different document.

And the identity itself is a fingerprint of the public key:

```python
def fingerprint(key: Ed25519PrivateKey | Ed25519PublicKey) -> str:
    """A short, human-readable name for a key. Twelve base64url characters of the public half."""
    return b64u(raw_public(key))[:12]
```

**Line by line:**

- The function accepts either half of the pair and always returns the *public* fingerprint, so a
  script cannot accidentally print a private key's identity and a public key's and get two answers
  for one agent.
- Twelve base64url characters is a display convenience, not a security boundary. It is short enough
  to read out in a table and long enough that this lab's six keys do not collide — and part
  [5.1](../05-in-production/5.1-what-a-registry-costs.md) says what to use in a system where an
  attacker gets to choose their own key.
- Ed25519 rather than RSA: a 32-byte public key and a 64-byte signature, no parameter choices to get
  wrong, and it is what the A2A card signature's `EdDSA` algorithm name refers to.

Two agents, two identities:

```bash
cd days/day-90-identity-and-registry/lab
uv run python -c "import _ids; print(_ids.fingerprint(_ids.REFUND)); print(_ids.fingerprint(_ids.IMPOSTOR))"
```

**Line by line:**

- Importing `_ids` generates both keys from fixed seeds, so these two values are the same on your
  machine as in this document. That is deliberate: a fingerprint in a day document should be
  checkable.

Measured on 2026-09-07:

```text
gTl3Dqh9F19W
7UkoxijRwsbq
```

Both of those agents send a card saying `"name": "refund-desk"`. Both cards verify perfectly against
their own key. **The name is identical and the identity is not**, and no amount of reading the card
more carefully will tell them apart.

## When it breaks

It breaks when code treats the name as the key, and the giveaway is a dictionary keyed by a display
name. There is no error text, so here is the shape to recognise instead:

```text
peers = {card["name"]: card for card in received}     # two cards, one survives
if peers["refund-desk"].verify():                     # verifies - against its own key
    give_it_the_ticket()
```

That code is correct in every respect except the one that matters. `verify()` returns `True`,
because the impostor really did sign its own card with its own key. A signature proves that **the
holder of a key signed this document**. It does not, and cannot, tell you that it was the right key.

Part [2.3](../02-the-registry/2.3-two-shops-one-name.md) measures exactly this collision and shows
which agent a name lookup actually returns.

The subtler break is a name that is *nearly* right. `refund-desk` and `refund-desk.example.co` are
different strings and a person skims them as the same word — which is why the identity a system
compares must be the key, and the name must be a thing it only ever displays.

## In production

**What a professional does.** Keys the peer table by a stable identifier that is never a display
name — a key fingerprint, or a URI the operator controls — and treats the display name as
presentation. The rule of thumb: if a value appears in a log line for a human *and* in an `if`
statement, one of those two uses is wrong.

**What degrades at scale.** Names collide more as the population grows, and they collide
*adversarially* once there is anything worth impersonating. A registry of ten agents in one team has
no collisions and needs no discipline; the same registry federated across three organisations has
two `triage` agents by Tuesday, and neither team did anything wrong.

**The failure that only shows with real traffic.** Unicode. Two names that render identically and
compare unequal — or worse, compare equal after a normalisation step somebody added for tidiness.
This is the same class as the lookalike domain and it is why the compared identity has to be raw key
bytes, where there is exactly one way to be equal.

**The review comment a senior engineer leaves:** *"You are looking peers up by `name`. Key the table
by fingerprint and keep the name for the log line — otherwise the first two agents that pick the same
word take each other's traffic and we find out from a customer."*

**The interview question:** *"An agent sends you a signed card. What have you learned?"* The answer
that shows experience is deliberately small: that whoever holds a particular private key signed that
particular document. Everything else — who they are, whether you should talk to them, what they may
do — is a separate question with a separate answer, and the next three sections are those answers.
