# 1.3 — What ADK puts in the card, and what it leaves out

## One-line answer

`AgentCardBuilder` produces a card with eight fields, `provider` and `securitySchemes` both null and
**zero signatures** — the A2A message type has a `signatures` field and ADK never fills it, so the
card the framework hands you is an introduction with nothing behind it.

## The story

The **government approved** sticker on a shop window.

It is a good sticker. Gold border, a serial number, an official-looking crest, and it has been in the
window long enough to have faded slightly at one corner, which somehow makes it more convincing.

Anybody can print one. There is a shop two streets away that will do a hundred for very little, and
nothing about holding one in your hand distinguishes the shop that was inspected from the shop that
liked the look of the sticker. The information that would settle it — a register, kept by whoever
does the approving, that you could look the serial number up in — is not on the sticker and was never
meant to be.

The sticker is not a lie. It is a *claim*, printed nicely, and the entire question is whether
anything anywhere corroborates it.

## The idea in plain language

ADK turns one of your agents into an A2A agent card with `AgentCardBuilder`. It reads the agent's
declaration — its name, its description, its sub-agents and their tools — and produces the document a
peer will fetch before deciding whether to talk to you.

Two things are worth knowing about that document before you rely on it.

**The A2A card type does have a place for signatures.** The message is a protobuf,
`lf.a2a.v1.AgentCard`, with fourteen fields, and one of them is a repeated `signatures`. Its element
type, `lf.a2a.v1.AgentCardSignature`, has exactly three fields — `protected`, `signature` and
`header` — which is the JSON serialization of a JWS. Day 89 is where that structure is taught. The
protocol clearly anticipates a signed card, and it anticipates **more than one signature**, which is
the detail section 2 turns out to need.

**ADK does not produce one.** `AgentCardBuilder.build()` assembles name, description, version, url,
skills, capabilities, provider, security schemes and the input and output modes, and returns. It never
touches `signatures`. That is not a bug — signing needs a key and a policy about which key, and a card
builder is the wrong place to decide either — but it does mean the default path produces a card that
answers question one of part [1.2](1.2-the-three-questions.md) with nothing at all.

So the card is the sticker: honest, useful, entirely self-asserted.

## Why Sutra needs it

Because this is the artefact Phase 14's gate hangs on. "A2A peer verified" is a claim about a
document, and knowing exactly which fields of that document are load-bearing — and which are
decoration a sender chose — is the difference between verifying a peer and admiring its description.

And because the gap is one this repository has to close itself, on purpose, with its own key and its
own policy. Nothing upstream will close it. Recognising *"the framework left this to me"* is a
different reaction from *"the framework handles this"*, and only one of them is followed by code.

## The mechanism

The whole measurement is: build a card the way ADK builds one, and count.

```python
DESK = LlmAgent(
    name="sutra_desk",
    model="gemini-2.5-flash-lite",  # pinned explicitly (ADK-73); never called here
    description="Answers support tickets and proposes refunds under an approval gate.",
    instruction="You are Sutra's support desk.",
)


async def build() -> dict:
    builder = AgentCardBuilder(agent=DESK, rpc_url="https://sutra.example/a2a")
    return MessageToDict(await builder.build())
```

**Line by line:**

- `LlmAgent` with a pinned model, and the model is **never called**. Building a card reads the agent's
  static declaration — its name, description and the tools hanging off it — so this whole part costs
  zero provider requests. The pin is still there because ADK-73 says every model is pinned explicitly,
  and a default would put this on `gemini-2.5-flash`.
- `AgentCardBuilder(agent=..., rpc_url=...)` — keyword-only, and both are the only two arguments this
  needs. The constructor also accepts `capabilities`, `doc_url`, `provider`, `agent_version` and
  `security_schemes`, all defaulting to `None`, which is why the measured card has nulls where it does.
- `await builder.build()` returns a protobuf message, not a dict. `MessageToDict` is the conversion,
  and it **omits unset fields entirely** rather than emitting them as null — which is exactly why the
  field count below is the interesting number.
- `rpc_url` defaults to `'http://localhost:80/a2a'` when omitted. Shipping a card with that address in
  it is a small, quiet way to publish a document nobody can use.

Constructing the builder emits a warning, and it is worth reading rather than filtering:

```text
UserWarning: [EXPERIMENTAL] AgentCardBuilder: ADK Implementation for A2A support
(A2aAgentExecutor, RemoteA2aAgent and corresponding supporting components etc.) is in
experimental mode and is subject to breaking changes. A2A protocol and SDK are themselves
not experimental. Once it's stable enough the experimental mode will be removed.
```

Note the sentence in the middle: *"A2A protocol and SDK are themselves not experimental."* The
protocol is stable and ADK's binding to it is not, which tells you where to expect churn and which
half of what you write today will survive.

Run it:

```bash
cd days/day-90-identity-and-registry/lab
uv run python card.py; echo "exit: $?"
```

**Line by line:**

- No flag: the card exactly as ADK builds it, with nothing added.

Measured on 2026-09-07:

```text
card built by AgentCardBuilder for agent 'sutra_desk'
  fields present: 8  ['capabilities', 'defaultInputModes', 'defaultOutputModes', 'description', 'name', 'skills', 'supportedInterfaces', 'version']

  signatures: 0

  what the card asserts about identity:
    name               "sutra_desk"
    version            "0.0.1"
    provider           null
    securitySchemes    null

  every field above is a claim the sender wrote about itself
  nothing in this card proves who sent it
```

**Eight fields of fourteen, and `signatures` is not among them.** Look at the four identity-relevant
rows: the name is a string the agent's own constructor set, the version is ADK's default `0.0.1`
because nothing supplied one, and `provider` and `securitySchemes` — the two fields that would say
*who runs this* and *how to authenticate to it* — are both null.

Attaching one signature is the whole difference:

```bash
uv run python card.py --signed; echo "exit: $?"
```

**Line by line:**

- `--signed` changes nothing about how the card is built. It attaches one signature afterwards, which
  is exactly where a real system would do it: the builder assembles the document, and signing is a
  separate step with a separate key.

Measured on 2026-09-07:

```text
  attached one signature by key gTl3Dqh9F19W
  verifies against that key: True
  signatures: 1
  ...
  the card carries a signature, so the name can be checked against a key
exit: 0
```

And now re-read part [1.1](1.1-a-name-is-not-an-identity.md)'s warning, because it applies to that
last line too: *"verifies against that key"* is true and is not yet enough. Which key it **should**
have been is section 2's question.

## When it breaks

The break is not an exception. It is a reasonable engineer reading the card, seeing a name, a version
and a skills list, and concluding that the framework has handled introductions.

The composite is short:

```text
1. AgentCardBuilder produces a card; it looks complete
2. the peer fetches it and the fields are all populated
3. nobody notices `signatures` is absent, because MessageToDict omits unset fields
4. a second agent publishes a card with the same `name`
5. the two are told apart by the only field anybody compared
```

Step three is the mechanical reason this is easy to miss: an unset protobuf field does not appear as
`null` in the converted dict, it does not appear **at all**, so a developer inspecting the card sees
eight populated fields and no gap where a signature would go. The absence is invisible in the exact
representation everybody debugs with.

The one thing that does raise here is unrelated and worth knowing anyway: `AgentCardBuilder` rejects a
non-agent early —

```text
TypeError: AgentCardBuilder requires a BaseAgent or Workflow, got dict.
```

— and wraps any failure inside `build()` as `RuntimeError: Failed to build agent card for <name>: ...`.
Both are loud. The missing signature is the one that is not.

## In production

**What a professional does.** Signs the card at publication time, in whatever step writes it to its
public address, using a key held by the deployment rather than by the code. The card is then a
document with a provenance, and — because A2A allows a repeated `signatures` field — a second
signature from an operator or a registry can be added later without invalidating the first. Section
[2](../02-the-registry/2.1-the-list-behind-the-counter.md) is what that second signature is for.

**What degrades at scale.** Card churn. Every deploy changes the skills list, which changes the
payload, which invalidates every signature over it — so a signing step that is manual becomes a
signing step that is skipped. This has to be part of the release pipeline on the day it is introduced
or it will not survive the second week.

**The failure that only shows with real traffic.** A card fetched over a channel the caller did not
authenticate. If the peer's card is retrieved from a URL, then whoever controls that URL controls the
card — and a card that is unsigned is exactly as trustworthy as the transport that delivered it. That
is the difference between a signed card, which you can cache and re-check later, and an unsigned one,
which is a fact about one moment on one connection.

**The review comment a senior engineer leaves:** *"The builder does not set `signatures` — check
`build()` if you do not believe me. Sign the card in the publish step and put the key in the
deployment, not in the repo. And set `provider`; a card with a null provider tells a peer nothing
about who to complain to."*

**The interview question:** *"Your framework generates a service descriptor. What do you check before
publishing it?"* The answer that shows experience checks what the generator **left unset** rather than
what it filled in — and the tell is whether the person knows that an unset field in a protobuf is
absent from the JSON rather than null, so the gap does not show up in any dump they are likely to look
at.
