# 2.3 — 💥 Two shops, one name

## One-line answer

Two agents registered under the same display name, both with valid signatures and both legitimately
in the registry, and a lookup by name returns the one with `move_money` in its capability list —
because nothing failed, the name was ambiguous, and the lookup had to pick something.

## The story

💥 **Two shops with the same name on the same road.**

🎬 **The scene.** *Sharma Electricals* has been on the main road for thirty years. Small shop, good
reputation, the place people go when a fan stops working.

😬 **The naive fix.** Last year another *Sharma Electricals* opened, four doors down. Different
family, entirely legitimate, registered properly. Everybody local knows which is which because
everybody local knows the old one.

💥 **Why it fails.** A delivery driver with a docket that says *Sharma Electricals, Main Road* does
not know which is which. He walks into the first one he reaches, hands over a consignment worth
rather a lot, gets a signature, and leaves. Nothing about his day contained an error. The docket was
correct, the shop was real, the name matched, and a signature was obtained.

💡 **The insight.** **An ambiguous identifier does not produce an error; it produces a choice.** And
because something has to be chosen, the system chooses — silently, by whatever rule happens to be in
the code, which is usually *the first one found* or *the last one written*. Neither of those is a
security policy, and both look like working software.

## The idea in plain language

Part [1.1](../01-what-an-identity-is/1.1-a-name-is-not-an-identity.md) said the name is a label and
the key is the identity. This part is what that costs when it is ignored — and the important thing is
that the collision does **not** require an attacker to do anything clever.

Consider the sequence. Sutra's registry has `refund-desk`. Six months later a second team registers
their agent, also called `refund-desk`, in the same registry, entirely above board, with a broader
capability set because their agent genuinely does more. Both entries are correct. Both keys are real.
Both signatures verify.

Now a piece of code does `registry_by_name["refund-desk"]`.

There are two entries and it returns one. Which one depends on whether the index was built with the
first write winning or the last, which depends on a loop nobody thought of as a decision. And the
consequence is not "the wrong agent got refused" — it is "the wrong agent got **accepted**, with its
own capability list."

That is the shape to recognise: an ambiguity resolved silently in favour of whichever entry the data
structure happened to keep.

## Why Sutra needs it

Because Phase 14 is where this repository stops being closed. Every peer so far was written here; from
day 89 onward some are not, and names are chosen by whoever registers them. `triage`, `desk`,
`refund-desk` are not creative names — they are the obvious ones, which is precisely why more than one
agent will have each.

And because the capability field makes the collision expensive rather than merely confusing. Getting
the wrong agent would be a correctness bug if agents were interchangeable. They are not: an entry
carries what its subject may do, so resolving to the wrong entry hands out the wrong permissions, and
part [4.1](../04-verified-is-not-authorised/4.1-the-man-the-office-sent.md) is what those permissions
then allow.

## The mechanism

The registry gains one more entry — a second, legitimate registration:

```python
LOOKALIKE = {
    "display_name": "refund-desk",
    "public_key": fingerprint(IMPOSTOR),
    "capabilities": ("read_ticket", "propose_refund", "move_money"),
    "vouched_by": "agent:registry.sutra.example",
    "status": "active",
}
```

**Line by line:**

- `display_name` is identical to the existing entry's. That is the whole setup and it required no
  forgery: a display name is a free-text field and nothing in a registry stops two rows sharing one.
- `public_key` is a different key. Both entries are internally consistent; each peer will sign with
  the key its own row names, and both will verify.
- `capabilities` includes `move_money`, which the original entry does not have. This is not
  contrived — a second team's agent doing more is the ordinary reason a second entry exists.
- `vouched_by` is the *same* voucher. Both registrations went through the same legitimate process,
  which is why an audit of how each peer got in finds nothing wrong with either.
- `status: active`. There is no sense in which this row is illegitimate. It is simply a second answer
  to a question that was supposed to have one.

And the index that turns two rows into a collision:

```python
    names: dict[str, list[str]] = {}
    for agent_id, entry in registry.items():
        names.setdefault(entry["display_name"], []).append(agent_id)
```

**Line by line:**

- Built as `dict[str, list[str]]` — a list per name, deliberately. Written the natural way, as
  `names[entry["display_name"]] = agent_id`, the second write silently overwrites the first and the
  collision becomes invisible: the index would have three entries and look perfectly healthy.
- `setdefault(...).append(...)` is what makes the ambiguity *representable*. A data structure that can
  hold the problem is the first step to detecting it; one that cannot will always report exactly one
  answer.
- Nothing here sorts or prefers. The order is the registry's insertion order, which is the order rows
  were added, which is a fact about history rather than about trust.

Resolve by id, which is what a registry is for:

```bash

```

**Line by line:**

- No flag: the lookup key is the id.

Measured on 2026-09-07:

```text
registry holds 4 agents under 3 display names
  billing-bot     1
  refund-desk     2  <- two agents answer to this name
  triage-desk     1

  we want to talk to: 'agent:refund-desk.example'
  lookup key:         id

  its key:            gTl3Dqh9F19W

  capabilities:       ['read_ticket', 'propose_refund']

  the id is unique, so the lookup had nothing to pick between

```

**Four agents under three names.** The collision is visible in the table and it changes nothing,
because the lookup never used the colliding column.

## When it breaks

Change one thing — the lookup key — and nothing else:

```bash
uv run python confusion.py --by-name; echo "exit: $?"
```

Measured on 2026-09-07:

```text
  we want to talk to: 'refund-desk'
  lookup key:         display_name
  resolved to:        agent:refund-desk.example.co
  its key:            7UkoxijRwsbq
  signature verifies: True
  capabilities:       ['read_ticket', 'propose_refund', 'move_money']

  a different agent was accepted, with a valid signature and a wider capability set
  nothing failed: the name was ambiguous and the lookup had to pick one
exit: 1
```

Read the two ids side by side:

```text
  agent:refund-desk.example
  agent:refund-desk.example.co
```

They differ by three characters at the end, and a person scanning a log line reads them as the same
thing. That is a second, independent trap living inside the first: even a system that correctly uses
ids will have a human somewhere comparing them by eye.

**There is no error text.** `signature verifies: True` on both runs. The only difference in the whole
output is one word on the `lookup key` line, and the consequence is a peer with `move_money` where a
peer without it was expected.

The composite, with each step defensible on its own:

```text
1. a display name is added to registry entries, for logs
2. a helper appears: peer_by_name(name), because ids are unwieldy
3. a second agent is registered, legitimately, with a name somebody else already used
4. peer_by_name returns one of them; the index kept the later write
5. that peer is verified, accepted, and asked to do something
6. its capability list is the one that was checked
```

Step four is where it goes wrong and step two is where it became possible. Nobody in that sequence
made a mistake that would be caught in review.

## In production

**What a professional does.** Makes the ambiguity impossible rather than detecting it: a unique
constraint on the identifier, and no lookup path keyed by anything else. Where a name lookup is
genuinely needed — an operator typing a name into a console — it returns **all** matches and refuses
to guess, because a human choosing between two rows is fine and a function choosing between them is
not.

**What degrades at scale.** Collisions go from accidental to adversarial. In one team, two agents
sharing a name is a coincidence you fix by renaming one. Across organisations, a name is worth taking,
and the second registration is the point of the exercise. At that stage the display name has to become
namespaced by whoever vouched for it — which is why `vouched_by` is a column and not a comment.

**The failure that only shows with real traffic.** Names that are not equal and not distinguishable.
Trailing whitespace, different capitalisation, a Unicode character that renders identically to an
ASCII one. Every one of those produces two rows that a comparison separates and a human does not,
which inverts the failure: now the *operator* is the component that resolves the ambiguity wrongly.

**The review comment a senior engineer leaves:** *"Delete `peer_by_name`. If the console needs it, have
it return a list and print all of them. The moment one caller does `[0]` on that we have shipped this
bug and we will find out when somebody's refund goes to the wrong agent."*

**The interview question:** *"Two records in your system have the same name. What happens?"* The answer
that shows experience does not say "we validate uniqueness" and stop — it asks what the lookup returns
when validation was added after the data, and points out that a silent choice is worse than an error
because it produces a working system with the wrong answer.
