# 2.2 — Trust on first use, and the swap it is meant to catch

## One-line answer

Pinning the first key you see costs nothing and catches a swap on the third contact, but it accepts
whoever turns up first — so it is strictly better than nothing, strictly worse than a registry, and
the difference between them is which contact is the dangerous one.

## The story

The milkman's substitute nobody mentioned.

The same man has come at half past six for four years. One morning a different man is at the door
with the same crate. He knows the flat number, he knows you take two litres, and he says the usual
fellow is unwell.

He is almost certainly telling the truth. And the reason you hesitate for a second is not
suspicion — it is that you have just noticed you have no way to check. What you have been relying on
all these years is not a credential; it is a *face you recognise*. The system worked perfectly for
four years and had nothing in it at all.

The first morning, four years ago, you did not check either. Somebody turned up with milk and became
the milkman.

## The idea in plain language

**Trust on first use** — pinning — is: the first time you meet a peer, remember its key; every time
after, require the same key. It is what an SSH client does the first time you connect to a host.

Its properties are unusually crisp, which is why it is worth studying rather than dismissing.

**What it gets right.** Every contact after the first is protected. A peer whose key changes is
noticed and refused, and noticed *loudly*, because a mismatch against a remembered value is a
detectable event rather than an absence.

**What it gets wrong.** The first contact is unprotected, completely. Whoever answers first becomes
the peer, for ever, and there is no moment at which pinning could have known better. If the impostor
is there on day one, pinning locks the impostor in and then faithfully defends it against the real
agent.

**Why it survives anyway.** Because the first contact is often the *safe* one — a developer setting
something up by hand, on a network they control, at a moment they chose. The exposure is concentrated
into a single event that a human can supervise. That is a real security property and it is why the
technique has lasted.

A registry moves the check earlier: it is a decision made before the first contact by somebody who
looked. The trade is that a registry has to exist, be maintained, and be right — and part
[2.1](2.1-the-list-behind-the-counter.md)'s third failure is what a stale one costs.

| | first contact | later contacts | needs |
| --- | --- | --- | --- |
| no pinning | accepted | accepted | nothing |
| pinning | accepted | swap refused | a place to remember |
| registry | checked | checked | a maintained record |

## Why Sutra needs it

Because the two policies fail at different moments and Sutra will use both. A registry for the peers
that matter, and pinning as the backstop for everything else — because pinning's failure is bounded
and doing nothing is not.

And because pinning is what a system does *by accident* when nobody decides. A process that holds a
peer's key in memory across contacts is pinning without calling it that, and a process that does not
is trusting every contact independently. Which of those two you have is a consequence of where a
variable was declared, and this part is the argument for making it a decision instead.

## The mechanism

One function, three policies, the same three contacts:

```python
def accept(presented, key_id: str, pinned: dict, policy: str) -> tuple[bool, str]:
    """One contact under one policy. `pinned` is this process's memory of who it has met."""
    if not signature_valid(presented.payload(), presented.signatures[0], KEYS[key_id]):
        return False, "signature does not verify"
    if policy == "registry":
        expected = REGISTRY[AGENT_ID]["public_key"]
        if expected != key_id:
            return False, f"registry expects {expected}"
        return True, "matches the registry entry"
    if policy == "no-pin":
        return True, "signature verified; no memory of any previous key"
    seen = pinned.get(AGENT_ID)
    if seen is None:
        pinned[AGENT_ID] = key_id
        return True, "first contact - key pinned"
    if seen != key_id:
        return False, f"pinned key is {seen}"
    return True, "same key as last time"
```

**Line by line:**

- The signature check happens **first and for every policy**. All three policies agree that a forged
  signature is refused; what they disagree about is which key should have signed. Keeping the shared
  check above the branch makes that structure visible.
- `policy == "registry"` compares against a value looked up from a record. Note there is no `pinned`
  write on this path — a registry does not need a memory, because its memory is the file.
- `policy == "no-pin"` returns `True` with a reason that names exactly what it did not do. This is the
  ablation and it is not a straw man: it is what code does when the key is verified inside a request
  handler and nothing outlives the request.
- `seen is None` is the first contact, and the assignment `pinned[AGENT_ID] = key_id` is the entire
  security decision, made silently, on whoever happened to arrive.
- `seen != key_id` is the catch, and it returns the **remembered** key in the message rather than just
  saying "mismatch" — an operator needs to know which of the two keys is the surprising one.
- `pinned` is a parameter rather than module state, so the caller decides its lifetime. That is the
  whole point of the part: pinning across a process is a different policy from pinning across a
  restart, and both are spelled the same way in most code.

**Line by line:**

- Same three contacts, same keys, same signatures. Only the policy differs, so any difference in the
  output is attributable to the policy and to nothing else.

Measured on 2026-09-07:

```text
  first     gTl3Dqh9F19W    accept    matches the registry entry
  second    gTl3Dqh9F19W    accept    matches the registry entry
  third     7UkoxijRwsbq    REFUSE    registry expects gTl3Dqh9F19W

  keys this process has ever pinned: 0
```

**Same verdicts, different reasons, and one number tells them apart:** the registry run pinned
**zero** keys. It never needed a memory, because it never learned anything from a contact — it knew
before the first one. That is the whole difference between the two policies expressed as a count.

## When it breaks

The ablation is the policy a system has when nobody chose one:

```bash
uv run python tofu.py --no-pin; echo "exit: $?"
```

Measured on 2026-09-07:

```text
policy: no-pin

  contact   key             verdict   why
  first     gTl3Dqh9F19W    accept    signature verified; no memory of any previous key
  second    gTl3Dqh9F19W    accept    signature verified; no memory of any previous key
  third     7UkoxijRwsbq    accept    signature verified; no memory of any previous key

  keys this process has ever pinned: 0
  a different key answered to the same id and was accepted
exit: 1
```

**Three contacts, three verifications, all genuine.** Every signature in that run is valid. The
impostor did not forge anything — it signed its own card with its own key, exactly as the real peer
did, and a verifier with no memory has no basis on which to prefer one over the other.

There is no error text and there cannot be, because nothing went wrong at the layer that was checking.
This is part [1.1](../01-what-an-identity-is/1.1-a-name-is-not-an-identity.md)'s sentence arriving as
a measurement: a signature proves the holder of a key signed the document, and *which key* is a
question the signature is structurally incapable of answering.

Pinning's own failure has no output here because it happens before the first line: if the impostor had
been `first` instead of `third`, the pin run would have printed `first contact - key pinned` against
`7UkoxijRwsbq` and then defended it. Change the order in `contacts` and watch it happen — that is the
check-yourself exercise.

## In production

**What a professional does.** Uses a registry for anything that matters and pinning underneath it, and
writes down where the pin lives. A pin held in a process variable is erased by every restart and every
new replica — which, on the container work of Day 86, means a system with four replicas has four
independent first contacts and gets four chances to be fooled. If pinning is the control, the pin
store must be as durable and as shared as the thing it protects.

**What degrades at scale.** Legitimate key changes become common. One peer rotating once a year is an
event; forty peers rotating on a schedule is a steady drip of pin mismatches, and a mismatch that
happens weekly is a mismatch somebody writes a script to clear. That is the moment pinning stops being
a control, and it arrives from ordinary growth rather than from any attack.

**The failure that only shows with real traffic.** Pinning the wrong thing. A pin on the key survives a
peer moving address; a pin on the address survives a peer changing key; teams frequently pin the
certificate, which survives neither and expires. Pin the identity, which by part
[1.1](../01-what-an-identity-is/1.1-a-name-is-not-an-identity.md) is the key.

**The review comment a senior engineer leaves:** *"Where does this pin live? If it is a dict on the
client object then every restart is a first contact and we have written the ceremony without the
protection."*

**The interview question:** *"Your service connects to a peer over TLS and verifies its certificate.
Is that enough?"* The answer that shows experience separates *this certificate is valid* from *this is
the peer I meant*, and then asks the question this part is about: what do you compare against, and
when was that value decided?
