# 3.1 — Rotation: the two rules that pull opposite ways

## One-line answer

When a peer changes its key, two things must both stay true — everything it signed before must still
verify, and it must no longer be accepted presenting the old key — and satisfying both is why a
registry entry needs a `previous_keys` list rather than a single field.

## The story

The new chequebook, and the cheques already written.

You close one account and open another, and the bank issues a new book. From today, a cheque drawn on
the old book is refused: the account is closed, that is the point of closing it.

But three cheques written last month are still going round. The electricity board has one, the school
has one, and one is sitting in somebody's drawer. Those were valid when they were signed and the whole
system depends on them staying valid — nobody would ever pay by cheque if closing an account
retroactively unpaid every bill you had settled.

So the bank holds both facts at once. *That account is closed for new instructions.* And: *instruments
drawn on it before the closing date are honoured.* Two rules, opposite directions, one record.

## The idea in plain language

Key rotation is routine and it should be. Keys are rotated on a schedule, after a suspected exposure,
when somebody leaves, when a machine is rebuilt. A system where rotation is painful is a system where
keys do not get rotated, which is the actual security failure.

The awkwardness is that rotation has two requirements which are not the same requirement.

**Rule one: history must still read.** A decision the peer signed in August is an artefact — it is in
a log, an audit trail, a stored approval. If rotating a key makes those unverifiable, then rotation
destroys evidence, and a system that punishes you for rotating keys will not have its keys rotated.

**Rule two: the old key must stop working *live*.** The reason for rotating is usually that the old
key should no longer be honoured. If a peer can still present it and be accepted, rotation has
achieved nothing.

Put together: the old key must be accepted **as a signer of the past** and refused **as a claimant in
the present**. That is one key with two different answers depending on what is being asked, and no
single boolean field can hold it.

Which gives the registry entry its shape:

```text
public_key      the one key accepted for a live contact today
previous_keys   keys that may still verify things signed before the change
```

The subtlety, worth naming now and returning to in **When it breaks**: `previous_keys` as written here
has no dates in it, so it says "this key was once ours" and not "this key was ours **until** the
seventh of September". That distinction is the difference between a correct implementation and this
one, and it is deliberate — the gap is the exercise.

## Why Sutra needs it

Because Sutra already stores signed things. Day 63's approval gate records that a human approved a
write; Day 82's regression discipline stores results a run produced. The moment any of those carries a
peer's signature, rotation becomes a question about the archive rather than about the connection.

And because the next part is revocation, which looks like rotation and is not. Getting rotation right
first is what makes the difference visible: rotation keeps the peer and changes its key; revocation
keeps the key and removes the peer.

## The mechanism

Two checks against the same registry entry, asking about two different moments:

```python
    # Rule one: an artefact signed before the rotation must still verify.
    accepted_keys = {current, *previous}
    old_id = fingerprint(TRIAGE_OLD)
    archive_ok = old_id in accepted_keys and signature_valid(ARCHIVED, ARCHIVED_SIG, KEYS[old_id])
```

**Line by line:**

- `accepted_keys` is a set union of the current key and every previous one. This set is used **only**
  for verifying history — building it once and reusing it for live contacts is precisely the bug this
  part exists to prevent.
- `old_id in accepted_keys` is checked **before** the cryptographic verification, and the order is the
  whole design. The signature will verify regardless — it is a real signature by a real key. What
  decides the outcome is whether this registry entry acknowledges that key at all.
- `signature_valid(ARCHIVED, ARCHIVED_SIG, ...)` verifies the stored artefact, not a fresh card. The
  payload is a decision recorded in August, which is what makes this rule one and not rule two.

```python
    # Rule two: the peer must not be accepted today presenting the old key.
    stale = card("triage-desk", ("read_ticket",), TRIAGE_OLD, AGENT_ID)
    live_ok = fingerprint(TRIAGE_OLD) == current and signature_valid(
        stale.payload(), stale.signatures[0], KEYS[old_id]
    )
```

**Line by line:**

- The comparison is against `current` **alone** — `previous` is not in scope on this path. That single
  difference from the block above is the whole of rotation, and writing the two checks a few lines
  apart is what keeps somebody from "simplifying" them into one.
- `card(...)` builds a *fresh* card signed with the old key: a peer turning up today with a
  credential it should have retired. The signature on it is perfectly valid, which is why the check
  cannot be a signature check.
- `live_ok` is named for the thing that must be **False**. A variable whose correct value is false
  reads oddly and it is worth it — the alternative is `not stale_refused`, and double negatives in
  security code are where mistakes hide.

Three lines, three different answers about **two keys**. The old key reads the archive and is refused
live; the new key is accepted live. One entry, two rules, both satisfied.

## When it breaks

Drop `previous_keys` and rule one fails immediately:

```bash
uv run python rotate.py --no-history; echo "exit: $?"
```

Measured on 2026-09-07:

```text
current:  iodf_x6zhFFX
previous: (not kept)

  archived decision signed 2026-08-02       UNREADABLE
  peer presenting the old key today         refused
  peer presenting the new key today         accepted

  keys the registry will verify history against: 1
  the old signature no longer verifies: rotating the key erased the archive
exit: 1
```

**Rule two is still satisfied.** The old key is refused live, the new key works, and every live
contact behaves correctly. Only the archive broke — and the archive is the thing nobody reads until an
audit, which means this failure has a latency measured in quarters.

There is no error text. The signature does not fail to verify in any cryptographic sense; the verifier
simply has no key to check it against, and returns the same `False` it would return for a forgery.
That collapse is its own trap: **"we do not have a key for this"** and **"this signature is invalid"**
must be distinguishable, or an audit will report tampering where the real answer is a rotation nobody
recorded.

And the gap this lab has, stated plainly rather than hidden: `previous_keys` carries no dates. So it
answers *"was this ever our key"* rather than *"was this our key when this artefact was signed"*. A
peer whose key was compromised in August and rotated in September would still have its August
signatures accepted — which is right for an honest rotation and wrong for a compromise. Fixing it
means storing a validity window per key and comparing it against the artefact's timestamp, and it is
in the build brief for exactly that reason.

## In production

**What a professional does.** Rotates on a schedule, with an overlap window during which both keys are
accepted for live contacts, and keeps retired keys for verification for as long as the artefacts they
signed are retained. The overlap is what makes rotation a non-event: without it, the peer and everyone
who talks to it must switch at the same instant, which means rotation needs a maintenance window,
which means it happens once a year at best.

**What degrades at scale.** `previous_keys` grows without bound. A peer rotating quarterly for five
years has twenty entries, and the verification set that history is checked against gets larger and
looser every time. The discipline is that retired keys expire out of the set on the same schedule the
artefacts do — which requires knowing how long artefacts are kept, and is where a key policy and a
data-retention policy turn out to be the same document.

**The failure that only shows with real traffic.** Rotation during a long-running conversation. A
session that authenticated with the old key and is still open when the rotation lands: does it
continue, or is it dropped mid-flight? Nothing in this lab has a session. Day 47's persistent sessions
and Day 60's durable execution are both places where the answer matters, and the answer nobody chose
is the one where the session survives indefinitely on a key that was retired.

**The review comment a senior engineer leaves:** *"Put a `valid_until` on every previous key. Right now
we accept an August signature from a key we rotated because it leaked, and the whole reason we rotated
was that somebody else had it in August."*

**The interview question:** *"How do you rotate a signing key?"* The answer that shows experience gives
two rules rather than one, notices that they pull in opposite directions, and then asks the question
that separates rotation from revocation: *why* is the key being rotated — because if the answer is
"it leaked", accepting its old signatures is exactly wrong.
