# 4.1 — Verified is not authorised

## One-line answer

Being certain who a peer is tells you nothing about what it may do, so the capability list on the
registry entry has to be consulted **on every call** — and a system that treats identity as permission
lets a correctly-verified refund desk move money.

## The story

The man the office sent to fix the air conditioning.

He arrives, and everything about him checks out. He knows which flat, he says the name of the company
correctly, the building secretary confirms the visit was booked, and he is wearing the right shirt.
You let him in, entirely reasonably.

Then he goes into the bedroom.

Nothing about him has changed. He is still exactly who he said he was, still sent by the company you
called, and if you asked for identification again it would be as convincing as the first time.
Verifying him harder answers nothing, because the question that just came up is not *who are you* — it
is *what did we agree you were here to do*, and that question was answered when the visit was booked,
by somebody who said **the air conditioning**.

## The idea in plain language

Part [1.2](../01-what-an-identity-is/1.2-the-three-questions.md) separated three questions. This part
is the third one, and it exists as a separate part because the collapse of question three into question
one is the most common mistake in this whole area, and it is committed by careful people.

The collapse looks like this. A great deal of work goes into verifying a peer — signatures, registry
lookup, key matching, revocation. All of it succeeds. There is a natural feeling of *arrival*: the hard
part is done, the peer is who it says it is, and the request can be served. And that feeling is exactly
the error, because the effort spent on question one has no bearing whatsoever on question three.

The correct shape is boring:

**The grant is per peer and lives in the registry.** Not in the card the peer sent — a peer stating its
own capabilities is stating what it would like. This lab's cards do carry a skills list, and it is
never consulted for authorisation; only the registry entry's `capabilities` is.

**The check is per call, not per session.** Verification happens once because identity does not change
mid-conversation. Authorisation is checked every time because the *request* changes every time, and the
peer's grant may also have changed since the conversation started.

**The default is refusal.** A call not in the list is refused, including calls that did not exist when
the entry was written. That is what makes adding a capability to Sutra safe: a new tool is available to
nobody until an entry names it.

This is Principle 13 — blast radius before capability — applied to a peer instead of a tool. Day 68
built least-privilege tools for Sutra's own use; the registry entry is the same idea pointed outward.

## Why Sutra needs it

Because the capability that matters is already in the table. `move_money` is a real entry in this
registry, and part [2.3](../02-the-registry/2.3-two-shops-one-name.md) already showed a lookalike peer
that has it. Identity work protects against the wrong peer arriving; capability work protects against
the *right* peer asking for something it was never given, which is the case identity checks cannot
address by construction.

And because Sutra's own approval gate (Day 63) is a capability boundary with a human on it. A peer that
can call the tool behind that gate directly has routed around a control this repository spent a day
building.

## The mechanism

The grant comes from the registry, and the call is checked against it:

```python
    entry = REGISTRY[AGENT_ID]
    granted = set(entry["capabilities"])
    ...
    for call in CALLS:
        in_grant = call in granted
        allowed = verified if open_door else (verified and in_grant)
```

**Line by line:**

- `granted` is built from `entry["capabilities"]` — the **registry's** view. The card the peer
  presented also carries a skills tuple and it is never read here, which is the design and not an
  oversight.
- `set(...)` because membership is the only operation, and because the tuple in the registry stays
  immutable while this local view is free to be a set.
- The loop is over `CALLS`, plural — the peer makes four calls in one conversation and each is checked
  independently. A check hoisted out of this loop is the bug the part is about.
- `verified and in_grant` is the correct expression, and `verified` alone is the ablation. Both are on
  the same line so the difference is legible: the wrong version does not omit a check, it omits a
  *conjunct*, which is a much easier thing to write by accident.
- `verified` is computed once, before the loop, and that is right — identity genuinely does not change
  between calls in one conversation. The asymmetry between the two is the whole lesson: one fact is
  stable and one is not.

Run it:

```bash
cd days/day-90-identity-and-registry/lab
uv run python authz.py; echo "exit: $?"
```

**Line by line:**

- No flag: every call checked against the grant.

Measured on 2026-09-07:

```text
peer:      agent:refund-desk.example
verified:  True (key gTl3Dqh9F19W, vouched by agent:registry.sutra.example)
granted:   ['propose_refund', 'read_ticket']
policy:    capability checked per call

  call              in grant   verdict
  read_ticket       True       allowed
  read_ticket       True       allowed
  propose_refund    True       allowed
  move_money        False      REFUSED

  calls outside the grant that were allowed: 0
  being verified got the peer through the door and no further
```

**`verified: True` on the second line and `REFUSED` on the last.** Both are correct simultaneously,
and holding those two facts together without discomfort is the whole skill this part teaches.

## When it breaks

Treat identity as permission — one conjunct removed:

```bash
uv run python authz.py --verified-is-authorised; echo "exit: $?"
```

Measured on 2026-09-07:

```text
policy:    identity is permission

  call              in grant   verdict
  read_ticket       True       allowed
  read_ticket       True       allowed
  propose_refund    True       allowed
  move_money        False      allowed

  calls outside the grant that were allowed: 1
  the peer is exactly who it says it is, and that was treated as a yes to everything
exit: 1
```

Note the `in grant` column: it still says `False`. **The system computed the right answer and did not
use it.** That is worth pausing on, because it is the realistic version of this bug — not an absent
capability model, but a capability model that is populated, logged, displayed on a dashboard, and not
in the branch that decides.

There is no error text. The refused call is not refused; it succeeds, money moves, and the audit log
records a fully verified peer making a request it was authorised to make, because the log is written by
the same code that made the decision.

The composite:

```text
1. authentication is built carefully and works
2. a handler asks: is this peer verified? yes -> serve the request
3. capabilities are added to the registry, for reporting
4. a peer is granted read access to help with triage
5. the same peer calls a write tool
6. it is verified, so it is served
```

Step four is where the exposure is created and it is the step that looks most benign — granting *less*
than full access is what created a peer whose grant could be exceeded. A system where every peer has
everything has no step five, which is why this failure arrives only after somebody starts doing the
right thing.

## In production

**What a professional does.** Puts the authorisation check at the boundary the capability names, not in
the request handler. If `move_money` is a tool, the check belongs where that tool is invoked, so that
every path to it is covered including the ones added next year. A check in the handler protects the
handler; a check at the tool protects the capability.

**What degrades at scale.** The grant list becomes a policy language. Ten peers with three capabilities
each is a table anybody can read; two hundred peers with conditional grants — this capability, but only
for tickets belonging to that customer — is a policy engine, and policy engines have the property that
nobody can answer "who can move money" by reading them. The discipline that survives is a periodic
report that answers exactly that question, generated from the policy rather than written alongside it.

**The failure that only shows with real traffic.** A grant that changes during a conversation. A peer
authorised at the first call and de-authorised while a long conversation is still open continues to be
served if the check was hoisted. This is the same conclusion part
[3.2](../03-keys-change/3.2-the-card-of-someone-who-left.md) reached about revocation, and the same fix
— check per call — closes both.

**The review comment a senior engineer leaves:** *"You compute `in_grant` and log it and then branch on
`verified`. Move the check to where the tool is called, so the next handler somebody writes gets it for
free."*

**The interview question:** *"You have verified the caller. What is left to do?"* The answer that shows
experience says that verification has established one thing and that the request has not been examined
at all — and then names where the grant is stored and how often it is consulted. The tell is *per call*
versus *per session*: only one of those answers survives a long-lived connection.
