# 2.3 — A site you own

## One-line answer

The page this agent drives is served from `lab/site/` on a port on your own machine for three
separate reasons — it cannot change under you, driving somebody else's site is not yours to do, and
the blast radius is a port you control — and only the first of the three is the one people think of.

## The story

A barber's shop, mid-afternoon, nobody waiting. The apprentice is not standing about. He has a
rubber head clamped to the end of the counter and he is cutting its hair.

Three things are true about that head at once, and only the first is usually said out loud.

The obvious one: **it does not change between attempts.** The hairline is where it was yesterday. So
when the fade finally comes out even, it came out even because he got better at it, and not because
this one happened to be easier.

The second, which nobody says because it sounds rude: **there is no customer being practised on.**
The person in the chair sat down for a haircut. They did not sit down to be somebody's lesson, and
using them as one is not a thing you get to decide on their behalf.

The third, which is the whole reason a shop keeps one: **the worst thing that can happen is a ruined
rubber head.** He can take too much off. He can take all of it off. Then he unclamps it and puts up
another one.

And there is a fourth thing, which is the honest limit of the practice head: nobody has ever become
a barber on one. Real hair has a crown that spirals the wrong way, a scar underneath that nobody
mentioned, and a person attached to it who turns to say something halfway through. He finds all of
that out on his first real head — with the owner standing behind him, watching every single pass.

## The idea in plain language

A **fixture** is a stand-in for a real thing, built on purpose so that a test has something fixed to
run against. This day's fixture is a two-page website — `status.html` and `history.html` in
`lab/site/` — served over HTTP from `127.0.0.1` by `lab/_site.py`. It is dressed as a cloud vendor's
service status page, because that is the page Sutra's desk actually needs to read.

`lab/_site.py` states three reasons for keeping it local, and they are worth taking one at a time,
because each is a different kind of argument and only one of them is about testing.

**It cannot change under you.** A real status page is maintained by somebody else's incident team,
in real time, on their worst morning of the quarter. Every number in this day — the screenshot sizes
below, the coordinates in [2.2](2.2-the-coordinates-are-not-your-pixels.md), the refusal counts in
section 3 — is a measurement, and a measurement taken against a page that is being edited while you
read it is not a measurement. It is an anecdote with a number in it. This is the same argument
[Day 69's 4.1](../../../day-69-pii-and-data-boundaries/parts/04-invented-on-purpose/4.1-why-invent-the-customers.md)
made about invented customers: being able to run the same thing again and get the same answer is a
**capability gained**, not a compromise accepted.

**Driving somebody else's site is not yours to do.** This one is not about testing at all. An agent
clicking around a third party's pages is using their service in a way they did not agree to, and the
agreement is usually written down somewhere in their terms. Above a volume of about one, it is
indistinguishable from scraping *from their side of the connection* — they cannot see your
intentions, only your requests, and a well-behaved experiment and a badly-behaved crawler produce
the same log lines. There is a sharper edge to it too. The scripts in this day are built to
misbehave on purpose: section 3's model tries to navigate somewhere it should not and to type a
credential into a page. Rehearsing that against a stranger's server is not a lab exercise. It is a
thing you are doing to them.

**The blast radius is a port on your own machine.** This is the reason that makes the rest of the
day possible rather than merely polite. Section 4 is about a boundary, and a boundary needs an
outside. If the agent starts out on the open web then "outside" is everything, and the sandbox has
nothing it can be measured against. Here the boundary is one origin, `http://127.0.0.1:8771`, and it
is an origin you serve yourself — so *the agent left the boundary* becomes a fact you can check
rather than a thing you hope about. That is Principle 13, blast radius before capability, applied
before the capability existed at all.

Notice that the three reasons are not ranked by importance and cannot substitute for each other. A
recorded copy of a real page would satisfy the first and fail nothing else; asking a vendor's
permission would satisfy the second and leave the page still moving. The fixture is local because
all three happen to point the same way.

## Why Sutra needs it

Sutra's desk will eventually read a real vendor's real status page, because that is where the
incident text lives and [1.3](../01-no-api/1.3-fifteen-doors-one-used.md) established that there is
no API to ask instead. Everything in sections 3 and 4 is the rule set that has to exist **before**
that day, and a rule has to be written against something.

The fixture is what makes those rules checkable rather than merely stated. Section 3 asks whether
the door refused an off-origin navigation, and that question has a crisp answer only because there
is exactly one origin this run is permitted to touch and you are the one serving it. Section 4's
findings are counts over a trace, and a count is evidence only if the same run produces the same
trace tomorrow.

It matters as well that the fixture is small enough to read. `lab/site/status.html` is one file you
can open in an editor: a banner, a four-row table, a link, a footer. When the agent misreads the
page you can settle what was actually on it at a glance — which is exactly what you cannot do when
the page belongs to somebody else, is assembled by their framework, and has changed by the time you
go to look.

## The mechanism

The server is the standard library's, with one behaviour turned off and one shape chosen
deliberately. From `lab/_site.py`:

```python
@contextlib.contextmanager
def serving(port: int = PORT):
    """Run the dummy site on `port` for the duration of the block, then shut it down.

    A context manager rather than a fixture or a background process, because a browser test that
    leaves a server bound to a port is a test that fails the second time it is run.

    Yields:
        The base URL, e.g. `http://127.0.0.1:8771`.
    """
    handler = partial(_Quiet, directory=str(ROOT))
    server = http.server.ThreadingHTTPServer(("127.0.0.1", port), handler)
    thread = threading.Thread(target=server.serve_forever, daemon=True)
    thread.start()
    try:
        yield f"http://127.0.0.1:{port}"
    finally:
        server.shutdown()
        server.server_close()
```

**Line by line:**

- `@contextlib.contextmanager` is the design decision, not a convenience. A context manager is a
  thing you use with `with`, and its defining property is that the code after `yield` runs
  **whatever happens inside the block** — a passing check, a failed assertion, an exception out of
  Chromium, a `KeyboardInterrupt` on the keyboard. The two alternatives both leak: a helper that starts a server
  and returns needs every caller to remember to stop it, and a background process started in a
  second terminal is remembered by nobody.
- The docstring's second paragraph is the argument, and it is a statement about people rather than
  about sockets. A browser test that leaves a port bound passes the first time and fails the second,
  so whoever runs it twice concludes the test is flaky — and a test believed to be flaky is a test
  whose output nobody reads again. The cleanup is not tidiness. It is the thing that keeps the test
  worth having.
- `("127.0.0.1", port)` binds the **loopback** address rather than `0.0.0.0`. Loopback is reachable
  only from this machine; `0.0.0.0` would offer this page to everything else on the café wifi. One
  of the three reasons above is that the blast radius is a port on your own machine, and this
  tuple is the line where that is either true or not.
- `partial(_Quiet, directory=str(ROOT))` binds the directory into the handler class before the
  server instantiates it, because `SimpleHTTPRequestHandler` takes `directory` as a constructor
  argument and the server constructs its own handlers. `ROOT` is `lab/site/`, resolved from
  `__file__`, so the fixture serves the same two files no matter which directory you run from.
- `_Quiet` is the stdlib handler with `log_message` overridden to return immediately. Without it
  every request — including the browser's automatic hunt for a favicon — writes a line to standard
  error, and a four-line measured table disappears into the noise.
- `ThreadingHTTPServer` rather than the single-threaded `HTTPServer`, because a browser opens more
  than one connection to a page, and a server that handles requests strictly one at a time can sit
  waiting for a browser that is itself waiting for the server.
- `daemon=True` on the thread is a safety net rather than the mechanism: it means an abandoned
  server can never keep the process alive. The `finally` block is what actually stops it.
- `server.shutdown()` and then `server.server_close()`, in that order and both of them.
  `shutdown()` ends the `serve_forever` loop; `server_close()` closes the listening socket. Do only
  the first and the port is still held.

### The port, checked rather than repeated

`_site.py` claims two things about ports: that 8771 is this day's, and that Day 15's AcmeCloud API
stub owns 8765. Both are the sort of claim worth verifying instead of copying forward, so here is
what a search of `days/` on 2026-09-06 turned up.

Day 15's stub does own 8765 — `PORT = 8765` sits at the top of its service module, and the same
address runs through its parts as `http://127.0.0.1:8765`. Its lab README calls that service a
fictional vendor named AcmeCloud, which is also the name across the top of this day's fixture pages:
the same imaginary company, fifty-six days later, now with a status page instead of an API. The
digits `8765` do appear in three other days and not one of them is a port — a DOI ending, an
invented telephone number, and a spreadsheet example. `8771` appears nowhere under `days/` except
this day's own lab.

The claim holds. The reason it is worth a paragraph is not neatness: two days that bind the same
port cannot both be demonstrated in one sitting, and the failure does not look like a port
collision. It looks like one day's agent reading the other day's page.

Now watch the port's whole life, since a lifetime is what `serving()` manages:

```bash
cd days/day-71-computer-use-and-the-sandbox/lab
uv run python -c "
import urllib.error
import urllib.request

from _site import serving

with serving() as base:
    with urllib.request.urlopen(f'{base}/status.html') as page:
        print(f'  inside the block   HTTP {page.status}, {len(page.read())} bytes')
    with serving() as again:
        print(f'  bound a second time on the same port: {again}')

try:
    urllib.request.urlopen(f'{base}/status.html')
except urllib.error.URLError as error:
    print(f'  after the block    {type(error).__name__}: {error.reason}')
" 2>/dev/null
```

**Line by line:**

- `cd` into `lab/` first, because the snippet imports `_site` by its plain name the way every script
  in this day does. No lab file is edited to run this.
- `urllib.request` rather than a browser, because the question here is only *is something listening
  on that port*, and a full Chromium would answer it far more slowly and less clearly.
- The nested `with serving() as again:` is the deliberately awkward part: a second server, on the
  same port, while the first is still up.
- The `try` block sits **outside** the outer `with`, so it runs after the `finally` in `serving()`
  has shut the server down. `base` is still in scope — Python's `with` does not scope its variables
  — which is what makes the after-the-fact request possible to write.

Measured on 2026-09-06:

```text
  inside the block   HTTP 200, 1648 bytes
  bound a second time on the same port: http://127.0.0.1:8771
  after the block    URLError: [WinError 10061] No connection could be made because the target machine actively refused it
```

The first and third lines are `serving()` doing its job: the page is there inside the block, and the
port is genuinely refusing connections once the block ends. That is the property the whole day rests
on, because every script here opens and closes the fixture and several of them do it twice in one
process.

The middle line is the honest surprise, and it is the reason the docstring's promise is worth
reading carefully. **Binding 8771 a second time did not fail.** The stdlib's server sets the socket
option that permits address reuse, and on this platform that is enough for a second bind on a port
that is already serving. Nothing errored, nothing warned, and there were briefly two servers where
the code says one. So the docstring's *"a test that fails the second time it is run"* describes the
failure you get when the operating system does object — and when it does not object, you get
something worse, which is two servers and no message. Either way the conclusion is the same, and it
is the `finally` block: cleaning up is your job, not the platform's.

### What the agent sees

`lab/look.py` opens each page and prints exactly what `current_state()` hands back.

```bash
uv run python days/day-71-computer-use-and-the-sandbox/lab/look.py --both 2>/dev/null
```

**Line by line:**

- Run from the repo root. The script puts its own directory on the import path, so the plain-name
  import of `_site` finds the sibling module.
- `--both` adds `/history.html` to the list of pages, which is what makes the output a comparison
  rather than a single reading.
- `2>/dev/null` drops the one line ADK writes to standard error here — `UserWarning: [EXPERIMENTAL]
  feature FeatureName.COMPUTER_USE is enabled.` — leaving only the table. No model runs in this
  script, so there is nothing else on that stream.

Measured on 2026-09-06:

```text
viewport 1280x936

  page              screenshot bytes   url the model sees
  /status.html                 28165   http://127.0.0.1:8771/status.html
  /history.html                14323   http://127.0.0.1:8771/history.html

  what current_state() returns: screenshot (bytes), url (str)
  what it does not return: the DOM, the text, the headings, the table, the link targets
```

Two pages served, two screenshots, two URLs, and both requests went to a socket on this machine that
existed for the length of one `with` block. The whole fixture is 2 139 bytes of HTML on disk and it
produced 42 488 bytes of PNG for the model to look at, which is a ratio worth remembering when
[2.1](2.1-see-decide-act.md)'s point about the cost of every extra turn comes back in section 4.

## When it breaks

The fixture is a **hypothesis about the real page**, and it will be wrong in ways you cannot list in
advance, because if you could list them you would have put them in the fixture.

`status.html` fits in one viewport, so nothing ever needs scrolling — and
[2.2](2.2-the-coordinates-are-not-your-pixels.md) already said what that hides. It loads instantly
from the local disk, so an agent that clicks before the page is ready never learns that it does
that. It has no cookie banner sitting over the top-left corner of everything, no consent dialog, no
"you appear to be in another region" interstitial, no A/B test serving a different layout to every
third visitor, and no rate limiter that starts returning a holding page after the fourth request in
a row. A real status page has some subset of these on any given morning, and each of them takes an
action set of fifteen and quietly makes the first one useless.

So an agent that works perfectly here can fail on the real page, and the honest thing to notice is
that **more fixture does not fix it**. Every one of those failures you add is a failure you already
knew about, and it was the ones you did not think of that were going to bite. A more faithful
practice head is still a practice head.

The way you actually find out is a **canary run**: one deliberate, small, watched run against the
real thing, with a person reading the trace as it happens and a hand on the stop. The name comes
from releasing a change to a tiny slice of traffic before everybody gets it. Here it means one
ticket, one page, one human, and the trace read line by line afterwards — not because the run is
expected to fail, but because it is the owner standing behind the chair, and there is no other way
to find the scar nobody mentioned.

The reason the fixture still earns its place is what the canary run costs. Every rule that was going
to be wrong for a stupid reason — a threshold in the wrong coordinate space, a check that never
fires, a refusal that does not log — has already been found here, for free, with nobody watching. A
canary run should be spending its attention on the surprises, and the fixture's job is to make sure
they are the only thing left.

## In production

**Real teams record real pages as fixtures, and that is where the privacy question walks in.** The
usual next step after a hand-written fixture is to capture the actual page — save the HTML, or a
screenshot, or a full request-and-response recording — and replay it. It is a good technique and it
answers the fidelity problem honestly. It also means the recording is now a file in your repository,
and a status page's incident text can carry a customer name, an internal hostname, an engineer's
handle in a comment. A screenshot of an authenticated page is worse, because it captures whatever
was in the header: the logged-in account, an email address, a session banner.

That file is exactly the thing
[Day 69's 2.3](../../../day-69-pii-and-data-boundaries/parts/02-where-the-copies-are/2.3-the-copy-nobody-calls-a-copy.md)
is about — a copy nobody calls a copy. Nobody thinks of `tests/fixtures/status-2026-09-06.png` as
personal data, and every argument in that part applies to it unchanged: it is a copy, it is in your
backups, it is in the clone on someone's laptop, and a deletion request against your database will
not touch it. The rule that follows is short. A recorded fixture is reviewed and redacted before it
is committed, exactly like any other data you took from somewhere else, and the day the review is
too much work is the day the fixture should have been written by hand instead — which is
[Day 69's 4.1](../../../day-69-pii-and-data-boundaries/parts/04-invented-on-purpose/4.1-why-invent-the-customers.md)'s
argument arriving from a different direction.

**What degrades as the fixture set grows** is trust in it. One hand-written page stays accurate
because it is small and somebody reads it. Forty recorded pages drift: the vendor redesigns, the
recordings do not, and the suite stays green against a version of the web that no longer exists. The
failure is silent and it is the expensive kind, because the suite is not merely useless at that
point — it is actively reassuring. Teams that survive this put a date on every recording, re-record
on a schedule they actually keep, and run one canary against the live page often enough that the
drift shows up as a failure rather than as a surprise.

**The failure mode that only appears with real traffic** is that the real page is not a page, it is
a distribution. Your recording is one draw from it: one region, one account tier, one time of day,
one experiment bucket. An agent tuned to that draw looks excellent in the suite and is worse than
random against the tail. This is why the canary is a permanent fixture of the system rather than a
launch step.

**The review comment a senior engineer leaves:** *"Good that this is local and good that the server
is a context manager — but the port is a bare literal in three files, so put it in one place and let
an environment variable override it, because the first thing that happens in CI is two jobs on one
machine. Before we start recording real pages into `tests/fixtures/`, I want a written rule about
redaction and a date stamp on each recording. And add a canary target that runs one ticket against
the live status page on demand, with the trace printed and no writes anywhere: I don't want the
first real page this agent ever sees to be in production."*

**The interview question:** *"Why is your browser agent tested against a page you wrote yourself,
and what does that cost you?"* An answer that has done both: *"Three reasons, and only one of them
is about testing. It cannot change under me, so my numbers are measurements rather than anecdotes.
Driving somebody else's site at any volume is scraping from their side of the connection, and I was
deliberately making the agent misbehave — trying off-origin navigations and typing fake credentials
— which is not a thing to rehearse on a stranger's server. And the sandbox needed a boundary I
owned, because 'the agent left the origin' has to be checkable and it isn't if the origin is the
open web. What it costs me is fidelity: my fixture has no cookie banner, no consent dialog, no A/B test, no
slow load and nothing that scrolls, and every one of those breaks a coordinate-based action set. The
answer is not a bigger fixture, because I can only add failures I already thought of. It's a canary
run — one watched run against the real page with someone reading the trace — and the fixture's job
is to make sure that run is spending its attention on the surprises rather than on my typos."*
