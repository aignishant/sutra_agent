# 4.2 — Isolation you can buy

## One-line answer

The door in section 3 decides **what the agent is allowed to ask for**, and that is a different thing
from **containing what the browser then does** — the second one is not a better rule, it is a wall the
running process cannot reach around, and it is bought at a layer underneath your code rather than
written into it.

## The story

A friend brings her one-year-old to your house for the afternoon. There is a staircase in the hall
with fourteen steps and no carpet on them.

You do the sensible thing, which is to say something. *"Don't let him near the stairs."* Everybody
agrees. Everybody means it. For an hour and a half it works, because three adults are watching a
child in a small room, and that is genuinely enough.

Then the kettle boils, somebody's phone rings, and the conversation moves to the kitchen. When you
come back through, he is on the fourth step, on his hands and knees, delighted with himself.

Nothing happened. You picked him up. But look at what the rule needed in order to work: it needed
each of you to have heard it, to still be holding it, and to be facing the right way at the moment it
mattered. Three conditions, every second, for the whole afternoon.

Now think about the thing people actually fit at the bottom of the stairs. A gate, screwed into the
two walls, with a latch a small hand cannot work.

It is a different kind of thing from the sentence, and it is worth being exact about how. The
sentence travelled through the adults. The gate does not travel through anybody. It does not need
attention, cannot be forgotten while the kettle boils, and is not less effective when everyone is
looking away. The child can push it, argue with it in his own fashion, and be extremely determined
about it, and the gate is a gate.

And here is the part that decides this whole document: **you cannot get the gate by saying the
sentence better.** It is metal, screws and two holes drilled into your wall. You either have one
fitted or you do not, and if you want one you go and buy it from somebody who makes them.

## The idea in plain language

Two words do most of the work in this part, and they are used interchangeably in conversation and mean
different things.

A **policy** is a rule about what may be requested. It sits in the path of a request, reads it, and
either passes it on or refuses it. The `Sandbox` plugin from section 3 is a policy: an action name and
a dictionary of arguments arrive, it forms a verdict, and it returns a refusal or `None`.

An **isolation boundary** is a wall that the running code cannot get past regardless of what it
requests. It is not in the request path. It does not read anything, form an opinion, or return a
verdict. It is a property of the place the code is running, enforced by something the code is not a
part of — the operating system kernel, the container runtime, the network stack, the browser's own
process model.

The difference that matters is **who has to be right**. A policy has to be right about every request:
Part [4.1](4.1-the-action-nobody-enumerated.md) is one long demonstration of what happens when it is
right about two of fifteen names. An isolation boundary does not have to be right about anything,
because it is not making decisions. It just is where it is.

There is a third word people reach for and it is the one that causes the trouble. **"Sandbox"** gets
used for both. This lab calls its plugin `Sandbox`; ADK's own documentation uses the word for
hermetic execution environments; a browser vendor uses it for a process with its system calls
restricted. The class in `door.py` is a policy with a sandbox-shaped name, and the honest sentence
about it is:

> The door constrains what the agent may **ask for**. It does not contain what the browser **does**.

That is not a criticism of the door. A policy is a good and necessary thing, it is cheap, it produces
the refusal record part 3.4 is about, and on this particular surface — where one origin check bounds
most of the actions — it earns its place. It is simply not the same object as a wall, and a system
that has only the first has one of the two.

Once you separate them, the layering falls out, and it is the layering that a design review is
actually about:

| Layer | What it is | What the agent can do about it |
| --- | --- | --- |
| The door (section 3) | a policy in your process | be asked for something the policy has no rule for |
| ADK's `navigate` guard ([3.2](../03-the-door/3.2-the-guard-adk-already-shipped.md)) | a policy in the framework's process | nothing, but it only covers `navigate` |
| The browser's own process sandbox | isolation, enforced by the operating system | nothing |
| A container | isolation, enforced by the kernel | nothing |
| A network namespace with no route out | isolation, enforced by the network stack | nothing |

Rows three to five are the subject of the rest of this part, and none of them are things you write.

## Why Sutra needs it

Because the build brief asks for `sutra/browser_sandbox.py`, and a module with that name is going to
be read by somebody as *the* sandbox. It is not. It is one row of the table above, and the module
docstring has to say which row, in the same way part
[4.1](4.1-the-action-nobody-enumerated.md) demands that the allow-by-default be stated rather than
implied.

It also fixes what Sutra can honestly claim later. Day 66's threat model has a column for the
mitigation attached to each row. A row that says *mitigated by the browser sandbox* means something
very different from a row that says *mitigated by a plugin that checks the navigate origin*, and the
second one is what this day built. Writing the first while shipping the second is exactly the
conflation Day 67 part
[6.3](../../../day-67-guardrail-callbacks/parts/06-in-production/6.3-the-drop-safe-not-another-supervisor.md)
called out: a system that raises the cost of an attack and a system that bounds its impact are two
different claims, and only one of them is a boundary.

And it is where the day meets Addendum 02 head on. The two isolation products ADK ships an
integration for both require an account, so this curriculum cannot build on them — and the interesting
part is that saying so *precisely* is more useful than a build would have been.

## The mechanism

There is nothing to run in this part, and that is the correct shape for a topic that is deliberately
not built. What there is instead is a survey with the verification attached, split into what costs
money and what does not.

### 🅿️ Parked — awareness-level, deliberately not built: hosted sandboxes

Two names come up whenever agent isolation is discussed, and both connect to ADK.

**Daytona.** There is a documentation page for it — <https://adk.dev/integrations/daytona/>, fetched
on 2026-09-06, titled *"Daytona plugin for ADK"*. It describes a plugin that lets an agent "execute
code, run shell commands, and manage files in isolated environments, enabling secure execution of
AI-generated code", and it exposes five tools: code execution, command execution, file upload, file
reading, and long-running commands. Its prerequisites list, verbatim, is **a Daytona account** and a
**Daytona API key**, supplied either to the constructor or through the `DAYTONA_API_KEY` environment
variable.

**e2b.** Here the honest report is more interesting than the expected one, and it is worth separating
two questions that get answered as if they were one. *Is there an adk.dev integration page?* No.
`https://adk.dev/integrations/e2b/` returned **HTTP 404** on 2026-09-06, and e2b does not appear on
the integrations index at <https://adk.dev/integrations/> — which lists Daytona, Code Execution, GKE
Code Executor, Environment Toolset and around a hundred others. *Does ADK ship an e2b integration?*
Yes. `google.adk.integrations.e2b.E2BEnvironment` is in the installed `google-adk==2.7.1` package. Its
class docstring calls it "a persistent remote workspace backed by an E2B sandbox", it is decorated
`@experimental`, it needs the extra `pip install google-adk[e2b]`, and its `api_key` argument
documents itself as: *"E2B API key. If `None`, the `E2B_API_KEY` environment variable is used."* The
class docstring also mentions a bounded time-to-live "to cap credit usage", which tells you what kind
of thing is on the other end.

So: one of the two is documented on adk.dev and one is only in the package, and **both require an
account**.

That is where Addendum 02 ends the discussion, and it ends it as a rule rather than as a preference.
The addendum opens with the constraint in one line — *"no paid API keys, no billing accounts, no
subscriptions"* — and its non-negotiable list says: *"Never write code that requires a billing
account, paid model, or paid API."* An API key that is tied to an account with credits is exactly that,
whatever the free allowance happens to be this month. The addendum wins over the plan on paid services
by the precedence rule in `CLAUDE.md`, so this is not a judgement call.

It is also not a new situation. Addendum 02 §5 already did this for the deploy days: Cloud Run becomes
the same container run locally, Agent Engine becomes a documented walkthrough with the config files
written rather than executed, and GKE becomes a real Kubernetes cluster on a laptop. The pattern is
**park the product, build the property**, and the property here is isolation, which is available for
nothing.

### The free layers, which are real

Four of them, in increasing order of how much they contain.

**The browser's own sandbox.** This one you already have and did not ask for. Chromium runs each
renderer — the thing that parses HTML and runs JavaScript from a page — in a separate operating-system
process with its access to the machine cut down by the kernel, so a page that finds a bug in the
renderer still has to find a second bug to get out of the process. `SiteComputer.initialize()` launches
real Chromium through Playwright, which means every page the agent visits is already inside that. It
is worth knowing about mostly so you do not double-count it: it protects the machine from **the
page**, and it does nothing about the agent, because the agent is the one driving.

**A separate browser profile.** A browser profile is the folder holding cookies, saved logins, history
and extensions. Launching the agent's browser with a profile of its own — which is what Playwright does
by default, and why the lab's Chromium starts logged in to nothing — means an agent talked into
visiting a site cannot arrive there **as you**. This is the cheapest isolation in the list and the one
most often skipped, because attaching the agent to your existing browser is so convenient. Day 68's
whole argument applies: the session cookie is ambient authority, and a deputy holding it acts with it.

**A container.** Run the browser and the agent inside a container and the boundary is the kernel's,
not your code's. What it contains is the filesystem — a `file:///` URL, a download, a crash dump — and
the process table. What it does **not** contain, by default, is the network: a container with default
networking can reach your private subnet perfectly well, which is precisely the class of target part
[3.2](../03-the-door/3.2-the-guard-adk-already-shipped.md)'s `navigate` guard exists for.

**A network namespace with no route out.** This is the strong one, and it is the one ADK's own safety
guidance asks for. From <https://adk.dev/safety/>, fetched on 2026-09-06:

> "We recommend creating execution environments that are hermetic: no network connections and API
> calls permitted to avoid uncontrolled data exfiltration; and full cleanup of data across execution
> to not create cross-user exfiltration concerns."

and, on the page's reason for saying so:

> "Code execution is a special tool that has extra security implications: sandboxing must be used to
> prevent model-generated code to compromise the local environment, potentially creating security
> issues."

Read the first quote against this day. *No network connections* would close every exfiltration channel
at once, including the ones part 4.1 could not enumerate — and it would also make a browser agent
useless, because a browser with no network has nothing to look at. The honest translation for computer
use is not *no network* but *one network*: a namespace whose only route is to the origin the agent is
meant to be working in, so that the isolation layer enforces the same sentence the door's `navigate`
rule enforces, and enforces it for the actions the door never heard of.

That is the shape worth carrying out of this part. The door and the namespace are **the same rule
stated twice**, once as a policy that can be incomplete and once as a wall that cannot. Neither
replaces the other: the wall has no vocabulary and cannot tell you *why* something was refused, and
the policy has the reason and the record and part 3.4's whole subject. Two layers, which is the design
the paper at the end of this day is about.

### What the door would need to become

There is one change the door needs before it can be the policy half of that pair, and it is small
enough to write out. Today:

```python
    def __init__(self, origin: str, trace: Trace) -> None:
        super().__init__(name="sandbox")
        self.origin = origin
        self.trace = trace
        self.refusals: list[str] = []
```

**Line by line:**

- `origin: str` — **one** origin, singular, and the whole rule is a comparison against it. That is
  correct for this lab, which serves one fixture, and it is the assumption that fails the first time a
  real task needs two hosts: the site and its login page, the site and its CDN, the ticket system and
  the status page.
- `self.origin = origin` stores the string. `_verdict` then re-parses it with `urlparse` on **every**
  call, which is fine at this size and is the second thing the change below tidies.
- `self.refusals` is the record, and it is on the plugin rather than in a global, so two sandboxes in
  one process cannot mix their evidence.

The version the build brief wants is one line different:

```python
    def __init__(self, origins: tuple[str, ...], trace: Trace) -> None:
        super().__init__(name="sandbox")
        self.hosts = frozenset(urlparse(o).netloc for o in origins)
        self.trace = trace
        self.refusals: list[str] = []
```

**Line by line:**

- `origins: tuple[str, ...]` takes a **list of permitted origins** instead of one. That is the change
  in a sentence, and everything else follows from it.
- `frozenset(...)` turns the list into a set of hosts, so `_verdict`'s comparison becomes
  `host not in self.hosts` — a membership test rather than a string equality. A set rather than a list
  because the question asked of it is only ever *is this one of them*, and `frozenset` rather than
  `set` because nothing should be adding an origin to a live sandbox.
- `urlparse(o).netloc` is computed **once per origin at construction** instead of once per action.
  That is not a performance argument at this size; it is that the parsing rule now lives in one place,
  so an origin written with a trailing slash and one without cannot behave differently depending on
  which call site built them.
- Note what did **not** change: the plugin is still a `BasePlugin`, the hook is still
  `before_tool_callback`, the refusal is still a truthy dict, and the default in `_verdict` is still
  allow. This change makes the rule **data** — which is the fifth check in `lab/gate.py`, the one that
  wants `ALLOWED_ORIGINS` to be a list, tuple or set rather than a chain of `if` statements — and it
  does nothing at all about part 4.1's gap. Widening a rule and closing a gap are different edits, and
  a review that accepts the first as the second is the one this section exists to prevent.

The gate asks for the allowlist as a module-level name precisely so that it can be printed, diffed and
reviewed. An origin rule spelled as branches is a rule only a reader of that function knows about; an
origin rule spelled as a tuple is a rule that shows up in a pull request diff with no effort from
anybody.

## When it breaks

**The parked route breaks at the door, before anything interesting happens.** Reach for the hosted
sandbox anyway and this is what a zero-budget machine gets:

```bash
uv run python -c "
import asyncio
from google.adk.integrations.e2b import E2BEnvironment

try:
    asyncio.run(E2BEnvironment().initialize())
except ImportError as error:
    print(f'{type(error).__name__}: {error}')
"
```

Measured on 2026-09-06:

```text
ImportError: The e2b package is required to use E2BEnvironment. Install it with `pip install google-adk[e2b]`.
```

That is the *first* wall, and it is the cheap one — a missing optional dependency, fixable with an
install. The second wall is the one this part is about and it has no error message worth quoting,
because it is not a bug: install the extra and the class asks for `E2B_API_KEY`, and an API key means
an account, and an account is what Addendum 02 forbids. Notice that the failure arrives in the wrong
order for learning. The dependency error is loud and looks like the problem; the account requirement is
quiet and is the problem.

**The conceptual failure is worse, and it has no error at all.** A team runs the agent in a container,
writes *"the browser agent is sandboxed"* in the design document, and stops. The container contains the
filesystem. The exfiltration channel Day 66 enumerated is an HTTP request, and the container's network
is up, so the sentence in the document is true about disks and false about the thing anybody was
worried about. The word "sandboxed" absorbed the difference.

**And the opposite failure, which this part must not cause.** A reader concludes that a policy is
worthless because it is not a wall, deletes the door, and ships the container alone. Now every refusal
is a connection reset with no reason attached, nothing is logged, part 3.4's record does not exist, and
the first incident review has a trace of what the browser did and no trace of what was asked for. The
wall does not know **why**. That is the standing division of labour: the policy carries the reason and
the evidence, the wall carries the guarantee.

**The failure mode of the wall itself.** An isolation boundary is only as good as its configuration,
and its configuration is not code, so it does not get reviewed like code. A container built from a
Dockerfile in the repository is reviewable. A container run by hand with an extra `--network host`
because somebody was debugging is not, and the flag survives into the run that matters. The property
you want is that **the isolation is expressed in a file the pull request shows you**, which is the same
demand part 4.1 made of the action list and Day 68 made of the permission table.

## In production

**What a real system layers, and in which order.** The order is not a preference; it follows from which
layer can be incomplete. Isolation first, because it is the one that holds when the policy is wrong.
Policy second, because it is the one that can say why. Logging across both, because an incident review
needs the refusals and the escapes in one place.

| Layer | Bought or written | Contains | Costs |
| --- | --- | --- | --- |
| Its own container | written, in a Dockerfile | filesystem, process table | build time, an image to keep patched |
| A network namespace routing only to the target origin | written, in the run configuration | the exfiltration channel | real work, and it breaks whenever a legitimate second host appears |
| A throwaway browser profile per run | written, one Playwright argument | your identity | almost nothing |
| A hosted sandbox (Daytona, e2b) | bought | all of the above, managed | an account, a key, a bill |
| The door | written, in your code | nothing — it decides | one plugin, and part 4.1's gap |

The last row's "contains nothing" is the sentence to carry into a review, and it is not an insult. The
door decides. Deciding is valuable and it is not containment.

**What degrades at scale.** Not the wall — a kernel boundary is the same boundary on the ten thousandth
run. What degrades is the number of exceptions carved into it. A namespace with one permitted origin is
clean on the day it is written and has eleven origins in it two years later, each added by a person
solving a real problem, none of them wrong on its own. The thing that decays is not the mechanism, it is
the **allowlist inside it**, which is why the tuple in `__init__` above matters more than it looks: a
list that appears in a diff decays visibly, and a firewall rule somebody typed into a console once does
not.

**The cost that is not money.** Hermetic is expensive in a way ADK's safety page does not spell out. An
agent with no network cannot resolve a hostname, cannot load an image, and cannot fetch the CSS that
makes the page it is meant to be reading look like a page. The moment the isolation is real, ordinary
tasks start failing for reasons that have nothing to do with the agent's reasoning, and the debugging
loop gets one layer longer. Teams that adopt strict isolation and then quietly widen it under delivery
pressure end up in the worst position of the three: the cost paid, the guarantee gone, and the design
document still saying *hermetic*.

**The review comment a senior engineer leaves:** *"Rename it or document it. `browser_sandbox.py` is a
policy — it decides what the agent may ask for, and part 4.1 already showed the default is allow. That
is fine, but the threat-model row currently reads as though we have containment, and we do not. What I
want before this ships: the browser gets its own throwaway profile, which is one Playwright argument and
stops an injected agent acting as us; the container's network policy goes in the repository rather than
in somebody's run command; and the allowed origins become a module-level tuple so I can see them change
in a diff. Daytona and e2b are both fine products and both need an account, so they are out under
Addendum 02 — put that in the docstring with the date, so nobody re-opens it in six months."*

**The interview question:** *"Your agent drives a browser. Is it sandboxed?"* An honest answer: *"Two
things go by that name and I'd separate them. We have a policy — an ADK plugin outside every tool that
checks the navigate origin and refuses off-origin requests, with the reason recorded. It is in the same
process as the browser, its default for an unrecognised action is allow, and it covers two of fifteen
declared actions explicitly. So it constrains what the agent asks for and it does not contain what the
browser does. The containment is a separate layer we buy or configure: the browser's own renderer
sandbox we get for free, a throwaway profile so the agent isn't logged in as anybody, a container for
the filesystem, and a network namespace if we want to close exfiltration properly. The hosted options —
Daytona has an ADK plugin, e2b ships as an integration in the package — both need an account and a key,
which our constraints ruled out, so we did the free layers and wrote down exactly what we skipped. The
sentence I'd want on the record is that the policy tells you why something was refused and the isolation
tells you it could not have happened, and a design needs both because neither does the other's job."*
