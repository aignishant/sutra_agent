# 4.1 — The action nobody enumerated

## One-line answer

A rule that switches on **action names** is only ever as complete as the list of action names, and
that list belongs to the framework rather than to you — so the door does not merely have gaps today,
it acquires new ones on a day you did not write any code.

## The story

Inside a cupboard door at home there is a laminated card with the washing symbols on it. A tub, a
triangle, a square, an iron, a circle, and next to each one a line saying what it means.

You did not make it. It came with the machine, years ago, and it has been right about every label
you have ever held up against it. Forty degrees, do not tumble dry, warm iron. You have used it a
hundred times without thinking, which is the correct thing to do with a reference that works.

Then a jumper comes home from a shop with a symbol on its label that is not on the card.

You look. You look again, along the row and then down the column, and it is genuinely not there. And
here is the whole of this part in one sentence: **not finding it does not read as "I don't know".**
It reads as "nothing special". So the jumper goes in with the rest, on the setting you always use,
and it comes out of the drum the size of something a child would wear.

Nobody was careless. The card was correct about every symbol printed on it and it stayed correct.
The card just did not grow, and the people who print the labels never agreed to stop adding to them.
It was never your list.

## The idea in plain language

Part [3.1](../03-the-door/3.1-the-check-outside-every-tool.md) built the door and named its shape
honestly: `_verdict` ends in `return ""`, the empty string means *allowed*, and so two of the fifteen
declared actions are checked and thirteen are waved through. It also said where the argument
continues — *"this is not fixed here"* — and this is where it continues.

The part that is left is not the count. It is the **tense**.

Thirteen unguarded actions is a fact about today, and today's fact is fixable: you could sit down
this afternoon, take the fifteen names part
[1.3](../01-no-api/1.3-fifteen-doors-one-used.md) read off the real request, write a rule for each
one, and go home with a door that has an opinion about every action in the framework. That would be
good work and it would be complete.

It would stay complete until the next `uv sync`.

The reason is the sentence 1.3 established and this part collects on: **you did not write the action
list.** `ComputerUseToolset` generates the tools from `BaseComputer`, so the set of names your door
must have an opinion about is a set somebody else maintains, in a package you upgrade, in a release
whose notes you may not read. A new action lands, the toolset declares it, the model can call it, and
your carefully complete list of fifteen is a carefully complete list of fifteen.

Two words, because the rest of the part uses them and they are used loosely everywhere else. An
**allowlist** is a rule written as the set of things that are permitted, with everything else
refused. A **blocklist** is the set of things that are forbidden, with everything else permitted. A
function that names two actions and returns `""` for the rest is a blocklist of length two, whatever
the class it lives in is called. Day 68's
[3.1](../../../day-68-least-privilege-tools/parts/03-absent-not-forbidden/3.1-deny-by-default-at-the-toolset.md)
argued the choice between them for tools; what a browser adds is that the enumeration is not a fixed
job you can finish, because the thing being enumerated is maintained by somebody else.

Which is why the interesting question in this part is not *what is missing* but a narrower and more
useful pair:

1. Which of the thirteen unguarded actions are **actually** dangerous, given that `navigate` is
   checked?
2. What is the ritual that tells you when the answer to (1) has changed?

## Why Sutra needs it

Because the build brief asks for `sutra/browser_sandbox.py` and `docs/PACKAGES.md` in the same day,
and this part is the line between them.

Sutra pins exact versions with `==` and records each pin in `docs/PACKAGES.md` with the date it was
verified — Principle 7, applied all the way down. For most packages the version number is the whole
fact: pin `ruff==x.y.z` and you know what you have. For a package that **generates your attack
surface**, the version number is half the fact. The other half is the list of actions that version
declared, because that list is what the sandbox was written against and it is what an upgrade can
change without touching a line you wrote.

Part [1.3](../01-no-api/1.3-fifteen-doors-one-used.md) already asked for the test that catches this —
read the declared names off a real request, compare to a list in the repository, fail on a
disagreement. This part is the other half of that: what the test is compared **against**, when it
runs, and what a human is supposed to do on the morning it goes red.

## The mechanism

Start by driving the failure rather than describing it. The door's decision function is pure — a name
and a dictionary in, a string out — so you can ask it about any action you like without a browser,
a model or a run:

```bash
cd days/day-71-computer-use-and-the-sandbox/lab
uv run python -c "
from door import Sandbox
from _computer import Trace

door = Sandbox('http://127.0.0.1:8771', Trace())
for name in ('navigate', 'type_text_at', 'drag_and_drop', 'key_combination', 'search', 'upload_file'):
    print(name.ljust(16), door._verdict(name, {}) or 'ALLOWED')
"
```

**Line by line:**

- `cd` first: `door.py` imports its siblings (`_computer`, `_fake`, `_site`) by plain name, so from
  the repository root the import fails with `ModuleNotFoundError: No module named '_computer'`.
- `Sandbox('http://127.0.0.1:8771', Trace())` builds the door with **no browser behind it**. Part
  [3.1](../03-the-door/3.1-the-check-outside-every-tool.md) measured the door by running the whole
  five-action script through a real Chromium; here the question is smaller and does not need one.
- `door._verdict(name, {})` passes **empty arguments** on purpose. The question is not "would this
  particular URL pass" — it is "does the door have an opinion about this action at all", and empty
  arguments are the cleanest way to ask it.
- The six names each make one point. `navigate` and `type_text_at` are the two the door knows.
  `drag_and_drop`, `key_combination` and `search` are real actions ADK declares today that the door
  has never heard of. And `upload_file` is **not an ADK action at all** — it stands in for the one
  that gets added next.
- `or 'ALLOWED'` turns the protocol into something readable. An empty string prints as nothing, and a
  column of blank lines is exactly the output a reader skims past.

Measured on 2026-09-06:

```text
navigate         navigate off-origin: '' is not 127.0.0.1:8771
type_text_at     ALLOWED
drag_and_drop    ALLOWED
key_combination  ALLOWED
search           ALLOWED
upload_file      ALLOWED
```

Read the last line first, because it is the one that is not about today. `upload_file` does not
exist. There is no such method on `BaseComputer` in the version this lab pins, no tool of that name
was ever declared to any model, and nothing in ADK has ever heard of it. The door was asked about a
thing that has never existed and answered **allowed**, instantly, with no warning and no log line.

That is the laminated card, and `upload_file` is the symbol that is not on it. The door will answer
the same way about whatever real action ADK adds next, on the morning it is added, before anybody has
read the release notes.

Here is the line that produces that answer, the last three of `_verdict` in `lab/door.py`
(part [3.1](../03-the-door/3.1-the-check-outside-every-tool.md) walks the whole function):

```python
            if SECRET in text or text.startswith("sk-"):
                return "type_text_at carries something shaped like a credential"
            return ""
        return ""
```

**Line by line:**

- The first `return ""` is **inside** the `type_text_at` branch: the door looked at this action,
  applied its rule, and concluded the text was fine. That empty string is a decision.
- The second `return ""` is at the **function's** indentation, after the last `if`. It is reached by
  every action name the function did not mention, and it is indistinguishable from the first one to
  the caller. Both are the empty string; `before_tool_callback` sees no difference.
- **Those two lines mean opposite things and are spelled identically.** One says *checked and clear*,
  the other says *not on the card*. Everything in this part follows from the fact that the type `str`
  cannot tell them apart, and neither can the code above them.
- The smallest honest change is not a fourteenth branch. It is to make the two answers different
  things — a value for *allowed*, a different value for *no rule* — so that the second one can be
  counted, logged, and eventually refused. A door that can say *I have no rule for this* has become a
  door somebody can fix.

### Now the fair half

An alarmed reading of that output would be wrong, and getting the argument right matters more than
getting a scare out of it. The thirteen unguarded actions are not thirteen equal holes.

**The origin check on `navigate` bounds most of them.** A click, a hover, a scroll, a drag, a key
combination and a wait all act on **the page the browser is currently on**, and the browser can only
be on a page the origin check permitted. So an action the door never enumerated is, in the ordinary
case, an action taking place inside a boundary that was already decided. That is not luck. It is why
`navigate` is the rule worth having, and `door.py`'s own module docstring says so: *everything else an
agent can do to a page it is allowed to be on is bounded by that page.*

That argument is sound, and it has exactly two holes.

**`search` is the first**, and part [1.3](../01-no-api/1.3-fifteen-doors-one-used.md) met it from the
other direction. It is a declared action whose entire purpose is to leave: there is no "search inside
the origin you were given", a search action means a search engine, and a search engine is somewhere
else by definition. The lab's `SiteComputer.search` refuses it. Notice **where** that refusal lives —
inside the computer, which is one implementation of one interface, and not in the door, which is the
thing you would point at in a review and call the sandbox. Swap in a different `BaseComputer` and the
door still says `ALLOWED`.

**Anything that could open a new context is the second.** The origin argument depends on there being
one page whose address was already vetted. Any action that produces a *second* place to be — a new
tab, a new window, a download opening in a viewer, a link target that escapes the page — breaks the
chain, because the new place never went through `navigate` and therefore never went through the
check. Nothing on today's list of fifteen does that, and *"nothing on today's list"* is a sentence
with a date in it.

| The door's coverage | Which of the fifteen | Why |
| --- | --- | --- |
| Decided explicitly | `navigate`, `type_text_at` | a rule names them |
| Bounded by the origin check | `click_at`, `hover_at`, `scroll_at`, `scroll_document`, `key_combination`, `drag_and_drop`, `wait`, `go_back`, `go_forward`, `current_state` | they act on a page `navigate` already vetted |
| Not covered | `search` | it leaves the origin and takes no argument a rule could read |
| Not covered and not seen | `initialize`, `open_web_browser` | they choose a starting page, and the door is never asked about the first one |

That last row is worth a second look, because it is not a gap in the list — it is a gap in *when the
door runs*. The door is a `before_tool_callback`, so it sees actions the **model** asks for.
Chromium's first page is opened by `SiteComputer.initialize()`, which the toolset calls before any
model turn happens at all. The door has no opinion about where the sandbox starts, because by the
time it could have one, the browser is already there.

So the honest summary is narrower than either "the door covers it" or "the door is theatre": one
action out of fifteen is genuinely unguarded today, ten are bounded by a rule that is checked, two
are decided, and two happen where the door cannot see. What makes that a *production* problem rather
than a satisfying answer is the row that is not in the table — the sixteenth action, whenever it
arrives, which lands in the "not covered" row by default and tells nobody.

## When it breaks

**The silent version, which is the one this part is about.** You upgrade `google-adk`. A new action
appears on `BaseComputer`, the toolset declares it, the model calls it, `_verdict` returns `""`. Your
test suite is green, because your tests assert that off-origin navigation is refused and that the
secret is not typed, and both are still true. The refusal count in the trace is unchanged. Nothing is
logged, because the door only writes a line when it refuses. The first sign is an incident.

**The loud version, for contrast.** Get a name wrong at the *plugin* level rather than at the verdict
level and the failure is immediate. Call the door's hook the way a runtime with a different
convention would:

```bash
cd days/day-71-computer-use-and-the-sandbox/lab
uv run python -c "
import asyncio
from door import Sandbox
from _computer import Trace

s = Sandbox('http://127.0.0.1:8771', Trace())
asyncio.run(s.before_tool_callback(tool=None, args={}, tool_context=None))
"
```

Measured on 2026-09-06:

```traceback
Traceback (most recent call last):
  File "<string>", line 6, in <module>
TypeError: Sandbox.before_tool_callback() got an unexpected keyword argument 'args'
```

That is Day 67 part
[2.4](../../../day-67-guardrail-callbacks/parts/02-where-a-check-stands/2.4-the-guardrail-that-never-ran.md)'s
failure — the runtime calls callbacks by keyword, so a parameter named `args` where the runtime sends
`tool_args` raises on the very first tool call. Put the two side by side. A misnamed **parameter**
fails instantly, in a way one test catches forever. A missing **branch** never fails at all. The
framework can protect you from the first and cannot protect you from the second, and that asymmetry
is the reason this part is in the production section rather than in section 3.

**The version that looks like a fix and is not.** Somebody reads this part, adds a rule for
`drag_and_drop` and `key_combination`, and closes the ticket. Next release adds an action, and the
door is exactly as complete as it was before — one symbol behind the label printers, permanently.
Enumerating harder is the fix that never finishes. Part
[3.1](../03-the-door/3.1-the-check-outside-every-tool.md) already named the alternative — invert the
default so an unrecognised action is refused — and the paper this day ends with is the same move
argued from first principles: you do not chase the list, you decide before execution from a rule set
small enough to read, and anything that does not fit does not run.

## In production

**Pin the framework, and treat the declared surface as part of the pin.** A `PACKAGES.md` row for
`google-adk` records a version and a date. For this package that is not enough information to
reproduce a security decision, because the sandbox was written against a *list*, and the list is a
property of the version that nothing in the row mentions. So the surface gets read off the framework
and written down beside the pin:

```bash
cd days/day-71-computer-use-and-the-sandbox/lab
uv run python -c "
from google.adk.tools.computer_use.base_computer import BaseComputer
from google.adk.tools.computer_use.computer_use_toolset import EXCLUDED_METHODS

declared = sorted(n for n in dir(BaseComputer) if not n.startswith('_') and n not in EXCLUDED_METHODS)
print(len(declared), 'declared:', ' '.join(declared))
"
```

**Line by line:**

- `dir(BaseComputer)` is what `ComputerUseToolset` itself loops over when it builds the tool list, so
  reading it here gives the same answer the runtime will give a model rather than a second list that
  has to be kept in step by hand.
- `EXCLUDED_METHODS` is ADK's own constant — `{"screen_size", "environment", "close", "prepare"}` —
  and importing it rather than retyping those four names is the difference between a check that stays
  correct across an upgrade and one that silently drifts. Retyping them would be this part's own bug,
  committed inside the tool meant to catch it.
- `not n.startswith("_")` drops the private helpers; only public methods become tools.
- The output is deliberately **one line**, so it can be pasted into a ledger row or compared with the
  previous release using `diff` and no ceremony. Part
  [1.3](../01-no-api/1.3-fifteen-doors-one-used.md)'s version of this reads the names off a live
  `LlmRequest`, which is the stronger evidence; this one needs no browser and no run, which is what
  makes it something you can put in an upgrade checklist.

Measured on 2026-09-06, against `google-adk==2.7.1`:

```text
15 declared: click_at current_state drag_and_drop go_back go_forward hover_at initialize key_combination navigate open_web_browser scroll_at scroll_document search type_text_at wait
```

Fifteen, and the same fifteen part 1.3 read off the real request. Two independent measurements
agreeing — one asking the runtime what it declared to a model, one asking the class what it holds —
is worth more than either alone, and the second one is the cheap one to run on every upgrade.

**What the ritual actually is.** Three small things, and the third is the one people leave out. A file
in the repository holding the sorted names. A test that regenerates them and asserts equality — part
1.3's test. And **a line in the upgrade checklist saying what to do when it goes red**, because a red
test with no instruction attached gets made green by whoever is unblocking the build. The instruction
is one sentence: *read the new action, decide which row of the coverage table it belongs in, and
write the answer in the pull request.* That turns an upgrade from a silent widening into a decision
somebody signed for.

**There is a stronger lever than the door, and it belongs in the same conversation.**
`ComputerUseToolset(computer=..., excluded_predefined_functions=[...])` removes named actions from
the declaration entirely, so the model is never told they exist. That is better than refusing them at
the door, for the reason Day 68's toolset filter is better than an argument check: a tool the model
was never offered cannot be called, cannot be mis-called, and cannot be argued into. `search` is the
obvious first entry on a sandbox pinned to one origin — it is the single genuinely uncovered action
in the table above, and this removes it rather than guarding it. Verified against
<https://adk.dev/integrations/computer-use/> and the installed `google-adk==2.7.1` source on
2026-09-06. Worth noting honestly: that adk.dev page is introductory and does **not** enumerate the
actions or document either constructor flag, which is exactly why this day reads them off the package
instead of the documentation.

**What changes at ten thousand.** Not the count — fifteen is fifteen whether you run one agent or a
fleet. What changes is who is holding the assumption. One engineer who wrote the door remembers that
an unknown action is allowed; a team of thirty inheriting a service that has run for two years does
not, and the code does not say, because both meanings are spelled `""`. At that size the difference
between an allowlist and a two-entry blocklist stops being a design argument and becomes an
onboarding one: what does a new engineer conclude from reading `_verdict` for ninety seconds? They
conclude it is a sandbox. It is a rule about `navigate` and a rule about typed text.

**The review comment a senior engineer leaves:** *"Separate from the default-deny change we already
agreed — that one is about today's thirteen, this one is about the sixteenth. The action list is
ADK's, not ours, so I want the version pin and the declared surface treated as one artifact: the
sorted names in a file, the test that regenerates them, and a line in the upgrade checklist telling
whoever hits the red test to classify the new action in the pull request rather than delete the
snapshot. And put `search` in `excluded_predefined_functions` now — we are pinned to one origin, so
an action whose whole job is to leave should not be on the menu at all, and removing it is stronger
than any rule we could write about it."*

**The interview question:** *"You've written a rule for every action your browser agent can take. Are
you covered?"* An honest answer: *"Not permanently, because the list isn't mine. The framework
generates the tools from a base class, so I measured what it declared rather than assuming: fifteen
actions in the version we pin, and our check had explicit rules for two. I'd defend most of the rest,
because the one rule we do have is an origin check on navigate and a click or a scroll only acts on a
page navigate already approved — but I'd name the exceptions out loud, which are the search action,
whose purpose is to leave the origin and which takes no argument a rule can read, and anything that
opens a second context the origin check never saw. The part that makes it a production problem is
tense: even a complete enumeration is complete until the next upgrade, and a new action arrives
already allowed with nothing logged. So we snapshot the declared list into the repo with a test that
fails on the next bump, we put an instruction next to that test so nobody just regenerates it, and we
drop the actions we know we don't want out of the declaration entirely."*

## Check yourself

```bash
cd days/day-71-computer-use-and-the-sandbox/lab
uv run python -c "
from door import Sandbox
from _computer import Trace

door = Sandbox('http://127.0.0.1:8771', Trace())
for name in ('go_forward', 'open_web_browser', 'current_state'):
    print(name.ljust(18), door._verdict(name, {}) or 'ALLOWED')
"
```

Three more names, all of them real actions in the pinned version. Before you run it, say what each
one will print, and then say which row of the coverage table each belongs in.

Then do the sixteenth-action exercise on paper. Invent a plausible new browser action — file upload,
open in a new tab, print to PDF, read the clipboard — and for each one write two lines: which row of
the table it lands in, and whether the origin check on `navigate` still bounds it. One of those four
breaks the origin argument outright. Find it and say why, because that sentence is what the upgrade
checklist is asking a future engineer to write.

**Out loud, without scrolling up:** `_verdict` returns the empty string in two different places and
they mean different things. Say what each one means, and say why a door that could tell them apart is
a door somebody can fix.

---

The door decides **what the agent may ask for**, and every gap in this part is a gap in that
sentence. But there is a larger gap in the sentence itself, and no amount of enumerating closes it:
even a door with a perfect list, refreshed on every upgrade, is a rule about requests, running in the
same process as the browser it is supposed to be containing.
