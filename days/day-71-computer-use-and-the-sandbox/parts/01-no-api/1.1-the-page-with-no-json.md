# 1.1 — The page with no JSON

## One-line answer

Most of the world publishes for people and not for programs, so an agent that can only call
functions is blind to it — and **computer use** closes that gap in the most literal way there is:
the model is shown the screen and allowed to move the pointer, exactly like a person, which makes
it the **last** thing you should reach for and sometimes the only thing left.

## The story

The results are out on Friday. There is no message, no email, no site to log into: the list is a
printed sheet taped inside the glass of the college office door, and the college is on the other
side of the city.

You ring the office. The clerk is polite and completely unable to help, and it is worth being
precise about why. She is not refusing. There is simply nothing at her end to read out — she has no
list on a screen, no register with your cousin's number in it, nothing but the same sheet you would
be looking at. *"It's on the board,"* she says. *"Come and see."*

So somebody goes. Your cousin goes on Friday morning, gets there, and stands in front of the glass
with forty other people looking for one name in four columns of small print. He comes back and says
he thinks it was there.

He *thinks*. The sheet was behind glass with the light on it, the names were not in alphabetical
order the way everybody assumed, and the column he read last was the one that mattered. Nobody was
careless. The answer simply arrived through a pair of eyes instead of down a wire, and every
weakness eyes have is now sitting inside your answer.

And if you want to know again on Monday — because the sheet is updated when the second list goes up
— somebody has to make the journey again.

## The idea in plain language

Software talks to software through an **API**: an agreed way for one program to ask another program
a question and get an answer back in a shape a program can use. The usual shape is **JSON** — text
written as labelled fields, `{"status": "degraded", "region": "eu-west"}` — so the asking program
gets `status` as a value it can compare, not as a sentence it has to interpret.

An agent that calls tools is doing exactly that. Every tool you have written since
[Day 10's 1.1](../../../day-10-function-tools/parts/01-the-form-fills-itself/1.1-the-declaration-you-no-longer-write.md)
ends in a function call against something with a defined interface.

Now the uncomfortable fact. **Most of what you actually need to read has no such interface.** A
supplier's price list, a courier's tracking page, an internal admin console somebody built in 2019,
a government portal, a vendor's status page. They were built for a person with a screen, a mouse and
eyes. Nobody at the other end refused to give you an API. There is simply nothing there to call, in
the same way there was nothing for the clerk to read out.

There are five ways to get information out of a system, and they are not equally good:

| The way in | What comes back | Why you want it |
| --- | --- | --- |
| an **API** the service documents | JSON, exact fields | one request, unambiguous values, versioned and supported |
| a **feed** or a webhook | a fixed record per event | you are told when something changes instead of asking |
| an **MCP server** wrapping the service | typed tool calls | the schema is the contract, and it is checkable |
| **scraping** the page's HTML | tags and text | the page's own structure is still there to select from |
| **computer use** | a picture of the screen | nothing else was available |

The first four are all versions of the same good luck: somebody left structure behind for you.
[Day 15's 4.1](../../../day-15-toolsets-and-openapi/parts/04-machine-packed/4.1-the-manual-the-service-publishes.md)
built tools straight out of an OpenAPI document, which is a service publishing its own manual.
[Day 34's 1.1](../../../day-34-building-sutra-mcp-tools/parts/01-the-server-object/1.1-three-things-and-no-fourth.md)
built an MCP server, which is you publishing that manual on somebody's behalf. Even scraping, which
has a bad reputation, is enormously better than a picture: the HTML says `class="bad"` and
`id="incident-title"`, and a selector that reads them is fast, free, deterministic and testable.

**Computer use** is the fifth rung, and it is the bottom one. The model is given a **screenshot** —
an image of what is on the screen right now — and a small set of actions it is allowed to perform:
move to a coordinate and click, type at a coordinate, scroll, go back, navigate to an address. It
looks, it decides, it moves the pointer, it looks again. A **browser agent** is that loop confined
to a browser window rather than a whole desktop.

Say the honest version out loud, because a lot of writing about this feature does not: computer use
is **the interface of last resort**. It is slower than an API, more expensive than an API, and less
reliable than an API, on every axis and by a wide margin. You use it when the four better rungs are
missing, and the correct first move when you meet a new system is always to go looking for one of
them before you write anything.

What makes this day's case different is that the four rungs really are missing, and there is a
second thing that only shows up in the incident: **you need it now.** The queue is filling with
tickets about the same outage, the vendor's own page has the answer on it, and "ask them for an API"
is not a plan for this afternoon.

## Why Sutra needs it

Sutra's desk answers support tickets. Since
[Day 54's 4.1](../../../day-54-sequential-parallel-loop/parts/04-where-they-meet/4.1-the-shape-of-the-triage-flow.md)
it has been a triage flow with several stages, and by Day 58 it was a graph. Every one of those
stages ends in a tool call against something with a schema.

Then the queue fills with fourteen tickets in a row that all say some version of *uploads are
failing*. They are not fourteen problems. They are one vendor outage, and the vendor has already
written it down — on a status page, in a red box, for humans.

The desk cannot read that box. It has no tool for it, and there is no tool to write, because there
is nothing to call.

Note carefully what is **not** the situation. Sutra already talks to a vendor API: Day 15 built its
tools from AcmeCloud's OpenAPI document, and that stub still serves on port `8765`. The API exists
and covers buckets, uploads and accounts. It does not cover *"is there an incident right now"*,
because incident communication is a thing companies do on a web page for customers to look at. A
service having an API is not the same as it having an API for the question you are asking.

This part is where the day's fixture arrives. The rest of section 1 measures what the model actually
receives from it ([1.2](1.2-pixels-and-a-url.md)) and how large the set of things it is allowed to
do turns out to be ([1.3](1.3-fifteen-doors-one-used.md)); section 2 drives it, and sections 3 and 4
are about keeping it inside a fence.

## The mechanism

The day serves its own status page, at `days/day-71-computer-use-and-the-sandbox/lab/site/`. It is
two files of plain HTML with no server logic behind them, and the first thing to do is read the one
that matters. Here is the incident banner, verbatim from `lab/site/status.html`:

```html
  <div class="banner">
    <h2 id="incident-title">Elevated error rates on Object Storage (eu-west)</h2>
    <p id="incident-body">Since 09:14 UTC a subset of PUT requests to eu-west buckets are
    returning 503. Uploads are affected; reads are not. Next update in 30 minutes.</p>
  </div>
```

**Line by line:**

- `<div class="banner">` is a container with a **class**, which is a label an author puts on an
  element so a stylesheet — or a program — can find every element wearing it. One selector,
  `.banner`, picks this box out of the whole document.
- `<h2 id="incident-title">` is a heading with an **id**, a label that is unique on the page. `h2`
  plus `id="incident-title"` is about as friendly as a document gets: a scraper asking for
  `#incident-title` gets the incident's headline and nothing else, today and next Tuesday.
- `<p id="incident-body">` is the same again for the body text, and it holds the three facts a
  support desk actually needs: what is failing, which operations are affected, and which are not.
- The text wraps onto a second line **inside** the paragraph. That is invisible to a reader and
  invisible to a parser — HTML collapses whitespace — and it is mentioned here only because it is
  the kind of thing that stops matching when somebody matches on raw text instead of on structure.

Read that fence and count what a parser gets for free: a class, two ids, and the exact words. Below
it in the same file there is a four-row table with a `<th>` header row, a class of `ok` or `bad` on
every status cell, an id on the degraded one, and a link with `id="history-link"`. It is, for a
scraper, a five-line job.

**None of that structure reaches a computer-use model.** It receives a picture of the rendered page.
The ids are gone, the classes are gone, the table is a grid of grey lines, and the difference between
`Operational` and `Degraded` is some green text and some red text.
[1.2](1.2-pixels-and-a-url.md) measures exactly what is left, which is why this part stops at
"read the markup and notice how much of it there is".

The page itself says so in its footer, which is the one line of the fixture written for you rather
than for the model: *This page is a local fixture. It has no API, which is the entire point.*

Serve it and look at it with your own eyes first:

```bash
uv run python days/day-71-computer-use-and-the-sandbox/lab/_site.py
```

**Line by line:**

- `uv run` executes inside the project's environment, so the script sees the same packages every
  other script in this repo sees.
- `_site.py` starts Python's own `http.server` on port `8771` and serves the `site/` directory as
  static files. There is no framework here and no application: a request for `/status.html` is
  answered by reading `status.html` off disk. That is deliberate, because a fixture with logic in it
  is a fixture that can develop opinions.
- It **runs until you interrupt it** with `ctrl-c`. It prints the base URL and the two page
  addresses first, then blocks. Open `http://127.0.0.1:8771/status.html` in a browser, read the red
  box, click *Past incidents*, and come back. Everything the rest of this day does, you have now done
  by hand — which is Principle 4 at the smallest possible scale.
- The port matters. Day 15's AcmeCloud API stub owns `8765`; this day owns `8771`. Two fixtures on
  one port is a confusing afternoon.

There is a reason the site is local, and it is not only convenience. `_site.py`'s own docstring gives
three, and the second one is the one people skip: **driving somebody else's site is not yours to
do.** An agent clicking around a third party's pages is using their service in a way they did not
agree to, and at volume it is indistinguishable from scraping them. The first reason is that a live
status page is edited by somebody else's incident team, so a measurement taken against it would print
a different number every time. The third is that section 4 needs something *outside* the sandbox to
point at, and a port on your own machine is a boundary you own.

## When it breaks

The first thing everybody does, before believing there is no API, is guess an endpoint. It costs
nothing to try, so try it — with the site running, ask for the JSON that is not there:

```bash
uv run python -c "
import urllib.request, urllib.error
from _site import serving

with serving() as base:
    for path in ['/api/status.json', '/status.html']:
        req = urllib.request.Request(base + path, headers={'Accept': 'application/json'})
        try:
            r = urllib.request.urlopen(req)
            print(path, '->', r.status, r.headers.get('Content-Type'))
        except urllib.error.HTTPError as e:
            print(path, '->', e.code, e.reason, '|', e.headers.get('Content-Type'))
"
```

**Line by line:**

- `from _site import serving` reuses the day's own context manager, so the server starts and stops
  around the block and no port is left bound. Run this from inside
  `days/day-71-computer-use-and-the-sandbox/lab/` so the plain-name import resolves.
- `headers={'Accept': 'application/json'}` is the polite way of asking a server for JSON. It is
  included to make the point that asking nicely changes nothing when there is nothing to serve.
- `urllib.error.HTTPError` is caught rather than allowed to end the script, because both answers are
  data here: the failing one and the working one are printed side by side.

Measured on 2026-09-06:

```text
/api/status.json -> 404 File not found | text/html;charset=utf-8
/status.html -> 200 text/html
```

Read the two lines together. The `404 File not found` is the honest answer to a guess. The second
line is the interesting one: the page that *does* exist is served as `text/html`, and it will be
served as `text/html` however you ask. There is no `Accept` header, no `?format=json`, no hidden
`/v1/` prefix that turns this service into a program-friendly one, because those things exist only
where somebody built them.

The other failure in this territory is louder and comes later: you decide to scrape the HTML,
because scraping is the fourth rung and much better than the fifth, and you find the page is empty
when you fetch it. Everything you wanted is drawn by JavaScript after the page loads, so the HTML
your HTTP client receives contains an empty `<div id="root">` and a script tag. That is the moment
most teams end up at computer use, and it is worth naming now so that it does not feel like a
surprise: **a rendered page and a fetched page are different documents.** This day's fixture is
deliberately plain HTML so that the fifth rung is a *choice you can see being made*, not a wall you
were pushed into.

## In production

**What a professional writes instead.** They write the ladder down before they write any code, and
they write down which rung they are on and why. A browser agent that exists because nobody went
looking for the vendor's API is a permanent maintenance cost, bought with a search nobody wanted to
do. In a real system this appears as a one-paragraph note next to the integration: *checked
for an API on this date, none exists for incident status, here is the support ticket asking for one.*
When the vendor ships that API a year later, that note is what makes somebody delete the browser
agent instead of maintaining it forever.

**What degrades at scale.** Brittleness, and in a particular direction. An API breaks **loudly** and
on a schedule: a field is deprecated, a version is announced, your client raises. A page redesign
breaks a browser agent **silently and without warning**, because nobody at the vendor considers
their own CSS a public interface — and they are right. The button moved eighty pixels down, the
banner became a dismissible toast, the status table became a set of coloured tiles. Nothing
returned an error. The agent now reports confidently about the wrong element, which is your cousin
reading the wrong column with total confidence.

**The cost, which is not the same kind of cost you are used to.** Every step of a computer-use loop
carries an image: look, decide, act, look again. A task that takes a person four clicks is four
screenshots into the model, plus the model's reasoning about each one. Compare that with an API
call, which is one request carrying a few hundred bytes and returning a few hundred more. This is
why the ladder is a ladder rather than a menu, and [1.2](1.2-pixels-and-a-url.md) puts real
numbers on the image.

**The failure that only appears with real traffic.** In a demo you point the agent at one page and it
reads one banner. In production the vendor's status page is behind a consent dialog in some regions,
shows a cookie banner over the incident box on a first visit, and occasionally serves an interstitial
asking whether you are a robot — which, for the purposes of that question, you now are. None of
these are on the page you tested against, all of them are on the page your users' agent meets, and
each one is a step the model has to notice and dismiss before it can even start.

**The review comment a senior engineer leaves:** *"Before this merges: is there an API? Not 'is there
an API for everything' — is there one for the incident status specifically. If there is, use it and
delete this. If there is not, say so in a comment with today's date and link the ticket you filed
asking for one, because in six months nobody will remember that we checked, and this browser agent
will be load-bearing."*

**The interview question:** *"When would you give an agent a browser instead of a tool?"* The answer
that shows you have actually done it: *"Only when there is nothing to call. My order is API, feed,
MCP server, scrape the HTML, and only then pixels, because each rung down is slower, more expensive
and easier to break silently. The case I hit was a vendor status page during an outage: the vendor
had an API for buckets and accounts but nothing for incident status, and the answer we needed was
sitting in a red box written for people. So we drove the page. I also wrote down that we checked, so
the day they ship an incidents endpoint, somebody deletes what we built instead of maintaining it."*
