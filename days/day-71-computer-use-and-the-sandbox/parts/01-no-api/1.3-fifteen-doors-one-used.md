# 1.3 — Fifteen doors, one used

## One-line answer

The surface you have to sandbox is what the **runtime declares**, not what your script happens to
call: this day's agent uses exactly one action, and the runtime offers the model **fifteen** — a
number read off the real request rather than counted in your head.

## The story

You join the sports club at the end of the road because you want to use the treadmill. That is the
whole reason. You go three evenings a week, walk in, run, walk out.

At the desk on the first day they fill in a form and hand you a plastic card. The form has a
printed list down one side with every door in the building on it — main gate, gym, pool, squash
court, sauna, terrace, the lift to the first floor, the staff corridor — and the girl at the desk
goes down the list ticking and crossing. She will not hand over the card until she has been down the
whole list, because the system refuses to issue a card with a blank against a door. There is no
"leave it for now".

You never think about that form again. Then one Sunday you are early, the gym is being cleaned, and
you wander upstairs out of boredom and touch your card to the reader by the pool. The light goes
green.

You never asked for the pool. You have never used the pool. If somebody had asked you what your card
opens, you would have said *"the gym"*, honestly, and you would have been wrong — because what your
card opens is the list on that form, and what you use is a habit.

A year later they convert the old storeroom into a weights room and add it to the standard member
profile. Your card opens it on the first morning. Nobody wrote to tell you.

## The idea in plain language

Two words, and the whole part sits on the difference between them.

**Declared** is what the model is told it may ask for. Before every call, the runtime sends the
model a list of tools with their names and argument shapes — the same mechanism
[Day 10's 1.1](../../../day-10-function-tools/parts/01-the-form-fills-itself/1.1-the-declaration-you-no-longer-write.md)
introduced, where a Python function becomes a declaration the model can read.

**Used** is what actually got called on a particular run.

The **attack surface** is the set of things that *can* happen — every door the card opens. It is
built out of the declared list, and it has nothing to do with the used list, in exactly the way that
your card opening the pool had nothing to do with your going there.

This is easy to agree with and surprisingly hard to act on, because when you sit down to write a
sandbox you write it against the code in front of you. Your script navigates and reads. So you write
a rule about navigation, you test it, it passes, and you have covered one door out of a form you
never looked at.

There is a companion idea from [Day 68's 6.2](../../../day-68-least-privilege-tools/parts/06-in-production/6.2-grant-is-a-claim-use-is-evidence.md),
*grant is a claim, use is evidence*, and it is worth putting the two side by side because they look
contradictory and are not:

- When you are **reducing** privilege, the used list is the evidence. Nobody has called `refund` in
  three months, so take it off the list. That is subtraction, and usage is what justifies it.
- When you are **defending** against what the model might do, the declared list is the surface.
  Until the tool has actually been removed, "nobody uses it" is a fact about the past and a
  guarantee about nothing.

Same measurement, opposite directions. Day 68 pointed it at what to delete. This part points it at
what to build a door for, and the door is not allowed to have gaps.

There is a second reason the declared list is the honest one here, and it is specific to computer
use. When you write a tool yourself, the declared list is a list *you* wrote, so at least it is not a
surprise. A computer-use toolset is different: you hand ADK one object and **the framework decides
what the model is offered**. You did not enumerate anything. The list is generated from the
interface, which means the only way to know it is to look at what came out.

## Why Sutra needs it

Sections 3 and 4 of this day build the door: a check that stands outside every tool call and decides
whether it may proceed. A door is only worth building if it has an answer for **everything that can
knock on it**, and this part is where you find out how many that is.

The specific failure it prevents is the one Sutra has already met twice.
[Day 67's 2.4](../../../day-67-guardrail-callbacks/parts/02-where-a-check-stands/2.4-the-guardrail-that-never-ran.md)
measured a guardrail that was configured and never ran. Day 68's
[5.2](../../../day-68-least-privilege-tools/parts/05-failure-lab/5.2-the-tool-that-arrived-without-a-row.md)
measured a tool that arrived without a permission row. Both are the same shape: a control written
against the list somebody had in their head, meeting a list the runtime actually had. A browser is
where that shape gets expensive, because a browser's action set is large, generated for you, and
about to grow with the framework.

## The mechanism

The honest way to learn the surface is to let the runtime declare it to a model you control, and
write down what arrived. `lab/_fake.py` does exactly that: `ScriptedActor` is a real `BaseLlm`, so
the runtime hands it the real request. Here is the part of `generate_content_async` that reads the
list, verbatim from the file and indented as it is there:

```python
        if not ScriptedActor.offered:
            # The runtime puts every declared tool in `tools_dict` on the request. Reading it here
            # is how this day learns the attack surface from the framework instead of from a guess.
            ScriptedActor.offered = sorted(llm_request.tools_dict or {})
```

**Line by line:**

- `llm_request` is the `LlmRequest` object the runtime builds for every model call. It carries the
  conversation, the config, and `tools_dict` — the tools that were declared for this call, keyed by
  name. This is not a debug view or a reconstruction: it is the same object a real Gemini call would
  be built from.
- `sorted(...)` over a dict iterates its keys, so `offered` becomes the tool **names**, in
  alphabetical order. Sorting matters for a measurement you intend to compare across runs — an
  unordered list that prints differently each time is not evidence, it is noise.
- `or {}` handles the case where no tools were declared at all. Without it, an agent with no tools
  would raise a `TypeError` here rather than record the honest answer, which is an empty list.
- `if not ScriptedActor.offered:` records only the **first** turn. The declaration is sent again on
  every turn of a multi-step loop, and capturing it once keeps the measurement a statement about
  what was offered rather than about how many turns happened to run.
- `offered` is a **class** attribute, not an instance one, so a script can read it after the run
  without holding on to the model object. `reset()` in the same file clears it between experiments
  in one process — a leftover value from a previous run would be the most embarrassing possible bug
  in a document about measurement.

`lab/surface.py` builds a `ComputerUseToolset` around the day's `SiteComputer`, gives the scripted
model a one-action script, runs it through a real `Runner`, and prints both lists:

```bash
uv run python days/day-71-computer-use-and-the-sandbox/lab/surface.py 2>/dev/null
```

**Line by line:**

- `ComputerUseToolset(computer=..., allow_private_network_access=True)` is the ADK class that turns a
  `BaseComputer` into tools the model can call. Verified against
  <https://adk.dev/integrations/computer-use/>, checked on 2026-09-06. The flag is the opt-out from
  ADK's own navigate guard and is needed only because the fixture is on `127.0.0.1`; what that guard
  is protecting you from everywhere else is section 4's subject.
- The script handed to the actor is one item long: `[("navigate", {"url": f"{base}/status.html"})]`.
  One action, chosen so the gap between declared and used is as stark as it can be.
- `2>/dev/null` discards ADK's `[EXPERIMENTAL] feature FeatureName.COMPUTER_USE is enabled` warning
  and the runtime's token-usage notes, so the table is readable.
  [1.2](1.2-pixels-and-a-url.md) is where that warning is read rather than hidden — it is telling
  you this toolset is a Preview release.

Measured on 2026-09-06:

```text
tools the runtime declared to the model: 15
  click_at
  current_state
  drag_and_drop
  go_back
  go_forward
  hover_at
  initialize
  key_combination
  navigate
  open_web_browser
  scroll_at

  type_text_at

actions the computer was actually asked for this run:
  navigate           http://127.0.0.1:8771/status.html  

  declared 15, used 1
```

**Declared 15, used 1.** That is the whole part, and every remaining paragraph is a consequence of
it.

The fifteen are not arbitrary. They are a person's hands and eyes at a browser, broken into the
smallest pieces that can be described in a function call:

| What the group is for | The actions |
| --- | --- |
| going somewhere | `navigate` · `go_back` · `go_forward` · `open_web_browser` · `search` |
| pointing at something | `click_at` · `hover_at` · `drag_and_drop` |
| moving the page under the pointer | `scroll_at` · `scroll_document` |
| putting text in | `type_text_at` · `key_combination` |
| starting up, looking, waiting | `initialize` · `current_state` · `wait` |

That table is why the number is fifteen rather than three. With a DOM you write one selector and the
browser finds the element; with pixels ([1.2](1.2-pixels-and-a-url.md)) every physical gesture a
person could make has to exist as its own callable action, because a coordinate is the only handle
there is.

Now the part that makes this a surface you cannot opt out of. `BaseComputer` is an **abstract base
class** — a class that lists methods a subclass is required to implement, and refuses to be
instantiated until they all are. Ask it which ones:

```bash
uv run python -c "
from google.adk.tools.computer_use.base_computer import BaseComputer

names = sorted(BaseComputer.__abstractmethods__)
print(len(names), 'abstract methods:', names)
"
```

**Line by line:**

- `__abstractmethods__` is the frozen set Python builds when the class is created, holding the names
  still marked `@abc.abstractmethod` and not yet overridden. It is the language's own answer, so
  there is no reading of documentation involved.
- Sorting again, for the same reason as before: a set prints in whatever order it likes.

Measured on 2026-09-06:

```text
16 abstract methods: ['click_at', 'current_state', 'drag_and_drop', 'environment', 'go_back', 'go_forward', 'hover_at', 'key_combination', 'navigate', 'open_web_browser', 'screen_size', 'scroll_at', 'scroll_document', 'search', 'type_text_at', 'wait']
```

Sixteen abstract, fifteen declared, and the difference is worth a sentence each way. `screen_size`
and `environment` are required of you but never offered to the model — they describe the computer
rather than act on it. `initialize` is the other way round: it is **not** abstract, because
`BaseComputer` provides a default, and it is still declared to the model as an action it may call.
Neither of those is guessable. Both came off the framework.

The last of the fifteen is the one to look at hardest, because the lab refuses it. From
`lab/_computer.py`:

```python
    async def search(self) -> ComputerState:
        """The action set's escape hatch: go to a search engine.

        Implemented as a refusal rather than as a search, because a search engine is off this
        computer's origin by definition and section 4's whole subject is that leaving the origin is
        the thing a browser sandbox must decide about. A `search` that quietly worked would put the
        agent on the open web through the one action nobody audits.
        """
        self.trace.record("search", "refused: off-origin by definition", allowed=False)
        return await self.current_state()
```

**Line by line:**

- `async def search(self)` takes **no arguments**. That is what makes it the escape hatch: a door in
  the action set with no address on it, so there is nothing for a rule about URLs to inspect. Every
  other way out of this origin goes through `navigate(url)`, where the argument is a string a check
  can read.
- The body does not search. It records the attempt with `allowed=False` and returns the unchanged
  state, so the run continues and the refusal is written down. A method that silently did nothing
  would be a lie to the caller (Principle 10); a method that raised would end the run and teach the
  reader nothing about what the model asked for.
- `self.trace.record(...)` appends to the shared `Trace`, which is why every measurement in this day
  is a count over a list of attempts rather than a claim about intentions. A sandbox that leaves no
  record of what it stopped has stopped nothing you can prove.
- `return await self.current_state()` gives the model a screenshot back, exactly as a successful
  action would. From the model's side a refusal and a no-op are indistinguishable, which is a
  deliberate choice with consequences — [Day 68's 4.5](../../../day-68-least-privilege-tools/parts/04-the-argument/4.5-what-a-refusal-must-not-tell-you.md)
  is the part about how much a refusal should say.

`search` is section 3's subject arriving early, and it arrives here because it is on the list. You
would never have written it. You do not want it. It is declared to the model anyway, and the check
that has to have an answer for it is
[3.1](../03-the-door/3.1-the-check-outside-every-tool.md).

## When it breaks

The loud failure is what happens when you try to implement only the actions you expect to need. You
do not have to edit `lab/_computer.py` to see it — write the computer you would have written if you
had gone by your own script:

```bash
uv run python -c "
from google.adk.tools.computer_use.base_computer import (
    BaseComputer,
    ComputerEnvironment,
    ComputerState,
)


class HalfComputer(BaseComputer):
    async def screen_size(self):
        return (1280, 936)

    async def environment(self):
        return ComputerEnvironment.ENVIRONMENT_BROWSER

    async def current_state(self):
        return ComputerState(screenshot=b'', url=None)

    async def navigate(self, url):
        return await self.current_state()

    async def click_at(self, x, y):
        return await self.current_state()


HalfComputer()
"
```

That class implements five methods: the two that describe the screen, the one that looks, and the
two the day's script actually uses. Measured on 2026-09-06:

```traceback
Traceback (most recent call last):
  File "<string>", line 26, in <module>
TypeError: Can't instantiate abstract class HalfComputer without an implementation for abstract methods 'drag_and_drop', 'go_back', 'go_forward', 'hover_at', 'key_combination', 'open_web_browser', 'scroll_at', 'scroll_document', 'search', 'type_text_at', 'wait'
```

Read where it failed. Not at the first `search` call, not at run time, not in production at eleven at
night — at **construction**, on the line that builds the object, before any agent, any model or any
page existed. The same happens to `SiteComputer` the moment you delete one of the methods at the
bottom of `lab/_computer.py`, with its own name in the message.

This error is the girl at the desk refusing to issue a card with a blank against a door. Python is
telling you that eleven more actions are part of the deal, and that "I did not think I needed
`drag_and_drop`" is not a position the interface allows you to hold. The comment block above those
methods in `_computer.py` says the same thing in one line: **the surface is not the subset you
thought about.**

The quiet failure has no traceback and is the one that actually bites. Implement all sixteen — as
the lab does — then write a sandbox rule about `navigate`, test it against the run that only
navigates, and watch it pass. Nothing is red. Fourteen other actions reach the browser with no rule
about them at all, and the test suite is perfectly happy, because the test drives the same one door
you wrote the rule for. That is why `surface.py` prints `declared 15, used 1` rather than a
reassuring summary: the two numbers are on the same line so that the gap is impossible to read past.

## In production

**What a professional writes instead.** They do not write the surface down by hand at all. They
assert it in a test: read the declared names off a real `LlmRequest`, compare them to a list checked
into the repo, and fail when the two disagree. That test is cheap, it needs no model, and it turns
the framework upgrade below from a silent event into a red build with a diff in it. Writing the
fifteen names into a comment instead produces a comment that is wrong within two releases and is
believed for a year.

**What degrades at scale — and this is the specific one for computer use.** The action set is not
yours. It grows when the framework grows. ADK adds a new browser action in some future release —
file upload, a new key gesture, a second navigation shape — and on the day you run `uv sync` the
declared list is sixteen while your sandbox still knows fifteen. Nothing fails. No test goes red. No
warning is printed. The agent simply gains a capability that no rule in your codebase has an opinion
about, exactly the way your membership card opened the new weights room on the first morning. A
Preview feature ([1.2](1.2-pixels-and-a-url.md)) makes this likelier rather than less likely, because
Preview is precisely the stage at which interfaces still gain methods.

**The failure that only appears with real traffic.** In the lab the model plays a fixed script, so
the used list is one item and stays one item. A real model chooses, and it chooses under pressure:
when it cannot find what it wants on the page it will scroll, then go back, then try the search
action, because those are on the list it was given and it is trying to complete your task. The
actions you never wrote a rule for are exactly the ones a stuck model reaches for, which means the
declared-but-unused set is not merely a theoretical surface. It is the *failure path*.

**The review comment a senior engineer leaves:** *"You have a rule for navigate. What happens on
search? It takes no URL, so your allowlist has nothing to look at, and it exists in the toolset
whether or not our script uses it. I want the declared tool list asserted in a test against a
checked-in expected list, and a default-deny for anything not on it — otherwise the next ADK upgrade
silently widens what this agent can do and we find out from a log."*

**The interview question:** *"How do you decide what a browser agent is allowed to do?"* The answer
that shows you have measured it: *"From the declared tool list, not from what my code calls. I read
it off the real `LlmRequest` — on our browser agent the runtime declared fifteen actions and our run
used one. The interface is an abstract base class, so I could not narrow it by implementing less
either: leaving methods out fails at construction with a `TypeError` naming every one I skipped. So
the surface is fifteen whatever I do, and the sandbox has to live outside the tools and cover all of
them by default. The one that convinced everybody was `search`, which takes no arguments at all, so
a URL allowlist has nothing to inspect — we implement it as a refusal and log the attempt."*
