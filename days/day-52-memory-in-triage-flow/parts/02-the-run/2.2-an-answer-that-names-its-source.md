# 2.2 — G02: an answer that names its source

## One-line answer

**G02:** every answer carries the reference of the row it came from and that reference resolves to a
row that exists — because an answer without a citation is exactly as fluent as one with it, and
cannot be checked, corrected or defended.

## The story

A plumber comes to look at a leak. Afterwards you get a quote by email. Halfway down there is a
line:

*"Replace inlet valve — as previously agreed. £180."*

Agreed with whom? You do not remember agreeing to anything about an inlet valve. Perhaps you did;
there was a conversation on the doorstep and you were half-listening. Perhaps they agreed it with
the previous tenant. Perhaps they agreed it with themselves.

There is no way to find out. The quote is well laid out, the arithmetic adds up, the total is
plausible. The one thing you would need in order to check it — *agreed when, with whom, in what
conversation* — is the one thing the line does not contain, and the absence is invisible because the
sentence reads perfectly well without it.

Compare a line that says *"Replace inlet valve — quoted in the visit on 3 September, see job sheet
4471. £180."* Same price, same work, same confidence. Now you can go and look.

## The idea in plain language

A **citation** is the address of the row an answer came from, carried alongside the answer.

The word "address" is doing the work. A citation is not the row's text, and it is not a description
of the row. It is a string you can take back to the store and use to fetch exactly one thing. In
this desk that string is a `ref`, and refs look like this:

| Ref | Where it lives | What it points at |
| --- | --- | --- |
| `ticket:4521` | the archive | one of fifty-seven documents that existed before this week |
| `kb:KB-104` | the archive | a knowledge-base article |
| `memo:7101:resolution:signed-out-of-the-dashboard` | memory | a memo, from case 7101, admitted by the `resolution` rule, about sign-outs |
| `ticket:4610#0` | the index | the first **chunk** of `ticket:4610`, after Day 50's cut at 900 characters |

The `#0` matters more than it looks. Day 50 cut every document into chunks, so the thing retrieval
returns is not a document — it is a piece of one. A citation that says `ticket:4610` when the row
was `ticket:4610#3` is a citation to the wrong amount of text, and the reader who follows it will
find a document that contains the answer *somewhere* and will not know where. `parent_ref` exists to
strip the suffix when you want the document; the citation keeps it, because the citation's job is to
name what the model was actually shown.

The memo ref is worth reading left to right, because every field earns its place:

- `7101` — which conversation this came out of, so you can go and read the conversation.
- `resolution` — which retention rule admitted it, which is
  [3.2](../03-the-write-path/3.2-every-memo-names-the-rule-that-kept-it.md)'s whole subject.
- `signed-out-of-the-dashboard` — what it is about, so a person scanning a list of citations can
  read it without fetching anything.

The middle field is there because one conversation can leave two memos about the same subject. That
is not an edge case, it is what a **correction** is: case 7108 in this lab produced an
`account_fact` and then a `correction` about the same billing account, and without the kind in the
ref they would be the same address.

Two terms, defined once:

- **Resolves** — the ref, handed back to the store, returns exactly one row. Not "looks plausible".
  Not "is well formed". Returns a row.
- **Grounded** — every claim in an answer traces to a retrieved row. A citation makes an answer
  *checkable*; it does not by itself make it grounded, because a model can cite a row and then say
  something the row does not contain. G02 is the checkable half. The grounded half needs a judge,
  and that is Phase 12's subject.

## Why Sutra needs it

Day 57 introduces the Writer↔Critic pattern, where one agent drafts and another one criticises. A
critic can only criticise what it can verify, and the only thing that makes a draft verifiable is
the citation: the critic fetches the row, reads it, and asks whether the draft says what the row
says.

A desk that produces uncited answers cannot be reviewed by a second agent, cannot be reviewed by a
person, and cannot be evaluated by the evalsets of Phase 12. The citation is not a nicety on the end
of the answer; it is the interface every later phase attaches to.

## The mechanism

The composition step takes the retrieved rows and builds the answer with the refs attached. Here is
the whole of it, from `_phase7.py`:

```python
def compose(self, question: str, rows: list[tuple[float, str]], texts: dict[str, str]) -> str:
    """One request: the question, the retrieved rows, and an answer with citations on it."""
    self.requests += 1
    block = "\n".join(f"[{ref}] {texts[ref]}" for _, ref in rows)
    self.prompt_chars += len(question) + len(block)
    if not rows:
        return NOTHING_FOUND
    best = texts[rows[0][1]].strip()
    refs = ", ".join(ref for _, ref in rows)
    return f"{best}\n\n(from {refs})"
```

**Line by line:**

- `rows` arrives as `(score, ref)` pairs, not as text. That ordering is deliberate: the composer
  never sees a piece of text without the ref that names it, so it is structurally unable to lose the
  association.
- `block` is what would be sent to a real model: each row prefixed with `[ref]`. The brackets are
  there so the model can repeat the ref back in its answer, which is how a real implementation gets
  per-sentence citations rather than a list at the bottom.
- `self.prompt_chars` counts the characters that would go over the wire.
  [5.3](../05-the-zero-claim/5.3-what-a-cache-can-and-cannot-reach.md) is built on this number.
- `if not rows` returns the honest-miss sentence **before** touching `rows[0]`. Getting that order
  wrong is an `IndexError` on the first unanswerable question, which is the most common way this
  function breaks.
- `refs` is joined from the same list that produced `block`, never from a second source. Two lists
  is how a citation ends up pointing at a row the model never saw.

Run it and look at both what the answer says and whether its citations resolve:

```bash
cd days/day-52-memory-in-triage-flow/lab
uv run python cite.py
```

**Line by line:**

- `cite.py` asks one question of two desks — the real one and the archive-only control — and then
  does the thing the criterion is actually about: it takes each ref back to `index.texts` and checks
  that a row comes out.
- Checking against `index.texts` rather than against a regular expression is the point. A ref can be
  perfectly well formed and name nothing.

Measured on 2026-09-05:

```text
--- with memory ---
Blue Peak signed out of the dashboard every few minutes on Chrome. Cause was the SameSite and Secure cookie attributes, see KB-104. Reported by [EMAIL].

(from memo:7101:resolution:signed-out-of-the-dashboard#0, ticket:4521#0)
    cite memo:7101:resolution:signed-out-of-the-dashboard#0  resolves: True
    cite ticket:4521#0  resolves: True

--- archive only ---
Ticket 4521. Keeps getting logged out. The customer is signed out of the dashboard every few minutes and lands back on the sign-in page. Started yesterday. Plan: Pro.

(from ticket:4521#0)
    cite ticket:4521#0  resolves: True
```

Both citations resolve, in both arms. G02 holds.

Now strip the citations off and read the same two answers again:

```bash
uv run python cite.py --strip
```

**Line by line:**

- `--strip` removes only the `(from ...)` line. The sentence itself is byte-for-byte identical.
- Nothing else changes: same retrieval, same rows, same score, same composition.

```text
--- with memory ---
Blue Peak signed out of the dashboard every few minutes on Chrome. Cause was the SameSite and Secure cookie attributes, see KB-104. Reported by [EMAIL].

--- archive only ---
Ticket 4521. Keeps getting logged out. The customer is signed out of the dashboard every few minutes and lands back on the sign-in page. Started yesterday. Plan: Pro.

Both answers are fluent. Neither can be checked.
```

Read those two paragraphs as a support agent who was not there. One of them is the right answer and
one of them is the wrong answer, and **there is nothing in either of them that tells you which.**
Both are specific. Both name a plan or a product detail. Both sound like somebody knew.

That is the argument for G02 in its entirety: the citation is not there to make the answer look
rigorous. It is there because fluency is free and correctness is not, and without an address the
reader has no way to tell them apart.

## When it breaks

The failure that costs the most is a citation that resolves to the wrong granularity.

Change the composer to cite `parent_ref(ref)` instead of `ref` and the output becomes
`(from ticket:4610)`. Every citation still resolves — `ticket:4610` is a real document — and the
citation now points at 1,400 characters of ticket when the model was shown 900 of them. A reviewer
following that citation reads the whole ticket, finds the answer *somewhere* in it, and concludes
the answer was grounded. It might not have been: the chunk the model saw might have been `#1`, which
does not contain the sentence the reviewer found in `#0`. Day 50's
[part 2.3](../../../day-50-chunking-and-top-k/parts/02-measuring-the-cut/2.3-the-cut-that-kept-the-ticket-and-lost-the-fix.md)
measured exactly this gap between "the right document came back" and "the answer was in it".

The second failure is an unresolvable citation, and it has a real error text. Ask the index for a
ref it does not hold:

```text
Traceback (most recent call last):
  File "<string>", line 5, in <module>
KeyError: 'memo:7101:resolution:signed-out-of-the-dashboard'
```

Note what that ref is missing: the `#0`. It is the parent ref, and the index is keyed by chunk, so
the document address is not a key at all. This is the most common citation bug in a chunked store
and it does not appear until somebody clicks a citation.

The third failure produces no error and no wrong answer. It is the empty-result path:

```text
Q  the office printer jams on thick paper
   (nothing cleared the floor)
A  I searched the archive and found nothing close enough to be useful. Nobody has written this one up yet.
```

There are no citations here, and there should not be. A sentence about the search itself is not a
claim about the archive's contents, so it has nothing to cite.
[4.3](../04-the-read-path/4.3-nothing-said-out-loud.md) is about why that sentence has to exist at
all, and about the sentence it must never be replaced with.

## In production

**What a professional writes instead.** Per-sentence citations, not per-answer. The `[ref]` prefix
in `block` is what makes that possible: the model is instructed to repeat the bracketed ref after
each claim it makes, and the output is then parsed and validated before it reaches anyone. A
per-answer citation list is checkable by a human; a per-sentence one is checkable by a machine, and
the difference is whether you can run it on every response or on a sample.

**What degrades at scale.** Refs become stale. A memo is superseded, a ticket is merged into
another, an article is rewritten — and a citation stored in a logged answer from three months ago
now resolves to something else, or to nothing. Real systems solve this by making the ref carry a
version or a content hash, which costs a field and turns "resolves" into "resolves to the same thing
it resolved to then". Without it, an audit of last quarter's answers is an audit of this quarter's
store.

**The failure mode that only appears with real traffic.** Models drop citations under pressure. When
the retrieved rows do not quite answer the question, a model that is instructed to cite will often
produce a good general answer and quietly omit the brackets, because it is no longer answering from
the rows. That is the single most useful signal in the whole flow — an answer with no citation is an
answer that did not come from your data — and it is invisible unless something counts uncited
sentences and alerts on the rate.

**The review comment a senior engineer leaves:** *"The citation is a string built by string
formatting in the composer. Nothing validates it before it leaves the process. Add the resolve check
to the response path, not just to the gate: if a ref does not resolve, that response does not go
out. Otherwise the first time we learn about it is a customer following a dead link."*

**The interview question:** *"Your agent answers from retrieved documents. How does a reviewer know
it did?"* An honest answer: *"Every answer carries the ref of every row it was shown, and the ref is
the chunk ref, not the document ref, so you can check the exact text the model saw. I validate that
each ref resolves before the answer leaves the process. What that gets me is checkability, not
grounding — the model can still cite a row and say something the row does not contain, and catching
that needs a judge. I ran the same answers with the citations stripped and they read exactly as
confidently, which is why I do not treat fluency as evidence of anything."*
