# 1.2 — A gate is not an audit

## One-line answer

An audit checks a component against a list of rules; a gate checks whether a **promise made to a
person** is kept end to end — and the difference decides what you check, in what order, and what
you are allowed to call green.

## The story

You are taking over a rented flat. The agent walks you round with a clipboard.

The clipboard is an inventory. Two sets of keys. One fridge, working. Four dining chairs, one with a
scuffed leg, photographed. Curtains in both bedrooms. Every line is ticked, initialled and dated,
and every line is true.

Then you move in and turn on the shower, and the water runs cold for four minutes and then runs
cold for another four.

Nothing on the clipboard was wrong. The boiler was on it, and the boiler is there, and it switches
on. What was never on the clipboard is the only question you actually had, which is *"can I have a
shower in this flat?"* That question is not about any single item. It is about the boiler, the
thermostat, the pipework and the pressure, all at once, in the order a shower uses them.

An inventory and a shower are both worth doing. They are not the same activity, they do not find
the same problems, and doing the first one very thoroughly does not get you the second one at all.

## The idea in plain language

Day 45 was the inventory. Its
[part 1.1](../../../day-45-the-mcp-audit/parts/01-what-an-audit-is/1.1-the-list-is-written-before-you-look.md)
established the rule that governs both activities: **the list is written before you look**, because
a list written while reading the code bends to the code. That rule stands unchanged today and this
part does not re-argue it.

What is different is the shape of the list.

| | An audit (Day 45) | A phase gate (today) |
| --- | --- | --- |
| Asks about | one component, against rules | one promise, end to end |
| A rule looks like | *"no module under `sutra/` imports an HTTP library"* | *"asked a question whose answer is only in this week's memo, the desk returns that memo first"* |
| Passes when | every rule holds | the promise is kept **and** every rule holds |
| Can pass while broken? | yes — every part correct, wired wrong | no, if the end-to-end criterion is real |
| Runs against | the code | the running system |

The last row is the one that matters. An audit reads source. A gate runs the thing and looks at what
came out. That is why today's headline command is a run and not a scan.

There is a second difference, and it is about what you are allowed to write down.

A criterion has **three** possible results, not two:

- **Green** — the criterion was checked and it holds.
- **Red** — the criterion was checked and it does not hold. This is a **finding**. Day 45's
  [part 1.2](../../../day-45-the-mcp-audit/parts/01-what-an-audit-is/1.2-a-finding-is-the-audit-working.md)
  gives a finding exactly two legitimate endings: fixed, with the change beside it, or filed, with
  the day it is scheduled for.
- **Amber** — the criterion was **not checked**, and the reason is stated. Not "probably fine". Not
  "no reason to think otherwise". Unchecked, and named.

Amber is the one people delete. It is uncomfortable to write down that you did not check something,
so it quietly becomes a tick, and a phase is declared green on a mixture of measurements and
opinions with no way to tell afterwards which was which. The whole value of a gate is that the
distinction survives.

Two more terms, defined once because this day leans on both:

- **The freshness check** — plan section 15 rule 5. At every phase boundary, four things *outside*
  this repository get re-read: the framework's releases, the MCP specification revision, the
  providers' free-tier rosters, and the skills ecosystem. They are outside your version control, so
  nothing in the repository will tell you when they move. [7.1](../07-the-phase-boundary/7.1-the-freshness-recheck.md)
  runs it, and three of its four rows come back amber, honestly.
- **An open ID** — a concept the plan assigned to a day that no written day declares. Plan section
  15 rule 2 says a phase is green only when no ID from this or any earlier phase is open.
  [7.2](../07-the-phase-boundary/7.2-six-conditions-and-the-one-that-is-amber.md) counts them.

## Why Sutra needs it

Phase 8's gate is *"triage graph v1 end-to-end"*. Phase 9's is *"kill it mid-run; it resumes; a
human approved the write"*. Phase 10's is *"injection attempts contained; quota router live"*.

Read those three sentences again. Not one of them is a rule about a module. Every one of them is a
promise about behaviour that spans several days' work, and every one of them will be argued about
in exactly the way today's is: someone will say the pieces are all built, and someone else will ask
whether anybody has run them in a line.

The habit this part is establishing — write the criteria first, run the system, record green, red
and amber separately — is the habit that makes those three gates possible. Getting it right on the
easiest of the four is the point of doing it here.

Eleven sentences, and the script that checks them is a hundred and fifty lines. Run it now, before
anything else in this day, and read what it says:

```bash
uv run python days/day-52-memory-in-triage-flow/lab/gate.py; echo "exit: $?"
```

**Line by line:**

- This one is run from the repository root, not from `lab/`, because it imports `sutra` — the
  project package — and that only resolves from the root. The script inserts the root on the import
  path itself, so either working directory works, but the root is where you will actually be.
- `; echo "exit: $?"` prints the exit code after the output. A gate whose result you have to infer
  from whether the text looked worrying is not a gate; the number is the result.
- It checks `sutra/`, never the lab's reference copy. The lab exists so the *parts* can measure
  things; the gate exists to judge the thing you are building, and those must not be the same code.

Measured on 2026-09-05:

```text
G01: sutra.memory.service (Day 46) is not importable: No module named 'sutra.memory'
G01: sutra.memory.persistence (Day 47) is not importable: No module named 'sutra.memory'
G01: sutra.memory.policy (Day 48) is not importable: No module named 'sutra.memory'
G01: sutra.retrieval (Days 49 and 50) is not importable: No module named 'sutra.retrieval'
G10: mcp is pinned in pyproject.toml with no row in PACKAGES.md
G11: tests/test_memory_flow.py does not exist
findings: 6
exit: 1
```

Six findings and a non-zero exit. That is the correct state of this repository today and it is what
Principle 11 means by *an eval that can go RED*: the gate is red before the work, and turning it
green is the work.

Four of the six are the modules Phase 7 told you to write, which you have not written yet. The fifth
is more interesting, and it is the reason a gate earns its day: **`mcp==1.29.1` is pinned in
`pyproject.toml` and has no row anywhere in `docs/PACKAGES.md`.** Principle 7 says every pin gets a
dated row. Nobody noticed for seven days of MCP work, because no rule was looking. The rule that
found it was written this morning, before anybody looked at the file.

That is the shape of a gate finding: not a bug in the feature you were building, but a piece of
discipline that quietly stopped being true while everyone was busy.

## When it breaks

The way a gate breaks is that it goes green and means nothing, and it happens by one of three
edits, all of which look like tidying.

The first is deleting amber. Four rows that say *"not checked, here is the command"* become four
ticks over a weekend, and the phase's record now claims four measurements that were never made.
Nothing in the file says so afterwards, which is precisely the problem: an unchecked row and a
checked row look identical once the honesty is removed.

The second is checking the reference instead of the product. If `gate.py` imported `_phase7` — the
lab's own working copy of the phase — every criterion above would pass today, on a repository where
`sutra/memory/` does not exist. That is not a hypothetical; it is one import line, and it is the
single easiest way to make a red gate green.

The third is treating a missing target as a skip. That one is subtle enough and common enough that
it has a part of its own: [6.3](../06-failure-lab/6.3-green-because-nothing-existed.md) runs both
versions of the same eleven checks over this repository and they disagree about whether Phase 7 is
finished.

There is a fourth thing that looks like a break and is not:

```text
findings: 6
exit: 1
```

An exit code of `1` from a gate is not an error. Nothing crashed. The script did exactly what it was
written to do and reported that six criteria do not hold. If your continuous integration treats that
as a build failure, that is correct and intended; if a person treats it as *"the gate is broken"*,
they have misread what the tool is for.

## In production

**What a professional writes instead.** They separate the gate from the audit in the repository
itself, because the two run at different times. The audit runs on every commit — it is cheap, it
reads source, and it should block a merge. The gate runs at a boundary and on a schedule, it needs
the system standing up, and it produces a report rather than a pass. Putting both behind one command
means either the audit is too slow to run often or the gate is too shallow to be worth running at
all.

**What degrades at scale.** Criteria rot faster than code. A criterion written against sixty-five
rows quietly stops meaning anything at sixty-five thousand — `G06`'s numbers, for instance, are
thresholds measured on one archive. The professional habit is to write the *measurement* into the
criterion rather than the *threshold*: "report hit rate and answered rate at the shipped k" ages
well; "hit rate is at least 9/10" is a number that will be either meaningless or wrong within a
year, and nobody will know which.

**The failure mode that only appears with real traffic.** An end-to-end criterion needs a question
whose answer is known. In a lab you write the answer key yourself. In production the key is stale
within weeks, because the archive it points at keeps changing — the ticket you nominated gets
merged, the article gets rewritten, the memo gets superseded. Gates that were green for a year turn
red on a Tuesday for reasons that have nothing to do with the code, and the team learns to ignore
them. The fix is that the key is maintained deliberately, by somebody whose job it is, and a gate
that nobody owns is a gate that will be switched off.

**The review comment a senior engineer leaves:** *"Eleven criteria and only one of them runs the
system — the other ten read code. That is an audit with one gate stapled on. Before I sign this
phase off I want at least three end-to-end criteria: one that must succeed, one that must return
nothing, and one that must fail loudly. Right now a wiring bug between the store and the index
passes ten of your eleven."*

**The interview question:** *"What is the difference between your test suite and a phase gate?"* An
honest answer: *"The suite checks that each piece behaves the way I decided it should, and it runs
on every commit. The gate checks one promise the whole system makes to a user, it runs at a
boundary, and it is allowed to come back amber. On the phase I just closed, the gate found something
the suite never could: a package pinned in `pyproject.toml` with no row in the package ledger. No
test was wrong. The discipline had drifted, and only a rule written to look for drift found it."*
