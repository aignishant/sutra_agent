# 4.2 — G07: every constant names its run

## One-line answer

**G07:** every tuned number carries a comment naming the run it came from and no two modules own the
same number — a check that deleting two comment lines takes from zero findings to one, and that this
project's own `TOP_K` fails on the second half.

## The story

The thermostat on the landing is set to 22.

You have lived here for two years. It was 22 when you moved in. You have never changed it, partly
because it is fine and mostly because you do not know why it is 22 rather than 21 or 23, and there
is a vague sense that somebody must have had a reason.

Then the heating bill arrives and you decide to try 20 for a week. And immediately you cannot
evaluate the result, because you do not know what 22 was for. Was it what the previous tenant found
comfortable? Was it the point below which the bathroom pipe froze one January? Was it the number the
engineer set when the boiler was installed, for reasons about the boiler and nothing about the room?

Three completely different reasons, three completely different conclusions about whether 20 is safe
to keep, and the number on the dial tells you none of them. It is a decision with the reasoning
thrown away, and the cost of throwing the reasoning away is not paid at the time — it is paid by the
next person, who has to either repeat the original experiment or leave it at 22 forever.

## The idea in plain language

A **tuned constant** is a number in the code that came from a measurement rather than from a
specification. `CHUNK_SIZE = 900` is tuned. `HTTP_OK = 200` is not — it comes from a document, and
anybody can look it up.

The difference matters because the two rot differently. A specified constant is right until the
specification changes, which is rare and loudly announced. A tuned constant is right until the data
changes, which happens continuously and announces nothing.

Phase 7 produced five of them:

| Constant | Value | The run it came from |
| --- | --- | --- |
| `CHUNK_SIZE` | 900 | Day 50 part 2.2 — seven sizes swept, 900 held 10/10 while cutting context from 459 tokens to 279 |
| `CHUNK_OVERLAP` | 0 | Day 50 part 1.4 — at 900, overlap buys nothing; only four of 57 documents are longer than the chunk |
| `TOP_K` | 2 | Day 50 part 3.2 — the answer rate reaches its maximum at k = 2 and never improves |
| `SIM_FLOOR` | 0.20 | Day 50 part 4.2 — worst real answer 0.180, best impostor 0.388 |
| `MIN_SHARED_TERMS` | 2 | Day 50 part 4.2 — the second condition, without which the floor is not enough |

Every one of those right-hand cells is a sentence somebody had to run something to be able to write.
G07 says the sentence lives **beside the number**, in the source, and not in a document somebody has
to know exists.

There is a second half to the criterion, and it is the one this project actually fails:

> **One number, one owner.**

Day 46's build brief tells the learner to put a `TOP_K` in `sutra/memory/service.py`, sized against
a token budget. Day 50's build brief tells the learner to put a `TOP_K` in `sutra/retrieval.py`,
read off a curve. Two modules, one name, two different pieces of evidence, and nothing that notices
if they disagree.

Day 50's build brief already flags this and asks the learner to **decide which module owns the
number and make the other import it**. G07 is the check that the decision was actually made.

One term, defined once: **evidence rot** is what happens when a number outlives the reason for it.
The number keeps working, because numbers do not stop working; it just stops being *the right
number*, and nothing in the system can tell.

## Why Sutra needs it

Day 70 builds the Quota-Router, which routes requests to whichever provider has headroom. It will
introduce a fresh handful of tuned numbers — window sizes, headroom thresholds, backoff bases — and
every one of them will be measured against provider limits that move. Addendum 02 exists because
free rosters moved once already.

The habit of writing the measurement beside the number is what makes those later constants
maintainable. Without it, Day 70's router is five magic numbers, and the first time a provider
changes its limits nobody will know which of the five to touch.

## The mechanism

The check is fifteen lines and it looks at the source rather than at the value:

```python
def audit(source: str, where: str) -> list[str]:
    """Every tuned constant assigned in `source` with no comment above it or beside it."""
    lines = source.splitlines()
    bare: list[str] = []
    for name in TUNED:
        for n, line in enumerate(lines):
            if not re.match(rf"^{name}\s*(:[^=]+)?=", line):
                continue
            beside = "#" in line
            above = n > 0 and lines[n - 1].lstrip().startswith("#")
            if not (beside or above):
                bare.append(f"{where}: {name} has no comment naming the run it came from")
    return bare
```

**Line by line:**

- It reads the **source text**, obtained with `inspect.getsource`, not the module's values. The
  criterion is about whether the reasoning is written down, and a value cannot tell you that.
- `rf"^{name}\s*(:[^=]+)?="` anchors at the start of a line so a mention inside a function body does
  not count, and the optional `(:[^=]+)?` allows an annotated assignment such as
  `SIM_FLOOR: float = 0.20`.
- Two acceptable positions, `beside` and `above`, because both are idiomatic. A one-line reason goes
  after the value; a three-line one goes above it, which is what all five of Phase 7's constants
  need.
- It reports a **finding**, not a boolean. The name of the offending constant is in the message,
  because a check that says "something is undocumented" costs the reader a search.
- It cannot tell a real reason from `# tuned`. Nothing can. What it enforces is that somebody had to
  type a line, and the value of the rule is entirely in the friction.

## When it breaks

The failure that survives this check is a comment that is a label rather than a reason.

```python
TOP_K = 2  # tuned
```

Passes. Says nothing. The check cannot distinguish it from the real thing, and no check can — the
enforcement is social, and the mechanism is that the rule exists so a reviewer can point at it.

The second failure is the reason drifting from the number. Somebody changes `CHUNK_SIZE` to `1200`
in response to a complaint about truncated answers and leaves the comment saying `900 held 10/10
while cutting context from 459 tokens to 279`. Now the code has a number and a confident, specific,
**false** justification beside it, which is strictly worse than no comment at all: the next reader
will believe it. This is the argument for the comment naming a *runnable* thing — a script and a
part — rather than restating a result, because a named run can be re-run and a quoted number cannot
be checked.

The third failure is the two-owner problem going from a smell to a bug. Suppose the reconciliation
is done by importing:

```text
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ImportError: cannot import name 'TOP_K' from 'sutra.config' (C:\...\sutra\sutra\config.py)
```

That is `from sutra.config import TOP_K` run against this repository today — a module that exists,
asked for a name it does not export. It is what happens when the owner is renamed or moved and the
importer is not updated, and it is the *good* outcome. The bad outcome is that both modules keep their own copy, somebody tunes one of
them, and the desk caps retrieval at two while the memory service caps it at three. Nothing raises.
The system simply behaves as though `TOP_K` were three in one code path and two in another, and the
person debugging it will spend an afternoon before thinking to grep for the name.

## In production

**What a professional writes instead.** The comment names the script, not the result:
`# measured by scripts/sweep_chunk.py, 2026-09-05; see docs/adr/ADR-0007`. A result in a comment is a
claim that decays; a command in a comment is an invitation to re-check. For a constant that matters
enough — a floor that decides whether the desk answers at all — the reasoning goes in an ADR and the
comment points at it, because an ADR has a date and a status and a comment has neither.

**What degrades at scale.** All five of these numbers are properties of a sixty-five-row archive.
Every one of them will be wrong at sixty-five thousand rows, and none of them will announce it. The
production answer is not to tune harder; it is to make the tuning **repeatable** — the sweep is a
script in the repository, it runs against the current store, and its output is compared against the
committed values. That turns "is 0.20 still right" from an argument into a command.

**The failure mode that only appears with real traffic.** Tuned constants get changed under
pressure. At three in the morning, with the desk returning nothing for a class of question, somebody
lowers `SIM_FLOOR` to `0.05` and the pages stop. The number stays. Six months later the desk answers
everything confidently and nobody connects it to a change made during an incident, because the
comment above the constant still describes a sweep from a year ago. The defence is not a better
comment; it is that the constant is configuration with an owner and a change log, not a literal.

**The review comment a senior engineer leaves:** *"Two modules declare `TOP_K` with different values
and different justifications. Pick an owner, make the other import it, and add a test that asserts
they are the same object. I do not care which one wins; I care that in six months nobody can tune one
and ship the other."*

**The interview question:** *"How do you keep magic numbers from accumulating in a retrieval
pipeline?"* An honest answer: *"Every tuned constant carries a comment naming the run it came from,
and I have a check that fails on a bare number — I ran it after deleting two comment lines and it
went from zero findings to one while the behaviour was unchanged, which is exactly the edit that
happens in a tidy-up. The harder half is ownership: I currently have two modules declaring `TOP_K`
with different values, one sized against a token budget and one read off an answer-rate curve, and
that is an open item rather than something I have fixed. Two owners for one number is a bug waiting
for a quiet week."*
