# 2.1 — Tools are plain functions: there is no magic in a tool

## One-line answer

A tool is an ordinary function that takes a string and returns a string — you can call it yourself,
test it yourself, and run it a thousand times without spending a single token, because **nothing
about a function becomes special when a model asks for it**.

---

## The story

A hotel has a concierge desk, and behind the desk there is a row of buttons on the wall. One rings
the kitchen. One calls a taxi. One opens the car-park barrier.

A guest walks up and says, "could someone bring the car round?" The concierge listens, decides which
button that request maps to, and presses it. The barrier opens.

Here is the thing worth noticing. The barrier does not know a guest asked. The barrier does not know
what language the guest spoke, or whether they were polite, or whether they were the owner of the
car at all. **The barrier is a barrier.** It has one behaviour: when the circuit closes, it lifts.
It behaved identically the week before the hotel hired a concierge, when a porter pressed the same
button, and it will behave identically next year when a machine presses it.

An engineer testing that barrier does not need a guest, a concierge, or a conversation. They walk
over and press the button.

That is the whole of this part. The button is a function. Pressing it yourself is a test. And the
concierge — however clever, however fluent — never becomes part of the wiring.

---

## The idea in plain language

In agent writing, the word **tool** carries an unearned aura. Blog posts say the model "has access
to tools", diagrams draw them as special boxes plugged into the model, and vendors sell "tool
platforms". It is easy to come away believing a tool is a category of software.

It is not. Here is a tool:

> A **tool** is a function in your own program that your loop is willing to call on the model's
> behalf.

That is the entire definition. Three things follow from it, and each one is load-bearing:

1. **You can call it directly.** A tool is importable and callable from a Python prompt, a test, or
   another function. If you cannot call it without a model in the room, it is not a tool — it is a
   tangle.
2. **It costs nothing to run.** No model call, no quota, no network. Today you will run both of
   Sutra's tools before you spend a single token, which is the correct order and also the frugal one
   (Principle 15: quota is the currency).
3. **The model never touches it.** The model emits the *name* of a tool as text. Your loop looks the
   name up and decides whether to call it. The gap between those two sentences is
   [2.2](2.2-the-dispatch-table-is-the-boundary.md), and it is where all the security lives.

Two terms defined here on first use, because both get used loosely elsewhere:

| Term | What it means here |
| --- | --- |
| **Tool** | The function itself — `lookup_ticket`, `search_kb`. Ordinary Python. |
| **Tool call** | The model's *request* that a tool be run, expressed as text. A request, not an action. |

The distinction matters because "the model called the tool" describes something that never happens.
The model *asked*. Somebody else called.

**Why is Sutra's tool signature `str -> str` today?** Because today the model can only speak text
([1.2](../01-loop-anatomy/1.2-the-transcript-is-the-world.md): the transcript is the world), so an
argument arrives as text and a result must go back as text. That is a real limitation and it does
real damage — you cannot express "a ticket id, an integer, required" in a string signature, and you
cannot stop the model sending `ticket 4521 please` where you wanted `4521`. **Day 4 (AG-04) is the
cure**: JSON schemas describe each parameter's name, type and requiredness, and the API validates
the model's request against them before your code ever sees it. Today you feel the absence. That is
the point of building first and comparing after (Principle 4).

## Why Sutra needs it

- **Today**, [2.2](2.2-the-dispatch-table-is-the-boundary.md) builds a dispatch table over these two
  functions, and [4.2](../04-running-the-loop/4.2-the-first-real-run.md) watches a model choose
  between them without ever touching either.
- **Day 4 (AG-04)** wraps these same two functions in JSON schemas. Same functions. The schema is
  packaging, not a rewrite — which only becomes obvious if the functions existed plainly first.
- **Day 10 (ADK-10, ADK-11)** hands these functions to ADK's `FunctionTool`, which reads the type
  hints and the docstring you write *today* and generates the schema from them. **The docstring you
  write this evening is machine-read seven days from now.** Write it as if it were.
- **Day 34 onward (MCP)** moves tools out of the process entirely, behind a protocol. What survives
  every one of those moves is the function. The transport changes; `lookup_ticket` does not.
- **Day 39 (`sutra-core`)** turns these into real database queries. Today's dictionary is a
  stand-in for a table, and the seam is deliberately in the same place.

## The mechanism

Sutra is a support-ticket triage desk, so its first two tools are the two things a human triager
does first: read the ticket, then look for a known cause.

Start with the data. It is synthetic, and that is a rule rather than a convenience: no real personal
or employer data goes through a free endpoint (Principle 9's cousin — a free tier is somebody else's
computer).

```python
# Synthetic desk data — never real personal or employer data (Principle 9).
TICKETS = {
    "4521": "Title: Keeps getting logged out. Body: I keep getting logged out "
    "of the dashboard every few minutes. Started yesterday. Plan: Pro.",
    "4522": "Title: CSV export empty. Body: Exporting my project as CSV gives "
    "an empty file. Small projects work; the big one does not.",
}

KB = {
    "logout": "KB-104 'Unexpected logouts': cookies set with SameSite=Strict plus "
    "an http:// dashboard URL end sessions early; fix is forcing https.",
    "export": "KB-201 'Large exports time out': exports over 10k rows hit the worker "
    "deadline and return an empty file; use the async export API.",
}
```

**Line by line:**

- `TICKETS = {...}` — a module-level dict standing in for a database table. The keys are strings, not
  integers, because **the model will hand you a string** — it has no other way to speak. Making the
  keys integers here would buy you a `KeyError` the first time a model writes `4521` and you look up
  `"4521"`. Choose the type the caller will actually produce.
- `"4521"` — the same ticket Day 2 used for token arithmetic in
  [2.1](../../../day-02-llm-mechanics/parts/02-tokens-the-meter/2.1-what-a-token-is.md). Continuity
  is deliberate: you already know roughly what this ticket costs to send.
- The ticket bodies are written the way users actually write — a symptom, a timeframe, an irrelevant
  detail. A tidy `{"issue": "logout"}` would let the model succeed without reading anything, which
  would prove nothing about the loop.
- `KB` — the knowledge base, keyed by the word a naive search would match on. **Both articles state a
  *mechanism*, not a platitude.** That is what makes step 3 of today's run checkable: an answer that
  mentions `SameSite` and `https` could only have come from KB-104, so you can prove the tool result
  reached the model. An article reading "check your settings" would make every answer unfalsifiable.
- `KB-104` and `KB-201` — article ids. When the final answer cites one, you have a **citation you can
  verify**. Day 16's grounding work and Day 49's retrieval both live on this habit.

Now the two functions. Read the signatures first: `str -> str`, both of them.

```python
def lookup_ticket(ticket_id: str) -> str:
    """Return the raw text of a ticket, or a not-found message.

    Example:
        >>> lookup_ticket("4521")
        "Title: Keeps getting logged out. ..."
        >>> lookup_ticket("9999")
        "No ticket with id '9999'."
    """
    return TICKETS.get(ticket_id.strip(), f"No ticket with id {ticket_id!r}.")


def search_kb(query: str) -> str:
    """Naive keyword match over the KB; returns the first matching article.

    Example:
        >>> search_kb("logout loop on the dashboard")
        "KB-104 'Unexpected logouts': ..."
        >>> search_kb("keeps getting logged out")
        "No KB article matched 'keeps getting logged out'."
    """
    q = query.lower()
    for keyword, article in KB.items():
        if keyword in q:
            return article
    return f"No KB article matched {query!r}."
```

**Line by line:**

- `def lookup_ticket(ticket_id: str) -> str:` — **type hints on both ends**, per house style. They
  are documentation today and machine-read on Day 10, when ADK's `FunctionTool` builds a JSON schema
  from exactly these annotations. A bare `def lookup_ticket(ticket_id):` costs you nothing this
  evening and costs you the schema next week.
- The docstring's `Example:` block — richer than an ordinary docstring, because in a day document the
  code *is* the teaching (house style). It is also the text a model reads on Day 10 to decide when
  this tool applies, so it is written for two audiences at once.
- `ticket_id.strip()` — **defensive, and specifically defensive against the model.** A model asked to
  emit `ACTION: lookup_ticket 4521` will sometimes emit two spaces or a trailing newline. Today there
  is no schema to reject that, so the tool absorbs it. Note this as the first small tax of the text
  protocol; [3.2](../03-the-protocol/3.2-parsing-a-reply-you-did-not-write.md) collects several more.
- `TICKETS.get(ticket_id, <default>)` — **`.get` with a default, not `TICKETS[ticket_id]`.** This is
  the single most consequential line in the file and it is the subject of
  [2.3](2.3-a-failed-tool-is-an-observation.md): a miss must come back as a *message the model can
  read*, not an exception that kills the loop.
- `f"No ticket with id {ticket_id!r}."` — `!r` calls `repr()`, so the id appears quoted:
  `No ticket with id '9999'.` The quotes are a diagnostic — they make a trailing space visible as
  `'9999 '` instead of invisible.
- `q = query.lower()` — case-insensitive matching, because the model writes prose, not a query
  language. It will send `Logged out` as readily as `logged out`.
- `for keyword, article in KB.items(): if keyword in q:` — **substring matching over a two-entry
  dict.** This is naive on purpose, and calling it naive is part of the teaching: it will match
  `logout` inside `logout loop` and miss a ticket that says "my session keeps ending". That gap is
  exactly the case for embeddings on Day 49 (AG-33), and you will meet it as a real miss before you
  meet it as a solution.
- `return f"No KB article matched {query!r}."` — same discipline as the ticket miss. Every path out
  of this function returns a string a model can read.

Now prove they work, with no model in the room at all:

```bash
uv run python -c "from sutra.loop import lookup_ticket, search_kb; print(lookup_ticket('4521')); print(search_kb('user logged out'))"
```

**Line by line:**

- `uv run` — the project's interpreter and its dependencies, per Day 0. `python -c` on its own would
  use whichever Python is first on your `PATH` and probably fail to import `sutra`.
- `python -c "..."` — a one-liner, deliberately not a test file. This is the check you will run for
  the rest of your career before wiring anything into a loop: **does the function work when I call
  it?**
- `from sutra.loop import lookup_ticket, search_kb` — an ordinary import of ordinary functions. If
  this line surprises you, re-read the definition at the top of this part.
- **Zero model calls. Zero tokens. Zero quota.** Write that down: today's tool work costs nothing,
  and every check you run here saves a call you would otherwise burn discovering a typo through a
  model.

## When it breaks

Run the check before creating the module and you get the day's first honest error:

```text
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'sutra.loop'
```

**What it means.** Exactly what it says — `sutra/loop.py` does not exist yet. It is listed here
because the *next* error is the one that actually confuses people:

```text
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'sutra'
```

**What it means.** One word shorter and a completely different fault. `sutra` itself was not
importable, which almost always means the command ran outside `uv run` — a bare `python -c ...` from
your shell uses an interpreter that has never heard of this project. **The smallest fix** is to put
`uv run` back at the front. The habit worth forming: read *how much* of the dotted path failed. The
missing piece names the layer that is wrong.

And the failure that matters most in this part is not an exception at all:

```text
No ticket with id '4521 '.
```

**What it means.** The ticket exists; you asked for it with a trailing space. This is the entire
reason `.strip()` is in the function, and it is the shape of every text-protocol bug you will hit
today: **the payload was nearly right.** A JSON schema (Day 4) turns "nearly right" into a
validation error before your code runs. A bare string cannot.

## In production

**A production tool is not a dict lookup, but it keeps this exact shape.** `lookup_ticket` becomes a
parameterised SQL query or a call to a ticketing API; `search_kb` becomes a search index. What a
professional keeps identical is the **seam**: a plain function, callable without a model, with a
declared signature and a docstring, and no knowledge whatsoever of the agent that will use it. Sutra
builds the real versions on Day 39, and the reason that day is not a rewrite is that today's
functions never learned anything about loops.

**What changes at scale is latency and failure, and both belong to the tool.** A dict returns
instantly and cannot time out. A real ticket API can be slow, rate-limited, or down — and in an
agent that runs a tool once per loop step, one slow tool multiplies by the step count. Production
tools therefore carry a timeout, a retry policy, and a bounded output, and they are the reason
Day 11 (AG-06, tool design) exists as a day of its own.

**The failure that only appears with real traffic is the unbounded result.** `search_kb` returns one
short article because the dict has two entries. The production version matches four hundred
documents, returns all of them, and every subsequent model call in the loop re-sends the lot —
[1.2](../01-loop-anatomy/1.2-the-transcript-is-the-world.md) showed you the arithmetic. The
professional's rule: **a tool returns an answer, not a haystack.** Top-k, truncate, summarise — at
the tool boundary, before the text ever becomes an observation.

**The review comment a senior engineer leaves:** *"`search_kb` has no result limit and no timeout.
What is the maximum number of bytes this can put into the context, and what happens when the index
is slow? Right now the answer to both is 'whatever the data does', which is not a bound."*

**The interview question:** *"how do you test an agent's tools?"* The answer that shows you have
done it: "Separately from the agent, and first. The tools are plain functions with plain signatures,
so they get ordinary unit tests with no model, no network and no quota — which means they can run in
CI on every commit. Then the agent-level tests only have to answer a different question: given
working tools, does the model choose the right one? Teams that skip the first layer end up debugging
tool bugs through a probabilistic interface, which is the most expensive way to find a typo I know
of."
