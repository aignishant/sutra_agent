# 1.2 — The ladder measured

## One-line answer

Given the same six attempts, the ladder **succeeds** where retrying every second **gives up** — not
because doubling is gentler, but because it reaches `t=15s` while flat retry reaches `t=5s`, and the
window opened at ten.

## The story

Results day. The board is going up on the school's website at some point during the morning, and the
office has said "before eleven" in the way that means nobody has told them either.

One boy refreshes the page every few seconds from half past eight. By half past nine he has loaded it
maybe four hundred times, he is no closer to knowing anything, and his thumb hurts.

His sister checks once at half eight. Nothing. She goes and has breakfast and checks at nine.
Nothing. She reads for a bit and checks at ten, and it is there.

They both spent the morning waiting for the same thing. One of them spent the morning *waiting for
it*, and the other one had breakfast.

## The idea in plain language

Part [1.1](1.1-why-doubling.md) argued that doubling is a search over an instant you cannot see. This
part runs the search and reports what it costs.

The comparison has to be fair, and "fair" here means one specific thing: **the same attempt budget**.
It is easy to make either strategy look good by giving it more tries. So both runs get six attempts
against the same provider, whose window opens at `t=10s`, and the only difference is how long they
wait between them.

Two numbers come out and they pull in opposite directions:

- **How far through time the strategy reaches**, which decides whether it finds the window at all.
- **How long the caller waits after the window has already opened**, which is latency the customer
  pays for nothing.

The ladder wins the first and loses the second. That is the whole trade, and it is worth having the
actual figures rather than the intuition, because the intuition — *"doubling means waiting longer"* —
gets the conclusion backwards on the number that matters most.

## Why Sutra needs it

Because Day 70's router already handles the *provider-side* half of a 429: it marks a lane cold and
routes elsewhere. Its part 4.2 was explicit that the caller's ladder is a separate mechanism at a
different level, and left it to this day. A desk with four lanes still needs to know what a single
call does when every lane is cold, and that is a retry loop with a budget.

It also decides a number that will end up in `sutra/backoff.py`. The build brief asks for an explicit
attempt budget, and choosing one without measuring what each strategy reaches within it is choosing
by feel.

## The mechanism

The loop is deliberately plain — the interesting part is the one line that differs between the arms:

```python
def run(opens_at: float, *, flat: bool) -> tuple[str, int, float, int]:
    """Retry until success or the attempt budget runs out.

    Returns:
        (outcome, attempts, elapsed, wasted) - the verdict, how many requests were made, how long
        the caller waited, and how many of those requests could never have succeeded.
    """
    clock = Clock(0.0)
    provider = Provider(opens_at=opens_at, clock=clock, says_retry_after=False)
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            provider.call()
            return "ok", attempt, clock.now, provider.wasted()
        except Refused:
            if attempt == MAX_ATTEMPTS:
                break
            clock.sleep(1.0 if flat else ladder_wait(attempt))
    return "gave up", MAX_ATTEMPTS, clock.now, provider.wasted()
```

**Line by line:**

- `says_retry_after=False` is set on purpose. This section is about the case where the server does
  *not* tell you when to come back — section 2 is the case where it does, and mixing them would make
  the ladder look worse than it is by comparing it against information it was never given.
- `clock.sleep` adds to a number rather than sleeping. That is what makes a sixteen-second ladder
  measurable in a test, and what makes the two arms comparable on any machine (Principle 15).
- `if attempt == MAX_ATTEMPTS: break` skips the final sleep. Waiting after the last attempt is time
  the caller spends learning nothing, and it is an easy off-by-one that inflates the elapsed figure
  in every naive implementation.
- `clock.sleep(1.0 if flat else ladder_wait(attempt))` **is the entire difference between the two
  arms.** Everything else — the provider, the budget, the clock, the counting — is shared.
- `provider.wasted()` counts requests that arrived before the window opened. Those are requests that
  reached a provider and could never have succeeded, and part
  [5.2](../05-in-production/5.2-what-to-alert-on.md) argues they are one of the two numbers worth
  watching in production.

Run the ladder:

```bash
cd days/day-72-backoff-with-honesty/lab
uv run python ladder.py
```

**Line by line:**

- `cd` first: every script in this lab imports its siblings by plain name.
- No flag means the ladder, six attempts, against a window that opens at `t=10s`.

Measured on 2026-09-06:

```text
window opens at t=10s   strategy: ladder 1-2-4-8   budget: 6 attempts

  outcome                  ok
  attempts made            5
  caller waited            15s
  wasted requests          4

  the caller waited 5s longer than it strictly had to
```

Now the same budget, spent evenly:

```bash
uv run python ladder.py --flat
```

**Line by line:**

- `--flat` replaces the doubling with a constant one-second wait. Six attempts either way.

Measured on 2026-09-06:

```text
window opens at t=10s   strategy: flat 1s   budget: 6 attempts

  outcome                  gave up
  attempts made            6
  caller waited            5s
  wasted requests          6

  the budget ran out before the window opened - section 3 is what happens next
```

**Read the `outcome` rows together.** The ladder got an answer. Flat retry did not — and it failed
while doing *more* work: six requests instead of five, all six of them wasted.

The arithmetic is worth writing out because it is the whole argument. Six attempts at one-second
intervals put the last request at `t=5s`. Six attempts on 1-2-4-8-8 put the last one at `t=23s`.
Against a window that opens at `t=10s`, one of those strategies is looking in the right place and the
other has stopped looking before the answer exists.

And now the honest half, which is the third run:

```bash
uv run python ladder.py --opens 40
```

**Line by line:**

- `--opens 40` moves the window out past the end of the ladder. Nothing else changes.

Measured on 2026-09-06:

```text
window opens at t=40s   strategy: ladder 1-2-4-8   budget: 6 attempts

  outcome                  gave up
  attempts made            6
  caller waited            23s
  wasted requests          6

  the budget ran out before the window opened - section 3 is what happens next
```

The ladder is not magic. It reaches further per attempt, and a window that outlasts its reach defeats
it exactly as flat retry was defeated — same `gave up`, same six wasted requests. What changed is
where the cliff is, not that there is one.

That matters more than the win does, because it is the thing people forget when they add backoff and
consider the problem solved. **Every retry strategy has a horizon, and past it the code is in section
3**, deciding what to say when it has nothing.

## When it breaks

The 5-second column is the cost and it is not trivial. In the successful run the window opened at
`t=10s` and the caller got its answer at `t=15s` — it slept through five seconds during which the
request would have worked. Flat retry, had it been given a seventh attempt, would have found the
window at `t=6s`.

So the ladder trades **latency on the request that would have succeeded early** for **reach on the
one that needs patience**, and which you want depends on something outside this file: whether a person
is waiting for the answer.

- A customer's ticket is being answered right now. Five seconds of avoidable latency is a real cost,
  and a shorter first rung is defensible.
- A nightly re-index runs at three in the morning. Nobody is waiting; reach is all that matters and
  the first rung could be much longer.

The lab uses one second because that is the shape the provider's own troubleshooting guidance
describes, and part [1.1](1.1-why-doubling.md) records what that page actually said on the day it was
read. It is a default, not a law, and a system that uses the same ladder for an interactive call and a
batch job has made one decision where it needed two.

## In production

**What degrades at scale.** Retries multiply load exactly when a provider is least able to take it. A
single client's ladder is polite; ten thousand clients each running a ladder against a provider having
a bad afternoon is a retry storm that keeps the provider having a bad afternoon. That is the failure
part [4.1](../04-everyone-at-once/4.1-the-herd.md) measures, and the reason a retry policy is never
finished at the point where it works for one caller.

**The failure mode that only appears with real traffic.** Nested retries. The provider's SDK retries,
your helper retries, and the queue that fed the job retries the whole task — three layers each
believing it is the only one, multiplying into a request count nobody designed. It shows up as a
wasted-request figure far larger than any single layer's budget explains, which is why part
[5.2](../05-in-production/5.2-what-to-alert-on.md) puts that number on the dashboard. The fix is to
decide, once, which layer owns retrying and to turn it off in the others — and that decision has to be
written down, because every layer's default is *on*.

**What a professional measures before choosing a ladder.** The actual distribution of how long the
window stays shut. A provider whose 429s clear in two seconds and one whose daily quota resets at
midnight need completely different policies, and Day 70 part 1.4 already established that those are
two different windows on the same provider. Reaching `t=23s` is the right target for the first and
useless for the second, where the only correct behaviour is to stop and escalate.

**The review comment a senior engineer leaves:** *"Both arms of this test use six attempts, which is
the right way to compare them — please keep that in the test name so nobody 'fixes' it later by giving
the ladder more tries. Two things to add: make the first rung configurable, because we're going to
want a different one for the interactive path and the nightly job, and log the wasted count. If we
ever see wasted requests well above six per call, something else in the stack is retrying too and
we'll want to know that before the provider tells us."*

**The interview question:** *"Why exponential backoff rather than a fixed retry interval?"* An honest
answer: *"Because within a fixed attempt budget it reaches much further through time. I measured this:
six attempts at one-second intervals put the last request five seconds out, and six attempts on a
1-2-4-8 ladder put it twenty-three seconds out — so against a window that opened at ten seconds, the
ladder got an answer and flat retry gave up having made more requests, all of them wasted. The cost is
latency when the window opens early: the successful run waited five seconds longer than it strictly
had to. So it's a trade between reach and latency, and which you want depends on whether a person is
waiting. What I'd push back on is treating it as solved once it's added — the ladder still has a
horizon, and a window that outlasts it fails exactly the same way."*

Before running anything, work out on paper where the sixth attempt lands for each strategy. Then find
the smallest `--opens` value that defeats the ladder, and the largest one that flat retry survives.
Those two numbers are the reach of each strategy, and you should be able to derive both without the
lab.

and explain why in terms of what each rung is worth.
