# 2.3 — Zero is not absent

## One-line answer

`retry_after=0.0` means *come back now* and `retry_after=None` means *the server said nothing*, and
one character decides whether your code can tell them apart: `refusal.retry_after or ladder_wait(1)`
turns a stated zero into a one-second wait, while `is not None` keeps it at zero.

## The story

The school sends home a form before the trip. One of the boxes says **number of siblings attending**.

A mother with no other children writes `0`. Another parent, in a hurry at the gate, hands it back with
that box empty.

To the teacher collecting them these are not the same. The first says *I have answered your question
and the answer is none*. The second says *nobody has answered this yet*, and she has to go and ask,
because an empty box might mean none and might mean three.

If she totals up the forms treating blanks as zero, her coach booking is wrong and nothing about the
paperwork will tell her.

## The idea in plain language

Python's truthiness rules collapse a set of quite different values into one branch. `0`, `0.0`, `""`,
`[]`, `{}` and `None` are all falsy, so `x or default` fires for every one of them — and for a
`retry_after`, two of those values carry opposite meanings:

| Value | What the server meant | What `or` does |
| --- | --- | --- |
| `0.0` | *the window is open; come back immediately* | replaces it with the default |
| `None` | *I am not telling you when* | replaces it with the default |

The second row is correct. The first is a bug, and it is a bug with no error, no exception and no log
line — the client simply waits a second longer than it was told to, every time.

Is one second a disaster? On its own, no. That is exactly why this survives: the cost is small,
invisible and constant, so nothing ever forces anybody to look at it. And it scales with the retry
count — a client honouring a series of zeroes waits a second on each one, which is a client that
believes it is honouring the server and is in fact ignoring it.

The shape is what matters more than the seconds. **A falsy check cannot distinguish "answered with a
zero" from "not answered"**, and any field where zero is a legitimate answer has this bug waiting in
it.

## Why Sutra needs it

Because `sutra/backoff.py` is about to be written and this is the single line most likely to be wrong
in it. `retry_after or default` is shorter, reads better, and is what most people type. The gate does
not check for it — no gate can — so the only thing standing between the repository and this bug is
somebody having seen it once.

It is also the third time this exact shape has appeared in the curriculum, which is why it earns a
part rather than a footnote. Day 67 part 2.5 found a guardrail returning an empty dict as a refusal
and being silently overridden, because the ADK runtime stops only on a **truthy** result. Same rule,
same language feature, opposite consequence: there a falsy value meant *nothing was refused*, here it
means *nothing was said*.

## The mechanism

`Refused` is typed to keep the two apart, and the type is doing real work:

```python
class Refused(Exception):
    """A refusal that carries what the server said.

    `retry_after` is `None` when the server did not say - which is a different situation from
    `retry_after=0`, and conflating the two is part 2.3's failure.
    """

    def __init__(self, status: int, retry_after: float | None) -> None:
        after = "none" if retry_after is None else f"{retry_after:.0f}s"
        super().__init__(f"{status}: refused, retry-after {after}")
        self.status = status
        self.retry_after = retry_after
```

**Line by line:**

- `retry_after: float | None` is the whole design. A plain `float` would force the absent case to be
  encoded as some number, and whichever number you pick becomes indistinguishable from a server that
  really sent it.
- `"none" if retry_after is None else f"{retry_after:.0f}s"` — the message itself uses `is None`
  rather than truthiness, so a refusal carrying `0.0` prints `retry-after 0s` and one carrying `None`
  prints `retry-after none`. A log line that cannot tell them apart is a log line that cannot help you
  find this bug.
- Both values are kept on the exception rather than formatted away, so the caller decides. Day 70 part
  4.1 made the same argument for a refusal carrying its own reason.

Now the bug and the fix, side by side, against both kinds of refusal:

```bash
cd days/day-72-backoff-with-honesty/lab
uv run python -c "
from _provider import Refused, ladder_wait

# A refusal that says: come back immediately, the window is open now.
refusal = Refused(429, 0.0)
# The same call, from a server that said nothing at all.
silent = Refused(503, None)

for label, r in (('server said 0s', refusal), ('server said nothing', silent)):
    buggy = r.retry_after or ladder_wait(1)
    correct = r.retry_after if r.retry_after is not None else ladder_wait(1)
    print(f'  {label:<22} retry_after={r.retry_after!r:<6} buggy waits {buggy:>4.0f}s   correct waits {correct:>4.0f}s')
"
```

**Line by line:**

- Two refusals are constructed by hand rather than produced by the provider, because the point is the
  *value*, and constructing it directly is the shortest path to seeing what each branch does with it.
- `r.retry_after or ladder_wait(1)` is the bug, written the way it gets written — it reads as "use the
  server's number, or fall back", and that is what the author intended it to mean.
- `r.retry_after if r.retry_after is not None else ladder_wait(1)` is the fix. Longer, uglier, and it
  says what was meant.
- Both branches are evaluated for both refusals in the same loop, so the two rows can be read against
  each other rather than trusted separately.

Measured on 2026-09-06:

```text
  server said 0s         retry_after=0.0    buggy waits    1s   correct waits    0s
  server said nothing    retry_after=None   buggy waits    1s   correct waits    1s
```

**Read the second row first**, because it is the one that hides the bug. When the server said nothing,
the two expressions agree — both wait a second. Every test written against the absent case passes.
Every code review that checks "does the fallback work" is satisfied.

The first row is where they part. The server said `0.0` — *the window is open, come back now* — and
the buggy expression waits a second anyway, because `0.0` is falsy and `or` cannot see the difference
between a zero somebody wrote and a box nobody filled in.

So the bug is invisible in exactly the case people test, and visible only in the case they do not
think to construct. That is not bad luck; it is the general property of falsy-check bugs, and it is
why this part exists as a measurement rather than as advice.

## When it breaks

The honest question is whether this matters, and the answer is *sometimes, and you should know which*.

**When it barely matters:** a provider that never sends `0` — many do not, because a server with an
open window usually just answers the request rather than refusing it with a zero wait. Against such a
provider the bug is unreachable, and it will sit in the code being harmless until the provider changes.

**When it matters a lot:** anywhere zero is a real answer. A rate limiter that says *"you may go now,
this refusal was a race"*; a queue reporting zero seconds until the next slot; a `Retry-After: 0` used
to mean *retry immediately against a different backend*. In those cases the client is adding latency
to every single retry while believing it is obeying instructions.

And the generalisation is the thing to carry out of this part rather than the seconds. **The same bug
lives in every `x or default` where `x` may legitimately be zero, empty, or false** — a configured
timeout of `0` meaning "no timeout", a `max_retries=0` meaning "do not retry", a page size of `0`. Day
67 part 2.5 found it in a guardrail's return value. It is the same line each time, and the fix is
always `is None`.

## In production

**How this is actually found.** Not by reading code, and not by a type checker — `float | None`
narrows correctly under `or` as far as the types are concerned, because the expression is
well-typed and simply means the wrong thing. It is found by a test that constructs the boundary value
on purpose, which is why the build brief asks for exactly that test and why it is worth writing before
the code.

**What degrades at scale.** The cost is per-retry and invisible per-request. A second added to every
honoured zero is nothing on one call and is a measurable share of latency on a service doing millions,
and there is no metric that will point at it — the retry succeeded, the request succeeded, the latency
is a little higher than it should be for reasons nobody can attribute. This is the class of bug that is
found by somebody reading the code for another reason, years later.

**What a professional does about the whole class.** Bans the pattern where the value is nullable, or
uses a sentinel that is never legitimate. Some codebases go further and forbid `or`-defaulting
entirely on optional numerics, with a lint rule, precisely because the failure is silent and the
correct form is only slightly longer. Whether that is worth a rule is a judgement about your codebase;
knowing why somebody would make the rule is not.

**The review comment a senior engineer leaves:** *"`retry_after or DEFAULT` — please make that
`is not None`. If the server ever sends a zero we'll add a second to every retry and nothing will tell
us. I'd also add the test with `retry_after=0.0` now rather than later, because the absent case passes
under both spellings and that's the one everyone writes first."*

**The interview question:** *"What's wrong with `value or default` in Python?"* An honest answer: *"It
fires on every falsy value, not just `None`, so any field where zero or empty is a legitimate answer
gets silently replaced. I hit this on a retry client: `retry_after or ladder_wait(1)` turned a server
saying 'retry after zero seconds' into a one-second wait, and the tests all passed because the absent
case — which is the case people write tests for — behaves identically under both spellings. The fix is
`is not None`, and the general rule is that a falsy check can't distinguish 'answered with a zero' from
'not answered'. The reason I'd flag it in review rather than shrug is that there's no error and no log
line; you find it by reading, years later."*
