# 2.2 — When it is absent

## One-line answer

Not every refusal carries the number, and when it does not the ladder is all you have — the same
provider, the same window at `t=37s`, and without the header the client **gives up after 6 attempts
and 6 wasted requests**, exactly as if it had ignored one.

## The story

There is a small shop at the end of the lane that sells one particular brand of flour, and it opens
when the owner opens it.

There is no sign. There has never been a sign. Some mornings the shutter is up at seven, some days
not until eleven, and once a month it does not open at all because he has gone to the wholesaler.

The people who live nearby have all worked out the same thing without discussing it: you look on your
way past. If it is shut you carry on and look again on your way back. Nobody stands outside waiting,
and nobody has any idea when it will open, because the one person who knows has not said.

## The idea in plain language

Part [2.1](2.1-retry-after-beats-your-ladder.md) established the ordering: honour the server's number,
and fall back to the ladder. This part is the fallback arm, and it exists because a reader who has
just been told *"your ladder is a guess"* could reasonably conclude the ladder was a waste of time.

It is not. It is the only thing left when the header is absent, and the header is absent more often
than the tidy version of this story suggests:

- **The provider does not send it.** Some APIs return a 429 with no timing information at all.
- **The failure is not a refusal.** A dropped connection or a socket timeout has no headers, because
  no response arrived. Part [3.2](../03-after-the-last-retry/3.2-which-calls-are-safe-to-retry.md) is
  about how differently those have to be treated.
- **Something in between stripped it.** A proxy, a gateway, a client library that surfaces only the
  status code.

The measurement is deliberately anticlimactic, and that is what makes it worth running: with the
header absent, honouring it and ignoring it produce **the same numbers**. There is nothing to honour,
so the honouring client is running the ladder, so it behaves like the ladder.

## Why Sutra needs it

Because the four lanes in Addendum 02 are four different vendors, and whether each one sends the
header is **a page you read, not a rule you derive**. Day 69 part 3.2 made exactly this argument about
provider training terms: a claim about somebody else's service is attributable to a document and a
date, and a script that guesses is worse than one that records *unknown*.

So `sutra/backoff.py` cannot assume the header. It has to work when it is there, work when it is not,
and — this is the part people skip — **make it visible which of the two happened**, because a client
that silently falls back to guessing looks identical to one that is honouring a number.

## The mechanism

The provider carries a flag for whether it says, and the refusal carries `None` when it does not:

```python
    def call(self) -> str:
        """Make one request. Raises `Refused` until the window opens."""
        self.attempts.append(self.clock.now)
        if self.clock.now < self.opens_at:
            remaining = self.opens_at - self.clock.now
            raise Refused(429, remaining if self.says_retry_after else None)
        return "ok"
```

**Line by line:**

- `self.attempts.append(self.clock.now)` happens **before** the refusal check, so a refused request is
  still counted as having reached the provider. That is Day 70 part 5.1's rule — the provider counts
  attempts, not successes — and it is what makes `wasted()` meaningful.
- `remaining = self.opens_at - self.clock.now` is the true answer, which this simulated provider
  happens to know exactly. A real one computes something similar from its own window state.
- `remaining if self.says_retry_after else None` is the whole of this part. The same refusal, the same
  window, and the client is either told or not told.
- `Refused(429, None)` is a refusal with no timing information — **not** a refusal with a timing of
  zero. Keeping those distinct is part [2.3](2.3-zero-is-not-absent.md)'s subject and the reason the
  parameter is `float | None` rather than `float`.

Run it with the header withheld:

```bash
cd days/day-72-backoff-with-honesty/lab
uv run python retryafter.py --silent
```

**Line by line:**

- `--silent` sets `says_retry_after=False` on the provider. The client's strategy is unchanged — it
  still *wants* to honour the header; there simply is not one.

Measured on 2026-09-06:

```text
window opens at t=37s   retry-after: absent   strategy: honour retry-after

  outcome           gave up
  attempts made     6
  caller waited     23s
  wasted requests   6

  nothing to honour, so the ladder is the only option - and it is a guess
```

Put the three runs of this section side by side, because the shape of the table is the argument:

| Run | Header | Strategy | Outcome | Attempts | Wasted |
| --- | --- | --- | --- | --- | --- |
| `retryafter.py` | present | honour | **ok** | 2 | 1 |
| `retryafter.py --ladder` | present | ignore | gave up | 6 | 6 |
| `retryafter.py --silent` | absent | honour | gave up | 6 | 6 |

**Rows two and three are identical**, and they got there for opposite reasons — one client threw the
information away, the other never had it. From the outside, and from any metric you are likely to
have, those two runs are indistinguishable. That is the finding: *a client that is guessing looks the
same whether or not it had to be.*

Which is why the sensible thing to record is not just the wait but **where the wait came from**. One
extra field — `source: "header"` or `source: "ladder"` — turns "we retried" into "we retried
according to what the server told us", and makes the third row above visible in production instead of
invisible.

## When it breaks

The ladder in the absent case is doing something subtly harder than the ladder in section 1, and it is
worth naming.

In section 1 the provider never said anything, so the ladder was the policy from the start. Here the
client is *hoping* for a header and falling back. If the provider sends the header on some responses
and not others — which happens, because different tiers of infrastructure answer different requests —
then the client's behaviour alternates between exact and guessed with nothing marking the boundary.
The retry pattern in the logs looks erratic, and the explanation is not in your code.

There is a second, quieter failure: **assuming absence means "retry immediately"**. A refusal with no
guidance is not permission to hammer; it is the absence of guidance, and the correct response is the
ladder's first rung rather than zero. That is the same confusion part
[2.3](2.3-zero-is-not-absent.md) measures from the other direction, and it is why the fallback lives
in an `else` branch rather than in a default value.

## In production

**Find out, per provider, and write it down.** Which of your vendors sends `Retry-After`, in which
form, and on which status codes, is four facts per vendor, and none of them is derivable — they are
read off a page on a date. Day 69's `terms.py` is the pattern worth copying: a table in the repository
recording what was read and when, with a command that prints the URLs to re-check, rather than a live
fetch that tells you what is true now while the code around it was written then.

**What degrades at scale.** Header support changes without notice, in both directions. A provider adds
`Retry-After` and your client keeps guessing because nobody noticed; or a proxy is introduced in front
of your service and strips it, and your carefully-honoured policy silently becomes a ladder. Both are
invisible unless the source of each wait is recorded, which is the one-line change above.

**What a professional does with the fallback path.** Treats it as the degraded mode it is. If the ratio
of ladder-waits to header-waits moves, something changed — a provider, a proxy, a library version — and
that ratio is a better early-warning signal than the retry count, because it moves *before* the retry
count does.

**The review comment a senior engineer leaves:** *"The fallback is right. Add the source of the wait to
the log line — `header` or `ladder` — because right now a run where we honoured a 37-second header and
a run where we guessed our way to giving up produce the same shaped output, and I want to be able to
tell those apart at three in the morning. And put the per-provider table somewhere in the repo with the
date it was read; I don't want to find out from an incident that one of them started sending a header
we've been ignoring."*

**The interview question:** *"What do you do when a 429 has no `Retry-After`?"* An honest answer: *"Fall
back to the backoff ladder, which is the only thing left — but record that you fell back. On the
provider I measured, honouring a present header took two attempts; with the header withheld the same
client gave up after six, identical to a client that had ignored a header that was there. Those two
failures look the same from outside and have completely different causes, so I'd log the source of
each wait. I'd also be careful not to read 'no header' as 'retry now' — absence of guidance isn't
permission, so the fallback is the ladder's first rung, not zero. And which of your providers sends it
is a page you read on a date, not something you can derive, so it belongs in a table in the repo."*
