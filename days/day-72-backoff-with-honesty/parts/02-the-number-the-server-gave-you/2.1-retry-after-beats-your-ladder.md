# 2.1 — `retry-after` beats your ladder

## One-line answer

Against the identical provider, honouring the server's own number finishes in **2 attempts with 1
wasted request**, while ignoring it and running the ladder instead **gives up after 6 attempts and 6
wasted requests** — because your ladder is a guess at a number the server already told you.

## The story

You go to the health centre without an appointment because your daughter has a rash and you want
somebody to look at it today.

The receptionist checks the screen and says: *"Doctor Rao is doing her rounds, she'll be back at
quarter past three. Come back then and I'll fit you in."*

You could ignore that. You could sit down and go up to the desk every ten minutes to ask whether she
is back yet, and the answer would be no, no, no, no, and eventually yes. Nobody would stop you. The
receptionist would be slightly less pleased with you each time.

But she told you quarter past three. She is not guessing — she has the rota on the screen in front of
her. Every trip to the desk before then is you re-asking a question that has already been answered,
by the one person in the building who actually knows.

## The idea in plain language

Section 1 built a ladder because the provider said nothing. This section is about the far more common
case, and it changes the whole shape of the problem.

**A `retry-after` is not advice.** It is not the server being polite, and it is not a hint about how
busy things are. It is the server stating **when its own window opens** — a fact it holds and you do
not. Everything in section 1 is an attempt to estimate that fact from outside.

Once you see it that way, the ordering falls out on its own:

| | What it is | How good it can be |
| --- | --- | --- |
| `retry-after` | the server's statement about its own state | exact |
| your ladder | a search over the space of possible answers | as good as your guess |

So the rule is one line, and it is not *"use backoff"*: **honour the server's number when it gives
one, and fall back to the ladder when it does not.** The ladder is the contingency, not the policy.

The measurement below is set up with an ordinary window and an ordinary ladder. It opens at `t=37s`,
and part [1.2](../01-the-ladder/1.2-the-ladder-measured.md) measured a six-attempt ladder as reaching
`t=23s` — so the window is a little beyond the ladder's reach. Neither number was chosen to be
unfair. That is the point: a perfectly ordinary window defeats a perfectly ordinary ladder, while the
server was willing to say the answer the whole time.

## Why Sutra needs it

Because Day 70's `_lane.Refused` already carries `retry_after`, and Day 70 part 4.1 already argued
that a 429 is an instruction with a time in it. What that day did with the number was mark a **lane**
cold. What this day does with it is decide a **caller's** wait, and those are two different consumers
of the same field.

There is also a budget consequence that Addendum 02 makes sharp. Every wasted request is a request
counted against the free tier that could never have succeeded — Day 70 part 5.1's whole subject. The
run below spends 1 instead of 6, which is not a latency optimisation; it is five requests of daily
quota that stay available for a customer.

## The mechanism

The entire policy is one branch:

```python
        except Refused as refusal:
            if attempt == MAX_ATTEMPTS:
                break
            if honour and refusal.retry_after is not None:
                clock.sleep(refusal.retry_after)
            else:
                clock.sleep(ladder_wait(attempt))
```

**Line by line:**

- `refusal.retry_after is not None` is the test, and it is `is not None` rather than a truthiness
  check for a reason that gets its own part — [2.3](2.3-zero-is-not-absent.md). A stated zero is a
  number; a missing header is not.
- `clock.sleep(refusal.retry_after)` waits exactly as long as the server asked. Not a fraction of it,
  not the maximum of it and your ladder — the number, as given.
- The `else` branch is section 1's ladder, and its position in this `if` is the whole design: it runs
  **only** when there was nothing to honour.
- `honour` is a flag here purely so the two arms can be compared in one script. In real code there is
  no flag; there is the header or there is not.

Honour it:

```bash
cd days/day-72-backoff-with-honesty/lab
uv run python retryafter.py
```

**Line by line:**

- `cd` first: the lab's scripts import their siblings by plain name.
- No flag means honour the header. The provider's window opens at `t=37s` and it does say when.

Measured on 2026-09-06:

```text
window opens at t=37s   retry-after: present   strategy: honour retry-after

  outcome           ok
  attempts made     2
  caller waited     37s
  wasted requests   1

  one refusal was enough: the server said when, and the client believed it
```

Now ignore it, and run the ladder against the same provider:

```bash
uv run python retryafter.py --ladder
```

**Line by line:**

- `--ladder` flips `honour` to false. The header is still sent; the client simply does not read it.

Measured on 2026-09-06:

```text
window opens at t=37s   retry-after: present   strategy: ignore it, use 1-2-4-8

  outcome           gave up
  attempts made     6
  caller waited     23s
  wasted requests   6

  the header was there and was ignored; every extra attempt was avoidable
```

**One refusal was enough.** The client asked once, was told to come back in 37 seconds, came back in
37 seconds, and got its answer. Two attempts, one of them wasted.

The ladder made six attempts, wasted all six, and **still failed** — it ran out of budget at `t=23s`
against a window that opened at 37. Every one of those five extra requests was avoidable in the
strongest possible sense: the information needed to avoid them arrived attached to the first refusal.

Notice the row that looks like the ladder winning. `caller waited` is **23s for the ladder and 37s for
honouring the header**, so on wall-clock time the ladder "finished" sooner. It finished sooner by
giving up. Comparing elapsed time between a run that succeeded and a run that failed is comparing
nothing, and it is exactly the comparison a latency dashboard makes by default — which is part
[5.2](../05-in-production/5.2-what-to-alert-on.md)'s subject.

## When it breaks

**A server can be wrong, and some are wrong in a specific direction.** A `retry-after` is the
server's estimate of its own future, and under load that estimate can be optimistic — you come back
when told and are refused again. That is not a reason to ignore it; it is a reason to treat it as a
**floor** rather than a promise. Honour the number, and if the next attempt is also refused, honour
the new number, which will be larger. The client that gets into trouble is the one that treats a
second refusal as evidence the header is useless and reverts to guessing.

**A hostile or broken server can send an enormous one.** Nothing stops a header saying 86400, and a
client that sleeps for a day inside a request handler has been taken out of service by a string. The
sensible shape is to honour the number **up to a ceiling you own**, and to treat anything above that
ceiling as an escalation rather than a wait — which is section 3's line, arriving early. That ceiling
belongs next to the two limits part [1.3](../01-the-ladder/1.3-the-last-rung.md) argued for.

**And the header may be attached to something that is not a 429.** A 503 with a `retry-after` is a
server saying it is down and will be back; a 429 with one is a quota window. Both are worth honouring
and they mean different things for what you should do *instead* while waiting — Day 70's router would
send the 429 elsewhere and has no other lane for a total outage.

## In production

**Where the number actually lives.** In HTTP it is the `Retry-After` header, and it comes in two
forms — a number of seconds, or an HTTP date. Client libraries differ in whether they parse both, and
a client that handles only the integer form silently falls back to guessing against any server that
sends the date form. That is a one-line bug with no error message, and the way to find it is to log
what you parsed rather than what you received.

**What degrades at scale.** The header is per-response and your policy is per-process. With Day 70's
router in front, several lanes can each be cold with different `retry_after` values at once, and the
useful question stops being *when may I retry this lane* and becomes *which lane opens soonest* —
which is exactly the `soonest` field Day 70 part 4.3 put on its `AllDry` exception. A caller-side
ladder that ignores the router's view will sleep on a lane while another one is open.

**The failure mode that only appears with real traffic.** Everybody honours the same number. If a
provider refuses a thousand clients at once and tells them all to come back in 37 seconds, they all
come back at 37 seconds, and the header has synchronised the herd more precisely than any ladder
would have — this is part [4.1](../04-everyone-at-once/4.1-the-herd.md)'s finding with the volume
turned up. Honouring `retry-after` and adding jitter are not alternatives; the second is required
*because* the first works.

**The review comment a senior engineer leaves:** *"Good — but honour it as a floor, not a target, and
put a ceiling on it. Right now a server sending `Retry-After: 3600` parks a worker for an hour inside
a request. Cap it at whatever our deadline allows and escalate above that. Also please log the parsed
value next to the raw header: half the bugs in this area are a client that only handles the integer
form and quietly guesses whenever it sees a date."*

**The interview question:** *"When would you not use exponential backoff?"* An honest answer: *"Whenever
the server tells you when to come back. A `retry-after` is the server stating a fact about its own
window, and a backoff ladder is my estimate of that same fact — so the ladder is the fallback, not the
policy. I measured the difference on the same provider: honouring the header took two attempts and one
wasted request; ignoring it and running 1-2-4-8 made six attempts, wasted all six, and still failed
because the budget ran out before the window opened. The subtlety is that the failing run looked
*faster* on elapsed time — it gave up at twenty-three seconds while the successful one waited
thirty-seven — so if you're watching a latency dashboard the wrong strategy looks better. And I'd add
two guards: treat the number as a floor rather than a promise, and cap it, because nothing stops a
server sending an hour."*
