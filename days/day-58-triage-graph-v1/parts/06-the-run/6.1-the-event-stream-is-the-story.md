# 6.1 — The event stream is the story

## One-line answer

A run is finished when you can **account for it**, and the account is the event stream: twelve lines,
in order, each naming the station that produced it and what it emitted — and if a station did work
that the stream cannot show, the station did not do it.

## The story

A cricket match is recorded ball by ball. Not the score at the end — every delivery, in order, with
who bowled it, who faced it, and what happened.

Somebody who arrives after the match can read that record and reconstruct the whole afternoon. They
can see that the middle order collapsed in eleven deliveries. They can see that a bowler was taken
off after two expensive overs and brought back later. They can see the delivery on which the game
turned.

The final score cannot tell them any of that. The score is one number and it is true, and it answers
exactly one question. Everything anybody actually wants to know about a match — why it went that way,
what to do differently — lives in the sequence, not the total.

And there is a discipline in that record that is easy to overlook: **a ball that was bowled is
written down**. Not summarised, not inferred from the score changing. If the record does not have
it, the argument afterwards has nowhere to go.

## The idea in plain language

Every station in an ADK graph emits an **event** when it runs. The runtime yields those events as
they happen, and collected in order they are the complete narrative of one run.

Three fields make the narrative readable, and this floor uses all three:

- **`node_info.path`** — the full address of the station inside the graph, including nesting and an
  execution counter: `triage_graph_v1@1/draft_review_box@1/writer@2`.
- **`output`** — what the station produced. The baton
  ([1.2](../01-the-floor/1.2-the-baton-has-a-declared-shape.md)).
- **`actions.route`** — the branch it chose, when it chose one
  ([2.2](../02-the-guess/2.2-the-route-is-an-action.md)).

The claim of this part, and of ADK-42 generally, is that **the stream is the primary artefact of a
run**, not a debugging aid. A pipeline that returns an answer and no account of how it got there has
produced something you cannot review, cannot explain to a customer, and cannot compare against
yesterday.

There is one rule that follows from taking the stream seriously, and it is worth stating as a rule
because it is the thing people quietly break: **if a station did something and the stream cannot show
it, the station did not do it.** A station that mutates state and emits nothing has done work that
did not happen, as far as any operator, trace or audit is concerned. That is also trap #3 from the
plan's §5.1 — a node that buffers its events and returns them at the end emits nothing until it is
finished, which destroys ordering and the ability to watch a run in progress.

## Why Sutra needs it

Day 84 wires OpenTelemetry across the app, and a trace is this stream with timing attached. Day 79
onwards builds evals, and an eval that scores only the final answer cannot tell a run that got the
right reply for the right reason from one that got it by accident.

More immediately, [7.1](../07-acceptance/7.1-every-part-passed.md) makes the case that acceptance is
a statement about a whole run rather than about a station. Every one of those statements is checked
against either this stream or the register in [6.2](6.2-state-is-the-case-file.md).

## The mechanism

```python
    for i, event in enumerate(run.events, 1):
        path = (event.node_info.path if event.node_info else "") or "-"
        route = (event.actions.route if event.actions else None) or "-"
        out = event.output
        text = out if isinstance(out, str) else repr(out)
        print(f"  {i:>2}  {path:<46} {route:<10} {text[:44]}")
```

**Line by line:**

- `enumerate(run.events, 1)` numbers the events from one. The number is not in the event; ordering is
  a property of the stream, and printing the index makes "the eighth event" a thing two people can
  talk about.
- `event.node_info.path if event.node_info else ""` guards because `node_info` can be absent — the
  workflow's own terminal event has none, which [1.2](../01-the-floor/1.2-the-baton-has-a-declared-shape.md)
  showed when a run died at a seam.
- The **full** path is printed rather than the leaf. Every other script in this lab trims it to the
  station name; this one does not, because the nesting and the `@n` counter are the story.
- `out if isinstance(out, str) else repr(out)` prints strings as themselves and everything else as
  its representation, so a `TriageResult` shows its fields rather than an object address.
- `text[:44]` truncates for the table. That is a display choice and it is a real limitation: the
  stream is being made readable at the cost of being complete, and a production reader must not do
  this to the data it stores.

Read it as a paragraph and it says: the ticket was found and the mouth let it through; the classifier
called it an authentication problem of severity two and sent it down the handling lane; two clerks
searched in parallel and one found a past ticket by meaning while the other found KB-104 by words;

the fix; a second draft was written; the critic approved it; the box packaged the result; the floor
stamped it.

Nobody had to read the source to know that. **That is the deliverable of ADK-42**, and it is worth
being explicit that the paragraph above was written from the twelve lines alone.

Four details in the stream are doing work that is easy to skip past.

**Event 8 names its reason.** `REVISE: ['names the fix']` — not "rejected", not a score. When a run is
investigated in three weeks, the difference between a stream that records *what* was decided and one
that records *why* is the difference between an answer and a shrug.

**Events 7 and 9 are `writer@1` and `writer@2`.** The loop is legible without a counter of its own,
because the runtime numbers each execution. Anything that needs to know how many rounds happened can
count, rather than trusting a field somebody remembered to increment.

**Event 5 shows the join's dict with `kb_clerk` first**, although `archive_clerk` produced event 3.
The clerks run concurrently and the join's record is built as they complete, so key order follows
completion rather than declaration — the instability
[3.2](../03-the-research-floor/3.2-the-join-hands-over-a-dict.md) warned about, visible in the
stream.

**The route column is empty for seven of twelve stations.** Most stations do not branch, and the
blanks are as informative as the labels: exactly two stations on this floor make routing decisions,
and both of them are in the top half.

run *finished*; it did not stop.

## When it breaks

The stream's characteristic failure is that it looks fine when the run did not finish. Compare these
two endings:

- A run that ended at `finalize` — twelve events, terminal station, complete.
- A run whose last event came from the workflow itself with `output: None`, because a station raised
  and the exception is on its way up.

[1.2](../01-the-floor/1.2-the-baton-has-a-declared-shape.md) showed the second one. Its stream is not
obviously broken; there are events, they are in order, and the last one exists. Code that checks
"did we get events?" or "what was the last output?" cannot tell the two apart.

The useful assertion is therefore not about the *number* of events or the *presence* of a final one.
It is: **did the run end at one of the graph's terminal stations?**
[5.1](../05-the-graph/5.1-the-edge-list-is-the-floor-plan.md) read those off the printed graph —
`no_such_ticket`, `escalate_lane`, `finalize` — and that list is what
[7.2](../07-acceptance/7.2-the-gate-that-goes-red.md) checks against.

The second break has no error text either, and it is trap #3. A station written like this:

```python
def buffering_station(node_input: str) -> Event:
    """Wrong on this runtime: collect everything, return at the end."""
    collected = []
    for item in work(node_input):
        collected.append(item)
    return Event(author="buffering_station", output=collected)
```

**Line by line:**

- `collected.append(item)` accumulates instead of yielding. Nothing is visible to anyone until the
  loop finishes.
- The single `return` at the end emits one event for what may have been a long piece of work.
- The 1.x habit this comes from is real and reasonable: custom agents used to collect events into a
  list and return them. In 2.x, nodes **yield** as they go, and this shape breaks streaming and
  ordering guarantees.

The consequence is that the run's story acquires a gap. An operator watching a live run sees nothing
for the whole duration of that station, and a run killed in the middle of it — which is precisely
what Day 65 does on purpose — leaves no record that it was ever there.

## In production

**What a professional writes instead.** The stream is not printed, it is **emitted**: each event
becomes a span in a trace, with the node path as the span name and the timing attached. Day 84 wires
that with one plugin. The reason to do it that way rather than logging is that a trace preserves the
parent-child structure the path already encodes, so `draft_review_box/critic@2` nests under the box
rather than sitting beside it in a flat log.

They also record the stream **whole**, not truncated. The 44-character cut in the script above is
right for a table on a terminal and wrong for storage: the one time you need event 9's full text is
the incident where the reply was wrong, and that is exactly when it has been trimmed away.

**What degrades at scale.** Volume. Twelve events per run at any real ticket rate is a lot of rows,
and most of them are never read. The production compromise is usually sampling — keep every event for
a small percentage of runs and for every run that failed or was flagged — which works, and the trap
in it is that the sample is chosen before you know what you will want to investigate. Keeping
everything for flagged runs ([4.2](../04-the-box/4.2-the-brake-belongs-to-the-critic.md)) is the
version of this that pays for itself.

**The failure mode that only appears with real traffic.** The stream contains customer text. Look at
event 1: the whole ticket, in the output. Every event of every run, in your log store, searchable by
whoever has access. Day 69 has to answer for that, and the answer is easier if the events carry
identifiers and lengths rather than bodies — which is a decision made here, in what a station puts in
its `output`, not later in the logging configuration.

**The review comment a senior engineer leaves:** *"This test asserts the run produced twelve events.
That will break the next time anybody adds a station, and it does not actually check the thing you
care about. Assert that the run ended at a terminal node and that the sequence contains classify
followed by finalize — the count is incidental."*

**The interview question:** *"How do you debug a multi-step agent run?"* The answer that shows you
have done it at three in the morning: *"I read the event stream, which on this runtime is one event
per station with the full node path, the output and the route. The path carries the nesting and an
execution counter, so a loop reads as `writer@1`, `critic@1`, `writer@2`, `critic@2` and I can see
how many rounds happened and why each one was sent back — our critic emits the failed rubric items,
not a score. The thing I check first is not the final answer, it is which station the run ended at.
A run that died at a seam still produces events in order with a final one, so 'did we get output' and
'did it finish' are different questions, and only the second one is worth asking."*
