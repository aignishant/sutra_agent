# 1.3 — Who ends the call

## One-line answer

The model finishing is not the session ending, and — measured — **closing the request queue is not
the session ending either**: the runtime hangs up on the model, and the `async for` is still waiting
when a 2.0s deadline stops it. What ends a session is the consumer closing the event stream.

## The story

You are at somebody's front door and the conversation is over.

*"Right, well."* — *"Yes, anyway."* — *"I'd better let you go."* — *"No, no, you get off."* And
neither of you moves. There is nothing left to say and you both know it, and the thing that has not
happened is not the end of the conversation. That happened several sentences ago. What has not
happened is somebody actually turning round and walking to the car.

Nobody is being rude and nothing is going wrong. It is simply that *having nothing left to say* and
*leaving* are two different acts, and only the second one ends the visit.

## The idea in plain language

`run_async` — every agent call in this repository before yesterday — ends by itself. You hand it a
message, it yields events, and when the model has finished it stops. The end of the work is the end
of the call, because a request is a thing with a size.

An open line has no size. The model finishing a sentence is a fact about the sentence. The connection
is still there, the caller might say something else, and the runtime has no opinion about whether the
conversation is over — because it cannot have one. Only the parties know.

So there are three separate things that could each be called "ending", and a voice endpoint has to do
the right ones in the right order:

| Act | Who does it | What it ends |
| --- | --- | --- |
| `turn_complete` arrives | the model | this sentence |
| `LiveRequestQueue.close()` | you | the *input*: the runtime stops reading, and hangs up on the model |
| closing the event stream | you | the session |

The middle row is the one people stop at, and it is the trap. Closing the queue looks like hanging up
— it *is* the hang-up as far as the model is concerned — and it leaves your own loop exactly where it
was.

## Why Sutra needs it

Because the build brief asks for `call(...)` in `sutra/voice.py` and the gate spends a check reading
its source for `aclose`. That is a crude test and the hub says so, but a `call` that never closes the
stream cannot be ending its sessions, and the consequence is not a wrong answer — it is a resource
held open per caller, which is part
[4.2](../04-what-it-costs/4.2-the-session-that-never-ended.md)'s subject.

It also matters because this is the first thing in the curriculum whose failure is *nothing
happening*. Day 73 part 3.3 made the general argument — absence is not a signal — and this is the same
shape at the scale of a single function: a session that has not ended emits no error, logs nothing,
and looks from the outside exactly like a session where somebody is thinking.

## The mechanism

The runtime's side of the hang-up is two lines, in ADK's live flow. Quoted from
`google/adk/flows/llm_flows/base_llm_flow.py` in `google-adk==2.7.1` as installed on 2026-09-06, at
the package's own two-space indentation:

```text
      if live_request.close:
        await llm_connection.close()
        return
```

That is what `LiveRequestQueue.close()` reaches. It closes the model connection and returns from the
loop that reads your input — so after it, nothing is listening for anything you might send, and the
model has been told the call is over. Everything a reasonable person would call "hanging up" has
happened.

Now the caller's side, from `lab/session.py`:

```python
    async def consume() -> None:
        async for event in stream:
            log.append("turn_complete" if event.turn_complete else "chunk")
            if not event.turn_complete:
                continue
            if close_queue:
                queue.close()
            if close_stream:
                await stream.aclose()
                break
```

**Line by line:**

- `async for event in stream` holds the session open for as long as it is running. The generator is
  the session, from the consumer's point of view — which is the fact this whole part turns on.
- `if not event.turn_complete: continue` — chunks are ignored here because this part is about
  lifetime rather than content. The only event that prompts a decision is the one that says the model
  has stopped talking.
- `queue.close()` is the middle row of the table. It is a synchronous call on the queue, and what it
  does is put a `LiveRequest` with `close` set into the queue for the runtime to find.
- `await stream.aclose()` is the bottom row: closing the async generator, which is what a web
  framework does when its client disconnects. Day 74 part 5.1 used the same call for the same reason.
- `break` leaves the loop. On its own it would abandon the generator rather than close it, at a time
  chosen by the garbage collector; `aclose()` first is what makes the ending deliberate.

Run all three arms:

```bash
cd days/day-75-the-bidi-voice-loop/lab
uv run python session.py; echo "exit: $?"
uv run python session.py --queue-only; echo "exit: $?"
uv run python session.py --hang; echo "exit: $?"
```

**Line by line:**

- No flag closes both the queue and the stream. `--queue-only` closes the queue and keeps listening.
  `--hang` does nothing at all.
- Every arm carries the same deadline, so the three runs differ only in what the caller closed.

Measured on 2026-09-06. Closing both:

```text
on turn_complete, the caller closed: the queue and the stream

  events received            7
  turn_complete seen         yes
  the loop ended             yes

  the events, in order: ['chunk', 'chunk', 'chunk', 'chunk', 'chunk', 'chunk', 'turn_complete']

  The turn ended and the session ended, and those were two separate acts. Only the
  first one came from the model.
```

Closing only the queue:

```text
on turn_complete, the caller closed: the queue only

  events received            7
  turn_complete seen         yes
  the loop ended             NO - deadline at 2.0s

  the events, in order: ['chunk', 'chunk', 'chunk', 'chunk', 'chunk', 'chunk', 'turn_complete']

  The queue was closed, so the runtime stopped reading input and hung up on the
  model - and the event stream kept waiting anyway. Closing the input is not
  closing the session.
```

Closing nothing:

```text
on turn_complete, the caller closed: nothing

  events received            7
  turn_complete seen         yes
  the loop ended             NO - deadline at 2.0s

  the events, in order: ['chunk', 'chunk', 'chunk', 'chunk', 'chunk', 'chunk', 'turn_complete']

  Nothing was closed, so nothing ended. The connection is open, the model has
  nothing to say, and this is what a phone call sounds like between sentences.
```

| | closed both | closed the queue | closed nothing |
| --- | --- | --- | --- |
| events received | 7 | 7 | 7 |
| `turn_complete` seen | yes | yes | yes |
| the loop ended | **yes** | no | no |
| exit code | 0 | 1 | 1 |

**The first three rows are identical.** Every arm got the same seven events, and every arm saw the
model say it had finished. Nothing in what the model did distinguishes the run that ended cleanly from
the two that did not, which is exactly why this is worth a part: the difference is entirely on your
side of the connection, and it is invisible in the event stream.

**And the middle column is the surprise.** The queue was closed, the runtime returned from its input
loop, the model connection was closed — and the consumer's `async for` was still sitting there when
the deadline fired. Doing the thing that reads like hanging up leaves you holding the line.

## When it breaks

**This is a measurement, not a specification.** What was measured is `google-adk==2.7.1`,
`InMemoryRunner`, and a scripted `BaseLlmConnection` whose `receive()` ends when `close()` is called.
A different runner, a different session service or a real model connection could behave differently in
detail, and the honest instruction is to run the three arms against your own stack before relying on
any of it. What does **not** depend on the version is the design conclusion, because it follows from
the shape rather than from the code: a session with no natural size can only be ended by a party who
knows the conversation is over, and the framework is not one of those parties.

**The deadline is doing real work in this lab and must not be mistaken for the finding.** Each script
gives up after 2.0 seconds and reports that it gave up. Without it, two of the three arms would hang
for ever and the day would have no output at all — and a reader who removed the deadline to "see what
really happens" would find out, slowly.

**The failure this produces in a real service has no error text**, which is why *When it breaks* has
no traceback to quote. The endpoint works. Calls are answered, answers are given, callers hang up
happily. What accumulates is sessions that nobody closed, and the first symptom is a resource limit
somewhere unrelated — file descriptors, memory, a connection pool — reported by a component that has
nothing to do with voice.

## In production

**Where the lifetime actually lives.** In a web service the client's connection is the natural owner:
when the socket goes away, close the stream. That covers the common case and not the important one — a
caller who says nothing and never disconnects, which is a browser tab left open on a train. So there
are two ends to own, and a service that only handles the disconnect has handled the polite half.

**What a professional writes.** A single function that owns the whole session, with the closes in a
`finally` so they happen whether the call ended, raised, or was cancelled — and a deadline in the same
place. The build brief asks for exactly that shape and the reason is that a session's ending is the
kind of thing that gets handled in three places, differently, none of them covering cancellation.

**What changes at scale.** One leaked session is invisible. The failure arrives as a slope rather than
an event: sessions opened per hour minus sessions closed per hour, a number nobody is graphing,
compounding until something unrelated falls over. The metric worth having is that difference, and it
costs one counter at each end.

**What this shares with the rest of the phase.** Day 73's nightly job could stop running and produce no
signal; Day 74's reader could leave and the session would keep no record; today a session can fail to
end and nothing anywhere says so. The pattern is the same one three times: **the failures that matter
in ambient and live systems are absences**, and absences have to be measured deliberately because they
do not arrive.

**The review comment a senior engineer leaves:** *"You close the queue when the turn completes and
that's not enough — the event stream is still open, so we're holding a session per caller. Close the
generator too, put both in a `finally` so a cancelled request doesn't skip them, and give the session
a deadline. Then emit a counter for sessions opened and sessions closed; if those two numbers ever
diverge I want to know from a graph rather than from the connection pool."*

**The interview question:** *"What ends a bidirectional session?"* An honest answer: *"You do, and
that's the whole point — there's nothing about a session that has a natural size. Three things get
called ending and they're different. The model sends `turn_complete`, which ends the sentence.
Closing the request queue ends the input — in the framework I measured, the runtime stops reading and
closes the model connection, so it genuinely is the hang-up from the model's side. And neither of
those ends your loop. I measured all three arms: same seven events, same `turn_complete`, and only
the run that closed the event stream actually finished — the other two were still waiting when a
two-second deadline stopped them. So the practical rule is that the consumer owns the lifetime: close
both, in a `finally`, with a deadline, because the failure mode is a session held open by nobody and
it doesn't raise anything."*
