# 4.2 — The session that never ended

## One-line answer

Part [1.3](../01-the-open-line/1.3-who-ends-the-call.md) showed that a session ends only when the
consumer closes the event stream, and part [4.1](4.1-a-connection-per-caller.md) showed that every
session occupies a connection while it lives — put those two together and a session nobody closed
holds a connection for ever, silently, and the only thing standing between a voice service and that
outcome is a **deadline you chose**, because no event ever arrives saying "this call is over".

## The story

There is a shelf of paperbacks by the coffee machine at work. The rule, such as it is, was written
on a scrap of card years ago by somebody nobody remembers: *help yourself, just bring it back*.

You took one. You read it on the train, you enjoyed it, you meant to bring it back, and you put it
on the shelf at home so you would remember. That was three years ago. It is still there. You are not
a thief, nobody has been wronged, and if anyone asked you would hand it over that afternoon — but
nobody asks, because there is nobody whose job that is.

Look at the shelf at work and you will see the gap. One gap is nothing. But the shelf has been losing
a book at a time to people exactly like you, all of whom meant well, and the shelf is now half empty.
Every single transaction was correct. What went wrong is the arrangement: *bring it back* names an
act and never names a moment. Nothing in it ever says **now**.

The fix is not a better class of borrower. It is a date. Somebody has to write *back by the end of
the month* on the card — a number they made up, that will occasionally be wrong, and that is still
the only thing that ever turns a loan back into a book on a shelf.

## The idea in plain language

Three words, and it is worth being exact about them because the rest of this part is built out of
them.

A **session** here is one open line: the runner, the queue, the model connection and your `async for`
loop, alive together from hello to hang-up. A **deadline** is a moment you decide in advance, after
which you stop waiting no matter what is happening. A **timeout** is the machinery that enforces a
deadline — the thing that wakes up and says *that is enough*. And **occupancy** is how much of a
resource is being held right now rather than how much work is being done: the number of books off the
shelf, not the number of pages read. Part [4.1](4.1-a-connection-per-caller.md) is the part that
established occupancy as the quantity a voice service is actually sized by.

Now stack the two findings this part inherits.

From part [1.3](../01-the-open-line/1.3-who-ends-the-call.md): all three arms of `session.py`
received the same **7 events** and the same `turn_complete`. Only the arm that closed the event
stream ended. The other two were still waiting when a **2.0s** deadline stopped them, and exited
`1`. The model finishing said nothing about the session, and closing the input queue said nothing
about the session either.

From part [4.1](4.1-a-connection-per-caller.md): a session is not a request that finishes and frees
its slot. While it lives it occupies one, and capacity is how many can be held at once.

Put the two side by side and the failure writes itself. A session that nobody closes never ends, and
a session that never ends never gives its slot back. That is a book that left the shelf and has no
due date — except that a service acquires them faster than a coffee-machine shelf does, and has no
gap to look at.

The uncomfortable part is the last step. In a request/response service you never need a rule about
this, because the request ending is a real event that genuinely happens. On an open line there is no
such event. The caller closing a laptop lid does not send anything. A phone going into a tunnel does
not send anything. Somebody who simply stops talking is indistinguishable from somebody thinking. So
a deadline here is **not a safety net stretched under a bug** — it is the mechanism. It is the only
thing in the whole system that will ever say *now*.

## Why Sutra needs it

Because the hub's §4 build brief asks for a deadline on the session in `sutra/voice.py`, sitting in
the same list as closing the stream and handling the `interrupted` event — and unlike those two, it
has no measured demonstration of its own anywhere in this day. It cannot have one. A demonstration
of a leak takes as long as the leak, and the honest version of this experiment is a service left
running for a fortnight with a graph pointed at it.

And because `lab/gate.py` spends one of its six checks on it. That check is the weakest in the file
and it is in the file anyway, for a reason this part will come to: there is a class of decision that
no test can grade, and the best you can do is refuse to let it be skipped.

## The mechanism

The deadline in this day's lab is three lines. Quoted from `lab/session.py`, dedented from its
original four-space indentation inside `drive()` so it reads at column 0:

```python
try:
    await asyncio.wait_for(consume(), timeout=DEADLINE)
    return log, True
except TimeoutError:
    return log, False
```

**Line by line:**

- `asyncio.wait_for` is the entire mechanism. There is no deadline framework, no watchdog task, no
  background sweeper — one standard-library call that runs an awaitable and cancels it if it has not
  finished in time. When people say a service "has session deadlines", this is usually all it is.
- The timeout wraps **`consume()`**, which is the whole session, rather than any single `await`
  inside it. That is the difference between a *session deadline* and a *read timeout*, and it is the
  most important line in the block. A read timeout fires when nothing has arrived for a while; here
  that would be wrong, because a caller thinking in silence is not a failure, and hanging up on
  somebody mid-thought is a bug you have shipped on purpose.
- `except TimeoutError` catches the deadline firing. Since Python 3.11 `asyncio.TimeoutError` is
  the same object as the builtin `TimeoutError`, so this one name covers both and there is nothing
  clever to remember.
- The `except` branch **returns a result** rather than re-raising. That is a deliberate statement
  about what reaching a deadline *is*: not an accident, not an exceptional condition, but
  information. The session did not end. That is a fact about the session, and facts belong in the
  return value.
- `return log, True` and `return log, False` make *did it end* a value the caller can act on. That
  is what lets `main()` print `NO - deadline at 2.0s` and exit non-zero, and it is why the hub can
  say the `--queue-only` arm exits `1`. A deadline that only wrote to a log would have proved the
  same thing and told no script about it.

`DEADLINE` itself is a module-level constant set to `2.0`. That number is not a finding. It is the
smallest value that lets the day's three arms produce output while a reader is watching, and its job
in the lab is exactly its job in production: to make a demonstration that would otherwise hang for
ever come to an end and say so.

Now the check that exists for this part, quoted from `lab/gate.py` and dedented the same way:

```python
check(
    "the session has a deadline",
    "timeout" in src or "wait_for" in src,
    "a session with no deadline is a session per caller, held open for ever; see part 4.2",
)
```

**Line by line:**

- `src` is the source text of `sutra.voice.call`, read with `inspect.getsource`. So the check is a
  **substring search over source code** — about as crude as a test can be while still being a test.
- `"timeout" in src or "wait_for" in src` passes on a comment containing the word *timeout*. It
  passes on a deadline of a fortnight. It passes on `wait_for` wrapped around one small await deep
  inside the function, which is the read timeout this part just argued against. It cannot tell a
  good deadline from a terrible one, because "good" here depends on who your callers are and what
  they are doing, and no static check has that.
- What it *can* verify is that somebody had to write one. That is the whole value, and it is not
  nothing: the failure this part describes comes from the subject never being raised, not from being
  raised and answered badly.
- This is the same argument Day 73 part 5.2 makes about its own gate — a check can confirm somebody
  wrote a function and cannot confirm they decided how it behaves — and the same shape as Day 72
  part 5.2, whose gate asserts that an escalation carries its `attempts` and `waited` fields while
  having no way to assert that anybody ever graphs them. **A gate proves a decision was made. It
  never proves the decision was made well.** The grading is a human's job, and the gate's job is to
  make sure the human is asked.

## When it breaks

**The deadline is a guess, and the wrong value is a real bug in both directions.** This is not a
detail to tune later; both directions cost something, and they cost it in different currencies.

| The deadline is | What happens | Who finds out |
| --- | --- | --- |
| too short | you hang up on a caller who was thinking, reading something out, or on hold at their end | the caller, who is annoyed and does not tell you |
| too long | a leaked session is merely slower to leak; occupancy still climbs, just with a ceiling | nobody, until the resource limit |

Read the right-hand column, because it is the trap. Cutting somebody off mid-sentence is a rudeness
your system **cannot detect** — from the inside it looks exactly like a deadline doing its job, and
the caller who gave up is not in any of your metrics. Meanwhile an over-long deadline produces no
complaint at all and quietly keeps the failure alive.

There is no correct value derivable from first principles. It depends on the length of your callers'
pauses, on whether they are reading a reference number off a letter, on whether the line is a
handset or a browser tab, and none of that is knowable in advance. The honest approach is: pick a
number, **log every single time it fires**, and use those logs to move it. What you want in the log
is enough to answer *should this one have been cut off* — the session's age, how many turns it had,
how long since the last event from the caller, and what the last thing that happened was. After a
week of real traffic, that log is the argument for whatever number you choose next. Without it you
are picking twice instead of once.

**A deadline is not the same as a silence timeout, and most real systems want both.** They bound
different things and neither substitutes for the other.

| Limit | What it bounds | What fires it | What it is for |
| --- | --- | --- | --- |
| session deadline | the whole call, from open to close | total elapsed time since the session started | a session nobody will ever close |
| silence (idle) timeout | one gap | time since the last event in either direction | a caller who has gone away mid-call |

A session deadline alone lets a caller who left the room hold a connection right up to the maximum.
A silence timeout alone lets a genuinely chatty session — or a stuck loop that keeps emitting
chunks — run for ever, because something is always arriving. The pair covers both, and the pair is
two numbers to choose rather than one.

**This failure has no error text**, which is why this part quotes no traceback. There is nothing to
quote. Every call works. The model answers, the caller is happy, the logs are clean, the tests pass,
and each individual request is correct. What accumulates is *occupancy* — the gap on the shelf,
widening a book at a time — and the first symptom appears somewhere with no obvious connection to
voice: a connection pool exhausted, file descriptors gone, memory climbing on a host, an unrelated
service failing to open a socket.

That is Day 73 part 3.3's argument arriving in a new place. That part showed that a nightly job which
stops running produces **nothing** to look at, so absence has to be measured deliberately because it
never announces itself. Here the absent thing is not a run — it is a close. A session that was never
ended emits no event saying it was not ended, for the same structural reason: the code that would
have reported it is in the path that did not execute. Part 1.3 made this point about a single
function; Day 73 made it about a whole process; this is the same shape at the level of a service's
capacity.

## In production

**Two counters make it visible before it bites.** Count sessions opened. Count sessions closed. The
metric is neither of those numbers — it is **their difference**, and it is a single number that
should stay flat. Flat means every session that started has finished. A slow upward drift is the leak,
visible as a slope long before anything falls over, and it is readable at a glance in a way that
"connections in use" is not, because that number moves for honest reasons too. Two counters and one
subtraction is the entire instrument, and it costs one line at each end of the session.

**The closes belong in a `finally`.** Not at the bottom of the happy path, and not in three places
that each handle one case. A voice session ends by completing, by raising, or by being cancelled —
and cancellation is the one people forget, which is unfortunate because a deadline firing *is* a
cancellation. Put the closes and the counter increment in a `finally` and all three routes out of the
function go through the same code. This is the shape the hub's build brief asks for, and it is the
same instruction part 1.3 already gave for closing the stream: one function owns the session, and its
ending lives in one place.

**A service can be entirely correct on every call and still fall over from this.** That is the fact
worth carrying out of this part. There is no failing test to write, because the bug is not in any
call — it is in the relationship between the calls and time. Every individual session did what it was
asked. The service died of how many of them there were, at once, still open. Correctness per request
is simply the wrong lens for a system whose resource is occupancy, and part
[4.1](4.1-a-connection-per-caller.md) is where that lens got swapped.

**The review comment a senior engineer leaves:** *"There's no deadline on the session, so `call` will
wait for as long as whatever is on the other end feels like existing — and the thing on the other end
is a browser tab, so that's for ever. Wrap the whole consume in a `wait_for`, not one await inside
it, because somebody pausing to think isn't a failure and I don't want us hanging up on people
mid-sentence. Pick a number, I don't mind which, but log it every time it fires with the session age
and the last event so we can argue about the number with data in a fortnight. Add an idle timeout as
well — the two catch different things. And put the closes and a sessions-closed counter in a
`finally`, because a deadline firing is a cancellation and that's exactly the path that skips your
cleanup. Then graph opened minus closed. That number should be flat, and if it isn't I want to see it
on a chart rather than in a page about the connection pool."*

**The interview question:** *"What happens to a voice session when the caller just closes their
laptop?"* An honest answer: *"Nothing — and that's the problem. There's no event. A request/response
service gets the request ending for free, but on an open line nothing ever arrives to say the call is
over, so the only thing that ends a session nobody closed is a deadline you chose in advance. I
measured the related half of this: same seven events and the same `turn_complete` on all three arms,
and only the arm that closed the event stream ended — the other two were still sitting there when a
two-second deadline stopped them. Combine that with the fact that each session is holding a
connection while it lives and a leaked session is a slot gone for good. What makes it nasty is that
there's no error text anywhere. Every call is correct, and what accumulates is occupancy, so the
first symptom shows up as a connection pool or file descriptors in some component that has nothing to
do with voice. So: a session deadline around the whole session rather than around one read, because
silence is normal on a phone call; separately an idle timeout, because they bound different things;
closes in a `finally` so a cancelled request doesn't skip them; and two counters, opened and closed,
because the difference between them is the one number that shows the leak as a slope instead of as an
outage. And I'd log every deadline that fires, because the value I picked is a guess and the log is
how it stops being one."*
