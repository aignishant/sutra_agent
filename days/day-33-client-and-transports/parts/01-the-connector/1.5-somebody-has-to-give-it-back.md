# 1.5 — Somebody has to give it back

## One-line answer

An `McpToolset` owns something outside your process — a child process or an HTTP client — and
`await toolset.close()` is the only thing that releases it, which is why every script in this day
puts its `get_tools()` inside a `try` and its `close()` inside the matching `finally`.

## The story

You hire a drill from the tool shop on the corner for a Saturday job.

The job takes an hour. By eleven you are finished, the shelf is up, and the drill goes into the
cupboard under the stairs because you are not going out again today. Nothing about that is a mistake
on Saturday.

On Monday you go to work. On Tuesday the cupboard is still shut. On Thursday somebody mentions the
shelf and you think, vaguely, about the drill. The shop does not ring you. There is no red light.
Nothing in your house behaves any differently, because a drill in a cupboard is exactly as quiet as
no drill at all.

Three weeks later you take it back and the man behind the counter, who is not unkind about it, adds
up three weeks.

The thing worth noticing is what made this possible. Not that you forgot — everybody forgets — but
that **forgetting was silent**. Nothing in the world changed shape to tell you. The only reason
anyone ever returns hired equipment on time is that they built a habit that does not depend on
noticing.

## The idea in plain language

Most Python objects clean themselves up. You stop referring to a list, the garbage collector notices,
the memory goes back. You never think about it, and you are right not to.

An `McpToolset` is not that kind of object, because what it holds is not memory. Over stdio it holds
a **child process**: a real operating-system process with a process id, its own memory, its own file
handles, and no idea that the Python object which started it has gone out of scope. Over Streamable
HTTP it holds an `httpx.AsyncClient` with a connection pool and open sockets. Neither of those is
reclaimed by Python's garbage collector, because neither of them is Python's to reclaim.

So the toolset has a `close()` and it is `async`:

> *"This method closes the MCP session and cleans up all associated resources. It's designed to be
> safe to call multiple times and handles cleanup errors gracefully to avoid blocking application
> shutdown."*
> — `McpToolset.close`, google-adk 2.7.1, read 2026-09-04

Three promises in that docstring, and each of them is a design decision worth naming.

**It is idempotent.** Calling it twice is safe, which means you never have to track whether you have
already closed. That is what makes it usable from a `finally` block that might run after an inner
cleanup already ran.

**It does not raise.** The implementation catches every exception from the session manager and logs
it at `WARNING` instead — *"Error during McpToolset cleanup"*. A cleanup path that throws turns a
tidy shutdown into a crash and hides the original error, so it deliberately does not.

**It clears the tool-list cache too.** The TTL cache from [1.3](1.3-before-the-model-sees-a-tool.md)
lives on the instance, so closing the toolset throws away the cached listing along with the
connection.

Who calls it depends on who owns the toolset, and there are exactly two answers:

- **Inside an agent**, ADK owns the toolset's lifetime and closes it as part of the framework's own
  shutdown. You do not call `close()` yourself, and calling it mid-run would break the agent.
- **In a script, a test, or a health check** — which is everything in this day's `lab/` — you own it,
  and nobody else is going to.

## Why Sutra needs it

Because `sutra/mcp/client.py` is a module other code imports, and a module that hands out resources
without saying who releases them produces a bug that only appears in the test suite.

Consider what Day 38's `tests/test_mcp_failures.py` is going to do: build a client against a
deliberately broken fake server, assert on the failure, and move to the next test. Do that a dozen
times without closing, and you have a dozen orphaned Python subprocesses, all still running, all
holding the port or the file the next test wants. The symptom is a test that passes alone and fails
in the suite, which is among the most expensive symptoms there is.

It also decides the shape of the three functions this day asks you to write. `connect_stdio` and
`connect_http` return something the caller must close, so their docstrings have to say so, and the
`TODO(me)` in the hub asks you to decide whether they should instead be async context managers —
`async with connect_stdio(...) as toolset:` — which would make forgetting impossible rather than
merely discouraged.

## The mechanism

The shape every script in this day uses, and the reason for each line:

```python
toolset = build(filtered=filtered, ttl=ttl)
try:
    for _ in range(rounds):
        tools = await toolset.get_tools()
        print("tools the model would see:", [tool.name for tool in tools])
finally:
    await toolset.close()
```

**Line by line:**

- `build(...)` is outside the `try`, because [1.2](1.2-constructing-is-not-connecting.md) established
  that construction cannot fail in a way that leaves a resource behind. There is nothing to clean up
  if that line raises.
- The `try` starts at the **first line that can connect**. Anything earlier in the block would be
  protected by a `finally` it does not need.
- `finally`, not `except`. The point is not to handle the error — Principle 10 says errors surface —
  it is to run the cleanup on every path out of the block, including the successful one, including a
  `return`, and including `KeyboardInterrupt`.
- `await toolset.close()` is awaited. Forgetting the `await` produces a coroutine that is never run,
  and Python's only complaint is a `RuntimeWarning: coroutine 'McpToolset.close' was never awaited`,
  which is easy to miss in a wall of output and does not change the exit code.
- There is no `except` clause at all, so an exception from `get_tools()` still propagates after the
  cleanup runs. The script exits non-zero and the traceback is intact.

The version a professional writes instead uses `contextlib.AsyncExitStack`, and the difference matters
as soon as there is more than one:

```python
import contextlib

async with contextlib.AsyncExitStack() as stack:
    tools = []
    for params in every_server:
        toolset = McpToolset(connection_params=params)
        stack.push_async_callback(toolset.close)
        tools.extend(await toolset.get_tools())
```

**Line by line:**

- `AsyncExitStack` is a stdlib object that collects cleanups and runs them all, in reverse order,
  when the `async with` block ends — on the happy path and on an exception alike.
- `push_async_callback(toolset.close)` registers the coroutine function without calling it. Note
  there are no parentheses after `close`: you are handing over the function, and the stack will
  `await` it later.
- Registering happens **immediately after construction and before the first use**, so a failure in
  `get_tools()` on the third server still closes the first two.
- `tools.extend(...)` is what an agent with several servers actually wants: one flat list of tools
  drawn from several connections. Day 40's filtering and Day 44's hardening both hang off this loop.
- The whole block is why ADK's own MCP examples talk about "properly managing the exit stack": it is
  the same stdlib type, used for the same reason.

## When it breaks

Here is the honest answer, and it is worse than an error message: in a short script, forgetting
`close()` changes **nothing you can see**. Comment out the `finally` in `lab/list_tools.py`, run it,
and you get the same tool names, the same exit code, and even the same
`[fake-desk] stdin closed, exiting` goodbye from the server — because the interpreter exiting closes
the child's stdin for you, and the operating system does the cleanup you skipped.

So the leak is invisible in exactly the shape you would test it in. The only thing you can observe
from outside is **when** the far end shuts down, and `lab/leak.py` puts both cases in one process:

```bash
uv run python days/day-33-client-and-transports/lab/leak.py
```

**Line by line:**

- It builds two toolsets against the same fake server, lists tools on both, and closes only the
  first.
- Every `print` passes `flush=True`. Without it, the parent's stdout is block-buffered when piped and
  all three lines appear at the end, which would destroy the only evidence there is.
- The server's own lines come out on stderr, unbuffered, so the two streams interleave in real order.

```text
[fake-desk] initialize
[fake-desk] initialized
[fake-desk] tools/list
[fake-desk] stdin closed, exiting
PARENT: closed the tidy toolset
[fake-desk] initialize
[fake-desk] initialized
[fake-desk] tools/list
PARENT: finished with the leaked toolset, and did not close it
PARENT: last line of my program
[fake-desk] stdin closed, exiting
```

Read the two goodbyes. The first server exits **before** the parent's next line: `close()` shut its
stdin, and it stopped, exactly as the stdio binding says it should
([2.4](../02-stdio/2.4-closing-up.md)). The second exits **after** the parent's last line — it was
alive for the whole rest of the program, doing nothing, holding a process slot, and no line of output
mentioned it.

Now imagine the parent's last line never comes, because the parent is a service.

The version that does raise is what happens when a `close()` runs at the wrong time. Close a toolset
and then use it again, and the session manager tries to re-establish a connection it has just torn
down; in an agent, where ADK is also managing that lifetime, the result is a
`ConnectionError` raised from inside a turn for no reason the user could understand. This is the
concrete reason for the rule above: **inside an agent, you do not call `close()`.** The ownership is
not shared.

The third one is the async slip:

```text
RuntimeWarning: coroutine 'McpToolset.close' was never awaited
```

That is Python telling you the cleanup was written and never ran. It is a warning, not an error, the
program exits 0, and the resource is still held. Run tests with `-W error::RuntimeWarning` once and
you will find every instance of it in an afternoon.

## In production

**What a professional writes instead:** the client module hands back an async context manager rather
than a bare object, so the correct usage is the shortest usage. If that is not possible — and inside
ADK it is not, because the framework wants a plain object it can put in `tools=[...]` — then the
module's docstring says in its first line who closes it, and there is a test that asserts the
subprocess is gone afterwards.

**What degrades at scale:** leaks are per-connection, so they scale with traffic rather than with
code size. One orphaned subprocess is nothing; a service that leaks one per conversation runs out of
process handles in a day, and the error it eventually produces is about resources rather than about
MCP — `OSError: [Errno 24] Too many open files`, or a container that gets killed for memory. Nothing
in that message points at the toolset, which is why the habit matters more than the diagnosis.

**The failure mode that only appears with real traffic:** shutdown under load. A container gets a
termination signal while forty conversations are in flight, each holding a toolset, and the cleanup
that worked perfectly in a script now has to run forty times against a runtime that is already tearing
down. This is exactly why `close()` swallows its own exceptions and logs instead: one failed cleanup
must not prevent the other thirty-nine.

**The review comment a senior engineer leaves:** *"`connect_stdio` starts a subprocess and returns it
wrapped in an object with no `__aenter__`. Every caller now has to remember a `finally`, and the one
who does not will be the test suite. Either return an async context manager, or say `caller must
await close()` in the first line of the docstring — not the fourth."*

**The interview question:** *"what happens if you never close an MCP toolset?"* The answer that shows
you have debugged it: *"Nothing, immediately, which is the problem. Over stdio the toolset owns a
child process and over HTTP it owns a connection pool, and neither is Python's to garbage collect. In
a script you leak one process. In a service you leak one per conversation and it surfaces days later
as 'too many open files', which does not mention MCP anywhere. We put every construction behind an
`AsyncExitStack` so the cleanup is registered on the line after the object exists, and we test that
the subprocess is actually gone rather than that `close()` was called."*
