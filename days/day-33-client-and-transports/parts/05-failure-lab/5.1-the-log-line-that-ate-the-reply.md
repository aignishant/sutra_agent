# 5.1 — 💥 The log line that ate the reply

## One-line answer

One `print()` in a stdio server puts non-protocol bytes on the wire, and whether that is a logged
warning you never read or a total failure depends on something nobody thinks about while writing it:
whether the text ended with a newline.

## The story

The belt at the supermarket checkout only understands one kind of thing.

Shopping goes on it, one item at a time, and the scanner at the far end reads a barcode off each one
and adds it to the bill. It has been doing that for years, and the only reason it works is that
everything on the belt is a thing with a barcode.

A man in front of you puts his car keys down on the belt while he looks for his card. Not on the
counter, not in his pocket — on the belt, because that is the flat surface in front of him and he is
thinking about the card.

The keys go through. The scanner sees something that is not a barcode, the till stops with a beep, and
the woman on the checkout picks them up, hands them back, and starts the belt again. Ten seconds.
Everyone is polite about it.

Now the same keys, but they land wedged against a loaf of bread. The scanner sees keys and bread as
one thing, reads the barcode as something it is not, and the bill has a mistake in it. Nothing beeped.
Nobody picked anything up. The queue moves on and the error is now in a receipt somebody will not read
until the weekend.

Same keys, same belt, same mistake. One of them is a ten-second interruption and the other one is
wrong data that nobody noticed, and the only difference is where the keys landed.

## The idea in plain language

[2.2](../02-stdio/2.2-one-message-per-line.md) gave the rule and
[2.3](../02-stdio/2.3-the-only-place-left-to-talk.md) gave the alternative. This part is what happens
when somebody breaks the rule, and the interesting finding is that it breaks in **two different ways**
that require completely different amounts of luck to survive.

Recall the client's reader from [2.2](../02-stdio/2.2-one-message-per-line.md): it accumulates bytes,
splits on `\n`, and tries to parse each resulting piece. When a piece will not parse it logs, sends
the exception down the stream in place of a message, and **continues**. Nothing stops.

So consider a server that writes `INFO: loading 3 tools` to stdout just before it writes a `tools/list`
reply, and consider the two ways that could go:

- **With a trailing newline** — an ordinary `print()`. The stream now contains two lines: the log
  line, then the reply. The reader splits them apart. Line one fails to parse and is logged. Line two
  parses perfectly and is delivered. **The call succeeds.**
- **Without a trailing newline** — a `sys.stdout.write` with no `\n`, or a partial write, or two
  threads writing at once. The log text and the reply are now **one line**. The reader splits and gets
  a single piece that is a log line with JSON glued on the end. It fails to parse. There is no second
  piece, because the reply was inside the one that failed. **The reply is gone, and the client waits
  for it until its timeout.**

That is the whole of this part, and it is worth stating as a principle because it generalises well
past MCP: **when a stream has a delimiter and no framing header, the damage a corrupt write does is
decided by where it lands relative to the delimiter, not by how big it is.** Twenty-one bytes destroy
a reply if they land inside one, and are a logged curiosity if they land beside it.

Which means the first version — the one that "works" — is the more dangerous of the two. It survives
development. It survives the test suite. It survives review, because the traceback in the output is
followed by a successful result and everybody reads the result. It fails the first time two writes
interleave under load, and by then the `print` is two years old.

## Why Sutra needs it

Because tomorrow you write a server, and the second thing anybody does when a server misbehaves is add
a `print` to see what is happening.

That instinct is correct everywhere else in this repository and is a bug in `sutra_mcp`. Day 34's
server has exactly one function that may write to stdout, for exactly this reason, and the reason is
not "style" — it is that stdout is the wire and there is no framing header to recover with.

It also explains a class of bug report you will get from other people's servers. "The tool works on my
machine and times out on the CI runner" is very often this: a library that prints a warning to stdout
only when it detects a non-interactive terminal, or only on first run, or only when a cache is cold.
The server is fine. Its output is not, in one environment, sometimes.

## The mechanism

Three runs of the same server, one environment variable apart. `lab/noisy_stdout.py` sets `NOISY` in
the child's environment — and note that it has to build the environment explicitly, because
[2.1](../02-stdio/2.1-connecting-is-launching.md) established that a stdio child does **not** inherit
your shell:

```python
noisy = "2" if "--glued" in sys.argv else "0" if "--quiet" in sys.argv else "1"
env = get_default_environment()
env["NOISY"] = noisy
print(f"stdout pollution mode: {noisy}")
```

**Line by line:**

- `get_default_environment()` is the MCP SDK's own allowlist builder — `PATH`, `TEMP` and the handful
  of others from [2.1](../02-stdio/2.1-connecting-is-launching.md). Starting from it and adding one
  key is the right way to pass a variable to a child; passing `{"NOISY": "1"}` alone would strip
  `PATH` and the launch would fail for an unrelated reason.
- Three modes rather than two, because the difference between mode 1 and mode 2 **is** the lesson. A
  two-mode version of this demo would teach the wrong thing.
- `NOISY` reaches the server as a string, and the server compares it as a string. There is no
  cleverness here on purpose: the switch has to be so simple that nobody suspects it of doing more
  than it does.

The server side is three lines, and they are the whole difference:

```python
if NOISY == "1":
    print("INFO: loading 3 tools")  # a whole extra line on the wire
elif NOISY == "2":
    sys.stdout.write("INFO: loading 3 tools")  # no newline: it glues onto the reply
reply(request_id, {"tools": TOOLS})
```

**Line by line:**

- `print(...)` appends `end="\n"` by default. That single implicit character is what makes mode 1
  survivable.
- `sys.stdout.write(...)` appends nothing. The next thing written to stdout is the reply, from
  `reply()`, and the two are now one line.
- Both are ordinary, plausible lines of Python. Neither looks like a protocol violation, and a
  reviewer scanning for bugs is looking at the `reply(...)` call.
- `reply()` itself is correct in both cases: it writes compact JSON and one newline. The corruption is
  entirely upstream of it, which is why "our serialiser is correct" is not a defence.

Run all three:

```bash
uv run python days/day-33-client-and-transports/lab/noisy_stdout.py --quiet
uv run python days/day-33-client-and-transports/lab/noisy_stdout.py --line
uv run python days/day-33-client-and-transports/lab/noisy_stdout.py --glued
```

**Line by line:**

- `--quiet` is the control. Same server, same client, nothing on stdout but protocol.
- `--line` is the survivable break. Run it and read the exit code as well as the output.
- `--glued` is the fatal one, and it takes the full connection timeout to fail, so it is the slow run
  of the three.

## When it breaks

**Mode 0, the control.** Everything as it should be:

```text
[fake-desk] initialize
[fake-desk] initialized
[fake-desk] tools/list
[fake-desk] stdin closed, exiting
stdout pollution mode: 0
tools: ['desk_ping', 'desk_ticket_count', 'desk_wipe_tickets']
```

**Mode 1, the whole extra line.** A traceback, and then the correct answer:

```text
[fake-desk] tools/list
Failed to parse JSONRPC message from server
Traceback (most recent call last):
  File "...\mcp\client\stdio\__init__.py", line 155, in stdout_reader
    message = types.JSONRPCMessage.model_validate_json(line)
pydantic_core._pydantic_core.ValidationError: 1 validation error for JSONRPCMessage
  Invalid JSON: expected ident at line 1 column 2 [type=json_invalid, input_value='INFO: loading 3 tools\r', input_type=str]
stdout pollution mode: 1
tools: ['desk_ping', 'desk_ticket_count', 'desk_wipe_tickets']
```

Read that carefully, because it is the most misleading output in this day. There is a full traceback
and the program **exits 0 with the right answer**. The `input_value` names the exact offending bytes —
`'INFO: loading 3 tools\r'`, with the Windows carriage return still attached — so the diagnosis is
sitting right there, above a successful result that everybody reads instead.

**Mode 2, glued.** The same twenty-one bytes, no newline:

```text
[fake-desk] tools/list
Failed to parse JSONRPC message from server
...
pydantic_core._pydantic_core.ValidationError: 1 validation error for JSONRPCMessage
  Invalid JSON: expected ident at line 1 column 2 [type=json_invalid, input_value='INFO: loading 3 tools{"j..."properties": {}}}]}}\r', input_type=str]
Exception during MCP session execution: Failed to get tools from MCP server:
...
    raise TimeoutError from exc_val
TimeoutError
...
ConnectionError: Failed to get tools from MCP server:
```

Three things to take from this.

**The `input_value` is the confession.** `'INFO: loading 3 tools{"j..."properties": {}}}]}}\r'` — the
log line with the entire `tools/list` reply welded onto it. That truncated middle is pydantic
shortening a long value, and what survives at each end is exactly enough to identify both halves.

**The visible cause is a `TimeoutError`.** The reply was destroyed at the moment it was written; the
client then waited the full connection timeout for a message that no longer existed, and reported the
waiting rather than the destruction. If you only read the last line you would go and look at the
network, or the server's speed, or the timeout value — none of which is involved.

**The final message says nothing.** `ConnectionError: Failed to get tools from MCP server:` ends with
a colon and an empty reason, because the underlying `TimeoutError` has no message text of its own.
The most-visible line in the failure is the least informative, and the useful line is nine frames
above it. Exit code is `1`.

## In production

**What a professional writes instead:** a stdio server that makes the mistake impossible rather than
discouraged. At the top of the process, `sys.stdout` is captured into a module-private handle and the
global one is repointed at `sys.stderr`, so a stray `print` anywhere — in your code, in a dependency —
lands harmlessly:

> the pattern is three lines: keep the real stdout, replace `sys.stdout` with `sys.stderr`, and write
> protocol bytes only through the kept handle.

That is worth doing because the risk is not your own `print`. It is the library you imported that
prints a banner on first use, and you will not find it by reading your own code.

**What degrades at scale:** interleaving. Mode 2 is unlikely from a single-threaded `print`, and
becomes ordinary the moment two things write to stdout concurrently — a server handling requests in
threads, or a subprocess of the server inheriting its stdout. Under load, partial writes interleave
and produce glued lines with no `print` statement anywhere in the codebase. The fix is a lock around
the one write, and it only occurs to people who know the framing cannot recover.

**The failure mode that only appears with real traffic:** the conditional print. Libraries print to
stdout on the first run of a cold cache, on a deprecation the first time a code path is hit, or when
they detect a non-interactive terminal. All three are rare, environment-dependent and invisible in
development. You get one corrupted call in ten thousand, on one machine, and the traceback blames a
timeout.

**The review comment a senior engineer leaves:** *"there is a `print` in the tool handler. On a stdio
server that is the protocol channel — today it will produce a parse error the client logs and ignores,
and the day it lands mid-write it will silently eat a reply and we will debug it as a timeout. Send it
to `stderr`, and repoint `sys.stdout` at startup so the next one cannot happen."*

**The interview question:** *"what happens if an MCP stdio server prints to stdout?"* This is the
question where the two-case answer marks you out: *"It depends entirely on the newline, which is the
uncomfortable part. If the text ends with one, it is its own line: the client's reader fails to parse
it, logs `Failed to parse JSONRPC message from server`, and carries on — the real reply is the next
line and the call succeeds. If it does not end with a newline, it glues onto the front of the reply,
the whole thing fails to parse, and the reply is gone; the client then times out and reports a
`ConnectionError` with an empty reason, so you debug it as a network problem. The first case is more
dangerous, because it survives every test you have and becomes the second case under concurrency. We
repoint `sys.stdout` at `stderr` at server startup and write protocol bytes through a kept handle, so
a stray print from a dependency cannot reach the wire."*
