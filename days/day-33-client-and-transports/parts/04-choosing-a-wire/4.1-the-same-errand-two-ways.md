# 4.1 — The same errand, two ways to run it

## One-line answer

Because protocol semantics are identical on every transport, choosing between stdio and Streamable
HTTP is an **operational** decision and never a functional one — and in ADK it is one class name, so
the choice must be made on purpose rather than inherited from whichever tutorial you read.

## The story

The electricity bill has to be paid by the fifteenth, and there are two ways to do it.

You can walk to the office on the main road, take a token, wait, hand over the cash, and get a
stamped receipt. Or you can pay it from your phone while the kettle boils.

The bill is the same bill. The amount is the same, the account number is the same, the receipt proves
the same thing, and the electricity board's records look identical afterwards. Nothing about *what
you did* differs.

What differs is everything around it. The office is shut on Sunday and has a queue on the fourteenth.
The phone works at midnight and does not work when the bank's app is down, which happens without
warning and is not your fault and is not fixable by you. The office needs you to be in that town. The
phone needs you to have set the account up once, correctly, with a password you now have to keep.

Nobody would say one of these is the *correct* way to pay a bill. You would ask where the person is,
what day it is, and how much they mind queuing. The answer changes and the bill does not.

## The idea in plain language

The specification states the equivalence in its first paragraph on transports, and it is worth reading
as a promise rather than as a description
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/transports`, read 2026-09-04):

> *"Protocol semantics are identical on every transport. A transport is a **binding**: it defines how
> messages are framed and delivered, how request metadata is carried, and how cancellation and
> termination are signaled. It does not define what the messages mean."*

Everything Sutra has learned about MCP is therefore transport-independent. `tools/list` returns the
same thing. `tools/call` takes the same arguments. The error codes are the same numbers. The
`_meta` block, the cacheable listings, the state handles from
[Day 32's 3.4](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md)
— none of them change.

Four things do change, and all four are operational:

- **Framing.** Newlines on stdio ([2.2](../02-stdio/2.2-one-message-per-line.md)); `Content-Length`
  and HTTP's own rules over the network.
- **Where the metadata rides.** Inline in `_meta` on stdio, because there is no header layer;
  mirrored into HTTP headers over Streamable HTTP so intermediaries can read it
  ([3.1](../03-streamable-http/3.1-one-endpoint-one-trip.md)).
- **How you cancel.** A `notifications/cancelled` message on stdio; closing the response stream over
  HTTP ([3.3](../03-streamable-http/3.3-standing-up-is-how-you-cancel.md)).
- **How it ends.** Close the child's stdin and let it exit ([2.4](../02-stdio/2.4-closing-up.md));
  nothing at all over HTTP, because each request already ended.

Which leaves the actual decision, and it comes down to one question: **does anything other than this
one client need to reach this server?** If no, stdio, and take the simplicity. If yes — a second
agent, a second machine, a deployment, a partner — HTTP, and take the address and everything that
comes with it ([3.4](../03-streamable-http/3.4-what-a-url-costs.md)).

The uncomfortable part is how cheap the switch looks in code. In ADK it is one class name and one
argument. Nothing warns you that you have just changed the blast radius, the authentication story and
the number of processes on the machine, because from the framework's point of view you have changed
none of those — you have changed a parameter object.

## Why Sutra needs it

Because `sutra/mcp/client.py` gets **two** functions today, `connect_stdio` and `connect_http`, and
the reason it is two functions and not one with a flag is this part.

A single `connect(transport="stdio" | "http")` would suggest the two are interchangeable at the call
site, which they are protocol-wise and are not operationally. Two functions with different parameters
— one takes a command and arguments, the other takes a URL — make the difference visible in every
call and impossible to flip by editing a string in configuration.

The decision also arrives concretely, twice, very soon. Day 34's `sutra_mcp` is developed over stdio
because the edit-and-rerun loop is unbeatable. Day 43's `sutra_mcp/app.py` is the same server behind
a URL because a deployment cannot be a subprocess of its clients. **Same server, same tools, same
protocol, different truck** — and the fact that the code in between does not change is the whole
argument for having a protocol at all.

## The mechanism

The two constructions, side by side:

```python
from google.adk.tools.mcp_tool import (
    McpToolset,
    StdioConnectionParams,
    StreamableHTTPConnectionParams,
)
from mcp import StdioServerParameters

local = McpToolset(
    connection_params=StdioConnectionParams(
        server_params=StdioServerParameters(command="uvx", args=["some-mcp-server"]),
        timeout=5.0,
    ),
)

remote = McpToolset(
    connection_params=StreamableHTTPConnectionParams(
        url="https://example.com/mcp",
        headers={"Accept": "application/json, text/event-stream"},
        timeout=5.0,
        sse_read_timeout=300.0,
        terminate_on_close=True,
    ),
)
```

**Line by line:**

- The two `McpToolset(...)` calls differ in exactly one argument. Everything downstream —
  `get_tools()`, `tool_filter`, `close()`, the agent it is attached to — is identical, which is the
  equivalence promise made concrete.
- `StdioConnectionParams` carries a **command**; `StreamableHTTPConnectionParams` carries a **URL**.
  That is the entire user-visible difference, and it is the difference between "I will start this"
  and "this is already running somewhere".
- `headers` exists only on the HTTP side and is where a static credential would go, until Day 37
  replaces it with something that can be refreshed. It is a `dict[str, Any] | None`.
- `timeout=5.0` means the same thing on both — seconds to establish the connection — and both default
  to `5.0`. Verified in `.venv/Lib/site-packages/google/adk/tools/mcp_tool/mcp_session_manager.py` on
  2026-09-04.
- `sse_read_timeout` exists only on the HTTP side and defaults to `60 * 5.0`. It is how long the
  client will wait for the next event on a stream before giving up, so it is the ceiling on how long
  a streaming tool ([3.2](../03-streamable-http/3.2-handed-over-or-told-to-wait.md)) may go quiet.
- `terminate_on_close=True` is the HTTP equivalent of [2.4](../02-stdio/2.4-closing-up.md)'s
  shutdown, and it is a leftover of the previous revision: it sends a DELETE to terminate a session,
  which a `2026-07-28` server answers with `405` because it has no sessions to terminate. Harmless,
  and a good reminder that the installed SDK is a document with a date on it.

The decision, as a table, because it is a set of enumerable facts:

| | stdio | Streamable HTTP |
| --- | --- | --- |
| Server is | launched by the client | already running somewhere |
| Address | a command line | one URL |
| Processes | one per client | one for everybody |
| Reachable by | only the launching process | anything that can reach the URL |
| Needs TLS, auth, `Origin` policy | no | yes |
| Survives the client restarting | no | yes |
| Right for | development, desktop hosts, personal tools | deployments, shared servers, partners |
| Sutra uses it on | Day 34's build loop | Day 42's agent server, Day 43's deployment |

## When it breaks

The break is picking a transport for a reason that is not on that table, and the commonest one is
that the tutorial you read used it. Point `StdioConnectionParams` at a command that is a web server
and you get [1.2](../01-the-connector/1.2-constructing-is-not-connecting.md)'s timeout; point
`StreamableHTTPConnectionParams` at a URL that is not an MCP endpoint and you get a `404` whose body
is HTML.

The break that actually costs a week is subtler and it looks like a scaling problem. A team develops
against stdio, ships it, and discovers under load that they are launching one server process per
conversation. The symptom is memory, not MCP: containers restarting, a machine that is fine at ten
users and dead at fifty, and nothing in any log that says "you chose the wrong transport". The fix is
a one-line change plus a deployment, an `Origin` policy, and an authentication story — which is to say
the one-line change is the smallest part of it.

There is a third, and it is the mirror image. A team uses HTTP for a genuinely local tool because
HTTP felt more professional, and now the development loop involves starting a server in another
terminal, remembering to restart it after every edit, and debugging a case where the agent is talking
to yesterday's code. stdio would have made that class of bug impossible, because the server is
launched fresh every run.

## In production

**What a professional writes instead:** the transport is a property of the *server record*, not of the
call site. One configuration entry per server — name, transport, command or URL, allowed tools, who
approved it — and `sutra/mcp/client.py` reads it and calls the right constructor. That way the answer
to "which transport does the ticket server use" is a lookup rather than a grep, and changing it is a
reviewable diff.

**What degrades at scale:** the mixed estate. Real systems end up with both, and the two have
different failure modes, different timeouts and different observability. A stdio server's health is a
process; an HTTP server's health is an endpoint. A dashboard that treats them as one kind of thing
will be wrong about half of them, and the on-call runbook needs two sections.

**The failure mode that only appears with real traffic:** transport-specific timeouts nobody set. The
`sse_read_timeout` default of `60 * 5.0` seconds is generous for a tool call and short for a
`subscriptions/listen` stream; the stdio `timeout` default of `5.0` is generous for a local script and
short for a cold `npx`. Both defaults are fine until traffic makes them not, and neither is written
down anywhere in a codebase that never passes the argument.

**The review comment a senior engineer leaves:** *"this switched the ticket server from
`StdioConnectionParams` to `StreamableHTTPConnectionParams` in one line and the PR description says
'move to HTTP'. That line also gives the server a public address, removes the guarantee that only we
can call it, and adds an authentication requirement we have not built. Split it: the transport change
is not the risky part of this change and it is the only part that is visible."*

**The interview question:** *"stdio or Streamable HTTP — how do you choose?"* The answer people get
wrong by treating it as a functional choice: *"Functionally there is nothing to choose. The spec says
protocol semantics are identical on every transport; a binding only defines framing, where the request
metadata rides, and how you cancel and terminate. So the decision is operational, and it is one
question: does anything other than this client need to reach this server? If not, stdio — the client
launches it as a child process, there is no port and no auth story because it has our own authority,
and the development loop restarts it on every run. If yes, Streamable HTTP, and I would be explicit
that this is a blast-radius change and not a config change: one address means `Origin` validation, a
bind interface, TLS and authentication. What I like about MCP here is that none of the tool code moves
when you switch."*
