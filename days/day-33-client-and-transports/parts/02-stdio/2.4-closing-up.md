# 2.4 — Closing up

## One-line answer

The stdio shutdown is an ordered sequence — close the server's input, wait for it to exit, and only
then force it — and its counterpart is that a server which dies unexpectedly is simply restarted,
because a stateless protocol has nothing to lose when it does.

## The story

Closing a small shop is three things in a fixed order, and everybody who has ever done it knows the
order matters.

First you lock the front door. Not because the shop is finished — there are still two people at the
back looking at the shelf — but because locking it is how you stop the queue growing. Nobody new
comes in.

Then you serve the people already inside. They take as long as they take. One of them wants to pay by
card and the machine is slow. You wait, because they were in before the lock and turning them out
would be a worse thing than the four extra minutes.

Only then do you switch the lights off and go.

Doing it in any other order produces a different evening. Switch the lights off first and you have two
confused people in the dark holding shopping. Leave the door unlocked and somebody walks in at the
moment you were about to leave, and the whole sequence starts again.

There is a fourth case that is not part of the routine at all: the power cuts out. Nobody performs a
sequence then. You get everyone out, you lock up, and you come back tomorrow and open normally.

## The idea in plain language

The stdio binding writes the closing routine down as three numbered steps
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio`, read 2026-09-04):

> *"The client **SHOULD** initiate shutdown by: 1. Closing the input stream to the child process (the
> server). 2. Waiting for the server to exit. 3. If the server does not exit within a reasonable
> time, forcibly terminating the process using the mechanism appropriate for the operating system."*

And the matching obligation on the other side:

> *"Servers **SHOULD** exit promptly when their standard input is closed or reads return end-of-file.
> This is the primary graceful-shutdown signal and the only portable one, so honoring it reduces the
> need for forced termination."*

Read those two together and the design becomes obvious. **Closing stdin is the shutdown signal.**
There is no `shutdown` message, no `bye` RPC and no protocol-level goodbye, because there does not
need to be: the client already owns the channel, and letting it go is unambiguous. A server sitting
in a `for line in sys.stdin:` loop sees that loop end. Nothing had to be invented.

Step 3 exists because a server can ignore the signal — stuck in a long call, blocked on a network
read, or badly written. So there is an escalation, and it is operating-system specific: on POSIX
systems it goes `SIGTERM` and then `SIGKILL`; on Windows, where those signals do not exist, the
client uses `TerminateProcess` or a Job Object. The MCP SDK has a module for each
(`mcp/os/posix/utilities.py` and `mcp/os/win32/utilities.py`, read 2026-09-04) and a constant
`PROCESS_TERMINATION_TIMEOUT = 2.0` for how long "a reasonable time" is before it escalates.

Then there is the fourth case, and it is the one worth carrying out of this part:

> *"If the server process exits unexpectedly, the client **SHOULD** restart it. Because the protocol
> is stateless, any in-flight requests are simply lost and the client can retry them against the
> fresh process."*

Read that sentence next to
[Day 32's 2.2](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md).
Under the old session model, a crashed server meant a lost session, and recovery meant re-doing the
handshake and hoping nothing had been remembered that could not be reconstructed. Under the 2026-07-28
revision there is nothing to reconstruct. **Restart and retry is a complete recovery strategy**, and
it is complete because of a property decided somewhere else entirely.

## Why Sutra needs it

Because "the server crashed" is going to happen to Sutra on a Tuesday, and the difference between an
outage and a hiccup is whether the client knows it may simply try again.

Day 44 builds `sutra/mcp/hardening.py` with `with_retries` and `with_timeout`, and a retry is only
safe if re-issuing a request cannot land in a half-finished state on the far end. Today's part is what
makes that true for stdio: a fresh process has no memory of the request that died with the old one.
The one thing you have to check before relying on it is whether the *tool* is idempotent — restarting
the process is safe, calling `desk_wipe_tickets` twice is not — and that check belongs to the tool,
not to the transport.

More immediately, it explains the line at the end of every transcript in this day:

```text
[fake-desk] stdin closed, exiting
```

That is step 1 and step 2 of the sequence, seen from the server. It appears because
`await toolset.close()` ran, and it is the receipt for
[1.5](../01-the-connector/1.5-somebody-has-to-give-it-back.md)'s whole argument.

## The mechanism

```mermaid
stateDiagram-v2
    [*] --> Running: client launches it
    Running --> Draining: client closes stdin
    Draining --> Exited: server finishes and exits
    Draining --> Forced: it does not exit in time
    Forced --> Exited: SIGTERM then SIGKILL (POSIX)<br/>TerminateProcess (Windows)
    Running --> Crashed: it dies on its own
    Crashed --> Running: client relaunches; in-flight requests are simply retried
    Exited --> [*]
```

The client half is in the SDK, and reading it is the fastest way to see that the specification's three
steps are three lines of code —
`.venv/Lib/site-packages/mcp/client/stdio/__init__.py`, read 2026-09-04:

```python
finally:
    # MCP spec: stdio shutdown sequence
    # 1. Close input stream to server
    # 2. Wait for server to exit, or send SIGTERM if it doesn't exit in time
    # 3. Send SIGKILL if still not exited
    if process.stdin:
        try:
            await process.stdin.aclose()
        except Exception:
            pass
```

**Line by line:**

- It is in a `finally`, so the sequence runs whether the block above it ended normally or by
  exception. This is [1.5](../01-the-connector/1.5-somebody-has-to-give-it-back.md)'s shape, at the
  layer below.
- `process.stdin.aclose()` is step 1 and it is the whole graceful path. Nothing is sent; a stream is
  released.
- The bare `except Exception: pass` around it is unusual for this curriculum and it is right here:
  stdin may already be closed because the process already died, and that is not a failure of
  shutdown, it is shutdown having happened. The comment in the SDK says exactly that.
- What follows in the file is the wait and the escalation, with `PROCESS_TERMINATION_TIMEOUT = 2.0`
  as the patience.
- Note what is **not** here: no message is sent to the server, and the client does not wait for a
  reply to anything. There is no protocol conversation about closing.

The server half is one line, and it is the last line of `lab/fake_desk_server.py`:

```python
def main() -> None:
    """Read one JSON-RPC message per line from stdin until the stream closes."""
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        handle(json.loads(line))
    log("stdin closed, exiting")
```

**Line by line:**

- `for line in sys.stdin:` is the entire server loop, and it is also the entire shutdown handler. When
  the client closes the pipe, the iterator is exhausted and the loop ends. No signal handler, no flag,
  no `while True`.
- `line.strip()` and the `continue` tolerate a blank line without treating it as a message. Blank
  lines happen — a double `\n` from a careless writer — and dropping them silently is the right
  behaviour for a delimiter, not for content.
- `log("stdin closed, exiting")` runs after the loop, on stderr, and it is the only reason you can
  tell a graceful shutdown from a kill in any transcript in this day. A server that exits silently is
  indistinguishable from one that was terminated.
- `main()` then returns and the process exits with status 0. That is "exit promptly" satisfied, and
  it required no code.

Watch the whole sequence:

```bash
uv run python days/day-33-client-and-transports/lab/list_tools.py 2>&1 | tail -3
```

**Line by line:**

- `2>&1` merges the server's stderr into stdout so both halves of the story arrive in one stream.
- `tail -3` keeps the end, which is where shutdown lives.
- The `[fake-desk] stdin closed, exiting` line you see is the server reporting the end of its own
  `for` loop. Nobody told it to stop; its input ran out.

## When it breaks

The interesting failure is the server that will not go. Add a `signal.pause()` or a long sleep after
the loop in a real server and the client's patience runs out, and on Windows the escalation is not
polite:

```text
[fake-desk] stdin closed, exiting
```

— never printed, because the process was terminated before it got there. That absence is the entire
diagnostic. On POSIX you would additionally see the exit code become `-15` or `-9` where a clean exit
is `0`, and a client that logs the child's return code can tell you which of the three steps did the
work.

The second break belongs to servers that hold something. A server that opened a database transaction,
wrote a temporary file, or acquired a lock, and treats "stdin closed" as "exit immediately", leaves
that thing behind. The specification says exit *promptly*, not *instantly*, and the difference is a
`finally` in the server. This is not a client-side problem and it is a good question to ask about any
third-party server you depend on: what does it do when its input closes mid-write?

The third one is the restart loop. A client that faithfully implements *"if the server process exits
unexpectedly, restart it"* against a server that crashes on startup will restart it forever, as fast
as the operating system allows, and the symptom is a machine at 100% CPU with no error message
anywhere except in a stderr stream nobody kept
([2.3](2.3-the-only-place-left-to-talk.md)). Restarting needs a bound and a backoff, which is exactly
the ladder Day 21 built for errors
([1.3](../../../day-21-errors-surface-not-swallow/parts/01-who-hears-it/1.3-retry-substitute-escalate.md))
and Day 44 will build again for MCP.

## In production

**What a professional writes instead:** a client that logs the child's exit status and distinguishes
the three outcomes — exited cleanly, terminated after the grace window, died on its own — because they
mean different things and only one of them is normal. On the server side, the loop's `finally`
releases anything held before the process ends, and the last stderr line says so, so the transcript
has a legible ending.

**What degrades at scale:** shutdown time. The grace window is per process, so a host closing forty
stdio servers at once serially waits forty times. Real hosts close them concurrently and cap the total,
because a container that does not exit inside its termination window is killed anyway, and being
killed halfway through a tidy shutdown is worse than having done a fast one.

**The failure mode that only appears with real traffic:** the crash you cannot see. A server dies
under a specific input, the client restarts it, the retry succeeds because the input was not retried,
and the system looks completely healthy while quietly restarting a process hundreds of times an hour.
Nothing is failing. The only evidence is a counter, which is why "servers restarted" belongs on a
dashboard alongside latency, and why
[Day 22's 4.1](../../../day-22-structured-logging/parts/04-in-production/4.1-what-to-log-and-what-to-count.md)
argued that some things are counted rather than logged.

**The review comment a senior engineer leaves:** *"the reconnect here has no backoff and no ceiling.
A server that fails to start will be relaunched in a tight loop, and the only place the reason exists
is a stderr stream we are discarding. Bound the restarts, back off between them, and keep the last
few lines of the child's stderr so the alert can say why."*

**The interview question:** *"how do you shut down and recover a stdio MCP server?"* Give the
sequence and then the property: *"Shutdown is close its stdin, wait, and escalate to a signal only if
it does not exit — there is no goodbye message, because closing the channel is the signal, and a
server reading stdin in a loop gets it for free. Recovery is more interesting: if the process dies
unexpectedly the client just restarts it and retries, and that is a complete strategy only because the
2026-07-28 revision made the protocol stateless. Under the old session model a crash lost negotiated
state and recovery was a real problem. The two things I would still add are a backoff on the restart
and keeping the child's stderr, because a crash-looping server is otherwise invisible and silent."*
