# 2.2 — One message per line

## One-line answer

stdio's entire framing is "one JSON-RPC message per line, and a message **MUST NOT** contain an
embedded newline", which makes the newline character the only thing separating two messages — and
therefore the only thing that can be got wrong.

## The story

The order pad in a small kitchen is a spike with paper on it.

The waiter writes one order per slip, tears it off, and pushes it onto the spike. The cook works down
the spike from the bottom, one slip at a time, and never asks anybody anything. The whole arrangement
works because of a rule nobody has ever written down: **one slip is one order.** Not "an order and a
note about it". Not "two orders for the same table". One.

On a Friday the waiter writes an order for table six and adds, underneath, *"no chilli, she is
allergic"*. Then, because the pad is nearly finished, she tears it in the middle of the sheet rather
than at the line.

The cook gets two slips. The first says table six wants a curry. The second says *"no chilli, she is
allergic"* and nothing else — no table, no dish, no context. He looks at it for a second, cannot make
an order out of it, and puts it aside.

Nobody lied. Nobody made a mistake about the food. The information about the allergy was written
down, correctly, by a careful person, and it did not arrive, because the thing that separates one
order from the next got used in the middle of one.

## The idea in plain language

The stdio binding is two sentences of framing, and this is both of them
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio`, read 2026-09-04):

> *"Each message is a single JSON-RPC request, notification, or response."*
> *"Messages are delimited by newlines, and **MUST NOT** contain embedded newlines."*

That is the entire protocol framing. There is no length prefix, no `Content-Length` header, no
delimiter you can escape, and no way for a reader to recover if a message spans two lines. The reader
splits the byte stream on `\n` and treats every piece as a whole message.

Which raises the obvious objection, and it is worth answering carefully because it is the thing
people get wrong: **JSON is allowed to contain newlines.** A ticket body with two paragraphs in it is
a perfectly ordinary tool result. So how does that ever fit on one line?

Because there are two different newlines and only one of them is a byte on the wire.

- A newline **inside a JSON string value** is written as the two characters `\` and `n`. That is what
  `json.dumps` produces by default. Two characters, no line break, the message stays on one line, and
  the reader on the other side turns it back into a real newline when it parses. This case is safe
  and needs no thought.
- A newline **between JSON tokens** is a real `\n` byte. That is what pretty-printing produces, and
  it is what a `print()` in the middle of writing produces. This case destroys the framing, and
  nothing about the JSON is invalid — the bytes are just no longer one message.

So the rule is not "avoid newlines in your data". It is **"serialise compactly and write exactly one
line"**. `json.dumps(message)` followed by `"\n"` obeys it. `json.dumps(message, indent=2)` does not,
and the resulting text is still valid JSON, which is exactly why the mistake survives a code review.

## Why Sutra needs it

Because Day 34 writes a server whose job is to answer on this exact channel, and the framing rule is
the one part of it that no library can protect you from.

The MCP SDK writes correctly framed messages — the client's `stdin_writer` calls
`model_dump_json(...)` and appends one `"\n"`, and that is fine. What the SDK cannot control is
everything *else* your server process writes to stdout: your `print` statements, a library's banner,
a warning from an import. [2.3](2.3-the-only-place-left-to-talk.md) is where those go instead, and
[5.1](../05-failure-lab/5.1-the-log-line-that-ate-the-reply.md) is what happens when they do not.

It matters on the client side too, and sooner than you think. Sutra's tools return ticket bodies and
knowledge-base articles — multi-paragraph text, written by other people, arriving through a channel
where the newline is structural. Understanding that `\n` inside a string is safe and a real line
break is not is the difference between trusting the transport with real text and quietly stripping
newlines out of your data "to be safe", which is a data-loss bug wearing a caution hat.

## The mechanism

How the reader actually splits the stream — this is the loop from
`.venv/Lib/site-packages/mcp/client/stdio/__init__.py`, read 2026-09-04:

```python
buffer = ""
async for chunk in TextReceiveStream(process.stdout, encoding=server.encoding):
    lines = (buffer + chunk).split("\n")
    buffer = lines.pop()
    for line in lines:
        try:
            message = types.JSONRPCMessage.model_validate_json(line)
        except Exception as exc:
            logger.exception("Failed to parse JSONRPC message from server")
            await read_stream_writer.send(exc)
            continue
        await read_stream_writer.send(SessionMessage(message))
```

**Line by line:**

- `buffer` exists because a `chunk` from a pipe is an arbitrary number of bytes, not a message. A
  reply can arrive split across two reads, and the leftover has to be kept.
- `(buffer + chunk).split("\n")` is the whole framing rule expressed as one call. Nothing else about
  the bytes is inspected.
- `lines.pop()` takes the **last** element back off and makes it the new buffer. That is correct
  precisely because `split` leaves an empty string at the end when the chunk ended in a newline, and
  a partial message when it did not. One line handles both.
- `model_validate_json(line)` parses and validates in one step. Note the input is `line`, singular: a
  message that spanned two lines never reaches this call as a whole.
- The `except` catches **everything**, logs `"Failed to parse JSONRPC message from server"`, and then
  does something unusual — it sends the *exception object itself* down the stream in place of a
  message, and `continue`s. The reader does not stop. That single `continue` is why a stray line is
  survivable and a glued-on line is not: a stray line is one bad element in the stream, while a glued
  line took a real reply down with it.
- There is no recovery, no resynchronisation and no request for a resend. There is nowhere to ask
  from: the sender does not know anything went wrong.

Now watch the two encodings side by side:

```bash
uv run python days/day-33-client-and-transports/lab/frame.py
```

**Line by line:**

- The script builds one ordinary message — a tool result whose text contains a line break — and
  serialises it twice, with `indent=None` and with `indent=2`.
- It then reads each stream back with the same `split("\n")` the SDK uses, and tries to parse every
  piece.
- Zero network, zero model calls, no subprocess. This is arithmetic on a string.

```text
compact, escaped (indent=None) - one message
  bytes on the wire : 101
  lines the reader sees : 1
    1: parses as JSON  <- '{"jsonrpc": "2.0", "id": 7, "result": {"content"'

pretty-printed (indent=2) - the same message
  bytes on the wire : 153
  lines the reader sees : 12
    1: NOT JSON - Expecting property name enclosed in double quotes  <- '{'
    2: NOT JSON - Extra data  <- '  "jsonrpc": "2.0",'
    3: NOT JSON - Extra data  <- '  "id": 7,'
    4: NOT JSON - Extra data  <- '  "result": {'
    5: NOT JSON - Extra data  <- '    "content": ['
```

One message became twelve, and **none** of the twelve is valid JSON. Look at line 8 of that output in
your own run: `'        "text": "line one\\nline two"'`. The newline that was actually in the data
survived both encodings perfectly, as the two characters `\n`. The newlines that destroyed the
message are the ones the pretty-printer added between tokens, which carried no information at all.

## When it breaks

There is no error on the sending side. A server that pretty-prints its replies runs, writes valid
JSON, and never hears a complaint. Everything visible happens on the client, and it looks like this:

```text
Failed to parse JSONRPC message from server
Traceback (most recent call last):
  File "...\mcp\client\stdio\__init__.py", line 155, in stdout_reader
    message = types.JSONRPCMessage.model_validate_json(line)
pydantic_core._pydantic_core.ValidationError: 1 validation error for JSONRPCMessage
  Invalid JSON: expected ident at line 1 column 2 [type=json_invalid, input_value='INFO: loading 3 tools\r', input_type=str]
```

Two details in that message are worth reading slowly, because both mislead.

**`at line 1 column 2`** refers to position inside the *fragment*, not inside your file or your
message. Every fragment is "line 1" as far as the parser is concerned, so the number is never a
location you can go to.

**`input_value=`** is the only genuinely useful field, and it is the one people skim past. It shows
the exact bytes that failed to parse. If it looks like a log line, the server wrote to stdout
([5.1](../05-failure-lab/5.1-the-log-line-that-ate-the-reply.md)). If it looks like a fragment of
JSON — a bare `{`, or `"id": 7,` — the framing is broken and somebody is pretty-printing.

Notice also the `\r` at the end of that captured value. On Windows the child's stdout arrives with
carriage returns, the SDK splits on `\n` only, and the `\r` stays glued to the end of every line.
Valid JSON tolerates trailing whitespace so it never matters — but it is in every error message you
will read on this platform, and it is not the bug.

## In production

**What a professional writes instead:** a server that never calls `print` and never lets a library
write to stdout. In Python that means one line at the top of the server —
`sys.stdout` is the protocol channel and everything else is redirected — plus a `logging` setup that
targets `stderr` explicitly. Serialisation goes through one function that does
`json.dumps(obj, separators=(",", ":")) + "\n"`, and it is the only place in the codebase that writes
to stdout.

**What degrades at scale:** message size. There is no length prefix, so the reader has to accumulate
bytes until it meets a newline, and a very large tool result is a very long line held in memory on
both sides. A server returning a whole log file in one `text` block is a real thing people do, and it
is the reason the answer to "can I return the file?" is usually "return a resource URI and let the
client fetch it" — which is [Day 35's](../../../day-35-resources-and-prompts/LESSON.md) subject.

**The failure mode that only appears with real traffic:** concurrency on one stdout. Two threads in a
server writing replies at the same time can interleave halfway through a line, producing exactly the
glued-together corruption of
[5.1](../05-failure-lab/5.1-the-log-line-that-ate-the-reply.md) with no `print` anywhere. It happens
under load and never in a test. The fix is a lock around the single write, and it is the kind of
thing you only think of once you know the framing has no way to recover.

**The review comment a senior engineer leaves:** *"this server writes its replies with
`json.dumps(payload, indent=2)`. It is readable in the logs and it is two or more messages on the
wire. Compact-dump it, and if you want it readable, log the pretty version to stderr where it cannot
break anything."*

**The interview question:** *"how does an MCP stdio client know where one message ends?"* Say the rule
and then the consequence: *"A newline, and nothing else — no length prefix, no framing header. A
message is one line and the spec says it MUST NOT contain an embedded newline, so a newline in your
data has to be the escaped `\n` inside a JSON string, which `json.dumps` gives you for free. What
follows is the part worth knowing: there is no resynchronisation. If a server pretty-prints a reply,
or prints a log line to stdout, the client's parser fails on the fragments and the real reply is
gone, and the sender never finds out. We treat stdout in a server as reserved: one function writes to
it, everything else goes to stderr."*
