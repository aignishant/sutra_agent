# 3.4 — What a URL costs

## One-line answer

Giving a server an address makes it reachable by everything that can reach addresses, which is why
the Streamable HTTP binding opens with three security requirements — validate `Origin`, bind to
localhost when local, authenticate — that the stdio binding does not need at all.

## The story

The shop has a back door onto the lane, and the staff prop it open with a crate because the yard is
where the bins are and nobody wants to walk round.

For years this is fine. The lane is not a thoroughfare. Everyone who comes through that door works
there. The owner knows the door is open and has never thought of it as a way in, because in his head
it is a way *out* — a convenience for taking rubbish to the bins.

Then a stranger walks up the lane, sees an open door, and goes in. He is not a burglar in a mask. He
is somebody who tried a door and it opened. He is in the stockroom within four seconds, and the two
people at the front counter cannot see the stockroom.

Afterwards, the thing that is hard to explain to the insurer is that nobody was careless. Every
person who used that door had a reason. The problem was that the door had one property everybody had
stopped thinking about: **it was reachable from outside**, and being reachable is not a thing you get
to decide is unimportant.

## The idea in plain language

[2.1](../02-stdio/2.1-connecting-is-launching.md) listed everything stdio does not need: no port, no
TLS, no `Origin`, no authentication. That list was not stdio being simple. It was stdio having no
address. A subprocess is reachable by exactly one thing — the process that launched it — and that
process already had the authority to run programs on this machine.

An HTTP endpoint has an address, and an address is an invitation to everything that can form a
request. So the Streamable HTTP binding opens with a section the stdio page does not have
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http`, read
2026-09-04):

> *"1. Servers **MUST** validate the `Origin` header on all incoming connections to prevent DNS
> rebinding attacks. If the `Origin` header is present and invalid, servers **MUST** respond with
> HTTP 403 Forbidden."*
> *"2. When running locally, servers **SHOULD** bind only to localhost (127.0.0.1) rather than all
> network interfaces (0.0.0.0)."*
> *"3. Servers **SHOULD** implement proper authentication for all connections."*
> *"Without these protections, attackers could use DNS rebinding to interact with local MCP servers
> from remote websites."*

Three terms, defined plainly.

The **`Origin` header** is a browser's statement of which site's page caused this request. Browsers
set it and pages cannot forge it, so it is the only reliable way a server can tell "a page from my own
site asked for this" from "a page on somebody else's site asked for this". Non-browser clients — the
MCP SDK included — do not send one at all, which is why the rule is *"if present and invalid"* rather
than *"if absent"*.

**Binding** is which network interfaces a server listens on. `127.0.0.1` means only this machine can
reach it. `0.0.0.0` means every interface, including the office Wi-Fi and, on a badly configured
network, the internet. The two differ by seven characters and by an entire threat model.

**DNS rebinding** is the attack the first rule exists for, and it deserves a moment because it defeats
the intuition that a localhost server is private. A browser refuses to let `evil.example` read a
response from `127.0.0.1` — that is the same-origin policy. So the attack does not cross origins; it
changes what an origin *means*. A page from `evil.example` is loaded, its domain's DNS record is
re-answered a moment later as `127.0.0.1`, and the browser makes a second request to what it still
believes is `evil.example`, which now resolves to your machine. The page is now talking to your local
MCP server from inside the same-origin policy, and it can read the replies. Validating `Origin` breaks
it, because the header still says `https://evil.example` and your server has never heard of that site.

Sit with what that means for a local MCP server. It has your filesystem tools, your database
credentials, and no authentication because it is "just running locally". A web page you opened in
another tab can call it.

## Why Sutra needs it

Because Sutra is going to be on both sides of this, and the two sides have different homework.

As a **client**, today: `connect_http` in `sutra/mcp/client.py` takes a URL, and a URL is where an
allowlist belongs. Not every string is an acceptable address — `http` rather than `https` outside
local development, a host nobody approved, a redirect to somewhere else — and Day 45's audit will ask
which servers Sutra talks to. That question is answerable only if the answer is written down
somewhere rather than assembled from configuration at runtime.

As a **server**, from Day 43: `sutra_mcp/app.py` is an ASGI application with a real address, and every
one of the three rules above becomes its responsibility. Day 37 brings the third one properly —
bearer tokens, issuer validation, the OAuth pieces — but the first two are free and are the ones that
get skipped, because they are invisible when they work.

This is Principle 13, blast radius before capability, applied to a transport rather than to a tool.
Moving from stdio to HTTP is the single largest increase in blast radius in this phase, and it happens
by changing one class name.

## The mechanism

The two bindings, side by side, on exactly the property that differs:

| | stdio | Streamable HTTP |
| --- | --- | --- |
| How the server is addressed | a command line | a URL |
| Who can reach it | the process that launched it | anything that can reach the address |
| Authority it runs with | the client's own | whatever it authenticates as |
| `Origin` validation | not applicable | **MUST**, when the header is present |
| Interface binding | not applicable | **SHOULD** be 127.0.0.1 when local |
| Authentication | not applicable | **SHOULD**, and see Day 37 |

The enforcement, from `lab/http_shape.py`, is the first thing the handler does:

```python
ALLOWED_ORIGINS = {"http://127.0.0.1", "http://localhost"}


def do_POST(self) -> None:
    origin = self.headers.get("Origin")
    if origin is not None and origin not in ALLOWED_ORIGINS:
        self._refuse(403, -32600, f"Forbidden: bad Origin {origin!r}")
        return
    ...
```

**Line by line:**

- `ALLOWED_ORIGINS` is an **allowlist**, the same shape as
  [1.4](../01-the-connector/1.4-the-allowlist-is-an-argument.md)'s `tool_filter`. A denylist here is
  worse than useless: an attacker chooses their own origin.
- `origin is not None and ...` implements the specification's exact condition. A missing header is
  **not** a violation, because non-browser clients do not send one — and a server that rejected
  headerless requests would reject every legitimate MCP client there is.
- Origins are compared as whole strings including the scheme, and never with `startswith`.
  `https://evil.example.com` starts with `https://evil.example`, and an `endswith` check on a domain
  is defeated by registering `notmybank.com`. Exact set membership is the only comparison that is not
  subtly wrong.
- This runs **before** the body is read. A request that fails the check must not be parsed, because
  parsing untrusted input is itself work you were tricked into doing.
- `403`, specifically, and not `400`. The specification names the status, and a `403` is
  distinguishable in a proxy log from every other refusal in this transport.
- The `-32600` JSON-RPC body alongside it follows the pattern from
  [3.1](3.1-one-endpoint-one-trip.md): an HTTP status for the infrastructure and a JSON-RPC error for
  the client, in the same response.

And the binding, in the line that starts the server:

```python
server = ThreadingHTTPServer(("127.0.0.1", 0), Endpoint)
```

**Line by line:**

- `"127.0.0.1"` is rule 2 as one string. `"0.0.0.0"` in that position would make this lab's fake
  endpoint reachable from every machine on your network for as long as the script runs.
- Port `0` asks the operating system for any free port, which is the right choice for a test — it
  cannot collide, and the actual number is read back from `server.server_port`.
- `ThreadingHTTPServer` handles each request in its own thread, which is what lets the client and the
  endpoint run in one process without deadlocking.

Watch the refusal:

```bash
uv run python days/day-33-client-and-transports/lab/http_shape.py --bad-origin
```

**Line by line:**

- `--bad-origin` adds `Origin: https://evil.example` to both POSTs and changes nothing else.
- The default run sends no `Origin` at all, which is what a real MCP client does — so the two runs
  together show both branches of the specification's condition.

```text
POST http://127.0.0.1:63678/mcp  Mcp-Method: tools/list
  <- 403 application/json
     {"jsonrpc": "2.0", "id": null, "error": {"code": -32600, "message": "Forbidden: bad Origin 'https://evil.example'"}}
```

## When it breaks

The break has no error text, because the break is a request that **succeeds**. Delete the three
`origin` lines from `do_POST` and run `--bad-origin` again:

```text
POST http://127.0.0.1:63678/mcp  Mcp-Method: tools/list
  <- 200 application/json
     {"jsonrpc": "2.0", "id": 1, "result": {"tools": [{"name": "desk_ping"}]}}
```

A page claiming to be from `evil.example` just listed your tools. Nothing in the transcript is
distinguishable from a legitimate call, nothing is logged as unusual, and the next request could be
`tools/call`.

The second break is the seven-character one. A local server started with
`ThreadingHTTPServer(("0.0.0.0", 8080), ...)` behaves identically on your machine — the tests pass,
the agent works, `curl 127.0.0.1:8080/mcp` answers — and is now also answering on your laptop's
address on the office network. The failure is invisible from inside and obvious from outside, which is
the worst combination there is, and it is why the specification writes the interface down rather than
leaving it to a default.

The third break is one to expect on this exact day and to read carefully. Point a client at an
`https://` URL that requires authentication and you get:

```text
urllib.error.HTTPError: HTTP Error 401: Unauthorized
```

That is a **correct** server doing its job, and the temptation is to make it go away by finding a
server that does not ask. Day 37 is where Sutra answers it properly, with issuer validation and
tokens; today the right response is to notice that stdio never asked you for a credential and HTTP
does, and that this is the cost side of the ledger for an address.

## In production

**What a professional writes instead:** the server's bind address and its `Origin` allowlist are
configuration, not literals, with a development default of `127.0.0.1` and a deployment that must
state its interface explicitly. On the client side, the URL is validated against an allowlist at
startup and the scheme is checked — plain `http` to anything that is not loopback is a startup
failure, not a warning, because a warning about transport security is a warning nobody has ever acted
on.

**What degrades at scale:** the number of people who can add a URL. One engineer configuring one
server thinks about all of this. A platform where any team can point an agent at any MCP endpoint has
made "which servers do we talk to" an unanswerable question, and the answer stops being a code review
and starts being a registry with an approval step. That is what Day 45's audit is for, and
[Day 32's 6.2](../../../day-32-mcp-stateless-core/parts/06-in-production/6.2-before-you-depend-on-a-server.md)
already wrote the intake questions.

**The failure mode that only appears with real traffic:** the redirect. A client follows a `301` from
the configured host to somewhere else, and every header — including the `Authorization` Day 37 adds —
goes with it unless the HTTP library is told not to. Your allowlist checked the URL you configured,
not the URL you ended up at. Disabling redirects on MCP clients is a one-line change and it closes a
hole that no amount of URL allowlisting can.

**The review comment a senior engineer leaves:** *"this binds the MCP server to `0.0.0.0` so the
container health check can reach it. That also exposes it to every pod in the namespace with no
authentication. Bind to localhost and have the health check run inside the container, or put the auth
in first — pick one, but not neither."*

**The interview question:** *"what changes about security when an MCP server moves from stdio to
HTTP?"* The answer that shows you have thought about it rather than read a checklist: *"Everything,
because it acquires an address. Over stdio the server is a subprocess of the client, so it is
reachable by exactly one process and it runs with that process's authority — there is no port, no
TLS, no auth, and that is not a gap. Over HTTP the spec opens with three rules the stdio page does not
have: validate `Origin`, bind to localhost when you are local, and authenticate. The one people skip
is `Origin`, and it is the interesting one, because it stops DNS rebinding — a web page in another tab
can otherwise reach a localhost MCP server and read the replies, and 'it is only on localhost' is
exactly the reasoning that leaves it unauthenticated. So moving transport is not a configuration
change, it is a blast-radius change, and it happens by editing one class name."*
