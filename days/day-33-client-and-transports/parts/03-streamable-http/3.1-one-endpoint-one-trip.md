# 3.1 — One endpoint, one trip per question

## One-line answer

Streamable HTTP gives a server exactly one URL that accepts POST, and every single JSON-RPC message
is its own POST to it — so there is no connection to establish, nothing to keep open between
requests, and no second address to configure.

## The story

The office has one window that deals with your kind of application, and it is window 3.

There is no window 3a for follow-ups and no separate desk for people who came last week. Everybody
who wants anything from this department queues at window 3, hands over one thing, and gets one thing
back. Then they leave the window. If they need a second thing they queue again.

The first time, this feels stupid. You were just there. The clerk was looking straight at you. Why
should you go to the back of the queue to ask a second question?

The reason is visible if you stand there for ten minutes. There are four clerks, and they rotate.
Somebody goes for lunch and somebody else sits down, and the queue does not notice, because nothing
about your application lives in a particular clerk's head. You bring the whole thing with you every
time, so it does not matter who is at the window.

The office next door does it the other way: you are "assigned" to a clerk and you come back to that
person. It feels much better, right up until the day your clerk is off, and then there is genuinely
nothing anyone can do for you.

## The idea in plain language

The second standard transport is **Streamable HTTP**, and its first rule is about addresses
(`https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http`, read
2026-09-04):

> *"The server **MUST** provide a single HTTP endpoint path (hereafter referred to as the **MCP
> endpoint**) that supports POST. For example, this could be a URL like `https://example.com/mcp`."*

One path. Not a REST-shaped family of URLs, one per tool — the whole point of MCP being seven fixed
methods rather than a generated client
([Day 32's 1.4](../../../day-32-mcp-stateless-core/parts/01-the-socket/1.4-not-just-another-api.md))
is that the address does not have to grow when the tools do.

And the second rule is about how you use it:

> *"Every JSON-RPC message sent from the client **MUST** be a new HTTP POST request to the MCP
> endpoint."*

Every message. Not "the first one, and then a connection is reused". At the MCP level, each message is
an independent HTTP request that begins and ends. There is no connect step, no session establishment,
and nothing that has to happen before a `tools/call` except sending it.

That word "connect" is worth pulling apart, because it means two different things and they now live at
different layers. **HTTP connections are still reused** — the underlying TCP and TLS connection is
pooled by `httpx`, which is why the second POST is much faster than the first. That is a transport
optimisation and it is invisible to MCP. What is gone is anything *protocol-level* that spans
requests: no `initialize`, no session identifier to carry, no server-side memory that the next request
depends on.

The 2026-07-28 revision states the removals directly:

> *"Revision 2026-07-28 changed the behavior of Streamable HTTP. Clients must ensure they handle
> backwards compatibility correctly. Changes included: Removal of the GET stream endpoint. Removal of
> protocol-level sessions."*

Which is why a modern server answers a GET to its MCP endpoint with `405 Method Not Allowed`, and
ignores an `Mcp-Session-Id` header instead of honouring it. Both of those were real features of the
previous three revisions.

What rides on each POST is
[Day 32's 3.1](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.1-the-label-on-the-envelope.md):
`MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` where the method has a target. That part explains
why they are there and what a gateway does with them; this part only needs you to know they are
**required on every POST**, because there is no earlier request in which they could have been said
once.

## Why Sutra needs it

Because `connect_http` in `sutra/mcp/client.py` takes a URL and nothing else, and the reason it is
that short is everything above.

More importantly, this is the transport Sutra will eventually be *served over*. Day 43 writes
`sutra_mcp/app.py`, an ASGI application where "any instance answers any request", and Day 42 serves
the whole desk agent over MCP. Neither of those is possible over stdio, because a subprocess is one
per client by construction. The property that makes them possible — one address, self-contained
requests, no instance memory — is the property this part is about.

It also changes what a deployment looks like. A stdio server is a file you can run. An HTTP server is
a thing with a URL, a certificate, a health check, an `Origin` policy
([3.4](3.4-what-a-url-costs.md)) and an authentication story (Day 37). The protocol is identical
([4.1](../04-choosing-a-wire/4.1-the-same-errand-two-ways.md)); the operational surface is not, and
that is the whole content of the choice between them.

## The paper behind it

> **Principled design of the modern Web architecture** · `doi:10.1145/514183.514185` · 2002 ·
> `https://doi.org/10.1145/514183.514185`

It argued that an architecture's useful properties — visibility, scalability, the freedom to replace
components independently — come from the constraints it accepts, and that each constraint has a named
price.

Two of those constraints are visible in this part alone: statelessness, which is why every POST
carries its own metadata and costs bytes to do so, and the uniform interface, which is why there is
one endpoint instead of a family of them. The paper is taught in full on Day 32, at
[`../../../day-32-mcp-stateless-core/papers/01-modern-web-architecture.md`](../../../day-32-mcp-stateless-core/papers/01-modern-web-architecture.md).

## The mechanism

```mermaid
sequenceDiagram
    participant C as client
    participant LB as load balancer
    participant S1 as instance 1
    participant S2 as instance 2
    C->>LB: POST /mcp  Mcp-Method: tools/list
    LB->>S1: (routed on the header)
    S1-->>C: 200 application/json
    Note over C,S2: the request is over; nothing is remembered
    C->>LB: POST /mcp  Mcp-Method: tools/call
    LB->>S2: (a different instance, and it does not matter)
    S2-->>C: 200 text/event-stream
```

What the client actually has to put on the request — from `lab/http_shape.py`:

```python
headers = {
    "Content-Type": "application/json",
    "Accept": "application/json, text/event-stream",
    "MCP-Protocol-Version": "2026-07-28",
    "Mcp-Method": message["method"],
}
if "name" in message.get("params", {}):
    headers["Mcp-Name"] = message["params"]["name"]

request = urllib.request.Request(url, data=json.dumps(message).encode(), headers=headers)
```

**Line by line:**

- `Content-Type: application/json` describes what you are sending. The body is a single JSON-RPC
  request or notification — one, never a batch.
- `Accept` is **required** to list both types, and the specification says so in a MUST: *"The client
  **MUST** include an `Accept` header listing both `application/json` and `text/event-stream` as
  supported content types."* The reason is [3.2](3.2-handed-over-or-told-to-wait.md): the server
  chooses which shape to reply with, per request, and a client that cannot accept both has taken that
  choice away.
- `MCP-Protocol-Version` is required on every POST, and its value must equal the
  `io.modelcontextprotocol/protocolVersion` inside the body's `_meta`. A mismatch is `400` with
  `-32020`, which is
  [Day 32's 3.2](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.2-the-header-that-must-match.md).
- `Mcp-Method` mirrors the body's `method`, always. `Mcp-Name` mirrors `params.name` or `params.uri`,
  and is required only for `tools/call`, `resources/read` and `prompts/get` — hence the conditional.
  Sending it when there is nothing to mirror is as wrong as omitting it when there is.
- `json.dumps(message).encode()` is the body, and note there is no newline this time. Framing on HTTP
  is `Content-Length`, so [2.2](../02-stdio/2.2-one-message-per-line.md)'s newline rule does not apply
  here at all — the same protocol, a different binding, a different set of things that can go wrong.
- What is **not** in this dictionary: no `Mcp-Session-Id`, no `Authorization` yet (Day 37), no cookie,
  and nothing left over from a previous request.

Run it against a loopback endpoint that enforces those rules:

```bash
uv run python days/day-33-client-and-transports/lab/http_shape.py
```

**Line by line:**

- The script starts a stdlib `ThreadingHTTPServer` on `127.0.0.1` with port `0`, which asks the
  operating system for any free port. That avoids the "port already in use" failure entirely, and it
  is the right pattern for a test.
- It is a **fake endpoint**, not an MCP server: it validates the transport rules and answers with
  plausible bodies. Day 34 writes the real thing.
- Two POSTs go out, one `tools/list` and one `tools/call`. Nothing connects, disconnects or
  negotiates in between.
- Zero model calls, no external network, no key.

```text
POST http://127.0.0.1:63672/mcp  Mcp-Method: tools/list
  <- 200 application/json
     {"jsonrpc": "2.0", "id": 1, "result": {"tools": [{"name": "desk_ping"}]}}

POST http://127.0.0.1:63672/mcp  Mcp-Method: tools/call
  <- 200 text/event-stream
     data: {"jsonrpc": "2.0", "method": "notifications/progress", "params": {"progress": 1, "total": 2}}
     data: {"jsonrpc": "2.0", "method": "notifications/progress", "params": {"progress": 2, "total": 2}}
     data: {"jsonrpc": "2.0", "id": 2, "result": {"content": [{"type": "text", "text": "pong"}]}}
```

Same URL twice, two independent requests, two different reply shapes. The second one is
[3.2](3.2-handed-over-or-told-to-wait.md).

## When it breaks

Send a POST that does not accept both content types and a conforming endpoint refuses it before it
looks at the body:

```bash
uv run python days/day-33-client-and-transports/lab/http_shape.py --bad-accept
```

```text
POST http://127.0.0.1:63675/mcp  Mcp-Method: tools/list
  <- 400 application/json
     {"jsonrpc": "2.0", "id": null, "error": {"code": -32600, "message": "Accept must list both content types, got 'text/plain'"}}
```

The thing to take from that is the pattern, not the wording: **the failure is an HTTP status and a
JSON-RPC error body, together.** That double shape is what makes a modern MCP endpoint
distinguishable from an old one, and the specification leans on it:

> *"On `400 Bad Request`, the client **SHOULD** inspect the response body before falling back: modern
> servers also use `400` for `UnsupportedProtocolVersionError`, `MissingRequiredClientCapabilityError`,
> and header-validation failures."*

So `400` on its own tells you nothing. A `400` whose body is a recognised JSON-RPC error means the
server is modern and your request was wrong. A `400` with an empty or unrecognised body means you may
be talking to something from before this revision, and that is
[4.2](../04-choosing-a-wire/4.2-the-route-with-a-withdrawal-date.md)'s territory.

The second break is the address itself. A URL that is missing the endpoint path — `https://host/`
instead of `https://host/mcp` — usually returns the site's own `404` page, in HTML, and the client
fails while parsing something that was never JSON. A modern MCP endpoint that does not implement a
method instead returns `404` **with** a JSON-RPC `-32601` body, which is the same distinction as
above: read the body, not the number.

The third one is peculiar to this revision and will bite anyone following an older tutorial. Open a
GET against the endpoint and you get:

```bash
uv run python days/day-33-client-and-transports/lab/http_shape.py --get
```

```text
GET http://127.0.0.1:63682/mcp
  <- 405
     {"jsonrpc": "2.0", "id": null, "error": {"code": -32601, "message": "Method Not Allowed: this revision has no GET stream"}}
```

That GET was, until `2025-11-25`, how a client opened a standalone stream for server-initiated
messages. It is gone. `405` is the specified answer, alongside ignoring `Mcp-Session-Id` and
`Last-Event-ID` rather than honouring them.

## In production

**What a professional writes instead:** the URL is configuration with a scheme check —
`https` in anything but local development — and the client never builds a second path from it. A
common and quietly wrong habit is storing the base URL and appending `/mcp` in code; the endpoint
path is part of the address the server publishes, so store the whole thing and let the server decide
what it is called.

**What degrades at scale:** per-request overhead. Every message pays for headers, and
[Day 32's 2.3](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.3-every-request-introduces-itself.md)
measured the `_meta` block at about 184 bytes repeated forever. On a chatty agent that is real
bandwidth, and it is the price the paper above says every constraint has. What you buy is that the
load balancer in the diagram can send the second request anywhere, which is the entire reason Day 43's
deployment can scale at all.

**The failure mode that only appears with real traffic:** connection pool exhaustion. MCP has no
connections, but `httpx` does, and a client that builds a new `AsyncClient` per request — or never
closes the ones it builds ([1.5](../01-the-connector/1.5-somebody-has-to-give-it-back.md)) — will
exhaust file descriptors under load while every individual request looks perfect. The symptom is
latency that grows with uptime and recovers on restart.

**The review comment a senior engineer leaves:** *"this treats a `400` from the MCP endpoint as
'server is old, fall back to `initialize`'. The spec is explicit that modern servers also return
`400` for a version mismatch and for header validation, so this will silently downgrade a perfectly
modern server the first time we send a bad header. Parse the body and only fall back when it is not a
JSON-RPC error."*

**The interview question:** *"walk me through what happens on the wire when your agent calls a tool
over Streamable HTTP."* Keep it concrete: *"One HTTP POST to the server's single MCP endpoint,
carrying the whole JSON-RPC request in the body, with the protocol version, the method and the tool
name mirrored into headers so a gateway can route without parsing. That is the entire exchange —
there is no connect step, because the 2026-07-28 revision removed the handshake and the session. The
reply comes back either as one JSON object or as an SSE stream scoped to that request, so the client
has to accept both. The practical consequence is the one I care about: any instance can serve any
request, so the load balancer needs no stickiness and we can scale the server without touching the
client."*
