# 4.1 — A red build is a decision

## One-line answer

A gate that fails on every difference fails on every new case, so the rule cannot be "something
moved" — it has to name **which** differences stop a merge, and on this fixture that is one of the
three that moved.

## The story

The barrier at the level crossing.

It comes down when a train is coming. Not when the wind blows, not when a goods wagon is shunting on a
siding two hundred metres away, not when the signalman is testing something. When a train is coming
and only then, because the barrier is not a warning — it is an instruction to stop, and an instruction
to stop that arrives when there is nothing to stop for is an instruction people learn to drive around.

Everybody has seen the other kind: a barrier that is down more often than it needs to be, and a queue
of people who have worked out that if it has been down for five minutes with no train in sight, it is
the fault one, and somebody lifts it by hand.

The barrier did not fail. It came down, exactly as designed, more often than the situation warranted —
and the mechanism that failed was the agreement that a lowered barrier means stop.

## The idea in plain language

Part [2.3](../02-the-result-is-a-file/2.3-comparing-two-runs.md) produced a comparison with four rows
and three categories. This part is about which of those categories a build should refuse to go green
on, and it is a **decision** rather than a computation.

Three candidate rules, and only the third survives:

**"Fail if the suite is red."** Fails on a case that is red on its first run — `escalation_wording` in
the fixture — which is a case somebody added five minutes ago and has not made pass yet. A rule that
blocks the commit that adds a case is a rule that stops people adding cases.

**"Fail if anything moved."** Fails on all three, including the judge flip that Day 81 part 1.2
measured happening on identical answers. Part [4.2](4.2-flaky-by-construction.md) is about what a gate
that fails on judge noise does to a team.

**"Fail if a case that used to pass now fails, because the system under test changed."** One of the
three. That is the sentence, and every clause in it is doing work: *used to pass* excludes new cases,
*now fails* excludes drift that has not crossed a threshold, and *because the system changed* excludes
the instrument and the data — which is the whole of part
[1.2](../01-what-a-regression-is/1.2-three-things-that-move-a-number.md).

The other two categories still have to go somewhere, and "nowhere" is not an option:

| Category | The build | Where it goes |
| --- | --- | --- |
| the desk changed and a case broke | **red** | the author of the commit |
| the judge flipped | green | a counter, watched over weeks |
| a new case is red | green | the author, as information |
| CANNOT TELL | **red** | whoever owns the harness |

The last row is the one people leave out. Part
[1.2](../01-what-a-regression-is/1.2-three-things-that-move-a-number.md)'s unattributable difference is
not a pass — it is a comparison that could not be made, and a build that goes green on it has silently
decided that not knowing is fine. `compare.py` exits 1 on exactly that, which is why its
`--unrecorded` arm is red.

And there is a fourth thing a gate must refuse that has nothing to do with the desk at all: **the
suite failing to be a suite.** The four meta-checks from part
[3.1](../03-two-cadences/3.1-the-fast-half-on-every-commit.md) — stub, prompt, spread, baseline — are
free, deterministic and fast, and a build that goes green while any of them is red has been told that
the measurement is broken and merged anyway.

## Why Sutra needs it

Because Sutra's gate is `./m check`, and it has had the same shape since Day 0: lint, format, tests,
depth, trace, wiki. Six things, all deterministic, all free, and a red one stops the commit. Adding
eval checks to that list means deciding which of them get that authority.

And because Day 83's gate is one day away and asks whether the eval suite is green. A suite whose CI
rule is "fail if anything moved" is a suite that has been red for a fortnight and been ignored for
thirteen days of it, and no gate can read anything from that.

## The mechanism

The rule, expressed as which categories are fatal. From `lab/nightly.py`'s filter, which part
[3.2](../03-two-cadences/3.2-the-full-run-rides-the-nightly.md) introduced and which is the same rule
CI needs:

```python
    regressions = [
        case
        for case in new
        if case in old and classify(case, old.get(case), new[case], True) == "the desk changed"
    ]
```

**Line by line:**

- `case in old` is the *used to exist* clause. A new case cannot be a regression, so
  `escalation_wording` is excluded here regardless of its score.
- `classify(...) == "the desk changed"` is the *because the system changed* clause, and it is an
  equality against one category rather than an inequality against several. Written as `!= "a new case"`
  it would include the judge flip, and the difference between those two spellings is part
  [4.2](4.2-flaky-by-construction.md).
- The `True` for `judge_recorded` is a **precondition**, not a convenience. With it false, `classify`
  returns `CANNOT TELL` and this list is empty — the gate would go green on a night nobody could
  attribute. That is why the unattributable row in the table above is red at a different level:
  `compare.py`'s own exit code, not this filter.
- It filters rather than counting. The build needs the **names**, because a red build whose message is
  "2 regressions" sends somebody to re-run it locally.

And the gate's own shape, which is two commands rather than one:

```bash
uv run python compare.py            # exits 1 if any difference is unattributable
uv run python nightly.py            # exits 1 if any attributable regression is the desk
```

**Line by line:**

- Two exit codes because there are two questions. The first is about the **harness** — can this
  comparison be made at all — and the second is about the **desk**. Collapsing them into one command
  produces a red build with two possible meanings and one owner.
- `compare.py` runs first. There is no point asking what regressed if the comparison is not
  attributable, and running them in this order means the first failure is the informative one.
- Neither of these is the meta-check set from part
  [3.1](../03-two-cadences/3.1-the-fast-half-on-every-commit.md), which runs earlier still and for
  free.

Run the comparison as CI would:

```bash
cd days/day-82-regression-discipline/lab
uv run python compare.py; echo "exit: $?"
```

**Line by line:**

- Both runs' versions are recorded, so every difference is attributable and the harness question is
  answered.

Measured on 2026-09-06:

```text
  case                metric                         was   now  why
  one_lookup          tool_trajectory_avg_score      1.0   0.0  the desk changed
  refund_limit        final_response_match_v2        1.0   0.0  the judge flipped on an identical answer
  escalation_wording  tool_trajectory_avg_score        -   1.0  a new case, never run before
  escalation_wording  final_response_match_v2         -   0.0  a new case, never run before

  4 differences, 3 cases affected
  every difference has a cause, and only one of them is the desk
exit: 0
```

Then the gate:

```bash
uv run python nightly.py; echo "exit: $?"
```

**Line by line:**

- The gate runs after the comparison, because there is no point deciding what regressed until
  the comparison has been made at all.

Measured on 2026-09-06:

```text
  evals: 6 of 9 passed, REGRESSED: one_lookup
  (3 cases moved; 1 of them because the desk changed)

  the comparison's verdict is the job's exit code
exit: 1
```

**Four differences, one red build, and the message names the case.** `REGRESSED: one_lookup` is the
whole of what somebody needs at the top of a failed build — one name, and the case id is a name because
Day 79 part 1.3 insisted it be one.

Now the harness question, failing on its own:

```bash
uv run python compare.py --unrecorded; echo "exit: $?"
```

**Line by line:**

- `--unrecorded` is the same two runs with the judge model not written down — part
  [1.3](../01-what-a-regression-is/1.3-what-has-to-be-written-down.md)'s missing field.

Measured on 2026-09-06:

```text
  refund_limit        final_response_match_v2        1.0   0.0  CANNOT TELL: judge flip or judge upgrade
...
    - refund_limit: a person says 'the judge flipped on an identical answer', the comparison says 'CANNOT TELL: judge flip or judge upgrade'
  a difference was reported without a cause somebody can act on
exit: 1
```

**A red build with a different owner.** Nothing about the desk changed between these two commands. The
build is red because the harness cannot answer, and the person who fixes that is whoever writes the
results file — not whoever wrote the commit.

## When it breaks

The rule breaks by being widened, and it is widened for a good reason each time.

A judge flip causes a real problem one week and somebody adds judge flips to the fatal set. A new case
is added red and somebody merges it anyway, so the next person adds a rule about new cases. Each change
makes the build red more often, and the cost is not the reds — it is that after enough of them the
build's redness stops carrying information and people start reading the diff instead of the status.

There is no error text. The observable is a number nobody measures: **the fraction of red builds that
resulted in a change to the system under test.** When that fraction falls below about a half, the gate
has become advisory, and the next stage is part [4.2](4.2-flaky-by-construction.md).

The other direction breaks too, and more quietly. Narrow the rule to *"fail only when a case that used
to pass now fails"* without the attribution clause, and a judge upgrade that moves twenty cases turns
the build red and gets attributed to the commit that happened to be merging. The author looks at their
change, finds nothing, re-runs, and it is still red — which is how a team learns that the eval gate is
not about their code.

The smallest defence is to make the rule **explicit and reviewable**: one function, named, with the
categories it treats as fatal written out, so widening it is a diff somebody sees rather than a
condition somebody edits.

## In production

**What a professional writes into the pipeline.** Two gates with two owners. A **harness** gate — the
meta-checks and the attributability check — owned by whoever maintains the suite, and a **desk** gate
owned by whoever wrote the commit. Same pipeline, different failure messages, different people paged.
A single red that could mean either is a red that gets forwarded rather than fixed.

**What degrades at scale.** The categories multiply. With one judged metric there are three; with five
metrics, a rubric and two judges there are a dozen, and the fatal set becomes a policy document. The
teams that survive it keep the *default* narrow — the desk changed and a case broke — and require a
written reason for anything added, which is the same discipline Day 80 part 3.1 applied to gate rubric
lines.

**The failure that only shows with real traffic.** A regression that is real, attributable, and not
the commit's fault. Two changes merged within an hour, the second one's build is the one that runs
after both are on the branch, and the gate names the second author. Part
[papers/01](../../papers/01-which-change-broke-it.md) is the mechanical answer to that and it is
needed precisely because "the build that went red" and "the change that caused it" are not the same
thing once more than one change is in flight.

**The review comment a senior engineer leaves:** *"Write the fatal set as one function with a name.
Right now it is a list comprehension in the nightly and a different condition in CI, and the day those
two disagree is the day somebody merges a regression because the local run was green."*

**The interview question:** *"When should an evaluation failure block a merge?"* The answer that shows
experience does not say "when it fails". It distinguishes a case that never passed from one that
stopped passing, and a change in the system under test from a change in the evaluator — and then names
the cost of getting it wrong in the loose direction, which is that people stop reading the status.
