# 1.3 — What has to be written down

## One-line answer

A comparison can only attribute a difference to things it was told about, so the fields a results
file carries **are** the questions it can answer — and four strings, written once per run, are the
difference between "the desk regressed" and "we cannot tell".

## The story

The logbook in the boiler room, ruled into columns.

Date. Time. Pressure. Temperature. Water treated, yes or no. Who was on. Six columns, filled in twice
a shift by somebody who has done it a thousand times and thinks of it as a chore.

The columns were not chosen at once. Every one of them is there because a question was asked that
nobody could answer. *Was the water treated on Tuesday?* — nobody knew, so there is a column. *Who was
on when the pressure dropped?* — nobody knew, so there is a column.

And the thing about the book is that it is completely useless on the day you write in it. Its entire
value is on some future morning when a question is asked, and the value is exactly bounded by which
columns exist. A question about something with no column has no answer, and no amount of care on the
day will produce one afterwards.

## The idea in plain language

Part [1.2](1.2-three-things-that-move-a-number.md) established that three things move an eval score
and only one of them is the desk. This part is the consequence: **the fields you record determine the
questions you can answer.**

That is worth stating as a rule because it inverts how record-keeping is usually justified. The
question is not *"what would be nice to store?"* — it is *"which questions will somebody ask at eight
in the morning, and which field answers each?"*

For a regression comparison the questions are known, and there are four:

| The question | The field that answers it |
| --- | --- |
| Did the thing under test change? | the desk's version |
| Did the instrument change? | the judge's model **and its provider version string** |
| Did the data change? | the evalset's content hash |
| Which run was this, and when? | the timestamp, which ADK already writes |

Four values. Three of them are strings and the fourth is already there. That is the whole cost, and it
is paid once per run rather than once per case.

Two properties of that list are worth arguing for, because both get compromised.

**The judge needs a *version*, not a name.** `gemini-2.5-flash-lite` is an alias, and Day 81 part 5.1's
hardest failure is a hosted model changing behind a stable alias. Recording the alias tells you that
nobody edited the config; it does not tell you the rater is the same rater. Where a provider exposes a
version string, that is the value to store.

**The evalset needs a hash, not a version number.** A version number is a thing somebody has to
remember to increment, and nobody does. A content hash of the evalset file is computed, always
correct, and free — and it changes when a reference answer is reworded, which is exactly the silent
data change Day 79 part 1.1 warned about.

And the fourth answer stays available. If two of the four moved, the honest output is *cannot tell* —
part [1.2](1.2-three-things-that-move-a-number.md)'s `CANNOT TELL` line, which exists precisely
because the alternative is a confident wrong attribution.

## Why Sutra needs it

Because ADK's own result type has none of these. `EvalSetResult.model_fields` on the installed
`google-adk==2.7.1` is `eval_set_result_id`, `eval_set_result_name`, `eval_set_id`,
`eval_case_results` and `creation_timestamp`; `EvalCaseResult` adds the per-case scores and a session
id. Nowhere in either is the judge, the desk or the data.

That is not a criticism of the library — a results type cannot know what your system's versions are —
and it does mean the four fields have to be added by whatever writes the file. Part
[2.1](../02-the-result-is-a-file/2.1-the-result-is-a-file.md) reads the type and part
[5.2](../05-in-production/5.2-what-a-real-regression-suite-adds.md) puts the wrapper on the list.

## The paper behind it

> **Yesterday, my program worked. Today, it does not. Why?**

> <https://doi.org/10.1145/318774.318946>

It took the question this part's title asks and made it mechanical: given a working version and a
broken one, systematically narrow the set of changes between them to the ones that actually cause the
failure.

## The mechanism

The version fields, and where they have to live. From `lab/_runs.py`:

```python
# The judge and the desk, as they were on each night. A results file that does not record these
# cannot tell you which of the three changed - part 1.2.
LAST_NIGHT_JUDGE = "gemini-2.5-flash-lite"
TONIGHT_JUDGE = "gemini-2.5-flash-lite"
LAST_NIGHT_DESK = "prompt-v7"
TONIGHT_DESK = "prompt-v8"
```

**Line by line:**

- These are module constants in the **fixture**, not fields on the `EvalSetResult`, because the
  library's record type has nowhere to put them. In a real system they would be written into the file
  by a wrapper — part [5.2](../05-in-production/5.2-what-a-real-regression-suite-adds.md) item 1.
- `LAST_NIGHT_JUDGE` and `TONIGHT_JUDGE` are separate constants rather than one. Two runs, two
  recordings: a single "the judge model" constant would be the *current* judge, applied
  retrospectively to a run that may have used something else, which is the shape of the error this
  part exists to prevent.
- They are **model aliases**, and the docstring of this part says why that is the weaker version.
  The fixture uses an alias because that is what a provider gives you here; the rule is to store
  whatever the provider will tell you and to be honest that an alias is not a version.

And the shape of the wrapper a real system needs, which is four lines around ADK's own record:

```python
def save_with_provenance(manager, app, eval_set_id, cases, desk, judge, evalset_path):
    """ADK's save, plus the four fields a comparison needs. One extra file per run."""
    manager.save_eval_set_result(app, eval_set_id, cases)
    newest = sorted(manager.list_eval_set_results(app))[-1]
    provenance = {
        "result": newest,
        "desk": desk,
        "judge": judge,
        "evalset_sha256": hashlib.sha256(Path(evalset_path).read_bytes()).hexdigest()[:12],
    }
    Path(f"{newest}.provenance.json").write_text(json.dumps(provenance, indent=2))
```

**Line by line:**

- It calls ADK's `save_eval_set_result` unchanged and writes a **sibling file** rather than
  subclassing the result type. That is deliberate: the library owns its schema, and a wrapper that
  adds a field to somebody else's pydantic model breaks on the next upgrade.
- `sorted(...)[-1]` recovers the name ADK generated, because `save_eval_set_result` returns `None` on
  2.7.1 — the id is built inside `create_eval_set_result` from the app name, the eval set id and
  `time.time()`, and is not handed back. Sorting works because the name ends in a timestamp.
- `hashlib.sha256(...).hexdigest()[:12]` is the evalset's content hash, truncated to something a
  person can read in a report. Twelve hex characters is what git uses for a short hash and it is
  enough to notice a change.
- `judge` is passed in rather than read from the criterion, so the caller records what it actually
  configured. Reading it back from the evaluator would be better and is not available once the run has
  finished.
- The provenance goes in a file named after the result, so the two are joinable without any index.

**Line by line:**

  case                metric                         was   now  why

Now make one of the four fields disagree. Change `TONIGHT_JUDGE` to `"gemini-2.5-flash"` in
`_runs.py` and run it again:

```bash
uv run python compare.py; echo "exit: $?"
```

**Line by line:**

- Nothing about the scores has changed. One recorded string is different, which means the run is now
  known to have used a different rater.

Measured on 2026-09-06:

```text
  one_lookup          tool_trajectory_avg_score      1.0   0.0  the desk changed
  refund_limit        final_response_match_v2        1.0   0.0  the judge model changed, so this is not comparable
```

**Read the second row across the two runs.** Same scores, same case, same desk. With the judge
recorded as unchanged, the difference is *"the judge flipped on an identical answer"* — a known,
tolerable thing that Day 81 part 1.2 measured. With the judge recorded as changed, the difference is
*"not comparable"* — because two different raters graded the two nights and no amount of arithmetic
recovers a comparison from that.

Three outputs from one pair of results files, decided entirely by one recorded string:

| The judge field says | The comparison says |
| --- | --- |
| the same model both nights | the judge flipped on an identical answer |
| different models | not comparable |
| nothing (part 1.2's `--unrecorded`) | CANNOT TELL, and the run exits 1 |

## When it breaks

Fields break by being **recorded wrongly rather than not at all**, and that is worse, because a
missing field produces `CANNOT TELL` and a wrong one produces a confident answer.

Three specific ways:

**The version is read at report time rather than at run time.** A comparison that looks up "the judge
model" from the current config attributes both nights to today's judge. Every historical comparison
silently becomes wrong the moment the config changes, and nothing in any file is incorrect — the file
never claimed anything.

**The alias is recorded and the model moved underneath it.** `gemini-2.5-flash-lite` on both nights,
and the provider updated it. The comparison says "the judge flipped", which is the most plausible
wrong answer available.

**The evalset hash is computed over the wrong bytes.** Hash the file after a formatter has touched it,
or hash a directory listing rather than the contents, and the field changes when nothing did — which
trains people to ignore it.

There is no error text for any of these. What you get is the boiler-room book with a column somebody
filled in from memory: worse than blank, because blank prompts a question.

The smallest fix is to write provenance **at the moment of the run, from the objects that were
actually used** — not from configuration read later, and not from a constant somebody maintains. That
is why the wrapper above takes `judge` as an argument from the caller who configured the evaluator
rather than looking it up.

## In production

**What a professional writes into every run.** A provenance block: the commit hash of the system under
test, the judge model and whatever version string the provider exposes, the evalset's content hash,
the harness's own version, and the timestamp. Five values, one block, written by the runner rather
than by a person — because anything a person has to remember is a field that will be wrong on the run
that matters.

**What degrades at scale.** The number of things that could have moved grows and the provenance block
grows with it, and there is a real temptation to stop at the two obvious ones. The discipline that
survives is not "record everything" — it is to record whatever appears in a *question somebody
actually asked*, which is how the boiler-room book got its columns, one incident at a time.

**The failure that only shows with real traffic.** Provenance and results drift apart. The results file
is written by the harness and the provenance by a deploy script, they end up in different places with
different retention, and six months later there are results with no provenance and provenance with no
results. Writing them as one artefact — or naming one after the other, as the wrapper above does — is
the cheap defence.

**The review comment a senior engineer leaves:** *"Write the provenance in the same function that
writes the results, from the objects that produced them. Not from config, not from environment
variables read later. And hash the evalset — a version number is a thing we will forget to bump, and
the reference-wording changes are exactly the ones that will confuse us."*

**The interview question:** *"What do you store alongside a test result so that it is still useful in
six months?"* The answer that shows experience works backwards from the questions — what changed in
the system, in the harness, in the data — and names the field for each, rather than listing metadata.
The tell is whether they mention capturing it at run time rather than at report time.
