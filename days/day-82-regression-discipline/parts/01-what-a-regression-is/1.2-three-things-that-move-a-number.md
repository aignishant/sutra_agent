# 1.2 — Three things that move a number

## One-line answer

An eval score has three inputs — **the desk**, **the judge** and **the data** — and only one of them
is the thing you are trying to measure, so a number that moved is a question about which of the three
changed, not an answer about the desk.

## The story

The electricity bill goes up by four hundred rupees and there is an argument at the table.

Somebody says it is the new geyser. Somebody says the children leave the fan on. Somebody says the
meter is wrong.

All three are the same shape of claim and only one of them can be settled by looking at the
appliance. The second is about behaviour and the third is about the instrument, and the reason the
argument goes round in circles for a week is that the bill is a single number produced by all three
at once.

What ends it, eventually, is somebody noticing the small print: the tariff changed on the first of the
month. Nobody used more of anything. The units are the same as last month. The **rate** moved, and
the rate is not written on the front of the bill.

## The idea in plain language

Part [1.1](1.1-a-regression-is-a-comparison.md) established that a regression is a comparison. This
part is about what a comparison has to control for.

Every judged eval score is produced by three things, and a change in any of them moves the number:

**1. The system under test — the desk.** Its prompt, its model, its tools, its code. This is the only
one you are trying to measure, and it is the only one anybody thinks about.

**2. The instrument — the judge.** Its model, its version, its sampling, its threshold. Day 81 part
1.2 measured a judge disagreeing with itself 3–2 on every case; Day 81 part 5.1 named the harder
version, which is a hosted model changing underneath a stable model string.

**3. The data — the cases and their references.** A case added, a reference reworded, a fixture whose
ticket aged by a day. Day 79 part 1.1's **In production** section named it: reference answers age, and
a suite reports a regression on the day the product got better.

The awkward property is that **all three produce the same observable**: a score that used to be one
thing and is now another. There is nothing in the number that distinguishes them, and there is nothing
in ADK's `EvalCaseResult` either — part
[2.1](../02-the-result-is-a-file/2.1-the-result-is-a-file.md) reads its fields and none of them is a
version of anything.

So the comparison has to be given the information from outside, and the rule is short: **record what
each run used, and attribute a difference only when everything else held still.** Three fields is
enough to start:

| Field | Answers |
| --- | --- |
| the desk's version | did the thing under test change? |
| the judge's model and version | did the instrument change? |
| the evalset's version | did the data change? |

And there is a fourth answer, which is the one people leave out: **cannot tell.** If two of the three
moved at once, the difference is not attributable, and saying so is more useful than picking the
familiar cause. That is Day 78 part 4.4's three-valued discipline again — *fits*, *over*, **cannot
say** — arriving in a completely different place.

Which metric moved is a clue, and it is worth knowing how far it goes. A change in
`tool_trajectory_avg_score` is almost always the desk: the metric is deterministic, so nothing about
the judge can move it. A change in `final_response_match_v2` could be any of the three. That asymmetry
is the strongest free signal a suite has, and it is one more reason to keep Day 79's deterministic
metrics alongside the judged one rather than replacing them.

## Why Sutra needs it

Because the nightly is about to run all three of these together, unattended, and report one number.
Day 73's job re-indexes, Day 82 adds the eval stage, and the desk, the judge and the fixture all live
in the same repository and all change.

And because Day 81 left a specific hazard open. Addendum 02 puts eval traffic on `gemini-2.5-flash-lite`
for cost reasons; that is a hosted model, and Day 81 part 5.1 established that the calibration is void
when it changes. A judged score that moves on a night nobody deployed anything is exactly the case
this part is about, and without a recorded judge version there is no way to reach that conclusion.

## The mechanism

The three versions are recorded in the fixture, because ADK's result type has nowhere to put them.
From `lab/_runs.py`:

```python
# The judge and the desk, as they were on each night. A results file that does not record these
# cannot tell you which of the three changed - part 1.2.
LAST_NIGHT_JUDGE = "gemini-2.5-flash-lite"
TONIGHT_JUDGE = "gemini-2.5-flash-lite"
LAST_NIGHT_DESK = "prompt-v7"
TONIGHT_DESK = "prompt-v8"
```

**Line by line:**

- Four constants, two per run. They are in the **fixture** rather than in the `EvalSetResult` because
  `EvalSetResult.model_fields` on the installed `google-adk==2.7.1` is
  `eval_set_result_id, eval_set_result_name, eval_set_id, eval_case_results, creation_timestamp` —
  there is no field for either.
- The judge is **the same** on both nights and the desk is **different**. That is the fixture's
  design: it makes the desk the only moving part, so a difference in the deterministic metric is
  attributable and a difference in the judged one is a flip rather than an upgrade.
- The evalset version is not here, and its absence is honest: the fixture has one case set with one
  case added, which part [1.1](1.1-a-regression-is-a-comparison.md) handles as a separate category.
  A real system needs the third field too.

And the attribution, which is a small decision tree:

```python
def classify(case: str, before: dict | None, after: dict, judge_recorded: bool) -> str:
    """Why did this case's result change? The last answer is 'we cannot tell'."""
    if before is None:
        return "a new case, never run before"
    moved = [m for m in after if before.get(m) != after.get(m)]
    if moved == [TRAJECTORY]:
        return "the desk changed"
    if moved == [JUDGED] and not judge_recorded:
        return "CANNOT TELL: judge flip or judge upgrade"
    if moved == [JUDGED] and TONIGHT_JUDGE == LAST_NIGHT_JUDGE:
        return "the judge flipped on an identical answer"
    if moved == [JUDGED]:
        return "the judge model changed, so this is not comparable"
    return "several metrics moved"
```

**Line by line:**

- `before is None` is checked **first**, so a case with no yesterday is categorised before any
  comparison is attempted. It is not a change; there is nothing to compare it against.
- `moved == [TRAJECTORY]` — the deterministic metric alone moved, so the judge cannot be responsible.
  This is the asymmetry above, encoded: the comparison is *more confident* about the cheap metric than
  about the expensive one.
- `not judge_recorded` comes **before** the equality check, because if you did not record the model
  you cannot ask whether it changed. Ordering these two the other way round would silently claim "the
  judge flipped" on runs where nobody knows.
- `"CANNOT TELL: judge flip or judge upgrade"` is a fourth outcome and it is in capitals. Part
  [2.3](../02-the-result-is-a-file/2.3-comparing-two-runs.md) is where it becomes an exit code.
- `moved == [JUDGED]` twice, with different guards, rather than a nested `if`. Written flat, each line
  is one attributable situation with its condition next to it, which is what a reader needs to check
  the logic against the table above.
- The fall-through — `"several metrics moved"` — is deliberately vague, because when two metrics move
  on one case there is nothing honest to say beyond that.

Run the comparison with the versions recorded:

```bash

```

**Line by line:**

- No flag: both runs' desk and judge versions are known, so every difference is attributable.

Measured on 2026-09-06:

```text

tonight:    desk prompt-v8, judge gemini-2.5-flash-lite

  case                metric                         was   now  why
  one_lookup          tool_trajectory_avg_score      1.0   0.0  the desk changed
  refund_limit        final_response_match_v2        1.0   0.0  the judge flipped on an identical answer
  escalation_wording  tool_trajectory_avg_score        -   1.0  a new case, never run before
  escalation_wording  final_response_match_v2         -   0.0  a new case, never run before

  4 differences, 3 cases affected
  every difference has a cause, and only one of them is the desk
exit: 0
```

**Read the two version lines at the top before the table.** They are what make the third column
possible: the desk moved from `prompt-v7` to `prompt-v8`, the judge did not move at all, so a
trajectory change is the desk and a judged change is the judge being uncertain rather than being
replaced.

Now take the judge's version away:

```bash
uv run python compare.py --unrecorded; echo "exit: $?"
```

**Line by line:**

- `--unrecorded` runs the identical two results files with the judge model treated as not written
  down. Nothing about the scores changes.

Measured on 2026-09-06:

```text
last night: desk prompt-v7, judge not recorded
tonight:    desk prompt-v8, judge not recorded

  case                metric                         was   now  why
  one_lookup          tool_trajectory_avg_score      1.0   0.0  the desk changed
  refund_limit        final_response_match_v2        1.0   0.0  CANNOT TELL: judge flip or judge upgrade
  escalation_wording  tool_trajectory_avg_score        -   1.0  a new case, never run before
  escalation_wording  final_response_match_v2         -   0.0  a new case, never run before

  4 differences, 3 cases affected
    - refund_limit: a person says 'the judge flipped on an identical answer', the comparison says 'CANNOT TELL: judge flip or judge upgrade'
  a difference was reported without a cause somebody can act on
exit: 1
```

**One row changed, and it changed from an answer to a question.** Same scores, same cases, same
desk — one field missing from the results file, and a difference that was attributable is now
unattributable.

Notice which row survived. `one_lookup` is still `the desk changed`, because the deterministic metric
cannot be moved by a judge and the comparison knows that without needing any version at all. The free
metric is the one that keeps working when the record-keeping does not.

## When it breaks

The failure is not the `CANNOT TELL` line. That line is the system working — it is an honest report of
a limit.

The failure is what happens when nobody wrote that branch. A comparison that has no fourth outcome
must attribute every difference to one of the three, and the one it will pick is the desk, because the
desk is the thing everybody assumes changed. So the report reads:

```text
  refund_limit        final_response_match_v2        1.0   0.0  the desk changed
```

which is confident, plausible, and wrong. Somebody spends a morning on `prompt-v8` looking for the
change that broke a case whose answer is byte-identical to last night's.

There is no error text. The tell is a specific pattern that is worth learning to recognise: **a judged
metric moved and the deterministic metric did not**, on a case whose input did not change. When the
cheap metric says the path is identical and the expensive one says the answer got worse, the answer
did not get worse. Something about the instrument moved.

The smallest fix is three strings in the results file. Not a schema, not a service — the desk's
version, the judge's model, and the evalset's version, written next to the scores, which is part
[1.3](1.3-what-has-to-be-written-down.md).

## In production

**What a professional records with every run.** A small block of provenance: the commit of the system
under test, the judge model **and its version string as reported by the provider**, the evalset's
content hash, and the date. Four values, written once per run, and they turn every future comparison
from an argument into a lookup.

**What degrades at scale.** The number of things that can move grows. A real deployment has a desk
version, a judge version, a prompt template version, a tool schema version and an evalset version, and
a difference is attributable only when all but one held still — which becomes rarer as the system gets
busier. Mature teams solve it by **not changing two things in one run**: the nightly runs against a
pinned judge, and judge upgrades get their own deliberate comparison run.

**The failure that only shows with real traffic.** The judge changes without anybody deploying
anything. A hosted model is updated behind a stable name and every judged score shifts on a night with
an empty deploy log — which reads as *"the desk regressed with no changes"* and is the single most
confusing report an eval suite can produce. The only defence is recording the provider's version
string rather than the model alias, and even that is only as good as what the provider exposes.

**The review comment a senior engineer leaves:** *"Every results row needs the judge model on it. And
put a rule in the runbook: we do not change the judge and the desk in the same night. If we are
upgrading the judge, that gets its own run against the previous night's desk, and we compare judges
rather than pretending we are comparing desks."*

**The interview question:** *"Your evaluation score dropped overnight and nobody deployed anything.
What do you check?"* The answer that shows experience does not go to the system under test. It asks
what else could have moved — the judge, the data, the fixture's dates — and can name the signal that
points at the instrument, which is the deterministic metric staying put while the judged one moves.
