# 1.1 — A regression is a comparison, not a failure

## One-line answer

A red suite tells you the system is not passing; a **regression** tells you it used to — and those
are different claims needing different evidence, because the second one requires a record of
yesterday that most projects do not keep.

## The story

The child's height marked on the door frame.

There is a pencil line, and next to it a date. Then another one, six months later, a bit higher.
Then another.

Now suppose the lines were not there. You could still measure the child today — you would get a
number, and it would be correct. What you could not do is answer the only question anybody actually
asks, which is *is she growing normally*, because that question is not about today's number. It is
about today's number **and** the ones before it, and the space between them.

The measurement is easy. Everybody has a tape. What is rare is the door frame: somebody, on a
Tuesday, thinking to make a mark that will not be useful for six months, and then not painting over
it.

## The idea in plain language

Days 79 to 81 built a suite that produces a verdict. Today is about producing a verdict **relative
to a previous one**, and the distinction is worth being exact about because the two words get used
interchangeably.

- A **failure** is a claim about now: this case did not pass. It needs one run.
- A **regression** is a claim about a change: this case used to pass and now does not. It needs
  **two** runs and a way to line them up.

Everything that makes regression testing hard follows from that second sentence. You need
yesterday's result, stored somewhere it survives, in a form that can be compared with today's, with
enough recorded alongside it to know that the comparison is fair. Part
[1.2](1.2-three-things-that-move-a-number.md) is about what "fair" requires and part
[2.2](../02-the-result-is-a-file/2.2-the-history-this-repo-throws-away.md) is about where this
repository currently puts it.

Two consequences, and the second is the one that changes what you build.

**A regression is not necessarily a failure and a failure is not necessarily a regression.** A case
that has been red since it was written is a failure and not a regression — it never worked. A case
whose score fell from 0.95 to 0.84 without crossing its threshold is a regression and not a failure —
it is still passing, and it is on its way somewhere. Watching only for red misses the second entirely,
which is the argument for keeping scores rather than statuses that
[Day 79 part 1.1](../../../day-79-evals-are-tests/parts/01-a-test-with-a-score/1.1-a-test-that-answers-how-much.md)
made.

**The comparison has to be against a stored artefact, not against a memory.** *"It was green last
week"* is not a comparison. It is a recollection, and the reason it is not enough is not that people
misremember — it is that "green" is one bit, and the useful comparison is over per-case scores, which
nobody remembers.

## Why Sutra needs it

Because Phase 12 built three instruments over three days and has run each of them exactly once.
Day 79's trajectory and ROUGE metrics, Day 80's rubric, Day 81's judge — every measurement in those
days is a single reading, and a single reading cannot say whether anything moved.

And because Day 73 put a nightly job on a clock and Day 78 priced it. The eval suite is about to
become the largest stage of that job, running every night without anybody present, which is exactly
the situation in which the difference between "it is red" and "it went red" decides whether anybody
is woken up.

## The mechanism

The two runs are fixtures, so the comparison is over fixed data. From `lab/_runs.py`:

```python
# Last night: eight cases, all green.
LAST_NIGHT_CASES = [
    _case("counts", 1.0, 1.0),
    _case("age_4740", 1.0, 1.0),
    ...,
]

# Tonight: one real regression, one judge flip, one new case, five unchanged.
TONIGHT_CASES = [
    _case("counts", 1.0, 1.0),
    ...,
    _case("one_lookup", 0.0, 1.0),  # the desk started reading the whole queue: a real regression
    ...,
    _case("refund_limit", 1.0, 0.0),  # the judge flipped; the answer is byte-identical
    _case("oldest_ticket", 1.0, 1.0),
    _case("escalation_wording", 1.0, 0.0),  # a case somebody added today, red on its first run
]
```

**Line by line:**

- `_case(eval_id, trajectory, judged)` builds an `EvalCaseResult` — ADK's own record type, not one
  this lab invented. Part [2.1](../02-the-result-is-a-file/2.1-the-result-is-a-file.md) reads its
  fields off the installed package.
- Two metric scores per case: `tool_trajectory_avg_score` from Day 79 and `final_response_match_v2`
  from Day 81. Two is the minimum that makes part
  [1.2](1.2-three-things-that-move-a-number.md)'s question answerable, because *which* metric moved
  is the first clue about *what* moved.
- The three comments name the three kinds of difference, and they are the whole design of the
  fixture: a real regression, a flip that is not one, and a case that has no yesterday. A fixture
  with only the first would teach that comparison is easy.
- `escalation_wording` is red on its first run — a **failure that is not a regression**, which is the
  distinction this part is about, sitting in the data.

And the truth, written down separately so the comparison can be checked rather than believed:

```python
# Which of tonight's three differences is which. Written down by a person, so `compare.py` can be
# checked against it rather than believed.
TRUTH = {
    "one_lookup": "the desk changed",
    "refund_limit": "the judge flipped on an identical answer",
    "escalation_wording": "a new case, never run before",
}
```

**Line by line:**

- This is a **reference**, in exactly the sense
  [Day 81's fixture](../../../day-81-llm-as-judge/parts/01-the-judge-is-a-system/1.1-a-judge-is-a-model-with-a-job.md)
  used human labels: written by a person, before the comparison ran, so the comparison is scored
  against it rather than trusted.
- Three entries for nine cases: only the cases that moved need one. The five that did not move are
  not in the dictionary and do not need to be, which is a small point about what a regression report
  is for — it is a report about differences.
- The strings are the exact phrases `compare.py` produces, so the check is an equality rather than a
  judgement. That coupling is deliberate and it is also a small trap: change the wording in one place
  and the check goes red for a reason that is not a finding, which part
  [1.3](1.3-what-has-to-be-written-down.md) has an opinion about.

Now the two ways of reporting the same two runs. First, the one everybody builds:

```bash
cd days/day-82-regression-discipline/lab
uv run python compare.py --count
```

**Line by line:**

- `--count` reports the pass count for each run and nothing else. That is what a test runner gives
  you and it is what a dashboard usually plots.

Measured on 2026-09-06:

```text
last night: desk prompt-v7, judge gemini-2.5-flash-lite
tonight:    desk prompt-v8, judge gemini-2.5-flash-lite

  last night: 8 of 8 passed
  tonight:    6 of 9 passed

  the suite went from 8/8 to 6/9; something regressed
  three cases moved, for three different reasons, and this names none of them
```

**`8/8` to `6/9`.** Both numbers are correct. The sentence "something regressed" is correct. And
there is nothing in it anybody can act on: the denominator moved as well as the numerator, so even
"two cases broke" is not derivable from those two fractions.

Now the comparison:

```bash
uv run python compare.py; echo "exit: $?"
```

**Line by line:**

- No flag walks both runs case by case and metric by metric, printing every value that differs.

Measured on 2026-09-06:

```text
  case                metric                         was   now  why
  one_lookup          tool_trajectory_avg_score      1.0   0.0  the desk changed
  refund_limit        final_response_match_v2        1.0   0.0  the judge flipped on an identical answer
  escalation_wording  tool_trajectory_avg_score        -   1.0  a new case, never run before
  escalation_wording  final_response_match_v2         -   0.0  a new case, never run before

  4 differences, 3 cases affected
  every difference has a cause, and only one of them is the desk
```

**Three cases moved and exactly one of them is a regression.** `one_lookup` is the desk: its
trajectory score fell, which means it took a different path, which is Day 79's metric doing its job.
`refund_limit` is the judge changing its mind on a byte-identical answer — Day 81 part 1.2 measured
that happening. `escalation_wording` has no yesterday at all.

A team paged by the `--count` report investigates a three-case regression. A team reading the second
one fixes one thing and files two notes.

## When it breaks

The comparison breaks when the two runs are not comparable, and the failure has no error text
because both files are perfectly well-formed.

The clearest case is a **case set that changed**. `escalation_wording` exists tonight and not last
night, so `old.get(case)` returns `None` and the code has to handle it. It does — the `before is
None` branch — and the version people write first does not:

```text
TypeError: 'NoneType' object is not subscriptable
```

which is at least loud. The silent version is worse: a comparison that iterates over **last night's**
cases rather than tonight's simply never looks at the new one, so a case that is red on its first run
is invisible in the report.

There is a second break with no message at all, and it is the reason part
[1.2](1.2-three-things-that-move-a-number.md) exists: the two runs used different versions of
something, and nothing in either file says so. That is not a bug in the comparison. It is a missing
field, and the comparison will confidently attribute a difference to the wrong cause.

The smallest fix for the first is to iterate over the **union** of the two case sets and treat a case
that exists in one and not the other as its own category — appeared, disappeared — rather than as a
change. A case that vanished between runs is a finding too, and a comparison that only walks
tonight's list will never report one.

## In production

**What a professional stores.** Per-case, per-metric **scores**, not statuses, with the run's date —
because the interesting regression is usually the one that has not crossed a threshold yet. A case
drifting from 0.95 to 0.84 over three months is invisible in any pass/fail record and obvious in a
score history, and it is the one you can still do something cheap about.

**What degrades at scale.** The case set is not stable. Cases are added, renamed and deleted, so a
comparison keyed on the case id degrades as the suite churns — a renamed case looks like one deletion
and one addition, and its history is severed. Real suites treat the case id as an identifier that must
never be reused or renamed, exactly as a database key would be, and that is a discipline rather than
a mechanism.

**The failure that only shows with real traffic.** Two runs that look comparable and are not, because
the *input* changed. The desk's fixture grew, a ticket in it aged, a date rolled over — and the case
that regressed did so because the world moved, not because the desk did. Nothing in a results file
records the input's version, and part [1.3](1.3-what-has-to-be-written-down.md) is the list of what
would have to.

**The review comment a senior engineer leaves:** *"The dashboard plots the pass count. Plot the
per-case scores instead — I want to see the case that has been sliding for two months, not just the
one that crossed the line last night. And iterate the union of the case sets; right now a case that
disappears between runs would not show up anywhere."*

**The interview question:** *"What is the difference between a failing test and a regression?"* The
answer that shows experience says a regression is a claim about two runs, so it needs stored history
and a way to line the runs up — and then names the practical consequence, which is that most teams
discover they cannot answer "when did this start?" on the first morning they need to.
