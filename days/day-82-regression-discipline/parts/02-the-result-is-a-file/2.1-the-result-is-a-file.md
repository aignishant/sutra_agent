# 2.1 — The result is a file

## One-line answer

ADK already writes every eval run to disk as a `.evalset_result.json` under
`<agents_dir>/<app_name>/.adk/eval_history/`, with per-case and per-metric scores in it — so the
history a regression comparison needs exists by default, and the only question is whether anything
keeps it.

## The story

The photocopy shop keeps every job.

You did not ask for that. You brought in a document, he copied it, you paid and left. But there is a
machine behind the counter that writes a small record for every job it does — how many pages, what
time, which tray — because the machine's manufacturer thought somebody might want to bill by the page
one day.

Six months later a customer says a job was never done. The man behind the counter presses four
buttons and there it is: the eleventh of March, twenty-two pages, four minutes past three.

Nobody in that shop designed a record-keeping system. It came with the machine, switched on, and the
only thing anybody did right was **not clear it**.

## The idea in plain language

Day 79 established that an evalset is a file. This part is the other half of the pair: a **result** is
a file too, and ADK writes it without being asked.

Three facts, read off the installed `google-adk==2.7.1`:

**The location.** `LocalEvalSetResultsManager(agents_dir=...)` puts results in
`<agents_dir>/<app_name>/.adk/eval_history`. The directory constant in the source is
`_ADK_EVAL_HISTORY_DIR = ".adk/eval_history"`, and the app name is a path segment in the middle.

**The extension.** `_EVAL_SET_RESULT_FILE_EXTENSION = ".evalset_result.json"` — deliberately unlike
the `.evalset.json` that Day 79's *cases* live in, so the two are never confused by a glob.

**The shape.** An `EvalSetResult` holding a list of `EvalCaseResult`, and on each of those a list of
`EvalMetricResult` with a metric name, a threshold, a score and a status.

The three methods are the ones you would expect: `save_eval_set_result`, `list_eval_set_results`,
`get_eval_set_result`. And `AgentEvaluator.evaluate` takes an `eval_set_results_manager` argument, so
a suite run through ADK's own entry point can be wired to write history without any extra code —
which is worth knowing before building one.

Two things about the record are worth noticing now, because they decide what part
[2.3](2.3-comparing-two-runs.md) can do:

**It stores scores, not just statuses.** `EvalMetricResult` has a `score` field alongside
`eval_status`, so the history supports the drift comparison Day 79 part 1.1 argued for — a case moving
from 0.95 to 0.84 without crossing its threshold is recoverable from these files.

**It stores nothing about what produced it.** Not the judge, not the desk, not the evalset's contents.
Part [1.3](../01-what-a-regression-is/1.3-what-has-to-be-written-down.md) is the list of what is
missing and why a wrapper has to add it.

## Why Sutra needs it

Because part [1.1](../01-what-a-regression-is/1.1-a-regression-is-a-comparison.md) established that a
regression needs two runs and Sutra has never stored one. Everything days 79 to 81 measured was
printed to a terminal and lost.

And because the thing that makes this cheap is that it is already built. There is no argument to have
about a storage format, a schema or a service: ADK writes a JSON file per run, with the right fields
in it, into a directory it creates. The only decision left is whether that directory survives — which
is part [2.2](2.2-the-history-this-repo-throws-away.md), and which turns out to be a decision this
repository has already made without noticing.

## The mechanism

Saving two runs and reading them back, through ADK's own manager. From `lab/history.py`:

```python
HERE = Path(__file__).resolve().parent
ROOT = HERE.parents[2]
HISTORY = HERE / "sutra" / ".adk" / "eval_history"  # <agents_dir>/<app_name>/.adk/eval_history


def main(argv: list[str]) -> int:
    manager = LocalEvalSetResultsManager(agents_dir=str(HERE))

    if "--ignored" not in argv:
        # Start from empty so two runs of this script produce the same listing.
        for stale in HISTORY.glob("*.evalset_result.json"):
            stale.unlink()
        manager.save_eval_set_result(APP, EVAL_SET, LAST_NIGHT_CASES)
        manager.save_eval_set_result(APP, EVAL_SET, TONIGHT_CASES)
```

**Line by line:**

- `LocalEvalSetResultsManager(agents_dir=...)` takes the **agents** directory, not the history
  directory. The app name is appended by `_get_eval_history_dir`, so a single manager serves several
  apps and each gets its own history — which is why the path has `sutra` in the middle of it.
- The comment on `HISTORY` spells the path out, because the layout is not guessable: the app name sits
  *between* the agents dir and `.adk`, and looking for `.adk/eval_history` directly under the agents
  dir finds nothing. That cost this lab a wrong path and a `FileNotFoundError` on the first run.
- The `unlink` loop is a lab convenience, not part of the API. `save_eval_set_result` **appends** — the
  filename carries `time.time()`, so every call writes a new file and nothing is ever overwritten.
  Clearing first is what makes this script's output the same on the second run.
- `save_eval_set_result(APP, EVAL_SET, cases)` takes the case results directly and builds the
  `EvalSetResult` itself, via `create_eval_set_result`. It returns `None` on 2.7.1, so the name it
  generated has to be recovered from `list_eval_set_results` afterwards — which is what part
  [1.3](../01-what-a-regression-is/1.3-what-has-to-be-written-down.md)'s wrapper does.

Reading them back:

```python
names = sorted(manager.list_eval_set_results(APP))
...
if names:
    latest = manager.get_eval_set_result(APP, names[-1])
    cases = latest.eval_case_results
    print(f"\n  the newest one holds {len(cases)} case results")
    first = cases[0]
    print(f"  fields on a case result: {sorted(type(first).model_fields)}")
    print(
        f"  metrics recorded:        {[m.metric_name for m in first.overall_eval_metric_results]}"
    )
    print("  judge model recorded:    no such field")
```

**Line by line:**

- `list_eval_set_results` returns **names**, not results — file names with the extension stripped.
  `sorted(...)` works as a chronological ordering only because the name ends in a `time.time()` float,
  which is a property of `create_eval_set_result` rather than a guarantee of the interface.
- `get_eval_set_result(APP, name)` reads one back into an `EvalSetResult`, so the round trip is
  through the library's own parser rather than through `json.load` — the same discipline
  [Day 79 part 2.1](../../../day-79-evals-are-tests/parts/02-the-evalset-file/2.1-the-evalset-is-a-file.md)
  applied to evalsets.
- `sorted(type(first).model_fields)` prints the record's real field list rather than a remembered one.
  That is what makes the last line — `judge model recorded: no such field` — a measurement rather than
  a claim.

Run it:

```bash
cd days/day-82-regression-discipline/lab
uv run python history.py; echo "exit: $?"
```

**Line by line:**

- No flag: clear, save both runs, list them, read the newest back.

Measured on 2026-09-06 — the two file names end in `time.time()`, so they differ on every run:

```text
agents_dir: days\day-82-regression-discipline\lab
history dir: sutra\.adk\eval_history
file extension: .evalset_result.json

  2 result files:
    sutra_triage_1788713499.346597  (8234 bytes)
    sutra_triage_1788713499.348567  (9249 bytes)

  the newest one holds 9 case results
  fields on a case result: ['eval_id', 'eval_metric_result_per_invocation', 'eval_metric_results', 'eval_set_file', 'eval_set_id', 'final_eval_status', 'overall_eval_metric_results', 'session_details', 'session_id', 'user_id']
  metrics recorded:        ['tool_trajectory_avg_score', 'final_response_match_v2']
  judge model recorded:    no such field
```

**Two files, eight and nine kilobytes, holding everything part
[2.3](2.3-comparing-two-runs.md) needs.** Nine case results in the newer one against eight in the
older, the two metric names per case, and a score for each.

And read the field list. `eval_id` joins a result to a case. `final_eval_status` is the pass or fail.
`overall_eval_metric_results` holds the scores. `eval_metric_result_per_invocation` holds them per
turn. `session_id` and `session_details` point back at the run that produced them.

There is no `judge_model`, no `agent_version`, no `evalset_hash`. Part
[1.3](../01-what-a-regression-is/1.3-what-has-to-be-written-down.md) is the four fields that would
have to be added around this, and the reason the addition has to be a sibling file rather than an
extra key.

## When it breaks

The path is the thing that breaks, and it breaks quietly in both directions.

Give the manager the history directory instead of the agents directory and it writes to
`<history>/<app>/.adk/eval_history` — a working directory nested inside the one you meant, with your
results in it, and `list_eval_set_results` will happily report zero from the place you were looking.
That is the mistake this lab made:

```text
FileNotFoundError: [WinError 3] The system cannot find the path specified:
'...\lab\.adk\eval_history\sutra_triage_1788713428.99613.evalset_result.json'
```

The message is clear and the cause is not obvious from it: the file *was* written, to
`lab/sutra/.adk/eval_history/`, and the script looked one directory too high.

The quieter break is the app name. `_get_eval_history_dir` calls `validate_path_segment(app_name,
"app_name")`, so an app name with a slash in it is rejected — good — but two *different* apps with
similar names each get their own directory, and a run saved under `sutra` is invisible to a manager
asked about `sutra-desk`. There is no error; `list_eval_set_results` returns `[]` for a directory that
does not exist.

The third is not a break at all and is worth knowing: **nothing ever cleans up.** Every run writes a
new file named with a timestamp, so a nightly job produces one file a night, forever. That is the
right default — history you did not ask to lose — and it means retention is a decision somebody has to
make, which part [5.2](../05-in-production/5.2-what-a-real-regression-suite-adds.md) puts on the list.

## In production

**What a professional wires up.** `AgentEvaluator.evaluate`'s `eval_set_results_manager` argument, so
history is written by the same call that runs the suite rather than by a second step somebody has to
remember. A history written by a separate script is a history that stops when that script breaks, and
it will break on a run nobody watched.

**What degrades at scale.** File count and size. Nine cases is nine kilobytes; four hundred cases with
`eval_metric_result_per_invocation` populated is megabytes, once a night, for ever. The local manager
is deliberately simple and the answer at scale is a different `EvalSetResultsManager` — the interface
exists to be implemented, and ADK ships a GCS one — plus a retention policy that keeps every run for a
month and one run a week after that.

**The failure that only shows with real traffic.** The history is on the machine that ran the suite.
On a laptop that is fine; on CI it is an ephemeral container, and every result is deleted with the
runner. A history that exists only inside the job that produced it is not a history, and the fix is an
upload step in the same job — which is part
[2.2](2.2-the-history-this-repo-throws-away.md)'s subject arriving from a different direction.

**The review comment a senior engineer leaves:** *"Pass the results manager into `evaluate` rather than
saving separately — one call, one artefact. And decide the retention now: one file a night with no
cleanup is fine for a year and a nuisance for three, and the decision is much cheaper to make before
there are a thousand files than after."*

**The interview question:** *"Where do your evaluation results go?"* The answer that shows experience
names a durable location outside the machine that ran them, and can say what is in the record — scores
per case per metric, not just a pass rate — because a store that keeps only statuses cannot answer any
question about drift.
