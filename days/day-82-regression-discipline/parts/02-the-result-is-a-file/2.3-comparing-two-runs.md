# 2.3 — Comparing two runs

## One-line answer

The comparison is a nested dictionary lookup — case, then metric, then score — and everything that
makes it useful is in what it does with the three cases where a lookup **misses**: no yesterday, no
today, and no recorded reason.

## The story

The stock-take at the end of the month.

Two sheets on the table: what the book says should be on the shelves, and what somebody counted this
morning. The job is to go down both and find where they differ.

Most lines match and are ticked in a second. What takes the afternoon is the handful that do not, and
they turn out to be four different kinds of thing. Some are genuinely short — that is the finding
everybody was looking for. Some are items the book has never heard of, because a new line came in last
week and nobody added it. Some are on the book and not on the shelf because they were sold and the
paperwork is in a drawer. And one is a counting mistake.

The arithmetic — this number against that number — is trivial. The work is in the four categories, and
a stock-take that reports one number for "discrepancies" has done the arithmetic and none of the work.

## The idea in plain language

Part [1.2](../01-what-a-regression-is/1.2-three-things-that-move-a-number.md) gave the categories.
This part is the loop that produces them, and it is smaller than it sounds.

A results file is a list of case results; each case result is a list of metric results; each metric
result has a score. Flatten that to `case → metric → score` for both runs and the comparison is a walk
over the newer one.

Three lookups can miss, and each is a category rather than an error:

- **`old[case]` misses** — the case is new. Not a regression; there is nothing to compare against.
- **`new[case]` misses** — the case has gone. A finding, and one a naive loop never reaches, because a
  walk over tonight's cases cannot see a case that is only in last night's.
- **the reason is not derivable** — both runs have the case, a score moved, and something else moved
  too. Part [1.2](../01-what-a-regression-is/1.2-three-things-that-move-a-number.md)'s `CANNOT TELL`.

And there is a design decision hiding in the first line of the loop that decides how much of this you
can see: **iterate over what?** Tonight's cases gives you changes and additions. Last night's gives
you changes and removals. Only the **union** gives you all three, and the version everybody writes
first iterates over one of them.

One more thing that is worth doing at the same time and costs nothing: compare **scores**, not
statuses. A case whose judged score fell from 1.0 to 0.0 and a case that fell from 0.95 to 0.84 are
both movements; only the first crosses a threshold, and a comparison over `final_eval_status` sees
only the first. Day 79 part 1.1 argued for keeping scores and this is where the argument is cashed.

## The mechanism

Flattening a result to `case → metric → score`. From `lab/_runs.py`:

```python
def scores(run: EvalSetResult) -> dict[str, dict[str, float | None]]:
    """case id -> metric name -> score, which is the shape a comparison needs."""
    return {
        case.eval_id: {m.metric_name: m.score for m in (case.overall_eval_metric_results or [])}
        for case in run.eval_case_results
    }
```

**Line by line:**

- `case.eval_id` is the key, which is why part
  [1.1](../01-what-a-regression-is/1.1-a-regression-is-a-comparison.md)'s **In production** section
  insists that case ids are never renamed or reused. This dictionary is the join, and a renamed case
  looks like one deletion and one addition with no connection between them.
- `overall_eval_metric_results or []` — the field is `Optional` on 2.7.1, so a case that produced no
  metric results at all gives an empty dictionary rather than a `TypeError`. A case with no metrics is
  a real state: Day 80 part 3.3 measured `NOT_EVALUATED` producing exactly that.
- `m.score` rather than `m.eval_status`. The score is `Optional[float]` — `None` when the case was not
  evaluated — so the comparison downstream has three values per metric and not two, which is what lets
  `NOT_EVALUATED` be its own category rather than being read as a zero.
- A nested comprehension rather than a loop, because the whole function is a re-shaping with no
  decisions in it. Every decision is in `classify`.

The walk, from `lab/compare.py`:

```python
    for case, metrics in new.items():
        was = old.get(case)
        for metric, score in metrics.items():
            if was is not None and was.get(metric) == score:
                continue
            reason = classify(case, was, metrics, recorded)
            shown = "-" if was is None else f"{was.get(metric):.1f}"
            print(f"  {case:<20}{metric:<28}{shown:>6}{score:>6.1f}  {reason}")
            findings += 1
```

**Line by line:**

- `new.items()` — this walks **tonight's** cases, so it reports changes and additions and would not
  see a case that vanished. That is a real limitation of this lab's version and it is named here
  rather than hidden; part [1.1](../01-what-a-regression-is/1.1-a-regression-is-a-comparison.md)'s
  check-yourself makes you find it.
- `old.get(case)` returns `None` for a new case, and `was is not None` guards every use of it. The
  `None` flows into `classify`, which turns it into a category rather than a crash.
- `was.get(metric) == score` skips unchanged values, so the report is **only differences**. Nine cases
  and two metrics is eighteen values; four of them moved, and a report that printed all eighteen would
  bury them.
- `shown = "-"` for a value that does not exist. Printing `0.0` or `None` there would read as a score,
  and a dash reads as an absence — a small formatting decision that stops a new case looking like a
  case that scored zero last night.
- `classify(...)` is called per metric but takes the whole `metrics` dictionary, because the category
  depends on **which metrics moved together** rather than on the one being printed. That is why the
  same reason appears twice on `escalation_wording`'s two rows.

**Line by line:**

- No flag: both versions recorded, so every category is derivable.

Measured on 2026-09-06:

```text
last night: desk prompt-v7, judge gemini-2.5-flash-lite
tonight:    desk prompt-v8, judge gemini-2.5-flash-lite

  case                metric                         was   now  why
  one_lookup          tool_trajectory_avg_score      1.0   0.0  the desk changed
  refund_limit        final_response_match_v2        1.0   0.0  the judge flipped on an identical answer
  escalation_wording  tool_trajectory_avg_score        -   1.0  a new case, never run before
  escalation_wording  final_response_match_v2         -   0.0  a new case, never run before

  4 differences, 3 cases affected
  every difference has a cause, and only one of them is the desk
exit: 0
```

**Four rows out of eighteen values.** Fourteen values were identical on both nights and are not in the
report, which is the whole reason a comparison beats a listing.

Read the `was` column on the last two rows: a dash, not a number. Those two rows are the new case, and
the dash is what makes it obvious at a glance that they are not movements. Then read the `why` column
down: one desk, one judge, two new. Three cases, three categories, and the exit code says every one of
them has a cause.

The exit code is the part that makes this usable by something other than a person. `0` means every
difference is attributable; `1` means at least one is not. Part
[4.1](../04-what-ci-must-refuse/4.1-a-red-build-is-a-decision.md) is about what a build should do with
that, and it is deliberately **not** "fail when anything moved" — a suite that fails on every
difference fails on every new case.

## When it breaks

The comparison breaks on the shape of the data rather than on the arithmetic, and the failures are
quiet in one direction and loud in the other.

**Loud:** a case with no metric results, on a version of `scores()` without the `or []`:

```text
TypeError: 'NoneType' object is not iterable
```

That is the friendly one. It arrives the first time a case comes back `NOT_EVALUATED` — Day 80 part
3.3's judged case with no verdict — and it names the line.

**Quiet:** the removed case. `new.items()` cannot reach a case that only exists in `old`, so a case
deleted between runs produces no row, no warning and no exit code. The suite got smaller and the report
says nothing, which is the same missing-denominator shape
[Day 78 part 3.2](../../../day-78-inside-free-quota/parts/03-when-you-cannot-afford-it/3.2-the-shrunken-run-that-reports-as-full.md)
measured.

**Quieter still:** a renamed case. It is a removal and an addition, which — with the removal invisible
— is reported as a new case that happens to be red, and its history is gone.

The smallest fix for the last two is one line:

```python
    for case in sorted(set(old) | set(new)):
```

**Line by line:**

- `set(old) | set(new)` is the union, so a case in either run is visited. `sorted` makes the report
  order stable rather than dictionary-insertion order, which matters when two runs are diffed.
- Each branch then needs a category: in `new` and not `old` is an addition, in `old` and not `new` is
  a **removal**, and in both is a comparison. Three branches, one of which the current code does not
  have.

## In production

**What a professional compares.** Score deltas, with a tolerance, per case per metric — and the delta
reported even when it does not cross a threshold. The most valuable output of a regression comparison
is not the case that broke last night; it is the list of cases whose scores have moved the most over
thirty runs, which is where the slow degradation lives and which no pass/fail view contains.

**What degrades at scale.** The report gets long. Four hundred cases with two metrics is eight hundred
values, and on a busy week two hundred of them move a little. Sorting by absolute delta and truncating
is the obvious answer and it hides exactly the small persistent drifts you wanted; the better answer is
to compare against a **window** — the median of the last five runs rather than the last one — so noise
cancels and drift survives.

**The failure that only shows with real traffic.** Comparing against "the previous run" is ambiguous
the moment runs are not serial. Two CI jobs on two branches, a re-run of a flaky night, a manual run
somebody did at lunchtime — and "the previous run" is whichever file has the largest timestamp, which
may be a different branch entirely. Real comparisons are against a named baseline: the last run **on
this branch**, or the last run on the trunk, chosen deliberately.

**The review comment a senior engineer leaves:** *"Iterate the union, not tonight's list — a case that
disappears is a finding and right now we would never see it. And compare against the median of the last
five runs rather than last night's; half of what we would page on is the judge being uncertain, and a
window makes that cancel."*

**The interview question:** *"How would you compare two test runs?"* The answer that shows experience
spends its time on the cases that are in one run and not the other, and on what counts as a difference
worth reporting — because the arithmetic is a dictionary lookup and everything hard is in the
categories.
