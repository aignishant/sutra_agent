# 2.2 — The history this repository throws away

## One-line answer

💥 ADK writes every eval run into `.adk/eval_history/`, and this repository's `.gitignore` line 24 is
`.adk/` — so the history a regression comparison needs is produced correctly on every run and exists
on exactly one machine until somebody clears their disk.

## The story

The shop's CCTV, recording over itself every seven days.

It works. The cameras are good, the angles are right, the recorder never fails. Every day it captures
everything that happens in the shop, faithfully, and every day it deletes the day from a week ago to
make room.

Nobody chose seven days. It was the default on the box, and the box was installed by somebody who was
thinking about theft — where a week is plenty, because you notice a theft the same afternoon.

Then a supplier disputes a delivery from three weeks ago. The footage of that morning was recorded
perfectly and no longer exists, and the reason is a setting nobody has looked at since the day it was
installed, chosen for a different question from the one being asked.

## The idea in plain language

Part [2.1](2.1-the-result-is-a-file.md) established that ADK writes a complete, well-formed result file
for every run, into `<agents_dir>/<app_name>/.adk/eval_history/`.

Now put that next to this repository's own `.gitignore`, written on Day 0:

```text
# ── runtime artifacts: never commit a session store ───────
.adk/
*.db
*.sqlite3
```

That rule is **correct**, and it is correct for the reason its own comment gives. `.adk/` is where ADK
puts session stores — conversations, user content, whatever a run happened to say — and committing
those into a repository that Phase 14 makes public is exactly the mistake Day 69's PII boundaries
exist to prevent.

And `.adk/` is also where it puts eval history. One directory, two kinds of artefact, one rule.

So the situation is:

- the history a regression needs is **produced**, correctly, on every run;
- it lands in a directory this repository **deliberately does not keep**;
- and nothing anywhere reports that, because ignoring a file is not an event.

Two things follow that are worth separating, because they lead to different fixes.

**The rule should not simply be relaxed.** Un-ignoring `.adk/` would commit session stores, which is a
worse problem than the one it solves. Whatever the fix is, it is not deleting line 24.

**A history that lives on one machine is not a history.** Even without git, the results in
`days/*/lab/sutra/.adk/eval_history/` exist on the laptop that ran them. A colleague comparing tonight
against last night has no last night. A CI runner has no last night at all — its container is deleted
with the job, which is part [2.1](2.1-the-result-is-a-file.md)'s **failure that only shows with real
traffic**, arriving here as a certainty rather than a risk.

## Why Sutra needs it

Because this is the gap between "we have a regression suite" and "we can detect a regression", and it
is a gap made of one line in a config file rather than of any missing code.

Everything else this day builds — part [2.3](2.3-comparing-two-runs.md)'s comparison, part
[3.2](../03-two-cadences/3.2-the-full-run-rides-the-nightly.md)'s nightly, part
[4.1](../04-what-ci-must-refuse/4.1-a-red-build-is-a-decision.md)'s CI decision — assumes there is a
previous run to compare against. Without this, all of it runs and none of it can say anything.

And the timing matters. Day 83's gate asks whether Phase 12's eval suite is green, and Day 84 begins
observability. A history that starts accumulating today is a history that exists by the time anybody
wants it; one that starts when somebody first needs it is a history that starts empty on the morning
of the incident.

## The mechanism

The check is one `git check-ignore` on the path a real deployment would write to. From
`lab/history.py`:

```python
    # The rule that matters is not this lab's. Ask git about the path a real deployment writes to:
    # <repo>/sutra/.adk/eval_history, which is where an agents_dir of "sutra" would put it.
    real = ROOT / "sutra" / ".adk" / "eval_history" / "x.evalset_result.json"
    check = subprocess.run(
        ["git", "check-ignore", "-v", str(real)], cwd=ROOT, capture_output=True, text=True
    )
    rule = check.stdout.strip().split("\t")[0] if check.stdout.strip() else "(not ignored)"
```

**Line by line:**

- The path asked about is under the **repository root**, not under `days/*/lab/`. That distinction is
  the whole point: the lab is ignored by `days/*/lab/`, which would be a finding about the lab rather
  than about the repository. Asking about `sutra/.adk/eval_history` asks the question a deployment
  would ask.
- `git check-ignore -v` prints the **rule that matched** — the file, the line number and the pattern —
  which is what turns "it is ignored" into evidence somebody can go and read.
- The path does not have to exist. `check-ignore` answers about a path, not about a file, so this
  works before anything has ever been written there.
- `split("\t")[0]` keeps the rule and drops the absolute path that follows it, so the output is the
  same on every machine.
- `check.returncode == 0` means **ignored**. That inversion — zero for "yes, ignored" — is git's
  convention and is worth a comment in any script that uses it, because zero usually means the
  reassuring answer and here it means the finding.

Run it:

```bash
cd days/day-82-regression-discipline/lab
uv run python history.py; echo "exit: $?"
```

**Line by line:**

- The same command as part [2.1](2.1-the-result-is-a-file.md); this part reads the last block of its
  output.

Measured on 2026-09-06:

```text
  git check-ignore on sutra/.adk/eval_history/x.evalset_result.json:
    .gitignore:24:.adk/

  the directory ADK writes its history into is gitignored in this repository
  every result above exists on one machine and nowhere else
exit: 1
```

**`.gitignore:24:.adk/`** — the file, the line, the pattern. Not an argument, a lookup.

And it is worth being clear that nothing is broken. The rule is right, the library is right, the files
are right. Two correct decisions, made months apart by people solving different problems, compose into
a regression suite with no history — which is the ordinary way this kind of gap appears.

There is no error, no warning and no log line, because a file being ignored is not an event. `git
status` shows nothing. `git add -A` adds nothing. The only way to find it is to ask.

## When it breaks

The break is a morning, and it goes like this:

```text
1. the nightly runs and the suite is red
2. somebody asks: was it red last night?
3. the results are in .adk/eval_history/ on the CI runner, which no longer exists
4. the local copy is on whoever last ran it, from whenever that was
5. the answer is "I think it was green on Tuesday"
```

Step 5 is part [1.1](../01-what-a-regression-is/1.1-a-regression-is-a-comparison.md)'s recollection
rather than a comparison, and it cannot distinguish any of part
[1.2](../01-what-a-regression-is/1.2-three-things-that-move-a-number.md)'s three causes.

Three fixes, and they are genuinely different rather than three flavours of one:

**Write history somewhere else.** Point the results manager at a directory that is not `.adk/` — a
`docs/eval_history/` or an `evals/history/` — and commit it. Small, obvious, and it means the history
lives in the same commit as the code that produced it, which is a real advantage: `git log` over that
directory *is* the regression history.

**Un-ignore the eval history specifically.** `.gitignore` supports negation, so `!.adk/eval_history/`
after the `.adk/` line keeps the session stores ignored and the results tracked. It is one line, and
it is the most fragile of the three because it depends on ADK continuing to put two unrelated kinds of
artefact in one directory.

**Upload it.** In CI, an artefact upload step in the same job; in production, a different
`EvalSetResultsManager` — ADK ships a GCS one — so results go somewhere durable by construction rather
than by a second step.

The first is what a repository like this one should do, and part
[5.2](../05-in-production/5.2-what-a-real-regression-suite-adds.md) puts it first on the list for a
reason: it is the only one of the three that needs no infrastructure and survives Phase 14 making the
repository public, provided the results carry no customer text — which they do not, because an
`EvalCaseResult` holds scores and ids rather than answers.

## In production

**What a professional does with eval history.** Treats it as an artefact of the build, not as a
scratch file: written by the run, uploaded or committed by the same job, retained on a stated schedule.
The test is simple and worth applying to any history you inherit — *can somebody who was not there
open last month's run?* If not, it is a log, not a history.

**What degrades at scale.** Committed history grows a repository. One file a night at nine kilobytes
is three megabytes a year, which is nothing; four hundred cases with per-invocation results is a
different conversation, and that is the point at which the "write it somewhere else and commit it"
answer stops being free and an object store starts being the right call. Making that switch is easy
*if* the results manager was always an interface and hard if the path was hard-coded.

**The failure that only shows with real traffic.** Session data leaking into a directory you decided
to commit. The reason `.adk/` is ignored is that ADK puts session stores there, and if you un-ignore
part of it, the day somebody's session store lands one directory over is the day customer text enters
a public repository. That is why *"write history somewhere else"* beats *"un-ignore part of `.adk/`"*
even though the second is one line.

**The review comment a senior engineer leaves:** *"Do not touch line 24. Point the results manager at
`evals/history/` and commit that instead — then `git log` on the directory is our regression history
and it travels with the code that produced it. And check what is actually in one of those files before
we commit any: I want to be sure a case result holds scores and ids and not the customer's sentence."*

**The interview question:** *"Your CI runs an evaluation suite. Where do the results go?"* The answer
that shows experience notices immediately that a container's filesystem is not a place — and then asks
the question that separates a log from a history, which is whether somebody who was not there can open
last month's run.
