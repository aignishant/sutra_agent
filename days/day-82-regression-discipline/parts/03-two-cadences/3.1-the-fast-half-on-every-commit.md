# 3.1 — The fast half, on every commit

## One-line answer

Six of Phase 12's eight checks cost **zero requests** and two cost 270, so the split is not a
compromise — the free six run on every commit and the paid two ride the nightly, because a gate that
spends a day's quota is a gate somebody will switch off.

## The story

The security check at the entrance to the building.

There are two of them and they are completely different. At the door, a guard glances at your card and
waves you through. It takes a second, it happens to everybody, every time, and nobody minds — the cost
of it is so low that it never becomes a negotiation.

Then there is the visitor process: a form, a phone call upstairs, a badge printed, somebody coming
down to collect you. Ten minutes. That one is not applied to everybody, because if it were, nobody
would get any work done and within a month there would be a propped-open side door.

The building is not less secure for having two levels. It is more secure, because the cheap check
actually runs on every entry, and the expensive one runs where it is worth ten minutes.

## The idea in plain language

Phase 12 built eight checks over three days. Sorting them by what one run costs produces a striking
split:

| Check | Requests | From |
| --- | --- | --- |
| `tool_trajectory_avg_score` | 0 | Day 79 |
| `response_match_score` | 0 | Day 79 |
| the stub check | 0 | Day 79 |
| the assembled-prompt check | 0 | Day 80 |
| the rubric spread check | 0 | Day 80 |
| the baseline check | 0 | Day 81 |
| `rubric_based_multi_turn_trajectory` | 30 | Day 80 |
| `final_response_match_v2` | 240 | Day 81 |

**Six at zero and two at 270.** There is no middle. That is not a coincidence — it is the line between
checks that compare structures and checks that ask a model — and it means the cadence decision makes
itself.

Three properties make the free six the right thing to run on every commit, and only the first is about
cost:

- **They cost nothing**, so running them a hundred times a day costs nothing.
- **They are deterministic.** Same inputs, same answer, so a red build is reproducible on a laptop.
  Part [4.2](../04-what-ci-must-refuse/4.2-flaky-by-construction.md) is about what happens when a
  gate is not.
- **They are fast.** Seconds, not minutes, so they fit inside the feedback loop a person is actually
  in while they are still looking at the change.

And it is worth noticing *what* the free six are, because it is not only the two metrics. Four of them
are the **meta-checks** this phase built — the stub check from Day 79 part 2.3, the assembled-prompt
check from Day 80 part 2.2, the rubric spread check from Day 80 part 3.2, the baseline check from Day
81 part 3.3. Those four do not test the desk at all. They test whether the suite is still capable of
measuring, and every one of them is free.

That is the argument for putting them in CI ahead of anything else: **a check that the suite can still
fail belongs on every commit, because the commit that breaks it is the commit that introduced it.**

## Why Sutra needs it

Because `./m check` has been this repository's gate since Day 0, and it runs `ruff`, `ruff format`,
`pytest -m "not live"`, the depth contract, traceability and the wiki. Six things, all free, on every
commit. Phase 12's free six belong in exactly that list and nothing about them makes it slower in any
way a person would notice.

And because the alternative has already been named. Day 79 part 5.1 argued that a suite outside the
habit decays at the speed of the codebase, and Day 81 part 5.2 put the baseline check first on its
list for the same reason. This part is where those recommendations become a cadence rather than an
intention.

## The mechanism

The eight checks with their costs, as data. From `lab/cadence.py`:

```python
@dataclass(frozen=True)
class Check:
    name: str
    requests: int
    day: str
    why: str
```

**Line by line:**

- `requests` is an integer per run, and it is the field the split is computed from. Storing the cost
  next to the check is what makes the cadence derivable rather than a decision somebody has to
  remember.
- `day` records which day of this curriculum built the check. That is not decoration: when a check goes
  red in eight months, the day that built it is where its argument is written down.
- `why` is one sentence. A check whose purpose fits in one sentence can be triaged by somebody who did
  not write it.
- `frozen=True` — the list is a fixture, and a cost that something could mutate mid-run is a cost
  nobody can trust.

The split itself is a comprehension:

```python
    free = [c for c in CHECKS if c.requests == 0]
    judged = [c for c in CHECKS if c.requests > 0]
    per_commit = CHECKS if all_in_ci else free
    nightly = () if all_in_ci else judged

    commit_cost = sum(c.requests for c in per_commit)
    nightly_cost = sum(c.requests for c in nightly)
    daily = commit_cost * COMMITS_PER_DAY + nightly_cost
```

**Line by line:**

- The predicate is `requests == 0`, not a hand-maintained list of names. A check added later lands in
  the right cadence by arithmetic, which is the same argument Day 78 part 1.2 made about deriving
  lanes from jobs rather than listing them.
- `commit_cost * COMMITS_PER_DAY` is the term that decides everything. A per-commit cost is multiplied
  by however many times a day people push, and `COMMITS_PER_DAY = 12` is written in the file as *"what
  a small team pushes on an ordinary day"* — a stated assumption rather than a hidden one.
- `nightly_cost` is **not** multiplied, because the nightly runs once. That asymmetry is the whole
  reason the split works: moving a check from the commit gate to the nightly divides its daily cost by
  the number of commits.
- `all_in_ci` swaps the two lists rather than changing the arithmetic, so the ablation and the honest
  arm are the same computation over a different partition.

Run the split:

```bash

```

**Six checks, zero requests, on every commit.** The `at 12 commits a day that is 270 requests` line is
the one to hold: the entire day's spend is the nightly's, and the number of times anybody pushes does
not enter into it.

Now put everything on the commit gate:

```bash
uv run python cadence.py --all-in-ci; echo "exit: $?"
```

**Line by line:**

- `--all-in-ci` moves the two judged checks into the per-commit set. Same eight checks, same costs.

Measured on 2026-09-06:

```text
    on every commit   8 checks, 270 requests
    on the nightly    0 checks, 0 requests

  at 12 commits a day that is 3240 requests
  a day's observed flash allowance: 20

  one commit costs 270 requests, which is 14x a whole day
  a gate that spends the day's quota is a gate somebody will switch off
exit: 1
```

**270 becomes 3,240.** Not because anything is more expensive — the eight checks cost exactly what
they cost — but because the per-commit half is multiplied by twelve.

And the line underneath is the one that matters more than the arithmetic: **one commit costs fourteen
times a whole day's measured allowance.** Long before that becomes a budget conversation it becomes a
behavioural one. A gate that takes minutes and can fail for quota reasons is a gate people learn to
push past, and a gate people push past is not a gate — which is
[Day 79 part 5.1](../../../day-79-evals-are-tests/parts/05-evals-are-tests/5.1-running-them-from-pytest.md)'s
fire-extinguisher argument arriving as a number.

## When it breaks

The split breaks by drifting, and the drift is always in the same direction: **a check moves from the
nightly to the commit gate because somebody wanted faster feedback.**

The request is always reasonable. A judged case caught something, the nightly found it twelve hours
later than the commit would have, and the obvious fix is to run it earlier. Each such move adds its
cost to every commit, multiplied by twelve, and there is no moment at which anybody computes the new
total.

There is no error text. What you get is a gate that gradually takes longer and occasionally fails with
a 429 — Day 78's recorded refusal — in the middle of somebody's pull request:

```text
429 RESOURCE_EXHAUSTED
generativelanguage.googleapis.com/generate_content_free_tier_requests
Please retry in ~53s
```

and a build that is red for a reason that has nothing to do with the change in it. That is the failure
that kills a gate: not being slow, but being **wrong in a way the author cannot fix**. After the third
one, somebody adds a way to skip it.

The smallest fix is to make the cadence a property of the check rather than of the pipeline
configuration — the `requests` field above — and to have the pipeline **derive** which set it runs.
Then moving a check between cadences means changing its cost, which is not something anybody does by
accident.

## In production

**What a professional puts on the commit gate.** Everything deterministic and fast, and nothing else.
The test is not "is this check important" — the judged checks are the most important ones in Phase 12 —
it is "can this run on every commit without becoming a negotiation". Importance decides whether a check
exists; cost and determinism decide when it runs.

**What degrades at scale.** The free half stops being free in wall-clock terms. Six deterministic
checks over eight cases is seconds; over four hundred cases with a rubric evaluator constructing
prompts it is minutes, and a commit gate that takes minutes gets the same treatment as one that costs
money. The answer is the same shape one layer down: sample the deterministic checks per commit and run
them all on the nightly.

**The failure that only shows with real traffic.** CI runs in parallel. Ten pull requests, ten runners,
each running the commit gate — and if any of those checks touches a shared resource, the per-commit
cost is multiplied by concurrency as well as by frequency. Free checks are immune to this and it is one
more reason the line is drawn where it is.

**The review comment a senior engineer leaves:** *"Put the four meta-checks in `./m check` today —
stub, prompt, spread, baseline. They are free, they are fast, and they are the ones that catch us
breaking the suite rather than the desk, which is exactly the thing a commit gate should catch. The
judged pair stays on the nightly and I do not want to hear a proposal to move it."*

**The interview question:** *"What runs on every commit and what runs nightly?"* The answer that shows
experience splits on cost and determinism rather than on importance, and can say why: a gate that is
slow or flaky or expensive gets bypassed, and a bypassed gate protects nothing regardless of what it
was checking.
