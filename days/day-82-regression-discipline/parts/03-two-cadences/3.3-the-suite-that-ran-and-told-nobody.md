# 3.3 — The suite that ran and told nobody

## One-line answer

💥 The eval stage found a regression, the digest named it, and the job exited **0** — because a
scheduled job's exit code says whether the stage completed, and cron discards stdout, so the only
channel left is a sentence nobody is obliged to read.

## The story

The smoke alarm in the stairwell, which is wired to nothing.

It works perfectly. It detects smoke, it sounds, and it is loud. Somebody tests it every year and it
passes.

What it is not wired to is the fire panel in the lobby, or the alarm company, or anything else. It was
installed by a contractor who fitted the units and left the wiring to a second contractor, and the
second contractor did the floors above.

So on the night it goes off, it goes off in an empty stairwell at three in the morning, for eleven
minutes, and then the battery-backed sounder gives up. The device did its whole job. The information
existed, correctly, in the right place at the right time, and reached nobody, because detecting and
telling are two different pieces of work and only one of them was anybody's.

## The idea in plain language

Part [3.2](3.2-the-full-run-rides-the-nightly.md) put the eval suite on the nightly. This part is
about what happens to its verdict afterwards.

A scheduled job has exactly two ways to tell anybody anything, and both are weaker than they look.

**Its exit code**, which is read by whatever started it. For a crontab line the answer is: nothing
reads it. `cron` may mail the output to a local mailbox nobody has opened since the machine was
provisioned, and that is the whole of the mechanism. Day 73 part 4.2 parked the operating system's
scheduler with exactly this observation — it does not tell you when the command was not run, and it
does not tell you what the command found.

**Its output**, which for an ambient job means the digest — Day 73's `state/digest.md`, read by Day
77's standup. That is a real channel and it is a **human** one: it works only if somebody reads it and
acts.

And there is a specific trap in the first, which is the one this part measures. A job made of stages
has two different things it could report:

- **did the job run?** — the reindex finished, the evals ran, the digest was written;
- **what did the job find?** — the suite regressed.

The natural implementation reports the first. Each stage completes, the script reaches the end, and it
exits 0 — because from the script's point of view everything worked. The regression is a *result*, not
an error, and nothing in an ordinary job structure carries a result into an exit code.

So the failure is not that the information is missing. The digest says `REGRESSED: one_lookup`, in
words, correctly. The failure is that the machine-readable channel says the opposite, and the
human-readable one depends on a person.

That is the same shape as
[Day 73 part 3.3](../../../day-73-ambient-agents/parts/03-the-morning-after/3.3-nobody-notices-silence.md),
which found that a job which stops running produces nothing to look at, and it is one step worse:
here the job produced something to look at and the thing that watches jobs was told everything is
fine.

## Why Sutra needs it

Because Sutra's nightly is a crontab line — Day 73 part 4.2 chose the operating system's scheduler
deliberately, because the hosted alternatives need a billing account — and a crontab line is exactly
the case where the exit code goes nowhere.

And because Phase 12's entire value is a verdict. Days 79 to 81 built three instruments to produce
one, and if that verdict reaches a `digest.md` and stops, the phase has built a measurement with no
consumer. Day 83's gate asks whether the eval suite is green; this part asks who would find out if it
were not.

## The mechanism

The two arms differ in one `return`. From `lab/nightly.py`:

```python
    if fire_and_forget:
        print("\n  the stage completed, so the job exits 0")
        print("  the crontab line discards stdout, and nothing else is watching")
        print(f"  {len(regressions)} regression(s) happened and no exit code anywhere says so")
        return 0

    print("\n  the comparison's verdict is the job's exit code")
    return 1 if regressions else 0
```

**Line by line:**

- `return 0` in the first branch is not a bug being simulated. It is what a stage-structured job
  returns: every stage completed, so the job succeeded. Writing it out as an explicit `return 0` makes
  visible a decision that is normally made by falling off the end of a function.
- `return 1 if regressions else 0` is the fix, and it is one line. The job's exit code becomes a
  function of the **comparison**, not of the stages.
- `regressions` is part [3.2](3.2-the-full-run-rides-the-nightly.md)'s narrow list — only
  `classify(...) == "the desk changed"`. So a judge flip does not turn the nightly red, which is the
  difference between an exit code that means something and one that fires on every difference.
- Both branches print the same digest line above them. The digest is unaffected by the choice, which is
  precisely the point: the human channel is identical and the machine channel is inverted.

Run the version whose exit code carries the verdict:

```bash
cd days/day-82-regression-discipline/lab
uv run python nightly.py; echo "exit: $?"
```

**Line by line:**

- No flag: the comparison's verdict becomes the job's.

Measured on 2026-09-06:

```text
nightly run, three stages

  ok       reindex
  ok       evals
  ok       digest

  evals: 6 of 9 passed, REGRESSED: one_lookup
  (3 cases moved; 1 of them because the desk changed)

  the comparison's verdict is the job's exit code
exit: 1
```

Now the ordinary version:

```bash
uv run python nightly.py --fire-and-forget; echo "exit: $?"
```

**Line by line:**

- `--fire-and-forget` returns 0 because the stages completed. Same fixture, same comparison, same
  digest.

Measured on 2026-09-06:

```text
nightly run, three stages

  ok       reindex
  ok       evals
  ok       digest

  evals: 6 of 9 passed, REGRESSED: one_lookup
  (3 cases moved; 1 of them because the desk changed)

  the stage completed, so the job exits 0
  the crontab line discards stdout, and nothing else is watching
  1 regression(s) happened and no exit code anywhere says so
exit: 0
```

**Read the two outputs side by side and find the difference.** The three stage lines are identical. The
digest sentence is identical, capital letters and all. The bracketed count is identical.

`exit: 1` against `exit: 0`.

That is the whole of it. A monitoring system watching this job's exit status sees a healthy job on both
nights. An alerting rule on the job's status fires on neither. The regression is in the output, in
words, in capitals — and the output goes to stdout, and the crontab line that Day 73 wrote sends stdout
nowhere.

## When it breaks

There is no error. Both runs are successful runs, and one of them is a monitoring system being told
that a night with a regression in it was fine.

The sequence, and it is short:

```text
1. the eval stage finds a regression
2. the digest says so, correctly
3. the job exits 0 because every stage completed
4. whatever watches the job records a successful run
5. the digest is read at seven, or is not
```

Step 5 is the only one that can save it, and it is a person. Day 73 part 3.2 measured what happens
when a digest is written to reassure rather than to alarm; Day 77 part 3.2 measured what happens when a
section is quietly missing. This is the version where the digest does everything right and the
surrounding machinery contradicts it.

Two fixes, and they are different rather than alternatives:

**Carry the verdict into the exit code.** One line, shown above. It makes the job's status mean *what
did it find* rather than *did it run*, which is what an alert on job status assumes.

**Keep both meanings.** The two questions are genuinely different and a real system wants both — *the
job failed* and *the job found something*. The usual encoding is two exit codes: `1` for a regression,
`2` for the job itself failing, with `0` for a clean run. That is Day 78 part 4.4's three-valued
discipline again, and it lets an alerting rule route a broken job to whoever owns the job and a
regression to whoever owns the desk.

And a third that is not a fix but a check, in the same family as
[Day 73 part 3.3](../../../day-73-ambient-agents/parts/03-the-morning-after/3.3-nobody-notices-silence.md):
**alert on the absence of a run.** A nightly that fails to start produces no exit code at all, and no
encoding of results rescues that. Something has to notice that no run happened, which is a different
alarm from either of the two above.

## In production

**What a professional wires up.** The verdict into the exit code, the exit code into whatever runs the
job, and a separate check that the job ran at all. Three things, and the third is the one that catches
the failure the other two cannot see. Day 73 part 4.2 listed the four jobs a scheduler does not do, and
"tell you when the command was not run" was one of them.

**What degrades at scale.** Alert fatigue, in the direction this part's fix creates. A nightly that
exits 1 on every difference goes red most nights — part
[4.2](../04-what-ci-must-refuse/4.2-flaky-by-construction.md) is about what that does — so the narrow
filter matters as much as the wiring. An exit code that means "something moved" is not more useful
than one that means "it ran"; it is less, because people stop looking at it faster.

**The failure that only shows with real traffic.** The digest is the channel and the digest has one
reader. Day 77 part 4.2 made the point: "needs a person" is a property of a ticket **and a listener**,
and the same is true here. On the morning the person who reads the standup is on leave, the regression
sits in a file, correctly reported, unread — which is why the machine-readable channel is not
redundant with the human one.

**The review comment a senior engineer leaves:** *"The exit code has to carry the verdict, and we need
two of them: 1 for a regression, 2 for the job breaking. And add a check that the nightly ran at all —
the failure we cannot see today is not a red run, it is no run, and neither of the other two catches
it."*

**The interview question:** *"Your nightly job found a problem. How does anybody find out?"* The answer
that shows experience notices that a job's exit status usually means *"it completed"* rather than
*"what it found"*, and names all three channels — the exit code, the report, and the absence of a run —
because a system with only the second is one person's holiday away from silence.
