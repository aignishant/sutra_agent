# 2.2 — The attributes are a contract, half-kept

## One-line answer

Half of what ADK writes on a span uses the OpenTelemetry GenAI conventions and half uses its own
`gcp.vertex.agent.*` names, so a backend that only speaks the standard reads thirty-seven of
sixty-eight attributes — and two span kinds, including the root of every trace, carry no
`gen_ai.operation.name` at all.

## The story

The address on an envelope.

There is a shape everybody uses: name, then house and street, then locality, then city, then the
postal code in a box at the bottom. Nobody was taught it as a rule and everybody follows it, which
is why a sorting machine can read a hundred thousand envelopes an hour without knowing a single
address in advance. The shape is the agreement.

Now write one with the postal code halfway up in the corner, and the street after the city. A human
will still deliver it. The machine will not — not because the information is missing, but because
the machine reads *positions*, and a position is only meaningful if everybody agreed to it.

The information and the agreement are different things. Only one of them scales.

## The idea in plain language

An **attribute** is a key-and-value written on a span: `gen_ai.tool.name = "ticket"`. The span's
name says what kind of thing happened; the attributes say the particulars.

A **semantic convention** is an agreement about what those keys are called. OpenTelemetry publishes
one for generative-AI systems — `gen_ai.operation.name`, `gen_ai.agent.name`, `gen_ai.tool.name`,
`gen_ai.request.model`, and so on — and the entire point is that a trace viewer written by people
who have never heard of ADK can display an ADK trace usefully, because it recognises the keys.

ADK writes two families:

| Family | Who defines it | What a generic backend does with it |
| --- | --- | --- |
| `gen_ai.*` | the OpenTelemetry GenAI conventions | understands it: filters, groups, charts it |
| `gcp.vertex.agent.*` | ADK itself | stores it as an opaque string |

Neither family is wrong. The standard family cannot express everything a framework knows — there is
no conventional key for "the ADK event id" — so a vendor namespace is the correct place for the
rest, and that is exactly what a namespaced prefix is for.

What matters is the **ratio**, and which side of the line the useful things fall on. If the
attribute you filter by every day is in the vendor family, you are locked to a backend that
understands ADK. If it is in the standard family, you can change backends.

There is a further split inside the standard itself, visible in ADK's source: `_stable_semconv.py`
and `_experimental_semconv.py`. The GenAI conventions are not finished, and ADK's own code imports
several keys from `opentelemetry.semconv._incubating` — a module whose name is a promise that it
will change. Anything built on those keys is built on a moving surface, and that is a fact to know
before a dashboard depends on one.

## Why Sutra needs it

Because Phase 13 ends with this desk deployable, and "which backend" is a decision nobody has made
yet. Whether that decision is reversible depends entirely on how much of the useful information is
in the standard family — this part is the measurement that makes the question answerable rather
than a matter of opinion.

And because Day 88 puts a tool server in a second container. Two processes emitting spans into one
trace only produce a coherent picture if both use the same names for the same ideas, and "the same
names" means a convention rather than a local habit.

## The mechanism

The lab sorts every attribute into its family and counts:

```python
def family(key: str) -> str:
    if key.startswith(STANDARD):
        return "gen_ai.*"
    if key.startswith(VENDOR):
        return "gcp.vertex.agent.*"
    return "other"
```

**Line by line:**

- Prefix matching, because that is exactly what a namespace is — the convention's whole enforcement
  mechanism is that everybody agrees to put their own things under their own prefix.
- A third bucket, `other`, for anything in neither. It is not empty in general: OpenTelemetry's own
  `error.type` lands there, and part [5.1](../05-in-production/5.1-reading-a-trace.md) uses it.
- No `else` raising on an unknown prefix. An unknown key is information, not a fault.

And the required-attribute check:

```python
        operations = {s.attributes.get(REQUIRED, "-") for s in same}
        if "-" in operations:
            missing += 1
```

**Line by line:**

- `REQUIRED` is `gen_ai.operation.name`, which the conventions mark as required on every GenAI span.
  It is the key a backend uses to decide *what kind of thing this is*, so a span without it cannot be
  classified by anything generic.
- `.get(REQUIRED, "-")` rather than indexing: a missing attribute is the finding, so it must not
  raise.
- The check is per span *name*, not per span, because the answer is a property of the instrumentation
  rather than of a particular run.

Run it:

```bash
cd days/day-84-the-trace-tree/lab
uv run python attrs.py; echo "exit: $?"
```

**Line by line:**

- No flag: the summary. `--one <name>` dumps a single span, which is part
  [2.1](2.1-agent-tool-and-model.md)'s view.

Measured on 2026-09-07:

```text
10 spans, grouped by name

  span name                           gen_ai.*  gcp.vertex.agent.*         operation
  call_llm                                   2                   5                 -
  execute_tool refund_limit                  6                   5      execute_tool
  execute_tool ticket                        6                   5      execute_tool
  generate_content scripted-desk-1           5                   2  generate_content
  invocation                                 0                   0                 -
  invoke_agent desk                          4                   0      invoke_agent

  attributes in the standard family:   37
  attributes in ADK's own family:      31
  a backend that only knows the conventions reads 37 of 68

  2 span name(s) carry no gen_ai.operation.name
```

Three things in that table are worth stopping on.

**`invocation` has zero attributes.** The root span of every ADK trace — the one a trace list shows
you, the one you search for, the one whose duration is the request's duration — carries no
attributes at all. Not the session id, not the app name, not the user. Every piece of context a
person would filter a trace list by lives on its *child*.

**`call_llm` has no `gen_ai.operation.name`.** It is the span with the most vendor attributes on it
(five, including the full request and response) and a generic backend cannot tell what kind of
operation it is.

**`invoke_agent desk` has four standard attributes and zero vendor ones.** The agent span is the one
piece of this trace that is entirely portable, which is a nice illustration that the split is not
random: the newer, convention-aligned instrumentation is clean and the older paths carry the vendor
payload.

Thirty-seven of sixty-eight is fifty-four per cent. That is the answer to "how much of our
observability is portable", and it is a number rather than an argument.

## When it breaks

The criterion exits `1`, and the reason is the two span kinds with no operation name:

```text
  2 span name(s) carry no gen_ai.operation.name
exit: 1
```

There is no error text, and no backend will complain either. What happens instead, in a real
viewer, is that those spans render as an unclassified row: no icon, no type filter, excluded from
any "show me all model calls" query. The information is on the span — `gen_ai.request.model` is
right there on `call_llm` — and the key that would let a machine find it is not.

The second failure is slower and worse. Build a dashboard on
`gcp.vertex.agent.llm_request`, and it works, and it is genuinely the most useful attribute in the
trace. Then the backend changes, or ADK realigns that data onto a conventional key, and the
dashboard is empty. The vendor namespace is not a promise; it is a namespace.

The third is the incubating one. ADK's `tracing.py` imports from
`opentelemetry.semconv._incubating.attributes.gen_ai_attributes` — a leading underscore and the word
*incubating*, which together are as clear a warning as a library can give. Those keys can be renamed
in a minor release, and the symptom is a chart that goes flat rather than an import error, because
the *emitter* upgraded and the *dashboard query* did not.

## In production

**What a professional does.** Writes queries against the standard family and treats the vendor
family as detail you read once you have found the span. That keeps the expensive artefacts — the
dashboards, the alerts, the saved searches — on the portable half, and confines the lock-in to
things a person looks at by hand.

**What degrades at scale.** Cardinality. `gen_ai.request.model` is a good attribute to group by
because there are a handful of models; `gen_ai.conversation.id` is a terrible one, because there is
one per session and a backend that indexes it will store an index the size of the data. The rule is
that anything unique per request belongs on the span for *finding* it, never in a group-by, and
nothing in the emitting library can enforce that.

**The failure that only shows with real traffic.** A convention version bump. ADK pins a schema URL
— `Schemas.V1_36_0` in `tracing.py` — and a backend that understands 1.36 and receives 1.40 has to
decide what to do about renamed keys. Most do nothing, which means a rename splits one metric into
two, and the chart shows a cliff on the day of a library upgrade that nobody connects to the
upgrade.

**The review comment a senior engineer leaves:** *"Our root span has no attributes. Put the app
name, the session id and the request id on it — everything a person types into a search box has to
be on the span they are searching for, not on its child."*

**The interview question:** *"Why do semantic conventions matter if you control both ends?"* The
answer that shows experience is that you do not control both ends for long: the backend gets
replaced, a second language gets added, a vendor agent starts emitting into the same pipeline, and
the conventions are the only reason those three produce one picture instead of three.
