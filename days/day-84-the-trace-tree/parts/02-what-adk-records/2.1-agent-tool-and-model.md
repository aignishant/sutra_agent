# 2.1 — Agent, tool and model: the three spans ADK writes

## One-line answer

ADK instruments its own framework boundaries — one span per agent invocation, one per model call
and one per tool execution — and the shape those produce is a five-level tree in which the tool call
sits under the model turn that asked for it, not under the agent.

## The story

The order docket in a small restaurant.

One table orders, and one docket is written. It goes to the kitchen, where the cook tears off the
food half; the bar keeps the drinks half; and both halves carry the same table number at the top.
When the manager wants to know why table six waited, she does not ask three people what they
remember. She finds the two halves, and the times pencilled on them, and the answer is in the gap.

Nobody at that restaurant decided to build a tracking system. They decided that each *station*
writes down what it did, on paper that already carries the table number. The tracking system is
what that adds up to.

## The idea in plain language

ADK does not trace everything. It traces the places where the framework itself does something
meaningful — which turns out to be exactly three kinds of boundary, plus a root.

| Span name | What it covers | Where it comes from |
| --- | --- | --- |
| `invocation` | one whole run of the runner | the runner |
| `invoke_agent <name>` | one agent doing its work | `trace_agent_invocation` |
| `call_llm` | ADK's model-call step | `trace_call_llm` |
| `generate_content <model>` | the request to the model itself | `use_generate_content_span` |
| `execute_tool <name>` | one tool running | `trace_tool_call` |

Two of those are worth pausing on because they surprise people.

**`call_llm` and `generate_content` are two spans, not one.** The outer one is ADK's step — assemble
the request, run the before-model callbacks, handle the response. The inner one is the call to the
model client. The gap between them is framework overhead, and having it be a *visible gap* rather
than a number somebody has to believe is the entire argument for instrumenting at boundaries.

**A tool span is a child of a model span.** In the tree from part
[1.1](../01-what-a-trace-is/1.1-a-trace-is-a-tree.md), `execute_tool ticket` sits under
`generate_content`, which sits under `call_llm`, which sits under `invoke_agent desk`. That is not a
mistake. The tool call happened *because* that model turn asked for it, and it happened while that
turn was still being processed, so the nesting is causally correct. It also means the model span's
duration includes the tool's, which is the thing to remember before reading any duration.

The station that writes the docket knows what it did; it does not know what happens next. That is
why the tree is built from children pointing up.

## Why Sutra needs it

Because these five span names are the vocabulary for everything else in this day and everything in
Phase 13. The cost measurement in part [4.1](../04-what-a-trace-costs/4.1-the-bill-is-bytes.md)
counts them, the sampler in the paper keeps or drops them whole, and Day 88's sidecar question is
"which of these spans happens in which container".

And because they map one-to-one onto things this curriculum already built. `execute_tool` is Day 4's
tool call. `call_llm` is Day 3's loop step. `invoke_agent` is Day 55's delegation unit. The trace is
not a new model of the system; it is the model the system already had, made visible.

## The mechanism

The desk is a real ADK agent with two real tools:

```python
AGENT = LlmAgent(
    name="desk",
    model=MODEL,
    description="Answers refund questions about one ticket at a time.",
    instruction="Look the ticket up, check the limit, then answer in one sentence.",
    tools=[ticket, refund_limit],
)
```

**Line by line:**

- `name="desk"` is not decoration — it becomes the span name (`invoke_agent desk`) and the
  `gen_ai.agent.name` attribute. An agent called `agent1` produces a trace nobody can read.
- `description` becomes `gen_ai.agent.description` on the agent span. It is the field a person reads when
  they meet an unfamiliar agent in a trace viewer, which is a use nobody thinks of when writing it.
- `tools=[ticket, refund_limit]` — plain Python functions. ADK wraps each in a `FunctionTool`, the
  wrapper class name lands on the span as `gen_ai.tool.type`, and the function's **docstring**
  becomes `gen_ai.tool.description`. An undocumented tool produces an unlabelled span.
- `model=MODEL` is `"scripted-desk-1"`, matched by `ScriptedDesk.supported_models()`. The registry
  seam from Day 80 is what makes this whole day free.

The spans come out of the runner with no instrumentation code of ours anywhere:

```python
async def run_desk(plugins: list | None = None) -> int:
    """Run one whole invocation. Returns the number of events the runner produced."""
    ScriptedDesk.calls = 0
    runner = InMemoryRunner(agent=AGENT, app_name=APP, plugins=plugins)
    session = await runner.session_service.create_session(app_name=APP, user_id=USER)
```

**Line by line:**

- `InMemoryRunner` rather than a hand-rolled loop, because the spans are emitted by the runner and
  the flows. Driving the agent directly would produce a different, smaller tree.
- `ScriptedDesk.calls = 0` resets the script between runs — a class attribute, so a second run in
  the same process starts from the same turn. Without it the second invocation would begin at turn
  three and answer immediately.
- `plugins=plugins` threads through to part [2.3](2.3-every-function-in-the-tree.md); `None` here
  means ADK's own instrumentation and nothing else.
- `create_session` before running: the session id becomes `gen_ai.conversation.id` on the agent
  span, which is the field that joins a trace to Day 47's persistent sessions.

Which spans carry which attributes:

```bash
cd days/day-84-the-trace-tree/lab
uv run python attrs.py --one execute_tool
```

**Line by line:**

- `--one execute_tool` prints every attribute on the first span whose name starts with that, which
  is how you find out what a span actually holds rather than what the documentation says it holds.

**The arguments and the response are both on the span.** `tool_call_args` is `{"ticket_id":
"4688"}` and `tool_response` is the dict the function returned. A tool span is not a marker saying
a tool ran; it is the whole call, recorded.

Note `llm_request` and `llm_response` sitting on a *tool* span as empty objects. They are set
unconditionally by ADK's tool tracing and are meaningless here — two attributes of pure noise on
every tool span in every trace. Small, and it is the kind of thing that becomes a gigabyte a year in
part [4.1](../04-what-a-trace-costs/4.1-the-bill-is-bytes.md).

## When it breaks

The nesting is the thing that breaks people's reading, and it breaks in the direction of
double-counting.

Because `execute_tool` is a child of `generate_content`, the model span's duration **contains** the
tool's. In part [1.1](../01-what-a-trace-is/1.1-a-trace-is-a-tree.md)'s measured tree:

```text
      call_llm                                 5556 us
        generate_content scripted-desk-1       4964 us
          execute_tool ticket                  4964 us
```

The model turn took 4,964 microseconds and the tool took 4,964 microseconds — the *same* number,
because in that run the model turn was almost entirely the tool call. Add those two figures together
and you get a total that is twice the elapsed time.

That is the standard trap with any nested timing, and the standard fix has a name: **self time**,
which is a span's duration minus the sum of its children's. Nothing in ADK computes it and nothing
in this lab does either; it is a `TODO(me)` in the hub, and it is the difference between "the model
is slow" and "the model is waiting for our ticket store".

There is no error here to quote. The durations are correct and the arithmetic a reader does with
them is not.

The second failure is a name. Span names include the agent, tool and model — `invoke_agent desk`,
`execute_tool ticket`, `generate_content scripted-desk-1` — which is good for reading and bad for
grouping: a backend that aggregates by span name sees one name per model version, so changing the
model splits every chart. The convention that avoids it is to keep the name generic and put the
detail in attributes, and ADK does not follow it.

## In production

**What a professional does.** Instruments at boundaries, not at functions. Every span costs storage
and every span name is a decision that has to survive a refactor, so the ones worth writing by hand
are the places where responsibility changes hands: a call out, a call in, a unit of work a person
would name. Part [2.3](2.3-every-function-in-the-tree.md) is what the opposite policy measures.

**What degrades at scale.** Fan-out. This desk called two tools serially. A real one calls five in
parallel (Day 54), and then five sibling spans start at once under one parent, and the parent's
duration is the slowest of them rather than the sum — which is the right answer and the opposite of
the serial case, and no one reading a duration column can tell which they are looking at without
the tree.

**The failure that only shows with real traffic.** A tool that spawns work outliving its span.
`execute_tool` ends when the function returns; if the function scheduled something on a queue, that
work is a different trace, and the tool span says it took a millisecond. Day 36's long jobs are
exactly this shape, and the fix is a span link rather than a parent — the same three numbers,
carried on the message.

**The review comment a senior engineer leaves:** *"Do not sum durations in that dashboard. Those
spans nest, so the total is meaningless — compute self time or show the tree."*

**The interview question:** *"What would you instrument in an agent framework?"* The answer that
shows experience names boundaries — agent, model, tool — and then says why the tool span belongs
under the model turn: because the causal parent of a tool call is the turn that requested it, and a
trace that flattens them cannot answer which turn went wrong.
