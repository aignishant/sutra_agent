# 2.3 — Every function in the tree: AutoTracingPlugin

## One-line answer

`AutoTracingPlugin` monkey-patches every in-scope Python function to emit a span, which takes this
desk from ten spans to sixty and from eight thousand bytes to a hundred and thirty-three thousand —
a complete picture that is sixteen times the size and, for most questions, harder to read than the
ten.

## The story

The house-shifting inventory that listed the loose screws.

The movers offered an itemised list and the family said yes, because the last time something went
missing and nobody could prove it. So everything got a line: the fridge, the beds, the four cartons
of kitchen things — and also, because the man with the clipboard was thorough, the packet of
curtain hooks, the spare screws from the bed frame in a matchbox, and each of the seven plastic
stools individually.

Nine pages. On the other end, a chair leg was cracked and the family wanted to raise it. Finding
"dining chair, 4" in nine pages of screws took twenty minutes of turning paper, and by then the
argument was about the paperwork.

The list was complete and true. The one-page version, with the eleven things worth arguing about,
would have won the argument.

## The idea in plain language

Part [2.1](2.1-agent-tool-and-model.md) described **manual instrumentation**: a library author
decides which boundaries matter and writes a span for each. It is precise and it is limited to what
the author thought of.

**Automatic instrumentation** takes the opposite policy: wrap everything, and let whoever reads the
trace decide what mattered. ADK ships one as a plugin.

`AutoTracingPlugin` works by monkey-patching. In its `before_run_callback` it walks `sys.modules`,
picks the modules whose names match its scope prefixes, and replaces their functions with wrapped
versions that open a span, call the original and close it. It does this once, guarded by a lock,
and remembers which modules it has already done.

Three constructor arguments decide how much it does:

| Argument | Default | What it controls |
| --- | --- | --- |
| `extra_scope_prefixes` | `()` | which extra module prefixes get wrapped |
| `max_walk_depth` | `30` | how deep it follows objects when recording arguments |
| `max_repr_len` | a cap in `auto_tracing_helpers` | how much of each argument it writes down |

The last two exist because the plugin records arguments and return values, and an argument in an
agent framework can be an entire conversation. Without caps a single span attribute could be
megabytes.

And the guard from part [1.3](../01-what-a-trace-is/1.3-the-run-that-left-no-trace.md) applies here
too: the constructor computes `tracer_will_record(self._tracer)` once, and `tracer_will_record` is
`not isinstance(tracer, NoOpTracer)`. Set `OTEL_SDK_DISABLED=true` in the environment and
`get_tracer` returns a real `NoOpTracer`, so the plugin installs itself, wraps nothing, and reports
nothing — measured in **When it breaks**.

## Why Sutra needs it

Because the plan names this plugin specifically (ADK-74), and because the honest answer to "should
we use it" is *sometimes*, which is only defensible with a number. This part produces the number.

And because the decision recurs for the rest of the phase. Day 86 puts this desk in a container with
a storage bill attached, and "trace everything" is a choice that looks free in development — where
ten extra spans on a laptop cost nothing — and is a line item in production.

## The mechanism

Fitting it is three lines, and each one is load-bearing:

```python
        plugins = [
            AutoTracingPlugin(
                tracer=trace.get_tracer("auto"),
                extra_scope_prefixes=("_desk",),
            )
        ]
```

**Line by line:**

- `tracer=trace.get_tracer("auto")` is passed explicitly rather than left to the default. Fetch order
  does not matter here — `get_tracer` before a provider is installed returns a `ProxyTracer` that
  resolves lazily, and `tracer_will_record` is `True` for it — but the tracer *name* does, because it
  is what a backend groups instrumentation by.
- `extra_scope_prefixes=("_desk",)` adds this lab's own module to the plugin's scope, so the desk's
  functions get wrapped alongside ADK's. Without it the plugin traces the framework and not the
  application, which is the wrong half.
- A tuple, not a list. The constructor stores `tuple(extra_scope_prefixes)`, and a prefix set that
  cannot be mutated after wrapping has begun is one fewer way to get a half-instrumented process.

Telling the plugin's spans from ADK's is prefix matching on the name:

```python
BY_HAND = {"invocation", "invoke_agent", "call_llm", "generate_content", "execute_tool"}


def hand_written(name: str) -> bool:
    return any(name == known or name.startswith(known + " ") for known in BY_HAND)
```

**Line by line:**

- The `known + " "` case is because ADK's span names carry a suffix — `invoke_agent desk`,
  `execute_tool ticket` — so an exact-match set is not enough.
- The plugin's own names are `Class.method`, which never collide with these, so a prefix test is
  sufficient and no attribute lookup is needed.

Run both arms:

```bash

```

**Line by line:**

- No flag: the plugin fitted. `--off` is the ablation, and it exits `1` — a plugin that adds nothing
  is reported as a failure, because the most likely reason is that it is not really running.

## When it breaks

It breaks by cost, and the cost is not the span count — it is the bytes, because the plugin records
arguments and return values.

```bash
uv run python cost.py --auto | tail -6
```

**Line by line:**

- `--auto` fits the plugin and then measures the same trace as part
  [4.1](../04-what-a-trace-costs/4.1-the-bill-is-bytes.md) measures without it.

Measured on 2026-09-07:

```text
  one invocation                       133220 bytes

  at 400 invocations a day: 53.3 MB/day, 19.45 GB/year
  spans a day: 24,000
```

Against 8,051 bytes and 1.18 GB a year for the ten hand-written spans. **The plugin multiplies the
span count by six and the storage by sixteen and a half**, because the extra spans each carry a
`repr` of their arguments, and in an agent framework an argument is often an invocation context
holding an entire conversation. `max_repr_len` and `max_walk_depth` exist precisely to stop that
being unbounded, and their existence is the clearest possible signal about what this plugin does.

There is no error text. Nothing fails; a bill arrives.

The second failure is the silent one, and it is one environment variable away:

```bash
OTEL_SDK_DISABLED=true uv run python auto.py; echo "exit: $?"
```

**Line by line:**

- `OTEL_SDK_DISABLED` is OpenTelemetry's own kill switch, read by the SDK at import. It is the
  supported way to turn tracing off in an environment, which is exactly why it is dangerous: somebody
  sets it in one deployment for a good reason and it is inherited by another.

Measured on 2026-09-07:

```text
AutoTracingPlugin: fitted

  spans in total:                 0
  spans ADK writes by hand:       0
  spans the plugin added:         0

  the plugin added nothing: either it is not fitted, or its tracer will not record
exit: 1
```

**Zero spans, including ADK's own ten.** The plugin is constructed, the `AutoTracingPlugin` is in the
runner's plugin list, `before_run_callback` runs — and `tracer_will_record` returned `False` at
construction, so nothing was wrapped, and ADK's hand-written spans are gone too because the whole SDK
is off. No warning, no error, and a startup line saying *tracing: enabled* would have been a lie.

The third failure is subtler and it is the reason to be careful with monkey-patching at all. The
plugin replaces functions in `sys.modules` at the moment `before_run_callback` runs. A module
imported *after* that — a lazily imported tool, a plugin loaded on demand — is not in `sys.modules`
yet, so it is not wrapped, and the coverage of an "automatic" instrumentation quietly depends on
import order. The plugin handles this by re-walking on each run and keeping a `_wrapped_modules`
set, so it catches up on the second invocation; the first invocation after a lazy import is
under-traced, and nothing says so.

## In production

**What a professional does.** Uses automatic instrumentation as a *diagnostic*, not as a default:
switch it on in a development environment or behind a flag while chasing something specific, read
it, switch it off. The permanent trace is the hand-written one, which is small, stable, and shaped
like the questions people actually ask.

**What degrades at scale.** Everything, in the same direction. More traffic multiplies the sixteen
times; deeper call stacks add depth to every trace; and the trace viewer itself becomes the
bottleneck, because rendering a six-hundred-span tree is slow and reading one is slower. The point
at which "complete" becomes "unusable" arrives well before the storage bill does.

**The failure that only shows with real traffic.** Content in arguments. Every wrapped function's
arguments get a `repr` written to a span, and somewhere in a real system a function takes a
customer's message, an API key, or a session token. Part
[4.2](../04-what-a-trace-costs/4.2-the-prompt-inside-the-span.md) measures the same problem for
ADK's own hand-written spans, where at least the fields are known and there is an environment
variable to turn them off. With automatic instrumentation the surface is every argument of every
function in scope, and there is no equivalent switch.

**The review comment a senior engineer leaves:** *"Not on by default. Put it behind an environment
variable, and never enable it in an environment that handles real customer messages until somebody
has read what ends up in the argument attributes."*

**The interview question:** *"Automatic instrumentation gives you complete coverage. Why would you
not use it?"* The answer that shows experience does not say "performance". It says that a trace is
read by a person under time pressure, that completeness and legibility trade against each other,
and that the argument-recording is a data-protection surface nobody audited.
