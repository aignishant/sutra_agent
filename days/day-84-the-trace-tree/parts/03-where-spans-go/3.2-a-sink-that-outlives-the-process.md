# 3.2 — A sink that outlives the process

## One-line answer

ADK ships `SqliteSpanExporter`, which writes every span to a local file with its parent link intact
at zero cost and no network — and its projection keeps only four columns beside the JSON blob, so
three of this desk's ten spans, including the root, land with no session id.

## The story

The chalkboard and the ledger.

Behind the counter there are two ways of writing something down. The chalkboard is for today: what
came in, who owes what, wiped at closing so tomorrow starts clean. It is fast, it is right there,
and everyone uses it a hundred times a day.

The ledger is the one under the counter. Slower to write in, harder to correct, and the only reason
it exists is the question that arrives three months later — *when did we last get a delivery from
them?* — which the chalkboard cannot answer, because the chalkboard is about now and that question
is about then.

Nobody argues about which is better. They are for different questions, and a shop with only a
chalkboard is a shop that cannot answer anything about last week.

## The idea in plain language

Every measurement so far in this day used `InMemorySpanExporter`, which is the chalkboard: a Python
list, wiped when the process exits. It is exactly right for a lab, where the whole point is to read
the spans back in the same script that produced them.

It is useless for the question people actually have, which is always about a run that already
finished.

ADK ships a ledger: `google.adk.telemetry.sqlite_span_exporter.SqliteSpanExporter`. It takes a
`db_path`, creates its schema on first use, and writes one row per span. Every relevant property of
this day's subject holds up:

- **Free.** SQLite is in the Python standard library. No account, no collector, no network, no
  container.
- **Durable.** A file survives the process, so a trace from this morning is readable this afternoon.
- **Queryable.** It is SQL, so "every span in this session" is a `WHERE` clause rather than a
  filter written in Python.

What it stores is worth reading, because the exporter is a **projection** — it picks fields out of
a span and puts them in columns, and what is not in a column is inside a JSON blob or gone:

```text
CREATE TABLE IF NOT EXISTS spans (
  span_id TEXT PRIMARY KEY,
  trace_id TEXT NOT NULL,
  parent_span_id TEXT,
  name TEXT NOT NULL,
  start_time_unix_nano INTEGER,
  end_time_unix_nano INTEGER,
  session_id TEXT,
  invocation_id TEXT,
  attributes_json TEXT
);
```

Nine columns. The three ids from part
[1.2](../01-what-a-trace-is/1.2-three-numbers-make-the-tree.md) are all there, which is what makes
the tree reconstructible after a round trip. Two timestamps. Then `session_id` and `invocation_id`,
promoted out of the attributes because they are what a person searches by — and there are indexes on
`session_id` and `trace_id` for exactly that reason.

Everything else is `attributes_json`.

## Why Sutra needs it

Because Day 82 spent a whole day on the fact that this repository keeps no history, and found that
`.gitignore` line 24 swallows ADK's eval results. The same question arrives here in a different
shape — where do the traces go — and it has a good answer that costs nothing, before Phase 13 gets
to the point where the answer involves a collector somebody has to run.

And because the zero-budget rule (Principle 15) makes this the only tracing sink available. There is
no OTLP exporter installed and there is no collector to send to. A file is what there is, and it
turns out to be enough for everything this day needs.

## The mechanism

Three lines to write spans to a file:

```python
    exporter = SqliteSpanExporter(db_path=str(DB))
    provider = with_processor(SimpleSpanProcessor(exporter))
```

**Line by line:**

- `db_path` is keyword-only — the constructor is `def __init__(self, *, db_path: str)` — which stops
  a positional argument from being silently taken as something else in a future version.
- `str(DB)` because the parameter is a `str` and `DB` is a `Path`. Passing the `Path` works today by
  accident of `sqlite3.connect` accepting path-likes; the annotation says `str`, so this converts.
- Same `SimpleSpanProcessor` as everywhere else in this lab. The destination changed and the timing
  did not, which is part [3.1](3.1-a-processor-and-an-exporter.md)'s whole argument.

Getting the spans out at the end matters, and the order matters:

```python
    provider.force_flush()
    provider.shutdown()
```

**Line by line:**

- `force_flush()` pushes anything pending through the processor. With `SimpleSpanProcessor` there is
  nothing pending, so this is a no-op — and it is here anyway, because the line that is a no-op today
  is the line that saves you when somebody swaps in `BatchSpanProcessor`.
- `shutdown()` closes the exporter, which closes the SQLite connection. Without it the file stays
  locked, which on Windows means it cannot be deleted — the `PermissionError` quoted in part
  [3.1](3.1-a-processor-and-an-exporter.md).

And reading it back is ordinary SQL:

```python
    connection = sqlite3.connect(DB)
    try:
        rows = connection.execute(
            "SELECT name, span_id, parent_span_id, session_id, length(attributes_json)"
            " FROM spans ORDER BY start_time_unix_nano"
        ).fetchall()
    finally:
        connection.close()
```

**Line by line:**

- `ORDER BY start_time_unix_nano` — start time, not end time, so the rows come out in the order the
  work began rather than part [1.1](../01-what-a-trace-is/1.1-a-trace-is-a-tree.md)'s
  finishing order.
- `length(attributes_json)` rather than the blob itself, because the interesting fact here is the
  size and pulling seven kilobytes of JSON to measure it would be silly.
- `try/finally` with an explicit `close()`. This is the bug from part
  [3.1](3.1-a-processor-and-an-exporter.md), fixed: the connection has to be closed before the file
  is touched, and a `finally` is the only way to guarantee it if the query raises.

Run it:

```bash
cd days/day-84-the-trace-tree/lab
uv run python sink.py; echo "exit: $?"
```

**Line by line:**

- No flag: the database is created, written, read back and deleted, so two runs of the script agree.
  `--keep` leaves it for you to open.

Measured on 2026-09-07:

```text
  spans stored:      10
  session ids:       1
  spans with none:   3
  orphaned spans:    0
  attribute payload: 7220 bytes of JSON

  spans.db removed; pass --keep to leave it behind

  every span came back, and every parent link still resolves
```

**Ten stored, zero orphans, and three with no session id.** The round trip is faithful — every
parent link still resolves, so the tree survives — and the promoted column is populated for seven of
the ten spans.

## When it breaks

The three spans without a session id are the finding, and the trap is the query a person writes
first. `WHERE session_id = ?` is the obvious thing — there is an index on that column, and the
column exists precisely to be searched — and it returns **seven of the ten spans**, missing
`invocation`, the **root**, along with two others.

Measured on 2026-09-07:

```text
groups: [(None, 3), ('0d9bdf4d-fdf8-40d4-8544-a02f15a33d72', 7)]
```

Nothing raises. The result is a tree with no root, which a viewer draws as several separate traces.

The cause is part [2.2](../02-what-adk-records/2.2-the-attributes-are-a-contract.md)'s finding one
layer down: the exporter promotes `session_id` out of the span's attributes, and the root span has
no attributes at all, so there is nothing to promote.

**ADK knows.** Its own accessor does not use that query, and its docstring says why:

```text
  def get_all_spans_for_session(self, session_id: str) -> list[ReadableSpan]:
    """Returns all spans for a session (full trace trees).

    We first find trace_ids associated with the session, then return all spans
    for those trace_ids. This works even if some spans are missing session_id
    attributes (e.g. parent spans).
    """
```

**Line by line:**

- Two queries rather than one: `SELECT DISTINCT trace_id ... WHERE session_id = ?`, then
  `SELECT * ... WHERE trace_id IN (...)`. The session column is used to *find* the traces and never
  to select the spans.
- `(e.g. parent spans)` is the library authors naming this exact gap in a comment.
- Called on the same database, it returns **ten of ten** — so the API is correct and the obvious
  hand-written query is not.

That is the shape worth carrying: the projection is lossy in a specific way, the library's own
accessor compensates, and anybody who writes the natural SQL instead gets a partial trace with no
error. Use the accessor, or copy its two-step pattern.

The second break is size. Ten spans made a 32,768-byte file, which is four SQLite pages and mostly
empty. That is not a measurement of the data — 7,220 bytes of it is attribute JSON — but it is a
reminder that a database has a floor, and the honest per-span numbers are in part
[4.1](../04-what-a-trace-costs/4.1-the-bill-is-bytes.md).

## In production

**What a professional does.** Uses a local file sink in development and for tests, and a collector in
production — with the same instrumentation and only the exporter swapped, which is exactly what part
[3.1](3.1-a-processor-and-an-exporter.md)'s split buys. The version of this that goes wrong is
writing application code that knows it is talking to SQLite.

**What degrades at scale.** SQLite is one writer. Under a threaded server every export contends for
the same file lock, and the batch processor's background thread becomes a serialisation point.
It is a fine sink for one process on a laptop and the wrong one for a container serving traffic,
which is the honest boundary to state before Day 86 asks the question.

**The failure that only shows with real traffic.** The file is inside the container. Day 82 part 2.2
found eval history written to a gitignored directory; the container version is worse, because the
filesystem does not merely go unread, it ceases to exist when the container stops. A sink that
survives the *process* is not the same as one that survives the *deployment*, and this exporter only
does the first.

**The review comment a senior engineer leaves:** *"Fine locally. Before this ships, the exporter is a
config value and the container writes to a collector, because a trace file in a container is a trace
file nobody will ever read."*

**The interview question:** *"Where do your traces go in development?"* The answer that shows
experience names a sink that survives the process and can be queried, and then names the thing that
changes in production and the thing that does not — the exporter changes, the instrumentation does
not.
