# 3.1 — A processor and an exporter

## One-line answer

A finished span goes to a **processor**, which decides when to hand it on, and then to an
**exporter**, which decides where it goes — and separating those two jobs is why you can change
backends without touching batching, and change batching without touching backends.

## The story

The suggestion box on the wall.

Somebody screwed it up by the canteen door with a slot in the top, and it works: a person with a
complaint writes it down and posts it, and walks away, and is not kept waiting while anybody reads
it. That is the whole value of the box — the writer is decoupled from the reader.

But a box is not a system. What makes it one is the second decision, which nobody wrote down and
everybody assumes: **who empties it, how often, and where do the slips go.** Somebody from the
office, Friday afternoon, into the folder for the monthly meeting. Change the day and the box still
works. Change the destination — send them to the site manager instead — and the box still works.

Two decisions, one hole in the wall, and confusing them is how a box ends up full for a year.

## The idea in plain language

When a span ends, OpenTelemetry hands it to whatever **span processors** are registered on the
tracer provider. That is a small interface with one important method, `on_end`, and it is the only
thing that happens synchronously in the code path that produced the span.

The processor's job is **timing**. There are two that ship:

| Processor | When it hands the span on | Use it for |
| --- | --- | --- |
| `SimpleSpanProcessor` | immediately, on the calling thread | tests, local development |
| `BatchSpanProcessor` | on a background thread, in batches | anything that talks over a network |

The exporter's job is **destination**. `InMemorySpanExporter` keeps them in a list;
`ConsoleSpanExporter` prints them; ADK's `SqliteSpanExporter` writes them to a file; an OTLP
exporter posts them to a collector.

The split is the design, and it is worth being explicit about why it is good. Batching is a hard
problem — queues, backpressure, a background thread, flushing on exit — and it has nothing to do
with any particular destination. Solving it once, in a processor, means every exporter gets it for
free, and writing a new exporter is a class with an `export` method.

This lab uses `SimpleSpanProcessor` everywhere except part
[3.3](3.3-the-queue-that-went-with-the-process.md), and that is a deliberate choice with a cost:
simple means synchronous, so the export happens *inside* the traced work. For an in-memory list that
is a list append. For anything with a network in it, it would mean the desk waits for the trace
backend, which is the wrong trade in every production system and the reason `BatchSpanProcessor`
exists.

## Why Sutra needs it

Because "where do the spans go" is the decision Phase 13 has to make, and it is two decisions.
Day 86 puts the desk in a container where the answer to *where* changes completely — a file inside a
container is gone when the container stops — while the answer to *when* does not change at all.

And because the processor is where the failure in part [3.3](3.3-the-queue-that-went-with-the-process.md)
lives. Knowing that the queue exists, and that something has to drain it before the process ends, is
the difference between a trace pipeline that works and one that works on a laptop.

## The mechanism

Installing them is three lines, and this lab keeps them in one place because a provider can only be
installed once per process:

```python
def collect() -> InMemorySpanExporter:
    """Record every span into memory. Returns the exporter to read them back from."""
    exporter = InMemorySpanExporter()
    provider = TracerProvider()
    provider.add_span_processor(SimpleSpanProcessor(exporter))
    trace.set_tracer_provider(provider)
    return exporter
```

**Line by line:**

- `TracerProvider()` is the SDK's implementation. The `opentelemetry-api` package alone gives you a
  no-op; the `opentelemetry-sdk` package gives you this. That split is why a library can depend on
  the API without forcing a tracing implementation on its users, and it is the reason part
  [1.3](../01-what-a-trace-is/1.3-the-run-that-left-no-trace.md)'s failure is the default.
- `add_span_processor`, plural by design: a provider can have several, so the same spans can go to a
  local file and a remote collector without either knowing about the other.
- `SimpleSpanProcessor(exporter)` — the processor wraps the exporter, which is the composition the
  whole design rests on.
- `set_tracer_provider(provider)` is global and one-shot. A second call logs
  `Overriding of current TracerProvider is not allowed` and is ignored, so this function is called
  exactly once per process, before anything that might emit a span.
- The exporter is *returned*, because it is the only handle on the spans afterwards. Nothing else in
  the API lets you read back what was exported.

The other shape, where the caller supplies the processor:

```python
def with_processor(processor: SpanProcessor) -> TracerProvider:
    """Install a provider with one caller-supplied processor. Returns it, so it can be shut down."""
    provider = TracerProvider()
    provider.add_span_processor(processor)
    trace.set_tracer_provider(provider)
    return provider
```

**Line by line:**

- This one returns the **provider**, not the exporter, and the docstring says why: `shutdown()` and
  `force_flush()` live on the provider, and parts 3.2 and 3.3 both need them.
- Taking a `SpanProcessor` rather than an exporter lets the caller choose the timing, which is the
  distinction this whole part is about.

## When it breaks

The processor runs `on_end` **on the thread that ended the span**. With `SimpleSpanProcessor` that
means the exporter's `export` call happens inside the traced code path, so anything slow or failing
in the exporter becomes slow or failing in the desk.

That is easy to say and easy to underestimate, so here is the shape of it:

```text
1. SimpleSpanProcessor is chosen in development, because it is simple and synchronous
2. the exporter is swapped for one that posts to a collector
3. the collector is slow one afternoon
4. every span end blocks on an HTTP request
5. the desk's latency doubles, and the traces say the desk got slower
```

Step 5 is the joke: the instrument reports the problem it caused. There is no error text, because a
slow export is not an error.

`BatchSpanProcessor` is the fix, and it has its own failure, which is the subject of part
[3.3](3.3-the-queue-that-went-with-the-process.md).

The second break is quieter and this lab hit it. An exporter holds a resource — a file handle, a
connection, a socket — and the only thing that closes it is `shutdown()`. On Windows an unclosed
SQLite handle makes the file undeletable, and the first version of `sink.py` failed with:

```text
PermissionError: [WinError 32] The process cannot access the file because it is being
used by another process: '...\\days\\day-84-the-trace-tree\\lab\\spans.db'
```

That was a real traceback from writing this lab, and the cause was a `sqlite3.connect` that was
never closed rather than the exporter — but the lesson is the same either way: an exporter is a
resource, and the provider's `shutdown()` is what releases it.

## In production

**What a professional does.** `BatchSpanProcessor` everywhere except tests, and `shutdown()` wired
to whatever the process uses for orderly exit — a signal handler, a framework lifespan hook, an
`atexit`. The choice is not a preference: a synchronous exporter puts the observability backend on
the critical path of every request, which means an outage in the thing that watches the system
becomes an outage in the system.

**What degrades at scale.** The queue. `BatchSpanProcessor` has a bounded queue — 2,048 spans by
default — and when it is full it drops. That is the correct behaviour and it is also silent, so at
high volume the number worth watching is the drop count, which is a metric the SDK exposes and
nobody looks at until traces go missing.

**The failure that only shows with real traffic.** Two providers. A library installs one at import,
the application installs another at startup, the second call is ignored with a warning nobody reads,
and half the system's spans go to an exporter that was meant to be temporary. The rule that prevents
it: exactly one place in the codebase calls `set_tracer_provider`, and it is the entry point.

**The review comment a senior engineer leaves:** *"Simple processor is fine for the tests. In the
server use the batch one, and show me where `shutdown()` gets called when the container gets its
termination signal."*

**The interview question:** *"Why does OpenTelemetry separate processors from exporters?"* The
answer that shows experience is not "separation of concerns". It is that batching, retry and
backpressure are one hard problem shared by every destination, so solving it once in the processor
makes a new exporter a class with one method — and it lets you change *when* without changing
*where*.
