# 3.3 — The queue that went with the process

## One-line answer

`BatchSpanProcessor` holds finished spans in memory and hands them on every five seconds, so a
process that exits without calling `shutdown()` delivers **zero of ten** spans — with no error, no
warning, and a run that was correct from end to end.

## The story

💥 **The letters left on the desk when the office closed for the holiday.**

🎬 **The scene.** Thursday afternoon before a long weekend. Four letters get written, signed, put in
envelopes and left in the out-tray on the corner of the desk, which is where letters go. The person
who empties the tray does it on their round, which is at four.

😬 **The naive fix.** The round happened at four and the tray was empty then, because the letters
were written at half past. No matter — they will go on Tuesday. Nobody thinks about it again,
because there is nothing to think about: the letters are written, signed and in the tray, which is
the whole of the job.

💥 **Why it fails.** On Friday the office is repainted and the desks are cleared. The out-tray gets
tipped into a box with everything else, the box goes into storage, and the four letters are not
posted, not returned, and not lost in a way anybody notices. The sender believes they were sent.
The recipients never heard. Both of those states are perfectly quiet.

💡 **The insight.** *In the tray* is not *sent*. There is a step between them that belongs to
somebody else, and it happens on a schedule — so anything that ends the day early ends it for
whatever is still in the tray.

## The idea in plain language

Part [3.1](3.1-a-processor-and-an-exporter.md) explained why you want a batch processor: exporting
synchronously puts the trace backend on the critical path of every request. `BatchSpanProcessor`
fixes that by putting finished spans on a queue and draining it from a background thread.

Its defaults are the whole story:

| Setting | Default | What it means |
| --- | --- | --- |
| `schedule_delay_millis` | 5000 | the background thread exports every five seconds |
| `max_queue_size` | 2048 | spans held before new ones are dropped |
| `max_export_batch_size` | 512 | how many go in one export call |

So at any moment, up to five seconds of spans and up to 2,048 of them are **in the tray**: recorded,
finished, correct, and not yet anywhere.

Two things drain the queue. The background thread on its timer, and an explicit
`provider.shutdown()`, which stops the timer, flushes everything and closes the exporter.

A short-lived process — a script, a job, a test, a container that gets a termination signal — very
often ends before the timer fires. If nothing called `shutdown()`, whatever was in the queue goes
with the process.

This is the same class of failure as part
[1.3](../01-what-a-trace-is/1.3-the-run-that-left-no-trace.md), reached from the opposite direction.
There, tracing was never turned on. Here it is turned on, configured correctly, and the spans are
produced — and the observable outcome is identical.

## Why Sutra needs it

Because Day 86 puts this desk in a container, and a container's normal way to stop is a `SIGTERM`
followed by a short grace period. Everything about that is designed around the assumption that the
process shuts itself down in an orderly way, and "flush the span queue" is one of the things orderly
means.

And because Day 73's nightly runs this desk as a scheduled job. A job is the worst case for this
bug: it starts, does a few seconds of work, and exits — so the timer never fires even once, and the
job produces a complete set of spans of which none are ever exported.

## The mechanism

The lab installs a batch processor and then deliberately does or does not shut it down:

```python
    exporter = InMemorySpanExporter()
    processor = BatchSpanProcessor(exporter)
    provider = with_processor(processor)
```

**Line by line:**

- `InMemorySpanExporter` as the destination, so nothing here depends on a network being slow. The
  spans have one hop to travel and they still do not arrive, which isolates the processor as the
  cause.
- `BatchSpanProcessor(exporter)` with no arguments — every default in the table above. This is what
  somebody writes when they follow a getting-started guide, which is the point.
- `with_processor` returns the provider precisely so `shutdown()` can be called on it, which part
  [3.1](3.1-a-processor-and-an-exporter.md) noted at the time.

And the measurement is a count taken twice:

```python
    before = len(exporter.get_finished_spans())
    if shutdown:
        provider.shutdown()
    after = len(exporter.get_finished_spans())
```

**Line by line:**

- `before` is taken immediately after the desk finishes, which is where an ordinary program would
  exit. It is the number of spans that had made it out on their own.
- `shutdown()` between the two reads is the entire experiment.
- Counting rather than inspecting, because the question is delivery, not content.

Run it the way most programs are written:

```bash
cd days/day-84-the-trace-tree/lab
uv run python flush.py; echo "exit: $?"
```

**Line by line:**

- No flag: the process ends without shutting the provider down, which is what happens when nobody
  thought about it.

Measured on 2026-09-07:

```text
processor: BatchSpanProcessor, schedule_delay_millis=5000
shutdown called: False

  spans that reached the exporter, before shutdown: 0
  spans that reached the exporter, after:           0
  errors raised:                                    0

  the run produced spans and 5 seconds of queue
  the process is about to exit and the queue goes with it
```

**Zero of ten.** The desk ran, the spans were created, the processor accepted every one of them, and
the exporter — one function call away, in the same process, with no network anywhere — received
nothing.

Now the same run with one line added:

```bash
uv run python flush.py --shutdown; echo "exit: $?"
```

**Line by line:**

- `--shutdown` calls `provider.shutdown()` before the process ends. That is the whole difference.

Measured on 2026-09-07:

```text
  spans that reached the exporter, before shutdown: 0
  spans that reached the exporter, after:           10
  errors raised:                                    0

  10 spans delivered, because the provider was shut down
```

**Zero before, ten after.** Note that `before` is `0` in *both* runs — the desk finishes in
milliseconds and the timer has five seconds on it, so on this workload the background thread never
gets a chance. Every span in this trace is delivered by `shutdown()` or not at all.

## When it breaks

There is no error text. That is worth stating flatly because it is the reason this survives review:
a reader looking at the failing run sees a correct answer, an exit code of zero from the desk's own
work, and an empty trace backend — three facts that do not obviously belong to each other.

The composite, which is how it reaches production:

```text
1. tracing is added, with BatchSpanProcessor, correctly
2. it is tested by running the server and browsing traces - they appear, because
   the server lives longer than five seconds
3. the same setup is used by the nightly job, which lives for four seconds
4. the nightly's traces never appear
5. somebody concludes the nightly is not instrumented
6. an hour is spent adding instrumentation that was already there
```

Step 2 is why this passes testing: the bug is invisible in exactly the process where somebody looks
for it. Long-running servers are mostly fine — mostly, because the last five seconds before a
deploy's `SIGTERM` are lost, which is the window containing whatever the deploy interrupted.

There are two real log lines nearby, and neither one fires in the run above. From
`opentelemetry/sdk/_shared_internal/__init__.py`:

```text
Shutdown called, ignoring Span.
Queue full, dropping Span.
```

**Line by line:**

- The first is logged at `INFO` when a span is emitted after `shutdown()`, which is the mirror-image
  mistake: flushing too early, from a `finally` that runs while background work is still going.
- The second is logged at `WARNING` when the queue is at `max_queue_size` and the oldest span is
  discarded to make room. That one matters at volume and is the subject of **In production** below.
- Neither says anything about spans still sitting in the queue when the process ends, because from
  the processor's point of view nothing has gone wrong — it is holding them, exactly as designed.

The fix is one line and a decision about where it goes:

- a script: `try/finally` around the work, or `atexit.register(provider.shutdown)`
- a server: the framework's shutdown hook, which for the API of Day 85 is a lifespan handler
- a container: the same hook, because a container's stop is a signal to the process

## In production

**What a professional does.** Registers the flush at the same moment as the provider, in the same
function, so the two cannot drift apart. The pattern is: build the provider, install it, and
immediately register its shutdown with whatever this process uses to end — and never rely on the
timer, because the timer is an optimisation, not a delivery guarantee.

**What degrades at scale.** The queue fills. `max_queue_size` is 2,048 and a busy service with
automatic instrumentation (part [2.3](../02-what-adk-records/2.3-every-function-in-the-tree.md)
measured sixty spans per invocation) reaches that in a fraction of a second. Over-queue spans are
dropped with a `Queue full, dropping Span.` warning that goes into a log nobody is reading, and the
symptom is a trace with holes rather than a trace that is missing — which is harder to diagnose,
because a partial trace looks like a partial *system*.

**The failure that only shows with real traffic.** The grace period. A container gets `SIGTERM` and
then, some seconds later, `SIGKILL`. If the flush takes longer than the grace period — because the
queue is deep and the collector is slow — the process is killed mid-flush, and the spans that
mattered most (the ones from the requests that were in flight during a deploy) are the ones lost.
Tuning that is a real operational task and nothing in a getting-started guide mentions it.

**The review comment a senior engineer leaves:** *"Where does `shutdown` get called? Not 'the SDK
handles it' — show me the line, and show me that it runs when the job exits normally and when it
gets a signal."*

**The interview question:** *"Your traces work in the API and not in the batch job. Why?"* The answer
that shows experience goes straight to the lifetime: the batch processor delivers on a timer, the
job is shorter than the timer, and the fix is a flush on exit rather than any change to
instrumentation.
