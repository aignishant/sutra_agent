# 4.1 — The bill is bytes, not requests

## One-line answer

Tracing costs zero provider requests and eight thousand bytes an invocation, which is a gigabyte a
year at this desk's traffic — and the two switches that move that number most are the automatic
plugin, which multiplies it by sixteen, and content capture, which halves it.

## The story

The phone plan with unlimited calls.

The shop sold it that way and it was true: talk as long as you like, to anyone, at no extra charge.
For two months that was the whole story, and the bill was the bill.

The third month it was nearly double. Not the calls — the calls were free, exactly as promised. The
data. Nobody had thought of the phone as a thing that used data when it was sitting in a pocket, and
it had been backing photographs up over the mobile network all along, quietly, because that was the
default and nobody changed it.

The advertised meter was at zero. A different meter, that nobody had been shown, was running.

## The idea in plain language

Every cost this curriculum has counted since Day 24 has been denominated in **requests** — RPM and
RPD against a provider's free tier, because that is the currency that runs out.

Tracing does not spend that currency at all. Not one span in this day cost a provider request, and
that remains true at any volume: spans are produced locally from work that was going to happen
anyway.

The meter it does move is **storage**, and storage has three parts:

| What | Where it comes from |
| --- | --- |
| the attributes | whatever the instrumentation chose to write down |
| the span name | one string per span |
| the identifiers | 32 hex characters of trace id plus two lots of 16 for span and parent |

The identifiers are a floor: 64 characters per span no matter what, before anything useful is
written. The attributes are the variable, and in an agent framework they are the whole bill, because
one of them can be an entire prompt.

Two switches move the number, and they move it in opposite directions:

- `AutoTracingPlugin` (part [2.3](../02-what-adk-records/2.3-every-function-in-the-tree.md)) records
  every in-scope function with its arguments.
- `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` (part
  [4.2](4.2-the-prompt-inside-the-span.md)) stops ADK writing prompts and responses into attributes.

This part measures all three states of the same desk answering the same question, so the decision is
arithmetic rather than instinct.

## Why Sutra needs it

Because Day 86 puts this desk somewhere with a storage bill and Day 88 puts a second container
beside it, and "turn tracing on everywhere" is a sentence somebody will say in both of those days.
It is a good idea and it has a price, and the price should be on the page before the sentence is
said.

And because this is the first cost in the whole curriculum that is *not* a provider request. Day
78's schedulability arithmetic, Day 81's judge bill, Day 82's nightly — all of them denominated in
requests against an allowance. This one is denominated differently, which means the existing budget
machinery does not see it at all.

## The mechanism

The measurement counts the three parts separately:

```python
    payload = sum(len(json.dumps({k: str(v) for k, v in s.attributes.items()})) for s in spans)
    names = sum(len(s.name) for s in spans)
    # A span carries a 16-byte trace id, an 8-byte span id and an 8-byte parent, twice as hex.
    identifiers = len(spans) * (32 + 16 + 16)
    total = payload + names + identifiers
```

**Line by line:**

- `json.dumps` rather than `len(str(...))`, because JSON is how every exporter in existence
  serialises attributes — part [3.2](../03-where-spans-go/3.2-a-sink-that-outlives-the-process.md)'s
  SQLite column is literally called `attributes_json`. Measuring the Python `repr` would measure the
  wrong thing.
- `{k: str(v) for ...}` normalises attribute values to strings first. Attribute values can be ints,
  bools and sequences, and `json.dumps` of a mixed dict would be a slightly different size than what
  an exporter writes; forcing strings is the pessimistic and honest choice.
- `(32 + 16 + 16)` is the hex width of the three identifiers from part
  [1.2](../01-what-a-trace-is/1.2-three-numbers-make-the-tree.md). This is a floor and it is charged
  on every span, including the empty root.
- Timestamps are **not** counted, which makes this an underestimate: two 64-bit integers per span,
  plus whatever the wire format adds. The number below is a lower bound, and saying so is part of
  the measurement.

Then it projects:

```python
INVOCATIONS_PER_DAY = 400
...
    daily = total * INVOCATIONS_PER_DAY
```

**Line by line:**

- A named constant rather than a literal in the f-string, because the reader has to be able to
  change it and see their own number.
- Four hundred is this desk's shape, not a universal figure. Multiply by your own traffic; the
  per-invocation number is the transferable part.

Run all three states:

```bash
cd days/day-84-the-trace-tree/lab
uv run python cost.py | tail -6
uv run python cost.py --auto | tail -6
uv run python cost.py --quiet | tail -6
```

**Line by line:**

- `tail` on each, because the breakdown above the totals is the same in all three runs and the
  totals are what differ. The full output names the three parts separately.
- No flag is ADK's hand-written spans with content capture at its default, which is on.
- `--auto` fits `AutoTracingPlugin`.
- `--quiet` sets `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` before importing anything, because
  ADK reads it at import time.

Measured on 2026-09-07:

```text
  spans a day: 4,000

```

```text

  at 400 invocations a day: 53.3 MB/day, 19.45 GB/year

```

```text

  at 400 invocations a day: 1.7 MB/day, 0.62 GB/year
  spans a day: 4,000

  none of this is a provider request; all of it is storage, and storage is billed
```

Three states of one desk, in one table:

| Configuration | Bytes per invocation | Per year | Spans per day |
| --- | --- | --- | --- |
| content capture off | 4,244 | 0.62 GB | 4,000 |
| default | 8,051 | 1.18 GB | 4,000 |
| automatic instrumentation | 133,220 | 19.45 GB | 24,000 |

**The default is under a gigabyte and a half a year.** That is the headline, and it is the reason
the right answer to "should we trace?" is almost always yes: for a desk of this size, a complete
picture of every request for a year fits on a memory card.

**The plugin is sixteen and a half times that.** Six times the spans and sixteen times the bytes,
because the extra spans carry argument `repr`s. Nineteen and a half gigabytes a year is a different
conversation from one, and it is the same code doing the same work.

**Content capture is half the default bill.** 8,051 down to 4,244 — and part
[4.2](4.2-the-prompt-inside-the-span.md) is about the other reason to consider that switch, which is
a stronger reason than the bytes.

## When it breaks

The model breaks by leaving out the things nobody counted, and there are three.

**Retries and errors are bigger than successes.** A failing tool call adds an exception event with a
message and, in some configurations, a stack trace. Part
[5.1](../05-in-production/5.1-reading-a-trace.md)'s failing run records the exception on three spans
— the tool and both ancestors — so the trace of a bad request is larger than the trace of a good
one, exactly when traffic is highest.

**Retention is a multiplier nobody puts in the sum.** A gigabyte a year is a gigabyte *if you keep
one year*. Keeping thirty days is a twelfth of that; keeping everything for compliance is the whole
of it, indexed, replicated, and billed by a vendor per gigabyte ingested rather than per gigabyte
stored — and ingestion is charged once whether you look at it or not.

**The floor is charged on empty spans.** The root `invocation` span has two bytes of attributes
(`{}`) and still costs its sixty-four characters of identifiers plus its name. Six per cent of this
trace's bytes are structural, which is fine here and is the reason a plugin that adds fifty
near-empty spans costs more than its content suggests.

There is no error text for any of this. The failure is an invoice.

## In production

**What a professional does.** Puts a number on it before turning it on, and picks retention
deliberately: short retention for everything, long retention for a sampled subset, and the sampling
decision made at the root so a kept trace is whole — which is the paper's contribution and the
subject of [papers/01](../../papers/01-the-trace-tree-at-scale.md).

**What degrades at scale.** Cardinality, not volume. A gigabyte of spans is cheap; a gigabyte of
spans with a unique `gen_ai.conversation.id` on every one is an index the size of the data, and that
is what backends charge for. Part
[2.2](../02-what-adk-records/2.2-the-attributes-are-a-contract.md) named this from the conventions
side; here it is the cost side of the same fact.

**The failure that only shows with real traffic.** The bill is not linear in requests, because trace
size varies with what happened. A conversation with twenty turns produces a trace many times the
size of one with three, so the mean is not the median, and a capacity plan built on the mean is
wrong in the direction of the busy days.

**The review comment a senior engineer leaves:** *"One gigabyte a year is fine, ship it. Nineteen is
not, so the plugin goes behind a flag — and put the retention period in the same config so the
person turning it on can see both numbers at once."*

**The interview question:** *"What does tracing cost?"* The answer that shows experience changes the
currency: it costs no requests to the model provider, it costs storage and ingestion at the
observability vendor, and the number that moves it most is not traffic but what you chose to write
on each span.
