# 4.2 — The prompt inside the span

## One-line answer

By default ADK writes the whole model request and response into span attributes, so the customer's
own sentence appears six times in one trace — in a stream that is copied to a dashboard, a
collector and a vendor, none of which is behind the approval gate the session store sits behind.

## The story

💥 **The delivery sheet in the group chat.**

🎬 **The scene.** A courier's daily sheet: thirty rows, each with a name, a flat number, a phone
number and what is being delivered. It is a working document, it lives on a clipboard in the van,
and it is exactly what the job needs.

😬 **The naive fix.** One address is unclear. The rider photographs the sheet and posts it to the
team's group chat — *"anyone know where this one is?"* — and somebody answers in a minute. Problem
solved, efficiently, by a person doing their job well.

💥 **Why it fails.** The group has forty people in it, including four who left last month and a
supplier who was added for one week in March. The photograph is now on forty phones, in a chat with
no retention policy, backed up to forty personal cloud accounts. Thirty customers' names, flats and
phone numbers, distributed to an audience nobody chose, permanently, to solve one address.

💡 **The insight.** The sheet was never the problem — it was fine on the clipboard, where the
audience was one person doing the deliveries. **What changed was the copy.** The same data in a
different place has a different set of readers, and nobody re-asked the question *who is allowed to
see this* when it moved.

## The idea in plain language

Day 47 put sessions in a database. Day 63 put an approval gate in front of the actions that matter.
Day 69 spent a whole day on personally identifiable information and where it is allowed to go. All
of that reasoning was about the **session store**: a place with a schema, an owner, a retention
policy and a threat model.

A trace is a copy of some of the same data in a completely different place.

ADK writes two attributes on every `call_llm` span: `gcp.vertex.agent.llm_request` and
`gcp.vertex.agent.llm_response`. Those are not summaries. The request attribute contains the system
instruction, the tool declarations and **every message in the conversation so far**; the response
contains what came back.

There is a switch, and ADK's own source names it plainly:

```text
# By default some ADK spans include attributes with potential PII data.
# This env, when set to false, allows to disable populating those attributes.
ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS = "ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS"
```

That comment is in `google/adk/telemetry/tracing.py`, and it is a good comment: it says exactly what
the default does, and it says the default is on.

The default is right for a framework. A trace without the prompt is much harder to debug, and most
people turning tracing on for the first time are debugging. It is a decision, though, and it is one
this repository has to make deliberately rather than inherit — because Phase 14 makes this
repository public, and because a trace goes somewhere a session never does.

## Why Sutra needs it

Because Principle 13 is *blast radius before capability*, and this is the first day that adds a
capability whose blast radius is a copy of the conversation. Turning tracing on is the capability;
this part is the containment story that has to arrive with it.

And because Principle 9 — secrets never touch git — has a sibling here that nobody has stated yet: a
trace pipeline is a place data goes, and the same care that goes into `.env` and `.gitignore` applies
to a stream that carries what customers typed.

## The mechanism

The lab looks for the customer's own sentence, and the operator's, in every attribute of every span:

```python
SECRET_PHRASES = {
    "the user's question": QUESTION,
    "the system instruction": "Look the ticket up, check the limit, then answer in one sentence.",
}
```

**Line by line:**

- Two phrases, chosen because each has exactly one legitimate home: the question belongs in the
  session, the instruction belongs in the agent's configuration. Finding either in a span means a
  copy exists somewhere new.
- The instruction is written out rather than imported from `_desk`, so the check would still fail if
  somebody changed the agent and forgot the trace — the test does not move when the code does.

The search is a substring scan across everything:

```python
    for span in spans:
        for key, value in span.attributes.items():
            for label, phrase in SECRET_PHRASES.items():
                if phrase in str(value):
                    found.append((span.name, key, label))
```

**Line by line:**

- Three nested loops over ten spans, which is fine and is the honest way to ask "is it anywhere".
  A targeted check on the two known attributes would pass the day ADK adds a third.
- `str(value)` because an attribute value may be a sequence, and a phrase can be inside one element.
- It records *where* — span name and attribute key — because "there is PII in the trace" is not
  actionable and "it is in `gcp.vertex.agent.llm_request` on `call_llm`" is.

The switch has to be set before the import:

```python
if "--off" in sys.argv:
    os.environ["ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS"] = "false"

from _desk import QUESTION, run_desk  # noqa: E402
```

**Line by line:**

- ADK reads the environment when `google.adk.telemetry` is imported, so setting it after the import
  does nothing. This is the reason for the `# noqa: E402` — the import genuinely must come second,
  and the comment says why rather than silencing a warning for convenience.
- `os.environ`, not a constant in ADK. The switch is an environment variable because it has to be
  settable by whoever deploys the thing, not by whoever wrote it — which on Day 86 is a line in a
  container's configuration.

Run the default:

```bash
cd days/day-84-the-trace-tree/lab
uv run python leak.py; echo "exit: $?"
```

**Line by line:**

- No flag: ADK as it comes out of the box, which is the state any project is in until somebody
  decides otherwise.

Measured on 2026-09-07:

```text
ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS = (unset - the default)
10 spans

  span                              attribute                             what is in it
  call_llm                          gcp.vertex.agent.llm_request          the user's question
  call_llm                          gcp.vertex.agent.llm_request          the system instruction
  call_llm                          gcp.vertex.agent.llm_request          the user's question
  call_llm                          gcp.vertex.agent.llm_request          the system instruction
  call_llm                          gcp.vertex.agent.llm_request          the user's question
  call_llm                          gcp.vertex.agent.llm_request          the system instruction

  attributes carrying content the customer typed: 6

  a session store is behind an approval gate; a trace is on a dashboard
  the same sentence is now in both, and only one of them was designed for it
```

**Six copies in one trace.** Three `call_llm` spans, and each carries the entire conversation up to
that point — so the question the customer typed is duplicated once per model turn, and a
twenty-turn conversation carries it twenty times.

Now with the switch:

```bash
uv run python leak.py --off; echo "exit: $?"
```

**Line by line:**

- `--off` sets the environment variable before the ADK import and changes nothing else. The desk, the
  tools, the tree and the durations are identical to the run above.

Measured on 2026-09-07:

```text
ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS = false
10 spans

  span                              attribute                             what is in it
  (nothing)

  attribute payload across the trace: 1313 characters
  attributes carrying content the customer typed: 0
```

**Six to zero, and 4,682 characters to 1,313.** The same ten spans, the same tree, the same
durations, the same error handling — and seventy-two per cent less payload, because most of a trace's
bytes were the conversation.

## When it breaks

There is no error text and there never will be. Everything in the default run is working correctly:
ADK documented the behaviour in a comment, provided a switch, and chose the default that helps most
people most of the time.

The composite is what makes it a finding, and every step is somebody being reasonable:

```text
1. tracing is turned on to debug a problem, with defaults
2. the traces are useful, so tracing stays on
3. an exporter is pointed at a hosted backend, because a local file is not enough
4. the backend is a vendor with its own retention, its own access list, its own region
5. the conversation is now in a system nobody reviewed for this purpose
6. a customer asks for their data to be deleted, and the session store honours it
7. the trace backend does not, because nobody knew it had a copy
```

Step 7 is the one that costs. Day 69's data-boundary work covers the session store and knows nothing
about a stream that was added five phases later.

The quieter break is **quadratic**. The request attribute holds the whole conversation, and there is
one per turn, so a conversation of *n* turns writes *n(n+1)/2* messages into the trace. This desk had
three turns and wrote the question three times. At twenty turns it is two hundred and ten messages
for a conversation that contains twenty — which is a cost story and a privacy story at once.

And the third, which is the one to remember: **the switch does not reach
`AutoTracingPlugin`.** Set the variable to `false`, fit the plugin, and run the same desk.

Measured on 2026-09-07:

```text
content capture OFF, plugin ON: 60 spans
attributes still containing the user's question: 21
   Context.get_invocation_context  ->  adk.fn.return
   BaseAgent._create_invocation_context  ->  adk.fn.arg.parent_context
   BaseAgent._create_invocation_context  ->  adk.fn.return
   BaseAgent._handle_before_agent_callback  ->  adk.fn.arg.ctx
   LlmAgent._handle_before_agent_callback  ->  adk.fn.arg.ctx
   BaseAgent._load_agent_state  ->  adk.fn.arg.ctx
```

**Twenty-one attributes, in a run where content capture was off.** The plugin writes a `repr` of
every argument and return value under `adk.fn.arg.*` and `adk.fn.return`, and an ADK invocation
context contains the conversation — so the question the customer typed is in twenty-one places that
ADK's own privacy switch has no opinion about.

Note the prefix. `adk.fn.*` is a third attribute family, in neither of the two part
[2.2](../02-what-adk-records/2.2-the-attributes-are-a-contract.md) counted, which is what the
`other` bucket in that check was for. A redaction rule written against the two known families would
not match a single one of these.

## In production

**What a professional does.** Treats the trace pipeline as a data store in the data inventory, with
the same questions asked of it as of the database: what is in it, who can read it, how long is it
kept, and what happens on a deletion request. The engineering half is one environment variable; the
work is the review that decides which way to set it, per environment.

**What degrades at scale.** Copies multiply. One backend becomes a backend plus a collector plus a
sampled long-term archive plus somebody's local export for a debugging session, and each is a place
the data now lives. The variable that controls all of them is set once, at the source, which is the
argument for setting it there rather than filtering downstream.

**The failure that only shows with real traffic.** Redaction that works on the fields you thought of.
The switch is thorough about ADK's own attributes — with it off, `llm_request`, `llm_response`,
`tool_call_args` and `tool_response` all become `{}` — and it does nothing at all about the plugin's
`adk.fn.*` family, or about anything a future library adds. A redaction policy that names fields is
correct until the next release; the durable version is an allow-list of attributes permitted to
leave the process.

**The review comment a senior engineer leaves:** *"Set the variable to false in every environment
that sees real traffic, and true in development. And the auto-tracing plugin does not honour it at
all, so that stays off in production regardless of what the flag says."*

**The interview question:** *"What is the risk of tracing an LLM application?"* The answer that shows
experience does not say "performance". It says the trace carries the prompt by default, that a prompt
contains whatever the user typed, and that the trace pipeline is usually outside whatever review the
primary data store went through.
