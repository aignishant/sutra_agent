# 5.1 — Reading a trace when something failed

## One-line answer

A failing tool produces a hundred-and-forty-line framework traceback and a five-span trace, and the trace
answers the three questions a person actually has — which step, under which parent, with which
arguments — while marking every ancestor `ERROR` so the deepest error span is the cause.

## The story

The fuse box in the dark.

Everything goes off at once. There are two ways to find out why. One is to walk the house checking
sockets, which tells you the state of every socket and not which one caused it. The other is to open
the box by the door, where the switches are grouped by circuit, and look for the one that is down.

The box does not know more than the house does. It knows the same thing arranged by **what belongs
to what** — kitchen, upstairs, sockets, lights — so one glance narrows an entire house to one
circuit, and then you go and look at what is plugged into that circuit.

Nobody would build a fuse box to diagnose a fault. It is built to isolate faults, and the diagnosis
is a side effect of the arrangement.

## The idea in plain language

When a tool raises, three things happen at once.

**Python produces a traceback.** It is complete and correct and, in a framework, it is mostly the
framework: the runner, the node runner, the base node, the agent, the flow, the postprocessor, the
function handler, the tool wrapper, and then finally your function. It answers *where in the code*.

**ADK records the exception on the span.** `trace_tool_call` calls `span.record_exception(error)`
and sets `error.type`, so the tool's span carries the type, the message and a recorded event.

**The status propagates up.** The tool span is `ERROR`, and so is every ancestor, because a child
failing means the parent did not succeed either.

That third one is what makes the trace readable, and it has a rule attached: **the deepest error
span is the cause.** Ancestors are marked because the failure passed through them. The leaf is where
it started.

So the trace answers a different question from the traceback, and it is the question people have
first:

| Question | Traceback | Trace |
| --- | --- | --- |
| where in the code? | yes, exactly | no |
| which step of the work? | buried in it | the span name |
| under which parent? | no | the parent link |
| with which arguments? | no | `tool_call_args` |
| which request was this? | no | the trace id |
| did it happen to others? | no | query the backend |

The last two are the ones a traceback structurally cannot answer, because a traceback is about one
process at one moment and a trace has an identity that outlives it.

## Why Sutra needs it

Because Day 21 established that errors surface rather than being swallowed, and Day 44 hardened the
client against failures that arrive over a network. Both produced good error handling and neither
produced a way to answer *which customer, which ticket, which step* after the fact.

And because Phase 13 is about to make that harder in every direction. Day 85 puts an HTTP boundary
in front of the desk, Day 86 puts it in a container, Day 88 puts a tool in a second container — and
a traceback stops at a process boundary while a trace does not.

## The mechanism

The lab makes the ticket lookup fail the way a real backend does:

```python
TICKET_LOOKUP_FAILS = False


def ticket(ticket_id: str) -> dict:
    """Look up one ticket by its id."""
    if TICKET_LOOKUP_FAILS:
        raise TimeoutError(f"ticket store did not answer for {ticket_id}")
    return {"id": ticket_id, "kind": "billing", "amount": 2400}
```

**Line by line:**

- A module-level flag flipped by the script, rather than a separate broken tool, so the failing run
  and the working run are the same code path with one branch different.
- `TimeoutError` rather than a custom exception, because `error.type` records the class name and the
  point is to see a familiar one appear on a span.
- The message contains the ticket id, which is the thing a person would want and is *also* the thing
  part [4.2](../04-what-a-trace-costs/4.2-the-prompt-inside-the-span.md) is about: exception messages
  are another place customer data leaks into a trace.

Finding the cause is a depth lookup, not a guess:

```python
        cause = max(failed, key=lambda s: depth_of[s.context.span_id])
```

**Line by line:**

- `depth_of` comes from the same `tree()` walk part
  [1.1](../01-what-a-trace-is/1.1-a-trace-is-a-tree.md) used, so depth is the real tree depth rather
  than an inference from names.
- `max` over the failing spans: the deepest one. This is the rule stated as code, and it is the whole
  trick — three spans are `ERROR` and exactly one of them is where it started.
- It would be tempting to use the earliest `start_time` instead. That is wrong: the root starts
  first and is not the cause.

And the framework's own traceback is silenced deliberately:

```python
    if "--traceback" not in argv:
        logging.getLogger("google_adk").setLevel(logging.CRITICAL)
```

**Line by line:**

- ADK logs the failure at `ERROR` with a full traceback, twice — once for the node and once for the
  root task. That is correct behaviour and it is what this part is comparing against.
- Raising the level rather than removing the handler, so the comparison is a flag away and nothing is
  permanently hidden.
- `--traceback` lets it through, which is how you see what the trace is being compared to.

Run it:

```bash
cd days/day-84-the-trace-tree/lab
uv run python answer.py; echo "exit: $?"
```

**Line by line:**

- No flag: the trace, with the framework's traceback quieted.

Measured on 2026-09-07:

```text
the runner raised: TimeoutError: ticket store did not answer for 4688

  span                                  status  error.type
  invocation                            ERROR   
    invoke_agent desk                   ERROR   
      call_llm                          UNSET   
        generate_content scripted-desk- UNSET   
          execute_tool ticket           ERROR   TimeoutError

  spans in the trace:   5
  spans marked ERROR:   3
  ancestors that inherited it: 2

  the deepest error span is the cause: execute_tool ticket
  its parent:         generate_content scripted-desk-1
  error type:         TimeoutError
  arguments:          {"ticket_id": "4688"}
  trace id:           090cc88342fdf8788b3cbd2ba6d2e0b5
  recorded event:     exception: ticket store did not answer for 4688
```

**Five spans instead of ten**, because the invocation stopped where it failed — which is itself
information: the desk never got to the second tool.

Read the status column. `invocation` and `invoke_agent desk` are `ERROR` with no `error.type`;
`execute_tool ticket` is `ERROR` **with** one. The two middle spans are `UNSET`, which is worth
noticing — `call_llm` and `generate_content` completed as far as they were concerned, and the
failure was recorded on the tool.

And the last four lines are the answer to a support ticket: the ticket store timed out looking up
4688, inside the first model turn, in trace `090cc883…`. No source file was opened to say that.

## When it breaks

The alternative is the run with the framework's own output let through:

```bash
uv run python answer.py --traceback 2>&1 | wc -l
```

**Line by line:**

- `2>&1` because the traceback goes to standard error, and `wc -l` because the count is the point.

Measured on 2026-09-07: **142 lines**, against the fifteen-line trace above. The traceback is
printed twice, across two chained exceptions — `DynamicNodeFailError` from
`google.adk.workflow._errors`, then the original `TimeoutError` — and it walks the runner, the node
runner, the base node, the agent, the flow, the postprocessor, the function handler and the tool
wrapper before it reaches `_desk.py`. Every one of those lines is true. Two of them are about the
desk.

There is a second failure, and it is the one that catches people reading traces for the first time:
**three spans say `ERROR` and only one is the cause.** A dashboard that counts error spans counts
this incident three times, and an alert that fires on "any span with status ERROR" fires three
alerts for one broken ticket store. The fix is to count *root causes* — the deepest error span per
trace — and it is arithmetic nobody does by default.

The third is the one this lab cannot show: a failure with **no** exception. A tool that returns
`{"error": "not found"}` instead of raising produces a span with status `UNSET` and no `error.type`,
and the trace looks completely healthy. ADK has a hook for it — `trace_tool_call` takes an
`error_type` argument for exactly this case, documented as *"used when the tool returned an error as
a dict rather than raising an exception"* — and nothing sets it unless the tool's author does.

## In production

**What a professional does.** Puts the trace id in front of the user. An error page or an API error
body that carries the trace id turns "it broke this morning" into a primary key, and it costs one
field. Everything downstream — support, on-call, the post-mortem — is faster because the first step
stopped being a search.

**What degrades at scale.** Alert volume, for the reason above: one failure marks a chain of spans,
and naive counting multiplies incidents by tree depth. The other half is sampling — part
[papers/01](../../papers/01-the-trace-tree-at-scale.md) measures a sampler keeping two of four
failing traces, which is fine for statistics and useless for the person holding the one ticket that
failed.

**The failure that only shows with real traffic.** The interesting trace was not kept. Head sampling
decides at the root, before anything has gone wrong, so it cannot prefer failures — and the traces
you most want are the rare ones. The answer the field settled on is **tail sampling**: buffer the
whole trace, decide after it finishes, keep everything that errored. It costs a collector that holds
traces in memory, which is why it is not in this lab.

**The review comment a senior engineer leaves:** *"Count the deepest error span per trace, not every
error span, or this alert will page us three times for one timeout. And put the trace id in the API
error response."*

**The interview question:** *"You have a traceback. Why do you also want a trace?"* The answer that
shows experience names what a traceback structurally cannot carry: an identity that survives the
process, the arguments the step was called with, and the ability to ask whether the same thing
happened to anybody else.

## Check yourself

```bash
cd days/day-84-the-trace-tree/lab
uv run python answer.py; echo "exit: $?"
uv run python answer.py --traceback 2>&1 | tail -20
```

Two views of one failure. From the second, find the line that names `_desk.py`, and count how many
lines you had to read to get to it.

Now make the tool return an error instead of raising: change the `raise TimeoutError(...)` to
`return {"error": "ticket store did not answer"}` and run it again. Predict what the status column
shows before you look, then put it back.

**Out loud, without scrolling up:** three spans are marked `ERROR` — which one is the cause, how do
you know, and what does an alert that counts all three get wrong?
