# 5.2 — What a real tracing setup adds

## One-line answer

The lab produces real ADK spans, reconstructs the tree, exports it to a file that survives the
process and finds the cause of a failure — and the distance between that and something a team can
rely on is nine things, of which the first three take under two hours and make the other six
possible.

## The story

The notes pinned above the till for whoever opens tomorrow.

Not a manual. Six lines on a card, in biro, added to one at a time by different people over two
years: *the shutter sticks, lift as you pull.* *Float is in the second drawer, count it before you
open.* *If the card machine says NO LINE, unplug it for a minute.* *Milk delivery Tuesdays, sign the
sheet.*

Every line is there because somebody once stood in front of that till not knowing, and wrote it down
so the next person would not have to. It is short because everything obvious was left out, and it is
useful because everything that was not obvious is on it.

The manual, in the office, is forty pages and nobody has opened it.

## The idea in plain language

The lab does four things properly, and it is worth being precise about which, because the gap is
where the work is.

It produces **real spans** — ADK's own instrumentation, driven by a real runner, with a scripted
model in place of a provider. It **reconstructs the tree** from the three identifiers, in any
arrival order. It **exports to a sink that outlives the process**, using ADK's own SQLite exporter.
And it **finds the cause of a failure** by depth rather than by guessing.

Here is what is not there.

**1. Install the provider once, at the entry point, and say so out loud.**
Part [1.3](../01-what-a-trace-is/1.3-the-run-that-left-no-trace.md) measured a run producing five
events, zero spans and zero warnings. One function called from one place, and a startup log line
naming the exporter and the sampler. This is first because every other item assumes tracing is
actually on.

**2. Flush on exit.**
Part [3.3](../03-where-spans-go/3.3-the-queue-that-went-with-the-process.md) measured zero of ten
spans delivered from a process that ended without `shutdown()`. `atexit` for a script, a lifespan
hook for the API of Day 85, a signal handler for the container of Day 86.

**3. Decide about message content, per environment.**
Part [4.2](../04-what-a-trace-costs/4.2-the-prompt-inside-the-span.md) measured the customer's
sentence in six attributes by default, and twenty-one more when the automatic plugin is fitted with
the switch already off. One environment variable, one decision, and it is a decision rather than an
inheritance.

**4. Put the trace id on every log line.**
Day 22 built structured logging and it does not know about spans. A log filter that reads the
current span context and adds `trace_id` turns two systems into one, and it is about ten lines.

**5. Put context on the root span.**
Part [2.2](../02-what-adk-records/2.2-the-attributes-are-a-contract.md) measured `invocation`
carrying **zero attributes**. The app name, the session id and the user id belong on the span
somebody searches for, not on its child.

**6. Configure a sampler explicitly.**
The default keeps everything. Part [papers/01](../../papers/01-the-trace-tree-at-scale.md) measures
head sampling at one in ten storing eleven per cent of the spans with every kept trace whole. Set it
to `1.0` in development and to a real ratio in production, and write the ratio in the startup line
from item 1.

**7. Compute self time.**
Part [2.1](../02-what-adk-records/2.1-agent-tool-and-model.md) measured a model span and a tool span
with the *same* duration, because the tool ran inside the model turn. A duration column that does
not subtract children answers "the model is slow" when the truth is "our ticket store is slow".

**8. 🅿️ Parked — tail sampling.**
Part [5.1](5.1-reading-a-trace.md)'s **In production** section, and the paper's own limitation: head
sampling cannot prefer failures, and the paper's demo kept two of four failing traces. Tail sampling
buffers a whole trace and decides after it finishes. It needs a collector holding traces in memory,
which is a process this repository does not run.

**9. 🅿️ Parked — an OTLP exporter and somewhere to send it.**
`opentelemetry-exporter-otlp` is not installed and there is no collector. Adding it is
`uv add opentelemetry-exporter-otlp` plus a dated row in `docs/PACKAGES.md`; the part that is not
parked-able is the endpoint, which belongs to Day 86's deployment question.

## Why Sutra needs it

Because Day 85 is tomorrow and it is where items 1, 2 and 4 stop being tidy and start being
load-bearing: an HTTP server has a lifespan, a request boundary and access logs, and all three are
places this list has an entry.

And because items 1 and 2 have the property that makes them urgent rather than important: they are
the difference between a tracing setup that works and one that produces nothing, and both failures
are silent. Everything else on the list makes a working setup better. The first two decide whether
there is one.

## The mechanism

The list, with what each costs, so it can be argued with rather than admired:

| # | Item | Where it lands | Roughly |
| --- | --- | --- | --- |
| 1 | provider installed once, logged | the entry point | half an hour |
| 2 | flush on exit | the same function | ten lines |
| 3 | content capture decided per environment | config | one decision |
| 4 | trace id on every log line | the logging setup | half an hour |
| 5 | context on the root span | a span processor or a wrapper | an hour |
| 6 | sampler configured explicitly | the same function as item 1 | ten lines |
| 7 | self time in any duration view | wherever durations are read | an hour |
| 8 | 🅿️ tail sampling | not built | needs a collector |
| 9 | 🅿️ OTLP exporter and an endpoint | not built | needs Day 86's answer |

**Items 1, 2 and 6 are the same function** and together are under an hour. Item 4 is the one that
pays back fastest afterwards, because it makes every log line already in the system joinable.

Item 5 is the only one with a shape worth writing out, because it is not obvious where it goes:

```python
class RootContext(SpanProcessor):
    """Copy the request's identity onto the root span, which ADK leaves empty."""

    def on_start(self, span, parent_context=None):
        if span.parent is None:
            span.set_attribute("app.name", APP)
            span.set_attribute("session.id", current_session_id())
```

**Line by line:**

- A `SpanProcessor`, not a wrapper around the runner, because the root span is created by ADK and
  there is no application code inside it to hook.
- `on_start`, not `on_end`: attributes have to be set while the span is still writable, and by
  `on_end` it is a `ReadableSpan`.
- `span.parent is None` is the root test from part
  [1.2](../01-what-a-trace-is/1.2-three-numbers-make-the-tree.md), reused.
- `current_session_id()` has to come from somewhere — a context variable set at the request
  boundary — which is why this item is an hour rather than ten lines, and why it lands more naturally
  on Day 85 where the boundary exists.

## When it breaks

The list breaks by being read as improvements, and the composite has been measured piece by piece
across this day:

```text
1. tracing is added and works on a laptop                        (part 1.3)
2. the API server has its own entry point, which does not install it
3. the nightly job exits before the batch processor's timer       (part 3.3)
4. the traces that do arrive carry the whole conversation         (part 4.2)
5. nobody sets a sampler, so storage grows with traffic           (part 4.1)
6. six months later somebody asks for a trace from March
7. it was never kept, or it was kept and cannot be searched
```

Seven steps, no error at any of them. Step 7 has two endings and the list splits them: items 1 and 2
decide whether anything was kept, item 6 decides whether keeping it was affordable, and item 5
decides whether it can be found.

## In production

**What a professional does instead of building all nine.** Items 1, 2 and 6 today, because they are
one function and the first two are the difference between working and silently not working. Then
item 4, because it multiplies the value of logging that already exists. Items 5 and 7 when somebody
first tries to read a trace in anger and cannot.

**What degrades at scale.** Every item gets more valuable except item 3, which gets *harder*: as
more services emit spans, "content capture off" has to be true in every one of them, and one service
that missed the memo puts the conversation back into the pipeline. That is a policy problem rather
than a code problem, which is why it is a decision in the table rather than a line count.

**The failure that only shows with real traffic.** The trace that was sampled away. Everything on
this list can be right and the one trace somebody needs can be absent, because a head sampler made
its decision before anything went wrong. Item 8 is the answer and it is parked, which means for now
the honest thing is to say so: at a ten per cent sample, nine in ten support requests cannot be
answered from a trace.

**The review comment a senior engineer leaves:** *"Items one, two and six are the same function and
under an hour. Do them before Day 85, because an API server with no flush on shutdown is the exact
shape that loses the traces from a bad deploy."*

**The interview question:** *"You have added OpenTelemetry to a service. What else does it need
before you would rely on it?"* The answer that shows experience starts with the two silent failures —
is the provider installed in this process, and does the queue get flushed on exit — because a setup
that fails either produces no error and looks exactly like a quiet system.
