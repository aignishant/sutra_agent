# 1.1 — A trace is a tree, not a log

## One-line answer

A log tells you what happened in the order it finished; a trace tells you what happened *inside*
what else — and for an agent, where one question becomes ten nested steps, the second question is
the only one anybody actually asks.

## The story

The flat-pack wardrobe, and the two pieces of paper in the box.

One of them is a list. Step one, step two, step three, forty-one steps, each a sentence. You can
follow it, and while you are following it you have no idea what you are building; if step
twenty-two goes wrong you cannot tell whether that was a door, a drawer or a back panel, because a
list has no shape.

The other is the exploded diagram: the whole wardrobe drawn hanging in the air with every piece
floating a little away from where it belongs, and thin lines showing what goes into what. Nobody
follows the diagram step by step. You look at it once at the start and again the moment something
does not fit, and both times it answers a question the list cannot: **which part is this a part
of?**

The list and the diagram describe the same wardrobe. Only one of them survives a mistake.

## The idea in plain language

Every day of this curriculum so far has produced logs. Day 22 built structured logging: one line
per event, each carrying a timestamp and some fields, written in the order things finished.

A log answers *what happened*. It is genuinely good at that, and for a program that does one thing
at a time it is enough.

An agent does not do one thing at a time. One user question becomes: the runner starts an
invocation, which invokes an agent, which calls a model, which asks for a tool, which runs, whose
result goes back to the model, which asks for another tool, and so on. Those are not forty-one
steps in a row. They are steps **inside** steps, and a log flattens that into a list in finishing
order — which, as the next section measures, is close to the reverse of the order they started in.

A **trace** keeps the nesting. Three words carry all of it:

- A **span** is one unit of work with a start and an end: one tool call, one model call, one agent
  invocation. It is the box on the diagram.
- A **trace** is every span produced by one request, taken together. It is the whole wardrobe.
- A **parent** is the span a span happened inside. It is the thin line.

That is the entire data model, and everything else in this day — attributes, exporters, sampling —
is machinery around those three words.

**Why an agent needs it more than an ordinary service does.** In a web service the nesting is
shallow and predictable: handler, query, response. In an agent the shape is decided at run time by
the model. How many tool calls happened, in what order, inside which model turn — that is not in
the code, so it cannot be read off the source. The trace is the only place the actual shape of a
particular run is written down.

## Why Sutra needs it

Because Phase 12 has just spent four days building instruments that measure whether the desk did
the right thing, and Day 83's gate found that the trajectory rubric was reading a transcript with
zero of three tool calls in it. A trace is the same information the rubric wanted, produced by the
system itself rather than reconstructed from a recorded file.

And because Phase 13 is about to put this desk behind an HTTP API (Day 85) and inside a container
(Day 86). Every one of those steps moves the running system further from the terminal it was
developed in. The trace is what you get instead of being able to watch it.

## The mechanism

ADK emits spans itself. Nothing in the lab draws a picture of what a trace *would* look like — the
desk in `_desk.py` is a real `LlmAgent` behind a real `InMemoryRunner`, with a scripted model in
place of a provider, so the spans below are ADK's own.

The tree is built by walking parent links:

```python
def tree(spans: list[ReadableSpan]) -> list[tuple[int, ReadableSpan]]:
    """Depth-first walk of the span forest, as (depth, span) pairs in parent-before-child order."""
    children: dict[int | None, list[ReadableSpan]] = {}
    for span in spans:
        children.setdefault(parent_id(span), []).append(span)
    for group in children.values():
        group.sort(key=lambda s: s.start_time)
```

**Line by line:**

- `children` is keyed by *parent* id, so one pass over a flat list produces the whole structure.
  A trace arrives as a bag of spans; nothing about the transport preserves the shape.
- `parent_id(span)` returns `None` for the root, so `children[None]` is the list of roots — and part
  of this script's job is to check there is exactly one of them.
- `sort(key=lambda s: s.start_time)` inside each group, because siblings arrive in whatever order
  they *finished*, and the useful order is the one they started in.
- `ReadableSpan` is OpenTelemetry's finished-span type. A span being read is not the same object as
  a span being written; the writing type has setters and the reading type does not, which is what
  stops an exporter from editing history.

Run it:

```bash
cd days/day-84-the-trace-tree/lab
uv run python tree.py; echo "exit: $?"
```

**Line by line:**

- No flag: the tree. `--flat` is the same spans as a list, and it is the comparison in **When it
  breaks**.

Measured on 2026-09-07 — the microsecond column will differ on your machine, and nothing else will:

```text
one invocation of the desk: 5 events, 10 spans

  invocation                                  88011 us
    invoke_agent desk                         71656 us
      call_llm                                 5556 us
        generate_content scripted-desk-1       4964 us
          execute_tool ticket                  4964 us
      call_llm                                    0 us
        generate_content scripted-desk-1          0 us
          execute_tool refund_limit               0 us
      call_llm                                 1006 us
        generate_content scripted-desk-1       1006 us

  trace ids in this run: 1
  spans with no parent:  1

  one trace, one root, every other span reachable from it
```

**One question, ten spans, five levels deep.** Read the shape rather than the numbers: the desk
called the model three times, and two of those three model turns had a tool call inside them. That
sentence is the trace. It is not in the source code — the source says "here are two tools, use them
if you need to" — and it is not in a log, which would have given ten lines in an order that starts
with the tool call.

Note the depth: `execute_tool ticket` is not a child of `invoke_agent desk`. It is a child of
`generate_content`, which is a child of `call_llm`, which is a child of the agent. The tool call
happened *inside the model turn that asked for it*, and the tree says so.

## When it breaks

Flatten it and the same ten spans stop answering the question:

```bash
uv run python tree.py --flat; echo "exit: $?"
```

**Line by line:**

- `--flat` prints the spans in the order the exporter received them, which is the order they
  finished. That is precisely what a log gives you.

Measured on 2026-09-07:

```text
  finished  span              parent            name
         1  ada55fa4d36857b4  604fa378567c9bb1  execute_tool ticket
         2  604fa378567c9bb1  5fdd884a3c8754c2  generate_content scripted-desk-1
         3  5fdd884a3c8754c2  03af3912cd120131  call_llm
         4  6fb37cfcbd7343e6  241c700e761004ba  execute_tool refund_limit
         5  241c700e761004ba  1cf522494740d56b  generate_content scripted-desk-1
         6  1cf522494740d56b  03af3912cd120131  call_llm
         7  65c1f326815fd17a  cf8fe773c9de4a53  generate_content scripted-desk-1
         8  cf8fe773c9de4a53  03af3912cd120131  call_llm
         9  03af3912cd120131  e525d60b6ef591e1  invoke_agent desk
        10  e525d60b6ef591e1  -                 invocation

  the order spans finish in is not the order they started in, and it is not
  the shape of the work: a parent always finishes after its children
```

**The innermost step is reported first.** A parent cannot finish before its children, so a
finishing-ordered list is depth-first *backwards*: the deepest, smallest, least important step is
line one, and the invocation that contains everything is the last line in the file.

That is not a defect in logging. It is what "in the order it finished" means, and it is why reading
production logs for an agent feels like reading a book from the index. There is no error text for
this failure, because nothing failed — the log is correct, complete, and shaped wrong for the
question.

The trap worth naming: a log line *can* carry a trace id and a span id, and then the two views are
the same data. Part [5.2](../05-in-production/5.2-what-to-pin-above-the-till.md) makes that a
`TODO(me)`, because a log without a trace id is a log you cannot join to anything.

## In production

**What a professional does.** Treats the trace as the primary artefact for a request and the log as
the place for things that are not attached to one — startup, configuration, scheduled work. When
both exist, the log lines carry the trace id, so "show me everything about this request" is one
query rather than a reconstruction.

**What degrades at scale.** Depth. Ten spans is a diagram you read at a glance; a multi-agent run
with delegation (Day 55) and a workflow graph (Day 53) produces hundreds, nested a dozen deep, and
at that point nobody reads the tree either — they read a *flame graph*, which is the same tree
drawn with width proportional to duration, and they read the one branch that is wide.

**The failure that only shows with real traffic.** Two roots. A trace with two parentless spans is
two traces that a viewer will draw as one, usually because context was lost crossing a boundary — a
thread, a queue, an HTTP hop. `tree.py` exits non-zero on exactly that, and Day 85 is where the
boundary appears, because that is where a request starts arriving over the network.

**The review comment a senior engineer leaves:** *"Do not add a log line for every step now that we
have spans. Add the trace id to the log lines we already have, and delete the ones that only exist
because we could not see the shape."*

**The interview question:** *"You have logs. Why do you need tracing?"* The answer that shows
experience is not "logs are unstructured" — structured logs are a solved problem. It is that a log
is ordered by completion and has no parent, so for nested work it answers *what happened* and
cannot answer *inside what*, and for an agent the nesting is decided at run time.
