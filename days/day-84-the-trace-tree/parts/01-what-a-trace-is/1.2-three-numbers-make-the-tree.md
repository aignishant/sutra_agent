# 1.2 — Three numbers make the tree

## One-line answer

A span carries a trace id, its own span id and its parent's span id, and those three numbers are
enough to rebuild the whole shape from a shuffled pile — which is what makes a trace survive being
split across processes, queues and machines that never speak to each other.

## The story

The family chart, rebuilt from a shoebox of cards.

An uncle had been writing them for years: one index card per person, and on the back, in the same
handwriting every time, *son of* and a name. When he died the cards were in a shoebox in no order
at all — a grandmother next to a second cousin, four generations shuffled together.

It took an afternoon and no knowledge of the family. Find the cards with nothing written after *son
of*: those are the roots. Then find every card whose *son of* names a root, and put them
underneath. Then repeat. The chart that came out was the chart the uncle would have drawn, and
nobody in the room could have drawn it from memory.

The cards were never in order. They did not need to be. **Each one said where it belonged, so the
order they were picked up in did not matter.**

## The idea in plain language

A span carries exactly three identifiers, and each does one job.

| Identifier | Width | What it answers |
| --- | --- | --- |
| **trace id** | 16 bytes, shown as 32 hex characters | which request is this part of? |
| **span id** | 8 bytes, 16 hex characters | which step is this? |
| **parent span id** | 8 bytes, or absent | which step was this inside? |

The trace id is the same on every span in one request. The span id is unique to the span. The
parent span id is another span's span id, or nothing at all — and a span with no parent is a
**root**.

Two properties fall out of that, and they are the reason tracing works at all across a real system.

**Order does not matter.** Spans can arrive at a collector in any order, from any number of
machines, minutes apart, and the tree is still reconstructible — the same afternoon with the
shoebox. Nothing has to be buffered until a request is "complete", because completeness is
recoverable rather than required.

**The ids are the only thing that has to cross a boundary.** When one process calls another, the
tree survives if the trace id and the caller's span id travel with the call. That is the whole of
what "context propagation" means: forty-eight bytes in a header. Day 85 is where the boundary
appears, and this is the sentence to remember when it does.

The ids are integers in the SDK and hex strings everywhere a person looks at them. That is worth
knowing before you go looking for `span.trace_id` in a debugger and find a number with thirty-eight
digits.

## Why Sutra needs it

Because this desk is about to stop being one process. Day 85 puts it behind HTTP, Day 86 puts it in
a container, Day 88 puts a tool server beside it in a second container. Each of those is a place
where a request crosses from one process to another, and each is a place where a trace becomes two

And because Day 82 built regression comparison over recorded runs, and Day 22 built structured

the trace, addressable by one string.

## The mechanism

The lab shuffles the spans on purpose and rebuilds the tree from the ids alone:

```python
    exporter = collect()
    asyncio.run(run_desk())
    spans = list(exporter.get_finished_spans())
    if "--shuffle" in argv:
        random.Random(4688).shuffle(spans)
```

**Line by line:**

- `random.Random(4688)` — a seeded generator rather than the global one, so the shuffle is the same
  on every run and the transcript below is reproducible. An unseeded shuffle would make this
  measurement a different measurement every time it was checked.
- The shuffle happens *after* export and before reconstruction, which is exactly where reordering
  happens in a real system: in the network, in a queue, in a collector.

Printing them is straight formatting, and the hex conversion is the only thing worth naming:

```python
def hex_id(value: int | None, width: int) -> str:
    """OTel ids are integers; every backend shows them as fixed-width hex."""
    return "-" if value is None else format(value, f"0{width}x")
```

**Line by line:**

- `format(value, "032x")` for a trace id and `"016x"` for a span id — zero-padded, so ids sort and
  align. Without the padding a trace id that happens to start with a zero byte prints shorter than
  the others and stops looking like an id.
- `None` becomes `-`, which is how a root shows up. This is the one place the absence of a parent is
  rendered, and rendering it as an empty string would make a root look like a formatting bug.

Run it:

```bash
cd days/day-84-the-trace-tree/lab

```

**Line by line:**

- `--shuffle` is the interesting arm: it proves the reconstruction does not depend on arrival order.
  Without the flag the spans arrive as emitted, which proves nothing.

Measured on 2026-09-07 — the last five rows of the shuffled list, and then the rebuild:

**The root arrived second and the deepest leaf arrived last, and the tree came out identical to
part [1.1](1.1-a-trace-is-a-tree.md)'s.** Every row shares the trace id `5e35a782…`, every span id
is distinct, and each parent column names a span id from the same list.

Note what is *not* needed: no timestamps were used to place anything, no ordering was assumed, and
no span had to know anything about its children. A parent does not have a list of its children —
children point up, never down. That is what lets a child be emitted long after its parent, from a
different machine, and still land in the right place.

## When it breaks

Two ways, and both produce a tree rather than an error.

**A parent that is not in the set.** If a span's parent id names a span that was never exported —
dropped, sampled away, still in flight — that span is a second root, and a viewer will draw it as a
separate trace sitting next to the real one. `ids.py` catches it by counting:

```python
    rebuilt = [span.name for _depth, span in tree(spans)]
    ...
    if len(rebuilt) != len(spans):
        print(f"\n  {len(spans) - len(rebuilt)} span(s) point at a parent that is not here")
        return 1
```

**Line by line:**

- The walk starts from `children[None]` and only reaches spans whose ancestors are all present, so
  anything unreachable is missing from `rebuilt` — a count comparison is the whole detection.
- It reports the *number* of unreachable spans rather than raising, because in production this is
  normal and expected: a trace read while the request is still running is legitimately incomplete.

**A duplicated span id.** Then two different pieces of work claim the same address, and the children
of one become children of the other. Nothing raises; the tree is simply wrong, and the wrongness
looks like a step that ran twice. The check is one line:

```python
    ids = {span.context.span_id for span in spans}
    if len(ids) != len(spans):
```

**Line by line:**

- A set against a list, which is the cheapest possible duplicate detection and the only one needed
  since ids are opaque.

Neither failure has error text to quote. That is the recurring shape of this whole subject: a
broken trace is a *plausible* trace, and the thing that catches it is a check somebody wrote for
the purpose.

## In production

**What a professional does.** Treats the ids as the join key across every observability surface —
the log line, the metric exemplar, the error report, the support ticket. When a customer says
"my request failed at half past three", the useful reply is "give me the trace id", and the useful
system is one where they have been given it.

**What degrades at scale.** Collisions become thinkable. A span id is 8 bytes; at the volumes where
that starts to matter you have other problems, but trace ids get truncated by well-meaning
middleware, and a truncated id collides. The rule is that the ids are opaque and fixed-width, and
anything that reformats them is a bug.

**The failure that only shows with real traffic.** A boundary nobody remembered. Context propagates
through function calls automatically, because it lives in a context variable — but it does not
cross a `queue.put`, a thread pool, a subprocess, or an HTTP call that was written before tracing
existed. Every one of those silently starts a new root, and the symptom is not an error: it is a
dashboard where the average trace has three spans in it because ninety per cent of the tree became
separate traces.

**The review comment a senior engineer leaves:** *"Every place we hand work to another process,
show me where the trace id goes. If the answer is 'the library does it', show me the header on a
real request."*

**The interview question:** *"How does a trace survive being split across services?"* The answer
that shows experience is the propagation half, not the data model: the ids travel in the request,
the receiving side makes its root a child of the caller's span, and everything else — the tree, the
ordering, the reassembly — falls out of that.
