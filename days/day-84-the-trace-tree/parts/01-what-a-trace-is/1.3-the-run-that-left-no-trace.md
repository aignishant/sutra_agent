# 1.3 — The run that left no trace

## One-line answer

Tracing is off unless somebody turns it on, and "off" in OpenTelemetry does not mean broken or
loud — it means every span is a `NonRecordingSpan`, every instrumentation call returns early, and a
run that produced five events and a correct answer leaves zero spans and zero warnings.

## The story

💥 **The answering machine nobody switched on.**

🎬 **The scene.** A small business, one phone line, and a machine on the shelf beside it for the
hours nobody is in. It was bought for exactly that. It sits there with a light on the front.

😬 **The naive fix.** Business is quiet, and somebody wonders whether anyone is even calling after
hours. Check the machine: no messages. Clearly nobody calls in the evening, so there is no point
staffing it.

💥 **Why it fails.** The record button was never pressed. The machine has power, the light is on,
the line works, and the answer side of it was never armed — so every evening for two years the
phone rang, rang out, and left nothing behind. "No messages" and "no calls" produce an identical
empty tape, and the business has been making a staffing decision on the difference between them.

💡 **The insight.** A recording device that is not recording looks exactly like a quiet world. The
only way to tell them apart is to check the *device*, not the tape — and nobody ever thinks to,
because the tape is what they came for.

## The idea in plain language

OpenTelemetry's default state is *not tracing*. That is a deliberate design decision and a good one:
a library that emitted spans the moment it was imported would impose cost on programs that never
asked for it.

The way it does nothing is worth understanding, because it is the reason the failure is silent.

- `trace.get_tracer(...)` with no provider installed returns a **`ProxyTracer`**, which forwards to
  a no-op implementation.
- Spans from it are **`NonRecordingSpan`** objects. They are real objects with the full API — you
  can call `set_attribute`, `record_exception`, `end` — and every one of those methods does nothing.
- `span.is_recording()` returns **`False`**.

That last one is the load-bearing part, because ADK checks it. From
`google/adk/telemetry/tracing.py`:

```text
  span = span or trace.get_current_span()
  if not span.is_recording():
    return
```

Every instrumentation path in ADK begins with a variation of that. It is correct — building
attribute dictionaries for a span nobody will read is pure waste — and it means the difference
between "tracing configured" and "tracing not configured" is not an error, a warning, or a
degraded mode. It is a `return`.

`AutoTracingPlugin` does the same thing one level up: its constructor computes
`self._tracer_eligible = auto_tracing_helpers.tracer_will_record(self._tracer)`, and
`tracer_will_record` is `not isinstance(tracer, trace_api.NoOpTracer)`. A plugin fitted to a no-op
tracer installs itself, wraps nothing, and reports nothing — part
[2.3](../02-what-adk-records/2.3-every-function-in-the-tree.md) measures that arm, reached by setting
`OTEL_SDK_DISABLED=true`.

One thing that does **not** cause this, and is worth knowing because it looks as though it should:
fetching a tracer before the provider is installed is fine. `get_tracer` returns a `ProxyTracer`
that resolves lazily, so a tracer captured at import time starts recording the moment a provider
appears.

So the failure mode is: **everything works, and there is no trace.**

## Why Sutra needs it

Because this is the first day the desk has had any observability at all, and the most likely way for
the day's work to be quietly wasted is for `sutra/tracing.py` to exist, be imported, be correct, and
never have a provider installed in the process that actually runs — which on Day 86 is a container
started by a command nobody reads.

And because this repository has now met this shape four days running. Day 82 part 3.3: a nightly
that found a regression and exited zero. Day 83 part 1.3: a suite green because it never ran. The
pattern is the same and it is worth naming as a class — **an instrument that is not installed
reports the same thing as a world with nothing to report** — because recognising the class is
faster than rediscovering each instance.

## The mechanism

The lab asks the tracer what it is, then runs the desk and counts:

```python
    tracer = trace.get_tracer("probe")
    with tracer.start_as_current_span("probe") as span:
        recording = span.is_recording()
        kind = type(span).__name__
```

**Line by line:**

- A probe span before any real work, because the question is about the *tracer*, not about the desk.
  This is the "check the device, not the tape" move from the story.
- `type(span).__name__` rather than `isinstance`, because the useful output is the class name the
  reader can go and look up.
- `is_recording()` is the one method whose answer differs between a real span and a no-op one while
  every other method silently succeeds on both.
- The probe span itself is recorded when a provider *is* installed, which is why the wired arm below
  reports eleven spans rather than ten.

Run it with no provider — the default state of any Python process:

```bash
cd days/day-84-the-trace-tree/lab
uv run python norecord.py; echo "exit: $?"
```

**Line by line:**

- No flag: nothing calls `trace.set_tracer_provider`, which is what a program that has not thought
  about tracing looks like.

Measured on 2026-09-07:

```text
tracer provider installed: False
  trace.get_tracer(...) returns:  ProxyTracer
  a span from it is a:            NonRecordingSpan
  span.is_recording():            False

  the desk ran and produced 5 events
  spans recorded:               0
  errors raised:                0
  warnings printed:             0

  the work happened, the answer came back, and there is no trace of it
  nothing failed, so nothing told you
```

**Five events, zero spans, zero errors, zero warnings.** The desk did all of its work: three model
turns, two tool calls, a correct answer. Every ADK instrumentation call ran and returned early.

Now install a provider and change nothing else:

```bash
uv run python norecord.py --wire-it; echo "exit: $?"
```

**Line by line:**

- `--wire-it` calls `_otel.collect()`, which is three lines: build a `TracerProvider`, add a
  processor, call `set_tracer_provider`. That is the entire difference.

Measured on 2026-09-07:

```text
  the desk ran and produced 5 events
  spans recorded:               11
  errors raised:                0
  warnings printed:             0

  11 spans recorded
```

**Zero and eleven, with identical work in between.** Eleven rather than ten because the probe span
is now recorded too.

## When it breaks

There is no error text for this part, and hunting for one is the lesson. What *does* exist is a
warning for the neighbouring mistake — installing a provider twice:

```text
Overriding of current TracerProvider is not allowed
```

That is logged by `opentelemetry.trace` when `set_tracer_provider` is called a second time, and it
matters here because it is the reason every script in this lab is its own process, and the reason
`_otel.collect()` exists in one place. A library that installs a provider on import will lose to
whichever code ran first, silently, and the loser's spans go to the winner's exporter — or to
nothing, if the winner is a no-op.

The composite failure, every step of which is a reasonable decision:

```text
1. tracing is wired up in a script somebody ran by hand, and works
2. the same code is imported by the API server, which has its own entry point
3. the entry point never calls set_tracer_provider
4. every span in production is a NonRecordingSpan
5. the dashboard is empty, so somebody concludes traffic is low
6. six weeks later a request fails and there is nothing to look at
```

Step 5 is the answering machine. Step 3 is the whole bug, and it is a missing line rather than a
wrong one, which is why no review caught it.

The check that catches it is the probe in this lab's first four lines, promoted into the product:
assert at startup that `trace.get_tracer(__name__).start_span("startup").is_recording()` is true,
and fail loudly if it is not. That is a `TODO(me)` in the hub, and it is check one of six in
`gate.py`.

## In production

**What a professional does.** Makes "is tracing on?" answerable without looking at a dashboard. A
one-line startup log — *tracing: enabled, exporter=sqlite, sampler=parentbased_traceidratio{0.1}* —
costs nothing and turns a silent misconfiguration into a line somebody can grep for. The stronger
version fails startup outright when tracing is required by the environment it is running in.

**What degrades at scale.** The number of entry points. One process becomes a server, a worker, a
scheduled job, a migration and a test harness, and each is a place where the provider has to be
installed. Every one that forgets is invisible in exactly the same way, and the aggregate symptom —
a system that appears to have less traffic than it does — is one nobody investigates because it is
good news.

**The failure that only shows with real traffic.** Partial coverage. Half the entry points are
wired and half are not, so the traces that exist are real and the picture they paint is a lie: the
paths that are traced look like the whole system, and the untraced worker that is actually failing
does not appear at all. This is worse than no tracing, because no tracing does not mislead.

**The review comment a senior engineer leaves:** *"Add the startup assertion. I do not want to find
out that tracing was off by noticing the dashboard is quiet — that is the one signal that reads as
good news."*

**The interview question:** *"Your traces stopped appearing. Where do you look?"* The answer that
shows experience checks whether the process is *recording* before it checks the exporter, the
network or the backend — because a no-op tracer is the only one of those failures that produces no
error anywhere.
