# 2.1 — The decorator that writes your schema

## One-line answer

`@server.tool()` reads your function's name, type hints, docstring and return annotation, and from
those four things writes the JSON Schema declaration that goes on the wire — which is convenient
until you realise it means your type hints are now a public interface.

## The story

You go to the office to apply for a duplicate ration card.

You do not fill in the form. You hand your identity card across the counter and the clerk fills it
in, reading off the card: name here, father's name here, address here, date of birth here. He turns
the form round for your signature, and the two of you have just produced a document neither of you
wrote from scratch. It is faster and it has fewer mistakes than the version where you copy fourteen
fields by hand.

Then you notice something on the form. Your address is the one on the card, and you moved last year.
You have been meaning to update the card. Until today it did not matter, because nobody read the
card except you.

But the form is not the card. The form goes into a file, and a letter will be sent to the address on
the form, and by the time the letter goes astray the card will be back in your pocket and forgotten.
The clerk did nothing wrong. He copied faithfully from the document you gave him — and the moment
that document became the source for something that leaves the building, every stale field in it
became a real problem.

## The idea in plain language

A **decorator** in Python is a line beginning with `@` that sits above a function and changes what
happens when the file is loaded. `@server.tool()` does not change what your function does when it is
called; it registers the function with the server and, on the way, builds a description of it.

That description is a **JSON Schema**: a JSON object that says what arguments a call may carry, what
type each one is, and which are required. Day 4's
[1.1](../../../day-04-tools-by-hand/parts/01-the-schema/1.1-the-form-that-rejects-itself.md) is where
this curriculum first met one, and Day 4's
[1.2](../../../day-04-tools-by-hand/parts/01-the-schema/1.2-declaring-a-tool.md) is where you wrote
one by hand into `sutra/tools.py`. Today the same object is produced for you.

Four things go in and four come out:

| The decorator reads | It becomes |
| --- | --- |
| the function's name | the tool's `name` |
| the docstring | the tool's `description` |
| the parameter type hints | `inputSchema` |
| the return type hint | `outputSchema` |

The clerk-and-card shape is exact. Your function is the identity card: a document written for one
audience, which now becomes the source for a form that leaves the building. Everything on it is
public.

## Why Sutra needs it

Because Sutra already has both halves and this is the day they meet.

`sutra/loop.py` has held `lookup_ticket` and `search_kb` since Day 3 — plain functions with type
hints and docstrings, written for a human reading the module. `sutra/tools.py` has held a
hand-written declaration for each of them since Day 4 — a dictionary with a `description` written
for a *model* to route on. Two artefacts, describing the same function, for two audiences.

Today's decorator collapses them into one, and the interesting question is whether that is a good
thing. It is, for the schema: a hand-maintained `inputSchema` drifts from the function the first
time somebody adds a parameter, and Day 4's
[4.2](../../../day-04-tools-by-hand/parts/04-the-limits/4.2-the-tool-that-is-never-called.md) is
about exactly that kind of silence. It is not obviously good for the description, because a
docstring written for a maintainer and a description written for a model are genuinely different
documents. [2.2](2.2-the-schema-is-all-they-get.md) is that argument in full, and the build brief
leaves the decision to you.

## The mechanism

The decorator, on Sutra's first tool. This is the extract from `lab/serve.py`:

```python
@server.tool()
def lookup_ticket(ticket_id: str) -> str:
    """Fetch the full text of one support ticket by its id.

    Use this first whenever the user names or implies a specific ticket, before
    offering any diagnosis. Returns the ticket's title and body, or a sentence
    saying no such ticket exists.

    Args:
        ticket_id: The ticket's id as it appears in the request, e.g. '4521'.
    """
    return TICKETS.get(ticket_id.strip(), f"No ticket with id {ticket_id!r}.")
```

**Line by line:**

- `@server.tool()` — note the parentheses. `server.tool` is a method that *returns* a decorator, so
  it must be called. Written as `@server.tool` with no parentheses, Python passes your function
  where the SDK expects a name string, and the failure is confusing and late.
- `def lookup_ticket(...)` — **the function name is the tool name.** Renaming this function renames a
  tool on the wire, which a client may have in an allowlist. The specification's tool-name rules,
  read from `https://modelcontextprotocol.io/specification/2026-07-28/server/tools` on 2026-09-04:
  1 to 128 characters, case-sensitive, and only letters, digits, underscore, hyphen and dot. Python
  identifiers satisfy that automatically, which is why nobody notices the rule exists.
- `ticket_id: str` — the type hint becomes the parameter's declared type in `inputSchema`, and it
  becomes the validation rule the SDK enforces on every call. It is no longer documentation.
  [2.3](2.3-the-argument-that-changed-on-the-way-in.md) is what happens when it is wrong.
- `-> str` — the return hint produces an `outputSchema`. `structured_output` in
  `add_tool`'s signature defaults to `None`, which the SDK's own docstring describes as
  *"auto-detects based on the function's return type annotation"* (read from
  `.venv/Lib/site-packages/mcp/server/fastmcp/server.py`, 2026-09-04). Annotate the return and you
  get an output schema whether you wanted one or not.
- The docstring's first line and body both travel. So does the `Args:` block, verbatim, indentation
  included.
- The body is unchanged from `sutra/loop.py`. The decorator wraps; it does not rewrite.

Now read what came out. This is the real `lookup_ticket` entry from `tools/list`, printed by
`lab/schema.py` on 2026-09-04:

```json
{
  "name": "lookup_ticket",
  "description": "Fetch the full text of one support ticket by its id.\n\n        Use this first whenever the user names or implies a specific ticket, before\n        offering any diagnosis. Returns the ticket's title and body, or a sentence\n        saying no such ticket exists.\n\n        Args:\n            ticket_id: The ticket's id as it appears in the request, e.g. '4521'.\n        ",
  "inputSchema": {
    "properties": {
      "ticket_id": {
        "title": "Ticket Id",
        "type": "string"
      }
    },
    "required": ["ticket_id"],
    "title": "lookup_ticketArguments",
    "type": "object"
  },
  "outputSchema": {
    "properties": {
      "result": {
        "title": "Result",
        "type": "string"
      }
    },
    "required": ["result"],
    "title": "lookup_ticketOutput",
    "type": "object"
  }
}
```

Five things in that output are worth stopping on, and three of them are surprises.

**`"required": ["ticket_id"]`** came from the absence of a default value, not from anything you
wrote. Give the parameter a default and it leaves the `required` list. That is the correct
behaviour and it is invisible in the source.

**`"title": "lookup_ticketArguments"`** is an artefact. The SDK builds a Pydantic model to hold the
arguments and names it after your function; the model's name then leaks into the schema. Nobody
chose that string and it is on the wire.

**`"description"` carries the entire docstring**, including the `Args:` block, the blank lines and
the leading spaces of the indentation. The model reads all of it.

**`outputSchema` wraps your `str` in an object with one key called `result`.** JSON Schema at the
top level of a tool result has to be an object, so a scalar return type is boxed. Your function
returns a string; the declaration says it returns `{"result": "..."}`.

**Nothing here required a running server.** `schema.py` builds the object, calls
`await server.list_tools()`, and prints. Zero model calls, no network, no process.

## When it breaks

The break is the missing parentheses, and the error is nowhere near the line that caused it:

```text
Traceback (most recent call last):
  File "...\days\day-34-building-sutra-mcp-tools\lab\_tmp_bare.py", line 6, in <module>
    @server.tool
     ^^^^^^^^^^^
  File "...\.venv\Lib\site-packages\mcp\server\fastmcp\server.py", line 493, in tool
    raise TypeError(
TypeError: The @tool decorator was used incorrectly. Did you forget to call it? Use @tool() instead of @tool
```

Captured on 2026-09-04. This one is kind: the SDK checks whether the thing it was handed is callable
and says exactly what you did. Not every framework does, and the generic version of this mistake —
a decorator factory used without its parentheses — usually surfaces as `TypeError: 'function' object
is not callable` several imports later.

The second break is not an error at all, and it is the one that costs an evening. Delete the
docstring:

```python
@server.tool()
def lookup_ticket(ticket_id: str) -> str:
    return TICKETS.get(ticket_id.strip(), f"No ticket with id {ticket_id!r}.")
```

**Line by line:**

- The function still works. Calling it in Python returns the same string.
- It still registers. `tools/list` still contains an entry named `lookup_ticket`.
- The entry's `description` is now the empty string `""` — measured on 2026-09-04, not `null` and
  not absent, just empty. Nothing warns you, no test fails, and the server starts perfectly.
- What has actually happened is that the model on the other side has been handed a tool with a name
  and no explanation of when to use it. It will guess from the name, and it will guess wrong on the
  cases the docstring existed to describe. That is [2.2](2.2-the-schema-is-all-they-get.md)'s whole
  subject, and `lab/gate.py` fails the day if any tool has an empty description precisely because
  nothing else will.

## In production

**What a professional writes instead:** the decorator for the schema, and an explicit `description=`
for anything the model must know. `@server.tool(description=LOOKUP_TICKET_DESCRIPTION)` separates
the maintainer's docstring from the model's routing text and keeps both. Some teams go further and
keep descriptions in a data file so they can be reviewed, versioned and A/B tested without touching
Python — which is exactly what `sutra/tools.py` already is.

**What degrades at scale:** the schema is generated from types, so a refactor changes an interface.
Rename a parameter for readability and you have shipped a breaking change to every caller, with no
compiler and no test to catch it, because nothing in your process knows the parameter name was
public. Teams that have been bitten add a test that snapshots `tools/list` and fails on any diff, so
the change is at least visible in review.

**The failure mode that only appears with real traffic:** the docstring that was fine as
documentation and is wrong as instruction. *"Fetch a ticket. Note: slow for large accounts."* is a
sensible note to a maintainer and, in a model's context on every turn, an invitation to avoid the
tool. You find out because tool-use rates drop after a documentation tidy-up nobody associated with
behaviour.

**The review comment a senior engineer leaves:** *"the docstring on this tool has an `Args:` block
with our internal parameter naming convention in it, and the whole thing including the indentation
goes on the wire and into the model's context on every turn. Either write it for the model or pass
`description=` separately — right now the audience of that text is not the audience it was written
for."*

**The interview question:** *"where does an MCP tool's schema come from?"* The honest answer: *"From
the function, if you let it. The SDK's decorator reads the function name for the tool name, the
docstring for the description, the parameter type hints for `inputSchema` and the return annotation
for `outputSchema`. That kills a whole class of drift — a hand-written schema stops matching its
function the first time somebody adds a parameter. The trade is that your type hints and your
docstring became a public interface. Renaming a parameter is a breaking change now, and the
docstring is in the model's context on every turn, so it should be written for the model. We ended
up generating the schema and passing the description explicitly."*
