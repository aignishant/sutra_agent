# 2.3 — 💥 The argument that changed on the way in

## One-line answer

A declared type is not only a filter, it is a converter: an argument the caller sent as `"04521"`
arrives in a tool that declared `int` as `4521`, with no error, no warning and no way for either
side to find out.

## The story

You are given a list of five hundred customer phone numbers in a text file and asked to tidy it up
in a spreadsheet.

You open the file, click through the import, and the numbers land in a column. It looks right. You
sort it, widen the column, save it, and email it back. Somebody rings you two days later: about a
fifth of the numbers do not connect.

The numbers that broke all began with a zero. The spreadsheet looked at `09876543210`, decided that
a string of digits is a number, and stored it as the number 9876543210. Numbers do not have leading
zeros, so it dropped it. Nothing was highlighted, nothing was flagged, and the cell looked plausible
— it was ten digits instead of eleven, and nobody counts digits in a column of five hundred.

The program was not broken. It was helpful. It looked at what you gave it, worked out what you
probably meant, and quietly made the data match its guess.

## The idea in plain language

**Validation** is checking that a value matches a declared type and refusing it if not.
**Coercion** is converting a value that does not match into one that does. They look like the same
feature and they are opposites: one protects the tool from the caller, the other protects the caller
from having to be exact.

The SDK's tool layer does both, and which one you get depends entirely on which direction the
mismatch runs:

| Declared | Caller sends | What happens |
| --- | --- | --- |
| `str` | `"4521"` | accepted, unchanged |
| `str` | `4521` (a JSON number) | **refused** — validation error |
| `int` | `4521` | accepted, unchanged |
| `int` | `"4521"` (a JSON string) | **converted** to `4521`, silently |
| `int` | `"04521"` | **converted** to `4521` — the leading zero is gone |

The asymmetry is not a bug in the library, and knowing why it exists is what makes it predictable.
A JSON string can hold anything, including something that looks like a number, so turning a numeric
string into a number is usually what the sender meant. A JSON number cannot hold a leading zero at
all, so a library that turned `4521` into `"4521"` would be inventing a representation the sender
never chose. So the rule is: **strings are tolerated where numbers are declared, and numbers are
refused where strings are declared.**

The dangerous cell in that table is the last row. It is not an error. It is a value that arrived
looking like an identifier and left looking like a quantity.

## Why Sutra needs it

Because `lookup_ticket(ticket_id: str)` declares a **string**, and ticket ids look exactly like
numbers.

Every model that has ever seen a support system knows tickets are numbered. Asked to look up ticket
4521, a model will sometimes emit `{"ticket_id": "4521"}` and sometimes `{"ticket_id": 4521}`, and
the second one is refused. That is the correct outcome and it is the reason the type hint is `str`
and not `int`, but you have to know it is going to happen, because the model is not wrong — it is
guessing at a distinction the description never mentioned.

Now imagine the type hint had been `int`. The refusals stop, which feels like an improvement. And
the first customer whose ticket id begins with a zero — `04521`, from the old numbering scheme —
gets *"No ticket with id 4521"*, because the identifier was corrected into a quantity somewhere
between the caller and the dictionary. Nobody in the chain did anything wrong and the ticket is
sitting in the archive.

This matters again on Day 39, when these tools are backed by SQLite instead of a dictionary and the
coerced value goes into a query.

## The mechanism

`lab/coerce.py` builds two tools whose only difference is one type hint, and reports the Python type
of the argument each one actually received:

```python
@server.tool()
def wants_string(ticket_id: str) -> str:
    """Declares ticket_id as a string."""
    return f"body received {ticket_id!r} ({type(ticket_id).__name__})"


@server.tool()
def wants_integer(ticket_id: int) -> str:
    """Declares ticket_id as an integer."""
    return f"body received {ticket_id!r} ({type(ticket_id).__name__})"
```

**Line by line:**

- The two functions are identical except for `str` against `int`. Everything the script shows is
  caused by that one word.
- `{ticket_id!r}` uses `repr`, so a string prints with its quotes and a number prints without them.
  That is the whole experiment: `'4521'` and `4521` have to be distinguishable in the output.
- `type(ticket_id).__name__` reports what the **body** got, not what the caller sent. The gap between
  those two is the subject of this part.
- No `try`, no validation of our own. Whatever protection exists comes from the declared type.

Run it and read the middle column:

```text
wants_string   sent '4521'   isError=False body received '4521' (str)
wants_string   sent 4521     isError=True  Error executing tool wants_string: 1 validation error for wants_stringArguments ticket_id   Input should be a valid string [type=string_type, input_value=4521, input_type=int]     For further information visit https://errors.pydantic.dev/2.13/v/string_type
wants_string   sent '04521'  isError=False body received '04521' (str)
wants_integer  sent '4521'   isError=False body received 4521 (int)
wants_integer  sent 4521     isError=False body received 4521 (int)
wants_integer  sent '04521'  isError=False body received 4521 (int)
```

Measured on 2026-09-04. Read the last line slowly. **The caller sent the six characters `'04521'`
and the tool body received the integer `4521`.** `isError` is `False`. There is no log line. Neither
side can discover that the value changed, because the caller has no idea what the body saw and the
body has no idea what was sent.

Where does the conversion happen? Not in the protocol — JSON carried the string faithfully. It
happens in the SDK, and the comment above it is unusually honest. From
`.venv/Lib/site-packages/mcp/server/fastmcp/server.py`, read 2026-09-04:

```python
# Note: we disable the lowlevel server's input validation.
# FastMCP does ad hoc conversion of incoming data before validating -
# for now we preserve this for backwards compatibility.
self._mcp_server.call_tool(validate_input=False)(self.call_tool)
```

**Line by line:**

- `validate_input=False` turns off the low-level server's schema check, the one that would have
  compared the arguments against the `inputSchema` you published and rejected a mismatch.
- *"ad hoc conversion of incoming data before validating"* is the library describing its own
  behaviour: convert first, then check. Convert-then-check is coercion; check-then-convert would be
  validation.
- *"for now we preserve this for backwards compatibility"* means the behaviour is known, kept
  deliberately, and may change in a later release. Which is a second reason to validate yourself:
  the behaviour you are relying on is documented as provisional.
- The specification, meanwhile, is not provisional at all
  (`https://modelcontextprotocol.io/specification/2026-07-28/server/tools`, read 2026-09-04):
  *"Servers **MUST**: Validate all tool inputs."* An argument that was silently reshaped has not
  been validated; it has been accommodated.

The defence is one line in the tool body, and it is worth writing even though it looks redundant:

```python
@server.tool()
def lookup_ticket(ticket_id: str) -> str:
    """Fetch the full text of one support ticket by its id."""
    if not isinstance(ticket_id, str):
        return f"ticket_id must be a string, got {type(ticket_id).__name__}. Send it quoted."
    return TICKETS.get(ticket_id.strip(), f"No ticket with id {ticket_id!r}.")
```

**Line by line:**

- `isinstance(ticket_id, str)` re-checks a thing the schema already declared. That is the point: the
  schema declared it to the *caller*, and this checks it in the *body*, which is the only place that
  knows what actually arrived.
- It **returns a sentence** rather than raising. A returned sentence becomes a tool result the model
  can read and correct itself from; a raised exception becomes an error whose text the model may
  never usefully act on. That distinction is section 4's whole subject, starting at
  [4.1](../04-two-kinds-of-no/4.1-the-tool-said-no.md).
- The message says what to do — *"Send it quoted"* — because the reader of this string is a model
  deciding what to try next, not a human reading a log.
- This is the end-to-end argument in one line: the check that matters is the one at the end that
  cares, not the one in the middle that is trying to be helpful.

## When it breaks

Here is the whole error a caller gets for the *refused* direction, which is the friendly half:

```text
Error executing tool wants_string: 1 validation error for wants_stringArguments
ticket_id
  Input should be a valid string [type=string_type, input_value=4521, input_type=int]
    For further information visit https://errors.pydantic.dev/2.13/v/string_type
```

Three things to notice. `wants_stringArguments` is the generated model name from
[2.1](2.1-the-decorator-that-writes-your-schema.md) surfacing in an error a model will read.
`input_value=4521` and `input_type=int` are the genuinely useful fields — they say what arrived, and
a model can use them to retry correctly. And there is a **URL to a third party's documentation site**
in a message that goes into the model's context, which is a small leak of your implementation stack
to every caller.

The other direction has no error text to show, and that is the failure this part is named for:

```text
wants_integer  sent '04521'  isError=False body received 4521 (int)
```

That line is what a successful call looks like when the data was changed on the way in. If you are
looking for the moment to remember from this part, it is that a screenshot of a healthy system and a
screenshot of this bug are the same screenshot.

## In production

**What a professional writes instead:** the narrowest type that is honest, plus a body-level check.
Identifiers are `str`, always — a ticket id, an account number, a postcode and a phone number are
strings that happen to be spelled with digits, and declaring any of them `int` is a decision to lose
leading zeros. Quantities are `int` or `float`. Where the range matters, the type carries it too: a
Pydantic model or an `Annotated` type with bounds turns "page must be positive" into a schema the
caller can read rather than a comment nobody sees.

**What degrades at scale:** silent coercion becomes silent data corruption once the value leaves
your process. In a dictionary lookup a coerced id is a miss, which is annoying. In a SQL query on
Day 39 it is a `WHERE id = 4521` that matches a different row. In a write tool it is an update
applied to the wrong record, and the audit log faithfully records the coerced value, so the
investigation starts from the corrupted number and never sees the original.

**The failure mode that only appears with real traffic:** the tool that worked for a year because
every id in the test data was five digits with no leading zero. It breaks on the first customer
migrated from an older numbering scheme, and it breaks as *"no such ticket"* rather than as an
error, so it is reported as a data problem by a support agent and closed as not reproducible by an
engineer who tries it with a normal id.

**The review comment a senior engineer leaves:** *"`ticket_id: int`. Ticket ids are identifiers, not
quantities — we have ids with leading zeros in the archive and this will turn `04521` into `4521`
with no error anywhere. Make it `str` and add an explicit check in the body, because the SDK
converts before it validates and the schema we publish is not the thing that runs."*

**The interview question:** *"your tool declares a type in its schema — is that enough?"* The honest
answer: *"No, for two reasons. First, the SDK we use converts before it validates, so a JSON string
sent to an `int` parameter is coerced rather than refused, and `'04521'` becomes `4521` with no
error on either side — the library says so in a comment above the line that disables the low-level
schema check. Second, the spec says servers must validate all tool inputs, and a value that was
reshaped to fit was not validated. So we type identifiers as strings, never integers, and we
re-check in the tool body and return a sentence the model can act on rather than raising. It looks
redundant next to a declared type, and it is the only check that sees what actually arrived."*
