# 2.2 — The schema is all they get

## One-line answer

The caller never sees your function, your data or your log — only the declaration — so anything the
caller must know to use the tool correctly has to be written into the description, and anything you
leave out is a guess somebody else has to make.

## The story

You are sent to the hospital for a blood test and you arrive at a corridor of closed doors.

Each door has a printed sign. *Sample collection — 8 to 11 — bring the doctor's slip.* *Reports —
after 2 — bring the receipt.* *Billing.* You have a slip, it is half past nine, so you join the
first queue. Twenty minutes later you reach the front and the person there tells you that fasting
samples are taken before nine, and it is now too late; come back tomorrow.

Nothing on the door said that. The rule is real, everyone behind the door knows it, and it has
probably been true for years. But the sign is the entire interface between you and the room, and the
sign said 8 to 11.

You did not make a mistake. You read the only information you were given, and you acted on it
correctly, and it was wrong. The next person will do the same thing, at the same time tomorrow,
because the correction lives in the room and the decision is made in the corridor.

## The idea in plain language

Everything on the other side of an MCP boundary is invisible. The caller has your tool's
declaration and nothing else:

| The caller can see | The caller cannot see |
| --- | --- |
| the tool's `name` | the function's body |
| the `description` | the data it reads |
| `inputSchema` — parameter names, types, which are required | what a miss looks like |
| `outputSchema` — the shape of a successful result | your log lines, your comments, your tests |

That list is the whole reason MCP is worth a network hop — Day 32's
[1.5](../../../day-32-mcp-stateless-core/parts/01-the-socket/1.5-one-gate-to-guard.md) is the
argument for one gate you can point at. It is also a discipline: **the declaration is not
documentation about the tool, it is the tool's entire user manual**, and it is read by a model that
cannot ask a follow-up question.

Day 4's
[1.3](../../../day-04-tools-by-hand/parts/01-the-schema/1.3-the-description-is-the-prompt.md) made
the first half of this point locally: a description is not a comment, it is prompt text, and it is
what makes a model choose one tool over another. Crossing a process boundary makes it stricter.
Locally, a wrong description is a bad hint about code the same team can read. Over MCP, the caller
may be someone else's agent, on someone else's machine, that will never see your repository.

## Why Sutra needs it

Because Sutra's own `search_kb` has a rule in its body that its description does not carry, and it
is not a hypothetical.

`search_kb` matches a fixed set of keywords with a substring test — `"logout"` and `"export"`, and
nothing else. Its description, generated from its docstring in
[2.1](2.1-the-decorator-that-writes-your-schema.md), says to call it *"with the symptom words from
the ticket body"*. Ticket 4521's body begins *"I keep getting logged out of the dashboard"*.

A model that follows the description exactly gets nothing back. Measured on 2026-09-04:

```text
'keeps getting logged out'     -> No KB article matched 'keeps getting logged out'.
'logout loop on the dashboard' -> KB-104 'Unexpected logouts': cookies set with SameSite=Stric...
'Logout'                       -> KB-104 'Unexpected logouts': cookies set with SameSite=Stric...
```

The instruction was followed and the tool answered honestly and the outcome was a dead end, because
the matching rule lives in the body where nobody outside can read it. That is the hospital door
exactly. This has been true since Day 3 and it did not matter, because the only caller was a loop
in the same file that you could read. Today it is on a wire.

## The mechanism

Here is `search_kb`'s complete declaration, printed by `lab/schema.py` on 2026-09-04. This — and
only this — is what a caller has:

```json
{
  "name": "search_kb",
  "description": "Search the internal knowledge base for a known issue matching a symptom.\n\n        Use this after reading a ticket, with the symptom words from the ticket body.\n        Returns one article, or a sentence saying nothing matched. Do not use this to\n        look up a ticket - use lookup_ticket for that.\n\n        Args:\n            query: Symptom words taken from the ticket, e.g. 'keeps getting logged out'.\n        ",
  "inputSchema": {
    "properties": {
      "query": {
        "title": "Query",
        "type": "string"
      }
    },
    "required": ["query"],
    "title": "search_kbArguments",
    "type": "object"
  },
  "outputSchema": {
    "properties": {
      "result": {"title": "Result", "type": "string"}
    },
    "required": ["result"],
    "title": "search_kbOutput",
    "type": "object"
  }
}
```

Now the body, which the caller does not have:

```python
def search_kb(query: str) -> str:
    q = query.lower()
    for keyword, article in KB.items():
        if keyword in q:
            return article
    return f"No KB article matched {query!r}."
```

**Line by line:**

- `q = query.lower()` — the match is case-insensitive. Nothing in the declaration says so, so a
  caller may waste effort normalising, or may assume the opposite and give up after one failure.
- `for keyword, article in KB.items()` — the search is over **two** keywords, `"logout"` and
  `"export"`. It is not a search engine. A caller told to send "symptom words" has been told
  something that is true of a search engine and false of this.
- `if keyword in q` — the keyword must be a substring of the query, which is backwards from what
  most people assume. `"logout"` in `"logout loop"` is a hit; `"logged out"` is a miss, because
  `"logout"` is not a substring of it.
- `return article` — **the first** match wins, in dictionary order. A query containing both words
  gets one article and no indication that another existed.
- `return f"No KB article matched ..."` — a miss is a sentence, not an error. Day 3's
  [2.3](../../../day-03-loop-hand-rolled/parts/02-tools-and-dispatch/2.3-a-failed-tool-is-an-observation.md)
  is why, and [4.1](../04-two-kinds-of-no/4.1-the-tool-said-no.md) is what the protocol calls that.

Five behaviours, none of them visible from outside, and at least three of them change what a
sensible caller would do. The fix is not to make the description longer for its own sake; it is to
put the *decisions* in it:

```python
@server.tool()
def search_kb(query: str) -> str:
    """Search the internal knowledge base for a known issue matching a symptom.

    Matching is a case-insensitive substring test against a small fixed set of
    topic keywords - currently 'logout' and 'export'. Send the topic word, not
    the customer's sentence: 'logout' matches, 'keeps getting logged out' does
    not. Returns one article, or a sentence saying nothing matched. Use
    lookup_ticket to fetch a ticket; this tool does not do that.
    """
```

**Line by line:**

- *"case-insensitive substring test against a small fixed set of topic keywords"* replaces the word
  "search", which promised something the code does not do.
- *"currently 'logout' and 'export'"* is the uncomfortable one, and it is right. The caller cannot
  enumerate the set any other way, and the word **currently** tells them not to hard-code it.
- *"'logout' matches, 'keeps getting logged out' does not"* is a worked example of the exact failure
  the old description caused. One example of a miss is worth three sentences of rule.
- *"Use lookup_ticket to fetch a ticket; this tool does not do that"* keeps the negative routing hint
  from the original. Telling a model what a tool is *not* for is what stops it being chosen by
  accident, which is Day 28's subject at
  [2.4](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.4-the-crowded-shelf.md).
- The `Args:` block is gone, because its one line said the same thing as the parameter name and it
  was costing tokens on every turn.

## When it breaks

The break has no error message, which is the whole difficulty. Here is the sequence, run against
the unfixed description on 2026-09-04:

```text
lookup_ticket 4521  -> Title: Keeps getting logged out. Body: I keep getting logged out of the
                       dashboard every few minutes. Started yesterday. Plan: Pro.
search_kb 'keeps getting logged out'
                    -> No KB article matched 'keeps getting logged out'.
```

`isError` is `False` on both. Both tools worked. The transcript a support engineer reads later says
the knowledge base has nothing on logouts, which is untrue: KB-104 is sitting right there, and the
query that would have found it is one word long.

The way you find this in a real system is a metric, not a stack trace: a tool with a suspiciously
high rate of "no match" replies. If your logging records the tool name and the outcome shape — Day
22's structured logging is where that habit was built — then a tool answering *"nothing matched"*
most of the time is a description problem, not a data problem, and it is visible from a dashboard
without reading a single transcript.

## In production

**What a professional writes instead:** a description that states the matching rule, gives one
example of a hit and one of a miss, and names the sibling tool this one is not. The test of a good
tool description is whether a competent stranger could use the tool correctly with the description
and no access to the code — which is exactly the situation every caller of an MCP server is in.

**What degrades at scale:** description length. Every tool's full declaration sits in the model's
context on every turn, so twenty tools with generous descriptions is a fixed tax on every request
before the user has typed anything — Day 24's token accounting is where that arithmetic lives.
Beyond a certain number of tools the answer stops being shorter descriptions and becomes fewer
tools in front of the model at once, which is Day 28's progressive disclosure and Day 40's
filtering.

**The failure mode that only appears with real traffic:** description drift. The code changes, the
description does not, and nothing connects them. Somebody adds a third KB keyword; the description
still says *"currently 'logout' and 'export'"*; a caller reasonably concludes the third topic is not
covered and routes the ticket to a human. There is no error and no test, because no test asserts
that a sentence in English matches a dictionary in Python. The teams that solve this generate the
enumerable part of the description from the data rather than writing it twice.

**The review comment a senior engineer leaves:** *"this description says 'search the knowledge
base'. The implementation is a substring test over two hard-coded keys. A model reading that
description will send whole sentences and get nothing, and the transcript will look like we have no
article on the topic. Say what the matching rule is and give one example of a query that misses."*

**The interview question:** *"how do you decide what goes in a tool's description?"* The honest
answer: *"Assume the caller has the declaration and nothing else — no code, no repository, no way to
ask. So anything that changes what a caller should do belongs in the description: the matching rule,
what a miss looks like, and what the tool is deliberately not for. We had a real example where a
knowledge-base tool told the model to send 'symptom words from the ticket', and the implementation
was a substring match on two topic keywords, so following the instruction exactly returned nothing
and the transcripts read as though the article did not exist. Nothing errored. We found it from the
rate of no-match results, and the fix was three sentences of description including one example of a
query that fails."*
