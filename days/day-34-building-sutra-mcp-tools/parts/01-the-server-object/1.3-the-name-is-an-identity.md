# 1.3 — The name is an identity

## One-line answer

The string you pass to `FastMCP(...)` travels out in every reply as `serverInfo.name`, gets written
into host configuration files, log lines and allowlists you do not own — so it is expensive to
change and, by the specification's own words, proves nothing about who wrote the server.

## The story

Your school certificates say one spelling of your name.

Your payslips say another, because the person typing them heard it rather than read it. The bank
copied the passport, the hospital copied the bank card, and the electricity bill copied whatever
was on the tenancy agreement. None of these places consulted each other. Each one wrote down what
it was handed on the day it opened your file, and then kept it.

You decide to fix the spelling. Now you find out how many places there are. The bank wants a form
and a document. The hospital wants you to come in. The electricity company changes it and then, six
months later, a new bill arrives with the old spelling because their billing system was never the
same system as their account system. Meanwhile a cousin with an almost identical name receives one
of your letters, and nobody along the chain finds this strange, because the only thing any of them
checked was that the name matched.

Two facts come out of that afternoon. Changing a name is not one job, it is one job per place that
copied it. And a matching name never proved anybody was who they said they were.

## The idea in plain language

**`serverInfo`** is the small block a server sends to identify itself: a `name` and a `version`. In
the 2026-07-28 revision it rides in the `_meta` of every result, under the reserved key
`io.modelcontextprotocol/serverInfo` (`https://modelcontextprotocol.io/specification/2026-07-28/basic/index`,
read 2026-09-04). In the revision the pinned SDK actually speaks it comes back once, inside the
`initialize` reply. Either way, the same string leaves your process.

Where does that string end up? In more places than you control:

| Where it lands | Who put it there | What breaks when you change it |
| --- | --- | --- |
| a host's configuration file, as the server's key | a human, once | the host stops finding the server |
| log lines and traces on both sides | your logging setup | dashboards and saved searches stop matching |
| a tool-name prefix, when a client merges several servers | the client, automatically | every prefixed tool name changes at once |
| an operations allowlist or a policy rule | a security team | the rule silently stops applying |

And now the part that surprises people, quoted from the specification's tools page
(`https://modelcontextprotocol.io/specification/2026-07-28/server/tools`, read 2026-09-04):

> *"The server `name` (from `serverInfo`) is not guaranteed to be unique across servers and
> **SHOULD NOT** be relied upon for disambiguation."*

So the name is an identity in the way the spelling on a bill is an identity: it is how people and
logs refer to the thing, and it is not a proof of anything. Day 32's
[4.3](../../../day-32-mcp-stateless-core/parts/04-governance-and-registry/4.3-a-name-that-proves-its-publisher.md)
made the harder version of this point about registry namespaces — a verified namespace proves
authorship, not safety — and this is the weaker cousin: a bare `serverInfo.name` does not even prove
authorship.

## Why Sutra needs it

Because you are choosing Sutra's name once, today, and Days 35 to 45 all inherit it.

`sutra-mcp` is the choice this day makes, and it is deliberate on three counts. It is lower-case
with a hyphen, which matches how every other server in the ecosystem is named and avoids the
question of whether a host's config key is case-sensitive. It says what the thing *is* rather than
what it currently does, so adding resources on Day 35 and an agent on Day 42 does not make the name
a lie. And it is not `sutra`, because `sutra` is the Python package the agent lives in and having
two different things answer to one word is a bug waiting for a tired evening.

The version matters for a different reason. Day 45 is the phase gate: an audit of everything Days
32 to 44 built. An audit that cannot tell which build of a server it is looking at is a description,
not an audit. Which makes the next section's finding awkward.

## The mechanism

Ask your own server who it is. `lab/wire.py` does this as one of its four probes; here is the
`result` block from the `initialize` reply, printed on 2026-09-04:

```text
{
  "protocolVersion": "2025-11-25",
  "capabilities": {
    "experimental": {},
    "prompts": {"listChanged": false},
    "resources": {"subscribe": false, "listChanged": false},
    "tools": {"listChanged": false}
  },
  "serverInfo": {
    "name": "sutra-mcp",
    "version": "1.29.1"
  },
  "instructions": "Read-only access to the Sutra support desk's ticket archive and knowledge base. Look a ticket up first, then search the knowledge base with the symptom words from its body."
}
```

Read `serverInfo` twice. The name is the string you passed. **The version is `1.29.1`, which is the
version of the `mcp` library** — Sutra has no version `1.29.1` and never will.

That is not a typo in the transcript. It is what the SDK does, and here is the line that does it,
from `.venv/Lib/site-packages/mcp/server/lowlevel/server.py`, read 2026-09-04:

```python
return InitializationOptions(
    server_name=self.name,
    server_version=self.version if self.version else pkg_version("mcp"),
    ...
)
```

**Line by line:**

- `server_name=self.name` — your string, passed straight through. This half behaves as expected.
- `self.version if self.version else pkg_version("mcp")` — if the low-level server was given a
  version, it uses it. If it was not, it falls back to the installed version of the `mcp` package
  itself.
- `pkg_version("mcp")` is `importlib.metadata.version("mcp")` wrapped in a `try`, returning
  `"unknown"` if the lookup fails. So the fallback never errors and never warns.
- The catch is one level up: `FastMCP.__init__` constructs the low-level server with `name`,
  `instructions`, `website_url`, `icons` and `lifespan` — and **no `version`**. Read from
  `.venv/Lib/site-packages/mcp/server/fastmcp/server.py` on 2026-09-04. So every `FastMCP` server in
  `mcp==1.29.1` reports the library's version as its own, and there is no constructor argument that
  changes it.

There is exactly one way to set it without abandoning `FastMCP`, and it reaches through a private
attribute:

```python
server = FastMCP("sutra-mcp", instructions="...", stateless_http=True)
server._mcp_server.version = "0.1.0"
```

**Line by line:**

- `server._mcp_server` is the low-level `Server` that `FastMCP` wraps. The leading underscore is the
  SDK saying *this is not part of my public interface*, and it means a future release may rename it
  without calling that a breaking change.
- `.version = "0.1.0"` sets the attribute the `if self.version` test reads, so the fallback stops
  firing.
- Assigning it after construction works because `create_initialization_options()` is called at
  connection time, not at construction time — the value is read when the reply is built.
- Measured on 2026-09-04: `create_initialization_options().server_version` printed `1.29.1` before
  the assignment and `0.1.0` after it.

Whether Sutra should reach through that underscore, pin its own version somewhere, or accept the
wrong number until the pin moves is a real decision with a cost either way, and it is left to you in
the build brief.

## When it breaks

Change the name and watch a host stop finding the server. This is the failure, verbatim, from a
client pointed at a configuration key that no longer matches:

```text
  File "...\Lib\asyncio\windows_utils.py", line 153, in __init__
    super().__init__(args, stdin=stdin_rfd, stdout=stdout_wfd,
  File "...\Lib\subprocess.py", line 1538, in _execute_child
    hp, ht, pid, tid = _winapi.CreateProcess(executable, args,
                       ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
FileNotFoundError: [WinError 2] The system cannot find the file specified
```

That was produced on 2026-09-04 by pointing a stdio client at the command
`sutra-mcp-server`, which does not exist. Read what it says and what it does not: the deepest frame
is `_winapi.CreateProcess`, and **the name of the file it could not find is nowhere in the message.**
By the time your server's name is wrong it has been copied into a launch command in somebody's
configuration file, and the failure surfaces as a missing file that refuses to say which one. Day
33's
[5.2](../../../day-33-client-and-transports/parts/05-failure-lab/5.2-the-spanner-not-in-the-boot.md)
is the full anatomy of that error and why it is a `ConnectionError` on the ADK path.

The quieter break has no error at all. A client that merges several servers prefixes tool names with
the server identifier to avoid collisions. Rename the server and every prefixed tool name changes
with it, so an allowlist that named `sutra-mcp.lookup_ticket` now matches nothing. The client does
not error — it hands the model a shorter tool list, and the model answers from its own knowledge.
Day 33's
[1.4](../../../day-33-client-and-transports/parts/01-the-connector/1.4-the-allowlist-is-an-argument.md)
is where that silence was first met.

## In production

**What a professional writes instead:** the name as a module constant, referenced everywhere and
typed once — `SERVER_NAME = "sutra-mcp"` — and the version read from package metadata rather than
hand-edited, so a release bump updates it in one place. The identity block is treated as an
interface: changing it is a change note, not a refactor.

**What degrades at scale:** identity stops being decoration the moment two servers are in the same
room. A client merging five servers needs a stable key per server for prefixing, for per-server
timeouts, for per-server rate limits and for the audit log. The specification explicitly declines to
guarantee that `serverInfo.name` is unique, so the client's own configuration key is the real
identifier and `serverInfo.name` is a display label. Systems that conflate the two break the first
time two vendors both call their server `search`.

**The failure mode that only appears with real traffic:** an operations dashboard grouped by
`serverInfo.name`. Two teams deploy servers that report the same name, the graphs merge, and an
incident is investigated against a latency line that is the average of two unrelated services. The
metric was never wrong; it was keyed on a field the spec said not to key on.

**The review comment a senior engineer leaves:** *"this reports `serverInfo.version` as `1.29.1`,
which is the MCP library's version, not ours. Anyone reading an audit log will think they know which
build answered and they will be wrong. Either set the version explicitly or leave a comment saying
we know it is wrong and why — a confidently incorrect version number is worse than an absent one."*

**The interview question:** *"what does a server's name actually guarantee?"* The honest answer:
*"Nothing about identity. It is a display and configuration label. The 2026-07-28 spec says outright
that `serverInfo.name` is not guaranteed to be unique across servers and should not be used for
disambiguation — the client's own configuration key is the real identifier. It is still expensive to
change, because it has been copied into config files, log queries, allowlists and tool-name prefixes
that you do not own, and none of those places will tell you when they stop matching. We also found
that the SDK we pin reports the library's version as the server's version unless you reach through a
private attribute, which is exactly the kind of confidently wrong field an audit trusts."*
