# 3.2 — The same order every time

## One-line answer

The order of the array in `tools/list` is part of what a client and a model provider cache on, so a
list that comes back in a different order is a different list — and the SDK gives you registration
order, which is stable only by accident.

## The story

The attendance register in a class of sixty is in one order and it never changes.

The teacher reads down it, the students know roughly when their name is coming, and a student
arriving late can find their own row in about two seconds because it is in the same place it was
yesterday. When the office wants a copy they photocopy it, and the photocopy is useful for a month.

Then a new teacher decides to reorder it — by house, which is a perfectly reasonable way to group
sixty children. Nothing is lost; every name is still there. But now every photocopy in the office is
wrong, in the specific sense that row 34 is a different child in the copy than in the original.
Nobody notices for a while, because both documents are complete and correct and neither is stale in
the way anyone checks for. It surfaces when two lists are compared and the mismatch is blamed on a
missing name, which is not the problem at all.

## The idea in plain language

The specification is unusually explicit about why order matters
(`https://modelcontextprotocol.io/specification/2026-07-28/server/tools`, read 2026-09-04):

> *"Servers **SHOULD** return tools in a deterministic order (i.e., the same ordering across
> requests when the underlying set of tools has not changed). Deterministic ordering enables clients
> to reliably cache the tool list and improves LLM prompt cache hit rates when tools are included in
> model context."*

Two separate caches are named in that sentence and they are worth separating.

**The client's cache** is [3.1](3.1-the-list-and-who-may-keep-it.md)'s subject. A client that keeps
a list and compares it against a later fetch to decide whether anything changed will see two
identical sets in different orders as a change, and re-do whatever it does on change.

**The model provider's prompt cache** is the expensive one. Tool declarations are sent to the model
as part of the prompt on every turn. Providers cache long prefixes of a prompt and charge less for a
cached prefix, and a cache is keyed on the exact bytes. Reorder two tools and the bytes differ from
the first tool onward, so the prefix that used to be cached is not, and the saving is gone. Nothing
errors. The bill changes.

And one harder rule from the same page, about the *set* rather than the order:

> *"This set **MAY** be empty and **MAY** change over time … but **MUST NOT** vary per-connection or
> as a side effect of other requests on the connection."*

That is Day 32's statelessness pointed at `tools/list`. Two callers on two connections get the same
list; calling a tool does not change what the next `tools/list` says. The one exemption the spec
allows is authorization — *"The set **MAY** vary by the authorization presented on the request …
since credentials are per-request input, not connection state"* — which is Day 37's territory and
is the reason [3.1](3.1-the-list-and-who-may-keep-it.md)'s `cacheScope` question has a real answer.

## Why Sutra needs it

Because `sutra_mcp` gains tools on Days 35, 36, 39, 41 and 42, and each of those days adds its
registration line to `build_server()` in whatever position the writer of that day found natural.

With two tools, registration order is stable because there is only one file. With eight tools
registered from six modules, the order is a consequence of the order of the lines in
`build_server()` — which is a thing people reorder while tidying imports, which is a thing linters
do automatically. `lab/gate.py` asserts the exact list *in order* for exactly this reason: a change
in ordering is a change that should have to be deliberate.

Day 33 already met the client half. Its
[1.3](../../../day-33-client-and-transports/parts/01-the-connector/1.3-before-the-model-sees-a-tool.md)
found that ADK sorts the tools it receives by name before handing them to the model, with the
framework's own comment saying a server's listing order is not contractual. So Sutra's own agent is
protected. Nobody else's is, and you are writing a server other people's clients will call.

## The mechanism

`lab/order.py` builds the same two tools twice, registering them in opposite orders:

```python
def by_hand(first: str, second: str) -> FastMCP:
    """Build a server whose two tools are registered in the order the caller names."""
    server = FastMCP("order-lab")
    bodies = {
        "lookup_ticket": lambda ticket_id: ticket_id,
        "search_kb": lambda query: query,
    }
    for name in (first, second):
        server.add_tool(bodies[name], name=name, description=f"the {name} tool")
    return server
```

**Line by line:**

- `server.add_tool(fn, name=..., description=...)` is the non-decorator form of
  [2.1](../02-function-to-declaration/2.1-the-decorator-that-writes-your-schema.md)'s
  `@server.tool()`. Its signature, read from
  `.venv/Lib/site-packages/mcp/server/fastmcp/server.py` on 2026-09-04, is
  `add_tool(fn, name=None, title=None, description=None, annotations=None, icons=None, meta=None, structured_output=None)`.
  It is the right tool here because the registration order has to be a variable, and a decorator's
  position is fixed by where you type it.
- `description=` is passed explicitly, because a `lambda` has no docstring and a tool with no
  description would fail the gate in [6.2](../06-in-production/6.2-red-before-you-ship-it.md).
- `for name in (first, second)` — the only difference between the two servers this script builds.
- Nothing sorts. Whatever the SDK does with registration order is what you will see.

The output, on 2026-09-04:

```text
registered lookup first : ['lookup_ticket', 'search_kb']
registered search first : ['search_kb', 'lookup_ticket']
same array              : False

sorted, either way      : ['lookup_ticket', 'search_kb'] / ['lookup_ticket', 'search_kb']
same array              : True
```

**The SDK preserves registration order.** That is deterministic in the sense the specification asks
for — the same server returns the same order on every request — and it is fragile in the sense that
matters, because the order is a property of the order of lines in your source rather than of the
data. Sorting makes it a property of the tool names, which change only when a tool changes.

One line, in one place, fixes it for every caller:

```python
async def list_tools_sorted(server: FastMCP) -> list[Tool]:
    """The tool list in a stable order, whatever order registration happened in."""
    return sorted(await server.list_tools(), key=lambda tool: tool.name)
```

**Line by line:**

- `sorted(...)` returns a new list rather than sorting in place, so nothing about the server's own
  registry is disturbed.
- `key=lambda tool: tool.name` sorts by name, which is the ordering ADK already applies on the
  client side, so Sutra's server and Sutra's client agree without either knowing about the other.
- The sort is by the **name**, not the description or the title, because the name is the only field
  that is guaranteed present, unique within a server, and constrained to a small character set.
- `async def` and `await` because `server.list_tools()` is a coroutine — the SDK's own
  `list_tools()` is `async` even though nothing in it does input or output today.
- It is called in exactly one place, the handler that answers `tools/list`, and every caller gets
  the benefit without asking.

## When it breaks

There is no error to show, because a reordered list is a valid list. What you get instead is a
change with no cause, so here is what it looks like from three different chairs:

```text
tools/list, deploy 41  -> ["lookup_ticket", "search_kb", "close_ticket", "get_status"]
tools/list, deploy 42  -> ["lookup_ticket", "close_ticket", "get_status", "search_kb"]
```

**From the client's chair:** a cached list and a fresh list that are not equal, so whatever the
client does on "the tools changed" happens — re-registering, re-notifying, invalidating a downstream
cache. Nothing changed.

**From the finance chair:** prompt-cache hit rate drops on a deploy that touched no prompts. The
tools block sits near the front of the prompt, so a difference in the first tool invalidates the
cached prefix for everything after it.

**From the model's chair:** the least measurable and the most annoying. Tool order is part of the
context, and a model's choice between two plausible tools is not perfectly order-independent. A
change in behaviour after a deploy that "only reordered a list" is the hardest kind of regression to
argue about, because the diff genuinely looks harmless.

The way this actually reaches you is a linter. An import sorter or a formatter reorders the
`register_*` calls in `build_server()`, the diff is three lines nobody reads carefully, and the tool
order changes in production. Sorting in the handler makes all of that a non-event.

## In production

**What a professional writes instead:** a sort in the list handler and a test that asserts the exact
list, in order. The test is the real defence: the sort makes the order stable, and the test makes a
change to the *set* something a human has to acknowledge. `lab/gate.py` is that test in its smallest
form — `names != EXPECTED` is one finding.

**What degrades at scale:** pagination. The specification supports paging `tools/list` with a
cursor, and the moment a list is paged the ordering stops being cosmetic and becomes correctness: an
unstable order means a tool can appear on two pages or on none. The caching page spells out the
consequence — *"There is no cross-page consistency guarantee. If the underlying data changes between
page fetches, clients may observe duplicates or gaps"* — and a client that needs a consistent
snapshot has to re-fetch from the beginning. With two tools this is theory. With a server that
aggregates a hundred, it is Tuesday.

**The failure mode that only appears with real traffic:** ordering that depends on iteration over
something unordered — a set, a `dict` built from concurrent registrations, a directory listing. It
is stable in one process and differs between processes, so three instances behind one address return
three different orders and a client's cache is invalidated by whichever instance answered. The
symptom is a cache hit rate that is roughly one over the number of instances, which looks like a
cache bug and is an ordering bug.

**The review comment a senior engineer leaves:** *"`tools/list` returns registration order. That is
the order of the lines in `build_server()`, which our formatter is allowed to change. Sort by name
in the handler and add a test asserting the exact list — otherwise a tidy-up commit silently
invalidates every client's cache and every prompt cache we are paying for."*

**The interview question:** *"does the order of a tool list matter?"* The honest answer: *"Yes, and
the spec says why. Deterministic order is what lets a client cache the list reliably and what keeps
the model provider's prompt cache warm, because tool declarations sit in the prompt and the cache is
keyed on bytes. Our SDK returns registration order, which is technically deterministic and
practically fragile — it is the order of lines in a function that a formatter may reorder — so we
sort by name in the list handler and assert the exact list in a test. The related rule is that the
*set* must not vary per connection or as a side effect of another request; the only thing it may
vary by is the authorization on the request, because credentials are per-request input rather than
connection state."*
