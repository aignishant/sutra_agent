# 6.2 — Red before you ship it

## One-line answer

Six things must be true of `sutra_mcp/` before this day is done, and a script that checks all six and
exits non-zero is worth more than a checklist, because it is red right now and it will still be
checking on Day 45.

## The story

You weigh the suitcase at home, on the bathroom scale, standing on it twice.

Twenty-four kilos. The allowance is twenty-three. This is a mildly annoying discovery in your own
bedroom, where the wardrobe is two steps away and you can take out the shoes, and it is a completely
different discovery at the check-in counter, with a queue behind you, a bag open on the floor and a
person asking whether you would like to pay for the extra kilo.

The scale did not do anything clever. It told you a number you could have guessed. What it changed
was **where** you found out, and by extension what your options were when you did.

## The idea in plain language

Principle 11 of this curriculum says evals are tests: every day ends with at least one check that can
go **RED**. A check that cannot fail has told you nothing.

The check for a day that writes a server is not *"does it run"*. A server that runs and has no tools
runs perfectly. The check is a small set of statements that must be true of the thing you built, each
one of which corresponds to something this day taught:

| The check | The part it comes from | What being red means |
| --- | --- | --- |
| `sutra_mcp.server.build_server` imports | [1.2](../01-the-server-object/1.2-a-server-you-build-not-one-that-runs.md) | the file does not exist, or importing it fails |
| `sutra_mcp.tools.register_tools` imports | [1.4](../01-the-server-object/1.4-the-shape-later-days-register-into.md) | the registration convention was not followed |
| the server's name is `sutra-mcp` | [1.3](../01-the-server-object/1.3-the-name-is-an-identity.md) | the identity other people's configuration holds is wrong |
| importing the module writes nothing to stdout | [1.2](../01-the-server-object/1.2-a-server-you-build-not-one-that-runs.md) | a `print` or a banner will corrupt the stdio transport |
| `tools/list` is exactly `["lookup_ticket", "search_kb"]`, in order | [3.2](../03-the-two-calls/3.2-the-same-order-every-time.md) | a tool is missing, extra, or the order moved |
| every tool has a description and an object `inputSchema` | [2.2](../02-function-to-declaration/2.2-the-schema-is-all-they-get.md) | a caller has been handed a tool it cannot use correctly |

Six statements, no model calls, and every one of them can be broken by a plausible edit.

## Why Sutra needs it

Because `sutra_mcp/` is the foundation seven later days build on, and none of those days can check
what this one left behind.

Day 35 registers resources into `build_server()`; if `build_server` is not importable or has a
different signature, Day 35 fails in a way that looks like Day 35's problem. Day 42 exposes the whole
desk agent through the same package. Day 45 is the Phase 6 gate and audits everything Days 32 to 44
built — and an audit of a foundation nobody asserted is an audit of an opinion.

There is a second reason and it is about honesty. This day's build brief leaves you to write
`sutra_mcp/server.py` and `sutra_mcp/tools.py` yourself. A day that ends *"and now you have a server"*
with nothing that can say otherwise has asked you to grade your own work. `lab/gate.py` is the
bathroom scale: it is in your own room, it costs nothing to step on, and it tells you before the
queue forms.

## The mechanism

The gate is one function returning a list of strings, and one wrapper turning that list into an exit
code:

```python
async def findings() -> list[str]:
    """Return one line per thing that is not yet true."""
    problems: list[str] = []

    try:
        from sutra_mcp.server import build_server
    except Exception as exc:  # noqa: BLE001 - any import failure is one finding
        return [f"sutra_mcp.server.build_server is not importable: {type(exc).__name__}: {exc}"]
    ...
    quiet = subprocess.run(
        [sys.executable, "-c", "import sutra_mcp.server"],
        capture_output=True,
        text=True,
        check=False,
    )
    if quiet.stdout:
        problems.append(f"importing sutra_mcp.server wrote to stdout: {quiet.stdout[:60]!r}")

    tools = await server.list_tools()
    names = [tool.name for tool in tools]
    if names != EXPECTED:
        problems.append(f"tools/list is {names}, not {EXPECTED} in that order")

    for tool in tools:
        if not (tool.description or "").strip():
            problems.append(f"{tool.name} has no description; the caller has nothing to route on")
        if tool.inputSchema.get("type") != "object":
            problems.append(f"{tool.name} inputSchema is not an object schema")

    return problems
```

**Line by line:**

- `-> list[str]`, not `bool`. A gate that says "no" is annoying; a gate that says which six things are
  wrong is a to-do list. Every finding names the thing and, where it can, shows the actual value.
- The first `try` **returns early** rather than appending. If `build_server` will not import there is
  nothing else to check, and twelve cascading findings would bury the one that matters.
- `except Exception` here is deliberate and is the one place in this day it is right: the point is to
  report *any* import failure as one finding, not to handle it. The `noqa` comment says so, which is
  the house rule for suppressing a lint.
- `subprocess.run([sys.executable, "-c", "import sutra_mcp.server"], capture_output=True)` — a
  **separate process**, because the check is whether importing writes to stdout and this process has
  already imported it. `capture_output=True` gives both streams; only `stdout` is inspected, because
  stderr is the legal place for a server to talk (Day 33's
  [2.3](../../../day-33-client-and-transports/parts/02-stdio/2.3-the-only-place-left-to-talk.md)).
- `check=False` — a non-zero exit from the child is not itself the finding; the finding is what it
  printed.
- `names != EXPECTED` compares **lists**, so order is part of the assertion.
  [3.2](../03-the-two-calls/3.2-the-same-order-every-time.md) is why that is not pedantry.
- `(tool.description or "").strip()` handles all three empty cases in one expression: `None`, `""`,
  and a docstring of only whitespace. [2.1](../02-function-to-declaration/2.1-the-decorator-that-writes-your-schema.md)
  measured that a missing docstring produces `""`, not `None`, and a check written against only
  `None` would have passed.
- `tool.inputSchema.get("type") != "object"` — the specification requires `inputSchema` to be a valid
  JSON Schema object, and an object schema is what every generated one is. Using `.get` rather than
  `[...]` means a schema with no `type` at all is a finding rather than a `KeyError`.

And the exit code, which is what makes it a gate rather than a report:

```python
def main() -> int:
    """Print the findings and return their count as the exit code."""
    problems = asyncio.run(findings())
    for problem in problems:
        print(f"- {problem}")
    print(f"findings: {len(problems)}")
    return 1 if problems else 0
```

**Line by line:**

- `asyncio.run(findings())` — `list_tools()` is a coroutine, so the checking is asynchronous and the
  entry point is not. One `asyncio.run` at the outside is the shape that keeps the rest simple.
- The findings are printed **before** the count, so the last line of output is always the summary and
  a human skimming a terminal sees the number.
- `return 1 if problems else 0` — one non-zero code for any number of problems. Exit codes are a
  yes/no channel; the detail is in the text above.
- `raise SystemExit(main())` at the bottom of the file turns the returned integer into the process's
  exit status, which is what `echo "exit: $?"` reads and what a CI step checks.

Run it today, before you have written anything:

```text
- sutra_mcp.server.build_server is not importable: ModuleNotFoundError: No module named 'sutra_mcp.server'
findings: 1
exit: 1
```

Measured on 2026-09-04. **That is the correct output right now.** `sutra_mcp/` has held nothing but an
empty `__init__.py` since Day 0, so the very first check fails and the early return stops there. As
you write `server.py` and `tools.py` the findings change shape — first the import, then the missing
`register_tools`, then the name, then the tool list — and each one is a smaller step than the last.
When it prints `findings: 0` and `exit: 0`, the six statements are true.

## When it breaks

The interesting failures are the ones you cause on purpose, because a gate you have never seen go red
is a gate you are trusting on faith. Four edits, four findings — each one measured on 2026-09-04
against a throwaway `sutra_mcp` written for the purpose, so the strings below are the script's, not a
description of them:

**Swap the two `register` lines** so `search_kb` is added first:

```text
- tools/list is ['search_kb', 'lookup_ticket'], not ['lookup_ticket', 'search_kb'] in that order
findings: 1
exit: 1
```

**Delete a docstring** from one tool:

```text
- search_kb has no description; the caller has nothing to route on
findings: 1
exit: 1
```

**Add `print("loading tools")` at the top of `sutra_mcp/tools.py`:**

```text
- importing sutra_mcp.server wrote to stdout: 'loading tools\n'
findings: 1
exit: 1
```

That third one is the check that pays for itself. A `print` at import time in a stdio server is Day
33's
[5.1](../../../day-33-client-and-transports/parts/05-failure-lab/5.1-the-log-line-that-ate-the-reply.md)
waiting to happen — one stray line on stdout either produces a parse error the client logs and
survives, or glues itself to the front of a real reply and destroys it, and which of the two you get
depends on a trailing newline. Neither is visible from inside the server. This check makes it visible
before the server is ever launched.

**Rename the server** to `sutra_mcp` with an underscore:

```text
- server name is 'sutra_mcp', not 'sutra-mcp'
findings: 1
exit: 1
```

That is [1.3](../01-the-server-object/1.3-the-name-is-an-identity.md)'s whole argument compressed into
one line: the name is in other people's configuration, and a check is the only thing that will notice
a one-character change to it.

The failure the gate does **not** catch is worth naming, because a gate that is trusted beyond its
scope is worse than none. It does not check that the descriptions are any *good* — only that they
exist. It does not check that `lookup_ticket` returns the right ticket. It does not check that error
messages are scrubbed. Those are `TODO(me)` extensions in the build brief, and the honest statement
of what this script proves is: the package is importable, correctly shaped, quiet, and offering
exactly the two tools it should, in a stable order, each with something a caller can read.

## In production

**What a professional writes instead:** the same six assertions as a `pytest` module rather than a
script, so they run inside `./m check` with everything else and a failure names the assertion. The
script form exists here because it can be run before the package exists, which a test collection
cannot — and Day 45's `tools/mcp_audit.py` is where checks like these graduate into a phase gate with
its own line in `./m check`.

**What degrades at scale:** the fixed list. `EXPECTED = ["lookup_ticket", "search_kb"]` is exactly
right for two tools and becomes a merge conflict once four days are adding tools to the same server.
The version that survives keeps the list in one place that both the server and the gate import, so
adding a tool is one edit and the assertion still means something. It is deliberately not written
that way today, because with two tools a shared constant is indirection without benefit.

**The failure mode that only appears with real traffic:** the check that runs in an environment
nothing else does. A gate that imports your package with a different working directory, a different
`PATH`, or without the environment variables the real server has will pass on a package that cannot
start, or fail on one that is fine. The subprocess check here is the smallest useful version of the
right instinct — launch it the way it will actually be launched, and look at what comes out.

**The review comment a senior engineer leaves:** *"this asserts the tool list as a sorted comparison,
so a tool added on any later day fails the gate with a message about ordering. That is the right
default — a new tool on our data boundary should be something a human acknowledges — but say so in a
comment, or the next person will 'fix' it with a set comparison and we will stop noticing."*

**The interview question:** *"what did you actually assert about the MCP server you built?"* The
honest answer: *"Six things, in a script that exits non-zero. That the package imports and exposes
`build_server`; that it follows the `register_<kind>(server)` convention so later modules can hook
in; that the server's name is the exact string other people's configuration holds; that importing it
writes nothing to stdout, because stdout is the protocol channel and one stray line either gets
logged as a parse error or destroys a reply; that `tools/list` is exactly the two tools we expect, in
order, because order is what a client's cache and a prompt cache key on; and that every tool has a
non-empty description and an object input schema, because the declaration is the only thing a caller
gets. It was red when we started — the package was empty — and it stayed useful afterwards because
every one of those can be broken by an ordinary edit. What it does not check is whether the
descriptions are good, and I would not pretend otherwise."*
