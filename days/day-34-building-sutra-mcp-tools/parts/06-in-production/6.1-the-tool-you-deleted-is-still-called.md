# 6.1 — 💥 The tool you deleted is still being called

## One-line answer

The `ttlMs` you chose is also how long a client may keep calling a tool you removed, so deleting a
tool in one deployment is a deliberate decision to serve errors for that long — and doing it in two
deployments costs nothing but patience.

## The story

The 14C is withdrawn on a Monday.

The company knows. The drivers know. The website is updated the same morning. What is not updated is
the enamel flag on the pole at the stop, which still says **14C** in white on green, because
replacing the flags is a different team with a different work order and about four hundred poles.

So people wait. Not confused people — people who read the sign, which is the only thing at that stop
telling them anything, and which says a bus comes here. They wait ten minutes, then twenty. Some walk
away, some ring somebody, and one of them writes to the company to complain that the 14C did not
come, which is true.

The company that did this well the previous year did it differently. For two weeks before the
withdrawal, the flag had a paper sleeve over the number: *"14C withdrawn from 3 March — use the 21
from the stop opposite."* Then the bus stopped running. Then, a month later, somebody came and
changed the flag.

Same withdrawal. Same flags. The difference was that for the fortnight when the sign was wrong, the
sign said so.

## The idea in plain language

[3.1](../03-the-two-calls/3.1-the-list-and-who-may-keep-it.md) gave clients permission to keep the
tool list for `ttlMs` milliseconds. This part is the bill for that permission.

A client that cached your list at ten o'clock with a one-hour TTL is entitled to offer those tools to
its model until eleven. If you remove a tool at half past ten, then for the next half hour a model
somewhere has a tool in front of it that no longer exists, and it will call it, because a tool list
is the model's menu and nothing has told it otherwise.

So **removing a tool is two deployments, not one**:

1. **Deployment one keeps the tool and empties it.** The name, the schema and the entry in
   `tools/list` all stay. The body stops doing anything and returns a sentence saying the tool is
   retired and what to do instead. This is the paper sleeve.
2. **Deployment two, at least one full TTL later, removes it.** By then every cached list has
   expired at least once and every client has fetched a list without it.

The specification supports a faster path but does not remove the need for the slow one. A server that
declares `listChanged: true` may notify clients, and the caching page says the notification
*"invalidates the cached response and it should be considered immediately stale"*. That is real and it
is not a guarantee: notifications reach clients that subscribed, and Day 33's
[1.3](../../../day-33-client-and-transports/parts/01-the-connector/1.3-before-the-model-sees-a-tool.md)
established that ADK — Sutra's own client — does not subscribe. Plan for the TTL; treat the
notification as a way to shorten it for the clients that listen.

## Why Sutra needs it

Because Sutra removes a tool on **Day 39**, and it will remove more later.

Day 39 replaces the dictionary-backed `lookup_ticket` with a SQL-backed one. If the replacement keeps
the name and the schema, nothing here applies — that is a body change, which is invisible from
outside and is exactly the property MCP was worth a network hop for. If it does not, the old name has
to go through this two-step, and the decision has to be made before the first deployment rather than
after somebody notices.

It also decides a number that has been outstanding since Day 32. Its
[3.3](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md) left
you a `TODO(me)` to choose `sutra_mcp`'s `ttlMs` and to write down what must happen before a tool is
deleted. This part is the second half of that answer, and the two halves constrain each other: a
long TTL saves requests and lengthens the retirement window, and a short TTL does the reverse. There
is no correct number, only a number you have chosen on purpose.

## The mechanism

`lab/stale.py` runs the same removal two ways. The tool it removes is `close_ticket`, which is a
realistic thing to retire: it changes something, and moving that action to another system is the most
common reason a tool disappears.

```python
if with_close and close_refuses:

    @server.tool(name="close_ticket")
    def close_ticket_tombstone(ticket_id: str) -> str:
        """Retired. Closing tickets moved to the workflow service on 2026-09-04."""
        return (
            "close_ticket has been retired and does nothing. Tell the user the "
            "ticket must be closed in the workflow service; do not retry."
        )
```

**Line by line:**

- `@server.tool(name="close_ticket")` — the **name is pinned explicitly**, so the Python function can
  be called `close_ticket_tombstone` for the benefit of whoever reads the file, while the wire name
  stays exactly what cached clients hold. Renaming the wire name here would defeat the entire
  exercise.
- The docstring is the description, so it goes on the wire and into the model's context. It says
  *"Retired"* first, because a model skimming a tool list needs the disqualifying word at the front —
  Day 28's
  [2.1](../../../day-28-progressive-disclosure-design/parts/02-descriptions-as-routing/2.1-a-description-is-a-routing-row.md)
  is why the first clause of a description does the routing.
- It names a **date**. Somebody will read this in six months and need to know whether it is safe to
  delete; a date in the description is the cheapest possible answer.
- The body **returns** rather than raising, so `isError` stays `false`
  ([4.1](../04-two-kinds-of-no/4.1-the-tool-said-no.md)). A retirement is not a failure and it must
  not read as one, because a model responds to failures by retrying.
- *"do not retry"* is the instruction, and *"Tell the user the ticket must be closed in the workflow
  service"* is the alternative. A tombstone with no forwarding address just moves the dead end.
- The tool still takes `ticket_id: str`, unchanged. A client calling with the old schema must get a
  valid call, not a validation error.

Run both arms. **One deployment**, on 2026-09-04:

```text
client cached tools/list : ['lookup_ticket', 'close_ticket']  (ttlMs=3600000, i.e. one hour)
deploy 1 of 1            : close_ticket deleted outright

the model still has close_ticket in its list and calls it:
  isError : True
  content : Unknown tool: close_ticket

what tools/list would say now : ['lookup_ticket']
what the client is using      : ['lookup_ticket', 'close_ticket']
```

**Two deployments**, same day, same removal:

```text
client cached tools/list : ['lookup_ticket', 'close_ticket']  (ttlMs=3600000, i.e. one hour)
deploy 1 of 2            : close_ticket kept, body replaced with a refusal

the model still has close_ticket in its list and calls it:
  isError : False
  content : close_ticket has been retired and does nothing. Tell the user the ticket must be closed in the workflow service; do not retry.

what tools/list would say now : ['lookup_ticket', 'close_ticket']
what the client is using      : ['lookup_ticket', 'close_ticket']
```

Same removal, same cache, and two completely different experiences for the person on the other end.

In the first arm the model gets `isError: True` and the words *"Unknown tool"*. It has no idea what
to do with that, and the sensible thing a model does with a failed tool call is try again — which
fails identically, for up to an hour. The user is told nothing useful, and the transcript records a
tool that broke.

In the second arm the model gets a normal result that tells it the tool is gone, tells it not to
retry, and tells it what to say. The user is told to close the ticket in the workflow service, which
is the actual truth, an hour before the tool physically disappears.

```mermaid
timeline
    title Removing close_ticket, two ways
    section One deployment
        10:00 : client caches [lookup_ticket, close_ticket]
        10:30 : tool deleted
        10:31 : "Unknown tool", isError true - repeats until 11:00
        11:00 : TTL expires, client re-fetches, sanity returns
    section Two deployments
        10:00 : client caches [lookup_ticket, close_ticket]
        10:30 : tool kept, body becomes a tombstone
        10:31 : "retired, do not retry, use the workflow service"
        11:30 : one full TTL later, tool deleted for real
```

One extra deployment, and the wrong hour becomes an informative hour.

## When it breaks

Read the first arm's reply again, because it contains the second trap of this part:

```text
  isError : True
  content : Unknown tool: close_ticket
```

`isError: True`. Not a JSON-RPC error. [4.2](../04-two-kinds-of-no/4.2-the-call-never-happened.md)
established that the specification puts *unknown tool* in the protocol-error category and that the
pinned SDK reports it as a tool execution error instead. Here is the consequence in a real workflow:
**a client cannot detect a stale tool list by branching on `isError`.** The obvious recovery —
*"if the call failed because the tool is unknown, re-fetch `tools/list`"* — never fires, because from
the client's point of view this is a tool that ran and failed.

There are two honest ways out and both are worth knowing:

- Match the message text. It works, and it is matching on a string produced by a library, which will
  change one day with no warning.
- Re-fetch `tools/list` on **any** unexpected tool failure and compare. Cheap, version-proof, and
  precisely what the caching page suggests: *"Clients **MAY** re-fetch before the TTL expires if they
  have reason to believe the data has changed (e.g., receiving an unexpected error on a tool call
  indicating the method was not found or the parameters were invalid)."*

The third break is the one nobody plans for, because it does not involve deleting anything:

```text
tools/list, before : ["lookup_ticket", "search_kb", "close_ticket"]
tools/list, after  : ["lookup_ticket", "search_kb", "close_ticket"]
```

Identical lists — and `close_ticket`'s `inputSchema` gained a required `reason` parameter. Every
cached client is calling it with the old schema, and every one of those calls now fails validation
for an entire TTL. **Adding a required parameter is a removal**, in every way that matters here, and
it does not look like one in a diff. New parameters are optional first, required a TTL later, or they
are a new tool name.

## In production

**What a professional writes instead:** a written retirement procedure that names the TTL. Announce,
tombstone, wait one full TTL plus a margin, delete. The tombstone's description carries the date and
the replacement. The same procedure covers making a parameter required, which is the case teams
forget.

**What degrades at scale:** the number of caches between you and the model. Your TTL, the client
library's own tool-list cache — ADK's `tool_list_cache_ttl_seconds`, in **seconds** where the
protocol's field is **milliseconds** — and any shared gateway holding a `cacheScope: "public"`
response. The real window is the sum of the longest chain, not your number, and the only way to know
it is to write the chain down. Day 33's
[1.3](../../../day-33-client-and-transports/parts/01-the-connector/1.3-before-the-model-sees-a-tool.md)
left the client half of that as its own `TODO(me)` for exactly this reason.

**The failure mode that only appears with real traffic:** the long-running client. A cache expires
when it is next consulted, not on a timer — the caching page is explicit that clients *"SHOULD NOT
treat TTL as a polling interval that triggers automatic background refetches"*. So a process that has
been up for a week and has an idle period may hold a list far longer than the TTL suggests, and a
client that serves a stale response on a re-fetch error — which the spec also permits — can hold one
through your entire deployment window.

**The review comment a senior engineer leaves:** *"this pull request deletes `close_ticket` and its
registration in one commit. Our tool list has an hour of TTL, so this ships an hour of 'Unknown tool'
errors to every client that listed us before the deploy. Split it: this deploy keeps the tool and
returns a retirement message naming the workflow service, and a follow-up next week removes it."*

**The interview question:** *"how do you remove a tool from an MCP server?"* The honest answer: *"In
two deployments, because the list is cacheable. The first keeps the name and the schema and replaces
the body with a message saying the tool is retired, what to use instead, and not to retry — returned
normally, not as an error, so the model does not treat it as something to try again. The second
removes it, at least one full TTL later. We measured the difference: deleting in one step gives every
cached client 'Unknown tool' with `isError` true until its cache expires, and the model retries
because that is what a failed call looks like. The subtlety is that a client cannot reliably detect
this by checking `isError` — our SDK reports unknown tool as a tool execution error rather than a
protocol error — so the client-side rule is to re-fetch the tool list on any unexpected tool failure.
And the case people miss is that adding a required parameter is a removal too."*
