# 5.2 — What your server actually answers

## One-line answer

Send the four requests yourself and read the replies: the server you built refuses `server/discover`,
refuses business before a handshake, and negotiates `2025-11-25` — so it is a handshake-era server,
and knowing that from its own mouth is worth more than knowing it from a changelog.

## The story

You are shown a flat and it looks fine, so you start turning things on.

The kitchen tap runs, hot after a while. The bathroom tap runs cold and stays cold. The shower head
does nothing at all for about four seconds and then works. There is a switch by the door that
operates nothing you can find. The agent, who is standing behind you, says the boiler is new.

Nothing the agent said was untrue. The boiler probably is new. But you now know three things about
this flat that no description would have told you, because you turned the handles yourself and
watched what came out. And the one that will matter on a Tuesday morning in December is the bathroom
tap, which nobody would have thought to mention because everybody who lives with it has stopped
noticing.

## The idea in plain language

There are three ways to find out which revision of MCP a server speaks, and they are not equally
reliable.

**Read the specification.** Tells you what a compliant server does. Says nothing about yours.

**Read the library's version.** Tells you what the library claims to support. Closer, and still a
document about a document.

**Send the request and read the reply.** Tells you what actually happens. This is the only one of the
three that can surprise you, which is exactly why it is worth doing.

`lab/wire.py` does the third. It launches your own `lab/serve.py` as a child process — the way a host
would — and writes raw newline-delimited JSON-RPC into its standard input, with no SDK client in the
way. Four probes, each against a **freshly launched server**, so that no probe can be affected by the
one before it:

1. `server/discover` with modern `_meta` — the mandatory RPC of the 2026-07-28 revision.
2. `tools/list` with modern `_meta` — business, straight in, no handshake.
3. `initialize` — the ritual the 2026-07-28 revision deleted.
4. `initialize`, then `notifications/initialized`, then `tools/list` — the same question after the
   ritual.

## Why Sutra needs it

Because this day writes the server that Days 35 to 45 extend, and every one of those days inherits
whatever this server actually is rather than whatever the plan says it should be.

Day 32 recorded the finding as a version number: the pinned SDK reports
`LATEST_PROTOCOL_VERSION = "2025-11-25"` while the specification is at `2026-07-28`. Its
[5.1](../../../day-32-mcp-stateless-core/parts/05-failure-lab/5.1-the-tutorial-from-four-months-ago.md)
also left a `TODO(me)` addressed to this day: *write the assertion Day 34 needs — the SDK's supported
versions contain the revision Sutra targets, and decide what it should say when it goes red.* You
cannot write that assertion honestly without first knowing what the server does, message by message,
rather than what the constant says.

There is also a plainer reason. A day that told you *"your server speaks an older revision"* and
never showed you would be asking you to take its word for it, which is the one thing this curriculum
is built not to do.

## The mechanism

The probe function, which is the whole client:

```python
def probe(label: str, messages: list[dict]) -> None:
    """Launch one server, send every message in order, print each reply and its stderr."""
    print(f"--- {label} ---")
    with tempfile.TemporaryFile() as errlog:
        child = subprocess.Popen(
            [sys.executable, str(HERE / "serve.py")],
            stdin=subprocess.PIPE,
            stdout=subprocess.PIPE,
            stderr=errlog,
        )
        try:
            for message in messages:
                child.stdin.write((json.dumps(message) + "\n").encode("utf-8"))
                child.stdin.flush()
                if "id" not in message:
                    continue  # a notification: no reply is coming, do not wait for one
                raw = child.stdout.readline()
                reply = raw.decode("utf-8").strip() if raw else "(the server closed its stdout)"
                print(f"--> {message['method']}")
                print(f"<-- {reply[:200]}")
        ...
```

**Line by line:**

- `subprocess.Popen([sys.executable, ".../serve.py"], ...)` — the server is launched exactly the way
  a host launches it, as a child process with pipes for its standard streams. Day 33's
  [2.1](../../../day-33-client-and-transports/parts/02-stdio/2.1-connecting-is-launching.md) is where
  that equivalence was established: on stdio, connecting *is* launching.
- `stderr=errlog` sends the child's stderr to a temporary file rather than a pipe. A pipe would be a
  deadlock waiting to happen — the buffer fills, the child blocks writing, and the parent is still
  waiting to read stdout.
- `json.dumps(message) + "\n"` — compact JSON and exactly one newline, which is the entire stdio
  framing rule from Day 33's
  [2.2](../../../day-33-client-and-transports/parts/02-stdio/2.2-one-message-per-line.md).
- `child.stdin.flush()` — a pipe is block-buffered, so without this the message sits in the parent's
  buffer and the child waits forever for a request that was written but not sent.
- `if "id" not in message: continue` — a notification has no `id`, so no reply is coming.
  `readline()` on a notification would block until the next reply or forever.
- `raw.decode(...) if raw else "(the server closed its stdout)"` — an empty read means the stream
  ended, which is different from an empty reply and has to be reported differently.
- **A new child per probe**, because a server that has refused one request may be in a state that
  changes how it answers the next. Isolation is what makes the output reproducible.

Run it. All four probes, on 2026-09-04:

```text
--- the mandatory 2026-07-28 RPC ---
--> server/discover
<-- {"jsonrpc":"2.0","id":1,"error":{"code":-32602,"message":"Invalid request parameters","data":""}}
(stderr) Failed to validate request: 31 validation errors for ClientRequest

--- business, straight in ---
--> tools/list
<-- {"jsonrpc":"2.0","id":2,"error":{"code":-32602,"message":"Invalid request parameters","data":""}}
(stderr) Failed to validate request: Received request before initialization was complete

--- the deleted handshake ---
--> initialize
<-- {"jsonrpc":"2.0","id":3,"result":{"protocolVersion":"2025-11-25","capabilities":{"experimental":{},"prompts":{"listChanged":false},"resources":{"subscribe":false,"listChanged":false},"tools":{"listCha

--- the handshake, then business ---
--> initialize
<-- {"jsonrpc":"2.0","id":3,"result":{"protocolVersion":"2025-11-25",...
--> tools/list
<-- {"jsonrpc":"2.0","id":4,"result":{"tools":[{"name":"lookup_ticket","description":"Fetch the full text of one support ticket by its id.\n\n        Use this first whenever the user names or implies a sp
```

Four probes, four findings.

**`server/discover` is not implemented, and the reason is in the stderr.** *"31 validation errors for
ClientRequest"* means the SDK tried to fit the message into its union of known client requests and
failed against every member. `server/discover` was added in the 2026-07-28 revision and does not
exist in this SDK — a `grep` for the string in `mcp/types.py` finds nothing. Day 32's
[2.4](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.4-server-discover-the-optional-question.md)
established that implementing it is a **MUST** for a server. Yours does not. That is not something
you can fix by writing better code today; it is a property of the pin.

**Business straight in is refused**, with the state machine from
[5.1](5.1-the-handshake-that-is-now-history.md) doing exactly what it was built to do. The reply says
*"Invalid request parameters"*; the stderr says *"Received request before initialization was
complete"*. Only one of those is true and the caller cannot see it.

**The handshake works and negotiates `2025-11-25`.** The one probe that is supposed to be history is
the only one that gets a result. Note the reply also carries `capabilities` and `serverInfo` — the
information a modern client would get from `server/discover` — which is the sense in which the old
handshake was doing three jobs at once.

**After the handshake, `tools/list` works**, and the fourth probe's request carried **no `_meta` at
all**. That is the clearest statement of the difference between the two eras in this whole day: in
the handshake era the context lives on the connection, so a request needs to carry nothing; in the
stateless era the connection carries nothing, so every request carries its own context.

The library's own numbers, read on 2026-09-04, agree with every one of those observations:

```text
mcp        : 1.29.1
LATEST     : 2025-11-25
SUPPORTED  : ['2024-11-05', '2025-03-26', '2025-06-18', '2025-11-25']
DEFAULT    : 2025-03-26
```

`2026-07-28` is not in that list. PyPI's current `mcp`, queried the same day, is `2.1.1`, and Day 32
verified that it speaks `2026-07-28`. **Nothing is bumped here**: a version change is a plan decision
with a `docs/PACKAGES.md` row behind it and Principle 14 says the plan is amended before the code.
What this day owes is honesty about what it built, and this is it.

## When it breaks

The break is believing a constant instead of a reply. Here is the check that looks sufficient and
is not:

```python
from mcp.shared.version import SUPPORTED_PROTOCOL_VERSIONS

assert "2026-07-28" in SUPPORTED_PROTOCOL_VERSIONS
```

**Line by line:**

- It imports from `mcp.shared.version`, not `mcp.types` — `SUPPORTED_PROTOCOL_VERSIONS` is not
  re-exported, and `from mcp.types import SUPPORTED_PROTOCOL_VERSIONS` raises
  `AttributeError: module 'mcp.types' has no attribute 'SUPPORTED_PROTOCOL_VERSIONS'`. Verified on
  2026-09-04.
- The assertion is **correct today** and it goes red, which is what you want from a check.
- What it does not tell you is anything about *your* server. It reports on a library. A server built
  on that library could still be missing `server/discover`, could still hold session state, and could
  still be wrong in a way the constant cannot see.
- And it is brittle in the wrong direction: it goes green the moment somebody upgrades the pin, which
  is the moment you most want to look at the four probes again.

The other break is subtler and it is why `wire.py` launches a fresh child per probe. Send
`server/discover` and then `tools/list` down **one** connection and the second reply may not arrive
at all — the server has already failed a validation on that session, and what happens next depends on
the SDK's internal task group rather than on the protocol. An earlier draft of this lab did exactly
that and produced two different transcripts on two runs. A probe that is not reproducible is not a
measurement.

## In production

**What a professional writes instead:** a conformance probe that runs in CI. Six or eight requests
covering the methods you claim to implement, each asserting a shape rather than a byte string, run
against the server the way a host runs it. It is not a unit test — it launches a process and talks
to it — and it is the only test that catches "the library changed how it answers" on a dependency
bump.

**What degrades at scale:** the number of things that can disagree. Your server, the SDK, the client
SDK, the gateway and the specification are five documents with five release schedules. A probe
against the running thing is the only artefact that reflects all five at once, and it is the reason
integration environments exist.

**The failure mode that only appears with real traffic:** the mixed fleet. Half your callers are
handshake-era clients and half are current, and a server that answers both is answering two
protocols. The measurement that matters then is not *"which revision do we speak"* but *"what
fraction of live requests carry `_meta` and what fraction opened with `initialize"* — a question
about traffic, not about libraries, and one that no constant can answer.

**The review comment a senior engineer leaves:** *"the ticket says this is a 2026-07-28 server. It
does not implement `server/discover`, which is a MUST, and it refuses `tools/list` until a handshake
it should not need. Neither is fixable at our layer — the pin does not support the revision — so
change the ticket, put the finding in the day's notes, and open the version bump as its own
decision."*

**The interview question:** *"how do you know which protocol revision your server speaks?"* The
honest answer: *"We asked it. We launch it as a child process, write raw JSON-RPC into its stdin and
read the replies — one fresh process per probe so the results are reproducible. Ours refuses
`server/discover`, which the current revision makes mandatory, refuses `tools/list` until it has been
through the old `initialize` handshake, and negotiates `2025-11-25`. So it is a handshake-era server,
regardless of what we intended, because the SDK version we pin tops out there. The reason we probe
rather than read the library's constant is that the constant describes the library and the probe
describes the thing that is running — and the reply we found most useful was one where the error sent
to the caller said 'invalid request parameters' while the server's own stderr said 'received request
before initialization was complete'. Only one of those is true."*
