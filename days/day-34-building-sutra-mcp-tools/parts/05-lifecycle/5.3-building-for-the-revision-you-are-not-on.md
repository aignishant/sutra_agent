# 5.3 — Building for the revision you are not on

## One-line answer

You cannot make `mcp==1.29.1` speak `2026-07-28`, and you can write every line of your server so
that the day the pin moves is a dependency bump rather than a rewrite — which means holding no state,
`stateless_http=True`, and knowing exactly what that flag does and does not do.

## The story

They resurface the road outside and, before the tarmac goes down, a team spends two days laying empty
plastic pipe along one side of it.

Nothing goes through the pipe. There is no fibre in this area and there is no date for any. The pipe
is capped at both ends, the trench is filled, the tarmac goes over it, and for four years it does
precisely nothing.

Then the fibre arrives. On your street it is a van, a morning, and a man pulling a cable through a
pipe that is already there. Two streets over, where nobody laid the pipe, it is the same road dug up
again — barriers, a month, and the surface never quite matches afterwards.

The people who laid the pipe did not know when the fibre was coming. They knew what shape it would
need when it did, and that the cheapest moment to make that shape was while the road was already
open.

## The idea in plain language

There are two kinds of gap between your server and the current revision, and only one of them is
your problem.

**Things the library must provide.** `server/discover`, `resultType` on every result, reading
`_meta` for the per-request protocol version, sending `ttlMs` and `cacheScope` natively. These are
message types and framing. You cannot add them from your own code without reimplementing the
library, and attempting it is how a codebase acquires a fork nobody wants to maintain.

**Things your own code decides.** Whether a handler reads state that was stored by a previous
request. Whether the tool list is sorted. Whether errors are honest and scrubbed. Whether long-lived
context travels in the payload as an explicit handle. **None of these depends on the pin**, and every
one of them is exactly what the 2026-07-28 revision requires.

So the strategy is: accept the first list, and get the second list right today. That is the empty
pipe. When the pin moves the second list is already correct, and the change is a dependency bump plus
whatever the library newly offers.

## Why Sutra needs it

Because the pin will move, and Days 35 to 45 will all have been written on top of whatever you do
now.

Day 43 is the day this is cashed in: *"stateless by default — deploy-shaped servers"*, where any
instance answers any request. If the handlers written today read module-level state, Day 43 is a
refactor of six days' worth of the learner's own code. If they do not, Day 43 is a deployment
exercise, which is what it is meant to be.

There is a smaller, sharper reason too. Day 32's
[5.1](../../../day-32-mcp-stateless-core/parts/05-failure-lab/5.1-the-tutorial-from-four-months-ago.md)
left a `TODO(me)` addressed to this day: write the assertion that says whether the SDK supports the

the fibre arrived.

## The mechanism

Start with the one flag that is already in `build_server()`:

```python
server = FastMCP(
    "sutra-mcp",
    instructions="...",
    stateless_http=True,
)
```

**Line by line:**

- `stateless_http=True` is a constructor argument on `FastMCP`, defaulting to `False`. Verified in
  `.venv/Lib/site-packages/mcp/server/fastmcp/server.py` on 2026-09-04.
- It sets `Settings.stateless_http`, which is read in exactly one place — the Streamable HTTP session
  manager — as `stateless=self.settings.stateless_http`.
- In that manager, `stateless` means *"creates a completely fresh transport for each request with no
  session tracking"*, quoting the manager's own docstring. There is no session table, so nothing to
  pin a caller to.
- It also changes the state machine from [5.1](5.1-the-handshake-that-is-now-history.md). In
  `mcp/server/session.py`:
  `self._initialization_state = InitializationState.Initialized if stateless else InitializationState.NotInitialized`.
  A stateless session **starts** in the finished state, so the handshake gate never refuses anything.
- **It does nothing at all on stdio.** `run_stdio_async` calls `self._mcp_server.run(read, write,
  create_initialization_options())` and passes no `stateless` argument, so the default `False`
  applies. That is why [5.2](5.2-what-your-server-actually-answers.md)'s probes are still refused:
  they go over stdio.

And here is the SDK's own description of what "stateless" means in this version, from the low-level
`run` method's parameter comment, read the same day:

```text
# When True, the server is stateless and
# clients can perform initialization with any node. The client must still follow
# the initialization lifecycle, but can do so with any available node
# rather than requiring initialization for each connection.
```

Read the middle sentence twice. *"The client must still follow the initialization lifecycle."* This
is a halfway house: the handshake still happens, it just no longer pins you to an instance. It is
`2025-11-25`'s answer to the problem `2026-07-28` solved by deleting the handshake. Passing the flag
is right — it gets you the deployment property a revision early — and calling your server stateless
because of it would be overclaiming.

Now the half that is entirely yours. This is what "hold no state" means in practice, as a rule you
can check by reading:

```python
# Wrong: the server remembers something about a caller.
_LAST_TICKET: dict[str, str] = {}


@server.tool()
def remember_ticket(ticket_id: str) -> str:
    """Remember which ticket we are working on."""
    _LAST_TICKET["current"] = ticket_id
    return f"Working on {ticket_id}."


@server.tool()
def summarise_current() -> str:
    """Summarise the ticket we are working on."""
    return TICKETS.get(_LAST_TICKET.get("current", ""), "No ticket selected.")
```

**Line by line:**

- `_LAST_TICKET` is a module-level dictionary that a handler writes to. That is a session, and the
  leading underscore does not change what it is. Day 32's
  [3.4](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md)
  named this pattern precisely: a module-level dict in a server is a session by another name.
- `summarise_current()` takes **no arguments**, which is the tell. A tool with no arguments that
  returns different answers at different times is reading something it was not given.
- On one process this works and the tests pass. On three instances behind one address,
  `remember_ticket` lands on instance 1 and `summarise_current` lands on instance 2, which has never
  heard of the ticket and says *"No ticket selected."*
- The specification forbids the shape, not just the deployment:
  *"Servers **MUST NOT** rely on prior requests over the same connection to establish context"*, and
  *"State that needs to span multiple requests … **MUST** be referenced by an explicit identifier the
  client passes on each request"*
  (`https://modelcontextprotocol.io/specification/2026-07-28/basic/index`, read 2026-09-04).

The version that survives a deploy is the boring one:

```python
@server.tool()
def summarise_ticket(ticket_id: str) -> str:
    """Summarise one support ticket. Pass the id you want; nothing is remembered."""
    return TICKETS.get(ticket_id.strip(), f"No ticket with id {ticket_id!r}.")
```

**Line by line:**

- The ticket id is an **argument**, so the request carries everything the handler needs. Any instance
  can answer it.
- *"nothing is remembered"* is in the description on purpose, because a model reading a tool list
  will otherwise assume a stateful sequence is available and plan for one.
- The tool takes exactly one call to do what the other pair took two calls and a shared dictionary to
  do, which is the usual outcome: removing server state usually removes a tool as well.
- Where genuine cross-call state is unavoidable — an open transaction, a long job — the answer is an
  explicit handle returned by one tool and passed to the next, which is the spec's own *Stateful
  Tools* guidance and **Day 36's** subject.

So the empty pipe, written out as a table. Everything on the left is decided by your code and is
already correct; everything on the right arrives with the pin.

| Yours today, and still right after the bump | The library's, and only after the bump |
| --- | --- |
| no module-level mutable state in handlers | `server/discover` implemented |
| every handler's inputs are its arguments | `resultType` on every result |
| cross-call state as an explicit handle | reading `_meta` per request |
| `tools/list` sorted by name ([3.2](../03-the-two-calls/3.2-the-same-order-every-time.md)) | `ttlMs` / `cacheScope` sent natively ([3.1](../03-the-two-calls/3.1-the-list-and-who-may-keep-it.md)) |
| descriptions written for the model ([2.2](../02-function-to-declaration/2.2-the-schema-is-all-they-get.md)) | `-32020` / `-32021` / `-32022` emitted correctly |
| `isError` used correctly ([4.1](../04-two-kinds-of-no/4.1-the-tool-said-no.md)) | the `initialize` handshake gone |
| error messages scrubbed ([4.3](../04-two-kinds-of-no/4.3-the-message-that-escaped.md)) | `Mcp-Method` / `Mcp-Name` header validation |

Six rows on the left, and not one of them needs a newer library.

## When it breaks

The break is silencing the cap on the pipe. Here is the assertion Day 32 asked this day to write,
and the tempting wrong version of it:

```python
from mcp.shared.version import SUPPORTED_PROTOCOL_VERSIONS

SUTRA_TARGET_REVISION = "2026-07-28"


def sdk_speaks_target() -> bool:
    """True when the installed SDK supports the revision Sutra's documents are written against."""
    return SUTRA_TARGET_REVISION in SUPPORTED_PROTOCOL_VERSIONS
```

**Line by line:**

- `from mcp.shared.version import ...` — the constant is not on `mcp.types`, and importing it from
  there raises `AttributeError`. Verified on 2026-09-04.
- `SUTRA_TARGET_REVISION` is a constant of **Sutra's**, not the library's. It records what this
  curriculum's documents were written against, which is the thing the check is really about.
- The function returns `False` today. That is correct and it must be allowed to stay `False`.
- The wrong fix, which somebody will propose the first time a build goes red, is
  `SUTRA_TARGET_REVISION = "2025-11-25"`. That turns the check green by making it agree with the
  library, which means it can never tell you anything again — it becomes an assertion that the
  library is the library.
- The other wrong fix is deleting it, on the reasonable-sounding grounds that a check nobody can
  make pass is noise. It is not noise; it is the only thing in the repository that will notice the
  day the gap closes.

The failure mode with no error text at all is the one on the other side of the flag:

```text
stateless_http=True, and the server is run over stdio
```

Nothing warns you. The flag is accepted, the server starts, and the setting is read by a code path
that never runs. A team that ships a stdio server with that flag set has a comment in the codebase
that says stateless and a state machine that says otherwise, and the two will not be reconciled until
somebody probes it — [5.2](5.2-what-your-server-actually-answers.md).

## In production

**What a professional writes instead:** the flag set, a comment beside it naming exactly which
transport it affects, and a test that fails if any module in the package grows a mutable module-level
binding that a handler writes to. That test is ten lines of `ast` walking and it is worth more than
any amount of care, because the state does not arrive as a design decision — it arrives as a cache
somebody added on a Friday for a good reason.

**What degrades at scale:** the deployment property, and it degrades all at once rather than
gradually. One instance hides every state bug perfectly. Two instances expose all of them
simultaneously, as intermittent wrong answers with no error, and the incident is reported as
*"sometimes it forgets"* — which is the hardest sentence in support to act on, because it is also
what a correct stateless system looks like to somebody who expected a session.

**The failure mode that only appears with real traffic:** the cache that is a session. Nobody writes
`_LAST_TICKET`. What they write is `@lru_cache` on a lookup, or a dict of pre-parsed documents, and
those are genuinely caches — until one of them is keyed on something caller-specific. A cache keyed
on data is fine on any number of instances. A cache keyed on a caller is a session, and the two look
identical in a diff.

**The review comment a senior engineer leaves:** *"we set `stateless_http=True` and we run this over
stdio, where that flag is read by a code path we never execute. Keep the flag, because the HTTP
deployment is coming, and put a comment on it saying it affects the Streamable HTTP transport only —
otherwise the next person reads it as a claim about the whole server and stops looking for session
state."*

**The interview question:** *"you were pinned to an SDK a revision behind the spec — what did you
do?"* The honest answer: *"Split the gap in two. The parts that are message types and framing —
`server/discover`, `resultType`, per-request `_meta`, native cache hints — we could not fix without
forking the library, so we wrote down that we do not have them. The parts our own code decides — no
server-side session state, sorted tool lists, model-facing descriptions, correct `isError` use,
scrubbed error messages — we got right immediately, because none of those depends on the library
version and all of them are what the new revision requires. We set the SDK's stateless flag with a
comment saying it only affects the HTTP transport and that even in that mode the handshake still
happens, so it is a deployment property rather than compliance. And we kept a check asserting that
the installed SDK supports our target revision. It is red, deliberately, and the two ways to make it
green are both wrong: lowering the target so it agrees with the library, or deleting it. It is how we
will find out the day the gap closes."*
