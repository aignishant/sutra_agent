# 2.1 — One line per happening

## One-line answer

Four plugin hooks — `before_run`, `on_event`, `on_tool_error`, `after_run` — produce a complete
six-line record of one invocation, and the plugin that writes them decides nothing: it is a flight
recorder, not a policy.

## The story

The minicab has a tracker box under the dashboard.

It does not drive. It does not choose the route, refuse a fare, or tell the driver to slow down. All
it does is write down where the car was, how fast, and when the brakes went on hard.

The month it earned its keep was the month a passenger claimed the driver had gone the long way
round. Nobody argued. Somebody printed the route.

## The idea in plain language

Day 21 established that ADK offers an exception to plugin hooks at three levels
([21.2.4](../../../day-21-errors-surface-not-swallow/parts/02-four-hooks/2.4-the-ladder.md)). Those
were the *error* hooks. The plugin surface has lifecycle hooks too, and together they cover
everything an invocation does:

| Hook | Fires | One line saying |
| --- | --- | --- |
| `before_run_callback` | once, at the start | `run_start` — who, which agent |
| `on_event_callback` | **once per event** | `event` — the author, any tool calls, whether it is final |
| `on_tool_error_callback` | per failing tool call | `tool_error` — the tool, the kind, the action taken |
| `after_run_callback` | once, at the end | `run_end` |

The one worth pausing on is `on_event_callback`, because it is the hook that makes the log a *record*
rather than a summary. An invocation is not one thing — it is a sequence of events: the model's reply,
a tool call, a tool result, a final response
([Day 7](../../../day-07-events-and-streaming/LESSON.md)). A log with one line per invocation tells
you it happened. A log with one line per event tells you what happened *inside* it, which is the only
level at which *"did the tool run before we substituted?"* has an answer.

There is a design rule that goes with this and it is the point of the story: **the logging plugin
decides nothing.** Every hook writes a line and returns `None`. It does not retry, substitute or
suppress — that is Day 21's policy plugin, and it is a *different object*. Two reasons:

**A recorder that decides can lie.** If the same code that writes the record also chooses the
outcome, a bug in the deciding half corrupts the record of what was decided. Day 21's
[4.2](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.2-the-handler-that-became-the-error.md)
measured exactly that: a plugin that raised while handling an error replaced the error it was
reporting.

**And ADK runs all registered plugins.** `plugins=[Flight(...), Policy(...)]` is a list, so recording
and deciding can be separate objects with separate reasons to change. The one exception in the
mechanism below is `on_tool_error_callback`, which both logs *and* substitutes — and the reason it is
combined there is worth reading in the walkthrough, because it is a compromise rather than a choice.

## Why Sutra needs it

Because this is the file Day 23 asserts against and Day 84 replaces.

Day 23 writes unit tests for tools and callbacks, and the way you test that a callback *ran* is to
check what it recorded. Day 24 counts requests, which is a `SELECT count(*) WHERE event='model_call'`
over this file. Day 79 onwards replays sessions for evals and needs to know what the system did, not
just what it answered.

And Day 84 swaps this plugin for ADK's `AutoTracingPlugin` and OpenTelemetry
([Addendum 01, ADK-74](../../../../docs/01_MASTER_PLAN_ADDENDUM_GAPS.md)). That swap is cheap if the
field names match and expensive if they do not, so the names chosen here — `invocation_id`, `event`,
`tool` — are chosen to survive it.

## The mechanism

One plugin, four hooks, one line each, over a run where the tool fails.

```python
# days/day-22-structured-logging/lab/log_the_run.py
"""One plugin, one line per happening: the run, every event, and every failure."""

FAIL = os.environ.get("FAIL", "1") == "1"

# Start each run from an empty log. Delete BEFORE the handler opens the file:
# on Windows an open FileHandler holds a lock and unlink raises WinError 32.
LOG_PATH.unlink(missing_ok=True)
log = get_logger("sutra")
_seq = itertools.count(1)


def lookup_article(article_id: str) -> dict[str, Any]:
    """Fetch a knowledge-base article. FAIL=1 means the knowledge base is down."""
    if FAIL:
        raise TimeoutError("kb.internal:8080 timed out after 5s")
    return {"article_id": article_id, "title": "SameSite cookie change", "found": True}


class Flight(BasePlugin):
    """The flight recorder. Every hook writes one line; no hook decides anything."""

    async def before_run_callback(self, *, invocation_context: Any) -> None:
        log.info(
            "run_start",
            extra={
                "seq": next(_seq),
                "invocation_id": invocation_context.invocation_id,
                "user_id": invocation_context.user_id,
                "agent": invocation_context.agent.name,
            },
        )

    async def on_event_callback(self, *, invocation_context: Any, event: Any) -> None:
        log.info(
            "event",
            extra={
                "seq": next(_seq),
                "invocation_id": invocation_context.invocation_id,
                "author": event.author,
                "calls": [c.name for c in event.get_function_calls()],
                "final": event.is_final_response(),
            },
        )

    async def on_tool_error_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, error: Exception
    ) -> dict[str, Any] | None:
        log.warning(
            "tool_error",
            extra={
                # tool_context carries the correlation id; the hook has no
                # invocation_context of its own. Forgetting this is 3.2.
                "seq": next(_seq),
                "invocation_id": tool_context.invocation_id,
                "tool": tool.name,
                "kind": type(error).__name__,
                "action": "substitute",
            },
        )
        return {"status": "unavailable", "reason": f"{type(error).__name__}: {error}"}

    async def after_run_callback(self, *, invocation_context: Any) -> None:
        log.info(
            "run_end",
            extra={"seq": next(_seq), "invocation_id": invocation_context.invocation_id},
        )
```

**Line by line:**

- `LOG_PATH.unlink(missing_ok=True)` sits **above** `get_logger`, and the comment says why. On Windows
  a `FileHandler` holds an open handle, so deleting the file after the logger exists raises
  `PermissionError: [WinError 32]`. It is the kind of ordering constraint that is obvious once seen and
  costs twenty minutes otherwise.
- `_seq = itertools.count(1)` is [1.4](../01-a-line-you-can-query/1.4-timestamps-are-not-an-order.md)'s
  counter, and every hook takes `next(_seq)`. One counter for the whole process, so the sequence spans
  hooks rather than restarting per hook.
- `before_run_callback(*, invocation_context)` takes only the context, because at that point nothing
  has happened yet. `invocation_context.agent.name` is where the agent's name lives — not on the
  context directly.
- `invocation_context.invocation_id` is the field that ties the whole run together, and it appears in
  **every** hook that has a context. [2.2](2.2-the-correlation-id.md) is why.
- `on_event_callback` is annotated `-> None` and returns nothing. Its real signature allows returning
  an `Event` to **modify** what gets persisted, which is a real power and exactly the power a recorder
  must not use. Declaring `None` documents the restraint.
- `[c.name for c in event.get_function_calls()]` records the tool names on that event rather than the
  whole call. The arguments could contain customer data, and
  [3.1](../03-failure-lab/3.1-the-log-that-leaked.md) is what happens when they are logged.
- `event.is_final_response()` in a `final` field is the cheapest possible way to find the end of a
  turn in a log. Without it you are guessing from the absence of later lines.
- `tool_context.invocation_id` — the compromise worth reading. `on_tool_error_callback` is handed no
  `invocation_context`, so the id has to come from `tool_context`. Both `ToolContext` and
  `CallbackContext` are the same `Context` class in `google-adk` 2.7.1, and it exposes
  `invocation_id`, `user_id`, `agent_name` and `function_call_id`.
- **This hook both logs and returns a substitute**, which breaks the *decides nothing* rule stated
  above. It is combined here because ADK offers one tool-error hook and this file has one plugin; in
  Sutra's own code the recording lives in a `Flight` plugin and the substituting in Day 21's `Policy`
  plugin, both in `plugins=[...]`, and both are called. Saying so rather than pretending the demo is
  the architecture is the honest option.
- `log.warning` for the failure and `log.info` for everything else —
  [1.3](../01-a-line-you-can-query/1.3-levels-are-routing.md)'s routing, applied.

```bash
cd days/day-22-structured-logging/lab
FAIL=1 uv run python log_the_run.py
FAIL=0 uv run python log_the_run.py
```

**Line by line:**

- `FAIL=1` is the interesting arm: the tool raises, so the `tool_error` line appears.
- Recording models throughout: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:


**Six lines, and the whole invocation is in them.** A run started for `priya` on the `desk` agent; the
model asked for `lookup_article`; the tool failed with a `TimeoutError` and was substituted; two more
events; the last one was the final response; the run ended. That is a complete account, and nobody had
to be watching.

**`FAIL=0` produces five lines.** One fewer, and the missing one is the `tool_error`. The count itself
is the signal — which is the whole idea of a record over a message.

**The `calls` field on line two names the tool** and on lines four and five is empty. Reading down that
column tells you which event carried a tool call without opening anything else, and it is the field
[4.1](../04-in-production/4.1-what-to-log-and-what-to-count.md) turns into a counter.

**And `seq` runs 1 through 6 across four different hooks.** The counter does not restart per hook,
which is what makes it usable as a total order for the run — the point of
[1.4](../01-a-line-you-can-query/1.4-timestamps-are-not-an-order.md). Note lines 5 and 6 already share
a timestamp.

## When it breaks

**The `PermissionError` from deleting an open log**, which is why the unlink is where it is:

```text
PermissionError: [WinError 32] The process cannot access the file because it is being
used by another process: 'logs\\sutra.jsonl'
```

Observed on 2026-09-03 with the unlink placed after `get_logger`. It is Windows-specific — POSIX
allows unlinking an open file — which makes it exactly the sort of bug that passes on a developer's
laptop and fails in a colleague's.

**And the hook that never fires.** A logging plugin installed via `Runner(agent=...)` instead of
`Runner(app=app, ...)` is not installed at all, and produces an empty log file with no error. Day 21's
[5.1](../../../day-21-errors-surface-not-swallow/parts/05-in-production/5.1-one-policy-not-a-hundred.md)
named this and [4.3](../04-in-production/4.3-testing-that-you-logged.md) is the test that catches it.
An empty log looks like a quiet system.

## In production

**Two plugins, not one: a recorder and a policy.** The recorder returns `None` from every hook and can
therefore never change behaviour, which means it can be reviewed once and trusted. Mixing them, as the
demo does for the tool-error hook, is a compromise to keep one file runnable — and it is the compromise
Day 21's [4.2](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.2-the-handler-that-became-the-error.md)
showed the cost of.

**What changes at scale** is that `on_event_callback` becomes the expensive hook. It fires several
times per invocation, so it is the line count multiplier in
[4.1](../04-in-production/4.1-what-to-log-and-what-to-count.md)'s arithmetic — six lines per run
rather than two. At five million runs a day that is the difference between two and six gigabytes, and
the honest answer is usually to log events at `DEBUG` and the run boundaries at `INFO`.

**The failure that only appears with real traffic** is the hook that blocks. These are `async def` and
they run inside the invocation, so a slow handler — a network log shipper, a synchronous disk flush on
a busy volume — adds latency to every event of every request. A `FileHandler` is fine; anything that
does I/O over a socket belongs behind a queue.

**The review comment a senior engineer leaves:** *"the logging plugin returns a substitute from the
tool-error hook. Split it — the recorder shouldn't be able to change what happens, or a bug in it
changes behaviour as well as the record."*

**The interview question:** *"how do you get a usable record of what an agent did?"* The answer that
shows you have wired it: *"a plugin with one line per happening — run start, every event, every tool
error, run end. The event hook is the one that matters, because an invocation is a sequence and one
line per invocation only tells you it happened. And the recorder returns `None` from every hook, so
it can't affect the thing it's recording."*
