# 2.3 — ADK logs too, and one line controls all of it

## One-line answer

Every logger inside ADK is named `google_adk.<module>` — 205 call sites of it — so
`logging.getLogger("google_adk").setLevel(...)` is the whole control surface: `ERROR` captured **0**
records from a run and `DEBUG` captured **8**, from three modules, with Sutra's own log untouched at
1,235 bytes either way.

## The story

The flat has a consumer unit by the front door with a row of switches in it.

Each one is labelled: lights, sockets, shower, oven. When the electrician needs to work on the
shower he flips one switch, and the fridge keeps running. Nobody has to go round unplugging things,
because whoever wired it grouped the circuits and put the grouping somewhere you can reach.

The alternative — and plenty of older buildings are like this — is one main switch and a lot of
guessing.

## The idea in plain language

Python's loggers form a **hierarchy** on the dots in their names. `sutra.context` is a child of
`sutra`, which is a child of the root. A record travels up that hierarchy, and a level set on a parent
governs every descendant that has not set its own.

Which makes the naming convention of a library a real interface, and ADK's is deliberate: **every
logger it creates is `google_adk.` plus the module path.** Counted in the installed `google-adk`
2.7.1 source on 2026-09-03, there are 205 `getLogger("google_adk." + __name__)` call sites and no
loggers created any other way.

So one line governs all of it:

```python
logging.getLogger("google_adk").setLevel(logging.ERROR)
```

**Line by line:**

- `"google_adk"` is a **parent name that no module uses directly**. Nothing in ADK logs to exactly
  this logger; it exists as a node in the hierarchy so that one call can govern the 205 children
  beneath it.
- `.setLevel(logging.ERROR)` on a parent governs every descendant that has not set its own level, and
  ADK's modules do not set their own — which is what makes one line sufficient rather than a starting
  point.

That is worth having for two reasons that pull in opposite directions.

**Turning it down.** ADK at `DEBUG` is verbose, and its records will otherwise propagate to the root
logger and land in whatever the root is configured to do — which, in the default configuration, is
print them to the terminal. If Sutra's own log is a clean JSON Lines file and ADK's chatter is
interleaved on stdout, you have two logs and one of them is noise.

**Turning it up.** When something inside the framework is behaving oddly — a compaction not firing
([20.2.2](../../../day-20-context-engineering-compaction/parts/02-the-config/2.2-the-turn-count-trigger.md)),
a plugin not installed — ADK's own `DEBUG` lines are the fastest way in. `_node_runner`,
`plugin_manager` and `telemetry._metrics` all say useful things.

And the two must not interfere, which is the other half of the mechanism. `propagate = False` on your
own logger ([1.2](../01-a-line-you-can-query/1.2-one-json-object-per-line.md)) stops your records
leaking into ADK's handlers, and setting a level on `google_adk` does not touch `sutra`. The
measurement below checks that rather than assuming it.

## Why Sutra needs it

Because Sutra runs `./m check` on every change and a noisy dependency makes a test run unreadable.

You have already seen it. Every ADK-based run in Days 20 and 21 emitted
`Skipping missing token usage metadata for agent desk and model recorder` — a `WARNING` from
`google_adk.google.adk.telemetry._metrics`, entirely correct, and irrelevant to every one of those
experiments. Each of those days' commands piped through `grep -v` to hide it. One line of
configuration is the version of that fix which does not need remembering.

The other direction matters more from Day 84. `AutoTracingPlugin` and OpenTelemetry mean ADK's
internals start producing telemetry Sutra actually consumes, and knowing that the whole hierarchy
hangs off one name is what makes that configurable rather than all-or-nothing.

## The mechanism

Capture ADK's records instead of printing them, at two thresholds, around a real run.

```python
# days/day-22-structured-logging/lab/adk_own_logs.py
"""ADK logs too. Every one of its loggers is under `google_adk`, so one line controls them all."""

import logging
import os
from pathlib import Path

VERBOSE = os.environ.get("VERBOSE", "0") == "1"
CAPTURED: list[logging.LogRecord] = []


class Capture(logging.Handler):
    """Keeps records instead of writing them, so this file can count them."""

    def emit(self, record: logging.LogRecord) -> None:
        CAPTURED.append(record)


adk = logging.getLogger("google_adk")
adk.handlers.clear()
adk.addHandler(Capture())
adk.propagate = False
adk.setLevel(logging.DEBUG if VERBOSE else logging.ERROR)

# Import and run only after the level is set - ADK logs during import and setup.
import asyncio  # noqa: E402

from log_the_run import main  # noqa: E402

asyncio.run(main())

names = sorted({r.name for r in CAPTURED})
levels = sorted({r.levelname for r in CAPTURED})
print(f"\nVERBOSE={'1' if VERBOSE else '0'}  adk level={logging.getLevelName(adk.level)}")
print(f"  records captured from ADK: {len(CAPTURED)}")
print(f"  distinct logger names    : {len(names)}")
print(f"  levels seen              : {levels or 'none'}")
for name in names[:6]:
    print(f"    {name}")
print(f"\n  every one starts with 'google_adk.': {all(n.startswith('google_adk.') for n in names)}")
print(f"  our own log is still {Path('logs/sutra.jsonl').stat().st_size} bytes and unaffected")
```

**Line by line:**

- `class Capture(logging.Handler)` with `emit` appending to a list is the standard way to *measure*
  logging rather than read it. It makes "how many records did ADK produce?" a number instead of an
  impression.
- `adk = logging.getLogger("google_adk")` — the **parent**, not any particular module. Nothing in ADK
  is named exactly `google_adk`; it is a node in the hierarchy that exists purely to be configured.
- `adk.handlers.clear()` before adding, so re-running in one process does not accumulate handlers.
  Same idempotency problem as [1.2](../01-a-line-you-can-query/1.2-one-json-object-per-line.md)'s
  `if not logger.handlers`.
- `adk.propagate = False` stops ADK's records also reaching the root logger, which is what would print
  them. Without it, this file would capture *and* print.
- **The import order is the load-bearing part.** `import log_the_run` is *below* the level setting and
  carries a `# noqa: E402` saying so. ADK logs during import and during `App` construction, so an
  import at the top of the file would emit records before the handler existed — and the count would be
  wrong for a reason nothing in the output reveals.
- `{r.name for r in CAPTURED}` collects **distinct logger names**, which is the evidence for the
  hierarchy claim. Three names from one small run; 205 exist.
- `all(n.startswith("google_adk."))` is the assertion, computed rather than asserted in prose. If ADK
  ever created a logger outside the hierarchy, this line would say so.
- The last line reads Sutra's own log file size, so "the two do not interfere" is a measured number
  rather than a hope.

**Line by line:**

- Two runs, one environment variable: ADK at `ERROR`, then at `DEBUG`.
- Recording models throughout: no key, no network, no quota.

Measured on `google-adk` 2.7.1 on 2026-09-03:

```text
VERBOSE=0  adk level=ERROR
  records captured from ADK: 0
  distinct logger names    : 0
  levels seen              : none

  every one starts with 'google_adk.': True
  our own log is still 1235 bytes and unaffected

VERBOSE=1  adk level=DEBUG
  records captured from ADK: 8
  distinct logger names    : 3
  levels seen              : ['DEBUG', 'INFO', 'WARNING']
    google_adk.google.adk.plugins.plugin_manager
    google_adk.google.adk.telemetry._metrics
    google_adk.google.adk.workflow._node_runner

  every one starts with 'google_adk.': True
  our own log is still 1235 bytes and unaffected
```

**Zero against eight, from one line.** Same run, same code, same plugin — one `setLevel` call and ADK
is either silent or fully instrumented. There is no per-module configuration to write and nothing to
enumerate.

**Three logger names, and they are the three you would want.** `plugin_manager` (are my plugins
installed and being called?), `telemetry._metrics` (the usage-metadata warning Days 20 and 21 kept
grepping away), and `workflow._node_runner` (what the runtime is doing with the agent). At `DEBUG`
those answer most "why is the framework not doing what I expect" questions.

**`every one starts with 'google_adk.': True`** — computed, over the names actually seen. That is the
hierarchy claim checked rather than repeated.

**And Sutra's own log is 1,235 bytes in both runs.** Identical. Turning ADK's logging all the way up
changed nothing about the file Sutra writes, because the two loggers are separate branches and both
have `propagate = False`. That separation is what makes the JSON Lines file safe to parse: nothing
else can write to it.

## When it breaks

**Set the level after importing and the count is wrong with no indication.** Moving
`from log_the_run import main` above the `setLevel` call loses every record ADK emits during import
and `App` construction — and the output still prints a number, so it looks like an answer.

**Forget `propagate = False` on your own logger and every line appears twice**, once as JSON in the
file and once as plain text on the terminal via the root logger's default handler. There is no error;
the file is correct and the terminal is a duplicate.

**And the quietest of the three: a name with a hyphen in it.**
`logging.getLogger("google-adk")` does not fail. `getLogger` creates a logger for any name you give
it, so you get a brand-new, unrelated logger, you configure it perfectly, and it governs nothing.
There is no error and no warning — the only symptom is that ADK's output is exactly as it was. The
name is `google_adk`, with an underscore, and it is worth copying rather than typing.

## In production

**Configure logging once, at startup, from environment variables.** Two settings:
`SUTRA_LOG_LEVEL` for your own hierarchy and `ADK_LOG_LEVEL` for `google_adk`. Both default sensibly
— `INFO` and `WARNING` — and both are one restart from being turned up during an incident.

**What changes at scale** is that a dependency's log volume becomes your bill. ADK at `DEBUG` is eight
records for one tiny run; at real traffic that is a multiple of your own volume, in a format you did
not choose, going to storage you pay for. `WARNING` is the right production setting for a dependency,
and `DEBUG` is a switch you flip for one process for ten minutes.

**The failure that only appears with real traffic** is the dependency that logs something sensitive.
You control the fields in *your* formatter; you do not control what a library puts in its messages, and
[3.1](../03-failure-lab/3.1-the-log-that-leaked.md)'s redaction filter has to be attached to the
`google_adk` logger too if it is going to mean anything. A scrub on your own logger only cleans your own
lines.

**The review comment a senior engineer leaves:** *"we're grepping ADK's usage-metadata warning out of
the test output in three places. Set the `google_adk` level once in `conftest.py` and delete the greps."*

**The interview question:** *"how do you keep a library's logging out of your own?"* The answer that
shows you have configured it: *"Python's loggers are a hierarchy on the dots, so a well-behaved library
puts everything under one name — ADK uses `google_adk.<module>` for all 205 of its loggers. One
`setLevel` on that parent governs the lot. Then `propagate = False` on my own logger so my records
don't travel up into whatever handlers the root has."*
