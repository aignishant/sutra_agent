# 2.2 — The correlation id, and the hook that hides it

## One-line answer

Every line needs the same `invocation_id` or the log is a pile rather than a record — and the one
hook that most needs it, `on_tool_error_callback`, is handed no invocation context, so the id has to
come from `tool_context.invocation_id`.

## The story

The hospital puts a wristband on you before anything else happens.

Every sample, every chart, every form gets the same number off that band. It is not for you — you
know who you are — it is so that the blood taken on the ward and the result that comes back from the
lab four hours later can be put next to each other by somebody who was present for neither.

The one thing on that trolley without a number on it is the paper cup. And the day somebody needs to
know which patient the cup belonged to is the day they find out that *everything else* had a number.

## The idea in plain language

A log is a single stream and the system is concurrent. Two conversations happening at once put their
lines into the same file, interleaved, and there is nothing in a line's *content* that says which
conversation it belongs to.

A **correlation id** fixes that: one value, generated once per unit of work, stamped on every line
that unit produces. ADK generates one for you and calls it the **invocation id** — the `e-9db2cf9f-…`
in [2.1](2.1-one-line-per-happening.md)'s output. One press of the doorbell, one id
([17.2.2](../../../day-17-state-scopes-and-lifetimes/parts/02-four-lifetimes/2.2-an-invocation-is-not-a-session.md)
is where the invocation was defined as a unit).

With it, *"what happened to priya's request?"* is a filter. Without it, the question is unanswerable —
which [3.2](../03-failure-lab/3.2-the-line-nobody-can-correlate.md) measures.

Three ids, and it is worth being precise about which does what, because they are easy to conflate:

| Id | Scope | Answers |
| --- | --- | --- |
| `user_id` | a person, forever | *is this the same customer?* |
| `session_id` | a conversation | *what else was said in this thread?* |
| `invocation_id` | **one turn** | *what happened while answering this question?* |

All three belong on a line. The invocation id is the one that does the heavy lifting during an
incident, because an incident is about one request going wrong.

Now the awkward part, and it is the reason this part exists rather than being a paragraph in 2.1.
**The hooks are not handed the same things.** Three of the four in
[2.1](2.1-one-line-per-happening.md) receive an `invocation_context`, and the id is right there. The
fourth — `on_tool_error_callback` — receives `tool`, `tool_args`, `tool_context` and `error`, and
**no invocation context at all**.

That is the hook that logs the failure. The single line you will most want to correlate is the one
line whose hook signature does not obviously offer the means to do it.

The answer is `tool_context`, and it is easy to miss because its name suggests a narrower object than
it is. In `google-adk` 2.7.1, `ToolContext` and `CallbackContext` are **both the same `Context`
class**, and it exposes `invocation_id`, `user_id`, `agent_name`, `session`, `state` and
`function_call_id` among others. The id was available all along.

## Why Sutra needs it

Because the question Sutra will be asked is always about one request.

*"A customer says Sutra told them their ticket had no notes. What happened?"* That is
[21.3.2](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.2-a-substitute-must-say-so.md)'s
scenario, and answering it means finding the six lines belonging to that one invocation among
thousands. One filter, if the id is there; a reconstruction from timestamps, if it is not — and
[1.4](../01-a-line-you-can-query/1.4-timestamps-are-not-an-order.md) has already shown what
timestamps are worth for that.

Day 84's tracing makes the id structural rather than a field: a trace id, propagated, with spans
nested under it. Today's `invocation_id` is the same idea done by hand, and Sutra's log will map onto
a trace exactly if the id is on every line and nowhere near it if it is not.

## The mechanism

The four hooks side by side, with what each is handed and where the id comes from.

```python
# days/day-22-structured-logging/lab/log_the_run.py  (signatures only)

    async def before_run_callback(self, *, invocation_context: Any) -> None: ...

    async def on_event_callback(self, *, invocation_context: Any, event: Any) -> None: ...

    async def on_tool_error_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, error: Exception
    ) -> dict[str, Any] | None: ...

    async def after_run_callback(self, *, invocation_context: Any) -> None: ...
```

**Line by line:**

- Three of the four take `invocation_context`. On those, `invocation_context.invocation_id` is the
  whole answer and there is nothing to think about.
- `on_tool_error_callback` takes **no** `invocation_context`. Read the parameter list and the id looks
  unavailable: a tool, its arguments, a tool context, an exception.
- `tool_context` is the way in, and its type is the surprise. Verified on 2026-09-03 against the
  installed `google-adk` 2.7.1: both `google.adk.tools.tool_context.ToolContext` and
  `google.adk.agents.callback_context.CallbackContext` resolve to the same class, `Context`, whose
  attributes include `invocation_id`, `user_id`, `agent_name`, `session`, `state`,
  `function_call_id`, `branch` and `run_id`.
- `function_call_id` is worth knowing about even though this part does not use it: it identifies *this
  specific call*, which is what lets you match a `tool_error` line to the `tool_call` that produced it
  when a single event carries several calls.

So the line becomes:

```python
    async def on_tool_error_callback(
        self, *, tool: Any, tool_args: dict[str, Any], tool_context: Any, error: Exception
    ) -> dict[str, Any] | None:
        log.warning(
            "tool_error",
            extra={
                # tool_context carries the correlation id; the hook has no
                # invocation_context of its own. Forgetting this is 3.2.
                "seq": next(_seq),
                "invocation_id": tool_context.invocation_id,
                "tool": tool.name,
                "kind": type(error).__name__,
                "action": "substitute",
            },
        )
        return {"status": "unavailable", "reason": f"{type(error).__name__}: {error}"}
```

**Line by line:**

- `"invocation_id": tool_context.invocation_id` is the fix, and it is one expression. The comment
  above it exists because the *absence* of this line is invisible — the log still works, every other
  line still has the id, and only the failure lines are orphaned.
- `"tool": tool.name` rather than the `tool` object. Logging the object would serialise to a `repr`
  via `default=str` ([1.2](../01-a-line-you-can-query/1.2-one-json-object-per-line.md)) and produce an
  unfilterable string.
- `tool_args` is deliberately **not** logged. It is available, it is tempting, and it contains
  whatever the model passed — which for `list_notes` is a customer identifier.
  [3.1](../03-failure-lab/3.1-the-log-that-leaked.md) is that decision made wrongly.
- `type(error).__name__` rather than `str(error)` in the `kind` field: a type is a small closed
  vocabulary you can group by, a message is prose. The message belongs in a `detail` field if you want
  it, and [3.1](../03-failure-lab/3.1-the-log-that-leaked.md) is why you might not.

**Line by line:**

- Recording models throughout: no key, no network, no quota.

The failure line, from the run measured on 2026-09-03:

```text
{"ts": "2026-09-03T13:54:44.245Z", "level": "WARNING", "logger": "sutra", "event": "tool_error", "seq": 3, "invocation_id": "e-9db2cf9f-0756-4588-9c0b-c1b45952cd4a", "tool": "lookup_article", "kind": "TimeoutError", "action": "substitute"}
```

**The id on that line is identical to the id on the other five.** `e-9db2cf9f-0756-4588-9c0b-c1b45952cd4a`,
on `run_start`, on all three `event` lines, on `run_end`, and on this. Six lines, one filter, one
complete account of one turn.

**And it came from a different object than the other five.** Five lines read
`invocation_context.invocation_id`; this one reads `tool_context.invocation_id`. Same value,
different route, and the route is not visible from the hook's parameter list.

**`seq: 3` places it exactly.** Between the event that requested the tool (`seq: 2`, `calls:
["lookup_article"]`) and the event that followed (`seq: 4`). That is the ordering question from
[1.4](../01-a-line-you-can-query/1.4-timestamps-are-not-an-order.md) answered — *the tool was
requested, then it failed, then the run continued* — and it is answerable because of one integer.

## When it breaks

Omit the id and nothing raises. The line is written, the run succeeds, and the log is quietly
unusable for the one question it exists to answer. The measured version is
[3.2](../03-failure-lab/3.2-the-line-nobody-can-correlate.md).

Reach for the wrong attribute and it is loud, which is the better outcome:

```text
AttributeError: type object 'Context' has no attribute 'invocation'
```

That one was produced on 2026-09-03 by asking the class for a misspelled attribute; from inside a hook
you get the instance form, `'Context' object has no attribute ...`. Either way it names the real class,
which is the useful part: `ToolContext` resolves to `Context` from `google.adk.agents.context`.

And there is a third failure with no error text that is worth naming because it looks like success:
using a **different** id per line. Generating a fresh `uuid4()` in each hook gives every line an id,
passes any test that checks the field is present, and correlates nothing. A correlation id is only a
correlation id if it is the *same* value across the unit of work — which is why taking it from ADK's
context rather than generating your own is the right instinct.

## In production

**Assert the id on the failure line specifically, not on lines in general.** A test that checks *some*
line has an `invocation_id` passes while the failure lines are orphaned, because five of six lines get
it from the easy route. [4.3](../04-in-production/4.3-testing-that-you-logged.md) has that assertion,
named after this part.

**What changes at scale** is that one id stops being enough. A request that crosses into an MCP server
(Phase 5) or fans out across graph nodes (Phase 8) needs the id to *travel* — as a header, as an
argument — so the far side's lines carry it too. That is distributed tracing, it is Day 84, and the
id you propagate is this one.

**The failure that only appears with real traffic** is the id that is not unique. ADK's invocation ids
are `e-` plus a UUID and are fine. A hand-rolled `f"{user_id}-{int(time.time())}"` is not: two
requests from one user in the same second collide, and the log then merges two conversations under one
id — which is worse than no id, because it looks correlated and is wrong.

**The review comment a senior engineer leaves:** *"the tool-error line has no `invocation_id`. Pull it
off `tool_context` — that hook doesn't get an invocation context, and the failure line is the one
we'll actually be searching for."*

**The interview question:** *"how do you find the logs for one request?"* The answer that shows you
have searched for some: *"a correlation id on every line — ADK gives you an invocation id per turn.
The catch is that the hooks aren't handed the same objects: the tool-error hook has no invocation
context, so you take the id off `tool_context`, which in 2.7.1 is the same `Context` class the
callback context is. Miss that and every line has the id except the failures."*
