# 3.2 — 💥 The line nobody can correlate

## One-line answer

Two conversations at once, seven lines in one file, one of them a failure: with a correlation id the
question *"did priya's request fail?"* is answered **no, from three lines**; without it, the honest
answer is **unanswerable** — and the file looks identically healthy either way.

## The story

Two people hand in dry cleaning within a minute of each other and the shop is busy.

The assistant hangs both lots on the same rail. The tickets are in his hand, not on the garments, and
then the phone goes and he puts the tickets down.

On Thursday somebody rings to say a jacket came back with a mark on it. There is a jacket on the rail
with a mark on it. There is no way on earth to say whose it is, and both customers are now people who
might have a jacket with a mark on it.

Nothing was lost. Two things were mixed, and mixing is not recoverable by trying harder.

## The idea in plain language

[2.2](../02-wiring-the-run/2.2-the-correlation-id.md) said every line needs an `invocation_id` and
named the hook that makes it easy to forget. This part is what forgetting costs, measured, and the
number that matters is not a percentage — it is the difference between a question having an answer and
not having one.

The setup is the ordinary condition, not an edge case. **A log is one file and the system is
concurrent.** Two users, two invocations, overlapping in time, writing into the same stream. That is
what a server does; a system where it never happens is a system with one user.

Now interleave seven lines from two runs and ask the question an operator actually asks. Not *"how
many errors?"* — that one is answerable by counting. The question is *"did **this** request fail?"*,
because that is what a customer complaint is, and it is a question about **one** conversation among
several.

Without an id, three things are true at once and they compound:

**The failure line exists.** You can see there was a `tool_error`. Something went wrong for somebody.

**Nothing says whose.** No field distinguishes the runs, so the line belongs to either with equal
plausibility.

**And you cannot even bound it.** With two runs and one error you might reason *"it's fifty-fifty"* —
but you cannot know there were two runs, because the thing that would have told you is the same
missing field.

The last one is what makes this worse than a gap in the data. A log with a hole in it is a log you
distrust appropriately. A log with no correlation ids is a log that looks complete, answers
aggregate questions correctly, and is silently incapable of the one question you will be asked.

## Why Sutra needs it

Because Sutra's investigations always start from one request and its own history has already produced
the scenario twice.

[20.4.2](../../../day-20-context-engineering-compaction/parts/04-failure-lab/4.2-the-fact-that-was-true-and-is-now-gone.md)
ended with a customer told their ticket had no notes, and the diagnosis required knowing what was in
the window **on that call**.
[21.3.2](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.2-a-substitute-must-say-so.md)
ended with a false statement produced by a substituted tool result, and the diagnosis required knowing
whether a substitution had happened **for that request**. Both are one filter with an id and
guesswork without.

And it gets structurally worse from Phase 8. A graph runs several nodes per invocation, so one
conversation produces many more lines; two concurrent conversations interleave far more finely than
the seven lines below. The id is the only thing that scales.

## The mechanism

Seven interleaved lines from two runs, written with the correlating fields and without, then asked the
operator's question.

```python
# days/day-22-structured-logging/lab/no_correlation.py
"""Two conversations at once, one log file. Without a correlation id you cannot separate them."""

CORRELATE = os.environ.get("CORRELATE", "1") == "1"
OUT = Path("logs/interleaved.jsonl")

# Two runs happening at the same time, their lines arriving interleaved.
INTERLEAVED = [
    ("e-aaa", "priya", "run_start", "INFO"),
    ("e-bbb", "sam", "run_start", "INFO"),
    ("e-aaa", "priya", "tool_call", "INFO"),
    ("e-bbb", "sam", "tool_call", "INFO"),
    ("e-bbb", "sam", "tool_error", "WARNING"),
    ("e-aaa", "priya", "run_end", "INFO"),
    ("e-bbb", "sam", "run_end", "INFO"),
]

OUT.parent.mkdir(exist_ok=True)
records = []
for invocation_id, user, event, level in INTERLEAVED:
    line = {"level": level, "event": event}
    if CORRELATE:
        line["invocation_id"] = invocation_id
        line["user_id"] = user
    records.append(line)
OUT.write_text("\n".join(json.dumps(r) for r in records) + "\n", encoding="utf-8")

# The question an operator actually asks.
question = "did priya's request fail?"
if CORRELATE:
    priya = [r for r in records if r.get("user_id") == "priya"]
    failed = any(r["event"] == "tool_error" for r in priya)
    answer = f"no ({len(priya)} lines, no tool_error among them)" if not failed else "yes"
else:
    answer = "unanswerable - there is a tool_error, and nothing says whose"
```

**Line by line:**

- `INTERLEAVED` is the **ground truth**, written out so the answer is knowable to the reader and not to
  the log. The failure belongs to `sam`, and priya's request was fine — which is the fact the log
  either preserves or destroys.
- The interleaving is realistic: both runs start, both call a tool, one fails, both end. Nothing exotic,
  and it is the pattern any concurrent server produces.
- `if CORRELATE:` adds **two** fields, `invocation_id` and `user_id`, and that pairing is deliberate.
  The invocation id separates the runs; the user id is what a support ticket actually gives you to
  search by. One without the other leaves you a step short.
- Everything else about the two arms is identical — same events, same levels, same order, same file.
  The only variable is two keys per line.
- `[r for r in records if r.get("user_id") == "priya"]` is the whole investigation, in one line. That
  is the point of the part: correlation is not a feature you build, it is a field you put on a line so
  that a filter becomes possible.
- `.get("user_id")` rather than `["user_id"]`, because in the uncorrelated arm the key is absent and
  indexing would raise. The reader of a log does not get to assume its shape.
- `any(r["event"] == "tool_error" for r in priya)` — the question is asked over **priya's lines only**,
  which is the difference between a specific answer and an aggregate one.
- The `else` branch hardcodes `"unanswerable"`, and that is not a shortcut. There is no computation
  that would answer the question, so writing one would be pretending. Saying so is the finding.

```bash
cd days/day-22-structured-logging/lab
CORRELATE=0 uv run python no_correlation.py
CORRELATE=1 uv run python no_correlation.py
```

**Line by line:**

- `CORRELATE=0` first: the broken log, which looks fine.
- Pure Python and one small file. No ADK, no key, no quota.

Measured on 2026-09-03:

```text
CORRELATE=0  7 lines in logs\interleaved.jsonl
  {"level": "INFO", "event": "run_start"}
  {"level": "INFO", "event": "run_start"}
  {"level": "INFO", "event": "tool_call"}
  {"level": "INFO", "event": "tool_call"}
  {"level": "WARNING", "event": "tool_error"}
  {"level": "INFO", "event": "run_end"}
  {"level": "INFO", "event": "run_end"}

  did priya's request fail?
    unanswerable - there is a tool_error, and nothing says whose

  lines that mention a failure: 1
  runs in this file           : 2, not separable
```

**Read that file and it looks like a competent log.** Valid JSON Lines, a level on every line, a small
closed vocabulary of event names, a warning where the failure was. It is structured. It is
machine-readable. It answers *"how many failures?"* correctly. And it cannot answer the question
anybody will ask.

**`runs in this file: 2, not separable`.** Even the count of conversations is gone. Two `run_start`
lines is a hint, not a fact — a single run that restarted would look the same, and so would one run
logged twice by a duplicated handler
([1.2](../01-a-line-you-can-query/1.2-one-json-object-per-line.md)'s failure mode).

With the two fields, the same seven lines:

```text
CORRELATE=1  7 lines in logs\interleaved.jsonl
  ...
  did priya's request fail?
    no (3 lines, no tool_error among them)

  lines that mention a failure: 1
  runs in this file           : 2, separable
```

**`no (3 lines, no tool_error among them)`.** A specific, defensible answer with its evidence
attached: three lines belong to priya, none of them is a failure. That is what you say to a customer,
and it took a filter on a field.

**And `lines that mention a failure: 1` is unchanged between the arms.** The aggregate was always
right. Nothing about the broken log looks broken from a dashboard, which is precisely why this failure
survives to the moment it matters.

## When it breaks

There is no error text. That is the third day running that a failure lab in this curriculum has had
nothing to print — Day 20's lost constraint, Day 21's swallowed exception, and now this — and the
pattern is worth naming: **the failures that survive to production are the ones with no output.**

What you get instead is an investigation that stops:

```text
$ grep tool_error logs/sutra.jsonl | wc -l
1
$ grep tool_error logs/sutra.jsonl
{"level": "WARNING", "event": "tool_error"}
```

One line, correctly found, and it tells you nothing you can act on. The next move — *"which
conversation?"* — has no command. At that point the honest thing to tell the customer is that you
cannot say, and the honest thing to tell your team is that the log needs a field.

The variant that is worse than useless is a **wrong** correlation. Generating a fresh `uuid4()` per
line ([2.2](../02-wiring-the-run/2.2-the-correlation-id.md) named this) gives every line an id, passes
any test that checks the field exists, and correlates nothing — while looking like a log that
correlates. A `user_id` derived from a truncated hash that collides does the same thing and merges two
customers' conversations under one label, which is a data-protection problem on top of an
observability one.

## In production

**Make the id impossible to omit rather than easy to remember.** Put it in the formatter, not in
`extra`: a `logging.Filter` that reads the current invocation id from a `contextvars.ContextVar` and
attaches it to every record. Then no call site can forget, including one written next year — the same
argument as [Day 21's plugin over eleven try/excepts](../../../day-21-errors-surface-not-swallow/parts/05-in-production/5.1-one-policy-not-a-hundred.md).

**What changes at scale** is that the id becomes a join key across systems. Once the request touches an
MCP server (Phase 5) and several graph nodes (Phase 8), the id has to travel with the call so the far
side's lines carry the same value. That is distributed tracing, and Day 84 is where Sutra gets it —
built on this field.

**The failure that only appears with real traffic** is the log that is fine until it is concurrent. On
a laptop, one request at a time, an uncorrelated log reads perfectly: the lines are in order and
obviously belong together. Every test passes. The first day two users overlap, the file becomes a pile,
and nothing about the change is visible in the code.

**The review comment a senior engineer leaves:** *"none of these lines has an invocation id, so the
moment we have two concurrent requests this file is unreadable. Add it via a context filter rather than
per call site."*

**The interview question:** *"your log has an error in it and a customer is on the phone. What do you
need?"* The answer that shows you have been on that call: *"a correlation id on every line. Without one
I can tell you how many errors there were and nothing about whether this customer's request was one of
them — and the aggregate looks completely healthy, which is why nobody notices the field is missing
until the day it is needed."*
