# 3.1 — 💥 The log that leaked

## One-line answer

One `detail` field carrying a database driver's exception put a customer's email address and a bearer
token into a log file on disk — two secrets in 231 bytes — and a nine-line `logging.Filter` removed
both while keeping everything an operator needs.

## The story

The estate agent photographs the kitchen for the listing.

Good picture. Clean worktop, morning light, and on the noticeboard behind the kettle a repeat
prescription with a name and address on it, and a bank card somebody left face up by the fruit bowl.

Nobody photographed the prescription. It was in the frame.

The listing went up on four portals and got shared to a group chat, and by the time anyone noticed
it had been copied to places nobody could enumerate. The camera was pointed at the worktop, and the
camera does not know what a worktop is.

## The idea in plain language

Day 21 established that a public-facing error message must be a fixed string, because an exception
carries internal detail
([21.3.3](../../../day-21-errors-surface-not-swallow/parts/03-policy/3.3-giving-up-honestly.md)
measured four leaks in one 429 body). That part was about the **user-facing** path, and it explicitly
said the log gets the whole exception, unmodified, because an operator needs to search for the exact
string.

This part is the sting in that tail. **A log file is also an audience**, and it is a wider one than
people picture:

- it is on disk, and disks are backed up;
- it is shipped to a log platform, which is a third-party service with its own access model;
- it is readable by everyone with production access, which is more people than have database access;
- and it is retained for months, long after the request is forgotten.

So *"the log gets everything"* is right about **detail** and wrong about **secrets**, and the two
arrive in the same field. The exception a real database driver raises is helpful in exactly the way
that hurts:

```
OperationalError: timeout executing
SELECT * FROM notes WHERE email='priya.sharma@acme-corp.example' AND ticket=4521
```

Every part of that is useful to an operator. The query shape tells you which code path. The ticket
number tells you which record. And the email address is a customer's personal data, now in a file,
because the driver put the parameters in the message and the log put the message in a field.

The fix has a name — a **log filter** — and it is the right layer for a reason worth naming. Python's
`logging.Filter` runs on the record *before* any formatter sees it, so one filter attached to the
logger cleans every line from every call site, including lines written by code you did not write
([2.3](../02-wiring-the-run/2.3-adk-logs-too.md)'s point about a dependency's messages). It is
[Day 21's end-to-end argument](../../../day-21-errors-surface-not-swallow/papers/01-end-to-end-arguments.md)
applied once more: put the function where it covers the whole problem, not at each call site.

## Why Sutra needs it

Because Sutra's tools take customer identifiers as arguments, and its repository goes public in
Phase 14.

`list_notes(email=...)`, `fetch_customer(...)`, `check_entitlement(...)` — every one of those has a
personal identifier in `tool_args`, which is why
[2.2](../02-wiring-the-run/2.2-the-correlation-id.md) deliberately did **not** log `tool_args` and
said so. That decision is one line away from being reversed by anybody debugging on a Friday
afternoon.

And the failure is not symmetrical with other bugs. A crash is fixed and gone. A log that captured a
customer's email for three months is a data-protection incident with a notification obligation, and
the fix — deleting it — is harder than the mistake, because by then the file has been backed up,
shipped and indexed. Day 66 onwards is the safety phase; this is the output-side half of it, and it
starts here because today is the day Sutra starts writing files that outlive the process.

## The mechanism

One log line carrying a driver's exception and an auth header, written twice — with the filter and
without — and audited for three known secret shapes.

```python
# days/day-22-structured-logging/lab/leaked.py
"""A log file is a copy of your data. Count what one careless field puts in it."""

REDACT = os.environ.get("REDACT", "1") == "1"
OUT = Path("logs/leaked.jsonl")

# The exception a real database driver raises: it helpfully includes the query.
DB_ERROR = (
    "OperationalError: timeout executing "
    "SELECT * FROM notes WHERE email='priya.sharma@acme-corp.example' AND ticket=4521"
)

SECRETS = {
    "an email address": r"[\w.+-]+@[\w-]+\.[\w.]+",
    "a bearer token": r"Bearer [A-Za-z0-9._-]{8,}",
    "an API key": r"AIza[A-Za-z0-9_-]{10,}",
}
REDACTIONS = [(re.compile(p), f"<{name.split()[-1]} redacted>") for name, p in SECRETS.items()]


class Scrub(logging.Filter):
    """Rewrites known secret shapes out of every field before the record is formatted."""

    def filter(self, record: logging.LogRecord) -> bool:
        for key, value in list(record.__dict__.items()):
            if isinstance(value, str):
                for pattern, replacement in REDACTIONS:
                    value = pattern.sub(replacement, value)
                record.__dict__[key] = value
        return True  # never drop the line; only change it
```

**Line by line:**

- `DB_ERROR` is the shape a real driver produces. It is not a contrived example: including the
  statement in the error is standard, helpful behaviour, and it is why this leak is so common.
- `SECRETS` maps a human name to a **pattern**, and the same dictionary is used for both the redaction
  and the audit. That is deliberate: a redaction list and a test list that can drift apart is two
  lists, and the one that drifts is the test.
- `r"Bearer [A-Za-z0-9._-]{8,}"` — the `{8,}` avoids matching the literal word `Bearer` followed by
  something short and innocent. Patterns that are too greedy make logs unreadable, which is how
  redaction gets switched off.
- `r"AIza[A-Za-z0-9_-]{10,}"` is the shape of a Google API key, which matters here specifically: it is
  the credential in Sutra's own `.env`, and an exception from the model client can contain it.
- `class Scrub(logging.Filter)` — a **filter, not a formatter**. Filters run earlier and apply to every
  handler, so one attachment cleans the file handler, a future stream handler and anything a dependency
  logs through the same logger.
- `for key, value in list(record.__dict__.items())` iterates a **copy**. Strictly, it does not have to:
  assigning to a key that already exists does not change the dict's size, so CPython allows it — checked
  on 2026-09-03. The `list()` is there for the day somebody extends this filter to *add* a field (say,
  `detail_redacted: true`), which does change the size and does raise. Being defensive is cheap here and
  the alternative fails only on lines that contain a secret.
- `if isinstance(value, str)` — only strings are scrubbed. An `int` ticket number cannot contain an
  email, and calling `.sub` on a non-string would raise inside the error path, which
  [21.4.2](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.2-the-handler-that-became-the-error.md)
  showed the cost of.
- `return True` is the part of `logging.Filter` that surprises people: the return value decides
  whether the record is **kept**. Returning `False` would drop the line entirely. This filter is being
  used for its side effect on the record, which is a documented and slightly sneaky use of the hook.


**Line by line:**

- `REDACT=0` first: the leak, so it can be counted rather than imagined.
- Pure Python and one small file. No ADK, no key, no quota.

Measured on 2026-09-03:

```text
REDACT=0  231 bytes written to logs\leaked.jsonl
  secrets still present in the log file: ['an email address', 'a bearer token']

  {"event": "tool_error", "tool": "list_notes", "detail": "OperationalError: timeout executing SELECT * FROM notes WHERE email='priya.sharma@acme-corp.example' AND ticket=4521", "auth": "Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9"}

REDACT=1  192 bytes written to logs\leaked.jsonl
  secrets still present in the log file: none

  {"event": "tool_error", "tool": "list_notes", "detail": "OperationalError: timeout executing SELECT * FROM notes WHERE email='<address redacted>' AND ticket=4521", "auth": "<token redacted>"}
```

**Two secrets, on disk, in one line.** A customer's email address and a bearer token — and the line
was written by well-intentioned code doing the thing this whole day has been arguing for: put the
detail in a field so an operator can search it.

**And the redacted line loses nothing an operator needs.** Compare them: `OperationalError`, `timeout
executing`, the query shape, the table name, `ticket=4521` — all still there. What went is the email
and the token. The diagnosis is intact; the copy of somebody's personal data is not.

**39 bytes smaller.** That is the entire cost. Not a trade-off between safety and usefulness, which is
the argument people expect to have — the useful half of the line survives verbatim.

**`secrets still present: none`, computed.** The audit runs the same three patterns over the file that
were used to redact it, so the claim is a measurement rather than an assurance. That list is the
fixture [4.3](../04-in-production/4.3-testing-that-you-logged.md) turns into a test.

## When it breaks

The leak has no error text at all, which is the whole reason it survives to production. The file is
valid JSON Lines, the run succeeded, the operator got a better error message than usual, and nothing
anywhere is red.

The filter's own failure mode is the one with output, and it is one edit away. Extend the filter to
*add* a field while iterating `record.__dict__` without the `list()` copy — an entirely reasonable
change — and you get this, observed on 2026-09-03:

```text
RuntimeError: dictionary changed size during iteration
```

Raised inside a log filter, which means the logging breaks on exactly the lines that triggered the
extra field. A spectacularly bad time for logging to break, and the reason the `list()` is in the code
before anyone needs it.

And the quiet failure of the filter is the pattern that stops matching. A new provider issues tokens
that do not start with `Bearer`, or an identifier arrives as `priya.sharma[at]acme-corp.example` after
some sanitiser gets to it, and the redaction silently passes it through. A redaction list is a
blocklist, and blocklists are wrong by default — which is why the honest position is that
[2.2](../02-wiring-the-run/2.2-the-correlation-id.md)'s decision not to log `tool_args` at all is a
stronger defence than any filter.

## In production

**Prefer not logging it to redacting it.** The filter is a safety net for things that arrive inside
somebody else's message, which you cannot control. For your own fields the correct move is an
allowlist: log `tool`, `kind`, `invocation_id`, and never `tool_args`, never the prompt, never the
response body. A field you did not write cannot leak.

**Attach the filter to every logger, including the dependency's.** A `Scrub` on `sutra` does nothing
about a message ADK logs, and [2.3](../02-wiring-the-run/2.3-adk-logs-too.md) showed that ADK's records
go through the `google_adk` hierarchy. Two attachments, or one at the handler, which sees everything
routed to it.

**What changes at scale** is that the log leaves your control. Shipped to a platform, indexed, searched
by support staff, retained per a policy somebody else wrote. Every one of those multiplies the audience
for a leaked field, and none of them is visible from the code that wrote the line.

**The failure that only appears with real traffic** is the *unusual* record. Your patterns are tuned on
the errors you have seen. The first time a driver includes a full row in an exception — names, phone
numbers, a free-text note — the shapes do not match anything and the whole row is logged. This is why
a log platform's own retention and access controls matter as much as your filter.

**The review comment a senior engineer leaves:** *"this logs `str(error)` from the DB call. That
exception includes the statement and its parameters, which is a customer email. Log the exception
*type* and the query name, not the message — and put the scrub filter on the handler while you're
there."*

**The interview question:** *"what should never go in a log?"* The answer that shows you have cleaned
one up: *"anything you would not put in a spreadsheet and email to the whole company, because that is
roughly the audience once it is shipped and retained. In practice: credentials, personal identifiers,
prompts and model responses. The defence is an allowlist of fields rather than a redaction filter,
because a filter is a blocklist and the first unfamiliar exception format defeats it — though we run a
filter too, on the handler, for messages from libraries we do not control."*
