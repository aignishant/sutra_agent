# 1.2 — One JSON object per line

## One-line answer

A `logging.Formatter` subclass that returns `json.dumps(...)` turns every call to `log.info(...,
extra={...})` into one machine-readable line in a file — about thirty lines of stdlib, no
dependencies, and the four fields nobody has to remember.

## The story

The hospital ward keeps its observations on a chart at the end of the bed.

The chart has boxes. Time, temperature, pulse, blood pressure, initials. Nobody writes *"looked a bit
better this morning"* in the temperature box, because it is a box for a number, and the boxes are why
a doctor who has never met the patient can read four days of it in fifteen seconds.

What makes it work is not the discipline of the nurses. It is that the form was printed with the
boxes already on it. You would have to go out of your way to record something unusable.

## The idea in plain language

The format for logs that a program will read has a name — **JSON Lines** — and it is exactly what it
sounds like: one JSON object per line, newline-separated, no wrapping array. That last detail is the
whole reason it exists. A file that is one enormous JSON array cannot be appended to without
rewriting the end, cannot be read without parsing all of it, and cannot survive a process being
killed mid-write. A file of independent lines can be appended to forever, read a line at a time, and
truncated safely at any newline.

Python's `logging` gives you the machinery for this and one seam to fill:

| Piece | What it does | What you do with it |
| --- | --- | --- |
| **logger** | the thing you call, named in a hierarchy | `logging.getLogger("sutra")` |
| **record** | one happening, with your fields attached | created for you by `log.info(...)` |
| **handler** | where the line goes | `FileHandler` → `logs/sutra.jsonl` |
| **formatter** | how the record becomes text | **the seam** — subclass it |

The seam is one method, `format(record)`, which returns a string. Return JSON and you have structured
logging. There is no library to add and nothing to configure beyond three lines of wiring, which is
why Sutra's own house rule — *prefer the stdlib* ([CLAUDE.md](../../../../CLAUDE.md)) — is not a
hardship here.

Two details do most of the work, and both are easy to get wrong.

**`extra=` is the interface.** `log.info("tool_call", extra={"tool": "lookup_article"})` attaches your
fields to the record as attributes. The formatter then has to *find* them, and finding them means
knowing which attributes were yours and which are `LogRecord`'s own eighteen built-ins. The mechanism
below computes that set rather than hardcoding it.

**Four fields come free.** `ts`, `level`, `logger` and `event` are supplied by the formatter on every
line, so no caller can forget them. That is the printed boxes on the chart: the form makes the
right thing the default.

## Why Sutra needs it

Because Sutra's log has to be readable by three things that do not exist yet.

Day 23's tests will assert on log lines, which means parsing them — and `json.loads` on a line is a
one-liner while a regex over a sentence is a maintenance burden. Day 24 counts requests per model by
filtering on a field. Day 79 onwards replays sessions and scores them, and Day 84 ships the whole lot
into OpenTelemetry, which is field-oriented all the way down.

Every one of those is cheap if the log is JSON Lines and expensive if it is prose. And the choice is
being made now, on the day the format has four callers, rather than in Phase 13 when it has forty.

## The mechanism

A formatter, a file handler, and a logger that writes JSON Lines and nothing to the terminal.

```python
# days/day-22-structured-logging/lab/jsonl.py
"""One JSON object per line, written by stdlib logging. The whole toolbox is in the stdlib."""

import json
import logging
import time
from pathlib import Path

LOG_PATH = Path("logs/sutra.jsonl")

# Fields LogRecord always has. Anything else on the record was put there by us.
_BUILTIN = set(logging.LogRecord("", 0, "", 0, "", None, None).__dict__) | {
    "message",
    "asctime",
    "taskName",
}


class JsonLines(logging.Formatter):
    """Renders a record as one JSON object on one line."""

    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "ts": time.strftime("%Y-%m-%dT%H:%M:%S", time.gmtime(record.created))
            + f".{int(record.msecs):03d}Z",
            "level": record.levelname,
            "logger": record.name,
            "event": record.getMessage(),
        }
        # Everything passed via extra= lands on the record; copy it in.
        payload.update({k: v for k, v in record.__dict__.items() if k not in _BUILTIN})
        if record.exc_info:
            payload["exc_type"] = record.exc_info[0].__name__
        return json.dumps(payload, default=str)


def get_logger(name: str = "sutra") -> logging.Logger:
    """A logger that writes JSON lines to a file and nothing to the terminal."""
    LOG_PATH.parent.mkdir(exist_ok=True)
    logger = logging.getLogger(name)
    logger.setLevel(logging.INFO)
    logger.propagate = False  # do not also hand records to the root logger
    if not logger.handlers:
        handler = logging.FileHandler(LOG_PATH, encoding="utf-8")
        handler.setFormatter(JsonLines())
        logger.addHandler(handler)
    return logger
```

**Line by line:**

- `_BUILTIN` is computed by **constructing a throwaway `LogRecord` and reading its `__dict__`**, which
  is the honest way to answer *"which attributes are the framework's?"*. Hardcoding the eighteen names
  works today and silently drops a field the day CPython adds one.
- `| {"message", "asctime", "taskName"}` adds three that are not on a fresh record but are set later:
  `message` by `Formatter.format`, `asctime` by `formatTime`, and `taskName` by asyncio in 3.12+.
  Without `taskName` every line in an async run gains a stray field.
- `time.gmtime(record.created)` — **UTC, always.** A log with local timestamps from two machines in
  two offices cannot be merged, and merging is the only reason to have timestamps.
- `+ f".{int(record.msecs):03d}Z"` appends milliseconds, because `strftime` has no format for them and
  whole seconds are far too coarse. It is still not coarse enough:
  [1.4](1.4-timestamps-are-not-an-order.md) is about what happens when forty lines land in the same
  millisecond.
- `record.getMessage()` goes into **`event`**, not `message`. That is a naming decision with
  consequences: it says the first argument to `log.info` is an event *name* from a small vocabulary,
  not a sentence. Calling it `message` invites prose.
- `payload.update({... if k not in _BUILTIN})` is the line that makes `extra=` work. Everything you
  passed is now an attribute, and this is what distinguishes yours from the framework's.
- `if record.exc_info` adds the exception type when you log with `exc_info=True`. Only the type — the
  full traceback belongs in a field of its own, and putting a multi-line traceback in a JSON Lines
  file needs care, because a literal newline would break the one-object-per-line rule.
- `json.dumps(payload, default=str)` — `default=str` is the safety net. Anything unserialisable
  becomes its `repr` instead of raising, because **logging must never be the thing that breaks the
  run**. That is asserted in [4.3](../04-in-production/4.3-testing-that-you-logged.md).
- `logger.propagate = False` stops records also going to the root logger, which would print them to
  the terminal in the default configuration. Without it every line appears twice, once as JSON and
  once as plain text.
- `if not logger.handlers` makes `get_logger` idempotent. `logging.getLogger` returns the *same*
  object every call, so without this guard, importing twice adds a second handler and every line is
  written twice.

```python
if __name__ == "__main__":
    log = get_logger()
    log.info("run_start", extra={"invocation_id": "e-7f3a91", "user_id": "priya"})
    log.info(
        "tool_call",
        extra={"invocation_id": "e-7f3a91", "tool": "lookup_article", "article_id": "KB-104"},
    )
    log.warning(
        "tool_error",
        extra={
            "invocation_id": "e-7f3a91",
            "tool": "lookup_article",
            "kind": "timeout",
            "action": "substitute",
        },
    )
    log.info("run_end", extra={"invocation_id": "e-7f3a91", "events": 4})

    print(f"wrote {LOG_PATH} ({LOG_PATH.stat().st_size} bytes)")
    for line in LOG_PATH.read_text(encoding="utf-8").splitlines():
        print(f"  {line}")
```

**Line by line:**

- Four calls, one per happening, with the event name as the **first positional argument** and
  everything else in `extra`. That shape is the convention worth fixing now: the first argument is
  what you group by, `extra` is what you filter by.
- `log.warning` for the failure and `log.info` for the rest — the level is a routing decision, which
  is [1.3](1.3-levels-are-routing.md).
- `invocation_id` on **every** line, including the failure. That is the field
  [2.2](../02-wiring-the-run/2.2-the-correlation-id.md) is about and
  [3.2](../03-failure-lab/3.2-the-line-nobody-can-correlate.md) breaks.
- Reading the file back and printing it is not decoration: it is the check that the handler actually
  flushed and that the lines are one-per-line.

```text
  {"ts": "2026-09-03T13:52:51.147Z", "level": "WARNING", "logger": "sutra", "event": "tool_error", "invocation_id": "e-7f3a91", "tool": "lookup_article", "kind": "timeout", "action": "substitute"}
  {"ts": "2026-09-03T13:52:51.147Z", "level": "INFO", "logger": "sutra", "event": "run_end", "invocation_id": "e-7f3a91", "events": 4}
```

**Four lines, four objects, no array.** Each is independently parseable, which means a reader can
`json.loads` one line without caring about the others, and a crash mid-write costs you the last line
and nothing else.

**The four free fields are on every line and no caller supplied them.** `ts`, `level`, `logger`,
`event` — that is the printed form from the story doing its job. Each call site thought about two to
four fields; the line has six to eight.

**And every `extra` field arrived.** `article_id` on line two, `action` on line three, `events` on line
four. Different callers, different shapes, same format — which is the property that makes a log
queryable without a schema migration every time somebody logs something new.

**Now look at the timestamps.** All four lines say `13:52:51.147`. Not close — *identical*, to the
millisecond. Four events, one timestamp, and the file's own ordering is the only thing that tells you
which came first. That is not a bug in this formatter; it is what happens when a program does four
things faster than the clock ticks, and it is [1.4](1.4-timestamps-are-not-an-order.md)'s entire
subject.

## When it breaks

**A field name that collides with a `LogRecord` attribute is refused, loudly:**

```text
KeyError: "Attempt to overwrite 'name' in LogRecord"
```

`extra={"name": "priya"}` raises, because `name` is the logger's own attribute. So do `msg`, `args`,
`levelname`, `module`, `filename`, `lineno` and about a dozen others. It is a good failure — early and
specific — and it is why field names like `user_id` and `tool` are safer than `name` and `module`.

**A duplicated handler doubles every line**, silently, with no error at all. It happens when
`get_logger` is called from two modules without the `if not logger.handlers` guard, and the symptom is
a log file that is exactly twice as long as it should be and metrics that are exactly twice as high.
Nothing about that looks like a logging bug.

**And a newline inside a field breaks the format.** `json.dumps` escapes newlines to `\n`, so the file
stays one-object-per-line — but only because `json.dumps` is doing it. Writing the line by hand with
an f-string, which is the obvious first thing to try, produces a traceback spread over twelve lines
and a JSON Lines file that no reader can parse.

## In production

**Log to stdout, not to a file, in a container.** The `FileHandler` here is right for a laptop and
wrong for anything scheduled: in a container the platform collects stdout, and writing to a file means
the logs are inside a filesystem that is discarded. `StreamHandler(sys.stdout)` with the same
formatter is the one-line change, and Day 86's `docker compose` work is where it lands.

**What changes at scale** is that the field names become an interface with consumers. Once a
dashboard, an alert rule and an eval all filter on `event == "tool_error"`, renaming that value is a
breaking change. Keep the `event` vocabulary small and closed; put the variety in fields nothing
groups by.

**The failure that only appears with real traffic** is the field with unbounded values. `extra={"ts":
..., "prompt": the_whole_prompt}` is 6kB per line and turns a log into a copy of your traffic — and
[3.1](../03-failure-lab/3.1-the-log-that-leaked.md) is what happens when that prompt contains a
customer's data.

**The review comment a senior engineer leaves:** *"`get_logger` adds a handler every call. Guard on
`logger.handlers` or configure logging once at startup — right now importing this from two places
doubles every line."*

**The interview question:** *"how do you do structured logging in Python without a dependency?"* The
answer that shows you have written it: *"subclass `logging.Formatter`, and in `format` build a dict
from the record and `json.dumps` it. The two things to get right are computing which record
attributes came from `extra=` rather than hardcoding the built-in list, and `default=str` so an
unserialisable value can't take down the run. It's about thirty lines and it's JSON Lines, so every
line parses independently."*
