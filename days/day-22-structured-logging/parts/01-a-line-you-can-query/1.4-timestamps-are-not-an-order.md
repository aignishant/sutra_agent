# 1.4 — Timestamps are not an order

## One-line answer

Forty log lines written in a tight loop landed in **one or two distinct milliseconds**, so sorting the
file by timestamp did not recover the order they happened in — and a monotonic counter, one extra
field, did.

## The story

Two people photograph the same goal from opposite ends of the ground.

Both cameras stamp the time. One says 14:32:07 and the other says 14:32:04, because one was set from
the phone network and the other has not been touched since the clocks went back. Put the two photos
in a folder, sort by the stamp, and the ball is in the net before the shot.

Nothing is broken. Two clocks, each reasonable, each wrong by an amount nobody measured.

The stadium's own scoreboard has a different kind of number on it: a clock that only ever counts up,
from zero, from the same start. Two people reading *that* will always agree about which happened
first.

## The idea in plain language

[1.2](1.2-one-json-object-per-line.md) put a millisecond timestamp on every line, and the four-line
output there had a detail worth going back for: **all four lines carried the same timestamp**, to the
millisecond. Not nearly the same. Identical.

That is not a defect in the formatter. It is the ordinary consequence of a program doing several
things faster than the operating system's clock ticks — the same effect
[20.2.2](../../../day-20-context-engineering-compaction/parts/02-the-config/2.2-the-turn-count-trigger.md)
ran into when ADK's compaction trigger under-counted because six events shared a timestamp. It has
now appeared twice in three days, from two completely different directions, which is a fair sign it
is a property of the world rather than of a bug.

So a timestamp is a **reading**, not a **rank**. It answers *roughly when* and it does not answer
*which first*, for three separate reasons that stack:

**Resolution.** The clock ticks in units far coarser than a function call. Windows' default timer
granularity is around 15ms; a tight loop does thousands of things inside one tick.

**Skew.** Two machines' clocks differ. Merge logs from a gateway and a worker and the ordering of the
merged file is partly a statement about NTP.

**Non-monotonicity.** A wall clock can go *backwards* — an NTP correction, a leap second, a VM
resuming from a snapshot. `time.time()` is not guaranteed to increase.

The fix is small and it is the thing this part exists to install: **add a counter.** One
monotonically increasing integer per process, stamped on every line. It says nothing about when, and
it answers *which first* exactly, within that process. Physical time for humans; a counter for
ordering.

The measurement below does the honest version of this comparison, and there is a trap in it worth
naming before you see it.

## Why Sutra needs it

Because reconstructing what happened is the entire purpose of the log, and *what happened* is a
sequence.

Sutra's `on_event_callback` fires several times per invocation
([2.1](../02-wiring-the-run/2.1-one-line-per-happening.md)), and those events are milliseconds apart
by construction — a model reply, a tool call, a tool result, a final response. If the log cannot
order them, the log cannot answer *"did the tool run before or after we decided to substitute?"*,
which is the first question in any investigation of Day 21's error policy.

It gets worse in Phase 8. A graph runs several nodes inside one invocation, and Phase 6's MCP work
puts some of them in *other processes*. At that point the log is a merge of records from machines
whose clocks disagree, and the counter that solves it inside one process no longer suffices — which
is exactly what the paper below is about.

## The paper behind it

> **Time, clocks, and the ordering of events in a distributed system**
> `doi:10.1145/359545.359563` · Communications of the ACM 21(7), 558–565 · 1978 ·
> <https://doi.org/10.1145/359545.359563>

It argued that in a system of separate processes there is no meaningful total order given by physical
clocks, and defined an ordering built from **what could have caused what** instead — maintained by a
counter per process and one rule for messages between them.

It is taught in [the paper part](../../papers/01-time-clocks-ordering.md). Read it after the parts.

## The mechanism

Forty lines in a loop, written twice — once with a counter and once without — and then sorted by
whichever field each version has.

```python
# days/day-22-structured-logging/lab/ordering.py
"""A timestamp is a reading, not a rank. Count how many lines share one, then add a counter."""

import itertools
import json
import os
import random
import time
from pathlib import Path

SEQ = os.environ.get("SEQ", "1") == "1"
LINES = 40
OUT = Path("logs/ordering.jsonl")
_seq = itertools.count(1)


def line(event: str) -> dict[str, object]:
    """One log line, with or without a sequence number."""
    now = time.time()
    record = {
        "ts": time.strftime("%Y-%m-%dT%H:%M:%S", time.gmtime(now)) + f".{int(now % 1 * 1000):03d}Z",
        "event": event,
    }
    if SEQ:
        record["seq"] = next(_seq)
    return record


OUT.parent.mkdir(exist_ok=True)
records = [line(f"step_{n}") for n in range(1, LINES + 1)]
OUT.write_text("\n".join(json.dumps(r) for r in records) + "\n", encoding="utf-8")

stamps = [r["ts"] for r in records]
distinct = len(set(stamps))
biggest = max(stamps.count(s) for s in set(stamps))

print(f"SEQ={'1' if SEQ else '0'}  {LINES} lines written to {OUT}")
print(f"  distinct timestamps      : {distinct} of {LINES}")
print(f"  most lines sharing one ts: {biggest}")
print(f"  can the log be ordered?  : {'yes, by seq' if SEQ else 'not reliably'}")

# Shuffle first. Python's sort is stable, so sorting an already-ordered list by an
# all-equal key "works" for the wrong reason - and that would prove nothing at all.
shuffled = records[:]
random.Random(42).shuffle(shuffled)

key = "seq" if SEQ else "ts"
resorted = sorted(shuffled, key=lambda r: r[key])
print(f"  sorted by {key!r}: first={resorted[0]['event']} last={resorted[-1]['event']}")
print(
    "  original order recovered : "
    f"{[r['event'] for r in resorted] == [r['event'] for r in records]}"
)
```

**Line by line:**

- `itertools.count(1)` is the counter, and it is the whole fix. One shared generator, `next()` per
  line, never reset. It is not a clock and makes no claim to be one.
- `int(now % 1 * 1000)` computes the milliseconds from the fractional part of `time.time()`, which is
  what [1.2](1.2-one-json-object-per-line.md)'s formatter does with `record.msecs`. Same resolution,
  same problem.
- `records = [line(...) for n in range(1, LINES + 1)]` builds all forty in a **tight loop**, which is
  the condition being tested. Real code does exactly this whenever an invocation emits several events.
- **`random.Random(42).shuffle(shuffled)` is the most important line in the file**, and it is there
  because the first version of this script was wrong. Without it, sorting an already-ordered list by
  an all-equal key returns the same order — Python's sort is **stable** — and the script reported
  `original order recovered: True` for the broken version. It passed for the wrong reason, which is
  the trap Day 19, 20 and 21 each found in their own test suites.
- `Random(42)` rather than the global `random`, so the shuffle is the same on every run and the result
  is reproducible.
- `sorted(shuffled, key=...)` sorts the shuffled copy but compares against the **original** order, so
  the question being asked is *"can this field reconstruct what happened?"* rather than *"does sorting
  return something?"*.
- `distinct` and `biggest` are printed before the ordering result, because they are the *cause*: the
  ordering fails because the timestamps collide, and seeing the collision count first makes the
  failure unsurprising.

```bash
cd days/day-22-structured-logging/lab
SEQ=0 uv run python ordering.py
SEQ=1 uv run python ordering.py
```

**Line by line:**

- Two runs, one environment variable: no counter, then a counter.
- Pure Python and one small file. No ADK, no key, no quota.

Measured on 2026-09-03:

```text
SEQ=0  40 lines written to logs\ordering.jsonl
  distinct timestamps      : 2 of 40
  most lines sharing one ts: 22
  can the log be ordered?  : not reliably
  sorted by 'ts': first=step_10 last=step_28
  original order recovered : False

SEQ=1  40 lines written to logs\ordering.jsonl
  distinct timestamps      : 1 of 40
  most lines sharing one ts: 40
  can the log be ordered?  : yes, by seq
  sorted by 'seq': first=step_1 last=step_40
  original order recovered : True
```

**Two distinct timestamps for forty lines**, and in the second run **one**. Twenty-two lines share a
single millisecond. The timestamp is not slightly too coarse for this job; it is off by more than an
order of magnitude.

**Sorted by `ts`, the first line is `step_10` and the last is `step_28`.** Not the first and last
things that happened — just whichever landed there once the ties were broken arbitrarily. That is
what "sorted by timestamp" means on a file like this, and it looks perfectly orderly.

**`original order recovered: False`.** One field, added, and it becomes `True` with `first=step_1
last=step_40`.

The distinct-timestamp count moves between runs — `2` in one and `1` in the other — depending on
where the millisecond boundary happens to fall while the loop runs. That variation is itself the
point: **the ordering you get depends on timing you do not control.** A file that sorts correctly
today can sort differently tomorrow with no change to the code.

## When it breaks

There is no exception. The failure is an investigation that reaches a confident wrong conclusion, and
the honest thing to say about it is that **it is a matter of luck how bad it is on any given run.**

Here is a real Sutra invocation's log, six lines, sorted by timestamp after being shuffled — measured
on 2026-09-03:

```text
distinct timestamps: 5 of 6

{"ts": "2026-09-03T14:08:21.478Z", "event": "run_start", "seq": 1}
{"ts": "2026-09-03T14:08:21.532Z", "event": "event", "seq": 2}
{"ts": "2026-09-03T14:08:21.533Z", "event": "tool_error", "seq": 3}
{"ts": "2026-09-03T14:08:21.535Z", "event": "event", "seq": 4}
{"ts": "2026-09-03T14:08:21.539Z", "event": "event", "seq": 5}
{"ts": "2026-09-03T14:08:21.539Z", "event": "run_end", "seq": 6}

seq order after sorting by ts: [1, 2, 3, 4, 5, 6]
recovered: True
```

**It worked.** Five of six timestamps are distinct, because a real run does actual asynchronous work
between events rather than spinning in a loop, so most lines land in their own millisecond. Sorting
by time recovered the order.

That is the dangerous outcome, and it is worth sitting with rather than skipping past. Three things
are true about this output at once:

**One pair already collides.** `seq 5` and `seq 6` share `.539`. At six lines. Their relative order in
that listing is decided by the stability of the sort, not by anything in the data — so the log is
*already* ambiguous, on the smallest possible run, and nothing in the output says which pair is the
uncertain one.

**It worked here because the sort was stable and the input happened to be nearly ordered.** That is
exactly the false pass the mechanism's `shuffle` line exists to prevent. Change the reader — a log
viewer, a database query, a different language's sort — and the guarantee evaporates, because
stability is not something a log format can promise.

**And a tighter loop makes it much worse, not slightly worse.** The mechanism above put forty lines in
one or two milliseconds and lost the order completely. Six lines in five milliseconds is fine; forty
in one is not; and the difference between those two is how busy the process happens to be.

So the failure mode is not *"logs sorted by time are wrong"*. It is *"logs sorted by time are right
until they are not, and nothing tells you which day you are having."* A `seq` field removes the
question.

## In production

**Put `seq` on every line and make it the tie-break, not the sort key.** Sort by `(ts, seq)`: the
timestamp puts the line roughly in the day and the counter resolves lines that share a tick. Sorting
by `seq` alone stops working the moment there is more than one process.

**What changes at scale** is that a per-process counter stops being enough, and the replacement is the
one the paper describes: carry the counter across process boundaries so a receiver's counter jumps
past the sender's. Phase 6's MCP work is where Sutra needs that, and knowing the shape of the answer
now is why this part cites a 1978 paper rather than a logging tutorial.

**The failure that only appears with real traffic** is the counter that resets. A process restart
starts `itertools.count(1)` again, so a day's log contains `seq: 1` fifty times. The fix is to
namespace it — `seq` is only meaningful within one `invocation_id`, or within one process id — and to
say so in the field name if there is any doubt.

**The review comment a senior engineer leaves:** *"these two lines have the same timestamp and the
order in the file is the only thing distinguishing them. Add a sequence number — we've already been
bitten by this once in the compaction trigger."*

**The interview question:** *"you have a log file and you need to know what happened first. How?"* The
answer that shows you have been misled by one: *"not by the timestamp alone. In a tight loop we had
forty lines land in one or two milliseconds, so sorting by time didn't recover the order at all — it
gave `step_10` first. A monotonic counter per process fixes it inside one process, and across
processes you need the counter to travel with the message, which is Lamport's rule from 1978."*
