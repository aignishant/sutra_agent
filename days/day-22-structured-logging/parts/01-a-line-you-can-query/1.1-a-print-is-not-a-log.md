# 1.1 — A print is not a log

## One-line answer

`print("[safety_net] kb lookup failed for KB-104")` and a ten-field JSON line carry the same news,
and only one of them can answer *how many times before lunch* — five questions, and the print
answers none of them without a human reading it.

## The story

The corner shop's owner keeps the day's sales in his head.

He is good at it. Ask him on Tuesday afternoon whether the bread is moving and he will tell you, and
he will be right. Ask him whether it moves better on Thursdays than it used to, and he will tell you
that too, and now he might be wrong, and neither of you can check.

Then the accountant asks for the takings for the fourteenth of March.

Nothing was hidden and nothing was lost through carelessness. It just was never written down in a
form that a second person, later, could add up.

## The idea in plain language

By now Sutra has a plugin that knows when a tool fails — Day 21 built it — and what that plugin
currently does with the knowledge is `print()`. That worked, in the sense that you saw a line appear.

The trouble arrives a week later, when somebody asks a question about the past. *When did the
knowledge base start failing? How many times before lunch? Which tickets? Was it the same customer
each time?* Every one of those is answerable in principle — the information passed through the
process — and none of them is answerable in practice, because the answer was formatted for a human
who is no longer looking, and written to a terminal that no longer exists.

The distinction is not about being tidier. It is about **who the reader is**.

| | `print()` | a log line |
| --- | --- | --- |
| written for | a person, now, watching | a program, later, filtering |
| goes to | standard output, which is a terminal | a file, which survives the process |
| structure | a sentence | named fields |
| can be filtered | with `grep`, by luck | by field, exactly |
| carries a level | no | yes, and it routes |
| carries who and when | only if you remembered | always, from the formatter |

This is [21.1.2](../../../day-21-errors-surface-not-swallow/parts/01-who-hears-it/1.2-an-error-is-a-fact.md)
pointed at a different surface. There, the argument was that an error crossing a boundary should be a
**fact with fields** rather than a sentence, because code has to branch on it. Here, the same argument
applies to the *record*: the thing you will search at 2am should be a fact with fields, because you
will be asking it questions nobody anticipated.

And there is a Principle 12 reason, which is the one that makes it Sutra's business rather than a
matter of taste. **Everything is a trace.** Events gave Sutra a trace of the conversation
([Day 7](../../../day-07-events-and-streaming/LESSON.md)); state deltas a trace of facts
([Day 17](../../../day-17-state-scopes-and-lifetimes/LESSON.md)); artifacts a trace of files
([Day 18](../../../day-18-artifacts-that-survive/LESSON.md)). The system's own behaviour — which tool
ran, what failed, what it decided — has no trace at all, and evaporates when the process exits.

## Why Sutra needs it

Because Day 21 ended with an error policy that makes decisions, and a decision nobody recorded is
indistinguishable from no decision.

`on_tool_error_callback` now classifies a failure, substitutes a marked result, and lets the run
continue. That is the correct behaviour and it is **invisible**: the run succeeds, the user gets a
degraded answer, and nothing anywhere says a substitution happened. Day 21's own
[2.4](../../../day-21-errors-surface-not-swallow/parts/02-four-hooks/2.4-the-ladder.md) named the
consequence — *anything you rescue at rung one has to be counted at rung one* — and left the counting
for today.

Day 23 tests tools and callbacks, and needs to assert on what they recorded. Day 24 counts requests
per model, which is a log line with a number in it. Day 84 replaces this with OpenTelemetry tracing —
the industrial-strength sibling — and inherits today's field names. Getting the fields right now is
cheaper than renaming them across a tracing backend later.

## The mechanism

The same happening, printed and logged, put to five questions an operator actually asks.

```python
# days/day-22-structured-logging/lab/print_vs_log.py
"""The same happening, printed and logged. Then ask both of them a question."""

import json

PRINTED = "[safety_net] kb lookup failed for KB-104, substituting"

LOGGED = {
    "ts": "2026-09-03T14:22:07.481Z",
    "level": "WARNING",
    "event": "tool_error",
    "tool": "lookup_article",
    "kind": "timeout",
    "target": "kb.internal:8080",
    "action": "substitute",
    "invocation_id": "e-7f3a91",
    "session_id": "s-4521",
    "user_id": "priya",
}

QUESTIONS = {
    "how many failures before lunch?": "ts",
    "which tool?": "tool",
    "which conversation?": "invocation_id",
    "did we retry or substitute?": "action",
    "is this the same customer as the last one?": "user_id",
}

print(f"printed ({len(PRINTED)} chars):\n  {PRINTED}\n")
print(f"logged  ({len(json.dumps(LOGGED))} chars, {len(LOGGED)} fields):")
print(f"  {json.dumps(LOGGED)}\n")

print(f"{'question':<45} {'from the print':<16} {'from the log'}")
for question, field in QUESTIONS.items():
    answerable = field in LOGGED
    print(f"{question:<45} {'no':<16} {LOGGED[field] if answerable else 'no'}")

print(f"\n{len(QUESTIONS)} questions. the print answers none of them without a human reading it.")
```

**Line by line:**

- `PRINTED` is not a straw man. It has a component tag, the failing resource and the action taken —
  it is a *good* print statement, better than most, and it is the one Day 21's plugin actually
  contained.
- `LOGGED` carries the same news plus the four things the sentence left out: **when**, at what
  **level**, in which **conversation**, and for which **user**. Three of those are the fields a
  formatter can supply for free, which is the point of
  [1.2](1.2-one-json-object-per-line.md).
- `QUESTIONS` maps each question to **the single field that answers it**. That mapping is the
  argument: a question that maps to a field is a query; a question that maps to nothing is a
  conversation with whoever was watching.
- `"how many failures before lunch?": "ts"` — the timestamp is what makes counting possible, and it
  is the field a `print` almost never has. `[safety_net] kb lookup failed` tells you it happened, not
  when, and *"how many"* needs both.
- `"is this the same customer as the last one?": "user_id"` is the question that decides whether you
  have one angry customer or an outage, and it is unanswerable from any number of prints.
- `field in LOGGED` is a membership test, so the table is a mechanical read of the data above rather
  than five hand-written rows that could drift from it.
- The `'no'` column is hardcoded, and that deserves saying plainly: a `print` *cannot* answer any of
  these programmatically, so there is nothing to compute. Writing `'no'` is not a rhetorical shortcut,
  it is the whole finding.

**Line by line:**

- Pure Python: two constants and five questions. No ADK, no key, no quota.

Measured on 2026-09-03:

```text
printed (54 chars):
  [safety_net] kb lookup failed for KB-104, substituting

logged  (249 chars, 10 fields):
  {"ts": "2026-09-03T14:22:07.481Z", "level": "WARNING", "event": "tool_error", "tool": "lookup_article", "kind": "timeout", "target": "kb.internal:8080", "action": "substitute", "invocation_id": "e-7f3a91", "session_id": "s-4521", "user_id": "priya"}

question                                      from the print   from the log
how many failures before lunch?               no               2026-09-03T14:22:07.481Z
which tool?                                   no               lookup_article
which conversation?                           no               e-7f3a91
did we retry or substitute?                   no               substitute
is this the same customer as the last one?    no               priya

5 questions. the print answers none of them without a human reading it.
```

**Five questions, five `no`s.** Not four — the print does not answer a single one of them in a way a
program could use. You can *read* it and infer the tool, and that is exactly the difference: reading
is a person, and a person does not scale to three hundred thousand lines.

**249 characters against 54**, which is the honest cost. The log line is four and a half times bigger,
and [4.1](../04-in-production/4.1-what-to-log-and-what-to-count.md) turns that into gigabytes per day
at a realistic scale. It is a real trade and it is worth naming rather than glossing.

**Ten fields, and only four came from the caller.** `ts`, `level`, `logger` and `event` are the
formatter's job — nobody has to remember them. That leaves six fields of actual thought per line,
which is the difference between structured logging being a discipline and being a chore.

## When it breaks

`print` does not raise, which is the whole problem. But there is a real failure with real output, and
it is the one that bites first in a deployed process:

```text
ValueError: I/O operation on closed file.
```

That is `print` writing to a standard output that has gone away — a container whose log collector has
stopped, a subprocess whose parent has closed the pipe. `print` writes to a stream it does not own,
with no error handling, so **the failure reporting takes down the process.**

Run the same thing through `logging` and it does not. Measured on 2026-09-03, closing `sys.stdout`
and then logging to it:

```text
--- Logging error ---
Traceback (most recent call last):
  File ".../logging/__init__.py", line 1163, in emit
    stream.write(msg + self.terminator)
ValueError: I/O operation on closed file.
Call stack:
  File "<string>", line 12, in <module>
Message: 'to a closed stdout'
Arguments: ()
logging did NOT raise
```

Same underlying `ValueError`, and `logging` **caught it, reported it on stderr with the call stack,
and let the program continue.** That is not a detail of taste: an observability layer that can kill
the thing it observes is worse than none, and it is one of several reasons the house rule
([CLAUDE.md](../../../../CLAUDE.md)) is `logging` over `print` in library code.

The quieter failure has no output at all: the line went to a terminal that has since been closed, or
to a container's stdout that is rotated hourly and retained for a day. The information existed and was
never persisted, which is the same outcome as never having logged it and feels like having logged it.

## In production

**One line per happening, and the happening is a noun.** `run_start`, `tool_call`, `tool_error`,
`run_end`. Not a sentence, not a message that varies — a small closed vocabulary in the `event` field,
because that is the field everything else groups by. Free-text messages are the thing that makes a log
ungroupable, and they are what `print` encourages.

**What changes at scale** is that the log stops being read by you and starts being read by a query.
Nobody opens a 300,000-line file; they filter it to eleven lines. That inverts the design priority:
the line does not need to be readable, it needs to be *selectable*, and every field you leave out is a
filter somebody cannot apply.

**The failure that only appears with real traffic** is the log that is technically structured and
practically useless because every line says the same thing. A hundred `tool_error` lines with no
`tool`, no `kind` and no `invocation_id` is a count, not a record, and a count is
[4.1](../04-in-production/4.1-what-to-log-and-what-to-count.md)'s job at a fraction of the size.

**The review comment a senior engineer leaves:** *"this prints. Use the logger — and put the ticket id
and the invocation id in `extra` so we can find this line again from a customer complaint."*

**The interview question:** *"what is wrong with print for logging?"* The answer that shows you have
searched a real log: *"it is written for whoever is watching, and nobody is watching. It has no
timestamp unless you add one, no level so you cannot route it, no fields so you cannot filter it, and
it goes to a stream that does not outlive the process. The test I use is whether I could answer *how
many, in which conversation, for which user* — and a print answers none of the three."*
