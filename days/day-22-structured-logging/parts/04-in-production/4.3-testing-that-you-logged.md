# 4.3 — Testing that you logged

## One-line answer

Eight cases assert that the line is one JSON object, carries its four required fields, keeps every
`extra`, survives an unserialisable value, and has been scrubbed of three secret shapes — and
breaking the formatter turns three of them red, two with a bare `KeyError` and one with a message
that actually explains itself.

## The story

The lifeguard's radio gets a check at the start of every shift.

Two of them stand at opposite ends of the pool and one says a word and the other says it back. It
takes four seconds and it looks faintly silly, and the reason they do it is that a radio which is not
working looks exactly like a radio which is working.

There is no moment during a rescue at which you find out and can do something about it.

## The idea in plain language

Logging has a structural problem that most code does not: **it has no consumer inside the program.**
A function that returns a wrong value breaks its caller. A log line that is missing, malformed or
empty breaks nothing at all — the run succeeds, the tests pass, and the cost lands weeks later on
somebody trying to answer a question.

So logging is code with no natural test, which means it needs a deliberate one. There are four
things worth asserting, and only the fourth is obvious:

**That the line is well-formed.** One JSON object, no embedded newline. This is what makes every
downstream reader possible, and it is one `json.loads` away from being checked.

**That the required fields are there.** `ts`, `level`, `logger`, `event` come from the formatter, so
this is a test of the formatter rather than of any call site — and it is the assertion that catches a
refactor of `format()`.

**That `extra` arrives.** This is the interface
([1.2](../01-a-line-you-can-query/1.2-one-json-object-per-line.md)), and the whole value of structured
logging is that `tool`, `kind` and `invocation_id` land on the line. A formatter that drops them
produces a log that is still valid JSON and answers nothing.

**And that logging cannot break the run.** Pass an unserialisable object and the line must still be
written. This is the assertion nobody writes and it is the one that matters most, because a logging
call that raises turns an observability feature into an outage —
[21.4.2](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.2-the-handler-that-became-the-error.md)
measured exactly that shape.

Plus one that is specific to this day: **that the scrub filter still works**
([3.1](../03-failure-lab/3.1-the-log-that-leaked.md)). One case per secret shape, so a failure names
which pattern stopped matching rather than reporting *"a secret leaked"*.

All of it runs with no key, no network and no ADK. Logging is pure computation over a `LogRecord`, so
these are the cheapest tests in the repository.

## Why Sutra needs it

Because every failure this day has described is silent, and a test is the only thing that is not.

An empty log file because the plugin was never installed
([2.1](../02-wiring-the-run/2.1-one-line-per-happening.md)). A failure line with no `invocation_id`
([3.2](../03-failure-lab/3.2-the-line-nobody-can-correlate.md)). A leaked email address
([3.1](../03-failure-lab/3.1-the-log-that-leaked.md)). A formatter refactor that quietly stops copying
`extra`. Not one of those produces an error, a red test or a changed output — they change the *log*,
and nothing reads the log.

And these tests go into the default suite rather than behind a `live` marker, which is what decides
whether they ever run. `./m check` executes on every change; anything needing a key is skipped and
therefore protects nothing.

## The mechanism

Eight cases over a formatter and a filter, with one helper that renders a record without touching a
file.

```python
# days/day-22-structured-logging/lab/test_logging_demo.py
"""Asserting that you logged, and that the line is usable - with no key and no network."""

REQUIRED = ("ts", "level", "logger", "event")


def render(logger_name: str, level: int, message: str, **fields: object) -> dict[str, object]:
    """Format one record through JsonLines and hand back the parsed object."""
    record = logging.LogRecord(logger_name, level, __file__, 1, message, None, None)
    record.__dict__.update(fields)
    return json.loads(JsonLines().format(record))


def test_every_line_is_one_json_object() -> None:
    """A reader splits on newlines, so a line that is not an object is a corrupt log."""
    rendered = JsonLines().format(
        logging.LogRecord("sutra", logging.INFO, __file__, 1, "run_start", None, None)
    )
    assert "\n" not in rendered
    assert isinstance(json.loads(rendered), dict)


def test_the_four_required_fields_are_always_present() -> None:
    """No caller has to remember these; the formatter supplies them."""
    line = render("sutra", logging.INFO, "run_start")
    for field in REQUIRED:
        assert field in line, f"the formatter dropped {field!r}"


def test_extra_fields_survive_to_the_line() -> None:
    """`extra=` is the interface; if it does not arrive, the log is prose again."""
    line = render(
        "sutra", logging.WARNING, "tool_error", tool="lookup_article", kind="TimeoutError"
    )
    assert line["tool"] == "lookup_article"
    assert line["kind"] == "TimeoutError"
    assert line["event"] == "tool_error"
    assert line["level"] == "WARNING"


def test_the_correlation_id_is_present_on_a_failure_line() -> None:
    """The failure line is the one you most need to correlate - see 3.2."""
    line = render("sutra", logging.WARNING, "tool_error", invocation_id="e-abc123", tool="t")
    assert line.get("invocation_id"), "a failure line with no invocation_id cannot be correlated"


def test_a_value_that_is_not_json_serialisable_does_not_kill_the_run() -> None:
    """Logging must never be the thing that breaks. `default=str` is why."""
    line = render("sutra", logging.INFO, "event", obj=object())
    assert isinstance(line["obj"], str)


@pytest.mark.parametrize("name", sorted(SECRETS))
def test_the_scrub_filter_removes_each_known_secret_shape(name: str) -> None:
    """One case per secret shape, so a failure says which pattern stopped matching."""
    samples = {
        "an email address": "contact priya.sharma@acme-corp.example about it",
        "a bearer token": "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9",
        "an API key": "key=AIzaSyABCDEFGHIJKLMNOP12345",
    }
    record = logging.LogRecord("sutra", logging.WARNING, __file__, 1, "tool_error", None, None)
    record.detail = samples[name]
    assert re.search(SECRETS[name], record.detail), "the sample does not match its own pattern"
    Scrub().filter(record)
    assert not re.search(SECRETS[name], record.detail), f"{name} survived the scrub"
```

**Line by line:**

- `render(...)` builds a `LogRecord` **by hand** rather than going through a logger and a file. That
  keeps every test free of file I/O, levels and handlers — the thing under test is the formatter, so
  nothing else should be able to make these fail.
- `record.__dict__.update(fields)` is what `extra=` does internally. Doing it directly means the test
  is not also testing `Logger.info`'s argument handling, and it sidesteps the `KeyError` guard that
  would refuse a field named `name` ([1.2](../01-a-line-you-can-query/1.2-one-json-object-per-line.md)).
- `assert "\n" not in rendered` is the one that protects the format itself. JSON Lines survives on the
  promise that a newline separates records, and a single embedded newline silently corrupts every
  reader downstream.
- `assert field in line, f"the formatter dropped {field!r}"` — the message names the field. Without it
  the failure is `assert 'ts' in {...}` printed against the whole line, which is technically complete
  and hard to read.
- `render(..., obj=object())` is the unserialisable case. A bare `object()` has no JSON representation
  at all, so this asserts `default=str` is doing its job — and the assertion is
  `isinstance(line["obj"], str)`, which checks it became text rather than that it merely did not
  raise.
- `@pytest.mark.parametrize("name", sorted(SECRETS))` iterates the **same dictionary the filter uses**.
  A new secret shape added to the redaction list gains a test case automatically, which is the only way
  a redaction list and its tests stay in step.
- `assert re.search(SECRETS[name], record.detail), "the sample does not match its own pattern"` is a
  **precondition**, not the assertion. It checks the sample would have been caught, so that the
  following `assert not re.search(...)` means *"the filter removed it"* rather than *"the sample never
  matched"*. That is the presence-before-absence discipline from
  [21.4.2](../../../day-21-errors-surface-not-swallow/parts/04-failure-lab/4.2-the-handler-that-became-the-error.md).
- `sorted(SECRETS)` rather than `SECRETS` so the parametrised case ids are stable between runs.

**Now break the formatter.** Delete the one line that copies `extra` into the payload — the
`payload.update({...})` from [1.2](../01-a-line-you-can-query/1.2-one-json-object-per-line.md), which
is exactly the sort of line a refactor loses:

```text
..FFF...                                                                 [100%]
test_logging_demo.py:42: KeyError: 'tool'
test_logging_demo.py:51: AssertionError: a failure line with no invocation_id cannot be correlated
test_logging_demo.py:57: KeyError: 'obj'
```

**Three red, five green.** The five survivors are the well-formedness test, the required-fields test
and the three scrub cases — correctly, because none of them depends on `extra`. A suite where every
test goes red on one change is testing one thing repeatedly.

**And the three messages are a direct A/B on assertion quality.** Two of them say `KeyError: 'tool'`
and `KeyError: 'obj'`: true, useless, and they do not mention logging at all. The third says
**`a failure line with no invocation_id cannot be correlated`**, which tells you what broke and why it
matters, in one line, at 2am.

The difference is entirely `line["tool"]` versus `line.get("invocation_id"), "message"`. That is the
fourth consecutive day on which deliberately failing a green suite has found a weak assertion — Day 19
found two, Day 20 a `StopIteration`, Day 21 a bare `assert False`, and today two `KeyError`s. The
habit is the transferable part: **you only ever read a failure message when you have caused the
failure on purpose.**

## When it breaks

The tests themselves have a blind spot worth stating plainly, because it is large: **they assert the
shape of a line, not that a line was ever written.**

Every case above renders a `LogRecord` directly. None of them runs an agent, installs a plugin, or
opens a file — so all eight pass in a system where the logging plugin was never added to the `App`
and the log file is empty. That is
[2.1](../02-wiring-the-run/2.1-one-line-per-happening.md)'s `Runner(agent=...)` failure, and this suite
does not catch it.

The test that would is an integration one: run an invocation, read the file, assert six lines with the
same `invocation_id`. It needs no key either — the recording models from Day 21 are enough — and it
belongs in `tests/test_logging.py` beside these. `TODO(me)` in the hub's build brief.

The other blind spot is the scrub's blocklist nature, already named in
[3.1](../03-failure-lab/3.1-the-log-that-leaked.md): three passing cases prove three patterns work and
say nothing about the fourth secret shape nobody has met yet.

## In production

**Assert the required fields once, centrally, and never per call site.** There is no value in a test
per log statement — there are hundreds and they are all the same shape. One test of the formatter
covers every line the system will ever write, which is the leverage that makes testing logging worth
doing at all.

**Make the leak list a shared fixture.** `SECRETS` is imported by both the filter and the test here,
and in Sutra it becomes one constant in `sutra/logging_setup.py` used by both. A redaction list and a
test list maintained separately drift, and the one that drifts is the test — which fails silently, by
passing.

**What changes at scale** is that you start testing the *consumer*. Once a dashboard filters on
`event == "tool_error"` and an alert counts it, that string is an interface with consumers, and
renaming it is a breaking change no Python test notices. The mature version pins the vocabulary: a
test asserting the set of event names the system can emit, so adding one is a deliberate act.

**The failure that only appears with real traffic** is the field that is present and always empty.
`invocation_id: null` on every line passes `field in line` and correlates nothing. Asserting
truthiness rather than presence — `assert line.get("invocation_id")`, as the correlation test does —
is a one-character difference that catches it.

**The review comment a senior engineer leaves:** *"these test the formatter, which is good, but they'd
all pass with the plugin uninstalled and an empty log file. Add one that runs an invocation and counts
lines in the file."*

**The interview question:** *"do you test your logging?"* The answer that shows you have been burned:
*"the formatter, yes — that the line is one JSON object, that the required fields are always there,
that `extra` arrives, and that an unserialisable value can't make the logging call raise. Then one
integration test that runs a request and asserts the lines exist with a shared correlation id, because
the formatter tests all pass happily against an empty log file."*
