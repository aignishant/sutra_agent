# 4.2 — A log file only grows

## One-line answer

`RotatingFileHandler` bounded 200 lines to 6,445 bytes across four files — and **silently discarded
96 of them**, including the first line ever written, which is the trade it makes and does not mention.

## The story

The kitchen bin has a bag in it and the bag has a size.

When it is full somebody ties it and puts it out, and a new bag goes in. The kitchen never fills up,
which is the point, and the cost is that last Tuesday's rubbish is gone and there is no way to get it
back if it turns out you threw away a receipt.

Everybody accepts that trade without discussing it, because the alternative is a kitchen you cannot
walk through.

The bit that catches people out is the *other* bin — the one in the garage that nobody ever empties,
which is fine for years and then is a problem you have to hire a van for.

## The idea in plain language

A `FileHandler` appends. That is all it does, and it does it forever. There is no size at which it
stops, no age at which it prunes, and nothing that warns you.
[4.1](4.1-what-to-log-and-what-to-count.md) put a number on where that becomes real — 6.15 GB a day
at five million runs — and this part is what you do about it.

The stdlib's answer is `logging.handlers.RotatingFileHandler`, and it takes two arguments that
together define a **ceiling**:

- `maxBytes` — when the current file reaches this, rotate.
- `backupCount` — keep this many old files.

Rotating means `sutra.jsonl` is renamed to `sutra.jsonl.1`, the existing `.1` becomes `.2`, and so on,
and anything past `backupCount` is **deleted**. So the total on disk is bounded at roughly
`maxBytes × (backupCount + 1)`, and it stays there forever.

That is exactly what you want, and the part worth saying out loud — because the documentation states
it and nobody reads it as a warning — is the other half: **rotation is deletion.** The oldest lines
do not move somewhere colder. They are removed, permanently, without a log line saying so, by the
component whose job is logging.

Which means the choice is not *"rotate or do not rotate"*. It is:

| | unbounded | rotating |
| --- | --- | --- |
| disk | grows until the volume is full | bounded, permanently |
| history | complete | the most recent `maxBytes × (backupCount + 1)` |
| failure mode | the disk fills and **the application stops** | old evidence is gone when you go looking |
| tells you | nothing | nothing |

Neither column has a warning in the last row, and that is the reason this is a `production` part
rather than a footnote. Both failures are silent; you are choosing which one you would rather have.
For almost every system the answer is the right-hand column, because a full disk takes the whole
service down and a missing log line loses you one investigation.

## Why Sutra needs it

Because Sutra's `logs/` directory is on a laptop that also has a `.venv` in it, and because Phase 13
puts Sutra in a container.

The laptop case is mundane and immediate: `logs/sutra.jsonl` is gitignored (the hub's §3 sets that up),
so nothing in the repository grows — but the file does, every run, forever, and nobody notices a
gitignored file. A `RotatingFileHandler` with a modest ceiling means the directory has a maximum size
and you never think about it again.

The container case is the one that decides the design. In a container, logs go to **stdout** and the
platform handles retention ([2.3](../02-wiring-the-run/2.3-adk-logs-too.md) touched this), so
rotation is not your problem — and the rotation you configured on a laptop is dead code that writes
to a filesystem that is discarded. Day 86 builds the "Cloud-Run-shaped" `docker compose` version, and
knowing *which* of the two handlers is appropriate where is the actual lesson.

## The mechanism

Two hundred lines, written twice — once through a plain `FileHandler` and once through a rotating one
with a deliberately small ceiling — then counted on disk.

```python
# days/day-22-structured-logging/lab/rotation.py
"""A log file only grows. RotatingFileHandler is the stdlib's answer, and it has a sharp edge."""

ROTATE = os.environ.get("ROTATE", "1") == "1"
LOG_DIR = Path("logs/rot")
LOG_FILE = LOG_DIR / "sutra.jsonl"
MAX_BYTES = 2_000
BACKUPS = 3
LINES = 200

for stale in LOG_DIR.glob("sutra.jsonl*"):
    stale.unlink()
LOG_DIR.mkdir(parents=True, exist_ok=True)

log = logging.getLogger("rotation-demo")
log.handlers.clear()
log.setLevel(logging.INFO)
log.propagate = False
if ROTATE:
    handler = logging.handlers.RotatingFileHandler(
        LOG_FILE, maxBytes=MAX_BYTES, backupCount=BACKUPS, encoding="utf-8"
    )
else:
    handler = logging.FileHandler(LOG_FILE, encoding="utf-8")
handler.setFormatter(logging.Formatter("%(message)s"))
log.addHandler(handler)

for n in range(1, LINES + 1):
    log.info('{"event": "tool_call", "seq": %s, "tool": "lookup_article"}', n)

handler.close()
files = sorted(LOG_DIR.glob("sutra.jsonl*"))
total = sum(f.stat().st_size for f in files)
kept = sum(len(f.read_text(encoding="utf-8").splitlines()) for f in files)

print(f"ROTATE={'1' if ROTATE else '0'}  wrote {LINES} lines")
print(f"  files on disk : {len(files)}  ({', '.join(f.name for f in files)})")
print(f"  bytes on disk : {total:,}")
print(f"  lines still readable: {kept} of {LINES}")
# Exact match: 'seq": 1' would also match 'seq": 100'.
oldest = any('"seq": 1,' in f.read_text(encoding="utf-8") for f in files)
print(f"  the very first line still on disk: {oldest}")
print(f"  bounded?      : {'yes, at ~' + str(MAX_BYTES * (BACKUPS + 1)) if ROTATE else 'no'}")
```

**Line by line:**

- `MAX_BYTES = 2_000` is absurdly small on purpose, so 200 short lines cross it several times and the
  behaviour is visible in a file you can run instantly. A real value is megabytes.
- `BACKUPS = 3` gives four files total — the live one plus three — and therefore a ceiling of about
  8,000 bytes. The arithmetic `maxBytes × (backupCount + 1)` is printed at the end rather than asserted
  in prose.
- `for stale in LOG_DIR.glob("sutra.jsonl*"): stale.unlink()` cleans **before** the handler opens
  anything, for the Windows reason from
  [2.1](../02-wiring-the-run/2.1-one-line-per-happening.md): an open handler holds a lock and unlink
  raises.
- The `glob` pattern is `sutra.jsonl*` with the star, because rotation creates `sutra.jsonl.1`,
  `.2`, `.3`. A cleanup that only removes `sutra.jsonl` leaves the backups and the next run's counts
  are wrong.
- `log.info('...{"seq": %s...}', n)` uses **`logging`'s own `%s` interpolation** rather than an
  f-string. That is the idiom for a reason: the formatting only happens if the record survives the
  level filter, so a `DEBUG` line that is filtered out costs nothing to build.
- `handler.close()` before measuring. Without it the last records may still be in a buffer and the
  byte counts are short — a measurement error that looks like a smaller log.
- `kept` counts lines across **all** files, so it is the honest total of what is still readable rather
  than what is in the current file.
- `'"seq": 1,'` with the trailing comma is the exact-match probe, and the comment says why. The first
  version of this line used `'seq": 1'`, which also matches `seq": 100` and `seq": 15`, and reported
  the first line as present when it had been deleted. That is the fourth time this week a probe has
  passed for the wrong reason.

```bash
cd days/day-22-structured-logging/lab
ROTATE=0 uv run python rotation.py
ROTATE=1 uv run python rotation.py
```

**Line by line:**

- `ROTATE=0` first: unbounded, everything kept.
- Pure stdlib and a small directory. No ADK, no key, no quota.

Measured on 2026-09-03:

```text
ROTATE=0  wrote 200 lines
  files on disk : 1  (sutra.jsonl)
  bytes on disk : 12,292
  lines still readable: 200 of 200
  the very first line still on disk: True
  bounded?      : no

ROTATE=1  wrote 200 lines
  files on disk : 4  (sutra.jsonl, sutra.jsonl.1, sutra.jsonl.2, sutra.jsonl.3)
  bytes on disk : 6,445
  lines still readable: 104 of 200
  the very first line still on disk: False
  bounded?      : yes, at ~8000
```

**6,445 bytes against 12,292 — bounded, as advertised**, and it would still be about 6,445 after two
million lines. That is the whole benefit and it is a real one: the directory has a maximum size and
nobody has to watch it.

**And 104 lines of 200.** Ninety-six lines are gone. Not archived, not compressed — deleted, by the
logging handler, with no line in the log saying it happened and no return value anybody checks.

**`the very first line still on disk: False`.** The oldest evidence is the first to go, which is
precisely backwards from what an investigation wants: *"when did this start?"* is a question about the
oldest lines, and they are the ones rotation removes first.

**Four files, and only one of them has the name you configured.** `sutra.jsonl.1` through `.3` are the
backups, and any reader that opens `sutra.jsonl` alone sees the most recent 2,000 bytes and believes
that is the log. Every count in the `ROTATE=1` arm above is across all four files; a naive reader would
have reported far fewer.

## When it breaks

The unbounded arm's failure is the one that takes a service down, and it is the only failure in this
day that is genuinely loud:

```text
OSError: [Errno 28] No space left on device
```

That is the standard `ENOSPC` text rather than a line captured here — filling a volume is not
something this lab does on purpose. What matters is what it is *not*: it is not a logging error. It is
*every* write in the process failing — the database driver, the
temp file, the artifact save — because a gitignored log file nobody was watching filled the volume.
The application does not degrade; it stops. That is the failure the right-hand column of the table
exists to prevent, and it is why rotating is the correct default despite the deletion.

The rotating arm's failure has no output at all: you go looking for the line that would have explained
an incident, and the window has moved past it. An investigation that ends in *"the logs don't go back
that far"* is this part's failure mode, and it is the reason `maxBytes` and `backupCount` are a
**retention decision** rather than a disk-space one — the question is not "how much space can I
spare?" but "how far back do I need to be able to look?".

There is also a concurrency edge worth knowing: `RotatingFileHandler` is not safe across multiple
processes writing the same file. Two workers rotating at once can lose lines or leave a file renamed
out from under the other. The stdlib's answer for that is `QueueHandler`, and the platform's answer is
stdout.

## In production

**In a container, use `StreamHandler(sys.stdout)` and delete the rotation.** The platform collects
stdout, applies its own retention, and ships it somewhere durable. Rotation on a filesystem that is
discarded when the container restarts is effort spent bounding something that was already bounded.

**Choose `maxBytes × backupCount` from how far back you need to look, then check it fits.** Work out
your bytes per day from [4.1](4.1-what-to-log-and-what-to-count.md)'s arithmetic, multiply by the days
of history you want, and *then* see whether the disk has it. Sizing from free space gives you a
retention window nobody chose.

**What changes at scale** is that local files stop being the log at all. The file becomes a buffer in
front of a shipper, retention lives in the platform, and rotation is a safety net for the case where
the shipper is down — which is the case that matters, because that is when the buffer grows.

**The failure that only appears with real traffic** is rotation during an incident. Log volume spikes
exactly when things are going wrong, so a window sized for normal traffic can rotate away the start of
an outage while you are still reading about the middle of it. The lines you most need are the ones the
spike pushed out.

**The review comment a senior engineer leaves:** *"`FileHandler` with no rotation, and `logs/` is
gitignored so nobody will see it grow. Either rotate it or send it to stdout — right now this fills the
disk eventually and takes the process with it."*

**The interview question:** *"how do you stop a log file filling the disk?"* The answer that shows you
have chosen: *"`RotatingFileHandler` with `maxBytes` and `backupCount`, sized from how far back I need
to look rather than from free space — and knowing it deletes rather than archives: we measured 200
lines becoming 104, oldest first. In a container I wouldn't rotate at all; stdout and let the platform
own retention."*
