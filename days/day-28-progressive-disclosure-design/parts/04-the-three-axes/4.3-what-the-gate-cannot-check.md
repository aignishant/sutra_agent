# 4.3 — What the gate cannot check

## One-line answer

A script can raise **suspects** on the placement axis — a body with two step lists, a standing rule, a
table, a row of record ids — but it can never issue the verdict, because whether something is an action,
a procedure, a standing value or data is a fact about the world and not about the file.

## The story

You go to see a flat with a list on your phone, because the last time you did this you forgot to check
the water pressure.

The list works. Water pressure, mobile signal in the back room, how many plug points, does the front
door actually lock, is there a place for the washing machine. You go round ticking things, and the flat
ticks everything, and the agent is pleased with you.

Then on the way out you meet the neighbour on the stairs, and you ask how it is in the monsoon, and she
tells you the lane floods to knee height twice a year and the ground floor keeps sandbags. That single
answer decides it, and it was never going to be on the list — not because you wrote a bad list, but
because the list is made of things you can stand in a room and verify, and this was not one of them.

You still take the list next time. It stops you forgetting the plug points. It has simply never been the
thing that decides.

## The idea in plain language

[4.1](4.1-three-axes-one-change.md) named three axes and said two of them have a command and one does
not. This part is about that third one, and about the specific and useful thing a script **can** still
do for it.

The reason placement is not machine-checkable is not that the code would be hard. It is that the
question is not about the file. *"Is this an action on the real world?"* depends on whether a real system
exists that could do it. *"Is this true on every call?"* depends on what the business has decided.
*"Does this change without the skill changing?"* depends on who owns the underlying store. None of those
facts is in the Markdown, and a script that guessed at them would be inventing the judgement rather than
making it.

What a script can do is **notice shapes**. Each container has a shape it tends to leave behind, and a
section that has the shape of one container while living in another is worth a person's attention:

| The shape found in a skill body | Suggests | Why it is only a suspect |
| --- | --- | --- |
| two sections that each start at step 1 | two procedures, two homes | a long procedure may legitimately restart its numbering |
| a sentence with *never*, *always* or *must* | a standing rule | the body may be quoting the rule to explain it, which is correct |
| a table | reference detail, or data behind a tool | a three-row table beside the step that uses it is right where it belongs |
| ids in the shape `KB-104` | a copy of a live store | a worked example quotes real records **on purpose** |

Every row's third column is a legitimate reason for the shape to be there. That is what makes this a
suspect list and not a lint, and the distinction is worth being pedantic about: a lint that is wrong a
third of the time gets switched off, whereas a report headed *suspects* that is wrong a third of the
time is doing exactly what it said it would.

So the shape of the whole review is three lines and one question:

- **price** — a script, exact, exit code optional.
- **routing** — a script, exact, exit code meaningful.
- **placement** — a script that lists suspects, and a **person** who answers, for each one: *what
  property does this actually have?*

## Why Sutra needs it

Because Day 31 turns checks into `./m check`, and this is the part that decides what does **not** go in.

The temptation on Day 31 will be to make the suspect list a gate — exit 1 if any suspect is raised —
because that is what the other checks do and consistency is attractive. It would be wrong, and it would
be wrong in the way that is hardest to undo: `ticket-triage`'s worked example quotes KB-104 on purpose
([27.1.5](../../../day-27-authoring-first-skills/parts/01-extraction/1.5-one-worked-example.md)), so the
gate would be red on Sutra's own correct shelf from the day it was written, and the fix everybody would
reach for is deleting the real output from the example. A gate that makes people worsen the thing it is
checking is worse than no gate.

There is a nearer use too. Day 29 audits skills Sutra did not write, and reading somebody else's body
cold is slow. A suspect list is a reading order: it says *look at these four sections first*, which is
exactly what a reviewer wants from a machine and exactly what a verdict would take away from them.

## The mechanism

Four shapes, one function each, and a report that says *suspects* rather than *findings*.

```python
# days/day-28-progressive-disclosure-design/lab/suspects.py
"""Container smells: the sections of a skill body that probably belong somewhere else."""

import re

from google.adk.skills import models

from overloaded import overloaded

SECTION = re.compile(r"^## (.+)$", re.M)
STANDING = re.compile(r"\b(never|always|must)\b", re.I)
RECORD = re.compile(r"\b[A-Z]{2,}-\d+\b")


def sections(body: str) -> list[tuple[str, str]]:
    """(heading, text) for every '## ' section of a skill body."""
    marks = list(SECTION.finditer(body))
    out = []
    for i, mark in enumerate(marks):
        end = marks[i + 1].start() if i + 1 < len(marks) else len(body)
        out.append((mark.group(1).strip(), body[mark.end() : end]))
    return out


def smells(skill: models.Skill) -> list[str]:
    """Sections whose shape suggests a different container. Suspects, never verdicts."""
    found = []
    parts = sections(skill.instructions)
    stepped = [head for head, text in parts if re.search(r"^\s*1\.", text, re.M)]
    if not stepped:
        found.append("no numbered steps anywhere - is this a procedure at all?")
    if len(stepped) > 1:
        names = ", ".join(stepped)
        found.append(f"{len(stepped)} sections have their own step 1 ({names}) - two jobs?")
    for head, text in parts:
        if STANDING.search(text):
            found.append(f"'{head}' states a standing rule - instruction or callback?")
        if RECORD.search(text):
            found.append(f"'{head}' quotes records by id - data behind a tool?")
        if text.count("|") >= 4:
            found.append(f"'{head}' is a table - data behind a tool, or a reference?")
    return found


def review(skills: list[models.Skill]) -> int:
    """Print every suspect for every skill; return how many were raised."""
    total = 0
    for skill in skills:
        found = smells(skill)
        total += len(found)
        print(skill.name)
        for line in found or ["(no suspects)"]:
            print(f"  {line}")
    print(f"\nsuspects: {total}")
    return total


review([overloaded()])
```

**Line by line:**

- `sections()` splits on `## ` headings and slices each section up to the next one, so a suspect can be
  reported **by heading**. Scanning the whole body would find the same words and tell the reviewer to go
  and look at a file rather than at a paragraph, which is the difference between a useful report and a
  true one.
- The heading split relies on the house shape Day 27 established — `## Steps`, `## Worked example`,
  `## Edge cases`
  ([27.4.3](../../../day-27-authoring-first-skills/parts/04-the-authoring-loop/4.3-sharpening-without-a-model.md)).
  A body with no `## ` headings gets one nameless section and every suspect points at the whole file,
  which is a fair degradation rather than a crash.
- `STANDING` matches `never`, `always` and `must` as **whole words**, so *"must not"* is caught and
  *"customer"* is not. Case-insensitive, because a sentence starting with *Never* is the common form.
- `RECORD = r"\b[A-Z]{2,}-\d+\b"` is deliberately about the **shape of an identifier**, not about the
  string `KB`. It catches `KB-104`, `INC-2291` and `JIRA-88` without anybody maintaining a list of
  prefixes, and it is the check most likely to fire on something correct.
- `text.count("|") >= 4` is the crudest test here and it is enough: four pipes is two rows of two
  columns, which is the smallest thing anybody would call a table. Parsing Markdown properly to answer
  this would be a dependency and a maintenance burden for a signal that is advisory anyway.
- `stepped` collects **which** sections start at step 1, so the message can name them. `len(stepped) > 1`
  is the two-procedures suspect; `not stepped` is the opposite one — a skill with no steps at all, which
  is usually data or a rule wearing a skill's clothes
  ([3.2](../03-four-containers/3.2-the-two-boundary-cases.md)).
- Every message ends in a **question mark**. That is not decoration: the tool's whole contract is that it
  asks and a person answers, and a message phrased as a statement would be read as a verdict within a
  week.
- `review()` returns a count and does **not** call `sys.exit`. Compare
  `routing_gate.py` ([2.3](../02-descriptions-as-routing/2.3-measuring-routing-without-a-model.md)),
  which does — that one is a gate and this one is a report, and the presence or absence of an exit code
  is how a reader tells them apart without reading the docstring.
- `review([overloaded()])` runs it on [4.2](4.2-refactoring-the-overloaded-skill.md)'s specimen. Swap the
  argument for `load_skills_from_dir(pathlib.Path("skills"))` to point it at your own shelf, which is
  this part's *Check yourself*.
- **Zero model calls**, no key. Four regular expressions over strings.

Run it from the lab directory:

```bash

uv run python suspects.py
cd -
```

**Line by line:**

- From the lab, so `overloaded.py` resolves as a sibling. **Zero generations.**

Measured on 2026-09-04:

```text
support-desk
  2 sections have their own step 1 (Steps, Reply style) - two jobs?
  'Rules' states a standing rule - instruction or callback?
  'Severity rubric' is a table - data behind a tool, or a reference?
  'Known articles' quotes records by id - data behind a tool?

suspects: 4
```

Four suspects, and they are exactly the four moves
[4.2](4.2-refactoring-the-overloaded-skill.md) made — the two procedures, the standing rule, the rubric,
the store. That is a good result and it is worth being precise about **why** it is a good result, because
it is easy to over-read.

The script did not decide anything. It found four sections whose shape did not match the container they
were in, and it phrased all four as questions. A person then answered them, using facts that are nowhere
in the file: that the two step lists have different owners, that *"never invent ticket contents"* is a
company rule rather than a triage rule, that the rubric is edited by support leadership, and that the
article list is a copy of a store somebody else maintains.

**None of those four answers could have come from the Markdown.** The script narrowed a five-section file
down to four questions, which is most of the work, and then stopped precisely where its knowledge ran
out.

## When it breaks

**A suspect list turned into a gate.** Point it at Sutra's real shelf and one of the lines you will get
back is this one, because `ticket-triage`'s worked example quotes `KB-104` on purpose — the real output
of a real tool call, pasted in deliberately
([27.1.5](../../../day-27-authoring-first-skills/parts/01-extraction/1.5-one-worked-example.md)):

```text
ticket-triage
  'Worked example' quotes records by id - data behind a tool?
```

That is the check working correctly and the answer being *no*. As a report it costs the reviewer a
glance. As a gate it is red on a correct shelf, and the cheapest way to make it green is to take the real
tool output out of the example — which would remove the one thing that made the example worth having.

**Suspects that are counted instead of answered.** *"We are down to two suspects this quarter."* The
number means nothing: two answered suspects and two ignored ones print the same line. What should be
recorded is the **answer** — *"'Worked example' quotes KB-104: intentional, it is real tool output"* —
and once it is recorded the same suspect stops costing anything on the next reading.

**The false negative nobody notices.** A body that describes an action in flowing prose — *"read the
ticket and note its title"* — has none of the four shapes. No numbered steps beyond the first list, no
`never`, no table, no ids. The most expensive misfiling in
[3.3](../03-four-containers/3.3-what-a-misfiling-costs.md) is invisible to every heuristic in this
script, and the honest response is to write that down rather than to add a fifth regular expression that
half-catches it.

**Regular expressions grown into a parser.** The fifth heuristic is added, then the sixth, then an
exception list for the false positives, and eighteen months later there is a small unmaintained Markdown
parser in `lab/` that nobody trusts and nobody deletes. The four here are the ones that pay for
themselves; the test for a fifth is whether it would have changed a real review.

## In production

**Ship it as a report and say so in its own output.** A line at the top — *these are shapes, not
verdicts; a person answers each one* — costs nothing and is the only thing standing between this and the
gate it must not become. The same sentence goes at the top of the source file, for the person who adds
the fifth heuristic.

**Record the answers next to the skill, not in the review thread.** A short block in the body or in
`skills/README.md` — *"the worked example quotes KB-104 deliberately"* — turns a recurring question into
a one-time one. The pull request comment where the same thing was explained is unfindable within a
month, and the next reviewer will ask again.

**Put the suspect list in the pull request, above the two gates.** Reading order matters: suspects are
questions and gates are answers, and a reviewer who reads the green ticks first has already decided
before reaching the questions.

**What changes at scale** is that the false-positive rate becomes the whole story. Two skills produce a
handful of suspects and a reviewer reads all of them. Forty skills produce a page, most of them
intentional, and the page is skimmed and then skipped. The fix is not better heuristics; it is a
**per-skill answer file**, so a suspect that has been answered once stops being printed until the section
it points at changes. That is the same idea as a lint baseline, and it is what makes an advisory check
survive its second year.

**The review comment a senior engineer leaves:** *"do not wire the suspect check into `./m check` as a
gate. It fires on our own worked example, correctly, and the only way to make it green is to delete the
real tool output that makes the example useful. Print it in the pull request, above the gates, and let a
person answer it."*

**The interview question:** *"can you automate the decision about where knowledge belongs?"* The answer
that shows you know where a tool stops: *"no, and it is worth being clear about why. Whether something is
an action, a procedure, a standing value or data depends on facts that are not in the file — whether a
system exists that could perform it, who owns the underlying store, whether the business considers the
rule unconditional. What I can automate is a suspect list: two step lists in one body, a "never" sentence,
a table, record ids in the prose. On our overloaded specimen that found all four misplaced sections and
narrowed a five-section file to four questions. Then a person answers them. I deliberately did not give
it an exit code, because it fires on our own worked example — which quotes a real article id on purpose —
and a gate that makes people delete the correct thing is worse than no gate."*
