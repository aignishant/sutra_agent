# 2.3 — Measuring routing without a model

## One-line answer

A word-overlap scorer is not what the model does, and it is a good enough proxy for the one thing that
matters — the **margin** between the best skill and the second — because a shelf whose descriptions
collide on words collides on meaning too.

## The story

The eye chart on the wall of the optician's room is a strange way to measure sight.

Nobody in real life reads rows of unrelated capital letters at six metres. The chart does not test
whether you can recognise your neighbour, drive at dusk, or find your keys — which is the whole of what
you actually wanted to know when you made the appointment.

And it works. It is quick, it is the same chart for everybody, and it turns a thing you cannot judge
from inside your own head into a number that two opticians in two cities will agree on. You do not get
sight from it; you get comparability.

The letters are not the point. Being able to say *"worse than last year"* is the point.

## The idea in plain language

The real router is a language model reading an XML index and choosing
([26.2.2](../../../day-26-loading-skills-into-adk/parts/02-the-four-tools/2.2-the-index-is-a-tool-call.md)).
It understands synonyms, it reads the name, it knows *urgent* and *priority* are related, and observing
it costs three to five generations per request
([27.4.1](../../../day-27-authoring-first-skills/parts/04-the-authoring-loop/4.1-draft-run-read-sharpen.md)).

The proxy is set arithmetic: strip the stopwords from the request and from each card, count the shared
words, sort. It understands nothing.

Be precise about where the proxy is wrong, because a measurement whose limits are unstated becomes a
belief:

- **No synonyms.** *"How bad is this?"* shares no word with either description and scores zero, and the
  real model would route it correctly.
- **No stemming.** *"drafting"* and *"draft"* are different words here. Day 27's description says
  *drafting*, so a request saying *draft* misses on that word
  ([2.1](2.1-a-description-is-a-routing-row.md)'s third row).
- **No weighting.** *"ticket"* and *"severity"* count the same, although one is domain filler and the
  other is a trigger.
- **No order, no phrases.** *"knowledge base"* is two independent words.

Given all that, why is it worth anything? Because of what it is used for. It is not used to predict
which skill fires. It is used to detect **collisions**, and collisions have a property the proxy is
good at: if two descriptions share the words that a request uses, they will share the meaning too. The
proxy under-detects — it will miss a collision expressed in synonyms — and it very rarely produces a
false alarm. For a check that runs on every change, under-detecting cheaply beats over-detecting
expensively.

So the output is a **margin**, and the gate is a threshold on the minimum margin across a fixed request
list. That number can go red, it costs nothing, and it is comparable across months — which is the eye
chart's actual contribution.

## Why Sutra needs it

Because the alternative is spending generations to find out that two descriptions collide.

Sutra has twenty a day. A single routing question costs one to three, so measuring the routing of seven
requests against a six-skill shelf, live, is not a thing that fits in a day — and it would have to be
repeated every time a description changed.

There is a second reason, and it is the one that lasts. A live routing test is not reproducible. Run
the same request twice and the model may choose differently, so a change that made routing worse is
indistinguishable from noise until you have run it several times. The proxy is deterministic: same
shelf, same requests, same numbers. That is what makes *"this pull request reduced the minimum margin
from 2 to 0"* a sentence you can put in a review.

## The mechanism

The scorer, in full. It is thirty lines and every one of them is a decision about what to measure.

```python
# days/day-28-progressive-disclosure-design/lab/route.py
"""Score every card on the shelf against a request, by shared content words."""

import re

from google.adk.skills import models

STOP = set(
    "a an and are as at be by for from has have how in is it its of on or that the to use "
    "used when where which with someone something you your do does not no i my me we can "
    "this these those what s t".split()
)


def words(text: str) -> set[str]:
    """Lowercase content words."""
    return set(re.findall(r"[a-z]+", text.lower())) - STOP


def card(skill: models.Skill) -> str:
    """What the model sees before it activates anything."""
    return f"{skill.frontmatter.name} {skill.frontmatter.description}"


def rank(skills: list[models.Skill], request: str) -> list[tuple[int, str]]:
    """Every skill scored against one request, best first."""
    asked = words(request)
    scored = [(len(asked & words(card(s))), s.name) for s in skills]
    return sorted(scored, reverse=True)


def report(skills: list[models.Skill], requests: list[str]) -> int:
    """Print the ranking for each request; return the number of ties at the top."""
    ties = 0
    for request in requests:
        scores = rank(skills, request)
        top, runner = scores[0], scores[1] if len(scores) > 1 else (0, "-")
        margin = top[0] - runner[0]
        if margin <= 0:
            ties += 1
        print(f"{request[:38]:<40} {top[1]:<20} {top[0]:>2}  margin {margin:>2}")
    return ties


# The fixed request list: things engineers actually type, plus one that no skill should match.
REQUESTS = [
    "how urgent is this ticket",
    "what priority should this ticket get",
    "triage this ticket for me",
    "draft a reply to the customer on this ticket",
    "how do we word an answer that cites a KB article",
    "can you take a look at this ticket",
    "what time do you close",
]
```

**Line by line:**

- `STOP` is written out rather than imported from a library, and that is deliberate twice over. Adding a
  dependency to remove sixty common words would be exactly the anti-pattern this repository warns
  against; and more importantly, **the stopword list decides what the number means**, so it has to be
  visible and arguable. Somebody will want `ticket` in it one day, and that is a conversation worth
  having in the open.
- `words()` returns a **set**, so a request repeating a word gains nothing. This is a vocabulary
  comparison, not a frequency one, which is the right accounting for a selection problem.
- `re.findall(r"[a-z]+", ...)` after `.lower()` splits on everything that is not a letter, so
  `customer-facing` becomes two words and `KB-104` becomes `kb`. That is crude and it is honest:
  hyphenated compounds genuinely do match on their halves in this scheme, and
  [2.1](2.1-a-description-is-a-routing-row.md) showed a row that wins because of exactly that.
- `card()` is **name plus description**, because the model sees both in the index. Leaving the name out
  would under-score `ticket-triage` on the word *triage*, which is doing real work.
- `rank()` returns `(score, name)` tuples and sorts them **reverse**, so ties break alphabetically by
  name descending. That is arbitrary and it is stable, which is what matters: two runs of the same
  shelf print the same order.
- `report()` returns the **tie count**, not a boolean. A caller can use it as an exit code, and a human
  reading the printed table can see which requests are close without any threshold being imposed on
  them.
- `margin = top[0] - runner[0]` is the number the whole part is about. A margin of zero is a tie; a
  margin of one on scores of 2 and 1 is a request where a single word decides.
- `scores[1] if len(scores) > 1 else (0, "-")` handles a one-skill shelf without a special case. On a
  shelf of one, the margin is the score, which is the right answer.
- `REQUESTS` lives **here**, at the bottom of the scorer, and every other script imports it. One list,
  one home - the same rule Day 27 spent a part on
  ([27.2.1](../../../day-27-authoring-first-skills/parts/02-what-leaves-the-prompt/2.1-one-fact-one-home.md))
  - and it keeps this module free of side effects, so importing it prints nothing.
- **Zero model calls.** No key, no network, and deterministic.

Using it as a gate is four more lines:

```python
# days/day-28-progressive-disclosure-design/lab/routing_gate.py
"""Fail if any standard request routes with a margin below the threshold."""

import pathlib
import sys

from google.adk.skills import load_skills_from_dir

from route import REQUESTS, rank

MINIMUM_MARGIN = 1

skills = sorted(load_skills_from_dir(pathlib.Path("skills")), key=lambda s: s.name)
positive = [r for r in REQUESTS if rank(skills, r)[0][0] > 0]
margins = {r: rank(skills, r)[0][0] - rank(skills, r)[1][0] for r in positive}

for request, margin in sorted(margins.items(), key=lambda kv: kv[1]):
    print(f"margin {margin:>2}  {request}")
worst = min(margins.values())
print(f"\nworst margin: {worst} (threshold {MINIMUM_MARGIN})")
sys.exit(0 if worst >= MINIMUM_MARGIN else 1)
```

**Line by line:**

- `positive` filters out the requests that match **nothing**, because a margin is meaningless for them
  and a coverage failure is a different finding
  ([2.2](2.2-coverage-orthogonality-specificity.md)). Without this line, *"what time do you close"*
  would fail the routing gate for being correctly unmatched.
- `MINIMUM_MARGIN = 1` is a **choice**, not a fact, and it is a named constant at the top so it can be
  argued with. One is what Sutra's shelf actually achieves — the *"draft a reply"* request wins by a
  single word — and setting the threshold at the current value turns the gate into a ratchet: it does
  not demand improvement, it forbids regression.
- The results are printed **sorted by margin ascending**, so the worst case is the first line read. A
  report that prints in request order buries the finding in the middle.
- `sys.exit(0 if ... else 1)` — an exit code, so this is a gate rather than a report, and Day 31 can
  wire it into `./m check` alongside the preflight
  ([27.4.3](../../../day-27-authoring-first-skills/parts/04-the-authoring-loop/4.3-sharpening-without-a-model.md)).
- `REQUESTS` is imported from `route.py` rather than redefined. Two copies of a request list drift, and
  the copy in the gate is the one nobody would remember to update.

Measured on 2026-09-04:

```text

margin  2  how urgent is this ticket
margin  2  what priority should this ticket get
margin  2  triage this ticket for me
```

Six requests scored — the seventh matched nothing and was filtered out — and the worst margin is
**one**, not two. That is the first thing the instrument has said that reading the descriptions did
not: *"draft a reply to the customer on this ticket"* wins by a single word, and
[2.1](2.1-a-description-is-a-routing-row.md) already identified which word and why it is fragile. A
two-skill shelf is already one edit away from a tie on one of its six requests, which is exactly the
baseline [2.4](2.4-the-crowded-shelf.md) is about to destroy.

## When it breaks

**A proxy trusted as a prediction.** *"The scorer says `ticket-triage` wins, so the model will pick
it."* It says no such thing. It says the two descriptions are not competing on these words. A request
phrased in synonyms scores zero everywhere and routes perfectly well in reality.

**A threshold set aspirationally.** `MINIMUM_MARGIN = 4` on a shelf that achieves two is a gate that is
red from the day it is written, and a gate that is always red is deleted within a fortnight. Set it at
today's value and raise it only when the shelf improves.

**A stopword list that swallows a trigger.** Adding `ticket` to `STOP` — tempting, because it is
everywhere — removes it from every score and changes every margin. It might be the right call; it must
not be an accident. Anything added to that list should be added in its own commit with the before-and-
after margins in the message.

**Requests written by the description's author.** They use the description's words and everything
scores well. The list has to come from what people actually typed; a list invented during review is a
mirror.

## In production

**Run the gate on every change to `skills/` and print the table.** The exit code catches the
regression; the table is what tells the author which request got worse. Both, always — an exit code
alone produces a pull request comment saying *"routing gate failed"* and no idea what to do.

**Keep the threshold as a ratchet.** Start at the current worst margin. When a change improves it,
raise it in the same commit. That converts an occasional heroic clean-up into a property the shelf
keeps.

**Record what the proxy is not.** A short comment at the top of `route.py` — *no synonyms, no stemming,
no weighting; detects collisions, does not predict selection* — is the difference between a check
people use correctly and a check somebody eventually quotes in a design review as evidence of
something it never measured.

**What changes at scale** is that the proxy's under-detection starts to matter. At forty skills there
are collisions expressed entirely in synonyms, and word overlap cannot see them. The upgrade is
embeddings — score by vector similarity rather than by shared words — which catches synonyms and costs
an embedding call per description rather than a generation per request. That is a real option, it is
cheap, and it is not needed at two skills: the honest sequence is word overlap now, embeddings when the
shelf outgrows it, and a live evalset for the cases that matter most (Phase 12).

**The review comment a senior engineer leaves:** *"the routing gate is green and I can see from the
table that two requests are now at margin one. Green is a threshold, not a trend — put the worst margin
in the pull request description so we can see it drifting before it crosses."*

**The interview question:** *"how do you test that the right skill gets selected?"* The answer that
shows you know what your instrument measures: *"with a deterministic proxy first and a live run second.
The proxy scores each description against a fixed list of real requests by shared content words and
reports the margin between the best and the second-best. It is not what the model does — no synonyms,
no stemming — but it is good at the thing that matters, which is detecting collisions: if two
descriptions share the words a request uses, they compete. It is free, it is reproducible, and a live
routing test is neither. The live runs then get spent on the cases the proxy cannot judge."*
