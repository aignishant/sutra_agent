# 2.1 — A description is a row in a routing table

## One-line answer

With one skill a description only has to match; with twenty it has to **beat the other nineteen** — so
past a handful of skills a description stops being a summary and becomes a routing rule, and it is
graded against its neighbours rather than on its own.

## The story

The board inside the hospital entrance lists twelve departments and an arrow for each.

Radiology. Pathology. Out-patients. Day surgery. Physiotherapy. Cardiology. You have a paper from your
doctor and a pain in your side, and you stand in front of the board for a moment working out which of
those twelve words is about you, while people walk around you.

Every one of those labels is correct. Every one of them was chosen by somebody who knew exactly what
happens in that department. And none of them was chosen by somebody standing where you are standing,
holding what you are holding — which is why there is a desk beside the board with a person at it, and
why the queue at that desk is longer than any of the twelve.

## The idea in plain language

Day 25 measured a description on its own: seven overlapping words against realistic requests where a
vague one scored one
([25.2.3](../../../day-25-skills-the-open-spec/parts/02-the-frontmatter/2.3-the-description-field.md)).
That is the right measurement for one skill, and it is the wrong shape of question for twenty.

The model does not evaluate skills one at a time and decide yes or no. It receives the whole index in
one block — every name, every description, in one XML result
([26.2.2](../../../day-26-loading-skills-into-adk/parts/02-the-four-tools/2.2-the-index-is-a-tool-call.md))
— and picks. So the quantity that matters is not a score, it is a **margin**: how far ahead the right
skill is of the second-best one.

That reframing changes three things about how a description is written.

**A description can get worse without changing.** Add a skill next month whose description also mentions
tickets, and yesterday's description is now a worse routing rule than it was, with the same words in
it. Nothing in your file changed and its job got harder.

**Absolute quality stops being the target.** A description scoring seven against a request is
irrelevant if another one scores seven too. Two mediocre descriptions with a clear margin between them
route better than two excellent ones that overlap.

**The unit under review is the shelf, not the skill.** A pull request adding a skill cannot be judged
by reading that skill. It has to be judged against the descriptions already there, which is a
comparison nobody can do by memory past about five skills, and which is the whole reason
[2.3](2.3-measuring-routing-without-a-model.md) exists.

None of this is unusual. It is what a routing table is: a set of rules where each entry is only
meaningful relative to the others, where the interesting failure is two rules matching the same
traffic, and where adding an entry can break an existing one. The vocabulary is worth borrowing on
purpose, because it comes with the right instincts — you audit a routing table for **coverage** and
**collisions**, not for the elegance of individual rules.

## Why Sutra needs it

Because Sutra has two skills today and the number only goes one way.

Day 29 sources third-party skills, and a vendor pack does not know what is already on your shelf. Day
30 tests them. Phase 8 builds a multi-agent graph where several agents have their own shelves. Every
one of those adds descriptions written by somebody who could not see yours.

And there is a specific, near-term collision to worry about. `ticket-triage` and `kb-answer-style`
already share four content words — `asks`, `base`, `id`, `knowledge` — and both are procedures about
the same tickets, even though only one of their descriptions says the word
([27.3.3](../../../day-27-authoring-first-skills/parts/03-procedure-and-capability/3.3-two-skills-one-toolset.md)).
That was measured yesterday and found acceptable: four shared out of forty-seven. The
third skill Sutra adds is the one that will make it stop being acceptable, and the only way to know
which one that is, is to check before merging.

## The paper behind it

> **RouteLLM: Learning to Route LLMs with Preference Data** · `arXiv:2406.18665` · 2024 ·
> <https://arxiv.org/abs/2406.18665>

It treats the choice of where to send a request as a first-class, measurable problem — a router trained
and evaluated on its own terms rather than as a side effect of the things being routed to, with cost and

## The mechanism

The index the model actually receives, for Sutra's two skills, is the routing table:

```text
<available_skills>
<skill>
<name>
kb-answer-style
</name>
<description>
The house style for a customer-facing reply that is grounded in one knowledge-base article - structure, tone, and how to cite the article id. Use when drafting or rewriting a reply to a reporter, when a reply has to cite a KB article, or when someone asks how we word an answer.
</description>
</skill>
<skill>
<name>
ticket-triage
</name>
<description>
Sutra&#x27;s standard procedure for triaging a support ticket - look the ticket up, find the symptom, search the knowledge base, and choose a severity with the rule that decided it. Use when a ticket id needs triage, when someone asks how urgent or serious a ticket is, when a severity or priority has to be set, or when a first diagnosis is wanted.
</description>
</skill>
</available_skills>
```

Read it as a table with two rows and ask a routing question about it rather than a writing question.

| Request | Which row should win | On what words |
| --- | --- | --- |
| *"how urgent is this ticket"* | `ticket-triage` | urgent, ticket |
| *"what priority should this get"* | `ticket-triage` | priority |
| *"draft a reply to the customer"* | `kb-answer-style` | reply, customer |
| *"how do we word an answer"* | `kb-answer-style` | word, answer |
| *"can you take a look at this ticket"* | `ticket-triage` | look, ticket |

**Line by line:**

- Every winning word in the third column appears **verbatim** in one description and not the other. That
  is not luck: yesterday's rule was to write the *"use when"* half in the vocabulary a requester would
  type ([27.1.3](../../../day-27-authoring-first-skills/parts/01-extraction/1.3-the-six-question-pass.md)),
  and the third column is what that rule buys.
- The words that appear in **both** descriptions are `asks`, `base`, `id` and `knowledge`, measured on
  2026-09-04. None of them appears in the third column, and that is the rule: a word present in every
  row of a routing table carries no routing information, however central it is to the domain. Note what
  is *not* in that list — `ticket` is in `ticket-triage`'s description and not in `kb-answer-style`'s,
  which is why it is doing work in three of the five rows.
- The third row is the fragile one and it is worth reading closely. It wins on `reply` and on
  `customer` — the latter only because `customer-facing` splits into two words. It does **not** win on
  `draft`, because the description says *drafting* and an exact word match does not join them. A
  routing rule that depends on a hyphen and misses on a suffix is a routing rule one edit away from
  changing its mind.
- The last row wins on *"look"*, which is in `ticket-triage`'s description because the first sentence
  says *"look the ticket up"*. That is an accidental match — the word was written to describe a step,
  not to catch a request — and accidental matches are exactly what makes a routing table fragile.
- Notice `&#x27;` in the second description: the apostrophe in *"Sutra's"* is HTML-escaped by the
  formatter, so it costs five characters instead of one. Not a routing problem, and worth knowing when
  the index total looks larger than the descriptions you wrote.
- The table has no *"neither"* row, and it should. A request like *"what time do you close?"* matches
  nothing, and a routing table with no way to lose is a routing table that always routes.

## When it breaks

**A description written to be read rather than matched.** *"This skill implements the standard triage
workflow used by the support organisation."* Every word is true and none of them is a word anybody
types. It scores near zero against real requests and reads beautifully in review, which is the worst
combination available.

**A word that is in every row.** *"Support"*, *"ticket"*, *"customer"* — the words most central to the
domain are the ones least useful for routing, because everything is about them. The description that
leads with them is spending its most-read position on nothing.

**A collision introduced by somebody else.** The third skill is added, it mentions severity, and
`ticket-triage`'s routing quietly degrades. No file you own has changed and no test covers it. This is
the failure [2.4](2.4-the-crowded-shelf.md) demonstrates and
[2.3](2.3-measuring-routing-without-a-model.md) catches.

**Routing that fails upward.** The model, faced with two equally plausible rows, may pick one, pick
both, or pick neither — and picking both is not obviously wrong, so it does not look like a failure.
Two activations is two round trips and two bodies carried for the rest of the conversation
([1.1](../01-the-price-list/1.1-five-rungs-five-frequencies.md)).

## In production

**Review descriptions as a set, and in the rendered index.** Print the XML the model will actually
receive and read it as one document. Descriptions reviewed one at a time in a diff always look fine;
the collision is only visible when they are side by side.

**Keep a fixed set of real requests, in a file.** Ten to twenty things people actually typed. It is the
test set for the routing table, it makes two months' worth of changes comparable, and it is the seed of
an evalset for Phase 12. Ad-hoc requests invented while reviewing test the description against the mood
of the reviewer.

**Treat adding a skill as a change to every existing skill.** That is what it is. The pull request that
adds one should show the routing table before and after, which is a script rather than a discipline
([2.3](2.3-measuring-routing-without-a-model.md)).

**What changes at scale** is that the shelf stops being auditable by reading. Twenty descriptions is
190 pairwise comparisons, and no reviewer does that. Past that point routing is only manageable with a
measurement, and past a few hundred it is not manageable with listing at all — the index itself becomes
the bottleneck, which is [5.1](../05-in-production/5.1-when-the-index-outgrows-listing.md).

**The review comment a senior engineer leaves:** *"this new skill's description is good on its own and
it shares four trigger words with `ticket-triage`. Post the routing table for the six standard requests
before and after — if any margin drops to zero we have made an existing skill worse by adding this
one."*

**The interview question:** *"how do you write a skill description?"* The answer that shows you have
run a shelf rather than a skill: *"for one skill, in the words a requester would actually type, saying
what it does and when to use it. For a shelf, that is not enough — the model sees every description at
once and picks, so what matters is the margin between the right one and the second-best. A description
can become a worse routing rule without a word of it changing, just because somebody added a neighbour.
So descriptions are reviewed as a set, against a fixed list of real requests, and adding a skill is
treated as a change to every skill already there."*
