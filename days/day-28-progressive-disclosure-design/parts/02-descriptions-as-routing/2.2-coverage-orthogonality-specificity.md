# 2.2 — Coverage, orthogonality, specificity

## One-line answer

A shelf is audited on three properties — every expected request matches something, no request matches
two things equally, and each description says the specific thing rather than the general one — and only
the first is about whether a skill exists.

## The story

The switchboard in the corridor has eight switches and four labels.

*Lights.* *Lights 2.* One with a strip of tape that says *fan?* in somebody's handwriting, question
mark included. And five with nothing on them at all. When the corridor light needs turning on, you flip
the first, and if that was the wrong one you flip it back and try the second, and everybody in the
building has learned the sequence by doing it rather than by reading it.

The interesting label is *fan?*. Somebody stood there, worked out that it was probably the fan, and
wrote down their uncertainty. It is the most honest label on the board and it is still useless, because
the next person has to test it too.

Eight switches, and the board tells you nothing you could not have found out by trying.

## The idea in plain language

Three properties, audited in this order, because each one only makes sense once the previous holds.

**Coverage — does every request you expect match something?** This is about the shelf having the right
skills on it, not about wording. Run your real requests past the index and look for the ones that score
zero everywhere. Some of those are gaps worth filling; others are requests that legitimately have no
procedure, and the honest outcome for those is *"no skill fired"* rather than a skill stretched to
cover them.

The measurement has a subtlety worth naming: a request scoring zero is a **good** result when there is
genuinely nothing for it. *"What time do you close?"* should match nothing on Sutra's shelf. A shelf
where everything matches something is not well covered; it is mushy, which is the second property.

**Orthogonality — does any request match two things equally?** This is the property that degrades as
the shelf grows, and it is measured as a **margin** ([2.1](2.1-a-description-is-a-routing-row.md)):
best score minus second-best. A margin of zero is a coin flip. A margin of one, on scores of two
against one, is a coin flip with extra steps — one word away from a tie, and the word is usually a
plural or a hyphen.

The single biggest destroyer of orthogonality is **shared filler**. Words that appear in every
description carry no routing information at all, however central they are to the domain. Sutra's two
descriptions share `asks`, `base`, `id` and `knowledge` — four words, measured, that decide nothing
ever.

**Specificity — does the description say the particular thing?** *"Handles support tasks"* is a
category; *"choose a severity with the rule that decided it"* is a job. Categories match everything
weakly, which is the worst possible profile: they never win cleanly and they always narrow somebody
else's margin.

A useful way to hold all three: **coverage is about the shelf, orthogonality is about the pairs,
specificity is about the row.** Fixing them requires three different actions — add or remove a skill,
sharpen the descriptions that collide, rewrite one description — and confusing which one you have is
how a team spends a week rewriting descriptions to fix a missing skill.

## Why Sutra needs it

Because Sutra's shelf passes all three today and none of that is durable.

Coverage: six of Sutra's seven standard requests match something and the seventh — *"what time do you
close"* — matches nothing, which is correct. Orthogonality: the worst margin is one, measured, on a
two-skill shelf - narrower than it feels. Specificity: both descriptions name jobs.

All three of those are properties of a shelf with **two** items on it. Day 29 adds skills Sutra did not
write, from a source that has never seen these descriptions, and the first thing that will happen is a
margin dropping to zero somewhere. The audit is worth building now, while the answer is boring, because
an audit you first run on a broken shelf is an audit you cannot calibrate.

## The mechanism

The three properties as three measurements, on Sutra's actual shelf.

```python
# days/day-28-progressive-disclosure-design/lab/audit_the_shelf.py
"""Coverage, orthogonality and shared filler, for the shelf as it stands."""

import pathlib

from google.adk.skills import load_skills_from_dir

from route import REQUESTS, card, rank, words

SHELF = pathlib.Path("skills")

skills = sorted(load_skills_from_dir(SHELF), key=lambda s: s.name)

print("-- coverage --")
for request in REQUESTS:
    top = rank(skills, request)[0]
    print(f"{request[:46]:<48} {top[1] if top[0] else '(nothing)':<18} {top[0]}")

print("\n-- shared filler --")
common = set.intersection(*(words(card(s)) for s in skills))
print(sorted(common))

print("\n-- specificity --")
for skill in skills:
    unique = words(card(skill)) - common
    print(f"{skill.name:<18} {len(unique):>3} words of its own")
```

**Line by line:**

- `from route import card, rank, words` — the scorer is a separate module because
  [2.3](2.3-measuring-routing-without-a-model.md) is where it is built and justified. This part uses it;
  that part explains why it looks the way it does.
- `REQUESTS` is imported from `route.py`, where [2.3](2.3-measuring-routing-without-a-model.md) keeps
  it, so there is one list and no copy to drift.
- That list includes **one request that should match nothing** - *"what time do you close"*. A coverage
  check with no negative case cannot distinguish a well-covered shelf from a mushy one, and the negative
  case is the cheapest possible guard against descriptions that match everything.
- `top[1] if top[0] else '(nothing)'` — a zero score prints as `(nothing)` rather than as the
  alphabetically-first skill. Without that, a total miss looks like a routing decision, which is
  precisely the confusion this check exists to remove.
- `set.intersection(*(...))` over every card gives the shared filler. With two skills it is a small set;
  the generator form is written so it stays correct at twenty without an edit.
- **Specificity is measured as the count of words a description does not share with every other one.**
  It is a crude proxy and it is the right shape: a description made entirely of common words scores
  zero and is, by construction, unable to win anything.
- `card(skill)` is name **plus** description, because the name is part of what the model sees and
  `ticket-triage` as a name is doing real routing work.
- **Zero model calls**, no key needed. Everything here is set arithmetic over strings.

Read the three blocks as three verdicts.

**Coverage is right, including the negative case.** Six requests route, one does not, and the one that
does not is the one that should not.

**Shared filler is four words**, and none of them is a trigger. Note what that means: about
seventeen per cent of `kb-answer-style`'s vocabulary is shared. At forty skills that fraction rises,
because domain words are finite and every new description reuses them.

**Specificity is 17 and 24 words of their own.** Not a target and not a threshold — a baseline. The
number to watch is a **new** skill scoring in single digits, which is a description made of the same
words as everything else.

## When it breaks

**Coverage confused with mush.** A shelf where every request matches something looks well covered and
is usually the opposite: it means at least one description is broad enough to catch anything, and that
description is quietly narrowing every margin on the shelf.

**Orthogonality checked one pair at a time.** The interesting collisions are not between the two skills
somebody happened to compare; they are between the new one and whichever existing one it accidentally
resembles. That is a full sweep, and a full sweep is a script
([2.3](2.3-measuring-routing-without-a-model.md)).

**Specificity mistaken for length.** A longer description has more words and therefore more unique
ones, and scores better on the crude proxy above while routing no better. The proxy is a smoke alarm,
not a scale — it catches the description made entirely of filler and it says nothing useful about the
difference between good and very good.

**An audit run only on the requests you invented.** Requests written by the person who wrote the
descriptions use the description's vocabulary, and everything passes. The list has to come from what
people actually typed, which is why
[2.1](2.1-a-description-is-a-routing-row.md) says to keep it in a file rather than in the reviewer's
head.

## In production

**Run the audit on every change to `skills/`, and print all three blocks.** The three properties fail in
three different ways and a single pass/fail hides which one you have. Three blocks of output is not
verbose here; it is the diagnosis.

**Keep the negative cases in the request list forever.** They are the only thing standing between a
shelf and a description that matches everything, and they cost nothing. One or two is enough — a
question about opening hours, a question about a refund.

**Watch the shared-filler set as the shelf grows.** It only ever gets larger, and the day a genuine
trigger word appears in it — `severity`, `reply`, `triage` — is the day two skills have started
competing for the same traffic. That set is a better early warning than any single margin, because it
predicts collisions before a request happens to hit one.

**What changes at scale** is that specificity stops being achievable by writing and starts requiring
**structure**. At forty skills the domain vocabulary is exhausted and descriptions genuinely cannot be
made orthogonal by choosing better words. The answers then are hierarchical — one skill that routes to
a family — or a searchable registry rather than a listed index
([5.1](../05-in-production/5.1-when-the-index-outgrows-listing.md)). Neither is a writing problem.

**The review comment a senior engineer leaves:** *"the audit shows this new description sharing eleven
words with `ticket-triage` and winning nothing by more than one. That is not a description problem — it
is the same job. Either merge them or say plainly what this one does that the other does not, in words
the other one does not use."*

**The interview question:** *"how do you know if a set of skill descriptions is any good?"* The answer
that shows you audit a shelf rather than proof-read a file: *"three properties, in order. Coverage —
does every request I expect match something, **and** does a request with no procedure match nothing?
Orthogonality — does anything match two skills equally, measured as the margin between best and
second-best, not as a score. And specificity — does each description use words the others do not? The
big destroyer is shared filler: words that appear in every description carry no routing information,
and the set of them only grows. When a real trigger word joins that set, two skills have started
competing and no amount of rewriting fixes it."*
