# 1.2 — Pricing your own shelf

## One-line answer

One script prints every rung of every skill you own — card, body, references — and the whole point of
running it is that the numbers are never the ones you guessed.

## The story

You weigh the suitcase at home because the desk at the airport is a bad place to find out.

The bathroom scales, held at arm's length, standing on them yourself and then again holding the bag.
It is undignified and slightly inaccurate and it takes ninety seconds. Twenty-three kilos allowed,
and the bag comes out at twenty-six — which is a pair of shoes and the second jacket, decided in the
bedroom with the wardrobe open, rather than on the floor of the terminal with a queue behind you.

The scales did not make the bag lighter. They moved the decision to a place where you could make it
calmly and had options.

## The idea in plain language

[1.1](1.1-five-rungs-five-frequencies.md) gave the five rungs and their frequencies. This part is the
scale: a script that prices your actual shelf, so that every later decision in this day is made against
numbers rather than instincts.

Three things it must do, and each one is a decision that would be easy to get wrong:

**Measure the card as the model receives it, not as you wrote it.** The index is XML, and the tags cost
tokens — the same description is 55 tokens as two plain lines and 95 inside `<skill>` blocks
([26.2.2](../../../day-26-loading-skills-into-adk/parts/02-the-four-tools/2.2-the-index-is-a-tool-call.md)).
Measuring the description string alone under-reports the rung by about forty per cent.

**Subtract the envelope.** `<available_skills>` and its closing tag are 12 tokens, paid once no matter
how many skills there are. Measuring each skill's block *with* the envelope included and then adding
them up double-counts it once per skill, and the error grows with the shelf.

**Count with the model's tokeniser, not with `len()`.** Day 24 established that tokens are not
characters and the ratio is not stable across text
([24.1.1](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.1-a-ticket-id-costs-five-tokens.md)).
`count_tokens` is a separate endpoint on a separate quota, so the whole measurement costs **zero**
generations.

What comes out is a table you will use for the rest of the day, and one number that is not obvious
until you see it: **the index total**, which is what every conversation that asks about skills pays,
and which grows with every skill you add whether or not it is ever used.

## Why Sutra needs it

Because the two skills written yesterday were designed by reasoning and today they get audited by
measurement, and those two things disagree more often than is comfortable.

The specific guesses waiting to be checked: `kb-answer-style` *feels* like the smaller skill — is it?
The rubric was moved behind a link because it would *grow* — how big is it now? `ticket-triage`'s body
has three sections and one of them is a worked example — what fraction of the body is that?

Every one of those has an answer that takes one second to obtain, and
[1.4](1.4-moving-the-example.md) turns one of them into a design change and then argues the change
back out again.

## The mechanism

The scale.

```python
# days/day-28-progressive-disclosure-design/lab/price_the_shelf.py
"""Every rung of every skill on the shelf, priced with the model's own tokeniser."""

import os
import pathlib

from google import genai
from google.adk.skills import load_skills_from_dir, prompt

from sutra.config import load_env

MODEL = "gemini-3.7-flash"
SHELF = pathlib.Path("skills")

load_env()
client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])


def cost(text: str) -> int:
    """Tokens for one string on the pinned model. Costs 0 generations."""
    return client.models.count_tokens(model=MODEL, contents=text).total_tokens


skills = sorted(load_skills_from_dir(SHELF), key=lambda s: s.name)
envelope = cost(prompt.format_skills_as_xml([]))

print(f"{'skill':<18}{'card':>6}{'body':>7}{'refs':>7}")
index = envelope
for skill in skills:
    card = cost(prompt.format_skills_as_xml([skill])) - envelope
    body = cost(skill.instructions)
    refs = sum(cost(skill.resources.get_reference(r)) for r in skill.resources.list_references())
    index += card
    print(f"{skill.name:<18}{card:>6}{body:>7}{refs:>7}")

print(f"\n{'index envelope':<18}{envelope:>6}")
print(f"{'index, if asked':<18}{index:>6}")
```

**Line by line:**

- `prompt.format_skills_as_xml` is imported from `google.adk.skills` and is **the same function the
  `list_skills` tool calls**. Measuring the real formatter rather than reconstructing the XML is the
  difference between a measurement and an estimate, and it means the number stays right if ADK changes
  the format.
- `envelope = cost(format_skills_as_xml([]))` — the empty index. Twelve tokens of tags with no skills in
  them, and subtracting it from each block is what makes the per-skill numbers additive.
- `cost(...) - envelope` per skill, then `index += card`, then the envelope added back once at the
  start. Two lines, and they are the whole reason this script is worth writing rather than eyeballing.
- `skill.resources.list_references()` is the accessor rather than iterating the dictionary, because the
  accessor is the public surface
  ([26.1.2](../../../day-26-loading-skills-into-adk/parts/01-loading-a-folder/1.2-the-skill-object.md)).
- `refs` **sums** a skill's references into one number, which is right for a total and hides the split
  when a skill has several. `ticket-triage` has one today and will have two by
  [1.4](1.4-moving-the-example.md) — printing them individually is a `TODO(me)`.
- `sorted(..., key=lambda s: s.name)` because `load_skills_from_dir` returns filesystem order, and a
  table you will compare against a later run needs a stable order.
- `load_env()` at module scope with the client built once. The script is a measurement, not a library.
- **Zero generations.** `count_tokens` is a separate endpoint, verified by Day 24 to keep working while
  `generate_content` is refusing
  ([24.2.1](../../../day-24-token-accounting-and-budgets/parts/02-two-ceilings/2.1-two-ceilings-one-clears.md)).

Run it from the repository root:

```bash
uv run python days/day-28-progressive-disclosure-design/lab/price_the_shelf.py
```

**Line by line:**

- Needs `GOOGLE_API_KEY` for the token counts; spends **0** of the twenty daily generations.

Measured on 2026-09-04 against yesterday's two skills:

```text
skill               card   body   refs
kb-answer-style       93    375      0
ticket-triage        109    654    142

index envelope        12
index, if asked      214
```

Four things in that table are worth stopping on, and three of them contradict a guess.

**The cards are nearly the same size.** 93 against 109, for descriptions that felt very different in
length. Card cost tracks description length, and both descriptions were written to the same shape
([27.1.3](../../../day-27-authoring-first-skills/parts/01-extraction/1.3-the-six-question-pass.md)), so
they land close together. That is the discipline paying off in a place nobody was aiming.

**The bodies are not nearly the same size.** 654 against 375 — `ticket-triage` is three-quarters larger,
and it is the one that also carries a reference.

**The reference is small.** 142 tokens, and it was moved out of the body on the argument that it would
grow ([27.1.7](../../../day-27-authoring-first-skills/parts/01-extraction/1.7-what-goes-behind-a-link.md)).
It has not grown yet. That decision is now checkable rather than merely defensible, and
[1.4](1.4-moving-the-example.md) checks it.

**The index total is 214 and the preamble is 479.** The fixed cost of having skills at all is more than
twice the cost of listing both of them. Anybody optimising descriptions before knowing that is
optimising the smaller half.

## When it breaks

**The key is missing.** The counts need one:

```text
KeyError: 'GOOGLE_API_KEY'
```

The fix is a `.env` ([1.3.3](../../../day-01-bootstrap-and-map/parts/03-keys-and-env/3.3-loading-keys-failing-loudly.md)),
and the script deliberately does not fall back to a character estimate — a measurement that quietly
prints a guess is worse than one that stops.

**A skill on the shelf that will not load.** `load_skills_from_dir` is all or nothing and its exception
names the pydantic rule rather than the folder
([26.4.1](../../../day-26-loading-skills-into-adk/parts/04-failure-lab/4.1-one-bad-folder.md)):

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for Frontmatter
```

For a lab script that is acceptable; for anything that runs at startup it is not, which is why
`sutra/desk/skills.py` loops instead.

**Measuring the description instead of the card.** The most likely error in a re-implementation, and it
under-reports by the width of the XML tags — about forty tokens per skill. It is also silent, because
the number that comes out is plausible.

**Comparing runs across models.** Token counts are per-tokeniser. A table measured on
`gemini-3.7-flash` and compared against one measured on anything else is comparing two different
questions, and the difference will look like a change in your skills.

## In production

**Keep the table, dated, in the repository.** A file of these numbers per release is what turns *"the
skills got bigger"* from an impression into a diff. It costs nothing to produce and it is the only
record of what a skill used to cost.

**Put a ceiling on the index and fail the build at it.** Not on the bodies — those are activated
conditionally and the spec's 5,000 is far away. The index is what every asking conversation pays, it
grows with every skill added, and nobody notices it growing. A ceiling of a few thousand tokens, checked
in CI, is the cheapest guard against the failure in
[5.1](../05-in-production/5.1-when-the-index-outgrows-listing.md).

**Price a skill before it merges, not after.** A new skill's card is a permanent addition to every
listing. A pull request that adds one should say what it costs, the same way a dependency change says
what it adds to the install.

**What changes at scale** is that the interesting number stops being any single skill and becomes the
**distribution**. Forty skills where three carry half the index is a shelf with three descriptions
worth rewriting and thirty-seven to leave alone. The table sorted by card cost is a to-do list; the
table read row by row is not.

**The review comment a senior engineer leaves:** *"we have no idea what our shelf costs. Add the pricing
script to the repository and print its output in CI, so the next skill's cost shows up in the diff
rather than in the bill."*

**The interview question:** *"how big are your skills?"* The answer that shows you have run a scale:
*"about a hundred tokens per card in the index, three to seven hundred per body, and a hundred and
forty for our one reference file — measured with the model's own tokeniser against the formatter the
framework actually uses, not estimated from characters. The number I watch is the index total, because
it is paid by every conversation that asks about skills and it grows with every skill we add. Right now
it is 214 against a fixed 479-token preamble, which tells me the descriptions are not yet where the
money is."*
