# 3.3 — The list you kept is the list you trust

## One-line answer

`tool_list_cache_ttl_seconds` turns three listings into one, and buys that saving with a window in
which a tool the server has added or removed is invisible to you.

## The story

You photograph the price list at the wholesale shop so you do not have to ask every time.

For a few weeks it is the best thing you have done. You quote prices to customers off your phone, you
work out margins on the bus, and you never once have to stand at the counter waiting for somebody to
read numbers out.

Then oil goes up. The shop reprints the board on a Monday morning. Your phone still has the old
photograph, and it does not look old — a photograph of a price list looks exactly the same whether it
was taken this morning or in March. You quote Thursday's customer a price you cannot buy at.

The photograph was not wrong when you took it. It was a fact with a date on it, and you stored the
fact without the date.

## The idea in plain language

Listing a server's tools costs a round trip, and ADK does it on **every** call to `get_tools()` unless
you tell it otherwise. In a busy agent that is a request per turn, per server.

`McpToolset` takes an argument for this: `tool_list_cache_ttl_seconds`. Set it, and the toolset reuses
one `tools/list` answer for that many seconds instead of asking again. Day 32's
[3.3 — Lists you may keep](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md)
is where this became possible at all: the 2026-07-28 revision made list results cacheable, with `ttlMs`
and `cacheScope` on the response, precisely so clients could stop re-asking.

Three facts about ADK's implementation, and each one changes a decision:

- **The filter still runs on a cache hit.** The framework's own comment says so: *"This runs on every
  call even on a cache hit, so only the round trip is skipped."* So caching does not weaken your
  allowlist. What it caches is the server's answer, not your decision about it.
- **ADK does not subscribe to change notifications.** Its docstring is explicit: *"ADK does not
  subscribe to `notifications/tools/list_changed`, so a tool the server adds or removes goes unnoticed
  until the entry expires."* Combined with what [3.1](3.1-the-tuesday-a-tool-appeared.md) established —
  that under the current revision the notification only reaches clients that opened a
  `subscriptions/listen` stream — the honest summary is that **the TTL is your entire refresh
  mechanism**.
- **The cache lives on the toolset instance.** Sharing the cache means sharing the object. Build a new
  `McpToolset` per agent and you have built one cache per agent, and your saving is divided by the
  number of agents.

So the TTL is a dial between two costs, and neither end is free:

| TTL | What you pay | What you get |
| --- | --- | --- |
| `None` (default) | a listing per turn per server | you always see the current list |
| small (tens of seconds) | most of the listings | a short staleness window |
| large (an hour or more) | almost no listings | a removed tool keeps being offered for that long |

That last cell is the one people miss. Day 32's
[3.3](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.3-lists-you-may-keep.md) put it
as a rule for server authors — removing a tool is two deployments — and this is the same rule read from
the client's side of the socket.

## Why Sutra needs it

Because Sutra is about to connect to several servers and cannot afford a listing per server per turn,
and because the moment it caches, its pin check and its listing diff acquire a lag.

The concrete decision `sutra/mcp/filtering.py` has to make is what TTL each server gets, and the
answer is not one number. Sutra's own `sutra_mcp` server changes only when this repository is deployed,
so a long TTL costs nothing. A third-party server on somebody else's release schedule is the one you
want to notice quickly, and it is also the one you list most often. That is an awkward pairing and it
should be written down per server rather than set once globally.

Day 44 builds `sutra/mcp/hardening.py` with retries and timeouts and the no-held-connection rule. A
retry that re-lists is a cache miss, so hardening and caching interact — and Day 45's audit is the day
that has to check both are configured deliberately rather than left at their defaults.

## The mechanism

`lab/cache.py` measures the saving instead of asserting it. The prop server prints one line to standard
error per request it handles, so the number of listings can be counted rather than assumed.

```python
# lab/cache.py
async def listings(ttl: float | None, calls: int) -> tuple[int, list[str]]:
    """Ask one toolset for its tools `calls` times; count the server's listings."""
    with tempfile.TemporaryDirectory() as tmp:
        log = pathlib.Path(tmp) / "server.err"
        with log.open("w+", encoding="utf-8", errors="replace") as errlog:
            toolset = McpToolset(
                connection_params=StdioConnectionParams(
                    server_params=StdioServerParameters(
                        command=sys.executable, args=[str(PROP)], env={**os.environ}
                    ),
                    timeout=20,
                ),
                tool_filter=["check_status", "list_regions"],
                tool_list_cache_ttl_seconds=ttl,
                errlog=errlog,
            )
            try:
                names: list[str] = []
                for _ in range(calls):
                    names = [tool.name for tool in await toolset.get_tools()]
            finally:
                await toolset.close()
        return log.read_text(encoding="utf-8", errors="replace").count(LISTED), names
```

**Line by line:**

- `errlog=` is `McpToolset`'s parameter for where the child process's standard error goes. Its default
  is `sys.stderr`, which is why every other transcript in this day has stray
  `Processing request of type ListToolsRequest` lines in it. Here it is redirected so it can be counted.
- **A real file, not an `io.StringIO`.** The child process is launched with its standard error wired to
  an operating-system handle, and a `StringIO` has no file descriptor to hand over. Passing one fails
  with `io.UnsupportedOperation: fileno`, which is worth knowing before you spend an afternoon on it.
- `tempfile.TemporaryDirectory()` so the log is deleted when the block ends. A lab script that leaves
  files behind is a lab script somebody will later find and wonder about.
- `errors="replace"` on both open and read. Server output is not guaranteed to be valid UTF-8 — a
  crashing child can emit anything — and a measurement script that dies on a decoding error has failed
  at the one job it had.
- `tool_list_cache_ttl_seconds=ttl` is the only argument that differs between the two runs. Everything
  else, including the allowlist, is identical, so the difference in the count has exactly one cause.
- The loop calls `get_tools()` `calls` times on **one** toolset object. Calling it on a fresh toolset
  each time would measure nothing, because the cache lives on the instance — which is itself the point
  the *In production* section below turns into a warning.
- `.count(LISTED)` counts occurrences of the string `ListToolsRequest` in the captured stream. Crude,
  and correct for this purpose: the server prints exactly one such line per listing it serves.
- `finally: await toolset.close()` inside the `with`, so the child process is stopped before the file
  is closed and read. Reading the log while the writer is still open would give you a partial count.

```bash
uv run python days/day-40-filtering-and-allowlists/lab/cache.py
```

**Line by line:**

- No arguments and no environment variable. The script runs both arms itself and prints them together,
  because the number that matters is the difference.

Measured on 2026-09-04:

```text
3 calls to get_tools(), tools handed over each time: ['check_status', 'list_regions']
  tool_list_cache_ttl_seconds=None -> 3 listings on the wire
  tool_list_cache_ttl_seconds=60   -> 1 listing(s) on the wire

requests saved by the cache: 2
seconds a tool added now stays invisible: up to 60
```

Three listings become one. The tools handed over are identical in both arms, which is the framework's
comment made visible: the filter ran three times either way, and only the round trip was skipped.

The last line is not decoration. It is the price, in the same units the saving is quoted in.

## When it breaks

The first break is the one you meet while building the measurement, and it has a real message. Pass an
`io.StringIO` as `errlog` and the connection fails before any listing happens:

```text
io.UnsupportedOperation: fileno

The above exception was the direct cause of the following exception:

ConnectionError: Failed to create MCP session: Failed to create MCP session: fileno
```

The second `ConnectionError` message really does say "Failed to create MCP session" twice — the inner
error is wrapped once by the session context and once by the session manager. It is worth recognising,
because "fileno" is a strange thing to see at the end of a connection error and it sends people looking
at their transport when the problem is one argument.

The second break is the stale entry, and its message is quieter than you would like. A long TTL and a
vendor that removes a tool means your agent keeps being offered a tool that no longer exists and calls
it. Calling `open_incident` on the reviewed version of the prop, which does not have it, printed this
on 2026-09-04:

```text
Tool 'open_incident' not listed, no validation will be performed
isError: True
content: Unknown tool: open_incident
```

Three things to notice. The first line is a **client-side** warning that the tool was not in the
listing, which is the SDK telling you it could not validate the arguments. The second is that this
came back as a tool result with `isError: True` rather than as a JSON-RPC protocol error — so it goes
to the model, not to your exception handler. And the third is that the model then does what models do
with a failed tool: it tries again, or it apologises, or it improvises. None of those is the right
response to "your cache is stale", and none of them tells you that is what happened.

The third break is a configuration one and it is the most common. `tool_list_cache_ttl_seconds` must be
positive; the constructor rejects zero and negatives:

```text
ValueError: tool_list_cache_ttl_seconds must be positive, got 0.
```

That is a good error and a trap all the same, because `0` is the natural way to write "no caching" and
the correct way to write it is `None`.

## In production

**What a professional writes instead:** the TTL is per server, in the policy record, with a comment
saying why that number. Servers you deploy get a long TTL because you know when they change; servers
somebody else deploys get a short one, and the pin check from
[3.2](3.2-the-name-held-the-sentence-moved.md) runs on its own schedule rather than riding on the
agent's listings. The toolset objects are built once at startup and shared, so there is one cache per
server rather than one per agent.

**What degrades at scale:** the cache key. ADK keys cache entries the way it pools sessions, so each
distinct `header_provider` identity gets its own entry — and a `header_provider` that mints a fresh
value per request would produce a new key every time. The framework caps that at 64 entries so it
cannot grow without bound, but a capped cache with a fresh key per request is a cache with a hit rate
of zero, and the symptom is that your listing count does not go down after you enabled caching. If you
enable a TTL and the numbers do not move, look at what varies in your headers.

**The failure mode that only appears with real traffic:** the deploy window. You remove a tool from your
own server and deploy. For the length of the longest TTL any client is using, some agents are still
being offered it and are calling it. Those `Unknown tool` results are real user-visible failures, and they are
concentrated in the minutes after a deploy, which is exactly when everyone is looking at a dashboard
and attributing them to the deploy in general. Removing a tool is two deployments: stop advertising it,
wait longer than the TTL, then delete the handler.

**The review comment a senior engineer leaves:** *"you have set a one-hour TTL on a vendor server. That
means for up to an hour after they ship, we are working from a list we know is stale, and ADK does not
subscribe to list-changed notifications so nothing will tell us. Either drop it to a minute or run the
listing diff out-of-band and treat the TTL purely as a cost control — but say which one you chose in
the policy, because right now the number reads like a default somebody copied."*

**The interview question:** *"you cache your MCP tool listings. What did that cost you?"* The honest
spoken answer: *"A staleness window, and it is bigger than people expect because ADK does not subscribe
to the server's list-changed notification — the TTL is the whole refresh mechanism. We measured the
saving: three `get_tools()` calls against one toolset, three listings on the wire without a TTL and one
with, and the allowlist still applied on every call because the framework filters on cache hits and
only skips the round trip. The two costs I would name are a removed tool that stays callable until the
entry expires, which surfaces as `Unknown tool` results right after a deploy, and a listing diff
that is now delayed by up to the TTL. So we set the TTL per server rather than globally — long for
servers we deploy ourselves, short for third parties — and we run the pin and diff checks out of band
so their freshness does not depend on the agent's traffic."*
