# 1.1 — The list of things you thought of

## One-line answer

A deny-list is a list of things you thought of, an allowlist is a list of things you agreed to, and
the two are identical right up to the moment somebody adds something neither of you discussed.

## The story

The school gate has a guard and a book.

In one school the book lists the people who must **not** be given a child: a named uncle nobody
trusts, a former driver who was let go. The guard reads the book, does not find the person standing
in front of him, and opens the gate.

In the school across the road the book lists the people who **may** collect each child: the mother,
the father, the grandmother, the neighbour on the second floor. The guard reads the book, does not
find the person standing in front of him, and does not open the gate.

Both books are correct on the day they are written. Both guards are doing their job. The difference
only shows up when somebody arrives who is in neither book — a new driver, a cousin, a man in a
delivery uniform who says he was sent. The first guard lets him in. The second guard makes a phone
call.

Nothing in the first school is broken. Nobody wrote a bad rule. The gate simply opens for everything
that was not imagined in advance, and the number of things nobody imagined only ever goes up.

## The idea in plain language

Two ways to write a rule about what is allowed:

- A **deny-list** — sometimes called a blocklist — names the things you refuse. Everything else is
  permitted. The default is *yes*.
- An **allowlist** names the things you permit. Everything else is refused. The default is *no*.

They are not two styles of the same thing. They differ in exactly one place, and it is the place
where the rule meets something its author never saw: the **default**.

That single word decides the outcome of every case you did not enumerate, and every list you write
today is a list of what you could think of today. A deny-list is therefore a bet that you have
already imagined every dangerous thing, forever. An allowlist is a bet that you have already
imagined every *useful* thing — a bet that is much easier to lose safely, because losing it means a
tool you wanted is missing and somebody notices in the first minute.

The name for choosing the second one is **fail-safe defaults**: when a decision cannot be made from
the rules you have, the answer that costs least when it is wrong is the one that refuses. It sounds
like a slogan. It becomes a felt thing the first time you watch the same afternoon play out both
ways.

One more distinction, because it is where the vocabulary gets sloppy. A deny-list that is *complete*
is exactly as safe as an allowlist. Completeness is the problem: you cannot check it, because
checking it would mean enumerating everything, and if you could enumerate everything you would have
written the allowlist.

## Why Sutra needs it

Because Phase 6 is the phase in which Sutra stops writing all its own tools.

Day 32 decided that Sutra's data boundary is MCP and that a boundary you can point at is one you can
guard ([1.5 — One gate to guard](../../../day-32-mcp-stateless-core/parts/01-the-socket/1.5-one-gate-to-guard.md)).
Day 33 built the client that reaches through it, Day 34 built Sutra's own server, and Day 39 put a
real database behind one. Every one of those was code you wrote or a server you own.

From here on that stops being true. A vendor status server, a search server, a partner's server: a
box of tools with names and descriptions written by somebody else, arriving over a socket. Today is
the day Sutra decides what its answer is when that box contains something nobody discussed — and the
answer has to be decided *before* the box arrives, because deciding afterwards is called an
incident.

Day 45's audit walks every server Sutra talks to, and it can only do that if there is a written list
to walk. Day 44 hardens the client that carries the calls. Both of them assume today's answer.

## The mechanism

The mechanism is small enough to hold in one function, which is the point — this is not a framework
feature, it is a choice about a default.

```python
# lab/postures.py
# What the vendor server offered on the day you reviewed it.
REVIEWED = ["check_status", "list_regions"]

# What it offers on Tuesday. Nobody told you; nothing broke.
TUESDAY = ["check_status", "list_regions", "open_incident"]

# The two postures, written the way people actually write them.
DENY = ["execute_sql", "delete_ticket"]  # the ones you thought of
ALLOW = ["check_status", "list_regions"]  # the ones you agreed to


def admitted(
    offered: list[str], *, deny: list[str] | None = None, allow: list[str] | None = None
) -> list[str]:
    """Tool names that survive one posture. Exactly one of deny/allow is used."""
    if allow is not None:
        return [name for name in offered if name in allow]
    return [name for name in offered if name not in (deny or [])]
```

**Line by line:**

- `REVIEWED` and `TUESDAY` are the same server on two different days. The only difference is one
  extra name, and that is deliberately the whole experiment: no bug, no attack, no version bump you
  would have noticed. A server added a tool, which is a thing servers do.
- `DENY` holds the two names a careful engineer would think of — a raw SQL tool and a delete. They
  are genuinely the right things to refuse. They are also the things that already existed when the
  list was written, which is the only kind of thing a deny-list can hold.
- `ALLOW` holds the two names somebody read, understood and signed off. It is shorter than `DENY` in
  this example and that is common: the set of things you actually want is usually smaller than the
  set of things you are afraid of.
- The `*` in the signature forces `deny` and `allow` to be passed by name. Without it a reader of the
  call site sees `admitted(TUESDAY, SOMETHING)` and has to go and look up which posture that is —
  and this is exactly the function where guessing wrong is expensive.
- `if allow is not None` is checked **first**, so passing both is not ambiguous: permission wins over
  exclusion. It is also `is not None` rather than a plain truth test, because an empty allowlist must
  mean *nothing is allowed* and not *no allowlist was given*. That distinction has its own part —
  [2.4](../02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md) — and it is the single
  most expensive bug in this whole subject.
- The deny branch returns everything **not** named. Read that line again and notice there is no list
  of what it returns. That is the property being taught: the deny-list's output is defined by
  subtraction from something you do not control.
- **Zero model calls, no network, no framework.** It is four lists and a comprehension.

- The path is given from the repository root, which is where every command in this curriculum is run

- `echo "exit: $?"` prints the exit status of the command before it. The script exits `1` when the

Measured on 2026-09-04:

```text
deny-list  reviewed  -> ['check_status', 'list_regions']
deny-list  Tuesday   -> ['check_status', 'list_regions', 'open_incident']
allowlist  reviewed  -> ['check_status', 'list_regions']
allowlist  Tuesday   -> ['check_status', 'list_regions']

deny-list admitted without asking: ['open_incident']
allowlist admitted without asking: []
exit: 1
```

The first and third rows are identical. On the day you write them, the two postures are
indistinguishable, and that is why this argument is so hard to win in a design review: the reviewer
looks at the reviewed column, sees the same answer twice, and concludes the choice does not matter.

The second row is the whole day. `open_incident` is a tool that files a public record with a vendor,
it arrived without a conversation, and under the deny-list the model can now call it. Nobody was
attacked. Nobody made a mistake. The default did its job.

## When it breaks

The deny-list breaks in the way that is hardest to notice: **silently, and in the direction of more
capability**.

There is no error text to paste here, and that absence is the lesson. Compare it with the
allowlist's failure, which does have text — a tool you wanted is simply not in the model's list, and
the model says so:

```text
I don't have a tool for opening an incident with the vendor. I can check
its status and list its regions.
```

That sentence arrives in the first minute of the first attempt, from the person who wanted the tool,
and it is fixed by adding one line to a list after somebody reads what the tool does. The
deny-list's failure arrives when a model, at some point in the next several months, decides on its
own that filing an incident is a reasonable step — and then the first person to find out is whoever
reads the vendor's incident queue.

The second break is subtler and it is a real argument people make: *"our deny-list is generated from
the server's tool list, so it is complete."* It is complete against the list you generated it from,
which is a snapshot. The snapshot is the thing that goes stale
([3.1](../03-when-the-server-changes/3.1-the-tuesday-a-tool-appeared.md)), and a deny-list generated
from a stale snapshot is a deny-list with a hole shaped exactly like the change.

## In production

**What a professional writes instead:** nothing much bigger, and that is the point — this is a
one-word design decision, not a component. What a professional does add is a **test** that the
posture is what they think it is, because the posture is invisible in a diff. A line that removes
two names from a list looks the same whether the list is a permission or an exclusion, and the
reviewer who approves it has to remember which. A test named `test_unlisted_tool_is_refused` does
not have to remember.

**What degrades at scale:** the number of servers. With one server, a human eye on the tool list is a
control. With thirty, nobody looks at all of them, and the exact thing that stops being done is the
periodic re-reading that a deny-list depends on. Allowlists survive inattention; deny-lists are
maintained by attention, and attention is the resource that runs out first.

**The failure mode that only appears with real traffic:** a server that varies its tool list by
caller. The 2026-07-28 specification permits exactly this — a server's tool set *"**MAY** vary by the
authorization presented on the request — for example, returning only the tools the caller's granted
scopes permit"*. So the list your reviewer saw with their credentials is not necessarily the list
production sees with its own. A deny-list reviewed against one identity is being applied to a
different one.

**The review comment a senior engineer leaves:** *"this reads as an allowlist and behaves as a
deny-list — you named two tools to block and returned everything else. Invert it. If the argument is
that you cannot enumerate the tools you want, then you have not read them, and reading them is the
review we are supposed to be doing here."*

**The interview question:** *"allowlist or deny-list for the tools an agent can reach, and why?"* The
honest spoken answer: *"Allowlist, and the reason is not that I am afraid of malicious servers. It is
that servers add tools, which is a normal Tuesday, and a deny-list's default answer for a tool nobody
discussed is yes. We measured it on our own prop: same server, one extra tool, and the deny-list
handed the model a tool that files public incident records while the allowlist handed it nothing new.
The cost of the allowlist is a line of maintenance every time we genuinely want a new tool, and that
cost is paid by the person who wants the tool, in the first minute, with an obvious error. The cost
of the deny-list is paid by whoever reads the vendor's incident queue, months later."*
