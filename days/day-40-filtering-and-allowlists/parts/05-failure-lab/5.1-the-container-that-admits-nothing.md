# 5.1 — 💥 The container that admits nothing

## One-line answer

A tuple or a bare string in `tool_filter` falls off the end of ADK's selection rule and refuses every
tool, so the agent starts cleanly with no tools at all and nobody finds out until a user complains.

## The story

The mobile recharge goes through and the phone still says no balance.

You paid. The app said success. There is a receipt with a reference number on it, and the money has
left the account. Everything that could confirm the transaction has confirmed it.

An hour later somebody works out what happened: the number typed in was one digit off. The recharge
went to a real, valid, working number that belongs to a stranger, and every system in the chain did
exactly what it was told. There was nothing to fail. A valid number is a valid number; none of them
know which one you meant.

What makes it expensive is that success looked like success. If the digit had made the number
invalid, the app would have refused in two seconds and you would have retyped it. It was **almost**
right, and almost right is what gets through validation.

## The idea in plain language

[2.4](../02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md) was one half of the
truthiness problem: a falsy filter admits everything. This is the other half, and it fails in the
opposite direction.

Read the fourth branch of ADK's rule again:

- `None` or any falsy value → admit everything.
- callable → ask it.
- `list` → membership test.
- **anything else → `return False`.**

That last line means the framework's answer to a filter it does not understand is *refuse this tool* —
and it says it about every tool, so the agent is handed an empty list.

Which is, on its own, a defensible design. Fail-safe defaults say the answer to "I cannot decide"
should be no. The problem is not the direction; it is that **there is no signal**. No exception, no
warning, no log line. A filter of a type nobody supports is treated as a filter that matched nothing,
and "matched nothing" is a perfectly ordinary thing for a filter to do.

The three values that land here in real code:

| Value | Why somebody wrote it |
| --- | --- |
| `("check_status",)` | a constant "should" be immutable, and a tuple is the immutable sequence |
| `"check_status"` | there is only one name, so a list felt like ceremony |
| `{"check_status"}` | membership is a set operation, and this is a membership test |

Every one of those is a reasonable instinct applied to an argument that does not accept it. None of
them is a typo, so none of them looks wrong in review — and this is where
[4.2](../04-the-policy-module/4.2-a-policy-you-can-diff.md)'s tuple field becomes a trap rather than a
nicety: the record stores `allow` as a tuple for good reasons, and the module has to convert it, and
forgetting the conversion is this bug.

## Why Sutra needs it

Because `sutra/mcp/filtering.py` holds `allow` as a tuple inside a frozen record and hands it to a
framework that only understands lists. The conversion is one call to `list()`, and it is the single
most forgettable line in the module.

The reason this failure is worth its own part rather than a footnote is what it does to a person's
model of the system. An agent with no tools does not look broken; it looks like a weaker model. It
answers from what it knows, it apologises when it cannot help, and it never mentions that it has no
tools, because it does not know that it used to. Days can be spent tuning an instruction to fix
something that is a type error in a config layer.

Day 45's audit is the natural home for the check that catches it — the number of tools resolved
against the number of names in the policy — and it belongs there because it is the only check in this
whole day that catches *both* directions at once.

## The mechanism

The rule, one more time, with attention on the last line:

```python
# .venv/Lib/site-packages/google/adk/tools/base_toolset.py
    if isinstance(self.tool_filter, list):
      return tool.name in self.tool_filter

    return False
```

**Line by line:**

- `isinstance(self.tool_filter, list)` is an exact-ish type test: `list` and its subclasses pass,
  everything else does not. A `tuple` is a sequence, is iterable, supports `in`, and is not a `list`.
- `return tool.name in self.tool_filter` — this line would have worked perfectly on a tuple or a set.
  The value is never reached, which is what makes the bug feel unfair the first time you meet it.
- `return False` is the fall-through. Not a raise, not a warning: a per-tool verdict of "no", returned
  for every tool in the listing.
- The version that would have been kinder is `isinstance(self.tool_filter, (list, tuple, set,
  frozenset))`, or a raise on an unrecognised type. Neither is what is installed, so the defence is
  yours.

Ask the framework, with no server involved:

```bash

```

**Line by line:**

- Same script as [2.1](../02-the-filter-in-adk/2.1-one-argument-three-spellings.md). The last two rows
  are this part.

Measured on 2026-09-04:

```text
tool_filter=None                         admits ['check_status', 'list_regions', 'open_incident']

tool_filter=[]                           admits ['check_status', 'list_regions', 'open_incident']

```

Rows four and five are the same value expressed two ways and the same outcome: nothing.


Two correct tool names, spelled correctly, matching tools that exist on a server that is running — and
the agent gets nothing.

## When it breaks

There is no error text, and that is the finding. The run above exits 0. So does the agent that uses it.

What the failure looks like from the outside is a conversation. **This exchange is written out rather
than captured** — no model was called anywhere in this day, and inventing a transcript and calling it
a measurement would be exactly the dishonesty Principle 10 forbids. It is here as the shape to
recognise, not as evidence:

```text
User: what regions does the vendor cover?
Agent: I don't have access to the vendor's region list. Based on general
       knowledge, most providers of this kind cover Europe, Asia-Pacific
       and North America - but you should confirm that with them directly.
```

Read that reply as an operator. It is polite, it is well-formed, it hedges appropriately, and it is a
**hallucination with good manners** — the model answering from its training because it has no tool,
and having no way to say "I used to be able to look this up".

The thing that makes this expensive is the diagnosis path. The reply looks like a model quality
problem, so the first responses are the wrong ones: strengthen the instruction, add an example, try a
bigger model. Every one of those is work, and none of them can succeed, because the tool list was
empty before the instruction was ever considered.

The check that would have caught it is two lines, at the door, at startup:

```python
tools = await toolset.get_tools()
if len(tools) != len(names):
    raise RuntimeError(f"{server_key}: asked for {len(names)} tools, resolved {len(tools)}")
```

**Line by line:**

- `await toolset.get_tools()` at startup, once, rather than waiting for the first agent turn. It costs
  one listing and it converts a silent misconfiguration into a deployment that does not happen.
- `len(tools) != len(names)` catches **both** directions, which is why it is the check worth having.
  Fewer than asked for is this bug, or the renamed tool from
  [3.1](../03-when-the-server-changes/3.1-the-tuesday-a-tool-appeared.md). More than asked for is
  [2.4](../02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md)'s empty list.
- Comparing lengths rather than sets because the message stays readable and the failure is already
  unambiguous. A production version compares the sets and prints the difference, which is strictly
  better and slightly longer.
- `RuntimeError` with the server key in the message. Not a log line: a log line here is a sentence in a
  file that will be read after the incident rather than before it.
- This belongs in `sutra/mcp/filtering.py`, at the one door
  ([4.1](../04-the-policy-module/4.1-one-door-and-a-check-there-is-one.md)), for the same reason every
  other guard in this day does — a call site that bypasses the door bypasses the check.

There is one more spelling worth knowing about, because it passes the length check and still fails.
A `list` holding something that is not a string:

```python
tool_filter = [b"check_status"]  # a list, holding the wrong type
```

**Line by line:**

- `b"..."` is a `bytes` literal, which is what you get from reading a file without decoding it.
- The value **is** a `list`, so branch three fires and the membership test runs.
- `tool.name in [b"check_status"]` compares a `str` to a `bytes` and is `False` — Python does not raise
  on that comparison, it simply says no.
- So the container is right, the branch is right, the name is right, and the tool is refused. The fix is
  decoding at the boundary, and the general rule is that the value handed to `tool_filter` should be
  built by one function that knows the types rather than passed through from wherever it came from.

## In production

**What a professional writes instead:** the argument is never passed through from anywhere. One function
takes the policy record, converts explicitly with `list(policy.allow)`, asserts every element is a
`str`, refuses an empty result, and returns. Four lines, all boring, and between them they close the
empty-list hole, the wrong-container hole and the wrong-element-type hole. The type annotation is not
the defence — nothing enforces annotations at runtime — the explicit conversion is.

**What degrades at scale:** detection time. With one server and one agent, an empty tool list is noticed
in the first manual test. With a fleet, the affected path is one agent talking to one server out of
many, and everything else works, so the signal is a small dip in tool-call volume for one server —
which nobody has a graph of. What scales is the startup assertion, because it fails at deploy rather
than depending on somebody noticing an absence.

**The failure mode that only appears with real traffic:** the partial one. Six servers configured, one
of them with the tuple, and that server happens to be the one used by a minority of requests. The
error rate does not move, the latency does not move, and the only visible effect is that a small group
of users gets worse answers. That is indistinguishable from normal variance until somebody complains
twice.

**The review comment a senior engineer leaves:** *"`tool_filter=SERVERS[key].allow` passes a tuple.
ADK's selection rule only recognises `list`, so this refuses every tool and the agent starts with
none — silently. Wrap it in `list()`, and please add the resolved-count assertion at startup, because
this is the second time we have shipped a silently empty toolset."*

**The interview question:** *"what happens if you misconfigure a tool filter?"* The honest spoken
answer: *"It depends on the direction, and both are silent. An empty list is falsy, so it takes the
'no filter' branch and grants everything. Anything that is neither callable nor a `list` — a tuple, a
set, a bare string — falls off the end of the selection rule and refuses everything. The second one is
the harder incident, because an agent with no tools does not error; it answers from the model's own
knowledge with a polite hedge, which reads as a model quality problem, so people go and tune the
prompt. We caught ours with a startup assertion: resolve the toolset once at boot and fail the process
if the number of tools does not equal the number of names in the policy. It is two lines and it catches
both directions, plus a tool the vendor renamed."*
