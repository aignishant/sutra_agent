# 5.3 — 💥 The pattern that matched more than it named

## One-line answer

The moment an allowlist is written as a pattern instead of as names, it stops being a list of things
you agreed to and becomes a rule about strings — and an unanchored pattern agrees to every name that
merely contains one of yours.

## The story

You search the voter list for your uncle and type "Kumar".

The screen fills. There is Kumar the uncle, and there is also Kumari on the next street, and
Rajkumar, and Kumaraswamy, and eleven Kumars from three different families. The search did not
misbehave. You asked which rows contain "Kumar" and it told you, accurately, all of them.

The mistake was in your head, not in the machine. You meant *the person called Kumar*. What you typed
was *anything with those five letters in it*, and those are different questions that happen to have the
same answer on a short list.

On a list of forty names you notice immediately and refine the search. On a list of four thousand you
scroll, find the row you were looking for near the top, and never learn what else came back.

## The idea in plain language

An allowlist of names is a **membership test**: is this exact string one of the strings I wrote down?
It is boring, it is exact, and it has one useful property — you can read the list and know what it
permits, because what it permits is the list.

A pattern is a **predicate over strings**. It permits whatever matches, and what matches is something
you have to reason about rather than read. That is a real loss and it should be paid for.

The reasons people reach for a pattern are always the same, and always reasonable at the time:

- the server has fourteen `get_*` tools and typing them out feels like noise;
- a naming convention exists (`read_`, `list_`, `check_`) and the policy "we allow reads" maps onto it;
- the vendor keeps adding read tools and the list keeps needing edits.

Notice that the third reason is [1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md)'s
argument turned upside down. "The list keeps needing edits when the server adds tools" is not a defect
of the allowlist; **it is the allowlist working.** A pattern that stops the edits is a pattern that
stopped the reviews.

And then there is the mechanical trap on top of the design one. Python's `re.search` looks for the
pattern *anywhere* in the string. It is the function everybody reaches for, and it is the wrong one
here:

| Function | What it does | On `"check_status_and_page_oncall"` with pattern `check_status` |
| --- | --- | --- |
| `re.search` | matches anywhere in the string | matches |
| `re.match` | matches at the start | matches |
| `re.fullmatch` | the whole string must match | does not match |

`re.match` is the one that catches careful people, because "match" sounds like the strict option and it
is not. The strict one is `re.fullmatch`, or an explicitly anchored pattern using `\A` and `\Z`.

## Why Sutra needs it

Because the day the vendor server grows fourteen tools, somebody will suggest a pattern, and the
argument against it has to be ready.

The specific danger for Sutra is that its own naming is prefix-shaped. `lookup_ticket`, `search_kb`,
`list_regions`, `check_status` — a pattern like `^(lookup|search|list|check)_` would match every read
tool Sutra currently has, which is exactly what makes it attractive. It would also match
`list_customer_emails`, `check_status_and_page_oncall`, and `search_kb_including_internal_notes`, none
of which anybody has read.

`sutra/mcp/filtering.py` should therefore hold names. If a pattern is genuinely needed, it belongs in
the `ToolPredicate` form from [2.2](../02-the-filter-in-adk/2.2-the-rule-that-reads-the-room.md), where
it is code that can be unit-tested against a list of names that must *not* match — and Day 45's audit
should flag any policy record whose allowlist is not a list of literal strings.

## The mechanism

`lab/anchors.py` puts the two spellings side by side against a tool list that has grown.

```python
# lab/anchors.py
OFFERED = [
    "check_status",
    "list_regions",
    "check_status_and_page_oncall",  # added on Tuesday, nobody told you
    "list_regions_admin",
]

LOOSE = re.compile(r"check_status|list_regions")
ANCHORED = re.compile(r"\A(?:check_status|list_regions)\Z")


def admitted(pattern: re.Pattern[str]) -> list[str]:
    """Names this pattern lets through, using search - the default habit."""
    return [name for name in OFFERED if pattern.search(name)]
```

**Line by line:**

- `OFFERED` holds the two reviewed names plus two that a release added. Both additions are plausible:
  a status check that also pages the on-call engineer, and an administrative variant of a listing. Both
  are the kind of tool a vendor ships without thinking of it as a security event.
- `LOOSE` is what a policy file grows into: two alternatives, no anchors, written by somebody saving
  themselves typing. It is not sloppy — alternation is exactly the right construct for "either of
  these" — it is just missing the part that says "and nothing else".
- `ANCHORED` is the same alternation with `\A` at the start and `\Z` at the end. **`\A` and `\Z`, not
  `^` and `$`.** In Python, `^` and `$` match at line boundaries when `re.MULTILINE` is on, and `$` also
  matches just before a trailing newline even without it — so a name ending in `\n` would slip past a
  `$`-anchored pattern. `\A` and `\Z` mean start-of-string and end-of-string, full stop.
- `(?:...)` is a non-capturing group. Without the group, `\Acheck_status|list_regions\Z` parses as
  *"starts with check_status"* **or** *"ends with list_regions"*, which is a third, differently wrong
  pattern. Alternation binds looser than the anchors, and this is the classic way an anchored pattern
  is written and still leaks.
- `pattern.search(name)` is used for **both** patterns on purpose. The experiment is not "search versus
  fullmatch"; it is "what does the habit everybody has do to each of these two patterns". The anchored
  one is safe even under `search`, which is the property you want: correctness that does not depend on
  the caller remembering which function to use.
- `re.Pattern[str]` as the parameter type, so a reader knows a compiled pattern is expected rather than
  a string. Compiling at module level rather than inside the loop is also the right shape for a filter
  that runs per tool per listing.


**Line by line:**

- No server and no framework: this is a property of the pattern, and involving either would obscure it.
- Exit code 1 when the loose pattern admitted anything the anchored one did not, so the script is a
  check that can go red.

Measured on 2026-09-04:

```text
pattern 'check_status|list_regions'
  admits: ['check_status', 'list_regions', 'check_status_and_page_oncall', 'list_regions_admin']
pattern '\\A(?:check_status|list_regions)\\Z'
  admits: ['check_status', 'list_regions']

admitted by the unanchored pattern alone: ['check_status_and_page_oncall', 'list_regions_admin']
```

The pattern that names two tools admitted four. One of the extras pages a human being at three in the
morning, and the other is an administrative listing — and both arrived without a conversation, which
is precisely the property the allowlist was chosen to prevent.

## When it breaks

There is no error text. The pattern compiled, the filter ran, four tools were admitted, and the exit
code of the agent using it would be 0.

The closest thing to a signal is the one place where a bad pattern *does* fail loudly, and it is worth
seeing because it teaches the wrong lesson:

```text
re.error: missing ), unterminated subpattern at position 2
```

That is what you get from an unbalanced parenthesis, and it happens at compile time, at import, in
front of you. It trains people to believe that a pattern which compiles is a pattern which is right —
and every pattern in this part compiles.

The break with real consequences is the one where the pattern is anchored and the grouping is not:

```python
BAD = re.compile(r"\Acheck_status|list_regions\Z")
```

**Line by line:**

- This looks anchored. It has `\A` at the front and `\Z` at the back, which is the visual check a
  reviewer performs.
- Alternation has the lowest precedence in a regular expression, so the pattern actually reads as
  `(\Acheck_status)` or `(list_regions\Z)`.
- The left branch admits anything **starting** with `check_status`, so
  `check_status_and_page_oncall` is back in.
- The right branch admits anything **ending** with `list_regions`, so a tool called
  `admin_list_regions` would be admitted too — a name that is not in `OFFERED` and that nothing in this
  lab would have shown you.
- The fix is the non-capturing group, and the way to never depend on remembering it is to not use
  patterns for this at all.

And the break that has nothing to do with regular expressions: the pattern is correct, anchored,
grouped, tested — and it is still a rule rather than a list. Six months later the vendor renames
`check_status` to `service_status`, the pattern silently stops matching it, and you are in
[3.1](../03-when-the-server-changes/3.1-the-tuesday-a-tool-appeared.md)'s renamed-tool failure with an
extra layer of indirection between the symptom and the cause.

## In production

**What a professional writes instead:** literal names, generated if there are many of them. If a server
has fourteen read tools, the policy holds fourteen strings, and they were produced by listing the
server once and pasting the output into the record — which is a review, performed once, leaving an
artefact. That is strictly better than a pattern, because the artefact is what
[3.2](../03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)'s pin check needs and a
pattern gives it nothing to pin.

**What degrades at scale:** the reviewability of the policy. One pattern in one record is a thing a
reviewer can reason about. Thirty records with patterns is a policy that nobody can answer "what can
this agent reach?" from without running it, and the moment the answer requires running something, the
policy has stopped being a document and become a program with no tests.

**The failure mode that only appears with real traffic:** the pattern that was correct against the tool
list it was written for. Every pattern in this part is exactly right about `OFFERED` as it stood on the
day. The failure is not in the pattern; it is that the set it is evaluated against is under somebody
else's control, and a rule evaluated against an adversary's input is a different object from a rule
evaluated against your own.

**The review comment a senior engineer leaves:** *"this allowlist is a regex. Two problems and the
second is the real one. It is unanchored, so it admits `check_status_and_page_oncall`, which pages
somebody. And even anchored, it means the next tool matching our naming convention gets in without a
review — which is the exact behaviour we chose an allowlist to avoid. List the names. If that is
fourteen lines, it is fourteen lines that somebody read."*

**The interview question:** *"can you write your tool allowlist as a pattern?"* The honest spoken
answer: *"You can, and I would push back on it twice. Mechanically, `re.search` matches anywhere and
`re.match` matches at the start, so the pattern that names two tools admits anything containing them —
we have a lab where `check_status|list_regions` admits four tools including one that pages the on-call.
Anchoring fixes that, with `\\A` and `\\Z` rather than `^` and `$`, and inside a non-capturing group,
because alternation binds looser than the anchors and the classic bug is an anchored-looking pattern
that is actually 'starts with A or ends with B'. But the design objection is bigger than the mechanical
one. The reason to prefer a list is that the list needs editing when the server adds a tool, and that
edit *is* the review. A pattern's selling point is that it stops the edits, which means it stops the
reviews. If somebody genuinely needs a rule, it goes in the predicate form as code with tests for the
names that must not match — not in a policy file where it reads like a list."*
