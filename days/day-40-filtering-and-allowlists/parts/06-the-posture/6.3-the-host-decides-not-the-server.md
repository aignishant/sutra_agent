# 6.3 — The host decides, not the server

## One-line answer

Every trust decision in MCP belongs to the host application, because the server is the party being
trusted and a server's own claims about itself are exactly the thing under question.

## The story

The payment app asks you to confirm before the money moves.

You typed the amount, you picked the person, and the app still puts up one more screen with the number
on it and a button. Then the bank sends a code to your phone, separately, and you type that in.

It is friction, and it is friction on purpose. The shop is not asked whether this payment is fine. The
person receiving the money is not asked. The only party asked is you, because you are the only one in
the transaction whose interests are the ones being protected — everybody else has a reason to want the
payment to go through.

The version without that screen is faster, and everybody who has ever sent money to the wrong person
knows exactly which of the two designs they want.

## The idea in plain language

MCP has three roles, and Day 32's
[1.2 — Host, client, server](../../../day-32-mcp-stateless-core/parts/01-the-socket/1.2-host-client-server.md)
introduced them: the **host** is the application the user is talking to, the **client** is the
connector inside it — one per server — and the **server** is the thing offering tools.

The whole of today's argument reduces to which of those three makes decisions. The specification is not
subtle about it. The tools page carries this, as a warning:

> *"For trust & safety and security, there **SHOULD** always be a human in the loop with the ability to
> deny tool invocations."*

and the same page tells applications to *"provide UI that makes clear which tools are being exposed to
the AI model"*, to *"insert clear visual indicators when tools are invoked"*, and to *"present
confirmation prompts to the user for operations, to ensure a human is in the loop"*.

Every one of those is addressed to the **application**, not to the server. And the reason is not a
preference about architecture. It is that the server is the party being evaluated:

- A server's tool **descriptions** are its own claims about what it does
  ([1.2](../01-the-list-you-agreed-to/1.2-a-tool-list-is-a-strangers-text.md)).
- A server's tool **annotations** — the optional `annotations` field saying things like "this is
  read-only" — are also its own claims. The specification says so directly: *"clients **MUST** consider
  tool annotations to be untrusted unless they come from trusted servers."* A tool that declares itself
  read-only has declared it, nothing more.
- A server's **name**, from `serverInfo`, is not unique and
  [6.1](6.1-two-servers-one-tool-name.md) already established it cannot be used to tell servers apart.

So there is nothing a server can say that settles a question about the server. Every input the server
provides is evidence about what it *claims*, and the decision has to be made somewhere the server does
not reach. That somewhere is the host.

Day 32's [4.3 — A name that proves its publisher](../../../day-32-mcp-stateless-core/parts/04-governance-and-registry/4.3-a-name-that-proves-its-publisher.md)
made the same argument about the registry: verification proves who published something, not that it is
safe. Identity is not safety, and self-description is not identity.

## Why Sutra needs it

Because the allowlist is a host-side decision, and everything Phase 9 adds on top of it will be too.

There is a concrete decision this changes today. It is tempting, when a tool's `annotations` say
`readOnlyHint`, to let that drive policy — allow every read-only tool automatically, review only the
writers. That would be delegating a trust decision to the party being trusted, and the specification
tells you not to. In `sutra/mcp/filtering.py` the `writes` field from
[4.2](../04-the-policy-module/4.2-a-policy-you-can-diff.md) is filled in by the human doing the review,
not read off the server's annotations. The annotation is a hint worth reading; it is not the answer.

The second thing it decides is where the approval gate lives. ADK offers `require_confirmation` on
`McpToolset`, which is host-side and is the right shape. Phase 9 builds Sutra's real gates, and this
part is why they are built into the host rather than requested from servers.

## The mechanism

ADK's constructor carries the host-side hook, alongside the filter. Read them together, because they
are the two halves of the same decision:

```bash
sed -n '153,158p' .venv/Lib/site-packages/google/adk/tools/mcp_tool/mcp_toolset.py
grep -n "require_confirmation: Whether" -A 2 .venv/Lib/site-packages/google/adk/tools/mcp_tool/mcp_toolset.py
```

**Line by line:**

- The first command prints the argument block around `tool_filter`, so you can see
  `require_confirmation` a few lines below it in the same signature - the range stops just above it
  so the docstring line, printed by the second command, is the one that explains it.
- `grep -n "<text>" -A 2 <file>` prints the matching line and the two after it, with line numbers. It is
  the quickest way to pull one docstring entry out of a long one without guessing a line range.

On 2026-09-04 those printed:

```text
      tool_filter: ToolPredicate | list[str] | None = None,
      tool_name_prefix: str | None = None,
      tool_list_cache_ttl_seconds: float | None = None,
      errlog: TextIO = sys.stderr,
      auth_scheme: AuthScheme | None = None,
      auth_credential: AuthCredential | None = None,
201:      require_confirmation: Whether tools in this toolset require confirmation.
202-        Can be a single boolean or a callable to apply to all tools.
203-      header_provider: A callable that takes a ReadonlyContext and returns a
```

Three host-side controls in one constructor, and it is worth naming what each decides:

| Argument | The question it answers | Who answers it |
| --- | --- | --- |
| `tool_filter` | which tools exist for the model | the host |
| `tool_name_prefix` | which server a name belongs to | the host |
| `require_confirmation` | whether a human sees this before it runs | the host |

Not one of the three consults the server. That is the pattern, and it is the thing to recognise in any
framework: **the controls live on the client object, in your process, expressed in your code.**

And the mechanism by which confirmation actually reaches a human is one you have already met.
[2.3](../02-the-filter-in-adk/2.3-the-names-the-framework-keeps.md) listed the four reserved tool names,
and `adk_request_confirmation` is one of them. That is why they are reserved: a server that could
advertise a tool by that name could answer the framework's own confirmation requests, which is exactly
a server deciding a host-side question. The reservation in
[2.3](../02-the-filter-in-adk/2.3-the-names-the-framework-keeps.md) and the principle in this part are
the same fact seen from two ends.

What the host cannot delegate, stated as three rules:

```text
1. Which servers may be reached at all         -> policy in your repository
2. Which of a server's tools reach the model   -> tool_filter, at construction
3. Which calls a human sees before they run    -> require_confirmation / an approval gate
```

**Line by line:**

- Rule 1 is [4.2](../04-the-policy-module/4.2-a-policy-you-can-diff.md)'s registry, and the reason it
  raises on an unknown key rather than defaulting.
- Rule 2 is the whole of sections 1 to 5 of this day.
- Rule 3 is the one Sutra has not built. It is named here so it is a gap with an address rather than an
  omission — Phase 9 owns it, and Principle 13 says the capability and its containment arrive together.
- None of the three is expressible in a server's response. That is the test for whether a decision is
  host-side: if a server could change the answer by editing its own listing, it was never your control.

## When it breaks

The break has no error text, because it is a design choice that works. It looks like this in a policy
loader:

```python
allow = [t.name for t in listed.tools if t.annotations and t.annotations.readOnlyHint]
```

**Line by line:**

- `listed.tools` is the server's own listing. Every value in this expression came from the server.
- `t.annotations.readOnlyHint` is the server's claim that a tool does not modify anything. It is a hint
  in the protocol's own vocabulary — the field is literally named with `Hint` — and the specification
  says clients **MUST** treat annotations as untrusted unless the server is trusted, which is the thing
  being decided here.
- The expression is an **allowlist by shape and a delegation by effect**. It looks exactly like the
  control this day has been building, and the server is choosing what goes in it.
- The failure mode is not that a hostile server lies, although it can. It is that this line makes the
  server's next release automatically approved, which is
  [3.1](../03-when-the-server-changes/3.1-the-tuesday-a-tool-appeared.md)'s Tuesday with the review
  removed.
- The version that is a control reads the annotations, shows them to a human, and writes the human's
  decision into the policy file. Same information, different party deciding.

The second break is the confirmation that is not one. `require_confirmation=True` with a host that
auto-approves, or that shows a dialog nobody reads, satisfies the specification's letter and none of its
purpose. The specification asks for a human *with the ability to deny*; a prompt that appears forty
times an hour is a prompt that is dismissed forty times an hour, and the ability to deny has been
trained away. That is a real design problem and it is not solved by a boolean — which is why
`require_confirmation` also accepts a callable, so that confirmation can be asked for the calls that
matter rather than all of them.

The third break is the one that is only visible in an incident review. Somebody asks *"who approved the
agent being able to do this?"* and the answer is that a server offered it and a rule admitted it. There
is no person in the chain. Every mechanism worked; the decision was simply never made by anybody.

## In production

**What a professional writes instead:** confirmation is scoped by classification, not applied
uniformly. The policy record's `writes` field drives it, so read tools run freely and anything that
changes the world outside the process goes through a gate. The annotations from the server are read
into the review — they are genuinely useful as a starting point for a human — and never into the
runtime decision. And the gate logs both outcomes, because a gate that only logs denials cannot tell
you how often it was approved without being read.

**What degrades at scale:** consent fatigue, and it degrades fast. The number of confirmations is
proportional to traffic while a human's attention is not, so a gate on a busy path is dismissed
reflexively within days. What survives is a gate on a small, stable set of genuinely consequential
calls, plus an audit trail on everything else — which is a weaker guarantee, honestly stated, and much
better than a strong guarantee that nobody performs.

**The failure mode that only appears with real traffic:** the batch. A single confirmation covering
twelve tool calls, because asking twelve times was unusable, and the twelfth is not the one the human
read. The specification's advice to *"show tool inputs to the user before calling the server, to avoid
malicious or accidental data exfiltration"* is about arguments, not just tool names, and a batched
confirmation almost never shows all the arguments.

**The review comment a senior engineer leaves:** *"this builds the allowlist from the server's
`readOnlyHint` annotations. That is the server deciding what we allow. Read the annotations during
review by all means — they are a useful starting point — but the list in the policy file has to be
names a person chose, or the vendor's next release approves itself."*

**The interview question:** *"who decides what an MCP-connected agent is allowed to do?"* The honest
spoken answer: *"The host application, and the reason is that every other input is the server's own
claim about itself. Descriptions are claims. Annotations are claims, and the spec says explicitly that
clients must treat them as untrusted unless the server is trusted — which is the question you were
trying to answer. Even the server's name is not unique, so it cannot identify who you are talking to.
So the three decisions that cannot be delegated are which servers we reach at all, which of their tools
reach the model, and which calls a human sees first. In ADK all three are arguments on the client-side
toolset object — `tool_filter`, `tool_name_prefix`, `require_confirmation` — and none of them consults
the server, which is the test I use: if the server could change the answer by editing its own listing,
it was never a control. The honest weakness is the third one. The spec says there should always be a
human able to deny a tool invocation, and at real traffic volumes a uniform confirmation gets dismissed
reflexively. So we scope it to the tools our own review classified as writes, and we accept an audit
trail rather than a gate on everything else."*
