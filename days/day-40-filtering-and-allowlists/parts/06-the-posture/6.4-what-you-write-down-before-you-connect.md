# 6.4 — What you write down before you connect

## One-line answer

Connecting to a new MCP server is an intake with eight written answers, and the value of writing them
down is that adding a server becomes a reviewable commit rather than a line somebody added on a
Thursday.

## The story

The new tenant moves in on Saturday, and the society office has a form.

Name, previous address, employer, two references, a photograph, a copy of the agreement, the vehicle
number, and how many people are moving in. It takes fifteen lines and nobody enjoys it.

The form is not there because the society believes the tenant is a criminal. It is there because in
eighteen months, when a car is parked in somebody else's space or the water bill needs splitting or
somebody has to be contacted about a leak, there will be a question that nobody in the building can
answer from memory — and the person who took the form will have moved out too.

The interesting property is that the form is filled in **before** the keys are handed over. Afterwards
it never gets filled in, because afterwards there is no moment where somebody is standing there
waiting.

## The idea in plain language

Everything in this day has been a control. This part is the process the controls sit inside, and it is
short on purpose: eight questions, each of which turns into a field of the policy record from
[4.2](../04-the-policy-module/4.2-a-policy-you-can-diff.md) or into a decision that is written down.

| # | The question | Where the answer lives |
| --- | --- | --- |
| 1 | Who runs this server, and how is it reached? | `launch` in the record |
| 2 | What does it advertise **today** — every name, description and schema? | a listing, read by a person |
| 3 | Which of those does this agent actually need? | `allow` |
| 4 | Which of the allowed tools change something outside the process? | `writes` |
| 5 | What does the text we approved hash to? | `pinned` |
| 6 | What must never be taken from this server, whatever else happens? | `deny` |
| 7 | How stale may our copy of its tool list be? | `ttl_seconds` |
| 8 | Who read it, and when? | `reviewed_on` and an owner |

Two things about this list are worth arguing for, because both get cut first.

**Question 2 is the whole review, and it is the one that is skipped.** Reading every description means
reading text a stranger wrote, with the specific question *"is any of this addressed to a model rather
than to me?"* in mind. It is the only defence in the entire day against a description that was hostile
on its first day, and no script can do it —
[6.2](6.2-the-attacks-a-filter-does-not-stop.md)'s table has that row marked *"a human reading it at
review time. Nothing automated."*

**Question 4 is the one that determines everything downstream.** Whether a tool writes decides whether
a rewritten description is a queue item or a block
([3.2](../03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)), and whether a call goes
through an approval gate ([6.3](6.3-the-host-decides-not-the-server.md)). And it must be answered by
the person reviewing, not read off the server's annotations, for the reason
[6.3](6.3-the-host-decides-not-the-server.md) gives: a server's claim about itself is not an answer to
a question about the server.

The intake is deliberately not a risk score. A number invites comparison and averaging; eight answers
invite eight arguments, which is what you want, because the interesting ones are always specific.

## Why Sutra needs it

Because Day 45 is the Phase 6 gate — a full MCP audit of `sutra-core` — and an audit is a walk over
answers somebody wrote down.

`tools/mcp_audit.py`, which Day 45 adds to `./m check`, can only check things that exist. Every row in
the table above is a field it can read: a record with no `pinned` entries is a server that was
connected without a listing being taken; a `reviewed_on` older than some agreed age is a finding; an
`allow` list with a name that is not in `pinned` is a tool approved without its text being recorded.
None of those checks can be written unless today's intake produced the data.

There is a second reason, and it is about Sutra specifically. The plan's Phase 6 gate is *"MCP audit of
sutra-core passes"*. That is a claim about a system, and a claim about a system is only as good as the
inventory behind it. This part is the inventory.

## The mechanism

The intake as a checklist you can copy into a pull-request template, with the commands beside the
questions that have one:

```bash
# 2 - read everything it advertises, before any agent exists
uv run python days/day-40-filtering-and-allowlists/lab/listing.py

# 5 - record the surface you approved
uv run python days/day-40-filtering-and-allowlists/lab/pin.py; echo "exit: $?"

# 3, 6 - prove the filter resolves to exactly the names you chose
uv run python days/day-40-filtering-and-allowlists/lab/resolve.py allow

# and the standing check: is there still only one door?
uv run python days/day-40-filtering-and-allowlists/lab/one_door.py; echo "exit: $?"
```

**Line by line:**

- Question 2 first, and with no agent anywhere. Reading a tool list is not a thing to do *while*
  wiring up an agent, because at that point you are debugging a connection and not reviewing text.
- The pin comes after the reading, not instead of it. Running `pin.py` on a server nobody has read
  records a digest of text nobody approved, which is
  [3.2](../03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)'s third failure — a pin
  that certifies whatever it found.
- `resolve.py allow` is the check that the policy you wrote produces the tool list you meant. It is the
  one that catches [5.1](../05-failure-lab/5.1-the-container-that-admits-nothing.md)'s wrong container
  and [2.4](../02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md)'s empty list, because
  both show up as a resolved list of the wrong length.
- `one_door.py` last, because it is about the repository rather than about this server, and it is the
  check that keeps every other one meaningful
  ([4.1](../04-the-policy-module/4.1-one-door-and-a-check-there-is-one.md)).
- These are lab scripts today. Day 45 is where their reusable half becomes `tools/mcp_audit.py` and a
  line in `./m check`, and the intake stops being something you remember to run.

The three answers that are decisions rather than data, written out so they can be disagreed with:

```text
Default posture         : allowlist. A tool nobody discussed is refused.
Filtering point         : at toolset construction, never at dispatch.
Trust decisions         : host-side. Nothing the server says about itself decides anything.
```

**Line by line:**

- The first line is [1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md), and it
  is written as a sentence rather than a setting because it has to survive the person who set it.
- The second is [5.2](../05-failure-lab/5.2-filtered-after-it-was-read.md). "Never at dispatch" is
  slightly too strong as a rule and exactly right as a default — a dispatch check is welcome as a
  second layer and unacceptable as the only one.
- The third is [6.3](6.3-the-host-decides-not-the-server.md), and it is the one that most often gets
  quietly reversed, because reading `readOnlyHint` off the listing is genuinely convenient.
- All three belong at the top of `sutra/mcp/filtering.py` as a comment. A policy in a module docstring
  is read by everybody who edits the module, which is exactly the audience, and it does not go stale in
  a wiki nobody opens.

And what the intake **cannot** tell you, listed so nobody mistakes a completed form for a safe server:

| Question the intake answers | Question it does not |
| --- | --- |
| what this server offers today | what it will return when called |
| what its descriptions say | whether a result carries an instruction |
| which tools this agent may use | what those tools can do in combination |
| when it was last read | whether it behaves the same for every caller |

## When it breaks

The break is a completed form and an unread listing, and there is no output to paste because
everything succeeded:

```text
pin: 2 tools, findings: 0
exit: 0
```

That is what `pin.py` prints for a server somebody pinned without reading. It is identical to what it
prints for a server somebody read carefully. The digest records that the text has not changed since it
was recorded, and it makes no claim at all about whether the text was ever appropriate — which is why
question 2 cannot be replaced by question 5, however much the second one looks like evidence.

The second break is the intake done during an incident. Something is down, a vendor's tool would help,
and a record appears in the registry with `allow` copied from a similar server and `reviewed_on` set to
today. Every field is populated. The audit will pass. There is no technical defence against this and
inventing one would be dishonest — what there is, is making the *shape* of a rushed record visible: an
entry whose `pinned` table is empty was added without a listing, and a check for that is three lines.

The third break is the form that grows. Eight questions is a form people fill in. Twenty is a form
people copy from the entry above, and a copied form is worse than no form, because it produces the
appearance of a review. If a ninth question is genuinely needed, something should come off.

## In production

**What a professional writes instead:** the intake is a pull-request template, so the answers land in
the review where the code lands, and the reviewer is looking at the descriptions and the policy record
in the same diff. The commit that adds a server and the commit that records the review are the same
commit — which is the only arrangement where the review cannot be skipped, because there is no separate
moment for it to be skipped in.

**What degrades at scale:** who does question 2. At three servers, the engineer adding the integration
reads the descriptions. At thirty, integrations are added by people who did not write the policy and
have never seen an injected description, and the reading becomes a box. What holds up is a shared page
of real examples — this day's prop is one — so the reviewer knows what they are looking for rather than
being asked to be generally careful.

**The failure mode that only appears with real traffic:** the server that was reviewed in one
environment and connected in another. The intake was completed against a sandbox instance with three
tools; production points at the real host, which has nine. Every answer is honest and about a different
server. The countermeasure is that the pin check runs in the environment that matters, against the
credentials the agent uses, and fails when the surface it finds is not the surface that was recorded.

**The review comment a senior engineer leaves:** *"this pull request adds a server and its policy
record, and the record is complete. What I cannot see is the listing — paste the tool names and
descriptions into the description of this pull request so the reviewer is reviewing the text and not
just the fact that somebody typed a date into `reviewed_on`."*

**The interview question:** *"walk me through connecting your agent to a new third-party MCP server."*
The honest spoken answer: *"It is an intake before it is a code change. Eight questions: who runs it and
how it is reached, what it advertises today with every description and schema read by a person, which
of those this agent actually needs, which of the allowed ones write rather than read, digests of the
text we approved, anything that must never be taken from it, how stale the cached listing may be, and
who read it and when. Seven of the eight become fields in a policy record, and it all lands in one
pull request with the listing pasted into the description, so the review is of the text rather than of
a date somebody typed. The question that carries the most weight is the second one, reading every
description, because it is the only defence we have against a description that was hostile from day
one — nothing automated catches that. And the one I am most careful about is classifying which tools
write, because that has to be our judgement rather than the server's `readOnlyHint`, or the vendor is
deciding what needs approval."*

## Check yourself

```bash
uv run python days/day-40-filtering-and-allowlists/lab/listing.py
uv run python days/day-40-filtering-and-allowlists/lab/pin.py; echo "exit: $?"
uv run python days/day-40-filtering-and-allowlists/lab/resolve.py allow
uv run python days/day-40-filtering-and-allowlists/lab/one_door.py; echo "exit: $?"
```

Run all four in order against the prop and fill in the eight answers for it as if it were a real
vendor. Then run the first one with `VENDOR_V2=1` and decide, from the text alone, whether you would
approve it.

**Out loud, without scrolling up:** name the intake question that no script can answer, and say why a
green pin check is not evidence that a server was reviewed.
