# 2.1 — One argument, three spellings

## One-line answer

`tool_filter` accepts exactly three things — `None`, a `list[str]` of names, or a callable — and the
framework decides which of the three you meant by looking at the value's type, not at what you
intended.

## The story

The note for the milkman goes under the flowerpot every night.

Some nights it says *"2 litres"* and that is what arrives. Some nights it says *"whatever is on the
board today"*, and the milkman looks at the board outside the dairy and brings that. Some nights
there is no note at all, and he brings what he always brings, which is his standing idea of your
order.

Three kinds of note, and the milkman decides which kind he is holding by looking at it. A number is a
quantity. A sentence is a rule. Nothing is nothing.

Now put a blank slip of paper under the flowerpot. You meant *"nothing today"*. He picks it up, finds
no quantity and no rule, treats it as the same as no note at all, and leaves the usual two litres.
Nobody was careless. The slip was a fourth kind of note and there were only three kinds.

## The idea in plain language

`tool_filter` is one keyword argument on `McpToolset`, and it is **overloaded**: the same parameter
name accepts values of different types and means something different for each.

| You pass | The framework reads it as | Result |
| --- | --- | --- |
| nothing, or `None` | "no filter" | every tool the server offered |
| `["a", "b"]` | a list of names to include | only tools whose name is in the list |
| a function | a `ToolPredicate` | the function is asked about each tool |

That is the whole surface. There is no wildcard, no prefix match, no regular expression and no
"exclude these" form. If you want any of those, you write the function — which is
[2.2](2.2-the-rule-that-reads-the-room.md).

Two things follow from "the framework decides by looking at the type", and both of them are the
subject of a later part in this day:

- A value that is none of the three is not an error. It falls through to a default, and the default is
  not the same in both directions. `[]` admits everything ([2.4](2.4-the-empty-list-that-admits-everything.md));
  a tuple or a bare string admits nothing ([5.1](../05-failure-lab/5.1-the-container-that-admits-nothing.md)).
- Overloaded arguments are quiet. A wrong type in a normal function raises a `TypeError` at the call.
  Here it is stored on the object and consulted much later, in a coroutine, in a loop, where nothing
  is left of the mistake but a tool list of the wrong size.

Day 33's [1.4 — The allowlist is a constructor argument](../../../day-33-client-and-transports/parts/01-the-connector/1.4-the-allowlist-is-an-argument.md)
established that the argument exists and that omitting it is a decision. This part is about what it
actually accepts, read out of the installed framework rather than out of a docs page.

## Why Sutra needs it

Because `sutra/mcp/filtering.py` — the module [4.1](../04-the-policy-module/4.1-one-door-and-a-check-there-is-one.md)
tells you to write — is going to build every one of Sutra's toolsets, which means it will be the one
place in the repository where a value gets handed to this argument. If it hands over the wrong shape,
every server is wrong at once, and it will be wrong quietly.

That is also why the module's public function is going to return a `list[str]` and not "whatever the
policy record happened to hold". A policy record read out of a file gives you a JSON array, which
`json.load` gives back as a `list` — fine — but a policy record built by a comprehension over a `set`
gives you a `set`, and a set is not a list. Nothing in this stack will tell you.

Day 44 adds `sutra/mcp/hardening.py` alongside this module, and Day 45's audit walks both. The audit
can only check "is there a filter" if there is one shape it knows how to look at.

## The mechanism

The signature, read out of the installed package:

```bash
sed -n '144,158p' .venv/Lib/site-packages/google/adk/tools/mcp_tool/mcp_toolset.py
```

**Line by line:**

- Same technique as [1.3](../01-the-list-you-agreed-to/1.3-the-filter-is-on-your-side.md): quote the
  code that is actually installed, at a line range you can re-run to see whether it moved.
- `google-adk==2.7.1` is what `pyproject.toml` pins, so this is the surface Sutra is built against.

On 2026-09-04 that printed:

```text
  def __init__(
      self,
      *,
      connection_params: (
          StdioServerParameters
          | StdioConnectionParams
          | SseConnectionParams
          | StreamableHTTPConnectionParams
      ),
      tool_filter: ToolPredicate | list[str] | None = None,
      tool_name_prefix: str | None = None,
      tool_list_cache_ttl_seconds: float | None = None,
      errlog: TextIO = sys.stderr,
      auth_scheme: AuthScheme | None = None,
      auth_credential: AuthCredential | None = None,
```

`tool_filter: ToolPredicate | list[str] | None = None`. Three types, and the default is the permissive
one. The `*` on the third line makes every argument keyword-only, so `McpToolset(params, names)` is a
`TypeError` — a small kindness, because it means nobody ever passes a filter into the connection slot
by accident.

Now the rule that consumes it. It lives one class up, on `BaseToolset`, because every toolset in ADK
shares it and not only the MCP one:

```bash
sed -n '194,206p' .venv/Lib/site-packages/google/adk/tools/base_toolset.py
```

**Line by line:**

- A different file: `base_toolset.py`, not `mcp_toolset.py`. That is worth noticing on its own — the
  filtering semantics are ADK's, not MCP's, so they apply identically to the OpenAPI toolset from Day
  15 and to anything else you build on `BaseToolset`.

On the same day that printed:

```text
  def _is_tool_selected(
      self, tool: BaseTool, readonly_context: Optional[ReadonlyContext]
  ) -> bool:
    if not self.tool_filter:
      return True

    if isinstance(self.tool_filter, ToolPredicate):
      return self.tool_filter(tool, readonly_context)

    if isinstance(self.tool_filter, list):
      return tool.name in self.tool_filter

    return False
```

Four branches, in order, and the order is the whole behaviour. Read them as a decision list:

1. **Falsy filter → admit.** `None` is falsy. So is `[]`. So is `""`. So is `0`.
2. **Callable → ask it.**
3. **List → membership test.**
4. **Anything else → refuse.**

You can ask the framework directly rather than reasoning about it. `lab/filter_semantics.py` builds a
throwaway toolset per spelling and asks the real method what it would admit:

```python
# lab/filter_semantics.py
class Named(BaseTool):
    """The smallest thing `_is_tool_selected` will accept: something with a name."""

    def __init__(self, name: str) -> None:
        super().__init__(name=name, description="")


class Probe(BaseToolset):
    """A toolset that exists only to be asked what its filter would admit."""

    async def get_tools(self, readonly_context=None) -> list[BaseTool]:
        return []


SPELLINGS: list[object] = [
    None,
    ["check_status"],
    [],
    "check_status",
    ("check_status",),
]
```

**Line by line:**

- `Named` subclasses ADK's real `BaseTool` rather than faking one with a `namedtuple`. The membership
  branch reads `tool.name` and the predicate branch is handed the whole object, so a stand-in has to
  be the real type or the test is testing your stand-in.
- `description=""` because `_is_tool_selected` never looks at a description. Giving it a fake one
  would imply the description matters here, and it does not — which is precisely why a rewritten
  description sails through an allowlist in
  [3.2](../03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md).
- `Probe` exists because `BaseToolset` is abstract: `get_tools` is an `@abstractmethod`, so you cannot
  instantiate the base class. The smallest legal subclass returns an empty list and is never called.
- `SPELLINGS` is typed `list[object]` on purpose. Typing it `list[str] | None` would be a lie — half
  these values are the wrong type, and that is the point of the experiment.
- The last two entries are the two mistakes people actually make: a bare string when they meant one
  name, and a tuple because a constant "should" be immutable. Both are reasonable instincts and both
  are wrong here.

```bash
uv run python days/day-40-filtering-and-allowlists/lab/filter_semantics.py
```

**Line by line:**

- No server, no network, no model. The script imports the framework's own class and calls its own
  method, so the answer is the framework's answer and not a description of it.

Measured on 2026-09-04:

```text
tool_filter=None                         admits ['check_status', 'list_regions', 'open_incident']
tool_filter=['check_status']             admits ['check_status']
tool_filter=[]                           admits ['check_status', 'list_regions', 'open_incident']
tool_filter='check_status'               admits []
tool_filter=('check_status',)            admits []
```

Rows one and two are what everybody expects. Rows three, four and five are the day's material.

## When it breaks

The break with an actual message is the one you *want*, because it happens at the call:

```text
TypeError: McpToolset.__init__() takes 1 positional argument but 3 were given
```

That is the `*` doing its job: you tried `McpToolset(params, ["check_status"])` and it refused
immediately. Nothing was constructed, nothing was silently mis-configured, and the fix is to name the
arguments.

The break with no message is everything else. Pass a tuple and you get an agent with no tools; pass an
empty list and you get an agent with every tool. Both constructions succeed, both `get_tools()` calls
return normally, and the only evidence is the length of a list nobody printed. Those two are big
enough to own parts of their own —
[2.4](2.4-the-empty-list-that-admits-everything.md) and
[5.1](../05-failure-lab/5.1-the-container-that-admits-nothing.md).

There is one more, and it is the one that catches careful people. A `set` is not a `list`:

```python
ALLOWED = {"check_status", "list_regions"}  # a set literal, not a list
McpToolset(connection_params=params, tool_filter=ALLOWED)
```

**Line by line:**

- `{...}` with no colons is a set literal. It looks enough like a list at a glance that reviewers miss
  it, and enough like a dict that people assume it is one.
- A non-empty set is truthy, so branch 1 does not fire. It is not callable, so branch 2 does not fire.
  `isinstance(set, list)` is `False`, so branch 3 does not fire. It falls to branch 4 and **every tool
  is refused**.
- The fix is `sorted(ALLOWED)`, which also gives you a stable order for logging and hashing — a set's
  iteration order is not something to build a pinned digest on.

## In production

**What a professional writes instead:** they do not pass a literal to this argument at all. The value
comes from one function whose return type is annotated `list[str]`, and there is a test that asserts
the number of tools handed to the agent equals the number of names in the policy. A type annotation is
a claim; the assertion is the check, and this is exactly the argument where a claim is not enough
because nothing verifies it at runtime.

**What degrades at scale:** the number of construction sites. One toolset built by hand is reviewable.
Fifteen, spread across agent files written by five people, is fifteen chances for one of them to be a
tuple. That is the entire reason for
[4.1](../04-the-policy-module/4.1-one-door-and-a-check-there-is-one.md)'s single door — not tidiness,
but reducing the number of places this particular mistake can be made from fifteen to one.

**The failure mode that only appears with real traffic:** the config-driven filter. Policy in a YAML
file, loaded at startup, passed straight through. A YAML list is a Python list, so it works — until
someone writes `tool_filter: check_status` without the dash, YAML gives you a string, and the agent
silently has no tools. It comes back as *"the assistant has stopped being able to look things up"*,
reported by a user, days later.

**The review comment a senior engineer leaves:** *"`tool_filter` is overloaded and the type decides
the meaning. This value comes out of a config loader, so please assert `isinstance(names, list)` and
`all(isinstance(n, str) for n in names)` before you pass it, or convert with `sorted()`. Otherwise the
config file is a place where a missing dash turns the agent off and nothing raises."*

**The interview question:** *"what does `tool_filter` accept, and what happens if you pass something
else?"* The honest spoken answer: *"`None`, a list of tool names, or a `ToolPredicate` callable. What
I would emphasise is what happens outside those three, because the framework picks a branch by type
and there is no error path. A falsy value — including an empty list — takes the first branch and
admits everything, and anything that is neither callable nor a `list` falls off the end and admits
nothing. So a set or a tuple silently disables every tool and an empty list silently disables the
filter. I read `_is_tool_selected` in `base_toolset.py` to establish that rather than guessing, and I
keep a small script that asks the framework what each spelling admits, so the answer is measured
whenever we upgrade."*
