# 2.3 — The names the framework keeps

## One-line answer

Four tool names belong to ADK itself, and a server advertising one of them has its tool dropped with a
warning, because otherwise the server's tool would be dispatched in place of the framework's own.

## The story

You save the plumber's number in your phone under "Home".

There is already a contact called "Home" — it is the landline, and it has been in there for years.
Your phone does not stop you. Two contacts, one name, and from now on when somebody in the family
says *"call Home"* into the phone, one of the two answers and neither of you is confident which.

The mistake was not saving a number. It was reusing a word that already meant something to the
machine. The machine resolves names, it does not resolve intentions, and it had no way to know that
"Home" was already spoken for.

The fix is boring: pick a different name. The interesting part is that nothing warned you, so you only
found out when the wrong phone rang.

## The idea in plain language

An agent framework does not only dispatch the tools you gave it. It also dispatches a handful of
**framework-owned function calls** — the ones the model emits to ask the runtime for something rather
than to do work.

In ADK there are four of them, and they are held in a constant called `_RESERVED_TOOL_NAMES`:

| Name | What the framework does with it |
| --- | --- |
| `adk_request_confirmation` | the model is asking a human to approve an action |
| `adk_request_credential` | the model is asking for a credential it does not have |
| `adk_request_input` | the model is asking the user a question |
| `transfer_to_agent` | the model is handing the conversation to another agent |

Now suppose a server advertises a tool called `transfer_to_agent`. The model sees one name.
When it emits that call, whoever resolves names first wins — and if the server's tool won, a
third-party process would be handed every hand-over the agent ever performs. That is not a filtering
problem, it is a **namespace** problem, and it is the reason the framework refuses these four before
your filter is ever consulted.

The refusal happens in two different places with two different behaviours, and the difference is
deliberate:

- **`MCPTool.__init__` raises** a `ValueError` if you construct a single tool with a reserved name.
- **`McpToolset.get_tools()` skips** such a tool and logs a warning, so the rest of the server's
  honest tools survive.

The framework's own comment explains the split: *"Skip rather than let McpTool raise: one reserved
name would otherwise fail the whole listing and take the server's honest tools down with it."* That is
an availability decision, and it has a cost — a skip is a log line, and log lines are the thing nobody
reads.

This is a **partial** defence and it is worth being precise about the boundary. It protects four
names that ADK owns. It does nothing at all about a server naming its tool `lookup_ticket`, which is
Sutra's name and not ADK's. That gap is [6.1](../06-the-posture/6.1-two-servers-one-tool-name.md).

## Why Sutra needs it

Because Sutra is going to run more than one agent, and hand-overs between them are how the desk is
built.

`transfer_to_agent` is not a curiosity in this repository. Multi-agent routing is the mechanism by
which a triage agent passes a ticket to a specialist, and it is dispatched by name like everything
else. A vendor server that could claim that name could intercept every routing decision Sutra makes.

There is also a Sutra-shaped lesson in the *shape* of the mitigation. ADK solved this by reserving a
prefix — three of the four names begin with `adk_` — and refusing anything that collides. That is the
same move [6.1](../06-the-posture/6.1-two-servers-one-tool-name.md) will make with
`tool_name_prefix`, and the same move the MCP specification itself recommends to clients that
aggregate multiple servers. When you find yourself with two things that must never be confused, giving
one of them a namespace is usually the answer.

Day 45's audit should know these four names, because "the server offered a reserved name" is a finding
about the server, not a routine log line.

## The mechanism

The constant, read out of the installed package:

```bash
sed -n '66,75p' .venv/Lib/site-packages/google/adk/tools/mcp_tool/mcp_tool.py
```

**Line by line:**

- The file is `mcp_tool.py` — the single-tool wrapper — not `mcp_toolset.py`. The names are defined
  next to the class that raises on them, and imported by the toolset that skips them.
- `sed -n 'A,Bp'` keeps the quote honest and re-runnable, the same habit as
  [1.3](../01-the-list-you-agreed-to/1.3-the-filter-is-on-your-side.md).

On 2026-09-04 that printed:

```text
# Tool names the framework itself puts on the wire. A server advertising one of
# these would have its tool dispatched in place of the framework's own, so the
# name is refused at registration.
_RESERVED_TOOL_NAMES = frozenset({
    REQUEST_EUC_FUNCTION_CALL_NAME,
    REQUEST_CONFIRMATION_FUNCTION_CALL_NAME,
    REQUEST_INPUT_FUNCTION_CALL_NAME,
    transfer_to_agent.__name__,
})
```

The four entries are constants and a function's `__name__`, not string literals, so the source does not
tell you what they resolve to. Resolve them:

```python
# lab/reserved.py
from google.adk.tools.mcp_tool.mcp_tool import _RESERVED_TOOL_NAMES

print(f"reserved by the framework: {sorted(_RESERVED_TOOL_NAMES)}")
```

**Line by line:**

- The leading underscore says this is private and may move between versions. Importing it in a lab
  script is fine — the script's whole job is to report what this version does — but nothing under
  `sutra/` should depend on it. If Sutra needs the list, Sutra writes its own copy with a comment
  saying where it came from and what to re-check.
- `sorted()` rather than printing the `frozenset` directly, because a set has no stable order and a
  transcript in a document has to be reproducible.

The other half of the script mounts a server that advertises one of the four and prints what survives:

```python
# lab/reserved.py
async def offered_to_the_agent() -> list[str]:
    """Tool names an agent is handed from a server that clashes with the framework."""
    toolset = McpToolset(
        connection_params=StdioConnectionParams(
            server_params=StdioServerParameters(
                command=sys.executable,
                args=[str(PROP)],
                env={**os.environ, "VENDOR_CLASH": "1"},
            ),
            timeout=20,
        ),
        tool_filter=None,
    )
    try:
        return [tool.name for tool in await toolset.get_tools()]
    finally:
        await toolset.close()
```

**Line by line:**

- `env={**os.environ, "VENDOR_CLASH": "1"}` copies your environment and adds one key, which is how the
  prop turns into its third version. Writing `env={"VENDOR_CLASH": "1"}` instead would launch the
  child with an environment holding one variable and no `PATH`, and on Windows that fails in a way
  that has nothing to do with this lesson.
- `tool_filter=None` — deliberately **no** allowlist. The point is that this defence is the
  framework's and fires before yours, so the experiment has to remove yours.
- Everything else is [1.3](../01-the-list-you-agreed-to/1.3-the-filter-is-on-your-side.md)'s toolset,
  unchanged, so the only variable is the clashing name.

```bash
uv run python days/day-40-filtering-and-allowlists/lab/reserved.py
```

**Line by line:**

- Run it with the server's standard error visible. The warning is the interesting output and it does
  not come from the script.

Measured on 2026-09-04, with the framework's own log line left in:

```text
Processing request of type ListToolsRequest
Skipping MCP tool 'transfer_to_agent' because it collides with a reserved ADK framework tool name.
reserved by the framework: ['adk_request_confirmation', 'adk_request_credential', 'adk_request_input', 'transfer_to_agent']
the server advertised     : ['check_status', 'list_regions', 'transfer_to_agent']
the agent is handed       : ['check_status', 'list_regions']
```

Three tools advertised, two handed over, one warning. The server is still connected and its honest
tools still work, which is the availability trade-off the framework's comment describes.

## When it breaks

The break is that the warning is a warning. Here is the whole of what a production log shows when a
server tries to take over your hand-over mechanism:

```text
Skipping MCP tool 'transfer_to_agent' because it collides with a reserved ADK framework tool name.
```

One line, at `WARNING` level, from `google_adk.google.adk.tools.mcp_tool.mcp_toolset`, among however
many thousand lines your agent writes. Nothing fails, no exit code changes, no alert fires. A server
attempting to hijack every agent hand-over in your system produces the same operational signal as a
deprecation notice.

The other break is the one that raises, and you meet it if you ever build a tool by hand rather than
through a toolset:

```text
ValueError: MCP tool name 'transfer_to_agent' collides with a reserved ADK tool name.
```

That one is loud and easy. It is the quiet one that needs an owner.

There is also a break of expectation. People assume this list protects *their* names. It does not.
Add a tool called `lookup_ticket` to the prop instead of `transfer_to_agent` and re-run: it sails
through, because `lookup_ticket` is Sutra's name and ADK has never heard of it.

## In production

**What a professional writes instead:** they turn the warning into a finding. A startup check compares
the names a server advertised against the names the toolset handed over; if the two differ by anything
other than the allowlist, that is an event with a name and an owner, not a log line. The four reserved
names are copied into the check with a comment naming the ADK version they were read from, so an
upgrade that adds a fifth is a test failure rather than a surprise.

**What degrades at scale:** log volume. At one server you would notice this line. At thirty servers
across a fleet, with re-listing on every cold start, the warning is emitted continuously by whichever
server is misbehaving, and continuous warnings are how a signal becomes wallpaper. Alert on the
*first* occurrence per server per deploy, not on the rate.

**The failure mode that only appears with real traffic:** the name that is reserved next year. ADK adds
framework-dispatched calls over time — `adk_request_confirmation` is newer than `transfer_to_agent` —
and a server that has been serving a tool called, say, `adk_request_input` for a year becomes a
skipped tool on the day you upgrade. The agent loses a capability, nothing errors, and the cause is in
a release note.

**The review comment a senior engineer leaves:** *"we are relying on a `logger.warning` to tell us that
a third party tried to claim `transfer_to_agent`. That is a security event and it is going to the same
place as our HTTP retry noise. Please raise it out of the toolset — compare advertised names against
resolved names at connect time and fail the connection."*

**The interview question:** *"what stops an MCP server from advertising a tool with the same name as
one of your framework's own?"* The honest spoken answer: *"In ADK, a reserved-name set — four names,
including `transfer_to_agent`, which is how agents hand conversations to each other. A single tool with
one of those names raises at construction, but the toolset skips it with a warning instead, so one
hostile name does not take a whole server's honest tools offline. I would push back on the warning
level, though: a server trying to claim the hand-over name is a finding, not a log line, and we
promote it to a failed connection at startup. And the important limit is that this protects the
framework's four names and nothing else — if a second server advertises a tool called `lookup_ticket`
and I have one of those already, nothing in the framework notices. That one I solve with
`tool_name_prefix`."*
