# 2.4 — 💥 The empty list that admits everything

## One-line answer

`tool_filter=[]` reads as "no filter" and hands the model every tool the server has, because the
framework tests the value for truth rather than for absence — and an empty list is false.

## The story

The plumber fits a water filter under the kitchen sink on a Saturday.

It is a proper housing with a lid, a bracket, an inlet and an outlet, and it is plumbed in correctly.
The tap runs. The water is clear. For four months the family drinks it and nobody thinks about it
again, because the whole point of a filter is that you stop thinking about it.

In February someone opens the housing to change the cartridge and finds the housing empty. The
cartridge was never fitted. Water had been running straight through a plastic cylinder and out into
the glass.

Nothing had failed. The tap never spluttered, the pressure never dropped, and the water never once
looked wrong — because a filter with nothing in it does not restrict flow. **The absence of the thing
that filters is indistinguishable, from the outside, from a filter that has nothing to remove.**

## The idea in plain language

Python treats several very different values as false in a boolean test: `None`, `False`, `0`, `""`,
`[]`, `{}`, `set()`. This is normally a convenience. Here it is a security bug, because two of those
values mean opposite things in this argument.

- `tool_filter=None` means *"I have not set a filter"*.
- `tool_filter=[]` means *"I have set a filter, and it names nothing"*.

The first should admit everything. The second should admit nothing. ADK's rule cannot tell them apart,
because its first line is `if not self.tool_filter: return True` — a test for truthiness, not for
`None`. Both fall into the same branch, and the branch is the permissive one.

Two words for what has gone wrong, and both are from the paper this day ends on:

- **Fail-safe defaults** says the default action when a decision cannot be made should be to refuse.
  Here the default action is to admit.
- **Economy of mechanism** says a protection mechanism should be small enough to be verified by
  inspection. `if not x` is as small as a mechanism gets, and it is still wrong, because "small" and
  "correct" are different properties.

The reason this particular mistake gets written is that an empty list is what you get from doing
everything right. A policy file with no names yet. A comprehension that filtered out everything. A
`.get("allow", [])` on a config section somebody forgot to fill in. Nobody types `tool_filter=[]`; they
compute it, and computing it is exactly how a missing policy becomes an open door.

## Why Sutra needs it

Because `sutra/mcp/filtering.py` will compute its allowlist rather than typing it, which is the shape
that produces this bug.

The module's job is to turn a policy record into an argument. A record for a server that has been
added to the policy but not yet reviewed — no names filled in — produces an empty list. Handing that
straight to `McpToolset` means the server nobody has reviewed is the one server with no restrictions
at all. The failure is not merely silent; it is **inverted**, and it targets exactly the servers you
trust least.

This is why [4.1](../04-the-policy-module/4.1-one-door-and-a-check-there-is-one.md) insists on one
construction site. One place to compute the argument is one place to refuse to compute an empty one.

Day 45's audit should carry this as a check on the code, not on the config: "no call site passes a
possibly-empty list to `tool_filter`" is a grep, and it is worth having.

## The paper behind it

> **The protection of information in computer systems** · `doi:10.1109/PROC.1975.9939` · 1975 ·
> `https://doi.org/10.1109/PROC.1975.9939`

**Fail-safe defaults**: base access decisions on permission rather than exclusion, so that a mistake in
the mechanism fails by refusing access rather than by granting it. This part is one line of framework
code getting that exactly backwards.

## The mechanism

The line, read out of the installed package. It is the first branch of the rule
[2.1](2.1-one-argument-three-spellings.md) walked through:

```python
# .venv/Lib/site-packages/google/adk/tools/base_toolset.py
    if not self.tool_filter:
      return True
```

**Line by line:**

- `not self.tool_filter` is a truthiness test. It is `True` for `None`, and it is equally `True` for
  `[]`, `()`, `""` and `set()`.
- `return True` means "this tool is selected", so a falsy filter admits every tool.
- The version that would have been safe is `if self.tool_filter is None:` — an identity test against
  the one value that actually means "unset". It is three characters longer and it distinguishes
  "no filter" from "a filter naming nothing".
- **This is not a bug report.** It is the documented behaviour of a widely used framework, the same
  choice several other frameworks make, and it is the reason this part exists: your code has to defend
  against it, because the framework is not going to.

Prove it against a real server rather than trusting the reading:

```bash
uv run python days/day-40-filtering-and-allowlists/lab/resolve.py empty
```

**Line by line:**

- `empty` is one of `resolve.py`'s five postures and it passes `tool_filter=[]`. Every other argument
  is identical to the `allow` run, so the difference in output has exactly one cause.


Rows one and three are identical. That is the bug, printed.

## When it breaks

There is no error text. That is the entire failure mode, and pretending otherwise would be dishonest:

```text
server v2 (Tuesday), posture 'empty' -> tool_filter=[]
  the agent is handed: ['check_status', 'list_regions', 'open_incident']
```

Exit code 0. No warning, no log line, no traceback. The agent works. It works *better*, from the
model's point of view, because it has more tools.

What it looks like in a real repository is a diff nobody objects to:

```diff
-    allow=["check_status", "list_regions"],
+    allow=[],  # TODO: re-review after the vendor's v2 release
```

**Line by line:**

- The intent is obvious and good: somebody is being cautious. They have not re-reviewed the tools, so
  they have emptied the list until they can.
- The comment says exactly the right thing, which is why the reviewer approves it.
- The effect is the opposite of the intent. Emptying the list turned the filter off, so the server
  that is pending review is now the only server with no restrictions.
- The fix that expresses the intent is to remove the server from the policy entirely, so that
  constructing its toolset raises. "Do not use this yet" is a different statement from "use all of
  it", and only one of them can be written as a list.

The way to make this loud is one line at the boundary. If the argument is computed, refuse to compute
an empty one:

```python
if not names:
    raise ValueError(f"{server_key}: empty allowlist - remove the server instead")
```

**Line by line:**

- `if not names` deliberately uses the same truthiness test that caused the problem, because here it is
  the right test: `None` and `[]` are both "you have not told me what to allow", and both should stop.
- Raising rather than logging. A log line here is a note in a file nobody opens; an exception at
  startup is a deployment that does not happen.
- The message names the server key and says what to do instead. An error that only says
  "empty allowlist" makes the reader guess which of eleven servers it meant.
- This belongs in `sutra/mcp/filtering.py` and nowhere else, which is the whole argument for a single
  door.

## In production

**What a professional writes instead:** they never pass a list literal to this argument, and they never
let a possibly-empty value reach it. The construction helper takes the names, refuses an empty
collection, converts to `list` explicitly, and asserts afterwards that the number of tools handed back
equals the number of names requested. That last assertion is what catches the neighbouring failure —
an allowlist naming a tool the server renamed, which silently produces a shorter list rather than a
longer one.

**What degrades at scale:** review attention. In a policy file with three servers, an empty `allow` is
visible. In one with thirty, it is one line among hundreds, and the reviewer's eye slides over an
empty list exactly as it slides over an empty string. The mechanism that scales is the one that
refuses at load time; nothing that relies on somebody noticing an empty pair of brackets scales past a
few entries.

**The failure mode that only appears with real traffic:** the fallback path. Configuration loaders
often have a "use defaults" branch for a missing section, and the natural default for a list is an
empty one. So the servers that get the empty allowlist are the ones whose configuration section was
missing — a typo in a key name, a new environment nobody templated — which means this bug arrives with
a deploy to a new region rather than with a code change, and there is nothing in the diff at all.

**The review comment a senior engineer leaves:** *"`allow=[]` does not mean 'nothing allowed', it means
'no filter'. This line grants the model every tool on a server we have specifically flagged as
unreviewed. If the intent is to disable the server, delete the entry and let the lookup raise. And
please add the guard in `filtering.py` so the next person cannot express this at all."*

**The interview question:** *"is there anything surprising about how tool filters behave when
misconfigured?"* The honest spoken answer: *"Yes, and it is the one I check for first on any new
codebase. In ADK the selection rule starts `if not self.tool_filter: return True`, which is a
truthiness test, so an empty list takes the same branch as `None` and admits every tool. We measured
it — same server, same code, `tool_filter=[]` handed the agent a write tool that the two-name
allowlist next to it kept out. It matters because nobody types an empty list, they compute one: a
policy record with no names filled in, or a `.get` with a default. So the server you have not reviewed
yet is the one that ends up unrestricted, which is precisely backwards. Our fix is one guard in the
single module that builds toolsets: an empty allowlist raises with the server's name in the message,
because 'do not use this yet' has to be expressible as something other than an empty list."*
