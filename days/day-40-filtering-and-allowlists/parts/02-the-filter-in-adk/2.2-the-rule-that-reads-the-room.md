# 2.2 — The rule that reads the room

## One-line answer

A `ToolPredicate` is a function ADK calls once per tool per listing, handing it the tool and the
current context, so the answer can depend on who is asking rather than only on what the tool is
called.

## The story

The conductor on the morning bus does not carry a list of passengers.

He carries a rule, and he applies it to each person as they get on. A monthly pass with today's month
on it: fine. A student pass on a Sunday: not fine, because the student concession is weekday-only and
Sunday is printed right there in the rule. Cash: fine, here is your ticket.

The same person can be a yes on Tuesday and a no on Sunday, and the conductor does not need a new
list for each day of the week. The rule reads the pass **and** the day.

This works because the rule is small, and because everyone agrees what it says. The morning it stops
working is the morning a rule gets added that nobody can check from the pass alone — *"students going
to the exam centre travel free"* — and now the conductor is guessing at something he cannot see.

## The idea in plain language

The list form of `tool_filter` answers one question: *is this name on the list?* The callable form
answers a wider one: *given this tool and this moment, should the model be told about it?*

ADK names the shape `ToolPredicate`. It is a `Protocol` — Python's word for "any object with this
method counts", no inheritance required — with a single call signature:

```
__call__(tool: BaseTool, readonly_context: ReadonlyContext | None = None) -> bool
```

Three things about that signature carry the whole idea.

- **It is handed the tool object, not just the name.** So the rule can look at
  `tool.description`, which the list form cannot.
- **It is handed a context.** `ReadonlyContext` is ADK's read-only view of the current invocation,
  including session state. So the rule can look at who is asking.
- **It returns a plain `bool`.** No exceptions, no "maybe", no reasons. Whatever the rule decides, the
  reader of your logs will not learn why unless you log it yourself.

And one thing about *when* it runs: it is called inside `get_tools()`, once per tool, **on every
listing** — including a listing served from the tool-list cache, as
[1.3](../01-the-list-you-agreed-to/1.3-the-filter-is-on-your-side.md) read out of the source. A
predicate is therefore hot code. It runs far more often than a human would guess, and it must be pure
and fast: no database call, no network, no file read.

The honest framing is that a predicate is a **more expressive allowlist, not a different posture**. It
still has to say yes explicitly. A predicate whose last line is `return True` has quietly become a
deny-list, and [1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md)'s whole
argument applies to it unchanged.

## Why Sutra needs it

Because Sutra will eventually have two kinds of caller reaching the same server, and the tool a
support agent may use is not the tool an unauthenticated one may.

That is not a hypothetical for this repository. Day 37 gave `sutra_mcp/auth.py` and `sutra/mcp/auth.py`
their jobs — issuer validation on one side, token handling on the other — which means an invocation
can carry an identity. A predicate is where that identity turns into a smaller tool list. The list
form cannot express it, because a list is fixed at construction and an identity is not known until a
request arrives.

The second reason is narrower and more immediate: a predicate can refuse a tool whose **description**
has changed shape, which no name list can do. That is not a complete answer to
[3.2](../03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md) — a pin comparing
digests is — but it is the mechanism a pin check would be enforced through at listing time.

`sutra/mcp/filtering.py` is going to expose `allowlist` and `deny` as the everyday API. Knowing the
predicate form exists is what stops you from trying to express "reads only, unless the caller is
support" as a list of names in fifteen places.

## The mechanism

`lab/predicate.py` writes the rule as an ordinary function and asks it about the same three tools
under two different contexts.

```python
# lab/predicate.py
READS = frozenset({"check_status", "list_regions"})
WRITES = frozenset({"open_incident"})
LABEL = "may_write"


def allow_reads_and_labelled_writes(
    tool: BaseTool, readonly_context: FakeContext | None = None
) -> bool:
    """The rule. Reads always; writes only for a caller carrying the label."""
    if tool.name in READS:
        return True
    if tool.name in WRITES:
        labels = readonly_context.state["labels"] if readonly_context else frozenset()
        return LABEL in labels
    return False
```

**Line by line:**

- `frozenset` rather than `list` for the two name groups. Membership is the only operation, it is
  constant-time, and a frozen set cannot be appended to by accident from somewhere else in the
  process. These are *inside* the rule, so [2.1](2.1-one-argument-three-spellings.md)'s warning about
  passing a set to `tool_filter` does not apply — nothing here is handed to the framework as a
  container.
- The signature matches the protocol exactly: first positional parameter is the tool, second is the
  context and it has a default of `None`. ADK's `ToolPredicate` is `@runtime_checkable`, which means
  `isinstance` only verifies that the object is callable — it does **not** check parameter names or
  types. A function with the wrong signature passes `isinstance` and then raises `TypeError` at the
  moment the first tool is filtered, which is somewhere deep inside an agent turn.
- `readonly_context: FakeContext | None = None` — the default matters. ADK calls `get_tools()` with
  `readonly_context=None` in several places, including when an agent is being inspected rather than
  run. A predicate that assumes a context exists crashes there.
- `if tool.name in READS: return True` is checked first because it is the common case, and because a
  rule read top-to-bottom should say the permissive thing about the safe things before it gets
  complicated.
- `readonly_context.state["labels"] if readonly_context else frozenset()` — **when there is no context,
  assume no privileges.** This is the fail-safe default from
  [1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md) written as one
  conditional expression. Writing `.get("labels", frozenset())` on the state would be the same idea
  applied to a missing key.
- The final `return False` is the line that makes this an allowlist. A tool whose name is in neither
  group is refused, so a tool the server adds tomorrow is refused without anybody editing this
  function. Change it to `return True` and you have written a deny-list with extra steps.
- **Zero model calls.** A predicate that needed a model to decide would be run once per tool per
  listing, which is a rate limit and a bill and a source of nondeterminism all at once.

**Line by line:**

- The script asks `isinstance(rule, ToolPredicate)` first, so you can see the framework accept a plain
  function with no base class and no decorator. That is what `Protocol` buys.
- Then it applies the same rule under two fake contexts, one carrying the label and one not, and
  prints what each caller would be handed.

Measured on 2026-09-04:

```text
is this a ToolPredicate? True
ordinary caller      -> ['check_status', 'list_regions']
support-desk caller  -> ['check_status', 'list_regions', 'open_incident']

a name the rule has never seen -> False
```

One rule, two answers, and the last line is the one that matters most: a tool called
`delete_everything` that the rule has never heard of is refused even for the privileged caller,
because the function ends in `return False`.

## When it breaks

Get the signature wrong and nothing complains until a tool is filtered. A predicate written as
`def rule(tool):` — one parameter, which reads perfectly well — passes `isinstance` because it is
callable, and then:

```text
TypeError: rule() takes 1 positional argument but 2 were given
```

That exception surfaces inside `get_tools()`, so what the user sees is an agent turn that failed
before it started, and what the traceback points at is framework code. The fix is one parameter, and
the way to never meet it is a test that calls your predicate with two arguments.

The quieter break is the context that is not there:

```text
AttributeError: 'NoneType' object has no attribute 'state'
```

Same shape, same place, and it appears only on the code paths that list tools without a live
invocation. A predicate that is correct in every agent turn and crashes when someone opens the
inspector is a predicate that was written assuming a context.

The break with no message at all is the rule that ends `return True`. Every test passes, every tool
you named works, and the server's next release is admitted without a conversation — which is exactly
[1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md)'s deny-list wearing a
function's clothes.

## In production

**What a professional writes instead:** the predicate is a thin adapter over data. The policy lives in
a structure — names, groups, required labels — and the function does nothing but read it and return a
bool. That way the interesting part is reviewable as a diff and testable without ADK, and the function
itself is four lines that nobody needs to review twice.

**What degrades at scale:** the number of calls. The predicate runs per tool per `get_tools()`, and
`get_tools()` runs per agent turn unless a cache is set. Thirty tools and a busy agent is thousands of
predicate calls a minute. Anything with I/O in it — a database lookup of the caller's roles, a call to
a policy service — turns a filter into a dependency, and now your agent cannot list tools when that
service is slow. Load the policy once at startup; decide in memory.

**The failure mode that only appears with real traffic:** stale state. The predicate reads
`readonly_context.state`, and session state is written by callbacks and tools during a run. A tool
whose availability depends on state that another tool sets means the agent's tool list changes
mid-conversation, which reads to a user as an assistant that "forgot" it could do something. If the
tool list must vary, vary it on identity, which is stable for the session, not on state that moves.

**The review comment a senior engineer leaves:** *"this predicate ends in `return True`. That makes it
a deny-list with a function's syntax, and it will admit whatever the vendor ships next. Invert it and
list the groups you actually want — and add a test that a name nobody has ever seen returns `False`,
because that test is the only thing that will keep it inverted."*

**The interview question:** *"when would you use a callable tool filter rather than a list of names?"*
The honest spoken answer: *"When the answer depends on who is asking. A list is fixed at construction
and an identity is not known until a request arrives, so anything like 'reads for everyone, writes
only for support' has to be the callable form. Two cautions I would raise. It runs once per tool per
listing, which is hot enough that anything doing I/O in there becomes an availability dependency for
listing tools at all — so the policy is loaded once and the function only reads memory. And a
predicate is still an allowlist only if it ends in `return False`; I have seen one end in `return
True`, which quietly turns it back into a deny-list, and the test that catches it is asking it about a
tool name that does not exist."*
