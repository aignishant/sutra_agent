# 4.3 — `deny` inside the allowlist

## One-line answer

`deny` is a second subtraction applied **after** the allowlist has already decided, so it can only ever
make Sutra's tool list smaller — and it exists to hold the names that must stay out even if somebody
adds them to the allowlist by mistake.

## The story

The house help has a key ring with four keys on it: the main door, the kitchen, the back gate and the
terrace.

There is a fifth key in the drawer, for the room where the family keeps documents and the small
almirah. It is not on the ring. It was never on the ring — not because anybody distrusts her, but
because there is no errand in her day that needs that room, and there never will be.

The ring is the allowlist. Four keys, each chosen because a job needs it.

The fifth key being *deliberately absent* is the interesting bit, and it is a different decision from
the other four. The four are "yes, for this reason". The fifth is "no, and if somebody hands you this
key one day, hand it back" — a standing instruction that survives whoever is making up the ring next
month, when the person who knows why is not in the room.

Nothing about the ring stops a new key being added to it. What stops the fifth key is that somebody
wrote down, once, that it is not to go on.

## The idea in plain language

By now [1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md) has argued
that a deny-list is the wrong **posture**, and that argument stands. So why does
`sutra/mcp/filtering.py` have a `deny` at all?

Because posture and refinement are different jobs.

- The **posture** is the default answer for a name nobody discussed. Sutra's is *no*, and that is what
  the allowlist provides.
- A **refinement** narrows an answer that has already been given. It cannot widen anything, because it
  only ever removes names from a set that was already restricted.

Concretely, the order matters and there is only one safe one:

```
offered  →  keep only names in allow  →  remove names in deny  →  hand to tool_filter
```

`deny` applied to `offered` would be a deny-list, and it would carry every problem
[1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md) named. `deny` applied to
the output of `allow` cannot admit anything, ever, no matter what is in it. Same word, opposite
properties, and the difference is one line's position.

What is it for, then, if `allow` could simply not name the tool? Three real uses, and none of them is
"instead of the allowlist":

| Use | Why the allowlist alone is not enough |
| --- | --- |
| A name that must never be allowed on this server | it survives somebody widening `allow` in a hurry, and it is a place to write **why** |
| A tool temporarily withdrawn during an incident | the approval history in `allow` is preserved, so restoring it is deleting one line rather than re-approving |
| A name banned across every server | it can be a module-level constant applied to all records, which `allow` cannot express |

That third row is the one that earns its keep. `execute_sql` is a name Sutra should never take from
anybody — Day 39 made that decision about its own database tools, and it should not have to be
re-made per server. A global `deny` is where a decision like that lives so that it applies to the
server nobody has added yet.

## Why Sutra needs it

Because the day spine gives `sutra/mcp/filtering.py` both `allowlist` and `deny` as public names, and
a reader who meets `deny` without this part will reasonably assume it is the other posture and use it
as one.

There is a Sutra-specific decision behind it too. Day 39 put a real SQLite database behind
`sutra_mcp/db_tools.py` and made the deliberate choice that the agent gets narrow read tools rather
than a general query tool. That choice is worth nothing if a *different* server — the database toolbox,
a partner's server, anything — offers a general query tool that somebody allowlists for a good reason
one afternoon. A global `deny` is how a decision made on Day 39 keeps being true on Day 70.

Day 45's audit should read `deny` as a set of decisions with reasons attached, and should flag a
server whose `allow` and `deny` overlap — because an overlap means two people disagreed and neither
knows it.

## The mechanism

The function, in the order that makes it a refinement:

```python
# sutra/mcp/filtering.py  -- the shape; the build brief asks you to write it
NEVER: tuple[str, ...] = (
    "execute_sql",  # Day 39: the agent gets narrow read tools, not a query language
)


def deny(names: Iterable[str], policy: ServerPolicy) -> list[str]:
    """Remove the names this server, or Sutra as a whole, refuses. Never adds."""
    refused = set(policy.deny) | set(NEVER)
    return [name for name in names if name not in refused]
```

**Line by line:**

- `NEVER` is a module constant, not a field. A per-server field could be forgotten on the next server
  somebody adds; a module constant applies to every record including the ones that do not exist yet,
  which is precisely the property a standing decision needs.
- The comment on `"execute_sql"` names the day the decision was made. A refusal with no reason attached
  is a line somebody will delete in two years while cleaning up, because it looks like a leftover.
- `names: Iterable[str]` — the input is *already-allowed* names, not everything the server offered. The
  type is `Iterable` rather than `list` because this function does not care how it arrives, and the
  parameter name says what it is. Naming it `offered` would invite exactly the misuse this part exists
  to prevent.
- `set(policy.deny) | set(NEVER)` unions the per-server refusals with the global ones. A set because
  the only operation is membership, and building it once outside the comprehension rather than testing
  two tuples per name.
- The comprehension **removes** and never adds. There is no branch in this function that can put a name
  into the output that was not in the input, and that is the property that makes `deny` safe to have in
  a codebase whose posture is allowlist. Read the function looking for a way to widen the result; there
  is not one, and there should never be one.
- The return type is `list[str]`, which is what
  [2.1](../02-the-filter-in-adk/2.1-one-argument-three-spellings.md) established `tool_filter` needs.
  The conversion happens here rather than at the call site so that every caller gets it right by
  default.

How the two compose, with the order visible:

```python
# sutra/mcp/filtering.py
def toolset_for(server_key: str) -> McpToolset:
    """The one door. Every Sutra MCP toolset is built here."""
    policy = REGISTRY[server_key]  # raises on an unknown server
    names = deny(allowlist(server_key), policy)
    ...  # TODO(me): refuse an empty `names`, then construct with tool_filter=names
```

**Line by line:**

- `REGISTRY[server_key]` with no `.get` and no default. A `KeyError` naming the missing key is the
  default-deny of [1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md), and it
  happens at construction rather than at a tool call.
- `deny(allowlist(server_key), policy)` — read the nesting outward. `allowlist` runs first and produces
  the permitted set; `deny` runs on its output. Swapping them would produce a deny-list, and the swap
  would look like a formatting change in a diff.
- The `TODO(me)` is deliberately the interesting half. Refusing an empty `names` is
  [2.4](../02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md)'s guard; deciding what
  else this function asserts — that the tool count matches, that `policy.pinned` is non-empty — is the
  design work the build brief leaves to you.
- **This function makes no model call**, and neither does anything else in this module. The policy layer
  is arithmetic over strings.

The check that an overlap is a disagreement:

```python
overlap = set(policy.allow) & (set(policy.deny) | set(NEVER))
if overlap:
    raise ValueError(f"{server_key}: {sorted(overlap)} is both allowed and refused")
```

**Line by line:**

- `&` is set intersection: the names present in both. An empty intersection is the normal case and
  costs nothing to compute at import.
- Raising rather than resolving. There is a tempting third option — let `deny` win, since it is
  narrower, and carry on — and it is the wrong one. An overlap means one person wrote a name into
  `allow` and another wrote it into `deny`, and silently picking a winner buries a disagreement that
  should be a conversation.
- `sorted(overlap)` so the message is stable and the same overlap always reads the same way in a log.
- The message names the server key. In a registry with thirty entries, "allowed and refused" without a
  key is a message that starts a search.

## When it breaks

The break that matters is the order, and it produces no error at all. Here is the same two functions
composed the other way round:

```python
names = allowlist_over(deny(offered, policy))  # WRONG: deny applied to everything offered
```

**Line by line:**

- `deny(offered, policy)` hands `deny` the server's full offering rather than the allowed subset. The
  function itself is unchanged and still only removes — it has not been broken.
- What has changed is what it is removing *from*. Subtracting a short refusal list from everything the
  server offers leaves everything the server offers minus a few names, which is a deny-list.
- If `allowlist_over` then intersects, the result happens to be correct today and the code is one
  refactor away from not being. If it does not, this line silently became the wrong posture.
- In a code review this is one word moved. `deny(allowlist(...))` and `allowlist(deny(...))` differ by
  the position of a bracket, and a reviewer reading for style will not see it. The defence is a test
  that asserts a name the server offers and the allowlist does not name is absent from the result —
  which fails immediately under the wrong order and cannot be satisfied by any arrangement of a
  deny-list.

The second break is the overlap left unchecked:

```text
ValueError: vendor_status: ['check_status'] is both allowed and refused
```

That message is the good outcome. Without the check, the same state is a tool that somebody approved,
in writing, in the policy file, that never reaches the agent — and the person who approved it debugging
why for an afternoon.

The third break has no output and is a habit rather than a bug. Somebody who has read only this part
and not [1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md) starts putting the
day's real decisions in `deny` because it reads as the security-shaped field. Six months later `allow`
is a broad list nobody curates and `deny` is where all the thinking is, which is a deny-list built out
of an allowlist's parts.

## In production

**What a professional writes instead:** `deny` entries carry a reason and a date in the source, and the
global `NEVER` tuple is reviewed on the same schedule as the servers. A name in `NEVER` is a decision
with a blast radius across the whole system, so it gets the same treatment as any other
system-wide constant: a comment saying why, a link to where the decision was made, and a check that
nothing has quietly stopped applying it.

**What degrades at scale:** `NEVER` becomes a superstition list. Every incident adds a name, nothing
ever removes one, and after two years it holds forty strings whose reasons nobody remembers. The
mitigation is the comment-with-a-date discipline plus a periodic read-through — and an acceptance that
this list is allowed to shrink, which is a cultural rather than a technical property.

**The failure mode that only appears with real traffic:** the name that is banned and the tool that is
not. `NEVER` holds `execute_sql`, and a server offers the same capability as `run_query`. The refusal
is on a string, and capability does not live in strings. This is a real limit and there is no clever
fix for it inside this module — the answer is that `allow` is the control and `deny` is a backstop, and
anybody who inverts that in their head has a system protected by a spelling.

**The review comment a senior engineer leaves:** *"`deny` is doing the real work in this record and
`allow` names eleven tools nobody has read. That is a deny-list assembled out of an allowlist's parts.
Cut `allow` down to what we actually use and let `deny` go back to being three names with reasons
next to them."*

**The interview question:** *"you argued for allowlists. Why does your policy have a deny field?"* The
honest spoken answer: *"Because posture and refinement are different jobs, and the order in the code
is what keeps them apart. The allowlist decides the default for a tool nobody discussed, and `deny`
runs on its output, so `deny` can only ever make the list smaller — it structurally cannot admit
anything. What it buys is three things the allowlist cannot express: a refusal that survives somebody
widening the allowlist in a hurry, a temporary withdrawal that keeps the approval history, and a
name banned across every server including the ones nobody has added yet. We have `execute_sql` in that
last category, from a decision made when we built our own database tools. The failure I watch for is
cultural rather than technical — teams start putting the real thinking in `deny` because it looks like
the security field, and then the allowlist becomes a broad list nobody curates."*
