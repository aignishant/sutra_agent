# 4.1 — One door, and a check that there is one

## One-line answer

Sutra builds every MCP toolset in `sutra/mcp/filtering.py` and nowhere else, and the way that stays
true is a script that reads the source and names any other file that constructs one.

## The story

The shop has one billing counter at the front and everybody knows it.

The owner can tell you the day's takings because everything goes through that machine. Returns go
through it. Discounts go through it. When something does not add up he has one place to look.

Then the salesman at the back starts keeping a small cash box in his drawer. Not to steal — to save
customers the walk when they buy one small thing on their way out. He is helpful, the customers like
it, and for a while nobody notices.

The shop now has two counters. Only one of them is on the paperwork. The owner is not being lied to;
he is answering questions about the shop using a picture of the shop that stopped being complete on a
Tuesday, and every question he answers from now on is slightly wrong in a direction he cannot see.

Nobody would defend the second counter if asked. It was never decided. It grew because it was
convenient and because there was nothing that would have noticed.

## The idea in plain language

A policy is a claim about **all** the places something happens. "Every MCP toolset Sutra builds is
filtered" is that kind of claim, and it is false the moment one file builds a toolset the policy has
never heard of.

The usual answer is discipline: everybody knows to use the helper. Discipline works until the
repository has more than a couple of authors, or until somebody is debugging at speed and constructs a
toolset inline to try something, and the line survives the commit.

The answer that keeps working is smaller and duller. **One module builds toolsets, and a check reads
the source to prove no other module does.** Not a code review convention, not a comment at the top of a
file — a script with an exit code, so that "somebody built a toolset somewhere else" is a red check
rather than a thing you find out about later.

The tool for reading source without running it is the **abstract syntax tree**: Python's own parser,
exposed through the `ast` module, which hands you the structure of a file as objects you can walk. It
is not a text search. `grep McpToolset` matches the word inside a comment, a docstring or a string
literal; the syntax tree tells you specifically that a *call* is being made, which is the thing you
care about.

Sutra has done this before. Day 32's
[1.5 — One gate to guard](../../../day-32-mcp-stateless-core/parts/01-the-socket/1.5-one-gate-to-guard.md)
used the same technique to check that agent-side code does not reach past the MCP boundary — a scan
for imports that should not be there. This part is the same shape pointed at construction rather than
at imports, and for the same reason: **a boundary that nothing enforces is a diagram.**

## Why Sutra needs it

Because [§8.2 of the day spine](../../LESSON.md) gives Sutra exactly one file for this — `sutra/mcp/filtering.py`,
holding `allowlist`, `deny`, and the filter applied at toolset construction — and a single file is only
a single door if nothing else opens one.

The concrete reason it matters here rather than in general is
[2.4](../02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md). The empty-list guard, the
type conversion, the assertion that the number of tools matches the number of names: all of those are
one function's worth of defence, and every one of them is bypassed by a call site that constructs
`McpToolset` directly. The value of the single door is not tidiness. It is that every protection in
this day only exists at that door.

Day 44 adds `sutra/mcp/hardening.py` to the same package, and its retries and timeouts want to be
applied at the same place. Day 45's audit is the phase gate and this check is a natural part of it —
which is why it lives in `lab/` today as something you run by hand, and becomes a line in
`tools/mcp_audit.py` then.

## The mechanism

`lab/one_door.py` parses every Python file under `sutra/`, walks the tree for calls, and reports any
that construct a toolset outside the module allowed to.

```python
# lab/one_door.py
DOOR = pathlib.Path("sutra/mcp/filtering.py")
SCANNED = pathlib.Path("sutra")
BUILDERS = {"McpToolset", "MCPToolset"}


def builds_a_toolset(path: pathlib.Path) -> list[int]:
    """Line numbers where this file calls a toolset constructor."""
    tree = ast.parse(path.read_text(encoding="utf-8"))
    hits = []
    for node in ast.walk(tree):
        if not isinstance(node, ast.Call):
            continue
        target = node.func
        name = getattr(target, "id", None) or getattr(target, "attr", None)
        if name in BUILDERS:
            hits.append(node.lineno)
    return hits
```

**Line by line:**

- `DOOR` is the one file allowed to construct. It is a constant at the top rather than a parameter,
  because a check whose exemption list can be passed in on the command line is a check somebody will
  eventually pass an exemption to.
- `SCANNED = pathlib.Path("sutra")` — the **agent** side only. `sutra_mcp/` is the server side; it does
  not build client toolsets, and scanning it would produce confusing misses rather than useful ones.
- `BUILDERS` holds both spellings. ADK exports the class under two names, `McpToolset` and
  `MCPToolset`, and a check that knows only one of them is a check somebody can walk past by importing
  the other. Verified against `.venv/Lib/site-packages/google/adk/tools/mcp_tool/__init__.py` on
  2026-09-04.
- `ast.parse(...)` builds the tree. It raises `SyntaxError` on a file that does not parse, which is
  correct behaviour — a file Python cannot read is not a file this check can vouch for.
- `ast.walk(tree)` yields every node in the tree in no particular order. That is fine because the check
  is a membership test, not an analysis of control flow.
- `if not isinstance(node, ast.Call): continue` — only calls. A file that imports `McpToolset` without
  calling it, or mentions it in a docstring, is not building one and is not a finding.
- `getattr(target, "id", None) or getattr(target, "attr", None)` handles the two ways a call can be
  spelled. `McpToolset(...)` is an `ast.Name` and has `.id`; `mcp_tool.McpToolset(...)` is an
  `ast.Attribute` and has `.attr`. Checking only one of the two would miss half the real call sites.
- `node.lineno` rather than a boolean, so the report can name the line. A check that says "there is a
  problem in this file" is a check somebody has to go and re-find.
- **This is static analysis, so it is honest about its limits.** A toolset built by
  `getattr(module, "McpToolset")(...)`, or through a factory that takes the class as an argument, is
  invisible to it. That is a real gap and the answer is not more cleverness in this script — it is that
  such code is unusual enough to be caught in review, and a check that catches the ordinary case is
  worth far more than no check at all.

```bash
uv run python days/day-40-filtering-and-allowlists/lab/one_door.py; echo "exit: $?"
```

**Line by line:**

- Run from the repository root: the paths in the script are relative to it, which is deliberate — a
  check that must be run from a particular directory is one that can be run consistently in CI.
- `echo "exit: $?"` because the verdict is the exit code. Non-zero means at least one finding, which is
  what makes this usable as a gate rather than as a report somebody reads.

Measured on 2026-09-04, before `sutra/mcp/filtering.py` exists:

```text
  sutra\mcp\filtering.py does not exist - there is no door yet, only openings
doors other than sutra\mcp\filtering.py: 1
exit: 1
```

**Red, and correctly red.** This is Principle 11 — the eval must be able to fail — and it is failing
for the honest reason: the module the build brief asks you to write has not been written. Write it and
this goes green; add an `McpToolset(...)` anywhere else under `sutra/` and it goes red again with a
file and a line number.

## When it breaks

The check's own failure is a `SyntaxError`, and it is loud:

Reproduced on 2026-09-04 against a copy of the check and a deliberately broken file:

```text
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "<unknown>", line 1
    def build(
             ^
SyntaxError: '(' was never closed
```

`File "<unknown>"` is the giveaway, and it is worth recognising. `ast.parse` was given a string
rather than a path, so it has no filename to report — the file that failed is whichever one the loop
was on, and the check does not say which.

The traceback points at the *check*, and the fault is in the file being checked. That is worth knowing
before it happens at half past six on a Friday: the fix is in `sutra/`, not in `one_door.py`. A
production version catches `SyntaxError` per file and reports it as a finding with the filename, so one
unparseable file does not stop the other forty being checked.

The break that matters more is the one the check cannot see. Here is a call site it will not report:

```python
BUILD = McpToolset
toolset = BUILD(connection_params=params)
```

**Line by line:**

- `BUILD = McpToolset` binds the class to another name. The assignment is not a call, so it is skipped.
- `BUILD(connection_params=params)` **is** a call, but `node.func.id` is `"BUILD"`, which is not in
  `BUILDERS`, so it is not a finding.
- Nobody writes this on purpose to evade a check. It appears in test helpers and in factories, and the
  honest response is to say so in the check's docstring rather than to pretend the check is complete.
  A control with a documented gap is a control; a control whose gaps are unknown is a belief.

The third break has no output at all: the check exists, it is green, and nobody runs it. That is why
Day 45 puts its successor into `./m check` rather than leaving it as a script in a lab folder.

## In production

**What a professional writes instead:** the same walk, plus two more findings. First, a call to the
constructor inside the door module that does **not** pass `tool_filter` — the door being open is worse
than a second door. Second, a `tool_filter=` whose value is a literal empty list, which is
[2.4](../02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md) caught at parse time. Both
are a few lines on top of the same tree walk, and both catch a real mistake that review misses.

**What degrades at scale:** the exemption list. The first time somebody has a legitimate reason to build
a toolset elsewhere — a test fixture, a one-off script — the pressure is to add a path to an `ALLOWED`
set in the check. Do that twice and the check is describing the codebase rather than constraining it.
The version that survives puts test code outside the scanned tree entirely, so the question never
arises, and treats any request to add an exemption to production code as a design conversation.

**The failure mode that only appears with real traffic:** the door that is bypassed by configuration
rather than by code. Every call site goes through `filtering.py`, the check is green, and the policy
data itself has an entry with an empty allowlist or a name nobody reviewed. Static analysis proves the
shape of the code and says nothing about the values flowing through it, which is why
[4.2](4.2-a-policy-you-can-diff.md) makes the data reviewable and Day 45 audits the data separately.

**The review comment a senior engineer leaves:** *"this is the third file that builds its own
`McpToolset`. Each one is reasonable on its own and together they mean we cannot answer 'which servers
can this agent reach' without reading the whole repository. Route them through `filtering.py` and add
the AST check to the gate, so the fourth one is a red build instead of a conversation."*

**The interview question:** *"how do you stop a security control from being bypassed by the next person
who joins?"* The honest spoken answer: *"Make the bypass detectable rather than relying on everyone
remembering. For our MCP toolsets there is exactly one module that constructs them, because that is
where the allowlist, the empty-list guard and the tool-count assertion live — and every one of those
protections is skipped by a direct constructor call. So there is a check that parses the agent-side
package with `ast`, finds calls to either exported spelling of the class, and fails with a file and
line number for any outside that module. I would be upfront about the limits: it is static, so a class
bound to another name or reached through a factory slips past, and it says nothing about the values in
the policy. It catches the ordinary case, which is somebody constructing one inline while debugging and
leaving it in, and that is the case that actually happens."*
