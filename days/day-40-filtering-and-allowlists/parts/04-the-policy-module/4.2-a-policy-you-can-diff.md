# 4.2 — A policy you can diff

## One-line answer

The allowlist is one field of a record — how the server is reached, which names are allowed, what
their descriptions hashed to, who reviewed them and when — and the record exists so that approving a
server is a commit somebody can read rather than a conversation nobody can find.

## The story

The flat comes with a warranty card for the water heater, and somebody fills it in at the shop.

Date of purchase, model number, dealer's stamp. It goes in a folder and nothing happens to it for two
years. Then the heater starts tripping the fuse, and the question that decides who pays is not what
anybody remembers — it is whether the card says the installation was done by an authorised fitter, and
what date is on it.

The family that filled the card in has a two-minute conversation with the service centre. The family
that meant to fill it in has a long one, and loses, because "we definitely bought it around then" is
not a thing anybody can act on.

Nothing about the card made the heater safer. What it did was make one specific question answerable
later, cheaply, by somebody who was not there at the time.

## The idea in plain language

An allowlist on its own answers one question: *may this tool through?*

The questions people actually ask about a running system are different, and none of them can be
answered from a list of strings:

- Which servers can this agent reach at all?
- Who approved this one, and when?
- Is the text being served today the text that was approved?
- Which of these tools change the world, and which only read it?
- When was this last looked at?

So the policy is a **record per server**, and the allowlist is one of its fields. That is not
bureaucracy for its own sake. Every one of those questions turns into a field, and every field turns
into a check that Day 45's audit can run without a human.

The word for this is **provenance**, and Sutra has a working example of it already. Day 29's
[4.1 — No row, no run](../../../day-29-sourcing-and-auditing-skills/parts/04-provenance/4.1-no-row-no-run.md)
established the rule for skills: a skill with no row in `docs/SKILL_PROVENANCE.md` does not get
loaded. The same rule, pointed at servers: **no record, no connection.** A server that is not in the
policy cannot be reached, and the way that is enforced is that the lookup raises rather than returning
a default.

## Why Sutra needs it

Because Day 45 is a phase gate that audits every server Sutra talks to, and an audit is a walk over
records.

`sutra/mcp/filtering.py` is where the record lives. The build brief asks you to write `allowlist` and
`deny` and to apply the filter at construction; this part is about the shape of the thing those
functions read. Getting that shape right today is what makes Day 45 a script rather than an
archaeology exercise.

Two later days lean on specific fields. Day 44's `sutra/mcp/hardening.py` needs the connection
details and a per-server timeout policy, so the record has to carry how the server is reached and not
only what it may offer. And [3.2](../03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)'s
pin check needs somewhere to keep the digests it compares — which is this record, because a digest
stored away from the names it belongs to is a file nobody keeps in step.

## The mechanism

The record is a frozen dataclass. Here is the shape, and every field is here because a question above
needs it:

```python
# sutra/mcp/filtering.py  -- the shape; the build brief asks you to write it
@dataclass(frozen=True)
class ServerPolicy:
    """One reviewed MCP server, and everything Sutra is allowed to take from it."""

    launch: StdioServerParameters
    allow: tuple[str, ...]
    deny: tuple[str, ...] = ()
    writes: tuple[str, ...] = ()
    pinned: Mapping[str, str] = field(default_factory=dict)
    reviewed_on: str = ""
    ttl_seconds: float | None = None
```

**Line by line:**

- `@dataclass(frozen=True)` makes instances immutable. A policy object that can be mutated at runtime
  is a policy that can be widened by a bug three modules away, and the traceback would point at the
  place that used it rather than the place that changed it.
- `launch: StdioServerParameters` is how the server is reached. It is in the record rather than in the
  call site because "which servers can this agent reach" has to be answerable by reading one file.
  A server reachable over HTTP would carry `StreamableHTTPConnectionParams` instead; the field is the
  connection, not the transport.
- `allow: tuple[str, ...]` — a tuple, because the record is frozen and a `list` inside a frozen
  dataclass is still mutable. **It is converted to a `list` at the moment it is handed to
  `tool_filter`**, because [2.1](../02-the-filter-in-adk/2.1-one-argument-three-spellings.md) showed
  that a tuple falls off the end of ADK's selection rule and admits nothing. That conversion is one of
  the reasons the module exists.
- `allow` has **no default**. Every other field has one. That asymmetry is deliberate: a record can be
  written without a review date and be merely incomplete, but a record written without an allowlist
  would be a server with no policy, and the dataclass refuses to construct it.
- `deny: tuple[str, ...] = ()` is [4.3](4.3-deny-inside-the-allowlist.md)'s subject — a second, narrower
  subtraction applied inside the allowlist, never instead of it.
- `writes: tuple[str, ...]` names the tools that change something. It is not enforcement; it is
  classification, and it is what lets a check say "a description was rewritten on a tool that writes"
  with a different severity from the same event on a read-only tool.
- `pinned: Mapping[str, str]` is [3.2](../03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)'s
  digests: tool name to a hash of the description and schema that a human read. `Mapping` rather than
  `dict` in the annotation because the field is read, never written, and the annotation should say so.
- `field(default_factory=dict)` rather than `= {}`. A mutable default on a dataclass is shared by every
  instance, which here would mean every server sharing one pin table — a bug that looks like the pin
  check going mad rather than like a default argument.
- `reviewed_on: str = ""` is a date. Empty means nobody has reviewed this, and an empty string is
  falsy, which makes the check a plain `if not policy.reviewed_on`.
- `ttl_seconds: float | None = None` is [3.3](../03-when-the-server-changes/3.3-the-list-you-kept-is-the-list-you-trust.md)'s
  dial, per server, defaulting to ADK's own default of no caching. Note the type: `None` means no
  cache, and `0` is a `ValueError` from the constructor, so this field must never be spelled `0`.

The registry, and the lookup that refuses:

```python
# sutra/mcp/filtering.py
REGISTRY: dict[str, ServerPolicy] = {
    # TODO(me): one entry per server Sutra may reach. Start with the vendor
    # status prop from Day 40's lab so the shape is exercised, then decide
    # whether sutra_mcp itself belongs here - and write down the reason.
}


def allowlist(server_key: str) -> list[str]:
    """The tool names Sutra may take from this server. Raises if unknown."""
    ...  # TODO(me)
```

**Line by line:**

- `REGISTRY` is a plain dict from a short key to a record. The key is what call sites pass, so it is
  short and readable — `"vendor_status"`, not a URL.
- It is **left empty on purpose.** Filling it in is the day's exercise, and the comment says which
  decision has to be made rather than making it: whether Sutra's own server goes in the same registry
  as a third party's is a real design question with arguments both ways, and it belongs to whoever is
  building the desk.
- `allowlist(server_key) -> list[str]` returns a `list`, converting from the record's tuple, so the
  value that reaches `tool_filter` is the type the framework's third branch tests for.
- **Raises on an unknown key.** That is the default-deny of
  [1.1](../01-the-list-you-agreed-to/1.1-the-list-of-things-you-thought-of.md) expressed in code: a
  server nobody wrote a record for is not reachable, and forgetting to add one is a loud failure at
  startup rather than a silent connection.
- The body is `TODO(me)`. What it has to do is stated in this part and in
  [2.4](../02-the-filter-in-adk/2.4-the-empty-list-that-admits-everything.md): look the key up, refuse
  an empty allowlist with a message naming the server, subtract `deny`, and return a `list`.

Why a Python module rather than a YAML file, since a policy is data? Two reasons, and the second is
the one that decides it. A Python file can hold the `StdioServerParameters` object directly instead of
a string that has to be parsed into one. And a YAML value that should be a list is a string when
somebody forgets a dash, which is
[2.1](../02-the-filter-in-adk/2.1-one-argument-three-spellings.md)'s silent-disable bug arriving through
the configuration loader. The moment the policy has to be edited by people who do not deploy this
repository, that trade flips — and then the loader owes you the type checks the dataclass was giving
you for free.

## When it breaks

The dataclass catches the missing allowlist at construction:

```text
TypeError: ServerPolicy.__init__() missing 1 required positional argument: 'allow'
```

That is the good case. It happens at import, before any agent runs, and it names the field.

The break with no message is the record that is complete and stale:

```python
"vendor_status": ServerPolicy(
    launch=VENDOR,
    allow=("check_status", "list_regions"),
    reviewed_on="2026-04-11",
    pinned={"check_status": "50e9430b", "list_regions": "c23d3b97"},
),
```

**Line by line:**

- Every field is filled in. Nothing is empty, nothing is defaulted, and a reviewer scanning the file
  sees a well-maintained entry.
- `reviewed_on="2026-04-11"` is months old. There is nothing in this record, and nothing in Python,
  that will ever notice.
- The `pinned` digests are the real defence and they still work — a rewritten description still fails
  the comparison. But the pin was taken against a review that is now old, so what it is enforcing is
  "unchanged since April", not "still appropriate".
- The fix is not in the record. It is a check that reads `reviewed_on`, subtracts it from today, and
  fails past some age you have agreed on. Which is to say: the field is worth nothing until something
  reads it, and adding a field nobody reads is how policy files become decoration.

The third break is the one that makes the whole record pointless — `REGISTRY` gains an entry during an
incident, at speed, to unblock somebody, with `reviewed_on` copied from the row above. There is no
technical defence against that and it would be dishonest to invent one. What there is, is a check that
`pinned` is non-empty for every entry, so a record added without a listing having been taken is at
least visibly different from one that was reviewed.

## In production

**What a professional writes instead:** the record carries an owner as well as a date — a team, never a
person — and the check that reads `reviewed_on` opens a ticket against that owner rather than failing a
build, because failing a build for a stale review teaches people to backdate the field. The registry
itself is generated into a report at deploy time: one row per server, the tools allowed, the write
tools among them, and the review age. That report is the answer to "what can this agent reach", and it
is worth more than the policy file to everyone except the people editing it.

**What degrades at scale:** the pin table's size and the temptation to make it optional. Thirty servers
with twenty tools each is six hundred digests living in a Python file, at which point somebody moves
them into a generated JSON artefact next to the module. That is fine and is the right move — as long as
the artefact is committed and regenerated by a human action, because
[3.2](../03-when-the-server-changes/3.2-the-name-held-the-sentence-moved.md)'s third failure is a pin
that regenerates itself.

**The failure mode that only appears with real traffic:** the record that is right and the environment
that is not. `launch` names a command and arguments; production runs a different version of that
command, or reaches a different host behind the same name. Everything in the policy is accurate about a
server that is not the one being talked to. The countermeasure is to pin something the server says
about itself — its `serverInfo` name and version — alongside the tool digests, and to check that too.

**The review comment a senior engineer leaves:** *"this entry has an allowlist and nothing else. Add
the review date and the pins, or delete the entry — an allowlist with no provenance tells us what we
permit and not why, and in six months nobody will know whether these two names were chosen or
inherited."*

**The interview question:** *"what does your MCP server policy actually contain?"* The honest spoken
answer: *"One record per server, and the allowlist is one field of it. The others exist because of
questions we could not answer without them: how the server is reached, which of its tools write rather
than read, digests of the descriptions and schemas we approved, who reviewed it and when, and the
list-cache TTL for that server. The record is frozen and the lookup raises on an unknown key, so a
server nobody wrote a record for cannot be connected to — that is the same rule we use for skills,
where no provenance row means the skill does not load. The honest weakness is the review date: nothing
technical stops it from being stale or copied, so we treat it as an input to a report with an owner
rather than as a gate, because a gate on that field just teaches people to backdate it."*
