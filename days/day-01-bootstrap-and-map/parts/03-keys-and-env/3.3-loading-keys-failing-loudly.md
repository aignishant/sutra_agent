# 3.3 — Loading keys, and failing loudly

## One-line answer

Configuration should be **read and checked once, at start-up, by code that refuses to continue when
something is missing** — because a program that starts happily and fails forty minutes later has
converted a one-line configuration error into an incident.

---

## The story

A nightly job runs at two in the morning. Its work takes about twenty minutes: pull the day's
records, process them, generate a report, and send it.

One night somebody rotates a credential and updates it in three of the four places it lives. The
fourth is the nightly job's configuration.

At 02:00 the job starts. It pulls the records — that part uses a different credential, and it works.
It processes them, which takes eighteen minutes and is the expensive bit. It generates the report.

At 02:19 it reaches the send step, reads the credential it needs, finds nothing there, and crashes.

Nobody is awake. The alert goes to a channel nobody watches overnight. In the morning the report is
missing, and eighteen minutes of processing has to be redone — but the real cost is not the compute.
It is that somebody spends the first hour of their day working out **why**, because the traceback
points at the send step, and the send step is not where the problem is. The problem was set eight
hours earlier and eighteen minutes of successful-looking work sat between the cause and the symptom.

Had the job read its configuration at 02:00 and refused to start, the failure would have been
instant, unambiguous, and free.

---

## The idea in plain language

There are two ways a program can meet its configuration, and the difference decides how expensive a
mistake is.

**Lazily** — read each value at the moment it is needed. This is what `os.environ["X"]` scattered
through a codebase does. It is easy to write and it means a missing value surfaces *wherever* it
happened to be needed first, which may be deep in a call stack, hours in, on a path that only runs
sometimes.

**Eagerly** — read and validate everything at start-up, before doing any work. A missing value stops
the program immediately, at a moment when nothing has been half-done and the error can say exactly
what is wrong.

**The second is called fail-fast**, and it is the same instinct as `set -euo pipefail` from Day 0
([3.1](../../../day-00-toolchain-skeleton-driver/parts/03-the-m-driver/3.1-set-euo-pipefail.md)): stop at the first sign of trouble rather
than carrying on into a half-valid state. It is also the plan's Principle 10 — *fail honestly;
errors surface, escalate, and are logged* — applied to start-up rather than to agents.

### The three jobs of a config module

Sutra's `sutra/config.py` does exactly three things, and keeping them to three is the point:

1. **Load** — copy `.env` into `os.environ`, *without overwriting* anything already there
   ([3.2](3.2-env-and-the-environment-as-interface.md)'s precedence rule).
2. **Require** — fetch a variable and raise a clear error if it is absent or empty.
3. **Never print a value** — not in a log, not in a traceback, not in a debug helper.

That third one deserves its own sentence, because it is the rule people break while trying to be
helpful. A key that reaches a log file has leaked: log files are copied, shipped to aggregators,
searched, screenshotted and pasted into tickets. **The safe things to report are whether a value is
present and how long it is** — enough to diagnose, useless to an attacker.

### Why not just use a library?

There is a well-known package for reading `.env` files. Sutra hand-rolls it instead, on Day 1, for a
reason the plan states as Principle 4: **build first, compare after.** Hand-roll the mechanism once
so the library is a convenience rather than a mystery.

It is about fifteen lines. Writing them means you will never again be confused about what a `.env`
loader does, what it does *not* do, or why a `$` in your key vanished
([3.2](3.2-env-and-the-environment-as-interface.md)). And it keeps Day 1 at **zero new
dependencies** — packages arrive on the day they are first genuinely needed (Principle 7).

> 💡 **The mental model:** a config module is a **bouncer at the door**, not a shop assistant you
> ask for things as you go. Everyone is checked on the way in, and if someone is missing their
> ticket the queue stops there — not halfway through the venue.

## The mechanism

Create `sutra/config.py`. This is Sutra's **first line of product code** — everything before it was
tooling and documents.

```python
"""Environment loading for Sutra.

Configuration reaches this program through the environment, never through a committed file
(Day 1, part 3.2). `.env` is a laptop convenience that populates the environment; in a
container the platform does it and nothing here reads a file at all.

Stdlib only, by design: hand-roll the mechanism once, then the library is a convenience
rather than a mystery (Principle 4).

Usage:
    from sutra.config import load_env, require

    load_env()                       # laptop: copy .env into os.environ
    key = require("GOOGLE_API_KEY")  # raises ConfigError if absent or empty
"""

from __future__ import annotations

import os
from pathlib import Path

ROOT = Path(__file__).resolve().parents[1]


class ConfigError(RuntimeError):
    """A required configuration value is missing or empty.

    Its own type so callers can catch exactly this, rather than every RuntimeError.
    """


def load_env(path: Path | None = None) -> None:
    """Copy KEY=value lines from .env into os.environ, without overwriting.

    Real environment variables always win: in CI and in production the platform sets them,
    and a stray .env must never override the platform.

    Args:
        path: an alternative .env location. Tests pass one; nothing else should.

    Example:
        >>> load_env()
        >>> "GOOGLE_API_KEY" in os.environ
        True
    """
    env_file = path if path is not None else ROOT / ".env"
    if not env_file.exists():
        return  # no .env is normal in production - the platform already set the environment

    for raw in env_file.read_text(encoding="utf-8").splitlines():
        line = raw.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        key, _, value = line.partition("=")
        os.environ.setdefault(key.strip(), value.strip())


def require(name: str) -> str:
    """Return an environment variable, or raise ConfigError naming it.

    Example:
        >>> require("PATH")            # doctest: +ELLIPSIS
        '...'
        >>> require("NOPE_NOT_SET")
        Traceback (most recent call last):
        sutra.config.ConfigError: NOPE_NOT_SET is not set. Add it to .env (see .env.example).
    """
    value = os.environ.get(name, "").strip()
    if not value:
        raise ConfigError(f"{name} is not set. Add it to .env (see .env.example).")
    return value


def describe(name: str) -> str:
    """Report a variable's presence and length. NEVER its value.

    Example:
        >>> describe("NOPE_NOT_SET")
        'NOPE_NOT_SET: MISSING'
    """
    value = os.environ.get(name, "")
    return f"{name}: set ({len(value)} chars)" if value else f"{name}: MISSING"
```

**Line by line:**

- The module docstring says **where configuration comes from and why**, not what the functions are
  called. A docstring that restates the signature is noise; one that states the design decision is
  the thing a reader needs.
- `from __future__ import annotations` — lets annotations like `Path | None` be evaluated lazily.
  House style, and it keeps type hints cheap.
- `ROOT = Path(__file__).resolve().parents[1]` — `__file__` is this module's path; `.resolve()`
  makes it absolute and follows symlinks; `.parents[1]` goes up two levels (`sutra/config.py` →
  `sutra/` → repo root). **Computing the root from the module's own location means the program works
  regardless of the directory you launched it from** — which matters the first time something runs
  from a scheduler.
- `class ConfigError(RuntimeError)` — a specific exception type. Principle 10 and house style: raise
  specific errors, never a bare `Exception`. A caller can catch `ConfigError` without also catching
  every other runtime failure, which is the whole point of having types.
- The class body is only a docstring — no `pass` needed, since a docstring is a valid body.
- `if not env_file.exists(): return` — **a missing `.env` is not an error.** In production there is
  no file and the platform has already populated the environment. Raising here would break exactly
  the deployment this design exists to support.
- `for raw in ... .splitlines()` — read the whole file and iterate lines. Configuration files are
  small; streaming would be premature.
- `if not line or line.startswith("#") or "=" not in line: continue` — skip blanks, comments and
  anything that is not an assignment. Being permissive here is right: a malformed line should not
  stop the program from starting.
- `key, _, value = line.partition("=")` — `partition` splits on the **first** occurrence only and
  always returns three parts. `line.split("=")` would break a value containing `=`, which is common
  in base64-ish tokens. The `_` discards the separator.
- **`os.environ.setdefault(...)`** — the most important line in the file. `setdefault` writes **only
  if the key is absent**, so a real environment variable always wins over `.env`
  ([3.2](3.2-env-and-the-environment-as-interface.md)). Using `os.environ[key] = value` here would
  let a stray `.env` copied into a container override the platform's injected secrets — the same
  fifteen lines, one word different, and a production hazard instead of a laptop convenience.
- `value = os.environ.get(name, "").strip()` — `.get` with a default avoids a `KeyError`, and
  `.strip()` means a variable set to whitespace is treated as unset. **An empty string is a missing
  value**, and a key with a trailing newline is a 400 you will otherwise spend twenty minutes on.
- `raise ConfigError(f"{name} is not set. Add it to .env (see .env.example).")` — the error names
  **the variable, the file, and where to find the list of names**. A good error tells you what to do
  next; `KeyError: 'GOOGLE_API_KEY'` tells you only what happened.
- `describe()` returns **presence and length, never the value.** This is the function you reach for
  when debugging, and it exists so that the tempting `print(os.environ["GOOGLE_API_KEY"])` never
  gets written. Making the safe thing the convenient thing is how a rule survives a bad evening.

**Try it:**

```bash
uv run python -c "
from sutra.config import load_env, require, describe
load_env()
for name in ('GOOGLE_API_KEY', 'GROQ_API_KEY', 'OPENROUTER_API_KEY'):
    print(describe(name))
print('vertex:', require('GOOGLE_GENAI_USE_VERTEXAI'))
"
```

**Line by line:**

- `uv run python -c "..."` — run in the project environment, no activation (Day 0,
  [2.5](../../../day-00-toolchain-skeleton-driver/parts/02-repo-skeleton/2.5-the-venv-you-never-activate.md)).
- `load_env()` first — nothing works before the environment is populated.
- `describe(name)` for each key: three lines of `set (N chars)`. **You never see a key.** If one says
  `MISSING`, that is today's bug and not tomorrow's.
- `require('GOOGLE_GENAI_USE_VERTEXAI')` — printed in full because it is a switch, not a secret, and
  it must read `FALSE` or you are pointed at paid Vertex AI (Addendum 02 §2).

## When it breaks

**The failure this module exists to produce**, and it is a good one:

```text
Traceback (most recent call last):
  File "<string>", line 3, in <module>
  File "C:\...\sutra\config.py", line 61, in require
    raise ConfigError(f"{name} is not set. Add it to .env (see .env.example).")
sutra.config.ConfigError: GROQ_API_KEY is not set. Add it to .env (see .env.example).
```

**Read what that error gives you.** The variable name, the file to edit, and where the list of names
lives. Compare with what a lazy read produces from deep inside a call stack eighteen minutes into a
run:

```text
KeyError: 'GROQ_API_KEY'
```

Same underlying problem, and one of the two tells you what to do. **The difference is entirely in
the error message and the moment it fires.**

**The `.env` that was never loaded:**

```text
>>> require("GOOGLE_API_KEY")
sutra.config.ConfigError: GOOGLE_API_KEY is not set. Add it to .env (see .env.example).
>>> # ...but the key IS in .env
```

`load_env()` was not called. **A file is not an environment**
([3.2](3.2-env-and-the-environment-as-interface.md)), and this module does nothing on import — by
design, because Day 0's rule is that no module does work at import time
([2.1](../../../day-00-toolchain-skeleton-driver/parts/02-repo-skeleton/2.1-the-folder-skeleton.md)). Loading must be an explicit call at
start-up, which is also what makes it testable.

**The stale value that will not update:**

```text
$ grep GROQ .env
GROQ_API_KEY=gsk_NEWKEY...
$ uv run python -c "from sutra.config import load_env,describe; load_env(); print(describe('GROQ_API_KEY'))"
GROQ_API_KEY: set (56 chars)     # ...but it is the OLD key
```

`setdefault` refused to overwrite a real environment variable that was already set — probably by a
`. ./.env` earlier in this shell ([3.2](3.2-env-and-the-environment-as-interface.md)). **This is the
precedence rule working correctly**, and it is exactly what protects a container from a stray file.
Locally: open a fresh shell, or `unset GROQ_API_KEY` first.

**The key with a trailing newline**, which produces the worst error of the four because it points
somewhere else entirely:

```text
{"error": {"code": 400, "message": "API key not valid. Please pass a valid API key.",
 "status": "INVALID_ARGUMENT"}}
```

The variable is set, `describe()` says `set (41 chars)` when the key is 40, and the provider rejects
it. `.strip()` in both `load_env` and `require` is what prevents this — **and the length is how you
see it**, which is the second reason `describe` reports one.

## In production

**Fail-fast at start-up is the standard, and the reason is blast radius over time.** A process that
validates its configuration and refuses to start fails at deploy time, in front of whoever is
deploying, with nothing half-done. A process that reads lazily fails at request time, in front of a
user, possibly hours later, on the one code path that touches the missing variable. **Orchestrators
are built around the first behaviour**: a container that exits immediately is caught by a readiness
probe and never receives traffic, and a rollout that cannot start is a rollout that automatically
stops.

**The professional version is a typed settings object, validated once.** Rather than `require()`
calls scattered through the codebase, real services define a settings class listing every variable
with its type and whether it is required, instantiate it at start-up, and pass it down. That gives
one place to look for "what does this service read", type errors instead of string errors, and a
single failure point. Sutra hand-rolls the two-function version first because Principle 4 says build
before adopting — and because at four variables, a settings framework would be a dependency for
something ten lines already do.

**Never log a secret, and design so it cannot happen by accident.** The `describe()` function exists
because the alternative — reaching for `print(os.environ[...])` at eleven at night — is what
actually happens under pressure. Production systems go further: secret values wrapped in a type
whose `__repr__` returns `***`, so that even an accidental interpolation into a log line or a
traceback is safe. **The general principle is to make the unsafe thing hard rather than forbidden**,
because forbidden things happen anyway.

**What degrades at scale.** Four variables read at start-up is trivial. Forty across six services
becomes a question of *which service reads what*, and the answers people reach for are generating a
document of every variable a service requires, failing the build when a variable is read but not
documented, and treating a configuration change as a deploy rather than an edit. **An environment
variable changed by hand on one instance is drift that nothing will ever tell you about** — which is
the same reasoning as the lockfile on Day 0
([2.4](../../../day-00-toolchain-skeleton-driver/parts/02-repo-skeleton/2.4-pyproject-and-the-lockfile.md)).

**The failure that only shows in production.** Locally, `.env` is always there, so `load_env()`
always finds it and `require()` always succeeds. In a container there is no file, and everything
depends on the platform having injected the variables — which is a completely different code path
that your laptop never exercises. **The mitigation is to test the production path**: run once with
`.env` renamed and the variables exported, and confirm the program is identical. Day 86 does this
for real.

**The review comment a senior engineer leaves.** On a pull request with `os.environ["API_KEY"]` in
the middle of a request handler: *"Read this at start-up through the config module — right now a
missing key gives us a 500 on a user's request instead of a container that refuses to start, and the
`KeyError` won't tell whoever is on call which variable or where to set it."* The point is not
style: **it is moving the failure from the user's request to the deploy**, which is the cheapest
place a configuration error can happen.

**The interview question.** *"How does your service handle a missing configuration value?"* The
answer that lands says **fail at start-up, not at first use**, and then explains why — the failure
lands on the deployer rather than on a user, nothing is half-done, and the orchestrator's readiness
probe turns it into a stopped rollout instead of an incident. Adding that error messages should name
the variable and where to set it, and that values are never logged (only presence and length), shows
you have been the person reading the log at two in the morning.

from sutra.config import load_env, require, describe, ConfigError
load_env()
for n in ('GOOGLE_API_KEY','GROQ_API_KEY','OPENROUTER_API_KEY'):

Three `set (N chars)` lines, then `PASS refused:` with a message naming the variable **and** the
file. If any line prints an actual key, `describe()` is wrong — fix it before you use it anywhere
else.
