# 1.2 — What may live in state

## One-line answer

State holds **small serializable values** — strings, numbers, booleans and simple lists or
dictionaries of those — and nothing enforces it today, so the object you put in works perfectly until
the day the session has to be written to a database.

## The story

The left-luggage lockers at the station.

There is a row of them, three sizes, and a laminated card explaining what they are for: bags, cases,
a coat. Not bicycles. Not anything alive. Not anything that leaks.

The rules are not there to be unkind. They are there because the lockers get emptied into a van at
night, and the van has assumptions: a thing that fits a locker fits the van, and a thing that fits the
van gets to the depot. Put something in that does not fit those assumptions and nothing happens at
first. The door closes. The light goes green. Your ticket prints.

The trouble starts later, somewhere you are not standing, when the thing that was never supposed to be
in there meets the machinery that assumed it was not.

## The idea in plain language

The rule for state, from `adk.dev/sessions/state/` read on 2026-09-03: values must be
**serializable** — strings, numbers, booleans, and simple lists or dictionaries containing only those.
The page is explicit about what to avoid: complex objects, functions, connections.

The reason is the van. Today Sutra runs on `InMemorySessionService`, which keeps everything in a
Python dictionary in this process, so *anything* fits: a database connection, an open file, a custom
class. From Day 47, Sutra runs on a `DatabaseSessionService`, which has to turn the session into rows
and JSON — and at that moment every value has to be something JSON can express.

Three consequences, and the third is the one that costs people a day:

- **Small.** State travels with the session. Every read of the session reads all of it, and with a
  persistent service every write writes it. A key holding a 40-kilobyte blob is 40 kilobytes moved
  every turn, forever, for a fact you needed once. That is what
  [2.4](../02-four-lifetimes/2.4-why-temp-exists.md)'s `temp:` prefix is for.
- **Serializable.** Not "serializable if we are careful". A `datetime` is not JSON; an enum is not
  JSON; a pydantic model is not JSON until you call `model_dump()`. Store the string, store the
  number, and reconstruct on the way out.
- **Not secret.** State is persisted, logged, and in Phase 8 passed between nodes. Keys and tokens live
  in the environment ([Day 1](../../../day-01-bootstrap-and-map/LESSON.md)), never here. This is
  Principle 9 applied to a store that did not exist when Principle 9 was written.

And the fact that makes all three worth stating explicitly: **nothing checks any of this today.**
Assign an arbitrary object to a state key and it is accepted, silently, and works for as long as
nothing tries to persist it.

## Why Sutra needs it

Because Phase 3's gate is *"state survives restarts"*, and the restart is where the bill for this
arrives.

The sequence is always the same. Development happens on the in-memory service, where every value is
allowed. Persistence is added later — Day 47 for Sutra — and at that point every key that was quietly
holding something unserializable becomes an error in a code path nobody changed. It is a bad day,
because the failure is far from the write and the traceback points at the storage layer rather than at
the tool that made the mistake.

There is a nearer reason on Day 18: artifacts. Tomorrow's subject is files that survive turns — a
screenshot, a log a customer attached, a generated report. The line between the two stores is exactly
this part's rule: **small structured facts go in state, bytes go in artifacts.** Knowing where the
line is stops the classic mistake of base64-encoding a file into a state key.

## The mechanism

Two things to watch: what state accepts, and what happens when the same values meet JSON.

```python
# days/day-17-state-scopes-and-lifetimes/lab/what_fits.py
"""What state accepts, and what survives being written down. Zero model calls."""

import json
from datetime import datetime

from google.adk.sessions.state import State


class Ticket:
    """A perfectly ordinary object, of the kind nobody should put in state."""

    def __init__(self, number: int) -> None:
        self.number = number


state = State(value={}, delta={})

candidates = {
    "severity": "high",
    "ticket_id": 4521,
    "escalated": False,
    "tags": ["auth", "eu"],
    "counts": {"open": 3, "closed": 1},
    "opened_at": datetime(2026, 9, 3, 9, 12),
    "ticket": Ticket(4521),
}

for key, value in candidates.items():
    state[key] = value
    print(f"accepted by state: {key:12} {type(value).__name__}")

print()
for key in candidates:
    try:
        json.dumps({key: state[key]})
        print(f"survives JSON    : {key:12} yes")
    except TypeError as error:
        print(f"survives JSON    : {key:12} NO  - {error}")
```

**Line by line:**

- `State(value={}, delta={})` — the state object built directly, without a session, because the
  subject here is what the container accepts rather than how a session commits it.
  [1.3](1.3-the-pad-and-the-rail.md) explains the two dictionaries.
- The `candidates` dictionary runs from the obviously fine to the obviously wrong, in order: a string,
  an integer, a boolean, a list of strings, a small dictionary, a `datetime`, and a custom object.
- `state[key] = value` inside the loop — **every one of these is accepted**. There is no validation on
  this path at all, which is the finding.
- `json.dumps({key: state[key]})` — the second loop asks the question that actually matters: would
  this survive being written to a database? JSON is the honest stand-in, because that is what a
  persistent session service stores.
- `except TypeError as error` — the specific exception `json.dumps` raises for a value it cannot
  encode, and the message names the type, which is what makes it findable.

**Line by line:**

- No service, no session, no model. This is a property of the value, not of the run.

Seven accepted, five that can be written down. The gap between those two numbers is the bug, and today
it is invisible: on the in-memory service both halves of that output describe a working system.

## When it breaks

**The error arrives on the day you add persistence, from a layer you did not touch.**

```text
TypeError: Object of type datetime is not JSON serializable
```

That is the message, verbatim, from the second half of the measurement above. In a real system it
surfaces inside the session service while committing an event, with a traceback full of framework
frames and no mention of the tool that wrote the key. The fix is one line in the tool —
`state["opened_at"] = when.isoformat()` — and finding which tool is the expensive part.

**The value is fine and the session is now enormous.** No error at all. A tool that stashes an API
response in state adds it to every subsequent read and write of that session, and on a persistent
service to every row. The symptom is latency that grows through a conversation and never comes back
down.

**Something confidential ends up in a store you did not think of as a store.** Also silent. State is
persisted by design, printed in debugging, and passed between nodes. A tool that helpfully records the
credential it used has put it somewhere with a much longer life than the request.

## In production

**Write the types down, and normalise at the boundary.**

The version a professional writes converts at the moment of the write: `isoformat()` for times,
`.value` for enums, `model_dump()` for pydantic models, and never the object itself. The reconstruction
happens on the read side, in one helper, so there is exactly one place that knows what
`opened_at` is. ADK 2.x gives you a way to declare the shape as well
([5.1](../05-a-schema-for-state/5.1-declaring-the-boxes.md)), which catches the misspelled key but not
the unserializable value — [5.2](../05-a-schema-for-state/5.2-what-the-schema-does-not-do.md) measures
exactly where that check stops.

**What changes at scale** is that state size becomes a cost you can see on a graph. Sessions get long,
and a session's state is read and written on every turn. Teams that hit this add a size budget — a few
kilobytes per session, checked in a test — long before they add a cache.

**What fails only under real traffic** is the shared dictionary. Two tools both writing `result` is
fine in testing, where only one of them runs, and a silent overwrite in production, where both do.
Namespacing keys by the component that owns them (`triage.severity`, not `severity`) costs nothing and
is very hard to retrofit.

**The review comment**: *"this stores the whole API response. Which field does the next step actually
need, and does the rest need to exist after this invocation?"*

**The interview question**: *"what would you not put in an agent's session state?"* The strong answer
is three things with reasons: anything unserializable, because persistence arrives later; anything
large, because state moves with every turn; and anything secret, because state is written down.
