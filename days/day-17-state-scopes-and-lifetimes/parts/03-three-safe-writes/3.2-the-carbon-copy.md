# 3.2 — The carbon copy

## One-line answer

`output_key="last_triage"` is one argument that makes the agent's **final text** land in state as well
as in the conversation — and if the agent also has an `output_schema`, what lands is the parsed
object rather than the string.

## The story

The receipt book with carbon paper.

The plumber writes the job on the top sheet: what was done, the parts, the total. Under it there is a
sheet of carbon and a yellow copy, and the copy is written at the same instant by the same pen. Nobody
copies anything out afterwards. There is no step where somebody could forget.

You take the white one. The yellow one stays in the book, and at the end of the week the book is what
the plumber does the invoicing from. One act of writing, two places, no discipline required.

## The idea in plain language

[3.1](3.1-writing-from-inside-a-tool.md) covered writing state from inside your own code. `output_key`
covers the case where the thing you want to keep is the **agent's own answer**, and you would otherwise
have to catch it on the way past and write it yourself.

Set it on the agent:

```
Agent(name="sutra_triage", model=..., instruction=..., output_key="last_triage")
```

and when the agent produces its final response, ADK adds `last_triage: <the text>` to that event's
state delta. Same path as everything else — an event, a delta, a commit — with no code of yours
involved.

Reading the implementation in `llm_agent.py` (`google-adk` 2.7.1) pins down exactly when it fires,
which matters because "the final response" is doing a lot of work in that sentence:

- only on an event where `is_final_response()` is true;
- only if that event has **text parts** — an event carrying just a function response is skipped, so a
  turn that ends in a tool result does not overwrite the key with nothing;
- thought parts are excluded from the text that gets stored;
- if the agent declares an `output_schema` ([Day 12](../../../day-12-structured-output/LESSON.md)), the
  text is validated against it first and the **validated object** is stored;
- during streaming the text is accumulated across chunks, so the key holds the whole answer rather than
  the last fragment.

The reason this exists at all is the pipeline case, and it is worth seeing before Phase 8 arrives: one
agent's answer is the next agent's input. With `output_key` the handoff is a state key, which means the
second agent reads a value instead of being handed a transcript to interpret.

## Why Sutra needs it

Because Phase 8's graph is built out of exactly this move, and because it is the cheapest way to make
today's desk useful tomorrow.

Concretely: the triage node answers, its answer lands in `last_triage`, and the writer node's
instruction templates that key straight into its prompt
([4.1](../04-state-in-the-prompt/4.1-state-steers-the-next-turn.md)). No parsing, no extra model call
to summarise, no passing the whole conversation between nodes.

It is also the honest answer to *"how do I keep what the agent just said?"*, which is a question people
usually answer badly by scraping the final event in their own loop. That works and it puts the write
outside the event stream, which is the mistake [6.1](../06-failure-lab/6.1-the-write-that-was-never-written.md)
is about.

## The mechanism

Two agents, identical except for one having a schema, and the state each one leaves behind:

```python
# days/day-17-state-scopes-and-lifetimes/lab/carbon_copy.py
"""output_key: the agent's own answer, copied into state. Zero model calls."""

from google.adk.agents import Agent
from google.adk.runners import InMemoryRunner
from google.genai import types
from pydantic import BaseModel
from scripted import ScriptedModel, text

ANSWER = "Ticket 4521 is high severity: a whole team cannot log in."


class Triage(BaseModel):
    severity: str
    reason: str


def run(agent: Agent, label: str) -> None:
    runner = InMemoryRunner(agent=agent)
    session = runner.session_service.create_session_sync(app_name=runner.app_name, user_id="u1")
    for _ in runner.run(
        user_id="u1",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text="triage 4521")]),
    ):
        pass
    stored = runner.session_service.get_session_sync(
        app_name=runner.app_name, user_id="u1", session_id=session.id
    )
    print(f"{label}: {dict(stored.state)}")


run(
    Agent(
        name="plain",
        model=ScriptedModel(model="scripted", replies=[[text(ANSWER)]]),
        output_key="last_triage",
    ),
    "text answer     ",
)

run(
    Agent(
        name="typed",
        model=ScriptedModel(
            model="scripted",
            replies=[[text('{"severity": "high", "reason": "whole team locked out"}')]],
        ),
        output_schema=Triage,
        output_key="triage",
    ),
    "with a schema   ",
)
```

**Line by line:**

- `class Triage(BaseModel)` — Day 12's structured output, reused. Two fields, both strings, deliberately
  small.
- `for _ in runner.run(...): pass` — draining the event stream without inspecting it. The point of this
  script is what is left **afterwards**, so the loop body is empty on purpose.
- `output_key="last_triage"` on the first agent, and no schema: the answer is a sentence.
- `output_schema=Triage` with `output_key="triage"` on the second: the scripted reply is JSON text, and
  the agent has been told what shape to expect.
- `get_session_sync(...)` after each run — reading the committed state through the service, not the
  session object held before the run.
- The two agents differ in **exactly one thing** apart from their scripted reply, which is what makes
  the difference in the output attributable.

```bash
cd days/day-17-state-scopes-and-lifetimes/lab
uv run python carbon_copy.py
```

**Line by line:**

- Scripted model, so no requests and no key. Two runs, two agents, zero cost.

Measured on `google-adk` 2.7.1 on 2026-09-03 (framework log lines removed):

```text
text answer     : {'last_triage': 'Ticket 4521 is high severity: a whole team cannot log in.'}
with a schema   : {'triage': {'severity': 'high', 'reason': 'whole team locked out'}}
```

The second line is the one worth a second look. State holds a **dictionary**, not the JSON string the
model produced: the schema was applied on the way in, so what a later step reads is
`state["triage"]["severity"]` and not a string somebody has to parse. That is Day 12's structured
output and today's state landing in the same place, and it is the shape Phase 8's nodes hand each
other.

## When it breaks

**The key is missing after a turn that ended in a tool call.**

No error. The implementation skips events with no text parts, so a turn whose final event is a function
response leaves `output_key` untouched — deliberately, because overwriting the previous answer with
nothing would be worse. If you expected a value and got the last turn's, this is why.

**The schema and the answer disagree, and the key is simply not there.**

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for Triage
reason
  Field required [type=missing, input_value={'severity': 'high'}, input_type=dict]
    For further information visit https://errors.pydantic.dev/2.13/v/missing
```

Measured on 2026-09-03 with a scripted reply of `{"severity": "high"}` against the `Triage` schema
above. Read what happened around that traceback, because it is the finding: **the exception did not
reach the caller.** The run completed, the loop over events finished normally, and the state
afterwards was `{}` — the key was never written and nothing in your code was given the chance to
notice. The traceback is printed by the framework's logging and nothing else.

So an `output_schema` is a boundary that refuses bad values, and the refusal arrives as an *absence*
rather than as an error you can catch. The defence is the one Day 21 will build properly — never read
an `output_key` without deciding what to do when it is missing — and it is a live example of the trap
the 2.x baseline warns about (plan §5.1, trap 4): errors that do not surface where they can be acted
on.

**The key holds an assistant's chatter rather than an answer.** `output_key` stores the final text
*verbatim*, including "Sure, here's the triage:". If the value is going to be read by code or templated
into another prompt, either give the agent an `output_schema` so what lands is structured, or instruct
it to answer with the value and nothing else.

## In production

**Use `output_key` for handoffs, and a schema whenever anything but a human reads the result.**

The version a professional writes almost never stores raw final text for machine consumption. The text
is for the person; the structured object is for the next step. Sutra's own build brief today follows
that: the desk's answer may go to `last_triage` as prose, and the *decision* — severity and ticket id —
is written by a tool ([3.1](3.1-writing-from-inside-a-tool.md)) where it can be typed and validated.

**What changes at scale** is that `output_key` becomes an interface between components, so its name
becomes public. Renaming it breaks whichever node reads it, and nothing tells you which node that is
unless the key is a shared constant ([1.3](../01-form-not-story/1.3-the-pad-and-the-rail.md)) or
declared in a state schema ([5.1](../05-a-schema-for-state/5.1-declaring-the-boxes.md)).

**What fails only under real traffic** is the overwrite. `output_key` writes the same key every turn, so
by design it holds *the most recent* answer and nothing else. A system that needs the last three
answers needs a tool that appends to a list, not a second `output_key`.

**The review comment**: *"this stores the final text and the next node parses it with a regular
expression. Add an `output_schema` and let the framework do it at the boundary."*

**The interview question**: *"how do you pass one agent's answer to the next?"* The answer that shows you
have built a pipeline: *"an output key, ideally with a schema, so the handoff is a typed value in state
rather than a transcript the next agent has to interpret."*
