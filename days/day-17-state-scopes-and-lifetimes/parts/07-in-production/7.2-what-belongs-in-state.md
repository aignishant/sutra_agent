# 7.2 — What belongs in state

## One-line answer

State is for **small structured facts your code will branch on**; bytes go to artifacts, secrets stay
in the environment, and the two scopes with the longest lives — `user:` and `app:` — need a written
owner, because nothing checks them and nothing ever clears them.

## The story

The glovebox.

There is a logic to what ends up in it, even though nobody wrote it down. The registration document,
because you need it and only ever in the car. A pen. The tyre pressures on a card. Sunglasses. The
manual, which nobody has opened since the day the warning light came on.

There is also a logic to what does not. The spare key is not in there, because the glovebox is inside
the thing the key opens. Your passport is not in there, because a car is not a safe. And the box of
things you have been meaning to take into the house is not in there — it is on the back seat, where
you can see it, because the glovebox is small on purpose.

Everyone works this out without being told, and the day somebody gets it wrong is the day their
passport spends a week in a car park.

## The idea in plain language

Sutra now has four places a fact can live, and this part is the map.

| Where | For | Example | Lifetime |
| --- | --- | --- | --- |
| **the transcript** | what was said, for the model to read | the customer's wording | the session |
| **state** | small structured facts your code branches on | `severity`, `ticket_id` | by prefix ([2.1](../02-four-lifetimes/2.1-the-prefix-is-the-lifetime.md)) |
| **artifacts** | bytes: files, screenshots, generated reports | the log the customer attached | Day 18's subject |
| **the environment** | secrets | `GOOGLE_API_KEY` | the process |

Four tests decide which one a given fact belongs in:

1. **Will code branch on it?** If yes, state. If only a model or a human reads it, prose is fine.
2. **Is it bytes?** If yes, an artifact. Never base64 in a state key — that is the classic version of
   putting the passport in the glovebox.
3. **Is it a secret?** Then the environment, always. State is persisted, logged and passed between
   components, and Principle 9 predates all three.
4. **How long must it outlive this turn?** That is the prefix, and getting it wrong is a bug in a later
   conversation rather than in this one.

Then two disciplines that are not about *which* store, but about how much:

**Keep it small.** State travels with the session on every read and every write
([2.4](../02-four-lifetimes/2.4-why-temp-exists.md) measured 57,530 bytes after twelve modest turns).
A size budget — a few kilobytes per session, asserted in a test — is a cheap way to keep the class of
bug out entirely.

**Give `user:` and `app:` an owner.** They have the longest lives, they are shared by every component,
they bypass the schema entirely ([5.2](../05-a-schema-for-state/5.2-what-the-schema-does-not-do.md)),
and nothing ever cleans them up. One module owning them, with constants and helpers, is the whole
discipline — and it is much easier to introduce today, with two keys, than in Phase 8 with twenty.

## Why Sutra needs it

Because tomorrow adds a store and Day 47 makes them durable, and both of those days are much easier if
today's facts are already in the right places.

Day 18's artifacts are the direct case. A customer attaches a log file. It is bytes; it belongs in the
artifact service; and the *fact* that it exists — a filename, perhaps a size — is what belongs in state
so a later step can find it. A day that has not drawn the line puts the file's contents in a state key,
and the session is then hundreds of kilobytes that get loaded on every turn.

Day 47 is the second. `DatabaseSessionService` makes state survive a restart, which is Phase 3's gate,
and it also makes every value's serializability a hard requirement rather than a convention
([1.2](../01-form-not-story/1.2-what-may-live-in-state.md)) and every long-lived key a row that
outlives your deployment.

## The mechanism

The map, as a module: Sutra's keys, their scopes and their owner, written so the next person does not
have to guess.

```python
# sutra/state.py - the shape today's build brief asks for
"""Sutra's working memory: the keys, their scopes, and the one tool that writes them.

Scopes (day 17, part 2.1) are chosen by the key's name and enforced by the runtime:
    no prefix -> this conversation      user: -> this engineer, always
    app:      -> everyone               temp: -> this one question

Never put a secret here (Principle 9), never put bytes here (artifacts, day 18),
and normalise types at the write - the schema validates but does not convert (5.2).
"""

from __future__ import annotations

from google.adk.tools import ToolContext
from pydantic import BaseModel

SEVERITY = "severity"  # session: this ticket only
TICKET_ID = "ticket_id"  # session: this ticket only
LAST_TRIAGE = "last_triage"  # session: written by output_key
REPLY_STYLE = "user:reply_style"  # user: follows the engineer
REFUND_WINDOW = "app:refund_window_days"  # app: the same for everyone
RAW_SEARCH = "temp:raw_search"  # invocation: handed between tools


class DeskState(BaseModel):
    """The unprefixed keys the desk may write. Prefixed keys bypass this (5.2)."""

    severity: str
    ticket_id: int
    last_triage: str = ""


def record_triage(severity: str, ticket_id: int, tool_context: ToolContext) -> dict:
    """Record this ticket's triage decision so later steps can read it.

    Args:
        severity: one of "low", "normal", "high".
        ticket_id: the ticket's number.
    """
    tool_context.state[SEVERITY] = severity
    tool_context.state[TICKET_ID] = int(ticket_id)
    return {"recorded": severity, "ticket_id": int(ticket_id)}
```

**Line by line:**

- The module docstring states the scope rules **and the three prohibitions**, because this is the file
  somebody opens when they want to add a key, and that is the moment to tell them.
- Six constants, each with its scope in a comment. Sorted by shrinking lifetime, so the shape of the
  system is visible in the order.
- `DeskState` declares only the unprefixed keys, because those are the only ones the schema can check
  ([5.2](../05-a-schema-for-state/5.2-what-the-schema-does-not-do.md)). Saying so in the docstring stops
  the next person adding `user:reply_style` to it and expecting protection.
- `last_triage: str = ""` has a default because it is written by `output_key`
  ([3.2](../03-three-safe-writes/3.2-the-carbon-copy.md)) and is legitimately absent before the first
  answer.
- `record_triage` is the **only** writer of `severity` and `ticket_id`. One writer per fact is the rule
  from [3.1](../03-three-safe-writes/3.1-writing-from-inside-a-tool.md), and a module like this is where
  it becomes enforceable by grep.
- `int(ticket_id)` — the conversion the schema will not do for you
  ([5.2](../05-a-schema-for-state/5.2-what-the-schema-does-not-do.md)). It happens at the write, once,
  in the one place that writes it.
- The docstring's `Args:` section is what the model reads as the tool's description
  ([Day 10](../../../day-10-function-tools/LESSON.md)), so *"one of low, normal, high"* is doing real
  work: it is the only thing constraining what the model passes.

There is no output block for this one, because it is a module rather than a script. Its behaviour is
asserted in [7.1](7.1-testing-state-without-a-model.md), which is the honest place for a module's
evidence.

## When it breaks

**The file that became a state key.**

```text
TypeError: Object of type bytes is not JSON serializable
```

Measured in [1.2](../01-form-not-story/1.2-what-may-live-in-state.md) for other types, and the same
mechanism: bytes are not JSON, so the failure arrives when persistence does — Day 47, not today. The
fix is tomorrow's subject, and the rule is worth writing before you need it: **bytes are artifacts,
their names are state.**

**The `user:` key nobody owns.** No error, ever. It is written by a tool somebody added, it is not in
any schema, and it is still there in a year. The first symptom is usually a preference that cannot be
turned off, because nothing in the codebase writes the value that would turn it off.

**The session that got slow.** Also no error. Every turn loads all of state, so a session that has been
accumulating intermediates gets heavier with each turn. The measurement is in
[2.4](../02-four-lifetimes/2.4-why-temp-exists.md), and the defence is a size assertion in the test
suite.

**The secret in the state.** No error and the worst outcome. State is written to storage, printed in
debugging, and in Phase 8 passed between nodes; a token written there has a much longer life than the
request that used it. Principle 9 is absolute: credentials come from the environment
([Day 1](../../../day-01-bootstrap-and-map/LESSON.md)) and go nowhere else.

## In production

**Write the map down, and put it where keys are added.**

The version a professional ships has exactly what the module above has: constants with their scope in a
comment, a schema for the checkable half, one writer per fact, and a docstring that says what must not
go in. It is fifteen lines of discipline that saves the two conversations everybody eventually has —
*"why is this value still here?"* and *"why is this session so big?"*

**What changes at scale** is retention. A per-user store with no expiry is a small database of personal
data with no lifecycle, and eventually somebody asks how long you keep it and who can delete it. Having
one module that owns those keys makes the answer a function; having them written from twelve places
makes it a project.

**What fails only under real traffic** is the shape of real values. A ticket id arriving as
`"#4521"` from an email subject, a severity arriving as `"High"` with a capital, a reply style arriving
as `"SHORT"` from a form — all of them write successfully and none of them compares equal to what your
code expects. Normalising at the single writer is what makes that a one-line fix instead of a
scattering of `.lower()` calls.

**The review comment**: *"this adds a state key from inside a tool. Add it to `sutra/state.py` with its
scope, and let that module own the write."*

**The interview question**: *"what goes in an agent's session state and what does not?"* The answer that
sounds like experience is a rule with reasons: *"small structured facts the code branches on. Not bytes
— those are artifacts. Not secrets — those are environment. And the scope is chosen deliberately,
because the long-lived ones are the ones nobody cleans up."*
