# 3.2 — `scripts/`, `references/`, `assets/`

## One-line answer

Three conventional subdirectories — code to run, documents to read on demand, and static resources —
none of them required, all of them loaded **only when the body's links are followed**, which is what
keeps a skill's activation cost at 292 tokens instead of everything it knows.

## The story

The school library has three kinds of shelf and the librarian will tell you which one you want before
you have finished the question.

The textbooks go out on a ticket and come home with you. The reference shelf — dictionaries, the atlas,
the big encyclopaedia — does not leave the room; you go to it, look up the one thing, and put it back.
And in the corner there is a plan chest with the maps and the laminated diagrams in it, which are not
books at all and are pulled out when a particular lesson needs one.

Nothing about the arrangement is enforced by the building. Somebody decided, years ago, that these
three kinds of thing are used differently, and shelved them accordingly — and the arrangement survived
because it matches how people actually work rather than how the catalogue is organised.

## The idea in plain language

A skill directory may contain anything. The specification says so plainly:

> A skill directory may contain any files and directories beyond the required `SKILL.md`. The
> conventions below are recommendations for organizing common types of content.

**Recommendations**, not rules. The validator does not require any of them and will not complain about
extra directories with other names. What follows is a convention that has been given names so that
skills from different authors look the same to a reader.

**`scripts/` — executable code that agents can run.** The spec's guidance: scripts should *"be
self-contained or clearly document dependencies"*, *"include helpful error messages"*, and *"handle
edge cases gracefully"*. Which languages work depends on the client, and the spec names Python, Bash
and JavaScript as common options — so a script is the least portable thing in a skill.

**`references/` — additional documentation the agent reads when needed.** The spec suggests
`REFERENCE.md` for a technical reference, `FORMS.md` for templates, and domain files like `finance.md`.
And the sentence that explains the whole directory: *"Agents load these on demand, so smaller files
mean less use of context."*

**`assets/` — static resources.** Templates, images, data files, lookup tables, schemas. Things that
are used rather than read.

The distinction between the three is **how the thing is consumed**, and it is worth holding on to
because it is the useful part:

| Directory | The agent | Cost |
| --- | --- | --- |
| `scripts/` | **runs** it | output only, whatever the script prints |
| `references/` | **reads** it | the whole file, when it opens it |
| `assets/` | **uses** it | depends — a template read is context, an image may not be |

And the rule that ties them to the body: **file references are relative paths from the skill root**, and
the spec adds *"keep file references one level deep from `SKILL.md`. Avoid deeply nested reference
chains."* A reference that points at a file that points at a file is a chain the agent has to follow,
and each hop is a decision it may not make.

There is one more consequence worth stating early because Day 29 is built on it: **a skill can contain
code, and code runs.** A folder of Markdown you can read before trusting is one thing; a folder with a
`scripts/` directory is a folder that may execute on your machine. That is the blast radius of the
format, and it is why auditing a third-party skill means reading the scripts, not the description.

## Why Sutra needs it

Because the triage procedure has three kinds of content in it already, and only one of them belongs in
the body.

The **steps** are the body: read the ticket, compare, record, report. Short, always needed, cheap.

The **severity table** is reference material: needed on most activations but not all, likely to grow
from three rows to twelve, and the sort of thing a support lead edits without touching anything else.
It goes in `references/SEVERITY.md`, and the body links it — which is the difference between a skill
that costs 292 tokens and one that costs 292 plus the table, every time, forever
([3.1](3.1-the-body-is-loaded-whole.md)).

And the **script** is the case worth thinking hardest about, because Sutra does not strictly need one.
`scripts/severity_table.py` prints the table as JSON for a client that would rather parse data than
prose. It is a convenience, it is the only part of the skill that is not portable, and deleting it
would leave the skill entirely functional — which is exactly the test to apply before adding code to a
folder that was working without it.

## The mechanism

The `ticket-triage` skill's whole tree, and then each directory's contents.

```text
days/day-25-skills-the-open-spec/lab/skills/ticket-triage/
├── SKILL.md                    # loaded whole on activation - 292 tokens
├── references/
│   └── SEVERITY.md             # loaded only if the body's link is followed
└── scripts/
    └── severity_table.py       # never loaded; run, and its output enters context
```

The reference file. It is a table and nothing else:

```text
# Severity table

| Severity | The ticket says |
| --- | --- |
| high | money moved, data lost, or nobody can log in |
| normal | one feature is wrong for one customer |
| low | a question, a typo, or a feature request |
```

**Line by line:**

- One heading and one table. The spec's advice is *"keep individual reference files focused"*, and the
  reason is arithmetic: this file is loaded whole when it is opened, so a file containing the severity
  table **and** the escalation policy costs both every time either is needed.
- The right-hand column is written in **the words a ticket would contain** — *money moved*, *nobody can
  log in* — rather than in abstract severity language. The model is matching ticket text against this
  table, so the table should look like ticket text. That is the same principle as
  [2.3](../02-the-frontmatter/2.3-the-description-field.md)'s description, applied one level in.
- It is Markdown, so a person editing it needs no tooling. The support lead who owns the severity
  policy can change this file, and that is the point of it being a separate file rather than a
  paragraph in a body somebody is nervous about touching.

The script. It exists to make one point about `scripts/`:

```python
#!/usr/bin/env python
"""Print the severity table as JSON, for a client that prefers data to prose."""

import json
from pathlib import Path

TABLE = Path(__file__).resolve().parents[1] / "references" / "SEVERITY.md"


def rows() -> list[dict[str, str]]:
    """Parse the two-column Markdown table into a list of dicts."""
    out = []
    for line in TABLE.read_text(encoding="utf-8").splitlines():
        cells = [c.strip() for c in line.strip().strip("|").split("|")]
        if len(cells) == 2 and cells[0] in {"high", "normal", "low"}:
            out.append({"severity": cells[0], "when": cells[1]})
    return out


if __name__ == "__main__":
    print(json.dumps(rows(), indent=2))
```

**Line by line:**

- `Path(__file__).resolve().parents[1]` walks up from `scripts/` to the skill root, then down into
  `references/`. **The script reads the reference file rather than duplicating the table**, so there is
  exactly one copy of the severity policy in the skill. A script with its own hard-coded copy is a
  second source of truth that will drift within a month.
- The path is relative to the **script's own location**, not to the working directory. A client may run
  a script from anywhere, and `Path("references/SEVERITY.md")` would work only when the shell happened
  to be in the skill root.
- `line.strip().strip("|").split("|")` is a two-column Markdown table parser in one line, which is
  adequate here and would not be adequate for arbitrary Markdown. Being small and obviously limited is
  better than pulling in a Markdown library for one table, and it is what the spec means by
  *"self-contained"*.
- `cells[0] in {"high", "normal", "low"}` filters out the header row and the `| --- |` separator
  without needing to count lines. It also means a new severity would be silently skipped — a real
  limitation, and the honest kind for a helper script whose failure is visible in its output.
- The stdlib only: `json` and `pathlib`. Every import is a dependency the client has to have, and a
  script that needs a package is a script that will fail somewhere the skill otherwise works.
- The docstring says **who it is for** — *"a client that prefers data to prose"* — which is the spec's
  *"clearly document dependencies"* rule extended to intent. A script with no stated purpose in a skill
  is a thing a reviewer has to reverse-engineer before approving.

Run it:

```bash
uv run python days/day-25-skills-the-open-spec/lab/skills/ticket-triage/scripts/severity_table.py
```

**Line by line:**

- Runs from anywhere, because the path is derived from `__file__`. No key, no network, no model.

Measured on 2026-09-04:

```text
[
  {
    "severity": "high",
    "when": "money moved, data lost, or nobody can log in"
  },
  {
    "severity": "normal",
    "when": "one feature is wrong for one customer"
  },
  {
    "severity": "low",
    "when": "a question, a typo, or a feature request"
  }
]
```

**One table, two representations, one source.** The prose version is what a model reads; the JSON is
what a program consumes; and both come from `references/SEVERITY.md`, so they cannot disagree.

## When it breaks

The validator has nothing to say about any of this:

```text
Valid skill: days\day-25-skills-the-open-spec\lab\skills\ticket-triage
```

Empty `scripts/`, a `references/` file the body never links to, an `assets/` directory full of images
nothing uses — all valid. The directories are conventions and the format does not check that they are
used sensibly.

The failure with a real error is the broken link. A body pointing at a file that is not there produces,
at best, a client saying so:

```text
FileNotFoundError: [Errno 2] No such file or directory: '.../references/SEVERITY.md'
```

and, at worst, a model that follows the link, finds nothing, and continues from memory — which is the
same shape as [Day 21](../../../day-21-errors-surface-not-swallow/LESSON.md)'s swallowed exception. A
lint that checks every relative link in a `SKILL.md` resolves to a file is the cheapest thing on Day
31's list.

The subtle failure is the **stale reference**. The body says *"compare against the table"* and the table
has been renamed, or the section it referred to has moved. Nothing errors, because the model reads
whatever is at the path and does its best. And the very subtle one: a reference file that has grown
large enough that opening it costs more than putting its contents in the body would have — at which
point the split has inverted and nobody has noticed.

And the failure that is a security question rather than an engineering one: **`scripts/` runs**. A skill
downloaded from anywhere carries executable code, and reading a `SKILL.md` before trusting it is
insufficient if the folder also contains Python. That is Day 29's audit, and this directory is the
reason it is not optional.

## In production

**`references/` is where a skill's real content lives.** A mature skill has a short body and several
focused reference files — one per topic, each loadable alone. The pattern to copy is the one the spec
names: a `REFERENCE.md` for the detail, `FORMS.md` for templates, and a file per domain. The body
becomes a table of contents with instructions attached.

**Scripts are the least portable part and should be the smallest.** They depend on the client's
willingness to execute, on a language being available, and on dependencies being installed. A skill
that works everywhere except where it needs its script is more annoying than a skill with no script.
The `compatibility` field ([2.4](../02-the-frontmatter/2.4-the-optional-fields.md)) is where that gets
written down.

**What changes at scale** is that assets get large. An `assets/` directory with a few templates is fine;
one with a hundred megabytes of PDFs is a repository problem, a clone-time problem and a review
problem. Skills are text-shaped, and anything big enough to need a storage decision probably belongs
somewhere a skill *points at* rather than somewhere a skill *contains*.

**The failure that only appears with real traffic** is a reference file nobody loads. The body links it,
the model never follows the link because the body already said enough, and a carefully-maintained
document is dead weight that nobody knows is dead. Activation counts tell you a skill is used; only
reading what actually entered the context tells you whether its references were.

**The review comment a senior engineer leaves:** *"this script hard-codes the severity table and so does
`references/SEVERITY.md`. Pick one source and have the other read it, or they'll disagree by
Christmas."*

**The interview question:** *"what goes in a skill besides `SKILL.md`?"* The answer that shows you have
organised one: *"three conventional directories — `scripts/` for code the agent runs, `references/` for
documents it reads on demand, `assets/` for static resources. None required. The important property is
that references are loaded only when the body's link is followed, so bulky material goes there rather
than in the body. And `scripts/` is the part that makes a third-party skill a security question,
because a folder of Markdown you can read is very different from a folder that executes."*
