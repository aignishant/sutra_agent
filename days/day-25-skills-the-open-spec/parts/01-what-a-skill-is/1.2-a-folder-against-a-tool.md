# 1.2 — A folder against a tool

## One-line answer

A tool is a capability the model may invoke and a skill is a **procedure** telling it when and in what
order — which is why a tool's description is one sentence about a function and a skill's `ticket-triage`
body is 292 tokens of steps, edge cases and a linked table.

## The story

The vending machine in the corridor and the noticeboard beside it are both useful and they are not the
same kind of useful.

The machine has buttons. Press B4 and a packet falls down. It does one thing, it does it identically
every time, and it has no opinion about whether you should be eating crisps at four in the afternoon.

The noticeboard has a sheet on it about what to do if the machine takes your money. Ring extension
2210. Write the slot number on the pad by the door. Do not shake the machine — somebody did and it is
now the reason there is a sign. None of that is a mechanism; it is knowledge about how the mechanism
behaves here and what has already gone wrong.

You need both. A noticeboard with no machine gives nobody a packet of crisps, and a machine with no
noticeboard eats a coin every week and nobody knows what to do about it.

## The idea in plain language

Sutra already has tools. [Day 10](../../../day-10-function-tools/LESSON.md) built them: you write a
Python function, ADK reads its name, parameters, type hints and docstring, and the model is told the
function exists. When the model wants it, the runtime calls it and hands back the result.

A tool answers one question: **what can this system do?**

A skill answers a different one: **how does this system do a particular job?** Which tool first. What
to check before calling it. What counts as "urgent" here. What to say when it fails. Which of two
overlapping tools is right for this case. What the table on page four says.

The distinction that makes it click: **a tool is a verb and a skill is a procedure.** A tool cannot
tell you when to use itself, because its description is read alongside every other tool's on every
request, and a paragraph of procedure in each one would fill the window
([24.1.2](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.2-charged-again-every-turn.md)).
A skill can, because it is only loaded when it is relevant.

Three practical differences fall out of that:

| | Tool | Skill |
| --- | --- | --- |
| Is | a function, in your language | a folder of Markdown |
| Written by | a programmer | anyone who knows the procedure |
| Loaded | its declaration, on every request | name + description always; body on activation |
| Can carry | a schema and a docstring | steps, edge cases, tables, templates, scripts |
| Changing it means | editing and deploying code | editing a file |

The last row is the one that changes who can contribute. A support lead who cannot write Python can
write down how triage actually works, and that folder becomes part of the system.

And there is a third thing that is neither, which is worth naming so the three do not blur: the
**instruction** ([Day 6](../../../day-06-instructions-and-personas/LESSON.md)) is the standing
character and rules of the agent, present on every request. The rule for choosing between the three is
about *when the knowledge applies*: always → instruction; when the model chooses to act → tool; when
this kind of task comes up → skill.

## Why Sutra needs it

Because Sutra's instruction is carrying knowledge that does not belong to every request, and it is
being paid for on every request.

Day 19 measured the desk's request and found the instruction growing
([19.4.1](../../../day-19-context-engineering-selection/parts/04-measuring/4.1-a-scale-for-prompts.md)),
and Day 24 put a price on it: the desk instruction is **32 tokens**, on every turn, forever
([24.1.1](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.1-a-ticket-id-costs-five-tokens.md)).
That is fine for *"never invent a ticket that does not exist"*, which applies always. It is not fine
for a triage procedure with a severity table, which applies to perhaps one request in five.

Skills are the mechanism for moving the second kind out. And the measurement below shows what the move
buys: the `ticket-triage` procedure costs **64 tokens** when it is merely available and **292** when
it is used, against a flat 292 if the same words lived in the instruction.

## The mechanism

Put the two side by side. Here is the tool declaration from
[Day 4](../../../day-04-tools-by-hand/LESSON.md), still in `sutra/tools.py`:

```python
# sutra/tools.py - Day 4, unchanged
LOOKUP_TICKET = {
    "type": "function",
    "name": "lookup_ticket",
    "description": (
        "Fetch the full text of one support ticket by its id. "
        "Use this first whenever the user names or implies a specific ticket, "
        "before offering any diagnosis. "
        "Returns the ticket's title and body, or a message saying no such ticket exists."
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "ticket_id": {
                "type": "string",
                "description": "The ticket's id as it appears in the request, e.g. '4521'.",
            }
        },
    },
}
```

**Line by line:**

- `"description"` is three sentences and it is already straining. It has to say what the function
  does, when to call it, and what comes back — and every word of it is loaded on **every** request,
  alongside every other tool's description.
- `"parameters"` is a JSON Schema. It constrains the *shape* of the call and can say nothing about the
  *order* of calls, which is what a procedure is made of.
- There is nowhere in this structure to put *"a ticket that matches no row is `normal`, and you must
  say that no row matched"*. It is not a parameter, not a return value, and not a sentence about this
  one function.
- `"Use this first whenever..."` is a procedure sentence that has been squeezed into a tool
  description because there was nowhere else for it. That squeezing is exactly the pressure skills
  relieve.

Now the same knowledge, as a skill. From
[1.1](1.1-a-skill-is-a-folder.md)'s `SKILL.md`, the body only:

```text
## Steps

1. Read the ticket with `lookup_ticket`. If it returns `status: not_found`, stop and say so.
2. Compare the ticket text against the table in
   [references/SEVERITY.md](references/SEVERITY.md).
3. Call `remember_triage` with the ticket id and the chosen severity.
4. Tell the engineer which severity you chose and which row of the table decided it.

## Edge cases

- A ticket that matches no row is `normal`, and you must say that no row matched.
- Never invent a ticket id. If the lookup fails, the answer is that the ticket does not exist.
- Do not change a severity that is already set unless the engineer asks.
```

**Line by line:**

- The steps **name two tools in an order**. That is the thing a tool declaration structurally cannot
  express: `lookup_ticket` does not know `remember_triage` exists, and neither of them knows which
  comes first.
- Step 2 links a **file**, so the severity table is not in the body at all. It is loaded only if the
  agent needs it, which is
  [3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md)'s third level and is impossible
  for a tool description.
- The Edge cases section is three sentences of hard-won local knowledge. Every one of them is the kind
  of line that gets added after something went wrong, and there is nowhere in a JSON Schema to put
  any of them.
- It is **Markdown, not code**. The person who knows the severity table is the support lead, and this
  is a file they can edit.

Measure what the choice costs, using the counting endpoint from Day 24:

```bash
cd days/day-25-skills-the-open-spec/lab
uv run python what_a_skill_costs.py
```

**Line by line:**

- Needs `GOOGLE_API_KEY`, spends **0** generations —
  [24.1.1](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.1-a-ticket-id-costs-five-tokens.md)
  established that `count_tokens` is a separate endpoint on a separate quota.

Measured on 2026-09-04 against `gemini-3.7-flash`:

```text
skill                 startup  activated   ratio
bad-name                   31         72     2.3x
ticket-triage              64        292     4.6x
vague-description          20         55     2.8x
```

**Read the `ticket-triage` row.** Sixty-four tokens is what it costs to have the skill *available* —
its name and description, loaded at startup. Two hundred and ninety-two is what it costs once the model
decides to use it.

Put the same procedure in the instruction instead and you pay **292 on every request**, including the
four requests in five that have nothing to do with triage. As a skill you pay 64 always and 292 only
when it is used. On a twenty-request day that difference is the whole reason the format exists.

**And a tool could not have carried it at all**, at any price. There is no field in a function
declaration for step four.

## When it breaks

The mistake is not choosing wrongly between them; it is thinking you have to. A skill that describes a
procedure with no tools to carry it out produces an agent that explains what it would do:

> To triage this ticket I would first look it up, then compare it against the severity table, and then
> record the result.

Grammatically confident, operationally useless. The skill is instructions; the tools are hands. A skill
naming a tool that does not exist is worse than no skill, because the model will try to satisfy the
procedure with whatever it does have, which usually means inventing the answer.

The reverse mistake has a more familiar shape. Tools with no procedure produce an agent that calls
things in a plausible order and gets it subtly wrong — recording a severity before reading the ticket,
or answering from the model's own idea of what "high severity" means rather than from your table. That
is not a bug you will see in an error log. It is a bug you see in a customer complaint six weeks later.

There is also a real trap in the `compatibility` field's direction: a skill that assumes tools which
exist in one client and not another. The spec has a field for exactly this
([2.4](../02-the-frontmatter/2.4-the-optional-fields.md)), and it is advisory — nothing enforces it, so
a skill can be perfectly valid and unusable where it lands.

## In production

**The split follows ownership.** Tools are owned by engineers because they are code with a blast
radius; skills are owned by whoever owns the procedure, which is usually not an engineer. Teams that
get this right end up with a small, stable set of tools and a growing, frequently-edited set of skills
— and the review process for the two is deliberately different, because editing a Markdown file cannot
delete a customer's data and a tool can.

**Skills do not replace instructions; they relieve them.** The instruction keeps what is true on every
request — who the agent is, what it must never do, how it speaks. Everything conditional moves out.
A useful review question for any line in a system prompt: *"is this true for every request?"* If not,
it is a skill or a tool.

**What changes at scale** is that skills start referring to each other and to tools that move. A skill
naming `remember_triage` breaks silently when somebody renames that tool, and nothing type-checks a
Markdown file. The mature answer is a lint that extracts backtick-quoted tool names from every
`SKILL.md` and asserts they exist in the registry — which is Day 31's skills lint, and this is the
first reason to want it.

**The failure that only appears with real traffic** is procedure drift. The skill says what triage
used to be; the team changed the severity table in a spreadsheet and nobody edited the folder. Unlike
code, nothing fails. The defence is treating skills as reviewed artefacts with an owner, and putting
the table in `references/` where it is one file rather than a paragraph buried in prose.

**The review comment a senior engineer leaves:** *"this tool's description has grown to a paragraph
about when to use it and in what order. That's a procedure — move it to a skill and let the
description go back to describing the function."*

**The interview question:** *"when would you write a skill instead of a tool?"* The answer that shows
you have shipped both: *"a tool is a capability — a function with a schema. A skill is a procedure:
which tools, in what order, with the edge cases and the reference table. If what I'm writing is 'call
this, then that, and here's what counts as urgent here', it can't go in a function declaration and it
shouldn't go in the system prompt either, because the system prompt is paid for on every request and
the procedure only applies to some of them."*
