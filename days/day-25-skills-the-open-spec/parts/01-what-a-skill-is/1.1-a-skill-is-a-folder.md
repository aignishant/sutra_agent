# 1.1 — A skill is a folder, not a program

## One-line answer

A skill is a directory whose only required member is a file called `SKILL.md` with two required
frontmatter fields — `name` and `description` — and everything else, including whether there is any
code at all, is optional.

## The story

The new person starts on Monday and somebody hands them a folder.

Not a laptop, not a login, not a training course. A folder, with a few printed pages in it: how the
phones are answered, which forms go to which department, the numbers to ring when the lift stops. Half
of it is somebody's typing from years ago and one page is a photocopy of a photocopy.

By Wednesday they can do things they could not do on Monday, and nothing about them has changed except
that they have read those pages. Nobody installed anything. Nobody wrote software. The folder is not a
tool; it is the accumulated knowledge of how this particular place works, written down in the order
somebody thought you would need it.

The most useful thing in the whole building, and it is a folder.

## The idea in plain language

An **Agent Skill** is a folder on disk that teaches an agent how to do a particular kind of task.

That is the whole definition, and the surprising part is how little the format requires. From the
specification, fetched from `agentskills.io/specification` on 2026-09-04:

> A skill is a directory containing, at minimum, a `SKILL.md` file.

`SKILL.md` is a Markdown file with **YAML frontmatter** — a block at the top, between two lines of
`---`, holding key-value pairs — followed by ordinary Markdown. Two frontmatter fields are required
and everything else in the format is optional:

| Field | Required | What it is |
| --- | --- | --- |
| `name` | **yes** | the skill's identifier, and it must match the folder name |
| `description` | **yes** | what the skill does *and when to use it* |

Then, optionally, three conventional subdirectories:

- `scripts/` — executable code the agent can run
- `references/` — documents the agent reads only when it needs them
- `assets/` — templates, images, data files

Notice what is **not** in that list. There is no manifest, no build step, no registration call, no
class to subclass, no runtime, no package. A skill is text in a folder, and the folder is the unit.

Two terms, defined here because the rest of the day leans on them:

- A **client** is any agent product that reads skills. The format is not owned by one runtime — the
  specification exists precisely so that several can read the same folder
  ([1.3](1.3-an-open-spec.md)).
- **Activating** a skill means the client has decided this task needs it and loads the `SKILL.md`
  body into the model's context. Before that moment, only the name and description were loaded
  ([3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md)).

## Why Sutra needs it

Because Sutra has spent fifteen days learning to give the model **capabilities** and has not yet given
it any **procedures**.

A tool ([Day 10](../../../day-10-function-tools/LESSON.md)) is a function the model may call:
`lookup_ticket`, `remember_triage`, `save_note`. Each one does exactly one thing and knows nothing
about when it should be used or in what order. The knowledge of *how the desk actually triages a
ticket* — read this first, compare against that table, never invent an id, say which row decided it —
currently lives in one place: the instruction string
([Day 6](../../../day-06-instructions-and-personas/LESSON.md)), where it competes for room with
everything else the desk needs to know and is paid for on every single request
([24.1.2](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.2-charged-again-every-turn.md)).

A skill is where that knowledge goes instead. And Phase 4 spends seven days on it because the format
turns out to have consequences: it decides what can be shared, what Day 29 will be able to audit in a provenance ledger, and what
gets loaded when.

## The mechanism

Here is a complete, valid skill. It is the whole file.

```text
days/day-25-skills-the-open-spec/lab/skills/ticket-triage/
├── SKILL.md                    # required: metadata + instructions
├── references/
│   └── SEVERITY.md             # read only when the agent needs the table
└── scripts/
    └── severity_table.py       # runnable, for a client that prefers data to prose
```

```text
---
name: ticket-triage
description: Assign a severity to a support ticket and record it, using the desk's published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.
license: Apache-2.0
compatibility: Requires the Sutra desk tools and Python 3.12
metadata:
  author: sutra-desk
  version: "1.0"
---

# Ticket triage

Assign one of three severities to a support ticket and write it to session state.

## Steps

1. Read the ticket with `lookup_ticket`. If it returns `status: not_found`, stop and say so.
2. Compare the ticket text against the table in
   [references/SEVERITY.md](references/SEVERITY.md).
3. Call `remember_triage` with the ticket id and the chosen severity.
4. Tell the engineer which severity you chose and which row of the table decided it.

## Edge cases

- A ticket that matches no row is `normal`, and you must say that no row matched.
- Never invent a ticket id. If the lookup fails, the answer is that the ticket does not exist.
- Do not change a severity that is already set unless the engineer asks.
```

**Line by line:**

- The **folder name is `ticket-triage` and so is the `name` field**. That is not a convention, it is a
  rule the validator enforces ([2.2](../02-the-frontmatter/2.2-the-name-field.md)), and it exists so
  that a skill can be identified by its directory without opening it.
- `description` says **what it does and when to use it**, in one field, and the "when" half is the
  part that does the work. The client shows this sentence to the model and the model decides from it
  ([2.3](../02-the-frontmatter/2.3-the-description-field.md)).
- `license`, `compatibility` and `metadata` are all optional
  ([2.4](../02-the-frontmatter/2.4-the-optional-fields.md)). They are here so that a real example
  shows what a real skill looks like, not because a skill needs them.
- The body is **ordinary Markdown with no required structure**. The specification says so explicitly:
  *"There are no format restrictions. Write whatever helps agents perform the task effectively."* The
  headings here — Steps, Edge cases — are the spec's *recommendation*, not its rule.
- Step 1 begins with a failure case, and step 4 says what to tell the engineer. That is not padding:
  the body is a prompt, and a procedure that only describes the happy path is a procedure the model
  will improvise its way past ([Day 21](../../../day-21-errors-surface-not-swallow/LESSON.md)).
- `[references/SEVERITY.md](references/SEVERITY.md)` is a **relative path from the skill root**, which
  is the spec's rule for file references, and it is what makes the table loadable **only when needed**
  rather than being pasted into the body.
- *"Never invent a ticket id"* is in the skill rather than in the desk's global instruction, and that
  placement is the whole argument of Phase 4: a rule that only applies while triaging should only be
  in context while triaging.

Validate it with the reference library, which is a real package with a real command:

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate \
  days/day-25-skills-the-open-spec/lab/skills/ticket-triage
```

**Line by line:**

- `uv run --no-project --with skills-ref==0.1.1` runs the tool in a **throwaway environment** without
  adding it to `pyproject.toml`. That is how to try a tool before deciding to depend on it, and §3 of
  the hub explains when Sutra should adopt it properly.
- The command is **`agentskills`**, not `skills-ref` — see
  [5.1](../05-in-production/5.1-validating-before-you-ship.md), where that discrepancy is the whole
  point.

Measured on 2026-09-04, against `skills-ref` 0.1.1:

```text
Valid skill: days\day-25-skills-the-open-spec\lab\skills\ticket-triage
```

**That is a complete skill.** A folder, a Markdown file, two required fields, and a procedure written
in the language you would use to explain it to a colleague. No Python was necessary — the one script
in the tree is a convenience, and deleting it would change nothing about the skill's validity.

## When it breaks

The first failure is trying to put the folder where the client is not looking. A skill that is not in
a directory the client scans is not a skill; it is a Markdown file. There is no error, because nothing
went wrong — the client simply never saw it. Where clients look is the client's business, and Day 26 is where ADK's `SkillToolset` answers it for
Sutra.

The second is a `SKILL.md` with no frontmatter at all. The validator is clear:

```text
Validation failed for days\day-25-skills-the-open-spec\lab\skills\ticket-triage:
  - Skill name 'Ticket--Triage' must be lowercase
  - Skill name cannot contain consecutive hyphens
  - Directory name 'bad-name' must match skill name 'Ticket--Triage'
```

Three separate complaints from one file, each naming the rule and the offending value. That output is
from [4.2](../04-failure-lab/4.2-the-name-that-did-not-match.md)'s deliberately broken skill and is
worth seeing once now, because it shows that the required fields are checked mechanically and the
useful ones are not.

Which is the third and largest failure, and it has no error message: **a skill can be perfectly valid
and completely useless.** A `description` of *"Helps with tickets."* passes every check the validator
makes and will never be chosen by a model.
[4.1](../04-failure-lab/4.1-the-skill-that-never-triggered.md) measures exactly that.

## In production

**Skills are how a team's tacit knowledge stops being tacit.** The procedures that live in senior
people's heads — how a refund is actually approved, which log to check first, what "urgent" means
here — become folders that can be reviewed, versioned and improved. That is a documentation practice
with an agent attached, and the documentation benefit arrives whether or not the agent ever reads it.

**The unit being a folder rather than a file is the design decision that matters.** It means a skill
can carry a reference table, a template, a script and a worked example, and it means the whole thing
moves, versions and is reviewed as one object. A single-file format would have forced everything into
the prompt, which is exactly the problem
[3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md) is about.

**What changes at scale** is that skills accumulate, and every one of them costs context at startup.
Measured on 2026-09-04, this day's `ticket-triage` costs **64 tokens** before it is used, and two
hundred skills of that size would be roughly **7,600 tokens** of permanent overhead on every request
([5.2](../05-in-production/5.2-what-a-skill-costs.md)). That is the ceiling on how many skills a
system can carry, and it is a real one.

**The failure that only appears with real traffic** is skill overlap. Two skills whose descriptions
both plausibly match a request, and the model picks whichever it likes — which may be neither
consistently. It is the same problem as two tools with overlapping purposes
([11.3.4](../../../day-11-tool-context/parts/03-designing-a-tool/3.4-two-tools-that-overlap.md)), one
level up, and it is why Day 28 spends a day on skill design rather than treating it as obvious.

**The review comment a senior engineer leaves:** *"this is a good procedure and it's in the system
instruction, so we pay for it on every request whether or not anyone is triaging. Make it a skill."*

**The interview question:** *"what is an Agent Skill?"* The answer that shows you have opened one:
*"a folder with a `SKILL.md` in it — YAML frontmatter with a name and a description, then Markdown
instructions, and optionally `scripts/`, `references/` and `assets/`. No code required. The point is
that the name and description are cheap and always loaded, and the body is only loaded when the agent
decides the task needs it, so you can carry a lot of procedural knowledge without paying for all of it
on every request."*
