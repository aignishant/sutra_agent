# 1.3 — An open spec, and what "open" buys

## One-line answer

The format is published at `agentskills.io/specification` with a reference implementation on PyPI, and
what that buys is portability in both directions: a skill written for one client works in another, and
Sutra can validate a skill without running any client at all.

## The story

A wooden pallet is 1,200 millimetres by 800, and nobody in the warehouse knows why.

They know that the forklift's forks are spaced for it, that the racking is built for it, that the
lorry's floor is a whole number of them across, and that a pallet from a factory four countries away
slides into the racking here without anybody measuring anything. A driver who has never been to this
warehouse backs up to the dock and the goods come off.

None of that required a single agreement between this warehouse and that factory. They agreed with the
same published number, separately, years apart. The standard is doing the negotiating that would
otherwise have to happen every single time two people met.

## The idea in plain language

**Open** here means something specific and checkable, and it is worth being precise because the word
is used loosely.

**The format is published.** There is a document at `agentskills.io/specification` that states the
directory structure, every frontmatter field, its constraints, and the conventions for the optional
subdirectories. It can be read by somebody who is not building the client and not building the skill.

**There is a reference implementation.** `skills-ref` on PyPI — version **0.1.1**, requiring Python
3.11 or later, verified on 2026-09-04 — parses, validates and renders skills. A published format with
no reference implementation is an invitation to twelve incompatible interpretations; a reference
implementation is the tie-breaker.

**And more than one client reads it.** The spec's own site carries a *Client Showcase* page listing
the products that support the format, which is the observable difference between a standard and a
vendor's file layout.

Three things follow, and they are the reason this day exists before the ADK day rather than after it.

**A skill is portable.** The same folder can be read by different agent products. You are not writing
for a runtime; you are writing for a format.

**A skill is inspectable without a runtime.** You can validate, lint, diff, review and count the tokens
of a skill using nothing but a parser — which is what makes
[5.1](../05-in-production/5.1-validating-before-you-ship.md) and Day 31's lint possible.

**And a skill can be audited before it is trusted.** A folder of Markdown from the internet can be read
in full before anything runs it, which is a very different security posture from a package that
executes on install. That is Day 29's subject, and the format is what makes the audit tractable.

One honest caveat, and it matters. **Open does not mean uniform.** The spec defines the *format*, not
what a client does with it: where clients look for skills, how they decide to activate one, whether
they execute `scripts/`, and what tools exist for a skill to name are all client decisions. A skill is
portable in the sense that a pallet is portable — the dimensions match everywhere, and whether this
particular warehouse has a forklift is a separate question.

## Why Sutra needs it

Because the alternative is writing procedures against one runtime's private convention, and Sutra
already knows how that ends.

[Day 15](../../../day-15-toolsets-and-openapi/LESSON.md) made the same argument about tools: an OpenAPI
document is a published description, so a toolset can be generated from it without anyone agreeing to
anything in advance. This is the same shape one layer up, and it is why the plan puts the spec day
before the `SkillToolset` day: **learn the format, then learn one client's handling of it**, so that
when ADK's behaviour and the spec disagree you can tell which is which.

It also decides what Phase 4 can promise. Day 29 sources third-party skills and records each one in
`docs/SKILL_PROVENANCE.md` before it runs. That is only a meaningful discipline if a skill from
elsewhere is a thing that can arrive in the first place — which requires a format somebody else is
also writing to.

## The mechanism

The reference implementation, used three ways. It ships one command and — this is the part to notice —
**the command is not what the specification page says it is**.

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills --help
```

**Line by line:**

- `--no-project` tells `uv` to ignore the surrounding project, so nothing is added to
  `pyproject.toml` and `uv.lock` is untouched. This is how to evaluate a tool before adopting it.
- `--with skills-ref==0.1.1` pins the exact version, verified against `pypi.org/pypi/skills-ref/json`
  on 2026-09-04 (Principle 7: never invent a version).
- The executable is **`agentskills`**. The specification page says `skills-ref validate ./my-skill`,
  and running that gives `error: Failed to spawn: skills-ref — program not found`. The package's
  entry point is `agentskills = skills_ref.cli:main`, read from its own metadata. Documentation and
  package disagree, and the package wins — which is Principle 8 in one small, checkable instance.

Measured on 2026-09-04:

```text
Usage: agentskills [OPTIONS] COMMAND [ARGS]...

  Reference library for Agent Skills.

Options:
  --version  Show the version and exit.
  --help     Show this message and exit.

Commands:
  read-properties  Read and print skill properties as JSON.
  to-prompt        Generate <available_skills> XML for agent prompts.
  validate         Validate a skill directory.
```

**Three commands, and each one is a different kind of open.**

`validate` is the format being checkable ([5.1](../05-in-production/5.1-validating-before-you-ship.md)).

`read-properties` is the metadata being machine-readable:

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills read-properties \
  days/day-25-skills-the-open-spec/lab/skills/ticket-triage
```

**Line by line:**

- Reads the frontmatter and prints it as JSON, so anything — a lint, a registry, a review script —
  can consume a skill without parsing YAML itself.

```text
{
  "name": "ticket-triage",
  "description": "Assign a severity to a support ticket and record it, using the desk's published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.",
  "license": "Apache-2.0",
  "compatibility": "Requires the Sutra desk tools and Python 3.12",
  "metadata": {
    "author": "sutra-desk",
    "version": "1.0"
  }
}
```

And `to-prompt` is the most interesting of the three, because it shows **exactly what a client puts in
front of the model**:

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills to-prompt \
  days/day-25-skills-the-open-spec/lab/skills/ticket-triage \
  days/day-25-skills-the-open-spec/lab/skills/vague-description
```

**Line by line:**

- Takes several skill directories and emits the block a client would include in the system prompt.
  This is the startup half of progressive disclosure, made visible rather than described.

```text
<available_skills>
<skill>
<name>
ticket-triage
</name>
<description>
Assign a severity to a support ticket and record it, using the desk&#x27;s published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.
</description>
<location>
...\lab\skills\ticket-triage\SKILL.md
</location>
</skill>
<skill>
<name>
vague-description
</name>
<description>
Helps with tickets.
</description>
```

**Look at what is in there and what is not.** Name, description, location. **The body is absent.** The
model is told the skill exists and where it lives, and nothing about how it works — which is
[3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md)'s first level, and it is the entire
reason a system can carry many skills.

And look at the second entry. `Helps with tickets.` is the only thing the model will ever know about
that skill before choosing. That is the failure in
[4.1](../04-failure-lab/4.1-the-skill-that-never-triggered.md), visible here as three words in an XML
block.

## When it breaks

Run the command the specification names and it does not exist:

```text
error: Failed to spawn: `skills-ref`
  Caused by: program not found
```

That is a documentation bug in an actively-developed spec, found on 2026-09-04 by running the command
rather than trusting it, and the fix — read the package's own entry point — takes one line:
`importlib.metadata.distribution("skills-ref").entry_points` returns
`[('agentskills', 'skills_ref.cli:main')]`.

It is a small thing and it is the day's best argument for Principle 8. The specification is a good
document, carefully written, and one line of it is stale. Every ADK symbol in this curriculum is
verified against the installed package on the day it is used for exactly this reason, and the same
discipline applied here paid immediately.

The other failure of "open" is subtler and has no error: **a valid skill that a particular client
cannot use.** A skill whose steps name tools that client does not have, or whose `scripts/` are Python
where the client only runs Bash. The format validated; the deployment does not work. The spec
anticipates this with the `compatibility` field
([2.4](../02-the-frontmatter/2.4-the-optional-fields.md)), and that field is a *note to a human*
— nothing enforces it.

## In production

**A published format is what makes a review process possible.** Before a third-party skill runs in your
system, somebody reads it — and reading is tractable because the shape is known and the parser is
somebody else's problem. Day 29 builds the provenance ledger on this: source URL, licence, audit date,
recorded before first use.

**Pin the reference library like any other dependency.** `skills-ref==0.1.1` is a version-zero package
on an actively-moving spec, so its behaviour will change. The dated row in `docs/PACKAGES.md` is what
lets you tell "the spec moved" from "our skill broke".

**What changes at scale** is that the spec becomes a compatibility surface you have to track. A field
added to the format is a field your lint does not know about; a constraint tightened is a skill of
yours that stops validating. The teams that handle this well subscribe to the spec's own repository and
re-run their validator on every skill when the version moves — which is cheap, because validating a
skill needs no runtime.

**The failure that only appears with real traffic** is the divergence between what the spec says and
what a client does. The spec recommends keeping `SKILL.md` under 500 lines and the instructions under
about 5,000 tokens; a client may truncate, or may not. Nothing tells you which. The only reliable
answer is to measure what actually reached the model, which is why
[5.2](../05-in-production/5.2-what-a-skill-costs.md) counts tokens rather than trusting the
recommendation.

**The review comment a senior engineer leaves:** *"we're relying on this client's behaviour, not on the
spec. Write down which of the two we're depending on, because one of them is a promise and the other
is an observation."*

**The interview question:** *"why does it matter that the skill format is an open spec rather than one
product's convention?"* The answer that shows you have used it: *"portability and inspectability. The
same folder works in more than one client, so procedures aren't locked to a runtime. And because the
format is published with a reference parser, I can validate, lint and review a skill without running
any agent at all — which is what makes auditing a third-party skill before it executes a realistic
thing to do rather than a policy nobody follows."*
