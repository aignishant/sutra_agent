# 2.2 — `name`: five rules and a directory

## One-line answer

`name` has five constraints — 1 to 64 characters, lowercase alphanumerics and hyphens only, no leading
or trailing hyphen, no consecutive hyphens, and **it must match the parent directory name** — and the
last one is the only rule in the whole format that reaches outside the file.

## The story

Choosing a username on a website is a small negotiation with a machine that has opinions.

You type the name you want. It comes back and says no capitals. You lower-case it. It says no spaces,
so you put in a hyphen. It says that one is taken, and also that it cannot start with a hyphen, which
you did not know until you tried.

Two minutes later you have a name that satisfies every rule and is not quite the one you wanted, and
you will type it for years. None of the rules were arbitrary — each of them exists because something
downstream needs the name to be predictable — but you only ever meet them one refusal at a time.

## The idea in plain language

`name` is the skill's identifier. Everything that refers to a skill — a log line, a lint, a provenance
row, a client's list — refers to it by this string, so the format constrains it hard.

The five rules, from `agentskills.io/specification` fetched on 2026-09-04:

1. **1–64 characters.**
2. **Only lowercase alphanumerics (`a-z`, `0-9`) and hyphens (`-`).**
3. **Must not start or end with a hyphen.**
4. **Must not contain consecutive hyphens (`--`).**
5. **Must match the parent directory name.**

The first four are the ordinary shape of an identifier that has to survive being a directory name, a
URL segment, a log field and a shell argument without quoting. Rules 3 and 4 in particular exist so
that the name can be split, joined and displayed without producing empty segments.

**Rule 5 is the interesting one**, because it is the only cross-file constraint in the format. The
`name` inside the file must equal the name of the folder containing it. Say what that buys:

- A skill can be **identified without being opened**. A directory listing is an inventory.
- A skill can be **moved by renaming a folder** only if you remember to edit the file, which sounds
  like a burden and is actually the point: the rule makes a half-done rename fail loudly instead of
  producing two names for one thing.
- And **the filesystem becomes the namespace**. Two skills cannot share a name in one directory,
  because two directories cannot share a name.

The rule that is *not* there is worth noticing too: nothing requires the name to be globally unique, or
to be prefixed by an organisation, or to be registered anywhere. Uniqueness is scoped to wherever the
client is looking, which is a decision that becomes interesting on Day 29 when skills start arriving
from elsewhere.

## Why Sutra needs it

Because Sutra will soon have skills from more than one source, and the name is what every ledger keys
on.

`docs/SKILL_PROVENANCE.md` — the ledger the plan requires before any third-party skill runs — has one
row per skill, and the row is found by name. Day 31's skills lint reads a directory of skills and
reports by name. A log line recording which skill was activated carries the name
([Day 22](../../../day-22-structured-logging/LESSON.md)'s format). If the name in the file and the name
of the folder can differ, every one of those has two possible answers.

That is why the format spends a rule on it, and it is why the validator checks it.

## The mechanism

A skill that breaks three rules at once, so the validator's output can be read as a checklist:

```text
---
name: Ticket--Triage
description: Assign a severity to a support ticket. Use when a ticket has no severity.
---

# Ticket triage

This file is meant to be INVALID. Three rules are broken at once: an uppercase letter,
consecutive hyphens, and a name that does not match the parent directory.
```

**Line by line:**

- `Ticket--Triage` breaks rule 2 (uppercase `T`), rule 4 (the `--`), and rule 5 (the directory is
  called `bad-name`). One string, three violations, which is a realistic amount of wrong for a name
  somebody typed the way they would type a title.
- The `description` here is perfectly fine, which matters: it isolates the failure to the name field so
  the validator's output is unambiguous.
- The file lives at `lab/skills/bad-name/SKILL.md`, so the directory and the `name` genuinely disagree
  rather than the mismatch being simulated.

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate \
  days/day-25-skills-the-open-spec/lab/skills/bad-name
```

**Line by line:**

- Points the validator at the deliberately broken skill. Exit status is non-zero, which is what makes
  this usable in a lint (Day 31).

Measured on 2026-09-04 against `skills-ref` 0.1.1:

```text
Validation failed for days\day-25-skills-the-open-spec\lab\skills\bad-name:
  - Skill name 'Ticket--Triage' must be lowercase
  - Skill name cannot contain consecutive hyphens
  - Directory name 'bad-name' must match skill name 'Ticket--Triage'
```

**Three findings from one field, each naming the rule and quoting the offending value.**

Read the third one carefully, because it is the one that could not have been checked by looking at the
file alone: `Directory name 'bad-name' must match skill name 'Ticket--Triage'`. The validator had to
know where the file was, not just what was in it. That is rule 5 being enforced, and it is why the
validator takes a **directory** as its argument rather than a file.

Notice also what it did **not** say. There is no complaint about the description, no complaint about
the body, and no complaint about the missing optional fields — because none of those is a rule. A
validator that reported style opinions alongside format violations would be a validator people learn to
ignore.

## When it breaks

The three above are the loud failures. There are two quiet ones.

**A name that is valid and unhelpful.** `skill-1`, `helper`, `stuff` — all legal, all satisfying every
constraint, and none of them tells a reviewer scanning a directory what they are looking at. The
validator cannot help; this is the same class of problem as
[2.3](2.3-the-description-field.md)'s vague description, applied to a shorter field.

**A name that collides after a move.** Two skills called `triage`, one from your team and one from a
third party, dropped into the same directory. Whichever is loaded second wins, or the client errors, or
both appear — the spec does not say, because it is a client decision. The defence is a naming
convention with a prefix, decided before you need it: `sutra-ticket-triage` rather than `triage`. It
costs a few tokens and prevents an ambiguity that is very hard to debug from the model's behaviour.

And one that will catch you at least once: **renaming the folder and forgetting the file.** Everything
looks right in a directory listing, and the validator refuses with the mismatch message above. The fix
takes seconds; recognising the message takes having seen it, which is why this part shows it.

## In production

**Names are prefixed by owner once there is more than one owner.** `finance-invoice-check`,
`support-ticket-triage`. The prefix is not bureaucracy — it is what makes a name unambiguous in a log
line, a provenance ledger and a directory that contains skills from three teams and two vendors.

**A name is an interface, so renaming is a breaking change.** Anything that referred to the old name —
a pinned reference, a dashboard filter, a test, a document — is now wrong, and none of it will fail
loudly. The mature convention is the same as for any identifier: rename rarely, and when you do, grep
for the old string across the repository before committing.

**What changes at scale** is that the filesystem stops being a big enough namespace. Skills come from
several directories — a bundled set, a team set, a vendor set — and "must match the parent directory"
guarantees uniqueness only within one of them. At that point a client has to decide precedence, and the
useful discipline is to make the decision explicit and log it rather than discovering it from behaviour.

**The failure that only appears with real traffic** is a name that is a substring of another.
`triage` and `triage-escalation` are both valid and both fine to a model — and are a nuisance to
anything doing string matching, including your own dashboard filters and any lint written in a hurry.
Names that are prefixes of other names are worth avoiding for the same reason function names are.

**The review comment a senior engineer leaves:** *"this is called `triage` and we're about to install a
vendor pack that almost certainly has one too. Prefix it now, while nothing depends on the name."*

**The interview question:** *"what constrains a skill's name?"* The answer that shows you have hit the
validator: *"length, lowercase alphanumerics and hyphens, no leading, trailing or doubled hyphens —
and the one that surprises people, it has to match the parent directory name. That last rule is what
lets a directory listing be an inventory, and it's why the validator takes a directory rather than a
file. It also means renaming a skill is a two-part edit that fails loudly if you only do half of it."*

## Check yourself

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate \
  days/day-25-skills-the-open-spec/lab/skills/bad-name
```

Now fix the name to `bad-name` — matching its folder — and validate again. It passes, with a
description that is still mediocre and a body that says it is broken. That gap is the next part.
