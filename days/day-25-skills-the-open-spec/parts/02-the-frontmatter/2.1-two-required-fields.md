# 2.1 — Two required fields and nothing else

## One-line answer

The whole required frontmatter is `name` and `description`; the format's other four fields — `license`,
`compatibility`, `metadata` and `allowed-tools` — are optional, and a skill with only the two costs
**20 tokens** at startup against 64 for one carrying all of them.

## The story

There is a jar at the back of the shared fridge and somebody has written two things on the masking
tape.

Whose it is, and what is in it. That is the whole label, and it is enough: you know not to eat it, and
you know it is not the milk. Every other question you might have — when it was made, whether it needs
refrigerating, what is in it exactly — has an answer somewhere, and none of those answers is what the
label is *for*.

The jar next to it has a full printed label with ingredients, a batch code and a nutrition table, and
no name on it at all. It has been there for three weeks and nobody will touch it or throw it away,
because the one thing the fridge needs to know about a jar is missing.

## The idea in plain language

Frontmatter is the block at the top of `SKILL.md`, between two lines of `---`, written in YAML. The
specification defines six fields in it. **Two are required.**

From `agentskills.io/specification`, fetched on 2026-09-04:

| Field | Required | Constraint |
| --- | --- | --- |
| `name` | **Yes** | Max 64 characters. Lowercase letters, numbers and hyphens only. Must not start or end with a hyphen. |
| `description` | **Yes** | Max 1024 characters. Non-empty. Describes what the skill does and when to use it. |
| `license` | No | License name or reference to a bundled license file. |
| `compatibility` | No | Max 500 characters. Environment requirements. |
| `metadata` | No | Arbitrary key-value mapping (string keys to string values). |
| `allowed-tools` | No | Space-separated string of pre-approved tools. (Experimental) |

Two observations about that table are worth more than the table itself.

**The required two are exactly the two that get loaded at startup.** Everything a client shows the
model before activation is `name` and `description`
([1.3](../01-what-a-skill-is/1.3-an-open-spec.md)'s `to-prompt` output). So the required set is not an
arbitrary minimum — it is precisely the information the format cannot function without, because it is
the information the selection decision is made from.

**And there is no `version` field.** Look for it: there is not one. If you want a version you put it
inside `metadata`, which is a free-form map the spec explicitly says clients may use for *"additional
properties not defined by the Agent Skills spec"*. That absence is a design choice with consequences,
and Day 30's versioning day has to live with it.

The general shape of the format is worth naming: **a small required core with an open extension
point.** Two fields everybody must provide, four the spec defines and nobody must use, and a `metadata`
map for anything else. That is how a format stays writable by hand while remaining useful to tooling.

## Why Sutra needs it

Because the temptation with a new format is to fill in every field, and every field costs tokens on
every request forever.

Measured on 2026-09-04, a skill carrying `license`, `compatibility` and `metadata` costs **64 tokens**
at startup, and one with only the required pair costs **20**. Multiply by the number of skills and by
every request — because the startup block is part of the prompt, so
[24.1.2](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.2-charged-again-every-turn.md)'s
re-charging applies to it — and the difference between a minimal skill and a fully-annotated one is a
real, permanent cost.

Which does not mean the optional fields are waste. It means each one has to earn its place, and
[2.4](2.4-the-optional-fields.md) is about when they do.

## The mechanism

The minimal valid skill, in full. This is the entire file:

```text
---
name: vague-description
description: Helps with tickets.
---

# Ticket helper

This file is valid and useless. It passes every mechanical check and will never be chosen,
because the description says nothing an agent could match a request against.
```

**Line by line:**

- Two fields between two `---` lines, then Markdown. There is no third required thing — no schema
  reference, no format version, no id.
- `name: vague-description` matches the directory it sits in, which is the one cross-field rule the
  format has ([2.2](2.2-the-name-field.md)).
- `description: Helps with tickets.` satisfies the constraint — non-empty, under 1024 characters — and
  is a complete failure at the field's actual job. The validator has no opinion about that, which is
  the point being made and the subject of
  [4.1](../04-failure-lab/4.1-the-skill-that-never-triggered.md).
- The body is three lines of ordinary Markdown. Nothing requires headings, sections or any structure
  at all.
- YAML rules apply, which matters in one practical way: a description containing a colon followed by a
  space needs quoting, or the parser reads it as a nested key. The one in
  [1.1](../01-what-a-skill-is/1.1-a-skill-is-a-folder.md) avoids colons for exactly this reason.

Validate it:

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate \
  days/day-25-skills-the-open-spec/lab/skills/vague-description
```

**Line by line:**

- Same command as before, pointed at the minimal skill.

Measured on 2026-09-04:

```text
Valid skill: days\day-25-skills-the-open-spec\lab\skills\vague-description
```

**Valid.** Two fields, three lines of body, and the format is satisfied.

Now count what each shape costs:

```bash
cd days/day-25-skills-the-open-spec/lab
uv run python what_a_skill_costs.py
```

**Line by line:**

- Counts the startup card (`name` + `description`) and the whole file, for every skill in `lab/skills/`.
  Needs a key, spends **0** generations.

```text
skill                 startup  activated   ratio
bad-name                   31         72     2.3x
ticket-triage              64        292     4.6x
vague-description          20         55     2.8x
```

**Twenty tokens against sixty-four**, for the startup cost of a minimal skill against a fully-annotated
one. Both are real skills; the difference is entirely how much description was written and how many
optional fields were filled in.

And notice which direction the ratio moves. The well-described skill has the *highest* ratio, 4.6×,
because its body is substantial and its card is a good summary of it. A high ratio is a sign of the
format working: a lot of procedure, available cheaply. A ratio near one would mean a skill whose card
is nearly as long as its body, which is a skill that should probably have been a tool description.

## When it breaks

Omit a required field and the validator says which:

```text
Validation failed for days\day-25-skills-the-open-spec\lab\skills\bad-name:
  - Skill name 'Ticket--Triage' must be lowercase
  - Skill name cannot contain consecutive hyphens
  - Directory name 'bad-name' must match skill name 'Ticket--Triage'
```

That is [4.2](../04-failure-lab/4.2-the-name-that-did-not-match.md)'s skill, and the useful property to
notice is that it reports **all three** problems rather than stopping at the first. A validator that
reports one error per run turns fixing a file into a conversation.

The failure with no message is the YAML one, and it is worth meeting once. A description containing an
unquoted colon parses as a nested mapping, so the `description` key holds something that is not a
string — and depending on the client you get a confusing type error or, worse, a silently truncated
description. The habit that avoids it: **quote any description containing a colon**, or write around
the colon, which is what the spec's own examples do.

And the largest failure in this part is the one the validator is structurally unable to see: `Helps
with tickets.` is a valid `description` and a useless one. Every mechanical constraint on that field
is about length and emptiness; every useful property of it is about content.
[2.3](2.3-the-description-field.md) is what the constraint cannot express.

## In production

**Teams settle on a house frontmatter and lint it.** The spec's required two plus, typically, `license`
and a `metadata.version` — because a skill that gets shared needs a licence and a skill that gets
updated needs a version, and the format supplies neither by default. That house standard is enforced by
a lint rather than by the spec's validator, which correctly accepts the minimum.

**`metadata` is where organisational fields go.** Owner, review date, the ticket that introduced it,
which team is on the hook when it misfires. The spec's advice is to make key names *"reasonably unique
to avoid accidental conflicts"*, which is a polite way of saying prefix them: `sutra_owner` rather than
`owner`.

**What changes at scale** is that the frontmatter becomes the index. With five skills you read the
folder; with five hundred you query `read-properties` across all of them and build a table. At that
point every field you did *not* fill in is a column of nulls in your inventory — which is the argument
for a house standard, and the counter-argument to the token cost above. Both are real; the resolution
is that `metadata` costs tokens only if the client includes it in the startup card, and most include
only `name` and `description`.

**The failure that only appears with real traffic** is a description written for a human reviewer
rather than for a model. *"Internal triage skill, see RFC-114"* is meaningful to the team and matches
no user request that will ever arrive. The field has one audience and it is the model.

**The review comment a senior engineer leaves:** *"there's no version anywhere in this skill and we're
about to change it. The spec has no `version` field — put one in `metadata` and decide now what
happens to a skill someone has pinned."*

**The interview question:** *"what's in a `SKILL.md` frontmatter?"* The answer that shows you have
written one: *"`name` and `description` are required and everything else is optional — licence,
compatibility, a free-form metadata map, and an experimental allowed-tools field. The two required ones
are the two that get loaded at startup for every skill, which is why they're the required ones. And
there's no version field, so if you need versioning it goes in metadata and you have to decide the
policy yourself."*

## Check yourself

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills read-properties \
  days/day-25-skills-the-open-spec/lab/skills/vague-description
```

Two fields come back. Now add `metadata: {owner: you}` to that file, run it again, and then run
`what_a_skill_costs.py` to see whether the startup number moved.
