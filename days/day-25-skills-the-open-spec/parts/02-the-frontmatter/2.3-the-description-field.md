# 2.3 — `description`: the field the agent actually reads

## One-line answer

`description` is the only part of a skill the model sees before choosing it, so it has to say **what
the skill does and when to use it** — and measured against five realistic requests, a description
written that way overlapped on **7** words where *"Helps with tickets."* overlapped on **1**.

## The story

The sign above the shop is the only thing most people ever read.

They are walking, they are looking for somewhere to get a phone screen replaced, and they have about a
second per shop front. The one that says **PHONE REPAIRS · SCREENS · BATTERIES · WHILE YOU WAIT** gets
them. The one that says **TECH SOLUTIONS** does not, even though it is the better shop, staffed by
somebody who has been doing this for twenty years.

The second shop is not badly run. It is badly *found*. Everything good about it is on the inside of a
door nobody opens, because the sign was written by somebody describing their business to themselves
rather than to a stranger walking past with a broken phone.

## The idea in plain language

Here is the mechanism, stated plainly, because everything else in this part follows from it.

When a client starts, it reads every skill's `name` and `description` and puts them in the model's
context ([1.3](../01-what-a-skill-is/1.3-an-open-spec.md) shows the exact XML block). The bodies are
**not** loaded. Then a request arrives, and the model decides — from those names and descriptions
alone — whether any skill applies.

So the description is not documentation. **It is the selection interface.** It is the only evidence the
model has, and a skill with a poor one is functionally absent no matter how good its body is.

The spec's own guidance, fetched on 2026-09-04, is unusually direct about this:

> Should describe both what the skill does and when to use it.
> Should include specific keywords that help agents identify relevant tasks.

And it gives a good example and a poor one:

> **Good:** Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use
> when working with PDF documents or when the user mentions PDFs, forms, or document extraction.
>
> **Poor:** Helps with PDFs.

The difference between those two is not effort or eloquence. It is that the good one contains **the
words a user's request would contain**. Somebody asking for help will say *"extract"*, *"form"*,
*"merge"*, *"PDF"* — and those words are in the description, so there is something to match.

Three rules that fall out of it:

**Write the "when", not just the "what".** Half of the good example is a sentence beginning *"Use
when"*. That half is doing most of the work.

**Use the requester's vocabulary, not yours.** If the team says "triage" and users say "how urgent is
this", both belong in the description. Internal names for things are the most common way a description
becomes unfindable.

**Be specific enough to exclude.** A description that could match anything will be chosen for things it
cannot do, which is a worse failure than not being chosen — the model activates the skill, reads a
procedure that does not fit, and improvises.

The constraint is **1 to 1024 characters**, which is generous: roughly a solid paragraph. The limit is
not the pressure; the token cost is
([5.2](../05-in-production/5.2-what-a-skill-costs.md)), and it is a cost worth paying, because a skill
that is never selected costs its tokens and returns nothing.

## Why Sutra needs it

Because Sutra's whole Phase 4 investment is worthless if the desk never chooses the skill it wrote.

The `ticket-triage` skill in this day's lab contains a real procedure: read the ticket first, compare
against the published table, never invent an id, say which row decided it. Every one of those lines is
the accumulated result of something going wrong. And none of it is reachable unless a request about an
urgent ticket causes the model to pick this skill out of a list where its only representation is one
sentence.

Day 28 spends a whole day on skill design and Day 30 on testing skills, and both of them are downstream
of this field. It is the highest-leverage sentence in the entire folder.

## The mechanism

Compare descriptions against realistic requests. This is a **proxy** — the model does not do word
matching — but it measures the one thing the model has to work with.

```python
# days/day-25-skills-the-open-spec/lab/describe_or_not.py
REQUESTS = [
    "how urgent is ticket 4521?",
    "please triage this ticket",
    "what severity should I give a login outage?",
    "set the priority on 4522",
    "can you help me with tickets",
]

STOP = {"a", "an", "the", "is", "on", "this", "with", "i", "you", "me", "should", "can", "please"}


def words(text: str) -> set[str]:
    """Lowercase alphabetic words, minus the ones every sentence contains."""
    return {w for w in re.findall(r"[a-z]+", text.lower()) if w not in STOP and len(w) > 2}


def description_of(skill: Path) -> str:
    """The description line out of the frontmatter, unwrapped."""
    body = (skill / "SKILL.md").read_text(encoding="utf-8").split("---")[1]
    for line in body.splitlines():
        if line.startswith("description:"):
            return line.partition(":")[2].strip()
    return ""
```

**Line by line:**

- The five `REQUESTS` are written the way people actually ask, not the way the team talks. *"How urgent
  is ticket 4521"* uses none of the words *triage* or *severity*, and that is the realistic case: the
  description has to bridge the gap.
- The last request, *"can you help me with tickets"*, is deliberately vague. It is the control: a
  request with no specific words should not strongly match a specific skill, and if it does, the
  description is too broad.
- `STOP` removes the words every English sentence contains. Without it, *"the"* and *"is"* would
  dominate every overlap and the numbers would measure nothing.
- `len(w) > 2` drops two-letter fragments and, incidentally, the digits — `re.findall(r"[a-z]+", ...)`
  already excludes numbers, so `4521` is not counted. That is correct here: an id in a request should
  not match a description, and a description containing example ids would be gaming the measurement.
- `words()` returns a **set**, so a word repeated in a long description does not inflate the score. The
  question is whether a concept is present, not how often.
- `description_of` splits on `---` and takes element `[1]`, the frontmatter block. It is a deliberately
  small parser: this script's job is to compare text, and reaching for a YAML library to read one line
  would obscure that.
- Nothing here calls a model. **This is a proxy and the script says so in its own docstring** — a real
  client hands the descriptions to the model and lets it choose. The proxy is honest because the model
  is choosing from these exact words, so word overlap is a lower bound on findability rather than a
  simulation of the decision.

```bash
cd days/day-25-skills-the-open-spec/lab
uv run python describe_or_not.py
```

**Line by line:**

- No key, no network, **0** generations. It reads three `SKILL.md` files and counts.

Measured on 2026-09-04:

```text
request                                            bad-name  ticket-triage  vague-descrip
how urgent is ticket 4521?                                1              3              0
please triage this ticket                                 1              2              0
what severity should I give a login outage?               1              1              0
set the priority on 4522                                  0              1              0
can you help me with tickets                              0              0              1
total overlapping words                                   3              7              1

This is word overlap, not model judgement - but the model sees only these words.
```

**Read the `vague-description` column top to bottom: 0, 0, 0, 0, 1.**

It matched nothing except the one request that was itself vague. *"Helps with tickets."* shares no
words with *"how urgent is ticket 4521"* beyond the ones the stop list removes — and note that even
*"tickets"* against *"ticket"* does not match, because they are different strings. A model is better at
that than this script is, and it is still choosing between three sentences of which one says almost
nothing.

**And the `ticket-triage` column: 3, 2, 1, 1, 0.** It matches every specific request and — this is the
part worth noticing — matches the vague one **least**. That is the "be specific enough to exclude" rule
paying off: a skill that matches everything is a skill that will be activated for tasks it cannot do.

Look at where the matches come from. The description is:

> Assign a severity to a support ticket and record it, using the desk's published severity table. **Use
> when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words
> triage, severity or priority appear.**

The bold half — the "when" — supplies *urgent*, *triage*, *severity* and *priority*. Delete it and the
column becomes 1, 1, 1, 0, 0. **More than half the findability is in the second sentence**, and the
second sentence is the one people leave out.

## When it breaks

There is no error message. That is the entire difficulty with this field, and it is why
[4.1](../04-failure-lab/4.1-the-skill-that-never-triggered.md) exists as a failure lab part rather than
a warning here.

The validator's verdict on the worst description in the lab:

```text
Valid skill: days\day-25-skills-the-open-spec\lab\skills\vague-description
```

Valid. Every constraint satisfied — non-empty, under 1024 characters. The one thing that matters about
the field is not a constraint and cannot be one.

The second failure mode is the opposite and produces visible bad behaviour: a description broad enough
to match everything. *"Assists with support desk tasks"* will be selected for a refund question, a
password reset and a complaint about the website, and each time the model loads a triage procedure that
does not fit and does its best with it. That looks like the model being unreliable and is a description
being greedy.

The third is writing for the wrong reader:

> Internal triage skill. See RFC-114 for the severity rubric. Owner: platform.

Every word of that is useful to a human reviewer and none of it is a word a user would type. The field
has one audience.

## In production

**Descriptions are tuned against real requests, not written once.** The workflow that works is: collect
the requests that *should* have activated a skill and did not, extract the words they used, and add
those words to the description. The spec has a whole page on this — *Optimizing descriptions* — because
it is the field that most reliably decides whether a skill is used, and it is the one people write last
and never revisit.

**Test the selection, not just the output.** Day 30's skill testing includes asserting that a given
request activates a given skill, which is a test of this field and nothing else. It is cheap, it is
the thing that regresses when somebody "tidies up" a description, and almost nobody writes it until
they have been burned.

**What changes at scale** is that descriptions start competing. With five skills, a mediocre
description is still the only plausible match. With fifty, several will plausibly match any request,
and the differences between descriptions do the selecting — which means each one has to say not just
what it does but implicitly what it is *not* for. That is a harder writing task, and it is why Day 28
exists.

**The failure that only appears with real traffic** is vocabulary drift. The description was written
with the words the team used a year ago; the product renamed "severity" to "impact"; users now say
*impact* and the skill quietly stops being found. Nothing errors, the skill is still valid, and the
activation rate falls. Watching activation counts per skill — a Day 22 metric — is the only way this
gets noticed.

**The review comment a senior engineer leaves:** *"the description says what it does but not when to
use it. Add the sentence starting 'Use when' with the words a user would actually type, including the
ones we don't use internally."*

**The interview question:** *"what makes a good skill description?"* The answer that shows you have
watched one fail to trigger: *"it has to carry both halves — what the skill does and when to use it —
and the second half is where the keywords live, because the description is the only thing the model
sees before choosing. I write it in the requester's vocabulary rather than ours, and I make it specific
enough to exclude, because a description that matches everything gets the skill activated for tasks it
can't do. And it's the field with no validator: a useless description passes every check."*
