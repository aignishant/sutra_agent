# 2.4 — The four optional fields

## One-line answer

`license` says who may reuse it, `compatibility` says what it needs, `metadata` is a free-form map for
everything the spec did not define — including the version the format lacks — and `allowed-tools` is
marked **experimental**, which means a skill that depends on it may behave differently in every client.

## The story

The medicine box has a great deal printed on it that you have never read.

Batch number. Storage below 25 degrees. Manufactured by, licensed to, marketing authorisation number.
Do not use if the seal is broken. Expiry.

None of it is needed to swallow the tablet, and every single line is needed by somebody. The pharmacist
checks the expiry. The wholesaler checks the batch when there is a recall. The person with a cupboard
above the oven should have read the storage line. The information is not for the person at the moment
they take the tablet; it is for everyone else in the chain, at the moments when something has to be
traced, checked or blamed.

## The idea in plain language

Four fields, none required. Taken from `agentskills.io/specification`, fetched 2026-09-04.

**`license`** — *"License name or reference to a bundled license file."* The spec recommends keeping it
short: either a name (`Apache-2.0`) or a pointer (`Proprietary. LICENSE.txt has complete terms`). It
answers one question: may somebody else use this folder, and on what terms.

**`compatibility`** — max 500 characters, and *"should only be included if your skill has specific
environment requirements"*. It states what the skill needs to work: an intended product, system
packages, network access. The spec's own examples are
`Designed for Claude Code (or similar products)`, `Requires git, docker, jq, and access to the
internet`, and `Requires Python 3.14+ and uv`. It is **advisory**: nothing enforces it, and a client
that cannot satisfy it will not necessarily say so.

**`metadata`** — *"a map from string keys to string values"*, for *"additional properties not defined
by the Agent Skills spec"*, with the advice to *"make your key names reasonably unique to avoid
accidental conflicts"*. This is the format's extension point, and it is where the missing `version`
field goes ([2.1](2.1-two-required-fields.md)).

**`allowed-tools`** — *"a space-separated string of tools that are pre-approved to run"*, and the spec
labels it **Experimental**, adding that *"support for this field may vary between agent
implementations"*. The example given is `Bash(git:*) Bash(jq:*) Read`.

The rule for using them is one sentence: **fill in a field when somebody downstream needs it, and leave
it out otherwise.** Each one is text in every skill's file, and two of them — `license` and
`metadata` — are the sort of thing that gets copied from a template into fifty skills and then never
read.

`allowed-tools` deserves a separate warning because it looks like a security control and is not one
yet. *Experimental* in a specification means the field may change, may be ignored, or may be
interpreted differently by two clients. A skill that relies on it for safety is relying on a promise
the spec has not made. **The containment story for a skill is the client's, not the field's** — which
is Principle 13's blast-radius rule pointed at a format, and it is why Day 29 audits third-party skills
by reading them rather than by trusting their frontmatter.

## Why Sutra needs it

Because three of the four are load-bearing for days that are already scheduled.

`license` is a column in `docs/SKILL_PROVENANCE.md`, the ledger the plan requires before any
third-party skill runs. A skill arriving from elsewhere with no licence is a skill you cannot legally
ship, and finding that out at audit time is much cheaper than finding out later.

`metadata` is where Sutra's version goes, because the format has no `version` field and Day 30 is about
skill versioning. Deciding the key name **now**, before there are twenty skills to edit, is the cheap
moment.

And `compatibility` is where a skill records that it needs Sutra's own tools. The `ticket-triage` skill
names `lookup_ticket` and `remember_triage` in its steps; dropped into a client that has neither, it is
a procedure with no hands ([1.2](../01-what-a-skill-is/1.2-a-folder-against-a-tool.md)). The field does
not prevent that. It documents it, which is the difference between a confusing failure and an obvious
one.

## The mechanism

All four, in one file, with the values Sutra would actually use:

```text
---
name: ticket-triage
description: Assign a severity to a support ticket and record it, using the desk's published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.
license: Apache-2.0
compatibility: Requires the Sutra desk tools and Python 3.12
metadata:
  author: sutra-desk
  version: "1.0"
---
```

**Line by line:**

- `license: Apache-2.0` is an SPDX identifier — a short standard name for a licence — rather than a
  paragraph of terms. Short is the spec's recommendation and it is also what a provenance ledger can
  put in a column and a script can compare.
- `compatibility: Requires the Sutra desk tools and Python 3.12` names both halves of what this skill
  assumes: the tools its steps call, and the runtime its `scripts/` need. It is under the 500-character
  limit by a wide margin, which is normal — the spec says most skills do not need this field at all.
- `metadata:` is a **nested mapping**, not a string, and it is the one field with structure. Its values
  must be strings.
- `version: "1.0"` is **quoted**, and the quotes are load-bearing. Unquoted, YAML reads `1.0` as a
  float, and `1.10` would parse as `1.1` — which is a real versioning bug that produces no error and
  breaks ordering. The spec's own example quotes it for this reason.
- `author: sutra-desk` is a generic key name, and the spec's advice would prefer something less
  collision-prone. Sutra's own convention should be `sutra_owner` or similar; this example uses the
  spec's own key so that a reader comparing the two documents sees the same thing.
- **`allowed-tools` is deliberately absent.** It is experimental, Sutra does not yet know what any
  client will do with it, and an absent field cannot be depended on by mistake.

Read the frontmatter back the way a tool would:

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills read-properties \
  days/day-25-skills-the-open-spec/lab/skills/ticket-triage
```

**Line by line:**

- Emits the frontmatter as JSON, which is how a lint, a registry or a provenance script consumes a
  skill without parsing YAML itself.

Measured on 2026-09-04:

```text
{
  "name": "ticket-triage",
  "description": "Assign a severity to a support ticket and record it, using the desk's published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.",
  "license": "Apache-2.0",
  "compatibility": "Requires the Sutra desk tools and Python 3.12",
  "metadata": {
    "author": "sutra-desk",
    "version": "1.0"
  }
}
```

**`"version": "1.0"` came back as a string**, which is the quoting doing its job — and is exactly what a
provenance ledger wants, because `"1.10"` sorts and compares correctly as text in a way it never would
as a float.

**And `allowed-tools` is absent from the output** rather than present and null. An omitted optional
field is simply not there, which means a consumer must handle its absence and cannot mistake an empty
value for a declared one.

Now compare that with the minimal skill from [2.1](2.1-two-required-fields.md): two fields against five,
and **64 tokens at startup against 20** — although only if the client puts them all in the startup card.
The `to-prompt` output in [1.3](../01-what-a-skill-is/1.3-an-open-spec.md) shows this client putting in
only name, description and location, which means most of the optional frontmatter costs nothing at
runtime and everything at review time. That is a good trade and it is worth knowing it is the trade
being made.

## When it breaks

The YAML mistakes are the common ones and only one of them raises.

Unquoted versions parse as numbers:

```text
>>> yaml.safe_load('version: 1.10')
{'version': 1.1}
```

No error. `1.10` became `1.1`, and any ordering built on it is now wrong in a way that shows up months
later when someone releases `1.9` and it sorts above `1.10`.

A `metadata` value that is not a string is accepted by the YAML parser and violates the spec's
*"map from string keys to string values"*. Whether a given client complains is a client decision; the
safe habit is to quote every metadata value, always.

And the failure that is not a parse error at all: **`compatibility` is a note, not a gate.** A skill
saying `Requires the Sutra desk tools` will load perfectly happily in a client that has none of them,
validate cleanly, be selected for a triage request, and then produce a confident description of what it
would have done. The field warned a human who did not read it.

The same is true, more sharply, of `allowed-tools`. It is experimental, so the honest assumption is that
it does nothing. Writing `allowed-tools: Read` and believing the skill therefore cannot write files is
a security conclusion drawn from a field the spec has not finished designing.

## In production

**`license` is checked before a skill is installed, not after.** The provenance ledger Day 29 builds
has a licence column, and populating it at audit time is the point — a skill whose licence is unknown
is a skill nobody can approve. For skills you write, an explicit licence is what lets another team
inside the same company reuse them without a legal conversation.

**`metadata` becomes the organisational schema.** Owner, review date, source, the ticket that
introduced it, the version. None of that is in the spec, all of it is in `metadata`, and the useful
discipline is to write down your key names once and lint for them — because a `metadata` map with
different keys in every skill is not an index.

**What changes at scale** is that `compatibility` starts mattering, because skills start moving between
environments. A skill written where `jq` exists, deployed where it does not, fails inside a script with
a message about a missing binary rather than a message about a missing requirement. Mature setups turn
`compatibility` from prose into something checkable — a preflight that parses it or a structured key in
`metadata` — precisely because the spec's version is free text.

**The failure that only appears with real traffic** is the copied template. One skill's frontmatter
becomes the template for the next twenty, and now twenty skills claim `author: sutra-desk` and
`version: "1.0"` regardless of who wrote them or what has changed. The fields are present, the ledger
looks complete, and none of it is true. A field that is always the same value is a field that is not
being maintained, and it is worth auditing for exactly that.

**The review comment a senior engineer leaves:** *"this sets `allowed-tools` and the spec marks that
field experimental. If we're relying on it for containment, we're relying on something that may be
ignored — say what the actual control is."*

**The interview question:** *"what optional metadata does a skill carry?"* The answer that shows you
have shipped one: *"licence, compatibility, a free-form metadata map, and an experimental allowed-tools
field. The one I always fill in is licence, because anything shared needs it. Compatibility only when
the skill genuinely needs something specific — and it's advisory, nothing enforces it. Metadata is where
the version goes, because the spec doesn't have a version field, and I quote it so YAML doesn't turn
1.10 into 1.1. I don't rely on allowed-tools for anything security-shaped while it's still
experimental."*
