# 4.1 — 💥 The skill that never triggered

## One-line answer

`Helps with tickets.` is a **valid** skill description — the validator says `Valid skill` — and across
five realistic requests it overlapped on **one** word, and that one match was the vaguest request in
the set: a folder that is correct, cheap, permanently loaded, and never chosen.

## The story

The CV says *"responsible for various tasks in a fast-paced environment"* and it is never read past
that line.

The person who wrote it has done remarkable things. They rebuilt a payments integration over a
weekend, they trained four people who now run teams, they found a bug that had been costing money for
two years. All of it is true and all of it is on page two.

Page two does not get reached, because two hundred CVs arrived and the person reading them spends a
few seconds on each, looking for the words in the job advert. *"Various tasks"* contains none of them.
The CV is not rejected on its merits; it is not evaluated at all.

## The idea in plain language

This is the failure that has no error message anywhere in the chain, and it is the most common failure
in the whole format.

Reconstruct it from the mechanism ([3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md)):

1. The client loads every skill's `name` and `description` at startup.
2. A request arrives.
3. The model chooses a skill **from those cards alone** — it has not seen any body.
4. If none matches, the request is answered without any skill, normally and plausibly.

Step four is the problem. There is no *"no skill matched"* signal. The agent answers. The answer may
even be fine — models are good at support-desk prose. It is simply an answer that did not use the
procedure you wrote, did not consult the severity table, and did not obey the three edge cases somebody
learned the hard way.

So the failure presents as: **an agent that works, and a skill that appears to do nothing.**

And every mechanical check passes. The skill is valid. The file parses. The body is excellent. The
folder is in the right place. The only thing wrong is one sentence, and no validator can have an
opinion about it, because the property that sentence needs is *"contains the words a real request will
contain"*, which is a fact about your users and not about YAML.

## Why Sutra needs it

Because this is the failure that makes people conclude skills do not work.

The sequence is predictable. Somebody writes a good skill with a hurried description. It never fires.
They add more detail to the body, which changes nothing, because the body is not what selection reads.
They conclude the model is unreliable at choosing skills and go back to putting everything in the
system instruction — which does work, and costs a permanent 292 tokens on every request
([3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md)), and undoes the whole point of
Phase 4.

The diagnosis has to be available before that conclusion is reached. Which is why this is a failure lab
part with a measurement in it rather than a warning in a bullet list.

## The mechanism

Two skills. The bodies are irrelevant; the cards are everything.

```text
---
name: vague-description
description: Helps with tickets.
---

# Ticket helper

This file is valid and useless. It passes every mechanical check and will never be chosen,
because the description says nothing an agent could match a request against.
```

**Line by line:**

- `Helps with tickets.` is three words and satisfies every constraint the spec places on the field:
  non-empty, well under 1024 characters. It is the spec's own *"Poor example"* pattern —
  *"Helps with PDFs."* — with the noun changed.
- It says **what** and never **when**, which is the half [2.3](../02-the-frontmatter/2.3-the-description-field.md)
  measured as carrying most of the findability.
- The body is honest about the situation, which is the only reason this file is not a waste of disk:
  it is a specimen.

Against the well-written one from [1.1](../01-what-a-skill-is/1.1-a-skill-is-a-folder.md):

```text
description: Assign a severity to a support ticket and record it, using the desk's published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.
```

**Line by line:**

- First sentence: **what**. Assign a severity, record it, using the published table.
- Second sentence: **when**, and it names four trigger shapes — a ticket arriving without one, somebody
  asking how urgent, and the words *triage*, *severity*, *priority*. Those are the words a request will
  contain.
- It is deliberately **not** open-ended. There is no *"and other ticket tasks"*, because a card that
  matches everything gets activated for things the body cannot do — the opposite failure, and a worse
  one.

Now run the proxy from [2.3](../02-the-frontmatter/2.3-the-description-field.md):

```bash
cd days/day-25-skills-the-open-spec/lab
uv run python describe_or_not.py
```

**Line by line:**

- Counts word overlap between five realistic requests and each skill's description. Not model
  judgement — but the model is choosing from exactly these words, so overlap is a floor on
  findability. No key, **0** generations.

Measured on 2026-09-04:

```text
request                                            bad-name  ticket-triage  vague-descrip
how urgent is ticket 4521?                                1              3              0
please triage this ticket                                 1              2              0
what severity should I give a login outage?               1              1              0
set the priority on 4522                                  0              1              0
can you help me with tickets                              0              0              1
total overlapping words                                   3              7              1
```

**The `vague-descrip` column is four zeros and a one.**

Zero on *"how urgent is ticket 4521"*. Zero on *"please triage this ticket"*. Zero on *"what severity
should I give a login outage"*. Zero on *"set the priority on 4522"*. Those are four requests that are
unambiguously about triage, and the skill written to handle them shares no meaningful word with any of
them.

**And its one match is the request that was itself vague** — *"can you help me with tickets"* — which is
the only request in the set that nobody should want a specific procedure for. The skill is findable
exactly when it is least useful.

Now confirm that nothing anywhere complains:

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate \
  days/day-25-skills-the-open-spec/lab/skills/vague-description
```

**Line by line:**

- The format's own validator, pointed at the failing skill.

```text
Valid skill: days\day-25-skills-the-open-spec\lab\skills\vague-description
```

**Valid.** That single line is the whole failure lab. Every automated check the format offers is green
on a skill that will never be used, and the cost of it — 20 tokens of card, on every request, forever
([3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md)) — is paid indefinitely for
nothing.

**And now the ablation.** Take the good description and delete only its second sentence — the *"Use
when"* half — leaving the first sentence intact and factually complete:

```text
request                                            bad-name  ticket-triage  vague-descrip
how urgent is ticket 4521?                                1              1              0
please triage this ticket                                 1              1              0
what severity should I give a login outage?               1              1              0
set the priority on 4522                                  0              0              0
can you help me with tickets                              0              0              1
total overlapping words                                   3              3              1
```

**Seven became three**, and *"set the priority on 4522"* went from a match to nothing. One sentence —
the one that most people leave out because the first sentence already says what the skill does —
carried **more than half** the findability.

## When it breaks

It does not break. That is the finding, stated as plainly as it can be stated.

There is no error, no warning, no failed validation, no exception, no log line. The agent answers the
request. The customer gets a reply. The skill sits in its folder, valid, costing tokens, contributing
nothing, and the only observable signal is an absence: an activation count that stays at zero.

Which is why the detection has to be built rather than caught:

**Count activations per skill.** Day 22's structured logging is already the right shape — one line per
happening, with a field for which skill fired. A skill with zero activations after a week of real
traffic is either unnecessary or unfindable, and those need different responses.

**Test the selection, not the output.** Day 30's skill testing includes asserting that a given request
activates a given skill. It is the only test that catches a description regression, and it is the test
nobody writes until this has happened once.

**And keep the requests that should have matched.** When somebody says *"it didn't use the triage
thing"*, that sentence is data. The words they used go into the description.

## In production

**Descriptions are tuned, not authored.** The realistic workflow is: ship, collect the requests that
should have activated a skill and did not, extract their vocabulary, and edit the card. The spec has a
page called *Optimizing skill descriptions* for exactly this reason, and the fact that it is a separate
page rather than a paragraph in the spec tells you how much of the difficulty lives here.

**Watch the activation rate as a first-class metric.** Not accuracy, not latency — *did the skill
fire*. It is one counter, it is nearly free, and it converts an invisible failure into a number that
goes to zero.

**What changes at scale** is that the failure inverts. With five skills the risk is not being chosen;
with five hundred it is being chosen wrongly, because several cards plausibly match every request and
the differences between them do the selecting. At that point a description has to say what the skill is
*not* for as well as what it is for, which is a much harder sentence to write and is Day 28's subject.

**The failure that only appears with real traffic** is vocabulary drift. The description was tuned
against last year's requests; the product renamed a concept; users now use a word that is not in any
card. Nothing errors, everything validates, and the activation rate falls slowly enough that no single
day looks wrong. Only the counter shows it.

**The review comment a senior engineer leaves:** *"this description tells me what it does. Now tell me
when — in the words a customer would use, not ours. And check the words against three real requests
before merging."*

**The interview question:** *"you've written a skill and the agent never uses it. What do you check?"*
The answer that shows you have debugged one: *"the description, first and probably last. It's the only
thing the model sees before choosing — the body isn't loaded yet — so if it doesn't contain the words a
real request contains, the skill is invisible. Everything else validates fine, which is what makes it
confusing: there's no error, the agent just answers without it. I'd look at the actual requests that
should have triggered it and put their vocabulary in the card, and I'd add a counter so I find out next
time from a number rather than from someone mentioning it."*
