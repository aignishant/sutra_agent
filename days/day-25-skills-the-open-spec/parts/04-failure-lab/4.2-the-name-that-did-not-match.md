# 4.2 — 💥 The name that did not match

## One-line answer

One badly-typed `name` produced **three** validation failures at once — lowercase, consecutive hyphens,
and the directory mismatch — and the value of this failure is precisely that it is loud, immediate and
enumerated, which is what [4.1](4.1-the-skill-that-never-triggered.md)'s failure is not.

## The story

The exam hall has a register and a boy with the wrong name on his paper.

He wrote *Rajeev* in the box because that is what everyone calls him. The register says *Rajiv*,
because that is what his birth certificate says, and the invigilator walking the rows with a clipboard
stops at his desk because the two do not match.

It takes forty seconds to sort out. He is not sent away, nothing is lost, and the paper gets the right
name on it before he starts.

Now imagine the invigilator did not check. The paper is marked, the mark is entered against a name that
matches nobody, and it is found in August when a boy who sat an exam has no result for it. The
forty-second interruption existed to prevent a problem that would otherwise surface months later,
attached to no obvious cause.

## The idea in plain language

[2.2](../02-the-frontmatter/2.2-the-name-field.md) listed the five rules on `name`. This part is about
what happens when they are broken, and — more usefully — about **what a good failure looks like**,
because this day has one of each and the contrast is the lesson.

The five rules again, with what each protects:

| Rule | Broken by | Protects |
| --- | --- | --- |
| 1–64 characters | an essay | log fields, directory names |
| lowercase alphanumerics and hyphens | `Ticket_Triage` | shell arguments, URLs, case-sensitive filesystems |
| no leading or trailing hyphen | `-triage` | splitting and joining without empty segments |
| no consecutive hyphens | `ticket--triage` | the same, and readability |
| matches the parent directory | a rename done halfway | the folder being the identity |

The fifth is the one that catches people, and it catches them in a specific situation: **a rename done
in one place.** You improve a skill's name, you edit the frontmatter, and the folder still has the old
name — or you rename the folder in a file browser and never open the file. Both leave a skill that is
internally consistent and externally wrong.

And there is a version of this that is not a typo at all. Copying a skill to start a new one — the most
natural way to write the second skill you ever write — produces a folder with a new name and a
frontmatter with the old one, every single time, unless you remember.

## Why Sutra needs it

Because the name is the key that every ledger, log line and lint uses, and Sutra is about to have
several of each.

`docs/SKILL_PROVENANCE.md` has one row per skill, found by name. Day 22's log line records which skill
activated, by name. Day 31's lint reports by name. If the name in the file and the name of the folder
can differ, every one of those has two candidate answers and no way to choose — and the bug does not
present as "a name is wrong", it presents as a provenance row that matches nothing and a log line
nobody can trace to a folder.

The rule exists so that this cannot happen, and the validator exists so that breaking it costs ten
seconds rather than an afternoon.

## The mechanism

One file with three problems in a single field:

```text
---
name: Ticket--Triage
description: Assign a severity to a support ticket. Use when a ticket has no severity.
---

# Ticket triage

This file is meant to be INVALID. Three rules are broken at once: an uppercase letter,
consecutive hyphens, and a name that does not match the parent directory.
```

**Line by line:**

- `Ticket--Triage` is written the way a person writes a **title**: capitalised, with a separator between
  words. That is exactly how this mistake happens — the name field looks like a place for a label, and
  it is a place for an identifier.
- The capital `T` breaks rule 2. The `--` breaks rule 4. And the file lives in
  `lab/skills/bad-name/`, so rule 5 is broken as well.
- The `description` is deliberately **fine** — it has a what and a when — so that the validator's
  output is unambiguous. A specimen that breaks two things at once teaches neither.
- The body announces that the file is a specimen. A deliberately-broken file with no explanation in it
  is a file somebody will try to fix in six months.

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate \
  days/day-25-skills-the-open-spec/lab/skills/bad-name
```

**Line by line:**

- The validator takes a **directory**, which is what lets it check rule 5 at all — a file-based checker
  could never see the mismatch ([2.2](../02-the-frontmatter/2.2-the-name-field.md)).
- Exit status is non-zero on failure, which is what makes this usable in `./m check` on Day 31 rather
  than only by eye.

Measured on 2026-09-04 against `skills-ref` 0.1.1:

```text
Validation failed for days\day-25-skills-the-open-spec\lab\skills\bad-name:
  - Skill name 'Ticket--Triage' must be lowercase
  - Skill name cannot contain consecutive hyphens
  - Directory name 'bad-name' must match skill name 'Ticket--Triage'
```

**Four things about that output are worth more than the fact that it failed.**

**It reports all three, not the first.** A validator that stops at the first problem turns one fix into
three runs. This one lets you fix everything in a single edit, which is the difference between a check
people run and a check people avoid.

**Each line names the rule in words.** Not `E002: invalid name` — *"cannot contain consecutive
hyphens"*. Nobody has to look anything up.

**Each line quotes the offending value.** `'Ticket--Triage'` appears in every message, and the third
line quotes **both** values it is comparing. With a hundred skills in a directory, a message that does
not include the value is a message you have to go and match up by hand.

**And the third line could not have come from reading the file.** `Directory name 'bad-name' must match
skill name 'Ticket--Triage'` required knowing where the file was. That is the cross-file rule being
enforced, and it is the reason the tool's argument is a folder.

**Now the contrast that makes this a failure lab part.** Put the two failures of this day side by side:

| | 4.1 — bad description | 4.2 — bad name |
| --- | --- | --- |
| Validator says | `Valid skill` | three named failures |
| When you find out | never, or from a counter | in ten seconds |
| Cost of the fix | rewriting and re-tuning | one edit |
| Cost of not fixing | a skill that is never used | nothing runs at all |

**The loud failure is the cheap one.** Every property that makes 4.2 annoying — it refuses, it lists
everything, it will not let you proceed — is what makes it harmless. The failure that lets you carry on
is the expensive one.

That is the general lesson worth taking out of the day: when you design a check, **make the thing you
can detect fail loudly**, because everything you cannot detect will fail quietly and you will need the
budget of attention for that.

## When it breaks

The three messages above are the failure. What is worth adding is the shapes that produce them in real
work, because none of them is somebody typing a title into a name field on purpose.

**A half-done rename.** `git mv skills/triage skills/ticket-triage` and no edit to the file. The
validator refuses, names both values, and the fix is one line. Ten seconds, and the reason it is ten
seconds is that rule 5 exists.

**A copied skill.** `cp -r skills/ticket-triage skills/refund-check` produces a folder called
`refund-check` containing `name: ticket-triage`. Without the rule, you would now have two skills with
one name and a client picking whichever it loaded last — a genuinely horrible bug to diagnose from the
model's behaviour. With the rule, the copy refuses to validate until you edit it, which you were going
to do anyway.

**A name from a different world.** `Ticket_Triage` from a codebase where identifiers use underscores;
`ticketTriage` from one where they are camel-case. Both refuse, both name the rule.

And the one the validator cannot catch, for completeness: a name that is valid, matches its folder, and
is `skill-2`. Nothing is broken. Nothing is findable either. That is
[4.1](4.1-the-skill-that-never-triggered.md)'s territory, arriving through the shorter field.

## In production

**The validator goes in the gate, not in a habit.** A check that depends on somebody remembering to run
it is a check that runs on the days it is not needed. Day 31 wires the skills lint into `./m check`,
and the non-zero exit status above is the whole integration.

**Validate on the way in as well as on the way out.** A third-party skill is validated before it is
added, not after somebody notices it misbehaving — and the same command does both jobs, which is one of
the benefits of an open format with a reference implementation
([1.3](../01-what-a-skill-is/1.3-an-open-spec.md)).

**What changes at scale** is that the mismatch stops being a typo and starts being a build problem.
Skills generated from templates, synced from another repository, or unpacked from an archive can all
arrive with names that disagree with their directories, and the failure is then in a pipeline rather
than in an editor. The validator's exit status is what turns that into a red build instead of a
mystery.

**The failure that only appears with real traffic** is the name collision the rule does *not* prevent.
Rule 5 guarantees uniqueness within a directory; it says nothing about two directories. A bundled
`triage` and a vendor `triage`, loaded from two paths, are both valid and the client decides which
wins — quietly. Prefixing by owner is the defence, and the moment to adopt it is before the second
source exists.

**The review comment a senior engineer leaves:** *"this was copied from `ticket-triage` and the name
field came with it. The validator would have caught it — is it in the gate yet?"*

**The interview question:** *"what makes a good validation error?"* The answer that shows you have read
a lot of them: *"it reports everything it found rather than the first thing, it names the rule in words
rather than a code, and it quotes the offending value — and where it's comparing two things, both of
them. The skills validator does all three: three findings from one bad name, each naming the rule and
quoting the value. And I'd rather have that kind of failure than a silent one, because the loud
failures are the cheap ones."*

## Check yourself

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate \
  days/day-25-skills-the-open-spec/lab/skills/bad-name
echo "exit status: $?"
```

Three findings and a non-zero status. Now fix only the capital letter, run it again, and count what is
left — that is what "reports everything" buys you.

**Out loud, without scrolling up:** say which of the three findings could not have been produced by
reading the file alone, and say why this failure is cheaper than the one before it.
