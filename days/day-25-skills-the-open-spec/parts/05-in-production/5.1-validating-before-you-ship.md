# 5.1 — Validating before you ship

## One-line answer

`agentskills validate` exits **1** with a named list of failures and **0** on a valid skill, which is
everything a gate needs — and the command is `agentskills`, not the `skills-ref` the specification
page names, which is what running it rather than trusting it discovered.

## The story

The printer sends you a proof and asks you to sign it before the run.

One sheet, the same paper, the same ink, the same fold. You are meant to read it properly — the phone
number, the date, the spelling of the street — and then write your name on it, because after that the
machine runs and there are ten thousand of them.

Nobody enjoys the proof. It arrives when you have already finished the design and want to be done. And
every printer insists on it, because the alternative is a pallet of leaflets with a transposed digit in
the phone number and a conversation about who is paying for them.

## The idea in plain language

A skill is text, so it can be checked before anything runs it. That sounds obvious and it is the direct
consequence of the format being open with a reference implementation
([1.3](../01-what-a-skill-is/1.3-an-open-spec.md)): validation needs a parser, not an agent.

`skills-ref` — version **0.1.1** on PyPI, requiring Python 3.11+, verified 2026-09-04 — supplies it.
Three commands, and the first is the gate:

| Command | Answers |
| --- | --- |
| `validate` | is this a legal skill? |
| `read-properties` | what does its frontmatter say, as JSON? |
| `to-prompt` | what would a client put in the model's context? |

For a gate, only two properties matter: it says **what** is wrong in words, and it **exits non-zero**.
The first makes it usable by a person, the second makes it usable by `./m check`.

And there is a discrepancy worth meeting now rather than in six months. The specification page says:

> Use the `skills-ref` reference library to validate your skills:
> `skills-ref validate ./my-skill`

Run that and the shell says:

```text
error: Failed to spawn: `skills-ref`
  Caused by: program not found
```

The package's actual entry point, read from its own metadata, is
`agentskills = skills_ref.cli:main`. The **package name** is `skills-ref`; the **command** is
`agentskills`. The documentation is one line stale, and the way to find that out is to run it.

That is not a complaint about the spec, which is a careful document on a fast-moving format. It is
Principle 8 — never invent an API — arriving in miniature, on a day when the thing being verified is
not even ADK. **Read the docs, then run the thing, and when they disagree the thing wins.**

## Why Sutra needs it

Because Day 31 puts a skills lint in `./m check`, and this command is what it will be built on.

`./m check` already runs ruff, ruff format, pytest, the depth contract, traceability and the wiki. Each
of those is a program that exits non-zero when something is wrong, and that is the entire contract the
gate needs. `agentskills validate` fits it exactly — verified on 2026-09-04, a failing skill exits
`1` — so the integration is a loop over the skills directory and a check of the status.

It matters more for skills that arrive from elsewhere. Day 29 sources third-party skills and records
each one in `docs/SKILL_PROVENANCE.md` before it runs. **Validating is the first step of that audit**,
and it is the cheap one: a skill that does not even parse never reaches the expensive step, which is a
human reading its `scripts/`.

## The mechanism

The three commands, on the skills this day built.

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills validate \
  days/day-25-skills-the-open-spec/lab/skills/ticket-triage
echo "exit status: $?"
```

**Line by line:**

- `--no-project` keeps `pyproject.toml` and `uv.lock` untouched, so this is an evaluation rather than
  an adoption. When Sutra adopts the tool properly it becomes a dev dependency with a dated row in
  `docs/PACKAGES.md` — the hub's §3 says when.
- `==0.1.1` pins the exact version verified against `pypi.org/pypi/skills-ref/json` on 2026-09-04.
  A version-zero package on a moving spec will change; an unpinned one changes without telling you.
- `echo "exit status: $?"` prints the status of the previous command. **This is the line that matters
  for a gate**, and it is the one people forget to check when evaluating a validator.

Measured on 2026-09-04:

```text
Valid skill: days\day-25-skills-the-open-spec\lab\skills\ticket-triage
exit status: 0
```

And on the deliberately broken one from
[4.2](../04-failure-lab/4.2-the-name-that-did-not-match.md):

```text
Validation failed for days\day-25-skills-the-open-spec\lab\skills\bad-name:
  - Skill name 'Ticket--Triage' must be lowercase
  - Skill name cannot contain consecutive hyphens
  - Directory name 'bad-name' must match skill name 'Ticket--Triage'
exit status: 1
```

**Zero and one.** That is the whole interface a gate needs, and everything above the status line is for
the person who has to fix it.

The second command answers a different question — *what does this skill declare?* — in a form a script
can use:

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills read-properties \
  days/day-25-skills-the-open-spec/lab/skills/ticket-triage
```

**Line by line:**

- Emits the frontmatter as JSON. This is what a provenance script consumes to fill in
  `SKILL_PROVENANCE.md`: name, licence, and whatever is in `metadata`, without anybody writing a YAML
  parser.

```text
{
  "name": "ticket-triage",
  "description": "Assign a severity to a support ticket and record it, using the desk's published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.",
  "license": "Apache-2.0",
  "compatibility": "Requires the Sutra desk tools and Python 3.12",
  "metadata": {
    "author": "sutra-desk",
    "version": "1.0"
  }
}
```

And the third answers the question this day has been circling: **what does the model actually see?**

```bash
uv run --no-project --with skills-ref==0.1.1 agentskills to-prompt \
  days/day-25-skills-the-open-spec/lab/skills/ticket-triage \
  days/day-25-skills-the-open-spec/lab/skills/vague-description
```

**Line by line:**

- Takes several skill directories and emits the block a client puts in the system prompt. It is the
  closest thing to a rehearsal of selection that can be run without a model.

```text
<available_skills>
<skill>
<name>
ticket-triage
</name>
<description>
Assign a severity to a support ticket and record it, using the desk&#x27;s published severity table. Use when a ticket arrives without a severity, when someone asks how urgent a ticket is, or when the words triage, severity or priority appear.
</description>
<location>
...\lab\skills\ticket-triage\SKILL.md
</location>
</skill>
```

**Two things in that output are review material rather than curiosities.**

`&#x27;` is the apostrophe in *"desk's"*, HTML-escaped. The block is XML, so text is escaped, and a
description full of quotes and ampersands costs more tokens than its character count suggests
([24.1.1](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.1-a-ticket-id-costs-five-tokens.md)
measured exactly this effect for JSON). A small argument for plain prose in a description.

And `<location>` is an **absolute path**, which means it differs between machines, appears in the
model's context, and may leak a directory structure into a prompt. It is worth knowing it is there
before somebody notices it in a log.

## When it breaks

The failure this part exists for is running the documented command:

```text
error: Failed to spawn: `skills-ref`
  Caused by: program not found
```

Three seconds of confusion, and the fix is to ask the package rather than the page:

```bash
uv run --no-project --with skills-ref==0.1.1 python -c \
  "import importlib.metadata as m; print(list(m.distribution('skills-ref').entry_points))"
```

**Line by line:**

- `importlib.metadata.distribution(...).entry_points` lists what a package installs as commands. It is
  the authoritative answer, it needs no documentation, and it works for any installed package — which
  makes it worth memorising.

```text
[EntryPoint(name='agentskills', value='skills_ref.cli:main', group='console_scripts')]
```

`name='agentskills'`. The documentation said otherwise; the package is right.

The other failure is the validator's own scope, and it is the most important sentence in this part:
**it validates the format and nothing else.** It said `Valid skill` about
[4.1](../04-failure-lab/4.1-the-skill-that-never-triggered.md)'s useless description. It will say
`Valid skill` about a body that names tools which do not exist, a link pointing at a missing reference
file, a script that does not run, and a licence that is a lie.

Which means a gate built only on this command is checking the cheapest third of what matters. The other
two thirds — links resolve, tool names exist, the description contains real request vocabulary — are
Sutra's own lint to write, and Day 31 is where.

## In production

**Validation runs in three places, not one.** On a developer's machine before a commit; in CI on every
change; and on the way in, when a skill arrives from outside. The same command does all three, which is
the practical value of the format being checkable without a runtime.

**The house lint is bigger than the spec's validator, and that is expected.** A published validator has
to accept everything the format permits. Your lint may refuse things the format permits but your team
does not want: a missing licence, a `metadata.version` that is absent, a description under some minimum
length, a `SKILL.md` over a line count. The two are complementary — the validator says *legal*, the
lint says *ours*.

**What changes at scale** is that validation becomes an inventory. Running `read-properties` across
every skill and collecting the output gives a table of everything installed, with owners, licences and
versions — which is what makes questions like *"which skills have no owner"* and *"which are on a
licence we cannot ship"* answerable in a command rather than a survey.

**The failure that only appears with real traffic** is the skill that validates and does not work,
because the client it runs in cannot do what it assumes. The format is portable; the environment is not
([1.3](../01-what-a-skill-is/1.3-an-open-spec.md)). Validation is necessary and nowhere near
sufficient, and the only complete check is running the skill against a real request — which is Day 30.

**The review comment a senior engineer leaves:** *"we validate on commit but not on the skills we pull
in from the vendor pack. Validate on the way in too — it's the same command and it's the cheapest step
of the audit."*

**The interview question:** *"how do you check a skill before shipping it?"* The answer that shows you
have wired a gate: *"the reference validator for format — it names every failure and exits non-zero, so
it drops straight into CI. But it only checks the format, so it'll happily pass a skill with a useless
description or a broken link to a reference file. Those need a house lint. And the thing I'd tell
anyone starting: run the command the docs give you, because on the version I used the documented
command name didn't exist — the package installs a different one."*
