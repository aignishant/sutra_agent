# 5.2 — What a skill costs at startup

## One-line answer

Three skills cost **115 tokens** of permanent context between them, so a library of two hundred at the
same size would cost about **7,600 tokens on every request** — paid whether any of them is used, which
is the real ceiling on how many skills a system can carry.

## The story

You walk into the trade fair and somebody puts a leaflet in your hand, and then somebody else does.

By the time you reach the far end of the hall you are carrying eleven of them and you have read the top
line of about three. You did not choose any of it. Every stand's leaflet is designed on the assumption
that you might be interested in that stand, and each one is individually reasonable, and the sum of
them is a wad of paper you will put in a bin by the exit.

The stands are not competing for your attention one at a time. They are competing with the pile — and
the twelfth leaflet is fighting ten others you are already holding, not just the person handing it to
you.

## The idea in plain language

[3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md) established the three levels and
the crucial asymmetry: levels two and three are **conditional**, and level one is not.

> **Metadata** (~100 tokens): The `name` and `description` fields are loaded at startup **for all
> skills**.

That is a fixed cost, and fixed costs have a different arithmetic from conditional ones.

A skill's body costs tokens **times the number of requests that activate it**. If it is a good skill
used one request in five, the expected cost is a fifth of the body. Improve the skill, add a section,
and the extra cost lands only on the requests that use it.

A skill's card costs tokens **times every request the system ever serves**. Not the requests where it
is relevant — all of them. Adding a skill to a library is a permanent tax on every future request,
including all the ones with nothing to do with it.

Which produces the number that governs skill library design:

> **fixed cost = (average card size) × (number of skills)**

And on a per-request tier ([24.1.3](../../../day-24-token-accounting-and-budgets/parts/01-what-a-request-costs/1.3-the-unit-that-gets-rationed.md))
there is a second effect people miss: tokens are not what is rationed, so the fixed cost does not
directly reduce the number of requests you can make. What it reduces is the **room left in the window**
— for the conversation, for tool results, for compaction summaries, for the skill body when one is
finally activated. It competes with the work, not with the quota.

So there are two ceilings on a skill library and they are different:

- **The context ceiling.** Cards plus conversation must fit, and the cards are the part that never
  shrinks.
- **The selection ceiling.** Past some number of plausibly-similar cards, the model chooses less
  reliably — which is a quality problem before it is a size problem, and is Day 28's subject.

## Why Sutra needs it

Because Phase 4 lasts seven days and the natural output of seven days on skills is a lot of skills.

Sutra will finish Phase 4 with skills it wrote (Day 27), skills it sourced from elsewhere (Day 29), and
a lint keeping them tidy (Day 31). Every one of them adds to a number that is paid on every request
including the ones that answer *"what is our refund window"* from the handbook.

Day 19 gave Sutra a budget per organ of the request and Day 24 gave it a budget in requests. Skills are
a **new organ** and they arrived after both budgets were set. The number below is what has to be added
to Day 19's table, and knowing it now — before there are twenty skills — is what makes it a design
constraint rather than an incident.

## The mechanism

Measure the fixed cost and project it.

```python
# days/day-25-skills-the-open-spec/lab/what_a_skill_costs.py
    print(f"\n{len(list(SKILLS.iterdir()))} skills cost {startup_total} tokens at startup")
    for n in (10, 50, 200):
        print(f"  {n:>3} skills of this size would cost about {startup_total // 3 * n:>6} tokens")
```

**Line by line:**

- `startup_total` is the sum of the card sizes measured earlier in the script — `name` and
  `description` wrapped in the tags a client uses
  ([3.3](../03-the-body-and-the-folders/3.3-progressive-disclosure.md)). Bodies are excluded, because
  bodies are not part of the fixed cost.
- `startup_total // 3` is the **average** card across the three skills in the lab, and integer division
  is honest here: a fractional token is not a thing, and rounding down keeps the projection
  conservative.
- The projection multiplies rather than measuring, and that is the assumption to be explicit about: it
  assumes two hundred skills would have cards of the same average size as these three. A real library
  skews larger, because a real skill has a more careful description than `Helps with tickets.` — so
  **7,600 is a floor, not an estimate**.
- Three points — 10, 50, 200 — rather than one, because the shape matters more than any single number.
  The cost is linear in the number of skills, which is the whole point: there is no economy of scale in
  a skill library.

**Line by line:**

Measured on 2026-09-04 against `gemini-3.7-flash`:

```text
skill                 startup  activated   ratio
bad-name                   31         72     2.3x
ticket-triage              64        292     4.6x
vague-description          20         55     2.8x

3 skills cost 115 tokens at startup
   10 skills of this size would cost about    380 tokens
   50 skills of this size would cost about   1900 tokens
  200 skills of this size would cost about   7600 tokens
```

**Start with the top of the table, because it contains the design lever.**

`ticket-triage` costs **64** and `vague-description` costs **20**. The difference is not that one skill
is bigger — it is that one has a description that says what it does *and when to use it*, and the other
has three words. **Findability costs about 44 tokens, permanently.** That is the price of
[2.3](../02-the-frontmatter/2.3-the-description-field.md), stated as a number, and it is obviously
worth paying: a 20-token card that is never selected is 20 tokens spent on nothing at all.

**Now the projection.** Ten skills is 380 tokens — invisible. Fifty is 1,900 — noticeable beside Day 19's
organ budgets. Two hundred is **7,600 tokens on every request**, which for a model with a large window
is affordable and for the conversation sharing that window is a real subtraction.

And the shape is **linear**. There is no point at which adding skills gets cheaper, and no compaction
step for cards the way [Day 20](../../../day-20-context-engineering-compaction/LESSON.md) compacts
history. Every skill you keep is a skill you pay for on every request until you delete it.

Which gives the operational conclusion, and it is not the one people expect: **the expensive skills are
the unused ones.** A skill activated often earns its card many times over — 4.6× the knowledge for the
cost, by the ratio column. A skill never activated is pure fixed cost. So the discipline that keeps a
library affordable is not writing shorter descriptions; it is **deleting skills that do not fire**,
which requires knowing which ones do — a counter, from Day 22.

## When it breaks

Nothing errors. There is no message anywhere that says the skill library has become expensive, and the
symptoms arrive attached to other things.

**The window gets tight.** Compaction fires earlier than it used to
([Day 20](../../../day-20-context-engineering-compaction/LESSON.md)), or a long conversation starts
losing its earliest turns, and the cause is 7,000 tokens of cards that were added one at a time over
six months. Nobody connects the two, because each individual addition was 40 tokens.

**Selection gets worse.** With many similar cards the model picks less reliably, and the failure looks
like model quality rather than library size. That is
[4.1](../04-failure-lab/4.1-the-skill-that-never-triggered.md)'s failure arriving from the other
direction — not one bad description, but too many similar ones.

**And the ratio inverts without anybody noticing.** A library where the average card is 100 tokens and
the average skill fires once a week is spending far more on availability than on use. The number that
shows it is `activations ÷ requests` per skill, and almost nobody computes it until the window is
already tight.

There is one genuine error worth naming, from the day this was written. `to-prompt`'s output includes
`<location>` with an **absolute path**
([5.1](5.1-validating-before-you-ship.md)) — which is real tokens per skill for a string the model
almost never needs, and which differs between machines. Whether a given client includes it is the
client's decision, and it is worth checking rather than assuming, because on a two-hundred-skill
library a long path per card is a meaningful fraction of the fixed cost.

## In production

**The library gets a token budget, written down.** *"All skill cards together may not exceed N
tokens"*, enforced in the lint, for the same reason Day 19 gave each organ of the request a budget: a
limit that is not enforced is a limit that is discovered. The number comes from what is left after the
conversation, the tools and the instruction have had their share.

**Skills are audited for use, not just for correctness.** Once a quarter, list every skill by activation
count and delete the zeros — after checking whether they are unused because they are unnecessary or
unfindable, which are different problems with different fixes
([4.1](../04-failure-lab/4.1-the-skill-that-never-triggered.md)).

**What changes at scale** is that clients stop loading every card. Past some library size the sensible
design is to select candidate skills *before* the model sees them — by directory, by user role, by a
retrieval step over the descriptions — so that a request sees ten cards rather than two hundred. That
is a client capability rather than a format one, and it changes the fixed cost from *"every skill"* to
*"every candidate"*, which is the only thing that makes very large libraries possible.

**The failure that only appears with real traffic** is a library that is affordable in aggregate and
badly distributed. Fifty skills at 40 tokens is fine; forty-nine at 30 and one at 800, because somebody
put a worked example in a description, is the same total and a much worse library — the long card
crowds the others in the model's attention as well as in the window. Measuring the average hides it;
measuring the maximum does not.

**The review comment a senior engineer leaves:** *"we're at fifty skills and nobody has measured what
the cards cost. Run the count before we add the vendor pack, because that's another thirty and the
number is linear."*

**The interview question:** *"what limits how many skills an agent can have?"* The answer that shows you
have counted: *"the metadata is loaded for every skill on every request, so the fixed cost is linear in
the library size — I measured about 64 tokens for a well-described skill, so two hundred is around
seven and a half thousand tokens before the conversation starts. It doesn't reduce how many requests you
can make on a per-request tier; it reduces the room left for the actual work. And past a certain number
selection quality degrades too, which usually bites first. The fix isn't shorter descriptions — it's
deleting skills that never fire, which means counting activations."*
