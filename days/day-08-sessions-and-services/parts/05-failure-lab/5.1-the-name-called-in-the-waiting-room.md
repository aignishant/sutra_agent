# 5.1 — 💥 The name called in the waiting room

## One-line answer

Today's deliberate failure is one bug — an address that does not match — wearing three different
faces: an exception, a `None`, and a log line nobody reads, and the three are worth producing on
purpose because you will only recognise the last two if you have seen them.

---

## The story

🎬 **The scene.** You are in a clinic waiting room with about twenty other people. You gave your name
at the desk an hour ago and sat down.

A nurse comes to the door with a file and calls a name. It is close to yours but not yours — a
different spelling, one syllable off. You half stand up, hesitate, and sit down again, because
twenty people are watching and you are not sure.

She calls it twice, waits, says "not here", and goes back in.

😬 **The naive fix.** You wait longer. The person at the desk clearly has your name; you watched them
write it. Your turn will come round again.

💥 **Why it fails.** It will not come round again. From the file's point of view, that patient was
called and did not answer, and the queue has moved on. You are in the room and you are in the
register — under a spelling nobody is going to say out loud. Everything is working perfectly. The
desk recorded a name, the nurse called the name that was recorded, and the two of you are in the
same room for another hour.

💡 **The insight.** The failure was not in the calling and not in the writing. It was that **the
written name and the spoken name were never checked against each other**, and there was no moment in
the process where anybody would have noticed. The fix is not to call louder. It is to read the name
back at the desk, once, at the start.

An agent that cannot find a session is in this waiting room. Today you put it there three times.

---

## The idea in plain language

The plan's §17.7 asks every day to carry a part whose subject is a deliberate failure. Today's is the
address from [1.2](../01-the-session/1.2-three-parts-to-one-key.md), broken on purpose in the three
places it can break.

What makes it worth a part rather than a warning is that **the same underlying mistake produces three
completely different symptoms**, and only one of them looks like a problem:

| Where the mismatch is | What you get | Loud? |
| --- | --- | --- |
| the runner's `app_name` vs the session's | `SessionNotFoundError` | yes |
| any part, on a direct `get_session` | `None` | no |
| any part, on `append_event` to an in-memory store | a log warning, and the event vanishes | no |

The first is a good failure. It stops, it names the session id, and you go and look.

The second is [1.2](../01-the-session/1.2-three-parts-to-one-key.md)'s near miss: a perfectly correct
answer to the question you asked, which was the wrong question. It becomes an `AttributeError` on
`NoneType` somewhere else, or — worse, with a get-then-create in the way — a brand new empty
conversation, which is
[4.2](../04-what-in-memory-means/4.2-two-counters-two-notebooks.md)'s split brain.

The third is the one this part exists for. `InMemorySessionService.append_event` looks the session up
**by the address on the session object you passed** ([3.2](../03-the-services/3.2-three-drawers-deep.md)).
If it does not find it, it logs and returns your event as though nothing happened. The method's
signature promises an `Event` and it gives you one. From the call site, success and failure are
identical.

And the reason all three are realistic rather than contrived: an app name has at least four sources
in a repository like yours, and you have already met three of them.

- `sutra/desk/run_once.py` says `APP_NAME = "sutra"`.
- `adk web` derived `"sutra.desk"` from a folder path
  ([Day 7, part 6.1](../../../day-07-events-and-streaming/parts/06-reading-a-run/6.1-the-camera-you-already-installed.md)).
- `InMemoryRunner` defaults to `"InMemoryRunner"`
  ([3.5](../03-the-services/3.5-the-furnished-flat.md)).
- And on Day 86 it will also come from an environment variable.

Four spellings of one name, in one repository, none of them wrong.

---

## Why Sutra needs it

**Today**, immediately: `sutra/desk/sessions.py` exists precisely so that `APP_NAME` has one home,
and this part is the argument for it.

**Day 85** puts Sutra behind an API server where the session id arrives from a client and the app
name from configuration, which is the first time the two can drift without anybody editing a Python
file.

**Day 86 and 88** deploy Sutra, where the app name becomes environment-dependent and this failure
becomes an operational one rather than a coding one.

**Day 22** builds structured logging, and one of the strongest arguments for it is that failure
number three has nowhere to be seen unless somebody is reading warnings.

And this is the part of today that **can go RED** (Principle 11): all three arms are deterministic
and cost nothing, so all three can be tests.

## The mechanism

Three arms, one script:

```python
# lab/mismatch.py - one bug, three faces. No model, no key, no cost.
import asyncio
import logging

logging.basicConfig(level=logging.WARNING, format="%(levelname)s:%(name)s:%(message)s")

from collections.abc import AsyncGenerator

from google.adk.agents import BaseAgent
from google.adk.agents.invocation_context import InvocationContext
from google.adk.events import Event
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types


class Echo(BaseAgent):
    async def _run_async_impl(self, ctx: InvocationContext) -> AsyncGenerator[Event, None]:
        yield Event(
            author=self.name,
            invocation_id=ctx.invocation_id,
            content=types.Content(role="model", parts=[types.Part(text="ok")]),
        )


async def main() -> None:
    service = InMemorySessionService()
    session = await service.create_session(app_name="sutra", user_id="local")
    print("the session really exists:", session.id)
    print()

    print("--- arm A: the runner's app_name does not match ---")
    runner = Runner(agent=Echo(name="echo"), app_name="sutra-desk", session_service=service)
    try:
        async for _ in runner.run_async(
            user_id="local",
            session_id=session.id,
            new_message=types.Content(role="user", parts=[types.Part(text="hi")]),
        ):
            pass
    except Exception as exc:
        print(f"    {type(exc).__name__}: {exc}")
    print()

    print("--- arm B: get_session with the wrong user_id ---")
    found = await service.get_session(app_name="sutra", user_id="Local", session_id=session.id)
    print("    returned:", type(found).__name__, "- no exception, no warning")
    print()

    print("--- arm C: append_event to an address the store does not know ---")
    stranger = await service.create_session(app_name="other-app", user_id="local")
    stranger.app_name = "sutra"
    returned = await service.append_event(stranger, Event(author="echo", invocation_id="run-x"))
    print("    append returned:", type(returned).__name__)
    after = await service.get_session(app_name="sutra", user_id="local", session_id=session.id)
    print("    events in the real session:", len(after.events))


asyncio.run(main())
```

**Line by line:**

- `logging.basicConfig(...)` before the ADK imports — arm C is *only* a log line, so without this the
  third arm produces no visible output at all. Which is, itself, the lesson.
- `class Echo(BaseAgent)` — one event, no model, so all three arms are free and arm A actually
  reaches the runner rather than dying on a missing key.
- `app_name="sutra-desk"` on the runner against a session created under `"sutra"` — a hyphen. Not a
  contrived string: it is the shape of every real version of this bug.
- `user_id="Local"` in arm B — a **capital L**. Chosen deliberately over an obviously-wrong value,
  because the realistic version of this mistake is a case difference from a form field or a header,
  not a typo you would spot.
- `stranger.app_name = "sutra"` in arm C — building a session whose address does not correspond to
  anything the store holds. `Session` is an ordinary Pydantic model and nothing stops you editing it,
  which is exactly how this happens in real code: a session gets rebuilt, deserialised, or copied
  with a field changed.
- `type(returned).__name__` printed — because the method returns an `Event` whether or not it stored
  anything, and seeing `Event` next to an unchanged count is the whole finding.
- The final `get_session` and event count — proving the event went nowhere. Checking `stranger` would
  not do: it is a copy, and [3.2](../03-the-services/3.2-three-drawers-deep.md) explained why.

The output:

```text
WARNING:google_adk.google.adk.sessions.in_memory_session_service:Failed to append event to session c89c97a9-9d82-4ed7-bd77-bc63f674e4db: session_id c89c97a9-9d82-4ed7-bd77-bc63f674e4db not in sessions[app_name][user_id]
the session really exists: 089b3db2-0e3d-4e38-b94a-9ca5d59019ac

--- arm A: the runner's app_name does not match ---
    SessionNotFoundError: Session not found: 089b3db2-0e3d-4e38-b94a-9ca5d59019ac

--- arm B: get_session with the wrong user_id ---
    returned: NoneType - no exception, no warning

--- arm C: append_event to an address the store does not know ---
    append returned: Event
    events in the real session: 0
```

Four things worth reading carefully.

**Arm A raises, and its message names the session id and nothing else.** Not the app name it looked
under, not the one the session has. So the most useful piece of information — *which two names
disagreed* — is not in the error. (ADK can sometimes add an alignment hint when it is able to infer
the agent's origin directory; it did not here, and you should not count on it.)

**Arm B is one word of output.** `NoneType`. That is the entire failure, and in real code there is no
output at all — just a variable that is `None` and a traceback three functions later.

**Arm C returned an `Event`.** The signature was honoured. Nothing was stored. And the real session
still has zero events, so the write is not merely misfiled, it is gone.

**And the warning printed first**, above the heading of the arm it belongs to, for the buffering
reason from [3.2](../03-the-services/3.2-three-drawers-deep.md). In a service this is not a cosmetic
problem: the warning goes to a log stream and the symptom appears in a user's chat window, and no
human ever sees the two together.

Note also that the id in the warning is **not** the id printed on the second line. It is the
`stranger` session's, which the store genuinely does not hold under that address — so the one piece
of identifying information the warning carries points at a session that, from the reader's point of
view, does not exist. Correct, and about as unhelpful as a correct message can be.

Now the fix, which is not clever:

```python
# sutra/desk/sessions.py - read the name back, once, at the start.
import logging

from google.adk.sessions import BaseSessionService

logger = logging.getLogger(__name__)

APP_NAME = "sutra"
USER_ID = "local"


def announce(service: BaseSessionService, *, app_name: str = APP_NAME) -> None:
    """Log the effective address once at startup. One line; saves an evening."""
    logger.info("sessions: app_name=%r store=%s", app_name, type(service).__name__)
```

**Line by line:**

- `logger = logging.getLogger(__name__)` — a module logger, named after the module, which is the
  standard shape and lets somebody silence or raise the level of exactly this without touching
  anything else.
- `app_name: str = APP_NAME` as a parameter with a default — so the function reports what is
  **actually being used** rather than what the constant says. The day the value starts coming from an
  environment variable, this line keeps telling the truth without being edited.
- `logger.info("...%r...", app_name)` with `%r` and **lazy formatting** — the arguments are passed to
  the logger rather than formatted into the string, which is the `logging` convention and means the
  formatting is skipped entirely when the level is off. `%r` shows quotes, so a trailing space is
  visible.
- `type(service).__name__` — the store as well as the name, because "which app name" and "which
  store" are the two questions an incident starts with, and they cost one line together.
- One function, no cleverness, no validation. It does not *prevent* the mismatch. It makes the
  mismatch **visible in the first ten lines of the log**, which is the same thing a nurse reading the
  name back at the desk does.

## When it breaks

This part is the break, so here are the three things that are **not** the cause and will absorb your
evening if you let them.

**💥 Not the store.** All three arms use one `InMemorySessionService`, holding one real session, the
whole time. Swapping it for SQLite changes nothing about any of them. The instinct on seeing "session
not found" is to suspect storage, and storage is working perfectly.

**💥 Not the session id.** In every arm the session id is correct and is passed correctly. This is
the hardest one to let go of, because the id is the part that *looks* like an identifier and the
other two look like configuration.

**💥 Not `auto_create_session`.** Turning it on removes arm A's exception and replaces it with a
brand-new empty session, which is worse. A setting that makes an error go away without fixing
anything is the most expensive kind of fix, and this is one.

The actual diagnostic is two lines, and it works before you run anything:

```python
print("runner  :", runner.app_name)
print("session :", session.app_name, session.user_id, session.id)
```

**Line by line:**

- `runner.app_name` — a public attribute, and the value the runner will actually search under. Not
  the constant you think it read; the value it has.
- All three parts of the session's own address on the second line, in the order they are matched, so
  a difference is a visual diff rather than a comparison you have to do in your head.
- Two `print` calls rather than an assertion — because at the moment you need this you do not yet
  know what the values *should* be, and an assertion that fails tells you less than two lines that
  show you.

## In production

**What a professional writes instead of the teaching version** is the `announce` function above,
called once at startup, plus the `fetch` from
[1.2](../01-the-session/1.2-three-parts-to-one-key.md) that raises with all three parts of the
address in the message. Together they turn all three arms into something a person can diagnose from a
log rather than from a reproduction. Neither is clever and neither prevents the bug; both make it
five minutes instead of an evening.

**What degrades at scale** is the number of sources for the name. One constant in one module is
fine. A constant, a default, an environment variable, a per-tenant record and a dev tool deriving one
from a folder path — which is roughly where a real system lands — means the effective value is the
output of a merge, and the merge is where the mismatch lives. Logging the effective value is the only
thing that keeps up with that, because it reports the answer rather than the inputs.

**The failure that only shows with real traffic** is arm C at volume. A silent append that loses one
event is invisible; a code path that silently loses one event per run, on a fraction of requests, is
a transcript with holes in it. Nobody reports it, because a conversation with one missing agent turn
still reads plausibly. It surfaces months later as "our evals disagree with what users say happened",
and reconstructing why is close to impossible after the fact.

**The review comment a senior engineer leaves:** *"`append_event` here can silently no-op if the
session's address doesn't match the store — we get a warning at whatever level nobody reads and the
event is gone. Assert the session came from `fetch()` rather than being constructed, and log the
effective app name at startup. Right now, if these two ever disagree, we find out from a customer."*

**The interview question:** *"tell me about a bug that was hard to diagnose."* This one is a good
honest answer because the difficulty is structural rather than exotic: "A session lookup that failed
three different ways depending on where the mismatch was. The app name was defined in four places in
one repo — a constant, a framework default, a name a dev tool derived from a folder, and an
environment variable — and none of them was wrong. When the runner's name disagreed we got a clean
exception. When a direct lookup disagreed we got `None`, which became an `AttributeError` three
frames later. And when an append disagreed we got a log warning and the event silently vanished,
with the method still returning normally, so the call site couldn't tell success from failure. What
actually fixed it wasn't clever: log the effective app name and store once at startup, and raise on a
failed lookup with all three parts of the address in the message. Both are one-liners and both turn
it into a five-minute diagnosis."
