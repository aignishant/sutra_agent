# 6.2 — The tray the driver cannot see

## One-line answer

The pinned SDK has the *question* — both elicitation modes, all three actions, the CIMD client id —
and lacks the *carriage*, the `iss` check and the extensions framework, so this day is half runnable
and you must know which half before you write a line.

## The story

The office printer has a second paper tray. You can see it. There is a sheet of A4 in it and a green
light on the front.

You send a document, choose the second tray, and it comes out of the first one. Not an error — the
job printed, the paper was the wrong size, and nothing anywhere said why. It takes a while to work
out that the driver installed on your machine is for the model without the extra tray. The tray is
physically there and the software has no concept of it, so the option you clicked was mapped to the
nearest thing the driver did understand.

The hardware and its driver disagree about what this printer is. Neither is broken. They are just
different documents about the same machine, written at different times.

## The idea in plain language

[Day 32 established the finding](../../../day-32-mcp-stateless-core/parts/05-failure-lab/5.1-the-tutorial-from-four-months-ago.md):
the `mcp` package pinned in this repository at `1.29.1` reports
`LATEST_PROTOCOL_VERSION = "2025-11-25"`, while the specification everything in Phase 5 is written
against is `2026-07-28`. That day's lesson was *a library is a document and it has a date*. This part
is the consequence for today's three subjects, measured rather than assumed.

The measurement matters because "the SDK is one revision behind" is not a single fact — it is a
different fact per feature. Some of today's mechanisms exist in `1.29.1` exactly as the newer
specification describes them. Some exist in an **older carriage**, doing the same job by a different
route. Some are simply absent.

Getting this wrong in either direction costs you. Assume everything is missing and you hand-roll
things the SDK already does correctly, including the elicitation types. Assume everything is present
and you write against `InputRequiredResult` and get an `AttributeError` at import time.

The way to find out is not to search the web. It is to read the installed package, because the
installed package is the only authority on what your code can call.

## Why Sutra needs it

Because `sutra_mcp/auth.py` and `sutra/mcp/auth.py` are being written today, and every symbol in them
either exists or does not.

The specific decisions this measurement settles:

- **Elicitation types**: import them from `mcp.types` or define them yourself?
- **The MRTR carriage**: is `InputRequiredResult` available, or does the server hand-build the result
  dict as [3.1](../03-the-question/3.1-the-job-that-stopped-and-left-a-number.md) does?
- **CIMD**: does the client pass a `client_metadata_url`, or is that a hand-rolled authorization
  request?
- **The `iss` check**: does the SDK do it, or is that entirely yours to write?
- **Extensions**: is there a type for the capability declaration, or is the `_meta` block hand-built?

And it settles one thing that is *not* a code decision: whether to bump the pin. **No.** A version
bump is a plan decision with a `docs/PACKAGES.md` row behind it and a check of every day that already
depends on the current behaviour. [Day 32 recorded the same finding and did not act on it](../../../day-32-mcp-stateless-core/parts/05-failure-lab/5.1-the-tutorial-from-four-months-ago.md);
this day records the shape of the gap and does not act on it either. Principle 14: if reality has
moved, the plan is amended first.

## The mechanism

A script that asks the installed package ten questions and counts the answers it does not like.

```python
# days/day-37-auth-and-elicitation/lab/sdk_surface.py  (extract)
def has_type(name: str) -> bool:
    """Is this symbol exported by mcp.types at all?"""
    return hasattr(t, name)


def source_of(module: str) -> str:
    """The text of an installed module, so a claim about it can be grepped rather than recalled."""
    return inspect.getsource(importlib.import_module(module))
```

**Line by line:**

- `hasattr(t, name)` on the imported `mcp.types` module is the honest test for "does this symbol
  exist", and it is better than `try: from mcp.types import X` because it does not need one import
  statement per question. A symbol that is absent returns `False` rather than raising.
- `inspect.getsource` returns the **text** of the installed module. That is deliberate and slightly
  crude: for questions like *does this file mention `iss` anywhere*, reading the source is a claim you
  can verify by opening the same file, whereas introspecting objects tells you only about the shapes
  that happened to be constructed. A grep over a file you can name is reproducible by a reader.
- `importlib.import_module` rather than a literal import, so the module name is a string that can sit
  in a table beside the question it answers. The output can then say *where* each answer came from,
  which is the difference between a report and an assertion.

```python
# days/day-37-auth-and-elicitation/lab/sdk_surface.py  (extract)
    checks: list[tuple[str, bool, str]] = [
        ("form mode elicitation", has_type("ElicitRequestFormParams"), "mcp.types"),
        ("url mode elicitation", has_type("ElicitRequestURLParams"), "mcp.types"),
        ("three-action result", has_type("ElicitResult"), "mcp.types"),
        ("elicit_url on the server session", "async def elicit_url" in session, "mcp.server.session"),
        ("MRTR carriage (InputRequiredResult)", has_type("InputRequiredResult"), "mcp.types"),
        ("requestState", "requestState" in source_of("mcp.types"), "mcp.types"),
        ("CIMD client_id", "client_metadata_url" in oauth2, "mcp.client.auth.oauth2"),
        ("RFC 9207 iss validation", '"iss"' in oauth2 or "iss=" in oauth2, "mcp.client.auth.oauth2"),
        ("token verification protocol", True, "mcp.server.auth.provider.TokenVerifier"),
        ("extensions negotiation", has_type("ExtensionCapability"), "mcp.types"),
    ]
```

**Line by line:**

- Each row is `(what today teaches, is it here, where the answer came from)`. The third element is
  what makes the output auditable: a reader who doubts a row opens that module and looks.
- The first three rows use `has_type` because these are exported classes. `ElicitRequestFormParams`
  and `ElicitRequestURLParams` are the two modes from
  [3.2](../03-the-question/3.2-a-form-the-till-can-print.md) and
  [4.1](../04-out-of-band/4.1-the-link-you-check-before-you-click.md); `ElicitResult` carries
  `action: Literal["accept", "decline", "cancel"]`, which is
  [3.3](../03-the-question/3.3-three-answers-not-two.md)'s three-way model, present exactly as taught.
- The fourth row greps for a **method definition** rather than a type, because `elicit_url` is
  behaviour on `ServerSession` and there is no class to test for.
- `"iss"` **with the quotes** is searched for, not the bare three letters, because `iss` appears
  inside `issuer`, `issued` and `dismiss`. A bare substring search would have returned `True` and told
  you the opposite of the truth — which is the single most likely way to get this measurement wrong.
- The token-verification row is a hard-coded `True` with the module path as its evidence, because that
  answer was established by reading `mcp/server/auth/provider.py` in
  [1.1](../01-the-badge/1.1-the-badge-the-desk-and-the-door.md) and
  [1.3](../01-the-badge/1.3-a-voucher-for-one-shop.md). Writing it as a literal with its source named
  is more honest than a grep that would pass for the wrong reason.
- `ExtensionCapability` is the name the extensions framework would need
  ([5.1](../05-policy/5.1-the-optional-extras-list.md)). Testing for a name that does not exist is a
  legitimate way to establish absence, provided you say which name you looked for — otherwise
  "absent" is unfalsifiable.
- The exit code is the count of `False` rows, so the script is an assertion as well as a report: it
  goes red when a mechanism this day teaches is not speakable by the pinned SDK, and it will change
  value the day somebody bumps the pin.

Run it — and note that this one needs the **virtual environment's** interpreter, because it imports
the pinned package:

```bash
.venv/Scripts/python.exe days/day-37-auth-and-elicitation/lab/sdk_surface.py; echo "exit: $?"
```

**Line by line:**

- From the repository root, on Git Bash for Windows. Every other script in this day runs on any
  Python 3.12 because they are standard library only; this one reads `mcp`, so it must be the
  interpreter that has it installed. **Zero generations, no network** — it reads files on disk.

Measured on 2026-09-04:

```text
pinned SDK speaks protocol : 2025-11-25

mechanism                             present   read from
------------------------------------------------------------------------------------------------
form mode elicitation                 True      mcp.types
url mode elicitation                  True      mcp.types
three-action result                   True      mcp.types
elicit_url on the server session      True      mcp.server.session
MRTR carriage (InputRequiredResult)   False     mcp.types
requestState                          False     mcp.types
CIMD client_id                        True      mcp.client.auth.oauth2
RFC 9207 iss validation               False     mcp.client.auth.oauth2
token verification protocol           True      mcp.server.auth.provider.TokenVerifier
extensions negotiation                False     mcp.types

mechanisms taught today that this SDK cannot speak: 4
exit: 4
```

**Six of ten present, four absent**, and the pattern in them is not random.

The **question** is fully there. Both modes, all three actions, the flat-schema validator, and
`ctx.elicit` / `ctx.elicit_url` on the server context. You can write a real elicitation today and run
it.

The **carriage** is not. `InputRequiredResult` and `requestState` do not exist, because `1.29.1`
speaks `2025-11-25`, where `elicitation/create` is a **server-initiated request** and the URL-mode
version is signalled by error code `-32042`, `URL_ELICITATION_REQUIRED`, carrying
`ElicitationRequiredErrorData`. Same question, older envelope. That is why
[3.1](../03-the-question/3.1-the-job-that-stopped-and-left-a-number.md) teaches the shape from the
specification and builds the dict by hand.

**Authorization is split.** CIMD is present — `client_metadata_url`, `is_valid_client_metadata_url`,
`should_use_client_metadata_url`, and a check for `client_id_metadata_document_supported`. The RFC
9207 `iss` validation is **not**: the callback handler's type is
`Callable[[], Awaitable[tuple[str, str | None]]]`, which returns the code and the state, and there is
no third slot for the issuer. Verified on 2026-09-04 in
`.venv/Lib/site-packages/mcp/client/auth/oauth2.py`, `mcp==1.29.1`. Section 2 is therefore entirely
yours to write, which is exactly why it got three parts.

**Extensions** are absent, as expected — the framework arrived in `2026-07-28`.

## When it breaks

The break if you write against the newer names:

```text
Traceback (most recent call last):
  File "sutra_mcp/auth.py", line 8, in <module>
    from mcp.types import InputRequiredResult
ImportError: cannot import name 'InputRequiredResult' from 'mcp.types' (C:\...\.venv\Lib\site-packages\mcp\types.py)
```

Loud, at import, before anything runs. That is the good kind of failure and it is why this
measurement is cheap to get wrong safely.

The break that is quiet is the `iss` one, and it is the reason this part sits in the production
section rather than as a footnote. Nothing raises. The SDK completes the authorization flow, returns
a token, and everything works — including the case where the response came from the wrong
authorization server. The absence of a check has no error message, which is
[2.1](../02-issuer-checks/2.1-which-desk-actually-answered.md)'s whole argument arriving as a
concrete property of the code on your disk.

The third break is the one to be careful about in your own measurement:

```text
RFC 9207 iss validation               True      mcp.client.auth.oauth2
```

That is what the row prints if you grep for the bare string `iss` instead of `"iss"`, because
`issuer` contains it. A measurement that returns the comfortable answer for a mechanical reason is
worse than no measurement, and it is the failure mode of every "does the library support X" script
ever written. Read the file when the answer surprises you.

## In production

**What a professional writes instead:** an assertion in the test suite, not a script somebody runs.
`tests/test_mcp_sdk_surface.py` asserts the exact set of symbols this codebase depends on, so a
dependency bump that removes or renames one fails the build with a message naming it. The version
string goes in the assertion too: when the SDK moves to a release that speaks `2026-07-28`, the test
goes red on purpose and somebody reads the migration notes. That is what
[Day 32 left as a `TODO(me)`](../../../day-32-mcp-stateless-core/parts/05-failure-lab/5.1-the-tutorial-from-four-months-ago.md)
and it is the same assertion.

**What degrades at scale:** the hand-rolled half. Every mechanism the SDK does not provide is code you
own, test and carry — the `iss` comparison, the `requestState` signing, the `InputRequiredResult`
shape, the extensions block. That is four things whose correctness is now your problem, and the debt
compounds with every day of Phase 5 that adds to them. The exit strategy is explicit: when the pin
moves, each hand-rolled piece has a named replacement, and the day that bumps the pin deletes them
rather than leaving both.

**The failure mode that only appears with real traffic:** the interoperability window. A server
speaking `2026-07-28` returns an `InputRequiredResult` to your `1.29.1` client, which does not know
that `resultType` and goes looking for tool content — the `KeyError` from
[3.1](../03-the-question/3.1-the-job-that-stopped-and-left-a-number.md). In development you test
against your own server and never see it. In production the servers are other people's, and they
upgrade on their own schedule. Handling an unknown `resultType` gracefully is cheap insurance and it
belongs in `sutra/mcp/client.py`.

**The review comment a senior engineer leaves:** *"this PR adds `mcp==2.1.1` to `pyproject.toml` to
get `InputRequiredResult`. That is a protocol revision change across every day from 32 onward, not a
dependency bump — it needs a plan amendment, a `PACKAGES.md` row and a pass over the client code. Put
the pin back and open the amendment; the hand-rolled shape works and is tested."*

**The interview question:** *"how do you find out whether your MCP SDK supports a feature?"* The
answer that shows you have been burned: *"read the installed package, not the docs and not the
changelog — the installed package is the only thing your code can actually call. We ran ten checks
against `mcp==1.29.1` and got a split that surprised us: elicitation is fully there, both modes and
the three-action result, but the 2026 MRTR carriage isn't, so `elicitation/create` is still a
server-initiated request with a `-32042` error for the URL case. CIMD is there and RFC 9207 `iss`
validation isn't — the callback returns code and state with no slot for the issuer, so that check is
ours to write. The trap is the measurement itself: grep for the bare string `iss` and you get a false
positive from the word `issuer`, and a script that returns the comfortable answer for a mechanical
reason is worse than not checking. We turned the whole thing into a test that asserts the symbol set,
so a bump fails the build instead of surprising us."*
