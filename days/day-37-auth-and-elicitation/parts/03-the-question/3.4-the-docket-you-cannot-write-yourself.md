# 3.4 — The docket you cannot write yourself

## One-line answer

`requestState` travels through the client, so the specification requires you to treat it as
**attacker-controlled input**: sign it, put the principal, an expiry and a digest of the original
request inside, and refuse anything that fails verification.

## The story

You drop a coat at the dry cleaner. They tear a numbered docket in half — one half goes in your
pocket, the other is stapled to the coat.

The docket is not a coat. It is not worth anything. It is a small piece of card whose only job is to
point at one item on one rail. And yet the whole system runs on it: you come back a week later, hand
over the half you were given, and get your coat, and neither of you has to remember anything about
the other.

Now think about what stops you writing your own. The number is printed, not handwritten. It is one
of a numbered book, so a made-up number does not match anything. If you cross out the number and
write a different one, the halves stop matching. And after a certain number of weeks, uncollected
items are dealt with anyway, so a docket from two years ago gets you nothing.

None of that is because they think you are a thief. It is because a piece of card that has been in
somebody's pocket is not a piece of card the shop can vouch for, and the shop's entire memory is
that card.

## The idea in plain language

`requestState` is the opaque string a server includes in its `InputRequiredResult`
([3.1](3.1-the-job-that-stopped-and-left-a-number.md)) and the client echoes back on the retry. Its
purpose is to let a stateless server remember what the first request was about, without storing
anything.

The client's obligations are simple and absolute: clients **MUST NOT** inspect, parse, modify or make
any assumption about the contents; if the result carried one, the retry **MUST** echo the exact value;
if it did not, the retry **MUST NOT** include one. Servers are free to encode it however they like —
base64-encoded JSON, an encrypted JWT, serialised binary. And a server **MUST** include at least one
of `inputRequests` or `requestState` in every `InputRequiredResult`.

Now the part that matters. The string spent time in somebody else's program. The specification
therefore states, in normative language: if a client request contains a `requestState`, servers
**MUST** treat it as **attacker-controlled input**. If it influences authorization, resource access or
business logic, servers **MUST** protect its integrity — HMAC or AEAD are the named options — and
**MUST** reject state that fails verification. Integrity protection **MAY** be omitted only when
tampering can cause nothing worse than the request failing.

Two terms, defined.

**HMAC** stands for hash-based message authentication code. You take the payload and a secret key,
run them through a hash function, and get a short tag. Anybody holding the key can recompute the tag
and check it matches; anybody without the key cannot produce a valid tag for a payload they changed.
It does not hide the payload — anybody can read it — it only proves the payload has not been altered
since you signed it.

**AEAD** stands for authenticated encryption with associated data. It does the same integrity job and
also encrypts, so the payload is unreadable as well as unforgeable. The specification's own example
`InputRequiredResult` uses the placeholder string `"AEAD-protected blob"`, which tells you what shape
they have in mind. Use AEAD when the state contains something the client should not read; HMAC is
enough when it only contains things the client already knows.

Then there is a replay list, which is the part people skip. To prevent replay, servers **SHOULD**
include the following inside the integrity-protected payload and verify each on receipt:

- **the authenticated principal**, rejecting state presented by a different principal;
- **a short expiry (TTL)**, rejecting state presented after it lapses;
- **an identifier for the originating request** — the method name and a digest of its salient
  parameters — rejecting state presented on a request that does not match.

And a warning attached to that list: these measures bound the replay window and prevent cross-user
and cross-request reuse, but do **not** guarantee single use. If a given `requestState` must be
consumed at most once — a one-time redemption — the server **MUST** enforce that invariant itself,
server-side. That is the one case where statelessness runs out and you need a store.

## Why Sutra needs it

Because `sutra_mcp/auth.py` is where the signing key is read and where the verification lives, and
because the alternative design is the one everybody writes first.

The alternative is a dictionary: `PENDING[request_id] = context`, returned as an opaque handle,
looked up on the retry. It works perfectly on one process and fails the moment there are two, which
is [Day 43](../../../day-43-stateless-by-default/)'s entire subject and
[Day 32's measurement](../../../day-32-mcp-stateless-core/parts/02-the-reframe/2.2-three-instances-one-url.md):
three instances, one held session, two of four requests refused on the happy path.

Signed state is the same idea as
[Day 32's payload handles](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md),
with one addition that makes it safe rather than merely convenient: the handle carries a tag proving
the server minted it. A handle without that is a number the client can guess.

The three replay defences also do specific work for Sutra. The principal check is what stops one
support agent's confirmation being used to close another agent's ticket. The expiry is what stops a
confirmation from last week being replayed today. The parameter digest is what stops a user
confirming *"close ticket 4521"* and the retry arriving with `ticket_id` changed to `9999` — an
attack that needs no cryptography at all, only an edited JSON field.

## The mechanism

Mint and verify, with the three replay defences inside the signed payload.

```python
# days/day-37-auth-and-elicitation/lab/request_state.py  (extract)
# In a real server this comes from the environment, never from a literal (Principle 9).
SECRET = os.environ.get("SUTRA_STATE_KEY", "dev-only-not-a-real-key").encode()
TTL_SECONDS = 300


def mint(principal: str, method: str, params: dict[str, object], now: int) -> str:
    """Pack the context the retry will need, then sign it."""
    payload = {
        "sub": principal,
        "method": method,
        "digest": hashlib.sha256(json.dumps(params, sort_keys=True).encode()).hexdigest()[:16],
        "exp": now + TTL_SECONDS,
    }
    body = base64.urlsafe_b64encode(json.dumps(payload, sort_keys=True).encode()).decode()
    tag = hmac.new(SECRET, body.encode(), hashlib.sha256).hexdigest()[:32]
    return f"v1.{body}.{tag}"
```

**Line by line:**

- `SECRET` comes from `os.environ`, with a development fallback that is *named* as one. That is
  Principle 9 in a file about credentials: a key literal in a repository is a key in every clone of
  that repository, for ever. The fallback exists so the lab runs; the string says out loud that it is
  not a key.
- `TTL_SECONDS = 300` is a number you must be able to defend. It is the window in which a stolen
  state string is useful, and it is also the longest a human may take to answer before their answer
  is refused. Those two pull in opposite directions and 300 is a compromise, not a truth.
- `sub` is the **authenticated** principal — the subject claim off the validated access token from
  [1.3](../01-the-badge/1.3-a-voucher-for-one-shop.md), not a name the client supplied. State bound
  to a client-supplied identity is bound to nothing.
- `method` is stored so the state cannot be lifted from a `tools/call` and presented on a
  `resources/read`. The specification asks for "an identifier for the originating request", and the
  method name is half of that identifier.
- `digest` is the other half: a hash of the parameters, so a retry that changed the arguments does not
  match. `json.dumps(..., sort_keys=True)` is what makes the hash stable — two dicts with the same
  contents in different insertion orders must produce the same bytes, or the honest retry fails
  randomly. Truncating to 16 hex characters is a size trade-off; it is a collision-resistance
  reduction, and for a value that also carries a TTL and a principal it is a reasonable one to argue
  for in review.
- `exp` is an absolute instant, not a duration. A duration would have to be interpreted against a
  "now" the verifier chooses, and there is no shared clock —
  [Day 22's paper](../../../day-22-structured-logging/papers/01-time-clocks-ordering.md) is the
  reason that matters.
- `base64.urlsafe_b64encode` rather than plain `b64encode`, because the value may end up in a URL or
  a header where `+` and `/` need escaping. The `urlsafe` variant uses `-` and `_` instead.
- The tag is computed over the **encoded** body, not the original dict. Signing the encoded form is
  what makes verification a byte comparison rather than a re-serialisation, and re-serialisation is
  where signature schemes get subtly broken.
- `f"v1.{body}.{tag}"` puts a version prefix on the string. When you rotate the key or change the
  payload shape, `v2` lets both be accepted during the transition instead of every in-flight
  elicitation failing at deploy time.

The verification side, with five refusals:

```python
# days/day-37-auth-and-elicitation/lab/request_state.py  (extract)
def verify(
    state: str, principal: str, method: str, params: dict[str, object], now: int
) -> str | None:
    """Return None when the slip is good, otherwise why it is not."""
    try:
        version, body, tag = state.split(".", 2)
    except ValueError:
        return "malformed state"
    if version != "v1":
        return f"unknown state version {version!r}"
    expected = hmac.new(SECRET, body.encode(), hashlib.sha256).hexdigest()[:32]
    if not hmac.compare_digest(tag, expected):
        return "signature does not verify"
    payload = json.loads(base64.urlsafe_b64decode(body))
    if payload["sub"] != principal:
        return f"state was minted for {payload['sub']!r}, not {principal!r}"
    if payload["method"] != method:
        return f"state was minted for {payload['method']!r}"
    digest = hashlib.sha256(json.dumps(params, sort_keys=True).encode()).hexdigest()[:16]
    if payload["digest"] != digest:
        return "arguments changed between the first call and the retry"
    if payload["exp"] < now:
        return "state has lapsed"
    return None
```

**Line by line:**

- The `try`/`except ValueError` around `split` is the first line of defence, and it is here because
  the input is a stranger's string. `state.split(".", 2)` on a value with no dots raises, and an
  unhandled exception at this point is a 500 where a refusal belongs.
- **The signature is checked before the payload is decoded.** That ordering is the whole discipline.
  Decode first and you are parsing attacker-controlled bytes with `json.loads` before you have any
  reason to believe them; check first and everything after that line is data you minted.
- `hmac.compare_digest` rather than `==`. A plain string comparison returns as soon as two characters
  differ, so the time it takes leaks how many leading characters were right, and an attacker can
  recover a tag one character at a time. `compare_digest` takes the same time whatever the input.
  This is the single most-skipped line in hand-rolled token code.
- `payload["sub"] != principal` — the principal comes in as an **argument**, from the validated token
  on *this* request. It is never read out of the state. The state says who it was minted for; the
  request says who is presenting it; the check is that they agree.
- The digest is recomputed from **this** request's params, with the same `sort_keys=True`. Any
  difference in the arguments, however small, changes the hash and the retry is refused.
- The expiry check is **last**, and that is deliberate for the error messages: a lapsed state from
  the wrong user should report the wrong user, because that is the more interesting fact for whoever
  reads the log.
- `verify` returns a reason string rather than a bool, for the same reason as
  [1.3](../01-the-badge/1.3-a-voucher-for-one-shop.md)'s `accept`. In `sutra_mcp/auth.py` the caller
  turns any non-`None` into a JSON-RPC error and a log line, and the reason is what makes the log line
  worth having.
- There is no single-use enforcement here at all, and that is honest rather than an omission: the
  specification says a server that needs single use **MUST** enforce it server-side, which means a
  store, which means this function is not where it lives.

## When it breaks

The break the client sees when it tampers, or when the key has rotated:

```text
{"jsonrpc":"2.0","id":2,"error":{"code":-32602,"message":"Invalid params: requestState failed verification"}}
```

Note what the message does **not** say. Not *"signature mismatch"*, not *"minted for u-1"*, not the
decoded payload. The detailed reason goes in your log, keyed by request id; the client gets one
sentence. Telling a caller exactly which check failed hands them a map of your verification order.

The break that is your own fault, and the one you will hit first:

```text
Traceback (most recent call last):
  File "sutra_mcp/auth.py", line 62, in verify_state
    payload = json.loads(base64.urlsafe_b64decode(body))
              ~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
binascii.Error: Invalid base64-encoded string: number of data characters (33) cannot be 1 more than a multiple of 4
```

That is what a truncated state string produces if you decode before verifying. The traceback is the
diagnosis: the decode is happening on bytes nobody has checked. Move the signature comparison above
it and this becomes a refusal instead of a 500.

The third break has no error text and is the reason the version prefix exists. You rotate
`SUTRA_STATE_KEY` and deploy. Every elicitation currently in flight — every user who has a question
open on their screen right now — retries with a state signed by the old key, fails verification, and
sees a generic error. Nothing is broken; nothing is logged as an incident; a slice of users simply
lose the thing they were half way through. A rotation that accepts both keys for one TTL window, and
mints only with the new one, has no such slice.

## In production

**What a professional writes instead:** not this. A production server uses a vetted AEAD construction
from a maintained library — Fernet, or a JWE, or `libsodium`'s secretbox — with a versioned key, key
rotation built in, and the payload encrypted as well as authenticated. The hand-rolled HMAC above
exists so you can see every field and every check; shipping it is how a subtle mistake in
serialisation becomes a forgery. The rule of thumb is the one this whole curriculum runs on: build the
mechanism by hand once so the library is a convenience rather than a mystery, then use the library.

**What degrades at scale:** size. Every byte of `requestState` is carried in the server's response and
again in the client's retry, and it is not compressible in any useful way because it is encrypted or
hashed. A state blob that grows with the size of the request — because somebody put the whole
parameter object in it rather than a digest — turns a large tool call into two large tool calls. The
digest is what keeps the state a fixed small size regardless of the request.

**The failure mode that only appears with real traffic:** clock skew against the TTL. `exp` is
compared against the verifying instance's clock, and two instances that disagree by a few seconds
will reject each other's freshly minted state at a low rate — the same skew problem
[1.1](../01-the-badge/1.1-the-badge-the-desk-and-the-door.md) named for token expiry, arriving in a
place nobody instruments. A small tolerance, logged when it is used, is the standard answer, and the
log line is what lets you notice a clock drifting before it becomes an outage.

**The review comment a senior engineer leaves:** *"`verify` decodes the payload and then checks the
tag. Swap them. Right now we're running `json.loads` on bytes an attacker chose, before we have any
reason to trust them — and while you're in there, `tag == expected` needs to be
`hmac.compare_digest`, because a plain comparison leaks the tag one character at a time."*

**The interview question:** *"a stateless server needs to remember something between two requests. How
do you do that safely?"* The spoken answer: *"you don't remember it — you hand it to the client and
let it come back, which is what MCP's `requestState` is. The catch is that it spent time in somebody
else's program, so the spec says treat it as attacker-controlled: integrity-protect it with HMAC or
AEAD and reject anything that fails verification. Inside the protected payload you put three things,
and they map to three specific attacks: the authenticated principal, so one user's confirmation can't
be replayed by another; a short expiry, so an old confirmation can't be replayed at all; and the
method plus a digest of the parameters, so the user can't confirm 'close ticket 4521' and have the
retry arrive saying 9999. Two implementation details matter more than they look — check the signature
*before* you decode, and use a constant-time comparison. And if the state must be single-use, none of
this gives you that; the spec is explicit that single use needs server-side enforcement, and that's
the one place statelessness runs out."*
