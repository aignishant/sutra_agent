# 3.2 — A form the till can print

## One-line answer

The schema a server sends with a question is deliberately crippled — a **flat object of primitive
fields**, nothing nested — so that every client, however simple its interface, can render the same
question as a real form.

## The story

Watch the order pad in a busy café.

It has printed boxes. Size: small, medium, large. Milk: yes, no. Sugar: a number. Name: one line.
That is the whole pad, and it is the same pad whether the person serving has worked there for a
decade or started this morning.

Somebody once suggested a better pad — a free-text section where customers could describe exactly
what they wanted, nested notes, options within options. It was tried. The orders became unreadable
at the machine, two people made the same drink differently, and the queue backed out of the door.

The boxes are not there because the shop cannot imagine complexity. They are there because six
different people, at six different levels of experience, on a Saturday, have to read the same pad and
produce the same drink. The constraint is what makes the pad portable between them.

## The idea in plain language

`requestedSchema` is the field on a form-mode elicitation that describes what the answer should look
like. It is written in **JSON Schema** — a standard way of saying "this value is a string, this one
is a number between 0 and 100, this one is required". You have met JSON Schema before on this
curriculum: it is how a tool declares its arguments, back on
[Day 4](../../../day-04-tools-by-hand/).

Full JSON Schema can describe arbitrarily deep structures. Elicitation refuses almost all of it. The
specification's own words: *to simplify client user experience, form mode elicitation schemas are
limited to flat objects with primitive properties only*, and *complex nested structures, arrays of
objects (beyond enums), and other advanced JSON Schema features are intentionally not supported.*

What is allowed, exactly:

| Kind | `type` | Extra fields you may use |
| --- | --- | --- |
| String | `string` | `minLength`, `maxLength`, `format`, `default` |
| Number | `number` or `integer` | `minimum`, `maximum`, `default` |
| Boolean | `boolean` | `default` |
| Single-select | `string` with `enum`, or `oneOf` of `{const, title}` | `default` |
| Multi-select | `array` whose `items` are an enum of strings, or `anyOf` of `{const, title}` | `minItems`, `maxItems`, `default` |

The supported string `format` values are exactly four: `email`, `uri`, `date`, `date-time`. Every
kind supports `title` and `description`, and every kind supports `default` — and clients that
support defaults **SHOULD** pre-populate the field with it.

The array row is the only one that looks like an exception and is not. An array is permitted *only*
as a multi-select of strings. An array of objects is not a multi-select; it is a nested structure
wearing a list's clothing, and it is out.

Why cripple it? Because of who has to render it. An MCP client might be a chat window, a code
editor's side panel, a terminal, or a voice interface. A flat object of primitives maps onto a stack
of ordinary widgets in every one of those: a checkbox, a text box, a dropdown, a number field. A
nested object maps onto a tree editor, which most of those cannot draw, and the ones that can draw
it badly. The specification is trading expressiveness for the guarantee that **the same question
renders everywhere**.

The specification lists what a client does with the schema, and the three uses are worth separating:
generate the form, **validate the input before sending it**, and guide the user. That middle one is
the reason the schema is on the wire at all rather than being purely the server's private business.

## Why Sutra needs it

Because the first schema you will want to write is illegal, and knowing that now saves an afternoon.

`close_ticket` wants to ask about the duplicates. The natural design is one field per duplicate,
each with an id and a checkbox and maybe a note — which is a list of objects, and it is refused. The
legal design is one boolean for all of them, or a multi-select of ticket ids as strings. That is not
a workaround; it is the constraint pushing you towards a question a human can actually answer in one
glance, which is the question you wanted anyway.

`sutra_mcp/auth.py` is not where the schema lives — the schema belongs with the tool. But the
**check** belongs somewhere shared, because every elicitation Sutra ever sends has to satisfy it, and
a server that emits an illegal schema does not fail at the server. It fails in somebody else's client,
where you cannot see it. That is the same argument as
[Day 21's](../../../day-21-errors-surface-not-swallow/papers/01-end-to-end-arguments.md) end-to-end
paper: check it at the end that can actually do something about it, which here means the server, before
it sends.

You meet the same restriction again on [Day 41](../../../day-41-capabilities-and-mcp-apps/), where
MCP Apps let a tool ship a whole interface — and the reason that is a separate extension is precisely
that this schema cannot express one.

## The mechanism

A linter for the restriction, small enough to read in one sitting:

```python
# days/day-37-auth-and-elicitation/lab/elicit_form.py  (extract)
PRIMITIVES = {"string", "number", "integer", "boolean", "array"}


def flat(schema: dict[str, object]) -> list[str]:
    """Findings against the specification's flat-object restriction. Empty is a pass."""
    findings: list[str] = []
    if schema.get("type") != "object":
        findings.append(f"top level is {schema.get('type')!r}, not 'object'")
    properties = schema.get("properties")
    if not isinstance(properties, dict):
        return findings + ["no properties object"]
    for name, prop in properties.items():
        kind = prop.get("type") if isinstance(prop, dict) else None
        if kind not in PRIMITIVES:
            findings.append(f"{name}: type {kind!r} is not a primitive")
        elif kind == "object":
            findings.append(f"{name}: nested object")
        elif kind == "array" and isinstance(prop.get("items"), dict):
            item_type = prop["items"].get("type")
            if item_type != "string":
                findings.append(
                    f"{name}: array items are {item_type!r}, only enums of strings are allowed"
                )
    return findings
```

**Line by line:**

- `PRIMITIVES` includes `"array"` and does **not** include `"object"`. That asymmetry is the whole
  restriction in one line: arrays survive because a multi-select is a real widget, objects do not
  because a nested form is not.
- `schema.get("type") != "object"` checks the **top** level, which must be an object. A schema whose
  top level is a bare string is not a form; there is nowhere for the field name to go, and the answer
  map would have no keys.
- `properties` is fetched with `.get` and then type-checked with `isinstance`, rather than indexed.
  A schema missing `properties` entirely is a plausible mistake — someone writes the `type` and stops
  — and the linter should say so rather than raise `KeyError`.
- `return findings + ["no properties object"]` builds a new list instead of appending, so the
  early-return path cannot accidentally mutate and continue. It is a small thing, and it is the kind
  of small thing that stops a linter reporting one finding twice.
- `prop.get("type") if isinstance(prop, dict) else None` guards against a property whose value is not
  an object at all — `{"close_all": true}` rather than `{"close_all": {"type": "boolean"}}`. That
  yields `kind = None`, which is not in `PRIMITIVES`, so it is reported rather than skipped.
- The `elif kind == "object"` branch is **unreachable**, because `"object"` is not in `PRIMITIVES` and
  the first branch already caught it. It is left in deliberately as documentation of intent: a reader
  who later adds `"object"` to `PRIMITIVES` for some reason will find the second refusal waiting. If
  you would rather delete it, delete it — but say why in the commit message.
- The array branch only fires when `items` is a dict, because `items` may also be an `anyOf` list of
  `{const, title}` pairs for a titled multi-select, and that form has no `type` key to check. A
  stricter linter would validate that shape too; this one does not, and saying so out loud is better
  than a reader assuming coverage that is not there.
- `flat` returns findings rather than raising, for the same reason as
  [2.3](../02-issuer-checks/2.3-the-menu-you-host-yourself.md)'s `validate`: an author fixing a schema
  wants every problem at once.

The nested schema in the file is the one everybody writes first:

```json
{
  "type": "object",
  "properties": {
    "contact": {
      "type": "object",
      "properties": { "email": { "type": "string" } }
    }
  }
}
```

It is valid JSON Schema. It is a reasonable way to model a contact. And it is refused, because a
client with a single-line text prompt has no way to draw it.

The legal version of the same question flattens the path into the field name:

```json
{
  "type": "object",
  "properties": {
    "contact_email": { "type": "string", "format": "email", "title": "Email address" }
  },
  "required": ["contact_email"]
}
```

## When it breaks

The break on the server side, if you are using the pinned SDK's typed helper, is loud and early:

```text
TypeError: Elicitation schema field 'contact' has unsupported type <class '__main__.Contact'>. Only str, int, float, bool, and enums are allowed.
```

That is `_validate_elicitation_schema` in `.venv/Lib/site-packages/mcp/server/elicitation.py`,
`mcp==1.29.1`, read on 2026-09-04. It walks the Pydantic model you passed and refuses anything that
is not primitive **before** any request is sent. That is the right place for it: the failure happens
in your own process, at the call site, rather than in a stranger's client.

The break on the wire is quieter, because nothing in the protocol makes a client reject a bad
schema:

```text
{"jsonrpc":"2.0","id":2,"error":{"code":-32602,"message":"Invalid params: inputResponses.close_duplicates.content does not match requestedSchema"}}
```

That is what a careful client sends when the user's answer does not fit the schema the server asked
for. Note who reports it: the **server**, after the retry. Clients **SHOULD** validate before sending,
but "should" is not "must", and servers **SHOULD** validate what they receive. If you only do one of
the two, do the server one — it is the end that can refuse to act.

The third break has no error at all and is the reason this restriction is worth respecting rather
than testing the limits of. A client that cannot render your nested field renders it as *nothing* —
the form appears with the other fields and that one missing. The user answers what they see and
presses accept. Your server receives `action: "accept"` with a `content` map that has no key for the
thing you actually needed, and if you did not mark it `required` and check it, the tool proceeds with
a silently absent answer.

## In production

**What a professional writes instead:** a Pydantic model, not a hand-written dict. The pinned SDK's
`ctx.elicit(message=..., schema=SomeModel)` takes the model class, validates it is primitive-only at
call time, generates the JSON Schema, and parses the reply back into an instance — verified on
2026-09-04 in `.venv/Lib/site-packages/mcp/server/elicitation.py`, `mcp==1.29.1`. The dict above is
what you should be able to read on the wire; it is not what you should be typing. Hand-written
schemas drift from the code that reads the answers, and the drift is silent because both sides are
dicts.

**What degrades at scale:** not the schema, which is small, but the **question count**. A tool with
five optional refinements can express them as five booleans in one form, and it will, and users will
stop reading it. The production discipline is not technical: ask the fewest questions that make the
action unambiguous, put the destructive option behind an explicit boolean with `default: false`, and
push everything else into a sensible default the user can change afterwards. A form nobody reads is
worse than no form, because it manufactures consent.

**The failure mode that only appears with real traffic:** heterogeneous clients. Your form renders
beautifully in the client you developed against, and in another one the `oneOf` titled enum comes out
as raw constants — `#FF0000` instead of *Red* — because that client implemented the untitled enum
form only. The user picks the wrong one. The mitigation is to prefer the plain `enum` of
human-readable strings when the values are for humans, and to reserve the `oneOf` `{const, title}`
form for when the stored value genuinely has to differ from the label.

**The review comment a senior engineer leaves:** *"this schema has eight fields, six of them optional,
and the destructive one defaults to true. Cut it to the one boolean the action actually needs and set
its default to false. Everything else can be a default we apply and a follow-up the user can change —
a confirmation dialogue that takes a paragraph to read is a confirmation nobody gives."*

**The interview question:** *"why does MCP elicitation only allow flat schemas?"* The answer that
shows you have rendered one: *"because the client is what draws the form, and clients are wildly
different — a chat window, an editor panel, a terminal, possibly a voice interface. A flat object of
primitives maps to a checkbox, a text field, a number field and a dropdown in all of them, so the
same question renders the same way everywhere. Nesting maps to a tree editor, which most clients
can't draw. Arrays are allowed only as multi-selects of strings, which is the same argument — that's
still one widget. The practical consequence is that you flatten the path into the field name,
`contact_email` rather than `contact.email`, and if you genuinely need a rich interface that's what
the MCP Apps extension is for, not this."*
