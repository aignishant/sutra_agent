# 2.2 — The comparison that must not be helpful

## One-line answer

The `iss` value is form-decoded once and then compared **byte for byte** — no case folding, no
trailing-slash trimming, no default-port elision — because every tidy-up you add is one more string
an attacker's issuer is allowed to be.

## The story

You are at an airport check-in desk. The agent takes your passport and your booking and puts them
side by side.

On the booking your surname has one letter doubled that the passport spells single. It is obviously
you. The photo is you, the date of birth is you, the flight is yours, and there is a queue of forty
people behind you.

The agent has two choices. Fix it — decide the two are "the same really" and print the boarding pass
— or refuse and send you to the ticket desk. Fixing it is kinder, faster, and correct almost every
time. And it is exactly the habit that, on some other day, lets through a name that is *nearly* the
one on a watchlist, because the rule that made your day easier is the same rule that made the near
match acceptable.

The agent who refuses is not being obtuse. They are refusing to be the person who decides which
differences do not matter.

## The idea in plain language

When you compare two URLs in ordinary code, being tolerant is the right instinct.
`https://Example.com/` and `https://example.com` do point at the same web page, and a program that
insisted otherwise would be a nuisance. There is even a standard for the tidy-ups — RFC 3986 calls
them *syntax-based normalisation*: fold the scheme and host to lower case, drop the default port,
add a missing empty path.

The MCP specification forbids every one of them here. The exact sentence: after decoding the `iss`
value from the form-encoded response, clients **MUST NOT** apply scheme or host case folding,
default-port elision, trailing-slash, or percent-encoding normalisation before comparison. What is
permitted is **simple string comparison**, defined in RFC 3986 §6.2.1 — the crudest possible test,
character for character, with nothing done to either side first.

Why forbid something so obviously convenient? Because normalisation is not a comparison, it is a
**many-to-one function**, and every tidy-up you enable makes the set of strings that pass the check
bigger. `https://auth.example` compared strictly matches exactly one string. Compared after case
folding it matches every capitalisation. After trailing-slash trimming, two more. After default-port
elision, more again. Each rule is defensible alone; together they turn one accepted value into a
family, and a security check whose accepted set grows with each helpful edit is a check that will
eventually accept something you did not intend.

There is a second reason, and it is more practical: **the two sides of this comparison come from
different places.** The expected value comes from the authorization server's own validated metadata
document, where it is published as the `issuer` field. The returned value comes from the redirect. If
those two disagree by so much as a trailing slash, the honest reading is *the server is inconsistent
about its own identity*, and that is a fact you want surfaced rather than smoothed over. A strict
comparison surfaces it on the first flow. A lenient one hides it for years.

One thing you *must* do before comparing: decode. The authorization response is
`application/x-www-form-urlencoded`, so the value arrives as
`https%3A%2F%2Fauth.sutra.example`. Form-decoding that back to `https://auth.sutra.example` is not
normalisation — it is reading the value at all. The rule is: decode once, then nothing.

## Why Sutra needs it

Because this is the exact line of code somebody will "improve" in a review, and the improvement will
look like a bug fix.

The scene writes itself. `sutra/mcp/auth.py` ships with `returned == expected`. Three weeks later
somebody integrates a second identity provider, hits a mismatch, discovers the difference is a
trailing slash, and pushes a one-line change to `.rstrip("/")` both sides. The tests pass. The
integration works. Nobody notices that the accepted set just doubled, and there is no test that could
have noticed, because a test asserts what you thought of.

So the defence is not the comparison — it is the **comment above the comparison** saying why it is
not normalised, and a test that asserts a near-miss is rejected. Both belong in `sutra/mcp/auth.py`
today, and [Day 45's audit](../../../day-45-the-mcp-audit/) will look for the near-miss test rather
than the check, because the check is easy and the test is what stops it being softened.

The same discipline shows up again on [Day 40](../../../day-40-filtering-and-allowlists/), where a
tool allowlist is a set of exact names and somebody will want prefix matching.

## The mechanism

Two functions with the same signature and different consciences.

```python
# days/day-37-auth-and-elicitation/lab/compare.py  (extract)
EXPECTED = "https://auth.sutra.example"


def strict(raw: str) -> bool:
    """Form-decode once, then compare byte for byte. This is the whole of RFC 3986 section 6.2.1."""
    return unquote(raw) == EXPECTED


def helpful(raw: str) -> bool:
    """The version a reviewer asks for and the specification forbids."""
    value = unquote(raw).lower().rstrip("/")
    return value.replace(":443", "") == EXPECTED.lower().rstrip("/")
```

**Line by line:**

- `unquote` is `urllib.parse.unquote`, and it is the **one** transformation both functions share. It
  turns `%3A` back into `:` and `%2F` back into `/`. Without it, the strict comparison would fail on
  every honest response, because you would be comparing an encoded string to a decoded one — which is
  the mistake that makes people conclude strict comparison is impractical.
- `strict` is one expression and has no branches. That matters more than it looks: a comparison with
  no branches has no place for a special case to be added later. The first `if` somebody adds to this
  function is the beginning of the accepted set growing.
- The docstring on `strict` names the specification section. A reader who wants to loosen it now has
  to argue with a citation rather than with a colleague's preference, and that is the entire purpose
  of putting the reference in the docstring rather than in a commit message.
- `helpful` chains three tidy-ups on purpose, each of which is individually reasonable. `.lower()`
  handles a host written in capitals. `.rstrip("/")` handles a trailing slash. `.replace(":443", "")`
  handles the default HTTPS port written out. None of them is stupid. That is the point — this is not
  a straw man, it is what the change actually looks like when somebody makes it.
- `helpful` applies its tidy-ups to **both** sides, which is what makes it feel safe. It is
  symmetrical, it is deterministic, and it still widens the accepted set from one string to at least
  five.
- Neither function raises on a malformed input. In `sutra/mcp/auth.py` the real one does, because a
  missing or unparseable `iss` when one was advertised is [2.1](2.1-which-desk-actually-answered.md)'s
  second table row and it is a rejection, not a `False`.

**Line by line:**

- From the repository root. **Zero generations, no network.** Five literal values in, one table out.

Measured on 2026-09-04:

```text
value carried in the redirect               strict    helpful   tidy-up that differs
------------------------------------------------------------------------------------------------------------
https%3A%2F%2Fauth.sutra.example            True      True      none - this is the honest value
https%3A%2F%2FAUTH.SUTRA.EXAMPLE            False     True      host case folding
https%3A%2F%2Fauth.sutra.example%2F         False     True      trailing-slash removal
https%3A%2F%2Fauth.sutra.example%3A443      False     True      default-port elision
HTTPS%3A%2F%2Fauth.sutra.example            False     True      scheme case folding

issuer strings the helpful version accepts and the strict one does not: 4
```

**Four.** One expected issuer became five acceptable strings, from three lines of tidying. Nothing in
that table is an attack by itself — an attacker does not gain anything from `AUTH.SUTRA.EXAMPLE`,
because they do not control that host either. What the table measures is the *shape* of the change:
the accepted set is no longer "the issuer" but "a family of things that resemble the issuer", and
the boundary of that family is now defined by whichever tidy-ups happen to be in the function rather
than by the specification.

## When it breaks

The break that gets the lenient version written is an honest one, and it looks like this:

```text
mcp.client.auth.exceptions.OAuthFlowError: issuer 'https://auth.vendor.example/' is not the recorded issuer 'https://auth.vendor.example'
```

One trailing slash. A real integration, a real user, blocked. The pressure to `.rstrip("/")` in that
moment is considerable, and the right response takes longer: find out **which** of the two values is
wrong. The metadata document's `issuer` field and the `iss` parameter are supposed to be the same
string produced by the same server. If they differ, that server is inconsistent, and the fix belongs
there. If you cannot get it fixed, the honest workaround is an explicit, per-issuer, commented
exception with the provider named — not a general loosening that silently applies to every issuer you
will ever talk to.

The break you will not see is the second one:

```text
issuer strings the helpful version accepts and the strict one does not: 4
```

That is not an error. It is a count, printed by a script you wrote, and it is the only visible
consequence of the change. Nothing throws. No test goes red — unless you wrote the near-miss test,
which is the entire argument for writing it.

The third break is percent-encoding, and it is the one worth understanding rather than memorising.
`%2F` and `/` are the same character after decoding, so decoding once is required. But
`https://auth%2Esutra.example` also decodes to `https://auth.sutra.example`, and re-encoding or
double-decoding either side introduces a second family of equivalent strings. The rule *decode once,
then nothing* is what keeps that from becoming a question you have to answer.

## In production

**What a professional writes instead:** the comparison stays exactly this austere, and everything
around it gets stronger. The expected issuer is read from the validated metadata document and stored
verbatim; the comparison is in one function with the specification section in its docstring; and
there is a test named something like `test_near_miss_issuers_are_rejected` that feeds it the four
rows from the table above and asserts every one is refused. The test is the artefact that survives
the next reviewer.

**What degrades at scale:** not the comparison — string equality does not care how many flows you
run. What degrades is the *support load*. A strict client will hit interoperability failures against
identity providers that are inconsistent about their own issuer string, and each one arrives as a user
saying "I can't connect". The operational answer is to log the two values side by side on every
mismatch, so the on-call engineer sees `'https://x/' != 'https://x'` in one line rather than
reproducing the flow. That log line is worth writing before the first mismatch, because the mismatch
arrives at an inconvenient moment and is not reproducible from the outside.

**The failure mode that only appears with real traffic:** case-varying hosts behind a CDN. Some
deployments serve the same authorization server under a hostname whose case differs between the
metadata document and the redirect, because two different systems generate them. It affects a small
fraction of users — the ones routed to a particular edge — and it looks random. It is not the
comparison's fault, and loosening the comparison hides a genuine misconfiguration that will bite in
some other way later.

**The review comment a senior engineer leaves:** *"this PR adds `.lower()` to the issuer comparison
to fix one provider. That is not a fix, it is a widening — the spec forbids case folding here by
name, and the four near-misses in `tests/test_mcp_auth.py` will now pass. If the provider's `iss`
disagrees with its own metadata `issuer`, that is their bug; raise it with them and, if we must ship
before they fix it, add a named per-issuer exception with a link to the ticket and a date to remove
it."*

**The interview question:** *"why can't you normalise a URL before comparing it in a security
check?"* The answer that shows you have thought about it: *"because normalisation is a many-to-one
function, so every rule you add makes the set of accepted inputs larger, and a check whose accepted
set grows as people make it friendlier is not a check any more. Concretely, RFC 9207 and the MCP spec
require simple string comparison for the `iss` parameter, and explicitly forbid case folding,
default-port elision, trailing-slash and percent-encoding normalisation. We measured it: three
reasonable tidy-ups took one accepted issuer to five. The one transformation you must do is
form-decoding the value, because it arrives percent-encoded — decode once, then nothing. And the
thing I'd actually put in the codebase is the near-miss test, because the comparison is one line and
the pressure to soften it comes from a real user being blocked."*
