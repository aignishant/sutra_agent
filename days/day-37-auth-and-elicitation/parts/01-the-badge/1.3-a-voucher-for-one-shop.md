# 1.3 — A voucher for one shop

## One-line answer

An access token names the one service it was minted for, and a server **must** check that the name
is its own — and must never spend a token it was given somewhere else, because a token that travels
is a token that has stopped meaning anything.

## The story

Somebody gives you a gift voucher. It has a value printed on it, and it has a shop name printed on
it — the bookshop on the corner.

You walk into the shopping centre and try it at the coffee counter. The person behind the till turns
it over, reads the name, and hands it back. Not because you are untrustworthy, and not because the
voucher is fake. It is a perfectly real voucher. It is just not for here.

Now imagine the coffee counter had accepted it. Not spent it — *accepted* it, and then walked next
door to the bookshop and spent it there on your behalf, keeping the coffee. The voucher would have
worked. Everything would look fine on the receipt. And the bookshop would have no idea it had just
served the coffee counter rather than you.

That second scenario is the interesting one, because nobody had to forge anything. The voucher was
genuine at every step. The only thing that went wrong is that a shop accepted a voucher with
somebody else's name on it, and then passed it along.

## The idea in plain language

An access token is not a general permission. It is issued for a specific service, and the name of
that service is written inside the token in a field called **`aud`**, short for *audience*.

The MCP specification is unusually direct here, and it is worth having the exact sentences in your
head because three of them are separate rules:

- MCP servers **MUST** validate that access tokens were issued specifically for them as the
  intended audience.
- MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by that MCP
  server's authorization server.
- MCP servers **MUST NOT** accept or transit any other tokens.

The word that carries the third rule is **transit**. A server that takes the token you gave it and
forwards it to some upstream API is doing *token passthrough*, and the specification forbids it by
name. Passthrough is the coffee counter walking next door.

Two more definitions, because they arrive together.

**The `resource` parameter.** So that a token can say who it is for, the client has to say who it
wants it for. MCP requires clients to implement *Resource Indicators for OAuth 2.0*: a `resource`
parameter, carrying the MCP server's canonical URI, sent on **both** the authorization request and
the token request. Clients must send it whether or not the authorization server appears to support
it. That parameter is what makes the `aud` claim in the returned token specific rather than blank.

**Scope versus audience.** These are different questions and people run them together. *Audience*
asks **which service**; *scope* asks **which actions at that service**. A token with the right
audience and the wrong scope is a real key to the right door that does not turn the lock on this
particular room. A token with the right scope and the wrong audience is a key to a different
building entirely, and the fact that its label says `tickets:read` is meaningless.

Why does the audience check matter so much when the token is genuine anyway? Because without it, any
service that can obtain a token from your authorization server can spend it at any *other* service
that trusts the same authorization server. One compromised low-value service becomes a key to every
high-value one. Checking `aud` reduces the blast radius of a stolen token from "everything this
issuer protects" to "one service" — which is Principle 13, *blast radius before capability*, applied
to a single string comparison.

## Why Sutra needs it

Because `sutra_mcp/auth.py` is the file where this check either exists or does not, and there will
be no error message either way.

A server that validates the signature on a token, reads the `sub` claim to find out who is calling,
checks the scope, and never looks at `aud` will behave perfectly in every test you write. It only
fails when somebody presents a valid token minted for a different service — and at that moment it
does not fail at all. It succeeds. That is the whole problem: **a missing audience check has no
failing case, only a widened one.**

The passthrough rule bites on [Day 39](../../../day-39-database-tools/), where `sutra_mcp/db_tools.py`
reaches a database, and again anywhere Sutra's server calls an upstream vendor API. The temptation is
obvious and the reasoning sounds thrifty: *the caller already gave us a token, why get a second
one?* Because the first one names us as its audience, and using it anywhere else is exactly the
thing the specification says a server must not do. The correct pattern — the server getting its own
credential for the upstream service, on the user's behalf but not with the user's MCP token — is
[4.1](../04-out-of-band/4.1-the-link-you-check-before-you-click.md)'s subject.

## The mechanism

The whole of the check, in one function with three refusals in it:

```python
# days/day-37-auth-and-elicitation/lab/audience.py  (extract)
OUR_RESOURCE = "https://mcp.sutra.example/mcp"
OUR_ISSUER = "https://auth.sutra.example"


@dataclass(frozen=True)
class Token:
    """The claims a resource server actually reads off a validated access token."""

    iss: str
    aud: str
    sub: str
    scopes: frozenset[str] = field(default_factory=frozenset)


def accept(token: Token, required: str) -> str | None:
    """Return None when the token may be used here; otherwise the reason it may not."""
    if token.iss != OUR_ISSUER:
        return f"issuer {token.iss!r} is not ours"
    if token.aud != OUR_RESOURCE:
        return f"audience {token.aud!r} is not this server"
    if required not in token.scopes:
        return f"scope {required!r} not granted"
    return None
```

**Line by line:**

- `OUR_RESOURCE` is the same canonical URI the metadata document published in
  [1.2](1.2-the-refusal-that-carries-directions.md). It has to be the same string, character for
  character, or the client will ask for a token whose audience the server then rejects. Publishing it
  once and importing it is the only way that stays true.
- `@dataclass(frozen=True)` because a token's claims are a fact about something that already
  happened. `frozen=True` makes the object hashable and stops any later code "correcting" a claim,
  which is the sort of helpfulness this whole day is about refusing.
- The four fields are exactly the claims a **resource server** reads, and no more. There is no
  `password`, no `email`, no `roles` — [1.1](1.1-the-badge-the-desk-and-the-door.md)'s `FORBIDDEN`
  table said the resource server holds no identities, and this dataclass is that rule written as
  code. `sub` is the *subject*, a stable identifier for the user that is unique **only within one
  issuer**; two different issuers may both call somebody `u-1`, which is one more reason the issuer
  check comes first.
- `accept` returns `str | None` rather than a `bool`. A boolean tells the caller it failed; a reason
  tells the log line *why*, which is the difference between an alert somebody can action and an
  alert somebody mutes. This is [Day 21's](../../../day-21-errors-surface-not-swallow/) rule applied
  to a security check: the failure has to survive as information.
- The order of the three checks is not arbitrary. Issuer first, because `aud` and `sub` are only
  meaningful relative to an issuer — comparing an audience on a token from an unknown desk is
  comparing a string you have no reason to believe. Audience second, because scope names are also
  issuer-relative. Scope last, because it is the only one of the three that means *"this is you, at
  the right server, without this particular permission"* — the 403 from
  [1.2](1.2-the-refusal-that-carries-directions.md) rather than the 401.
- Every comparison is `!=` on a plain string. No lower-casing, no trailing-slash trimming, no `in`.
  [2.2](../02-issuer-checks/2.2-the-comparison-that-must-not-be-helpful.md) is an entire part about
  why that matters, and the habit starts here.


The third row is the one to sit with. That token is signed by *your own* authorization server, for

and it is accepted, and no test in the repository goes red.

## When it breaks

The first break is what a client sees when the audience is wrong and the server does its job:

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token", error_description="token audience https://vendor.example/api does not match https://mcp.sutra.example/mcp", resource_metadata="https://mcp.sutra.example/mcp/.well-known/oauth-protected-resource"
```

The status is 401, not 403, and that catches people out. The reasoning is in
[1.2](1.2-the-refusal-that-carries-directions.md)'s table: 403 is *invalid scopes or insufficient
permissions*, and a token minted for somebody else is not a permissions problem. It is an invalid
token. Sending 403 here tells the client to ask for wider scopes, which will not help, and it will
loop.

The second break has no error text at all, and it is the reason this part exists. Comment out the
`aud` check and re-run:

```text
ours, correct scope         accept
ours, missing scope         reject - scope 'tickets:read' not granted
issued for the vendor API   accept
minted by another desk      reject - issuer 'https://evil.example' is not ours
```

One line changed from `reject` to `accept`. Nothing raised. Nothing logged. The only way to notice
is to have a test that asserts the reject, which is why the check is worth writing a test for
before it is worth writing at all.

The third break is passthrough, and it announces itself in an audit rather than in a traceback. The
symptom in a log is an upstream API receiving requests bearing tokens whose `aud` is your MCP
server. The upstream may even accept them, if it is also lax. The finding reads: *"service B accepts
tokens minted for service A"*, and the fix is two changes — B checks its audience, and A stops
forwarding.

## In production

**What a professional writes instead:** the check does not live in a hand-written function at all.
It lives in the token verifier the server framework calls, once, before any tool code runs. The
pinned SDK's shape is `mcp.server.auth.provider.TokenVerifier`, a protocol with a single method
`async def verify_token(self, token: str) -> AccessToken | None`, where `AccessToken` carries
`token`, `client_id`, `scopes`, `expires_at`, `resource`, `subject` and `claims`. Note the field
name: `resource`, documented in the source as the RFC 8707 resource indicator — the audience, under
the name OAuth gives it on the request side. Verified on 2026-09-04 in
`.venv/Lib/site-packages/mcp/server/auth/provider.py`, `mcp==1.29.1`. Writing the check per-tool is
how one tool ends up without it.

**What degrades at scale:** nothing about the comparison, and quite a lot about what precedes it.
Getting from a token string to a `Token` object means either verifying a signature locally against a
cached key set or asking the authorization server. Local verification is a few microseconds and
cannot see a revocation until expiry; introspection sees revocations immediately and puts a second
network hop in front of every MCP request, which means your server's availability is now the product
of two services' availability. The common answer is local verification plus short expiry, and the
number to be able to defend in a review is the expiry — it *is* the revocation window.

**The failure mode that only appears with real traffic:** multi-tenant audience drift. A server
deployed behind two hostnames — an internal one and a public one — issues tokens with whichever
canonical URI the client discovered, and rejects the other. It works in staging, where there is one
hostname, and produces a low background rate of `invalid_token` in production that correlates with
nothing obvious. The fix is to pick one canonical URI, publish it in the metadata document, and
treat the other hostname as a redirect rather than an identity.

**The review comment a senior engineer leaves:** *"`db_tools.py` line 40 passes
`request.headers['authorization']` straight into the vendor client. That is token passthrough — the
spec calls it out by name and forbids it. The vendor needs its own credential, obtained by this
server on the user's behalf. If you genuinely need the user's identity at the vendor, that is a URL
mode elicitation, not a forwarded header."*

**The interview question:** *"a token is signed by the right issuer, has the right scope, has not
expired, and belongs to a real user. Name a reason to reject it."* The answer that shows you have
shipped one: *"the audience. The `aud` claim names the service the token was minted for, and if that
is not us, the token is genuine and not ours. It is the check with no failing test case — skip it and
everything passes, and you have quietly made any service that trusts the same issuer into a key for
this one. The related rule is that we never forward a token we were given to an upstream API. That is
token passthrough; the spec forbids it, and the reason is the same one — the moment a token is
accepted somewhere it does not name, its audience has stopped meaning anything."*
