# 4.2 — Shared is not the same as safe

## One-line answer

Moving state into a store both instances can reach fixes *reachability* and not *correctness*: two
instances reading a number, adding to it and writing it back will lose most of the additions, and the
fix is one line that takes the lock before the read rather than after the decision.

## The story

It is a joint account and there are two cash machines in the same row.

You stand at one, your brother stands at the next one along, and you both ask for money at the same
moment. Both machines check the balance — the same balance, because it is the same account — and both
of them see enough. Both dispense. Both write the new balance back.

The account is now short by one withdrawal, because the second machine wrote a balance it had worked
out from a number that was already out of date by the time it finished counting the notes.

Nobody did anything wrong and nothing broke. The account is shared, which is the whole point of a
joint account. What was missing is that between *checking* and *writing*, the other machine got in.

Real banks solved this a long time ago, and the shape of the solution is the same everywhere: one of
the two machines has to wait.

## The idea in plain language

Section 3's fix was to move state out of the process and into a file both instances open. Every
behaviour that had failed then passed. It is tempting to stop there.

But "both instances can reach it" is a statement about **reachability**, and correctness under
concurrent writers is a different property with its own name.

A **read-modify-write** is any operation that reads a value, computes a new one from it, and writes
it back. Almost every counter, quota, progress update and status transition is one:

    n = read()
    n = n + 1
    write(n)

Three separate steps. Between step 1 and step 3 there is a **window**, and anything else that reads
in that window sees the old value. Both writers then write the same new number, and one of the two
increments is gone. This is a **lost update**, and it is the oldest concurrency bug there is.

The window is small, which is exactly why this survives testing. Two sequential requests never
overlap. A test with one client never overlaps. It needs two callers arriving at the same moment, and
"the same moment" is measured in microseconds — until you have real traffic, several instances, and
requests all day, at which point the improbable happens continuously.

The fix is a **transaction**: a group of statements the database treats as one indivisible step. And
the detail that decides whether it works is *when the lock is taken*.

- `BEGIN` — a deferred transaction. The database takes no write lock until the first write, which is
  *after* your read and *after* your decision. Two writers can both read the old value inside their
  own transactions, and you have the same bug with more ceremony.
- `BEGIN IMMEDIATE` — take the write lock now, before the read. The second writer waits at the
  `BEGIN` rather than discovering a conflict later.

That word `IMMEDIATE` is the entire difference between the two runs at the end of this part.

Two SQLite settings make the waiting workable, and they are per connection:

- `PRAGMA journal_mode=WAL` — write-ahead logging. Readers do not block the writer and the writer
  does not block readers, so only writer-against-writer contends. Without it every read blocks every
  write.
- `PRAGMA busy_timeout=<milliseconds>` — how long a connection waits for a lock before giving up.
  The default is **zero**, which means "fail immediately", and that default is the reason people
  conclude SQLite cannot handle concurrency.

## Why Sutra needs it

Because every piece of state this day moved into the store is a read-modify-write.

The **budget** from [3.4](../03-two-instances/3.4-three-a-day-per-instance.md) reads the count,
compares it to the limit, and writes the new count. Under two instances without a transaction it
over-spends — the same failure as the per-process counter, arrived at from the opposite direction,
and much harder to spot because the counter is now correctly shared.

The **draft** from [3.5](../03-two-instances/3.5-the-handle-b-had-never-heard-of.md) reads the body,
appends a line, and writes it back. Two appends in the same window and one sentence vanishes — which
is exactly the symptom that made the broken version dangerous rather than annoying.

The **task progress** from [Day 36](../../../day-36-long-jobs-and-tasks/) reads a percentage, updates
it, and writes it back. Lost updates there make progress move backwards, which is the sort of thing
users report and nobody can reproduce.

So the fix in section 3 is only half a fix, and the missing half is one keyword. Today's build brief
asks you to write it into `sutra_mcp/`, and [Day 45's audit](../../../day-45-the-mcp-audit/) is where
the absence of it becomes a finding.

## The mechanism

The two versions, side by side, differing by two statements:

```python
# days/day-43-stateless-by-default/lab/race.py  (extract)
def bump_unsafe(con: sqlite3.Connection) -> None:
    """Read, add one, write it back. Three statements, nothing holding them together."""
    n = con.execute("SELECT n FROM counter WHERE key = 'spend'").fetchone()[0]
    time.sleep(0.001)  # the window every read-modify-write has, made visible
    con.execute("UPDATE counter SET n = ? WHERE key = 'spend'", (n + 1,))


def bump_safe(con: sqlite3.Connection) -> None:
    """The same three statements, inside one transaction that takes the lock first."""
    con.execute("BEGIN IMMEDIATE")
    n = con.execute("SELECT n FROM counter WHERE key = 'spend'").fetchone()[0]
    time.sleep(0.001)
    con.execute("UPDATE counter SET n = ? WHERE key = 'spend'", (n + 1,))
    con.execute("COMMIT")
```

**Line by line:**

- `SELECT` then `UPDATE` with the new value computed in Python is the shape to learn to recognise. It
  appears in every codebase and it is a lost update waiting for a second writer.
- `time.sleep(0.001)` is the window, widened so the demo is deterministic rather than lucky. It is
  **not** what causes the bug. Delete it and the same failure happens at a lower rate, which is the
  production version and the reason nobody catches it in a test.
- `BEGIN IMMEDIATE` is the whole fix. `IMMEDIATE` takes the write lock at the `BEGIN`, so a second
  process waits *there* rather than reading a value it is about to invalidate. A plain `BEGIN` defers
  the lock to the `UPDATE` — after the read, after the decision — and on this database that does not
  quietly lose the update; it raises. See *When it breaks*, because the difference between the two
  words is more interesting than it sounds.
- `COMMIT` releases the lock. Everything between `BEGIN IMMEDIATE` and `COMMIT` is serialised across
  every process on that file, so it must be **short** — a read, an arithmetic step and a write, and
  never a network call or a model call, which is
  [4.1](4.1-down-out-or-nowhere.md)'s tail-latency point arriving as a lock-hold time.
- Both functions take an already-open connection, so the demo measures contention on the counter
  rather than the cost of opening files.

The connection settings that make the waiting work:

```python
# days/day-43-stateless-by-default/lab/race.py  (extract)
def connect() -> sqlite3.Connection:
    """One connection, with the two pragmas that let several processes share a file."""
    con = sqlite3.connect(DB, timeout=10.0, isolation_level=None)
    con.execute("PRAGMA journal_mode=WAL")
    con.execute("PRAGMA busy_timeout=10000")
    return con
```

**Line by line:**

- `isolation_level=None` turns off the Python driver's implicit transaction management. Without it
  the driver decides where transactions begin, and your `BEGIN IMMEDIATE` is competing with a library
  for control of something that must be explicit.
- `PRAGMA journal_mode=WAL` is persistent in the database file rather than per connection, so setting
  it on every connect is harmless repetition — and it is worth doing anyway, because a file created
  by whichever instance got there first is not something to leave to chance.
- `PRAGMA busy_timeout=10000` gives a blocked writer ten seconds before it raises. The default is
  zero. This one line is the difference between "SQLite cannot do concurrency" and "SQLite handles
  our write rate comfortably".
- `timeout=10.0` on the connection is the driver's own equivalent of the same thing, set to the same
  value so that the two cannot disagree about who gives up first.

An alternative worth knowing, because it removes the whole category:

```sql
UPDATE counter SET n = n + 1 WHERE key = 'spend' AND n < 3;
```

**Line by line:**

- The new value is computed **inside** the database from the current row, so there is no window
  between a read in your process and a write from your process — there is no read in your process at
  all.
- `AND n < 3` puts the limit check in the same statement. The database applies it against the value
  it is about to change, not against a value somebody read a moment ago.
- The number of rows the statement affected tells you whether it was allowed: one means spent, zero
  means refused. That is the whole quota decision in one round trip.
- When you can express the change as arithmetic on the existing row, do this instead of a
  transaction. Reach for `BEGIN IMMEDIATE` when the new value genuinely cannot be computed in SQL —
  when it depends on something outside the database.

## When it breaks

Four processes, twenty-five increments each, one counter. The answer must be 100. Measured on
2026-09-05:

```text
mode          : read-modify-write, no transaction
increments    : 4 processes x 25 = 100
counter says  : 30
lost updates  : 70
exit: 1
```

Seventy of the hundred increments are gone. Not seventy failures — seventy **successes** that were
overwritten. Every one of those `UPDATE` statements ran, committed, and was correct with respect to
the number the process had read.

Now the same four processes with `BEGIN IMMEDIATE`:

```text
mode          : BEGIN IMMEDIATE
increments    : 4 processes x 25 = 100
counter says  : 100
lost updates  : 0
```

One hundred. Same file, same processes, same hundred increments; two extra statements.

Read the broken run against [3.4](../03-two-instances/3.4-three-a-day-per-instance.md) once more,
because the pair is the point of this part. There, a limit of three allowed six. Here, a hundred
increments count as thirty. **Both bugs are in a counter, and the second one appears only after you
have fixed the first.** A shared store is necessary and it is not sufficient, and a team that
celebrates the section 3 fix and stops is holding a quota that under-counts instead of one that
over-counts.

Now change the one word. Replace `BEGIN IMMEDIATE` with a plain `BEGIN`, leaving everything else —
the transaction, the `COMMIT`, the ten-second busy timeout — exactly as it was:

```text
sqlite3.OperationalError: database is locked
sqlite3.OperationalError: database is locked
Traceback (most recent call last):
  ...
  File "...\lab\race.py", line 62, in bump_safe
    con.execute("UPDATE counter SET n = ? WHERE key = 'spend'", (n + 1,))
sqlite3.OperationalError: database is locked

mode          : BEGIN IMMEDIATE
increments    : 4 processes x 25 = 100
counter says  : 25
lost updates  : 75
```

Three of the four processes died. This is worth understanding rather than memorising, because it is
the one place SQLite's behaviour is genuinely surprising.

Under write-ahead logging, a deferred transaction that has already **read** is pinned to the snapshot
it read. If another writer commits in the meantime, this transaction can no longer write without
building on a value it did not see, so the database refuses — and it refuses with a conflict that
`busy_timeout` deliberately does **not** retry, because waiting cannot help. The snapshot is stale
and waiting makes it staler.

So `BEGIN` versus `BEGIN IMMEDIATE` is not "the same bug with extra ceremony". It converts a silent
lost update into a loud crash, which is a strict improvement and still not what you want: the fix is
to take the lock before the read, so the second writer waits for its turn instead of discovering
afterwards that it never had one. Notice also that the run's own label still says
`BEGIN IMMEDIATE` — the label is a string in the printing code, not a fact about what ran. A
self-describing report is only as honest as the person editing it.

The last break is the one people take as proof the whole approach is wrong. Set the busy timeout to
zero and let two writers meet:

```text
Traceback (most recent call last):
  File "...\lock.py", line 10, in <module>
    b.execute("BEGIN IMMEDIATE")
sqlite3.OperationalError: database is locked
```

That is not SQLite refusing to do concurrency. It is SQLite doing exactly what it was configured to
do: wait zero milliseconds, then fail. The default `busy_timeout` is `0`, so a connection that has
not set it fails on the first collision, and a great deal of folklore about SQLite comes from
exactly this line.

## In production

**What a professional writes instead:** the update as a single statement wherever the arithmetic
allows it, and an explicit `BEGIN IMMEDIATE` transaction where it does not. On a networked database
the equivalents are `SELECT … FOR UPDATE`, a conditional `UPDATE … WHERE`, or an atomic increment in
a cache server. The framing that generalises: **never compute a new value in your application from a
value you read in a separate statement.** A unique constraint is the same idea for creation rather
than update — let the database refuse the duplicate rather than checking first and inserting after.

**What degrades at scale:** the serialised section becomes the throughput limit. Everything between
`BEGIN IMMEDIATE` and `COMMIT` happens one writer at a time across the whole system, so a transaction
that takes ten milliseconds caps you at a hundred writes per second no matter how many instances you
run. This is where a single hot row — one global counter — turns into the bottleneck, and the usual
answers are to shard the counter or to accept approximate counting, both of which are decisions with
consequences rather than tuning.

**The failure mode that only appears with real traffic:** the timeout that starts firing. Under light
load nobody waits, so `busy_timeout` never matters. As write rate climbs, waits get longer until
some exceed the timeout, and the errors arrive in a burst at the busiest moment — which looks like an
outage rather than a gradual degradation. Raising the timeout converts them into slow requests, which
is usually better and is still a symptom of a lock held too long.

**The review comment a senior engineer leaves:** *"we moved the budget into the database, which fixes
the two-instance problem, and the code is still `SELECT` then `UPDATE` in Python. Two requests in the
same window both read the old count and one increment is lost — the counter now under-counts, so we
will over-spend and our own numbers will say we did not. Make it a single conditional `UPDATE`, or
wrap it in `BEGIN IMMEDIATE`. And set `busy_timeout`; the default is zero."*

**The interview question:** *"you moved a counter into shared storage. Are you done?"* The honest
answer: *"No — that fixed reachability, not correctness. Read, add, write is three statements with a
window in the middle, so two writers both read the old value and one increment is lost. I measured it:
four processes doing a hundred increments landed on thirty. The fix is either a single statement that
does the arithmetic in the database — `UPDATE … SET n = n + 1 WHERE n < limit`, where the row count
tells you if it was allowed — or an explicit `BEGIN IMMEDIATE` transaction. `IMMEDIATE` matters:
a plain `BEGIN` takes the lock after the read, and on write-ahead logging that transaction is pinned
to a snapshot somebody else has already moved past, so it fails outright rather than waiting. On
SQLite you also
have to set `busy_timeout`, because the default is zero and that is where most of the 'SQLite cannot
do concurrency' reputation comes from."*
