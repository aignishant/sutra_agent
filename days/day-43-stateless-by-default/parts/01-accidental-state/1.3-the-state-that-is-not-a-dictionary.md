# 1.3 — The state that is not a dictionary

## One-line answer

Most of the state in a real server is not a container at all — it is an open connection, a file
handle, a lock, a context variable or a seeded generator — and every one of those belongs to exactly
one process, which is why looking only for dictionaries finds about half the problem.

## The story

Your building has one pipe coming in from the street and a pump in the basement.

Each flat has a tap. The tap is not water. It is not a container of water either — there is nothing
inside it. It is a *connection to* the water, and it belongs to one flat: your tap is open or shut,
your washer is worn or new, your tap and the one upstairs are two different objects with two
different histories.

The pump has a limit. It can push enough for a few taps at once and no more. Open every tap in the
building on a summer evening and everybody gets a trickle, including the person who opened theirs
first and did nothing wrong.

And there is the failure everyone in a shared building has seen at least once: somebody's tap is
left running behind a locked door while they are away. Nothing is stored anywhere. No container is
full. But the state of that tap is affecting everybody, and you cannot fix it from your flat,
because it does not belong to your flat.

## The idea in plain language

[1.1](1.1-the-dictionary-nobody-called-state.md) taught the obvious shape of accidental state: a
dictionary at module level. If that were the only shape, this day would be short. It is not, and the
others are harder to see because they do not *contain* anything.

Here are the ones you will actually meet.

**An open connection.** `sqlite3.connect(...)` or a database engine created at module level hands
you a live object that owns a socket or a file descriptor. It has a transaction state, a cursor
position and, in SQLite's case, a thread it was created on. It exists in one process and cannot be
shared with another.

**A connection pool.** The grown-up version of the same thing: a set of open connections kept ready
so a request does not pay to open one. The pool has a size, and the size is per process. Two
instances with a pool of ten are twenty connections to your database, not ten — which is how a
service that was fine yesterday exhausts a database's connection limit on the day it scales out.

**An open file.** `LOG = open("audit.log", "a")` at module level gives you a handle with a buffer
and a write position. Two processes appending to the same file interleave their buffers, so lines
arrive torn or out of order. On Windows a second process may not be able to open it at all.

**A lock.** `threading.Lock()` at module level does exactly what it promises: it stops two *threads
in this process* from entering a section at once. It has no opinion about the other process, so the
mutual exclusion you think you have is per instance. This one is dangerous precisely because the
code looks careful.

**A context variable.** `contextvars.ContextVar` holds a value that belongs to the current task, so
a request handler can stash the caller's identity and a function five levels down can read it
without it being passed as an argument. That is useful and legitimate. It becomes state when a value
is set and never reset, because the underlying worker is reused for the next request — and the next
caller inherits the previous caller's context.

**A seeded generator.** `random.seed(42)` or a module-level `random.Random()` makes one process's
sequence reproducible. Two processes then produce the *same* sequence, which is the opposite of what
anyone wants from a random identifier. If you are generating anything that must be unique, use
`secrets.token_urlsafe`, which does not have a shared starting point.

The single sentence underneath all six: **anything created once at start-up and used by request
handlers afterwards is per-instance, whether or not it holds data.**

## The mechanism

Each of the six, in the form it usually appears, with what it costs on two instances:

| Written at module level | Looks like | Per-instance cost |
| --- | --- | --- |
| `CON = sqlite3.connect(DB)` | an optimisation | one transaction state, one owning thread |
| `POOL = create_engine(URL, pool_size=10)` | best practice | 10 × instance count connections to the database |
| `LOG = open("audit.log", "a")` | convenience | interleaved buffers, torn lines, a Windows lock |
| `GATE = threading.Lock()` | care | mutual exclusion inside this process only |
| `CALLER = ContextVar("caller")` | plumbing | a leaked value if it is set and never reset |
| `random.seed(42)` | determinism | every instance generates the identical sequence |

The connection is the one to see happen, because it fails loudly enough to teach:

```python
import sqlite3
import threading

CON = sqlite3.connect(":memory:")


def worker():
    CON.execute("SELECT 1")


t = threading.Thread(target=worker)
t.start()
t.join()
```

**Line by line:**

- `CON = sqlite3.connect(":memory:")` at module level is the whole setup. `":memory:"` keeps the
  example self-contained; a file path behaves the same way for this failure.
- `def worker()` uses `CON` without opening anything, which is exactly the appeal of a module-level
  connection: every function gets one for free.
- `threading.Thread(target=worker)` is standing in for what a server does on its own. You never
  write this line in an ASGI application, because the framework runs handlers on a worker thread or
  an event-loop task for you — which is why the failure arrives without anybody writing threading
  code.
- `t.start()` then `t.join()` runs the body somewhere other than the thread that created `CON`, and
  waits for it. The `join` matters: without it the process can exit before the thread raises, and
  the error disappears.
- There is no exception handler anywhere, on purpose. Principle 10: the error is the output.

The lab's own store does the opposite of all of this, and it is worth seeing that the fix is not
complicated:

```python
# days/day-43-stateless-by-default/lab/store.py  (extract)
def connect() -> sqlite3.Connection:
    """Open the shared database with the settings that make it safe to share."""
    con = sqlite3.connect(DB_PATH, timeout=5.0, isolation_level=None)
    con.execute("PRAGMA journal_mode=WAL")
    con.execute("PRAGMA busy_timeout=5000")
    con.executescript(SCHEMA)
    return con
```

**Line by line:**

- `def connect()` is a function, not an assignment. Nothing is created at import time, so there is
  nothing for a second instance to have its own private copy of.
- Every caller opens its own connection and closes it, so the connection is scoped to the work
  rather than to the process. On SQLite that is cheap. On a networked database it is not, which is
  why real code uses a pool — and a pool is fine, as long as you *count* it per instance
  (`pool_size × instances`) when you size the database.
- `timeout=5.0` is how long this connection waits for a lock another writer holds before giving up.
  Two instances writing to one file is the whole point of the day's fix, so the wait has to be
  deliberate rather than accidental.
- `isolation_level=None` turns off the Python driver's automatic transaction handling, so `BEGIN`
  and `COMMIT` are written where you can see them. [4.2](../04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md)
  is where that matters.
- The two `PRAGMA` lines are per-connection settings, which is why they are here and not once at
  start-up: a setting applied to a connection that no longer exists has been applied to nothing.
- `executescript(SCHEMA)` uses `CREATE TABLE IF NOT EXISTS`, so any instance can be the one that
  creates the tables and none of them needs to be first. That is the same principle as the rest of
  the day, applied to start-up rather than to requests.

## When it breaks

Running the module-level connection above, on 2026-09-05:

```text
Exception in thread Thread-1 (worker):
Traceback (most recent call last):
  File "...\Lib\threading.py", line 1075, in _bootstrap_inner
    self.run()
  File "...\Lib\threading.py", line 1012, in run
    self._target(*self._args, **self._kwargs)
  File "...\t.py", line 5, in worker
    CON.execute("SELECT 1")
sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread. The object was created in thread id 13380 and this is thread id 1296.
```

Read the last line carefully, because it is more interesting than it looks. It names two thread
identifiers and says nothing about instances, deployment or statelessness. A developer meeting it
for the first time reaches for the documented escape hatch — `check_same_thread=False` — which makes
the message go away and replaces a loud error with a silent one: several threads now share one
connection and one transaction, so a `BEGIN` on one request can be committed by another.

The right reading of that message is *"this object belongs to whoever made it"*, and that is a
sentence about processes as much as threads. The fix is not a flag. It is to stop creating the thing
at start-up.

The other five in the table fail without a message at all. A lock that only locks within one process
produces two callers doing the thing you locked around, and no error anywhere. A pool that is per
instance produces a database that refuses new connections during the busiest part of the day, with
the error landing on your database rather than in your code. Those are the ones the scan in section
2 exists for: you cannot wait for an exception that never comes.

## In production

**What a professional writes instead:** connections come from a pool the framework opens at start-up
and hands out per request, and the pool size is chosen with the instance count in the arithmetic.
Files are opened, written and closed inside the request, or better, not written at all — logs go to
standard output and the platform collects them, which is the only approach that works when the
filesystem is temporary. Locks that protect anything shared are held in the store, not in the
process: a row lock or a conditional update, not a `threading.Lock`.

**What degrades at scale:** the resources multiply by the instance count and the limits do not.
Ten instances with a pool of twenty is two hundred connections against a database configured for a
hundred, and the symptom is not a slow service — it is new instances that fail to start, which is
precisely when you are scaling up because you are busy.

**The failure mode that only appears with real traffic:** the context variable that is set and not
reset. With one request at a time you never see it, because the next request overwrites the value
before anybody reads it. Under concurrency, a handler that returns early leaves the value behind,
and the next request on that worker reads somebody else's caller identity. That is not a wrong
answer; it is an authorisation bug, and it is the reason
[Day 37's auth work](../../../day-37-auth-and-elicitation/) belongs to the request rather than to
the process.

**The review comment a senior engineer leaves:** *"`GATE = threading.Lock()` at module level and the
comment says it prevents double submission. It prevents double submission within one process. We run
several. This needs to be a unique constraint or a conditional update in the database — the lock is
giving us the feeling of safety and none of it."*

**The interview question:** *"other than caches and globals, where does state hide in a Python
service?"* The honest answer: *"In everything created at import time. An open database connection, a
connection pool, an open file handle, a `threading.Lock`, a context variable that never gets reset,
a seeded random generator. None of them look like state because none of them contain data, but all
of them are per process, so a lock only locks one instance and a pool of ten is ten per instance.
The one I have actually been bitten by is the pool: the arithmetic that matters is pool size times
instance count against the database's connection limit, and nobody does that multiplication until
the autoscaler does it for them."*
