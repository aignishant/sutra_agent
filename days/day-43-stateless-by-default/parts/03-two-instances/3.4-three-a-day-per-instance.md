# 3.4 — 💥 Three a day, per instance

## One-line answer

A limit enforced by a counter inside each process is not one limit — it is one limit **per instance**,
so a service allowed three requests a day allows three times the number of containers, and the number
of containers is chosen by an autoscaler rather than by you.

## The story

The tea shop gives out a card: nine stamps, tenth cup free.

You collect your stamps over a few weeks, and then you notice the shop has opened a second branch
across town, with the same name, the same cards and the same stamp. The stamp on your card does not
say which branch put it there.

So you can get a card stamped at both. Two cards, filled at the same time, and the shop is giving
away two free cups where it had budgeted for one. Nobody cheated exactly — you used the card the way
the card works. The rule *"nine stamps, one free cup"* was written when there was one shop, and
opening a second branch changed what that sentence means without anybody rewriting it.

The owner finds out at the end of the month, from the numbers, which is the worst way to find out
anything.

## The idea in plain language

A **rate limit** is a rule about how many times something may happen in a period. A **quota** is the
same idea with a longer period and usually a harder edge: twenty requests per day, and then no more.

The naive implementation is a counter and a comparison. Increment on use, refuse when the count
passes the limit. It is three lines and it is obviously correct — on one process.

On *n* processes it enforces `limit × n`, because each process has its own counter and no process
knows about the others. Nothing about it fails; each instance is scrupulously enforcing the rule it
was given. The rule was just given to each of them separately.

Three properties make this specific bug nastier than the other two failures in this section.

**The multiplier is not under your control.** Instance count is an autoscaler's decision, changing
through the day with traffic. So the effective limit changes with load, which means the constraint is
loosest exactly when the service is busiest — the opposite of what a limit is for.

**Dividing does not fix it.** The obvious repair is to give each instance `limit / n`. That fails in
both directions. Traffic is never even, so the busy instance exhausts its share while idle instances
sit on unused budget, and you are refusing requests while under the real limit. And `n` is not a
constant, so the division is against a number that was true when the configuration was written.

**The consequence is external.** A cache disagreeing with itself is your problem. A quota exceeded is
somebody else's system telling you to stop — and, on a free tier, it is the whole day's budget gone.

## Why Sutra needs it

Because this is the exact shape of Sutra's own budget, and the number is small enough to lose in one
afternoon.

Every day of this curriculum is designed against **twenty free-tier generate requests per day** for
`gemini-3.7-flash`, read off a live `429` on Day 2 and recorded in `docs/PACKAGES.md`.
[Day 24](../../../day-24-token-accounting-and-budgets/) built the accounting for it. That accounting
is a counter, and a counter is the thing this part is about.

Run `sutra-mcp` twice with a per-process counter and the twenty becomes forty as far as your code is
concerned — and stays twenty as far as the provider is concerned. The failure does not arrive as a
number in a dashboard. It arrives as a `429` from the provider, at whatever moment the real twentieth
request happens, on a code path that believed it had budget left. That is a service that stops
working for the rest of the day, caused by a variable that was never in your configuration.

It also settles a decision for [Day 44](../../../day-44-client-hardening/). Retrying a `429` with
backoff is correct client behaviour and it does nothing about this, because the budget really is
gone. The counter has to be right *before* the request is sent.

## The mechanism

The broken version and the fixed version sit side by side in the lab server, chosen by one variable:

```python
# days/day-43-stateless-by-default/lab/leaky_server.py  (extract)
# --- leak 2: a counter that counts this process's requests and no others. ---
SPENT = itertools.count(1)
QUOTA_LIMIT = 3


@mcp.tool()
def spend_quota() -> str:
    """Spend one unit of a daily quota of three."""
    if SHARED:
        allowed, spent = store.spend("gemini", QUOTA_LIMIT)
        return f"{INSTANCE} allowed={allowed} spent={spent}/{QUOTA_LIMIT}"
    spent = next(SPENT)
    allowed = spent <= QUOTA_LIMIT
    return f"{INSTANCE} allowed={allowed} spent={spent}/{QUOTA_LIMIT}"
```

**Line by line:**

- `itertools.count(1)` is shape 2 from
  [2.2](../02-finding-the-state/2.2-the-four-shapes-worth-flagging.md): not a container, entirely
  per-process, and the scan finds it.
- `QUOTA_LIMIT = 3` instead of twenty, so the lab spends six requests instead of forty-one. The
  arithmetic is identical and the run is short.
- `next(SPENT)` then `spent <= QUOTA_LIMIT` is the whole naive limiter. Read it and try to find the
  fault; there is not one. It is correct code implementing a rule that no longer means what it says.
- `store.spend("gemini", QUOTA_LIMIT)` is the same rule against a row in a file both instances open.
  Same signature, same return, same message format — the difference is entirely *where the number
  lives*, which is the day's whole argument in one branch.
- The key is `"gemini"` rather than the instance, so the row is the provider's budget and not this
  process's. A shared store with a per-instance key would be the same bug with extra steps, and it is
  a mistake people genuinely make.
- The reply reports `spent` after the decision, so a refused caller can see how far over it is. That
  matters more than it looks: *"denied"* sends somebody to read code, and *"denied, 3/3"* sends them
  to look at the budget.

And the shared version, which is short because SQLite is doing the hard part:

```python
# days/day-43-stateless-by-default/lab/store.py  (extract)
def spend(key: str, limit: int) -> tuple[bool, int]:
    """Spend one unit of a shared quota. Returns (allowed, spent_after)."""
    con = connect()
    try:
        con.execute("BEGIN IMMEDIATE")
        row = con.execute("SELECT spent FROM quota WHERE key = ?", (key,)).fetchone()
        spent = row[0] if row else 0
        if spent >= limit:
            con.execute("COMMIT")
            return False, spent
        spent += 1
        con.execute(
            "INSERT INTO quota (key, spent) VALUES (?, ?) "
            "ON CONFLICT(key) DO UPDATE SET spent = excluded.spent",
            (key, spent),
        )
        con.execute("COMMIT")
    finally:
        con.close()
    return True, spent
```

**Line by line:**

- `BEGIN IMMEDIATE` takes the write lock *before* the `SELECT`, so no other instance can read the same
  value and decide to spend it too. A plain `BEGIN` would defer the lock until the first write, which
  is after the decision has already been made on a stale read — and that is
  [4.2](../04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md)'s entire subject.
- `SELECT` then compare then `UPDATE` is a read-modify-write. Being inside the transaction is what
  makes it one indivisible step rather than three interleavable ones.
- `if spent >= limit: COMMIT; return False` commits rather than rolls back, because nothing was
  changed and holding the lock any longer than necessary is how you build a queue.
- `ON CONFLICT(key) DO UPDATE` is an upsert, so the first spend of the day does not need a separate
  "create the row" path. One statement that works whether or not the row exists removes a whole class
  of start-up race.
- `return True, spent` gives the caller the post-decision number, matching the naive version's
  message exactly so the two arms of the run are comparable line for line.
- `finally: con.close()` — [1.3](../01-accidental-state/1.3-the-state-that-is-not-a-dictionary.md)'s
  rule. The connection belongs to the call, not to the process.

## When it breaks

Six requests against a limit of three, on 2026-09-05:

```text
-- the quota: a limit of 3, asked for 6 times --
   B allowed=True spent=1/3
   A allowed=True spent=1/3
   B allowed=True spent=2/3
   A allowed=True spent=2/3
   B allowed=True spent=3/3
   A allowed=True spent=3/3
   allowed 6 of 6 against a limit of 3
```

Six of six allowed. Read the `spent` column downwards and the bug is legible without any explanation:
`1/3`, `1/3`, `2/3`, `2/3`, `3/3`, `3/3`. Each number appears twice, because there are two counters
and each of them is counting correctly to three.

Not one of those six requests was refused, and not one of them was wrong to be allowed *from where it
was decided*. There is no error to catch and nothing to log. The failure is a total, and totals are
not something a request handler can see.

Now the same run with the counter moved into the store:

```text
   B allowed=True spent=1/3
   A allowed=True spent=2/3
   B allowed=True spent=3/3
   A allowed=False spent=3/3
   B allowed=False spent=3/3
   A allowed=False spent=3/3
   allowed 3 of 6 against a limit of 3
```

The instance letters still alternate. The numbers no longer repeat, because there is one number.
Three allowed, three refused, and — the detail worth pausing on — **the refusals come from both
instances**. Neither of them is the one that "owns" the budget. Any instance can refuse, because any
instance can read the total.

The real-world version of the broken run prints none of this. It prints the line
[Day 2 recorded](../../../day-02-llm-mechanics/parts/01-first-contact/1.4-the-first-interaction.md)
off a live free tier:

```text
google.genai.errors.ClientError: 429 RESOURCE_EXHAUSTED. {'error': {'code': 429,
'message': 'You exceeded your current quota', 'status': 'RESOURCE_EXHAUSTED',
'details': [{'@type': 'type.googleapis.com/google.rpc.RetryInfo',
'retryDelay': '47s'}]}}
```

— from the provider, on a request your own accounting believed was inside budget, with the rest of
the day's work now blocked.

## In production

**What a professional writes instead:** the counter lives where every instance can reach it, and the
increment is atomic — a single database statement, or a cache server's atomic increment, never a read
followed by a write from the application. For rate limits rather than daily quotas the usual choice
is a token bucket held in a shared cache, which is
[Day 24's leaky-bucket reading](../../../day-24-token-accounting-and-budgets/) with its state moved
out of the process. The rule of thumb: **if exceeding the limit has a consequence outside your
system, the counter cannot be inside one process.**

**What degrades at scale:** the limit itself, linearly and invisibly. Ten instances turn a
twenty-a-day budget into two hundred as far as your code is concerned. And because instance count
tracks traffic, the over-spend is largest on your busiest day, which is the day the provider's limit
matters most.

**The failure mode that only appears with real traffic:** uneven distribution defeating the division
fix. A team that discovers this bug and responds with `limit / instances` finds that real traffic is
lumpy — one instance takes a burst, exhausts its share, and starts refusing while the others are
idle. The service now refuses requests *and* under-uses its budget, which is a strictly worse
position than the bug they set out to fix, and much harder to explain.

**The review comment a senior engineer leaves:** *"the daily budget is an `itertools.count` at module
level. That is one budget per container, so with three containers we can spend three times the free
tier and find out from a 429 rather than from our own accounting. This needs to be a row we increment
inside a transaction. And do not 'fix' it by dividing the limit by the replica count — our traffic is
not even, and we would start refusing while under budget."*

**The interview question:** *"you have a rate limiter. How do you know it works with more than one
instance?"* The honest answer: *"By spending past the limit through a load balancer and counting how
many were allowed. If the answer is the limit times the instance count, the counter is in the
process. I would not fix it by dividing the limit — traffic is lumpy, so one instance burns its share
and starts refusing while the others are idle, and now you are both over-refusing and under-using the
budget. The counter has to be shared and the increment has to be atomic: one statement in a
transaction, or an atomic increment in a cache, never read-then-write from application code. And the
test is cheap — six requests against a limit of three."*
