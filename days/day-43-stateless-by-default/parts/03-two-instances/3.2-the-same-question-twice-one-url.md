# 3.2 — The same question, twice, one URL

## One-line answer

The probe sends the ordinary request sequence to one address and prints which instance answered each
one, so "stateless" stops being a property you argue about and becomes four lines of output with a
count at the bottom and an exit code.

## The story

The school marks two hundred papers with two markers and one mark scheme.

Most of it is fine, because most questions have one answer. Then a moderator pulls twenty papers at
random and marks them again, and the point of that exercise is not to find bad marking. It is to
find **questions where the two markers disagree** — the ones where the scheme left room, and the mark
you got depended on which desk your paper landed on.

Nobody at the school thinks this is unfair to the markers. Both of them were doing the job carefully.
The disagreement is information about the *scheme*, and the only way to get that information is to
put the same paper in front of both of them and compare.

What the moderator does not do is send each marker a different set of questions and then declare that
both sets were marked consistently.

## The idea in plain language

The probe is a client. It does three things and nothing else: it starts the servers, it sends a fixed
sequence of ordinary requests to one address, and it prints who answered what.

The sequence is deliberately unremarkable — this is the moderator's rule from the story. Every
request is one a real caller would send:

1. **Four `whoami` calls.** They establish that alternation is happening at all, and they give you a
   picture of the rig before anything interesting occurs. If this does not print `A B A B`, nothing
   after it means anything.
2. **A read, a write, and two more reads of the same ticket.** The most ordinary sequence in any
   support system.
3. **A handle minted and then used twice.** Exactly the cross-call pattern
   [Day 32's 3.4](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.4-state-that-travels-in-the-payload.md)
   said was the correct shape and [Day 36](../../../day-36-long-jobs-and-tasks/) built on.
4. **Six requests against a limit of three.** A quota, asked to do its job.

Each block ends with a comparison the probe makes itself, and the run ends with a count of the
behaviours that did not survive. That count is the exit code, so this is a check in the sense
[2.4](../02-finding-the-state/2.4-a-scan-that-can-go-red.md) meant.

And there is an **ablation switch**: `--shared` restarts the identical servers with one environment
variable changed, moving all three pieces of state out of the processes and into a shared file. Same
code, same requests, same balancer. If the second run is clean and the first is not, the difference
can only be where the state lives — which is the claim the day is making, demonstrated rather than
asserted.

## Why Sutra needs it

Because the phase gate on [Day 45](../../../day-45-the-mcp-audit/) says `sutra-mcp` serves tools
statelessly, and a gate needs evidence with an exit code.

Everything `sutra_mcp/` does today is exercised by this shape of sequence. The tools from
[Day 34](../../../day-34-building-sutra-mcp-tools/) are the reads. The task handles from
[Day 36](../../../day-36-long-jobs-and-tasks/) are the mint-then-use block. The archive from
[Day 39](../../../day-39-database-tools/) is what the reads read. The budget from
[Day 24](../../../day-24-token-accounting-and-budgets/) is the quota. There is nothing in the probe
that is not already in the system.

So when you write `sutra_mcp/app.py` in [5.1](../05-deploy-shape/5.1-an-object-not-a-program.md),
this is the harness that says whether it is deploy-shaped or merely deploy-*shaped-looking*. Point
the probe's server command at your own package instead of the lab's leaky one and the same output
grades your code.

## The mechanism

Every request the probe sends goes through one function:

```python
# days/day-43-stateless-by-default/lab/twoup.py  (extract)
def post(method: str, params: dict | None = None, session: str | None = None) -> tuple[dict, dict]:
    """POST one JSON-RPC request to the single URL. Returns (body, response headers)."""
    payload: dict = {"jsonrpc": "2.0", "id": next(IDS), "method": method}
    if params is not None:
        payload["params"] = params
    headers = {
        "Content-Type": "application/json",
        "Accept": "application/json, text/event-stream",
        "MCP-Protocol-Version": PROTOCOL_VERSION,
        "Mcp-Method": method,
    }
    if session is not None:
        headers["mcp-session-id"] = session
    req = urllib.request.Request(
        URL, data=json.dumps(payload).encode(), method="POST", headers=headers
    )
    try:
        with urllib.request.urlopen(req, timeout=10) as resp:
            return json.loads(resp.read() or b"{}"), resp.headers
    except urllib.error.HTTPError as exc:
        return {"http_status": exc.code, **json.loads(exc.read() or b"{}")}, exc.headers
```

**Line by line:**

- `URL` is `http://127.0.0.1:8900/mcp` — the dispatcher, never a backend. Nothing in the probe knows
  that 8901 and 8902 exist, which is the same discipline the story's moderator keeps.
- `next(IDS)` from `itertools.count(1)` gives every request a distinct JSON-RPC `id`. This is
  per-process state in the client and is entirely correct there: the probe is one caller, and a
  caller is allowed to remember its own request numbering.
- `"Accept": "application/json, text/event-stream"` names both reply shapes the transport allows. The
  lab server is built with `json_response=True` so it always chooses JSON, but sending the header
  that a compliant client sends keeps the probe honest.
- `"MCP-Protocol-Version": PROTOCOL_VERSION` is `2025-11-25`, not `2026-07-28`, and that is not a
  typo — see *When it breaks*.
- `"Mcp-Method": method` is the routable header from
  [Day 32's 3.1](../../../day-32-mcp-stateless-core/parts/03-headers-and-caches/3.1-the-label-on-the-envelope.md).
  Nothing in this rig routes on it, and it is sent anyway, because it is what a client on the current
  revision sends and a gateway in front of a real deployment would.
- `if session is not None` is used by exactly one arm of the probe, the stateful one in
  [3.5](3.5-the-handle-b-had-never-heard-of.md). The stateless path never sends it, because there is
  nothing to send.
- `except urllib.error.HTTPError` folds the HTTP status into the returned body. `urlopen` raises on
  4xx and 5xx, and a 404 carrying a JSON-RPC error is a *reply* rather than a transport failure —
  losing it in an exception would throw away the most interesting result in the day.
- The response headers come back alongside the body because the session identifier travels in a
  header rather than in the payload. Returning only the body would make
  [3.5](3.5-the-handle-b-had-never-heard-of.md) impossible to write.

And the comparison for the first block, which is small enough to read in one go:

```python
# days/day-43-stateless-by-default/lab/twoup.py  (extract)
        print("who answered   :", " ".join(tool("whoami") for _ in range(4)))
```

**Line by line:**

- `tool("whoami")` sends a `tools/call` and returns the first text content block. Four of them,
  joined with spaces.
- Four rather than two, because two would print `A B` and leave you unsure whether that was
  alternation or coincidence. Four shows the cycle repeating.
- This line asserts nothing. It is the picture of the rig that every later assertion is read against,
  and if it ever prints `A A A A` the rest of the run is worthless and you need to look at the
  dispatcher before you look at the server.

## When it breaks

The full run of the leaky arm, on 2026-09-05:

```text
state = process memory   routing = round-robin over A and B

who answered   : A B A B

-- the cache: one ticket, one status change, two answers --
   A cached=False 4521: printer offline since Tuesday [status=open]
   B wrote 4521 -> resolved
   A cached=True 4521: printer offline since Tuesday [status=open]
   B cached=False 4521: printer offline since Tuesday [status=resolved]

-- the handle: minted by one instance, used by the next --
   minted: draft-A-1
   ERROR B: unknown handle 'draft-A-1'
   Sorry about the delay. Line 3.

-- the quota: a limit of 3, asked for 6 times --
   B allowed=True spent=1/3
   A allowed=True spent=1/3
   B allowed=True spent=2/3
   A allowed=True spent=2/3
   B allowed=True spent=3/3
   A allowed=True spent=3/3
   allowed 6 of 6 against a limit of 3

behaviours that did not survive: 3
```

Four behaviours went in and one came out intact. The scoreboard:

| Behaviour | Survived? | Why | Where |
| --- | --- | --- | --- |
| answering at all | yes | the tool needs nothing but its arguments | — |
| a cached read | **no** | two caches, two answers to one question | [3.3](3.3-two-answers-to-one-question.md) |
| a minted handle | **no** | the draft is in one process's memory | [3.5](3.5-the-handle-b-had-never-heard-of.md) |
| a quota | **no** | a limit of three enforced twice is a limit of six | [3.4](3.4-three-a-day-per-instance.md) |

Now the two things about this output that are easy to miss.

**Every single request succeeded.** There is no HTTP error, no exception, no `isError: true` anywhere
in that run. The three failures are all differences between successful answers. Any monitoring built
on status codes would have shown a perfectly healthy service for the whole run — which is why the
probe compares answers rather than counting errors.

**The protocol version says `2025-11-25`.** The specification is at `2026-07-28`, and this probe
deliberately sends the older number, because `mcp==1.29.1` tops out there — the gap
[Day 34's 5.2](../../../day-34-building-sutra-mcp-tools/parts/05-lifecycle/5.2-what-your-server-actually-answers.md)
measured and this day does not close. Send the current revision instead and the server refuses the
request outright, so the probe would measure the pin rather than the architecture. That substitution
is written in a comment at the top of `twoup.py`, and it is exactly the kind of quiet accommodation
that has to be *visible* in a test rather than discovered later by somebody reading a passing run and
believing more than it says.

## In production

**What a professional writes instead:** the same idea, promoted to a test that runs on every change.
Two instances of the real server started as fixtures, a real client driven against them, and
assertions on the *answers* rather than on the status codes. It belongs with the integration tests
rather than the unit tests, it needs no network and no credentials, and it is the single highest-value
test a service like this has, because it is the only one that can fail for the reason production
fails.

**What degrades at scale:** the fixed sequence. Two instances and a scripted order find state that
crosses a request boundary; they do not find state that only breaks under concurrency, when two
requests are in flight at once and interleave inside a read-modify-write. That is a different and
harder test — [4.2](../04-where-state-goes/4.2-shared-is-not-the-same-as-safe.md) is about the bug it
finds — and it needs concurrent load rather than a script.

**The failure mode that only appears with real traffic:** an odd number of instances. Two instances
and strict alternation give a perfectly regular `A B A B`, so every "next request" is a different
process. Three instances with real, uneven traffic give you sequences where the same process sometimes
does answer twice in a row, and a bug that needs two consecutive requests on different instances then
appears at some fraction of a percent instead of every time. Regular alternation is a *sharper*
instrument than production, which is exactly what you want in a test and exactly why the production
symptom looks like noise.

**The review comment a senior engineer leaves:** *"the two-instance test asserts on exit codes. Every
request in the failing run returned 200, so it passes. Assert on the answers: read the ticket twice
and require the two results to be equal, spend the quota seven times and require exactly the limit to
be allowed. The bug we have is two successful answers that disagree, and no status code will ever
tell you that."*

**The interview question:** *"what does your integration test for a stateless service actually
assert?"* The honest answer: *"That the same question asked twice through one URL gets the same
answer, and that a limit enforced anywhere is enforced everywhere. Not that requests succeed — in the
run where our server was broken, every request succeeded. The failures were all pairs of successful
answers that disagreed, which is invisible to anything watching status codes. The rig is two
processes and a round-robin, the requests are the ordinary ones, and there is one environment
variable that moves the state into a shared store so I can show the same test going green without
changing a line of the server."*
