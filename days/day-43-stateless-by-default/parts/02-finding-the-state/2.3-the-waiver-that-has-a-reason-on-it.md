# 2.3 — The waiver that has a reason on it

## One-line answer

Every useful check produces some findings that are correct code, and the only two honest responses
are to **fix the shape** or to **waive it with a written reason** — because the third response, a
silent switch-off, is how a check that was working stops working and nobody notices.

## The story

The smoke alarm in the kitchen goes off every time somebody makes toast.

It is not broken. It is doing exactly what it was fitted to do: there is smoke, and it is telling
you. But it happens four mornings out of five, and after a fortnight of standing on a chair waving a
tea towel at the ceiling, somebody takes the battery out.

Now the kitchen has an alarm that never goes off. It looks identical to a kitchen with no problem.
Six weeks later nobody in the flat remembers that the battery is on the shelf behind the tin, and
the alarm above their heads is a plastic box.

There were two better endings available and both were more work on the day. Move the alarm, or the
toaster, so the smoke stops reaching it — the shape changes and the alarm goes back to being useful.
Or, if it truly has to stay where it is, leave a note taped to it saying *battery out, toaster
underneath, put it back when the toaster moves*. Either way, the next person to walk into the
kitchen can tell the difference between a solved problem and an abandoned one.

## The idea in plain language

The check from [2.2](2.2-the-four-shapes-worth-flagging.md) looks at the shape of a line, not at
what it means. It cannot tell a cache from a lookup table, because they are the same node in the
tree. So it will sometimes point at code that is entirely correct, and what happens next decides
whether anybody is still running it in six weeks.

Three responses, and only two of them are honest.

**Fix the shape.** Very often a flagged constant is flagged only because it was written as a mutable
type out of habit. Change `{"open", "resolved"}` to `frozenset({"open", "resolved"})` and the finding
disappears — not because the check was silenced, but because the code became something the check has
no reason to object to. This is the best outcome and it is usually available. Reach for it first.

**Waive it, with a reason.** Some findings are real state that is genuinely fine, and no rewrite
changes that. Then you record the decision *in the file, on the line*, so the next reader gets the
argument along with the code.

**Silence it.** Delete the rule, drop the file from the scan, or add a bare marker with no
explanation. Six weeks later that line is indistinguishable from code nobody ever looked at.

The scanner's waiver is a comment:

    # stateless-ok: <reason>

and it has one rule that most linters do not have: **the reason is mandatory**. A bare
`# stateless-ok:` with nothing after it does not waive anything; the finding still fires. That single
constraint is what stops the waiver from becoming the battery on the shelf, because it converts
"make the warning go away" into "write down why this is safe" — which is enough friction to make
fixing the shape look attractive, and enough record to make a bad waiver reviewable.

The reason is also the thing that can be *wrong later*. Code that changes under a waiver written for
an earlier version is the standard way a suppressed warning turns into an incident, and a reason
gives the next reader something to check the code against. A bare suppression gives them nothing to
disagree with.

## Why Sutra needs it

Because the first thing this scan will meet in `sutra_mcp/` is a pile of correct code.

Every module in that package has constants: the server name from
[Day 34's 1.3](../../../day-34-building-sutra-mcp-tools/parts/01-the-server-object/1.3-the-name-is-an-identity.md),
the tool allowlist from [Day 40](../../../day-40-filtering-and-allowlists/), the declared capability
set from [Day 41's `capabilities.py`](../../../day-41-capabilities-and-mcp-apps/), the forbidden
tokens from [Day 34's 4.3](../../../day-34-building-sutra-mcp-tools/parts/04-two-kinds-of-no/4.3-the-message-that-escaped.md).
Most of them are probably dictionaries and sets today, because that is how everybody writes a
constant.

If the first run of the scan produces a dozen findings and the response is a dozen waivers, the check
is dead on arrival. If the response is a dozen `frozenset` and tuple literals, the package gets
*measurably* safer — nothing can mutate a declared capability set by accident any more — and the
handful of findings that remain are the ones worth arguing about.

That is also why [Day 45's audit](../../../day-45-the-mcp-audit/) can rely on this: a gate whose
green state was reached by fixing shapes means something, and a gate whose green state was reached
by waiving everything means nothing at all.

## The mechanism

The waiver is nine lines, and every one of them is a decision:

```python
# days/day-43-stateless-by-default/lab/scan.py  (extract)
PRAGMA = "stateless-ok:"


    def waived(line: int) -> bool:
        """True when the line carries `# stateless-ok:` followed by a non-empty reason."""
        if not 0 < line <= len(lines):
            return False
        text = lines[line - 1]
        head, sep, reason = text.partition(PRAGMA)
        return bool(sep) and "#" in head and bool(reason.strip())
```

**Line by line:**

- `PRAGMA = "stateless-ok:"` includes the colon, so the marker cannot be matched by prose that
  happens to contain the phrase.
- `def waived(line)` is a closure over `lines`, the raw source text from
  [2.1](2.1-reading-the-code-without-running-it.md). It has to be: the tree carries no comments at
  all, because comments are not part of the program. Any comment-based waiver has to look back at the
  text.
- `if not 0 < line <= len(lines)` guards the index. A node's `lineno` is one-based and the list is
  zero-based, and a decorated function reports the line of the `def`, so this is a real off-by-one
  risk rather than defensive noise.
- `text.partition(PRAGMA)` splits once into before, separator, after. `partition` rather than `split`
  because the three pieces are exactly the three questions being asked, and it never raises when the
  separator is absent.
- `bool(sep)` — the marker is present.
- `"#" in head` — it is inside a comment. Without this, a string literal containing the phrase would
  waive the line, and a scanner defeated by putting text in a string is not a scanner.
- `bool(reason.strip())` — **there is a reason**. This is the line the whole part is about. Delete it
  and the tool becomes an ordinary suppression comment.
- The function returns a plain `bool` and is called at every finding site, so the waiver applies
  uniformly to all four shapes rather than being re-implemented per rule.

Here is the choice in the lab, on two lines that were both flagged on the first run:

```python
# days/day-43-stateless-by-default/lab/dispatcher.py  (extract)
BACKENDS = itertools.cycle(  # stateless-ok: which backend is next, never a correctness fact
    ["http://127.0.0.1:8901", "http://127.0.0.1:8902"]
)

# Headers that describe this hop rather than the message, so they are never copied through.
HOP_BY_HOP = frozenset({"host", "connection", "content-length", "transfer-encoding", "keep-alive"})
```

**Line by line:**

- `itertools.cycle(...)` is shape 2 and it is *real* per-process state: this dispatcher genuinely
  remembers which backend it sent the last request to.
- The waiver's reason is the argument, in eight words: the position in the cycle affects *which*
  instance answers and never *what* the answer is. If the dispatcher restarts and starts again at A,
  nothing is wrong. That is what makes it safe, and it is a claim the next reader can check against
  the code.
- The comment sits on the opening line of the call, not on the closing bracket, because the finding
  is reported at `node.lineno`, which is where the statement starts. A waiver on the wrong line does
  nothing and looks like it does something.
- `HOP_BY_HOP` took the other road. It was `{"host", ...}` — a plain set, flagged as shape 1 — and it
  became a `frozenset`. No waiver, no argument, and now nothing in the process can add an entry to it
  at runtime either.
- The two lines together are the whole lesson: identical findings, and the right answer was different
  for each, decided by asking *"could this legitimately change while the server runs?"*

## When it breaks

Take the reason off the `cycle` line and the finding comes straight back. Measured on 2026-09-05:

```text
dispatcher.py:22: module-level cycle(): BACKENDS - built once at import; no other instance shares it

1 finding(s) in dispatcher.py
exit: 1
```

Put the comment back, exactly as it was, and:

```text

0 finding(s) in dispatcher.py
exit: 0
```

Two runs, one comment. That is the mechanism working, and it is also the first way this breaks: a
waiver is line-based, so **moving the code moves the waiver off it**. Reformat the file, let a
formatter split the call across different lines, and the comment ends up on a line the finding is not
reported at. The check goes red on code nobody changed, which is annoying — but notice that it fails
in the *safe* direction. A waiver that silently survived a refactor would be worse.

The second and more serious break is the waiver that was true and stopped being true. `BACKENDS` is
safe because nothing reads meaning from the cycle position. The day somebody adds a per-backend
counter beside it and starts making decisions on the number, the comment is still there, still
authoritative-looking, and now wrong. Nothing in the scanner can detect that; only a reviewer reading
the reason against the code can. That is the argument for the reason being mandatory — it is the only
part of a waiver that anybody can disagree with.

The third break is social and it is the one that actually happens. Somebody in a hurry writes
`# stateless-ok: TODO` and moves on. It passes — `TODO` is a non-empty reason. The check cannot
enforce honesty, and pretending otherwise would be its own kind of dishonesty. What it can do is make
the bad waiver *visible in a diff*, which is where it gets caught.

## In production

**What a professional writes instead:** a waiver that names the reason, and a review rule that a
waiver is a change reviewers read rather than skim. Some teams go further and require an owner or a
ticket in the reason, so a suppression has somebody to expire it; that is worth it exactly when
suppressions have started outnumbering fixes. The nearest thing already in this repository is
`# noqa` with a mandatory explanation — the same rule, from
[the house style](../../../../CLAUDE.md), applied to a different check.

**What degrades at scale:** waivers accumulate and nothing removes them. A codebase two years old has
suppressions written for code that no longer exists, and each one is a small lie in the file. The
practical countermeasure is to make waivers cheap to audit — one grep, one line, one reason — which
is exactly why the marker is a fixed string rather than a decorator or a configuration file.

**The failure mode that only appears with real traffic:** a waiver that was correct under one
instance. Someone waives a counter with the reason *"only used for logging"*, and eighteen months
later a rate limit is built on that counter and the reason is quietly obsolete. That is
[3.4](../03-two-instances/3.4-three-a-day-per-instance.md), and it is why a green scan is a filter
rather than a proof.

**The review comment a senior engineer leaves:** *"three new `stateless-ok` lines in this diff and
all three say 'constant'. Two of them are sets that should just be frozensets — fix the shape and the
comment goes away. The third is a real cache, so the reason needs to say what happens when two
instances disagree, not that it is a constant, because it is not one."*

**The interview question:** *"how do you keep a lint rule alive once people start hitting false
positives?"* The honest answer: *"Make the fix easier than the waiver, and make the waiver cost a
sentence. On the check I wrote, most findings were constants written as mutable types, and changing
them to frozensets removed the finding and made the code better, so the common case has a real fix
rather than a suppression. For the genuine cases the waiver requires a written reason — a bare
marker does not suppress anything — because the reason is the only part a reviewer can disagree with
later. What I would not do is exclude files or drop the rule; a check that has been turned off looks
exactly like a codebase with no problem."*
