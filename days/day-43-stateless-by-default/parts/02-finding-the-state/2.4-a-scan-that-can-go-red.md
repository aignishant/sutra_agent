# 2.4 — A scan that can go red

## One-line answer

A finder becomes a check when it exits non-zero, and it becomes *trustworthy* when you have watched
it go red on purpose — including the case that matters most here, where it is green because there is
nothing to look at.

## The story

At the airline desk, your bag goes on the scale and the number decides.

Nobody debates the number. There is no conversation about whether the bag is nearly the limit, or
whether it was fine last time, or whether the person behind the desk thinks it looks heavy. The
scale says 24.6, the allowance says 23, and the bag either loses something or you pay.

The scale is useful precisely because it does not have opinions and cannot be persuaded. And you can
tell it is working, because you have watched it go over. A scale that has only ever shown numbers
under the limit is not a scale you trust — it is a scale you have not tested. That is why the person
in front of you moving two books into their hand luggage and watching the number drop is more
reassuring than any certificate on the wall.

## The idea in plain language

A program's **exit code** is the single number it hands back to whatever ran it. Zero means success;
anything else means failure. It is the only part of a program's output that other tools read
reliably, because everything else is text somebody has to look at.

That is the entire difference between a *report* and a *check*. A report prints findings and exits
zero, so the pipeline goes green either way and the findings scroll past. A check prints the same
findings and exits one, and now something stops.

Three properties make a check worth having, and the third is the one people skip.

**It must be able to fail.** A check that cannot go red on any input is not testing anything. This is
Principle 11, and it is the reason every eval in this curriculum arrives with a way to break it on
purpose.

**It must fail for the right reason.** A check that goes red on a syntax error, a missing file or an
empty directory is measuring your environment rather than your code. Each of those needs a decision:
which of them is a failure, and which is a different message.

**It must be honest about a green run.** This is the hard one. `0 finding(s)` can mean *your code is
clean* or it can mean *there was nothing to read*, and the two look identical. A check whose green
state cannot be distinguished from a check that did not run is the battery on the shelf from
[2.3](2.3-the-waiver-that-has-a-reason-on-it.md), one level up.

## Why Sutra needs it

Because of a specific, slightly uncomfortable fact you are about to see with your own eyes: **running
this scan over `sutra_mcp/` today prints zero findings, and that proves nothing at all.**

`sutra_mcp/` holds `__init__.py` and, until you type them, nothing else. The scan reads one empty
file and reports a clean result. It will keep reporting a clean result while you write `server.py`,
until the first time somebody adds a dictionary — which is the day it earns its place and not one day
sooner.

So the check has to be installed *before* it can catch anything, and it has to be proved on code that
does have findings. That is what [Day 45's audit](../../../day-45-the-mcp-audit/) inherits: not a
green line in a pipeline, but a check that has been seen red, on real code, by the person who wrote
it.

The wiring itself is not today's job. `./m check` already exists and
[Day 31](../../../day-31-the-quality-gate/) owns its shape; Day 45 adds the MCP audit line. Today
produces the check and the evidence that it works.

## The mechanism

The whole gate is the last eight lines of the scanner:

```python
# days/day-43-stateless-by-default/lab/scan.py  (extract)
def main(argv: list[str]) -> int:
    """Scan every path given and return 1 if anything was found."""
    targets = [Path(a) for a in argv] or [ROOT / "sutra_mcp"]
    findings: list[Finding] = []
    for target in targets:
        if not target.exists():
            print(f"skipped (does not exist): {target.as_posix()}")
            continue
        findings.extend(scan_path(target))
    for finding in findings:
        print(finding)
    scanned = ", ".join(t.as_posix() for t in targets)
    print(f"\n{len(findings)} finding(s) in {scanned}")
    return 1 if findings else 0
```

**Line by line:**

- `def main(argv) -> int` returns the exit code rather than calling `sys.exit` itself, so the function
  can be called from a test and its answer asserted. The one `raise SystemExit(main(sys.argv[1:]))` at
  the bottom of the file is the only place the process actually exits.
- `[Path(a) for a in argv] or [ROOT / "sutra_mcp"]` gives a default target, so `uv run python scan.py`
  with no arguments checks the package this day is about. `ROOT` is derived from `__file__`, so the
  default works from any directory.
- `if not target.exists(): print(...); continue` is a deliberate decision and it is arguable. A
  missing path prints a line and does **not** fail, because a path that is not there yet is a normal
  state in a curriculum that adds packages as it goes. In a production pipeline you would invert
  this: a check pointed at a path that does not exist is a check that is not running, and that should
  be loud. Say which you chose and why, in a comment, wherever you use it.
- The findings are printed *before* the summary line, so the last line of output is always the count.
  A person scanning a long log reads the last line.
- `f"\n{len(findings)} finding(s) in {scanned}"` names what was scanned, not just the number, which is
  the smallest possible answer to *"green because clean, or green because empty?"*. It does not
  answer it fully — see *When it breaks*.
- `return 1 if findings else 0`. Not `return len(findings)`: an exit code is a byte, so 256 findings
  would exit 0 and report success. This is a real bug that real tools have shipped.

Running it from the repository root over both packages, on 2026-09-05:

```bash
uv run python days/day-43-stateless-by-default/lab/scan.py sutra sutra_mcp
```

**Line by line:**

- Two targets in one run, because a scan of one package tells you nothing about the other and the
  exit code is shared.
- `sutra_mcp` is the day's real subject. `sutra` is here to prove the check works, since it holds
  code written on Days 3 and 4 that nobody wrote with statelessness in mind.
- **Zero model calls.** It reads files.

## When it breaks

That command, today:

```text
sutra/loop.py:21: module-level container: TICKETS - one per process; a second instance starts with its own empty one
sutra/loop.py:28: module-level container: KB - one per process; a second instance starts with its own empty one
sutra/loop.py:70: module-level container: TOOLS - one per process; a second instance starts with its own empty one
sutra/tools.py:9: module-level container: LOOKUP_TICKET - one per process; a second instance starts with its own empty one
sutra/tools.py:35: module-level container: SEARCH_KB - one per process; a second instance starts with its own empty one
sutra/tools.py:59: module-level container: DECLARATIONS - one per process; a second instance starts with its own empty one

6 finding(s) in sutra, sutra_mcp
exit: 1
```

Six findings, all from `sutra/`, none from `sutra_mcp/`. Both halves of that are worth a paragraph.

**The six are all false alarms — and all worth acting on.** `TICKETS` and `KB` are the fake archive
from [Day 3](../../../day-03-loop-hand-rolled/), `TOOLS` is the dispatch table, and the three in
`tools.py` are the tool declarations from [Day 4](../../../day-04-tools-by-hand/). Nothing writes to
any of them. They are constants, and they are all written as mutable types because that is how
everybody writes a constant. Per [2.3](2.3-the-waiver-that-has-a-reason-on-it.md) the response is to
fix the shape rather than to waive six lines — and note what that fix buys beyond a quiet scan:
`TICKETS` becoming immutable means no tool body can ever quietly edit the archive it is reading from.

**The zero from `sutra_mcp/` is the dangerous line.** It contains one empty `__init__.py`. The check
read it, found nothing, and was completely correct — and if you had glanced at that output expecting
reassurance about your MCP server, you would have received it, from a check that had nothing to look
at. This is the failure mode of every green result: *scanned nothing* and *found nothing* print the
same word.

The summary line names its targets partly for this reason, but naming a path is not the same as
proving it had content. A production version of this check counts the files it parsed and fails when
that count is zero, so a mis-pointed path is loud rather than reassuring. That is one of the pieces
left for you in the hub's build brief.

The last break is the one that gets shipped most often, and it is the reason for the final line
above:

```text
0 finding(s) in sutra_mcp
exit: 0
```

If `main` had returned `len(findings)` instead, a run with exactly 256 findings would exit 0 and your
pipeline would go green on the worst codebase it had ever seen. Exit codes are one byte and they wrap.

## In production

**What a professional writes instead:** the check has three outcomes, not two. Green, red, and
**error** — a distinct exit code for "the check could not run", so a syntax error, an unreadable
file or an empty target is never confused with a clean result. Most tools use 0, 1 and 2 for exactly
that split, and the reason is that a monitoring system reading only "did it exit zero" will otherwise
treat a broken check as a passing one for as long as it stays broken.

**What degrades at scale:** the check's usefulness, if it is allowed to be advisory. On a small
repository people read the output. On a large one, a check that prints findings and exits zero is
invisible within a month — which is why "make it fail" is not a stylistic preference but the whole
mechanism. The corollary is that a check which fails must also be *fixable*, which puts real weight
on the waiver from [2.3](2.3-the-waiver-that-has-a-reason-on-it.md) being available and cheap.

**The failure mode that only appears with real traffic:** none, for the third time in this section,
and it is now a point rather than a coincidence. Everything in section 2 runs on files. It cannot
observe a request, cannot see a second instance, and cannot tell you that the code it approved is
correct. Section 3 is the part with traffic, and this check exists to make section 3's job smaller
rather than to replace it.

**The review comment a senior engineer leaves:** *"the scan exits zero when the target path does not
exist. That means a typo in the path in the pipeline config gives us a permanently green check that
is reading nothing, and we will not find out until an incident. Fail on a missing path, and print the
number of files parsed so a zero is visible."*

**The interview question:** *"you have written a static check. How do you know it works?"* The honest
answer: *"I run it on code I know is bad and watch it go red, and then I fix one thing and watch it go
green. The specific trap with this kind of check is that green and 'nothing to read' look identical:
when I pointed mine at a package that was still empty it printed zero findings and exited zero, which
is technically correct and completely uninformative. So the version I would ship reports how many
files it parsed and fails when that is zero, and it uses a separate exit code for 'could not run' so
a broken check is never mistaken for a passing one."*
