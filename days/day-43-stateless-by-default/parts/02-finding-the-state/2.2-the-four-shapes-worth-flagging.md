# 2.2 — The four shapes worth flagging

## One-line answer

Four patterns catch almost all accidental per-instance state — a mutable literal, a call that returns
something stateful, a cache decorator, and a function that writes a module global — and everything
immutable is deliberately left alone, because a rule that fires on constants gets switched off.

## The story

You learn to check pockets before a wash, and you learn it by ruining one load.

After that you always check for the same four things, and they are four rather than everything,
because everything is not a habit anybody keeps. A pen, which is why the whole load came out
speckled. A tissue, which is why the whole load came out furry. Coins, which rattle round the drum
and chip the glass. A hairpin, which gets into the pump and makes a noise you will pay somebody to
explain to you.

You do not check for buttons. Buttons go through the wash constantly and nothing happens. If you
tried to check for buttons you would stop checking pockets at all, because the check would be
unbearable and you would decide you did not need it.

The four are not a complete list of things that can be in a pocket. They are the list that is worth
looking for every single time.

## The idea in plain language

The scanner from [2.1](2.1-reading-the-code-without-running-it.md) walks a module's top level. This
part is what it looks for when it gets there, and — just as important — what it deliberately ignores.

**Shape 1: a mutable literal.** `X = {}`, `X = []`, `X = set()` written directly, plus the
comprehension forms. Mutable means the object can be changed after it is made, so if any function
changes it, the change is remembered by this process and no other. This is
[1.1](../01-accidental-state/1.1-the-dictionary-nobody-called-state.md).

**Shape 2: a call that returns something stateful.** `sqlite3.connect(...)`, `itertools.count(...)`,
`open(...)`, `threading.Lock()`, `ContextVar(...)`, `create_engine(...)`. The value is not a
container, so shape 1 misses it entirely, and it is per instance for exactly the same reason. This
is [1.3](../01-accidental-state/1.3-the-state-that-is-not-a-dictionary.md).

**Shape 3: a cache decorator.** `@functools.lru_cache`, `@functools.cache`, `@cached_property`. No
assignment happens at all, so shapes 1 and 2 see nothing; the storage is attached to the function
object. This is [1.2](../01-accidental-state/1.2-the-cache-that-becomes-a-second-opinion.md).

**Shape 4: a `global` statement.** This is the only one that looks *inside* a function, and it is
the only one that proves intent. A module-level dictionary that nothing writes to is a constant with
the wrong type; a `global` in a request handler is somebody deliberately writing to module state at
request time. That is the difference between a smell and a decision.

Now the more interesting half: **what is not flagged, and why not.**

Anything immutable. A tuple, a `frozenset`, a string, a number. These cannot drift between instances,
because they cannot change at all. Two instances holding two copies of `frozenset({"open",
"resolved"})` hold the same value forever.

That exclusion is not a technicality. It is what makes the rule survivable, and it hands the reader
a *fix* instead of a *waiver*: a constant that the scanner objects to can usually be made immutable
in one keystroke, and then it is not just quiet — it is genuinely safer, because nothing can mutate
it by accident either.

One thing that is *not* an exclusion, and surprises people: `Final`. Writing
`STATUSES: Final = {"open"}` tells a type checker that the **name** will not be rebound. It says
nothing about the dictionary, which is as mutable as it ever was. `Final` protects the label on the
box, not the contents, so the scanner ignores it and flags the dictionary anyway.

## Why Sutra needs it

Because the four shapes are not a general theory of Python — they are a list drawn from what
`sutra_mcp/` is actually likely to grow, and each one has a named source.

Shape 1 is the drafts dictionary and any "already handled" set. Shape 2 is
[Day 39](../../../day-39-database-tools/)'s SQLite connection hoisted to module level for speed, and
[Day 36](../../../day-36-long-jobs-and-tasks/)'s progress lock. Shape 3 is the cache somebody will
put in front of the archive read the first time a tool feels slow. Shape 4 is the counter behind
[Day 24's budget](../../../day-24-token-accounting-and-budgets/), which becomes
[3.4](../03-two-instances/3.4-three-a-day-per-instance.md).

Four rules, four modules that already exist, one scan. That is why this list and not a longer one.

## The mechanism

The rules are three frozen sets and one tuple, at the top of the scanner:

```python
# days/day-43-stateless-by-default/lab/scan.py  (extract)
STATEFUL_CALLS = frozenset(
    {
        "dict",
        "list",
        "set",
        "defaultdict",
        "OrderedDict",
        "deque",
        "Counter",
        "count",
        "cycle",
        "connect",
        "create_engine",
        "open",
        "Lock",
        "RLock",
        "Semaphore",
        "Event",
        "Queue",
        "ContextVar",
        "Client",
        "AsyncClient",
        "Session",
        "Random",
        "seed",
        "Pool",
        "TemporaryDirectory",
    }
)

CACHE_DECORATORS = frozenset({"lru_cache", "cache", "cached_property", "cached"})

MUTABLE_LITERALS = (ast.Dict, ast.List, ast.Set, ast.DictComp, ast.ListComp, ast.SetComp)
```

**Line by line:**

- `frozenset` rather than `set`, and a tuple rather than a list, so **the scanner passes its own
  scan**. That is not a joke: a rule its author had to waive on their own file is a rule with a
  credibility problem on everybody else's.
- `STATEFUL_CALLS` holds bare names, not dotted paths, because the next line resolves
  `sqlite3.connect` down to `connect`. That is a deliberate trade — it means a locally defined
  function called `open` would be flagged — and the alternative, resolving imports properly, is a
  different and much larger program.
- `"connect"`, `"create_engine"`, `"Client"`, `"Session"`, `"Pool"` are the database and HTTP client
  names most libraries settle on. They are guesses at other people's naming conventions, and they
  are the part of this list most likely to need editing for a codebase that names things
  differently.
- `"seed"` and `"Random"` are in the list for the reason
  [1.3](../01-accidental-state/1.3-the-state-that-is-not-a-dictionary.md) gave: a seeded generator
  makes every instance produce the *same* sequence, which is the worst possible property for an
  identifier.
- `CACHE_DECORATORS` holds bare names too, so `@lru_cache`, `@functools.lru_cache` and
  `@lru_cache(maxsize=128)` all match — the last one because the scanner unwraps a decorator that is
  itself a call before reading its name.
- `MUTABLE_LITERALS` is a tuple of `ast` node classes, so it can be passed straight to `isinstance`.
  `ast.Tuple` is deliberately absent, and that absence is the "buttons" rule from the story.
- There is no `ast.Str` or `ast.Num` anywhere: strings and numbers are immutable and are never state.

Shape 4 is the only one that leaves the top level:

```python
# days/day-43-stateless-by-default/lab/scan.py  (extract)
    for node in ast.walk(tree):
        if isinstance(node, ast.Global) and not waived(node.lineno):
            findings.append(
                Finding(
                    path,
                    node.lineno,
                    ", ".join(node.names),
                    "global write",
                    "a request handler that rewrites module state as a side effect",
                )
            )
```

**Line by line:**

- `ast.walk(tree)` and not `tree.body`, because a `global` statement is by definition inside a
  function. This is the one rule where the whole tree is the right scope, and it is worth noticing
  that it is the exception rather than the pattern.
- `ast.Global` is its own node type, which is why this rule is three lines. Python makes the
  intention explicit in the grammar: you cannot write to a module-level name from inside a function
  without saying `global` first.
- `node.names` is a list, because `global A, B` is legal. Joining them keeps one finding per
  statement rather than one per name, which matches how the line will be fixed.
- The message says *"as a side effect"* on purpose. The problem is not the write. It is that a
  function whose signature promises a return value is also changing something the next request will
  read.

The four shapes, in one file, with what each one costs:

| Shape | Written as | Found by | What it is on two instances |
| --- | --- | --- | --- |
| mutable literal | `SEEN = {}` | node type of the value | two dictionaries, one empty |
| stateful call | `ARCHIVE = sqlite3.connect(...)` | the callee's bare name | two connections, two transactions |
| cache decorator | `@lru_cache` | the decorator's bare name | two answers to one question |
| global write | `global SEEN` inside a function | `ast.Global` anywhere | a write half the callers never see |

## When it breaks

`lab/shapes.py` holds one of each, plus two constants that must **not** be flagged. Measured on
2026-09-05:

```text
shapes.py:19: module-level container: SEEN - one per process; a second instance starts with its own empty one
shapes.py:22: module-level count(): TICKET_NUMBERS - built once at import; no other instance shares it
shapes.py:23: module-level connect(): ARCHIVE - built once at import; no other instance shares it
shapes.py:32: @lru_cache: title - a per-process cache; two instances answer from different ones
shapes.py:38: global write: SEEN - a request handler that rewrites module state as a side effect

5 finding(s) in shapes.py
exit: 1
```

Five findings from four shapes, because `SEEN` is caught twice: once for existing and once for being
written to. That is not a duplicate to deduplicate. The two findings say different things and have
different fixes — line 19 says *this is per-instance memory*, line 38 says *and here is the handler
that depends on it* — and a reviewer wants both lines.

Lines 26 and 27 of that file are `STATUSES = frozenset({...})` and `PORTS = (8901, 8902)`, and
neither appears in the output. Check that yourself in the file; a scanner you have not seen stay
quiet is one you do not yet trust.

Now the ways the rules are wrong, stated plainly, because a check whose limits are undocumented gets
believed too much:

- **`CACHE = build_cache()`** is missed. `build_cache` is not in `STATEFUL_CALLS`, so a call to a
  function you wrote yourself passes silently. Every accurate answer to this needs to follow the call,
  and that is a different program.
- **A local function named `open`** is flagged, because names are resolved by their last segment and
  nothing tracks imports.
- **`self.cache = {}` in a class whose instance is a module-level singleton** is missed, which is
  exactly the shape [1.4](../01-accidental-state/1.4-the-session-your-sdk-keeps-for-you.md) found
  inside the SDK. The most consequential state in the whole day is invisible to this scan.
- **A mutable default argument** — `def f(seen: dict = {})` — is missed, and it is genuinely
  per-process state with a long history of surprising people. It is not a hard rule to add; it is
  left out so that [2.4](2.4-a-scan-that-can-go-red.md) has something honest to ask you to add.

## In production

**What a professional writes instead:** the same four rules, expressed as a plugin to whatever linter
is already in the pipeline, and tuned per repository. The tuning is the real work: `STATEFUL_CALLS`
is a list of other people's naming conventions, so a codebase built on a different database library
needs different names in it, and a codebase with a house `Registry` class needs that added. A rule
list nobody has edited is a rule list nobody has read.

**What degrades at scale:** the ratio of findings to fixes. On one package these five lines are a
morning's work. On a repository with two hundred modules the same rule set returns hundreds of
findings, almost all of them legitimate constants, and the honest first move is not to waive them one
by one — it is to fix the shape: make constants immutable, and the count collapses. Waivers are for
what is left.

**The failure mode that only appears with real traffic:** none, again, and the reason is worth saying
out loud in a review. Nothing in this section can observe a running system. It finds a *shape*
correlated with a problem. The correlation is strong enough to be worth a gate and weak enough that
a clean scan proves nothing on its own, which is why this day has a
[section 3](../03-two-instances/3.1-the-dispatcher-that-knows-nothing.md).

**The review comment a senior engineer leaves:** *"the scan is green but `db_tools.py` builds its
connection through a helper, so the rule never sees a `connect` call. Either add the helper's name
to the list or stop wrapping it — right now the check is telling us about the modules that were
written the obvious way and staying quiet about the one that was not."*

**The interview question:** *"you are writing a lint rule for globals. What do you flag and what do
you leave alone?"* The honest answer: *"I flag four shapes: a mutable literal at module level, a call
that returns something stateful like a connection or a counter, a cache decorator, and a `global`
statement inside a function. I deliberately leave every immutable value alone — tuples, frozensets,
strings — because they cannot drift between processes, and because a rule that fires on constants
gets disabled within a week. The one that surprises people is that `Final` is not an exemption:
`Final` stops the name being rebound and does nothing about the dictionary. And I would document
what the rule cannot see, starting with state built inside a library's own objects, so nobody reads
a green run as proof."*
