doesn't only work buried inside the full triage graph — a single gated node can pause
and resume on its own, which is exactly what Day 65's drill (and later, smaller flows
like the nightly job) need.

## 3 · 📚 Concepts

### ADK-48 — The anatomy of an executing gate

**The story.** Think of the *held breath* at a notary's desk. You bring papers; the
notary reads them, seals *a copy* into an envelope, writes a case number on it, and
says: "come back when the magistrate signs." Three properties make this office work,
and each maps to a line of today's code:

| Notary property | Gate property | Where it lives today |
| --- | --- | --- |
| The sealed copy — what's approved is what was *filed*, not what's on your desk later | payload pinned at request time; hash re-checked at execute time | `request_approval(...)` then `_verify_hash(...)` before the write |
| The case number — any clerk can find the case, no matter who filed it | `approval_id` stored in the run; `invocation_id` stored in the approval row | both ids cross-referenced, either side can find the other |
| The desk closes at night and reopens — the case doesn't care | the pause is durable events, not a waiting thread | `RequestInput` + `ResumabilityConfig` + `DatabaseSessionService` |

The execution order deserves care, because two failure windows hide in it:

```
review node runs:
  1. build the payload   (ticket, draft reply, duplicates, severity)
  2. request_approval()  -> approval_id into the store         [window A]
  3. yield RequestInput(message=..., payload={approval_id,...})
  --- run parks; hours pass; human decides via the CLI ---
resumed successor runs:
  4. status(approval_id) -> approved? amendments?
  5. re-hash the ACTION it is about to take vs payload_sha     [window B]
  6. close_ticket(ticket_id, request_id=f"{invocation_id}/{approval_id}",
                  confirmed=True)
```

**Window A** — crash between filing and pausing: on resume, the node re-runs
(at-least-once) and would file a *second* approval. Fix: the node makes its
`request_approval` idempotent the Day 60 way — check the store for a pending row with
this `invocation_id` + tool first, reuse it. **Window B** — the world moved while the
human slept (draft re-generated, ticket edited): the hash check turns "silently do the
new thing" into "refuse loudly and re-file" — yesterday's failure lab, now enforced by
code. And notice the `request_id` in step 6: the idempotency key is *derived from the
approval*, so even a double-resumed successor closes once.

💡 **Mental model: the gate is a seam, not a wall.** Everything upstream (classify,
research, draft) runs at machine speed; everything downstream (the write) runs at human
speed; the seam between them is just rows — an approval row and parked events. Systems
with walls block threads and time out; systems with seams close the laptop.

### ADK-76 — What 2.5 actually added, and why you care

Before 2.5, the durable-pause story had a composition gap: it worked for *workflow
agents* — a `RequestInput` inside a full graph resumed fine — but a **standalone node**
(a gate used directly, no surrounding graph) and a node invoked *as a tool* had no
clean resumption story. The 2.5 release notes (verified 2026-08-19) close it with three
bullets you can now map to machinery you own:

- **"HITL resumption for standalone nodes"** — your gate node works bare. Day 65's
  drill uses this; so will any small flow (the nightly digest approving its own summary
  post) that doesn't want the whole triage graph as a chaperone.
- **"…and NodeTool"** — a node wrapped as a *tool*, callable by an LLM agent, may pause
  for a human and resume. Read that twice: an agent can now *delegate to a gated
  sub-flow*, and the pause propagates out cleanly instead of wedging the outer agent.
  (Exact class location is probed, not guessed, in step 6 — the release notes verify
  the capability, not the import path.)
- **"State-based resumption for task-mode agent workflow nodes"** — the sticky-note
  mechanism you built on Day 61 participates for agent nodes running in task mode.

The theme across all three: **pausability became a property of *any* node, regardless
of how it's mounted** — graph member, standalone, or tool. That's what lets Day 63's
"one policy, many doors" design stay honest as Sutra grows new, smaller flows.

Implementation notes the shape must honor: `_file_once` queries for an existing
*pending* row with this `invocation_id` before inserting (window A); the verdict is

gate deliberately reads its verdict from the store rather than from the
`RequestInput` answer — the answer's arrival *wakes* the run; the row *authorizes* it.
That split is what makes the CLI, a future Apps panel, and any other door equivalent.

## 5 · 💥 Failure lab — the second morning

> 🎬 **The scene:** the overnight gate works so well that two weeks in, nobody thinks
> about it. One Tuesday the operator approves `appr_7c…` at 09:31 and — Windows update,
> network hiccup, gremlin — the resume command errors halfway. They shrug and run it
> again at 09:33. Then the on-call, seeing the run still listed as paused in their
> dashboard, *also* resumes it at 09:40.
> 😬 **The naive fix:** none — that's the scene's point. Nobody did anything wrong.
> Retrying a failed command and a second operator double-checking are both *correct*
> behaviors in a healthy team.
> 💥 **Why it would have failed (in the un-keyed world):** three resume attempts, each
> replaying the successor node, each calling `close_ticket(confirmed=True)`. One
> customer, three close events, and — if `post_reply` had existed — three copies of
> the same reply in their inbox, timestamped minutes apart. The audit trail would show
> one approval and three executions, and every individual action defensible.
> 💡 **The insight:** **gates don't remove retries — they add more humans, who retry
> more.** The system is safe not because anyone is careful but because the write's
> idempotency key is *derived* — `invocation_id/approval_id` — so every resume of this
> approval names the same intent, and the ledger replays instead of repeating. Day 60
> built the lock; today's derivation is the reason the lock engages by construction
> rather than by convention. Safety that depends on nobody double-clicking isn't
> safety.

Proven in step 4 when you ran the resume twice on purpose. Do not skip that re-run.

## 6 · 🎤 Interview corner

1. **"Walk me through your human-approval flow, end to end, with the failure
   windows."** — The review node builds the exact payload a human must judge, files it
   idempotently in a durable approvals store (re-filing is deduped by invocation, so an
   at-least-once re-run can't double-ask), and yields a request-input event; the whole
   invocation then parks as rows in the session database — no waiting thread. A human
   decides through a CLI against the store: typed verdict, identity, timestamp,
   append-only. Resume rebuilds the run by invocation id, and the successor reads the
   verdict *from the store*, re-hashes the action against the payload the human
   actually saw — refusing loudly on drift — and executes the write with an
   idempotency key derived from invocation + approval, so N resumes produce one
   effect. The two windows I engineered around: crash-between-file-and-pause, and
   world-moved-while-human-slept.
2. **"Why does the verdict come from the store instead of the resume message?"** —
   Because arrival and authority are different jobs. The resume payload *wakes* the
   run — it travels through transcript machinery that models and tools can touch, so I
   treat it as transport. The store row *authorizes* — it's on a channel only the
   operator tooling writes, it's append-only, and it pins the payload hash. That split
   also buys pluggable fronts: today a CLI, later a sandboxed UI panel, same audit row
   either way. It's the same principle as structured tool-calling: prose requests,
   channels guarantee.
3. **"What did ADK 2.5 change for HITL, and did it matter to your design?"** — It made
   pausability mounting-independent: standalone nodes and nodes wrapped as tools
   (NodeTool) now resume from human-input pauses, not just nodes inside full
   workflows, plus state-based resumption for task-mode agent nodes. For me it meant
   the gate is one class mounted three ways instead of three gates — the same node
   guards the triage graph, runs bare in drills and small flows, and can sit behind an
   LLM's tool call with the pause propagating out cleanly. Before 2.5 I'd have had to
   keep the gate inside the big graph or hand-roll the standalone pause.
