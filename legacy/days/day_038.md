## 3 · 📚 Concepts

### MCP-11 — Timeouts: "no answer" is an answer you must budget for

**The story.** You mail a letter (Day 32's frame). Weeks pass. Is the recipient dead?
Slow? Was the letter lost? The postal service will never tell you — **the sender's
patience is the only clock that exists.** Every distributed system truth compresses
into that sentence.

What the 2026 transport gives you, and what it pointedly does not:

| Given | Not given |
| --- | --- |
| Per-request response streams — one request's hang can't block another's | Any server promise to answer at all |
| Cancellation = **close the request's stream** (that's the whole protocol on HTTP; `notifications/cancelled` exists only on stdio) | Any refund of work already done server-side (cancellation is cooperative — Day 36's lesson) |
| Resumability: **none, by design** — a broken stream loses the in-flight request; the client MUST re-issue with a *new* request id (the 2026 revision deleted `Last-Event-ID` redelivery) | Deduplication of the re-issued work — that's idempotency, *your* job (Day 60) |

So the client-side law: **every call carries a deadline; every deadline has a policy**
(retry? claim ticket? escalate to human?). Day 36 built the escape hatch for
legitimately-long work; today drills what happens when the deadline fires anyway; Day 44
writes the policy into Sutra's client for good; and honest backoff (Day 72) governs how
often you knock again.

### MCP-12 — Malformed servers: parse-or-perish at the boundary

**The story.** Customs doesn't taste the food in a crate labeled "food" — it x-rays the
crate first. A client that does `json.loads(...)["result"]["tools"]` on whatever bytes
arrive has skipped the x-ray: one server bug (or one hostile server) and the exception
detonates *inside your triage loop*, not at the boundary where it belongs.

The boundary checklist a hardened client runs **before believing anything** (today you
build the reflex; Day 44 builds the wrapper):

1. **Is it JSON at all?** `JSONDecodeError` at the edge, not three frames deep.
2. **Is it a JSON-RPC message?** `jsonrpc: "2.0"`, and an `id` matching something you
   actually asked (a mismatched id is a protocol violation, not a curiosity).
3. **Is it `result` XOR `error`?** Both or neither = malformed, full stop.
4. **Does the payload match the schema the method promises?** `tools/list` without a
   `tools` array is garbage wearing a suit — and in 2026, results missing a valid
   `resultType` from a *modern* server deserve suspicion too (from an *old* server,
   absence means `"complete"` — the compat rule).
5. **Then, and only then**, business logic.

And the disposition rule, previewing Day 44: a server that fails the x-ray gets
**quarantined** (skip it, log it, tell the user), never retried in a hot loop —
malformed is not transient, and hammering it turns one bug into two outages.

### MCP-31 — The deprecation lifecycle: reading a server's birth certificate

The 2026 revision did something rarer than adding features: it **formalized how
features die**. A lifecycle policy (SEP-2596) with three states — Active, Deprecated
(≥12 months, fully functional, new code SHOULD NOT adopt), Removed — plus a public
registry of what sits in the middle state. Three big residents of that middle state
(SEP-2577), each with a named migration:

| Deprecated | What it was | Migrate to | Why it died |
| --- | --- | --- | --- |
| **Roots** | Client told servers which directories/files are in scope; servers got `notifications/roots/list_changed` | Pass paths as **tool parameters, resource URIs, or server config** | It was connection-state — and the notification half is already *removed* |
| **Sampling** | Server asked the *client's* LLM for a completion (`sampling/createMessage`) mid-request | **Integrate with an LLM provider directly**; where the interaction itself matters, it's an MRTR input request | Server-initiated requests no longer exist; also `includeContext: "thisServer"/"allServers"` is deprecated alongside |
| **Logging** | `logging/setLevel` per connection; server pushed `notifications/message` | **stderr (stdio) or OpenTelemetry**; per-request verbosity via `_meta` `io.modelcontextprotocol/logLevel` — and a server MUST NOT emit log notifications for requests that didn't ask | Connection-scoped again — and observability grew a real home (OTel; Sutra's Day 84) |

Around them, outright **removals** that date a server instantly: `ping`,
`logging/setLevel`, `notifications/roots/list_changed`, the GET notification stream,
SSE resumability, `tasks/result`/`tasks/list` (Day 36), `resources/subscribe` (Day 35).

And the unifying replacement you already own from Day 37: **every** server-initiated
request pattern — roots queries, sampling asks, elicitation — collapsed into **MRTR**:
the server returns `InputRequiredResult` with `inputRequests`; the client retries with
`inputResponses`. One pattern to rule what used to be three protocols' worth of
back-channel.

💡 **Mental model: a protocol's deprecation list is a carbon-dating kit.** Ask a server
three questions — does it demand `initialize`? does it offer `sampling/createMessage`?
does it answer `tasks/result`? — and you can name its era to the quarter. Day 45's
audit sheet has exactly this column.

        "io.modelcontextprotocol/clientCapabilities": {},

def post(body: dict, headers: dict, *, timeout: float = 10.0) -> tuple[int, str]:
    """POST one JSON-RPC message; return (http_status, response_text).

    Args:
        body: the JSON-RPC message.
        headers: HTTP headers ON TOP of Content-Type (caller controls the

```python
"""Day 38 — the x-ray at the boundary: naive parse vs hardened parse.

Run:  python -m sutra_mcp.broken_client_drill
"""
from __future__ import annotations

import json
import subprocess
import sys


def hardened_parse(raw: str, expected_id: int) -> dict:
    """Validate the envelope BEFORE believing a byte (doc §3, MCP-12).

    Args:
        raw: one line from the server.
        expected_id: the id we actually sent.

    Returns:
        The validated message.

    Raises:
        ValueError: naming exactly which check failed - at the boundary,
            where a quarantine decision can be made (Day 44).

    Example:
        >>> hardened_parse('{"jsonrpc":"2.0","id":1,"result":{"ok":1}}', 1)
        {'jsonrpc': '2.0', 'id': 1, 'result': {'ok': 1}}
    """
    try:
        msg = json.loads(raw)                                   # check 1: JSON?
    except json.JSONDecodeError as e:
        raise ValueError(f"not JSON: {e}") from e
    if msg.get("jsonrpc") != "2.0":                             # check 2: JSON-RPC?
        raise ValueError("missing jsonrpc 2.0 marker")
    if msg.get("id") != expected_id:                            # check 2b: OUR id?
        raise ValueError(f"id mismatch: sent {expected_id}, got {msg.get('id')!r}")
    has_result, has_error = "result" in msg, "error" in msg
    if has_result == has_error:                                 # check 3: XOR
        raise ValueError("must have exactly one of result/error")
    return msg                                                  # check 4 (schema)
                                                                # is per-method: Day 44


def main() -> None:
    """Send four requests; show every crime caught AT THE BOUNDARY."""
    proc = subprocess.Popen([sys.executable, "-m", "sutra_mcp.broken_server"],
                            stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)
    try:
        for i in range(4):
            proc.stdin.write(json.dumps({"jsonrpc": "2.0", "id": i,
                                         "method": "tools/list", "params": {}}) + "\n")
            proc.stdin.flush()
            raw = proc.stdout.readline()
            try:
                hardened_parse(raw, expected_id=i)
                print(f"req {i}: accepted (!?)")
            except ValueError as e:
                print(f"req {i}: QUARANTINE-WORTHY -> {e}")     # caught at the edge,
    finally:                                                     # loop keeps running
        proc.terminate()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the retry that made it worse

*(Today the whole build is failure labs; this scene is the one that ties them
together.)*

> 🎬 **The scene:** Phase 6, a vendor's MCP server starts answering your
> `tools/list` with truncated JSON — some proxy on their side is mangling bodies. Your
> client's parse throws.
> 😬 **The naive fix:** wrap it in the fix that "always works":
> `for attempt in range(10): try: ... except: continue` — retry until it parses.
> 💥 **Why it fails:** you've applied a *timeout-class* remedy to a *malformed-class*
> disease. Retries are medicine for **transient** failures (a dropped stream, a busy
> instance — Day 36/44 territory). Malformed output is **deterministic**: the eleventh
> identical request meets the same mangling proxy. Your loop (1) hammers a struggling
> server 10× per call — you have built a tiny, sincere DDoS; (2) hides the real
> diagnosis (the exception *named* the crime — you caught and discarded the name);
> (3) blocks the triage loop for 10 × timeout seconds before failing anyway — slower
> AND blinder. And bare `except:` swallowing is trap #4's spirit (Day 21), returned
> with a network costume.
> 💡 **The insight:** **classify before you cure: transient gets patience (deadline,
> backoff, re-issue with a new id), deterministic gets quarantine (skip, log, surface
> to a human).** The hardened parse exists precisely to make the classification
> possible at the boundary — a `ValueError("not JSON")` is a *diagnosis*, and Day 44
> writes the treatment protocol into Sutra's client permanently: which errors retry,
> which quarantine, and who gets told.

Observed today, not just asserted: Step 5's drill caught four distinct crimes by name
and kept running; Step 4's timeout was the transient counter-example — the one that
*does* deserve a retry, with a fresh request id, per the spec's own resumability rule.

## 6 · 🎤 Interview corner

1. **"An MCP server stops responding mid-call. Walk me through your handling."** —
   First: my client always had its own deadline — the transport will never declare a
   peer dead for me. On expiry over Streamable HTTP I close the request's response
   stream, which *is* the cancellation signal in the 2026 spec — cooperative, so
   the server may finish anyway, which is why the work item, if it was long-running,
   should have been a task handle I can poll rather than a held connection. There's
   deliberately no stream resumability anymore — a broken stream means re-issue with a
   new request id — so the pairing discipline is: deadlines + claim tickets +
   idempotent server operations. I've demonstrated each half on my own server,
   including watching the server obliviously finish work whose caller had died.
2. **"How do you protect an agent from a misbehaving or malicious MCP server?"** —
   Envelope validation at the boundary before any field is believed: is it JSON; is it
   JSON-RPC 2.0 with *my* request id; exactly one of result/error; does the payload
   match the method's schema. Each failure raises a *named* diagnosis at the edge, and
   the disposition is classification-driven: deterministic garbage gets quarantined —
   skipped, logged, surfaced — never hot-retried, because retrying deterministic
   failure is a self-inflicted DDoS that hides the diagnosis. I keep a broken-server
   fixture in the repo and drill the client against four crime classes; the hardened
   reader survives all four while a naive `loads()["result"]` dies on the first.
3. **"A partner says their MCP integration 'supports MCP'. How do you find out what
   that means?"** — I carbon-date it with three or four probes. Does a bare modern
   request work, or does it demand `initialize`? (pre- vs post-2026 core). Does it
   answer `sampling/createMessage` or `roots/list`? (it predates the SEP-2577
   deprecations — those live in a formal ≥12-month sunset with a public registry).
