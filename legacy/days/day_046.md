## 3 · 📚 Concepts

### ADK-27 — MemoryService semantics: the drawer and the cabinet

**The desk-drawer story.** Watch a human support agent work a ticket. Two kinds of paper
are involved:

- The **desk drawer**: everything about *this* customer, *this* conversation — open,
  messy, instantly reachable, and **cleared when the ticket closes**.
- The **filing cabinet** in the corridor: the distilled residue of *every past case* —
  organized, searchable, shared by the whole desk, and deliberately **not** a transcript
  of everything anyone ever said. Someone decided what was worth filing.

Map the story to the machinery:

| Office | Our system | Technical name |
| --- | --- | --- |
| The desk drawer | one conversation's events + state | **Session** (`SessionService`, Days 8/17) |
| The filing cabinet | searchable cross-session knowledge | **Memory** (`MemoryService`, today) |
| "File this case" | pushing a finished session into the store | `add_session_to_memory(session)` |
| "Any precedent for X?" | querying the store | `search_memory(app_name, user_id, query)` |
| The filing clerk's judgment | which parts get kept, how search matches | **per-implementation** — the interface doesn't say |

💡 **Mental model: a session is what THIS conversation knows; memory is what the DESK has
learned.** Sessions are automatic — every event lands in one. Memory is **opt-in** —
nothing enters the cabinet until code explicitly files it. That asymmetry is a feature:
filing is a *decision* (Day 48 turns it into written policy).

Two semantics details that earn their place in an interview:

1. **The interface is thin on purpose.** `BaseMemoryService` promises only: things go in
   (`add_session_to_memory`), relevant snippets come out (`search_memory` →
   `SearchMemoryResponse`). It does *not* promise how matching works. The in-memory
   implementation matches **keywords**. A Vertex-backed one matches **meaning** (vectors).
   Same interface, wildly different recall quality — the contract's silence is what lets
   Day 49 slide a better brain underneath without touching the agent.
2. **Scoping.** Search takes `app_name` and `user_id` — the cabinet is per-user within an
   app, not one global pile. Sutra's synthetic users keep their memories separate, the
   same discipline the Day 8 `shared` demo taught for sessions (and the same privacy line
   SEC-13 will harden on Day 69).

**The managed cousins (read, not run).** The docs page shows two GCP-backed services:
`VertexAiMemoryBankService` (an LLM *extracts* durable facts from sessions — the filing
clerk is itself a model) and `VertexAiRagMemoryService` (sessions land in a vector corpus,
search is semantic). Both need a Google Cloud project with billing, so under Addendum 02
they are 🅿️-style *map knowledge inside a closing ID*: know they exist, know what they'd
buy you, build the free equivalent (Day 49 hand-rolls the vector part locally — which
means you'll understand what Memory Bank sells before anyone pays for it).

### ADK-28 — Memory in practice: wiring, and the two tools

Three wires connect the cabinet to a running agent, and you will touch all three today:

**Wire 1 — the Runner carries the service.** Just like `session_service`, the memory
service rides on the runner, not the agent:

```python
runner = Runner(agent=…, app_name=…, session_service=…, memory_service=memory)
```

The agent stays portable; *deployment* decides which cabinet stands in the corridor
(in-memory today, something persistent later) — the same swap-at-the-runner pattern as
Day 47's session upgrade.

**Wire 2 — `load_memory`: the agent asks.** A prebuilt tool
(`from google.adk.tools import load_memory`). Put it in `tools=[…]` and the *model*
decides when history might help — it calls the tool with a query, gets snippets back in a
tool-result turn. This is our Day 4 machinery, pointed at the past.

**Wire 3 — `preload_memory`: the runner asks for you.** Same import home. Instead of
waiting for the model to think of it, relevant memory is retrieved **automatically at the
start of every turn** and injected. No tool call in the transcript.

| | `load_memory` | `preload_memory` |
| --- | --- | --- |
| Who decides | the model, per question | the framework, every turn |
| Costs when irrelevant | nothing (no call made) | retrieval every turn + context tokens |
| Failure mode | model forgets to ask | context stuffed with near-miss history |
| Sutra's default | ✅ researcher-style agents | narrow always-need-history agents only |

That table is Day 19's context-budget lesson wearing a memory hat: `preload_memory` spends
window on every turn *whether or not it pays* — exactly the "kitchen sink" habit Day 19
measured and rejected. Default to `load_memory`; promote to `preload_memory` only with
evidence.

**Step 1 — `sutra/memory_lab.py`: the lab, zero quota.**

```python
"""Day 46 — sessions vs memory: the desk drawer and the filing cabinet.

Session A learns something about ticket #4521. Session B — a brand-new
conversation — is asked a related question. Without memory, B knows
nothing (drawer demo). With a MemoryService and the load_memory tool,
B recalls A's findings (cabinet demo). preload_memory automates it
(auto demo), and the miss demo shows exactly where keyword matching
stops working — the cliff Day 49 exists to fix.

Importable with no side effects. Run from the repo root:

    python -m sutra.memory_lab drawer    # honest amnesia, ~2 calls
    python -m sutra.memory_lab cabinet   # memory rescue, ~3 calls
    python -m sutra.memory_lab auto      # preload variant, ~2 calls
    python -m sutra.memory_lab miss      # the keyword cliff, ~2 calls
"""
from __future__ import annotations

import asyncio
import sys

from google.adk.agents.llm_agent import Agent
from google.adk.memory import InMemoryMemoryService          # the cabinet (keyword search)
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService       # the drawers (Day 8)
from google.adk.tools import load_memory, preload_memory     # the two prebuilt memory tools
from google.genai import types

from sutra.config import load_env                            # .env keys (Day 1)
from sutra.logging_setup import get_logger                   # JSON-lines logs (Day 22)

log = get_logger(__name__)

APP = "sutra_memory_lab"                                     # cabinet + drawers share this app_name
USER = "agent_riya"                                          # one synthetic user; scoping is per-user
PRIMARY_MODEL = "gemini-3.5-flash"                           # pinned, never defaulted (ADK-73)

# Session A's seed: the "past case" we want the desk to remember. The
# transcript itself becomes the memory once we file it — so we make the
# turn state the facts plainly. (Synthetic data only — SEC-12/13 rule.)
PAST_CASE = (
    "For the record: ticket 4521 'Keeps getting logged out' was resolved. "
    "Root cause: the session cookie was set without the SameSite and Secure "
    "flags, so the browser dropped it on cross-site redirects. Fix: KB-104."
)
# Session B's question — different words, same disease family:
TODAY_Q = "A user reports being logged out over and over. Any past cases like this?"


def make_agent(name: str, memory_tools: list) -> Agent:
    """Build the lab agent, with or without memory tools.

    Args:
        name: agent name shown in events.
        memory_tools: [] for the drawer demo, [load_memory] or
            [preload_memory] for the rescue demos.

    Returns:
        A pinned-model Agent. Honesty rule included: no past case may be
        invented — if memory yields nothing, say so.

    Example:
        >>> a = make_agent("desk", [load_memory])
        >>> a.model
        'gemini-3.5-flash'
    """
    return Agent(
        name=name,
        model=PRIMARY_MODEL,                                 # explicit pin (ADK-73)
        instruction=(
            "You are Sutra, a support-desk assistant. When asked about past "
            "cases, rely ONLY on memory search results. If nothing is found, "
            "say plainly that no past case is on file — never invent one."
        ),
        tools=memory_tools,                                  # the only knob today
    )


async def _one_turn(runner: Runner, session_id: str, text: str) -> str:
    """Send one user message; print tool activity; return final text.

    Args:
        runner: a Runner already carrying session + memory services.
        session_id: which drawer this turn belongs to.
        text: the user message.

    Returns:
        The agent's final text (empty string if none).

    Example:
        >>> # inside an event loop, after creating the session:
        >>> reply = await _one_turn(runner, "sessA", "hello")
    """
    msg = types.Content(role="user", parts=[types.Part(text=text)])
    final = ""
    async for event in runner.run_async(
        user_id=USER, session_id=session_id, new_message=msg
    ):
        for call in event.get_function_calls():              # narrate memory lookups
            print(f"  TOOL CALL: {call.name}({call.args})")
        if event.is_final_response() and event.content and event.content.parts:
            final = "".join(p.text or "" for p in event.content.parts)
    return final


async def _run_lab(memory_tools: list, *, file_the_case: bool, question: str) -> None:
    """Shared scenario: session A learns; maybe file it; session B asks.

    Args:
        memory_tools: tools handed to the agent (the experiment variable).
        file_the_case: True = add_session_to_memory after session A —
            the single line where knowledge crosses the session gap.
        question: what session B asks.
    """
    sessions = InMemorySessionService()                      # drawers
    memory = InMemoryMemoryService()                         # cabinet (empty)
    agent = make_agent("memory_lab", memory_tools)
    runner = Runner(
        agent=agent, app_name=APP,
        session_service=sessions, memory_service=memory,     # BOTH ride the runner
    )

    # --- Session A: the desk works a past case -----------------------------
    sess_a = await sessions.create_session(app_name=APP, user_id=USER)
    print("--- session A (the past case) ---")
    print("A:", (await _one_turn(runner, sess_a.id, PAST_CASE))[:160], "…")

    if file_the_case:                                        # THE line of the day:
        completed = await sessions.get_session(              # fetch the finished session…
            app_name=APP, user_id=USER, session_id=sess_a.id
        )
        await memory.add_session_to_memory(completed)        # …and file it in the cabinet
        print("[filed session A into memory]")
    else:
        print("[session A NOT filed — no memory]")

    # --- Session B: a NEW conversation asks a related question -------------
    sess_b = await sessions.create_session(app_name=APP, user_id=USER)
    print("\n--- session B (today's question) ---")
    print("B:", await _one_turn(runner, sess_b.id, question))


def demo_drawer() -> None:
    """No memory tools, nothing filed: honest amnesia across sessions."""
    asyncio.run(_run_lab([], file_the_case=False, question=TODAY_Q))


def demo_cabinet() -> None:
    """load_memory + a filed case: session B recalls session A's findings."""
    asyncio.run(_run_lab([load_memory], file_the_case=True, question=TODAY_Q))


def demo_auto() -> None:
    """preload_memory: retrieval happens before the turn, no tool call."""
    asyncio.run(_run_lab([preload_memory], file_the_case=True, question=TODAY_Q))


def demo_miss() -> None:
    """The keyword cliff: same cabinet, a SYNONYM query — and nothing matches.

    'sign-in trouble' shares meaning with 'logged out', but shares no
    keyword. InMemoryMemoryService matches words, not meanings — watch
    the honest miss. This exact failure is why Day 49 exists.
    """
    asyncio.run(_run_lab(
        [load_memory], file_the_case=True,
        question="Any past cases about sign-in trouble after a redirect?",
    ))


def main() -> None:
    """Tiny demo dispatcher — the house pattern since Day 2."""
    demos = {
        "drawer": demo_drawer, "cabinet": demo_cabinet,
        "auto": demo_auto, "miss": demo_miss,
    }
    name = sys.argv[1] if len(sys.argv) > 1 else "drawer"
    if name not in demos:
        print(f"usage: python -m sutra.memory_lab [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the cabinet that only reads labels

> 🎬 **The scene:** the cabinet demo worked, so you get ambitious: file every past ticket
> session into `InMemoryMemoryService` and tell support "Sutra remembers everything now."
> A week later a teammate asks about "sign-in trouble after redirects." Sutra, with the
> 4521 case *sitting right there in memory*, answers: no past cases on file.
> 😬 **The naive fix:** prompt engineering — instruct the agent to "try several query
> wordings"; or worse, stuff every memory with a hand-written synonym list ("logged out,
> log-out, sign-in, signin, auth loop…").
> 💥 **Why it fails:** you are patching a *representation* problem at the *query* layer.
> Keyword matching compares surface strings; natural language has unbounded surfaces for
> one meaning. Every synonym list is finished exactly until the next ticket ("bounced back
> to the login page"). Retry-with-rewording burns 5-RPM quota on guesses, and each miss
> still *looks* like an honest "no precedent" — the worst kind of wrong answer, the
> confident-sounding false negative you can't detect without already knowing the truth.
> 💡 **The insight:** **recall quality is a property of the representation, not of the
> effort.** Words must become something where "logged out" and "sign-in trouble" are
> *near each other* — vectors. The MemoryService interface was built for exactly this
> swap: the contract stays (`search_memory` in, snippets out), the brain underneath
> changes. That swap is Day 49, and it is why today's interface-first day matters.

## 6 · 🎤 Interview corner

1. **"What's the difference between session state and memory in an agent system?"** —
   Scope and intent. A session is one conversation's working set — events and state,
   automatic, short-lived, private to that thread. Memory is the system's cross-session
   knowledge — explicitly curated (nothing enters unless code files it), searchable, and
   scoped per user/app. In ADK they're two services on the runner: `SessionService` and
   `MemoryService`. My rule of thumb from building Sutra: the session is what *this
   conversation* knows; memory is what *the desk* has learned — and promotion between
   them is a policy decision, not a default.
2. **"Your agent has a memory store but keeps missing relevant history. Debug it."** —
   First separate the three failure points: filing (did the session ever enter memory? —
   log the `add_session_to_memory` calls), retrieval (does a direct `search_memory` with
   the user's wording return it?), and usage (did the model call the memory tool at
   all?). In my lab the second point was the cliff: keyword-based search returned nothing
   for a synonym query while the exact-word query hit. That's a representation problem —
   no amount of prompting fixes it; you swap in semantic (embedding) search behind the
   same interface. I built that exact swap the same week.
3. **"When would you auto-inject memory versus giving the model a retrieval tool?"** —
   Default to the tool (`load_memory`): it costs nothing when history is irrelevant and
   the call is visible in the transcript for auditing. Auto-injection (`preload_memory`)
   pays retrieval plus context tokens *every* turn — justified only for agents whose every
   answer needs history, and it hides the lookup from the event log. It's the context-
   budget argument: spend window on demand, not on habit.
