What do you have when power returns? Under Phase 8's rules: **nothing.** The run lived in
one Python process, and the process *was* the run. You restart, the graph starts from
intake, and every model call you already paid for (out of a 5-RPM allowance!) is paid
again. Worse: if the crash had landed one step later — *after* `close_ticket` fired but
*before* the result was recorded — a blind rerun would close the ticket **twice**.

Day 36 already met this monster in miniature: the re-index job that returns a task handle
and survives Ctrl-C. Day 43 proved any server instance can pick up any request. Day 44
made the client refuse to retry non-idempotent writes. Three threads, one lesson, and
today they braid together: **work must be able to outlive the process that started it.**
That property has a name — durable execution — and ADK 2.x builds it in.

## 3 · 📚 Concepts

### AG-22 — Durable execution: the night-shift clerk

**The story.** A support desk employs a night clerk. At 02:00, mid-task, the clerk drops
dead. (Harsh, but processes die without notice — that's exactly what SIGKILL is.) At
06:00 a fresh clerk sits down at the same desk. The question that decides whether your
desk is a toy or a product: **what can the morning clerk do?**

- If the night clerk kept everything *in their head* — nothing. Start over. That was
  Sutra until yesterday.
- If the night clerk kept a **written log on the desk** — "18:40 classified #4610 as
  auth-bug; 19:12 archive search done, found #4521" — the morning clerk reads the log,
  skips the finished work, and continues from the first missing entry.

That written log is durability, and it decomposes into exactly three ideas:

| Idea | Plain words | Defends against | Where it lives in Sutra tonight |
| --- | --- | --- | --- |
| **Replay** | rebuild "where was I?" by re-reading the log, not by re-doing the work | losing the *memory* of a run | the session's Event history (Days 7/8), persisted since Day 47 |
| **Resume** | continue from the first unfinished step | losing the *progress* of a run | `ResumabilityConfig` + `invocation_id` (step 5) |
| **Idempotency** | doing a step twice has the effect of doing it once | the step *in between* — did it happen or not? | `request_id` on `close_ticket` (step 3) |

The third one deserves its own scene, because it is the one everyone underestimates.

**The uncertainty gap.** The clerk's log says "19:58 — closing ticket #4610…" and then
nothing. Did the close happen before death, or not? *You cannot know.* The log entry is
written either before the action (maybe it never ran) or after (maybe death struck between
action and entry). No log discipline closes this gap — it is physics, not sloppiness.
Distributed-systems people call it the *at-least-once* reality: any step that can be
retried after a crash **may execute twice**, because the safe policy when unsure is to
redo it.

💡 **Mental model: durability doesn't make steps run exactly once — it makes running
them twice harmless, then retries fearlessly.** Exactly-once *delivery* is a myth;
exactly-once *effect* is engineering, and the tool that buys it is the idempotency key.

**The idempotency key, concretely.** The caller invents a unique id for the *intent* —
"close #4610 as part of run inv_20260819_a, step review" — and sends it with the write.
The server keeps a little table of keys it has already honored. A retry arrives with the
same key → the server does **nothing new** and returns the *original* answer. The effect
happened once, no matter how many times the request did. You already met the pattern's
cousins: Day 36's task claim-ticket (same handle, same job) and Day 44's
`IDEMPOTENT_TOOLS` frozenset, whose docstring promised that `close_ticket` stays out
"until it carries idempotency keys — Phase 9 makes this law." Today is Phase 9.

### ADK-43 — Durable execution in ADK 2.x

ADK's version of the clerk's log is the thing you've used since Day 7: **Events**. Every
step of a run is already an Event committed to the session. What 2.x adds is the ability
to *use* that log as a recovery plan (verified on adk.dev/runtime/resume/, 2026-08-19):

1. **Opt in** — wrap your agent in an `App` carrying
   `ResumabilityConfig(is_resumable=True)`. (You met `App` on Day 20 for compaction —
   same object, one more config.)
2. **Every run gets an `invocation_id`** — the run's claim ticket. You've seen it in
   every Event since Day 7; today it stops being trivia.
3. **To resume, run again with the old id** — `runner.run_async(user_id=...,
   session_id=..., invocation_id=...)`. ADK re-reads the session's Events, *reinstates*
   the completed ones (skip, don't redo), and continues where the log stops. For
   workflow agents (Sequential/Loop/Parallel — Day 54) each tracks its own progress;
   graph nodes that completed are skipped (adk.dev/graphs/dynamic/).

And the official page hands us, in one sentence, the reason today's second half exists:
**"Tools in an agent are run at least once, and may run more than once."** ADK is being
honest about the uncertainty gap — it will re-run the step it isn't sure about. Your
tools must be ready to be asked twice. Which — after step 3 — they are.

Two limits worth knowing before you fall in love (same page): resume is for the
programmatic runner (the Web UI / CLI don't resume runs today), and a *custom* agent
only resumes cleanly if it checkpoints its own state — that's Day 61's `BaseAgentState`.

```python
# ---------------------------------------------------------------------------
# Day 60: the idempotency ledger. One table, two columns of consequence:
# the key the caller invented, and the JSON answer we gave the first time.
# A retry with a known key gets the SAME answer and NO new side effects.
# ---------------------------------------------------------------------------
import json
import sqlite3
from pathlib import Path

_WRITES_DB = Path("data/tasks.db")                 # reuse Day 43's WAL database


def _writes_conn() -> sqlite3.Connection:
    """Open the shared rack and make sure the ledger table exists.

    Returns:
        A WAL-mode connection to data/tasks.db.

    Example:
        >>> conn = _writes_conn()
        >>> conn.execute("SELECT 1").fetchone()
        (1,)
    """
    conn = sqlite3.connect(_WRITES_DB)             # same file as the task rack
    conn.execute("PRAGMA journal_mode=WAL")        # two writers, no torn reads (Day 43)
    conn.execute(                                  # idempotency ledger, if missing
        "CREATE TABLE IF NOT EXISTS processed_writes ("
        " request_id TEXT PRIMARY KEY,"            # the caller's invented key
        " tool TEXT NOT NULL,"                     # which tool honored it
        " result TEXT NOT NULL)"                   # the answer we gave, as JSON
    )
    return conn


@mcp.tool()
def close_ticket(ticket_id: str, request_id: str, confirmed: bool = False) -> dict:
    """Close a ticket - at most once per request_id, and only if confirmed.

    Day 37 taught this tool to refuse without a confirmed answer. Day 60
    teaches it to refuse to repeat itself: the caller sends a request_id
    (any unique string naming this INTENT, e.g. "inv_abc/review/close-4610"),
    and a retry with the same id returns the original result with no new
    side effects. This is the idempotency law: writes carry keys.

    Args:
        ticket_id: which ticket to close.
        request_id: unique name for this close-intent. Retries REUSE it.
        confirmed: False on a first, innocent call (Day 37's gate, unchanged).

    Returns:
        The same status dicts as Day 37 - plus, on a replayed request_id,
        the original dict with replayed=True added.

    Example:
        >>> close_ticket("4610", "demo-1", confirmed=True)
        {'status': 'closed', 'ticket_id': '4610'}
        >>> close_ticket("4610", "demo-1", confirmed=True)   # the retry
        {'status': 'closed', 'ticket_id': '4610', 'replayed': True}
    """
    conn = _writes_conn()
    row = conn.execute(                            # have we honored this key before?
        "SELECT result FROM processed_writes WHERE request_id = ?", (request_id,)
    ).fetchone()
    if row is not None:                            # yes -> replay the old answer,
        replay = json.loads(row[0])                #        touch NOTHING else
        replay["replayed"] = True                  # honest flag: this is a replay
        conn.close()
        return replay

    # --- from here down: Day 37's logic, unchanged in spirit ---------------
    if ticket_id not in _all_ticket_ids():         # program-facing miss (Day 39's db)
        result = {"status": "failed", "error": f"unknown ticket {ticket_id!r}"}
    elif not confirmed:                            # the confirmation gate, as before
        result = {
            "status": "input_required",
            "question": f"Close ticket {ticket_id} - are you sure?",
        }
    else:
        _mark_closed(ticket_id)                    # the one real side effect
        result = {"status": "closed", "ticket_id": ticket_id}

    if result["status"] == "closed":               # only completed WRITES are recorded;
        conn.execute(                              # refusals/misses may retry fresh
            "INSERT INTO processed_writes (request_id, tool, result) VALUES (?,?,?)",
            (request_id, "close_ticket", json.dumps(result)),
        )
        conn.commit()
    conn.close()
    return result
```

> *finished* the close and died on the way back (step 2 showed you the shape of this).
> The retry closes the ticket a second time. With today's simple close that's just an

> the night the crash lands between effect and record, no log can even tell you whether
> to apologize. You built a machine that is *sometimes* wrong and *never* sure.
> 💡 **The insight:** **retry-ability is not a client setting — it is a property the
> server must grant, and the grant is spelled `request_id`.** Day 44's refusal to retry
> writes was never the bug; it was the fence around a hole. Today you filled the hole,
> and only then moved the fence.

## 6 · 🎤 Interview corner

1. **"What does durable execution actually mean, and how would you add it to an agent
   system?"** — Three separable properties: *replay* (state is reconstructed from an
   event log, not from process memory), *resume* (execution continues from the first
   unfinished step, skipping completed ones), and *idempotency* (any step that might run
   twice has the same effect as running once). In my triage system, ADK gives the first
   two — sessions are event logs, and `ResumabilityConfig` plus re-running with the same
   `invocation_id` reinstates completed events. The third one nobody gives you: I added
   idempotency keys to every write tool, with a processed-writes table that replays the
   original result on a duplicate key.
2. **"Why can't you just make each step run exactly once?"** — Because a crash between
   an action and the record of the action leaves you provably unable to know whether it
   ran — so any recovery policy must choose between "maybe never" and "maybe twice", and
   "maybe twice" is the only one you can engineer around. ADK's docs say it plainly:
   tools run *at least once*. Exactly-once *effect* is achievable — dedupe on an
   intent-scoped key at the effect's home — exactly-once *execution* is not.
3. **"When is a retry dangerous, and who should decide?"** — A retry is dangerous
   exactly when the operation has external effects and no dedupe. The *server* owning
   the effect should decide, by granting or withholding an idempotency contract; the
   client's allowlist (my `IDEMPOTENT_TOOLS`) is just a cache of those grants. I've had
   both versions in one repo: reads retried freely from day one; `close_ticket` was
   barred from retry for twenty days until it carried a key — then, and only then, the
   client's list changed.
