## 3 · 📚 Concepts

### MCP-04 — Server anatomy: a shop is a sign, a menu, and a kitchen

**The story.** Opening a shop needs three things: a **sign** over the door (who you are),
a **menu in the window** (what you offer, in a format any passerby can read), and a
**kitchen** (the code that actually does the work). Nothing else. No guest book at the
door — remember, the 2026 protocol fired the receptionist.

| The story | Our system | Technical name |
| --- | --- | --- |
| The sign over the door | `MCPServer("sutra-mcp")` | the server's **identity** (returned in `_meta` serverInfo / `server/discover`) |
| The menu in the window | what `tools/list` returns | declared **capabilities** — tools today; resources & prompts tomorrow (Day 35) |
| One dish on the menu | one decorated function | a **tool** with name, description, JSON Schema |
| The kitchen | your Python function bodies | the handlers |

The v2 SDK's central kindness: **the decorator writes the menu from the type hints.**

```python
@mcp.tool()
def lookup_ticket(ticket_id: str) -> str:
    """Return the raw text of a support ticket by its id."""
```

From this it derives: name `lookup_ticket`, description from the docstring, and a JSON
Schema with a required string property `ticket_id` — the *same* schema you wrote by hand
in Day 4's `LOOKUP_TICKET_DECL`, and the same trick ADK's auto-wrapping pulled on Day 10.
Third time you meet this idea; first time it serves strangers. 💡 **Mental model: your
docstring and type hints ARE the API contract now — write them for the model that will
read them, not the human who won't.** (Day 11's tool-design principles apply verbatim to
MCP tools; nothing about good descriptions changed when the caller moved out of process.)

### MCP-05 — Tools over the wire: Day 4, now between processes

What actually travels? Two requests, both of which you can now read cold (Day 32 Step 4):

1. **`tools/list`** → the menu: an array of `{name, description, inputSchema}` objects.
   New in 2026: the result also carries `ttlMs` + `cacheScope` (it is a `CacheableResult`),
   and SHOULD be deterministically ordered — so hosts cache your menu instead of
   re-fetching it before every meal.
2. **`tools/call`** with `{name, arguments}` → one dish ordered. The result carries
   `content` (what the model reads) and, always in 2026, `resultType: "complete"` — the
   field whose *other* value (`"input_required"`) powers Day 37's elicitation story.

Map it once to what you hand-rolled, and MCP stops being new:

| Day 4 (in-process) | Today (over MCP) |
| --- | --- |
| `types.FunctionDeclaration(... parameters_json_schema=...)` | one entry in `tools/list` |
| `response.function_calls` → your dispatch dict | `tools/call` → the SDK routes to your decorated function |
| `Part.from_function_response(...)` | the `tools/call` result's `content` |

The model still only *requests*; your code still *decides and executes*. Moving the
kitchen across a process boundary moved the authority **with the kitchen** — the server
enforces its own rules now, whoever the client is. That flip matters: on Day 33 you
filtered as a cautious customer; from today you can also refuse as the shopkeeper
(Day 40 builds exactly that).

### MCP-06 — Lifecycle without a handshake: what "running" even means now

**History, one paragraph (recognize it; don't build it):** until 2025, a server's life
began with a ritual — client sends `initialize` (name, version, capabilities), server
answers with its own, client confirms with `notifications/initialized`, and both sides
kept that agreement *in memory* for the life of the connection. Every tutorial started
with that dance; every load balancer had to respect it.

**The present:** a modern server's lifecycle is just —

1. **Process starts.** (stdio: the host launches you; HTTP: your process binds a port.)
2. **Requests arrive, each self-contained.** Version + capabilities ride in `_meta`
   *every time*; you answer from nothing but the letter in your hand.
3. **`server/discover` answers on demand.** The one REQUIRED introduction RPC — but it is
   a *pull*, cacheable, not a stateful ceremony. A client MAY call it first; a client MAY
   also never call it.
4. **Process stops.** Nothing to tear down, because nothing was remembered.

That's it. No step is "and now the server remembers the client." A server you can describe
this way is a server three replicas of which are indistinguishable — which is why Day 43's
"deployment" will be almost insultingly short. **Stateless is not a feature we add later;
it is the absence of a feature we refuse to add today** (and Step 6 proves ours refuses
correctly).

```python
"""sutra-mcp — Sutra's ticket archive and KB, served over MCP.

Day 34 scope: two tools (lookup_ticket, search_kb), stdio transport,
stateless by construction (2026-07-28 spec: no handshake, no sessions).
Resources and prompts arrive on Day 35; long jobs on Day 36.

Run it three ways:

    # HTTP arrives properly on Day 38/43:
    uv run mcp run sutra_mcp/server.py --transport streamable-http

Importing this module must NOT start anything - the CLI owns startup.

from __future__ import annotations

from mcp.server import MCPServer            # the v2 SDK server class (2026-07-28 era)

from sutra.loop import KB, TICKETS          # Day 3's synthetic data - data ONLY,
                                            # no agent imports: the server stands alone

# The sign over the door. This name is what clients will see in
# serverInfo / server/discover - keep it stable; it is an identity.
mcp = MCPServer("sutra-mcp")


@mcp.tool()                                  # decorator = menu entry writer:
def lookup_ticket(ticket_id: str) -> str:    # type hints -> JSON Schema
    """Return the raw text of a support ticket by its id.

    Args:
        ticket_id: The ticket id, e.g. '4521'.

    Returns:
        The stored ticket text, or a clear not-found sentence.

    Example:
        >>> lookup_ticket("4521")
        'Title: Keeps getting logged out...'
        >>> lookup_ticket("9999")
        "No ticket with id '9999'."
    """
    # Same honesty contract as every prior costume of this tool (Day 3):
    # a miss is DATA the model can read, never an exception it can't.
    return TICKETS.get(ticket_id, f"No ticket with id {ticket_id!r}.")


@mcp.tool()
def search_kb(query: str) -> str:
    """Search the internal knowledge base; return the best-matching article.

    Args:
        query: Symptom keywords, e.g. 'user logged out'.

    Returns:
        The best-matching KB article text, or a clear no-match sentence.

    Example:
        >>> search_kb("logged out")
        'KB-104: ...SameSite...'
    """
    q = query.lower()                                  # naive match, same as Day 3 -
    for key, article in KB.items():                    # the POINT is the socket today,
        if any(word in q for word in key.split()):     # retrieval gets its real day (49)
            return article
    return f"No KB article matched {query!r}."


# NOTE what is ABSENT here, on purpose (this absence is MCP-06):
# - no initialize handler: the 2026 protocol has no handshake to answer
# - no session store: every request self-carries its context in _meta
# - no state between calls: a server you could clone x3 behind one URL
# The SDK answers server/discover for us from what the decorators declared.
```

**Step 6 — Wire lab: speak protocol with your bare hands.** Create `sutra_mcp/wire_lab.py`:

```python
"""Day 34 wire lab — raw JSON-RPC to sutra-mcp over stdio, no SDK client.

Proves MCP-06 with your own eyes:
  1. tools/list works IMMEDIATELY - no handshake happened first.
  2. The old 'initialize' ritual gets a polite modern shrug, not a session.

Run:  python -m sutra_mcp.wire_lab
"""
from __future__ import annotations

import json
import subprocess
import sys

# Launch the server exactly as any host would (stdio = child process).
SERVER_CMD = ["uv", "run", "mcp", "run", "sutra_mcp/server.py"]

# _meta that a modern client self-carries in EVERY request (Day 32, Step 4):
META = {
    "io.modelcontextprotocol/protocolVersion": "2026-07-28",
    "io.modelcontextprotocol/clientCapabilities": {},
    "io.modelcontextprotocol/clientInfo": {"name": "wire-lab", "version": "0.1"},
}


def rpc(proc: subprocess.Popen, req: dict) -> dict:
    """Send one newline-delimited JSON-RPC request; read one response line.

    Args:
        proc: the running stdio server process.
        req: the JSON-RPC request as a dict.

    Returns:
        The parsed JSON-RPC response.

    Example:
        >>> # rpc(proc, {"jsonrpc": "2.0", "id": 1, "method": "tools/list",
        ...  #           "params": {"_meta": META}})
        ... # -> {'jsonrpc': '2.0', 'id': 1, 'result': {...}}
    """
    line = json.dumps(req) + "\n"                 # stdio framing: one msg, one line
    proc.stdin.write(line.encode())               # letters go into the child's stdin
    proc.stdin.flush()
    raw = proc.stdout.readline()                  # answers come out of its stdout
    return json.loads(raw)


def main() -> None:
    """The two-act lab: modern request first, then the historical ritual."""
    proc = subprocess.Popen(                      # the host's job: launch the child
        SERVER_CMD, stdin=subprocess.PIPE, stdout=subprocess.PIPE
    )
    try:
        # ACT 1 - modern: straight to business, no introduction.
        out = rpc(proc, {"jsonrpc": "2.0", "id": 1, "method": "tools/list",
                         "params": {"_meta": META}})
        names = [t["name"] for t in out["result"]["tools"]]
        print("ACT 1  tools/list with NO handshake ->", names)

        # ACT 2 - history: the 2025-era opening move.
        out = rpc(proc, {"jsonrpc": "2.0", "id": 2, "method": "initialize",
                         "params": {"protocolVersion": "2025-06-18",
                                    "capabilities": {},
                                    "clientInfo": {"name": "time-traveler",
                                                   "version": "0.0"}}})
        print("ACT 2  'initialize' from the past ->",
              json.dumps(out.get("error", out.get("result")), indent=2)[:300])
        # Expected on a pure-2026 server: an error (e.g. method not found) or a
        # compatibility answer - EITHER WAY: no session begins. Whatever your
        # SDK version actually prints, write it in the margin here; that line
        # IS the historical record for your repo.
    finally:
        proc.terminate()                          # stdio lifecycle: dies with us


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the handshake that nobody answers

> 🎬 **The scene:** a teammate (or a four-month-old blog post) hands you a "battle-tested"
> MCP client snippet. Its first act: send `initialize`, await the reply, store the session,
> *then* start work. You point it at `sutra-mcp`. It connects… and hangs, or dies on its
> very first message.
> 😬 **The naive fix:** "the server must be broken — add a retry loop around the
> handshake." Now it hangs *persistently*.
> 💥 **Why it fails:** the client is performing a ceremony the counterpart no longer
> holds. Your server was born under 2026-07-28: it expects every request to be
> self-contained and treats `initialize` as just another method it may not implement.
> Retrying a ritual does not resurrect it. And the reverse failure exists too — a modern
> client hitting a 2025-era server gets rejected for *skipping* the ceremony. Same
> protocol name, two eras, and the bug lives in the *pairing*, not in either program.
> 💡 **The insight:** **in a protocol transition, "is it broken?" is the wrong first
> question — ask "which era is each side speaking?"** You now own a one-command era
> detector: ACT 2 of the wire lab. Modern spec even codifies the answer — modern clients
> try a modern request first and only fall back to `initialize` on a legacy-shaped
> failure. Day 38 turns this from a story into a drill; Day 45's audit makes it a
> checklist column.

Observed today, not just asserted: wire-lab ACT 1 (business with no handshake) vs ACT 2
(the ritual, answered with a shrug) — one server, two eras of caller, and you read both
transcripts raw.

## 6 · 🎤 Interview corner

1. **"Design an MCP server for me. What are the moving parts?"** — Three: an identity, a
   declared capability surface, and handlers. In the 2026 SDK that is one `MCPServer`
   object plus decorated typed functions — the decorator derives each tool's JSON Schema
   from type hints and the docstring becomes the model-facing description, so the contract
   layer is generated, not hand-maintained. What a good server *doesn't* have is just as
   important: no session store, no handshake state — every request self-carries version
   and capabilities in `_meta`, and `server/discover` answers identity questions on
   demand. I built Sutra's this way and proved the statelessness by piping raw JSON-RPC
   into it: `tools/list` answers cold, first message.
2. **"What actually travels when a tool is called over MCP?"** — Two JSON-RPC exchanges.
   `tools/list` returns the declarations — name, description, JSON Schema — and in the
   2026 revision that result is cacheable (`ttlMs`, `cacheScope`, deterministic ordering).
   `tools/call` carries the chosen name plus schema-shaped arguments; the result returns
   `content` for the model and a `resultType`. It is precisely the function-calling
   contract I once hand-rolled in-process — MCP is that contract promoted to a
   between-processes standard, which is why learning raw function calling first made MCP
   feel like review.
3. **"Your MCP server and your agent framework pin conflicting versions of the SDK — what
   do you do?"** — Never force the resolver. I check what each side actually requires
   (`uv add --dry-run` shows the conflict precisely), keep the resolvable set, and
   document the losing preference in the package ledger with the date. Because the
   protocol is versioned independently of any SDK, I verify behavior against the *spec*
   revision, not the library README — my server's concepts survive either SDK era, and my
   wire lab tells me in one command which era any counterpart speaks.
