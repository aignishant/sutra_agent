## 3 · 📚 Concepts

### ADK-35 — Sequence: the straight belt (and its contract)

You built one yesterday; today make the idea explicit. A sequence in 2.x is **a tuple**:

```python
edges=[("START", a, b, c)]
```

**The relay-race story.** A relay team wins or loses at the baton pass, not in the running.
A graph sequence is the same: the interesting part is not "b runs after a" — it is that
**a's `output` must be exactly what b's `node_input` expects.** The baton is typed
(Day 53: `output_schema` → deserialized `node_input`). When you design a sequence, you are
designing batons first, runners second.

💡 **Mental model: a sequence is a chain of contracts, not a chain of steps.** Write the
types between the arrows before you write any node: `str → TicketText → TriageResult →
ReportLine`. If you cannot name a baton, the sequence is not designed yet.

### ADK-36 — Parallel: two clerks, one in-tray (fan-out / fan-in)

**The two-clerks story.** A ticket arrives. One clerk searches the archive for similar
tickets; another checks the knowledge base. They work at *separate desks* and drop their
findings into *one in-tray*, and only when **both** envelopes are in the tray does the
analyst pick it up.

The 2.x drawing (adk.dev/graphs/routes/, 2026-08-19): fan-out has **no special keyword** —
you draw two edges leaving `"START"`; fan-in is a **`JoinNode`**:

```python
from google.adk.workflow import JoinNode

my_join = JoinNode(name="evidence_join")
edges=[
    ("START", archive_clerk, my_join),      # branch 1
    ("START", kb_clerk,      my_join),      # branch 2
    (my_join, analyst),                     # continues only when BOTH arrive
]
```

Two rules keep parallel honest:

1. **The join is a barrier.** `analyst` sees the *combined* branch outputs, and runs once.
   No polling, no sleeps — the runtime owns the waiting (compare your hand-rolled Day 36
   task polling; this is the same idea with the runtime holding the clipboard).
2. **Parallel stations must not share a pencil.** Two branches writing the same `state` key
   is a race — who wins depends on timing you do not control. Branch outputs belong in
   `output` (each branch has its own); merged truth is written ONCE, after the join. (You
   met this exact disease as SQLite lost-updates in Day 43's hammer lab. Same disease,
   graph edition.)

*When to use it:* independent work only. Research tasks (archive vs KB) — yes. Classify
then draft — no: there is a baton between them, so it is a sequence by nature.

### ADK-37 — Loop: the do-over, with a brake

**The proofreading story.** A writer drafts a paragraph. An editor reads it: "again —
tighten the middle." Second draft. "Good, ship it." That conversation is a loop with two
exits: *quality reached* or *patience exhausted*. Professional editors have both. Only
amateurs have one.

The 2.x drawing needs three parts, all from pages you have already used:

1. **A router** — a function node that inspects the work and returns `Event(route=...)`:
   `"REVISE"` or `"SHIP"`.
2. **Dict edges + a back-edge** — the dict maps each route string to its target; routing
   *backwards* to an earlier node is what makes it a loop:

   ```python
   edges=[
       ("START", drafter, checker_router),
       (checker_router, {
           "REVISE": drafter,        # the back-edge: go around again
           "SHIP":   publisher,      # the exit
       }),
   ]
   ```

3. **A state counter — the brake.** The docs' own idiom (adk.dev/graphs/data-handling/):
   a node declares an extra parameter (`rounds: int`) and the runtime injects it from
   state; the node increments it via `Event(state={"rounds": rounds + 1})`. The router's
   FIRST check is the brake, not the quality:

   ```python
   if rounds >= MAX_ROUNDS: return Event(route="SHIP")   # patience exit — checked FIRST
   ```

💡 **Mental model: a loop without a brake is not a loop, it is a bet.** You are betting
that a model will eventually satisfy a condition you do not control. Day 3 gave you
`MAX_STEPS`; Day 7 gave you `max_llm_calls` (the runtime's global fuse, default 500);
today's counter is the same law drawn as an edge. Three brakes at three altitudes — Sutra
keeps all three, because they fail independently.

**🅿️ The other way to draw all three shapes — dynamic workflows.** One page over
(adk.dev/graphs/dynamic/), 2.x offers `@node`-decorated async orchestrators where sequence
is just line-after-line, parallel is `asyncio.gather(...)`, and a loop is a `while` —
with `ctx.run_node()` executing children and automatic checkpointing. Read the page today
(10 minutes, it is short); do not build with it yet. Rule of thumb from the docs: static
paths → graph; gnarly branching → dynamic. Day 56 (planning) and Day 60 (durability — that
"checkpointing" word is a Phase 9 flare) use it in anger.

from google.adk.workflow import JoinNode               # the in-tray (verified 08-19)

def archive_clerk(node_input: str) -> Event:
    """Branch 1: search the ticket archive for look-alikes (deterministic here).

    Real archive search is Day 49's retrieval index; today's clerk calls the
    keyword fallback so the PARALLEL SHAPE is the only new thing on the table.

    Example:
        >>> archive_clerk("4521").output.startswith("ARCHIVE:")
        True
    """
    from sutra.loop import TICKETS                     # synthetic data, as ever
    tid = node_input.strip().lstrip("#")
    hits = [f"#{k}" for k, v in TICKETS.items()        # crude look-alike scan:
            if k != tid and "log" in v.lower()]        #   shared keyword = neighbor
    return Event(output=f"ARCHIVE: similar tickets: {', '.join(hits) or 'none'}")


def kb_clerk(node_input: str) -> Event:
    """Branch 2: fetch the best KB article for the symptom (deterministic).

    Example:
        >>> "KB-104" in kb_clerk("4521").output
        True
    """
    from sutra.loop import search_kb                   # Day 3's tool, reused raw
    return Event(output=f"KB: {search_kb('logged out')}")


def evidence_analyst(node_input) -> Event:
    """After the join: merge BOTH branch outputs into one evidence block.

    The JoinNode hands us the combined branch results; we normalize to text
    and staple them together. This is the ONLY place merged truth is written
    (parallel rule #2: branches never share a pencil).

    Example:
        >>> ev = evidence_analyst(["ARCHIVE: ...", "KB: ..."])
        >>> "ARCHIVE" in ev.output and "KB" in ev.output
        True
    """
    parts = [str(p) for p in (node_input if isinstance(node_input, (list, tuple))
                              else [node_input])]      # tolerate either join shape;
    block = "\n".join(parts)                           #   print once, then pin it
    return Event(output=f"EVIDENCE:\n{block}",
                 message="Both clerks reported; evidence merged.")


evidence_join = JoinNode(name="evidence_join")         # the in-tray itself

evidence_graph = Workflow(
    name="evidence_graph",
    edges=[
        ("START", archive_clerk, evidence_join),       # clerk 1 -> tray
        ("START", kb_clerk, evidence_join),            # clerk 2 -> tray
        (evidence_join, evidence_analyst),             # tray full -> analyst, once
    ],
)

**Step 4 — the polish loop (~2–3 flash-lite calls).** Append:

```python
# --- Day 54: loop — router + back-edge + state-counter brake ---------------
MAX_ROUNDS = 2                                         # the brake. Small on purpose.

polisher = Agent(
    name="polisher",                                   # the "writer" of this mini-loop
    model="gemini-3.5-flash-lite",                     # lite lane: cheap rounds (Day 24)
    instruction="""Improve the reply you are given for a support ticket.
Keep it under 3 sentences, plain English, no invented facts. Return only
the improved reply.""",
)

def quality_router(node_input: str, rounds: int = 0) -> Event:
    """Decide REVISE or SHIP. The brake is checked BEFORE the quality.

    Args:
        node_input: the current draft from the polisher.
        rounds: injected from workflow state by the runtime (docs' idiom);
            defaults to 0 on the first pass.

    Example:
        >>> quality_router("Sorry! " * 40, rounds=2).route
        'SHIP'
    """
    if rounds >= MAX_ROUNDS:                           # patience exit — FIRST, always
        return Event(route="SHIP",
                     message=f"Brake: {rounds} rounds used, shipping as-is.")
    ok = len(node_input) < 400 and "sorry" not in node_input.lower()[:40]
    return Event(route="SHIP" if ok else "REVISE",     # quality exit
                 state={"rounds": rounds + 1},         # count EVERY pass through
                 output=node_input)                    # the draft rides along


def publish_draft(node_input: str) -> Event:
    """Terminal station: stamp the surviving draft."""
    return Event(output=f"SHIPPED after review: {node_input}",
                 message="Draft shipped.")


polish_loop = Workflow(
    name="polish_loop",
    edges=[
        ("START", polisher, quality_router),
        (quality_router, {
            "REVISE": polisher,                        # the back-edge: around again
            "SHIP":   publish_draft,                   # the exit
        }),
    ],
)
```

## 5 · 💥 Failure lab — the loop that ate the daily quota

> 🎬 **The scene:** the polish loop works, but the brake bothers you aesthetically.
> "Shipping a draft the checker rejected? That's shipping known-bad work!" You delete
> `MAX_ROUNDS` so only quality can exit the loop. Standards!
> 😬 **The naive fix:** trust the polisher to eventually satisfy the checker. It usually
> does — in the demo, with an easy draft, on a good day.
> 💥 **Why it fails:** "usually" again. One awkward ticket makes the checker's condition
> unsatisfiable — say the reply legitimately needs 5 sentences but the checker demands 3.
> The polisher and the router now play catch forever. Nothing crashes; that is the cruel
> part. Events keep flowing, the graph is "working", and the only brake left is the
> runtime's `max_llm_calls` fuse at 500 — which your 5 RPM free lane will spend
> **100 minutes** feeding, torching the day's Gemini quota on one ticket before dying
> anyway. Day 24's ledger will show you the bill; SEC-04 (Day 59) will show you this same
> failure wearing scarier clothes.
> 💡 **The insight:** **every loop needs two exits — quality and patience — and patience
> is checked first.** Shipping a twice-reviewed imperfect draft (flagged, logged,
> escalatable) is a policy. An unbounded loop is an outage. Between those two, there is no
> third option, only the fantasy of one.

## 6 · 🎤 Interview corner

1. **"How do you express parallel work in a graph runtime, and what's the classic bug?"**
   — Fan-out is just multiple edges from the start marker; fan-in is a join node that
   barriers until every branch delivers. The classic bug is branches sharing mutable
   state — a write-write race where the winner depends on scheduling. My rule: branches
   speak only through their own outputs; merged truth is written once, after the join. I
   have hit the same bug at the storage layer (two MCP server instances on one JSON file)
   — parallelism moves, the disease travels with it.
2. **"Design a review loop that can't run away."** — Three brakes at three altitudes:
   a route-level counter checked *before* the quality condition (patience exit), the
   runtime's global LLM-call fuse (`max_llm_calls`), and quota accounting underneath so
   even a bug that dodges both can't spend tomorrow's budget. Exit-by-brake is an honest,
   logged outcome — ship-with-flag or escalate — never silent.
3. **"Sequential, parallel, loop — classes or patterns?"** — In ADK 1.x they were wrapper
   classes; 2.0 superseded them: now they're edge patterns on one graph — a tuple, a
   fan-out/join, a back-edge with a router. That's more than syntax: one floor means the
   shapes compose (a loop around a parallel block is just edges), and deterministic glue
   becomes free function nodes instead of prompt-driven agents.
