## 1 · 🎬 Where we are — the story so far

Every ID in the plan is closed. Ninety-two days of a system that triages support tickets,
consults an archive it cannot write to, escalates to humans through a durable gate,
survives being killed, refuses injections, proves who is calling, runs in a container on a
cluster, grades itself with an eval suite, and shows you all of it in a trace tree.

And to anyone who has not lived the ninety-two days, it is a folder of Python.

Today's job is translation. Not marketing — translation. A reader lands on the repo with
one question ("what is this and does it do anything?") and about forty seconds of patience.
If they leave without an answer, the ninety-two days did not happen as far as they are
concerned. This is a real engineering skill and it is *hard*, because you are the worst
possible person to judge whether your own README is clear: you cannot un-know the project.

There is also a second reader, and they matter more than the casual one: **the person
deciding whether to interview you.** They will not run the code. They will read the README,
open two or three files, and look at the commit history. Today is the day that path is
built deliberately instead of by accident.

## 3 · 📚 Concepts

### The forty-second README

**The story.** A stranger picks up a jar in a shop. They look at the front for a second and
a half, and either it goes in the basket or back on the shelf. Nobody reads the ingredients
first. A README's front label is the first screenful — roughly the first fifteen lines —
and everything below it is ingredients, read only by people the label already convinced.

Four questions, in this order, in the first screenful:

| Question | Failure mode if you skip it |
| --- | --- |
| **What is this?** one sentence, no framework names | "An ADK-based multi-agent orchestration platform" tells a reader nothing they can picture |
| **What does it do?** — *shown*, not claimed | a feature list is a promise; a transcript is evidence |
| **How do I run it?** | if setup looks like a research project, they leave |
| **What is it not?** | the single most trust-building section, and almost nobody writes one |

💡 **Mental model: the README is not documentation, it is a *decision aid*.** Its job is to
help someone decide, fast and correctly, whether to spend more time. That means being
honest about limits is not a weakness in a README — it is the feature that makes the rest
of it credible.

⚠️ **The trap for this project specifically.** Ninety-two days of work creates enormous
pressure to list all of it. Resist. A wall of accomplishments reads as noise, and worse, it
reads as *undifferentiated* — the injection defence and the trace exporter get equal
billing, so nothing lands. Pick the two or three things that are genuinely unusual for a
learning project — mine would be *the approval gate that survives a kill*, *the red-team
fixtures with a scorecard*, and *the eval suite* — and let the rest live in the docs index.

### "What it is not" — the section that earns trust

This project has real limits, most of them chosen: no billing account, so no managed
identity, no Postgres, no cloud deployment; single replica, for the reasons Day 86 found by
scaling and breaking; free-tier models only; synthetic data throughout. Every one of those
is a *decision with a reason*, and a reader who sees them stated plainly concludes something
specific: this person knows where the edges are.

> 🎬 **The scene:** you write the limitations section and it feels like an apology. So you
> soften it — "currently single-replica", "production deployment coming soon".
> 😬 **The naive fix:** the future tense. It costs nothing and sounds better.
> 💥 **Why it fails:** "coming soon" is a promise to a stranger that you have no plan to
> keep, and a knowledgeable reader discounts everything else you wrote, because now they
> cannot tell which parts are real and which are aspirational. It also hides the good part
> — you did not fail to scale, you *scaled it, measured three specific bugs, and wrote down
> the migration path*.
> 💡 **The insight: state the limit, then state what you learned from it.** "Single replica.
> Two replicas double-spend the quota ledger and race the write-idempotency guard — measured,
> see `docs/DEPLOY.md`. Fixing it means Postgres and a shared counter, which needs a billing
> account this project doesn't have." That paragraph is *stronger* than a working cluster
> would be, because it proves you tested rather than assumed.

### What "public" means, one last time

Day 92 checked the repository. Today checks the *presentation*, and there are three things
the security review did not cover because they are not security questions:

1. **Attribution.** Anything vendored from elsewhere — Day 71 copied ADK's
   `PlaywrightComputer` sample under Apache-2.0 with a provenance header — needs its licence
   preserved and visible. Check `SKILL_PROVENANCE.md` against the tree, file by file.
2. **Your licence.** Choose deliberately. MIT/Apache-2.0 for "use it, learn from it"; no
   licence at all means nobody may legally use it, which is a choice you can make but should
   make on purpose. If any vendored code is Apache-2.0, Apache-2.0 for the whole repo is the
   simplest compatible answer.
3. **Everything that names a real person or company.** Synthetic tickets are lint-checked
   (Day 69), but commit messages, TODOs, screenshots and trace exports are not.

## 5 · 💥 Failure lab — the README that only you can read

> 🎬 **The scene:** you finish the README and it is good. It is accurate, well-organised,
> technically precise. Then you run the forty-second test on a friend who writes software
> but knows nothing about agents. You watch their eyes.
>
> They stop on line one. Your sentence is:
>
> > *Sutra is a multi-agent triage system built on Google ADK 2.x, featuring durable
> > workflow execution, HITL approval gates, defense-in-depth guardrails and an
> > OTel-instrumented graph runtime.*
>
> Forty seconds later they can tell you it involves agents. They cannot tell you what it
> *does*, whether they could run it, or what it will not do. Every word is true.
>
> 😬 **The naive fix:** add a paragraph explaining the terms. The README gets longer and
> the first screenful gets worse.
>
> 💥 **Why it fails.** The sentence is written from the *inside*. Every noun is a thing you
> chose — the framework, the execution model, the gate design — and choices are what feel
> significant to the builder. A reader has made none of those choices, so the nouns carry
> no meaning; they are a list of unfamiliar terms, and unfamiliar terms in the first line
> read as "this is not for me". Worse, the sentence has no **subject a human can picture**.
> Nobody is in it. Nothing happens to anyone.
>
> Compare:
>
> > *Sutra reads incoming support tickets, works out what's wrong, searches past tickets
> > for a fix, and either answers or hands it to a human — and it asks permission before it
> > touches anything real.*
>
> Same system. No framework named. A reader now knows what it does, and the last clause
> quietly tells a technical reader the most interesting thing about the design.
>
> 💡 **The insight: describe the behaviour, not the architecture.** Architecture goes in the
> second section, where the reader who is still there actually wants it. The test is
> mechanical, which is what makes it usable: **would this sentence still make sense if the
> framework had been different?** If not, you have described your implementation, not your
> system.
>
> The same disease has three other forms, all of them in this repo's drafts:
>
> - **Curse-of-knowledge steps.** "Set up your `.env` as usual" — usual for whom? A stranger
>   has never seen your `.env`. This is why Step 5 clones into a temp directory: you cannot
>   *reason* your way out of the curse of knowledge, you have to be caught by an environment
>   that does not share your assumptions.
> - **Feature lists as evidence.** "Includes prompt-injection defence" is a claim. A
>   transcript showing an injection arriving and being refused is evidence, and it takes the
>   same amount of space.
> - **The undifferentiated wall.** Ninety-two days listed flat, so a reader cannot tell the
>   trace exporter from the durable approval gate. Rank ruthlessly; three things, then a
>   link.
>
> Rewrite, and run the forty-second test again on a **different** person — the first one is
> burned, they know the project now. Two clean passes and it ships. And keep the failed
> draft in `docs/DEMO.md`'s appendix as a before/after: it is a better demonstration of
> engineering judgement than the polished version alone.

## 6 · 🎤 Interview corner

1. **"Give me the elevator pitch for this project."** — Sutra reads incoming support
   tickets, works out what's wrong, searches past tickets for a fix, and either answers or
   hands it to a human — and it asks permission before it touches anything real. Under that:
   it's a graph of agents on Google's ADK, the approval gates survive the process being
   killed mid-run, and it holds a red-team fixture suite and an eval suite that both run in
   CI. I lead with the behaviour rather than the architecture on purpose — I had a version
   that opened with "multi-agent triage system with durable workflow execution and HITL
   gates", handed it to a developer who doesn't work on agents, and after forty seconds they
   couldn't tell me what it did. Every word was true and none of it was about anyone. The
   test I use now: would this sentence still make sense if I'd picked a different framework?
   If not, I've described my implementation instead of my system.
2. **"What doesn't your project do?"** — Quite a lot, and mostly on purpose. It runs one
   replica: I scaled it to two and got three specific bugs — doubled quota spend because the
   ledger is a JSON file, approval verdicts not reliably visible across instances because
   SQLite WAL doesn't work on a shared mount, and a race in the write-idempotency guard that
   can close a ticket twice. Fixing it properly means Postgres and a shared atomic counter,
   which needs a billing account I don't have, so it's documented with the migration path
   rather than half-built. Same for managed identity and cloud deployment — mapped, costed,
   never run. Free-tier models only, synthetic data throughout. I put that section in the
   README because it's the part that makes the rest credible: I'd rather a reader knows I
   measured the limit than assume I never reached it. And "coming soon" is a phrase I keep
   out — it's a promise to a stranger I have no plan to keep, and it makes everything else
   look aspirational.
3. **"How do you know your setup instructions work?"** — I don't trust my own machine to
   tell me. I cloned the repo into a temp directory and followed `docs/DEMO.md` literally,
   typing nothing that wasn't written down. Every place I had to think, the doc was missing
   a line — and it was always something boring: the Python version, where the key comes
   from, what success looks like on screen. My working copy has a `.env`, a warm database
   and four months of state; it's the exact environment that hides setup bugs. The general
   version is that you can't reason your way out of the curse of knowledge — you have to
   put yourself in a situation that doesn't share your assumptions. Same reason I hand the
   README to a person and take it away after forty seconds instead of asking myself whether
   it's clear.
