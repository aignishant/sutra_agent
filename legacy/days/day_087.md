kind that a project with a written master plan is supposed to catch and record rather

## 3 · 📚 Concepts

### ADK-68 — What a managed agent runtime actually sells you

**The story.** You have built a good bread oven in your garage. It works. Then someone
offers you a slot in a commercial bakery: proper extraction, someone else's gas bill,
someone else's inspections, and a queue system that handles a hundred customers. What
they sell is not "an oven" — you already have one. They sell **the things around the
oven**, and they charge for them.

A managed agent runtime is the same trade. Your container already runs the agent. What
the platform adds is scaling, an API layer, session storage, identity plumbing and
observability wired into their console. What it removes is control over the process
model, and money from your account.

📌 **Finding #1 — the product is not called what the plan calls it.** The master plan
(§14, Day 87) says *"Agent Engine — documented walkthrough (config written, not billed)"*.
On 2026-08-20, `adk.dev/deploy/` lists four targets and names the managed one **"Agent
Runtime"**, part of **Google Cloud Agent Platform**. `adk.dev/deploy/agent-runtime/` uses
"Agent Runtime" throughout. "Agent Engine" was the earlier name (and still appears in
older CLI surfaces, e.g. `adk deploy agent_engine`, and in community threads).

This is exactly the situation Principle 14 exists for: **reality disagrees with the plan,
so the plan gets amended, not silently reinterpreted.** ADK-68 still closes today — the
concept is unchanged and the ID is about the managed-hosting *idea* — but
`CHANGELOG_PLAN.md` gets a row saying the product was renamed and when that was observed.
An interviewer who knows the ecosystem will notice if you use a two-year-old name; more
importantly, someone reading this repo in a year needs to know which name to search for.

**What the docs say, quoted and dated (2026-08-20, `adk.dev/deploy/agent-runtime/`):**

| Fact | Quoted / recorded |
| --- | --- |
| Cost | *"Agent Runtime is a paid service and you may incur costs if you go above the no-cost access tier."* |
| Languages | Python and Go (Go from v1.2.0+) |
| Two paths | manual (Cloud Console + ADK CLI), or the Agents CLI which brings CI/CD + infrastructure-as-code |
| What's uploaded (Python) | your agent code + declared dependencies — **not** the ADK API server or web UI libraries; the runtime provides those |
| What's uploaded (Go) | includes the dedicated ADK API server |

That fourth row is the one with teeth, and §5 is about it.

### The four deployment targets, and how to choose between them

`adk.dev/deploy/` (2026-08-20) lists exactly four. The useful skill is not knowing they
exist — it is having a reason for each:

| Target | You choose it when | Sutra's position |
| --- | --- | --- |
| **Agent Runtime** (Agent Platform) | you want the least infrastructure and will pay for it | 🅿️ — paid |
| **Cloud Run** | you have a container and want it to scale to zero | 🅿️ — paid; `adk deploy cloud_run --project … --region …` written in `docs/DEPLOY.md`, never run |
| **GKE** | you need cluster-level control, sidecars, or open models | Day 88 does this **locally** with kind/k3d — free |
| **Other container infrastructure** | offline, on-prem, your own box | ✅ **this is Sutra** (Day 86) |

💡 **Mental model: the four targets are one axis — how much of the process model you are
willing to stop owning.** At one end you own everything (Day 86's compose file: you chose
the ports, the healthcheck, the volumes). At the other you own almost nothing and it
mostly Just Works, including the bill. Nothing about that axis is agent-specific; it is
the same trade as any hosting decision. Say that in an interview and you sound like
someone who has deployed things, rather than someone who has read a landing page.

### The parked-document discipline

A 🅿️ artifact is a promise about the future written by someone who cannot test it. Left
alone it decays into confident nonsense — the worst possible thing to find in a repo,
because it *reads* like it works. Four rules, and they apply to everything marked 🅿️ in
this project (Days 39, 41, 71, 89, 90, 91 all have some):

1. **The first line says it never ran.** Not a footnote. The first line.
2. **Every claim carries its source and date** — the URL, and the day it was read.
3. **It names the command that would re-verify it**, so re-checking is a paste, not a
   research project.
4. **It states the trigger condition** — the specific thing that would have to become
   true before anyone should run it. "If we get budget" is not a trigger condition;
   "if sustained traffic exceeds N runs/day, at which point the free tier is exhausted
   anyway" is.

## 5 · 💥 Failure lab — the deploy that succeeded and the agent that couldn't do anything

> This lab is a **thought experiment run against the docs**, not a live break — which is
> itself the point of a parked day. It is also the reason Step 5 exists.
>
> 🎬 **The scene:** a future you gets a billing account. The parked walkthrough is
> right there, and it looks complete. `adk deploy agent_engine …`. The upload succeeds.
> The console shows a green agent. You send it a ticket.
>
> It answers — and it is *wrong in a way that takes an hour to see*. The reply cites no
> KB article. Every triage comes back at severity 3. Nothing is ever escalated. There are
> no approvals pending. And `/readyz` returns 404.
>
> 😬 **The naive fix:** the agent must not have deployed properly — redeploy, bump the
> version, check the logs for an exception. There is no exception; that is the problem.
>
> 💥 **Why it fails.** Nothing crashed, because nothing was *supposed* to crash. Four
> different assumptions quietly evaporated, and each one degraded rather than failed:
> **(1)** The runtime provides its own API server — so `sutra/api.py` never ran, and with
> it went `/readyz`, the ambient trigger route, and the CORS default. A 404 is the only
> symptom.
> **(2)** There is no writable `data/`, so the session store, the approvals database and
> the `processed_writes` idempotency table are gone. Approvals do not *error*; the gate
> just never finds a verdict, and the escalate lane sits there.
> **(3)** `localhost:11434` is not there, so the embedder fails and Day 49's retrieval
> returns nothing — which the graph handles gracefully, because a research step that finds
> no evidence is a legitimate state. So: no citations, and no error.
> **(4)** `sutra-mcp` is not a sidecar any more, so `lookup_ticket` falls back or fails
> quietly depending on how the client was written.
> The through-line: **every one of these is a dependency on the environment that the
> container made invisible by satisfying it.** Day 86 didn't remove those dependencies —
> it packaged them, which felt like the same thing.
>
> 💡 **The insight: portability is a claim, and the only way to hold it honestly is to
> enumerate what you depend on *outside* your own code.** "It's containerised" describes
> the packaging; it says nothing about localhost ports, writable paths, sidecars, or an
> HTTP server you assumed you owned. That enumeration is Step 5's table, and it is worth
> more than the config file it sits next to — a config file is ten minutes of work when
> you actually need it; the audit is the thing you cannot reconstruct under deadline.
>
> Second insight, about parked documents themselves: **the danger of a walkthrough you
> never ran is not that it's wrong — it's that it's *plausible*.** Which is why every 🅿️
> artifact in this repo starts by admitting it, carries dated sources, and names the
> command that would re-check it. A future reader with a deadline will trust a confident
> document. Make yours honest instead of confident.

## 6 · 🎤 Interview corner

1. **"What are your options for deploying an ADK agent, and how would you choose?"** —
   Four, and they sit on one axis: how much of the process model you're willing to stop
   owning. Fully managed Agent Runtime on Google's Agent Platform — least infrastructure,
   paid. Cloud Run — you bring a container, it scales to zero. GKE — cluster control,
   sidecars, open models. Or any container host, which is where I actually am. I chose the
   last because the project has a hard zero-budget constraint, and I wrote the other three
   up as parked walkthroughs with dated sources. Worth knowing: the managed runtime is the
   one that was called "Agent Engine" and is now "Agent Runtime" — I logged the rename in
   my plan changelog when I noticed the docs had moved.
2. **"You wrote deployment configs you never ran. Isn't that just fiction?"** — It is,
   unless you write it under rules that stop it rotting. Mine are: first line says it was
   never executed; every factual claim carries the URL and the date it was read; the
   re-verification commands are in the file so re-checking is a paste; and it states the
   specific condition under which someone should run it. The risk with a parked doc isn't
   that it's wrong — it's that it's plausible, and a future reader under deadline will
   believe it. So the artifact's job is to be honest rather than confident.
3. **"How portable is your agent, really?"** — Less than "it's containerised" suggests,
   and I have the list. I audited every dependency my code has on its environment and
   colour-coded it: the five plugins port cleanly because they live on the agent; tracing
   ports with a config change. But a managed runtime provides its own API server, so my
   custom `/readyz` and ambient-trigger routes would vanish; there's no writable volume,
   so my SQLite session, approval and idempotency stores would have to move to a managed
   database; my embedder is a local Ollama on a fixed port, which doesn't exist there; and
   my MCP server is a sidecar, which that model doesn't have. Four red rows. What makes
   that dangerous rather than merely inconvenient is that most of them *degrade silently* —
   no retrieval means no citations, not an exception. Containerising didn't remove those
   dependencies; it satisfied them, which feels like the same thing right up until it
   isn't.
