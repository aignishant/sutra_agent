## 1 · 🎬 Where we are — the story so far

Everything works. Every subsystem has a green test, a failure lab, and a day document
explaining why it exists. The repo is public. By any reasonable accounting the project is
finished.

And it has never once been run end to end, cold, in a single unbroken sequence, against a
scenario nobody wrote the code for.

That gap is not pedantry. Every proof so far was collected on a warm machine — a populated
`data/`, a cache with entries, an embeddings index already built, a `.env` you last touched
in April, a peer registry whose entries were fresh when you added them. Subsystems were
tested in isolation, each with the others already working. What has never been tested is
the **composition**, from zero, under time pressure, with a scenario chosen to require all
of it at once.

That composition is exactly what a demo is. It is also exactly what a first day in
production is. Today you run it, with a clock going, and you write down what happens —
including, and especially, the parts that go wrong.

## 2 · 🎯 Today's mission

## 3 · 📚 Concepts

### Integration is a property, not a sum

**The story.** A restaurant's dishes are all excellent, tested individually by the chef over
weeks. Opening night, thirty tables order at once. The starters are cold by the time the
mains are ready, two dishes need the same pan, and the one person who knows where the spare
gas bottle is has gone home. Nothing on the menu was wrong. The *composition* was never
tested, because composition only exists when everything runs at the same time.

Software has the identical shape, and agent systems have it worse, because the components
share three things that never appear in a unit test: **a rate limit**, **a clock**, and
**state that outlives the process**.

| Tested in isolation | What only appears in composition |
| --- | --- |
| each agent answers correctly | they compete for one 5 RPM lane |
| the approval gate resumes | it resumes *while the cache is cold and the index is rebuilding* |
| the guardrail refuses injection | it refuses it *and the run has to carry on sensibly* |
| the eval suite is green | it is green against fixtures, not against today's live trajectory |

💡 **Mental model: subsystem tests prove the parts exist; a cold end-to-end run proves the
seams do.** Almost every capstone finding lives in a seam — an assumption one component
makes about another's state, which was true because you had already run that other
component this week.

### Why "cold" is the whole point

> 🎬 **The scene:** you demo to someone important. You have run this flow twenty times. It
> works. On the day, on their machine or your freshly-restarted laptop, the first stage
> takes ninety seconds and then fails on something about an index.
> 😬 **The naive fix:** "let me just run it once first to warm it up" — said out loud, in
> front of the audience.
> 💥 **Why it fails:** the twenty successful runs all inherited state from run zero, which
> you did months ago and have forgotten. The embeddings index (Day 49), the cache (Day 51),
> the session database (Day 47) and the quota ledger all existed before your first
> *successful* attempt, so no run has ever exercised the empty-state path. And empty-state
> code is the least-tested code in any system, because it executes exactly once per
> machine.
> 💡 **The insight: your machine's memory is an undocumented dependency.** The only way to
> find it is to delete it. That is why today starts with a fresh clone rather than
> `rm -rf data/` in your working copy — the clone also drops the things you would not think
> to delete.

### Designing a scenario that forces everything

A demo that shows a happy path proves the least interesting claim. Build the scenario so
each beat *requires* a subsystem, and write the mapping down before you run anything —
otherwise you will unconsciously choose a story your system already handles.

A worked example (adapt to your fixtures):

| Beat | What happens | Subsystem it forces |
| --- | --- | --- |
| 1 | A ticket arrives through the intake surface, not a curl | Day 91 intake contract |
| 2 | It is vague; the agent must consult the archive | Days 32/49 MCP + retrieval |
| 3 | A past ticket in the archive contains an injected instruction | Days 66–68 guardrails |
| 4 | The fix requires closing a ticket — a real write | Days 63/64 approval gate |
| 5 | You kill the process while the approval is pending | Days 60–62 durability |
| 6 | You approve via the operator CLI; the run resumes | Day 63 durable store |
| 7 | The customer's email must not reach the model or the peer | Days 69/89 data boundary |
| 8 | Everything above appears as one trace | Day 84 tracing |
| 9 | The trajectory is graded against the rubric | Days 79–80 evals |

⚠️ Beat 3 matters more than it looks: the injection is planted in **the archive**, not in
the user's message. That is the trifecta arrangement Day 67 identified as the dangerous one
— private data, untrusted content, an external channel — and demoing it is far more
convincing than a user typing "ignore your instructions".

## 4 · 🛠️ The build

> Shell: **PowerShell**. Today you work in a **fresh clone**, not the repo you have been
> living in.

**Step 1 — design the scenario and write the beat table.** Fill in §3's table with your
actual fixture ids, then write the *narration* — two sentences per beat, the words you
would say out loud. Tomorrow (Day 95) turns this into a recording script; today it is the
thing that keeps you honest about coverage.

✅ *Verify:* every subsystem from the plan's fifteen phases appears at least once, or is
explicitly listed as "not in the capstone, and why" (voice/live and browser-use are the
likely honest omissions — say so rather than pretending).

**Step 2 — go cold.**

```powershell
cd $env:TEMP ; git clone <your repo url> sutra-capstone ; cd sutra-capstone
uv sync --frozen
Copy-Item <your .env path> .\.env        # keys only; nothing else crosses over
Get-ChildItem data, logs -ErrorAction SilentlyContinue   # must be empty or absent
```

✅ *Verify:* `data/` and `logs/` do not exist or are empty; no `.adk/`; no cache; no
embeddings index. **Start a stopwatch now** — total elapsed time is one of today's outputs.

📌 The `.env` is the only thing you copy, and copy it deliberately rather than symlinking:
if any step needs a file you did not knowingly bring, that is the finding.

**Step 3 — dry run the wiring before spending tokens.** Everything that can be proven
without a model, first:

```powershell
uv run pytest -q -m "not model"          # or your suite's offline subset
python tools\check.py ; python tools\trace.py
uv run python -m sutra.redteam seed      # fixtures into a fresh data/tickets.db
```

✅ *Verify:* offline tests green, **199/199**, fixtures seeded. Any failure here is free to
find and expensive to find later — a cold-start bug caught before the first model call
costs nothing but a minute.

**Step 4 — the run, part 1: intake → triage.** Start the stack the way the runbook will
(`docker compose up` if you are demoing the container, otherwise the local processes), send
the ticket through the **intake surface**, and watch.

✅ *Verify:* the reply arrives; the trace shows every expected span (intake → triage →
archive → judge); the quota ledger increments on the lanes you predicted in §2. If the
router sent the judge to the flash lane instead of lite, that is a finding — Day 70 said it
would not.

**Step 5 — part 2: the injection beat.** The archive result carries the planted
instruction.

✅ *Verify:* the guardrail neutralises or refuses it, the event is logged with its `kind`
and score, **and the run continues to a sensible answer**. That last clause is the one
people forget to check: a defence that turns every injection into a dead end is a denial of
service on yourself. Capture this moment — it is the best thirty seconds of tomorrow's
recording.

**Step 6 — part 3: approval, kill, resume.**

```powershell
# ... run reaches the gate and pauses ...
# kill the process HARD — not Ctrl+C, which is a graceful shutdown path you have tested
Stop-Process -Name python -Force            # or `docker compose kill sutra-api`
uv run python -m sutra.approvals list
uv run python -m sutra.approvals approve <id>
# resume with the recorded invocation id
```

✅ *Verify — the four-part check that is the heart of the whole project:* the pause survived
the kill · the verdict came from the durable store, not the transcript · the payload hash
still matched (no `ApprovalDriftError`) · and `close_ticket` executed **exactly once**
(check `processed_writes`, not the logs). If any of those slips, stop and fix it today —
this is the claim the README leads with.

**Step 7 — part 4: evals against this run.** Grade the trajectory you just produced, not a
fixture:

```powershell
uv run python -m sutra.evals run --from-trace <this run's id>
```

✅ *Verify:* the rubric lines pass — especially *"escalated before any external write"*
(Day 80). A capstone where the eval suite grades the live run is materially more convincing
than one where it grades a saved file, and it is the same command.

**Step 8 — time it, write it, log the stumbles.** Stop the clock. Then write
`docs/runbooks/capstone.md` with, per stage: the command, the expected output, the observed
duration, and the recovery move if it fails.

Then run the whole thing **a second time** on the same clone (now warm).

✅ *Verify:* the second run is meaningfully faster — cache hits, index built, sessions
present — and you can state the cold/warm delta in seconds. That number is a great answer to
"how long does your demo take?" and an honest one, because it names both.

```powershell
# back in your real repo:
git add -A ; git commit -m "day 094: capstone I — the end-to-end scenario, run cold"
```

✅ *Verify:* `trace.py` still **199/199, 0 problem(s)**.

## 5 · 💥 Failure lab — the stumbles are the deliverable

> 🎬 **The scene:** you are twenty minutes into the cold run with the clock going, and it
> stops. Not dramatically — it just sits there, then returns something empty. The archive
> search found nothing, so the triage agent had nothing to reason with and produced a
> confident, useless answer.
>
> The cause takes eleven minutes to find: `data/archive_index.json` (Day 49) does not exist.
> Nothing built it. On your real machine it was built months ago by a step in the Day 49
> document, and it has been quietly present ever since — so every subsequent test, every
> eval, every demo rehearsal ran against an index that no code path in the repo creates.
>
> 😬 **The naive fix:** build the index, note the command in the runbook, carry on. You have
> lost eleven minutes; the instinct is to buy back time.
>
> 💥 **Why that is not enough.** Three things just happened and only one of them is about
> the index.
>
> **(1) A setup step lived only in a day document.** `docs/days/day_049.md` is a *narrative*,
> not a build system. Anything a fresh clone needs must be reachable from `docs/DEMO.md` or
> a `make` target — otherwise the project's real setup procedure is "read ninety-six essays
> in order", which is a thing you will never notice while you are the only user.
>
> **(2) The empty-state behaviour was wrong, and worse than the missing file.** A missing
> index made the search return *nothing* rather than *fail*. The agent then answered anyway,
> confidently, because an empty result looks exactly like "no relevant past tickets". That
> is the failure mode this whole project exists to prevent — a system that cannot tell the
> difference between "I looked and there was nothing" and "I could not look". Fix the
> behaviour, not just the file: a missing index must raise, loudly, at startup.
>
> **(3) Every green result that depended on the archive is now suspect.** Not wrong —
> suspect. The evals, the red-team scorecard, several failure labs. They ran against an
> index nobody could rebuild, so nobody knows whether they would pass on a clean machine.
> Re-run what you can and mark the rest honestly.
>
> 💡 **The insight: a cold run does not test your code, it tests your *assumptions about
> your environment* — and those are the ones you cannot see, because you are standing in
> them.** The stumbles are therefore the point. A capstone that runs perfectly first time on
> a fresh clone usually means the clone was not fresh.
>
> So the deliverable of today is two documents, not one:
>
> - `docs/runbooks/capstone.md` — the script that now works.
> - **The incident log** — every stumble, in order, with: what you expected · what happened ·
>   how long the diagnosis took · root cause · fixed or accepted. Put it in the runbook's
>   appendix. It is the most honest artifact in the repo, it converts directly into three
>   interview answers, and it is the thing that tells you where the seams are.
>
> Then close the loop so the finding cannot recur: **add a cold-start check** —
> `python tools/check.py --cold` (or a startup assertion) that verifies every file the
> system needs either exists or has a documented command that creates it. Day 92's lesson
> applies unchanged: a control you have to remember is not a control. If the fresh-clone
> path can break silently, it will, on the day someone is watching.

## 6 · 🎤 Interview corner

1. **"Have you actually run this end to end?"** — Yes, and from a fresh clone with an empty
   database, which is a different claim from "the tests pass". I designed one scenario that
   forces every subsystem — a vague ticket arrives through the intake surface, the agent has
   to consult the archive, a past ticket in that archive contains a planted injection, the
   fix requires a real write so it hits the approval gate, I kill the process while the
   approval is pending, approve through the operator CLI, and the run resumes and executes
   exactly once. Then the eval suite grades that live trajectory rather than a fixture. I
   timed it cold and warm and I can give you both numbers. The reason I insist on cold is
   that every previous run inherited state from months of use — the embeddings index, the
   cache, the session database — so no run had ever exercised the empty-state path, which is
   the least-tested code in any system because it executes once per machine.
2. **"What broke?"** — The best one: the archive returned nothing, and the agent answered
   anyway. Root cause was that the embeddings index didn't exist, because the only thing
   that ever built it was a step inside a day-log document — so the project's real setup
   procedure was "read the essays in order", which I'd never notice as the only user. But
   the file was the least interesting part. The actual bug was that a missing index made
   search return *empty* instead of *failing*, and empty is indistinguishable from "no
   relevant history", so the system couldn't tell "I looked and found nothing" from "I
   couldn't look" — which is precisely the failure this project exists to prevent. And it
   cast doubt on every earlier green result that touched the archive; not wrong, but
   unverified on a clean machine. I fixed the behaviour to fail loudly at startup, moved
   setup into the demo doc and a check target, and added a cold-start check so it can't
   regress silently.
3. **"How long does your demo take, and what happens if it fails live?"** — Cold it's on the
   order of tens of minutes because indexes build and caches are empty; warm it's a few
   minutes, and I can quote both. There's a written runbook with expected output and a
   recovery move per stage, because the failure I actually expect is a 429 — I'm on a free
   tier at roughly 5 requests a minute, and a full run is 25–40 model calls. So the demo has
   a quota plan: the judge and eval passes route to the cheaper lane, the cache stays on for
   the second run, and there's exponential backoff with a runbook if I hit the wall. If it
   dies mid-run, the interesting part is that it's *resumable* — that's the whole point of
   the durability work, so I'd let it resume in front of you rather than restart, which is a
   better demo than the happy path.
