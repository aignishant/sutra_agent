## 3 · 📚 Concepts

### AG-01 — What an agentic system is

**The story of three employees.** A support ticket arrives: *"user reports a login loop."*
Imagine three different employees receiving it:

1. **The parrot** answers immediately with general advice about logins. It never looks
   anything up, never takes an action. One reply, done. That is a **chatbot**.
2. **The assembly-line worker** follows a fixed checklist someone wrote last year:
   classify the ticket → pick template #7 → send. Fast and reliable — *until* a ticket
   arrives that fits no step on the list. Then the line just jams. That is a **workflow**:
   the *programmer* decided every step, in advance.
3. **The detective** reads the ticket and *thinks about what this particular case needs*:
   "Let me search the archive… interesting, an old 'auth redirect bug' looks similar… let me
   check the vendor status page too… now I'll draft a reply citing both." Nobody scripted
   those steps. The detective *chose* them, at runtime, because the situation demanded them.
   That is an **agent**.

**Simple version:** a program is *agentic* when **the model, not the programmer, decides what
happens next**. You give it a **goal**, some **tools**, and a **loop**; it looks at the
situation, picks an action, observes the result, and repeats until the goal is met or it
decides to stop.

The same three, as a table you can reuse in an interview:

| Kind | Who decides the steps? | Ticket #4521 experience |
| --- | --- | --- |
| **Chatbot** | Nobody — it just answers | Replies with generic login advice. One turn, no actions. |
| **Workflow** | The programmer, in advance | Runs the fixed pipeline: classify → template reply. Breaks the moment the ticket doesn't fit the pipeline. |
| **Agent** | The model, at runtime | Decides to search the archive, finds an old "auth redirect bug", checks the vendor status page, drafts a reply citing both — because *it judged* those steps were needed. |

💡 **Mental model:** a workflow is a **railway** — fast, safe, fixed track. An agent is a
**taxi** — it goes wherever the situation demands, which is exactly why it needs brakes,
budgets, and audits. Sutra is a taxi fleet with very good brakes: an autonomous triage desk
where every risky action sits behind a gate. Most of the 96 days are about *earning the
autonomy safely* — capability and containment always arrive together (Principle 13).

### OPS-01 — Project bootstrap (the repo is the memory)

**Simple version:** one repository holds everything — the product code (`sutra/`), the data
boundary (`sutra_mcp/`), the skills, the tooling, and, most importantly, the docs and the
ledgers. There is no knowledge that lives only in a chat window.

Two tooling choices, and the *why* behind each:

- **`uv`** manages Python and dependencies. Think of it as a very fast, very tidy
  quartermaster: it keeps an exact list (a lockfile) of every package and version, so the
  environment can be rebuilt identically anywhere.
- **Python 3.12** is the pin. The supported window is 3.10–3.14, and 3.12 is the middle-aged,
  boring, stable pick (plan §5). Boring is a feature in a foundation.

*Example of why this matters:* on Day 40, someone asks "which version of `google-adk` did we
install, and why?" The answer is a ledger row with a date — not a scroll through a
conversation that may no longer exist.

### OPS-02 — Secrets discipline

**The photocopier story.** Git is like an office photocopier that automatically keeps a copy
of **every page ever placed on it — forever**. Now imagine taping your house key to a page
"just for a second." Removing the page later changes nothing: the copy with the key is still
in the archive, and anyone who gets the archive gets your key.

That is exactly how git history works. A key committed once and deleted in the next commit is
**still in history forever** — `git log -p` digs it out in seconds. And this repo goes
**public in Phase 14**, so a leaked key today is a real future incident, not a hypothetical.

**Simple version:** keys are radioactive. Three rules, all structural (rules that *can't* be
forgotten beat rules you must remember):

1. Keys live in `.env`, and **git is told to ignore `.env` before the file even exists**
   ("ignore-first").
2. Code reads keys from the environment — never from a committed file, never printed.
3. The only cure for a leak is **revocation** — which is why today includes a real
   revoke-and-rotate drill, not just a warning.

The three keys (all free, no credit card — Addendum 02 §2): **Gemini** (aistudio.google.com —
the primary brain), **Groq** (console.groq.com — the speed lane), **OpenRouter**
(openrouter.ai — the breadth lane, `:free` models only).

### OPS-03 — Ledgers & traceability

**The diary and the scoreboard.** Sutra keeps two kinds of record, and mixing them up is the
classic mistake:

- **Append-only ledgers** are the project's *diary*: you only ever add new rows at the
  bottom, never edit old ones. `PROGRESS.md` (one row per finished day), `PACKAGES.md` (every
  install, with version and date), `SKILL_PROVENANCE.md`, `CHANGELOG_PLAN.md`. A diary you
  can rewrite is not a diary.
- **Regenerated ledgers** are the project's *scoreboard*: a script computes them from the
  sources of truth, and **you never edit them by hand**. `TRACEABILITY.md` is the one we
  build today.

How the scoreboard works: the master plan's §14 map says which concept IDs each day must
close. `tools/trace.py` reads that map, reads the day docs, reads which days `PROGRESS.md`
marks green — and prints every ID as *closed on day N* or *still open*.

*Example of why a solo project needs this:* at the Phase 4 gate, trace.py prints `SK-16 OPEN`.
That single line is the difference between "I *feel* done" and "I *am* done." The rule is
blunt: **any open ID from a completed phase is, by definition, a bug.**

### Windows recovery: `uv` cannot remove a package directory

If `uv add`, `uv sync`, or `uv remove` fails with `failed to remove directory` and
`Access is denied. (os error 5)`, first close Python processes using this virtual environment.
If the failure persists, inspect the exact path named by `uv`:

```powershell
icacls .venv\Lib\site-packages\<package>.dist-info\<blocked-directory>
```

An `Everyone:(...)(DENY)(DC)` entry denies deletion even when your account has
`FullControl`. Remove only that deny entry from the blocked directory, then retry the same
`uv` command:

```powershell
icacls .venv\Lib\site-packages\<package>.dist-info\<blocked-directory> /inheritance:d
icacls .venv\Lib\site-packages\<package>.dist-info\<blocked-directory> /remove:d Everyone
uv add <package-you-were-adding>
```

✅ *Verify:* `icacls` no longer prints an `Everyone ... (DENY)(DC)` entry, and the retried
`uv` command completes. Do not delete or broadly reset ACLs on `.venv`; fix only the path
reported in the error.

**Step 7 — `tools/trace.py`, the traceability generator.**

This is the scoreboard-keeper from §3. Read it top to bottom with the comments — it is three
small readers (the plan, the progress diary, the day docs) plus one writer (the scoreboard).

> *(2026-08-14 note: this listing carries richer comments and docstrings than the version you
> may already have on disk — the **code statements are identical**. Re-pasting is optional;
> behavior does not change.)*

```python
"""Regenerate docs/days/TRACEABILITY.md.

Sources of truth:
  - master plan §14: which IDs each day must close
  - docs/days/day_NNN.md headers: which IDs a day doc claims
  - PROGRESS.md: which days are actually green (only those count as closed)
Never edit TRACEABILITY.md by hand.

Usage (from the repo root):
    python tools/trace.py
    # prints e.g.:  traceability: 4/199 closed, 0 problem(s)
"""
from __future__ import annotations

import re                      # regular expressions — how we find IDs in text
from datetime import date      # to stamp the file with today's date
from pathlib import Path       # modern, clean file paths (house style)

ROOT = Path(__file__).resolve().parents[1]      # tools/trace.py -> repo root
PLAN = ROOT / "docs" / "00_MASTER_PLAN.md"      # where the day->ID map lives
DAYS = ROOT / "docs" / "days"                   # day docs + the ledgers
# One pattern matches every concept ID we use: AG-01, ADK-73, MCP-26, ...
ID_RE = re.compile(r"\b(?:AG|ADK|MCP|SK|OPS|SEC)-\d{2}\b")


def plan_map() -> dict[int, dict]:
    """Read §14 of the master plan into {day: {'phase': int, 'ids': [...]}}.

    Example:
        >>> plan_map()[4]
        {'phase': 1, 'ids': ['AG-04']}
    """
    out: dict[int, dict] = {}
    phase, in_map = None, False                 # tiny state machine, two flags
    for line in PLAN.read_text(encoding="utf-8").splitlines():
        if line.startswith("## 14"):            # found the §14 heading:
            in_map = True                       #   start paying attention
        elif in_map and line.startswith("## "): # next big heading:
            break                               #   §14 is over, stop reading
        elif in_map:
            if m := re.match(r"### Phase (\d+)", line):
                phase = int(m.group(1))         # remember the current phase
            elif (m := re.match(r"\|\s*(\d+)\s*\|", line)) and phase is not None:
                # a table row that starts with a day number -> record its IDs
                out[int(m.group(1))] = {"phase": phase, "ids": ID_RE.findall(line)}
    return out


def green_days() -> set[int]:
    """The day numbers that have a row in PROGRESS.md (i.e. finished days).

    Example:
        >>> green_days()
        {1, 2, 3}
    """
    text = (DAYS / "PROGRESS.md").read_text(encoding="utf-8")
    # every line that starts like "| 3 |" is a finished day's row
    return {int(m.group(1)) for m in re.finditer(r"^\|\s*(\d+)\s*\|", text, re.M)}


def doc_claims(day: int) -> list[str]:
    """The IDs a day doc's header claims to close (empty if no doc yet).

    Example:
        >>> doc_claims(1)
        ['AG-01', 'OPS-01', 'OPS-02', 'OPS-03']
    """
    f = DAYS / f"day_{day:03d}.md"              # e.g. day_001.md (zero-padded)
    if not f.exists():
        return []                               # day not generated yet — fine
    for line in f.read_text(encoding="utf-8").splitlines():
        if "IDs closed:" in line:               # the header row we standardize on
            return ID_RE.findall(line)          # pull every ID out of that line
    return []


def main() -> None:
    """Cross-check plan vs docs vs progress; rewrite TRACEABILITY.md."""
    plan, green = plan_map(), green_days()
    lines = [                                   # the file we are about to write
        "# Traceability (regenerated; do not edit by hand)",
        f"_Generated {date.today().isoformat()} by tools/trace.py_",
        "",
        "| ID | Phase | Planned day | Status |",
        "| --- | --- | --- | --- |",
    ]
    total = closed = 0
    problems: list[str] = []                    # anything suspicious lands here
    for day in sorted(plan):                    # walk all 96 planned days
        claimed = set(doc_claims(day))
        for cid in plan[day]["ids"]:            # every ID the plan assigns
            total += 1
            if day in green and cid in claimed:     # finished AND documented:
                closed += 1
                status = f"✅ closed day {day}"      #   properly closed
            elif day in green:                      # finished but not claimed:
                status = "🐛 green day, ID missing from doc"   # that's a bug
                problems.append(f"{cid}: day {day} is green but its doc does not claim it")
            else:
                status = "⬜ open"                   # not reached yet — normal
            lines.append(f"| {cid} | {plan[day]['phase']} | {day} | {status} |")
        # the reverse check: a doc claiming IDs the plan never gave that day
        if day in green and (extra := claimed - set(plan[day]["ids"])):
            problems.append(f"day {day} claims IDs not assigned by the plan: {sorted(extra)}")
    lines += ["", f"**{closed} / {total} IDs closed.**"]
    if problems:                                # problems get their own section
        lines += ["", "## 🐛 Problems", *[f"- {p}" for p in problems]]
    (DAYS / "TRACEABILITY.md").write_text("\n".join(lines) + "\n", encoding="utf-8")
    print(f"traceability: {closed}/{total} closed, {len(problems)} problem(s)")


if __name__ == "__main__":                      # run as a script, not on import
    main()
```

## 5 · 💥 Failure lab — the key that almost went public

> 🎬 **The scene:** you're moving fast, `.gitignore` slipped your mind, and you run
> `git add -A` with `.env` sitting in the root.
> 😬 **The naive fix:** notice it after committing, delete `.env`, commit again. Clean, right?
> 💥 **Why it fails:** git is the photocopier from §3 — an append-only archive. The key is
> still in the previous commit, retrievable by anyone with `git log -p` on a clone of your
> (Phase 14: public!) repo. Deleting the file *forward* does nothing *backward*.
> 💡 **The insight:** prevention must be structural (`.gitignore` before the secret exists,
> verified with `git check-ignore`), and the only real cure is **revocation** — treat the key
> as burned the moment it touches history.

**Drill it now** (in a scratch clone, or carefully in-place): comment out the `.env` line in
`.gitignore`, run `git status`, and watch `.env` appear as addable — the entire disaster is
one config line away. Restore `.gitignore`, then rehearse rotation once for real: AI Studio →
delete key → create key → paste into `.env` → confirm nothing else needed changing. That
30-second muscle memory *is* the incident response plan.

## 6 · 🎤 Interview corner

1. **"What makes a system agentic, versus a workflow?"** — Who decides the next step at
   runtime. A workflow's steps are fixed by the programmer; an agent chooses actions (which
   tool, whether to continue) from the situation, in a think→act→observe loop. Follow with
   the trade-off: autonomy buys flexibility and costs predictability — hence budgets, gates,
   evals. (Railway vs taxi, if they want the one-liner.)
2. **"How do you handle secrets in a repo that becomes public?"** — Structure over
   discipline: ignore-first `.gitignore`, env-injected config, verification
   (`git check-ignore`), and a rehearsed revocation drill — because git history makes every
   leak permanent, the plan is revoke-and-rotate, never delete-and-hope.
3. **"Why formal traceability on a solo project?"** — Because "the repo is the memory" only
   works if completeness is *computed*, not felt. A regenerated ledger turns "I think I
   covered MCP auth" into "MCP-13 closed on day 37, says the script" — and it matches this
   project's own origin story: the plan file was lost once, and the system survived because
   state lived in more places than one.
