## 3 · 📚 Concepts

### ADK-16 — Plugins: infrastructure, not behavior

**The story.** Day 13's compliance officer sits at *one* desk. Today the company installs
**building systems**: CCTV in every corridor, a power meter on the main line, sprinklers
on every floor. Nobody asks each desk to opt in — you're in the building, you're covered.
New desks (Phase 8's agents) are covered the day they're built, automatically.

| Building | Our system | Technical name |
| --- | --- | --- |
| One desk's compliance officer | per-agent checkpoint | agent callbacks (Day 13) |
| Building-wide CCTV & the power meter | cross-cutting watcher on ALL agents | a **plugin** on the runner |
| The front door & the exit | whole-request brackets | `before_run_callback` / `after_run_callback` |
| Every parcel through the mailroom | every event pre-delivery | `on_event_callback` |
| The fire alarm | error hooks | `on_model_error_callback`, `on_tool_error_callback` |

Mechanics, in three sentences. A plugin is a **class** extending `BasePlugin` — a name
plus any of the twelve hooks you choose to override (unused doors cost nothing). It
registers on the **runner** — `InMemoryRunner(agent=..., plugins=[MyPlugin()])` — which is
exactly why it covers everything: agents belong to the run tree, and the runner sees it
all. Hooks share Day 13's return-rule — `None` waves through, a value overrides — so
everything you learned yesterday (including the failure mode!) transfers unchanged.

**What plugins have that agent callbacks don't:** the run-level doors. `after_run_callback`
is where "what did this request *cost*?" becomes answerable — count in the model door,
report in the run door. That's today's build, and it is precisely the skeleton Day 70's
Quota-Router fills in (route to whichever provider has headroom — you need the meter
before the router). `on_event_callback` and the error hooks feed Days 21–22's
logging/error story.

💡 **Mental model: callbacks are what an agent *does*; plugins are what the *system*
does.** Behavior belongs to the desk. Infrastructure belongs to the building. Ordering
follows the metaphor: you pass the building's CCTV before your desk's officer — plugin
hooks fire first (verified, quoted above).

**The decision test** — three questions for any cross-cutting idea:

1. Would I want this on an agent I haven't written yet? → plugin.
2. Does it need whole-run visibility (cost, tracing, digest)? → plugin.
3. Is it about *this* agent's specific policy or persona? → agent callback.

**Step 1 — `sutra/plugins.py` (zero quota).**

```python
"""Day 14 — the QuotaWatcherPlugin: Sutra's building-wide power meter.

One class, three doors: count every model call, count every tool call,
print the bill when the run ends. Registered on the RUNNER, so every
agent - present and future - is covered without being touched.

Importable with no side effects. Run demos from the repo root:

    python -m sutra.plugins counted   # triage + the per-run quota bill
    python -m sutra.plugins layered   # plugin + Day 13 callbacks, order observed
"""
from __future__ import annotations

import sys
from collections import Counter

from google.adk.plugins.base_plugin import BasePlugin    # verified import (2026-08-18)
from google.adk.runners import InMemoryRunner
from google.genai import types

from sutra.config import load_env
from sutra.adk_tools import triage_agent                 # Day 10's agent - UNTOUCHED
from sutra.callbacks import guarded_agent                # Day 13's agent - UNTOUCHED
from sutra.loop import TRIAGE_QUESTION


class QuotaWatcherPlugin(BasePlugin):
    """Counts model + tool calls per run; prints the bill at the exit door.

    The seed of Day 70's Quota-Router: before routing on headroom you must
    METER usage - this is the meter.

    Usage:
        >>> runner = InMemoryRunner(agent=any_agent,
        ...                         plugins=[QuotaWatcherPlugin()])
        # ... run as usual; a RUN REPORT prints after the final answer.
    """

    def __init__(self) -> None:
        super().__init__(name="quota_watcher")       # every plugin needs a name
        self.counts: Counter[str] = Counter()        # our tiny meter

    # TODO(confirm hook signatures in the 2.6 API reference - written here
    # async, keyword names matching Day 13's contract)

    async def before_model_callback(self, *, callback_context, llm_request):
        """Door: every model call, any agent. Count it; never interfere."""
        self.counts["model_calls"] += 1              # tick the meter
        self.counts[f"model:{callback_context.agent_name}"] += 1  # per-agent tick
        print(f"P-AUDIT model call #{self.counts['model_calls']} "
              f"(agent={callback_context.agent_name})")
        # no return -> None -> proceed (Day 13's one rule, unchanged)

    async def before_tool_callback(self, *, tool, args, tool_context):
        """Door: every tool call, any agent. Count it; never interfere."""
        self.counts["tool_calls"] += 1
        print(f"P-AUDIT tool call: {tool.name}")
        # no return -> proceed

    async def after_run_callback(self, *, invocation_context):
        """The exit door: the whole request is over - print the bill."""
        print("\n--- RUN REPORT (quota_watcher) ---")
        for key, n in sorted(self.counts.items()):   # model_calls, tool_calls, per-agent
            print(f"  {key}: {n}")
        print("(5 RPM lane: every line above was real spend)")
        self.counts.clear()                          # fresh meter for the next run


def run_with_plugin(agent, question: str) -> str:
    """Day 10's harness + one line: plugins=[...] on the runner."""
    runner = InMemoryRunner(agent=agent,
                            plugins=[QuotaWatcherPlugin()])   # <- the whole install
    session = runner.session_service.create_session_sync(
        app_name=runner.app_name, user_id="day14"
    )
    final = ""
    for event in runner.run(user_id="day14", session_id=session.id,
                            new_message=types.Content(
                                role="user",
                                parts=[types.Part(text=question)])):
        if event.is_final_response() and event.content:
            final = "".join(p.text or "" for p in event.content.parts)
    return final.strip()


def demo_counted() -> None:
    """Plain Day 10 agent + plugin: coverage without modification.

    Usage: python -m sutra.plugins counted   (~3 model calls)
    """
    print("\nANSWER:", run_with_plugin(triage_agent, TRIAGE_QUESTION))


def demo_layered() -> None:
    """Day 13's guarded agent + plugin: watch the firing ORDER.

    Usage: python -m sutra.plugins layered   (~2 model calls)
    """
    print("\nANSWER:", run_with_plugin(
        guarded_agent, "Look up ticket 4521 and summarize it in one line."))


def main() -> None:
    demos = {"counted": demo_counted, "layered": demo_layered}
    name = sys.argv[1] if len(sys.argv) > 1 else "counted"
    if name not in demos:
        print(f"usage: python -m sutra.plugins [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the sprinkler that soaks every floor

> 🎬 **The scene:** Day 13's password-search veto worked so well that you promote it:
> into the plugin it goes, as a `before_tool_callback` that blocks *any* `search_kb` call
> containing a suspicious term. Global policy, enforced everywhere. Feels responsible.
> Then you add — hypothetically, or really, if you build it — a little FAQ agent whose
> *legitimate job* is answering "how do I reset my password?" from the KB.
> 😬 **The naive fix:** "it's a security rule — stricter is safer, and global is
> stricter."
> 💥 **Why it fails:** the FAQ agent's core query is now vetoed **by infrastructure it
> cannot see, from a file nobody thinks about while debugging an agent.** You'll stare at
> the FAQ agent's instruction, its tools, its docstrings — all perfect — while the block
> comes from the building, not the desk. A desk-level rule (triage agents shouldn't chase
> credentials) was promoted to a building-level law (nobody may mention passwords), and
> the two are *not the same policy*. Global hooks have global blast radius: one wrong
> line degrades agents you haven't written yet.
> 💡 **The insight:** **put the mechanism where the policy's scope is.** Agent-specific
> rules stay in agent callbacks (Day 13 had it right); plugins carry only genuinely
> universal concerns — metering, tracing, honest-error surfacing — and any global *veto*
> must be something true for every agent, forever ("no tool may read `.env`" qualifies;
> "no password queries" does not). When a plugin does veto, label the refusal with the
> plugin's name so the block is findable from the transcript.

Run it: add the veto to the plugin, run `counted` with a password-flavored triage question
— watch even the guarded flow double-block and the plain agent lose a capability it
legitimately had — then delete the veto. ~1–2 model calls.

## 6 · 🎤 Interview corner

1. **"Same hook exists as an agent callback and a plugin — how do you choose?"** — By the
   scope of the *policy*, not the convenience of the wiring. My test: would I want this on
   an agent that doesn't exist yet? Does it need whole-run visibility? Then plugin
   (metering, tracing, error surfacing). Is it this agent's persona or policy? Callback.
   I've felt the failure of getting it wrong: a per-agent security rule promoted to a
   global plugin vetoed a different agent's legitimate queries — invisible from that
   agent's own code.
2. **"How would you measure what a multi-agent request actually costs?"** — Not inside any
   agent — no single agent sees the whole run. I hang a plugin on the runner: count in
   `before_model_callback` (keyed per agent), report in `after_run_callback`. Zero agent
   modifications, covers future agents automatically, and it's the substrate for routing:
   my quota-router later reads exactly this meter to pick the provider with headroom.
3. **"What ordering guarantees matter between global and local hooks?"** — In ADK, plugin
   callbacks run before agent callbacks — infrastructure sees traffic first, and a plugin
   override can make the agent-level hook moot. I verified the order empirically (two
   audit layers, watch which prints first) because ordering bugs between layers are the
   kind you want to *observe* once before you trust them.
