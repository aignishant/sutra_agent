## 1 · 🎬 Where we are — the story so far

Every tool Sutra owns was hand-made, one at a time: write a function, craft its docstring,
add it to a list. Six tools total, artisanal quality. Fine — while it's six.

Now look at what's coming. The real triage desk needs the **ticket archive API** (Phase
6), **vendor status pages** (the Researcher's evidence), maybe a partner's API with forty
endpoints. Hand-wrapping forty endpoints means writing forty docstrings *about someone
else's API* and keeping them true as that API drifts. That's not craft anymore; that's
transcription — boring, error-prone, and *already done by someone*: the API's own
**OpenAPI spec** (the machine-readable manual most HTTP services publish — paths,
parameters, types, descriptions; the file behind every Swagger page).

One more itch. `Agent(tools=[...])` takes a frozen list at construction. But Day 11 built
tools that only make sense in some sessions, and Phase 5's MCP servers will offer tools
that change over time. A *list* can't do that. A **toolset** can.

## 3 · 📚 Concepts

### ADK-17a — Toolsets: the crate with a manifest

**The story.** Until today, hiring a tool meant walking one person to their desk
(`tools=[fn, fn, fn]`). A **toolset** is a *staffing agency*: the agent holds one
contract, and asks the agency — every time it needs to know — "who's available **today**?"
That question has a name: **`get_tools()`**.

```python
Agent(tools=[lookup_ticket, TicketToolset()])   # functions and crates mix freely
```

Why a dynamic answer matters (three real cases, two of them already yours):

1. **Conditional inventory** — Day 11's `recall_last_triage` is only *meaningful* once
   something was recorded; a crate can withhold it until then.
2. **Feature-flagging** — one env var removes a risky tool from every agent using the
   crate (no code edits — ops does it).
3. **Remote inventories** — Phase 5's MCP servers *are* toolsets whose contents live on
   another machine and change without redeploying you. Today's `get_tools()` is the same
   handshake, in miniature.

💡 **Mental model: a tool list is a photograph; a toolset is a phone call.** The list
shows who worked here when the agent was built. The call asks who's on shift right now.

### ADK-17b — OpenAPIToolset: the crate a machine packs

Feed the spec in; tools fall out:

| The spec says | The toolset generates | Day-10 equivalent |
| --- | --- | --- |
| `paths: /status: get:` | one `RestApiTool` | your hand-written function |
| `operationId: getVendorStatus` | tool name `get_vendor_status` | the function's name |
| `summary: Current platform status…` | the tool's description | your docstring's first line |
| `parameters:` types/required | the argument schema | your type hints |
| the server URL | the actual `httpx` call | your function body |

Read the last column again: **it's Day 4's translation table, run by a machine.** You've
personally done every row by hand — which is exactly why you can trust (and audit) the
robot doing it at scale. Auth for real APIs rides in once, globally
(`auth_scheme=`/`auth_credential=`) — keys from `.env`, as ever.

**🅿️ The wrappers (map-level, deliberately unbuilt).** `LangchainTool` and `CrewaiTool`
adapt tools written for those frameworks into ADK tools. Worth knowing they exist —
ecosystems interoperate at the tool boundary — but we install neither: every dependency is
an audit surface (Phase 4 makes that formal), and nothing in Sutra needs them. Knowing
*why not* is the skill.

### 📌 Where trust moves (hold this for Day 40)

Hand-written tools: you vouch for every line. Generated tools: you vouch for **the spec
and the endpoint** — the code is mechanical. So review shifts from "is my wrapper right?"
to "do I trust this API's manual, and this server?" Sit with that: when MCP arrives
(Phase 5), *entire toolsets come from strangers*, and that question — filtered through
allowlists (`tool_filter`, Day 40) — becomes a security discipline. Today plants the
instinct.

**Step 1 — `sutra/toolsets.py` (zero quota).**

```python
"""Day 15 — toolsets: the hand-packed crate and the machine-packed crate.

Three pieces:
  1. A stdlib stub HTTP server playing "AcmeCloud", a fictional vendor
     with a status API (Sutra's Researcher will live on such pages).
  2. VENDOR_SPEC - AcmeCloud's OpenAPI manual - and the OpenAPIToolset
     that turns it into working tools, zero wrapper code.
  3. TicketToolset(BaseToolset) - our own crate with a dynamic manifest.

Run from the repo root (two windows):

    python -m sutra.toolsets serve     # window 1: the vendor comes online
    python -m sutra.toolsets vendor    # window 2: agent -> generated tool
    python -m sutra.toolsets crate     # window 2: dynamic get_tools()
    python -m sutra.toolsets names     # window 2: print generated tool names (0 quota)
"""
from __future__ import annotations

import json
import os
import sys
from http.server import BaseHTTPRequestHandler, HTTPServer

from google.adk.agents import Agent
from google.adk.runners import InMemoryRunner
from google.adk.tools.openapi_tool.openapi_spec_parser.openapi_toolset import (
    OpenAPIToolset,                                  # verified import (2026-08-18)
)
from google.genai import types

from sutra.config import load_env
from sutra.adk_tools import (                        # Day 10/11 tools, reused untouched
    lookup_ticket, search_kb, record_triage, recall_last_triage,
)

PORT = 8765                                          # local, free, ours

# --- 1. The fictional vendor ------------------------------------------------
INCIDENT = {                                         # today's synthetic "outage"
    "status": "degraded",
    "incident": "Elevated error rates on the EU auth cluster since 09:10 UTC.",
}


class _AcmeHandler(BaseHTTPRequestHandler):
    """Three-route stub: /status is the one the agent will discover."""

    def do_GET(self) -> None:                        # every GET lands here
        if self.path == "/status":                   # the route our spec describes
            body = json.dumps(INCIDENT).encode()
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(body)                   # the JSON the tool will fetch
        else:                                        # anything else: honest 404
            self.send_error(404)

    def log_message(self, fmt: str, *args) -> None:  # tidy one-line access log
        print(f"[acme] {self.address_string()} {fmt % args}")


def serve() -> None:
    """Run AcmeCloud on localhost:8765 until Ctrl+C. Zero model calls."""
    print(f"AcmeCloud status API on http://localhost:{PORT}/status (Ctrl+C stops)")
    HTTPServer(("localhost", PORT), _AcmeHandler).serve_forever()


# --- 2. The vendor's manual, and the machine-packed crate -------------------
VENDOR_SPEC = {                                      # a minimal-but-honest OpenAPI 3 spec
    "openapi": "3.0.0",
    "info": {"title": "AcmeCloud Status API", "version": "1.0.0"},
    "servers": [{"url": f"http://localhost:{PORT}"}],  # where httpx will really call
    "paths": {
        "/status": {
            "get": {
                "operationId": "getVendorStatus",    # -> tool name get_vendor_status
                "summary": ("Current AcmeCloud platform status and any "
                            "active incident. Use when a ticket may be "
                            "caused by a vendor-side outage."),
                "responses": {"200": {"description": "Status object."}},
            }
        }
    },
}

vendor_toolset = OpenAPIToolset(                     # the machine packs the crate:
    spec_str=json.dumps(VENDOR_SPEC),                # manual in...
    spec_str_type="json",                            # ...tools out. No wrapper code.
)


# --- 3. Our own crate with a dynamic manifest -------------------------------
try:                                                 # TODO(confirm BaseToolset import
    from google.adk.tools.base_toolset import BaseToolset  # path in 2.6 API reference)
except ImportError:                                  # fallback some versions use
    from google.adk.tools import BaseToolset         # type: ignore[no-redef]


class TicketToolset(BaseToolset):
    """Sutra's ticket tools as a crate that answers 'who's on shift?'.

    Inventory rules (tiny on purpose - the DYNAMISM is the lesson):
      - lookup_ticket + search_kb: always available.
      - record/recall (the Day 11 state pair): only when SUTRA_MEMORY_TOOLS=1.

    Usage:
        >>> agent = Agent(..., tools=[TicketToolset()])
        # flip $env:SUTRA_MEMORY_TOOLS between runs; NO code changes.
    """

    async def get_tools(self, context=None):         # ADK calls this per-need
        tools = [lookup_ticket, search_kb]           # the permanent staff
        if os.getenv("SUTRA_MEMORY_TOOLS") == "1":   # the on-call pair
            tools += [record_triage, recall_last_triage]
        return tools                                 # today's manifest

    async def close(self) -> None:                   # lifecycle hook; nothing to release
        pass


# --- Agents & demos ---------------------------------------------------------
vendor_agent = Agent(
    name="sutra_vendor_check",
    model="gemini-3.5-flash",                        # pinned - ADK-73, always
    instruction="""You check whether support tickets might be caused by a
vendor-side problem. Use the status tool; report what it actually says -
never invent an incident.""",
    tools=[vendor_toolset],                          # the whole crate, one entry
)

crate_agent = Agent(
    name="sutra_crate",
    model="gemini-3.5-flash",
    instruction="""You are Sutra's triage assistant. Use the tools you
have; if asked about tools you lack, say you lack them.""",
    tools=[TicketToolset()],                         # our dynamic crate
)


def _run(agent: Agent, question: str) -> str:
    """The Day 10 harness, shared by both demos."""
    runner = InMemoryRunner(agent=agent)
    session = runner.session_service.create_session_sync(
        app_name=runner.app_name, user_id="day15"
    )
    final = ""
    for event in runner.run(user_id="day15", session_id=session.id,
                            new_message=types.Content(
                                role="user",
                                parts=[types.Part(text=question)])):
        for part in (event.content.parts if event.content else []):
            if part.function_call:
                print(f"CALL: {part.function_call.name}({part.function_call.args})")
        if event.is_final_response() and event.content:
            final = "".join(p.text or "" for p in event.content.parts)
    return final.strip()


def demo_names() -> None:
    """Print the machine-generated tool names. 0 model calls."""
    import asyncio
    tools = asyncio.run(vendor_toolset.get_tools())  # ask the crate for its manifest
    for t in tools:
        print(f"generated tool: {t.name} - {t.description[:60]}...")


def demo_vendor() -> None:
    """Usage: python -m sutra.toolsets vendor  (~2 calls; serve must be running)."""
    print("\nANSWER:", _run(vendor_agent,
        "Ticket 4521 is about auth problems. Is AcmeCloud currently healthy, "
        "or could this be on their side?"))


def demo_crate() -> None:
    """Usage: python -m sutra.toolsets crate   (~2 calls). Flip the flag between runs."""
    flag = os.getenv("SUTRA_MEMORY_TOOLS", "0")
    print(f"SUTRA_MEMORY_TOOLS={flag}")
    print("\nANSWER:", _run(crate_agent,
        "What was the last triage you recorded in this session?"))


def main() -> None:
    demos = {"serve": serve, "names": demo_names,
             "vendor": demo_vendor, "crate": demo_crate}
    name = sys.argv[1] if len(sys.argv) > 1 else "names"
    if name not in demos:
        print(f"usage: python -m sutra.toolsets [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the manual from the wrong machine

> 🎬 **The scene:** you inherit a "real-world" spec — meaning: exported by a tired
> backend, `operationId`s like `op_7f3a` or missing entirely, summaries blank. Simulate
> it: delete `operationId` and `summary` from `VENDOR_SPEC`, rebuild, run
> `python -m sutra.toolsets names`.
> 😬 **The naive fix:** "whatever — the tool still *works*; names are cosmetic."
> 💥 **Why it fails:** the manifest now reads like `get_status_http_get - ...` with an
> empty description (names get machine-generated from method+path when `operationId` is
> missing). Run the vendor demo a few times: the model — which chooses tools by **name
> and description alone** (Day 10's law) — hesitates, or answers without checking the
> vendor at all. Nothing errored. The tool is perfectly functional and practically
> invisible. You've reproduced Day 10's ruined-docstring lab *without touching a line of
> Python* — the rot came in through data.
> 💡 **The insight:** **generated tools inherit the spec's writing quality — garbage
> manual in, invisible tools out.** An OpenAPI spec you consume is prompt engineering
> someone else wrote. So audit specs like docstrings: does every operation have an honest
> `operationId` and a when-to-use summary? If not, fix the spec (yours) or wrap/rename
> (theirs) before handing the crate to a model. Restore the real spec; watch the tool
> become visible again.

## 6 · 🎤 Interview corner

1. **"You need an agent to use a 40-endpoint internal API. Hand-write 40 tools?"** — No —
   generate them from the OpenAPI spec (ADK's `OpenAPIToolset`: one `RestApiTool` per
   operation, names from `operationId`, schemas from parameters, auth injected once).
   But I'd audit the spec first like I audit docstrings, because the model picks tools by
   the spec's names and descriptions — I've demonstrated that a spec with junk
   `operationId`s produces working-but-unusable tools. Hand-write only the endpoints
   whose semantics the spec can't express.
2. **"Why do frameworks have a 'toolset' abstraction instead of just lists of tools?"** —
   Because real inventories are dynamic: conditional on state, feature flags, or a remote
   server's offering. A toolset answers `get_tools()` at need — I built a crate that adds
   memory tools only when a flag is set, with zero agent changes — and it's the exact
   shape of MCP: a remote toolset whose contents you don't control. The list is a
   photograph; the toolset is a phone call.
3. **"What changes, risk-wise, when tools are generated rather than written?"** — Trust
   moves from code to source-of-truth: I no longer vouch for wrapper lines, I vouch for a
   spec and an endpoint. That demands new controls — spec review, drift detection (the
   spec and the live server *will* diverge), and allowlist filtering so I only expose the
   operations I've reasoned about. The last one becomes non-negotiable with MCP, where
   whole toolsets come from third parties.
