## 3 · 📚 Concepts

### SK-01 — What a skill is (and why it isn't just a prompt)

**The new-employee story.** Imagine the support desk hires a new person, Priya. She is
smart and careful — but she has never seen *your* company. On day one you do not read her
the entire company manual out loud every morning. You hand her a **binder**: "Ticket
triage — how we do it here." Steps, examples, the severity rubric, a response template.
She keeps it on her shelf. When a ticket comes in, she opens the binder, follows it, and
puts it back.

Now map the story:

| Office world | Agent world | Technical name |
| --- | --- | --- |
| Priya, smart but new | the model — capable, but knows nothing about *your* procedures | the LLM |
| Reading the whole manual aloud every morning | stuffing every procedure into the system prompt | instruction bloat (Day 19's kitchen sink) |
| The binder on the shelf | a folder of written know-how the agent opens when needed | an **Agent Skill** |
| The binder's spine label ("Ticket triage — how we do it") | one line the agent always sees, so it knows the binder exists | the skill's `name` + `description` (L1) |
| Opening the binder when a ticket arrives | loading the full instructions on demand | skill activation (L2) |
| The appendix pages she only checks for edge cases | extra files loaded only when needed | `references/`, `assets/`, `scripts/` (L3) |

💡 **Mental model: a skill is procedural knowledge with a shelf label. The prompt says
who the agent *is*; a skill says how a job *is done here* — and it stays on the shelf
until the job shows up.**

Three facts make this bigger than a formatting trick:

1. **It is an open spec** — agentskills.io. The same skill folder works in ADK, and in
   many other agent products (the ecosystem count is "40+" in Google's own developer
   blog). Write once, carry your know-how between frameworks. That portability is why
   the plan gives skills a whole curriculum (SK-01..20), not a footnote.
2. **It is text in your repo.** Skills are versioned, diffed, reviewed, and tested like
   code — which is exactly Principle 2 ("the repo is the memory") applied to know-how.
3. **It is also an attack surface.** A skill is instructions your agent will follow.
   Day 29 treats third-party skills like unaudited contractors, and Day 66 will show the
   injection attacks that make that caution non-negotiable. Plant that flag today.

### SK-02 — `SKILL.md` anatomy: the two-part file

Every skill is a directory with, at minimum, one file: **`SKILL.md`**. That file has two
parts, and each part talks to a different reader — the same trick you saw in Day 4's tool
declarations:

```
---                       ← part 1: YAML frontmatter — read by MACHINES (loaders, linters)
name: ticket-triage
description: ...
---
# How to triage a ticket  ← part 2: Markdown body — read by the MODEL when activated
Step 1: ...
```

**The frontmatter fields** (spec table, verified 2026-08-18):

| Field | Required? | The rules | Why the rule exists |
| --- | --- | --- | --- |
| `name` | ✅ yes | 1–64 chars; only `a-z`, `0-9`, `-`; no leading/trailing/consecutive hyphens; **must match the folder name** | it's an identifier — loaders key on it, so it must be filesystem-safe and unambiguous |
| `description` | ✅ yes | 1–1024 chars, non-empty; say **what it does AND when to use it** | this is the *shelf label* — the only thing the agent sees before deciding to open the binder |
| `license` | ⬜ no | short: a licence name or a pointer to a bundled file | third-party sourcing (Day 29) needs this answerable |
| `compatibility` | ⬜ no | 1–500 chars; only if the skill has real environment needs | most skills should omit it; ours will |
| `metadata` | ⬜ no | a map of string → string; put custom keys here (e.g. `version: "1.0"`) | the spec's escape hatch — extra data without polluting the spec |
| `allowed-tools` | ⬜ no | space-separated tool names, pre-approved for the skill; **experimental** | least-privilege for skills (Day 68's theme, arriving early) |

Read the `name` rules again — they should feel familiar. `PDF-Processing` is invalid
(uppercase), `-pdf` is invalid (leading hyphen), `pdf--processing` is invalid (double
hyphen). This is the same "the contract is a form, not a pinky promise" lesson from
Day 4: tight rules mean a *linter* can check them, and on Day 31 ours will.

**The `description` is prompt engineering, not paperwork.** The spec's own example of a
bad one is `Helps with PDFs.` Compare:

> ✅ "Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs.
> Use when working with PDF documents or when the user mentions PDFs, forms, or document
> extraction."

The good one names *capabilities* and *trigger words*. Remember Day 4's tool
`description` field — "this sentence is prompt engineering, not paperwork"? The skill
description is the same organ in a bigger animal: it is the **only** text the model has
when deciding whether this skill is relevant. A vague label means a binder that is never
opened. (You will watch that failure happen live on Day 26.)

**The body** has no format rules at all — it is Markdown instructions, and the spec's
advice is exactly what you'd tell a human writing for Priya: step-by-step instructions,
examples of inputs and outputs, common edge cases. One hard number to remember: the spec
recommends keeping the whole `SKILL.md` **under 500 lines**, because the entire body
loads at once when the skill activates.

### SK-03 — The folder, and the three-rung ladder

A skill directory can hold more than the one required file:

```
skill-name/
├── SKILL.md          # REQUIRED — metadata + instructions
├── scripts/          # optional — executable code the agent can run
├── references/       # optional — extra docs, loaded on demand
├── assets/           # optional — templates, images, data files
└── ...               # anything else the skill needs
```

Why three optional folders instead of one big file? Because of the idea that makes
skills *cheap*: **progressive disclosure**. The spec defines a three-rung ladder — climb
only as high as the task requires:

| Rung | What loads | When | Cost (spec's own numbers) |
| --- | --- | --- | --- |
| **L1 — Metadata** | `name` + `description` only | at startup, for **all** skills | ~100 tokens each |
| **L2 — Instructions** | the full `SKILL.md` body | only when the skill is **activated** | keep it < 5000 tokens |
| **L3 — Resources** | files in `scripts/` `references/` `assets/` | only when actually needed | per file, on demand |

Run the numbers with Day 24's accountant eyes. Ten skills, always available: the
always-resident cost is ten shelf labels — about **1,000 tokens**. The kitchen-sink
alternative (all ten procedures pasted into the system prompt at, say, 3,000 tokens
each) is **30,000 tokens on every call**, relevant or not, billed against a 5 RPM free
tier. The ladder is not tidiness. On our budget it is the difference between fitting in
the window and not.

💡 **Mental model: L1 is the spine of the binder, L2 is the binder opened, L3 is the
appendix. You pay for what you open, not for what you own.**

Two mechanical rules complete the picture (both will be lint checks later):

- **File references are relative paths from the skill root**, e.g.
  `See references/severity-rubric.md`. Keep them **one level deep** from `SKILL.md` —
  a reference that points to a reference that points to a reference is a maze no agent
  (or human) follows reliably.
- **Split before you bloat.** If the body approaches the 500-line ceiling, move detail
  into `references/` and leave a pointer. Smaller files = less context per load — the
  Day 20 compaction lesson, applied at authoring time instead of rescue time.

## 5 · 💥 Failure lab — three broken binders

> 🎬 **The scene:** you are about to write real skills (Day 27) and later *install other
> people's* (Day 29). You need a feel for how skills go wrong — before an agent, a
> loader, or a stranger's repo shows you the hard way.
> 😬 **The naive fix:** "it's just Markdown, what could go wrong?"
> 💥 **Why it fails:** three separate ways, each failing at a *different layer* — try
> each mutation on `skills/hello-desk/SKILL.md` and reason it through:
>
> 1. **`name: Hello-Desk`** (capitals). Fails at the *loader/linter* layer: the identity
>    contract is broken, and a strict loader may refuse the folder outright. The skill
>    never even reaches the shelf.
> 2. **`description: Helps with greetings.`** (the spec's own "poor example" shape).
>    Fails at the *model* layer — and this one is **silent**. Everything parses;
>    the skill loads; but the shelf label is so vague the model never connects it to a
>    real task. A skill that never activates is indistinguishable from no skill, except
>    you still pay its ~100 L1 tokens on every call. Worst failure mode: invisible +
>    costs money.
> 3. **Body says `see references/rubric.md`, file doesn't exist.** Fails at the *runtime*
>    layer, and only *sometimes*: the day the model actually climbs to L3 and asks for
>    that file, it gets an error mid-task. A landmine that sleeps until stepped on.
>
> 💡 **The insight:** **the three layers fail at three different times — load time,
> decision time, use time — so only the first is caught free.** A linter catches #1
> and #3 mechanically (Day 31 does exactly that). #2 can only be caught by *design
> review and observation* — which is why description-writing is a skill-design topic
> (Day 28), not a syntax topic.

Restore the valid version before committing (step 5's verify checks this).

## 6 · 🎤 Interview corner

1. **"What are Agent Skills, and how do they differ from just writing a better system
   prompt?"** — A skill is procedural knowledge packaged in an open spec: a folder with
   a `SKILL.md` (YAML frontmatter + Markdown instructions) plus optional scripts,
   references, and assets. The difference from a prompt is *loading economics and
   portability*: only the name+description (~100 tokens) are resident; the instructions
   load on activation, resources on demand. So know-how scales without inflating every
   call — and the same folder works across the 40+ products that speak the
   agentskills.io spec, not just one framework. I'd add the ops angle: skills are files
   in the repo, so procedures get code review, diffs, and tests like everything else.
2. **"Walk me through what's in a SKILL.md."** — Two parts for two readers. Frontmatter
   for machines: required `name` (≤64 chars, lowercase kebab-case, must equal the folder
   name) and `description` (≤1024 chars — what it does *and* when to use it); optional
   `license`, `compatibility`, `metadata`, and experimental `allowed-tools`. Body for
   the model: free-form Markdown instructions, recommended under 500 lines, with
   relative one-level-deep pointers into `references/` and friends. The description is
   the load-bearing field — it's the only thing the model sees pre-activation, so it's
   prompt engineering with a character budget.
3. **"Why does progressive disclosure matter in production?"** — Context is a metered
   resource — on my project literally, since Sutra runs on free tiers where every token
   rides a 5 RPM window. L1/L2/L3 turns skill cost from O(everything, every call) into
   O(index, every call) + O(what you use). Ten skills cost ~1k resident tokens instead
   of ~30k. And the same ladder is a safety boundary: on the sourcing side we audit L3
   scripts before they can ever run — a skill is instructions plus possibly code, so
   it's supply chain, not just documentation.
