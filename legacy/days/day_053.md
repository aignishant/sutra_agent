## 3 · 📚 Concepts

### ADK-32 — The Workflow Runtime: the factory floor

**The factory story.** Yesterday's Sutra is a brilliant craftsman alone in a workshop: one
person who takes the order, finds the parts, builds the thing, and inspects it. Craftsmen
scale badly. A factory scales — not because any worker is smarter, but because the
**conveyor belt** is: each station does one job, and the belt itself decides what goes
where next. No worker needs to know the whole floor plan.

| Factory | Our system | Technical name |
| --- | --- | --- |
| The floor plan | your `Workflow(...)` object | the **graph** |
| One station | one unit of work | a **node** |
| The belt between stations | "after A, run B" | an **edge** |
| The item riding the belt | data passed along | `Event.output` → `node_input` |
| The factory whistle | where work enters | the `"START"` marker |

💡 **Mental model: agents think, the graph decides.** In 1.x, agents were the whole
universe and composition happened *inside* agents (`sub_agents` trees). In 2.x the graph is
the composition layer, and an agent is *one kind of station* — a very smart one — standing
on a floor it does not control.

**Trap #1, named and framed** (master plan §5.1). The old world composed everything through
special agent classes: `SequentialAgent`, `ParallelAgent`, `LoopAgent`, wired via
`sub_agents`. The 2.x docs retire that world in one sentence, which you should read twice
(adk.dev/agents/workflow-agents/, checked 2026-08-19):

> "Starting in ADK 2.0 for Python and Go, template workflows have been superseded by more
> flexible workflow structures, including graph-based workflows and dynamic workflows."

*Superseded*, not deleted — you will still meet the template classes in old code and old
blog posts. The trap is not that they crash; the trap is building new compositions in the
old idiom and fighting the runtime forever after. **Every tutorial that starts with
`SequentialAgent(sub_agents=[...])` is teaching you 1.x** — check the date, close the tab.

| | 1.x habit (the mirage) | 2.x reality (today) |
| --- | --- | --- |
| Composition layer | agent trees (`sub_agents=`) | the graph (`Workflow(edges=...)`) |
| Sequence | `SequentialAgent` wrapper class | an edge tuple `("START", a, b, c)` |
| A deterministic step | fake it with an agent + prompt | a plain Python function node — free, exact, no quota |
| Who routes | the parent agent's LLM decides | edges decide (LLM only routes where YOU put a router) |
| Unit of reuse | an agent subtree | a node — including a whole nested `Workflow` |

### ADK-33 — Nodes: the three species of station

A node is *anything that can take an input and yield events*. Three species matter today
(adk.dev/graphs/, 2026-08-19):

1. **Agent nodes** — an ordinary `Agent(...)` instance dropped straight into the graph.
   The runtime runs it, collects its final structured output, and puts that on the belt.
   Use when the step needs judgment. Costs quota.
2. **Function nodes** — a plain Python function. The runtime wraps it automatically (the
   docs also show an explicit `FunctionNode` wrapper for when you need knobs). Use when
   the step is deterministic: formatting, lookups, filing, math. Costs nothing.
3. **Nested workflows** — a whole `Workflow` used as a single node inside a bigger one.
   A factory can contain a smaller factory. (We use this on Day 57 — the Writer↔Critic
   pair becomes one sealed box.)

*A concrete example of choosing the species:* "extract the ticket id from the request" is a
regex — function node, free. "Decide whether this ticket is billing or auth" is judgment —
agent node, quota. Day 3 taught you the loop; Day 53's version of that lesson is: **never
pay a model to do an `if`.**

### ADK-34 — Edges: the belt, and what rides on it

Edges are declared in one place — the `edges=` list of the `Workflow` — as tuples read
left to right. The magic string `"START"` marks where the whistle blows:

```python
Workflow(name="...", edges=[("START", step_one, step_two, step_three)])
```

That single tuple means: *start → step_one → step_two → step_three → done*. (Tomorrow adds
branching dicts, fan-out, and back-edges — today is the straight belt.)

**What rides the belt.** Each node hands data forward by yielding an `Event`. The workflow
flavor of `Event` has four fields you must keep straight (adk.dev/graphs/data-handling/):

| Field | Who sees it | What it is for |
| --- | --- | --- |
| `output` | the NEXT node (as its `node_input`) | the item on the belt — **one per node execution**, the docs enforce it |
| `message` | the user | narration; it does NOT travel down the belt |
| `state` | every later node + the session | small shared facts (the Day 17 rules apply — small!) |
| `route` | the edges | tomorrow's business: picking a branch |

And the receiving side: a function node simply declares `def my_node(node_input: ...)`.
If the upstream node has an `output_schema` (our `TriageResult` — hello, Day 12), the
runtime deserializes into that type before calling you. The schema you learned on Day 4
as "the form the model fills" is now also **the contract between stations**.

💡 **Mental model: `output` is the parcel, `message` is the postcard, `state` is the
warehouse shelf, `route` is the signpost.** Four fields, four jobs, no overlap.

Create `sutra/graph.py` with the listing below. Read the imports as a story: the `Agent`

```python
"""Day 53 — Sutra's first graph: the Workflow Runtime, three nodes, one belt.

The graph is the 2.x composition layer (trap #1: do NOT reach for
SequentialAgent/sub_agents trees — those are the superseded 1.x idiom).
Nodes do work; edges decide order; agents are just one node species.

Importable with no side effects. Run demos from the repo root:

    python -m sutra.graph hello     # two function nodes, zero quota
    python -m sutra.graph classify  # function -> agent -> function (~1 LLM call)
"""
from __future__ import annotations

import sys

from google.adk import Event, Workflow                 # the graph citizens (NEW today)
from google.adk.agents.llm_agent import Agent          # same import as Day 5 — unchanged

from sutra.config import load_env                      # .env loader (Day 1)
from sutra.logging_setup import get_logger             # JSON-lines logging (Day 22)
from sutra.schemas import TriageResult                 # the classifier's form (Day 12)

log = get_logger(__name__)                             # library code never print()s

PRIMARY_MODEL = "gemini-3.5-flash"                     # pinned, never the floating alias
                                                       # (ADK-73; Day 5's failure lab)

# ---------------------------------------------------------------------------
# Species 2: function nodes. Plain Python — deterministic, instant, quota-free.
# The runtime wraps them for us; node_input arrives typed from upstream.
# ---------------------------------------------------------------------------

def fetch_ticket(node_input: str) -> Event:
    """Look the ticket text up so downstream nodes get BODY, not just an id.

    Args:
        node_input: the raw request, e.g. "4521" (the workflow's entry input).

    Returns:
        Event whose .output is the ticket text ready for classification.

    Example:
        >>> ev = fetch_ticket("4521")
        >>> "logged out" in ev.output
        True
    """
    from sutra.loop import TICKETS                     # Day 3's synthetic archive —
    tid = node_input.strip().lstrip("#")               # tolerate "#4521" politely
    body = TICKETS.get(tid, f"No ticket with id {tid!r}.")  # honest miss (Day 3 rule)
    log.info("graph_fetch_ticket", extra={"ticket_id": tid})
    return Event(output=f"Ticket #{tid}: {body}")      # the parcel for the next station


def file_report(node_input: TriageResult) -> Event:
    """Turn the classifier's typed verdict into a one-line routing report.

    Note the parameter type: the runtime hands us a REAL TriageResult,
    deserialized from the upstream agent's output_schema. The schema is
    the contract between stations (Day 12 pays off here).

    Args:
        node_input: the TriageResult produced by the classifier node.

    Returns:
        Event with .output = the report line (the workflow's final answer)
        and .message = narration for the user.

    Example:
        >>> from sutra.schemas import TriageResult
        >>> r = TriageResult(category="auth", severity=3,
        ...                  needs_human=False, notes="cookie flags")
        >>> file_report(r).output
        'ROUTE: auth queue, severity 3, human: no'
    """
    line = (f"ROUTE: {node_input.category} queue, "     # closed-set category (Literal)
            f"severity {node_input.severity}, "         # 1..4, schema-checked
            f"human: {'yes' if node_input.needs_human else 'no'}")
    log.info("graph_file_report", extra={"route": node_input.category})
    return Event(output=line,                           # parcel: the belt's end product
                 message=f"Filed. {line}")              # postcard: what the user reads

# ---------------------------------------------------------------------------
# Species 1: an agent node. Same Agent class as Day 12 — the graph changes
# WHERE it stands, not WHAT it is. It reads the fetched text, fills the form.
# ---------------------------------------------------------------------------

classify_node = Agent(
    name="classify_node",                              # names show up in event.node_info
    model=PRIMARY_MODEL,                               # pinned explicitly (ADK-73)
    instruction="""You classify ONE support ticket. Read the ticket text you
are given and fill the triage form. If no category fits, use 'other' and
set needs_human true. Never invent ticket contents.""",
    output_schema=TriageResult,                        # the form = the belt contract
)

# ---------------------------------------------------------------------------
# The graphs. Edges are tuples read left to right; "START" is the whistle.
# ---------------------------------------------------------------------------

hello_graph = Workflow(
    name="hello_graph",                                # two functions, zero quota
    edges=[("START", fetch_ticket, file_report)],      # START -> fetch -> file
)   # NOTE: this graph feeds a raw str into file_report — the 'hello' demo
    # patches file_report's expectations by sending ticket 9999 (a miss),
    # proving the belt moves before any model is involved. See demo below.

triage_line_v0 = Workflow(
    name="triage_line_v0",                             # the real 3-station line
    edges=[("START", fetch_ticket, classify_node, file_report)],
)


def _drive(workflow: Workflow, request: str) -> None:
    """Run a workflow and narrate every event with the node that yielded it.

    Args:
        workflow: the graph to run.
        request: the entry input placed on the belt at START.

    Example:
        >>> _drive(triage_line_v0, "4521")     # ~1 LLM call
        [fetch_ticket] ...
        [classify_node] ...
        [file_report] ROUTE: auth queue, ...
    """
    from google.adk.runners import InMemoryRunner      # same runner as Day 8
    import asyncio
    from google.genai import types

    async def run() -> None:
        runner = InMemoryRunner(agent=workflow,        # a Workflow drops in where an
                                app_name="sutra")      #   agent used to (it IS a node)
        session = await runner.session_service.create_session(
            app_name="sutra", user_id="u1")            # Day 8's (app,user,session) key
        msg = types.Content(role="user",
                            parts=[types.Part(text=request)])
        async for event in runner.run_async(user_id="u1",
                                            session_id=session.id,
                                            new_message=msg):
            who = getattr(event, "node_info", None)    # 2.0 added node_info (Day 7);
            label = getattr(who, "name", None) or event.author or "?"
            if event.is_final_response():              # Day 7's truth table, reused
                print(f"[{label}] FINAL: {(event.output or event.message or '').strip()}")
            else:
                print(f"[{label}] ...")                # each station announces itself

    asyncio.run(run())


def main() -> None:
    """Demo dispatcher — the same shape every sutra module has had since Day 2."""
    demos = {
        "hello": lambda: _drive(hello_graph, "9999"),      # zero quota (miss path)
        "classify": lambda: _drive(triage_line_v0, "4521"),  # ~1 LLM call
    }
    name = sys.argv[1] if len(sys.argv) > 1 else "hello"
    if name not in demos:
        print(f"usage: python -m sutra.graph [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()                                         # keys from .env, never code
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — paying a model to do an `if`

> 🎬 **The scene:** flush with graph power, you rebuild the line as *agents all the way
> down*: an agent to extract the ticket id, an agent to fetch the text, an agent to
> classify, an agent to format the report. Four smart stations! The demo works. It feels
> thorough.
> 😬 **The naive fix:** ship it. More intelligence per station must mean more quality.
> 💥 **Why it fails:** three ways, all at once. **Cost:** the run went from 1 model call
> to 4 — on a 5 RPM lane your throughput just dropped 4×, and Day 24's ledger will show
> the extraction agent burning tokens to do what `.lstrip("#")` does for free. **Exactness:**
> the formatting agent will *usually* write `ROUTE: auth queue…` — and sometimes
> `Routed to the auth queue!` — and the downstream consumer you build in Phase 9 needs the
> colon. You reintroduced Day 3's pinky-promise parsing INSIDE your own pipeline.
> **Debuggability:** when the report is wrong you now must ask "which of four models
> hallucinated?" instead of reading one deterministic function.
> 💡 **The insight:** **put judgment in agent nodes, put certainty in function nodes, and
> let the graph — not a model — decide what runs.** The most senior sentence in agentic
> engineering is "this step doesn't need an LLM." (It is also, not by accident, the
> cheapest sentence.)

Observed today, not just asserted: the `classify` demo does the whole job with ONE model
call because the other two stations are Python.

## 6 · 🎤 Interview corner

1. **"What actually changed in ADK 2.0's composition model?"** — The composition layer
   moved out of agents. 1.x composed by nesting agents in `sub_agents` trees with special
   wrapper classes; 2.0's Workflow Runtime makes the graph the first-class citizen: nodes
   (agents, plain functions, nested workflows) connected by edges, with the runtime owning
   order, data hand-off, and concurrency. The template classes still exist but are
   officially superseded — I treat any `SequentialAgent` tutorial as a dated artifact. I
   ported Sutra's triage line to a three-node graph and the immediate win was surgical:
   the two deterministic stations became free, exact Python.
2. **"How does data move between nodes?"** — As typed parcels. A node yields an `Event`
   whose `output` becomes the next node's `node_input`, deserialized against the upstream
   `output_schema` — my classifier emits a Pydantic `TriageResult` and the next function
   receives a real object, not JSON-ish text. The other event fields have disjoint jobs:
   `message` narrates to the user, `state` persists small shared facts, `route` picks
   branches. Keeping those four straight is most of graph hygiene.
3. **"When is a function node the wrong choice?"** — Whenever the step needs judgment that
   survives contact with messy input: classification, summarization, drafting. My rule is
   the inverse of the common failure: never pay a model to do an `if`, and never ask an
   `if` to do a model's job. The graph makes the boundary explicit — which is half the
   reason to use one.
