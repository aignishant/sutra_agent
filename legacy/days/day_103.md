## 1 · 🎬 Where we are — the story so far

Six days, five platforms, one container. Day 100's `Dockerfile.adk` has been the workhorse:
Container Apps ran it unchanged, Day 102's Terraform pointed at the same public `ghcr.io` image,
and both times the deal was simple — you hand over a container that listens on a port, the
platform sends it HTTP.

Today that deal is off, twice over.

AWS Lambda will not take your image from `ghcr.io`; it insists on its own registry. And more
fundamentally: **Lambda does not send your container HTTP at all.** It expects your image to
implement a specific AWS protocol — to *ask* for work, in a loop, over a local API. A container
that sits there listening on port 8000 will start, look healthy, and then time out on every
single invocation, because nothing is ever going to connect to it.

This repo's own [`04_aws.md`](../deployment/04_aws.md) §4 walks straight into this. It presents
Lambda's container support as *"the natural fit for an agent packaged the same way as
[day_086.md](day_086.md)'s Dockerfile."* That's the mistake §5 reproduces on purpose.

## 3 · 📚 Concepts

### DEPLOY-07a — Two free meters, and the headline one isn't the binding one

Verified 2026-08-21 (`aws.amazon.com/lambda/pricing/`): *"The free tier includes one million
requests and 400,000 GB-seconds per month."* And per `aws.amazon.com/free/`, Always Free applies
*"on both the Free and Paid plans"* — so unlike EC2 (Day 104's problem), this grant survived the
2025 free-tier overhaul.

Now do the arithmetic before deploying, per `00_stay_free_safety.md` §2:

| Meter | Grant | At 512 MB and ~5 s per agent request | Requests/month before you exceed it |
| --- | --- | --- | --- |
| Requests | 1,000,000 | — | **1,000,000** |
| GB-seconds | 400,000 | 0.5 GB × 5 s = **2.5 GB-s per request** | **160,000** |

💡 **The binding constraint is GB-seconds, and it binds at roughly one-sixth of the headline
number.** That gap exists because an LLM agent's requests are *slow*: most of those five seconds
are spent blocked on Gemini, and Lambda bills memory × wall-clock, not memory × CPU. You are
paying for the wait.

📌 Two levers, and the second one is counter-intuitive:
- **Lower `--memory-size`** → fewer GB-s per request. 512 MB is already modest; going lower risks
  the Python process not fitting.
- **⚠️ *Raising* memory can sometimes reduce total GB-s**, because Lambda scales CPU with memory,
  so CPU-bound work finishes sooner. It does **not** help here — our five seconds are network
  wait, which more CPU cannot shorten. Worth knowing so you don't apply the usual advice to the
  one workload where it's wrong.

### DEPLOY-07b — 📌 The Runtime API: why an HTTP server doesn't work

From `docs.aws.amazon.com/lambda/latest/dg/images-create.html`, quoted:

> *"The container image must implement the Lambda runtime API… You can add a runtime interface
> client to your preferred base image to make it compatible with Lambda."*

💡 **Mental model — the direction of the arrow is reversed.** Every platform so far has been a
*push* model: traffic arrives, the platform connects to your listening socket. Lambda is a
**pull** model: your process starts and must **call out** to a local endpoint
(`$AWS_LAMBDA_RUNTIME_API`) saying "give me an event," handle it, POST the response back, and
loop. Nothing ever connects *to* you.

So `adk api_server`, which binds a socket and waits, satisfies none of that. It starts fine. It
looks healthy. It waits forever for a connection that will never come, and Lambda times out the
invocation because no response was ever POSTed back.

**The bridge: AWS Lambda Web Adapter** (`github.com/awslabs/aws-lambda-web-adapter`, release
**1.0.1**, verified 2026-08-21). It's a Lambda *extension* — a small binary that runs alongside
your process, speaks the Runtime API on your behalf, and translates each event into an ordinary
HTTP request against your local server. Your app doesn't change at all; the adapter does the
protocol work.

```
Lambda ──(Runtime API)──▶ lambda-adapter ──(plain HTTP :8000)──▶ adk api_server
       ◀──(response)─────                ◀───────────────────────
```

### DEPLOY-07c — Three more image requirements that fail in unhelpful ways

All from the same AWS page (2026-08-21):

| Requirement | Quoted | What it means for us |
| --- | --- | --- |
| Read-only filesystem | *"must be able to run on a read-only file system… a writable `/tmp` directory with between 512 MB and 10,240 MB"* | ⚠️ **`--session_service_uri=sqlite:///...` can only write under `/tmp`** — and `/tmp` is per-execution-environment and disappears. Day 98's VM trick does not port here. Same gap as Day 100 §5, now enforced by the filesystem itself |
| Single architecture | *"the image you build for your function must target only one of the architectures. Lambda does not support functions that use multi-architecture container images"* | ⚠️ modern `docker buildx` can attach provenance/attestation manifests that make an image *look* multi-arch. Step 4 passes `--provenance=false` for this reason |
| No `USER` needed | *"Lambda follows security best practices by defining a default Linux user… you don't need to specify a USER in your Dockerfile"* | Day 86's non-root discipline is handled by the platform here — one of the rare cases where doing less is correct |

📌 And the **function lifecycle**, which produces a genuinely confusing failure weeks later:
*"If a function is not invoked for multiple weeks, Lambda reclaims its optimized version… Lambda
rejects the first invocation and the function enters the Pending state."* A function you demoed
last month will fail its first call and succeed on the retry. That is documented behaviour, not a
bug — and it is worth knowing before you demo something to an interviewer.

### DEPLOY-07d — The registry you cannot swap, and what that costs

Day 100's DEPLOY-04b established the rule: **compute grants meter consumption; registries bill
for existence.** Day 100 escaped it by using a free public `ghcr.io` package. Day 102 reused that
same image. Today there is no escape:

> *"build your image locally and upload it to an Amazon Elastic Container Registry (Amazon ECR)
> repository… The Amazon ECR repository must be in the same AWS Region as the Lambda function."*

⚠️ **ECR Public's 50 GB always-free grant does not help** — that's for *public* repositories, and
Lambda pulls function images from **private** ECR. The private free tier is 500 MB/month **for
one year**, then $0.10/GB-month — and post-2025-07-15 accounts never get that year.

💡 **The honest verdict: Lambda is free; deploying to Lambda is not quite.** A few cents a month
for one image. The mitigation isn't clever, it's disciplined — **the repository exists for the
hours you're working, not the months you're not.** §7's cleanup deletes it, and the gate checks.

⚠️ **Cleanup order matters here**, and it's the reverse of what feels natural: *"If the
corresponding container image no longer exists on Amazon ECR… the function enters the Failed
state."* Delete the **function first**, then the repository.

## 4 · 🛠️ The build

> Shell: **PowerShell**, repo root. Docker Desktop running.

**Step 1 — IAM sanity, and the number you expect.**

```powershell
aws sts get-caller-identity
$ACCOUNT = aws sts get-caller-identity --query Account --output text
$REGION = "us-east-1"
```

✅ *Verify:* the ARN printed is an **IAM user or role, not `:root`**. If it says root, stop and
create an IAM user first — `04_aws.md` §2 is right about this and it is not optional. Then state
your budget from DEPLOY-07a: **~160,000 agent requests/month before GB-seconds bind.**

**Step 2 — the execution role.**

Every Lambda function runs *as* an IAM role. It must exist before the function does:

```powershell
$TRUST = '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"lambda.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
$TRUST | Out-File -Encoding ascii trust-policy.json

aws iam create-role --role-name sutra-lambda-role `
  --assume-role-policy-document file://trust-policy.json

aws iam attach-role-policy --role-name sutra-lambda-role `
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
```

| Piece | What it does |
| --- | --- |
| the trust policy | says *"the Lambda service may assume this role"* — without it, Lambda cannot run as anything and function creation fails |
| `AWSLambdaBasicExecutionRole` | AWS's own managed policy granting CloudWatch Logs write access — least-effort least-privilege, and §5 needs those logs |

✅ *Verify:* `aws iam get-role --role-name sutra-lambda-role --query Role.Arn --output text` prints
an ARN. Note it. ⚠️ IAM is eventually consistent — if Step 4 fails with a role error, wait ~10
seconds and retry before changing anything.

**Step 3 — ECR repository and login.**

```powershell
aws ecr create-repository --repository-name sutra-agent --region $REGION
$REPO = "$ACCOUNT.dkr.ecr.$REGION.amazonaws.com/sutra-agent"

aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin "$ACCOUNT.dkr.ecr.$REGION.amazonaws.com"
```

✅ *Verify:* `Login Succeeded`. ⚠️ **Write `$REPO` down and set a reminder to delete it** — this is
the one billable object of the day (DEPLOY-07d).

**Step 4 — build naively, on purpose, and deploy it.**

We are going to deploy the image **as Day 100 built it**, exactly as `04_aws.md` §4 suggests. It
will not work. Doing it deliberately is the point — §5 is the lesson.

```powershell
uv export --no-hashes -o requirements.txt

docker build --platform linux/amd64 --provenance=false `
  -f Dockerfile.adk -t "${REPO}:naive" .
docker push "${REPO}:naive"

aws lambda create-function `
  --function-name sutra-agent `
  --package-type Image `
  --code "ImageUri=${REPO}:naive" `
  --role "arn:aws:iam::${ACCOUNT}:role/sutra-lambda-role" `
  --memory-size 512 `
  --timeout 60 `
  --environment "Variables={GOOGLE_GENAI_USE_VERTEXAI=FALSE,GOOGLE_API_KEY=$env:GOOGLE_API_KEY}" `
  --region $REGION
```

| Flag | What it does |
| --- | --- |
| `--provenance=false` | DEPLOY-07c — stops buildx attaching attestation manifests that make the image look multi-architecture, which Lambda rejects |
| `--package-type Image` | this is a container function, not a zip |
| `--memory-size 512` | DEPLOY-07a's arithmetic — this number *is* the GB-second burn rate |
| `--timeout 60` | ⚠️ Lambda's default is **3 seconds**. An agent request is 3–10. Leave the default and every call fails for a reason that has nothing to do with today's actual lesson |
| `--environment` | ⚠️ note this is a **literal value**, like Day 101's App Service and unlike Days 097/100's secret references. AWS's free equivalent is **SSM Parameter Store** (standard parameters are free); Day 105 revisits this when the same key lands in Terraform state |

✅ *Verify:* `aws lambda get-function --function-name sutra-agent --query "Configuration.State"`
eventually returns `"Active"` (it passes through `Pending` while Lambda optimises the image —
DEPLOY-07c). **Wait for `Active` before Step 5**, or you'll misdiagnose the failure.

## 5 · 💥 Failure lab — the container that starts, stays healthy, and answers nothing

> 🎬 **The scene:** the function is `Active`. The image is the exact same one Container Apps ran
> perfectly on Day 100. Invoke it:
>
> ```powershell
> aws lambda invoke --function-name sutra-agent --region $REGION `
>   --payload '{"rawPath":"/list-apps","requestContext":{"http":{"method":"GET"}}}' `
>   --cli-binary-format raw-in-base64-out out.json
> Get-Content out.json
> ```
>
> 💥 **It hangs for the full 60 seconds, then returns a timeout error.** Not a crash. Not a 500.
> No Python traceback. The logs show the container starting normally —
> `Uvicorn running on http://0.0.0.0:8000` — and then nothing at all.
>
> 😬 **The naive fixes, all of which are wrong here:** raise the timeout (it'll just fail slower);
> raise the memory; check the API key; suspect a VPC or networking problem; conclude Lambda "can't
> do FastAPI."
>
> 💥 **Why it fails, mechanically.** Read the logs first, per Day 097 §5's discipline:
>
> ```powershell
> aws logs tail /aws/lambda/sutra-agent --region $REGION --since 10m
> ```
>
> The tell is what's *absent*: no request ever arrives. `adk api_server` is bound to port 8000
> waiting for someone to connect — and **on Lambda, nobody ever connects.** Lambda's contract is
> the opposite direction (DEPLOY-07b): the process is supposed to call *out* to
> `$AWS_LAMBDA_RUNTIME_API`, ask for an event, and POST a reply. Our container never asks, so
> Lambda concludes the invocation never completed, and kills it at the timeout.
>
> 💡 **The insight: "it's a container" is not a portability guarantee — it's a packaging format.**
> The same image ran unchanged on Container Apps because Container Apps speaks HTTP to it. Lambda
> speaks a different protocol entirely. Portability lives at the **interface**, not the artifact,
> and this repo's own `04_aws.md` §4 gets that wrong by calling Day 86's HTTP Dockerfile "the
> natural fit."

**Step 6 — the real fix: the Web Adapter.**

`Dockerfile.lambda` (repo root — new file; three lines of difference from `Dockerfile.adk`):

```dockerfile
# Dockerfile.lambda — Dockerfile.adk plus the AWS Lambda Web Adapter.
# The adapter speaks Lambda's Runtime API and forwards each event to our
# ordinary HTTP server, so sutra/ needs no change at all. See day_103.md §3b.
FROM python:3.12-slim

# The ONLY Lambda-specific line. Pinned to a release, never :latest —
# same rule as the model pin (Day 5) and the image tag (Day 100).
COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter:1.0.1 /lambda-adapter /opt/extensions/lambda-adapter

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY sutra/ ./sutra/

ENV PYTHONPATH=/app
ENV AWS_LWA_PORT=8000
ENV AWS_LWA_READINESS_CHECK_PATH=/list-apps

CMD ["sh", "-c", "adk api_server --host 0.0.0.0 --port 8000 sutra"]
```

| Line | What it does |
| --- | --- |
| `COPY --from=...:1.0.1 ... /opt/extensions/` | installs the adapter as a Lambda **extension** — anything in `/opt/extensions` is started by the Lambda runtime automatically. Version **1.0.1**, verified 2026-08-21 |
| `AWS_LWA_PORT=8000` | tells the adapter which local port our server listens on. ⚠️ Its default is **8080**; leave this out and you get the identical timeout as §5, having "fixed" nothing |
| `AWS_LWA_READINESS_CHECK_PATH=/list-apps` | the adapter waits for this path to answer before forwarding traffic. Default is `/`, which `adk api_server` may not serve — pointing it at a route we *know* exists avoids a false "not ready" |

```powershell
docker build --platform linux/amd64 --provenance=false -f Dockerfile.lambda -t "${REPO}:lwa" .
docker push "${REPO}:lwa"

aws lambda update-function-code --function-name sutra-agent `
  --image-uri "${REPO}:lwa" --region $REGION

aws lambda wait function-updated --function-name sutra-agent --region $REGION
```

✅ *Verify (the actual test of today's fix):* re-run the **identical** invoke from §5. It now
returns `["sutra"]` instead of timing out. Same agent, same server, same platform — one extension
binary and two environment variables in between.

**Step 7 — a Function URL and one real turn.**

```powershell
aws lambda create-function-url-config --function-name sutra-agent `
  --auth-type NONE --region $REGION

aws lambda add-permission --function-name sutra-agent `
  --statement-id FunctionURLAllowPublicAccess `
  --action lambda:InvokeFunctionUrl --principal "*" `
  --function-url-auth-type NONE --region $REGION

$URL = (aws lambda get-function-url-config --function-name sutra-agent --region $REGION --query FunctionUrl --output text).TrimEnd('/')

curl.exe "$URL/list-apps"
curl.exe -X POST -H "Content-Type: application/json" "$URL/apps/sutra/users/u1/sessions/s1" -d "{}"
curl.exe -X POST -H "Content-Type: application/json" "$URL/run" `
  -d '{"appName":"sutra","userId":"u1","sessionId":"s1","newMessage":{"role":"user","parts":[{"text":"A customer says checkout is broken."}]}}'
```

⚠️ `--auth-type NONE` makes this **publicly invocable by anyone with the URL**, and the separate
`add-permission` call is required — creating the URL config alone is not enough, which is a
common and confusing gap. Same caveat as Day 98 §4 Step 3 and Day 100 §4 Step 6: fine for a
deliberate, short-lived test you tear down today. Function URLs add no charge of their own.

✅ *Verify:* `/run` returns Sutra's real triage reply over HTTPS. **This is the step that spends
quota.**

**Step 8 — read the free-tier discipline back.**

```powershell
aws lambda get-function-configuration --function-name sutra-agent --region $REGION `
  --query "{mem:MemorySize, timeout:Timeout, arch:Architectures, state:State, pkg:PackageType}" -o table

aws lambda get-function-configuration --function-name sutra-agent --region $REGION `
  --query "Environment.Variables" -o json
```

✅ *Verify:* `mem` is `512` and `timeout` is `60` — the two numbers DEPLOY-07a's arithmetic
depends on, read back rather than assumed. ⚠️ Note honestly what the second command shows: your
API key, **as a literal value**, because that's what `--environment` does. Day 105 revisits this;
AWS's free answer is SSM Parameter Store standard parameters.

Then check the one thing that actually accrues:

```powershell
aws ecr describe-images --repository-name sutra-agent --region $REGION `
  --query "imageDetails[].{tag:imageTags[0], mb:imageSizeInBytes}" -o table
```

✅ *Verify:* you can see **both** images (`naive` and `lwa`) and their sizes. Two images, two
copies of a Python base layer — DEPLOY-07d's cost, made visible. This is why §9 deletes the
repository rather than just the function.

## 6 · 🎤 Interview corner

1. **"You containerised an agent once and deployed it to three clouds. What broke on AWS?"** —
   The assumption that a container is portable. Container Apps and Cloud Run speak HTTP *to* your
   process; Lambda inverts it — your process must call the Runtime API and pull events. So the
   identical image that worked on Azure started cleanly on Lambda and timed out on every
   invocation, with no error, because nothing ever connected to the socket it was waiting on. The
   fix was the Lambda Web Adapter as an extension in `/opt/extensions`, which speaks the Runtime
   API and forwards to my server unchanged. Portability lives at the interface, not the artifact.
2. **"Lambda gives you a million free requests. How many can you actually make?"** — About a
   sixth of that, for this workload. The second meter — 400,000 GB-seconds — binds first, because
   an agent request is slow: at 512 MB and ~5 seconds, that's 2.5 GB-s each, so ~160,000 requests.
   And the usual advice to raise memory so CPU scales up doesn't help here, because the five
   seconds are network wait on the model, not compute.
3. **"Is deploying to Lambda free?"** — The compute is; the deployment isn't quite. Lambda only
   accepts images from private ECR, and private ECR's free 500 MB is a 12-month offer that new
   accounts don't get at all — so you're paying cents a month for image storage regardless. I
   handled it by treating the repository as session-scoped: create it, use it, delete it the same
   day, function first so the function doesn't enter the Failed state on the way out.
4. **"What's a bug that only shows up weeks later?"** — Lambda reclaims a container function's
   optimised image if it isn't invoked for several weeks; the next invocation is *rejected* while
   it re-optimises, then works on retry. So a demo that ran fine last month fails its first call
   in front of an audience and succeeds when you try again — which looks like flakiness and is
   actually documented lifecycle behaviour.

**Cleanup — order matters (DEPLOY-07d):**

```powershell
# 1. Function first — deleting the image out from under a live function makes it Failed.
aws lambda delete-function-url-config --function-name sutra-agent --region $REGION
aws lambda delete-function --function-name sutra-agent --region $REGION

# 2. THEN the repository and both images.
aws ecr delete-repository --repository-name sutra-agent --force --region $REGION

# 3. The role, and the local artifacts.
aws iam detach-role-policy --role-name sutra-lambda-role `
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
aws iam delete-role --role-name sutra-lambda-role
Remove-Item trust-policy.json, requirements.txt -ErrorAction SilentlyContinue

# 4. Prove it.
aws ecr describe-repositories --region $REGION --query "repositories[].repositoryName"
aws lambda list-functions --region $REGION --query "Functions[].FunctionName"
aws logs describe-log-groups --region $REGION --query "logGroups[?contains(logGroupName,'sutra')].logGroupName"
```

⚠️ That last check is a genuine orphan: CloudWatch **log groups survive deleting the function**,
and they have their own (small, free-tier-covered) storage. Delete with
`aws logs delete-log-group --log-group-name /aws/lambda/sutra-agent` if you want a clean slate.
