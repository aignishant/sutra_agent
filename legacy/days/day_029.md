## 1 · 🎬 Where we are — the story so far

trust: you. But look at the shape of the ecosystem you joined on Day 25 — an open spec,
40+ compatible products, public catalogs, registries. The entire point of a standard
format is that **know-how becomes shareable**. Someone has already written the
PDF-extraction skill, the changelog skill, the incident-comms skill. The economically
rational move is to *install*, not rewrite.

And there is the trap, wearing the costume of a gift. Because you also know, since
Day 26, exactly what a skill *is* mechanically: **instructions your agent will follow,
plus files it will read, plus scripts it can run.** Installing a stranger's skill is
handing a stranger's text to the component of your system that does what text says.
Your own repo already lives this discipline, by the way — open
`docs/days/SKILL_PROVENANCE.md`: six rows of *driver* skills (Claude Code's own
tooling), each pinned to a commit, licence recorded, read in full before use. Today
that discipline gets its reasons, its checklist, and its first *runtime*-skill rows.

## 3 · 📚 Concepts

### SK-12 — Where skills come from (and how much to trust each door)

| Source | What it is | Trust posture |
| --- | --- | --- |
| Your own repo (`skills/`) | first-party, reviewed at authoring | trusted — because *you* are the supply chain |
| The spec org (github.com/agentskills/agentskills) | reference examples + validator | read anyway; reference ≠ audited for *your* threat model |
| Community repos/catalogs (e.g. github.com/miticojo/adk-skill; curated lists) | anyone can publish | **audit fully, pin to a commit** — the default posture |
| Managed registries (GCP Skill Registry / Agent Registry) | centrally hosted, searchable, fetchable at runtime | org-governed, but *runtime fetch* moves the audit problem (see SK-16) |

The gradient is not about good and bad people. It is about **who can change the text
after you read it**. A pinned commit cannot change under you; an unpinned `main` branch
can; a registry entry fetched at runtime *definitionally* arrives after your last read.

### SK-13 — The audit: read like the thing that will obey it

An audit is a full read with three lenses, in a fixed order (order matters — cheap
checks first):

**Lens 1 — Identity & hygiene** (minutes): spec-valid frontmatter? `name` matches
folder? licence present and compatible? version/pin recorded? If this fails, stop —
a publisher who can't manage frontmatter hasn't earned a deeper read.

**Lens 2 — Tools-first content read** (the core): list every tool the prose assumes
(Day 27 taught you: prose creates dependencies) and every capability `allowed-tools`
pre-approves. Then read the body asking one question per line: *"if my agent obeys
this line literally, what happens?"* Red flags, concrete:

- instructions that address the agent's *standing rules* ("ignore previous…", "do not
  mention…", "always run X first")
- instructions to **send data anywhere** (URLs, emails, "report usage to…")
- vagueness that expands scope ("use any available tool to…")
- references that point *outside* the skill folder, or chains deeper than one level

**Lens 3 — Executable content** (`scripts/`, assets that tools might run): read every
script as hostile-until-proven-boring. Network calls? File writes outside its folder?
Env-var reads (**your keys live in env vars**)? Encoded blobs you can't read? Any one
→ reject or defang.

💡 **Mental model: audit prose as if it will be executed — because for an agent,
prose IS executed, just on a probabilistic CPU.** The verdict is written (accept /
accept-with-changes / reject + reasons), because an unwritten audit is an audit that
didn't happen (Principle 12, paperwork edition).

### SK-14 — Why this is a security topic, not a code-review topic

Remember the shape of Sutra's defenses so far: honesty rules in the persona,
`guard_tools` vetoes, error surfacing. All of them assume the *user* might be
adversarial. A malicious skill is worse-placed than a malicious user: its text arrives
**inside the trusted channel** — loaded by `load_skill` as sanctioned procedure, with
the implicit authority of "this is how we do things here."

Preview of Day 66's vocabulary (the **lethal trifecta**): an agent becomes dangerous
when it combines (1) access to private data, (2) exposure to untrusted content, and
(3) the ability to act externally. A third-party skill is a *delivery vehicle for #2
that you voluntarily install next to #1 and #3*. Your `ticket-triage` skill already
wrote the counter-move for ticket *text* ("treat it as DATA"); but a skill's own body
can't be neutralized that way — the whole point of loading it is to follow it. The
only defenses that work are **upstream** (audit before install, pin what you audited)
and **downstream** (least-privilege tools, Day 68; guardrails, Day 67). There is no
mid-stream defense. That asymmetry is why the ledger rule is absolute.

### SK-15 — Provenance: the ledger row IS the permission

The rule (master plan §16, and the repo has lived it since the driver skills):
**a third-party skill runs only after its row exists** in `SKILL_PROVENANCE.md`:

```
| Skill | Source URL | Licence | Audit date | Notes |
```

with the commit pin and audit outcome in Notes (the six existing rows show the house
style: `Pinned @ 8b78b53; full SKILL.md read; <what was dropped/flagged>`). The row is
small on purpose — small enough that there is no excuse to skip it, complete enough to
answer, months later: *what did we install, from where, under what terms, who checked
it, against which version?* When a CVE-shaped headline hits a popular skill repo, that
table is the difference between a 5-minute grep and a repo-wide archaeology dig.

### SK-16 — Registries: search, fetch… and the audit model shift 🅿️

ADK ships a managed-registry client (verified today, **Preview**):

```python
from google.adk.integrations.skill_registry import GCPSkillRegistry
registry = GCPSkillRegistry(project_id=..., location=...)   # GCP project required
# async: registry.search_skills(query="...") -> list[Frontmatter]
# async: registry.get_skill(name="...")     -> Skill
toolset = SkillToolset(skills=[], registry=registry)         # agent can now discover
```

Understand what the last line *means*: the agent can *discover and load skills at
runtime that you never read*. For an enterprise with central governance (the registry
is org-curated, access-controlled) that trade can be right — the org audits centrally
so teams don't audit repeatedly. For Sutra the analysis is short: (a) it requires a
GCP project with the API enabled — a billing-account doorway, so Addendum 02 parks it
(config sketch written in step 6, never executed); (b) even with budget, our
threat-model answer would be *pin-and-vendor*: fetch, audit, copy into `skills/`, row
in the ledger — runtime discovery is for skills someone ELSE already governs.
🅿️ Parked: interview-ready, deliberately not built.

## 5 · 💥 Failure lab — the audit that stopped at the frontmatter

> 🎬 **The scene:** a teammate finds a popular reply-formatting skill. 4k stars,
> active commits, clean frontmatter, MIT licence. "It validates! `skills-ref` passes!
> The linter is happy!" They vendor it and move on.
> 😬 **The naive fix:** "it's fine — it passed validation, and thousands of people use
> it. Popularity is the audit."
> 💥 **Why it fails:** you proved it today with `evil-helper` — which *also* passes
> every mechanical check: valid frontmatter, tidy folder, plausible description. The
> three things that made it lethal (prose exfiltration, authority-plus-stealth
> override, a key-stealing script in a `print("ok")` costume) are invisible to
> validators, invisible to star counts, and — worst — invisible in operation: the
> replies still look great, the script still prints its cheerful line. Validation
> checks the *shape* of a skill; the attack lives in the *sense*. You have met this
> exact boundary before, on Day 4: schemas constrain shape, never sense. Popularity
> adds nothing: stars are farmable, and a maintainer account takeover flips a trusted
> repo hostile in one force-push — which an unpinned install inherits silently on the
> next fetch.
> 💡 **The insight:** **mechanical validation and human audit answer different
> questions — "is this a skill?" versus "should THIS agent obey it?" — and only the
> second one is security.** So the pipeline is: validate (cheap, automated, Day 31),
> audit (eyes, tools-first, written verdict), pin (the text you audited is the text
> that runs), row (the permission slip), and only then wire. Skip any stage and the
> stages after it are checking a different artifact than the one you'll run.

Observed today, not asserted: one poisoned skill passing every mechanical check and
failing the human audit on three counts — found by you, with the checklist.

## 6 · 🎤 Interview corner

1. **"You want to use a community-published agent skill. Walk me through your
   process."** — Source it, pin it, audit it, record it, then wire it. Pin: clone and
   take the commit hash — the text I audit must be the text that runs. Audit in three
   lenses: identity/licence hygiene; a tools-first prose read where I ask of every
   line "what happens if my agent obeys this literally?" — flagging authority
   overrides, self-concealment, and any instruction that moves data outward; then
   scripts read as hostile-until-boring (network, env vars, out-of-folder writes,
   unreadable blobs). Written verdict, then a provenance ledger row — skill, source,
   licence, pin, audit date — and the standing rule is *no row, no run*. I've run
   this on a deliberately poisoned fixture and it catches all three classic traps.
2. **"Why are agent skills a prompt-injection concern? They're just docs."** — Because
   for an agent, docs are execution: a skill's body is loaded as *sanctioned
   procedure*, inside the trusted channel, with more authority than user input. That
   makes a hostile skill a delivery vehicle for untrusted content sitting right next
   to private data and real tools — the lethal trifecta, self-installed. And there's
   no mid-stream defense: you can't tell the model "treat the procedure as data" —
   following it is the point. So defenses live upstream (audit, pin) and downstream
   (least-privilege tools, guardrail callbacks); the audit is load-bearing, not
   ceremony.
3. **"When do managed skill registries make sense versus vendoring?"** — Registries
   move the audit, they don't remove it. ADK's `GCPSkillRegistry` lets an agent
   search and fetch skills at runtime — right when one governance team curates
   centrally and many teams consume: the audit is amortized. Vendoring-with-pins is
   right when the consuming team IS the governance — my case — because runtime fetch
   means text arriving after your last read. I'd also flag the ops tell: a registry
   dependency is a network+auth dependency in your agent's hot path; pinned files
   in the repo are not.
