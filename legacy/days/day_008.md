## 3 · 📚 Concepts

### ADK-06 — Sessions & runs: the filing cabinet

**The clinic story.** A medical clinic sees hundreds of patients. Dr. Model has total
amnesia (Day 2 — this never changed and never will). The clinic still functions,
because of the **records room**: every patient has a folder; every visit, the assistant
pulls the folder, the doctor reads it cover to cover, sees the patient, and the
assistant files the new notes back in. The doctor never remembers; the *system*
remembers.

Map it (and notice you built the whole left column on Day 3):

| Clinic | ADK | Day 3 ancestor |
| --- | --- | --- |
| one patient folder | a **Session** | your `transcript` list |
| the folder's label | `(app_name, user_id, session id)` | — (you had one folder, unlabeled) |
| pages inside | `session.events` | the transcript's entries |
| the sticky note on the cover | `session.state` (a dict) | — (Day 17 opens this) |
| "last visit" stamp | `session.last_update_time` | — |
| the records room | a **SessionService** | the Python variable holding your list |
| pulling + filing the folder | the runner's commit cycle (Day 7) | your two `append`s |

The **Session's anatomy** (verified 2026-08-18): `id`, `app_name`, `user_id`, `state`,
`events`, `last_update_time`. Six fields, and you already deeply know the important two:
`events` is the record (Day 7), `state` is the sticky note (Day 17's whole day —
today we only look at it).

The filing scheme deserves a beat: sessions are filed under **app, then user, then
session**. One user can hold many sessions (your three tabs in `adk web` yesterday), and
sessions of different users are strangers by construction — the service simply will not
hand you a folder without the right `(app_name, user_id, session_id)` triple. Isolation
is not a policy here; it is an address.

And a **run**? One `run_async(user_id=..., session_id=..., new_message=...)` call: the
runner pulls the folder, replays it to the amnesiac doctor, drives the turn (yielding
events through the commit cycle), and files every event back. A minimal chat turn
appends two pages — the user's message-event and the model's final-response event; tool
calls will add more pages from Day 10 on.

💡 **Mental model: the agent never remembers — the session is remembered *at* it.**
Every turn is still Day 2's cold call; the session is Day 3's transcript with a
landlord, a label, and a lock.

### ADK-07 — In-memory services: the swappable records room

**The story, continued.** The clinic's records room is an *interface*, not a place:
"give me folder X," "file these pages." Whether the folders live on paper shelves, in a
fireproof archive, or in the receptionist's astonishing short-term memory — the doctor
and assistant work identically. Storage is someone else's problem, *behind a stable
counter*.

That is the **service pattern**, and ADK applies it everywhere: `SessionService` for
conversations, and siblings you will meet later (`MemoryService` — Day 46,
artifact services — Day 18). Each service is an interface with several implementations,
and today's implementation is the receptionist's memory: **`InMemorySessionService`** —
folders kept in the Python process's RAM.

Its contract (verified, and note every call is `await`ed — services are async):

```python
from google.adk.sessions import InMemorySessionService

service = InMemorySessionService()
s  = await service.create_session(app_name=..., user_id=..., state={...})  # new folder
s2 = await service.get_session(app_name=..., user_id=..., session_id=...)  # pull it
await service.delete_session(app_name=..., user_id=..., session_id=...)    # shred it
```

The trade, stated honestly:

| | In-memory | Database-backed (Day 47) |
| --- | --- | --- |
| speed | RAM-fast | disk/network |
| setup | zero | connection string, schema |
| survives a restart | **no — total amnesia** | yes |
| right for | development, tests, labs | anything users touch |

"Total amnesia on restart" is not a footnote — it is the *defining property*, and §4's
`amnesia` demo makes you feel it instead of read it. The payoff of the pattern is the
other half: on Day 47 we swap `InMemorySessionService` for a database-backed one, and
**the agent, the runner calls, and every demo written today keep working unchanged** —
because they talk to the counter, never to the shelves. (Yesterday's `adk web` flag
`--session_service_uri "sqlite:///sessions.db"` is this exact swap, as a command-line
option — a preview of Day 47.)

One convenience ties the day together: **`InMemoryRunner`** — the runner we have used
since Day 5 — is simply a `Runner` pre-wired with in-memory services, exposed at
`runner.session_service`. Loop-in-a-box, records-room included. Perfect for labs;
replaced piece by piece as Sutra grows up.

💡 **Mental model: a service is a counter, not a warehouse.** Code that talks to the
counter never notices the warehouse changing behind it — which is exactly what makes
Day 47's upgrade a one-line swap instead of a rewrite.

```python
"""Day 8 — sessions, runs & in-memory services, observed live.

Demos (each name = one lesson):

    python -m sutra.run_agent bowls     # isolation + continuity (3 model calls)
    python -m sutra.run_agent inspect   # a session's anatomy     (1 model call)
    python -m sutra.run_agent amnesia   # the restart test        (0 model calls)
    python -m sutra.run_agent shared    # failure lab: one bowl for everyone (2 calls)

Importable with no side effects (the house rule since Day 2).
"""
from __future__ import annotations

import asyncio
import sys

from google.adk.runners import InMemoryRunner   # loop-in-a-box + in-memory services
from google.genai import types

from sutra.agent import root_agent


def _msg(text: str) -> types.Content:
    """Wrap plain text as a user turn (same shape as Days 3-7).

    Args:
        text: what the user says.

    Returns:
        Content(role="user") ready for run_async's new_message.

    Example:
        >>> _msg("hi").parts[0].text
        'hi'
    """
    return types.Content(role="user", parts=[types.Part(text=text)])


async def _turn(runner: InMemoryRunner, user_id: str, session_id: str,
                text: str) -> str:
    """Run ONE turn in an existing session; return the final answer text.

    This is Day 3's run_loop from the outside: the runner pulls the
    session, replays it to the amnesiac model, commits every event back
    (Day 7's cycle), and the final-response event carries the answer.

    Args:
        runner: the InMemoryRunner owning agent + services.
        user_id: whose folder drawer to open.
        session_id: which folder in that drawer.
        text: the user's message this turn.

    Returns:
        The final response's text (empty string if none arrived).

    Example:
        >>> # answer = await _turn(runner, "u1", sid, "hello")   # 1 model call
    """
    answer = ""
    async for event in runner.run_async(          # one run = one filed visit
        user_id=user_id,
        session_id=session_id,
        new_message=_msg(text),
    ):
        if event.is_final_response() and event.content and event.content.parts:
            answer = "".join(p.text or "" for p in event.content.parts
                             if getattr(p, "text", None))
    return answer.strip()


async def demo_bowls() -> None:
    """Two sessions for one user: continuity inside, isolation between.

    Usage:  python -m sutra.run_agent bowls    (3 model calls - pace them)
    """
    runner = InMemoryRunner(agent=root_agent)
    svc = runner.session_service                   # the records room, exposed
    a = await svc.create_session(app_name=runner.app_name, user_id="dana")
    b = await svc.create_session(app_name=runner.app_name, user_id="dana")
    print(f"two folders, same user: A={a.id[:8]}… B={b.id[:8]}…")

    # Turn 1, bowl A: plant a fact.
    print("A:", await _turn(runner, "dana", a.id,
                            "For this conversation: my name is Priya."))
    # Turn 2, bowl A: the fact must survive - THIS session remembers.
    print("A:", await _turn(runner, "dana", a.id, "What is my name?"))
    # Turn 3, bowl B: same user, different folder - the fact must NOT leak.
    print("B:", await _turn(runner, "dana", b.id, "What is my name?"))


async def demo_inspect() -> None:
    """One turn, then read the session's six fields off the record.

    Usage:  python -m sutra.run_agent inspect   (1 model call)
    """
    runner = InMemoryRunner(agent=root_agent)
    svc = runner.session_service
    s = await svc.create_session(app_name=runner.app_name, user_id="dana",
                                 state={"desk": "night-shift"})   # a sticky note
    before = len(s.events)                        # pages before the visit
    await _turn(runner, "dana", s.id, "One sentence: what do you do?")
    s = await svc.get_session(app_name=runner.app_name, user_id="dana",
                              session_id=s.id)    # re-pull the folder (fresh copy)
    print(f"id:            {s.id}")
    print(f"app / user:    {s.app_name} / {s.user_id}")
    print(f"state:         {s.state}")             # the sticky note, untouched today
    print(f"events:        {before} -> {len(s.events)} (user msg + final answer)")
    print(f"last_update:   {s.last_update_time:.2f}")


async def demo_amnesia(step: str) -> None:
    """The restart test: in-memory folders die with the process.

    Run 'amnesia' (this function, step=create) - it creates a session and
    prints its full address, then EXITS. Then run 'amnesia2' with that
    address pasted as extra args - a NEW process asks the records room
    for the folder. RAM is gone between processes; so is the folder.

    Usage:  python -m sutra.run_agent amnesia            (0 model calls)
            python -m sutra.run_agent amnesia2 <session_id>
    """
    runner = InMemoryRunner(agent=root_agent)
    svc = runner.session_service
    if step == "create":
        s = await svc.create_session(app_name=runner.app_name, user_id="dana")
        print(f"created session {s.id}")
        print(f"now run:  python -m sutra.run_agent amnesia2 {s.id}")
    else:                                          # step == "find", new process
        sid = sys.argv[2] if len(sys.argv) > 2 else ""
        found = await svc.get_session(app_name=runner.app_name,
                                      user_id="dana", session_id=sid)
        print(f"get_session({sid[:8]}…) -> {found}")   # expect: None. RAM died.


async def demo_shared() -> None:
    """Failure lab: every user shares ONE session id (see doc section 5).

    Usage:  python -m sutra.run_agent shared    (2 model calls)
    """
    runner = InMemoryRunner(agent=root_agent)
    svc = runner.session_service
    s = await svc.create_session(app_name=runner.app_name, user_id="everyone")
    # "User A" confides something into the shared bowl:
    print("A:", await _turn(runner, "everyone", s.id,
          "I'm reporting ticket 4521 - I keep getting logged out. Please remember that."))
    # "User B" - different human, SAME session - asks an innocent question:
    print("B:", await _turn(runner, "everyone", s.id,
          "Hi, I'm a different customer. What ticket am I asking about?"))


def main() -> None:
    """Tiny demo dispatcher - the house pattern since Day 2."""
    demos = {
        "bowls": lambda: asyncio.run(demo_bowls()),
        "inspect": lambda: asyncio.run(demo_inspect()),
        "amnesia": lambda: asyncio.run(demo_amnesia("create")),
        "amnesia2": lambda: asyncio.run(demo_amnesia("find")),
        "shared": lambda: asyncio.run(demo_shared()),
    }
    name = sys.argv[1] if len(sys.argv) > 1 else "bowls"
    if name not in demos:
        print(f"usage: python -m sutra.run_agent [{'|'.join(demos)}]")
        raise SystemExit(2)
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — one bowl for everyone

> 🎬 **The scene:** you are wiring Sutra into a little web endpoint next month, and
> session bookkeeping feels like ceremony — create, store the id, look it up per user…
> A shortcut whispers: *use one well-known session id for everybody.* One line of
> config. The demo works instantly.
> 😬 **The naive fix:** `session_id = "global"` for every request. Ship it.
> 💥 **Why it fails:** run `python -m sutra.run_agent shared`. "User A" reports ticket
> 4521 and their logout problem. "User B" — explicitly a different customer — asks what
> ticket *they* are asking about… and the agent helpfully answers **with A's ticket**,
> because the runner faithfully replayed the shared folder, A's confidences included,
> into B's turn. Nothing malfunctioned: every component did its job perfectly. The
> *filing* was the bug. Now scale the scene up: swap "ticket 4521" for a password, an
> address, a medical detail — this shortcut is a data breach with good uptime. And its
> quieter cousin costs you too: the shared folder grows without bound, so every user
> pays the token bill of every other user's history (Day 24 will price that).
> 💡 **The insight:** **conversation isolation lives entirely in the (app, user,
> session) address — the model cannot enforce what the filing system gives away.** The
> model has no concept of "different customer"; it sees one transcript and serves it
> loyally. Session-per-conversation, keyed to the authenticated user, is not
> bookkeeping ceremony — it is the privacy boundary itself (a SEC-13 preview, Phase 10).

Observed today, not just asserted: B read A's ticket out of the shared bowl, in one
demo, with the persona rules fully intact — because no instruction can refuse what the
context already contains.

## 6 · 🎤 Interview corner

1. **"How does an ADK agent remember a conversation if LLM calls are stateless?"** — It
   doesn't; the session does. Every turn, the runner pulls the Session — an addressed
   record of events filed under (app, user, session id) — replays it to the model,
   drives the turn, and commits the new events back through the SessionService. I've
   built both halves: hand-rolled transcript management first, then ADK's version. The
   model stays a goldfish forever; engineering the *filing* is what makes it look like
   memory.
2. **"What's the difference between in-memory and persistent session storage, and when
   is each right?"** — Same interface, different warehouse. In-memory is RAM-fast and
   zero-setup, ideal for dev and tests — and it forgets everything on restart, which
   I've demonstrated across two processes rather than taken on faith. Anything
   user-facing needs a database-backed service. The service pattern is the real answer:
   because callers talk to the SessionService interface, swapping in-memory for
   database is a wiring change, not a rewrite.
3. **"Tell me about a session-management bug that isn't a crash."** — The shared-session
   privacy leak. Reuse one session id across users and the runner faithfully replays
   user A's history into user B's turn — no error, no warning, just B reading A's data.
   I've reproduced it deliberately: isolation in these systems is purely the storage
   address; no persona rule can refuse context it's already been handed. So
   session-per-conversation keyed to the authenticated user is a security control, not
   hygiene — and it also caps the unbounded context growth that a shared folder
   accumulates.
