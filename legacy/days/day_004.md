## 3 · 📚 Concepts

### AG-04 — Tools by hand: function calling, JSON schemas, the tool-result turn

**The restaurant story.** Picture a busy restaurant. Yesterday's system was a customer
*shouting* an order across the room: "One lookup of ticket 4521, please!" The waiter (your
regex) tries to hear it right over the noise. Usually fine. Sometimes: "Did he say 4521 or
4531? Was that an order at all, or just talking?"

Today the restaurant switches to **printed order forms**. Each dish on the menu has a form
with labeled boxes: *dish name* (pick from the menu only), *quantity* (a number, required).
The customer fills in the boxes. There is nothing to mis-hear anymore — the form either is a
valid order, or it is not an order at all.

Map the story to our system, piece by piece:

| Restaurant | Our system | Technical name |
| --- | --- | --- |
| The menu + its order forms | Your tool descriptions with typed argument boxes | function **declarations** with a **JSON Schema** |
| The customer filling a form | The model deciding to act | the **function_call** part in the response |
| The kitchen actually cooking | Your Python function running | your code — this NEVER changes |
| The waiter bringing food back to the table | The result going back into the conversation | the **tool-result turn** (`role="tool"`) |

💡 **Mental model: function calling is not the model calling functions. It is the model
filling out a form that your code executes.** Day 3's contract was prose ("please write
`ACTION:`…"). Today's contract is a form. **Prose is a request; a form is a guarantee.**

#### a) The menu: declarations and JSON Schema

To put a tool on the menu, you write a **declaration** with three parts — and each part talks
to a different reader:

| Part | Who reads it | What it is for |
| --- | --- | --- |
| `name` | your dispatcher | which Python function to run |
| `description` | the model | *when* and *why* to use this tool — this sentence is prompt engineering, not paperwork |
| `parameters_json_schema` | both sides | the shape of the arguments: which fields, which types, which are required |

**What is JSON Schema, simply?** A standard way to describe the *shape* of data, written in
JSON itself. Read this one out loud and it explains itself:

```json
{
  "type": "object",                          ← "the arguments come as one object (a dict)"
  "properties": {                            ← "here are its fields:"
    "ticket_id": {                           ← "a field called ticket_id…"
      "type": "string",                      ← "…which must be text"
      "description": "The ticket id, e.g. '4521'."
    }
  },
  "required": ["ticket_id"]                  ← "and you may not leave it empty"
}
```

That's the whole idea. And here is why learning it *today* pays for weeks: this exact
mini-language returns again and again — ADK `FunctionTool`s (Day 10), structured output
(Day 12), MCP tool definitions (Day 34). Learn it once, in the raw, and every later framework
becomes "oh, it's just schemas again."

*A concrete win over yesterday:* on Day 3 the model could send `ACTION: lookup_ticket` with no
argument, and you found out at runtime. Today `ticket_id` is a **required** box on the form —
that mistake stopped being a bug you handle and became a sentence the protocol cannot say.

#### b) The order slip: what the model actually sends

When the model decides to act, its reply carries **no text**. Instead,
`response.function_calls` holds one or more small objects, each with:

- `.name` — guaranteed to be a name from *your* menu (the model cannot order a dish you never
  declared), and
- `.args` — a Python **dict**, already parsed from JSON by the API. No regex. No
  `partition(" ")`. No "protocol error" branch. Dispatch collapses to one beautiful line:
  `TOOLS[fc.name](**fc.args)`.

Two details are load-bearing, so look at them now:

1. **It is a list.** The model may fill *several* forms in one turn — say, looking up two
   tickets at once. This is called **parallel function calling**. Our loop handles all of
   them and returns all results together. (Day 10 shows ADK doing the same.)
2. **It is still only a request.** Nothing ran inside the model. Your dispatch table — the one
   dict you can guard, log, or refuse — is exactly where it was yesterday. The model proposes;
   the loop disposes. The API upgrade changed the *format* of the proposal, never the
   *authority* (Principle 13, unmoved).

#### c) The waiter returns: the tool-result turn

Day 3 smuggled results back disguised as user messages spelled `OBSERVATION:` — because in the
raw two-role world, everything that isn't the model counts as "user". The native protocol
gives results their own citizenship: a part built with `types.Part.from_function_response(…)`,
wrapped in a `types.Content(role="tool", …)`. The conversation now has **three** voices:

```
user  → the question
model → function_call: lookup_ticket(ticket_id="4521")     ← the filled form
tool  → function_response: {"result": "Title: Keeps getting logged out…"}   ← the food arrives
model → function_call: search_kb(query="logged out")
tool  → function_response: {"result": "KB-104 …"}
model → text: the final answer                              ← no form this time = we're done
```

The goldfish law from Day 3 still rules everything: the model only knows what is in the
transcript, and *you* still rebuild that transcript on every call. Note the small but crucial
move: you must re-append **the model's own function-call turn**
(`response.candidates[0].content`) *before* the tool turn — so the model sees *what it asked
for* right next to *what came back*. Skip either half and you have built a fancier goldfish.

And termination got cleaner too. There is no `FINAL:` magic word anymore: **a turn with no
function calls IS the answer.** The grammar of the protocol now encodes what Day 3 needed a
convention for. But `MAX_STEPS` stays — a brake written in your loop outranks any grammar,
because an agent you can't stop is still an outage.

#### d) The three moods — and a convenience we politely refuse

A setting called `tool_config` controls the model's "mood" about tools:

| Mode | Meaning | When it's right |
| --- | --- | --- |
| `AUTO` (default) | the model chooses: call a tool *or* just answer | almost always — it keeps the model's ability to say "no tool needed" |
| `ANY` | a tool call is **forced**, every turn | narrow extraction jobs where exactly one call is always correct |
| `NONE` | tools are switched off | when you want a plain-text answer even though tools are declared |

`ANY` looks tempting — "force a call and my agent will always ground its answers!" — and the
failure lab (§5) shows exactly why that thought is a trap.

One last thing the SDK offers, which today we *deliberately refuse*: if you pass a plain
Python function in `tools=[…]`, the SDK will read its signature, generate the schema, run the
function, and loop — all by itself. That feature is called **automatic function calling**, and
it is a miniature agent loop hiding inside the client library. It is almost exactly what ADK
does tomorrow, grown up. Today we keep every wire visible (declarations only, our own
dispatch), because Principle 4 says: build it once by hand, *then* let the framework take
over — so the framework is a convenience, never a mystery.

```python
"""Day 4 — tools by hand: native function calling and the tool-result turn.

Same two tools as Day 3, but the hand-parsed text protocol is gone: the
model now requests actions as structured function_call parts, and results
travel back as function_response parts inside a role="tool" turn.
Still no framework — ADK arrives on Day 5.

Importable with no side effects. Run the demos from the repo root:

    python -m sutra.tools oneshot   # the tool-result turn, in slow motion
    python -m sutra.tools triage    # Day 3's headline demo, native edition
    python -m sutra.tools unknown   # a lookup that fails; honesty check
    python -m sutra.tools forced    # failure lab: mode="ANY" (see doc section 5)
"""
from __future__ import annotations

import sys

from google import genai
from google.genai import types

from sutra.config import load_env                                    # loads .env (Day 1)
from sutra.loop import MAX_STEPS, TRIAGE_QUESTION, lookup_ticket, search_kb  # Day 3, reused
from sutra.mechanics import ask                                      # Day 2's 429-honest call

# ---------------------------------------------------------------------------
# The menu: one declaration per tool. Three parts, three readers:
#   name        -> read by OUR dispatcher (must match a key in TOOLS below)
#   description -> read by THE MODEL to decide when to use the tool
#   schema      -> read by BOTH: the exact shape of the arguments
# ---------------------------------------------------------------------------

LOOKUP_TICKET_DECL = types.FunctionDeclaration(
    name="lookup_ticket",                        # the name on the "order form"
    description="Return the raw text of a support ticket by its id.",
    parameters_json_schema={
        "type": "object",                        # arguments arrive as one dict
        "properties": {
            "ticket_id": {
                "type": "string",                # must be text, not a number
                "description": "The ticket id, e.g. '4521'.",
            },
        },
        "required": ["ticket_id"],               # the model CANNOT omit this box
    },
)

SEARCH_KB_DECL = types.FunctionDeclaration(
    name="search_kb",
    description="Search the internal knowledge base for a symptom; "
                "returns the best-matching article.",
    parameters_json_schema={
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Symptom keywords, e.g. 'user logged out'.",
            },
        },
        "required": ["query"],
    },
)

# Both declarations bundled into one Tool object — this is what the API wants
# inside GenerateContentConfig(tools=[...]).
TOOL = types.Tool(function_declarations=[LOOKUP_TICKET_DECL, SEARCH_KB_DECL])

# The dispatch table: form name -> real Python function.
# This dict is the ONLY door between the model's wishes and the real world —
# guard it, log it, or refuse it here (Principle 13).
TOOLS = {"lookup_ticket": lookup_ticket, "search_kb": search_kb}

# Day 3's SYSTEM prompt was ~20 lines, mostly begging for a text format.
# The format now lives in the declarations, so only persona + honesty remain.
SYSTEM = """You are Sutra, a support-ticket triage assistant. You cannot see
any data directly; use the tools. Never invent ticket contents or KB
articles — if a lookup fails, say so in your answer."""


def _config(**overrides: object) -> types.GenerateContentConfig:
    """Build today's standard model config: persona, deterministic, tools on.

    Args:
        **overrides: extra GenerateContentConfig fields for special demos
            (the `forced` demo passes tool_config through here).

    Returns:
        A ready-to-use GenerateContentConfig.

    Example:
        >>> cfg = _config()                    # the normal setup
        >>> cfg.temperature
        0.0
    """
    return types.GenerateContentConfig(
        system_instruction=SYSTEM,   # who the model is + the honesty rule
        temperature=0.0,             # deterministic: same input -> same output
        tools=[TOOL],                # hand the model the menu
        **overrides,                 # room for demo-specific extras
    )


def _run_calls(calls: list[types.FunctionCall]) -> types.Content:
    """Execute every call the model requested; return the role='tool' turn.

    This is the 'kitchen': the only place where a model request becomes a
    real Python call. A failed dispatch comes back as a RESULT the model can
    read — never a crash (agent-visible errors vs programmer errors, Day 3).

    Args:
        calls: the function_call objects from response.function_calls.

    Returns:
        One Content(role="tool") holding one function_response part per call.

    Example:
        >>> fake = types.FunctionCall(name="lookup_ticket",
        ...                           args={"ticket_id": "4521"})
        >>> turn = _run_calls([fake])          # prints CALL/RESULT lines
        >>> turn.role
        'tool'
    """
    parts = []                                       # one result part per call
    for fc in calls:                                 # the model may send SEVERAL (parallel calling)
        print(f"CALL: {fc.name}({fc.args})")         # audit trail (Principle 12)
        tool = TOOLS.get(fc.name or "")              # look the name up on OUR table
        if tool is None:                             # near-impossible natively, but…
            result = f"Unknown tool {fc.name!r}."    # …belt and braces costs 2 lines
        else:
            result = tool(**(fc.args or {}))         # args is already a dict: no parsing!
        print(f"RESULT: {result}")                   # show what the model will see
        parts.append(                                # wrap the result the official way
            types.Part.from_function_response(
                name=fc.name,                        # ties the result to its request
                response={"result": result},         # the payload the model reads
            )
        )
    return types.Content(role="tool", parts=parts)   # the third voice in the transcript


def run_loop(
    client: genai.Client,
    question: str,
    *,
    max_steps: int = MAX_STEPS,
) -> str | None:
    """Think->act->observe on the native protocol: no regex, no FINAL:.

    Termination is built into the grammar now: a reply with no function
    calls IS the final answer. MAX_STEPS stays as the hard brake — the
    prompt is a request, the step budget is a law (Day 3).

    Args:
        client: an authenticated genai.Client.
        question: the user's request, plain text.
        max_steps: hard cap on loop turns (default: Day 3's MAX_STEPS).

    Returns:
        The model's final text answer, or None if the brake tripped.

    Example:
        >>> load_env()
        >>> client = genai.Client()            # needs GOOGLE_API_KEY in .env
        >>> run_loop(client, "Ticket 4521 came in. What is wrong?")
        '...text citing KB-104...'             # after ~3 model calls
    """
    # The dossier starts with just the question — we rebuild the model's
    # whole world on every call (the API is stateless; Day 2's big lesson).
    transcript = [types.Content(role="user", parts=[types.Part(text=question)])]

    for step in range(1, max_steps + 1):             # the brake is not optional
        response = ask(client, transcript, _config())  # Day 2's wrapper: 429-safe
        print(f"\n--- step {step} ---")

        calls = response.function_calls or []        # None -> [] for easy checks
        if not calls:                                # no forms filled?
            return (response.text or "").strip()     # then this text IS the answer

        # Two appends, both essential (skip either -> fancier goldfish):
        transcript.append(response.candidates[0].content)  # what the model ASKED
        transcript.append(_run_calls(calls))               # what CAME BACK

    print(f"\nNo answer within {max_steps} steps — stopping. "
          "That is containment, not success.")       # honest failure (Principle 10)
    return None


def demo_oneshot(client: genai.Client) -> None:
    """The tool-result turn in slow motion: one call out, one result back.

    Usage:  python -m sutra.tools oneshot     (~2 model calls)
    """
    question = "What does ticket 4521 say? Quote the title."
    contents = [types.Content(role="user", parts=[types.Part(text=question)])]

    # Call 1: the model should answer with a FORM, not with text.
    first = ask(client, contents, _config())
    print("first response text:", repr(first.text))  # expect None — no prose!
    calls = first.function_calls or []
    if not calls:                                    # didn't call? config problem
        print("model answered without calling a tool — check tools made it "
              "into the config, then re-run.")
        return
    print("function_call:", calls[0].name, calls[0].args)  # .args is a dict already

    # Now WE perform the tool-result turn by hand:
    contents.append(first.candidates[0].content)     # 1) re-show its own request
    contents.append(_run_calls(calls))               # 2) attach the kitchen's result

    # Call 2: with the result in view, the model can finally answer.
    second = ask(client, contents, _config())
    print("final:", second.text)


def demo_triage(client: genai.Client) -> None:
    """Day 3's headline demo, re-run on the native protocol.

    Usage:  python -m sutra.tools triage      (~3 model calls)
    """
    print("\nANSWER:", run_loop(client, TRIAGE_QUESTION))


def demo_unknown(client: genai.Client) -> None:
    """A lookup that fails; honesty must survive the protocol upgrade.

    Usage:  python -m sutra.tools unknown     (~2 model calls)
    """
    print("\nANSWER:", run_loop(client, "Summarize ticket 9999 for the morning standup."))


def demo_forced(client: genai.Client) -> None:
    """Failure lab: mode='ANY' forces a call even when no tool applies.

    Usage:  python -m sutra.tools forced      (1 model call; read doc §5 first)
    """
    config = _config(
        tool_config=types.ToolConfig(                # the "mood" setting…
            function_calling_config=types.FunctionCallingConfig(mode="ANY")
        )                                            # …ANY = a call is mandatory
    )
    # A question that needs NO tool at all:
    question = "Write a one-line cheerful greeting for the support desk homepage."
    response = ask(
        client,
        [types.Content(role="user", parts=[types.Part(text=question)])],
        config,
    )
    for fc in response.function_calls or []:         # watch it invent a call anyway
        print(f"forced call: {fc.name}({fc.args})")
    print("text:", repr(response.text))              # expect None: text is FORBIDDEN


def main() -> None:
    """Tiny demo dispatcher — mirrors Day 2's and Day 3's pattern."""
    demos = {
        "oneshot": demo_oneshot,
        "triage": demo_triage,
        "unknown": demo_unknown,
        "forced": demo_forced,
    }
    name = sys.argv[1] if len(sys.argv) > 1 else "oneshot"
    if name not in demos:
        print(f"usage: python -m sutra.tools [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()                                       # keys from .env, never from code
    demos[name](genai.Client())


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the forced hand

> 🎬 **The scene:** you want Sutra to *always* ground its answers in real data — no more
> vibes-based replies, ever. Scrolling the docs you spot `mode="ANY"`: force a tool call on
> every turn. Grounding by construction! The logs will look wonderfully diligent.
> 😬 **The naive fix:** ship it. Every turn now provably calls a tool.
> 💥 **Why it fails:** you took away the model's right to say *"no tool applies here."* Asked
> for a homepage greeting, it *must* fill some form — so it invents one, and the fabricated
> arguments pass schema validation **perfectly**. `{'query': 'greeting'}` is a string; the
> form is filled correctly; it is just nonsense. Put ANY inside a loop and it gets worse: a
> turn with *no* calls is how the native protocol says "done" — under ANY that turn can never
> come, so the loop can never end. The model fabricates calls until `MAX_STEPS` trips. You
> have built a machine that produces well-typed garbage at 5 RPM.
> 💡 **The insight:** **a schema constrains the *shape* of an action, never the *sense* of
> it.** Validation is not judgment. Keep the mode on AUTO so the model may decline to act,
> keep the honesty rule in the instructions, and enforce *policy* — allowlists, approvals,
> budgets — in the loop, where enforcement is real (Principle 13). ANY is a scalpel for
> single-turn extraction jobs where exactly one call is always correct. It is not a grounding
> strategy.

## 6 · 🎤 Interview corner

1. **"What actually happens when a model 'calls a function'?"** — Nothing executes inside the
   model. It emits a structured *request* — a declared name plus arguments parsed against a
   JSON Schema — and my runtime decides whether to execute it and what to report back. I have
   built this channel both ways: Day 3 as a hand-parsed text protocol, Day 4 on the native
   API. The upgrade deleted a whole failure class (malformed actions) by moving the contract
   from prose to schema — and changed nothing about authority: my dispatch table still decides
   what runs.
2. **"Why does JSON Schema show up everywhere in agent engineering?"** — Because it is the one
   contract language every layer shares: function declarations, structured output, MCP tool
   definitions. It makes the model's side machine-checkable — a reply either parses or it is
   not a tool call at all. I can also say where it stops: schemas validate *shape*, not
   *sense*. I have watched a forced-mode model fabricate perfectly valid, perfectly
   meaningless arguments — so schema validation is necessary, never sufficient. Judgment stays
   with the model; policy stays with the loop.
3. **"How does a tool result get back to the model, and what goes wrong there?"** — As a
   dedicated tool-role turn in the next request's transcript: you re-append the model's own
   function-call turn, then one `function_response` part per call. The classic bug is
   dropping either half — then the model can't connect what it asked to what it got, or never
   sees the result at all and just repeats itself (my Day 3 goldfish demo shows that
   deterministically). And results are a list because calls are a list — parallel calling
   means the plumbing handles several per turn from day one.
