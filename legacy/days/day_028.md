## 1 · 🎬 Where we are — the story so far

Sutra has three skills and they work. But "works with three" is not a design — it is a
lucky small number. The support desk you are building toward (the master plan's Phase 8
graph, the Phase 11 nightly jobs) will accumulate skills the way every real desk
accumulates procedures: steadily, forever. Ten skills. Twenty. At what point does the
shelf itself become the problem?

Yesterday you learned to write one good binder. Today you learn to run a good
**library** — because the failure modes of one skill (vague label, missing stove) and
the failure modes of *many* skills (bloated index, colliding labels, mush routing) are
different animals, and only one of them shows up in demos.

## 3 · 📚 Concepts

### SK-09 — The ladder has a price list

The spec's three rungs are not just a loading order — they are three *budgets*, and each
is spent at a different frequency:

| Rung | Spent | Frequency | Design rule that follows |
| --- | --- | --- | --- |
| L1 (name+description) | ~100 tokens × **every** skill | **every call**, forever | the shelf index is the only per-call rent — keep descriptions sharp, not long |
| L2 (body) | body size | per activation | body < 5000 tokens; steps + one example + edges, nothing else |
| L3 (resources) | file size | per fetch | split by *question* ("severity?" → rubric file), so a fetch pulls only its answer |

The multiplication is what people miss. A lazy 300-token description feels free — until
it is one of twenty, and your agent pays 6,000 tokens of *index* on every "hello". On
our 5 RPM / free-tier budget (Day 24's ledger counts every one of these tokens), L1
discipline is literally uptime.

And the rungs trade against each other — that is the design part. A fat body that
answers every question nobody asked should shed weight *downward* into L3 files fetched
rarely; a description that has swollen to summarize the whole body should shed weight
*downward* into the body. Weight flows down the ladder; only triggers stay on top.

💡 **Mental model: L1 is rent, L2 is a delivery fee, L3 is pay-per-item. Design moves
cost down the ladder — from rent you always pay toward items you rarely need.**

### SK-10 — Twenty binders, one glance: descriptions are a routing table

At Day 26 scale, a description had one job: *match or not*. At library scale it has a
harder one: **match better than every other label on the shelf**. The model chooses
where to reach with one glance across all spines — so the spines compete.

Think of the label set as a routing table, and audit it the way you'd audit routes:

- **Coverage** — every task you expect has *some* label that matches it.
- **Orthogonality** — no task matches two labels equally well. The killers are shared
  filler words ("helps with support tasks…") that appear on every spine and mean
  nothing on any of them.
- **Specificity beats breadth** — "severity, diagnosis, first reply, ticket id" routes;
  "handles tickets and communication and workflows" is mush.

The test is empirical, and cheap: one crowded-shelf run (step 4) tells you more than an
hour of squinting at YAML. Routing quality is *observable* — the `load_skill` calls in
the events ARE the routing decision, printed.

### SK-11 — Skill, tool, persona, or reference? The decision table

Four containers now exist for "something Sutra should know or do." Choosing wrong is
the root cause behind most messy agents — so choose by property, not by habit:

| It is… | Put it in a… | Because | Example from our repo |
| --- | --- | --- | --- |
| an *action* with typed inputs, executed by code | **tool** | the model must request it, never imitate it | `lookup_ticket` (Day 10) |
| a *procedure*: multi-step know-how for a kind of task | **skill** | needed sometimes; loads on demand; reviewable prose | `ticket-triage` (Day 27) |
| an *identity or standing value*, true on every call | **persona** (instruction) | it must never be skipped; it's cheap and constant | "never invent ticket contents" |
| *long detail* consulted occasionally within a procedure | **reference (L3)** | pay-per-item beats rent | `severity-rubric.md` |

Two boundary cases people argue about, settled with a question each:

- *Procedure that must ALWAYS run?* (e.g. "check honesty before sending") — that
  frequency makes it persona-or-callback, not a skill: skills load on decision, and
  "always" must not depend on a decision. (Enforcement beats prose: Day 13's
  `guard_tools` veto is the hard version — recall the ANY-mode lesson from Day 4:
  policy belongs where enforcement is real.)
- *Knowledge with no steps at all?* (e.g. the KB itself) — that is *data*, and data
  belongs behind a tool (`search_kb`) or, at scale, retrieval (Day 49) — not pasted
  into a skill body that would instantly bust its L2 budget.

```python
from google import genai                          # count_tokens lives here (Day 19)
from google.adk.skills import models              # in-code skills (Day 26)


def _tokens(client: genai.Client, text: str) -> int:
    """Count tokens the way the real model would.

    Args:
        client: an authenticated genai client.
        text: any string.

    Returns:
        The token count as an int.

    Example:
        >>> _tokens(client, "hello desk")   # small numbers for small strings
        2
    """
    resp = client.models.count_tokens(            # Day 19's scale, reused
        model=PRIMARY_MODEL, contents=text
    )
    return resp.total_tokens                      # one honest number


def demo_measure() -> None:
    """Price every rung of every production skill. Near-zero quota.

    Usage:  python -m sutra.skill_agent measure
    """
    client = genai.Client()                       # needs GOOGLE_API_KEY (Day 1)
    shelf_total = 0                               # the always-paid rent (L1)
    print(f"{'skill':<18}{'L1':>6}{'L2':>7}  L3 files")
    for folder in sorted(SKILLS_DIR.iterdir()):   # every binder on the shelf
        if not (folder / "SKILL.md").exists():    # skip strays
            continue
        s = load_skill_from_dir(folder)           # parse it
        l1 = _tokens(client,                      # the spine: name + description
                     s.frontmatter.name + " " + s.frontmatter.description)
        l2 = _tokens(client, s.instructions)      # the body: paid per activation
        shelf_total += l1                         # rent accumulates PER SKILL
        print(f"{s.frontmatter.name:<18}{l1:>6}{l2:>7}  "
              f"{[p.name for p in folder.rglob('*') if p.is_file() and p.name != 'SKILL.md']}")
    print(f"\nL1 rent for the whole shelf, paid on EVERY call: ~{shelf_total} tokens")
```

```python
def _decoys(labels: list[tuple[str, str]]) -> list[models.Skill]:
```

## 5 · 💥 Failure lab — death by a thousand helpful labels

> 🎬 **The scene:** months from now. Every time someone automates a procedure, they add
> a skill — each one individually fine, each description written in a hurry, most of
> them starting "Helps with…". The shelf hits twenty. Users report the desk got slower,
> dumber, and weirdly random about which procedure it follows.
> 😬 **The naive fix:** prompt harder — "Carefully consider ALL available skills and
> choose the most appropriate one!" Maybe raise the model's thinking budget.
> 💥 **Why it fails:** you watched the mechanism in miniature today. Routing runs on
> one glance across the spines. Twenty near-identical labels give the glance nothing
> to grip: the choice degrades toward a coin-flip (`crowd` showed you wrong-loads and
> load-everything both). The prompt fix makes the *deliberation* longer, not the
> *information* better — the labels still don't distinguish the binders. Meanwhile the
> L1 rent has grown to thousands of tokens on every call including "hello", and each
> misroute pays an L2 delivery fee for a binder that gets ignored. Slower, dumber,
> random: all three symptoms, one root cause.
> 💡 **The insight:** **a skill library is a routing table plus a rent bill, and both
> are design artifacts — neither can be prompted into health.** Label hygiene
> (orthogonal, task-worded, filler-free) fixes routing; ladder hygiene (weight flows
> down) fixes rent. Both are checkable: the events show the routing, `measure` shows
> the rent — which is why Day 30 puts a description-quality check into the test suite
> and Day 31 wires the shelf into `make check`.

Observed today: `crowd` misrouting (logged) vs `crowd2` first-try routing — same
question, same agent, better labels.

## 6 · 🎤 Interview corner

1. **"How does an agent with many skills stay fast and cheap?"** — Progressive
   disclosure, treated as a budget rather than a slogan. Each rung has a price and a
   frequency: L1 name+description (~100 tokens/skill) is rent on *every* call; L2 body
   is paid per activation; L3 files per fetch. Design moves weight down the ladder —
   sharp short labels up top, lean step bodies, detail split into per-question
   reference files. I keep real `count_tokens` numbers on the shelf and can show the
   L2 drop from one refactor with unchanged behavior — measured, not vibed.
2. **"What goes wrong when skills scale, and how do you catch it?"** — Two compounding
   failures: index bloat (rent grows linearly with skill count) and label collision
   (near-identical descriptions turn routing into a coin-flip — I've reproduced
   wrong-skill loads with six mushy decoys and fixed them by rewriting labels alone).
   Both are observable: token counts for the rent, `load_skill` calls in the event
   stream for the routing. So both live in CI — lint the labels' shape, watch the
   events in tests — instead of in postmortems.
3. **"Skill, tool, or system prompt — how do you choose?"** — By property: actions
   with typed inputs are tools (the model requests, code executes); sometimes-needed
   procedures are skills (load on demand, reviewable prose); always-true identity and
   safety rules are persona — and the safety-critical subset gets *enforced* in
   callbacks, because "always" must not depend on a model's routing decision. Long
   detail inside a procedure goes to L3 references. The frequency question — every
   call, or some calls? — settles most arguments in one line.
