## 3 · 📚 Concepts

### ADK-19 — Session state: the desk's sticky notes

**The support-desk story.** Watch a good human agent work a ticket. The *conversation* with
the customer is one thing — but around it, the agent keeps structured scraps:

- **sticky notes on this ticket's folder** — "severity: high", "already tried reboot";
- **the customer's file card** — "Priya · prefers short answers · timezone IST";
- **the company handbook on the shelf** — "refund window: 30 days" (same for every customer);
- **a scratch pad** — quick arithmetic, thrown in the shredder at the end of the task.

Nobody writes "severity: high" as a paragraph in the middle of the chat log and hopes to
find it later by re-reading everything. Structured facts get structured homes. That is
session state.

| Support desk | Our system | Technical name |
| --- | --- | --- |
| Sticky notes on the ticket folder | Facts for *this* conversation | state, **no prefix** |
| The customer's file card | Facts about *this user*, any conversation | state, **`user:`** prefix |
| The company handbook | Facts for *everyone* | state, **`app:`** prefix |
| The scratch pad → shredder | Facts for *this one invocation* | state, **`temp:`** prefix |

💡 **Mental model: the transcript is a story; state is a form stapled to it.** Stories are
for the model to read. Forms are for your code to read — O(1), typed-ish, and cheap.

**What state actually is:** a dict-like object living on the session
(`session.state`), holding small, serializable values — strings, numbers, booleans, small
lists/dicts. Not objects, not file contents (files are tomorrow's topic: artifacts), not
secrets (those stay in `.env`, always).

#### The three safe ways to write it

ADK is strict about *how* state changes, and the reason is one word: **events**. Day 7 taught
that everything that happens in a run is an event, appended to the session's history. State
changes ride *inside* events (as a `state_delta`), so the history stays a complete, replayable
record (Principle 12: everything is a trace). Any write path that skips the event stream is
therefore a lie waiting to be discovered. The three honest paths:

1. **Inside a tool or callback: `context.state["k"] = v`.** Both `ToolContext` (Day 11) and
   `CallbackContext` (Day 13) carry `.state`. You just assign. The framework collects your
   writes into the current event's `state_delta` automatically. This is the everyday path.
2. **On the agent: `output_key="last_triage"`.** One argument, and the agent's final text
   reply is *also* saved to that state key. Zero plumbing — perfect for "the answer of step A
   is an input of step B" pipelines (the Workflow Runtime in Phase 8 leans on this hard).
3. **From the outside: `EventActions(state_delta={…}) → append_event(…)`.** When no agent is
   running — a script, a nightly job, an intake process — you build a small event by hand
   whose only cargo is the state change, and append it through the session service. It looks
   ceremonial, but notice what you get: the change is *in the history*, timestamped and
   attributed, like every other fact.

And the forbidden path, straight from the docs: **fetch a session, then write on it**
(`retrieved_session.state["k"] = v`). It feels natural. It "works" in the in-memory service
just often enough to betray you later: the write bypasses the event history, persistent
services may never save it, and two concurrent updates can race. The failure lab makes this
concrete today, on purpose, so you never debug it by surprise in Phase 7.

#### State talks back: `{key}` templating

One more wire closes the loop: `instruction="… The user prefers {user:reply_style} answers."`
— ADK fills `{…}` placeholders from state before the model sees the prompt. So state is not
just *written* by the conversation; it *steers* the next turn. (That is exactly how the
customer's file card changes how a human agent talks.)

### ADK-20 — Scopes & lifetimes: knowing when a key dies

Same dict, four lifetimes — chosen **by the key's name alone**:

| Prefix | Scope | Dies when… | Sutra example |
| --- | --- | --- | --- |
| *(none)* | this session | the session is deleted (or the in-memory service stops) | `severity`, `ticket_id` under triage |
| `user:` | this user, all their sessions | the user's data is deleted | `user:reply_style`, `user:name` |
| `app:` | the whole app, all users | the app's data is deleted | `app:refund_window_days` |
| `temp:` | this **invocation** only | the invocation ends — *never* persisted | `temp:raw_search_json` between two tools |

Two words need pinning, because the lifetimes hang on them:

- **Session** — the whole conversation container (Day 8): many turns, one user, one thread.
- **Invocation** — *one* press of the doorbell: from a user message arriving to Sutra's final
  answer for that message, including every tool call in between. A session holds many
  invocations. So `temp:` is narrower than "this session" — it is "this one question".

💡 **Mental model: the prefix is not decoration — it is the lifetime, machine-enforced.**
Naming a key `user:reply_style` doesn't *label* it as user data; it *makes* it user data.

**Why `temp:` exists at all** (it looks useless until it saves you): tools often need to hand
each other bulky intermediates — a raw JSON blob from `search_kb` that a summarizer tool eats
one step later. Put that in plain state and it gets persisted, forever, in every snapshot of
the session — cost and clutter with zero future value. `temp:` says: *pass it, then shred it.*

**A quiet warning about the in-memory service:** with Day 8's `InMemorySessionService`,
*everything* dies when the process exits — even `user:` and `app:` keys. The scopes still
behave correctly *relative to each other* (new session ≠ new process!), and that is what we
demo today. Real persistence — `DatabaseSessionService` — is Day 47's job. Today you learn
the semantics; Phase 7 gives them a disk.

Create `sutra/state_lab.py` with the listing below. Read the shape first: one tiny

```python
"""Day 17 — session state: prefixes, scopes, lifetimes.

One tool writes four state keys, one per scope (none/user:/app:/temp:),
so we can watch exactly which keys survive a new session and which die
with the invocation. output_key and append_event round out the three
safe write paths. Persistence to disk is deliberately NOT today's topic
(Day 47 brings DatabaseSessionService).

Importable with no side effects. Run demos from the repo root:

    python -m sutra.state_lab scopes     # the four lifetimes, side by side
    python -m sutra.state_lab outputkey  # the agent's answer lands in state
    python -m sutra.state_lab delta      # a state write with NO model call
    python -m sutra.state_lab lost       # failure lab: the forbidden write
"""
from __future__ import annotations

import asyncio                                   # ADK's runner API is async
import sys
import time

from google.adk.agents import Agent              # same class as Day 5
from google.adk.events import Event, EventActions    # for the manual write path
from google.adk.runners import Runner            # Day 8's programmatic runner
from google.adk.sessions import InMemorySessionService  # Day 8's session store
from google.genai import types                   # user message Content parts

from sutra.config import load_env                # .env loader (Day 1)

APP = "sutra"                                    # one app name, used everywhere today


def remember_triage(severity: str, tool_context) -> dict:
    """Record a triage decision into state — one key per scope, on purpose.

    This tool exists to make lifetimes VISIBLE, so it writes the same
    fact at four different scopes. Real tools write each fact once, at
    the one scope where it belongs.

    Args:
        severity: the triage severity to record, e.g. "high".
        tool_context: injected by ADK (Day 11) — carries .state.

    Returns:
        A confirmation dict (tools return dicts — Day 10 house rule).

    Example:
        Called by the model as remember_triage(severity="high").
        After the call, state has: severity, user:last_severity,
        app:tickets_triaged, temp:debug_note.
    """
    state = tool_context.state                   # the dict-like state view
    state["severity"] = severity                 # no prefix  -> this session only
    state["user:last_severity"] = severity       # user:      -> follows this USER
    count = state.get("app:tickets_triaged", 0)  # app:       -> shared by everyone
    state["app:tickets_triaged"] = count + 1     # ...so it works as a global counter
    state["temp:debug_note"] = f"triaged at {time.time():.0f}"  # temp: -> dies with the invocation
    return {"status": "recorded", "severity": severity}


# The lab agent: one tool, plus output_key so its final TEXT also lands
# in state (write path #2) without any plumbing.
state_agent = Agent(
    name="sutra_state_lab",
    model="gemini-3.5-flash",                    # pinned — never the default (ADK-73)
    description="Triage lab agent that records decisions into session state.",
    instruction=(
        "You are Sutra's triage assistant. When the user reports a problem, "
        "decide a severity (low, medium, or high), call remember_triage with "
        "it, then answer in ONE short sentence naming the severity."
    ),
    tools=[remember_triage],
    output_key="last_triage",                    # final reply text -> state["last_triage"]
)


async def _ask(runner: Runner, service: InMemorySessionService,
               user_id: str, session_id: str, text: str) -> None:
    """Send one user message through the runner and print the final reply.

    Args:
        runner: a Runner already wired to state_agent and the service.
        service: the session service (only passed for symmetry/clarity).
        user_id: which user is speaking (scopes care about this!).
        session_id: which conversation this belongs to.
        text: the user's message.

    Example:
        >>> await _ask(runner, service, "priya", "s1", "Checkout crashes!")
        reply: Severity high — checkout crash affects payments.
    """
    message = types.Content(role="user", parts=[types.Part(text=text)])
    # run_async yields events as they happen (trap #3: yield, don't collect).
    async for event in runner.run_async(
        user_id=user_id, session_id=session_id, new_message=message
    ):
        if event.is_final_response() and event.content:      # only print the end
            print("reply:", event.content.parts[0].text.strip())


def _peek(service: InMemorySessionService, user_id: str, session_id: str) -> None:
    """Print the interesting state keys of one session, prefix by prefix.

    Reading state OUTSIDE a run is fine — the rule is never to WRITE on a
    fetched session (see the failure lab).
    """
    session = asyncio.run(
        service.get_session(app_name=APP, user_id=user_id, session_id=session_id)
    )
    state = session.state                        # read-only view for us
    print(f"  state of {user_id}/{session_id}:")
    for key in ("severity", "user:last_severity", "app:tickets_triaged",
                "temp:debug_note", "last_triage"):
        # .get so missing keys print as None instead of crashing:
        print(f"    {key!r:26} = {state.get(key)!r}")


def demo_scopes() -> None:
    """The four lifetimes, made visible across two sessions and two users.

    Usage:  python -m sutra.state_lab scopes    (~3 model calls)
    """
    service = InMemorySessionService()
    runner = Runner(agent=state_agent, app_name=APP, session_service=service)

    # Session 1, user priya: one triage happens.
    asyncio.run(service.create_session(app_name=APP, user_id="priya", session_id="s1"))
    asyncio.run(_ask(runner, service, "priya", "s1",
                     "Users report the checkout page crashes on submit."))
    _peek(service, "priya", "s1")                # expect: ALL four keys? read on…

    # Session 2, SAME user, brand-new conversation:
    asyncio.run(service.create_session(app_name=APP, user_id="priya", session_id="s2"))
    asyncio.run(_ask(runner, service, "priya", "s2",
                     "Just checking in — any note on my last issue's severity?"))
    _peek(service, "priya", "s2")                # user:/app: survive; no-prefix doesn't

    # Session 3, DIFFERENT user:
    asyncio.run(service.create_session(app_name=APP, user_id="marco", session_id="s3"))
    asyncio.run(_ask(runner, service, "marco", "s3",
                     "The login page shows a typo in the title."))
    _peek(service, "marco", "s3")                # app: shared; user: is marco's own


def demo_outputkey() -> None:
    """Write path #2: the agent's final text lands in state, free of charge.

    Usage:  python -m sutra.state_lab outputkey   (~2 model calls)
    """
    service = InMemorySessionService()
    runner = Runner(agent=state_agent, app_name=APP, session_service=service)
    asyncio.run(service.create_session(app_name=APP, user_id="priya", session_id="s1"))
    asyncio.run(_ask(runner, service, "priya", "s1",
                     "Ticket 4521 again: users keep getting logged out."))
    _peek(service, "priya", "s1")                # last_triage = the whole final sentence


def demo_delta() -> None:
    """Write path #3: change state with NO agent and NO model call.

    This is how scripts and nightly jobs (Day 73) will touch state:
    a hand-built event whose only cargo is a state_delta — so the
    change still lands in the session HISTORY, not just the dict.

    Usage:  python -m sutra.state_lab delta       (0 model calls)
    """
    service = InMemorySessionService()
    asyncio.run(service.create_session(app_name=APP, user_id="priya", session_id="s1"))

    actions = EventActions(state_delta={
        "user:reply_style": "short",             # a preference, set by an intake form
        "app:kb_version": "2026-08-01",          # a global fact, set by an ops script
    })
    event = Event(
        invocation_id="manual-delta-1",          # any id; this is OUR event
        author="system",                         # who did it — auditability
        actions=actions,                         # the cargo: the state change
    )
    session = asyncio.run(
        service.get_session(app_name=APP, user_id="priya", session_id="s1")
    )
    asyncio.run(service.append_event(session, event))   # the ONE honest door
    _peek(service, "priya", "s1")                # both keys set; zero quota spent
    print("  (and the change is an EVENT in history — auditable, replayable)")


def demo_lost() -> None:
    """Failure lab: the forbidden write — see doc section 5 BEFORE running.

    Usage:  python -m sutra.state_lab lost        (~1 model call)
    """
    service = InMemorySessionService()
    runner = Runner(agent=state_agent, app_name=APP, session_service=service)
    asyncio.run(service.create_session(app_name=APP, user_id="priya", session_id="s1"))

    # THE ANTI-PATTERN, on purpose: fetch a session and write on it.
    session = asyncio.run(
        service.get_session(app_name=APP, user_id="priya", session_id="s1")
    )
    session.state["vip"] = True                  # ← no event. No delta. A ghost write.
    print("wrote vip=True on a FETCHED session object (the wrong way)…")

    # Now a real invocation happens (a real event gets appended):
    asyncio.run(_ask(runner, service, "priya", "s1",
                     "Payment page is fully down for everyone!"))

    # Re-fetch and look for our ghost:
    fresh = asyncio.run(
        service.get_session(app_name=APP, user_id="priya", session_id="s1")
    )
    print("vip after a real turn:", fresh.state.get("vip"))
    print("(whether it survived here or not: NO event records it — with a")
    print(" persistent service it is exactly the write that vanishes. §5.)")


def main() -> None:
    """Tiny demo dispatcher — the house pattern since Day 2."""
    demos = {"scopes": demo_scopes, "outputkey": demo_outputkey,
             "delta": demo_delta, "lost": demo_lost}
    name = sys.argv[1] if len(sys.argv) > 1 else "scopes"
    if name not in demos:
        print(f"usage: python -m sutra.state_lab [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()                                   # keys from .env, never from code
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the ghost write

> 🎬 **The scene:** you need to mark Priya as a VIP from an admin script. You already know
> `get_session` — so you fetch her session, set `session.state["vip"] = True`, and move on.
> A quick manual test with the in-memory service even shows the flag afterwards. Shipped.
> 😬 **The naive fix:** "it worked when I checked" — the classic words before every state bug.
> 💥 **Why it fails:** the object `get_session` returns is a **copy of the record, not a live
> handle**. Your write changed the copy in your hand. No event was created, so there is no
> `state_delta` in the history; a persistent `DatabaseSessionService` (Day 47) persists state
> *by applying event deltas* — your write simply never reaches the database. It can also be
> silently overwritten the moment a real event is appended, and two admin scripts doing this
> concurrently race each other. Cruelest of all: with `InMemorySessionService` it often
> *appears* to work, so the bug sleeps until the day you switch services — Phase 7 — and then
> "VIP flags randomly disappear, but only in production."
> 💡 **The insight:** **state changes are events, or they are lies.** There is one honest
> door — a delta inside an event (`context.state` in tools/callbacks does this for you;
> `append_event` does it for scripts). If a write didn't go through an event, the history
> doesn't know about it, and in this architecture *what the history doesn't know never
> happened* (Principle 12).

Observed today, not just asserted: `python -m sutra.state_lab lost` — one ghost write, zero
events recording it.

## 6 · 🎤 Interview corner

1. **"How does state differ from conversation history in an agent framework?"** — History is
   the prose record the model reads; state is a small structured store the *code* reads. In
   ADK they're joined at the hip: state changes travel as `state_delta`s inside events, so
   the history stays a complete audit log. I use history for language, state for facts —
   e.g. my triage agent stores `severity` in state via a tool, and later pipeline steps read
   it in O(1) instead of re-parsing prose with a second model call.
2. **"How do you scope agent memory to a user versus an app?"** — In ADK, by key naming:
   no prefix = this session, `user:` follows the user across sessions, `app:` is global,
   `temp:` dies with the invocation. The prefix isn't a label, it's machine-enforced
   lifetime. I demoed a counter in `app:` incrementing across three sessions and two users
   while each user's `user:` keys stayed private to them — all against the in-memory service,
   where the semantics hold even though nothing survives a process restart until you attach
   a persistent service.
3. **"What's a state-management bug you can describe mechanically?"** — The fetched-session
   write: mutating `session.state` on an object returned by the session service. It bypasses
   the event stream, so persistent backends never see a delta to apply; it races concurrent
   writers; and it *works* in memory, which is why it ships. I reproduced it deliberately —
   my fix rule is "state changes are events": tools write through `context.state`, scripts
   through `EventActions(state_delta=…) + append_event`.
