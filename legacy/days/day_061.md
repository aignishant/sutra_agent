## 1 · 🎬 Where we are — the story so far

Yesterday you learned the three words — replay, resume, idempotency — and proved the
smallest possible version: a two-step agent that "crashed" between steps and continued
without re-paying step one. Honest confession from yesterday's step 5, though: the crash
was a raised exception, and both runs happened moments apart in a warm terminal. A skeptic
would squint: *"Cute. Now pull the plug for real."*

Today is for the skeptic. Real kill — the process dies mid-node, PowerShell window and
all. Real distance — the resume happens in a *new* process that shares nothing with the
old one but a SQLite file. And a real workflow — not two toy steps, but a little version
of the triage flow with a custom node that has *its own* private progress to lose.

That last part is today's genuinely new idea. ADK checkpoints what it can see: the event
log, which workflow child finished, which tool call completed. But a **custom** node's
internal progress — "I had scored 2 of 4 duplicate candidates when the lights went out" —
is invisible to the framework unless the node *writes it down*. ADK gives your node a pen:
`ctx.set_agent_state(...)`. A node that uses the pen resumes mid-thought. A node that
doesn't starts its thought over — or worse, can't resume at all (the docs are blunt:
custom agents without state modifications don't support resume).

## 3 · 📚 Concepts

### ADK-44 — Checkpoints: three layers of "written down"

**The story.** You're reading a thick novel when the fire alarm rings. Three readers,
three outcomes. Reader A memorized nothing and marked nothing — afterwards they start at
page one. Reader B uses the bookmark the library glued into the spine — they reopen at
the right *chapter*. Reader C also scribbles a sticky note — "p. 214, the detective
suspects the gardener, I don't" — they reopen at the right chapter *and* the right
thought.

Sutra's runs have the same three layers, and it pays to keep them separate in your head:

| Layer | Who writes it | What it recovers | You've had it since |
| --- | --- | --- | --- |
| **The event log** | ADK, automatically, every yield | *what already happened* — the transcript, tool calls, results | Day 7 (events), durable on disk since Day 47 |
| **Workflow progress** | ADK, once `is_resumable=True` | *which children finished* — Sequential/Loop/Parallel and graph nodes skip completed work | Day 60 |
| **Custom node state** | **your node**, with the pen ADK hands it | *where the node was mid-thought* | today |

The pen, verified on adk.dev/runtime/resume/ (2026-08-19), is four moves:

```python
class DedupeState(BaseAgentState):        # 1) name the sticky note's fields
    scored: list[str] = []                #    (a pydantic-style state class)

state = self._load_agent_state(ctx, DedupeState)   # 2) on entry: read the note
                                                   #    (fresh run -> defaults)
ctx.set_agent_state(self.name, agent_state=state)  # 3) after real progress: rewrite it
ctx.set_agent_state(self.name, end_of_agent=True)  # 4) done: mark the chapter finished
```

💡 **Mental model: ADK checkpoints the *conversation* for free; only you can checkpoint
a *thought*.** If your custom node holds progress in a local variable, that progress is
Reader A. Local variables are where checkpoints go to die.

**How often to write the note?** After every unit of work that is *expensive or
effect-ful* — one scored candidate, one fetched page — and not more often. Each
checkpoint is an event in the log: too rare and a crash re-does real work (at-least-once
makes that safe but wasteful — you re-pay model calls out of 5 RPM); too frequent and
the log drowns in bookkeeping (Day 20's compaction lesson applies to your own noise too).

### ADK-45 — Pause & resume: the invocation is the unit of recovery

Words matter here, because three id-like things float around a run:

| Thing | Names | Lifetime |
| --- | --- | --- |
| the conversation | `(app_name, user_id, session_id)` | weeks — Day 8's bowls |
| **one run through the agent** | `invocation_id` | one user turn... *unless it's interrupted* |
| one model/tool step | event id | milliseconds |

Resume operates on the middle one. An interrupted invocation is not dead — it is
**paused**, whether the pause was chosen (a human question — Days 62–64) or violent
(Ctrl-C, OOM, battery). The recovery recipe is the same for both, which is the deep
reason this phase pairs durability with humans:

1. the session's events (and your agent-state notes) are already on disk —
   `DatabaseSessionService` wrote them as they happened;
2. a *fresh* process builds the same `App` (same workflow — remember the caveat:
   changing the workflow between crash and resume is unsupported; ship the code change
   *after* draining paused runs, or accept starting those runs over);
3. `runner.run_async(user_id=..., session_id=..., invocation_id=<the old one>)` —
   ADK reinstates completed events, skips finished children, hands your custom node its
   sticky note, and the run walks on.

Note what is *absent* from the recipe: the old process. Nothing survived it except rows
in SQLite. That is the whole trick, and it's why step 6 of the build makes you watch the
recipe fail with `InMemorySessionService` — resumability config without durable storage
is a bookmark glued into a book you burned.

## 5 · 💥 Failure lab — the deploy that ate the paused runs

> 🎬 **The scene:** Phase 13 future-you deploys Sutra weekly. This Tuesday, three triage
> runs sit paused overnight waiting for morning approvals (Day 64's gates). The Tuesday
> deploy also renames a graph node and inserts a validation station before review —
> routine growth. Ship it.
> 😬 **The naive fix:** deploy, then resume the three paused invocations into the new
> code. They're "just rows", the new process will read them fine.
> 💥 **Why it fails:** resume rebuilds the run by *replaying the old log against the new
> workflow* — and the docs say plainly that a modified workflow is unsupported territory.
> The old events name stations the new graph spells differently; completed-child
> bookkeeping points at a child that no longer exists at that position; your renamed
> node's sticky notes are filed under the old name, so the "same" node starts fresh
> while the runtime believes it finished. Best case: a loud crash. Worst case: a quiet
> half-resume that skips the *new* validation station because the old log says the phase
> after it already completed. Silent skips of safety stations — that's the nightmare
> variant.
> 💡 **The insight:** **a paused invocation is a contract between a log and the exact
> code that wrote it.** Deploys must drain first: let paused runs finish on the old
> code, or explicitly restart them on the new (their idempotency keys — Day 60 — make
> the restart safe). Version the workflow, refuse resumes across versions, and make the
> refusal loud. Kubernetes people call the pattern drain-before-upgrade; Day 88 will
> meet it again with prettier tooling.

Rehearsed in miniature today as step 6's cousin: the contract also breaks when the log
simply isn't there.

## 6 · 🎤 Interview corner

1. **"Your agent crashed 40 minutes into an hour-long workflow. Walk me through
   recovery."** — Nothing to salvage from the process; everything from the log. Sessions
   are event streams in SQLite (server-grade stores swap in without code changes), so a
   fresh process rebuilds the same app and re-runs with the original `invocation_id`.
   The framework reinstates completed events and skips finished workflow children; my
   custom nodes additionally checkpoint internal progress through the framework's
   agent-state API, so a node that was 2-of-4 through a scoring list resumes at item 3.
   The step that was in flight when we died re-executes — at-least-once — which is safe
   because every write in the system carries an idempotency key. I've run exactly this
   drill: Ctrl-C mid-node, resume in a new terminal, welded output.
2. **"What state would you checkpoint, and what would you deliberately not?"** —
   Checkpoint progress that is expensive to recompute or dangerous to redo: which items
   are already processed, handles returned by external systems, accumulated
   decisions. Don't checkpoint what the event log already implies (the transcript), or
   derived caches (recompute beats stale), and never secrets. Granularity follows cost:
   one checkpoint per paid unit of work. Checkpointing more often than you do real work
   just turns your log into noise.
3. **"Why is 'pause for a human' the same machinery as 'crashed'?"** — Both end the
   process's involvement mid-invocation and both recover by replaying the log into a
   fresh runner. The only difference is intent: a crash pauses at a random line, a
   human gate pauses at a chosen one with a question attached. Building the violent case
   first means the polite case comes free — which is exactly the order my project did it.
