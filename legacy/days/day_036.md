## 1 · 🎬 Where we are — the story so far

Every request `sutra-mcp` has ever answered finished in milliseconds: dict lookups,
string searches. That luck is about to run out. Phase 7 will build an embedding index
over the whole ticket archive (Day 49), and "re-index the archive" is not a
milliseconds job — it is a *minutes* job. Day 73's nightly run makes it routine.

And minutes-long work breaks the beautiful machine we built, in a specific way: a
request that blocks for three minutes holds its HTTP response open for three minutes.
Client timeouts fire. Proxies give up. And if anything drops the connection at minute
two — the work is *gone*, with no way to ask "how far did you get?" because the only
name that work ever had was a request id that just died with its stream.

Yesterday's shop metaphor knows this problem. A dry cleaner does not make you stand at
the counter while your suit is cleaned. They hand you a **claim ticket** and say "come
back". Today `sutra-mcp` learns to hand out claim tickets — and you will meet the exact
mechanism the 2026 protocol standardized for them.

## 3 · 📚 Concepts

### MCP-10 — Progress: the voice through the workshop door

While a request *is* still running, MCP has a narrow channel for "still alive, 60%
done": **`notifications/progress`**, sent on the response stream of that very request
(on Streamable HTTP, the request-scoped SSE stream; Day 33's table said replies are
"JSON *or* a stream" — this is what the stream is *for*). Three properties matter:

1. **Request-scoped.** Progress for request 7 rides only on request 7's stream — never
   on `subscriptions/listen`, never on some global channel. When the stream closes, that
   voice is gone.
2. **Advisory.** Progress is narration, not state. Nothing you can redeem later.
3. **Dies with the connection.** Which is precisely the limitation: the client that
   disconnects loses both the progress *and* the result.

So progress answers "is it alive?" but not "can I come back?" — the dry cleaner
shouting "halfway!" through the workshop door is nice, but it is **not** a claim ticket.
For work that must outlive the conversation, we need the next idea. 🅿️ *SDK note:*
whether your resolved SDK version exposes a progress-reporting helper inside tool
handlers is part of today's TODO check; the concept stands either way, and our build gets
its progress through the handle instead — deliberately.

### MCP-14 — The claim ticket: state as a handle in the payload

Recite Day 32's rule: *the 2026 protocol holds no state in the connection.* So where
does the re-index job live while no request is running? **In the server's world, filed
under a name the server invented** — and that name travels to the client *inside an
ordinary result*, coming back *inside ordinary arguments*. That is SEP-2567, whole:

| Dry cleaner | Our system | The rule it encodes |
| --- | --- | --- |
| You drop off the suit | `reindex_start()` returns in <1 s | starting is cheap; the work continues elsewhere |
| The claim ticket, numbered by THE SHOP | `{"job_id": "rx-7f3a9c"}` — server-minted, opaque | the client never fabricates or interprets a handle |
| "Ticket 7f3a, ready yet?" | `reindex_status(job_id="rx-7f3a9c")` | state rides **in the payload**, as a plain argument |
| The rack in the back room | `data/mcp_tasks.json` (today) — a shared store *behind* the server | the **protocol** stays stateless; the *application* keeps state in a store any instance can reach |

That last row deserves a hard stare, because it resolves an apparent paradox: "stateless
server" never meant "amnesiac application". It means state lives **behind** the request
handler in a store that *any replica* could consult — today a JSON file, in production a
database or Redis. Three Cloud-Run instances of `sutra-mcp` (Day 43) can all redeem
`rx-7f3a9c`, because the rack is shared and the ticket says everything needed to find
the suit. Statelessness is about *where memory lives*, not *whether* it lives.

💡 **Mental model: the connection is the conversation; the handle is the claim ticket.
Conversations end; claim tickets are honored by whoever is at the counter tomorrow.**

### MCP-28 — The Tasks extension: your claim ticket, standardized

What you build by hand in Step 3, the ecosystem standardized as the **Tasks extension**
(`io.modelcontextprotocol/tasks`) — so any host can handle any server's long jobs
without bespoke start/status tool pairs. The moving parts, from the live extension docs:

1. **Negotiation, per-request.** The client declares the extension inside
   `_meta.io.modelcontextprotocol/clientCapabilities.extensions`; the server advertises
   it via `server/discover`. A server MUST NOT hand a task to a client that didn't
   declare support — no surprise claim tickets.
2. **Creation is server-directed.** The client just calls the tool; *the server* decides
   this run will be long and answers with a `CreateTaskResult`
   (`resultType: "task"`) carrying `taskId`, initial status, `ttlMs` (how long the
   ticket is honored) and `pollIntervalMs` (how often to ask). The task is durably
   created *before* the response is sent.
3. **One lifecycle, five statuses.** `working` → possibly `input_required` (the job
   needs a human/model answer mid-flight — Day 37's elicitation, riding inside a task) →
   terminal `completed` (with the `result` the original call would have returned) /
   `failed` (with the JSON-RPC `error`) / `cancelled`.
4. **Three verbs.** `tasks/get` polls (respecting `pollIntervalMs`); `tasks/update`
   delivers the client's answers when status is `input_required`; `tasks/cancel` is
   **cooperative** — an intent the server acknowledges but need not obey (the suit may
   already be sewn). `tasks/list` existed in the experimental era and was *removed* —
   dating servers by which verbs they speak is a Day 38 skill.
5. **Optional push.** Servers may emit `notifications/tasks` over `subscriptions/listen`
   so well-connected clients skip polling; polling stays the universal fallback.

Addendum 01's example was already right: *"re-index the whole ticket archive" returns
`task_abc123` immediately; Sutra checks progress every 10 s.* Today you build that
behavior; the extension is its passport for strangers. 🅿️ The extension *wire shapes*
stay map-level today exactly where SDK support is unverified — the honest line between
"built" and "read" runs through your Step-TODO result, and the doc asks you to record it.

**Step 3 — The claim ticket.** Append the right shape:

```python
def _load_tasks() -> dict:
    """Read the shared task rack (empty dict if none yet).

    Returns:
        Mapping of job_id -> {"status", "done", "total", "result"}.

    Example:
        >>> _load_tasks()
        {}
    """
    if TASKS_FILE.exists():
        return json.loads(TASKS_FILE.read_text(encoding="utf-8"))
    return {}


def _save_tasks(tasks: dict) -> None:
    """Write the rack back. One writer today; a real store handles races.

    Args:
        tasks: the full mapping to persist.
    """
    TASKS_FILE.parent.mkdir(parents=True, exist_ok=True)
    TASKS_FILE.write_text(json.dumps(tasks, indent=2), encoding="utf-8")


@mcp.tool()
def reindex_start() -> dict:
    """Start re-indexing the archive; return AT ONCE with a claim ticket.

    Returns:
        {"job_id": <server-minted opaque handle>, "status": "working",
         "poll_after_s": 2} - the handle is the ONLY thing a client needs
        to remember; it is meaningful to the server alone (SEP-2567).

    Example:
        >>> reindex_start()
        {'job_id': 'rx-7f3a9c...', 'status': 'working', 'poll_after_s': 2}
    """
    job_id = f"rx-{uuid.uuid4().hex[:8]}"       # WE mint it; opaque to clients
    tasks = _load_tasks()
    tasks[job_id] = {"status": "working", "done": 0,
                     "total": REINDEX_STEPS, "result": None}
    _save_tasks(tasks)                          # durably created BEFORE returning
    return {"job_id": job_id, "status": "working", "poll_after_s": 2}
    # Honesty note: the WORK advances inside reindex_status below (each poll
    # processes a slice). A production server would run a worker thread/queue;
    # we fold worker into poller so the whole mechanism stays visible in two
    # functions - the protocol shapes are identical either way.


@mcp.tool()
def reindex_status(job_id: str) -> dict:
    """Redeem a claim ticket: report progress; hand over the result when done.

    Args:
        job_id: the handle reindex_start returned. Unknown handles get a
            clear error status - a program-facing miss (Day 35's lesson).

    Returns:
        {"status": "working", "done": n, "total": N}  while running, or
        {"status": "completed", "result": ...}        when finished.

    Example:
        >>> t = reindex_start()
        >>> reindex_status(job_id=t["job_id"])
        {'status': 'working', 'done': 5, 'total': 15}
    """
    tasks = _load_tasks()
    if job_id not in tasks:                     # expired/foreign ticket:
        return {"status": "failed",             # machine-readable, unambiguous
                "error": f"unknown job_id {job_id!r}"}
    job = tasks[job_id]
    if job["status"] == "working":              # advance one slice per poll
        job["done"] = min(job["done"] + 5, job["total"])
        if job["done"] >= job["total"]:
            job["status"] = "completed"
            job["result"] = f"Re-indexed {job['total']}/{job['total']} chunks."
        _save_tasks(tasks)
    if job["status"] == "completed":
        return {"status": "completed", "result": job["result"]}
    return {"status": "working", "done": job["done"], "total": job["total"]}
```

## 5 · 💥 Failure lab — "just raise the timeout"

> 🎬 **The scene:** Day 49 arrives; the real re-index takes four minutes. The blocking
> tool times out at sixty seconds.
> 😬 **The naive fix:** the oldest incantation in distributed systems — *raise the
> timeout.* Client to 300 s, proxy to 300 s, one more layer someone forgot, then 600 s
> "to be safe".
> 💥 **Why it fails, thrice:** (1) You cannot outbid every intermediary — some proxy,
> some LB idle rule, some laptop lid-close will always undercut you; the connection is a
> chain, and its timeout is the chain's weakest link. (2) Even when it holds, you've
> pinned one held-open stream per running job to specific processes — the sticky-session
> disease (Day 32) reinvented at the tool layer; replicas can't share jobs whose only
> identity is a live socket. (3) Worst: when the stream *does* break at minute three,
> the work has **no name** — nothing to poll, nothing to cancel, so the client retries
> and the server happily re-indexes *twice*, concurrently. A timeout bump converts
> "fails visibly" into "fails expensively".
> 💡 **The insight:** **any work that can outlive a connection must have a name that
> isn't the connection.** Hand out the name early (`reindex_start` returns in
> milliseconds), make it durable *before* answering (the extension mandates exactly
> this), redeem it from anywhere. Timeouts then stop being cliffs and become mere poll
> pacing. And the duplicated-work goblin gets its full exorcism — idempotency — on
> Day 60, where durable execution picks up tonight's claim ticket and runs with it.

Observed today, not just asserted: the frozen 15-second Inspector call in Step 2 versus
Step 5's Ctrl-C'd client whose job a *different server process* completed.

## 6 · 🎤 Interview corner

1. **"How do you handle a 4-minute operation behind a request/response protocol?"** —
   Never by holding the request open: some intermediary always times out first, and a
   broken stream means unnamed, unrecoverable, probably-duplicated work. I return a
   server-minted opaque handle immediately — durably persisted before the response — and
   expose a status operation that redeems it; progress notifications can narrate while a
   stream happens to live, but the handle is the source of truth. I've demonstrated the
   failure and the fix on my own MCP server: killed the client mid-job and redeemed the
   same handle from a fresh process. MCP standardizes this whole pattern as the Tasks
   extension — `resultType: "task"`, five statuses, `tasks/get|update|cancel`.
2. **"Doesn't storing task state break your 'stateless server' claim?"** — No, and the
   distinction is the whole design: *protocol*-stateless means no state lives in the
   connection or in per-client server memory — any replica can serve any request. The
   application state lives behind the handlers in a shared store keyed by the handle,
   exactly like a web app keeps orders in a database while its HTTP layer stays
   stateless. My claim ticket works on a server process that wasn't even alive when the
   job started — that's the proof the state is in the right place.
3. **"Walk me through the MCP Tasks extension lifecycle."** — Client opts in per-request
   via the extensions field of its `_meta` capabilities; server advertises support in
   `server/discover`; a server never returns a task to a non-declaring client. On a
   long call the server answers `CreateTaskResult` — `taskId`, `ttlMs`,
   `pollIntervalMs`, status `working`. Client polls `tasks/get`; a task needing a human
   or model answer flips to `input_required` and the client responds via `tasks/update`;
   `tasks/cancel` is cooperative intent, not a kill switch. Terminal states —
   `completed` carrying the original call's result, `failed` carrying the JSON-RPC
   error, `cancelled` — never change afterward. And a dating tip from the redesign:
   a server offering `tasks/result` or `tasks/list` is speaking the pre-2026
   experimental dialect.
