## 3 · 📚 Concepts

### SK-04 — Two ways to load a binder

**From disk** — the normal way, and ours:

```python
import pathlib
from google.adk.skills import load_skill_from_dir

hello = load_skill_from_dir(pathlib.Path("skills") / "hello-desk")
```

One call: reads `SKILL.md`, parses the frontmatter, discovers the resource files. The
folder you hand-validated yesterday is exactly what this function expects — the spec is
the contract between your editor and this loader.

**In code** — for skills that are generated or tested programmatically:

```python
from google.adk.skills import models

greeting = models.Skill(
    frontmatter=models.Frontmatter(name="greeting-skill",
                                   description="..."),
    instructions="Step 1: ...",
    resources=models.Resources(references={"hello.txt": "Hello!"}),
)
```

Same object either way — a `Skill` with frontmatter, instructions, resources. Disk is
for *authored, versioned* know-how (our case: skills live in the repo, Principle 2);
in-code is for tests and dynamic generation (we will use it exactly once, in Day 30's
test suite, to build throwaway skills without touching disk).

### SK-05 — How a skill reaches the model (the part worth staring at)

Here is the question that matters: when you give an agent ten skills, *what actually
enters the context window?* Not the ten bodies. The runtime injects only the **L1
index** — each skill's name and description — plus three small tools:

| Auto-tool | What it does | Ladder rung |
| --- | --- | --- |
| `load_skill` | fetch a skill's full `SKILL.md` instructions | L1 → **L2** |
| `load_skill_resource` | fetch one file from the skill's folder | L2 → **L3** |
| `run_skill_script` | execute a file from `scripts/` | L3, with consequences (Day 29 ⚠️) |

So "using a skill" is literally **function calling** — the same form-filling you built
by hand on Day 4. The model reads the shelf labels in its instructions, decides binder
`hello-desk` is relevant, and emits `load_skill(name="hello-desk")`. The runtime returns
the body as a tool result. Next turn, the model *has* the procedure and follows it.

💡 **Mental model: `SkillToolset` turns "knowing things" into "asking for things."
Knowledge stops being prompt payload and becomes a tool call — so it obeys every rule
you already know about tools: it shows in events, it can be logged, vetoed, counted,
and budgeted.** (Your Day 13 `guard_tools` veto and Day 14 `QuotaWatcherPlugin` meter
apply to skill loads *for free*. Sit with that for a second — that is composability
paying rent.)

Note what this design quietly implies: a skill only activates if the model *decides* to
call `load_skill`. The decision runs on the description — the shelf label. A weak label
means no call, silently. That is today's failure lab, and Day 28's design topic.

### ADK-24 — `SkillToolset`: the wiring

```python
from google.adk.tools import skill_toolset

toolset = skill_toolset.SkillToolset(
    skills=[hello],                 # the binders on this agent's shelf
    additional_tools=[...],         # optional: ordinary tools bundled alongside
)
agent = Agent(model=PRIMARY_MODEL, name="desk_agent", tools=[toolset])
```

Two design details deserve your attention:

1. **It is a toolset, not a tool** — the same `BaseToolset` idea you met on Day 15: one
   object that *contributes several tools* to the agent. The three auto-tools above are
   its contribution, plus whatever you pass in `additional_tools`.
2. **`additional_tools` bundles procedure with capability.** A skill that documents
   "how we triage" pairs naturally with the `lookup_ticket` tool the procedure calls.
   Shipping them in one toolset keeps know-how and capability next to each other —
   Day 27 uses this for real.

**Experimental means experimental.** The page says so, and our project rule for
experimental surfaces is: pin the version (done — PACKAGES.md), name the page you
checked (done — header), and re-verify at every phase gate (the freshness ritual).

```python
"""Day 26 — SkillToolset: the hello-desk binder reaches an agent.

Wires Day 25's hand-crafted skill into an ADK agent and shows, from the
event stream, that progressive disclosure is real: the model calls
load_skill (L2) and load_skill_resource (L3) instead of carrying the
binder's text on every request.

Importable with no side effects. Demos (run one at a time — 5 RPM lane):

    python -m sutra.skill_agent shelf   # zero quota: print the L1 index
    python -m sutra.skill_agent use     # watch load_skill fire, then the styled answer
    python -m sutra.skill_agent deep    # an L3 fetch: load_skill_resource
    python -m sutra.skill_agent miss    # failure lab: the vague shelf label
"""
from __future__ import annotations

import asyncio                                   # runner API is async (Day 8)
import pathlib
import sys

from google.adk.agents.llm_agent import Agent    # canonical import (Day 5)
from google.adk.runners import InMemoryRunner    # everything-in-memory runner (Day 8)
from google.adk.skills import load_skill_from_dir  # disk -> Skill object
from google.adk.tools import skill_toolset       # the toolset module
from google.genai import types                   # Content/Part, as always

from sutra.agent import PRIMARY_MODEL            # the ONE pinned model string (Day 5)
from sutra.config import load_env                # .env keys (Day 1)

SKILLS_DIR = pathlib.Path("skills")              # repo-root shelf for all binders


def make_desk_agent(description_override: str | None = None) -> Agent:
    """Build the demo agent with hello-desk on its shelf.

    Args:
        description_override: if given, replaces the skill's description —
            used ONLY by the `miss` failure-lab demo to show what a vague
            shelf label does. Normal callers pass nothing.

    Returns:
        An Agent whose tools=[SkillToolset(...)].

    Example:
        >>> agent = make_desk_agent()
        >>> agent.name
        'desk_agent'
    """
    skill = load_skill_from_dir(SKILLS_DIR / "hello-desk")  # parse the binder
    if description_override is not None:          # failure-lab hook:
        skill.frontmatter.description = description_override  # sabotage the label
    toolset = skill_toolset.SkillToolset(skills=[skill])  # shelf with one binder
    return Agent(
        model=PRIMARY_MODEL,                      # pinned, never defaulted (ADK-73)
        name="desk_agent",
        instruction=(                             # persona stays SHORT on purpose:
            "You are Sutra's support desk writer. "     # who you are
            "Follow any available skill that matches "  # the standing rule
            "the task before improvising."
        ),                                        # ...the know-how lives in the skill
        tools=[toolset],                          # the toolset contributes its 3 tools
    )


async def _run(agent: Agent, question: str) -> None:
    """Send one question; narrate every event so the ladder is visible.

    Args:
        agent: the agent to run.
        question: plain-text user message.

    Example:
        >>> asyncio.run(_run(make_desk_agent(), "Hi!"))   # prints CALL/FINAL lines
    """
    runner = InMemoryRunner(agent=agent)          # sessions + artifacts in memory
    session = await runner.session_service.create_session(
        app_name=runner.app_name, user_id="learner"
    )                                             # one throwaway session
    msg = types.Content(role="user", parts=[types.Part(text=question)])
    async for event in runner.run_async(
        user_id="learner", session_id=session.id, new_message=msg
    ):
        for call in event.get_function_calls():   # tool requests, 2.x accessor (Day 7)
            print(f"CALL: {call.name}({call.args})")   # load_skill shows up HERE
        if event.is_final_response() and event.content:
            print("FINAL:", event.content.parts[0].text)


def demo_shelf() -> None:
    """Zero-quota: load the binder and print exactly what L1 costs.

    Usage:  python -m sutra.skill_agent shelf     (0 model calls)
    """
    skill = load_skill_from_dir(SKILLS_DIR / "hello-desk")
    print("name       :", skill.frontmatter.name)         # the shelf label,
    print("description:", skill.frontmatter.description)  # ...all the model sees
    print("body chars :", len(skill.instructions))        # loaded ONLY on activation


def demo_use() -> None:
    """The headline: watch the model open the binder before answering.

    Usage:  python -m sutra.skill_agent use       (~2 model calls)
    """
    asyncio.run(_run(
        make_desk_agent(),
        "Write the opening line of a reply to Dana's ticket about being "
        "logged out. Use our house greeting style.",
    ))


def demo_deep() -> None:
    """Push to L3: a question whose answer lives in references/.

    Usage:  python -m sutra.skill_agent deep      (~2-3 model calls)
    """
    asyncio.run(_run(
        make_desk_agent(),
        "Dana's logout ticket was REOPENED. Greet her the way our "
        "reopened-ticket example shows.",
    ))


def demo_miss() -> None:
    """Failure lab: a vague shelf label — see doc section 5 first.

    Usage:  python -m sutra.skill_agent miss      (1 model call)
    """
    asyncio.run(_run(
        make_desk_agent(description_override="Helps with messages."),  # the sabotage
        "Write the opening line of a reply to Dana's ticket about being "
        "logged out. Use our house greeting style.",
    ))


def main() -> None:
    """Tiny demo dispatcher — the house pattern since Day 2."""
    demos = {"shelf": demo_shelf, "use": demo_use,
             "deep": demo_deep, "miss": demo_miss}
    name = sys.argv[1] if len(sys.argv) > 1 else "shelf"
    if name not in demos:
        print(f"usage: python -m sutra.skill_agent [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()                                    # keys from .env, never from code
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the binder nobody opens

> 🎬 **The scene:** you shipped the skill. It parses, it loads, `shelf` prints it
> proudly. Weeks later you notice replies ignoring the house style. The skill is
> *right there.*
> 😬 **The naive fix:** make the persona shout — "ALWAYS check your skills before
> answering!!" — and move on.
> 💥 **Why it fails:** you watched the mechanism today. Activation is a *model decision*
> made by reading shelf labels. `Helps with messages.` gives the model nothing to match
> against "write an opening line in our house greeting style" — so no `load_skill`
> call, no L2, no rules. And notice how the shouting fix backfires: if the model obeys
> it literally, it loads *every* skill on *every* task (you'll meet that failure at
> scale on Day 28); if it doesn't, you're back to silence. Worse, the failure is
> **invisible in every place you normally look**: no exception, no lint error, a
> perfectly fluent answer. Only the *event stream* shows the absence — the missing
> CALL line between question and FINAL.
> 💡 **The insight:** **a skill's description is load-bearing routing logic, not
> documentation — and absence-of-a-call is a failure class only observability can
> catch.** Write labels with the reader's *task words* in them ("greeting", "sign-off",
> "customer-facing reply"), and when a skill misbehaves, check the events for whether
> the binder was ever opened before you blame its contents. Every principle here is an
> old friend: Day 4 (the description is prompt engineering), Day 12 (Principle 12 —
> if it isn't observable, it didn't happen).

Observed today, not asserted: `use` shows the CALL line; `miss` — same body, sabotaged
label — shows none.

## 6 · 🎤 Interview corner

1. **"How do Agent Skills actually reach the model in ADK?"** — Through a toolset, not
   through the prompt. `SkillToolset` injects each skill's name+description (the L1
   index) and exposes three tools — `load_skill`, `load_skill_resource`,
   `run_skill_script`. Activation is the model *calling a tool* to fetch instructions,
   so skill usage rides the standard function-calling channel: it appears in events,
   and callbacks/plugins can log, veto, or meter it like any other tool call. I've
   watched the `load_skill` call in the event stream — and diagnosed a skill that never
   fired by the *absence* of that call.
2. **"When would you define a skill in code versus loading from disk?"** — Disk
   (`load_skill_from_dir`) for real know-how: it keeps skills as reviewable, versioned
   files in the repo and portable to any spec-compliant product. In code
   (`models.Skill(frontmatter=..., instructions=..., resources=...)`) for tests and
   generated skills — my skill test suite builds throwaway skills in memory so tests
   don't depend on fixture folders. Same object either way, so the choice is purely
   about where the source of truth should live.
3. **"What's the operational risk of a feature marked Experimental, and how do you
   manage it?"** — Surface may change under me. I manage it the same way I manage free
   tiers that shrink: pin the exact version in the package ledger, record the doc page
   and date I verified against, keep an import probe in the day's runbook, and re-check
   at every phase gate. If the surface moves, the plan gets amended first — the
   discipline is cheaper than debugging a silent rename later.
