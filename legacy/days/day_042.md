## 1 · 🎬 Where we are — the story so far

Since Day 33, MCP has been Sutra's *intake*: data flows in through servers Sutra consumes.
Yesterday you even learned how a tool can ship a UI outward. But Sutra itself — the agents,
the judgment, the KB-answering skill you've been sharpening for six weeks — is still only
reachable one way: by running *your* Python, in *your* repo, through *your* runner.

Now flip the table. Your teammate uses Claude Desktop. A partner team runs their own agent
stack. An IDE wants "ask the Sutra desk" as a right-click. None of them want your repo;
they all already speak MCP. What if Sutra's KB-answering agent were just… a server on their
list? One tool: ask it a question, get its answer — the whole think→act→observe loop from
Day 3 humming *behind* the counter, invisible, exactly like SQLite hums behind
`archive_lookup`.

ADK 2.5 made this a one-liner: **`to_mcp_server`** wraps an entire agent as an MCP server.
Today you serve one, call it from the outside, and — just as important — learn the sharp
edges of squeezing a conversational thing through a tool-shaped hole. That contrast has a
name you'll use all through Phase 14: **agent-as-tool** (MCP, today) versus
**agent-as-peer** (A2A, Day 89).

## 3 · 📚 Concepts

### MCP-33 — An agent behind the counter

**The expert-in-the-back-room story.** A hardware store has a wall of parts (tools: look
up, search — Phase 5's `sutra-mcp`). It also has Gustav, the retired engineer in the back
room. You don't browse Gustav. You hand the clerk a question, the clerk disappears, Gustav
does *whatever Gustav does* — reads manuals, cross-checks, mutters — and the clerk returns
with an answer. To you, Gustav has the interface of a vending machine: question in, answer
out. Inside, he's the most complicated thing in the building.

`to_mcp_server` puts an agent in the back room:

```python
from google.adk.tools.mcp_tool import to_mcp_server   # verified import, 2026-08-18

server = to_mcp_server(
    agent,                # any BaseAgent — the whole loop goes behind the counter
    name=None,            # server/tool name; defaults to the agent's name
    instructions=None,    # optional usage note shown to MCP hosts
    runner=None,          # bring your own Runner; else in-memory services are created
)
server.run(transport="stdio")            # or transport="streamable-http"
```

What the outside world sees: **one MCP tool** that takes a single text `request` and
returns the agent's final answer. What actually happens per call: a full runner session —
model calls, tool calls, the whole Day 3 loop — executed behind the protocol boundary.

The guide's documented caveats, which you will meet personally in step 5:

| Caveat (from the guide) | Plain meaning |
| --- | --- |
| Text-only single `request` string | no images, no structured args — a question in a box |
| In-memory default services | the auto-created runner forgets everything between restarts (and its sessions are per-connection plumbing, not a promise) |
| Sequential calls per shared connection | it's one Gustav, not a call center — don't parallel-spam one connection |
| **Experimental** | re-verify the API the day you build (step 1 makes this a gate, not a vibe) |

💡 **Mental model: `to_mcp_server` is Day 15's `AgentTool` pointed outward.** AgentTool let
*your* agents call another agent as a tool, inside one process. `to_mcp_server` gives that
same "agent wearing a tool costume" a public counter — any MCP host becomes the caller.

### ADK-26 — Agent-as-tool vs agent-as-peer

Two ways to let outsiders at your agent, and the difference is *who keeps the thread*:

| | **Agent-as-tool** (MCP, today) | **Agent-as-peer** (A2A, Day 89) |
| --- | --- | --- |
| Interface | a tool: request → result | a conversation: messages, tasks, negotiation |
| Who holds context | the **caller** must pack everything into the request | both sides carry a shared task state |
| Discovery | `tools/list` on a server | signed Agent Cards declaring skills |
| Right when… | the caller needs an **answer** ("what does KB-104 say about logout loops?") | the caller needs a **collaborator** ("work this ticket with me; I'll review your draft") |
| Failure smell | callers building para-protocols inside the request string | peers used for one-shot lookups (a handshake to ask the time) |

The failure-smell row is tomorrow's-you insurance: the moment you catch a caller writing
`"CONTEXT: … PREVIOUS ANSWER: … NOW ANSWER: …"` into the single request string, they
needed a peer, not a tool — the para-protocol is Day 3's pinky-promise reborn on the
outside of your server. Route them to A2A when Phase 14 arrives.

```python

to_mcp_server wraps a whole agent as an MCP server exposing ONE tool:
a text question in, the agent's final answer out. The agent inside is
deliberately narrow — KB questions only — because everything we serve

from google.adk.agents.llm_agent import Agent          # Phase 1 canon import
from google.adk.tools.mcp_tool import to_mcp_server    # verified 2026-08-18; EXPERIMENTAL
from sutra.adk_tools import search_kb                  # Day 10's ADK function tool

# The specialist going behind the counter. Note what it does NOT have:
# no lookup_ticket (ticket data stays inside the desk), no write tools.
# Serving an agent = granting its ENTIRE toolbox to every caller.
kb_answerer = Agent(
    name="sutra_kb_answerer",
    model="gemini-3.5-flash",                          # pinned, always (ADK-73)
    instruction=(
        "You answer questions using the internal knowledge base via the "
        "search_kb tool. Cite article ids (like KB-104). If the KB has "
        "nothing relevant, say so plainly — never invent an article."
    ),
    tools=[search_kb],                                 # ONE narrow capability
)

# The counter itself. Default runner => in-memory services: fine for a
# lab, documented amnesia (step 5 proves it). A persistent Runner is a
# Day 47 upgrade, noted there.
server = to_mcp_server(
    kb_answerer,
    instructions="Ask one self-contained KB question per call. "
                 "The server keeps no memory between calls.",
)

if __name__ == "__main__":
    server.run(transport="stdio")                      # streamable-http exists too (Day 43)
```

## 5 · 💥 Failure lab — the conversation squeezed through a keyhole

> 🎬 **The scene:** the partner team loves the KB answerer. Two weeks later their calls
> look like this: `request = "CONTEXT: user is on mobile v2.3. EARLIER YOU SAID: check
> cookie settings. USER REPLIED: didn't work. NOW: next step?"` — and they file a bug:
> *"your agent contradicts what it said earlier."*
> 😬 **The naive fix:** make the server remember callers — keep a session per client,
> maybe keyed by connection.
> 💥 **Why it fails twice:** first, you just rebuilt the pre-2026 session-pinned server —
> Day 43 exists precisely to kill that shape: state tied to a connection dies with the
> connection, breaks behind load balancers, and turns "any instance answers" into "one
> instance owns you." Second, even if it worked, the caller's transcript and your session
> now silently diverge — two versions of "what was said," no owner. The bug report was
> mis-titled: the agent didn't contradict itself; the *protocol shape* was wrong. They're
> holding a conversation through a tool-shaped keyhole.
> 💡 **The insight:** **statelessness is a contract, not a limitation — and contracts
> route.** Answer-shaped needs stay on MCP (caller packs context, or passes an explicit
> handle à la Day 36). Conversation-shaped needs go to a peer protocol with real shared
> task state — A2A, Day 89. The smell that tells you which side of the line you're on:
> uppercase para-protocols inside a request string.

## 6 · 🎤 Interview corner

1. **"How would you expose an existing agent to other teams' tooling?"** — Over MCP as
   agent-as-tool: ADK's `to_mcp_server` wraps the whole agent as a one-tool server —
   text question in, final answer out — so anything MCP-capable can call it with zero
   knowledge of my stack. I serve a deliberately narrowed agent (serving = granting its
   whole toolbox), declare the amnesia contract in the server's instructions, and route it
   through the same allowlist policy as inbound servers. When callers start smuggling
   conversation history into the request string, that's my signal they need agent-as-peer
   — A2A — instead.
2. **"MCP vs A2A — when each?"** — Who keeps the thread? MCP's unit is a request: caller
   holds all context, server holds none — perfect for answer-shaped integrations and
   trivially scalable because it's stateless. A2A's unit is a shared task between peers
   with discovery via signed agent cards — for collaborations where both sides carry
   state. Tool for answers, peer for work.
3. **"What are the sharp edges of wrapping an agent as a tool?"** — From shipping it: the
   interface collapses to one text string, so structure and media are out; the default
   runner is in-memory, so amnesia between calls is the contract and must be *declared*
   to callers; calls on a shared connection are sequential, so it's not a throughput
   device; and in ADK it's flagged experimental, so the API gets re-verified against the
   current guide before every build — I gate the build step on that diff.
