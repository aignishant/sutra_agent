## 3 · 📚 Concepts

### AG-26 — A driving exam, not a crash test

**The story.** Day 23's car metaphor, finished: the *car* gets crash tests — same dummy,
same wall, same speed, pass/fail. The *driver* gets a driving exam — a scripted route
with an examiner holding a rubric: *signalled before turning? checked mirrors? stopped at
the line?* Nobody fails a driver for taking the second-to-left lane when the left one
was also fine. Nobody passes one for arriving at the destination after running a red
light. The exam scores **how you drove**, tolerates harmless variation, and is repeated
across candidates and days so the examiner's own drift shows up too.

An eval is a driving exam for the model's judgment. Four properties make it a different
instrument from a unit test:

| Property | Unit test (Day 23) | Eval (today) |
| --- | --- | --- |
| Input | one call, fixed args | a **conversation** (one or more user turns) plus starting state |
| Expected | one exact value | an expected **trajectory** (which tools, which args, which order) *and* an expected **answer** |
| Verdict | pass/fail, deterministic | a **score** per metric, compared to a **threshold**; may be sampled over `num_runs` |
| Cost | milliseconds, zero quota | model calls — budgeted, scheduled, on the cheap lane |

💡 **Mental model: a unit test asks "did the code do X?"; an eval asks "did the agent
*behave* well, and how well, and is that getting better or worse?"** The first is a
switch. The second is a gauge.

Two design rules fall out of "it's a gauge":

1. **Small and daily beats big and never.** A 12-case dev set you can afford to run after
   every behavior change catches regressions the day they land. A 60-case set you run
   "at the gate" (Day 83) measures the phase. Both exist; they have different jobs
   (Addendum 02 §5 wrote this down for you: "10–15 cases dev, full 60+ at gates").
2. **Cases come from reality and from fear.** Reality: the tickets that built Sutra
   (4521, 4610, 4633, 4701). Fear: the inputs that *should* make it decline — the
   nonexistent 9999 (Day 58's lab), a poisoned ticket from Day 66's fixtures. An evalset
   with only happy paths measures the demo, not the system.

### ADK-58 — The evalset file: a conversation with answers in the margin

ADK's evalset is a JSON file. Read one case top-down and every field explains itself:

```
eval_set_id ─ the set's name (one set = one file)
└── eval_cases[]
    ├── eval_id ──────────── "triage_4521_auth" — selectable by id from the CLI
    ├── session_input ────── {app_name, user_id, state} — the starting shelf (Day 17)
    └── conversation[] ───── the turns
        ├── user_content ─── what the user said            ("#4521")
        ├── final_response ─ what a good answer looks like  ("...KB-104...")
        └── intermediate_data
            └── tool_uses[] ─ the EXPECTED trajectory: [{name, args}, ...]
```

It is Day 4's three-voice transcript (user → function_call → function_response → text),
written *in advance* as the answer key. Two honesty notes about the answer key:

- **`final_response` is a reference, not a script.** Today's `response_match_score`
  compares by word overlap (ROUGE-1), so write the reference the way a good reply *would*
  read — the key facts (KB-104, "SameSite", "re-login") — not a paragraph you hope the
  model copies. Day 81 swaps in a judge that compares *meaning*.
- **`tool_uses` is the trajectory you intend.** For the graph, the "tools" are the
  stations' function calls the runtime records: `lookup_ticket`/`search_kb` inside the
  clerks, and — crucially — the *absence* of `close_ticket`. An expected trajectory that
  never contains a write is itself a safety assertion (Day 80 turns that into a rubric).

### ADK-59 — Criteria and the two doors

`test_config.json` sits next to the evalset and says what "good" means, numerically:

```json
{
  "criteria": {
    "tool_trajectory_avg_score": {"threshold": 1.0, "match_type": "IN_ORDER"},
    "response_match_score": 0.6
  }
}
```

- `tool_trajectory_avg_score` — did the agent make the expected tool calls? `EXACT` means
  the list must match perfectly; `IN_ORDER` allows *extra* calls between expected ones
  (the graph's clerks may run `search_kb` twice — harmless); `ANY_ORDER` ignores sequence.
  Sutra starts at `IN_ORDER`: strict about *what*, tolerant about *chatter*.
- `response_match_score` — ROUGE-1 overlap with the reference. 0.8 is the documented
  default; a *reviewed reply* legitimately varies in wording, so the dev set starts at
  **0.6 and is tuned from data** (Step 4 prints the real scores; pin the threshold from
  the print, never from taste — the Day 53 "print-then-pin" rule applied to evals).

Two doors open onto the same file:

| Door | Command | When |
| --- | --- | --- |
| CLI | `adk eval tests\evals\triage_app tests\evals\triage.evalset.json --config_file_path tests\evals\test_config.json --print_detailed_results` | exploring, tuning thresholds, the nightly job (Day 82) |
| pytest | `uv run pytest -m quota tests\evals` | the suite; CI on demand (Day 82); `AssertionError` on failure = red |

Both need to *find the agent*: `adk eval` takes a **directory** whose `__init__.py`
exposes an `agent` module with `root_agent`. Sutra's graph is a `Workflow`, which Day 53's
probe showed drops in wherever an agent does — so Step 2 builds a tiny shim package,
`tests/evals/triage_app/`, whose `root_agent` *is* `triage_graph_v1`. Probe, don't
assume: the page says graph architectures work "without modification"; your installed
version gets to confirm that.

## 5 · 💥 Failure lab — the evalset that only graded the destination

> 🎬 **The scene:** a teammate (fine: past-you) trims `test_config.json` to
> `{"criteria": {"response_match_score": 0.5}}` — "trajectory scoring is fiddly; the
> answer is what the customer sees anyway." The dev set goes green. Two weeks later a
> refactor of `escalate_lane` accidentally routes severity-4 tickets into the draft box.
> The eval is *still green*: the box writes a lovely reply to the outage ticket, the
> reference answer for 4701 says "blank dashboard … outage", ROUGE-1 overlap is fine.
> 😬 **The naive fix:** make the 4701 reference say "ESCALATED" in capital letters and
> raise the threshold. Now it's a word-spotting test with extra steps.
> 💥 **Why it fails:** you graded the destination and deleted the route. Sutra's most
> important behaviors are *what it did not do* — not drafting for a fire (Day 58), not
> closing without a human (Day 64), not obeying ticket text (Day 66) — and none of those
> are visible in the final sentence. They are visible in the **trajectory**: which
> stations ran, which tools were called, which were *not*. A response-only eval is Day
> 12's "schema with no other box" again: it will happily grade confident garbage as
> confident.
> 💡 **The insight:** **the final answer is one observation; the trajectory is the
> behavior.** Keep `tool_trajectory_avg_score` in every config, make the *absence* of a
> write tool an expectation, and — tomorrow — turn "escalated before any external
> write" into a rubric line a judge checks across the whole conversation. Grade the
> driving, not just the parking.

Run it: remove the trajectory criterion, re-run only the 4701 case
(`triage.evalset.json:triage_4701_escalates`, ~2 calls), watch it pass on words alone;
restore the criterion.

## 6 · 🎤 Interview corner

1. **"How is evaluating an agent different from unit-testing it?"** — Different
   instrument for a different component. Below the model boundary everything is
   deterministic Python and gets millisecond unit tests (my repo-green gate is zero
   quota). Across the boundary I run evals: scripted conversations with an expected tool
   trajectory *and* an expected answer, scored per metric against thresholds, sampled
   when it matters, tracked over time — a gauge, not a switch. The dev set is 12 cases I
   can afford daily on the cheap lane; the 60-case set runs at phase gates and nightly.
2. **"What goes into one eval case?"** — Starting session state, the user turns, the
   expected tool calls with arguments (including, by omission, the tools that must *not*
   be called — no `close_ticket` without a human), and a reference answer. The cases
   come half from real tickets and half from fear: a nonexistent ticket, a poisoned one,
   an outage that must escalate. An evalset with only happy paths measures the demo.
3. **"How do you keep evals from burning your budget?"** — Pin the whole graph to the
   cheapest lane for eval runs, start with deterministic metrics (trajectory match, ROUGE)
   before adding LLM judges, keep the daily set small, mark the pytest door `quota` so the
   default suite never spends, and write the call math *before* the run: 12 cases ×
   ~4 calls ≈ 50 — then confirm it in the quota ledger after.
