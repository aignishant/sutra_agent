## 1 · 🎬 Where we are — the story so far

`sutra/agent.py` has existed since Day 5. You've talked to it with `adk run sutra` and
`adk web`, on your own machine, using your own terminal, your own Python, your own `.env`. It
has never once answered a request that didn't originate on your laptop.

Today it gets a public HTTPS URL. Not a demo of a URL — a real one, on Google's actual
infrastructure, inside a quota that costs $0 for up to two million requests a month. The
interesting part isn't the deploy command itself (it's one command). It's everything the
command is quietly doing on your behalf — building a container image, wiring a secret,
choosing exactly which permissions a build process needs versus which permissions a running
service needs — and one thing it is *not* doing: nothing about it requires Vertex AI, a
service account key, or a single cent, if you set the flags correctly. Getting the flags wrong
is the whole lesson of this day's failure lab.

## 3 · 📚 Concepts

### DEPLOY-01a — `adk deploy cloud_run`: the framework builds the container for you

**The story.** Day 86 (elsewhere in this repo) hand-writes a `Dockerfile`: a base image, a
dependency layer, a non-root user, a healthcheck — full control, full responsibility. There is
a second, shorter path for exactly this framework: ADK ships its own CLI command that reads
your agent's Python source, builds an equivalent container itself, and deploys it — you never
see the Dockerfile it generates.

💡 **Mental model: `adk deploy cloud_run` is the rental car; Day 86's Dockerfile is the car you
built yourself.** Both drive. The rental is faster to get moving and someone else maintains the
engine; your own build is the one you can explain screw-by-screw in an interview. Today you
drive the rental — on purpose, so this day doesn't have to wait for Day 86 to be built first —
and `docs/deployment/02_gcp.md` §3 has the other path for later comparison.

**The required shape** (`adk.dev/deploy/cloud-run/`, quoted 2026-08-21): the agent directory
must contain an `agent.py` defining `root_agent`, an `__init__.py` containing `from . import
agent`, and a `requirements.txt`. Sutra's `sutra/` directory already has the first two-thirds of
this — `agent.py` and `root_agent` are real. The other two are today's gaps (§4 Step 2).

### DEPLOY-01b — The environment-variable trap in the docs' own example

📌 **Finding, 2026-08-21.** The Cloud Run page's own "Environment variables" section shows:

```bash
export GOOGLE_CLOUD_PROJECT=your-project-id
export GOOGLE_CLOUD_LOCATION=us-central1
export GOOGLE_GENAI_USE_ENTERPRISE=True
```

`GOOGLE_GENAI_USE_ENTERPRISE=True` (or ADK's older equivalent spelling
`GOOGLE_GENAI_USE_VERTEXAI=True`) tells ADK to call Gemini through **Vertex AI**, authenticated
by the Cloud Run service's own service-account identity — no API key file anywhere, which is
genuinely elegant, and is *exactly the wrong instruction for this project*: Vertex AI is a
billed API surface, and Addendum 02's entire model policy is built on the **free AI Studio API
key** instead (`GOOGLE_API_KEY` + `GOOGLE_GENAI_USE_VERTEXAI=FALSE`).

⚠️ **Copy the docs' example verbatim and you silently opt into a paid code path the first time
someone raises Sutra's traffic past whatever no-cost allowance Vertex AI has.** The fix is not
to use Vertex at all: pass `GOOGLE_API_KEY` (from Secret Manager, §3) and
`GOOGLE_GENAI_USE_VERTEXAI=FALSE` as the environment instead, and never set
`GOOGLE_GENAI_USE_ENTERPRISE`. This is Addendum 02's rule doing real work at deploy time, not
just in local `.env` files.

### DEPLOY-01c — Two permissions, two different reasons

`adk deploy cloud_run` needs Cloud Build (to *build* the container) and the running service
needs Secret Manager access (to *read* the key) — these are different service accounts' worth
of trust, granted for different reasons, and conflating them is a common misconfiguration:

| Permission | Granted to | Why | If missing |
| --- | --- | --- | --- |
| `roles/cloudbuild.builds.builder` | the default **compute** service account | `adk deploy` uses Cloud Build behind the scenes to build the image | the deploy command itself fails, before anything runs |
| `roles/secretmanager.secretAccessor` | the same (or the Cloud Run service's) service account | the **running container** reads `GOOGLE_API_KEY` from Secret Manager at request time | the container starts, but the model call fails — a *runtime* failure, not a *deploy-time* one |

### DEPLOY-01d — `requirements.txt`: a build artifact today, not tomorrow's source of truth

Sutra's real dependency source of truth is `pyproject.toml` + `uv.lock` (Day 1). `adk deploy
cloud_run` wants a `requirements.txt` in the agent directory regardless — that's ADK's
requirement, not a choice this project is making. Day 86 (when it's actually run) will make
exactly this same point about `pip install -r requirements.txt` vs `uv sync --frozen`: *"the
repo's source of truth is pyproject.toml + uv.lock... exporting a requirements.txt just to
satisfy a sample would create a second, staler source of truth."* Today's resolution: generate
`requirements.txt` **freshly, right before each deploy**, and never commit it — treat it as a
build artifact, exactly like a `.pyc` file, not a second lockfile.

> Shell: **PowerShell**, repo root. Commands below are written to be pasted as-is.

**Step 2 — fix the two structural gaps.**

`sutra/__init__.py` is currently empty. Add exactly one line (this is the one piece of
`sutra/`'s own code this day touches, and it's additive — nothing existing breaks):

```python
# sutra/__init__.py
from . import agent   # required by `adk deploy cloud_run`'s expected package shape
```

✅ *Verify:* `python -c "import sutra"` still exits cleanly (no output = success — `agent.py`
promises "importable with no side effects," and this import chain must keep that promise).

Generate `requirements.txt` fresh (per DEPLOY-01d, this is a build artifact, not a commit):

```powershell
uv export --no-hashes -o requirements.txt   # ⚠️ verify the exact flag with `uv export --help` —
                                              # not executed in this session; uv's export syntax
                                              # has changed before across versions.
"requirements.txt" | Add-Content .gitignore  # keep it a build artifact, not a second lockfile
```

✅ *Verify:* `requirements.txt` exists and lists `google-adk`/`google-genai` with real resolved
versions (not the `>=` ranges from `pyproject.toml` — a lockfile export should be exact pins).

**Step 3 — GCP project setup and the secret.**

```powershell
gcloud config set project YOUR_PROJECT_ID
gcloud services enable run.googleapis.com cloudbuild.googleapis.com secretmanager.googleapis.com

$PROJECT_NUMBER = (gcloud projects describe YOUR_PROJECT_ID --format="value(projectNumber)")
$SA = "$PROJECT_NUMBER-compute@developer.gserviceaccount.com"

gcloud projects add-iam-policy-binding YOUR_PROJECT_ID `
  --member="serviceAccount:$SA" --role="roles/cloudbuild.builds.builder"

$env:GOOGLE_API_KEY | gcloud secrets create GOOGLE_API_KEY --data-file=-

gcloud secrets add-iam-policy-binding GOOGLE_API_KEY `
  --member="serviceAccount:$SA" --role="roles/secretmanager.secretAccessor" `
  --project=YOUR_PROJECT_ID
```

| Line | What it does |
| --- | --- |
| `services enable …` | Cloud Run, Cloud Build, and Secret Manager are separate APIs; each must be turned on once per project before anything below can work |
| `$PROJECT_NUMBER` / `$SA` | the **default compute service account** — the identity both the build and (by default) the running service use |
| `add-iam-policy-binding … cloudbuild.builds.builder` | DEPLOY-01c's build-time permission |
| `$env:GOOGLE_API_KEY \| gcloud secrets create …` | creates the secret from your *local* `.env`'s value, piped directly — never written to a temp file |
| `secrets add-iam-policy-binding … secretAccessor` | DEPLOY-01c's runtime permission |

✅ *Verify:* `gcloud secrets versions list GOOGLE_API_KEY` shows exactly one enabled version.

**Step 4 — the deploy.**

```powershell
adk deploy cloud_run `
  --project=YOUR_PROJECT_ID `
  --region=us-central1 `
  --service_name=sutra-agent `
  --app_name=sutra `
  sutra `
  -- --set-env-vars=GOOGLE_GENAI_USE_VERTEXAI=FALSE --set-secrets=GOOGLE_API_KEY=GOOGLE_API_KEY:latest --min-instances=0 --max-instances=2 --no-allow-unauthenticated
```

| Flag | What it does |
| --- | --- |
| `--project` / `--region` | required; any Cloud-Run-supported region works for the free grant |
| `--service_name` | the Cloud Run service's name — shows up in the URL and the console |
| `--app_name` | the ADK "app" name the API server exposes at `/list-apps` — defaults to the directory name (`sutra`) if omitted; set explicitly so §5's verification is predictable |
| `sutra` (positional `AGENT_PATH`) | the directory containing `agent.py` + `__init__.py` + `requirements.txt` — §3's fixes made this real |
| everything after `--` | passed straight to the underlying `gcloud run deploy`, per `adk.dev/deploy/cloud-run/`'s documented passthrough mechanism — this is *how* DEPLOY-01b's fix and the free-tier discipline actually get applied, since `adk deploy cloud_run` itself has no `--env-vars`/`--secrets` flag of its own |
| `--set-env-vars=GOOGLE_GENAI_USE_VERTEXAI=FALSE` | the DEPLOY-01b fix — keeps ADK on the free AI Studio path, not billed Vertex |
| `--set-secrets=GOOGLE_API_KEY=GOOGLE_API_KEY:latest` | injects the Secret Manager value as an env var at **runtime** — never baked into the image, same rule as Day 86 §3, expressed through a managed platform instead of `docker run -e` |
| `--min-instances=0` | **the line that keeps this free** — scales fully to zero between requests; Cloud Run's 2M-free-requests/month grant assumes this |
| `--max-instances=2` | caps worst-case concurrent instances from an unexpected spike |
| `--no-allow-unauthenticated` | requires an identity token to call the service — safer default than public; §5 shows the authenticated curl |

When prompted `Allow unauthenticated invocations…? (y/N)`, press **Enter** (accepts the default
`N` — matches `--no-allow-unauthenticated` above; answering `y` here would override that flag).

✅ *Verify:* the command ends by printing a URL shaped like
`https://sutra-agent-<hash>-uc.a.run.app`. Save it — §5 needs it.

**Step 5 — prove it actually runs Sutra.**

```powershell
$TOKEN = gcloud auth print-identity-token
$URL = "https://sutra-agent-<hash>-uc.a.run.app"   # paste your real URL from Step 4

curl.exe -H "Authorization: Bearer $TOKEN" "$URL/list-apps"

curl.exe -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" `
  "$URL/apps/sutra/users/u1/sessions/s1" -d "{}"

curl.exe -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" `
  "$URL/run" -d '{"appName":"sutra","userId":"u1","sessionId":"s1","newMessage":{"role":"user","parts":[{"text":"A customer says checkout is broken."}]}}'
```

⚠️ **Field names are `camelCase`** (`appName`, `userId`, `sessionId`, `newMessage`) — confirmed
against `adk.dev/runtime/api-server/`, 2026-08-21. Every ADK API server response and request
body uses this convention; a `snake_case` body silently returns a validation error, not a typo
you'd notice from the shape of the error alone.

✅ *Verify:* `/list-apps` returns `["sutra"]`; the session call returns a session object; `/run`
returns Sutra's real triage reply (the same persona from `agent.py`'s `INSTRUCTION`), not an
error. This is the one step that spends real quota (1–2 model calls).

## 5 · 💥 Failure lab — the honest one: nobody has run this exact command against `sutra/agent.py` yet

> Unlike most failure labs in this repo, this one is not a mistake planted on purpose — it's a
> genuine open question this doc cannot resolve without the human actually running Step 4, so it
> is written as a diagnostic guide rather than a scripted scene.
>
> 🎬 **The scene:** Step 4 succeeds — a real `*.run.app` URL prints. You run Step 5's first
> `curl`. It fails: either a 500, or the Cloud Run logs show
> `ModuleNotFoundError: No module named 'sutra'`.
>
> 😬 **The naive fix:** redeploy, maybe with a different region, maybe twice.
>
> 💥 **Why it might actually fail:** `sutra/agent.py` imports with
> `from sutra.config import load_env` — an **absolute** import that only resolves if the
> *parent* of `sutra/` is on the Python path. `adk deploy cloud_run`'s documented directory shape
> (`agent.py` + `__init__.py` directly inside `AGENT_PATH`) matches how ADK's own sample
> (`capital_agent/`) is a **self-contained top-level package**, not a subpackage of something
> bigger — which is subtly different from Sutra's real shape, where `sutra/` is one package
> among several (`sutra_mcp/`, `tests/`, `tools/`) at the repo root, and `agent.py` reaches
> *sideways* to a sibling module via an absolute import.
>
> 💡 **The insight, and how to actually resolve it (this is today's real diagnostic work, not a
> canned answer):**
> 1. Read the Cloud Run **logs**, not just the HTTP response —
>    `gcloud run services logs read sutra-agent --region=us-central1 --limit=50` — the traceback
>    tells you definitively whether it's an import error, a missing-secret error (§3's IAM
>    binding didn't take effect yet — these can take a minute to propagate), or something else.
> 2. **If it's the import**, the fix that costs the least: change `sutra/agent.py`'s
>    `from sutra.config import load_env` to the relative form `from .config import load_env`,
>    and re-run Step 4. Record in `DEPLOY_TRACK_TRACKER.md` whether this was necessary — it's
>    exactly the kind of finding future days in this track need to know about, since every
>    later "deploy `sutra/` somewhere" day inherits the same import shape.
> 3. **If it's a permissions error** ("permission denied" reading the secret), the IAM binding
>    from Step 3 needs a minute to propagate — wait, then retry Step 5 before touching anything
>    else.
> 4. **The one thing not to do:** don't guess-and-redeploy repeatedly without reading the log
>    first (Principle 10 — investigate honestly rather than thrash). Each redeploy re-runs Cloud
>    Build, which is free but not instant, and guessing burns the one resource this day doesn't
>    otherwise spend: your time.
>
> Whichever it turns out to be, write the actual answer into this section (or a note in
> `DEPLOY_TRACK_TRACKER.md`) so Day 100/103's Azure/AWS equivalents know whether Sutra's import
> shape needs the same fix there too.

## 6 · 🎤 Interview corner

1. **"Walk me through deploying an ADK (or any Python) agent to Cloud Run."** — Two paths: hand
   a Dockerfile to `gcloud run deploy --source .`, or let the framework's own CLI
   (`adk deploy cloud_run`) build the container from source directly. I used the second because
   it doesn't require a Dockerfile to already exist, and it forces you to understand the
   required package shape (`agent.py`, `__init__.py`, `requirements.txt`) rather than hiding it.
2. **"How do you keep a deployed agent inside a free tier, concretely?"** — Not by trusting the
   word "free" — by setting `min-instances=0` (scales to zero between requests, so idle time
   costs nothing) and then *reading back* the deployed config
   (`autoscaling.knative.dev/minScale`) to confirm the flag actually took effect, rather than
   assuming the deploy command did what I asked.
3. **"How do secrets get into a Cloud Run service, and how do you prove none leaked?"** —
   Injected at deploy time via `--set-secrets`, which stores a *reference* to Secret Manager in
   the service's env, not the value itself — I confirmed that distinction by describing the
   deployed service and checking the env value was a reference, not a literal string, the same
   discipline this project already applies to Docker images (Day 86) and Kubernetes Secrets
   (Day 88).
