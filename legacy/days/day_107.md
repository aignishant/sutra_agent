## 1 · 🎬 Where we are — the story so far

Three Terraform configs exist, written eight days apart, and each taught something the others
couldn't. Day 99: a plan is something you read before you trust, and drift is the cloud and the
file disagreeing. Day 102: whether your API key ends up in `terraform.tfstate` is decided by a
resource schema, not by your discipline. Day 105: `destroy` removes what `apply` created and not
one thing more.

They also share a smell. Three directories, three near-identical `variables.tf` files, three
different naming schemes for the same service, three provider versions nobody wrote down in the
same place, and three sets of instructions living in three different day documents. The obvious
move is to unify them — one module, one variable set, one `terraform apply` that deploys Sutra
to three clouds at once.

That would be a genuinely bad idea, for four separate reasons, and being able to explain them is
worth more than the module would have been.

## 3 · 📚 Concepts

### DEPLOY-11a — 📌 Four reasons not to put three clouds in one root module

The tempting design:

```hcl
# DON'T. One root, one state, three providers.
provider "google"  { ... }
provider "azurerm" { features {} }
provider "aws"     { ... }

module "sutra_gcp"   { source = "./modules/gcp" }
module "sutra_azure" { source = "./modules/azure" }
module "sutra_aws"   { source = "./modules/aws" }
```

One `terraform apply`, three clouds. Here is what it actually buys you:

| # | Problem | Why it bites |
| --- | --- | --- |
| 1 | **One blast radius** | A typo, a bad `plan` typed through, or a corrupt state file now affects *three* production surfaces instead of one. Day 099 §5's drift revert becomes a three-cloud revert. |
| 2 | **No transaction** | Terraform has no cross-provider rollback. If AWS fails halfway, GCP and Azure stay applied. §5 reproduces this. |
| 3 | **One state file holding three sets of secrets** | Day 102 and Day 105 established that Azure's and AWS's schemas put values in state. Merging means **one** file whose leak compromises everything, instead of three with different contents. |
| 4 | **All-or-nothing credentials** | Every `plan` — even one that only touches GCP — needs live, valid credentials for all three clouds, or it errors. That makes the common case (change one cloud) depend on the rare case. |

💡 **The rule underneath all four: the unit of Terraform state should match the unit of
change.** Sutra's GCP deployment and its AWS deployment do not change together, do not fail
together, and are not reviewed together. Fusing their state fuses their failure modes for no
gain.

### DEPLOY-11b — The abstraction to refuse, and how to tell

The second temptation is subtler: *"extract a `modules/agent-service` that takes an image and a
region and deploys to whichever cloud."*

⚠️ **It cannot exist meaningfully, and the reason is worth stating precisely.** A Terraform module
is a wrapper over *resources*, and there is no shared resource here —
`google_cloud_run_v2_service`, `azurerm_container_app`, and `aws_lambda_function` are three
unrelated schemas from three unrelated providers. A module spanning them would be a `count`/
`for_each` switch that contains all three configurations plus the branching, i.e. **strictly more
code than the three files it replaced**, with an interface that has to be the *intersection* of
what three clouds can express — which is roughly "a name and an image."

📌 Everything genuinely interesting is in the *differences*, and the differences are the part an
intersection-shaped interface throws away:

| Property | GCP | Azure | AWS |
| --- | --- | --- | --- |
| Scale-to-zero | `min_instance_count` | `min_replicas` | implicit (per-invocation) |
| Secret handling | reference ✅ | value ⚠️ | value ⚠️ (+ `ignore_changes`) |
| Resource count for one deployment | 1 | 3 | 4 |
| Deletion guard | `deletion_protection` | — | — |
| Required-but-empty block | — | `features {}` | — |

💡 **So what *is* shared, and therefore worth extracting?** Not resources — **conventions.** The
service name, the region variable's name and meaning, the tag/label set, the `.gitignore` rules,
the pinning policy, and the teardown checklist. Those are documentation and a couple of variable
defaults, not a module. Step 4 extracts exactly that and stops.

⚠️ **The test for next time:** if the "shared" module's body is a switch on which cloud you're
using, you don't have an abstraction — you have three functions in a trench coat, plus a
dispatcher you now also have to maintain.

### DEPLOY-11c — `.terraform.lock.hcl`: the file this repo already has an opinion about

Terraform writes a **dependency lock file** recording the exact provider versions and their
checksums. It is the direct analogue of something this repo already treats as sacred:

| | Python | Terraform |
| --- | --- | --- |
| Declares intent | `pyproject.toml` (`google-adk>=2.7.1`) | `required_providers { version = "~> 6.0" }` |
| Records the resolution | `uv.lock` | `.terraform.lock.hcl` |
| Committed? | ✅ yes | ✅ **yes** |

📌 Day 099 §3's `.gitignore` block covers `.terraform/`, `*.tfstate`, and `*.tfvars` — and
deliberately **not** the lock file. That was correct and worth making explicit today: a
`~> 6.0` constraint lets `init` pick `6.9.0` on your laptop and `6.14.0` in CI, and provider
minor versions have changed defaults before. `05_terraform.md` §7 asks for pinning; the lock file
is what makes the pin *reproducible* rather than *approximate*.

### DEPLOY-11d — Where state should live, now that you know what's in it

`05_terraform.md` §5's backend table, re-read through Days 102 and 105' findings — **two of three
state files contain a real API key**:

| Backend | Cost | Verdict for this project |
| --- | --- | --- |
| **Local** (default) | Free | ✅ What this track uses. Fine for solo work, on an encrypted disk, gitignored. ⚠️ One laptop failure loses the ability to `destroy` cleanly |
| GCS bucket | free ≤5 GB (GCP Always Free) | ✅ Survives a wiped laptop, still $0, encrypted at rest by default |
| S3 / Azure Blob | free-ish, with caveats | ⚠️ S3's 5 GB is 12-months-only for legacy accounts (Day 104's finding) |
| HCP Terraform | free ≤5 users | ✅ Adds **locking** — the thing local state cannot do |

💡 **The point of the locking column:** local state has no lock, so two `apply`s at once corrupt
it. Solo, that's theoretical. The moment a second person or a CI job exists, it isn't — and
recovering a corrupted state for a resource you can no longer `destroy` is how a free-tier
project starts costing money.

**Today's decision: stay local, and write down why.** It's free, it's honest, the blast radius is
one laptop, and this is a solo learning project. Recording the *reason* is what makes it a
decision rather than a default.

## 4 · 🛠️ The build

> Shell: **PowerShell**, repo root. Steps 1–7 create nothing in any cloud.

**Step 1 — inventory.**

```powershell
Get-ChildItem infra -Recurse -File | Select-Object FullName
terraform -chdir=infra/gcp   version
terraform -chdir=infra/azure version
terraform -chdir=infra/aws   version
```

✅ *Verify:* three roots exist, and each `version` call prints both Terraform's version **and**
the provider versions that root has installed. ⚠️ If a root is missing, that day wasn't run — go
back to it. Today refactors what exists; it does not invent the missing config.

**Step 2 — consolidate the pins.**

Put the three actual resolved versions in one place. In each root's `main.tf`, tighten the
constraint from a major-version range to what you actually tested:

```hcl
# infra/gcp/main.tf — and the equivalent in azure/ and aws/
terraform {
  required_version = ">= 1.9"
  required_providers {
    google = { source = "hashicorp/google", version = "~> 6.0" }   # <- record the RESOLVED
  }                                                                 #    version in infra/README.md
}
```

✅ *Verify:* `terraform -chdir=infra/<cloud> init -upgrade=false` succeeds on all three, and the
versions match what your tracker recorded on Days 099/102/105. ⚠️ If they don't, something moved
between then and now — that is exactly what pinning is for, and it's a finding worth a tracker
line.

**Step 3 — commit the lock files.**

```powershell
git add -f infra/gcp/.terraform.lock.hcl infra/azure/.terraform.lock.hcl infra/aws/.terraform.lock.hcl
git status --short infra/
```

✅ *Verify:* all three lock files are staged, and **no** `.tfstate` or `.tfvars` file appears
anywhere in that output. ⚠️ The `-f` is there in case an overly broad `.terraform*` pattern crept
into `.gitignore` — check that it hasn't, rather than fighting it with `-f` forever.

**Step 4 — shared conventions, and nothing more (DEPLOY-11b).**

Make the three roots agree on names and labels. This is a *convention*, applied three times by
hand, deliberately not a module:

| Convention | Value | Applied in |
| --- | --- | --- |
| Service name | `sutra-agent` | all three |
| Label/tag set | `project=sutra`, `phase=16`, `managed-by=terraform` | `labels` (GCP), `tags` (Azure/AWS) |
| Variable name for region | `region` (Azure's is `location` natively — ⚠️ keep Azure's own name; renaming a provider's vocabulary to match a convention is a cost, not a benefit) | all three |
| Teardown | `destroy` **plus** the provider sweep from Day 105 §5 | `infra/README.md` |

⚠️ **The `region`/`location` row is the day's discipline in miniature.** The urge is to normalise
everything. Don't: Azure calls it `location` in every document, error message, and portal screen
its users will ever read. A local rename buys internal tidiness and costs every reader a
translation step.

✅ *Verify:* `terraform -chdir=infra/<cloud> plan` on each root still produces the same resource
count as its origin day (**1 / 3 / 4**). Conventions changed labels, not architecture.

**Step 5 — `terraform.tfvars.example` per root, committed.**

Day 099 §3's `.gitignore` has `*.tfvars` with a `!*.tfvars.example` exception already. Use it:

```hcl
# infra/gcp/terraform.tfvars.example   (committed — no real values)
project_id = "your-gcp-project-id"
image_uri  = "us-central1-docker.pkg.dev/PROJECT/cloud-run-source-deploy/sutra-tmp:latest"
```

```hcl
# infra/azure/terraform.tfvars.example
image          = "ghcr.io/YOUR-GITHUB-USER/sutra-agent:v1"
google_api_key = "REPLACE-ME — see day_102.md §5: this WILL land in terraform.tfstate"
```

```hcl
# infra/aws/terraform.tfvars.example
image_uri = "ACCOUNT.dkr.ecr.us-east-1.amazonaws.com/sutra-agent:lwa"
# NOTE: no API key here on purpose — day_105.md §3a explains why it is set out-of-band.
```

📌 The Azure example's warning and the AWS example's *absence* of a key are the two most useful
lines in these files. They carry Days 102 and 105's findings to whoever runs this next without
requiring them to read either day.

✅ *Verify:* `git status` shows three `.example` files staged and **no** real `.tfvars`.

**Step 6 — `infra/README.md`.**

Write the file that lets someone deploy without reading eleven day documents. It should contain
exactly: the four-command workflow, the three roots and what each deploys, the resolved provider
versions from Step 2, the state decision from DEPLOY-11d **with its reason**, the two secret
warnings, and the teardown checklist including Day 105 §5's blind spot.

✅ *Verify (the real test):* hand it to someone — or reread it tomorrow — and check they could get
from a clean machine to a deployed service without opening `docs/days/`. If they'd have to ask a
question, the README is missing that answer.

**Step 7 — the driver.**

The "one workflow" part, done honestly — a loop over independent roots, not a merged state:

```powershell
# infra/plan-all.ps1
param([ValidateSet("plan","apply","destroy")][string]$Action = "plan")

foreach ($cloud in @("gcp","azure","aws")) {
  Write-Host "`n=== $cloud : $Action ===" -ForegroundColor Cyan
  terraform -chdir="infra/$cloud" $Action
  if ($LASTEXITCODE -ne 0) {
    Write-Host "!! $cloud failed (exit $LASTEXITCODE) — the others are unaffected." -ForegroundColor Yellow
  }
}
```

| Design choice | Why |
| --- | --- |
| A loop, not a merged config | each root keeps its own state, lock, and blast radius — DEPLOY-11a |
| Continues past a failure, loudly | ⚠️ **the honest bit** — with three independent roots, one failing genuinely does not affect the others, and pretending otherwise (`exit 1` on first error) would hide the partial state §5 is about |
| No `-auto-approve` | `apply` still prompts per cloud. A driver that makes three clouds change without three confirmations is a footgun, not a convenience |

✅ *Verify:* `.\infra\plan-all.ps1` runs three plans and prints three summaries. ⚠️ A root whose
credentials aren't currently valid will fail — **and the other two still run.** That is
DEPLOY-11a reason #4 demonstrated for free, with no cloud resources involved.

## 5 · 💥 Failure lab — the deploy that half-happened

> 🎬 **The scene:** you run `.\infra\plan-all.ps1 apply`, confirm all three, and walk away. You
> come back to: **GCP applied. Azure applied. AWS failed.**
>
> ```
> Error: creating Lambda Function: InvalidParameterValueException:
> The role defined for the function cannot be assumed by Lambda.
> ```
>
> (Day 105 §4 Step 4's IAM eventual-consistency error — the most reproducible way to see this,
> and a real one rather than a contrived fault.)
>
> 😬 **The naive read:** "one command failed, so the deploy didn't happen — I'll fix it and re-run."
>
> 💥 **What is actually true right now:** two clouds are serving live traffic and one is not. There
> was never a transaction. Terraform's atomicity boundary is **one root, one state, one apply** —
> and even *within* the AWS root it isn't all-or-nothing: the IAM role and its policy attachment
> were created successfully before the function failed, so `infra/aws/terraform.tfstate` now
> describes a half-built deployment that neither exists as intended nor is absent.
>
> 💡 **The insight: "infrastructure as code" borrows the vocabulary of software but not its
> guarantees.** There is no rollback, no two-phase commit, no cross-provider consistency. What
> you get instead is *convergence* — re-running `apply` moves reality closer to the file, one
> resource at a time, from wherever it currently is.
>
> ⚠️ **And this is DEPLOY-11a reason #2 arguing for itself.** With three separate roots, the blast
> radius of this failure is one cloud, the state that needs attention is one file, and the fix is
> `terraform -chdir=infra/aws apply` again. **Merged into a single root, the identical failure
> would leave one state file describing a partly-applied three-cloud world** — and every
> subsequent `plan`, for any cloud, would surface the mess.

**The fix, and the habit:**

```powershell
# 1. Converge the root that failed. Terraform picks up where it stopped.
terraform -chdir=infra/aws apply

# 2. Then verify all three CONVERGED, rather than trusting that apply succeeded:
.\infra\plan-all.ps1 plan
```

✅ *Verify:* all three plans report `No changes.` **That triple no-op is the real definition of
done for a multi-cloud deploy** — not "the apply command exited 0," but "every root now agrees
with reality." Day 099 §5 taught this for one cloud; today it's the acceptance test for three.

📌 **To reproduce this without three live clouds:** point one root's `terraform.tfvars` at a
nonexistent image URI, run the driver, and watch the other roots complete while that one fails.
Same lesson, no bill.

## 7 · 🎤 Interview corner

1. **"You deploy the same service to three clouds. How do you structure the Terraform?"** — Three
   independent root modules with three state files, sharing conventions rather than code. Not one
   root with three providers, for four reasons: a single blast radius across three production
   surfaces; no cross-provider transaction, so a partial failure leaves one state describing a
   half-applied three-cloud world; one state file holding three sets of secrets instead of three
   with different contents; and every plan requiring valid credentials for all three clouds even
   when you're only changing one. The unit of state should match the unit of change.
2. **"Why not extract a shared module?"** — Because there's nothing shared to extract. The three
   resources are unrelated schemas from unrelated providers, so a spanning module would be a
   switch containing all three configurations plus a dispatcher — more code than it replaced —
   and its interface would have to be the intersection of what three clouds can express, which
   throws away everything interesting: scale-to-zero semantics, secret handling, deletion guards.
   What I did extract was conventions — naming, tags, gitignore rules, the teardown checklist —
   which is a README and two variable defaults, not a module. If a module's body is a switch on
   which backend you're using, it isn't an abstraction.
3. **"Do you commit the Terraform lock file?"** — Yes, same reasoning as `uv.lock` or
   `package-lock.json`. The `required_providers` constraint states intent; the lock records the
   resolution with checksums, so my laptop and CI get the same provider build. Provider minor
   versions have changed defaults before, and defaults are where cost lives — a `~> 6.0`
   constraint alone means "some 6.x," which isn't reproducible.
4. **"What does infrastructure-as-code *not* give you?"** — Transactions. It borrows software's
   vocabulary without its guarantees: no rollback, no two-phase commit, no cross-provider
   consistency. What you get is convergence — re-run apply and it moves reality toward the file
   from wherever it is. So my acceptance test for a deploy isn't "the command exited zero," it's
   "a subsequent plan reports no changes on every root." And my teardown isn't `destroy`, it's
   destroy plus an explicit per-provider sweep, because destroy only removes what apply created.
