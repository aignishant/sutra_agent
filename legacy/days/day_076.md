## 3 · 📚 Concepts

### ADK-56 — Voice activity detection: who decides when a turn ends

**The walkie-talkie story.** A walkie-talkie has a button: you press to talk, release
to listen — *you* decide the turns. A phone has no button: the network carries both
ways and *people* decide turns by listening for pauses. A voice agent must pick one of
those — and the pick is a **config**, not a feeling:

| Mode | Who detects speech | ADK/Gemini config | When it's right |
| --- | --- | --- | --- |
| **Automatic** (default) | the model's server-side ear | `realtime_input_config.automatic_activity_detection` — `disabled=False`, `start_of_speech_sensitivity`, `end_of_speech_sensitivity`, `prefix_padding_ms`, `silence_duration_ms` | hands-free conversation; yesterday's demo |
| **Automatic + explicit signals** (2.5) | the model — and it *tells you* | `RunConfig(explicit_vad_signal=True)` → events carry `voice_activity` | UIs that show "listening…", latency measurement, analytics |
| **Manual** | **you** (the client) | `automatic_activity_detection.disabled=True` + `queue.send_activity_start()` / `send_activity_end()` | push-to-talk, noisy rooms, client-side VAD, accessibility |

Two dials deserve a sentence each. `silence_duration_ms` is *how long a pause means
"done"*: too short and the model answers your half-sentence; too long and every reply
feels laggy — tune it with your own voice. `prefix_padding_ms` keeps the audio *just
before* detection so the first syllable isn't clipped. And the interruption rule you
saw yesterday is VAD's: when the ear hears you during a reply, "the ongoing generation
is canceled and discarded" — only what already reached the client stays in history.

What 2.5 added is the *visibility*: `explicit_vad_signal=True` makes the model emit
voice-activity signals, ADK attaches them to the live event (`event.voice_activity`,
an object from `google.genai.types`), and your code can finally *see* the thing that
was controlling the conversation all along.

💡 **Mental model: VAD is the turn-taking rule of the conversation — automatic means
the model holds the talking stick, manual means you do, and 2.5 lets you watch the
stick move.**

### ADK-77 — Non-blocking tools: the agent keeps talking while it works

**The radio DJ story.** A good DJ takes a request, says "let me pull that up for you,"
*keeps talking*, and when the track is cued, plays it — the show never goes silent. A
bad one says "one moment" and the station broadcasts dead air for ten seconds. Until
2.5, every ADK tool on the live path was the bad DJ: the model calls the tool, the
flow awaits it, nothing speaks until it returns.

2.5's mechanism (verified in the commit, not a blog): mark a `FunctionTool` with a
**response scheduling** and ADK treats it as non-blocking —

```python
tool = FunctionTool(fetch_last_digest)
tool.response_scheduling = types.FunctionResponseScheduling.WHEN_IDLE   # attribute, post-construction
```

- ADK starts the function in a **background `asyncio` task**, registered per call
  (`f"{tool.name}_{function_call.id}"`), and **returns immediately** — the model is
  free to keep generating ("let me pull that up…").
- When the task completes, ADK **appends the function-response event to the session**
  (the commit point — trap #3 honoured by the framework, not by you) **and pushes the
  result back into the live request queue**, so the model sees it as new input and
  can speak to it.
- The scheduling value says *how* the model should react when the result lands:
  `WHEN_IDLE` — mention it at the next natural pause; `INTERRUPT` — break in now
  (alarms); `SILENT` — take it in without announcing (bookkeeping).

Three things to hold onto. **One:** this is trap #3 in a new costume — the tool's
result must *re-enter the event stream through the runner*; a tool that tried to "just
append to the session" from its background task would break exactly the way Day 7
warned. ADK does the re-entry; you only write the function. **Two:** not every tool
should be non-blocking — a tool whose answer the *next sentence depends on* ("what's
ticket 4610's status?") must block, or the model guesses. Non-blocking is for
*fetch-while-talking*: digests, counts, lookups whose result can wait a beat. **Three:**
brakes on the live path: model callbacks don't fire here (Day 74), so a non-blocking
tool's only fences are (a) it is **read-only** and (b) it is **on the agent's tool
list** — Day 68's tiers enforced by what the agent *has*, not by a callback. Today's
tool reads a Markdown file; the standup's tools read SQLite read-only. No write tool
ever goes on a live agent.

Streaming tools (async-generator tools that *yield* partial results, e.g. watching a
video stream) are the cousin: Experimental, Live-only, with a mandatory
`stop_streaming` tool — 🅿️ mapped, not built; Sutra's standup has nothing to stream.

💡 **Mental model: a non-blocking tool is "let me pull that up for you" — the work
goes to the background, the result comes back through the runner's front door, and
the conversation never hears dead air.**

## 5 · 💥 Failure lab — dead air

> 🎬 **The scene:** you remove the one line — `digest_tool.response_scheduling = …` —
> and ask "how did last night go?"
> 😬 **The naive fix:** none needed, surely; tools are tools.
> 💥 **Why it fails:** six seconds of **silence**. Then the answer — fine, accurate —
> but while the tool ran, the turn was frozen: you could talk (frames still went up the
> queue) and nothing happened until the tool returned; in a real standup you'd have
> asked your follow-up into a void and heard it answered out of order. Now put the line
> back but make the tool `INTERRUPT` and ask it to recite something long while the
> fetch runs: it **breaks in** mid-sentence the moment the digest lands — correct for an
> alarm ("approval queue is empty!"), rude for a digest. The scheduling value is a
> product decision you make per tool, not a default you accept.
> 💡 **The insight:** **on a voice path, a blocking tool is an outage measured in
> seconds of silence; non-blocking is the default for anything the next sentence
> doesn't depend on — and the scheduling mode is the tone of voice the result arrives
> in.** Keep blocking only for lookups the very next words must be correct about.

## 6 · 🎤 Interview corner

1. **"How does your voice agent handle turn-taking?"** — By config, explicitly: by
   default the model's server-side VAD holds the talking stick (I tune
   `silence_duration_ms` and `prefix_padding_ms` with my own voice), with ADK 2.5's
   `explicit_vad_signal` on so the client sees speech-start/end events and shows
   "listening"; for push-to-talk or noisy rooms I disable automatic VAD and drive
   turns with `send_activity_start/end`. And interruption is VAD's side effect — the
   server cancels and discards the in-flight generation, the client flushes playback.
2. **"Tools take time — how do you keep a voice conversation from freezing?"** — ADK
   2.5 non-blocking tools: set `response_scheduling` (`WHEN_IDLE`/`INTERRUPT`/`SILENT`)
   on the `FunctionTool`; ADK runs it as a background task, returns immediately, and
   when it completes appends the function response through the runner *and* pushes it
   back into the live queue so the model speaks to it. I use it for fetch-while-talking
   (digests, counts); anything the next sentence depends on stays blocking. And the
   result re-enters through the runner's commit path — the yield-don't-append rule
   honoured by the framework.
3. **"Where do guardrails live on the live path if model callbacks don't run?"** — On
   the tool surface and the agent's inventory: live agents get only read-only tools,
   no write tool is ever on their list, and the approval policy still gates every write
   elsewhere in Sutra. I verified the callback caveat on the ADK docs page rather than
   discovering it in production — it's why the standup agent *reports* and never acts.
