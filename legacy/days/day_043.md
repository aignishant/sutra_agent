## 1 · 🎬 Where we are — the story so far

Phase 5 taught the theory in one metaphor: old MCP was a phone call, new MCP is the web.
You built `sutra-mcp` "stateless-first" and believed it. But belief is not a gate. Nothing
you have run so far would actually *notice* if the server were secretly stateful — one
client, one process, one lifetime. A phone call and a web request look identical when
there's only ever one caller and the server never restarts.

Deployment is where the difference stops being philosophical. The 2026-07-28 release notes
make the promise concrete: *"any request can now land on any server instance behind a plain
round-robin load balancer without needing shared storage."* That sentence is either true of
`sutra-mcp` or it isn't — and there is exactly one way to know. Today you run **two**
instances of your server, bounce requests between them on purpose, and watch what survives.
Spoiler worth spoiling: one thing you built in Phase 5 will break beautifully, and fixing
it teaches the last stateless lesson better than ten diagrams.

## 3 · 📚 Concepts

### MCP-20 — Stateless is the architecture, not a mode

**The food-truck fleet story.** A restaurant with table service is stateful: *your* waiter
knows *your* order; if he goes home mid-meal, someone reconstructs your evening from
scraps. A food-truck fleet is stateless: you walk up to *any* truck, your order is complete
in the sentence you say, and the truck forgets you the moment you leave. Scaling a
restaurant means training waiters to hand over tables. Scaling a fleet means parking
another truck.

The 2025-era protocol was table service — `initialize`, a session, and every later message
implicitly meaning "same table as before." The 2026-07-28 protocol removed the table:

| Gone | Replaced by |
| --- | --- |
| `initialize` handshake | nothing — first request is just a request |
| The session | `_meta` on **every** request: protocol version, client identity, capabilities |
| "Which conversation is this?" | the request payload says everything it means |
| Server-side "your last result" | **explicit handles**: a tool mints `task_abc123`, the caller passes it back as an argument |

And one addition that only makes sense once you think in fleets: routable **headers**.
Every Streamable HTTP request carries `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name`
(SEP-2243) — so a load balancer, rate limiter, or WAF can steer `tools/call` for
`reindex_archive` to the beefy pool *without parsing a byte of JSON*. Infrastructure can
route on meaning. That is what "deploy-shaped" means at the wire level.

💡 **Mental model: a stateless request is a message in a bottle — it must survive being
opened by any instance, any time, with no memory of previous bottles.** If understanding a
request requires remembering another request, the design is wrong, not the fleet.

### MCP-21 — Where state goes when the server won't hold it

"Stateless server" never meant "no state exists" — re-indexing *takes a minute and has
progress*. It means state may not live **in the server process**. Three legal homes:

| Home | Pattern | Sutra example |
| --- | --- | --- |
| **The payload** | caller carries context each call | Day 42's contract: pack the question whole |
| **A handle + shared storage** | server mints an id; the *data behind it* sits where every instance can **safely** read *and write* it | today's fix: the task rack moves from a JSON file to SQLite |
| **The client** | results cached client-side per `ttlMs`/`cacheScope` | Day 40's pinned tool lists |

The trap you'll spring in step 4 is subtler than "not shared." Day 36 did the *first* half
right: explicit handles, rack in a file (`data/mcp_tasks.json`) — so a second instance
*can* see a handle minted by the first. But look at how a JSON-file rack updates: read the
whole file → change one entry → **rewrite the whole file**. One process: fine, forever.
Two processes: instance A and instance B both read, both rewrite — last writer silently
erases the other's update; and a reader who arrives mid-rewrite gets half a file and a
`JSONDecodeError`. Shared, yes. **Safely** shared — under concurrent writers, with atomic
updates — no. The word "shared storage" was always quietly carrying the word
"transactional" on its back; today it has to pay up.

**Step 3 — [C] The 12-line round-robin.**

Create `sutra_mcp/roundrobin.py` — deliberately dumb, because the *spec* claims a dumb
balancer suffices:

```python
"""Day 43 — the dumbest possible load balancer, on purpose.

Alternates every request between two sutra-mcp instances. If the spec's
promise holds, no client can tell. stdlib only; lab quality.

    python -m sutra_mcp.roundrobin        # listens on 8900 -> 8901/8902
"""
from __future__ import annotations

import itertools
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.request import Request, urlopen

BACKENDS = itertools.cycle(["http://127.0.0.1:8901", "http://127.0.0.1:8902"])


class RoundRobin(BaseHTTPRequestHandler):
    """Forward each POST to the next backend, verbatim, headers and all."""

    def do_POST(self) -> None:                        # every MCP call is a POST
        backend = next(BACKENDS)                      # alternate: A, B, A, B…
        body = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        req = Request(backend + self.path, data=body, method="POST",
                      headers=dict(self.headers))     # forward Mcp-* headers untouched
        with urlopen(req) as resp:                    # relay the backend's answer
            payload = resp.read()
            self.send_response(resp.status)
            self.send_header("Content-Type", resp.headers.get("Content-Type", ""))
            self.end_headers()
            self.wfile.write(payload)
        print(f"-> {backend}  {self.headers.get('Mcp-Method', '?')}")  # who answered what


if __name__ == "__main__":
    print("round-robin on :8900 -> 8901/8902")
    HTTPServer(("127.0.0.1", 8900), RoundRobin).serve_forever()
```

Point your client at 8900 and run the Phase 5 demo suite — list, lookup #4521, search:

```powershell
# [C]
python -m sutra_mcp.roundrobin
# (fourth terminal, or run the demos first) point sutra/mcp_client at http://127.0.0.1:8900
```

✅ *Verify:* the proxy log alternates `-> 8901`, `-> 8902`, … and **every** answer is
correct. Read the alternation aloud: consecutive requests of one logical "conversation"
answered by different processes, flawlessly, because no request needed a previous one.
MCP-20, observed.

**Step 4 — Break it: the long job under two writers (the good part).**

First confirm the happy half: start a re-index through the proxy, poll it through the
proxy. Handles are explicit and the rack is a file, so cross-instance *reads* work:

```powershell
python -m sutra.mcp_client call --server archive_http --tool reindex_start --args "{}"
#   -> returns the claim ticket, e.g. {"task": "task_..."} — minted by A or B
python -m sutra.mcp_client call --server archive_http --tool reindex_status --args "{\"task\": \"task_...\"}"
```

✅ *Verify:* polls answer from **both** instances (watch the proxy log alternate). Day 36's
handle design earns its keep. Now the hammer — concurrent *writers*. Create
`sutra_mcp/hammer.py`, a ten-line lab script that fires `reindex_start` and a burst of
`reindex_status` polls through the proxy in a tight loop (20–50 iterations, stdlib
`urllib`, reuse step 1's request shape), while BOTH instances are mid-job and updating
progress in `data/mcp_tasks.json`:

```powershell
python -m sutra_mcp.hammer
```

✅ *Verify (the failure IS the verification):* within a few dozen iterations you observe at
least one of: a `JSONDecodeError`-flavored server error (a reader caught a half-written
file), a poll whose progress went **backwards**, or a finished task that snapped back to
`running` (last-writer-wins erased an update). On Windows you may also see a
`PermissionError` — two processes fighting over the same open file. If the race refuses to
fire on your machine, that's luck, not safety — open `sutra_mcp/tasks.py` and point at the
read-modify-rewrite lines: no lock, no atomic rename, no transaction. Write the finding
down either way; a race you can *explain* is observed enough (and say which you got in
tonight's PROGRESS note).

**Step 5 — Fix it: the rack becomes transactional.**

In `sutra_mcp/tasks.py` (Day 36's module), migrate the JSON rack to a tiny SQLite table —
a *separate, writable* file (the archive stays read-only per Day 39):

```python
# sutra_mcp/tasks.py — storage swap, shape unchanged
# BEFORE (Day 36): json.load / dict update / json.dump of data/mcp_tasks.json
# AFTER: every instance reads/writes data/tasks.db (WAL mode: concurrent
# readers + a writer interleave safely; each UPDATE is atomic). Same
# functions, same claim tickets:
#   create_task() -> id     : INSERT the row, return the id
#   update_task(id, ...)    : UPDATE progress/state — atomic, no lost writes
#   get_task(id) -> dict    : SELECT — any instance, any moment, never torn
# sqlite3.connect("data/tasks.db"); con.execute("PRAGMA journal_mode=WAL")
# TODO(write the ~30 lines; mirror-test in tests/test_mcp_tasks.py:
#      create in one connection, update+get from a FRESH connection = the
#      two-instance situation in miniature; delete data/mcp_tasks.json after
#      migration so no code path can quietly fall back to it)
```

Restart [A] and [B], rerun the hammer. ✅ *Verify:* zero errors, progress only ever moves
forward, `done` stays `done`. Now the theatrical finale — **kill instance A mid-job**
(Ctrl+C in [A]) and keep polling through the proxy: the round-robin's A-requests fail
(Day 44 hardens that), but B answers every poll it receives, correctly, because the truth
lives in a transactional store, not in the fallen process — and not in a file two
processes were scribbling over. A server died and the *system* shrugged. That shrug is
MCP-21.

## 5 · 💥 Failure lab — the sticky-session siren

> 🎬 **The scene:** step 4's rack races, but in production, at 2 a.m. — progress bars
> jumping backwards, the occasional half-read JSON error. A teammate finds the
> industry-classic remedy in an old runbook: *session affinity* — configure the balancer
> so each client always lands on "its" instance. One writer per client's tasks, no more
> races. The bug vanishes. Everyone sleeps.
> 😬 **The naive fix:** ship the sticky config. It even has a checkbox in every cloud
> console — how wrong can a checkbox be?
> 💥 **Why it fails:** you have quietly rebuilt the phone call on top of the web. Instance
> A now *owns* its clients: deploy a new version → A drains and its tasks strand; scale
> from 2 to 5 instances → existing clients stay glued to the old 2 and the new 3 idle;
> A crashes → its clients' handles die with it, which is the original bug wearing a delay.
> Worse, the checkbox *hides* the design flaw instead of fixing it — the state is still in
> a process's head; you've just bribed the router to pretend that's fine. The 2026 spec
> didn't add statelessness as an optimization; it removed sessions so this checkbox would
> have nothing to protect.
> 💡 **The insight:** **state moves down (shared storage) or out (the payload) — never
> sideways (the connection).** Affinity is an anesthetic, not a cure: the pain returns at
> the worst moment reality can schedule. If a handle must outlive a process, the data
> behind it must live where every process can reach it — that's the whole fix, and it was
> 30 lines.

## 6 · 🎤 Interview corner

1. **"How do you prove a service is actually stateless?"** — Adversarially: two instances
   behind a deliberately dumb round-robin, run the full client suite, then hammer the
   long-job flow with concurrent traffic. My MCP server passed the reads and failed the
   hammer — its task rack was a shared JSON file, so two instances doing
   read-modify-rewrite gave me lost updates and torn reads: progress moving backwards,
   half-written JSON. Migrating the rack to SQLite in WAL mode made the hammer clean,
   including kill-one-instance-mid-job. Lesson: 'shared storage' silently means
   'transactional shared storage' the moment there's a second writer — and statelessness
   is a property you demonstrate under instance churn, not a word in the README.
2. **"What did the 2026 MCP revision change for deployment?"** — It deleted the things
   that forced affinity: no initialize, no session — every request self-contained with its
   version and capabilities in `_meta`, so any instance answers any request behind a plain
   balancer. Plus routable headers (`Mcp-Method`, `Mcp-Name`) so infrastructure can steer
   and meter calls without parsing JSON, and cacheable list results. Long-lived work
   becomes explicit handles whose backing state you keep in shared storage.
3. **"When is session affinity the right answer?"** — Almost never as a *fix* — as a fix
   it's an anesthetic for state that's living in the wrong place, and it bites back on
   deploys, scaling, and crashes. Legitimate uses are narrow performance cases (warm local
   caches) where correctness never depends on hitting the same instance. My rule: if
   affinity failing would produce a wrong answer rather than a slow one, the design is
   broken.
