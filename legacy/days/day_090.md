## 1 · 🎬 Where we are — the story so far

Yesterday Sutra learned to check a signature and came away with a sharp, narrow result:
it now knows *who wrote a card*. That is real progress, and it is also conspicuously less
than it sounds, because every question that actually matters at runtime is still open.

A request arrives at Sutra's A2A endpoint. Right now, Sutra will answer it. Not because it
decided to — because nobody wrote the code that decides. `securitySchemes` on the card is
empty, which is a *claim* that no credential is needed, and Day 89 §7 made you say that out
loud specifically so it would itch today. Anyone who can reach the port is, as far as
Sutra is concerned, an authorised caller.

And there is a second gap, quieter and worse. When Sutra calls the release-notes peer, it
calls as *Sutra*. But Sutra is acting for a support engineer who is acting for a customer.
Three identities are involved and the wire carries none of them. If that peer logs
anything, it logs "an agent asked" — which is not enough for an audit, a rate limit, or a
revocation.

Today Sutra gets an identity, learns to demand one from callers, and gets a registry:
a written, checkable answer to "which agents exist, who runs them, and what may they do".
Google sells a very good one. You cannot afford it, so you will build the twenty-line
version that teaches the same thing and read theirs closely enough to say what you gave up.

## 3 · 📚 Concepts

### AG-29 — four words people use interchangeably, and one real request

**The story.** Someone rings the office doorbell.

| Word | The doorway version | The wire version |
| --- | --- | --- |
| **Identification** | "It's Priya from Acme" | a name/id in the request |
| **Authentication** | the Acme badge you photograph and check | a signature or token you verify |
| **Authorization** | badge-holders may enter the lobby, not the server room | a policy table you consult |
| **Delegation** | "Priya is here to collect a parcel *for Sam in Finance*" | an on-behalf-of chain in the request |

Everyone says "auth" and means two of these. The bugs live in the gaps: a system that
authenticates perfectly and authorizes nothing lets a verified stranger into the server
room, which is exactly the shape of Day 89's failure lab.

Now the real request, and this is the diagram that goes at the top of `docs/REGISTRY.md`:

```
customer  ──asks──▶  support engineer  ──uses──▶  Sutra  ──calls──▶  release_notes_peer
 (data subject)        (human principal)        (agent)              (someone else's agent)
```

Four parties. When the peer receives that call, **which identity should it see?**

- Only Sutra's → the peer cannot rate-limit or audit per customer, and cannot honour a
  revocation aimed at one engineer.
- Only the engineer's → Sutra has impersonated a human. Now nobody can tell which actions
  a person took and which an agent took on their behalf — the distinction that matters
  most the day something goes wrong.
- **Both, explicitly** → the peer sees *this agent, acting for this principal*. That is
  delegation, and it is the only option that stays true.

💡 **Mental model: an agent's identity is a badge, not a mask.** It never replaces the
human's identity; it accompanies it. If your logs cannot answer "which human is this
ultimately for?", you have built a mask.

⚠️ **The distinction that gets people fired:** an agent acting *as* a user inherits every
permission that user has, invisibly — and agents make far more calls per second than
humans, so a mistake scales at machine speed. An agent acting *for* a user carries its own
identity with its own, smaller permission set, and the intersection is what applies. Day 70
already built the smaller set (`ROLE_TOOLS` — the writer role holds nothing). Today makes
the *caller* side match.

**Where identity actually comes from** — ranked, because this is a great interview answer:

| Mechanism | Strength | Sutra |
| --- | --- | --- |
| A name in a JSON field | ❌ none — it is a claim | what Sutra does *today*, before Step 5 |
| A shared secret / API key | 🟡 works, but it is a bearer token: whoever holds it *is* you, and it does not expire | fine for a laptop, written down as such |
| A signature over the request (asymmetric) | ✅ the caller proves possession of a private key; nothing secret crosses the wire | **today's build** — reuses Day 89's ES256 machinery |
| Platform-issued workload identity | ✅✅ no key exists to steal; the platform vouches | 🅿️ — this is what Day 88's `adk-agent-sa` + Workload Identity row was, and why that row was the interesting *absence* |

Note the through-line: Day 88 noticed that GKE's reference deployment needs no key because
the platform *is* the credential; Day 89 signed a document; today signs a *request*. Same
idea, three layers.

### ADK-71 — a registry is a list you can revoke from

**The story.** A building with fifty contractors has a list at the desk: who they are, who
hired them, which floors, until when. The list is boring. The list is also the only thing
that lets you say "not any more" once, in one place, instead of hunting down fifty badges.

A registry answers four questions and no more: **which agents exist · who owns each ·
what may it do · until when.** Everything else in registry products is convenience.

**Google's Agent Registry** (`adk.dev/integrations/agent-registry/`, read 2026-08-20) —
the exact surface, so `docs/REGISTRY.md` can be specific rather than vague:

```python
# pip install "google-adk[a2a,agent-identity]"
from google.adk.integrations.agent_registry import AgentRegistry

registry = AgentRegistry(project_id="...", location="global")   # or e.g. "us-central1"
```

| Method | Returns |
| --- | --- |
| `list_agents()` / `list_mcp_servers()` | enumerate what the org has registered |
| `get_agent_info(name)` / `get_mcp_server(name)` | metadata for one entry |
| `get_remote_a2a_agent(agent_name)` | a ready `RemoteA2aAgent` (Day 89) |
| `get_mcp_toolset(mcp_server_name)` | a ready `McpToolset` (Day 32) |

Two things are worth noticing about that table, and they are the reason it is on the
curriculum at all:

1. **It hands you back the same objects you already build by hand.** Day 89's
   `RemoteA2aAgent` and Day 32's `McpToolset` are the return types. The registry is not a
   new runtime — it is *late binding*: your code says "the agent named `release-notes`"
   instead of a hard-coded URL, and the org decides at call time which endpoint that is,
   whether it still exists, and whether you may have it.
2. **`get_*` is where governance lands.** Once resolution goes through a service, the org
   can revoke, rotate an endpoint, or retire an agent without anyone editing code. That is
   the whole product, and it is also exactly what `registry/peers.json` will do today at
   1/1000th the scale.

🅿️ **Why it is parked, precisely.** `AgentRegistry` needs the Agent Registry API enabled on
a Google Cloud project plus `GOOGLE_CLOUD_PROJECT` / `GOOGLE_CLOUD_LOCATION`, and the
module imports the A2A SDK *and* the Agent Identity auth provider at module scope — so it
needs both extras (`google-adk[a2a,agent-identity]`) or it raises `ImportError` on import
alone. Addendum 02 forbids the billed project, so the extra is **not installed** and the
code is **not run**. `docs/REGISTRY.md` carries the install line, the constructor, the
method table above, the date they were read, and one sentence on what Sutra's file-backed
version gives up: **no central authority, no cross-team revocation, no audit trail anyone
else can see.** That sentence is the honest cost, and knowing it is the deliverable.

**Step 3 — Sutra's own identity.**

`sutra/identity.py` — the module that will own every "who is this?" answer in the repo:

```python
"""Agent identity: who Sutra is, who is calling, and on whose behalf.

Four questions, kept deliberately separate (Day 90 §3):
  identify()  — who does this request CLAIM to be?
  verify()    — can it prove it?
  authorize() — is it allowed to do this specific thing?
  delegation  — whose authority is it acting under?

Everything here fails closed. An identity that cannot be verified is not a
degraded identity, it is no identity.
"""
```

The agent id itself should be **derived from the key, not chosen** — a name you pick is a
claim; a fingerprint is a fact:

```python
def agent_id(public_key_pem: bytes) -> str:
    """Stable id for an agent: 'sutra:' + first 16 hex of SHA-256 over its public key.

    Deriving the id from the key means rotating the key changes the id, which is
    the honest behaviour: a new key IS a new identity until someone vouches that
    it is the same agent. That vouching is what a registry is for.

    Example:
        >>> agent_id(Path("secrets/a2a_signing_key.pub").read_bytes())
        'sutra:3f9a1c74b0e2d558'
    """
```

**Step 5 — inbound authentication.** Today's central change: Sutra stops answering
strangers.

The caller signs a small assertion — its `agent_id`, the target skill, a timestamp and a
nonce — with its private key, and sends it in an `Authorization` header. Sutra's A2A app
gets middleware that runs **before** the agent:

```python
# In sutra/a2a_peer.py — wraps the ASGI app from to_a2a().
# Order matters: identity is checked before a single token is spent.
async def require_caller_identity(request, call_next):
    ...
```

Five checks, fail closed, cheapest first:

1. Header present → else **401**.
2. `agent_id` is in the registry → else **401** (and log the id, so you can see who is
   knocking).
3. Entry not expired → else **401** with `expired` in the log.
4. Signature verifies against the registered `kid` → else **401**.
5. Timestamp within ±60s and nonce unseen → else **401** with `replay` — otherwise a
   captured header is a permanent credential.

```powershell
# no credential at all
curl.exe -i -X POST http://localhost:8001/ -H "Content-Type: application/json" -d "{}"
# a valid one, minted by the peer's key
python tools\mint_assertion.py --as peer --skill archive_research | % { curl.exe -i -X POST http://localhost:8001/ -H "Authorization: $_" ... }
```

✅ *Verify:* three outcomes observed — **401** with no header · **401** with a header signed
by a key not in the registry · **200** with a good one. And check the *token* cost: the
401s must not appear in the quota ledger at all (`logs/quota.json` unchanged). If they do,
the middleware is running after the agent and an unauthenticated stranger can spend your
free tier.

⚠️ The card's `securitySchemes` must now describe this scheme. A card that says "no
credential needed" while the endpoint returns 401 is a card that lies — and it is signed,
so it lies durably. Update `sutra/agent_card.json`, **re-sign it** (Day 89 Step 5), and

## 5 · 💥 Failure lab — the agent that inherited a person

> 🎬 **The scene:** Step 5 works, and it feels restrictive. The support engineer asks Sutra
> to look up a customer's account details, and Sutra can't — the archive tool it holds is
> narrower than the engineer's own access. The engineer *is* allowed to see this. It looks
> like a bug in your own system, and there is an obvious fix that a real team would ship
> under deadline: let the agent act **as** the user. Pass the engineer's own session token
> through to the tools, and Sutra can do anything the engineer can do.
>
> One field. Everything unblocks. Ticket closed, and the team is pleased.
>
> 😬 **The naive fix:** it *is* the naive fix — impersonation. Note how reasonable it
> sounds: "the agent should have exactly the permissions of the person it's helping."
>
> 💥 **Why it fails**, in four ways that arrive in order of increasing cost:
>
> **(1) The audit log becomes fiction.** Every action now reads as the engineer's. When
> someone asks "did a human approve this refund or did the agent decide?", the log cannot
> answer — the two are the same identity. Day 63 built an approval gate whose entire value
> is the difference between those two answers, and one field just erased it.
>
> **(2) The blast radius becomes the human's, not the agent's.** A support engineer can
> read every ticket in the queue. A human doing that takes weeks and would look odd on
> Tuesday afternoon. An agent under prompt injection (Day 66) does it in ninety seconds,
> with the engineer's badge on every read. Day 70's `ROLE_TOOLS` deliberately gave the
> writer role *nothing*; impersonation hands it the union of every permission the human
> holds, including ones nobody thought about because no human would ever use them that
> way.
>
> **(3) Revocation stops working.** Step 7's revocation targets an *agent* id. If the agent
> presents the engineer's identity, revoking the agent revokes... the engineer. So the
> real-world response is to not revoke — which means the control you built is one you will
> never actually pull.
>
> **(4) It is contagious across the boundary.** Sutra calls the peer with the engineer's
> token. The peer now holds a credential belonging to a human at your company, and its
> logs, its cache and its incident reports now contain it. You have exported a person's
> authority to a third party, and Day 92's security review has to ask them what they did
> with it.
>
> 💡 **The insight: an agent should act *for* a principal, never *as* one.** The permission
> that applies is the **intersection** — what the agent is allowed to do ∩ what the
> principal is allowed to do — never the union, and never a substitution. That intersection
> is smaller than both, deliberately, and the gap you hit at the top of this scene is
> supposed to exist. When it blocks something legitimate, the fix is to widen the *agent's*
> permission by one specific tool, in code, in review — not to dissolve the boundary.
>
> The one-line test, worth memorising: **"After this change, can my log tell the difference
> between the human doing it and the agent doing it?"** If no, you have built
> impersonation, whatever the field is called.
>
> Concretely, today:
>
> - `DELEGATION` carries `agent` **and** `on_behalf_of` as separate fields. There is no
>   code path that sets `agent` to a human id — add a test that asserts exactly that, since
>   this is the kind of thing a well-meaning refactor introduces.
> - Authorization computes the intersection: `may(agent_role, tool)` (Day 70) **and** the
>   principal's own rights. Two checks, both must pass.
> - The engineer's token never leaves Sutra. Outbound calls carry Sutra's identity plus the
>   principal's *identifier* — an id is not a credential, and that distinction is the whole
>   design.
> - `docs/REGISTRY.md` gets the paragraph, because in six months the deadline version of
>   this conversation will happen again and the document is the only participant that will
>   remember.

## 6 · 🎤 Interview corner

1. **"How do you know which agent is calling your service?"** — I make them prove it, and
   I keep the four questions separate: identification is a claim in the request,
   authentication is a signature I verify, authorization is a table I consult, delegation
   is who they're acting for. Concretely, a caller signs a small assertion — its agent id,
   the skill, a timestamp and a nonce — with its private key; my middleware checks the id
   against a registry, checks the entry hasn't expired, verifies the signature against the
   registered `kid`, and rejects replays outside a ±60s window. All of that runs *before*
   the agent, which matters more than it sounds: on a free tier, an unauthenticated
   stranger who reaches your model has spent your quota whatever you do next, so I verified
   the 401s don't touch the quota ledger. The agent id itself is derived from the public
   key rather than chosen, because a name is a claim and a fingerprint is a fact. The
   strongest version of this is platform workload identity, where no key exists to steal —
   that's what GKE's service-account binding does, and I documented it as the thing I gave
   up by staying on a free tier.
2. **"You built your own registry instead of using one. Defend that."** — The requirement
   is four questions: which agents exist, who owns each, what may it do, until when. That's
   a validated JSON file and about twenty lines, and it gave me the two behaviours that
   matter — an `expires` field so a forgotten integration turns itself off, and revocation
   that takes one edit and no deploy, which I proved by revoking a peer mid-session and
   watching the next call get refused and logged while the run degraded gracefully. Google's
   Agent Registry is the real version: `AgentRegistry(project_id, location)` with
   `list_agents()`, `get_agent_info()`, `get_remote_a2a_agent()` and `get_mcp_toolset()` —
   note it hands back the same `RemoteA2aAgent` and `McpToolset` objects I already build,
   so the product isn't a new runtime, it's late binding plus governance. It needs a billed
   project and both the `a2a` and `agent-identity` extras, which this project doesn't have,
   so it's documented and not run. What I gave up is specific: no central authority, no
   cross-team revocation, no audit trail anyone outside my repo can see.
3. **"Should an agent use the user's credentials?"** — No, and this is the mistake I find
   most tempting, because it presents as a bug fix. My agent's tool access is narrower than
   the engineer it helps, so there's a moment where something legitimate is blocked and one
   field — pass the user's token through — unblocks everything. It costs four things: the
   audit log can no longer distinguish a human's action from the agent's, which destroys
   the value of the approval gate I built; the blast radius under prompt injection becomes
   everything that human may do, at machine speed; revoking the agent now means revoking
   the person, so nobody ever pulls the lever; and if it's forwarded to a partner, you've
   exported an employee's authority to a third party. The rule is act *for*, never *as* —
   the effective permission is the intersection of the agent's rights and the principal's,
   and outbound calls carry the principal's *identifier*, not their credential. My test for
   any change in this area is one question: can the log still tell the difference between
   the human doing it and the agent doing it?
