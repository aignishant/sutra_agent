## 1 · 🎬 Where we are — the story so far

Sutra can be *graded* (Phase 12) but it cannot be *watched*. When a triage run takes
forty seconds, nobody can say where the forty seconds went. When an eval case fails,
the only evidence is the final text and whatever `logs/sutra.jsonl` happened to record
(Day 22). The graph has nine nodes, five plugins, four lanes and a cache; a failure
inside it is currently diagnosed by adding print statements and running it again — which
costs quota, and which changes the thing being measured.

Twelve phases of discipline have produced a system whose behaviour is checked but whose
*mechanism* is opaque. Today that ends. Tonight one triage run produces a tree: the
invocation at the root, every node under it, every model call and tool call under those,
each with a duration, and the whole thing readable in a browser at `localhost:16686`.

And the moment that tree exists, it becomes a **new egress path** — which is why the
data boundary has to follow it there. That is today's failure lab, and it is the real
lesson.

## 3 · 📚 Concepts

### ADK-63 — A log is a photograph; a trace is the film, with a stopwatch running

**The story.** A parcel goes missing. You have photographs: one of the parcel leaving
the warehouse, one of it in a van, one of an empty doorstep. Each photo is true. None of
them tells you that the van sat for two hours outside a depot, because nobody
photographed the waiting. Now imagine instead a record where every leg of the journey is
an entry with a *start time*, an *end time*, and a *parent leg it belongs to*. You can
see the two hours immediately — it is the gap that is not covered by any child.

That record is a **trace**. Each leg is a **span**.

| Word | Plain meaning | In Sutra |
| --- | --- | --- |
| **Trace** | one whole journey, start to finish | one invocation of `triage_graph_v1` |
| **Span** | one leg of it, with a start, an end, and a name | `execute_tool lookup_ticket` |
| **Parent span** | the leg this leg happened inside | `invoke_agent evidence_analyst` |
| **Attributes** | labelled facts stuck to a leg | model name, token counts, tool args |
| **Trace ID** | the number that ties all the legs together | one per `invocation_id` (Day 60) |

The difference from logging (Day 22) is not detail — it is **structure and duration**.
A log line says *"lookup_ticket returned"*. A span says *"lookup_ticket ran for 41 ms
inside evidence_clerk_a, which ran inside the parallel branch, which ran inside
invocation 8f3c…"*. Only the second one can answer "what was slow" or "what ran twice".

💡 **Mental model: logs answer *what happened*; traces answer *what happened inside what,
and for how long*.** You keep both. Logs are for grepping after the fact; traces are for
looking at a shape.

**The span names ADK emits** (verified on `adk.dev/observability/traces/`, 2026-08-20) —
learn these four, because they are what you will search for in the UI:

| Span name pattern | Emitted for |
| --- | --- |
| `invoke_agent {agent.name}` | one agent's turn |
| `invoke_workflow {workflow.name}` | one graph run (Day 53's Workflow Runtime) |
| `generate_content {model.name}` | one model call |
| `execute_tool {tool.name}` | one tool call |

Note what that gives you for free: `generate_content gemini-3.5-flash-lite` spans are
exactly the calls Day 70's Quota-Router billed. Two independent records of the same
event — which means they can be cross-checked, and Day 96's retrospective will.

### ADK-74 — One plugin instruments everything (and it does it by monkey-patching)

The naive way to trace a codebase is to decorate it: `@tracer.start_as_current_span` on
every function you care about. That works and it rots — new node, forgotten decorator,
blind spot. ADK 2.2 shipped the alternative.

**Verified from source** (`src/google/adk/plugins/auto_tracing_plugin.py`, read
2026-08-20). Its module docstring is one line and tells you the whole design:

> "Monkey-patches Python fns to emit OpenTelemetry spans."

```python
class AutoTracingPlugin(BasePlugin):
    def __init__(
        self,
        *,
        name: str = "AutoTracingPlugin",
        extra_scope_prefixes: tuple[str, ...] = (),
        tracer: trace.Tracer | None = None,
        max_repr_len: int = auto_tracing_helpers.DEFAULT_MAX_REPR_LEN,
        max_recorded_yields: int = auto_tracing_helpers.DEFAULT_MAX_RECORDED_YIELDS,
        max_walk_depth: int = DEFAULT_MAX_WALK_DEPTH,
    ):
```

Three of those parameters are today's actual controls:

- **`extra_scope_prefixes`** — by default it instruments ADK's own modules. Give it
  `("sutra",)` and it walks *your* package too, so `sutra.graph` nodes and
  `sutra.retrieval` helpers get spans without a single decorator.
- **`max_repr_len`** — how much of each argument's `repr()` gets recorded as an
  attribute. This is a **privacy control**, not a tidiness control (see §5).
- **`max_walk_depth`** — how deep into the module tree it patches. Deeper = more spans
  = more overhead and more recorded arguments.

⚠️ **Import path trap — pinned from source, 2026-08-20.** `google/adk/plugins/__init__.py`
declares `__all__` as `BasePlugin`, `DebugLoggingPlugin`, `LoggingPlugin`,
`PluginManager`, `ReflectAndRetryModelPlugin`, `ReflectAndRetryToolPlugin`.
**`AutoTracingPlugin` is not in it.** So this fails:

```python
from google.adk.plugins import AutoTracingPlugin          # ✗ ImportError
from google.adk.plugins.auto_tracing_plugin import AutoTracingPlugin   # ✓
```

The plugin implements **`before_run_callback`** — it hooks in once at the start of an
invocation and installs its patches; it is not a per-model or per-tool hook like Day 70's
router. That is why its position in the plugin list matters differently from the others
(Step 5).

### OPS-16 — Where do the spans go? (the free answer)

A tracer produces spans; something has to *receive* them. Three receivers exist, and
Addendum 02 picks for us:

| Receiver | How | Cost | Sutra's use |
| --- | --- | --- | --- |
| **Console exporter** | spans printed to stdout | free | the fallback; always works; unreadable past ~20 spans |
| **Local collector (Jaeger all-in-one)** | OTLP over HTTP → `localhost:4318`, UI on `:16686` | free, one container | **the default this phase** |
| **Google Cloud Trace** | `from google.adk.telemetry.google_cloud import get_gcp_exporters`, or `adk web --otel_to_cloud` | **billed** | 🅿️ documented, never run |

The wiring is standard OpenTelemetry, which is the point: ADK does not invent a protocol,
it speaks OTLP. Two facts from `adk.dev/observability/traces/` (2026-08-20):

- the environment variable is **`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`**;
- the helper is `from google.adk.telemetry.setup import maybe_set_otel_providers`.

🅿️ **Parked, know the map:** the same OTLP endpoint is what Datadog, Grafana Cloud,
Arize AX, Phoenix, W&B Weave and MLflow Tracing all consume (they are all listed on
`adk.dev/integrations/`). Swapping Jaeger for any of them is a URL and a header. That is
the *entire* value of the standard, and it is worth one sentence in an interview.

**Step 4 — `sutra/tracing.py`.** Small on purpose: one setup function, one plugin
factory, one scrubber (Step 6 fills the scrubber in).

```python
"""OpenTelemetry wiring for Sutra.

One module owns tracing so that every entry point — the graph, the API server
(Day 85), the nightly job (Day 73) and the eval runner (Day 82) — turns it on the
same way and inherits the same redaction rules.

Example:
    >>> from sutra.tracing import setup_tracing, tracing_plugin
    >>> setup_tracing()            # console exporter unless OTEL_..._ENDPOINT is set
    >>> plugins = [tracing_plugin(), DataBoundaryPlugin(), ...]
"""

from __future__ import annotations

import os

from opentelemetry import trace
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter

# Verified 2026-08-20: NOT re-exported from google.adk.plugins (see __all__).
from google.adk.plugins.auto_tracing_plugin import AutoTracingPlugin

from sutra.logging_setup import get_logger

logger = get_logger(__name__)

SERVICE_NAME = "sutra"
#: Env var ADK itself reads (adk.dev/observability/traces/, 2026-08-20). We read the
#: same one so `adk web` and our own entry points agree on where spans go.
OTLP_ENV = "OTEL_EXPORTER_OTLP_TRACES_ENDPOINT"

_configured = False


def setup_tracing(*, force_console: bool = False) -> TracerProvider:
    """Install a global TracerProvider. Safe to call more than once.

    Chooses the exporter from the environment: if OTEL_EXPORTER_OTLP_TRACES_ENDPOINT
    is set (e.g. "http://localhost:4318/v1/traces") spans go to that collector;
    otherwise they are printed. Never talks to a billed backend.
    """
    global _configured
    if _configured:                                   # idempotent: the API server and
        return trace.get_tracer_provider()            # the nightly may both call it
    provider = TracerProvider(
        resource=Resource.create({"service.name": SERVICE_NAME})
    )
    endpoint = os.getenv(OTLP_ENV)
    if endpoint and not force_console:
        # Imported lazily so a missing exporter package degrades to console,
        # rather than breaking every entry point at import time.
        from opentelemetry.exporter.otlp.proto.http.trace_exporter import (
            OTLPSpanExporter,
        )

        exporter = OTLPSpanExporter(endpoint=endpoint)
        logger.info("tracing_exporter", extra={"kind": "otlp", "endpoint": endpoint})
    else:
        exporter = ConsoleSpanExporter()
        logger.info("tracing_exporter", extra={"kind": "console"})
    provider.add_span_processor(BatchSpanProcessor(exporter))
    trace.set_tracer_provider(provider)
    _configured = True
    return provider


def tracing_plugin() -> AutoTracingPlugin:
    """The one AutoTracingPlugin Sutra registers.

    `extra_scope_prefixes=("sutra",)` makes it walk our package too, so graph nodes
    and helpers get spans without decorators. `max_repr_len` is deliberately small:
    span attributes are an egress path (see docs/DATA_BOUNDARY.md).
    """
    return AutoTracingPlugin(
        extra_scope_prefixes=("sutra",),
        max_repr_len=200,     # privacy control, not a tidiness control — see Day 84 §5
    )
```

Why first, when Day 69 said DataBoundary must be first? Because they are first in
*different senses*, and it is worth being precise: DataBoundary must be the first
**mutator** — nothing may alter a request before it has been redacted. `AutoTracingPlugin`
mutates nothing; it installs instrumentation in `before_run_callback`, before the
invocation starts. Putting it ahead of DataBoundary means the redaction *itself* shows up
in the trace, which is exactly what you want when you are debugging why something leaked.
**Order rule, written down: tracing is the outermost observer; DataBoundary is the
innermost-first mutator.** Add that sentence to `docs/DATA_BOUNDARY.md`.

**Step 6 — close the boundary: scrub the spans.** Do §5's failure lab *first*, then
come back and add this to `sutra/tracing.py`:

```python
from opentelemetry.sdk.trace import ReadableSpan, SpanProcessor

from sutra.data_boundary import redact_for_model


class RedactingSpanProcessor(SpanProcessor):
    """Redact span attributes on the way out, using the Day 69 door patterns.

    Spans leave the process. That makes them an egress path, so the same rules
    that guard the model prompt guard the trace. Wrapping the exporter's processor
    is the only place that sees every span exactly once.
    """

    def __init__(self, inner: SpanProcessor) -> None:
        self._inner = inner

    def on_start(self, span, parent_context=None) -> None:
        self._inner.on_start(span, parent_context)

    def on_end(self, span: ReadableSpan) -> None:
        for key, value in list(span.attributes.items()):
            if isinstance(value, str):
                span._attributes[key] = redact_for_model(value)   # noqa: SLF001
        self._inner.on_end(span)

    def shutdown(self) -> None:
        self._inner.shutdown()

    def force_flush(self, timeout_millis: int = 30_000) -> bool:
        return self._inner.force_flush(timeout_millis)
```

⚠️ `span._attributes` is private. That is a real smell and it needs a real comment, not a
bare `# noqa`: the OTel SDK freezes attributes at span end, and the documented seam for
this is a *collector-side* processor — which we do not have, because our collector is a
disposable container. Write that reasoning above the line. Then leave a TODO to move the
redaction into an OTel Collector config the day a collector exists (Day 86 has one
candidate: a `otel-collector` service in the compose file).

Wire it in `setup_tracing`: `provider.add_span_processor(RedactingSpanProcessor(BatchSpanProcessor(exporter)))`.

## 5 · 💥 Failure lab — the trace that leaked what the guardrails caught

> 🎬 **The scene:** you finish Step 5 and everything works. The tree is beautiful. You
> re-run the Day 69 PII fixture — the ticket whose body contains a customer's email
> address and a card number — to see how the redaction looks in a trace. The
> `generate_content` span shows the prompt with `[REDACTED_EMAIL]` and
> `[REDACTED_CARD]`. DataBoundaryPlugin did its job. You take a screenshot for the
> README.
>
> Then you click the span *above* it: `execute_tool lookup_ticket`. Its attributes
> include the tool's return value. There is the email address. There is the card number.
> Raw. And two spans further up, `invoke_agent evidence_clerk_a`'s attributes carry the
> repr of the row that came out of `data/tickets.db`.
>
> 😬 **The naive fix:** "the Jaeger container is on localhost, so it's fine" — or, one
> step better, add `lookup_ticket` to a list of tools whose spans are dropped.
>
> 💥 **Why it fails.** Two separate mechanisms, and both matter.
> First: **DataBoundaryPlugin guards the model call, not the process.** Its job (Day 69)
> is "nothing unredacted reaches a third-party model." `AutoTracingPlugin` records
> function arguments and return `repr`s *inside* your process, upstream of that
> redaction, by design — that is what makes it useful for debugging. The two are not in
> conflict; the boundary simply never covered this door, because until today the door
> did not exist.
> Second: **"it's only localhost" has a 48-hour shelf life.** On Day 86 this application
> goes into a container and the endpoint becomes a hostname on a Docker network. On Day
> 88 it becomes a Service in a cluster. On some later day somebody points
> `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` at a hosted backend — Datadog, Grafana, Arize;
> `adk.dev/integrations/` lists a dozen, and swapping is a URL — and every customer email
> Sutra has ever read is now in a third party's index, retained under *their* policy,
> with no record that it was ever sent. That is a data-protection incident produced
> entirely by a config change, which is precisely the kind that has no author.
> And dropping one tool's spans doesn't help: the same values ride in the clerk's span,
> the analyst's input, the retrieval chunk repr. Enumerating leaks is a losing game
> (Day 68 taught this with permissions: allowlists win, blocklists rot).
>
> 💡 **The insight: an observability pipeline is an egress path, and every egress path
> gets the same door.** The fix is not per-tool and not per-environment: it is one
> processor at the exit, running the same `redact_for_model` the model door runs, so
> there is exactly *one* definition of "must not leave" (Day 69's `DOOR_PATTERNS`) and
> exactly one place to fix when it changes. `max_repr_len` is the second, blunter half of
> the same idea: a truncated repr leaks less by construction, and 200 characters is
> plenty to debug with.

Two things follow, and both are load-bearing later:

- **`docs/DATA_BOUNDARY.md` gets a fourth door today** — the trace exporter, listed
  beside the model call, the log file and the browser box (Day 71). Day 92's security
  review reads that table; if the door isn't in it, the review will not check it.
- **Day 96's habit list gets a line:** whenever a new sink is added — an exporter, a
  webhook, a metrics backend — the question is not "is it safe?" but **"which door is
  it, and what redacts it?"**

## 6 · 🎤 Interview corner

1. **"You have logs. Why do you also need traces?"** — Because they answer different
   questions. My logs are JSON lines: good for "did the guardrail fire on 4521 last
   Tuesday". They cannot answer "where did the forty seconds go", because a log line has
   no duration and no parent. A trace does: one triage run is one tree — the workflow at
   the root, nine node spans, the model calls and tool calls under them, each timed. The
   first trace I looked at told me something my logs never had: my two "parallel"
   evidence clerks were serialised in wall-clock, because the free-tier lane is 5 RPM.
   Nobody would have grepped their way to that.
2. **"How did you instrument it — how much code?"** — Roughly forty lines, and none of
   it in the agent code. ADK ships `AutoTracingPlugin`, which monkey-patches functions to
   emit spans; I register it once on the App with `extra_scope_prefixes=("sutra",)` so it
   walks my package too. No decorators, so no blind spot when I add a node. It exports
   OTLP to a local Jaeger container — free, disposable — and falls back to a console
   exporter when no endpoint is set. Because it is plain OTLP, moving to a hosted backend
   is a URL change, not a rewrite. One gotcha worth knowing: the class is not re-exported
   from `google.adk.plugins`; you import it from
   `google.adk.plugins.auto_tracing_plugin`.
3. **"Did adding observability create any risk?"** — Yes, and finding it was the useful
   part of the day. My PII redaction guarded the *model call*. The tracer records
   function arguments and return values *upstream* of that, so the first trace tree I
   produced contained a customer email in a tool span, unredacted — invisible while the
   collector was on localhost, and a third-party data disclosure the moment someone
   repoints the OTLP endpoint at a hosted backend. I fixed it at the exit rather than
   per-tool: a span processor that runs the same redaction function as the model door,
   plus a short `max_repr_len` so truncation limits the blast radius by construction.
   The rule I wrote down is that an observability pipeline is an egress path, and every
   egress path gets listed in `DATA_BOUNDARY.md` with the thing that guards it.
