## 1 · 🎬 Where we are — the story so far

Two days ago, agents became stations on a belt: the **graph** decides who runs, agents
just work. That is one way to organize smart workers, and for pipelines it is the right
one. But watch a real support desk for an hour and you will see a second organization
pattern that no fixed belt can draw: the *shift lead*. A hard ticket comes in; the lead
reads it and says "Priya, take this one — it smells like the billing thing from March."
Nobody drew that hand-off on a floor plan. The lead **decided**, in the moment, based on
the ticket.

Today you build the shift lead. ADK calls the pattern **collaborative workflows**:
a parent agent with `sub_agents`, where the *model* chooses whom to bring in. And you will
build its quieter cousin — **agent-as-tool** — where a whole specialist agent is wrapped
up and handed to another agent as just one more tool on its belt-less desk. Day 16 already
smuggled that one in (`AgentTool.create()` around the searcher, to dodge the built-in-tool
exclusivity wall). Today it stops being a workaround and becomes a design choice you make
on purpose.

## 3 · 📚 Concepts

### ADK-38 — Delegation & transfer: the shift lead

**The mechanics, from the page.** You give a parent agent a staff list, and each staff
member a working style:

```python
lead = Agent(
    name="triage_lead",
    model="gemini-3.5-flash",
    instruction="...",
    sub_agents=[kb_specialist, archive_specialist],   # the staff list
)
```

Behind the scenes ADK **auto-generates one delegation tool per subagent, named after it**
— the lead's model literally sees tools called `kb_specialist` and `archive_specialist`
and "calls" a colleague the way it calls any tool. Day 4's insight completes itself:
first functions became forms; now *coworkers* are forms too.

Each subagent's `mode` sets the working style (the page's table, condensed):

| `mode` | Talks to the user? | Who ends the hand-off | Parallel-safe |
| --- | --- | --- | --- |
| `"chat"` (default) | fully — it can take over the conversation | manual transfer back | no |
| `"task"` | clarifying questions only | itself, via `finish_task()` | no |
| `"single_turn"` | never | itself, automatically, with its result | **yes** |

And the sentence that explains everything else on the page: *"the runtime determines the
appropriate control flow based on how the agent was invoked."* The same specialist returns
control differently as a graph node (control flows to the next edge) than as a delegate
(control returns to the lead). You do not wire returns; the invocation style implies them.

Two sharp edges, both from the docs, both worth saying out loud:

1. ⚠️ **`task` mode is disabled inside graph workflows** (Python v2.0.0). The two
   organization patterns do not blend freely — a graph wants nodes that finish, not
   colleagues that chat. When Day 58 assembles the full graph, its stations are plain
   agents and functions, not task-mode delegates.
2. **Isolation:** task/single_turn subagents run in isolated session branches — parallel
   delegates cannot see each other's events. Same law as yesterday's "no shared pencil,"
   enforced by the runtime this time.

**🅿️ Also on the map: Agent Routing** (adk.dev/agents/routing/) — an experimental feature
where a plain *routing function* (not a model) picks one agent per invocation: fallbacks,
A/B tests. The page ships TypeScript examples only; Python specifics are undocumented
today, so Sutra notes it and moves on.

### ADK-39 — Agent-as-tool: the consultant on speed-dial

Delegation *transfers* responsibility: the lead steps back. `AgentTool` does something
smaller and often smarter — it wraps a whole agent so another agent can use it **without
ever giving up the floor**:

```python
research_tool = AgentTool.create(kb_specialist)   # Day 16's shape; confirm via the probe
writer = Agent(..., tools=[research_tool, lookup_ticket])
```

**The consultant story.** The lead calls a consultant, asks one question, writes down the
answer, hangs up, and keeps working. The consultant never meets the customer. Compare
delegation: the lead walks the customer to the consultant's office and leaves. Both are
legitimate; they are different *social contracts*.

| | Delegation (`sub_agents`) | Agent-as-tool (`AgentTool`) |
| --- | --- | --- |
| Who owns the conversation after | the specialist (until it returns) | the caller — always |
| What the specialist sees | its own session branch | just the tool-call arguments |
| Result shape | the specialist's answer becomes the reply | a tool result the caller can use, quote, or ignore |
| Feels like | "take this ticket" | "quick question" |

💡 **Mental model: delegation hands over the steering wheel; agent-as-tool keeps the wheel
and opens the glovebox.** If the caller needs to keep judging after the answer comes back
— keep the wheel.

### AG-16 — The decision: where does judgment live?

Strip the framework away and there is one question with three honest answers. You now hold
all three:

| The step is… | The right home | Why |
| --- | --- | --- |
| Known in advance, same every time | **an edge** (graph, Days 53–54) | determinism is free; models add variance and cost |
| A bounded question inside a bigger judgment | **agent-as-tool** | caller keeps context and the wheel; specialist stays cheap and isolated |
| A genuinely different job needing its own conversation | **transfer/delegation** | the specialist needs the floor, its own instruction, maybe its own model lane |

*Concrete Sutra example, one row each:* "after classify, run research" — edge, always.
"Writer needs one KB fact mid-draft" — agent-as-tool. "This ticket turned out to be a
refund dispute; the billing agent should own it end-to-end" — transfer.

💡 **Mental model: choose the smallest hand-off that does the job.** Edge < tool <
transfer, in blast-radius order (Principle 13 again — a transfer grants a whole
conversation; a tool call grants one question). When unsure, start smaller; promoting a
tool to a delegate later is cheap, demoting a delegate that users already talk to is not.

```python
"""Day 55 — the shift lead: delegation, transfer, and agent-as-tool.

Two organization patterns for the same specialists:
  lead demo  -> sub_agents delegation (the model picks the colleague)
  tool demo  -> AgentTool (the caller keeps the wheel, specialist = glovebox)

Run from repo root:
    python -m sutra.delegation lead    # ~3 LLM calls
    python -m sutra.delegation tool    # ~2-3 LLM calls
"""
from __future__ import annotations

import sys

from google.adk.agents.llm_agent import Agent
from google.adk.tools import AgentTool                 # probe-confirm import (header)

from sutra.adk_tools import lookup_ticket, search_kb   # Day 10's FunctionTools
from sutra.config import load_env
from sutra.logging_setup import get_logger

log = get_logger(__name__)

PRIMARY = "gemini-3.5-flash"                           # pinned (ADK-73)
LITE = "gemini-3.5-flash-lite"                         # cheap lane for specialists

# --- the two specialists: narrow, single_turn, parallel-safe ----------------

kb_specialist = Agent(
    name="kb_specialist",                              # this NAME becomes the lead's
    model=LITE,                                        #   delegation tool name!
    mode="single_turn",                                # answers once, returns control
    instruction="""You answer ONE question against the knowledge base using
search_kb. Quote the article id (e.g. KB-104). If nothing matches, say so.
Never invent articles.""",
    tools=[search_kb],
)

archive_specialist = Agent(
    name="archive_specialist",
    model=LITE,
    mode="single_turn",
    instruction="""You look up ONE ticket by id using lookup_ticket and
report its contents in one sentence. If the ticket does not exist, say
exactly that. Never invent ticket contents.""",
    tools=[lookup_ticket],
)

# --- pattern 1: the shift lead (delegation via sub_agents) ------------------

triage_lead = Agent(
    name="triage_lead",
    model=PRIMARY,                                     # judgment lane for the router-brain
    instruction="""You are the triage shift lead. Read the user's request and
hand it to the right specialist: kb_specialist for how-to/symptom questions,
archive_specialist for "what does ticket N say" questions. Delegate — do not
answer from memory. Summarize the specialist's finding in your reply.""",
    sub_agents=[kb_specialist, archive_specialist],    # the staff list; ADK generates
)                                                      #   one delegation tool per name

# --- pattern 2: the consultant (agent-as-tool) ------------------------------

kb_tool = AgentTool.create(kb_specialist)              # Day 16's shape — if your probe
                                                       # showed AgentTool(agent=...) is
                                                       # current, use that and note it.

drafting_writer = Agent(
    name="drafting_writer",
    model=PRIMARY,
    instruction="""Draft a 2-3 sentence reply to the user's ticket. Use
lookup_ticket for the ticket text, and consult the kb_specialist tool when
you need the fix. YOU write the final reply — the specialist only feeds you
facts. Cite the KB id you used.""",
    tools=[lookup_ticket, kb_tool],                    # a person and a database, both
)                                                      #   just tools from where it sits


def _run(agent: Agent, prompt: str) -> None:
    """Drive one agent and narrate delegation/tool calls from the event stream.

    Example:
        >>> _run(triage_lead, "What does ticket 4521 say?")
        CALL: archive_specialist({...})   # the auto-generated delegation tool
        FINAL: ...
    """
    import asyncio
    from google.adk.runners import InMemoryRunner
    from google.genai import types

    async def go() -> None:
        runner = InMemoryRunner(agent=agent, app_name="sutra")
        session = await runner.session_service.create_session(
            app_name="sutra", user_id="u1")
        msg = types.Content(role="user", parts=[types.Part(text=prompt)])
        async for ev in runner.run_async(user_id="u1", session_id=session.id,
                                         new_message=msg):
            for fc in (ev.get_function_calls() or []):   # Day 7's accessor, reused
                print(f"CALL: {fc.name}({fc.args})")     # delegation tools show HERE
            if ev.is_final_response():
                print("FINAL:", (ev.output or ev.message or "").strip()
                      if hasattr(ev, "output") else ev)  # print-then-pin the text field

    asyncio.run(go())


def main() -> None:
    demos = {
        "lead": lambda: _run(triage_lead, "What does ticket 4521 actually say?"),
        "tool": lambda: _run(drafting_writer,
                             "Draft a reply for ticket 4521 (user keeps getting logged out)."),
    }
    name = sys.argv[1] if len(sys.argv) > 1 else "lead"
    if name not in demos:
        print(f"usage: python -m sutra.delegation [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the coordinator who answers everything itself

> 🎬 **The scene:** you demo the lead to a friend. They ask it "what does ticket 4521
> say?" — and the lead answers *without delegating*: "Ticket 4521 appears to describe a
> login issue…" Plausible. Fast. And invented — the lead has no `lookup_ticket`; it has
> colleagues it declined to call.
> 😬 **The naive fix:** strengthen the prompt: "You MUST ALWAYS delegate!!" More caps,
> more musts.
> 💥 **Why it fails:** you have seen this movie twice. Day 4: a prompt is a request, not a
> law — delegation tools are still just tools the model may skip when it feels confident
> (and confident-but-wrong is the one failure mode LLMs never announce). Day 12's cousin
> failure: the instruction "usually" holds. On the tickets where the lead's prior is
> strongest — the familiar-looking ones — it will freelance the most, which means your
> most common tickets get the most invented answers. The fix is structural, not
> rhetorical: the lead's OWN toolbox is empty *by design* (look at the listing — no
> `lookup_ticket` on the lead), its instruction says "never from memory," and the honesty
> rule rides in every specialist. But the real spine is Sutra-wide: answers must cite
> tool-sourced facts, and Phase 12's evals will fail any trajectory where a reply cites no
> tool result. Belt (structure), braces (instruction), and an inspector (evals).
> 💡 **The insight:** **a coordinator you want to always delegate should have nothing else
> it can do.** Capability design beats prompt begging — remove the option, don't forbid
> it. (Principle 13, in its friendliest costume.)

## 6 · 🎤 Interview corner

1. **"Delegation vs agent-as-tool — when each?"** — By who keeps the conversation.
   Agent-as-tool keeps the caller in charge: the specialist answers one bounded question
   into the caller's context, never meets the user — right when judgment must continue at
   the call site. Delegation transfers the floor: the sub-agent owns its own session
   branch and returns per its mode. My heuristic is blast-radius order — edge, then tool,
   then transfer — take the smallest hand-off that does the job.
2. **"How does ADK implement delegation under the hood?"** — As tool-calling: the parent
   gets one auto-generated tool per sub-agent, named after it, and 'transferring' is the
   model calling that tool. Which means every tool discipline transfers verbatim —
   descriptions are prompt engineering, calls are visible in the event stream for audit,
   and the model can decline to call — so structural guarantees (an otherwise-empty
   toolbox) beat instruction-level begging.
3. **"Any sharp edges mixing delegation with graph workflows?"** — Yes, a documented one:
   task-mode collaboration is disabled inside Python graph workflows in 2.0 — a graph
   wants nodes that finish, not colleagues holding conversations. So I compose at one
   altitude at a time: graphs for the pipeline spine, delegation inside a node where
   in-the-moment judgment picks the worker. And parallel delegates run in isolated session
   branches — same no-shared-state law as parallel graph branches, enforced by the runtime.
