## 1 · 🎬 Where we are — the story so far

Sutra now has a front door (Day 85) and a way to watch itself (Day 84). It also has a
dependency on your laptop that nobody has ever written down: a particular Python, a
particular `uv` lockfile, a `.env` in a particular folder, an `ollama` on `:11434`, a
`sutra-mcp` you start by hand in a second terminal, and six SQLite files in `data/`.
"It works on my machine" is not a joke here — it is currently the *specification*.

Today Sutra gets packaged. Not deployed to a cloud — Addendum 02 forbids spending — but
packaged into the exact shape a cloud would run: one stateless container, configuration
and secrets from the environment, a port it is told about, a healthcheck it answers, and
a second container beside it for the MCP server. Everything a Cloud Run or a GKE
deployment would do, done locally with `docker compose`, for free.

The interesting part is not the Dockerfile. It is what containerising **reveals**: this
system is not as stateless as it looks, and today is when you find out precisely where.

## 3 · 📚 Concepts

### ADK-66 — A container is a recipe that cannot lie

**The story.** Two cooks make the same soup. One writes "some stock, an onion, simmer
until done". The other writes "800 ml of *this* stock, one onion 150 g, 22 minutes at a
bare simmer in a 20 cm pan". Both recipes work — for their author. Only the second one
works for a stranger, and only the second one tells you which change broke it when it
stops working.

A container image is the second recipe, for software: base image, exact dependency
versions, exact files, exact command. The value is not isolation (that is a side effect),
it is that **the environment stops being an unwritten assumption**.

**The reference Dockerfile from `adk.dev/deploy/gke/` (quoted verbatim, 2026-08-20):**

```dockerfile
FROM python:3.13-slim
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

RUN adduser --disabled-password --gecos "" myuser && \
    chown -R myuser:myuser /app

COPY . .

USER myuser

ENV PATH="/home/myuser/.local/bin:$PATH"

CMD ["sh", "-c", "uvicorn main:app --host 0.0.0.0 --port $PORT"]
```

Four things in it are doing real work, and Sutra keeps all four:

| Line | Why it matters |
| --- | --- |
| `COPY requirements.txt` **before** `COPY . .` | dependencies are a cached layer; editing `sutra/graph.py` does not reinstall 40 packages |
| `adduser` + `USER myuser` | the process is not root. A container escape from root is a much shorter story |
| `--host 0.0.0.0` | inside a container, loopback means "unreachable from outside" — this is the one place `0.0.0.0` is correct |
| `--port $PORT` | the platform tells you the port; you do not choose it |

Sutra changes three things:

- **`uv`, not `pip install -r requirements.txt`** — the repo's source of truth is
  `pyproject.toml` + `uv.lock` (Day 1). Exporting a `requirements.txt` just to satisfy a
  sample would create a second, staler source of truth. Use `uv sync --frozen`.
- **Pin the base by digest, not by tag.** `python:3.13-slim` moves. `@sha256:…` does not.
- **Add a `HEALTHCHECK`** — the sample has none, and Sutra has `/readyz` (Day 85)
  precisely so that something can ask.

### ADK-67 — Secrets are injected, and "injected" has a testable meaning

Three ways a secret gets into a running container. Only one is acceptable:

| Way | What it looks like | Verdict |
| --- | --- | --- |
| Baked into a layer | `COPY .env .` or `ENV GOOGLE_API_KEY=AIza…` | ❌ **the key is now in the image forever** — layers are immutable; deleting the file in a later layer does not remove it |
| Build argument | `ARG API_KEY` then used at build time | ❌ visible in `docker history` |
| Injected at run time | `docker run -e GOOGLE_API_KEY=…` / compose `env_file:` / a k8s Secret (Day 88) | ✅ |

💡 **Mental model: the image is a public artifact; the environment is the private part.**
Assume the image will be pushed to a registry someone else can pull — because on Day 93
this repo goes public, and an image built from a public Dockerfile is trivially
reproducible by anyone. Anything secret must therefore live *outside* the thing you can
rebuild.

That makes `.dockerignore` a **security control**, not a build optimisation. Without it,
`COPY . .` copies `.env`, `data/*.db` (real conversation history), `logs/` and `.git`
(which contains every version of everything you ever committed) straight into the image.

⚠️ **Day 2's rule, extended: the image is a place secrets can leak.** Day 92's security
review gets a new line — "grep the built image, not just the repo".

### OPS-17 — Compose is the shape, not the tool

`docker-compose.yml` is doing one honest job today: describing Sutra as a **system of
processes** rather than a program. Three services:

| Service | What it is | Why separate |
| --- | --- | --- |
| `sutra-api` | Day 85's FastAPI app | the thing that scales, in a world where it could |
| `sutra-mcp` | Day 33's MCP server | it owns the data boundary (Day 32's whole argument); different lifecycle, different privileges |
| `jaeger` | Day 84's collector | infrastructure, disposable, never in the production compose |

🅿️ **Parked (know the map, do not spend):** `adk deploy cloud_run --project … --region …`
packages exactly this shape onto Cloud Run, and `adk.dev/deploy/` also lists Agent
Runtime and GKE. The Cloud Run mapping is one-to-one — image, `PORT`, env vars, health
endpoint, stateless — which is *why* building it locally teaches the real thing. Write
the command in `docs/DEPLOY.md` with a line saying it has never been run and why
(Addendum 02: no billing account). Day 87 does the same for Agent Runtime, in more
depth.

**Step 3 — the Dockerfile.**

```dockerfile
# Pin by digest, not tag: tags move, digests do not.
# Refresh with: docker pull python:3.13-slim; docker image inspect python:3.13-slim --format '{{index .RepoDigests 0}}'
FROM python:3.13-slim@sha256:<paste-the-digest-you-printed>

# uv, also pinned. Copying the binary from its own image is the documented install
# path and keeps the build offline-ish and fast.
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv

WORKDIR /app

# --- dependency layer: changes rarely, cached aggressively -------------------
COPY pyproject.toml uv.lock ./
# --frozen: fail if the lock is stale rather than silently resolving something new.
# --no-dev: pytest and friends do not belong in a served image.
RUN uv sync --frozen --no-dev --no-install-project

# --- application layer: changes constantly ----------------------------------
COPY sutra/ ./sutra/
COPY sutra_mcp/ ./sutra_mcp/
RUN uv sync --frozen --no-dev

# Non-root. Also owns /app/data so the volume mount is writable.
RUN adduser --disabled-password --gecos "" sutra \
    && mkdir -p /app/data /app/logs \
    && chown -R sutra:sutra /app
USER sutra

ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONUTF8=1 \
    PORT=8080

EXPOSE 8080

# The platform decides the port; we only agree to listen on it.
HEALTHCHECK --interval=30s --timeout=3s --start-period=15s --retries=3 \
  CMD python -c "import os,urllib.request,sys; sys.exit(0 if urllib.request.urlopen(f'http://127.0.0.1:{os.environ[\"PORT\"]}/readyz').status==200 else 1)"

CMD ["sh", "-c", "uvicorn sutra.api:app --host 0.0.0.0 --port $PORT"]
```

Notice the healthcheck points at **`/readyz`**, not `/health`. A liveness check that
always passes teaches Docker to restart nothing; readiness is the signal with information
(Day 85).

```powershell
docker build -t sutra-api:dev .
docker run --rm -p 8080:8080 --env-file .env -e PORT=8080 sutra-api:dev
# second terminal:
curl.exe http://127.0.0.1:8080/readyz ; curl.exe http://127.0.0.1:8080/list-apps
```

✅ *Verify:* `/readyz` returns 200 and `/list-apps` names the app. `docker ps` shows
status `(healthy)` after the start period. Note `-p 8080:8080` publishes to **all**
interfaces on some Docker versions — prefer `-p 127.0.0.1:8080:8080` (Day 85 §5: this
server has no authentication).

📌 **Finding you will probably hit here, recorded 2026-08-20.** `google-adk`'s `mcp`
extra pins **`mcp>=1.24,<2`** (read from `adk-python/pyproject.toml`), while PyPI's `mcp`
is at **2.0.0** (Day 32's finding). `uv sync --frozen` in a clean container is the first
place this resolves without your laptop's history to cushion it. Whatever it prints is
the truth: record the resolved `mcp` version in `PACKAGES.md` with today's date, and if
it is v1 then Phase 5's documented fallback branch is now the *actual* branch — say so in
`CHANGELOG_PLAN.md` rather than leaving two possibilities alive. Day 92's dependency
audit will ask.

**Step 4 — prove the secret is not in the image.** Assertions are not evidence.

```powershell
docker history --no-trunc sutra-api:dev | Select-String -Pattern "GOOGLE_API_KEY|AIza|GROQ|sk-"
docker save sutra-api:dev -o "$env:TEMP\sutra.tar"
# crude but honest: does the raw image archive contain your key's first 12 chars?
python -c "import os,sys; key=os.environ['GOOGLE_API_KEY'][:12].encode(); data=open(os.path.join(os.environ['TEMP'],'sutra.tar'),'rb').read(); print('LEAK' if key in data else 'clean')"
Remove-Item "$env:TEMP\sutra.tar"
```

✅ *Verify:* `clean`, and the history grep is empty. Then the **negative test**, which is
the one that proves injection actually happened:

```powershell
docker run --rm -p 127.0.0.1:8080:8080 sutra-api:dev    # NO --env-file
curl.exe http://127.0.0.1:8080/readyz
```

✅ *Verify:* **503**, with `no_api_key` in the body. If it returns 200 without a key, then
either `/readyz` is lying or a key came from somewhere you did not intend — both are
today's most important possible findings.

**Step 5 — `docker-compose.yml`.**

```yaml
# Cloud-Run-shaped, locally. Three processes, one network, one volume.
services:
  sutra-api:
    build: .
    image: sutra-api:dev
    env_file: [.env]                 # injected, never baked (Day 86 §3)
    environment:
      PORT: "8080"
      SUTRA_SESSION_DB: "sqlite+aiosqlite:///./data/sessions.db"
      SUTRA_ALLOW_ORIGINS: ""        # same-origin only (Day 85 §5)
      OTEL_EXPORTER_OTLP_TRACES_ENDPOINT: "http://jaeger:4318/v1/traces"
      SUTRA_MCP_URL: "http://sutra-mcp:8000/mcp"
    ports: ["127.0.0.1:8080:8080"]   # localhost only: this API has no auth
    volumes: ["./data:/app/data"]    # see the statefulness audit, step 6
    depends_on:
      sutra-mcp: {condition: service_started}
    restart: unless-stopped

  sutra-mcp:
    build: .
    image: sutra-api:dev             # same image, different command — one build to trust
    env_file: [.env]
    command: ["python", "-m", "sutra_mcp.server", "--http", "--port", "8000"]
    volumes: ["./data:/app/data:ro"] # read-only: the archive server does not write
    restart: unless-stopped

  jaeger:                            # infrastructure. Not part of a production compose.
    image: jaegertracing/all-in-one:latest
    ports: ["127.0.0.1:16686:16686"]
```

Two deliberate choices worth defending in an interview: **one image, two commands** (you
only have to trust one build, and the MCP server cannot drift from the API's dependency
set), and **`:ro` on the MCP server's volume** — Day 32 argued the MCP server *is* the
data boundary; a read-only mount makes that argument enforceable by the kernel rather
than by intention.

```powershell
docker compose up --build
curl.exe http://127.0.0.1:8080/readyz
# one real triage through the containerised path:
curl.exe -X POST "http://127.0.0.1:8080/apps/<app-name>/users/u1/sessions" -H "Content-Type: application/json" -d "{}"
# ... then /run_sse as on Day 85
```

✅ *Verify:* four things: `/readyz` 200 · the triage completes · **the trace appears in
Jaeger at `:16686`** (proving `jaeger` resolved as a *hostname on the compose network* —
the moment "localhost is fine" stopped being true, exactly as Day 84 §5 predicted) · and
`docker compose logs sutra-mcp` shows the API actually called it, rather than falling
back to direct SQLite.

## 5 · 💥 Failure lab — `docker compose up --scale sutra-api=2`

> 🎬 **The scene:** everything is green. The image is clean, the compose file is tidy,
> the word "stateless" is in your notes. So you do the thing the word invites:
>
> ```powershell
> docker compose up --scale sutra-api=2
> ```
>
> It starts. Both instances report `/readyz` 200. You run four triages. Then you look.
> Three separate things have gone wrong, and only one of them is visible.
>
> **The visible one:** you got 429s much earlier than expected. **The quiet one:** an
> approval you granted through the operator CLI is invisible to the instance that asked
> for it — the run hangs, then resumes with "no verdict". **The dangerous one:** a
> `close_ticket` executed twice on the same ticket.
>
> 😬 **The naive fix:** mount `data/` into both containers — it is already a shared
> volume, so they *are* sharing state. Add a retry for the 429s.
>
> 💥 **Why it fails.** The shared volume is real; the assumption it papers over is not.
>
> **(1) Quota.** Day 70's ledger lives in `logs/quota.json`, which is not on the volume
> at all — and even if it were, two processes doing read-modify-write on a JSON file is a
> race by construction. Each replica therefore believes it has the *entire* free-tier
> budget: two replicas on a 5 RPM lane try to spend 10 RPM. The 429s are not bad luck,
> they are arithmetic. Retries make it worse — that is what Day 72's backoff was for, and
> retrying a structural over-spend just spends it more slowly.
>
> **(2) Approvals and durable state.** SQLite over a shared *bind mount* is not a
> multi-writer database. It is a file whose locking semantics depend on the host
> filesystem, and on Docker Desktop for Windows that filesystem is a network share.
> WAL mode (Day 63) explicitly does not support that. So the second replica's reads may
> come from a stale page cache: the verdict is committed, and the other instance cannot
> see it.
>
> **(3) Idempotency.** Day 62's `processed_writes` table is the thing that makes
> "tools run at least once" survivable — it is a *check-then-act* guarded by a database
> transaction. Split that database across two processes whose locking is unreliable and
> the guard has a window. Two replicas, one retried request, one double `close_ticket`.
> That is the failure that reaches a customer, and it was produced by a flag.
>
> 💡 **The insight: "stateless" describes where state *lives*, not whether it exists.**
> A container is stateless when every piece of durable state has been moved to a service
> that is designed to be shared — a database with real concurrency, not a file on a
> mount. Sutra has not done that, because doing it means Postgres or Cloud SQL, and this
> project has no budget (Addendum 02). That is a perfectly good engineering answer. What
> is *not* acceptable is leaving it undiscovered. So the constraint gets written where
> someone will read it before they scale:
>
> - a comment at the top of `docker-compose.yml`: **"single replica only — see
>   docs/DEPLOY.md §Statefulness. `--scale` will double-spend quota and can double-execute
>   writes."**
> - the table from Step 6 in `docs/DEPLOY.md`, with the "survives a second replica"
>   column filled in honestly — that column *is* the finding;
> - the migration path named, not hand-waved: session + approval + idempotency stores
>   move to Postgres (`session_service_uri="postgresql+asyncpg://…"`, which Day 47's
>   `DatabaseSessionService` already supports), and the quota ledger moves to a single
>   shared counter with atomic increments. Both are a day of work and a billing account,
>   which is why they are 🅿️.
> - Day 88's Kubernetes manifests therefore set `replicas: 1` **with the comment
>   explaining why** — a `1` without a reason is the thing somebody edits.

The general form, worth keeping: **before you scale anything horizontally, list every
path it writes and ask what happens when two of them do it at once.** Most systems answer
that question in production, once.

## 6 · 🎤 Interview corner

1. **"Walk me through your Dockerfile."** — Base pinned by digest rather than tag, so a
   rebuild in six months is the same build. Dependencies installed from the lockfile with
   `uv sync --frozen` in their own layer before the source is copied, so editing a node
   doesn't reinstall forty packages, and `--frozen` fails loudly instead of quietly
   resolving something new. Non-root user. `--host 0.0.0.0` because inside a container
   loopback means unreachable, and `--port $PORT` because the platform picks the port.
   A `HEALTHCHECK` on `/readyz`, not on a liveness endpoint — readiness is the signal
   that carries information. And a `.dockerignore` written *before* the first build,
   because the first build is the one that would have baked `.env` into a layer, and
   layers are immutable.
2. **"How do secrets get in?"** — At run time only: `env_file` in compose, `-e` for a
   one-off, a Secret in Kubernetes. Never `COPY .env`, never `ENV KEY=`, never a build
   arg — those all end up in the image, and `docker history` will show them. I checked
   rather than asserted: grepped the layer history, then `docker save`'d the image and
   searched the raw tarball for the first twelve characters of my key. And the test that
   actually proves injection works is the negative one — run the container with no
   environment and confirm `/readyz` returns 503 `no_api_key`. If it had returned 200,
   the key was coming from somewhere I didn't intend.
3. **"You said stateless. Is it?"** — No, and I found out by trying to scale it. The API
   process is stateless; the *system* isn't. Sessions, approvals and the write-idempotency
   table are SQLite files on a bind mount, and the quota ledger is a JSON file that wasn't
   even mounted. Two replicas gave me three distinct bugs: each replica assumed the whole
   free-tier rate limit, so I hit 429s at double rate; approval verdicts weren't reliably
   visible across instances because SQLite WAL doesn't support network mounts; and the
   idempotency guard developed a race, which is how you get a ticket closed twice. The fix
   is real infrastructure — Postgres for the durable stores, a shared atomic counter for
   quota — which needs a billing account I don't have. So the honest deliverable was the
   constraint, written down in three places including a comment at the top of the compose
   file and `replicas: 1` with a reason next to it. "Stateless" describes where state
   lives, not whether it exists.
