## 3 · 📚 Concepts

### ADK-31 — Two caches, two questions

**The coffee-shop story.** A regular walks in. The barista has two distinct memories:

- **Muscle memory** for the *start* of every order — cup, lid, espresso base are
  half-done before anyone speaks. That's the **provider's implicit cache**: the shared
  prefix of your requests (instruction block, tool declarations) processed once,
  reused when the *same beginning* arrives again.
- The **"usual?" shortcut** — for a known regular with a known order, don't make the
  drink again mentally; just hand over what they always get. That's a **response
  cache**: same question, same answer, zero thinking.

| Coffee shop | Layer | What's saved | Who runs it |
| --- | --- | --- | --- |
| Muscle memory for order-starts | implicit context cache | *prefix processing* (input tokens) — the call still happens | the provider, by default, when the request clears **4,096 tokens** (3.x Flash) |
| ADK's cup-stacking policy | `ContextCacheConfig` | how long / how often that reuse is worth managing (`ttl_seconds`, `cache_intervals`, `min_tokens`) | your `App` object |
| The "usual?" shortcut | response cache (`sutra/cache.py`) | **the whole call** | you, in a `before_model_callback` |

Two honest limits, before excitement sets in:

1. **The threshold reality.** Implicit caching starts at ~4,096 tokens of request for
   our model class. Sutra's lean prompts (Day 19 made them lean!) often sit *below*
   that line — meaning the provider cache mostly helps our *fat* requests: retrieval-
   stuffed researcher turns, eval batches, Phase 8 graph prompts. Verify, don't assume:
   the usage metadata prints cached-token counts, and step 1 reads them.
2. **What a context cache can never do:** skip the call. It discounts input processing;
   the request still spends an RPM slot. On a 5 RPM lane, **only the response cache
   gives requests back.** That's why OPS-10 pairs with today: the cache that matters
   operationally is the one the ledger can count.

💡 **Mental model: context caching discounts the reading; response caching skips the
meeting.** You want both, and you want to know which one just helped — that's what the
usage fields and the HIT/MISS log lines are for.

### OPS-10 — A cache is a promise with an expiry date

A response cache is three decisions, and every cache bug is one of them made silently:

- **The key** — what counts as "the same question"? Ours: SHA-256 over (model,
  instruction, the full message list). Anything looser returns wrong answers to
  *almost*-same questions; anything omitted from the key is a thing that can change
  behind the cache's back (today's failure lab).
- **The TTL** — how long an answer stays credible. "What does KB-104 say?" ages
  slowly; anything touching *current* state ages in minutes. One number, chosen per
  cache, written down.
- **The miss policy** — a miss must *silently* fall through to the real call (a cache
  should never make anything worse), and a hit must be **observable** (logged +
  counted) — Principle 12: if it isn't observable, it didn't happen.

**Step 2 — `sutra/cache.py`.**

```python
"""Day 51 — the response cache: same question, second time free.

A before_model_callback checks SQLite (data/cache.db) for a prior
answer to an identical request. HIT -> return the stored LlmResponse
(no model call, no RPM spent, ledger credits a save). MISS -> proceed;
an after_model_callback stores the fresh answer with a TTL.

Day 13 built the toy (shortcut_ping); this is the tool.

    python -m sutra.cache cached    # miss, then hit (~1 model call total)
    python -m sutra.cache stale     # TTL expiry forces honest re-fetch
    python -m sutra.cache stats     # hit/miss/saved counters from the ledger
"""
from __future__ import annotations

import hashlib
import json
import sqlite3
import sys
import time
from pathlib import Path

from google.adk.models import LlmResponse                 # Day 13's verified import home
from google.genai import types

from sutra.logging_setup import get_logger
from sutra.quota import QuotaLedger                       # Day 24 — saves get counted

log = get_logger(__name__)

CACHE_DB = Path("data/cache.db")                          # writable state -> SQLite (house rule)
DEFAULT_TTL_S = 15 * 60                                   # 15 min; per-cache decision, written down


def _connect() -> sqlite3.Connection:
    """Open (and once, create) the cache table. WAL like data/tasks.db."""
    conn = sqlite3.connect(CACHE_DB)
    conn.execute("PRAGMA journal_mode=WAL")               # same discipline as Day 43's rack
    conn.execute(
        "CREATE TABLE IF NOT EXISTS cache ("
        " key TEXT PRIMARY KEY,"                          # SHA-256 of the whole request
        " answer TEXT NOT NULL,"                          # the model's text, verbatim
        " stored_at REAL NOT NULL)"                       # epoch seconds, for TTL math
    )
    return conn


def request_key(callback_context, llm_request) -> str:
    """One hash for 'the same question' — model + instruction + messages.

    EVERYTHING that could change the answer must be in here; whatever
    you leave out can change behind the cache's back (doc §5).

    Example:
        >>> # identical requests -> identical keys; one char of drift -> new key
    """
    material = json.dumps({
        "model": str(getattr(llm_request, "model", "")),   # which brain
        "contents": [str(c) for c in getattr(llm_request, "contents", [])],
        "system": str(getattr(llm_request, "config", "")), # instruction+tools ride config
    }, sort_keys=True)
    return hashlib.sha256(material.encode()).hexdigest()


def before_model_cache(callback_context, llm_request):
    """HIT -> return stored LlmResponse (call skipped). MISS -> None (proceed).

    Return semantics are Day 13's law: an object skips the model; None
    lets it run. A cache must never make things worse: any internal
    error logs and returns None (fail open to the real call).
    """
    try:
        key = request_key(callback_context, llm_request)
        with _connect() as conn:
            row = conn.execute(
                "SELECT answer, stored_at FROM cache WHERE key=?", (key,)
            ).fetchone()
        if row and (time.time() - row[1]) < DEFAULT_TTL_S:  # fresh enough?
            log.info("cache_hit", extra={"key": key[:12]})
            QuotaLedger().record_saved("gemini")            # a call NOT spent — counted
            callback_context.state["temp:cache_hit_key"] = key   # temp: = never persisted
            return LlmResponse(content=types.Content(       # hand back the stored turn
                role="model", parts=[types.Part(text=row[0])],
            ))
        log.info("cache_miss", extra={"key": key[:12], "stale": bool(row)})
        callback_context.state["temp:cache_store_key"] = key    # after_model will fill it
    except Exception:                                       # noqa: BLE001 — fail OPEN
        log.exception("cache_error_failing_open")
    return None                                             # miss -> real call proceeds


def after_model_cache(callback_context, llm_response):
    """Store fresh answers under the key the before-hook parked in temp: state."""
    key = callback_context.state.get("temp:cache_store_key")
    text = "".join(
        p.text or "" for p in (llm_response.content.parts or [])
    ) if llm_response.content else ""
    if key and text:                                        # only cache real answers
        with _connect() as conn:
            conn.execute(
                "INSERT OR REPLACE INTO cache VALUES (?,?,?)",
                (key, text, time.time()),
            )
    return None                                             # never alter the response
```

## 5 · 💥 Failure lab — the cache that kept being right about yesterday

> 🎬 **The scene:** flush with success, you widen the cache key "for a better hit rate":
> just the user's question text — ignore the instruction, ignore the transcript. Hit
> rate soars. A week later, Day 27's ticket-triage skill gets a severity-rubric update.
> Users ask the same questions; Sutra keeps answering **from the old rubric**. Every
> answer arrives instantly, confidently, and wrong.
> 😬 **The naive fix:** "cache invalidation on deploys" — a script that clears
> `data/cache.db` whenever *someone remembers* that something changed.
> 💥 **Why it fails:** the key no longer describes the question. "Same question" for an
> agent is question + instruction + tools + relevant state — you cached against a
> *subset* and made everything outside it invisible to the cache. Remember-to-flush is
> a process solution to a correctness bug: the first forgotten flush ships stale
> answers, and nothing in the logs distinguishes them from fresh ones. (There's a
> nastier cousin, which our code dodged by design: caching *error* text. Cache a 429's
> apology once and you'll serve apologies all day, free and useless — only real
> answers enter the store.)
> 💡 **The insight:** **a cache key is a completeness claim: "nothing outside this hash
> affects the answer."** Make the claim true — hash everything that shapes the reply —
> and accept the honest hit rate that follows; let the TTL bound how long *the world*
> is allowed to drift underneath a true key. A cache that's fast, confident, and stale
> is Principle 10's fabrication in a cheaper costume.

Pinned by test: `test_cache.py`'s one-char-drift case is exactly the rubric-update
scenario in miniature.

## 6 · 🎤 Interview corner

1. **"How does context caching differ from response caching, and when do you need
   each?"** — Context caching (provider-side, implicit on modern Gemini above a token
   threshold) reuses the processed *prefix* — cheaper input tokens, but the request
   still happens and still costs a rate-limit slot. Response caching skips the call
   entirely for an identical request. Under a paid bill you chase context caching for
   token cost; under rate limits — my project lives at 5 RPM — only response caching
   returns *requests*, so it's the operational lifeline. I run both: ADK's
   `ContextCacheConfig` at the App level for fat prompts, and a callback-based
   response cache keyed on a hash of model+instruction+messages, TTL'd, with hits
   counted in the quota ledger.
2. **"What goes into your cache key and why?"** — Everything that shapes the answer:
   model id, full instruction/config, the message list — hashed. The key is a
   completeness claim; anything omitted can change behind the cache's back and serve
   stale answers with fresh confidence (I keep a test where one character of drift
   must produce a new key). Two more rules from scars: never cache error responses,
   and fail *open* — a cache exception falls through to the real call, because a
   cache must never make anything worse.
3. **"How do you know your cache is helping?"** — It's in the ledger, not the vibes:
   every hit increments a calls-saved counter per provider, misses and stale-misses
   are logged distinctly, and the provider's cached-token field in usage metadata
   tells me when the *other* layer engaged. If it isn't observable, it didn't happen
   — a cache without counters is how teams discover, during an incident, that their
   hit rate has been ~0 for a month.
