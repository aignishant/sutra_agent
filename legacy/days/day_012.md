## 3 · 📚 Concepts

### ADK-13 — Structured output: the outbox gets a template

**The story.** Our support desk has been writing outcomes on blank paper. The new office
manager replaces the blank paper with a **carbonless triage slip**: Category (tick one),
Severity (1–4), Needs-human (yes/no), Notes. Agents may still *think* however they like —
but what leaves the desk is the slip, every time, or it doesn't leave.

Day 4 put forms on the way **in** to tools. Today puts a form on the way **out** of the
agent:

| Direction | Mechanism | You built it |
| --- | --- | --- |
| User/tool → model | function declarations (JSON Schema) | Day 4, by hand; Day 10, via docstrings |
| Model → your system | **`output_schema`** on the agent | today |

The shape is declared once, as a Pydantic model — Python's standard way to write "this
exact JSON shape, with types and allowed values":

```python
class TriageResult(BaseModel):
    category: Literal["auth", "billing", "outage", "other"]
    severity: int          # 1 (annoyance) .. 4 (fire)
    needs_human: bool
    notes: str
```

Hand that to `LlmAgent(output_schema=TriageResult, ...)` and the contract moves from
"please answer in JSON, pretty please" (prose begging — Day 3's pinky promise, again) to
a constraint the framework enforces on the reply format.

💡 **Mental model: `output_schema` is Day 4's lesson pointed the other way — the answer
itself becomes a filled form.** Prose is a request; a form is a guarantee. Same sentence,
new door.

**`output_key`: the auto-filing cabinet.** Set `output_key="triage_result"` and ADK saves
the final response into `session.state["triage_result"]` — no `record_triage`-style "please
call the tool" step, no *usually*. Day 11's notepad now fills itself for this agent.
(`input_schema` 🅿️ also exists for JSON-shaped *inputs* — agent-to-agent edges use it;
it'll matter in Phase 8. Know it exists; move on.)

### ⚠️ The caveat that designs your architecture for you

Quoted from the docs (2026-08-18): *"Using `output_schema` with `tools` in the same LLM
request is only supported by specific models, including Gemini 3.0."* Elsewhere: the
combination may be unreliable.

Read that as an architecture hint, not an obstacle: **don't build one agent that both
wields tools and promises shapes.** Split the roles:

```
classifier  (no tools, output_schema)   -> reads ticket text, emits TriageResult
researcher  (tools, free-form output)   -> digs through KB, gathers evidence
```

That split is not a workaround — it is *good design arriving early*. Phase 8's triage
graph is literally these boxes with arrows. Single-responsibility agents, structured
edges: today's constraint is tomorrow's blueprint.

**Schema design rules** (they rhyme with Day 11's tool rules, because they are the same
idea):

1. **Enums for closed sets** — `Literal["auth", ...]` beats `category: str`, or you'll
   get "Authentication/Login-related" one day and "auth" the next.
2. **Always an escape valve** — an `"other"` bucket, a `needs_human` flag, a free-text
   `notes`. §5 shows what happens without one.
3. **Small.** Every field is something the model must get right *every single time*.
   Five honest fields beat fifteen aspirational ones.
4. **Describe fields for the model** — Pydantic `Field(description=...)` text reaches the
   model the same way docstrings did on Day 10. Same care applies.

## 4 · 🛠️ Build

> Shell: **PowerShell**, venv active, repo root.

**Step 1 — `sutra/schemas.py` (zero quota).**

```python
"""Day 12 — structured output: the classifier that can only speak JSON.

One Pydantic schema (TriageResult) + one tool-less classifier agent with
output_schema set. The tools/schema split follows the documented caveat:
tool-wielding agents and shape-promising agents are DIFFERENT agents.

Importable with no side effects. Run demos from the repo root:

    python -m sutra.schemas classify   # one ticket -> one TriageResult (1 call)
    python -m sutra.schemas batch      # three tickets -> three objects (3 calls)
"""
from __future__ import annotations

import json
import sys
from typing import Literal

from pydantic import BaseModel, Field                # ships with google-adk
from google.adk.agents import Agent
from google.adk.runners import InMemoryRunner
from google.genai import types

from sutra.config import load_env
from sutra.loop import TICKETS                       # synthetic tickets, one home (Day 3)


class TriageResult(BaseModel):
    """The carbonless triage slip: what leaves the desk, every time."""

    category: Literal["auth", "billing", "outage", "other"] = Field(
        description="Problem area. Use 'other' when nothing fits - do not force a fit."
    )
    severity: int = Field(
        ge=1, le=4,                                  # 1 = annoyance ... 4 = fire
        description="Impact: 1 cosmetic, 2 inconvenient, 3 blocks work, 4 outage/data loss."
    )
    needs_human: bool = Field(
        description="True if a human should review before any action is taken."
    )
    notes: str = Field(
        description="One short sentence of reasoning a teammate could act on."
    )


# The classifier: NO tools, shape guaranteed, result auto-filed to state.
classifier_agent = Agent(
    name="sutra_classifier",
    model="gemini-3.5-flash",                        # pinned - ADK-73, always
    instruction="""You classify support tickets. Read the ticket text you
are given and fill the triage slip. Be conservative: if unsure of the
category, use 'other' and set needs_human true.""",
    output_schema=TriageResult,                      # the slip (ADK-13)
    output_key="triage_result",                      # auto-file into session state
)


def classify(ticket_text: str) -> TriageResult:
    """Run one ticket through the classifier; return a validated object.

    Args:
        ticket_text: the raw ticket text (NOT an id - this agent has no
            lookup tool on purpose; callers fetch text first).

    Returns:
        A TriageResult parsed and validated from the model's JSON reply.

    Example:
        >>> classify("Customer keeps getting logged out every few minutes")
        TriageResult(category='auth', severity=3, needs_human=False, notes='...')
    """
    runner = InMemoryRunner(agent=classifier_agent)
    session = runner.session_service.create_session_sync(
        app_name=runner.app_name, user_id="day12"
    )
    raw = ""                                         # will hold the JSON text
    for event in runner.run(user_id="day12", session_id=session.id,
                            new_message=types.Content(
                                role="user",
                                parts=[types.Part(text=ticket_text)])):
        if event.is_final_response() and event.content:
            raw = "".join(p.text or "" for p in event.content.parts)
    result = TriageResult.model_validate_json(raw)   # parse; raises loudly on mismatch
    # Show the auto-filing worked too (output_key -> state, no tool needed):
    fresh = runner.session_service.get_session_sync(
        app_name=runner.app_name, user_id="day12", session_id=session.id
    )                                                # TODO(confirm getter name, Day 8 pattern)
    print("state['triage_result'] present:", "triage_result" in fresh.state)
    return result


def demo_classify() -> None:
    """Usage: python -m sutra.schemas classify   (1 model call)."""
    result = classify(TICKETS["4521"])               # the famous logout ticket
    print(json.dumps(result.model_dump(), indent=2)) # guaranteed shape, pretty-printed


def demo_batch() -> None:
    """Usage: python -m sutra.schemas batch      (3 model calls - mind 5 RPM)."""
    for tid, text in list(TICKETS.items())[:3]:      # first three synthetic tickets
        result = classify(text)                      # every one MUST parse
        print(f"#{tid}: {result.category} sev{result.severity} "
              f"human={result.needs_human} - {result.notes}")


def main() -> None:
    demos = {"classify": demo_classify, "batch": demo_batch}
    name = sys.argv[1] if len(sys.argv) > 1 else "classify"
    if name not in demos:
        print(f"usage: python -m sutra.schemas [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the form with no "other" box

> 🎬 **The scene:** a tidy-minded refactor: `"other"` looks like a cop-out category, and
> `needs_human` "never fires anyway." You trim the schema to
> `Literal["auth", "billing", "outage"]` and delete the flag. Cleaner! Then a ticket
> arrives: *"Your marketing email called me by the wrong name and I want it fixed."*
> 😬 **The naive fix:** none needed — look, the classifier still returns valid JSON!
> 💥 **Why it fails:** *of course* it returns valid JSON. It **must** — that's what a
> schema does. So the misfit ticket gets shoehorned into `billing` or `outage`, severity
> guessed, confidently wrong, and your pipeline routes a data-privacy complaint to the
> outage team. Nothing crashed. No log line. The schema didn't fail — it *succeeded* at
> exactly the wrong job: laundering "I don't know" into "billing".
> 💡 **The insight:** **a schema is a fence, and a fence with no gate turns confusion into
> confident garbage.** (Day 4's forced-call lab, one level up: shape ≠ sense.) Every
> closed enum needs an `other`; every classifier needs a `needs_human`-style valve; and
> the instruction must *bless* using them ("if unsure, say other"). Uncertainty you can
> route is a feature. Uncertainty you've made unspeakable is a time bomb.

Run it: shrink the enum, classify the misfit ticket text (paste it as a string), watch the
shoehorn; restore the schema, re-run, watch it land in `other` with `needs_human: true`.
~2 model calls.

## 6 · 🎤 Interview corner

1. **"How do you get *reliable* structured data out of an LLM?"** — Constraint plus
   validation plus escape valves. I declare the shape once (Pydantic → `output_schema` on
   the agent), validate on receipt (`model_validate_json`, failing loudly), and design the
   schema so uncertainty is expressible — an `other` bucket and a `needs_human` flag,
   blessed in the instruction. And I keep prompt-side JSON-begging out of it entirely;
   I've built the beg-and-regex version by hand, and I know exactly which failure classes
   the schema deletes and which (semantic ones) it cannot.
2. **"Why not give your classifier tools too?"** — Two reasons. Documented model support:
   schema-plus-tools in one request only works on specific models, so it's a portability
   trap. And architecture: a classifier that can only classify is testable, cacheable, and
   composable — my triage graph wires a tool-less shape-guaranteed classifier next to a
   tool-wielding researcher, with the schema as the edge contract between them.
3. **"Where does the structured result go after the model produces it?"** — Into session
   state automatically — ADK's `output_key` files the final response under a state key, so
   downstream nodes read `state["triage_result"]` instead of scraping chat. Structure at
   the edges, state as the bus: that's what makes multi-agent graphs debuggable.
