## 3 · 📚 Concepts

### ADK-52 — Streaming architecture: letters, phone calls, and a two-way radio

**The story, continued from Day 7.** A letter (`NONE`) arrives whole. A phone call
(`SSE`) lets you hear the answer form — but it is *one-way*: you asked, they talk,
you can't interrupt mid-sentence through the same wire. A **two-way radio** (`BIDI`)
is open in both directions at once: you can talk over them, they stop, voice activity
on either side is a first-class signal. That third mode is the Live API.

| | `StreamingMode.NONE` | `StreamingMode.SSE` | `StreamingMode.BIDI` |
| --- | --- | --- | --- |
| ADK entrypoint | `run_async` | `run_async` | **`run_live`** (+ `LiveRequestQueue`) |
| transport to a browser | plain HTTP response | **Server-Sent Events** (HTTP, one-way, `text/event-stream`) | **WebSocket** (two-way, binary-friendly) |
| what flows | final event | `partial=True` chunks, then the final event (Day 7) | text *and* audio parts, transcriptions, `turn_complete`, `interrupted`, voice-activity |
| input | one message | one message | a **queue**: text, audio blobs, activity signals, `close()` — continuously |
| model callbacks | ✅ | ✅ | ❌ **not invoked on the streaming path** (adk.dev, 2026-08-19) |
| models | any | any | Live-capable only; native-audio models **cannot text-chat** |

What `RunConfig` controls is the same object on every row — that is the elegance: the
agent does not change between a letter and a radio; the *run configuration* does.
`StreamingMode` picks the path; on the live path `response_modalities` (`["TEXT"]` or
`["AUDIO"]`), `speech_config`, `realtime_input_config` (VAD), transcription configs,
`session_resumption`, `context_window_compression` shape the session (Days 75–76 use
each). And `max_llm_calls` (Day 7's fuse) still counts on both paths.

Two architecture facts decide tonight's design. (1) **SSE is a normal HTTP response
that never ends**, `Content-Type: text/event-stream`, lines of `data: …` separated by
blank lines. Browsers consume it with the built-in `EventSource` — no library. Every
proxy and server you will ever meet knows HTTP, which is why SSE is the web's default
typewriter transport. (2) **The live path is a different code path in ADK**, not SSE
with audio bolted on — hence the callback caveat. Anything Sutra enforces with
`before_model_callback` (cache, guardrails) must be enforced *another* way on that
path: tool-level permissions (Day 68), instructions, and the fact that the standup
agent gets no write tools at all (Day 77).

💡 **Mental model: the agent never changes; the run configuration chooses letter,
phone call, or radio — and the radio has its own rules.**

### ADK-53 — The quota check, and a voice that can't run out

**The story.** A street performer with a great act and a generator-powered amp.
Professionals carry an acoustic backup — not because the amp is bad, but because the
show must not depend on the generator. Live audio is the amp: brilliant, tier-limited,
"concurrent sessions: tier-based" in ADK's own table. The browser's speech engines are
the acoustic backup: `speechSynthesis` (text → voice) and `SpeechRecognition`
(voice → text) ship inside Chrome/Edge, cost nothing, and meter nothing.

So the design for Phase 11, stated once (Addendum 02's Days 74–78 amendment):

| Layer | Primary build (always works) | Live layer (run inside quota) |
| --- | --- | --- |
| model → you | Gemini **text** stream over SSE; browser `speechSynthesis` speaks it | Live `AUDIO` modality over WebSocket (Day 75) |
| you → model | browser `SpeechRecognition` → text → same SSE endpoint (Day 75) | mic PCM 16 kHz over the `LiveRequestQueue` (Day 75) |
| quota | `gemini-3.5-flash` / `-lite` text lanes, already routed (Day 70) | Live model's own rows in AI Studio — **read today, recorded, re-checked at the gate** |

The *check* is a real step (step 2) because the rate-limits page no longer publishes
a free-tier table — it says "view your active rate limits in AI Studio." Numbers you
didn't read are numbers you invented (Principle 7).

💡 **Mental model: build the acoustic set first; plug in the amp second.** Voice UX is
a browser feature; Live audio is the upgrade.

```python
"""Days 74–76 — the live lab: Sutra's stream leaves the terminal.

Day 74 (this half): GET /sse?q=...  -> Server-Sent Events carrying the text
stream of a pinned gemini-3.5-flash agent (run_async + StreamingMode.SSE).
Days 75–76 add WebSocket /ws/live on top (run_live + LiveRequestQueue).

Run:   uvicorn sutra.live_lab:app --port 8766 --reload
Then:  open sutra/live_client.html in Chrome/Edge (file:// is fine)
Probe: curl.exe -N "http://localhost:8766/sse?q=hello"

Day 7's consumer rule still rules: partial chunks are for the eyes (we
forward them), the final event is for the books (we forward one `done`).
Importable with no side effects (uvicorn imports `app`; nothing runs).
"""
from __future__ import annotations

import asyncio
import json
from typing import AsyncIterator

from fastapi import FastAPI, Query
from fastapi.responses import StreamingResponse
from google.adk.agents.llm_agent import Agent
from google.adk.agents.run_config import RunConfig, StreamingMode   # Day 7, verified
from google.adk.runners import InMemoryRunner
from google.genai import types

from sutra.logging_setup import get_logger

log = get_logger("live_lab")

TEXT_MODEL = "gemini-3.5-flash"          # pinned (ADK-73); the text lane, free tier

# A small, read-only agent for the lab. Day 77 swaps in the real standup agent.
text_agent = Agent(
    name="sutra_live_text",
    model=TEXT_MODEL,
    instruction=("You are Sutra's spoken assistant. Answer in short sentences - "
                 "they are read aloud. Never invent ticket data; you have no tools "
                 "today, say so if asked for specifics."),
    tools=[],                             # read-only by construction (Day 68 tier)
)

app = FastAPI(title="sutra live lab")
_runner = InMemoryRunner(agent=text_agent)            # one runner, many sessions


async def _session(user_id: str) -> str:
    """One session per browser question (Day 8's shape)."""
    s = await _runner.session_service.create_session(
        app_name=_runner.app_name, user_id=user_id)
    return s.id


def _sse(payload: dict) -> str:
    """Format one SSE frame: `data: <json>` + blank line (the protocol, whole).

    Example:
        >>> _sse({"t": "hi"})
        'data: {"t": "hi"}\\n\\n'
    """
    return f"data: {json.dumps(payload)}\n\n"


async def stream_answer(question: str, user_id: str = "browser") -> AsyncIterator[str]:
    """Yield SSE frames for one question: chunks as they arrive, then `done`.

    Args:
        question: the user's text (from the browser, or tomorrow from speech).
        user_id: session owner label.

    Yields:
        SSE frames: {"chunk": str} per partial event; {"done": true, "text": full}
        once, from the final aggregated event (Day 7: chunks=eyes, final=books).
    """
    sid = await _session(user_id)
    cfg = RunConfig(streaming_mode=StreamingMode.SSE)        # letter -> phone call
    async for event in _runner.run_async(
        user_id=user_id, session_id=sid,
        new_message=types.Content(role="user", parts=[types.Part(text=question)]),
        run_config=cfg,
    ):
        text = "".join(p.text or "" for p in (event.content.parts if event.content else [])
                       if getattr(p, "text", None))
        if event.partial and text:                           # eyes
            yield _sse({"chunk": text})
        elif event.is_final_response():                      # books
            yield _sse({"done": True, "text": text})
    log.info("sse_done", extra={"user_id": user_id, "session_id": sid})


@app.get("/sse")
async def sse(q: str = Query(..., min_length=1, max_length=500)) -> StreamingResponse:
    """The endpoint: an HTTP response that never ends until the answer does."""
    return StreamingResponse(
        stream_answer(q),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache",          # never cache a stream
                 "X-Accel-Buffering": "no"},           # tell proxies: don't buffer (see lab)
    )


@app.get("/healthz")
async def healthz() -> dict:
    """Day 86 wants this; free to add now."""
    return {"ok": True, "model": TEXT_MODEL}
```

const SERVER = "http://localhost:8766";

## 5 · 💥 Failure lab — the stream that arrived all at once

> 🎬 **The scene:** the typewriter works beautifully against `localhost:8766`. You put
> it behind the reverse proxy you'll use on Day 86 (or a corporate proxy, or some
> hosting's default nginx) and suddenly the box sits empty for six seconds, then the
> whole answer *appears at once*. The server logs show chunks leaving on time.
> 😬 **The naive fix:** "SSE must be flaky — switch to WebSockets," or worse, "turn off
> streaming, it adds nothing."
> 💥 **Why it fails:** nothing is wrong with SSE. Intermediaries **buffer** responses
> by default — they wait for a chunk of N KB or end-of-response before forwarding, which
> is a fine optimisation for a 200 KB HTML page and fatal for a 2 KB stream. Day 7's
> lesson in a new coat: the protocol sent chunks; something between you and the
> consumer treated two kinds of response as one kind. Reproduce it tonight without a
> proxy: remove `"X-Accel-Buffering": "no"` and pipe curl through a buffering stage —
> `curl.exe -s "…/sse?q=…" | Out-String` — and watch everything arrive together.
> 💡 **The insight:** **a stream is only as live as its least-live hop.** Set the headers
> that tell intermediaries not to buffer (`Cache-Control: no-cache`,
> `X-Accel-Buffering: no` for nginx-family proxies), keep `-N`/no-buffering on test
> clients, and when a stream "doesn't stream," check the hops before the transport.
> WebSockets dodge *this* problem and bring their own (stateful connections — Day 75's
> second half is exactly about that).

## 6 · 🎤 Interview corner

1. **"SSE or WebSockets for an LLM product — how do you choose?"** — One-way token
   streaming to a browser is SSE: plain HTTP, `EventSource` built in, cache/proxy
   semantics everyone understands, trivially load-balanced. Two-way, continuous,
   binary-friendly (audio in *and* out, interruptions) is WebSocket — which is what
   ADK's live path needs. I built both in one file: `/sse` on `run_async` with
   `StreamingMode.SSE`, `/ws/live` on `run_live` with a `LiveRequestQueue`. And the
   failure I'd warn about for SSE is buffering intermediaries, not the protocol.
2. **"What does switching an ADK agent to the Live API actually change?"** — The agent
   object, nothing; the run, everything: `run_live` instead of `run_async`, input
   through a queue (text, PCM audio, activity signals, close), output events carrying
   audio parts, transcriptions, `turn_complete`, `interrupted`; `RunConfig` gains
   modalities, speech, VAD, transcription, resumption, compression. And two caveats I
   found on the docs page, not by accident in production: model callbacks don't run on
   the live path, and native-audio models can't do text chat — so guardrails and
   caching need a different enforcement point there.
3. **"How do you demo voice on a free tier you can't rely on?"** — Acoustic set first:
   text streaming over SSE with the browser's own `speechSynthesis`/`SpeechRecognition`
   — voice UX, zero audio quota, works on the day. Then the Live API as the upgrade,
   run briefly inside the limits I read in AI Studio and recorded with a date. The demo
   never depends on the part that can run out.
