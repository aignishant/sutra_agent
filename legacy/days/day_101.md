## 1 · 🎬 Where we are — the story so far

Yesterday Sutra ran on Azure Container Apps: a container you built, a public registry that costs
nothing, a replica count of zero between requests, and a failure lab that showed you exactly what
zero replicas costs — the agent forgetting its own last sentence.

Azure has two *other* free tiers that look, from a distance, like they'd do the same job. App
Service has a Free tier called F1 that has existed roughly forever. Functions has a Consumption
plan with a million free executions a month. Both are real. Both are genuinely free. And exactly
one of them is a sensible place to put an agent.

Today is about the difference between "is this free?" and "is my program the *shape* this
platform wants?" — and about a quota unlike any other in this track: not vCPU-seconds, not
requests, not instance-hours, but **60 CPU-minutes per day**, after which your app stops
answering until tomorrow.

## 3 · 📚 Concepts

### DEPLOY-05a — What F1 actually gives you, quoted rather than recalled

From `azure.microsoft.com/en-us/pricing/details/app-service/linux/` (2026-08-21):

> **CPU:** *"Shared (60 CPU minutes / day)"* — **RAM:** 1 GB — **Storage:** *"1.00 GB"*
>
> *"The free plan is intended for trials, experimentation, and learning the service. There is no
> SLA for free plan and it is metered on a per app basis. Use of free plan for production
> workloads is not supported."*
>
> *"Free and shared service plans do not support SSL"* (custom-domain TLS; the default
> `*.azurewebsites.net` hostname is still HTTPS).

And from `learn.microsoft.com/en-us/azure/app-service/overview-hosting-plans`:

> *"In the Free and Shared tiers, an app receives CPU minutes on a shared VM instance and can't
> scale out."*

💡 **The mental model, and it is the third distinct one in four days.** Every free grant in this
track meters something different, and the flag that keeps you inside it changes accordingly:

| Day | Platform | Meter | What keeps you inside it |
| --- | --- | --- | --- |
| 097 | Cloud Run | requests/month | `--min-instances=0` |
| 098 | Compute Engine | instance-hours/month, pooled | run exactly **one** `e2-micro` |
| 100 | Container Apps | vCPU-s + GiB-s/month | `--min-replicas 0` |
| **101** | **App Service F1** | **CPU-minutes per *day*** | **keep per-request CPU low, and accept a hard daily ceiling** |

⚠️ **The daily reset is the part that surprises people.** The other three grants are monthly: run
out and you're inconvenienced for weeks. F1's resets every 24 hours — much more forgiving over a
month, much less forgiving in a single afternoon of debugging.

### DEPLOY-05b — Why today deploys *code*, not a container

App Service can run either a built-in language stack ("code deploy," where the platform builds
your app from source with Oryx) or your own container image. F1 unambiguously supports the first.
The second is this day's open question (see the header ⚠️ and §6).

📌 **This is the first day in the track that does *not* use `Dockerfile.adk`.** That's worth
noticing rather than glossing: Day 100's whole lesson was that leaving GCP meant owning a
container. Today shows the other side of the same coin — a platform with a built-in Python stack
takes source code and builds it for you, which is *convenient* and also *less portable*. The
container from Day 100 runs unchanged on Container Apps, Lambda (with Day 103's adapter), Oracle,
and your laptop. Today's code deployment runs on App Service.

⚠️ **The gap that follows from that convenience:** with code deploy, the platform decides how your
process starts, and you tell it via a **startup command** rather than a `CMD` line. Step 4 sets
it. The relevant unknown — flagged honestly rather than asserted — is whether the `adk` console
script is on `PATH` in the environment Oryx builds. Step 4 gives the diagnostic and a fallback
rather than promising a specific answer.

### DEPLOY-05c — Functions is genuinely free, and genuinely the wrong shape

From `azure.microsoft.com/en-us/pricing/details/functions/` (2026-08-21):

> *"Consumption plan pricing includes a monthly free grant of 1 million requests and 400,000 GB-s
> of resource consumption per month per subscription."*

⚠️ **With a caveat worth reading twice**, stated on that same page: these free grants apply to
**paid, consumption subscriptions**. A subscription still in the Free Trial state is not
obviously covered — confirm your subscription type before assuming the grant applies to you.
(`az account show --query "{name:name, state:state}"`.)

**So why not put Sutra there?** Not cost — shape:

| What a Function wants | What an ADK agent is |
| --- | --- |
| A short-lived handler, invoked per event, that returns and exits | A long-lived HTTP server (`adk api_server`) holding routes, sessions, and an SDK client |
| Cold starts amortised over many small, fast invocations | Cold starts on top of an LLM call that already takes seconds |
| Stateless by design | Stateful across turns — the exact thing Day 100 §5 showed breaking |
| Billed on execution time × memory | Model latency dominates, so you pay GB-seconds to *wait on a network call* |

💡 **The insight worth keeping: paying by the GB-second for time spent blocked on someone else's
API is the worst possible billing shape for an LLM agent.** A request that takes four seconds
— of which 3.8 are Gemini thinking — bills you for four seconds of memory-time either way. Cloud
Run and Container Apps have this problem too, but their grants are large enough (and their
concurrency models let one instance serve many simultaneous requests) that it stays theoretical.
On a per-invocation model it's the dominant cost.

📌 **Where Functions *would* earn its place in this project:** as a small, free, event-shaped
front door to an agent hosted elsewhere — a webhook receiver that validates and enqueues, a timer
that runs a nightly digest, an alert handler. Small, fast, stateless, event-driven. That is
exactly what the shape is good at, and none of it is the agent itself.

## 4 · 🛠️ The build

> Shell: **PowerShell**, repo root.

**Step 1 — confirm the runtime string rather than guessing it.**

```powershell
az webapp list-runtimes --os linux | Select-String -Pattern "PYTHON"
```

✅ *Verify:* you get back a concrete list (e.g. `PYTHON:3.12`, `PYTHON:3.13`). **Use one that
appears in your own output.** This repo requires `>=3.12` (`pyproject.toml`), so pick 3.12 or
newer. ⚠️ Don't paste a version string from this doc — runtime availability changes, and this is
exactly the class of value the project's standing rules say to look up rather than invent.

**Step 2 — resource group, F1 plan, and read the SKU back.**

```powershell
az group create --name sutra-f1-rg --location eastus

az appservice plan create --name sutra-f1-plan --resource-group sutra-f1-rg `
  --sku F1 --is-linux

az appservice plan show --name sutra-f1-plan --resource-group sutra-f1-rg `
  --query "{sku:sku.name, tier:sku.tier, linux:reserved}" -o table
```

| Flag | What it does |
| --- | --- |
| `--sku F1` | the Free tier — no cost, 60 CPU-min/day, no scale-out, no custom-domain TLS (DEPLOY-05a) |
| `--is-linux` | Linux plans are what support the Python built-in stack; Windows plans have a different model |

✅ *Verify:* `sku` is `F1`, `tier` is `Free`, `linux` is `True`. ⚠️ Read this back **now** rather
than trusting the create command — an App Service plan silently created at B1 is a real,
recurring charge, and this is the cheapest possible moment to catch it.

**Step 3 — deploy the code.**

```powershell
uv export --no-hashes -o requirements.txt   # Oryx installs from this — build artifact, gitignored

az webapp up `
  --name sutra-f1-<your-suffix> `
  --resource-group sutra-f1-rg `
  --plan sutra-f1-plan `
  --runtime "PYTHON:3.12" `
  --os-type Linux
```

⚠️ The app name becomes part of a **globally unique** hostname
(`https://<name>.azurewebsites.net`), so add a suffix. And ⚠️ `az webapp up` will create a plan
for you if it can't find one — passing `--plan sutra-f1-plan` explicitly is what stops it
provisioning a *different*, possibly billed, plan.

✅ *Verify:* the command prints your app URL and a deployment success message. The site will not
serve Sutra yet — Step 4 is what makes it do that.

**Step 4 — the startup command and the app settings.**

App Service's Linux Python stack expects your app to listen on **port 8000**. Set the startup
command and inject configuration — the same "never bake in" rule as every other day in this
track:

```powershell
az webapp config appsettings set --name sutra-f1-<your-suffix> --resource-group sutra-f1-rg `
  --settings GOOGLE_GENAI_USE_VERTEXAI=FALSE `
             GOOGLE_API_KEY="$env:GOOGLE_API_KEY" `
             SCM_DO_BUILD_DURING_DEPLOYMENT=true

az webapp config set --name sutra-f1-<your-suffix> --resource-group sutra-f1-rg `
  --startup-file "adk api_server --host 0.0.0.0 --port 8000 sutra"
```

| Setting | What it does |
| --- | --- |
| `SCM_DO_BUILD_DURING_DEPLOYMENT=true` | tells Oryx to actually run `pip install -r requirements.txt` on the server rather than deploying the files raw |
| `GOOGLE_GENAI_USE_VERTEXAI=FALSE` | Day 097's DEPLOY-01b — keeps ADK on the free AI Studio path. Provider-independent rule; it applies here unchanged |
| `GOOGLE_API_KEY` | ⚠️ **note the honest difference from Days 097/100:** this is an app setting holding the **literal value**, not a reference to a secret store. App Service app settings are encrypted at rest and not exposed to the app's own `/Env` endpoint, but this is genuinely a weaker posture than Cloud Run's `--set-secrets` or Container Apps' `secretref:`. The stronger version is Key Vault references, which is a separate service with its own free-tier question — out of scope today, and the weaker choice is recorded here rather than hidden |
| `--startup-file` | the code-deploy equivalent of a `CMD` line (DEPLOY-05b) — port **8000** because that is what the Linux Python stack forwards to |

✅ *Verify:*

```powershell
$APP = "https://sutra-f1-<your-suffix>.azurewebsites.net"
curl.exe "$APP/list-apps"
```

returns `["sutra"]`. ⚠️ **If it doesn't, this is DEPLOY-05b's flagged unknown, and the log stream
is the answer — not a guess:**

```powershell
az webapp log config --name sutra-f1-<your-suffix> --resource-group sutra-f1-rg --docker-container-logging filesystem
az webapp log tail --name sutra-f1-<your-suffix> --resource-group sutra-f1-rg
```

- **`adk: not found`** → the console script isn't on `PATH` in Oryx's environment. Try the
  virtualenv path Oryx builds (`antenv/bin/adk ...`) or a module invocation. Record which worked.
- **`ModuleNotFoundError: No module named 'sutra'`** → this is Day 097 §5's import question in a
  new costume. Day 100 fixed it in the container with `ENV PYTHONPATH=/app`; the code-deploy
  equivalent is an app setting: `PYTHONPATH=/home/site/wwwroot`.
- **A timeout with no error** → the port is wrong; the platform forwards to 8000.

📌 Whichever it is, **write the real answer into the tracker.** Day 104 and Day 106 run processes
directly on VMs and will hit the same family of "is the entry point where I think it is" question.

**Step 5 — one real turn.**

```powershell
curl.exe -X POST -H "Content-Type: application/json" "$APP/apps/sutra/users/u1/sessions/s1" -d "{}"
curl.exe -X POST -H "Content-Type: application/json" "$APP/run" `
  -d '{"appName":"sutra","userId":"u1","sessionId":"s1","newMessage":{"role":"user","parts":[{"text":"A customer says checkout is broken."}]}}'
```

✅ *Verify:* Sutra's real triage reply. ⚠️ `camelCase` field names — Day 097's finding, unchanged.

📌 Note what F1 gives you that Day 100's Container App did *not*: this app does **not** scale to
zero, so a second request minutes later reaches the **same process** — and the in-memory session
from the first request is still there. Day 100 §5's amnesia doesn't reproduce here. That is not
because F1 is better; it's because "always one shared instance" and "zero to N instances" are
different failure surfaces. ⚠️ It is still not *durable* — an app restart (which the platform
does on its own schedule, and which Step 7's quota wall causes) loses it just the same.

**Step 6 — the container-on-F1 diagnostic (the day's open question).**

This is the experiment `03_azure.md` §5 implies works and Microsoft's own quickstarts avoid. Run
it deliberately, in its own throwaway app, and record the outcome:

```powershell
az webapp create --name sutra-f1-ctr-<your-suffix> --resource-group sutra-f1-rg `
  --plan sutra-f1-plan `
  --deployment-container-image-name "ghcr.io/<your-github-username>/sutra-agent:v1"

az webapp config appsettings set --name sutra-f1-ctr-<your-suffix> --resource-group sutra-f1-rg `
  --settings WEBSITES_PORT=8000 GOOGLE_GENAI_USE_VERTEXAI=FALSE GOOGLE_API_KEY="$env:GOOGLE_API_KEY"
```

(`WEBSITES_PORT` is the custom-container port setting, confirmed at
`learn.microsoft.com/en-us/azure/app-service/configure-custom-container` — App Service assumes
port 80 otherwise. It is the exact analogue of Day 100's `--target-port`, with a different name
and a different failure signature: a silent hang rather than a 502.)

✅ *Verify — and this verification is the deliverable, whichever way it goes:*

- **If `az webapp create` fails** with a tier/SKU error → `03_azure.md` §5 is wrong, B1 is the
  real minimum, and this track should say so. Record the exact error text.
- **If it succeeds and the app serves `/list-apps`** → `03_azure.md` §5 is right, F1 does accept
  custom containers, and Day 100's "leaving GCP means owning a container" story gains a second
  Azure home. Record that too.
- **If it succeeds but never becomes healthy** → read `az webapp log tail` before concluding
  anything. A container that pulls but won't start is a third, different answer.

Either way, delete this throwaway app immediately after: it shares the F1 plan's single daily CPU
budget with the app from Step 3 (DEPLOY-05a: F1 is *"metered on a per app basis"*, but they share
one shared-VM allocation).

```powershell
az webapp delete --name sutra-f1-ctr-<your-suffix> --resource-group sutra-f1-rg
```

## 5 · 💥 Failure lab — the day your app stops answering, and nothing is broken

> 🎬 **The scene:** F1 is working. You're iterating — a few requests to check a prompt change, a
> few more to show a colleague, a browser tab left refreshing. Some time in the afternoon,
> requests start returning **403** with a message about quota, or the site simply serves an error
> page. Nothing was deployed. No code changed. `az webapp show` says the app is running.
>
> 😬 **The naive fix:** restart the app. Redeploy. Check whether Gemini is down. Read the
> application logs for an exception that isn't there.
>
> 💥 **What actually happened, mechanically:** you spent the day's **60 CPU-minutes**
> (DEPLOY-05a). App Service's Free tier meters *CPU time consumed by your app*, per day, and when
> the allowance is exhausted the platform **stops the app until the quota resets** — roughly
> midnight UTC. This is not a throttle that slows you down; it is a stop. And critically, it is
> not visible in any of the places you'd instinctively look, because nothing failed: the app was
> switched off on purpose, by the tier you chose.
>
> 💡 **The insight: a "free tier" can meter something your monitoring doesn't watch.** Requests,
> memory, and error rates all looked fine right up to the moment the app stopped. The resource
> that ran out was one you were never counting — and this is precisely why
> `00_stay_free_safety.md` §2 asks you to *write down the number you intend to stay under, in the
> units the provider bills in*, before creating anything. Requests are not the unit here.
> CPU-minutes are.

**Where you actually look:**

```powershell
az webapp show --name sutra-f1-<your-suffix> --resource-group sutra-f1-rg `
  --query "{state:state, usageState:usageState, enabled:enabled}" -o table
```

✅ *Verify:* `usageState` is the field that tells the truth. `Normal` means you have budget;
**`Exceeded`** means you hit the wall and the app is stopped until reset.

**The budget arithmetic — do this instead of hitting the wall empirically, unless you want to
spend the model quota to watch it happen:**

60 CPU-minutes = 3,600 CPU-seconds per day. An `adk api_server` request spends most of its
wall-clock time *waiting on Gemini*, which is not CPU time — so per-request CPU is small
(tens of milliseconds for routing and serialisation), but the **process's idle overhead is not
zero**, and F1 has no scale-to-zero to protect you from it.

📌 So the honest statement is: **the wall is real, and where exactly it sits depends on your app's
idle CPU, which you should measure rather than estimate.** Leave the app up for an hour with no
traffic, then read `usageState` and the portal's CPU-time metric. That measurement is worth more
than any number this doc could print, and it's free.

**The two real fixes, and neither is "restart it":**

1. **Accept the ceiling and design for it** — F1 is documented, in Microsoft's own words, as
   *"intended for trials, experimentation, and learning… not supported for production
   workloads."* Using it for a demo you switch on for a meeting is inside its design. Using it
   for anything with a pulse is not.
2. **Move to the tier whose meter matches your workload** — which, for a bursty agent, is
   Day 100's Container Apps: metered on vCPU-seconds *actually consumed*, with a replica count of
   zero when nobody's asking. An idle Container App consumes nothing; an idle F1 app consumes
   from a daily allowance you can't see.

## 6 · 🎤 Interview corner

1. **"Azure gives you App Service Free, Functions Consumption, and Container Apps — all free.
   How do you choose?"** — By what each one *meters*, not by the word free. F1 meters CPU-minutes
   per day and can't scale out, so it's a demo tier with a hard daily stop. Functions meters
   invocations and GB-seconds, which is a bad shape for an agent because you'd be paying by the
   GB-second for time spent blocked on someone else's LLM API. Container Apps meters
   vCPU-seconds with real scale-to-zero, so idle costs nothing and the grant matches bursty
   traffic. I put the agent on Container Apps and used the other two for what they're shaped for.
2. **"Tell me about a time a service failed and nothing was wrong."** — App Service F1 stops your
   app when the daily 60-CPU-minute allowance runs out. Requests start failing, no code changed,
   the app reports as running, and there's no exception anywhere — because the platform switched
   it off on purpose. The tell is the `usageState` field reading `Exceeded`. The lesson I took
   from it is to write down which unit a free tier actually meters before deploying, because your
   dashboards will be watching a different one.
3. **"When would you put an LLM agent behind Functions?"** — I wouldn't put the agent there, but I
   would put its *edges* there: a webhook receiver that validates and enqueues, a nightly digest
   on a timer, an alert handler. Those are short, stateless, event-shaped — which is what the
   runtime is good at. The agent itself is a long-lived stateful server whose latency is
   dominated by a network call, and per-invocation billing punishes exactly that.
4. **"How did you handle a documentation conflict?"** — Our own internal Azure notes paired
   `--sku F1` with a custom container image, while every Microsoft quickstart used B1 and the
   official plan docs didn't state a position. Rather than pick the convenient reading, I routed
   the real deployment through the path that was unambiguously supported, then ran the disputed
   configuration as an isolated experiment and recorded the actual result — so the next person
   gets an answer instead of inheriting the same ambiguity.
