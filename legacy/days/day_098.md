## 1 · 🎬 Where we are — the story so far

Day 97 rented a car: one command, and Google decided how the container starts, restarts, and
scales. Today Sutra gets its own car — a real Debian VM, billed nothing as long as you don't
exceed one instance's worth of hours a month — and with it, a new job nobody was doing before:
**deciding what happens when the process dies.** On a laptop, that job is "you, noticing." On
Cloud Run, it was Google's scheduler. On a bare VM, it's whatever you write down — today, that's
`systemd`, and the day's failure lab is about exactly the moment you find out you need it.

## 3 · 📚 Concepts

### DEPLOY-02a — The Always-Free terms, exactly (not "commonly documented")

Quoted verbatim from `docs.cloud.google.com/free/docs/free-cloud-features` (2026-08-21, page
last updated 2026-08-11):

> *"1 non-preemptible e2-micro VM instance per month in one of the following US regions:
> Oregon: us-west1. Iowa: us-central1. South Carolina: us-east1. 30 GB-months standard
> persistent disk. 1 GB of outbound data transfer from North America to all region destinations
> ... per month. Your Free Tier e2-micro instance limit is by time, not by instance. Each month,
> eligible use of all of your e2-micro instances is free until you have used a number of hours
> equal to the total hours in the current month."*

💡 **Mental model, and it's the opposite of Day 97's:** Cloud Run's free grant rewards scaling
**to zero**. The e2-micro grant rewards running **one instance, continuously, all month** — one
VM running 24/7 for a full month uses exactly "the total hours in the current month," which is
precisely what the free tier covers. The trap isn't leaving it running — it's ending up with
**more than one instance's worth of hours** at once (a second e2-micro you forgot about, running
in parallel, silently doubling your hour-count for the month).

### DEPLOY-02b — Persistent sessions, on real disk, for free

Day 97's Cloud Run deployment defaulted to **in-memory** sessions — gone on every cold start.
`adk api_server`'s `--session_service_uri` option (confirmed, `adk.dev/api-reference/cli/`)
accepts a `sqlite://<path>` URL. On a VM with a real, persistent disk, this is genuinely
free and genuinely durable across restarts — not a workaround, the actual right tool for a
single-instance deployment. (When you outgrow *single instance*, that's Day 108's job — a real
managed Postgres, not a bigger SQLite file.)

### DEPLOY-02c — IaaS vs PaaS, said as the one sentence that survives an interview

Day 97: you gave Google a container; Google decided how it starts, restarts, and is exposed. Today:
you get a kernel and a blank disk, and every one of those decisions is now explicitly yours to
write down. 💡 **Neither is "better" — they trade control for undifferentiated labor, in
opposite directions.** The rest of today is that trade made concrete: §7's `systemd` unit is the
one-paragraph answer to "who restarts this?" that a managed platform gives you for free and a VM
does not.

## 4 · 🛠️ The build

> Shell: **PowerShell** locally for `gcloud`; a Linux shell over SSH once you connect.

**Step 1 — sanity and region check.**

```powershell
gcloud auth list
```

✅ *Verify:* an account is listed. Pick **one** of the three confirmed-free regions
(§3): `us-west1`, `us-central1`, or `us-east1`. This doc uses `us-central1-a`.

**Step 2 — create the VM, in the free-tier shape exactly.**

```powershell
gcloud compute instances create sutra-vm `
  --zone=us-central1-a `
  --machine-type=e2-micro `
  --image-family=debian-12 `
  --image-project=debian-cloud `
  --boot-disk-size=30GB `
  --boot-disk-type=pd-standard `
  --tags=sutra-agent
```

| Flag | What it does |
| --- | --- |
| `--machine-type=e2-micro` | the exact shape the free grant covers (§3) — any other type bills from the first second |
| `--boot-disk-size=30GB` | matches the free grant's **30 GB-months** exactly — larger bills for the overage, smaller wastes nothing but is fine too |
| `--boot-disk-type=pd-standard` | "standard persistent disk" is what the free grant names; SSD (`pd-ssd`/`pd-balanced`) is a different, billed product |
| `--tags=sutra-agent` | a label the firewall rule (Step 3) targets — without a shared tag, a firewall rule can't scope itself to just this VM |

✅ *Verify:* `gcloud compute instances list` shows `sutra-vm`, zone `us-central1-a`, status
`RUNNING`.

**Step 3 — firewall rule for port 8000.**

GCP VMs default to **no open inbound ports** beyond SSH/ICMP. Nothing reaches `adk api_server`
without this:

```powershell
gcloud compute firewall-rules create allow-adk-api-server `
  --allow=tcp:8000 --target-tags=sutra-agent --source-ranges=0.0.0.0/0
```

⚠️ `--source-ranges=0.0.0.0/0` means **anyone on the internet** can reach port 8000, and
`adk api_server` has no authentication of its own (same caveat Day 85/86 already raise for
Sutra's own API surface). Fine for today's brief, deliberate test; narrow
`--source-ranges` to your own IP (`curl ifconfig.me` tells you what that is) if you leave this
running unattended.

✅ *Verify:* `gcloud compute firewall-rules describe allow-adk-api-server` shows the rule,
scoped to the `sutra-agent` tag.

**Step 4 — get the code onto the VM.**

```powershell
gcloud compute ssh sutra-vm --zone=us-central1-a
```

On the VM, if your repo is pushed to a remote you control:

```bash
sudo apt-get update && sudo apt-get install -y git
git clone <your-repo-url> sutra-repo && cd sutra-repo
```

If it isn't pushed anywhere yet, copy it directly instead (run this from a **second, local**
PowerShell window, repo root):

```powershell
gcloud compute scp --recurse --zone=us-central1-a `
  .\sutra .\pyproject.toml .\uv.lock sutra-vm:~/sutra-repo/
```

✅ *Verify:* `ls sutra-repo/sutra/agent.py` on the VM shows the file.

**Step 5 — `uv sync`, the `.env`, and the swapfile.**

```bash
# on the VM, inside sutra-repo/
curl -LsSf https://astral.sh/uv/install.sh | sh
source $HOME/.local/bin/env
uv sync
```

The `.env` file is never committed and never cloned with `git` — copy it explicitly, the same
"inject, don't bake in" rule as every other day in this track:

```powershell
# from your LOCAL machine, second window
gcloud compute scp --zone=us-central1-a .env sutra-vm:~/sutra-repo/.env
```

`e2-micro` has **1 GB of RAM** — real, and tight for a Python process holding an HTTP client and
a model SDK. Add a swapfile as a safety net (standard Linux practice for small VMs, not
GCP-specific):

```bash
sudo fallocate -l 1G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

✅ *Verify:* `free -h` shows a `Swap:` line with `1.0Gi`; `python -c "import sutra.agent;
print(sutra.agent.root_agent.name)"` (run via `uv run python -c "..."`) prints `sutra_triage`.

**Step 6 — first manual run.**

```bash
mkdir -p data
uv run adk api_server --host 0.0.0.0 --port 8000 `
  --session_service_uri="sqlite:///$(pwd)/data/sessions.db" sutra
```

Wait — this is PowerShell-style continuation; in a real `bash` shell on the VM, use `\` instead
of `` ` ``:

```bash
uv run adk api_server --host 0.0.0.0 --port 8000 \
  --session_service_uri="sqlite:///$(pwd)/data/sessions.db" sutra
```

| Flag | What it does |
| --- | --- |
| `--host 0.0.0.0` | binds all interfaces — the VM equivalent of Day 86's note that `0.0.0.0` is *correct* only inside a container/VM boundary, never on a laptop |
| `--session_service_uri="sqlite:///…/data/sessions.db"` | DEPLOY-02b — real, disk-backed sessions, confirmed supported by `adk api_server` |
| `sutra` (positional `AGENTS_DIR`) | a single-agent folder, exactly like the `adk run sutra` you've used since Day 5 — **no** `__init__.py` change needed here |

From your **local** machine:

```powershell
$VM_IP = gcloud compute instances describe sutra-vm --zone=us-central1-a --format="value(networkInterfaces[0].accessConfigs[0].natIP)"
curl.exe "http://$($VM_IP):8000/list-apps"
curl.exe -X POST "http://$($VM_IP):8000/apps/sutra/users/u1/sessions/s1" -H "Content-Type: application/json" -d "{}"
curl.exe -X POST "http://$($VM_IP):8000/run" -H "Content-Type: application/json" `
  -d '{"appName":"sutra","userId":"u1","sessionId":"s1","newMessage":{"role":"user","parts":[{"text":"A customer says checkout is broken."}]}}'
```

✅ *Verify:* `/list-apps` returns `["sutra"]`; `/run` returns Sutra's real triage reply. This is
the step that spends real quota (1–2 model calls). Leave this running — the failure lab needs it
alive.

## 5 · 💥 Failure lab — the SSH session you closed

> 🎬 **The scene:** Step 6 worked. You close the laptop lid, or your SSH connection drops
> because your Wi-Fi hiccuped for two seconds. You reconnect a minute later, run the same `curl`
> from Step 6 again.
>
> 😬 **The naive fix:** SSH back in, run the `adk api_server` command again, keep the terminal
> open this time, promise yourself you won't close it.
>
> 💥 **Why it fails, mechanically:** `adk api_server` in Step 6 is a **foreground process**
> attached to your SSH session's terminal. When that session ends — cleanly or not — the
> terminal sends `SIGHUP` ("hang up") to every process still attached to it, and the default
> handling for `SIGHUP` is to terminate. Nothing about Cloud Run's `--min-instances=0` model
> applies here: there is no scheduler watching this process, because you haven't told anything
> to watch it yet. A closed laptop lid or a flaky Wi-Fi connection is now a full outage.
>
> 💡 **The insight: on a VM, "keeps running" is not a property of the program — it's a property
> of whatever supervises it, and by default nothing does.** The fix that actually holds is
> `systemd` — the same init system that starts every other long-running service on this Debian
> box, doing the same job for yours.

**The real fix — a `systemd` unit:**

```bash
# stop the manual foreground run (Ctrl-C) first
sudo tee /etc/systemd/system/sutra-agent.service > /dev/null <<'EOF'
[Unit]
Description=Sutra ADK API server
After=network.target

[Service]
Type=simple
User=YOUR_VM_USERNAME
WorkingDirectory=/home/YOUR_VM_USERNAME/sutra-repo
ExecStart=/home/YOUR_VM_USERNAME/.local/bin/uv run adk api_server --host 0.0.0.0 --port 8000 --session_service_uri=sqlite:///home/YOUR_VM_USERNAME/sutra-repo/data/sessions.db sutra
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now sutra-agent
systemctl status sutra-agent
```

| Line | What it does |
| --- | --- |
| `Type=simple` | systemd treats the `ExecStart` process itself as the service — right model for a process that doesn't fork/daemonize on its own |
| `Restart=always` / `RestartSec=5` | **the actual fix** — if the process dies for *any* reason (crash, OOM-kill, you `kill` it by mistake), systemd starts it again 5 seconds later, indefinitely |
| `WantedBy=multi-user.target` | starts automatically on every future boot — the VM rebooting is no longer an outage either |
| `enable --now` | `enable` wires it into boot; `--now` also starts it immediately, in one command |

✅ *Verify (the actual test of today's fix):* close your SSH session entirely (`exit`), wait ten
seconds, then from your **local** machine re-run the `curl` from Step 6. It still answers —
the terminal that started the process is gone, and the process is still running, supervised by
`systemd` instead of by you.

## 7 · 🎤 Interview corner

1. **"Compute Engine vs Cloud Run — how do you choose?"** — Cloud Run for bursty, scale-to-zero
   HTTP workloads where idle time should cost nothing; a VM when you need a real, addressable,
   always-on host — a persistent local database, a process that isn't naturally request-shaped,
   or (today's actual reason) learning what a managed platform does for you by first not having
   it. I used `sqlite`-backed sessions on real disk today specifically because Cloud Run's
   filesystem couldn't give me that for free.
2. **"What keeps a long-running process alive on a bare VM?"** — Nothing, by default — and I can
   describe exactly the failure mode that teaches that (a dropped SSH session sends `SIGHUP` to
   everything attached to it). The fix is a process supervisor; I used `systemd` with
   `Restart=always`, which is also what makes a reboot survivable, via `WantedBy=multi-user.target`.
3. **"How does GCP's free VM tier actually work, mechanically?"** — Not "one instance is free" —
   a pool of hours per month, combined across every e2-micro instance on the account, sized to
   exactly cover one instance running continuously. That's a materially different economic model
   from Cloud Run's per-request free grant, and confusing the two (e.g., assuming *idle* VM time
   is free the way idle Cloud Run time is) is the mistake that turns "free" into a bill.
