## 1 · 🎬 Where we are — the story so far

Two days into the framework era, and something should be nagging you. On Day 3 *you*
were the loop — every message that moved, moved because your code moved it, and every
step printed its `CALL:` and `RESULT:` lines because you wrote the `print`. Since Day 5,
ADK runs the loop — and yesterday, in the `adk web` Events panel, you *saw* the records
it keeps instead. You clicked them. You read the instruction riding inside a request.

Today we stop clicking and start programming. The records have a name — **events** — and
they are not a debugging garnish: they are **the actual substance of an ADK run**. The
runner does not "produce an answer and also log some events." It produces *only* events;
the answer is simply the last event with text in it. Understand events and you
understand everything ADK will do for the next 89 days — tool calls, state changes,
streaming, pauses for human approval: all of it arrives as events.

And there is a second reason today matters: this is the most dangerous corner of the
1.x→2.x minefield. The internet's ADK tutorials handle events with 1.x field names and
1.x habits (build a list, append, return). ADK 2.0 renamed and extended the schema
(trap #2) and made direct appending illegal (trap #3). Today you learn the 2.x truth
from the 2.x source, once, properly.

## 3 · 📚 Concepts

### ADK-04 — The event model: everything is a receipt

**The courtroom story.** A court does not "just reach a verdict." Every motion, every
piece of evidence, every objection is **entered into the record** — typed, numbered,
attributed, timestamped. The verdict is only the final entry. Ask "what happened in this
trial?" and the answer is never a vibe; it is the record, entry by entry.

An ADK run is a trial, and events are the record:

| Courtroom | ADK | Field that carries it |
| --- | --- | --- |
| who spoke | `'user'` or the agent's name | `author` |
| what was said/submitted | text, function calls, function responses | `content` |
| rulings with side effects | state changes, artifact saves, control signals | `actions` |
| the entry's number | unique id per event | `id` |
| "all entries of this hearing" | one user-turn's whole cycle | `invocation_id` |
| the clock | creation time | `timestamp` |

Those are the fields you already conceptually built on Day 3 — `author`+`content` are
your transcript entries; the printed `CALL:`/`RESULT:` lines were `content` carrying
function calls and responses. The genuinely new machinery (verified 2026-08-18):

- `partial` — `True` on a streaming chunk (today's second half lives here),
- `turn_complete` — the turn-boundary flag,
- `branch` — which path of a multi-agent hierarchy authored this (Phase 8),
- `long_running_tool_ids` — tools that answer *later* (Day 36's MCP tasks rhyme),
- **`node_info` and `output` — added in 2.0** (trap #2 made concrete: these two fields
  track graph-node identity and node outputs for the Workflow Runtime; their arrival is
  exactly why strict 1.x-shaped validators and DB schemas break on 2.0 events).

**"Which event is the answer?"** is a real question — a single turn emits several
events. The official helper is `event.is_final_response()`, and its logic is worth
knowing by heart because it encodes the whole protocol (verified): it is `True` when the
event has **no function calls, no function responses, is not partial**, and is not an
intermediate code-execution result (with two special-case early-`True`s:
`skip_summarization` and long-running tool ids). Read that list again — it is Day 4's
termination rule ("a turn with no forms filled IS the answer"), grown field-checks.

**Who writes the record?** The runner, alone — and this is trap #3's territory, so take
the mechanism slowly (verified on the event-loop page):

1. An agent (or node) that wants to say something **yields** an Event and *stops*.
2. The runner catches it, hands it to the SessionService, which **persists it and
   applies its `actions`** (state changes, etc.). This is the **commit point**.
3. Only then does the agent's code **resume** past its `yield`.

That pause-until-committed rhythm is why "just append my event to
`session.events`" — the 1.x folk habit — is now forbidden: an appended event skips the
commit point, so nothing applied its actions, nothing routed it, nothing streamed it.
It is a minute in the record that no court reporter wrote: the record is now lying.

💡 **Mental model: an ADK run is not a function that returns an answer — it is a court
that produces a record, and the answer is the record's last line.** Everything is a
trace (Principle 12), enforced by architecture.

### ADK-05 — Streaming: the difference between a letter and a phone call

**The story.** Ask a colleague a question by letter, and you wait, then receive the full
answer at once. Ask by phone, and the answer *arrives as it is being thought* — you can
nod along, interrupt, or hang up early. Same words; radically different experience.

Until today every Sutra turn was a letter: `run_async` yielded nothing visible until the
model finished. Streaming turns it into a phone call. The verified switch:

```python
from google.adk.agents.run_config import RunConfig, StreamingMode

config = RunConfig(streaming_mode=StreamingMode.SSE)   # letters -> phone call
```

passed as `run_config=config` into `run_async`. Three modes exist: `NONE` (default —
letters), `SSE` (server-sent events — one-way phone call, the web's standard
"typewriter" transport), and `BIDI` (two-way, for the Live API — Phase 11's territory;
parked until then).

What changes in the event stream — and this is the part people get wrong: the runner now
yields **many events per turn**: a series of chunk-events with `partial=True`, each
carrying a *piece* of text, and then a **final aggregated event** carrying the *complete*
text, with `partial` false — and only that last one passes `is_final_response()`. So a
correct consumer prints the pieces as they come, and uses the final event for
*bookkeeping only* (it is what gets persisted, and what code should treat as "the
answer"). Print both, and every reply appears twice (§5 makes you do it on purpose,
because you will see this bug in the wild).

One more `RunConfig` field, spotted while we are on the page and too good to skip:
`max_llm_calls` (default 500) — a hard cap on model calls per run. Recognize it? It is
`MAX_STEPS` from Day 3, industrialized. The brake you hand-rolled is a config field now;
Sutra's runs will set it deliberately from Phase 8 on.

💡 **Mental model: streaming does not change what is said — it changes when you get to
hear it.** The final event is identical either way; SSE just lets you listen in while it
forms. Protocol unchanged, experience transformed.

```python
"""Day 7 — events & streaming: the 2.x event model, observed live.

Two demos against the Day 5/6 agent:

    python -m sutra.events_lab anatomy   # one turn, every event, as a table
    python -m sutra.events_lab stream    # the typewriter: SSE partial events

2.x trap notes (plan 5.1): event handling here is written from the 2.x
docs (fields incl. the 2.0 additions node_info/output) - never from 1.x
tutorials (trap #2). We only CONSUME events; producing them stays the
runner's job - custom nodes yield, never append (trap #3, Phase 8).

Importable with no side effects. Each demo costs exactly 1 model call.
"""
from __future__ import annotations

import asyncio
import sys

from google.adk.agents.run_config import RunConfig, StreamingMode  # verified 2026-08-18
from google.adk.runners import InMemoryRunner                      # Day 8 opens this box
from google.genai import types

from sutra.agent import root_agent


def _msg(text: str) -> types.Content:
    """Wrap plain text as the user turn the runner expects.

    Args:
        text: what the user says.

    Returns:
        A Content(role="user") - same shape we hand-built on Days 3-4.

    Example:
        >>> _msg("hello").role
        'user'
    """
    return types.Content(role="user", parts=[types.Part(text=text)])


async def _new_session(runner: InMemoryRunner, user_id: str) -> str:
    """Create one throwaway session; return its id.

    The session is Day 3's `transcript` list with a proper landlord -
    Day 8 is a whole day on this. Today we just need somewhere to talk.

    Args:
        runner: the InMemoryRunner owning the session service.
        user_id: any stable string naming the user.

    Returns:
        The new session's id string.

    Example:
        >>> sid = asyncio.run(_new_session(runner, "lab"))  # doctest: +SKIP
    """
    session = await runner.session_service.create_session(
        app_name=runner.app_name,   # the runner names the app for us
        user_id=user_id,            # sessions are filed under (app, user)
    )
    return session.id


def _describe(event: object) -> str:
    """One table row summarizing an event - only 2.x-verified fields.

    Args:
        event: an ADK Event yielded by run_async.

    Returns:
        A fixed-width line: author, partial, calls, final, text preview.

    Example:
        >>> # given a final text event e:
        >>> # _describe(e) -> 'sutra_triage  partial=False calls=0 final=True  "Hello..."'
    """
    calls = event.content and getattr(event.content, "parts", None) and [
        p for p in event.content.parts if getattr(p, "function_call", None)
    ] or []                                           # function-call parts, if any
    text = ""                                         # first text part, previewed
    if event.content and event.content.parts:
        for p in event.content.parts:
            if getattr(p, "text", None):
                text = p.text[:40].replace("\n", " ")  # keep the table readable
                break
    return (f"{event.author:<14} partial={bool(event.partial)!s:<5} "
            f"calls={len(calls)} final={event.is_final_response()!s:<5} "
            f'"{text}"')


async def demo_anatomy() -> None:
    """One non-streaming turn, every event printed as a table row.

    Usage:  python -m sutra.events_lab anatomy     (1 model call)
    """
    runner = InMemoryRunner(agent=root_agent)          # loop-in-a-box
    session_id = await _new_session(runner, "anatomy")
    print(f"{'author':<14} {'partial':<13} calls final  text")
    async for event in runner.run_async(               # the record, entry by entry
        user_id="anatomy",
        session_id=session_id,
        new_message=_msg("In one sentence: what do you do?"),
    ):
        print(_describe(event))                        # each event = one receipt
        # Trap #2 exhibit: the 2.0-added fields, present on every event.
        print(f"{'':14}   node_info={getattr(event, 'node_info', None)!r} "
              f"output={getattr(event, 'output', None)!r}")


async def demo_stream(misprint: bool = False) -> None:
    """The typewriter: SSE streaming, chunk by chunk.

    Correct consumption: print text from partial events AS IT ARRIVES;
    treat the final aggregated event as bookkeeping, not display.
    With misprint=True we do it WRONG on purpose (failure lab, doc 5).

    Usage:  python -m sutra.events_lab stream      (1 model call)
    """
    runner = InMemoryRunner(agent=root_agent)
    session_id = await _new_session(runner, "stream")
    config = RunConfig(streaming_mode=StreamingMode.SSE)   # letters -> phone call
    chunks = 0                                             # count the pieces
    async for event in runner.run_async(
        user_id="stream",
        session_id=session_id,
        new_message=_msg("Explain in 3 sentences what ticket triage means."),
        run_config=config,                                 # the one-line switch
    ):
        text = ""
        if event.content and event.content.parts:
            text = "".join(p.text or "" for p in event.content.parts
                           if getattr(p, "text", None))
        if event.partial:                                  # a chunk: print AS IT ARRIVES
            chunks += 1
            print(text, end="", flush=True)                # no newline: typewriter feel
        elif event.is_final_response():                    # the aggregated final event
            if misprint:                                   # the classic bug, on demand
                print(text, end="", flush=True)            # WRONG: prints it all again
            print(f"\n--- done: {chunks} partial chunks, then 1 final event ---")


def main() -> None:
    """Tiny demo dispatcher - the house pattern since Day 2."""
    demos = {
        "anatomy": lambda: asyncio.run(demo_anatomy()),
        "stream": lambda: asyncio.run(demo_stream()),
        "misprint": lambda: asyncio.run(demo_stream(misprint=True)),
    }
    name = sys.argv[1] if len(sys.argv) > 1 else "anatomy"
    if name not in demos:
        print(f"usage: python -m sutra.events_lab [{'|'.join(demos)}]")
        raise SystemExit(2)
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the answer that arrived twice

> 🎬 **The scene:** you wire streaming into a chat UI. The obvious consumer: "for every
> event, if it has text, print the text." Symmetric, clean, works in the non-streaming
> mode you tested first.
> 😬 **The naive fix:** ship that consumer with `StreamingMode.SSE` turned on.
> 💥 **Why it fails:** run `python -m sutra.events_lab misprint` and watch: the full
> answer types itself out… and then **prints again, whole**. Nothing is duplicated on
> the wire — the protocol is *supposed* to send both: N `partial=True` chunk-events (for
> display) and then one aggregated final event (for the permanent record — it is what
> the session persists and what `is_final_response()` blesses). The bug is a consumer
> that treats two different kinds of receipt as the same kind. And the mirror-image bug
> is nastier: print only *final* events and streaming "does nothing" — the UI sits
> silent for the whole generation, then dumps everything at once, and someone "fixes" it
> by turning streaming off. In the wild you will meet both, usually copied from a 1.x
> tutorial that checked fields which no longer say what the author thought (trap #2's
> revenge).
> 💡 **The insight:** **in a streaming protocol, chunks are for the eyes and the final
> event is for the books — a consumer must pick exactly one job per event kind.**
> Display code keys on `partial`; bookkeeping code keys on `is_final_response()`; no
> event serves both masters.

Observed today, not just asserted: `stream` printed each sentence once; `misprint`
printed the story twice; the code differs by one deliberate line.

## 6 · 🎤 Interview corner

1. **"Walk me through what actually happens, event-wise, in one agent turn."** — The
   runner drives the agent; everything the agent wants to say or do is yielded as a
   typed Event — author, content, actions, timestamps, plus graph metadata since 2.0.
   Each yield is a synchronization point: the agent pauses, the runner hands the event
   to the session service which persists it and applies its state actions — the commit
   point — and only then does the agent resume. The "answer" is just the one event that
   passes `is_final_response()`: no function calls, no function responses, not partial.
   I've consumed this stream directly — table-dumping a turn is my first debugging move.
2. **"Why can't an agent just append its event to the session history?"** — Because
   persistence is the runner's commit point, and appending skips it: nothing applies the
   event's state actions, nothing routes or streams it, and the history now contains an
   entry the framework never processed — a record that lies. ADK 2.0 made this explicit:
   custom nodes yield events and pause until the runner commits; that ordering is what
   makes "state I read after yielding is up to date" a guarantee instead of a race.
3. **"How does streaming change your consuming code?"** — The turn becomes many events:
   partial chunks carrying pieces of text, then one aggregated final event. Display
   keys on `partial` and prints as pieces arrive; bookkeeping keys on
   `is_final_response()` and touches only the aggregate. Conflate them and you get the
   two classic bugs — every answer printed twice, or streaming that appears dead. And
   the switch is config, not code: `RunConfig(streaming_mode=SSE)` — the same consumer
   discipline then carries to bidirectional streaming for voice.
