## 1 · 🎬 Where we are — the story so far

Ninety-five days ago there was an empty folder and a plan that had already been lost once
and rebuilt (ADR-0001). Today there is a system that triages support tickets end to end, a
public repository, one hundred and ninety-nine closed concept IDs, five ledgers, a security
review, an eval suite, a red-team scorecard, a container, a cluster, a demo recording, and
a document explaining every one of them.

The plan gets its own gate today, by its own rules. §15 defines what "green" means, and
it applies to the last phase exactly as it applied to the first — which is the point of
having written it down before you knew whether you would make it.

Then the honest part. A ninety-six-day project ends in one of two ways: it becomes a thing
you maintain, or it becomes a screenshot. Nothing about today decides that except what you
write in the last section — a checklist small enough that you will actually run it, aimed
at the specific things that decay. Everything in this repo is pinned to a date: an ADK
version, three free-tier model policies, an MCP spec revision, an experimental A2A surface,
a security review with a next-review date. Pinned means reproducible. It does not mean
true.

## 3 · 📚 Concepts

### A gate you apply to yourself at the end is worth what you wrote at the start

**The story.** Anyone can judge a race after seeing who ran it. The finish line has to be
painted before the runners arrive, or it is not a finish line — it is an opinion.

§15's criteria were written on Day 0, before you knew which parts would go badly. That is
the only reason they can be trusted now. Applying them today, unaltered, even where a
criterion is inconvenient, is what makes the whole ledger discipline mean something in
retrospect.

⚠️ **The temptation, stated so you can watch for it:** on the last day, with everything
essentially working, there is enormous pressure to interpret a criterion generously. A
skipped verification here, a "close enough" there. Resist it for one specific reason —
this repo is public and the ledgers claim things. A green row you did not earn is now a
false public statement, and it is the kind of thing that unravels an entire body of work
when someone finds it.

### The lessons that recurred are the real ones

A retrospective that lists ninety-six lessons has none. The useful move is to find the
lessons that showed up **more than once, in unrelated places** — those are structural
rather than incidental. This project has several, and they are worth naming precisely
because you will carry them to work that has nothing to do with agents:

| Recurred as | The pattern underneath |
| --- | --- |
| Day 92's undocumented MCP tool · Day 94's index that only a day-log built · Day 95's decisions buried in narrative | **Writing it down is not making it findable.** A control you must remember is not a control; a doc nobody can route to is not documentation. |
| Day 86's two replicas · Day 88's `emptyDir` · Day 91's chat arrival rate | **State and load live somewhere, whether or not you designed for them.** "Stateless" describes where state lives, not whether it exists. |
| Day 88's loopback MCP · Day 91's Socket Mode · Day 85's localhost bind | **Direction of connection is a security property.** Prefer dialling out to listening. |
| Day 63's approval gate · Day 89's signature ≠ authorization · Day 90's act-for-not-as | **Proving who ≠ deciding what.** Authentication and authorization are separate systems and mixing them is how permissions leak. |
| Every fail-closed table (`POLICY`, `TIERS`, `ROLE_OF`, `TRUSTED_ISSUERS`, registry) | **Unknown input must mean no.** The default case is a security decision, always. |
| Day 66's injection · Day 94's empty archive answered anyway | **A system that can't distinguish "I looked and found nothing" from "I couldn't look" will confidently make things up.** |

💡 **Mental model: a retrospective is a compression pass.** Ninety-six documents in, six or
seven transferable sentences out. If you cannot compress it, you have not finished
understanding it — which is the same test Day 95's drill applied to your spoken answers.

### The habit, and why it is small on purpose

Everything pinned in this repo has a half-life:

| What | Decays because |
| --- | --- |
| `google-adk` version | releases, and 2.x moves fast; security fixes land in it |
| Model pins + free tiers | providers change free lists and retire models on published dates |
| MCP spec revision | the standing rule in Addendum 01 Part 2 exists precisely for this |
| A2A / ADK's A2A surface | flagged **experimental** by ADK itself (Day 89) |
| The security review | has a next-review date (Day 92) |
| Vendored skills | licences and upstream sources move (`SKILL_PROVENANCE.md`) |

> 🎬 **The scene:** you finish, and you write an ambitious maintenance plan — monthly full
> re-verification, quarterly dependency upgrades, a rerun of the whole eval suite.
> 😬 **The naive fix:** more ambition. If fifteen minutes is good, an hour is better.
> 💥 **Why it fails:** you will do it twice. A maintenance ritual competes with whatever
> you are actually doing next, and it loses, because its value is invisible until the week
> it isn't. Then six months pass, the ADK is four minor versions ahead, a pinned model was
> retired, and the repo you point interviewers at does not start.
> 💡 **The insight: size the habit to the worst week, not the best one.** Fifteen minutes
> that gets done beats an hour that doesn't. And make the *first* fifteen minutes happen
> today, in this document, so it is a thing you have done rather than a thing you intend.

## 5 · 💥 Failure lab — the repo that stopped working while nobody was looking

> 🎬 **The scene:** six months from now. An interview is going well, and they ask to see
> the project. You clone it fresh — you have learned that much — and it does not start.
>
> Three things have happened, none of them dramatic:
>
> - `google-adk` is several minor versions ahead. Your lockfile still resolves, so that is
>   not it.
> - The pinned model string returns a 404. The provider retired it on a date that was
>   published months in advance, in a changelog you stopped reading on Day 96.
> - The free tier changed shape. Not removed — *changed*: a lower RPM, and a new
>   requirement that quietly makes your quota assumptions wrong.
>
> The system is not broken. It is **out of date**, which looks identical from the outside
> and is much more annoying, because every individual fix is small and there are eleven of
> them.
>
> 😬 **The naive fix:** fix the model string, re-lock, move on. Fifteen minutes, and the
> demo survives.
>
> 💥 **Why it fails.** The immediate fix is correct and the situation will recur in another
> six months, because nothing changed about *why* it happened. And there is a subtler cost
> that matters more than the demo: the repo's ledgers now assert things that are no longer
> true. `PACKAGES.md` records a model pinned as free on a date when it was; a reader in
> month seven has no way to know that statement expired. The document that made this project
> trustworthy is now quietly misleading, which is worse than if you had never written it.
>
> 💡 **The insight: a repository is a claim about the world, and claims need maintenance or
> expiry dates.** You get two honest options, and choosing one is today's real deliverable:
>
> **Option A — maintain it.** The fifteen-minute weekly check, done. Cheap, and the repo
> stays a live artifact you can show at any moment.
>
> **Option B — freeze it, and say so.** Add a dated banner to the README: *"Verified working
> against google-adk X.Y.Z and <model> on <date>. Not actively maintained — expect version
> drift after that date."* This is a completely respectable choice, it costs one line, and
> it converts "this person's project is broken" into "this person knows how software ages".
>
> **What is not acceptable is neither** — a repo that implies currency and quietly rots.
> That is the same failure as an accepted risk with no expiry (Day 92) and a control you
> have to remember (Day 92 again, and Day 94, and Day 95). Third occurrence of one pattern:
> **anything that depends on nobody forgetting will fail.** Design for the forgetting.
>
> Pick A or B **today**, write it into the README, and put a calendar reminder in whichever
> tool you actually use — not in this repo, because the repo is the thing that will be
> forgotten.

## 6 · 🎤 Interview corner

1. **"What did ninety-six days actually teach you?"** — Six things that recurred, which is
   how I know they're structural rather than incidental. Writing something down isn't making
   it findable — I hit that three separate times: an undocumented MCP tool that drifted for
   four weeks, an index that only a day-log knew how to build, and forty real decisions
   buried in narrative docs with one ADR to show for it. "Stateless" describes where state
   lives, not whether it exists — I proved that by scaling to two replicas and getting three
   specific bugs. Direction of connection is a security property: dial out rather than
   listen, which is why my MCP server is loopback-only in the pod and my chat intake uses
   Socket Mode instead of a tunnel. Proving *who* is not deciding *what* — a perfectly valid
   signature on an agent card told me nothing about whether obeying it was safe. Unknown
   input must always mean no. And a system that can't tell "I looked and found nothing" from
   "I couldn't look" will confidently invent an answer. None of those are about agents
   specifically, which is why I think they'll transfer.
2. **"How do you keep a project like this from going stale?"** — I picked one of two honest
   options and wrote it in the README, because the third option — implying currency and
   quietly rotting — is the one that actually damages you. Mine is a fifteen-minute weekly
   check: outdated packages with security notes, ADK releases since last time, the provider
   free-tier pages to confirm every pinned model is still free and still alive, and a clone
   from scratch to confirm it still starts. Then one dated line in the changelog even when
   nothing changed, because an undated "still fine" is worthless next quarter. It's
   deliberately small — I sized it for my worst week, not my best one, since a maintenance
   ritual competes with whatever I'm actually doing and loses. And I ran it once on the last
   day rather than scheduling the first run for later. The two steps that matter most are
   the model pins and the fresh clone: those are what make the repo *not work*, as opposed
   to merely out of date.
3. **"What's the weakest part of the project?"** — The durable stores are SQLite on a
   filesystem, which caps the whole system at one replica, and I know precisely what that
   costs because I measured it rather than assuming: doubled quota spend, approval verdicts
   not reliably visible across instances, and a race in the write-idempotency guard that can
   close a ticket twice. The fix is Postgres and a shared atomic counter, which needs a
   billing account this project deliberately doesn't have. Second-weakest is that the API
   server has no authentication — it's mitigated by binding to loopback, and the identity
   scheme I built covers the agent-to-agent door only, so it's in the security review as an
   accepted risk with an expiry rather than as something I overlooked. And there are whole
   areas I never touched: managed deployment, agent payments, real customer data. I'd rather
   name those than have someone find them.
