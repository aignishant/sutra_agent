## 1 · 🎬 Where we are — the story so far

Three days on Google's infrastructure taught three different lessons: a managed platform decides
how your process runs (97), a bare VM makes every one of those decisions yours (98), and a file
can hold those decisions so they survive you forgetting them (99).

Today Sutra leaves Google for the first time — and the interesting part is not that Azure has a
Cloud Run equivalent. It does; it's called Container Apps, it scales to zero, and the flag that
keeps it free is spelled `--min-replicas 0` instead of `--min-instances=0`. Ten minutes of
translation.

The interesting part is what stops working. `adk deploy cloud_run` doesn't exist here. Cloud
Build doesn't exist here. The thing that quietly built and stored a container image on Days 97
and 99 was a **Google-specific convenience**, and today you find out what it was actually doing —
by doing it yourself, and by discovering that the obvious Azure path for storing the result
costs money every single day whether you use it or not.

## 3 · 📚 Concepts

### DEPLOY-04a — The free grant, converted into hours you can actually reason about

Verified 2026-08-21 (`azure.microsoft.com/en-us/pricing/details/container-apps/`, via
`03_azure.md` §1): the Consumption plan's first **180,000 vCPU-seconds**, **360,000 GiB-seconds**,
and **2 million requests** per subscription per month are free.

`00_stay_free_safety.md` §2 asks you to write down the number you expect *before* creating
anything. So do the arithmetic rather than trusting the word "free":

| At this size | vCPU-s budget | GiB-s budget | Replica-hours/month you get |
| --- | --- | --- | --- |
| 0.25 vCPU / 0.5 GiB | 180,000 ÷ 0.25 = 720,000 s | 360,000 ÷ 0.5 = 720,000 s | **200 hours** |
| **0.5 vCPU / 1.0 GiB** (today's) | 180,000 ÷ 0.5 = 360,000 s | 360,000 ÷ 1.0 = 360,000 s | **100 hours** |
| 1.0 vCPU / 2.0 GiB | 180,000 s | 180,000 s | **50 hours** |

💡 **Read the last column again: a month is ~730 hours.** Even at the smallest size, this grant
does *not* cover one replica running continuously. That is the whole reason `--min-replicas 0`
is not a nice-to-have here — it is the difference between "free forever" and "free for the first
four days of every month." Compare Day 98's `e2-micro`, whose grant is sized to *exactly* one
instance running all month: **two platforms, two opposite economic shapes, and the flag that
keeps you inside each one is the opposite flag.**

### DEPLOY-04b — 📌 The finding: `az containerapp up --source .` is not free

`03_azure.md` §3 — this repo's own Azure reference — leads with:

```powershell
az containerapp up --name myagent --source . ...
```

It's the obvious analogue of `gcloud run deploy --source .`, and it works. But `--source .` has
to put the built image *somewhere*, and on Azure that somewhere is an **Azure Container
Registry**, which the command creates for you if one doesn't exist.

⚠️ **ACR has no free tier.** Verified 2026-08-21 at
`azure.microsoft.com/en-us/pricing/details/container-registry/`: the tiers are Basic, Standard,
and Premium; there is no free tier, only the $200/30-day signup credit. (The page renders its
actual prices client-side, so this day does **not** quote a dollar figure — the checkable fact is
"no free tier," which is enough to make the decision. Read the real number in the pricing
calculator for your region before you ever create one.)

💡 **The insight, and it generalises well beyond Azure:** a registry is *storage*, and storage
bills for **existing**, not for being used. Every compute grant in this track is metered on
consumption — requests, vCPU-seconds, instance-hours — so an idle service costs nothing. A
registry inverts that: it costs the same on the day you deploy and every day afterward, including
the eleven months you forget it exists. Registries are therefore the single most likely orphan on
this entire track, which is exactly why `00_stay_free_safety.md` §5 keeps a danger list.

**Today's choice instead: `ghcr.io` (GitHub Container Registry), public.** Free for public
images, and Microsoft's own docs confirm Container Apps pulls from "any public or private
container registry" — public ones need no credentials at all, so there is nothing to configure
and nothing to leak.

⚠️ **Not Docker Hub**, and for a reason Microsoft states on that same page: Docker Hub rate-limits
image pulls, and *"when the limit is reached, containers in your app fail to start."* A free tier
you can be rate-limited off in the middle of a demo is a worse free tier than one you can't.

📌 **A public image is a public image.** `Dockerfile.adk` copies only `sutra/` and installs
dependencies — no `.env`, no key, nothing secret (Step 2's `.dockerignore` enforces this). The
API key arrives at *runtime* as a Container Apps secret, exactly the "inject, never bake in" rule
from Day 97's DEPLOY-01c and Day 86 §3. If that rule were ever broken, a public registry turns a
mistake into a published mistake.

### DEPLOY-04c — Two Azure specifics that reject your config outright

Both are from `learn.microsoft.com/en-us/azure/container-apps/containers` (2026-08-21), and both
fail *at create time* with errors that don't obviously say what's wrong:

1. **`linux/amd64` only.** *"Linux-based (`linux/amd64`) container images are required."* On a
   Windows or Intel machine, `docker build` produces this by default. On Apple Silicon it does
   **not** — it produces `arm64`, and the app will fail to start with an exec-format error.
   Step 2 passes `--platform linux/amd64` explicitly so the command is correct everywhere rather
   than correct-by-accident on your machine.
2. **CPU and memory must be one of a fixed set of pairs**, not arbitrary numbers. The Consumption
   plan accepts `0.25/0.5Gi`, `0.5/1.0Gi`, `0.75/1.5Gi`, `1.0/2.0Gi`, and so on in 0.25-vCPU
   steps — always exactly 2 GiB per vCPU. Asking for `0.5` vCPU with `512Mi` is not "a bit small,"
   it's invalid.

### DEPLOY-04d — What Day 098 already settled, and still holds here

Day 98 established that ADK's **packaging** commands (`adk deploy ...`) require
`sutra/__init__.py` to contain `from . import agent`, while its **serving** commands
(`adk run` / `adk web` / `adk api_server`) accept an agent folder directly and don't.

Today's container runs `adk api_server`. So — same as Day 98 — **no `sutra/` code change is
needed.** That finding has now paid for itself twice, and it's the reason this day can ship a
container without touching a line of the agent.

⚠️ One thing this day *does* fix rather than leave to chance: Day 97 §5 flagged an open question
about whether `sutra/agent.py`'s absolute import (`from sutra.config import load_env`) resolves
inside a packaged container. `Dockerfile.adk` sets `ENV PYTHONPATH=/app` explicitly, which makes
the answer *yes, deterministically*, instead of depending on how a CLI entry point happens to
arrange `sys.path`. One line, no ambiguity, no code change.

## 4 · 🛠️ The build

> Shell: **PowerShell**, repo root. Docker Desktop must be running for Step 2.

**Step 1 — Azure sanity, and the number you expect.**

```powershell
winget install -e --id Microsoft.AzureCLI
az login
az account show --query "{name:name, id:id, state:state}" -o table
```

✅ *Verify:* the subscription you expect is listed and `state` is `Enabled`. Then write down, in
your own words, the number from DEPLOY-04a you're aiming to stay under: **at 0.5 vCPU / 1.0 GiB,
the free grant is ~100 replica-hours a month, so this app must scale to zero.**

**Step 2 — build the container image.**

`Dockerfile.adk` (repo root — new file, committed):

```dockerfile
# Dockerfile.adk — the ADK API-server image for Phase 16's non-GCP deployments.
# NOT the same artifact as Day 086's `Dockerfile` (which serves sutra.api:app and
# healthchecks /readyz — both Day 085 code that does not exist yet). See day_100.md's header.
FROM python:3.12-slim

WORKDIR /app

# Dependencies in their own layer, before the source, so editing agent.py
# doesn't reinstall every package (Day 086 §4 Step 3 makes the same point).
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY sutra/ ./sutra/

# DEPLOY-04d: makes `from sutra.config import load_env` resolve deterministically,
# rather than depending on how the adk entry point arranges sys.path.
ENV PYTHONPATH=/app

# Day 098's finding: api_server is a SERVING command — it takes the agent folder
# directly and needs no `from . import agent` in sutra/__init__.py.
EXPOSE 8000
CMD ["sh", "-c", "adk api_server --host 0.0.0.0 --port ${PORT:-8000} sutra"]
```

`.dockerignore` (repo root — new file, committed). ⚠️ **Write this before the first build**, not
after: it is what guarantees the public image in Step 3 contains no secret.

```gitignore
.env
.venv
.git
**/__pycache__
**/*.pyc
infra/
docs/
tests/
*.tfstate*
*.tfvars
sutra/.adk/
```

Generate the dependency list and build:

```powershell
uv export --no-hashes -o requirements.txt    # build artifact — gitignored, per Day 097's DEPLOY-01d
docker build --platform linux/amd64 -f Dockerfile.adk -t sutra-agent:v1 .
```

Test it locally *before* it touches Azure — the cheapest place to find a broken image:

```powershell
docker run --rm -p 8000:8000 --env-file .env sutra-agent:v1
# in a second window:
curl.exe http://localhost:8000/list-apps
```

✅ *Verify:* `/list-apps` returns `["sutra"]`. If it doesn't, fix it here — a container that fails
locally will fail identically on Azure, ten minutes later, behind a much worse error message.
Then confirm the image contains no secret:

```powershell
docker run --rm sutra-agent:v1 sh -c "ls -a /app ; printenv | Select-String GOOGLE_API_KEY"
```

✅ *Verify:* no `.env` in `/app`, and `GOOGLE_API_KEY` is **not** in the image's environment. It
arrives at runtime in Step 5, or not at all.

**Step 3 — push to `ghcr.io`, free and public.**

```powershell
$GH_USER = "your-github-username"
$env:CR_PAT | docker login ghcr.io -u $GH_USER --password-stdin   # a PAT with write:packages

docker tag sutra-agent:v1 "ghcr.io/$GH_USER/sutra-agent:v1"
docker push "ghcr.io/$GH_USER/sutra-agent:v1"
```

Then make the package **public** in GitHub (Profile → Packages → `sutra-agent` → Package settings
→ Change visibility → Public), and prove that worked:

```powershell
docker logout ghcr.io
docker pull "ghcr.io/$GH_USER/sutra-agent:v1"
```

✅ *Verify:* the pull succeeds **while logged out**. That is the actual test — if it needs
credentials, Container Apps will need a registry secret too, and Step 5's command won't work as
written.

⚠️ Tag `:v1`, never `:latest`. Microsoft's own guidance on that page: *"Avoid using static tags
like `latest`… Using static tags can lead to caching problems and can make your app difficult to
troubleshoot."* Day 5's model-pin lesson, in a different costume — a floating tag is fish of the
day.

**Step 4 — resource group and Container Apps environment.**

```powershell
az group create --name sutra-rg --location eastus
az containerapp env create --name sutra-env --resource-group sutra-rg --location eastus
```

| Command | What it does |
| --- | --- |
| `az group create` | Azure's unit of "delete everything at once" — the single most useful cleanup primitive Azure has, and what Step 9 relies on |
| `az containerapp env create` | the shared networking + logging boundary a Container App must live inside; one environment can hold many apps |

✅ *Verify:* `az containerapp env show --name sutra-env --resource-group sutra-rg --query "properties.provisioningState"` returns `"Succeeded"`. This takes a couple of minutes — it's the
slowest step of the day, and creating the app before it finishes fails confusingly.

**Step 5 — create the app, with the key injected at runtime.**

```powershell
az containerapp create `
  --name sutra-agent `
  --resource-group sutra-rg `
  --environment sutra-env `
  --image "ghcr.io/$GH_USER/sutra-agent:v1" `
  --target-port 8000 `
  --ingress external `
  --min-replicas 0 `
  --max-replicas 2 `
  --cpu 0.5 --memory 1.0Gi `
  --secrets "google-api-key=$env:GOOGLE_API_KEY" `
  --env-vars "GOOGLE_GENAI_USE_VERTEXAI=FALSE" "GOOGLE_API_KEY=secretref:google-api-key"
```

| Flag | What it does | Why it's set this way |
| --- | --- | --- |
| `--image ghcr.io/...` | pulls the public image from Step 3 | no `--registry-*` credentials needed, because it's public — DEPLOY-04b |
| `--target-port 8000` | the port **inside** the container that ingress forwards to | ⚠️ must match what the process actually binds. `Dockerfile.adk` binds `${PORT:-8000}`; set this to 8080 and every request returns a 502 with a perfectly healthy container behind it |
| `--ingress external` | gives the app a public HTTPS FQDN | `internal` instead, if only other apps in this environment should reach it |
| `--min-replicas 0` | **the line that keeps this free** — scales fully to zero when idle | DEPLOY-04a: the grant is ~100 replica-hours/month; a warm replica burns that in four days |
| `--max-replicas 2` | ceiling on concurrent replicas | bounds worst-case consumption from a spike or a retry loop |
| `--cpu 0.5 --memory 1.0Gi` | the replica size | one of the **exact** pairs the Consumption plan accepts (DEPLOY-04c) — `0.5` with `512Mi` is rejected, not rounded |
| `--secrets` + `secretref:` | stores the key in the app's secret store, then references it | the env var holds a *reference*; Step 7 verifies the literal never appears in the app's config |

✅ *Verify:* the command prints an FQDN like `sutra-agent.<random>.eastus.azurecontainerapps.io`.

**Step 6 — prove it actually serves Sutra.**

```powershell
$FQDN = az containerapp show --name sutra-agent --resource-group sutra-rg --query "properties.configuration.ingress.fqdn" -o tsv
$URL = "https://$FQDN"

curl.exe "$URL/list-apps"
curl.exe -X POST -H "Content-Type: application/json" "$URL/apps/sutra/users/u1/sessions/s1" -d "{}"
curl.exe -X POST -H "Content-Type: application/json" "$URL/run" `
  -d '{"appName":"sutra","userId":"u1","sessionId":"s1","newMessage":{"role":"user","parts":[{"text":"A customer says checkout is broken."}]}}'
```

✅ *Verify:* `/list-apps` returns `["sutra"]`; `/run` returns Sutra's real triage reply. ⚠️ The
first request after an idle period pays a **cold start** — the replica count is genuinely zero,
so something has to boot. If it times out, retry once before debugging anything.

⚠️ `--ingress external` with no auth means this FQDN is reachable by anyone who learns it, and
`adk api_server` has no authentication of its own — the same caveat Day 98 §4 Step 3 raises for
the VM's open port. Fine for a deliberate, short-lived test that you tear down in Step 9. Not
something to leave running.

**Step 7 — read the free-tier discipline back from the API.**

```powershell
az containerapp show --name sutra-agent --resource-group sutra-rg `
  --query "{min:properties.template.scale.minReplicas, max:properties.template.scale.maxReplicas, cpu:properties.template.containers[0].resources.cpu, mem:properties.template.containers[0].resources.memory}" -o table

az containerapp show --name sutra-agent --resource-group sutra-rg `
  --query "properties.template.containers[0].env" -o json
```

✅ *Verify:* `min` is `0`, `cpu` is `0.5`, `mem` is `1Gi`. In the env output, `GOOGLE_API_KEY`
appears with a **`secretRef`**, not a `value` — and `GOOGLE_GENAI_USE_VERTEXAI` is `FALSE`, so
ADK is on the free AI Studio path (Day 97's DEPLOY-01b, which is a *provider-independent* rule
and applies here exactly as it did on GCP).

And confirm no registry credentials were needed, which is the proof that Step 3's public-pull
actually worked:

```powershell
az containerapp show --name sutra-agent --resource-group sutra-rg --query "properties.configuration.registries"
```

✅ *Verify:* returns `null` or an empty list. Nothing to store, nothing to rotate, nothing to
leak — the whole benefit of a public image built from a `.dockerignore`d source tree.

## 5 · 💥 Failure lab — the agent that forgets between sentences

> 🎬 **The scene:** Step 6 worked, so you do the natural thing and hold a *conversation*. Two
> requests, same `sessionId`, a couple of minutes apart while you read the first answer:
>
> ```powershell
> curl.exe -X POST -H "Content-Type: application/json" "$URL/run" `
>   -d '{"appName":"sutra","userId":"u1","sessionId":"s1","newMessage":{"role":"user","parts":[{"text":"A customer says checkout is broken. What priority?"}]}}'
>
> # ... read the reply, think for two minutes, then:
> curl.exe -X POST -H "Content-Type: application/json" "$URL/run" `
>   -d '{"appName":"sutra","userId":"u1","sessionId":"s1","newMessage":{"role":"user","parts":[{"text":"And what was my reason for that priority again?"}]}}'
> ```
>
> 😬 **The naive expectation:** same session ID, so same conversation. Sutra should remember.
>
> 💥 **What actually happens:** either a 404 on the session, or Sutra answering as though the
> first message never happened. Not a bug in Sutra, and not a bug in Azure — a direct,
> predictable consequence of two settings that are each individually correct:
>
> | Setting | Why it's right | What it costs here |
> | --- | --- | --- |
> | `--min-replicas 0` | the only reason this deployment is free (DEPLOY-04a) | between requests there is **no process** — nothing is holding anything in memory |
> | `adk api_server` with no `--session_service_uri` | the default is the **in-memory** session service | session state lives in the replica's RAM, and the replica just ceased to exist |
>
> 💡 **The insight: scale-to-zero and in-memory state are mutually exclusive, and nobody warns
> you, because each half is the documented default.** Day 98 sidestepped this without making a
> fuss about it — a VM has a real disk, so
> `--session_service_uri="sqlite:///.../sessions.db"` just worked. There is no equivalent here:
> a Container Apps replica's filesystem is ephemeral, so a SQLite file written during one
> request isn't reliably there for the next, *and* two replicas (you allowed `--max-replicas 2`)
> wouldn't share it anyway.
>
> ⚠️ **The tempting fix is a trap.** `--min-replicas 1` makes the symptom disappear instantly —
> and burns the entire monthly grant in about four days (DEPLOY-04a's table). Trading a
> correctness problem for a billing problem is not a fix; it's a different, later, more
> expensive bug.

**What to actually do, in order of honesty:**

1. **Name it, don't hide it.** For a stateless demo this is *fine* — the client can send the
   whole conversation each turn. Say so out loud rather than pretending the deployment is
   something it isn't.
2. **Move the state outside the compute.** This is the real fix, and it's
   [Day 108](day_108.md)'s entire job: a free managed Postgres (Neon) behind
   `--session_service_uri`, which `adk.dev/api-reference/cli/` confirms accepts SQLAlchemy
   database URIs and not just SQLite paths. `07_free_databases_and_extras.md` §1 exists as a
   file precisely because of the failure you just reproduced.
3. **Do not reach for `--min-replicas 1`** unless someone has agreed to pay for it, in which
   case it stops being this project's problem and starts being a budget line.

✅ *Verify (today's actual lesson):* you can state, in one sentence and without looking it up,
*why* the second request failed — and the sentence mentions both settings, not just one.

## 6 · 🎤 Interview corner

1. **"You've deployed to Cloud Run and Container Apps. How do they compare?"** — Structurally
   near-identical: a container, HTTP ingress, request-driven autoscaling, and a free grant that
   only makes sense if you scale to zero. The flags translate almost one-to-one
   (`--min-instances=0` → `--min-replicas 0`). The differences that actually cost you time are
   around the edges: Azure meters the grant in vCPU-seconds and GiB-seconds rather than requests,
   so I converted it to replica-hours before deploying anything; Container Apps requires an
   environment resource first; and it constrains CPU/memory to fixed pairs rather than accepting
   arbitrary values.
2. **"Where do you store container images, and what does it cost?"** — On GCP the build pushed
   to Artifact Registry automatically. On Azure the equivalent convenience,
   `az containerapp up --source .`, silently provisions an Azure Container Registry, and ACR has
   no free tier — so I used a public `ghcr.io` package instead, which is free and needs no pull
   credentials. The general lesson is that registries bill for *existing* while compute bills for
   *running*, which makes an unused registry the likeliest thing to still be costing you money
   six months after a project ends.
3. **"What breaks when a service scales to zero?"** — Anything held in memory. I reproduced it
   deliberately: two requests with the same session ID, minutes apart, and the agent had no idea
   they were related, because between them there was no process. The correct fix is to move
   session state out of the compute into an external store; the tempting fix — keeping one
   replica warm — makes the symptom vanish and consumes the entire free grant in four days.
4. **"How do you keep secrets out of a public container image?"** — Three layers, and I verified
   each rather than assuming: a `.dockerignore` written *before* the first build so `.env` can't
   be copied in; the key injected at runtime as a platform secret referenced by
   `secretref:`, never as a literal env value; and then an actual check — I ran the image and
   grepped its environment, and read the deployed app's config back to confirm the API returns a
   `secretRef` rather than the key.
