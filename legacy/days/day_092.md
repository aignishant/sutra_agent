## 1 · 🎬 Where we are — the story so far

Ninety-one days have produced a system and a habit. The habit is the more valuable one:
every time something was too big for the day it was found on, it got written down instead
of forgotten — a line in `THREAT_MODEL.md`, a "Day 92 will ask" in a build step, a
`⚠️` in a runbook. There are a lot of those lines now. Today they all come due at once,
and that is the design: a security review with a list of promises is a different exercise
from a security review that starts with "hmm, let's look around".

Nothing about today is speculative. You are not imagining an attacker; you are checking
specific claims you already made, in a repo that becomes readable by anyone tomorrow
morning. The most likely outcome is two or three genuinely uncomfortable findings, and the
correct response to each is to fix it or to write down precisely why you did not.

⚠️ **The one rule for today: a finding you decide not to fix must be written down with a
reason and an owner.** A silently-accepted risk is not a decision, it is a memory that
will fade — and after tomorrow it fades in public.

## 3 · 📚 Concepts

### SEC-16 — a review is a list of claims, not a feeling

**The story.** Two people check a house before a holiday. The first walks around and feels
that everything is fine. The second has a list: back door, windows upstairs, gas, the tap
in the utility room, the spare key under the pot. Only the second one can tell you
afterwards *what they checked*, and only the second one notices the window nobody has
opened in a year.

A security review is the list. The output is not "it's secure" — nobody can say that. The
output is: **here is what I checked, here is how, here is what I found, here is what I
chose not to fix and why.** That document is what makes the review repeatable, and
repeatable is what makes it worth anything in six months.

💡 **Mental model: you are not looking for cleverness, you are closing the gap between what
the docs claim and what the code does.** Almost every real finding in a project like this
lives in that gap — a control that was described accurately on the day it was built, and
quietly outgrown three weeks later.

### The three questions each pass must answer

Every pass below produces the same three lines, and `docs/SECURITY_REVIEW.md` is
structured as a table of them:

| | |
| --- | --- |
| **Claim** | what the repo currently says is true (quote the doc or the code) |
| **Evidence** | the command you ran and what it printed — **not** "I checked" |
| **Verdict** | ✅ holds · 🔧 fixed today · ⚠️ accepted, with reason + owner + expiry |

⚠️ A verdict of "⚠️ accepted" is legitimate and this project will have several of them —
no budget means no Postgres, no secret manager, no managed identity. What is not legitimate
is an accepted risk with no expiry: **"until we have a billing account" is an expiry;
"for now" is not.**

### What "public" actually changes

Tomorrow's publication changes three things, and it is worth being precise because people
usually name only the first:

1. **Every historical commit becomes readable.** Not the current tree — the *history*. A
   key deleted in commit 40 is still in commit 39, forever, and `git log -p` is one command.
2. **The architecture becomes an attacker's map.** Your `THREAT_MODEL.md` is an excellent
   document and it is also a summary of where the valuables are. This is fine — security
   through obscurity was never doing the work — but it raises the bar on the controls it
   describes actually existing.
3. **Your synthetic data becomes a claim you are making publicly.** `test_repo_is_synthetic`
   (Day 69) has been a lint. Tomorrow it is a promise to strangers about people's data.

📌 The reverse is also true and worth saying in an interview: publishing is a *forcing
function*. Most of the controls in this repo exist because a specific day knew that Day 92
would ask. Deadlines with an audience are a legitimate engineering tool.

## 5 · 💥 Failure lab — the control that was true when you wrote it

> 🎬 **The scene:** Pass 5 is going well. You print the MCP tool list expecting the three
> read-only tools from Day 32 — `search_archive`, `get_ticket`, `get_release_note` — and
> there are five. Two arrived later: one added during Phase 7's memory work, one you do not
> immediately recognise. Both are read-only, so nothing is on fire.
>
> Then you check the second one properly. It takes a file path.
>
> It was added on a day when the MCP server ran on your laptop as you, in a repo full of
> synthetic tickets, and it was completely reasonable — a debugging convenience for reading
> a fixture. It is now in a container, in a pod, mounted read-only over `data/`, reachable
> by an agent that reads a stranger's A2A card and a public Slack channel.
>
> 😬 **The naive fix:** delete the tool. Which is correct, and is also the least valuable
> thing you will do today.
>
> 💥 **Why deleting is not enough.** The tool is not the finding. The finding is that
> **`docs/DATA_BOUNDARY.md` described three tools and reality had five, and nothing
> noticed for four weeks.** Every control in this repo has the same failure mode: it was
> accurate on the day it was written, and it decays silently as the system grows around it.
> Consider how many of today's passes are checking exactly this shape — the threat model
> written before A2A existed, the data boundary written before there were peers to leak to,
> the CORS setting decided when there was one listener. Delete the tool and the *mechanism*
> that let it drift is untouched, so the next one arrives on schedule.
>
> Notice also what nearly saved you and didn't: you *wrote the doc*. Documentation is not a
> control. A control is something that fails a build.
>
> 💡 **The insight: a control you have to remember to check is not a control — it is a
> reminder, and reminders decay.** The fix for drift is never vigilance; it is to make the
> drift **fail something automatically**. Three concrete conversions, all cheap, all
> today:
>
> 1. **Inventory tests.** `test_mcp_tools_match_docs` asserts the exposed tool names equal
>    an explicit list in the test file. Adding a tool now breaks the build, and the
>    author's fix is to update the doc — which is exactly the review you wanted, at the
>    moment the change is fresh. Do the same for `sutra/graph.py`'s agent list versus
>    `ROLE_OF` (Day 70 already has this shape — extend it) and for the listener table in
>    Pass 6.
> 2. **A dated freshness check, not a promise.** `docs/SECURITY_REVIEW.md` ends with the
>    repeat instructions and a next-review date. Day 96's weekly habit picks it up.
> 3. **The rule, written where it will be read:** *any new tool, listener, or egress path
>    ships with the doc line and the inventory test in the same commit.* Put it in
>    `CLAUDE.md`'s project section, because that is the file that governs future days.
>
> Then find out how bad the drift was overall: for each of the eight passes, count how many
> of that pass's claims were *stale* rather than *wrong*. That count is the honest health
> metric for the project, and it belongs at the top of the review document — it is far more
> informative than "no critical findings", and considerably more likely to be true.

## 6 · 🎤 Interview corner

1. **"Walk me through how you'd security-review your own project."** — As a list of claims,
   not a vibe. I ran eight passes and each one produced claim / evidence / verdict, where
   evidence is a command and its output rather than "I checked". Secrets in three places —
   working tree, **git history**, and the built image, because a key deleted in commit 40 is
   still in commit 39 and layers are immutable. Then the threat model and the data boundary
   re-read against what the system actually does now, dependencies, the MCP tool surface,
   every network listener and its CORS posture, every fail-closed permission table, and
   finally logs and traces — which people skip because they feel internal, and which is
   where automatic tracing quietly captures whatever passes through it. The output artifact
   matters as much as the findings: what was checked, what was fixed, what was accepted
   with a reason, an owner and an **expiry**, and the commands to repeat it. "For now" is
   not an expiry; "until we have a billing account" is.
2. **"What was your most uncomfortable finding?"** — My documented MCP surface said three
   read-only tools and the server exposed five. One had been added weeks earlier as a
   debugging convenience, and it took a file path. When it was written it ran on my laptop,
   as me, against synthetic fixtures — entirely reasonable. By the time I found it, the same
   process was in a container reachable from an agent that reads third-party A2A cards and
   a public chat channel. Deleting the tool took a minute; the actual finding was that
   nothing noticed for four weeks. Documentation isn't a control — a control is something
   that fails a build. So I added inventory tests that assert the exposed tools equal an
   explicit list, and the same shape for the agent-to-role mapping and the listener table.
   Now adding a tool breaks CI and the author updates the doc while the change is fresh.
3. **"You're publishing this repo. What did that change?"** — Three things, and people
   usually name only the first. Every historical commit becomes readable, so the scan that
   matters is `git log -p --all`, and if it hits, the fix is rewrite *and* rotate — rotation
   first in importance, because once a secret has been committed you have to assume it's
   compromised; rewriting without rotating is theatre. Second, my threat model becomes a map
   of where the valuables are, which is fine — obscurity was never doing the work — but it
   raises the bar on those controls actually existing, which is what the inventory tests are
   for. Third, my synthetic-data lint stops being a lint and becomes a public claim about
   people's data. I'd add that publication was a genuinely useful forcing function: a good
   share of the controls in that repo exist because earlier days knew this review was
   coming and wrote "Day 92 will ask" instead of quietly moving on.
