## 1 · 🎬 Where we are — the story so far

Three clouds, three Terraform configs, and one question that keeps getting a different answer.

Day 99 wrote a Cloud Run service in HCL, grepped the state file for the API key, and found
nothing — because Cloud Run's API takes a *pointer* to Secret Manager. That felt like good
practice. Day 102 wrote the same deployment for Azure, ran the identical grep, and found the key
sitting in plaintext — because `azurerm_container_app` takes the secret's *value*. Same
engineer, same discipline, opposite outcome, decided entirely by a resource schema.

Today is the tiebreaker, and it does not go the way the pattern suggests. AWS has a genuinely
free secret store — SSM Parameter Store standard parameters — so you'd expect a Cloud-Run-shaped
happy ending. You do not get one, for a reason that is about **how Terraform works** rather than
about AWS, and it changes what "handle secrets properly in Terraform" actually means.

And then EKS: the one place in this track where all three major clouds genuinely diverge, and
the only Kubernetes offering where an *empty* cluster costs $73 a month.

## 3 · 📚 Concepts

### DEPLOY-09a — 📌 The third answer: why AWS's free secret store doesn't save you either

AWS **does** have the free store you'd want: SSM Parameter Store *standard* parameters cost
nothing (`04_aws.md` §1). So the obvious move is to put the key there and have Terraform read it:

```hcl
# The tempting version. It does NOT solve the problem.
data "aws_ssm_parameter" "google_api_key" {
  name            = "/sutra/google-api-key"
  with_decryption = true
}

resource "aws_lambda_function" "sutra" {
  environment {
    variables = { GOOGLE_API_KEY = data.aws_ssm_parameter.google_api_key.value }
  }
}
```

⚠️ **This is worse than it looks, in two separate ways:**

1. **`aws_lambda_function`'s `environment.variables` takes literal values**, exactly like
   `azurerm_container_app`'s `secret` block (Day 102). Whatever is on the right-hand side ends up
   as a resource attribute — so it ends up in state.
2. **A `data` source's result is *also* stored in state.** Terraform caches what it reads so it
   can diff on the next run. So the SSM lookup doesn't launder the value; it puts it in state
   **twice** — once as the data source's `value`, once as the function's env var.

💡 **The insight, and it is the real conclusion of the three-day thread: Terraform can only keep
a secret out of state when the *resource schema* accepts a reference instead of a value.** No
amount of care on your side changes that — it isn't a discipline problem, it's an API-shape
problem. Cloud Run's `secret_key_ref` accepts a name. Azure's and AWS's accept values. Two out of
three clouds put your key in `terraform.tfstate`, and the honest response is to treat state as a
credential everywhere rather than to feel safe on the one cloud where you got lucky.

| Cloud | Resource | Schema takes | Key in `tfstate`? |
| --- | --- | --- | --- |
| GCP (Day 099) | `google_cloud_run_v2_service` | a **reference** (`secret_key_ref`) | ❌ no |
| Azure (Day 102) | `azurerm_container_app` | a **value** (`secret { value }`) | ✅ yes |
| **AWS (today)** | `aws_lambda_function` | a **value** (`environment.variables`) | ✅ **yes** — and twice if you route it through a data source |

**So what does today actually do?** Day 102's DEPLOY-06c option 2, now clearly the right default
rather than a fallback: **keep the secret out of Terraform entirely.** Set it out-of-band, and
tell Terraform not to manage that attribute:

```hcl
lifecycle {
  ignore_changes = [environment]
}
```

⚠️ **State the cost honestly:** `main.tf` no longer fully describes the deployment. Someone
reading it cannot tell what environment the function runs with. That is a real loss of the
property Day 99 §3 sold Terraform on — and it is still the better trade, because the alternative
is a plaintext key in a file that gets copied, backed up, and zipped.

### DEPLOY-09b — What `terraform destroy` does *not* remove

`05_terraform.md` §7 calls `destroy` *"the single highest-leverage habit in this entire folder,"*
because it removes the orphan neighbours manual cleanup misses. True — with a boundary that
matters enormously today:

💡 **`terraform destroy` removes exactly what `terraform apply` created, and nothing else.** It
reads state. Anything not in state is invisible to it, no matter how obviously related.

Today that's two things, both of which cost money or clutter:

| Not in state | Created by | Still there after `destroy` |
| --- | --- | --- |
| The **ECR repository** and both images | Day 103 §4 Step 3, by hand | ✅ — and it's the one billable object of the AWS days |
| The **CloudWatch log group** `/aws/lambda/sutra-agent` | AWS, automatically, on first invocation | ✅ — nothing ever "created" it in any config |

⚠️ **This is precisely the false confidence Day 104 §6 warned about**, arriving from a different
direction: there, "I stopped it" wasn't "it's free"; here, "destroy succeeded" isn't "nothing is
left." §5 reproduces it.

### DEPLOY-09c — EKS: where the three clouds actually diverge

| Cloud | Control plane | Nodes | Verdict for a zero-budget project |
| --- | --- | --- | --- |
| GCP GKE (Day 099) | ✅ free for 1 cluster/month | ❌ Autopilot bills per pod's *request* | parked |
| Azure AKS (Day 102) | ✅ *"cluster management is free"* | ❌ ordinary billed VMs | parked |
| **AWS EKS (today)** | ❌ **$0.10/hour, no free tier** | ❌ ordinary billed EC2 (+ Day 104's four meters each) | **parked hardest** |

Verified 2026-08-21, `aws.amazon.com/eks/pricing/`: **$0.10 per cluster per hour** for standard
Kubernetes version support, and *"there is no free tier mentioned for Amazon EKS cluster
pricing."* That's **~$73/month for a cluster with zero pods on it.**

💡 **Why this is worth knowing as a fact rather than a vibe:** "Kubernetes is expensive" is a
cliché. "GKE and AKS give you the control plane and charge for nodes; EKS charges $0.10/hour for
the control plane *before* you add a single node, which itself carries EC2's four meters" is an
answer that demonstrates you've actually priced the three. `04_aws.md` §3 already reaches this
conclusion and recommends writing a parked walkthrough instead — §6 is that walkthrough.

**Step 2 — put the secret where Terraform won't read it.**

Per DEPLOY-09a, the key goes to SSM **for the human's benefit**, and Terraform never touches it:

```powershell
aws ssm put-parameter --name "/sutra/google-api-key" --type SecureString `
  --value "$env:GOOGLE_API_KEY" --region $REGION --overwrite
```

✅ *Verify:* `aws ssm get-parameter --name "/sutra/google-api-key" --region $REGION --query "Parameter.Type"` returns `"SecureString"`. ⚠️ Standard parameters are free; **`SecureString` uses
KMS**, and the AWS-managed key for SSM is free to use — but confirm on your own bill rather than
taking that from this doc. If you'd rather not risk it, use `--type String` and accept that the
value is visible to anyone with SSM read access in your account.

**Step 3 — write the AWS config.**

```powershell
New-Item -ItemType Directory -Force infra/aws | Out-Null
```

`infra/aws/main.tf`:

```hcl
terraform {
  required_version = ">= 1.9"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = var.region
}

resource "aws_iam_role" "lambda_exec" {
  name = "sutra-lambda-role-tf"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "lambda.amazonaws.com" }
    }]
  })
}

resource "aws_iam_role_policy_attachment" "basic_exec" {
  role       = aws_iam_role.lambda_exec.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole"
}

resource "aws_lambda_function" "sutra" {
  function_name = "sutra-agent-tf"
  package_type  = "Image"
  image_uri     = var.image_uri
  role          = aws_iam_role.lambda_exec.arn
  memory_size   = 512    # DEPLOY-07a: this number IS the GB-second burn rate
  timeout       = 60     # NOT the 3-second default — an agent request is 3-10s

  environment {
    variables = {
      GOOGLE_GENAI_USE_VERTEXAI = "FALSE"
      # DEPLOY-09a: the API key is deliberately ABSENT. Step 5 sets it out-of-band.
    }
  }

  lifecycle {
    # Terraform must not manage `environment`, or it will revert Step 5's key on
    # the next apply (Day 099 §5's drift mechanism, working exactly as designed).
    ignore_changes = [environment]
  }
}

resource "aws_lambda_function_url" "sutra" {
  function_name      = aws_lambda_function.sutra.function_name
  authorization_type = "NONE"
}
```

| Block | What it does | Why it's written this way |
| --- | --- | --- |
| `aws_iam_role` + `assume_role_policy` | the trust policy letting the Lambda service assume this role | required before Lambda can run as anything — Day 103 §4 Step 2 did this by hand |
| `aws_iam_role_policy_attachment` | attaches AWS's managed basic-execution policy (CloudWatch Logs write) | least-effort least-privilege; hand-writing an equivalent adds risk, not security |
| `image_uri` | the `:lwa` image from Day 103 | ⚠️ Terraform does **not** build or push images; the registry stays outside its world, which is exactly §5's blind spot |
| `timeout = 60` | agent requests take seconds | Lambda's default is 3 — the single most common first-deploy failure |
| `ignore_changes = [environment]` | **the DEPLOY-09a decision, in one line** | without it, `apply` would wipe the key Step 5 sets, on every run, forever |
| `aws_lambda_function_url` | a public HTTPS endpoint, no API Gateway | ⚠️ `authorization_type = "NONE"` is genuinely public. Torn down in §7 |

`infra/aws/variables.tf`:

```hcl
variable "region" {
  type    = string

}

variable "image_uri" {
  type = string
```

## 5 · 💥 Failure lab — `destroy` succeeded, and you are still paying

> 🎬 **The scene:** you're done. You run the command this whole track has been calling the
> highest-leverage cleanup habit there is:
>
> ```powershell
> terraform -chdir=infra/aws destroy    # type: yes
> ```
>
> ```
> Destroy complete! Resources: 4 destroyed.
> ```
>
> Four created, four destroyed. The function is gone, the URL is gone, the role is gone. Every
> signal says the account is clean.
>
> 😬 **The naive conclusion:** `destroy` is the teardown. Nothing is left.
>
> 💥 **Check it:**
>
> ```powershell
> aws ecr describe-repositories --region $REGION --query "repositories[].repositoryName"
> aws logs describe-log-groups --region $REGION `
>   --query "logGroups[?contains(logGroupName,'sutra')].logGroupName"
> ```
>
> **Both still exist.** The ECR repository — with two images in it, the one billable object of
> the AWS days (Day 103's DEPLOY-07d) — and a CloudWatch log group holding every log line from
> §4 Step 5.
>
> 💡 **Why, mechanically: `destroy` reads *state*, and state only contains what `apply` created.**
> The repository was created by hand on Day 103. The log group was created by *AWS itself*, on
> first invocation, on your behalf — nothing anywhere ever declared it. Terraform is not being
> careless; it has no idea either object exists. **The blast radius of `destroy` is exactly the
> blast radius of `apply`, and your account is larger than your config.**
>
> ⚠️ **This is the same false-confidence failure as Day 104 §6, from the opposite direction.**
> There: "I stopped the instance" ≠ "it stopped costing." Here: "destroy succeeded" ≠ "nothing
> is left." Both are cases of a *verb you trusted* covering less than you assumed — and both are
> why [Day 110](day_110.md)'s audit queries the account directly instead of reasoning from what
> you remember doing.

**The fix — teardown is `destroy` **plus** an explicit sweep, always:**

```powershell
# What Terraform owned:
terraform -chdir=infra/aws destroy

# What it never knew about (Day 103's order still applies: function first, then repo —
# and `destroy` already removed the function, so the repo is safe to delete now):
aws ecr delete-repository --repository-name sutra-agent --force --region $REGION
aws logs delete-log-group --log-group-name /aws/lambda/sutra-agent-tf --region $REGION
aws logs delete-log-group --log-group-name /aws/lambda/sutra-agent --region $REGION   # Day 103's
aws ssm delete-parameter --name "/sutra/google-api-key" --region $REGION

# Day 104 §6's sweep, because EC2 orphans don't care which day created them:
aws ec2 describe-volumes --filters Name=status,Values=available --query "Volumes[].VolumeId"
aws ec2 describe-addresses --query "Addresses[].PublicIp"
```

✅ *Verify:* every one of those queries returns empty. ⚠️ And run the two `describe` calls **in
every region you have used**, per Day 104 §6 — the console shows one region at a time and a
forgotten `eu-west-1` bills exactly like `us-east-1`.

⚠️ Finally, the state file: it holds no API key today (Step 5 verified that), but it does hold
your account ID, ARNs, and the full image URI. `05_terraform.md` §5's rule stands — it's
gitignored, and delete it deliberately when you're finished rather than leaving it in a folder
you might one day zip and share.

## 6 · 🅿️ EKS — priced, and never run

> **Never executed, and must not be, until the trigger condition below is met.** Same discipline
> as [Day 087](day_087.md), [Day 099](day_099.md) §6, and [Day 102](day_102.md) §6.

**Why it's parked, in one number:** $0.10/cluster/hour with no free tier — **~$73/month before a
single pod exists** — and every node on top of that carries Day 104's four meters (instance
hours, EBS, public IPv4, egress) individually.

**What the commands would be** (reference only):

```powershell
# NOT RUN. The control plane bills from creation, whether or not any workload exists.
eksctl create cluster --name sutra-eks --region us-east-1 --nodes 1 --node-type t3.small
aws eks update-kubeconfig --name sutra-eks --region us-east-1
kubectl get nodes
eksctl delete cluster --name sutra-eks --region us-east-1
```

⚠️ **The orphan risk here is the worst in the track.** An EKS cluster creates a VPC, subnets,
NAT gateways (⚠️ **NAT gateways bill hourly *and* per GB**, and are a classic six-month
surprise), security groups, and node groups. `eksctl delete cluster` normally removes its own
CloudFormation stacks — but a half-failed delete leaves the expensive parts running with no
cluster left in the console to remind you. Day 102 §6 flagged the same shape for AKS's hidden
`MC_*` group; on AWS it's spread across CloudFormation stacks instead.

**Re-verification commands, if this is ever revisited:**

```powershell
Start-Process "https://aws.amazon.com/eks/pricing/"
aws eks list-clusters --region us-east-1
aws ec2 describe-nat-gateways --query "NatGateways[].{id:NatGatewayId, state:State}" -o table
aws cloudformation describe-stacks --query "Stacks[?contains(StackName,'eksctl')].StackName"
```

**Trigger condition:** EKS stops being parked when *either* (a) this project has a funded budget
that explicitly covers ~$73/month of control plane plus nodes **and** a stated requirement that
`kind` cannot serve, **or** (b) AWS introduces a free or waived control-plane tier comparable to
GKE's and AKS's. Neither was true on 2026-08-21. Until then, [Day 088](day_088.md)'s `kind` is
the Kubernetes story — same API, same manifests, genuinely $0.

## 7 · 🎤 Interview corner

1. **"Where do secrets live in your Terraform?"** — It depends on the resource schema, and that
   surprised me enough that I checked all three clouds the same way: write the config, then grep
   the state file. Cloud Run takes a Secret Manager *reference*, so nothing leaked. Azure's
   Container App and AWS's Lambda both take the *value*, so both leak — and on AWS, routing it
   through an SSM data source makes it worse, because data-source results are cached in state
   too. So on two of three clouds I keep the secret out of Terraform entirely and set it
   out-of-band with `ignore_changes`, accepting that the config no longer fully describes the
   deployment. That's a real trade, not a best practice I copied.
2. **"Is `terraform destroy` a complete teardown?"** — Only of what `apply` created. It reads
   state, so anything created by hand or by the cloud itself is invisible to it. On my Lambda
   deployment, `destroy` reported four resources destroyed and left behind the ECR repository —
   the one thing actually accruing storage charges — plus the CloudWatch log group AWS created
   automatically on first invocation. So my teardown is `destroy` **plus** an explicit sweep of
   the account, in every region, because the blast radius of destroy is exactly the blast radius
   of apply.
3. **"Compare managed Kubernetes across the three clouds."** — GKE and AKS both give you the
   control plane free and bill the nodes. EKS charges $0.10 per cluster-hour for the control
   plane itself, with no free tier — about $73 a month for an empty cluster, before nodes, each
   of which carries EC2's separate instance/EBS/IPv4/egress meters. And EKS's teardown risk is
   the highest: it provisions NAT gateways, which bill hourly and per GB and survive a
   half-failed delete. For a zero-budget project all three are out, so I priced them, wrote them
   up run-ready, and ran `kind` locally instead.
4. **"When is `ignore_changes` the right call rather than a smell?"** — When something outside
   Terraform is the legitimate owner of an attribute. Here the function's environment holds an
   API key that must never enter state, so it's set out-of-band and Terraform is told not to
   manage it. Without that line, every `apply` would helpfully delete the key — Terraform's drift
   reconciliation working exactly as designed, against me. It's a smell when it's used to silence
   drift nobody wants to explain; it's correct when you can name the other owner.
