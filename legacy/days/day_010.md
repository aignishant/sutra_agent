## 3 · 📚 Concepts

### ADK-10 — Automatic wrapping: the same restaurant, self-printing forms

**Back to the restaurant.** On Day 4 you were both chef and stationery department: for
every dish you cooked (the Python function) you also designed its printed order form (the
JSON Schema), by hand, and heaven help you if the form said `ticket_id` while the kitchen
expected `ticketId`.

ADK's deal is simple: **write the recipe card properly, and the forms print themselves.**
The framework reads your function — its name, its docstring, its parameters, their type
hints, their defaults — and generates the same `FunctionDeclaration` you wrote manually
six days ago.

| Day 4 (by hand) | Day 10 (ADK) | What generates it |
| --- | --- | --- |
| `name="lookup_ticket"` | the function's own name | Python introspection |
| `description="Return the raw text…"` | the **docstring's first lines** | your writing |
| `"ticket_id": {"type": "string"}` | `ticket_id: str` | the **type hint** |
| `"required": ["ticket_id"]` | no default value on the parameter | signature rules |
| your `TOOLS` dispatch dict + `**fc.args` | gone — ADK dispatches for you | the framework |

```python
def lookup_ticket(ticket_id: str) -> dict:
    """Return the text of a support ticket by its id."""
    ...

agent = Agent(..., tools=[lookup_ticket])   # <- that's the whole registration
```

💡 **Mental model: ADK didn't remove the schema — it moved the schema into your docstring
and type hints.** The contract from Day 4 still exists, word for word; you just stopped
writing it twice. Which has a sharp consequence: **your docstring is now production
config, not a comment.** A lazy docstring is a broken order form.

Two mechanical rules worth pinning to the wall (both verified on the function-tools page):

- **Type hint + no default = required.** A default value makes the parameter optional.
  Day 4's `"required": ["ticket_id"]` line is now spelled `ticket_id: str` with no `=`.
- **`*args` / `**kwargs` are ignored** — invisible to the model. No secret escape hatches
  onto the menu.

### ADK-11 — The docstring contract & what a tool should return

**Who is the docstring for?** Three readers, in order of importance:

1. **The model** — it decides *when* to call your tool and *what* to pass, based almost
   entirely on this text. This is prompt engineering wearing a docstring costume.
2. **The schema generator** — the description travels into the declaration.
3. The human — last, for once.

So a tool docstring answers, in plain language: what does this do, when should you use it,
what does each argument mean (with an example value), and what comes back — including
what failure looks like.

**Return values: speak status, not prose.** The docs' best practice is a dict with a
`"status"` key. Compare:

| Day 3/4 style | ADK best practice |
| --- | --- |
| `"No ticket with id '9999'."` (a string the model must interpret) | `{"status": "not_found", "message": "No ticket with id '9999'."}` (a structure it can *branch* on) |

Return a bare string and ADK wraps it as `{"result": "..."}` — legal, but you gave up the
chance to make success and failure *structurally* different. Sutra's tools graduate to
status dicts today; on Day 12 the same schema thinking spreads to the agent's *answers*.

**🅿️ Preview — `LongRunningFunctionTool`.** Some tools cannot answer now: "ask a human for
approval" might take an hour. Wrapping such a function in `LongRunningFunctionTool` lets
the run *pause* after an initial `{"status": "pending", ...}` and *resume* when the real
answer arrives. Park it — this is the exact mechanism under Day 62–64's approval gates,
and it deserves its own days. Today you only need to know the escape hatch exists.

### 📌 One quiet ADK-vs-Day-4 difference that will matter

Day 4's `TOOLS` dict was your **policy chokepoint** — one place to log, allow, or refuse
every call (Principle 13). ADK dispatches internally, so where did the chokepoint go? It
moved into **callbacks and plugins** — `before_tool_callback` and friends — which is
exactly Days 13–14. The authority didn't vanish; it got a nicer office. Hold that thought.

## 4 · 🛠️ Build

**Step 1 — `sutra/adk_tools.py` (zero quota).**

We *rewrite* the two tools rather than importing Day 3's versions: the logic is identical,
but the docstrings are now written for a model to read, and returns are status dicts. The
synthetic data stays imported from `sutra/loop.py` — data has one home.

```python
"""Day 10 — Sutra's tools, ADK edition.

Same two capabilities as Days 3-4 (ticket lookup, KB search), but declared
the ADK way: plain functions whose docstrings and type hints ARE the
schema. No FunctionDeclaration, no dispatch table - ADK generates both.

Importable with no side effects. Run demos from the repo root:

    python -m sutra.adk_tools triage    # the Day 3 headline, framework edition
    python -m sutra.adk_tools unknown   # honesty check on a missing ticket
"""
from __future__ import annotations

import sys

from google.adk.agents import Agent                  # Day 5
from google.adk.runners import InMemoryRunner        # Day 9's harness
from google.genai import types                       # Content/Part

from sutra.config import load_env                    # .env (Day 1)
from sutra.loop import TICKETS, KB, TRIAGE_QUESTION  # synthetic data, one home (Day 3)


def lookup_ticket(ticket_id: str) -> dict:
    """Fetch the full text of one support ticket by its exact id.

    Use this FIRST whenever the user mentions a ticket number, before
    answering anything about that ticket.

    Args:
        ticket_id: the ticket's id digits as a string, e.g. "4521".

    Returns:
        On success: {"status": "success", "ticket": "<full ticket text>"}.
        If the id is unknown: {"status": "not_found", "message": "..."} -
        report that honestly; NEVER invent ticket contents.
    """
    text = TICKETS.get(ticket_id)                    # plain dict lookup - the "kitchen"
    if text is None:                                 # unknown id?
        return {                                     # structurally different from success
            "status": "not_found",
            "message": f"No ticket with id {ticket_id!r}.",
        }
    return {"status": "success", "ticket": text}     # the happy path


def search_kb(query: str) -> dict:
    """Search the internal knowledge base for a symptom or error message.

    Use this AFTER reading a ticket, to find the article that explains
    the root cause. Best queries are short symptom phrases.

    Args:
        query: symptom keywords, e.g. "user logged out repeatedly".

    Returns:
        On a hit: {"status": "success", "article": "<best matching article>"}.
        On no match: {"status": "no_match", "message": "..."} - say so;
        do not invent an article.
    """
    hit = KB.search(query)                           # Day 3's little matcher, reused
    if hit is None:                                  # nothing matched?
        return {"status": "no_match",
                "message": f"No KB article matched {query!r}."}
    return {"status": "success", "article": hit}     # e.g. KB-104 on logout loops


# The agent: instruction + tools. Note what is ABSENT versus Day 4 -
# no declarations, no schemas, no dispatch dict. The two function objects
# in `tools=[...]` are the entire registration (auto-wrapping, ADK-10).
triage_agent = Agent(
    name="sutra_triage",
    model="gemini-3.5-flash",                        # pinned - ADK-73, always
    instruction="""You are Sutra, a support-ticket triage assistant.
You cannot see any data directly; use the tools. If a tool reports
not_found or no_match, say so plainly - never invent tickets or articles.""",
    tools=[lookup_ticket, search_kb],                # <- the whole Day 4 apparatus, one list
)


def run_once(question: str) -> str:
    """Drive triage_agent through one question; return the final text.

    Same InMemoryRunner harness as Day 9 (see that doc for the verified
    event API notes - trap #2 lives here).

    Example:
        >>> run_once("Ticket 4521 came in. What is wrong?")
        '...cites KB-104...'
    """
    runner = InMemoryRunner(agent=triage_agent)      # agent + in-memory services
    session = runner.session_service.create_session_sync(
        app_name=runner.app_name, user_id="day10"    # throwaway session
    )
    final = ""
    for event in runner.run(                         # stream the 2.x events
        user_id="day10", session_id=session.id,
        new_message=types.Content(role="user",
                                  parts=[types.Part(text=question)]),
    ):
        # Narrate tool traffic as it happens (Principle 12: everything is a trace).
        for part in (event.content.parts if event.content else []):
            if part.function_call:                   # the model filled a form
                print(f"CALL: {part.function_call.name}({part.function_call.args})")
            if part.function_response:               # the kitchen answered
                print(f"RESULT: {part.function_response.response}")
        if event.is_final_response() and event.content:
            final = "".join(p.text or "" for p in event.content.parts)
    return final.strip()


def demo_triage() -> None:
    """Usage: python -m sutra.adk_tools triage   (~3 model calls)."""
    print("\nANSWER:", run_once(TRIAGE_QUESTION))


def demo_unknown() -> None:
    """Usage: python -m sutra.adk_tools unknown  (~2 model calls)."""
    print("\nANSWER:", run_once("Summarize ticket 9999 for the standup."))


def main() -> None:
    demos = {"triage": demo_triage, "unknown": demo_unknown}
    name = sys.argv[1] if len(sys.argv) > 1 else "triage"
    if name not in demos:
        print(f"usage: python -m sutra.adk_tools [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the recipe card nobody can read

> 🎬 **The scene:** refactor mood. Those long docstrings look bulky, so you trim
> `search_kb`'s to a tidy one-liner: `"""Searches."""` — and rename its parameter to `q`
> while you're at it. The code still runs; nothing crashes.
> 😬 **The naive fix:** ship it — docstrings are comments, and comments are free.
> 💥 **Why it fails:** run the triage demo a few times. The model starts skipping
> `search_kb` entirely (it can't tell *when* the tool applies), or calls it with junk like
> the whole ticket text as `q` (nothing explains what a good query looks like). Nothing
> errors — the *schema* is still valid. The behavior just quietly rots, because you
> deleted the only text the model had about when and how to use the tool.
> 💡 **The insight:** in ADK, **the docstring is the interface.** Day 4 made this visible
> — description and schema were code you wrote by hand. Auto-wrapping folded them into
> prose, and prose *feels* optional. It is not: a tool's docstring is load-bearing
> production configuration, and "refactoring" it is an API change. Restore the real
> docstring and watch correct behavior return.

Run it: ruin the docstring → `python -m sutra.adk_tools triage` (once or twice) → observe
→ restore → re-run → healed. ~2–3 model calls.

## 6 · 🎤 Interview corner

1. **"How do tools work in ADK compared to raw function calling?"** — Mechanically they're
   the same protocol — I've built both. Raw: you hand-write a JSON-Schema declaration, read
   `function_calls` from the response, dispatch yourself, and append a `role="tool"` turn.
   ADK: you pass a plain function; the framework derives the declaration from the
   signature + docstring, executes the call, and threads the result turn — and you observe
   it all as events. The trade: less plumbing, but your docstrings and type hints are now
   the contract, so they need engineering-grade care.
2. **"What makes a *good* tool for an LLM agent?"** — A docstring that says when to use it
   and what good arguments look like; few, primitive-typed parameters; and returns that are
   structured for branching — I use `{"status": "success" | "not_found", ...}` dicts so
   failure is a *shape*, not a sentence the model must interpret. And design the failure
   return as carefully as success: my agent says "ticket 9999 doesn't exist" because the
   tool returns `not_found` explicitly, which the instruction tells it to respect.
3. **"What happens if a tool needs an hour — say, human approval?"** — You don't block the
   loop. ADK has `LongRunningFunctionTool`: the function returns an immediate
   `{"status": "pending"}`-style result, the run pauses, and the client resumes it later
   with the real outcome. It's the primitive under human-in-the-loop approval gates, which
   I built later in the project.
