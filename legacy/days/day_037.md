## 3 · 📚 Concepts

### MCP-13 — Authorization: the badge, the front desk, and two 2026 fixes

**The story.** An office tower. To visit a company (the MCP server), you first stop at
the **front desk** (the *authorization server* — the OAuth service that checks who you
are), which issues a **visitor badge** (the *access token*). The company's own door
scanner (the *resource server* role, played by the MCP server) admits badges, not faces.
MCP over HTTP adopted OAuth 2.1 wholesale, so the cast is standard — what 2026 changed
is two doors people were sneaking through:

**Fix 1 — the badge that came from the wrong desk (RFC 9207, SEP-2468).** Classic
"mix-up" attack: a malicious server tricks your client into starting auth at desk A but
redeeming the code at desk B, smuggling your credentials across issuers. The vaccine:
the authorization server now stamps its identity (`iss`) on the redirect back, and the
client **MUST compare that stamp against the desk it *meant* to visit before redeeming
the code**. One string comparison, mandatory, kills the class. Relatedly (SEP-2352):
credentials are *keyed by issuer* — a client must never replay client credentials from
desk A at desk B, and must re-register when the desk changes.

**Fix 2 — how a stranger-client introduces itself: CIMD replaces DCR.** The old way
(Dynamic Client Registration, RFC 7591 — now formally **deprecated**, kept only as
fallback): every client *asks every desk* to create it an identity — write traffic,
junk-drawer registrations, no proof of who's asking. The 2026 way, **Client ID Metadata
Documents**: the client's `client_id` **is an HTTPS URL it controls** — e.g.
`https://app.example.com/oauth/client-metadata.json` — hosting a JSON document
(`client_id` echoing the exact URL, `client_name`, `redirect_uris`, …). The desk
*fetches* it, verifies the echo, validates redirect URIs against it, caches per HTTP
headers. Identity becomes something you **host and control**, portable across every
desk, instead of something you beg each desk to mint. Desks advertise support via
`client_id_metadata_document_supported: true`; the client priority order is:
pre-registered creds → CIMD → DCR fallback → ask the human. 🅿️ *Map-level today:*
Sutra runs keyless stdio on a laptop; this section becomes hands-on knowledge the day
`sutra-mcp` fronts real users — but the flow walk in Step 5 is closed-book material now.

### MCP-27 — Elicitation: the waiter comes back with a question

**The story.** You order the salmon (call `close_ticket`). The waiter returns — not
with food, but with a question: *"it comes with three duplicates; close all four
together?"* You answer; the order proceeds. Crucially: the *kitchen* asked, the *waiter*
carried, **you** answered — three different parties, and the question happened *inside*
an order that was already placed.

The 2026 carriage for this is a pattern you must recognize on sight (it returns
tomorrow as the replacement for three deprecated features): **Multi Round-Trip Requests
(MRTR)**. There are no server-initiated requests anymore — the server cannot tap the
client on the shoulder. Instead:

1. The tool call comes in; the server realizes it needs the human.
2. It answers — not with a result, but with an **`InputRequiredResult`**
   (`resultType: "input_required"`) whose **`inputRequests`** carries an
   `elicitation/create` request, plus opaque **`requestState`**.
3. The client shows the human the question, gathers the answer, and **retries the
   original call** with **`inputResponses`** (and the echoed `requestState`) attached.
4. The server, finding answers enclosed, completes — or asks again.

The question itself comes in two modes:

| | **Form mode** | **URL mode** |
| --- | --- | --- |
| For | structured, non-secret data | anything that must **not** transit the client: OAuth to third parties, card entry, API keys |
| Shape | `message` + `requestedSchema` — a deliberately *flat* JSON-Schema object of primitives (string/number/boolean/enum only; nesting refused so every client can render a simple form) | `message` + `url` the user opens out-of-band |
| Comes back | `action: "accept"` + `content` matching the schema | `action: "accept"` — *consent to open*, not completion; the server learns the outcome via its own state when the retry arrives |
| Also possible | `decline` (explicit no) / `cancel` (dismissed) — servers MUST handle all three | same three |

Client-side rules with teeth (you'll audit against these on Day 45): show the **full
URL** and highlight the domain before consent; never prefetch; open in a
container the client/LLM can't inspect. Server-side, the phishing rule: the URL a
server hands out could be forwarded to a victim, so the server **MUST verify the user
who completes the flow is the user who started it** (session-cookie ↔ `sub`-claim
comparison is the canonical move). And the headline MUST NOT, which §5 dramatizes:
**never ask for credentials via form mode.**

💡 **Mental model: elicitation is the server putting a form INSIDE the "try again"
envelope — the protocol never calls you; it tells you what to bring when you call back.**

### MCP-30 — Extensions & EMA: features on their own clocks, policy at the IdP

**The framework.** The 2026 core is deliberately small; capabilities ship as
**extensions** with reverse-DNS identifiers (`io.modelcontextprotocol/tasks` — official
prefix; third parties use their own domain, `com.example/...`). Negotiation is the
per-request handshake replacement you already know: the client lists extensions inside
its `_meta` capabilities; the server lists its own in `server/discover`; **both-or-
nothing, opt-in, disabled by default**, each versioned and evolved independently of the
core (breaking change ⇒ new identifier, e.g. `…/my-extension-v2`). You met Tasks
yesterday; MCP Apps arrives Day 41; and the official `ext-auth` repo holds two more:
**OAuth Client Credentials** (machine-to-machine badges — no human at the desk) and —

**Enterprise-Managed Authorization (EMA), 🅿️.** The story: your company has one
identity desk already (the IdP — Okta/Entra-class). EMA's premise: MCP permission
decisions should live *there*, not in each employee's chat app. Addendum 01's example
stands verbatim: *the company allows the GitHub MCP server but blocks any server using
the Apps extension — by policy, centrally.* The client consults enterprise policy; the
extension carries the framework for expressing it. For Sutra the takeaway is
architectural: because extensions are *negotiated per-request and visible in
`server/discover`*, a gateway or IdP can see — and veto — exactly which capabilities any
session would use. Governance rides on the same discovery surface you built Tuesday.
(Depth is 🅿️ deliberate: EMA needs an IdP to demonstrate; the *shape* is interview-ready
today.)

```python
# ---------------------------------------------------------------------------
# Day 37: the first WRITE tool - and the retry-with-answers gate around it.
# The confirmed= parameter is elicitation's skeleton, hand-rolled: refuse,
# say exactly what answer you need, complete when the retry brings it.
# ---------------------------------------------------------------------------
CLOSED_TICKETS: set[str] = set()        # today's "write" effect (in-process, synthetic)


@mcp.tool()
def close_ticket(ticket_id: str, confirmed: bool = False) -> dict:
    """Close a ticket - IF the caller confirms, on a retry, that they mean it.

    This is the MRTR interaction pattern in miniature: the first call
    returns status='input_required' plus the exact question; the caller
    gathers the human's answer and RETRIES with confirmed=True. Compare
    doc section 3 (MCP-27) - elicitation standardizes this dance so any
    host can render the question as a real form.

    Args:
        ticket_id: which ticket to close.
        confirmed: False on a first, innocent call. True only when a human
            actually said yes - the caller's promise, which Day 63's
            approval gates will stop taking on faith.

    Returns:
        {"status": "input_required", "question": ...}   before consent,
        {"status": "closed", "ticket_id": ...}          after, or
        {"status": "failed", "error": ...}              for unknown tickets.

    Example:
        >>> close_ticket("4521")
        {'status': 'input_required', 'question': "Close ticket 4521 ...?"}
        >>> close_ticket("4521", confirmed=True)
        {'status': 'closed', 'ticket_id': '4521'}
    """
    if ticket_id not in TICKETS:                      # program-facing miss (Day 35)
        return {"status": "failed", "error": f"unknown ticket {ticket_id!r}"}
    if not confirmed:                                 # act 1: refuse + ask precisely
        return {
            "status": "input_required",               # same word the spec uses -
            "question": (f"Close ticket {ticket_id} permanently? "  # on purpose
                         "Reply yes to confirm, no to keep it open."),
        }
    CLOSED_TICKETS.add(ticket_id)                     # act 2: the retry did it
    return {"status": "closed", "ticket_id": ticket_id}
```

## 5 · 💥 Failure lab — the helpful form that phished your users

> 🎬 **The scene:** Phase 6 planning. `sutra-mcp` will need each user's key for a
> third-party status API. Elicitation just taught you forms — so the design writes
> itself: `mode: "form"`, `requestedSchema: {"api_key": {"type": "string"}}`, message
> "Please paste your ACME API key to continue." Clean UX, typed, validated!
> 😬 **The naive fix:** ship it — the schema validates the key's *shape*, what could go
> wrong?
> 💥 **Why it fails:** everything between the user's clipboard and your server now
> *holds the secret*. The MCP client sees it (and may log it); the LLM's context may
> ingest it (models echo context — your key can surface in an unrelated answer); every
> intermediary on the retry path carries it. Worse, you have *trained users* that
> "a chat window asking me to paste credentials" is normal — a phishing simulator
> couldn't design a better curriculum. That's why the spec doesn't advise here; it
> **forbids**: servers MUST NOT request credentials via form mode; secrets go through
> **URL mode**, where the user enters them on the server's own HTTPS page and the
> client, by rule, sees only the URL it consented to open — never the data. And URL mode
> carries its own sting the spec makes you handle: the link can be forwarded to a
> victim, so the server must verify same-user-who-started before accepting (the
> `requestState` + session `sub`-claim check from §3).
> 💡 **The insight:** **schemas validate shape; MODES draw the security boundary.**
> Form mode is for answers the client may see; URL mode is for secrets the client must
> never see; and "the model might echo it" is reason enough to classify something as the
> second kind. The lethal-trifecta framing of Day 66 will generalize this; today you
> already know its most concrete instance.

Observed-adjacent (buildable part shown, forbidden part refused): your Step 3 gate
carries a *boolean consent* through the client legitimately; the difference between
that and a *credential* through the same channel is the entire content of the rule.

## 6 · 🎤 Interview corner

1. **"How does an MCP server ask the user a question mid-tool after the 2026 revision?"**
   — It can't call the client — server-initiated requests are gone. It returns an
   `InputRequiredResult` (`resultType: "input_required"`) whose `inputRequests` carries
   an `elicitation/create` — form mode with a deliberately flat `requestedSchema`, or
   URL mode for out-of-band secrets — plus opaque `requestState`. The client renders,
   the user answers (`accept`/`decline`/`cancel`), and the client *retries the original
   call* with `inputResponses` attached; the server correlates via `requestState`, not
   session memory. I've hand-rolled the skeleton (refuse → precise question → retry
   completes) on my own server, so I can say exactly what the standard adds: typed
   answers, three-way user intent, and stateless correlation.
2. **"What did MCP's 2026 auth hardening actually fix?"** — Two holes. Mix-up attacks:
   the authorization response now carries RFC 9207's `iss`, and clients must match it
   against the issuer they started with before redeeming the code — plus credentials
   are keyed per-issuer and never reused across authorization servers. And registration
   sprawl: Dynamic Client Registration is deprecated in favor of Client ID Metadata
   Documents — the client_id *is* an HTTPS URL the client controls, hosting its own
   metadata; the server fetches and verifies the echo. Identity you host beats identity
   you request: verifiable, cacheable, portable across issuers, no write-endpoint spam.
3. **"How would an enterprise control which MCP capabilities employees can use?"** —
   The protocol makes it governable by design: every capability beyond the core is a
   named, versioned extension, negotiated in the open — clients declare theirs in
   per-request `_meta`, servers advertise theirs via `server/discover`. So policy
   infrastructure can see and veto precisely: allow this server, deny any server
   offering the Apps extension, require the client-credentials auth extension for
   service accounts. Enterprise-Managed Authorization is the official extension framing
   those decisions where they belong — the IdP — instead of per-user client settings.
