## 3 · 📚 Concepts

### AG-33 — Embeddings: meaning as a place on a map

**The library-without-titles story.** Imagine a library where you may only search by
words *in the title*. "Keeps getting logged out" is on the shelf; you ask for "sign-in
trouble" — nothing. The librarian isn't stupid; the *filing system* is. Now imagine a
different librarian who reads each book and places it **physically on a giant table**:
cookery books cluster here, login-bug reports cluster there, and two books about the
same problem end up centimeters apart even if their titles share no words. Finding
"anything like this one" becomes: *put my query on the table, look at its neighbors.*

That table is an embedding space. Concretely:

| Library | Our system | Technical name |
| --- | --- | --- |
| Reading a book, choosing its spot | model maps text → list of numbers | **embedding** (`nomic-embed-text`: 768 numbers) |
| The giant table | the space of all possible spots | vector space (768 dimensions instead of 2) |
| "centimeters apart" | angle between two vectors | **cosine similarity** (1.0 = same direction) |
| The filled table | vectors for every archive row | the **index** (`data/archive_index.json`) |
| "look at its neighbors" | rank all rows by similarity, keep k | **top-k retrieval** |
| neighbors handed to the agent | snippets into context, model answers | **RAG** — retrieval-augmented generation |

Why does this work at all? The embedding model was trained on oceans of text to place
*texts that appear in similar contexts* near each other. "Logged out repeatedly" and
"bounced back to the login page" occur in the same kinds of documents, surrounded by the
same kinds of sentences — so they land close. Nobody wrote a synonym list; geometry
absorbed the job. 💡 **Mental model: an embedding turns "what is this about?" into "where
does this sit?" — and search becomes measuring distance.**

Cosine similarity, since we'll write it by hand: two vectors pointing the same way have
cosine ≈ 1; unrelated ≈ 0. Formula: dot(a,b) / (|a|·|b|) — one `zip`, two `sqrt`s, no
library. You will *see* `sim("cat","kitten") > sim("cat","carburetor")` as printed
numbers before any of this touches an agent — build first, compare after (Principle 4).

**And the honest part** (AG-33 is "one honest RAG day"): retrieval adds a new failure
mode — the *plausible neighbor*. Keyword search fails loudly (zero results); vector
search **always returns k neighbors**, relevant or not. Ask about billing when the
archive holds only login bugs and you still get "nearest" tickets — nearest garbage. The
agent must judge results, not trust them (the instruction says so explicitly), and
Day 50 measures where top-k lies to you. RAG is also frequently the wrong tool — that
table is tomorrow's centerpiece.

```python
"""Day 49 — retrieval & embeddings: the librarian who remembers meanings.

Embeds the ticket archive (data/tickets.db) with a LOCAL model via
Ollama's /api/embed, stores vectors in data/archive_index.json, and
searches by cosine similarity. Then wraps the whole thing as a
BaseMemoryService so Day 46's load_memory tool searches by MEANING.

Every embedding is local: zero API quota, works offline. Run:

    python -m sutra.retrieval feel     # cosine on 3 words — see the geometry
    python -m sutra.retrieval index    # embed the archive -> data/archive_index.json
    python -m sutra.retrieval search "sign-in trouble after a redirect"
    python -m sutra.retrieval memory   # Day 46's MISS query, now through the agent
"""
from __future__ import annotations

import asyncio
import json
import math
import sqlite3
import sys
import urllib.request
from pathlib import Path

from sutra.logging_setup import get_logger

log = get_logger(__name__)

OLLAMA_EMBED_URL = "http://localhost:11434/api/embed"    # current endpoint (NOT /api/embeddings)
EMBED_MODEL = "nomic-embed-text"                          # pinned 2026-08-19; 768-dim; local
ARCHIVE_DB = Path("data/tickets.db")                      # Day 39's read-only archive
INDEX_PATH = Path("data/archive_index.json")              # derived; rebuild any time
TOP_K = 3                                                 # Day 50 interrogates this number


def embed(texts: list[str]) -> list[list[float]]:
    """Turn texts into vectors via the local Ollama embedder.

    Args:
        texts: one or more strings (the endpoint batches natively).

    Returns:
        One 768-number list per input text, in order.

    Example:
        >>> vecs = embed(["hello desk"])
        >>> len(vecs), len(vecs[0])
        (1, 768)
    """
    body = json.dumps({"model": EMBED_MODEL, "input": texts}).encode()
    req = urllib.request.Request(                        # stdlib on purpose: no new deps
        OLLAMA_EMBED_URL, data=body,
        headers={"Content-Type": "application/json"},
    )
    with urllib.request.urlopen(req, timeout=60) as resp:  # local call; generous timeout
        payload = json.load(resp)
    return payload["embeddings"]                         # the server did the batching


def cosine(a: list[float], b: list[float]) -> float:
    """Cosine similarity by hand — the whole 'AI search' secret in 3 lines.

    Args:
        a, b: same-length vectors.

    Returns:
        ~1.0 same direction (same meaning), ~0.0 unrelated.

    Example:
        >>> cosine([1.0, 0.0], [1.0, 0.0])
        1.0
    """
    dot = sum(x * y for x, y in zip(a, b))               # how aligned are they…
    mag = math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b))
    return dot / mag if mag else 0.0                     # …normalized by their lengths


def load_archive_rows() -> list[dict]:
    """Read every ticket and KB row from the archive (read-only, Day 39 rule).

    Returns:
        [{"ref": "ticket:4521", "text": "..."}, {"ref": "kb:KB-104", ...}, ...]

    Example:
        >>> refs = [r["ref"] for r in load_archive_rows()]
        >>> "ticket:4521" in refs
        True
    """
    uri = f"file:{ARCHIVE_DB.as_posix()}?mode=ro"        # the tools' own read-only door
    rows: list[dict] = []
    with sqlite3.connect(uri, uri=True) as conn:
        for tid, body in conn.execute("SELECT id, body FROM tickets"):
            rows.append({"ref": f"ticket:{tid}", "text": body})
        for kid, body in conn.execute("SELECT id, body FROM kb"):
            rows.append({"ref": f"kb:{kid}", "text": body})
    return rows


def build_index() -> int:
    """Embed the whole archive and write the index file.

    Returns:
        Number of rows indexed.

    Example:
        >>> n = build_index()                            # prints progress; ~seconds, $0
    """
    rows = load_archive_rows()
    vectors = embed([r["text"] for r in rows])           # ONE batched local call
    for row, vec in zip(rows, vectors):
        row["vector"] = vec                              # vector rides next to its text
    INDEX_PATH.write_text(json.dumps(rows), encoding="utf-8")
    log.info("index_built", extra={"rows": len(rows)})
    return len(rows)


def search(query: str, k: int = TOP_K) -> list[tuple[float, str, str]]:
    """Rank the archive by meaning-closeness to the query.

    Args:
        query: natural-language question, any wording.
        k: how many neighbors to return (Day 50's knob).

    Returns:
        [(score, ref, text), ...] best-first. ALWAYS returns k rows —
        judging their relevance is the CALLER'S job (see doc §3).

    Example:
        >>> search("sign-in trouble after a redirect")[0][1]
        'ticket:...'                                     # a login-flavored neighbor
    """
    rows = json.loads(INDEX_PATH.read_text(encoding="utf-8"))
    qvec = embed([query])[0]                             # the query joins the same map
    scored = sorted(
        ((cosine(qvec, r["vector"]), r["ref"], r["text"]) for r in rows),
        reverse=True,                                    # closest meaning first
    )
    return scored[:k]


# ---------------------------------------------------------------------------
# ADK-30: the index wrapped as a MemoryService — the Day 46 socket, new brain.
# ---------------------------------------------------------------------------
from google.adk.memory import BaseMemoryService          # the extension point (Day 46's page)


class SutraArchiveMemoryService(BaseMemoryService):
    """search_memory backed by the local embedding index.

    Day 46's agent + load_memory tool work UNCHANGED on top of this —
    that interface-held/brain-swapped moment is the entire point of
    ADK-30. Construction of the response object is probed in demo
    `memory`: TODO(python -c "from google.adk.memory import
    SearchMemoryResponse, MemoryEntry; help(SearchMemoryResponse)") —
    print-then-adjust the two marked lines if your 2.7.x shapes differ.
    """

    async def add_session_to_memory(self, session) -> None:
        """Accept filings, but route them through Day 48's gate first."""
        from sutra.memory_policy import keepers          # the one road in (Day 48)
        text = "\n".join(                                # flatten the session's text parts
            p.text or ""
            for e in session.events if e.content
            for p in (e.content.parts or [])
        )
        for finding in keepers(text):                    # only findings pass the bouncer
            log.info("memory_filed", extra={"finding": finding[:80]})
        # (Storage of filed findings into the index: Day 52 wires the loop closed.)

    async def search_memory(self, *, app_name: str, user_id: str, query: str):
        """Embed the query, cosine-rank the archive, return top-k snippets."""
        from google.adk.memory import SearchMemoryResponse   # shape-probe target (TODO above)
        hits = search(query)                             # our index does the thinking
        return SearchMemoryResponse(                     # ← adjust field names if help() differs
            memories=[self._entry(f"[{ref} sim={score:.2f}] {text}")
                      for score, ref, text in hits],
        )

    @staticmethod
    def _entry(text: str):
        """Build one memory entry (isolated so a shape change touches ONE line)."""
        from google.adk.memory import MemoryEntry        # shape-probe target (TODO above)
        from google.genai import types
        return MemoryEntry(content=types.Content(role="model",
                                                 parts=[types.Part(text=text)]))

if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the nearest garbage

> 🎬 **The scene:** semantic search feels like magic, so you wire it everywhere and stop
> thinking. A ticket arrives: *"Requesting a refund for double billing in March."* The
> researcher dutifully searches the archive — which contains login bugs, email bounces,
> and dashboard glitches, and **nothing about billing**.
> 😬 **The naive fix:** trust the top-k. It returned three results with scores; results
> are results, and the draft reply cites "similar past case ticket:4633."
> 💥 **Why it fails:** cosine ranking is a *sorting* machine, not a *relevance oracle* —
> it will happily rank all the wrong answers and hand you the least-wrong one with a
> straight face. 0.42 similarity to a refund question doesn't mean "related"; it means
> "the closest thing on a table that contains nothing close." Keyword search fails
> *loudly* (zero rows); vector search fails *politely* — and polite failures walk
> straight into drafts. This is Day 46's false-negative problem mirrored: now we
> manufacture false *positives*.
> 💡 **The insight:** **top-k always returns k; relevance is a threshold decision the
> caller must own.** Ship the score with every snippet (our service embeds `sim=0.42`
> in the text on purpose), teach the agent that low-similarity neighbors are absence
> ("if nothing looks genuinely similar, say so"), and measure where your corpus's
> honest cutoff sits — which is precisely Day 50's lab. A retrieval system without a
> notion of "nothing found" is a fabrication engine with citations.

Try it now, before Day 50 formalizes it: `python -m sutra.retrieval search "refund for
double billing"` — read the scores, notice they're numerically *there* and semantically
*nothing*, and notice how much lower they sit than step 4's genuine hits.

## 6 · 🎤 Interview corner

1. **"Explain embeddings to a non-ML engineer."** — An embedding model turns a piece of
   text into a list of numbers — a *location* — such that texts with similar meanings
   get nearby locations. Search stops being string comparison and becomes measuring
   distance: embed the query, embed the documents, rank by cosine similarity. I
   hand-rolled exactly this over a support-ticket archive: 768-dim vectors from a local
   model, cosine in three lines of Python, and a query about "sign-in trouble" finding a
   ticket that says "keeps getting logged out" — zero shared keywords. The magic
   demystifies fast once you've printed the numbers.
2. **"When is RAG the wrong tool?"** — More often than the hype admits. If the corpus
   fits in the context window, just include it — retrieval adds a miss-probability for
   nothing. If the question is structured ("how many tickets last week?"), SQL is
   correct and vectors are noise. If freshness matters, retrieval serves you yesterday
   confidently. And the failure mode people miss: top-k *always* returns k results, so
   over an irrelevant corpus RAG manufactures plausible-looking evidence — you need a
   similarity threshold and an explicit "nothing found" path. I keep the scores attached
   to every snippet for exactly that reason.
3. **"Local versus API embeddings — how did you choose?"** — By what the workload does
   to the constraint. Indexing embeds *everything*, repeatedly as data grows; my API
   lane is rate-limited free tier where requests are the currency, and embedding limits
   aren't even published anymore — dashboard-only. A local model (nomic-embed-text via
   Ollama) costs zero requests, works offline, and keeps data on-machine — which also
   answers the "free tiers may train on your data" concern structurally. The trade is
   quality ceiling and ops (a running daemon); for a support-desk archive, 768-dim local
   retrieval was measurably sufficient, and the interface makes swapping later a
