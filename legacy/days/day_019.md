## 1 · 🎬 Where we are — the story so far

Sutra now has three kinds of memory, each in its right place: the transcript (the story),
state (the sticky notes), artifacts (the filing cabinet). Storage is solved — for now.

But storage was never the hard question. The hard question arrives on every single model
call, and Day 2 taught it to you in goldfish form: **the model knows only what is in the
request you send right now.** Nothing else. Not what's in state — unless you put it in. Not
what's in the cabinet — unless you paste it in. Every call, you (or ADK on your behalf)
assemble a package of text, and the model's entire universe *is that package*.

So far we let ADK assemble it with defaults and never looked inside. That stops today.
Because the package — the **context window** — is the scarcest resource in this whole
system, and deciding *what earns a place in it* is the closest thing agent engineering has
to a core craft. It even has a name now: **context engineering**. Today is theory + a
measuring instrument. Tomorrow (Day 20) we act on it with compaction.

## 3 · 📚 Concepts

### AG-08 — The window is a budget, not a bag

**The courtroom story.** A judge will read exactly one binder before ruling. Whatever is in
the binder exists; whatever isn't, doesn't. Now watch two paralegals prepare it. The first
photocopies *everything* — every email, every old filing, three near-identical drafts —
"just in case." The second selects: the two contracts that matter, one timeline, one page
of open questions. Same case. The second judge rules faster *and better* — not because the
binder was cheaper to print, but because **attention spent wading is attention not spent
judging**.

The model is the judge. The request you assemble is the binder. And "1M-token context"
means the binder *can* be a pallet of paper — not that it should be.

Three real costs grow with every token you add:

| Cost | Mechanism | You feel it as |
| --- | --- | --- |
| **Money/quota** | every input token is billed & counted per call — and the loop resends the whole transcript *every step* (Day 3's lesson) | RPD burned; on our free tier: the day ends early |
| **Latency** | more input = more prefill work before the first output token | slow replies; multiplied across a multi-step run |
| **Attention** | relevant facts drown among irrelevant ones; models weight beginnings/ends more than middles ("lost in the middle"); distractor text invites confident wrong answers | quality quietly degrades — the worst kind of bug, because nothing errors |

💡 **Mental model: the context window is a carry-on suitcase with a weight fee, not a
shipping container.** Room ≠ free. Pack for the trip you're taking *this call*.

The professional reflex this builds: **"what does the model need to answer *this* step?"**
— asked fresh at every step. Not "what do I have?" (everything), but "what earns a place?"

### AG-09 — Anatomy of the window, and a selection rule per part

When ADK (or your Day 3 loop) fires a model call, the package has recognizable organs.
Learn them, because *each one is a dial you control*:

| Organ | What it is | Who put it there | Selection rule |
| --- | --- | --- | --- |
| **System instruction** | persona + standing rules | you, on the `Agent` (Day 6) | short, stable, no per-task facts — it's re-sent every call, so every word here is a *subscription*, not a one-time cost |
| **Tool declarations** | the menu (Day 4/10) | your `tools=[…]` | every tool costs tokens *and* decision-difficulty; an agent with 40 tools mis-picks more than one with 6 (Day 11's design lesson, now with a token reason) |
| **State-templated facts** | `{key}` values injected into the instruction (Day 17) | you, via key naming | inject *facts*, never blobs — this is why Day 18 kept documents out of state |
| **Conversation history** | prior turns + tool results | the framework, from session events | the fastest-growing organ, and the only one that grows *by itself* — tomorrow's compaction target |
| **Documents / retrieved text** | pasted file or search content | tools & (Phase 7) retrieval | never "the whole file" when a slice answers the question; retrieval = *selection at scale* |
| **The current message** | the user's actual ask | the user | untouchable — but everything else exists to serve it |

Two consequences deserve their own sentences:

**First: the history organ grows quadratically in total cost.** Each turn resends all prior
turns, so a 40-turn session pays for turn 1 forty times. Nothing else in the anatomy has
that property — which is why history gets a whole day (tomorrow) and the others get rules.

**Second: "put it in context" and "make it findable" are different acts.** A fact on page
212 of a pasted log is *in* the window and still functionally invisible. Position and
framing matter: summaries in front, verbatim detail only where the step needs it. The
binder has a table of contents for a reason.

🅿️ *Parked pointer:* selection at scale — finding the right 5 chunks in 10,000 documents —
is **retrieval**, Day 49's topic. Today's rule "only what earns a place" is exactly the
rule retrieval automates.

```python
"""Day 19 — context engineering I: weighing what goes in the window.

No agent runs today. This module is a SCALE: it assembles two candidate
context packages for the same triage question — kitchen-sink vs curated —
and weighs them with count_tokens (which counts, but never generates).
Day 20 extends this file with compaction (the fix for the heaviest organ).

    python -m sutra.context weigh      # ~2 count_tokens calls, 0 generations
"""
from __future__ import annotations

import sys

from google import genai

from sutra.config import load_env

MODEL = "gemini-3.5-flash"                           # pinned; count_tokens needs a model
                                                     # because tokenizers differ per model

# --- Ingredients for the binder ------------------------------------------------
# The task (identical in both packages — the judge's actual question):
QUESTION = "Ticket 4521: users keep getting logged out. What is the likely cause?"

# A curated fact — what Day 17 state templating would inject:
CURATED_FACTS = "Known context: severity=high. KB-104: SameSite/https cookie change."

# The kitchen sink — what "just in case" packing looks like. We fake a big
# log cheaply: one plausible line, repeated. (Real logs are worse: varied
# noise is HARDER for attention than repetition, not easier.)
FAKE_LOG = ("2026-08-14T09:12:03Z INFO session-svc token refresh ok user=4411\n" * 400)
OLD_TICKETS = "\n".join(
    f"Ticket {4000 + i}: printer issue, resolved by restart." for i in range(60)
)


def build_kitchen_sink() -> str:
    """The 'photocopy everything' binder: question + logs + 60 old tickets.

    Returns:
        One big string — everything we HAVE, not what the step NEEDS.

    Example:
        >>> len(build_kitchen_sink()) > 30_000
        True
    """
    return (
        "You are a support triage assistant.\n\n"
        + "FULL SESSION LOG:\n" + FAKE_LOG            # 400 lines nobody asked for
        + "\nARCHIVE OF PAST TICKETS:\n" + OLD_TICKETS  # 60 unrelated printers
        + "\n\nQUESTION: " + QUESTION                 # the actual ask, buried last
    )


def build_curated() -> str:
    """The curated binder: persona line, two relevant facts, the question.

    Returns:
        A small string — what this step actually needs (AG-09's rule).

    Example:
        >>> "KB-104" in build_curated()
        True
    """
    return (
        "You are a support triage assistant.\n"
        + CURATED_FACTS + "\n\n"                      # facts EARNED their place:
        + "QUESTION: " + QUESTION                     # both directly serve the question
    )


def demo_weigh() -> None:
    """Weigh both binders on the token scale and print the bill.

    Usage:  python -m sutra.context weigh
    """
    client = genai.Client()                           # GOOGLE_API_KEY from .env
    for name, text in [("kitchen-sink", build_kitchen_sink()),
                       ("curated", build_curated())]:
        result = client.models.count_tokens(          # counts WITHOUT generating —
            model=MODEL, contents=text                # no text produced, near-zero cost
        )
        print(f"{name:13} = {result.total_tokens:>6} tokens")
    print("\nSame question. Same available facts. The difference is packing.")
    print("Now multiply the heavy binder by every step of a loop that")
    print("resends history each call (Day 3) — that is the real bill.")


def main() -> None:
    """Demo dispatcher — house pattern."""
    demos = {"weigh": demo_weigh}
    name = sys.argv[1] if len(sys.argv) > 1 else "weigh"
    if name not in demos:
        print(f"usage: python -m sutra.context [{'|'.join(demos)}]")
        raise SystemExit(2)
    load_env()
    demos[name]()


if __name__ == "__main__":
    main()
```

## 5 · 💥 Failure lab — the "just in case" binder

> 🎬 **The scene:** a triage answer came back wrong last week, and the postmortem said "the
> model didn't know about the cookie change." Someone proposes the fix that always gets
> proposed: *"just give it everything — the full log, the whole ticket archive. Context is
> 1M tokens now, we have room!"*
> 😬 **The naive fix:** ship the kitchen-sink binder. Nothing errors. Demo looks fine.
> 💥 **Why it fails:** three slow leaks, none of which throw an exception. The **bill**: the
> loop resends the pallet of paper on every step; your RPD budget dies by mid-afternoon
> (Day 24 will put numbers on this). The **latency**: prefill on thousands of junk tokens
> before the first useful output token, on every call. The **attention**: the one relevant
> fact (KB-104) sits between 400 log lines and 60 printer tickets; "lost in the middle" is
> exactly this geometry, and distractor tickets actively invite a confident wrong diagnosis
> — the model finds a *plausible* answer in the noise you provided. Quality degrades with no
> stack trace, which means no alarm, which means you find out from users.
> 💡 **The insight:** **more context is not more knowledge — it's more competition for
> attention.** The question is never "does it fit?" but "does it earn its place *for this
> step*?" Facts in, blobs out; summaries in front, detail on demand; and when the archive is
> genuinely needed, *select* from it (retrieval, Day 49) rather than *ship* it.

Observed today: the scale printed the two weights; you did the multiplication.

## 6 · 🎤 Interview corner

1. **"Context windows are huge now — is context engineering still a thing?"** — More than
   ever; the budget moved from "can it fit" to "what does it cost in quota, latency, and
   attention." Long-context models still degrade on middle-buried facts and still bill every
   token, and agent loops resend history every step, so waste compounds per step. I measured
   a kitchen-sink vs curated package for the same triage question — order-of-magnitude
   weight difference, same available facts — and on a rate-limited tier that ratio is
   literally the number of user questions I can serve per day.
2. **"Walk me through what's actually in a model call your agent makes."** — Six organs:
   system instruction (persona + rules — a subscription, re-sent every call), tool
   declarations (the menu — each tool costs tokens and decision quality), state-templated
   facts (small values injected from session state), conversation history (the only organ
   that grows by itself — compaction's target), document/retrieved text (slices, never whole
   files), and the current message. Each has its own selection rule; naming them is what
   lets me debug quality problems as *packing* problems.
3. **"A fact is in the context but the model ignores it — what do you check?"** — Position
   and competition. Is it mid-window behind kilobytes of noise ("lost in the middle")? Is it
   phrased as one line among 500 similar lines? I move load-bearing facts near the
   instruction or the question, cut distractors, and if the fact came from a document, I
   send the relevant slice instead of the file. Only after packing is clean do I suspect the
   model.
