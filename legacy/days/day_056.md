## 1 · 🎬 Where we are — the story so far

Every loop you have built so far — Day 3's hand-rolled one, Day 54's polish loop — shares
a personality: it is **reactive**. Look at the latest thing, decide the next single step,
repeat. Think→act→observe is a fine way to handle a ticket… and a terrible way to handle
a *project*. Ask a reactive loop to "investigate whether ticket 4521, 4610 and 4633 are
the same underlying bug" and watch it wander: it looks up one ticket, gets interested,
searches the KB, forgets it never read the third ticket, and confidently reports on two.

You already know the human fix, because you use it every morning: **write the plan down
first.** Plan on paper, then execute the paper, then — and this is the part amateurs skip
— *change the paper* when reality disagrees with it. Today Sutra learns both halves:
planning (AG-17) and replanning (AG-18). And the code will feel like a homecoming: the
executor you build today is Day 3's loop wearing a project manager's badge.

## 3 · 📚 Concepts

### AG-17 — Plan-and-execute: the shopping list

**The supermarket story.** Send someone hungry into a supermarket with "get what we need
for the week" and they will come home with interesting snacks and no rice — every aisle
renegotiates the mission. Send them with a **list**, and the shopping becomes almost
mechanical: next item, find it, cart, next. The list did the thinking; the legs just walk.

Map it onto agents:

| Supermarket | Our system | Technical name |
| --- | --- | --- |
| Writing the list at home | one model call that ONLY plans | the **planner** |
| The list itself | a typed object — steps, not prose | the **plan** (Pydantic, of course) |
| Walking the aisles | executing steps one at a time | the **executor** |
| "They're out of rice" | a step result that breaks the list | the trigger for **replanning** (AG-18) |

Why this beats pure react for multi-part work — three concrete wins:

1. **Coverage.** The planner sees the WHOLE request at once, so "compare three tickets"
   yields steps for all three. A reactive loop's attention is always on the last
   observation; parts of the request quietly fall off the table (you will build exactly
   this failure in the demo's baseline).
2. **Inspectability.** A plan is an artifact. You can log it (Principle 12), show it to a
   human *before* execution (the Phase 9 approval gate will do literally this), and eval
   it (Phase 12 can score "did the plan cover the request?" separately from "did the
   execution succeed?"). A reactive agent's plan lives in its head, which is to say
   nowhere.
3. **Cheap steps.** Once the plan exists, many steps stop needing judgment — "look up
   ticket 4610" is a function call. The expensive brain runs once up front; the legs are
   cheap. (Day 53's law again: never pay a model to do an `if` — planning moves MORE
   steps into `if` territory.)

And the honest cost: **a plan is a prediction, and predictions go stale.** The list says
"rice, aisle 4"; the shop moved the rice. Hold that thought two paragraphs.

💡 **Mental model: react thinks with its eyes; plan-and-execute thinks with its memory of
the whole request.** Use react for single-goal loops (a triage), planning for multi-part
work (an investigation). Sutra now owns both, which is the actual skill.

### AG-18 — Replanning: the list meets the shop

A failed step tells you one of two things, and the whole discipline is telling them apart:

- **The step is fine, the world hiccuped** → *retry the step*. Transient 429s, timeouts —
  you built this reflex on Days 21 and 44. The plan is untouched.
- **The step's assumption is false** → *revise the plan*. "Look up ticket 9999" cannot be
  retried into working; the ticket does not exist. Retrying harder is the definition of
  the Day 72 anti-pattern. The remaining plan is built on rubble; it needs a new edition.

Replanning mechanics, the honest version:

1. The executor notices a step result that is a *contradiction*, not a hiccup ("no such
   ticket"), and stops walking.
2. The planner runs AGAIN — with the original request **plus the plan so far and the
   failure**. Its job: a revised plan for what is left. Not a fresh plan from scratch —
   the successes are sunk capital, keep them.
3. **The replan counter is a brake.** Sutra allows ONE replan (`MAX_REPLANS = 1`). A task
   that needs a third plan is not being planned badly — it is being *understood* badly,
   and that is a human's job now (escalation, honestly logged — Principle 10; Day 62 will
   give escalation its full machinery).

💡 **Mental model: a failed step is data about the plan, not just the step.** Amateurs
retry; professionals ask "what did this failure teach me about my list?" — and the
humblest possible answer, "the list was fine, retry the step," is allowed too.

**Why the dynamic-workflow API is today's right home:** yesterday's graph draws edges at
*design time*, but a plan's steps exist only at *run time* — you cannot draw edges for
steps you have not planned yet. The `@node` orchestrator is exactly this: real Python
control flow (`for step in plan.steps`, `while failures`) with `ctx.run_node()` executing
children. The docs' own division of labor, and today you are on the dynamic side of it.

```python
"""Day 56 — plan-and-execute with honest replanning.

The planner is one model call that ONLY writes a typed plan. The executor
is a dynamic-workflow orchestrator that walks the steps, retries hiccups,
and replans (once) on contradictions. Day 3's loop, promoted to management.

Run from repo root:
    python -m sutra.planning plan      # just the planner (~1 LLM call)
    python -m sutra.planning execute   # full plan->execute (~4 LLM calls)
    python -m sutra.planning replan    # poisoned step -> one replan (~6 LLM calls)
"""
from __future__ import annotations

import sys
from typing import Literal

from pydantic import BaseModel, Field

from google.adk import Context                          # dynamic-workflow context
from google.adk.agents.llm_agent import Agent
from google.adk.workflow import node                    # the @node decorator

from sutra.config import load_env
from sutra.logging_setup import get_logger

log = get_logger(__name__)

PRIMARY = "gemini-3.5-flash"                            # planner: judgment lane
MAX_REPLANS = 1                                         # the brake. One new edition.


# --- the plan is a FORM (Day 4's lesson, promoted) --------------------------

class PlanStep(BaseModel):
    """One step of a plan — small enough to be checked, typed enough to route.

    Example:
        >>> PlanStep(action="lookup_ticket", argument="4610",
        ...          why="read the second ticket")
        PlanStep(action='lookup_ticket', ...)
    """
    action: Literal["lookup_ticket", "search_kb", "summarize"] = Field(
        description="The ONLY actions the executor owns. Closed set, like Day 12.")
    argument: str = Field(description="Ticket id, search query, or summary focus.")
    why: str = Field(description="One line: what this step contributes. For humans.")


class Plan(BaseModel):
    """The whole list: goal restated + ordered steps."""
    goal: str = Field(description="The request, restated in one line.")
    steps: list[PlanStep] = Field(description="Ordered. Every part of the "
                                              "request must be covered by a step.")


planner = Agent(
    name="planner",
    model=PRIMARY,
    instruction="""You write plans; you NEVER execute. Cover every part of the
user's request with steps drawn only from the allowed actions. Prefer few,
concrete steps. If the request mentions several tickets, plan a step per
ticket — coverage beats cleverness.""",
    output_schema=Plan,                                 # the planner fills a form
)

replanner = Agent(
    name="replanner",
    model=PRIMARY,
    instruction="""You revise plans. You get: the goal, the steps already
completed (keep their results — they are paid for), and a step that FAILED
with a reason. Write a new plan covering only what remains. Drop steps whose
assumptions the failure disproved. Never re-plan completed work.""",
    output_schema=Plan,
)


# --- the executor's hands: deterministic, free (Day 53's law) ---------------

def run_step(step: PlanStep) -> tuple[bool, str]:
    """Execute one step. Returns (ok, result_text).

    ok=False means CONTRADICTION (the step's assumption is false), not a
    hiccup — transient errors raise and are retried by the caller instead.

    Example:
        >>> run_step(PlanStep(action="lookup_ticket", argument="9999", why="x"))
        (False, "No ticket with id '9999'.")
    """
    from sutra.loop import TICKETS, search_kb
    if step.action == "lookup_ticket":
        body = TICKETS.get(step.argument.strip().lstrip("#"))
        if body is None:                                # honest miss = contradiction
            return False, f"No ticket with id {step.argument!r}."
        return True, f"Ticket #{step.argument}: {body}"
    if step.action == "search_kb":
        return True, search_kb(step.argument)           # KB miss is still information
    return True, f"[summarize] focus: {step.argument}"  # handled by the final wrap-up


# --- the orchestrator: runtime control flow = dynamic workflow --------------

@node(rerun_on_resume=True)                             # docs: orchestrators MUST use
async def plan_and_execute(ctx: Context, node_input: str) -> str:
    """Plan → walk the steps → replan once on contradiction → summarize.

    Args:
        ctx: dynamic-workflow context; ctx.run_node() executes children.
        node_input: the user's multi-part request.

    Returns:
        A closing summary that cites which plan edition delivered it.

    Example:
        >>> # via the runner:  python -m sutra.planning execute
    """
    plan: Plan = await ctx.run_node(planner, node_input)     # edition 1
    print(f"PLAN v1: {len(plan.steps)} steps")
    for s in plan.steps:
        print(f"  - {s.action}({s.argument})  # {s.why}")

    done: list[str] = []                                 # sunk capital: kept forever
    editions = 1
    steps = list(plan.steps)
    i = 0
    while i < len(steps):
        step = steps[i]
        ok, result = run_step(step)                      # deterministic hands
        print(f"STEP {i+1}/{len(steps)} {step.action}({step.argument}) "
              f"-> {'ok' if ok else 'CONTRADICTION'}")
        if ok:
            done.append(f"{step.action}({step.argument}): {result}")
            i += 1
            continue
        if editions > MAX_REPLANS:                       # the brake — checked FIRST
            return ("ESCALATE: plan failed twice; a human should look. "
                    f"Completed: {len(done)} steps. Failure: {result}")
        briefing = (f"GOAL: {plan.goal}\nCOMPLETED:\n" + "\n".join(done) +
                    f"\nFAILED STEP: {step.action}({step.argument}) -> {result}")
        plan = await ctx.run_node(replanner, briefing)   # edition 2, informed by pain
        editions += 1
        print(f"REPLAN -> v{editions}: {len(plan.steps)} steps")
        steps, i = list(plan.steps), 0                   # walk the NEW list

    wrap = f"Goal: {plan.goal}\nFindings:\n" + "\n".join(f"- {d}" for d in done)
    return f"[plan edition v{editions}] {wrap}"
```

## 5 · 💥 Failure lab — the plan that outlived the world

> 🎬 **The scene:** proud of the planner, you plan BIG: a ten-step investigation plan,
> executed over an hour, with slow steps in between. Step 9 is
> `lookup_ticket("4633")` — planned while 4633 was open. By the time the legs reach step
> 9, a colleague merged 4633 into 4610 and closed it. The lookup "succeeds" — closed
> tickets still read — and the final report recommends action on a ticket that no longer
> meaningfully exists.
> 😬 **The naive fix:** plan in even MORE detail, so nothing is ambiguous. Bigger list,
> firmer ink.
> 💥 **Why it fails:** detail is not freshness. A plan is a photograph of the world at
> planning time, and every minute of execution is the world walking out of frame. Worse:
> unlike ticket 9999, this staleness produced no CONTRADICTION — the step *worked*, the
> data was just quietly obsolete. Your replan trigger never fired because your executor's
> definition of failure was "step errored," not "step's assumption aged out." (Your Step 5
> answer, checked: replanning catches loud contradictions; nothing today catches silent
> staleness.)
> 💡 **The insight:** **plan at the altitude your world's half-life allows.** Fast-moving
> context → short plans, frequent replans, verify-before-act steps for anything
> load-bearing ("confirm 4633 is still open" is a legitimate plan step — the plan
> planning its own freshness checks). Stable context → longer plans are safe and
> cheaper. And any plan that must survive hours belongs in front of a human first —
> which is precisely the Phase 9 approval gate, one phase early. This is Principle 14
> ("reality outranks the plan") — for the agent's plans this time, not just ours.

## 6 · 🎤 Interview corner

1. **"Plan-and-execute vs ReAct — when each?"** — ReAct decides one step at a time with
   eyes on the latest observation: unbeatable for single-goal loops, prone to dropping
   parts of multi-part requests. Plan-and-execute pays one up-front model call to cover
   the whole request in a typed artifact, then executes cheaply — and the plan becomes
   loggable, human-reviewable, evaluable. I built the comparison into Sutra: same
   request, the reactive baseline lost a ticket, the planner covered all parts. Cost of
   planning: an extra call, plus staleness risk on long executions.
2. **"What triggers a replan, versus a retry?"** — Classification of the failure. Hiccup
   (429, timeout) → retry the step; the plan is intact. Contradiction (the step's
   assumption is false — 'ticket doesn't exist') → replan what remains, feeding the
   planner the completed steps and the failure so successes aren't redone and the dead
   end is dropped. Bounded: one replan, then escalate — a task needing a third plan is
   being misunderstood, not mis-planned. The subtle miss is *silent* staleness: steps that
   succeed on obsolete data; the countermeasure is planning verify-steps for load-bearing
   facts, not more retries.
3. **"Where does the typed plan pay off beyond execution?"** — Everywhere a prose plan
   can't go: it's diffable across editions (v1 vs v2 shows exactly what the failure
   taught), it can be gated (show the plan to a human BEFORE the legs move — our approval
   gates do this), and it's evaluable in isolation (score coverage without running
   anything). Artifacts beat intentions.
