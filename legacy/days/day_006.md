## 3 · 📚 Concepts

### AG-05 — Instruction design: the employee handbook

**The new-hire story.** Two support desks hire the same brilliant temp worker.

Desk A hands over a note: *"Be helpful and answer tickets well!"* The temp is helpful —
wildly, randomly helpful. They speculate about refunds, promise features, apologize for
things that never happened. Every answer is polite; many are liabilities.

Desk B hands over a one-page **handbook**: here is your role; here are the three things
you do; here are the things you must *never* do and what to say instead; here is the
tone; here are two examples of a perfect reply. The same temp is now consistent,
scoped, and safe — not because they got smarter, but because the handbook made "good"
concrete.

The model is that temp: enormously capable, zero context, no memory of your company
values (the goldfish law never left). The instruction is the handbook. Its sections:

| Handbook section | In the instruction | Why it earns its place |
| --- | --- | --- |
| **Role** | one sentence: who you are, for whom | anchors every other line |
| **Scope** | what you do — and the refusal script for what you don't | the #1 defense against confident nonsense |
| **Honesty rules** | never invent data; say "I can't see that" plainly | Principle 10, worn as persona |
| **Tone** | concrete adjectives + a length budget | "professional, warm, ≤3 sentences" beats "be nice" |
| **Examples (few-shot)** | 1–2 tiny perfect exchanges, when behavior is hard to describe | showing beats telling for format/tone edge cases |

And the anti-sections — things that must **stay out**:

- **Protocol** — output formats, "reply with ACTION:", JSON shapes. That is schema
  territory (Day 4's whole lesson; Day 12 does structured output properly).
- **Contradictions** — "be concise" + "always explain your full reasoning" forces the
  model to break one rule per answer, and *which* rule it breaks changes randomly. Every
  new line must be checked against the old ones.
- **Dead weight** — the instruction is re-sent on **every model call**, forever. A
  40-line instruction is a tax on every turn of every day (Day 24 puts numbers on this).
  If a line never changes an answer, it is not an instruction; it is a lucky charm.

💡 **Mental model: an instruction is an employee handbook, not a wish.** Wishes describe
the mood you want; handbooks define behavior you can *check*. If you can't imagine a test
that a line would pass or fail, the line isn't doing anything.

That last idea is the day's sharpest edge: **personas are tested, not admired.** For
every rule you write, design the probe message that would expose its absence. We run
three such probes in §4.

### ADK-03 — The mechanics: two fields, a template language, and a glass engine

**Two fields, two different readers.** ADK gives the agent both an `instruction` and a
`description`, and mixing them up is a real (and common) design bug:

| Field | Who actually reads it | Job |
| --- | --- | --- |
| `instruction` | **your own model**, every turn | how to behave |
| `description` | **other agents' models**, when deciding where to route work | what this agent is *for* |

Today `description` is one honest line. In Phase 8, when an orchestrator chooses between
`sutra_triage` and a researcher agent by reading their descriptions, that line becomes a
routing contract — write it as "what I do," never "how I do it."

**State templating** (verified 2026-08-18): the instruction string is not static text —
ADK substitutes session-state values into it at call time:

- `{customer_tier}` → replaced by `state["customer_tier"]`; **the turn errors if the
  key is missing** (§5 demonstrates this on purpose),
- `{customer_tier?}` → same, but a missing key is silently skipped instead of fatal,
- `{artifact.notes}` → injects the text of a stored artifact (artifacts are Day 18).

This is the bridge between Day 6 and Day 17 (session state): the handbook can have
**fill-in-the-blank fields** that the system — not the model — populates per
conversation. The instruction can also be a *function* returning a string (dynamic
instructions); we note it exists and leave it until a day needs it.

**The glass engine — `adk web`.** Launched from the repo root, it serves a developer UI
at `http://localhost:8000` (flags: `--port`, `--host`; auto-reload is on by default, so
editing `agent.py` hot-reloads the agent — perfect for today's persona iteration). What
it gives you (verified against the web-interface page):

| Panel | What you see | Day 3 ancestor |
| --- | --- | --- |
| Chat | the conversation, streamed | your terminal `print()`s |
| **Events** | every turn as structured records — user message, model response, and (from Day 10) each tool call and result | the `CALL:`/`RESULT:` audit lines |
| **State** | the session's state dict — viewable **and editable** live | (nothing — Day 17 builds this) |
| **Trace** | per-event timing: where the milliseconds went | (nothing — Phase 13 industrializes this) |
| Sessions | create/switch conversations | your `transcript = []` reset |

⚠️ Two standing warnings, straight from the docs: **`adk web` is a development tool, not
a production deployment** (Sutra's real API surface arrives on Day 85); and everything it
shows rides on the same 5 RPM free-tier quota — the UI makes calls feel free, and they
are not.

💡 **Mental model: `adk web` is Principle 12 with a screen** — "everything is a trace; if
it isn't observable, it didn't happen." From today on, "it feels wrong" is never a bug
report in this project. "Event 3 shows X" is.

## 5 · 💥 Failure lab — the fill-in-the-blank that wasn't filled

> 🎬 **The scene:** you learn about `{var}` templating and love it. Personalization,
> for free! You add one elegant line to the end of the handbook's Role section:
> `Today's triage focus: {triage_focus}.` — planning to set that state value "later,
> somehow" (state is Day 17's topic, after all).
> 😬 **The naive fix:** ship it. It's just a template variable; surely an unset variable
> renders as blank.
> 💥 **Why it fails:** send any message in `adk web`. The turn **errors** — ADK treats a
> missing `{triage_focus}` key as a hard failure, not an empty string (verified behavior:
> `{var}` is strict; only `{var?}` is optional). And notice *when* you find out: not at
> import, not at startup — at the first live turn, in front of the user. A typo'd
> variable name fails the same way, which is worse: the state key exists, the reference
> doesn't match, and the agent is down. Prove the fix: change it to `{triage_focus?}` —
> the turn now runs, silently skipping the blank. Then prove the *feature*: in the
> **State** panel, add `triage_focus = "login issues"` to the session state, send
> `What's today's focus?` — the agent answers from the injected value. The handbook just
> got its first working fill-in-the-blank.
> 💡 **The insight:** **a template variable is a contract with future state — `{var}`
> makes it a hard contract, `{var?}` a soft one. Choose per line, on purpose.** Hard for
> values the persona cannot function without (fail fast, loudly, at the boundary); soft
> for garnish. And never leave a hard contract dangling on a promise to "set it later" —
> later is where outages live.

Remove the experiment line before committing (or keep it as `{triage_focus?}` with a
comment saying why — your call, but make it a decision, not a leftover).

## 6 · 🎤 Interview corner

1. **"How do you write a good system prompt / instruction?"** — Like an employee
   handbook, not a wish list: role, hard scope with a refusal script, honesty rules,
   concrete tone with a length budget, and one or two few-shot examples where behavior
   is hard to describe. Just as important is what I keep *out*: output protocol belongs
   in schemas where it's machine-enforced, contradictions are randomized behavior, and
   every line is a per-turn token tax. My acceptance test for any line: name the probe
   message that would fail without it. If I can't, the line goes.
2. **"How do you *test* a persona?"** — Adversarial probes per handbook section, run
   after every instruction edit: a scope probe (ask it to promise a refund), an honesty
   probe (ask about data it can't see), and a happy-path probe (real work, checking tone
   and format). I iterate in ADK's dev UI with hot-reload — edit, probe, inspect the
   events — and later (Phase 12) the same probes graduate into an automated evalset, so
   persona regressions fail CI instead of surprising users.
3. **"Same field, two audiences: what's the difference between an agent's instruction
   and its description?"** — Different readers entirely. The instruction is read by the
   agent's own model on every turn — it shapes behavior. The description is read by
   *other* agents' models when routing — in a multi-agent system it's the line an
   orchestrator uses to decide whether to delegate here. So the instruction says "how to
   behave," the description says "what I'm for," and writing either for the wrong reader
   breaks either behavior or routing.
