## 1 · 🎬 Where we are — the story so far

Sutra's data boundary is now guarded (Day 40) and backed by real storage (Day 39). Every
tool the agents see has been reviewed, filtered, and pinned. So far, though, everything a
tool *returns* has one shape: text for the model to read.

Think about the approval moment coming in Phase 9. A human must decide: close ticket #4521
together with its three duplicates, or not? Today that decision would arrive as a paragraph
the model wrote, and the human would type "approve" into a chat box — free text, typo-prone,
un-auditable. What you actually want is a little panel: the four tickets listed, two
buttons, one click. The question is: *whose* panel? The chat client doesn't know about
tickets. Your server does — but servers don't have screens.

The 2026-07-28 ecosystem answers with **MCP Apps**: a tool can ship its own small HTML
interface, which the *host* renders in a locked sandbox next to the conversation. And
before that answer makes sense, you need the more basic machinery it rides on: how a
stateless server **declares what it can do** (capabilities), and why everything it will
ever show a client must be **declared up front** (templates) rather than improvised at
runtime. That's today: capabilities, declarations, and the first official MCP extension.

## 3 · 📚 Concepts

### MCP-18 — Capabilities: the declaration form

**The customs story.** A stateless world has no long conversation at the border — no "let's
get to know each other" handshake (that died with `initialize`). Instead, every server is
like a market stall with its licenses **posted on the wall**: *I serve tools. I serve
resources. I speak the tasks extension. Version 2026-07-28.* Two consequences:

1. **Discovery is a request, not a ceremony.** A client that wants the wall-poster up
   front calls the **`server/discover`** RPC — one self-contained request like any other.
   Two sides, two obligations, don't mix them up: **servers MUST implement
   `server/discover`** (Day 32 verified this against the live spec — sutra-mcp answers
   it), while **clients MAY skip calling it** and just call `tools/list`; nothing depends
   on having "introduced yourself" first (the release post's "not required" is about the
   *client's* side).
2. **Negotiation rides in the request.** Each request's `_meta` carries the client's
   protocol version and capabilities — including which **extensions** it speaks, by
   reverse-DNS name (`io.modelcontextprotocol/tasks`, `io.modelcontextprotocol/apps`,
   EMA). Server and client agree per-request, which is the only kind of agreement a
   stateless protocol can keep.

💡 **Mental model: old MCP negotiated like a phone call ("can you hear me? good, let's
talk"); new MCP negotiates like HTTP headers — every envelope says what dialect it speaks.**

### MCP-19 — Pre-declared templates: nothing improvised

Look at the pattern you've met three times this phase and once today:

| Where | What must be declared up front |
| --- | --- |
| Tools (Day 34) | name, description, schema — before any call |
| Cacheable lists (Day 40) | stable, deterministic catalogs a client can pin & diff |
| Tasks (Day 36) | the handle contract — state travels as explicit payload |
| **Apps (today)** | the **UI resource** (`ui://…`) a tool will render — registered as a resource before any tool call renders it |

That's not coincidence; it's the protocol's security stance: **a client should be able to
review everything a server will ever do to it, before anything runs.** For Apps
specifically, the tool's definition carries `_meta.ui.resourceUri` pointing at a `ui://`
resource the server registered up front — so a host can fetch, review, CSP-lock, and even
prefetch the HTML *before* the first render. An improvised, per-call HTML blob would be
unreviewable by construction; a declared template is just another catalog entry your
Day 40 discipline already knows how to pin.

For `sutra-mcp` the takeaway is a posture, not code: what our server declares (tools,
resources, prompts, tasks) is exactly what a stranger's client may review — so the
declarations are part of the public contract, and changing them is a versioned event
(Day 45's audit checks this).

### MCP-29 — MCP Apps: the tool that brings its own window

The moving parts, from the official build guide (all names verified 2026-08-18):

| Part | What it is | Concrete detail |
| --- | --- | --- |
| The UI resource | an HTML page the server serves as an MCP **resource** | URI scheme `ui://` (path is yours); mime `text/html;profile=mcp-app` |
| The link | the tool points at its UI | tool `_meta: { ui: { resourceUri: "ui://…" } }` |
| The stage | where the host renders it | **sandboxed iframe**, deny-by-default CSP — no network calls out, assets bundled into the HTML |
| The bridge | how the page talks | the `App` class: `app.connect()`, `app.ontoolresult` (host pushes the tool's result in), `app.callServerTool()` (page calls tools back through the host) |
| The SDK | server + client helpers | npm `@modelcontextprotocol/ext-apps` — `registerAppTool`, `registerAppResource`, `RESOURCE_MIME_TYPE` |

Read the bridge row twice, because it is the security story: the iframe cannot fetch, phone
home, or touch the page around it. Its **only** wire to the world is JSON-RPC through the
host — which means every click that becomes a tool call passes through the same channel,
same policy, same audit trail as the model's own tool calls. A button is just another way
to fill Day 4's form.

🎬 One sentence of ecosystem honesty: hosts must *choose* to support Apps (Claude web/
desktop do; the `ext-apps` repo ships a free local `basic-host` for development). A server
that ships UI degrades gracefully — hosts that don't render it still get the tool's normal
text result. Sutra-side, that means UI is always an *enhancement*, never the only path —
which conveniently is also the accessibility answer.

```typescript
// server.ts — the three moves that make a tool an "app" (official example, 2026-08-18)
import { registerAppTool, registerAppResource, RESOURCE_MIME_TYPE }
  from "@modelcontextprotocol/ext-apps/server";

const resourceUri = "ui://get-time/mcp-app.html";     // 1) a ui:// address, declared

registerAppTool(server, "get-time", {
  title: "Get Time",
  inputSchema: {},
  _meta: { ui: { resourceUri } },                     // 2) the tool points at its UI
}, async () => ({ content: [{ type: "text", text: new Date().toISOString() }] }));
                                                      //    ^ normal text result still exists!
registerAppResource(server, resourceUri, resourceUri,
  { mimeType: RESOURCE_MIME_TYPE },                   // 3) the HTML served as a resource,
  async () => ({ contents: [{ uri: resourceUri,      //    mime text/html;profile=mcp-app
                              mimeType: RESOURCE_MIME_TYPE,
                              text: bundledHtml }] }));
```

And the page's side of the bridge:

```typescript
// src/mcp-app.ts — the page can ONLY talk through the host
const app = new App({ name: "Get Time App", version: "1.0.0" });
app.connect();                                        // open the JSON-RPC bridge
app.ontoolresult = (r) => render(r);                  // host pushes the tool result in
button.onclick = () => app.callServerTool({           // clicks become tool calls,
  name: "get-time", arguments: {} });                 // same channel, same audit trail
```

## 5 · 💥 Failure lab — the improvised interface

> 🎬 **The scene:** a teammate prototypes a slicker approval panel. To iterate fast, their
> tool builds the HTML *in the tool result* — fresh markup every call, styled by whatever
> the model decided to interpolate. "Ship it; it's just HTML."
> 😬 **The naive fix:** render whatever HTML a tool result carries. It works in the demo.
> 💥 **Why it fails:** you've reinvented the poisoned description, but executable. Ticket
> #4633's body says "Password reset email never arrives" — now imagine a body containing
> `<button onclick="…">Approve all</button>`-shaped markup that flows model → tool result →
> your improvised renderer. Nothing was declared, so nothing was reviewed, so the host is
> executing attacker-influenced UI next to a human's Approve button. The 2026 design makes
> this *unspeakable*: hosts render only **pre-declared `ui://` templates** with the mcp-app
> mime profile, in a deny-by-default sandbox; data flows into that fixed template through
> the bridge, as data. Improvised markup has no lane to arrive in.
> 💡 **The insight:** **declare templates, flow data — never flow templates.** It's the
> same sentence as Day 4 ("prose is a request; a form is a guarantee") with pixels: the
> template is the form, the tool result fills its boxes, and the human's click is
> trustworthy because the thing they clicked was reviewed before it ever rendered.

## 6 · 🎤 Interview corner

1. **"How does capability negotiation work in stateless MCP?"** — There's no handshake to
   negotiate in. A server's capabilities are discoverable via an optional `server/discover`
   request, and every ordinary request carries the client's protocol version and
   capabilities — including extensions by reverse-DNS name — in `_meta`, so both sides
   agree per-request. Extensions like Tasks and Apps are versioned capabilities on their
   own timelines rather than core-spec bloat; that's the 2026-07-28 extensions framework.
2. **"A tool wants to show a human an interactive UI. Walk me through doing that safely."**
   — MCP Apps pattern: the server registers the UI as a pre-declared `ui://` resource with
   the mcp-app mime profile; the tool's `_meta` points at it; the host fetches, reviews,
   and renders it in a sandboxed iframe with deny-by-default CSP; the page's only channel
   is the host bridge, so clicks become normal, filtered, audited tool calls. Two rules
   carry the safety: templates are declared and pinned, and data flows into templates —
   never markup out of results.
3. **"Why did you not build your approval UI as part of your own client app?"** — Because
   the server owns the domain knowledge (what a duplicate ticket is), and hosts change.
   Shipping the panel as an MCP App means one reviewed template works in any Apps-capable
   host, degrades to text elicitation elsewhere, and inherits the protocol's audit trail —
   versus a bespoke UI I'd re-secure and re-build per host.
