## 1 · 🎬 Where we are — the story so far

Day 99 taught the idea: infrastructure as a file, a plan you read before you trust, and a drift
lab that showed what happens when the cloud and the file disagree. Day 100 moved Sutra to Azure
and made you build your own container to get there.

Today those two meet. On paper it's a translation exercise — swap `google_cloud_run_v2_service`
for `azurerm_container_app`, swap `min_instance_count` for `min_replicas`, done before lunch.

It isn't, and the reason is worth the day. Day 99 ended with a small victory that nobody dwelt
on: the API key never entered Terraform's state, because Cloud Run takes a *reference* to a
secret rather than a value. Azure's Container App resource takes the **value**. Terraform writes
what it manages into state, in plaintext, by design. So today's config does something Day 99's
config specifically did not — and the widely-recommended fix for it doesn't work.

## 3 · 📚 Concepts

### DEPLOY-06a — The `features {}` block, and why an empty block is mandatory

```hcl
provider "azurerm" {
  features {}
}
```

⚠️ That empty `features {}` block is **required**. Omit it and `terraform init`/`plan` fails with
an error that reads like a schema complaint rather than "you forgot a mandatory block." It exists
so the provider can expose opt-in behaviour toggles (how aggressively to purge soft-deleted Key
Vaults, whether to delete OS disks with a VM, and so on) — and Azure's team chose to make the
block mandatory even when empty, so that every config has a place for those switches.

📌 Worth knowing because it's the single most common first-run stumble on the Azure provider, and
because the toggles inside it are genuinely cost-relevant once a config grows: several of them
control whether Terraform leaves things behind on destroy.

### DEPLOY-06b — 📌 The real difference: reference vs value

This is the concept the whole day turns on.

| | Day 099 — GCP | Day 102 — Azure |
| --- | --- | --- |
| Resource | `google_cloud_run_v2_service` | `azurerm_container_app` |
| How the key is supplied | `value_source.secret_key_ref` → the **name** of a Secret Manager secret | `secret { name, value }` → the **value itself**, inline in the config |
| Where the secret lives | Secret Manager; Terraform never sees it | Terraform's config *and* its state |
| `grep` the state file | no match | **match** |

💡 **Mental model: Terraform stores everything it manages, and it can only avoid storing a secret
if the resource lets it manage a *pointer* instead of the thing.** Cloud Run's API accepts a
pointer. The Container App resource's `secret` block accepts a value. That's not Terraform being
careless; it's the shape of the underlying API surfacing in the state file.

⚠️ **And the fix everyone reaches for does not fix this.** Marking a variable `sensitive = true`
stops Terraform printing it in `plan`/`apply` output and in `terraform output`. It does **not**
redact it from `terraform.tfstate`. State is plaintext JSON. `sensitive` is a *console* feature,
not a *storage* feature — and mistaking one for the other is how a secret ends up in a git repo
belonging to someone who genuinely believed they'd handled it.

### DEPLOY-06c — So what *is* the honest handling?

Three options, in increasing order of effort, with the trade-off stated rather than the "best
practice" asserted:

1. **Treat state as a secret, unconditionally.** It already is one. `.gitignore` from Day 099 §3
   covers `*.tfstate` and `*.tfvars`; local state on an encrypted disk is a reasonable posture for
   a solo learning project, and it costs nothing. ⚠️ The failure mode is human: a `git add -f`, a
   backup script, a screen share. This is what today actually does, with eyes open.
2. **Keep the secret out of Terraform entirely.** Set it out-of-band
   (`az containerapp secret set ...`, as Day 100 §4 Step 5 did) and tell Terraform not to manage
   that attribute — `lifecycle { ignore_changes = [secret] }`. ⚠️ Cost: Terraform no longer
   describes the whole resource, so `main.tf` stops being a complete answer to "what does this
   deployment look like" — you've traded one honesty problem for another.
3. **A managed secret store with a Terraform data source** (Azure Key Vault). This is what a
   funded project does. ⚠️ It is out of scope here for a reason worth stating plainly rather than
   hand-waving: Key Vault is a separate service with its own pricing (per-operation, small but
   not $0), and Addendum 02's bar is a genuine free floor, not "cheap." Documented, not adopted.

📌 **The generalisable lesson:** "where does this secret end up at rest?" is a question you have
to ask *per provider, per resource*, because the answer changed between two clouds doing the
identical job, four days apart, in this same track.

### DEPLOY-06d — Why AKS is parked, in one table

`03_azure.md` §4, verified 2026-08-21, quoting Azure: *"AKS cluster management is free; you'll
incur a charge for resources consumed by nodes."*

| What | Free? | What actually bills |
| --- | --- | --- |
| AKS control plane / cluster management | ✅ | — |
| Node VMs (e.g. `Standard_B2s`) | ❌ | ordinary Azure VMs, billed per hour they exist |
| Load balancer, managed disks, egress | ❌ | the orphan neighbours `00_stay_free_safety.md` §5 warns about |

💡 **This is structurally identical to GKE** (Day 099 §3's DEPLOY-03d) and structurally *unlike*
AWS EKS, which charges for the control plane itself — Day 105's subject. Three clouds, three
positions on the same question, and the useful interview answer is being able to say which is
which and why it matters.

**Step 2 — write the Azure config.**

```powershell
New-Item -ItemType Directory -Force infra/azure | Out-Null
```

`infra/azure/main.tf`:

```hcl
terraform {
  required_version = ">= 1.9"
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
  }
}

provider "azurerm" {
  features {}          # DEPLOY-06a: mandatory even when empty
}

resource "azurerm_resource_group" "sutra" {
  name     = "sutra-tf-rg"
  location = var.location
}

resource "azurerm_container_app_environment" "sutra" {
  name                = "sutra-tf-env"
  resource_group_name = azurerm_resource_group.sutra.name
  location            = azurerm_resource_group.sutra.location
}

resource "azurerm_container_app" "sutra" {
  name                         = "sutra-agent"
  container_app_environment_id = azurerm_container_app_environment.sutra.id
  resource_group_name          = azurerm_resource_group.sutra.name
  revision_mode                = "Single"

  # DEPLOY-06b: this is a VALUE, not a reference. It lands in terraform.tfstate.
  secret {
    name  = "google-api-key"
    value = var.google_api_key
  }

  template {
    min_replicas = 0     # the line that keeps this free — Day 100's DEPLOY-04a
    max_replicas = 2

    container {
      name   = "sutra-agent"
      image  = var.image
      cpu    = 0.5       # one of the Consumption plan's exact pairs (Day 100 DEPLOY-04c)
      memory = "1Gi"

      env {
        name  = "GOOGLE_GENAI_USE_VERTEXAI"
        value = "FALSE"
      }

      env {
        name        = "GOOGLE_API_KEY"
        secret_name = "google-api-key"
      }
    }
  }

  ingress {
    external_enabled = true
    target_port      = 8000     # must match what Dockerfile.adk binds
    traffic_weight {
      percentage      = 100
      latest_revision = true
    }
  }
}
```

| Block | What it does | Why it's written this way |
| --- | --- | --- |
| `azurerm_resource_group` | Azure's "delete everything at once" unit | makes Step 8's teardown a single, reliable operation — Azure's best cleanup primitive |
| `azurerm_container_app_environment` | the shared networking/logging boundary a Container App must live in | Day 100 §4 Step 4 created this by hand; here it's a dependency Terraform orders for you |
| `revision_mode = "Single"` | one active revision at a time | the simple model; multi-revision traffic splitting is a deploy strategy this day doesn't need |
| `secret { value = ... }` | supplies the key to the platform's secret store | ⚠️ DEPLOY-06b — a **value**, so it enters state. §5 is about this |
| `env { secret_name = ... }` | the container reads the key via the secret store, not as a literal env value | the *deployed resource* is still correct; the exposure is in Terraform's own state, not in Azure |
| `min_replicas = 0` | scale to zero | Day 100 computed why: ~100 replica-hours/month at this size, against a ~730-hour month |
| `traffic_weight` | routes 100% to the newest revision | ⚠️ required — omit it and `apply` fails; there's no sensible default for "which revision serves traffic" |

## 5 · 💥 Failure lab — the key you thought you'd handled

> 🎬 **The scene:** Step 5 just showed `secretRef` in the deployed app's environment. You marked
> the variable `sensitive = true`. `terraform apply` printed `(sensitive value)` instead of the
> key. Every signal you've been given says this is handled. So you do what Day 099 §4 Step 6 did
> — the same grep, the same discipline, one cloud over:
>
> ```powershell
> Select-String -Path infra/azure/terraform.tfstate -Pattern "AIza" -Quiet
> ```
>
> 💥 **It prints `True`.** On Day 099 the identical command printed `False`.
>
> 😬 **The naive reading:** "`sensitive = true` must not have applied — I'll double-check the
> variable, maybe mark the output sensitive too, maybe upgrade the provider."
>
> 💥 **Why it fails, mechanically:** `sensitive` has nothing to do with storage. It is a
> **display** attribute — it redacts a value from `plan` output, `apply` output, and
> `terraform output`. `terraform.tfstate` is plaintext JSON containing every attribute of every
> managed resource, because that is what lets Terraform diff and destroy them. The
> `azurerm_container_app` resource has a `secret` block that takes a **value**, so the value is an
> attribute, so it is in state. Nothing malfunctioned. The tool did exactly what it documents.
>
> 💡 **The insight: the console and the disk are different threat surfaces, and one tool's flag
> covers only the first.** Day 099's config avoided this *not* because it was written more
> carefully, but because Cloud Run's API happens to accept a pointer where Azure's accepts a
> value. **The same engineer, the same discipline, the same day of the week — and a different
> outcome, decided by the resource schema.** Which is why "is my secret in state?" is a question
> to re-ask per provider rather than answer once.

**What to actually do — and note that the first line is the one that matters most today:**

```powershell
# 1. Confirm the blast radius is contained: is state in git, or anywhere it could reach git?
git check-ignore -v infra/azure/terraform.tfstate    # expect: a matching .gitignore rule
git log --all --oneline -- "*.tfstate"               # expect: no output, ever

# 2. If it was EVER committed, the key is compromised — rotate it, don't just delete the file.
#    A key in git history is a published key. Regenerate at aistudio.google.com and update .env.
```

✅ *Verify:* `git check-ignore` names the rule that's protecting you, and the `git log` search
returns nothing. **That pair, not the `sensitive` flag, is what is actually keeping this key
safe.**

Then pick your posture from DEPLOY-06c deliberately and write it in the tracker. For this
project, option 1 — *treat state as a secret, unconditionally* — is the honest choice: it costs
nothing, it's already true, and pretending otherwise is how the mistake happens. What you must
not do is leave believing `sensitive = true` solved it.

## 6 · 🅿️ AKS — documented, costed, and never run

> **This section has never been executed, and must not be, until the trigger condition at the end
> is met.** Same discipline as [Day 087](day_087.md) and [Day 099](day_099.md) §6.

**Why it's parked:** the control plane is free; every node is an ordinary billed VM (DEPLOY-06d).
Azure gives you the orchestrator and charges for the computer — which is the same deal GKE offers
and a *better* deal than EKS (Day 105), and still not a free one.

**What the commands would be** (from `03_azure.md` §4, reference only):

```powershell
# NOT RUN. Each node is a billed Azure VM for every hour it exists.
az aks create --resource-group sutra-tf-rg --name sutra-aks `
  --node-count 1 --node-vm-size Standard_B2s --generate-ssh-keys
az aks get-credentials --resource-group sutra-tf-rg --name sutra-aks
kubectl get nodes
az aks delete --resource-group sutra-tf-rg --name sutra-aks --yes --no-wait
```

⚠️ **The orphan risk is higher here than anywhere else in this track.** An AKS cluster creates a
*second, hidden* resource group (conventionally `MC_<rg>_<cluster>_<region>`) holding the node VMs,
disks, and a load balancer. Deleting the cluster normally removes it — but deleting the *visible*
resource group by hand, or a half-failed delete, can leave that node group running. `az group
delete` on the group you know about is not automatically sufficient. This is
`00_stay_free_safety.md` §5's orphan pattern in its most expensive form.

**Re-verification command, if this is ever revisited:**

```powershell
Start-Process "https://azure.microsoft.com/en-us/pricing/details/kubernetes-service/"
az aks list --query "[].{name:name, rg:resourceGroup, nodes:agentPoolProfiles[0].count}" -o table
az group list --query "[?starts_with(name,'MC_')].name" -o tsv    # the hidden node groups
```

**Trigger condition:** AKS stops being parked when *either* (a) this project has a funded billing
account with a signed-off monthly budget **and** a stated requirement Kubernetes serves that
`kind` locally cannot, **or** (b) Azure begins offering a genuine free node allowance, not just
a free control plane. Neither was true on 2026-08-21. Until then the Kubernetes story is
[Day 088](day_088.md)'s `kind` — same API, same manifests, genuinely $0.

## 7 · 🎤 Interview corner

1. **"Same infrastructure, two clouds, one Terraform. What actually differed?"** — Less than
   expected structurally, more than expected in consequences. The resource names and the
   scale-to-zero attribute translated almost directly. What didn't translate was secret handling:
   Cloud Run's API takes a *reference* to Secret Manager, so the key never entered Terraform
   state; Azure's Container App resource takes the secret's *value*, so it does. I found it by
   running the same grep on both state files and getting different answers.
2. **"Does `sensitive = true` protect a secret in Terraform?"** — Only from your terminal. It
   redacts values from plan, apply, and output. State is plaintext JSON with every managed
   attribute in it, and `sensitive` doesn't touch that. The real controls are keeping state out
   of version control, treating the state file itself as a credential, and — if it ever did reach
   a repo — rotating the key rather than deleting the file, because history is forever.
3. **"AKS, GKE, EKS — compare the free tiers."** — GKE and AKS both give you the control plane
   free and bill the nodes; EKS bills $0.10/hour for the control plane itself, with no free tier
   at any level. So on GCP and Azure a Kubernetes experiment costs whatever the nodes cost, and on
   AWS it costs that *plus* about $73/month for the privilege. For a zero-budget project all three
   are out, which is why I documented them to be run-ready and ran `kind` locally instead.
4. **"What's the most dangerous thing about `terraform destroy` on Azure?"** — What it doesn't
   reach. AKS in particular provisions a second, hidden `MC_*` resource group for its nodes and
   load balancer; if a delete half-fails or someone removes the visible group by hand, the
   expensive half can survive. So my teardown check isn't "did destroy succeed," it's an explicit
   query for leftovers — resource groups, App Service plans, registries — because the orphan is
   always the thing you didn't create directly.
