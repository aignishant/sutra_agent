## 3 · 📚 Concepts

### MCP-01 — What MCP is, and why it is Sutra's data boundary

**The story: the universal wall socket.** Before electrical standards, every appliance
maker invented its own plug. Buying a new lamp meant rewiring your wall. Then someone
standardized the socket — and suddenly *any* lamp works in *any* home, and lamp makers and
house builders stopped needing to know each other.

Before MCP, every AI app that wanted tools invented its own plug. A weather tool written
for one chat app had to be rewritten for the next one. MCP is the standardized socket:

| The story | Our system | Technical name |
| --- | --- | --- |
| The wall socket standard | The protocol: JSON-RPC messages in a fixed shape | **MCP** (Model Context Protocol) |
| A home's sockets | The AI app that wants tools/data (Sutra, Claude Desktop, an IDE) | the **host**, holding one **client** per server |
| An appliance | A program offering tools, data, or prompt templates | an MCP **server** |
| Kinds of appliances | What a server can offer | **tools** (functions), **resources** (data to read), **prompts** (templates) |

💡 **Mental model: MCP is USB-C for AI context.** One connector; any data source; either
side can be swapped without rewiring the other.

Why does Sutra *bet its data boundary* on this? Two reasons you can defend in an interview:

1. **Decoupling.** When the ticket archive moves from a Python dict (today) to SQLite
   (Day 39) to some future cloud database, agents don't change — only the server behind the
   socket does. The boundary is the contract.
2. **Security has one gate.** If every data access goes through MCP, then allowlists,
   filtering, and audit (Days 40, 45) have exactly one place to live. A boundary you can
   point at is a boundary you can guard (Principle 13).

You already know the *shape* of what travels through the socket: tools declared with JSON
Schema, calls with `name` + `arguments`, results going back — Day 4's material, now spoken
between processes instead of inside one. That is not a coincidence; it is why the plan made
you hand-roll it first.

### MCP-26 — The 2026-07-28 stateless core

> 💡 **The one-sentence version (Addendum 01, still true):** old MCP was a **phone call** —
> you dial (`initialize`), stay connected (the session), and hang up. New MCP is **the
> web** — every request is self-contained, any server instance can answer it, and nothing
> depends on a held connection.

**The story of why.** Imagine a call center. The old protocol was: you call, an operator
answers, you introduce yourself ("I speak protocol version X, I can do Y"), she writes it
on a sticky note, and *for the rest of the call she remembers you*. Cozy — until the call
center grows to 3 operators behind one phone number. Your next question lands on operator
2, who has no sticky note, and the call fails. The fix used to be "sticky sessions": route
this caller to that operator, forever. Load balancers hate it; serverless platforms
(Cloud Run scaling 0→3→0) make it nearly impossible.

The 2026-07-28 revision fires the sticky note. Now every message is a **letter that carries
its own envelope**: who you are, what version you speak, what you can do — all inside every
single request. Any operator can open any letter. Concretely, four mechanisms (each with
its SEP — the spec's numbered change proposals — so you can cite them):

1. **No handshake (SEP-2575).** `initialize`/`notifications/initialized` are *gone*. Every
   request carries, inside a `_meta` block: `io.modelcontextprotocol/protocolVersion`,
   `io.modelcontextprotocol/clientCapabilities`, and (SHOULD) `…/clientInfo`. A new RPC,
   **`server/discover`**, is REQUIRED on servers — clients MAY call it up front to learn
   supported versions and capabilities, but they don't have to.
2. **Headers for the mail sorters (SEP-2243).** Streamable HTTP requests MUST carry
   `MCP-Protocol-Version`, `Mcp-Method` (the JSON-RPC method), and — for `tools/call`,
   `resources/read`, `prompts/get` — `Mcp-Name` (the tool name or URI). Why duplicate what
   is in the body? So load balancers can route *without parsing JSON*. Addendum 01's
   example stands: send every `search_tickets` call to a dedicated pool, decided at the
   HTTP layer. Headers MUST match the body — a mismatch is rejected with error `-32020`
   (`HeaderMismatch`), because a router trusting one value while the server executes
   another is a security hole.
3. **State became explicit handles (SEP-2567).** Servers that need memory across calls
   mint a **handle** (an opaque string) and hand it back *in the payload*; the client
   passes it into the next call as an ordinary argument. State travels in the letters, not
   in the phone line. (Day 36 builds this with our own hands.)
4. **Lists became cacheable (SEP-2549).** `tools/list` & friends no longer vary
   per-connection, MUST return `ttlMs` (freshness hint) and `cacheScope`
   (`"public"`/`"private"`), and SHOULD list tools in deterministic order — so clients and
   even shared proxies can cache them, and LLM prompt caches hit more often.

*Concrete example of why you care:* Day 43 deploys `sutra-mcp` "Cloud-Run-shaped" — three
interchangeable containers behind one URL. Under the old spec that needed session
affinity machinery. Under the new spec it needs **nothing**: statelessness is not a mode
you enable, it is the architecture (exactly the reframe Addendum 01 promised for Day 43).

**What you must still recognize in the wild:** servers built on 2025-era revisions still
speak `initialize`, hold sessions via an `Mcp-Session-Id` header, and push server-initiated
requests over SSE streams. The spec defines exact fallback rules (a modern client tries a
modern request first; a legacy-shaped failure means "fall back to `initialize`"). You will
meet such servers during audits (Day 45) — history you can read, not history you write.

### MCP-32 — Governance & the registry: who owns the socket?

**The story.** Betting your house's wiring on a socket standard is only safe if no single
appliance company owns the standard. In December 2025 (2025-12-09), Anthropic donated MCP
to the newly formed **Agentic AI Foundation (AAIF)** under the **Linux Foundation** — the
same neutral home that hosts Kubernetes. MCP's fellow inaugural projects: **goose** (an
open agent) and **AGENTS.md** (the repo-instructions convention — cousin of our own
CLAUDE.md). Platinum members: AWS, Anthropic, Block, Bloomberg, Cloudflare, Google,
Microsoft, OpenAI — i.e., *every* major AI vendor, including direct competitors, funding
one protocol.

🎤 The interview line (Addendum 01, kept): *"MCP is vendor-neutral now — that's why betting
Sutra's data boundary on it is safe."*

And discovery has an official answer: the **MCP Registry** at
`registry.modelcontextprotocol.io` — an app store-like catalog of public servers with a
plain REST API (`/v0/servers`). Server names use reverse-DNS namespaces tied to verified
domains/GitHub accounts (`io.github.someone/their-server`), so a name proves its publisher.
Community sub-registries can mirror it. You query it live in Step 3 — and Day 45's audit
will ask of every server Sutra uses: *where did this come from, and who published it?*
(the same provenance discipline `SKILL_PROVENANCE.md` already taught you for skills).

## 5 · 💥 Failure lab — the tutorial from four months ago

> 🎬 **The scene:** it is Day 34 and you want a head start, so tonight you google "MCP
> python server tutorial". The top results are excellent, detailed — and written in early
> 2026. They open with a session handshake: the client sends `initialize`, waits for
> `notifications/initialized`, and stores the session ID for every later call.
> 😬 **The naive fix:** follow it — it has thousands of upvotes, surely it's right.
> 💥 **Why it fails:** you would be hand-building the exact machinery the protocol just
> deleted. Against a modern server, there is no handshake to complete; against a modern
> client, your server waits for an `initialize` that never comes. Worse, the failure is
> *quiet* — both sides just seem to hang or reject — because each is speaking a different
> era of the same protocol name. This is the ADK-1.x-tutorial trap (Day 5) wearing a
> network costume, and it bit within *weeks* of the revision, not years.
> 💡 **The insight:** **in fast-moving protocols, the date on the tutorial is part of the
> tutorial.** Check the spec revision a document assumes before trusting one line of it.
> The spec's own backward-compatibility section tells you how modern code *detects* the old
> era and falls back deliberately — recognition is a feature; imitation is a bug. (This is
> Principle 14 as a reading habit, and it is why every Sutra doc names the pages it
> checked, with dates.)

Observed today, not just asserted: in Step 2 you read the changelog line that removes
`initialize` — so you have seen, in the primary source, exactly which sentence makes those
tutorials historical.

## 6 · 🎤 Interview corner

1. **"What is MCP, and why would you build a product boundary on it?"** — A vendor-neutral
   protocol that gives AI apps one standard socket for tools, resources, and prompts —
   USB-C for context. I'd build on it for two reasons: decoupling (my agents don't change
   when a data source's implementation changes — the server behind the socket does) and
   governance (since Dec 2025 it's a Linux Foundation project under the Agentic AI
   Foundation, with every major vendor as a member — no single company can yank the
   standard). In Sutra, every data source is an MCP server, which also gives security
   exactly one gate to guard.
2. **"What did the 2026-07-28 revision actually change?"** — It made the protocol
   stateless: the `initialize` handshake and protocol-level sessions are gone; every
   request self-carries its version and capabilities in `_meta`, with `server/discover` as
   an optional up-front probe. Method and tool names are mirrored into `Mcp-Method`/
   `Mcp-Name` HTTP headers so infrastructure can route without parsing bodies — with
   mandatory header-body match validation. Cross-call state became explicit server-minted
   handles in the payload, and list endpoints became cacheable (`ttlMs`, `cacheScope`).
   One sentence: old MCP was a phone call; new MCP is the web.
3. **"Why did they do it — what breaks with sessions?"** — Horizontal scaling. A session
   pinned to the instance that did your handshake forces sticky routing; autoscalers and
   serverless platforms punish that. Stateless requests mean any replica answers any
   request — the same reason the web itself went stateless. The lesson generalizes: any
   protocol that holds per-client state in the connection will fight your infrastructure.
