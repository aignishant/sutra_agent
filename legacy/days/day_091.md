## 1 · 🎬 Where we are — the story so far

Ninety days in, Sutra can do the hard part. It triages a ticket, consults an archive
behind a data boundary, escalates to a human when the policy table says so, survives being
killed mid-run, refuses a prompt injection, proves who is calling, and shows you the whole
thing as a trace tree.

And nobody can use it. Every request Sutra has ever handled arrived because *you* typed it
— `adk run`, a curl, a test fixture. The system has no mouth and no ears in any room where
support work actually happens. This is not a small remaining task; it is the difference
between a project and a tool, and it is the single most common thing missing from
impressive agent demos.

Today asks the plainest question in the whole plan: **where does work come from, and where
does the answer go back to?** You will answer it once properly — a real intake surface,
built or precisely specified — and then survey the field so you can say what else exists
and what it would cost, without pretending to have built it.

## 3 · 📚 Concepts

### AG-30 — an integration is a promise, and the promise costs more than the code

**The story.** A café decides to take phone orders as well as counter orders. The phone
costs almost nothing. What costs is everything the phone *implies*: someone must hear it
over the grinder, orders arrive mid-conversation instead of one at a time, the caller
can't see the pastry case so they ask questions the counter never asks, and once the
number is printed on the window you can never quietly stop answering it.

Integrations are the same shape. `SlackRunner(runner, slack_app)` is two lines. What those
two lines commit you to:

| The implied promise | Why it is not free |
| --- | --- |
| **Availability** — the bot is in the workspace, so it is expected to answer | Sutra's free-tier lane is ~5 RPM; a busy channel is not |
| **Latency** — chat sets an expectation of seconds | a full triage with escalation takes longer than a human waits before re-asking |
| **Context** — people reply in threads, edit messages, and mean "it" | Days 8–10's context engineering assumed one clean request |
| **Audience** — anyone in the channel can talk to it | Day 90's identity work now has to map Slack users to principals |
| **Permanence** — removing a bot people rely on is a political act | the exit cost is social, not technical |

💡 **Mental model: the integration is the cheap part; the *contract* is the expensive
part.** Before wiring any surface, write the four lines of that contract — who may ask,
how fast you answer, what you do when you can't, and how you say no. If you cannot write
them, you are not ready to connect it.

### ADK-72 — Slack, and why it is Socket Mode

`adk.dev/integrations/slack/` (read 2026-08-20) — the exact surface:

```python
from google.adk.agents import Agent
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.adk.integrations.slack import SlackRunner
from slack_bolt.app.async_app import AsyncApp

runner = Runner(app_name="slack_agent", agent=root_agent,
                session_service=InMemorySessionService(),
                auto_create_session=True)
slack_app = AsyncApp(token=os.environ["SLACK_BOT_TOKEN"])
slack_runner = SlackRunner(runner, slack_app)
asyncio.run(slack_runner.start(os.environ["SLACK_APP_TOKEN"]))
```

Install: `pip install "google-adk[slack]"` (for this repo: `uv add "google-adk[slack]"`).

| Credential | Scopes | Env var |
| --- | --- | --- |
| Bot User OAuth Token (`xoxb-…`) | `app_mentions:read`, `chat:write`, `im:history` | `SLACK_BOT_TOKEN` |
| App-Level Token (`xapp-…`) | `connections:write` | `SLACK_APP_TOKEN` |

**Socket Mode, not the Events API** — and this is the detail worth understanding rather
than copying. The Events API needs Slack to POST to a **public HTTPS URL you host**.
Socket Mode has your process open an outbound websocket to Slack instead.

> 🎬 **The scene:** you want a Slack bot on your laptop. The Events API needs a public
> endpoint, so you reach for a tunnel (ngrok and friends) — a public URL forwarding
> straight into your machine.
> 😬 **The naive fix:** "it's just for development, the URL is random, nobody will find
> it."
> 💥 **Why it fails:** random URLs are found — scanners sweep tunnel providers' domains
> continuously. And what is behind that URL, on this project, is an agent with an archive,
> tools, and (until Day 90) no inbound authentication whatsoever. Day 88's rule about
> binding to `localhost` was not about ports; it was about not putting an unauthenticated
> agent on the internet.
> 💡 **The insight: prefer outbound connections to inbound endpoints.** Socket Mode
> reverses the direction, so there is no listener to attack, no tunnel, no TLS to manage,
> and it works behind any NAT. The same reasoning gives Day 88's MCP sidecar its
> loopback-only address. **Direction of connection is a security property.**

⚠️ Two things in that quoted snippet are **wrong for Sutra**, and spotting them is the
exercise:

1. `InMemorySessionService` — Day 47 moved Sutra to `DatabaseSessionService` precisely so
   conversations survive a restart. A chat bot losing the thread mid-conversation because
   you restarted the process is the most visible possible regression. Use the real one.
2. `auto_create_session=True` with a bare `Runner` skips the plugin stack. Sutra's runner
   carries five plugins in a deliberate order (Tracing → DataBoundary → QuotaRouter →
   Permission → Guardrail, Day 84). An intake surface that constructs its own naked
   `Runner` **bypasses every guardrail in the project** — including the injection scanner,
   on the one surface where strangers type. Build the `Runner` the way `sutra/api.py` does,
   then hand it to `SlackRunner`.

📌 That second one is the day's most transferable lesson: **integration snippets are
minimal by design, and "minimal" means every safety property you added is absent.** Diff
any vendor snippet against your own composition root before running it.

```python
# sutra/intake.py
@dataclass(frozen=True)
class IntakeRequest:
    """One unit of work arriving from anywhere.

    Every intake surface (Slack, email, HTTP, the scheduler) converts its own
    payload into this, and nothing downstream knows which surface it came from.

    Example:
        >>> IntakeRequest(text="printer is on fire", principal="slack:U123",
        ...               thread_key="C99:1724..", surface="slack", reply=post_to_thread)
    """
    text: str
    principal: str          # Day 90: an identifier, never a credential
    thread_key: str         # stable conversation id → the ADK session id
    surface: str            # for logs, quota attribution and rate limits
    reply: Callable[[str], Awaitable[None]]   # how this surface says things back
```

## 5 · 💥 Failure lab — the bot that answered everybody

> 🎬 **The scene:** the bot works, and it is delightful. You invite a colleague to try it.
> They invite the channel. By the afternoon nine people have discovered that asking Sutra
> is faster than searching, and the channel is busy.
>
> Then it degrades — not dramatically, which is what makes it interesting. Replies get
> slower. Some questions get answered twice. One person's follow-up gets answered with
> someone else's context. And `logs/quota.json` says the day's free-tier budget went at
> 11:40am, so every afternoon reply is a backoff-delayed apology.
>
> 😬 **The naive fix:** add a queue and raise the backoff cap. It *is* a throughput
> problem, and a queue *is* the right shape for throughput problems.
>
> 💥 **Why it fails.** A queue makes the symptom orderly without touching any of the three
> actual causes, and two of them are correctness bugs wearing a performance costume.
>
> **(1) Fan-in versus a fixed rate.** Every previous surface had exactly one user: you.
> Sutra's ~5 RPM lane was never a constraint because your typing was the bottleneck. A
> channel has no such bottleneck — arrival rate is now *other people's* and it is unbounded.
> A queue converts a burst into a wait; it does not create capacity. The honest answers are
> a **per-surface admission cap** ("this bot answers N questions an hour; I'm at capacity,
> ask again after X") and Day 51's cache doing real work, because in a support channel the
> same question genuinely does arrive five times.
>
> **(2) `thread_key` collisions — the answered-twice bug.** If the session id is derived
> from the channel rather than the thread, two conversations share one session, and each
> one's history poisons the other. That is the "answered with someone else's context"
> symptom, and it is a *data* bug: in a support channel, one customer's details reaching
> another customer's thread is exactly the boundary `docs/DATA_BOUNDARY.md` exists to
> protect. Not a latency issue at all.
>
> **(3) Retries meeting an at-least-once surface.** Slack redelivers events it thinks you
> did not acknowledge — a slow reply becomes a redelivery, which becomes a second triage,
> which spends quota, which makes replies slower, which causes more redeliveries. Day 62
> built `processed_writes` for precisely this shape, and the intake surface is currently
> **outside** that protection. Acknowledge fast and process after — the acknowledgement and
> the work must be two different things.
>
> 💡 **The insight: a new intake surface does not add users, it changes the *arrival
> process*.** Everything upstream of it was designed against a workload that arrived one
> request at a time, from a trusted human, with unlimited think-time between requests. All
> three assumptions die at once, silently, on the day you connect a channel — and they
> present as slowness, which sends you optimising instead of re-deriving.
>
> The questions to ask before connecting *any* surface — put these in
> `docs/INTEGRATIONS.md` as a checklist, because this is the reusable artifact:
>
> 1. What is the maximum arrival rate, and what happens at 10×?
> 2. Does this surface deliver at-least-once? If yes, what is my idempotency key?
> 3. What is my conversation key, and can two conversations collide on it?
> 4. Who are these users, and what happens to one I cannot identify?
> 5. When I must refuse, what exactly do the humans see?
>
> Then fix what you found: per-surface cap, `thread_key` from the **thread** (test it with
> two concurrent threads in one channel), fast-ack + async processing, and the intake
> surface brought inside Day 62's idempotency guard. Re-run the busy-channel scenario —
> two threads at once, one duplicate delivery — and confirm one triage per request, no
> cross-thread contamination, and a refusal message a human would find acceptable.

## 6 · 🎤 Interview corner

1. **"How do people actually use your agent?"** — Until Day 91 they couldn't, and I'd say
   that plainly: everything went through my terminal or curl, which meant the whole system
   was designed against a workload of one trusted user with unlimited think-time. So I
   added an intake contract first — a frozen `IntakeRequest` with text, principal, thread
   key, surface and a reply callable — and converted the existing ambient trigger onto it,
   because a contract with one implementation is a guess. Then a real surface on top. The
   payoff is that `sutra/graph.py` didn't change for either surface, and adding email next
   is a day rather than a rewrite.
2. **"You wired up Slack. What surprised you?"** — Four things, and none of them were the
   API. Concurrency: my free-tier lane is about 5 requests a minute and a channel's arrival
   rate is other people's typing, so I needed a per-surface admission cap and an honest
   "I'm at capacity" rather than a queue that just makes waiting orderly. Threading: the
   session key has to come from the thread, not the channel — I had two conversations
   collide on one session, which isn't a latency bug, it's one customer's context appearing
   in another customer's thread. Delivery: Slack redelivers events it thinks you didn't
   acknowledge, so a slow reply becomes a duplicate triage; ack fast, process after, and
   bring intake inside the idempotency table I'd built on Day 62. And injection: a public
   channel is the widest possible untrusted-input surface, so the guardrail plugin has to
   be in that path. Which brings up the thing I'd actually lead with — the vendor snippet
   uses `InMemorySessionService` and builds a bare `Runner`. Copy it verbatim and you lose
   session persistence *and* every plugin in your stack, on the one surface where strangers
   type. Integration snippets are minimal by design, and minimal means your safety
   properties are absent. I diff any vendor snippet against my own composition root now.
3. **"Why Socket Mode rather than the Events API?"** — Direction of connection is a security
   property. The Events API needs Slack to POST to a public HTTPS endpoint, which on a
   laptop means a tunnel — a public URL pointing at an agent that has an archive and tools
   behind it. Tunnel URLs get found; scanners sweep those domains. Socket Mode has my
   process dial *out* over a websocket, so there's no listener to attack, no TLS to manage,
   and it works behind NAT. It's the same reasoning that put my MCP server on a
   loopback-only address inside the pod on Day 88: prefer outbound connections to inbound
   endpoints, and when you must accept inbound, authenticate before you spend anything.
