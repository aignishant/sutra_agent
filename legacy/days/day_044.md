connection out of sentiment. One policy object, one place — the same move as Day 40's

## 3 · 📚 Concepts

### MCP-22 — Deadlines, retries, and the idempotency line

**The delivery-rider story.** A rider takes your order to a food truck (Day 43's fleet).
Three things can go wrong on the way, and a professional rider has a rule for each:

| Mishap | Amateur rider | Professional rider |
| --- | --- | --- |
| The truck is slow | waits forever, dinner cold | waits a **fixed time**, then reports back (deadline) |
| The truck is closed | gives up | tries the next truck, waiting a bit longer each time, at most N times (bounded backoff + jitter) |
| Unsure if the order *arrived* before the mishap | orders again — maybe you get two dinners | re-orders **only** if re-ordering twice is harmless (idempotency) |

That third row is the one that separates seniors from juniors. `lookup_ticket("4521")`
twice = same answer, no harm: **idempotent**, retry freely. `close_ticket("4521")` twice =
maybe two closure emails to a customer: **not idempotent**, and a timeout is precisely the
moment you *don't know* whether the first attempt landed. So the honest policy is asymmetric:

- **Reads:** retry with backoff (bounded, jittered, logged).
- **Writes:** no automatic retry. Fail loudly upward — until the operation carries an
  **idempotency key** the server deduplicates on. (Sound familiar? Day 36's task handles
  are exactly that shape: `reindex_archive` twice returns the *same* running task. Phase 9
  makes idempotency keys standard for every write; today we draw the line and enforce it.)

And the backoff itself follows the house discipline you've had since Day 2's 429 wrapper:
respect any server-stated delay first, then 1→2→4→8s with jitter, then **escalate honestly**
— never fabricate a result (Principle 10, SEC-15 formalizes it on Day 72).

### MCP-23 — No held connections (and why caching replaced them)

Under the 2025 protocol a connection *was* state: your session lived on it, so you clung to
it, and reconnecting meant re-handshaking and re-fetching everything. Under 2026 rules the
protocol answered every reason you had for clinging:

| Why you held connections | The 2026 answer |
| --- | --- |
| "The session lives on it" | there is no session |
| "Re-fetching catalogs is expensive" | lists carry **`ttlMs` + `cacheScope`** — cache them; deterministic order keeps caches valid across reconnects |
| "Reconnect = re-handshake" | there is no handshake |
| "The server knows me" | it never did anything for you that `_meta` doesn't do per-request |

So the modern client treats transport as plumbing: open what a request needs, close it
cleanly (the adk.dev docs' exit-stack guidance — leaked connections are the new leaked
file handles), and let the **cache**, not the socket, carry the warm feeling. Even ADK
moved this way: 2.7.0's McpToolset "reuses the MCP server's tool list" instead of
re-fetching per need. Your client does the same, but by the server's own `ttlMs` — the
server tells you how long its word is good; believe it, no longer.

💡 **Mental model: cache the catalog, not the connection.** A socket remembers nothing
worth keeping; a catalog with a TTL is the server's signed promise, portable across any
number of reconnects.

Extend `sutra/mcp_client.py`:

```python
"""Day 44 additions — one client policy, applied to every MCP call."""
from __future__ import annotations

import random
import time
from dataclasses import dataclass

from sutra.logging_setup import get_logger            # Day 22 house rule

log = get_logger(__name__)


@dataclass(frozen=True)
class ClientPolicy:
    """Sutra's one answer to 'what does a call get to cost?'.

    Args:
        connect_timeout_s: max seconds to establish/launch a server.
        call_timeout_s: max seconds for ONE tool call to answer.
        max_retries: attempts AFTER the first, for idempotent calls only.
        backoff_base_s: first wait; doubles each retry; jitter added.

    Example:
        >>> DEFAULT.call_timeout_s
        30
    """
    connect_timeout_s: int = 10
    call_timeout_s: int = 30
    max_retries: int = 3
    backoff_base_s: float = 1.0


DEFAULT = ClientPolicy()

# The idempotency line, explicit and greppable. A tool not listed here
# is treated as a WRITE (safe default: no retry). Reviewed on Day 45.
IDEMPOTENT_TOOLS = frozenset({
    "lookup_ticket", "search_kb", "list_tables",       # pure reads
    "reindex_status",                                  # polling is a read
    "reindex_start",                                   # Day 36: claim-ticket dedup makes it safe
    # close_ticket is CONSPICUOUSLY absent — it's been our gated write
    # since Day 38 (confirmed=False), and §5 is about the day someone
    # tries to add it here.
})


def call_with_policy(call_fn, tool_name: str, policy: ClientPolicy = DEFAULT):
    """Run one MCP tool call under deadlines + the retry rules.

    Args:
        call_fn: zero-arg callable performing the actual call (built by
            the Day 33 client with policy.call_timeout_s applied to the
            transport — the SDK owns the timeout kwarg, Day 34's doc
            owns its verified name).
        tool_name: which tool — decides retry eligibility.
        policy: the ClientPolicy in force.

    Returns:
        The call's result.

    Raises:
        The last error, after retries are exhausted or immediately for
        non-idempotent tools — loudly, per trap #4 / Day 21.

    Example:
        >>> call_with_policy(lambda: client.call("search_kb", q="x"), "search_kb")
        {...}
    """
    retries = policy.max_retries if tool_name in IDEMPOTENT_TOOLS else 0
    for attempt in range(retries + 1):                # first try + retries
        try:
            return call_fn()                          # deadline enforced inside
        except Exception as err:                      # noqa: BLE001 — reraised below
            if attempt == retries:                    # budget spent (or write):
                log.error("mcp_call_failed", extra={  # narrate, then surface
                    "tool": tool_name, "attempts": attempt + 1, "error": str(err)})
                raise                                 # NEVER swallow (SEC-02)
            wait = policy.backoff_base_s * (2 ** attempt) + random.uniform(0, 0.3)
            log.warning("mcp_call_retry", extra={
                "tool": tool_name, "attempt": attempt + 1, "wait_s": round(wait, 2)})
            time.sleep(wait)                          # jittered, bounded, honest
```

Mirror-test in `tests/test_mcp_client_policy.py` — no server needed, `call_fn` is a stub:

```python
"""Day 44 — the retry line is enforced, not aspirational."""
import pytest
from sutra.mcp_client import ClientPolicy, call_with_policy

FAST = ClientPolicy(backoff_base_s=0.01)              # tests shouldn't sleep for real


def flaky(n_failures):
    """A stub that fails n times, then succeeds — and counts attempts."""
    state = {"calls": 0}
    def fn():
        state["calls"] += 1
        if state["calls"] <= n_failures:
            raise ConnectionError("boom")
        return "ok"
    return fn, state


def test_read_retries_and_recovers():
    fn, state = flaky(2)
    assert call_with_policy(fn, "search_kb", FAST) == "ok"
    assert state["calls"] == 3                        # 1 try + 2 retries

def test_write_fails_fast_no_retry():
    fn, state = flaky(1)
    with pytest.raises(ConnectionError):
        call_with_policy(fn, "close_ticket", FAST)    # not in IDEMPOTENT_TOOLS
    assert state["calls"] == 1                        # exactly ONE attempt

def test_retry_budget_is_bounded():
    fn, state = flaky(99)
    with pytest.raises(ConnectionError):
        call_with_policy(fn, "search_kb", FAST)
    assert state["calls"] == FAST.max_retries + 1     # then it STOPPED
```

## 5 · 💥 Failure lab — the retry that closed a ticket twice

> 🎬 **The scene:** `close_ticket(ticket_id, confirmed=…)` has been sutra-mcp's gated
> write since Day 38. A network blip times out a confirmed call. A well-meaning teammate
> adds `close_ticket` to `IDEMPOTENT_TOOLS` — "retries fixed the flaky reads, let's fix
> the flaky writes too."
> 😬 **The naive fix:** symmetric retries. One policy, no special cases, beautiful diff.
> 💥 **Why it fails:** a timeout is not a failure — it is an **unknown**. The first
> attempt may have fully succeeded and died on the way back. Retry now and the customer
> gets two "your ticket was closed" emails; with a payment tool it's money; with a delete
> it's data. And the ugliest part: the double-fire is *rare* — it needs a timeout on a
> success — so it passes review, passes tests, and detonates in month three as a support
> escalation you can't reproduce. Simulate it today: stub a `call_fn` that *succeeds* but
> then raises TimeoutError, and watch the symmetric policy execute it twice.
> 💡 **The insight:** **you may only retry what you can afford to accidentally do twice.**
> The asymmetry isn't a wart; it's the design. The path to retryable writes is not
> optimism but *engineering*: an idempotency key the server deduplicates on — Day 36's
> handle-dedup was the preview, Phase 9 makes it law for every write in the triage graph.
> Until a write carries that key, its timeout is escalated to something with judgment: a
> human, or the graph's error path. Never the retry loop.

## 6 · 🎤 Interview corner

1. **"Design the retry policy for an agent's tool calls."** — One policy object, three
   rules. Every call gets a deadline (connect + per-call). Idempotent reads retry on a
   bounded, jittered exponential backoff that respects server-stated delays first.
   Writes never auto-retry — a timeout is an unknown, not a failure, and you may only
   retry what you can afford to do twice — until the write carries an idempotency key the
   server dedups on. The idempotency set is an explicit, reviewed allowlist in code with
   a fail-fast test; the safe default for an unlisted tool is 'write'.
2. **"Why don't modern MCP clients keep long-lived connections?"** — Because the 2026
   protocol removed every reason: no session lives on the socket, no handshake to
   amortize, and catalogs are explicitly cacheable — list results carry `ttlMs` and
   `cacheScope` with deterministic ordering, so the *cache* carries continuity across
   reconnects instead of the connection. The client opens what a request needs, closes
   cleanly, and treats reconnection as a non-event. Cache the catalog, not the connection.
3. **"How did you test resilience without flaky tests?"** — Two layers. Unit: the policy
   is a pure function over a stubbed `call_fn`, so retry counts, fail-fast writes, and
   bounded budgets are exact assertions with near-zero sleeps. System: a chaos replay —
   two real server instances behind a dumb round-robin, kill one, run the full demo
   suite, and require zero caller-visible failures while the logs show the retries doing
   the absorbing. Determinism where I assert, chaos where I observe.
