## 1 · 🎬 Where we are — the story so far

Two days, two ways to run Sutra in someone else's building.

Day 97 handed Google a directory and got back a URL: Google decided how the container starts,
how it restarts, when it scales. Day 98 took all of that back — a bare Debian VM where "what
happens when the process dies" was a question with no answer until you wrote a `systemd` unit,
and where the failure lab was the moment a dropped SSH session turned into a full outage.

Both days have something in common that nobody has said out loud yet: **the record of what you
built is your shell history.** Day 97's service exists because you typed a command once. Nothing
in the repo says it should exist, what shape it should have, or how to make it exist again on a
different day, in a different project, on a machine that isn't this one. Delete it and the only
way back is to remember.

Today that changes. And the second half of today is about the tier above both of them — the
orchestrator, GKE — which this project documents carefully and *does not switch on*, because
the free grant there does not mean what its name suggests.

## 3 · 📚 Concepts

### DEPLOY-03a — What Terraform actually adds, in one sentence that isn't marketing

`gcloud run deploy` answers *"make this exist."* `terraform apply` answers a harder question:
***"make reality match this file, whatever reality currently is."*** That difference is the
entire product. The first is a verb you type; the second is a noun you keep.

💡 **Mental model:** Day 98's `systemd` unit was the same idea one layer down. `Restart=always`
is not a command to restart the process — it is a *declaration* that the process should be
running, plus a control loop that keeps making it true. Terraform is `systemd` for cloud
resources: `main.tf` is the unit file, `terraform apply` is `daemon-reload`, and the drift you
create by hand in §5 is exactly what `Restart=always` exists to undo.

`docs/deployment/05_terraform.md` §1 draws the same line to Kubernetes' reconciliation loop.
Three tools, three layers, one idea — worth noticing, because it is the most transferable
concept in this entire track.

### DEPLOY-03b — State is the product, and it is a secret

`terraform.tfstate` is Terraform's memory of what it created and the real-world IDs it got
back. Without it, `terraform destroy` does not know what to remove — which makes state, not the
`.tf` files, the thing whose loss actually costs you money on a zero-budget project.

⚠️ **And it can hold secrets in plaintext.** `05_terraform.md` §5 is explicit about this. For
today's config that risk is small (the API key stays a Secret Manager *reference*, per Day 97's
DEPLOY-01c discipline — the value never enters Terraform), but the `.gitignore` rule is
unconditional, because the next config might not be so careful:

```gitignore
.terraform/
*.tfstate
*.tfstate.*
*.tfvars
!*.tfvars.example
```

📌 This is Principle 9 ("secrets never touch git") applied to a file most people don't think of
as a secret. Step 3 adds these lines **before** the first `terraform apply`, not after — the
window where an un-gitignored state file gets swept up by an absent-minded `git add -A` is
exactly the window between `apply` and remembering.

### DEPLOY-03c — The thing Terraform cannot give this service, and Day 98 already had

Day 98's `adk api_server --session_service_uri="sqlite:///.../data/sessions.db"` gave Sutra
sessions that survive a restart, because a VM has a real disk. Today's Cloud Run service, no
matter how well declared, **cannot have that** — Cloud Run's filesystem is ephemeral and the
service scales to zero between requests, so a SQLite file written during one request is not
reliably there for the next.

💡 **The insight worth carrying:** declarative infrastructure describes the *shape* of a
deployment perfectly and says nothing about whether that shape can hold your data. A flawless
`main.tf` for a stateless platform is still a stateless platform. That gap is what Day 108
closes with a real external database — and it is why
`07_free_databases_and_extras.md` §1 exists as a file at all.

### DEPLOY-03d — Why GKE is parked, in the terms that actually matter

The Always-Free grant reads *"one Autopilot or Zonal cluster per month."* Read quickly, that
sounds like a free cluster. It is not. It waives the **cluster management fee** — the control
plane — and nothing else:

| What | Free? | What actually bills |
| --- | --- | --- |
| Cluster management fee, 1 cluster/month | ✅ waived | — |
| Autopilot workloads | ❌ | per-pod **requested** vCPU/memory/storage, from the moment a pod exists |
| Standard/Zonal node VMs | ❌ | ordinary Compute Engine instances — only *one* `e2-micro`/month is free, and Day 98 already spent that grant's shape on something better |

⚠️ **The trap is specific and worth naming:** Autopilot bills on what a pod *requests*, not what
it *uses*. A pod that requests 1 vCPU and idles at 2% bills for 1 vCPU. There is no
`--min-instances=0` here — an idle GKE workload is not a cheap GKE workload, which is precisely
the opposite of the intuition Day 97 just built.

**So §6 is a 🅿️ section.** Same discipline as Day 87: written to be interview-answerable and
run-ready, never run.

**Step 3 — write the four files.**

`infra/gcp/main.tf`:

```hcl
terraform {
  required_version = ">= 1.9"
  required_providers {
    google = { source = "hashicorp/google", version = "~> 6.0" }
  }
}

provider "google" {
  project = var.project_id
  region  = var.region
}

resource "google_cloud_run_v2_service" "sutra" {
  name                = "sutra-agent"
  location            = var.region
  deletion_protection = false

  template {
    scaling {
      min_instance_count = 0   # DEPLOY-01/03: the line that keeps this free
      max_instance_count = 2
    }

    containers {
      image = var.image_uri

      env {
        name  = "GOOGLE_GENAI_USE_VERTEXAI"
        value = "FALSE"        # DEPLOY-01b: never the billed Vertex path
      }

      env {
        name = "GOOGLE_API_KEY"
        value_source {
          secret_key_ref {
            secret  = "GOOGLE_API_KEY"   # a REFERENCE — the value never enters tfstate
            version = "latest"
          }
        }
      }

      resources {
        limits = { memory = "512Mi", cpu = "1" }
      }
    }
  }
}
```

| Block | What it does | Why it's written this way |
| --- | --- | --- |
| `required_version` / `required_providers` | pins Terraform and the provider | `05_terraform.md` §7 — an unpinned provider can change defaults between two `init`s, and defaults are where cost lives |
| `deletion_protection = false` | lets `terraform destroy` actually delete this service | ⚠️ the provider defaults this to **`true`** on Cloud Run v2; leave it out and Step 8's `destroy` fails with a confusing error. This is the most common first-run surprise with this resource |
| `min_instance_count = 0` | scale to zero between requests | the Terraform spelling of Day 097's `--min-instances=0`; still the line that keeps this inside the 2M-requests/month grant |
| `max_instance_count = 2` | hard ceiling on concurrency | bounds worst-case cost from a spike or a retry loop |
| `env { GOOGLE_GENAI_USE_VERTEXAI = "FALSE" }` | keeps ADK on the free AI Studio path | Day 097's DEPLOY-01b, now a reviewable line in a file rather than a flag someone might forget to type |
| `value_source.secret_key_ref` | injects the key from Secret Manager at runtime | DEPLOY-03b — a *reference* is what lands in `tfstate`, so the key itself never enters Terraform's state at all |

## 5 · 💥 Failure lab — when the file and the cloud disagree

> 🎬 **The scene:** the service is live and you want to try something. It's one flag. Typing
> `gcloud run services update` takes five seconds; editing `main.tf`, re-planning and
> re-applying takes a minute. You take the five seconds:
>
> ```powershell
> gcloud run services update sutra-agent --region=us-central1 --min-instances=1
> ```
>
> It works. The service stays warm. You move on and forget.
>
> 😬 **The naive read:** the cloud is the source of truth — the change is live, so it's real.
>
> 💥 **What actually happens, mechanically.** Run this a week later, for something unrelated:
>
> ```powershell
> terraform -chdir=infra/gcp plan
> ```
>
> ```
> ~ resource "google_cloud_run_v2_service" "sutra" {
>       ~ template {
>           ~ scaling {
>               ~ min_instance_count = 1 -> 0
>             }
>         }
>     }
> Plan: 0 to add, 1 to change, 0 to destroy.
> ```
>
> Terraform has not noticed "someone improved the service." It has noticed **drift** — reality
> disagrees with the file — and its entire job is to end that disagreement *in the file's
> favour*. The next `terraform apply` anybody runs, for any reason, silently reverts your
> change. On a `min-instances` flag that's a happy accident: it reverts *toward* free. On a flag
> someone changed for a real reason — a memory limit raised during an incident, a concurrency
> setting tuned under load — the same mechanism silently undoes the fix, at the worst possible
> moment, with nobody having typed anything that looks destructive.
>
> 💡 **The insight: adopting Terraform is not adding a tool, it is moving where truth lives.**
> Once `main.tf` exists, the console and the CLI become read-only surfaces. Every write goes
> through the file, or the file will eventually win an argument you didn't know you were having.
>
> ⚠️ **The sharper version of the same trap, specific to this track:** running
> `adk deploy cloud_run --service_name=sutra-agent` against a Terraform-managed service does the
> identical thing at larger scale — it replaces the whole revision, and the next `plan` shows a
> pile of changes nobody intended. That is exactly why Step 1 deleted `sutra-tmp` immediately and
> gave the Terraform-managed service a different name.

**The fix, and the correct habit:**

```powershell
# 1. See the drift explicitly, rather than discovering it inside an unrelated plan:
terraform -chdir=infra/gcp plan -refresh-only

# 2. Decide, deliberately, which side is right — then make it true in the FILE:
#    - the change was wrong  -> terraform apply   (reverts reality to match main.tf)
#    - the change was right  -> edit main.tf to match, THEN apply (a no-op plan proves you agree)
```

✅ *Verify (the actual test of today's lesson):* after you have reconciled, `terraform plan`
prints `No changes. Your infrastructure matches the configuration.` — the file and the cloud
agree, and *you* chose which one moved.

## 7 · 🎤 Interview corner

1. **"Why use Terraform if `gcloud run deploy` already works?"** — Because they answer different
   questions. `gcloud` answers "make this exist"; Terraform answers "make reality match this
   file, whatever reality currently is." The second buys review, reproducibility, and a reliable
   teardown — `terraform destroy` removes the orphans that manual console cleanup routinely
   misses, which on a zero-budget project is the highest-leverage habit there is.
2. **"What's the biggest operational risk of adopting Terraform?"** — Drift, and specifically
   *who* it surprises. Once a config exists, out-of-band changes get silently reverted by the
   next `apply` — and the person hurt is usually not the person who made the change. I
   reproduced it deliberately: a hand-run `gcloud run services update` showed up as a `1 -> 0`
   change in the next plan. The discipline that follows is that the console becomes read-only,
   and `plan -refresh-only` is how you look before you leap.
3. **"GKE's free tier gives you a cluster — why didn't you use it?"** — Because it doesn't. It
   waives the cluster management fee for one cluster a month; Autopilot then bills each pod's
   *requested* vCPU and memory, so an idle workload is not a cheap workload — the exact opposite
   of Cloud Run's scale-to-zero economics. For learning Kubernetes, `kind` locally is the same
   API at genuinely $0, so I documented GKE to be run-ready and deliberately didn't run it.
4. **"Where do secrets live in your Terraform?"** — Nowhere. The config stores a Secret Manager
   *reference*, so the value never enters `terraform.tfstate` — which matters because state is
   plaintext and does hold secrets by default for many resource types. I verified rather than
