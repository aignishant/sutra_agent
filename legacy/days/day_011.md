## 1 · 🎬 Where we are — the story so far

Sutra's tools are grown-up now (Day 10): self-declaring, status-speaking, honest about
`not_found`. But watch what happens after the agent finishes a triage: the answer scrolls
past in the terminal… and that's it. Ask a follow-up — "so which KB article was that
again?" — and the *model* may remember (it's in the session transcript), but **your
system** has no record. Nothing you could show a dashboard, hand to another agent, or
route a decision on. The result of all that machinery evaporates as prose.

There is also a subtler gap. Tools so far are **pure functions**: same input, same output,
no memory of the conversation they serve. Real desk tools aren't like that — "log this
triage result" or "what did we decide earlier?" only make sense *inside* a session. Tools
need a safe, offered-by-the-framework way to touch session data — without becoming global
variables with extra steps.

## 3 · 📚 Concepts

### ADK-12 — ToolContext: the waiter's notepad

**The story.** In our restaurant, the kitchen (your functions) has so far been sealed off:
orders in, dishes out, no idea what table they're for. But real restaurants run on the
**waiter's notepad** — table 4 is celiac, table 7 already got the bill. The notepad isn't
on the menu; customers can't order from it. It's *working state that travels with the
service*, and staff can read and write it.

`ToolContext` is that notepad, handed to your tool by the framework:

```python
from google.adk.tools import ToolContext

def record_triage(category: str, kb_id: str, tool_context: ToolContext) -> dict:
    tool_context.state["last_triage"] = {...}   # write on the notepad
```

| Restaurant | Our system | Technical name |
| --- | --- | --- |
| The waiter's notepad | per-session key-value data | `tool_context.state` (dict-like) |
| Staff-only — not on the menu | the model never sees the parameter | injection via the `ToolContext` **type annotation** |
| Notes that die with this one order | intra-turn scratch values | `temp:`-prefixed state keys |
| "Send table 4 to the manager" | control flags a tool can raise | `tool_context.actions` (e.g. transfer) |
| The pantry for big items | files that outlive turns | `load_artifact` / `save_artifact` — **Day 18's whole story** |

Three rules that keep the notepad from becoming chaos:

1. **The annotation is the magic.** Any parameter annotated `ToolContext` is filled by ADK
   and *stripped from the model-facing schema*. Check it yourself: the model's view of
   `record_triage` has two string fields, not three. (Day 4 taught you to read schemas —
   use that eye.)
2. **State is session-scoped.** New session, clean notepad. Cross-session memory is a
   different organ (Phase 7). Prefixes like `user:` and `app:` widen the scope — that's
   Day 17's deep dive; today we stay session-local.
3. **Structured values, same reason as Day 10's status dicts.** Write
   `{"ticket_id": "4521", "kb_id": "KB-104", ...}`, not a prose sentence. State is for
   *machines* first — dashboards, routers, other agents.

💡 **Mental model: tools got promoted today — from pure functions to session citizens.**
And the instruction can read the notepad too: `{last_triage?}` in an instruction template
injects the state value if present (verified on the llm-agents page) — model and tools now
share one working memory.

### AG-06 — Tool design: the checklist you earned

Four days of building tools (3, 4, 10, 11) compress into seven principles. Tape them up:

1. **One job, named honestly.** `lookup_ticket` looks up a ticket. A tool named
   `process_data` teaches the model nothing about when to call it.
2. **The docstring is when + how + example.** When to use it, what each arg means with an
   example value, what failure returns. (Day 10's failure lab is the proof.)
3. **Few, primitive parameters.** `ticket_id: str`, not `config: TicketQueryOptions`.
   Every extra field is another way to fill the form wrong.
4. **Status-dict returns; failure is a shape.** `{"status": "not_found", ...}` — the model
   branches, it doesn't interpret prose (Day 10).
5. **Return the needle, not the haystack.** A tool's return lands *in the context window*
   and is re-sent **every turn after**. Return what the reasoning needs, never a dump —
   today's failure lab measures the damage, Day 19 builds the theory (AG-08).
6. **Side effects go through the notepad, not globals.** State via `tool_context` is
   session-scoped, observable, and survives the framework's process model; a module-level
   variable is invisible, shared across sessions, and lies to you in production.
7. **Least privilege, from birth.** A tool that only needs to read should not be able to
   write. Cheap today, priceless when tools get real powers (SEC-10, Day 68).

🎬 A worked example of principle 1+3: we could have built one mega-tool
`ticket_op(action: str, payload: dict)`. It would "work" — and the model would guess
action names, misfill payloads, and every call would need a paragraph of docstring per
branch. Two small honest tools beat one clever generic one, every time a model is the
caller.

**Step 1 — two stateful tools + wiring (zero quota).**

Add to `sutra/adk_tools.py`:

```python
from google.adk.tools import ToolContext             # the notepad type (verified 2026-08-18)


def record_triage(category: str, kb_id: str, tool_context: ToolContext) -> dict:
    """Record the outcome of the CURRENT triage in session state.

    Call this exactly once per triage, AFTER you have identified the
    ticket's category and the KB article that explains it.

    Args:
        category: short category label, e.g. "auth", "billing", "outage".
        kb_id: the KB article id you cited, e.g. "KB-104".

    Returns:
        {"status": "recorded"} on success.
    """
    tool_context.state["last_triage"] = {            # write the notepad -
        "category": category,                        # structured, not prose:
        "kb_id": kb_id,                              # machines read this later
    }
    return {"status": "recorded"}                    # tiny return - nothing to dump


def recall_last_triage(tool_context: ToolContext) -> dict:
    """Return the most recent triage recorded in THIS session, if any.

    Use this when the user asks about "the last ticket", "that article
    again", or anything referring back to earlier triage work.

    Returns:
        {"status": "success", "last_triage": {...}} if one exists,
        else {"status": "empty", "message": "..."} - say so honestly.
    """
    last = tool_context.state.get("last_triage")     # read the notepad
    if last is None:                                 # nothing recorded yet?
        return {"status": "empty",
                "message": "No triage recorded in this session."}
    return {"status": "success", "last_triage": last}
```

def demo_stateful() -> None:
    """Two turns, ONE session: triage, then a follow-up answered from state.

    Usage:  python -m sutra.adk_tools stateful   (~4 model calls)
    """
    runner = InMemoryRunner(agent=triage_agent)

        app_name=runner.app_name, user_id="day11"    # ONE notepad for both turns
    )

    def turn(text: str) -> None:                     # tiny local helper: one user turn
        print(f"\nUSER: {text}")
        for event in runner.run(user_id="day11", session_id=session.id,
                                new_message=types.Content(
                                    role="user",
                                    parts=[types.Part(text=text)])):
            for part in (event.content.parts if event.content else []):
                if part.function_call:               # narrate the tool traffic
                    print(f"CALL: {part.function_call.name}({part.function_call.args})")
            if event.is_final_response() and event.content:
                print("ANSWER:", "".join(p.text or "" for p in event.content.parts).strip())

    turn(TRIAGE_QUESTION)                            # turn 1: full triage + record_triage
    turn("Which KB article did you use for that, and what category was it?")  # turn 2

## 5 · 💥 Failure lab — the tool that returns everything

> 🎬 **The scene:** "why should `search_kb` pick ONE article? More context is better,
> right?" You change it to return the **entire knowledge base** — every article, full
> text — and let the model sort it out.
> 😬 **The naive fix:** ship it. The triage answer is still correct, so nothing's wrong.
> 💥 **Why it fails:** look at what you can't see in the answer text. That giant return
> became a tool-result turn — so it now lives **in the transcript**, and Day 3's goldfish
> law says the transcript is re-sent on *every* subsequent model call, for the rest of the
> session. One lazy return = a per-turn tax forever after. On a metered lane that's your
> token budget on fire (Day 24 will price it exactly); worse, relevance drowns —
> the model quotes adjacent-but-wrong articles because you handed it a haystack and asked
> it to admire the needle. And you *feel* it: turns get visibly slower.
> 💡 **The insight:** **a tool's return value is a context-window purchase, paid in every
> later turn.** Return the needle. If the haystack must exist somewhere, that's what
> artifacts (Day 18) and retrieval (Day 49) are for — pointers over payloads. This scene
> is AG-06's principle 5 observed, and it's the doorway to context engineering (Day 19).

Run it: make `search_kb` return the whole KB → `python -m sutra.adk_tools stateful` →
watch latency and (if your Day 2 wrapper prints usage) token counts jump → revert.
~2 model calls.

## 6 · 🎤 Interview corner

1. **"How do tools share data with the session without becoming global variables?"** —
   The framework injects a context object — in ADK, a parameter annotated `ToolContext`
   that the model never sees. It exposes session-scoped state as a dict, control actions,
   and artifact I/O. The key properties globals lack: scoping (each session its own
   notepad), observability (state changes ride the event/actions stream as deltas), and
   survivability across the runtime's process model. I demoed a tool writing a structured
   triage record and a later turn reading it back.
2. **"Top three mistakes people make designing agent tools?"** — Generic mega-tools
   (`process(action, payload)` — the model guesses, badly); docstrings written for humans
   or not at all (the docstring *is* the model's manual — I've watched a one-line
   docstring degrade behavior with zero errors); and returning haystacks (every tool
   return is re-sent each turn after — I measured a whole-KB return slowing and degrading
   the session). My rules: one job, primitives, status dicts, needle-sized returns.
3. **"When state and chat history disagree, which should the agent trust?"** — State.
   History is prose the model wrote; state is structure a tool wrote. That's why my
   record_triage stores `{"category", "kb_id"}` instead of relying on the model
   remembering its own sentence — downstream automation branches on the structure, and
   the instruction can inject it explicitly with `{last_triage?}` templating.
