## 1 · 🎬 Where we are — the story so far

`sutra-mcp` is open for business — but it is a strange shop: **you can only ask the staff
to do things.** Want to know what ticket 4521 says? Call a tool. Want the KB article?
Call a tool. Every interaction burns a model decision ("should I call? with what
arguments?") even when the caller just wants to *read something that already exists*.

Real shops have more than a service counter. They have a **reading shelf** — material you
can pick up and read *without asking anyone* — and, by the register, **recipe cards**:
pre-written instructions the shop hands out so customers do things the house way.

MCP has both, and today `sutra-mcp` gets them: **resources** (the shelf: tickets and KB
articles as addressable, readable data) and **prompts** (the cards: a house-standard
triage prompt any host can request). With them lands the third leg of today, **MCP-09**:
knowing *which* of the three surfaces — tool, resource, prompt — a given capability
belongs on. That design judgment is what separates a server people enjoy using from a
junk drawer of tools.

## 2 · 🎯 Today's mission

Tonight `sutra-mcp` advertises all three capability types; the Inspector browses tickets
by URI; a raw `resources/read` request comes back with a `contents` array you can read
cold; and a missing ticket returns a *protocol error* — deliberately different from what
the tool returns, and you can explain why.

- **MCP-07** — resources: data with an address. URI schemes, `resources/list`,
  `resources/read`, and templates (`ticket://{ticket_id}`) for parameterized families.
- **MCP-08** — prompts: reusable, parameterized message templates served by name
  (`prompts/get`), so the *server* owns the house style of asking.
- **MCP-09** — the design line: tools **act**, resources **inform**, prompts **phrase** —
  choosing the right surface, plus the discovery/annotation metadata (`title`,
  `mimeType`, `audience`, `priority`) that makes capabilities *findable*.

## 3 · 📚 Concepts

### MCP-07 — Resources: data with an address

**The story.** The service counter (tools) requires staff for every request — slow,
model-mediated, one question at a time. The reading shelf changes the economics: every
item has a **label** (a URI), a **catalog** lists what's on the shelf, and *the customer
decides what to read*. No staff involved.

| The story | Our system | Technical name |
| --- | --- | --- |
| A label on each item | `ticket://4521`, `kb://logged-out` | the resource **URI** (any RFC-3986 scheme; `file://`, `https://`, or custom like ours) |
| The catalog | `resources/list` → uri, name, title, description, mimeType | discovery (paginated, cacheable: `ttlMs` + `cacheScope`) |
| Reading an item | `resources/read` → a `contents` array; each item carries `uri` + `mimeType` + `text` (or base64 `blob`) | retrieval |
| A shelf *section* label ("tickets, by number") | `ticket://{ticket_id}` in `resources/templates/list` | **resource templates** (RFC 6570 URI templates) |
| "New arrivals" bell | `subscriptions/listen` + `notifications/resources/updated` | change notifications (the 2026 shape — the old `resources/subscribe` RPC is gone) |

The deep difference from tools — engrave this — is **who decides**. Tools are
**model-driven**: the LLM chooses to call. Resources are **application-driven**: the
*host* (or its user) picks what context to load, and the spec explicitly leaves the how
to the application — a picker UI, a search box, or automatic selection. Same data, two
doors, different decision-makers.

💡 **Mental model: a tool is a verb the model may use; a resource is a noun the
application may read.**

Why Sutra needs the noun door: Phase 8's triage graph wants to *preload* "the ticket
being triaged" into context before any model call happens — no reason to spend a model
turn asking a tool for data whose address we already know. And Day 51's caching leans on
resources being cacheable *by design* (`ttlMs` on the read result — the server tells the
client how long the read stays fresh).

### MCP-08 — Prompts: the house recipe, served by name

**The story.** Sutra's triage prompt — persona, honesty rules, output shape — currently
lives inside Sutra's own code (Day 6's instruction). But other hosts will connect to
`sutra-mcp` (that is the point of Day 34!), and *they* don't know the house way of asking
about a ticket. A **prompt** is the recipe card by the register: the server publishes,
under a stable name, a parameterized message template; a host requests
`prompts/get` with arguments; back come ready-to-use `messages` (each `{role, content}`).

Concretely tonight: `triage_prompt(ticket_id)` returns the message Sutra's own Day 3
demo always asked — "Ticket 4521 came in. What is wrong?" plus the honesty framing —
so Claude Desktop, an IDE, or a partner agent triages *in Sutra's house style* without
copying Sutra's code. **Prompts are user/application-invoked** (think slash-commands in a
chat UI), completing the decision-maker triangle: tools = model decides, resources =
application decides, prompts = *user* decides.

### MCP-09 — Which surface? The design line (and being findable)

The junk-drawer anti-pattern: shipping *everything* as tools, because tools were learned
first. Cost: every data fetch burns a model decision + a schema + tokens for the tool
declaration, and hosts can't preload or cache what only a tool can reach.

The three-question test for any new capability on `sutra-mcp`:

| Question | If yes → | Tonight's examples |
| --- | --- | --- |
| Does it **change** anything, or need judgment about *whether* to do it? | **tool** | `lookup_ticket`? No — read-only. (Kept as a tool anyway for model-driven flows — a capability MAY have two doors; the *write* tools of Phase 6 must have exactly one.) |
| Is it **data with a stable address** someone may want without a model in the loop? | **resource** | `ticket://{id}`, `kb://{key}`, `archive://summary` |
| Is it a **way of asking** we want standardized across hosts? | **prompt** | `triage_prompt` |

Findability is the second half of MCP-09: `name` is for programs, `title` is for humans,
`description` is for the model/user deciding relevance, `mimeType` tells readers how to
parse, and `annotations` (`audience: ["user"|"assistant"]`, `priority: 0.0–1.0`,
`lastModified`) let a smart host filter and rank the shelf. Sparse metadata is how good
servers become invisible in a picker — Day 45's audit checks these fields like a librarian
checks spine labels.

```python
# ---------------------------------------------------------------------------
# Day 35: the reading shelf (resources) and the recipe cards (prompts).
# Tools ACT, resources INFORM, prompts PHRASE - one section per door.
# ---------------------------------------------------------------------------


@mcp.resource("archive://summary")               # a STATIC resource: fixed address
def archive_summary() -> str:
    """One-paragraph summary of the archive - a cheap 'what is here?' read.

    Returns:
        Counts of tickets and KB articles, as plain text.

    Example:
        >>> archive_summary()
        'Sutra archive: 3 tickets, 2 KB articles. Try ticket://4521.'
    """
    return (f"Sutra archive: {len(TICKETS)} tickets, {len(KB)} KB articles. "
            f"Try ticket://4521.")


@mcp.resource("ticket://{ticket_id}")            # a TEMPLATE: one label, a family
def ticket_resource(ticket_id: str) -> str:      # {ticket_id} binds to this argument
    """The raw text of one support ticket, addressable by URI.

    Args:
        ticket_id: the id inside the URI, e.g. '4521' in ticket://4521.

    Returns:
        The stored ticket text.

    Raises:
        ValueError: if no such ticket exists. NOTE the contrast with the
            lookup_ticket TOOL, which returns a polite sentence: resources
            speak to APPLICATIONS, so a miss must be a protocol error
            (-32602), never look-alike data. See doc section 5.

    Example:
        >>> ticket_resource("4521")
        'Title: Keeps getting logged out...'
    """
    if ticket_id not in TICKETS:                 # miss -> raise: the SDK converts
        raise ValueError(f"No ticket {ticket_id!r}")   # this into a JSON-RPC error
    return TICKETS[ticket_id]


@mcp.resource("kb://{key}")
def kb_resource(key: str) -> str:
    """One KB article by its key, addressable by URI.

    Args:
        key: the KB key inside the URI, e.g. 'logged-out'.

    Returns:
        The article text.

    Raises:
        ValueError: if the key is unknown (protocol error, as above).

    Example:
        >>> kb_resource("logged-out")      # exact keys: see KB in sutra/loop.py
        'KB-104: ...'
    """
    normalized = key.replace("-", " ")           # URI-friendly key -> dict key
    if normalized not in KB:
        raise ValueError(f"No KB article {key!r}")
    return KB[normalized]


@mcp.prompt()                                    # the recipe card by the register
def triage_prompt(ticket_id: str) -> str:
    """Sutra's house-standard way to ask for a ticket triage.

    Args:
        ticket_id: which ticket the host wants triaged.

    Returns:
        The user-role message text a host should send its model. (The SDK
        wraps this into the prompts/get messages shape - role + content.)

    Example:
        >>> triage_prompt("4521")
        "Ticket 4521 came in. Diagnose the likely cause using the ticket
        text and the knowledge base, cite any KB article you rely on, and
        say clearly if information is missing. Never invent contents."
    """
    return (
        f"Ticket {ticket_id} came in. Diagnose the likely cause using the "
        f"ticket text and the knowledge base, cite any KB article you rely "
        f"on, and say clearly if information is missing. Never invent contents."
    )
```

## 5 · 💥 Failure lab — the polite resource that lied to a program

> 🎬 **The scene:** consistency feels virtuous. Your `lookup_ticket` *tool* returns
> `"No ticket with id '9999'."` on a miss — the honesty rule that served you since
> Day 3 — so you make `ticket_resource` do the same: unknown id, return the polite
> sentence as the resource body. Symmetry!
> 😬 **The naive fix:** ship it. Every read "succeeds"; no error handling needed anywhere.
> 💥 **Why it fails:** tools talk to **models**; resources talk to **programs**. A model
> reads "No ticket with id '9999'" and understands. A program — a host preloading
> context, a cache, Phase 8's graph — sees `resources/read` return HTTP-happy success
> with a `text/plain` body and *files the apology as the ticket's contents*. Now the
> triage graph attaches "No ticket with id '9999'." to a customer reply as evidence; your
> cache stores it under `ticket://9999` until `ttlMs` expires; nothing anywhere ever
> notices, because nothing failed. The spec's authors met this exact goblin — that's why
> the resources page contains an explicit MUST NOT: *never return an empty (or
> look-alike) contents for a nonexistent resource*; return error `-32602`, so the miss is
> **machine-distinguishable** from data.
> 💡 **The insight:** **honesty has two dialects: readable prose for models, error codes
> for programs — and the surface you're on picks the dialect.** The same archive, the
> same missing ticket: the *tool* answers with a sentence (agent-visible data, Day 3's
> law), the *resource* raises (protocol error, today's law). Knowing which dialect a
> caller speaks is MCP-09 in one line.

Observed today, not just asserted: wire-lab ACT 4's error object next to Day 34's
Inspector run where the tool returned its polite sentence — one archive, two doors, two
correct answers.

## 6 · 🎤 Interview corner

1. **"Tools vs resources vs prompts — how do you decide?"** — By decision-maker and by
   verb-versus-noun. Tools are model-invoked verbs: anything that acts or needs judgment
   about whether to act. Resources are application-read nouns: data with a stable URI
   that a host may load into context with no model in the loop — listable, cacheable
   (`ttlMs`/`cacheScope`), templated (`ticket://{id}`). Prompts are user-invoked
   phrasings the server standardizes. In Sutra: `close_ticket` can only ever be a tool;
   the ticket text is a resource so the triage graph preloads it without burning a model
   turn; the house triage question ships as a prompt so foreign hosts ask the way we do.
2. **"How does a resource miss differ from a tool miss in your server, and why?"** — My
   tool returns a readable sentence ("No ticket with id '9999'") because its consumer is
   a model and honest *data* keeps the agent loop sane. My resource raises, and the SDK
   returns JSON-RPC `-32602` (accepting legacy `-32002` when I'm the client), because its
   consumer is a program, and programs distinguish miss from data only via error codes —
   the spec even forbids empty-contents-as-not-found precisely because it poisons caches
   and context loaders silently.
3. **"How do change notifications work for resources after the 2026 revision?"** — There
   is no standing session to push through, so the client opts in explicitly: it POSTs
   `subscriptions/listen` naming what it cares about (list changes, or specific URIs
   under `resourceSubscriptions`), and that request's own response stream stays open,
   carrying `notifications/resources/updated` tagged with a subscription id. The old
   `resources/subscribe` RPC and the free-floating GET stream are gone — one opted-in
   stream, everything else stateless.
