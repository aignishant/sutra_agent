## 1 · 🎬 Where we are — the story so far

Sutra is an image, and `docker compose up` puts three processes on one network. That is a
real deployment — but it is a deployment you *drive*. You typed `up`; if a container
dies, compose restarts it because you asked for `restart: unless-stopped`; if you close
the terminal, you own the consequences.

Today Sutra meets the other model: you stop describing what to *do* and start describing
what should be *true*, and something else spends the rest of its life making reality
match. That is the whole idea of Kubernetes, and it takes about forty lines of YAML to
meet honestly. Everything else — the ecosystem, the certifications, the 900-page books —
is built on that one sentence.

It also costs nothing. `kind` runs a genuine Kubernetes cluster inside Docker containers
on your laptop. Same API, same objects, same failure modes, no billing account. And the
second half of the day is the part that is actually about *agents*: the MCP server has
been a separate process since Day 33, and Kubernetes makes you decide, explicitly, how
close it lives to the agent that calls it.

## 3 · 📚 Concepts

### ADK-69 — Kubernetes is a thermostat, not a remote control

**The story.** A remote control sends *actions*: on, off, warmer. If someone else opens a
window, the remote does not care — it already did its job. A thermostat is given a
*desired state* — 20°C — and then spends all night measuring, comparing and correcting.
Nobody presses anything. If a window opens, the heating comes on, because the gap between
"what should be true" and "what is true" is the only thing the thermostat reacts to.

`docker run` is a remote control. Kubernetes is a thermostat. You hand it a document
saying "there should be one pod running this image, and it is healthy when this URL
returns 200", and a control loop compares that to reality forever. Delete the pod and it
comes back — not because deletion was blocked, but because one pod is now missing from
the desired state.

💡 **Mental model: you stop writing verbs and start writing adjectives.** Almost every
confusing thing about Kubernetes becomes obvious once you ask "which loop is trying to
make which sentence true?"

**The reference from `adk.dev/deploy/gke/` (read 2026-08-20).** The page ships a
`deployment.yaml` for an ADK agent. The fields that carry meaning:

| Field on the ADK reference | Value there | What Sutra does |
| --- | --- | --- |
| `replicas` | `1` | **`1`, with a comment naming Day 86's finding** — see below |
| `serviceAccountName` | `adk-agent-sa`, bound to `roles/aiplatform.user` via Workload Identity | ❌ not applicable — that binding exists so the pod can reach Vertex *without a key*. Sutra is AI-Studio-keyed (Addendum 02), so the key comes from a Secret |
| `imagePullPolicy` | `Always` | **`Never`** — the image is loaded into the node by hand (Step 3); `Always` is the single most common reason a local cluster sits in `ErrImagePull` |
| `resources` | 128Mi memory, 500m CPU, requests == limits | kept, but memory raised — a Python process with ADK, OTel and an httpx pool does not live in 128Mi |
| `containerPort` | `8080` | same — Day 86 already agreed to `$PORT` |
| Service `type` | `LoadBalancer`, port 80 → target 8080 | **`ClusterIP` + `kubectl port-forward`** — a LoadBalancer on kind has nothing to allocate, and this API still has no authentication (Day 85 §5) |
| env | `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION`, `GOOGLE_GENAI_USE_ENTERPRISE=true` | `GOOGLE_GENAI_USE_VERTEXAI=FALSE` + `GOOGLE_API_KEY` from a Secret — the zero-budget path (Addendum 02) |

Two of those rows are worth more than the manifest they came from:

**`replicas: 1` is a finding, not a default.** Day 86 scaled to two replicas and got three
bugs — double-spent quota, invisible approvals, a double `close_ticket`. In compose that
required a flag. In Kubernetes it is a one-character edit in a file that looks like
configuration, which someone will make in six months while tidying. So the number carries
its reason *in the file*, immediately above it. A `1` without a comment is an invitation.

**The service account row is the interesting absence.** On GKE the reference gets its
credentials from the *platform* — no key exists anywhere, the pod's identity is the
credential. Sutra cannot do that (no billing account), so it does the next-best thing: a
Kubernetes Secret, injected as env, never in the repo. Knowing *why* the good version is
better than yours is worth more in an interview than having the good version.

🅿️ **Parked:** `adk deploy gke` (Python only) does containerise, push, generate manifests
and apply them in one command, with `--service_type`, `--with_ui` and `--log_level`. It
needs a GKE cluster, which needs a project with billing. Write the command in
`deploy/k8s/README.md` with "never run — no billing account", same discipline as Day 87.

### The MCP sidecar — how close should the data boundary live?

Day 32 argued that the MCP server *is* the data boundary; Day 86 made that enforceable
with a read-only mount. Kubernetes now asks a sharper question: is `sutra-mcp` **another
container in the same pod** (a sidecar), or **its own Deployment behind its own Service**?

A pod is a group of containers that share a network namespace and a lifecycle. Same pod
means: they reach each other on `localhost`, they are scheduled together, they die
together, they scale together.

| | Sidecar (same pod) | Separate Deployment |
| --- | --- | --- |
| Address | `http://127.0.0.1:8000/mcp` | `http://sutra-mcp:8000/mcp` (DNS) |
| Exposed to the cluster network? | **No** — nothing else can reach it | Yes — any pod can call it |
| Scaling | 1:1 with the API, always | independent |
| Failure | one dies, both restart | independent, needs retries |
| Upgrades | atomic, one manifest | two lifecycles to keep compatible |

Sutra takes the **sidecar**, for a security reason rather than a convenience one: the MCP
server holds read access to the archive, and in the same pod it has *no cluster-visible
address at all*. There is no Service, no DNS name, no NetworkPolicy to get right — the
only process that can talk to it is the one sharing its network namespace. That is the
Day 32 boundary expressed as topology.

💡 **Mental model: a pod is a machine with several processes on it; the cluster is the
network between machines.** Put things in one pod when you would have put them on one
box; separate them when you would have bought a second box.

⚠️ And note what the sidecar choice *costs*: `sutra-mcp` now scales with the API and
cannot be updated independently. At real scale, with several agents sharing one archive
server, that is the wrong trade and it becomes a Deployment with a Service. Write that
sentence in the README — a decision without its expiry date is a decision that gets
cargo-culted.

### OPS-18 — kind, and the image that isn't there

`kind` ("Kubernetes IN Docker") runs each cluster node as a Docker container. Latest
release observed **v0.32.0**, default node image Kubernetes **v1.32.0** (2026-08-20 —
verify, Step 1). `k3d` (k3s in Docker) is the equally valid alternative: lighter, starts
faster, ships a built-in local registry; `kind` is the reference implementation the
Kubernetes project tests itself with. Either is fine — this doc uses `kind` and says so;
if you pick `k3d`, the only different commands are cluster creation and image import.

The one trap that catches everybody on day one:

> 🎬 **The scene:** you built `sutra-api:dev` five minutes ago. `docker images` shows it.
> You apply the Deployment and the pod sits in `ErrImagePull`, then `ImagePullBackOff`.
>
> 💥 **Why:** the cluster's nodes are *other containers*. They have their own image store.
> Your laptop's Docker daemon and the node's containerd are two different libraries, and
> the node — finding nothing locally — did the reasonable thing and asked Docker Hub for
> a public image called `sutra-api:dev`, which does not exist.
>
> 💡 **The insight:** `kind load docker-image sutra-api:dev` copies it in. Then
> `imagePullPolicy: Never` makes the mistake *loud* — the pod fails immediately with
> `ErrImageNeverPull` instead of silently pulling a stale registry copy. **Prefer the
> error that cannot be mistaken for success.**

```powershell
# Nothing here is written to a file, so nothing here can be committed.
Get-Content .env | Where-Object { $_ -match '^\s*[A-Z_]+=' } | ForEach-Object {
  $k,$v = $_ -split '=',2 ; Set-Item -Path "env:$k" -Value $v.Trim('"')
}
kubectl create secret generic sutra-secrets `
  --from-literal=GOOGLE_API_KEY=$env:GOOGLE_API_KEY `
  --from-literal=GROQ_API_KEY=$env:GROQ_API_KEY `
  --from-literal=OPENROUTER_API_KEY=$env:OPENROUTER_API_KEY

```

⚠️ **Say this out loud so you never mis-answer it:** a Kubernetes Secret is
**base64-encoded, not encrypted**. Anyone with `get secret` permission reads it in one
command. It is better than a file in git (RBAC applies, it is not in your history, and it
never lands in an image layer) and worse than a real secret manager. That is the honest
ranking, and Day 92's review gets the line.

**Step 5 — the Deployment, with the sidecar and the probes.**

`deploy/k8s/deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sutra-api
spec:
  # ⚠️ ONE. NOT A DEFAULT — A FINDING. Day 86 ran two replicas and got three bugs:
  # doubled quota spend (the ledger is a JSON file), approval verdicts invisible across
  # instances (SQLite WAL on a shared mount), and a double close_ticket (the Day 62
  # idempotency guard develops a race). See docs/DEPLOY.md §Statefulness.
  # Raising this needs Postgres + a shared quota counter FIRST.
  replicas: 1
  selector:
    matchLabels: {app: sutra-api}
  template:
    metadata:
      labels: {app: sutra-api}
    spec:
      containers:
        # --- the agent -------------------------------------------------------
        - name: api
          image: sutra-api:dev
          imagePullPolicy: Never          # loaded by `kind load`; fail loudly if missing
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef: {name: sutra-config}
            - secretRef:    {name: sutra-secrets}
          resources:
            requests: {memory: "512Mi", cpu: "250m"}
            limits:   {memory: "1Gi",   cpu: "1000m"}
          # Liveness = "is this process wedged?"  Restarting must be able to fix it.
          livenessProbe:
            httpGet: {path: /healthz, port: 8080}
            initialDelaySeconds: 20
            periodSeconds: 30
            failureThreshold: 3
          # Readiness = "should traffic come here?"  Restarting need NOT fix it.
          readinessProbe:
            httpGet: {path: /readyz, port: 8080}
            initialDelaySeconds: 5
            periodSeconds: 10
          volumeMounts:
            - {name: data, mountPath: /app/data}
        # --- the data boundary (Day 32), with no cluster-visible address -----
        - name: mcp
          image: sutra-api:dev            # one image, two commands (Day 86)
          imagePullPolicy: Never
          command: ["python", "-m", "sutra_mcp.server", "--http", "--port", "8000"]
          envFrom:
            - configMapRef: {name: sutra-config}
            - secretRef:    {name: sutra-secrets}
          resources:
            requests: {memory: "256Mi", cpu: "100m"}
            limits:   {memory: "512Mi", cpu: "500m"}
          volumeMounts:
            - {name: data, mountPath: /app/data, readOnly: true}   # kernel-enforced (Day 86)
      volumes:
        # ⚠️ emptyDir dies with the pod. See the failure lab — this is deliberate,
        # and deliberately temporary. A PersistentVolumeClaim is the next step.
        - name: data
          emptyDir: {}
```

```powershell

kubectl get pods -w        # Ctrl-C when it settles

```

## 5 · 💥 Failure lab — the probe that restarts a pod forever

> 🎬 **The scene:** the pod is green. You are tidying the manifest and you notice you have
> two probes pointing at two different endpoints, which looks like an oversight. So you
> make them consistent — one endpoint, less to maintain:
>
> ```yaml
>           livenessProbe:
>             httpGet: {path: /readyz, port: 8080}   # was /healthz
> ```
>
> Apply it. Everything is still fine, because your key is valid. Then, later — say you
> rotate the key, or the Secret gets applied to a fresh cluster before you export the new
> value — you come back to this:
>
> ```
> NAME                         READY   STATUS             RESTARTS   AGE
> sutra-api-7c9f6b8d4d-x2knp   1/2     CrashLoopBackOff   7          9m
> ```
>
> Seven restarts. The logs of the current container show a healthy uvicorn start and
> nothing wrong at all. `kubectl logs --previous` shows the same. The pod is being killed
> by something that leaves no trace in the application's own logs.
>
> 😬 **The naive fix:** the probe is "too aggressive" — raise `initialDelaySeconds` to 120
> and `failureThreshold` to 10. The restarts get further apart. It feels like progress.
>
> 💥 **Why it fails.** Nothing is slow. `/readyz` is returning **503 `no_api_key`** —
> correctly, deliberately, exactly as Day 86 Step 4 verified it should. Readiness is a
> *statement about traffic*: "do not send me requests, I cannot serve them." Liveness is a
> *statement about the process*: "I am wedged; kill me and a fresh one will be better."
>
> By pointing liveness at the readiness endpoint you told the kubelet that a missing API
> key is a wedged process. It is not. Restarting cannot produce a key. So the kubelet
> kills a perfectly healthy process, the new one comes up, reads the same empty
> environment, reports 503, and is killed again — a config problem converted into an
> infinite loop, with exponential backoff making it *look* like a flaky dependency.
>
> Worse, the loop destroys the evidence. Every restart wipes the `emptyDir` volume, so
> `data/sessions.db` and the approvals database are gone; and the crash-loop backoff means
> that when you *do* fix the key, the pod waits up to five minutes before trying again —
> so the fix appears not to work, and you go looking for a second bug that does not exist.
>
> Read it from the cluster rather than guessing, which is the transferable skill:
>
> ```powershell
> kubectl describe pod -l app=sutra-api | Select-String -Pattern "Liveness|Killing|Unhealthy|Last State|Exit Code" -Context 0,3
> kubectl get events --sort-by=.lastTimestamp | Select-Object -Last 15
> ```
>
> The application logs are silent because the application did nothing wrong. The *cluster*
> logs say `Liveness probe failed: HTTP probe failed with statuscode: 503` and
> `Killing container with a failed liveness probe`. **When a pod dies without an
> application error, the truth is in the events, not the logs.**
>
> 💡 **The insight: a liveness probe must only fail for something a restart can fix.**
> Deadlock, a leaked event loop, an unrecoverable memory state — yes. A missing key, a
> dependency that is down, a rate limit — no; those are readiness. The test is one
> question: *"if I restart this process, will the condition clear?"* If the answer is no,
> a liveness probe on it is a machine for turning an outage into a louder outage.
>
> This has a specific bite for agents. Sutra's `/readyz` (Day 85) checks the model
> provider. Put liveness on that and a **provider-side 429** — the thing Day 72 built
> backoff for, the thing that is *guaranteed* on a free tier — becomes a restart, which
> throws away every in-flight triage, every session in `emptyDir`, and every pending
> approval, and then retries the same rate-limited provider from a cold start. The
> free-tier project would take itself down on schedule.
>
> **Restore `livenessProbe: /healthz`**, re-apply, confirm the pod stops restarting, and
> add two lines to `deploy/k8s/README.md`: what each probe is allowed to check, and the
> one-sentence test above. Then fix the second thing the lab exposed — `emptyDir` — or at

## 6 · 🎤 Interview corner

1. **"Why Kubernetes if you're running one replica on a laptop?"** — Because the
   deliverable was the *description*, not the scale. Compose describes commands to run;
   Kubernetes describes a state to maintain, and I wanted the artifact that says "one pod,
   this image, healthy when `/readyz` returns 200" and then holds it — I proved the
   difference by deleting the pod and watching the controller replace it. It also forced
   three decisions compose let me avoid: where the MCP server lives topologically, what
   each health endpoint is allowed to mean, and where the API key comes from. And it cost
   nothing: `kind` runs a real cluster inside Docker, so the objects, the API and the
   failure modes are the same ones GKE has.
2. **"Sidecar or separate service for your MCP server?"** — Sidecar, and for a security
   reason rather than a convenience one. The MCP server owns read access to the archive —
   it *is* the data boundary in this design. In the same pod it shares the network
   namespace with the agent, so it is reachable on `127.0.0.1:8000` and has no
   cluster-visible address at all: no Service, no DNS name, nothing to get wrong in a
   NetworkPolicy. Its volume mount is `readOnly: true`, so the boundary is enforced by
   the kernel and not by intention. The cost is that it scales and upgrades in lockstep
   with the API, which is the wrong trade once several agents share one archive server —
   that is written in the README with the condition that would flip it, so the decision
   doesn't get cargo-culted.
3. **"Tell me about a probe that bit you."** — I unified my liveness and readiness probes
   onto `/readyz` because two endpoints looked redundant, and later hit
   `CrashLoopBackOff` with completely clean application logs. `/readyz` checks the model
   provider, so a missing API key returned 503, the kubelet read that as a wedged process
   and killed it — and restarting cannot conjure a key, so it looped forever, wiping the
   `emptyDir` volume each time and then backing off long enough that the real fix looked
   like it hadn't worked. The rule I took away: a liveness probe may only fail for
   something a restart can fix. Ask "if I restart, does this clear?" — deadlock yes,
   missing credential no, rate limit *definitely* no. That last one matters for an agent
   on a free tier: liveness on a provider check turns a routine 429 into a restart that
   discards every in-flight run and pending approval, so the system takes itself down
   exactly when it is already struggling. I also learned to look in the right place —
   when a pod dies with no application error, `kubectl describe` and the event stream have
   the answer, because the application didn't do anything wrong.
